### Title
`filter_preexisting_from_diff` masks new attacker-controlled `+` lines as pre-existing context via `.strip()`-equal removed lines, hiding malicious code from LLM review - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`filter_preexisting_from_diff` decides whether an added `+` line is "pre-existing" solely by comparing its `.strip()`-ed text against the set of `.strip()`-ed removed `-` lines [1](#0-0) . Since an attacker fully controls both the removed and added content of a Write-tool full-file rewrite, they can craft a removed line whose stripped text exactly equals a malicious added line's stripped text, causing the added malicious line to be converted to a context line (`' ' + content`) and removed from what the LLM reviewer sees as new code [2](#0-1) . The comment in the code explicitly acknowledges this as a "known imprecision" but treats it as an accepted trade-off backstopped by "the diff-review prompt's previous-findings recheck" [3](#0-2) .

### Finding Description
`filter_preexisting_from_diff(diff_files, cwd, baseline_sha)` is called from `security_reminder_hook.py` before diffs are handed to `analyze_code_security`/the Stop-hook LLM review pipeline [4](#0-3) . For each file's diff, it builds `removed_lines` as a **set** of `.strip()`-ed removed-line text and `added_lines` as a list of `.strip()`-ed added-line text [5](#0-4) . Any `+` line whose stripped content is a member of `removed_lines` is rewritten from `'+' + content` to `' ' + content` (i.e., demoted to unchanged context) [6](#0-5) .

Because the match is purely a **set membership check on stripped text**, and the attacker (via a full-file `Write` tool call, e.g. rewriting a file so git shows the entire old content removed and the entire new content re-added) controls every line on both sides of the diff, they can:
1. Include, among the "removed" lines, a padded/reindented line whose `.strip()` exactly equals their new malicious payload line's `.strip()` (e.g., removed: `"    os.system(cmd)  "`, added: `"os.system(cmd)"` — both strip to `"os.system(cmd)"`).
2. That new malicious `+` line then gets converted to a `' '`-prefixed context line and is excluded from the "NEWLY INTRODUCED in + lines" scope that the reviewer prompt is instructed to focus on [7](#0-6) .
3. The actual file on disk retains the malicious new code, unaffected by this text-only diff manipulation — only the diff seen by the reviewer is altered.

The one-removal-masks-N-additions property (`removed_lines` is a `set`, `added_lines` a list) makes this trivially repeatable: a single crafted removed line with common boilerplate text (e.g. a padded `pass` or a reformatted existing statement) can mask any number of unrelated added malicious lines that share the same stripped text.

Existing mitigations do not close this gap:
- The prompt-level rule "issues where the SAME pattern existed in the removed (-) lines and was re-added in + lines... is pre-existing" is *exactly* the rule this attack exploits — the LLM is explicitly told to treat such matches as pre-existing/rewritten code and not flag them [8](#0-7) .
- The "previous-findings recheck" backstop mentioned in the code comment only re-examines findings already surfaced in a prior fire of the same session [9](#0-8) ; it provides no coverage for a vulnerability that was never flagged in the first place because it was masked as context on its very first (and possibly only) review pass.
- The agentic reviewer's diff-intersect filter (`_intersects_diff`) is a *different, additive* mechanism used only in `agentic_review` (commit/push review path), and it operates on the same post-`filter_preexisting_from_diff` diff text — it does not re-derive additions independently of the masking, so a line already converted to context by `filter_preexisting_from_diff` is not distinguishable to it either [10](#0-9) .

### Impact Explanation
This is a genuine bypass of the plugin's core security-review guard: security-relevant new code introduced by an attacker (or an attacker-influenced agent turn, e.g. via a crafted Write-tool full-file rewrite) is silently converted to "pre-existing context" and is never surfaced to either the single-shot Haiku reviewer or (indirectly, through the shared diff-derivation) the agentic reviewer, while the vulnerable code remains live on disk. This matches the scoped impact: "security review guard bypass allowing malicious code changes to escape LLM-based detection."

### Likelihood Explanation
Preconditions are modest and match the stated threat model: the attacker needs to control both sides of a diff for a file, which is trivially satisfied whenever a full-file `Write` rewrite occurs (a very common editing pattern, especially by an LLM agent producing whole-file rewrites, or an attacker-crafted patch/PR content that gets applied via Write). No privilege escalation, secrets, or social engineering is required — only that the "removed"/"added" content of one commit/session-diff includes a benign-looking padded/reindented duplicate of the new payload text. The bug is deterministic and always reproducible given such a diff; it does not depend on any race, LLM randomness, or heuristic tuning of the reviewer prompt beyond the documented instruction to skip pattern-consistent rewrites.

### Recommendation
Do not use exact/stripped-text set matching to decide "pre-existing" for the purpose of suppressing new lines from the reviewed diff. Options:
- Only convert `+`/`-` pairs into context when they are matched positionally/by proximity (e.g., adjacent same-index lines in the hunk, or via a proper diff/line-alignment algorithm such as `difflib.SequenceMatcher`) rather than by an unordered set of stripped text across the whole file.
- Cap how many `+` lines a single removed line can mask (currently unbounded via set membership) and require a much closer match (e.g., normalized whitespace only, not full stripping of leading/trailing content) before masking.
- Regardless of masking for prompt-brevity purposes, always pass the full unmasked diff (or at least a flag identifying masked lines) to a secondary/independent check (e.g., the agentic reviewer's diff derivation) so that at least one review path sees genuinely new lines even when whitespace-based heuristics collapse them, closing the "never surfaced at all" failure mode.

### Proof of Concept
Unit test for `filter_preexisting_from_diff`:
```python
def test_filter_preexisting_does_not_mask_new_malicious_content():
    diff_content = (
        "@@ -1,2 +1,2 @@\n"
        "-    pass  \n"                 # benign padded removed line
        "-import os\n"
        "+import os\n"
        "+os.system(cmd)\n"             # NEW malicious line
    )
    # Craft: the malicious added line's stripped text equals the stripped
    # text of a differently-indented/padded removed line elsewhere in the file,
    # e.g. removed line "    os.system(cmd)  " and added "os.system(cmd)".
    diff_content_attack = (
        "@@ -1,3 +1,3 @@\n"
        "-    os.system(cmd)  \n"       # padded pre-existing-looking removed line
        "-import os\n"
        "+import os\n"
        "+os.system(cmd)\n"             # genuinely NEW malicious line (same stripped text)
    )
    diff_files = [("evil.py", diff_content_attack)]
    result = filter_preexisting_from_diff(diff_files, cwd=".", baseline_sha="deadbeef")
    _, filtered_diff = result[0]
    # Assert the malicious line is still present as an ADDITION ('+'-prefixed),
    # not demoted to context (' '-prefixed) or dropped.
    assert "+os.system(cmd)" in filtered_diff.splitlines(), (
        "Malicious new line was masked as pre-existing context and would "
        "never be surfaced to the LLM reviewer"
    )
```
Expected current (buggy) behavior: the assertion fails because `os.system(cmd)` is converted to `' os.system(cmd)'` (context), demonstrating the LLM reviewer never sees it as new code even though it is genuinely new in this diff.

    # Mechanical pre-existing filter: drop findings whose cited vulnerableCode
    # does NOT intersect any +-line in the diff. Investigate reads full files
    # and often flags pre-existing patterns in unchanged context; this is the
    # single largest false-positive source. String match on
    # normalized whitespace; keep if any non-trivial token from the cited code
    # appears on a +-line (lenient — only drops obvious unchanged-context hits).
    if os.environ.get("SG_AGENTIC_DIFF_INTERSECT") != "0":
        added = [ln[1:] for ln in diff_text.splitlines()
                 if ln.startswith("+") and not ln.startswith("+++")]
        removed = [ln[1:] for ln in diff_text.splitlines()
                   if ln.startswith("-") and not ln.startswith("---")]

        def _norm(s: str) -> str:
            return " ".join(t for t in " ".join(s.split()).split() if len(t) > 2)

        added_norm = _norm("\n".join(added))
        removed_norm = _norm("\n".join(removed))

        def _intersects_diff(cand: Dict[str, Any]) -> bool:
            vc_raw = " ".join(str(cand.get("vulnerableCode") or "").split())
            vc = _norm(vc_raw)
            if len(vc) < 8:
                return True
            # 1) vc 3-gram appears in + lines (original check, now symmetric norm)
            toks = vc.split()
            for i in range(max(1, len(toks) - 2)):
                if " ".join(toks[i:i + 3]) in added_norm:
                    return True
            # 2) any individual + line (≥8 chars) is contained in vc — handles
            #    "investigate cites whole block, diff added one list item"
            for ln in added:
                ln_n = _norm(ln)
                if len(ln_n) >= 8 and ln_n in vc:
                    return True
            # 3) deletion-aware: vc tokens match REMOVED lines and there are
            #    fewer + than - lines in the diff — vuln introduced by removing
            #    a guard. Keep so self-refute can adjudicate.
            if len(added) < len(removed):
                for i in range(max(1, len(toks) - 2)):
                    if " ".join(toks[i:i + 3]) in removed_norm:
                        return True
            return False
