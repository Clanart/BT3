### Title
SignableTransaction validates fee and weight against a transaction that omits the OP_RETURN output, so the signed transaction settles a lower effective fee rate than was validated - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` builds `tx_outs` including an optional `OP_RETURN` data output, then computes `weight`, `vbytes`, `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check using `calculate_weight_vbytes(tx_ins.len(), payments, None)` — which reconstructs a transaction from `payments` only and never includes the data output. The protocol validates one economic reality (fee rate and weight of a smaller transaction) and then settles another (the actual signed transaction commits, via `Prevouts::All` sighash, to the larger transaction whose real fee rate is lower). This is the same bug class as the Rhea exploit: a validation function that computes over a different structure than the one that settles, with no post-settlement recheck that the two agree. [1](#0-0) 

### Finding Description

At `send.rs:193-202`, the `OP_RETURN` output is pushed onto `tx_outs` before the fee/weight calculation at line 204:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62–127) rebuilds the transaction from `payments` — not from `tx_outs` — so the data output's ~11–92 serialized bytes (8-byte value + script encoding of up to 80 bytes of attacker-controlled `data`) are excluded from `vbytes`. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is undercounted by `fee_per_vbyte * (op_return_output_vbytes)`.
- The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same undercounted `vbytes`, so a transaction whose true vsize pushes it below the relay minimum still passes.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the undercounted `weight`.
- When `change` is present, the change branch recomputes with `calculate_weight_vbytes(..., Some(&change))` — still omitting the data output — so `fee_with_change` is undercounted by the same amount.

The actual fee paid is `sum(inputs) - sum(outputs)` (`fee()`, lines 138–141), i.e., exactly `needed_fee` (plus any sub-dust change), but the actual transaction is larger than the one the fee was sized for. Because `TransactionSignMachine::sign` commits to `Prevouts::All` over the real `tx` (lines 373–390), the threshold signature locks in the mismatch; nothing ever re-verifies that the signed transaction's effective fee rate meets `fee_per_vbyte` or the relay minimum. The change-output path has a second instance of the pattern: the `TooLowFee` check runs only against the no-change `vbytes`, and is never re-run after `fee_with_change`/`vbytes_with_change` replace them at lines 227–233. [2](#0-1) 

### Impact Explanation

`data` is attacker-influenced transaction data fed into `SignableTransaction::new` (the `Option<Vec<u8>>` data path is used for refund/instruction payloads that external depositors control). An attacker who causes a transaction to be signed with a large `data` payload while the coordinator selects a `fee_per_vbyte` near the relay minimum produces a fully-signed threshold transaction whose effective fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` — standard `bitcoind` rejects it with "min relay fee not met". The UTXOs are not lost, but the signed payout is unbroadcastable and the multisig must coordinate a fresh signing round with corrected parameters; repeated across payout batches this is a liveness/availability DoS on withdrawals. Even when the transaction remains relayable, every OP_RETURN-bearing transaction pays a systematically lower fee rate than the operator selected, degrading confirmation reliability. Severity: Medium (availability impact on signed transactions, no direct theft). [3](#0-2) 

### Likelihood Explanation

Any code path that passes `Some(data)` to `SignableTransaction::new` with a low fee rate hits this unconditionally — no racing or collusion required. The condition is met whenever `fee_per_vbyte` is at or near the minimum such that the ~10–92 omitted vbytes tip the true rate below 1 sat/vb, or whenever an operator relies on `needed_fee()` to predict the actual fee (the documented fee is `sum(inputs) - sum(outputs)`, which exceeds the predicted vsize-based rate). It is deterministic given the inputs, reachable purely through public transaction data.

### Recommendation

Compute `calculate_weight_vbytes` over the final `tx_outs` (including the OP_RETURN output) rather than `payments`, or add the data output's serialized size to `vbytes`/`weight` explicitly. Re-run the `TooLowFee` check against the final `vbytes`/`needed_fee` after the change-output decision, and after constructing the `SignableTransaction`, assert `self.fee() >= fee_per_vbyte * actual_vsize` so settlement is checked against what was validated.

### Proof of Concept

```rust
// In networks/bitcoin/tests/wallet.rs style, on regtest:
let data = vec![0u8; 80]; // max allowed, adds ~92 serialized bytes
let tx = SignableTransaction::new(
  vec![output],
  &payments,
  None,
  Some(data),
  1, // fee_per_vbyte at the relay minimum
).unwrap();
// Passes TooLowFee because vbytes excluded the OP_RETURN output.
// The produced tx's real vsize is ~92 bytes larger:
let actual_vsize = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < actual_vsize * 1);
// => effective fee rate < 1 sat/vb; bitcoind rejects send_raw_transaction
//    with "min relay fee not met", leaving the threshold-signed TX unbroadcastable.
```

        inputs: input_sat,
        payments: payment_sat,
