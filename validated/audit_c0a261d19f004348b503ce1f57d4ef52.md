### Title
ReceivedOutput deserialization accepts an unbound outpoint and TxOut - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an attacker-controlled scalar offset, `TxOut`, and `OutPoint` as three independent serialized fields, without verifying that the `TxOut` is actually the output referenced by the outpoint. This is analogous to validating a block header without verifying that its body-root matches its body.

### Finding Description
`ReceivedOutput` consists of `offset`, `output`, and `outpoint` fields. [1](#0-0)  Its deserializer simply decodes each field and returns the resulting object, performing no check that `outpoint.txid` and `outpoint.vout` resolve to `output`. [2](#0-1)  Outputs produced by the scanner have this binding implicitly because the scanner derives `outpoint` from the containing transaction’s `compute_txid()` and output index while copying the same indexed `TxOut`. [3](#0-2)  That invariant is lost when an attacker supplies serialized bytes to `ReceivedOutput::read`.

`SignableTransaction::new` then consumes the untrusted object as if this binding had been verified: it uses `input.output.value` as the available input amount, `input.outpoint` as the transaction input, and later preserves `input.output` as the prevout committed by the Taproot sighash. [4](#0-3) [5](#0-4)  The signing machine commits to all supplied prevouts with `Prevouts::All`, so a mismatched `TxOut` is incorporated into the signed sighash rather than discovered before signing. [6](#0-5) 

### Impact Explanation
An unprivileged party who can supply serialized `ReceivedOutput` data can cause an application to treat a real `OutPoint` as having an arbitrary amount or script. For example, the attacker can reference a real UTXO but encode a higher-value `TxOut`; the resulting object reports that inflated value and transaction construction accepts it as available input value, even though the referenced chain output contains less. Any resulting spend is not validly spendable: its Taproot sighash commits to the forged prevout amount/script, while Bitcoin consensus validates the signature against the actual UTXO.

This can produce funds reported as received which cannot actually be spent, incorrect balance/fee decisions, and signing attempts doomed to be rejected by the Bitcoin network. The primitive does not permit stealing the underlying key or forging a valid Bitcoin spend, so the issue is best classified as Medium rather than High.

### Likelihood Explanation
Exploitation requires an attacker to control or corrupt a serialized `ReceivedOutput` consumed by an application. The byte format is public and contains no authentication or consistency proof, so constructing mismatched data is straightforward. The attack does not require compromising a validator, Bitcoin RPC server, signing participant, or private key.

The likelihood depends on whether applications pass untrusted or externally synchronized serialized outputs into `ReceivedOutput::read`; if deserialization is used only for trusted local state produced by `Scanner`, this is not reachable. The exposed public read API nevertheless makes the invariant easy to violate at a trust boundary.

### Recommendation
Do not treat `ReceivedOutput::read` as sufficient validation. Prefer serializing only the scanner offset and `OutPoint`, then resolving the actual `TxOut` from the transaction identified by the outpoint before creating a spend. Alternatively, serialize the containing transaction or a committed proof with the output and verify `tx.compute_txid() == outpoint.txid` and `tx.output[outpoint.vout] == output` during deserialization.

If retaining the current format, add a separate explicit verification API and require it before using `value()`, constructing `SignableTransaction`, or reporting the output as spendable. Documentation should state that `read` performs syntax-only decoding and does not establish the outpoint-to-output binding.

### Proof of Concept
The following Rust test demonstrates the missing binding by serializing a mismatched `TxOut` and real `OutPoint`; it requires access to the private fields, so it belongs inside `networks/bitcoin/src/wallet/mod.rs` or its child test module:

```rust
#[test]
fn received_output_read_accepts_mismatched_outpoint() {
  let actual: ReceivedOutput = /* output returned by Scanner::scan_transaction */;
  let forged_output = bitcoin::TxOut {
    value: actual.output().value + bitcoin::Amount::from_sat(10_000),
    script_pubkey: actual.output().script_pubkey.clone(),
  };

  let mut encoded = actual.offset().to_bytes().to_vec();
  forged_output.consensus_encode(&mut encoded).unwrap();
  actual.outpoint().consensus_encode(&mut encoded).unwrap();

  let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
  assert_eq!(forged.outpoint(), actual.outpoint());
  assert_eq!(forged.value(), actual.value() + 10_000);

  // This is accepted as spendable input value despite the referenced UTXO
  // containing only `actual.value()`.
  let signable = SignableTransaction::new(
    vec![forged],
    &[(actual.output().script_pubkey.clone(), 1_000)],
    None,
    None,
    1,
  )
  .unwrap();

  assert!(signable.fee() > 0);
}
```

The constructed transaction references the genuine outpoint while committing to the forged prevout amount. Bitcoin Taproot validation compares that commitment with the actual UTXO, so the represented balance cannot be spent as reported.
