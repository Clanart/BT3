### Title
`ThresholdKeys::read` accepts inconsistent/attacker-chosen verification shares without validating them against the secret share, silently substituting the group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) deserializes `t`, `n`, `i`, the interpolation mode, the secret share, and all `n` verification shares purely from the input byte stream, then hands them to `ThresholdKeys::new`. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) checks only structural properties — the count and range of verification shares, and `t == n` for `Interpolation::Constant` — and then computes the group key as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` for `i in 1..=t` (crypto/dkg/src/lib.rs:376-378). It never checks that `secret_share * C::generator()` equals `verification_shares[i]`, nor that the verification shares form a consistent polynomial. The deserialized keys are therefore fully attacker-determined: an attacker who can feed bytes to `ThresholdKeys::read` can replace the entire verification-share vector (and hence `group_key()`) with keys of their own construction.

### Finding Description
This is the Serai analog of the Cockpit remote-file-inclusion bug class: a deserialization path accepts attacker-controlled content and installs it as trusted state without validating it against the trusted anchor. In Cockpit, an uploaded PHP file was treated as executable code; here, an uploaded key blob is treated as the node's threshold identity.

Specifically:

- `ThresholdKeys::read` reads an arbitrary `secret_share` scalar and an arbitrary `verification_shares` map of `n` points (lines 604-623), including shares for participants other than `i` — values this party never generated and cannot verify locally except by the consistency check that is missing.
- `ThresholdKeys::new` (line 377) derives `group_key` exclusively from `verification_shares[1..=t]`. Nothing binds that group key to `secret_share`.
- The only runtime tripwire is inside `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:487-494): if every returned share verifies against the (attacker-chosen) verification shares yet the aggregate signature fails against `view.group_key()`, it returns `InternalError`. But this check does not catch the real attack — if the attacker supplies a *self-consistent* fake (a known polynomial: their own `secret_share` and matching verification shares, with `group_key` set so the resulting address still receives funds, or set to an attacker-known key), signing succeeds normally under the substituted key set.

Because `group_key()` (line 445) is what downstream code (e.g., the Bitcoin `Scanner`/`p2tr_script_buf` in networks/bitcoin/src/wallet/mod.rs:80-86) uses to derive deposit addresses, substituting it changes where "received" funds are actually controlled.

### Impact Explanation
Two concrete impacts matching the accepted criteria:

1. **Funds reported received that are not spendable / are spendable by the attacker**: the attacker provides a `ThresholdKeys` blob whose `verification_shares` interpolate to a group key whose discrete log the attacker knows (e.g., all shares `x_j * G` for attacker-known `x_j` on a known polynomial). The scanner derives the deposit address from `group_key()`, deposits are confirmed and reported as received, but the key is the attacker's — or, if `secret_share` is left mismatched to `verification_shares[i]`, no valid signature can ever be produced and funds are frozen (only detectable at first attempted spend).
2. **Signing under an unintended key**: `AlgorithmMachine::new(algorithm, keys)` consumes the deserialized `ThresholdKeys` and produces valid FROST signatures for the attacker-chosen group key, so any protocol action gated on "the multisig signed this" can be redirected to a key outside the intended threshold set.

### Likelihood Explanation
Reachability requires attacker-controlled bytes to reach `ThresholdKeys::read` (listed as an in-scope untrusted-input sink). Compared to Cockpit this is narrower — it is a key-blob substitution rather than arbitrary code execution — but the missing check is unconditional: there is no code path in `read`/`new` that rejects a blob whose `secret_share` doesn't match `verification_shares[i]` or whose verification shares don't interpolate the claimed `group_key`. The only mitigation is the post-hoc `InternalError` at sign.rs:494, which fires only for *inconsistent* forgeries that nonetheless produce individually-valid shares — a self-consistent substitution never triggers it.

### Recommendation
In `ThresholdKeys::new` (or at the end of `ThresholdKeys::read`), add consistency validation:

- Verify `C::generator() * secret_share == verification_shares[i]` for the local participant `i`.
- For `Interpolation::Lagrange`, verify the group key independently: e.g., check that the set of verification shares lies on a degree-`t-1` polynomial (verify share `j` against a multiexp over shares `1..=t` for a few `j > t`), or document/require a binding transcript over the serialized blob.
- Consider committing `group_key` explicitly in the encoding and comparing it to the computed value, so a tampered share vector is caught at deserialization rather than at first signature.

### Proof of Concept
```rust
// Attacker constructs a self-consistent fake ThresholdKeys blob for a
// known secret, substituting the multisig's group key.
let t: u16 = 2; let n: u16 = 3; let i = Participant::new(1).unwrap();

// Known polynomial f(x) = a0 + a1*x, group key = a0 * G (attacker knows a0)
let a0 = <C as Ciphersuite>::random_nonzero_F(&mut OsRng);
let a1 = <C as Ciphersuite>::random_nonzero_F(&mut OsRng);

let mut blob = vec![];
blob.extend((C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes());
blob.extend(n.to_le_bytes());
blob.extend(i.to_bytes());
blob.push(1); // Interpolation::Lagrange
// secret_share for participant 1: f(1)
blob.extend((a0 + a1).to_repr().as_ref());
// verification shares f(j)*G for j = 1..=n
for j in 1u16 ..= n {
    let share = a0 + a1 * C::F::from(u64::from(j));
    blob.extend((C::generator() * share).to_bytes().as_ref());
}

let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// keys.group_key() == a0 * G — attacker knows a0, controls the "multisig" key.
// No error is raised: neither read() nor ThresholdKeys::new() checks that
// these shares came from the real DKG.
```

The fix requires binding the deserialized structure to its origin — absent that check, any byte-level substitution of the serialized keys silently rekeys the validator.
