Based on my investigation, this codebase has a directly analogous vulnerability in `BaseRewardPool`/`BaseRewardPoolV2`.

### Title
Reward donations instantly update `rewardPerTokenStored`, allowing sandwich-deposit theft of other stakers' rewards - ([File: rewards/BaseRewardPool.sol])

### Summary
`WombatPoolHelper.harvest()` is a fully permissionless, unprivileged-wallet-callable function that triggers `WombatStaking.harvest()`, which in turn calls `IBaseRewardPool(_rewarder).queueNewRewards(...)` for each configured rewarder [1](#0-0) , and reward tokens flow into `_provisionReward` which updates `rewardPerTokenStored` in a single atomic, stepwise jump proportional to the *current* `totalStaked()` at the moment the harvest lands [2](#0-1) . There is no vesting/streaming of the newly queued rewards and no deposit cooldown in `MasterMagpie.deposit`/`WombatPoolHelper.deposit`, so anyone can front-run a pending harvest with a large `deposit`, receive their pro-rata share of the entire freshly-donated reward the instant it lands, and immediately `withdraw` right after, exactly the "stepwise donation sandwich" pattern described in the report for `UpliftOnlyExample`.

### Finding Description
`_provisionReward` in `BaseRewardPool.sol`/`BaseRewardPoolV2.sol` adds `_amountReward` into `rewardInfo.rewardPerTokenStored` divided by `this.totalStaked()` at the time of the call [2](#0-1) . This function is reached via `queueNewRewards`, which is called by `WombatStaking._sendRewards` during harvest flows [3](#0-2) , and harvest itself is externally callable without restriction through `WombatPoolHelper.harvest()` [1](#0-0) .

Because `earned`/`rewardPerToken` accounting in `BaseRewardPool` is checkpointed per-account only on deposit/withdraw/claim (via `userRewardPerTokenPaid`), and there is no minimum staking duration, delay, or streaming/vesting mechanism for newly provisioned rewards, a wallet can:
1. Observe a pending, harvestable reward accrued in `WombatStaking` (e.g. `pendingWom()` reported by `WombatPoolHelper.pendingWom()` [4](#0-3) ) that is about to be distributed via `queueNewRewards`.
2. Deposit a large stake into `MasterMagpie` right before the harvest transaction (`WombatPoolHelper.deposit` → `MasterMagpie.depositFor`) [5](#0-4) .
3. Let (or trigger) the harvest happen, instantly capturing a large pro-rata share of `rewardPerTokenStored`'s stepwise jump, diluting the share that should have accrued to genuine long-term stakers.
4. Immediately withdraw right after, walking away with reward tokens they did not economically earn, at the expense of existing stakers.

This mirrors the report's root cause exactly: instantaneous, non-vested donation/injection of value into a pooled accounting variable (`rewardPerTokenStored` here, vs. pool BPT value in the original report) that is shared pro-rata by current balance, with no timelock protecting against transient deposits timed around the donation event.

### Impact Explanation
This results in theft of unclaimed yield from existing/legitimate stakers by an unprivileged attacker who deposits and withdraws around a harvest/donation event, redirecting rewards that should have accrued over time to those who staked before the reward was earned. This qualifies as direct theft of user funds (unclaimed yield) as defined in the validation criteria.

### Likelihood Explanation
Harvest calls are permissionless and their timing/pending amounts (`pendingWom()`) are observable on-chain in advance, so any wallet can time a large deposit immediately before a harvest and withdraw immediately after, requiring no privileged access, MEV infrastructure beyond ordinary mempool front-running, or race-condition luck beyond standard transaction ordering (or same-block bundling where available). The larger the pending, un-harvested reward relative to existing `totalStaked()`, the more profitable the attack, similar to the "large whale/large fee donation" scenario in the original report.

### Recommendation
Introduce a linear reward-streaming/vesting mechanism for newly provisioned rewards in `_provisionReward` (release the `_amountReward` gradually over a fixed duration rather than instantly updating `rewardPerTokenStored`), or add a minimum stake duration / deposit cooldown before a user's share of newly queued rewards becomes claimable, so that the reward accrual window cannot be sandwiched by transient deposits.

### Proof of Concept
1. Attacker monitors `WombatPoolHelper.pendingWom()` for a pool with a large pending, un-harvested WOM reward amount relative to current `totalStaked()` [4](#0-3) .
2. Attacker calls `WombatPoolHelper.deposit(largeAmount, minLiquidity)` → `MasterMagpie.depositFor` immediately before the harvest transaction lands [5](#0-4) .
3. Attacker (or anyone) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest` → `_sendRewards` → `IBaseRewardPool.queueNewRewards`, which instantly boosts `rewardPerTokenStored` based on the attacker-inflated `totalStaked()` [6](#0-5) [2](#0-1) .
4. Attacker immediately calls `WombatPoolHelper.withdraw(largeAmount, minAmount)`, claiming their inflated share of `earned()` reward that accrued from the just-added stake, then exits the pool having captured value diluted from genuine long-term LPs.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
