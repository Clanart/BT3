## Title
Malicious/MITM remote can spoof a `WWW-Authenticate: realm="GitHub"` header to force Desktop's credential-helper into an unauthenticated Enterprise sign-in flow for an attacker-controlled endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The bug-class seed is "an attacker-controlled response manipulates a value used purely for internal trust/accounting decisions, and the code trusts that value without validating the origin it came from." In `VeryFastRouter`, the unvalidated pair's return value corrupts `ethAmount` accounting. The closest verified analog in this Desktop codebase is `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts:137-179`, which classifies a remote endpoint as GitHub Enterprise based on an HTTP response header that is fully controlled by whatever server git is talking to, and that classification drives whether Desktop pops the real GitHub sign-in UI for that endpoint.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's trampoline credential helper (`createCredentialHelperTrampolineHandler`) with the credential fields Git captured for that request, including any `wwwauth[...]` entries taken verbatim from the server's `WWW-Authenticate` response header: [1](#0-0) 

`getEndpointKind` trusts this attacker/server-supplied header to decide the endpoint's trust class: [2](#0-1) 

If the realm string contains `GitHub`, the endpoint is classified `'enterprise'` — with no proof the host is actually a GitHub Enterprise server (no TLS/host verification against GitHub's server certificate fingerprint, no API probe corroboration at this branch — that only happens in the fallback path via `isGitHubHost`). This is directly analogous to `VeryFastRouter::swap` trusting the return value of an unvalidated pair contract to update accounting (`ethAmount`) — here, the untrusted "return value" is an HTTP header from an arbitrary remote, and it is used to decide the app's authentication trust boundary.

That classification then flows into `getCredential`: [3](#0-2) 

If `endpointKind !== 'generic'` and no existing account matches, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which shows the real GitHub Sign-In dialog (`PopupType.SignIn`) and, for a non-`github.com` hostname, invokes `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` using the attacker-controlled `endpoint`: [4](#0-3) 

This means a user who simply clones/fetches/pushes to a URL pointing at an attacker's server (or a MITM proxy sitting in front of one) — with no unusual user action beyond a normal remote operation — can be shown Desktop's legitimate-looking "Sign in to GitHub Enterprise" flow pre-populated with the attacker's origin as the "enterprise" endpoint. Because the existing guards (`isDotCom`, `isGHE`, and the account-store lookup checks) only *short-circuit early* for known-good hosts, and only fall back to a real API probe (`isGitHubHost`) when there is no `wwwauth[]` header claiming a GitHub realm, an attacker who controls the server side of the connection can bypass that probe entirely by simply sending the crafted header. There is no verification tying the `realm="GitHub"` string to an actual GitHub Enterprise Server instance before triggering the sign-in UI.

### Impact Explanation
The attacker's endpoint becomes registered as the enterprise "sign-in endpoint" and the OAuth/PAT sign-in dialog is shown against it. Depending on how `beginEnterpriseSignIn`/`setSignInEndpoint` resolve the OAuth authorize/token endpoints for a non-dotcom host (typically derived from the same origin), an unsuspecting user could complete an authentication flow that sends credentials/tokens to the attacker's server, or Desktop could persist the attacker's endpoint as a trusted enterprise account entry. At minimum this is a credential/token-phishing primitive triggered purely by the server's HTTP response to a normal Git network request — not by any social engineering step beyond the ordinary "clone/fetch this repo" action a Desktop user routinely performs.

### Likelihood Explanation
Likelihood is medium: the attacker needs to control (or MITM) the git remote endpoint the victim connects to, which is squarely in-scope per the task's "attacker controls ... a git remote/proxy response" criterion. Setting a custom `WWW-Authenticate` header on an HTTP 401 response is trivial for any server operator and requires no special conditions on the victim's machine, no local access, and no prior credential compromise.

### Recommendation
Do not let an unauthenticated `WWW-Authenticate` realm string alone elevate an endpoint's trust classification enough to trigger the GitHub/Enterprise sign-in UI. Require corroboration via an actual capability/API probe (as already done via `isGitHubHost`) or via TLS certificate/known-host pinning before trusting the `wwwauth[]`-derived classification, and clearly surface the exact origin being signed into (including scheme/host) so users can recognize an unexpected sign-in target.

### Proof of Concept
1. Stand up an HTTPS server at `https://attacker.example` (or MITM an HTTP git remote) that responds to unauthenticated Git HTTP requests with `WWW-Authenticate: Basic realm="GitHub Enterprise"`.
2. In GitHub Desktop, clone or fetch `https://attacker.example/foo.git` as a normal remote.
3. Git invokes the credential helper trampoline; `command.stdin` contains the `wwwauth[...]` entry with `realm="GitHub"` substring, matched at `app/src/lib/trampoline/trampoline-credential-helper.ts:159-161`.
4. `getEndpointKind` returns `'enterprise'`; since no account exists for `attacker.example`, `getCredential` calls `ui.promptForGitHubSignIn('https://attacker.example')` (`trampoline-credential-helper.ts:118`).
5. `promptForGitHubSignIn` opens the real Sign-In dialog and calls `beginEnterpriseSignIn` / `setSignInEndpoint(origin)` for `https://attacker.example` (`trampoline-ui-helper.ts:91-92`), presenting the user with what looks like a legitimate GitHub Enterprise sign-in flow scoped to the attacker's server.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
