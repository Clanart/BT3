### Title
`Verifier::is_deposit_valid` never checks the deposit UTXO is unspent, letting an attacker get N-of-N signatures on a move_to_vault_tx spending an already-consumed deposit output - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` (`core/src/verifier.rs:541-731`) validates a deposit outpoint by fetching the deposit *transaction* with `self.rpc.get_tx_of_txid(&deposit_txid)` and checking that `deposit_txout_in_chain.value == bridge_amount` and the script pubkey matches, but it never checks whether that specific output is still unspent (e.g. via `rpc.is_utxo_spent`/`get_tx_out`). Because the recovery path of the deposit address (`TimelockScript`, script index 1 in `deposit_data.get_deposit_scripts`) can be spent unilaterally by the depositor after `user_takes_after` blocks, an attacker can spend the deposit output via that path and then still pass `deposit_sign`/`deposit_finalize` for the same `deposit_outpoint`, causing verifiers to produce N-of-N partial signatures for a `move_to_vault_tx` that spends a UTXO which no longer exists.

### Finding Description
The binding the protocol relies on is: *for every deposit_outpoint that verifiers N-of-N sign a move_to_vault_tx for, the outpoint's txout must be currently unspent and equal to exactly one `bridge_amount` deposit UTXO* — i.e. `deposit_outpoint.is_unspent() == true` at the moment `deposit_sign`/`deposit_finalize` run.

`is_deposit_valid` (`core/src/verifier.rs:659-705`) implements only:
- `deposit_tx = rpc.get_tx_of_txid(deposit_txid)` — this returns the historical transaction data (which is immutable once mined), not the current UTXO-set state.
- `deposit_txout_in_chain.value != bridge_amount` → reject
- `deposit_txout_in_chain.script_pubkey != expected_scriptpubkey` → reject
- confirmation height ≥ `start_height` → reject

There is no call to `rpc.is_utxo_spent(&deposit_outpoint)` (defined in `crates/clementine-extended-rpc/src/client.rs:356`) or equivalent `get_tx_out` check anywhere in `is_deposit_valid`, and `deposit_sign`/`deposit_finalize` (`core/src/verifier.rs:866-994`) both call only `is_deposit_valid` before proceeding to sign. `create_nofn_sighash_stream` (`core/src/builder/sighash.rs`) similarly never checks UTXO spentness — it only builds the transaction graph and sighashes deterministically from `deposit_data`.

The deposit address is constructed from two script paths (`core/src/deposit.rs:176-205`, `core/src/builder/address.rs:45-67`): script index 0 is `BaseDepositScript` (N-of-N spend path used by `create_move_to_vault_txhandler`, `SpendPath::ScriptSpend(0)` at `core/src/builder/transaction/mod.rs:330`), and script index 1 is `TimelockScript` with the user's recovery key and `user_takes_after` relative timelock. The depositor controls the recovery key and can unilaterally spend via the `TimelockScript` path once `user_takes_after` blocks have passed (confirmed spendable in `core/src/builder/script.rs:905-941`, `test_timelock_script_spendable`).

Exploit flow:
1. Attacker sends `bridge_amount` BTC to their own deposit address (`generate_deposit_address`), recording `deposit_outpoint`.
2. Attacker waits `user_takes_after` confirmations, then spends the deposit output via the `TimelockScript` recovery path to any address they control. This is now a normal, confirmed Bitcoin transaction; the historical `deposit_tx` is still fully valid and unchanged on chain.
3. Attacker calls `new_deposit` on the aggregator's public gRPC (unauthenticated) with the same `deposit_outpoint` and an EVM address.
4. Each verifier's `deposit_sign`/`deposit_finalize` calls `is_deposit_valid`, which only re-reads the *original* deposit transaction's output value/script/confirmation height — all of which still pass, because these are immutable facts about the mined transaction, not about current spent-ness.
5. Verifiers proceed to generate nonces and issue MuSig2 partial signatures over the `move_to_vault_tx` sighash for an outpoint that Bitcoin's UTXO set no longer contains.

Existing guards do not catch this: `insert_deposit_data_if_not_exists` (`core/src/verifier.rs:880-886`) only prevents *re-signing a different* deposit for the same outpoint, not spent-state validation. `check_nofn_correctness` (Citrea client check) validates only the N-of-N key, unrelated to UTXO liveness. No component in the signing path queries `is_utxo_spent`/`get_tx_out` for the deposit outpoint.

### Impact Explanation
The resulting `move_to_vault_tx` can never be broadcast successfully — Bitcoin nodes will reject it as a double-spend since the input is already consumed. So no BTC actually moves and no false Citrea credit is issued as a direct consequence of this specific signing round. However, this exactly matches the listed Critical category "N-of-N partial signatures produced for a spend no Citrea withdrawal authorises": verifiers reveal MuSig2 partial signatures (and by extension nonce/session cooperation) for a transaction spending a UTXO that is no longer part of the bridge's valid deposit set. This is repeatable per-deposit by any unprivileged user who deposits, self-spends via the timelock recovery path, and then calls `new_deposit` again on the same outpoint — no verifier, operator, or aggregator privilege is required, and it does not depend on a majority-hashrate or key-compromise assumption.

### Likelihood Explanation
Preconditions: the attacker only needs to (a) deposit `bridge_amount` BTC to a deposit address they generate for themselves (as any user can), (b) wait `user_takes_after` confirmations (a paramset value, feasible on regtest/testnet and on mainnet at moderate BTC/fee cost — only the deposit amount plus timelock spend fee), (c) call the aggregator's unauthenticated `NewDeposit` gRPC endpoint with the already-spent `deposit_outpoint`. All of this is within the stated unprivileged attacker capability (broadcast BTC txs, deposit into the bridge, call aggregator gRPC). It is fully repeatable across deposits and does not depend on any other actor's misbehavior.

### Recommendation
In `Verifier::is_deposit_valid` (`core/src/verifier.rs`), after confirming the deposit tx's output value/script/height, add an explicit unspent check on `deposit_outpoint` (e.g. `self.rpc.is_utxo_spent(&deposit_outpoint)` or `get_tx_out(deposit_txid, vout)` returning `Some`) and reject with `BridgeError::InvalidDeposit` if the output is already spent. This check should be re-run in both `deposit_sign` and `deposit_finalize` (both already call `is_deposit_valid`, so fixing it there covers both) immediately before any nonce/signature is produced, and ideally re-verified again right before final signature verification in `deposit_finalize` to close any race between initial validation and final signing.

    /// Checks if an UTXO is spent.
    ///
    /// # Parameters
    ///
    /// * `outpoint`: The outpoint to check
    ///
    /// # Returns
    ///
    /// - [`bool`]: `true` if the UTXO is spent, `false` otherwise.
    ///
    /// # Errors
    ///
    /// - [`BitcoinRPCError`]: If the transaction is not confirmed or if there
    ///   was an error retrieving the transaction output.
    pub async fn is_utxo_spent(&self, outpoint: &OutPoint) -> Result<bool> {
        if !self.is_tx_on_chain(&outpoint.txid).await? {
            return Err(BitcoinRPCError::TransactionNotConfirmed);
        }

        let res = self
            .get_tx_out(&outpoint.txid, outpoint.vout, Some(false))
            .await
            .wrap_err("Failed to get transaction output")?;

        Ok(res.is_none())
    }
