### Title
`SignableTransaction` omits the OP_RETURN data output from weight/vsize/fee and standardness accounting - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` computes transaction weight, vbytes, `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check using `calculate_weight_vbytes`, which builds its template transaction only from the payment outputs plus an optional change output. The OP_RETURN output carrying up to 80 bytes of caller/attacker-influenced `data` is pushed onto the real transaction's output list (lines 194-202) before the fee/weight calculations run (lines 204-227), yet it is never included in the template. The derived "rate" of the transaction (fee-per-vbyte and total weight) is therefore computed on incomplete state — directly analogous to BEVO's `getRate()`/`balanceOf` being driven by an accounting variable that had been skewed — producing a transaction that is larger and pays a lower effective fee rate than all the code's own checks assume.

### Finding Description
`calculate_weight_vbytes` (send.rs:62-127) constructs a `Transaction` whose outputs are `payments` plus an optional `change` output only:

```rust
// networks/bitcoin/src/wallet/send.rs
output: payments
  .iter()
  .map(|payment| TxOut { value: Amount::from_sat(payment.1), script_pubkey: payment.0.clone() })
  .collect(),
```

In `new` (send.rs:194-235) the data output is appended to `tx_outs` first, then `calculate_weight_vbytes(tx_ins.len(), payments, None)` and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` are called — both unaware of the OP_RETURN output. Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227) are underestimated by roughly `(8 + 1 + data_len) * 4` weight units (up to ~364 WU / ~91 vbytes for 80-byte data).
2. The `TooLowFee` minimum-relay check (line 211) and `NotEnoughFunds` check (line 215) are evaluated against the underestimated value.
3. The change-amount computation `input_sat - (payment_sat + fee_with_change)` (line 228) over-pays the change output by the missing fee, silently lowering the real fee rate below `fee_per_vbyte`.
4. `weight > MAX_STANDARD_TX_WEIGHT` (line 241) is checked on the underestimated weight, so a transaction that actually exceeds the 400,000 WU standardness limit can pass.

The `data` field is populated from on-chain Serai instructions (e.g. `extract_serai_data` feeding payments/data in the processor), i.e., bytes an unprivileged Bitcoin transaction sender controls — the same reachability class as BEVO's public `deliver()` mutating the accounting variable.

### Impact Explanation
The signed transaction's actual weight is higher than every internal accounting figure assumed. Where `fee_per_vbyte` is close to the relay minimum, the effective fee rate of the real (larger) transaction can fall below the node's minimum relay fee, or the real weight can exceed `MAX_STANDARD_TX_WEIGHT`, so the fully-signed, valid transaction is rejected by the Bitcoin P2P network as non-standard/underpaying. Funds committed as inputs are then locked until corrected code produces a new transaction — a permanent freeze if the signer set cannot or does not re-sign with a fixed builder. Additionally the change output is inflated at the expense of the fee, degrading confirmation. This is "funds moved to a state the operator cannot actually spend/broadcast," which is the concrete impact class the validation criteria accept.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some`, since the miscalculation happens on every such call — no adversarial race or collusion is needed. Whether it becomes harmful depends on margins: a transaction near the standardness boundary, a near-minimum `fee_per_vbyte`, or a tight `input_sat - payment_sat` margin makes the constructed transaction non-relayable or the fee materially wrong. For a ~91-byte underestimate this requires parameters near the edges, so exploitation is situational rather than guaranteed; Medium likelihood at most.

### Recommendation
Include the data output in the fee/weight template: pass the fully-built `tx_outs` (or build the template after pushing the OP_RETURN output) into `calculate_weight_vbytes` for both the no-change and with-change calculations, and re-run `calculate_weight_vbytes` on the final output set before the `MAX_STANDARD_TX_WEIGHT` check. Alternatively, add a conservative constant bound for the maximum OP_RETURN output (80-byte push + overhead) to both weight calculations.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte * (vbytes_true)` satisfies the minimum relay fee but `fee_per_vbyte * (vbytes_true - 91)` just meets the check.
2. Observe `needed_fee`/`fee()` reflect only `payments + change`; the returned `tx` additionally contains the ~91-byte OP_RETURN output.
3. `tx.weight()` exceeds the `weight` value checked against `MAX_STANDARD_TX_WEIGHT`, and `fee() / tx.vsize() < fee_per_vbyte`. Broadcasting the signed result is rejected by nodes enforcing `DEFAULT_MIN_RELAY_TX_FEE` or the standard weight limit, stranding the inputs.

The omission is provable by inspection: `tx_outs.push(... ScriptBuf::new_op_return ...)` at send.rs:194-202 executes before both `calculate_weight_vbytes` calls at send.rs:204 and send.rs:225-226, and neither call receives the data output.
