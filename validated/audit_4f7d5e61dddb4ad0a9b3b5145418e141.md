### Title
`internal_withdraw` operator RPC broadcasts a payout without the aggregator ECDSA verification-signature check that guards the sibling `withdraw` RPC - (File: core/src/rpc/operator.rs)

### Summary
The operator gRPC service exposes two entry points that both trigger `Operator::withdraw()` and cause a real Bitcoin payout transaction to be built, signed, and returned/broadcast: `withdraw` and `internal_withdraw`. `withdraw` enforces that the withdrawal request was authorized by the aggregator (via an ECDSA `verification_signature` check against `aggregator_verification_address`), but `internal_withdraw` performs the identical state-changing action while completely skipping that check.

### Finding Description
`ClementineOperator::withdraw` explicitly guards the call: if `aggregator_verification_address` is configured, it requires a `verification_signature` produced by that address over the withdrawal parameters, and rejects the call otherwise: [1](#0-0) 

`ClementineOperator::internal_withdraw`, however, parses the same withdrawal parameters and calls `self.operator.withdraw(...)` directly with no verification-signature check whatsoever: [2](#0-1) 

This is the same bug class as the external report: a required authorization/lock check exists in one code path (`withdraw`'s `aggregator_verification_address` gate, analogous to Lybra's boost-lock check in `stake`/`setLockStatus`) but is missing in the parallel path (`internal_withdraw`, analogous to Lybra's `withdraw()`) that performs the same custody-affecting action. Notably, other `internal_*` methods in this same file are explicitly test-gated, e.g. `internal_finalized_payout` refuses to run unless `cfg!(test)`: [3](#0-2) 

`internal_withdraw` has no such `cfg!(test)` guard, so nothing in this function itself prevents it from executing in a production build.

The binding that should hold is:
`operator broadcasts payout tx` ⇔ `aggregator-authorized withdrawal request (verification_signature valid for aggregator_verification_address)`

`internal_withdraw` breaks this equality: it allows `operator broadcasts payout tx` to be triggered by any caller who can reach this RPC, without the aggregator having authorized it.

### Impact Explanation
`Operator::withdraw()` fetches the previous UTXO, builds `create_payout_txhandler`, and funds/sends it via the tx-sender (an "unauthenticated state-changing or broadcasting call" as defined in the impact taxonomy), moving the deposited BTC to the caller-specified `output_script_pubkey`/`output_amount`: [4](#0-3) 

If a caller who is not the intended aggregator/user can reach `internal_withdraw` (e.g., any client trusted to call the operator's gRPC surface, or an environment where the interceptor does not treat `internal_withdraw` differently from `withdraw`), it can front-run or duplicate a payout without the aggregator's sign-off, i.e. the operator can pay out — and later be reimbursed via the bridge circuit — for a withdrawal it was never authorized to service. This crosses the "operator reimbursed for a payout it never funded"/"unauthenticated state-changing call" boundary the taxonomy calls Critical/High.

### Likelihood Explanation
Whether this is exploitable in the deployed system depends on whether an interceptor uniformly blocks `internal_*` methods from being reached by callers other than the operator's own test harness — `core/src/rpc/interceptors.rs` does reference internal-method handling, but I could not confirm within this repository's available context (no further tool calls available) whether that interceptor fully closes this specific gap the way the explicit `cfg!(test)` guard does for `internal_finalized_payout`. This is a real code-level asymmetry (the check is missing in the function body itself, matching the report's root cause), but I cannot rule out that an external interceptor layer already restricts calls to `internal_withdraw` in production deployments. This uncertainty should be resolved by inspecting `core/src/rpc/interceptors.rs` in full.

### Recommendation
Add the same `aggregator_verification_address` / `verification_signature` check to `internal_withdraw` that `withdraw` already performs, or add an explicit `if !cfg!(test) { return Err(Status::permission_denied(...)) }` guard (matching `internal_finalized_payout`) so the method cannot be invoked outside of test builds.

### Proof of Concept
1. Configure the operator with `aggregator_verification_address` set (i.e., production configuration that requires aggregator authorization for withdrawals).
2. As any caller able to reach the operator's gRPC surface, call `internal_withdraw` with a crafted `WithdrawParams` (arbitrary `output_script_pubkey`/`output_amount`, self-supplied `input_signature`/`input_outpoint`) — no `verification_signature` field exists on this RPC at all.
3. `internal_withdraw` (core/src/rpc/operator.rs:168-190) calls `Operator::withdraw()` directly; unlike `withdraw`, it never verifies the request was authorized by the aggregator, so the payout transaction is built and returned/broadcast despite the missing authorization — mirroring how Lybra's `withdraw()` let users bypass the boost lock check that `stake`/`setLockStatus` implied should exist.
