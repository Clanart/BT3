Based on the investigation, the closest local analog to the CoinGecko bug class (unsanitized external data causing an uncaught panic/DoS in a fee/price computation path) is in `VWAPOracle.sol`'s `recordSpread()` function.

### Title
Unguarded external `decimals()` call in `VWAPOracle.recordSpread()` can be forced to revert on attacker-chosen token addresses - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle.recordSpread()` is called by the `IntentGatewayV2` (`_intentGateway`) to record VWAP spread data for a filled order's input/output tokens. For any non-zero-address output token, it makes an unguarded external call `IERC20Metadata(outputToken).decimals()` [1](#0-0)  with no try/catch. The `outputToken` value is decoded straight from `outputs[i].token`, which originates from order data (the intent's declared output assets), not from a value the oracle or protocol controls [2](#0-1) .

### Finding Description
This mirrors the CoinGecko report's core pattern: code trusts a value from an external/untrusted source (there, the API's token id string; here, an order-supplied token address) and performs an operation on it — a low-level call / arithmetic — without sanitizing for the case where that external actor supplies malformed or adversarial input. If `outputToken` points to a contract that does not implement `decimals()`, or one whose `decimals()` implementation always reverts, the call in `recordSpread()` bubbles up an unhandled revert, exactly as the CoinGecko report's unguarded `getPrice()`/panic path brought down the fee oracle process. `recordSpread` itself has no local error handling (`restrict(_intentGateway)` modifier only checks the caller, not the token data), so this failure propagates directly into whatever call in `IntentGatewayV2`/`IntentsBase` invoked `recordSpread` as part of settlement [3](#0-2) .

### Impact Explanation
If `recordSpread` is invoked synchronously on the fill/settlement critical path (as its two call sites in `IntentsBase.sol`/`IntentGatewayV2.sol` suggest, given `IIntentPriceOracle` is wired into intent settlement [4](#0-3) ), a user-controlled order field (the declared output token) can force every settlement transaction touching that order to revert. This is not a "malicious relayer/prover" scenario — an ordinary unprivileged user can place an order whose `outputs[].token` is such a hostile/nonstandard contract, and because the settlement transaction that eventually calls into the price-oracle recording path cannot be completed, escrowed funds tied to that order's fill/redemption path can become stuck, satisfying the "loss/lock of funds" impact class.

### Likelihood Explanation
Medium-to-high: constructing a token address whose `decimals()` reverts (or a non-contract address) requires no privileged access — it is trivial to deploy such a contract and reference it as the output token in an order. The main uncertainty (noted below) is confirming the exact call site and whether `recordSpread` runs before or after escrow funds move, which determines whether the DoS merely griefs the specific order's VWAP bookkeeping or actually blocks fund release.

### Recommendation
Wrap the `IERC20Metadata(outputToken).decimals()` call (and any other external call in `recordSpread`) in a low-level `staticcall`/try-catch, defaulting to a safe fallback (e.g., skip that token's spread update, analogous to how `inputDecimals == 0` is already skipped) rather than allowing an unbounded revert to propagate into the settlement flow. This mirrors the CoinGecko fix's recommendation to sanitize external data and use `recover()`-equivalent guards around external call stacks that are on a critical funds-moving path.

### Proof of Concept
1. Deploy a `MaliciousToken` contract whose `decimals()` function always reverts (or simply deploy a contract with no `decimals()` selector).
2. Place a cross-chain intent order via `IntentGatewayV2` whose `outputs[0].token` (as a `bytes32`-encoded address) is `MaliciousToken`.
3. When a solver fills the order (or when `redeemEscrow`/whatever code path invokes `IIntentPriceOracle.recordSpread`) and `VWAPOracle.recordSpread()` is reached, the `IERC20Metadata(outputToken).decimals()` call reverts.
4. The revert is not caught anywhere in `recordSpread` or its caller, causing the entire settlement transaction to fail.

**Verification gap:** I was not able to fully read `IntentsBase.sol`/`ExtrinsicIntents.sol` in this session to confirm exactly where `recordSpread` is invoked relative to escrow fund transfer (i.e., whether the revert blocks actual fund release or only blocks price bookkeeping after funds have already moved). This detail is necessary to determine whether the impact is a fund-lock (in-scope) or a benign bookkeeping DoS (out-of-scope, "generic gas or network DoS"). I recommend a Devin session or further manual review of `evm/src/apps/intentsv2/IntentsBase.sol` and `ExtrinsicIntents.sol`/`IntrinsicIntents.sol` to pin down the exact call ordering before treating this as a submittable finding.

    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }
