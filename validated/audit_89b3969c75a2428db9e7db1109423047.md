### Title
Unvalidated duplicate encryption-key registration panics the PedPoP DKG participant, enabling remote denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::register` enforces the "one encryption-key registration per participant" precondition with an `assert!` that panics instead of returning a typed error. Because `EncryptionKeyMessage` values are deserialized from bytes supplied by other DKG participants (`EncryptionKeyMessage::read`), an unprivileged participant who submits a second registration message for their own index triggers a panic in the victim's DKG session, aborting key generation and denying service. This is the same bug class as CVE-2021-44591: a missing boundary/precondition check on attacker-controlled input that converts malformed input into a crash.

### Finding Description
`Decryption::register` at `crypto/dkg/pedpop/src/encryption.rs:351-362` does:

```rust
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
``` [1](#0-0) 

The `participant` index and `msg` both originate from a deserialized `EncryptionKeyMessage` read via `EncryptionKeyMessage::read` (`encryption.rs:57-59`), which accepts arbitrary bytes through `M::read` and `C::read_G`. `C::read_G` bounds-checks the encoding itself (`crypto/ciphersuite/src/lib.rs:91-101`), so the crash is not in the point parser — it is in the semantic precondition check that follows. If the same participant's registration is delivered twice (a malicious or faulty participant broadcasting two `EncryptionKeyMessage`s, or a relay/transport that redelivers a message), `enc_keys.contains_key(&participant)` is true and the `assert!` aborts the process.

The codebase generally distinguishes recoverable protocol faults from internal invariants — e.g., `AlgorithmSignMachine::sign` returns `FrostError::InvalidSigningSet`/`InvalidParticipant`/`DuplicatedParticipant` for the analogous duplicate/out-of-range participant conditions (`crypto/frost/src/sign.rs:298-310`), and `ThresholdKeys::view` returns `DkgError::DuplicatedParticipant` for duplicate indexes (`crypto/dkg/src/lib.rs:477-479`). `Decryption::register` is the outlier: a peer-controlled condition is enforced by `assert!` rather than an error.

### Impact Explanation
A panic inside the DKG aborts key generation for the victim. In the PedPoP flow, `Encryption::register` delegates directly to `Decryption::register` (`encryption.rs:452-458`), and the resulting `Decryption` state is required for every subsequent `decrypt`/blame operation (`encryption.rs:469-501`). Crashing the participant prevents it from completing the DKG, blocking formation of the threshold key (denial of service against the signing set), matching the Medium-severity DoS profile of the reference CVE. The attacker needs only the ability to send a second registration message under an already-registered `Participant` index — a public-input condition with no key material required.

### Likelihood Explanation
Every DKG participant can broadcast an `EncryptionKeyMessage`, and the trigger requires no cryptographic validity: the second message only needs to parse, which any well-formed bytes will satisfy via `EncryptionKeyMessage::read`. Whether duplicates reach `register` depends on upstream message routing; the code's own error enums (`DuplicatedParticipant` used elsewhere) show the authors expected duplicates to occur in practice on the channel, yet this particular path lacks that handling. No proof, key share, or collusion is needed — a single unprivileged participant suffices.

### Recommendation
Replace the `assert!` in `Decryption::register` with a typed error (e.g., a `DkgError`-style `DuplicatedParticipant` variant or a new `PedPopError`), propagated to the caller so a duplicate registration is rejected without aborting. Alternatively, treat re-registration deterministically (reject the second message or keep the first key) so that `enc_keys` contents remain well-defined. Callers in `crypto/dkg/pedpop/src/lib.rs` that invoke `register` should handle the error path instead of relying on the panic. An audit of other panics on peer-controlled paths in pedpop (`enc_keys[&participant]` indexing in `encrypt`/`decrypt_with_proof`) for the same issue is advisable.

### Proof of Concept
Conceptual: during a PedPoP session, a participant serializes two `EncryptionKeyMessage` values (each `M::write` output followed by `enc_key.to_bytes()`), sends both under their own `Participant` index, and the victim delivers both to `Encryption::register`. The second call hits `assert!(!self.enc_keys.contains_key(&participant))` at `encryption.rs:356-359` and panics, terminating the victim's DKG. No malformed encoding is required — both messages are canonical and parse successfully via `EncryptionKeyMessage::read`.
