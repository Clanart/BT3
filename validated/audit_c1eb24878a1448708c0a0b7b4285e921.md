### Title
`OP_RETURN` data is omitted from transaction size and fee accounting, producing underpriced transactions - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` appends a caller-controlled `OP_RETURN` output to the transaction, but calculates weight, virtual size, minimum relay eligibility, sufficiency of funds, and change using only the payment outputs and optional change output. [1](#0-0) [2](#0-1) 

### Finding Description
`calculate_weight_vbytes` reconstructs a model transaction containing the inputs, each `payments` entry, and optionally one change output. [3](#0-2) 

Before those calculations, `SignableTransaction::new` adds an `OP_RETURN` output to `tx_outs` when `data` is supplied. [4](#0-3) 

Both fee calculations nevertheless pass `payments`, not `tx_outs` or an equivalent representation containing the data output. [5](#0-4) [2](#0-1) 

The final signed transaction does include the omitted output because `tx_outs` is installed directly into the returned transaction. [6](#0-5) 

When change is created, its value is `input_sat - payment_sat - fee_with_change`, so the underestimated `fee_with_change` becomes the actual transaction fee rather than merely an inaccurate estimate. [7](#0-6) [8](#0-7) 

The signature then commits to the enlarged transaction through the Taproot sighash, making this a consensus-relevant accounting error rather than a display-only issue. [9](#0-8) 

### Impact Explanation
A transaction carrying the maximum 80-byte payload can be roughly 92 vbytes larger than the size used for fee calculation. [10](#0-9) 

With `fee_per_vbyte = 1`, the minimum-relay check can pass using the underestimated virtual size even though the completed transaction pays less than one satoshi per actual vbyte. [5](#0-4) 

For a transaction with change, the shortfall is not absorbed by leftover input value because the change calculation locks the actual fee to the underestimated value. [7](#0-6) 

The resulting signed transaction can fail relay policy, remain unconfirmed, or otherwise consume inputs in an attempted spend that does not satisfy the caller-requested feerate. [11](#0-10) 

### Likelihood Explanation
The vulnerable path is reachable through the public `data: Option<Vec<u8>>` argument to `SignableTransaction::new`; no malformed transaction or compromised signer is required. [12](#0-11) 

The issue occurs for any nonempty `data` value accepted by the 80-byte bound, with the fee discrepancy increasing with payload length. [10](#0-9) 

It is most damaging when a change output is used because the change calculation preserves the underestimated fee as the final fee. [13](#0-12) 

### Recommendation
Include the serialized `OP_RETURN` output in both weight calculations. [1](#0-0) [14](#0-13) 

For example, change `calculate_weight_vbytes` to accept the complete output list used for modeling, calculate the no-change case from `tx_outs`, and calculate the change case from `tx_outs` plus the change output. [15](#0-14) 

A regression test should assert that `needed_fee` increases by the serialized size of the maximum-length `OP_RETURN` output and that `transaction().vsize() * fee_per_vbyte <= fee()`. [16](#0-15) 

### Proof of Concept
```rust
// Conceptual regression PoC for networks/bitcoin/src/wallet/send.rs.
let payment = (payment_script, 10_000);
let change = change_script;
let rate = 1;

let without_data = SignableTransaction::new(
    vec![funded_output.clone()],
    &[payment.clone()],
    Some(change.clone()),
    None,
    rate,
)
.unwrap();

let with_data = SignableTransaction::new(
    vec![funded_output],
    &[payment],
    Some(change),
    Some(vec![0u8; 80]),
    rate,
)
.unwrap();

// The OP_RETURN output was never represented in either fee model.
assert_eq!(with_data.needed_fee(), without_data.needed_fee());

// The serialized transaction is approximately 92 vbytes larger.
assert!(with_data.transaction().vsize() > without_data.transaction().vsize());

// If change was created, the underestimated needed_fee is also the actual fee.
assert_eq!(with_data.fee(), with_data.needed_fee());
assert!(
    with_data.fee() <
    u64::try_from(with_data.transaction().vsize()).unwrap() * rate
);
```

The equality of both `needed_fee` values follows from both calls calculating size from `payments` while excluding `tx_outs`. [17](#0-16) 

The actual fee equality follows from the change formula subtracting only the underestimated fee from the input remainder. [7](#0-6)
