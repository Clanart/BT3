### Title
`SignableTransaction` fee/weight calculation omits the `OP_RETURN` data output, producing transactions below the requested fee rate and potentially below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` payload which is appended as an `OP_RETURN` output, but `calculate_weight_vbytes` is only ever called with `payments` (and optionally `change`). The data output is never included in the weight/vsize computation, so `needed_fee` and `fee()` understate the real transaction size by roughly `8 + 1 + (1 + data.len())` bytes (~11–92 vbytes for 1–80 bytes of data). A transaction carrying data therefore pays strictly less than the caller-specified `fee_per_vbyte`, can pass the `TooLowFee` guard while being under the network's minimum relay fee, and can pass the `MAX_STANDARD_TX_WEIGHT` guard while being non-standard. This mirrors the BlueBerryBank class: a required piece of accounting is skipped, rendering the produced asset (the spend transaction) unusable on the network.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the data output is pushed at lines 194–202, before fee/size accounting at lines 204–235:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

`calculate_weight_vbytes` (lines 62–127) builds a dummy transaction from `inputs`, `payments`, and `change` only — there is no `data` parameter at all, so both the no-change branch (line 204) and the change branch (lines 225–226) omit the serialized `OP_RETURN` output from the weight. Consequently:

1. `needed_fee` is computed against a vsize up to ~92 vbytes too small. Since `change` is computed as `input_sat - payment_sat - fee_with_change` (lines 228–230), the *actual* paid fee equals this understated `needed_fee`. The real fee rate is `needed_fee / actual_vsize < fee_per_vbyte`.
2. The `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the same underestimated `vbytes`, so a transaction can pass this check yet be below the true minimum relay fee for its real size — making it non-relayable.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the understated `weight`, so a transaction exceeding the standardness weight limit can be constructed.

The `data` field is attacker-influenced: in the processor, out-instruction `data` originates from user-submitted InInstruction messages (c.f. `Output::data()` population in `processor/src/networks/bitcoin.rs` lines 730–734), so an unprivileged party supplying up to 80 bytes of data controls the size of the omitted output and maximizes the underestimate.

### Impact Explanation
Every spend transaction that carries an `OP_RETURN` data output pays less than the caller-requested fee rate. At higher `fee_per_vbyte` values the shortfall is proportional (e.g., ~90 vbytes × rate). More critically, a transaction sized near the `TooLowFee` boundary can be constructed which passes the library's own minimum-fee check yet is below `DEFAULT_MIN_RELAY_TX_FEE` for its actual size, so Bitcoin nodes will reject it from the mempool. Outputs previously scanned and reported as received (via `Scanner::scan_transaction` / `get_outputs`) then cannot actually be moved through this code path without rebuilding the transaction without the data payload — funds are reported spendable but the produced spend is not relayable. Likewise, `needed_fee()` misreports the fee required to achieve the requested rate, and `weight` no longer bounds the transaction against `MAX_STANDARD_TX_WEIGHT`, so an oversized non-standard transaction can be emitted.

### Likelihood Explanation
Deterministic whenever `data: Some(_)` is passed to `SignableTransaction::new`: the miscalculation happens on every such call, independent of any party's behavior. Whether the resulting transaction is actually rejected by the network depends on the chosen `fee_per_vbyte`, the data length, and current relay policy; at minimum, the stated fee-rate contract (`fee_per_vbyte`) is silently violated for every data-carrying transaction. Data-carrying transactions are a first-class, documented feature of this API (`If data is specified, an OP_RETURN output will be added`, line 149) and are exercised by the processor for user-controlled InInstruction payloads, so the path is reachable with public inputs.

### Recommendation
Pass the planned `OP_RETURN` output (or its script/size) into `calculate_weight_vbytes` so the weight and vsize reflect the final transaction, for both the no-change and change branches. Concretely, add a `data: Option<&ScriptBuf>` (or the constructed `TxOut`) parameter and include it in the dummy transaction's outputs before calling `tx.weight()`. The `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` checks will then operate on the true size.

### Proof of Concept
```rust
// networks/bitcoin context; conceptual demonstration of the size mismatch
let data = vec![0xaa; 80]; // max allowed, passes the 80-byte check at line 171
let tx = SignableTransaction::new(
    vec![output],
    &payments,
    Some(change_addr),
    Some(data.clone()),
    fee_per_vbyte,
).unwrap();

// tx.transaction() includes a 3rd output: OP_RETURN with ~83 bytes of script
// actual serialized vsize > the vbytes used to compute tx.needed_fee()
let actual_vsize = /* vsize of tx.transaction() */;
assert!(tx.needed_fee() < actual_vsize * fee_per_vbyte);
// For a fee_per_vbyte chosen exactly at the TooLowFee boundary,
// needed_fee / actual_vsize < DEFAULT_MIN_RELAY_TX_FEE / 1000,
// i.e., the tx passes the library check but is below the real min relay fee.
```
The dummy transaction built inside `calculate_weight_vbytes` never contains the `OP_RETURN` output pushed at lines 194–202, so the discrepancy holds for any non-empty `data`.
