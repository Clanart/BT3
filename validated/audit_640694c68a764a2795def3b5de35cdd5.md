## Finding

### Title
Unrefunded ETH overpayment permanently trapped in `EvmHost` during fee-swap dispatch — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all swap the caller's `msg.value` for an exact amount of fee tokens via Uniswap V2's `swapETHForExactTokens`, but never account for or refund the unspent native-token change. This is the same "insufficient slippage/overpayment protection" class described in the external report, applied to Hyperbridge's own fee-payment path instead of a liquidity pool.

### Finding Description
`dispatch(DispatchPost memory post)` executes: [1](#0-0) 

`swapETHForExactTokens(amountOut, path, to, deadline)` requires `amountIn <= msg.value` and — per the Uniswap V2 Router02 spec — refunds any leftover ETH (`msg.value - amounts[0]`) to `msg.sender` of that call. In this call, `msg.sender` is `EvmHost` itself (since `EvmHost` is the contract invoking the router), not the original `_msgSender()` who funded the transaction. `EvmHost` never reads the router's `amounts` return value and never forwards any leftover ETH back to `_msgSender()`. The identical pattern exists in: [2](#0-1) [3](#0-2) 

By contrast, the codebase demonstrates the developers know this refund is required — `IntentGatewayV2.placeOrder` performs the same `swapETHForExactTokens` call and explicitly captures `amounts[0]` and refunds the difference to `msg.sender`: [4](#0-3) 

The docs even warn that fee estimation via `quote()` is imprecise and sandwich-attack-prone, implying callers must send a native-token amount with margin above the exact quoted fee to avoid reverts from price movement between quote-time and execution-time — exactly the "slippage" scenario the external report describes: [5](#0-4) 

Any margin the caller adds to guard against this price movement is swallowed by `EvmHost` rather than returned.

### Impact Explanation
Every `dispatch`/`fundRequest` caller who sends `msg.value` greater than the exact ETH needed to buy `post.fee`/`get.fee`/`amount` fee tokens loses that entire difference permanently — it accumulates as native token stuck in the `EvmHost` contract with no user-facing sweep or refund mechanism visible in these functions. Because off-chain fee estimation is explicitly imprecise (per the docs' own warning against on-chain `quote()` use), a rational caller must overpay for safety margin on every single dispatch call, making this a persistent, guaranteed loss of funds condition rather than an edge case — matching the bounty's "loss of funds" impact class.

### Likelihood Explanation
This triggers on the normal, unprivileged, permissionless call path (`dispatch`, `fundRequest`) with no need for a malicious relayer, prover, or governance actor — any regular app or user paying fees in native token via `EvmHost` and providing any non-exact `msg.value` (which is the expected off-chain estimation behavior) hits this path every time.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Caller estimates `post.fee` off-chain and, per documentation guidance, sends `msg.value` with a safety margin above the exact quote to avoid transaction failure from price movement.
2. Caller invokes `EvmHost.dispatch{value: msg.value}(post)`.
3. Inside `dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; the router refunds `msg.value - amountIn` ETH to `address(this)` (i.e., `EvmHost`), since `EvmHost` is the router's caller.
4. `dispatch` returns without reading `amounts[0]` or transferring any ETH back to the original caller.
5. The overpaid ETH remains permanently in `EvmHost`'s balance; the caller has no way to reclaim it. Repeating this on every dispatch call accumulates a growing unclaimed balance drawn entirely from callers' overpayments.
