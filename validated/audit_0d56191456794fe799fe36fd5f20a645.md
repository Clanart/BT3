Missing non-payable check on `rewards()` strands native value sent to the distribution precompile - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards(address)` query method on the distribution precompile (`0x0000000000000000000000000000000000001007`) is dispatched without any check that `msg.value` is zero, unlike every other value-aware method in the same `Execute` switch. Because the distribution precompile address is registered as a "payable precompile" (transfer events to/from it are suppressed), an EVM caller can attach native value to a call to `rewards(address)`, have that value debited from their EVM balance and credited to the precompile's Sei-mapped account, and receive back only ABI-encoded reward data — with no code path that refunds or forwards the value anywhere. The funds become permanently stranded at the precompile address.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute()` dispatches `RewardsMethod` directly to `p.rewards(ctx, method, args)` with no validation of `value`: [1](#0-0) 

Contrast this with `WithdrawValidatorCommissionMethod`, which explicitly rejects non-zero value via `pcommon.ValidateNonPayable(value)`: [2](#0-1) 

and with the other query methods (`validatorOutstandingRewards`, `delegationRewards`, etc.), which route `value` into `p.validateInput(value, args, n)` for validation before proceeding: [3](#0-2) [4](#0-3) 

The `rewards` implementation itself never touches `value` at all — it only queries `DelegationTotalRewards` and packs the ABI output, with no refund/transfer logic: [5](#0-4) 

This is unlike transaction-side (state-mutating) precompile paths, e.g. the bank precompile's `sendNative`, which explicitly refunds the payer for value credited to the precompile before debiting the intended recipient (`HandlePaymentUseiWei` first sends the value back to the payer): [6](#0-5) 

The distribution precompile is registered in the payable-precompile set, which suppresses the underlying transfer events to/from the precompile address, making the value movement invisible in standard EVM transfer logs: [7](#0-6) 

The project's own integration test explicitly documents this exact gap as a known quirk and deliberately omits a "view rejects value" assertion for `rewards()`: [8](#0-7) 

This is the direct analog of the reported `earlyEndGame` bug class: value is accepted/deducted from the caller but there is no mechanism to move it back out, so it becomes permanently locked in the precompile's underlying account.

### Impact Explanation
Any EVM value sent with a call to `rewards(address)` on the distribution precompile is irrecoverably locked at the precompile's associated Sei address — there is no withdrawal, refund, or sweep mechanism for it, unlike the ante/fee and coinbase-sweep paths elsewhere in the codebase which always route collected value to a destination (fee collector, distribution module, etc.). This is a permanent fund loss for any caller (EOA or contract) that mistakenly or unknowingly attaches value to this call (e.g., through a proxy/aggregator contract that forwards `msg.value` on all calls). Because the precompile is in the payable set, standard transfer-event-based balance reconciliation tooling will not surface the stranded value, making it harder for users to detect before the loss occurs.

### Likelihood Explanation
This function is reachable by any unprivileged EVM transaction sender or contract with no special permissions — a plain `rewards(address)` call with non-zero `value` triggers the bug. Given that `rewards()` is a commonly-called read query for reward dashboards/aggregators, and that many wallet/contract integrations forward `msg.value` generically on calls, accidental value attachment is plausible, especially via `PrecompileCaller`-style forwarding contracts that pass `msg.value` through indiscriminately: [9](#0-8) 

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check (or equivalent refund-on-payment logic) to the `RewardsMethod` case in `Execute`, consistent with `WithdrawValidatorCommissionMethod` and the other read-only distribution query methods that already reject or handle non-zero value: [1](#0-0) 

### Proof of Concept
1. Deploy or use an existing EVM contract (or send a raw transaction) that calls the distribution precompile at `0x0000000000000000000000000000000000001007` with function selector for `rewards(address)` and a non-zero `value` (e.g. 1 usei worth of wei).
2. The EVM debits `msg.value` from the caller and credits it to the precompile's EVM-mapped Sei address as part of standard EVM call-value semantics.
3. `Execute()` dispatches to `p.rewards(ctx, method, args)` without any `ValidateNonPayable`/refund check; the function only returns ABI-encoded reward data.
4. Because the distribution precompile is a registered "payable precompile," the underlying transfer event is suppressed, so no on-chain transfer log surfaces the value movement.
5. The attached value remains permanently held at the precompile's account with no method in the distribution module or precompile to withdraw or sweep it back to the caller.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
