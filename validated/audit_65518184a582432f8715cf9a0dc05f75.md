## Confirmed Analog

I found a real Agave analog matching the report's broken invariant: **a fund-eligibility/liquidation-style decision computed from a raw balance that ignores a known, already-recorded "pending but guaranteed" liability tracked elsewhere in the same account state.**

### Title
VAT eligibility/burn filtering ignores `pending_delegator_rewards`, allowing burn of funds owed to delegators - ([File: vote/src/vote_account.rs])

### Summary
`pending_delegator_rewards` is a per-vote-account liability introduced by SIMD-0123: it is money already credited into the vote account's lamport balance but earmarked for delegators, and the vote program's own `withdraw` logic treats it as reserved and non-withdrawable [1](#0-0) . However, the Validator Admission Ticket (VAT) eligibility filter that decides which vote accounts are "healthy" enough to remain admitted, and the subsequent VAT burn that debits lamports from those accounts, both operate on raw `vote_account.lamports()` without subtracting `pending_delegator_rewards`.

### Finding Description
`VoteAccounts::clone_and_filter_for_vat` computes `has_balance` purely from raw lamports: [2](#0-1) 

This is directly analogous to the Perennial bug's `InvariantLib.validate`, which checked only raw `collateral` and ignored the pending, already-guaranteed intent price adjustment. Here, `pending_delegator_rewards` is the Agave equivalent of that guaranteed pending adjustment — it is already reflected in the account's lamport balance but is not "free" collateral; the vote program's own `withdraw` path enforces `remaining_balance >= rent_exempt + pending_delegator_rewards` specifically because these lamports are reserved for delegators [3](#0-2) .

Once a vote account passes this unadjusted `has_balance` filter and is included in the top `MAX_ALPENGLOW_VOTE_ACCOUNTS`, the bank unconditionally burns `vat_to_burn_per_epoch` from its lamports: [4](#0-3) 

The `checked_sub(...).expect(...)` only guards against arithmetic underflow of raw lamports — it does not verify that `lamports - vat_to_burn_per_epoch` still covers `rent_exempt_reserve + pending_delegator_rewards`. The comment at line 2646-2647 asserts the invariant ("filtered to the top ... that contain enough balance for admission") but the filtering that produced that guarantee (`has_balance`) never accounted for `pending_delegator_rewards` in the first place.

### Impact Explanation
Because the burn debits raw lamports without honoring the `pending_delegator_rewards` reserve, a vote account can be pushed below `rent_exempt_reserve + pending_delegator_rewards` purely by the VAT burn. Delegators' already-accrued (but not yet withdrawn) rewards, which the protocol elsewhere treats as sacrosanct (`withdraw` refuses to let even the *withdrawer* touch this reserve), can be effectively consumed by the VAT burn mechanism. This is a fund-loss condition for delegators that mirrors the external report exactly: an on-chain fund-safety decision (admission/burn) is computed from a balance value that does not reflect a pending, already-recorded, guaranteed liability tracked in a sibling field of the very same account.

### Likelihood Explanation
This triggers deterministically, without any malicious actor, whenever a vote account (a) has accrued `pending_delegator_rewards` (a normal, expected state once SIMD-0123 rewards start accruing) and (b) has a lamport balance that is high enough to satisfy the naive `has_balance` check but not high enough to also cover `pending_delegator_rewards + vat_to_burn_per_epoch`. This is a realistic and likely-to-occur operating point for any validator running close to the VAT minimum balance while carrying accrued delegator rewards, and it occurs identically on all validators (deterministic bank state transition), so it is not merely a theoretical edge case — every honest node will apply the same incorrect burn.

### Recommendation
`clone_and_filter_for_vat`'s `has_balance` check, and `maybe_burn_vat_from_staked_accounts`'s burn subtraction, should both account for `pending_delegator_rewards` (and the rent-exempt reserve) the same way `withdraw` does: require `lamports >= rent_exempt_reserve + pending_delegator_rewards + minimum_vote_account_balance_for_vat` (or `+ vat_to_burn_per_epoch` for the burn path), so that VAT admission/burn can never consume the reserve that is contractually owed to delegators.

### Proof of Concept
1. A vote account accrues `pending_delegator_rewards = R` via the SIMD-0123 rewards path (`add_pending_delegator_rewards`, seen invoked from `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`) — this credits lamports into the account and simultaneously records the same amount as owed via `pending_delegator_rewards`.
2. Total lamports = `rent_exempt_reserve + R + vat_to_burn_per_epoch` (just enough to clear `minimum_vote_account_balance_for_vat` if that minimum is at or below this total, and enough to satisfy the naive `has_balance` check in `clone_and_filter_for_vat`, which never looks at `R`).
3. Bank epoch boundary calls `maybe_burn_vat_from_staked_accounts`, subtracting `vat_to_burn_per_epoch` from the account's lamports: `runtime/src/bank.rs:2662-2677`. This succeeds (`checked_sub` doesn't underflow) but leaves the account with lamports = `rent_exempt_reserve + R`, i.e., exactly at the reserve, or in a case where `vat_to_burn_per_epoch` is applied multiple epochs in a row while further rewards accrue, the account can be driven to lamports `< rent_exempt_reserve + R`.
4. At this point `withdraw`'s own invariant (`programs/vote/src/vote_state/mod.rs:1112-1121`) can no longer be satisfied for the full `R` — the delegator-owed reserve has been silently eroded by the VAT burn, an operation the withdraw code path treats as untouchable.

I could not fully trace whether `vat_to_burn_per_epoch` is normally small enough relative to typical `pending_delegator_rewards` accrual to make this a first-epoch problem versus requiring several epochs of compounding drift; this would require running the actual reward/burn cadence in a test harness (unavailable in this read-only investigation) to quantify the exact number of epochs needed to exhaust the reserve for realistic parameter values.
