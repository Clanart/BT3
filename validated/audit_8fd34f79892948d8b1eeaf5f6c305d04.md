### Title
Attacker-controlled `WWW-Authenticate` realm header spoofs GitHub Enterprise sign-in flow, phishing OAuth credentials for an arbitrary endpoint - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
When Git performs an authenticated HTTP(S) request against a remote and the server responds with a `401`/`WWW-Authenticate` challenge, Git forwards that header verbatim to the configured credential helper as a `wwwauth[]=` field. GitHub Desktop's credential helper implementation uses the *content of that attacker-controlled header* to decide whether the remote is a "GitHub" host and, if so, opens Desktop's real GitHub Enterprise sign-in / OAuth flow pointed at the attacker's own origin.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` classifies a credential request's endpoint before deciding how to source credentials: [1](#0-0) 

The `wwwauth[...]` keys are populated straight from the credential-helper protocol input, which in turn is populated by Git from the `WWW-Authenticate` HTTP response header sent by the remote server: [2](#0-1) 

If the substring `realm="GitHub"` is present anywhere in that header — fully controlled by whatever host or MITM/corporate proxy is answering the git HTTP request — `getEndpointKind` returns `'enterprise'` for that endpoint, with **no check that the endpoint is actually a real GitHub/GHE server** (no TLS cert pinning, no `/meta` API probe, nothing).

Because the endpoint is classified as `'enterprise'`, `getCredential` treats it as a first-party GitHub host. If no signed-in account already matches that endpoint's origin, it invokes: [3](#0-2) 

`ui.promptForGitHubSignIn(endpoint)` then drives Desktop's *real* GitHub Enterprise sign-in UI, pointed at the attacker's origin: [4](#0-3) 

`beginEnterpriseSignIn` + `setSignInEndpoint(origin)` put the app's `SignInStore` into the `Authentication` step for that attacker-supplied origin, and the resulting `PopupType.SignIn` dialog will let the user pick browser-based OAuth, which then calls `getOAuthAuthorizationURL(endpoint, csrfToken)`: [5](#0-4) [6](#0-5) 

`getOAuthAuthorizationURL` builds `${attacker-origin}/login/oauth/authorize?...` and opens it in the system browser. Because the base URL is entirely attacker-controlled, this is effectively an OAuth phishing primitive: Desktop's own legitimate-looking "Sign in" dialog and OAuth handoff are used to send the user's browser to a URL the attacker fully controls, which can present a fake GitHub Enterprise login page or an actual OAuth consent screen for a look-alike GHE-branded OAuth app to capture credentials or a code/token.

### Impact Explanation
This qualifies as "unauthorized OAuth or account binding" from an attacker-controlled git remote/proxy response, per the accepted impact categories. Concretely:
- A user need only add or clone from a plain HTTP(S) remote that the attacker controls (or is on-path for, e.g. a compromised/malicious corporate proxy), no elevated privileges or local access are required.
- The attacker's server does not need valid GitHub SSL/TLS certificates or any GitHub infrastructure — it just needs to answer unauthenticated Git-over-HTTP requests with a `401` and `WWW-Authenticate: Basic realm="GitHub"` header.
- The victim is shown Desktop's authentic "Sign in" UI (`PopupType.SignIn`), which increases the credibility of the resulting browser OAuth prompt, and the browser is then directed by Desktop itself to a URL under the attacker's control.
- This can lead to credential/token exfiltration and improper binding of an "enterprise" account entry to an attacker's server inside Desktop's `AccountsStore`.

### Likelihood Explanation
Likelihood is moderate-to-high for targeted phishing: the trigger condition is trivial to produce (any HTTP server can add the header), and it fires automatically the first time Desktop performs any git network operation (clone/fetch/push/pull) against the malicious remote, without any unusual user action beyond adding that remote — a normal, expected user workflow (e.g., "clone this internal repo" links or spoofed HTTP git servers).

### Recommendation
Do not trust the raw `wwwauth[]` realm string alone to classify a host as GitHub/GHE. At minimum:
- Require corroborating evidence, such as a successful call to `isGitHubHost(endpoint)` (which already exists and does a network round-trip to a known GitHub API path) before trusting the header-derived classification.
- Never auto-launch the enterprise sign-in / OAuth flow for a host discovered solely via response headers on an unauthenticated/unverified connection; instead, only offer this as a *suggestion* in the generic-auth prompt, requiring explicit user confirmation of the hostname before starting `beginEnterpriseSignIn`.
- Consider requiring TLS transport (reject `http://`) and cross-checking that the header-derived host doesn't get privileged treatment over what `isGitHubHost` returns.

### Proof of Concept
1. Run a small HTTP server that implements the minimal Git smart-HTTP protocol handshake and responds to the initial `GET /info/refs?service=git-upload-pack` with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add/clone this server as a remote, e.g. `https://attacker.example/foo.git`, and trigger a fetch.
3. Git invokes the Desktop credential helper (`GIT_CONFIG_PARAMETERS` sets `credential.helper=desktop`, see `withTrampolineEnv` in `app/src/lib/trampoline/trampoline-environment.ts:143`), forwarding the `wwwauth[]=Basic realm="GitHub"` field.
4. `getEndpointKind` classifies the endpoint as `'enterprise'` purely from that header value (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`).
5. Since no account matches `attacker.example`, Desktop calls `ui.promptForGitHubSignIn('https://attacker.example')`, which opens the enterprise sign-in dialog and, on browser-auth, opens `https://attacker.example/login/oauth/authorize?...` in the user's default browser — a URL fully controlled by the attacker.

Note: I was unable to fully trace how the `AuthenticationForm` UI copy displays the endpoint to the user (whether it clearly shows `attacker.example` before the user proceeds), which would affect real-world exploitability/user-awareness; a Devin session with full repo access could confirm this UI detail.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

import { exec as git } from 'dugite'

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
