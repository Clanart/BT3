## Title
VC authorization policy in `add_vc_authorization` can be bypassed for CR-CAT outputs the wallet currently owns - (File: `chia/wallet/vc_wallet/vc_wallet.py`)

### Summary
`VCWallet.add_vc_authorization()` is the client-side policy gate that decides whether a wallet's Verified Credential (VC) should be attached to authorize a CR-CAT spend embedded in an offer being built or accepted. The function's docstring states it should only authorize a spend when outputs go to a wallet-known address, back to the source puzzle hash (change), to the pending-approval state, or to the offer mod. However, the implemented check `if our_crcat or outputs_ok:` short-circuits and skips the output-destination validation (`outputs_ok`) entirely whenever the *currently spent* coin's puzzle hash is already known to the wallet, regardless of where the outputs of that spend actually go, similar to how Inspektor Gadget's client-supplied fields could bypass server-side policy enforcement (GHSA-pv22-fqcj-7xwh).

### Finding Description
`add_vc_authorization` is invoked from `TradeManager.check_for_final_modifications()` for every offer that contains CAT/CR (CR-CAT) driver info, both when making and when responding to an offer: [1](#0-0) 

Inside `add_vc_authorization`, for each incomplete CR-CAT spend found in the offer bundle, the wallet computes two independent signals:

- `our_crcat`: true if the wallet recognizes the derivation for `crcat_spend.crcat.inner_puzzle_hash` — i.e., the puzzle hash of the coin **as it currently exists before being spent** (whether we currently own it): [2](#0-1) 

- `outputs_ok`: computed by iterating the spend's `CREATE_COIN` conditions and requiring each output puzzle hash to be either wallet-known, equal to the source's own inner puzzle hash (change), the pending-approval-state hash, or the offer mod hash: [3](#0-2) 

The two are then combined with a logical OR, not AND: [4](#0-3) 

Because `our_crcat` is derived from the coin's *pre-spend* puzzle hash rather than its *destination*, it evaluates to `True` for practically any CR-CAT spend of a coin the wallet already owns/knows about — which is exactly the class of spend the destination checks (`outputs_ok`) are supposed to police. As a result, whenever a wallet already has a derivation record for a CR-CAT it is contributing to a trade, `add_vc_authorization` will attach the required VC authorization/proof-of-inclusion announcement to that spend without validating that its `CREATE_COIN` outputs actually go to one of the four sanctioned destinations. A malicious offer counterparty can embed the taker's own recognized CR-CAT coin in the driver dict with a solution whose `CREATE_COIN` output points to an arbitrary attacker-controlled puzzle hash instead of the wallet, change, pending-approval, or offer-mod destinations, and the wallet's policy check will still authorize (VC-sign) it because `our_crcat` alone satisfies the `or` condition.

### Impact Explanation
The VC authorization is the on-chain gate (`CREDENTIAL_RESTRICTION` puzzle layer) that lets a CR-CAT spend proceed; the wallet-side `add_vc_authorization` heuristic exists specifically to prevent the wallet from rubber-stamping this authorization onto spends whose outputs were not vetted. Bypassing it means the wallet can be induced, via a crafted offer, to co-sign/authorize movement of the user's own CR-CAT holdings to an unintended, attacker-chosen destination — an unauthorized coin movement enabled purely by a client-visible policy check that fails to actually gate on destination once the "we own the source" condition is met.

### Likelihood Explanation
Exploitation only requires a counterparty able to propose or respond to an offer containing a CR-CAT (offers/trades and CR-CAT/VC flow are explicitly reachable by any wallet user negotiating a trade), and requires the taker's wallet to already hold a derivation record for the coin used in the crafted spend (a realistic precondition, since the coin belongs to that wallet). No privileged network position or timelord/harvester access is needed — it is purely an offer/trade interaction.

### Recommendation
Change the gating logic from `if our_crcat or outputs_ok:` to require destination validation unconditionally (e.g., `if outputs_ok:`), or make `our_crcat` a component that still forces the standard destination checks (`and`), matching the docstring's intent that authorization is only added when outputs actually land in one of the four sanctioned states.

### Proof of Concept
1. Taker owns a CR-CAT coin `C` at inner puzzle hash `P` (wallet has derivation record for `P`).
2. Maker constructs an offer whose combined spend bundle includes a spend of `C` with solution creating a `CREATE_COIN` condition to attacker puzzle hash `Q` (not `P`, not pending-approval hash, not offer-mod, not any wallet-known hash).
3. Taker calls `respond_to_offer`, which calls `check_for_final_modifications` → `add_vc_authorization`.
4. For the spend of `C`, `our_crcat` evaluates `True` (wallet knows `P`), so the `or` short-circuits and `outputs_ok` (which would be `False` for destination `Q`) is never enforced — see [5](#0-4) .
5. The wallet attaches the VC proof-of-inclusion/announcement authorization to the spend, allowing the crafted offer (redirecting `C`'s value to `Q`) to be validly authorized and pushed.
