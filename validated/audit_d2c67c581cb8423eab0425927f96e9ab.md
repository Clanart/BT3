### Title
DataLayer Mirror Coins Enable Attacker-Controlled SSRF via `create_new_mirror`/`fetch_and_validate` - ([File: chia/data_layer/data_layer.py])

### Summary
Chia's DataLayer mirror mechanism lets **any spend-bundle submitter** create an on-chain "mirror" coin that publishes an arbitrary URL for a given `launcher_id`. Any node that subscribes to that store treats this attacker-supplied URL as a legitimate download source and performs a server-side HTTP fetch to it, then writes the response to disk. This mirrors the CWE-918 SSRF pattern in the HAXcms report: untrusted, attacker-controlled input becomes a server-side fetch target with no validation of scheme/host/destination.

### Finding Description
`create_mirror_puzzle()` is a generic puzzle (`P2_PARENT.curry(Program.to(1))`) with a fixed, publicly known puzzle hash (`MIRROR_PUZZLE_HASH`) [1](#0-0) . Any wallet — not just the store owner — can spend coins to create a `CREATE_COIN` output to this puzzle hash with memos `[launcher_id, url1, url2, ...]`, exactly as `DataLayerWallet.create_new_mirror()` does [2](#0-1) .

When any full node's wallet observes such a coin, `DataLayerWallet.coin_added()` extracts the `launcher_id` and URLs via `get_mirror_info()` and, critically, only checks `is_launcher_tracked(launcher_id)` — not whether the coin was created by the store's actual owner — before persisting the mirror record: [3](#0-2) 

```
if await self.wallet_state_manager.dl_store.is_launcher_tracked(launcher_id):
    ours: bool = await self.wallet_state_manager.get_wallet_for_coin(coin.parent_coin_info) is not None
    await self.wallet_state_manager.dl_store.add_mirror(
        Mirror(coin.name(), launcher_id, uint64(coin.amount), Mirror.decode_urls(urls), ours, height)
    )
```

`get_mirror_info()` performs no validation of the URL content, scheme, or destination whatsoever — it simply extracts raw memo bytes as URL strings [4](#0-3) .

The DataLayer service later consumes these attacker-supplied mirror URLs in `fetch_and_validate()`, iterating `servers_info` (sourced from `get_available_servers_for_store`, populated from `dl_store`'s `mirrors` table) and calling `insert_from_delta_file(...)` with `server_info.url` [5](#0-4) . That in turn calls `download_file()` → `http_download()` which performs an unrestricted `aiohttp` GET to `server_info.url + "/" + filename` with no scheme, host, or IP-range restriction, and writes the response body directly to disk under `server_files_location`: [6](#0-5) 

```
async with session.get(
    server_info.url + "/" + filename,
    headers=headers,
    timeout=timeout,
    proxy=proxy_url,
) as resp:
    ...
    with target_filename_path.open(mode="wb") as f:
        async for chunk, _ in resp.content.iter_chunks():
            f.write(chunk)
```

The written file can then be served back over HTTP via `DataLayerServer.file_handler`/`folder_handler`, which only validates the *filename* format, not the file's provenance or content, and streams the raw bytes to any HTTP client [7](#0-6) .

This precisely matches the HAXcms bug class: an authenticated (here, merely "can submit a spend bundle / run a wallet") actor supplies a URL that is fetched server-side with no restriction on destination (internal services, `169.254.169.254` metadata endpoints, etc.), and the response becomes retrievable from a web-accessible path.

### Impact Explanation
Any party able to submit a standard coin spend (no special privilege beyond owning spendable XCH) can force every DataLayer node subscribed to a targeted store to issue outbound HTTP requests to attacker-chosen hosts (internal services, cloud metadata endpoints, etc.) and persist/serve the response. This is an SSRF / internal-network-probing and potential-data-exfiltration primitive reachable purely from a submitted spend bundle, without needing to be the store owner, matching the "Medium/High" severity bar (CWE-918 analog) requested. It does not directly cause unauthorized coin movement or consensus divergence, but it is a genuine, concretely reachable SSRF against DataLayer operators triggered by an unprivileged spend.

### Likelihood Explanation
Likelihood is high for any actively-used DataLayer store: the mirror-creation code path is a normal, documented feature (`chia data add_mirror` CLI, `dl_new_mirror` RPC) [8](#0-7) [9](#0-8) , and nothing restricts *who* can spend to the well-known `MIRROR_PUZZLE_HASH` for a given `launcher_id`, nor does `coin_added()` verify mirror ownership before trusting the URL for downloads.

### Recommendation
- Validate mirror URLs before use in `fetch_and_validate`/`http_download`: restrict scheme to `https`/`http` with explicit allow-listing, reject loopback/link-local/private/metadata IP ranges (e.g., resolve DNS and check against RFC1918/169.254.0.0/16 etc.) before connecting.
- Consider only trusting mirrors created by the store owner (`ours`) by default, or require explicit user opt-in/allow-listing before a subscriber's node will fetch from a third-party-submitted mirror URL.
- Apply the same URL validation in `get_downloader`/plugin `handle_download` flow and any place a mirror-sourced URL is dereferenced.

### Proof of Concept
1. Any wallet holding XCH creates a mirror coin for a `launcher_id` of a store it does not own, calling `create_new_mirror` (or `dl_new_mirror` RPC) with `urls=[b"http://169.254.169.254/latest/meta-data/"]` and a valid `launcher_id` for a store a victim operator subscribes to.
2. The transaction confirms; any victim node subscribed to that `launcher_id` observes the coin in `coin_added()` and adds it to its local `mirrors` table since `is_launcher_tracked(launcher_id)` is true, with no ownership check [3](#0-2) .
3. During its normal sync cycle, the victim's DataLayer service calls `fetch_and_validate()`, selects this malicious `server_info`, and issues `http_download()` against `http://169.254.169.254/latest/meta-data/` [6](#0-5) .
4. The fetched response is written to `server_files_location` and, depending on naming, becomes retrievable via the DataLayer HTTP file server [7](#0-6) , or at minimum causes the victim node to leak an SSRF probe/request to an attacker-chosen internal endpoint.

def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```

    async def file_handler(self, request: web.Request) -> web.Response:
        filename = request.match_info["filename"]
        if not is_filename_valid(filename):
            raise Exception("Invalid file format requested.")
        file_path = self.server_dir.joinpath(filename)
        with open(file_path, "rb") as reader:
            content = reader.read()
        response = web.Response(
            content_type="application/octet-stream",
            headers={"Content-Disposition": f"attachment;filename={filename}"},
            body=content,
        )
        return response

    async def folder_handler(self, request: web.Request) -> web.Response:
        tree_id = request.match_info["tree_id"]
        filename = request.match_info["filename"]
        if not is_filename_valid(tree_id + "-" + filename):
            raise Exception("Invalid file format requested.")
        file_path = self.server_dir.joinpath(tree_id).joinpath(filename)
        with open(file_path, "rb") as reader:
            content = reader.read()
        response = web.Response(
            content_type="application/octet-stream",
            headers={"Content-Disposition": f"attachment;filename={filename}"},
            body=content,
        )
        return response
