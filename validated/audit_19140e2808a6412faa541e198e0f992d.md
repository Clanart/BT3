## Title
Silent leftover-conflict-marker commit due to divergent hunk-boundary parsing between Copilot conflict extraction and reassembly - (File: `app/src/lib/copilot-conflict-resolution.ts`)

## Summary
GitHub Desktop's AI-assisted merge-conflict resolution feature uses two independently hand-written state machines to parse the same raw conflict-marker text: one (`extractConflictHunks`) to build the hunks sent to the Copilot model, and a second, structurally different one (`reassembleResolvedFile`) to splice the model's per-hunk answers back into the file that gets written to disk and staged for commit. The two parsers disagree on what counts as a "closing" `>>>>>>>` marker when an attacker-crafted repository state contains a stray 7-`>` sequence before the real `=======` separator. This causes `reassembleResolvedFile` to treat a real, well-formed conflict block as malformed and pass it through verbatim — literally re-emitting `<<<<<<<`/`=======`/`>>>>>>>` markers into the file that Desktop then writes and `git add`s as the "Copilot-resolved" commit content, with no downstream re-check for leftover markers.

## Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-238`) walks a conflicted file to build the hunks that are sent as context to the Copilot model: [1](#0-0) [2](#0-1) 

Its "collect ours" loop only terminates on a base marker (`|||||||`) or separator (`=======`); it never checks for a `>>>>>>>` line while collecting `ours`/`theirs` content, so a stray `>>>>>>>`-looking line appearing anywhere before the real closing marker is simply absorbed as ordinary content. The whole block from `<<<<<<<` to the real trailing `>>>>>>>` is treated as **one well-formed hunk**, and its content (including the stray marker text) is sent to the model, which returns exactly one `resolvedContent` entry for it.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), which later splices the model's hunk answers back into the on-disk file, uses a **different** boundary rule: [3](#0-2) 

Its lookahead loop breaks on the **first** line matching the theirs-marker regex, regardless of whether a separator was already seen. If a `>>>>>>>`-looking line occurs before the real `=======`, `hasSeparator` is still `false` when the loop breaks, so the block is classified as "malformed" and copied through **unchanged** — the literal `<<<<<<<`, the stray `>>>>>>>`, `=======`, and the real `>>>>>>>` all remain in the output, and `hunkIndex` is never advanced, so the model's resolution for that hunk is silently discarded.

This is a structural analog of the reported bug class: two independent parsers of the same input format disagree on where a structural unit (opcode sequence / conflict hunk) ends, and the parser responsible for the security-relevant guarantee (no leftover conflict markers in what gets committed) silently under-processes the input rather than erroring.

The only marker check in the pipeline is applied to the model's raw per-hunk output, not to the final reassembled file: [4](#0-3) 

The reassembled full-file content is written straight to disk and staged with no re-validation: [5](#0-4) 

## Impact Explanation
An attacker who controls a branch/PR that a Desktop user merges (or a repository state that produces a merge conflict) can shape the conflicting content so that, when the user clicks "Resolve with Copilot" → "Continue Merge", Desktop writes a file to disk and stages it (`git add`) that still contains raw `<<<<<<<`/`=======`/`>>>>>>>` conflict markers, while the UI has told the user the file was resolved. This is silent corruption of what the user commits: the resulting commit/push can contain broken source (syntax errors, disabled security checks left inside marker blocks, or one side's code silently dropped) that the user did not knowingly write and was not shown as unresolved. Because the write path (`_applyCopilotConflictResolutions`) only skips a file if git status already shows it as unconflicted (someone resolved it manually), it does not detect this class of malformed-marker corruption, since git's index/worktree state is not re-diffed after the write.

## Likelihood Explanation
Exploitation only requires crafting file content that produces this exact conflict (an ordinary, unprivileged git operation — no admin rights, no local access, no leaked credentials). The trigger is a normal merge conflict against attacker-controlled branch content, which fits the "attacker controls a cloned/fetched repository" pattern. It does require the user to opt into the Copilot conflict-resolution flow and click "Continue Merge", which is a feature the tool actively promotes; no unnatural steps beyond normal usage of the shipped feature are needed.

## Recommendation
Unify the hunk-boundary logic between `extractConflictHunks` and `reassembleResolvedFile` (e.g., share a single conflict-block scanner) so both agree on what constitutes a well-formed block. Additionally, after `reassembleResolvedFile` produces the final file content, re-run a conflict-marker check (the same regex/logic used by `isConflictWithMarkers`/`hasUnresolvedConflicts`) on the *entire reassembled file* before writing/staging it, and refuse to stage/commit if markers remain.

## Proof of Concept
1. Set up a merge that conflicts on a file with the following content (a stray `>>>>>>> stray` line inside the "ours" section, before the real separator):
```
<<<<<<< HEAD
ours line
>>>>>>> stray
=======
theirs content
>>>>>>> feature
```
2. In Desktop, trigger the merge, open the manual conflicts dialog, and click "Resolve with Copilot".
3. `extractConflictHunks` sends this whole block as a single hunk to the model; the model returns one `resolvedContent`.
4. Click "Continue Merge" to invoke `_applyCopilotConflictResolutions`.
5. `reassembleResolvedFile` classifies the block as malformed (its lookahead hits `>>>>>>> stray` before seeing `=======`), copies the opening `<<<<<<< HEAD` line through literally, and never advances `hunkIndex` — none of the real conflict lines are replaced.
6. The resulting file (with literal `<<<<<<<`/`=======`/`>>>>>>>` markers intact) is written to disk and `git add`-ed, then included in the merge commit, while the Copilot dialog reports the file as resolved.
