## Analysis

The external report's core broken invariant: **a weighted quorum check counts raw signature entries without deduplicating signer identity**, letting one signer's repeated signature inflate the participation count past the threshold while genuine per-signer membership is only checked in a separate, decoupled step.

The Hyperbridge analog exists in the BEEFY consensus-proof verifiers (both the Solidity light-client and the Rust off-chain/pallet verifier), which verify a 2/3+1 supermajority of the relay-chain authority set purely by counting `votes`/`signatures` array length, then separately verifying merkle-multiproof membership for the indices claimed in that same array — with no check that the claimed authority indices (or recovered addresses) are distinct.

### Title
False BEEFY consensus quorum acceptance via duplicated validator votes in `verifyMmrUpdateProof`/`verify_mmr_update_proof` - (File: `evm/src/consensus/EcdsaBeefy.sol`, `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` and its Rust counterpart `verify_mmr_update_proof` compute the supermajority participation count from the raw length of the caller-supplied `votes`/`signatures` array, then separately verify merkle-multiproof membership of each entry's claimed authority index. Neither function rejects duplicate entries (same signature and/or same `authorityIndex` repeated). A single validator can repeat their own valid signature/index N times to satisfy `checkParticipationThreshold`/`check_participation_threshold` while the merkle-multiproof step only needs to re-validate that one real, legitimate leaf position — which trivially succeeds since it belongs to a real signer.

### Finding Description
In `evm/src/consensus/EcdsaBeefy.sol`: [1](#0-0) 

`sigLen` is `relayProof.signedCommitment.votes.length` — the raw array length — and is passed directly to `checkParticipationThreshold(sigLen, authoritySet.len)` with no dedup on `vote.authorityIndex` or the recovered `authority` address. The subsequent loop builds one `MerkleMultiProof.Leaf` per vote entry (including duplicates) and passes them all to `MerkleMultiProof.VerifyProof`. Because each duplicated entry references the *same* real authority index with the *same* recovered address, the multiproof step is proving the same genuine leaf repeatedly rather than proving N distinct authorities — the count used for the quorum threshold and the count of *actually distinct* signers diverge exactly as in the reported bug class.

The Rust verifier used off-chain/in-pallet has the identical structure: [2](#0-1) [3](#0-2) 

`signatures_length` (used for `check_participation_threshold`) is the raw length of `mmr.signed_commitment.signatures`, and `authority_indices`/`authority_leaves` are built per-entry with no uniqueness enforcement before calling `merkle_proof.verify`.

For contrast, other consensus verifiers in this same codebase explicitly guard against this exact class of bug: the BSC verifier rejects vote-bitset bits beyond the validator count, the sync-committee verifier does the same for `sync_committee_bits`, the Pharos verifier explicitly checks `Error::DuplicateParticipant` via a `BTreeSet` dedup: [4](#0-3) 
and GRANDPA's `finality_grandpa::validate_commit` explicitly rejects `num_duplicated_precommits() > 0`: [5](#0-4) 

BEEFY's ECDSA vote-array scheme is the one consensus client in this codebase missing an equivalent duplicate-signer/duplicate-index guard.

### Impact Explanation
A malicious (or compromised, but not privileged/admin) validator holding a single valid BEEFY key can submit a `RelayChainProof` where `votes` contains the same `(authorityIndex, signature)` pair repeated enough times to satisfy `checkParticipationThreshold` (2/3+1 of `authoritySet.len`), without any other validator's participation. If accepted, this becomes a trusted `BeefyConsensusState` update (new MMR root, and potentially rotates `currentAuthoritySet`/`nextAuthoritySet`), which is the root of trust for all subsequent parachain header / state-commitment verification on Hyperbridge. This directly enables false remote-state acceptance — the exact "must never let false remote state become trusted" pivot — and can cascade into forged request/response delivery proofs, fraudulent relayer reward claims, or fund-moving message execution based on a falsely finalized MMR root.

### Likelihood Explanation
Exploitability requires only one real, currently-in-set validator's private key (no admin, no relayer collusion, no governance) — the attacker crafts the `RelayChainProof.signedCommitment.votes` array themselves and submits it via the public `verify` entrypoint / `submit_proof` message path. The merkle-multiproof step does not block this because it only needs to prove that one real leaf exists at the repeated index, which is true. This is a directly attacker-controlled input path.

### Recommendation
In both `verifyMmrUpdateProof` (Solidity) and `verify_mmr_update_proof` (Rust), before computing/using the participation count:
- Deduplicate on `authorityIndex` (and/or recovered address) across the `votes`/`signatures` array, rejecting the proof if any index repeats.
- Compute `checkParticipationThreshold`/`check_participation_threshold` using the count of *unique* authority indices rather than raw array length.

### Proof of Concept
1. Attacker controls authority index `X` (a real, current-epoch BEEFY validator) with valid ECDSA key.
2. Attacker signs the legitimate `commitmentHash` once, producing `sig`.
3. Attacker builds `RelayChainProof.signedCommitment.votes = [Vote(X, sig), Vote(X, sig), ..., Vote(X, sig)]` (repeated `N = ceil(2*total/3)+1` times) and a merkle multiproof that only needs to prove the single real leaf at index `X` (reused for each duplicated entry).
4. Calls `verify(previousState, proof)` on `EcdsaBeefy` (or submits the equivalent unsigned extrinsic/message that reaches `verify_mmr_update_proof`).
5. `sigLen == N` passes `checkParticipationThreshold(N, authoritySet.len)`. `MerkleMultiProof.VerifyProof` succeeds because it is validating the same genuine leaf `X` each time. `BeefyConsensusState` is updated with attacker-influenced/forged MMR root data despite zero other validators participating.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
