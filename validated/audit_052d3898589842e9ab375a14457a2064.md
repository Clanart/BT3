### Title
Unauthenticated JSON-RPC `send_tx` Allows Attacker-Controlled `rbf_signing_info` to Trigger Arbitrary Sighash Signing, Enabling Theft of tx-sender-managed UTXOs — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The tx-sender's JSON-RPC `send_tx` endpoint carries **zero authentication**. Any caller who can reach the port can submit an `InsertTryToSendParams` payload with a fully attacker-controlled `rbf_signing_info` (including `vout`, `spend_path::KeyPath{tweak_merkle_root}`, and `tap_sighash_type`). The background loop will later call `send_rbf_tx → attempt_sign_psbt`, which blindly signs the sighash for the attacker-specified input index using the tx-sender's private key. No guard checks that the input being signed is actually a UTXO the tx-sender is supposed to spend. The result is a valid Schnorr signature over an attacker-crafted sighash, enabling theft of the tx-sender's fee-payer UTXOs.

---

### Impact Explanation

The tx-sender's signing key controls its fee-payer UTXOs — P2TR outputs at the tx-sender's address used to fund CPFP and RBF fee bumps. An attacker who can reach the JSON-RPC port can:

1. Scan the chain for UTXOs at the tx-sender's P2TR address.
2. Craft a transaction spending one of those UTXOs to an attacker-controlled address.
3. Submit it via `send_tx` with `fee_paying_type=RBF` and `rbf_signing_info={vout:0, spend_path:KeyPath{tweak_merkle_root:None}, tap_sighash_type:Default}`.
4. Bitcoin Core's `walletcreatefundedpsbt` adds `witness_utxo` for the tx-sender's input (it's in the UTXO set), funds the fee, and `wallet_process_psbt` returns `complete=false` (the input is not a wallet key).
5. `attempt_sign_psbt` computes the sighash and signs it — producing a valid witness for the tx-sender's UTXO.
6. The transaction is broadcast; the tx-sender's fee funds are stolen.

**Clarification on scope**: The tx-sender's key alone cannot spend bridge-controlled UTXOs (those require the n-of-n multisig). The direct impact is **theft of tx-sender-managed balances** (fee-payer UTXOs), which is explicitly in scope per the allowed impact gate. Liveness of the bridge is also degraded because the tx-sender can no longer pay fees for critical bridge transactions (kickoff, challenge, reimbursement).

### Likelihood Explanation

- If `TX_SENDER_JSONRPC_BIND=0.0.0.0` (explicitly supported by the code), any network-reachable attacker can exploit this immediately.
- If `TX_SENDER_JSONRPC_BIND=127.0.0.1` (default), any co-located process (e.g., a compromised sidecar, a malicious dependency, or SSRF in another service on the same host) can exploit it.
- No authentication, no rate limiting beyond the body-size cap, no HMAC, no token — the attack requires a single HTTP POST.

---

### Recommendation

1. **Add authentication** to the JSON-RPC server (e.g., a shared secret/bearer token validated in a `jsonrpsee` middleware layer, or restrict to Unix domain socket with filesystem permissions).
2. **Validate `rbf_signing_info` on ingestion**: verify that the specified `vout` corresponds to an input whose `previous_output` is a UTXO controlled by the tx-sender's own key before persisting it.
3. **Inside `attempt_sign_psbt`**: after computing the sighash, verify that the `script_pubkey` of the prevout at `input_index` matches the tx-sender's expected P2TR address (with the claimed `tweak_merkle_root`) before signing.
4. Consider restricting the JSON-RPC to a Unix socket rather than a TCP port to eliminate network exposure entirely.

### Proof of Concept

```
1. Start tx-sender with TX_SENDER_JSONRPC_BIND=0.0.0.0 and a funded signing key.
2. Find UTXO U at the tx-sender's P2TR address (xonly_pk, no merkle root).
3. Build raw tx T: input=U, output=attacker_address (value = U.value - fee).
4. POST to http://<host>:3030:
   {
     "jsonrpc":"2.0","id":1,"method":"send_tx",
     "params":[{
       "signed_tx_hex": "<hex of T>",
       "fee_paying_type": "RBF",
       "rbf_signing_info": {
         "vout": 0,
         "spend_path": {"KeyPath": {"tweak_merkle_root": null}},
         "tap_sighash_type": "Default"
       },
       "tx_metadata": null,
       "cancel_outpoints":[], "cancel_txids":[],
       "activate_txids":[], "activate_outpoints":[]
     }]
   }
5. Wait for the background loop to call send_rbf_tx → attempt_sign_psbt.
6. Observe the transaction broadcast; U is now spent to attacker_address.
```

The signature produced by `attempt_sign_psbt` is a valid BIP-340 Schnorr signature over the sighash of T committing to U's `script_pubkey` and `value`, signed with the tx-sender's untweaked keypair — accepted by Bitcoin consensus.

    pub(crate) fn sign_with_tweak_data(
        &self,
        sighash: TapSighash,
        tweak_data: TapTweakData,
    ) -> Result<schnorr::Signature, BridgeError> {
        let keypair;
        let keypair_ref = match tweak_data {
            TapTweakData::KeyPath(merkle_root) => {
                keypair = calc_tweaked_keypair(&self.keypair, merkle_root)?;
                &keypair
            }
            TapTweakData::ScriptPath => &self.keypair,
            TapTweakData::Unknown => return Err(eyre::eyre!("Spend Data Unknown").into()),
        };

        Ok(SECP
            .sign_schnorr_no_aux_rand(&Message::from_digest(sighash.to_byte_array()), keypair_ref))
    }
