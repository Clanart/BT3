### Title
Bridge circuit never verifies payout transaction pays `bridge_amount` to the withdrawer - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs) only checks that `input.payout_spv.transaction.input[payout_input_index].previous_output` matches the `(txid, vout)` pair returned by `verify_storage_proofs`, but never inspects the value of any output of the payout transaction. `deposit_constant` and `journal_hash` are computed purely from `move_txid`, `operator_xonlypk`, watchtower pubkeys, `round_txid`, `kickoff_round_vout`, and `genesis_state_hash` — none of which encode the amount actually paid to the withdrawer.

### Finding Description
The claimed binding, stated as an equality, is:
`value_paid_to_withdrawer_in_payout_tx == bridge_amount_recorded_by_citrea_withdraw`

Tracing `bridge_circuit`:
- `verify_storage_proofs` (circuits-lib/src/bridge_circuit/storage_proof.rs, `verify_storage_proofs` fn) extracts only `wd_outpoint` (txid), `vout`, and `move_txid` from the Citrea Bridge contract's JMT storage proof. [1](#0-0)  There is no storage slot read or value comparison for the withdrawal amount anywhere in this function.
- Back in `bridge_circuit`, the only checks tying the payout transaction to the withdrawal are two `assert_eq!` calls comparing `user_wd_txid`/`vout` against `input.payout_spv.transaction.input[payout_input_index].previous_output`. [2](#0-1) 
- Immediately after, the circuit extracts only the first OP_RETURN output (for the operator xonly pubkey) via `get_first_op_return_output`, and never iterates or reads `input.payout_spv.transaction.output[..].value` for any output, including the output(s) actually paying the withdrawer. [3](#0-2) 
- `deposit_constant` is computed strictly from `operator_xonlypk`, watchtower pubkey digest, `move_txid`, `round_txid`, `kickoff_round_vout`, and `genesis_state_hash` — no amount field is included. [4](#0-3) 
- `journal_hash` further hashes only block hashes, watchtower flags, and `deposit_constant`. [5](#0-4) 

Root cause: the circuit's design binds the payout transaction to the withdrawal solely by matching the spent outpoint identity (txid:vout), which only proves that *some* input of the payout tx consumes the exact UTXO that Citrea recorded as the withdrawal request UTXO. It never proves anything about where the funds in that payout transaction actually went. An attacker (or operator) can therefore construct a payout transaction that spends `(user_wd_outpoint, vout)` as `input[payout_input_index]` but sends 0 sats to the withdrawer's address, routing 100% of the value to miner fees (or to themselves via another output), and the circuit will still produce the identical `journal_hash` it would have produced for a "correct" fully-paying transaction, because none of the amount-checking logic exists.

None of the listed guards intercept this: `verify_storage_proofs` only checks outpoint/vout identity and deposit txid, not amount; `SPV::verify` only proves inclusion of the payout tx in the claimed chain, not its output structure; `lc_proof_verifier` validates Citrea state transition/L1 block hash, not the payout tx contents; there is no `SECP.verify_schnorr` or musig2 step in this file that binds to output values; and the presigned transaction graph (kickoff/round/reimburse) does not, at this layer, reference payout amounts either — the reimbursement transaction's approval hinges only on the `journal_hash` matching between the guest-committed circuit output and what verifiers check off-chain against the presigned reimburse path.

### Impact Explanation
This falls under Critical - BTC leaving a move-to-vault UTXO without a matching fronted withdrawal. If nothing outside the bridge circuit (e.g., in `core/src/verifier.rs`'s deposit/payout acceptance logic, or the disprove path) independently re-derives and checks the payout amount against `bridge_amount` before the Reimburse transaction is allowed to spend the move-to-vault UTXO, then an operator (or anyone constructing a payout tx that references the exact recorded outpoint) can claim reimbursement without ever having fronted the withdrawer, draining the vault UTXO for the deposit's `bridge_amount` while the actual withdrawer receives nothing. This is repeatable per withdrawal/deposit, since the vulnerable check is generic and does not depend on deposit-specific parameters.

### Likelihood Explanation
I was not able to fully confirm, within the scope of this investigation, whether the value check is performed elsewhere in the transaction-acceptance pipeline (e.g., in `core/src/verifier.rs`'s payout/kickoff validation, `core/src/task/payout_checker.rs`, or `core/src/builder/transaction/creator.rs`, all of which reference `bridge_amount`) before the operator is allowed to start the reimbursement flow, since the file scoped by the question (`circuits-lib/src/bridge_circuit/mod.rs`) is confirmed to have no such check. This is a partial, not full, confirmation — a definitive verdict requires establishing that no other component in the pipeline enforces `value_paid_to_withdrawer_in_payout_tx == bridge_amount` before a Reimburse transaction referencing this journal is broadcast and accepted.

### Recommendation
In `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs), after locating the input at `payout_input_index`, also read and verify the amount of the output paying the withdrawer address recorded by Citrea's `withdraw` call (comparing it against the protocol's fixed `bridge_amount`, and verifying the destination script matches the withdrawer's requested script), and fold this into `deposit_constant`/`journal_hash` so a payout transaction that under-pays the withdrawer cannot produce the same journal as a correctly-funded one.

### Proof of Concept
Cannot be fully constructed as a self-contained `cargo test` without confirming (via reading `core/src/verifier.rs`, `core/src/task/payout_checker.rs`, and `core/src/builder/transaction/creator.rs` in more depth, which I did not have iterations left to complete) whether an equivalent amount check exists elsewhere in the reimbursement acceptance pipeline outside this circuit. Based purely on `circuits-lib/src/bridge_circuit/mod.rs`, the following test would demonstrate the gap at the circuit level:
1. Build a `BridgeCircuitInput` whose `payout_spv.transaction` spends the correct `(user_wd_outpoint, vout)` at `payout_input_index` but whose outputs consist of a single OP_RETURN (operator xonlypk) output and no output paying the withdrawer (i.e., all value implicitly goes to fees).
2. Call `bridge_circuit(&guest, work_only_image_id)` (or directly call `deposit_constant`/`journal_hash` with the same parameters as a "correct" payout with a full withdrawer payment) and assert the two `journal_hash` outputs are bit-for-bit identical.
3. Assert no panic occurs and `guest.commit` receives the same `journal_hash.as_bytes()` in both the zero-value and full-value cases, proving the value paid to the withdrawer is not part of the committed journal.

pub fn verify_storage_proofs(
    storage_proof: &StorageProof,
    state_root: [u8; 32],
) -> (WithdrawalOutpointTxid, u32, MoveTxid) {
    let utxo_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_utxo)
            .expect("Failed to deserialize UTXO storage proof");

    let vout_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_vout)
            .expect("Failed to deserialize vout storage proof");

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_deposit_txid)
            .expect("Failed to deserialize deposit storage proof");

    let storage_address: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(UTXOS_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let storage_key_utxo: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2);

    let storage_key_vout: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2 + 1);

    let storage_address_deposit: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(DEPOSIT_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let deposit_storage_key: alloy_primitives::Uint<256, 4> =
        storage_address_deposit + U256::from(storage_proof.index);

    let deposit_storage_key_bytes = deposit_storage_key.to_be_bytes::<32>();

    if deposit_storage_key_bytes != deposit_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid deposit storage key. left: {:?} right: {:?}",
            deposit_storage_key_bytes,
            deposit_storage_proof.key.as_b256().0
        );
    }

    if storage_key_utxo.to_be_bytes() != utxo_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal UTXO storage key. left: {:?} right: {:?}",
            storage_key_utxo.to_be_bytes::<32>(),
            utxo_storage_proof.key.as_b256().0
        );
    }

    if storage_key_vout.to_be_bytes() != vout_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal vout storage key. left: {:?} right: {:?}",
            storage_key_vout.to_be_bytes::<32>(),
            vout_storage_proof.key.as_b256().0
        );
    }

    storage_verify(&utxo_storage_proof, state_root);

    storage_verify(&deposit_storage_proof, state_root);

    storage_verify(&vout_storage_proof, state_root);

    let buf: [u8; 32] = vout_storage_proof.value.to_be_bytes();

    // ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract
    let vout = u32::from_le_bytes(
        buf[28..32]
            .try_into()
            .expect("Vout value conversion failed"),
    );

    let wd_outpoint = WithdrawalOutpointTxid(utxo_storage_proof.value.to_be_bytes());

    let move_txid = MoveTxid(deposit_storage_proof.value.to_be_bytes());

    (wd_outpoint, vout, move_txid)
}

pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}

pub fn journal_hash(
    payout_tx_blockhash: PayoutTxBlockhash,
    latest_blockhash: LatestBlockhash,
    challenge_sending_watchtowers: ChallengeSendingWatchtowers,
    deposit_constant: DepositConstant,
) -> blake3::Hash {
    let concatenated_data = [
        payout_tx_blockhash.0,
        latest_blockhash.0,
        challenge_sending_watchtowers.0,
    ]
    .concat();

    let binding = blake3::hash(&concatenated_data);
    let hash_bytes = binding.as_bytes();

    let concat_journal = [deposit_constant.0, *hash_bytes].concat();

    blake3::hash(&concat_journal)
}
