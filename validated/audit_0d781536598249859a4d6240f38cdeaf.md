### Title
Inconsistent host-param phishing check in OAuth callback bypasses the hardened embedded-host validation - (File: `app/controllers/shopify_app/callback_controller.rb`)

### Summary
`ShopifyApp::CallbackController#deduced_phishing_attack?` validates the `host` query parameter using a different, weaker code path than the one the maintainers hardened in `ShopifyApp::EmbeddedApp#safe_embedded_app_url`. This mirrors the AAVE report's bug class: a fix ("harden embedded app host validation to prevent parser-differential open redirects", changelog #2078) was applied to one location but an equivalent, reachable location was left using the old logic.

### Finding Description
`EmbeddedApp#redirect_to_embed_app_in_admin` decodes the `host` param and, before ever calling `ShopifyAPI::Auth.embedded_app_url`, runs it through `unsafe_embedded_host?`, which rejects control characters, backslashes, and `@` in the authority component, in addition to `sanitize_shop_domain` (Addressable-based) validation: [1](#0-0) 

By contrast, `CallbackController` — used at the end of the OAuth flow — decodes the host directly with the gem helper and only checks the resulting URI's `host` attribute using Ruby's stdlib `URI`, then feeds that into `sanitize_shop_domain`, without any of the `unsafe_embedded_host?` character/authority-confusion checks: [2](#0-1) 

Because the callback's check relies on Ruby's `URI` for `.host` extraction while `sanitize_shop_domain` internally reparses the string with `Addressable::URI`, a `host` value that is malformed in a way the two parsers disagree on (e.g., characters treated as authority-delimiters differently, backslashes, or embedded userinfo/`@`) can slip past `deduced_phishing_attack?` even though it would have been rejected by the hardened `unsafe_embedded_host?` gate used elsewhere in the same gem. This is exactly the same class of inconsistency as the AAVE report: the fix landed in one code path (`EmbeddedApp`) and not the sibling path (`CallbackController`) that performs the analogous check. [3](#0-2) 

If `deduced_phishing_attack?` returns `false` for an attacker-controlled `host`, `redirect_to_app` performs `redirect_to(redirect_to, allow_other_host: true)`: [4](#0-3) 

### Impact Explanation
A successful bypass results in the app redirecting, with `allow_other_host: true`, to an attacker-controlled host immediately after a real OAuth callback completes (session already stored). This can be used to redirect the merchant browser off-domain right after authentication, enabling phishing of the merchant/staff session or leakage of any sensitive query data appended to the redirect target — a concrete embedded-app-redirect / open-redirect issue in an unprivileged, externally reachable flow (the OAuth callback endpoint).

### Likelihood Explanation
Likelihood depends on finding a concrete string where Ruby's `URI` and `Addressable::URI` disagree on host parsing (a known general class of parser-differential bug, which is why the gem authors explicitly hardened the sibling code path against it). No authentication is required to reach `CallbackController#callback`; only a completed/valid-looking OAuth redirect with an attacker-chosen `host` parameter is needed, which an attacker can induce by directing a victim through the install/OAuth flow with a crafted `host` value.

### Recommendation
Route `deduced_phishing_attack?` through the same hardened validation used in `EmbeddedApp#safe_embedded_app_url` (i.e., reuse `unsafe_embedded_host?`/`unsafe_embedded_host_characters?`/`embedded_host_authority` before computing/trusting the host), or refactor both call sites to share a single validation helper so future hardening can't silently miss one of the two paths.

### Proof of Concept
1. Trigger the OAuth flow for a shop so that Shopify redirects the victim to `GET /auth/shopify/callback?code=...&shop=...&state=...&timestamp=...&hmac=...&host=<attacker-crafted-base64>`.
2. Craft `host` so that after `ShopifyAPI::Auth.embedded_app_url` decoding, the resulting string is malformed in a way that Ruby's `URI(...).host` and `Addressable::URI` (used internally by `sanitize_shop_domain`) disagree on the parsed host/authority (e.g., strings using backslashes or authority-confusing separators that the `unsafe_embedded_host?` check in `embedded_app.rb` would have rejected).
3. If `sanitize_shop_domain(URI(decoded_host).host)` returns non-nil despite the underlying host effectively being attacker-controlled, `deduced_phishing_attack?` returns `false`, and `redirect_to_app` issues `redirect_to(redirect_to, allow_other_host: true)` to the attacker's domain right after a legitimate OAuth completion.

    def safe_embedded_app_url(host)
      decoded_host = Base64.decode64(host.to_s)
      return if deduced_phishing_attack?(decoded_host)

      ShopifyAPI::Auth.embedded_app_url(Base64.strict_encode64(decoded_host))
    end

    def deduced_phishing_attack?(decoded_host)
      sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(decoded_host) unless unsafe_embedded_host?(decoded_host)
      if sanitized_host.nil?
        message = "Host param for redirect to embed app in admin is not from a trusted domain, " \
          "redirecting to root as this is likely a phishing attack."
        ShopifyApp::Logger.info(message)
      end
      sanitized_host.nil?
    end

    def unsafe_embedded_host?(decoded_host)
      return true if decoded_host.empty? || !decoded_host.valid_encoding?
      return true if unsafe_embedded_host_characters?(decoded_host)

      embedded_host_authority(decoded_host).include?("@")
    end
