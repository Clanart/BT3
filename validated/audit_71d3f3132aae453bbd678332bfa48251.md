### Title
CW20-over-ERC20 wrapper contract treats a boolean-`false` ERC20 `transfer`/`transferFrom` return as success, enabling fake-deposit/fake-transfer confirmation to downstream CosmWasm contracts - ([File: example/cosmwasm/cw20/src/contract.rs])

### Summary
The production ERC20→CW20 wrapper contract (compiled and embedded as `cwerc20.wasm`, `CurrentVersion 2`) executes the wrapped ERC20's `transfer`/`transferFrom` via an EVM delegatecall and treats *any non-reverting* call as a successful transfer, without ever decoding/checking the ERC20 boolean return value. This mirrors the reported DODO issue: contracts assume `IERC20.transfer`/`transferFrom` semantics without validating the returned success flag.

### Finding Description
`execute_transfer`/`execute_transfer_from` in the CW20 wrapper (`transfer`/`transfer_from` in `example/cosmwasm/cw20/src/contract.rs`) build a `DelegateCallEvm` message pointing at the wrapped ERC20 address and simply queue it in the `Response`: [1](#0-0) [2](#0-1) 

The CosmWasm message handler that actually executes this delegatecall (`HandleInternalEVMDelegateCall` → `CallEVM`) only errors if the EVM execution itself reverts (`res.Err != nil`); it never inspects/decodes `res.ReturnData` to confirm the ABI-encoded `bool` returned by `transfer`/`transferFrom` is `true`: [3](#0-2) 

Because the CW20 wrapper's `Response` (including the `Cw20ReceiveMsg` sub-message dispatched to a receiving contract in `execute_send`/`execute_send_from`) is generated unconditionally once the delegatecall doesn't revert, any ERC20 token that returns `false` on failure instead of reverting (the exact non-standard-compliance pattern called out in the original DODO report) will cause the wrapper to report a successful transfer and forward a `Cw20ReceiveMsg` to the target contract, even though the underlying ERC20 balance never moved.

This is distinct from the well-known "USDT missing return value" issue in that it's the *opposite* class of non-compliance handled unsafely: tokens that return `false` (rather than reverting) on failure are silently accepted as successful transfers.

### Impact Explanation
Any CosmWasm contract that trusts the wrapper's success response or the forwarded `Cw20ReceiveMsg` (e.g., a vault, AMM, or lending contract crediting a user based on receipt of the CW20 wrapper's `send`/`send_from`) can be tricked into crediting deposits/transfers that never actually happened on the ERC20 side, when the wrapped token is one that returns `false` instead of reverting on failed transfers. This is a fund-loss vector for any downstream Cosmwasm integrator relying on the pointer/wrapper's `Response` to signal token movement.

### Likelihood Explanation
Exploitability depends on the specific ERC20 token pointed to by the CW20 wrapper (`ERC20_ADDRESS`) exhibiting the "return false on failure" non-standard behavior, and on a downstream contract trusting the wrapper's `Cw20ReceiveMsg`/success response without independently verifying balances. This is a real but token-dependent condition, reachable by any unprivileged user who can call `execute_transfer`/`execute_send`/`execute_transfer_from`/`execute_send_from` on a CW20-ERC20 pointer contract wrapping such a token.

### Recommendation
In `example/cosmwasm/cw20/src/contract.rs` (and correspondingly `x/evm/keeper/evm.go`'s `CallEVM`/`HandleInternalEVMDelegateCall` path used by it), decode the ABI-encoded boolean return value from the ERC20 `transfer`/`transferFrom` call and fail the CosmWasm execution (return `ContractError`) if it is `false`, mirroring OpenZeppelin `SafeERC20`'s pattern of validating both call success and the returned boolean before treating a transfer as complete.

### Proof of Concept
1. Deploy (or point to) an ERC20 contract whose `transfer`/`transferFrom` returns `false` on insufficient balance/authorization instead of reverting.
2. Create a CW20-over-ERC20 wrapper (`ERC20_ADDRESS` set to that token) using the embedded `cwerc20.wasm` contract.
3. Call `execute_send`/`execute_send_from` on the wrapper targeting a receiving contract that trusts `Cw20ReceiveMsg` to represent a successful deposit, using an amount that the underlying token will refuse (returns `false`).
4. Observe: the wrapper's delegatecall to the ERC20 does not revert (`CallEVM` succeeds since `res.Err == nil`), so the wrapper's `Response` succeeds and dispatches `Cw20ReceiveMsg` to the receiving contract, which credits the sender despite no actual ERC20 balance change — confirmed by inspecting `example/cosmwasm/cw20/src/contract.rs` lines 227-274 and `x/evm/keeper/evm.go` lines 79-123, neither of which decodes/validates the ERC20 boolean return value.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

		return nil, fmt.Errorf("%w: code size %v, limit %v", core.ErrMaxInitCodeSizeExceeded, len(data), params.MaxInitCodeSize)

	if to != nil && to.Cmp(common.HexToAddress(solo.SoloAddress)) == 0 {
		return nil, errors.New("cannot call Solo precompile via CosmWasm")
	}
	value := utils.Big0
	if val != nil {
		if val.IsNegative() {
			return nil, sdkerrors.ErrInvalidCoins
		}
		value = val.BigInt()
	}
	// This call was not part of an existing StateTransition, so it should trigger one
	executionCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx)).WithEVMEntryViaWasmdPrecompile(false)

	if res.Err != nil {
		return nil, res.Err
	}
