### Title
Case-sensitive dotcom-redirect check in `SignInStore.setEndpoint` can misclassify a GitHub.com-equivalent URL as an Enterprise endpoint - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.setEndpoint` decides whether a user-typed URL is GitHub.com or a GitHub Enterprise host using a case-sensitive regular expression, while URL/host normalization elsewhere in the stack (JS `URL` parsing) is case-insensitive for hostnames. A mixed-case variant of `github.com`/`api.github.com` bypasses the dotcom-redirect check, is treated as an Enterprise endpoint, and is passed to `getEnterpriseAPIURL` before the store looks up `existingAccount` via `accounts.find(x => x.endpoint === endpoint)`.

### Finding Description
The dotcom-redirect guard is: [1](#0-0) 

This regex has no `i` flag, so `https://GitHub.com`, `https://API.Github.com`, etc. do **not** match and are not redirected to `beginDotComSignIn`. Instead they fall through to `validateURL` (which preserves the original casing of the address, only prefixing `https://` if no host is detected) and then `getEnterpriseAPIURL(validUrl)`: [2](#0-1) [3](#0-2) 

The resulting `endpoint` is used for an exact-string lookup against existing accounts: [4](#0-3) 

If `getEnterpriseAPIURL` normalizes the host to lowercase internally (e.g., via `new URL(...).hostname`, which JS always lowercases) and the resulting computed endpoint string happens to equal an existing dotcom account's stored `endpoint` (`https://api.github.com`), the store would set `existingAccount` to that dotcom account inside an `ExistingAccountWarning` state that is otherwise intended for Enterprise re-authentication. The rendering layer trusts this state without independently re-validating that `existingAccount.endpoint` matches the host the user actually typed: [5](#0-4) [6](#0-5) 

On continuing, the wrapper dispatches `removeAccount(state.existingAccount)` for whatever account object is embedded in that state: [7](#0-6) 

**Unverified part:** I could not retrieve the body of `getEnterpriseAPIURL` (nor `getDotComAPIEndpoint`) in `app/src/lib/api.ts` before running out of tool iterations, so I cannot confirm whether it actually produces a string literally equal to `https://api.github.com` for a mixed-case Enterprise-looking input, or whether it always appends a distinguishing suffix (e.g. `/api/v3`) that would prevent the collision. Without that confirmation, the exact-match collision with a dotcom account's `endpoint` field is plausible but not proven.

### Impact Explanation
If the collision is achievable, `renderExistingAccountWarningStep` would display a warning naming the wrong host/account pairing (Enterprise host in the message text, but a dotcom `Account` object bound as `existingAccount`), and continuing would force-sign-out the user's actual GitHub.com account instead of any Enterprise account — a legitimate, valid dotcom session would be silently destroyed based on a typo/case variant the user did not intend as equivalent to github.com.

### Likelihood Explanation
Low-to-moderate, and unconfirmed. It requires: (1) the user (or an attacker via a deep link/credential-helper flow that calls `setSignInEndpoint`) to supply a mixed-case variant of `github.com`/`api.github.com` that bypasses the case-sensitive regex, and (2) `getEnterpriseAPIURL` to normalize that into the exact literal dotcom API endpoint string. Point (2) is the part I could not verify from the code retrieved.

### Recommendation
- Make the dotcom-redirect check in `sign-in-store.ts` case-insensitive (add `i` flag) and normalize the URL (e.g., via `new URL()`) before testing, rather than testing the raw string.
- Regardless of `getEnterpriseAPIURL`'s current behavior, ensure it can never produce a value equal to `getDotComAPIEndpoint()` for non-canonical input, or add an explicit guard rejecting/redirecting any Enterprise endpoint whose normalized host resolves to `github.com`/`api.github.com`.

### Proof of Concept
Not fully verified end-to-end due to missing confirmation of `getEnterpriseAPIURL`'s normalization; the concrete reproduction would be:
1. Have an existing GitHub.com account signed in.
2. Trigger the Enterprise sign-in flow and enter `https://API.Github.com` (or another case variant) as the endpoint.
3. Observe whether `SignInStore.setEndpoint` classifies it as Enterprise (bypassing the case-sensitive regex) and whether the subsequent `existingAccount` lookup matches the dotcom account.
4. If step 3 succeeds, continuing through `renderExistingAccountWarningStep` and confirming would call `removeAccount` on the dotcom account.

Given the confirmed case-sensitivity gap but unconfirmed downstream string-collision, I present this as a plausible but not fully proven finding — flagging the specific code fact I could verify (the regex) as the actionable weakness, and recommending it be hardened regardless of whether the exact collision in `getEnterpriseAPIURL` is reproducible.

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
