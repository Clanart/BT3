## Title
`updateRemoteUrl` silently rewrites a repository's `origin` remote based on unauthenticated GitHub API data, redirecting future pushes/fetches without user confirmation - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
The seeded report describes a single privileged mutation (`MochiEngine.setNFT`) that, once changed, silently redirects every downstream consumer (vault) to a new, unverified target, breaking the whole system's referential integrity with no user consent. The closest unprivileged analog in GitHub Desktop is `updateRemoteUrl`, which automatically calls `gitStore.setRemoteURL()` to repoint the local `origin` remote to whatever `clone_url` the GitHub API currently reports for the repository, with no user prompt, whenever a small set of heuristic conditions line up.

### Finding Description
`updateRemoteUrl` compares the current `origin` remote URL to the previously-cached `GitHubRepository.cloneURL` and the freshly-fetched `IAPIRepository.clone_url`: [1](#0-0) 

If the URL scheme (`https`/`ssh`) matches, and the current remote still matches the last cached `cloneURL` (i.e. the user hasn't manually edited it), but the API-reported `clone_url` no longer matches the current remote, the function calls `gitStore.setRemoteURL(...)`, which shells out to `git remote set-url` and silently changes where all future `git push`/`git fetch`/`git pull` operations go: [2](#0-1) 

The matching logic (`urlMatchesRemote`) only compares hostname/owner/name extracted via regex from the URL strings — it has no notion of repository identity (API ID), ownership continuity, or user confirmation: [3](#0-2) 

Because the trigger is simply "the API's `clone_url` for this GitHub repository record differs from the current remote," any legitimate-looking change reported by the API (e.g. a repository rename/transfer, or an owner login change reflected by the API) causes Desktop to automatically rewrite the git remote on disk — no dialog, no explicit user action, and no cross-check that the new destination is actually the same underlying repository the user originally trusted. This mirrors the seeded bug's core pattern: a single automatic write silently repoints every subsequent operation (all "vaults"/git commands) to a new target picked from external, attacker-influenced data.

### Impact Explanation
If an attacker can influence what `clone_url` is returned for a `GitHubRepository` record the user already has open in Desktop (for example, through a compromised/malicious GitHub Enterprise Server whose API responses Desktop trusts, or by controlling a repository that later gets renamed/transferred in a way that changes its reported clone URL while still resolving hostname/owner/name plausibly), Desktop will silently retarget the user's `origin` remote. Once retargeted:
- All subsequent `git push` operations (and the credentials/tokens attached via the trampoline credential helper, which resolves credentials by URL origin) go to the new destination instead of the repository the user believes they're working with.
- This is a "silent corruption of what the user commits or pushes" scenario — the user's future commits could be pushed to a different (attacker-controlled or attacker-renamed) endpoint without any visible change in the UI besides the remote URL, which most users never inspect.

This is not as sweeping as the seeded report's "entire protocol broken" (only one repository's remote is affected, not all repositories, and a same-origin GitHub host is still required for credential leakage to be relevant), so the severity is comparatively lower, but the invariant violated — "network destination changes only with explicit user consent" — is analogous.

### Likelihood Explanation
Likelihood is moderate-to-low and depends on external/enterprise-controlled conditions I could not fully verify from the codebase alone:
- The attacker must control or influence the GitHub/GHES API response for `clone_url` on a repository the victim has already added to Desktop (this typically requires a compromised GHES instance, a MITM position for GHES traffic, or a legitimate-looking repository rename/transfer scenario).
- The guard conditions (`protocolsMatch`, `remoteUrlUnchanged`) reduce the attack surface to cases where the user hasn't manually customized the remote and the protocol stays the same.
I was not able to fully trace every call site that feeds `apiRepo` into `updateRemoteUrl` within the indexed portion of the codebase (only the function definition and its test file were confidently located; the exact refresh/poll path in `app-store.ts` that invokes it was not retrieved in full), so I cannot state with certainty how frequently/automatically this runs (e.g., on every background repository refresh vs. only on manual actions).

### Recommendation
- Require explicit user confirmation (a dialog, similar to the existing `UpstreamAlreadyExists` dialog pattern already in the codebase) before rewriting the `origin` remote URL based on API data.
- Bind the "is this the same repository" check to a stable identifier (the GitHub repository's numeric API ID) rather than solely to a fuzzy hostname/owner/name string comparison in `urlMatchesRemote`.
- Log/audit and surface remote-URL changes made automatically by Desktop so users can detect unexpected retargeting.

### Proof of Concept
Conceptual trace (exact triggering call site in `app-store.ts` not fully confirmed due to indexing limits):
1. User has repository R cloned, with `origin` = `https://ghe.example.com/acme/app.git`, and Desktop's cached `GitHubRepository.cloneURL` also `https://ghe.example.com/acme/app.git`.
2. A subsequent Desktop background refresh calls the GitHub API for repository R and receives an `IAPIRepository` whose `clone_url` field has changed (e.g., because the attacker-influenced GHES instance now reports a different, but hostname/owner/name-plausible, clone URL).
3. `updateRemoteUrl` finds `protocolsMatch = true`, `remoteUrlUnchanged = true` (matches old cached cloneURL), and `urlsMatch = false` (new API url differs) — [4](#0-3)  — and calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)`.
4. `setRemoteURL` executes `git remote set-url origin <new-url>` [2](#0-1)  with no user prompt.
5. The next time the user pushes, Desktop pushes to the new, unconfirmed URL.

Note: I could not verify the exact scheduling/frequency of the call site that supplies `apiRepo` to `updateRemoteUrl`, nor confirm whether GitHub.com itself could realistically supply a divergent `clone_url` for the same repo ID outside of a GHES/MITM scenario. A Devin session with full repository access would be needed to trace `app-store.ts`'s invocation of `updateRemoteUrl` end-to-end and confirm the precise trigger conditions.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
