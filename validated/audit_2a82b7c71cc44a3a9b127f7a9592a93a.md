### Title
Direct token donation to MasterMagpie inflates `totalStaked()` and permanently dilutes reward accrual for legitimate stakers - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`totalStaked()` in `BaseRewardPoolV2.sol` reads `IERC20(stakingToken).balanceOf(operator)` directly instead of relying on an internally tracked sum of user deposits. An attacker can transfer `stakingToken` directly to the `operator` (MasterMagpie) address, inflating `totalStaked()` without crediting any account via `IMasterMagpie.stakingInfo`, which permanently dilutes the `rewardPerTokenStored` growth applied in `_provisionReward`.

### Finding Description
`totalStaked()` is defined as: [1](#0-0) 
This queries the raw ERC20 balance of the `operator` (MasterMagpie contract) rather than an internally accounted total of legitimate deposits. Meanwhile, `balanceOf(_account)` for individual users is tracked separately via `IMasterMagpie(operator).stakingInfo`: [2](#0-1) 

These two values are not guaranteed to stay in sync: a plain `stakingToken.transfer(operator, amount)` call by any unprivileged holder increases the value returned by `totalStaked()` but does not update any user's `stakingInfo` entry in MasterMagpie.

When rewards are subsequently queued, `_provisionReward` computes the new `rewardPerTokenStored` increment as: [3](#0-2) 
Because the denominator `totalStaked()` is inflated by the donated (unattributed) tokens, the per-token increment is smaller than it should be for the actual staked supply. Since `earned()`/`_earned()` compute a user's yield from `userShare * (rewardPerToken - paid)`, and `userShare` (`balanceOf`) is unaffected by the donation, every real staker's accrued yield for that reward distribution is permanently reduced — the "missing" portion corresponding to the phantom donated balance is not owed to (and cannot be claimed by) anyone, since no account is credited with it in `stakingInfo`. This effectively locks/underpays real stakers' yield for every future `queueNewRewards`/`donateRewards` call until the donated tokens are somehow removed from the operator's balance (which the reward pool has no mechanism to do).

`BaseRewardPool.sol` (v1) exhibits the identical pattern, confirming this is a design choice reused across the reward-pool implementations rather than a one-off bug in V2. [4](#0-3) 

No modifier, reentrancy guard, or reward-index recomputation logic protects against this, since the flaw is in the choice of `totalStaked()`'s data source, not a reentrancy/access-control gap.

### Impact Explanation
This is a permanent, uncorrectable dilution of unclaimed yield for all legitimate stakers in the pool — every subsequent reward distribution computed while the donated balance sits in the operator contract permanently underpays real depositors proportional to `donatedAmount / (donatedAmount + realStaked)`. This matches the "theft or permanent freezing of unclaimed yield" impact class. The loss is realized immediately at the next `queueNewRewards`/`donateRewards` call and is not automatically reversible (there is no sweep/skim function in the shown code that returns the balance to `totalStaked()`'s legitimate baseline), so it persists indefinitely, well beyond 24 hours, until a privileged actor intervenes (out of scope for the attacker's own remediation).

### Likelihood Explanation
The attack requires only that the attacker hold `stakingToken` (freely purchasable/mintable depending on the token) and call the standard ERC20 `transfer` function targeting the MasterMagpie `operator` address — no special privileges, flash loans, or reentrancy needed. It is cheap (only the cost of the donated tokens, which can be a trivial "dust" amount relative to `totalStaked()` to have a small-but-nonzero effect, or a larger amount for greater dilution) and fully repeatable by any unprivileged actor at any time.

### Recommendation
Track `totalStaked` as an internal state variable incremented/decremented exclusively inside `deposit`/`withdraw` flows initiated through MasterMagpie (mirroring the sum of `stakingInfo` balances), rather than deriving it from `IERC20.balanceOf(operator)`. This removes the ability for arbitrary direct transfers to influence the reward-per-token computation.

### Proof of Concept
Foundry test plan:
1. Deploy `stakingToken` (mock ERC20), `MasterMagpie`, and `BaseRewardPoolV2` wired to it; register a reward token and a `rewardManager`.
2. Have a legitimate staker deposit `X` tokens through MasterMagpie's normal deposit flow (crediting `stakingInfo`).
3. Record `rewardPerTokenStored` after queuing a reward of amount `R1` via `queueNewRewards` (baseline case with `totalStaked() == X`), and record the staker's `earned()` value.
4. Reset/redo in a second scenario: before queuing rewards, have the attacker call `stakingToken.transfer(masterMagpieAddress, D)` (a "dust" or large donation) — this is **not** a deposit, so `stakingInfo` for the attacker remains 0.
5. Call `manager.queueNewRewards(R1, rewardToken)` again with the donation present; assert `totalStaked() == X + D`.
6. Assert `rewardPerTokenStored` after this call is strictly lower than in the baseline (step 3) despite identical `R1` and `X`.
7. Call `staker.getReward()` and assert the claimed reward amount is strictly less than in the baseline scenario, quantifying the permanent yield loss equal to `R1 * D / (X + D)`.
