### Title
Unbounded length-prefixed deserialization loop in `SchnorrAggregate::read` enables attacker-controlled resource exhaustion (hang) - ([File: crypto/schnorr/src/aggregate.rs](https://github.com/serai-dex/serai))

### Summary
`SchnorrAggregate::read` trusts a raw `u32` count read directly from the input stream and iterates that many times performing elliptic-curve point deserialization (`C::read_G`) with no upper bound, no pre-validation, and no early termination beyond I/O error. This is the direct analog of CVE-2025-30721's "hang or frequently repeatable crash" class mapped onto Serai's untrusted-byte deserialization surface.

### Finding Description
At `crypto/schnorr/src/aggregate.rs:77-88`:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;

  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }

  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

An attacker supplies the 4-byte little-endian count. Two independent abuse modes exist:

1. **Proportional-work amplification**: each loop iteration performs a full `C::read_G`, which for `dalek-ff-group`/`ed448`/`kp256` suites is a point decompression — a field inversion / square-root and validity check, the most expensive scalar-free operation in the crate. A claimed count of `u32::MAX` (~4.29 billion) with a stream that serves bytes slowly or indefinitely (the reader is generic over `Read`, including streaming sources) hangs the deserializing thread effectively forever.
2. **Unbounded allocation**: each successful iteration `push`es a decoded point into `Rs`. With no capacity cap, memory grows linearly with attacker input; against a sufficiently large input this drives the process to OOM — a "frequently repeatable crash (complete DOS)."

Every other `read` path in the in-scope crates (e.g. `EncryptedMessage::read` at `crypto/dkg/pedpop/src/encryption.rs:171-177`, `EncryptionKeyProof::read` at `crypto/dkg/pedpop/src/encryption.rs:267-269`) reads a fixed number of group elements, so attacker input cannot multiply work. `SchnorrAggregate::read` is the only in-scope deserializer where a length prefix multiplies per-element decompression cost.

### Impact Explanation
Any component that feeds attacker-supplied bytes into `SchnorrAggregate::read` (or into a serialization format embedding it) can be made to hang or be killed by resource exhaustion, denying service to the signing/verification pipeline. This matches the CVE's availability-only impact class: no confidentiality or integrity loss, but complete DoS of the affected process, repeatable on demand by resubmitting the crafted payload.

### Likelihood Explanation
The payload is trivially small (4 bytes declaring `0xFFFFFFFF`, followed by attacker-controlled point encodings) and requires no privileges, no valid key material, and no protocol state — only the ability to get bytes into this deserializer. The constraint is reachability: impact requires an in-scope caller to pass untrusted input to `SchnorrAggregate::read` rather than a fixed-size signature path. Since aggregate verification (`SchnorrAggregate::verify`, same file) is designed to check signatures from multiple signers, its deserializer exists precisely to accept multi-party input. Severity is capped at Medium because the hang is linear-in-input work rather than a single-byte infinite loop.

### Recommendation
Bound the length prefix before iterating, consistent with the fact that `write` can never emit more elements than exist in memory:

```rust
let n = u32::from_le_bytes(len);
// Cap at a protocol-meaningful maximum number of aggregated signatures
if n > MAX_AGGREGATED_SIGNATURES {
  return Err(io::Error::new(io::ErrorKind::InvalidData, "aggregate too large"));
}
let mut Rs = Vec::with_capacity(usize::try_from(n).map_err(|_| ...)?);
for _ in 0 .. n {
  Rs.push(C::read_G(reader)?);
}
```

Alternatively, or additionally, size-check the reader when it is `&[u8]` (reject if `remaining_len < n * <C::G as GroupEncoding>::Repr::default().as_ref().len()`), which makes malformed counts fail in O(1) instead of O(n·decompression).

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;
use dalek_ff_group::Ed25519; // any in-scope ciphersuite

// Crafted input: length prefix = u32::MAX, followed by attacker-controlled
// point encodings. With a streaming reader the deserializer performs up to
// ~4.3 billion read_G decompressions or allocates until OOM.
let mut payload = Vec::new();
payload.extend_from_slice(&u32::MAX.to_le_bytes());
payload.extend(std::iter::repeat(0u8).take(1 << 20)); // attacker bytes
let _ = SchnorrAggregate::<Ed25519>::read(&mut Cursor::new(&payload));
// With a `Read` impl that throttles or never returns EOF, the loop hangs
// the calling thread; with a large enough buffer, `Rs` grows until OOM.
```

Note on scope/uncertainty: I verified the root cause exactly (the unbounded `u32` loop at `aggregate.rs:78-85`); I could not enumerate every caller of `SchnorrAggregate::read` within the in-scope `networks/bitcoin/src` and signing pipeline to confirm which specific production entry point exposes it to untrusted bytes — that confirmation is the remaining step before severity assignment. If no in-scope production path feeds attacker bytes to this function, the finding reduces to a latent hardening issue and should be downgraded accordingly.
