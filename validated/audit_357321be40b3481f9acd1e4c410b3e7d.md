## Finding



### Title
Submodule diff full path is built via unsanitized `Path.join` and can direct "Open Repository" outside the cloned repo - (File: app/src/lib/git/diff.ts)

### Summary
`buildSubmoduleDiff()` computes the path used to open a submodule as `Path.join(repository.path, path)`, where `path` is the submodule's path as reported by `git status`/`git diff` parsing (ultimately sourced from the repository's own tracked submodule entry). This value is not checked for path-traversal or absolute-path components, unlike the analogous flow for the `x-github-client://openrepo` deep link, which explicitly rejects absolute paths and calls `resolveWithin()` before touching the filesystem.

### Finding Description
`buildSubmoduleDiff` is invoked from `buildDiff()` whenever a changed file has a `submoduleStatus`, and computes: [1](#0-0) 
`fullPath` is derived purely from `file.path` joined onto `repository.path`, with no call to any traversal-safe join (such as the `resolveWithin()` helper Desktop already uses in a sibling code path): [2](#0-1) 

That `fullPath` is surfaced in the UI's submodule diff panel and, when the user clicks "Open Repository," is passed unchanged to `dispatcher.openOrAddRepository`: [3](#0-2) [4](#0-3) 

Just as the audited Solidity code failed to check `data.submoduleReservesSelector != bytes4(0)` before using it in `submodule.staticcall(...)`, here Desktop fails to check that the submodule's reported path stays within `repository.path` before using it in `Path.join()` and subsequently in `openOrAddRepository`. The equivalent guard already exists in the codebase (`isAbsolute(filepath)` check + `resolveWithin`) but is not applied to the submodule-diff path, showing the omission is a missing-check bug rather than a deliberate design choice.

### Impact Explanation
If a malicious/compromised repository records a submodule "path" value containing traversal segments (e.g. `../../../../Users/victim/.ssh`) in a `git status`/diff-visible gitlink entry, `buildSubmoduleDiff` computes a `fullPath` outside the cloned repository. Clicking the resulting "Open Repository on GitHub Desktop" suggestion causes Desktop to add/open an arbitrary directory as a tracked repository via `openOrAddRepository`, which could expose or operate on files/directories the user never intended to add to Desktop, and could be used to prime further Desktop operations (e.g. commits/pushes) against an unintended sensitive directory.

### Likelihood Explanation
Exploitability depends on whether current git tree/index validation permits a gitlink entry's recorded path to include `..`/absolute segments when read back by `git status --porcelain`. Modern git enforces path safety checks on checkout for such entries, so the practical reachability of a traversal payload through this exact code path is uncertain without further verification in a live git environment; this reduces confidence relative to a fully confirmed proof, but the missing defensive check itself is a genuine gap since Desktop already treats analogous untrusted path fields (from URL actions) as unsafe and validates them, while this one is not validated at all.

### Recommendation
Apply the same guard used in `openRepositoryFromUrl` to `buildSubmoduleDiff`/`onOpenSubmoduleClick`: reject `path` values that are absolute, and resolve `fullPath` with a traversal-safe helper (e.g. `resolveWithin(repository.path, path)`) before it is stored on the diff object or passed to `openOrAddRepository`, refusing to render/act on the "Open Repository" action if resolution fails.

### Proof of Concept
1. Construct/obtain a repository whose tree contains a gitlink (submodule) entry whose recorded path string includes traversal segments (e.g. `../../outside`).
2. Have the victim clone/fetch and open this repository in GitHub Desktop, then view the changed file in the Changes/History diff view so `buildSubmoduleDiff` runs and computes `fullPath = Path.join(repository.path, '../../outside')`. [5](#0-4) 
3. Click "Open Repository on GitHub Desktop" in the submodule diff panel. [6](#0-5) 
4. Observe `dispatcher.openOrAddRepository(fullPath)` is called with the traversal-resolved path, outside the original repository, with no `isAbsolute`/`resolveWithin`-style check applied (contrast with the guarded `filepath` handling in `openRepositoryFromUrl`). [3](#0-2)
