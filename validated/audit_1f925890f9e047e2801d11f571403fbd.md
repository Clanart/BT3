### Title
Silent remote URL rewrite trusts stale GitHub API state as an implicit invariant instead of verifying user intent - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently calls `git remote set-url` to repoint a repository's `origin` remote whenever the cached GitHub API `clone_url` disagrees with the current git remote, gated only by a same-protocol check and a "previously matched" heuristic (`remoteUrlUnchanged`). Like the Alchemix `_melt` bug — which assumed a 1:1 price relationship and used `balanceOf` as a stand-in for real slippage protection — this code assumes that "the API repo used to match the remote, and protocols still agree" is a safe proxy for "the user still wants this remote pointed here," and skips any confirmation or stronger validation. Because the trigger value (`apiRepo.clone_url`) comes from GitHub's API and can change for reasons fully outside the local user's control (repo rename, ownership transfer, or a compromised/duplicated repo on the same host — including GitHub Enterprise Server instances Desktop is configured to trust), this "invariant" does not actually guarantee the new URL is safe or intended.

### Finding Description
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` computes:
- `urlsMatch`: whether the git remote URL still matches the latest API `clone_url` via `urlMatchesRemote`.
- `remoteUrlUnchanged`: whether the *stored* `GitHubRepository.cloneURL` still matches the current remote.
- `protocolsMatch`: whether URL protocol strings are equal. [1](#0-0) 

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, it calls `gitStore.setRemoteURL(...)` with the new `clone_url`, with no user confirmation. The matching logic (`urlMatchesRemote`/`urlsMatch`) is a loose comparison of hostname/owner/name derived from `parseRemote`/`parseRepositoryIdentifier`, not a cryptographic or identity-based check. [2](#0-1) 

This mirrors the reported bug's broken-invariant pattern: a value that *sounds* like a safety check (`remoteUrlUnchanged`, "the URL used to match") is treated as sufficient proof that repointing the remote is safe, when in fact it only reflects an assumption ("GitHub API clone_url data is trustworthy and monotonically correct") that does not always hold — analogous to assuming alETH is always ≤ WETH price. The GitHub API `clone_url` value is fetched by Desktop's normal repo-refresh flow and stored/used elsewhere (e.g. `app-store.ts`, `api-repositories-store.ts`), so any attacker who can influence what API repository object is associated with the local repository (e.g., through a malicious/renamed repo served by an Enterprise instance, or by causing the app to briefly associate the local repo with a different GitHub repository object) can cause Desktop to silently rewrite `origin` to a different host/owner/repo without any user prompt. [3](#0-2) 

### Impact Explanation
If `origin` is silently rewritten to attacker-controlled infrastructure, subsequent `git push` operations (and any credential/token handling tied to the remote host, e.g. `envForRemoteOperation`) will target the attacker's endpoint instead of the legitimate one — corrupting what the user believes they are pushing to and potentially exfiltrating push credentials/tokens to an unintended host. This is a "silent corruption of what the user commits or pushes" class impact, matching the requested valid-impact criteria.

### Likelihood Explanation
The likelihood depends on how easily an attacker can influence the cached `GitHubRepository`/API `clone_url` pairing that feeds this function; I was not able to fully trace, within the remaining tool budget, every code path in `app-store.ts` that calls `updateRemoteUrl` and how `apiRepo` is sourced/refreshed (e.g., whether it's tied to repo renames, transfers, or explicit user actions like adding an Enterprise account). This determines whether an external, non-social-engineering trigger (e.g., a GitHub repo rename/transfer race, or a malicious GHES clone_url) is reachable without additional user steps. Given the reasoning-effort and iteration constraints, I could not confirm a complete, concrete end-to-end trigger chain from a purely external/unprivileged actor to this code path — I recommend a follow-up Devin session with full repo access to trace all callers of `updateRemoteUrl` and `GitHubRepository` cache population before treating this as a confirmed, high-confidence finding.

### Recommendation
- Do not silently rewrite `origin` based solely on `remoteUrlUnchanged` + `protocolsMatch`; require explicit user confirmation before changing a repository's push destination.
- Strengthen `urlMatchesRemote`/`urlsMatch` beyond hostname/owner/name string comparison (e.g., verify repository ID/node ID stability from the API rather than just cloneURL string equality) so a renamed/transferred/attacker-supplied API object cannot silently redirect trust.
- Log/audit remote URL changes and surface them in the UI so users can detect unexpected repointing.

### Proof of Concept
Not independently reproduced against live GitHub API behavior within this session; a concrete PoC would require constructing two `GitHubRepository`/`IAPIRepository` objects where `clone_url` differs from the cached value while `remoteUrlUnchanged` still evaluates true (e.g., via a repo rename/transfer sequence) and observing that `app/src/lib/stores/updates/update-remote-url.ts` calls `setRemoteURL` without any prompt. This should be validated with a background Devin session that can run the existing test suite at `app/test/unit/stores/updates/update-remote-url-test.ts` and trace the full caller graph in `app-store.ts` to confirm attacker reachability.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
