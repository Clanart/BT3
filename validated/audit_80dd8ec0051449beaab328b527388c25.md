### Title
Cached FROST preprocess is never invalidated after use, enabling deterministic nonce reuse across signing calls — ([File: crypto/frost/src/sign.rs](crypto/frost/src/sign.rs), [File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The kernel bug class here is a premature release of a resource whose later use becomes a use-after-free: `ksmbd_put_durable_fd(fp)` dropped the reference early, and a subsequent error path or concurrent access used the freed object. The Serai analog is a one-time secret resource — a cached FROST preprocess seed — that is consumed by `from_cache` but never invalidated, so every subsequent signing call rebuilds a machine with *identical* nonces. `from_cache` explicitly documents "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:216-224`), yet the only store of that preprocess, `CachedPreprocesses` (`coordinator/src/tributary/signing_protocol.rs:88`), has no delete path — only `get`/`set` — and `preprocess_internal` happily reloads the same seed on every call (`signing_protocol.rs:137-145`).

### Finding Description
`SigningProtocol::preprocess_internal` derives a deterministic encryption key from `self.context` (`signing_protocol.rs:107-115`), and caches the preprocess seed under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` only when absent (`signing_protocol.rs:123-135`). Every invocation then decrypts the same seed and calls `AlgorithmSignMachine::from_cache` (`signing_protocol.rs:144-145`), which — per the seeded-RNG design described in `spec/cryptography/FROST.md:45-62` — regenerates the identical nonce material.

`share_internal` then calls `self.preprocess_internal(participants).0` and `machine.sign(preprocesses, msg)` (`signing_protocol.rs:156-180`). Two distinct callers consume this machine:

- `DkgConfirmer::share` → `share_internal` (`signing_protocol.rs:288-309`)
- `DkgConfirmer::complete` → `share_internal` *again* (`signing_protocol.rs:312-327`), because the signature machine is rebuilt rather than persisted.

This is the direct analog of the kernel fix: the "put" (consumption of the one-time nonce) happens in the first `share_internal`, but the object is never actually invalidated, so the later access in `complete` (or any retried `share`) operates on logically freed state — the same nonce — exactly like the early `ksmbd_put_durable_fd` leaving `fp` reachable by later code paths. The comment block at `signing_protocol.rs:25-54` acknowledges this risk ("it is explicitly unsafe to reuse nonces across signing sessions") and rests safety entirely on context binding, but nothing enforces single-use of the cached seed; an error path after `sign` is invoked (e.g., `FrostError::InvalidPreprocess` from a malformed peer preprocess at `signing_protocol.rs:170-178`) leaves the seed intact for the next call, mirroring the kernel's error-path use-after-free.

### Impact Explanation
If two `sign` calls are reached with the same `context` (same `b"DkgConfirmer"` label and `attempt`) but different effective challenge inputs — different peer preprocess sets, or a different `set_keys_message` (different `KeyPair`/`removed`, `signing_protocol.rs:296-301`) — the signer emits two Schnorr signature shares under the *same* nonce `d + b·e`. Standard FROST/MuSig nonce-reuse algebra then recovers the validator's private key share from the two public shares. That is full key-share recovery, the highest-severity outcome for this protocol, achievable from data (preprocesses, `KeyPair`) that reaches these functions through BFT-ordered but validator-supplied messages.

### Likelihood Explanation
The unsafe precondition — reuse of the cached preprocess — is guaranteed by construction: `CachedPreprocesses` is written once per context and never cleared, and `complete` re-runs `share_internal` unconditionally (`signing_protocol.rs:321-324`). Whether a second emitted share has a *different* challenge depends on whether the preprocess set or `key_pair` can differ between the `share` and `complete` invocations within one attempt; I could not fully trace the BFT accumulation in `handle.rs` to confirm divergence within a single attempt (grep on that file returned unexpanded matches). If inputs are guaranteed identical, the second share is identical and harmless — but that safety property is implicit, undocumented at the call site, and contradicts the `from_cache` contract ("must be deleted"), making this a real latent vulnerability rather than a safe-by-accident design. The file's own TODOs (`signing_protocol.rs:50-54`) show this area is known-unreviewed.

### Recommendation
Delete the cached seed when it is loaded: add a `CachedPreprocesses::del(self.txn, &self.context)` (or a take-style API) immediately after `CachedPreprocesses::get` in `preprocess_internal` (`signing_protocol.rs:137`), and re-generate + re-store a fresh seed only when a new preprocess is actually published, not on every `share_internal`/`complete_internal` rebuild. Alternatively, persist the built `AlgorithmSignMachine`'s state (or the produced share) keyed by context so `complete` reuses the *result* of `share` rather than re-deriving the nonce. This mirrors the upstream fix: keep the resource valid until the operation fully returns, then release it exactly once.

### Proof of Concept
Conceptual trace (execution requires the coordinator harness):

1. DKG attempt `a` reaches confirmation. `DkgConfirmer::new(..., a)` builds context `(b"DkgConfirmer", a)`.
2. `preprocess()` → `preprocess_internal` stores seed `S` under `CachedPreprocesses[(b"DkgConfirmer", a)]` and returns commitments `C` (`signing_protocol.rs:123-147`).
3. `share(preprocesses_1, key_pair_1)` → `share_internal` → `from_cache(S)` → `sign(preprocesses_1, set_keys_message(..., key_pair_1))` emits share `σ₁` under nonce `N(S)` (`signing_protocol.rs:288-309`).
4. `complete(preprocesses_2, key_pair_2, shares)` → `share_internal` → `from_cache(S)` again — `CachedPreprocesses::get` still returns `S` (`signing_protocol.rs:137`) — emitting share `σ₂` under the *same* nonce `N(S)` whenever `(preprocesses_2, key_pair_2) ≠ (preprocesses_1, key_pair_1)` (`signing_protocol.rs:312-327`).
5. Given `σ₁`, `σ₂`, and the public commitment `C`, solve `s = (σ₁ − σ₂) / (λ₁c₁ − λ₂c₂)`-style linear relation for the signer's secret share — nonce reuse key recovery per `spec/cryptography/FROST.md:51-55` and the `from_cache` warning at `crypto/frost/src/sign.rs:216-224`.

Uncertainty: whether `share` and `complete` (or repeated `share`/`Reattempt`-driven calls) can observe differing preprocess sets or `key_pair`s under one `attempt` within the tributary BFT flow was not fully verified; the invariant the design relies on is undocumented and unenforced at the layer where the seed is stored.
