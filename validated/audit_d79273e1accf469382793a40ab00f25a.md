### Title
Prefix-only path containment check in `_resolveWithin` allows escape to sibling directories sharing a name prefix - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` (used via `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`) is the shared sandbox-boundary primitive that GitHub Desktop uses to make sure an attacker-influenced relative path (e.g. a conflicted file path handed off to the AI-conflict-resolution feature) stays inside the repository's working directory. The final containment check uses raw string `startsWith`, which is vulnerable to the classic "prefix without separator" bug.

### Finding Description
The containment check is: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` treats `realRoot` as a plain string prefix instead of a path-segment prefix. If `realRoot = '/Users/x/repo'` and the attacker-influenced relative segment resolves to `realResolved = '/Users/x/repo-evil/secret'`, the JavaScript string `'/Users/x/repo-evil/secret'.startsWith('/Users/x/repo')` evaluates to `true`, even though `repo-evil` is a completely different, sibling directory, not a subdirectory of `repo`. The function then returns `resolved` (a path outside the intended root) as if it had been validated.

The existing unit tests in `app/test/unit/path-test.ts` only cover: paths that fully leave and never re-enter the root (`../..`), paths that traverse out and return to the same root (`../<basename(root)>`), null bytes, and symlink escapes — none of them cover the "sibling directory whose name is prefixed by root's basename" case, so this gap is not caught by the current test suite: [2](#0-1) 

### Impact Explanation
`resolveWithin` is documented and used as a security boundary ("Guard against path traversal and symlink escapes") for file paths that originate from repository content. One confirmed caller is `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts`, which resolves conflict file paths against the repository's working directory before reading file content and sending it to the Copilot conflict-resolution model: [3](#0-2) 

If the containment check can be bypassed, a resolved path pointing to a sibling directory (outside the repository) could be treated as "safe," and the corresponding file's contents could be read (`readFile`) and exfiltrated to the conflict-resolution flow, or an out-of-repo path could otherwise be handed to file-consuming code paths that assume `resolveWithin` guarantees containment.

### Likelihood Explanation
Exploitability is significantly constrained by how `resolved` is derived: `pathSegments` for the confirmed caller come from `file.path`, which is produced by git's own status/conflict machinery. Git tracked paths generally cannot contain `..` path components (git refuses to check out or record tree entries with `..` segments), so it is unclear whether an attacker can actually get a `..`-containing `file.path` into this specific call site without some other primitive (e.g., a crafted rename/conflict entry) that has not been demonstrated here. Additionally, exploitation requires a sibling directory to exist on disk whose name is prefixed by the victim repository's directory name (e.g. `repo` vs `repo-evil`), which is an environmental precondition outside the attacker's direct control unless the victim's local layout happens to satisfy it (plausible under GitHub Desktop's default `~/Documents/GitHub/<repo-name>` clone layout when a user has multiple similarly-named repos cloned). I was not able to fully trace, within the available tool budget, whether `resolveWithin`'s other call sites (referenced in `dispatcher.ts` / `app-store.ts`, which I could not locate string matches for at the exact lines expected, possibly due to index limitations) provide a more directly attacker-reachable path for the `..`-segment.

### Recommendation
Fix the containment check to require an exact match or a proper path-separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
and add a regression test mirroring the reported PoC (`/tmp/root` vs `/tmp/root-evil/file`) to `app/test/unit/path-test.ts`.

### Proof of Concept
```ts
// app/test/unit/path-test.ts (new case)
it('fails for sibling directories sharing a name prefix', async () => {
  const tempDir = await mkdtemp(join(tmpdir(), 'path-test-'))
  const root = join(tempDir, 'root')
  const evilDir = join(tempDir, 'root-evil')
  await mkdir(root)
  await mkdir(evilDir)
  await writeFile(join(evilDir, 'secret'), 'top secret')

  // Should be null (outside root) but with current code the
  // startsWith check incorrectly returns the resolved path.
  const result = await resolveWithin(root, join('..', 'root-evil', 'secret'))
  assert.equal(result, null)
})
```
Given the current implementation, `resolveWithin(root, '../root-evil/secret')` resolves `resolved`/`realResolved` to `/tmp/.../root-evil/secret`, and `realResolved.startsWith(realRoot)` (`realRoot = /tmp/.../root`) returns `true`, so the function incorrectly returns the out-of-root path instead of `null`.
