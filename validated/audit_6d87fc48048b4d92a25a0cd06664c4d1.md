### Title
Panic on unregistered participant index in PedPoP blame handling allows remote crash - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The PedPoP blame-resolution path indexes `HashMap`s with participant identifiers taken from an incoming blame accusation without validating that the identifier was a registered DKG participant. `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` evaluates `self.commitments[&sender]`; both panic when the attacker-supplied `Participant` (any non-zero `u16`) is outside the registered set `1..=n`. This mirrors CVE-2017-7394: unauthenticated input reaches code that aborts instead of returning an error.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender`, `recipient`, `msg`, and `proof` entirely from an accusation message. `blame_internal` calls `Decryption::decrypt_with_proof(sender, recipient, msg, proof)`, which computes:

- `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388` — `HashMap` indexing panics on a missing key.
- `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` — same panic class.

`enc_keys` is only populated by `Decryption::register`, called for indexes `1..=n` during `verify_r1` / `AdditionalBlameMachine::new` (`crypto/dkg/pedpop/src/lib.rs:656-660`). `Participant::new` rejects only `0`, so any `recipient`/`sender` in `n+1..=u16::MAX` is a well-formed `Participant` that passes `io` deserialization yet is absent from both maps, producing a guaranteed panic. No bounds check against `params.n()` exists anywhere on this path.

### Impact Explanation
A peer (or any party able to submit a blame accusation referencing arbitrary participant indexes) can crash the victim's DKG/blame-handling task or process with a single crafted message — e.g., `sender = Participant::new(n + 1)` or `recipient = Participant::new(u16::MAX)` with any syntactically valid `EncryptedMessage`. A panic across an `unwrap`-able boundary aborts the victim's key-generation session and, depending on the host, the whole process. This is an availability loss reachable from public inputs only.

### Likelihood Explanation
Blame accusations are inherently adversary-supplied data (they exist to adjudicate disputes between parties), so a hostile participant or observer relaying a malformed accusation is an expected input. The panic is deterministic and requires no key material, valid proofs, or valid ciphertext — `decrypt_with_proof` indexes `enc_keys` before any cryptographic check that could reject the message early... note `msg.pop.verify` runs first, but the attacker can produce a valid self-signed PoP for their own key, or the recipient-index panic fires regardless once `proof` is `Some`.

### Recommendation
Replace `HashMap` indexing with `get`/`ok_or` and return a `PedPoPError::DkgError(DkgError::InvalidParticipant { .. })` (or a dedicated blame error) when `sender`/`recipient` are not registered. Alternatively validate both indexes against `1..=n` at the top of `blame_internal` before touching `enc_keys`/`commitments`.

### Proof of Concept
```rust
// After a completed/collecting DKG, feed an accusation with an out-of-range index
let bogus = Participant::new(u16::from(params.n()) + 1).unwrap();
// Any EncryptedMessage with a self-consistent PoP suffices
let msg: EncryptedMessage<C, SecretShare<C::F>> = /* read or craft */;
// Panics: self.enc_keys[&bogus] -> index into HashMap with missing key
let (_machine, _faulty) = blame_machine.blame(bogus, params.i(), msg, None);
```
The same crash is reachable via `AdditionalBlameMachine::blame(&self, sender, recipient, ..)` (`crypto/dkg/pedpop/src/lib.rs:674-682`), which an external observer — not even a DKG participant — can drive to a panic with an out-of-range `sender` or `recipient`.

Caveat: severity is Medium — the crash is confined to code paths the host application exposes to blame-accusation traffic, and depends on the caller propagating attacker-chosen `Participant` values, which is the documented purpose of the API.
