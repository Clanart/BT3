### Title
`SignableTransaction::new()` omits the OP_RETURN data output from the weight/vsize calculation, undercharging fees and bypassing the standard-weight check — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the LoopFi finding where an internal amount was used in one path without the `tokenScale` conversion applied everywhere else, `SignableTransaction::new()` adds an `OP_RETURN` output to `tx_outs` but then computes the transaction's weight/vbytes — and therefore `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check — over only `payments` and the change output. The data output's ~90+ bytes are silently dropped from the size accounting, so the returned transaction underpays its fee and may evade the size limit.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` before the weight calculation:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds its template transaction's outputs exclusively from `payments` (plus an optional change output) — it has no knowledge of the `OP_RETURN` output that was just added:

```rust
output: payments
  .iter()
  .map(|payment| TxOut { value: ..., script_pubkey: payment.0.clone() })
  .collect(),
```

The same omission applies in the change-handling branch: `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again ignores the data output. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is computed on a vsize that excludes the data output (up to 80 bytes of data plus ~11 bytes of output overhead ⇒ roughly 93 vbytes unaccounted).
- The `TooLowFee` minimum-relay check is evaluated against the understated vsize.
- `weight` compared against `MAX_STANDARD_TX_WEIGHT` for the `TooLargeTransaction` error excludes the data output's weight (~372 weight units).
- When change is present, `fee_with_change` and the change amount are derived from the same understated vsize, so the change output absorbs a value computed as if the data output did not exist.

### Impact Explanation
The signed transaction pays `fee_per_vbyte * vbytes` where `vbytes` excludes the `OP_RETURN` output. The effective fee rate of the broadcast transaction is therefore lower than the caller-specified `fee_per_vbyte` — a caller requesting, e.g., the minimum relay rate produces a transaction that fails the actual minimum-fee relay policy and will not propagate, stalling the associated funds. In the boundary case, a transaction can also pass the `TooLargeTransaction` check while its real weight exceeds the standardness limit. This is the same shape as the reference bug: a quantity maintained in one unit/accounting is used in a path where its full contribution was not applied, producing a concrete economic discrepancy (underpaid fee / oversized transaction) reachable purely through the public `data` parameter.

### Likelihood Explanation
Triggering requires only calling `SignableTransaction::new` with `Some(data)` — an unprivileged public input, analogous to a liquidator invoking `liquidatePosition`. Any integrator that attaches data payloads hits the miscalculation deterministically. The magnitude is bounded (~93 vbytes per transaction, since data is capped at 80 bytes), so this is a fee-correctness/liveness issue rather than direct theft, consistent with a Medium assessment.

### Recommendation
Include the OP_RETURN output in the size accounting. Either pass the fully constructed `tx_outs` (or a `data` length) into `calculate_weight_vbytes` so the template transaction mirrors the real transaction, or compute the weight/vbytes from `tx_outs` directly. Recompute `needed_fee`, the `TooLowFee` check, the change value, and the `MAX_STANDARD_TX_WEIGHT` check against the data-inclusive size.

### Proof of Concept
```rust
// Construct a transaction with a maximal data payload
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![input],
  &payments,
  None,
  Some(data.clone()),
  fee_per_vbyte,
).unwrap();

// The actual transaction contains the OP_RETURN output
let real_vbytes = tx.transaction().vsize() as u64;

// needed_fee was computed WITHOUT the OP_RETURN output
let claimed_vbytes = tx.needed_fee() / fee_per_vbyte;

// The real transaction is ~93 vbytes larger than what was charged
assert!(real_vbytes > claimed_vbytes);
// Effective fee rate is below the caller-specified rate:
// tx.fee() / real_vbytes < fee_per_vbyte
```

Concretely: `calculate_weight_vbytes` counts only `payments` outputs, while `Transaction { output: tx_outs }` (returned in `self.tx`) additionally contains the `OP_RETURN` output, so `tx.vsize() > needed_fee / fee_per_vbyte` whenever `data` is `Some`. At `fee_per_vbyte` equal to the minimum relay rate (1 sat/vbyte), the resulting transaction is below the effective minimum and will be rejected by relay policy.
