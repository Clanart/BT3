## Title
Balance desync between EVM `StateDB` and native bank ledger via nested/recursive precompile calls sharing `BalanceHandler` event-offset state - (File: `precompiles/common/precompile.go`, `precompiles/common/balance_handler.go`)

### Summary
The `BalanceHandler` mechanism that reconciles native Cosmos SDK bank events into the EVM `StateDB` balance model records only an *event offset* (`prevEventsLen`) at the start of each precompile invocation and replays events from that offset onward when the call returns. Because a single Cosmos `sdk.Context`'s `EventManager` is shared across nested/recursive EVM calls (precompile → EVM call → precompile again, or contract → precompile → callback into caller → precompile), an inner precompile invocation's `BeforeBalanceChange`/`AfterBalanceChange` pair can consume or shift the event window that an outer, still-in-flight invocation expects to process, corrupting the correspondence between recorded bank events and `StateDB.AddBalance`/`SubBalance` calls.

### Finding Description
`Precompile.runNativeAction` in [1](#0-0)  creates a brand-new `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()`, calls `BeforeBalanceChange(ctx)` which snapshots `prevEventsLen = len(ctx.EventManager().Events())`, executes the native `action`, then calls `AfterBalanceChange(ctx, stateDB)` which replays `events[bh.prevEventsLen:]` to apply `stateDB.AddBalance`/`SubBalance` per bank `coin_spent`/`coin_received`/precisebank fractional-balance events, as shown in [2](#0-1) .

This design implicitly assumes each precompile call's event window is self-contained. However, several precompiles (e.g. the `ics20`, `staking`, `distribution` precompiles) can trigger further EVM execution or reentrant precompile calls before returning (e.g. via `CallEVMWithData` inside a precompile handler, or a caller contract's fallback/callback being invoked as part of a bank `SendCoins`/module call, or via IBC callback contract execution). When a nested precompile call occurs *inside* an outer precompile call that is still executing native logic, the nested call's own `BeforeBalanceChange` captures a `prevEventsLen` that is *larger* than the outer call's, and the nested call's `AfterBalanceChange` consumes/replays events up to the then-current length. When control returns to the outer call and its own `AfterBalanceChange` runs, it replays `events[outerPrevEventsLen:]`, which now **overlaps** with events already applied to `StateDB` by the inner handler — i.e., the same bank event window gets processed twice (once by the inner handler, once again by the outer handler), or conversely some events get skipped depending on ordering, because `prevEventsLen` is purely a length-based cursor on a single shared, ever-growing event log, not scoped per call.

This is the direct native analog of the Aragon `DAO.execute` re-entrancy pattern from the external report: the vulnerable primitive is a sequence of “actions” (event windows to be replayed) whose correct, non-overlapping, single-application execution depends on no reentrant call happening in between — exactly the assumption Aragon's `execute()` makes about action ordering. Here it's the `BeforeBalanceChange`/`AfterBalanceChange` event-window bookkeeping that breaks under recursion.

The repository's own integration test explicitly documents and reproduces this exact bug: [3](#0-2)  states "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB," and the debug precompile used to trigger it recursively re-enters the EVM via `CallEVMWithData` from inside `Call0` at [4](#0-3) .

### Impact Explanation
If `StateDB` balances diverge from the underlying native bank keeper balances due to double-application or dropped application of bank events, an attacker-controlled contract that triggers reentrant precompile calls (via ICS20 transfer callbacks, distribution reward claims that transfer coins, staking operations, or any precompile using `BalanceHandlerFactory`, i.e. `distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) can cause the EVM-visible balance of an address to be inflated relative to its true bank balance (or the reverse). An inflated `StateDB` balance is directly spendable within the same or later EVM calls (e.g., ETH-style value transfers, or subsequent precompile calls that check `StateDB` balance), enabling unauthorized extraction/duplication of value — a Critical "unauthorized minting/duplication ... accounting corruption of spendable user value" per the impact gate, since the corrupted balance is a native-EVM-balance vs bank-ledger desync (not privileged, not fee-only, and reachable by an ordinary user deploying a contract that reenters a precompile).

### Likelihood Explanation
Reentrant precompile calls are triggered by ordinary, unprivileged EVM transactions — any contract calling a precompile that itself performs bank transfers producing events during execution, and that also results in reentry (either directly via `CallEVMWithData` internal callbacks, IBC destination-callback execution, or a contract's `receive()`/fallback being invoked mid-precompile as demonstrated by numerous test helpers such as `StakingReverter`, `ICS20Caller.testIbcTransferWithTransfer`, and `InterchainSenderCaller` in the codebase performing native-token sends interleaved with precompile calls) is a realistic, user-triggerable pattern, and the repository already has a dedicated, passing-oriented test reproducing the desync, confirming the bug is reachable in the current code without any privileged assumption.

### Recommendation
Scope the event-window bookkeeping per call instead of using a single shared, monotonically-growing offset comparison across nested invocations:
- Track and consume events by removing/marking them as processed (or use a stack/counter that accounts for nested consumption) rather than a single `prevEventsLen` snapshot compared against the live, shared `EventManager`.
- Alternatively, use `MaxPrecompileCalls`-aware call-depth tracking (already present as `x/vm/types.MaxPrecompileCalls` / `precompileCallsCounter` in `StateDB`) to detect nested precompile invocations and disallow `BalanceHandler` reuse/interleaving, or process bank events using a dedicated per-call sub-EventManager (cache context per call, not a shared parent) so nested calls cannot shift or double-consume the outer call's window.
- Add regression tests asserting that after a nested/recursive precompile call sequence, `StateDB` balances for all touched addresses exactly equal the bank keeper's balances (not just event counts), to catch silent double-application or event skipping.

### Proof of Concept
The existing test `TestRecursivePrecompileCallsWithDebugPrecompile` in [5](#0-4)  already demonstrates the mechanism: it deploys `DebugPrecompileCaller.callback()` which recursively invokes the debug precompile's `Call0`, which itself calls back into the EVM via `p.evmKeeper.CallEVMWithData` (see [4](#0-3) ), causing nested `runNativeAction`/`BalanceHandler` instantiations that share the same growing `ctx.EventManager()`. To turn this into a concrete fund-extraction PoC, replace the debug precompile's no-op `Call1` with a precompile path that performs an actual `bankKeeper.SendCoins` (e.g., using the `distribution`/`ics20`/`staking` precompiles that already use `BalanceHandlerFactory`), and recurse through a caller contract that: (1) calls the money-moving precompile, (2) inside a callback triggered by that same call (e.g., IBC destination callback, or a contract fallback funded via native transfer as in `ICS20Caller.testIbcTransferWithTransfer`/`InterchainSenderCaller`), re-enters the same or another balance-handler precompile, and (3) after control returns to the outer call, compare `StateDB` balance (queryable via `eth_getBalance` in the same block before commit, or a subsequent read within the same tx) against the actual bank keeper balance — the two will diverge because the outer handler's `AfterBalanceChange` replays an event window overlapping with what the inner handler already consumed.

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}

func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()

func (p Precompile) Call0(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	// data := crypto.Keccak256([]byte("function callback()"))[:4]
	counter := new(big.Int).SetBytes(contract.Input[1:])
	counter = new(big.Int).Add(counter, big.NewInt(1))

	args := math.U256Bytes(counter)
	selector := []byte{0xff, 0x58, 0x5c, 0xaf}
	data := append(selector, args...)

	caller := contract.Caller()
	fmt.Printf("Execute debug precompile %s, %p\n", caller.String(), p.BalanceHandlerFactory)
	rsp, err := p.evmKeeper.CallEVMWithData(ctx, p.Address(), &caller, data, true, nil)
	fmt.Println("callback response:", rsp.Ret, err)
	if err != nil {
		return nil, err
	}
	return nil, nil
}
