Confirmed: vote-account creation via `vote_instruction::create_account_with_config` and nonce-account creation via `create_nonce_account` both still build ordinary `SystemInstruction::CreateAccount` instructions [1](#0-0) [2](#0-1) , which are still subject to the pre-funding check in `create_account`.

### Title
Unprivileged lamport pre-funding of a not-yet-created account permanently blocks legitimate `CreateAccount` (vote/nonce/PDA account initialization) - (File: `programs/system/src/system_processor.rs`)

### Summary
The System Program's `create_account` handler treats any non-zero balance on the target address as proof that the account is "already in use" and unconditionally rejects the instruction. Because Solana addresses can receive lamports via a simple, permissionless `Transfer` before the address is ever allocated/assigned, any unprivileged actor can grief a specific, publicly known future address (e.g., a validator's new vote account, a nonce account, or a program's PDA) by sending it 1 lamport ahead of time, permanently preventing the legitimate `CreateAccount` transaction from succeeding at that address.

### Finding Description
`create_account` in `system_processor.rs` performs this check before allocating/assigning the account:

```rust
if to.get_lamports() > 0 {
    ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
    return Err(SystemError::AccountAlreadyInUse.into());
}
``` [3](#0-2) 

This check only inspects the lamport balance, not ownership or data — it does not distinguish "actually initialized" from "merely funded by an unrelated transfer." Since account addresses (validator vote-account pubkeys, nonce-account pubkeys, seed-derived/PDA addresses) are known in advance (they must be published/signed before the creation transaction lands), any third party can front-run the intended creation transaction with a plain `SystemInstruction::Transfer` of 1 lamport to that address. Once `to.get_lamports() > 0`, every subsequent `CreateAccount` attempt at that address fails forever with `AccountAlreadyInUse` [4](#0-3) .

This is analogous to the CrabStrategy bug: a special "first initialization" code path (`strategyDebt == 0 && strategyCollateral == 0`) is bypassed by an unprivileged deposit, permanently breaking bookkeeping. Here, the "first initialization" gate (`lamports == 0`) that `create_account` relies on to decide whether to allocate/assign the account is exactly what an unprivileged transfer can flip, permanently breaking the ability to create the intended account at that address.

Critically, the codebase already contains a fix for this exact class of bug — `create_account_allow_prefund` / `SystemInstruction::CreateAccountAllowPrefund`, which explicitly skips the zero-lamport check ("Create a new account without checking for 0 lamports... Intended for use where account has already had rent paid... before creation") [5](#0-4) , gated behind the `create_account_allow_prefund` feature [6](#0-5) . However, this safer path is not used by the vote program's account-creation instruction builder or by the CLI's nonce-account creation, both of which still emit the vulnerable `SystemInstruction::CreateAccount` [7](#0-6) [2](#0-1) .

### Impact Explanation
An attacker can permanently deny a specific validator the ability to bring up a new vote account or a user the ability to create a specific nonce/derived account at an address they intended to use, forcing them to regenerate a new keypair/address and losing any funds/rent already sent to the griefed address (which becomes stuck under system-program ownership with no way to reclaim it back through the intended program without a manual withdrawal). This is an unprivileged, no-cost griefing/DoS primitive against account initialization in a core built-in program, not requiring any special permissions, malicious validator status, or trusted role.

### Likelihood Explanation
High likelihood for any address that must be revealed/signed ahead of submission (vote-account pubkeys are typically generated locally and the transaction is broadcast, giving an observer of the network/mempool or the transaction itself a window to front-run with a cheap 1-lamport transfer). The attack costs a single, ordinary `Transfer` instruction and requires no special access.

### Recommendation
Route all Agave-issued account-creation flows (vote-account and nonce-account creation at minimum) through the already-implemented prefund-tolerant path (`CreateAccountAllowPrefund`/`create_account_allow_prefund`) once the corresponding feature is active, rather than the legacy `CreateAccount` instruction that fails on any non-zero balance. Until the feature is broadly active, treat balance alone as an unreliable signal of "already initialized" and consider basing the "already in use" check on account data/ownership state rather than lamports where compatible with a hard fork.

### Proof of Concept
1. Alice generates a new vote-account keypair `V` and prepares (but has not yet landed) a transaction containing `vote_instruction::create_account_with_config(..., V, ...)`, which internally issues `SystemInstruction::CreateAccount { lamports, space, owner: vote_program }` targeting `V` [1](#0-0) .
2. Eve, having observed `V` (e.g., from a public announcement, gossip, or the pending transaction itself), submits a plain `Transfer` instruction sending 1 lamport to `V` before Alice's transaction lands.
3. When Alice's `CreateAccount` transaction executes, `create_account` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse` [8](#0-7) , matching the exact behavior asserted in `test_create_already_in_use` for a pre-funded target account [9](#0-8) .
4. Alice can never create the vote account at `V`; she must generate a new keypair, and any lamports already sent to `V` are stranded under the system program at that address.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
