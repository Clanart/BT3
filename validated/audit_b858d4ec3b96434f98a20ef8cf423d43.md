## Analysis Result

I found a direct analog of the Nibiru H-04 bug-class in this codebase, in the shared stateful-precompile execution path.

### Title
Precompile native-action gas is not charged to the EVM contract on error, enabling free computation / resource-consumption DoS - (File: `precompiles/common/precompile.go`)

### Summary
The generic `runNativeAction` helper used by every stateful precompile (staking, distribution, slashing, ics20, bank, wasm-equivalent, werc20, etc.) computes the Cosmos SDK gas cost consumed by the native action only *after* checking for an error, and returns early without calling `contract.UseGas()` when the action fails. This is the exact same defect pattern identified in Nibiru's H-04.

### Finding Description
`runNativeAction` executes the precompile's native Cosmos logic inside an isolated SDK gas meter bound to `contract.Gas`: [1](#0-0) 

```go
initialGas := ctx.GasMeter().GasConsumed()
defer HandleGasError(ctx, contract, initialGas, &err)()

ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)). ...
ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")
...
bz, err = action(ctx)
if err != nil {
    return bz, err          // <-- returns WITHOUT calling contract.UseGas()
}

cost := ctx.GasMeter().GasConsumed() - initialGas
if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
    return nil, vm.ErrOutOfGas
}
```

`contract.Gas` is the go-ethereum EVM call-frame gas allotment for the precompile call (carved out of the caller's gas by the CALL opcode). Only `contract.UseGas()` actually deducts spent gas from that frame's budget and propagates the real cost back up to the EVM interpreter's accounting. When `action(ctx)` returns a non-nil error (any application-level failure inside a precompile method — e.g. an invalid delegation amount, a failed transfer, a bad denom, etc.), the function returns immediately, so:

1. The SDK-level `ctx.GasMeter()` (bounded by `contract.Gas`, panics if exceeded, caught by `HandleGasError`) *did* track the real work performed.
2. But `contract.UseGas(cost, ...)` is never invoked, so from the EVM/interpreter's perspective this call frame consumed **zero** additional gas beyond the flat `RequiredGas()` charged before `Run` was invoked.
3. The unused portion of `contract.Gas` is then returned to the calling frame as "remaining gas," even though real CPU/storage work equal to `cost` was actually performed.

Only the `HandleGasError` panic-recovery path (an actual `OutOfGas` panic) correctly charges `usedGas` via `contract.UseGas`; the ordinary error-return path used by every precompile method (`Execute` switch-statement default returns, argument validation errors, business-logic failures such as `p.Delegate`, `p.Transfer`, `p.Unjail`, etc.) skips gas accounting entirely.

State mutations from a failing action are correctly rolled back via the cache-context/snapshot mechanism (`ReturnRevertError`), so this is not a balance-corruption bug — it is a pure gas-metering/DoS defect, identical in nature to Nibiru's confirmed H-04. [2](#0-1) 

### Impact Explanation
An unprivileged caller can construct a contract that repeatedly invokes any stateful precompile method with inputs engineered to perform substantial SDK-side work (state reads/writes, iteration, cross-module calls) and then fail at the end (return a non-nil error), e.g. repeated `staking.Redelegate` calls that fail validation after doing significant lookups, or `ics20.Transfer`/wasm-style calls that do heavy work before reverting. Each such call:
- Performs real, potentially expensive Cosmos-SDK computation bounded only by `contract.Gas` (which can be sized up to the tx's total gas limit via nested CALL gas forwarding),
- Is not charged against the EVM's gas accounting because `contract.UseGas` is skipped,
- Returns unused gas back to the caller's frame, which can be reused for further looped calls within the same transaction.

This lets an attacker perform far more computational work per unit of paid gas than the protocol's gas-pricing model intends, mirroring the Nibiru DoS: a transaction with a modest declared `GasLimit` can trigger disproportionate validator-side computation. Repeated/parallel exploitation across many transactions in a block can degrade block-processing performance for all validators — a resource-consumption DoS vector reachable by any unprivileged EOA through ordinary transaction flow, matching the "impact on block-processing liveliness" category the task's impact gate ties to chain-halt-adjacent scenarios.

### Likelihood Explanation
High likelihood of triggerability: no privileged role is required — any address can send an Ethereum transaction that calls a stateful precompile method with a crafted argument set designed to fail validation after doing internal work (e.g., failing redelegation, invalid recipient in a transfer, an already-processed action, etc.). The pattern is universal across every precompile that uses `common.Precompile.RunNativeAction` (staking, distribution, slashing, ics20, bank, werc20, and any others sharing this base struct), maximizing the attack surface.

### Recommendation
Compute and charge `cost` via `contract.UseGas()` before checking/returning the error from `action(ctx)`, matching Nibiru's PR-2152 mitigation:

```go
bz, err = action(ctx)

cost := ctx.GasMeter().GasConsumed() - initialGas
if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
    return nil, vm.ErrOutOfGas
}

if err != nil {
    return bz, err
}
```
Ensure this ordering is applied uniformly and covered by a regression test asserting `contract.Gas`/EVM gas usage reflects real work even when the native action returns an error.

### Proof of Concept
1. Deploy an EVM contract that calls, e.g., the staking precompile's `redelegate` (or any transactional precompile method) with parameters engineered to perform validator/delegation lookups but ultimately fail (as already demonstrated as a "fail" test case in `tests/integration/precompiles/staking/test_staking.go` lines 188-206, which asserts an error path exists for `RedelegateMethod`).
2. Send the call in a loop from a single EVM transaction with a generous `contract.Gas` allotment for the precompile CALL (e.g., via `CALL` with high stipend), while keeping the outer transaction's declared `GasLimit` low relative to actual work performed.
3. Compare total SDK gas consumed by `ctx.GasMeter()` inside `runNativeAction` (real work) versus gas actually deducted from `contract.Gas`/EVM gas accounting (near zero on each failing call) — analogous to the Nibiru PoC where `WasteGas` and `NoGas` scenarios that should cost the same instead differ drastically in gas charged.
