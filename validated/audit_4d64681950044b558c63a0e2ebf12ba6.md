### Title
CLZ opcode (EIP‑7939) missing `computationCost` causes it to default to zero, bypassing the transaction's opcode‑computation‑cost limit - (File: blockchain/vm/eips.go)

### Summary
The reported bug class is a lookup/definition table that is missing an entry for a newly introduced item, so the missing entry silently resolves to zero and breaks the accounting that depends on it. The Solidity report showed this with `WEAPON_SHARD_TABLE` lacking data for the `Mythical` rarity, causing `weaponShardChance` to be zero. The same root-cause pattern exists in the Kaia EVM: the `CLZ` opcode (EIP‑7939) is enabled without setting the `computationCost` field, so it defaults to Go's zero value and is never added to the per‑transaction computation-cost accounting.

### Finding Description
Every other opcode registered in the jump table sets an explicit, non‑zero `computationCost` value used to bound the EVM interpreter's execution-time accounting: [1](#0-0) 

The interpreter loop accumulates this value every step and aborts once the accumulated cost exceeds `ComputationCostLimit`: [2](#0-1) 

However, `enable7939`, which registers the `CLZ` opcode, only sets `execute`, `constantGas`, `minStack`, and `maxStack` — it omits `computationCost` entirely, leaving it at the Go zero value: [3](#0-2) 

Compare this to the sibling functions in the same file (`enable4399`, `enable3855`, `enable4844`, `enable7516`), which all explicitly set `computationCost` to a nonzero constant defined in `params/computation_cost_params.go`: [4](#0-3) [5](#0-4) 

`params/computation_cost_params.go` defines a `ClzComputationCost`-style constant, but it is not wired into `enable7939`'s operation definition (unlike `RandomComputationCost`, `Push0ComputationCost`, `BlobHashComptationCost`, `BlobBaseFeeComputationCost`, which are all wired to their opcodes).

This mirrors exactly the external report's bug class: a table/definition meant to cover every relevant "rarity"/opcode is missing the entry for the newest item, and that missing entry defaults to zero, silently breaking an accounting invariant (weapon-shard chance in the original report; opcode-computation-cost accounting here).

### Impact Explanation
`opcodeComputationCostSum` is Kaia's mechanism for bounding a transaction's real (wall-clock) EVM execution cost, independent of gas — it exists specifically to prevent computation-heavy opcodes from causing excessive per-transaction execution time regardless of the gas paid. Because `CLZ` contributes `0` to `opcodeComputationCostSum`, any transaction sender can construct a contract that loops on `CLZ` an arbitrary number of times (bounded only by gas, which is comparatively cheap since `CLZ`'s `constantGas` is `GasFastStep`, i.e., very low) without ever tripping `ErrOpcodeComputationCostLimitReached`. This effectively defeats the computation-cost metering safeguard for a broad class of transactions once Osaka/EIP‑7939 is active, allowing a single submitted transaction to consume disproportionate node execution time relative to what the computation-cost limit is meant to enforce — a state-transition/computation-cost-metering integrity issue reachable from any public-RPC transaction submission.

### Likelihood Explanation
High reachability: any unprivileged transaction sender can deploy or call a contract that executes `CLZ` in a tight loop. No special privileges, governance parameters, or validator/staking involvement are required — only that the chain has the Osaka hardfork (which introduces EIP‑7939/CLZ) active. The trigger is a simple, deterministic transaction.

### Recommendation
Set an explicit, appropriately-calibrated `computationCost` value (e.g., a new `ClzComputationCost` constant analogous to other opcodes' costs) on the `CLZ` operation registered in `enable7939`, matching the pattern used by `enable4399`, `enable3855`, and `enable4844`. Add regression tests asserting that every opcode enabled by every `enableXXXX` function has a nonzero `computationCost` (mirroring the fix applied to `WEAPON_SHARD_TABLE`, which was expanded to cover the missing rarity).

### Proof of Concept
1. On a chain with the Osaka hardfork active (where `enable7939` registers `CLZ`), deploy a contract whose bytecode is a tight loop of `CLZ` instructions (e.g., push a value, `CLZ`, `POP`, `JUMP` back), sized so that gas cost keeps it within the block gas limit but the number of `CLZ` executions is very large.
2. Send this as a normal transaction from any account; no special role or governance parameter is needed.
3. Observe that `in.evm.opcodeComputationCostSum` (blockchain/vm/interpreter.go) never increases from executing `CLZ` (since `operation.computationCost == 0` for `CLZ`), so `ErrOpcodeComputationCostLimitReached` is never triggered no matter how many `CLZ` iterations run, unlike equivalent loops using any other opcode with a properly set computation cost.

Note: I was not able to fully verify, within the tool-call budget, whether `ClzComputationCost` is defined in `params/computation_cost_params.go` and simply not referenced, or not defined at all — the single grep match in that file needs direct inspection to confirm. Regardless, the operative bug is confirmed directly in `blockchain/vm/eips.go`'s `enable7939`, which does not populate the `computationCost` field on the `CLZ` operation.
