### Title
`Scanner::scan_block` re-processes identical outpoints across duplicate-txid (BIP-30-style) transactions, reporting overwritten/unspendable outputs as received - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
The external report's bug class is a "single-processing" invariant that is never enforced on an alternate path: the same logical request can be processed/emitted multiple times because no "already processed" check is applied. In Serai, the in-scope `Scanner` (`networks/bitcoin/src/wallet/mod.rs`) exhibits the same shape: `scan_transaction`/`scan_block` identify outputs purely by `script_pubkey` match and emit a `ReceivedOutput` keyed by `(txid, vout)` with no deduplication or duplicate-txid handling, so two distinct transactions sharing one txid produce two "received" outputs for the same logical on-chain output, exactly one of which actually exists and is spendable.

### Finding Description
`Scanner::scan` builds `ReceivedOutput`s solely from a `script_pubkey` lookup in `self.scripts`, keying identity by `OutPoint::new(tx.compute_txid(), vout)`:

```rust
// networks/bitcoin/src/wallet/mod.rs
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
``` [1](#0-0) 

`scan_block` iterates every transaction — explicitly including the coinbase — and concatenates all results without any txid/outpoint uniqueness check:

```rust
for tx in &block.txdata {
  res.extend(self.scan_transaction(tx));
}
``` [2](#0-1) 

Bitcoin historically permits duplicate txids for coinbase transactions (the BIP-30 scenario; also pre-BIP-34 coinbases). A miner can craft a coinbase paying to a registered Serai `script_pubkey` whose txid equals a txid of a transaction in an earlier block that also paid Serai — or arrange two same-txid paying transactions such that the later one overwrites the earlier UTXO. `scan_block` then returns two `ReceivedOutput`s bearing the same `OutPoint`, even though the UTXO set contains only the later output. Unlike the contract's `randomNumberCallback`, which gates on `processedRequests`, this scan path performs no equivalent of `seen`-checking — it is an event-level replay channel where the same logical outpoint is reported as received multiple times, potentially with different values/offsets of context.

### Impact Explanation
- **Funds reported received that are not spendable**: the earlier duplicate's `ReceivedOutput` refers to an outpoint overwritten on-chain; any downstream consumer that trusts `scan_transaction`/`scan_block` results will treat non-existent funds as received. Scheduling a spend of that outpoint produces a transaction referencing a non-existent UTXO, which will never confirm — an effective liveness/finality break for that payment plan.
- **Conflicting results for the same logical request**: as in the external bug, two distinct `ReceivedOutput`s (different amounts possible) are emitted for one outpoint, so any downstream logic treating each emission as authoritative double-counts or misattributes the deposit.
- Severity Medium: requires a miner to craft duplicate-txid coinbases, and only the coinbase-immature/reorg-adjacent edge cases enable it on mainnet today, but the code contains no guard whatsoever.

### Likelihood Explanation
Triggering requires mining blocks (a crafted coinbase txid collision is only permitted for coinbase transactions on current mainnet rules — the BIP-30 exception list), so this is not freely exploitable by an arbitrary transaction sender. However, it is reachable purely with on-chain data an unprivileged miner can produce, the scanner has zero defenses (no txid dedup, no "seen" tracking at this layer, no BIP-30/BIP-34 awareness), and any consumer of `scan_block` receives the conflicting outputs. The crate itself is the component responsible for correctly reporting received outputs, so the flaw stands on Serai's own code rather than an integrator misuse.

### Recommendation
- In `Scanner::scan_block` (and/or `scan_transaction`), track emitted `OutPoint`s per scanned chain and suppress duplicates, or explicitly note and handle duplicate-txid transactions.
- Alternatively, deduplicate by `OutPoint` in `scan_block` before returning results, keeping only the latest occurrence (matching UTXO-set overwrite semantics).
- Complement with the existing downstream `seen`-key check (`processor/src/multisigs/scanner.rs` panics on re-seen output IDs rather than handling the BIP-30 case), so a duplicate report becomes a graceful dedup instead of a panic.

### Proof of Concept
Conceptual: a miner includes in confirmed block *h₁* a coinbase `T` paying to a registered script `S` (obtainable via `register_offset`/`external_address`), then in a later confirmed block *h₂* mines a coinbase `T'` with `txid(T') == txid(T)` (pre-BIP-34 style duplicate txid, still permissible as a validity edge case for coinbases on regtest/historical mainnet exceptions) also paying to `S`. `Scanner::scan_block` on *h₂* (or rescanning both) yields two `ReceivedOutput`s with identical `OutPoint { txid, vout: 0 }`, while only `T'`'s output exists in the UTXO set — the first reported output is unspendable despite being reported as received.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.

  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs

  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
