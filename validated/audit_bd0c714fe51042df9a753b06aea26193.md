The analog here is a missing authorization gate: in Serai, the `Scanner` lets any external Bitcoin sender choose which registered offset (and hence which `OutputType`) their payment is classified as, since matching is purely by `script_pubkey`. Let me check how `Branch`/`Change`/`Forwarded` outputs are handled.### Title
Unprivileged sender controls `ReceivedOutput::offset` classification — deposits to reserved offsets are reported yet never spendable/creditable - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_transaction` classifies every transaction output purely by `script_pubkey` lookup against the internally-registered offset table (`networks/bitcoin/src/wallet/mod.rs:199-214`). The offsets for `Branch`, `Change`, and `Forwarded` are derived deterministically from the public group key and public `hash_to_F` constants (`processor/src/networks/bitcoin.rs:308-346`), so any external Bitcoin user can compute the corresponding P2TR addresses and send funds to them. There is no authorization step distinguishing "an output the multisig itself created" from "an output some third party sent to a reserved offset address". Analogous to CVE-2026-74283 (mutating operations registered without an admin gate), the scan path treats any on-chain payment to a reserved script as a state mutator of that `OutputType`.

### Finding Description
`Scanner::new` inserts the zero-offset script, and `register_offset` inserts scripts for hashed offsets into `self.scripts: HashMap<ScriptBuf, Scalar>` (`wallet/mod.rs:162-196`). `scan_transaction` returns a `ReceivedOutput` carrying `offset` for *any* output whose `script_pubkey` is in the map (`wallet/mod.rs:205-211`). Because `register_offset` is surjective and the reserved offsets (`hash_to_F(b"Serai Bitcoin Output Offset", b"branch"|"change"|"forward")`) are computable by anyone who knows the group key, an unprivileged sender can mint a P2TR output that the scanner reports with `offset = Change` / `Branch` / `Forwarded` rather than `External`.

Downstream, the Bitcoin `get_outputs` maps `offset` → `OutputType` via `kinds` (`processor/src/networks/bitcoin.rs:686-700`), and `scanner_event_to_multisig_event` retains only `OutputType::External` outputs as credited deposits (`processor/src/multisigs/mod.rs:837`), while `Forwarded` outputs trigger `ForwardedOutputDb::take_forwarded_output` keyed solely on `balance` (`mod.rs:824-832`). So an external party can: (a) send funds to the `Change`/`Branch`/`Forwarded` script, which the scanner reports as a `ReceivedOutput` under the multisig's own key yet which is silently dropped from deposit handling — the multisig receives funds that are never scheduled and never credited; and (b) send an amount exactly equal to a pending forwarded output's expected balance to the `Forwarded` script, consuming the stored `InInstruction` without the multisig's forwarding transaction having occurred.

### Impact Explanation
Medium. Case (a) yields funds reported received (a `ReceivedOutput` is emitted, counted in `ram_outputs`, and can never be re-scanned due to the `seen`/`ram_outputs` uniqueness check in `processor/src/multisigs/scanner.rs:634-639`) that are not spendable through the normal scheduler flow — the output is classified as internal change/branch and dropped. Case (b) lets an attacker prematurely resolve a forwarded-output instruction by matching only its balance, mutating coordinator state without authorization. Neither requires any privilege; both are reachable by broadcasting a standard Bitcoin transaction.

### Likelihood Explanation
Any Bitcoin user can derive the reserved offset scripts: the group key is public, the DST and labels are hardcoded constants, and `hash_to_F` is deterministic. Triggering (a) costs only the sent funds (which the attacker may intentionally burn to cause an accounting discrepancy, or which a third party may be socially engineered into sending to a "deposit address" that is actually the change address). Triggering (b) requires learning the pending forwarded balance, which is derivable from on-chain instruction/forward amounts.

### Recommendation
Do not rely on `script_pubkey` matching alone to assign `OutputType`. Mark scanner-tracked outputs with their provenance: only treat `Change`/`Branch`/`Forwarded`-offset outputs as internal if they were created by a transaction the multisig itself signed (e.g., match the outpoint against scheduler-created outputs before classifying), and key `ForwardedOutputDb` entries by outpoint/txid rather than amount. Externally-received payments to reserved-offset scripts should be treated as `External` deposits (or explicitly rejected/alerted), not silently dropped.

### Proof of Concept
1. Observe the public multisig group key `K`.
2. Compute `forward_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` and increment until `K + G*forward_offset` is even (mirroring `register_offset`, `wallet/mod.rs:180-196`).
3. Broadcast a transaction paying ≥ dust to `p2tr_script_buf(K + G*forward_offset)`.
4. `Scanner::scan_transaction` returns `ReceivedOutput { offset: forward_offset, .. }`; `get_outputs` tags it `OutputType::Forwarded`/`Change`; `scanner_event_to_multisig_event` drops it from credited outputs (`mod.rs:837`) — the funds sit at a multisig-controlled key yet are never scheduled or credited, and if the amount equals a pending forwarded balance, `take_forwarded_output` releases the stored instruction.
