### Title
Scanner reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in `block.txdata`, including `txdata[0]` (the coinbase transaction), and emits a `ReceivedOutput` for any output whose `script_pubkey` matches a registered script. Coinbase outputs are unspendable for 100 blocks per Bitcoin consensus rules, yet they are returned indistinguishably from normal outputs. A miner (an unprivileged party who can send a Bitcoin transaction — the coinbase — paying to a Serai P2TR address) can therefore cause the wallet to report funds as received that are not actually spendable, and `SignableTransaction::new` will happily construct a transaction spending an immature coinbase outpoint that the network will reject.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `scan_block` calls `scan_transaction` for every transaction in the block with no maturity check:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`scan_transaction` (mod.rs:199-214) pushes a `ReceivedOutput` for any matching `script_pubkey`, and `ReceivedOutput` carries no flag distinguishing a coinbase-origin output. The only mitigation is a doc comment (mod.rs:216-220) stating "a post-processing pass is needed" — nothing in the type system or API enforces it. Downstream, `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs:150-256` consumes `Vec<ReceivedOutput>` and builds inputs from `input.outpoint` without any coinbase/maturity validation, producing a transaction consensus-invalid for 100 confirmations.

This mirrors the reported bug class: an accounting/availability check (`redeemable()` there; "scanned = spendable" here) reports funds as usable based on chain state that does not actually permit the spend. Here the invariant "an output paying our script is spendable" is violated for coinbase outputs within their maturity window.

### Impact Explanation
Any consumer calling `scan_block` (or `get_outputs`-style wrappers built on it) will treat an immature coinbase output as a valid input. Consequences: (a) funds are reported received that are not spendable — the exact accepted impact class; (b) if such an output is aggregated into a `SignableTransaction` alongside real UTXOs (e.g., the aggregation/`force_spend` plans in `processor/src/multisigs/scheduler/utxo.rs:423-432`), the resulting transaction is consensus-invalid, stalling the batch and wasting the signing ceremony; (c) if the coinbase output is later reorged or reaches maturity, the scheduler's balance accounting is silently wrong in the interim.

### Likelihood Explanation
Requires a miner to direct a coinbase output to a watched Serai P2TR script. This is an unprivileged action (any miner can pay arbitrary scriptPubKeys in their coinbase) but is a low-probability, non-profit-motivated event on mainnet. On regtest/testnet deployments it is trivial. The impact when triggered is temporary unspendability and failed transactions rather than permanent loss — Medium likelihood is generous; Medium overall severity fits.

### Recommendation
In `scan_block`, either skip `block.txdata[0]` (matching the documented workaround `scan_transaction` on `block.txdata[1 ..]`) or mark `ReceivedOutput`s originating from the coinbase transaction and expose a maturity check (e.g., store `is_coinbase` on `ReceivedOutput` in `networks/bitcoin/src/wallet/mod.rs:90-97` and have `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` reject or defer such inputs until ≥100 confirmations). At minimum, the processor-side output intake (`processor/src/networks/bitcoin.rs`) should filter coinbase-derived outputs by confirming the input `previous_output` nullity (`tx.is_coinbase()` / `previous_output.is_null()`).

### Proof of Concept
```rust
// networks/bitcoin context
let mut scanner = Scanner::new(key).unwrap();

// A miner constructs a block whose coinbase pays to the Serai P2TR script
let coinbase_tx = Transaction {
  input: vec![TxIn {
    previous_output: OutPoint::null(), // coinbase
    ..Default::default()
  }],
  output: vec![TxOut {
    value: Amount::from_sat(50 * 100_000_000),
    script_pubkey: p2tr_script_buf(key).unwrap(),
  }],
  ..Default::default()
};
let block = Block { txdata: vec![coinbase_tx], .. };

// Scanner reports the output as received and spendable
let outputs = scanner.scan_block(&block);
assert_eq!(outputs.len(), 1); // immature coinbase output reported as ReceivedOutput

// SignableTransaction builds an input spending it; the TX is consensus-invalid
// for 100 blocks and any node will reject it with "bad-txns-premature-spend-of-coinbase"
let tx = SignableTransaction::new(
  outputs, &payments, Some(change), None, fee_per_vbyte,
).unwrap();
```

Confidence caveat: I confirmed `scan_block` lacks a coinbase/maturity filter and that the processor path notes the need for such filtering only in a comment; whether downstream `get_outputs` implementations in `processor/src/networks/bitcoin.rs` independently exclude coinbase outputs could not be fully verified in the time available, which affects end-to-end reachability through the processor (but not the wallet-library API itself).
