Confirmed: there is no `removeSafeDirectory` / revocation function anywhere in the codebase — `addSafeDirectory` is write-only, and `_removeRepository` / repository-removal code paths never touch `safe.directory`.

### Title
Path-scoped `safe.directory` trust is never revoked when a repository is removed, letting a later attacker-controlled repo at the same path inherit "trusted" status - (File: `app/src/lib/git/config.ts`)

### Summary
When Git detects "dubious ownership" of a repository directory, GitHub Desktop lets the user click "Trust Repository," which calls `addSafeDirectory(path)` and permanently appends that filesystem path to the user's **global** `safe.directory` git config [1](#0-0) . This is a path-based allow-list, not a repository-identity-based one. Nothing in the codebase ever removes an entry from `safe.directory` — not when the user removes the repository from Desktop (`_removeRepository`) [2](#0-1) , not when the repository record is deleted from the database (`removeRepository`) [3](#0-2) , and not anywhere else in the repo. This is directly analogous to the reported Visor bug: an "approval" (trust) granted for a specific object (an NFT / a specific repository's contents) is not cleared when that object leaves the owner's control (transferred out / repository removed), so once a new object occupies the same slot (redeposited NFT / a new repo placed at the previously-trusted path), the stale approval/trust can be abused again.

### Finding Description
The trust decision is supposed to answer "do I trust the *content currently* at this path, owned by this (possibly different) user?" but Desktop encodes it as "do I trust this *path*, forever" [4](#0-3) . The UI surfaces for this are `MissingRepository.onTrustDirectory` [5](#0-4)  and `AddExistingRepository.onTrustDirectory` [6](#0-5) . Once a path is added, `getRepositoryType` will never again report `kind: 'unsafe'` for that path regardless of who owns the directory contents afterward [7](#0-6) , because Git's own dubious-ownership check is fundamentally path-scoped, and Desktop never scrubs the entry.

Because directories are frequently reused — shared multi-user machines, temp folders, removable/network drives, CI checkout paths that Desktop treats as "worktrees" (`_switchWorktree` explicitly re-checks `unsafe` status per path but has no mechanism to un-trust) [8](#0-7)  — an attacker who can write to that same path after the legitimate repository is removed/moved/deleted inherits the trust silently. Trusted paths skip Git's protections against untrusted repository configuration (e.g. `core.fsmonitor`, `core.hooksPath`, `core.pager`, malicious `include`/`includeIf`), so the next git operation Desktop performs in that directory (fetch, status, commit, etc., all of which run through `git()`/`exec` in that working directory) executes attacker-supplied config/hooks with no re-prompt and no warning shown to the user.

### Impact Explanation
This allows local code execution via git hooks/config that the user never explicitly consented to for the *new* repository — only for a repository that used to exist at that path. On shared machines, VDI/terminal-server environments, or after any workflow where a directory is repurposed (delete-and-reclone, restoring from a backup, mounting a different drive at the same mount point, decompressing an archive that recreates the path), this converts a one-time explicit trust decision into a persistent, silent trust of "whatever shows up at this path," undermining the entire purpose of Git's dubious-ownership protection that Desktop reimplemented this feature for.

### Likelihood Explanation
Requires: (1) the user previously trusted a directory once (a supported, expected flow that Desktop actively surfaces via `MissingRepository`/`AddExistingRepository` and is a documented feature — changelog entries "Trust repositories not owned by the current user" and "Trust repositories on network shares" confirm the feature is widely used) [9](#0-8) , and (2) an attacker being able to place content at that same path afterward (multi-user machine, removable media, network share, restored backup, or re-cloning attacker content to the same on-disk location). No admin rights or pre-existing malware are needed beyond ordinary filesystem write access shared with another user of the machine, which is exactly the "different owner" scenario the safe-directory feature was built to guard against in the first place — the vulnerability is that the guard, once bypassed once, stays bypassed forever for that path.

### Recommendation
Do not persist trust solely keyed by path. When Desktop calls `addSafeDirectory`, it should also record repository-identity metadata (e.g., the current HEAD/first-commit SHA, or the git dir's inode/creation time) at the moment of trust, and re-validate that metadata still matches before treating a previously "trusted" path as trusted; if the repository's identity has changed, invalidate the stored trust and re-prompt. At minimum, call a new `removeSafeDirectory(path)` whenever the corresponding repository is removed from Desktop (in `_removeRepository`) so leftover global git config doesn't outlive the app's own knowledge of that repository.

### Proof of Concept
1. On a shared machine (or via a network share/removable drive), User A clones a repository to `/shared/proj`.
2. User B places a different-owned repo at `/shared/proj` is detected by Desktop's `getRepositoryType` as `kind: 'unsafe'` [7](#0-6) ; User A clicks "Trust Repository," invoking `addSafeDirectory('/shared/proj')`, which globally and permanently whitelists that path [4](#0-3) .
3. User A later removes the repository from GitHub Desktop (`_removeRepository`) — the safe-directory config entry is not touched [2](#0-1) .
4. An attacker (User B, or anyone with write access to `/shared/proj`) deletes the old contents and places a new attacker-controlled git repository at the exact same path, with a malicious `.git/config` (e.g., `core.fsmonitor` pointing to an attacker script, or a malicious `core.hooksPath`).
5. User A re-adds `/shared/proj` in Desktop (`AddExistingRepository`) or Desktop rescans it as a known path; `getRepositoryType` now reports `kind: 'regular'` (not `unsafe`) because the path is already in `safe.directory`, so no trust prompt is shown.
6. The next git operation Desktop performs in that directory executes the attacker's config/hooks silently.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
