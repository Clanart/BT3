### Title
Deserialized `ReceivedOutput` can forge provenance and report unspendable Bitcoin funds - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts an attacker-controlled `(offset, TxOut, OutPoint)` tuple without proving that the outpoint identifies the supplied output. A crafted serialization can claim that an arbitrary or nonexistent UTXO pays the wallet and carries an arbitrary value. Downstream transaction construction trusts those fields for balance accounting and references the forged outpoint, while `SignableTransaction::multisig` only checks that the supplied script matches the offset-derived key. The result is an accepted deposit/spendable-input record for funds that are not actually spendable.

### Finding Description
`ReceivedOutput` is documented as “a spendable output” and stores three provenance-sensitive values: the scalar offset needed to spend it, the claimed `TxOut`, and the claimed `OutPoint` (`networks/bitcoin/src/wallet/mod.rs:88-97`).

`ReceivedOutput::read` parses all three attacker-controlled fields and returns the object without checking that the outpoint’s transaction output equals the decoded `TxOut`, or that the outpoint exists on-chain (`networks/bitcoin/src/wallet/mod.rs:120-134`).

By contrast, `Scanner::scan_transaction` establishes this association by deriving the outpoint from the actual transaction ID and output index (`networks/bitcoin/src/wallet/mod.rs:198-210`). Deserialization drops that provenance check.

`SignableTransaction::new` then trusts the decoded value for the input balance and places the forged outpoint directly into the transaction input (`networks/bitcoin/src/wallet/send.rs:175-185`). The only ownership check in `SignableTransaction::multisig` verifies that `p2tr_script_buf(keys.offset(offset).group_key())` equals the claimed previous output’s `script_pubkey` (`networks/bitcoin/src/wallet/send.rs:273-281`). It does not verify that the referenced outpoint contains that `TxOut` or value.

This is analogous to bypassing a provenance/security marker: the scanner creates a `ReceivedOutput` only after observing an output in a transaction, but the deserializer accepts the same “trusted” representation without preserving that origin binding.

### Impact Explanation
An attacker able to supply serialized `ReceivedOutput` bytes can cause the wallet to account for Bitcoin funds that do not exist or are not controlled by the threshold key. They can:

- report an arbitrary BTC amount as received;
- claim a nonexistent or unrelated outpoint is spendable;
- use a valid Serai Taproot script to pass the later key/script check;
- influence payment, change, and fee decisions with the forged `TxOut` value;
- cause generation and threshold signing of a transaction that references the forged input but is invalid on-chain.

Because `SignableTransaction::new` calculates available funds from the supplied `TxOut`, the false output can make insufficient funds appear sufficient. `SignableTransaction::multisig` then accepts the input when the forged `TxOut` uses the wallet’s own script, even if the `OutPoint` does not resolve to that output.

### Likelihood Explanation
The attack only requires control of bytes passed to `ReceivedOutput::read`; it does not require validator compromise, threshold collusion, private-key knowledge, invalid curve encodings, or Bitcoin consensus invalidity. If serialized `ReceivedOutput` values cross a process, database, synchronization, backup, or message boundary where another party can modify or provide them, the forged record is reachable.

The impact is constrained by the surrounding architecture: broadcast will fail if the outpoint is nonexistent or the actual prevout differs, and this does not by itself steal the threshold key or produce a valid spend of unrelated on-chain funds. The concrete impact is false receipt accounting and acceptance of an unspendable input.

### Recommendation
Avoid making `ReceivedOutput::read` produce an apparently trusted “spendable output” from unbound fields.

Preferred fixes:

1. Store the base scanning key in `ReceivedOutput`, or pass it to a new checked constructor/deserializer.
2. During checked deserialization, verify that `p2tr_script_buf(base_key + GENERATOR * offset) == output.script_pubkey`.
3. Require a transaction or chain proof establishing `outpoint -> output`; at minimum, deserialize the containing transaction and recompute `tx.compute_txid()` and output index.
4. Separate raw decoded data from scanner-authenticated data, for example `RawReceivedOutput` versus `ReceivedOutput`.
5. Ensure `SignableTransaction::new` only accepts scanner-authenticated outputs, not objects constructed through unauthenticated byte parsing.

### Proof of Concept
```rust
use bitcoin::{
  Amount, OutPoint, TxOut, Txid,
  consensus::Encodable,
  hashes::Hash,
};
use k256::{ProjectivePoint, Scalar};
use bitcoin_serai::wallet::{
  p2tr_script_buf, ReceivedOutput, SignableTransaction,
};

fn forged_received_output(group_key: ProjectivePoint, fake_value: u64) -> Vec<u8> {
  let mut bytes = Vec::new();

  // Claim zero scalar offset: the spend key is the wallet group key.
  bytes.extend(Scalar::ZERO.to_bytes());

  // Claim a valid Serai P2TR script and an arbitrary amount.
  TxOut {
    value: Amount::from_sat(fake_value),
    script_pubkey: p2tr_script_buf(group_key).unwrap(),
  }
  .consensus_encode(&mut bytes)
  .unwrap();

  // Claim an outpoint which need not exist or contain the above TxOut.
  OutPoint {
    txid: Txid::all_zeros(),
    vout: 0,
  }
  .consensus_encode(&mut bytes)
  .unwrap();

  bytes
}

let serialized = forged_received_output(group_key, 100_000_000);
let forged = ReceivedOutput::read(&mut serialized.as_slice()).unwrap();

// The forged value is now exposed as received balance.
assert_eq!(forged.value(), 100_000_000);

// Transaction construction trusts the claimed value and outpoint.
let signable = SignableTransaction::new(
  vec![forged],
  &[(payment_script, 50_000_000)],
  None,
  None,
  10,
).unwrap();

// The key/script check succeeds because the forged TxOut uses the wallet script.
assert!(signable.multisig(&threshold_keys).is_some());
```

The resulting transaction references `Txid::all_zeros():0`, while its signature commits to the attacker-supplied `prevouts` list. Unless that outpoint really resolves to the supplied `TxOut`, the signed transaction is not spendable, despite `ReceivedOutput` presenting it as received wallet funds.
