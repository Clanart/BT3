### Title
`ThresholdKeys::read` deserializes attacker-supplied verification shares and derives the group key from them without binding them to the secret share — group-key substitution / unilateral signing - (File: crypto/dkg/src/lib.rs)

### Summary

The analog of CWE-434 (accepting a dangerous, unchecked object that is later executed/used) is Serai's acceptance of untrusted serialized `ThresholdKeys`. `ThresholdKeys::read` parses `t`, `n`, `i`, an `Interpolation` method, a `secret_share`, and `n` `verification_shares` entirely from the byte stream, then hands them to `ThresholdKeys::new`. `ThresholdKeys::new` computes `group_key` as the interpolated sum of `verification_shares[1..=t]` but never checks that `secret_share * G == verification_shares[i]` (or any consistency between the share and the shares map). The result is a deserialized object whose advertised `group_key` and `verification_shares` are fully attacker-controlled while its `secret_share` is independently attacker-chosen — a "dangerous type" accepted at the parser and later used by FROST signing and key handling.

### Finding Description

In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), every field is read straight from the reader: `Interpolation::Constant` reads `n` scalars (lines 606-613), `secret_share` is read via `C::read_F` (line 618), and `verification_shares` are read via `C::read_G` — the base `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101), which only enforces a canonical encoding, not non-identity or proof of possession.

`ThresholdKeys::new` (lines 349-391) validates only:
- the count of verification shares equals `n`,
- participant indexes are `<= n`,
- `Constant` interpolation requires `t == n`,

then computes `group_key = sum_{i in 1..=t} V_i * interpolation_factor(i)` over the supplied shares (lines 376-378). Nothing verifies `G * secret_share == V_i`, and nothing verifies the `Constant` coefficients reproduce a consistent polynomial. `ThresholdView::view` (lines 463-533) then interpolates the *secret share* with `interpolation_factor(i)` and the *verification shares* with the same factors, and adds `offset` to `included[0]` — all consistent internally, so a crafted object behaves like a coherent key.

Concretely, an attacker crafts a blob with `t = n = 1`, `i = 1`, `Interpolation::Constant([1])`, `secret_share = s` (attacker-known), `verification_shares = {1: s*G + X}` — or simply `{1: A}` for any `A` they choose, since consistency is never checked. Deserialization succeeds; `group_key()` returns `A`. If `A` is a key the attacker fully controls (e.g., `a*G`), they hold a `ThresholdKeys` object that signs for `A` using FROST single-handedly. Alternatively they set `V_1 = s*G` (consistent) but make `group_key`-relevant higher shares inconsistent — or pick `V_i` so `group_key` is a victim address, causing `sign_share`/`complete` to emit shares verified against `view.verification_shares` yet aggregate to signatures under a group key no honest party agreed to.

### Impact Explanation

- **Forged signatures / unintended-message signing**: a crafted key blob yields valid FROST signatures for a group key chosen at deserialization time, not one produced by a real DKG. Any consumer that treats `ThresholdKeys::read` output as a legitimate threshold key (key loading, key rotation import, test-vector-style imports as in crypto/frost/src/tests/vectors.rs:107-143 which deserializes externally supplied shares) accepts signatures for attacker-defined keys.
- **Funds reported under a wrong key**: `group_key()` is derived from the attacker-supplied `verification_shares`, so downstream address derivation (e.g., `N::tweak_keys`, Bitcoin TapTweak offsets applied in `view()`) binds to an attacker-selected key.
- **Consistency violations without detection**: since `secret_share` is never checked against `verification_shares[i]`, blobs where `V_i != s*G` produce views whose per-participant verification shares are wrong — signature shares will fail verification post-interpolation in confusing ways, and with `Constant` interpolation the attacker controls every coefficient anyway.

### Likelihood Explanation

Reachability requires attacker-controlled bytes reaching `ThresholdKeys::read` — the prompt's scope explicitly admits "untrusted bytes fed to … `ThresholdKeys::read`". Within the library itself the attack surface is real: the function performs no cryptographic binding between the share and the verification shares, and the codebase's own test-vector loader demonstrates the pattern of constructing these blobs from external data. A malicious or corrupted key blob (backup restore, key import, DB tampering reachable to a lower-privilege writer) yields a machine that signs under an attacker-chosen group key. That maps directly to the advisory class: an uploaded object of a dangerous type that is later executed (here: used to sign) with no type/invariant enforcement at the boundary.

### Recommendation

In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), add:
1. `if <C as Ciphersuite>::read_G` paths — require non-identity verification shares (use `frost::Curve::read_G`-style rejection where applicable, or check `is_identity` in `new`).
2. A consistency check `C::generator() * secret_share == verification_shares[&params.i()]` before constructing the core.
3. For `Interpolation::Constant(c)`, verify `c.len() == n` is implicit (it is, via read loop) but also that the reconstructed `group_key` equals `G * (sum_i c_i * s_i)` evaluated over the declared shares — i.e., recompute and sanity-bind the share.

At minimum, document that `ThresholdKeys::read` requires trusted input, and gate it behind an explicit `unsafe`/trusted-load API while adding the share↔verification-share binding check for defense in depth.

### Proof of Concept

```rust
// Serialize a fully attacker-controlled ThresholdKeys for any ciphersuite C.
// Chooses t=n=1, i=1, constant interpolation coefficient 1,
// secret share s (attacker-known), verification share = a*G (attacker's key).
let s = C::F::random(&mut OsRng);            // attacker-known secret
let a = C::F::random(&mut OsRng);            // attacker group key discrete log
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes());             // t
blob.extend(1u16.to_le_bytes());             // n
blob.extend(1u16.to_le_bytes());             // i = Participant(1)
blob.push(0);                                // Interpolation::Constant
blob.extend(C::F::ONE.to_repr().as_ref());   // c_1 = 1
blob.extend(s.to_repr().as_ref());           // secret_share
blob.extend((C::generator() * a).to_bytes().as_ref()); // V_1 -> group_key = a*G

let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
assert_eq!(keys.group_key(), C::generator() * a); // attacker-chosen group key accepted
// keys can now be fed to a FROST SignMachine; the "threshold" signature is
// unilaterally produced by the attacker under group key a*G, even though
// secret_share s may be inconsistent with V_1 (never checked).

  pub fn view(&self, mut included: Vec<Participant>) -> Result<ThresholdView<C>, DkgError> {
    if (included.len() < self.params().t.into()) ||
      (usize::from(self.params().n()) < included.len())
    {
      Err(DkgError::IncorrectAmountOfParticipants {
        t: self.params().t,
        n: self.params().n,
        amount: included.len(),
      })?;
    }
    included.sort();
    {
      let mut found = included[0] == self.params().i();
      for i in 1 .. included.len() {
        if included[i - 1] == included[i] {
          Err(DkgError::DuplicatedParticipant(included[i]))?;
        }
        found |= included[i] == self.params().i();
      }
      if !found {
        Err(DkgError::NotParticipating)?;
      }
    }
    {
      let last = *included.last().unwrap();
      if u16::from(last) > self.params().n() {
        Err(DkgError::InvalidParticipant { n: self.params().n(), participant: last })?;
      }
    }

    // The interpolation occurs multiplicatively, letting us scale by the scalar now
    let secret_share_scaled = Zeroizing::new(self.scalar * self.original_secret_share().deref());
    let mut secret_share = Zeroizing::new(
      self.core.interpolation.interpolation_factor(self.params().i(), &included) *
        secret_share_scaled.deref(),
    );

    let mut verification_shares = HashMap::with_capacity(included.len());
    for i in &included {
      let verification_share = self.core.verification_shares[i];
      let verification_share = verification_share *
        self.scalar *
        self.core.interpolation.interpolation_factor(*i, &included);
      verification_shares.insert(*i, verification_share);
    }

    /*
      The offset is included by adding it to the participant with the lowest ID.

      This is done after interpolating to ensure, regardless of the method of interpolation, that
      the method of interpolation does not scale the offset. For Lagrange interpolation, we could
      add the offset to every key share before interpolating, yet for Constant interpolation, we
      _have_ to add it as we do here (which also works even when we intend to perform Lagrange
      interpolation).
    */
    if included[0] == self.params().i() {
      *secret_share += self.offset;
    }
    *verification_shares.get_mut(&included[0]).unwrap() += C::generator() * self.offset;

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;

      Err(io::Error::other("non-canonical point"))?;
