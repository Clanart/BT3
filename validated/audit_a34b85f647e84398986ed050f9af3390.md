## Analysis

The external report's core broken invariant: a security-critical authorization check binds only a partial identity component (interface/version conformance) rather than fully authenticating the counterparty, letting a code path that should require a fully-verified identity execute against context it was never designed to trust.

The direct Hyperbridge analog is in `ExtrinsicIntents.onAccept`, which handles privileged, fund/logic-affecting host-management operations (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`).

### Title
Privileged `ExtrinsicIntents.onAccept` admin branch authenticates only the source chain, not the sending module, unlike the escrow path - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`ExtrinsicIntents.onAccept` implements two authentication styles for incoming ISMP POST requests. For `RedeemEscrow`/`RefundEscrow`, it calls `_authenticate()`, which validates **both** the source chain id and the specific sending module address (`request.from`) against the registered gateway instance: [1](#0-0) 

But for the far more sensitive admin operations (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`), the check only compares `request.source` (the chain identifier) to `IDispatcher(host()).hyperbridge()`, and never inspects `request.from` (which module/pallet on that chain actually dispatched the message): [2](#0-1) 

### Finding Description
`EvmHost.dispatchIncoming` performs no module-identity gating itself — it only checks the destination contract has code and forwards the verified request via a raw low-level call to `onAccept`, leaving all sender-identity binding to the destination app: [3](#0-2) 

This means the app-level check is the *only* barrier preventing arbitrary Hyperbridge-chain-originated messages from reaching the `UpgradeContract` / `SweepDust` / `UpdateParams` / `NewDeployment` branches. The current check:

```solidity
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
```

only proves the request's `source` field equals the coprocessor's state-machine id — it does **not** prove the request was dispatched by the intended, authorized governance/host-manager module on that chain. This is architecturally inconsistent with the pattern used two branches above it in the same function, where `_authenticate()` explicitly re-derives `module = address(bytes20(request.from))` and compares it to the registered `_instance(request.source)`.

This is the same *class* of flaw as the Brahma report: a critical gate that is supposed to fully bind an identity (module/app identity, per the Hyperbridge pivot requirement to "bind chain id, module/app identity, commitment uniqueness... on both Substrate and EVM") instead only partially validates it (chain id alone), silently accepting any counterparty that satisfies the weaker condition.

### Impact Explanation
If any dispatch path capable of setting `source = <hyperbridge chain id>` but with `from` set to something other than the legitimate host-manager/governance module can reach a relayer that submits it against `ExtrinsicIntents`, an attacker-influenced message could trigger:
- `UpgradeContract` → `ERC1967Utils.upgradeToAndCall(newImpl, initData)`, i.e., a full unauthorized implementation swap / contract takeover, directly enabling theft of all escrowed order funds.
- `SweepDust` → transfer of accumulated protocol dust to an attacker-chosen beneficiary.
- `UpdateParams` → manipulation of protocol fee/config parameters.

These are exactly the impacts the bounty gate calls out: unauthorized execution, transaction manipulation, and loss/theft of funds.

### Likelihood Explanation
This is a code-level asymmetry directly visible in the file (the escrow branch authenticates `from`; the admin branch does not), which is sufficient to flag as a real gap in the identity-binding invariant. I was **not able to fully verify** within this session whether the current pallet/router wiring on the Hyperbridge coprocessor chain enforces, at the ISMP dispatch layer, that only one specific pallet/account can ever produce a POST request with `source` equal to the coprocessor's own chain id (which would make this latent rather than directly exploitable today). The router examples I reviewed (`pallet_ismp_demo`, `pallet_bandwidth`, `pallet_hyper_fungible_token`) show that `from` is set by whichever pallet performs the dispatch, and multiple pallets on the same runtime can dispatch POST requests — but none I inspected currently allow a user to freely choose the destination `to`/`body` needed to hit this exact code path with attacker-controlled `newImpl`/`initData`. This dependency should be confirmed against the live host-manager/governance dispatch wiring before treating this as immediately triggerable by an unprivileged actor.

### Recommendation
Change the admin-branch check in `ExtrinsicIntents.onAccept` to authenticate both `request.source` **and** `request.from` against the specific, registered host-manager/governance module id (mirroring `_authenticate()`), rather than trusting chain-id equality alone. Apply the same full (chain id + module id) binding pattern consistently to every privileged branch, and audit other `IApp` implementations in the codebase for the same asymmetry between "authenticate source+from" and "authenticate source only."

### Proof of Concept
1. Identify or induce any dispatch path on the Hyperbridge coprocessor chain that can produce a `Request::Post` with `source == HostStateMachine (hyperbridge coprocessor id)`, `to == address(ExtrinsicIntents)`, and attacker-chosen `body` beginning with `RequestKind.UpgradeContract`, `abi.encode(maliciousImpl, initData)`.
2. A relayer submits this request with a valid membership/state proof through the normal ISMP request handler (`modules/ismp/core/src/handlers/request.rs`), which only verifies proof validity and receipt-replay protection, not the semantic legitimacy of `from`: [4](#0-3) 
3. `EvmHost.dispatchIncoming` forwards it to `ExtrinsicIntents.onAccept` without any module-identity check: [5](#0-4) 
4. `onAccept` sees `kind == UpgradeContract`, checks only `request.source == hyperbridge()` (true), and calls `ERC1967Utils.upgradeToAndCall(newImpl, initData)`, replacing the gateway's implementation with attacker-controlled code that can drain all escrowed funds: [6](#0-5)

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
