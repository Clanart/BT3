## Analysis

The finding is valid, though note the question mislabels the file — this bug is not in `rewards/BNBZapper.sol`, it lives entirely in `rewards/ReferralStorage.sol` and `VLMGP.sol`.

### Title
Referral boost factor uses instantaneous vlMGP lock snapshot, enabling atomic flash-lock self-referral farming to extract disproportionate referral yield - ([File: rewards/ReferralStorage.sol], [File: VLMGP.sol])

### Summary
`ReferralStorage.updateTotalFactor` computes a referrer's boost `factor` from the *current* `getUserTotalLocked` balance with no time-weighting, minimum duration, or vesting. Because `VLMGP.lock`/`_lock` and `VLMGP.startUnlock` both synchronously call `updateTotalFactor`, and `MasterMagpie.multiclaimFor` is callable by anyone for any `_account` with no access control, an attacker can atomically lock a large amount of MGP, trigger a referee's claim (self-controlled) so `ReferralStorage.trigger` reads the inflated `boostesd`, and immediately start unlocking — all in a single transaction — capturing a boost reward disproportionate to any real locked duration.

### Finding Description
- `ReferralStorage.updateTotalFactor` (called from `VLMGP._lock` on every `lock`/`lockFor`, and from `VLMGP.startUnlock`) sets `userInfo.factor = sqrt(getUserTotalLocked(_account))` and updates `totalBoostFactor` immediately, with no cool-off, no time-weighted average, no minimum holding period: [1](#0-0) 
- `_calBoosted` computes `boostesd = BoostPoint * factor / totalBoostFactor` purely from this instantaneous snapshot: [2](#0-1) 
- `trigger()`, called by `MasterMagpie._multiClaim` on every claim, uses this snapshot to split `_amount` between referrer and referee and credits `rewardAmount` (paid out later from `ReferralStorage`'s own MGP balance via `claimReward`): [3](#0-2) [4](#0-3) 
- Critically, `MasterMagpie.multiclaimFor` has no access control restricting who can trigger a claim for `_account` — anyone can call it for any address: [5](#0-4) 
- `VLMGP.lock` and `VLMGP.startUnlock` are both regular `external` functions reachable by any EOA/contract, each re-syncing the boost factor: [6](#0-5) [7](#0-6) 

Exploit flow (single atomic transaction, via an attacker-deployed contract):
1. Attacker registers a referral code (`registerCode`) and links a second attacker-controlled wallet as referee (`useCode`) which has accrued a large pending MGP reward.
2. Attacker's contract calls `VLMGP.lock(largeAmount)` — this synchronously inflates `userInfo.factor` and `totalBoostFactor` for the referrer via `_lock -> updateTotalFactor`.
3. Same transaction calls `MasterMagpie.multiclaimFor([vlmgp], ..., refereeAddress)` (permissionless) which triggers `_multiClaim -> ReferralStorage.trigger`, computing `boostesd` off the just-inflated factor and crediting an inflated `refererAmount`/`refereeAmount` (both attacker-controlled).
4. Same transaction calls `VLMGP.startUnlock(largeAmount)`, which re-syncs `updateTotalFactor` back down and starts the cooldown, so the boost never persisted beyond the single trigger call.

Existing protections (`whenNotPaused`, `nonReentrant`) do not stop this because it's not reentrancy — it's three independent, permissionless, single-transaction calls composed by the attacker. There is no check anywhere tying the boost factor to a minimum lock duration or time-weighted average.

### Impact Explanation
This lets an attacker extract referral yield from `ReferralStorage`'s MGP reward budget that is disproportionate to any real, sustained vlMGP commitment — the boost is "free" except for the cooldown-period illiquidity on capital that isn't actually at risk (principal is fully recoverable after `coolDownInSecs`). This constitutes theft/over-extraction of protocol-funded unclaimed yield (`ReferralStorage.userInfos[...].rewardAmount`), and can push the contract into insolvency where legitimate referrers' later `claimReward()` calls fail because the MGP balance was drained by this manipulation — matching "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
Feasibility is high: it requires no special privileges, just capital (MGP to lock, temporarily) and a second wallet to act as the self-controlled referee, both of which an ordinary attacker can set up. It is fully atomic (single transaction) because `multiclaimFor` is permissionless for any `_account`, so there is no front-running/ordering risk. It is repeatable each time the referee wallet has accrued pending reward, and scales with `largeAmount` relative to other lockers' totals (bounded by `BoostPoint`).

### Recommendation
Compute the boost factor from a time-weighted average lock (e.g., checkpointed/decayed average over a minimum window) rather than instantaneous `getUserTotalLocked`, and/or require a minimum holding period before a change in locked amount affects `factor`/`totalBoostFactor`. Additionally, restrict `multiclaimFor` to require `msg.sender == _account` or an authorized operator, removing the ability for arbitrary third parties to trigger another account's claim/referral event.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `ReferralStorage`, MGP token; fund `ReferralStorage` with a referral reward budget; set `BoostPoint`, `sharePercent`, tier 1 `rewardPercentage`.
2. Attacker wallet A: `registerCode(codeA)`. Attacker wallet B (referee): `useCode(codeA)`, then stake/lock enough over time in `MasterMagpie`/`VLMGP` pools to accrue a large pending MGP reward (simulate time passing to accumulate `accMGPPerShare`).
3. Deploy an attacker contract `Exploiter` that in one transaction: (a) `MGP.approve` + `VLMGP.lock(largeAmount)` as A, (b) `MasterMagpie.multiclaimFor([vlmgp], [[]], B)`, (c) `VLMGP.startUnlock(largeAmount)` as A.
4. Assert: `ReferralStorage.userInfos[A].rewardAmount` after step 3 is materially larger (compare `boostesd` used) than the amount computed if `factor` were based on a time-weighted average lock of A over the relevant period (e.g., near zero, since A held the lock for effectively 0 elapsed blocks).
5. Assert A can recover full `largeAmount` principal after `coolDownInSecs` via `unlock`, proving no principal was ever at risk while still capturing the inflated boost — demonstrating disproportionate reward relative to sustained commitment.
