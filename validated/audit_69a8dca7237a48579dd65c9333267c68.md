### Title
Deterministic nonce derivation from `CachedPreprocess` enables nonce reuse across signing sessions, leaking the FROST secret share - (File: crypto/frost/src/sign.rs)

### Summary
The analog of CVE-2020-12387 (a race condition producing use-after-free / state reuse) in Serai is **parallel/replayed signing sessions reusing a deterministic preprocess seed**. `AlgorithmMachine::seeded_preprocess` derives the FROST nonces `d, e` purely from a caller-supplied 32-byte seed via `ChaCha20Rng`, with no binding to the message or signing set. Any path that causes the same cached seed to be loaded into `SignMachine::from_cache` twice — a parallel-session race or a retry/replay of `share_internal`-style flows — produces two signature shares over the *same* nonces for *different* messages/challenge values, which is textbook nonce reuse and yields direct algebraic recovery of the signer's secret share.

### Finding Description
In `crypto/frost/src/sign.rs`, `seeded_preprocess` constructs the nonce pair deterministically: [1](#0-0) 

```rust
let mut rng = ChaCha20Rng::from_seed(*seed.0);
let (nonces, commitments) = Commitments::new::<_>(
  &mut rng, params.keys.original_secret_share(), &params.algorithm.nonces());
```

The seed is exposed/loaded through `cache()` and `from_cache`, which simply re-runs `seeded_preprocess` on the stored seed: [2](#0-1) 

Crucially, the seed is the *only* entropy input: `sign(self, preprocesses, msg)` consumes the machine but the nonces were fixed at seed time and are identical for every re-instantiation from the same `CachedPreprocess`. `sign` itself performs no freshness check — it validates the participant set and computes the share from the stored `nonces`: [3](#0-2) 

FROST's own documentation in this repo acknowledges the consequence: "Reusing preprocesses would enable a third-party to recover your private key share" (spec/cryptography/FROST.md:51-55), and `sign.rs:85-87` warns "Reuse will enable third-party recovery of your private key share." However, nothing in the FROST crate *enforces* single-use: `from_cache` is a pure function of the seed, and the library relies entirely on the caller deleting the seed — a classic TOCTOU/race pattern. In the consuming code (`SigningProtocol::preprocess_internal` in coordinator/src/tributary/signing_protocol.rs:100-148), the seed is persisted in `CachedPreprocesses` keyed only by `context` and is re-read on every `share_internal` call; any interleaving where two sign rounds share a context (parallel sessions for the same tributary context, or a retry after failure where the context does not include the attempt) reuses identical `d, e` commitments. [4](#0-3) 

### Impact Explanation
When two shares are produced with the same nonce `(d, e)` but different bound sessions — i.e., different `msg`, different participant sets, or different addenda — the attacker observes shares `s1 = d + e·ρ1 + λ·x·c1` and `s2 = d + e·ρ2 + λ·x·c2`. With `ρ` and `c` computable from public data, the two equations eliminate `d, e` and solve for `x`, the signer's secret share (modulo the binding factor cases; even in degenerate `ρ1 = ρ2` cases, `x = (s1 − s2)/(λ(c1 − c2))`). An unprivileged participant who supplies `read_preprocess`-parsed bytes and influences the signed message — both reachable per the scope rules — can therefore recover a threshold key share, reducing the effective security of every multisig the compromised validator participates in and enabling share-collection attacks toward full key reconstruction. This is the "key share recovery" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: exploitation requires inducing the same `CachedPreprocess` seed to sign two distinct sessions. The in-repo race analysis (`coordinator/src/main.rs:1209-1211`) already documents races between Tributary consensus and preprocess availability, and the check-then-set pattern `if CachedPreprocesses::get(...).is_none() { ... set(...) }` in `preprocess_internal` is itself a non-atomic TOCTOU: two concurrent tasks with the same context can each generate, cache, and *sign with* their own seed while publishing two different preprocesses under one context — desynchronizing the nonce/commitment pair across peers and producing the reuse condition when the losing task's cached value is overwritten between its preprocess broadcast and its share generation. An attacker-participant who can trigger parallel signing attempts or force retries controls the `msg` and preprocess set fed to `sign`, satisfying the public-input reachability requirement.

### Recommendation
Bind the cached preprocess to a unique session identifier: include `msg` hash (or a monotonically increasing attempt/session counter) in the `CachedPreprocesses` key or in the seed derivation (`ChaCha20Rng::from_seed(H(seed ‖ session ‖ msg))`) so a replayed seed cannot produce identical nonces for a different session. Make the check-and-set in `preprocess_internal` atomic within a single DB transaction, and on `sign`, assert the stored seed is consumed (e.g., a `used` flag written and committed before the share is emitted) so any second `from_cache`/`sign` for the same context hard-fails instead of silently reusing nonces.

### Proof of Concept
Conceptual, against `crypto/frost`:

1. Construct `ThresholdKeys` via `musig(...)`/`ThresholdKeys::new` for a `t`-of-`n` set including attacker participant `a`.
2. Victim loads `AlgorithmSignMachine::from_cache(alg, keys, seed)` and produces `share1 = sign(preprocesses_1, msg_1)` where `preprocesses_1` contains the attacker's preprocess.
3. Trigger a second session under the same persisted context (parallel `share_internal` invocation or retry after a failed round, per coordinator/src/tributary/signing_protocol.rs:137-147 re-reading the same cached seed). The victim emits `share2 = sign(preprocesses_2, msg_2)` with `msg_2 ≠ msg_1` chosen by the attacker.
4. Since both shares use identical `d, e` (same `ChaCha20Rng` seed, same `original_secret_share` input to `Commitments::new`), compute `c1, c2` (the FROST/Schnorr challenge transcripts over `group_key`, `R`, `msg`) and `λ` (Lagrange coefficient for the victim's participant index, both publicly derivable), then solve `x = (s1 − s2 − e(ρ1 − ρ2)) / (λ(c1 − c2))` mod the group order, recovering the victim's secret share. Verify against `victim_share · G == verification_share` from the victim's public verification share in `ThresholdKeys`.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
