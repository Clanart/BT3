### Title
`Scanner::scan_transaction` reports outputs of any value (including dust/zero) as received spendable funds, enabling uneconomical deposits that can never be spent without net loss - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` returns a `ReceivedOutput` for every transaction output whose `script_pubkey` matches a registered script, without checking the output's value. An unprivileged party can send a dust (or even zero-value) output to a vault address; the scanner reports it as received funds even though spending it costs more in fees than it is worth — funds reported received that are not spendable. This is the same bug class as the reference report: a value that must be bounded (there, an upper bound on `_paybackRatio`; here, a lower bound on received amount) is accepted unchecked, and the acceptance is irreversible once the transaction confirms.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` matches, with no minimum-value check: [1](#0-0) 

The only dust handling in the crate lives on the *sending* side: `SignableTransaction::new` rejects payments below `DUST` and refuses to create a change output worth less than `DUST` (such leftovers become fee). No equivalent check exists on the receiving side: [2](#0-1) [3](#0-2) 

The codebase itself documents that each input costs ~57 vbytes (230 weight units) to spend, and that economic viability requires outputs to be spendable under a 5000 sat/kvB fee rate — motivating a 10,000-sat threshold at the processor layer — yet `scan_transaction` happily reports a 1-sat or 0-sat output: [4](#0-3) 

`ReceivedOutput::read` also performs no value validation, so such outputs propagate through deserialization unchanged: [5](#0-4) 

### Impact Explanation
An unprivileged party crafts a normal Bitcoin transaction paying a dust amount (e.g., 1 sat, or any amount below the ~10,000 sat economic-spendability threshold) to the vault's tracked script. `scan_transaction`/`scan_block` report it as a `ReceivedOutput`, so downstream accounting credits it as received collateral. Like the reference bug where User0 becomes "entitled to the contract's full collateral balance," the vault now accounts for value it cannot actually claim: including the dust output as an input adds ~57 vbytes of fee cost exceeding its value, and it cannot be economically consolidated. If the deposit is credited to a user, the vault owes more than the spendable collateral it holds — a direct loss of user funds at the expense of all other depositors, mirroring the reference's redistribution-of-collateral impact. It is irreversible: once confirmed, the UTXO exists and the credited accounting cannot be undone by the vault.

### Likelihood Explanation
The attack requires only sending a standard Bitcoin transaction — fully within the "Bitcoin transactions they send" reachability model — and costs the attacker a dust amount plus one transaction's fee. There is no mitigation in `scan_transaction`, `scan_block`, or `ReceivedOutput::read`; the only safeguard is an implicit, undocumented requirement that callers filter out uneconomical outputs (analogous to the reference's reliance on a trusted admin never erring). Repeated dust deposits compound the discrepancy between credited balances and economically spendable collateral.

### Recommendation
Add a minimum-value check on the receive path, symmetric with the send-side `DUST` check — e.g., in `Scanner::scan_transaction` skip outputs with `output.value.to_sat() < DUST` (or expose the value and require callers to enforce `N::DUST`), and reject sub-threshold values in `ReceivedOutput::read`, so that only economically spendable outputs are ever reported as received.

### Proof of Concept

// Attacker broadcasts a tx paying 1 sat to the vault's P2TR script
let vault_script = p2tr_script_buf(vault_key).unwrap();
let dust_tx = Transaction {
    version: Version(2),
    lock_time: LockTime::ZERO,
    input: vec![/* attacker-funded input */],
    output: vec![TxOut {
        value: Amount::from_sat(1),            // far below economic spendability
        script_pubkey: vault_script.clone(),
    }],
};

let mut scanner = Scanner::new(vault_key).unwrap();
let outputs = scanner.scan_transaction(&dust_tx);
assert_eq!(outputs.len(), 1);          // reported as received
assert_eq!(outputs[0].value(), 1);     // spending it costs ~57+ sats of fee
// The vault has credited 1 sat it can never spend without net loss;
// the deposit is irreversible once dust_tx confirms.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

    A Taproot input is:
    - 36 bytes for the OutPoint
    - 0 bytes for the script (+1 byte for the length)
    - 4 bytes for the sequence
    Per https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format

    There's also:
    - 1 byte for the witness length
    - 1 byte for the signature length
    - 64 bytes for the signature
    which have the SegWit discount.

    (4 * (36 + 1 + 4)) + (1 + 1 + 64) = 164 + 66 = 230 weight units
    230 ceil div 4 = 57 vbytes

    Bitcoin defines multiple minimum feerate constants *per kilo-vbyte*. Currently, these are:
    - 1000 sat/kilo-vbyte for a transaction to be relayed
    - Each output's value must exceed the fee of the TX spending it at 3000 sat/kilo-vbyte
    The DUST constant needs to be determined by the latter.
    Since these are solely relay rules, and may be raised, we require all outputs be spendable
    under a 5000 sat/kilo-vbyte fee rate.

    5000 sat/kilo-vbyte = 5 sat/vbyte
    5 * 57 = 285 sats/spent-output

    Even if an output took 100 bytes (it should be just ~29-43), taking 400 weight units, adding
    100 vbytes, tripling the transaction size, then the sats/tx would be < 1000.

    Increase by an order of magnitude, in order to ensure this is actually worth our time, and we
    get 10,000 satoshis.
  */
  const DUST: u64 = 10_000;
