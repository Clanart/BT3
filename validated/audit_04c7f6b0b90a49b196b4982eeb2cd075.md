### Title
Ed25519 `read_G` / `SchnorrSignature::read` accepts non-canonical point encodings despite documented canonicality guarantee - (File: crypto/dalek-ff-group/src/lib.rs)

### Summary
The bug class in the reference advisory is a parser accepting data variants that were never negotiated/expected (compressed frames when permessage-deflate was off). The Serai analog is `EdwardsPoint::from_bytes` / `C::read_G` accepting non-canonical Ed25519 encodings — points whose y-coordinate is ≥ the field prime and therefore has multiple byte representations — even though `SchnorrSignature` explicitly documents that it "mandates canonical encodings in its read function".

### Finding Description
`EdwardsPoint::from_bytes` (produced by the `dalek_group!` macro) decompresses a `CompressedEdwardsY` via `curve25519-dalek`'s `decompress()`: [1](#0-0) . Dalek's `CompressedEdwardsY::decompress` masks off the top bit and reduces the y-coordinate mod p via `FieldElement::from_bytes`, but does not reject encodings where the 255-bit y value is ≥ p = 2²⁵⁵−19. There are ~19 non-canonical values that decode to a valid canonical point. The only extra checks Serai applies are `decompressed.is_some()` and `point.is_torsion_free()` — no canonicality check is performed.

This flows into the untrusted-input surface: `SchnorrSignature::read` calls `C::read_G` for `R` and `C::read_F` for `s` [2](#0-1) , while the struct documentation claims strictness and canonical encodings [3](#0-2) . Scalar parsing (`Scalar::from_repr` → `DScalar::from_repr`) is canonical [4](#0-3) , so the discrepancy is confined to point encodings.

The same non-canonical acceptance also applies wherever `read_G` deserializes attacker-supplied points on the `Ed25519` ciphersuite: FROST `Commitments`/`EncryptionKey`/`ThresholdKeys` reads, PedPoP `EncryptedMessage` contents, and `SchnorrSignature`s embedded in signed data.

### Impact Explanation
Any Serai verification or deduplication that treats the serialized bytes of a signature or commitment as an identifier is subject to malleability: an unprivileged party can take a valid Schnorr signature `(R, s)` on an Ed25519 key, re-encode `R` using a non-canonical y (`y + p`, still < 2²⁵⁵ so it fits the encoding), and obtain a second byte string that `SchnorrSignature::read` accepts and `verify` accepts — same mathematical signature, distinct bytes. Likewise, attacker-supplied commitment/verification-share points in `read_preprocess`/`Commitments::read`/`ThresholdKeys::read` can be provided in non-canonical form, so byte-level equality or hashing of raw encodings cannot distinguish two encodings of the same group element. This violates the crate's own documented "strict, canonical" contract, and breaks any downstream assumption (signature-hash uniqueness, transcript byte-binding) that serialized points are canonical. Concrete exploitability is limited to malleability — no forgery or key recovery — so this is Medium.

### Likelihood Explanation
Reachable by any remote party who can submit bytes to `SchnorrSignature::read` + `verify` or a DKG/FROST `read_G` path on the Ed25519 ciphersuite — the affected audience is all integrators consuming Ed25519 signatures/commitments over the wire. Exploitation requires only arithmetic (add p to the y coordinate) — no collusion, no honest-party misbehavior, no secret knowledge. Whether the malleability has real consequences depends on how integrators key state by signature bytes, which is a documented assumption the library itself establishes.

### Recommendation
Reject non-canonical y encodings in `EdwardsPoint::from_bytes` (`crypto/dalek-ff-group/src/lib.rs`): after masking the sign bit, compare the 255-bit little-endian integer against p = 2²⁵⁵−19 and return `CtOption::none()` if ≥ p (constant-time comparison). Alternatively check `point.to_bytes().ct_eq(bytes)`. This closes the gap between the documented canonical contract of `SchnorrSignature`/`read_G` and the actual Ed25519 decoder; Ristretto and Ed448 are unaffected (Ristretto is canonical by construction, Ed448 `FieldElement::from_repr` is canonical). Add a regression test feeding `y + p` encodings into `EdwardsPoint::from_bytes`.

// y_nc = y + p, still < 2^255 so it fits the field element bytes
let mut carry = -19i64; // y + (2^255 - 19) == y - 19 (mod 2^255 wrap-free since y < p)
// compute non_canonical = (y + p) with constant integer math...
// (omitted carry arithmetic) — result: bytes encoding the same point

// Assertion: current code ACCEPTS the non-canonical encoding
let decoded = Option::<EdwardsPoint>::from(EdwardsPoint::from_bytes(&non_canonical));
assert!(decoded.is_some());
