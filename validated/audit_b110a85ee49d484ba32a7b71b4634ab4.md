### Title
Fee-on-transfer ERC20 tokens bridged via `requestERC20Transfer` cause bridge to promise more value than actually collateralized - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom` and then unconditionally emits a `RequestValueTransfer` event and (in mint-burn mode) burns `_value`, using the caller-supplied `_value` parameter rather than the amount actually received by the bridge contract.

### Finding Description
`requestERC20Transfer` is a public, permissionless entry point that any unprivileged transaction sender can call to bridge ERC20 tokens to another chain: [1](#0-0) 

It calls `IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then immediately proceeds to `_requestERC20Transfer` with the *declared* `_value`, never checking the actual token balance delta the bridge received. `_requestERC20Transfer` then either burns `_value` (mint-burn mode) or simply leaves the declared `_value` backing a `RequestValueTransfer` event that the counter-chain operators will honor 1:1 via `handleERC20Transfer`, which mints or transfers exactly `_value` tokens to the recipient on the other chain: [2](#0-1) [3](#0-2) 

For any ERC20 token that charges a fee-on-transfer (deflationary/reflection token), the bridge contract will actually receive `(1 - fee%) * (_value + _feeLimit)` tokens, strictly less than the amount promised in the emitted event and less than what is burned or held as collateral. `_payERC20FeeAndRefundChange` compounds the issue: it pays the fixed protocol fee and refunds `_feeLimit - fee` out of whatever balance actually arrived, using the caller-declared `_feeLimit` rather than any measured actual-received amount: [4](#0-3) 

This is the same root cause as the referenced "Queue deposit doesn't take account of fee-on-transfer tokens" finding: an amount is trusted at face value instead of being derived from a before/after balance check on the token contract.

### Impact Explanation
- In lock/unlock mode, the bridge promises (via `RequestValueTransfer`, honored by operators calling `handleERC20Transfer` on the counter chain) more tokens than it actually holds as collateral. Over repeated fee-on-transfer bridging, the bridge's real token balance drifts below the sum of all values it has promised to release, so honest users' subsequent legitimate withdrawals/handles can be left unable to be honored — a direct value-movement/accounting divergence between the two chains' balances.
- In mint-burn mode, `ERC20Burnable(_tokenAddress).burn(_value)` will revert if the bridge's actual balance (net of the transfer fee) is less than `_value`, causing a denial of service for the deposit, and if the burn happens to succeed on excess balance from prior underpaid fees, it silently mis-accounts the token supply relationship between the two chains.
- This directly enables unauthorized value movement/supply mismatch across the bridge, matching the "Medium" severity bar for concrete unauthorized value movement.

### Likelihood Explanation
The bridge contract does not restrict which ERC20 tokens can be registered to non-fee-on-transfer tokens; `onlyRegisteredToken`/`onlyUnlockedToken` are administrative gates but do not validate transfer semantics. Any bridge operator registering a fee-on-transfer or rebasing token (a common real-world token category) makes this reachable by any ordinary user simply calling the public `requestERC20Transfer` function with standard parameters — no special privilege needed.

### Recommendation
In `requestERC20Transfer` (and `onERC20Received`), measure the token balance of the bridge contract before and after `safeTransferFrom`, and use the actual received delta (rather than the caller-supplied `_value + _feeLimit`) as the basis for fee deduction, refund calculation, burning, and the `_value` emitted in `RequestValueTransfer`/relied upon by `handleERC20Transfer` on the counter chain.

### Proof of Concept
1. Bridge operators register a fee-on-transfer ERC20 token (e.g., 5% transfer fee) via the existing token registration flow.
2. A user calls `requestERC20Transfer(token, to, value, feeLimit, extraData)` with `value = 100`, `feeLimit = 0`.
3. `safeTransferFrom(msg.sender, address(this), 100)` executes, but due to the 5% fee the bridge actually receives only 95 tokens.
4. `_requestERC20Transfer` emits `RequestValueTransfer(..., _value = 100, ...)` and, if `modeMintBurn` is true, calls `ERC20Burnable(token).burn(100)` — reverting because the bridge only holds 95 tokens (DoS), or in lock mode simply records/promises 100 tokens to be released while only 95 sit as collateral.
5. Bridge operators on the counter chain observe the event and call `handleERC20Transfer(..., _value = 100, ...)`, minting/transferring the full 100 tokens to `_to` — a 5-token deficit relative to actual collateral, which is unaccounted for and accumulates with every fee-on-transfer bridge deposit.

        address _to,
        uint256 _value,

        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);

            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );

    }

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
