### Title
Missing `chain_id` in `CLEMENTINE_EIP712_DOMAIN` Allows Cross-Network Replay of Withdrawal Authorization Signatures — (`core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

The EIP-712 domain used to authenticate withdrawal and optimistic-payout authorization signatures contains only `name` and `version`. It omits `chainId` and `verifyingContract`. A valid `verification_signature` produced by the aggregator key on one Citrea deployment (e.g., testnet) is cryptographically identical to a valid signature on any other Citrea deployment that shares the same aggregator key, because the domain separator does not bind the signature to a specific chain.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

No `chain_id` and no `verifying_contract` are present. The EIP-712 specification includes these fields precisely to prevent cross-chain and cross-contract replay. The `BatchProofMethodIdBody` struct in the same codebase explicitly includes a `chain_id` field with the comment "Network identifier to prevent cross network replay attacks", confirming the developers understand the requirement — but it was not applied to the withdrawal domain. [2](#0-1) 

The domain is used in `recover_address_from_ecdsa_signature` to compute the EIP-712 signing hash for both `OptimisticPayoutMessage` and `OperatorWithdrawalMessage`: [3](#0-2) 

This hash is then checked in `Verifier::sign_optimistic_payout` and `OperatorServer::withdraw`: [4](#0-3) [5](#0-4) 

The `aggregator_verification_address` field is `Option<alloy::primitives::Address>`. When it is `None` (not configured), the entire signature check is skipped, meaning the protection is entirely absent by default. [6](#0-5) 

---

### Impact Explanation

If the same aggregator ECDSA key is used across multiple Citrea deployments (e.g., mainnet chain_id=5655 and a testnet or fork), a `verification_signature` produced for a withdrawal on one network is valid on any other network. An attacker who observes a legitimate signed withdrawal request on one network can submit the identical `(withdrawal_params, verification_signature)` tuple to operators/verifiers on a different network. If a matching `withdrawal_id` and `input_outpoint` exist on the target network (possible when the same user has deposited on both networks or when a bridge fork shares state), the operator will front a BTC payout for a withdrawal that was never authorized on that specific chain. This results in the operator losing bridged BTC collateral without a valid reimbursement path on the target network.

---

### Likelihood Explanation

The `aggregator_verification_address` is optional; when unset, the check is bypassed entirely. When set, the missing `chain_id` in the domain is exploitable whenever the same aggregator key signs for multiple Citrea deployments. The withdrawal params include a Bitcoin UTXO outpoint (`input_outpoint_txid:vout`), which constrains replay to cases where the same outpoint appears as a withdrawal UTXO on both networks. This is a realistic scenario when the same operator runs on both Citrea mainnet and testnet with the same key material, or when a chain fork preserves existing state.

---

### Recommendation

Add `chain_id` (and optionally `verifying_contract`) to `CLEMENTINE_EIP712_DOMAIN`:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
    chain_id: CITREA_CHAIN_ID,  // bind to the specific Citrea deployment
};
```

The `chain_id` should be sourced from `BridgeConfig::citrea_chain_id` at runtime, or the domain should be constructed per-request using the configured chain ID rather than as a static constant. Additionally, consider making `aggregator_verification_address` a required field rather than optional, so the protection cannot be silently disabled by omitting the environment variable.

---

### Proof of Concept

1. Deploy Clementine on Citrea mainnet (chain_id=5655) and Citrea testnet (chain_id=5656) using the same aggregator key.
2. User deposits BTC on both networks; both networks assign `withdrawal_id=0` to the first withdrawal.
3. User initiates a withdrawal on testnet; aggregator signs `OptimisticPayoutMessage { withdrawal_id: 0, input_outpoint: X, output_script_pubkey: Y, output_amount: Z }` using `CLEMENTINE_EIP712_DOMAIN` (no chain_id).
4. Attacker captures the `verification_signature` from the testnet gRPC call.
5. Attacker submits the identical `OptimisticWithdrawParams` with the captured `verification_signature` to the mainnet aggregator's `optimistic_payout` RPC.
6. `recover_address_from_ecdsa_signature` computes the same EIP-712 hash (domain has no chain_id), recovers the same aggregator address, and the check passes.
7. Mainnet verifiers sign the optimistic payout; the operator fronts BTC on mainnet for a withdrawal that was only authorized on testnet. [1](#0-0) [7](#0-6)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
