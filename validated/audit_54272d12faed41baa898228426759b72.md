### Title
Giga-executor gas-pool consumption not restored before falling back to V2 execution - ([File: app/app.go])

### Summary
`executeEVMTxWithGigaExecutor` in `app/app.go` mutates the shared, per-block EVM gas pool (`app.GigaEvmKeeper.GetGasPool()`) as part of a speculative ("optimistic") execution attempt, then on several failure conditions returns an error so the caller falls back to re-executing the same transaction through the full V2 ante/msg-server pipeline. There is no evidence the gas-pool consumption from the aborted Giga attempt is rewound before the V2 path independently consumes gas from the same pool for the same transaction, mirroring the kernel bug class of "advance a shared cursor/resource during an optimistic fast path, then retry without restoring it."

### Finding Description
`executeEVMTxWithGigaExecutor` follows an "optimistic path, fallback on failure" pattern: [1](#0-0) 

It fetches the live, per-tx-mutated gas pool and hands it to the Giga executor for `ExecuteTransactionFeeCharged`: [2](#0-1) 

If execution fails for a reason the code explicitly calls out as expected (EIP-7623 floor-data-gas), or if self-destruct is hit, the function returns an error and a comment states the caller "re-runs the tx through v2": [3](#0-2) 

The comment for the gas pool explicitly says it "is mutated per tx, cannot be cached", acknowledging it is stateful and shared: [4](#0-3) 

`stateDB.Cleanup()` (deferred) discards the Giga-side StateDB changes on fallback, but that only affects the `gigaevmstate.DBImpl`/StateDB — it says nothing about the separate `GasPool` object obtained via `GetGasPool()`, which is a different piece of block-level mutable state consumed by `core.StateTransition`/`ApplyMessage` during `ExecuteTransactionFeeCharged`. If that gas pool is not explicitly rolled back to its pre-attempt value before returning the fallback error, the subsequent V2 execution of the same transaction (which also calls `GetGasPool()`/consumes gas from it in its own ante/message flow) will consume gas from a pool that has already been debited once by the aborted Giga attempt — i.e., the same real resource is decremented twice for one logical transaction, while only one execution's gas usage is ultimately reflected in the receipt/GasUsed used for base-fee and block-gas accounting.

This is structurally analogous to the kernel CVE: `tls_decrypt_sg()` advances `msg->msg_iter` (a shared cursor) during an optimistic zero-copy attempt; when the optimistic path is abandoned and a retry through the kernel-copy path happens, the iterator is not restored, so the retry operates from the wrong position, corrupting later data. Here, the Giga executor advances the shared gas-pool cursor during an optimistic execution attempt; when that path is abandoned in favor of a full re-run via V2, the pool position (already-consumed gas) is not shown to be restored, so the retry's own gas accounting operates against an already-decremented pool — either under-counting gas availability for later transactions in the block (each Giga-aborted tx silently steals gas-pool headroom) or, if V2's bookkeeping desyncs from the pool's true remaining value, corrupting block gas-limit enforcement for subsequent transactions in the same block.

### Impact Explanation
If confirmed, this causes incorrect block gas-limit accounting: transactions that hit the Giga-fallback path (EIP-7623 floor-data-gas failures, self-destruct, validation failures, balance-migration, etc.) would silently consume gas-pool capacity twice — once during the aborted Giga attempt and once during the V2 re-execution — without a matching restoration. Over a block with many fallback transactions, this could cause the effective gas pool to be exhausted well before the declared block gas limit is reached, causing spurious out-of-gas rejections for later transactions in the same block, or (if the double consumption diverges between validators depending on non-deterministic Giga-enablement/config) an apphash mismatch / chain split, since `GasPool` state feeds directly into deterministic block execution and base-fee/gas accounting shared by all validators.

### Likelihood Explanation
Likelihood depends on implementation details not fully visible in the indexed context — specifically whether `ExecuteTransactionFeeCharged`/`core.StateTransition` snapshots and restores the `GasPool` internally on failure, or whether some other layer resets `GetGasPool()`'s underlying counter before the V2 fallback executes. The fallback path is reached by any ordinary user submitting an EVM transaction that fails EIP-7623 floor-data-gas checks, self-destructs, or triggers unassociated-address/authority-association/validation-failure conditions — all attacker-reachable without special privilege, and exercised in the codebase's own fallback tests (`TestGiga_FailedExecutionFallsBackToV2`). This makes the trigger condition easy to reach; what remains unverified is whether the gas pool double-consumption actually occurs uncorrected.

### Recommendation
Verify (and if necessary fix) that `app.GigaEvmKeeper.GetGasPool()`'s underlying gas counter is explicitly snapshotted before `gigaExecutor.ExecuteTransactionFeeCharged` runs and restored to that snapshot on every fallback return path in `executeEVMTxWithGigaExecutor` (`ErrValidationFailed`, `ErrBalanceMigrationRequired`, `ErrSelfDestructUnsupported`, `ErrExecutionFailed`, and the fail-fast-precompile abort), mirroring how `stateDB.Cleanup()` discards the Giga StateDB's speculative changes. Add a regression test asserting that the gas pool's remaining gas after a Giga-fallback-then-V2-execute sequence equals the remaining gas from a pure V2-only execution of the same transaction in the same block.

### Proof of Concept
Not directly reproducible from the indexed context alone: confirming double-consumption requires inspecting `GigaEvmKeeper.GetGasPool()`'s implementation and `gigaexecutor.NewGethExecutor(...).ExecuteTransactionFeeCharged`'s internal gas-pool handling on error, neither of which was retrievable within this investigation's tool budget. A Devin session with full repo access should trace `GetGasPool()` call sites and `core.StateTransition`'s gas-pool debit/refund logic to confirm whether the pool is rolled back on the fallback paths in `app/app.go` lines 1900-1969, and construct a block with a transaction that deliberately fails EIP-7623 floor-data-gas checks under `GigaExecutorEnabled=true` to observe whether the block's effective remaining gas pool differs from a `GigaExecutorEnabled=false` run of the identical block.

func (app *App) executeEVMTxWithGigaExecutor(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, cache *gigaBlockCache) (*abci.ExecTxResult, error) {
	// Get the Ethereum transaction from the message
	ethTx, _ := msg.AsTransaction()
	if ethTx == nil {
		return nil, fmt.Errorf("failed to convert to eth transaction")
	}

	chainID := cache.chainID

	// Recover sender using the same logic as preprocess.go (version-based signer selection)
	sender, seiAddr, _, recoverErr := evmante.RecoverSenderFromEthTx(ctx, ethTx, chainID)
	if recoverErr != nil {
		return &abci.ExecTxResult{
			Code: 1,
			Log:  fmt.Sprintf("failed to recover sender from signature: %v", recoverErr),
		}, nil
	}

	// Prepare context for EVM transaction (set infinite gas meter like original flow)
	ctx = ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))

	_, isAssociated := app.GigaEvmKeeper.GetEVMAddress(ctx, seiAddr)

	// Create state DB before validation so balance checks use DBImpl hooks.
	stateDB := gigaevmstate.NewDBImpl(ctx, &app.GigaEvmKeeper, false)
	defer stateDB.Cleanup()

	// Run validation checks (fee/nonce/balance - stateless checks done earlier)
	validation := app.validateGigaEVMTx(ctx, stateDB, ethTx, sender, seiAddr, isAssociated)

	if validation.err != nil {
		// v2 rejects fee/nonce/balance failures in its ante chain, whose
		// receipt gas fields giga cannot reconstruct; a giga-side receipt here
		// diverges LastResultsHash on mixed fleets (CON-368). Fall back to v2,
		// which also owns the nonce bump.
		return nil, gigautils.ErrValidationFailed
	}

	if !isAssociated {
		// Unassociated addresses require balance migration (iterating all balances),
		// which giga's cachekv doesn't support. Fall back to v2 for this tx.
		return nil, gigaprecompiles.ErrBalanceMigrationRequired
