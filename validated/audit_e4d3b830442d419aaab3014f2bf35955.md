### Title
Stale-proof-height replay in `_cancelFromSource` lets an order creator double-spend escrow and permanently brick the solver's `RedeemEscrow` payout - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromSource` lets the order creator request a refund by proving, via a Hyperbridge GET request, that `_filled[commitment]` is empty on the destination chain at an arbitrary `options.height`. The only check on that height is `options.height > order.deadline` — it is never required to be the *latest* height Hyperbridge has committed. A user can pick an early, already-finalized height that predates a solver's legitimate fill, get a refund on the source chain, and thereby zero out the escrow that the solver's later `RedeemEscrow` message needs — permanently reverting that message and losing the solver's already-delivered output tokens, an exact structural analog of H-11's "counter zeroed on one path, required by another path, causing a permanent revert-lock."

### Finding Description
`_cancelFromSource` (source chain) only validates the proof height against the order's deadline, not against "is this the freshest known destination state": [1](#0-0) 

The GET response handler blindly trusts whatever state the chosen height reflects: [2](#0-1) 

Meanwhile, a solver can independently fill the very same order on the destination chain up to `order.deadline` (checked against the destination chain's own block height in `fillOrder`), immediately release output tokens to the beneficiary, and dispatch a `RedeemEscrow` request back to the source chain expecting to withdraw the escrowed input tokens: [3](#0-2) 

Both the cancel-refund path and the redeem-escrow path converge on the same accounting primitive on the source chain, `_orders[commitment][token]`, which is decremented unconditionally to zero on first use and reverts on subsequent use because it underflows / hits the explicit zero-check: [4](#0-3) 

If the user's stale-height refund lands on the source chain *before* the solver's `RedeemEscrow` message is delivered (which is entirely plausible — Hyperbridge accretes state commitments incrementally, so a commitment for a height right after `order.deadline` can exist well before the height containing the actual fill transaction is proven, and nothing forces the user to wait for or reference the fill height), `_orders[commitment][token]` is zeroed by the refund. When the solver's `RedeemEscrow` message subsequently arrives via `onAccept`, `_withdraw` reverts with `UnknownOrder()` because `escrowed == 0`: [5](#0-4) 

There is no reconciliation step (nothing analogous to `liensOpenForEpoch` incrementing) that lets the protocol recognize "a fill already happened after the proven height, so the pending redeem must still be honored." The result is a permanent, unrecoverable revert of the solver's legitimate redemption, exactly mirroring how `PublicVault`'s stale epoch bookkeeping made `decreaseEpochLienCount` revert forever once the invariant was broken.

### Impact Explanation
This is a direct loss-of-funds / double-settlement bug against the live bounty's impact gate: the order creator receives a refund of their escrowed input tokens on the source chain *while the solver has already irrevocably paid out the requested output tokens on the destination chain* (see `_fillCrossChain`, which transfers to `beneficiary` and executes calldata before ever dispatching the `RedeemEscrow` message). The solver's compensating claim on the source-chain escrow is left permanently unpayable. No malicious relayer, prover, or admin is required — an ordinary order creator acting alone, choosing an unfavorable (but valid, already-finalized) proof height, triggers the conflict.

### Likelihood Explanation
The attacker only needs to be the order's own `user` (checked at `_cancelFromSource` line 189) and to supply a `CancelOptions.height` that is any already-provable height greater than `order.deadline` but earlier than the block containing the solver's fill. Since Hyperbridge commits states incrementally and relayers race to deliver whichever proofs are cheapest/available first, such a height will commonly exist in normal operation without any protocol-level malfeasance — this is not a front-run-only or malicious-relayer scenario, it is a standard timing gap in cross-chain proof availability that the contract fails to close.

### Recommendation
`_cancelFromSource` should not accept an arbitrary caller-chosen height as sufficient proof of non-fill. Require the proof height to be validated against the latest state commitment Hyperbridge holds for the destination chain (or otherwise bound the acceptable height window so it cannot predate a fill that could legitimately still occur before `order.deadline`), and/or have the destination-side fill path register an on-chain marker on the source chain (or a reservation) before releasing output tokens, so that a subsequent stale-height refund can be rejected/reconciled rather than silently zeroing escrow the solver is entitled to.

### Proof of Concept
1. User places a cross-chain order on chain A (source) with `deadline = D` (destination block height).
2. Hyperbridge finalizes destination-chain state at height `D+1` (before any fill happens) and relays that consensus update.
3. Solver fills the order on chain B (destination) at height `D+1` itself or shortly after but still `<= D` per `fillOrder`'s check — releasing output tokens to `beneficiary` via `_fillCrossChain`, and dispatching a `RedeemEscrow` POST back to chain A.
4. Before the `RedeemEscrow` message is relayed and processed on chain A, the user calls `cancelOrder` → `_cancelFromSource` on chain A with `options.height = D+1` (a height Hyperbridge already committed, in which the destination's `_filled[commitment]` slot was still empty because the fill actually landed in a later or same-block-but-unproven state).
5. The GET response comes back showing an empty `_filled` slot; `onGetResponse` calls `_withdraw(body, true, true)`, refunding escrow to the user and zeroing `_orders[commitment][token]`.
6. The solver's `RedeemEscrow` message later arrives at `onAccept`, calls `_withdraw`, and reverts with `UnknownOrder()` permanently — the solver has released real output tokens on chain B and can never recover the source-chain escrow.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                IERC20(token).safeTransfer(beneficiary, amount);
