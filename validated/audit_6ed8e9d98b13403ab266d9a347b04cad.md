### Title
Unchecked TRC20 transfer return value in `IntentGatewayV2.withdraw()` permanently locks settled escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) settles orders using raw low-level `.call()` invocations of `IERC20.transfer` and only checks that the *call itself* did not revert, never the boolean return value. This is the same class of defect as the seed report: a token-movement step that can silently no-op while the surrounding bookkeeping proceeds as if the transfer succeeded, permanently stranding the underlying funds with no recovery path.

### Finding Description
The escrow-settlement path in this file: [1](#0-0) 
decrements `_orders[body.commitment][token]` and marks `_filled[body.commitment] = beneficiary` right alongside a token payout done via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only verifies that the low-level `call` did not revert — it never inspects `success`'s accompanying return data to confirm the token itself reported `true`. Any TRC20/ERC20-style token whose `transfer()` executes without reverting but returns `false` on failure (e.g., paused token, blacklisted recipient, insufficient allowance-adjacent internal checks, or any non-standard/malicious token registered as an order asset) will pass this check even though no tokens moved. The same unchecked pattern recurs in the `SweepDust` branch of `onAccept`: [2](#0-1) 

This directly contrasts with the sibling EVM contract, which performs the equivalent settlement using OpenZeppelin's `SafeERC20.safeTransfer`, which reverts on a `false` return: [3](#0-2) 
The Tron variant imports `SafeERC20` and uses `safeTransferFrom` correctly in `placeOrder`'s escrow-collection path, but the settlement/withdraw path was rewritten with manual low-level calls, dropping that guarantee only at the payout step.

### Impact Explanation
This mirrors exactly the seed bug's failure mode: a token-transfer step is assumed to succeed, and the state that depends on it succeeding is committed unconditionally. Here, `_orders[commitment][token] -= amount` runs and `_filled[commitment]` is finalized even when the token transfer silently failed. Because the escrow accounting is already zeroed and the order is marked filled/refunded, there is no code path left to retry or reclaim those tokens — the underlying balance is permanently stuck in the `IntentGatewayV2` contract with no beneficiary able to claim it. This is unauthorized/incorrect settlement (funds never reach the rightful beneficiary) and a fund-loss condition, matching the bounty's "loss of funds" and "false settlement acceptance" categories.

### Likelihood Explanation
Triggering this requires only that one of the order's input/output tokens be a real-world TRC20/ERC20 implementation that returns `false` rather than reverting on failure — a documented, common pattern for many tokens (and part of why `SafeERC20` exists in the first place). Any legitimate order using such a token, combined with an ordinary transfer-failure condition (blacklist, pause, insufficient internal balance edge case) at settlement time, hits this path. No malicious relayer, prover, or governance actor is needed — it's a property of the token contract interacting with an unprivileged, permissionless `fillOrder`/`onAccept` settlement flow.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout pattern in `withdraw()` and the `SweepDust` branch with `SafeERC20.safeTransfer`, consistent with how `placeOrder` already uses `safeTransferFrom` and how the primary EVM `IntentsBase.sol` implementation performs settlement. `SafeERC20` correctly treats a `false` return as failure while still tolerating tokens that omit the return value entirely (like USDT), so switching does not break support for non-standard tokens.

### Proof of Concept
1. Register an order whose escrowed/output token is a TRC20 contract that returns `false` from `transfer()` under some in-contract failure condition (e.g., recipient is blacklisted, or contract is paused) instead of reverting.
2. Fill/settle the order so `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is invoked with that token and a beneficiary that triggers the token's internal `false`-returning failure path.
3. `token.call(...)` succeeds at the EVM-call level (no revert), so `success == true`; the `if (!success) revert TransferFailed();` check passes.
4. `_orders[body.commitment][token] -= amount;` executes, `_filled[body.commitment] = beneficiary;` is set, and `EscrowReleased`/`EscrowRefunded` fires — but the beneficiary's token balance never increased.
5. The tokens remain in the `IntentGatewayV2` contract's balance with no `_orders` entry pointing to them and no code path to withdraw them again: permanent loss for the intended beneficiary.
