## Analog Vulnerability Found

### Title
Signature replay in the `addr` precompile / `AssociateTx` lets anyone force an unrelated identity association and drain a victim's cast address - (File: precompiles/addr/addr.go)

### Summary
The Asterisk CVE stems from authentication succeeding while the *asserted identity* embedded in message content is never bound/validated against the authenticated principal, letting an authenticated party spoof arbitrary identities. Sei-chain's address-association path has the analogous flaw: the `associate` precompile method (and its ante-handler counterpart for `AssociateTx`) accepts an arbitrary caller-supplied message string, hashes it with a bare `keccak256`, and recovers an EVM/Sei address pair purely from a supplied ECDSA signature — without ever checking that the message conforms to the canonical association text, without any chain-ID/domain separation, and without requiring that the transaction sender (`caller`) be the party whose identity is being associated.

### Finding Description
`PrecompileExecutor.associate` in [1](#0-0)  takes `v, r, s, customMessage` directly from calldata, computes `customMessageHash := crypto.Keccak256Hash([]byte(customMessage))`, and recovers `evmAddr, seiAddr, pubkey` from that hash via `helpers.GetAddresses`. It never checks:
- that `customMessage` matches the canonical association template (`ASSOCIATE_MESSAGE` used only client-side in tests, e.g. [2](#0-1) ),
- that the message is bound to Sei's chain ID or to this specific contract/purpose (no domain separator at all — just a raw `keccak256` of attacker-controlled bytes), or
- that the transaction `caller` corresponds to the recovered `evmAddr`/`seiAddr`.

The recovered addresses are then handed to `associateAddresses` → `AssociationHelper.AssociateAddresses` [3](#0-2) , which unconditionally calls `MigrateBalance`, automatically sweeping all spendable coins and wei from the "cast address" (`sdk.AccAddress(evmAddr[:])`) to the newly bound `seiAddr` [4](#0-3) .

Because the signature is verified over an arbitrary, attacker-supplied plaintext with no domain binding, **any (message, v, r, s) tuple a victim ever produced for any unrelated purpose** (a `personal_sign`/EIP-191 signature for a different dApp, a different chain, or any protocol that signs raw bytes the attacker can reproduce) can be replayed by *any* unprivileged transaction sender against this precompile. The submitting `caller` need not be, and is never checked to be, the identity being associated — exactly the same class of failure as the CVE: authentication of "a" signature succeeds, but the system fails to verify that the asserted identity/context in the signed content is the one intended, letting a third party impersonate/act on behalf of another identity's cryptographic proof outside its intended context.

The same unguarded pattern (`AssociateTx` custom message hashed with `crypto.Keccak256Hash` and no domain separation) exists in the ante-handler path used for native `MsgEVMTransaction` "Associate" transactions: [5](#0-4)  and [6](#0-5) , both reachable directly by any transaction submitter without needing to control the target account at all.

### Impact Explanation
An unprivileged transaction sender can:
1. Force-associate a victim's Sei and EVM addresses at a time of the attacker's choosing (rather than the victim's), using a signature/message pair the victim produced for an entirely unrelated purpose.
2. Trigger an automatic, unauthorized fund transfer via `MigrateBalance`, sweeping all `usei`/wei balance sitting in the victim's cast address into the pubkey-derived `seiAddr` — a state-changing transfer the victim never authorized for this context, at a time chosen by an attacker rather than the account owner. Any downstream system relying on a Sei EVM address remaining an un-associated "cast address" until explicit user action (e.g., custodial deposit addresses, exchange flows, escrow relying on delayed association semantics) can have funds moved out from under it without user consent, and the account becomes permanently associated, blocking the victim from ever performing their own intended association (`ErrInvalidRequest: "account already has association set"`).

### Likelihood Explanation
Exploitability only requires an attacker to obtain any signature the victim has produced with their private key over any message whose plaintext is known to the attacker (extremely common for `personal_sign`-style flows used broadly in web3 UX, e.g. "sign-in" messages, off-chain order signing, or other protocols) — no privileged access, node compromise, or special conditions needed. The precompile is a standard public contract at address `0x1004`, reachable by anyone via a normal EVM call.

### Recommendation
- Bind the signed message to a fixed, canonical template enforced on-chain (not just conventionally used by test/client code), including the Sei chain ID and the contract's purpose/domain (EIP-712-style domain separation), so a signature cannot be replayed from another context.
- Require that the recovered `seiAddr`/`evmAddr` match the transaction's authenticated sender (or otherwise require the account owner's participation), rather than allowing any third-party caller to submit someone else's signature to force association.
- Apply the same domain-separation and caller-binding fix to the `AssociateTx` transaction type handled in `app/ante/evm_checktx.go` and `x/evm/ante/preprocess.go`.

### Proof of Concept
1. Obtain any `(message, v, r, s)` tuple signed by a victim's EOA key for an unrelated purpose (e.g., a `personal_sign` message from any dApp login flow, captured off-chain or leaked).
2. As any unrelated attacker account, call `addr.associate(v, r, s, message)` on the `0x1004` precompile (see call path `PrecompileExecutor.associate` → `associateAddresses` → `AssociateAddresses` → `MigrateBalance`), before the victim ever submits their own association.
3. Observe that: (a) the victim's cast address and pubkey-derived Sei address are now permanently linked without their consent or knowledge at that specific moment, and (b) all spendable balance in the cast address is automatically transferred to the derived `seiAddr` as a side effect of `MigrateBalance`, triggered entirely by the attacker's transaction.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
