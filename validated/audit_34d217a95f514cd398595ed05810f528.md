## Analysis Result

I found a directly analogous rounding-to-zero bug in the CPI cost-accounting code, matching the reported bug class (integer division of a small numerator by a much larger denominator silently truncating to zero, causing the intended per-unit cost to permanently disappear).

### Title
Unbounded truncating division allows CPI instruction/account-data byte costs to be charged as zero compute units - (File: program-runtime/src/cpi.rs)

### Summary
Several CPI cost calculations in `program-runtime/src/cpi.rs` compute a "cost per byte" using `checked_div(cpi_bytes_per_unit)` with no minimum floor. When the numerator (instruction data length, account-meta bytes, or account-info bytes) is smaller than `cpi_bytes_per_unit`, the division truncates to zero, so the corresponding compute cost component is charged as `0`.

### Finding Description
In `translate_instruction_rust` and `translate_instruction_c`, the per-CPI-call data/account-meta translation cost is computed as: [1](#0-0) 

Same pattern for the C ABI variant: [2](#0-1) 

And for translating `account_infos`: [3](#0-2) 

And for executable-account data and caller-account length costs inside `translate_accounts_common`: [4](#0-3) 

None of these five call sites apply a `.max(base_cost)` floor. This is inconsistent with the rest of the syscall cost model, which explicitly guards against this exact truncation-to-zero problem by taking the max with a nonzero base cost, e.g. in `mem_op_consume`: [5](#0-4) 

and in `SyscallSetReturnData`/`SyscallGetReturnData`, which add `syscall_base_cost` on top of the byte-division term: [6](#0-5) 

Because `cpi_bytes_per_unit` is a fixed, relatively large constant, any CPI invocation whose instruction data, account-meta list, or account-info list is smaller than that threshold pays exactly zero compute units for that component of CPI cost, regardless of how many bytes were actually translated/copied by the runtime.

### Impact Explanation
An unprivileged on-chain program performing many CPI calls (`invoke`/`invoke_signed`) with small instruction data and few accounts can have the byte-proportional cost components of CPI (instruction data cost, account-meta cost, account-info cost, executable-account data cost, and per-account length cost) rounded down to zero on every single call. Since CPI is a hot path reachable by any unprivileged program, this results in real translation/copy work inside the invoke context being performed without being charged, which is a form of underpriced compute analogous to the reported "rewards round to zero" bug — the flat `invoke_units` cost is still charged per `cpi_common` call, but that is decoupled from the actual data/account size, so cost scales incorrectly with the true amount of work done.

### Likelihood Explanation
High reachability: this code executes on every `invoke`/`invoke_signed` syscall performed by any unprivileged BPF program, with no special permissions required. The truncation triggers deterministically whenever data length / account count stays below the `cpi_bytes_per_unit` threshold, which covers the overwhelming majority of real-world CPI calls (most instruction payloads and account lists are small).

### Recommendation
Apply the same defensive pattern already used elsewhere in the codebase (e.g. `mem_op_consume`, `SyscallGetSysvar`): either round the division up (`ceil` division) or take the `max` of the computed byte-cost and an appropriate nonzero floor cost, so that small-but-nonzero byte counts are never charged 0 compute units. This should be applied consistently to all five division sites identified in `program-runtime/src/cpi.rs`.

### Proof of Concept
1. Deploy a program that repeatedly performs `invoke_signed`/`invoke` CPI calls to a no-op callee with instruction data length and account count both smaller than `cpi_bytes_per_unit`.
2. Instrument with `sol_remaining_compute_units()` before/after each CPI call, as already done in the test harness: [7](#0-6) 
3. Observe that the CU delta reflects only `invoke_units` plus fixed base costs, with the data/account-meta/account-info byte-cost terms evaluating to `0` because `data.len()`, `account_metas.len() * size_of::<AccountMeta>()`, and `account_infos_bytes` are each smaller than `cpi_bytes_per_unit`.
