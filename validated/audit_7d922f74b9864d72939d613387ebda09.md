### Title
Unchecked integer overflow in `compute_assert_height()` when combining attacker-controlled relative timelock values with coin timestamps/heights - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` unconditionally calls `compute_assert_height()` on every incoming spend bundle's parsed conditions to compute the most restrictive height/seconds assertions, adding attacker-supplied `seconds_relative`/`height_relative` condition arguments directly to the corresponding coin's `confirmed_block_index`/`timestamp` and casting the result with `uint32(...)`/`uint64(...)`.

### Finding Description
`compute_assert_height()` performs unchecked Python arithmetic and then narrows the result into a fixed-width type: [1](#0-0) 
Specifically:
- `h = uint32(removal_coin_records[...].confirmed_block_index + spend.height_relative)`
- `s = uint64(removal_coin_records[...].timestamp + spend.seconds_relative)`
- `h = uint32(removal_coin_records[...].confirmed_block_index + spend.before_height_relative)`
- `s = uint64(removal_coin_records[...].timestamp + spend.before_seconds_relative)`

`spend.seconds_relative`/`spend.before_seconds_relative` originate from the CLVM `ASSERT_SECONDS_RELATIVE`/`ASSERT_BEFORE_SECONDS_RELATIVE` condition arguments in a spend bundle's puzzle solution — fully attacker-controlled up to the width the Rust condition parser accepts (an 8-byte atom, i.e., values approaching `int64`/`uint64` bounds, mirroring the "near `i64::MAX`" value shown in the referenced GHSA-xqmp-fxgv-xvq5 PRUNE backoff report). `CoinRecord.timestamp` can itself be a large `uint64` value for old/coinbase coins. Adding an attacker-chosen near-maximum relative value to an existing large timestamp/height can push the Python integer result outside the representable range of `uint32`/`uint64`, and the `chia_rs` sized-int constructors raise on out-of-range construction rather than wrapping.

Crucially, this Python-side computation is **not gated by the Rust `check_time_locks(..., nowrap=...)` result** that runs immediately before it: [2](#0-1) 
`tl_error_rust` is stored but `compute_assert_height()` at line 876 executes regardless of whether `check_time_locks` already rejected the bundle for a timelock violation. This mirrors the disclosed bug class exactly: an earlier hardened/checked-arithmetic path (the Rust `check_time_locks` with `nowrap` — analogous to the "checked insertion" fix in CVE-2026-33040) coexists with a secondary, still-unchecked arithmetic path performed later in the same processing flow (analogous to the unchecked `backoff_time + slack` in the heartbeat path of the reported gossipsub CVE).

### Impact Explanation
If reachable, this causes an unhandled `ValueError` inside `MempoolManager.add_spend_bundle()`/`validate_spend_bundle()`, which is on the hot path for every spend bundle submitted to the mempool (via RPC `push_tx`, wallet transactions, or peer-gossiped transactions). An uncaught exception here would abort processing of that spend bundle and, depending on how the caller wraps this coroutine, could propagate and disrupt the full node's transaction-processing loop — a spend-triggered transaction-processing halt, which matches the "Validate" criteria for acceptable impact classes in this exercise.

### Likelihood Explanation
Reachability requires only a single unprivileged spend bundle submission (mempool admission path), no special peer/node/farmer privileges, satisfying the "unprivileged spend-bundle submitter" reachability bar. However, I could **not fully confirm** the exact bound where the overflow triggers, because:
- I was unable to verify the precise `chia_rs` binding type (`int64` vs `uint64`) enforced on `seconds_relative`/`height_relative` at CLVM-condition-parse time (this parsing lives in the Rust `chia_rs` extension, which is not indexed as readable source in this repository snapshot).
- I could not confirm whether the surrounding async call chain (e.g., `add_spend_bundle` callers in `full_node.py`/RPC handlers) already wraps this in a broad `try/except` that would downgrade the crash to a logged error rather than a full processing halt.

### Recommendation
Add explicit checked/saturating arithmetic in `compute_assert_height()` (e.g., use `min(value, MAX_UINT64)` clamping or an explicit overflow check with a proper `Err` return, such as `ASSERT_SECONDS_RELATIVE_FAILED`/`ASSERT_HEIGHT_RELATIVE_FAILED`) instead of relying on the `uint32()`/`uint64()` constructors to raise on overflow. Additionally, make the Python-side computation conditional on (or consistent with) the already-validated `nowrap` result from `check_time_locks`, so that a bundle already rejected for a timelock overflow does not proceed to unchecked Python arithmetic.

### Proof of Concept
Conceptual reproduction (would require running the full mempool manager, which I could not execute in this read-only session):
1. Submit a spend bundle where the spent coin has a large `CoinRecord.timestamp` (e.g., close to `uint64::MAX / 2`).
2. Include a condition `ASSERT_SECONDS_RELATIVE <very large 8-byte value>` (e.g., near `2**63`) in the puzzle solution.
3. Call `MempoolManager.add_spend_bundle()` (as any RPC `push_tx` caller would).
4. `check_time_locks(..., nowrap=True)` on the Rust side may reject or accept depending on its own bounds checking, but execution still reaches `compute_assert_height()` at [3](#0-2) , where `uint64(coin_record.timestamp + spend.seconds_relative)` is computed without a bounds check, raising `ValueError` if the sum exceeds `2**64-1`.

Because I could not execute code or inspect the compiled `chia_rs` condition-parsing bounds in this session, this should be treated as a **plausible, code-supported analog requiring dynamic verification** (fuzzing `compute_assert_height` with boundary `seconds_relative`/`height_relative` values against realistic `CoinRecord` timestamps) rather than a confirmed exploit.
