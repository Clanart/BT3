## Analog Found: Atomic multi-token escrow release in `IntentsBase._withdraw` / `IntentGatewayV2.withdraw` can be permanently bricked by a single poisoned token/beneficiary, locking the entire order's escrow

### Title
Atomic multi-token escrow settlement is one bad transfer away from permanent fund lockout - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_withdraw` (and its Tron-fork twin `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol`) releases *all* escrowed tokens for an order commitment to a *single* beneficiary in one atomic loop, followed by an atomic transfer of accumulated transaction fees to the same beneficiary. This is the same "atomic multi-transfer" anti-pattern flagged in the external report's `collectFees`: if any single transfer in the bundle reverts (blacklisted beneficiary for one of several tokens, or a malicious/paused token in the order's asset list), the entire settlement reverts, and — because the beneficiary and token set are fixed by the immutable order data and the triggering ISMP message never times out — the failure is permanent and unrecoverable rather than merely delayable.

### Finding Description
`_withdraw` in [1](#0-0)  iterates `body.tokens` and transfers each escrowed asset to one `beneficiary`, then (when `finalize`) transfers accumulated relayer/transaction fees to the same address, all within a single non-reverting-tolerant loop using `IERC20.safeTransfer`/raw `.call`. The Tron fork's `withdraw` at [2](#0-1)  is functionally identical, using explicit `TransferFailed()` reverts on any failed `.call`.

This function is invoked from `onAccept` for both `RequestKind.RedeemEscrow` and `RequestKind.RefundEscrow`, i.e. it is the terminal settlement step for both a solver's payout and a user's refund, as seen in `evm/tron/contracts/apps/IntentGatewayV2.sol` [3](#0-2) . It is also reachable via `onGetResponse` for destination-side cancellation proofs, at [4](#0-3) .

Both dispatch sites that trigger this settlement set `timeout: 0`, e.g. the RefundEscrow dispatch at [5](#0-4) , meaning ISMP will never generate a timeout callback that could open an alternate refund/recovery path — the message either eventually succeeds via `onAccept`/`onGetResponse`, or it fails forever.

Because:
1. `body.tokens` can contain multiple distinct ERC-20s escrowed for the same commitment (order inputs for a refund, or multiple output assets for a fill),
2. `beneficiary` is fixed by data baked into the order (`order.user`) or chosen once by the filler (for `RedeemEscrow`), with no mechanism to substitute a different address later, and
3. the loop has no per-token isolation (no try/catch, no partial-success bookkeeping),

a single poisoned pair — e.g. the beneficiary is blacklisted on a USDC-style token that is one of several escrowed assets, or one of the escrowed tokens itself is a malicious ERC-20 configured to revert transfers to that specific beneficiary — causes every retry of the settlement to revert. All other, perfectly transferable tokens and the accumulated transaction fees tied to that same commitment become permanently stuck in the contract, since `_orders[commitment][token]` is never decremented and `_filled[commitment]` is never set (the whole transaction unwinds).

### Impact Explanation
This directly matches the "loss/lock of funds" and "logic attack" bounty categories: escrowed user or solver funds for an order become permanently unrecoverable through the contract's own defined flows. Unlike the OrderBook DAO/host case, there is no governance lever to swap the stuck address (the beneficiary is user- or filler-supplied order data, not a mutable protocol parameter), and the `timeout: 0` on both `RedeemEscrow` and `RefundEscrow` dispatches removes even the timeout-based refund path other ISMP flows rely on. Any counterparty (a griefing user placing an order with a beneficiary they know is blacklist-prone on one output token, or a solver filling with a malicious output token) can trigger this without needing any privileged role, relayer collusion, or governance compromise — purely by constructing the order/fill inputs, which are unprivileged, user-controlled entrypoints (`placeOrder`, `fillOrder`, `cancelOrder`).

### Likelihood Explanation
Medium: it requires either (a) a beneficiary that is later blacklisted on a fee-token/output token that is part of a multi-token order (plausible for any order routed through a token with an allow/deny-list like USDC), or (b) inclusion of a token in `order.inputs`/`output.assets` that is adversarially configured to revert transfers to a particular address. Both are realistic given intents protocols accept arbitrary ERC-20s as inputs/outputs and beneficiaries are freely chosen by users/solvers. This mirrors exactly the conditions Spearbit accepted as Medium severity in the source report.

### Recommendation
Decouple token delivery in `_withdraw`/`withdraw` so a failure transferring one token/fee does not block release of the others: transfer each token independently with isolated failure handling (e.g. skip-and-credit-to-a-claimable-balance on failure rather than reverting the whole batch), and only gate `_filled`/order-finalization on the set of tokens that require atomicity with the fill accounting, not on unrelated assets. At minimum, provide a governance or per-order escape hatch (e.g. a redirectable beneficiary or forced sweep after a grace period) so funds are not permanently unrecoverable when a single transfer is unblockable.

### Proof of Concept
1. User places an order whose `inputs` include two tokens: `USDC` and `DAI`, with `beneficiary`/`user` set to address `B`.
2. Before refund/redemption settles, `B` gets blacklisted on `USDC` (or the order/fill included a malicious ERC-20 that unconditionally reverts transfers to `B`).
3. Destination cancels or a solver fills the order; the countervailing chain dispatches `RefundEscrow`/`RedeemEscrow` with `WithdrawalRequest{ commitment, tokens: [USDC, DAI], beneficiary: B }` and `timeout: 0` as in [5](#0-4) .
4. `onAccept` → `withdraw(body, isRefund)` loops the tokens: `DAI` transfer would succeed, but `USDC` transfer to `B` reverts, per [6](#0-5) ; the whole call reverts, so nothing — not even `DAI` or the escrowed fees — is released.
5. Because the message has `timeout: 0`, there is no alternate timeout-triggered refund; every re-delivery attempt of the same message hits the same revert, permanently locking all escrowed assets and fees for that commitment.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
