## Finding

Based on direct comparison within the same codebase — `IntentGatewayV2.sol` explicitly refunds unspent native tokens after a fee-token swap, while `EvmHost.sol`'s `dispatch()`/`fundRequest()` functions perform the *same kind of exact-output swap* but never refund the leftover ETH. This is a directly provable local analog to the "no slippage control" bug class.

### Title
Unrefunded native-token overpayment permanently lost in `EvmHost.dispatch()` / `fundRequest()` fee swaps - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native token payment and internally call Uniswap V2's `swapETHForExactTokens` to obtain an exact amount of `feeToken()`. None of these functions expose a caller-controlled maximum-input bound or refund logic — any native token sent beyond what the swap actually consumes is retained by `EvmHost` and never returned to the caller, unlike the equivalent flow in `IntentGatewayV2.sol` which explicitly refunds excess native tokens.

### Finding Description
`dispatch()`: [1](#0-0) 

`dispatch(DispatchGet)`: [2](#0-1) 

`fundRequest()`: [3](#0-2) 

In all three, the full `msg.value` is forwarded to `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The Uniswap V2 router's `swapETHForExactTokens` implementation refunds any leftover ETH (`msg.value - amounts[0]`) to `msg.sender` of that call — which is `EvmHost` itself, not the original transaction sender (`_msgSender()`). None of the three functions capture that refund and forward it back to the caller; there is no post-swap balance check or ETH transfer back to `_msgSender()` anywhere in these functions.

This is directly contrasted by the project's own `IntentGatewayV2.sol`, which performs the same fee-token native-swap pattern but explicitly refunds unspent native tokens to the caller: [4](#0-3) 

Because `EvmHost` has no analogous refund step, any caller who overestimates `msg.value` — which the documentation itself says is unavoidable since off-chain `quote()` estimates are approximate and "vulnerable to sandwich attacks": [5](#0-4) 

...has the surplus permanently trapped in `EvmHost`. There is no minimum-output/maximum-input parameter exposed to the caller (exactly the missing "slippage control option" from the source report), and worse, unlike a pure sandwich case there is no mechanism at all — not even under normal, non-adversarial conditions — to reclaim the overpayment.

### Impact Explanation
This causes direct, permanent loss of user funds (native ETH/BNB/etc.) through core, unprivileged, frequently-used public entrypoints (`dispatch`, `fundRequest`) that every Hyperbridge app relies on for cross-chain message dispatch fee payment. No malicious relayer, prover, or admin is required — an ordinary user simply overestimating the native fee (which the docs themselves acknowledge is imprecise/manipulable) loses the difference with no recovery path. This is a straightforward "loss of funds" impact under the required bounty gate.

### Likelihood Explanation
High. Every caller of `dispatch()`/`fundRequest()` who pays with native tokens is exposed, since exact quoting is explicitly documented as unreliable on-chain, and users commonly pad `msg.value` for safety margin — that padding is silently absorbed by the contract with no refund path, and there is no test in the suite asserting a native-token refund for these functions (in contrast to `IntentGatewayV2Test.sol`, which does test native refunds for its analogous flows).

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.sol`: after the `swapETHForExactTokens` call, compute `msg.value - amounts[0]` (the router's returned `amounts[0]`) and refund the difference to `_msgSender()` via a low-level call, reverting on failure. Apply this fix consistently to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `EvmHost.sol`.

### Proof of Concept
1. A user calls `EvmHost.dispatch(post)` with `post.fee = 100e18` (feeToken units) and sends `msg.value = 1 ether`, based on an off-chain `quote()` estimate that assumed the swap would need close to 1 ETH.
2. Between quoting and execution, the pool price improves (or the user simply padded the value for safety), so `swapETHForExactTokens` only consumes `amounts[0] = 0.8 ether` to produce the required `100e18` fee tokens.
3. The Uniswap V2 router refunds the leftover `0.2 ether` to `msg.sender`, which is the `EvmHost` contract address (since `EvmHost` is the caller of the router in this internal call), not the original user.
4. `EvmHost.dispatch()` never checks or forwards this ETH; the function proceeds to emit `PostRequestEvent` and returns. The `0.2 ether` remains stuck in the `EvmHost` contract balance with no code path that returns it to the user.
5. Repeat for any user of `dispatch()`/`fundRequest()` — each overpayment is a guaranteed, non-recoverable loss, confirmed by the absence of a refund block matching the one present in `IntentGatewayV2.sol` lines 364-368.
