### Title
Participant-controlled identity/small-subgroup encryption key silently downgrades DKG share encryption to a publicly-computable keystream - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
PedPoP's per-message encryption does `ecdh = per_msg_key * recipient_enc_key`, where `recipient_enc_key` is supplied by the recipient inside their `EncryptionKeyMessage` and is stored verbatim with no validation (no non-identity check, no subgroup check, no proof of possession). A participant who registers `enc_key = identity` (or a low-order torsion point on non-prime-order curves) forces every dealer's ECDH output to the identity point (or a tiny subgroup), making the ChaCha20 keystream publicly derivable by anyone who observes the ciphertext. The secret shares "encrypted" to that participant are then plaintext-recoverable by passive observers of the channel — an exposure-of-sensitive-information analog to the Jenkins credential capture (attacker-specified endpoint/key causes secrets to be delivered where an attacker can read them).

### Finding Description
- `Decryption::register` inserts `msg.enc_key` into `enc_keys` with only a duplicate-registration assert; there is no `is_identity()` check, no torsion/subgroup check, and no PoP binding the key to its owner. `EncryptionKeyMessage::read` accepts whatever `C::read_G` returns, and `C::read_G` only checks canonical encoding — the identity point is a canonical encoding and is accepted. [1](#0-0) [2](#0-1) 
- `Encryption::encrypt` → `encrypt` computes `cipher(context, &ecdh(&key, to))` where `to = self.decryption.enc_keys[&participant]`. With `to` = identity, `ecdh` = `identity * key` = identity regardless of the random per-message key, so the keystream is `ChaCha20` keyed solely by `transcript(context, identity.to_bytes())` — fully public. [3](#0-2) [4](#0-3) 
- The message's PoP (`pop`) still verifies — it proves knowledge of the *per-message* key, not the registration key — so nothing detects the downgrade. On blame, `decrypt_with_proof` verifies a DLEq between `enc_keys[decryptor]` and `proof.key`, which also succeeds (identity key → identity proof key). [5](#0-4) 
- The code itself documents the invariant being violated: "Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be leaked" — an identity `enc_key` makes *every* ECDH identical and known. [6](#0-5) 
- In deployment, the shares are routed through the processor/coordinator which reads and relays `EncryptedMessage` bytes (`EncryptedMessage::<C, SecretShare<C::F>>::read`), i.e., the transport is authenticated but not private — exactly the party positioned to exploit a public keystream. [7](#0-6) 

### Impact Explanation
Any observer of the channel (relay/coordinator, or an eavesdropper on the authenticated-but-encrypted transport, which the spec treats as needing ECDH protection: "In order to protect the secret shares during communication") can decrypt every `SecretShare` addressed to the malicious participant from all n dealers, recovering that participant's complete threshold secret share. Combined with shares the attacker legitimately holds as a participant, this reduces the effective threshold and constitutes key-share recovery of material that was intended to be confidential — a genuine secret leak, not merely a DoS. On Ed25519-class curves with torsion, a non-identity small-subgroup `enc_key` gives the same result with a brute-forceable keystream.

### Likelihood Explanation
The attack requires only that the adversary control one DKG participant slot and submit `enc_key = identity` in their public `EncryptionKeyMessage` — a fully public input reachable via `EncryptionKeyMessage::read`/`Commitments::read`. No collusion, no network privilege, and no deviation from message formats is needed; every subsequent dealer execution deterministically encrypts to the public keystream. Medium likelihood/Medium severity, matching the source advisory's class.

### Recommendation
Validate `enc_key` at registration time in `Decryption::register`/`Encryption::register`: reject `enc_key.is_identity()` and, where the ciphersuite has a cofactor, reject non-prime-subgroup points (e.g., require `enc_key` be torsion-free via the `PrimeGroup` guarantee or an explicit `is_torsion_free` check such as `mul_by_cofactor`). Optionally require a Schnorr PoP over the registration key binding it to the participant index and context, mirroring the per-message `pop` already used for `EncryptedMessage`, so registration keys cannot be attacker-chosen degenerate values or replayed/co-opted from other participants.

let chal = t.challenge(b"key");
