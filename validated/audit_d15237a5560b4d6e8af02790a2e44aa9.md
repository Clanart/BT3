### Title
Deposits sent to the deterministic internal offset addresses are silently discarded — funds received that the processor will never credit or plan to spend - (File: processor/src/networks/bitcoin.rs)

### Summary
Analog of the Alligator "gives refunds but cannot receive refunds" class: Serai's Bitcoin pipeline creates value flows that are asymmetric — the scanner can recognize and emit outputs for internal offset-derived addresses (`Branch`, `Change`, `Forwarded`), but only `External` outputs are ever turned into instructions/plans. Because the `Branch`/`Change`/`Forwarded` offset scalars are derived from fixed public strings via `Secp256k1::hash_to_F(KEY_DST, ...)`, any unprivileged party can compute these script_pubkeys and send Bitcoin to them. The scanner will match the output (it keys purely on `script_pubkey`), classify it as non-`External`, and the multisig logic will then drop it — the deposit is received on-chain, spendable only by the threshold key, but never credited, never forwarded, and never included in any Plan.

### Finding Description
`scanner()` in `processor/src/networks/bitcoin.rs:313-346` registers three internal offsets from constant, publicly computable seeds: `hash_to_F(b"Serai Bitcoin Output Offset", b"branch"|b"change"|b"forward")`. `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches outputs solely on `script_pubkey` against the registered script map, so an attacker-crafted transaction paying to the `Forwarded` or `Change` script_pubkey is returned as a `ReceivedOutput` with that offset.

In `processor/src/multisigs/mod.rs:837`, scanned outputs are filtered with `outputs.retain(|output| output.kind() == OutputType::External)` before instruction/plan construction. `Forwarded` outputs are only consumed if `ForwardedOutputDb::take_forwarded_output` finds a matching saved instruction (lines 824-833) — an attacker's unsolicited output has none, so it is dropped. `Change`/`Branch` outputs are dropped outright. The result: the funds sit at a key the multisig controls but the processor has no plan, no instruction, and no code path that will ever spend or credit them — identical in structure to Alligator paying out refunds it could never reclaim: value flows into the system through a path the system cannot account for.

### Impact Explanation
An attacker (or a mistaken depositor) can burn funds into the multisig with zero accounting trail — deposited BTC that is provably received yet permanently unplanned-for, corrupting the processor's accounting invariants. There is no recovery path in the scanned-output flow for non-`External` classifications that lack a matching `ForwardedOutputDb` entry. For a bridge/custody processor, misclassified deposits that vanish from instruction generation are a funds-loss/accounting-integrity issue. Medium.

### Likelihood Explanation
The offset scalars are deterministic constants derivable by anyone (`hash_to_F` of fixed strings); computing the corresponding Taproot script_pubkeys and sending to them requires only a standard Bitcoin transaction — fully reachable by an unprivileged party with public inputs. No collusion, validator access, or leaked material is needed.

### Recommendation
Distinguish unsolicited sends to internal script_pubkeys from legitimately generated internal outputs: only treat `Change`/`Forwarded`/`Branch` outputs as internal if they appear in a transaction the multisig itself constructed (match by txid against known plans/eventualities), or require a per-output commitment/round-bound offset rather than global constant offsets, so external parties cannot forge the classification. Unmatched non-`External` outputs should be surfaced as an error/refund path instead of silently dropped.

### Proof of Concept
1. Compute `offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")` and increment it per `register_offset`'s evenness loop (logic public in `networks/bitcoin/src/wallet/mod.rs:180-196`).
2. Derive `script_pubkey = p2tr_script_buf(group_key + G*offset)` for the current multisig `group_key`.
3. Broadcast a Bitcoin transaction paying ≥ `DUST` to that script_pubkey.
4. `get_outputs`/`scan_transaction` emits it with `OutputType::Forwarded`; `scanner_event_to_multisig_event` finds no `ForwardedOutputDb` entry, `retain(kind == External)` removes it, and no instruction or plan is ever created — the output is received yet never spendable through any processor flow.
