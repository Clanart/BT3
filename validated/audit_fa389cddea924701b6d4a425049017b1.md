### Title
Deterministic nonce reuse via persistent `CachedPreprocesses` across repeated signing calls leaks the validator's private key - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The CVE-2023-47233 class is a lifecycle bug: a resource freed/detached in one path is still used by a concurrently scheduled worker, so the same underlying object is operated on under two different states. Serai's structural analog is `SigningProtocol`'s nonce lifecycle in the MuSig DKG-confirmation signing protocol. `preprocess_internal` stores a single `CachedPreprocess` seed keyed only by `context` (`("DkgConfirmer", attempt)`), and every call to `share_internal` re-derives a fresh `AlgorithmSignMachine` from that same seed — i.e., the nonce object "detached" from a completed sign is silently resurrected and reused by the next call. If `sign` is invoked a second time with a different message or different preprocess set, identical nonces are committed to two distinct Schnorr transcripts, which is textbook nonce reuse and enables recovery of the validator's private key.

### Finding Description
`preprocess_internal` only generates a new seed when `CachedPreprocesses::get` returns `None`; afterward it always loads the persisted seed and calls `AlgorithmSignMachine::from_cache` (`coordinator/src/tributary/signing_protocol.rs:123-147`). `from_cache` routes to `seeded_preprocess`, which deterministically expands the seed with `ChaCha20Rng::from_seed(*seed.0)` to produce `nonces`/`commitments` (`crypto/frost/src/sign.rs:121-141`). Therefore every machine built by `share_internal` for a given `context` has byte-identical nonces.

`share_internal` is reached from two places:

- `DkgConfirmer::share` → `generated_key_pair` (`coordinator/src/tributary/handle.rs:47-60`), which signs `set_keys_message(set, removed, key_pair)`.
- `DkgConfirmer::complete` → `share_internal` again (`signing_protocol.rs:321-324`) to rebuild the machine for share verification.

The message signed is `set_keys_message(...)`, which commits to `key_pair` and `removed`. Both `share` and `complete` take `key_pair` from caller-supplied data (the DKG confirmation flow), and `removed` is recomputed via `removed_as_of_dkg_attempt`. The seed is never deleted, rotated, or bound to `msg`/`preprocesses`: the nonce is bound only to `(b"DkgConfirmer", attempt)`, while the message being signed can vary within that context. The file's own header acknowledges this exact hazard — "it is explicitly unsafe to reuse nonces across signing sessions… In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — and relies on BFT finality plus "no logical flaw letting new messages overwrite prior messages" for safety. That assumption is not enforced by the code: nothing in `share_internal`, `share`, or `complete` records which `(preprocesses, msg)` the cached seed was already used with (the analogous TODO on line 53-54 for Processor preprocesses is unimplemented for this path as well).

### Impact Explanation
Each signature share is of the Schnorr form `s = d + b·e·ρ + λ·x·c` where `d + b·e·ρ` are the deterministic nonces expanded from the cached seed. Two shares produced under distinct challenges `c1 ≠ c2` (distinct `key_pair` or distinct signing set changing `hash_msg`/binding factors) with identical nonces yield `x = (s1 − s2) / (λ·(c1 − c2))` — the validator's MuSig private key, which is the root-of-trust key used for on-chain DKG confirmation. Recovery of this key lets an attacker forge confirmation shares and compromise the validator set's signing authority. The FROST docs confirm severity: "Reusing preprocesses would enable a third-party to recover your private key share" (`spec/cryptography/FROST.md:51-53`).

### Likelihood Explanation
Triggering requires `sign` to run twice under one context with differing inputs. Reachable paths include `complete` being invoked with a `key_pair` differing from the one used in the earlier `share` (the two calls take `key_pair` independently and there is no stored binding between them), or a repeat of `generated_key_pair`/confirmation handling within an attempt where the `removed` set or key pair presented differs (e.g., after a partial rebuild, which the header explicitly permits: "This does set a bound preventing partial rebuilds which is accepted" — an accepted-but-unenforced bound). Because messages are BFT-ordered, honest operation keeps the inputs identical; the vulnerability is that the protocol provides no defense if any path — a bug in attempt/removed handling, a re-execution edge, or an unprivileged participant's confirmation data causing a distinct `key_pair` to be supplied — produces a second `sign` with a different message. The nonce is guaranteed identical whenever that happens, since it is regenerated from the persisted seed rather than freshly sampled.

### Recommendation
Bind the cached preprocess to its exact usage and delete it after first use:
1. Store alongside the seed a commitment `H(preprocesses || msg)` (or the serialized preprocess/commitments and the `key_pair` hash) in `CachedPreprocesses`, and in `share_internal` refuse to `sign` if the stored commitment differs from the current inputs.
2. Clear `CachedPreprocesses` (or set a "spent" flag) once a share is produced, so `complete` rebuilds only for verification via a stored machine state rather than re-signing.
3. Implement the already-noted check (line 50-54 TODOs) verifying the regenerated preprocess/commitments match what was published on-chain before any share is emitted.

### Proof of Concept
Conceptual, using the code's own flow:

```rust
// Attempt N context: ("DkgConfirmer", N)
// Path 1: share() invoked for key_pair A
let share1 = confirmer.share(preprocesses.clone(), &key_pair_a).unwrap();
// internally: preprocess_internal reloads seed S -> nonces k fixed
// machine.sign(preprocesses, set_keys_message(..., key_pair_a))
//   -> s1 = k + c1 * lambda * x

// Path 2: complete() invoked for key_pair B (distinct DKG confirmation data)
// complete -> share_internal(preprocesses, key_pair_b)
// preprocess_internal reloads the SAME seed S -> identical nonces k
// machine.sign(preprocesses, set_keys_message(..., key_pair_b))
//   -> s2 = k + c2 * lambda * x
// c1 != c2 because the transcript commits key_pair via hash_msg

// Attacker observes both shares on tributary and solves:
// x = (s1 - s2) / (lambda * (c1 - c2))
// x is the validator's MuSig private key.
```

Determinism of `k` is guaranteed by `seeded_preprocess` (`crypto/frost/src/sign.rs:127-132`): `ChaCha20Rng::from_seed(*seed.0)` fully determines `Commitments::new` outputs, and the seed is reloaded verbatim from `CachedPreprocesses` on every call (`signing_protocol.rs:137-145`).

Caveat: I could not fully trace every caller of `DkgConfirmer::complete`/`generated_key_pair` to confirm a concrete flow that supplies two distinct `key_pair` values within one attempt; the finding rests on the missing input-binding/spent-flag in `share_internal`, which makes any such path a silent nonce-reuse key-recovery rather than a rejected operation.
