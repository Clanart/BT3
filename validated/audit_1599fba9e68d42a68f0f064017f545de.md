### Title
Commit-review reflog freshness gate trusts attacker-controlled `%ct` (committer date), letting a backdated commit be silently marked "stale" and skip the LLM security gate - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`_git_reflog_recent_commits` classifies reflog entries as "fresh" or "stale" using each commit's own `%ct` (committer timestamp) compared to wall-clock `now`, except for the single most-recent reflog entry (`idx==0`), which is unconditionally exempt. Since committer/author timestamps are fully attacker-controlled via `--date`/`GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` (ordinary git usage, no privilege required), an attacker can chain a backdated malicious commit with a fresh cover commit inside one quiet/redirected Bash invocation so the malicious commit lands at `idx>=1` with `age > max_age_s`, gets counted as `stale`, and is dropped from the `fresh` list before `handle_commit_review_posttooluse` ever calls `analyze_code_security` on it.

### Finding Description
`_git_reflog_recent_commits` (`plugins/security-guidance/hooks/gitutil.py:227-300`) reads `git log -g -n max_n --format=%H|%ct|%gs HEAD` and, for each `commit*` reflog entry, marks it fresh if `idx == 0` or `age <= max_age_s` (120s default), else increments `stale`. This function is only consulted from `handle_commit_review_posttooluse` (`plugins/security-guidance/hooks/security_reminder_hook.py:965-989`) as a *fallback* when the stdout-based `[branch sha]` fast path fails to detect a successful commit (e.g., output piped, redirected, or `-q`).

An attacker who chains two commits in a single Bash invocation with suppressed output, e.g.:
```
git commit -q -m "malicious" --date="2000-01-01T00:00:00" ; git commit -q --allow-empty -m "cover"
```
produces a reflog where `HEAD@{0}` is the fresh "cover" commit (exempt anyway) and `HEAD@{1}` is the "malicious" commit with an attacker-forged, decades-old `%ct`. Since `GIT_COMMITTER_DATE`/`--date` also backdates the timestamp git writes into the reflog entry itself, `_git_reflog_recent_commits` computes `age >> max_age_s` for the malicious entry and classifies it as `stale`, excluding it from `fresh`. Back in `handle_commit_review_posttooluse`, `_reflog_shas = [s for s in _fresh if s not in _already]` therefore contains only the cover commit's SHA. The subsequent `git show -p <sha>` / `analyze_code_security` loop (`security_reminder_hook.py:1117-1178`) reviews only the cover commit, and the malicious commit's diff is never sent to the LLM review pipeline; it is also never appended to `.git/sg-reviewed-shas` (`_append_reviewed_shas` is only called for `shas` that were actually resolved/reviewed, `security_reminder_hook.py:1254-1263`), so it isn't a dedup miss - it's a genuine skip of review for that specific commit's content via the fast per-commit gate. [1](#0-0) [2](#0-1) [3](#0-2) 

Existing mitigations that don't fully close the gap: `_load_reviewed_shas` dedup correctly prevents a SHA from being reviewed twice once actually reviewed [4](#0-3) ; push-sweep (`_compute_push_sweep_base`) would independently re-catch the content on a subsequent `git push` since the malicious SHA never entered the reviewed set [5](#0-4) ; and the Stop hook's content-diff-based review (`compute_v2_review_set`) is a separate, timestamp-independent backstop. So the exploit's scoped impact is specifically: the fast, agentic per-commit LLM review is bypassed for the backdated commit, not a permanent, unconditional escape from every review surface.

### Impact Explanation
This is a trust-boundary bypass of the commit-review LLM security gate: a genuinely new, unreviewed, malicious commit's diff is withheld from `analyze_code_security` because a security-relevant "freshness" decision is derived from an attacker-forged git timestamp rather than actual review state. It matches the "malicious commit content escapes the LLM commit-review gate" impact class named in the question - it is a control-bypass of an automated security review, not merely a UX/perf quirk.

### Likelihood Explanation
Fully reachable by an unprivileged user with normal local git access: no admin rights, no leaked keys, no social engineering - just `--date`/`GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` (documented, ordinary git flags) plus chaining two commits with suppressed stdout in one Bash tool call. It is deterministic and repeatable every time the fallback path is exercised with a sufficiently backdated first commit.

### Recommendation
Do not gate freshness on the commit's own `%ct`/committer date, which is fully attacker-controlled. Use `%gd`/reflog entry ordinal position and/or the reflog file's own mtime-independent sequence, or simply drop the age gate for any reflog entry that is part of the *same* Bash invocation's HEAD movement (e.g., compare against `head_at_capture`/pre-command HEAD captured at PreToolUse rather than a wall-clock/committer-date delta). At minimum, treat every `commit*` reflog entry between the pre-command HEAD and the post-command HEAD as fresh regardless of `%ct`, since that range is by construction "commits made by this Bash call."

### Proof of Concept
Integration test in a scratch repo:
1. `git init`; create baseline commit.
2. Run `git commit -q --allow-empty -m "malicious" --date="2000-01-01T00:00:00Z"` then `git commit -q --allow-empty -m "cover"` as one Bash invocation with stdout/stderr captured but suppressed (`-q`), simulating `tool_response`.
3. Call `handle_commit_review_posttooluse` (or directly `_git_reflog_recent_commits(repo_root)`) and assert:
   - `stale_count >= 1` and the "malicious" SHA is present in the stale bucket, not in `fresh`.
   - `analyze_code_security` / `git show -p` is invoked only for the "cover" SHA (mock/spy on `subprocess.run` for `git show`).
   - `.git/sg-reviewed-shas` after the run does NOT contain the "malicious" SHA.
4. Assert the invariant violation: the "malicious" commit object exists in the repo, is genuinely new (not previously reviewed), yet never appears in any `analyze_code_security` call during this invocation.

def _compute_push_sweep_base(prev_upstream, push_range, reviewed):
    """Advance the diff base past the contiguous reviewed prefix.

    Spec: review `git diff B..HEAD` where `B` is the newest commit such that
    `prev_upstream..B` is entirely in `reviewed`. Returns (B, unreviewed_tail).
    `B == None` means the whole range is reviewed (caller should skip).
    `push_range` must be oldest→newest.

    Examples (✓=reviewed, ✗=not):
      [✓1, ✗2, ✓3]  → B=1, tail=[2,3]   (cannot trim suffix; Read is at HEAD)
      [✓1, ✓2, ✓3]  → B=None            (all reviewed → skip)
      [✗1, ✓2, ✗3]  → B=prev_upstream, tail=[1,2,3]
      []            → B=None
    """
    i = 0
    while i < len(push_range) and push_range[i] in reviewed:
        i += 1
    if i == len(push_range):
        return None, []
    base = push_range[i - 1] if i > 0 else prev_upstream
    return base, push_range[i:]

def _load_reviewed_shas(repo_root):
    """Set of full 40-hex shas previously reviewed in this clone."""
    p = _reviewed_shas_path(repo_root)
    if not p or not os.path.exists(p):
        return set()
    out = set()
    try:
        with open(p, "r") as f:
            for line in f:
                sha = line.split("\t", 1)[0].strip()
                if len(sha) == 40 and all(c in "0123456789abcdef" for c in sha):
                    out.add(sha)
    except OSError:
        pass
    return out
