### Title
Cached FROST preprocess is reused across multiple `share`/`complete` calls, enabling nonce reuse and validator secret-key recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`SigningProtocol::preprocess_internal` stores a deterministic `CachedPreprocess` seed in the DB keyed only by `context` and never deletes it. Every call to `share_internal` (and therefore `DkgConfirmer::share` and `DkgConfirmer::complete`) re-derives the *same* nonces from that seed via `AlgorithmSignMachine::from_cache` → `seeded_preprocess`, which feeds the seed into `ChaCha20Rng` deterministically. This is the Serai analog of CVE-2018-16402's "decompress twice" class: an object that must be consumed once is silently consumed repeatedly. FROST explicitly requires a preprocess to be used only once — reuse "will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85`, `sign.rs:211-219`).

### Finding Description
- `coordinator/src/tributary/signing_protocol.rs:123-145`: if `CachedPreprocesses::get(txn, context)` returns a value, it is decrypted and passed to `from_cache`. There is no `remove`/`delete` anywhere — `CachedPreprocesses` is only ever `set`/`get` (only file matching).
- `crypto/frost/src/sign.rs:121-144` (`seeded_preprocess`): `ChaCha20Rng::from_seed(*seed.0)` → identical seed ⇒ identical `nonces` and identical published `preprocess`.
- `share_internal` (`signing_protocol.rs:150-180`) calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` where `preprocesses` is an attacker-influenced map of *other participants'* preprocess bytes and `msg` is attacker-influenced (via `key_pair` in `DkgConfirmer::share`, `signing_protocol.rs:288-302`).
- `DkgConfirmer::complete` (`signing_protocol.rs:312-327`) re-invokes `share_internal` a second time for the same `attempt` context, and `share()` can itself be invoked repeatedly with different `preprocesses` maps or different `key_pair`s.
- In FROST the share is `s = d + e·ρ + λ·secret·c` where the binding factor ρ and challenge `c` are computed over `(msg, commitments set)`. Same `(d, e)` but different counterparty commitments or message ⇒ two shares `s₁, s₂` with known differing `c₁·ρ` terms let an observer solve for `λ·secret`, hence recover the validator's MuSig secret share (λ is a known public Lagrange coefficient).

### Impact Explanation
Any party who can cause the coordinator's `DkgConfirmer` to run `share`/`complete` more than once per attempt with differing inputs (different submitted `preprocesses` sets, or a different `key_pair` / `removed` set) receives two FROST signature shares produced under the *same* nonce pair. This is textbook nonce reuse: it yields the validator's `Ristretto` secret key share (`self.key`) directly, breaking the MuSig signing for the validator set — the recovered key can be used to forge the validator's participation in tributary consensus signatures. This meets the "key share recovery" bar.

### Likelihood Explanation
The determinism is unconditional: `preprocess_internal` always reads back the cached seed and `from_cache` deterministically regenerates nonces (`signing_protocol.rs:137-145`). The only question is whether `share_internal` can execute twice for one `(DkgConfirmer, attempt)` context — and `complete()` inherently re-runs `share_internal` after `share()` already ran (`signing_protocol.rs:321-323`), so the code itself performs the second use. If either call observes a different `preprocesses` map or message (both are per-call parameters supplied from network-provided data), the reused nonces are bound to two distinct challenges — sufficient for recovery. Reboot/retry paths ("caller is expected to re-issue") make repeat invocations routine rather than exceptional.

### Recommendation
Consume the cache on use: after `CachedPreprocesses::get` in `preprocess_internal`, delete the DB entry (or store a "spent" marker) so `from_cache` can never be invoked twice with the same seed — matching the documented invariant that a `CachedPreprocess` "MUST only be used once" (`crypto/frost/src/sign.rs:211`). `complete` should reuse the machine produced by `share` rather than regenerating it via `share_internal` (e.g., persist/share the `AlgorithmSignatureMachine` or store the produced share and short-circuit).

### Proof of Concept
1. `DkgConfirmer::share(preprocesses_A, key_pair_A)` → `preprocess_internal` fetches cached seed `S`, regenerates nonces `(d, e)`, emits share `s₁ = d + e·ρ₁ + λ·sk·c₁` for `(msg₁, commitments_A)`.
2. `DkgConfirmer::complete(preprocesses_B, key_pair_A, shares)` (or a second `share` call with a modified `preprocesses` map — one altered counterparty commitment byte suffices) → same seed `S`, same `(d, e)`, emits `s₂ = d + e·ρ₂ + λ·sk·c₂`.
3. With `ρ₁,ρ₂,c₁,c₂` recomputed publicly from the published preprocesses and message, solve the two linear equations for `λ·sk` (and `d + e·ρ`), recovering the validator's secret share `sk`.

Root cause: missing consumption/deletion of the cached seed at `coordinator/src/tributary/signing_protocol.rs:137-145`, violating the single-use contract documented at `crypto/frost/src/sign.rs:83-92` and `sign.rs:209-224`.
