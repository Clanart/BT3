### Title
Deterministic `CachedPreprocess` reuse across `share`/`complete` re-execution leaks the validator's private key share - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
`SigningProtocol::preprocess_internal` deterministically derives FROST nonces from a seed cached in the DB under `context` (`coordinator/src/tributary/signing_protocol.rs:123-145`). Every call to `share_internal` re-invokes `preprocess_internal`, so every signature share produced under the same context uses **the same nonce scalars**. `DkgConfirmer::share` and `DkgConfirmer::complete` are two distinct public entry points that both reach `share_internal` (`signing_protocol.rs:288-327`), and `complete` accepts an independent, caller-supplied `preprocesses` map. If the set of preprocesses passed to `complete` differs from the set used at `share` time (e.g., additional honest validators' preprocesses arrive later), the same nonce is used to sign a different `preprocesses` binding challenge — FROST nonce reuse — allowing third-party recovery of the validator's private key share from the two published shares.

### Finding Description
- `preprocess_internal` loads `CachedPreprocesses` keyed only on `self.context` and rebuilds the sign machine via `AlgorithmSignMachine::from_cache(...)` (`coordinator/src/tributary/signing_protocol.rs:123-145`). Per the FROST spec this seeded RNG makes the entire preprocess — including the nonce scalars `(d, e)` — deterministic for a given context (`crypto/frost/src/sign.rs:83-92`, `spec/cryptography/FROST.md:45-62`).
- `share_internal` calls `self.preprocess_internal(participants).0` every time it is invoked (`signing_protocol.rs:150-156`).
- `DkgConfirmer::share` is called once when threshold preprocesses are available (`signing_protocol.rs:303-310`); `DkgConfirmer::complete` is invoked later with its own `preprocesses` argument and internally calls `share_internal` again (`signing_protocol.rs:312-327`).
- The signing set `included` is derived from `preprocesses.keys()` inside `SignMachine::sign` (`crypto/frost/src/sign.rs:290-313`). The `preprocesses` challenge that binds each participant's commitments — and the Lagrange coefficient `λ_i` and per-participant binding factor `ρ_i` — therefore depend on which participants' preprocesses are supplied. Two calls with different `preprocesses` maps produce shares `s₁ = r + c₁·λ₁·x` and `s₂ = r + c₂·λ₂·x` with the **identical** nonce `r` but different challenges/coefficients.
- The header comment acknowledges the danger of re-execution with fixed nonces but only argues safety via BFT message ordering (`signing_protocol.rs:25-54`); it does not account for the `share`/`complete` pair being executed with *different* preprocess sets under the same cached seed.

### Impact Explanation
Both signature shares are published on the tributary (signed `SignData` transactions). Any observer who sees two shares generated from the same `CachedPreprocess` seed but different signing sets/challenges can solve the linear system for the validator's MuSig private key share — full compromise of that validator's root-of-trust key, enabling forgery of further DKG confirmations/tributary signatures. This matches the documented consequence of `CachedPreprocess` reuse ("Reuse will enable third-party recovery of your private key share", `crypto/frost/src/sign.rs:85-87`).

### Likelihood Explanation
No malicious validator is required: `share` runs with whatever preprocesses have arrived (≥ threshold), and `complete` runs later with the preprocesses accompanying the shares — frequently a superset or a differently-truncated set. A validator that simply reboots, or receives preprocesses from a different subset at each stage, produces the second signature share. Any participant can also deliberately widen the set by contributing additional valid preprocesses. Severity: Critical/High (private key share recovery).

### Recommendation
Bind the cached-preprocess context to the exact signing set/message (e.g., key `CachedPreprocesses` on `(context, hash(included, msg))` and refuse to sign if a previously used seed is requested for different inputs), or track in the DB that a share was already produced for a context and never re-derive the same seed for a second `sign` call. Alternatively, have `complete` reuse the exact `preprocesses` map persisted at `share` time rather than accepting a fresh caller-supplied map.

### Proof of Concept
1. During DKG confirmation attempt `a`, coordinator calls `DkgConfirmer::share(preprocesses_A, key_pair)` where `preprocesses_A` covers participants `{1..=t}`. `preprocess_internal` derives seed `S` from `("DkgConfirmer", a)` and signs → publishes share `s₁ = r + c₁·λ₁·x`.
2. Later, `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` is invoked where `preprocesses_B` covers `{1..=t+1}` (an extra honest validator's preprocess arrived). `share_internal` reloads `S`, regenerates the identical nonce `r`, and signs over a different `preprocesses` challenge → share `s₂ = r + c₂·λ₂·x`.
3. An observer solves the two linear equations (known `cᵢ, λᵢ`, common `r`) for `x`, recovering the validator's Ristretto private key share.
