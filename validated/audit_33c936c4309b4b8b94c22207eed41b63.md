### Title
Gasless swap admission checks use stale AMM state, letting a public swap frontrun a pending `GaslessSwapTx` to force its rejection - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The `kaiax/gasless` module admits a `GaslessSwapTx` into the pool/pending-queue based on a point-in-time check of the DEX exchange rate (`checkBalanceForSwap`), but the actual swap is executed later inside a bundle during block building. Any unprivileged account can submit an ordinary swap transaction against the same liquidity pool to move the price between admission time and block-building time, causing the previously-valid `GaslessSwapTx.AmountIn` to become insufficient for the DEX's `GetAmountIn(token, minAmountOut)` requirement. This is directly analogous to the reported `SwapperImpl.flash` issue: a threshold/amount check performed against a shared, externally-manipulable state value (pool reserves / balance) can be invalidated cheaply by any third party between validation and execution, causing the legitimate transaction to be rejected/reverted.

### Finding Description
`GaslessModule.checkBalanceForSwap` computes the current required input amount from the swap router and compares it against the user-supplied `AmountIn`: [1](#0-0) 

This check is performed once, at tx-pool admission (`GetCheckBalance`), using the DEX price at that moment: [2](#0-1) 

The gasless flow trusts this single admission-time check; the `GaslessSwapTx` is only re-validated for structural correctness in `VerifyExecutable` (nonce, token, amounts consistency) but not the DEX rate again: [3](#0-2) 

Because `GaslessSwapRouter.swapForGas` (the on-chain function actually invoked at block-building time) itself computes/enforces `amountIn >= getAmountIn(token, minAmountOut)` against the pool state *at execution time* (as evidenced by the identical assertion being re-run on-chain, producing `"insufficient amountIn"` reverts in the on-chain test suite): [4](#0-3) 

an attacker can submit a normal swap on the same pool (any public, unprivileged transaction) to shift reserves after the victim's `GaslessSwapTx` has already been admitted/promoted to pending, but before it is picked up for block building. When the block builder later executes the bundle `[LendTxGenerator, GaslessApproveTx?, GaslessSwapTx]`, `swapForGas` reverts on-chain because the now-current `requiredAmountIn` exceeds the victim's fixed `AmountIn`.

Because bundle execution is atomic and rolled back on any failure: [5](#0-4) 

the entire bundle (including the proposer-funded `LendTxGenerator` transaction) is discarded via `restoreEnv()`, so the proposer does not lose the lent gas fee. However, on failure the code calls `markAllTxUnexecutable()`, marking the swap (and any paired approve) transaction unexecutable: [6](#0-5) 

This mirrors the Swapper `flash` bug class exactly: a threshold comparison (`AmountIn >= requiredAmountIn`, analogous to `baseAmount <= balanceOf`) is validated against mutable shared state (pool reserves / contract balance) at one point in time, but enforced again later against the *current* state at execution time, and any unprivileged party can manipulate that shared state cheaply to force the check to fail for someone else's transaction.

### Impact Explanation
An attacker (any address, no special privilege) can grief specific gasless-swap users by:
1. Observing a pending `GaslessSwapTx` (or a bundle of `GaslessApproveTx`+`GaslessSwapTx`) in the mempool.
2. Submitting a small/cheap swap on the same token pair to move `GetAmountIn(token, minAmountOut)` above the victim's fixed `AmountIn`.
3. Causing the victim's gasless swap to fail atomically at block-building time, wasting the victim's opportunity to use the gasless flow for that nonce, and causing the transaction/bundle to be marked unexecutable and dropped from further inclusion attempts.

This is a denial-of-service against the gasless (KIP-247) feature that a single unprivileged transaction sender can trigger repeatedly and cheaply against any target user, undermining the intended "gasless UX" guarantee and repeatedly consuming the victim's nonce/bundle slot without ever letting the swap succeed, which can be sustained to permanently block a specific user's gasless transactions for as long as the attacker is willing to pay for cheap swaps.

### Likelihood Explanation
Likelihood is high in an active DEX pool: the attacker only needs visibility into the public mempool (to see a pending gasless swap referencing a particular token/pool) and needs to submit one ordinary, low-cost swap transaction that nudges `GetAmountIn` upward beyond the victim's specified `AmountIn`. No special role (validator, operator, or node) is required — this is reachable purely as a public transaction sender competing with block assembly timing, similar to the original Sherlock finding's requirement of "any caller frontrunning `flash`."

### Recommendation
- Add slippage tolerance/margin awareness in `checkBalanceForSwap` and re-validate the DEX-rate condition (`AmountIn >= GetAmountIn(...)`) immediately before/at block-building time (in `ExtractTxBundles`/`commitBundleTransaction`), not only at admission time, so bundles with stale rates are proactively excluded rather than discovered as failures during on-chain execution.
- Consider allowing the swap router/module to tolerate a bounded price-impact window (e.g., checking against a recent price average or an oracle-bounded amount) rather than a raw spot-price comparison that is trivially manipulable by any subsequent swap.
- Avoid marking the `GaslessSwapTx` permanently unexecutable purely because of a transient price-based revert that could succeed in a later block once prices normalize; instead, distinguish deterministic invalidity (e.g., bad signature, insufficient balance to the sender's true assets) from transient/price-dependent invalidity before dropping the transaction from future consideration.

### Proof of Concept
1. Victim submits `ApproveTx` (nonce N) + `SwapForGas(token, amountIn=X, minAmountOut=Y, amountRepay=R, deadline)` (nonce N+1). At submission time, `checkBalanceForSwap` computes `GetAmountIn(token, Y) <= X`, so both pass admission and are promoted to pending (module logic in `kaiax/gasless/impl/tx_pool.go` lines 107-182, `IsReady` lines 185-230).
2. Attacker observes this pending pair in the mempool and submits (and gets included first, e.g. with a higher gas tip) an ordinary swap on the same token/WKAIA pool that shifts reserves so that `GetAmountIn(token, Y)` now exceeds `X`.
3. When the proposer builds a subsequent block and extracts the gasless bundle via `ExtractTxBundles` (`kaiax/gasless/impl/builder.go` lines 28-72), the bundle `[LendTxGenerator, ApproveTx, SwapTx]` is executed atomically in `commitBundleTransaction` (`work/worker.go` lines 877-954). The on-chain `swapForGas` call reverts because `amountIn < getAmountIn(token, minAmountOut)` under the new reserves (same assertion validated off-chain in `tests/gasless_test.go` lines 251-253), causing `receipt.Status != types.ReceiptStatusSuccessful`.
4. The whole bundle state (`lastSnapshot`) is rolled back and all bundle transactions are marked unexecutable (`markAllTxUnexecutable`, `work/worker.go` lines 887-894), so the victim's gasless swap never succeeds in that block or any subsequent attempt, at negligible cost to the attacker.

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

// VerifyExecutable checks if the given transactions form a valid gasless transaction
// It returns an error explaining why the transaction is not executable if it's not,
// and a boolean indicating whether the transaction is executable
func (g *GaslessModule) VerifyExecutable(approveTxOrNil, swapTx *types.Transaction) error {
	// Sx.
	swapArgs, ok := decodeSwapTx(swapTx, g.signer)
	if !ok {
		return ErrDecodeSwapTx
	}
	if !g.isSwapTx(swapArgs) {
		return ErrSwapTxInvalid
	}

	// Conditions involving ApproveTx
	if approveTxOrNil != nil {
		// Ax.
		approveArgs, ok := decodeApproveTx(approveTxOrNil, g.signer)
		if !ok {
			return ErrDecodeApproveTx
		}
		if !g.isApproveTx(approveArgs) {
			return ErrApproveTxInvalid
		}
		// AP1.
		if approveArgs.Sender != swapArgs.Sender {
			return ErrDifferentSenders
		}
		// SP1.
		if approveArgs.Token != swapArgs.Token {
			return fmt.Errorf("%w: approve token %s, swap token %s", ErrDifferentTokens, approveArgs.Token.Hex(), swapArgs.Token.Hex())
		}
		// SP2.
		if approveArgs.Amount.Cmp(swapArgs.AmountIn) < 0 {
			return fmt.Errorf("%w: approve amount %s, required amount %s", ErrInsufficientApproveAmount, approveArgs.Amount.String(), swapArgs.AmountIn.String())
		}
		// SP3.
		if approveTxOrNil.Nonce()+1 != swapTx.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, swap nonce %d (expected %d)", ErrNonSequentialNonce, approveTxOrNil.Nonce(), swapTx.Nonce(), approveTxOrNil.Nonce()+1)
		}
		if nonce := g.getCurrentStateNonce(approveArgs.Sender); nonce != approveTxOrNil.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, current nonce %d", ErrApproveNonceNotCurrent, approveTxOrNil.Nonce(), nonce)
		}
	} else {
		// SP3.
		if nonce := g.getCurrentStateNonce(swapArgs.Sender); nonce != swapTx.Nonce() {
			return fmt.Errorf("%w: swap nonce %d, current nonce %d", ErrSwapNonceNotCurrent, swapTx.Nonce(), nonce)
		}
	}

	// SP4.
	if swapArgs.AmountRepay.Cmp(repayAmount(approveTxOrNil, swapTx)) != 0 {
		return fmt.Errorf("%w: got %s, expected %s", ErrIncorrectRepayAmount, swapArgs.AmountRepay.String(), repayAmount(approveTxOrNil, swapTx).String())
	}

	return nil
}
