### Title
Payout `OP_RETURN` operator attribution is unauthenticated, letting anyone reimburse an operator that never fronted the withdrawal - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` attributes a confirmed payout transaction to whichever operator's x-only pubkey happens to appear in the transaction's `OP_RETURN` output, with no check that this operator actually supplied the funds that paid the user. Because the withdrawal input is signed with `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, that signature only commits to the single vault input and its corresponding user-payout output — it does not commit to the other inputs (who funds the transaction) or to the `OP_RETURN` output (who gets credited). This lets an unprivileged party reuse the leaked signature, pay the user with their own funds, and stamp an arbitrary operator's key in `OP_RETURN`, causing that operator to be credited by the protocol for a payout it never funded.

### Finding Description
`update_finalized_payouts` reads the operator identity for a confirmed payout purely from the transaction body: [1](#0-0) 

This value is persisted as `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk`: [2](#0-1) 

An operator's own reimbursement flow later trusts this DB field as proof that *it* fronted the withdrawal, checking only that the stored key equals its own signer key — never that it actually broadcast or funded the transaction: [3](#0-2) 

If the check passes, the operator proceeds to build and sign its kickoff/reimbursement transactions for that deposit: [4](#0-3) 

The withdrawal input signature that anchors the whole payout transaction is explicitly documented/required to use `SinglePlusAnyoneCanPay`: [5](#0-4) 

`SIGHASH_SINGLE|ANYONECANPAY` only binds the signer's input to the single corresponding output; it places no constraint on any other input (i.e., who pays the fee/funding) or any other output (i.e., the `OP_RETURN` attribution byte string). Consequently, once this signature is observable — either because the aggregator forwards `WithdrawParamsWithSig` (containing `input_signature`) to potentially many operator clients: [6](#0-5) 
or because any attempted payout transaction is visible in the mempool before confirmation — any outside party can build a *different* transaction that reuses the same signed input, funds the user's output itself, and writes an arbitrary operator's x-only pubkey into `OP_RETURN`. If that competing transaction confirms instead of (or as) the canonical payout, `update_finalized_payouts` will attribute the payout to the named operator regardless of who actually paid.

This breaks the intended equality: **the operator credited with reimbursement == the party that actually fronted the withdrawal BTC**. The bug class matches the external report precisely — the code accepts a self-declared/unauthenticated field (the `OP_RETURN` operator key, analogous to `msg.sender`/`from` in the ERC-20 example) as authoritative for an attribution decision, without verifying that the named party is the one who actually performed the debited action.

### Impact Explanation
An operator that is credited (falsely) as the payer will run its normal automated flow (`validate_payer_is_operator` → `get_next_txs_to_send` → kickoff/challenge/reimbursement) and ultimately reclaim `bridge_amount` from the deposit's collateral/round mechanism for a withdrawal it never funded. This is a direct instance of "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" — the Critical impact category listed in scope. The party who actually paid the withdrawing user receives nothing back from the protocol; the vault-backed reimbursement instead goes to whichever operator's key the attacker chose to write into `OP_RETURN`.

### Likelihood Explanation
The attacker needs only ordinary Bitcoin capability: observe/obtain the `SIGHASH_SINGLE|ANYONECANPAY` witness for the withdrawal input (available directly if the aggregator forwards the withdrawal to multiple operator endpoints, or from the mempool once any payout attempt is broadcast), assemble a competing transaction with their own funding input(s) and a chosen `OP_RETURN`, and get it confirmed instead of/along with the intended payout. No verifier, operator, watchtower, or aggregator role, no key compromise, and no majority hashrate is required — only the ability to construct and relay one Bitcoin transaction, which is available to any unprivileged actor.

### Recommendation
Do not derive payer attribution solely from a self-declared `OP_RETURN` field in the confirmed transaction. Bind the operator identity to something the operator actually authenticated when funding the payout — e.g., require the operator's funding input(s) to be signed by (or otherwise cryptographically tied to) the specific operator's key that is being credited, or have the operator pre-commit (e.g., via a MuSig2/pre-signed commitment at deposit/kickoff setup time) to the payout transaction's txid before it is broadcast, and verify that commitment during `validate_payer_is_operator` instead of trusting the mined transaction's `OP_RETURN` content.

### Proof of Concept
1. During a withdrawal, the aggregator forwards `WithdrawParamsWithSig` (including the user's `SIGHASH_SINGLE|ANYONECANPAY` `input_signature` over the vault UTXO) to the target operator(s) (`core/src/rpc/aggregator.rs:1870-1886`), or the attacker simply observes the operator's payout transaction in the mempool before it confirms.
2. The attacker (an unprivileged third party with no protocol role) constructs an alternative transaction: it reuses the same signed vault input/output pair (valid because the sighash does not commit to other inputs/outputs), adds its own funding input(s) to pay the user's output amount out of its own pocket, and sets the `OP_RETURN` output to an arbitrary operator's x-only public key (e.g., the key of a targeted honest operator).
3. The attacker broadcasts and gets this transaction confirmed (e.g., with a higher fee, before the legitimate payout is mined).
4. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses this confirmed transaction, extracts the attacker-chosen x-only key from `OP_RETURN`, and records it via `update_payout_txs_and_payer_operator_xonly_pk` as `payout_payer_operator_xonly_pk` for that withdrawal.
5. The named operator's automation later calls `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`), sees its own key matches the DB record, and proceeds with `get_next_txs_to_send`/kickoff signing to claim reimbursement for a withdrawal it never funded — draining vault-backed funds to an operator that performed no corresponding payout.

        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,

        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
