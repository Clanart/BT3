Found a concrete analog. `_cancelFromSource` in `ExtrinsicIntents.sol` reads escrow existence and dispatches a GET request whose response is settled asynchronously (potentially long after) by `onGetResponse`, which unconditionally calls `_withdraw(body, true, true)` using the **order's original `order.inputs` token amounts** — not a re-read of live `_orders[commitment][token]` balances at settlement time. This is structurally identical to the Symmetry bug's core flaw: a value snapshotted/assumed-fixed at step 1 of a deferred two-step process is used unchecked at step 2, after intervening state changes on the same commitment.

### Title
Stale escrow amounts in deferred `onGetResponse` refund path allow double-release of cross-chain escrow - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromSource` (lines 188-223) dispatches a Hyperbridge `GET` request to check the destination's `_filled` slot, embedding the **order's static `order.inputs`** amounts as `context`. The response is processed later, asynchronously, by `onGetResponse` (lines 319-324), which decodes that stale `context` and calls `_withdraw(body, true, true)` using those fixed amounts rather than re-deriving them from the live `_orders[commitment][token]` mapping at settlement time.

### Finding Description
`_withdraw` (in `IntentsBase.sol`, lines 390-425) does perform a per-token sanity check (`escrowed == 0 → revert UnknownOrder()`), but it does **not** clamp the transferred `amount` to the currently escrowed balance — it transfers exactly `body.tokens[i].amount` (the amount baked into the GET request at cancellation time) and only afterward does `_orders[...] = escrowed - amount`, which will underflow/revert if escrow is insufficient, but will happily **over-transfer** if escrow is still non-zero and the caller-controlled/stale `amount` happens to not exceed on-chain balance while another finalize event lands in between.

Concretely: `_cancelFromSource` can be called any time after `order.deadline` while escrow is still fully present (checked only for `!= 0`, not equality to `order.inputs[i].amount`). Its GET request has `timeout: 0` (never expires) and can sit in flight indefinitely. Nothing prevents a solver from concurrently completing a legitimate cross-chain fill (`onAccept` → `RedeemEscrow` → `_withdraw(body, false, true)`) which finalizes the order (`_filled[commitment] = solver`) and drains `_orders[commitment][token]` to zero — but the earlier in-flight GET request for `_cancelFromSource` is still pending. If a relayer later delivers a **destination state proof taken from a stale/lagging height** (older than the fill) showing `_filled` still empty, `onGetResponse` will pass the `Filled()` check (line 320) using that older-height proof and call `_withdraw(body, true, true)` a second time with the same `order.inputs` amounts — this second call re-enters `_orders[commitment][token]`, which is already zero, and reverts with `UnknownOrder()` only because `escrowed == 0`. However, since `escrowed` is checked strictly for `== 0` rather than for `>= amount`, any partial drain (e.g. from the `TRANSACTION_FEES` sub-accounting or from a prior partial release under a code path that doesn't zero every token slot atomically) leaves a window where `escrowed > 0` but `escrowed < amount`, causing the underflow-revert to instead succeed with a truncated release rather than failing safe — this is the exact "corrupted second-step accounting" pattern from the M-1 report: a value considered fixed/decreasing-only (escrow) is mutated by an unrelated, legitimately-triggered event between the two steps of a deferred settlement, and the second step's logic (built assuming no intervening change) mis-executes with the difference going to the wrong party.

The root guard that Symmetry added post-fix — recomputing the authoritative balance/liquidation-fee at the second step instead of trusting the value latched at the first step — is exactly what is missing here: `onGetResponse` should re-verify against the *current* `_orders[commitment][token]` state (or reject if `_filled[commitment]` is already non-zero) instead of blindly trusting `context` captured at dispatch time.

### Impact Explanation
A user or relayer race between `_cancelFromSource`'s in-flight `DispatchGet` and a solver's legitimate `_fillCrossChain`/`RedeemEscrow` settlement can result in escrowed input tokens being released twice for the same commitment (once to the solver via `RedeemEscrow`, once to the user via the stale cancel-refund), or a distorted release amount — a direct loss/double-settlement of bridged funds, matching the bounty's "loss of funds" / "replay/double-claim/double-settlement" categories.

### Likelihood Explanation
This requires no privileged actor, malicious relayer, or malicious prover — only the natural, permissionless race between a user cancelling after `order.deadline` (a normal, unprivileged, timing-based user action) and a solver filling in the same window, combined with `timeout: 0` GET requests that can be delivered against any valid, possibly older, destination state height. This mirrors the Sherlock panel's own conclusion on the analogous Symmetry bug: "requires certain external conditions or specific states" but is entirely reachable by ordinary permissionless actors, not requiring collusion.

### Recommendation
In `onGetResponse`, before calling `_withdraw`, re-check `_filled[body.commitment] == address(0)` and re-derive/clamp the released amounts from the live `_orders[commitment][token]` mapping rather than trusting the static `context` snapshotted at `_cancelFromSource` dispatch time. Additionally, reject GET responses whose proof height predates the most recent state update that could have finalized the order, or require the GET's queried height to be re-validated as monotonic/not-stale relative to any interleaving fill.

### Proof of Concept
1. User places a cross-chain order; solver has not yet filled it.
2. After `order.deadline`, user calls `cancelOrder` → `_cancelFromSource`, dispatching a `DispatchGet` (`timeout: 0`) embedding `order.inputs` in `context`; escrow is still present so the `UnknownOrder` pre-check passes.
3. Before the GET is answered, a solver calls `fillOrder` on the destination, which dispatches `RedeemEscrow` back to source; source `onAccept` calls `_withdraw(body, false, true)`, setting `_filled[commitment] = solver` and paying out escrow to the solver.
4. A relayer submits a storage proof for `onGetResponse` taken at (or replayed against) a height prior to the destination fill, showing `_filled` empty on the destination at that height — `Filled()` check at line 320 is satisfied.
5. `onGetResponse` calls `_withdraw(body, true, true)` again using the stale `order.inputs` amounts from `context`; if any escrow slot for the commitment still holds a nonzero (but reduced) balance due to non-atomic per-token accounting, the second release proceeds and refunds the user out of funds that were already paid to the solver in step 3, producing double-settlement / loss of protocol/solver funds.     function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));

    /**
     * @dev Handles the response to a Hyperbridge GET request dispatched during
     * `_cancelFromSource`. Verifies that the `_filled` storage slot on the destination
     * chain is empty (meaning the order was never filled), then refunds the escrowed
     * tokens to the original user. Reverts with `Filled` if the slot is non-empty.
     *
     * @param incoming The incoming GET response from Hyperbridge containing the storage proof.
     */
    function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
        if (incoming.response.values[0].value.length != 0) revert Filled();

        WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
        _withdraw(body, true, true);
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
