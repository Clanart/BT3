## Title
`API.fetchPushControl` fails open to "fully permitted" on any network/API error, causing Desktop to silently hide branch-protection warnings - (`File: app/src/lib/api.ts`)

### Summary
This mirrors the root cause in the Mantra report: a value meant to gate a risky operation (`belief_price` for slippage; here, branch-protection status for commit/push) is silently replaced with a "no protection" default whenever the real check can't be evaluated, rather than failing closed. In Desktop, `fetchPushControl` returns a hard-coded "fully permissive" `IAPIPushControl` object whenever the `push_control` API call throws for *any* reason, and this object is used to decide whether to warn the user that the current branch is protected before they commit/push.

### Finding Description
`API.fetchPushControl` is documented to assume full access if the request fails: [1](#0-0) 

Concretely, on any thrown error (network failure, a proxy/MITM tampering with the response, a compromised or misbehaving GitHub Enterprise Server, rate limiting, TLS interception, etc.) it returns:
```
{
  pattern: null,
  required_signatures: false,
  required_status_checks: [],
  required_approving_review_count: 0,
  required_linear_history: false,
  allow_actor: true,
  allow_deletions: true,
  allow_force_pushes: true,
}
```
This result flows directly into `isBranchPushable`, which treats the branch as unprotected whenever `allow_actor !== false` and there are no required checks/reviews - exactly the values baked into the fail-open default: [2](#0-1) 

`refreshBranchProtectionState` calls `fetchPushControl` and stores the result as `currentBranchProtected` in the repository state, which is then used to decide whether the UI shows a "this is a protected branch" warning and whether repo-rules (signed commits required, review required, etc.) are surfaced: [3](#0-2) 

The commit UI consumes this flag (`showBranchProtected`) to decide whether to show the protected-branch warning at all: [4](#0-3) 

Just like `belief_price` silently becoming `None` broke the intended slippage-protection invariant without the user's knowledge, here the intended invariant "warn the user before they commit/force-push to a branch that is actually protected" is silently broken whenever the network path to GitHub is interfered with. An attacker who can influence the response to the `push_control` request (a malicious/compromised proxy sitting on the connection, a compromised GHES instance, or simply forcing the request to fail/return malformed JSON) can force this fail-open path deterministically, since `ghRequest`/`parsedResponse` will throw on any non-2xx or malformed body.

### Impact Explanation
When the fail-open path is triggered, GitHub Desktop:
- Suppresses the "branch is protected" warning entirely, and
- Reports `required_signatures: false`, `required_approving_review_count: 0`, `allow_force_pushes: true`, so repo-rule-derived warnings (commit signing required, force-push confirmation implications) are also suppressed.

This gives the user false confidence that an operation (e.g., a force-push during a rebase/amend/reorder) is safe on a branch that is actually protected, increasing the chance that they proceed with a destructive operation without the safety prompt they would normally receive. The actual git push is still ultimately subject to server-side enforcement by GitHub, so this is a UI/decision-support bypass rather than a direct server-side protection bypass; the practical harm is inducing the user into believing a risky rewrite/force-push is safe, and skipping the explicit warning flow designed to stop that.

### Likelihood Explanation
Any condition that makes the `push_control` (or `fetchAllRepoRulesets`/`fetchRepoRulesForBranch`) request throw triggers this — including a network intermediary or compromised/rogue GitHub Enterprise Server tampering with responses, since this is a routine authenticated GET fired every time the checked-out branch changes (`refreshBranchProtectionState`, invoked from `onGitStoreUpdated`). No special user action is required beyond normal use over a network path an attacker can influence.

### Recommendation
Do not fail open to "fully permitted" defaults when `fetchPushControl` cannot get a reliable answer. Instead:
- Distinguish "no protection configured" from "protection status unknown," and surface an explicit "couldn't verify branch protection" state in the UI rather than silently assuming no protection.
- Avoid defaulting `allow_force_pushes`/`required_signatures`/`required_approving_review_count` to permissive values on error; treat unknown as "protected" (fail closed) for warning purposes, since the cost of an extra warning is far lower than silently skipping one.

### Proof of Concept
1. Attacker positions as (or compromises) a network intermediary/proxy or a GHES instance the victim's Desktop client talks to.
2. Victim has a repository checked out to a branch that is actually protected (e.g., requires signed commits / linear history / reviews).
3. Attacker causes the `GET repos/:owner/:repo/branches/:branch/push_control` request to fail (drop connection, return 5xx, or return malformed JSON) — `ghRequest`/`parsedResponse` throws.
4. `fetchPushControl` catches the error and returns the hard-coded permissive object (`app/src/lib/api.ts:1657-1666`).
5. `isBranchPushable` (`app/src/lib/helpers/push-control.ts:23-49`) evaluates this object as "pushable"/unprotected.
6. `refreshBranchProtectionState` sets `currentBranchProtected = false` and an empty `RepoRulesInfo` (`app/src/lib/stores/app-store.ts:1521-1524`).
7. The Commit UI does not show the protected-branch or repo-rules warnings (`app/src/ui/changes/commit-message.tsx:1334-1440`), and the user proceeds to commit/force-push believing there are no restrictions, without the safety prompt Desktop normally provides.

  /**
   * Get branch protection info to determine if a user can push to a given branch.
   *
   * Note: if request fails, the default returned value assumes full access for the user
   */
  public async fetchPushControl(
    owner: string,
    name: string,
    branch: string
  ): Promise<IAPIPushControl> {
    const path = `repos/${owner}/${name}/branches/${encodeURIComponent(
      branch
    )}/push_control`

    const headers: any = {
      Accept: 'application/vnd.github.phandalin-preview',
    }

    try {
      const response = await this.ghRequest('GET', path, {
        customHeaders: headers,
      })
      return await parsedResponse<IAPIPushControl>(response)
    } catch (err) {
      log.info(
        `[fetchPushControl] unable to check if branch is potentially pushable`,
        err
      )
      return {
        pattern: null,
        required_signatures: false,
        required_status_checks: [],
        required_approving_review_count: 0,
        required_linear_history: false,
        allow_actor: true,
        allow_deletions: true,
        allow_force_pushes: true,
      }
    }
```

export function isBranchPushable(pushControl: IAPIPushControl) {
  const {
    allow_actor,
    required_status_checks,
    required_approving_review_count,
  } = pushControl

  // See https://github.com/desktop/desktop/issues/9054#issuecomment-582768322
  // We'll guard against this being undefined until we can determine the
  // root cause and fix that.
  const requiredStatusCheckCount = Array.isArray(required_status_checks)
    ? required_status_checks.length
    : 0

  // If user is admin and branch is not admin-enforced,
  // required status checks and reviews get zeroed out in API response (no merge requirements).
  // If user is admin and branch is admin-enforced,
  // required status checks and reviews do NOT get zeroed out in API response.
  // If user is allowed to push based on `Restrict who can push` setting, they must still
  // respect the merge requirements, and can't push if checks or reviews are required for merging
  const noMergeRequirements =
    requiredStatusCheckCount === 0 && required_approving_review_count === 0

  // We check for !== false so that if a future version of the API decides to
  // remove or rename that property we'll revert to assuming that the user
  // _does_ have access rather than assuming that they _don't_.
  return allow_actor !== false && noMergeRequirements
```
