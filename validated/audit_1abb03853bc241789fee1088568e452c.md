### Title
OP_RETURN data output excluded from transaction weight/vbytes accounting, allowing non-standard oversized transactions and underpaid fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight and virtual size via `calculate_weight_vbytes`, which is passed only `payments` and the optional `change` script — never the OP_RETURN output carrying up to 80 bytes of attacker-supplied `data`. The `TooLargeTransaction` check against `bitcoin::policy::MAX_STANDARD_TX_WEIGHT` and the fee calculation therefore omit the data output entirely, mirroring the dnsmasq CVE class: a protocol-relevant maximum is enforced against an under-measured value, so the produced artifact can exceed the standard bound.

### Finding Description
At `send.rs:194-202`, the OP_RETURN output is pushed onto `tx_outs` before the weight calculation. However, `calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204 builds a template transaction whose `output` vector is constructed only from `payments` — the OP_RETURN output is never included. Similarly, when change is added at lines 224-235, `weight_with_change`/`vbytes_with_change` still exclude the OP_RETURN output. The enforcement at line 241 (`weight > MAX_STANDARD_TX_WEIGHT`) and the fee at lines 206/227 (`fee_per_vbyte * vbytes`) are thus computed on a smaller transaction than the one actually signed and broadcast. An ~80-byte OP_RETURN output adds roughly 90+ bytes (~360+ weight units) that are completely unaccounted for. [1](#0-0) [2](#0-1) 

### Impact Explanation
Two concrete impacts from public input (the `data` field, which is reachable by anyone able to request a payment/instruction carrying data):

1. The signed transaction can exceed `MAX_STANDARD_TX_WEIGHT` (400,000 WU) while passing the check at line 241. Default-policy Bitcoin nodes will refuse to relay it — the threshold signatures still complete (`TransactionSignMachine::sign` / `complete` succeed), so the protocol believes a valid transaction was produced, but the funds it moves are effectively unbroadcastable/stuck. This is "funds moved by a transaction that is not spendable/relayable."
2. The fee is underpaid relative to the caller's specified `fee_per_vbyte`, since `vbytes` omits the data output. In boundary cases the effective fee rate can fall below the intended rate and below relay minima relative to actual size.

### Likelihood Explanation
The gap is only ~360-400 WU, so the oversized-transaction case requires the base transaction to sit within ~400 WU of the 400,000 WU limit — feasible near `MAX_INPUTS`/`MAX_OUTPUTS` boundaries used by the processor (`processor/src/networks/bitcoin.rs` allows up to 520 inputs and outputs). The underpaid-fee consequence triggers on every transaction carrying `data`, regardless of size. Any unprivileged party who can get `data` included in a payment request reaches this path; no validator collusion or leaked key material is needed.

### Recommendation
Include the OP_RETURN output in the template transaction used by `calculate_weight_vbytes`. The cleanest fix is to compute weight/vbytes from the fully assembled `tx_outs` vector (payments + OP_RETURN + change) rather than reconstructing outputs from `payments` inside `calculate_weight_vbytes`, so future output types cannot be silently dropped from the accounting.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Construct a SignableTransaction whose computed weight is just under
// MAX_STANDARD_TX_WEIGHT, then attach up to 80 bytes of `data`.
let data = vec![0xaa; 80];
let stx = SignableTransaction::new(
  inputs,            // enough inputs to push weight near 400_000 WU
  &payments,
  Some(change_script),
  Some(data),        // OP_RETURN output added to tx_outs
  fee_per_vbyte,
).unwrap();
// `weight` was computed on a tx WITHOUT the OP_RETURN output, so the
// line-241 check passed even though stx.transaction().weight() >
// MAX_STANDARD_TX_WEIGHT. Default-policy nodes reject it as non-standard.
assert!(
  u64::from(stx.transaction().weight().to_wu()) >
    u64::from(bitcoin::policy::MAX_STANDARD_TX_WEIGHT)
);
// The actual signed transaction after TransactionMachine::complete()
// will not relay; funds remain locked in the spent prevouts' successors.
```
