### Title
`WombatStaking.updatePoolHelper()` pool-helper rotation permanently locks user funds staked via the old helper - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.updatePoolHelper()` lets the owner change `pools[_lpAddress].helper` (and `rewarder`, `pid`, `depositToken`, `depositTarget`) for an already-registered pool while keeping the same `receiptToken`/`stakingToken` [1](#0-0) . All state-changing entry points that a user's already-deployed `WombatPoolHelper` calls (`withdraw`, `burnReceiptToken`) are gated by a modifier that checks `msg.sender == pools[_lpAddress].helper` [2](#0-1) . Once the owner rotates the helper, the *old* `WombatPoolHelper` instance — the one users already interacted with and whose address is baked into `stakingToken`'s staking position in `MasterMagpie` — is silently orphaned: any call it makes into `WombatStaking.withdraw()`/`burnReceiptToken()` on behalf of its users now reverts with `OnlyPoolHelper()`, because `msg.sender` (old helper) no longer matches the updated `poolInfo.helper`. This mirrors the reported bug class: an address stored in a registry mapping is upgraded, and the stale/previous "privileged" contract instance is treated as an unauthorized caller by the accounting logic, trapping the funds and positions that were opened through it.

### Finding Description
`WombatPoolHelper` is an immutable, non-upgradable contract per pool — `lpToken`, `wombatStaking`, `masterMagpie`, `rewarder`, `pid`, `stakingToken` are all `immutable` and fixed at deployment [3](#0-2) . Users deposit through this specific helper instance, which stakes their `stakingToken` (receipt token) into `MasterMagpie` on their behalf [4](#0-3) , and later withdraw through the *same* helper instance, which calls back into `WombatStaking.withdraw()` and `WombatStaking.burnReceiptToken()` [5](#0-4) .

`WombatStaking.withdraw()` and `burnReceiptToken()` are protected by `_onlyPoolHelper`/`_onlyActivePoolHelper`, which read the *current* `pools[_lpToken].helper` from storage: [2](#0-1) 

The owner can update this mapping at any time via `updatePoolHelper()`, replacing `poolInfo.helper` with a brand-new helper contract while the pool's `receiptToken` (the token already staked by existing users) is left unchanged and is propagated to `MasterMagpie.set()`: [1](#0-0) 

After this call, the *old* `WombatPoolHelper` contract's `wombatStaking` immutable still points at `WombatStaking`, and its `lpToken` immutable is unchanged, so any user who calls `withdraw()` on the old (now orphaned) helper will have that helper call `IWombatStaking(wombatStaking).withdraw(lpToken, ...)`, which will now revert because `msg.sender` (the old helper address) no longer equals the updated `poolInfo.helper` [6](#0-5) . There is no migration path exposed to move a user's already-staked `stakingToken` position from association with the old helper to the new one, and no function allows the old helper (or the user directly) to reach `withdraw`/`burnReceiptToken` once it is no longer the registered `helper`.

### Impact Explanation
Because `WombatStaking` holds custody of the underlying deposit/LP tokens for all users of a pool, and the only sanctioned withdrawal path is gated to the single address currently recorded as `pools[_lpAddress].helper`, rotating that address orphans every position opened through the prior helper. Users who deposited before the rotation have their principal (and until-then unclaimed WOM/MGP rewards routed through the old rewarder) become permanently unwithdrawable through the interface they used to deposit — a direct, permanent freezing of user funds, matching the "freezing of funds" bar for validity.

### Likelihood Explanation
`updatePoolHelper()` is a normal, documented maintenance function (`@notice update the pool information on wombat deposit and master magpie`) intended to be used during ordinary protocol operations (e.g., to fix a bug in a pool helper or migrate deposit targets), not an act of malicious governance. Any time it is invoked for a pool that already has depositors, all existing depositors' redemption path breaks. Given that this is a documented, expected operational lever (analogous to Union Finance's `MarketRegistry.setUToken` upgrade path) rather than an attack requiring a compromised or adversarial owner, the likelihood of accidental triggering during routine pool maintenance is significant.

### Recommendation
When rotating a pool's helper/rewarder in `updatePoolHelper()`, either (1) retain backward-compatible authorization for the previous helper address for a grace period sufficient for all users to withdraw, or (2) provide an explicit migration function that moves each user's staked balance from the old helper/rewarder association to the new one atomically, or (3) require the pool to be fully drained (`totalStaked() == 0`) before a helper/rewarder change is permitted for an already-active pool.

### Proof of Concept
1. Owner calls `WombatStaking.registerPool(...)`, deploying `HelperV1` for lp `L`; `pools[L].helper = HelperV1`.
2. User `A` calls `HelperV1.deposit(amount, minLiquidity)`, which calls `WombatStaking.deposit(L, ...)` and stakes the resulting `stakingToken` into `MasterMagpie` on `A`'s behalf [4](#0-3) .
3. Owner (routine maintenance) calls `WombatStaking.updatePoolHelper(L, pid, HelperV2, newRewarder, depositToken, depositTarget, allocPoint)`, setting `pools[L].helper = HelperV2` [7](#0-6) .
4. User `A` calls `HelperV1.withdraw(liquidity, minAmount)`. `HelperV1` calls `WombatStaking.withdraw(L, liquidity, minAmount, A)`. Since `msg.sender == HelperV1 != pools[L].helper (HelperV2)`, the `_onlyPoolHelper` modifier reverts with `OnlyPoolHelper()` [2](#0-1) [8](#0-7) .
5. `A` has no alternative contract path to withdraw the principal already staked through `HelperV1`; the funds remain locked in `WombatStaking`/`MasterMagpie` indefinitely.

    /// @param _liquidity the amount of liquidity to withdraw

        // we have to withdraw from wombat exchange to harvest reward to base rewarder
        IWombatStaking(wombatStaking).withdraw(
            lpToken,
            _liquidity,
            _minAmount,
            msg.sender

    }
