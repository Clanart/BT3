### Title
Unprivileged re-initialization of a "selfdestructed" native ERC20 token pair via `ConvertERC20` + permissionless `RegisterERC20` enables mint-authority hijack - (File: x/erc20/keeper/msg_server.go, x/erc20/keeper/proposals.go)

### Summary
`ConvertERC20` treats the *absence of a code hash* on the mapped ERC20 contract address as proof the underlying contract self-destructed, and unilaterally deletes the token pair (denom map, ERC20 map, allowances) as a side effect of an ordinary user-initiated conversion call. [1](#0-0) 
Deletion clears `IsERC20Registered`/`IsDenomRegistered`/bank `GetDenomMetaData`, which are exactly the "initialization" guards `registerERC20`/`CreateCoinMetadata` rely on to prevent double-registration. [2](#0-1) [3](#0-2) 
When `PermissionlessRegistration` is enabled (the default in several deployments/tests), any account can call `MsgRegisterERC20` without governance. [4](#0-3) 

### Finding Description
`registerERC20`/`CreateCoinMetadata` use `IsERC20Registered`, `IsDenomRegistered`, and bank `GetDenomMetaData(denom)` as the sole "already initialized" checks for a token pair keyed by contract address. [5](#0-4) [6](#0-5) 
This is analogous to Amun's `ERC20Facet`, where "initialized" is inferred from mutable `name`/`symbol` state that can be reset to empty. Here, "initialized" is inferred from erasable keeper state (`TokenPair`/`DenomMap`/`ERC20Map`/bank metadata) that gets wiped by `ConvertERC20` whenever `k.evmKeeper.GetAccountWithoutBalance(ctx, pair.GetERC20Contract())` returns nil or `!acc.HasCodeHash()`. [7](#0-6) 
`DeleteTokenPair` removes the token pair, ERC20 map, denom map, and any outstanding allowances in one shot. [8](#0-7) 

The condition triggering deletion (no code / no code hash at the contract address) is not exclusively "the contract self-destructed forever" — it can also occur transiently or be engineered by the external contract owner (native ERC20 token pairs are `OWNER_EXTERNAL`, i.e., arbitrary externally-deployed contracts the module does not control) via `SELFDESTRUCT`-then-`CREATE2` redeploy to the same address, or any operation that clears the account's code hash bookkeeping. Once the pair is deleted:
1. `IsERC20Registered`/`IsDenomRegistered` return false, and bank metadata for that denom is gone (since `DeleteTokenPair` does not explicitly restore/clean bank metadata, but `CreateCoinMetadata`'s check is against bank metadata "already registered" — if that's also cleared/absent, the guard is bypassed).
2. Any account (if permissionless registration is on) can call `MsgRegisterERC20` again for the same contract address, which passes `IsERC20Registered` (now false) and re-runs `CreateCoinMetadata`, minting fresh bank denom metadata and a brand-new `TokenPair` with a new/different owner/state.
3. Because ERC20↔coin conversion for native tokens is a straight `transfer`/mint of the *same* Cosmos coin denom (derived deterministically from the contract address via `types.CreateDenom`), any native coins/escrow balances tied to the old pair's denom become re-associated with whatever the redeployed (attacker-controlled) contract now reports as its ABI behavior. [9](#0-8) 

### Impact Explanation
If the contract at the token-pair address can be selfdestructed and redeployed (CREATE2) with attacker-chosen bytecode reporting arbitrary `balanceOf`/`transfer` results, the attacker can re-register it as a "fresh" token pair mapped to the *same* pre-existing Cosmos coin denom and escrow account. Subsequent `ConvertERC20`/`ConvertCoin` flows would mint/burn native coins based on the attacker's fabricated contract responses, resulting in unauthorized minting or duplication of spendable native coin balances — a critical accounting corruption matching the "unauthorized minting/duplication of spendable user value" impact category.

### Likelihood Explanation
This requires: (a) `PermissionlessRegistration=true` (governance-configurable, not guaranteed on all deployments) or the attacker being able to pass `validateAuthority`, and (b) an externally-owned (`OWNER_EXTERNAL`) ERC20 contract that can be selfdestructed and redeployed to the identical address (CREATE2), which is only possible for contracts specifically designed to allow this (Solidity's `SELFDESTRUCT` + deterministic redeploy is a known but non-trivial technique, and post-Dencun `SELFDESTRUCT` semantics limit some of this). I could not fully verify within available time whether `GetAccountWithoutBalance`/`HasCodeHash` can be made false through a means an ordinary user fully controls without contract-owner cooperation, nor whether `CreateCoinMetadata`'s bank-metadata guard is actually left cleared after `DeleteTokenPair` (I did not find explicit bank metadata cleanup in `DeleteTokenPair`, meaning `CreateCoinMetadata`'s "denom metadata already registered" check would likely still block re-registration in the common case). This uncertainty significantly lowers confidence that the full exploit chain is reachable by an unprivileged actor without additional privileged cooperation from the token contract's deployer/owner.

### Recommendation
- Do not silently delete an ERC20 token pair based solely on `!acc.HasCodeHash()`; require this to be a governance/authority-gated cleanup action, or verify irrecoverable state (e.g., check `SelfDestructed` marker or an explicit deprecation flag) rather than inferring "the contract died forever" from a transient absence of code hash.
- Ensure `DeleteTokenPair` also purges bank denom metadata for the pair's denom, or (safer) ensure `registerERC20`/`CreateCoinMetadata` re-registration paths explicitly reject re-registering a denom/contract-address that previously had an active pair with outstanding native coin supply/escrow balance greater than zero.
- Treat "denom has non-zero supply/escrow" as an additional invariant check before allowing any re-registration of that denom to a new ERC20 contract address.

### Proof of Concept
Could not be fully constructed/verified in this pass. The theoretical PoC sketch is: deploy an `OWNER_EXTERNAL` ERC20 at address `X` via `CREATE2`, register it with `MsgRegisterERC20`, convert some coin to ERC20 and back to accumulate escrowed native coin supply under `pair.Denom`, then `SELFDESTRUCT` the contract at `X` and redeploy attacker-controlled bytecode to the same address via `CREATE2`, call `ConvertERC20` to trigger the `DeleteTokenPair` branch, then call `MsgRegisterERC20` again (assuming `PermissionlessRegistration=true`) to re-map `X` to the same denom, and finally call `ConvertCoin`/`ConvertERC20` to mint/duplicate native coin balances via the attacker's fabricated contract logic. This requires validating the actual reachability of `!acc.HasCodeHash()` under a genuine SELFDESTRUCT+redeploy scenario and confirming the bank-metadata guard state after deletion — both unverified here due to tool-call limits.

func (k Keeper) registerERC20(

	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
