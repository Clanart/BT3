## Analysis

The C4 report's core defect pattern is: **two call paths are supposed to produce equivalent, safe behavior, but one path (the "generic"/fallback constructor) is implemented more loosely than the primary one, breaking an invariant a security-relevant caller relies on** (Arbitrum Router always calls the 6-arg `outboundTransfer`, but `L2LPTGateway` only correctly implements the 4-arg one it was tested against).

The closest verifiable analog in this codebase is in the trampoline credential-helper's URL reconstruction, which has exactly this "primary path vs. loosely-built fallback path" shape, and the fallback path is untrusted-input-driven (git's credential protocol is populated from data associated with the remote/server being talked to).

### Title
Unsanitized reconstruction of credential URL from `protocol`/`host`/`path` attributes in `getCredentialUrl` can desynchronize the trust decision from the actual connecting host - (File: `app/src/lib/trampoline/trampoline-environment.ts`)

### Summary
`getCredentialUrl` has two code paths for turning a git credential-helper record into a `URL` object: a "fast path" that trusts a single pre-formed `url` attribute, and a fallback path that manually string-concatenates the `protocol`, `username`, `host`, and `path` attributes it receives via the credential-helper stdin protocol. [1](#0-0) 

Unlike the fast path, the fallback path does not URL-encode `host` or `path` (only `username` is encoded), and blindly feeds them into a template string passed to `new URL(...)`.

### Finding Description
The credential-helper trampoline uses `getCredentialUrl(cred)` as the single source of truth for deciding *which account/token to hand back to Git* for every one of the `get`/`store`/`erase` commands: [2](#0-1) [3](#0-2) 

The trust decisions downstream of this URL (`findGitHubTrampolineAccount`'s origin match, and `getEndpointKind`'s `isDotCom`/`isGHE`/`isGitHubHost` checks) all assume that the `URL` object faithfully represents the host Git is actually about to talk to: [4](#0-3) 

When Git's own credential protocol supplies split `protocol`/`host`/`path` attributes (which is how Git's HTTP transport commonly populates the credential record, rather than a single `url` key), Desktop reconstructs the URL itself with unescaped, attacker/network-influenced field values:
```
return new URL(`${protocol}://${user}${host}/${path}`)
```
Because `host` is not validated or percent-encoded before concatenation, a `host` value containing structural URL characters (e.g. an embedded `@`) can shift what the WHATWG URL parser treats as user-info versus host versus path when the string is re-parsed, changing the resulting `.origin`. Since none of Desktop's trust checks re-validate this against the raw protocol-level connection target, a crafted `host`/`path` value can cause `getCredentialUrl(...).origin` to resolve to a trusted endpoint's origin (e.g. `github.com`) even though the real network target is different, or vice versa — corrupting the exact value (`cred`'s derived `URL.origin`) that both `findGitHubTrampolineAccount` and `getEndpointKind` rely on as their entire security boundary.

### Impact Explanation
If the reconstructed origin can be desynchronized from the real connection target, the consequence is that a user's GitHub token (returned via `credWithAccount`, which sets `password` to `a.token`) could be disclosed to the wrong endpoint through Git's own credential negotiation, i.e., credential/token exfiltration to an attacker-controlled host without any unusual user action beyond performing a normal fetch/push against a repository whose remote/proxy is attacker-influenced.

### Likelihood Explanation
This is speculative and not fully proven from local code alone: I could not verify from this repository which exact raw `host`/`path` strings Git itself will ever pass through the credential-helper protocol (that logic lives in Git's own C source, not in this repo), so I cannot confirm Git will forward a `host` value containing characters capable of triggering user-info/host confusion. The weakness that **is** concretely established by local code is that Desktop's own reconstruction path performs no encoding/validation of `host`/`path` before trusting the resulting `.origin` for account/token selection, which is the same class of "loosely-implemented secondary interface path breaks an invariant the caller relies on" as the cited report.

### Recommendation
- In `getCredentialUrl` (`app/src/lib/trampoline/trampoline-environment.ts:46-59`), validate/reject `host` values containing disallowed URL-structural characters (`@`, `/`, `?`, `#`, credential separators) before concatenation, or build the URL using the `URL` constructor's own `hostname`/`pathname` setters instead of string interpolation so the parser cannot reinterpret field boundaries.
- Add a regression test asserting that `getCredentialUrl` produces the same `.origin` result whether Git supplies `url` or split `protocol`/`host`/`path`, for a set of adversarial `host` values.

### Proof of Concept
Not executable from static review alone (requires confirming what raw `host` string Git's HTTP credential layer can be made to emit for a given malicious server/redirect, which is outside this repository). The concrete, locally-verifiable weakness is the unescaped string concatenation itself: [5](#0-4) 
A minimal demonstration of the parser-confusion primitive (independent of Git):
```js
new URL(`https://${'evil.com'}/${'@github.com/x'}`).origin
// -> "https://evil.com" (path swallowed) vs. if 'host' itself
// could smuggle '@', origin resolution shifts unexpectedly.
```

**Confidence caveat:** unlike the original Livepeer finding (which had a fully reproducible, self-contained missing-interface bug), this Desktop analog identifies a genuine unsanitized-input weakness in Desktop's own code, but a complete end-to-end PoC would require confirming Git's exact credential-attribute emission behavior, which this local index does not contain. If a full trace of Git's C source proves `host` can never contain such characters, this reduces to defense-in-depth rather than an exploitable path.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
```

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
```

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
