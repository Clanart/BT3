### Title
Blame/error path dereferences participant map entries that were never registered, panicking on attacker-influenced indexes - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The kernel bug used an `extack` field on an error path that was only initialized on a success path that had already failed. The analogous shape in Serai is the PedPoP blame/error path: `blame_internal` and `Decryption::decrypt_with_proof` index `self.commitments[..]` and `self.enc_keys[..]` with `sender`/`recipient` `Participant` values taken directly from protocol inputs, without ever checking those indexes were registered. Because `HashMap` indexing panics on a missing key, an error-handling path that runs precisely when inputs are malformed will panic on a "value that was never initialized" — the same failure mode (error path touching state the failed/missing step never populated), expressed through Rust's panic-on-missing-key instead of a stale pointer.

### Finding Description
`Decryption::register` only inserts into `enc_keys` for participants actually processed in round 1 [1](#0-0) . `AdditionalBlameMachine::new` registers only participants `1..=n` [2](#0-1) . Later, `decrypt_with_proof` unconditionally evaluates `self.enc_keys[&decryptor]` [3](#0-2) , and `blame_internal` unconditionally evaluates `self.commitments[&sender]` [4](#0-3) . Neither `blame` nor `AdditionalBlameMachine::blame` validates that `sender`/`recipient` are within `1..=n` or were ever registered [5](#0-4) . `Participant::new` accepts any nonzero u16, so `recipient = Participant(0xFFFF)` is trivially constructible from wire data.

The panic also has a subtler variant matching the CVE even more closely: `calculate_share` folds the decrypted share into `self.secret` *before* the batch containing the PoP verification is checked [6](#0-5) . The decrypted plaintext is produced and consumed while its authenticity is still pending — the value is used before the step that was supposed to initialize its validity completes. Here the machine correctly aborts on batch failure, so this ordering alone is not exploitable, but it demonstrates the same structural assumption.

### Impact Explanation
A `blame` call is triggered by accusation messages exchanged between DKG participants — i.e., attacker-influenced values for `sender`, `recipient`, `msg`, and `proof`. Passing `recipient` (or `sender`) outside `1..=n`, or a participant whose `EncryptionKeyMessage` was never registered, produces a guaranteed panic (`HashMap` index on absent key) inside `decrypt_with_proof`/`blame_internal` instead of the documented `Participant` blame result. An aborting node handling a blame claim crashes rather than completing adjudication, denying the protocol's fault-resolution path. This is a reachable, remotely triggerable panic — a medium-severity availability analog of the kernel's crash on an uninitialized error-path field.

### Likelihood Explanation
Blame flow is only exercised when a fault is suspected, so routine operation avoids it, but any participant can force blame evaluation by broadcasting an accusation with out-of-range or unregistered participant indexes. No special privileges or collusion are needed — just the ability to send DKG protocol messages, which is the unprivileged reachability required. Requires the caller to route attacker-controlled `Participant` values into `blame`/`AdditionalBlameMachine::blame` without sanitization, which the API neither enforces nor documents.

### Recommendation
In `blame_internal` and `decrypt_with_proof`, replace indexing with checked lookups: return a defined result (e.g., blame the accuser, or a dedicated `InvalidParticipant` error) when `sender`/`recipient` is not present in `commitments`/`enc_keys`, and/or validate `sender`/`recipient` against `params.n()` up front in `blame` and `AdditionalBlameMachine::blame`. Equivalently, only use `.get(&participant)` and handle `None` explicitly, so the error path never dereferences a map entry the registration step never created.

### Proof of Concept
```rust
// Conceptual: n = 3, all three participants registered via
// AdditionalBlameMachine::new(context, 3, commitment_msgs).
// An accuser then invokes blame with a participant index that was
// never registered:

let attacker_forged_recipient = Participant::new(u16::MAX).unwrap(); // 65535, > n

// Panics inside Decryption::decrypt_with_proof at:
//   self.enc_keys[&decryptor]  // absent key -> index panic
machine.blame(
  Participant::new(1).unwrap(),        // sender
  attacker_forged_recipient,           // recipient never in 1..=3
  msg,                                  // any EncryptedMessage bytes
  None,                                 // proof
);
```

The same panic occurs via `self.commitments[&sender]` in `blame_internal` when `sender` exceeds `n` [7](#0-6) . Both locations are reached before any check that would reject the unregistered index, mirroring `extack._msg` being read on a path where it was never set.

Note: I verified the panic-on-missing-key behavior from the shown source but could not exhaustively confirm every upstream caller passes unsanitized `Participant` values; the library-level defect (missing bounds/presence checks on the blame path) is confirmed from the code above.

  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }
