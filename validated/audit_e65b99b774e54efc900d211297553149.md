### Title
Unbounded point-vector allocation in `SchnorrAggregate::read` enables remote OOM denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report describes a DoS where a malformed length field (`zero-length TCP option`) drives an unbounded allocation/parse loop in a decoder. The direct Serai analog is `SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs`, which reads an attacker-controlled 32-bit count and then loops that many times, pushing decoded points into a `Vec` with no upper bound, no byte budget, and no relationship to the actual input size.

### Finding Description [1](#0-0) 

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;

  #[allow(non_snake_case)]
  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }

  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

The `len` field is a raw `u32` taken verbatim from the wire, so the loop bound can be up to ~4.29 billion iterations. The function takes a generic `R: Read` — nothing requires the reader to be a fixed, already-buffered slice. If the reader is a live stream (a network socket, a decompression stream, or any `Read` adapter fed by a remote peer), the attacker simply keeps producing valid point encodings and `Rs` grows without limit. Each pushed element is a full decompressed group element `C::G` (far larger than its serialized form — e.g., a Ristretto point in projective representation is ~124+ bytes plus `Vec` overhead), so ~4 billion iterations means tens-to-hundreds of GB of heap allocation, guaranteeing an out-of-memory abort long before `read_exact` ever fails.

This is structurally identical to the Nmap bug: a protocol element's declared count/length is trusted as the loop bound, and allocation proceeds per-iteration against a source that only terminates when the *sender* stops sending. Compare with `Block::read` in `coordinator/tributary/src/block.rs:88-95` which does `Vec::with_capacity(txs)` on an unchecked `u32` (immediate pre-allocation OOM — out of scope but shows the same pattern class), and with `networks/ethereum/src/machine.rs:51-60` where Serai's own developers explicitly documented and mitigated this exact bug class ("A valid DoS would be to claim a 4 GB data is present for only 4 bytes"), confirming the pattern was recognized as a real risk and was not applied here.

### Impact Explanation
An unprivileged remote party who can get untrusted bytes fed to `SchnorrAggregate::read` — the aggregate signature format is intended for on-chain/public submission and verification — can crash any node/process that deserializes it from a streaming source, via deterministic OOM. Even against a buffered `&[u8]` reader there is a weaker effect: `u32::MAX` iterations of `read_exact` failures is CPU-burning, but the dominant impact is the unbounded `Rs` growth against a live reader. This maps to the report's `VA:H` (availability high) with no confidentiality/integrity impact.

### Likelihood Explanation
Reachability requires only that an attacker deliver a byte stream beginning with `\xff\xff\xff\xff` to a deserialization path. `SchnorrAggregate` is a public network-facing type (its `read`/`write`/`serialize` are all `pub`), and `Read`-generic APIs in Serai are routinely called on socket-backed readers elsewhere (e.g., `coordinator/src/p2p.rs` reads untrusted libp2p payloads into `io::Read` consumers). No authentication, no valid signature, and no threshold of colluding parties is needed — the crash happens during parsing, before any verification at `SchnorrAggregate::verify` (line 127) is reached.

### Recommendation
Enforce a semantic bound before the loop: either (a) cap `len` at a protocol maximum (e.g., `MAX_SIGNERS` / `u16::MAX as usize`, since aggregate signer sets are inherently small), erroring like `"more signatures in aggregate than allowed"`, matching the style used for `commitments_len`/`TRANSACTION_SIZE_LIMIT` checks in `coordinator/src/tributary/transaction.rs:279-290`; or (b) read incrementally and stop at first `read_exact` failure without pre-committed loop count — at minimum never trust a `u32` count as an iteration bound over a streaming `Read`. Auditing the sibling readers (`ThresholdKeys::read` uses `u16` counts, bounded at ~65k — tolerable) confirms `SchnorrAggregate::read` is the only in-scope `u32`-bounded read-loop.

### Proof of Concept
Conceptual: instantiate `SchnorrAggregate::<Ristretto>::read` over a `Read` impl that yields valid 32-byte canonical point encodings indefinitely (e.g., a repeating generator encoding), with a 4-byte prefix `0xFFFFFFFF`. Memory usage grows monotonically (~136 bytes/iteration minimum for `Vec<C::G>` elements plus Vec growth) until the allocator aborts. With `Ristretto` (32-byte encoding), the input bandwidth-to-heap amplification is ~4x; the attacker needs to stream only ~137 GB of trivially repeatable bytes — or, more practically, crash any memory-limited container after streaming a few hundred MB — a single unauthenticated connection suffices.
