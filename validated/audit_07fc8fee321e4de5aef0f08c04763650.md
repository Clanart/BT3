## Title
NFT royalty rounding-to-zero on offer settlement allows royalty avoidance via bundling/low-value trades - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

## Summary
The NFT royalty calculation used when constructing and settling offers performs integer (floor) division to compute the royalty owed to an NFT creator. When the effective per-asset amount is small relative to the royalty percentage — either because a single fungible amount is small, or because multiple royalty-enabled NFTs are bundled into one offer (dividing the requested/offered amount across them) — the computed royalty truncates to zero, letting the trade settle with no royalty paid at all. This mirrors the reported `Allo.fundPool` bug class: an amount is divided such that `amount * percentFee / denominator` (here `amount * percentage / MAX_ROYALTY_BASIS_POINTS`) floors to `0`, defeating the intended fee.

## Finding Description
`compute_royalty_amount` performs the core division: [1](#0-0) 

`amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` truncates to `0` whenever `abs(offered_amount) // royalty_split` multiplied by `percentage` is smaller than `10000` (`MAX_ROYALTY_BASIS_POINTS`). This is directly analogous to `feeAmount = (_amount * percentFee) / getFeeDenominator()` in the reported issue — both are floor-division fee formulas that can be forced to zero by shrinking the numerator (`offered_amount`) or increasing the divisor (`royalty_split`).

This function is invoked from `NFTWallet.make_nft1_offer` when building royalty payments for an offer: [2](#0-1) 

Critically, `royalty_split` (i.e. `request_side_royalty_split` / `offer_side_royalty_split`) is the *count of royalty-enabled NFTs bundled into the same offer*: [3](#0-2) 

An offer maker fully controls how many royalty NFTs to bundle into a single offer and what fungible amount to request/offer. By bundling more NFTs together (increasing `royalty_split`) or using a smaller fungible amount, the per-asset `amount // royalty_split` shrinks, and the subsequent `* percentage // MAX_ROYALTY_BASIS_POINTS` truncates to `0` — exactly the "split into smaller amount to avoid fee" pattern from the report, except here the "splitting" is expressed as dividing the settlement value across multiple bundled NFTs (or simply picking a low enough per-trade amount) rather than issuing multiple `fundPool` calls.

The same rounding also affects `trade_prices`, which are similarly divided by `offer_side_royalty_split` and then filtered for zero contribution without forcing the trade to fail or the amount to increase: [4](#0-3) [5](#0-4) 

## Impact Explanation
When royalty truncates to zero, the trade settles normally but the NFT creator/royalty address receives nothing, even though a royalty was intended and would apply for a non-bundled/larger trade of equivalent aggregate value. This is a loss of intended fee revenue to the royalty beneficiary, fully controllable by the offer-maker's choice of bundling and amount — matching the report's "Medium" impact class (avoiding a mandatory-fee mechanism by structuring amounts to hit integer-division truncation), rather than any protocol-consensus break.

## Likelihood Explanation
This is trivially and repeatably reachable by any wallet user constructing an offer via `make_nft1_offer` (offers/trades path, no privilege required). It requires no cooperation from a third party beyond a willing counterparty accepting the offer, and the rounding behavior is deterministic and directly test-covered (`test_small_amount_truncates_to_zero`, `test_zero_royalty` in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`), confirming the maintainers are aware truncation-to-zero is a reachable, unguarded outcome of this arithmetic. [6](#0-5) [7](#0-6) 

## Recommendation
Apply the same class of fix used for other rounding-sensitive fee computations in this codebase (e.g. `FeeRate.create()` rounding up with `math.ceil`) rather than silently truncating to zero: [8](#0-7) 

Specifically, either (a) round the royalty computation up (or use a minimum non-zero royalty) whenever `percentage > 0`, or (b) reject/require a minimum trade amount per bundled royalty-NFT so that `abs(offered_amount) // royalty_split * percentage` cannot floor to zero while `percentage > 0`.

## Proof of Concept
1. Create an NFT with a non-zero `royalty_percentage` (e.g. 100 basis points = 1%).
2. Construct an offer bundling that NFT with additional royalty-enabled NFTs (or simply requesting a low fungible amount) such that `abs(offered_amount) // royalty_split` is small enough that `compute_royalty_amount(offered_amount, royalty_split, percentage)` returns `0` — as directly demonstrated by:
`compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100) == uint64(0)` (see `test_small_amount_truncates_to_zero`).
3. Accept the offer through `make_nft1_offer` / `respond_to_offer`; the trade settles and the NFT transfers, but the royalty address receives `0` mojos despite `percentage > 0`.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
