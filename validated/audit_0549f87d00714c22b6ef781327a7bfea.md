### Title
Silent, unauthenticated rewrite of a repository's git remote URL from GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a local repository's `origin` remote URL to match `apiRepo.clone_url` — a value taken directly from a GitHub API response — without any user confirmation, whenever a loose heuristic ("protocol matches" + "remote still matches the last cached clone URL") is satisfied. [1](#0-0) 

### Finding Description
This mirrors the report's broken-invariant pattern: a value the rest of the pipeline implicitly trusts (the "balance" available for the low-level call in the Solidity report; here, the git remote URL the user configured) is silently mutated by an intermediate step before the operation that depends on it (pushing/fetching) executes.

`updateRemoteUrl` is invoked with a `GitHubRepository`/`IAPIRepository` pair, presumably during a repository refresh cycle that re-fetches metadata from the GitHub API:
- It reads the current remote URL from `gitStore.defaultRemote.url`.
- It compares protocols between the current remote and the API-provided `clone_url` using `URL.parse`.
- It checks whether the current remote still matches the previously cached `gitHubRepository.cloneURL` via `urlMatchesRemote`.
- If protocols match, the remote is unchanged from what Desktop last recorded, and the new API URL differs from the current remote, it calls `gitStore.setRemoteURL(...)` to silently rewrite the remote — no user prompt, no diff shown. [2](#0-1) 

The value that gets corrupted is the git `origin` remote URL — the destination for every subsequent `push`/`fetch`/`pull` the user performs in Desktop. The trust boundary being crossed is: **GitHub API responses are attacker-influenceable** (a compromised/malicious GitHub Enterprise server, a MITM'd API response, or a repository transferred to/renamed by an attacker-controlled account can all produce a crafted `clone_url`) but Desktop treats `apiRepo.clone_url` as authoritative enough to overwrite local git configuration without any user-visible confirmation.

Existing guards do not stop this path:
- The protocol-match check only prevents an `https` remote from being silently swapped to `ssh` (or vice versa); it does nothing to prevent swapping the **host/owner/repo** portion of the URL, which is exactly what matters for where credentials and code get sent.
- The "remote unchanged from cached clone URL" check is meant to respect manual user edits, but it does not protect first-time or already-synced repositories: if the cached `gitHubRepository.cloneURL` already equals the local remote (the common case), the check trivially passes and any new attacker-controlled `clone_url` from a subsequent API refresh is silently applied.
- There is no path/host allow-list, no user prompt, and no diffing shown to the user before `setRemoteURL` executes. [3](#0-2) 

### Impact Explanation
If an attacker can influence the `clone_url` returned by the GitHub API for a repository Desktop has cached (e.g. via a compromised/rogue GitHub Enterprise instance, a repository-rename/ownership-transfer race, or a MITM on the API channel), Desktop will silently repoint the user's `origin` remote to an attacker-controlled URL. From then on:
- Every `git push` the user performs sends their code (and potentially credentials via the credential-helper flow) to the attacker's server instead of the legitimate one.
- Every `git fetch`/`pull` retrieves attacker-controlled content into the user's working copy without any indication the remote changed.

This satisfies "silent corruption of what the user commits or pushes" and potential credential exfiltration via the redirected push destination, without requiring local/physical access, admin rights, or prior malware.

### Likelihood Explanation
Exploitation requires the attacker to control or spoof a GitHub API response for a repository the victim already has cloned in Desktop (e.g., operating a malicious GitHub Enterprise Server the org points Desktop at, or intercepting/manipulating API traffic). This is a plausible "attacker controls a GitHub API object" scenario per the valid-impact criteria, though it is not a fully unauthenticated, zero-interaction exploit against github.com itself — likelihood is moderate and depends on the deployment (GHE proxies/mirrors increase feasibility).

### Recommendation
- Never silently call `setRemoteURL` based on API-provided `clone_url` changes. Require explicit user confirmation (a dialog showing old vs. new remote URL) before rewriting `origin`.
- Strengthen the equality/consistency checks to compare full host + owner + repo, not just protocol, before considering an auto-update "safe."
- Add unit/integration tests that simulate a malicious `IAPIRepository.clone_url` (different host) to confirm the remote is not silently rewritten.

### Proof of Concept
1. Victim adds/clones a repository through Desktop, associated with a `GitHubRepository` whose `cloneURL` matches their `origin` remote.
2. Attacker controls (or MITMs) the GitHub API endpoint Desktop queries during a background repository refresh (e.g., a rogue GitHub Enterprise Server, or an API response manipulated in transit) and returns an `IAPIRepository` object with `clone_url` pointing to `https://attacker.example/victim/repo.git`.
3. Desktop's refresh flow calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`. Because the protocol (`https`) matches and the previously cached `gitHubRepository.cloneURL` still equals the existing remote, the function calls `gitStore.setRemoteURL('origin', 'https://attacker.example/victim/repo.git')` with no user prompt. [4](#0-3) 
4. The user's next `git push`/`fetch` silently targets the attacker's server.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
