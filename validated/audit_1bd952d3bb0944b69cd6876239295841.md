### Title
Crafted `ThresholdKeys` blob causes quadratic blow-up in `group_key` computation during deserialization - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes attacker-controlled `t`/`n` fields (both `u16`, up to 65535) and then calls `ThresholdKeys::new`, which computes `group_key` by evaluating `interpolation_factor` for every participant `1..=t`. `Interpolation::Lagrange::interpolation_factor` is O(len(included)), so the total work is O(t²) field operations — about 4.3 billion multiplications for `t = n = 65535` — triggered by a tiny input (roughly `2 + 2 + 2 + 1 + 32 + 65535 * point_size` bytes). This mirrors the XStream bug class: unmarshalling a small malformed object triggers disproportionate/crashing work.

### Finding Description
In `ThresholdKeys::read`, `t`, `n`, and `i` are read directly from the byte stream with no bound other than `u16` range and `t <= n`, `i <= n` enforced by `ThresholdParams::new` [1](#0-0) [2](#0-1) . `read` then delegates to `ThresholdKeys::new`, which sums `verification_shares[i] * interpolation_factor(i, t)` for all `i` in `1..=t` [3](#0-2) . For `Interpolation::Lagrange` (tag `1`), each factor loops over the full `included` list performing a multiply per element [4](#0-3) . With `t = 65535`, that is ~4.3e9 `C::F` multiplications plus a field inversion — a deserialization-time quadratic DoS on any code path that calls `ThresholdKeys::read` on untrusted bytes (e.g., receiving peers' serialized key material during reshare/recovery/`promote` flows). The same O(t²) term also makes `verification_shares` reading O(n) but dominated by the group-key computation.

### Impact Explanation
An unprivileged party that can cause a validator/node to deserialize attacker-supplied `ThresholdKeys` bytes (the exact entry point the audit rules whitelist) can pin a CPU core for an extended period with an input of only ~2 MB — far less for meaningful slowdowns (e.g., `t = 8192` already yields ~67 million field multiplications). If invoked in a consensus or signing path, repeated submissions stall the node or cause missed rounds — a remote denial of service analogous to the XStream crash, but via algorithmic complexity rather than a single panicking call.

### Likelihood Explanation
`ThresholdKeys::read` is a public API over `io::Read` intended for exchanging/loading key material; any protocol path that accepts serialized keys from another participant (recovery data, promoted key shares, coordinator-distributed key blobs) exposes this. No authentication or size cap is applied before the quadratic work is performed — the only check is `t <= n <= 65535`.

### Recommendation
Cap `n`/`t` at a sane protocol maximum (e.g., a few hundred) inside `ThresholdParams::new` or `ThresholdKeys::read` before any interpolation work, or compute `group_key` lazily/streamed. Alternatively, bound deserialization by expected `n` known from context rather than trusting the blob's own header.

### Proof of Concept
Serialize a `ThresholdKeys` blob for any in-scope `Ciphersuite` with valid `C::ID`, then `t = 0xFFFF`, `n = 0xFFFF`, `i = 1`, interpolation byte `1` (Lagrange), a 32-byte secret share, and `65535` valid `C::G` encodings (identity is acceptable if `read_G` admits it, otherwise repeat one valid encoding). Feeding this to `ThresholdKeys::<C>::read` reaches `ThresholdKeys::new`, which performs `sum_{i=1}^{65535} interpolation_factor(i, [1..=65535])` — each factor doing 65534 field multiplications — totaling ~4.3 billion `C::F` multiplications before `read` returns.
