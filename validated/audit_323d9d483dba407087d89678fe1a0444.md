## Title
Concurrency guard for network Git operations can be bypassed by `_fetchRefspec`, allowing an attacker-controlled fork remote to run a Git process concurrently with a user-initiated push/pull/fetch - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The external report's broken invariant is: a security-relevant guard is checked/enforced globally (a single shared "in-progress" flag), but a second, less-visible code path can be invoked in parallel that never checks the guard, letting an attacker-influenced action interleave with the protected operation and undermine the guarantee the guard was meant to provide. In GitHub Desktop, the same pattern occurs with `withPushPullFetch`, the mutex meant to serialize all push/pull/fetch network operations on a given repository. `_fetchRefspec` — the code path used when a user is viewing a pull request from a fork (an attacker-controlled remote) — intentionally does not go through `withPushPullFetch`, and its own docstring says so.

### Finding Description
`withPushPullFetch` in `app-store.ts` is the single mutex Desktop uses to prevent concurrent network Git commands from running against the same working copy: [1](#0-0) 

Every normal fetch/pull/push path (`performFetch`, `performPull`, `performPush`) is wrapped in this guard. However, `_fetchRefspec` explicitly opts out, as documented in its own comment: [2](#0-1) 

`_fetchRefspec` calls `gitStore.fetchRefspec(refspec)`, which iterates over every configured remote (including any attacker-added fork remote from `_findPullRequestBranch`) and runs `git fetch <remote> <refspec>` for each one: [3](#0-2) [4](#0-3) 

Because this path skips the `isPushPullFetchInProgress` check, a `git fetch` initiated against a fork remote (whose content, refs, and object graph are entirely attacker-controlled since it is the head repository of a PR the attacker opened) can execute concurrently with a user-initiated `git push`/`git pull`/`git fetch` on the same repository working directory and `.git` directory. Both processes race on the same on-disk repository (packed-refs, loose refs, `FETCH_HEAD`, index, `.git/objects`), which is the exact TOCTOU/concurrency hazard `withPushPullFetch` exists to prevent for every other Git network path.

### Impact Explanation
Git does have its own internal locking for individual ref updates and the object database, so this is not necessarily an immediate corruption in every case — but the codebase's own design intent (a single global mutex for *all* network operations on the repo) demonstrates the authors consider concurrent Git processes on the same working directory unsafe enough to warrant a dedicated guard everywhere else. `_fetchRefspec` is reachable via a pull request whose head repository (attacker's fork) is fully attacker-controlled, satisfying the "attacker controls a git remote/proxy response" precondition. A race between this attacker-triggered fetch and the user's own push/pull could:
- Interleave writes to shared Git state (`FETCH_HEAD`, packed-refs, reflogs) leading to inconsistent local ref state that Desktop's UI/state cache (`gitStore.lastFetched`, `aheadBehind`, `tip`) then reflects incorrectly, causing a user to commit/push against unexpected parent state (silent corruption of what the user commits or pushes).
- On slower/networked filesystems or under heavier load, increase the odds of lock-file contention/partial writes to refs during concurrent fetch+push, since `withPushPullFetch`'s comment explicitly frames its purpose as preventing exactly these races ("Don't allow concurrent network operations").

### Likelihood Explanation
The trigger requires only that the user opens/views a pull request from a fork the attacker controls (a routine, unprivileged GitHub interaction) while independently performing a push/pull/fetch — a very plausible sequence of ordinary user actions, with no admin rights, no local access, and no social engineering beyond "open a PR view from an attacker's fork," which is a normal Desktop workflow. That said, I could not fully trace every UI call site that invokes `dispatcher.fetchRefspec` within the indexed portion of the codebase (only the `app-store.ts` definition and dispatcher wrapper were found; the exact UI trigger for `_fetchRefspec` was not located in the available index), so I cannot confirm with full certainty how easily an unprivileged user reaches this specific code path today, versus historically documented in the comment. This is a caveat to flag explicitly rather than assert as fully proven.

### Recommendation
Either route `_fetchRefspec` through `withPushPullFetch` (queuing it behind other Git network operations rather than skipping the guard), or use a per-remote/per-refspec lock scoped narrowly enough to avoid concurrent writes to shared repository-wide state (refs, FETCH_HEAD, index) while still allowing PR-preview fetches to proceed independently of unrelated remotes.

### Proof of Concept
1. Attacker opens a pull request against a public repo, with a head branch hosted in an attacker-controlled fork.
2. Victim, using GitHub Desktop, opens that PR (triggering `_findPullRequestBranch`/`_fetchRefspec`-style fetch against the attacker fork remote, bypassing `withPushPullFetch`).
3. Concurrently (e.g., scripted to align timing, or simply because the victim manually triggers a push/pull while the PR view is loading), the victim performs a `git push` or `git pull` on the same repository, which goes through the normal `withPushPullFetch`-guarded path.
4. Because `_fetchRefspec`'s `git fetch` was never blocked by the mutex, two Git processes run concurrently against the same `.git` directory, one of which is driven by attacker-supplied remote content — a state the app's own concurrency guard is designed to prevent for every other fetch/pull/push path.

*Note: I was unable to fully verify the exact current UI entry point(s) that call `dispatcher.fetchRefspec`/`_fetchRefspec` within the available index, so the practical reachability of this path from today's PR-viewing UI should be confirmed in the full source (a Devin session with full repo access would be needed to trace this precisely).*

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

   * As this action is required to complete when viewing a Pull Request from

  public async _fetchRefspec(
    repository: Repository,
    refspec: string
  ): Promise<void> {
    return this.withRefreshedGitHubRepository(repository, async repository => {
      const gitStore = this.gitStoreCache.get(repository)
      await gitStore.fetchRefspec(refspec)

/** Fetch a given refspec from the given remote. */
export async function fetchRefspec(
  repository: Repository,
  remote: IRemote,
  refspec: string
): Promise<void> {
  await git(['fetch', remote.name, refspec], repository.path, 'fetchRefspec', {
    successExitCodes: new Set([0, 128]),
    env: await envForRemoteOperation(remote.url),
  })
}
