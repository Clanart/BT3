### Title
`ThresholdKeys::read` deserializes inconsistent key material — crafted bytes let an attacker dictate the group key and the node's secret share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reconstructs a node's full threshold key state (params, interpolation coefficients, secret share, and all `n` verification shares) from attacker-supplied bytes, then calls `ThresholdKeys::new`, which derives `group_key` purely from the supplied verification shares. At no point is it checked that `secret_share * G == verification_shares[i]`, nor are identity verification shares rejected (the plain `Ciphersuite::read_G` is used, which accepts the identity point, unlike `Curve::read_G` in FROST). This is the deserialization-of-crafted-objects bug class (CWE-502/CWE-74) mapped onto Serai: a crafted serialized `ThresholdKeys` blob yields a self-consistent-looking but entirely attacker-defined key set.

### Finding Description
`ThresholdKeys::read` at `crypto/dkg/src/lib.rs:574-632`:
- Reads `t`, `n`, `i`, the interpolation variant (for `Constant`, `n` scalars via `C::read_F`), the `secret_share` via `C::read_F`, and `n` verification shares via `<C as Ciphersuite>::read_G` — which performs canonical-encoding checks but explicitly does not reject the identity point (contrast `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131`, which does).
- Then calls `ThresholdKeys::new` (`lib.rs:349-391`), which computes `group_key` as the interpolation-weighted sum of `verification_shares[1..=t]` and stores the secret share verbatim.

Missing validation:
1. No check that `C::generator() * secret_share == verification_shares[i]` (the node's own public share). A node can therefore load a `secret_share` that is unrelated to the verification shares it claims to own.
2. No rejection of identity verification shares. Since interpolation weights are public, an attacker can craft `verification_shares` (e.g., mostly identity plus one chosen point) so that `group_key = k * G` for an attacker-known `k`.

Downstream, `view()` (`lib.rs:463-533`) blindly interpolates `secret_share` and re-weights the (crafted) `verification_shares`, adding the offset to `included[0]`, and FROST signs using `view.secret_share()`. The consistency of the aggregate is only enforced against `view.verification_shares()` — i.e., against the attacker's own values.

### Impact Explanation
If serialized `ThresholdKeys` reach a participant over any channel an unprivileged party can influence (coordinator-distributed key material, a tampered backup, or a crafted blob passed to any API calling `ThresholdKeys::read`):

- **Group key substitution**: the node computes a `group_key` chosen by the attacker. If the attacker supplies a fully consistent crafted set to all `t` signers (e.g., shares of a known scalar distributed via the same compromised channel), the threshold produces valid FROST signatures for a key whose discrete log the attacker knows — attacker-controlled signatures and, in the bitcoin-serai flow, funds sent to an address controlled by the attacker.
- **Inconsistent share → mis-blame/DoS**: with only some nodes corrupted, produced partial signatures fail aggregate verification, causing honest nodes to blame-and-abort honest (corrupted-config) participants.

This meets the validation bar as concrete signing under an unintended (attacker-chosen) group key and verification of shares against attacker-supplied verification shares — both reachable purely through crafted bytes to `ThresholdKeys::read`.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API intended for key persistence/distribution. The trust assumption "the bytes are authentic" is exactly the assumption the Synapse advisory violates — any path where serialized key material crosses an untrusted boundary (network distribution, shared storage, restorations) is exploitable. The math checks required to detect the corruption are cheap (one scalar mul + comparison) yet absent, so the failure is deterministic once bytes are tampered. Likelihood is bounded by deployment: it requires the key blob to be attacker-influenced rather than locally generated and protected, hence High rather than Critical.

### Recommendation
In `ThresholdKeys::new` (and therefore transitively in `ThresholdKeys::read`):
1. Reject identity verification shares: `if bool::from(share.is_identity()) { Err(...) }` (or use a strict reader as in `Curve::read_G`).
2. Verify `C::generator() * secret_share.deref() == verification_shares[&params.i()]` before constructing the keys.
3. Reject an identity resulting `group_key`.
4. For `Interpolation::Constant`, additionally bound-check coefficient count vs `t == n` is already enforced, but each coefficient should be documented/enforced non-zero to avoid silently zero shares.

### Proof of Concept
```rust
// Crafted ThresholdKeys serialization for C = Secp256k1 (or Ed25519/Ristretto):
// attacker picks scalar k, sets:
//   t = n = 1, i = Participant(1)
//   interpolation = Lagrange (tag byte 1)
//   secret_share = k                      // attacker-known
//   verification_shares[1] = G * k        // or even identity combined with others when n > 1
// Result: ThresholdKeys::read succeeds, group_key() == G*k, view([1]).secret_share() == k.
// Every signature produced is valid under a key the attacker fully controls,
// and the node never detects that the loaded keys were not produced by a real DKG.
//
// For n > 1, attacker sets verification_shares[2..=n] = identity (accepted by
// Ciphersuite::read_G, rejected only by Curve::read_G which is not used here)
// and verification_shares[1] = G * k / lagrange_1, again yielding group_key = G*k
// while shares for participants 2..=n are silently invalid.
```
The absence of the `secret_share * G == verification_shares[i]` check is visible directly at `crypto/dkg/src/lib.rs:574-632` (read path) and `lib.rs:349-391` (`ThresholdKeys::new` computes `group_key` without validating the private share or rejecting identity shares).
