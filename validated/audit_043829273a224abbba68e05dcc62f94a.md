Audit Report

## Title
Partitioned Epoch-Reward Recalculation Uses Live `StakesCache` State Instead of Reward-Epoch-Boundary Stake, Corrupting Individual Stake-Reward Payouts - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

## Summary
`recalculate_stake_rewards`, invoked from `recalculate_partitioned_rewards_if_active` whenever the `EpochRewards` sysvar is still `active` mid-distribution, rebuilds each stake account's `Delegation` from the bank's *current* `stakes_cache` rather than from a frozen snapshot taken at the reward-epoch boundary. [1](#0-0)  While the fixed `PointValue` (`total_rewards`/`total_points`) denominator is correctly pulled from the sysvar rather than recomputed, the individual delegation's points/effective-stake numerator is recomputed against whatever `Delegation` (stake amount, activation/deactivation epochs) currently exists in `stakes_cache`. [2](#0-1)  A delegator performing an ordinary `Split`/`Merge`/`Deactivate` between the original epoch-boundary calculation and a mid-distribution recalculation trigger (fork switch/restart while `EpochRewards` is still active) causes their reward for the already-elapsed `rewarded_epoch` to be recomputed from the mutated `Delegation`, producing a payout inconsistent with what was actually earned and with the fixed total-rewards/points denominator.

## Finding Description
`recalculate_stake_rewards` asserts `epoch_rewards_sysvar.active`, computes `rewarded_epoch = self.epoch() - 1`, and derives `point_value` directly from the immutable sysvar fields (`total_rewards`, `total_points`) — this part is correctly frozen. [3](#0-2)  It then reads `self.stakes_cache.stakes()` — the bank's live state at the moment of recalculation — and passes it into `get_epoch_params_for_recalculation(rewarded_epoch, &stakes)` to obtain `stake_delegations`, which are fed straight into `calculate_stake_rewards_and_commissions`, the same routine used for the original epoch-boundary calculation. [4](#0-3)  The function's own comment explicitly disclaims correctness only for `RewardCommissionAccounts`, on the grounds that commission accounts are "loaded from the current bank, and not the start of the epoch," but does not extend this caveat to the `stake_rewards` field that is actually used to drive real payouts and partition assignment (`hash_rewards_into_partitions`). [5](#0-4) 

Because `Delegation.stake`/`activation_epoch`/`deactivation_epoch` are ordinary, permissionlessly mutable fields (changed by `Split`, `Merge`, `Deactivate`, redelegate instructions issued by the stake account's own authority), any recalculation that occurs after such a mutation but before the sysvar transitions to `active = false` will compute that delegator's `rewarded_epoch` points/reward from the *post-mutation* delegation state rather than the state that actually earned the reward. The existing regression test only asserts that the frozen `RewardEpochDelegatedStakes` denominator is stable across recalculation; it does not cover mutation of an individual `Delegation` between initial calculation and recalculation. [6](#0-5) 

## Impact Explanation
This falls in the `runtime`/`accounts` fund-accounting-correctness impact class: an individual staker's recalculated epoch reward can silently diverge from the amount actually earned for `rewarded_epoch`, because the numerator (per-delegation points/effective stake) is computed from live, potentially-mutated state while the denominator (`total_rewards`/`total_points`) remains fixed from the sysvar. This can result in over- or under-payment relative to what was legitimately earned, an accounting corruption of the exact stake-reward lamport value delivered via `PartitionedStakeRewards`/`stake_rewards`.

## Likelihood Explanation
Triggering recalculation requires no privilege — it happens automatically whenever a bank observes an `active` `EpochRewards` sysvar (e.g., on fork switch or restart during the multi-block partitioned distribution window), a condition entirely outside attacker control but not rare during normal operation. Mutating one's own `Delegation` via `Split`/`Merge`/`Deactivate` requires only the delegator's own signature — a fully unprivileged, permissionless action. The combination (distribution window still open + self-mutation before a recalculation event) is a plausible, non-contrived sequence, though its occurrence is timing-dependent on fork/restart cadence and distribution duration.

## Recommendation
Snapshot each account's `Delegation` (stake amount, activation/deactivation epochs) at the reward-epoch boundary, analogous to how `RewardEpochDelegatedStakes` freezes the epoch's total delegated stake, and have `recalculate_stake_rewards` consult that frozen per-account snapshot instead of `self.stakes_cache.stakes()` when redoing the calculation mid-distribution.

## Proof of Concept
1. Epoch `N` ends; stake rewards are computed for delegator `D` with `Delegation.stake = S1`; partitioned distribution begins (`EpochRewards.active = true`).
2. Before all partitions are distributed, `D` submits `Split`/`Deactivate` on their stake account, changing the live `Delegation` to `stake = S2` (or setting `deactivation_epoch`).
3. A fork switch/restart occurs while the sysvar is still `active`, triggering `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards`. [7](#0-6) 
4. `recalculate_stake_rewards` reads `D`'s `Delegation` from the now-mutated `stakes_cache`, recomputing `D`'s `rewarded_epoch = N` reward from `S2` rather than the historically correct `S1`.
5. `D` receives a reward inconsistent with the fixed `PointValue` denominator and with what was earned during epoch `N`, verifiable by extending the existing recalculation regression test to assert per-delegator reward stability (not just the `RewardEpochDelegatedStakes` denominator) after mutating a delegation between initial calculation and recalculation.

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
        drop(stakes);
        let partition_indices = hash_rewards_into_partitions(
            &stake_rewards,
            &epoch_rewards_sysvar.parent_blockhash,
            epoch_rewards_sysvar.num_partitions as usize,
        );
