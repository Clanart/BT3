## Title
Cross-session OAuth account binding via unrevalidated `this.state.oauthState` after async gaps in `resolveOAuthRequest` - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`resolveOAuthRequest` validates the CSRF `state` value against `this.state.oauthState.state` only *before* the two asynchronous network calls (`requestOAuthToken`, `fetchUser`). After those awaits complete, it re-reads `this.state.oauthState` fresh instead of using a value captured/validated earlier, and never re-checks that the sign-in session is still the same one that initiated the request. If a second sign-in flow (e.g. a new `beginEnterpriseSignIn`/`setEndpoint`/`authenticateWithBrowser` sequence) replaces `this.state` while the first flow's `requestOAuthToken`/`fetchUser` calls are still pending, the first flow's resolved account is delivered to the *second* flow's `oauthState.onAuthCompleted`, binding the wrong host's token/account to the second session.

### Finding Description
In `resolveOAuthRequest`, the CSRF check happens once at the top: [1](#0-0) 

But the completion call at the end re-reads `this.state.oauthState` directly, after two `await`s, rather than using a reference captured at validation time: [2](#0-1) 

Because `this.state` is a mutable store field, anything that runs during the `await requestOAuthToken(...)` / `await fetchUser(...)` window can replace it — for example a user (or an attacker-influenced UI flow, such as a second OAuth deep link or a new `beginEnterpriseSignIn` call) invoking `beginEnterpriseSignIn`, `setEndpoint`, or `authenticateWithBrowser` again, which calls `reset()` and then `setState()` with a brand-new `IAuthenticationState` containing a new `oauthState` (new CSRF token, new `resolve`/`reject`, potentially a different `endpoint`): [3](#0-2) [4](#0-3) 

When the first `resolveOAuthRequest` call finally resumes after its awaits, `this.state.oauthState` no longer belongs to the first session — it belongs to whatever session is now active. Calling `this.state.oauthState.onAuthCompleted(account)` therefore resolves the *second* session's promise with the *first* session's `Account` (which embeds the first endpoint's OAuth token). The consuming `.then()` handler in `authenticateWithBrowser` only checks that `this.state.kind === SignInStep.Authentication` — it has no way to know the account it just received doesn't correspond to the currently active endpoint/session: [5](#0-4) 

The trigger is externally reachable: `resolveOAuthRequest` is invoked from a custom-protocol deep link (`x-github-client://oauth?code=...&state=...`) parsed by `parseAppURL`, whose `code` and `state` values come straight from the URL query string with no origin validation beyond the CSRF token comparison: [6](#0-5) 

### Impact Explanation
A stale, in-flight OAuth completion from one sign-in session (e.g. against Enterprise host A) can be delivered as the result of a different, currently active sign-in session (e.g. against host B or github.com), causing `emitAuthenticate` and the session's `resultCallback` to receive an `Account` object bound to the wrong endpoint/token. Depending on the caller of `beginEnterpriseSignIn`/`beginDotComSignIn` (e.g., "Add Account" flow), this can result in the wrong account/token being added or presented as if it belonged to the endpoint the user just intended to authenticate with — an unauthorized/incorrect OAuth account binding.

### Likelihood Explanation
Exploitation requires interleaving two sign-in flows within the narrow window of the `requestOAuthToken`/`fetchUser` network round trip (e.g., a user or automated deep-link redirect starting a second Enterprise sign-in before the first OAuth callback is processed). This is a real race but requires specific timing/UI interaction (starting a second sign-in while a first is still resolving), which is not a completely trivial one-click attack, though it is triggerable through normal app UI use plus a delayed/duplicate OAuth callback deep link.

### Recommendation
Capture the validated `oauthState` (and possibly the whole session identity/CSRF token) into a local variable immediately after the initial CSRF check, and use that captured reference for `onAuthCompleted`/`onAuthError` instead of re-reading `this.state` after the `await`s. Additionally, re-verify after each await that `this.state?.oauthState?.state === action.state` before completing, mirroring the check already done in the `.catch()` handler of `authenticateWithBrowser`.

### Proof of Concept
1. Start Enterprise sign-in to host A, reach the `Authentication` step, and click "authenticate with browser" (`oauthState.state = csrfA`, `endpoint = A`).
2. Deep link `x-github-client://oauth?code=codeA&state=csrfA` arrives, `resolveOAuthRequest` passes the CSRF check and begins `await requestOAuthToken(A, codeA)` / `await fetchUser(A, tokenA)`.
3. Before those awaits resolve, trigger a new sign-in flow (`beginEnterpriseSignIn` → `setEndpoint(B)` → `authenticateWithBrowser`), which resets `this.state` to a new `Authentication` state for host B with `oauthState.state = csrfB`.
4. The pending call from step 2 resolves; `this.state.oauthState.onAuthCompleted(accountA)` now calls the resolver belonging to the host B session.
5. Observe that `authenticateWithBrowser`'s `.then()` for host B's flow receives `accountA` (endpoint A, token A) and calls `emitAuthenticate(accountA)`/`resultCallback` as if it were the result of the host B sign-in.

```typescript
  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
```
