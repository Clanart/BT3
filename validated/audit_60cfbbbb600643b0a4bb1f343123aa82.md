### Title
BIP-340 HRAm panics on point-at-infinity nonce sum reachable via crafted FROST preprocesses - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Bitcoin Taproot `Schnorr` algorithm's `Hram` computes `x(R)`, which panics (`expect("point at infinity")`) when the aggregate nonce commitment `R` is the point at infinity. `Commitments::read`/`Curve::read_G` only reject identity for *individual* committed points; the *sum* of valid, non-identity nonce commitments can still be identity. A participant who supplies preprocess nonce commitments chosen as the negation of the other signers' aggregate commitments forces `R` (or a per-generator `nonce_sums` element) to infinity, crashing the signer process in `sign_share`/`verify`. This mirrors CVE-2017-18199's class: a malformed, attacker-supplied input drives a NULL/crash-level denial of service.

### Finding Description
In `networks/bitcoin/src/crypto.rs`, `x()` extracts the x-coordinate of a `ProjectivePoint` and unconditionally unwraps `encoded.x()`, which is `None` for the point at infinity:

```rust
// networks/bitcoin/src/crypto.rs:13-16
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

`Hram::hram` calls `x(R)` and `x(A)` on the aggregate nonce `R` and group key `A` (crypto.rs:59-67). The `Schnorr` `Algorithm` documentation even concedes the panic: "If either `R` or `A` is the point at infinity, this will panic" (crypto.rs:54) and claims a "negligible probability ... even with malicious participants present" (crypto.rs:78-80). That claim is incorrect: the probability is not negligible when a malicious participant *adaptively* chooses their preprocess commitments.

On the FROST side, `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) rejects identity for each deserialized commitment point, so every individual nonce commitment in a `Preprocess` (read via `read_preprocess`, `Commitments::read`) is a valid non-identity point. However, FROST computes `R = sum_j (D_j + rho_j * E_j)` over all participants' commitments. An attacker who observes the other participants' preprocesses before submitting their own (a rushing adversary, which is the standard FROST threat model since preprocess delivery is not simultaneous broadcast with binding ordering — Serai's coordinator collects and forwards preprocesses) sets their commitments to `-(sum of others' contributions)`, making `R` the point at infinity. When `AlgorithmSignMachine::sign` → `sign_share` → `Hram::hram` runs (crypto/frost/src/sign.rs), `x(R)` panics, aborting the whole signer process rather than returning a `FrostError`.

The same panic path exists in `verify`/`verify_share` during `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:465-489), so even honest-share validation crashes instead of producing `FrostError::InvalidShare`.

### Impact Explanation
An attacker controlling a single signer slot in a Bitcoin-secured multisig can deterministically crash every honest signer's process during each signing attempt by submitting a preprocess whose nonce commitments cancel the aggregate. Because the panic occurs before `InvalidPreprocess`/`InvalidShare` errors can be returned, the failure is not attributable to the malicious participant — each re-attempt yields the same crash, permanently stalling all Taproot (BIP-340) signing for that group. This is a remote, unauthenticated-input-driven denial of service of the signing service, matching the Medium-severity availability impact of the reference bug class (crafted input → crash).

### Likelihood Explanation
The attacker only needs to be one participant in the multisig able to submit preprocess messages, and needs their preprocess to be processed after learning the others' commitments — achievable whenever preprocesses are relayed through a coordinator or ordered delivery, which is how Serai's processor forwards `Preprocesses`/`SubstratePreprocesses` messages to signers. Constructing the canceling commitment is a single point negation and addition, so no probabilistic preconditions exist. The only mitigation is protocol-level simultaneous commitment exchange, which is not enforced by `read_preprocess`/`Commitments::read`.

### Recommendation
In `Hram::hram` (or in the `Schnorr` algorithm's `sign_share`/`verify` wrappers), detect `R.is_identity()` / `A.is_identity()` and return an error/`Err(FrostError::InvalidPreprocess(l))` instead of panicking. More robustly, in `crypto/frost`'s signing flow (`AlgorithmSignMachine::sign` and `SignatureMachine::complete`), check each aggregate `nonce_sums` element for identity after summing commitments and return `FrostError::InvalidPreprocess` naming the participant set, so blame is attributable. Avoid `expect`/`panic!` on values derived from deserialized peer input.

### Proof of Concept
1. Set up `t-of-n` `ThresholdKeys<Secp256k1>`, construct `bitcoin::Schnorr::new()` `AlgorithmMachine`s for all participants.
2. Honest participants call `preprocess(rng)` and publish their `Preprocess` messages (nonce commitments `D_l, E_l`).
3. The attacker, after receiving the other preprocesses, computes the aggregate contribution of all other participants for generator 0: `S = sum_{l != a} (D_l + rho_l * E_l)` (computable because `rho_l = hash_binding_factor(group_key || l || hash_msg(msg) || encoded commitments)` is fully public), then submits a preprocess whose commitments satisfy `D_a + rho_a * E_a = -S` (e.g., set `D_a = -S - rho_a * E_a` for an arbitrary valid `E_a`). All points are non-identity, so `Commitments::read` accepts them.
4. When any honest signer calls `sign(preprocesses, msg)` → `sign_share`, `nonce_sums[0]` is identity, `Hram::hram` calls `x(&identity)`, and `expect("point at infinity")` panics, crashing the process. Repeating on every attempt yields a persistent signing DoS with no attributable `FrostError`.
