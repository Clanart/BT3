### Title
`SignableTransaction::new` excludes the OP_RETURN output from the weight/fee calculation, underestimating `needed_fee` and the amount available for change - (networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the RageTrade `maxWithdraw`/`maxAvailable` bug — where the cap on withdrawable assets was computed with an incomplete formula — `SignableTransaction::new` computes the transaction's weight, required fee, and leftover change using `calculate_weight_vbytes`, which is only ever passed the `payments` slice and the optional change output. The OP_RETURN output carrying `data` is pushed onto `tx_outs` before the fee math but is never included in the size estimate, so `needed_fee` and the change value are computed against a smaller transaction than the one actually signed.

### Finding Description
In `SignableTransaction::new`:

1. The OP_RETURN output is appended to `tx_outs` when `data` is present [1](#0-0) .
2. The vbytes used for the fee and the minimum-relay check come from `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a mock transaction containing only `payments` outputs — the OP_RETURN output in `tx_outs` is ignored [2](#0-1) .
3. The change path repeats the same incomplete estimate: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again omits the data output, and the change value is set to `input_sat - payment_sat - fee_with_change` [3](#0-2) .
4. `calculate_weight_vbytes` itself only serializes `payments` plus optional change; nothing in the function accounts for the OP_RETURN output [4](#0-3) .

The signed transaction therefore includes an output (up to ~92 vbytes for an 80-byte payload: 1-byte OP_RETURN + pushdata + 80-byte push, plus the 9-byte `TxOut` header) that was never priced. `needed_fee` is exactly the fee the transaction pays (`sum(inputs) - sum(outputs)`, confirmed by `fee()` [5](#0-4) ), so the effective fee rate is strictly lower than `fee_per_vbyte`.

### Impact Explanation
Two concrete consequences:

- **Below-minimum-relay transactions.** The `TooLowFee` guard checks `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the understated `vbytes`. With `fee_per_vbyte` at or near the relay minimum and `data` attached, the real transaction's fee rate falls below the relay minimum and the fully-signed transaction is rejected by the Bitcoin P2P network. The consumed `ReceivedOutput`s remain locked to a dead transaction until a new plan is built and re-signed — a liveness/availability failure on funds the system reported as spendable, mirroring the vault's incorrect available-liquidity cap.
- **Misquoted fee/change accounting.** Callers using `needed_fee()`/`transaction()` observe a transaction whose actual sat/vb rate is lower than the requested `fee_per_vbyte`, and when a change output exists the change amount is calculated against a fee estimate for a smaller transaction than the one broadcast.

The underestimation is bounded (~11–92 vbytes per transaction, one OP_RETURN output), so this is a correctness/availability issue rather than direct theft — consistent with a Medium severity analog.

### Likelihood Explanation
Triggering requires `data` to be supplied alongside a fee rate near the minimum relay fee (or any case where the marginal ~92 vbytes matter to the intended rate). `data` capped at 80 bytes is accepted unconditionally [6](#0-5) , and any caller building a transaction with both an OP_RETURN payload and a low fee rate hits the discrepancy deterministically — no adversarial timing or cooperation is needed.

### Recommendation
Include the OP_RETURN output in the size estimate. The cleanest fix is to pass the fully-assembled `tx_outs` (or a `data: Option<&[u8]>` parameter) into `calculate_weight_vbytes` so the mock transaction exactly mirrors the outputs of the real one, for both the no-change and with-change estimates. This keeps the `TooLowFee` check, `needed_fee`, and the change-value subtraction consistent with the transaction that is actually signed.

### Proof of Concept
```rust
// Conceptual PoC against SignableTransaction::new (send.rs:150)
let inputs = vec![received_output];        // any ReceivedOutput, e.g. value = 10_000 sats
let payments = &[(payment_script, 5_000)]; // >= DUST
let change = Some(change_script);
let data = Some(vec![0u8; 80]);            // max-size OP_RETURN payload

let stx = SignableTransaction::new(inputs, payments, change, data, 1 /* sat/vb */).unwrap();

// stx.transaction() contains: payment output + OP_RETURN output + change output.
// calculate_weight_vbytes priced only payment + change, so:
//   actual_vbytes ≈ priced_vbytes + ~92
//   stx.fee() == needed_fee == 1 * priced_vbytes
//   effective rate ≈ priced_vbytes / (priced_vbytes + 92) < 1 sat/vb
//
// With priced_vbytes ≈ 200, effective rate ≈ 0.68 sat/vb < DEFAULT_MIN_RELAY_TX_FEE
// (1000 sat/kvb == 1 sat/vb), so the signed transaction is non-relayable despite
// passing the TooLowFee check at send.rs:211.
```
