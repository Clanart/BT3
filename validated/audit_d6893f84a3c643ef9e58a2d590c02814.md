### Title
`SignableTransaction` signs over self-declared prevout values without verifying the `TxOut` corresponds to the `outpoint`'s actual on-chain UTXO — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Tokensoft `claim` issue — where a caller-supplied `totalAmount` was never checked against the initialized distribution record — `ReceivedOutput` carries a self-declared `TxOut` (value + script) alongside an `outpoint`, and `SignableTransaction::new` / `multisig` never verify that the declared `TxOut` is the actual UTXO referenced by `previous_output`. The Taproot sighash then commits `Prevouts::All` built from these unverified, attacker-controllable `TxOut`s, causing the threshold key to sign a message whose prevout amounts do not match chain reality.

### Finding Description
`ReceivedOutput` bundles three independent fields read verbatim from untrusted bytes: an `offset` scalar, a `TxOut output`, and an `OutPoint outpoint` — `ReceivedOutput::read` performs no consistency check between them (`networks/bitcoin/src/wallet/mod.rs:122-134`).

`SignableTransaction::new` trusts `input.output.value` for its funding math (`input_sat`) and places `input.outpoint` into the unsigned transaction, while `input.output` is stored into `prevouts` (`send.rs:175-185, 253`). `SignableTransaction::multisig` verifies only that `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — i.e., the *script* is bound to the key — but there is no binding that the `prevouts[i]` value is the true value locked by `tx.input[i].previous_output` (`send.rs:273-285`). `TransactionSignMachine::sign` then computes `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), ...)`, committing the signature to the declared, not actual, amounts (`send.rs:373-390`).

Since BIP-341 key-path sighashes commit to each input's amount and script, any `ReceivedOutput` whose `TxOut.value` does not equal the real UTXO's value produces a signature that is well-formed under FROST/BIP-340 yet consensus-invalid: every honest validator will produce a valid share and a "valid" signed transaction that Bitcoin nodes reject. The declared-vs-actual amount is the exact analogue of `totalAmount` vs the initialized record amount.

### Impact Explanation
An unprivileged party who can feed forged `ReceivedOutput` bytes (via `ReceivedOutput::read`) or otherwise inject an output whose `TxOut` value mismatches its `outpoint` causes the validator set to produce a threshold signature over fabricated prevout data. The resulting transaction can never confirm, yet the signing plan completes: a completion is published and the consumed outpoints may be marked spent/handed off while no funds actually moved — stranding real UTXOs and burning a signing session (re-attempt loops per input set). Unlike the Solidity case there is no second on-chain record to check locally, so the discrepancy is undetectable until broadcast failure — the signature commits to an unintended message.

### Likelihood Explanation
Reachability requires untrusted bytes reaching `ReceivedOutput::read`/`Output::read` or a mismatch introduced before `SignableTransaction::new`; the scanner normally constructs consistent outputs, so the attack surface is the deserialization path and any component passing outputs it did not itself scan. Because `multisig`'s script check passes regardless of value, a purely value-mismatched record slips through every existing validation. Medium likelihood, Medium impact.

### Recommendation
Bind the declared `TxOut` to the outpoint's actual UTXO before signing. Where chain data is unavailable inside `networks/bitcoin`, require callers to prove consistency: at minimum, `SignableTransaction::new` should recompute and enforce that `prevouts[i]` is the exact `TxOut` observed at `tx.input[i].previous_output` (e.g., by storing the outpoint→TxOut binding at scan time and re-verifying it in `multisig`), and `fee()`/`needed_fee` sanity checks should compare against values sourced from the same verified record — mirroring `require(amountFromRecord == totalAmount)`.

### Proof of Concept
```rust
// networks/bitcoin: craft a ReceivedOutput whose declared value differs
// from the UTXO actually locked by `outpoint`.
let real: ReceivedOutput = scanner.scan_transaction(&tx).pop().unwrap(); // value = 50_000 sats

let mut forged_bytes = real.serialize();
// Overwrite the TxOut value field (offset[32..40] of the serialized TxOut)
// to claim 5_000_000 sats while keeping the same script_pubkey and outpoint.
let mut forged = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();
assert_eq!(forged.outpoint(), real.outpoint()); // same UTXO claimed
assert_ne!(forged.value(), real.value());       // with a different "totalAmount"

// SignableTransaction::new performs its funding math on forged.value()
let stx = SignableTransaction::new(vec![forged], &payments, None, None, fee).unwrap();

// multisig passes: the script_pubkey still matches keys.offset(offset).group_key()
let machine = stx.multisig(&keys).unwrap();

// sign() commits Prevouts::All containing the forged 5_000_000-sat TxOut.
// Every participant produces a valid share; the aggregated BIP-340 signature
// verifies against the forged sighash but is consensus-invalid on-chain —
// the threshold signed a message whose claimed input amount was never
// checked against the real output record.
```
