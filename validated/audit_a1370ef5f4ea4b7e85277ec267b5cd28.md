### Title
Recursive clone explicitly disables Git's built-in clone-time hook/symlink protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in [1](#0-0)  always performs `git clone --recursive` and explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for the operation. This is the same env var upstream Git uses internally to gate the hardening it added for clone-time attacks where a malicious repository (typically via nested/recursive submodules combined with symlinks or crafted `.git` directories) can get its hooks or config executed/read during `clone --recursive` before the user ever opens the repository. By forcing this flag to `false` for every Desktop-initiated clone, the app appears to intentionally turn that protection off rather than leaving Git's default (protective) behavior in place.

### Finding Description
The `clone` function builds:
```
'-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive', ..., '--', url, path
```
with an environment containing `GIT_CLONE_PROTECTION_ACTIVE: 'false'` [2](#0-1) . `--recursive` means submodules are fetched and checked out automatically as part of the same clone call, without any additional user confirmation step, and `envForRemoteOperation` only adds proxy/auth env vars on top, it does not remove or override the protection flag [3](#0-2) .

The invariant being broken is: "Git's own clone-time defenses against hostile repository content (hooks/config reachable through crafted submodule trees) remain active for repositories fetched by Desktop, an untrusted, attacker-controlled input." Desktop is explicitly opting out of that defense for every clone, including clones of arbitrary user-supplied URLs (the "Clone repository" URL/GitHub tabs feed straight into `_clone` → `CloningRepositoriesStore.clone` → `clone()` [4](#0-3) [5](#0-4) ), and to "Open in Desktop" deep-link driven clones (`openOrCloneRepository` from `parseAppURL`'s `open-repository-from-url` action [6](#0-5) ).

Existing repo-level guards do not cover this gap:
- `isClonePathSensitive()` only validates the destination directory, not what the fetched content can do during the clone itself [7](#0-6) .
- The hooks proxy/interception mechanism (`withHooksEnv`, `getRepoHooks`) is designed for hooks Desktop itself later invokes in an *existing* repository, not for whatever Git natively executes as a side effect of the `clone --recursive` invocation itself [8](#0-7) .
- `updateSubmodulesAfterOperation`, used for later checkout/pull-driven submodule updates, deliberately restricts `protocol.file.allow` and does not set `GIT_CLONE_PROTECTION_ACTIVE` at all [9](#0-8) ; the disabling is unique to the initial `clone()` path.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE` genuinely gates Git's clone-time mitigation for hostile nested-repository content (the class of issue Git hardened against for scenarios where a crafted repository/submodule tree can cause code to run or files to be written outside the intended checkout during `clone --recursive`), then disabling it means any attacker who can get a user to clone or "Open in Desktop" a malicious repository (a plain public GitHub URL is enough) gets the pre-hardening behavior back: potential code execution or writes outside the intended repository root as a direct consequence of the recursive clone, with no additional user action beyond initiating a normal clone. This maps directly to the requested impact class: attacker controls a cloned/fetched repository → code execution / file write outside the repo.

### Likelihood Explanation
Likelihood is high for exposure (every clone goes through this exact code path, including clones triggered by external `x-github-client://openRepo/...` deep links and by pasting arbitrary URLs into the Clone dialog), but I could not independently confirm from the available local index exactly which upstream Git security behavior `GIT_CLONE_PROTECTION_ACTIVE` toggles (no Git source, changelog, or code comments explaining the rationale were present in the indexed files, and blame/commit history for this repository only shows a single "Initial commit"). The variable name and its pairing with a forced `--recursive` clone strongly suggest it corresponds to Git's clone-time protection against hostile repositories, but this should be verified against the Git version vendored by Desktop (`dugite`) before treating this as confirmed rather than a strong analog.

### Recommendation
- Do not force `GIT_CLONE_PROTECTION_ACTIVE=false`; leave Git's default (protective) value in place unless there is a specific, documented, narrow reason to disable it, and if so scope that reason in a code comment referencing the exact upstream advisory it relates to.
- If `--recursive` clone is required for UX reasons, verify against the actual `dugite`/Git version bundled with Desktop whether recursive clone protection is still needed for that version, and add a regression test cloning a crafted repository (symlinked `.git`, submodule pointing to a path containing hooks) to prove hooks are not executed and no writes occur outside the destination directory.
- Add explicit code comments in `clone.ts` documenting why this override exists (if intentional) and link the Git security advisory it references, so future contributors don't mistake it for dead code and can evaluate compatibility with newer Git versions.

### Proof of Concept
Not verified end-to-end in this environment (no ability to run Git commands or inspect the actual protection semantics of `GIT_CLONE_PROTECTION_ACTIVE` against the vendored Git binary). Conceptually:
1. Attacker publishes a public repository containing a submodule (or nested `.git` structure) crafted to place a hook/executable reachable via a symlink that Git would normally refuse to materialize/execute during `clone --recursive` due to its built-in protection.
2. Victim opens the repository in GitHub Desktop via Clone dialog or `x-github-client://openRepo/<url>` deep link, which invokes `clone()` in [1](#0-0) .
3. Because `GIT_CLONE_PROTECTION_ACTIVE=false` is forced, Git performs the recursive clone without its protective checks, potentially executing hook content or writing outside the intended checkout tree.

Confirming this PoC requires reproducing it against the specific Git version Desktop bundles and confirming the semantics of `GIT_CLONE_PROTECTION_ACTIVE` for that version — recommend validating with a background Devin session that has access to the actual Git binary/dugite dependency.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

  public async clone(
    url: string,
    path: string,
    options: CloneOptions
  ): Promise<boolean> {
    const repository = new CloningRepository(path, url)
    this._repositories.push(repository)

    const title = `Cloning into ${path}`

    this.stateByID.set(repository.id, { kind: 'clone', title, value: 0 })
    this.emitUpdate()

    let success = true
    try {
      await cloneRepo(url, path, options, progress => {
        this.stateByID.set(repository.id, progress)
        this.emitUpdate()
      })
    } catch (e) {
      success = false

      const retryAction: RetryAction = {
        type: RetryActionType.Clone,
        name: repository.name,
        url,
        path,
        options,
      }
      e = new ErrorWithMetadata(e, { retryAction, repository })

      this.emitError(e)
    }

    this.remove(repository)

    return success
  }
