### Title
Relayer fee balance is debited to zero before the cross-chain withdrawal executes, permanently losing funds if the destination-side transfer fails - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in the relayer pallet zeroes a relayer's accrued `Fees` entry immediately after dispatching an ISMP POST request, without waiting for confirmation that the destination chain's `HostManager.withdraw()` actually transferred the tokens. If that destination-side transfer reverts (e.g. insufficient fee-token balance on the `EvmHost`), the failure is silently swallowed by `EvmHost.dispatchIncoming`, and the relayer's fee balance is unrecoverably lost — this is the same "action commits before knowing whether the dependent external call succeeds" defect as the seed report's `PromiseRouter.process()`, but here it destroys the relayer's actual principal rather than just wasting gas.

### Finding Description
`Pallet::withdraw` performs the following sequence:
1. Verifies signature/nonce and reads `available_amount = Fees::<T>::get(dest_chain, address)`.
2. Dispatches a `DispatchPost` to the destination's `HostManager` (EVM) via `dispatcher.dispatch_request(...)`, encoding `WithdrawalParams { beneficiary_address, amount, token }`.
3. Unconditionally zeroes the balance: `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());` [1](#0-0) 

`dispatch_request` only enqueues the ISMP message — it provides no guarantee that the destination-side effect (the actual token transfer) will succeed. On the EVM side, delivery is handled by `EvmHost.dispatchIncoming(PostRequest, relayer)`:
```solidity
(bool success,) = address(destination).call(abi.encodeWithSelector(IApp.onAccept.selector, ...));
if (!success) {
    delete _requestReceipts[commitment];
    return;
}
``` [2](#0-1) 

`HostManager.onAccept` forwards the withdrawal to `EvmHost.withdraw(WithdrawParams)`, which reverts with `WithdrawalFailed()` (native) or bubbles a `SafeERC20` revert (ERC20) if the host's fee-token balance is insufficient: [3](#0-2) [4](#0-3) 

This exact failure mode is exercised in the test suite (`test_host_manager_insufficient_balance` shows the withdraw reverting when the host lacks the requested balance): [5](#0-4) 

When that revert happens, `dispatchIncoming` catches it, deletes the request receipt "so it can be retried," and returns — no error propagates back to Hyperbridge, and the message is not tied to any timeout logic that could restore the relayer's `Fees` balance (the dispatched `DispatchPost` also uses `timeout: 0`, i.e. it never times out via the standard timeout path). Since `Fees::<T>::insert(..., U256::zero())` on the source chain already executed unconditionally in step 3 above, the relayer's fee is permanently gone: it is neither in `Fees` on Hyperbridge nor ever transferred by the `EvmHost`.

The `HostManager`'s `withdraw` and the `pallet-relayer` withdrawal both draw from the *same* single ERC20 balance held by `EvmHost` — there is no reserved/ring-fenced sub-balance for accrued relayer fees versus protocol/governance revenue. Governance can independently drain that same balance via `pallet-host-executive::withdraw` → `IHostManager(_params.host).withdraw(...)`: [6](#0-5) 

so any accounting mismatch between accrued-but-unpaid relayer fees (tracked only off-chain in `pallet-relayer::Fees`) and the actual on-chain fee-token balance held by `EvmHost` — caused by concurrent relayer withdrawals, governance revenue withdrawal, or simple timing races — causes the destination transfer to revert while the source-side balance has already been zeroed.

### Impact Explanation
This is a direct, permanent loss of relayer funds — the accrued fee entitlement is deleted from `Fees` regardless of whether the corresponding on-chain payout ever lands. It matches the bounty's "stealing or loss of funds" impact category. Unlike the seed report (only gas griefing), the destroyed value here is the relayer's actual earned fee balance, and there is no code path (timeout, retry, reconciliation) that restores it once the destination call fails.

### Likelihood Explanation
No malicious actor is strictly required: any legitimate race between (a) multiple relayers withdrawing against a shared `EvmHost` fee-token balance smaller than the sum of currently accrued `Fees`, or (b) governance's `pallet-host-executive::withdraw` draining the same balance concurrently with a relayer withdrawal, is sufficient to trigger the destination-side revert. Because withdrawals are permissionless, unsigned, and can be submitted by anyone holding a valid relayer signature, and destination confirmation is not awaited before zeroing `Fees`, this condition is readily reachable in normal operation, not just via a crafted attack.

### Recommendation
Do not zero `Fees` until destination-side settlement is confirmed. Options:
- Track the withdrawal as "pending" (as is already partially done on the tesseract relayer client side via `pending_withdrawals`) and only clear `Fees` once a delivery/execution receipt for the withdrawal request is observed on the destination chain.
- Alternatively, have `EvmHost.dispatchIncoming` propagate a distinguishable failure signal (e.g. an event) for `HostManager`-originated withdrawal failures, and have an ISMP timeout/retry path on Hyperbridge restore `Fees` when the destination call is known to have failed, mirroring the existing "delete receipt so it can be retried" pattern but connecting it back to the source-chain balance instead of leaving it orphaned.
- Ring-fence relayer-fee revenue from governance-withdrawable "bridge revenue" in a separate on-chain balance so the two withdrawal paths cannot race against the same pool.

### Proof of Concept
1. Relayer R accrues `Fees[dest_chain][R] = 100` on Hyperbridge (via `accumulate_fees`).
2. `EvmHost` on `dest_chain` currently holds only `60` fee-token due to a concurrent governance `pallet-host-executive::withdraw` call draining revenue, or simply because accrued fees for multiple relayers collectively exceed the host's actual balance at that moment.
3. R calls `Pallet::withdraw` with `dest_chain`. The pallet reads `available_amount = 100`, dispatches the `WithdrawalParams{ amount: 100, ... }` POST request to `HostManager`, then unconditionally sets `Fees[dest_chain][R] = 0` at `modules/pallets/relayer/src/withdrawal.rs:177`.
4. The message is delivered to `EvmHost.dispatchIncoming`, which calls `HostManager.onAccept` → `EvmHost.withdraw(WithdrawParams{amount:100,...})`, which reverts (`SafeERC20` revert / `WithdrawalFailed()`) because the host only holds `60`.
5. `dispatchIncoming` catches the revert (`success == false`), deletes `_requestReceipts[commitment]`, and returns without any effect and without surfacing the failure to Hyperbridge.
6. R's `100` fee-token entitlement is now unrecoverable: `Fees[dest_chain][R]` is `0` on Hyperbridge, and no tokens were ever transferred on `dest_chain`. [7](#0-6) [8](#0-7) [9](#0-8)

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
