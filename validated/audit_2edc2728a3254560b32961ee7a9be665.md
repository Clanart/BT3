### Title
Scanner::scan_block reports immature coinbase outputs as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including `block.txdata[0]` — the coinbase transaction. Any coinbase output paying to a script the `Scanner` is tracking is returned as a `ReceivedOutput`, indistinguishable from a normal confirmed output. Because coinbase outputs are bound by Bitcoin's 100-block maturity rule, funds reported as received are not actually spendable.

### Finding Description
`scan_transaction` matches every `tx.output` against `self.scripts` and emits a `ReceivedOutput` carrying the registered scalar `offset`, the `TxOut`, and the `OutPoint` (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` then extends the result set with *all* transactions in the block (`networks/bitcoin/src/wallet/mod.rs:221-227`), with no `tx.is_coinbase()` check and no maturity tracking.

The doc comment acknowledges the hazard ("This will also scan the coinbase transaction which is bound by maturity"), but the function still returns these outputs with full `offset`/`output`/`outpoint` populated, so any caller that consumes the `Vec<ReceivedOutput>` — e.g., to schedule a `SignableTransaction` spending them — will construct a transaction spending an immature coinbase input. Such a transaction is consensus-invalid and will be rejected by the Bitcoin network. There is no height/maturity field on `ReceivedOutput` (`networks/bitcoin/src/wallet/mod.rs:90-97`), so downstream code cannot even detect the condition from the type.

### Impact Explanation
A Bitcoin miner — an unprivileged party who can craft a coinbase transaction paying to Serai's P2TR script for dust or any amount — can cause the scanner to emit a `ReceivedOutput` that cannot be spent for 100 blocks. If the wallet layer attempts to spend it (e.g., including it as an input to a `SignableTransaction` and signing via `TransactionSignMachine` in `networks/bitcoin/src/wallet/send.rs`), the signed transaction is invalid and rejected, stalling the payout/batch pipeline and burning the threshold-signing round. This maps the CVE class (an unprivileged party causing an inconsistency in bookkeeping, leading to DoS / inability to use otherwise-valid resources) onto the scanner's output-tracking structure.

### Likelihood Explanation
Reachability is limited to miners able to win a block, and impact is bounded by the 100-block maturity window plus any scheduling/DoS effect. Additionally, the behavior is flagged in the doc comment, so a caller performing the documented post-processing is unaffected; the vulnerability is that the API itself reports unspendable funds with no marker enabling correct handling.

### Recommendation
Skip coinbase transactions in `scan_block` (e.g., iterate `block.txdata[1..]` by default), or annotate `ReceivedOutput` with the block height / an `immature` flag so callers can defer scheduling until maturity. At minimum, filter coinbase outputs at the same place the dust filter is applied in the consuming scanner loop.

    // ... coinbase tx with output { script_pubkey: script, value: 50*COIN }
    ..Default::default()

let block = Block { header, txdata: vec![coinbase, /* ... */] };

let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput for outpoint (coinbase_txid, 0)
// with offset = Scalar::ZERO — reported as received.
// Any SignableTransaction spending outputs[0].outpoint() is
