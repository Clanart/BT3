### Title
Coinbase outputs reported as received/spendable before maturity, locking Serai's Bitcoin funds — (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
`Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs` iterates over *all* transactions in a block, including `block.txdata[0]` (the coinbase), and returns any matching output as a `ReceivedOutput` indistinguishable from a normal confirmed output. Coinbase outputs are unmature for 100 blocks and cannot be spent. This is the direct analog of the Cyan bug class ("state transitions to completed while the asset remains locked"): the scanner marks value as *received* — the terminal, actionable state — while the underlying UTXO is locked by consensus rules and unusable.

### Finding Description
`scan_block` calls `scan_transaction` on every transaction in `block.txdata` without special-casing the coinbase:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
        res.extend(self.scan_transaction(tx));
    }
    res
}
```

`scan_transaction` matches solely on `output.script_pubkey` against registered offset scripts (`self.scripts.get(&output.script_pubkey)` at line 205) and has no concept of coinbase maturity. A `ReceivedOutput` produced for a coinbase output is structurally identical to a spendable one — same `offset`, `output`, `outpoint` fields (`mod.rs:90-97`) — so downstream consumers of `scan_block` cannot distinguish it.

The doc comment on `scan_block` (lines 216-220) acknowledges the hazard ("This will also scan the coinbase transaction which is bound by maturity... a post-processing pass is needed"), but the function itself performs no filtering and no maturity data is carried in `ReceivedOutput`, so nothing in the type forces the caller to honor the requirement. This mirrors the CyanPeerPlan report exactly: the "unlocked/spendable" state is reached without the resource actually being released.

### Impact Explanation
If the coinbase `ReceivedOutput` is fed into output selection for a spend plan, the constructed transaction spends an immature coinbase and will be rejected by the Bitcoin network as a consensus violation. Until the 100-block maturity elapses, the plan cannot complete — the "received" funds are effectively locked mid-plan, and any signing rounds built on that outpoint produce unbroadcastable transactions. This satisfies the "funds reported received that are not spendable" impact class. Likely Medium severity: it causes a temporary availability/lock-up of protocol funds rather than permanent loss, since the output becomes spendable after maturity.

### Likelihood Explanation
Reachable by an unprivileged party: anyone who mines a Bitcoin block (permissionless) can set the coinbase output's script to Serai's tweaked P2TR key — the scanner script is public and computable via `p2tr_script_buf`/`register_offset` from the group key. No validator collusion, leaked keys, or broken BFT is required; the trigger is purely a Bitcoin transaction appearing on-chain. The residual question is whether downstream consumers call `scan_block` vs. `scan_transaction` on `txdata[1..]` — the processor-side call site is outside the indexed in-scope crates, so end-to-end exploitation depends on that integration path using `scan_block`. If it does, likelihood is moderate; if all callers already slice off the coinbase, this reduces to a latent footgun rather than an active bug.

### Recommendation
Either exclude `block.txdata[0]` inside `scan_block` itself, or extend `ReceivedOutput` with a maturity/`is_coinbase` flag set during scanning so consumers cannot treat immature coinbase outputs as spendable. Alternatively, return coinbase matches through a separate channel so "received" never conflates mature and immature outputs.
