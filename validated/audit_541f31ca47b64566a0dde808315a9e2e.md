### Title
IBC receive-packet callback permanently locks user funds when the destination token's ERC20 contract implements USDT/Axie-style approval restrictions - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`ContractKeeper.IBCReceivePacketCallback` unconditionally calls `approve(contractAddr, amount)` on the token pair's underlying ERC20 contract from a deterministic, unowned "isolated address" every time an IBC transfer-with-callback packet is received. This is structurally the same pattern flagged in the Caviar report: an unconditional approval call is made on every invocation without checking whether an approval already exists, and the caller assumes the token's `approve` semantics are the vanilla OpenZeppelin ones. If the registered token pair's ERC20 contract instead follows a restrictive/non-standard approval pattern (e.g. requiring the allowance be reset to zero before it can be changed again, as with USDT, or reverting on a repeated identical approval as with Axie), a second callback packet using the same isolated address will revert at the `approve` call. Because the isolated address has no known private key (it is a hash-derived address, not an EOA the user controls), the tokens already escrowed there by the underlying (successful) IBC transfer become permanently unrecoverable once the accompanying callback logic can never execute again.

### Finding Description
`IBCReceivePacketCallback` derives a deterministic "isolated address" from `(destChannel, sender)` via `types.GenerateIsolatedAddress` [1](#0-0) , and requires the packet's `receiver` field to equal that address. On every packet delivery it then executes:

```go
res, err := k.evmKeeper.CallEVM(cachedCtx, erc20.ABI, receiverHex, tokenPair.GetERC20Contract(), true, remainingGas, "approve", contractAddr, amountInt.BigInt())
``` [2](#0-1) 

Two important facts:
1. The ABI used to encode/decode the call is the fixed `ERC20MinterBurnerDecimalsContract.ABI` [3](#0-2) , but the *address* the call is executed against is `tokenPair.GetERC20Contract()` — the actual, potentially externally-deployed ERC20 contract backing a "native ERC20" token pair, not necessarily one whose bytecode matches that ABI's assumed OpenZeppelin behavior.
2. The call is made unconditionally every time a callback packet targets this isolated address — there is no check of the current allowance (analogous to the missing `isApprovedForAll` check in the Caviar `EthRouter`).

If any subsequent transfer over the same channel from the same sender arrives again to the same isolated address (a normal, unprivileged, repeatable user action — nothing prevents a user/relayer from sending multiple transfer-with-callback packets on the same channel), the `approve` call is re-issued with the same operator (`contractAddr`) and a non-zero amount. For tokens that implement the well-known "approve race condition" mitigation pattern (require resetting to zero before re-approving a non-zero value, as with USDT) or an Axie-style "cannot set the same approval state twice" guard, this second `approve` reverts. `CallEVM` then returns an error, and `IBCReceivePacketCallback` returns `types.ErrAllowanceFailed` [4](#0-3) .

Per ADR-008 callback semantics used by ibc-go's callbacks middleware, a failed destination callback does not roll back the underlying token transfer itself — the transfer packet is still acknowledged as successful and the tokens remain credited to the `receiver` (the isolated address) on-chain; only the *callback execution* (moving tokens into the target contract via `cbData.Calldata`) fails. Since the isolated address is generated by hashing `(channel, sender)` with no corresponding private key (it is explicitly a non-EOA "isolated address" used purely for allowance/security isolation, per the function's own doc comments) [5](#0-4) , no one can ever manually call `approve`/`transfer` from that address to recover the funds once the callback path is permanently broken for that channel/sender pair.

### Impact Explanation
This qualifies as Critical permanent freezing/locking of user funds: any legitimate, unprivileged user who sends two or more IBC transfer-with-callback packets over the same channel to a native ERC20 token pair whose contract enforces a non-zero-to-non-zero approval restriction will have their second (and every subsequent) transferred amount become permanently stuck at an address with no known private key, with no path to move or recover it. This matches the allowed-impact category of "permanent freezing, locking, theft, or unauthorized extraction of user funds ... token-pair-backed balances."

### Likelihood Explanation
Likelihood depends on the token pair's ERC20 contract exhibiting this specific approval behavior. `x/erc20` token pairs for "native ERC20" tokens can be created for arbitrary externally-deployed contracts (subject to whatever registration policy — governance or permissionless — is configured on the chain); nothing in `IBCReceivePacketCallback` verifies the target contract's `approve` semantics match the assumed OpenZeppelin implementation. Given how common the "reset-to-zero" approval pattern is among real-world ERC20 tokens (USDT and forks) and that the finding's own seed report demonstrates an on-chain token (Axie) with even stricter behavior, this is a realistic condition for any bridged/wrapped asset with such a contract, and the trigger (sending more than one IBC-callback transfer over a channel) is entirely ordinary user behavior requiring no special privilege.

### Recommendation
Before calling `approve`, check the existing on-chain allowance from the isolated address to the target contract (e.g., via a `allowance(owner, spender)` call) and skip or adjust the approval call according to the actual semantics required — e.g., reset to zero first if a non-zero value already exists, mirroring the fix applied in the referenced Caviar mitigation (`_approveNfts` pattern: only call `approve`/`setApprovalForAll` if the current approval state differs from the desired one, and handle the "reset to zero" requirement explicitly). Additionally, consider not reusing the same non-EOA "isolated address" as an approval owner across multiple packets, or documenting/enforcing an ERC20-interface compatibility check at token-pair registration time so that only contracts with standard unrestricted `approve` behavior can be registered as callback-eligible token pairs.

### Proof of Concept
1. Register a native ERC20 token pair whose contract implements an approval guard rejecting a change from a non-zero allowance directly to another non-zero allowance without first resetting to zero (USDT-style), or an Axie-style guard rejecting setting the same approval state twice.
2. User `A` sends an IBC transfer with a destination callback targeting a contract `C`, to receiver = `GenerateIsolatedAddress(channel, A)`. `IBCReceivePacketCallback` calls `approve(C, amount1)` from the isolated address — succeeds (0 → amount1).
3. `A` sends a second IBC transfer with a callback over the same channel to the same isolated address (tokens are received/escrowed to the isolated address by the underlying, already-committed transfer). `IBCReceivePacketCallback` calls `approve(C, amount2)` from the isolated address — reverts because the allowance is already non-zero and the token requires resetting to zero first.
4. The callback returns `types.ErrAllowanceFailed`, but the transfer itself was already accepted/acknowledged; `amount2` tokens are now credited to the isolated address on-chain.
5. Since the isolated address has no private key, no future transaction can be signed from it to move, approve, or recover `amount2`; the funds are permanently locked.
