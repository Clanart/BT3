### Title
Attacker-Controlled `WWW-Authenticate` Header Spoofs GitHub-Host Classification and Triggers Sign-In Flow Bound to an Untrusted Endpoint — (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind` in `trampoline-credential-helper.ts` classifies a git credential request's host as `'enterprise'` if the credential map contains a `wwwauth[...]` entry whose value includes `realm="GitHub"`, and it does so **before** performing any real validation (no `isGitHubHost` network check, no comparison to a known GHE domain suffix). Because this header is populated from the `WWW-Authenticate` response header that git captures from the remote server being authenticated against, an attacker who controls the git server (or a proxy in front of it) fully controls this value. [1](#0-0) 

### Finding Description
`getCredential` calls `getEndpointKind(cred, store)` to decide whether to treat a request as a GitHub-flavored credential request or a generic one: [2](#0-1) 

Inside `getEndpointKind`, the classification order is: `isGist` → `isDotCom` → `isGHE` (all hostname-suffix checks, safe) → the `wwwauth[...]` header heuristic → existing-account lookup → protocol check → `isGitHubHost` (an actual network probe): [3](#0-2) 

The comment above the header check explicitly acknowledges this is a "happy path" substitute for making a verification request:
```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host without
// having to resort to making a request ourselves.
```
Because this branch returns `'enterprise'` immediately on a header match, the later network-based verification (`isGitHubHost`) is never reached for a spoofed host — the attacker's server only needs to respond to the initial authentication attempt with `WWW-Authenticate: Basic realm="GitHub"` to be classified as `'enterprise'`, regardless of hostname.

Once classified as non-`'generic'` and with no existing account matching `apiEndpoint`, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)` using the raw, attacker-chosen `endpoint` string: [4](#0-3) 

`promptForGitHubSignIn` then binds the sign-in flow's target origin directly to that endpoint — for any hostname other than the literal string `github.com`, it invokes `beginEnterpriseSignIn` and `setSignInEndpoint(origin)` using the attacker-controlled `origin`: [5](#0-4) 

This launches the full Enterprise sign-in UI/OAuth-or-basic-auth flow scoped to the attacker's chosen origin, and any resulting `Account` is stored keyed by that same endpoint (via `credWithAccount`/the sign-in store), i.e., the endpoint the user is prompted to authenticate against is exactly the attacker-controlled string, not something validated against a known-good GitHub/GHE identity.

### Impact Explanation
An attacker who controls a git remote (or a MITM/proxy in front of one) that Desktop is fetching/cloning from can force Desktop to display its native "Sign in to GitHub Enterprise" dialog for an arbitrary hostname, purely by returning a crafted `WWW-Authenticate: ... realm="GitHub"` header on an HTTP 401 during the git authentication handshake — no real GHE/GitHub software needs to run on that host, and no prior validation (`isGitHubHost`) is performed in this branch. This turns an otherwise inert git-fetch/clone action into an unprompted trigger for Desktop's sign-in UI bound to an attacker-chosen origin, which can be leveraged for credential-phishing (if the enterprise sign-in flow falls back to Basic Auth for hosts that don't support OAuth, whatever the user types would be sent to the attacker's server) and improperly binds any resulting `Account`/token to that attacker-controlled endpoint string in the account store.

### Likelihood Explanation
The trigger only requires the attacker to control the git server's HTTP responses (explicitly in-scope: "remote/proxy response") and does not require any unnatural user action beyond a normal `git fetch`/`clone` that Desktop already performs; once the sign-in dialog appears, ordinary user behavior (entering their real credentials for what they believe is a legitimate GHE sign-in prompt initiated by Desktop) completes the flow.

### Recommendation
Do not trust the `wwwauth[...]` "realm" header value as sufficient proof of a GitHub-flavored host. Either remove this heuristic or gate it behind the same `isGitHubHost` network verification used later in the function (query the candidate host's `/meta` or equivalent well-known GitHub API signature) before returning `'enterprise'`, and clearly surface the actual target hostname/origin in the sign-in dialog so users can recognize a mismatched or unexpected host before entering credentials.

### Proof of Concept
1. Set up a malicious HTTPS git server that, on the initial unauthenticated `git-upload-pack`/`git-receive-pack` request, responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Add this server as a remote in Desktop (e.g. `https://evil-corp-git.example.com/repo.git`) and trigger a fetch/clone.
3. Git forwards the captured `wwwauth[0]` value to Desktop's credential helper via `createCredentialHelperTrampolineHandler('get', ...)`.
4. In `getEndpointKind`, the header match (`realm="GitHub"`) causes an immediate `'enterprise'` classification, bypassing the `isGitHubHost` network check.
5. `getCredential` finds no existing account for `evil-corp-git.example.com` and calls `ui.promptForGitHubSignIn('https://evil-corp-git.example.com')`.
6. `promptForGitHubSignIn` calls `beginEnterpriseSignIn` and `setSignInEndpoint('https://evil-corp-git.example.com')`, presenting Desktop's native Enterprise sign-in dialog scoped to the attacker's host.

Note: I was unable to fully trace `sign-in-store.ts` and the downstream Basic-Auth/OAuth negotiation logic within the available investigation budget to confirm whether the resulting flow always requires a real OAuth handshake (limiting impact to a spoofed-UI/phishing surface) or can fall back to submitting raw Basic-Auth credentials to the attacker's server; this distinction affects whether the impact is "phishing-UI trigger" vs. direct "credential exfiltration," and should be verified in a full session with repository access.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
