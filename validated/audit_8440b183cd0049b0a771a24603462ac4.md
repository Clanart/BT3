## Binding being tested

The code assumes: `xonly_pk parsed from get_first_op_return_output(payout_tx)` == `xonly_pk of the operator who actually funded/broadcast that payout_tx`. I traced this binding through `Verifier::update_finalized_payouts` and found it is **not enforced anywhere** — the OP_RETURN content is unauthenticated, self-declared data, and the transaction's malleability under `SinglePlusAnyoneCanPay` lets a third party rewrite it before confirmation.

## Trace

`create_payout_txhandler` builds the payout tx with the user's payout output at index 0, an anchor at index 1, and the operator's self-declared xonly-pk OP_RETURN at index 2 [1](#0-0) . The only committed data is the withdrawal input plus output 0, per `TapSighashType::SinglePlusAnyoneCanPay` verified in `Operator::withdraw` [2](#0-1) . `ANYONECANPAY` leaves every other input unauthenticated, and `SIGHASH_SINGLE` leaves every output except index 0 unauthenticated — including the anchor and OP_RETURN outputs. Any party who observes this unconfirmed transaction (mempool, RBF broadcast, or a race against propagation) can reuse the same input+signature in a transaction it fully constructs itself: same output 0, but arbitrary additional inputs and an arbitrary OP_RETURN inserted before the real one.

On confirmation, `update_finalized_payouts` calls `get_first_op_return_output`, which does a plain `.find()` over outputs in order with no signature or ownership check [3](#0-2) , then `parse_op_return_data` extracts whatever bytes are there [4](#0-3) , and this result is stored as `payout_payer_operator_xonly_pk` unconditionally [5](#0-4) .

This DB field then drives two automated, unauthenticated consumers:
- `PayoutCheckerTask::run_once` on **every** operator polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, if a match is found, automatically calls `handle_finalized_payout` and eventually sends its own kickoff — with no check that this operator actually funded the payout [6](#0-5) .
- `Verifier::is_kickoff_malicious` compares the DB-stored `operator_xonly_pk` to `kickoff_data.operator_xonly_pk` of whoever submits the kickoff [7](#0-6) .

Because the framed operator's own automation self-generates a kickoff with its own key, the comparison in `is_kickoff_malicious` **matches** (both sides equal the framed operator's key), so no challenge/disprove is ever triggered — the "collateral burn via Disprove" outcome claimed in the question does **not** occur. Instead, two different Critical outcomes occur:
- The real funding operator's own `PayoutCheckerTask` filters `WHERE payout_payer_operator_xonly_pk = <self>`; since the DB now attributes the payout to the attacker-chosen victim, the real funder never finds this withdrawal and is **permanently unable to claim reimbursement** for a payout it legitimately made.
- The framed victim operator's automation, finding the (bogus) attribution to itself, automatically builds and sends a kickoff and is ultimately **reimbursed with bridge collateral for a payout it never made**.

`Verifier::is_deposit_valid`, `SECP.verify_schnorr`, and the storage-proof/SPV checks only validate that output 0 pays the correct user/amount; none of them bind the OP_RETURN xonly-pk to a real signer.

### Title
Unauthenticated, malleable payout OP_RETURN lets a third party hijack payer attribution and redirect reimbursement to an uninvolved operator - (File: core/src/verifier.rs, circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`get_first_op_return_output`/`parse_op_return_data` treat the first OP_RETURN push in a confirmed payout transaction as ground truth for "which operator funded this withdrawal," but that data is never signed: the payout tx's `SinglePlusAnyoneCanPay` signature covers only the withdrawal input and output 0, leaving every other input/output (including the OP_RETURN) freely rewritable by any third party before confirmation. This lets an attacker redirect the `payout_payer_operator_xonly_pk` DB field to an arbitrary operator.

### Finding Description
Binding assumed: `xonly_pk(get_first_op_return_output(payout_tx))` == `xonly_pk of operator who funded payout_tx`. This is broken because (a) the operator's payout tx signs only input 0 and output 0 under `SinglePlusAnyoneCanPay` [8](#0-7) , and (b) `get_first_op_return_output` blindly takes the first OP_RETURN by output order with no ownership/signature check [3](#0-2) . An attacker constructs/broadcasts a competing (or replacement) transaction reusing the withdrawal input and its signature, but supplying its own funding inputs and outputs after index 0, including a spoofed OP_RETURN naming any public operator xonly-pk before/instead of the legitimate one. Once mined, `update_finalized_payouts` persists that attacker-chosen key as `payout_payer_operator_xonly_pk` [9](#0-8) . Downstream: the real funder's `PayoutCheckerTask` never sees this withdrawal (its `WHERE payout_payer_operator_xonly_pk = self` filter no longer matches) [10](#0-9) , and the framed operator's own `PayoutCheckerTask` picks it up and auto-generates a matching kickoff, which passes `is_kickoff_malicious`'s pubkey-equality check since both sides now reflect the framed operator's own key [7](#0-6) , so it is reimbursed for a payout it never made.

### Impact Explanation
Two Critical outcomes per attempt: (1) the legitimate funding operator becomes permanently unable to claim reimbursement for real work performed (its automated lookup keyed on its own xonly-pk no longer finds the withdrawal); (2) an uninvolved operator's automation is deceived into sending a kickoff and receiving bridge collateral reimbursement for a withdrawal it never funded. This is repeatable against any operator xonly-pk (all are public) for any withdrawal, and does not require verifier/

    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,

            DEFAULT_SEQUENCE,

        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
