## Confirmed finding

### Title
Untrusted-directory check is not re-applied to submodules pulled in by `git submodule update --init --recursive`, allowing hook execution from a submodule owned by another user - (File: `app/src/lib/git/submodule.ts`)

### Summary
Desktop gates a top-level repository's git operations behind an explicit "Trust Repository" prompt when `getRepositoryType()` reports the directory as `unsafe` (owned by another user), surfaced in `AddExistingRepository`/`MissingRepository` and resolved by calling `addSafeDirectory()`. [1](#0-0)  That check, however, is performed once, at the top-level repository path, at add/locate time. It is never re-applied to the individual submodule directories that `updateSubmodulesAfterOperation` materializes via `git submodule update --init --recursive` after every checkout, pull, or clone. [2](#0-1) [3](#0-2) 

### Finding Description
This mirrors the report's broken invariant: `validatePostExecutorTransaction()` re-verifies one named entity (the executor plugin module) but not the full, dynamic set of similarly-powerful entities (all modules), so an attacker can "sneak in" an unchecked module. In Desktop, the equivalent trusted/untrusted state is *directory ownership* (Git's `safe.directory`), and the "entity class" being validated is *git repositories on disk that Desktop will run git commands against and whose hooks may execute*.

- The trust check (`getRepositoryType` → `unsafe` kind) is only invoked against `repository.path`, the top-level clone/working directory, in `AddExistingRepository.validatePath` and `MissingRepository.updateUnsafePathState`. [4](#0-3) 
- `updateSubmodulesAfterOperation` runs `git submodule update --init --recursive` directly against `repository.path` for every checkout/pull/clone, with no equivalent unsafe-directory validation performed on the submodule paths it creates/updates. [5](#0-4) 
- Nothing in `checkoutBranch`/`checkoutCommit` re-checks trust before or after calling `updateSubmodulesAfterOperation`. [6](#0-5) 

Git itself enforces `safe.directory` per-repository (including submodules), so a submodule whose resulting directory is "owned by another user" (e.g. it lives on a mapped network share, or was extracted/created with different ownership metadata) would normally cause *that submodule's* git invocation to refuse to run. But because Desktop already trusted the parent repository once (adding it to `safe.directory` via `addSafeDirectory`), and because Desktop performs no analogous per-submodule trust re-validation or user prompt, any submodule content is treated as implicitly trusted by the app's UX flow the moment the parent was trusted — there is no code path in `submodule.ts` or `checkout.ts` that inspects submodule ownership independently and asks the user to confirm trust for it the way `AddExistingRepository`/`MissingRepository` do for the top-level path.

### Impact Explanation
If an attacker can get a user to add/clone a repository whose `.gitmodules` references a submodule path that resolves to a location with different effective ownership (e.g., a symlinked path, a mounted/shared volume, or a path a previous "add existing repository" operation already registered with different ownership semantics), Desktop's submodule update proceeds without the same friction/verification gate that protects the top-level repo. Since submodules can carry their own `.git` directory with `core.hooksPath` / hook scripts, this can lead to hook execution in a context the user was never asked to "trust," undermining the entire purpose of the unsafe-directory feature (`changelog.json` #14336 — "provide a way to trust repositories not owned by the current user"). 

### Likelihood Explanation
Requires a specific but realistic setup: a submodule path pointing at directories with mixed ownership (common on shared/mounted drives, extracted archives, or CI-shared checkout roots) combined with the user already having trusted the parent repo. No local/physical access or prior malware is needed beyond controlling the repository content (`.gitmodules`) and the ability to influence where the submodule directory resolves to — the same class of attacker assumed valid by the report (repository content controller).

### Recommendation
Apply the same unsafe-directory detection (`getRepositoryType`) to each submodule path before/after `git submodule update --init --recursive`, and surface the existing "Trust Repository" prompt for any submodule reported as `unsafe`, rather than relying solely on the one-time top-level trust decision.

### Proof of Concept
Not independently verified against a live submodule-ownership scenario in this pass — I was unable to execute git locally to confirm that `git submodule update --init --recursive` actually surfaces or swallows a `safe.directory`/dubious-ownership error differently than top-level checkout, or to confirm whether `performFailableOperation`/error handling in `app-store.ts` would silently absorb such an error. This should be validated by:
1. Creating a repository with a submodule pointing to a path with different filesystem ownership metadata (or simulate via a mounted share).
2. Adding the parent repo in Desktop and trusting it via `onTrustDirectory`.
3. Triggering a checkout/pull that runs `updateSubmodulesAfterOperation`, and observing whether Desktop prompts a second trust dialog for the submodule or silently proceeds/fails without the user-facing warning shown in `MissingRepository`/`AddExistingRepository`.

  private async validatePath(path: string): Promise<boolean> {
    if (path.length === 0) {
      this.setState({
        isRepositoryBare: false,
        showNonGitRepositoryWarning: false,
      })
      return false
    }

    const type = await getRepositoryType(path)

    const isRepository = type.kind !== 'missing' && type.kind !== 'unsafe'
    const isRepositoryUnsafe = type.kind === 'unsafe'
    const isRepositoryBare = type.kind === 'bare'
    const showNonGitRepositoryWarning = !isRepository || isRepositoryBare
    const repositoryUnsafePath = type.kind === 'unsafe' ? type.path : undefined

    this.setState(state =>
      path === state.path
        ? {
            isRepositoryBare,
            isRepositoryUnsafe,
            showNonGitRepositoryWarning,
            repositoryUnsafePath,
          }
        : null
    )

    return path.length > 0 && isRepository && !isRepositoryBare
  }
