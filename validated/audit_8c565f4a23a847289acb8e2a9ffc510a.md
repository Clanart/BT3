### Title
Missing empty-outputs check in `placeOrder` lets a solver drain escrowed inputs for free via zero-output same-chain fills - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` only enforces `order.inputs.length > 0`; it never rejects `order.output.assets.length == 0`. An order with escrowed inputs but zero declared outputs can still be filled through `_fillSameChain`, which computes `isFullyFilled` starting at `true` and never sets it to `false` because its per-output loop has nothing to iterate. The fill therefore proceeds straight to full-escrow withdrawal without the solver providing any output tokens.

### Finding Description
This is the same bug class as the external report: a downstream consumer function silently accepts a degenerate empty array because the producing/setter function (`placeOrder`) does not enforce the invariant that the array must be non-empty.

- `placeOrder` checks `order.inputs.length == 0` but has no equivalent check on `order.output.assets.length` [1](#0-0) .
- Any address (the order creator or a colluding “solver”) can therefore submit an `Order` with non-empty `inputs` (escrowed tokens) and an empty `output.assets` array.
- When such an order is filled via `_fillSameChain`, `outputsLen = 0`, so the `for` loop over outputs is skipped entirely; `isFullyFilled` stays at its initialized value `true` [2](#0-1) .
- Execution proceeds to build a `WithdrawalRequest` covering the full escrowed input amounts and calls `_withdraw(body, false, true)`, finalizing the order and transferring 100% of escrow to `msg.sender`, the caller of `fillOrder` [4](#0-3) .
- `_withdraw` performs no cross-check that any output tokens were ever delivered to the beneficiary — it purely trusts `isFullyFilled` and the withdrawal token list built from escrow records [5](#0-4) .

The user could self-place an order with empty outputs and immediately self-fill it, or (worse) an attacker could get a naive off-chain matching/relaying flow to sign/attest to a zero-output order, then call `fillOrder` to redeem the escrow without providing any consideration. Because no invariant in `placeOrder` prevents `output.assets.length == 0`, and no invariant in `_fillSameChain`/`_withdraw` requires `outputsLen > 0` before finalizing, the escrow-for-consideration guarantee of the intent-settlement flow is broken.

### Impact Explanation
This directly matches "stealing or loss of funds" and "logic attacks" in the bounty scope. A user's escrowed input tokens can be extracted without the counterparty ever delivering the promised output, defeating the entire escrow/settlement guarantee of the same-chain Intent Gateway. Because the same `Order`/`PaymentInfo` structures and gateway logic are shared between `IntentGatewayV2.sol` and `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`, a similar path should be checked for the cross-chain fill flow as well (the cross-chain path may be protected by `RedeemEscrow` message flow bindings, but that was not fully confirmed in this pass given tool-call limits).

### Likelihood Explanation
The path is reachable by any unprivileged externally-owned account: crafting an `Order` with a non-empty `inputs` array and an empty `output.assets` array requires no special permission, no relayer/prover/governance participation, and no malformed proof. `placeOrder` and `fillOrder` are both public entry points. The only friction is that the order creator must be the one to place the zero-output order (or be tricked into signing one), but a self-serving attacker can trivially place such an order themselves and immediately call `fillOrder` on it to reclaim their own escrow — this doesn't drain other users' funds directly, but it does show the missing invariant lets `isFullyFilled` become vacuously true, and the underlying validation gap is a real defect that a background engineer should confirm doesn't compose with other flows (e.g., session/solver-selection signing where a user might sign approval for output amounts that could be set to zero-length independently of what was actually agreed).

### Recommendation
Add a check in `placeOrder` (both `evm/src/apps/IntentGatewayV2.sol` and the Tron variant `evm/tron/contracts/apps/IntentGatewayV2.sol`) rejecting `order.output.assets.length == 0`, mirroring the existing `if (order.inputs.length == 0) revert InvalidInput();` guard. Additionally, harden `_fillSameChain` in `evm/src/apps/intentsv2/IntrinsicIntents.sol` to explicitly revert when `outputsLen == 0`, rather than relying solely on the upstream check — following the same "defense in depth" recommendation as the original report (enforce at both the setter and the consumer).

### Proof of Concept
1. Attacker (or any user) calls `placeOrder(order, graffiti)` with `order.inputs = [{token: USDC, amount: 1000e6}]` and `order.output.assets = []` (empty array), paying/approving 1000 USDC to be escrowed. This succeeds because only `inputs.length == 0` is checked [1](#0-0) .
2. Attacker (as `msg.sender`, acting as "solver") calls `fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: []}))`.
3. Inside `_fillSameChain`, `outputsLen = 0`; the for-loop body never runs; `isFullyFilled` remains `true` [6](#0-5) .
4. `_withdraw` is invoked with the full escrowed `1000 USDC` and finalizes the order, transferring escrow to `msg.sender` with no output ever delivered [5](#0-4) .

Note: this PoC demonstrates self-fill of a self-placed zero-output order, which mainly proves the missing invariant rather than a direct third-party fund theft; a background engineer should verify whether any signing/matching flow (e.g., off-chain solver bidding, `select`/`SolverAccount`) could allow an attacker to induce a victim to place or approve a zero-output order, which would elevate this into direct third-party fund loss.
