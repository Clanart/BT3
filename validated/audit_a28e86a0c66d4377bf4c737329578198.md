## Title
DataLayer mirror URLs allow any coin owner to inject arbitrary server addresses that the local node automatically fetches via HTTP, enabling SSRF against internal/local network services - (File: chia/data_layer/data_layer.py, chia/wallet/db_wallet/db_wallet_puzzles.py, chia/data_layer/download_data.py)

### Summary
DataLayer's mirror mechanism lets any wallet create a `MIRROR_PUZZLE_HASH` coin whose memo encodes an arbitrary `launcher_id` plus a list of URLs [1](#0-0) . `create_new_mirror` builds this coin purely from user-supplied `launcher_id`/`urls` with no proof that the caller owns or controls the referenced singleton/store [1](#0-0) . These mirror records are later read back by `get_mirrors_for_launcher`/`dl_get_mirrors` and turned into subscription server URLs consumed by `update_subscriptions_from_wallet`, which strips only the trailing slash before storing them as fetchable server entries [2](#0-1) . During the periodic sync loop, `fetch_and_validate` randomly selects one of these attacker-influenced URLs and performs a direct HTTP GET against it via `http_download` (`session.get(server_info.url + "/" + filename, ...)`) with no allow-list, scheme restriction, or private-network filtering [3](#0-2) [4](#0-3) . This is structurally the same bug class as kodbox's `cover` SSRF: a network fetch is driven by an attacker-controlled "path"/URL value with no server-side restriction on destination.

### Finding Description
Any chain participant can spend XCH to create a mirror coin for **any** DataLayer `launcher_id`, including stores they do not own, since `create_new_mirror` only creates a `CreateCoin` with the mirror puzzle hash and a memo `[launcher_id, *urls]` — it performs no singleton-ownership check [1](#0-0) . The DataLayer service treats all such mirrors for a subscribed/owned store as legitimate download servers: `update_subscriptions_from_wallet` pulls `mirror.urls` for the `store_id` and feeds them straight into `DataStore.update_subscriptions_from_wallet` as new server entries [2](#0-1) . `periodically_manage_data`/`update_subscription` then calls `fetch_and_validate`, which iterates `servers_info` (built from these attacker-supplied URLs) and issues raw HTTP requests through `http_download`/`download_file` without validating the URL's host, scheme, or target network [3](#0-2) [5](#0-4) [4](#0-3) . Consequently, an attacker (no special privilege, just able to broadcast a spend bundle creating a mirror coin) can force any node that subscribes to or owns that store to send outbound HTTP requests to attacker-chosen hosts — including internal/loopback/cloud-metadata addresses — mirroring the "manipulation of the argument path leads to SSRF" pattern in the CVE.

### Impact Explanation
This qualifies as a concrete spend-triggered SSRF: an unprivileged spend-bundle submitter can cause a victim's DataLayer node to make outbound requests to arbitrary hosts (internal services, cloud metadata endpoints, etc.) merely by broadcasting a coin spend that creates a mirror coin referencing the victim's tracked/owned store. It does not directly cause coin-set divergence or fund loss, but it does allow a spend-triggered request to reach internal network endpoints from a node process, which can be leveraged for internal reconnaissance/attack pivoting and denial-of-service against the DataLayer sync loop (repeated failed connections/timeouts). The `MaxDeltaFileSizeExceededError`/timeout handling reduces some resource-exhaustion risk but does not restrict destination.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to know a target's tracked/owned `launcher_id` (fully public on-chain), pay the mirror-coin fee, and the target's DataLayer instance must have `manage_data_interval` sync active and either be subscribed to or own that store, or be configured with `auto_subscribe_to_local_stores` — a normal operating configuration for many DataLayer users. No special authorization or existing relationship with the victim is required.

### Recommendation
Validate or restrict mirror URLs before treating them as fetch targets: enforce scheme allow-listing, resolve/validate destination IPs (reject loopback/link-local/private ranges unless explicitly configured), and/or restrict mirror creation for a `launcher_id` to only the coin(s) demonstrably tied to that singleton's current owner. At minimum, apply the same SSRF-hardening pattern used for other outbound fetch paths (plugin/S3 downloader) to `http_download`/`fetch_and_validate`.

### Proof of Concept
1. Identify a public DataLayer `launcher_id` known to be tracked/owned by a victim node (store IDs are public on-chain).
2. Using any wallet, call `dl_new_mirror` (`DLNewMirror(launcher_id=<victim_store_id>, amount=..., urls=["http://169.254.169.254/latest/meta-data/"], fee=..., push=True)`), which is exposed via `chia/wallet/wallet_rpc_api.py::dl_new_mirror` and reachable by any wallet RPC caller/CLI (`chia data add_mirror`) [6](#0-5) [7](#0-6) .
3. Once the spend confirms, the victim's `DataLayer` service (subscribed/owning that store) calls `update_subscriptions_from_wallet`, ingesting the attacker's URL as a server entry [2](#0-1) .
4. On the next sync cycle, `fetch_and_validate` selects that server and `http_download` issues `GET http://169.254.169.254/.../<filename>` from the victim node [3](#0-2) [4](#0-3) , confirming the SSRF.

**Uncertainty note:** I could not fully trace the exact coin-scan/ingestion path that populates the wallet-side `mirrors` DB table from on-chain mirror coins (i.e., whether `DataLayerWallet` cross-checks the mirror coin's spender/owner against the singleton's current owner puzzle before persisting it) due to index truncation of `data_layer_wallet.py`. If such a check exists and rejects mirrors not created by the current singleton owner, the described SSRF would be mitigated to only apply to legitimate store owners' own mirrors (self-SSRF, lower severity). This should be verified directly in `chia/data_layer/data_layer_wallet.py` (mirror coin-state handling) before treating this as fully confirmed.

async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
            progress_byte = 0
