Found it: `onGetResponse` in `ExtrinsicIntents.sol` is the direct local analog to the "unchecked remaining_accounts length" bug — it indexes into an attacker/relayer-influenced response array without validating its length, just like the vault code indexed into `remaining_accounts` without validating its size.

### Title
Unchecked `response.values` length in `onGetResponse` allows array-bounds assumptions to be violated, mirroring the missing-length-check knock-in bug - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
### Finding Description
`_cancelFromSource` dispatches a `DispatchGet` with exactly one storage key (`keys[0]`), and the corresponding `onGetResponse` handler assumes the returned `response.values` array has at least one element and that `values[0]` corresponds to that single key: [1](#0-0) [2](#0-1) 

```solidity
function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
    if (incoming.response.values[0].value.length != 0) revert Filled();
    WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
    _withdraw(body, true, true);
}
```

This is structurally identical to the CEGA bug: the vault code indexed into `remaining_accounts` (a caller/relayer-supplied array) assuming it had the right shape, and when the assumption didn't hold, the code fell through to the "safe for the attacker" branch (full payout instead of the knock-in-adjusted payout). Here, the correctness of the entire cancellation/refund decision hinges on `values[0]` being *the* value for the `_filled[commitment]` slot that was actually queried. There is no on-chain check that `incoming.response.values.length == 1` nor that `values[0]` corresponds to the key this contract dispatched — the code implicitly trusts that the GET response returned by Hyperbridge's message-handling pipeline preserves a 1:1, order-correct mapping between the single dispatched key and `values[0]`.

`GetResponse` values are populated upstream by `modules/ismp/core/src/handlers/response.rs`, one `StorageValue` per key in `request.keys`, in key order: [3](#0-2) 

Because the source-chain dispatch always sends exactly one key, this path is normally safe in the honest case. However, `onGetResponse` performs no defensive validation of `incoming.response.values.length` or that `incoming.response.request.keys` matches what `_cancelFromSource` actually dispatched (it only trusts `context`, which is arbitrary calldata decoded via `abi.decode` and never checked against the number of keys/values delivered). If any code path in the message pipeline (present or future — e.g. a batching/optimization change to `GetResponseMessage`/`GetResponseLeaf` handling in `HandlerV2.sol`, or a bug in how responses are packed for multi-key or batched delivery) ever produces a `values` array with a different length or ordering than the corresponding `keys` array, `values[0]` could be empty (or non-corresponding) even though the order *was* actually filled — silently satisfying `revert Filled()`'s negation and calling `_withdraw`, refunding escrow to the user while the solver who legitimately filled the order already received nothing back and the destination-side `_filled[commitment]` was actually set.

### Impact Explanation
If `values[0]` can be decoupled from the actual state of the queried `_filled[commitment]` slot (due to any indexing/ordering mismatch introduced upstream), an attacker or the order owner can trigger `_withdraw(body, true, true)` — refunding the escrowed input tokens to `order.user` — for an order that was already filled on the destination. This is a direct double-payment: the solver already delivered output tokens to the beneficiary and is owed the escrow via `RedeemEscrow`, and the user would *also* receive the refund via `RefundEscrow`/`onGetResponse`, resulting in loss of protocol/solver funds (the same "false negative on knock-in" pattern from the CEGA report — the missing array-shape validation causes the code to take the branch that pays out fully to the wrong party).

### Likelihood Explanation
The exploitability of this issue is contingent on the response-value array actually becoming misaligned with the query keys, which is not directly triggerable by an unprivileged attacker against the current single-key dispatch and current `handlers/response.rs` implementation (which is 1:1, key-ordered). It is a latent/defense-in-depth gap rather than a fully self-contained live exploit; I could not find a concrete, current on-chain path where an ordinary user or relayer can force `values.length != keys.length` or reorder values without collusion from a malicious relayer/prover (which is explicitly out of scope). I flag this with lower confidence than a fully provable end-to-end exploit and recommend it primarily on the basis that the code lacks the same defensive invariant that the CEGA report identified as missing (validate array shape/length before trusting index-0), and any future protocol change to batch/optimize `GetResponse` delivery would silently reintroduce the CEGA-class bug here with no compile-time or runtime guard to catch it.

### Recommendation
Add an explicit length check in `onGetResponse` (and the Tron variant `evm/tron/contracts/apps/IntentGatewayV2.sol:729`) before indexing:
```solidity
if (incoming.response.values.length != 1) revert InvalidResponseLength();
if (incoming.response.values[0].value.length != 0) revert Filled();
```
Additionally consider validating `incoming.response.request.keys.length == 1` and that the key matches the one derivable from `body.commitment` via `_calculateCommitmentSlotHash`, rather than trusting `context` and positional indexing alone — this closes the same class of gap the CEGA remediation applied (validate array length/shape against the expected, request-derived value before using it to decide the payout branch).

### Proof of Concept
Not independently reproducible against the current codebase as a standalone unprivileged exploit — this analog can only be triggered by a discrepancy between the queried key(s) and the delivered `values` array, which requires either a future protocol change to GET-response batching/packing or a compromised/malicious relayer supplying a malformed `GetResponse` before it reaches `onGetResponse`, both aligned with the CEGA bug's "array shape not checked" root cause but not directly demonstrable end-to-end with only the current single-key path and the current `handlers/response.rs` 1:1 key-to-value mapping.
