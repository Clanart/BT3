### Title
Arbitrary Command Execution via `ext::`/`fd::` Git Transport Helper in Malicious Fork's `clone_url` when Opening a Pull Request Deep Link - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_findPullRequestBranch` takes an untrusted `headCloneUrl` string that originates from a pull request's head-repository `clone_url` field (fetched from the GitHub API via a deep link `x-github-client://openRepo/...?pr=...`) and passes it, unvalidated, into `addRemote` and subsequently `git fetch`. Git supports the `ext::` and `fd::` "remote helper" URL schemes, which execute an arbitrary shell command as the transport. Because there is no scheme allow-list anywhere along this path, a malicious fork owner can set their repository's clone URL (via GitHub API impersonation, or by crafting a PR head repo whose `clone_url` is attacker-influenced) to something like `ext::sh -c "calc"%20` and have Desktop execute it when the user opens a PR deep link that this code path handles.

### Finding Description
- `openPullRequestFromUrl` (deep link handler) leads into `_checkoutPullRequest` → `_findPullRequestBranch` in `app/src/lib/stores/app-store.ts`, receiving `headCloneUrl` straight from the API PR object. [1](#0-0) 
- Inside `_findPullRequestBranch`, if no existing remote matches the URL, Desktop calls `addRemote(repository, forkPullRequestRemoteName(headRepoOwner), headCloneUrl)` with the raw, attacker-supplied string. [2](#0-1) 
- `addRemote` in `app/src/lib/git/remote.ts` does zero validation of the URL — it directly forwards it as an argv element to `git remote add name url`. [3](#0-2) 
- The remote is then fetched via `_fetchRemote`, which will invoke `git fetch` against that remote and trigger Git's own URL-scheme dispatch, including `ext::`/`fd::` remote helpers that spawn an arbitrary command. [4](#0-3) 
- `envForRemoteOperation`/`envForProxy` in `app/src/lib/git/environment.ts` only special-case `http(s)://` URLs for proxy resolution; there is no `GIT_ALLOW_PROTOCOL`, `GIT_PROTOCOL_FROM_USER`, or explicit scheme allow-list set anywhere in the invocation chain to restrict Git to safe transports (git/http/https/ssh). [5](#0-4) 
- A repo-wide search for any such protocol restriction (`GIT_ALLOW_PROTOCOL`, `ext::`, `fd::`) returned no matches, confirming there is no mitigating control present in this codebase.

Since `git remote add` and `git fetch` are invoked through argv (not a shell), classic shell-metacharacter injection into the OS shell is not the mechanism — the actual sink is Git's own transport-helper URL scheme (`ext::<command>`), which Git itself will exec via `/bin/sh -c` once a fetch/push targets that remote. This is the documented "ext transport" issue class that has affected multiple Git GUIs and is why Git strongly discourages accepting untrusted remote URLs without an allow-list, and why upstream Git added `GIT_ALLOW_PROTOCOL` / `protocol.allow` config for exactly this purpose.

### Impact Explanation
If exploitable, this results in full arbitrary command execution on the victim's machine under the Desktop app's user context — the highest possible impact (RCE), including potential credential/token exfiltration and workstation compromise, once the user follows a PR deep link (or automatic PR checkout flow) pointing to a PR whose fork/head `clone_url` is attacker-controlled.

### Likelihood Explanation
The likelihood is dependent on: (1) whether the GitHub API actually allows a fork's `clone_url` field to contain a non-`https://`/`git://`/`ssh://` value such as `ext::...`, and (2) whether `urlMatchesRemote` short-circuits and prevents `addRemote` from ever being called for non-conforming URLs before reaching the sink. I could not verify in this pass whether the GitHub API server-side validates/rejects non-standard clone_url schemes for repository objects (this is typically enforced server-side by GitHub.com, which would make the "attacker controls clone_url" precondition unreachable in practice for github.com-hosted repos, though it may be more feasible against GitHub Enterprise instances with custom API responses, or via a compromised/spoofed API response). This precondition (whether GitHub's API can be made to emit an attacker-chosen `clone_url` scheme) is the key uncertainty and should be validated with a proof-of-concept unit test against `addRemote`/`_fetchRemote` as suggested, and ideally against a live/staged API response, before treating this as fully exploitable end-to-end.

### Recommendation
- Validate the `clone_url` (and any other remote URL sourced from the GitHub API or deep links) against an explicit allow-list of schemes (`https:`, `http:`, `ssh:`, `git:`) before calling `addRemote`/`setRemoteURL`.
- Set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or use `--allow-unrelated-histories`-style explicit protocol config via `-c protocol.allow=never` plus per-protocol `protocol.<name>.allow=always`) in the environment used for all remote-invoking git commands, e.g., in `envForRemoteOperation` in `app/src/lib/git/environment.ts`, so that Git itself refuses `ext::`/`fd::`/`file::`-style transport helpers regardless of caller validation.
- Apply the same URL validation/allow-list to any other code path that takes a remote URL from untrusted API data (clone flows, upstream remote setup, etc.).

### Proof of Concept
1. Craft (or mock the API response for) a pull request whose head repository `clone_url` is `ext::sh -c "touch /tmp/pwned"`.
2. Trigger `openPullRequestFromUrl` via a crafted deep link `x-github-client://openRepo/https://github.com/owner/repo?pr=1`, or directly unit test:
```ts
// app/src/lib/git/remote.ts
await addRemote(repository, 'test-remote', 'ext::sh -c "touch /tmp/pwned"')
await fetchRemote(repository, { name: 'test-remote', url: 'ext::sh -c "touch /tmp/pwned"' }, FetchType.UserInitiatedTask)
```
3. Observe that `git remote add` succeeds without any validation error, and confirm whether the subsequent `git fetch` invokes the `ext::` helper and executes the shell command (this final step is the one to confirm experimentally, since Git version/build-time configuration can disable `ext::` transport by default in some distributions).
