### Title
Relayer fee payout uses the *current* `feeToken()` instead of the token the fee was escrowed in, allowing mis-denominated payouts after a fee-token migration - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the closest local analog of the "stale cached value used after governance updates it" bug class from the report. `EvmHost` records a relayer's fee amount in `FeeMetadata.fee` when a request is dispatched, but only checks *which* token that amount is meant to be paid from at claim time — by calling the live `feeToken()` getter — never storing (or re-validating) the token the fee was actually escrowed in. `updateHostParamsInternal` attempts to guard against changing `feeToken` while outstanding fees exist, but the guard only inspects the *contract's current balance* of the old token, not the actual set of pending `_requestCommitments`. Because `withdraw()` lets governance drain the entire balance of any token (including the old fee token) independent of outstanding commitments, the guard can be neutralized by ordinary governance operations, after which a stale `FeeMetadata.fee` value gets paid out in the new fee token.

### Finding Description
`EvmHost` stores relayer fees per commitment: [1](#0-0) 

When a GET response is delivered, the relayer fee is paid from the *live* `feeToken()`, not from whatever token was configured when the request was dispatched: [2](#0-1) 

`updateHostParams`/`updateHostParamsInternal` is the only guard against changing the fee token while value is still owed in the old one, and it is restricted to `hostManager` (i.e., governance) as intended: [3](#0-2) [4](#0-3) 

That guard only checks `IERC20(oldFeeToken).balanceOf(address(this)) != 0`. It has no knowledge of `_requestCommitments` state, and `withdraw()` — the sibling `IHostManager` function, also `hostManager`-restricted — can freely move the entire balance of any token (including the old `feeToken`) out of the contract with no accounting against pending commitments: [5](#0-4) 

Sequence that breaks the invariant "each escrowed fee is paid in the token it was escrowed in":
1. Requests are dispatched while `feeToken = TokenA`; their `fee` amounts are recorded in `_requestCommitments` (denominated in TokenA units) but *not tagged* with which token they belong to.
2. Governance withdraws the outstanding TokenA balance via `withdraw()` (a normal governance action, e.g. periodic revenue sweep), zeroing `IERC20(TokenA).balanceOf(host)`.
3. Governance calls `updateHostParams` to migrate `feeToken` to TokenB. The `CannotChangeFeeToken` check passes because TokenA's balance is now 0 — even though `_requestCommitments` still holds fee entries meant to be paid in TokenA.
4. A relayer delivers the still-pending GET response. `dispatchIncoming(GetResponse,...)` reads the *raw* `fee` number from step 1 and calls `IERC20(feeToken()).safeTransfer(relayer, fee)`, where `feeToken()` now resolves to TokenB.
5. The relayer receives `fee` units of TokenB — an amount and token never actually escrowed for that specific commitment, drawn from whatever TokenB balance the contract holds (fees paid by *other, unrelated* TokenB dispatches). This both mis-pays the relayer (wrong token/likely wrong economic value) and drains funds that belong to other TokenB fee-payers/relayers.

The `hostManager`/`withdraw`/`updateHostParams` calls used above are ordinary, intended governance operations (fee-token migration and periodic revenue withdrawal) — no malicious/compromised governance key is required, only the fact that these two independently-legitimate operations compose to break the fee-token/escrow invariant that `CannotChangeFeeToken` was clearly designed to protect.

### Impact Explanation
This breaks a fund-custody invariant explicitly called out in the pivots: bandwidth/relayer-reward balances must move exactly once and only to the rightful beneficiary and amount. Here a relayer reward recorded against one token gets silently redenominated and paid from a different token's pool, which either overpays/underpays the relayer relative to the fee they were promised, or drains value belonging to unrelated TokenB payers — a form of fund loss/misdirection through a stale escrowed value that the code trusts unconditionally.

### Likelihood Explanation
Requires: (a) `hostManager` to migrate `feeToken` at some point during the contract's life (an explicitly supported, documented flow — `DeployConsensusRouter.s.sol` and TRON migration scripts show host-param rotation is routine), and (b) revenue withdrawal via `withdraw()` occurring before all pending fee-denominated commitments are settled. Neither requires a compromised or malicious governance actor — only that governance performs its two supported functions (`withdraw`, `updateHostParams`) without being aware `CannotChangeFeeToken`'s guard is bypassable this way, since nothing in the code cross-checks outstanding `_requestCommitments` fee sums against the balance check.

### Recommendation
- Tag each `FeeMetadata` entry with the token it was escrowed in (not just a raw `uint256 fee`), and pay out from that recorded token rather than the live `feeToken()`.
- Alternatively, make `CannotChangeFeeToken`'s check sum against outstanding `_requestCommitments`/`_responseReceipts` fee obligations rather than just the current on-chain balance, and make `withdraw()` respect a reserved/escrowed balance that can never be swept below the sum of unpaid commitments.

### Proof of Concept
1. Deploy `EvmHost` with `feeToken = TokenA`.
2. Dispatch a GET request with `fee = 100` (in TokenA), recorded into `_requestCommitments`.
3. As `hostManager`, call `withdraw({beneficiary: gov, amount: 100, token: TokenA})`, draining the TokenA balance to zero (see `evm/src/core/EvmHost.sol:651-660`).
4. As `hostManager`, call `updateHostParams` with `feeToken = TokenB`; `CannotChangeFeeToken` does not revert because `IERC20(TokenA).balanceOf(host) == 0` (see `evm/src/core/EvmHost.sol:617-621`).
5. Fund the host with TokenB (from unrelated, subsequent TokenB-fee dispatches).
6. Deliver the pending GET response via `dispatchIncoming(GetResponse, relayer)`; the relayer receives `100` units of TokenB (see `evm/src/core/EvmHost.sol:841-846`) — value drawn from TokenB fee reserves that belong to other requests, not the TokenA fee originally escrowed for this one.

            (bool sent,) = params.beneficiary.call{value: params.amount}("");
