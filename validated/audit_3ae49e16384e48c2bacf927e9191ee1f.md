### Title
`SignableTransaction::new` validates the pre-state balance but unchecked u64 arithmetic lets crafted inputs produce an unspendable/invalid signed transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The Perennial bug class is: a pre-operation check (`total_unclaimed >= total_balance`) validates the inputs but not the *resulting state* of the operation, so the transaction reverts or leaves the system in an unsafe position. In `serai`'s Bitcoin wallet, `SignableTransaction::new` has the same shape: it checks `input_sat < payment_sat + needed_fee` before constructing the transaction, yet the arithmetic used for that check — and the arithmetic that decides whether/how much change to emit — is unchecked `u64` addition/subtraction over attacker-influenced output values.

### Finding Description
`SignableTransaction::new` computes:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
...
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
...
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {
    tx_outs.push(TxOut { value: Amount::from_sat(value), ... });
``` [1](#0-0) 

`input_sat`, `payment_sat + needed_fee`, and `payment_sat + fee_with_change` are plain `u64` operations. `ReceivedOutput::read` accepts a `TxOut` via `consensus_decode` with no bound on `output.value` — consensus decoding does not enforce the `Amount::MAX_MONEY` range — so an untrusted serialized `ReceivedOutput` can carry `value` near `u64::MAX`. [2](#0-1) 

Consequences:

- `sum::<u64>()` over inputs, or `payment_sat + needed_fee`, overflows. In release builds this wraps; a wrapped-small `payment_sat + needed_fee` makes the `NotEnoughFunds` check pass when it should fail, and `input_sat.checked_sub(payment_sat + fee_with_change)` then computes a change `value` derived from wrapped arithmetic. The constructed `Transaction` can then have `sum(outputs) > sum(inputs)` — invalid under consensus — yet it is still returned as `Ok`, txid'd, and handed to the FROST `TransactionMachine` for signing.
- In debug builds (or via `self.fee()` at line 138-141, which subtracts `sum(outputs)` from `sum(prevouts)` with plain `u64` subtraction), the same inputs cause a panic — a reachable DoS.

This mirrors the report exactly: the guard validates the nominal inputs, but the post-operation state (outputs vs inputs, or the underflowing `fee()` accounting) is never verified, so the operation "succeeds" while producing a result the network will reject or that crashes accounting.

### Impact Explanation
An unprivileged party who can cause a `ReceivedOutput` to be deserialized from untrusted bytes (`ReceivedOutput::read`) — e.g. a stored/relayed output record — can make the wallet construct a transaction paying a fee/change that exceeds consensus-valid amounts. The multisig will then produce a validly-signed transaction that Bitcoin nodes reject as invalid (or never relay), burning a signing session and potentially pinning funds in an outpoint set that was marked "spent" by an unconfirmable tx. Alternatively it panics fee accounting (`fee()` underflow / `sum` overflow), DoSing the wallet path.

### Likelihood Explanation
Reachable whenever `ReceivedOutput` bytes come from storage or peers rather than from `Scanner::scan_transaction` directly. Requires a crafted `TxOut.value` above the 21M-BTC range, which `consensus_decode` does not reject. Not triggerable through a normal on-chain send (consensus already bounds real output values), which limits it — hence Medium, matching the source report.

### Recommendation
- Bound-check `output.value` in `ReceivedOutput::read` (e.g. `<= Amount::MAX_MONEY.to_sat()`).
- Use `checked_add`/`checked_sub`/`checked_sum` in `SignableTransaction::new` and `fee()`, returning `TransactionError::NotEnoughFunds` (or a new overflow error) instead of wrapping/panicking.
- As a defense-in-depth analog of "check the post-state", assert `sum(inputs) >= sum(outputs)` on the constructed `tx` before returning `Ok`.

### Proof of Concept
```rust
// Craft a ReceivedOutput with a near-u64::MAX TxOut value and feed it to
// SignableTransaction::new with a normal payment + change address.
let mut bytes = Vec::new();
bytes.extend_from_slice(&Scalar::ZERO.to_bytes());           // offset
// TxOut: value = u64::MAX - 1000, script_pubkey = minimal P2TR
bytes.extend_from_slice(&serialize(&TxOut {
    value: Amount::from_sat(u64::MAX - 1000),
    script_pubkey: some_p2tr_script,
}));
bytes.extend_from_slice(&serialize(&OutPoint::default()));
let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// input_sat overflows / payment_sat + needed_fee wraps in release;
// NotEnoughFunds is skipped and an invalid (outputs > inputs) transaction
// is constructed and returned as Ok, or fee() later underflows and panics.
let tx = SignableTransaction::new(
    vec![output],
    &[(payment_script, 1000)],
    Some(change_script),
    None,
    20,
); // returns Ok(...) or panics instead of NotEnoughFunds
```
