### Title
Gasless swap `Deadline` is validated only once at mempool admission and never re-checked at promotion or block-inclusion time, allowing stale-price swap execution - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The `kaiax/gasless` module implements KIP-247 gasless swaps. A `GaslessSwapTx` carries a user-signed `Deadline` that is supposed to guarantee the swap cannot be executed after the user's price/quote has gone stale. This deadline is checked exactly once, in `checkBalanceForSwap`, at the moment the transaction is admitted to the pool via `GetCheckBalance()`. No other stage of the transaction's lifecycle — promotion (`IsReady`/`isSwapTxReady`), pool reset (`PreReset`/`PostReset`), or bundle execution (`commitBundleTransaction`) — re-validates the deadline against the block time at which the transaction is actually going to be executed. This mirrors the root cause of the NATS advisory: an expiry/validity check exists in the code, but it is not enforced by the component that actually performs the privileged action, so a value that "looks" time-bound can still be acted upon after it should have expired.

### Finding Description
`checkBalanceForSwap` performs the deadline check against the current chain head at admission time: [1](#0-0) 

This function is only invoked from `GetCheckBalance()`, which is the tx-pool's one-shot admission-time balance/validity hook: [2](#0-1) 

Once a `GaslessSwapTx` passes this one-time check, it is tracked purely by generic pool-residency timers (`QueueTimeout`, `PendingTimeout`, `KnownTxTimeout`), not by its own declared `Deadline`: [3](#0-2) [4](#0-3) 

Promotion logic (`IsReady`, `isSwapTxReady`, `isApproveTxReady`) only checks nonce ordering and `IsExecutable`, never the swap's `Deadline`: [5](#0-4) 

Finally, when the block builder actually executes the bundled swap, it calls `bc.ApplyTransaction` directly with no deadline re-check against the block being built: [6](#0-5) 

A search of the on-chain Solidity contracts in this repository turned up no `deadline` keyword at all, indicating the `GaslessSwapRouter` contract referenced via the `kip247` bindings does not itself enforce a deadline on-chain either — enforcement is expected to happen entirely off-chain, in the Go tx-pool code, at admission time only.

### Impact Explanation
Because the deadline is validated only against the state of the chain at the moment the transaction was first submitted to a node's mempool, and never re-validated at the moment of inclusion/execution, a gasless swap can be executed well after its user-intended deadline has elapsed if:
- the tx lingers past `QueueTimeout`/`PendingTimeout` boundaries in edge-case timing/backlog scenarios, or
- a chain reset/reorg (`PreReset`/`PostReset`) requeues the tx and it re-enters pending without a fresh deadline check, or
- a block proposer deliberately delays including an already-promoted/pending swap tx until it is more profitable to execute (classic MEV "sandwich/stale price" pattern), since nothing in the block-building path (`commitBundleTransaction`) revalidates `Deadline` against the block being built.

Since `minAmountOut`/`amountRepay` were fixed by the user based on market conditions at signing time, and the deadline exists specifically to prevent execution once those conditions are stale, executing after expiry lets a proposer or delayed inclusion extract value from the gasless user at an unfavorable, no-longer-consented-to price — a concrete value-extraction/fee-delegation abuse scenario reachable by any gasless-swap-submitting user and any block proposer, which is squarely in scope (gasless settlement theft).

### Likelihood Explanation
Likelihood is moderate: the timing windows (`QueueTimeout`/`PendingTimeout` = 10s, `KnownTxTimeout` = 30s) are short under normal operation, which limits the exposure window in the common case. However, a block proposer is not prevented by any protocol-level check from including a `GaslessSwapTx` bundle whose `Deadline` has already passed — nothing in `commitBundleTransaction` or `ApplyTransaction` rejects it — so a proposer who chooses to delay/reorder inclusion (which is within their normal privileges) can trivially trigger the stale-deadline execution, and no other honest node validating the resulting block would reject it either, since deadline is not part of on-chain/consensus validation.

### Recommendation
- Enforce the `Deadline` check on-chain in the `GaslessSwapRouter` contract itself (as is standard practice for AMM router `deadline` parameters), so consensus-level validation guarantees expiry cannot be bypassed regardless of off-chain pool behavior.
- Additionally/alternatively, re-validate `SwapArgs.Deadline` against the block's timestamp immediately before block inclusion in `commitBundleTransaction` (or in `IsReady`/`isSwapTxReady`), and drop/exclude any gasless swap bundle whose deadline has passed relative to the block being built, rather than relying solely on the pool admission-time check in `checkBalanceForSwap`.

### Proof of Concept
1. A gasless user submits a `GaslessSwapTx` with `Deadline = T`, computed off `Token.getAmountIn` quoted at admission time; `checkBalanceForSwap` accepts it because `Deadline >= CurrentBlock.Time()` at that instant (`kaiax/gasless/impl/tx_pool.go:175-179`).
2. The tx is promoted to pending via `isSwapTxReady`, which never inspects `Deadline` (`kaiax/gasless/impl/tx_pool.go:269-290`).
3. A block proposer (who controls tx bundling/ordering, `work/worker.go` `ExtractTxBundles`/`commitBundleTransaction`) withholds inclusion of the bundle for several blocks, past `T`, while `QueueTimeout`/`PendingTimeout` do not trigger removal because they measure pool-residency time, not the tx's own `Deadline`.
4. When finally included, `commitBundleTransaction` calls `bc.ApplyTransaction` unconditionally (`work/worker.go:905-936`), executing the swap at the user's originally signed `minAmountOut`/`amountRepay` even though the market/quote has moved and the user's declared deadline has expired, allowing the proposer/MEV actor to capture the difference.

Note: I was not able to fully trace every call site of `GetCheckBalance()` inside `blockchain/tx_pool.go`/`blockchain/tx_list.go` within the available iterations, nor inspect the actual on-chain `GaslessSwapRouter` Solidity source (only Go bindings `kip247` are referenced in this repo) to confirm with certainty that no on-chain deadline check exists — this should be verified directly against the deployed KIP-247 router contract before treating the on-chain-enforcement gap as fully confirmed.

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

// isSwapTxReady assumes that the caller checked `g.IsSwapTx(swapTx)`
func (g *GaslessModule) isSwapTxReady(swapTx, prevTx *types.Transaction) bool {
	addr, err := types.Sender(g.signer, swapTx)
	if err != nil {
		return false
	}
	nonce := g.getCurrentStateNonce(addr)

	var approveTx *types.Transaction
	if swapTx.Nonce() == nonce {
		approveTx = nil
	} else if swapTx.Nonce() == nonce+1 {
		if prevTx == nil || !g.IsApproveTx(prevTx) {
			return false
		}
		approveTx = prevTx
	} else {
		return false
	}

	return g.IsExecutable(approveTx, swapTx)
}

// PreReset removes timed out tx from the tx pool and knownTxs.
func (g *GaslessModule) PreReset(oldHead, newHead *types.Header) []common.Hash {
	g.knownTxsMu.Lock()
	defer g.knownTxsMu.Unlock()

	drops := make([]common.Hash, 0)

	for hash, knownTx := range *g.knownTxs {
		// remove pending timed out tx from tx pool
		if knownTx.status == TxStatusPending && knownTx.elapsedPromotedTime() >= PendingTimeout {
			drops = append(drops, hash)
		}
		// remove queue timed out tx from tx pool
		if knownTx.status == TxStatusQueue && knownTx.elapsedAddedTime() >= QueueTimeout {
			drops = append(drops, hash)
		}
		// remove known timed out tx from knownTxs
		if knownTx.elapsedPromotedOrAddedTime() >= KnownTxTimeout {
			g.knownTxs.delete(hash)
		}
	}

	return drops
}
