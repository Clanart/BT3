## Analysis

The Ondo report's core broken invariant: **a fund-recovery path is gated by a check that has no escape hatch even for a trusted admin**, so once the gating condition can never be satisfied again, the funds are permanently unreachable by anyone, including governance.

The closest local analog is in Hyperbridge's Intent Gateway same-chain cancellation path.

### Title
Same-chain order escrow has no governance/relayer recovery path when `order.user` cannot sign — funds permanently stuck - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_cancelSameChain` — the only function that can release same-chain escrowed input tokens back to a user — is hard-gated by `msg.sender == order.user` with no time-based public fallback and no governance/admin override, unlike the cross-chain destination-cancel path which explicitly allows "anyone" to trigger cancellation after the deadline on behalf of an unreachable user.

### Finding Description
`_cancelSameChain` unconditionally reverts unless the caller is `order.user`: [1](#0-0) 

Contrast this with the cross-chain destination-side cancel path, which was deliberately designed to let "a relayer acting on behalf of the user" trigger cancellation once the order has expired: [2](#0-1) 

and documented explicitly as the recovery mechanism for users who can no longer act themselves: [3](#0-2) 

The same-chain path has **no such fallback and no deadline field at all** — the documentation itself confirms "the original user must always call it": [4](#0-3) 

Escrow for an individual order is tracked in the `_orders[commitment][token]` mapping, which is only read/cleared by `_withdraw` (called from `_cancelSameChain`, `_fillSameChain`, or the cross-chain `onAccept`/`onGetResponse` paths). The only governance-triggered fund-moving action, `SweepDust`, operates on separately accumulated protocol-dust balances, not on a specific order's `_orders[commitment][token]` escrow — so governance has no generic mechanism to release a stuck same-chain order's escrow. If `order.user`'s key is lost, its address becomes non-functional (e.g., contract wallet upgrade failure), or the address is blacklisted by the underlying ERC-20 token issuer (e.g., USDC/USDT compliance freeze) so it can no longer originate the cancel transaction, the escrowed input tokens for that specific same-chain order become permanently unrecoverable — by the user, by a relayer, and by Hyperbridge governance alike.

This mirrors the CashManager bug class precisely: a legitimate, trusted party (here, Hyperbridge governance/the gateway's own admin path) has no way to release funds once the sole authorized caller can no longer transact, even though the protocol elsewhere (destination-side cross-chain cancel) explicitly solved this exact problem for the cross-chain case.

### Impact Explanation
Escrowed input tokens for a same-chain order are permanently locked with no recovery path if `order.user` becomes unable to sign transactions (lost key, compromised/frozen account, or token-level blacklist by the ERC-20 issuer). This is a direct loss/lock of user funds within the bridge's own escrow custody, with no admin, governance, or relayer path to remediate it — matching the "stealing or loss of funds" impact class.

### Likelihood Explanation
This requires no malicious peer, relayer, or governance actor — only that an already-placed same-chain order's `order.user` address becomes unable to sign (a realistic, externally-triggered event such as a stablecoin issuer freeze or lost key), which is entirely plausible for high-value escrowed orders and does not depend on any protocol misbehavior.

### Recommendation
Add a governance- or time-gated fallback for same-chain cancellation analogous to the destination-side cross-chain path: after some deadline/timeout, allow a permissioned recovery action (via Hyperbridge governance `onAccept`, similar to `SweepDust`) to release a specific order's `_orders[commitment][token]` escrow to `order.user` (or a governance-specified beneficiary) without requiring `order.user` to sign.

### Proof of Concept
1. User places a same-chain order via `IntentGatewayV2.placeOrder`, escrowing input tokens tracked in `_orders[commitment][token]`.
2. Before the order is filled, `order.user`'s address becomes blacklisted by the input token's issuer (e.g., Circle freezes the address) or the user's private key is lost.
3. `order.user` can no longer call `cancelOrder` → `_cancelSameChain` because `msg.sender == order.user` can never again be satisfied.
4. No other function path clears `_orders[commitment][token]` for this specific order — `SweepDust` only touches separate dust accounting, and `onAccept` governance actions (`UpdateParams`, `UpgradeContract`, `NewDeployment`, `SweepDust`) never call `_withdraw` for an arbitrary commitment.
5. The escrowed tokens remain locked in the `IntentGatewayV2` contract indefinitely, exactly as in the referenced CashManager finding — an admin who could otherwise be trusted has no on-chain path to release the funds.

```text
### Cancel from the Destination Chain

Cancelling from the destination chain is simpler and does not require a storage proof. The destination gateway immediately marks the order as settled, blocking any future fill attempts, and sends a refund message to the source chain via Hyperbridge. When the message arrives, the source chain authenticates it as coming from the registered destination gateway and returns the escrowed tokens to the original user.

Before and **at** the order deadline only the order creator can trigger this path. From the first destination block after the deadline, anyone may call. This lets relayers act on behalf of users whose orders have expired without being filled, providing a recovery mechanism that does not require the user to be online. The caller pays the dispatch cost, but cannot change `WithdrawalRequest.beneficiary`: the refund always goes to `order.user`.
```
