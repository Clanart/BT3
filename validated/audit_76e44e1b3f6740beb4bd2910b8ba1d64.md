### Title
EIP-712 domain used to authenticate aggregator withdrawal/payout authorizations omits `chainId` and `verifyingContract` - ([File: core/src/rpc/ecdsa_verification_sig.rs])

### Summary
`recover_address_from_ecdsa_signature()` recovers the signer address of an aggregator-issued authorization for `OptimisticPayoutMessage` / `OperatorWithdrawalMessage` and compares it against the configured aggregator address before an operator is allowed to execute an optimistic payout or a withdrawal reimbursement. The EIP-712 domain used for this hash, `CLEMENTINE_EIP712_DOMAIN`, only sets `name` and `version` and omits `chainId` and `verifyingContract`, exactly the domain-separator weakness described in the external report (fixed elsewhere by binding `hashForKYC()` to `chain.id` and contract address).

### Finding Description
The signing/verification pipeline is: [1](#0-0) 

which is used to compute the signing hash consumed both when the aggregator signs a withdrawal authorization off-chain (test helper mirrors production logic): [2](#0-1) 

and when an operator/verifier recovers the signer to authenticate the request: [3](#0-2) 

The EIP-712 domain struct produced by `alloy_sol_types::eip712_domain!` binds only `name: "ClementineVerification"` and `version: "1"` — there is no `chainId` and no `verifyingContract` field, contrary to the EIP-712 domain separator's purpose of scoping a signature to one exact verifying context. The recovered address is then checked against the operator/verifier configuration's expected aggregator address in `core/src/rpc/operator.rs` (via `recover_address_from_ecdsa_signature`, imported at lines 17-19) before the withdrawal/optimistic-payout flow proceeds: [4](#0-3) 

Because the domain separator carries no chain- or deployment-specific binding, a signature the aggregator produces authorizing withdrawal parameters (`withdrawal_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) for one Clementine deployment is not cryptographically scoped to that deployment. Any other Clementine deployment (or environment) that is configured to trust the same aggregator public key will accept and process the identical signature for a withdrawal request with the same struct field values, without any indication of which chain/contract/instance it was intended for.

### Impact Explanation
This breaks the equality "operator reimbursed for a payout" == "the withdrawal actually fronted and authorized in *this* deployment's context." If the same aggregator key is trusted by more than one Clementine environment (a realistic operational scenario — the same aggregator key material re-used across a staging/production pair, or across two chains served by the same team), an operator (or anyone able to observe/relay the authorization) can present the aggregator's signature meant for deployment A to trigger the optimistic-payout / withdrawal-reimbursement path on deployment B for matching withdrawal parameters, causing an operator to be reimbursed for a payout it never fronted on that deployment. This matches the required High/Critical impact class of "an operator reimbursed for a payout it never funded" via "an unauthenticated state-changing... call" relative to the intended verifying context.

### Likelihood Explanation
Exploitation requires no signing key, only capturing/relaying a legitimately produced aggregator signature and submitting it to a second trusting deployment (or replaying it after any future re-key/redeploy that keeps the same aggregator key). No privileged role beyond "party who can call the operator/withdrawal RPC" is needed, and the withdrawal parameters (`withdrawal_id`, `outpoint`, `script_pubkey`, `amount`) are attacker-visible on-chain/off-chain data, not secrets. The likelihood is directly tied to how many deployments/environments share an aggregator key, which is an operational choice not prevented or warned against anywhere in the domain construction itself.

### Recommendation
Add `chain_id` and `verifying_contract` (or an equivalent deployment-unique identifier such as a bridge instance ID / operator xonly public key) to `CLEMENTINE_EIP712_DOMAIN` in `core/src/rpc/ecdsa_verification_sig.rs`, following the EIP-712 domain separator specification, so a signature produced for one Clementine deployment cannot be replayed as valid on another.

### Proof of Concept
1. Deployment A and deployment B are both configured with aggregator verification address `V` (shared key or misconfiguration across two Clementine instances).
2. Aggregator signs a withdrawal authorization for `(withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount)` intended for deployment A, producing `sig` over `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` — see [5](#0-4) .
3. An operator on deployment B submits the identical `(withdrawal_id, ..., output_amount, sig)` to deployment B's operator RPC.
4. `recover_address_from_ecdsa_signature` on deployment B recomputes the exact same hash (domain has no chain/contract binding distinguishing A from B) and recovers `V`, matching the locally configured aggregator address, so deployment B accepts the authorization and reimburses the operator for a withdrawal it never fronted on deployment B.

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
