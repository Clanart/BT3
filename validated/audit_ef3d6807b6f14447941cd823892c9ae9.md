### Title
Denial of Service via unmetered blob sidecar disk writes bypassing blob-gas accounting - (File: blockchain/blob_storage.go, blockchain/tx_pool.go)

### Summary
Kaia's EIP-4844 blob transaction handling charges blob gas (`params.BlobTxBlobGasPerBlob`, capped by `MaxBlobGasPerBlock`) for the blobs referenced in a transaction, but the actual sidecar bytes are persisted to the node's local filesystem by `BlobStorage.Save` [1](#0-0)  completely outside of the EVM/state-transition gas metering path. This mirrors the CVE-2020-8557 pattern where writes to a filesystem location (`/etc/hosts`) were not accounted for by the resource-tracking subsystem (kubelet eviction manager vs. Kaia's gas accounting), letting a client cause unbounded local disk growth relative to the fee actually paid.

### Finding Description
When a blob transaction is mined, `TxPool.saveAndPruneBlobStorage` persists the sidecar (blobs, commitments, proofs) to disk via `pool.blobStorage.Save(...)` for every blob tx found in the new head block, and also opportunistically for blob txs still resident in the local pool [2](#0-1) . The actual `Save` call performs `os.MkdirAll` / file writes to `BaseDir` bucketed by block number [3](#0-2) , with retention-based pruning (`BLOB_SIDECARS_RETENTION = 21 * 24 * time.Hour`) that only runs every `BLOCKS_PER_BUCKET` (1000) blocks [4](#0-3) [5](#0-4) .

The fee actually charged to a blob-tx sender is `blobGasCost = blobGasUsed * blobBaseFee`, driven purely by KZG-commitment blob-gas accounting (verified in `TestBlobTx` to only account for `blobGas`/`gasUsed`, not for the raw file-system bytes retained for 21 days) [6](#0-5) . There is no coupling between the per-byte disk-retention cost of the sidecar (proofs + commitments + raw blob data, persisted per node for up to 21 days across up to 1000-block buckets) and the blob-gas fee schedule, nor any global cap on cumulative disk usage from the retention window independent of the target-blob-per-block market design. This is structurally the same root cause as CVE-2020-8557: a filesystem write performed by node software on behalf of an untrusted, remotely-supplied input is not tracked/limited by the same resource-accounting mechanism (there, the eviction manager; here, the gas/fee metering) that is supposed to bound the attacker's footprint.

### Impact Explanation
An attacker who can sustain the maximum blob throughput per block over the 21-day retention window can force every full/RPC node that retains blob sidecars to accumulate disk usage bounded only by `max_blobs_per_block * blob_size * blocks_in_21_days`, independent of any additional protocol-level throttle beyond the existing KIP-71/blob-gas market (which caps blocks, not aggregate retained bytes). Because pruning is deferred to `BLOCKS_PER_BUCKET`-aligned checkpoints and skipped entirely when the head block is "too old" relative to wall-clock time [7](#0-6) , nodes that fall behind (e.g., during resync or after downtime) can also accumulate un-pruned buckets, compounding local storage exhaustion. Sustained disk exhaustion on validator/full nodes is a Medium-severity availability risk consistent with CWE-400, matching the impact class of the advisory.

### Likelihood Explanation
Reaching this path only requires submitting ordinary, protocol-legal blob transactions (`TxTypeEthereumBlob`) paying the market-rate blob fee — no special privilege, no malicious peer/node behavior, and no protocol violation is needed. The likelihood is bounded by the cost of blob fees over time (an economic, not technical, barrier), and by disk capacity/retention-window assumptions made at node-operator configuration time (`DefaultBlobStorageConfig`) [8](#0-7) .

### Recommendation
Tie blob-sidecar retention footprint to an explicit, governance-adjustable disk-budget parameter independent of the blob-gas fee market, and/or incorporate a storage-rent style disk-accounting check before/while calling `BlobStorage.Save`. Consider pruning eagerly (per block instead of per `BLOCKS_PER_BUCKET`) and enforcing an upper bound on total on-disk sidecar bytes with LRU/oldest-first eviction independent of block-time bucketing, so that fee payment and disk-retention cost stay coupled even under sustained maximum-throughput blob submission or during resync gaps.

### Proof of Concept
1. An attacker (or set of colluding senders) submits `TxTypeEthereumBlob` transactions filling the maximum blob-gas-per-block quota, sustained across blocks, paying only the market blob-gas fee.
2. Each block's `saveAndPruneBlobStorage` call persists the full sidecar (blobs+commitments+proofs) to `BaseDir` via `BlobStorage.Save` [9](#0-8) .
3. Because pruning only triggers on `newHead.Number() % BLOCKS_PER_BUCKET == 0` and is skipped when the block is older than `Retention` relative to now [10](#0-9) , an attacker can sustain accumulation for the full 21-day retention window (or longer if a node is behind), causing disk usage proportional to `blobs_per_block * blob_size * blocks_over_21_days` on every node retaining blob storage — without any additional protocol-level fee scaling to that disk cost.

// saveAndPruneBlobStorage saves and prunes blob storage.
func (pool *TxPool) saveAndPruneBlobStorage(newHead *types.Block) {
	if pool.blobStorage == nil || newHead == nil {
		return
	}

	// skip if the block is too old
	if time.Since(time.Unix(int64(newHead.Time().Uint64()), 0)) > pool.config.BlobStorageConfig.Retention {
		logger.Debug("skipping blob storage save and prune because the block is too old", "blockNumber", newHead.Number(), "blockTime", newHead.Time(), "retention", pool.config.BlobStorageConfig.Retention)
		return
	}

	// prune blob storage at BLOCKS_PER_BUCKET block interval
	if new(big.Int).Mod(newHead.Number(), big.NewInt(int64(BLOCKS_PER_BUCKET))).Cmp(big.NewInt(0)) == 0 {
		go func() {
			if err := pool.blobStorage.Prune(newHead.Number()); err != nil {
				logger.Warn("failed to prune blob storage", "err", err)
			}
		}()
	}
