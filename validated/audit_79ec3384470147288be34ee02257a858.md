### Title
Truncating fee-rate division causes Bitcoin multisig transactions to systematically underpay the intended fee rate — (`networks/bitcoin/src/wallet/send.rs`, `processor/src/networks/bitcoin.rs`)

### Summary
`SignableTransaction::new` computes the required fee as `fee_per_vbyte * vbytes`, where `fee_per_vbyte` is an integer sat/vbyte rate produced by `Bitcoin::median_fee` via `(in_value - out) / tx.vsize()`. Both the division and the multiplication round down, so the fee actually committed to the transaction is less than the fee rate the network observed. Like the GroupBuy `minBidPrices = initialPrice / totalSupply` bug, integer truncation makes a per-unit price too low, and multiplying it back over all units never recovers the target amount — here the "target" is the fee needed for the transaction to be competitive/relayable at the intended rate.

### Finding Description
In `processor/src/networks/bitcoin.rs`, the processor derives its fee rate from the median of in-block transactions:

```rust
fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
``` [1](#0-0) 

This floors each sampled rate (e.g. 299 sat / 200 vB → 1 sat/vB). That integer rate is then passed to `SignableTransaction::new`, which computes:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
``` [2](#0-1) 

and likewise for the change case (`fee_with_change = fee_per_vbyte * vbytes_with_change`, line 227). The correct fee to achieve rate `r` over `v` vbytes is `ceil(r * v)`; since `r` itself was already floored from the true rate `r + f` (0 ≤ f < 1), the committed fee underpays by up to `(vbytes - 1) + vbytes * f` satoshis — nearly 2 sat/vbyte of systematic under-payment. The check at line 215 only ensures `input_sat ≥ payment_sat + needed_fee`, so the shortfall is silently absorbed as change (or extra fee is never added). Unlike a fixed budget (`initialPrice`), the "not enough collected" manifests as the transaction carrying a lower fee rate than the measured market median that the scheduler intended to match. [3](#0-2) 

### Impact Explanation
The Serai bitcoin multisig signs all outgoing payments (withdrawals, branch aggregation, change) through `make_signable_transaction` using this `median_fee` result. [4](#0-3) 
Every transaction produced under-pays relative to the median fee rate it sampled. In a rising fee market — precisely when accurate fee estimation matters — these transactions can sit unconfirmed or fail mempool acceptance vs. the intended rate, stalling user withdrawals and branch/change recoupment until a later block's (also truncated) estimate happens to suffice. Funds are not stolen, but they are temporarily unspendable/unmoved, and the truncation is worst exactly for the large transactions (up to `MAX_STANDARD_TX_WEIGHT`, ~520 inputs/outputs) Serai produces, where the lost `vbytes * f` term is largest.

### Likelihood Explanation
An unprivileged party reaches this path with public inputs: `median_fee` samples every non-coinbase transaction in a block, so any Bitcoin user can broadcast transactions with fee rates chosen to maximize downward truncation of the median (e.g. fee/vsize just below the next integer boundary), directly steering `Fee(fee.max(1))` used for the multisig's next `SignableTransaction`. [5](#0-4) 
Even without manipulation, ordinary fractional fee rates (the common case on Bitcoin) guarantee the double truncation occurs on essentially every transaction the processor builds.

### Recommendation
Round up rather than down, mirroring the report's suggested fix:
- In `median_fee`, compute `(in_value - out + vsize - 1) / vsize` (or keep a fixed-point sat/kilo-vbyte rate) so the sampled rate never underestimates.
- In `SignableTransaction::new`, take `fee_per_vbyte` in sat/kilo-vbyte and compute `needed_fee = ceil(fee_per_kvb * vbytes / 1000)`, or equivalently `fee_per_vbyte * vbytes + (vbytes - 1)` style ceiling, so `needed_fee / vbytes >= fee_per_vbyte`.
- Alternatively compute the fee in milli-sat/vbyte end-to-end and only ceil once at the end.

### Proof of Concept
1. Reference block contains non-coinbase txs whose fee/vsize ratios are e.g. `fee = 299`, `vsize = 200` → `median_fee` yields `299/200 = 1` sat/vB instead of `ceil = 2`. [6](#0-5) 
2. Processor builds a payout with `vbytes = 1000`. Intended fee at true rate 1.495 sat/vB ≈ ≥1495 sat; computed `needed_fee = 1 * 1000 = 1000` sat — a ~33% under-payment. [7](#0-6) 
3. `fee()` confirms the signed transaction pays exactly `sum(inputs) - sum(outputs)` where change absorbed only the floored estimate; the resulting 1 sat/vB transaction relays (barely above `DEFAULT_MIN_RELAY_TX_FEE`) but is far below the observed market median and can remain unconfirmed, stalling the payment plan. [8](#0-7) 

Numerically: `floor(299/200) * 1000 = 1000 < ceil(299/200 * 1000) = 1495`, directly paralleling `floor(initialPrice/totalSupply) * totalSupply < initialPrice`.
