## Analysis

The Sherlock report's core broken invariant: a function credits/assumes a state of custody (`_returnCollateral()` assuming the router holds the NFT) that does not match where the asset actually landed, so the critical withdrawal path fails.

The closest verifiable local analog is in the **Tron** deployment of the Intent Gateway, which independently duplicates `placeOrder`'s predispatch-escrow logic but is missing a fix present in the canonical EVM contract.

### Comparison

In the canonical EVM contract `evm/src/apps/IntentGatewayV2.sol`, after sweeping the predispatch-derived input tokens from the `CallDispatcher` back to the gateway, the code explicitly measures what was **actually received** and mutates `order.inputs[i].amount` to that real value before computing `reducedInputs`/the commitment/escrow crediting: [1](#0-0) 

In the Tron contract `evm/tron/contracts/apps/IntentGatewayV2.sol`, the equivalent predispatch branch computes `dust` from the *dispatcher's pre-transfer balance* vs. `requiredAmount`, credits `_orders[commitment][token] += reducedInputs[i].amount` — a value derived only from the **declared** `order.inputs[i].amount`/protocol fee, not from actual gateway receipt — and only *afterwards* executes the transfer that moves tokens from the dispatcher to the gateway: [2](#0-1) 

Because the second-hop `IERC20.transfer` (dispatcher → gateway) is never re-measured, any input token that deducts a transfer fee on that hop (fee-on-transfer/tax token, exactly the class of asset the EVM test suite explicitly covers in `testPlaceOrder_FeeOnTransferToken_Predispatch`) causes the gateway to hold strictly less than the amount it just credited to `_orders[commitment][token]`. [3](#0-2) 

That escrow ledger is the sole source used later by `withdraw()` (for both `RedeemEscrow` fills and `RefundEscrow` cancellations) to pay out: [4](#0-3) 

`withdraw()` only guards against a *zero* escrow entry (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`), not against the escrow entry exceeding the contract's real token balance. When the real balance is short, the low-level `token.call(transfer...)` for the full ledgered amount fails and the function reverts with `TransferFailed()` — permanently: there is no lower-amount retry path, and `SweepDust` only sweeps *surplus* balances, not this ledger/balance shortfall.

### Title
Tron `IntentGatewayV2.placeOrder` over-credits escrow for fee-on-transfer predispatch inputs, permanently bricking `withdraw()` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron IntentGatewayV2, the predispatch escrow-crediting step in `placeOrder` uses the user-declared (fee-reduced) input amount rather than the amount actually received by the gateway after sweeping funds back from the `CallDispatcher`. For any input token that charges a transfer fee on that final hop, the contract records more tokens as escrowed (`_orders[commitment][token]`) than it actually custodies.

### Finding Description
`placeOrder`'s predispatch branch computes `dust = balance - requiredAmount` using the dispatcher's balance *before* the sweep, then unconditionally sets `_orders[commitment][token] += reducedInputs[i].amount` before the sweep transfer executes: [5](#0-4)  The canonical EVM contract avoids this by re-measuring the gateway's actual post-sweep balance delta and clamping `order.inputs[i].amount` to it before crediting escrow: [6](#0-5) . The Tron implementation has no such correction, so `_orders[commitment][token]` can exceed the gateway's true token balance whenever the swept token taxes transfers.

### Impact Explanation
`withdraw()` is the only function that pays out `_orders[commitment][token]` — to solvers on `RedeemEscrow` and to users on `RefundEscrow`/cancellation — and it only checks that the ledger entry is non-zero, not that it's actually backed: [7](#0-6) . When the ledgered amount exceeds the real balance, the ERC20 `transfer` call fails and the whole withdrawal reverts with `TransferFailed()`, with no alternate/partial-recovery path. The escrowed tokens for that order become permanently unreachable — matching the same "critical settlement function always reverts, locking user funds" pattern as the source H-5 report, but on the fund-release path rather than the deposit path.

### Likelihood Explanation
Any unprivileged user placing an order can trigger this by supplying a fee-on-transfer/tax ERC20 as a predispatch/input asset — no relayer, prover, or admin cooperation is required, and the predispatch mechanism (arbitrary swap via `CallDispatcher`) already exists to let users compose input assets before escrow.

### Recommendation
Mirror the EVM mainline fix in the Tron contract: after the transfer-back `dispatch(abi.encode(transferCalls))` call, measure the gateway's actual balance delta for each input token and credit `_orders[commitment][token]` (and the commitment computation) using that measured value instead of the declared `reducedInputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g. 1% fee) as an order input on the Tron gateway.
2. Place an order with `predispatch.assets` containing that token, routed through the `CallDispatcher` (even a no-op call suffices, as in `testPlaceOrder_FeeOnTransferToken_Predispatch`).
3. Observe: `_orders[commitment][token]` is credited with `reducedInputs[i].amount` (derived from the pre-fee declared amount), while the gateway's real balance is `balance_after_two_fee_deductions < reducedInputs[i].amount`.
4. Have a solver fill (or the user cancel) the order, triggering `withdraw()` for the full ledgered amount.
5. The internal `token.call(transfer(...))` reverts (insufficient balance), `withdraw()` reverts with `TransferFailed()`, and the order's escrow can never be released — the funds are stuck.
