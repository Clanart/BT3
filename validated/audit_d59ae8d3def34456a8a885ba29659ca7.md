### Title
OP_RETURN output omitted from transaction fee and weight accounting - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/blackvul/serai--022/blob/master/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends an attacker-supplied OP_RETURN output to `tx_outs`, but calculates `needed_fee` and `weight` using only `payments`, excluding the output already added. The resulting transaction commits to a larger transaction than the one measured, so `needed_fee()` and the maximum-standard-weight check are computed against stale transaction state.

### Finding Description
At construction, payment outputs are copied into `tx_outs`, then an OP_RETURN output containing up to 80 bytes of caller-controlled `data` is pushed into `tx_outs`. However, the subsequent call to `calculate_weight_vbytes(tx_ins.len(), payments, None)` passes `payments` rather than the already-updated `tx_outs`, meaning the OP_RETURN output is absent from both the vbyte and weight estimates. [1](#0-0) 

The later change calculation repeats the same pattern: `tx_outs` may contain payment outputs and the OP_RETURN output, but `calculate_weight_vbytes` is again called with only `payments` plus the optional change output. [2](#0-1) 

The stale `weight` value is then used to enforce `MAX_STANDARD_TX_WEIGHT`, while the returned `SignableTransaction` contains the larger `tx_outs` vector. [3](#0-2) 

`needed_fee()` exposes this understated amount to callers, while `fee()` computes the actual consensus fee from `prevouts` minus all final outputs. [4](#0-3) 

### Impact Explanation
A caller can create a transaction whose signed transaction is up to 80 bytes larger than the transaction used for fee estimation and standardness validation. The actual fee remains `sum(inputs) - sum(outputs)`, so the transaction pays the caller-specified fee amount rather than the specified fee rate for its actual vsize; it may therefore be underpriced or exceed standard transaction weight when the omitted OP_RETURN pushes it over the limit. This can cause constructed spends to be rejected by standard relay policy or remain unconfirmed despite `needed_fee()` reporting success.

### Likelihood Explanation
The issue is reachable through the public `SignableTransaction::new` API by supplying any non-empty `data` value. No validator compromise, malformed cryptographic object, or private-key access is required; the discrepancy occurs whenever `data.is_some()` and the measured transaction differs from the committed transaction. The practical severity is bounded by the 80-byte `TooMuchData` check and by needing the omitted bytes to change relay/mining behavior. [5](#0-4) 

### Recommendation
Calculate weight and vbytes after all outputs have been finalized. This can be done by changing `calculate_weight_vbytes` to accept the final `tx_outs` slice, or by deferring the OP_RETURN insertion until after fee/weight sizing and recalculating once every output—including OP_RETURN and change—is present. The `MAX_STANDARD_TX_WEIGHT` check should use the actual final transaction weight.

### Proof of Concept
Conceptually, construct two otherwise identical transactions:

```rust
let without_data = SignableTransaction::new(
  inputs.clone(),
  payments,
  change.clone(),
  None,
  fee_per_vbyte,
);

let with_data = SignableTransaction::new(
  inputs,
  payments,
  change,
  Some(vec![0x42; 80]),
  fee_per_vbyte,
);
```

`with_data` adds an 80-byte OP_RETURN output before measurement, but `calculate_weight_vbytes` receives only `payments` and optional `change`, producing the same `needed_fee` accounting basis as a transaction without the OP_RETURN. The returned transaction nevertheless includes the extra output and its real serialized transaction/vsize is larger than the measured one. [6](#0-5) [7](#0-6)
