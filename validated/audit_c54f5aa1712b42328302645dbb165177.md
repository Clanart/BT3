### Title
Unauthenticated JSON-RPC `send_tx` Endpoint Allows Arbitrary Transaction Enqueuing and Fee-Payer Wallet Drain — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

### Summary

The `start_jsonrpc_server` function builds a plain `jsonrpsee` HTTP server with **zero authentication**. The code explicitly supports binding to `0.0.0.0`. Any network peer that can reach the port can call `send_tx`, enqueue an arbitrary transaction with `FeePayingType::CPFP`, and cause the tx-sender to spend Bitcoin Core wallet funds creating fee-payer UTXOs and then spend those UTXOs on the attacker's transaction.

### Finding Description

`start_jsonrpc_server` uses `ServerBuilder::default()` with no middleware, no API key, no mTLS, and no IP allowlist: [1](#0-0) 

The `send_tx` handler immediately calls `insert_try_to_send` → `db.save_tx` with no caller identity check: [2](#0-1) 

The config parser explicitly validates and accepts `0.0.0.0` as a legal bind address — this is not an undocumented edge case, it is a first-class supported value: [3](#0-2) 

Once a row is in the `try_to_send` queue with `FeePayingType::CPFP`, the task loop calls `send_cpfp_tx`. When no confirmed fee-payer UTXOs exist for the new entry, `create_fee_payer_utxo` is invoked, which calls `fund_raw_transaction` + `sign_raw_transaction_with_wallet` against the Bitcoin Core wallet — spending wallet-controlled funds to create a fee-payer UTXO: [4](#0-3) 

On the next poll iteration, `build_and_sign_child_tx` spends those fee-payer UTXOs (signed with the tx-sender's own signer key) as inputs to a child transaction that confirms the attacker's parent: [5](#0-4) 

### Impact Explanation

An unprivileged remote attacker who can reach the JSON-RPC port (reachable when `TX_SENDER_JSONRPC_BIND=0.0.0.0`) can:

1. **Drain the tx-sender's Bitcoin Core wallet** by repeatedly submitting CPFP-flagged transactions, each causing the tx-sender to fund a new fee-payer UTXO from the wallet.
2. **Corrupt the `try_to_send` queue** with arbitrary entries, interfering with legitimate bridge transaction scheduling.
3. **Cause the tx-sender to broadcast attacker-chosen transactions** (spending the attacker's own UTXOs) at the bridge's expense.

The tx-sender-managed balances (fee-payer wallet) are a scoped impact per the allowed impact gate.

### Likelihood Explanation

`0.0.0.0` is an explicitly supported, documented configuration value. Any deployment that exposes the tx-sender JSON-RPC to a non-loopback interface (e.g., containerized or cloud deployments where the service is reachable from other pods or the internet) is immediately exploitable with a single `curl` command — no credentials, no keys, no prior knowledge required.

### Recommendation

Add an authentication layer to `start_jsonrpc_server`. Options in increasing strength:
- **Shared secret / Bearer token**: validate a `Authorization` header in a `jsonrpsee` middleware layer before dispatching any method.
- **IP allowlist**: reject connections from addresses outside a configured CIDR at the server layer.
- **mTLS**: require a client certificate signed by the bridge's internal CA, consistent with how gRPC actor endpoints are protected elsewhere in Clementine.

At minimum, the server should refuse to start when `bind=0.0.0.0` and no authentication mechanism is configured.
