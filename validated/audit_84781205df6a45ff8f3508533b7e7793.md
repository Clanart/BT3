### Title
`SignableTransaction::new` omits the OP_RETURN output from fee/weight accounting, producing transactions that underpay the required fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `queueNewRewards` adding `queuedRewards` on top of the transfer amount without accounting for it, `SignableTransaction::new` appends the OP_RETURN `data` output to `tx_outs` but computes the transaction weight/vbytes — and therefore `needed_fee`, the minimum-relay-fee check, and the change amount — from `payments` alone. The extra output exists in the final signed transaction yet is invisible to the fee accounting, so the produced transaction's real fee rate is lower than `fee_per_vbyte` and can fall below the network minimum relay fee even though `TooLowFee` was checked.

### Finding Description
In `SignableTransaction::new`, when `data` is `Some`, an `OP_RETURN` output of up to ~92 serialized bytes (8-byte value + `OP_RETURN` + pushdata + ≤80-byte payload) is pushed into `tx_outs` at lines 194–202 of `networks/bitcoin/src/wallet/send.rs`. Immediately after, the weight is computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), which builds a dummy transaction whose outputs come only from `payments` (lines 85–94) — the OP_RETURN output is not included. The same omission occurs for the change path at lines 225–226 (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`).

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (lines 206, 227) underestimates the true required fee by `fee_per_vbyte * ~[12..92]` satoshis.
- The `NotEnoughFunds` check at line 215 and the change-value computation `input_sat - (payment_sat + fee_with_change)` at line 228 both use the underestimated fee, so the change output absorbs the difference — an unaccounted surplus, mirroring the trapped surplus of the reference bug.
- The `TooLowFee` check at line 211 compares against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` computed on the underestimated vbytes, so a transaction whose *actual* fee rate is below the relay minimum can be constructed, signed by `TransactionMachine`/`TransactionSignMachine` (lines 297+), and broadcast, only to be rejected by peers — leaving the payment unconfirmed and the inputs effectively unspendable until a new transaction is built.

The bug is reachable by any caller supplying a public `data: Some(vec)` parameter to `SignableTransaction::new` (data up to 80 bytes is explicitly permitted by the `TooMuchData` check at line 171).

### Impact Explanation
The signed transaction commits (via `Prevouts::All` sighash over all outputs) to an OP_RETURN output that was never priced. The wallet reports `needed_fee()`/`fee()` values inconsistent with the intended `fee_per_vbyte`, and in the worst case produces a transaction below `DEFAULT_MIN_RELAY_TX_FEE` that cannot propagate — a funds-frozen / incorrect-fee-formula condition, and excess funds are silently redirected into the change output (or into the fee when change is `None`) without being accounted as intended. This mirrors the reference report's "transferred amount includes an unaccounted component" class.

### Likelihood Explanation
Any use of the `data` field triggers it deterministically — no adversary needed. Exploitability for loss of funds is limited (the surplus goes to change/fee, not an attacker), but the minimum-fee bypass means a transaction can be produced that the Bitcoin network will not relay, which is a Medium-severity reliability/accounting defect within the wallet's public API surface.

### Recommendation
Include the OP_RETURN output in the weight/fee accounting. The cleanest fix is to have `calculate_weight_vbytes` take the fully-built `tx_outs` (or append the OP_RETURN `TxOut` inside it) so every output present in the final transaction is priced:

```rust
// networks/bitcoin/src/wallet/send.rs — build tx_outs (payments + data) first,
// then pass them to the weight calculation
let mut tx_outs = payments.iter().map(...).collect::<Vec<_>>();
if let Some(data) = &data { tx_outs.push(op_return_txout); }
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, None);
// and for the change path:
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, Some(&change));
```

### Proof of Concept
```rust
// Construct a transaction with a max-size OP_RETURN payload
let inputs = vec![received_output];            // sufficient funds
let payments = vec![(p2tr_script_buf(key).unwrap(), 1000)];
let tx = SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), 1).unwrap();

// The serialized transaction contains the ~92-byte OP_RETURN output,
// yet needed_fee() was computed as if it didn't exist.
// fee() / actual_vsize < 1 sat/vbyte, and with low fee_per_vbyte the real
// fee can fall below DEFAULT_MIN_RELAY_TX_FEE while new() still returns Ok.
let actual_vsize = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < actual_vsize * 1); // underpriced: OP_RETURN unaccounted
```
