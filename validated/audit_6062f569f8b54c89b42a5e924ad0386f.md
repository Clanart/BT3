### Title
Participants with a zero (identity) public key are still counted as full MuSig signers, inflating the member count and silently weakening the n-of-n threshold - (File: crypto/dkg/musig/src/lib.rs)

### Summary
`check_keys`, used by `musig_key_vartime`, `musig_key`, and `musig`, validates only that the key list is non-empty, fits in `u16`, and contains no duplicate encodings. It never rejects the identity point (`C::G::identity()`), which is the group-theoretic equivalent of "zero voting power" in the FrankenDAO finding: a party that contributes nothing to the group key is still registered as a full participant with its own binding factor, `Participant` index, and verification share. [1](#0-0) 

### Finding Description
In `musig`, every provided key is assigned a `Participant` index and inserted into `verification_shares`, and the aggregate `group_key` is `sum(binding_factor_i * key_i)`. If `key_i` is the identity, its multiexp term contributes nothing — the group key is unchanged — yet the participant count `n` (= `t`, since MuSig is n-of-n) still grows. [2](#0-1) 

The resulting `ThresholdKeys` uses `Interpolation::Constant(binding_factors)`, so signing requires all `n` "participants". The identity key, however, corresponds to secret share `0` — a value that is *publicly known*. Anyone can compute that participant's interpolated "share" (`binding_factor_i * 0 = 0` under Constant interpolation) and its contribution to any FROST signature. This is the direct analog of a zero-power voter still accruing `userCommunityScoreData` and inflating `totalCommunityScoreData.votes`: an entity with zero weight is counted as a real participant, distorting the accounting (`n`, `t`, `all_participant_indexes`, quorum-equivalent signing set size) used by all downstream consumers of `ThresholdParams`.

Notably, the rest of the crate family treats zero as a privileged, invalid value: `Participant::new` rejects `0` [3](#0-2) , `ThresholdParams::new` rejects `t == 0`/`n == 0` [4](#0-3) , `scale` rejects a zero scalar [5](#0-4) , and PedPoP uses `random_nonzero_F` for every coefficient [6](#0-5) . `check_keys` is the only place a zero-weight contribution is silently accepted.

### Impact Explanation
- **Threshold understatement**: an integrator building a supposed k-of-k MuSig from an externally supplied key list can end up with a group whose real security is (k - m)-of-(k - m), where m is the number of identity keys inserted. Every identity slot is trivially satisfiable by any party, so the *effective* required signers are fewer than `params().t()`/`n()` report — analogous to the report's `proposalThreshold`/`quorumVotes` being inflated by zero-power votes, except here the miscounting understates who must actually collude.
- **Accounting corruption**: `n`, `all_participant_indexes()`, and the length of `verification_shares`/`Constant` interpolation factors are all derived from the padded list; downstream logic (e.g., `coordinator/src/tributary/signing_protocol.rs` mapping `Participant` indexes to validator keys [7](#0-6) ) reasons about a participant set larger than the set of real key holders.
- **Unforgeable-blame asymmetry**: since identity contributes the zero share, honest participants cannot even blame the "participant" — `share_verification_statements` would accept a zero share against identity commitments — the forgery surface is structural, not attributable.

### Likelihood Explanation
Reachable whenever `musig`/`musig_key` is invoked over a key list influenced by an untrusted party (the exact public-input surface the rules allow — attacker-supplied keys fed to a `verify`/`sign`-adjacent API). Whether a serialized identity survives `C::read_G` upstream is ciphersuite-dependent (Ed25519/Ristretto accept identity encodings unless the caller separately checks), and nothing in `musig`, `check_keys`, `musig_key_multiexp`, or `ThresholdKeys::new` (`ThresholdKeys::new` only checks count and index bounds [8](#0-7) ) rejects it. Because impact requires an integrator to aggregate attacker-influenced keys without its own identity check, Likelihood is Medium; severity is Medium (miscounted threshold / weakened effective security rather than direct forgery).

### Recommendation
In `check_keys` (crypto/dkg/musig/src/lib.rs), reject `key.is_identity()` alongside the duplicate check, returning a dedicated error (e.g., `MusigError::IdentityKey`). Optionally, `ThresholdKeys::new` could defensively reject identity verification shares for `Interpolation::Constant`, since a constant-interpolated identity share implies a publicly known secret.

### Proof of Concept
```rust
// crypto/dkg/musig: a 2-"of"-2 that is really 1-of-1
use dkg::Participant;
use ciphersuite::{Ciphersuite, group::Group};
use zeroize::Zeroizing;

fn identity_participant_inflates_threshold<C: Ciphersuite>() {
    let context = [0u8; 32];
    let alice_secret = Zeroizing::new(C::F::random(&mut rand_core::OsRng));
    let alice_pub = C::generator() * *alice_secret;

    // Attacker-supplied "participant": the identity point (secret = 0, publicly known)
    let keys = vec![alice_pub, C::G::identity()];

    // Accepted — no identity check in check_keys
    let group = musig_key::<C>(context, &keys).unwrap();
    // The identity term contributes binding_factor * identity = identity,
    // so group == binding_factor(1) * alice_pub — controlled solely by Alice's key.

    let keys_machine = musig::<C>(context, alice_secret, &keys).unwrap();
    assert_eq!(keys_machine.params().n(), 2); // counted as 2 participants
    assert_eq!(keys_machine.params().t(), 2); // reported as 2-of-2
    // ...yet the second "share" is 0, satisfiable by anyone without a secret.
}
```

fn check_keys<C: Ciphersuite>(keys: &[C::G]) -> Result<u16, MusigError<C>> {
  if keys.is_empty() {
    Err(MusigError::NoKeysProvided)?;
  }

  let keys_len = u16::try_from(keys.len())
    .map_err(|_| MusigError::TooManyKeysProvided { max: u16::MAX, provided: keys.len() })?;

  let mut set = HashSet::with_capacity(keys.len());
  for key in keys {
    let bytes = key.to_bytes().as_ref().to_vec();
    if !set.insert(bytes) {
      Err(MusigError::DuplicatedParticipant(*key))?;
    }
  }

  Ok(keys_len)
}
