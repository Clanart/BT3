### Title
Symlinked working-directory files bypass repo-containment checks and leak arbitrary local files via image/diff preview - (File: `app/src/lib/git/diff.ts`)

### Summary
Git tracks symlinks as ordinary blobs whose content is the link target, and a malicious/attacker-controlled repository can commit a symlink (e.g. named `evil.png`) pointing to an arbitrary absolute path such as `/Users/<user>/.ssh/id_rsa` or `/etc/passwd`. When the user clones/fetches/checks out this repository, Desktop's change-list and diff-preview code paths read the file straight off disk with plain Node `fs` calls that transparently follow symlinks, instead of using the codebase's own symlink-safe helper.

### Finding Description
`getWorkingDirectoryImage` builds the file path with `Path.join(repository.path, file.path)` and passes it straight to `readFile` from `fs/promises`: [1](#0-0) 

Likewise, the syntax-highlighting code path used to preview text diffs reads working-directory content with `readPartialFile(Path.join(repository.path, file.path), ...)`: [2](#0-1) 

`readPartialFile` itself is a thin wrapper over `fs.createReadStream`, with no `lstat`/symlink check at all: [3](#0-2) 

`file.path` originates from `git status --porcelain=2` parsing and is fully attacker-influenced content (any tracked or committed path/name, including a symlink entry), as parsed in `status-parser.ts`/`status.ts`: [4](#0-3) 

The codebase already recognizes that raw filesystem paths derived from repository content need "path traversal and symlink escape" protection — see the explicit `resolveWithin` guard used for reading conflict-resolution files: [5](#0-4) 

and for opening files via deep links: [6](#0-5) 

`resolveWithin` performs `realpath()` on both the root and the resolved path specifically to catch symlink escapes: [7](#0-6) 

But `getWorkingDirectoryImage` and `getNewFileContent` never call `resolveWithin` (or any `lstat` check) before touching the filesystem — the containment invariant the rest of the codebase enforces is silently skipped for these two read paths, exactly analogous to how `fs.openAsBlob()` skipped Node's permission-system checks that other `fs` APIs enforced.

### Impact Explanation
An attacker who controls a cloned/fetched repository (or a branch/PR the victim checks out) can commit a symlink with an image-like extension (`.png`, `.jpg`, etc., per `imageFileExtensions`) pointing at any file readable by the victim's OS user account (SSH keys, cloud-credential files, `.netrc`, browser cookie stores, other repos' `.git/config`, etc.). Simply selecting that changed file in Desktop's Changes/History diff view triggers `getWorkingDirectoryImage`/`getNewFileContent`, which reads the target file's bytes off disk and renders them as a base64 data URI (or feeds them to the syntax highlighter). The bytes become inspectable via the renderer (dev tools, "Copy Image", clipboard, or screen contents), constituting an arbitrary local file read outside the repository — the exact class of "permission system bypass leading to disclosure of files an attacker should not be able to read" described in the report.

### Likelihood Explanation
Likelihood is moderate-to-high: no special local access, admin rights, or social engineering beyond normal repo interaction is required — merely cloning/fetching a hostile repo and viewing the Changes/History pane (a routine action) is sufficient to trigger the read. The attacker fully controls the symlink target and filename extension, and the vulnerable code paths (`getWorkingDirectoryImage`, `getNewFileContent`) are on the default "view a changed file" flow.

### Recommendation
Route `getWorkingDirectoryImage` and `getNewFileContent` (and any other direct `fs`/`readPartialFile` reads keyed off `file.path`) through `resolveWithin`/`resolveWithinPosix` (already implemented in `app/src/lib/path.ts`) before reading, and/or `lstat` the target path first and refuse to read (or clearly flag) entries whose mode is a symlink, mirroring the existing guard in `copilot-conflict-context.ts`.

### Proof of Concept
1. On a machine controlled by the attacker, create a repo containing a symlink: `ln -s /Users/victim/.ssh/id_rsa evil.png; git add evil.png; git commit -m "add image"`.
2. Push this repo (or a branch/PR) and get the victim to clone/fetch/checkout it in GitHub Desktop.
3. In Desktop, open the Changes/History view and select `evil.png`.
4. `getWorkingDirectoryImage` (`app/src/lib/git/diff.ts:926-937`) reads `Path.join(repository.path, 'evil.png')` via `fs.readFile`, which follows the symlink and returns the contents of `/Users/victim/.ssh/id_rsa` base64-encoded into the rendered `<img>` data URI — disclosing the private key content outside the repository, with no containment check ever invoked.

```typescript
export async function readPartialFile(
  path: string,
  start: number,
  end: number
): Promise<Buffer> {
  return await new Promise<Buffer>((resolve, reject) => {
    const chunks = new Array<Buffer>()
    let total = 0

    createReadStream(path, { start, end })
      .on('data', (chunk: Buffer) => {
        chunks.push(chunk)
        total += chunk.length
      })
      .on('error', reject)
      .on('end', () => resolve(Buffer.concat(chunks, total)))
  })
```
