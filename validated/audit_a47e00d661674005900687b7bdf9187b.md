Based on my investigation, I found `_findPullRequestBranch()` in `app/src/lib/stores/app-store.ts` which passes `headCloneUrl` — a value taken directly from a GitHub API pull-request object's `head.repo.clone_url` field (attacker-controlled, since anyone can open a PR from a fork with an arbitrary-looking remote) — straight into `addRemote()` and then `git fetch`, with no protocol/scheme allowlist anywhere in that path.

### Title
Unvalidated PR `head.repo.clone_url` from GitHub API is passed to `git remote add` / `git fetch` without scheme restrictions - (File: app/src/lib/stores/app-store.ts)

### Summary
When a user opens a pull request from a fork (via the PR list, a notification, drag-and-drop cherry-pick, or the `x-github-client://openRepo/...?pr=NNN` deep link), Desktop calls `_checkoutPullRequest()` → `_findPullRequestBranch()` with `headCloneUrl` taken verbatim from the `IAPIPullRequest.head.repo.clone_url` field returned by the GitHub API. [1](#0-0) [2](#0-1) 

### Finding Description
`_findPullRequestBranch()` looks for a matching existing remote and, if none is found, calls `addRemote(repository, forkRemoteName, headCloneUrl)` directly, then performs `git fetch` on that new remote via `_fetchRemote()`. [3](#0-2) 

`addRemote()` shells out to `git remote add name url` with no validation of the URL's scheme: [4](#0-3) 

`head.repo.clone_url` is part of the pull request JSON returned by the GitHub REST API for a PR, and its value is controlled by whoever opened the PR (they can rename their fork, or in Enterprise/self-hosted contexts influence how this field is rendered) — this makes it an "attacker controls a GitHub API object" input as defined by the valid-impact scope. Nowhere in this call chain (`_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote`/`_fetchRemote` → `fetch()` in `app/src/lib/git/fetch.ts`) is the URL scheme checked against an allowlist (e.g., restricting to `https:`/`ssh:`/`git:`), unlike the clone path which at least validates the *destination directory* via `isClonePathSensitive()` but never validates the *source URL scheme*. [5](#0-4) [6](#0-5) 

Git historically has supported dangerous "smart" transports (e.g. `ext::`) that can be abused to run arbitrary local commands when `git fetch`/`clone` is invoked against a URL using that scheme (the class of bug behind CVE-2017-1000117 and later `protocol.ext.allow` hardening in modern Git). Because Desktop never restricts the transport of `headCloneUrl` before handing it to `git remote add`/`git fetch`, whether this is exploitable in practice depends entirely on the installed Git version's own protocol allowlist defaults (`protocol.ext.allow=user`) — Desktop's own code provides no defense-in-depth here, unlike the deep-link `filepath` handling which does validate that a resolved path stays within the repository (`resolveWithin`) before use. [7](#0-6) 

### Impact Explanation
If the installed Git binary's protocol allowlist is permissive (or an older Git version is bundled/used), a malicious PR author could set their fork's remote/clone URL to an `ext::` (or similar) transport string that, when Desktop silently adds it as a remote and fetches from it, results in local command execution on the victim's machine — entirely through opening a PR that another Desktop user views/checks out, satisfying the "GitHub API object" attacker vector and "code execution" impact criteria.

### Likelihood Explanation
Likelihood is **moderate to low**: modern Git (>= 2.11.1 with subsequent hardening) disables `ext::`/other dangerous transports by default (`protocol.ext.allow=user`, requiring explicit opt-in), and dugite/Desktop bundles a maintained Git version, so exploitation requires either an outdated bundled Git or a locally misconfigured `protocol.*.allow`. However, the underlying design flaw — no application-level scheme validation on API-supplied clone URLs before shelling out to git remote/fetch — is a real gap that exists independent of Git's own hardening, and is inconsistent with the defense-in-depth already applied elsewhere in the codebase (e.g., `isClonePathSensitive`, `resolveWithin` for `filepath`, `testForInvalidChars` for branch names).

### Recommendation
Before calling `addRemote()`/`_fetchRemote()` with a URL sourced from the GitHub API (`head.repo.clone_url`, `base.repo.clone_url`), validate that the URL's scheme is restricted to an explicit allowlist (`https:`, `http:`, `ssh:`, `git:`) using the existing `parseRemote()`/`remote-parsing.ts` helpers, rejecting anything else (e.g. `ext::`, `fd::`, `file://` where inappropriate) before it ever reaches `git remote add`. This mirrors the scheme validation already recommended pattern used for clone-path safety.

### Proof of Concept
Not independently verifiable without a live Git binary configuration and a controllable PR-fork rename/API response; would require: (1) a Desktop instance paired with a Git version/config that has `protocol.ext.allow` (or another risky transport) enabled, and (2) crafting a PR whose `head.repo.clone_url` is a specially-formed transport URL, then having the victim open that PR from Desktop (via UI, notification, or the `openRepo` deep link with `pr=`). This dependency on the underlying Git transport hardening state is the main uncertainty in confirming real-world exploitability from the application code alone.
