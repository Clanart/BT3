### Title
Unhandled `IndexError` in `is_clvm_canonical` from an attacker-controlled CLVM atom length prefix can crash mempool spend-bundle admission - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the length-prefix encoding of CLVM atoms in an unprivileged submitter's `puzzle_reveal`/`solution` bytes without ever validating that the decoded atom length keeps the parse cursor inside the buffer. This mirrors the CVE-2021-44502 bug class: an attacker-controlled "size" field is trusted and used to advance/derive a memory offset without a bounds check.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads a length-prefix byte and, depending on its top bits, reads 0–5 additional prefix bytes to build `atom_len`, an attacker-controlled integer that can be as large as `0x3FFFFFFFF` (6-byte prefix form) purely from the encoded bytes: [1](#0-0) 

The function returns `1 + prefix_len + atom_len` as the number of bytes the atom occupies, without ever checking that this value is consistent with the remaining length of `clvm_buffer`.

`is_clvm_canonical(clvm_buffer)` uses this return value to advance its own `offset` cursor: [2](#0-1) 

Because `atom_len` is attacker-controlled and unchecked, `offset` can be pushed far beyond `len(clvm_buffer)`. On the next loop iteration, `b = clvm_buffer[offset]` (line 199) performs a Python `bytes` index access with an out-of-range index, which raises an uncaught `IndexError` (Python's memory-safe equivalent of the C `memset`-style out-of-bounds condition in the CVE).

This function is called directly on every submitted coin spend's puzzle reveal and solution during mempool admission: [3](#0-2) 

`validate_spend_bundle()` is invoked from `add_spend_bundle()`: [4](#0-3) 

I was not able to fully trace, within the tool budget available, whether every caller of `add_spend_bundle()`/`validate_spend_bundle()` (e.g. the RPC/peer transaction-admission entry points) wraps this call in a blanket `try/except Exception`. The visible code around `add_spend_bundle()` only handles the `Err` return value, not exceptions raised inside `validate_spend_bundle()`, and no `except IndexError` or generic exception handler is visible around the `is_clvm_canonical` calls themselves.

### Impact Explanation
If the `IndexError` from `is_clvm_canonical` is not caught by an upstream generic exception handler, an unprivileged actor could submit a single spend bundle whose puzzle reveal or solution ends in a truncated but syntactically-valid-looking non-canonical atom prefix (e.g., a 6-byte `0xFC` prefix encoding a huge length near the end of the buffer). This would raise an unhandled exception during `validate_spend_bundle()`, which — depending on how the calling task/coroutine handles exceptions — could disrupt mempool spend-bundle processing for that request path. This falls into the "spend-triggered transaction-processing halt" impact category called out in scope, though the exact blast radius (single request failure vs. broader mempool manager disruption) depends on exception handling in code not fully visible in this pass.

### Likelihood Explanation
`is_clvm_canonical` is on the hot path of ordinary mempool admission — it runs on every `puzzle_reveal` and `solution` of every coin spend in every submitted spend bundle, with no prior gating. Constructing a byte sequence with a long/legal-looking multi-byte length prefix whose length field, decoded, exceeds the buffer size requires no special privileges and is a purely local, deterministic crafting exercise (same class of PoC used in `chia/_tests/clvm/test_chialisp_deserialization.py`'s `serialized_atom_overflow` helper, which builds exactly this kind of oversized-prefix payload for other tests).

### Recommendation
In `is_atom_canonical`, after computing `atom_len` and `prefix_len`, validate that `offset + prefix_len` and the eventual `offset + 1 + prefix_len + atom_len` stay within `len(clvm_buffer)` before returning, and have `is_clvm_canonical` treat an out-of-bounds atom length as "not canonical" (return `False`) rather than allowing the cursor to run past the buffer end. Add explicit bounds checks mirroring those already used in `chia/full_node/full_block_utils.py` (`skip_bytes`, `skip_list`), which do check `n > len(buf)` before trusting a length field.

### Proof of Concept
Not independently executed in this pass; based on code inspection, the following should reproduce the crash path:
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0xFC prefix = 6-byte total-length atom header, encoding a huge atom_len
# far exceeding the actual (short) buffer that follows.
malicious_buf = bytes.fromhex("fc03ffffffff")  # header claims atom_len = 0x3FFFFFFFF, no atom bytes present
is_clvm_canonical(malicious_buf)  # expected: IndexError instead of `False`
```
This matches the "not canonical" test vectors already present in the repo's test suite (`test_atom_not_canonical` in `chia/_tests/core/mempool/test_mempool_manager.py`), which exercise `is_atom_canonical` directly but do not exercise `is_clvm_canonical`'s cursor-overrun behavior when such an atom appears mid-buffer with insufficient trailing bytes — this gap is where the unhandled `IndexError` would surface.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
