## Title
Missing lower-bound check on `range.split('...')` causes unhandled exception when rendering attacker-controlled "compare" links - (File: `app/src/lib/markdown-filters/commit-mention-link-filter.ts`)

## Summary
The go-ethereum fix addressed a missing-length-check pattern: code split/derived a slice from external input and indexed into it without verifying the slice actually had the expected number of elements, causing a panic when the slice was shorter than assumed (`len(txs) == 0`). The same broken-invariant pattern — checking only an *upper* bound on a `.split()` result and then indexing an element that assumes a *lower* bound — exists in `CommitMentionLinkFilter.getRefFromComparePath`.

## Finding Description
`getRefFromComparePath` parses the path portion of an autolinked commit-mention URL that matches the `compare/<range>` pattern: [1](#0-0) 

```
const shas = range.split('...')
if (shas.length > 2) {
  return null
}
const slashIndex = shas[1].indexOf('/')
```

The code guards against `shas.length > 2` (too many `...` separators) but never checks that `shas.length` is at least `2`. Since `comparePath` is defined as `/^compare\/(?<range>.+)$/` (any non-empty string, no requirement that it contain `...`), a `range` value with **no** `...` in it (e.g. `compare/deadbeef`) produces `shas = ["deadbeef"]` (`length === 1`), which passes the `> 2` check, and then `shas[1]` is `undefined`. Calling `.indexOf('/')` on `undefined` throws an unhandled `TypeError`.

This filter runs over markdown-rendered content (commit messages, PR/issue bodies, etc.) that is fully attacker-controlled: any GitHub object containing a link whose `href` and `innerText` are identical and match `https://github.com/<owner>/<repo>/compare/<anything-without-triple-dot>` will trigger `filter()` in `CommitMentionLinkFilter` (see the tree-walker at lines 102-114, which accepts any anchor whose `href === innerText` and matches `commitMentionUrl`).

## Impact Explanation
This is analogous to the go-ethereum "zero index" defect: a bounds check that verifies only one side of an invariant, letting a shorter-than-expected array reach an unchecked index access. In Desktop, it results in an unhandled exception thrown from within the markdown-filter pipeline while rendering attacker-supplied content (a commit message, PR description, or comment containing a crafted "compare" link). At minimum this breaks rendering of that content; depending on how/where the filter promise chain is awaited, an uncaught rejection could propagate and destabilize the rendering of that view.

I was not able to fully trace, within the remaining investigation budget, whether `filter()` calls in the broader markdown-filter pipeline are wrapped in a try/catch that swallows exceptions per-node (which would reduce this to a silent rendering failure) or whether an uncaught rejection can escape to a broader scope. Given the report's own bug class is fundamentally a crash/DoS class (which the task's valid-impact criteria explicitly excludes as "DoS/rate-limit-only"), I cannot confidently claim this rises above that excluded category without confirming a code-execution, data-exfiltration, or corruption-of-commit outcome downstream of the exception.

## Likelihood Explanation
Reaching the vulnerable line only requires the victim to view/render a piece of content (commit message, PR body, comment) containing a plain autolinked GitHub `.../compare/<value>` URL with `<value>` not containing `...` — no local access, no elevated privileges, and no unnatural user steps (viewing PR/commit content in Desktop is normal usage). This makes the trigger condition trivial for anyone who can post to a repository/PR that the victim views in Desktop.

## Recommendation
Add an explicit lower-bound check before indexing:
```ts
const shas = range.split('...')
if (shas.length !== 2 || shas[0] === '' || shas[1] === '') {
  return null
}
```
or use optional access (`shas[1]?.indexOf('/')`) and treat `undefined` as "not a compare link."

## Proof of Concept
Render (via Desktop's commit/PR markdown pipeline) an anchor element such as:
```html
<a href="https://github.com/owner/repo/compare/deadbeef">https://github.com/owner/repo/compare/deadbeef</a>
```
`comparePath` matches with `range = "deadbeef"`; `shas = ["deadbeef"]`; `shas[1]` is `undefined`; `shas[1].indexOf('/')` throws `TypeError: Cannot read properties of undefined (reading 'indexOf')`.

**Note on confidence:** Because I could not confirm the ultimate blast radius of the uncaught exception (silent per-node failure vs. broader renderer disruption) within the available investigation, and because the underlying bug class mirrors the excluded "DoS/rate-limit-only" category from the report itself, this finding should be treated as a **plausible but not fully impact-confirmed** analog rather than a definitively qualifying vulnerability under the stated valid-impact bar.   private getRefFromComparePath(path: string) {
```typescript
    const match = path.match(this.comparePath)
    if (match === null || match.groups === undefined) {
      return null
    }

    const { range } = match.groups

    if (/\.(diff|path)$/.test(range)) {
      return null
    }

    const shas = range.split('...')
    if (shas.length > 2) {
      return null
    }

    const slashIndex = shas[1].indexOf('/')
    const secondSha = slashIndex >= 0 ? shas[1].slice(0, slashIndex) : shas[1]

    return {
      ref: `${this.trimCommitSha(shas[0])}...${this.trimCommitSha(secondSha)}`,
      filepathToAppend: slashIndex >= 0 ? shas[1].slice(slashIndex) : undefined,
    }
  }
```
