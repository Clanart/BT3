Based on my research, I found a concrete, local analog of the reported bug class: a stale-authority-on-upgrade invariant break, but in the **lazy module initialization** subsystem (`init.move` / `code.move`), not a hypothetical DAO-address case.

### Title
`init::reset_initialized` re-initialization-on-upgrade contract is never invoked from the publish path, so `only_once=false` initializers silently stop re-running after a module upgrade - (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
The `aptos_framework::init` module implements a self-init mechanism (`internal_maybe_initialize`) used by newly-published/upgraded modules to lazily get a signer for one-time or per-upgrade initialization. `init.move` defines a `package fun reset_initialized`, documented as "Called on code upgrade to request re-run of initialization for the named module," which is supposed to clear the `only_once = some(false)` marker so that non-`only_once` initializers re-run after each upgrade [1](#0-0) . However, a repo-wide search for callers of `reset_initialized` finds it referenced only inside `init.move` itself and a test file — there is no call site in `code::publish_package` (the actual upgrade entry point) or in `object_code_deployment::upgrade`, which are the two functions that mutate on-chain module bytecode [2](#0-1) [3](#0-2) .

### Finding Description
`internal_maybe_initialize(only_once)` marks a module "initialized" the first time it is called and, for `only_once = false`, is meant to be re-armed on every subsequent code upgrade so the initializer function runs again with fresh module logic [4](#0-3)  and [5](#0-4) . That re-arming is supposed to happen via `reset_initialized`, called "on code upgrade" per its own doc comment [1](#0-0) .

The actual upgrade code path, `code::publish_package`, only performs two `init`-related actions: it records/updates the object's `deploy_owner` for the self-init ownership guard, and it runs compatibility/upgradability checks — it never calls `init::reset_initialized` for the modules being (re)published [6](#0-5) . The object-code-deployment `upgrade` entry function also only forwards to `code::publish_package_txn` without touching `init` state [3](#0-2) .

This is directly analogous to the external report's bug class: an authoritative/behavioral invariant (`DAO` address in `Reserve.sol`, here: "module is due for re-init after upgrade") is supposed to be refreshed as part of an upgrade action, but the code path responsible for the upgrade (`moveDao` / here `publish_package`) never calls the function that would perform that refresh (`setIncentiveAddresses` / here `reset_initialized`), leaving stale state after the upgrade.

### Impact Explanation
Any module relying on `internal_maybe_initialize(false)` to re-run its initializer after each upgrade (e.g. to migrate/re-derive resources, refresh capabilities, or reset per-upgrade configuration) will silently continue to see `option::none()` returned after the first initialization, because `state.only_once` remains `some(false)` from the original publish and is never cleared. This means upgraded module code can run indefinitely against stale initialization state instead of the intended freshly-reinitialized state, defeating the entire purpose of the `only_once=false` mode of this framework-level primitive. Since this is a shared framework module (`0x1::init`) that any Move package can depend on for reliable "reinit on every upgrade" semantics, incorrect behavior here affects the module-init/upgrade contract system-wide rather than one contract.

### Likelihood Explanation
This triggers deterministically and unconditionally whenever the `LAZY_MODULE_INITIALIZATION` feature is enabled and any package uses `internal_maybe_initialize(false)`, then gets upgraded via `code::publish_package` (both direct account publish and code-object upgrade paths funnel through it). No attacker action is needed — it is a straightforward logic gap in the framework's own upgrade flow. My repo-wide `grep_search` for `reset_initialized` found only the definition/tests in `init.move` and `init_module_api.rs`, with zero call sites in `code.move` or `object_code_deployment.move`, supporting that this is currently dead code in the shipped upgrade flow rather than a rarely-hit edge case.

### Recommendation
Call `init::reset_initialized(addr, module_name)` for every module in the package inside `code::publish_package` when it is invoked as an upgrade (i.e., when `index < len`, matching the existing upgrade branch that already runs per-module logic at line 209), mirroring how `record_deploy_owner` is already correctly re-invoked on every publish. Add/extend the existing test coverage in `init_module_api.rs` to assert that `only_once=false` initializers actually re-run after a real `code::publish_package`/`object_code_deployment::upgrade` invocation, not just via the internal test-only `reset_initialized` helper calls.

### Proof of Concept
1. Enable the `LAZY_MODULE_INITIALIZATION` feature.
2. Publish a module at address `0xcafe` whose entry function calls `init::internal_maybe_initialize(false)` and, when it returns `Some(signer)`, increments/mutates a resource (mirrors the `Counter` pattern used in `init_module_api.rs` [7](#0-6) ).
3. Call the entry function once — `Counter.value == 1`, and `only_once` is now recorded as `some(false)`.
4. Upgrade the package via `code::publish_package` (compat-upgrade) with new module bytecode.
5. Call the entry function again, expecting `internal_maybe_initialize(false)` to return `Some(signer)` again (per the documented "upgrade resets it" semantics) — instead it returns `None` because `check_and_set_initialized` sees `state.only_once = some(false)` already set and no code path called `reset_initialized` during step 4's `publish_package` execution, so `Counter.value` remains `1` instead of being reinitialized/re-run as documented.

**Confidence caveat:** the code-index truncated several internal lines of `code.move` (roughly lines 210–240) which I could not fully view due to indexing limits; I could not directly inspect every statement in that range. However, a comprehensive repo-wide text search for the exact call token `reset_initialized` found no invocation outside `init.move`'s own definition and test helpers, which is strong (though not microscopically exhaustive) evidence that no call site exists elsewhere in the framework. If a Devin session with full file access confirms a call site does exist in the omitted lines, this finding would be invalidated.

    /// upgraded since -- marks it initialized and returns a signer for its address; else returns
    /// `none`. Marking happens before the initializer runs, so a cyclic call terminates.
    ///
    /// The caller module is derived by the VM from the call stack, so a module can only initialize
    /// itself. Aborts if the feature is disabled (`ELAZY_MODULE_INITIALIZATION_NOT_ENABLED`), the
    /// caller is not module code (`EINVALID_INITIALIZE_CALLER`), or an object-hosted module changed
    /// owner since publish (`EOWNER_CHANGED_SINCE_DEPLOY`).
    public fun internal_maybe_initialize(only_once: bool): Option<signer> {
        assert!(
            features::is_lazy_module_initialization_enabled(),
            error::invalid_state(ELAZY_MODULE_INITIALIZATION_NOT_ENABLED),
        );
        let (addr, module_id) = get_caller_address_and_module_id();
        if (check_and_set_initialized(addr, module_id, only_once)) {
            option::none()
        } else {
            // Guard only when actually minting: a legitimate transfer after initialization must not
            // brick ordinary calls. An abort here rolls back the mark set above.
            assert_may_self_initialize(addr, module_id);
            option::some(create_signer::create_signer(addr))
        }
    }

        if (exists<InitializationState>(addr)) {
            let modules = &mut InitializationState[addr].modules;
            let module_id = module_id_from_name(module_name);
            if (modules.contains(&module_id)) {
                let state = modules.borrow_mut(&module_id);

                    state.only_once = option::none();

    /// Returns true if the module is already initialized. Otherwise marks it initialized, recording
    /// `only_once`: if true the entry survives upgrades (initializer never re-runs); if false an
    /// upgrade resets it (initializer re-runs).
    fun check_and_set_initialized(addr: address, module_id: ModuleId, only_once: bool): bool {
        ensure_module_state(addr, module_id);
        let state = InitializationState[addr].modules.borrow_mut(&module_id);
        if (state.only_once.is_some()) {
            true
        } else {
            state.only_once = option::some(only_once);
            false
        }
    }

        let allowed_deps = check_dependencies(addr, &pack);

    public entry fun upgrade(
        publisher: &signer,
        metadata_serialized: vector<u8>,
        code: vector<vector<u8>>,
        code_object: Object<PackageRegistry>,
    ) {
        let publisher_address = signer::address_of(publisher);
        assert!(
            object::is_owner(code_object, publisher_address),
            error::permission_denied(ENOT_CODE_OBJECT_OWNER),
        );

        let code_object_address = code_object.object_address();
        assert!(exists<ManagingRefs>(code_object_address), error::not_found(ECODE_OBJECT_DOES_NOT_EXIST));

        let extend_ref = &borrow_global<ManagingRefs>(code_object_address).extend_ref;
        let code_signer = &extend_ref.generate_signer_for_extending();
        code::publish_package_txn(code_signer, metadata_serialized, code);

        event::emit(Upgrade { object_address: signer::address_of(code_signer), });
    }
