### Title
`resolveWithin()` uses an unanchored `startsWith` prefix check, allowing sandbox-escape via sibling-directory name confusion when opening a deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` in `app/src/lib/path.ts` is the shared guard used to make sure an attacker-influenced relative path cannot escape a trusted root directory. It is invoked directly on a `filepath` parameter that comes from a `x-github-client://openRepo/...` deep link that a user can be tricked into clicking, via `Dispatcher.openRepositoryFromUrl()`. The containment check at the end of the function compares resolved paths with a plain string `startsWith`, which is not anchored on a path-separator boundary, so a target directory whose name merely shares a prefix with the repository root (e.g. `myrepo` vs `myrepo-secrets`) is incorrectly treated as "inside" the root.

### Finding Description
`app/src/lib/path.ts` `_resolveWithin()`: [1](#0-0) 

The final line is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a classic CWE-22-style prefix-check flaw: `"/Users/victim/Documents/GitHub/myrepo-evil".startsWith("/Users/victim/Documents/GitHub/myrepo")` evaluates to `true` even though `myrepo-evil` is a completely different, sibling directory, not a child of `myrepo`. The correct check needs to verify that `realResolved === realRoot` or `realResolved.startsWith(realRoot + path.sep)`.

This helper is the sole containment guard used when the app opens a `filepath` supplied via an untrusted x-callback-url deep link: [2](#0-1) 

The only other check applied before `resolveWithin` is `isAbsolute(filepath)`, which does nothing to stop a `../`-relative path that walks up out of the repo and back down into a same-prefixed sibling folder. Because GitHub Desktop deduplicates clone directory names by appending suffixes (`myrepo`, `myrepo-1`, `myrepo-2`, etc. — see the dedicated `repositories-clone-grouping-test.ts` test suite, which exists precisely because this naming collision behavior is a real, common occurrence for users with multiple related repos/forks), it's realistic for a victim to already have two repositories on disk whose paths share this kind of prefix (e.g., a fork `project` and its upstream clone `project-upstream`, or duplicate clones `project` / `project-1`).

The same guard is reused for filesystem paths coming from repository content as well: [3](#0-2) 
which resolves file paths taken from a Git conflict/merge, another attacker-influenced source (a crafted commit in a fetched/merged branch).

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openRepo/<url>?filepath=../<sibling-dir-name>/<secret-file>` link can cause GitHub Desktop to call `shell.showItemInFolder(resolved)` on a file located in a directory outside the intended repository root, as long as that sibling directory's name has the repo's directory name as a string prefix. This satisfies the report's required impact class: "a link or deep link the user clicks... resulting in file read outside the repo" — `showItemInFolder` reveals/selects the file in the OS file manager, disclosing its existence/location and, depending on the file manager, its content preview, without the user ever intending to browse that folder. The same broken primitive additionally weakens the Copilot conflict-resolution file reader, which could be induced (via a crafted commit path in a fetched/merged repository) to read file content from a similarly-named sibling directory and feed it into AI request context.

### Likelihood Explanation
Exploitation requires: (1) the victim has GitHub Desktop, (2) the victim has (or can be led to create) two local directories whose names share a prefix relationship of the kind Desktop itself produces on name collisions, and (3) the victim clicks a crafted deep link. Prefix-collision directory names are a routine, unremarkable occurrence for GitHub Desktop users (forks, re-clones, `-1`/`-2` suffixes are handled by dedicated app logic), so condition (2) is not a contrived edge case. No local/physical access, no admin rights, and no pre-existing malware are required — only clicking a link, matching the allowed "unprivileged... link or deep link the user clicks" attacker model.

### Recommendation
Fix the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to anchor on a path-separator boundary instead of a raw string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory sharing a name prefix (e.g., root `.../myrepo` vs target `.../myrepo-evil/secret.txt`) is rejected, complementing the existing `path-test.ts` symlink-escape tests, which do not cover this specific unanchored-prefix case.

### Proof of Concept
1. On disk, create two directories that a real GitHub Desktop user could plausibly have simultaneously:
   - `~/Documents/GitHub/myrepo` (the tracked repository, `origin` matching the URL used in the deep link)
   - `~/Documents/GitHub/myrepo-secrets/passwords.txt` (an unrelated sibling directory containing a sensitive file)
2. Attacker crafts and sends the victim a link:
   `x-github-client://openRepo/https://github.com/victim/myrepo?filepath=..%2Fmyrepo-secrets%2Fpasswords.txt`
3. Victim clicks the link. `handleAppURL` → `parseAppURL` → `Dispatcher.openRepositoryFromUrl` runs:
   - `isAbsolute('../myrepo-secrets/passwords.txt')` is `false`, so the absolute-path guard is bypassed.
   - `resolveWithin('~/Documents/GitHub/myrepo', '../myrepo-secrets/passwords.txt')` resolves to `~/Documents/GitHub/myrepo-secrets/passwords.txt`; `realResolved.startsWith(realRoot)` is `true` because the string `"…/GitHub/myrepo-secrets/passwords.txt"` starts with `"…/GitHub/myrepo"`.
   - The function therefore returns the resolved (out-of-repo) path instead of `null`.
4. `shell.showItemInFolder(resolved)` is called, revealing/selecting `passwords.txt` from the unrelated sibling directory in the victim's OS file manager — a file outside the repository the link claimed to open.

This PoC is derived from static code analysis of `app/src/lib/path.ts` and `app/src/ui/dispatcher/dispatcher.ts`; it has not been executed against a running build, so live confirmation in a Devin session is recommended before treating it as fully verified.

```typescript
  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
```
