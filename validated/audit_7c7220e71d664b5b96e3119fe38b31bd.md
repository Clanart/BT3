### Title
Untrusted donation to a PlotNFT's p2_singleton address raises an unhandled `ValueError` during wallet coin-state processing, permanently halting sync/transaction processing for that wallet - ([File: chia/wallet/plotnft_wallet/plotnft_wallet.py])

### Summary
`PlotNFT2Wallet.coin_added()` treats any coin sent to a plot-NFT's `p2_singleton_puzzle_hash` whose parent does not match the expected pool-reward parent-id pattern as an error condition and raises a bare `ValueError`, rather than ignoring or gracefully recording the unexpected coin: [1](#0-0) 

This is directly analogous to the reported `MarketMaker.getTargetBalance()` bug: a would-be invariant ("only genuine pool-reward coins are ever paid to this address") is enforced with a hard revert/exception instead of a tolerant check, and the address in question (`p2_singleton_puzzle_hash`) is a public, well-known destination that any unprivileged party can pay into — exactly like donating 1 wei to the AMM contract. The CHANGELOG itself documents that this exact class of issue ("coins sent by accident to the pool contract address") was previously a real incident that had to be fixed by making the wallet *ignore* such coins rather than choke on them: [2](#0-1) [3](#0-2) 

### Finding Description
`p2_singleton_puzzle_hash` for a PlotNFT is a puzzle hash that is publicly known/derivable (it is displayed to users specifically as the "pool contract address," used for plotting) and is subscribed to via `add_interested_puzzle_hashes` in `PlotNFT2Wallet.create()`: [4](#0-3) 

Because it is a `p2_singleton`-style puzzle (pay-to-anyone-who-can-satisfy-singleton-claim, but *creatable* by anyone), any wallet user or bot can send an arbitrary XCH payment to this address without any special privilege — this is the "spend-triggered" surface reachable by an ordinary spend bundle/transaction.

When such a coin is farmed/confirmed and observed by wallet sync, `coin_added` is invoked with `coin_data is None` and `coin.puzzle_hash == self.p2_singleton_puzzle_hash`. The code assumes the *only* legitimate way funds arrive at this address is as a genuine block/pool reward, identified by checking whether the coin's `parent_coin_info` bytes match the genesis-challenge prefix pattern used for real reward coins: [1](#0-0) 

If an attacker (or even an innocent/confused wallet user) simply sends a normal (non-reward) coin to that address — trivially achievable via `send_transaction`, exactly as demonstrated in existing test code that pays 100 mojos to a pool's `p2_singleton_puzzle_hash` in `test_absorb_self`: [5](#0-4) 

then `parent_coin_info[0:16]` will not equal `GENESIS_CHALLENGE[0:16]`, and `coin_added` raises `ValueError(f"A non-pooling reward coin was paid to PlotNFT with id: {self.plotnft_id}")` unconditionally. This exception is raised from deep inside the wallet's coin-state ingestion pipeline (`WalletStateManager._add_coin_state` → dispatch into per-wallet `coin_added`), the same code path used for every incoming coin during normal sync. An unhandled exception here is a hard failure of the wallet-state-manager's coin processing for that update; there is no catch/skip logic visible around this specific raise inside `coin_added`, so — unlike the pool-wallet's own reward-detection logic in `PoolWallet`, which simply filters unknown coins via `coin_to_height_farmed` lookups and silently skips non-reward coins (see `claim_pool_rewards`) — the newer `PlotNFT2Wallet` path chooses to hard-fail instead of ignore.

This mirrors the reported vulnerability precisely: an `assert`/hard-revert intended to encode an internal invariant ("all funds here are pool rewards") is trivially falsifiable by donating any ordinary coin to a public, unprivileged, well-known address, and the resulting exception is not something normal spend/consensus logic protects against — it is purely an application-level DOS on the wallet's own bookkeeping.

### Impact Explanation
If wallet sync processing for a PlotNFT2Wallet aborts on this unhandled `ValueError` while iterating coin states for the newly farmed/confirmed block range, it can prevent the wallet from making forward progress on subsequent coin-state updates for that wallet (or, depending on where the exception propagates to in the sync loop, potentially interrupt processing for the whole sync batch). This is a spend-triggered halt of wallet transaction processing: a single external donation transaction — something any counterparty, wallet user, or malicious actor with knowledge of a victim's PlotNFT `p2_singleton_puzzle_hash` (a value shown to users and used for advertising the pool/plotting address) can trivially submit — can render claim/absorb/travel operations for that plot-NFT wallet permanently broken until manual intervention (e.g., database repair or code fix), analogous to the reported freeze of AMM buy/sell capability. This qualifies as a spend-triggered transaction-processing halt affecting a pool-participant wallet path.

### Likelihood Explanation
Likelihood is high for any user whose plot-NFT `p2_singleton_puzzle_hash` becomes known to a third party (which is expected, since it is explicitly displayed/used for plotting/pool registration). No special privilege, timing, or race condition is required — a single standard `send_transaction` call from any wallet (as already exercised, for a different but structurally identical purpose, in the existing test suite) suffices to trigger the code path.

### Recommendation
In `PlotNFT2Wallet.coin_added`, do not raise on unexpected/non-reward coins observed at `p2_singleton_puzzle_hash`. Instead, mirror the tolerant handling already used elsewhere in the pooling code (e.g., `PoolWallet.claim_pool_rewards`, which simply skips coins not present in `coin_to_height_farmed`): log a warning and skip/ignore the coin (optionally still recording it as a plain incoming-XCH balance item) rather than raising `ValueError` and aborting coin-state processing.

### Proof of Concept
1. Create/observe a PlotNFT with a known `p2_singleton_puzzle_hash` (as shown via `pw_status`/`pprint_pool_wallet_state`, which explicitly prints this address to the user: `chia/cmds/plotnft_funcs.py:174-177`).
2. From any other wallet, submit an ordinary standard-wallet transaction paying an arbitrary amount to that `p2_singleton_puzzle_hash` (exactly as the test harness already does for a different scenario): [5](#0-4) 
3. Farm the block so the wallet's sync path observes the new coin via `coin_added` on the `PlotNFT2Wallet`.
4. Because the coin's `parent_coin_info` does not match the `GENESIS_CHALLENGE` prefix expected for genuine pool rewards, `coin_added` raises `ValueError("A non-pooling reward coin was paid to PlotNFT with id: ...")`: [1](#0-0) 
5. This uncaught exception occurs inside the wallet's coin-state processing pipeline, breaking further processing for the affected wallet's sync/claim/absorb operations until the offending state is somehow bypassed or the code is patched.

**Note on completeness:** I was not able to fully trace the exact exception-propagation boundary inside `WalletStateManager._add_coin_state`/the sync loop (i.e., whether there is an outer try/except that would down-grade this to a per-coin skip rather than aborting the whole sync batch) within the available tool budget. If such a broad catch-all exists at a higher layer, the severity could be lower than a full sync halt (though the wallet would still likely fail every subsequent processing of that address unless the specific coin is skipped). I recommend a Devin session review `chia/wallet/wallet_state_manager.py`'s `_add_coin_state` and its caller(s) to confirm whether/where exceptions raised from per-wallet `coin_added` implementations are caught, to precisely establish blast radius (single wallet vs. whole sync batch).
