## Title
Malicious git server can spoof `WWW-Authenticate: realm="GitHub"` to trigger an unrequested GitHub/Enterprise sign-in prompt, binding user credentials to an attacker-controlled endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Similar to the XVS Vault bug — where a security-relevant state (voting power) was cleared based on the wrong field (`reward token == XVS` instead of `pool token == XVS`), allowing state duplication — GitHub Desktop's credential trampoline classifies a git remote's trust level (`endpointKind`) using an attacker-influenced value (an HTTP `WWW-Authenticate` header returned by the remote server) instead of a value the app actually controls or verifies. This lets any git server (including a non-GitHub server the user is merely fetching/cloning from) impersonate "GitHub Enterprise" and cause Desktop to launch a real sign-in flow scoped to the attacker's own origin.

### Finding Description
When git needs credentials for a remote, Desktop's credential helper decides how to treat the endpoint via `getEndpointKind()`: [1](#0-0) 

If none of the hard checks (`isGist`, `isDotCom`, `isGHE`) match, the code falls back to trusting any `wwwauth[...]` header value forwarded from git — which originates from the HTTP response of the remote server itself — and if it contains `realm="GitHub"`, unconditionally classifies the endpoint as `'enterprise'`: [2](#0-1) 

This classification then drives `getCredential()`, which — because no account exists yet for this brand-new endpoint — invokes `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` binds the sign-in flow directly to the attacker's `origin` (not to github.com) via `beginEnterpriseSignIn` + `setSignInEndpoint(origin)`, then shows the standard Desktop `SignIn` popup: [4](#0-3) 

The broken invariant: the "is this a GitHub host" decision — which gates whether Desktop shows an authenticated GitHub sign-in dialog and later hands out stored account tokens for that host (via `findGitHubTrampolineAccount` matching origin) — is derived from a header value the remote server fully controls, rather than from a value the app independently verifies (Desktop does have `isGitHubHost()`, which does an out-of-band `/meta` probe and checks `x-github-request-id`, but that stronger check is only reached if the header heuristic doesn't already short-circuit the decision).

### Impact Explanation
A user cloning/fetching from any attacker-hosted git-over-HTTP remote (or a malicious proxy/MITM on a network the user's git client trusts) can trigger this path merely by having their git server return `401` with `WWW-Authenticate: realm="GitHub"` when Desktop's credential helper is invoked during clone/fetch/push. This causes an unsolicited "Sign in to GitHub Enterprise" dialog to appear, bound to the attacker's origin. If the user completes it (entering a PAT or completing OAuth/device flow scoped to what they believe is a legitimate enterprise login), the resulting `Account` (with token) is persisted via `AccountsStore.addAccount` and keyed by that origin. On subsequent operations against the same origin, `findGitHubTrampolineAccount` in `getGitHubCredential` will supply that stored token as HTTP Basic auth to the attacker's server automatically — i.e., silent credential exfiltration to an attacker-chosen endpoint, and an unauthorized account/credential binding created without deliberate user action in Preferences. This matches the "unauthorized OAuth or account binding" / "credential exfiltration" categories called out as valid impact.

### Likelihood Explanation
No local access, malware, or leaked credentials are required — only a git remote the app already talks to (the user's normal clone/fetch/push target) needs to return a crafted header, which is trivial for anyone operating the server (or capable of a network MITM on plain-HTTP/relayed HTTPS proxy scenarios). The existing stronger guard, `isGitHubHost()`'s `/meta` probe, is bypassed entirely because the `wwwauth[...]` branch in `getEndpointKind()` returns early before that check is reached.

### Recommendation
Do not let the git-forwarded `WWW-Authenticate` realm value alone classify an endpoint as an authoritative GitHub/Enterprise host for the purposes of triggering a sign-in prompt. At minimum, treat the header as a weak hint and always corroborate with the independent `isGitHubHost()` network check (the same one already used later in the function) before calling `ui.promptForGitHubSignIn()`, and surface the destination host prominently in the sign-in dialog so users can recognize it isn't the real github.com.

### Proof of Concept
1. Stand up an HTTP git server (attacker-controlled) at `https://evil.example.com/repo.git`.
2. Configure it to respond to unauthenticated git-http-backend requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, clone/add `https://evil.example.com/repo.git` as a remote and perform a fetch.
4. Git invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler`) with the `wwwauth[0]=Basic realm="GitHub"` field forwarded in the credential protocol payload.
5. `getEndpointKind()` matches `realm="GitHub"` and returns `'enterprise'` [5](#0-4) ; since no account exists for `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, popping the native Desktop "Sign in to GitHub Enterprise" dialog bound to that origin.
6. If the victim signs in, the resulting token is stored keyed to `evil.example.com` and will be auto-attached to future requests to that host.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
