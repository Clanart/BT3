### Title
Stateful global regex in `testForInvalidChars` lets a crafted `x-github-client://openRepo` deep-link bypass branch-name validation - ([File: app/src/lib/sanitize-ref-name.ts])

### Summary
`parseAppURL` is the entry point for `x-github-client://openRepo/...` deep links, which are fully attacker-controlled (a malicious website or email can construct such a link and get the user to click it). It sanitizes the `branch` query parameter using `testForInvalidChars` before allowing it to flow into `git clone -b <branch>`. That validator uses a module-level `RegExp` literal that carries the `g` (global) flag and is reused with `.test()`, which is stateful across calls because `RegExp.prototype.test` advances `lastIndex` on every match when the `g` flag is set.

### Finding Description
The regex is defined once at module scope and shared by every call to `testForInvalidChars`: [1](#0-0) 

Because the regex object (and thus its `lastIndex`) persists between invocations, and `testForInvalidChars` only calls `.test()` (never resetting `lastIndex` or recreating the regex), a prior successful match leaves `lastIndex` pointing past the start of the string. On a subsequent call — triggered by a second, differently-crafted `openRepo` deep link — the engine resumes scanning from the stale `lastIndex` instead of position 0, so characters earlier in the new string that would normally be rejected (control chars, space, `~ ^ : ? * [ \ | " < >`, `@{`, leading/trailing dot, etc.) can be skipped and the function incorrectly returns `false` ("no invalid chars found").

The call site is the only consumer of this function: [2](#0-1) 

A validated (but not re-sanitized) `branch` is then handed to the dispatcher and ultimately into `git clone`: [3](#0-2) 

Unlike the `url` field, which is protected by the `--` argv separator before it's passed to `git`, `options.branch` is pushed as the literal value of `-b` *before* the `--` separator with no additional escaping — its only protection is `testForInvalidChars`. This is the broken invariant: the deep-link handler assumes `testForInvalidChars` deterministically rejects any string containing disallowed ref characters, but the stateful `g`-flag regex makes that guarantee false for the second (and every subsequent) call in the process lifetime.

### Impact Explanation
This breaks the intended "no illegal ref characters may reach git" invariant for a fully unprivileged, attacker-controlled input path (`x-github-client://openRepo/<url>?branch=<branch>`). A branch value that should have been rejected (e.g., containing `~`, `^`, `:`, control characters, or the `@{` magic sequence) can instead be passed straight into `git clone -c init.defaultBranch=... clone --recursive -b <branch> -- <url> <path>`, defeating the sanitization step that is the only thing standing between untrusted deep-link input and the `git` argv. Depending on which characters slip through, this can range from unexpected git ref-parsing behavior to enabling further downstream primitives that depend on this same "no invalid ref chars" guarantee.

### Likelihood Explanation
The trigger only requires the victim to click two attacker-supplied `x-github-client://openRepo` links (or one link processed twice, e.g., via the app's existing multi-argument/second-instance handling in `handleCommandLineArguments`/`handleAppURL`) — no local access, credentials, or elevated privileges are needed. The first link "poisons" the shared regex's `lastIndex`; the second, malicious link exploits the skip. Because `testForInvalidChars` is invoked exactly once per parsed URL and the regex object is never reset between calls, the precondition is trivially satisfiable by an external attacker who controls link content and delivery (e.g., two links opened in quick succession from a webpage).

### Recommendation
Do not reuse a `g`-flagged `RegExp` object across `.test()` calls. Either:
- Remove the `g` flag from `invalidCharacterRegex` when it's only used for boolean testing (keep a separate non-global regex for `testForInvalidChars`), or
- Reset `invalidCharacterRegex.lastIndex = 0` before each `.test()` call, or
- Rewrite `testForInvalidChars` to use `String.prototype.match`/`RegExp.prototype.exec` in a way that doesn't rely on shared mutable state, e.g. `new RegExp(invalidCharacterRegex.source).test(name)`.

### Proof of Concept
1. Visit/click `x-github-client://openrepo/https://github.com/a/a?branch=bad%20name` (a branch containing a space, which is in the disallowed set). `parseAppURL` calls `testForInvalidChars('bad name')`, which matches the space, returns `true`, and the action is correctly rejected as `unknown` — but the shared regex's `lastIndex` is now advanced past the match.
2. Immediately click a second link: `x-github-client://openrepo/https://github.com/a/a?branch=%7Eevil%3Aref`, i.e. branch `~evil:ref` (both `~` and `:` are disallowed characters). Because `invalidCharacterRegex.lastIndex` was left non-zero from step 1, `.test()` resumes scanning from that offset in the new string and can miss the leading `~`/`:` characters, returning `false`.
3. `parseAppURL` treats the action as valid `open-repository-from-url` with `branch: "~evil:ref"`, which is forwarded to `dispatcher.dispatchURLAction` → clone flow → `git clone ... -b ~evil:ref -- <url> <path>` in `app/src/lib/git/clone.ts`, bypassing the intended ref-name sanitization entirely.

(Note: exact exploitability of specific character sequences for further escalation beyond git ref-parsing anomalies was not verified further within available search iterations; the core, verified defect is the stateful global-regex validation bypass itself.)

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
