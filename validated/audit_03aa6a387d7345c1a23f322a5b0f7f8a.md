## Analysis

The regex bypass is real, and the interceptor gap is real, but I could not fully confirm whether Electron's main-process window-open gating (`setWindowOpenHandler`/`will-navigate` in `app/src/main-process/main.ts`) provides an additional backstop for a video's native context-menu navigation before it reaches `onMarkdownLinkClicked`. I found references to these handlers but ran out of budget to inspect their implementation, so the ultimate reachable impact (vs. a renderer-level invariant break) is not fully verified.

### Title
Host-boundary-free regex in `githubAssetVideoRegex` lets attacker-controlled origins become `<video src>`, bypassing the anchor-only link interceptor - (File: `app/src/lib/markdown-filters/video-url-regex.ts`)

### Summary
`githubAssetVideoRegex` only checks that the resolved anchor `href` *starts with* the literal string `https://user-images.githubusercontent.com`, with no delimiter enforcing that this is the actual hostname boundary. Combined with the fact that the "extension" alternation includes an empty-string option, the effective check degenerates to "starts with this string." `VideoLinkFilter.filter` then trusts this and assigns the full attacker-influenced URL to `videoNode.src` without further validation, replacing the original anchor. Because `SandboxedMarkdown.setupLinkInterceptor` only vets clicks whose target `closest('a')` resolves to a real `<a>` element, a `<video>` element's native browser controls/context-menu (e.g. "Open video in new tab", "Copy video address") never pass through the `/^https?:/.test(a.protocol)` check or the `onMarkdownLinkClicked` callback at all.

### Finding Description
`githubAssetVideoRegex.test(node.firstChild.href)` in `getGithubVideoLink` [1](#0-0)  is the sole gate for turning a markdown auto-link into a `<video>` element. The regex is built as `^` + escaped `https://user-images.githubusercontent.com` + `.+` + `(mp4|webm|ogg|mov|qt|avi|wmv|3gp|mpg|mpeg|)$` [2](#0-1) . Two problems compound:

1. There is no boundary character (`/`, `.`, or `$`) required immediately after the literal host string, so any URL whose string representation merely begins with that prefix matches — e.g. a resolved href of `https://user-images.githubusercontent.com.attacker.example/x` satisfies `^https://user-images\.githubusercontent\.com` followed by `.+`.
2. The trailing extension group includes an empty alternative (`...|mpeg|)$`), so the "extension" requirement is not actually enforced — `.+` will always be able to consume to end-of-string and match the empty alternative, making the regex effectively `^https://user-images\.githubusercontent\.com.+$` (case-insensitive).

Because the check is run against `node.firstChild.href` — the browser-resolved absolute URL — rather than parsing the URL and comparing `url.hostname === 'user-images.githubusercontent.com'`, an attacker who controls markdown content (issue/PR/comment body, commit message, etc., all attacker-controlled per scope) can craft a link whose *resolved* href starts with the trusted prefix but actually points at an attacker-registered origin. `VideoLinkFilter.filter` unconditionally does `videoNode.src = videoSrc` [3](#0-2) , producing a `<video>` element pointing at that attacker origin.

Separately, `setupLinkInterceptor` — the only place where `onMarkdownLinkClicked` and the `/^https?:/.test(a.protocol)` scheme check are applied — only fires for click targets whose `closest('a')` is non-null [4](#0-3) . A `<video>` element is not an `<a>`, so any interaction with it (native context menu "Open video in new tab", "Copy video address", double-click fullscreen navigation, etc.) is entirely outside this code path — it is never inspected, never passed to `onMarkdownLinkClicked`, and never subjected to the https-only anchor invariant the interceptor is meant to enforce.

### Impact Explanation
This breaks the intended invariant "only https anchors, vetted through `onMarkdownLinkClicked`, are user-navigable" for a class of elements (`<video>`) that the markdown pipeline itself introduces. Combined with the regex's prefix-only host check, an attacker can get an arbitrary attacker-controlled https origin rendered as a "GitHub CDN video," and any native-browser navigation off that element (context menu → open in new tab/copy address, etc.) happens without going through the app's own link-vetting/callback logic at all. Practically this enables convincing-looking-domain navigation (e.g., a domain that visually/textually begins with `user-images.githubusercontent.com`) reachable via a rendered PR/issue video block, which is a plausible vector for phishing-style redirection. I could not confirm what further gatekeeping (e.g., `setWindowOpenHandler`/`will-navigate` in `app/src/main-process/main.ts`) exists at the Electron main-process level for such native "open in new tab" navigations, so I cannot state with certainty whether this ultimately escapes to an OS-level browser window unmitigated, or whether main-process policy independently blocks/redirects it.

### Likelihood Explanation
High for reaching the renderer-level break: any attacker who can post markdown reviewed via `SandboxedMarkdown` (issue/PR/comment bodies are explicitly in scope) can trigger `VideoLinkFilter` with a single crafted link containing the trusted prefix followed by an attacker-controlled suffix, with no unnatural user interaction required to render the malicious `<video>` element. Triggering the actual navigation does require a user context-menu interaction, which is a normal (not unnatural) manner of interacting with an embedded video.

### Recommendation
- In `getGithubVideoLink`, parse `node.firstChild.href` with the `URL` constructor and compare `url.protocol === 'https:' && url.hostname === 'user-images.githubusercontent.com'` instead of a string-prefix regex.
- Fix `videoExtensionRegex` so the alternation cannot match an empty string (drop the trailing empty alternative), and anchor it to require a real path segment/extension.
- Consider disabling/removing the browser's native context menu on injected `<video>` elements inside the sandboxed markdown iframe (or intercepting `contextmenu`/`click` events on non-`<a>` media elements the same way anchors are vetted), so any navigation originating from filter-injected elements is routed through the same validation as `setupLinkInterceptor`.

### Proof of Concept
1. Post a PR/issue comment containing a bare link whose resolved href is, e.g., `https://user-images.githubusercontent.com.attacker.example/video.mp4` (register `attacker.example` with the CNAME/subdomain `user-images.githubusercontent.com.attacker.example`, or otherwise ensure the anchor's resolved `href` string starts with the trusted prefix).
2. GitHub-flavored markdown auto-links this into `<p><a href="...">...</a></p>`.
3. `VideoLinkFilter.getGithubVideoLink` matches via `githubAssetVideoRegex.test(...)` (prefix-only, empty-extension-tolerant) and returns the attacker URL.
4. `filter()` creates `<video src="https://user-images.githubusercontent.com.attacker.example/video.mp4">`, replacing the anchor.
5. Right-click the rendered video and choose "Open video in new tab" / "Copy video address" — confirm in `setupLinkInterceptor`'s click listener that `ev.target.closest('a')` is `null` for this interaction, so `onMarkdownLinkClicked` and the `/^https?:/.test(a.protocol)` check are never invoked, demonstrating the video path is unvetted relative to the anchor path.

  private getGithubVideoLink(node: Node): string | null {
    if (
      isElement(node, 'p') &&
      node.childElementCount === 1 &&
      node.firstChild &&
      isElement(node.firstChild, 'a') &&
      githubAssetVideoRegex.test(node.firstChild.href)
    ) {
      return node.firstChild.href
    }

    return null
  }
