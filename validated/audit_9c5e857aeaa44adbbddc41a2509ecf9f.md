### Title
Webhook Shop-Domain Header Not Bound to HMAC-Signed Payload Enables Cross-Shop Webhook Spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` validates the authenticity of an inbound webhook solely by HMAC-verifying the raw request body against the app's shared secret. The `X-Shopify-Shop-Domain` header, which the app trusts to identify which merchant a webhook belongs to, is never included in that HMAC computation and is never cross-checked against the signed payload or against any known/installed shop record.

### Finding Description
`verify_request` computes `hmac_valid?(request.raw_post)` and only inspects the request body: [1](#0-0) 

The shop-domain value used by consuming controllers/jobs is read straight from an unauthenticated header: [2](#0-1) 

`hmac_valid?` itself confirms only that *some* secret produced the HMAC over the body — it says nothing about which shop or header values were used: [3](#0-2) 

Both the built-in controller and the generator-scaffolded controller take the "shop" identity from this unverified source and hand it directly to background jobs that act on shop-scoped data: [4](#0-3) [5](#0-4) 

Any merchant who installs the app can legitimately trigger real Shopify webhooks for their own store (e.g. via `carts/update`), obtaining an authentic body + HMAC signature pair generated by Shopify using the app's shared secret. Because the `X-Shopify-Shop-Domain` header is outside the signed content, that same attacker can replay the captured body/signature to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value (any other merchant's `*.myshopify.com` domain). HMAC verification still passes — it only proves the body's authenticity, not the header's — and the app dispatches the job with `shop_domain` set to the attacker-chosen (victim) domain, exactly analogous to the reported bug class: a critical identifier ("wallet"/shop) is accepted and used without validating that it is the correct/expected one.

### Impact Explanation
Downstream jobs (e.g. `CartsUpdateJob`, `OrdersCreateJob`, or the mandatory privacy webhooks `customers/data_request`, `customer/redact`, `shop/redact`) receive `shop_domain` as an app-trusted, unauthenticated value. Depending on the app's job implementation, this can lead to cross-shop data corruption, incorrect data attribution, spurious redaction/erasure actions performed against a shop that never requested them, or state confusion between tenants — all without needing any session, cookie, or CSRF token, since this endpoint is unauthenticated by design and only protected by the (bypassable-in-this-way) HMAC check.

### Likelihood Explanation
Any actor able to install the target app on a shop they control (a normal, unprivileged, "unrelated-merchant" capability) can obtain a validly-signed webhook body/signature pair for their own shop and replay it with a forged shop-domain header — no secret leakage or privileged access is required. Exploitability depends only on the header value being trusted downstream, which is the documented/expected usage pattern shown in both the built-in controller and the official generator template.

### Recommendation
Bind the shop identity to the signed content instead of trusting the header: verify the `shop_domain` header against the shop encoded in the webhook body/topic where available, or cross-check it against `ShopifyApp::SessionRepository` to confirm the shop has an active session/installation before dispatching any job. At minimum, treat `shop_domain` from `WebhookVerification#shop_domain` as untrusted until corroborated by data inside the (HMAC-covered) payload.

### Proof of Concept
1. Merchant A installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., updates a cart), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` to the app's `/webhooks/:type` endpoint.
2. Attacker captures `B` and `H` (e.g., via their own request logs/proxy).
3. Attacker replays: `POST /webhooks/carts_update` with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body unchanged), but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `verify_request` recomputes HMAC over the unchanged body `B` and it matches, so the request passes verification per `hmac_valid?`.
5. The controller/registry dispatches the corresponding job with `shop_domain: "victim-shop.myshopify.com"` and the attacker-controlled `webhook` payload, causing the app to process attacker data under the victim shop's identity.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
