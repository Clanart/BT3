### Title
Unbounded CLVM execution when parsing an untrusted offer's inner puzzle allows an offer counterparty to hang a wallet's transaction-processing (`get_offered_coins`) - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_offered_coins()` / `Offer._get_offered_coins()` runs the inner puzzle of every coin spend in an untrusted, counterparty-supplied offer file with `cost_left = INFINITE_COST`, i.e. no CLVM cost limit at all, unlike the rest of the offer-parsing code path (`__post_init__`, `conditions()`), which correctly bounds execution to `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`.

### Finding Description
When a wallet loads/inspects an offer (`Offer.summary()`, `get_offered_amounts()`, `arbitrage()`, `get_pending_amounts()`, etc. — all UI/CLI paths that a wallet calls before the user decides to accept a trade), it eventually calls `get_offered_coins()`: [1](#0-0) 

which lazily computes `_get_offered_coins()`. That method sets `cost_left = INFINITE_COST` and then calls `inner_puzzle.run_with_cost(cost_left, inner_solution)` for every coin spend in the bundle: [2](#0-1) 

This stands in contrast to every other place in this same file that runs CLVM against attacker-supplied puzzle/solution data, which explicitly bounds execution with `max_cost = int(DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM)` and decrements/aborts on `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)`: [3](#0-2) [4](#0-3) 

`Offer` objects are constructed directly from bech32-encoded offer files supplied by an untrusted offer counterparty (an "unauthorized" party from the perspective of the receiving wallet), and are parsed/inspected by the wallet (CLI/RPC `get_offer_summary`, trade manager preview, etc.) *before* the mempool's own cost metering (`pre_validate_spendbundle`) or any full-node consensus check ever runs. At that point, none of the mempool/consensus DoS mitigations documented for the CLVM execution paths apply — `max_tx_clvm_cost`, `MAX_BLOCK_COST_CLVM`, atom/pair bounds, and the 2-second validation-duration guard are all mempool-side (`chia/full_node/mempool_manager.py`), and do not protect this earlier, purely-local offer-parsing step.

Since a malicious offer author fully controls the inner puzzle/solution pairs bundled inside the offer (an offer is just an unsigned/partially-signed `SpendBundle` with settlement-payment coins), they can construct a CLVM puzzle designed to consume an extremely large (but finite) amount of CLVM cost/CPU time (e.g. deep recursion, large loops building big structures) with no cost ceiling enforced by `_get_offered_coins`. Feeding such an offer to a victim's wallet (e.g. via any UI/RPC that displays an offer summary before signing) causes CLVM execution local to the wallet to run for an unbounded amount of time/memory, blocking the asyncio event loop (or whichever thread it executes on) and thus stalling the wallet's transaction-processing pipeline — a spend/offer-triggered processing halt, matching the bug class of the referenced Prometheus DoS report (attacker-controlled input driving unbounded resource consumption in a component that should be cost/regex/complexity-bounded).

### Impact Explanation
This is a Denial-of-Service against a wallet process: opening/inspecting/summarizing a malicious offer file received from an offer counterparty (a normal, expected trust boundary in the offers flow) can hang or exhaust CPU/memory for the wallet, without needing any signature, fee payment, or mempool submission. Because `get_offered_coins()` is invoked from summary/UI code paths that are typically called automatically when an offer is loaded (to show the user what is being offered), the victim does not need to explicitly "accept" the trade to trigger the expensive execution.

### Likelihood Explanation
High reachability: any party who can hand a wallet user an offer file (a routine, unauthenticated interaction inherent to the offers feature) can trigger this code path. No special privileges, signing, or broadcast are required — only that the wallet parses/summarizes the offer, which is the normal first step in every offer UI flow.

### Recommendation
Bound the CLVM execution in `Offer._get_offered_coins()` (and any other caller using `INFINITE_COST` on attacker-supplied puzzle/solution pairs from an offer) to the same `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` (or a smaller, wallet-appropriate limit) used elsewhere in this file, decrementing a shared `cost_left`/`max_cost` budget across all coin spends in the bundle and raising `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` when exceeded, consistent with `__post_init__` and `conditions()`.

### Proof of Concept
1. Craft an `Offer`/`WalletSpendBundle` whose settlement-payment parent coin's inner puzzle is a CLVM program engineered to consume a very large amount of CPU/memory when run without a cost bound (e.g., deep unrolled recursion or repeated cons-pair generation that would exceed `MAX_BLOCK_COST_CLVM` if metered).
2. Encode this as a normal offer file (bech32) and send it to a victim (e.g., via the standard offer-file exchange mechanism used for trades).
3. Have the victim's wallet load/inspect the offer (e.g. via `chia wallet get_offer` / any RPC or UI action that calls `Offer.summary()` / `get_offered_amounts()` / `arbitrage()`), which internally calls `get_offered_coins()` → `_get_offered_coins()`.
4. Observe that `inner_puzzle.run_with_cost(INFINITE_COST, inner_solution)` runs unbounded, consuming CPU/memory disproportionate to any cost limit enforced elsewhere in the codebase, stalling the wallet process — the "spend-triggered transaction-processing halt" described by the analog bug class.

**Note on confidence**: I confirmed the unbounded `INFINITE_COST` call and the contrast with the properly-bounded sibling methods in the same file via static analysis of `chia/wallet/trading/offer.py`. I was not able to execute a live wallet/offer flow to empirically measure wall-clock hang time or confirm event-loop blocking behavior (this is a static-analysis-based finding from the indexed code, not a runtime-verified exploit), so the practical severity depends on how large a cost differential is achievable within realistic offer-file size/puzzle constraints — this should be validated with a live PoC in a Devin session with full repo/runtime access.
