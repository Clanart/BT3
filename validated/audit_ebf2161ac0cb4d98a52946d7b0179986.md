### Title
Participant-indexed HashMap lookups in PedPoP blame handling panic on attacker-chosen indexes, aborting the process - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
CVE-2014-8241 is a failure to check the result of an allocation/lookup, causing a NULL dereference DoS. The Serai analog is failure to check the result of participant-indexed `HashMap` lookups in PedPoP's blame path: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` indexes `self.commitments[&sender]`. Both maps contain only keys for participants `1..=n` registered during the DKG. The public `blame` APIs accept `sender` and `recipient`/`decryptor` as free `Participant` arguments, so passing any participant index outside the registered set causes a `HashMap` index panic and aborts the calling process — the Rust equivalent of an unchecked lookup producing a NULL dereference.

### Finding Description
`EncryptedMessage::read` / `EncryptionKeyProof::read` accept untrusted bytes, and `BlameMachine::blame` / `AdditionalBlameMachine::blame` are public APIs taking attacker-influenced `sender`, `recipient`, `msg`, and `proof` arguments. Inside `blame_internal`, `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` is invoked first; when a `proof` is supplied it reaches `self.enc_keys[&decryptor]` unconditionally after the PoP check. `enc_keys` is only populated by `register` for the fixed participant set `1..=n`, so any `decryptor`/`recipient` index not in the set panics. Later in `blame_internal`, `self.commitments[&sender]` panics the same way for an out-of-set `sender` once the message's PoP verifies. `AdditionalBlameMachine` is explicitly designed for non-members to adjudicate blame, making this reachable by an unprivileged party submitting a blame claim referencing a non-existent participant. ### Impact Explanation
An unprivileged party who can trigger the blame/arbitration path (e.g., by submitting an accusation naming a forged `sender`, or a recipient index that was never registered, together with a message carrying a valid PoP bound to that `sender`) causes a panic in the host process performing blame evaluation. Since `HashMap` indexing panics rather than returning an error, this is a deterministic crash DoS of the validator/coordinator evaluating blame — the same crash-impact class as the TigerVNC NULL dereference.

### Likelihood Explanation
Reachability requires the integrator to route peer-supplied `sender`/`recipient`/`msg`/`proof` into `blame()` — which is exactly what the API exists for (it takes an externally authenticated `EncryptedMessage`). The attacker needs a message with a valid PoP naming the forged `from` participant; the PoP only binds `sender` as transcript bytes, so an attacker who controls any real participant key (or is evaluating blame as a third party over relayed data) can satisfy it while choosing a `recipient`/`decryptor` index outside `1..=n`. No threshold collusion or malformed curve data is needed — only an out-of-range `Participant` index.

### Recommendation
Replace the indexing with checked lookups in `Decryption::decrypt_with_proof` (`self.enc_keys.get(&decryptor)` → `Err(DecryptionError::InvalidProof)`) and in `BlameMachine::blame_internal` (`self.commitments.get(&sender)` → treat as `sender` faulty or return a dedicated error). Additionally validate `sender`/`recipient` against the known participant set at the `blame` entry points, matching the `InvalidParticipant`/`MissingParticipant` error style already used elsewhere in the crate.

### Proof of Concept
1. Run a PedPoP DKG with `ThresholdParams::new(t, n, i)`, or construct `AdditionalBlameMachine::new(context, n, commitment_msgs)` so `enc_keys`/`commitments` contain only `Participant(1)..=Participant(n)`.
2. Build an `EncryptedMessage` with a valid `pop` for sender `s` (any participant the attacker controls, or honestly generated), serialize/deserialize via `EncryptedMessage::read`.
3. Call `blame(sender, Participant::new(n + 1).unwrap(), msg, Some(proof))` — `decrypt_with_proof` indexes `self.enc_keys[&Participant(n+1)]`, which was never inserted, panicking immediately.
4. Equivalently, `blame(Participant::new(n + 1).unwrap(), recipient, msg, proof)` reaches `self.commitments[&sender]` and panics, since `commitments` only holds `1..=n`.

  pub fn new(
    context: [u8; 32],
    n: u16,
    mut commitment_msgs: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<Self, PedPoPError<C>> {
    let mut commitments = HashMap::new();
    let mut encryption = Decryption::new(context);
    for i in 1 ..= n {
      let i = Participant::new(i).unwrap();
      let Some(msg) = commitment_msgs.remove(&i) else { Err(PedPoPError::MissingParticipant(i))? };
      commitments.insert(i, encryption.register(i, msg).commitments);
    }
    Ok(AdditionalBlameMachine(BlameMachine { commitments, encryption, result: None }))
  }
