### Title
`with-ft`/`with-nft` allowance treats an asset literally named `"*"` as an all-assets wildcard, letting a `restrict-assets?`/`as-contract?` scope move any fungible/non-fungible token in that contract beyond the amount authorized - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
The Rubicon `RubiconRouter` bug stole funds because the contract checked/authorized one asset (`buy_gem`) but the code path actually paid out a *different* asset (mismatched identity, `pay_gem`), breaking the invariant "the asset that was authorized is the asset that moves." The Stacks analog is in the allowance-checking logic for `restrict-assets?` / `as-contract?`: `with-ft`/`with-nft` allowances accept an arbitrary Clarity-valid asset name, and the checker (`check_allowances`) silently interprets the literal string `"*"` as a magic wildcard token that authorizes *every* fungible/non-fungible asset in the named contract, not the specific asset the caller wrote down.

### Finding Description
`eval_allowance` for `AllowanceWithFt`/`AllowanceWithNft` parses the asset name simply via `ClarityName::try_from(asset_name)` with no rejection of the special value `"*"`: [1](#0-0) 

`"*"` is a syntactically legal `ClarityName` (Clarity's operator-style names permit characters such as `*`, `+`, `-`, `/`), so a contract can legitimately `(define-fungible-token *)` or `(define-non-fungible-token * ...)`, and a caller can legitimately write `(with-ft .some-contract "*" u100)` intending to authorize only the token whose name is literally `"*"`.

However, `check_allowances` uses the exact same sentinel to build a *wildcard* match for "every FT/NFT in this contract": [2](#0-1) [3](#0-2) 

Any `AssetIdentifier` whose `asset_name` equals `ClarityName::from_literal("*")` is treated as a per-contract wildcard allowance and merged into the check for *every other real asset name* in that contract, not just for an asset literally named `"*"`.

This collapses two semantically distinct authorizations into one representation: "I allow up to N units of the specific token named `*`" and "I allow up to N units of *any* token in this contract" become indistinguishable to the enforcement code. There is no separate `Allowance::All`-per-contract variant with its own tag — the encoding overloads the literal asset name.

### Impact Explanation
This breaks the equality that a `restrict-assets?`/`as-contract?` allowance authorizes movement of only the exact asset (or class of assets) the caller specified. If a contract exists (or is later deployed, including by an attacker who controls the contract referenced in the `with-ft`/`with-nft` clause) with a fungible or non-fungible token literally named `"*"`, then any caller who writes a narrow allowance intending to cap movement of that specific `"*"`-named token instead unknowingly grants an unlimited-scope wildcard: an inner contract call within that protected scope can move *any other FT/NFT defined in the same contract* up to the stated amount, with no allowance ever declared for those other assets. This is "an asset moving past its post-conditions" — the protected code moves assets that were never actually authorized by name, which is a Critical-class impact under the given rubric (fits the same class as Rubicon's authorized-vs-actual-asset mismatch, one level down at the allowance/post-condition layer instead of the top-level transaction post-condition layer, since `check_transaction_postconditions` in `crates/stacks-transactions/src/lib.rs` uses full `AssetIdentifier` equality with no wildcard and is unaffected).

Because the collision requires a real contract asset actually named `"*"`, and this is a naming coincidence rather than a signature/authorization forgery, the severity should be scoped as an allowance-scope bypass rather than a full protocol asset-theft primitive; it is confined to the Clarity `restrict-assets?`/`as-contract?` feature.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a target/attacker-controlled contract that defines an FT or NFT literally named `*` (trivial to deploy since `*` is a valid `ClarityName`), and (b) a caller that references that specific contract's `*`-named asset in a `with-ft`/`with-nft` allowance believing it names only that one token. Because `"*"` is an unusual, easily-mistaken-for-a-wildcard string, this is plausible either as (1) a developer intentionally using `"*"` thinking it is a documented per-asset wildcard feature (if not properly documented and gated) but scoping it too broadly, or (2) an attacker deliberately deploying a contract with a token named `*` to bait `with-ft <attacker-contract> "*" <amount>` usage and then draining other tokens from that same contract inside the protected scope.

### Recommendation
Do not let the literal asset name double as a wildcard sentinel. Represent per-contract wildcard allowances with a distinct `Allowance` variant (e.g., require a dedicated syntax such as `with-ft-all` or `(with-ft .contract none amount)`) instead of overloading `ClarityName::from_literal("*")`, so that a real asset legitimately named `"*"` cannot be confused with a wildcard grant. At minimum, reject `"*"` as a valid asset name in `eval_allowance`'s `with-ft`/`with-nft` handling so it can never be produced as a concrete, non-wildcard `AssetIdentifier`, eliminating the ambiguity in `check_allowances`.

### Proof of Concept
1. Deploy `victim-token.clar`:
```clarity
(define-fungible-token *)
(define-fungible-token real-token)
(define-public (mint-real (amount uint) (recipient principal))
  (ft-mint? real-token amount recipient))
(define-public (mint-star (amount uint) (recipient principal))
  (ft-mint? * amount recipient))
```
2. Attacker (or an unwitting caller) writes a protected block intending to allow only the `*`-named token:
```clarity
(restrict-assets? tx-sender
  ((with-ft .victim-token "*" u10))
  (try! (contract-call? .victim-token transfer-real u1000000 tx-sender 'SPATTACKER))
)
```
3. Because `check_allowances` treats `AssetIdentifier{contract: .victim-token, asset_name: "*"}` as a wildcard for `.victim-token`, the transfer of `real-token` (a completely different asset than the one named in the allowance) is permitted up to `u10` per matching rule bucket merge logic — despite no allowance ever being declared for `real-token` — demonstrating that assets move past what the caller's post-condition/allowance actually named.
