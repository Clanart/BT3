### Title
Balance handler state corruption via recursive/nested precompile calls causes native↔EVM balance desync - (File: precompiles/common/balance_handler.go)

### Summary
The Cosmos EVM analog to the ABIEncoderV2 "encoder invariant violation" class of bug is a stateful-decoding invariant violation in the precompile balance-synchronization path: `BalanceHandler.prevEventsLen` is a single mutable offset that is overwritten by nested/recursive precompile invocations, breaking the assumption that `AfterBalanceChange` always processes exactly the bank events emitted by "its own" call. This is explicitly documented and reproduced in this repository's own test suite.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` into `bh.prevEventsLen`, and `AfterBalanceChange` later replays `events[bh.prevEventsLen:]` to mirror `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` bank events into the EVM `StateDB` via `AddBalance`/`SubBalance` [1](#0-0) , applying the deltas per event type [2](#0-1) .

If a precompile call reenters the EVM (e.g. via `CallEVMWithData`/`CallEVM`) and that nested execution path invokes `BeforeBalanceChange` again on the *same* `BalanceHandler` instance, `prevEventsLen` is overwritten with a higher index corresponding to the inner call's starting point. When the inner call's `AfterBalanceChange` runs, it consumes/clears the offset up to the inner call's tail. When control returns to the outer call and its own `AfterBalanceChange` executes, `bh.prevEventsLen` no longer reflects the outer call's original starting offset — bank events emitted by the outer call before the reentrant call can be skipped (never mirrored into StateDB), or events can be double counted, depending on ordering.

This exact scenario — recursive precompile calls sharing a `BalanceHandler` instance and corrupting `prevEventsLen`, described as causing "balance desync between native bank keeper and EVM stateDB" — is documented and reproduced in this repository's own integration test: [3](#0-2) 

The reproduction uses a debug precompile that recursively calls back into itself through the EVM (`Call0` invokes `CallEVMWithData` back to the caller, which invokes the precompile again) [4](#0-3) , and the precompile's `Run` method creates/starts the balance handler around the nested execution using the shared `BeforeBalanceChange`/`AfterBalanceChange` lifecycle [5](#0-4) . The generic (non-debug) precompile `RunNativeAction` path follows the identical pattern of creating a `balanceHandler` and calling `BeforeBalanceChange`/`AfterBalanceChange` around `action(ctx)` [6](#0-5) , so any production precompile whose action triggers a nested EVM call that reenters a stateful precompile (bank, erc20/werc20, staking, distribution, ICS20, etc.) is exposed to the same class of bug if the handler instance is shared across the reentrant boundary.

### Impact Explanation
If bank-side coin movements are skipped from being mirrored into the EVM `StateDB`, an account's EVM-visible balance (used by `balanceOf`-style native asset checks, `msg.value` semantics, and further EVM-level transfers) diverges irreversibly from the actual x/bank ledger balance. Depending on the direction of the desync this allows:
- Native coins debited from bank but never subtracted from the EVM StateDB balance, letting the actor still spend the "phantom" EVM-visible balance in subsequent EVM operations within the same or later transactions — an unauthorized duplication of spendable value.
- Coins credited in bank but never added to StateDB balance, or vice versa, causing permanent accounting corruption between the two balance views that back the same spendable asset.

This matches the "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances, EVM balances" impact bucket.

### Likelihood Explanation
I could not confirm from static reading whether `GetBalanceHandler()` (used by the debug precompile) returns a per-call-fresh handler or a shared/cached instance stored on the `Precompile` struct — the definition of `GetBalanceHandler` was not found in `precompiles/common` within the indexed content, so I cannot fully verify the exact sharing mechanism or confirm whether current production precompiles (bank, erc20, staking, distribution, ICS20) are reachable through a code path that reenters the EVM mid-execution with a shared handler instance in the same way the debug precompile does. The repository's own test is explicitly named/commented as demonstrating "the balance handler bug," which indicates the maintainers are aware of and are tracking this exact invariant violation, but I cannot state with certainty whether it is already mitigated in the production precompile registration (e.g., via `BalanceHandlerFactory.NewBalanceHandler()` creating a fresh instance per top-level `Run`, which the factory pattern in `balance_handler.go` suggests is intended) [7](#0-6) , versus a scenario (as in the debug precompile) where a single shared handler is reused across reentrant calls.

### Recommendation
- Ensure every precompile `Run` invocation (including calls reentered via `CallEVM`/`CallEVMWithData` from within an already-running precompile action) obtains a **new** `BalanceHandler` from `BalanceHandlerFactory.NewBalanceHandler()` rather than reusing a shared instance, so `prevEventsLen` is always scoped to the call that owns it.
- If nested precompile calls are expected, make the event-offset tracking stack-based (push/pop per call depth) rather than a single mutable field, so an inner call's `Before/AfterBalanceChange` cannot corrupt the outer call's bookmark.
- Add an invariant check post-transaction that reconciles total EVM StateDB native-denom balances against x/bank ledger balances, and fail/revert the transaction (rather than silently persisting) on divergence.
- Extend `TestRecursivePrecompileCallsWithDebugPrecompile` into the production precompiles (bank/erc20/staking/distribution) with actual balance assertions before/after nested calls to confirm the fix holds outside the debug precompile.

### Proof of Concept
Use the existing test as the reproduction skeleton: deploy `DebugPrecompileCaller`, fund it, and call `callback(0)`, which recursively calls back into the debug precompile through `CallEVMWithData` [4](#0-3) . The test asserts on event counts [8](#0-7)  — to turn this into a fund-impact PoC, replace the debug `Call1` emit-event method with a real bank `SendCoins` call inside the recursive frame, and assert that the resulting EVM `StateDB` balance for the sender/receiver matches (or diverges from) the x/bank ledger balance after the recursive round-trip completes.

```go
// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

	return nil
```

```go
func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}
```
