## Title
Hookify PreToolUse Block Rules Silently Downgrade to No-Op on Format/Case Mismatch, Letting Destructive Commands Execute Unblocked - ([File: plugins/hookify/core/rule_engine.py])

### Summary
The `hookify` plugin's `PreToolUse`/`PostToolUse` rule engine mirrors the reported bug class: a user-facing "validation" that *appears* to enforce a security invariant (blocking a dangerous command) but silently accepts malformed/mismatched configuration and degrades to a no-op, with the underlying action (an irreversible shell command) already executed by the time any diagnostic is surfaced.

### Finding Description
`RuleEngine.evaluate_rules()` only escalates a rule to the hard-blocking `permissionDecision: "deny"` path when `rule.action == 'block'` exactly [1](#0-0) . `Rule.from_dict()` reads this value straight from user-authored YAML-like frontmatter with no normalization or validation: `action=frontmatter.get('action', 'warn')` [2](#0-1) . Any case mismatch, extra whitespace, or typo (`Block`, `BLOCK`, `block ` with a trailing space introduced by the hand-rolled parser) causes the rule to silently fall into the `warning_rules` bucket instead of `blocking_rules`.

In the warning-only path, `evaluate_rules()` returns only `{"systemMessage": ...}` with **no** `hookSpecificOutput.permissionDecision` set [3](#0-2) . This means the tool call proceeds under whatever the ambient permission mode is (e.g., auto-accept/bypass mode) — the user's intended hard block is silently downgraded to an advisory note that arrives via `additionalContext`/`systemMessage`, not a synchronous block, so a destructive `Bash` command (e.g. `rm -rf`) can already be executing or have executed by the time the message is even relevant.

The same silent-degrade pattern exists deeper in condition matching: an unmatched/absent field returns `False` with no diagnostic (`if field_value is None: return False`) [4](#0-3) , an unrecognized operator returns `False` silently [5](#0-4) , and a rule with zero parsed conditions (e.g., because the bespoke frontmatter parser mis-parsed an inline list — see the comma-splitting inline-dict branch that breaks if the user's regex `pattern` itself contains a comma) never matches at all: `if not rule.conditions: return False` [6](#0-5) . All of these failures are logged, if at all, only to `stderr` via `print(..., file=sys.stderr)` in `config_loader.py` [7](#0-6) , and the top-level `pretooluse.py` executor is explicitly designed to **never block on any internal error**: `finally: sys.exit(0)` unconditionally [8](#0-7) .

This is the direct structural analog of `_validateToLength()`: a check that exists and superficially looks like enforcement, but does not validate the actual invariant the user relies on (a length matching a real 20-byte address / an `action` value matching the literal string `"block"`), so malformed input passes through into an irreversible operation (fund burn / destructive shell command) with no recoverable feedback loop for the affected user.

### Impact Explanation
A user relying on a hookify `action: block` rule (e.g. to prevent `rm -rf`, `git push --force`, credential-file writes) as a safety net for an autonomous/auto-accept Claude Code session gets no actual enforcement if their rule's `action` field has any casing/whitespace deviation, or if their `pattern`/`conditions` block is mis-parsed by the simplistic hand-rolled frontmatter parser. The dangerous command then executes exactly as if no rule existed, and unlike a normal validation error, there is no exception, no blocking exit code, and no user-visible indication that protection failed — only a best-effort `stderr` line in a log the user is not watching in real time. In an auto-accept/bypass-permissions session (the scenario this plugin is explicitly built for), this converts directly into unauthorized/irreversible local file or shell actions.

### Likelihood Explanation
This requires only normal, unprivileged usage: writing a `.claude/hookify.*.local.md` rule file, which is a documented and encouraged workflow [9](#0-8) . No malicious actor, network peer, or dependency compromise is needed — a simple authoring typo (a very plausible one, since YAML conventionally treats `Block`/`block` as equivalent booleans-adjacent tokens, but this code does an exact string compare) is sufficient to trigger silent fail-open.

### Recommendation
- Normalize and validate `action` at load time (case-insensitive compare, trim whitespace) and reject/warn loudly — surfaced to the user in the transcript, not just `stderr` — on any unrecognized value instead of silently defaulting to `warn`.
- Make `load_rules()`/`load_rule_file()` failures visible in-band: emit a `systemMessage` (not just `stderr`) when a rule file fails to parse or yields zero conditions, so the user knows their intended block is not active.
- Consider failing closed (block) rather than open (allow) when a rule marked with an unrecognized/malformed `action` cannot be confidently classified as `warn`, at least for the `PreToolUse` bash-command case.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm\s+-rf
action: Block
---
Dangerous rm blocked.
```
2. `Rule.from_dict()` stores `action = "Block"` verbatim [10](#0-9) .
3. On a `Bash` `rm -rf /some/important/dir` call, `_rule_matches()` matches the pattern, but `evaluate_rules()` checks `rule.action == 'block'` (lowercase) — false — so the rule lands in `warning_rules`, not `blocking_rules` [1](#0-0) .
4. The response contains only `systemMessage`, no `permissionDecision: deny` [3](#0-2) , so the command executes under the active permission mode (destroying the directory) while the "block" message is delivered only as post-hoc context — the intended protection silently never engaged, with no recoverable state.

- Verify the path is correct
- Consider using a safer approach
- Make sure you have backups
```

- `warn`: Shows warning but allows operation (default)
- `block`: Prevents operation from executing (PreToolUse) or stops session (Stop events)
