### Title
Fixed, size-independent compute charge for BPF program deployment underprices ELF loading/verification/JIT compilation - (File: `programs/bpf_loader/src/lib.rs`, `program-runtime/src/deploy.rs`)

### Summary
When a user deploys or upgrades an Upgradeable Loader (BPF Loader v3) program, the runtime charges a single fixed compute-unit fee (`UPGRADEABLE_LOADER_COMPUTE_UNITS = 2_370`) for the entire instruction, regardless of the size or complexity of the ELF bytecode being processed. The actual expensive work — parsing the ELF, running the stricter `RequisiteVerifier`, and JIT-compiling the program — happens afterward inside `deploy_program()`, and its cost scales with the size of the (attacker-controlled) program data, up to `MAX_PERMITTED_DATA_LENGTH`. This mirrors the reported WASM-activation issue: a computationally expensive, size-dependent operation on user-supplied bytecode is billed at a flat rate that does not reflect its true cost.

### Finding Description
`process_instruction_inner` charges the flat `UPGRADEABLE_LOADER_COMPUTE_UNITS` fee once, at instruction entry, before any account/data validation or ELF processing occurs: [1](#0-0) 

This fee is a compile-time constant, not derived from the size of the buffer/programdata the caller supplies: [2](#0-1) 

For `DeployWithMaxDataLen` (and similarly `Upgrade`), after the fixed charge, the handler accepts attacker-controlled buffer data (bounded only by `MAX_PERMITTED_DATA_LENGTH`, tens of megabytes) and invokes `deploy_program!`, which calls into `program-runtime/src/deploy.rs::deploy_program`: [3](#0-2) [4](#0-3) 

`deploy_program` performs three size-dependent, expensive operations — registering syscalls into a stricter deployment environment, `Executable::<InvokeContext>::load` (ELF parsing), and `executable.verify::<RequisiteVerifier>()` — none of which consume any additional compute units: [5](#0-4) 

The verifier used here is also the *stricter* `reject_broken_elfs = true` deployment-time verifier, making this pass more expensive than ordinary invocation-time verification: [6](#0-5) 

The `LoadProgramMetrics` struct even explicitly tracks `load_elf_us` and `verify_code_us` as separate timed phases, confirming these are recognized as non-trivial, size-dependent costs internally — yet none of this measured time is translated into additional compute-unit consumption charged to the transaction: [7](#0-6) 

This is structurally identical to the reported bug class: an expensive, attacker-controlled-input-dependent operation (ELF parse + verify, analogous to Brotli decompression) is billed at a flat rate set once at the start of the instruction, rather than being priced according to the actual cost of processing the supplied bytecode.

### Impact Explanation
Any unprivileged user can submit a `DeployWithMaxDataLen`/`Upgrade` instruction containing a large, adversarially structured (but otherwise loadable) ELF payload near the maximum permitted size. The validator must fully parse and verify (and potentially JIT-compile) this payload while only 2,370 CUs are deducted for the entire instruction — the same cost as deploying a trivial one-instruction program. Because compute-unit accounting is what bounds per-transaction and per-block validator work, an attacker can craft transactions that consume disproportionate CPU time in ELF parsing/verification relative to the compute budget charged, enabling a denial-of-service vector against block-producing/replaying validators (materially underpriced compute).

### Likelihood Explanation
This code path is reachable by any unprivileged account holder — deploying/upgrading a BPF Loader v3 program is a standard, permissionless user operation requiring no special privileges, only that the caller fund the buffer and programdata accounts. The size of the ELF payload subject to expensive parsing/verification is fully attacker-controlled up to `MAX_PERMITTED_DATA_LENGTH`.

### Recommendation
- **Short term:** Charge compute units proportional to the size of the ELF/program data being loaded and verified in `deploy_program` (e.g., before or incrementally during `Executable::load`/`verify::<RequisiteVerifier>`), rather than only the fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS` charged at `process_instruction_inner` entry.
- **Long term:** Audit all other user-triggerable, size/complexity-dependent operations in the BPF loader and program cache path (ELF loading, verification, JIT compilation across all loader versions and `ProgramCacheEntry::new`/`reload`) to ensure compute costs scale with actual work performed, consistent with the metrics already collected in `LoadProgramMetrics`.

### Proof of Concept
Not executed against a live cluster; the analysis is based on static code reachability: any signer can submit `InitializeBuffer` + repeated `Write` instructions to stage a maximum-size ELF buffer, then submit `DeployWithMaxDataLen` (or `Upgrade`) referencing that buffer. Per [1](#0-0)  only 2,370 CUs are deducted for the instruction regardless of buffer size, while [5](#0-4)  shows the subsequent load/verify work scales with that buffer's size — demonstrating the cost/charge mismatch.
