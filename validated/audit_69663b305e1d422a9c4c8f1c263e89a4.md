## Finding: Valid — reward-accrual inflation via `cancelUnlock()` missing checkpoint [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Reward inflation via balance restoration without checkpoint in `cancelUnlock()` - (File: VLMGP.sol / rewards/vlMGPBaseRewarder.sol)

### Summary
`vlMGPBaseRewarder._updateFor`/`_earned` compute `delta(rewardPerToken) * balanceOf(_account)` at checkpoint time, assuming the account's balance was constant since the last checkpoint. `startUnlock()` and `unlock()` correctly call `IMasterMagpie.multiclaimFor` (which checkpoints via `updateReward`) *before* mutating cooldown state, but `cancelUnlock()` mutates state (restoring full lock weight) without any preceding checkpoint. This asymmetry lets a user accrue a reward-index delta while holding a reduced (cooldown-weighted) balance, then restore their full balance and only checkpoint afterward, so `_earned` retroactively applies the full-weight balance to a period where the true balance was lower.

### Finding Description
`balanceOf` in `vlMGPBaseRewarder` reflects the vlMGP weighting (full lock vs. half-weighted cooldown amount) as read from `IMasterMagpie.stakingInfo` [4](#0-3) . `_updateFor`/`_earned` snapshot `userRewards` using `balanceOf(_account)` read **at the time `_updateFor` runs**, multiplied by the reward-per-token delta accumulated since the last checkpoint [3](#0-2) [5](#0-4) . This model is only correct if a checkpoint is forced on every balance-changing call.

`startUnlock()` correctly forces this checkpoint by calling `multiclaimFor` (which triggers `getReward`/`updateReward`) *before* moving the amount into cooldown (which reduces weighting) [6](#0-5) . `unlock()` does the same before removing the position entirely [7](#0-6) . However, `cancelUnlock()` mutates `slot.amountInCoolDown` and `totalAmountInCoolDown` — restoring the account's full lock weight instantly — **without** any call to `multiclaimFor` or `_updateFor` [1](#0-0) .

Exploit flow:
1. Attacker locks a large amount of MGP (`lock`), balance = full weight `W`.
2. A reward is queued (`queueNewRewards`), bumping `rewardPerTokenStored`. Nothing has been claimed yet, so no checkpoint has occurred for the attacker — their `userRewardPerTokenPaid` is stale at a pre-lock value, meaning `_earned` already owes them `deltaIndex * W`.
3. Attacker calls `startUnlock(W)`. This triggers `multiclaimFor` → `_updateFor`, checkpointing `userRewards` at the correct full-weight `W` for the elapsed period, and setting `userRewardPerTokenPaid` = current index. Balance then drops to cooldown-weighted `W/2`.
4. While in cooldown (balance = `W/2`), another reward is queued, bumping the index again.
5. Attacker calls `cancelUnlock()`. This restores balance to full weight `W` **instantly, with no checkpoint** — the stale `userRewardPerTokenPaid` from step 3 is untouched.
6. Attacker calls `getReward()`. `_updateFor` now computes `_earned` using the **current** (full) balance `W` against the reward-index delta accumulated during step 4, when the true held balance was only `W/2`. The attacker is credited roughly double the rewards actually earned during the cooldown window.

This directly violates the Conservation invariant: the attacker extracts yield proportional to a balance they did not hold during the accrual interval, at the expense of other stakers' share of `rewardPerTokenStored`.

### Impact Explanation
Theft of unclaimed yield beyond the account's true time-weighted stake — funds diverted from the shared reward pool to the attacker, diluting honest stakers' claimable rewards. This matches the Immunefi "theft of unclaimed yield" impact class.

### Likelihood Explanation
No privileged role is required — any vlMGP holder can call `lock`, `startUnlock`, and `cancelUnlock` freely and permissionlessly. The only precondition is that a reward gets queued (via `queueNewRewards`, callable by reward managers as part of normal protocol operation, or opportunistically timed by the attacker around known distribution events) while the attacker is mid-cooldown. The attack is repeatable every time a reward distribution lands while the attacker has an open (but not yet finalized) unlock slot, and requires only capital proportional to the attacker's own locked MGP.

### Recommendation
Force a reward checkpoint (`_updateFor`/`multiclaimFor`) in `cancelUnlock()` before mutating `slot.amountInCoolDown` / `totalAmountInCoolDown`, mirroring the pattern already used in `startUnlock()` and `unlock()`, so that any balance-weight change is always preceded by a checkpoint against the pre-change balance.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` with a reward token.
2. Attacker locks `W` MGP; a control account also locks `W` MGP and never touches unlock functions.
3. Queue reward R1; call `startUnlock(W)` for attacker (checkpoints at full weight `W`, balance drops to `W/2`).
4. Queue reward R2 while attacker is in cooldown (balance `W/2`), control account still at `W`.
5. Call `cancelUnlock()` for attacker (no checkpoint, balance restored to `W`).
6. Call `getReward()` for both attacker and control.
7. Assert: attacker's earned reward for the R2 interval equals `deltaIndex_R2 * W` instead of the correct `deltaIndex_R2 * (W/2)`, diverging from the control account's proportionally correct accrual — demonstrating the inflation and consequent underfunding of the reward pool for other stakers.

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        uint256 userVlMGPAmount = balanceOf(_account);

        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;

            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userVlMGPAmount);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
    }
