### Title
Unattributed operator reimbursement via SIGHASH_SINGLE|ANYONECANPAY payout transaction malleability - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/operator.rs, core/src/verifier.rs)

### Finding Description
The payout transaction that fronts a withdrawal is built by `create_payout_txhandler`, which spends the user's withdrawal UTXO with `SpendPath::KeySpend` and `NormalSignatureKind::NotStored` [1](#0-0) . The user's signature covering this input is required to use `TapSighashType::SinglePlusAnyoneCanPay`, as enforced in `Operator::withdraw` (`sighash_type` is taken directly from the caller-supplied `in_signature`, and the verification error message explicitly instructs callers to use this sighash type) [2](#0-1) .

`SIGHASH_SINGLE|ANYONECANPAY` only commits to the single (input, output) pair at the same index (the user's withdrawal input and the user payout output). It does **not** commit to any other input (the operator's funding input, added later via `fund_raw_transaction`/RBF, see lines 651-674) nor to the OP_RETURN output that records `operator_xonly_pk` for attribution (`op_return_txout(operator_xonly_pk.serialize())`, output index 2) [3](#0-2) . Because the OP_RETURN and the funding input sit outside the signed message, they can be freely swapped by anyone who has the user's `in_signature`/`in_outpoint` pair (which is transmitted to operators over the withdraw RPC, and becomes visible to any actor who observes the resulting transaction template or a failed/competing broadcast attempt) while the user's payout output stays valid and unmodified.

Downstream, `Verifier::update_finalized_payouts` scans the finalized chain, extracts whichever xonly-pubkey happens to be in the first OP_RETURN output of the transaction that actually spent the withdrawal UTXO, and stores it as `payout_payer_operator_xonly_pk` — this is the sole source of truth for "who fronted this withdrawal" and gates subsequent reimbursement bookkeeping [4](#0-3) . `PayoutCheckerTask` then calls `operator.handle_finalized_payout` for whichever operator this attribution names, driving that operator's `end_round`/kickoff reimbursement flow without re-verifying that the funding input actually originated from that operator's wallet [5](#0-4) .

This breaks the intended binding: {operator whose UTXOs funded the payout} == {operator xonly-pk recorded/credited for reimbursement}. Because the OP_RETURN and the extra funding input are unsigned by the covenant, any party that learns a valid `(withdrawal_index, in_signature, in_outpoint, out_script_pubkey, out_amount)` tuple can construct their own payout transaction reusing the same signed input/output, substitute a different `operator_xonly_pk` in the OP_RETURN (attributing reimbursement to an arbitrary operator, including an operator that never sent this money), fund it with their own UTXO, and broadcast it before the intended operator does.

### Impact Explanation
This maps to the Critical category "an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed": an attacker (which could be a rival operator, or any actor able to observe the transaction template) can mint an on-chain payout attributed to an operator who did not fund it, causing that operator to be credited (and later able to claim collateral reimbursement via kickoff) for BTC it never sent, while the true funder receives no attribution and no reimbursement path. It can also be used to deny the legitimate operator its rightful reimbursement by racing them with a copy of their own transaction template but a different OP_RETURN.

### Likelihood Explanation
Exploitability requires only observing a single `(in_signature, in_outpoint, ...)` combination — which is passed unauthenticated over the `withdraw`/`Withdraw` RPC and becomes fully public the moment it appears in a mempool transaction or is leaked by any observer of the withdraw flow — plus the ability to construct and fund a standard Bitcoin transaction and broadcast it before the legitimate operator's transaction confirms. No verifier, operator, watchtower, or key-compromise role is needed beyond normal network observation and wallet funds, so this is reachable by an unprivileged attacker.

### Recommendation
Bind the OP_RETURN attribution and the funding input(s) into the same signed commitment as the user's payout output, e.g., by having the user (or the aggregator) additionally sign a message that includes the intended `operator_xonly_pk`, or by using a sighash type/covenant construction that commits to all inputs and outputs of the payout transaction (not just the anyone-can-pay pair). Alternatively, verify at `update_finalized_payouts` time that the funding input(s) of the finalized payout transaction are attributable to the operator named in the OP_RETURN before recording `payout_payer_operator_xonly_pk`.

### Proof of Concept
1. Operator A calls the withdraw flow; the user supplies `in_signature` (SIGHASH_SINGLE|ANYONECANPAY over `(in_outpoint, out_script_pubkey, out_amount)`) via the `Withdraw` RPC as in `core/src/rpc/clementine.proto:241-253`.
2. Operator A (or Aggregator on its behalf) constructs `payout_txhandler` via `create_payout_txhandler` with `operator_xonly_pk = A`, funds it with `fund_raw_transaction`, and attempts to broadcast (`core/src/operator.rs:620-689`).
3. An observer (attacker) sees this transaction (e.g. in the mempool, or via a leaked withdraw request) and extracts `(in_outpoint, in_signature, out_script_pubkey, out_amount)`.
4. Attacker builds a new transaction: same signed input (user's withdrawal UTXO with the same `in_signature`) and same output (payout to the user, unchanged), but replaces the OP_RETURN with operator B's xonly-pk (or their own), and adds their own funding input to cover the payout amount + fees. Since SIGHASH_SINGLE|ANYONECANPAY doesn't cover the OP_RETURN output or the extra input, the user's signature remains valid for this new transaction.
5. Attacker broadcasts and gets this transaction confirmed first (or as the only confirmed variant).
6. `Verifier::update_finalized_payouts` parses the confirmed transaction's OP_RETURN and records operator B as `payout_payer_operator_xonly_pk`, even though operator B never funded anything [4](#0-3) .
7. `PayoutCheckerTask`/`handle_finalized_payout` subsequently drives reimbursement flow crediting operator B for a payout it never made [6](#0-5) .

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
