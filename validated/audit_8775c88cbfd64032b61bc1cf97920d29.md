### Title
`SignCompleted` verifies its embedded signature under an attacker-supplied key, letting any unprivileged party falsely report a signing plan as completed - (File: coordinator/src/tributary/transaction.rs)

### Summary
This is the Serai analogue of the SignXML algorithm-confusion bug class: a verifier accepts a signature produced under a key/algorithm the attacker chooses, rather than restricting verification to the expected key(s). `Transaction::SignCompleted` is classified as `TransactionKind::Unsigned`, so it bypasses the `Signed` wrapper's signer-validation path entirely. Instead, `Transaction::verify` verifies an embedded `SchnorrSignature<Ristretto>` against `first_signer` — a Ristretto point read directly from the untrusted transaction bytes — under a transcript challenge that binds `first_signer` itself. Because the "public key" is supplied by the attacker, the check reduces to a self-referential proof of possession of any key the attacker controls.

### Finding Description
In `coordinator/src/tributary/transaction.rs`, `Transaction::verify` does:

```rust
if let Transaction::SignCompleted { first_signer, signature, .. } = self {
  if !signature.verify(*first_signer, self.sign_completed_challenge()) { ... }
}
```

and `sign_completed_challenge` computes a challenge over `plan`, `tx_hash`, `signer` (= `first_signer`), and `signature.R`. `first_signer` is read from the serialized transaction via `Ristretto::read_G` (in `Transaction::read`), and `kind()` maps `SignCompleted` to `TransactionKind::Unsigned`, so `verify_transaction`/`mempool.add` never route it through `get_and_increment_nonce`, which is what checks a signer is an actual participant (`TransactionError::InvalidSigner`).

In the block handler (`coordinator/src/tributary/handle.rs`), the only gating is:

```rust
if AttemptDb::attempt(self.txn, genesis, Topic::Sign(plan)).is_none() {
  self.fatal_slash(first_signer.to_bytes(), ...);
  return;
}
self.processors.send(..., sign::CoordinatorMessage::Completed { session, id: plan, tx: tx_hash }).await;
```

There is no check that `first_signer` is a validator (`self.spec.i(&removed, first_signer)` / validator set membership is never consulted for this variant), and the signature was already verified against that same attacker-chosen key. So the signature is vacuously satisfiable: pick any secret `x`, set `first_signer = xG`, sign the challenge. Contrast with every `Signed` transaction, where `verify_transaction` confirms `signer` maps to a real participant before accepting the signature.

### Impact Explanation
An unprivileged party who can get bytes into the tributary mempool/block pipeline (publish `Transaction::SignCompleted` via `add_transaction`) can, for any currently-recognized `Topic::Sign(plan)`, emit `CoordinatorMessage::Completed { id: plan, tx: arbitrary_tx_hash }` to the processors. The processors are told the external-network transaction for a signing plan has completed, bound to a hash of the attacker's choosing — i.e., a forged "completion" attestation accepted with no valid signer at all. This corresponds to accepting a "signature" made with the wrong key entirely — the direct analog of SignXML accepting a signature made with a non-HMAC key when only `hmac_key` was configured. Downstream, `Completed` causes the plan's output to be recorded as finalized with a tx hash that may not exist or may not spend the intended outputs — a false confirmation of funds movement.

### Likelihood Explanation
Reachable entirely with public inputs: `plan`, `tx_hash`, `first_signer`, and `signature` are all attacker-controlled fields of an unsigned transaction fed to `Transaction::read`/`verify`. The only precondition is that `Topic::Sign(plan)` has been recognized (a plan exists), which is the normal state of an operating network. No threshold of validators, no leaked keys, no collusion required. The `fatal_slash` deterrent only fires for *unrecognized* plans, and even then it slashes a meaningless attacker-generated "key" that was never a validator — providing zero deterrence since the point is not in the validator set.

### Recommendation
Either make `SignCompleted` a `TransactionKind::Signed` (with a proper `Signed` wrapper so `verify_transaction` enforces participant membership via `get_and_increment_nonce`/`spec.i`), or in `Transaction::verify`/`handle_application_tx` require `self.spec.i(&removed, first_signer)`/`spec.validators()` membership before accepting the embedded signature. As-is, verifying a signature under a key embedded in the same untrusted blob binds nothing.

### Proof of Concept
Conceptual, on `coordinator/src/tributary/transaction.rs` logic:

```rust
// Attacker: any Ristretto key they control
let x = Zeroizing::new(<Ristretto as Ciphersuite>::F::random(&mut OsRng));
let first_signer = Ristretto::generator() * x.deref();

// Pick any in-flight plan and any tx hash
let tx = Transaction::SignCompleted {
  plan: victim_plan,            // a plan for which Topic::Sign is recognized
  tx_hash: b"attacker-chosen".to_vec(),
  first_signer,
  signature: /* placeholder */,
};

// Compute the challenge exactly as the verifier does and sign under x
let challenge = tx.sign_completed_challenge();
let nonce = Zeroizing::new(<Ristretto as Ciphersuite>::F::random(&mut OsRng));
tx.signature = SchnorrSignature::<Ristretto>::sign(&x, nonce, challenge);

// tx.verify() passes: signature verifies under the attacker's own first_signer.
// handle_application_tx then emits Completed { id: victim_plan, tx: tx_hash }
// to processors despite no validator ever producing the real threshold signature.
```

Caveat: the exact downstream consequences of `CoordinatorMessage::Completed` (whether processors treat the reported `tx` hash as authoritative finalization or cross-check it on the external network) are in `processor/`, which I did not fully trace; the forgery of the completion report itself is confirmed by the code above.
