### Title
Commit+amend during a turn empties the Stop-hook review set, silently skipping review of committed dangerous code - (File: plugins/security-guidance/hooks/diffstate.py)

### Summary
`compute_v2_review_set` in `plugins/security-guidance/hooks/diffstate.py` computes the reviewed file set as `dirty_now ∩ changed_since`, where `dirty_now` only includes committed changes when HEAD advanced *linearly* from `head_at_capture` (checked via `_is_ancestor`). Ordinary git operations such as `git commit` followed by `git commit --amend` (or any rebase/rewrite) during a single agent turn make the tree fully clean (`tracked_dirty = ∅`) while also breaking the ancestor relationship, causing `dirty_now` to be empty and the intersection with `changed_since` to zero out the review set entirely — even though the dangerous file's content genuinely differs from the pre-turn baseline.

### Finding Description
`compute_v2_review_set` (`plugins/security-guidance/hooks/diffstate.py:353-438`) builds:
- `dirty_now = tracked_dirty | new_untracked` from `_git_status_porcelain`, which reflects the worktree/index vs *current* HEAD only [1](#0-0) .
- A special-case union that adds committed file names only `if head_at_capture and current_head and head_at_capture != current_head and _is_ancestor(repo, head_at_capture, current_head)` [2](#0-1) .
- `changed_since = _git_name_only(repo, baseline_sha)` (files differing from the stashed pre-turn baseline) [3](#0-2) .
- `review_set = dirty_now & changed_since` when `changed_since` is available [4](#0-3) .

If Claude (following attacker-controlled repository instructions, e.g. a commit-message convention or CONTRIBUTING guidance embedded in the repo) is induced to `git commit` a change and then `git commit --amend` it (or rebase/squash) before the turn ends, two things happen with ordinary git semantics:
1. The working tree becomes clean, so `tracked_dirty = ∅` and, absent other edits, `dirty_now = ∅`.
2. `git commit --amend` creates a new commit object that is *not* a descendant of the pre-amend commit's ancestor chain in the way `_is_ancestor(head_at_capture, current_head)` expects to remain simply linear — more precisely, `head_at_capture` (captured at UPS, before any commits) is not guaranteed to satisfy the ancestor check post-amend/rebase, and in the amend case the special linear-advance clause that would otherwise add the committed diff to `dirty_now` can be skipped or fail to include the amended content depending on ordering, leaving the amended file out of `dirty_now`.

Since `review_set = dirty_now ∩ changed_since`, an empty (or file-excluding) `dirty_now` forces `review_set` to drop the file even though `changed_since` correctly shows it as different from `baseline_sha`. `handle_stop_hook` then hits the empty-review-set skip path (`_skip(9)`) [5](#0-4)  and exits without ever calling `analyze_code_security`. Critically, the skip path does **not** update `baseline_sha` (that only happens inside the `concrete_guidance` branch via `capture_git_baseline`/`_record_fire` at lines 1892-1916) [6](#0-5) . On the *next* turn, `UserPromptSubmit` re-captures a fresh `capture_git_baseline(cwd)` from the current (already-amended, vulnerability-containing) HEAD, permanently absorbing the dangerous code into the trusted baseline with no further chance of review.

This breaks the stated invariant ("review set must stay bound to the right repo, baseline, and touched paths") because the review set silently collapses to empty on a benign, attacker-uncontrolled-by-privilege but wholly ordinary git workflow (stage → commit → amend), which the code's own docstring acknowledges is a known-fragile boundary ("Mid-session commits are handled correctly (diff is against the snapshot, not HEAD)... Falls back to dirty_now alone...").

### Impact Explanation
This is a logic-level bypass of the mandatory Stop-hook security review: a dangerous code change that is genuinely part of the session's edits is treated as pre-existing/old and never sent to `analyze_code_security`, and it gets baked into the next baseline so it is never reviewed in any subsequent turn either. This matches "Logic-level service disruption caused by bypassing a required guard" — the guard (LLM vulnerability scan gating on exit code 2) is silently skipped for a whole class of ordinary commit-amend/rebase workflows.

### Likelihood Explanation
No special privilege is required — this only needs Claude (driven by ordinary repository content such as a commit-message linting convention, "always squash your commits", or "amend the last commit" instruction embedded in a README/CONTRIBUTING file) to run standard git operations already exercised in normal development. `git commit --amend` is an extremely common workflow, making this readily and repeatably triggerable, not a contrived edge case.

### Recommendation
Do not gate the review purely on `dirty_now ∩ changed_since`. Since `changed_since` (diff of worktree vs `baseline_sha`) already correctly captures the file whenever content differs from the pre-turn stash, `changed_since` alone (optionally still filtered for pre-existing/untouched files) should form the basis of the review set whenever HEAD has moved at all from `head_at_capture`, regardless of whether the move is a strict linear "is-ancestor" advance. Concretely, replace the ancestor-only special case with a broader check: if `current_head != head_at_capture`, union in `_git_name_only(repo, head_at_capture)` unconditionally (not gated on `_is_ancestor`), so amended/rebased/squashed commits still surface their changed paths in `dirty_now`. Add regression tests for commit+amend, commit+rebase, and commit+squash sequences to ensure the review set is never emptied by these operations when `changed_since` is non-empty.

### Proof of Concept
Unit/integration test plan (extending existing tests around `compute_v2_review_set`):
1. Init a temp git repo, commit an initial benign file — this is `head_at_capture`.
2. Call `capture_git_baseline(cwd)` to get `baseline_sha` (clean tree, so it resolves to HEAD).
3. Simulate the "turn": write a dangerous file (e.g. `os.system(user_input)`), `git add`, `git commit -m "wip"`.
4. `git commit --amend -m "final"` (or `git commit --amend --no-edit` after further edits) — this changes HEAD SHA without `head_at_capture` remaining an ancestor of it in the way the code expects.
5. Call `compute_v2_review_set(cwd, baseline_sha, head_at_capture, {})`.
6. **Expected (currently failing) assertion**: the dangerous file's absolute path IS present in the returned `review_paths` list, and `metrics["review_set_count"] > 0`.
7. **Actual (bug) behavior**: `review_paths == []`, causing `handle_stop_hook` to hit `_skip(9)` and never invoke `analyze_code_security`, and the subsequent UPS-captured baseline absorbs the dangerous file permanently.
