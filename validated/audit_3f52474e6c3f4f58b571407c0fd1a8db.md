### Title
Unbounded recursive AccountKey RLP decoding causes fatal Go-runtime stack overflow / node crash (DoS) - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` recursively decode nested `AccountKey` values with no depth limit, mirroring the RabbitMQ `ValueReader.readTable/readArray` bug class (CWE-674, unbounded recursion during untrusted-input deserialization). An attacker can craft an `AccountKey` byte blob that nests `AccountKeyRoleBased` inside itself arbitrarily deeply. Decoding it — reachable via a `TxTypeAccountUpdate` transaction's `Key` field, or directly via the public RPC method `kaia_decodeAccountKey` — drives unbounded mutual recursion between `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP`, eventually exhausting the goroutine stack. Unlike a Java `StackOverflowError` (which kills only the offending thread), a Go stack-overflow is a **fatal, unrecoverable runtime error that terminates the entire process**, making this DoS more severe than the original analog.

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a key type byte and then recursively decodes the corresponding `AccountKey` value: [1](#0-0) 

When the decoded type is `AccountKeyTypeRoleBased`, the resulting value is an `*AccountKeyRoleBased`, whose `DecodeRLP` decodes a list of raw byte strings and, for **each element**, constructs a brand-new `AccountKeySerializer` and calls `rlp.DecodeBytes` on it again: [2](#0-1) 

This creates mutual recursion:
`AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → …

There is no depth counter anywhere in this chain, nor in the generic `rlp` decoder (`rlp/decode.go`) that it rides on. The only place that rejects nested `RoleBased` keys — `checkAccountKeyZeroValues` in `api/api_kaia.go` and `AccountKeyRoleBased.CheckInstallable` — runs **after** decoding has fully completed and unwound, so it cannot prevent the recursive-decode crash itself: [3](#0-2) [4](#0-3) 

**Two reachable entry points for an unprivileged caller:**

1. **Public RPC call, no transaction needed.** `KaiaAPI.DecodeAccountKey` takes arbitrary attacker-supplied hex bytes and feeds them straight into the recursive decoder with no size/depth restriction: [5](#0-4) 

2. **Account-update transaction.** `TxInternalDataAccountUpdate.DecodeRLP`/`fromSerializable` decode the `Key` byte blob via the same `AccountKeySerializer`, and this happens for *every* incoming `TxTypeAccountUpdate` transaction — before signature validation (`SanityCheckSignatures`) is checked in `Transaction.DecodeRLP`: [6](#0-5) [7](#0-6) 

This means a raw, even improperly-signed, `AccountUpdate` transaction submitted via `eth_sendRawTransaction`/p2p broadcast, or a raw byte blob submitted to `kaia_decodeAccountKey`, triggers the vulnerable decode path.

### Impact Explanation
A Go stack overflow triggers `fatal error: stack overflow`, which is **not** a recoverable panic — it immediately terminates the entire process, including all other goroutines, RPC connections, and in-flight consensus/mining activity. This is a full node crash (High severity DoS), reachable pre-authentication (no valid signature required to trigger the crash in the tx path) and pre-authorization (arbitrary caller for the RPC path). Any node exposing the `kaia` RPC namespace or that processes/propagates `AccountUpdate` transactions from the mempool/p2p network is affected, which can be leveraged to crash validator or RPC nodes, degrading availability of the network.

### Likelihood Explanation
High. Constructing the malicious nested-`RoleBased` payload requires only iteratively RLP-encoding `AccountKeySerializer{keyType: RoleBased, key: [prevEncoded]}` in a loop — no cryptographic material or special privileges are needed. Submitting it via `kaia_decodeAccountKey` requires only a public RPC endpoint; submitting it via a crafted `AccountUpdate` transaction requires only broadcasting a transaction (even with a garbage signature, since the crash occurs during `DecodeRLP`, prior to signature checks).

### Recommendation
Add an explicit recursion/nesting-depth counter (e.g., via a `context`/counter parameter or a package-level `Stream` depth field) to `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP`, rejecting decode with an error once a small threshold (e.g., 2, since nested `RoleBased` is never semantically valid) is exceeded — enforcing the "no nested composite type" rule *during* decode rather than only after the fact. Consider also enforcing this depth check generically at the `rlp.Stream` level for recursive `Decoder` implementations, and reject `kaia_decodeAccountKey` input whose decoded structure exceeds a sane size/nesting bound before recursing.

### Proof of Concept
Conceptual construction (Go pseudocode) of an ever-deeper malicious `AccountKey` blob usable either as the `key` argument to `kaia_decodeAccountKey` or as the RLP-encoded `Key` field of a `TxTypeAccountUpdate` transaction:

```go
// start with an innocuous key (e.g., AccountKeyNil encoded)
blob := rlpEncode(AccountKeySerializer{keyType: AccountKeyTypeNil})

// nest it N times inside AccountKeyRoleBased (N ~ tens of thousands,
// since Go stacks grow dynamically, more nesting is required than in Java,
// but the crash is still trivially reachable with a payload of a
// few hundred KB, well within max tx/RPC payload limits)
for i := 0; i < N; i++ {
    roleBasedEnc := rlpEncode([][]byte{blob})           // AccountKeyRoleBased.EncodeRLP format
    blob = rlpEncode(AccountKeySerializer{
        keyType: AccountKeyTypeRoleBased,
        rawKey:  roleBasedEnc,
    })
}

// Trigger via public RPC:
//   kaia_decodeAccountKey(hexutil.Bytes(blob))
// -> api.KaiaAPI.DecodeAccountKey -> rlp.DecodeBytes(blob, &AccountKeySerializer{})
// -> unbounded AccountKeySerializer.DecodeRLP <-> AccountKeyRoleBased.DecodeRLP recursion
// -> fatal error: stack overflow (entire node process crashes)
```

The same `blob`, embedded as the `Key` field of a `txInternalDataAccountUpdateSerializable` and RLP-encoded as a full `TxTypeAccountUpdate` transaction, crashes the node the moment it is decoded from the wire (mempool ingestion or block processing), via `TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable`.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}

			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}

		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
