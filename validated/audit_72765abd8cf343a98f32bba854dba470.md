Audit Report

## Title
Partitioned epoch-reward distribution silently burns earned inflation rewards when a stake account legitimately mutates between the calculation and payout blocks - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

## Summary
Solana's partitioned epoch-reward mechanism computes `PartitionedStakeReward`s from a `StakesCache` snapshot at the epoch boundary in `begin_partitioned_rewards`, then pays them out several blocks later in `store_stake_accounts_in_partition`. If a staker performs an ordinary, unprivileged action (e.g. `Withdraw` or `Split` draining the account to zero lamports) between calculation and their specific partition's payout block, `build_updated_stake_reward` fails to find the pubkey in the current `StakesCache` and the reward is added to `stake_reward_lamports_burned`, which is never credited to capitalization or any account, permanently forfeiting the staker's already-earned reward.

## Finding Description
`begin_partitioned_rewards` computes rewards from a snapshot and schedules payout `REWARD_CALCULATION_NUM_BLOCKS` blocks later, spread across `num_partitions` further blocks [1](#0-0) . At payout time, `build_updated_stake_reward` looks up the stake pubkey in the *current* `StakesCache` snapshot and returns `DistributionError::AccountNotFound` if absent [2](#0-1) . `store_stake_accounts_in_partition` treats this error by adding the reward to `stake_reward_lamports_burned` and `block_reward_lamports_burned` instead of crediting it anywhere [3](#0-2) . In `distribute_epoch_rewards_in_partition`, only `stake_reward_lamports_minted` increases `capitalization`; `stake_reward_lamports_burned` is used solely to keep the `EpochRewards` sysvar bookkeeping consistent via `update_epoch_rewards_sysvar`, marking the reward "distributed" from the sysvar's perspective even though no one received it [4](#0-3) . The function's own doc comment states the (incorrect) assumption that "there should never be rewards burned" because "further state mutation prevent[ed] by stake-program restrictions" [5](#0-4) . `StakesCache::check_and_store` confirms a stake pubkey is removed from `stake_delegations` the instant its lamports reach zero, independent of any pending-reward state [6](#0-5) . Only the narrow rent-adjustment case is reconciled via `adjust_delegation_for_rent`, which mutates an existing delegation still present in the cache [7](#0-6) ; full account closure (pubkey entirely removed) has no equivalent reconciliation and falls into the burn path unconditionally.

Notably, the existing unit test `test_epoch_credit_rewards_and_history_update` explicitly injects a "non-existent account" reward entry and asserts total distributed rewards match `expected_inflation_rewards` computed *before* pushing that extra entry [8](#0-7)  — i.e., the codebase's own test suite already demonstrates that a reward for an account absent from the cache at distribution time does not get credited to capitalization, corroborating the burn behavior described in the claim.

## Impact Explanation
This is an unprivileged fund-loss issue in the runtime rewards/accounts path: a staker's already-computed inflation reward entitlement for the prior epoch is permanently forfeited — neither paid to the staker nor returned to capitalization/incinerator — if that staker performs a normal `Split` or `Withdraw` operation draining their stake account to zero lamports during the multi-block window between reward calculation and their specific partition's payout block. The exact corrupted/lost value is the staker's pending `PartitionedStakeReward` lamports (`stake_reward_lamports_burned` / `block_reward_lamports_burned`), which are dropped from `capitalization` accounting entirely rather than credited or refunded.

## Likelihood Explanation
The distribution window spans `REWARD_CALCULATION_NUM_BLOCKS` plus one block per partition, during which ordinary transactions continue processing normally. Any staker whose account is scheduled for a later partition and who independently closes, splits, or withdraws that account before their partition's specific block — using only standard, unprivileged Stake-program instructions and no special timing knowledge — will trigger this path. This can occur unintentionally, e.g., an automated withdrawal bot acting immediately upon full deactivation.

## Recommendation
- At distribution time, when a stake pubkey is missing from `StakesCache` due to legitimate zeroing, credit the pending reward through an alternate path (e.g., pay to a recorded withdraw destination, or return to capitalization/treasury) instead of unconditionally burning it, following the pattern already established for `adjust_delegation_for_rent`.
- Alternatively, prevent full closure of a stake account while a `PartitionedStakeReward` is still pending for the current epoch's reward status.
- At minimum, treat `stake_reward_lamports_burned` as an explicit, separately audited loss metric distinct from `distributed_rewards`, so this leakage is observable rather than silently absorbed into sysvar bookkeeping.

## Proof of Concept
1. At an epoch boundary, `begin_partitioned_rewards` computes a `PartitionedStakeReward` for staker A's pubkey and schedules it for a later partition block.
2. Before that block arrives, staker A submits an ordinary `Withdraw` (fully deactivated stake) or `Split` (100% of lamports) that drains the account to zero lamports.
3. `StakesCache::check_and_store` observes `account.lamports() == 0` and calls `remove_stake_delegation`, deleting the pubkey from `stake_delegations`.
4. When the scheduled partition block is processed, `build_updated_stake_reward` returns `DistributionError::AccountNotFound`; `store_stake_accounts_in_partition` adds the reward to `stake_reward_lamports_burned`.
5. `distribute_epoch_rewards_in_partition` never adds `stake_reward_lamports_burned` to `capitalization`; the reward is permanently lost while the `EpochRewards` sysvar treats it as distributed.
6. This can be reproduced as a Rust unit test analogous to the existing `test_epoch_credit_rewards_and_history_update`, but asserting that the "non-existent account" reward's lamports are absent from post-distribution `capitalization` rather than merely absent from `updated_stake_rewards`.
