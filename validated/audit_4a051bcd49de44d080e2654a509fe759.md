### Title
Forged aggregate Schnorr signatures accepted because aggregation weights omit keys and nonces - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary

`SchnorrAggregate::verify` derives each aggregation weight only from the ordered Schnorr challenges, omitting both the public keys and the aggregate’s supplied `R` values from the weight transcript. This lets an unauthenticated attacker predict every weight and choose each `R_i` so its weighted verification equation produces a chosen scalar contribution, then set the aggregate `s` to the sum of those contributions. The resulting serialized `SchnorrAggregate` verifies for arbitrary public keys and messages. [1](#0-0) 

### Finding Description

`SchnorrAggregate::read` accepts attacker-controlled `Rs` and `s` from serialized input, and `verify` checks:

```text
Σ z_i * (R_i + c_i * A_i) - s * G == 0
```

where each `z_i` comes from `weight(&mut digest)`. Before calculating the weights, the digest only receives `challenge` values; it does not receive `A_i`, `R_i`, or a commitment to the complete signature batch. [2](#0-1) [3](#0-2) 

Because `z_i` is independent of `R_i`, an attacker can first calculate the weights and then choose any scalar `s_i` and:

```text
R_i = s_i * G - c_i * A_i
s   = Σ z_i * s_i
```

Substitution gives `z_i * (R_i + c_i * A_i) = z_i * s_i * G`, so the verifier equation always holds without knowledge of any private key. [4](#0-3) 

The aggregation side has the same incomplete transcript: `SchnorrAggregator::aggregate` appends only the challenge before `complete` derives weights and combines the submitted signature scalars. [5](#0-4) 

### Impact Explanation

An attacker can create a valid aggregate signature over public keys they do not control and challenges corresponding to messages they did not sign. Any protocol accepting `SchnorrAggregate` as authorization can therefore be convinced that multiple signatures were produced without any signer participating. [6](#0-5) 

This is a signature forgery caused by insufficient Fiat-Shamir binding in the aggregate-verification weights, not merely malformed-input handling.

### Likelihood Explanation

The attack requires only the public verification inputs: target public keys and their message challenges. The attacker can serialize arbitrary `R_i` points and the calculated aggregate scalar, feed them to `SchnorrAggregate::read`, and pass the result to `verify`; no secret, participant position, privileged role, or protocol interaction is required. [2](#0-1) [3](#0-2) 

The calculation is deterministic and succeeds for every non-empty `keys_and_challenges` list whose length matches the supplied `Rs` list.

### Recommendation

Bind the entire aggregate statement into every aggregation weight, including at minimum:

- The ordered public keys.
- The ordered supplied `R` values.
- The ordered challenges/messages.
- The aggregate context/domain separator.

The verifier must reconstruct weights from the same complete transcript used by honest aggregators. Alternatively, reject aggregate verification unless the aggregate format commits to all `(A_i, R_i, c_i)` tuples before deriving weights. Add a regression test that constructs the `R_i = s_iG - c_iA_i` forgery and asserts verification fails.

### Proof of Concept

For each target pair `(A_i, c_i)`, where `A_i` is the public key and `c_i` is the challenge produced for the attacker-selected message:

```text
choose s_i
compute z_i using the implementation's challenge-only transcript
compute R_i = s_i * G - c_i * A_i
compute s = Σ z_i * s_i
serialize len(Rs) || R_1 || ... || R_n || s
```

The verifier calculates:

```text
z_i * R_i + z_i * c_i * A_i
= z_i * (s_i * G - c_i * A_i) + z_i * c_i * A_i
= z_i * s_i * G
```

Therefore the final check becomes:

```text
Σ z_i * s_i * G - s * G == 0
```

which is true when `s = Σ z_i * s_i`. The only obstacle would be if `z_i` depended on `R_i` or `A_i`, but the implementation appends only `c_i` before calling `weight`. [1](#0-0)
