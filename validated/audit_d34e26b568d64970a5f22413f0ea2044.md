## Title
Git argument/option injection via unsanitized fork clone URL in `addRemote`/`setRemoteURL` - (File: app/src/lib/git/remote.ts)

## Summary
`addRemote` and `setRemoteURL` build git commands as `['remote', 'add', name, url]` / `['remote', 'set-url', name, url]` and pass the `url` argument directly to `git()` without a `--` end-of-options separator. [1](#0-0) [2](#0-1)  This `url` value is not always locally sourced — for the "checkout PR from fork" flow it is populated straight from a `PullRequest`/GitHub API object's `head.repo.clone_url` (or `headCloneUrl` parameter), an attacker-influenced field, and passed into `addRemote` unchanged. [3](#0-2)  Compare this to `clone()` in the same module family, which explicitly guards against this exact class of bug by inserting a `--` separator before the url/path: `args.push('--', url, path)`. [4](#0-3)  No such separator, and no validation that the string is a well-formed http(s)/ssh URL (as opposed to a string beginning with `-`), exists in `remote.ts`.

## Finding Description
The broken invariant, analogous to the Sherlock finding's missing "is not uToken" check, is: *"any value flowing into a privileged git operation that originates from a network‑attacker‑influenced object must be validated/escaped before being placed as a positional argument."* This invariant is enforced in `clone.ts` (via `--`) but not in `remote.ts`'s `addRemote`/`setRemoteURL`.

The `_findPullRequestBranch` flow in `app-store.ts` takes `headCloneUrl`, which is ultimately `pullRequest.head.gitHubRepository.cloneURL` / `pullRequest.head.repo.clone_url`, values returned by the GitHub API for a pull request's head repository. [5](#0-4)  A pull request's head repo is typically a fork owned by an arbitrary (possibly malicious) GitHub account, and the `clone_url` field returned by the API for that fork is nominally always a well-formed GitHub URL — but Desktop performs no defense-in-depth validation of its shape before calling `addRemote(repository, forkRemoteName, headCloneUrl)`. [6](#0-5)  If this string ever begins with `-` (e.g. via a compromised/spoofed API response, a man‑in‑the‑middle on a GHES/proxy endpoint, or an alternate code path that trusts a locally-parsed remote URL string), `git remote add <name> <url>` will parse it as an option rather than the remote URL, since `git remote add` accepts flags such as `-f` (immediately fetch), `-t`, `-m`, and `--mirror=fetch|push` via its own option parser.

`urlMatchesRemote`/`parseRemote` (used just before `addRemote` is called) only recognize strings matching known GitHub URL shapes and return `null` otherwise, [7](#0-6)  but this rejection is not used as a security gate — it is only used to decide whether an *existing* remote already matches; when no match is found, the raw, unvalidated `headCloneUrl` is still passed to `addRemote` as-is. [8](#0-7) 

## Impact Explanation
If an attacker can get an option-like string (starting with `-`) into `headCloneUrl`/`remote.url`, `addRemote`/`setRemoteURL` would silently misinterpret it as a `git remote` option instead of a URL, most notably `--mirror=fetch`/`--mirror=push`, which changes the fetch refspec to mirror **all** refs of whatever the *next* positional token resolves to, or `-f` which triggers an immediate implicit fetch with attacker-influenced fetch options. This corrupts the remote configuration silently — the user believes a normal PR-fork remote was added, but the actual git config/refspec differs from what Desktop intended, which can affect what subsequently gets fetched/merged/pushed without the user's knowledge (matching the "silent corruption of what the user commits or pushes" impact class). This is a Medium-severity issue: it requires a specific attacker-controlled string shape reaching this parameter, and the currently reachable public path (via well-formed GitHub `clone_url` fields) is unlikely to produce such a string under normal GitHub API behavior, but the code contains no defensive check comparable to the one present in `clone.ts`.

## Likelihood Explanation
Likelihood is Low-to-Medium. GitHub's API `clone_url`/`ssh_url` fields are always well-formed today, so the most direct path is not trivially exploitable without a compromised or spoofing API/proxy response. However, `addRemote`/`setRemoteURL` are general-purpose functions used across several call sites (fork upstream tracking, PR checkout, repository conversion to fork) with values sourced from GitHub API objects, and none of these call sites, nor `remote.ts` itself, defend against option-injection the way `clone.ts` does. Any future code path, API response anomaly, or enterprise/GHES proxy response that supplies an attacker-shaped string reaches an unguarded git argument boundary.

## Recommendation
Harden `addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts` to insert a `--` separator before the `url` argument (mirroring `clone.ts`'s `args.push('--', url, path)` pattern), e.g. `git(['remote', 'add', name, '--', url], ...)`. Additionally, validate that any externally-sourced `cloneURL`/`clone_url` passed into these functions parses via `parseRemote` (or an equivalent allow-list check for `https://`/`ssh://`/`git@` prefixes) before being used, rejecting/erroring rather than silently passing through malformed values.

## Proof of Concept
1. Simulate a PR whose head repository's `clone_url` (as would be returned from `pullRequest.head.repo.clone_url`) is set to a string such as `--mirror=fetch` (feasible if this value ever originates from an untrusted intermediary, e.g., a GHES instance under attacker influence, rather than github.com's API directly).
2. Desktop's `openPullRequestFromUrl`/`_checkoutPullRequest` flow calls `_findPullRequestBranch(repository, prNumber, headRepoOwner, headCloneUrl, headRefName)`. [5](#0-4) 
3. Since no existing remote matches this URL, Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)`. [3](#0-2) 
4. `addRemote` executes `git(['remote', 'add', forkRemoteName, '--mirror=fetch'], repository.path, 'addRemote')` — git's own argument parser for `remote add` interprets `--mirror=fetch` as an option rather than the destination URL, silently changing the remote's fetch behavior/refspec instead of erroring out or setting a normal remote URL, unlike `clone()` which is hardened against exactly this pattern via `--`. [1](#0-0) [4](#0-3) 

Note: I could not verify from the local index whether GitHub's API layer (`app/src/lib/api.ts`) performs its own strict URL-shape validation on `clone_url`/`ssh_url` before these values reach `app-store.ts`; if such validation exists it would reduce the reachable likelihood of this path. This should be confirmed with a full repository checkout/Devin session since the index may not include all of `api.ts`.

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
