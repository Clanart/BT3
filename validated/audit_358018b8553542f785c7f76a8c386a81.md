### Title
Unrestricted, timelock-free `owner` privileges in `GaslessSwapRouter` (KIP-247) allow rug/fund-redirection against gasless users - (File: contracts/bindings/kip247/GaslessSwapRouter.go / kaiax/gasless module)

### Summary
The KIP-247 gasless-transaction pipeline routes every whitelisted user's token-to-gas swap through a single `Ownable` contract, `GaslessSwapRouter`. Its `owner` can unilaterally repoint the DEX used for any token (`addToken`), change the commission taken from every swap (`updateCommissionRate`), sweep the router's entire native-KAIA balance (the `CommissionClaimed`/balance-transfer path), and hand the whole role to a new address (`transferOwnership`) — all with no timelock, no multisig, and no on-chain delay, exactly the centralization pattern described in the referenced Li.Fi finding (`contractOwner` has complete freedom to change functionality and withdraw/rug assets).

### Finding Description
`GaslessSwapRouter` is deployed as an `Ownable` contract and registered in the KIP-149 `Registry` so that the `kaiax/gasless` module can route gasless swaps to it [1](#0-0) . The gasless module treats it as the trusted `swapRouter` for validating and bundling `GaslessApproveTx`/`GaslessSwapTx` pairs: a transaction is only recognized and promoted as gasless if its spender/router equals `g.swapRouter` and its token is in `g.allowedTokens`, both of which are derived from this owner-controlled contract's state [2](#0-1) .

The contract exposes owner-only mutators with no time delay:
- `addToken(token, factory, router)` / `removeToken(token)` — lets the owner point any whitelisted token to an arbitrary factory/router pair used during `swapForGas` [3](#0-2) .
- `updateCommissionRate(_commissionRate)` — lets the owner set the commission taken from every user's swap with no cap enforced by governance [4](#0-3) .
- A balance-claiming function (emits `CommissionClaimed`) that transfers the router's entire native balance to the owner via `address(this).balance` / low-level `call` [5](#0-4) .
- `transferOwnership` / `renounceOwnership` with no multisig or timelock guard [6](#0-5) .

Because gasless users cannot choose their own DEX/router — the module strictly enforces `args.Router == g.swapRouter` and `g.allowedTokens[args.Token]` before treating a transaction as gasless and having the block proposer lend it gas [7](#0-6)  — every gasless swap's execution path is entirely dictated by values the `owner` can change atomically in a single transaction, with the very next gasless swap immediately subject to the new routing/commission.

### Impact Explanation
An `owner` key compromise or malicious update lets the attacker:
1. Redirect a whitelisted token's swap route (`addToken`) to an attacker-controlled router/factory that returns less WKAIA than expected or drains the swapped tokens, directly stealing gasless users' funds during `swapForGas`.
2. Set `updateCommissionRate` to (near) 100%, expropriating the value of every gasless swap.
3. Sweep the router's accumulated native balance at will.
4. Transfer ownership to conceal the above, with no on-chain delay for users/monitors to react before the change takes effect on the next transaction.

Because this is the sole gate that determines whether the proposer lends gas and how a user's tokens are swapped for gas repayment, this is a real path to unauthorized value movement, not merely a governance/reputation concern.

### Likelihood Explanation
Exploitation requires only that the router's `owner` key be used maliciously or compromised — no consensus-level or peer-only capability is needed, and no waiting period exists to blunt a bad update. Given the report itself concedes this is the intended trust model, and Kaia's docs confirm every gasless swap for every user unconditionally goes through this one owner-controlled contract, likelihood of impact realization following any key compromise or malicious action is high and immediate (effective on the very next `swapForGas` transaction).

### Recommendation
- Require a timelock (e.g., 24–72h) before `addToken`, `removeToken`, `updateCommissionRate`, and commission withdrawal take effect, giving gasless users/monitors time to react.
- Cap `commissionRate` on-chain to a governance-approved maximum rather than allowing arbitrary owner-set values.
- Move `owner` to a multisig or DAO-controlled address, consistent with the mitigation Li.Fi itself acknowledged adopting.
- Emit and require an on-chain grace period between `addToken`/`removeToken` updates and their effect on already-pending gasless bundles, to avoid mid-flight route changes affecting a user's already-signed swap.

### Proof of Concept
1. Owner deploys/holds `GaslessSwapRouter`, registered in the KIP-149 `Registry` as the canonical gasless swap router (as in the test setup) [1](#0-0) .
2. A user signs a `GaslessApproveTx` + `GaslessSwapTx` pair against the currently registered `(token, router)` pair, expecting the module's `IsApproveTx`/`IsSwapTx` checks to route the swap safely [8](#0-7) .
3. Before the user's transaction is included, the owner calls `addToken(token, maliciousFactory, maliciousRouter)` in a single transaction, replacing the DEX route for that token with an attacker-controlled router/factory pair [3](#0-2) .
4. The proposer, per the gasless block-building rule, still lends gas and bundles `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` [9](#0-8) , and `swapForGas` executes against the now-malicious router, causing the user to receive less (or none) of the expected WKAIA while still repaying the lent gas — a direct fund loss enabled purely by unrestricted, non-timelocked owner privilege.

# kaiax/gasless

This module is responsible for facilitating gasless transactions specified by [KIP-247](https://kips.kaia.io/KIPs/kip-247).

## Concepts

Gasless transaction (GaslessTx) consists of two types: gasless approve transaction (GaslessApproveTX), and gasless swap transaction (GaslessSwapTx).

Note that gasless transaction does not mean the gas prices of gasless transactions are zero, but it means that proposer will lend the user with gas fee and user will pay back during gasless swap.

The gas fee of gasless transaction's is funded by block proposer (i.e., lend transaction generated by `GetLendTxGenerator`), and user repays the lent amount during gasless swap.
