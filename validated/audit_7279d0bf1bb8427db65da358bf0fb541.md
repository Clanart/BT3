Based on my investigation, I found a genuine Cosmos-EVM analog to the reported "non-payable proxy fallback" bug class: instead of a low-severity "funds can't reach the target function" issue, this repository has a **stateful balance-handler bug with a shared (non-reentrant-safe) instance**, which can cause the EVM `StateDB` balance to desynchronize from the real `x/bank` balance when precompiles are called recursively/nested in one EVM transaction — a critical accounting-corruption class.

Key evidence:
- The generic (newer) precompile base `Precompile.runNativeAction` in [1](#0-0)  correctly allocates a **fresh** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()`.
- However, several precompiles (distribution, erc20, gov, ics20, slashing, staking) instead use a persistent, shared handler obtained via `p.GetBalanceHandler()` (pattern shown in the debug-precompile analog at [2](#0-1) ), meaning the *same* `BalanceHandler` object (with its single `prevEventsLen` field) is reused across nested precompile invocations within one transaction.
- `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` in [3](#0-2)  rely on `prevEventsLen` being correct at the time `AfterBalanceChange` slices `ctx.EventManager().Events()[bh.prevEventsLen:]` to translate bank `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events into `StateDB.AddBalance`/`SubBalance` calls.
- If an inner/nested precompile call re-invokes `BeforeBalanceChange` on the *same* handler instance, it overwrites `prevEventsLen`, so when the outer call's `AfterBalanceChange` runs, it reads the wrong event-slice boundary — causing bank balance-change events belonging to the outer call to be dropped or mis-attributed, and thus the EVM `StateDB` balance diverges from the actual `x/bank` ledger balance for the affected accounts.
- This exact defect is documented and reproduced by a dedicated regression test, whose comment explicitly states the bug: "recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB" [4](#0-3) , reproduced via a contract that recursively calls a precompile inside the same tx [5](#0-4) .

Because this test exists specifically to characterize the bug, it strongly suggests the underlying defect is real in the shared-handler precompiles, but I was not able to fully trace whether the currently-shipped `distribution`, `staking`, `gov`, `ics20`, or `slashing` precompiles still use the vulnerable shared-instance pattern in their production `Run` methods (I only confirmed the pattern in the `testutil`/`evmd/tests` debug-precompile helper, which is test-only code, and confirmed the *safe* per-call pattern in the current common `Precompile.runNativeAction`). I could not conclusively verify, within available tool calls, whether a production precompile path (e.g. ICS20 IBC callback re-entering another precompile, or a distribution `claimRewards` call nested inside another precompile call) still exercises this shared/stale-instance defect, or whether it has already been fixed to always use `BalanceHandlerFactory.NewBalanceHandler()` per call.

### Title
Shared BalanceHandler instance across recursive/nested precompile calls corrupts EVM StateDB balances vs. native bank ledger - (File: precompiles/common/balance_handler.go, precompiles/distribution/distribution.go, precompiles/staking/staking.go, precompiles/gov/gov.go, precompiles/ics20/ics20.go, precompiles/slashing/slashing.go)

### Summary
Precompiles that obtain a single, persistent `BalanceHandler` via `p.GetBalanceHandler()` (rather than creating a fresh handler per invocation, as the current `common.Precompile.runNativeAction` does) share the handler's `prevEventsLen` bookkeeping field across nested/recursive precompile calls made within one EVM transaction. When an inner precompile call runs `BeforeBalanceChange`, it overwrites `prevEventsLen`, causing the outer call's `AfterBalanceChange` to compute the wrong slice of bank events, resulting in `StateDB.AddBalance`/`SubBalance` calls that don't match the real `x/bank` coin movements.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` at call start; `AfterBalanceChange` later processes `events[prevEventsLen:]` to mirror bank-module `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events into the EVM `StateDB` ( [3](#0-2) ). This design assumes a strict LIFO, non-overlapping call/response cycle per handler instance. If the same `BalanceHandler` instance is invoked again (nested call) before the outer call finishes, `prevEventsLen` is clobbered, and the outer `AfterBalanceChange` will use a boundary that no longer reflects the outer call's own starting event index — silently skipping or double-processing events tied to real coin movements.

The regression test [5](#0-4)  demonstrates the mechanics using a contract that recursively invokes a debug precompile (`Call0` → `CallEVMWithData` → recursive precompile re-entry), confirming that nested precompile execution paths reuse handler state and produce divergent counts of applied balance events versus expected precompile invocations.

### Impact Explanation
If exploitable in a production precompile (e.g., `distribution`, `staking`, `gov`, `ics20`, or `slashing`) that both moves bank coins and can be re-entered within a single EVM transaction (e.g., via a contract calling the precompile, receiving a callback, and calling the precompile again before the outer call returns), the EVM-visible balance (`StateDB`) can diverge from the true `x/bank` ledger balance for the duration of, and possibly beyond, that transaction. This is an accounting-corruption primitive: an attacker-controlled contract could arrange for the `StateDB` to retain a stale (higher) balance while the real bank balance has already been decremented, enabling additional spends/transfers against phantom balance in the same transaction — i.e., duplication of spendable value, which is Critical severity under the invariant "irreversible accounting corruption of spendable user value across native balances ... precompile-mediated assets."

### Likelihood Explanation
Reachability depends on whether any of the shipped precompiles still use the shared/one-per-precompile-instance `BalanceHandler` pattern (`p.GetBalanceHandler()`) in their `Run` methods, and whether an unprivileged, attacker-deployed contract can legitimately trigger a nested/recursive precompile call within a single transaction (e.g., a distribution `claimRewards` call whose execution path invokes another balance-affecting precompile, or an ICS20 transfer with an IBC callback hook that re-enters a precompile). I confirmed the vulnerable shared-handler code path exists in the test/debug precompile helper and that the newer common precompile base has since moved to a safe per-call factory pattern, but I could not fully verify within available tool budget whether the specific in-scope precompiles (`distribution`, `staking`, `gov`, `ics20`, `slashing`) still instantiate `GetBalanceHandler()` as a shared struct field versus already having been migrated to `BalanceHandlerFactory.NewBalanceHandler()` per call.

### Recommendation
Ensure every precompile creates a fresh `BalanceHandler` for each `Run`/`RunNativeAction` invocation (as `precompiles/common/precompile.go`'s `runNativeAction` already does), rather than sharing one instance across the precompile's lifetime. Add reentrancy/nesting guards or use call-scoped local variables (not struct fields) for `prevEventsLen` so nested precompile invocations cannot corrupt each other's event-slice bookkeeping. Extend the existing regression test in `evmd/tests/integration/balance_handler/balance_handler_test.go` to assert exact balance equality between `x/bank` and `StateDB` after nested/recursive calls to each of `distribution`, `staking`, `gov`, `ics20`, and `slashing` precompiles.

### Proof of Concept
The existing test `TestRecursivePrecompileCallsWithDebugPrecompile` in [5](#0-4)  is itself a proof-of-concept skeleton: a contract calls a debug precompile method that recursively re-enters via `CallEVMWithData`, producing a call graph identical in shape to what a malicious contract could construct against a bank-balance-moving precompile (e.g., calling `distribution.claimRewards`, which internally triggers a nested precompile-mediated transfer via a hook/callback, before the outer call's `AfterBalanceChange` executes). To fully validate exploitability against a real Critical-impact target, this pattern needs to be replicated against `distribution`, `staking`, `gov`, `ics20`, or `slashing` with balance assertions comparing `x/bank` `GetBalanceFromBank` results against the EVM `StateDB`/`eth_getBalance` result after the nested call completes, to confirm a measurable balance divergence (duplication or loss of spendable value).

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}
