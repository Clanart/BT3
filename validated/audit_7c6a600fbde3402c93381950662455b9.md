### Title
Reward-index manipulation via totalStaked() front-running in `BaseRewardPool._provisionReward`/`queueNewRewards` - ([File: rewards/BaseRewardPool.sol])

### Summary
`_provisionReward` computes a single, instantly-applied global reward-per-token increment as `(_amountReward * 10**stakingDecimals()) / totalStaked()`, where `totalStaked()` is read live at call time [1](#0-0) . Because deposits/withdrawals in `MasterMagpie` are permissionless and have no cooldown, an unprivileged staker can watch the manager's `queueNewRewards` transaction in the mempool and front-run it with a large `withdraw()` that shrinks `totalStaked()` to a dust value, causing the divisor to collapse and `rewardPerTokenStored` to spike to an artificially huge value, then back-run with a small `deposit()`/`getReward()` to capture an outsized share of the reward.

### Finding Description
`totalStaked()` in `BaseRewardPool`/`BaseRewardPoolV2` is defined as the live balance of the staking token held by the `operator` (MasterMagpie) [2](#0-1) , not a value snapshotted or averaged over time. `queueNewRewards`/`_provisionReward` immediately folds the entire donated reward amount into the single, monotonically-increasing accumulator `rewardInfo.rewardPerTokenStored` in one shot, using whatever `totalStaked()` happens to be at that exact instant [3](#0-2) . There is no time-weighted streaming (unlike MasterMagpie's own MGP emission which is rate-based via `accMGPPerShare`/`lastRewardTimestamp` in `updatePool` [4](#0-3) ), and no minimum-liquidity floor or cooldown protecting the denominator.

`MasterMagpie.deposit`/`withdraw` are unrestricted, `nonReentrant`/`whenNotPaused`-gated public functions available to any staker [5](#0-4) . An attacker holding a meaningful share of a pool's stake can observe the manager's `queueNewRewards(amount, token)` transaction in the public mempool and front-run it by calling `withdraw()` to reduce `totalStaked()` to near-zero just before `_provisionReward` executes. Because `_provisionReward` divides the reward amount by this near-zero `totalStaked()`, `rewardPerTokenStored` becomes disproportionately inflated. The attacker then back-runs with a small `deposit()` (which calls `_harvestBaseRewarder` → `updateFor` snapshotting `userRewardPerTokenPaid` at the pre-injection low value) followed by `getReward`, so `earned()` computes `balanceOf(account) * (rewardPerToken - paid) / 10**decimals`, multiplying even a tiny balance against the artificially huge rate and yielding a reward payout far beyond the attacker's true pro-rata contribution [6](#0-5) [7](#0-6) .

Existing safeguards — `onlyManager` on `queueNewRewards`, `nonReentrant`/`whenNotPaused` on deposit/withdraw, and the `updateReward`/`updateFor` snapshot pattern — do not address this because they only govern *who* can call these functions and *when balances are recorded*, not the *temporal ordering* of `totalStaked()` relative to reward injection, which is exploitable purely through public mempool front-running by any staker holding a large enough share of the pool at that moment.

### Impact Explanation
This allows direct theft of reward funds: the attacker can claim reward tokens far exceeding their true time-weighted share, at the expense of the reward pool's other legitimate stakers, and can potentially drain most of a `queueNewRewards` donation with only a dust stake at claim time. This matches the Immunefi "theft of unclaimed yield / direct theft of user funds" impact class for `BaseRewardPool`/`BaseRewardPoolV2`/`BribeRewardPool`-style reward pools.

### Likelihood Explanation
The attack requires the attacker to already hold a dominant share of a given pool's stake (so their withdrawal materially shrinks `totalStaked()`) and to observe/front-run the manager's `queueNewRewards` transaction in the mempool — both are realistic for low-TVL or newly launched pools and require no privileged role, only capital already deployed as a normal staker plus standard MEV front-running capability. It is repeatable each time a `queueNewRewards` call is broadcast while the pool has low/concentrated liquidity.

### Recommendation
Do not let a single instantaneous `totalStaked()` reading gate a lump-sum reward injection. Options: (1) stream/vest injected rewards over time (as MasterMagpie already does for MGP via `accMGPPerShare`/`lastRewardTimestamp`) rather than applying the full amount in one `rewardPerTokenStored` update; (2) enforce a minimum `totalStaked()` floor or revert `_provisionReward` if `totalStaked()` is below a sane threshold relative to recent history; (3) add a withdrawal cooldown/delay so stake cannot be pulled out immediately before a reward injection; (4) snapshot `totalStaked()` at a fixed point (e.g., start of epoch) rather than reading it live at the exact call.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, a staking token, and `BaseRewardPool` with a reward token; register the pool with a manager.
2. Staker A (victim) deposits `1000e18` staking tokens; staker Attacker deposits `9000e18` (90% of pool), so `totalStaked() = 10000e18`.
3. Simulate mempool front-running: in the same block, Attacker calls `withdraw(stakingToken, 8999e18)` immediately before the manager's `queueNewRewards(1000e18, rewardToken)` executes, leaving `totalStaked() ≈ 1001e18` (still not dust enough — to make the PoC dramatic, have Attacker withdraw down to `1e18`, so `totalStaked() = 1001e18` vs the naive expectation of `10000e18`).
4. Manager calls `queueNewRewards(1000e18, rewardToken)`; assert `rewardPerTokenStored` is now computed against the shrunk `totalStaked()`, i.e., roughly 10x higher than it would have been without the front-run withdrawal.
5. Attacker calls `deposit(stakingToken, 1)` (back-run) then `getReward`; assert Attacker's claimed reward exceeds their true pro-rata share (i.e., exceeds `1000e18 * (attacker's actual time-weighted stake / 10000e18)`), and that staker A's `earned()` is correspondingly diluted below their fair share of `1000e18` based on their `1000e18` constant stake.
6. Assert total reward token balance paid out plus remaining pool balance is consistent, demonstrating that the attacker extracted a share of the `1000e18` donation disproportionate to time-weighted stake, confirming the conservation invariant (`earned <= rightful share`) is violated.

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            userRewards[rewardToken][_account] = earned(_account, rewardToken);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
