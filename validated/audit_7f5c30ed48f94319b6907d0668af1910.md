## Finding: Silent Loss of Conflict Content When Copilot's Hunk-Resolution Count Doesn't Match the File's Marker Count

### Title
Order-based (not identity-based) hunk splicing in Copilot conflict resolution can silently delete user code from a committed file - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
This is the closest Desktop analog to the `RewardDistributor` bug: instead of "not enough reward tokens → tokens silently lost," the invariant here is "not enough model-returned hunk resolutions → conflicted code silently lost," and the loss is written directly into the file the user then commits.

### Finding Description
`reassembleResolvedFile` reconstructs the final file by walking the raw on-disk content (which still has literal `<<<<<<<`/`=======`/`>>>>>>>` markers) and, for every well-formed marker block it finds, splices in the next entry from `hunkResolutions` **by array order, not by any stable identity** [1](#0-0) . If `hunkIndex` ever reaches or exceeds `hunkResolutions.length`, the code does nothing for that block — it has already advanced `i` past the closing `>>>>>>>` marker, so both the "ours" and "theirs" content of that conflict block are dropped from the output with no fallback and no error: [2](#0-1) 

The hunk count that `hunkResolutions` is expected to have is derived from `extractConflictHunks`, a separate, independently-run regex scan of the same file that is only used to build the prompt sent to the model [3](#0-2) . Nothing in the pipeline enforces that the model's JSON response contains exactly one resolution per hunk that `extractConflictHunks` found, nor that `reassembleResolvedFile`'s independent marker walk finds the same count of blocks as `extractConflictHunks` did. The two counts are computed by two different parsers over the same text and are only reconciled implicitly, "by order."

The result of `_applyCopilotConflictResolutions` is written straight to disk and staged without any diff/line-count sanity check against the original file: [4](#0-3) 

### Impact Explanation
Because the reassembled content is written verbatim to the working file and staged for commit, a resolution-count mismatch causes the tool to silently strip an entire conflict block (both sides' code) from the file that the user then commits — a corruption of what the user is about to push, without any warning surfaced in the "Continue Merge" flow. This matches the "Valid Impact" criterion of *silent corruption of what the user commits or pushes*, triggered purely by processing an attacker-influenced/crafted repository (a merge with unusual, malformed, or ambiguous conflict-marker content is exactly the kind of "attacker controls a cloned/fetched repository" scenario named in the report).

### Likelihood Explanation
This requires no local access, admin rights, or leaked credentials — only that the user resolves a merge conflict with Copilot on a repository containing conflict-marker-like text that causes a mismatch between what `extractConflictHunks` counted for the prompt and what the model returned or what the reassembly walk finds (e.g., additional marker-shaped blocks that were skipped from the prompt for being oversized/too-long per `getHunkSkipReason`, but are *not* skipped by `reassembleResolvedFile`'s more permissive marker-matching, since that function only checks for well-formedness, not size). The function's own documentation acknowledges the ordering assumption is a shortcut ("matched by order, not by line number") [5](#0-4) , and no downstream code (the retry loop, `validateResolutionPaths`, etc., visible around [6](#0-5) ) is confirmed to cross-check the resolved-hunk count against the actual marker-block count in `rawContent` before it's written to disk. I was unable to fully inspect the body of `validateResolutionPaths` in this session, so it is possible (but unconfirmed) that path-level validation exists without a corresponding hunk-count validation — this should be verified directly in the source before treating this as fully proven.

### Recommendation
- In `reassembleResolvedFile`, assert that `hunkResolutions.length` equals the number of well-formed marker blocks found in `rawContent`; if they don't match, reject the resolution (throw) instead of silently truncating the output.
- Additionally/alternatively, key hunk resolutions to a stable identifier (e.g., hunk start line number or a content hash of the ours/theirs pair) instead of positional order, so a mismatch produces a clear failure rather than misaligned or dropped splices.
- Surface any such mismatch to the user in the result dialog rather than writing a silently-shortened file to disk and staging it.

### Proof of Concept
1. Attacker crafts/pushes a branch such that, when merged locally, a file ends up with N genuine conflict blocks plus additional conflict-marker-shaped content that is filtered out of the model prompt by `getHunkSkipReason` (e.g., one hunk's combined content exceeds `MAX_CONFLICT_CONTENT_SIZE`, or one hunk has an over-long line per `MAX_CONFLICT_LINE_LENGTH`) [7](#0-6) , while another, unrelated well-formed marker block still exists elsewhere in the same file's raw content on disk.
2. The user opens the merge in Desktop and triggers Copilot conflict resolution. The prompt reflects only the hunks that passed the skip filters, so the model returns fewer `hunkResolutions` entries than the number of marker blocks physically present in `rawContent`.
3. On "Continue Merge," `reassembleResolvedFile` walks the raw file, successfully resolves the first N-1 blocks, and for the Nth (unaccounted) block simply advances past it without emitting any replacement content — the entire hunk (both "ours" and "theirs" text) disappears from the written file [2](#0-1) .
4. `_applyCopilotConflictResolutions` writes this truncated content to disk and `git add`s it [8](#0-7) , so the user commits and can push a file silently missing a chunk of code, with no error or warning shown.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}
