Based on my research, I found a Windows-only analog to the tree-kill issue: unsanitized string interpolation of a filesystem path into a command line that is executed via `spawn(..., { shell: true })` (i.e., through `cmd.exe`).

### Title
Cmd.exe metacharacter injection via unescaped repository path in Windows shell launch - (File: app/src/lib/shells/win32.ts)

### Summary
`app/src/lib/shells/win32.ts` builds the command line for "Open in [Shell]" by string-concatenating the target repository `path` directly into an argument string, then invokes it with `spawn(cmd, args, { shell: true, cwd: path })`. This mirrors the tree-kill bug: on the Windows-only code path, the value is `+`-style embedded into a string that is handed to a shell, without cmd.exe-aware escaping (only naive `"` wrapping is applied), while POSIX shells (macOS/Linux) go through the properly escaped/quoted path in `app/src/lib/hooks/shell-escape.ts`.

### Finding Description
The `launch()` function wraps `path` in double quotes but does not escape characters that are cmd.exe metacharacters (`&`, `|`, `^`, `%`, `<`, `>`) which are nonetheless legal in Windows folder names (only `<>:"/\|?*` are illegal in NTFS filenames): [1](#0-0) 
Every case in `launch()` follows the same unsafe pattern — plain double-quote wrapping instead of `cmd`-aware escaping: [2](#0-1) [3](#0-2) 
Contrast this with the project's own POSIX quoting utility, which explicitly escapes shell metacharacters before building a command string — the same rigor is absent in the Windows `shell: true` `spawn` calls: [4](#0-3) 
The comment in `get-shell.ts` also shows the team's assumption that "there shouldn't be any user input" going into these shell invocations — an assumption that doesn't hold for a repository path that traces back to a remote/clone source: [5](#0-4) 

### Impact Explanation
If a repository's on-disk directory name (attacker-influenced via the folder name derived from a cloned/attacker-controlled remote, or a crafted deep link that resolves to a path containing cmd.exe metacharacters such as `&`) is opened via "Open in Command Prompt / PowerShell / Git Bash / etc.", the resulting `spawn(..., { shell: true })` call passes the unescaped string to `cmd.exe`, allowing arbitrary command execution in the context of the logged-in Desktop user. This is the same "insecure concatenation only affects Windows" class as the tree-kill report — POSIX platforms are properly quoted, Windows is not.

### Likelihood Explanation
Exploitation requires the user to trigger "Open in Shell" (or a custom shell integration) against a repository whose local folder name contains a cmd.exe metacharacter. I could not fully verify within this session whether GitHub Desktop's default clone-folder naming logic can produce such a folder name from an attacker-controlled remote/URL (e.g., a generic/self-hosted git remote or `x-github-client://openRepo/...` deep link), since Windows filesystem rules permit `&`, `%`, `^`, etc. in folder names while GitHub.com's own repo-name validation would block them. This part of the chain — how far an attacker can push characters into the local repository folder name — needs further verification against the clone-path derivation code, which I was not able to fully trace in the time available.

### Recommendation
Use a proper Windows/`cmd.exe`-aware quoting/escaping function (equivalent to the `cmd` escaper already implemented in `app/src/lib/hooks/shell-escape.ts`) for every path/argument interpolated into the `spawn(..., { shell: true })` calls in `app/src/lib/shells/win32.ts`, or avoid `shell: true` entirely by passing arguments as an array to the target executable directly.

### Proof of Concept
Not independently verified end-to-end due to tool-call limits; the reachable primitive is: create/clone a repository into a folder such as `C:\Users\victim\repo & calc.exe`, add it to GitHub Desktop, then use "Open in Git Bash" (or any listed shell), which executes:
```
"<git-bash.exe>" --cd="C:\Users\victim\repo & calc.exe"
```
via `cmd.exe` (`shell: true`), causing `calc.exe` to launch as an injected command. Confirmation of exactly how an attacker-supplied remote/clone flow can produce such a folder name automatically (without local/physical access) is the remaining unverified step.

// https://github.com/ericcornelissen/shescape/blob/89072ba7de233f81f5553b52098671c94eb9bd0c/src/internal/win/cmd.js#L35
const cmdEscape = (arg: string) =>
  arg
    .replace(/[\0\u0008\r\u001B\u009B]/gu, '')
    .replace(/\n/gu, ' ')
    .replace(/"/gu, '""')
    .replace(/([%&<>^|])/gu, '"^$1"')
    .replace(/(?<!\\)(\\*)(?="|$)/gu, '$1$1')

export const cmd: Shell = {
  args: ['/d', '/s', '/c'],
  quoteCommand: (cmd, ...args) =>
    `"${[cmd, ...args].map(a => `"${cmdEscape(a)}"`).join(' ')}"`,
}
