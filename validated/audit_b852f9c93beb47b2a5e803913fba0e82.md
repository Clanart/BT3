### Title
Missing receiver-safety check in `CW721ERC721Pointer.transferFrom` can permanently lock CW721-backed NFTs sent to contracts - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer` is the EVM-side pointer contract that represents a CosmWasm CW721 NFT collection as an ERC721 token, reachable by any EVM transaction sender who holds or is sent one of these pointer NFTs. Its overridden `transferFrom` performs the actual ownership move by executing a `transfer_nft` message against the underlying CW721 contract via the wasmd precompile, but it never performs (nor delegates to) an ERC721-receiver capability check on `to`, unlike the sibling `CW1155ERC1155Pointer`, which explicitly calls `onERC1155Received`/`onERC1155BatchReceived` on the recipient in its transfer paths.

### Finding Description
`transferFrom` in `CW721ERC721Pointer.sol` is fully overridden and bypasses the OpenZeppelin `ERC721` internal state machine (`_update`/`_ownerOf`) entirely — it queries/verifies ownership against the CosmWasm contract and issues a `transfer_nft` execute message directly: [1](#0-0) 

Because this override never calls `_safeTransfer`/`_checkOnERC721Received` (or any receiver capability check), any recipient address — including a smart contract that does not implement `onERC721Received` or otherwise cannot dispose of ERC721 tokens — can be sent the pointer NFT and it becomes stuck forever with no path to move it back.

Additionally, `CW721ERC721Pointer` does not override `safeTransferFrom` at all, so it inherits OpenZeppelin's default `ERC721.safeTransferFrom`, which operates on the local, never-populated `_ownerOf` mapping (since minting/transfers are only reflected in the remote CW721 contract, not in local ERC721 storage). Calling the inherited `safeTransferFrom` on the pointer therefore does not perform a real transfer and cannot be relied upon as the "safe" entry point, leaving the unsafe `transferFrom` as the only functional transfer mechanism users interact with.

This is analogous to the reported bug class in the external report (minting via `_mint()` without a receiver-capability check, leading to tokens becoming stuck in contracts that cannot handle ERC721): here, the sei-chain CW<->EVM NFT pointer's only working transfer path lacks the equivalent safety check that `_safeMint()`/`safeTransferFrom()` normally provide.

By contrast, the CW1155 pointer's transfer functions do perform the receiver check: [2](#0-1) 

confirming that the omission in the CW721 pointer is an inconsistency/gap rather than an intentional design choice.

### Impact Explanation
Any EVM user (an unprivileged transaction sender) who owns or is transferred a CW721-pointer NFT and calls `transferFrom` to move it to a smart contract address (e.g., a marketplace, vault, or any non-EOA integration that doesn't specifically handle bare ERC721 transfers) can have the underlying CW721 NFT permanently locked with no recovery mechanism, since the pointer's `transferFrom` unconditionally executes the transfer on the CW721 side regardless of whether the recipient can act on it. This is a permanent freezing/loss-of-asset scenario for NFTs bridged through the pointer.

### Likelihood Explanation
Likelihood is moderate: it requires a user (or an integrating contract calling `transferFrom` on their behalf, e.g. via `NftMarketplace`-style flows as exercised in the test suite) to send the pointer NFT to a contract address that isn't designed to receive/handle bare ERC721 transfers. Given that pointer contracts are meant to be composable with generic EVM tooling and marketplaces that commonly expect `safeTransferFrom` semantics, this is a realistic operational path, not a contrived edge case.

### Recommendation
Add the standard ERC721 receiver-capability check (`_checkOnERC721Received` equivalent) to `CW721ERC721Pointer.transferFrom`, or expose a properly implemented `safeTransferFrom` that performs the real CW721-backed transfer and then checks `onERC721Received` on contract recipients, reverting on failure — mirroring the pattern already used in `CW1155ERC1155Pointer.safeTransferFrom`/`safeBatchTransferFrom`.

### Proof of Concept
1. Deploy a `CW721ERC721Pointer` for an existing CW721 collection and mint/own an NFT (token id `X`) as `accountA`.
2. Deploy a plain contract `Sink` with no `onERC721Received` implementation and no other means to transfer ERC721 tokens out.
3. From `accountA`, call `pointer.transferFrom(accountA, address(Sink), X)`.
4. Observe: the call succeeds (no receiver check), `Sink` now "owns" token `X` on the CW721 side, but `Sink` has no function to call `transfer_nft`/`transferFrom` again, so the NFT is permanently stuck, unrecoverable by anyone. [1](#0-0)

        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }
