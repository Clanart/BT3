### Title
Panic (DoS) via unchecked `commitments[&sender]` indexing on attacker-controlled participant index in blame evaluation - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame_internal` indexes `self.commitments[&sender]` without validating that `sender` is within the participant set, so an out-of-range or unknown participant index supplied with a blame statement causes a HashMap-index panic (the Rust analog of the CVE-2018-18457 NULL-deref crash class: fatal error on attacker-crafted input). [1](#0-0) 

### Finding Description
`blame_internal` is reached through `BlameMachine::blame` and `AdditionalBlameMachine::blame`, both of which take `sender`/`recipient` `Participant` values derived from untrusted blame messages. [2](#0-1)  The function first calls `decrypt_with_proof(sender, recipient, msg, proof)`; if that succeeds it evaluates `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)`. [3](#0-2)  `self.commitments` is populated only for participants `1..=n` (in `KeyMachine::calculate_share` via `verify_r1`'s `validate_map`, or in `AdditionalBlameMachine::new` via the `1..=n` loop). [4](#0-3)  Neither `blame` entry point bounds-checks `sender` or `recipient` against `params.n()` before the indexing, and `HashMap`'s `Index` impl panics on a missing key. [5](#0-4)  An analogous unguarded index exists in `calculate_share` at `self.commitments[&l]`, but there `validate_map` constrains `l` to legitimate participants; the blame path lacks that guard. [6](#0-5) 

### Impact Explanation
A panic inside blame evaluation aborts the DKG/blame protocol — and in a hosting binary (e.g. a processor handling blame statements, which feeds attacker-supplied `accuser`/`accused`/`share` bytes into `AdditionalBlameMachine::new(...).blame(accuser, accused, ...)`) crashes the task or process. This is a remote denial of service reachable purely from public protocol inputs: a blame accusation naming a participant index outside `1..=n` paired with an `EncryptedMessage` that passes `decrypt_with_proof`. [7](#0-6) 

### Likelihood Explanation
The attacker must be able to submit a blame statement (a normal protocol message naming arbitrary sender/recipient indexes) and an `EncryptedMessage` whose PoP/decryption proof verifies — trivially achievable by encrypting to a key they control, since `EncryptedMessage::read` accepts arbitrary serialized bytes. [8](#0-7)  The crash then requires only choosing `sender` as a `Participant` value not present in the commitments map (e.g. `n+1`). Note `recipient` is only passed through to `share_verification_statements`, but a bogus `sender` alone suffices.

### Recommendation
In `blame_internal` (or both `blame` wrappers), validate `sender` and `recipient` against the commitments map / `params` before indexing: return a defined fault (or an error) for out-of-range participants instead of using `self.commitments[&sender]`. Prefer `self.commitments.get(&sender)` with an explicit early return of `sender`/`recipient` as faulty. [9](#0-8) 

### Proof of Concept
Conceptually: run a PedPoP DKG to a `BlameMachine`/`AdditionalBlameMachine` for `n` participants. Construct `msg = EncryptedMessage::<C, SecretShare<C::F>>::read(...)` for a share encrypted under a key whose ECDH to `recipient`'s registered encryption key is known (i.e. attacker is a legitimate sender producing a well-formed message), then call `blame(sender = Participant::new(n + 1).unwrap(), recipient = 1, msg, proof)`. `decrypt_with_proof` returns `Ok`, then `self.commitments[&sender]` panics on the missing key — a crash from bytes entirely under attacker control, matching the crafted-file → null-deref class of CVE-2018-18457. [10](#0-9)
