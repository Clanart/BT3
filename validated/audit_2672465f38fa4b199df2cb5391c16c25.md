### Title
`assign_program` transition matcher lacks arms for documented `Closed`/`Loaded`/`FailedVerification` → `Closed` same-slot transitions, causing silent cache-poisoning fallback in release builds - (File: `program-runtime/src/loaded_programs.rs`)

### Summary
`ProgramCache::assign_program`'s `match (&existing.program, &entry.program)` guard only whitelists five transitions (`Builtin→Builtin`, `Closed→Loaded`, `Closed→FailedVerification`, `Unloaded→Loaded`, `Unloaded→FailedVerification`), while `program_cache_entry.rs` documents additional valid same-slot transitions including `Closed => Closed` and `Loaded/FailedVerification => Closed` (via `UpgradeableLoaderInstruction::Close`). When these documented-but-unlisted transitions occur, execution falls into the `_ => { debug_assert!(false, ...); self.stats.replacements.fetch_add(1, ...); return true; }` branch, which is a no-op safety check in release builds (`debug_assert!` compiled out) and leaves `*existing` **unmodified** despite the function reporting success.

### Finding Description
The whitelist in `assign_program` is: [1](#0-0) 

Documented valid transitions in the same file family explicitly include same-slot `Closed => Closed` (loader migration) and `Loaded / FailedVerification => Closed` (regular `Close` instruction): [2](#0-1) 

Under ordinary operation, distinct deploy/close/upgrade actions for a given program key produce entries with distinct `deployment_slot` values, so the `binary_search_by` keyed on `(deployment_slot, account_owner, ...)` in `assign_program` almost always returns `Err(index)` (fresh insert), never reaching the `match (&existing.program, &entry.program)` guard at all: [3](#0-2) 

An unprivileged attacker who deploys and manages their own program can force multiple program-management instructions (`Close`, `DeployWithMaxDataLen`, `Close`) against the same program/programdata address to be processed within a single slot. Because these are executed back-to-back inside the same slot, the resulting cache entries share the same `deployment_slot`, which causes the binary search to hit the existing slot version (`Ok(index)`) instead of inserting a new one. This forces evaluation of the `match (&existing.program, &entry.program)` arm on the second `Close` (i.e. `Loaded => Closed`, or in a chained migration case `Closed => Closed`), neither of which is present in the whitelist, so control falls to the `_ => { ... return true; }` fallback. In a release build the `debug_assert!` is compiled out, `self.stats.replacements` is incremented as if a real replacement happened, and the function returns `true` (indicating success) — but `*existing` is never updated with the new `entry`. The cache therefore continues to hold the stale entry (e.g., the `Loaded` program) even though the last executed instruction was `Close`.

### Impact Explanation
This is a loader/cache-determinism defect: the on-chain effective state (last successful `Close`/`Deploy` instruction) diverges from what `ProgramCache` reports as loaded for subsequent lookups within the same slot/fork, and the divergence is silent in release builds (only visible via `debug_assert!` in debug/test builds), risking behavioral divergence between debug and release validator builds and stale/incorrect program resolution for later transactions referencing the same key in the same slot. This falls into Agave's loader/cache-correctness bounty category rather than memory safety or privilege escalation — it does not itself grant CPI privilege escalation or out-of-bounds memory access, but it undermines the invariant that the cache always reflects the last valid instruction outcome.

### Likelihood Explanation
Reachable by any unprivileged user who owns an upgradeable program: issue `Close` → `DeployWithMaxDataLen` (same programdata address) → `Close` as three separate transactions landing in the same slot (feasible since transactions from the same fee payer/program authority can be sequenced into one slot). No validator/leader control, no staked node, no special privileges required — this matches the documented same-slot transition scenarios explicitly called out in `program_cache_entry.rs` (`Closed => Closed (in the same slot)`), which the code comments themselves flag as an expected occurrence, confirming the pattern is a real, reachable operational sequence rather than a contrived edge case.

### Recommendation
Extend the whitelist match in `assign_program` to include all transitions documented in `program_cache_entry.rs`, specifically: `(Closed, Closed)`, `(Loaded(_), Closed)`, `(FailedVerification(_), Closed)`, and any other documented same-slot migration pairs (e.g. `(FailedVerification(_), FailedVerification(_))` with differing `account_owner`, `(Loaded(_), Loaded(_))` with differing `account_owner`). Ensure the fallback `_ => {}` arm truly represents an unreachable/invalid state (keep the `debug_assert!` but do not increment `replacements` or return `true` without actually updating `*existing` for cases that are legitimately reachable).

### Proof of Concept

2. Insert an initial entry via `assign_program(env, key, slot, Arc::new(ProgramCacheEntry { deployment_slot: 5, program: ProgramCacheEntryType::Loaded(...), account_owner, .. }))`.
3. Call `assign_program` again with a new entry having the **same** `deployment_slot = 5` and `account_owner`, but `program: ProgramCacheEntryType::Closed` (simulating the `Close` instruction landing in the same slot as the prior `Loaded` entry).
