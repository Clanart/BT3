### Title
`earned`/`allEarned` in vlMGPBaseRewarder/mWOMSVBaseRewarder overstate claimable rewards by ignoring expiry forfeit - ([File: rewards/vlMGPBaseRewarder.sol], [File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder.earned()`/`allEarned()` and their mirror functions in `mWOMSVBaseRewarder.sol` report a user's pending reward as the raw accrued amount, without deducting the expiry-based forfeit that is actually applied when the reward is paid out via `getReward`/`getRewards`. This mirrors the reported analog: a view function (`earned`) fails to account for a penalty (`_calExpireForfeit`) that a corresponding state-changing function (`_sendReward`) applies before transferring funds to the user.

### Finding Description
`earned()` computes the raw reward accrual with no forfeit deduction: [1](#0-0) 

`allEarned()` simply aggregates `earned()` across all reward tokens, inheriting the same omission: [2](#0-1) 

However, when the reward is actually paid out via `getReward`/`getRewards` → `_sendReward`, the contract computes and subtracts a forfeit amount based on the user's `getRewardablePercentWAD` (i.e., how much of their vlMGP/mWomSV is still fully locked vs. mid-cooldown): [3](#0-2) 

The same pattern exists in `mWOMSVBaseRewarder.sol`, which has an identical `earned()`/`allEarned()`/`_sendReward`/`_calExpireForfeit` structure: [4](#0-3) 

The `calExpireForfeit(address,address)` external view helper exists and correctly computes the forfeit amount, but it is a separate function that `earned()`/`allEarned()` do not call or subtract: [5](#0-4) 

This is a direct structural analog of the reported `View::queryAssetBalances` bug: the "preview" function (`earned`/`allEarned`) does not apply the penalty logic (`_calExpireForfeit`) that the actual claim path (`_sendReward`) applies before transferring funds, causing a value mismatch whenever a user has partially unlocked/cooling-down positions (`getRewardablePercentWAD(_account) < 100%`).

### Impact Explanation
Users, integrators, and off-chain frontends relying on `earned`/`allEarned` (e.g., `MagpieReader.sol`, `MagpieReaderArb.sol`, pool helpers) to display or compute expected claimable rewards will see an inflated figure that does not reflect the forfeit that is silently deducted and redirected into the reward pool (`_queueNewRewardsWithoutTransfer`) upon actual claim. This can mislead users into transactions/decisions based on incorrect expected yield, and any on-chain consumer that treats `earned()`/`allEarned()` as the true claimable amount (rather than calling `getReward` and checking realized balances) will be misled by more than the negligible dust threshold whenever forfeit applies. This does not constitute a direct theft, insolvency, or freeze by itself — the actual claim function still correctly deducts forfeit and routes it back into the reward pool for other stakers, so no funds are stolen or frozen; the discrepancy is confined to the view/read layer, consistent with the "Medium" (incorrect view value) classification of the original report.

### Likelihood Explanation
Any user with `getRewardablePercentWAD(_account) < 100%` (i.e., has ever started an unlock and is still mid-cooldown or force-unlocked) will trigger a non-zero forfeit whenever `_calExpireForfeit` is invoked on claim, guaranteeing the `earned()`/`allEarned()` value diverges from the actual amount received. This is a normal, expected, and common state for active lockers/stakers (no privileged action or attack required), making the discrepancy highly likely to occur in practice.

### Recommendation
Have `earned()` (and consequently `allEarned()`) subtract the forfeit that would be applied at claim time, using the existing `_calExpireForfeit`/`calExpireForfeit` logic, so the view function reflects the actual amount a user would receive if they called `getReward`/`getRewards` at that moment — mirroring the fix approach used for `View::queryAssetBalances` (apply the same penalty function used in the real withdrawal path to the view path).

### Proof of Concept
Not executed (index-only analysis); reasoning is based on direct code comparison of `earned()`/`allEarned()` versus `_sendReward()`/`_calExpireForfeit()` in `rewards/vlMGPBaseRewarder.sol` and `rewards/mWOMSVBaseRewarder.sol`, showing the view path omits the forfeit deduction applied on the actual claim path.

**File:** rewards/vlMGPBaseRewarder.sol (L363-400)

```text
    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userVlmgpShare) internal view returns (uint256) {
        return ((_userVlmgpShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**vlMGPDecimal) + userRewards[_rewardToken][_account];
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
