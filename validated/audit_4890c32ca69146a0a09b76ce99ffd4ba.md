## Title
Cross-chain calldata signature in `hyper-fungible-token` only binds `(nonce, runtime_call)`, letting anyone replay a captured beneficiary signature against an unrelated (or trivial) token transfer to force privileged call execution - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler lets an incoming cross-chain transfer carry optional `SubstrateCalldata` — a beneficiary-signed `runtime_call` that is dispatched as the beneficiary's origin once the tokens land. The signed payload is `(nonce, runtime_call)` only — it never includes the transferred `amount`, the source contract/state machine, or any commitment/message-specific value. This mirrors the reported staking-signature bug: a signature meant to authorize one specific client-side flow can be replayed through a completely different, unprivileged path because the signature doesn't bind to the context it was meant for.

### Finding Description
In `on_accept`, when `message.data` is non-empty, the pallet decodes `SubstrateCalldata { signature, runtime_call }` and verifies the signature over just `(nonce, runtime_call)`, where `nonce` is read live via `frame_system::Pallet::<T>::account_nonce(beneficiary)`: [1](#0-0) 

The `SubstrateCalldata` type's own doc comment confirms the scope of what is signed: [2](#0-1) 

Critically:
- The signature does **not** cover `message.amount`, `message.to`, `from` (source contract), or `source` (origin chain) — i.e., nothing that ties the authorization to the specific bridging event the beneficiary intended to gate the call on.
- `nonce` is only incremented after a successful dispatch: `frame_system::Pallet::<T>::inc_account_nonce(origin)` runs only after `runtime_call.dispatch(...)` succeeds. If dispatch fails for any reason, the function returns an error before incrementing, leaving the nonce — and therefore the signature — valid and reusable.
- `on_accept` is invoked once per distinct ISMP `PostRequest` commitment (ISMP's one-time receipt system prevents literal replay of the *same* request), but nothing stops a *different* `PostRequest` — carrying the identical captured `signature`/`runtime_call` bytes, and an arbitrary/trivial `amount` or different source contract mapped via `ContractToAsset` — from re-presenting that same signature as long as the beneficiary's nonce hasn't advanced.

Because the source-chain calldata (which embeds this signature) must be visible before/at submission (mempool, relayer logs, or a first attempt that reverts without touching the mint or the nonce), any unprivileged party who observes it can construct their own teleport (e.g. a dust-value transfer, or from a different registered asset/contract) targeting the same `beneficiary`, attach the observed `signature`+`runtime_call`, and force dispatch of that privileged call under conditions the beneficiary never signed off on.

### Impact Explanation
This allows unauthorized execution of an arbitrary runtime call as the beneficiary's origin, decoupled from the specific transfer amount/context the beneficiary intended to gate it on. Depending on `runtime_call`, this can be used to trigger sensitive beneficiary-authorized actions (transfers, staking, governance votes, etc.) prematurely, with the wrong amount context, or repeatedly attempted by third parties, and it also lets an attacker grief the legitimate flow (a failed dispatch burns the intended one-time authorization opportunity's timing without consuming the nonce, but the legitimate teleport can still land later — the more direct harm is unauthorized/decoupled execution of the call). This matches the "unauthorized execution" / "transaction manipulation" impact class.

### Likelihood Explanation
Requires only that the client-side signed calldata used for one honest teleport becomes visible to a third party (mempool visibility, or any relayer/observer) before it lands — a realistic condition for any cross-chain flow relying on public relaying, and does not require a malicious relayer, prover, or governance actor; any holder of a valid asset/contract mapping can initiate the replaying teleport themselves.

### Recommendation
Bind the signed payload to the specific bridging context: include `message.amount`, `message.to`, `source`, and ideally the request commitment/hash in the signed struct, and/or invalidate the signature immediately after first use regardless of dispatch outcome (e.g., increment the nonce, or track a consumed-signature/commitment set, before attempting `dispatch`, rolling back the nonce increment only if the whole message processing must be aborted for unrelated reasons).

### Proof of Concept
1. Beneficiary signs `(nonce=N, runtime_call=X)` for an app that plans to teleport 1000 USDC and then execute `X` (e.g., `stake(1000)`).
2. Attacker observes this `signature`/`runtime_call` bytes before/while the legitimate teleport transaction propagates (mempool, relayer telemetry, or a same-block race).
3. Attacker submits their own teleport from any registered `ContractToAsset` source, `to = beneficiary`, `amount = 1` (or any different asset), `data = SubstrateCalldata { signature, runtime_call: X }`.
4. Since `frame_system::Pallet::<T>::account_nonce(beneficiary)` is still `N`, verification in `on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:124-172`) succeeds, and `X` dispatches as `beneficiary`'s origin — decoupled from the 1000 USDC context it was meant to be gated on.
