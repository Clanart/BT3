## Finding: Permanent Loss of Unclaimed Rewards on Delayed First Stake

The reported `AbstractRewarder` bug class (reward-per-token accounting failing to correctly track periods without stakers) has a genuine analog in this codebase's `WomUp` contract, though it manifests as permanent freezing of yield rather than unfair distribution to the first staker.

### Title
Permanent Freezing of Queued MGP Rewards When `WomUp.stake()` Is First Called After Reward Program Start - (File: wombat/WomUp.sol)

### Summary
`WomUp` implements a Synthetix-style staking rewards accounting scheme identical in structure to the reported `AbstractRewarder` bug. Unlike the vulnerable pattern, `WomUp`'s `updateReward` modifier unconditionally advances `lastUpdateTime` regardless of whether `totalSupply()` is zero, which avoids the "first staker steals everything" variant but introduces a different critical flaw: any reward accrued while `totalSupply() == 0` is permanently skipped and can never be claimed by anyone, nor recovered by the admin.

### Finding Description
`initializeRewards()` starts the reward period and funds `rewardRate` based on the MGP balance already in the contract, setting `lastUpdateTime = block.timestamp` and `periodFinish = block.timestamp + duration`: [1](#0-0) 

The `updateReward` modifier recalculates `rewardPerTokenStored` and then **always** resyncs `lastUpdateTime`, even when no one is staked yet: [2](#0-1) 

`rewardPerToken()` returns the stored value unchanged whenever `totalSupply() == 0`, meaning no rewards accrue for that period: [3](#0-2) 

Because `stake()` is wrapped by `updateReward(msg.sender)`, the very first `stake()` call after the reward program starts (or after `_totalSupply` returns to zero, e.g. after all withdraw) advances `lastUpdateTime` to the current timestamp without crediting the elapsed `rewardRate * timeElapsed` amount to anyone: [4](#0-3) 

The tokens corresponding to that skipped interval remain in the `WomUp` contract (already transferred in via `initializeRewards`), but are never reflected in `rewardPerTokenStored`, so no user's `earned()` calculation will ever include them.

### Impact Explanation
The MGP tokens funding the skipped interval become permanently stuck in the contract. Unlike `BaseRewardPool._provisionReward()` elsewhere in this codebase, which explicitly diverts rewards accrued during zero-supply periods into `queuedRewards` to be redistributed later: [5](#0-4) 

`WomUp` has no such queuing mechanism. Once `rewardRate > 0`, `rescueReward()` is permanently disabled (it requires `rewardRate == 0`), so the owner cannot recover the stuck portion either: [6](#0-5) 

This results in a permanent freeze of unclaimed yield — funds that are neither claimable by stakers nor recoverable by governance.

### Likelihood Explanation
This requires no attacker action or malicious admin behavior — it is triggered by ordinary, expected protocol operation: the admin calls `initializeRewards()` to start a 7-day reward program (`duration = 7 days`), and any delay before the first ordinary user calls `stake()` (a normal unprivileged action) causes that delay's worth of rewards to be permanently lost. Given the reward duration is a full week, even modest onboarding delays easily exceed a day, satisfying a permanent (well beyond 24-hour) freeze of funds.

### Recommendation
Mirror the `BaseRewardPool` remediation: in `updateReward`/`rewardPerToken`, do not advance `lastUpdateTime` past the last moment `totalSupply()` was non-zero, or accumulate the reward attributable to zero-supply intervals into a `queuedRewards`-style bucket that gets folded into `rewardPerTokenStored` once a nonzero `totalSupply` exists.

### Proof of Concept
1. Owner deposits MGP and calls `initializeRewards()`, setting `lastUpdateTime = T0`, `rewardRate = R`, `periodFinish = T0 + 7 days`, with `_totalSupply == 0`.
2. No one stakes for `X` seconds (`X` up to and beyond 1 day).
3. At `T0 + X`, a user calls `stake()`. `updateReward` runs: `rewardPerTokenStored = rewardPerToken()` returns unchanged value (since `totalSupply()==0` prior to state update), then `lastUpdateTime = lastTimeRewardApplicable() = T0 + X`.
4. `X * R` MGP tokens, already resident in the contract from step 1, are now permanently excluded from all future `rewardPerToken()` calculations — no staker will ever earn them, and `rescueReward()` is blocked since `rewardRate > 0`. [7](#0-6)

    function initializeRewards() external onlyOwner returns (bool) {
        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();

        rewardRate = rewardsAvailable / (duration);

        lastUpdateTime = block.timestamp;
        periodFinish = block.timestamp + (duration);

        emit RewardAdded(rewardsAvailable);

        return true;
