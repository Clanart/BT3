### Title
Recycled `CachedPreprocesses` context reuses FROST nonces across distinct signing executions, enabling private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The bug class in CVE-2019-3844 is *identifier recycling*: a transient identifier (GID) is reused and a later, different principal inherits ownership/privileges bound to it. In Serai, `SigningProtocol::preprocess_internal` caches a FROST preprocess seed in the DB under the key `CachedPreprocesses[context]`, where `context` is only `(b"DkgConfirmer", attempt)`. That context identifier is recycled for every signing action of the attempt — `preprocess()`, `share()`, and `complete()` — while the actual inputs to `sign()` (the peers' preprocess map and the message `set_keys_message(...)`) are *not* part of the context. Two executions under the same recycled context derive identical nonces via `ChaCha20Rng::from_seed` but sign under different binding factors/challenge, which is textbook FROST/Schnorr nonce reuse and yields the validator's MuSig private key.

### Finding Description

`preprocess_internal` (lines 100-148) loads or creates `CachedPreprocesses::get(txn, &self.context)` and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`. `from_cache` → `seeded_preprocess` (crypto/frost/src/sign.rs:121-144) deterministically regenerates the same `nonces` and `commitments` from the same 32-byte seed.

`share_internal` (lines 150-181) then calls `machine.sign(preprocesses, msg)`, where:

- `preprocesses` is built from caller-supplied bytes parsed by `machine.read_preprocess` — the externally-supplied `serialized_preprocesses` map (read_preprocess is untrusted-input surface).
- `msg` is `set_keys_message(set, removed, key_pair)` where `key_pair` is supplied per-call (line 296-300).

`DkgConfirmer::complete` (lines 312-327) unconditionally calls `self.share_internal(preprocesses, key_pair)` *again*, re-deriving the same machine and calling `sign` a second time under the same recycled context. There is no record binding the context to a specific preprocess set or message — the DB stores only `context -> seed`, and no "share already produced for context X with inputs Y" check exists. The file's own header (lines 25-55) acknowledges safety depends on nonces never being reused against distinct received commitments/messages, and leaves a TODO noting the commitments are not yet verified to match the presumed preprocess before publishing shares (line 51).

Per the FROST share equation in crypto/frost, the signature share is `z_i = d_i + e_i·rho_i + lambda_i·s_i·c` where `rho_i` is the per-participant binding factor over the commitment set and `c` the challenge over the message. If `sign` runs twice with the same `(d_i, e_i)` but a different preprocess map (different `rho_i`) or a different `key_pair` (different `c`), two shares `z`, `z'` let an observer solve for `s_i`, the private key share.

The only guards are the BFT-ordering assumptions documented in the header — nothing in the code enforces that the two `sign` invocations see identical inputs; the recycled context silently reissues the same nonce to whatever inputs arrive next.

### Impact Explanation

Reuse of FROST nonces across two `sign` calls with different preprocess sets or different `key_pair` leaks the validator's MuSig secret key share (i.e., the validator's root-of-trust key on Substrate). With the share recovered, an attacker can forge `set_keys` signatures from that validator: the MuSig aggregation produces signatures weighted over the validator set, so a compromised validator share contributes toward confirming attacker-chosen `key_pair`s — i.e., installing attacker-controlled multisig keys, which controls all funds bridged to that multisig. Severity: High (key share recovery, a listed acceptance criterion).

### Likelihood Explanation

Two `sign` executions under one `(b"DkgConfirmer", attempt)` context occur whenever `share()`/`complete()` are invoked more than once, which is the normal flow (share during confirmation handling, then `complete` re-executes `share_internal`). Distinctness of inputs requires the second call's `preprocesses` map or `key_pair` to differ — the preprocess map is assembled from other validators' finalized preprocess transactions, and the map fed to `complete` is re-derived from the shares' participant set via `threshold_i_map_to_keys_and_musig_i_map`, so any difference between the set of signers processed at `share` time versus `complete` time (e.g., an additional validator's confirmation transaction being included, or a different subset mapping) produces shares over a different commitment set with identical nonces. It does not require the attacker to hold a validator key — only that distinct preprocess sets/messages are processed under one attempt context, which the code neither prevents nor detects. Likelihood is bounded by BFT finality assumptions and is therefore rated moderate rather than certain.

### Recommendation

- Bind the cached preprocess to the full signing session: include a hash of the finalized preprocess set and `msg` (or `key_pair`) in the `CachedPreprocesses` key, or store alongside the seed a commitment to the inputs used at first `sign` and refuse (panic) if a subsequent `sign` under the same context presents different inputs.
- Implement the header's TODO: before publishing a share, verify the locally regenerated commitments equal the preprocess already published/finalized on-chain for this context.
- Have `complete` reuse the already-computed share/signature machine rather than re-executing `share_internal`, or record that a share was already emitted for the context and make `complete` a pure aggregation of shares.

### Proof of Concept

Conceptual (requires coordinator-level execution):

1. During attempt `a`, the coordinator runs `DkgConfirmer::share(preprocesses_A, key_pair)` with preprocess set A from validators {1..t}. `preprocess_internal` stores seed `s` under `CachedPreprocesses[(b"DkgConfirmer", a)]`, derives nonces `(d, e)`, and publishes share `z_A = d + e·rho_A + λ·s_i·c_A`.
2. Later, `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` runs where `preprocesses_B` contains a different participant subset (a different set of confirmation transactions was finalized/processed). `share_internal` reloads seed `s` → identical `(d, e)` → `machine.sign(preprocesses_B, msg)` yields `z_B = d + e·rho_B + λ·s_i·c_A` with `rho_B ≠ rho_A`.
3. Both `z_A` and `z_B` are broadcast. Solve the 2×2 linear system in `(d, e)`, then recover `s_i = (z_A - d - e·rho_A)/(λ·c_A)` — the validator's private MuSig share.
4. Use `s_i` to sign `set_keys_message` for an attacker-chosen `KeyPair`, contributing a forged share toward the threshold needed to install a malicious multisig key.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
