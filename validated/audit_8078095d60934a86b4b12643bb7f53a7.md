Based on my investigation, I found a plausible analog in Kaia's `kaiax/gasless` module (KIP-247 gasless transactions), which relies on a spot-price read from an AMM pool to validate transactions at mempool-admission time, while actual settlement happens later — the same "manipulate the balance/price input used for a financial calculation" bug class as the Surge `tokenToShares` donation attack.

### Title
Gasless swap admission relies on manipulable AMM reserves ("GetAmountIn"), enabling price-griefing of block-proposer-funded lend transactions - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
`GaslessModule.checkBalanceForSwap` validates a `GaslessSwapTx` at transaction-pool admission time by reading the *live* DEX exchange rate via `GaslessSwapRouter.GetAmountIn(token, minAmountOut)`, which is itself derived from the underlying Uniswap-V2-style pair's reserves (populated from `balanceOf(address(this))`) [1](#0-0) [2](#0-1) . Because the pair's reserves can be pushed by any unprivileged account (direct token donation plus the pair's public `sync()`, or ordinary swaps), an attacker can shift the effective price between the moment a `GaslessSwapTx` is admitted/validated and the moment it is actually executed in a block.

### Finding Description
The gasless flow works as follows:
- A user signs a `GaslessSwapTx` with fixed `amountIn`, `minAmountOut`, and `amountRepay` values [3](#0-2) .
- The tx pool calls the gasless module's balance-check hook instead of the standard native-balance check for gasless transactions [4](#0-3) .
- `checkBalanceForSwap` re-derives the "required" `amountIn` from the router's `getAmountIn`, which reflects the *current* AMM reserves at admission time, and only rejects the tx if the user-declared `amountIn` is insufficient relative to that snapshot [5](#0-4) .
- The actual settlement (the on-chain `swapForGas` call) occurs later, when the transaction is bundled by the block builder together with a proposer-funded `LendTxGenerator` and, optionally, a preceding `GaslessApproveTx` [6](#0-5) , and can sit in `pending`/`queue` for up to `PendingTimeout`/`QueueTimeout` (10s each) before inclusion [7](#0-6) .

Because the price check at admission and the price at actual execution are two different reads of the same externally-manipulable AMM state, any unprivileged holder of the target token can:
1. Observe a pending `GaslessSwapTx` (or its parameters) in the mempool.
2. Directly transfer tokens into the corresponding Uniswap-style pair and trigger a reserve update (`sync()`) or perform a counter-swap, shifting the effective exchange rate.
3. Cause the previously-signed, fixed `amountIn`/`minAmountOut` combination to become unprofitable/unmeetable by execution time, so the on-chain `swapForGas` call reverts on its own slippage protection.

This is structurally identical to the Surge `Pool.sol` issue: a value that gates an important accounting decision (`tokenToShares`, here `getAmountIn`) is derived from a balance/reserve that any external account can move by direct token transfer, independent of the "normal" deposit/swap entrypoint, letting an attacker retroactively invalidate another user's already-validated calculation.

### Impact Explanation
The `LendTxGenerator` prepends a proposer-funded gas grant ahead of the `GaslessApproveTx`/`GaslessSwapTx` in the bundle so the user can execute without holding native KAIA [8](#0-7) . If the subsequent `swapForGas` reverts because the manipulated reserves no longer satisfy the fixed `minAmountOut`, the user does not repay the lent gas as originally planned. Whether the proposer's lend transaction is rolled back atomically with a failing swap, or the lend succeeds independently while the swap reverts (in which case the proposer/network absorbs the lent-gas loss), depends on the bundle atomicity semantics in `work/builder`, which I was **not able to fully verify** in this pass — I could not confirm whether `builder.Bundle` guarantees all-or-nothing execution for `[LendTxGenerator, GaslessApproveTx/GaslessSwapTx]` sequences. This is the key open question that determines whether the impact is:
- **High**: proposer/block-reward loses lent gas value with no repayment (a concrete value-transfer / fee-delegation abuse), or
- **Medium/Low**: only a denial-of-service on the specific gasless bundle (wasted mempool slot / repeated rejection cycles), if the bundle is atomic and lend gas is clawed back automatically.

### Likelihood Explanation
Likelihood is high for the DoS variant: manipulating a public AMM pair's reserves via ordinary transfers/swaps is a normal, permissionless, single-transaction action requiring no special privilege, and is directly analogous to the donation-based griefing pattern in the source report. The scenario does not require compromising validators, the network, or any protocol-internal secret — only ordinary token holdings and a public RPC/transaction submission, matching the allowed threat model (unprivileged transaction sender / public-RPC caller).

### Recommendation
- Re-validate the AMM-derived `amountIn`/`minAmountOut` relationship at the moment of inclusion in a block (i.e., inside block-building/execution, not only at mempool admission), or use a bounded staleness window plus a TWAP/oracle-based price rather than instantaneous reserves for the mempool-level check.
- Confirm and, if necessary, enforce true atomicity for `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` bundles so that a reverting `swapForGas` never leaves an unrepaid lend transaction committed on-chain.
- Consider rejecting/re-checking gasless bundles whose admission-time price snapshot is older than a short threshold, to shrink the window an attacker has to manipulate reserves between admission and execution.

### Proof of Concept
Conceptual sequence (exact PoC code could not be constructed without the `GaslessSwapRouter.sol`/pair source, which was not present in the indexed repo content):
1. Attacker observes a pending `GaslessSwapTx` for `token X` with fixed `amountIn=A`, `minAmountOut=M`, `amountRepay=R` in the mempool, admitted successfully because at time T0 `getAmountIn(X, M) <= A` [1](#0-0) .
2. Attacker sends a plain ERC-20 `transfer` of token X (or WKAIA) directly to the Uniswap-style pair backing `dexAddress(X)` [9](#0-8) , then calls the pair's public `sync()`/or performs a small swap, shifting `getReserves()` used by `getAmountIn`.
3. At block-inclusion time T1, the bundle executes `swapForGas(X, A, M, R, deadline)`; because reserves moved, the effective output for `A` is now `< M`, causing the swap to revert per its own slippage check.
4. Depending on bundle atomicity (unverified), the proposer's already-lent gas for this bundle is either reclaimed (DoS-only) or left unrepaid (value loss) — this distinction needs confirmation from `work/builder` bundle-execution semantics before assigning final severity, but the underlying manipulable-price root cause and unprivileged reachability are established.

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}

Gasless transaction (GaslessTx) consists of two types: gasless approve transaction (GaslessApproveTX), and gasless swap transaction (GaslessSwapTx).

Note that gasless transaction does not mean the gas prices of gasless transactions are zero, but it means that proposer will lend the user with gas fee and user will pay back during gasless swap.

The gas fee of gasless transaction's is funded by block proposer (i.e., lend transaction generated by `GetLendTxGenerator`), and user repays the lent amount during gasless swap.
