### Title
SignableTransaction underestimates weight/fee by omitting the OP_RETURN output, silently violating the caller-specified `fee_per_vbyte` bound — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a caller-specified `fee_per_vbyte` — a protective bound the transaction's fee rate must satisfy — plus optional `data` for an OP_RETURN output. The weight/vbyte estimation (`calculate_weight_vbytes`) is called with only `payments` and `change`; the OP_RETURN output is appended to `tx_outs` before the estimation but is never passed into the estimator. The resulting transaction is larger than estimated, so the actual fee rate is silently lower than the bound the caller requested — the same class as the referenced bug: a user-supplied protective value (`amount_out_min` / `fee_per_vbyte`) is weakened by the library rather than honored.

### Finding Description
In `send.rs`, the OP_RETURN output is pushed at line ~195, then:

```rust
// networks/bitcoin/src/wallet/send.rs
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

`calculate_weight_vbytes` builds a template `Transaction` whose outputs are derived solely from `payments` (plus optional `change`) — the `data` output is not included anywhere:

```rust
output: payments.iter().map(|payment| TxOut { ... }).collect(),
```

Consequences:
1. `needed_fee` is computed over a `vbytes` that omits the OP_RETURN output (~10–90+ vbytes for marker/flag/pushdata/data).
2. The `TooLowFee` check is evaluated against this understated size, so a transaction whose *real* feerate is below `DEFAULT_MIN_RELAY_TX_FEE` passes the check.
3. The change computation (`input_sat - payment_sat - fee_with_change`) likewise uses the understated `fee_with_change`, so `change` is over-credited: `fee()` (actual = `sum(inputs) - sum(outputs)`) ends up *less* than the true required `fee_per_vbyte * actual_vbytes`, and the change output absorbs sats that should have been fee.

Attackers/users who call `SignableTransaction::new` with `data` and a minimal `fee_per_vbyte` receive a signed transaction whose real feerate is below both the requested rate and potentially the network minimum relay feerate.

### Impact Explanation
A transaction produced with a caller-specified fee bound will not actually satisfy that bound once broadcast. If the true feerate falls under `DEFAULT_MIN_RELAY_TX_FEE`, the transaction is rejected by relay policy and the funds (including the oversized change output) are locked until a replacement/CPFP is constructed — the wallet API gives no indication this happened since `needed_fee()` reports the compliant-looking underestimated value. More generally, the discrepancy means the signed transaction commits the threshold key's signature to a fee/change distribution different from what the caller authorized: change is inflated and feerate is diluted by an attacker-influenced `data` length.

### Likelihood Explanation
Deterministic whenever `data: Some(..)` is provided to `SignableTransaction::new` — the OP_RETURN output's size is always missing from the estimate. Severity of the outcome scales with data length and with how close the requested `fee_per_vbyte` is to the relay minimum; at `fee_per_vbyte == 1` a large `data` payload reliably pushes the true feerate below relay policy. The data field is attacker-reachable in deployments where external users attach refund/metadata instructions to payments.

### Recommendation
Include the OP_RETURN output in the size estimate. Two clean options:
- Pass the already-constructed `tx_outs` (payments + OP_RETURN + optional change) into `calculate_weight_vbytes` instead of rebuilding outputs from `payments`, so the template matches the real transaction exactly; or
- Add a `data_len`/`extra_outputs` parameter to the estimator and account for the OP_RETURN script's serialized size (opcodes + pushdata length prefix + payload).

Also re-verify `fee()` against `fee_per_vbyte * actual_vbytes` post-construction (e.g., `debug_assert!`) so any future output added to `tx_outs` cannot silently diverge from the estimate again.

### Proof of Concept
```rust
// Construct a single-input spend paying to `payment_script` with a large OP_RETURN.
let data = vec![0u8; 80]; // max standard OP_RETURN payload
let fee_per_vbyte = 1u64;

let stx = SignableTransaction::new(
  vec![input],                     // e.g. 50_000 sat input
  &[(payment_script, 10_000)],     // one payment
  Some(change_script),
  Some(data.clone()),
  fee_per_vbyte,
).unwrap();

// The estimator omitted the ~82+ byte OP_RETURN output from `vbytes`,
// so needed_fee = 1 * vbytes_underestimated.
let reported = stx.needed_fee();

// Actual transaction includes the OP_RETURN output:
let actual_vbytes = stx.transaction().vsize() as u64;
let actual_fee = stx.fee();

// The real feerate is below the requested bound — and can be < 1 sat/vbyte,
// below DEFAULT_MIN_RELAY_TX_FEE, despite the TooLowFee check having passed:
assert!(actual_fee < fee_per_vbyte * actual_vbytes);
```
