## Title
Stale line-index based diff selection can cause unintended content to be silently committed or discarded when working-directory file content changes between diff load and action - (`File: app/src/lib/stores/app-store.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The reported Blueberry Staking bug is a case of an index/length being derived from the wrong data source, so downstream indexed operations act on the wrong elements. The closest reachable Desktop analog is in the changes/diff pipeline: partial line selections (`DiffSelection`) are keyed purely by **absolute line index** within a diff, and when the diff is reloaded after the underlying file changes, Desktop does not verify that a previously-selected line still corresponds to the same content — it only checks that the same *index* still exists and is "includeable". If a file's content shifts underneath an existing partial selection (same or greater line count, different content), the stale index-based selection is silently reapplied to the new content when generating the commit or discard patch, corrupting what is actually committed/discarded without the user's knowledge.

### Finding Description
`selectWorkingDirectoryFiles`/`updateChangesWorkingDirectoryDiff` reloads the diff for the selected file and attempts to preserve the user's partial line selection by recomputing only which absolute indices are still "selectable": [1](#0-0) 

The comment explicitly acknowledges the gap: *"The diff might have changed dramatically since last we loaded it... we'll settle on just updating the selectable lines such that any previously selected line which now no longer exists or has been turned into a context line isn't still selected."* This only guards against index-out-of-range/type-mismatch; it does not validate that the *content* at that index is the same content the user intended to select.

Downstream, `formatPatch` and `formatPatchToDiscardChanges` build the commit/discard patch purely from `hunk.unifiedDiffStart + lineIndex` compared against `file.selection.isSelected(absoluteIndex)`: [2](#0-1) [3](#0-2) 

There is no cross-check that the line text at `absoluteIndex` matches what was displayed/selected by the user originally. If the working tree file is modified by an external actor (e.g. a git hook shipped in a cloned/fetched malicious repository, such as `post-checkout`/`post-merge`/`post-commit`, or a background process racing with the UI) between the moment the diff is rendered and the moment the user clicks "Commit" or "Discard changes", the selection bitmap silently applies to different underlying content while line counts/positions coincidentally line up.

### Impact Explanation
This breaks the fundamental integrity invariant Desktop relies on: what the user visually reviewed and selected in the diff view is what gets committed or reverted. Silent corruption of what a user commits or pushes is explicitly listed as valid impact. An attacker who controls a cloned/fetched repository (through a git hook) can cause a victim's partial selection to be reapplied against attacker-controlled replacement content, resulting in unintended (attacker-influenced) content entering a commit, or unintended content silently discarded from the working directory, without any error being surfaced.

### Likelihood Explanation
Requires the diff to be reloaded (which Desktop already does automatically on file-system changes and background status refreshes) between selection and action, and a hook or process capable of mutating the tracked file with same-or-compatible line geometry. This is a git-hook-triggerable, no-additional-user-interaction scenario reachable purely from a cloned/fetched repository — matching the required attacker model — though it depends on git hooks being enabled/executed by Desktop's git operations and on the file mutation preserving enough structure to keep the stale index "includeable".

### Recommendation
Validate selection state against line **content**, not just index/type, when a diff is reloaded — e.g., hash or compare the line text at each previously-selected index and drop the selection (or force full reselection with a warning) if content differs. Alternatively, invalidate all partial selections whenever the underlying diff's line content at any selected index has changed, rather than only when the index becomes out of range or non-includeable.

### Proof of Concept
1. Clone a malicious repository containing a `post-checkout` (or similar) hook.
2. Modify `foo.txt` locally so it has a partial diff; select some but not all changed lines in Desktop's diff view.
3. Trigger a background repository refresh (e.g., switch branches and back, or wait for periodic status refresh) that invokes the malicious hook, which rewrites `foo.txt` with different content but the same number of changed lines at the same positions.
4. `updateChangesWorkingDirectoryDiff` reloads the diff, keeps the same `selectedFileIDs`, and reapplies the old absolute-index selection set via `withSelectableLines` since indices are still "includeable".
5. Click "Commit" — `formatPatch` builds the patch using the stale index-based selection against the new hunk content, silently including attacker-modified lines the user never reviewed or intended to select. [4](#0-3)
