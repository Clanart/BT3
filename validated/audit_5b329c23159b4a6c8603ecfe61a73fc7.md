### Title
`ReceivedOutput::read` trusts a claimed scalar offset, letting forged bytes report unspendable outputs as owned by the group key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Gitcoin finding concerns a factory accepting an unvalidated `ownedBy` parameter, letting anyone register objects that appear legitimately owned by a program. Serai's analog lives in `ReceivedOutput`, the wallet-level record of "an output owned by our key": its `offset` field claims "this output is spendable by `key + offset*G`," and `ReceivedOutput::read` deserializes that claim from raw bytes with zero validation. A forged `ReceivedOutput` can therefore claim ownership of (i.e., an offset for) an arbitrary `TxOut`/`OutPoint`, and downstream spend logic will treat it as a spendable input owned by the group.

### Finding Description
`ReceivedOutput` couples an output with the scalar offset needed to spend it under the scanner's key [1](#0-0) . The only legitimate constructor is `Scanner::scan_transaction`, which produces the offset by looking up `output.script_pubkey` in the registered script map, guaranteeing `p2tr_script_buf(key + G*offset) == output.script_pubkey` [2](#0-1) . However, `ReceivedOutput::read` reconstructs the struct directly from untrusted bytes — reading `offset` via `Secp256k1::read_F`, then a `TxOut` and `OutPoint` — and never verifies that the claimed offset actually derives the output's script [3](#0-2) . The struct's fields are private and `serialize`/`read` round-trip freely, so a forged buffer is indistinguishable from a scanner-produced output [4](#0-3) . This mirrors `RoundFactory.create` accepting `ownedBy` verbatim: the "ownership" relation between the offset and the output is asserted, never proven.

### Impact Explanation
Any component that consumes a `ReceivedOutput` — e.g., `SignableTransaction` construction, which re-keys the signing view per input via the claimed offset — will believe the referenced outpoint is spendable by the multisig when it is not. An attacker who can feed bytes to `ReceivedOutput::read` can fabricate deposits: outputs that the group reports as received but cannot actually spend (wrong offset ⇒ wrong signing key ⇒ the BIP-340 signature does not satisfy the output's script). This produces funds counted as available balance yet permanently unspendable, the exact "funds reported received that are not spendable" consequence, and can also be used to attribute arbitrary on-chain outputs to the group key — the illegitimate-round analog.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read` (an explicitly in-scope untrusted sink). No secret, collusion, or validator misbehavior is needed — the byte stream fully determines `offset`, `TxOut`, and `OutPoint`. The bug is a missing-consistency-check issue: cheap to trigger (one crafted serialization), though the blast radius depends on the integrator piping untrusted `ReceivedOutput` blobs into spend-planning code. Medium severity.

### Recommendation
Make the ownership relation verifiable instead of trusting the serialized claim:
- Change the read path to take the scanner's base `key` (or move deserialization behind `Scanner`), and after decoding check `p2tr_script_buf(key + C::generator() * offset) == Some(output.script_pubkey)`, rejecting mismatched inputs.
- Alternatively store `ReceivedOutput`s keyed by `OutPoint` as produced by `scan_transaction` only, treating `read`/`serialize` purely as trusted persistence, and documenting that `read` must never be exposed to untrusted input.

### Proof of Concept
```
// Ristretto/Secp256k1 context; key is the group's even Taproot key.
let scanner = Scanner::new(key).unwrap();

// Attacker picks any real on-chain output paying to someone else's script
// and any scalar they like.
let forged_offset = Scalar::random(rng);
let foreign_txout: TxOut = /* arbitrary TxOut with an unrelated script_pubkey */;
let foreign_outpoint: OutPoint = /* arbitrary OutPoint */;

// Manually build the wire format of ReceivedOutput::write
let mut buf = vec![];
buf.extend(forged_offset.to_bytes().as_ref());
buf.extend(serialize(&foreign_txout));
buf.extend(serialize(&foreign_outpoint));

// Deserialization succeeds despite offset/script mismatch:
let out = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// `out` is now indistinguishable from a scanner output:
// SignableTransaction::new(vec![out], ...) will try to spend `foreign_outpoint`
// under key + forged_offset*G, which cannot satisfy foreign_txout.script_pubkey.
// The outpoint is tallied as received funds yet is unspendable.
```
The absence of any `p2tr_script_buf`/`key` check in `ReceivedOutput::read` (lines 122–134 of `networks/bitcoin/src/wallet/mod.rs`) is the root cause: the claimed offset is the unvalidated `ownedBy`.

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
