### Title
Stale GitHub repository identity re-bound to a name-squatted repo silently rewrites the local git remote - ([File: app/src/lib/stores/updates/update-remote-url.ts](), [File: app/src/lib/stores/app-store.ts](), [File: app/src/lib/stores/repositories-store.ts]())

### Summary
GitHub Desktop periodically "refreshes" the GitHub metadata for a repository by looking the repo up on the API using the **owner login + repo name** parsed from the local git remote, not GitHub's immutable numeric repository id. The result is merged into the locally cached `GitHubRepository` record keyed by `[ownerID+name]`, and that fresh data (including the API's `clone_url`) is then used to silently rewrite the user's git remote URL. If the original owner/name pair is deleted and re-created (owner username squatting or repo re-creation with the same name — a well known "repo/owner reuse" scenario on GitHub), Desktop will attach the new, attacker-controlled repository's identity to the existing local record and can auto-update the user's remote to point at it, exactly analogous to the Lens `_profileIdByHandleHash` bug where a mutable human-readable identifier (`handle`/`login+name`) was treated as if it were a stable identity.

### Finding Description
`matchGitHubRepository` derives the `owner`/`name` pair purely by string-parsing the configured git remote URL: [1](#0-0) 

`repositoryWithRefreshedGitHubRepository` uses that owner/name pair to call `api.fetchRepository(owner, name)` and then persists whatever comes back: [2](#0-1) 

The persistence layer, `_upsertGitHubRepository`, looks up (and overwrites) the existing local `GitHubRepository` record by the compound key `[ownerID+name]` — `ownerID` itself being resolved from the case-insensitive `login` string via `putOwner`, not a stable GitHub numeric owner id: [3](#0-2) [4](#0-3) 

The database schema itself documents this identity choice: `gitHubRepositories: '++id, name, &[ownerID+name]'`, i.e. uniqueness is enforced on owner+name, not on the GitHub API's own repository id: [5](#0-4) 

Crucially, before that upsert, `updateRemoteUrl` is invoked with the *stale* local `gitHubRepository.cloneURL` and the *freshly fetched* `apiRepo.clone_url`. If the fetched clone URL differs from what's cached (which it will if the name/owner was reassigned to a different underlying repository) and the local remote still matches the old cached clone URL, Desktop calls `gitStore.setRemoteURL(...)` and rewrites the user's `origin` remote automatically, with no prompt: [6](#0-5) 

This mirrors the Lens finding precisely: the code checks "does a record exist for this name" (`_profileIdByHandleHash[...] == 0` / `db.gitHubRepositories.where('[ownerID+name]')...`) instead of "does this record still refer to the same underlying entity I originally bound to" (`profileIdByHandleHash == profileIds[i]` / GitHub's immutable repository `id`). Existing guards (`urlMatchesRemote`, `protocolsMatch`, `remoteUrlUnchanged` checks in `updateRemoteUrl`) only validate URL *shape* consistency; none of them validate that the API repository object returned actually corresponds to the same underlying GitHub repository the user originally added, because that check would require comparing GitHub's numeric repository id — which is never stored or compared anywhere in this path.

### Impact Explanation
An attacker who can cause a GitHub owner/name pair previously used by a legitimate repository to resolve to attacker-controlled content (e.g., through owner-username reuse after account rename/deletion, or an org repository being deleted and recreated with the same name by a different/compromised actor — both are real, previously documented GitHub "repo-jacking" primitives) can get Desktop to:
- Silently associate the victim's locally tracked repository record (same local `dbID`, so all UI, PR fetching via `PullRequestCoordinator`, and permission checks continue operating "as before") with the attacker's GitHub repository metadata.
- Automatically rewrite the user's `origin` git remote URL to the attacker's clone URL via `updateRemoteUrl` → `gitStore.setRemoteURL`, with no user confirmation.

Once the remote is silently repointed, subsequent fetches/pulls the user performs from within Desktop pull attacker-controlled history/refs into the local repository, and subsequent pushes go to the attacker's repository — corrupting what the user commits/pushes and exfiltrating what they push, matching the "silent corruption of what the user commits or pushes" and "attacker controls a git remote" impact classes.

### Likelihood Explanation
This requires an attacker to control a repository reachable under the exact owner-login+name string a victim previously used (via username/repo-name reuse after deletion), and for the victim's Desktop background refresh (`repositoryWithRefreshedGitHubRepository`, triggered periodically/on repository load) to run while the remote URL still matches the old cached `cloneURL`. This is a realistic but not trivial attacker setup — it depends on GitHub allowing the reused login/name to be re-registered and on timing the recreation before the user notices anything wrong, similar in spirit to known repojacking attacks against dependency tooling.

### Recommendation
Bind the locally cached `GitHubRepository` record and any remote-URL auto-update logic to GitHub's immutable numeric repository `id` returned by the API, not to the mutable `owner login + name` pair:
- Store and index `gitHubRepositories` by the API's numeric repo id (in addition to/instead of `[ownerID+name]`).
- In `_upsertGitHubRepository`/`repositoryWithRefreshedGitHubRepository`, verify that `apiRepo.id` (once available) matches the previously cached repository's known id before merging fresh data or rewriting the remote URL; if it doesn't match, treat it as a different repository and require explicit user confirmation instead of silently updating.
- In `updateRemoteUrl`, refuse to auto-rewrite the remote when there is any indication the underlying repository identity changed (e.g., mismatched id), rather than relying solely on clone-URL string comparisons.

### Proof of Concept
1. Victim clones `https://github.com/OwnerA/project.git` in Desktop; Desktop stores a `GitHubRepository` row keyed by `[ownerID(OwnerA)+name(project)]` with `cloneURL` pointing to the legitimate repo.
2. `OwnerA` account is later renamed/deleted, and repo `project` under that account ceases to exist upstream.
3. An attacker registers the now-free `OwnerA` login (or otherwise causes an `OwnerA/project` repository to exist again) and creates a repository named `project` with a different `clone_url` pointing to attacker infrastructure.
4. On the victim's next background refresh, `repositoryWithRefreshedGitHubRepository` (app-store.ts:4874) resolves `owner="OwnerA", name="project"` via `matchGitHubRepository` from the still-configured remote, calls `api.fetchRepository('OwnerA','project')`, and receives the attacker's repo object.
5. `updateRemoteUrl` (update-remote-url.ts:7) compares the victim's still-unchanged local remote (matching the old cached `cloneURL`) against the new `apiRepo.clone_url`; since they don't match and protocols match, it calls `gitStore.setRemoteURL(...)`, silently repointing `origin` to the attacker's clone URL.
6. `repoStore.upsertGitHubRepository` (repositories-store.ts:596) matches the existing DB row by `[ownerID+name]` and overwrites its `cloneURL`/`htmlURL`/`permissions` with the attacker's repository's values, all under the same local `dbID` the victim's `Repository` already references.
7. The victim's next "Fetch"/"Push" in Desktop now operates against the attacker's repository without any warning dialog.

```typescript
/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
```

```typescript
  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }
```

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
