### Title
Blame proof reveals Alice's ECDH key before her copied per-message key's PoP is verified, leaking secret shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`EncryptedMessage` carries a proof-of-possession (PoP) on its ephemeral key specifically so an attacker cannot copy Alice's per-message encryption key `K_A` into their own message and then trigger a blame event that reveals `ecdh = enc_key_Bob * K_A` — which would also decrypt Alice's real message to Bob (spec/cryptography/Distributed Key Generation.md lines 28–35). The defense is implemented in `Encryption::decrypt`, which queues the PoP into a `BatchVerifier` under `BatchId::Decryption(l)` [1](#0-0) . However, in `KeyMachine::calculate_share`, if the decrypted bytes are not a canonical scalar, the function returns `PedPoPError::InvalidShare { blame: Some(blame) }` **early — before `batch.verify_with_vartime_blame()` is ever run** [2](#0-1) . The queued PoP check is discarded, so the ECDH key is revealed even for a message whose PoP is invalid.

### Finding Description
`calculate_share` iterates over `shares.drain()`, calls `self.encryption.decrypt(...)`, and immediately tries `C::F::from_repr(share_bytes.0)`:

- `crypto/dkg/pedpop/src/lib.rs:476-484`: on `from_repr` failure it returns `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) })`. The `?` propagates out of `calculate_share`; `batch` (containing the still-unverified `BatchId::Decryption(l)` PoP statement) is dropped.
- `crypto/dkg/pedpop/src/encryption.rs:487-499`: `decrypt` computes `key = ecdh(&self.enc_key, msg.key)` and returns it inside `EncryptionKeyProof` unconditionally — its validity as a blame instrument depends entirely on the PoP, which was only *queued* at line 479, never verified on this path.
- `processor/src/key_gen.rs:419-425`: this blame is serialized into `ProcessorMessage::InvalidShare` and broadcast, publishing the ECDH shared point.

Because `ecdh` is `enc_key_Bob * msg.key`, copying `msg.key = K_A` (the public per-message key field from Alice's honest `EncryptedMessage` to Bob, readable via `EncryptedMessage::read`) makes Eve's blame proof reveal exactly the shared key that decrypts Alice's message. The PoP intended to stop this (challenge binds `from`, the ciphertext, and `msg.key` — `pop_challenge` at encryption.rs:484) is bypassed.

### Impact Explanation
An attacker DKG participant recovers the ECDH shared key protecting an honest sender's secret share to another participant, then decrypts that share off the published transcript. This leaks threshold secret-share material to an unauthorized party — a confidentiality breach of "critical data" matching the CVE class — and weakens the DKG's secret (each leaked polynomial share contribution directly reduces the secrecy of the victim's final share). The very side effect the spec documents the PoP as preventing is reintroduced.

### Likelihood Explanation
Fully deterministic and reachable: the attacker needs only to (a) observe an honest `EncryptedMessage`'s public `key` field, (b) send their own `EncryptedMessage` reusing that key with ciphertext that decrypts (under the shared ChaCha20 keystream) to a non-canonical scalar — which occurs with high probability for a random field repr and can be retried across protocol runs — and (c) supply any PoP, since it is never checked before the early return. No control of the victim or the RNG is needed.

### Recommendation
Verify the queued PoP batch before returning a blame proof. Concretely, in `calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499), do not attach `blame` on the `from_repr` early-return path until the PoP statement for that participant has been verified — e.g., split `decrypt` so the `EncryptionKeyProof` is only produced after `batch` confirms the `BatchId::Decryption(l)` statement, or run a partial/single-statement verification of the PoP before emitting the blame. Alternatively, return `blame: None` for the non-canonical-share case (treating it like a PoP failure) unless the PoP is proven valid.

### Proof of Concept
1. Alice and Bob (participants `i_a`, `i_b`) run PedPoP. Bob registers `enc_pub_key_b` in round 1. In round 2, Alice sends Bob `EncryptedMessage { key: K_A, pop: σ_A, msg: c_A }` where `c_A = share ⊕ ChaCha20(context, enc_key_b * K_A)`.
2. Eve (a participant) copies `K_A` and sends Bob `EncryptedMessage { key: K_A, pop: σ_E (invalid/forged or signed over garbage), msg: c_E }` where `c_E` is chosen so `c_E ⊕ keystream` is not a canonical `C::F` repr.
3. Bob calls `calculate_share`. `decrypt` queues Eve's PoP (never verified) and returns `EncryptionKeyProof { key: enc_key_b * K_A, dleq }`. `from_repr` fails → early `Err(InvalidShare { blame: Some(proof) })` at lib.rs:480-482.
4. `processor/src/key_gen.rs` broadcasts `blame.serialize()`. Eve (and all observers) now hold `enc_key_b * K_A` and decrypt `c_A`, recovering Alice's secret share for Bob — despite the PoP that exists precisely to prevent this never having been validated.
