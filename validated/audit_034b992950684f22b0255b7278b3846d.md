### Title
Cached FROST preprocess seed is reused across multiple signing sessions, enabling private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` generates a FROST preprocess seed once per `context`, encrypts it, stores it in `CachedPreprocesses`, and on every subsequent call decrypts and re-loads the *same* seed via `AlgorithmSignMachine::from_cache`. Because `from_cache` deterministically re-derives the nonces from the seed (`seeded_preprocess`), every signature produced under the same context uses identical secret nonces `d, e`. The cache is never deleted or rotated after `share_internal` consumes it. Any two shares issued under one context therefore reuse the nonce, and FROST's own documentation states nonce reuse enables third-party recovery of the private key share — the crypto analog of the reported "excessive rights" bug: a capability that should be single-use/privileged (fresh nonce generation) is left permanently accessible to whatever triggers signing under that context.

### Finding Description
In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:123-147):

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
  let mut cache = machine.cache();
  ... encrypt ...
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
... decrypt ...
let (machine, preprocess) = AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

`from_cache` calls `AlgorithmMachine::new(algorithm, keys).seeded_preprocess(cache)` (crypto/frost/src/sign.rs:268-274), which fully derives the nonce pair and commitments from the 32-byte seed. Nothing invalidates the DB entry afterward, so a second invocation of `share_internal` for the same `context` — e.g., a `Reattempt`, a retry after an `InvalidShare` blame event, or any second message signed under the same context — reconstructs the identical nonce vector.

A FROST share has the form `s_i = d_i + e_i·rho_i + c·lambda_i·x_i`. With the same `(d_i, e_i)` but a different `msg`, different signing set (hence different `rho_i`/`lambda_i`), or different aggregated commitment `R` (hence different challenge `c`), an observer holding two shares obtains two linear equations in the unknown `x_i` and recovers the signer's secret share. The library itself documents this exact consequence: "A preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:84-87), and "the only way for this seeded RNG to fail is if a preprocess is loaded multiple times, which was already a failure point" (spec/cryptography/FROST.md:57-62) — yet the coordinator deliberately loads it on every call.

Reachability from public inputs: any counterparty able to cause a second `share_internal` under the same context — by supplying preprocesses/shares that trigger a blame-and-reattempt path (`CoordinatorMessage::Reattempt`, processor/src/signer.rs:632, or `InvalidParticipant` blame flows) — forces honest nodes to emit a second share bound to the same nonce. The two shares are broadcast publicly over the authenticated channel, so recovery requires only observing messages the attacker caused to be produced.

### Impact Explanation
Recovery of a validator's FROST secret share. Combined with the shares an attacker already holds (or can similarly extract from `t - k` additional victims via the same trick), this yields the full threshold secret key for the affected context, enabling forged signatures on arbitrary messages — equivalent in consequence to the reported "manager drains all tokens": the protected capability (the group key's signing power) is fully compromised. Severity: Critical/High.

### Likelihood Explanation
Likelihood is moderate-to-high: the reuse is unconditional in code (the cache is keyed only by `context` and never cleared after `sign`), so exploitation only requires triggering two signing passes under one context. Blame-triggered reattempts and reboot/re-issue paths ("The caller is expected to re-issue sign orders on reboot", processor/src/signer.rs:463) make repeat `share_internal`/`attempt` calls a normal occurrence rather than an edge case. The main uncertainty is whether `context` is guaranteed unique per signed message — if it is per-session/per-set (as the naming suggests for a MuSig-of-validator-set construction), all signatures under it share the seed and the issue is deterministic.

### Recommendation
Delete or rotate the `CachedPreprocesses` entry atomically when a share is produced (e.g., overwrite it with a fresh seed after each `sign`, or key the cache by a per-attempt/session nonce rather than the long-lived `context`). At minimum, on reboot derive a domain-separated seed such as `H(context || attempt)` so reattempts never reuse nonces. Alternatively, drop the caching entirely and keep the `PreprocessMachine` in memory, regenerating with `OsRng` on any retry — accepting the loss of the reboot-recovery property rather than nonce reuse.

### Proof of Concept
1. A signing session under context `C` reaches `share_internal`; node stores seed `s` in `CachedPreprocesses[C]` and emits share `σ1 = d + e·rho1 + c1·λ·x` for message `m1` / set `S1`.
2. Attacker submits a malformed share from a participant, causing an `InvalidShare` blame and a `CoordinatorMessage::Reattempt` (or simply a second sign request under `C` with message `m2` / set `S2` after reboot re-issue).
3. `preprocess_internal` reloads `s`, `seeded_preprocess` regenerates identical `d, e`; node emits `σ2 = d + e·rho2 + c2·λ'·x`.
4. Attacker (and any observer of the broadcast shares) solves the 2×2 linear system for `x`, recovering the victim's secret share. Repeat across `t` victims to recover the group private key.

Note on scope confidence: the nonce-derivation and caching mechanics are verified in the cited code; the residual uncertainty is whether `context` uniqueness per signed payload is enforced upstream (not visible in the indexed coordinator code). If context is reused across distinct messages or reattempts — which the DB-persistence design implies — the vulnerability holds.
