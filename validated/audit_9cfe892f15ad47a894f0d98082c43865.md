### Title
Bitcoin transaction fee calculation omits OP_RETURN outputs, underestimating transaction weight - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` accepts caller-controlled `data` and adds it as an OP_RETURN output before calculating transaction weight, but the weight and fee calculations are passed only `payments`, omitting the added output. [1](#0-0)  The same omission occurs when change is considered, so the constructed transaction can have a lower effective fee rate and larger weight than the values used for validation. [2](#0-1) 

### Finding Description
`tx_outs` is extended with a zero-value OP_RETURN output when `data` is supplied. [3](#0-2)  However, `calculate_weight_vbytes` is called with `payments`, not `tx_outs`, so the model transaction contains only payment outputs and optionally change. [4](#0-3) [5](#0-4) 

Because change consumes the remainder after subtracting `payment_sat + fee_with_change`, the actual fee remains based on the underestimated virtual size while the final transaction includes the additional OP_RETURN output. [6](#0-5) [7](#0-6)  The maximum-standard-weight check likewise uses the underestimated `weight`, allowing a transaction that crosses the policy limit after the data output is added. [8](#0-7) 

### Impact Explanation
An unprivileged caller can cause the threshold wallet to sign a Bitcoin transaction whose real fee rate is below both the requested rate and the minimum relay rate validated by the constructor. [9](#0-8)  The resulting transaction is properly signed for the actual serialized transaction through `taproot_key_spend_signature_hash`, so the flaw is not a signature mismatch: Serai produces a completed transaction that Bitcoin nodes may reject from their mempools or that pays substantially less fee than intended. [10](#0-9) 

For example, a one-input transaction with one P2TR payment, one P2TR change output, and an 80-byte OP_RETURN is modeled as roughly 154 vbytes, while the additional output contributes about 92 serialized bytes and makes the real transaction roughly 246 vbytes. [11](#0-10) [12](#0-11)  With `fee_per_vbyte = 1`, the constructor validates a 154-sat fee against an estimated 154-vbyte transaction, but the completed 246-vbyte transaction pays only about 0.63 sat/vbyte. [13](#0-12) 

### Likelihood Explanation
The bug is reachable whenever a caller supplies non-empty `data` together with change; both are public parameters of `SignableTransaction::new`. [14](#0-13)  The discrepancy scales with the caller-controlled data length, up to the accepted 80-byte limit. [15](#0-14)  The primary production processor currently passes `None` for data, which limits the observed integration path, but the exposed in-scope wallet API still constructs and signs the inconsistent transaction when its documented data option is used. [16](#0-15) 

### Recommendation
Build the complete output vector—including payments, optional OP_RETURN data, and optional change—before estimating weight and fee, or extend `calculate_weight_vbytes` to accept the OP_RETURN output explicitly. [17](#0-16)  Calculate both the no-change and with-change candidates from the exact final output set, recalculate the minimum relay fee from that actual virtual size, and perform `MAX_STANDARD_TX_WEIGHT` on the final transaction rather than the reduced model. [18](#0-17) 

### Proof of Concept
1. Create a valid `ReceivedOutput` controlled by the multisig and select a P2TR payment and P2TR change script. [19](#0-18) 
2. Call `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0; 80]), 1)`. [14](#0-13) 
3. The function appends the 80-byte OP_RETURN output to `tx_outs` but estimates only the payment output when deriving `vbytes`. [1](#0-0) 
4. For one P2TR input, payment, and change output, the estimate is approximately 154 vbytes; the 80-byte OP_RETURN adds approximately 92 serialized bytes, making the actual transaction approximately 246 vbytes. [20](#0-19) 
5. The change calculation subtracts only `payment_sat + 154`, leaving a valid change output, so `needed_fee` remains 154 sats even though the actual transaction is 246 vbytes. [21](#0-20) 
6. Signing commits to the actual transaction containing the OP_RETURN output via `SighashCache` and `Prevouts::All`, and completion inserts the signatures into its witnesses. [10](#0-9) [22](#0-21) 
7. The completed transaction pays approximately 0.63 sat/vbyte rather than the requested and checked 1 sat/vbyte, making it below Bitcoin's default minimum relay fee policy. [9](#0-8)

          witness: Witness::from_slice(&[vec![0; 64]])

        .iter()

          script_pubkey: payment.0.clone(),

      // the value is fixed size (so any value could be used here)
