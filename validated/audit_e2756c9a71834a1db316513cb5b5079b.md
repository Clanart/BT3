### Title
Discarded swap return value causes permanent loss of overpaid native token in `placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder` in the Tron variant of `IntentGatewayV2` calls `swapETHForExactTokens` to pay order fees but discards its return value entirely, and — unlike the sibling EVM implementation — never refunds the caller's unspent native `msg.value`. This mirrors the Illuminate/Tempus H-01 bug class: an external call's return value (which tells the caller exactly how much native asset was actually consumed) is dropped, so downstream native-token accounting is wrong, and here the consequence is stranded/unrecoverable user funds rather than a mint miscalculation.

### Finding Description
In the canonical implementation, `evm/src/apps/IntentGatewayV2.sol`, the fee-swap block captures the router's return value and decrements `msgValue` accordingly, then refunds any leftover native token to `msg.sender`: [1](#0-0) 

In the Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`, the analogous fee-swap call is made without capturing the returned `amounts` array, `msgValue` is never decremented, and there is no subsequent "refund unspent native token" step before the function emits `OrderPlaced` and returns: [2](#0-1) 

`swapETHForExactTokens` is an exact-output swap: the router only spends as much native token as required to produce `order.fees` output tokens and returns the rest to the caller (the `IntentGatewayV2` contract itself, since it is `msg.sender` of the router call), not to the user. Because the Tron contract:
1. does not read `amounts[0]` (actual native spent) to adjust `msgValue`, and
2. has no refund path for any leftover native balance,

any native token sent by the user beyond what predispatch/inputs required (i.e., whatever the router refunds back into the contract after the exact-output swap) is left sitting in the contract's balance with zero escrow accounting (`_orders[commitment][...]` is not updated for it) and no `emit`/withdrawal path tied to the order. The value is effectively orphaned inside the contract.

### Impact Explanation
This is a direct loss-of-funds bug reachable by any ordinary user through the public `placeOrder` entrypoint — no relayer, prover, or admin involvement is required. A user who slightly overestimates `msg.value` when the order pays fees via native-token swap permanently loses the difference: it becomes unaccounted, unescrowed native balance inside the contract with no code path to reclaim or credit it to any order, beneficiary, or refund. This satisfies the bounty's "loss of funds" / "logic attacks" impact class, matching the intent of the Tempus H-01 analog where a dropped/misused external-call return value corrupted asset accounting.

### Likelihood Explanation
Likelihood is high for normal usage: any `placeOrder` call with `order.fees > 0`, native-token fee payment (`msgValue > 0` at that point), and a `msg.value` that isn't an exact minimal amount (which is the common case, since `swapETHForExactTokens` is an exact-output swap and callers cannot know the precise WETH price to the wei ahead of time) will trigger the router refund into the contract, and that refund is never returned to the user or accounted for.

### Recommendation
Mirror the EVM implementation: capture the return value of `swapETHForExactTokens`, subtract the actual native amount spent from `msgValue`, and refund any remaining `msgValue` to `msg.sender` before emitting `OrderPlaced`, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 353–368. [3](#0-2) 

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with one native-token input of amount `X` and `order.fees = F > 0`, sending `msg.value = X + Y` where `Y` is meant to cover the native-token-to-feeToken swap.
2. In the native-input branch, `msgValue` is reduced by `X`, leaving `msgValue = Y`. [4](#0-3) 
3. Since `order.fees > 0` and `msgValue (Y) > 0`, the contract calls `swapETHForExactTokens{value: Y}(F, path, address(this), block.timestamp)` without capturing the return value. [5](#0-4) 
4. The router spends only `Z < Y` (the WETH-equivalent needed to buy exactly `F` fee tokens) and refunds `Y - Z` back to the calling contract (`address(this)`), landing as unaccounted native balance.
5. `placeOrder` returns without ever inspecting or refunding `Y - Z`; the escrow map `_orders[commitment][...]` has no entry for this leftover amount, so it is permanently stuck in the contract with no beneficiary, no refund, and no order tied to it — a direct, unconditional loss of `Y - Z` native tokens for the user.
