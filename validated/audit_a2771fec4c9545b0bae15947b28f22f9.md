The double-free/error-path bug class maps to Serai's cached preprocess reuse. Let me check whether `CachedPreprocesses` is ever cleared after `from_cache`.### Title
Cached FROST preprocess re-used across `share`/`complete` enables nonce reuse and secret key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Linux bug is a failure-path double-release: two pointers alias the same object and it is "put" twice. The Serai analog is deterministic reuse of a cached FROST preprocess seed: `SigningProtocol::preprocess_internal` reads `CachedPreprocesses` from the DB and reconstructs identical nonce material via `AlgorithmSignMachine::from_cache`, but never deletes or rotates the cached seed afterward. Every path that calls `share_internal` therefore calls `SignMachine::sign` with the exact same nonces. `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal` — i.e., the same nonce is consumed twice on what is effectively a retry/alternate path — while the preprocess map and message are attacker-influenced inputs. Two shares under the same nonce with different binding factors/challenges let any observer solve for the signer's secret, recovering the validator's Ristretto key share and enabling signature forgery.

### Finding Description
- `preprocess_internal` only writes `CachedPreprocesses` when absent, then unconditionally reads it back and calls `from_cache`, which routes to `seeded_preprocess(cache)` — so the same seed deterministically regenerates the same `nonces`. No `CachedPreprocesses::del`/rotation exists anywhere; the same seed is reused for every subsequent call with that context. [1](#0-0) [2](#0-1) 
- `share_internal` rebuilds the machine by calling `preprocess_internal` a second time and then `machine.sign(preprocesses, msg)` — a fresh signing operation on already-consumed nonces. [3](#0-2) 
- `DkgConfirmer::share` calls `share_internal`, and `DkgConfirmer::complete` calls `share_internal` *again* (via `.expect("trying to complete a machine which failed to preprocess")`), so the nonce is consumed at least twice whenever both paths execute. Both take `preprocesses` and `key_pair` supplied from tributary transaction data. [4](#0-3) 
- In `SignMachine::sign`, the nonce is `base + actual * binding_factor` and the share is `sign_share(&view, &Rs, nonces, msg)`; with fixed nonces, any change to `preprocesses` (binding factors) or `msg` (challenge) yields a second linear equation in the same secret share. [5](#0-4) 
- The signed material here is the MuSig n-of-n key over the validator's own key (`musig(musig_context(...), self.key, participants)`), so the recovered secret is the validator's tributary signing key. [6](#0-5) 
- Serai's own spec acknowledges the consequence: "Reusing preprocesses would enable a third-party to recover your private key share." [7](#0-6) 

### Impact Explanation
Nonce reuse in Schnorr/FROST share generation is fatal: from two shares `s1 = k + c1·x` and `s2 = k + c2·x` (same nonce `k`, different challenges `c`), the secret `x = (s1 − s2)/(c1 − c2)` (up to the interpolation/binding-factor scaling the attacker can compute publicly). Because the key being signed with is the validator's MuSig key, recovery yields the validator's private key share, enabling arbitrary signature forgery and impersonation of that validator — equivalent in consequence to the CVE's use-after-free, realized as key compromise rather than memory corruption. Severity: High–Critical.

### Likelihood Explanation
The trigger is two `sign` executions under the same `CachedPreprocesses` context with differing inputs. `share` and `complete` are separate entry points driven by tributary messages carrying attacker-controllable `preprocesses`/`key_pair`; a differing preprocess set or a differing `key_pair` between the two calls is sufficient. No collusion or malicious validator internals are required beyond the ability to submit the transaction data that reaches `share`/`complete` — but note the inputs must actually differ (identical inputs reproduce the identical share and leak nothing), and exploitation requires observing both emitted shares, which are broadcast over the authenticated channel.

### Recommendation
Delete the cached seed from `CachedPreprocesses` before (or atomically with) `from_cache` in `preprocess_internal`, and fail closed if the cache entry is absent rather than regenerating — mirroring `from_cache`'s contract that "the preprocess must be deleted so it's never reused." Additionally, `complete` should reuse the `AlgorithmSignatureMachine` produced by `share` rather than re-running `share_internal`, so a second `sign()` on the same nonces is impossible by construction.

### Proof of Concept
1. `DkgConfirmer::share(preprocesses_A, key_pair)` runs `share_internal` → `from_cache(seed)` → `sign(preprocesses_A, msg_A)` → emits share `s1` with nonce `k = base + rho_A·actual`.
2. `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` runs `share_internal` again → the same `seed` regenerates the same `base`/`actual`, but `preprocesses_B` yields binding factor `rho_B` and/or `key_pair`/`msg` changes the challenge → emits share `s2` with nonce `k' = base + rho_B·actual`.
3. With `s1 = k + c1·x`, `s2 = k' + c2·x`, and `k' − k = (rho_B − rho_A)·actual` where `actual` is recoverable as `base·(rho difference)` only if `rho_A == rho_B`; in the simplest exploitable case, identical preprocess set with different `msg` (different `key_pair`) gives identical `k` and the textbook two-equation solve for `x`.
4. The recovered `x` is the validator's MuSig secret key contribution, enabling forged tributary signatures.
