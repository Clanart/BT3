## Title
Git's anti-RCE clone protections are explicitly disabled during clone, re-opening a known malicious-repository code-execution class - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` runs every `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'`. This variable is the kill-switch Git itself introduced (as part of the 2024 security hardening around CVE-2024-32002/32004/32020/32021, the "hooks-via-nested-.git-directory during clone" class of remote code execution) to prevent a maliciously crafted repository from planting executable content (e.g. a hook, or a `.git` directory alias reachable through a case-insensitive/short-name/symlink collision inside a submodule) that Git would otherwise write and potentially execute during a recursive clone/checkout. Git's own documentation explicitly warns this variable exists only for testing and must never be disabled for real clones of untrusted content. Desktop disables it unconditionally, for every clone of every (by definition, untrusted-until-proven-otherwise) repository URL a user pastes or opens via `x-github-client://` deep links.

### Finding Description [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c', `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

This is invoked from every "Clone repository" flow in the UI (URL paste, "Open in Desktop" protocol handler, GitHub repo picker), meaning the attacker fully controls the remote repository content and the recursive-submodule graph that gets cloned. The mitigations Desktop *does* have (`isClonePathSensitive` restricting the destination directory, `sanitizeCloneName` preventing path traversal in the derived folder name) only protect the top-level clone *destination path*; they do nothing to constrain what Git itself may write inside `.git/` for nested submodules during a `--recursive` clone, which is precisely the surface `GIT_CLONE_PROTECTION_ACTIVE` was designed to guard. [2](#0-1) 

Because the flag is hardcoded off rather than left at Git's secure default, none of Desktop's other layers (trampoline env, credential helper host-matching, hooks proxy) come into play here — this happens purely inside Git's own clone/checkout machinery, before Desktop's hook-interception (`interceptHooks`) logic is even relevant, since `clone.ts` doesn't pass `interceptHooks` at all. [3](#0-2) 

### Impact Explanation
If reachable (see Likelihood), this corrupts the invariant "cloning a repository the user selected should never execute code or write files outside the intended working tree" — the same invariant broken in the report's parameterizer analogy (an unchecked value from an external actor is trusted and applied without validation, undermining downstream guarantees). Concretely, disabling Git's clone protections allows a hostile repository, when recursively cloned, to potentially write into locations that get treated as hook paths in nested submodule `.git` directories, resulting in arbitrary command execution on the victim's machine the moment the clone/checkout completes — full code execution outside the intended repo tree, no user hooks/settings interaction required.

### Likelihood Explanation
Any Desktop user cloning any URL, or GitHub repository, or following an "Open in GitHub Desktop" deep link, exercises this exact code path with an attacker-supplied `url`. No local access, admin rights, or prior compromise is needed — this is squarely the "attacker controls a cloned/fetched repository" scenario the task asks for. I could not verify from the available index which Git version ships with the bundled `dugite`/`git` binary, nor whether the specific upstream CVEs this flag mitigates are still applicable to that exact version; that would need to be confirmed in a full checkout (e.g. `git --version` bundled with the app, and cross-referencing the exact fixed-version boundaries for CVE-2024-32002/32004/32020/32021) before treating this as a confirmed exploitable 0-day rather than a "protection intentionally disabled" finding.

### Recommendation
- Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` so clone operations run with Git's secure default protections enabled.
- If this override exists to work around a legitimate compatibility issue, gate it narrowly (e.g., only for local/trusted `file://` sources used in tests) instead of unconditionally for all network clones.
- Add a regression test asserting that `clone()` never sets `GIT_CLONE_PROTECTION_ACTIVE=false` for non-test invocations, and audit `updateSubmodulesAfterOperation`/`resetSubmodulePaths` for the same pattern.

### Proof of Concept
1. An attacker publishes a public repository containing a submodule whose path/name is engineered to collide with a Git-internal directory on a case-insensitive filesystem (macOS default, Windows), following the same technique behind CVE-2024-32002.
2. Victim opens the repository's clone URL in GitHub Desktop (via UI paste or an `x-github-client://openLocalRepo`/clone deep link).
3. Desktop calls `clone(url, path, options)` → `git -c init.defaultBranch=... clone --recursive -- url path` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment, disabling Git's own defenses against exactly this repository shape.
4. If the bundled Git version is otherwise vulnerable to the underlying issue, the recursive clone/checkout executes attacker-controlled content outside the intended working tree.

I was not able to independently confirm the bundled Git binary's exact version/patch level from the index, so step 4's exploitability should be validated against the shipped `dugite`/git version before treating this as a proven RCE versus a defense-in-depth regression.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
