### Title
Flash/JIT-deposit reward-sandwich lets an attacker steal a disproportionate share of freshly-donated yield from `BaseRewardPoolV2` - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2` distributes rewards as a one-shot snapshot increment to `rewardPerTokenStored`, computed from `totalStaked()` at the exact moment `queueNewRewards`/`donateRewards` executes [1](#0-0) . Because `balanceOf`/`totalStaked` read live, unbonded stake from `MasterMagpie` with no lock-up or cooldown on deposit/withdraw [2](#0-1) [3](#0-2) , an attacker can inflate `totalStaked` right before a reward event and grab a disproportionate share of that specific reward batch, diluting what genuine long-term stakers would have received.

### Finding Description
`_provisionReward` (called from both `queueNewRewards`, restricted to `onlyManager`, and `donateRewards`, which has **no access control at all**) increases `rewardPerTokenStored` by `_amountReward * 10**decimals / totalStaked()` in a single, instantaneous step [4](#0-3) . This is fundamentally a snapshot/dividend model, not a time-weighted streaming model (no `periodFinish`/`rewardRate`/`lastUpdateTime` as in Synthetix-style pools).

`balanceOf` and `totalStaked` both read the *current* live stake from `IMasterMagpie(operator).stakingInfo` / `IERC20(stakingToken).balanceOf(operator)` [5](#0-4) , and `MasterMagpie.deposit`/`withdraw` have no cooldown or vesting period — a user can deposit and withdraw the same block/consecutive txs, subject only to `nonReentrant`/`whenNotPaused` [3](#0-2) [6](#0-5) .

`_deposit`/`_harvestAndUnstake` call `_harvestBaseRewarder` (which triggers the rewarder's `updateReward`/`_updateFor` and checkpoints `userRewardPerTokenPaid`) **before** the user's balance is mutated [7](#0-6) [8](#0-7) , so the new depositor's checkpoint is correctly set at deposit time — this closes the "backdated theft of pre-existing accrual" variant, but does **not** close the "sandwich a single reward event" variant:

1. Attacker deposits a large flash-loaned amount `A` of `stakingToken` into `MasterMagpie` (checkpoint `userRewardPerTokenPaid` set to `rewardPerTokenStored_before`, since attacker balance was 0 pre-deposit).
2. A legitimate reward event fires — either a manager's `queueNewRewards` call the attacker front-runs, or, more critically, `donateRewards`, which anyone can call at will with no `onlyManager` restriction [9](#0-8) . `totalStaked()` at this moment is `S + A` (genuine stake `S` plus attacker's `A`), so `rewardPerTokenStored` increases by `R * 1e_dec / (S + A)` instead of `R * 1e_dec / S`.
3. Attacker calls `MasterMagpie.withdraw`, which internally harvests via `_harvestBaseRewarder` → `getReward`/`updateReward(_account)` → `_earned` = `A * (rewardPerTokenStored_after - rewardPerTokenStored_before) / 1e_dec` = `A * R / (S + A)`, i.e., a share of the entire donated reward `R` proportional only to the attacker's momentary stake, not to time actually staked.
4. Genuine stakers only ever collect `S * R / (S + A)` of `R` from that event — the increment they would have received (`R/S` per token) has been permanently diluted by the attacker's presence during the single-block snapshot.

The existing `nonReentrant`/`onlyManager`/`onlyMasterMagpie` guards do not prevent this because the attack does not require reentrancy or manager privileges — it is a same-block/adjacent-transaction sandwich around a permissionless (`donateRewards`) or front-runnable (`queueNewRewards`) call, executed entirely through public deposit/withdraw functions.

### Impact Explanation
This is a direct theft of unclaimed yield from genuine long-term stakers: the attacker with sufficient flash-loan-able capital `A >> S` can claim close to 100% of any given reward-injection event's tokens while contributing essentially zero time-weighted stake, permanently reducing the `rewardPerTokenStored` increment available to honest, continuously-staked users. This matches the Immunefi impact class "theft of unclaimed yield."

### Likelihood Explanation
Feasibility is high: `donateRewards` is fully permissionless (no `onlyManager` check) so an attacker can watch the mempool for any `donateRewards`/`queueNewRewards` call (or induce their own economically-neutral one to test) and front-run it with a large deposit, back-run with a withdraw. It requires only flash-loan-able `stakingToken` liquidity and no privileged role, and is repeatable for every future reward-injection event on any pool built on `BaseRewardPoolV2`/`BribeRewardPool` (`BribeRewardPool` even tracks its own `_balances`/`totalSupply`, mutated by the operator on stake/unstake with the same lack of vesting) [10](#0-9) .

### Recommendation
Move to a time-weighted reward-streaming model (Synthetix-style `rewardRate`/`periodFinish`/`lastUpdateTime` with continuous linear accrual) instead of instantaneous lump-sum crediting based on the momentary `totalStaked()`, and/or add a minimum staking duration / withdrawal cooldown in `MasterMagpie` so that deposited stake cannot be withdrawn in the same block/short window as a reward-crediting event. Additionally, restrict `donateRewards` with the same `onlyManager` gate as `queueNewRewards`, or at minimum rate-limit/timelock reward injections to prevent precise sandwichable timing.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, a `stakingToken`, and register a `BaseRewardPoolV2` for it with a `rewardToken`.
2. Have `userHonest` deposit `S` tokens and remain staked.
3. Simulate attacker: `attacker` flash-borrows `A >> S` `stakingToken`, calls `MasterMagpie.deposit(stakingToken, A)`.
4. Call `rewardPool.donateRewards(R, rewardToken)` (permissionless) or have a manager call `queueNewRewards` in the very next tx (front-run scenario).
5. `attacker` calls `MasterMagpie.withdraw(stakingToken, A)` in the same block/immediately after, repays flash loan.
6. Assert `attacker`'s claimed reward (via `getReward`) ≈ `A * R / (S + A)`, which is disproportionate to the zero time actually staked, and assert `userHonest.earned(rewardToken)` is reduced to `S * R / (S + A)` versus the expected `R` (or `R` minus attacker's fair share if attacker had genuinely time-staked), demonstrating the diluted, stolen yield.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
