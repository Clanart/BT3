### Title
Out-of-range `Participant` in a blame request panics on `enc_keys[&decryptor]` HashMap index — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2024-52974 (a crafted request crashing the Kibana server), `Decryption::decrypt_with_proof` in the PedPoP DKG performs an unchecked HashMap index on an attacker-influenced `Participant` index, turning a crafted blame/accusation message into a process-crashing panic.

### Finding Description
`AdditionalBlameMachine::new` / `BlameMachine` register encryption keys only for participants `1..=n` (pedpop/src/encryption.rs:356-361 registers via `Decryption::register`; lib.rs:656-660 iterates `1..=n`). `blame(sender, recipient, msg, proof)` forwards `recipient` to `blame_internal` → `decrypt_with_proof`, which executes `self.enc_keys[&decryptor]` at crypto/dkg/pedpop/src/encryption.rs:388 with no bounds check.

`Participant` is any non-zero `u16` (crypto/dkg/src/lib.rs:29-35), so values `n < participant <= 65535` are constructible from untrusted bytes (e.g., `Participant::deserialize_reader` at crypto/dkg/src/lib.rs:121-126 accepts any non-zero u16). Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` validates that `sender`/`recipient` are within the DKG's participant set before indexing. The panic fires before the DLEq verification completes — it occurs at the argument evaluation `self.enc_keys[&decryptor]` inside `decrypt_with_proof` (encryption.rs:381-390), reached as soon as `msg.pop` (attacker-controlled `SchnorrSignature::read` bytes) verifies, or trivially when `proof` is `Some`.

Reachability: in the Serai coordinator's blame flow, `VerifyBlame { id, accuser, accused, share, blame }` reads `accuser`/`accused` as raw `Participant` values from the transaction and passes them into `AdditionalBlameMachine::blame(accuser, accused, ...)` (processor/src/key_gen.rs:504-549), so a crafted accusation carrying an out-of-range participant index crashes the node rather than returning an error. Even in library-only usage, `blame()` is a public API consuming untrusted `EncryptedMessage`/`EncryptionKeyProof` bytes plus caller-supplied participant indexes.

### Impact Explanation
A single crafted message causes an unconditional panic (`HashMap` index on missing key), aborting the task/process handling blame verification. Since blame adjudication runs on the consensus/key-management path, the crash halts the validator — remote, unauthenticated-by-design DoS matching the advisory's "specially crafted request crashes the server" class.

### Likelihood Explanation
Any party able to submit a blame/accusation (a DKG participant submitting an `InvalidDkgShare`/VerifyBlame message, or an integrator exposing `AdditionalBlameMachine::blame` to network input) can trigger it by setting `accuser`/`recipient` to any `Participant` in `(n, 65535]`. The only preconditions are a structurally valid `EncryptedMessage` and a `Some` proof (or a valid `msg.pop` signature the attacker can trivially produce for their own key).

### Recommendation
Validate `sender` and `recipient` against the registered set in `blame_internal`/`AdditionalBlameMachine::blame` (e.g., `enc_keys.get(&decryptor)` returning `InvalidProof`/a defined fault result on `None`), mirroring the `MissingParticipant`/`InvalidParticipant` errors already used elsewhere.

### Proof of Concept
```rust
// params: n = 3; commitment_msgs for participants 1..=3 registered normally
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker crafts blame naming a recipient outside the DKG
let recipient = Participant::new(500).unwrap(); // > n, no enc_key registered
let msg = EncryptedMessage::<Ristretto, SecretShare<_>>::read(&mut bytes, params).unwrap();
let proof = EncryptionKeyProof::read(&mut proof_bytes).ok();

// Panics at crypto/dkg/pedpop/src/encryption.rs:388:
// `self.enc_keys[&decryptor]` — key not found in map
machine.blame(sender, recipient, msg, proof);
```

Confidence caveat: `blame` is not in the prompt's enumerated read/verify API list, so acceptance hinges on treating the blame-adjudication entry point as attacker-reachable; in the coordinator it is reached by `Participant` fields parsed from untrusted transaction bytes.
