Based on the exploit class in the report — an untrusted external input (a Curve pool call) causing loss of value through a code-path that "shouldn't" be reachable — the closest verified Desktop analog is not the git-hooks/askpass/PR-checkout paths (all of which have concrete guards: the `unsafe`/dubious-ownership check in `rev-parse.ts`, the sandboxed `withHooksEnv` proxy that copies stub executables rather than running repo-provided hook binaries directly, the `sanitizeCloneName`/`isClonePathSensitive` clone-path checks, and `resolveWithin` for deep-link file opens). The one place where the codebase *deliberately reverses* an upstream Git hardening control is the `allowFileProtocol` flag on submodule updates.

### Title
Re-enabling `protocol.file.allow=always` for submodule updates lets an attacker-controlled repo read local filesystem paths into the working tree - ([File: app/src/lib/git/submodule.ts])

### Summary
Git added `protocol.file.allow=user` as a default-deny for `file://` submodule URLs specifically to stop malicious repositories from using `.gitmodules` to exfiltrate/disclose arbitrary local paths during `submodule update` (the class of bug fixed upstream as CVE-2022-39253). GitHub Desktop's `updateSubmodulesAfterOperation` contains an `allowFileProtocol` parameter that, when `true`, re-adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation, explicitly overriding that protection.

### Finding Description
`updateSubmodulesAfterOperation` builds its argument list as: [1](#0-0) 
and is invoked from `checkoutBranch`/`checkoutCommit` with an `allowFileProtocol` boolean that defaults to `false`: [2](#0-1) [3](#0-2) 

When `allowFileProtocol` is `true` for a checkout operation, any `.gitmodules` entry in the (attacker-controlled, cloned/fetched) repository with a `url = file:///…` value pointing at a sensitive local path (e.g. `~/.ssh`, `~/.aws`, another unrelated repo on disk) will be honored by `git submodule update --init --recursive`, since the command-level override neutralizes Git's own `protocol.file.allow=user` default-deny. The result is that content from outside the repository's working directory gets copied into the submodule path inside the checked-out tree.

### Impact Explanation
This satisfies the "file read outside the repo" and "silent corruption of what the user commits/pushes" impact categories: local files the user never intended to share can be pulled into the working tree via a malicious `.gitmodules` entry, and if the user is unaware and later stages/commits/pushes the submodule content, sensitive local data (keys, credentials, unrelated project files) could be pushed to a remote the attacker controls.

### Likelihood Explanation
I was not able to trace, within the remaining tool budget, every production call site that passes `allowFileProtocol: true` into `checkoutBranch`/`checkoutCommit` from `app-store.ts` (the parameter defaults to `false`, and the only concrete call sites I directly observed with `true` are in test helpers/fixtures, e.g. `app/test/unit/git/checkout-test.ts:160-166`). This is a real gap in my verification: the severity depends entirely on whether/when the production UI flow sets this flag to `true` for a repository whose `.gitmodules` file is attacker-controlled (i.e., freshly cloned/fetched, not yet trusted by the user). Given the index size limits noted in my instructions, I could not fully confirm this from the available code snippets — a full Devin session with complete file access would be needed to trace all call sites of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` in `app-store.ts` and confirm whether `allowFileProtocol=true` is ever reachable from an untrusted-repo checkout without an explicit, informed user opt-in.

### Recommendation
Audit every call site that passes `allowFileProtocol: true` into `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation`, and ensure it is never enabled implicitly for a repository whose ownership/trust has not been explicitly confirmed by the user (mirroring the existing `unsafe`-repository gating in `rev-parse.ts`). Consider scoping any legitimate use of `file://` submodules to paths that are provably inside the user's already-cloned repository tree, rather than a blanket `protocol.file.allow=always`.

### Proof of Concept
1. Attacker publishes/serves a repository whose `.gitmodules` contains:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
2. Victim clones/fetches the repo in Desktop and performs a checkout/branch switch that internally invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true` (production trigger unconfirmed — see Likelihood).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which clones `~/.ssh` into `leak/` inside the working directory.
4. If the victim commits and pushes, the contents of `~/.ssh` are exfiltrated to the attacker's remote.
