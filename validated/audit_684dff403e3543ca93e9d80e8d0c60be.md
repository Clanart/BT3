## Title
Stale AI-generated conflict resolutions are written to disk and staged without revalidating that they still match the current conflict content - (File: `app/src/lib/stores/app-store.ts`)

### Summary
This is a structural analog of the reported "missing slippage protection" bug class: a value is computed against one snapshot of state, then applied later against a possibly-different state, with no check that the two still agree. In the Uniswap report, the amount of tokens returned is computed at execution time and never validated against the amounts the user expected when they initiated the withdrawal. In GitHub Desktop, `_applyCopilotConflictResolutions` computes AI-resolved file content against one snapshot of a merge/rebase/cherry-pick conflict, then — often much later — writes that stale content to disk and stages it for commit, only checking a coarse binary "is this file still conflicted" flag rather than verifying the resolution still corresponds to the conflict currently on disk.

### Finding Description
When Desktop kicks off Copilot conflict resolution, it captures the working directory's conflict markers, sends them to the AI, and stores the returned `resolutions` (including `resolution.resolvedContent`) in `multiCommitOperationState` [1](#0-0) . The comment even documents that the wait can be very long: the app tracks `copilotConflictResolutionOver60sCount` and `copilotConflictResolutionOver120sCount` [2](#0-1) .

Later, when the user clicks "Continue Merge", `_applyCopilotConflictResolutions` writes each `resolution.resolvedContent` straight to disk and stages it with `git add`. The only staleness guard is:

```
const onDiskFile = state.changesState.workingDirectory.files.find(
  f => f.path === resolution.path
)
if (
  onDiskFile !== undefined &&
  isConflictedFileStatus(onDiskFile.status) &&
  !hasUnresolvedConflicts(onDiskFile.status)
) {
  continue
}

await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [3](#0-2) 

This check only asks "does git status still consider this file conflicted with unresolved markers?" — it never compares the *current* on-disk conflict content (the actual "ours"/"theirs" markers) with what `resolution.resolvedContent` was generated from. If the underlying conflict content changes between resolution generation and the user clicking "Continue Merge" — for example, the theirs-side content originates from a fetched branch tip supplied by a remote/proxy that a repo owner or MITM-capable party controls, and a subsequent fetch/rebase continuation changes which commit is actually being merged while the file path remains "conflicted" — the app will silently overwrite the file with resolution content computed from a different (stale) conflict, then stage it via `git add` for the commit [4](#0-3) .

### Impact Explanation
The commit that gets produced can silently contain merged content that never actually corresponds to a review-time snapshot the user saw approved in the result dialog — this is the "silent corruption of what the user commits" category. Because the content is `git add`-ed automatically right before commit, a user who trusts the Copilot result dialog and clicks "Continue Merge" may push a commit whose file contents don't match either side of the conflict they believed was being resolved.

### Likelihood Explanation
The window for divergence is the entire AI-resolution processing time, which the code's own instrumentation acknowledges can exceed 120 seconds [5](#0-4) , plus additional time for the user to review the result dialog before clicking "Continue Merge". The check that exists (`isConflictedFileStatus` / `hasUnresolvedConflicts`) is a status-kind check, not a content-equality check, so it does not stop application of a resolution computed against different (stale) marker content as long as the file is still nominally "conflicted."

### Recommendation
Before writing `resolution.resolvedContent` to disk, re-diff or hash the current on-disk conflicted content against the content snapshot that was sent to Copilot for that path, and skip (or re-run) the resolution if they no longer match — mirroring how a slippage check re-validates the actual execution-time outcome against the value the operation was authorized against, rather than trusting a value computed earlier under different conditions.

### Proof of Concept
1. Start a multi-commit operation (rebase/cherry-pick/merge) against a branch fetched from a remote where the conflicting "theirs" content is attacker/remote-controlled.
2. Trigger Copilot conflict resolution; while the (potentially 60-120+s) resolution is in flight, cause the underlying conflict content for one of the paths to change (e.g., the operation advances to a different patch, or the file's conflict markers otherwise change) while `git status` still reports the path as conflicted with unresolved markers.
3. When the Copilot result returns and the user clicks "Continue Merge", `_applyCopilotConflictResolutions` passes the `isConflictedFileStatus`/`hasUnresolvedConflicts` check (the file is still flagged conflicted) and writes the stale `resolvedContent` over the now-different on-disk content, then stages it for commit [6](#0-5) .
