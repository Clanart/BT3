### Title
Cached FROST preprocess reused across distinct signing contexts because `CachedPreprocesses` is keyed only on `(label, attempt)` — nonce reuse leaks the signer's private key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The upstream CVE (ALPINE-CVE-2022-27775) is a connection-pool confusion: a pooled connection is reused because the lookup key omits a distinguishing attribute (the IPv6 zone id), so a request for a logically different endpoint silently reuses a resource scoped to another. The exact analog exists in Serai's coordinator: the persistent FROST preprocess cache `CachedPreprocesses` is keyed solely on a `context` value that, for the DKG confirmation MuSig signing protocol, is only `(b"DkgConfirmer", attempt)`. It does not include the validator-set session/genesis, the participant/`removed` set, or the message being signed. Any second signing operation that resolves to the same `(label, attempt)` key but differs in any of those omitted dimensions reuses the identical deterministic nonces — and nonce reuse across two different messages/challenges reveals the signer's secret key.

### Finding Description
`preprocess_internal` stores a freshly generated preprocess seed under `CachedPreprocesses::set(self.txn, &self.context, ...)` only if `CachedPreprocesses::get(self.txn, &self.context).is_none()`, and otherwise reloads and reuses it (`coordinator/src/tributary/signing_protocol.rs:123-145`). The seed deterministically generates the FROST nonces `(d, e)` via `ChaCha20Rng::from_seed` in `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`).

For `DkgConfirmer`, the context is `let context = (b"DkgConfirmer", self.attempt);` (`signing_protocol.rs:275`). Omitted from the key:

- `self.spec.set()` / `spec.genesis()` — the validator-set session. The coordinator DB persists across sessions; a validator's `self.key` (its Ristretto MuSig key) is the same across sets. A `DkgConfirmer` for attempt `0` of a new session collides with attempt `0` of the previous session.
- The `removed` set and `key_pair` — both feed `set_keys_message`, i.e. the signed `msg` (`signing_protocol.rs:296-301`).

The encryption of the cache (`encryption_key_preimage = "Cached Preprocess Encryption Key" || context || key`) likewise binds only `context` and the key, so a collision decrypts cleanly.

Two signatures produced with the same nonces `(d, e)` but different messages leak the secret share by the standard Schnorr/FROST argument: each share is `s_i = d + e·ρ_i + λ_i·s·c`; with `(d, e)` fixed and `(ρ, λ, c)` differing across sessions/messages, `s` is solved from two shares — both of which are broadcast publicly as `DkgConfirmed`/`confirmation_share` data on tributary.

### Impact Explanation
Recovery of `self.key` — the coordinator validator's Ristretto private key used for all MuSig confirmations of DKG results (`set_keys` authorizations on Substrate). A recovered key lets an attacker forge DKG confirmation signatures / impersonate the validator in the confirmation MuSig for that set and any set reusing the key. The FROST library itself documents that cached-preprocess reuse "will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`, `spec/cryptography/FROST.md:51-55`), and the coordinator explicitly encrypts the cache because "recovery of it will enable recovering the private key" (`signing_protocol.rs:104-106`) — yet the reuse-prevention depends entirely on the context key being unique per actual signing operation, which it is not.

### Likelihood Explanation
Within a single attempt, `share()` (via `generated_key_pair`, `handle.rs:47-60`) and `complete()` (via `DkgConfirmed` accumulation, `handle.rs:526-535`) both call `share_internal` → `preprocess_internal`, but with identical `ConfirmationNonces` and `key_pair`, producing an identical (harmless) share. The collision becomes exploitable when a second *distinct* signing operation reuses the same `(b"DkgConfirmer", attempt)` key:

1. Cross-session: a new validator set/session runs DKG attempt `0` (or any matching attempt number) on the same coordinator DB. The `CachedPreprocesses` table is namespaced only by `b"Cached Preprocess Encryption Key" + context`, with no session/genesis field — the stale seed is loaded and its nonces reused against a different `set_keys_message`. Any observer of both confirmation shares (all tributary data is public) recovers the key.
2. Same-attempt re-key: `generated_key_pair` unconditionally overwrites `DkgKeyPair` and calls `share` again (`handle.rs:53-59`). If key generation for an attempt is re-run (e.g., after blame/share invalidation produces a different `KeyPair` under the same attempt number, or the processor re-invokes it), a second, different `msg` is signed with the same nonces — directly leaking the share.

The trigger requires no collusion threshold, no malicious node software on the victim, and only public tributary data to exploit; the required condition is a retry/re-session edge case which the protocol's re-attempt machinery (`ReattemptDb::schedule_reattempt`, `handle.rs:129`) makes realistic, though I could not fully verify whether the attempt counter is always bumped before any second `generated_key_pair`/new-session call — that is the residual uncertainty in this finding.

### Recommendation
Bind the full signing context into the cache key: include `self.spec.set()` (or `spec.genesis()`), the `removed` set hash, and the digest of the message/participant set in `context` (e.g. `(b"DkgConfirmer", genesis, session, attempt, msg_hash)`), and include the same fields in the encryption-key preimage. Additionally, treat reuse as fatal rather than silently reusing: track that a cached preprocess has been consumed by `sign` and refuse a second `sign`/`share` under the same context (the FROST API documents the preprocess "MUST only be used once" but enforcement is left to the caller). Alternatively, delete the `CachedPreprocesses` entry after a successful `share_internal` rather than leaving it for `complete` to re-derive (re-derive cost is negligible).
