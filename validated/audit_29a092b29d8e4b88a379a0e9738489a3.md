## Analog Found

### Title
`instance()` fallback to `address(this)` for unregistered chains allows forged cross-chain RedeemEscrow/RefundEscrow authentication - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core issue is trusting a **mutable, unpinned reference** (a movable tag / mutable Docker image reference) instead of requiring an explicit, immutable pin — allowing a swapped-in value to be silently accepted as trusted. `evm/tron/contracts/apps/IntentGatewayV2.sol` contains a direct on-chain analog: the gateway's peer-authentication lookup, `instance()`, does not require a chain's peer gateway address to be explicitly pinned. When no explicit deployment has been registered for a given source `stateMachineId`, it silently falls back to trusting `address(this)` as the peer, rather than rejecting the unpinned reference.

### Finding Description
`instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` resolves the trusted peer gateway for a given source chain: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

`authenticate()` gates the acceptance of `RedeemEscrow`/`RefundEscrow` withdrawal messages: [2](#0-1) 

For any `stateMachineId` that governance has not yet pinned via `NewDeployment` (i.e., `_instances[keccak256(stateMachineId)] == address(0)`), `instance()` returns `address(this)` instead of reverting. Because `IntentGatewayV2` is deployed at a deterministic CREATE2 address by design (the contract explicitly documents that its address must be "identical across chains under deterministic CREATE2"), this fallback is not a benign default — it means **any chain that Hyperbridge's ISMP host already recognizes as a valid, consensus-proven state machine, but on which IntentGatewayV2 has not yet been officially deployed**, is implicitly treated as pinned to `address(this)`.

Because CREATE2 deployment via the standard deterministic deployer proxy is permissionless, an attacker can deploy the identical, publicly-known `IntentGatewayV2` bytecode to that same deterministic address on the not-yet-onboarded chain themselves, before the protocol does. Since nobody has initialized it yet, the attacker calls `initialize`/`setParams` and fully controls this instance (including which "host" it trusts). They then dispatch a `RequestKind.RefundEscrow`/`RedeemEscrow` message from this self-controlled instance. Because the message's `from` field equals `address(this)` (the deterministic address, matching what `instance()` on the honest destination-chain contract will fall back to for that unregistered source), `authenticate()` treats it as coming from a "known instance" and accepts it — despite the peer never having been pinned by protocol governance.

This is the direct analog of the report's core flaw: trusting a value ("the peer for this state machine") that was never explicitly, immutably pinned, and silently accepting a substitute reference (here, "no explicit peer ⇒ trust myself") instead of failing closed.

Notably, the newer/hardened sibling contract explicitly documents the corrected behavior — confirming this fallback pattern is recognized internally as unsafe and has been fixed there but not in the `tron` variant: [3](#0-2) 

```
* One-time init ... Registers the initial cross-chain peers ...; `_instance` reverts with
* `UnknownInstance` for any chain not registered here or later via `onAccept` governance.
```

### Impact Explanation
A successful forged `RedeemEscrow`/`RefundEscrow` message reaches `withdraw()`, which marks the order `_filled` and transfers the escrowed tokens to an attacker-chosen `beneficiary`: [4](#0-3) 

This is direct fund loss/theft from the gateway's escrow — matching the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories, since the destination gateway ends up trusting a message from a peer that was never legitimately pinned by governance.

### Likelihood Explanation
Exploitation does not require a malicious relayer, prover, or governance actor, nor a leaked key — it only requires:
1. A chain that Hyperbridge's ISMP infrastructure already accepts as a valid, consensus-proven state machine.
2. IntentGatewayV2 not yet formally deployed/registered as a peer on that chain (a normal, temporary state during any phased multi-chain rollout).
3. Permissionless CREATE2 redeployment of the public `IntentGatewayV2` bytecode at the deterministic address, which is exactly the deployment mechanism the protocol itself documents and relies on.

Because rollout is inherently staged (new chains get consensus support before every app registers every peer), this window is realistic and repeatable for every not-yet-registered chain, not merely a theoretical corner case.

### Recommendation
- **Short term**: Change `instance()` to revert (e.g. `UnknownInstance`) when `_instances[keccak256(stateMachineId)] == address(0)`, exactly matching the pattern already implemented in `evm/src/apps/intentsv2/IntentsBase.sol`. Never fall back to trusting an unpinned/implicit peer.
- **Long term**: Audit all other `mapping(bytes32 => address)`-style peer/module lookups across the codebase (e.g., LayerZero endpoint's `_eidToStateMachine`, token gateway contract mappings) for similar "default to self/zero-check bypass" fallback patterns, and require explicit, governance-pinned entries with fail-closed defaults everywhere peer authentication is derived from an unpinned key.

### Proof of Concept
1. Hyperbridge's ISMP host onboards Chain X (valid consensus client + state commitments), but governance has not yet called `NewDeployment` to register an `IntentGatewayV2` peer for Chain X on Chain A (`_instances[keccak256("X")] == address(0)` on Chain A's gateway).
2. Attacker uses the public deterministic CREATE2 deployer to deploy the identical, open-source `IntentGatewayV2` bytecode at the same deterministic address on Chain X (nobody else has deployed there yet).
3. Attacker calls `initialize`/`setParams` on their self-deployed instance, pointing `host` at a host contract of their choosing.
4. Attacker crafts and dispatches a `RequestKind.RefundEscrow` message from their Chain X instance targeting a real, escrowed order commitment on Chain A's `IntentGatewayV2`, with `beneficiary` set to an attacker-controlled address.
5. The message is delivered and proven via a legitimate ISMP proof for Chain X (consensus for X is real; only the peer-pinning for the app is missing).
6. On Chain A, `onAccept` → `authenticate(request)` computes `instance(request.source="X")`; since `_instances[keccak256("X")] == 0`, it returns `address(this)`, which equals `request.from` (the deterministic self-deployed address on X) → authentication passes.
7. `withdraw()` releases the escrowed tokens for the referenced commitment to the attacker's `beneficiary`.
