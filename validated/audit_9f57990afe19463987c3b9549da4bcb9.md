### Title
Unprivileged blame accusation causes panic via unregistered-participant HashMap indexing in PedPoP blame handling - (crypto/dkg/pedpop/src/encryption.rs)

### Summary
The kernel bug class is a registry inconsistency: an entry is attached to a global list, a later init step fails, and the stale entry causes a panic on the next use. The PedPoP blame path exhibits the same class in mirror image: `Decryption::decrypt_with_proof` unconditionally indexes `self.enc_keys[&decryptor]`, assuming every `decryptor` named in a blame statement was registered. Registration is attacker-influenced and incomplete — a party's own index is never inserted into `enc_keys`, and `AdditionalBlameMachine` callers can be asked to evaluate accusations naming arbitrary `Participant` indexes. A fabricated accusation therefore hits a `HashMap` index panic, crashing the process evaluating blame.

### Finding Description
`Decryption::register` inserts an encryption key per participant only when that participant's round-1 `EncryptionKeyMessage` is processed (`verify_r1` registers only counterparties present in `commitment_msgs`, never `self.params.i()`), and `AdditionalBlameMachine::new` registers only `1..=n`. In `decrypt_with_proof`, once the attacker-controllable `msg.pop` verifies — trivially satisfiable since the accuser constructs `msg` and its PoK themselves — the code evaluates `self.enc_keys[&decryptor]` as an argument to `dleq.verify` before any range/membership check on `decryptor`.

Reachable paths:
- `BlameMachine::blame(sender, recipient, msg, proof)` → `blame_internal` → `decrypt_with_proof(sender, recipient, msg, proof)`. If `recipient == params.i()` (the local party, whose key is never in `enc_keys`), the index panics. A malicious DKG participant can file such an accusation to abort a processor evaluating blame.
- `AdditionalBlameMachine::blame(sender, recipient, ...)` — explicitly designed for non-members evaluating third-party blame — panics for any `recipient > n` or unregistered index.
- Secondarily, `blame_internal` reaches `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` after successful decryption; an out-of-range `sender` panics identically.

### Impact Explanation
Any DKG participant (or any party able to submit an accusation to an `AdditionalBlameMachine` holder) can deterministically crash the blame-evaluation path with a single crafted message, exactly the availability-only panic profile of CVE-2022-50414 (CVSS 5.5, A:H). This turns the blame mechanism — meant to identify faulty parties — into a kill switch: an accused faulty party can crash nodes evaluating the accusation, preventing completion/blame adjudication of the DKG and denying key generation.

### Likelihood Explanation
Trigger requires only submitting a blame statement with an unregistered `recipient` (or `sender`), plus a self-consistent PoP signature the attacker generates freely (the PoK binds `from` and `msg`, both attacker-chosen; it does not prove `recipient` was registered). No secret knowledge, collusion, or privileged position is needed — the accuser role is exactly the unprivileged-input surface named in the rules (`EncryptedMessage::read`, `EncryptionKeyProof::read` feed attacker bytes into `blame`/`complete` APIs). Likelihood depends on how callers gate accusations, which is outside these crates, hence Medium rather than High.

### Recommendation
Validate `sender` and `recipient` against the registered participant set before indexing: replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `get`/`ok_or`-style lookups returning `DecryptionError`/`PedPoPError`, treating an unregistered party as an invalid accusation rather than a panic. Optionally have `blame` return `Result`/`Option` for malformed accusations. Registering the local party's own `enc_pub_key` under its own index would also remove the `recipient == i` asymmetry.

### Proof of Concept
```rust
// In a PedPoP DKG where we are participant i, or via AdditionalBlameMachine for any context:
// 1. Attacker fabricates an EncryptedMessage: pick k, K = G*k, sign PoP for
//    pop_challenge(context, R, K, sender, ciphertext). All fields attacker-chosen, so the
//    PoP verifies.
// 2. Build any EncryptionKeyProof { key, dleq } — its contents are irrelevant.
// 3. Submit blame(sender, recipient, msg, Some(proof)) with:
//    - recipient == victim's own Participant i (BlameMachine path), or
//    - recipient == Participant::new(n + 1) or any index not in 1..=n (AdditionalBlameMachine).
// 4. In decrypt_with_proof, msg.pop.verify passes, then evaluation of
//    self.enc_keys[&decryptor] panics (indexing an absent key) before the DLEq is even checked.
// Equivalently, after a fully valid decryption, self.commitments[&sender] with sender > n
// panics in blame_internal.
```

Uncertainty note: whether downstream processor code lets an arbitrary party trigger `blame`/`AdditionalBlameMachine::blame` with fully attacker-controlled `sender`/`recipient` values is outside the in-scope crates, so real-world reachability is probable but not confirmed end-to-end.
