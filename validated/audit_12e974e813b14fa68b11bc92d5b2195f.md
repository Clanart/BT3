### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/fee calculation, producing transactions that underpay the required fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Serai analog of "a fee quantity is computed but never actually charged/applied" lives in `networks/bitcoin/src/wallet/send.rs`. When a `data` payload is supplied, an OP_RETURN `TxOut` is pushed onto the transaction, but both fee-estimation calls to `calculate_weight_vbytes` are made with only `payments` — the data output's weight is never included in `vbytes`, so `needed_fee` and `fee_with_change` are computed for a smaller transaction than the one actually built and signed.

### Finding Description
`SignableTransaction::new` appends the OP_RETURN output to `tx_outs` before the fee is calculated:

- `networks/bitcoin/src/wallet/send.rs:193-202` pushes the data output into `tx_outs`.
- `networks/bitcoin/src/wallet/send.rs:204` computes `(weight, vbytes)` via `calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` does not contain the data output.
- `networks/bitcoin/src/wallet/send.rs:206` sets `needed_fee = fee_per_vbyte * vbytes` on this under-counted size.
- `networks/bitcoin/src/wallet/send.rs:211` validates the minimum relay fee against the same under-counted `vbytes`.
- `networks/bitcoin/src/wallet/send.rs:225-227` repeats the omission when sizing the transaction with change (`fee_with_change`).

`calculate_weight_vbytes` (send.rs:62-99) builds a template transaction only from `payments` plus optional change, so a caller supplying up to 80 bytes of `data` (allowed by the `TooMuchData` check at line 171) produces a signed transaction whose real vsize is larger than what every fee check assumed. The exact same class as the reference bug: the code retrieves/computes the parameters needed to charge the correct amount, then silently fails to apply it to the value actually transferred.

### Impact Explanation
- The fee-difference leftover (`input_sat - payment_sat - change`) still goes to miners, but `needed_fee()` and the `TooLowFee`/`NotEnoughFunds` gates all assume a smaller transaction. A caller can pass the `NotEnoughFunds` check and produce a transaction whose *effective* fee rate is below `fee_per_vbyte`, and potentially below `DEFAULT_MIN_RELAY_TX_FEE`, since the real size is never checked after adding the ~93-weight-unit OP_RETURN output. The result is a signed transaction that will not relay/confirm — funds committed to it are effectively stuck (an under-fee ancestor with no RBF hooks here).
- `needed_fee()` is a public getter used by integrators to budget inputs; it returns a systematically low value whenever `data` is set.

### Likelihood Explanation
Reachable by any unprivileged caller of the public `SignableTransaction::new` API with a non-`None` `data` argument (up to 80 bytes is explicitly permitted). The miscalculation is deterministic, not edge-case-dependent; every data-bearing transaction is under-charged by `fee_per_vbyte` × (OP_RETURN output vsize). Severity is bounded because the excess input value still becomes fee, and the in-repo processor currently passes `data: None` — hence Medium rather than High.

### Recommendation
Include the data output in the size estimation. Either pass the final `tx_outs` (or a synthesized `(op_return_script, 0)` payment entry) into `calculate_weight_vbytes`, or add `data` as a parameter so both the initial `vbytes` and the `vbytes_with_change` computations account for the OP_RETURN output before `needed_fee`, the `TooLowFee` check, and `NotEnoughFunds` are evaluated.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Conceptual: any caller doing
let st = SignableTransaction::new(
    inputs,            // sum = payment + needed_fee (no slack)
    &payments,
    change,
    Some(vec![0u8; 80]), // permitted: <= 80 bytes
    fee_per_vbyte,
)?;
// st.needed_fee() == fee_per_vbyte * vbytes_without_opreturn
// but st's serialized size is larger by the OP_RETURN output
// (~8 value + ~83 script + overhead weight units).
// Actual fee = inputs - outputs = needed_fee, which is
// fee_per_vbyte * (real_vbytes - opret_vbytes) < intended fee,
// and can fall under DEFAULT_MIN_RELAY_TX_FEE without the
// TooLowFee check ever seeing the real vsize.
```
The defect is visible directly at `networks/bitcoin/src/wallet/send.rs:193-227`: `tx_outs` gains an output that `calculate_weight_vbytes` (called with `payments`, not `tx_outs`) never measures.
