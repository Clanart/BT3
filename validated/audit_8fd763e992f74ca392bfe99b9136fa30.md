### Title
Ungoverned `kip71.gastarget` value of `0` causes division-by-zero panic in `NextMagmaBlockBaseFee`, halting block validation/production - (File: params/kip71_config.go)

### Summary
The KIP-71 base-fee governance parameters (`kip71.gastarget`, `kip71.basefeedenominator`, `kip71.maxblockgasusedforbasefee`) are voted on and ratified through the on-chain governance mechanism (`header.Vote` / `header.Governance`) with no lower-bound (non-zero) validation, analogous to the reported Notional issue where `maxOracleFreshnessInSeconds` could be set to `0` by an admin with no bound checks to disrupt a core financial computation.

### Finding Description
`Kip71GasTarget` is registered with `FormatChecker: noopFormatChecker`, meaning any `uint64` value including `0` passes format validation when a vote is created via `NewVoteData`/`NewGovData`. [1](#0-0) 

The consistency check performed on ratified votes (`checkConsistency`) explicitly treats `Kip71GasTarget` (along with `Kip71BaseFeeDenominator` and `Kip71MaxBlockGasUsedForBaseFee`) as requiring no further validation, simply returning `nil`. [2](#0-1) 

This contrasts with `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which do have cross-parameter bound checks. [3](#0-2) 

In `NextMagmaBlockBaseFee`, the code explicitly guards `BaseFeeDenominator == 0` (defaulting to `64` "to avoid panic"), but performs **no equivalent guard for `GasTarget == 0`**: [4](#0-3) 

When `parentGasUsed > gasTarget` (true whenever `gasTarget == 0` and any gas was used), the code computes:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))  // gasTarget == 0 => division by zero panic
``` [5](#0-4) 

`big.Int.Div` panics with "division by zero" when the divisor is zero. This function is invoked from `VerifyMagmaHeader`, which is called during block header validation in `blockchain/block_validator.go`, and also during block assembly in `work/worker.go` and gas price suggestion in `node/cn/gasprice/gasprice.go`. [6](#0-5) 

### Impact Explanation
Once `kip71.gastarget` is ratified to `0` (via governance vote, reachable through the standard governance voting transaction/API flow that any governing-node-authorized voter can submit and any node processes deterministically from block headers), every node computing `NextMagmaBlockBaseFee` for a block whose parent used any gas will panic. This affects block validators (`block_validator.go`), block proposers (`work/worker.go`), and RPC gas price/fee-history estimators (`node/cn/gasprice`) uniformly, since it is a deterministic, network-wide parameter — causing a full network halt (denial of block production/validation) rather than a localized node crash. This is a governance-parameter-triggered chain halt reachable by any transaction/vote submitted to the governance parameter subsystem, matching the whitelisted "governance parameters" and "state transition and gas/burn accounting" attack surfaces.

### Likelihood Explanation
The path requires a ratified governance vote setting `kip71.gastarget` to `0`. This is the same class of issue as the reported bug (an authorized-but-unvalidated parameter setter lacking bounds checks), and the codebase already demonstrates awareness of this exact hazard for the sibling parameter `BaseFeeDenominator` (explicit `== 0` guard "to avoid panic") but omits the same guard for `GasTarget`, indicating an overlooked edge case rather than a deliberately accepted risk.

### Recommendation
Add a zero-guard for `GasTarget` symmetric to the existing `BaseFeeDenominator` handling in `NextMagmaBlockBaseFee` (e.g., treat `0` as an invalid/default value), and/or add a `FormatChecker` for `Kip71GasTarget` (and `Kip71MaxBlockGasUsedForBaseFee`) in `kaiax/gov/param.go` rejecting `0`, plus add a corresponding case in `checkConsistency` in `kaiax/gov/headergov/impl/header.go` to reject votes setting these to `0` before ratification.

### Proof of Concept
1. A governing-node-authorized account submits a `governance_vote` transaction/API call setting `kip71.gastarget = 0`. [1](#0-0) 
2. The vote is ratified at the next epoch boundary per the standard governance ratification flow (no consistency check rejects it, see `checkConsistency` default branch). [2](#0-1) 
3. At the next block after ratification where `parentHeaderGasUsed > 0`, any node calling `NextMagmaBlockBaseFee` (during header verification, block assembly, or gas price estimation) hits `x.Div(x, new(big.Int).SetUint64(0))` and panics. [5](#0-4) 
4. Because this function is invoked from the block validation path (`VerifyMagmaHeader`), the panic occurs deterministically on every full node processing the new block, halting the chain.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
