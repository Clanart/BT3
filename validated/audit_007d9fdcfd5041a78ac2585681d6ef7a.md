Synthetic ERC20 `Transfer` events for CW20↔ERC20 pointers report the nominal message amount instead of the actual balance delta, allowing fee-on-transfer/deflationary CW20 tokens to spoof log-based accounting - ([File: app/receipt.go])

### Summary
Sei's dual-VM pointer system generates synthetic ERC20 `Transfer`/`Approval` EVM logs whenever a CW20 token with a registered ERC20 pointer is transferred via CosmWasm. The log's `amount` (topic data) is taken directly from the wasm event's declared `amount` attribute, not from an actual before/after balance comparison. Any CosmWasm user can deploy an arbitrary CW20 contract (with fee-on-transfer, deflationary-burn, or rebasing logic) and register/obtain an ERC20 pointer for it, then execute transfers whose synthetic `Transfer` log amount does not match the real balance change recorded by the CW20 contract.

### Finding Description
When a wasm transaction touches a CW20 contract that has an ERC20 pointer, `app.AddCosmosEventsToEVMReceiptIfApplicable` calls `translateCW20Event`, which scans the wasm module's emitted actions and, for `mint`, `burn`, `send`, `transfer`, `transfer_from`, `send_from`, `burn_from` actions, unconditionally emits a synthetic `Transfer` log using `action.Amount` — the amount declared in the CW20 message/event itself: [1](#0-0) 

This is analogous to the reported bug class: the contract assumes the declared/requested transfer amount is what was actually moved, without verifying the amount against the real state change (e.g., recipient/sender balance deltas). A CW20 contract is arbitrary CosmWasm code — nothing in the pointer/registration flow (`SetERC20CW20Pointer`) restricts the CW20 implementation to a standard, fee-free `transfer` semantics: [2](#0-1) 

Meanwhile, the ERC20 pointer's own `balanceOf`/`totalSupply` are live proxy queries into the CW20 contract (correctly reflecting true balances): [3](#0-2) 

but any downstream EVM consumer that watches/relies on the synthetic `Transfer` event's `amount` field (e.g., via `eth_getLogs`, indexers, or an EVM contract crediting deposits/shares based on observed log amounts rather than re-querying `balanceOf` before/after) would be fed the *nominal* amount declared in the CW20 message, not the actual, possibly fee-reduced, balance change. This is the same "declared/expected value ≠ actually transferred value" data-validation gap described in the external report, just manifesting at the synthetic cross-VM event-translation layer instead of inside a custodian's `_deposit`/`_withdraw`.

### Impact Explanation
If any EVM-side contract or bridge logic (built by third-party dApps on Sei, but reachable purely through the platform's own pointer/log-translation mechanism) trusts the amount reported in the pointer's synthetic `Transfer` log to credit balances, shares, or settle transfers (a common integration pattern for token bridges/vaults that watch `Transfer` events instead of doing a live `balanceOf` diff), an attacker can deploy a CW20 token with a fee-on-transfer or deflationary mechanism, register (or use) its ERC20 pointer, and cause the reported transferred amount to diverge from the true balance change. This can be leveraged to over-credit deposits or under-report withdrawals in any protocol relying on this log data, i.e., unauthorized value creation/fund loss via the pointer mechanism.

### Likelihood Explanation
Reachable by any CosmWasm user: deploying a custom CW20 contract and pointer, and executing standard CW20 messages (`transfer`, `transfer_from`, `send`, etc.), is entirely permissionless. No validator, governance, or privileged access is required. However, actual exploitation requires a downstream consumer (bridge/vault/DEX) that trusts synthetic log amounts rather than independently verifying balances, which is an assumption about ecosystem integrations rather than a guaranteed core-chain state corruption.

### Recommendation
- Short-term: In `translateCW20Event` (and its CW721/CW1155 counterparts), compute the synthetic `Transfer`/`TransferSingle` amount from an actual balance delta (query the CW20 contract balance before and after the action) rather than trusting the wasm-emitted `amount` attribute, mirroring the report's short-term recommendation to check custodian/contract balances during transfers rather than assuming nominal amounts.
- Long-term: Document and enforce that pointer-eligible CW20/CW721/CW1155 contracts must implement standard, fee-free, non-rebasing transfer semantics (or explicitly flag/reject pointer creation for tokens that don't), and audit all synthetic-log generation code paths for the same "declared amount == actual amount" assumption per the token integration checklist referenced in the original report.

### Proof of Concept
1. Deploy a CW20 contract (via `wasm store`/`instantiate`) whose `ExecuteMsg::Transfer` handler burns/deducts a fee, e.g., moves `amount` from sender but credits only `amount - fee` to the recipient, while still emitting the standard CW20 `wasm` event with the full nominal `amount` attribute (standard CW20 event emission macros report the message's `amount`, not the effective credited amount).
2. Register an ERC20 pointer for this CW20 contract via `deployErc20PointerForCw20`/`registerPointerForERC20` (permissionless).
3. Execute a `transfer` message on the CW20 contract for `amount = 100`.
4. Observe via `eth_getLogs`/`eth_getTransactionReceipt` that the synthetic `Transfer(from, to, 100)` log is emitted (per `translateCW20Event`'s use of `action.Amount`), while querying `pointer.balanceOf(recipient)` before/after shows an actual increase of less than 100 (e.g., 95) due to the fee — demonstrating the log-reported amount diverges from the real balance change that any log-trusting consumer would observe.

// ERC20 -> CW20
func (k *Keeper) SetERC20CW20PointerWithVersion(ctx sdk.Context, cw20Address string, addr common.Address, version uint16) error {
	if k.cwAddressIsPointer(ctx, cw20Address) {
		return ErrorPointerToPointerNotAllowed
	}
	err := k.setPointerInfo(ctx, types.PointerERC20CW20Key(cw20Address), addr[:], version)
	if err != nil {
		return err
	}
	return k.setPointerInfo(ctx, types.PointerReverseRegistryKey(addr), []byte(cw20Address), version)
}
