### Title
`SignableTransaction` fee/change calculation omits the OP_RETURN output's weight, over-crediting change and underpaying the intended fee — (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
The audit finding describes a formula which computes a payout as `total deposits + premiums` without subtracting terms that must be accounted for (`locked capital`, `default payouts`), producing an over-credited claimable amount. The same bug class — a value computed without subtracting a required term — exists in `SignableTransaction::new`: when a `data` payload is supplied, the OP_RETURN output is appended to `tx_outs` but is never included in the weight/vbytes calculation used to derive the fee and the change amount. The change output is therefore credited more than it should be, and the real fee paid is lower than `fee_per_vbyte` specifies — the missing-term analog of the Carapace issue.

### Finding Description
`SignableTransaction::new` builds the payment outputs, then pushes an OP_RETURN `TxOut` onto `tx_outs` when `data` is provided (`send.rs` lines 194–202). However, both fee estimations call `calculate_weight_vbytes(tx_ins.len(), payments, ...)` where `payments` is the caller-supplied `&[(ScriptBuf, u64)]` slice — it never contains the OP_RETURN output:

- `networks/bitcoin/src/wallet/send.rs:204`: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` → `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed for a transaction that is up to ~90 vbytes smaller than the real one.
- `networks/bitcoin/src/wallet/send.rs:225-228`: `fee_with_change` is computed from the same `payments` slice, and `change` is set to `input_sat - payment_sat - fee_with_change` (line 228), so the change output absorbs the entire weight cost of the OP_RETURN output instead of the fee.

Additionally, the minimum-relay-fee gate at lines 211–213 checks `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the undercounted `vbytes`. A transaction that nominally passes this check can actually pay a fee rate below the relay minimum once the real (larger) transaction is serialized and signed. The net effect: `needed_fee`/`fee()` report one fee while the signed transaction pays less, and the change output — which the OP_RETURN data was supposed to be funded by — is inflated, exactly the "subtraction never performed" shape of the source bug.

### Impact Explanation
Any `SignableTransaction` constructed with `data` pays an effective fee rate strictly below the requested `fee_per_vbyte`, by `fee_per_vbyte * (OP_RETURN output vbytes)`. For fee rates near the relay minimum, the produced transaction can be rejected by Bitcoin nodes (`min relay fee not met`), so the signed transaction cannot be broadcast: the burn/rotation it represents stalls and the inputs must be re-planned. Even when relayable, the change output is systematically over-credited and the wallet's fee accounting (`needed_fee`, `fee`) misreports the cost — the same "reported amount ≠ amount actually required by the obligation" misaccounting as the audit finding.

### Likelihood Explanation
The defect is deterministic: it triggers on every call to `SignableTransaction::new` that passes a non-`None` `data` argument together with `change`, requiring no attacker sophistication beyond supplying the payload that causes the OP_RETURN output to be added. The magnitude is bounded by the 80-byte data cap (checked at line 171), so the fee shortfall is `fee_per_vbyte * ~80–95` vbytes — small per transaction but sufficient to drop borderline transactions below relay policy.

### Recommendation
Include the OP_RETURN output (and any other outputs actually appended to `tx_outs`) in the weight/vbytes estimate. Compute `calculate_weight_vbytes` over the full `tx_outs` list rather than the `payments` slice — e.g., build the template `Transaction` from `tx_outs` (payments + OP_RETURN) before measuring, both for the no-change and with-change estimates at lines 204 and 225–227. Then re-check `needed_fee` against the corrected `vbytes`.

### Proof of Concept
```rust
// networks/bitcoin context
// Construct inputs with input_sat = payment_sat + fee + DUST so change is created.
let payments = vec![(dest_script, 10_000)];
let data = vec![0u8; 80]; // max allowed by the TooMuchData check
let stx = SignableTransaction::new(inputs, &payments, Some(change_script), Some(data), 1).unwrap();

// stx.needed_fee() was computed as fee_per_vbyte * vbytes(tx without OP_RETURN).
// The serialized stx.transaction() includes the ~90-vbyte OP_RETURN output,
// so actual fee rate = fee() / real_vbytes < 1 sat/vbyte requested.
// With fee_per_vbyte chosen so needed_fee == min relay for the undercounted size,
// the signed tx is rejected by bitcoind for insufficient fee, and the change
// output is ~90 sats larger than it should be.
```
The core defect is visible directly in the source: `tx_outs` gains the OP_RETURN `TxOut` at `send.rs:194-202`, while the fee and change math at `send.rs:204-228` only ever measures `payments`, so the added output's cost is never subtracted — the same missing-subtraction structure as the reference finding.
