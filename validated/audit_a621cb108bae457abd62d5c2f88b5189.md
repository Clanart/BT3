## Finding

### Title
Windows trailing-dot/space filename bypasses `isSafeFileExtension` extension safelist, enabling execution of a repo-supplied `.exe` via "Open with default program" - (File: `app/src/ui/lib/context-menu.ts`)

### Summary
`isSafeFileExtension` performs an exact string comparison of `Path.extname(file.path).toLowerCase()` against a fixed list `['.cmd', '.exe', '.bat', '.sh']` using `Array.prototype.indexOf`. Node's `path.extname` does not normalize trailing dots, trailing spaces, or NTFS Alternate Data Stream (`:stream`) suffixes, so a git-tracked filename like `payload.exe.` or `payload.exe ` produces an extname of `.` or `.exe ` instead of `.exe`, which never matches the blocklist. On Windows, the filesystem/Win32 layer strips trailing dots and spaces when the file is actually written to disk, so the resulting file is a real `payload.exe`, while GitHub Desktop's UI/menu logic still evaluates safety against the untrimmed git path.

Callers compute the `extension` argument with `Path.extname(path)` where `path` is `file.path` — the git-tracked working-directory path — not a value derived from resolving the real file on disk: [3](#0-2) 

The result gates whether the "Open with default program" menu item is `enabled`: [4](#0-3) 

Clicking that item calls `onOpenItem(path)`, which ultimately reaches `openFile`, which calls `shell.openExternal('file://' + fullPath)`: [5](#0-4) 

Node's `path.extname` algorithm returns the substring starting at the *last* `.` through the end of the basename, with no trimming of trailing `.`/space characters. For `'payload.exe.'` this yields `'.'` (not `.exe`); for `'payload.exe '` this yields `'.exe '` (with the trailing space, not exactly `.exe`). Neither matches an entry in `RestrictedFileExtensions` via exact `indexOf` comparison, so `isSafeFileExtension` incorrectly returns `true`.

Separately, it is well documented behavior of the Windows kernel/NTFS path-normalization layer (inherited from legacy DOS 8.3 compatibility) that trailing dots and trailing spaces in a requested filename are silently stripped when the file is actually created/opened via the Win32 API. This means a file committed to a repository as `payload.exe.` will, once checked out on a Windows working copy, physically exist on disk as `payload.exe` — a genuine executable — even though GitHub Desktop's UI/model still tracks/reports the path with the trailing dot (as recorded by git).

### Impact Explanation
An attacker who controls a repository's contents (a clone/fetch target) can commit a file named e.g. `malware.exe.` or `malware.exe ` at the working-directory level. When the victim opens Changes/History in GitHub Desktop and views this file, `isSafeFileExtension` will incorrectly mark it "safe," enabling the "Open with default program" context menu entry. If the victim clicks it (a normal, expected interaction offered by the application's own UI, not an unnatural step), Desktop calls `shell.openExternal('file://...')`, and Windows resolves/launches the physical `payload.exe` file, executing attacker-controlled code on the victim's machine. This is code execution triggered by attacker-controlled repository content via a single, application-sanctioned click, which fits the "Valid Impact" scope (repository content leading to code execution).

### Likelihood Explanation
Moderate. The attacker must get the victim to clone/fetch a repository containing the specially-named file and then manually invoke "Open with default program" from Desktop's context menu on that specific file. No admin/local access or pre-existing malware is required, and the extension check that is supposed to prevent exactly this scenario is trivially bypassed by a filename quirk that is easy to reproduce (append a `.` or a trailing space to `.exe`/`.cmd`/`.bat`/`.sh`).

### Recommendation
Do not rely on exact string matching of `Path.extname` output against a literal blocklist. Instead:
- Trim trailing dots/spaces (and strip any `:stream` ADS suffix) from the path before computing/comparing the extension on Windows, mirroring how the Win32 filesystem layer will normalize the name.
- Alternatively, resolve the extension from the real file that will actually be opened (e.g., via `fs.realpathSync`/`fs.statSync` on the resolved path) rather than from the raw git-tracked path string.
- Consider validating using a more robust check (e.g., regex requiring the extension to be the literal terminal token with no additional trailing characters) rather than `indexOf` equality against untrimmed input.

### Proof of Concept
1. In a test repository, on a machine (or via a manifest/tree entry) create/commit a file whose git path is `payload.exe.` (trailing dot) or `payload.exe ` (trailing space) containing a valid PE executable payload.
2. Clone/fetch this repository with GitHub Desktop on Windows; check out the branch so the file lands in the working directory. (Windows strips the trailing dot/space when actually creating the file, so the file on disk becomes `payload.exe`.)
3. In the Changes list, right-click the file and observe that `isSafeFileExtension(Path.extname('payload.exe.'))` → `isSafeFileExtension('.')` → returns `true`, so "Open with default program" is enabled: [6](#0-5) 
4. Click "Open with default program"; Desktop calls `shell.openExternal('file://<path-to-payload.exe>')` [7](#0-6) , and Windows executes the payload directly (an EXE's own "default handler" is to run it).

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
