### Title
Unbounded `txpool_content`/`txpool_inspect` RPC response amplification enables public-RPC DoS - ([File: api/api_txpool.go])

### Summary
The `txpool` namespace is registered as a **public** RPC module and exposes `Content()` and `Inspect()`, both of which dump *every* pending and queued transaction currently held in the node's mempool with no pagination, size cap, or per-call limit. Any unprivileged public-RPC caller can trigger this by (1) submitting many transactions/large-payload transactions into the pool via `eth_sendRawTransaction`/`kaia_sendRawTransaction`, and (2) repeatedly calling `txpool_content` to force the node to serialize and return the full mempool state. This mirrors the aim advisory's bug class: an attacker fills a large data store, then issues an unrestricted "return everything" query that makes the server unresponsive.

### Finding Description
`TxPoolAPI.Content()` and `TxPoolAPI.Inspect()` iterate over the *entire* `pending`/`queue` maps returned by `s.b.TxPoolContent()` and build nested maps for every single transaction, with no `maxItems`, no pagination, and no context deadline: [1](#0-0) [2](#0-1) 

This is registered on the public `txpool` namespace, reachable by any RPC client (no auth), unlike the `debug` namespace which is explicitly `Public: false` and additionally protected by `HeavyAPIRequestLimit`/`UnsafeDebugDisableFlag`: [3](#0-2) 

By contrast, other data-heavy read APIs in the codebase (e.g. `eth_getLogs`, filter APIs, `debug_traceBlock*`) were explicitly hardened against this exact bug class with `GetLogsMaxItems`/`GetLogsDeadline` caps and a global `HeavyAPIRequestLimit` counter: [4](#0-3) [5](#0-4) [6](#0-5) 

`TxPoolAPI.Content`/`Inspect` received no equivalent protection: it is a straight, unbounded dump of pool state, the exact analog of the aim `Text`-object bulk query DoS — attacker-controlled data volume (mempool size, which the attacker directly grows by broadcasting transactions) combined with an unthrottled "fetch everything" RPC call.

### Impact Explanation
An unprivileged transaction sender can (a) flood the node's mempool with many pending/queued transactions (each transaction can carry up to the node's configured max tx size of calldata) and (b) repeatedly call `txpool_content` (or `txpool_inspect`) over the public RPC/WS endpoint. Each call forces the node to allocate and JSON-marshal a potentially very large nested map (megabytes to tens of megabytes depending on pool occupancy and per-tx payload size), consuming CPU and memory on the single-threaded-ish RPC handling path and blocking/degrading service for all other RPC callers — a denial of service, matching CWE-1049 / the referenced advisory's impact class exactly. This does not cause fund loss or state divergence, but it is a concrete availability impact reachable purely through public RPC by an unprivileged transaction sender/RPC caller.

### Likelihood Explanation
High likelihood: `txpool` is enabled and marked `Public: true` by default in `node/cn/backend.go`; no authentication, gas payment, or special privilege is required to call `txpool_content`/`txpool_inspect` on any RPC-enabled node that exposes the `txpool` module (many operators enable it for monitoring). The attacker fully controls the input size (number/size of transactions submitted) and can trigger the expensive query at will, repeatedly, at negligible cost (transactions just need to enter pending/queued state, not be mined).

### Recommendation
- Cap the number of transactions/accounts returned per `Content()`/`Inspect()` call (analogous to `GetLogsMaxItems`), or require pagination parameters.
- Apply a request-rate limit or the existing `HeavyAPIRequestLimit`-style counter to `txpool_content`/`txpool_inspect`.
- Consider defaulting `txpool` namespace to non-public (IPC-only) similar to the `debug` namespace, letting operators opt in explicitly.
- Add a serialization/response-size ceiling and a context timeout for pool-dumping calls.

### Proof of Concept
1. Start a Kaia node with default config exposing the `txpool` public RPC module over HTTP/WS.
2. As an unprivileged sender, submit a large number of transactions with maximal allowed calldata via `eth_sendRawTransaction` from many nonces/accounts so they sit in `pending`/`queued` state (do not need to be mined; queued/underpriced/future-nonce transactions stay in the pool).
3. Concurrently issue repeated `txpool_content` (or `txpool_inspect`) calls against the public RPC endpoint.
4. Observe RPC server CPU/memory spike and increased latency/unresponsiveness for other concurrent RPC requests, demonstrating the unbounded query-driven DoS.

// Inspect retrieves the content of the transaction pool and flattens it into an
// easily inspectable list.
func (s *TxPoolAPI) Inspect() map[string]map[string]map[string]string {
	content := map[string]map[string]map[string]string{
		"pending": make(map[string]map[string]string),
		"queued":  make(map[string]map[string]string),
	}
	pending, queue := s.b.TxPoolContent()

	// Define a formatter to flatten a transaction into a string
	format := func(tx *types.Transaction) string {
		if to := tx.To(); to != nil {
			return fmt.Sprintf("%s: %v kei + %v gas × %v kei", tx.To().Hex(), tx.Value(), tx.Gas(), tx.GasPrice())
		}
		return fmt.Sprintf("contract creation: %v kei + %v gas × %v kei", tx.Value(), tx.Gas(), tx.GasPrice())
	}
	// Flatten the pending transactions
	for account, txs := range pending {
		dump := make(map[string]string)
		for _, tx := range txs {
			dump[fmt.Sprintf("%d", tx.Nonce())] = format(tx)
		}
		content["pending"][account.Hex()] = dump
	}
	// Flatten the queued transactions
	for account, txs := range queue {
		dump := make(map[string]string)
		for _, tx := range txs {
			dump[fmt.Sprintf("%d", tx.Nonce())] = format(tx)
		}
		content["queued"][account.Hex()] = dump
	}
	return content
