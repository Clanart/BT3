## Title
Attacker-controlled `WWW-Authenticate` realm on a git remote can trick Desktop into disclosing a signed-in GitHub account's token to a non-GitHub host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
The vulnerable pattern in the external report is: a security-relevant flag that should force strict validation (`0x40` checkpointer bit) can be left unset by the *signer/attacker*, causing downstream code to fall back to a permissive default (`_checkpointer == address(0)`, `snapshot.imageHash == 0`) that is then treated as "no constraint" rather than "unverified." The analogous invariant in GitHub Desktop's credential trampoline is: `getEndpointKind()` decides whether a remote endpoint is treated as a trusted GitHub/Enterprise host (in which case the stored GitHub account token is disclosed to it) or a `'generic'` host (handled by the external/generic credential helper). One of the signals used to make that trust decision is attacker-controlled data returned over the wire by the remote itself.

## Finding Description
`getEndpointKind` in [1](#0-0)  classifies a credential request as `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`. Before falling back to an actual network probe (`isGitHubHost`), it inspects the `wwwauth[...]` environment/credential fields that git forwards from the server's HTTP `WWW-Authenticate` response header: [2](#0-1) 

```
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
```

This header is emitted by the remote server, not verified by Desktop, and is used as a "happy path" shortcut specifically to *avoid* making a real network verification request. The comment in the code explicitly frames this as trading verification for convenience — structurally the same trade-off that created the checkpointer bypass in the Solidity report (skip verification when a “trusted-looking” flag is present).

Once `getEndpointKind` returns `'enterprise'` for an attacker-controlled remote, `getCredential` in [3](#0-2)  proceeds:

```
const endpointKind = await getEndpointKind(cred, store)
...
if (endpointKind !== 'generic' && !accounts.some(a => a.endpoint === apiEndpoint)) {
  ... prompt for sign-in ...
}
if (endpointKind !== 'generic') {
  return undefined
}
```

The gating check that limits credential disclosure is `apiEndpoint` matching an existing signed-in account, computed via `getAPIEndpoint(endpoint)`. Because the remote URL itself (host/port) is attacker-controlled but consistently used to derive `apiEndpoint`, a straightforward spoofed-realm header does not by itself make `apiEndpoint` match an *existing* github.com/GHE account entry unless the attacker's remote host string happens to collide with a stored endpoint (e.g. the same GHE hostname a user already authenticated to, reachable via a different port, subdomain-confusable host, or a MITM/proxy sitting in front of a legitimate GHE hostname). In those cases — which are realistic for the threat model of "attacker controls a git remote/proxy response" (e.g. a corporate/GHE-shaped proxy, a subdomain takeover, or a spoofed response while proxying a legitimate GHE URL) — the `wwwauth[...]: realm="GitHub"` trick short-circuits the "make sure this is really GitHub" check (`isGitHubHost`) that would otherwise perform genuine host verification, and Desktop's stored account token is handed to `getCredential` → `credWithAccount` → returned to git for that connection, i.e. sent to the attacker-controlled/proxied endpoint.

The broken invariant, expressed in the same terms as the seed report: a value that should require independent verification (“is this really GitHub?”) is instead accepted from unauthenticated, attacker-supplied protocol data (the `WWW-Authenticate` header), and the code path that would otherwise perform the real check (`isGitHubHost`, an actual outbound verification request) is skipped entirely once the shortcut matches — exactly mirroring how setting bit `0x40` inside the inner chained signature let `_ignoreCheckpointer` skip the real checkpointer call in `BaseSig.sol`.

## Impact Explanation
If successfully triggered against a host that also matches (or can be made to match) an already-authenticated account's `apiEndpoint`, this results in credential/token exfiltration: the user's real GitHub/GHE OAuth token is sent by git (via the credential helper) to a connection the attacker controls or can observe (a malicious/compromised git server, or a network position able to inject the `WWW-Authenticate` header, such as a proxy sitting in front of a real GHE hostname). This matches the report's "credential/token exfiltration" impact category directly.

## Likelihood Explanation
Exploitability is conditional: the attacker must control (or MITM) a remote whose derived `apiEndpoint` coincides with, or is confusable with, an endpoint the victim has already signed into (most plausible for GitHub Enterprise users behind a reverse proxy, custom port, or spoofable subdomain), and must be able to control the `WWW-Authenticate` response header on the HTTP auth challenge for that connection — both are attacker-controllable via "a git remote/proxy response," which is within the valid-impact scope of this exercise. I could not fully verify from the index whether `getAPIEndpoint`/`isDotCom`/`isGHE` add additional strict-origin checks that would block all realistic collision cases (their implementations in `app/src/lib/api.ts` and `app/src/lib/endpoint-capabilities.ts` were only partially visible), so likelihood should be treated as medium rather than confirmed, pending review of those functions and of `isGitHubHost`'s real verification logic.

## Recommendation
Remove or harden the `wwwauth[...]` "happy path" shortcut in `getEndpointKind`: never let an unauthenticated protocol header returned by the remote itself upgrade a connection to `'enterprise'`/GitHub trust without performing the actual `isGitHubHost` verification (or requiring a strict, pre-known endpoint match) first. At minimum, only honor the `realm="GitHub"` header when it corresponds to a remote whose origin already exactly matches a stored account's endpoint (i.e. use it only as a hint to skip enumeration ambiguity, not as a substitute for `isGitHubHost`/known-endpoint verification), and add regression tests simulating a spoofed `WWW-Authenticate: realm="GitHub"` header from a non-GitHub remote to confirm no account token is disclosed.

## Proof of Concept
Conceptual PoC (cannot be fully executed without the running Desktop app/dugite environment, but derivable from the code path):
1. Have a signed-in GHE account in Desktop for `https://ghe.example.com`.
2. Add/clone from a remote whose host resolves to an attacker-controlled server or proxy positioned at a URL that Desktop's `getAPIEndpoint` normalizes to the same `apiEndpoint` as the trusted account (e.g., via an alternate port or a proxy sitting in front of `ghe.example.com`).
3. Configure that server to respond to the HTTPS auth challenge with `WWW-Authenticate: Basic realm="GitHub"`.
4. Trigger a git operation (fetch/push) against that remote; git invokes Desktop's credential helper trampoline, forwarding the `wwwauth[...]` header as part of the credential request (`command.stdin`).
5. `getEndpointKind` matches `v.includes('realm="GitHub"')` and returns `'enterprise'` without calling `isGitHubHost`; `getCredential` finds the matching stored account and returns the account's token via `credWithAccount`, which git then sends to the attacker-controlled endpoint. /** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
