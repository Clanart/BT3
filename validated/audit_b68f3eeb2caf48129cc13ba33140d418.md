### Title
Spoofable "GitHub" web-flow committer badge lets a malicious repo commit impersonate GitHub's official web UI - (File: `app/src/lib/web-flow-committer.ts`)

### Summary
`isWebFlowCommitter()` decides whether a commit was made through GitHub's web UI (e.g. a PR merge button) purely by comparing the commit's plaintext `committer.name`/`committer.email` fields to the strings `'GitHub'`/`'noreply@github.com'` (or `'GitHub Enterprise'` for GHES). These fields come from `git log`/`CommitIdentity.parseIdentity` [1](#0-0) , i.e. from data an attacker fully controls when the user clones/fetches a repository or adds an attacker-controlled remote, since `git commit --author`/`--committer` can set arbitrary strings. There is no GPG/SSH signature check, no comparison against the repository's actual GitHub API committer identity, and no check of the commit's parent/merge structure that would tie it to an actual PR merge.

### Finding Description
`isWebFlowCommitter` treats a commit as GitHub's own web-flow commit purely on a string match of attacker-suppliable identity fields: [2](#0-1) 

These committer values are parsed straight out of `git log` output with a simple regex and no origin verification: [3](#0-2) 

The broken invariant: the value used to answer "was this authored by GitHub the platform" is the same untrusted field that "Transfer" event's `from` value was in the original report — attacker-controlled data being treated as an authoritative claim of origin. Git deliberately allows any committer identity string to be set (`git commit --committer="GitHub <noreply@github.com>"`), so any repository the app clones/fetches, or any commit received via `git fetch`/PR checkout from an untrusted remote, can forge this attribution with zero cost.

`getAvatarUserFromAuthor`/`Avatar` consume the same identity fields without any additional legitimacy check (they only affect avatar image lookup and don't verify provenance either) [4](#0-3) , showing this trust extends beyond a single call site — anywhere Desktop currently renders "authored/committed by GitHub" it is relying purely on the spoofable committer string.

### Impact Explanation
Because Desktop currently has no existing guard against this (no signature verification, no API cross-check), an attacker who controls a cloned/fetched repository can forge a commit whose committer identity is `GitHub <noreply@github.com>` (or `GitHub Enterprise` for a GHES endpoint) to make `isWebFlowCommitter()` return `true`. Any UI surface in Desktop that uses this signal to indicate "this change was made via GitHub's official web merge/edit flow" would then falsely present a malicious, locally-authored commit as if it were vetted/created by GitHub itself. This is a straightforward provenance-spoofing primitive that can be used to social-engineer a reviewer or contributor into trusting an unreviewed commit's content (e.g., thinking a suspicious squash-merge commit was produced automatically by the platform rather than by the attacker), which fits the report's class of "silently corrupting what the user believes about what was committed," since the UI's stated origin of the change does not reflect reality and there is no code path to detect or warn about the mismatch.

### Likelihood Explanation
High likelihood of triggering: any attacker who can get the victim to clone/fetch a repository, add a malicious remote, or fetch a PR branch (all normal, expected user actions in Desktop) can trivially forge these commit-identity strings with a single `git commit --committer` invocation — no special git internals knowledge, no admin rights, no local access to the victim's machine, and no social engineering beyond the repo/PR content itself being examined in Desktop (an in-scope trigger per the task's valid-impact definition).

### Recommendation
- Do not rely solely on plaintext committer name/email strings to assert GitHub-web-flow provenance. Cross-check against the GitHub API's known merge-commit / PR metadata for the repository (e.g., verifying the commit SHA is reported by the API as a PR merge commit), or require a verified/GPG-signed commit whose signer is confirmed as GitHub's known signing key for that endpoint.
- If a purely heuristic string-match approach must be kept for UX reasons, ensure any UI surface built on top of `isWebFlowCommitter` clearly labels it as a heuristic/best-effort guess rather than an authoritative "verified GitHub" indicator, and never uses it to elide normal review/trust warnings.

### Proof of Concept
1. Attacker creates/controls a public repository.
2. Attacker runs: `git commit --allow-empty -m "malicious change" --author="GitHub <noreply@github.com>" --committer="GitHub <noreply@github.com>"` (both `GIT_AUTHOR_*`/`GIT_COMMITTER_*` env vars are attacker-controlled with no repository-side enforcement).
3. Victim clones the repository (or fetches this branch/PR) into GitHub Desktop.
4. Any code path in Desktop that calls `isWebFlowCommitter(commit, gitHubRepository)` for that commit returns `true`, causing Desktop to treat/display the attacker's commit as though it were produced by GitHub's own web-flow merge process rather than by the attacker.

Note on limitations: I could not fully confirm every current UI call site that consumes `isWebFlowCommitter`'s boolean result within the indexed portion of the codebase (only `app/src/models/avatar.ts` references were found in the index) — for the complete set of UI surfaces that display this "GitHub" attribution and their exact rendering, a full-repository session (not limited by index size) would be needed to enumerate all consumers with certainty.

export function isWebFlowCommitter(
  commit: Commit,
  gitHubRepository: GitHubRepository
) {
  if (!gitHubRepository) {
    return false
  }

  const endpoint = gitHubRepository.owner.endpoint
  const { name, email } = commit.committer

  if (
    endpoint === getDotComAPIEndpoint() &&
    name === 'GitHub' &&
    email === 'noreply@github.com'
  ) {
    return true
  }

  if (endpoint !== getDotComAPIEndpoint() && name === 'GitHub Enterprise') {
    // We can't assume that the email address will match any specific format
    // here since the web flow committer email address on GHES is the same as
    // the noreply email which can be configured by domain administrators so
    // we'll just have to assume that for a GitHub hosted repository (but not
    // GitHub.com) a commit author of the name 'GitHub Enterprise' is the web
    // flow author.
    //
    // Hello future contributor: Turns out the web flow committer name is based
    // on the "flavor" of GitHub so it's possible that you're here wondering why
    // this isn't working and chances are it's because we've updated the
    // GHES branding or introduced some new flavor.
    return true
  }

  public static parseIdentity(identity: string): CommitIdentity {
    // See fmt_ident in ident.c:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L346
    //
    // Format is "NAME <EMAIL> DATE"
    //  Markus Olsson <j.markus.olsson@gmail.com> 1475670580 +0200
    //
    // Note that `git var` will strip any < and > from the name and email, see:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L396
    //
    // Note also that this expects a date formatted with the RAW option in git see:
    //  https://github.com/git/git/blob/35f6318d4/date.c#L191
    //
    const m = identity.match(/^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})/)
    if (!m) {
      throw new Error(`Couldn't parse identity ${identity}`)
    }

    const name = m[1]
    const email = m[2]
    // The date is specified as seconds from the epoch,
    // Date() expects milliseconds since the epoch.
    const date = new Date(parseInt(m[3], 10) * 1000)

    if (isNaN(date.valueOf())) {
      throw new Error(`Couldn't parse identity ${identity}, invalid date`)
    }

    // The RAW option never uses alphanumeric timezone identifiers and in my
    // testing I've never found it to omit the leading + for a positive offset
    // but the docs for strprintf seems to suggest it might on some systems so
    // we're playing it safe.
    const tzSign = m[4] === '-' ? '-' : '+'
    const tzHH = m[5]
    const tzmm = m[6]

    const tzMinutes = parseInt(tzHH, 10) * 60 + parseInt(tzmm, 10)
    const tzOffset = tzMinutes * (tzSign === '-' ? -1 : 1)

    return new CommitIdentity(name, email, date, tzOffset)
  }
