### Title
GaslessSwapRouter owner can front-run a pending `swapForGas` transaction by raising `commissionRate`, siphoning value from an unprivileged gasless user - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The gasless-swap flow lets any unprivileged token holder submit a fee-delegation-style `swapForGas` transaction that is admitted into the tx pool and, on execution, swaps ERC20 tokens for KAIA via the `GaslessSwapRouter` (KIP-247), deducting a `commissionRate`-based fee before sending the remainder to the user and repaying the block proposer. `commissionRate` is a single mutable contract-level parameter that the router owner can update at any time via `updateCommissionRate`, exactly analogous to the Lavarage lending-pool interest rate that a lender could change to harm an already-in-flight borrower transaction.

### Finding Description
`GaslessModule.checkBalanceForSwap` (the tx-pool admission check for `swapForGas` transactions) validates:
- `minAmountOut >= amountRepay`
- `amountIn >= router.GetAmountIn(minAmountOut)` computed against the *current* DEX exchange rate
- allowance/balance sufficiency
- `deadline >= currentTimestamp` [1](#0-0) 

None of these checks account for the router's own `commissionRate`, which is a separately mutable state variable on `GaslessSwapRouter` that the contract owner can change at any time via `updateCommissionRate`, emitting `CommissionRateUpdated(oldRate, newRate)`: [2](#0-1) 

The `swapForGas` execution itself emits `SwappedForGas(proposer, amountRepaid, user, finalUserAmount, commission)`, confirming that commission is deducted from the swap output at *execution* time, not at the time the user signed/submitted the transaction: [3](#0-2) 

Because a swap transaction can sit in the tx pool for some time before being picked up by a block proposer (the tx pool admission and the actual state-transition execution are decoupled, just as in the Lavarage report where the borrow transaction sits in the mempool before being mined), the owner of `GaslessSwapRouter` can observe a pending `swapForGas` tx and front-run it with `updateCommissionRate` set to a much higher value. Since the user's `minAmountOut` was chosen based on the commission rate that was in effect when they built the transaction (via `checkBalanceForSwap`'s `GetAmountIn` call, which reflects the pool's exchange rate but does not incorporate a commission-rate delta check), a higher commission taken at execution time reduces `finalUserAmount` for the same `amountIn`/`minAmountOut` inputs, exactly mirroring how the Lavarage lender could raise the interest rate to charge more fees on an already-signed borrow transaction that the borrower cannot react to.

### Impact Explanation
An unprivileged gasless-swap user (equivalent to the "innocent borrower" in the analog) can receive a smaller `finalUserAmount` than they intended, potentially even not enough to make the swap worthwhile after gas is repaid to the proposer, without any interaction that requires the user's consent to the new commission rate. This causes a mild but concrete economic loss to end users of the KIP-247 gasless swap mechanism and could require after-the-fact remediation from the protocol/router operator, similar to the medium-severity judgment on the original Lavarage finding. This is capped at medium severity because it requires the router owner to actively front-run and does not create unbounded value extraction (commission rate presumably has bounds enforced elsewhere in the contract, though this could not be verified from the available bindings).

### Likelihood Explanation
Likelihood is limited by privilege: the actor able to exploit this is the `GaslessSwapRouter` owner (an update-capable role), not an arbitrary unprivileged address — matching the original Lavarage report's own threat model where the "malicious lender" is privileged over their own pool parameters but the borrower is an unprivileged victim. Any owner (or an owner whose key is compromised) can trivially watch the public tx pool for pending `swapForGas` transactions and issue `updateCommissionRate` transactions ahead of them, since gas price/priority is fully within their control and no additional cryptographic material is needed.

### Recommendation
- Allow the user to pass an explicit maximum acceptable commission (or equivalently tighten `minAmountOut` semantics to account for commission at execution time) so `checkBalanceForSwap`/on-chain `swapForGas` reverts if the effective commission-adjusted output would fall below what the user actually authorized.
- Alternatively, snapshot/commit the commission rate at swap submission time (e.g., include it as an explicit parameter checked on-chain, analogous to storing the interest rate at the position level rather than only at the pool level in the original report), and revert if the on-chain `commissionRate` differs from the committed value at execution time.
- Consider a timelock or rate-of-change cap on `updateCommissionRate` to prevent abrupt front-runnable jumps.

### Proof of Concept
1. User A holds an allowed ERC20 token and wants to gaslessly swap it for KAIA via `GaslessSwapRouter`. They build a `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` transaction with `minAmountOut` computed to just cover `amountRepay` plus their desired margin, based on the currently observed `commissionRate` and DEX exchange rate (as validated by `checkBalanceForSwap`, which only checks `minAmountOut >= amountRepay` and `amountIn >= GetAmountIn(minAmountOut)`; see [1](#0-0) ).
2. The transaction is admitted into the tx pool and awaits inclusion.
3. The `GaslessSwapRouter` owner observes the pending transaction (public mempool) and submits `updateCommissionRate(newHigherRate)` with higher gas priority, which is included first (per [2](#0-1) ).
4. When User A's `swapForGas` is subsequently executed, the router deducts the new, higher commission from the swap output before computing `finalUserAmount`, as reflected in the `SwappedForGas` event fields (`finalUserAmount`, `commission`) at [3](#0-2) .
5. User A receives less KAIA than they expected when they signed the transaction, even though `minAmountOut >= amountRepay` still nominally holds, because the commission increase was not something they could account for or protect against at submission time.
