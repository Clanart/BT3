## Finding

### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to drain stranded token/ETH balances left by predispatch/postdispatch and cross-chain calldata execution - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The bug-class seed (CurveSpell) breaks when logic that manipulates a shared, balance-derived custody buffer isn't properly gated for the actual assets/approvals it operates on. Hyperbridge's `CallDispatcher` is the direct analog: it is a single, persistent, permissionless contract shared by `IntentGatewayV2` and `HyperFungibleTokenUpgradeable` for executing arbitrary predispatch/postdispatch/cross-chain calldata, but its `dispatch()` entrypoint has **no caller restriction whatsoever**. Any balance the dispatcher ends up holding — whether temporarily during a legitimate flow or permanently stranded as unaccounted dust — can be swept by any unprivileged address, not just the owning protocol contract. [1](#0-0) 

### Finding Description
`CallDispatcher.dispatch()` is declared `external` with no `onlyOwner`/`onlyGateway`/`msg.sender` check: [1](#0-0) 

It is used as a **shared, persistent** singleton (`_params.dispatcher`) by `IntentGatewayV2` for predispatch (swap-then-escrow) and postdispatch (fill-then-act) execution: [2](#0-1) 

as well as by `IntentsBase._execute()` for output-side calldata execution: [3](#0-2) 

and by `HyperFungibleTokenUpgradeable.onAccept()` for cross-chain calldata execution after minting to the beneficiary: [4](#0-3) 

In `IntentGatewayV2`, the sweep-back logic explicitly builds transfer calls from `IERC20(token).balanceOf(dispatcher)` — the *entire* balance, not just the amount attributable to the current order — and treats any excess as protocol "dust": [5](#0-4) 

`IntentsBase._execute()` performs a similar balance-based sweep for output assets only (line 447-473), meaning any token/ETH the dispatched calldata produces that is *not* one of `order.output.assets` is never swept back and is permanently stranded on the dispatcher.

Critically, `HyperFungibleTokenUpgradeable.onAccept()` calls `ICallDispatcher(_dispatcher).dispatch(message.data)` with **no sweep-back step at all** — any leftover value (e.g., slippage remainder, swap dust, referral rewards) produced by the attacker-supplied `Call[]` calldata (as documented in the wrapped-HFT docs, where swaps route ETH/WETH through the dispatcher) is left indefinitely on the dispatcher's balance: [6](#0-5) 

Because `dispatch()` has zero access control, any attacker can monitor the `CallDispatcher` address on-chain for a non-zero token/ETH balance and immediately call `dispatch()` themselves with a `Call{to: token, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)}` (or a raw ETH send via `to.call{value: balance}("")`), stealing funds that belong to users or the protocol before the legitimate sweep/dust-collection logic (which only runs inside the next `placeOrder`/`fillOrder`/`onAccept` invocation) ever executes.

### Impact Explanation
This is a direct fund-theft vector: any value that transiently or permanently sits on the shared `CallDispatcher` — user swap outputs mid-flow, unaccounted swap dust, or cross-chain calldata execution byproducts — is claimable by an arbitrary unprivileged address, not the rightful order beneficiary or protocol treasury. This satisfies "stealing or loss of funds" and "unauthorized execution," since the dispatcher was designed to be invoked only by the owning app contract as part of an atomic flow, yet nothing enforces that restriction.

### Likelihood Explanation
High. No privileged role, relayer, or malicious peer is required — a plain EOA can watch `balanceOf(CallDispatcher)` across supported tokens and race any residual balance with a single permissionless `dispatch()` call. Multi-hop swaps, slippage, or reward-bearing tokens routed through predispatch/postdispatch/cross-chain calldata (all user- or solver-supplied `Call[]`) make non-zero stranded balances a routine occurrence rather than an edge case.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the registered owning contract(s) (e.g., an `onlyAuthorized` modifier checking `msg.sender` against a registry of apps that were granted use of that dispatcher instance), or deploy a dedicated, ephemeral dispatcher per call/order so no shared, cross-order balance can ever accumulate. Additionally, add an explicit balance sweep-to-owner step in `HyperFungibleTokenUpgradeable.onAccept()` after `dispatch()`, and extend `IntentsBase._execute()`'s sweep to cover any token balance left on the dispatcher, not just the tokens listed in `order.output.assets`.

### Proof of Concept
1. A solver fills a cross-chain order whose `output.call` swaps the delivered output token for another token via `IntentsBase._execute()` → `CallDispatcher.dispatch(order.output.call)`; the swap returns a small amount of a reward/bonus token not listed in `order.output.assets`, so `_execute()`'s sweep loop never picks it up and it remains on `CallDispatcher`.
2. Attacker calls `IERC20(rewardToken).balanceOf(callDispatcherAddress)` off-chain and observes a non-zero balance.
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: rewardToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — this succeeds because `dispatch()` performs no caller check, only requiring `rewardToken` to have code.
4. The stranded balance is transferred to the attacker instead of being collected as protocol dust or returned to a rightful beneficiary.

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});

                        value: 0,
