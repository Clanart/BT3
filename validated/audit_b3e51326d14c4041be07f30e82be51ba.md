## Title
Divergent conflict-marker parsers between context-gathering and reassembly let a malformed marker in an attacker-controlled merge cause silent corruption of the "resolved" file that Copilot writes to disk - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Copilot's merge-conflict resolution feature "splits" a conflicted file into hunks with one marker-scanner (`extractConflictHunks`) to build the prompt/validation contract, and later "recomposes" the file by splicing model output back into the same raw text with a *second, independently implemented* marker-scanner (`reassembleResolvedFile`). The two scanners disagree on how to treat a malformed/unterminated conflict-marker block. `validateResolutionPaths` only checks that the *count* of hunks the model returned matches the *count* `extractConflictHunks` produced — it never verifies that `reassembleResolvedFile` will actually walk the same set of blocks in the same raw content. This is structurally the same class of bug as the reported issue: a value (the raw file) is split into parts by one routine and trusted by a downstream routine without a constraint tying the two together.

### Finding Description
`extractConflictHunks` (app/src/lib/copilot-conflict-context.ts, lines 179-279) walks a file line-by-line. When it opens a hunk (`<<<<<<<`) but never finds a closing `>>>>>>>` before EOF, `hunkEnd` stays `-1` and the code does: [1](#0-0) 
Because the inner collection loops already advanced `i` all the way to `lines.length` while searching, the outer `while (i < lines.length)` loop then terminates — **any conflict blocks after a malformed one are silently dropped from the returned `hunks` array**, and the earlier well-formed hunks are still reported and still cause `rawContent` to be attached: [2](#0-1) 

`reassembleResolvedFile` (app/src/lib/copilot-conflict-resolution.ts, lines 549-599) uses a *different* recovery rule for the same malformed case — it does a non-mutating lookahead and, on failure, treats only the single opening-marker line as ordinary content, then resumes scanning from the very next line: [3](#0-2) 

The only cross-check between the two stages is `validateResolutionPaths`, which compares hunk *counts*, not positions or the actual malformed-marker semantics: [4](#0-3) 

There is no assertion anywhere that the file `reassembleResolvedFile` produces is free of leftover conflict-marker lines or unresolved malformed blocks — unlike the per-hunk check that only inspects the model's own `resolvedContent`: [5](#0-4) 

Concretely, for a file with a well-formed first conflict block followed by a second, unterminated `<<<<<<<` block near EOF: `extractConflictHunks` reports `hunks.length === 1` (dropping the second block entirely), so the file is sent to the model as "1 conflict," `validateResolutionPaths` passes (1 == 1), but `reassembleResolvedFile` still encounters the malformed second marker line and copies it — and all trailing "junk" after it — through verbatim into the final file that gets written to disk and presented to the user as "fully resolved" content.

### Impact Explanation
This lets an attacker-controlled branch/PR/fork (i.e. arbitrary content the victim merges, rebases, or cherry-picks from a fetched remote) cause GitHub Desktop's AI conflict resolver to silently commit a file that still contains a literal, unresolved `<<<<<<<` conflict-marker line and arbitrary trailing content dictated by the attacker, while the UI/summary claims the conflict was fully resolved. This is exactly the "silent corruption of what the user commits or pushes" impact category: the user reviews a dialog claiming resolution, stages, and commits/pushes broken or attacker-shaped content without realizing conflict markers or malformed sections remain, since no invariant ties the reassembler's actual block-walk back to the block count validated earlier.

### Likelihood Explanation
Requires only that the victim (a) uses the Copilot conflict-resolution feature and (b) merges/rebases/cherry-picks a branch containing a crafted file with an early well-formed conflict and a later, deliberately unterminated marker — both of which are entirely within the capability of anyone who can get their commits merged or fetched (a malicious fork/PR/remote branch), with no local access, admin rights, or social engineering beyond the normal act of merging. The main uncertainty is how often real-world truncated/malformed conflict markers occur versus needing to be deliberately engineered, and I was not able to trace all downstream callers (e.g. `copilot-store.ts`) in this pass to confirm whether any additional post-reassembly sanity check exists before the file is written — this should be verified directly in the repository.

### Recommendation
Bind the "split" and "recompose" stages together with an explicit invariant, mirroring the fix pattern from the report (assert recomposition rather than trusting independent counts):
1. Use a single shared marker-scanning implementation for both `extractConflictHunks` and `reassembleResolvedFile` so they agree on malformed-block recovery semantics.
2. After reassembly, assert that the resulting content contains zero conflict-marker patterns (`<{7}`, `={7}`, `>{7}`) before it is treated as a valid resolution; if any remain, fail closed (surface the file as unresolved) instead of silently writing partially-resolved/malformed content.
3. Have `reassembleResolvedFile` return/track the number of blocks it actually spliced and assert it equals `hunkResolutions.length` exactly (not just that `hunkIndex < hunkResolutions.length` opportunistically), catching any divergence at write time rather than trusting the earlier count-only validation.

### Proof of Concept
1. Attacker pushes a branch/PR containing `conflicted-file.txt` such that, after the victim starts a merge, the working tree file looks like:
```
line A
<<<<<<< HEAD
oursA
=======
theirsA
>>>>>>> feature
line B
<<<<<<< HEAD
attacker-controlled trailing content with no closing marker before EOF
```
2. Victim opens GitHub Desktop, sees the merge conflict, and invokes the Copilot "Resolve conflicts" feature.
3. `buildConflictContext` → `extractConflictHunks` parses only the first block (the second consumes to EOF and is dropped), so the file is sent to the model as having exactly 1 conflict (`app/src/lib/copilot-conflict-context.ts:239-247`).
4. The model resolves that single hunk; `validateResolutionPaths` passes because both sides agree on `hunks.length === 1` (`app/src/lib/copilot-conflict-resolution.ts:514-519`).
5. `reassembleResolvedFile` splices the resolved hunk in place of the first block, but when it reaches the second, unterminated `<<<<<<<` marker it falls back to copying that marker line and all attacker-controlled trailing content verbatim (`app/src/lib/copilot-conflict-resolution.ts:574-579`).
6. The dialog reports the conflict as resolved; the file written to disk/staged for commit still contains a literal `<<<<<<<` marker and attacker-chosen trailing text, which the victim may commit and push without noticing.
