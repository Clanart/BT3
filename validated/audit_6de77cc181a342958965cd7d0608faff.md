### Title
Immaterial Bitcoin coinbase outputs are reported as received and can be selected for spending - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_block` scans every transaction in `block.txdata`, including the coinbase transaction, and returns matching outputs as ordinary `ReceivedOutput`s without enforcing Bitcoin’s coinbase maturity rule. Downstream, `SignableTransaction::new` treats every `ReceivedOutput` as spendable, signs a transaction spending its outpoint, and produces an invalid transaction if the referenced coinbase output has fewer than 100 confirmations.

### Finding Description
`Scanner::scan_transaction` converts any transaction output whose `script_pubkey` matches a registered script into a `ReceivedOutput`, committing only to `tx.compute_txid()` and the output index in the `OutPoint` [1](#0-0) . `Scanner::scan_block` then calls this routine for every transaction in `block.txdata`, which includes `block.txdata[0]`, the coinbase transaction [2](#0-1) .

Although the comment acknowledges coinbase maturity, the API still returns those outputs through the same type and does not expose or persist enough information for the wallet layer to distinguish immature outputs. The transaction constructor accepts the supplied `ReceivedOutput`s verbatim, uses their values as inputs, and maps each `input.outpoint` into `TxIn.previous_output` without checking whether the outpoint references a coinbase transaction or whether 100 blocks have elapsed [3](#0-2) .

The signing path then generates a valid Taproot key-spend signature hash for each such input and completes signatures for the transaction [4](#0-3) . Consensus still rejects the resulting transaction because coinbase outputs cannot be spent before maturity.

### Impact Explanation
An unprivileged party can send a Bitcoin block/transaction containing a matching Taproot output in the coinbase. If `scan_block` is used and the resulting `ReceivedOutput` reaches `SignableTransaction::new`, Serai will account for funds that are not yet spendable and may coordinate a threshold signature for a transaction that Bitcoin necessarily rejects. This can temporarily freeze withdrawal/batch construction until the invalid input is excluded, and misreports the currently spendable balance.

This directly matches the source bug class: a state transition/accounting operation incorrectly includes an item whose present ownership/spendability condition is not actually satisfied.

### Likelihood Explanation
Any miner can create a coinbase output paying to a monitored P2TR script, and any party relaying block data can cause that transaction to be scanned. The vulnerable path is entirely public-input driven: attacker-controlled block transaction data enters `Scanner::scan_block`, becomes a `ReceivedOutput`, and is later used as a `TxIn`. No validator, peer, key holder, or RPC compromise is required.

The practical trigger depends on the caller using `scan_block` rather than manually excluding `block.txdata[0]`. The code documents that `scan_transaction` can be called on `block.txdata[1 ..]` as a workaround [5](#0-4) , but the provided block scanner itself remains unsafe for applications expecting spendable outputs.

### Recommendation
Do not return coinbase outputs from `Scanner::scan_block` unless the block’s maturity status is known and the output is mature. The least error-prone fix is to skip `block.txdata[0]` inside `scan_block`, or add a maturity-aware API that accepts the current confirmation height and filters coinbase outputs with fewer than 100 confirmations.

Additionally, extend `ReceivedOutput` or the scanning result metadata to record whether the output came from a coinbase transaction, so wallet construction can reject it explicitly rather than relying on every caller to perform an undocumented separation.

### Proof of Concept
1. Register a scanner for an even Taproot key so `p2tr_script_buf(key)` returns its script [6](#0-5) .
2. Construct or relay a block whose `txdata[0]` coinbase contains an output paying to that script.
3. Call `Scanner::scan_block(&block)`.
4. The matching coinbase output is returned as a `ReceivedOutput` because `scan_block` iterates over all `block.txdata` and `scan_transaction` only compares `output.script_pubkey` [7](#0-6) .
5. Pass that `ReceivedOutput` to `SignableTransaction::new`.
6. `SignableTransaction::new` turns the immature coinbase `OutPoint` into an input and calculates its value as available funds [3](#0-2) .
7. `TransactionSignMachine::sign` signs the input’s Taproot key-spend sighash and `TransactionSignatureMachine::complete` installs the resulting witness [8](#0-7) [9](#0-8) .
8. Broadcasting the completed transaction fails under Bitcoin consensus rules because a coinbase output requires 100 confirmations before it can be spent.

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res

  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));

  }
