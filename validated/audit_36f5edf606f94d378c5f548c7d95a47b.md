### Title
Legacy `pattern:` rules for `stop`/`prompt`/`all` events silently never match, permanently disabling `block` rules - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` converts a legacy `pattern:` frontmatter field into a `Condition` whose `field` is inferred purely from the `event` value, but for any event other than `bash`/`file` (i.e. `stop`, `prompt`, or `all`) it hardcodes `field='content'`. `RuleEngine._extract_field` never resolves `'content'` for Stop/UserPromptSubmit events (it only recognizes `reason`, `transcript`, `user_prompt` there), so the condition's field value is always `None` and the condition can never match. As a result, any legacy-style `block` rule written for `stop`/`prompt`/`all` events is a permanent no-op, while the semantically equivalent explicit `conditions:` form (using `field: reason` or `field: user_prompt`) works correctly — breaking the invariant that legacy and explicit forms must have identical security semantics.

### Finding Description
In `Rule.from_dict` [1](#0-0) , the legacy pattern-to-condition conversion infers the condition `field` solely from `event`:
```
if event == 'bash': field = 'command'
elif event == 'file': field = 'new_text'
else: field = 'content'
```
This `else` branch fires for `event: stop`, `event: prompt`, and `event: all`.

At evaluation time, `RuleEngine._check_condition` calls `_extract_field(condition.field, ...)` [2](#0-1) . For Stop and UserPromptSubmit hook invocations, `tool_name` is empty and `tool_input` is `{}` [3](#0-2) [4](#0-3) , so `field in tool_input` is false, and `_extract_field` only special-cases the literal field names `reason`, `transcript`, and `user_prompt` [5](#0-4) . `'content'` is not one of them, so the function returns `None`. Back in `_check_condition`, a `None` field value makes the condition automatically fail [6](#0-5) , and `_rule_matches` requires all conditions to match [7](#0-6) , so the rule never fires — regardless of `action: block`.

The same issue reproduces for `event: all` combined with `tool_name == 'Bash'`: the legacy converter still sets `field='content'`, but `_extract_field`'s Bash-specific branch only resolves `field == 'command'` [8](#0-7) , so `'content'` again resolves to `None` and the rule is dead.

The documentation and the `/hookify` command explicitly advertise the simple `pattern:` format as valid for `stop`/`prompt`/`all` events [9](#0-8) , and `/hookify generation` (Step 3 of the command) can generate exactly this broken form when the user selects `stop` or `prompt` events with a simple pattern instead of explicit `conditions:`. A repo-shipped `.claude/hookify.*.local.md` file using this legacy form for a `stop`/`prompt` rule with `action: block` would silently never enforce, while an equivalent rule written with explicit `conditions: [{field: reason, ...}]` or `{field: user_prompt, ...}` enforces correctly — demonstrating the required legacy vs. explicit semantic divergence.

### Impact Explanation
This is a Security-control bypass: a rule author (or an automatically-generated rule from `/hookify`) believes they have installed a `block` rule guarding Stop or UserPromptSubmit events, but the rule is permanently inert due to the field-inference bug. There is no error, warning, or indication that the rule failed to load or match — `load_rule_file` succeeds and returns a valid `Rule` object [10](#0-9) , and the hook always exits 0 with an empty result when nothing matches [11](#0-10) . This silently routes around an intended blocking/permission boundary, matching the "Security-control bypass" impact category.

### Likelihood Explanation
This requires no privilege beyond normal repository content or normal `/hookify` usage: any `.claude/hookify.*.local.md` file (whether generated by `/hookify` for a `stop`/`prompt` rule using the simple `pattern:` form, or shipped in a repository and loaded via `load_rules()`'s glob scan [12](#0-11) ) triggers the bug deterministically and every time — it is not probabilistic. The command documentation itself encourages using the simple `pattern:` format for `stop`/`prompt` events, making accidental (or attacker-crafted) occurrence highly likely.

### Recommendation
In `Rule.from_dict`, infer the legacy condition's `field` per-event correctly (e.g., `event == 'stop'` → `field = 'reason'`, `event == 'prompt'` → `field = 'user_prompt'`), or reject/warn when a `pattern:`-only rule is defined for `stop`/`prompt`/`all` without an explicit compatible field, and ensure `RuleEngine._extract_field` handles the `'content'` fallback for these events. Add an invariant test enforcing that for every `event`, a legacy `pattern:` rule and an equivalent explicit `conditions:` rule produce identical `_rule_matches` results.

### Proof of Concept
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

# Legacy-style block rule for a Stop event
legacy_fm = {
    "name": "block-bad-stop",
    "enabled": True,
    "event": "stop",
    "pattern": "danger",
    "action": "block",
}
legacy_rule = Rule.from_dict(legacy_fm, "Blocked!")

# Explicit-style equivalent rule
explicit_fm = {
    "name": "block-bad-stop-explicit",
    "enabled": True,
    "event": "stop",
    "conditions": [{"field": "reason", "operator": "regex_match", "pattern": "danger"}],
    "action": "block",
}
explicit_rule = Rule.from_dict(explicit_fm, "Blocked!")

engine = RuleEngine()
input_data = {"hook_event_name": "Stop", "reason": "danger detected"}

legacy_result = engine.evaluate_rules([legacy_rule], input_data)
explicit_result = engine.evaluate_rules([explicit_rule], input_data)

assert explicit_result.get("decision") == "block"  # explicit form correctly blocks
assert legacy_result == {}  # BUG: legacy form silently never blocks despite action: block
```
Expected: both should return `{"decision": "block", ...}`; the legacy form instead returns `{}`, proving the security-semantics divergence.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
