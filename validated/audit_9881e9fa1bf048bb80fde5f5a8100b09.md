### Title
Unvalidated OP_RETURN operator pubkey allows permanent loss of operator reimbursement via RBF payout replacement - (File: circuits-lib/src/bridge_circuit/mod.rs, core/src/verifier.rs)

### Summary
`parse_op_return_data` extracts the first `PushBytes` after `OP_RETURN` and hands it directly to `XOnlyPublicKey::from_slice`, with no check that the resulting key belongs to any operator registered for the deposit being paid out. `update_finalized_payouts` in `core/src/verifier.rs` stores whatever key parses successfully, and `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:41-47) only ever looks up unhandled payouts by exact match against `self.operator.signer.xonly_public_key` [1](#0-0) , so a stored key that matches no real operator is never picked up by anyone.

### Finding Description
The binding that should hold is: `operator_xonly_pk` stored for withdrawal `i` == the xonly pk of an operator in `deposit_data.get_operators()` for the deposit that funded withdrawal `i`. `parse_op_return_data` (circuits-lib/src/bridge_circuit/mod.rs:608) only checks that the bytes form a syntactically valid x-only public key via `XOnlyPublicKey::from_slice(bytes).ok()`, with no membership check against the deposit's registered operator set. Since the attacker controls the withdrawal transaction's OP_RETURN via RBF (same input0/output0, `SinglePlusAnyoneCanPay` unaffected), they can replace the honest operator's mined payout with one whose OP_RETURN contains a 32-byte value that parses as a valid curve x-coordinate but corresponds to no operator that has ever registered with any verifier. Every `PayoutCheckerTask` instance queries `get_first_unhandled_payout_by_operator_xonly_pk` using its own operator's key [1](#0-0) ; since the recorded key doesn't match any real operator's key, no task will ever surface this withdrawal for handling.

### Impact Explanation
The honest operator who fronted the withdrawal's output0 from their own wallet permanently loses any path to reimbursement for those funds, since `handle_finalized_payout`/`mark_payout_handled` is only reachable through `get_first_unhandled_payout_by_operator_xonly_pk` matching a real operator's own key. This is a genuine "honest operator permanently unable to be reimbursed" scenario, matching the Critical severity bucket, and is repeatable per withdrawal against any operator willing to front funds.

### Likelihood Explanation
Requires the attacker to grind a random 32 bytes to be a valid x-only public key (~50% probability per random 32-byte string, i.e., trivial offline computation, no real cost beyond RBF fee bump), and to have RBF privileges over input0/output0 of the payout transaction. This is well within the described unprivileged attacker's capabilities (broadcasting transactions, paying fees, shaping OP_RETURN/witness), making the attack cheap and highly repeatable across withdrawals.

### Recommendation
Bind the OP_RETURN-extracted pubkey to the deposit's registered operator set at verification/parsing time: after `XOnlyPublicKey::from_slice` succeeds, additionally verify the key is a member of `deposit_data.get_operators()` (or the equivalent `OperatorData` set for the corresponding deposit) before calling `update_finalized_payouts`/accepting the payout as attributable to that operator. Reject or flag payouts whose OP_RETURN key does not correspond to any registered operator so operators can distinguish "no payout yet" from "payout stolen by unregistered key," and consider requiring the OP_RETURN payload to be signed or otherwise bound to the actual funder of output0.

### Proof of Concept
1. Set up a test bridge deposit and have a real operator fund/broadcast the payout transaction with a correct OP_RETURN containing their own xonly pk.
2. Before confirmation, broadcast an RBF replacement with identical input0/output0 but an OP_RETURN containing a 32-byte value chosen/grinded so `XOnlyPublicKey::from_slice` succeeds and does NOT equal any operator's registered xonly pk in the test's operator set.
3. Mine the replacement transaction.
4. Run the verifier's block-sync/`update_finalized_payouts` path so it parses this OP_RETURN and stores the unregistered pk against the withdrawal index.
5. Assert: for every configured operator `op`, `db.get_first_unhandled_payout_by_operator_xonly_pk(_, op.signer.xonly_public_key)` never returns this withdrawal's `citrea_idx`, i.e., `PayoutCheckerTask::run_once` never reaches `handle_finalized_payout`/`mark_payout_handled` for it — demonstrating the honest operator's funded output0 is permanently unclaimable.
