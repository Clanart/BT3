### Title
Silent, unconfirmed remote-URL rewrite on GitHub repo rename/transfer redirects pushes and fetches to a new, unverified owner - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop periodically "refreshes" the GitHub metadata for a tracked repository and, as part of that refresh, will automatically rewrite the local git remote's URL to whatever `clone_url` the GitHub API currently returns for that repository — with no user confirmation. This mirrors the `LienToken` bug pattern: a trust binding (here, "this local remote points at this specific GitHub repository/owner") is not re-verified or reset when the underlying object's ownership changes (a rename or ownership transfer), so a stale local binding silently starts being satisfied by a different, possibly attacker-controlled destination.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` re-resolves a repository's GitHub association on refresh: it re-parses the *current* local remote via `matchGitHubRepository` to get `owner`/`name`, calls `api.fetchRepository(owner, name)`, and if the repo already has an associated `GitHubRepository`, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`. [1](#0-0) 

`updateRemoteUrl` then compares the API's `clone_url` against the current remote. If the *previously stored* `gitHubRepository.cloneURL` still matches the current remote (`remoteUrlUnchanged`), the URL protocol hasn't changed, and the freshly-fetched `apiRepo.clone_url` differs from the current remote, it calls `gitStore.setRemoteURL(...)` — rewriting the local `origin` (or whichever remote) to point at the new URL, automatically and silently: [2](#0-1) 

The critical missing check is that GitHub's `repos/{owner}/{name}` endpoint transparently redirects across **renames and ownership transfers**. Nothing in `updateRemoteUrl` or `repositoryWithRefreshedGitHubRepository` distinguishes "this is the same logical repository that was merely renamed by its current owner" from "this repository was transferred to (or its old owner/name slot reused by) a different account/organization." The code trusts whatever `clone_url` the API redirect resolves to and rewires the user's remote to it, no confirmation dialog, no diffing of the owner identity, no revalidation of the association stored in `RepositoriesStore`.

This is architecturally the same flaw as the reported `LienToken` issue: an association (`payee` ↔ `ownerOf`, here `GitHubRepository` record ↔ actual remote git destination) is set once and then silently detaches from reality when the underlying object's ownership changes, because the code path that mutates state on "transfer" doesn't re-validate or reset the association — it just blindly follows the new pointer.

A comment in the same function acknowledges the broader class of problem exists and is known-unaddressed: [3](#0-2) 

`setRemoteURL` itself performs no additional validation — it's a thin wrapper around `git remote set-url`: [4](#0-3) 

### Impact Explanation
This satisfies the "silent corruption of what the user commits or pushes" impact category:
- If a repository the user has cloned is renamed or transferred by its owner (or the redirect chain otherwise resolves to a different destination), Desktop will, on its own background refresh cycle, rewrite the user's `origin` remote to the new URL without any prompt or diff shown to the user.
- All subsequent `git push`/`git fetch`/`git pull` operations silently target the new destination. If the new destination is not trustworthy (e.g., the original owner lost control of the org/repo, or ownership was transferred to a party the user did not intend to keep syncing with), the user's local commits get pushed to, and future code gets fetched from, a location the user never explicitly approved.
- Because the credential/account lookup (`getAccountForRepository`) is keyed on `endpoint`, not on the specific owner/repo, the user's existing stored GitHub token is reused against the new destination automatically, compounding the silent handoff of trust.

### Likelihood Explanation
The refresh path runs automatically as part of normal repository indicator/metadata refresh (no user interaction required beyond having previously added the repository to Desktop), and the only attacker-controlled input needed is a GitHub API repository object (its `clone_url`/owner) reachable via a rename or transfer — squarely within the "attacker controls a GitHub API object" category. No local access, admin rights, or social engineering step beyond normal repository collaboration/ownership dynamics is required.

### Recommendation
Do not silently rewrite the remote URL when the API-resolved owner differs from the previously-known owner (i.e., an ownership transfer, not just a same-owner rename). At minimum:
- Compare the *owner* portion of `gitHubRepository` vs `apiRepo.owner.login` in `updateRemoteUrl`, and require explicit user confirmation (a dialog, similar to other destructive/trust-changing actions in Desktop) before calling `setRemoteURL` when the owner has changed.
- Persist and re-verify the repository's identity (e.g., GitHub repository ID) rather than trusting owner/name path continuity, so a transfer to an unrelated account is detected rather than treated as a simple rename.

### Proof of Concept
1. User adds/clones `github.com/owner-a/project` in Desktop; Desktop stores `gitHubRepository.cloneURL = .../owner-a/project`.
2. `owner-a` transfers the repository to `owner-b` (or renames it in a way that changes the resolvable owner/name). GitHub's API now redirects `repos/owner-a/project` to the `owner-b/project` object and returns `clone_url = .../owner-b/project`.
3. On Desktop's next background refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('owner-a','project')`, gets back the `owner-b` object, and passes it to `updateRemoteUrl`. [5](#0-4) 
4. Since the stored `cloneURL` still matches the current remote and protocols match, `updateRemoteUrl` calls `gitStore.setRemoteURL(...)`, rewriting `origin` to `.../owner-b/project` with no confirmation. [6](#0-5) 
5. The user's subsequent pushes/fetches now silently go to `owner-b`'s repository.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
