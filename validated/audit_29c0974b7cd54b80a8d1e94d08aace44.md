### Title
Reward Sniping via Instant, Balance-Weighted `rewardPerTokenStored` Distribution - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool` (and `BaseRewardPoolV2`) distributes queued rewards to stakers instantly and proportionally to whatever `totalStaked()` (the current balance of the staking-receipt token held by `MasterMagpie`) is at the moment the reward is provisioned, with no time-weighting or minimum holding period. Because `MasterMagpie.deposit()`/`withdraw()` are fully permissionless and have no cooldown, an ordinary wallet can deposit a large stake immediately before a reward distribution event and withdraw immediately after, capturing a disproportionate share of the reward relative to the time actually staked — diluting and stealing yield from genuine long-term stakers. This mirrors the reported bug class ("a user may take advantage of the situation and take profits without staking for a considerable amount of time").

### Finding Description
Rewards are provisioned via `_provisionReward()`, which immediately updates the global accumulator based on the current total staked amount: [1](#0-0) 

`earned()` and `_updateFor()` compute a user's owed reward strictly from `balanceOf(_account)` (the user's live staked amount in `MasterMagpie`) multiplied by the delta in `rewardPerToken` since the account's last checkpoint: [2](#0-1) [3](#0-2) 

The same pattern exists in `BaseRewardPoolV2.sol`: [4](#0-3) 

`donateRewards()` is a fully public, unprivileged entry point that anyone can call to inject rewards for an already-registered token, immediately triggering `_provisionReward()`: [5](#0-4) 

Because there is no snapshot mechanism and `balanceOf()` reflects the account's instantaneous stake in `MasterMagpie`, a staker's reward entitlement is not time-weighted — it depends only on the balance held at the exact moment `rewardPerTokenStored` changes. Since `MasterMagpie.deposit()`/`withdraw()` (and the `_for` variants used by pool helpers) are freely callable by any wallet with no lock, cooldown, or minimum stake duration: [6](#0-5) 

an attacker can (1) observe or trigger an upcoming reward injection (via `donateRewards()`, or by front-running a `queueNewRewards()` call made by a manager such as `WombatStaking` after harvesting bribes/WOM rewards), (2) deposit a large stake just before the reward is provisioned so `rewardPerTokenStored` increases using a denominator that now includes the attacker's stake, (3) immediately claim the proportional share of the newly added reward, and (4) withdraw right after — all within one or two blocks, without ever having contributed capital to the pool for any meaningful duration. This both steals yield that should have accrued to genuine long-term stakers and inflates the denominator used for other users' calculations, permanently diluting their fair share of that reward event.

### Impact Explanation
This is a direct theft of unclaimed yield from legitimate stakers: an attacker with sufficient capital can repeatedly snipe reward distributions across any `BaseRewardPool`/`BaseRewardPoolV2` instance registered under `MasterMagpie`, extracting value that should belong to users who kept capital staked over time, with no admin or governance action required.

### Likelihood Explanation
Likelihood is high for any wallet with capital to briefly flash a large deposit around predictable reward events (harvest cadence in `WombatStaking`, or the fully public `donateRewards()` call), and the attack requires only two ordinary, permissionless transactions (deposit, then claim+withdraw) reachable directly by any EOA — no privileged role, oracle, or external protocol manipulation is needed.

### Recommendation
Introduce time-weighting or a minimum staking duration before newly deposited balances become eligible for freshly queued rewards (e.g., checkpoint-based accrual that excludes balance increases occurring within the same block/period as a reward injection), or stream rewards over time (rate-based distribution) rather than crediting the full amount to the current balance instantaneously.

### Proof of Concept
1. Attacker monitors `WombatStaking`/manager transactions that call `queueNewRewards()` on a target `BaseRewardPool`, or simply prepares to call the public `donateRewards()` themselves in the same block as a large deposit.
2. Attacker calls `MasterMagpie.deposit(_stakingToken, largeAmount)` [7](#0-6)  immediately before the reward-provisioning transaction, becoming the majority of `totalStaked()`.
3. The reward transaction executes `_provisionReward()`, increasing `rewardPerTokenStored` using the now-inflated `totalStaked()` denominator [8](#0-7) .
4. Attacker calls `MasterMagpie` claim functions (e.g., `multiclaim`) to receive `earned()`, which credits the full `rewardPerToken` delta against the attacker's large balance despite it having existed for only one block [9](#0-8) .
5. Attacker calls `MasterMagpie.withdraw(_stakingToken, largeAmount)` [10](#0-9)  to exit, having captured a disproportionate share of the reward at the expense of long-term stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
