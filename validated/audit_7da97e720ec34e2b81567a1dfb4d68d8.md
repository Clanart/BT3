### Title

Unbound PedPoP encryption-key registration enables DKG share theft - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary

PedPoP’s first-round proof authenticates a participant’s polynomial commitments but not the encryption key serialized alongside them. A participant capable of substituting registration bytes can attach their own encryption public key to another participant’s valid commitments, causing all shares intended for that participant to be encrypted to the attacker. This is analogous to the Keycloak flaw: the proof validating the primary credential does not bind the secondary authentication material being registered.

### Finding Description

`EncryptionKeyMessage` consists of the commitment message and a separate `enc_key`; its deserializer accepts the arbitrary encoded point following the commitments without cryptographically binding it to the commitment signature. [1](#0-0) 

The PedPoP proof-of-knowledge challenge covers only the DKG context, participant ID, Schnorr nonce, and polynomial commitments. [2](#0-1) 

`Commitments::read` preserves only the commitment bytes as `cached_msg`; the trailing `enc_key` is outside those authenticated bytes. [3](#0-2) 

When processing registrations, `Decryption::register` stores the supplied `enc_key` for the claimed participant without separately proving possession of its private key. [4](#0-3) 

Every sender then uses that registered public key when encrypting the share intended for the victim participant. [5](#0-4) 

Consequently, replaying the victim’s commitment payload with an attacker-controlled `enc_key` passes the existing participant-bound PoK while redirecting the victim’s incoming share ciphertexts to a key the attacker controls.

### Impact Explanation

The attacker can decrypt every polynomial contribution addressed to the victim and sum those field elements to recover the victim’s final DKG secret share.

The victim’s public verification share and the group verification data are derivable from the public commitment messages, so the recovered secret share can be used to construct a `ThresholdKeys` instance for the victim’s participant index and produce otherwise valid FROST signature shares.

In a `t`-of-`n` multisig, this effectively gives the attacker two independent shares—their own and the victim’s—reducing the honest participation required to authorize signatures. For example, in a 3-of-5 DKG, the attacker plus the stolen share needs only one additional honest signer.

### Likelihood Explanation

Exploitation requires an attacker participating in or influencing the DKG registration distribution to replace the `enc_key` portion of another participant’s serialized registration while preserving its commitment payload and PoK.

The PoK remains valid after this substitution because the challenge commits to `cached_msg`, participant, context, and nonce, but not to `enc_key`. The protocol’s assumption that callers use authenticated delivery mitigates arbitrary in-flight modification, but the library-level credential itself still does not authenticate the encryption-key registration or distinguish a legitimately paired key from a substituted one. Given the resulting key-share compromise, this is a Medium-severity issue.

### Recommendation

Bind the serialized encryption public key into the PedPoP commitment proof by extending the challenge inputs to include `enc_key.to_bytes()`, or by making `enc_key` part of `Commitments` before calculating `cached_msg` and the Schnorr PoK.

The commitment signature should authenticate the complete canonical registration payload, including:

- DKG context
- participant index
- all polynomial commitments
- encryption public key
- protocol/version domain separator

Additionally, require a proof of possession for the registered encryption key or derive the encryption key from authenticated participant-bound material. Add a regression test that splices another public key into a serialized `EncryptionKeyMessage` and asserts that `verify_r1` rejects it.

### Proof of Concept

Conceptually, for a victim `v` and attacker-controlled scalar `e`:

```rust
// Registration = Commitments || enc_key.
let victim_registration: EncryptionKeyMessage<C, Commitments<C>> = obtain_victim_registration();

// Serialize the valid registration.
let mut forged_bytes = victim_registration.serialize();

// Replace only the trailing encoded encryption key.
let enc_len = <C::G as GroupEncoding>::Repr::default().as_ref().len();
let attacker_enc_key = C::generator() * e;
forged_bytes[forged_bytes.len() - enc_len..]
  .copy_from_slice(attacker_enc_key.to_bytes().as_ref());

// Parsing succeeds because enc_key is an independent field.
let forged_registration =
  EncryptionKeyMessage::<C, Commitments<C>>::read(&mut forged_bytes.as_slice(), params)?;

// Insert under the victim's Participant ID.
registrations.insert(victim, forged_registration);
```

The forged registration still passes verification because `challenge` uses the unmodified `Commitments::cached_msg` and never hashes `enc_key`. During `generate_secret_shares`, each participant encrypts `share_i(v)` to `attacker_enc_key`. The attacker decrypts each ciphertext using `e`, deserializes the resulting scalar share, and computes:

```text
victim_secret_share = Σ share_i(v)
```

The attacker can then combine this recovered scalar with the public verification shares to act as participant `v` during subsequent FROST signing.

impl<C: Ciphersuite> ReadWrite for Commitments<C> {
  fn read<R: Read>(reader: &mut R, params: ThresholdParams) -> io::Result<Self> {
    let mut commitments = Vec::with_capacity(params.t().into());
    let mut cached_msg = vec![];

    #[allow(non_snake_case)]
    let mut read_G = || -> io::Result<C::G> {
      let mut buf = <C::G as GroupEncoding>::Repr::default();
      reader.read_exact(buf.as_mut())?;
      let point = C::read_G(&mut buf.as_ref())?;
      cached_msg.extend(buf.as_ref());
      Ok(point)
    };

    for _ in 0 .. params.t() {
      commitments.push(read_G()?);
    }

    Ok(Commitments { commitments, cached_msg, sig: SchnorrSignature::read(reader)? })
  }
