### Title
Reward-per-token accounting can be captured by an unprivileged wallet with a flash-style stake immediately before reward distribution, diluting long-term stakers - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2`/`BaseRewardPool`/`mWOMSVBaseRewarder`/`vlMGPBaseRewarder` use a Synthetix-style `rewardPerTokenStored` accumulator that is bumped **instantly and in full** whenever new rewards are provisioned, with no vesting/streaming over time and no minimum holding period enforced anywhere in the deposit/withdraw path (`MasterMagpie._deposit`/`_withdraw`, `WombatPoolHelperV2.deposit`/`withdraw`, `WombatStaking.deposit`/`withdraw`). An ordinary wallet can therefore deposit a large stake immediately before a reward distribution lands and withdraw (harvesting) immediately after, capturing a share of the rewards proportional to its momentary balance rather than to any meaningful holding duration — exactly the "almost flash loan" reward-capture pattern from the referenced Merit Circle finding.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPoolV2.sol` updates `rewardInfo.rewardPerTokenStored` in one step based on the `totalStaked()` at the moment the call executes: [1](#0-0) 

This is triggered either via the manager-only `queueNewRewards` or via the fully permissionless `donateRewards`: [2](#0-1) 

A user's claimable amount is computed purely from `rewardPerToken(_rewardToken) - userRewardPerTokenPaid` times the user's *current* `balanceOf`, which is read live from `MasterMagpie.stakingInfo`: [3](#0-2) [4](#0-3) 

Deposits and withdrawals into `MasterMagpie` (via `WombatPoolHelperV2`/`WombatStaking`) are instantaneous with no cooldown or vesting delay — `_deposit`/`_withdraw` immediately update `user.amount`/`rewardDebt` and immediately harvest via the reward pool's `updateReward` hooks: [5](#0-4) 

And the pool-helper deposit/withdraw path that stakes/unstakes LP receipt tokens into `MasterMagpie` has no lock period either: [6](#0-5) [7](#0-6) 

Because `rewardPerTokenStored` is bumped by `_amountReward * 10**decimals / totalStaked()` at the single moment a distribution (or a permissionless `donateRewards` call) happens, and a user's earned share is `balanceOf(user) * (rewardPerToken - userRewardPerTokenPaid)`, an attacker can:
1. Deposit a large LP/staking-token amount into the relevant pool right before (or in the same block as) a `queueNewRewards`/`donateRewards` transaction, instantly becoming a large fraction of `totalStaked()`.
2. Let the reward distribution land, which stamps `userRewardPerTokenPaid` for the attacker at the pre-distribution `rewardPerTokenStored` (via `_updateFor` on deposit) and then jumps `rewardPerTokenStored` for everyone based on the now-inflated `totalStaked()` that includes the attacker's flash-in stake.
3. Immediately call `withdraw`/`getReward` to harvest the proportional share and exit, having held capital at risk for only the time needed to fit the deposit + distribution + withdraw in adjacent blocks/transactions.

This mirrors the reported root cause 1:1: there is no delay in either the staking side (`_deposit`/`depositFor`) or the claiming side (`_harvestBaseRewarder`/`getReward`), so capital that never economically shared the risk/duration of long-term stakers can extract a disproportionate share of freshly distributed rewards, diluting existing stakers' proportional entitlement to the pot for that distribution cycle.

### Impact Explanation
Long-term stakers who supplied capital and risk exposure over an extended period lose a meaningful, disproportionate fraction of unclaimed yield to a large flash-style depositor that only holds the position for the duration required to straddle the reward distribution and an adjacent withdrawal. This is a direct theft/permanent loss of yield that would otherwise have accrued to legitimate long-term stakers, since once withdrawn by the attacker those reward tokens are gone from the pool's future distribution to the honest cohort.

### Likelihood Explanation
The attack requires no privileged role — any wallet can call `deposit`/`depositLP`/`withdraw` on `WombatPoolHelperV2` and stake/unstake through `MasterMagpie`, and `donateRewards` on the reward pools is fully permissionless, so an attacker doesn't even need to wait for or front-run the manager's `queueNewRewards` — they can self-trigger a distribution event after inflating their share, or watch the mempool for the manager's periodic `queueNewRewards` calls and front-run them with a large deposit, then back-run with a withdrawal. The only capital cost is the opportunity cost of holding a large stake for a few blocks, which for sufficiently valuable reward distributions can be trivially profitable — matching the "minimal duration, large capital" MEV-style profile described in the source report.

### Recommendation
Introduce either a time-weighted reward distribution (stream rewards over a period rather than instantly bumping `rewardPerTokenStored`, e.g. `rewardRate`/`periodFinish` streaming as already used in `wombat/WomUp.sol`) or require a minimum holding/lock duration before a deposit is eligible to accrue/claim newly queued rewards. Additionally, consider making `donateRewards` non-instant (queue into the next streaming period) so a single-block deposit cannot capture a proportional share of an externally-donated lump sum.

### Proof of Concept
1. Pool `P` has `totalStaked() = 100e18` and no pending rewards; attacker holds none.
2. Attacker calls `WombatPoolHelperV2.deposit`/`depositLP` with `9900e18` worth of stake, instantly becoming ~99% of `totalStaked()` via `MasterMagpie._deposit` (`rewards/MasterMagpie.sol:482-505`) — this also stamps `userRewardPerTokenPaid` at the current (pre-distribution) `rewardPerTokenStored` via the reward pool's `updateReward`/`_updateFor` hook.
3. Immediately after, a reward distribution occurs — either the manager's periodic `queueNewRewards` call (front-run) or the attacker's own `donateRewards` call (`rewards/BaseRewardPoolV2.sol:252-286`) — bumping `rewardPerTokenStored` based on the new `totalStaked()` that already includes the attacker's stake (`rewards/BaseRewardPoolV2.sol:290-313`).
4. Attacker calls `WombatPoolHelperV2.withdraw`, which calls `MasterMagpie.withdrawFor` → `_harvestAndUnstake` (`rewards/MasterMagpie.sol:516-534`), harvesting ~99% of the newly distributed reward tokens and exiting the position in the same or an adjacent block, having held capital at risk for a negligible duration compared to genuine long-term stakers.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    /// @notice internal function to deal with withdraw staking token
    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);

    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }

        address _lpAddress,
        uint256 _amount,
        uint256 _minimumLiquidity,
        address _for,
