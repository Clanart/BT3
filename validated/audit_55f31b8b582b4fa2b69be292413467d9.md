## Finding: `aptos move verify-package` never compares on-chain bytecode, only package metadata

### Title
`verify-package` gives false integrity assurance by never comparing on-chain module bytecode to locally compiled bytecode - ([File: aptos-move/cli/src/stored_package.rs])

### Summary
The Aptos CLI's `verify-package` command is documented as the way to confirm "on-chain bytecode matches a local compilation of the Move code" [1](#0-0) . In practice it never fetches or compares the actual on-chain module bytecode; it only compares `PackageMetadata` struct fields, none of which are a hash or byte-for-byte encoding of the deployed bytecode.

### Finding Description
`VerifyPackage::execute` builds a `CachedPackageRegistry` with `with_bytecode = false`: [2](#0-1) 

`CachedPackageRegistry::create` only populates `self.bytecode` when `with_bytecode` is `true`; here it is `false`, so no module bytecode is ever downloaded: [3](#0-2) 

The actual comparison, `CachedPackageMetadata::verify`, only checks `name`, `deps`, `modules` (the `ModuleMetadata` struct — name/source/source_map/extension, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest`: [4](#0-3) 

Critically, none of these fields are cryptographically bound to the actual compiled module bytes stored on-chain in the write set. `code::publish_package` accepts caller-supplied `code: vector<vector<u8>>` independently of the `PackageMetadata`, subject only to module-name matching, compatibility, and dependency checks — not to any correspondence between the claimed `source`/`source_digest` in the metadata and the real bytecode semantics: [5](#0-4) [6](#0-5) 

So a publisher can submit metadata whose `modules[].source` (and hence `source_digest`, which is derived from source text) matches trusted/reviewed Move source, while actually shipping different bytecode in the `code` argument (bounded only by module-address, compatibility and allowed-dependency rules, not by matching the claimed source). `verify-package`'s local build produces the same "expected" metadata from trusted source, and since `verify()` compares metadata-to-metadata rather than bytecode-to-bytecode, the mismatch goes undetected.

### Impact Explanation
This breaks the "verified bytes, package metadata... and committed module bytes must agree" invariant. `verify-package` exists precisely so that reviewers, governance voters, or dependent-package authors can trust that the on-chain code is what the published source implies. A false pass on this check enables silent code-safety bypass: bytecode that diverges from audited/expected source could be deployed and appear "verified," misleading downstream consumers/depending packages/users who rely on `verify-package` before trusting or depending on a package's on-chain code.

### Likelihood Explanation
High likelihood for the specific tool bug — it is deterministic and always occurs (bytecode is unconditionally not fetched for `VerifyPackage`, and `verify()` structurally never inspects it). It requires no race or special network conditions. The exploitation path (attacker publishes benign-looking metadata/source alongside differing bytecode) is straightforward and only limited by existing compatibility/dependency/verifier checks on the bytecode itself — none of which enforce bytecode-to-source correspondence.

### Recommendation
- Always fetch on-chain module bytecode in `VerifyPackage::execute` (`with_bytecode = true`), and extend `CachedPackageMetadata::verify` (or a new check) to compare each module's on-chain raw bytecode against the bytecode produced by the local build (`pack.extract_code()`), byte-for-byte, in addition to existing metadata comparisons.
- Consider also warning when `ModuleMetadata.source` is empty (source withheld) since `verify-package` cannot meaningfully verify code it never compares.

### Proof of Concept
1. Publish a package whose `PackageMetadata.modules[i].source` contains innocuous, reviewable Move source `A`, but whose accompanying `code[i]` bytes are a different, functionally divergent (but ABI/compat-compatible) compiled module `B` (e.g., adding a hidden admin backdoor not present in source `A`). `code::publish_package` accepts this as long as module names/compat/dependency checks pass — it never validates that `code[i]` was actually compiled from `pack.modules[i].source`.
2. A reviewer runs `aptos move verify-package --account <addr>` using the same trusted source `A`. The CLI builds `A` locally, fetches only `PackageMetadata` from chain (not bytecode), and compares metadata fields — all of which match (since the metadata's `source`/`source_digest` was crafted from `A`).
3. `verify-package` reports `"Successfully verified source of package"` even though the deployed bytecode `B` differs from and behaves differently than the reviewed source `A`.

Note: I could not fully trace whether any other Aptos-provided tooling (e.g. explorer-side verification, `aptos-release-tool`) independently performs a real bytecode diff for this same account/module path; the `aptos-release-tool` README explicitly notes "bytecode verification is a TODO" for framework releases, which is consistent with this same gap existing more broadly, but I did not verify that code path exhaustively.     /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

    public fun publish_package(owner: &signer, pack: PackageMetadata, code: vector<vector<u8>>) acquires PackageRegistry {
        // Disallow incompatible upgrade mode. Governance can decide later if this should be reconsidered.
        assert!(
            pack.upgrade_policy.policy > upgrade_policy_arbitrary().policy,
            error::invalid_argument(EINCOMPATIBLE_POLICY_DISABLED),
        );

        let addr = signer::address_of(owner);
        if (!exists<PackageRegistry>(addr)) {
            move_to(owner, PackageRegistry { packages: vector::empty() })
        };

        // Checks for valid dependencies to other packages
        let allowed_deps = check_dependencies(addr, &pack);

        // Check package against conflicts
        // To avoid prover compiler error on spec
        // the package need to be an immutable variable
        let module_names = get_module_names(&pack);

        // Record, per module in this package, the object's transitive root owner at (re)publish, so
        // lazy self-init can detect a later transfer of the object or an ancestor since that module
        // was published (see `init::internal_maybe_initialize`). Objects only; feature-gated.
        if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
            let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
            module_names.for_each_ref(|name| {
                init::record_deploy_owner(addr, *name.bytes(), owner);
            });
        };
        let package_immutable = &borrow_global<PackageRegistry>(addr).packages;
        let len = package_immutable.length();
        let index = len;
        let upgrade_number = 0;
        package_immutable.enumerate_ref(|i, old| {
            let old: &PackageMetadata = old;
            if (old.name == pack.name) {
                upgrade_number = old.upgrade_number + 1;
                check_upgradability(old, &pack, &module_names);
                index = i;
            } else {
                check_coexistence(old, &module_names)
            };
        });

        // Assign the upgrade counter.
        pack.upgrade_number = upgrade_number;

        let packages = &mut borrow_global_mut<PackageRegistry>(addr).packages;
        // Update registry
        let policy = pack.upgrade_policy;
        if (index < len) {
            pack.modules.for_each_ref(|m| {
                let m: &ModuleMetadata = m;
                init::reset_initialized(addr, *m.name.bytes());
            });
            *packages.borrow_mut(index) = pack
        } else {
            packages.push_back(pack)
        };

        event::emit(PublishPackage {
            code_address: addr,
            is_upgrade: upgrade_number > 0
        });

        // Request publish
        if (features::code_dependency_check_enabled())
            request_publish_with_allowed_deps(addr, module_names, allowed_deps, code, policy.policy)
        else
        // The new `request_publish_with_allowed_deps` has not yet rolled out, so call downwards
        // compatible code.
            request_publish(addr, module_names, code, policy.policy)
    }
