### Title
Lazy module self-initialization (`init::internal_maybe_initialize`) is front-runnable by any unprivileged caller, mirroring the "un-front-run-protected `initialize()`" bug class - (File: `aptos-move/framework/aptos-framework/sources/init.move`)

### Summary
`aptos_framework::init::internal_maybe_initialize` lets a module mint a signer for its *own* address the first time it is invoked, instead of running its one-time setup atomically inside the publish transaction (as classic `init_module` does). Because the gating logic only checks *which module* is calling and *whether an object owner changed*, and never checks *who the transaction sender is* or *whether this is the module's original publish/deploy transaction*, any account can be the one whose transaction wins the race to trigger the module's self-init logic. This is structurally the same bug class as the reported Solidity issue: an "initializer" that is reachable by an arbitrary caller before the intended owner gets to call it first.

### Finding Description
`code::publish_package` (`aptos-move/framework/aptos-framework/sources/code.move:159-231`) only records a `deploy_owner` for object-hosted packages, and resets the `only_once` flag on upgrade via `init::reset_initialized` (line 212) — it never itself calls the initializer. Initialization is deferred to whenever a module's own code later calls `init::internal_maybe_initialize`: [1](#0-0) 

The only checks performed before minting a signer for the module address are:
1. The lazy-init feature flag is enabled.
2. `check_and_set_initialized` — did *this module* already mark itself initialized (and is `only_once` semantics satisfied)?
3. `assert_may_self_initialize` — for object-hosted modules only, has the object's root owner changed since the module's own last publish: [2](#0-1) 

None of these checks constrain *who the transaction sender is*, nor do they require the call to happen as part of the publishing/upgrade transaction itself. Any account address module (`!object::is_object(addr)`) is unconditionally allowed to self-initialize (`recorded.is_none()` branch returns `!object::is_object(addr) == true`), and for object-hosted modules the only requirement is that the object hasn't changed hands — the caller (`tx sender`) is irrelevant either way.

Consequently, whichever public/entry function that internally invokes `init::internal_maybe_initialize` is exposed by the module becomes an unauthenticated, racey "constructor." The test harness itself demonstrates the pattern with a plainly public `run` function that anyone can call to trigger the module's initializer: [3](#0-2) 

In contrast to genesis-time `init_module`, which is invoked exactly once by the VM atomically within the publish transaction (before any other transaction can observe or interleave), lazy self-init introduces a publish→first-use gap during which an attacker can:
- Observe that a package/module has just been published or upgraded (module bytecode and package metadata, including whether it uses `init::internal_maybe_initialize`, are public on-chain via `code::PackageRegistry`).
- Submit their own transaction calling the module's public initializer-triggering entry function first, becoming the transaction whose execution wins the "not yet initialized" race and receives the module's self-signer, exactly as an attacker front-runs an uninitialized Solidity implementation contract's `initialize()`.

Whether this results in a corrupted admin/config value depends on what the receiving module *does* with the signer it is handed — but the framework provides no primitive (e.g., "only my own publish/upgrade transaction may trigger this," or "only a designated owner account may trigger this") to prevent it, unlike the atomic guarantee `init_module` gives.

### Impact Explanation
If a module written against this framework primitive stores caller-influenced state during its lazy self-init call (a very natural pattern, since `internal_maybe_initialize` exists specifically so a module can defer setup past the compiler-enforced no-op `init_module` and instead run its own constructor logic on first real use, taking arguments from the triggering transaction), an attacker who front-runs that first call can seed the module's config/admin/ownership resources with attacker-chosen values. This is a direct code-safety/ownership-of-published-code analog to the reported bug: unauthorized capture of a not-yet-initialized deployment before its legitimate owner acts. Because `object_code_deployment.move` and `code.move` are the framework's primary permissionless publish/upgrade paths, and lazy init interacts directly with both (owner tracking is recorded in `code::publish_package`), the blast radius covers any package built to rely on this documented pattern.

### Likelihood Explanation
Likelihood is bounded by two facts I could not fully resolve from the indexed code: (1) the feature `LAZY_MODULE_INITIALIZATION` is a `FeatureFlag = 127`, and it is not listed in `default_features()` in the fragment I inspected, so it may be opt-in / not yet enabled on mainnet; (2) whether any framework or widely-used package module actually stores caller-influenced privileged state (vs. framework-controlled fixed data like the `Counter` test example) inside its lazy self-init function is application-specific and I could not enumerate mainnet consumers of this API from the index. The mechanism itself (no sender/tx-origin check, no "must be the publish/upgrade transaction" check) is confirmed directly in `init.move`, but I could not verify a concrete production module that turns this into privilege escalation, so I am reporting the framework-level missing invariant rather than a fully proven exploited instance.

### Recommendation
Add an explicit authorization gate to `internal_maybe_initialize`/`assert_may_self_initialize` beyond "has the object owner changed": e.g., require that self-init can only be triggered by the transaction whose sender is the account/object owner at the time of the call (mirroring `object_code_deployment::upgrade`'s `object::is_owner` check), or restrict lazy self-init so it can only run within the same transaction that published or upgraded the module (closing the front-runnable gap entirely, analogous to OpenZeppelin's `_disableInitializers()` constructor pattern). At minimum, document prominently that any module using `internal_maybe_initialize` must not derive privileged identities (admin, owner) from the transaction that happens to win the initialization race, and provide a safer default helper that binds the resulting signer's privileges to a value fixed at publish time (e.g., the recorded `deploy_owner`) rather than to the arbitrary caller of the triggering entry function.

### Proof of Concept
Conceptual reproduction using the pattern shown in the existing test module (`aptos-move/e2e-move-tests/src/tests/init_module_api.rs:41-62`):
1. Publisher publishes a module with a public entry function such as:
   ```
   public entry fun run(caller: &signer) {
       let s = init::internal_maybe_initialize(true);
       if (s.is_some()) {
           // Hypothetical unsafe but natural pattern:
           move_to(&s.destroy_some(), Config { admin: signer::address_of(caller) });
       }
   }
   ```
2. Immediately after the publish transaction lands (before the publisher's own intended `run` call), an attacker submits a transaction calling `run(attacker_signer)`.
3. Because `internal_maybe_initialize` only checks "not yet initialized" and (for account addresses) unconditionally allows self-init, the attacker's call wins the race, `Config.admin` is set to the attacker's address, and the legitimate publisher's later call to `run` becomes a no-op (already initialized) — permanently locking the attacker in as admin.

I could not execute this against the actual harness within the current investigation to confirm the exact abort codes/behavior end-to-end (e.g., confirm `LAZY_MODULE_INITIALIZATION`'s default-on/off status and whether `check_and_set_initialized` has any additional undocumented guard), so this should be validated with a live e2e test using `MoveHarness` before treating it as fully confirmed.

    /// If the calling module needs initialization -- never initialized, or (with `only_once` false)
    /// upgraded since -- marks it initialized and returns a signer for its address; else returns
    /// `none`. Marking happens before the initializer runs, so a cyclic call terminates.
    ///
    /// The caller module is derived by the VM from the call stack, so a module can only initialize
    /// itself. Aborts if the feature is disabled (`ELAZY_MODULE_INITIALIZATION_NOT_ENABLED`), the
    /// caller is not module code (`EINVALID_INITIALIZE_CALLER`), or an object-hosted module changed
    /// owner since publish (`EOWNER_CHANGED_SINCE_DEPLOY`).
    public fun internal_maybe_initialize(only_once: bool): Option<signer> {
        assert!(
            features::is_lazy_module_initialization_enabled(),
            error::invalid_state(ELAZY_MODULE_INITIALIZATION_NOT_ENABLED),
        );
        let (addr, module_id) = get_caller_address_and_module_id();
        if (check_and_set_initialized(addr, module_id, only_once)) {
            option::none()
        } else {
            // Guard only when actually minting: a legitimate transfer after initialization must not
            // brick ordinary calls. An abort here rolls back the mark set above.
            assert_may_self_initialize(addr, module_id);
            option::some(create_signer::create_signer(addr))
        }
    }

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }

    /// The object root owner recorded for `module_id` at its last publish, or `none` if the module
    /// has no such record (an account module, or an object module never recorded).
    fun recorded_deploy_owner(addr: address, module_id: ModuleId): Option<address> {
        if (!exists<InitializationState>(addr)) return option::none();
        let modules = &InitializationState[addr].modules;
        if (modules.contains(&module_id)) modules.borrow(&module_id).deploy_owner else option::none()
    }
