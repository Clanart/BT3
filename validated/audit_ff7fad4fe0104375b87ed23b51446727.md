### Title
Submodule update forcibly re-enables `protocol.file.allow=always`, defeating Git's built-in submodule `file://` protection - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` conditionally injects the git config override `-c protocol.file.allow=always` into the `git submodule update --init --recursive` invocation whenever it is called with `allowFileProtocol: true`. This directly disables the upstream Git hardening (introduced for CVE-2022-39253) that blocks submodules from being cloned via the `file://` protocol, a protection that exists precisely because a malicious repository's `.gitmodules` file is attacker-controlled content.

`.gitmodules` (including submodule URLs) is fully attacker-controlled: it is part of the content of any cloned/fetched repository. Git's own protection against `protocol.file.allow` abuse exists because a submodule URL like `file:///some/absolute/path` (or a `file://` URL pointing at a path reachable via symlink/relative traversal) lets a malicious repo force git to treat an arbitrary local filesystem path as a submodule "remote" — which git will then read from, and if it contains its own `.git` metadata (e.g., hooks), potentially execute code from. Forcing `protocol.file.allow=always` via `-c` reintroduces this exact bypass for whatever call path in GitHub Desktop passes `allowFileProtocol: true`. The call sites live in `app/src/lib/git/checkout.ts`, which I was not able to fully audit in this session to confirm the precise conditions (e.g., whether it's scoped to trusted local test fixtures/`file://`-based dev clones vs. any generic checkout of an untrusted remote repo).

### Impact Explanation
If any reachable Desktop flow (e.g., checking out a branch of a cloned/fetched repository, or an operation following a pull/fetch) invokes `updateSubmodulesAfterOperation` with `allowFileProtocol: true` on a repository whose `.gitmodules` was supplied by an untrusted remote, an attacker-authored submodule entry pointing at `file://` paths could cause Desktop to read or execute content from arbitrary local filesystem locations outside the intended repository boundary — matching the "file read/write outside the repo" and potentially "code execution" categories of valid impact for this program.

### Likelihood Explanation
Likelihood depends entirely on whether `allowFileProtocol: true` is reachable from an untrusted-repo code path (clone/checkout/pull of a repo the user didn't author) versus being restricted to trusted/local scenarios (e.g., test helpers or explicitly local repositories the user created). This gating logic lives in `checkout.ts`, which I could not fully inspect before running out of tool budget, so I cannot confirm this is exploitable end-to-end without further investigation of `checkout.ts`.

### Recommendation
Audit every call site in `app/src/lib/git/checkout.ts` that sets `allowFileProtocol: true` and ensure it is never enabled for submodules originating from remote/untrusted repositories (i.e., restrict it strictly to repositories that are already local-only/trusted, matching Git's own default-safe behavior). Where possible, avoid the blanket `protocol.file.allow=always` override and instead scope any necessary local-path allowance to specific, validated, same-machine paths.

### Proof of Concept
Not independently reproduced end-to-end due to incomplete visibility into `checkout.ts` gating logic; the exploitable primitive is: attacker crafts a repository with a `.gitmodules` entry `url = file:///etc` (or another sensitive/arbitrary absolute path) and induces the victim to clone/fetch and then trigger the code path in `checkout.ts` that calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`, at which point Desktop executes `git -c protocol.file.allow=always submodule update --init --recursive`, satisfying the submodule URL against the local filesystem path rather than being blocked by git's default protection.
