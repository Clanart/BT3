### Title
Cross-deployment replay of relayer fee withdrawal/redirect signatures due to missing host-chain identity in signed payload - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-ismp-relayer`'s signed messages for `withdraw_fees` and the beneficiary-redirect path of `accumulate_fees` hash only `(nonce, dest_chain, beneficiary)` — never the identity of the Hyperbridge chain instance (genesis hash / host `StateMachine`) that is meant to verify them. Since this pallet is compiled into multiple independent Hyperbridge runtimes in this repo (`gargantua` and `nexus`) that each keep their own `Nonce`/`Fees` storage for the same relayer address, a signature produced for one deployment is byte-identical and valid on every other deployment sharing the same nonce state — exactly the "no `chain.id` in signed data" defect from the Harpie report.

### Finding Description
`message()` (used by `withdraw_fees`) and `beneficiary_message()` (used by `accumulate_fees`'s beneficiary-redirect branch) are defined as: [3](#0-2) [4](#0-3) 

Both hash only the relayer's local `nonce`, the *destination* `StateMachine` the funds are being routed to, and (for withdraw) the beneficiary — never `host.host_state_machine()` (the identity of the chain the pallet instance is running on). The `Nonce` and `Fees` maps are pallet storage, so they are per-runtime-instance, not globally shared: [5](#0-4) 

Both `accumulate_fees` and `withdraw_fees` are dispatched via `ensure_none(origin)` — i.e. unsigned/permissionless — with `validate_unsigned` only deduplicating the exact encoded call, not scoping it to a chain: [6](#0-5) . Because the call is unsigned, the signature itself is the sole authority check, and it is fully visible on-chain (mempool/block data) the moment it's first submitted, so anyone can copy and resubmit it verbatim to any other Hyperbridge deployment running the identical pallet.

This repo already ships two such runtimes with the same pallet — `gargantua` and `nexus` — confirming multiple live instances exist with independently tracked `Nonce`/`Fees` storage .

### Impact Explanation
A relayer's `(nonce=N, dest_chain=X, beneficiary=B)` withdrawal/redirect signature, once observed on one Hyperbridge deployment, can be replayed verbatim against any other Hyperbridge deployment (present or future — e.g. testnet vs. canary vs. mainnet, or any additional parachain runtime built from this same pallet) where that relayer's `Nonce[address][X]` also happens to equal `N` (guaranteed at the trivial and common case `N = 0`, i.e. a relayer's first-ever withdrawal/redirect on a given `dest_chain`). This lets an unrelated third party force execution of an authorization the relayer never issued for that specific chain — draining or redirecting that chain's independently accumulated `Fees[X][address]` balance to the beneficiary embedded in the intercepted signature, without a fresh signed decision from the fee owner for that chain. This is the direct on-chain analog of the Harpie bug: an action correctly authorized for one chain is silently re-applicable on another chain because chain identity was never part of what was signed.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to observe a broadcast/executed signature (trivial, since it's public and the calls are `ensure_none`/unsigned so no private mempool exists) and needs the victim relayer to have matching local nonce state on a second deployment for the targeted `dest_chain` — which is essentially guaranteed the very first time any relayer interacts with `withdraw_fees`/`accumulate_fees`'s redirect path on each new deployment (nonce starts at 0 everywhere). No malicious peer, relayer collusion, governance action, or leaked key is required — only public on-chain data and a second identically-coded Hyperbridge instance, both of which already exist in this monorepo.

### Recommendation
Bind the signed payload to the verifying chain's own identity, mirroring the Harpie fix of adding `chain.id`: include `host.host_state_machine()` (or an equivalent unique, config-baked chain/deployment identifier) inside `message()` and `beneficiary_message()` before hashing, e.g. `keccak_256(&(host_state_machine, nonce, dest_chain, beneficiary).encode())`. This makes a signature meaningful to exactly one Hyperbridge deployment.

### Proof of Concept
1. Deploy/observe two Hyperbridge instances built from this pallet with independent storage — e.g. `gargantua` and `nexus`, per `parachain/runtimes/{gargantua,nexus}`.
2. Relayer `R` accumulates relayer fees for `dest_chain = Evm(1)` on both instances (normal operation — R delivers messages to Evm(1) via both deployments).
3. On `gargantua`, `R`'s `Nonce[R][Evm(1)] == 0`. `R` signs `message(0, Evm(1), beneficiary=B)` and submits `withdraw_fees` there; it succeeds and `Nonce[R][Evm(1)]` becomes 1 on `gargantua` only.
4. An observer copies the exact `WithdrawalInputData { signature, dest_chain: Evm(1), beneficiary: Some(B) }` from the `gargantua` block/mempool.
5. On `nexus`, `R`'s `Nonce[R][Evm(1)]` is independently still `0` (R has not yet withdrawn there). The observer submits the copied `withdraw_fees` call unsigned to `nexus`. `Self::withdraw` recomputes `message(0, Evm(1), B)`, which matches the replayed signature, so verification passes and `nexus`'s independently-accumulated `Fees[Evm(1)][R]` is paid out to `B` — an action `R` never authorized on `nexus`, triggered purely because the signed payload never bound to which chain it was meant for.

		fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
			let res = match call {
				Call::accumulate_fees { withdrawal_proof } =>
					Self::accumulate(withdrawal_proof.clone()),
				Call::withdraw_fees { withdrawal_data } => Self::withdraw(withdrawal_data.clone()),
				Call::claim_outbound_consensus_delivery_reward { claim } =>
					Self::process_outbound_consensus_delivery_claim(claim.clone()),
				Call::claim_outbound_request_delivery_reward { claim } =>
					Self::process_outbound_request_delivery_claim(claim.clone()),
				_ => Err(TransactionValidityError::Invalid(InvalidTransaction::Call))?,
			};

			if let Err(err) = res {
				log::error!(target: "ismp", "Pallet Relayer Fees error {err:?}");
				Err(TransactionValidityError::Invalid(InvalidTransaction::Call))?
			}

			let encoding = match call {
				Call::accumulate_fees { withdrawal_proof } => withdrawal_proof.encode(),
				Call::withdraw_fees { withdrawal_data } => withdrawal_data.encode(),
				Call::claim_outbound_consensus_delivery_reward { claim } => claim.encode(),
				Call::claim_outbound_request_delivery_reward { claim } => claim.encode(),
				_ => unreachable!(),
			};

			let msg_hash = sp_io::hashing::keccak_256(&encoding).to_vec();

			Ok(ValidTransaction {
				priority: 100,
				requires: vec![],
				provides: vec![msg_hash],
				longevity: TransactionLongevity::MAX,
				propagate: true,
			})
		}
