### Title
Panic on identity aggregate nonce in BIP-340 `Hram`/`x_only` helper reachable via malicious FROST preprocess commitments - (File: networks/bitcoin/src/crypto.rs)

### Summary
CVE-2021-47289's bug class is "a shared helper invoked with a sentinel/empty value it was never built to handle" (`acpi_dev_put(NULL)` → crash). The direct analog in Serai is the point-to-x-only helpers `x()` and `x_only()` in `networks/bitcoin/src/crypto.rs`, which `expect()` non-infinity input and are invoked by `Hram::hram` on the aggregate nonce `R` and group key `A` during `Schnorr::sign_share`/`verify` in the Bitcoin `TransactionMachine` flow. A participant's preprocess commitments are validated individually (`Curve::read_G` rejects identity at `crypto/frost/src/curve/mod.rs:125`), but the *summed* nonce `R` — a linear combination an attacker can steer to identity by choosing their commitment as the negation of the others' sum — is passed to `Hram::hram` without any identity check, causing a panic.

### Finding Description
`x()` calls `key.to_encoded_point(true)` and then `encoded.x().expect("point at infinity")` (`crypto.rs:13-16`); `x_only()` wraps it with another `expect` (`crypto.rs:21-23`). `Hram::hram` calls `x(R)` and `x(A)` unconditionally (`crypto.rs:59-67`). The doc comments acknowledge this: "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`) and justify it only as "negligible probability for a well-reasoned caller" (`crypto.rs:78-80`). In FROST, the aggregate nonce is `R = D + rho*E` summed over all included commitments (`nonce_sums` in `TransactionSignMachine::sign` → `sig.sign(...)` at `wallet/send.rs:383-390`). Each individual commitment point is read through `Curve::read_G` which rejects identity encodings, but no code rejects an identity *sum* — a grep of `crypto/frost/src/sign.rs` shows no `is_identity` check before the Hram is evaluated. A malicious signer computes everyone else's contribution to the binding-weighted nonce sum (all inputs are public in the preprocess round: the commitment list, `hash_msg`, and rho are deterministic) and submits their commitment so the final `R` is the point at infinity. Note `Curve::random_nonce` deliberately rejects zero nonces because "commitments which will be rejected for being zero" (`crypto/frost/src/curve/mod.rs:103-108`), confirming identity is expected to be filtered — yet only the per-point decoder filters it, not the aggregate.

### Impact Explanation
Denial of service of the Bitcoin signing pipeline: a single malicious participant in a signing session can deterministically panic every honest signer's `TransactionSignMachine::sign` (or `verify`) call at the `expect("point at infinity")` in `x()`. Since `sign_share` panics rather than returning `FrostError`, there is no graceful blame/retry path — the multisig cannot produce the Bitcoin transaction, halting withdrawals/branches for that plan. This mirrors CVE-2021-47289's Medium-severity availability impact (CVSS 5.5, A:H): an unprivileged party uses only public inputs (their preprocess commitments) to crash the code path.

### Likelihood Explanation
Deterministic and freely reachable: any participant included in a FROST signing set for a `SignableTransaction` controls their own preprocess and can observe/coerce the nonce sum to identity. In a 2-of-3 or similar threshold, one malicious signer suffices; no collusion or internal access is needed. Caveat: I could not fully verify `crypto/frost/src/sign.rs`'s internal commitment handling (index coverage), so it is possible — though unlikely given the explicit panic documentation in `crypto.rs` — that a nonce-sum identity check exists upstream; the documented panic contract strongly suggests it does not.

### Recommendation
In `Hram::hram` (or before invoking it in `Schnorr::sign_share`/`verify`), check `R.is_identity()` and `A.is_identity()` and return a `FrostError::InvalidCommitment`/verification failure instead of panicking. Alternatively, have FROST's `sign` reject identity nonce sums before computing the binding/challenge, matching how `Curve::read_G` rejects identity points and `random_nonce` rejects zero scalars.

### Proof of Concept
1. Two participants run `TransactionSignMachine::sign` for a `SignableTransaction` (`send.rs:355`).
2. Honest signer sends preprocess commitments `(D_h, E_h)`. Attacker computes the binding factor `rho` over the public commitment list and message (`Curve::hash_msg`/`hash_commitments`, `curve/mod.rs:61-68`), then sets their commitment contribution to `-(D_h + rho*E_h)` (a valid, non-identity point pair passing `read_G`).
3. The aggregate nonce `R` becomes the point at infinity.
4. `FrostSchnorr::sign_share` calls `Hram::hram(&R, &A, msg)` → `x(&R)` → `to_encoded_point(true)` on infinity has no `x` → `expect("point at infinity")` panics, crashing the signing machine.
