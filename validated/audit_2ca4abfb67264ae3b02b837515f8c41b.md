### Title
Path-containment check `resolveWithin()` uses raw string-prefix comparison, allowing sibling-directory escape - ([File: app/src/lib/path.ts])

### Summary
The report's underlying bug class is a **boundary check that is subtly wrong** (off-by-one), letting something that should be rejected slip through. The same class of bug exists in GitHub Desktop's path-containment guard `resolveWithin()` in `app/src/lib/path.ts`. Instead of verifying that a resolved path is truly *inside* a root directory, it does a raw string-prefix test that also matches any sibling path whose name merely starts with the root directory's name.

### Finding Description
`_resolveWithin()` is the central utility Desktop uses to make sure a path derived from untrusted input (e.g. a deep-link `filepath` query parameter) stays inside a given repository root: [1](#0-0) 

The final guard is:
```ts
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a pure string comparison, not a path-segment comparison. `"/Users/victim/Documents/GitHub/myrepo-secrets".startsWith("/Users/victim/Documents/GitHub/myrepo")` evaluates to `true`, even though `myrepo-secrets` is a completely different directory next to `myrepo`, not inside it. The check is missing the trailing path-separator boundary (`realRoot + Path.sep`) that would be required to correctly express "is a descendant of root" — functionally the same class of defect as an off-by-one/boundary comparison that admits one extra, unintended element.

This function is consumed by the deep-link handler in the dispatcher: [2](#0-1) 

The `filepath` value originates from an attacker-controlled `x-github-client://openrepo/...&filepath=...` URL, parsed in `parseAppURL()`: [3](#0-2) 

The dispatcher rejects only `isAbsolute(filepath)` values before calling `resolveWithin`: [4](#0-3) 

A relative `filepath` such as `../myrepo-secrets/config` is not blocked by the `isAbsolute` check, is joined/resolved against `repository.path`, and then evaluated only against the flawed `startsWith` boundary check — so if a directory next to the repo happens to share the repo directory name as a string prefix, the containment check incorrectly passes.

### Impact Explanation
If the check passes for a path outside the intended repository root, Desktop calls `shell.showItemInFolder(resolved)`, revealing/opening a file outside the repository that the containment check was supposed to prevent — this is a "file read/expose outside the repo" primitive triggered purely by a link the user clicks, matching the accepted impact class. Because `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are the general-purpose containment primitives also used elsewhere (`app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`), any other caller that assumes "returns non-null ⇒ truly inside root" inherits the same broken invariant.

### Likelihood Explanation
Exploitation depends on a same-parent-directory sibling existing whose name has the repository folder name as a literal string prefix (e.g. `myrepo` vs. `myrepo-secrets` or `myrepo.bak`). This is not guaranteed on every victim machine, so likelihood is **environment-dependent/moderate** rather than universal — I could not confirm from the indexed code a call path that fully controls both the root directory name and guarantees a matching sibling exists, which is the main uncertainty in weaponizing this end-to-end. Still, the check itself is objectively broken and violates its own documented contract ("resolved path is guaranteed to reside at, or underneath this path").

### Recommendation
Change the final comparison in `_resolveWithin()` (`app/src/lib/path.ts`) to require a path-segment boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the appropriate separator for the `options` variant (`Path.sep`, `Path.posix.sep`, or `Path.win32.sep`), so a sibling directory that merely shares a string prefix can never be classified as "within" the root.

### Proof of Concept
1. Victim has GitHub Desktop with a repository cloned at `/Users/victim/Documents/GitHub/myrepo`, and (for this PoC) a sibling folder `/Users/victim/Documents/GitHub/myrepo-secrets/config` exists.
2. Attacker sends the victim a link:
   `x-github-client://openrepo/https://github.com/owner/myrepo?filepath=../myrepo-secrets/config`
3. `parseAppURL` extracts `filepath = "../myrepo-secrets/config"` (relative, so it bypasses the `isAbsolute` guard in `dispatcher.ts`).
4. `resolveWithin(repository.path, filepath)` resolves to `/Users/victim/Documents/GitHub/myrepo-secrets/config`, and the flawed `startsWith` check treats it as "within" `myrepo` because the strings share a prefix.
5. `shell.showItemInFolder(resolved)` opens/reveals the file outside the intended repository, confirming the boundary check can be bypassed with a crafted relative path plus a same-prefix sibling directory.
