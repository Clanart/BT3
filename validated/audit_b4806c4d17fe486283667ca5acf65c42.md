### Title
Forgeable output-type classification: unsolicited transfers to deterministic internal offset scripts are misclassified as protocol-internal outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the DTXT incident — where an attacker sent a small amount of USDT directly to the pair to forge "liquidity addition" classification — Serai's Bitcoin `Scanner` classifies received outputs purely by `script_pubkey` match against a fixed set of registered scripts. The scripts for the internal output kinds (Branch, Change, Forwarded) are deterministic functions of the group key and publicly-known `hash_to_F(KEY_DST, ...)` offsets, so any unprivileged party can craft a transaction paying those scripts and have it classified as an internal protocol output rather than an external deposit.

### Finding Description
`Scanner::scan_transaction` looks up `output.script_pubkey` in `self.scripts` and returns a `ReceivedOutput` carrying whatever offset was registered for that script, with no distinction between outputs the protocol itself created (change, forwarded, branch flows) and outputs an arbitrary third party created [1](#0-0) . The scripts map is seeded by `Scanner::new`/`register_offset` keyed solely on the P2TR script of `key + offset*G` [2](#0-1) .

The offsets used in production are fixed, publicly reproducible values: `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch" | b"change" | b"forward")`, registered for every key in `scanner()` [3](#0-2) . `get_outputs` then tags every scanned output's `kind` purely by the recovered offset — `External`, `Branch`, `Change`, or `Forwarded` — without checking whether the containing transaction is one Serai itself authored [4](#0-3) . There is no on-chain marker distinguishing a genuine protocol-produced change/forward output from an attacker-sent payment to the same script — identical to DTXT's reliance on raw balance deltas to detect liquidity additions.

### Impact Explanation
An attacker can forge the output-type classification of an arbitrary on-chain transfer:

- Funds sent directly to the `Forwarded`/`Change`/`Branch` script are reported as that kind, not as deposits. A user (or attacker staging a victim flow) sending value to the change/forward address has the funds classified as internal bookkeeping output rather than a creditable `External` deposit — value arrives at the multisig but is accounted under the wrong class, so it is not minted/credited to the depositor while still sitting in multisig-controlled UTXOs (funds received yet misattributed).
- Conversely, any dust output the protocol creates (e.g., scanning its own signed transaction, as exercised in the test where payments to the external script are re-scanned as fresh `ReceivedOutput`s) is indistinguishable from a genuine inbound transfer — self-payments can be re-reported as new received outputs [5](#0-4) .
- For `Forwarded`-kind outputs, downstream logic treats them as outputs to be forwarded/rotated per the multisig schedule, letting an attacker inject spurious forwarded outputs that trigger unintended signing/spend operations on attacker-chosen timing.

Because the classification primitive is reachable by any party that can broadcast a Bitcoin transaction, and it directly drives `OutputType` in `get_outputs`, this is a real forgeable-classification flaw, not a hypothetical.

### Likelihood Explanation
The internal scripts are fully deterministic and publicly computable (`key` is the known group key, offsets are fixed `hash_to_F` digests of constant strings). Exploitation requires only sending a standard P2TR output — the same trivial cost as the DTXT "send a small amount to the pair" step. No validator collusion, key knowledge, or RPC compromise is needed. Impact severity is Medium: misclassification corrupts accounting/forwarding behavior rather than directly yielding keys, but it can strand deposits, misattribute value, and force unintended multisig spend activity.

### Recommendation
- Tag protocol-generated internal outputs so they are distinguishable from foreign transfers, e.g., only treat `Change`/`Branch`/`Forwarded`-script outputs as internal when they appear in transactions the processor itself authored (track pending txids), and treat all other payments to those scripts as `External`-class deposits (or reject them).
- Alternatively, embed a per-output commitment (e.g., an OP_RETURN memo or a unique offset derived from the intent being fulfilled) so the offset alone is not a forgeable classification signal — the same fix DTXT needed (verify intent, not balance deltas).
- Document that `scan_transaction` must never be fed transactions that Serai did not itself create when interpreting `Change`/`Forwarded`/`Branch` kinds.

### Proof of Concept
```rust
// Any external party can compute the protocol's internal scripts and forge
// an internal-classified output:
let key = group_key; // publicly known multisig key
let branch_off = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch");
// May need +1 increments until even, exactly as register_offset does
let script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * branch_off_used)).unwrap();
// Attacker broadcasts a tx paying `script`. 
// scanner.scan_transaction(tx) yields ReceivedOutput{offset: branch_off_used, ...}
// get_outputs() tags it OutputType::Branch — misclassified as an internal output.
```
`register_offset`'s loop is deterministic and increments are publicly simulatable, so the attacker can reproduce the exact registered offset and hence the exact script [6](#0-5) .

  /// Register an offset to scan for.
  ///
  /// Due to Bitcoin's requirement that points are even, not every offset may be used.
  /// If an offset isn't usable, it will be incremented until it is. If this offset is already
  /// present, None is returned. Else, Some(offset) will be, with the used offset.
  ///
  /// This means offsets are surjective, not bijective, and the order offsets are registered in
  /// may determine the validity of future offsets.
  ///
  /// The offsets registered must be securely generated. Arbitrary offsets may introduce a script
  /// path into the output, allowing the output to be spent by satisfaction of an arbitrary script
  /// (not by the signature of the key).
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
