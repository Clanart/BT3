### Title
`ThresholdKeys::read` accepts identity verification shares, yielding a zero (identity) group key that makes received funds unspendable or trivially stealable - (File: crypto/dkg/src/lib.rs)

### Summary
The audit hint is "the recovery-critical owner address can be reset to `address(0)`". In Serai, the analogous "address that must never be zero" is the threshold **group key**: it is the sole authority under which scanned outputs are received and spent. `ThresholdKeys::read` deserializes attacker-controlled verification shares with `Ciphersuite::read_G`, which performs canonical-encoding checks but does **not** reject the identity point. `ThresholdKeys::new` then computes `group_key` as a plain sum of the first `t` verification shares with no identity/zeros check. The result is a `ThresholdKeys` whose `group_key()` is the point at infinity — the cryptographic equivalent of `owner = address(0)`.

### Finding Description
`Ciphersuite::read_G` only validates canonical encoding; identity is explicitly allowed:

- `crypto/ciphersuite/src/lib.rs` lines 91–101 — `read_G` checks `from_bytes` + canonical re-encoding only.
- `crypto/frost/src/curve/mod.rs` lines 123–131 — `Curve::read_G` *does* reject identity ("identity point"), showing the codebase knows this is dangerous, but `ThresholdKeys::read` deliberately uses `<C as Ciphersuite>::read_G` (line 622), bypassing that rejection.
- `crypto/dkg/src/lib.rs` lines 376–378 — `group_key` is computed as `Σ verification_shares[i] * interpolation_factor(i)` over participants `1..=t` with no check that the result is non-identity, and no check that individual verification shares are non-identity.

For `t = 1`, submitting `verification_shares[1] = identity` (a valid canonical encoding) yields `group_key = identity`. For larger `t`, any combination summing to identity works.

Downstream impact paths:

- `networks/bitcoin/src/wallet/mod.rs` `tweak_keys` (lines 46–75) applies `TapTweakHash(identity).G` as an offset — producing a key whose discrete log (`tweak_hash`) is known to everyone. Any output scanned to it is stealable by anyone.
- `Scanner::new` / `register_offset` (lines 162–196) will happily track outputs for such a key; `scan_transaction` reports them as `ReceivedOutput`s — funds reported received that are not spendable by the validator set (or are spendable by a third party who knows the zero/tweak discrete log).
- Any Schnorr/FROST verification against `public_key = identity` reduces `batch_statements` to `R - sG` (`crypto/schnorr/src/lib.rs` lines 88–99), i.e. signatures are forgeable by anyone with `R = s·G`.

### Impact Explanation
Permanent loss / theft of funds: outputs received to a zeroed group key are either unspendable (identical to renounced ownership bricking recovery in the source report) or spendable by an arbitrary party who knows the effective discrete log (0, or `TapTweakHash` after tweaking). Key material integrity is a documented security boundary of these crates, yet the deserialization boundary admits a degenerate key.

### Likelihood Explanation
Reachable wherever `ThresholdKeys::read` consumes bytes not fully trusted — backup/import paths, share redistribution, or any replication of serialized key material. An attacker who can supply or corrupt serialized `ThresholdKeys` (the rules explicitly include untrusted bytes to `ThresholdKeys::read`) can swap verification shares for identity/cancelling points without detection, since no consistency proof binds the shares to the group key at read time. The reader's own secret share is not checked against its verification share either.

### Recommendation
In `ThresholdKeys::new` (or in `read`), reject identity verification shares and assert `!bool::from(group_key.is_identity())`. Optionally use an identity-rejecting point reader (like `Curve::read_G` in frost) for verification-share deserialization in `crypto/dkg/src/lib.rs` line 622.

### Proof of Concept
```rust
// crypto/dkg - demonstrate ThresholdKeys::read accepts an identity group key
use ciphersuite::{Ciphersuite, group::GroupEncoding};
use dkg::ThresholdKeys;
use dalek_ff_group::Ristretto;

// Build a serialized ThresholdKeys for t=1, n=1, i=1, Lagrange,
// secret_share = 0, verification_shares[1] = identity.
let mut buf = vec![];
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(1); // Interpolation::Lagrange
buf.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr()); // secret share
buf.extend(<Ristretto as Ciphersuite>::G::identity().to_bytes()); // vs[1] = identity

let keys = ThresholdKeys::<Ristretto>::read::<&[u8]>(&mut buf.as_ref()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // "owner" is now 0

// A Schnorr "signature" for this group key is forgeable by anyone:
// choose any s, set R = s*G; verify(identity, c) checks R + c*I - sG == 0.
```
