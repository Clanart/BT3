### Title
Desktop silently rewrites the local `origin` remote from a GitHub API response with no user confirmation, enabling remote hijack via repo rename/transfer front-run - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported Fintroller bug is a classic "read-then-act-on-a-mutable-external-value" (TOCTOU/front-run) flaw: a privileged party can change a critical parameter between the time a user forms an expectation and the time an action executes, and the contract silently uses the new value instead of asking for reconfirmation. The Desktop analog is `updateRemoteUrl()`, which silently rewrites the user's local git `origin` remote to whatever `clone_url` the GitHub API currently reports for the matched owner/name, with no prompt, whenever the repository is refreshed in the background.

### Finding Description
`updateRemoteUrl` compares the locally configured remote URL against the *current* value returned by the GitHub API (`apiRepo.clone_url`) and, if the stored `GitHubRepository.cloneURL` used to match the local remote and the protocol (https/ssh) is unchanged, it silently calls `gitStore.setRemoteURL()` to overwrite the local `origin` URL: [1](#0-0) 

This function is invoked automatically as part of `repositoryWithRefreshedGitHubRepository`, which runs during routine background/foreground repository refreshes (e.g. account-change refresh, periodic repository refresh flows), not only in response to an explicit user action: [2](#0-1) 

The owner/name used to query the API (`api.fetchRepository(owner, name)`) comes from `matchGitHubRepository`, which resolves the owner/login and repo name from the currently configured remote URL text, not from a stable, unforgeable GitHub repository ID. Any external party who can cause GitHub to report a different `clone_url` for that same `owner/name` slug at the moment of refresh (e.g., a rename/transfer of a repository shared with the victim, or a repo that was deleted and the name immediately re-registered by someone else) can front-run the victim's next background refresh. Because `remoteUrlUnchanged` only checks that the *local* remote still matches the *previously cached* API value (not that the *identity* — the underlying repository ID — is unchanged), the "front-run" happens purely on the server side: whoever controls what `GET /repos/{owner}/{name}` returns at refresh time controls where Desktop points the victim's `origin`.

Unlike the git-safety confirmations Desktop otherwise implements for untrusted repositories (`addSafeDirectory` / "unsafe repository" trust prompt), there is no analogous "the remote destination changed, please confirm" prompt for the automatic origin-URL rewrite performed here — see `UpstreamAlreadyExists` dialog, which *does* prompt before touching the `upstream` remote in the fork case, in contrast to `updateRemoteUrl`'s silent `origin` rewrite: [3](#0-2) 

### Impact Explanation
If `origin` is silently repointed to a URL that resolves (at push time) to a repository the attacker controls, the next push performed by the user via Desktop will send commits — and, more importantly, since the credential trampoline matches credentials by host (e.g. `github.com`), the user's real GitHub credential/token will be sent by the credential helper to authenticate against whatever repository now lives at that owner/name path: [4](#0-3) 

This falls under "silent corruption of what the user commits/pushes" and potential credential exposure to an unintended repository/collaborator set, matching the valid-impact criteria (unprivileged attacker controls a GitHub API object / remote response, resulting in silent corruption of push destination).

### Likelihood Explanation
The precondition is narrow: the attacker needs to be able to cause the GitHub API to return a changed `clone_url` for the exact `owner/name` combination Desktop has cached for that repository (e.g., a collaborator renaming/transferring a shared repo, or timing a rename to reclaim a freed slug), and the victim's Desktop client must perform a background refresh in that window. Desktop's own commit history/changelog documents this exact rename-following behavior as an intentional feature ("Update the remote url when a repository's name changes on GitHub"), confirming the code path is real and reachable, not hypothetical: [5](#0-4) 

The tests demonstrate this update happens automatically with no user interaction once the guard conditions are satisfied: [6](#0-5) 

Likelihood is Low-to-Medium: it requires a rename/transfer race under attacker's partial control of the target repo's naming, and normal usage means the guard conditions (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) are usually benign. But there is no user-facing confirmation gate at all, so if the preconditions align, exploitation is fully silent and automatic — unlike the on-chain report where governance/timelocks were argued to mitigate risk, here there is no equivalent "waiting period" or explicit reconfirmation step.

### Recommendation
Do not silently rewrite `origin` based solely on `owner/name` string matching and cached URL comparison. Instead:
1. Resolve and pin the repository by its immutable GitHub repository `id` (already stored as `GitHubRepository.dbID`/API `id`) rather than by `owner/name`, and verify the API's `id` for the fetched repo matches the previously known id before treating a `clone_url` change as a legitimate rename.
2. When the `id` matches but the `clone_url` differs (a legitimate rename/transfer), surface a confirmation dialog similar to `UpstreamAlreadyExists`, showing old vs. new URL, before calling `gitStore.setRemoteURL()`.
3. Treat an API-returned `clone_url` whose owner/name no longer resolves to the previously known repository `id` as untrusted and leave the local remote untouched.

### Proof of Concept
1. Victim clones `https://github.com/attacker-org/shared-repo` in Desktop and it becomes their `origin`; Desktop caches `GitHubRepository.cloneURL` for `attacker-org/shared-repo`.
2. Attacker (owner/admin of `attacker-org/shared-repo`) renames the repository to `attacker-org/shared-repo-old`, then creates a brand-new empty (or malicious) repository at `attacker-org/shared-repo` that the attacker fully controls.
3. Desktop performs a routine background refresh (`repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` resolves `owner=attacker-org, name=shared-repo` from the still-configured local remote URL text) and calls `api.fetchRepository('attacker-org','shared-repo')`, which now returns the *new* attacker-controlled repository's `clone_url` (same string as before, since name/owner slug is reused) — or, in the rename case, `updateRemoteUrl` sees `remoteUrlUnchanged === true` (matches previously cached URL) and `urlsMatch === false`, and silently calls `gitStore.setRemoteURL('origin', <new-url>)`.
4. The victim, unaware of the swap, makes local commits and pushes via Desktop's normal push flow (`app-store.ts:performPush` → `pushRepo`), sending their commits (and having their GitHub credential presented via the trampoline credential helper) to the attacker's repository instead of the original one.
