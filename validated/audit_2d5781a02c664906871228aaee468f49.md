Based on my research, I was unable to fully verify the exact off-chain storage mechanics before running out of tool calls, but I found a concrete, locally-grounded structural flaw that closely mirrors the report's bug class ("state-mutating logic executes on a path that is supposed to be a no-op / rolled back, and a persistent artifact escapes that rollback"). I present it below with explicit caveats on what remains unverified.

### Title
Fee withdrawal/accumulation logic (nonce advance, fee zeroing, ISMP dispatch) executes inside `validate_unsigned`, a revalidation path whose effects are assumed rolled back but may leak via non-transactional storage - (File: `modules/pallets/relayer/src/lib.rs`, `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet_ismp_relayer`'s `ValidateUnsigned::validate_unsigned` calls `Self::withdraw(...)` and `Self::accumulate(...)` directly — the same fully state-mutating functions invoked by the real dispatchables — instead of performing read-only checks. The pallet's own comment on `pre_dispatch` ("empty pre_dispatch so we don't modify storage") shows the authors believed state mutation only happens once, at block-application time via the dispatchable. In fact it happens first, and potentially repeatedly, inside `validate_unsigned`. [1](#0-0) 

### Finding Description
`validate_unsigned` is invoked by every node that receives the unsigned extrinsic (on submission, on gossip propagation, and again on every block-building attempt while it sits in the transaction pool) — this is standard Substrate transaction-pool behavior, and the design goal of `ValidateUnsigned::validate_unsigned` is to be a **side-effect-free** check, with actual state changes reserved for `pre_dispatch`/dispatch execution. This pallet inverts that: `validate_unsigned` calls the exact same `Self::withdraw` / `Self::accumulate` functions that mutate `Nonce`, zero `Fees`, and call `dispatcher.dispatch_request(...)` to emit a real ISMP POST request: [2](#0-1) 

`Self::withdraw` increments the per-relayer `Nonce`, zeroes `Fees`, and dispatches a POST request instructing the destination host manager to pay out the withdrawal amount: [3](#0-2) 

Normal on-chain storage mutations performed during `validate_unsigned` calls are discarded because pool-validation runs against a throwaway state overlay. However, `dispatch_request` on `pallet_ismp` participates in the ISMP request/commitment machinery which is documented elsewhere in this same codebase as using an MMR-with-offchain-body design (confirmed presence of `modules/pallets/ismp/src/offchain.rs`, referencing `leaf_index`/offchain storage). Substrate's `sp_io::offchain_index::set` writes are explicitly **not** part of the transactional storage overlay used for extrinsic/validation rollback — they persist independent of whether the enclosing call's on-chain storage changes are committed. If any part of the request-dispatch path taken by `Self::withdraw`/`Self::accumulate` writes through `offchain_index` (as ISMP's MMR-leaf-body storage typically does), then every discarded `validate_unsigned` invocation — not just the one that eventually lands in a block — can leave a persistent artifact (an off-chain-indexed request body, or a signature "provides" tag replay surface) even though the corresponding on-chain `Nonce`/`Fees`/MMR-commitment state was rolled back.

This is structurally the same defect as the external report: a code path that is not supposed to durably commit state (a reverted/failed meta-transaction there, a discarded transaction-validation run here) nonetheless leaves behind a persistent artifact (unincremented nonce there; an orphaned off-chain-indexed payload here) that a subsequent, unrelated execution can pick up and act on, decoupling the "authoritative" state (Nonce/Fees counters) from what was actually externally observable/dispatched.

**What I could not fully verify before running out of tool calls:** the exact content of `modules/pallets/ismp/src/offchain.rs` and `modules/pallets/ismp/src/impls.rs`, i.e., whether `dispatch_request`'s off-chain write key is derived from content-addressed data (safe) or from a predictable/sequential index (which could let a rolled-back `validate_unsigned` run corrupt or forge the off-chain body of a legitimately-dispatched request sharing the same key). Given the size limits on the codebase index, I recommend a Devin session with full repository access to trace `dispatch_request` → `offchain.rs` to confirm the write key derivation and whether it is reachable without a mined block.

### Impact Explanation
If confirmed, this allows an unprivileged relayer to force redundant or divergent off-chain-indexed ISMP request bodies to be written on every node validating a withdrawal/accumulate-fees transaction (i.e., far more often than once), independent of whether that specific transaction is ever included in a block. Depending on the key derivation this could (a) desynchronize the off-chain body a relayer/consumer retrieves from the on-chain commitment it is supposed to correspond to, or (b) in the worst case, overwrite/poison the off-chain body of a different, already-committed request if keys collide, causing wrong-body delivery for an unrelated cross-chain message — a false/incorrect payload being delivered to a destination `IsmpModule`.

### Likelihood Explanation
Medium-to-low confidence pending verification of the off-chain storage key scheme. The structural precondition (state-mutating logic inside `validate_unsigned` instead of purely-informational checks) is confirmed and reachable by any account submitting an unsigned `withdraw_fees`/`accumulate_fees` extrinsic with a validly-signed relayer payload — no privileged relayer/prover/admin role required, since these calls use `ensure_none(origin)` and are gated only by relayer signature verification, which any relayer can produce for their own fees.

### Recommendation
Make `validate_unsigned` perform only read-only validation (signature check, nonce/amount sanity, ISMP proof structure) without calling the actual mutating `Self::withdraw`/`Self::accumulate` functions, and move all storage-mutating and dispatch-triggering logic exclusively into `pre_dispatch`/the dispatchable body, consistent with the pallet's own stated intent ("empty pre_dispatch so we don't modify storage" — this guarantee is currently violated by `validate_unsigned`). Separately, audit `pallet_ismp`'s request-dispatch path for any `offchain_index::set` calls reachable from `validate_unsigned`, and ensure off-chain-indexed keys are content-derived (e.g., keyed by request commitment hash) rather than by predictable sequence numbers that could be produced by a discarded/never-committed execution.

### Proof of Concept
Conceptual, pending full verification of the off-chain key scheme:
1. A relayer with a nonzero `Fees` balance and valid signature submits `withdraw_fees` as an unsigned extrinsic.
2. Every node in the network that receives/gossips/attempts to build a block with this pending extrinsic calls `validate_unsigned`, which executes `Self::withdraw(...)` end-to-end, including `dispatcher.dispatch_request(...)`.
3. If `dispatch_request`'s off-chain body write happens outside the transactional overlay (per Substrate's `offchain_index` semantics), each of these N validation attempts (N ≥ 1, potentially every block-building cycle while the extrinsic is pending) leaves a persistent off-chain artifact, while only one attempt's on-chain `Nonce`/`Fees`/commitment mutation is ever actually finalized.
4. This mismatch between "how many times the dispatch side-effect fired" and "how many times the authoritative state advanced" is the direct structural analog of the reported `NativeMetaTransaction` nonce/replay bug. [4](#0-3) [5](#0-4)

	#[pallet::validate_unsigned]
	impl<T: Config> ValidateUnsigned for Pallet<T>
	where
		<T as frame_system::Config>::Hash: From<H256>,
		<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		T::Balance: Into<u128>,
	{
		type Call = Call<T>;

		// empty pre-dispatch so we don't modify storage
		fn pre_dispatch(_call: &Self::Call) -> Result<(), TransactionValidityError> {
			Ok(())
		}

		fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
			let res = match call {
				Call::accumulate_fees { withdrawal_proof } =>
					Self::accumulate(withdrawal_proof.clone()),
				Call::withdraw_fees { withdrawal_data } => Self::withdraw(withdrawal_data.clone()),
				Call::claim_outbound_consensus_delivery_reward { claim } =>
					Self::process_outbound_consensus_delivery_claim(claim.clone()),
				Call::claim_outbound_request_delivery_reward { claim } =>
					Self::process_outbound_request_delivery_claim(claim.clone()),
				_ => Err(TransactionValidityError::Invalid(InvalidTransaction::Call))?,
			};

			if let Err(err) = res {
				log::error!(target: "ismp", "Pallet Relayer Fees error {err:?}");
				Err(TransactionValidityError::Invalid(InvalidTransaction::Call))?
			}

			let encoding = match call {
				Call::accumulate_fees { withdrawal_proof } => withdrawal_proof.encode(),
				Call::withdraw_fees { withdrawal_data } => withdrawal_data.encode(),
				Call::claim_outbound_consensus_delivery_reward { claim } => claim.encode(),
				Call::claim_outbound_request_delivery_reward { claim } => claim.encode(),
				_ => unreachable!(),
			};

			let msg_hash = sp_io::hashing::keccak_256(&encoding).to_vec();

			Ok(ValidTransaction {
				priority: 100,
				requires: vec![],
				provides: vec![msg_hash],
				longevity: TransactionLongevity::MAX,
				propagate: true,
			})
		}
	}
