### Title
User-chosen stale GET-proof height in `_cancelFromSource` lets an order owner reclaim escrow after a solver has already filled, permanently bricking the solver's `RedeemEscrow` claim - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The Streamr report's core invariant break is: a finalization function derives its unlock/settlement amount from **whatever the "current" on-chain state happens to be**, rather than from an amount fixed at the moment the obligation was created, and a party can reset that current state through an unrelated legitimate action, permanently reverting settlement. In Hyperbridge's `IntentGatewayV2` cross-chain intents (`evm/src/apps/intentsv2/ExtrinsicIntents.sol` + `evm/src/apps/intentsv2/IntentsBase.sol`), the analogous broken invariant is that `_cancelFromSource` proves "not yet filled" using a **user-supplied historical height** rather than the *current* destination state, and `_withdraw` derives its unlock amount from `_orders[commitment][token]`, which is a single mutable bucket shared by both the cancellation-refund path and the solver's redeem path.

### Finding Description
`_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171`) lets a solver deliver output tokens to the beneficiary on the destination chain and then dispatches a `RedeemEscrow` POST (with `timeout: 0`, i.e. it can never time out and be refunded) back to the source chain: [1](#0-0) 

`_cancelFromSource` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:188-223`) lets the order owner, after the deadline, dispatch a `DispatchGet` at a **caller-chosen `options.height`** to prove the `_filled` slot is empty on the destination: [2](#0-1) 

Because `options.height` is attacker-controlled and only bounded to be a height Hyperbridge has finalized consensus for (not necessarily the *latest* height), the order owner can pick a height that predates the solver's fill transaction on the destination chain. At that historical height `_filled[commitment]` is genuinely empty, so `onGetResponse` accepts the proof and calls `_withdraw(body, true, true)`, refunding the full escrow to the user: [3](#0-2) 

`_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-425`) unconditionally zeroes `_orders[commitment][token]` on this refund: [4](#0-3) 

When the solver's earlier `RedeemEscrow` message later arrives at `onAccept` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:289-309`), it calls `_withdraw` again for the same commitment/token, but `escrowed == 0` now, so the guard reverts with `UnknownOrder`: [5](#0-4) 

Because the `RedeemEscrow` POST was dispatched with `timeout: 0`, it can never time out and be reprocessed as a refund either — like `_endVote()` in the original report, this message is now stuck reverting forever. The order owner ends up with both: (a) the destination-side output tokens the solver already delivered to the beneficiary, and (b) their source-chain escrow refunded, while the solver who honestly filled the order is left with nothing and no recovery path — a double-settlement / stolen-funds outcome caused entirely by the caller-controlled proof height, with no relayer, prover, or admin collusion required.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary" invariant. An unprivileged order owner (attacker) can:
1. Wait for a solver to fill their order on the destination chain (paying out real value to the beneficiary).
2. Dispatch `_cancelFromSource` with `options.height` set to any Hyperbridge-finalized height prior to the fill block.
3. Receive back their escrowed input tokens on the source chain via `onGetResponse` → `_withdraw`.
4. Permanently deny the solver's legitimate `RedeemEscrow` claim (revert-forever, unrecoverable since `timeout: 0`).

Net effect: direct theft of solver funds/output tokens and permanent denial of the solver's rightful escrow claim — a concrete "unauthorized transaction," "double-settlement," and "fund loss" scenario matching the bounty's in-scope impacts.

### Likelihood Explanation
The only precondition is that Hyperbridge has finalized at least one destination-chain state commitment prior to the fill block — a routine, always-true condition once cross-chain communication is live; no relayer misbehavior, no malicious prover, and no admin action is required. The attacker only needs to be the order's own `user` (who is always authorized to cancel after `order.deadline`) and to control the `options.height` argument passed to their own `_cancelFromSource` call, which the contract does not validate against "latest known height" or against the fill's actual block.

### Recommendation
Do not let the GET height be freely chosen by the canceller for a state check whose semantics require "never filled," not "not filled as of some point in time." Either:
- Require `options.height` to equal (or be no less than) the *latest* Hyperbridge-known finalized height for the destination chain at dispatch time, so a stale/pre-fill snapshot cannot be used; and/or
- Make the escrow release atomic and idempotent across both settlement paths by having `_withdraw` check/set a single terminal `_filled`/`settled` flag *before* consulting `_orders`, and have the cancellation path also verify (via the receipt/nonce or a second, freshest-height GET) that no `RedeemEscrow` for this commitment is already in flight, or preferably give `RedeemEscrow` a nonzero `timeout` with a defined `onPostRequestTimeout` refund path so a lost race resolves at the destination gateway instead of reverting-forever on the source.

### Proof of Concept
1. User places a cross-chain order via `placeOrder` on the source chain (Chain A), depositing tokens into `_orders[commitment][tokenA]`.
2. Solver calls `_fillCrossChain` on the destination chain (Chain B) at block `H_fill`, delivering output tokens to the beneficiary and dispatching a `RedeemEscrow` POST (timeout 0) back to Chain A.
3. Hyperbridge finalizes a Chain B state commitment at some height `H_stale < H_fill` (this exists because consensus updates are periodic and Hyperbridge tracks a range of historical finalized heights, not only the newest one).
4. After `order.deadline` passes, the user calls `_cancelFromSource(order, options{height: H_stale, ...}, commitment)`. This dispatches a `DispatchGet` reading the `_filled` slot at `H_stale`, where the slot is provably empty (fill happened at `H_fill > H_stale`).
5. `onGetResponse` receives the empty-slot proof, calls `_withdraw(body, true, true)`, refunding the user's `_orders[commitment][tokenA]` and zeroing it.
6. The solver's `RedeemEscrow` POST (dispatched in step 2) is delivered to `onAccept` on Chain A. `_withdraw` reads `escrowed = _orders[commitment][tokenA] == 0` and reverts with `UnknownOrder` — permanently, since the request has `timeout: 0` and cannot be resubmitted as a timeout-refund.
7. Result: user has both the destination-side output tokens (from the solver) and the source-side escrow refund; solver's claim is irrecoverably stuck reverting.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    /**
     * @dev Handles the response to a Hyperbridge GET request dispatched during
     * `_cancelFromSource`. Verifies that the `_filled` storage slot on the destination
     * chain is empty (meaning the order was never filled), then refunds the escrowed
     * tokens to the original user. Reverts with `Filled` if the slot is non-empty.
     *
     * @param incoming The incoming GET response from Hyperbridge containing the storage proof.
     */
    function onGetResponse(IncomingGetResponse calldata incoming) external override onlyHost {
        if (incoming.response.values[0].value.length != 0) revert Filled();

        WithdrawalRequest memory body = abi.decode(incoming.response.request.context, (WithdrawalRequest));
        _withdraw(body, true, true);
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
