## Analog identified

### Title
`resolveWithin()` uses an unanchored `String.prototype.startsWith` boundary check, allowing a same-prefixed sibling directory to be treated as "inside" the root - ([File: app/src/lib/path.ts])

### Summary
The Sherlock finding's root cause is a boundary-comparison bug: `sqrtRatioX96 <= sqrtRatioAX96` treats the *equal* boundary as "outside the range" when Uniswap's own semantics require strict `<`. The Desktop analog is the same class of bug in the path-containment guard `resolveWithin()`: it decides "is this path inside the root?" using `realResolved.startsWith(realRoot)` with no check that the next character after the shared prefix is a path separator. Just as the audit bug misclassifies the exact boundary tick as out-of-range, this code misclassifies a **sibling** directory whose name merely starts with the same characters as the root directory as being *inside* the root.

### Finding Description
`_resolveWithin()` is the shared sandbox primitive used across Desktop to make sure a relative, possibly attacker-influenced path segment stays inside a trusted root directory: [1](#0-0) 

The final check is:
```ts
return realResolved.startsWith(realRoot) ? resolved : null
```
This is a pure string-prefix test. It does not require that `realResolved` either equals `realRoot` or continues with `Path.sep` immediately after the shared prefix. Consequently, if a directory `…/myrepo-evil` exists alongside the trusted root `…/myrepo`, then `realpath('…/myrepo-evil/x')` starts with `realpath('…/myrepo')` as a plain string, even though `myrepo-evil` is a completely different directory tree. The same off-by-boundary mistake as the Solidity code (`<=` where `<` — or here, "prefix match" where "prefix + separator match" — was required) causes the guard to accept paths it was designed to reject.

Contrast this with `isClonePathSensitive()` in the same codebase, which gets the boundary right by explicitly appending the separator: [2](#0-1) 
`resolveWithin` lacks this same discipline.

### Impact Explanation
`resolveWithin()` is the security boundary relied on by at least two attacker-reachable call sites:

1. **Deep link file reveal** — `Dispatcher.openRepositoryFromUrl()` takes a `filepath` straight from an `x-github-client://openRepo` deep link that the user clicks, rejects only absolute paths, then calls `resolveWithin(repository.path, filepath)` before handing the result to `shell.showItemInFolder(resolved)`: [3](#0-2) 
Because the boundary check is prefix-based, a crafted relative `filepath` (e.g. `../<repo-name>-something/target`) that lands in a same-prefixed sibling directory will pass the guard meant to keep the reveal action confined to the opened repository, exposing/opening arbitrary sibling paths outside the repo — a direct "read/expose outside the repo" via a link the user clicked.

2. **Conflict content read + exfiltration to Copilot** — `buildConflictContext()` resolves each conflicted file's repository-relative path with the same guard, then reads its full content and later ships that content to the Copilot API in the resolution prompt: [4](#0-3) [5](#0-4) 
If a conflicted-file path can be made to resolve into a same-prefixed sibling directory (rather than strictly under `workingDirectory`), the guard's job — "never let a diff entry escape the repo" — fails silently, and file content from outside the repository could be read and forwarded to an external API call, i.e., a form of unbounded file read + potential exfiltration.

Both consumers assume `resolveWithin` returning non-null guarantees strict-subtree containment; the implementation only guarantees a shared string prefix.

### Likelihood Explanation
The precondition (an existing filesystem entry whose name starts with the trusted root's name, e.g. `myrepo` vs. `myrepo-hooks`) is a real-world, plausible layout: GitHub Desktop's default clone location groups many repositories side-by-side under `~/Documents/GitHub/`, and repo names are attacker-influenced when the flow originates from an attacker-supplied clone URL / deep link. Existing regression tests for `resolveWithin` only cover `..`-only escapes and symlink escapes, not the same-prefix-sibling case, so this boundary bug is not currently caught by the guarded test suite: [6](#0-5) 

Note: I was not able to fully trace, within the available iterations, whether `buildConflictContext`'s `files[].path` values can be driven to contain traversal segments from ordinary git-conflict listings (this would need confirmation in `app-store.ts`). The deep-link path (`dispatcher.ts`) is the stronger, directly-verifiable primitive since `filepath` is taken verbatim from a URL the user clicks.

### Recommendation
Change the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to require an exact match or a match followed by the platform path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
and add a regression test asserting that a sibling directory sharing a name prefix with the root (e.g. `root` vs `root-evil`) is rejected.

### Proof of Concept
1. Victim has `~/Documents/GitHub/myrepo` (a Desktop-managed repository) and, coincidentally or via a prior attacker-influenced clone, `~/Documents/GitHub/myrepo-secrets` also exists on disk.
2. Attacker sends the victim a link: `x-github-client://openRepo?url=<url-for-myrepo>&filepath=..%2Fmyrepo-secrets%2Fid_rsa`.
3. Victim clicks the link; Desktop resolves the already-open `myrepo` repository, `isAbsolute(filepath)` is false so the guard proceeds, and `resolveWithin('~/Documents/GitHub/myrepo', '../myrepo-secrets/id_rsa')` computes `realResolved = ~/Documents/GitHub/myrepo-secrets/id_rsa`, which `startsWith('~/Documents/GitHub/myrepo')` as a raw string — passing the guard.
4. `shell.showItemInFolder(resolved)` reveals/opens the out-of-repo file, even though the code's intent (and the log message on failure) explicitly states the goal is to prevent exactly this: "Prevented attempt to open path outside of the repository root." [7](#0-6)
