### Title
Global `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` caps in the gasless module can reject legitimate gasless swaps due to unrelated senders' congestion - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
`GaslessModule.PreAddTx` rejects an incoming approve/swap ("bundle") transaction with `ErrBundleTxQueueFull` whenever the global counter `g.knownTxs.numQueue()` is at or above `MaxBundleTxsInQueue` [1](#0-0) . Likewise, `IsReady` blocks promotion to pending using the shared `MaxBundleTxsInPending` counter, computed from `numExecutable` across *all* senders [2](#0-1) . These are exactly the "maximum capital/aggregate cap" pattern described in the report: a single global counter shared by all unrelated transaction senders that, once saturated by other users' bundle activity, causes a legitimate, well-formed transaction from a new sender to be rejected outright rather than simply deprioritized.

### Finding Description
The gasless config defines global limits `MaxBundleTxsInPending` and `MaxBundleTxsInQueue` (default 100 / 200) [3](#0-2) . `PreAddTx` is invoked for every incoming transaction that is a gasless bundle tx (approve/swap pair), and it hard-rejects admission into the tx pool if `numQueue()` — a count aggregated across *all* senders' queued bundle transactions — has reached the configured cap [4](#0-3) . The count is computed globally over the `knownTxs` map, not per-sender [5](#0-4) .

This is structurally the same defect pattern as the Size report: `validateBorrowATokenCap` reverted a user's legitimate deposit because the *global* aToken balance (driven by unrelated market activity) had grown past the cap, even though the user's own deposit was harmless or even risk-reducing (e.g., adding collateral to avoid liquidation). Here, an unrelated, unprivileged public RPC caller submitting many gasless swap/approve bundle transactions can drive the shared `numQueue()`/`numExecutable()` counters up, causing a completely unrelated sender's legitimate gasless swap (which pays no ETH gas and depends on this mechanism to be included at all) to be rejected with `ErrBundleTxQueueFull`, or to be silently starved from promotion at `IsReady`.

### Impact Explanation
Because gasless users have no other means to pay gas directly (that's the entire point of the gasless module), an unrelated cap being globally exhausted denies them the only path to get their transaction included — unlike a normal EOA which could still pay ordinary gas to get a transaction in. This can be weaponized by a cheap flood of low-value approve/swap bundle pairs from many searchers/senders (bounded only by normal EOA transaction costs) to keep `numQueue()`/`numExecutable()` pinned at the cap, denying admission or promotion to a targeted victim's gasless swap indefinitely — effectively a denial-of-service/griefing vector against specific gasless users routed through a shared global resource, not a per-account limit.

### Likelihood Explanation
Any unprivileged public RPC caller can submit approve/swap transaction pairs recognized as bundle txs by `IsModuleTx` (`IsApproveTx`/`IsSwapTx`) [6](#0-5) , so reaching and maintaining the global cap requires no special privilege — only enough EOA transactions/nonces from possibly many low-funded accounts to keep `numQueue` at `MaxBundleTxsInQueue` (default 200) or `numExecutable` at `MaxBundleTxsInPending` (default 100).

### Recommendation
Follow the same remediation direction acknowledged by the Size team: replace the raw global aggregate check with a per-sender or per-target-tx quota (so unrelated congestion cannot block a specific legitimate sender), or make the cap eviction-based (evict the oldest/lowest-priority queued bundle tx to make room, similar to how `TxPool.add` evicts underpriced transactions) rather than unconditionally rejecting new legitimate submissions once the global counter is saturated.

### Proof of Concept
1. Deploy/enable the gasless module with default config (`MaxBundleTxsInQueue = 200`).
2. From N attacker-controlled EOAs (funded only enough to satisfy `checkBalanceForApprove`/`checkBalanceForSwap` token-balance checks), submit valid approve+swap bundle pairs so that `g.knownTxs.numQueue()` reaches 200, per `PreAddTx`'s counting logic [4](#0-3) .
3. Have the victim (a legitimate, unrelated gasless user) submit their own valid approve/swap pair.
4. Observe `PreAddTx` returns `ErrBundleTxQueueFull` for the victim's transaction purely because of the global counter, even though the victim's transaction is fully valid and unrelated to the attacker's activity — analogous to the Size deposit being reverted by an unrelated global aToken cap.
