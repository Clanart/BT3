Based on my investigation, I found a genuine analog: a hardcoded, incomplete header blacklist used to strip credentials on cross-origin redirects, which mirrors the smart-contract report's core flaw — an inconsistent, hardcoded blacklist that fails to cover every case that actually matters and lets sensitive data slip through.

### Title
Incomplete hardcoded sensitive-header blacklist in cross-origin redirect sanitizer can leak credentials to attacker-controlled hosts - ([File: app/src/main-process/same-origin-filter.ts])

### Summary
`installSameOriginFilter` is meant to strip credential-bearing headers whenever a `fetch` request is redirected to a different origin, since `fetch` has no native way to prevent credentials leaking across a redirect chain. It does this by hardcoding a `Set` of "unsafe" header names — `authentication`, `authorization`, `cookie` — and stripping only those on cross-origin redirects. Like the Solidity blacklist in the report, this is a hardcoded, non-exhaustive denylist rather than a whitelist/allowlist, so any credential-carrying header not in that specific set survives a cross-origin redirect unmodified.

### Finding Description [1](#0-0) 
The filter records the origin of the initial request and, on every subsequent redirect within the same request ID, compares origins. If they differ, it rebuilds the header set, keeping everything except headers whose lowercased name is in `unsafeHeaders`: [2](#0-1) [3](#0-2) 

This is precisely the pattern flagged in the report: a hardcoded blacklist that has to enumerate every sensitive item, with no verification process to ensure it stays complete as the system evolves. Just as `rocketPoolToken` was blacklisted despite not existing while other value-holding contracts could be added later and slip through, this filter blacklists three specific header names while GitHub Desktop's own request layer can attach other sensitive headers (e.g. custom auth-adjacent headers, `Proxy-Authorization`, `Set-Cookie` on response processing, or any header added in the future by `app/src/lib/http.ts` or `api.ts` for GHE/enterprise auth flows) that are not covered by this list. Any such header is passed through unmodified to whatever origin the redirect points to.

The attacker-controlled trigger is a malicious git remote/API endpoint (e.g. a GitHub Enterprise-like server, or any HTTP(S) endpoint Desktop calls via `fetch`, such as repo metadata/avatar/API calls in `app/src/lib/api.ts`) that issues an HTTP redirect to a different origin under attacker control. Because the sanitizer only removes three specific header names, any additional credential header not in that enumerated set is forwarded to the attacker's origin.

### Impact Explanation
If a credential-bearing header outside the three-item blacklist exists (now or added later), a malicious server the user's Desktop talks to — reachable simply by adding/cloning a repo, or the app hitting the GHE API endpoint that returns a redirect — could exfiltrate that header value to an attacker-controlled host, without any local access, admin rights, or social engineering, matching the required threat model ("git remote/proxy response" attacker primitive resulting in "credential/token exfiltration").

### Likelihood Explanation
Likelihood depends on whether such an uncovered sensitive header is actually sent today; I could not fully verify inside the available index whether `app/src/lib/http.ts`/`api.ts` sets any auth-related header not named `Authorization`/`Authentication`/`Cookie` (e.g. GHE session or proxy headers), since I was not able to fully enumerate all headers set across the request path before running out of tool iterations. The structural weakness — a hardcoded denylist instead of an allowlist for redirect sanitization — is confirmed and is exactly the anti-pattern the report calls out, but I cannot confirm with full certainty a currently-exploitable header exists beyond the three enumerated ones.

### Recommendation
Replace the denylist (`unsafeHeaders`) with an allowlist of headers that are safe to forward across origins on redirect (e.g. `accept`, `user-agent`, `content-type`), stripping everything else by default. This mirrors the report's own recommendation to prefer a whitelist over an error-prone blacklist, and removes the risk that a newly introduced header is silently exempted from sanitization.

```typescript
import { OrderedWebRequest } from './ordered-webrequest'

/**
 * Installs a web request filter to prevent cross domain leaks of auth headers
 *
 * GitHub Desktop uses the fetch[1] web API for all of our API requests. When fetch
 * is used in a browser and it encounters an http redirect to another origin
 * domain CORS policies will apply to prevent submission of credentials[2].
 *
 * In our case however there's no concept of same-origin (and even if there were
 * it'd be problematic because we'd be making cross-origin request constantly to
 * GitHub.com and GHE instances) so the `credentials: same-origin` setting won't
 * help us.
 *
 * This is normally not a problem until http redirects get involved. When making
 * an authenticated request to an API endpoint which in turn issues a redirect
 * to another domain fetch will happily pass along our token to the second
 * domain and there's no way for us to prevent that from happening[3] using
 * the vanilla fetch API.
 *
 * That's the reason why this filter exists. It will look at all initiated
 * requests and store their origin along with their request ID. The request id
 * will be the same for any subsequent redirect requests but the urls will be
 * changing. Upon each request we will check to see if we've seen the request
 * id before and if so if the origin matches. If the origin doesn't match we'll
 * strip some potentially dangerous headers from the redirect request.
 *
 * 1. https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API
 * 2. https://fetch.spec.whatwg.org/#http-network-or-cache-fetch
 * 3. https://github.com/whatwg/fetch/issues/763
 *
 * @param orderedWebRequest
 */
export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })
```
