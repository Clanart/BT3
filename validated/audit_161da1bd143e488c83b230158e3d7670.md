### Title
Argument injection in `git checkout` via malicious ref name due to misplaced `--` separator - (File: app/src/lib/git/checkout.ts)

### Summary
`getBranchCheckoutArgs` builds checkout argv as `[branch.name, '-b', branch.nameWithoutRemote (if remote), '--']`, appending the `--` end-of-options marker *after* the branch name instead of before it.

### Finding Description
`getBranchCheckoutArgs` returns the branch name as the first element, followed optionally by `-b <local-name>`, with `--` placed last: [1](#0-0) 
These args are then concatenated after `['checkout', ...]` and passed to `spawnGit`/`git`: [2](#0-1) 
The `--` separator only tells the command-line parser to treat everything *after* it as a positional argument; anything appearing *before* `--` is still parsed as a normal option. Since `branch.name` is placed before `--`, a ref name beginning with `-` would still be interpreted as an option/flag by `git checkout`, not as the intended ref, defeating the purpose of the separator.

`branch.name` originates from `getBranches` in `app/src/lib/git/for-each-ref.ts`, which populates `Branch` objects directly from `%(refname:short)` output of `git for-each-ref` against the local repository's refs (including `refs/remotes/*` created by `git fetch`): [3](#0-2) 
This value is never passed through `sanitizedRefName`; that sanitizer is exclusively wired into UI text inputs for locally-typed branch names (create-branch/rename-branch dialogs), not into the fetch/branch-listing pipeline: [4](#0-3) 

### Impact Explanation
If exploitable, a malicious remote could advertise a ref name that git accepts locally but that begins with `-`, and Desktop's `checkoutBranch` would then hand git checkout an argv where the attacker-controlled string is parsed as an option rather than a ref. Depending on which git-checkout flag can be smuggled this way, this could range from a harmless error to more consequential option injection (e.g., something like `--to=<path>`-style file writes if such flags existed on `checkout`), i.e. potential argv injection into the `git` sink.

### Likelihood Explanation
This depends entirely on whether upstream `git` itself permits creating a local/remote-tracking ref whose short name begins with `-` (i.e., whether `git fetch`/`check_refname_format` rejects such ref advertisements before Desktop ever sees them). I could not verify this within the codebase — `git`'s own ref-name validation lives outside this repository (in git/dugite itself), and I found no code in `blackvul/desktop--010` that either allows or blocks such names when fetching. This is the key unresolved fact needed to determine real-world exploitability; the code-level issue (placing `--` after `branch.name` instead of before it) is real and independently verifiable, but whether it is reachable with attacker-controlled remote refs requires confirming git's own ref-name acceptance rules, which I cannot confirm from this codebase alone.

### Recommendation
Regardless of whether git's own validation currently blocks such names, defense-in-depth dictates fixing the argument order: place `--` immediately before the branch name (after any option flags like `-b <name>`), e.g. `['-b', branch.nameWithoutRemote, '--', branch.name]` (for remote branches) and `['--', branch.name]` otherwise, mirroring the pattern already used correctly in `checkoutPaths` (`app/src/lib/git/checkout.ts:215`) and `checkoutConflictedFile` (`app/src/lib/git/checkout.ts:231`), which put `--` before the untrusted path/ref.

### Proof of Concept
Not fully verifiable without confirming whether `git fetch` will actually create a local ref whose short name starts with `-` from a malicious remote's advertised refs — this requires testing against real `git`/`dugite` behavior, which is outside the scope of static code review of this repository. If such a ref can be created (e.g. `refs/remotes/origin/-flag`), then calling `checkoutBranch(repository, branch, ...)` with `branch.name === '-flag'` would produce argv `['checkout', '-flag', '-b', 'flag', '--']`, in which `-flag` is parsed by git as an option before the `--` guard applies.
