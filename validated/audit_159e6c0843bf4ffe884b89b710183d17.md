### Title
Missing slippage protection in `WombatPoolHelperV2.depositFor()` exposes depositors to sandwich attacks - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2.depositFor()` is a public function that any wallet can call to deposit stable tokens into the Wombat pool on behalf of an arbitrary `_for` address (including itself). Unlike the sibling `deposit()` function, which lets the caller specify `_minimumLiquidity`, `depositFor()` hardcodes the slippage parameter to `0`, removing the only protection against adverse price movement/sandwich attacks during the swap-like deposit into the Wombat pool.

### Finding Description
`deposit()` forwards a caller-supplied `_minimumLiquidity` to `WombatStaking.deposit()`, which passes it through to the underlying `IWombatPool.deposit()` call and reverts if the LP/liability minted is below that threshold: [1](#0-0) 

However, `depositFor()` ignores any slippage input and always calls `_deposit(_amount, 0, _for, address(this))`: [2](#0-1) 

This `0` is passed all the way down as `_minimumLiquidity` in `WombatStaking.deposit()`, which is the exact parameter documented elsewhere as "the minimal amount the user accepts because of slippage": [3](#0-2) 

Because the Wombat pool's deposit liquidity calculation depends on the pool's cash/liability ratio at execution time (an AMM-like invariant), a searcher can manipulate that ratio in the same block (front/back-run) so the depositor's `lpReceived` is minimized, with the difference captured by the attacker. Since `depositFor()` cannot ever set a non-zero minimum, this protection is unconditionally disabled for every call to it, unlike `deposit()`, `depositNative()`, or `withdraw()`, all of which take a caller-supplied minimum.

### Impact Explanation
Any user calling `depositFor()` (including a normal user self-depositing via this entry point) receives no guarantee on the LP/staking-token amount minted for their deposited stablecoins. An attacker can sandwich the transaction to shift the pool's cash/liability ratio unfavorably, causing the victim to receive fewer LP/staking tokens than the fair-value deposit would produce — the extracted value is a direct, concrete loss of the depositor's principal value to the attacker. This is a direct theft-of-funds vector reachable by any ordinary wallet transaction (both as attacker and victim), with no privileged role required.

### Likelihood Explanation
Likelihood is medium: it requires a sandwich attacker to detect a `depositFor()` call in the mempool and have enough capital to move the pool's cash/liability ratio, and the pool must have sufficient depth imbalance potential. This is a routine MEV pattern for AMM-style deposits and does not require any privileged access, so it is realistically exploitable whenever `depositFor()` is used with non-trivial deposit sizes.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor()` (analogous to `deposit()`/`depositNative()`) and forward the caller-supplied value instead of hardcoding `0`:
```solidity
function depositFor(uint256 _amount, uint256 _minimumLiquidity, address _for) external {
    IERC20(depositToken).safeTransferFrom(msg.sender, address(this), _amount);
    IERC20(depositToken).safeApprove(wombatStaking, _amount);
    _deposit(_amount, _minimumLiquidity, _for, address(this));
}
```

### Proof of Concept
1. Attacker monitors mempool for a pending `WombatPoolHelperV2.depositFor(amount, for)` transaction.
2. Attacker front-runs with a large swap/deposit into the same Wombat pool to skew the cash/liability ratio unfavorably for the victim's deposit token.
3. Victim's `depositFor()` executes with `_minimumLiquidity = 0` hardcoded at [2](#0-1) , so it cannot revert regardless of how little liquidity/LP is minted.
4. Attacker back-runs to restore the ratio and extract the value skimmed from the victim's deposit, while the victim is minted a reduced `lpReceived`/receipt token amount at [4](#0-3) .
