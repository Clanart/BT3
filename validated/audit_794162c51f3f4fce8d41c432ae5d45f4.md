### Title
`SignableTransaction::new` excludes the OP_RETURN output from the fee/weight estimation, underpaying the intended fee rate and bypassing the max-weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds `tx_outs` including an optional `OP_RETURN` output carrying up to 80 bytes of attacker/integrator-supplied `data`, but calls `calculate_weight_vbytes(tx_ins.len(), payments, ...)` — passing `payments`, not `tx_outs` — so the `OP_RETURN` output is never included in the estimated weight, vbytes, or fee. Like the referenced `getL1GasUsed()` issue, the cost is computed from a size estimate that omits a real, variable-sized component of the final transaction.

### Finding Description
`calculate_weight_vbytes` constructs a mock transaction whose outputs are built solely from `payments` and an optional `change` output (networks/bitcoin/src/wallet/send.rs:85-99). In `new`, the `OP_RETURN` output is appended to `tx_outs` (lines 194-202) *before* the weight is computed at line 204 and again at lines 224-226 for the change variant, but both calls pass `payments` rather than the actual output set:

- The estimated `vbytes`/`weight` therefore excludes the `OP_RETURN` output (8-byte value + script length + 1-byte `OP_RETURN` + push opcode + up to 80 bytes of data ≈ up to ~92 WU·4 ≈ ~92 vbytes since it's non-witness data).
- `needed_fee = fee_per_vbyte * vbytes` (line 206/227) is thus lower than the fee required to actually achieve `fee_per_vbyte` on the broadcast transaction.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the underestimated `weight`, so a transaction whose real weight exceeds the standardness limit can be accepted.
- The `TooLowFee` check at line 211 compares `needed_fee` against the relay minimum for the underestimated `vbytes`, also missing the extra output.

The actual transaction assembled at lines 245-255 does contain the `OP_RETURN` output, so the signed/broadcast transaction is strictly larger than what the fee and weight accounting assume. The difference is attacker-influenceable: `data` is public input (e.g., the `Shorthand` payload used for in-instructions/burns), and a full 80-byte payload maximizes the underpayment.

### Impact Explanation
When a change output is used, the paid fee equals `needed_fee`, which was computed for a smaller virtual transaction. The broadcast transaction's effective fee rate is below the requested `fee_per_vbyte`, potentially below the prevailing relay/mempool minimum near boundary conditions, causing transactions to stall, be evicted, or require fee-bumping. When no change is used, the excess input value becomes fee regardless, but the `needed_fee`/`NotEnoughFunds`/`TooLowFee` logic is still computed against an incorrect size, and the `MAX_STANDARD_TX_WEIGHT` check can be bypassed, producing a transaction that standard nodes will not relay. This matches the report's class: a fee/size formula that assumes a fixed shape and omits a variable component, producing incorrect fee calculation.

### Likelihood Explanation
Any plan using `data` triggers it; the discrepancy grows with `data.len()` up to 80 bytes. It requires no adversarial validator or leaked key — only a transaction carrying an `OP_RETURN` payload, which is the normal mechanism for Serai in-instructions. The monetary loss is bounded (at most `fee_per_vbyte * ~92` sat of mis-estimation per transaction), so it maps to Medium/Low rather than High.

### Recommendation
Pass the actual output set into `calculate_weight_vbytes`. Either change its signature to accept `&[TxOut]`/`tx_outs` plus `change`, or call it after constructing `tx_outs` (including the `OP_RETURN` output) so `needed_fee`, the minimum-relay check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
```rust
// Conceptual: an input of value V, one payment, change, and 80 bytes of data.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), fee_per_vbyte)?;

// tx.needed_fee() == fee_per_vbyte * vbytes(payments + change)
// but the real transaction also carries the OP_RETURN output (~+92 vbytes),
// so tx.vsize() * fee_per_vbyte > tx.needed_fee() — the signed transaction
// pays a lower fee rate than requested, and `weight` checked against
// MAX_STANDARD_TX_WEIGHT never saw the OP_RETURN output.
```
The defect is visible directly in the code: `tx_outs` gains the `OP_RETURN` output at send.rs:194-202, while both `calculate_weight_vbytes` invocations (send.rs:204, 225-226) receive `payments` only.
