## Analysis

The reported bug class is an **unbounded loop that scales with a user-controlled data structure and can stall processing** when that structure grows large. The closest reachable analog in this codebase is in `chia/wallet/trading/offer.py`, in `Offer.get_cancellation_coins()`, which is invoked from `TradeManager.cancel_pending_offers()` — a completely ordinary wallet action (cancel an offer) that any wallet user can trigger, but whose input data can be attacker-controlled via an untrusted offer file received from a counterparty.

### Root cause

`Offer.get_cancellation_coins()` builds `dependencies`/`announcements` maps keyed by coin name, then repeatedly calls `detect_dependent_coin()`: [1](#0-0) 

and drives a nested nesting of `while True` loops to peel off dependent coins: [2](#0-1) 

`detect_dependent_coin` itself does a triple-nested scan (`names` × `deps[name]` × `announcement_dict.items()`), and it is called again from scratch on every iteration of the outer `while True` loop in `get_cancellation_coins`, with the inner `while True` loop also rescanning `dependencies.items()` on every pass. For a spend bundle with `n` coin spends, each producing announcement/assertion conditions, this is effectively an O(n^3)–O(n^4) computation with no cost accounting, no timeout, and no upper bound on `n` — directly analogous to the reported `_getUnlockedLiquidity` unbounded-loop pattern, except here the “locked amounts” are attacker-supplied coin spends/announcements inside an offer file.

### Reachability

`get_cancellation_coins()` operates on `self._bundle.coin_spends`, i.e., the full spend bundle of an `Offer`, which for a taker is the *aggregated* offer (maker’s untrusted coin spends plus the taker’s own), produced in `TradeManager.respond_to_offer`: [3](#0-2) 

That combined offer (bytes) is what gets stored as the trade record and is later fed straight into `get_cancellation_coins()` whenever the user calls `cancel_offer`/`cancel_offers`: [4](#0-3) [5](#0-4) 

Both `cancel_offer` and `cancel_offers` acquire `wallet_state_manager.lock` while doing this work, so a CPU-bound blow-up here stalls all other wallet RPC/transaction processing on that node for the duration: [6](#0-5) 

An attacker only needs to be an offer counterparty: craft a maker offer whose spend bundle contains many small coin spends chained together via `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions (cheap, so many can fit under `MAX_BLOCK_COST_CLVM`), get the victim to accept it via `respond_to_offer`/`take_offer`, and then the victim's own routine attempt to cancel that trade triggers the pathological loop.

### Title
Unbounded/superlinear loop in `Offer.get_cancellation_coins()` triggered by attacker-crafted offer coin spends stalls wallet transaction processing — (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` iterate over all coin spends, dependencies, and announcements in a spend bundle with no bound on iteration count or computational cost, unlike CLVM execution which is cost-metered. A malicious offer counterparty can construct an offer with many interdependent coin spends/announcements that is cheap to accept (fits within normal CLVM cost limits) but becomes extremely expensive to process in this pure-Python, unbounded nested-loop code once the victim tries to cancel the resulting trade.

### Finding Description
`get_cancellation_coins()` builds per-coin dependency/announcement maps and then runs an outer `while True` loop that calls `detect_dependent_coin()` (itself an O(names·deps·announcements) triple loop) until no more dependent coins are found, with an inner `while True` loop rescanning all remaining `dependencies.items()` each pass [7](#0-6) . None of this is bounded by CLVM cost or a wall-clock timeout, unlike the puzzle execution used elsewhere in the same file to compute `conditions()` [8](#0-7) . The data driving this computation — the number and structure of coin spends/announcements — is fully attacker-controlled through the offer's spend bundle, which for a taker becomes the aggregated `complete_offer` persisted to the trade store [9](#0-8) .

### Impact Explanation
When the victim later cancels the trade (a routine, expected wallet operation) via `cancel_offer`/`cancel_offers`, the RPC handler holds `wallet_state_manager.lock` for the duration of the call [6](#0-5) , so a crafted offer that makes `get_cancellation_coins()` run for a very long time (or effectively hang the process on CPU) blocks all other wallet operations — syncing, other transactions, other RPCs — on that node. This is a spend-triggered transaction-processing halt on the victim's wallet, reachable purely by another party's choice of offer content.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to (a) accept a malicious offer and (b) later attempt to cancel it — both are normal, expected wallet-user actions, and crafting an offer with many chained announcement-dependent coin spends is straightforward for any offer-issuing counterparty (no privileged access needed).

### Recommendation
Bound the work done in `get_cancellation_coins()`/`detect_dependent_coin()`: cap the number of coin spends/dependencies processed, replace the repeated full rescans with an incremental/graph-based algorithm (e.g., precomputed adjacency with a single linear/BFS pass), and/or impose a maximum offer size (number of coin spends) that the wallet will accept via `respond_to_offer`/`take_offer` before this computation is ever attempted.

### Proof of Concept
1. As a malicious maker, construct an offer whose spend bundle contains `N` (e.g., several thousand) small coin spends, each creating a `CREATE_COIN_ANNOUNCEMENT` and asserting a chain of `ASSERT_COIN_ANNOUNCEMENT`s to previous coins in the set, keeping total CLVM cost under `MAX_BLOCK_COST_CLVM` (announcement conditions are cheap).
2. Have the victim `take_offer` this bech32 offer; `respond_to_offer` aggregates it into `complete_offer` and stores it via `save_trade` [9](#0-8) .
3. Victim calls `cancel_offer` (or `cancel_offers`) on the resulting trade; `cancel_pending_offers` calls `Offer.from_bytes(trade.offer).get_cancellation_coins()` [4](#0-3)  which enters the unbounded nested-loop computation, stalling the wallet RPC while `wallet_state_manager.lock` is held.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```

    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
```
