The described behavior—appending `.myshopify.com` when a bare shop name contains no dot—is intended normalization, not an authentication bypass. When `name.include?(".")` is false, `uri_from_shop_domain` deliberately converts a bare label into `<label>.myshopify.com` [1](#0-0) , and the resulting host is genuinely a subdomain of the trusted `myshopify.com` domain, which `sanitize_shop_domain` legitimately treats as trusted since Shopify (not the attacker) controls the actual DNS/host resolution and shop provisioning under that root domain [2](#0-1) .

The real attack surface this question implies—dotted attacker domains designed to *look* trusted (e.g. `store.myshopify.com.evil.com`, `foo.myshopify.io.evil.ru`)—is explicitly covered and correctly rejected: because these contain a dot already, the `.myshopify.com` fallback never triggers, and `uri.domain` resolves to `evil.com`/`evil.ru` rather than any trusted domain, so `sanitize_shop_domain` returns `nil` [3](#0-2) .

The `CallbackController#deduced_phishing_attack?` also independently re-validates the `host` param through `sanitize_shop_domain` before allowing the post-OAuth redirect, and falls back to `ShopifyApp.configuration.root_url` (not an attacker URL) if validation fails [4](#0-3) , so there's no reachable open-redirect/token-leak path via this mechanism. No non-Shopify host can pass `sanitize_shop_domain` and be treated as trusted; the invariant holds.
