## Analysis

The CVE-2016-4954 bug class is **unauthenticated input modifying trusted peer state** (spoofed packets from arbitrary source IPs modify the victim's peer variables, triggering an incorrect leap indication → state corruption). Mapping this onto Serai's in-scope code, the matching shape is an untrusted deserialization path that asserts state variables which are never checked against the cryptographic reality they claim to describe.

### Title
`ReceivedOutput::read` accepts an attacker-claimed scalar offset without verifying it matches the output's `script_pubkey`, causing the wallet to sign spends with the wrong key - (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:121-134) deserializes three independent fields — `offset` (a Secp256k1 scalar), `output` (a `TxOut` containing `script_pubkey`), and `outpoint` — and returns a `ReceivedOutput` with no consistency check that `p2tr_script_buf(scanner_key + GENERATOR * offset)` equals `output.script_pubkey`. The only place this relationship is established is `Scanner::scan_transaction`, which sets `offset` *because* the script matched a registered offset (mod.rs:199-214). The deserialization path skips that invariant entirely.

### Finding Description
- `ReceivedOutput` is "a spendable output" whose `offset` is "the scalar offset to obtain the key usable to spend this output" (mod.rs:88-97).
- `Scanner::register_offset` (mod.rs:180-196) is the only code that binds an offset to a script, and it even handles the BIP-340 even-Y requirement by incrementing the offset until `p2tr_script_buf` returns `Some`.
- `ReceivedOutput::read` (mod.rs:121-134) accepts any `(offset, TxOut, OutPoint)` triple from a byte stream. An unprivileged party who can feed bytes to `ReceivedOutput::read` (a listed reachable entry point) can claim, e.g., an output paying to the *External* key's script while asserting a nonzero `offset`, or an output paying to `key + G·O′` while asserting offset `O ≠ O′`.
- When the wallet subsequently builds and signs a `SignableTransaction` from this `ReceivedOutput`, the per-input re-keying applies `output.offset()` — the signature is produced for `key + G·offset`, which does not match the key committed in the `script_pubkey`. The resulting witness is invalid and the funds cannot be spent.
- This mirrors the NTP analog: a spoofed/attacker-claimed state variable (`offset`, analogous to the leap-indication peer variable) overrides the cryptographically-correct value, and the inconsistency is only discovered after state is committed.

### Impact Explanation
Funds are reported received (a valid `ReceivedOutput` object referencing a real or plausible outpoint) that are not spendable: the produced transaction fails BIP-341 signature validation because the tweaked signing key doesn't match the output key. If the outpoint references real confirmed funds, those funds are effectively locked for any flow that consumes the deserialized `ReceivedOutput` without re-deriving the offset. This is the "funds reported received that are not spendable" impact class. Severity: Medium (requires an integration path where `ReceivedOutput` bytes cross a trust boundary rather than always being produced by the local `Scanner`).

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s are persisted, relayed, or supplied by an untrusted party (the `read`/`serialize` pair exists precisely for transport/storage). Exploitation requires no key knowledge — the attacker only needs to splice a mismatched scalar into the 32-byte offset field. Caveat: if every production consumer only ever uses `ReceivedOutput`s produced by its own `Scanner::scan_transaction`/`scan_block`, the attack surface narrows to storage corruption; the finding's strength depends on a deserialization consumer of untrusted bytes, which the type explicitly supports via the public `read`/`serialize` API.

### Recommendation
In `ReceivedOutput::read`, either:
- take the scanner's base key (or expected `script_pubkey` set) as a parameter and assert `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)`, or
- store the outpoint/output and *derive* the offset at read time via the `Scanner`, making the offset non-attacker-controlled.

At minimum, document that `read` must only be used on trusted bytes; currently nothing signals that the `offset`-vs-`script_pubkey` binding is unverified.

### Proof of Concept
```rust
// Attacker crafts bytes for an output paying to the EXTERNAL (offset = 0) key's
// script, but asserts a nonzero offset.
let key: ProjectivePoint = ...;            // victim's even-Y scan key
let mut bad = ReceivedOutput {
  offset: Scalar::from(7u64),              // claimed offset (attacker-chosen)
  output: TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: p2tr_script_buf(key).unwrap(), // script actually keyed by offset 0
  },
  outpoint: real_outpoint,
};
let bytes = bad.serialize();
let decoded = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // accepted, no check
// SignableTransaction::new(vec![decoded], ...) + multisig signing produces a
// signature under key + 7*G, which does NOT satisfy the script_pubkey's key.
// The spend is invalid -> reported funds unspendable.
```
Root cause: `networks/bitcoin/src/wallet/mod.rs:121-134` performs field-level decoding only; the `offset`↔`script_pubkey` binding established in `Scanner::register_offset`/`scan_transaction` (mod.rs:180-214) is never re-verified on deserialization.

---
**Uncertainty noted:** whether an in-scope production path actually feeds untrusted bytes to `ReceivedOutput::read` could not be fully confirmed within the search budget; the in-scope `processor`/`coordinator` consumers were out of the allowed rule scope to rely on. If no untrusted deserialization consumer exists, this reduces to a hardening gap and should be downgraded accordingly. The stronger candidate — deterministic `CachedPreprocess` reuse across `share_internal` calls — is rooted in `crypto/frost/src/sign.rs:121-144` but its reachable exploitation path lives in `coordinator/src/tributary/signing_protocol.rs:123-145`, which is outside the permitted scope, and the nonce-reuse hazard is explicitly documented as MUST-NOT, so it was rejected under the rules.
