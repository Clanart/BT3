### Title
AI conflict-resolution reassembly desyncs from hunk extraction on decoy marker-like lines, silently leaving raw conflict markers and misapplying resolutions to the wrong hunk - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`extractConflictHunks` (used to build the Copilot prompt) and `reassembleResolvedFile` (used to splice Copilot's per-hunk resolutions back into the file) independently re-parse the *same* raw file content with subtly different, order-unaware logic. `extractConflictHunks` is phase-aware: it only looks for a closing `>>>>>>>` marker *after* it has already consumed the `=======` separator. `reassembleResolvedFile` is not phase-aware: it scans forward from `<<<<<<<` for a separator and a closing marker independently, and takes whichever `>>>>>>>`-shaped line comes first, even if it precedes the real `=======`. A file containing a line that merely *looks* like a closing marker (`>>>>>>>` followed by whitespace/EOL) before the real separator — plausible in any text/code/doc file that itself contains example conflict-marker syntax — causes the two parsers to disagree on hunk boundaries, corrupting the reassembled, committed file.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` collects a conflict hunk in phases: it collects "ours" lines until it sees `baseMarker`/`separatorMarker` [1](#0-0) , then (for diff3) collects base lines until the separator, then collects "theirs" lines until `theirsMarker` [2](#0-1) . A `>>>>>>>`-looking line occurring before the real separator is simply pushed into `oursLines`/`baseLines` as ordinary content and does not terminate the hunk early, because the ours-collection loop only checks for `baseMarker`/`separatorMarker`.

`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` re-parses the identical raw content but with a single un-phased lookahead: for each `<<<<<<<` line it scans forward setting `hasSeparator` when it sees any `=======` line and immediately breaking with `closingIndex = j` on the *first* line matching the same `theirsMarker` regex — with no requirement that the separator be seen first [3](#0-2) . If a decoy `>>>>>>>`-shaped line appears before the real `=======`, the loop breaks on the decoy while `hasSeparator` is still `false`, so the block is classified "malformed" and the `<<<<<<<` line is copied through verbatim without consuming a hunk resolution [4](#0-3) . Because `hunkIndex` is only incremented in the well-formed branch, this creates a positional desync between `hunkResolutions` (matched "by order, not by line number", per the function's own doc comment) [5](#0-4)  and the actual conflict blocks physically present in the file.

The root cause mirrors the report's bug class exactly: code assumes a positional/index-based correspondence ("the Nth resolution belongs to the Nth marker block") always holds, with no verification that the reconstructed structure matches what was actually sent to/returned from the untrusted producer (there, a caller-supplied token; here, attacker-influenced file content merged from a remote branch).

### Impact Explanation
When a user merges/rebases against a branch supplied by someone else (a PR, a fork, any fetched remote) and a file being merged happens to contain a line that looks like `>>>>>>> ` before the real conflict is resolved, invoking the Copilot "resolve conflicts" feature will:
1. Send `extractConflictHunks`'s (correctly bounded) hunk content to the model, and
2. Reassemble using `reassembleResolvedFile`'s (incorrectly bounded) scan, which classifies that hunk as malformed and copies the raw `<<<<<<<`/`=======`/`>>>>>>>` markers straight into the output file, while shifting the corresponding model resolution onto a different (adjacent) conflict.

This is a silent corruption of what the user commits: the resulting file contains checked-in raw git conflict markers (broken code) and a resolution meant for one conflict silently applied to a different location — with the user believing Copilot fully resolved the file, since no error is raised and the write path treats the reassembled content as final [6](#0-5) .

### Likelihood Explanation
Requires only that a merged/fetched file (attacker-controlled branch content) contain a line matching `^>{7}(?:\s|$)` positioned before the real `=======` inside an actual conflict region — plausible in documentation, test fixtures, ASCII banners, or any file that itself discusses/represents git conflict syntax — combined with the victim using the built-in Copilot conflict-resolution feature. No local access, admin rights, or social engineering beyond a normal merge/PR review is needed.

### Recommendation
Make `reassembleResolvedFile`'s marker scan phase-aware and symmetric with `extractConflictHunks`: only search for `theirsMarker` after `hasSeparator` has been observed (mirroring the ours→base→separator→theirs state machine used during extraction), and validate that the number/order of hunks discovered during reassembly matches the count sent to and returned by the model before splicing, throwing a `CopilotValidationError` on mismatch rather than silently falling back to "copy as content."

### Proof of Concept
Given a file with a genuine conflict but a decoy line before the separator:
```
<<<<<<< HEAD
some ours code
>>>>>>> example marker embedded as text/docs
more ours code
=======
theirs code
>>>>>>> branch-name
```
- `extractConflictHunks` treats everything up to the real `=======`/`>>>>>>>` as one hunk (decoy line included as ordinary "ours" content) and sends it to Copilot as "Conflict 1 of 1".
- `reassembleResolvedFile` breaks at the decoy line (`closingIndex` = decoy's index) with `hasSeparator === false`, deems the block malformed, and copies `<<<<<<< HEAD` through as plain content without consuming the model's resolution — leaving the entire original conflict block (including all markers) intact in the file that gets written and committed, while the model's one resolution is silently discarded or misapplied to a subsequent conflict in the same file.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
