### Title
Deterministic nonce reuse in cached FROST preprocess discloses validator secret key when signing inputs differ under one context - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a FROST `CachedPreprocess` (the secret Schnorr nonces `d, e`) in `CachedPreprocesses`, keyed only by `context` — for the DKG confirmer this is `("DkgConfirmer", attempt)`. The entry is never deleted after `from_cache` reconstructs the signing machine. `share_internal`, `share`, and `complete` all re-run `preprocess_internal` and therefore reuse the identical nonces for whatever `preprocesses` map and `key_pair`-derived message are presented under the same attempt. Any second signing invocation under the same attempt whose participant set (FROST binding factor `rho`) or message (challenge `c`) differs produces a second signature share over the same nonce, allowing recovery of the validator's MuSig private key share — the Serai analog of unauthenticated access to secret-bearing state: there is no check that the caller is entitled to consume the nonce for these inputs.

### Finding Description
- `CachedPreprocesses` is keyed solely on `context` (`coordinator/src/tributary/signing_protocol.rs:88`), and `preprocess_internal` writes the cache the first time, then unconditionally reuses it (`signing_protocol.rs:123-145`). `from_cache` consumes the `CachedPreprocess` but the DB row remains, so every later call under the same context reuses `d, e`.
- `DkgConfirmer::signing_protocol` fixes the context to `(b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`) — it does not bind the preprocess set or the message.
- `share_internal` invokes `preprocess_internal` then calls `machine.sign(preprocesses, msg)` with caller-supplied `preprocesses` and `msg = set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:156-170`, `288-301`). `complete` calls `share_internal` again (`signing_protocol.rs:321-324`), so a share+complete sequence, or two share evaluations over differing preprocess subsets or differing `key_pair` values in the same attempt, reuses the nonce.
- In FROST the share is `s = d + e·rho + c·λ·x`. Two shares with identical `(d, e)` but different `rho`/`c`/`λ` yield linear equations exposing the per-signer secret `x` (ROS-style / nonce-reuse disclosure). The file header itself admits "it is explicitly unsafe to reuse nonces across signing sessions" and relies entirely on BFT ordering plus rebuilds "re-deciding nonces" (`signing_protocol.rs:25-48`) — but the nonce is persisted in the DB encrypted with a key derived from `context || self.key` (`signing_protocol.rs:107-115`), so it is deterministic across re-execution and restart, and no code enforces that the signing inputs match what the nonce was implicitly committed to.
- The root cause is a missing access-control-equivalent guard: nothing ties consumption of the cached nonce to a unique `(preprocess set, message)` — exactly the "unauthenticated endpoint returning protected data" shape of CVE-2024-30619 mapped onto Serai, where the leaked datum is a nonce that discloses the long-term secret.

### Impact Explanation
Disclosure of a validator's MuSig secret key share. Since this signing protocol uses raw validator keys (the root of trust for confirming DKG results on Substrate), recovering `x` lets an attacker who collects two same-nonce shares forge the validator's signature contribution toward `set_keys` confirmations, and combined with threshold-quantity shares compromises the validator-set key. Severity: High (confidentiality of secret key material, `C:H`, mirroring the CVE's confidentiality-only impact).

### Likelihood Explanation
Requires two `sign` executions under the same `("DkgConfirmer", attempt)` context with differing preprocess sets or `key_pair` — e.g., `share` and `complete` processing transactions that carry different preprocess maps, a failed share attempt followed by a retry with a different signer subset, or competing confirmation inputs for the same attempt. All such inputs are public on-tributary data (`preprocesses` come from `DkgConfirmationPreprocess` transactions; `key_pair` from DKG outputs), so the resulting shares are also public, giving observers the linear system for free. Likelihood is gated by whether handle logic permits distinct inputs per attempt — the DB persistence and unconditional reuse mean any such occurrence is fatal, and no defensive check exists in this file (the acknowledged TODOs at `signing_protocol.rs:50-54` were unimplemented).

### Recommendation
Bind the cached preprocess to its exact signing inputs: store the sorted participant key list and message hash alongside `CachedPreprocesses`, and refuse `from_cache`/`sign` if inputs differ. Alternatively, key `CachedPreprocesses` by `(context, preprocess-set-hash, msg-hash)` and delete the entry on use so a nonce can never serve two sign calls. At minimum, complete the TODO of verifying our published on-chain preprocess matches the presumed one before emitting shares.

### Proof of Concept
1. Under `attempt = A`, a first `DkgConfirmationShare`-triggering path calls `share(preprocesses_P, key_pair_K1)` → `preprocess_internal` stores and uses nonces `(d, e)`; share `s1 = d + e·rho1 + c1·λ1·x` is published.
2. A second path under the same attempt — `share` or `complete` with a different included preprocess set `P'` (different `rho2`, `λ2`) or a different `key_pair_K2` (different `c2`) — calls `preprocess_internal`, reloads the identical `CachedPreprocess` from `CachedPreprocesses` (no deletion at `signing_protocol.rs:123-145`), and publishes `s2 = d + e·rho2 + c2·λ2·x`.
3. Observer knows `rho_i` (recomputable from public preprocesses), `c_i` (from `set_keys_message` and public R), and `λ_i`; solving the two-equation system recovers `d + e·rho` terms and then `x`, the validator's secret key share — a pure-public-input key disclosure with no privileged access required beyond data the protocol already broadcasts.

Uncertain and worth confirming in a full session: whether `handle.rs` actually invokes `share`/`complete` more than once per attempt with attacker-distinguishable inputs, and whether `key_pair` can vary within an attempt; if neither can differ, the nonce reuse is latent but unreachable and severity drops.
