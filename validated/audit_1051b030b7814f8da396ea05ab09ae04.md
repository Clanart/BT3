### Title
Attacker-crafted P2TR outputs with a hidden script-path tree are reported as received/spendable by `Scanner`, yet are spendable by the attacker — (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary

The external report's bug class is *optimistic confirmation*: an operation is treated as having its intended effect (queued state discarded) while the actual effect — the call succeeding *and* exerting the intended state change — was never verified. In `bitcoin-serai`, the analog is `Scanner::scan_transaction`, which credits any transaction output whose `script_pubkey` matches a registered P2TR script as a `ReceivedOutput` spendable by the group key via key-path signature. Because P2TR output keys may commit to an arbitrary Taproot script tree that is invisible in the `script_pubkey`, an unprivileged sender can craft an output whose output key equals Serai's address while embedding a script path they control. Serai reports the funds as received and spendable; the attacker can later spend the same output via the script path, so the "successful receive" never had the intended effect of exclusively-spendable funds.

### Finding Description

`p2tr_script_buf` constructs Serai's receive script as a P2TR output over the (already tweaked) x-only group key [1](#0-0) . `Scanner` keeps a `HashMap<ScriptBuf, Scalar>` of scripts to offsets [2](#0-1)  and `scan_transaction` returns a `ReceivedOutput` for any output whose `script_pubkey` bytes match [3](#0-2) .

A P2TR `script_pubkey` commits only to the 32-byte output key `Q = P + H(P || merkle_root)·G`. The internal key `P` and the script tree are not revealed in the output. To deposit to Serai, an honest sender sets `P` = Serai's tweaked group key with an empty tree. An attacker can instead pick any `merkle_root` containing a leaf they can satisfy (e.g., a single-sig or timelocked leaf under their key) and set `P = Q_serai − H(P || merkle_root)·G` — i.e., solve for an internal key whose tweak produces exactly Serai's output key. The resulting on-chain output has `script_pubkey = p2tr(Q_serai)`, byte-identical to a genuine deposit: `scan_transaction` emits a `ReceivedOutput` whose `offset` implies it is spendable by `group_key + offset` via key path — which is true — yet the output is *also* spendable by the attacker alone via the hidden script path.

The library's own docs acknowledge the danger of script paths only for *locally registered* offsets ("Arbitrary offsets may introduce a script path"), but nothing prevents an external sender from introducing a script path into the *primary* output key, because the scanner never sees and cannot see the internal key [4](#0-3) . Downstream, `get_outputs`/`scan_block` feed these `ReceivedOutput`s to the processor as credited `External` deposits [5](#0-4) .

### Impact Explanation

Funds are reported received that are not exclusively spendable by Serai. An attacker makes a deposit to Serai's P2TR address, gets credited for it on the Serai side (the scanner treats it as a normal `ReceivedOutput`), then spends the same UTXO through their hidden script path — a double-spend of the credited deposit. This mirrors the report's depth-2 case exactly: the "transaction" (deposit) appears successful and returns the expected signal (matching `script_pubkey`), while the intended effect (funds spendable only by the threshold key) was never exerted.

### Likelihood Explanation

Reachable by any unprivileged party who can broadcast a Bitcoin transaction — they only need to construct a Taproot output with a chosen internal key and script tree whose tweaked output key equals Serai's published address. This requires no cooperation from validators, no malformed encodings, and no trusted inputs; the cost is one on-chain transaction plus the standard Taproot tweak math. Severity is High: direct loss of credited funds with a deterministic construction.

### Recommendation

Document or mitigate that P2TR deposits are vulnerable to script-path-enabled output keys. Options: only credit deposits after a key-path *spend* or interactive proof of the internal key (as some swap protocols do); accept deposits only to keys where the internal key is a provably nothing-up-my-sleeve point (e.g., `H(groups)·G` forms) and require senders to reveal the internal key via an OP_RETURN/witness commitment verified by the scanner; or treat unconfirmed-by-disclosure deposits as uncreditable. At minimum, the `Scanner`/`ReceivedOutput` API should expose that key-path spendability is not exclusive spendability.

### Proof of Concept

```rust
// Attacker crafts a deposit whose script_pubkey equals Serai's P2TR address,
// while retaining a unilateral script-path spend.

// serai_key: ProjectivePoint, the group's tweaked key (even-Y), published as
// the external address via p2tr_script_buf(serai_key).
// Let Q = x_only(serai_key) — the 32-byte output key Serai scans for.

// 1) Attacker builds a Taproot tree with a leaf they control:
//    leaf = tapscript "<attacker_pubkey> OP_CHECKSIG"
//    merkle_root = hash of that leaf.

// 2) Attacker solves for an internal key P such that the tweaked output key
//    equals Q:
//      t = tagged_hash("TapTweak", x(P) || merkle_root)
//      Need: P + t*G = Q  =>  P = Q - t*G
//    Iterate: guess P' (e.g., x-only of a random point), compute
//      t' = tagged_hash("TapTweak", x(P') || merkle_root)
//      P'' = Q - t'*G   — but t'' depends on x(P''), so iterate:
//      set P = Q - t*G, recompute t with x(P), repeat until fixpoint
//    (standard "key-disguising" fixpoint search; terminates quickly since
//     each step just needs x(P) consistent).

// 3) Attacker broadcasts a TX paying to script_pubkey = p2tr(Q).

// Scanner side:
let mut scanner = Scanner::new(serai_key).unwrap();
let outputs = scanner.scan_transaction(&attacker_tx);
assert_eq!(outputs.len(), 1);              // credited as a normal deposit
assert_eq!(outputs[0].offset(), Scalar::ZERO);
// Serai credits the deposit. But the output's control block
// (internal_key = P, merkle path to attacker's leaf) lets the attacker
// spend it via script path at any later time — the "received" funds were
// never exclusively spendable by the threshold key.
```

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
