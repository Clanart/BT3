Based on my investigation, I found a concrete local analog: an undocumented/incorrect reward-attribution calculation in `pallet-consensus-incentives` that pays the wrong beneficiary when a single submission batches consensus updates for multiple state machines.

### Title
Consensus-incentive rewards for an entire batch are attributed to the signer of only the first message, allowing reward misappropriation across state machines - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` is the `FeeHandler` hook invoked by `pallet-ismp` after processing a batch of ISMP `Message`s in a single extrinsic call. It recovers the relayer account to reward from **only `messages.get(0)`** [1](#0-0) , but then computes and pays a reward for **every distinct state machine** whose `StateMachineUpdated` event appears anywhere in the batch's `events` [2](#0-1) . There is no check binding a given state machine's reward to the specific `Message::Consensus` entry (and therefore the specific signer) that actually produced that state machine's update.

### Finding Description
Each `Message::Consensus` carries its own `signer` field, an independent secp/sr25519 signature over `keccak256(consensus_proof)` [3](#0-2) . `pallet-ismp` batches submissions as `Vec<Message>` per extrinsic, and the docs confirm consensus proofs are permissionless/public: "These proofs can be generated by anyone, as they are freely provided by its connected chains" [4](#0-3) . When `on_executed` runs, it does not iterate `messages` to find which `Message::Consensus` corresponds to which `state_machine_id`; instead it takes the signer of `messages[0]` only, and then collapses **all** `StateMachineUpdated` events in the batch (regardless of source message) into a `highest_per_state_machine` map, paying the reward for every one of them to that single recovered account [2](#0-1) .

The reward itself, computed by `calculate_reward`, is a real treasury-to-relayer token transfer plus a reputation mint, sized by `(latest_height - baseline) * cost_per_block` [5](#0-4)  and `process_message`'s transfer [6](#0-5) .

Because consensus proofs for any state machine are public once produced (per the docs), any unprivileged account can submit a `handle_messages` extrinsic containing: (1) their own `Message::Consensus` for a cheap/already-available state machine as `messages[0]`, and (2) one or more other already-public, valid `Message::Consensus` entries for other state machines (which they did not generate/sign, or which they simply re-sign themselves with a different key than the "intended" relayer would have used). Because attribution only reads `messages[0]`'s signer, the entire batch's per-state-machine block-span rewards land on the attacker's account instead of being split correctly per the message/signer that actually delivered each update.

### Impact Explanation
This directly produces a **wrong beneficiary** outcome for a real, non-reputation fund transfer: `T::Currency::transfer(&TreasuryAccount, &relayer_account, reward, ...)` moves treasury funds to an account that did not necessarily submit or sign the proof for every state machine being rewarded [7](#0-6) . This falls squarely in the "stealing or loss of funds ... wrong beneficiary" impact category from the bounty gate, since honest relayers' proportional share of consensus-incentive rewards can be systematically redirected to whoever controls `messages[0]` in a batched submission, with no compromised relayer/prover/admin required — only the ability to submit an ordinary `handle_messages` extrinsic, which is a public entrypoint.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that batches multiple consensus updates per submission (which the design explicitly supports, since `messages: Vec<MessageWithWeight>` is the hook's own input type) and where `pallet-consensus-incentives` is wired as the `FeeHandler`. No governance action, malicious peer, or race against another pending transaction is required — the attacker only needs to know of any already-public/valid consensus proof (by design, freely available) for a second state machine and include it after their own message in a single call.

### Recommendation
Attribute each `StateMachineUpdated` event's reward to the signer of the specific `Message::Consensus` that produced it, rather than the signer of `messages[0]`. Concretely, iterate `messages` to build a `state_machine_id -> signer` map (recovering the signer per `Message::Consensus` item, matching it to the state machine(s) it updates via the event stream), and use that per-item signer when calling `process_message`, instead of a single batch-wide `maybe_relayer_account`.

### Proof of Concept
1. Attacker observes (or generates, since proof generation is permissionless) a valid, already-signed `Message::Consensus` for state machine `B` that has not yet been applied on-chain, signed by relayer `Bob`.
2. Attacker crafts their own `Message::Consensus` for a cheap/known state machine `A`, signs it with their own key `Eve`, and submits a single `handle_messages` extrinsic with `messages = [EveMsgForA, BobMsgForB]`.
3. `pallet-ismp` processes both messages, producing `StateMachineUpdated` events for both `A` and `B`, and calls `on_executed(messages, events)`.
4. `on_executed` reads `messages.get(0)` → `EveMsgForA` → recovers `Eve` as the sole `relayer_account` [3](#0-2) .
5. The loop over `highest_per_state_machine` includes both `A` and `B`, and `process_message` transfers the treasury-funded reward for **both** state machines to `Eve`, even though `Bob` produced/signed the proof that advanced `B` [8](#0-7) .
6. `Bob` receives nothing for delivering `B`'s update, despite having done the work; `Eve` collects both rewards by simply including Bob's public proof in her own batch.

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
