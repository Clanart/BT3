### Title
`Scanner::scan_block` reports immature coinbase outputs as received funds that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over `block.txdata` including index `0`, the coinbase transaction. Any coinbase output whose `script_pubkey` matches a registered tweaked key is returned as a `ReceivedOutput` indistinguishable from a normal spendable output. Coinbase outputs are bound by a 100-block maturity rule enforced by Bitcoin consensus, so the scanner reports funds as received that cannot actually be spent. This is the Serai-side analog of "assets credited/minted to a destination that cannot be used": the wallet layer hands the caller a balance that looks spendable but will produce an invalid transaction if consumed.

### Finding Description
The bug class in the external report is "value is delivered to a destination that is unusable, so the delivered value is effectively lost/locked." In Serai's Bitcoin wallet, the analogous shape is the reverse direction of the same invariant break: the wallet reports an output as spendable value when it is not.

`scan_block` scans every transaction in the block:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`block.txdata[0]` is always the coinbase. `scan_transaction` matches only on `output.script_pubkey` and constructs a `ReceivedOutput` with no maturity or transaction-type check:

```rust
// networks/bitcoin/src/wallet/mod.rs:199-213
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

The code itself acknowledges the issue only in a doc comment ("This will also scan the coinbase transaction which is bound by maturity... a post-processing pass is needed to remove those outputs"), but the API returns a single undifferentiated `Vec<ReceivedOutput>` — the same type used for confirmed spendable inputs to `SignableTransaction::new`. A miner (an unprivileged party with respect to Serai) can craft a coinbase that pays a P2TR output to `p2tr_script_buf(key)` or to any registered offset script, causing Serai to credit the output immediately.

If a consumer feeds such a `ReceivedOutput` into `SignableTransaction::new` and signs/broadcasts it, the transaction is consensus-invalid (BIP-34/coinbase maturity), so the planned spend fails — and worse, the scanner's reported balance overstates spendable funds, the exact "collateral/funds locked" impact of the original report.

### Impact Explanation
An unprivileged miner directs a coinbase payment to the Serai vault key. The funds are reported as received by `scan_block` but are unspendable for 100 blocks. Any downstream logic that treats scanner outputs as immediately usable inputs will either build a transaction that the network rejects, or account for balance that does not exist as spendable. This is "funds reported received that are not spendable" — an accepted impact class.

### Likelihood Explanation
Reachable by any miner at negligible cost — a coinbase paying a known P2TR scriptPubKey requires no cooperation. Triggering it requires only that the vault key (or a registered offset script) be publicly known, which it is on-chain. The failure mode manifests only if the caller does not perform the undocumented post-processing filter the doc comment mentions.

### Recommendation
In `scan_block`, skip `block.txdata[0]` entirely, or track block height/context and exclude/filter immature coinbase outputs. At minimum, split the API so coinbase outputs are returned separately from spendable outputs rather than relying on callers to re-implement a consensus rule from a doc comment.

### Proof of Concept
1. Obtain the vault's tweaked group key `K` and compute `p2tr_script_buf(K)`.
2. Mine a block whose coinbase transaction contains `TxOut { value: X, script_pubkey: p2tr_script_buf(K) }`.
3. Call `Scanner::new(K).scan_block(&block)` — it returns a `ReceivedOutput` for the coinbase output at `(coinbase_txid, vout)`.
4. Feed that `ReceivedOutput` into `SignableTransaction::new`, sign, and broadcast — the transaction is rejected by consensus as it spends an immature coinbase output, while the scanner had already credited `X` as received.
