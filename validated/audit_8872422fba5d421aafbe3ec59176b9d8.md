## Analog Found: Distribution Precompile `rewards()` Missing Non-Payable Guard Strands Sent Value

### Title
Missing non-payable check on `rewards()` allows value-bearing calls to permanently strand funds at the distribution precompile - (File: `precompiles/distribution/distribution.go`)

### Summary
The external report describes a class of bug where a function is reachable with non-zero `msg.value` but the surrounding execution path does not correctly account for or forward that value, leading to fund loss. In sei-chain's `distribution` precompile, every state-changing method explicitly guards against unwanted value with `pcommon.ValidateNonPayable(value)`, but the `rewards()` view method is dispatched **without any payable check**, and the comment in the integration-test suite explicitly documents this as a known gap: *"rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)."*

### Finding Description
In the `Execute` dispatcher, every other query/transaction method that should reject value is guarded, e.g. `WithdrawValidatorCommissionMethod` calls `pcommon.ValidateNonPayable(value)` before proceeding [1](#0-0) . The `RewardsMethod` case, however, dispatches straight to `p.rewards(ctx, method, args)` with no value check at all [2](#0-1) , and the `rewards` implementation itself never inspects or forwards `value` — it only unpacks args, queries `DelegationTotalRewards`, and returns the packed output [3](#0-2) . This pattern is preserved across essentially every historical/legacy version of the distribution precompile (`v552` through `v640`) [4](#0-3) .

Crucially, the distribution precompile's address is **not** listed in the `payablePrecompiles` map used to suppress EVM value-transfer accounting for precompiles that internally redirect value (bank, staking, gov, wasmd) [5](#0-4) . Because `rewards` is a real, dispatchable EVM `CALL` target and the underlying EVM call mechanism moves `msg.value` from caller to target balance for any `CALL`, a value-bearing call to `rewards()` causes native value to be debited from the caller and credited to the distribution precompile's EVM-side balance, while the Go executor performs no corresponding bank-keeper transfer, refund, or accounting for that value (unlike `HandlePaymentUsei`/`HandlePaymentUseiWei` used elsewhere, e.g. in `staking.delegate` or `bank.sendNative`) [6](#0-5) . This is the direct architectural analog of the report's underlying flaw: an "action" reachable with attached value whose downstream handling never actually reconciles that value, so it becomes silently stranded.

### Impact Explanation
Any unprivileged EVM caller who invokes `rewards(address)` on the distribution precompile (`0x...1007`) with non-zero `msg.value` will have that value irrecoverably stuck at the precompile address, since the precompile exposes no withdrawal or sweep mechanism for accidentally-sent value and is excluded from the `payablePrecompiles` accounting path that other value-aware precompiles rely on. This is a direct, permanent loss of user funds triggerable by a single transaction from any EOA or contract — no privileged role required.

### Likelihood Explanation
The trigger is trivial: any external account or contract can call the `rewards` selector on the distribution precompile through a normal EVM `CALL` while attaching `value`. There is no special setup, no reliance on validator/consensus behavior, and no dependency on wasm/CosmWasm-gated features. The bug is also self-documented in the repository's own integration-test notes, confirming the maintainers are aware value-bearing calls to `rewards()` "succeed and strand the funds" [7](#0-6) , but the production dispatcher (`precompiles/distribution/distribution.go`) has not been patched with the missing guard.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` case in `Execute` (and all query-only branches lacking it) so that value-bearing calls to non-payment-handling view methods revert instead of silently transferring and stranding funds, mirroring the guard already applied to `WithdrawValidatorCommissionMethod` and other transaction methods.

### Proof of Concept
1. From any funded EVM account, encode a call to `rewards(address)` against the distribution precompile address `0x0000000000000000000000000000000000001007`.
2. Send the call as a real (mined) transaction with `value` set to a non-zero amount, e.g. `1000000000000` wei (1 usei).
3. Observe the transaction succeeds (status = 1) and returns the delegation rewards data as normal.
4. Query the caller's post-tx balance: it is reduced by the attached value; query the distribution precompile address balance in the EVM StateDB: it now holds the transferred value.
5. Confirm there is no bank-keeper-side Sei balance credited to any Sei account, and no method on the distribution precompile ABI that can retrieve or refund this stranded value — the funds are permanently lost.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
