### Title
Missing identity-point check in `ThresholdKeys::read` allows verification under a non-existent (identity) group key - (File: crypto/dkg/src/lib.rs)

### Summary
The upstream bug class is a success check that passes when the target does not exist: a low-level `call` to a non-existent contract returns `true`, so the protocol proceeds as if the counterparty existed. In Serai, the analogous shape is point deserialization that accepts the identity point (a "non-existent" key/share) in `ThresholdKeys::read`, while the rest of the stack (`view`, `verify`, `verify_share`) treats the resulting identity group key and identity verification shares as valid. `Curve::read_G` explicitly rejects identity (`crypto/frost/src/curve/mod.rs`), but `ThresholdKeys::read` calls `C::read_G` (the bare `Ciphersuite` reader, which performs no identity check) for verification shares — so crafted bytes produce a `ThresholdKeys` whose group key is the point at infinity.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs`, `ThresholdKeys::read`) reads `n` verification shares with `<C as Ciphersuite>::read_G(reader)` and passes them to `ThresholdKeys::new`. Neither `read` nor `new` rejects identity points:

- `crypto/dkg/src/lib.rs` (~line 620-631): `verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?)` then `ThresholdKeys::new(...)`.
- `crypto/dkg/src/lib.rs` (~line 376-378): `group_key = Σ verification_shares[i] * interpolation_factor(i)` — if all shares are identity, `group_key` is identity.
- By contrast, `Curve::read_G` (`crypto/frost/src/curve/mod.rs`, ~lines 124-131) explicitly checks `res.is_identity()` and errors — evidence that the identity case is known-dangerous and that the ciphersuite-level `read_G` does not enforce it.

With an all-identity `verification_shares` map, the deserialized `ThresholdKeys` has `original_group_key() == identity`. Any subsequent offset/scalar leaves the group key at `identity * scalar + offset * G = offset * G`; with `offset == 0` it stays identity. Verification then vacuously succeeds:

- `SchnorrSignature::batch_statements`/`verify` (`crypto/schnorr/src/lib.rs`, ~lines 88-110) computes `R + c·A − s·G == 0`. For `A == identity`, `c·A == 0`, so any `(R, s)` with `R = s·G` verifies for *any* challenge `c` — a forgery for the identity key, exactly like a call to a non-existent account returning success.
- `Schnorr::verify_share` (`crypto/frost/src/algorithm.rs`, ~lines 219-230) builds the same statements against `verification_share`; an identity verification share accepts any share `s` with commitment `R = s·G`, regardless of the signer's real secret share.

`ThresholdKeys::read` is listed as an attacker-reachable input sink, so an unprivileged party supplying crafted serialized keys reaches this path.

### Impact Explanation
A forged Schnorr signature (and forged FROST signature shares) can be produced that pass `SchnorrSignature::verify` / `Schnorr::verify` / `verify_share` under a group key that is the point at infinity — i.e., verification "succeeds" against a key that does not exist, without knowledge of any discrete logarithm. Where downstream logic treats these keys/shares as authoritative (e.g., accepting shares during `complete`, or any off-chain accounting keyed to emitted signature/verification success), an attacker obtains acceptance of data that was never signed by a real key holder — the same "success without a counterparty" outcome as the free-mint report. Shares verified as valid under identity verification shares can also poison share aggregation: an attacker submits shares that pass per-share verification but were not generated from the secret share, causing `complete` to emit an invalid aggregate or misattribute blame.

### Likelihood Explanation
Reaching the bug requires only that attacker-controlled bytes be fed to `ThresholdKeys::read` (or equivalently `ThresholdKeys::new` with identity verification shares) and that the resulting view be used in `verify`/`verify_share`/`complete`. No collusion, leaked keys, or malicious-RPC assumptions are needed — it is a pure deserialization-validity gap. The mitigating factor is that honest key-generation paths (`dkg`, `dealer`) never emit identity shares, so the exploit window is limited to contexts where serialized `ThresholdKeys` originate from or can be influenced by an untrusted party — hence Medium rather than High.

### Recommendation
In `ThresholdKeys::new` (or at the top of `ThresholdKeys::read`), reject identity verification shares and an identity computed `group_key`, mirroring `Curve::read_G`:

```rust
// crypto/dkg/src/lib.rs, inside ThresholdKeys::new after building verification_shares
for share in verification_shares.values() {
  if bool::from(share.is_identity()) {
    Err(DkgError::InvalidVerificationShare)?;
  }
}
let group_key = t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum::<C::G>();
if bool::from(group_key.is_identity()) {
  Err(DkgError::InvalidVerificationShare)?;
}
```

Optionally also have each in-scope `Ciphersuite::read_G` reject identity at the encoding layer so that `SchnorrSignature::read`, `Commitments::read`, and DKG share readers all inherit the check (note `SchnorrSignature::read` itself uses `C::read_G` and therefore also admits `R == identity`, which `verify` then treats as a valid nonce commitment for identity keys).

### Proof of Concept
```rust
// Conceptual: craft ThresholdKeys bytes with identity verification shares.
// After ThresholdKeys::read succeeds, group_key == identity.

use ciphersuite::{group::Group, Ciphersuite};
use schnorr::SchnorrSignature;
use frost::curve::Secp256k1;

// Any scalar s and R = s*G satisfies the verifier for A = identity:
let s = <Secp256k1 as Ciphersuite>::F::random(&mut rand_core::OsRng);
let sig = SchnorrSignature::<Secp256k1> {
  R: Secp256k1::generator() * s,
  s,
};
// For ANY challenge c: R + c*identity - s*G == R - s*G == 0
assert!(sig.verify(Secp256k1::G::identity(), <Secp256k1 as Ciphersuite>::F::random(&mut rand_core::OsRng)));
```

The `assert!` passes only because the identity group key ("non-existent" key) makes the `c·A` term vanish — the analog of a low-level call returning `true` for a non-existent contract. Root cause: `ThresholdKeys::read`/`ThresholdKeys::new` at `crypto/dkg/src/lib.rs` (~lines 620-631 and 376-378) accept identity points because they use `Ciphersuite::read_G` instead of the identity-rejecting `Curve::read_G` (`crypto/frost/src/curve/mod.rs` ~lines 124-131).
