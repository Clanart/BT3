## Finding: Missing source-module authentication in `VWAPOracle.onAccept` (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle.onAccept` authenticates an incoming cross-chain governance message by checking only the **chain identifier** of the sender (`incoming.request.source == IDispatcher(host()).hyperbridge()`), but never checks `incoming.request.from`, which is the field that identifies the specific **module/pallet** on that chain that dispatched the request. [1](#0-0) 

### Finding Description
`PostRequest` (per `IncomingPostRequest`) carries both `source`/`dest` (chain-level routing) and `from`/`to` (module-level routing): [2](#0-1) 

`HandlerV2`/the `EvmHost` uses `to` to route the call into `VWAPOracle.onAccept` (module-level dispatch target), and `onlyHost` only checks that `msg.sender` is the local Host, not who authored the request on the source side: [3](#0-2) 

Inside `onAccept`, the *only* authenticity check performed is:

```solidity
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
```

This proves the message originated from the Hyperbridge relay chain (a state-machine/chain-level identity), but it does **not** verify `incoming.request.from`, i.e., it does not bind the message to the specific governance module/pallet on that chain that is supposed to be the sole authority for `UpdateTokenDecimals` messages. Any pallet or account on the Hyperbridge chain capable of dispatching an ISMP POST request destined for the `VWAPOracle` contract address, with a body whose first byte encodes `RequestKind.UpdateTokenDecimals`, will have that payload accepted and applied via `_processTokenDecimalsUpdates`: [4](#0-3) 

This is a "module misbinding" pattern: the check enforces chain identity but not module identity, so a message that is authenticated only at the chain level can be misattributed to the specific governance module the invariant assumes is the exclusive source of decimal updates.

Note: whether this is remotely exploitable also depends on the Substrate side — specifically, whether dispatch of ISMP requests targeting arbitrary `to` addresses/bodies is restricted so only the intended governance pallet can produce a request with this `to`/body shape. I was not able to fully trace the Substrate-side dispatch/router restrictions for outbound ISMP requests within the available index to confirm whether an unprivileged or non-governance pallet could actually author such a message; that would need to be checked in the ISMP router/pallet code (`modules/ismp/core/src/router.rs` and related pallet dispatch logic) to determine if `from` is otherwise constrained upstream before reaching `onAccept`.

### Impact Explanation
If an unauthorized module on the Hyperbridge chain (one other than the intended governance module) can produce a message satisfying only the `source`-chain check, it can rewrite the `_tokenDecimals[chainHash][token]` mapping for any `(sourceChain, token)` pair. Since `recordSpread` uses this mapping to normalize amounts for spread/VWAP tracking: [5](#0-4) 

corrupting decimals would misprice fills, producing wrong spread values that (depending on downstream consumers of `spread()`/`recordSpread`) could lead to wrong order valuation, wrong reward/beneficiary amounts, matching the "High" impact template.

### Likelihood Explanation
Likelihood hinges entirely on the unverified assumption above — whether any account/pallet besides the intended governance module can, in production, dispatch an ISMP POST request with `source` = Hyperbridge chain and `to` = the `VWAPOracle` address. If the Substrate-side ISMP dispatch path already restricts which pallet can send to this specific `to` address (i.e., a module-level lock exists upstream), then this EVM-side gap is not independently exploitable. This upstream restriction could not be confirmed with the tools available in this session.

### Recommendation
Add an explicit check on `incoming.request.from` in `VWAPOracle.onAccept`, comparing it against the known/immutable governance module identifier (analogous to the existing `source`-chain check), so that both chain-level and module-level identity are verified before applying `UpdateTokenDecimals`.

### Proof of Concept
Not fully constructible without confirming the Substrate-side dispatch authorization for `from`/`to` on outbound governance-style ISMP requests; the EVM-side gap (missing `from` check in `onAccept`) is directly observable in the code cited above.

---

**Caveat:** This is reported as a **potential** finding contingent on unverified Substrate-side authorization of `from`/`to` for ISMP dispatch from the Hyperbridge chain. I could not confirm within this session whether that upstream restriction exists and closes the gap. If it does close the gap, this finding should be downgraded to informational (defense-in-depth) rather than an exploitable High.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        // Only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();

        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));

        if (kind == RequestKind.UpdateTokenDecimals) {
            TokenDecimalsUpdate[] memory updates = abi.decode(incoming.request.body[1:], (TokenDecimalsUpdate[]));
            _processTokenDecimalsUpdates(updates);
        }
    }
```

**File:** evm/src/utils/VWAPOracle.sol (L254-268)

    function _processTokenDecimalsUpdates(TokenDecimalsUpdate[] memory updates) internal {
        uint256 updatesLen = updates.length;
        for (uint256 j = 0; j < updatesLen; j++) {
            bytes32 chainHash = keccak256(updates[j].sourceChain);
            uint256 tokensLen = updates[j].tokens.length;
            for (uint256 i = 0; i < tokensLen; i++) {
                if (updates[j].tokens[i].decimals == 0) revert InvalidInput();

                _tokenDecimals[chainHash][updates[j].tokens[i].token] = updates[j].tokens[i].decimals;
                emit TokenDecimalsUpdated(
                    updates[j].sourceChain, updates[j].tokens[i].token, updates[j].tokens[i].decimals
                );
            }
        }
    }
```
