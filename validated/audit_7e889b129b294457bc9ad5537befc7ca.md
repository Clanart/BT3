### Title
Missing bounds validation in `is_atom_canonical()` / `is_clvm_canonical()` allows attacker-controlled CLVM bytes to trigger an out-of-bounds read and unhandled exception during spend-bundle validation - (File: chia/full_node/mempool_manager.py)

### Summary
`chia/full_node/mempool_manager.py` contains `is_atom_canonical()` and `is_clvm_canonical()`, which walk a raw CLVM-serialized byte buffer (`clvm_buffer`) taken from an unauthenticated spend bundle's puzzle/solution to determine DEDUP eligibility [1](#0-0) . Both functions advance an `offset` cursor and index directly into `clvm_buffer[offset]` based on attacker-supplied length-prefix bits, without first checking that `offset` is still within the buffer bounds before dereferencing it [2](#0-1) [3](#0-2) . This mirrors the Zephyr MCTP bug class: a length/opcode value supplied by an untrusted party is trusted to advance a cursor and dereference a buffer before any bounds/state validation is performed.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads `b = clvm_buffer[offset]` and then, depending on the top bits of `b`, decides how many additional prefix bytes (`prefix_len`, up to 5) to consume [4](#0-3) . It then loops `prefix_len` times, incrementing `offset` and indexing `clvm_buffer[offset]` again with no check that `offset < len(clvm_buffer)` [2](#0-1) . If the buffer is truncated relative to what the length-prefix header claims (e.g., a byte matching the 5-byte-prefix pattern `0b111111xx` placed at the very end of the buffer), this indexing goes out of bounds.

`is_clvm_canonical(clvm_buffer)` has the analogous issue in its main loop: after computing `atom_len` for the current atom via `is_atom_canonical()`, it advances `offset += atom_len` and immediately loops back to `b = clvm_buffer[offset]` without validating that the new `offset` is still in range before the next dereference [3](#0-2) . Because `atom_len` is derived entirely from attacker-controlled prefix bits, a crafted buffer can make `offset` overrun the buffer.

This is architecturally identical to the reported Zephyr flaw: a state-machine-style byte parser trusts an attacker-supplied "length" value to drive further buffer access, and performs the dereference before validating that the access is in-bounds. In Zephyr this produced a NULL/OOB *write*; here it produces an OOB *read* (Python raises `IndexError`), but the root cause — unchecked, attacker-driven cursor advancement immediately followed by a dereference — is the same class of defect (CWE-125 / missing bounds check before use).

### Impact Explanation
This code path processes the serialized CLVM bytes of spend bundles that reach the mempool from any unauthenticated network peer or local RPC client via `pre_validate_spendbundle()`'s DEDUP-eligibility path (per `.cursor/context/clvm-execution.md`, `is_clvm_canonical()` is used to determine "DEDUP-eligible" spends) [5](#0-4) . An `IndexError` raised here, if not caught by the caller, would propagate out of spend-bundle processing, potentially interrupting transaction validation for that bundle or, depending on the calling context (async task / thread pool worker), causing a broader halt in mempool processing — a spend-triggered transaction-processing denial of service, consistent with the accepted "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Any unprivileged party who can submit a spend bundle (e.g., via RPC `push_tx` or gossip) controls the exact byte layout of puzzle reveals/solutions, and therefore fully controls the prefix bits that drive `prefix_len` and `atom_len` computation. Crafting a buffer whose final bytes match a multi-byte length-prefix pattern with insufficient trailing bytes is straightforward and requires no special privileges or prior protocol state — directly analogous to the "malicious/malfunctioning bus master byte" trigger in the original report.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (validate `offset + prefix_len < len(clvm_buffer)` up front, and re-check within the loop) and in `is_clvm_canonical()`'s main loop before dereferencing `clvm_buffer[offset]` after advancing by `atom_len` (validate `offset <= len(clvm_buffer)` before continuing, and `offset < len(clvm_buffer)` before the next `b = clvm_buffer[offset]`). Treat any computed offset that exceeds the buffer length as non-canonical (return `False`) rather than allowing the index operation to raise, and ensure callers explicitly catch/handle any residual exceptions from this parsing path so a single malformed bundle cannot affect processing of others.

### Proof of Concept
Construct a `clvm_buffer` whose last byte is `0xFC` (matches `(b & 0b11111110) == 0b11111100`, selecting the 5-byte length-prefix branch, `prefix_len = 5`) with no further bytes following it, then call:
```python
from chia.full_node.mempool_manager import is_atom_canonical
is_atom_canonical(b"\x80\xfc", 1)  # offset=1 points at 0xfc, but no bytes follow for the 5 prefix bytes
```
This raises `IndexError: index out of range` while executing `atom_len |= clvm_buffer[offset]` inside the `for i in range(prefix_len)` loop, because `offset` runs past the end of the 2-byte buffer [2](#0-1) . The same class of truncation can be embedded inside a full spend bundle's serialized puzzle/solution to reach `is_clvm_canonical()` via the DEDUP-eligibility check during mempool admission.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```markdown
## Canonical serialization

**Location**: `mempool_manager.py:185`

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.

### `is_atom_canonical(clvm_buffer, offset)`

Validates a single atom's length prefix encoding. The CLVM format uses
variable-length prefixes (1-6 bytes) based on atom size. Each prefix
length has a minimum atom size threshold.
```
