### Title
`with-ft` wildcard allowance amount is not aggregated across distinct fungible-token asset names, letting `restrict-assets?`/`as-contract?` move `N×` the authorized cap - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`check_allowances` in `clarity/src/vm/functions/post_conditions.rs` enforces `with-ft` allowances (including the wildcard `asset-name = "*"` form) by comparing each *individual* moved fungible-token asset's amount against the allowance amount, rather than summing amounts across all fungible-token asset identifiers that match a wildcard entry. A single `(with-ft <contract> "*" <amount>)` allowance is thereby checked once per distinct `AssetIdentifier` under that contract, not once against the total value moved.

### Finding Description
`check_allowances` (`clarity/src/vm/functions/post_conditions.rs:598-627`) does:
```rust
if let Some(ft_moved) = assets.get_all_fungible_tokens(owner) {
    for (asset, amount_moved) in ft_moved {
        let mut merged: Vec<(usize, u128)> = Vec::new();
        if let Some(allowance_vec) = ft_allowances.get(asset) {
            merged.extend(allowance_vec.iter().cloned());
        }
        if let Some(wildcard_vec) = ft_allowances.get(&AssetIdentifier {
            contract_identifier: asset.contract_identifier.clone(),
            asset_name: ClarityName::from_literal("*"),
        }) {
            merged.extend(wildcard_vec.iter().cloned());
        }
        ...
        for (index, allowance) in merged {
            if *amount_moved > allowance {
                record_violation(&mut earliest_violation, index as u128);
            }
        }
    }
}
``` [1](#0-0) 

`assets.get_all_fungible_tokens(owner)` iterates over every distinct `AssetIdentifier` (contract + asset name) that moved. For each such asset, the wildcard allowance entry (`asset_name = "*"`) is looked up and re-checked from scratch with the *full* `amount` value the caller specified, and the comparison is `amount_moved > allowance` — a per-asset comparison, not a running total. Consequently if a target contract exposes `k` distinct fungible-token asset names, a single `(with-ft contract "*" X)` allowance lets a body evaluated inside `restrict-assets?`/`as-contract?` move up to `X` of asset₁, `X` of asset₂, …, `X` of asset_k — i.e. up to `k * X` total value — even though the caller wrote one allowance expecting the amount `X` to be the cap they were authorizing.

Contrast this with the STX check just above it (`clarity/src/vm/functions/post_conditions.rs:678-700`), which explicitly computes `total_stx_change = amount_moved + amount_burned` and checks that *combined* total against the allowance — showing the codebase is aware that multiple movement channels for the "same" allowance must be summed before comparison. The FT wildcard path lacks the analogous summation across asset identifiers matched by the wildcard.

This is the direct structural analog of the reported bug class: a single declared "amount" bound (the report's mispriced amount) is checked against the wrong aggregate/quantity, allowing more value to move than the bound was meant to cover.

### Impact Explanation
This breaks the equality the allowance mechanism promises: "no more than `amount` of a fungible asset moves from the protected owner while executing this restricted scope." `restrict-assets?`/`as-contract?` are the safety wrapper Clarity contracts use to bound value transferred to/from a principal during a nested/untrusted call (e.g. sending assets to a contract-call target and getting a hard-capped allowance back). A contract author who writes `(with-ft target-contract "*" u100)` intending "the callee may move at most 100 units of anything it owns from this contract" can in fact have `100 * k` units moved if the target contract defines `k` distinct fungible-token asset classes — an asset moving past its declared post-condition/allowance, which is the Critical-severity category defined in scope ("an asset moving past its post-conditions").

### Likelihood Explanation
Reachable by any unprivileged Clarity contract author using `restrict-assets?`/`as-contract?` with a wildcard `with-ft` allowance against any contract that defines more than one fungible-token asset — no privileged role, miner, or admin access is required. The condition (target contract exposing multiple FT asset names) is common (e.g., wrapped/synthetic multi-asset token contracts), making the trigger practical rather than purely theoretical.

### Recommendation
Sum `amount_moved` across all `AssetIdentifier`s that match a given wildcard allowance entry (grouped by allowance index) before comparing against that entry's `amount`, mirroring the combined STX movement+burn summation already implemented at `clarity/src/vm/functions/post_conditions.rs:678-700`. Exact-match (`asset_name != "*"`) entries can remain per-asset.

### Proof of Concept
1. Deploy a contract `multi-ft.clar` implementing SIP-010-like fungible tokens `token-a` and `token-b`, each independently mintable/transferable, both defined in the same contract.
2. In a caller contract, execute:
```clarity
(as-contract?
  ((with-ft 'SP...multi-ft "*" u100))
  (begin
    (contract-call? 'SP...multi-ft transfer-a u100 tx-sender recipient)
    (contract-call? 'SP...multi-ft transfer-b u100 tx-sender recipient)))
```
3. In `check_allowances`, `assets.get_all_fungible_tokens` yields two entries: `(token-a, 100)` and `(token-b, 100)`. Each is independently matched against the wildcard allowance `(index, 100)` and passes (`100 > 100` is false for each). Total STX-equivalent value moved from the `as-contract?` principal is 200 units against a caller-declared cap of 100 — no violation is recorded and `evaluate_body_with_allowance_check` commits the state at `clarity/src/vm/functions/post_conditions.rs:410-422`. fn evaluate_body_with_allowance_check(
    asset_owner: &PrincipalData,
    allowances: Vec<Allowance>,
    body_exprs: &[SymbolicExpression],
    invoke_ctx: &InvocationContext,
    exec_state: &mut ExecutionState,
    context: &LocalContext,
) -> Result<Value, VmExecutionError> {
    let epoch = *exec_state.epoch();
    exec_state.global_context.begin();

    // Evaluate the body expressions inside a closure so `?` only exits the closure
    let eval_result: Result<Option<Value>, VmExecutionError> =
        (|| -> Result<Option<Value>, VmExecutionError> {
            let mut last_result = None;
            for expr in body_exprs {
                let result =
                    eval(expr, exec_state, invoke_ctx, context)?.clone_with_cost(exec_state)?;
                last_result.replace(result);
            }
            Ok(last_result)
        })();

    // A block-rejecting error raised inside the body must abort the transaction.
    if matches!(&eval_result, Err(err) if err.rejectable()) {
        exec_state.global_context.roll_back()?;
        return Err(eval_result.unwrap_err());
    }

    let asset_maps = exec_state.global_context.get_readonly_asset_map()?;

    // If the allowances are violated:
    // - Rollback the context
    // - Return an error with the index of the violated allowance
    match check_allowances(asset_owner, allowances, asset_maps, epoch) {
        Ok(None) => {}
        Ok(Some(violation_index)) => {
            exec_state.global_context.roll_back()?;
            return Ok(Value::error(Value::UInt(violation_index))?);
        }
        Err(e) => {
            exec_state.global_context.roll_back()?;
            return Err(e);
        }
    }

    exec_state.global_context.commit()?;
