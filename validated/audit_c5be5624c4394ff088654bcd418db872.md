### Title
Out-of-range participant indexes in a blame accusation panic the blame evaluator (complete DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept an accusation consisting of a `sender` `Participant`, a `recipient` `Participant`, an `EncryptedMessage`, and an optional `EncryptionKeyProof`. Neither index is validated against the DKG's `n`. Both `Decryption::decrypt_with_proof` and `blame_internal` index `HashMap`s with these attacker-chosen indexes via `[]`, which panics on a missing key. Any participant (or any party feeding accusations to the machine) can crash the node evaluating the blame, matching the CVE-2020-14632 class of an attacker-reachable complete denial of service.

### Finding Description
`Participant` is only bounded to be non-zero and fit in `u16` (`crypto/dkg/src/lib.rs` line 123, `Participant::new`), so values `n + 1 ..= u16::MAX` are valid `Participant`s but not members of the DKG.

`AdditionalBlameMachine::new` registers encryption keys only for `1 ..= n` (crypto/dkg/pedpop/src/lib.rs line 656: `for i in 1 ..= n`), populating `Decryption.enc_keys` and `commitments` with exactly those participants. `blame` then calls `blame_internal` (lib.rs line 681), which calls `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs lines 366–397). When a `proof` is supplied, line 388 indexes `self.enc_keys[&decryptor]`:

```rust
&[self.enc_keys[&decryptor], *proof.key],
```

`HashMap`'s `Index` impl panics when the key is absent, so any `recipient` (the `decryptor`) outside `1 ..= n` — or simply a participant whose registration was never processed — panics the evaluator. If the panic survives to line 599 instead, `&self.commitments[&sender]` panics identically for a `sender` outside the registered set.

The message argument itself is untrusted bytes parsed by `EncryptedMessage::read` (encryption.rs lines 171–177), and the accusation originates from another party's claim that a share was invalid — a fully unprivileged input path.

### Impact Explanation
A single malformed blame accusation causes an unconditional panic in the node processing it. Since blame evaluation is part of DKG completion/key rotation, an attacker can crash every evaluator that attempts to arbitrate the accusation, aborting the key-generation/set-rotation protocol — a complete, repeatedly triggerable denial of service, directly analogous to the CVE's "hang or frequently repeatable crash (complete DOS)".

### Likelihood Explanation
Triggering requires only that the attacker be able to submit (or induce evaluation of) a blame statement with a `sender` or `recipient` `Participant` index greater than `n`, or referencing a party that never registered an encryption key — no cryptographic work or privileged position is needed. The panic occurs before any proof verification gate that would reject the accusation.

### Recommendation
In `blame_internal` (and `AdditionalBlameMachine::new`'s consumers), validate `sender` and `recipient` against `self.commitments` / `self.encryption.enc_keys` before indexing: return the accuser (or a dedicated `InvalidParticipant` error variant) when either index is not a registered participant. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` lookups that map misses to a blame result rather than panicking.

### Proof of Concept
1. Run a PedPoP DKG with `n` participants to completion, producing a `BlameMachine`/`AdditionalBlameMachine` (via `AdditionalBlameMachine::new(context, n, commitment_msgs)`).
2. A participant (or accusation relayer) submits `blame(sender, recipient, msg, proof)` where `proof` is `Some(...)` and `recipient = Participant::new(n + 1).unwrap()` (or `sender` beyond `n` for the `commitments` path).
3. `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` at encryption.rs line 388 → `HashMap` index panic, aborting the process evaluating the blame.
