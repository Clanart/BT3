This confirms the vulnerability. The comparison between `vlMGPBaseRewarder._calExpireForfeit` and `mWOMSVBaseRewarder._calExpireForfeit` shows the mWomSV version is missing the call to a `getRewardablePercentWAD`-equivalent function that should scale down `rewardableAmount` based on the user's unlocking status.

### Title
Tautological `_calExpireForfeit` in mWOMSVBaseRewarder always returns zero forfeiture, allowing unlocking mWomSV holders to claim 100% of rewards and draining the forfeiture-funded reward pool - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally and then computes `forfeitAmount = _amount - rewardableAmount`, which is always `0` regardless of the caller's mWomSV lock/unlock state. This is in contrast to the sibling `vlMGPBaseRewarder._calExpireForfeit`, which correctly scales `rewardableAmount` by `vlMGP.getRewardablePercentWAD(_account)` to penalize users who are unlocking. As a result, any mWomSV holder can call `getReward`/`getRewards` after starting an unlock and receive their full bonus-reward balance with zero forfeiture, even though the protocol's documented boosted-APR model depends on forfeitures from unlocking users being re-queued via `_queueNewRewardsWithoutTransfer` into `rewardInfo.queuedRewards`/`rewardPerTokenStored` for remaining lockers.

### Finding Description
`calExpireForfeit` calls `_calExpireForfeit(_account, earned(_account, _rewardToken))` [1](#0-0) , and `_sendReward` (invoked from `getReward`/`getRewards`) also computes `forfeitAmount` via `_calExpireForfeit(_account, userRewards[_rewardToken][_account])` before paying out `toSend = userRewards[...] - forfeitAmount` [2](#0-1) .

The root cause is in the internal helper itself:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
}
``` [3](#0-2) 

`rewardableAmount` is assigned directly from `_amount` with no dependency on `_account`'s lock/unlock status, so `forfeitAmount` is tautologically always `0`. Compare this to the sibling contract `vlMGPBaseRewarder._calExpireForfeit`, which correctly derives `rewardableAmount` from the account's live unlock state:
```solidity
uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
``` [4](#0-3) 

`mWomSV.sol` exposes the exact equivalent lock-status-aware function, `getRewardablePercentWAD(address _user)`, which reduces the rewardable percentage for tokens in cooldown or newly unlocked [5](#0-4) , but `mWOMSVBaseRewarder` never calls `mWOMSV.getRewardablePercentWAD(_account)` anywhere in the contract. No modifier, `nonReentrant` guard, or reward-index update mitigates this — the bug is in the forfeiture math itself, not access control, so it is reachable by any unprivileged holder via the standard flow: `mWomSV.lock` → accrue rewards → `mWomSV.startUnlock` (full stake) → `MasterMagpie.multiclaim`/`getReward` on `mWOMSVBaseRewarder` (via `onlyMasterMagpie`) → full payout with `forfeitAmount == 0`.

### Impact Explanation
This causes protocol insolvency in the bonus reward token relative to the accounting model: `queueNewRewards`/`_provisionReward` fund `rewardInfo.historicalRewards`/`rewardPerTokenStored` based partly on expected forfeiture re-injection via `_queueNewRewardsWithoutTransfer` [6](#0-5) , but that path is now permanently unreachable in practice (`forfeitAmount` is always `0`), so the boosted-APR yield promised to long-term lockers is never funded from forfeitures, and unlocking users still receive 100% of their earned share instead of the intended reduced share — a theft of the yield that should have been forfeited to (and redistributed among) remaining lockers, and a structural insolvency in the bonus token accounting versus advertised APR.

### Likelihood Explanation
Trivial and fully repeatable: any mWomSV holder with nonzero accrued rewards can trigger this on every unlock cycle with no special capital, front-running, or privileged role — it is the default code path for `getReward`/`getRewards`, so it happens systematically for every unlocking user, not just as an edge case.

### Recommendation
Fix `_calExpireForfeit` in `mWOMSVBaseRewarder.sol` to mirror `vlMGPBaseRewarder`'s logic, deriving `rewardableAmount` from `mWOMSV.getRewardablePercentWAD(_account)` (already implemented in `mWomSV.sol`) instead of setting `rewardableAmount = _amount` unconditionally.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
