## Analysis

The Solidity bug's core pattern is a **TOCTOU (time-of-check/time-of-use) race**: a user-facing operation (`close()`) is validated/previewed against one piece of state, but an attacker-triggered state mutation (`accrueInterest()`) can land between the check and the execution, so the operation either fails or silently uses different data than what was reviewed.

The same pattern exists in GitHub Desktop's **Merge** flow.

### The stale-preview / fresh-execution mismatch

When a user opens the merge dialog, `MergeChooseBranchDialog.updateStatus` computes a mergeability preview (`ComputedAction.Clean`/`Conflicts`) and commit count for the *currently selected branch's sha* and caches it in component state: [1](#0-0) 

The only staleness guard compares `this.state.selectedBranch.tip.sha` against the *branch object passed into the async call*, i.e. it only detects the user picking a *different* branch in the UI — it does **not** detect the branch's own tip moving underneath it while it stays selected: [2](#0-1) 

When the user clicks "Merge," the dialog forwards the (now possibly stale) `Branch` object and the *cached* `mergeStatus` straight to the dispatcher, with no re-validation: [3](#0-2) 

`AppStore._mergeBranch` also does not recompute or recheck mergeability/tip before executing — it just increments stats based on the stale `mergeStatus` and runs the merge: [4](#0-3) 

Critically, `GitStore.merge` and the underlying git command operate on the **branch name**, not the sha that was previewed: [5](#0-4) [6](#0-5) 

### The attacker-controlled mutation that lands "before close()"

Desktop performs unattended background fetches every ~30 minutes (or on window focus) and then fast-forwards local tracking branches to match whatever the remote currently reports — with no user interaction required: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

This is exactly the "lender front-runs `close()` with `accrueInterest()`" primitive: an attacker who controls the remote (or a proxy/MITM of the remote response) pushes new commits to the branch the user has selected in the merge dialog. Desktop's background fetch silently fast-forwards the local ref to the attacker's new tip while the merge dialog is still open, showing the old (reviewed, "Clean") preview. The user, trusting the displayed preview, clicks "Merge" and Desktop merges whatever the branch *name* currently resolves to — the attacker's new, unreviewed commits — into the user's current branch and creates a merge commit the user never saw.

### Title
Merge dialog executes on a stale-name lookup, allowing remote-controlled background fetch to silently swap in unreviewed commits before "Merge" is clicked - (File: app/src/ui/multi-commit-operation/choose-branch/merge-choose-branch-dialog.tsx)

### Summary
The Merge Branch dialog computes and caches a mergeability/commit-count preview for the currently selected branch's tip sha, but the actual merge, triggered by the "Merge" button, is executed against the branch **name** rather than the previewed sha. GitHub Desktop's automatic background fetch (unattended, every ~30 minutes or on focus) fast-forwards local tracking branches to match the remote in between. An attacker who controls the remote repository (or intercepts/spoofs the git remote response) can push new commits to the branch a user has open for merge review; Desktop will silently update the local ref and later merge those unreviewed commits when the user clicks "Merge," without ever refreshing or invalidating the stale preview shown in the dialog.

### Finding Description
`MergeChooseBranchDialog.updateStatus` (`app/src/ui/multi-commit-operation/choose-branch/merge-choose-branch-dialog.tsx:102-140`) computes `mergeStatus` and `commitCount` once, when a branch is selected, and only re-validates against the *same in-memory `Branch` object's* sha — it has no subscription to git-store updates for that branch's tip while the dialog remains open. `start()` (lines 38-57) then dispatches `mergeBranch` using this cached `Branch`/`mergeStatus` pair. `AppStore._mergeBranch` (`app/src/lib/stores/app-store.ts:7336-7380`) performs no re-check of the branch tip or mergeability before calling `GitStore.merge`, which invokes `git merge <branch.name>` (`app/src/lib/stores/git-store.ts:1489-1516`, `app/src/lib/git/merge.ts:29-59`) — i.e., it resolves and merges whatever the branch name currently points to at execution time, not the sha that was previewed.

Meanwhile, `BackgroundFetcher` (`app/src/lib/stores/helpers/background-fetcher.ts`) runs unattended fetches, and `AppStore.performFetch` calls `fastForwardBranches` to update local branch refs from the fetched remote data (`app/src/lib/stores/app-store.ts:5924-5966`, `app/src/lib/git/fetch.ts:103-141`) with no user confirmation. This can happen at any point while the merge dialog is open, moving the target branch's tip out from under the stale preview.

### Impact Explanation
A malicious or compromised remote (or a network-position attacker able to spoof the git remote's response) can inject arbitrary new commits into a branch between the time the user reviews a "clean" merge preview and the time they click "Merge." Desktop will merge and commit those new, unreviewed, attacker-supplied changes into the user's working branch — silently corrupting what the user commits, and potentially what they subsequently push to a shared/trusted remote (e.g., propagating malicious code into a shared repository history under the victim's authorship).

### Likelihood Explanation
Requires an attacker able to update the content behind a git remote a Desktop user has added (a supported valid-impact primitive), and reasonable timing — Desktop performs unattended background fetches roughly every 30 minutes and on window focus, which increases the odds of a race landing while a merge dialog is open, especially for a slower-reviewed merge (larger diff, waiting for teammate confirmation, etc.). It requires no unusual user action beyond the normal "open merge dialog, review, click Merge" flow.

### Recommendation
Re-validate the merge target immediately before execution: either re-fetch/re-resolve the target branch's tip sha and re-run `determineMergeability`/ahead-behind at the moment "Merge" is clicked (aborting or re-prompting if the tip changed since the preview), or pass the previewed sha through to the merge operation and merge that exact sha rather than the mutable branch name, failing loudly if the ref has moved.

### Proof of Concept
1. Attacker controls (or is a collaborator with push access to, or MITMs) a remote `origin` that Desktop is configured to fetch from.
2. Victim opens GitHub Desktop, selects the shared branch, opens "Merge into Current Branch...", and picks the attacker's branch. `updateStatus` computes and displays "Clean" merge with N commits (`merge-choose-branch-dialog.tsx:102-140`).
3. While the dialog remains open (during victim's review/hesitation), the attacker pushes new, malicious commits to that branch on the remote.
4. Desktop's `BackgroundFetcher` performs its periodic unattended fetch (`background-fetcher.ts:77-116`) and `fastForwardBranches` silently updates the local ref for that branch to the attacker's new tip (`app-store.ts:5924-5966`).
5. The dialog's cached `mergeStatus`/`commitCount` are never invalidated (no listener re-triggers `updateStatus`).
6. Victim clicks "Merge" trusting the stale preview; `_mergeBranch` → `GitStore.merge` → `git merge <branchName>` merges the attacker's new tip, not what was previewed (`app-store.ts:7336-7380`, `git-store.ts:1489-1516`).
7. A merge commit now exists in the victim's branch containing unreviewed attacker content, which the victim may subsequently push.

/** Merge the named branch into the current branch. */
export async function merge(
  repository: Repository,
  branch: string,
  options?: MergeOptions
): Promise<MergeResult> {
  const onTerminalOutputAvailable = options?.onTerminalOutputAvailable
    ? createMultiOperationTerminalOutputCallback(
        options?.onTerminalOutputAvailable
      )
    : undefined

  const args = ['merge']

  if (options?.squash) {
    args.push('--squash')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  args.push(branch)

  const { exitCode, stdout } = await git(args, repository.path, 'merge', {
    expectedErrors: new Set([GitError.MergeConflicts]),
    interceptHooks: ['pre-merge-commit', 'post-merge', 'commit-msg'],
    onHookProgress: options?.onHookProgress,
    onHookFailure: options?.onHookFailure,
    onTerminalOutputAvailable,
  })

    }

export async function fastForwardBranches(
  repository: Repository,
  branches: ReadonlyArray<ITrackingBranch>
): Promise<void> {
  if (branches.length === 0) {
    return
  }

  const refPairs = branches.map(branch => `${branch.upstreamRef}:${branch.ref}`)

  await git(
    [
      'fetch',
      '.',
      // Make sure we don't try to update branches that can't be fast-forwarded
      // even if the user disabled this via the git config option
      // `fetch.showForcedUpdates`
      '--show-forced-updates',
      // Prevent `git fetch` from touching the `FETCH_HEAD`
      '--no-write-fetch-head',
      // Take branch refs from stdin to circumvent shell max line length
      // limitations (mainly on Windows)
      '--stdin',
    ],
    repository.path,
    'fastForwardBranches',
    {
      // Fetch exits with an exit code of 1 if one or more refs failed to update
      // which is what we expect will happen
      successExitCodes: new Set([0, 1]),
      env: {
        // This will make sure the reflog entries are correct after
        // fast-forwarding the branches.
        GIT_REFLOG_ACTION: 'pull',
      },
      stdin: refPairs.join('\n'),
    }
  )
}
