## Analog Vulnerability Found

### Title
Unhandled `KeyError` crash in `Offer.to_valid_spend()` from a malicious counterparty offer with a zero-amount requested payment for an unoffered asset - ([File: chia/wallet/trading/offer.py])

### Summary
The rsync bug class is a receiver-side crash caused by trusting attacker-controlled data to index into an internal array/structure without validating that the referenced entry actually exists, leading to an out-of-bounds/invalid dereference and a deterministic crash. The chia analog is in `chia/wallet/trading/offer.py`, where `Offer.to_valid_spend()` indexes a dictionary (`all_offered_coins[asset_id]`) that is built heuristically from the counterparty-supplied spend bundle, using a key (`asset_id`) that comes from the same untrusted offer's `requested_payments`. The code assumes every requested `asset_id` will always have a corresponding entry in `all_offered_coins`, but that entry is only populated when `_get_offered_coins()` actually finds matching settlement coins for that asset. A crafted offer can request an asset with a zero-amount payment while never actually offering any coin for that asset, defeating the `is_valid()`/`arbitrage()` guard (since zero requested amount vs. zero offered amount nets to `0 >= 0`), and reach the unguarded dictionary access, raising an uncaught `KeyError`.

### Finding Description
`Offer.to_valid_spend()` (called when a wallet user accepts/completes a trade) loops over `self.requested_payments.items()` — attacker-controlled data parsed from the untrusted offer file via `Offer.from_spend_bundle()`/`Offer.from_bech32()` — and does: [1](#0-0) 

```python
all_offered_coins: dict[bytes32 | None, list[Coin]] = self.get_offered_coins()
total_arbitrage_amount: dict[bytes32 | None, int] = self.arbitrage()
for asset_id, payments in self.requested_payments.items():
    offered_coins: list[Coin] = all_offered_coins[asset_id]
```

`all_offered_coins` is produced by `_get_offered_coins()`, which only inserts a key for `asset_id` when it actually found matching "offered" coins for that asset in the bundle's real spends: [2](#0-1) 

The guard that is supposed to prevent an incomplete/invalid offer from reaching this code is `is_valid()`, which relies on `arbitrage()`: [3](#0-2) 

```python
def arbitrage(self) -> dict[bytes32 | None, int]:
    offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
    requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()
    arbitrage_dict: dict[bytes32 | None, int] = {}
    for asset_id in [*requested_amounts.keys(), *offered_amounts.keys()]:
        arbitrage_dict[asset_id] = offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)
    return arbitrage_dict
```

and [4](#0-3) 

```python
def is_valid(self) -> bool:
    return all([value >= 0 for value in self.arbitrage().values()])
```

Both `offered_amounts.get(asset_id, 0)` and `requested_amounts.get(asset_id, 0)` default to `0` when the asset id is absent, so a `NotarizedPayment` with `amount == 0` for an asset that is never actually offered produces `arbitrage[asset_id] == 0`, which satisfies `is_valid()` (`0 >= 0`). Execution then proceeds into the unguarded `all_offered_coins[asset_id]` lookup in `to_valid_spend()`, which raises `KeyError` because `_get_offered_coins()` never populated that key (no coin was found `coins_for_this_spend != []`).

This mirrors the rsync defect: attacker-controlled indexing metadata (the `ndx`/index equivalent, here `asset_id`) is trusted to correspond to a populated slot without the receiver validating that the slot actually exists, producing a deterministic crash when processing the malicious record.

### Impact Explanation
Any wallet user who receives and attempts to inspect, validate, or accept ("take") a maliciously crafted offer file/bech32 string reaches `Offer.to_valid_spend()` (directly, or transitively through trade-completion flows in `chia/wallet/trade_manager.py` that call it to build the final settlement spend bundle). The uncaught `KeyError` aborts that offer-processing/transaction-building operation. Since offer files are commonly shared out-of-band (chat, marketplaces, CLI/RPC `take_offer`) and processed by end users' wallets, this is a reachable, spend-triggered halt of transaction processing for any wallet that attempts to complete the crafted offer — a legitimate Medium-severity denial-of-service analog to the rsync out-of-bounds-read crash.

### Likelihood Explanation
Likelihood is Medium: constructing the malicious offer only requires building a `SpendBundle` with a dummy "requested payment" coin spend whose `NotarizedPayment` has `amount == 0` for an asset id that is not actually created/offered anywhere else in the bundle, then encoding it via `Offer.to_spend_bundle()`/`compress()` as a normal-looking offer. No special network position, keys, or privileged access are needed — a single attacker-authored offer suffices, and the trigger occurs purely in Python-side offer post-processing (`is_valid()`, `arbitrage()`, `to_valid_spend()`), not deep inside CLVM execution, making it easy to hit reliably.

### Recommendation
In `Offer.to_valid_spend()`, do not assume every `asset_id` in `self.requested_payments` has a corresponding entry in `all_offered_coins`. Use `all_offered_coins.get(asset_id, [])` (or explicitly validate/raise a domain-specific `ValueError`/`ValidationError` such as "Offer does not actually offer coins for asset_id X") instead of a bare `[asset_id]` lookup, and/or tighten `is_valid()`/`arbitrage()` to treat a requested asset with no corresponding offered-coins entry as invalid regardless of the requested amount being zero.

### Proof of Concept
1. Build a `SpendBundle` whose only "requested payment" dummy spend (parent `bytes32.zeros`) encodes a `NotarizedPayment` for some `asset_id` (e.g., a CAT asset id) with `amount = 0`, matching the format consumed by `Offer.from_spend_bundle()`.
2. Ensure the bundle's other ("leftover") coin spends do not create any coin sent to `OFFER_MOD_HASH`/the asset's settlement puzzle hash for that `asset_id` — i.e., nothing is actually offered for that asset.
3. Serialize/compress this bundle into an offer string via the same encoding `Offer.compress()`/`to_bech32()` uses, and hand it to a victim as a normal offer file.
4. Victim wallet calls `Offer.from_bech32()` and then `to_valid_spend()` (as done during offer acceptance in `chia/wallet/trade_manager.py`).
5. `is_valid()` returns `True` because `arbitrage[asset_id] == 0 - 0 == 0`, passing validation; execution reaches `all_offered_coins[asset_id]` in `to_valid_spend()`, which raises an uncaught `KeyError`, aborting the offer-acceptance transaction-building flow.

Note: I could not fully trace every call site in `chia/wallet/trade_manager.py` and `chia/wallet/vc_wallet/vc_wallet.py` that reach `to_valid_spend()` (e.g., whether any of them wrap the call in a broad `try/except` that would downgrade the crash to a handled RPC error rather than an unhandled exception) due to the limited number of remaining tool calls. If the wiki/README maintainers need certainty on whether this propagates as an unhandled process crash versus a caught RPC error, a Devin session with full file access should be used to confirm the exact exception-handling behavior at each `to_valid_spend()` call site.
