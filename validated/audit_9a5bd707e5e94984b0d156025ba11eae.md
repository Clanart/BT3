## Title
Independent, unsynchronized conflict-marker parsers in Copilot merge-conflict resolution can splice model output into the wrong hunk, silently corrupting committed content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Like the Popcorn `Vault.sol` bug — where each fee is validated in isolation but the combined total is never checked against the real invariant (`<1e18`) — GitHub Desktop's Copilot conflict-resolution pipeline validates hunk *counts* per file but never validates that the two independent conflict-marker parsers used at different stages of the pipeline actually agree on hunk *boundaries/order*. A crafted, attacker-controlled file (from a branch/PR the victim merges/rebases) can make the two parsers disagree while still passing the count check, causing the model's per-hunk resolution to be spliced into the wrong conflict region of the file that is subsequently written to disk and `git add`ed.

### Finding Description
Two separate regex-based parsers walk the same raw conflicted file independently, at different times, with different fallback behavior for malformed marker sequences:

1. **Extraction** (`extractConflictHunks`) uses `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` and, while collecting "ours" content, only breaks the collection loop on a base or separator marker — it does not re-validate that intervening lines are not themselves further marker sequences. When a well-formed closing `>>>>>>>` is never found, the malformed block is silently dropped (`continue`), and everything scanned up to EOF is discarded from the hunk list entirely. [1](#0-0) [2](#0-1) [3](#0-2) 

2. **Reassembly** (`reassembleResolvedFile`) uses a *second, independently-defined* set of marker regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) and a different fallback: a malformed block (missing separator/close) is treated as regular content and copied through **one line at a time**, after which scanning resumes and can pick up later, unrelated `<<<<<<<`-looking lines as new conflict blocks. [4](#0-3) [5](#0-4) 

The only cross-check between the two parses is a bare **count** comparison in `validateResolutionPaths`, which compares `resolution.hunks.length` to `expectedHunkCounts` derived from `extractConflictHunks`: [6](#0-5) 

Nothing verifies that the *positions/order* the two parsers assign to conflict blocks match. `reassembleResolvedFile` explicitly documents that hunks are "matched by order, not by line number": [7](#0-6) 

Because both regexes are purely syntactic (`/^<{7}(?:\s|$)/`, `/^={7}$/`, `/^>{7}(?:\s|$)/`) and do not verify that a marker block is a genuine git conflict (e.g. no check against actual git conflict state, labels, or SHA suffixes), any file containing marker-shaped text unrelated to a real conflict — such as documentation, ASCII examples, or generated content demonstrating conflict-marker syntax, fully controlled by whoever authored the attacker branch/PR — can cause `extractConflictHunks` and `reassembleResolvedFile` to disagree on how many/which regions are "hunks," while still coincidentally agreeing on the raw count. This is exactly the "each part individually checked, combined invariant violated" pattern from the source report: each parser's own malformed-handling logic is internally self-consistent, but the invariant that the two parsers must agree is never checked.

### Impact Explanation
When the two parses disagree on hunk boundaries/order (but by coincidence produce the same hunk count so `validateResolutionPaths` passes), `reassembleResolvedFile` splices the model's `resolvedContent` for hunk *N* into whatever marker block *it* identified as hunk *N* — which may correspond to a different, unrelated conflict block than the one the model actually reasoned about. The result is written straight to disk and staged: [8](#0-7) 

This is a silent corruption of what the user commits/pushes: the result dialog shows a plausible-looking resolution and reasoning, the user clicks "Continue Merge," and the actually-written file contains resolution text spliced into the wrong location (or decoy conflict-marker-shaped documentation content misinterpreted as a real, resolvable conflict and stripped/overwritten). The victim is an unprivileged user merging/rebasing a branch/PR whose content is entirely attacker-controlled — matching the required "attacker controls a cloned/fetched repository" impact category.

### Likelihood Explanation
Exploitation requires no unusual local access — only that the victim merges, rebases, or cherry-picks a branch/PR containing a specially crafted file (real conflict markers plus additional marker-shaped text, or a subtly malformed marker sequence) and then uses the "Resolve with Copilot" feature and accepts the result without diffing the model's summary against the actual on-disk bytes. Given that Copilot conflict resolution is explicitly designed to let users skip manual review of hunks, likelihood of the corrupted content being merged and pushed unnoticed is non-trivial, though it requires a fairly specific crafted input (an edge case, not the common well-formed two-way/diff3 conflict).

### Recommendation
Do not maintain two independent regex-based conflict-marker parsers with divergent malformed-block handling. Reuse a single parsing function/module for both hunk extraction (prompt-building) and reassembly (splicing), so hunk boundaries are guaranteed structurally identical. Additionally, tag each extracted hunk with a strong positional identifier (e.g. start/end line numbers or a content hash) that is threaded through the model interaction and validated at splice time — reassembly should fail closed (throw `CopilotValidationError`) if the marker blocks it finds at splice time don't structurally match the ones sent to the model, rather than only checking counts.

### Proof of Concept
Conceptual repro using the exported functions in `app/src/lib/copilot-conflict-context.ts` and `app/src/lib/copilot-conflict-resolution.ts`:
1. Construct `fileContent` with one well-formed conflict, followed later by an unrelated marker-shaped example (e.g. documentation containing a line matching `/^<{7}(?:\s|$)/` without a matching, correctly-scoped closing sequence understood the same way by both parsers).
2. Call `extractConflictHunks(fileContent)` and note the hunk count/positions it returns (used to build the prompt and by `validateResolutionPaths`).
3. Independently call `reassembleResolvedFile(fileContent, hunkResolutions)` with an array sized to match that count, and observe that the block(s) it locates via `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` do not correspond 1:1 in position/order to the ones `extractConflictHunks` identified — resulting in `hunkResolutions[i]` being spliced into a different location than the one the model actually reasoned about for that index. export function reassembleResolvedFile(
```typescript
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
```
