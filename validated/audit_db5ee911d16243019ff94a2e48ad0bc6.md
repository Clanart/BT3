### Title
Permissionless cross-chain bandwidth "purchase" spam evicts a victim app's paid, unused subscriptions - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
The external report's core primitive is: an unauthenticated actor can call a public entrypoint in an unbounded loop, and the receiving system has no rate limit or ownership check, so the attacker's repeated calls destroy resources belonging to someone else. In Hyperbridge, the analogous public entrypoint is `BandwidthManager.purchase()` [1](#0-0) , which lets *any* caller credit bandwidth to an **arbitrary** `(chain, app)` pair chosen by the caller, not necessarily their own. `pallet-bandwidth` stores each `(app_chain, app)`'s subscriptions in a FIFO list capped at `MAX_SUBSCRIPTIONS` (1024); pushing past the cap silently **evicts the oldest, still-unused entry** regardless of how much of it is unconsumed [2](#0-1) . An attacker can therefore repeatedly call `purchase()` targeting a victim app's `(chain, app)` key with 1024 cheap tier purchases, pushing the victim's legitimately-paid, unconsumed high-value subscriptions out of the FIFO and permanently destroying the bytes the victim already paid for.

### Finding Description
`purchase()` is fully permissionless and takes `app` and `chain` as caller-supplied parameters with no binding to `msg.sender` or to the calling chain [1](#0-0) . This is intentional "sponsorship" — the docs describe it as allowing "a treasury on a single chain [to] sponsor bandwidth for an app deployed across many chains" [3](#0-2) . On the pallet side, `on_accept` decodes the purchase message and calls `push_subscription(&msg.chain, &key, tier, bytes, duration)` keyed purely by the message body's `app_chain`/`app`, not by `request.source` [4](#0-3) .

`push_subscription` enforces the FIFO cap by evicting index `0` (the oldest entry) whenever the list is full — with no check on how much of that entry's `remaining_bytes` is unused:
```
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else {
        None
    };
    let _ = list.try_push(new_sub);
    evicted
});
``` [5](#0-4) 

The docs acknowledge the eviction mechanic exists ("`SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain") but assume it "only happens under pathological repeat-buy behavior" *by the app itself* [6](#0-5) . That assumption is false: because `app`/`chain` are attacker-controlled and unrelated to the payer's identity, a third party can target any victim's bucket directly.

This is exactly the DoS report's shape translated to a fund-bearing surface: an unbounded loop of calls to one public function (`purchase`/`sign`), with no per-caller/per-target throttling, corrupts state that belongs to a different party — here the corrupted value is the victim's `Allowance<T>` FIFO list, whose oldest (fully-paid, unconsumed) `Subscription.remaining_bytes` is deleted via `list.remove(0)` with no ownership or usage check.

### Impact Explanation
The eviction is a genuine, unrecoverable loss of paid-for value: `remaining_bytes` on the evicted subscription can be the full amount the victim purchased and never had a chance to use, and there is no compensation or refund path — only a `SubscriptionEvicted` event is emitted for auditability, not remediation [7](#0-6) . Because a `dispatch()`-gated app that runs out of bandwidth is rejected by `BandwidthGate::try_consume` at the ISMP router [8](#0-7) , this is not merely a griefing/DoS on a UI — it is a loss of funds (the money already paid for the destroyed bandwidth) and can additionally cause the victim app's legitimate cross-chain messages to be rejected once its remaining live subscriptions are exhausted.

### Likelihood Explanation
The attack requires no special privilege, no relayer/prover/validator compromise, and no governance access — only calling a public, unauthenticated function (`purchase`) from any chain that has a registered `BandwidthManager`, targeting an arbitrary victim `(chain, app)` pair. The only cost is paying for `MAX_SUBSCRIPTIONS` (1024) cheapest-tier purchases, which is a bounded, attacker-controlled expense rather than a structural barrier, and is far cheaper the smaller the victim's existing queue depth or the cheaper the configured tiers are.

### Recommendation
- Scope `purchase()`/credit targeting so a payer cannot arbitrarily choose a victim's `(chain, app)` bucket without some binding to the actual app owner (e.g., require `msg.sender == app` unless an explicit sponsorship allowlist/authorization is set by the app).
- On eviction, prefer evicting the subscription with the least remaining value or refund/carry-forward unused `remaining_bytes` rather than unconditionally dropping index 0, or increase `MAX_SUBSCRIPTIONS` / merge same-tier entries to raise the cost of a griefing campaign.
- Consider a minimum "cool-down" or a max number of subscriptions creditable by a single non-owner payer within a window, to prevent a single sponsor's purchases from crowding out the FIFO.

### Proof of Concept
1. Victim `AppX` on `EVM-8453` legitimately buys `TierFour` (8MB, largest allowance) once — `Allowance[EVM-8453, AppX]` now holds 1 subscription with `remaining_bytes = 8_000_000` and `expires_at` far in the future.
2. Attacker (any address, any registered source chain) calls `BandwidthManager.purchase(app = AppX, tier = TierOne, months = 1, chain = "EVM-8453")` 1024 times in a loop, paying the `$50` `TierOne` price each time — each call is independent, unauthenticated, and unrelated to `AppX`'s owner.
3. Each purchase dispatches a `BandwidthPurchaseMsg` to `pallet-bandwidth`; `on_accept` calls `push_subscription(EVM-8453, AppX, TierOne, 100_000, ...)` for each, appending to `Allowance<T>` [9](#0-8) .
4. On the 1025th append (the list is now full at `MAX_SUBSCRIPTIONS`), `push_subscription` evicts index `0` — the victim's original, unconsumed 8MB `TierFour` subscription — and emits `SubscriptionEvicted { lost_bytes: 8_000_000 }` [10](#0-9) .
5. `AppX` has permanently lost the 8MB of bandwidth it paid for, with no refund; if it had no other subscriptions, its subsequent ISMP dispatches are now rejected by `BandwidthGate::try_consume` returning `GateError::NoAllowance` [8](#0-7) .

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {

				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```
