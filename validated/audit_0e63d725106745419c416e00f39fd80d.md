This confirms the analog: `purchase()` in `BandwidthManager.sol` and the pallet's `push_subscription` in `modules/pallets/bandwidth/src/lib.rs` together create a permissionless, unbounded eviction primitive against any target `(chain, app)` bucket.

### Title
Permissionless bandwidth purchase lets an attacker evict a victim app's paid-for subscriptions via FIFO cap eviction - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`BandwidthManager.purchase()` accepts an arbitrary `app` and `chain` argument controlled entirely by the caller, with no relationship required to `msg.sender` [1](#0-0) . This is an intentional "sponsorship" feature so a payer can credit bandwidth for a third-party app on any chain [2](#0-1) . On the Hyperbridge side, `push_subscription` appends every purchase to a FIFO list capped at `MAX_SUBSCRIPTIONS` (1024); once full, the **oldest** entry is silently evicted regardless of its remaining byte balance or how much was paid for it [3](#0-2) .

### Finding Description
Because `purchase()` is fully permissionless with respect to the target `app`/`chain` and the cheapest configured tier can be bought in bulk, an attacker can flood a victim `(chain, app)` bucket with 1024 minimal, low-cost tier purchases. Each purchase is only gated by `UnknownTier`/`InvalidPurchase` checks on price/format, not by any relationship to the target app or by minimum-bytes/minimum-value floors [4](#0-3) . Once the FIFO list is saturated, each additional attacker purchase evicts the head of the queue — which, given enough attacker purchases, will eventually be the victim's own large, non-expired, previously-paid subscription — deleting its `remaining_bytes` permanently [5](#0-4) . The eviction path performs no value comparison between the incoming and outgoing subscription (it just calls `list.remove(0)` unconditionally when full), so a $5 attacker purchase can silently destroy a $1000 victim subscription that has thousands of paid bytes still remaining [6](#0-5) . The subsequent gate check (`try_consume`) then sees a truncated or empty allowance for the victim app and starts rejecting the victim's legitimate cross-chain traffic [7](#0-6) .

### Impact Explanation
This is a direct loss-of-funds vector: the victim app paid the fee token cost of its subscription (pulled via `safeTransferFrom` into `BandwidthManager`) but is deprived of the corresponding byte allowance it purchased, and the attacker did not even need to target the specific bytes — merely repeatedly calling `purchase()` against the victim's `(chain, app)` key with a cheap tier is sufficient to eventually push the FIFO past 1024 entries and evict the victim's real subscription. Beyond the fund loss, the victim's app is also effectively taken offline: with no live subscriptions, `BandwidthGate::try_consume` returns `NoAllowance` and every subsequent request from that app is rejected by the ISMP router until it repurchases [8](#0-7) .

### Likelihood Explanation
The cost to the attacker is bounded by `1024 × (cheapest tier price)`, a known, governance-set, and typically small dollar amount (the cheapest documented tier is $50) [9](#0-8) . No relayer collusion, prover compromise, or governance access is required — the attack is executable end-to-end by any unprivileged EVM account holding fee tokens, using the public `purchase()` entrypoint exactly as sponsorship is documented to be used. The eviction behavior is even called out as "auditable" via `SubscriptionEvicted`, indicating awareness of eviction but not of the fact that eviction is attacker-triggerable against an arbitrary target.

### Recommendation
Either (a) restrict `push_subscription` eviction so entries with non-trivial `remaining_bytes` cannot be evicted purely by list pressure — e.g., reject/queue new purchases instead of evicting when the oldest live entry still has significant unused allowance — or (b) require the caller purchasing bandwidth for an `app` it does not control to pay proportionally more per-purchase (e.g., a minimum bytes/months floor) so the 1024-slot cap cannot be exhausted cheaply, or (c) key eviction priority by remaining value rather than strict FIFO insertion order, so a large recently-funded subscription can never be evicted by a stream of dust purchases.

### Proof of Concept
1. Victim app buys `TierFour` (8MB / high price) for `(EVM-8453, victimApp)`, creating subscription #1 with large `remaining_bytes` and long `expires_at`.
2. Attacker calls `BandwidthManager.purchase(victimApp, TierOne, 1, "EVM-8453")` 1024 times (any EVM source chain with a registered manager), each a small, cheap purchase — permitted because `app`/`chain` are attacker-supplied with no relation to `msg.sender` [1](#0-0) .
3. On the 1024th+1 credit, `push_subscription` sees `list.len() == MAX_SUBSCRIPTIONS` and evicts index 0 — which is the victim's subscription #1 once enough attacker entries have pushed it to the front of the FIFO drain order (or directly if the victim had only that one entry and attacker purchases exceed 1024) [5](#0-4) .
4. Victim's paid `remaining_bytes` are gone; `Bandwidth::remaining(EVM-8453, victimApp)` drops to near zero, and `BandwidthGate::try_consume` starts returning `NoAllowance`/`Insufficient` for the victim's legitimate dispatches, even though the victim already paid for that bandwidth.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
