### Title
Path-prefix boundary bypass in `resolveWithin()` allows sandbox-escape reads outside the repository - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is Desktop's shared guard for confining a repository-relative path to the working directory. It ultimately validates containment with a bare string comparison, `realResolved.startsWith(realRoot)`, instead of checking for an exact match or a trailing path-separator boundary. This is the same class of bug as the reported `err_mid < 0` vs `err_mid <= 0` issue: a boundary/convergence check that is missing the exact-boundary case, so a value that is *outside* the intended set (a sibling directory whose name happens to share the root directory name as a string prefix) is incorrectly treated as *inside* it. [1](#0-0) 

### Finding Description
`_resolveWithin()` documents a strict invariant: "the resolved path is guaranteed to reside at, or underneath, this path" [2](#0-1) . It resolves the caller-supplied segments against the root, `realpath()`s both sides to defeat symlinks, and then checks containment purely with:

```
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

`String.prototype.startsWith` performs no notion of a path boundary. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo` and the resolved path is `/Users/victim/Documents/GitHub/myrepo-secrets/config.json` (a sibling directory that merely begins with the same characters as the repo's directory name), `startsWith` returns `true` even though that sibling directory is not underneath `myrepo` at all. The function's guarantee is silently violated — the "convergence condition" (containment check) is too permissive, exactly mirroring the reported `<` vs `<=` boundary defect, just inverted (too loose instead of too strict).

This helper is consumed by `buildConflictContext()` to gate which on-disk files get read and sent to Copilot when resolving merge/rebase/cherry-pick conflicts:
```
absolutePath = await resolveWithin(workingDirectory, file.path)
...
content = await readFile(absolutePath, 'utf8')
``` [4](#0-3) 
The comment explicitly frames this call as "Guard against path traversal and symlink escapes" — i.e., this is the security boundary the feature relies on [5](#0-4) . `file.path` is derived from the set of conflicted paths reported for a merge that the attacker's branch/remote participates in, so an attacker who controls the branch/commits being merged controls (or heavily influences) the relative path segments fed into `resolveWithin`.

The existing safeguards (null-byte check, `Path.normalize`/`Path.resolve` traversal collapsing, and symlink-resolution via `realpath`) do not stop this path: none of them inspect whether the character *immediately after* the root prefix in the resolved string is a path separator or end-of-string. As long as `resolve()` can walk far enough (e.g. via repeated `..` segments) to land in a directory whose name has the repo's directory name as a literal string prefix, the check passes.

### Impact Explanation
This breaks the fundamental invariant "resolved path is guaranteed to reside at, or underneath, the root path" that other code relies on for safety. Concretely, in the Copilot conflict-resolution feature this can cause Desktop to read a file **outside** the intended repository directory and forward its contents into the AI-conflict-resolution prompt sent to the SDK — an unprivileged, attacker-influenced file-read outside the repo, matching the stated valid-impact category ("attacker controls a cloned/fetched repository ... and the result is ... file ... read outside the repo").

### Likelihood Explanation
Exploitability is bounded by two factors this analysis could not fully rule out: (1) whether the underlying git tooling actually permits a conflicted-file relative path to contain `..`/traversal segments (git normally rejects `..` path components in tree entries), and (2) whether a sibling directory with a name that is a literal prefix-match of the repository directory exists on the victim's filesystem (e.g., backup folders like `myrepo-old`, `myrepo.bak`, or another repo cloned adjacently with a similar name — a plausible but not guaranteed real-world layout). Given these preconditions, likelihood is moderate-to-low, but the code defect itself is unambiguous and independently verifiable by inspection, and the containment check is the sole line of defense once symlink resolution has run.

### Recommendation
Replace the bare prefix check with an exact boundary-aware comparison, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This closes the sibling-directory prefix bypass and restores the documented invariant, in the same spirit as changing `err_mid < 0` to `err_mid <= 0` in the original report — adding the missing exact-boundary case to the comparison.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
// Root: /Users/victim/Documents/GitHub/myrepo
// Sibling dir exists: /Users/victim/Documents/GitHub/myrepo-secrets/config.json

const result = await resolveWithin(
  '/Users/victim/Documents/GitHub/myrepo',
  '../myrepo-secrets/config.json'
)
// Expected: null (outside root)
// Actual: '/Users/victim/Documents/GitHub/myrepo-secrets/config.json'
// because '/Users/victim/Documents/GitHub/myrepo-secrets/config.json'.startsWith(
//           '/Users/victim/Documents/GitHub/myrepo') === true
```
When reached through `buildConflictContext()` with an attacker-influenced conflicted `file.path` of `../myrepo-secrets/config.json`, this file outside the repo would be read and included in the Copilot prompt. [4](#0-3) [1](#0-0)
