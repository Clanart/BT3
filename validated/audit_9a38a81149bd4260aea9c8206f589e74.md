### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` allows remote stack-exhaustion DoS via crafted transaction - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP` decode account-key payloads without any recursion-depth limit. An attacker can nest `AccountKeyTypeRoleBased`-typed sub-keys inside each other and submit this as the `Key` field of an `AccountUpdate`/`FeeDelegatedAccountUpdate`-family transaction via the public RPC (`sendRawTransaction`). Because the composite-type rejection (`IsCompositeType`, `CheckInstallable`) only runs *after* the entire structure has been fully RLP-decoded, the decoder itself performs unbounded mutual recursion, which can exhaust the goroutine stack and crash the node — the same bug class as CVE-2018-15173 (crafted input causes uncontrolled recursive parsing → stack consumption → crash), reachable here from a single submitted transaction instead of a network scan response.

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a key type and then decodes into the corresponding `AccountKey` implementation: [1](#0-0) 

When the type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` iterates over an arbitrary-length list of raw byte strings and recursively decodes each one back into a new `AccountKeySerializer`: [2](#0-1) 

Nothing prevents one of those inner byte strings from itself encoding an `AccountKeyTypeRoleBased` value, which again triggers `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` recursively. `NewAccountKey` unconditionally constructs whatever type tag is present with no depth counter: [3](#0-2) 

The only protection against nested composite keys, `IsCompositeType`/`CheckInstallable`/`checkAccountKeyZeroValues`, is applied *after* decoding completes, e.g. in `AccountKeyRoleBased.CheckInstallable`: [4](#0-3) 
and in the JSON-RPC helper `checkAccountKeyZeroValues`: [5](#0-4) 

This is too late: the malicious recursion already happened inside `rlp.DecodeBytes` while parsing the raw transaction bytes, before any nesting validation runs. The same recursive `DecodeRLP` path is invoked for `TxInternalDataAccountUpdate`/`TxInternalDataFeeDelegatedAccountUpdate*` when a raw transaction is submitted: [6](#0-5) [7](#0-6) 

RLP list nesting overhead can be as small as a few bytes per level, so an attacker can pack thousands of nested `RoleBased` levels into a single transaction that still fits under typical transaction-size limits, producing thousands of nested Go call frames (`DecodeRLP` → `s.Decode` → `rlp.DecodeBytes` → `DecodeRLP` …) purely from parsing untrusted input.

### Impact Explanation
Deeply nested recursive decoding of a single crafted transaction can drive the decoding goroutine's stack toward Go's runtime stack limit, resulting in a fatal, unrecoverable `runtime: goroutine stack exceeds ... limit` crash rather than a catchable panic. Because this occurs during RLP decoding of a transaction — which happens both when a node accepts a transaction into the pool via public RPC and when it processes a block — a single unprivileged transaction sender can crash any node that decodes the transaction (mempool propagation and block execution), constituting a remote, unauthenticated denial-of-service against network availability.

### Likelihood Explanation
Likelihood is high: no privileged role, contract, or on-chain state is required — an attacker only needs to hand-craft the RLP payload for the `Key` field of an `AccountUpdate`-class transaction and submit it via any public RPC endpoint accepting raw transactions. Standard signature/type validation does not inspect nesting depth before decoding, and the depth check that exists (`IsCompositeType`) executes only after decoding, so it cannot prevent the crash.

### Recommendation
Add an explicit recursion-depth counter/limit to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if `AccountKeyTypeRoleBased` is nested more than one level deep, consistent with the "no nested composite type" business rule), enforced *during* decoding rather than only in post-decode validation. Alternatively, use `rlp.NewStream` with an explicit list-nesting/size limit for account-key payloads, and add a fuzz/regression test that submits deeply nested RoleBased-in-RoleBased encodings to confirm the decoder now fails fast without deep recursion.

### Proof of Concept
1. Recursively RLP-encode an `AccountKeySerializer` value of type `AccountKeyTypeRoleBased` whose single role slot is itself an `AccountKeySerializer` of type `AccountKeyTypeRoleBased`, repeating this nesting N times (N in the thousands) to build the `Key` byte string, mirroring the structure used in `AccountKeyRoleBased.DecodeRLP`. [2](#0-1) 
2. Embed the resulting bytes as the `Key` field of a `TxInternalDataAccountUpdate` (or `FeeDelegatedAccountUpdate`) transaction, RLP-encode the full transaction, and sign it as shown in the existing test harness pattern (`TestWronglyEncodedAccountKey`) that manually builds and RLP-encodes these transaction fields: [8](#0-7) 
3. Submit the raw transaction to a node's public RPC (`sendRawTransaction`). Decoding occurs through `TxInternalDataAccountUpdate.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`, recursing N times and driving the decoding goroutine stack toward the runtime limit, crashing the node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
