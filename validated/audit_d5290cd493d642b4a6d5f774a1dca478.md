### Title
Permanently stale `decimals()` on native-token EVM pointers after tokenfactory admin updates denom metadata - ([File: precompiles/pointer/pointer.go])

### Summary
The `pointer` precompile's `AddNative` handler snapshots a native/tokenfactory denom's `decimals` from `bankKeeper.GetDenomMetaData` at pointer-creation time and bakes it as an immutable constructor argument into the deployed `NativeSeiTokensERC20` ERC20 pointer contract. A tokenfactory denom admin can later change that same denom's `decimal` exponent via `MsgSetDenomMetadata`, but the already-deployed pointer's cached `decimals()` never updates and the pointer cannot be redeployed once it exists — permanently desynchronizing the ERC20 view of the token's decimal precision from its Cosmos-side ground truth, exactly the "stale-decimals-after-token-change" bug class described in the report.

### Finding Description
When a native pointer is created, `AddNative` in `precompiles/pointer/pointer.go` (lines 99-124, mirrored in every legacy pointer version, e.g. `precompiles/pointer/legacy/v640/pointer.go:99-133`) reads the denom's current `bank` `Metadata` via `p.bankKeeper.GetDenomMetaData`, derives `decimals` from the highest `DenomUnit.Exponent`, and forwards it into `k.UpsertERCNativePointer`: [1](#0-0) 

`UpsertERCNativePointer` passes that `Decimals` value straight into the constructor arguments used to deploy the `native` pointer bytecode: [2](#0-1) 

The deployed Solidity contract, `NativeSeiTokensERC20.sol`, stores this value in an immutable-by-design field `ddecimals` set only in the constructor and returned unconditionally by `decimals()`: [3](#0-2) 

Separately, the `tokenfactory` module lets the denom's admin (any permissionless creator of a `factory/{creator}/{subdenom}` denom, per `x/tokenfactory/README.md`) freely rewrite that denom's bank `Metadata` — including `DenomUnits`/`Exponent` (i.e., decimals) — at any later time via `MsgSetDenomMetadata`: [4](#0-3) 

Once a pointer already exists for a token, `AddNative` refuses to redeploy/refresh it (`existingVersion >= 1` guard seen consistently across pointer versions, e.g. `precompiles/pointer/legacy/v555/pointer.go:153-157`), so there is no user-triggered path to resynchronize the pointer's `decimals()` with a changed denom metadata. This is structurally analogous to the CW20 case, where `CW20ERC20Pointer.sol.decimals()` queries the CW20 contract live on every call rather than caching a value at creation time: [5](#0-4) 

### Impact Explanation
Any dApp, wallet, DEX, or bridging contract that treats a Sei native-token pointer as a standard ERC20 and uses its `decimals()` to compute swap ratios, prices, or scaled amounts will silently misinterpret raw base-unit balances after the admin changes the denom's exponent, because `balanceOf`/`totalSupply`/`transfer` on the pointer always operate in raw (undecimaled) base-denom units regardless of what `decimals()` reports. This is the same class of impact as the referenced report: a decimals field that is trusted downstream for value conversion becomes wrong after the underlying token's decimal configuration changes, which can produce mispriced trades, over/under-crediting in any downstream contract computing `amount / 10**decimals()`, and potential fund loss for counterparties who rely on the pointer's `decimals()` as source of truth.

### Likelihood Explanation
Reachability requires only: (1) creating a tokenfactory denom (permissionless, any account can do `MsgCreateDenom`), (2) creating an EVM pointer for it via the public `pointer` precompile `addNativePointer` (permissionless, callable by any EVM tx sender), and (3) later calling `MsgSetDenomMetadata` as that denom's own admin to change the `DenomUnits` exponent. All three steps are ordinary, unprivileged transactions from a single account acting as its own tokenfactory denom admin — no governance, validator collusion, or privileged role is required. The scenario is entirely self-inflicted-then-externally-exploited: the admin who controls the denom can intentionally launch a pointer at one decimals value, get it integrated by third-party contracts/DEXs, then change the underlying decimals to manipulate how those integrators compute value against the frozen pointer decimals.

### Recommendation
Either (a) make `NativeSeiTokensERC20.decimals()` query live bank denom metadata on every call (mirroring the CW20 pointer's live query pattern) instead of caching it in an immutable constructor field, or (b) disallow tokenfactory `MsgSetDenomMetadata` from changing `DenomUnits`/`Exponent` (decimals) once a pointer has been registered for that denom, or (c) allow a governance/permissionless pointer-refresh path that re-syncs `decimals()` (and emits an event) whenever the underlying denom metadata's decimal exponent changes.

### Proof of Concept
1. Attacker calls tokenfactory `MsgCreateDenom` to create `factory/attacker/coin`, which sets initial `Metadata` with `DenomUnits[0].Exponent = 0` (base denom itself, decimals effectively 0) — see `x/tokenfactory/keeper/createdenom.go:26-38`.
2. Attacker (or anyone) calls the `pointer` precompile's `addNativePointer("factory/attacker/coin")`. `AddNative` reads current metadata, computes `decimals = 0`, and deploys `NativeSeiTokensERC20` with `ddecimals = 0` baked in permanently (`precompiles/pointer/pointer.go:106-124`, `contracts/src/NativeSeiTokensERC20.sol:17-23`).
3. A third-party integrator (DEX, bridge) adds this pointer as an ERC20, reading `decimals() == 0` to compute swap math / pool pricing.
4. Attacker, still the tokenfactory admin, calls `MsgSetDenomMetadata` (`x/tokenfactory/keeper/msg_server.go:188-217`) to submit new `Metadata` with `DenomUnits` containing a higher exponent (e.g., 18), changing the token's intended decimal precision on the Cosmos side.
5. The already-deployed pointer's `decimals()` still returns `0` (immutable field), while raw balances/transfers are unchanged; any integrator that recomputes value using the now-stale `decimals()` against the (conceptually) redefined token miscalculates by orders of magnitude, and there is no mechanism to force-refresh the existing pointer (`existingVersion >= 1` guard blocks re-creation, e.g. `precompiles/pointer/legacy/v555/pointer.go:153-157`).

Note: I was unable to fully verify from the index whether any in-repo (first-party) contract or precompile besides third-party integrators actually consumes the pointer's `decimals()` for value computation — the concrete fund-loss path depends on downstream consumers (DEXs/bridges) treating the pointer as a standard ERC20, which is the documented intended use of these pointers but sits outside sei-chain's own code. If you need certainty about first-party consumers of pointer `decimals()`, a full-repo Devin session would be needed to grep broader integration/dapp code paths not indexed here.

```go
func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
```

```go
func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
```
