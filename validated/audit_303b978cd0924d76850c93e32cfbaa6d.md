### Title
Stale decimals invariant lets local asset owner mint/redeem far more tokens on the EVM side than were locked/burned - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet-hyper-fungible-token`'s `register_token`/`update_token` enforce `config.decimals >= local_decimals` only once, at registration time, and cache the EVM-side decimals in `Precisions` storage. The local asset's decimals, however, are **not** cached — `send()`, `on_accept()`, and `on_timeout()` all re-fetch them live via `fungibles::metadata::Inspect::decimals(asset_id)`. Because `pallet-assets` lets an asset's `Owner` change its `decimals` at any time via `set_metadata`, the registration-time invariant can be silently invalidated after the token is live. When `local_decimals` later exceeds the frozen `erc_decimals`, the scaling helper `convert_to_erc20` computes `erc_decimals.saturating_sub(local_decimals) == 0` instead of the (impossible, negative) scale-down factor, so no down-scaling is applied — the raw high-precision local amount is sent to the EVM contract as-is, which mints/redeems that raw number at its lower, fixed decimal count, over-crediting the recipient by orders of magnitude relative to what was actually escrowed/burned.

### Finding Description
- `register_token`/`update_token` validate the invariant once: [1](#0-0) 
- `Precisions` (the ERC-side decimals) is a fixed snapshot stored at registration/update time, never revisited: [2](#0-1) 
- But `send()` fetches the **local** asset's decimals fresh, at call time, from the live `Assets` metadata rather than any stored value: [3](#0-2) 
- The conversion helper masks any inversion of the invariant via `saturating_sub`, silently turning "scale down" into "no scaling": [4](#0-3) 

`pallet-assets`'s `Owner` of an asset can call `set_metadata` at any point after the bridge registers the token to change its `decimals`. This `Owner` is a normal (non-privileged, non-governance) account for any asset that is not itself administered by the runtime's bridge governance — the bridge's `CreateOrigin` only gates the *bridge's* `register_token`/`update_token` calls, not `pallet-assets::set_metadata`. Once `local_decimals > erc_decimals` (the stored, frozen value), `convert_to_erc20(amount, erc_decimals, local_decimals)` returns `amount * 10^0 == amount` unscaled, instead of dividing down as required. The message sent cross-chain therefore carries the raw, high-precision local amount, which the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract mints/releases at its own (lower) decimal count — over-crediting the recipient by `10^(local_decimals - erc_decimals)`.

### Impact Explanation
This is a direct false/duplicate-value fund-creation bug: a user burns/escrows a small local amount but the destination chain mints or releases an amount many orders of magnitude larger, directly violating the "move exactly once and only... the rightful... amount" invariant for bridged assets. It allows extraction of the entire custody/liquidity backing that asset on the destination chain, with no relayer, prover, or admin collusion required — only the ability to alter the local asset's own decimals metadata, which is a routine, unprivileged `pallet-assets` action available to any asset `Owner`.

### Likelihood Explanation
Requires the attacker to be (or become) the `Owner` of the specific local asset that bridge governance chose to register — plausible for any permissionlessly-created `pallet-assets` asset that governance later onboards without freezing its metadata. No relayer, prover, validator, or bridge-admin compromise is needed; `set_metadata` is a standard, publicly documented `pallet-assets` call gated only by asset ownership.

### Recommendation
Freeze the local asset's decimals at registration time by storing them (like `Precisions` does for the ERC side) rather than re-reading live metadata in `send`/`on_accept`/`on_timeout`, or re-validate `stored_erc_decimals >= live_local_decimals` on every transfer and reject if the invariant no longer holds. Alternatively, require registered assets to have `Owner` set to a bridge-controlled/frozen account so `set_metadata` cannot be called post-registration.

### Proof of Concept
1. Governance registers asset `X` (currently 6 local decimals) for `StateMachine::Evm(1)` with `ChainConfig { decimals: 6 }` — passes the `config.decimals >= local_decimals` check (6 >= 6). `Precisions[X, Evm(1)] = 6`.
2. `X`'s `pallet-assets` `Owner` (an ordinary account, e.g. attacker who created `X`) calls `pallet_assets::set_metadata` to change `X`'s decimals to `18`.
3. Attacker calls `HyperFungibleToken::send` with `asset_id = X`, `amount = 1 * 10^18` (i.e. "1 token" at the new 18-decimal precision), burning/escrowing that amount locally.
4. Inside `send`, `decimals` is fetched live as `18`; `erc_decimals` is still the frozen `6`. `convert_to_erc20(10^18, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, returning `10^18` unscaled instead of `10^18 / 10^12 = 10^6`.
5. The dispatched ISMP message carries `amount = 10^18`. The destination `HyperFungibleToken` EVM contract, configured at 6 decimals, mints/releases `10^18` raw units — i.e. `10^12` actual tokens — to the attacker's chosen recipient, versus the `1` token that should have been credited, draining the destination-side custody/supply.

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
