### Title
Scanner credits deposits to wallet outputs below the spendability/dust threshold, locking value the protocol can never economically recover - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The `Scanner` in `networks/bitcoin/src/wallet/mod.rs` matches received outputs solely on `script_pubkey` and never checks the output's value against the dust/spendability bound that the sending path enforces. Meanwhile `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` hard-gates on the `DUST` constant (546 sat): it refuses to *create* payments under `DUST` and silently converts sub-`DUST` change into additional fee. The result is a one-way ratchet analogous to the Comet `targetReserves` issue: an immutable threshold gates the value-recovery action, but nothing prevents value from accumulating *below* that threshold. Any unprivileged party can send a dust-valued P2TR output to a registered Serai address, and the scanner will report it as a spendable `ReceivedOutput` even though spending it costs more in fees than it is worth (or is outright rejected as uneconomical by the send path's own design assumptions).

### Finding Description
`Scanner::scan_transaction` iterates a transaction's outputs and pushes a `ReceivedOutput` whenever `output.script_pubkey` is in `self.scripts`, with no value check (mod.rs, `scan_transaction`, lines 199–214). `ReceivedOutput` is the type later fed as `inputs` to `SignableTransaction::new`.

The sending side enforces a strict economic bound in `send.rs`:

- `pub const DUST: u64 = 546;` (send.rs:32)
- Payments under `DUST` are rejected: `if *amount < DUST { Err(TransactionError::DustPayment)? }` (send.rs:165–169)
- Change is only materialized as an output if `value >= DUST`; otherwise the leftover is folded into the fee (send.rs:224–235)

So the wallet's own model is: outputs below `DUST` are not worth creating and are treated as fee/burn. Yet the scanning side has no symmetric check — it will happily report an output of value 1, 10, or 545 sats as a received, spendable UTXO.

A Taproot input costs ~57 vbytes to spend (36-byte outpoint + sequence + 66 WU witness, per the weight math in `calculate_weight_vbytes`, send.rs:62–127). At any nontrivial fee rate, an input worth less than ~`57 * fee_per_vbyte` satoshis is a net loss to include: its spend cost exceeds its value, and unlike Comet where the protocol could at least choose to HODL the collateral, a sub-cost input only ever subtracts value (it inflates `needed_fee` without contributing net funds). Once such an output is registered as received, the funds accounting treats it as available balance, but the `input_sat < payment_sat + needed_fee` check (send.rs:215–221) means these dust inputs can make a transaction *fail* `NotEnoughFunds` or, when included, burn value — they can never be profitably redeemed.

The asymmetry mirrors the bug class exactly: a hardcoded bound (`DUST`, like `targetReserves`) is enforced on the value-exit path while value is allowed to accumulate in a state where the bound makes it permanently unrecoverable/unprofitable.

### Impact Explanation
- **Funds reported received that are not spendable**: `scan_transaction`/`scan_block` produce `ReceivedOutput`s the protocol credits as balance, but which are uneconomical or impossible to spend under the wallet's own `DUST` policy. Depositors' funds (or refunds/change semantics built on this wallet) can be permanently locked in sub-dust UTXOs.
- **Persistent griefing**: an attacker can cheaply flood a registered Serai address with dust outputs. Each one is indexed as spendable input, and consuming them costs more in fees than they contribute — a forced value leak, or perpetual `NotEnoughFunds`/`NoOutputs` failures for plans built over them.
- Like the Comet finding, severity is bounded by the economics (each dust UTXO is small), but it is unbounded in count — an attacker can create arbitrarily many — and the "fix" requires exactly what the external report recommends: a consistent policy threshold enforced on both accumulation and disposition.

### Likelihood Explanation
- **Reachability**: fully reachable by any unprivileged party — they only need to send a Bitcoin transaction with a low-value output to a known Serai P2TR script (the script is public; `register_offset`/`Scanner::new` derive it from the public key). No validator status, no private state, no malformed encoding required.
- **Trigger condition**: any deposit output `< DUST` (546 sat), or more precisely `< ~57 * fee_per_vbyte`, sent to a registered script. This happens naturally for dust-sized deposits/refunds and deliberately via griefing.
- **Likelihood: Medium.** The class of input is trivially producible; impact per instance is small but cumulative and unrecoverable.

### Recommendation
Enforce the `DUST` bound symmetrically: in `Scanner::scan_transaction` (and by extension `scan_block`), skip outputs with `output.value.to_sat() < DUST` (or below a computed `input_cost * fee_rate` spendability floor), so that only economically spendable UTXOs are ever reported as `ReceivedOutput`. Alternatively/additionally, `SignableTransaction::new` could drop inputs whose value is below their marginal spend cost before computing `needed_fee`, rather than treating every scanned output as a contribution to `input_sat`. Whichever bound is chosen, it should be defined once (a single network-level spendability constant) and applied on both the receive and send paths to eliminate the accumulation-vs-disposition asymmetry.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs:199-214
// Scanner reports ANY matching output as spendable, regardless of value:
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),              // e.g. value = 1 sat
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}

// networks/bitcoin/src/wallet/send.rs:32, 165-169
// The send path defines 546 sats as the minimum economically sane output:
pub const DUST: u64 = 546;
for (_, amount) in payments {
  if *amount < DUST { Err(TransactionError::DustPayment)?; }
}
```
Concrete scenario: attacker sends a 10-sat P2TR output to a registered Serai script. `scan_transaction` returns it as a `ReceivedOutput`. A later `SignableTransaction::new` includes it in `input_sat`, but spending it adds ~57 vbytes of `needed_fee` for only 10 sats of value — net negative, and it can tip an otherwise-valid transaction into `NotEnoughFunds`. The value is permanently stranded, exactly the "protocol holds assets it cannot dispose of" shape of the Comet `targetReserves` finding.

Note on scope certainty: this analysis is confined to `networks/bitcoin/src/wallet/` per the in-scope rules; the higher-level scheduler's `N::DUST = 10_000` handling (in `processor/`, out of scope) amplifies the same issue by making even larger outputs uneconomical relative to Serai's own operating-cost accounting, but the in-scope wallet-layer mismatch above stands on its own.
