### Title
Unvalidated `Participant` indexes in the DKG blame path cause a panic, enabling remote denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

CVE-2021-40114 is a remote, unauthenticated denial of service: improperly handled attacker-controlled input (a series of ICMP packets) exhausts resources and forces a device reload. The Serai analog is a crafted input that drives the victim process into an unconditional panic (Rust `HashMap` index on a missing key), crashing/aborting the handler evaluating a blame claim. An unprivileged party can reach this by submitting a blame evaluation request naming a `Participant` who was never registered.

### Finding Description

`Decryption::decrypt_with_proof` indexes the registration map with an unchecked `decryptor` argument before any bounds check: [1](#0-0) 

`self.enc_keys` only contains entries for participants previously registered via `Decryption::register` (`encryption.rs:356-361`), i.e. participants `1..=n` whose commitment messages were supplied. `decryptor` is the `recipient: Participant` passed by the caller to `BlameMachine::blame` / `AdditionalBlameMachine::blame`: [2](#0-1) 

`blame` forwards `sender`/`recipient` into `blame_internal` with no validation that they belong to the protocol's participant set: [3](#0-2) 

A second identical panic exists at `self.commitments[&sender]` in `blame_internal` (`lib.rs:599`), reached whenever `sender` indexes a participant whose commitments were never inserted into the `commitments` map built in `AdditionalBlameMachine::new` (`lib.rs:656-659`) or `verify_r1` (`lib.rs:313-331`).

Root cause: `Participant` is an unconstrained non-zero `u16` (`crypto/dkg/src/lib.rs:29-34`); any value `> n` (or any participant whose message was absent) is a valid `Participant` but an absent map key. `HashMap`'s `Index` impl panics on missing keys, so the indexing expressions `self.enc_keys[&decryptor]` and `self.commitments[&sender]` are unconditional panics on attacker-chosen inputs.

### Impact Explanation

An unauthenticated/unprivileged party who can get a node to evaluate a blame claim — a public input path consisting of attacker-supplied `(sender, recipient, msg, proof)` bytes fed to `EncryptedMessage::read`, `EncryptionKeyProof::read`, and the `blame` API — can force `panic!` in the evaluating process. This mirrors the CVE exactly: improper handling of attacker-controlled input causes a crash/reload-equivalent DoS. If blame evaluation runs inside the coordinator/validator process (the natural deployment for `AdditionalBlameMachine::new`, which exists precisely so non-participants can arbitrate blame), a single crafted message kills or aborts that evaluation, potentially halting DKG completion handling. Severity: High (pure DoS, remotely triggerable, no secrets required).

### Likelihood Explanation

Triggering requires only:
- A `sender`/`recipient` argument set containing a `Participant` not present in `enc_keys`/`commitments` (e.g., `Participant::new(n + 1)` or an index whose registration was skipped).
- A `proof` value of `Some(...)` for the `enc_keys` panic (any `EncryptionKeyProof` — the panic at line 388 occurs inside `decrypt_with_proof` before the proof's validity matters; note `self.enc_keys[&decryptor]` is evaluated as an argument to `proof.dleq.verify`, so it indexes immediately).

No threshold collusion, valid signature, or valid share is needed — `msg.pop.verify` runs first (`encryption.rs:374-379`) but an attacker who is a legitimate participant can produce a valid PoP trivially, and even an invalid PoP path still reaches `commitments[&sender]` crashes elsewhere. Likelihood: high for any deployment exposing blame arbitration over the network.

### Recommendation

Replace indexing with fallible lookups and return a blame/fault verdict or error instead of panicking:

```rust
// crypto/dkg/pedpop/src/encryption.rs, in decrypt_with_proof
let Some(dec_key) = self.enc_keys.get(&decryptor) else {
  return Err(DecryptionError::InvalidProof); // or a new UnknownParticipant variant
};
proof.dleq.verify(&mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key], &[*dec_key, *proof.key])...

// crypto/dkg/pedpop/src/lib.rs, in blame_internal
let Some(commitments) = self.commitments.get(&sender) else {
  return sender; // unprovable/unknown sender — fault lies with the accuser's claim
};
```

Additionally, validate `sender`/`recipient` against `params.all_participant_indexes()` (or the registered key set) at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame` before any map access.

### Proof of Concept

Conceptual, against the library API:

```rust
// Assume a DKG with ThresholdParams { t: 2, n: 3 } completed such that an
// AdditionalBlameMachine was constructed via:
//   AdditionalBlameMachine::new(context, 3, commitment_msgs)
// enc_keys and commitments now hold keys {1,2,3} only.

// Attacker supplies a blame claim naming a participant outside 1..=3.
let bogus_recipient = Participant::new(4).unwrap(); // valid Participant, never registered
let real_sender = Participant::new(1).unwrap();
let any_msg: EncryptedMessage<C, SecretShare<C::F>> = EncryptedMessage::read(&mut bytes, params)?;
let any_proof = Some(EncryptionKeyProof::read(&mut proof_bytes)?);

// Inside blame_internal -> decrypt_with_proof:
//   `self.enc_keys[&decryptor]` with decryptor == bogus_recipient
// panics: "no entry found for key" -> process abort, DoS.
machine.blame(real_sender, bogus_recipient, any_msg, any_proof);
```

For the `sender` variant (no proof needed past the share-decoding path): pass `sender = Participant::new(4)` with a `recipient` that is registered and a `Some(proof)` whose DLEq verifies; `decrypt_with_proof` succeeds, `C::F::from_repr` yields a scalar, and `self.commitments[&sender]` at `lib.rs:599` panics identically.
