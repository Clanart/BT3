## Analysis

The Bisq report describes a trade-protocol vulnerability where a verification step was bypassed, allowing attackers to move (drain) escrowed funds without holding the proper authorization. The closest reachable analog in sei-chain is in the `CW721ERC721Pointer` contract, which wraps a CosmWasm CW721 NFT contract as an ERC721 token accessible from the EVM.

`CW721ERC721Pointer.transferFrom` only checks that the `from` argument equals the current owner returned from the CW721 contract — it never verifies that `msg.sender` is the owner, an approved spender, or an approved operator: [1](#0-0) 

This is in stark contrast to the sibling `CW1155ERC1155Pointer.safeTransferFrom`, which does perform the caller-authorization check: [2](#0-1) 

Because `transferFrom` is declared `public override` in the pointer contract, it fully replaces OpenZeppelin's base `ERC721.transferFrom` (which normally enforces `_isAuthorized(owner, spender, tokenId)`), and this pointer's `safeTransferFrom` (inherited from the base `ERC721`) internally calls this same overridden `transferFrom`, so the missing check propagates to both entry points. `approve` and `setApprovalForAll` are similarly unguarded (they forward directly to the CW721 `_execute` without checking that `msg.sender` owns/controls the token), but `transferFrom` is the most directly fund-impacting path.

### Title
Missing caller-authorization check in `CW721ERC721Pointer.transferFrom` allows unauthorized NFT transfer - (File: `contracts/src/CW721ERC721Pointer.sol`)

### Summary
`CW721ERC721Pointer.transferFrom(from, to, tokenId)` verifies only that `from` is the token's current owner (via a `WasmdPrecompile.query` round trip), but never verifies that `msg.sender` is that owner, an approved address, or an approved operator, before dispatching a `transfer_nft` CosmWasm execute message on behalf of `from`.

### Finding Description
In OpenZeppelin's standard `ERC721`, `transferFrom` calls `_isAuthorized(owner, msg.sender, tokenId)` to ensure the caller is either the owner, has been individually `approve`d for the token, or is an approved operator via `setApprovalForAll`. The `CW721ERC721Pointer` contract overrides `transferFrom` entirely and drops this authorization check: [1](#0-0) 

The function only requires `from == ownerOf(tokenId)`, which is trivially true for the legitimate owner regardless of who calls the function. Since `_execute` dispatches the `transfer_nft` CosmWasm message to the underlying CW721 contract using the pointer contract's own execute-context, the CW721 contract accepts the transfer (the pointer is generally the one authorized principal from the CW721 side), and the NFT moves from `from` to any `to` the caller supplies — with the caller being any unprivileged EVM address, not the owner or an approved party. Because `safeTransferFrom` on the base `ERC721` contract is not overridden here and internally invokes this same `transferFrom`, the vulnerability is reachable through both `transferFrom` and `safeTransferFrom`.

This matches the Bisq bug class of "bypass verification" that lets an unauthorized party drain assets that should require prior authorization/ownership — here applied to a CW721-backed pointer NFT reachable by any EVM transaction sender.

### Impact Explanation
Any unprivileged EVM account can steal any NFT wrapped by a `CW721ERC721Pointer` from any other holder, without owning the token, having been `approve`d, or being an approved operator. This is an unauthorized transfer via a pointer contract — a fund/asset-loss condition explicitly in the accepted impact list ("unauthorized transfer via precompile or pointer"). This is at least Medium/High severity since it enables direct asset theft with no privileged prerequisites.

### Likelihood Explanation
Trivially reachable: an attacker only needs to know a valid `tokenId` and its current owner's address (both discoverable via public `ownerOf`/query calls) and call `transferFrom(owner, attacker, tokenId)` directly against the pointer contract. No special permissions, no prior approval, and no unusual gas/complexity are required.

### Recommendation
Add an authorization check in `transferFrom` (and mirror it for any other overridden transfer-adjacent method) analogous to what `CW1155ERC1155Pointer.safeTransferFrom` already does:
```solidity
require(
    msg.sender == from || getApproved(tokenId) == msg.sender || isApprovedForAll(from, msg.sender),
    "ERC721: caller is not token owner or approved"
);
```
placed before dispatching the `transfer_nft` CosmWasm message.

### Proof of Concept
1. Deploy/obtain a `CW721ERC721Pointer` for an existing CW721 collection; `victim` owns `tokenId = 5`.
2. From an unrelated EVM account `attacker` (no approval, not the owner), call:
   `pointer.transferFrom(victimEvmAddress, attackerEvmAddress, 5)`.
3. The `require(from == ownerOf(tokenId), ...)` check passes because `from` is correctly the current owner; there is no check that `msg.sender == attacker` is authorized.
4. The pointer contract executes `transfer_nft` against the CW721 contract, moving token `5` from `victim` to `attacker` with no consent from `victim`. [1](#0-0)

```text
    function transferFrom(address from, address to, uint256 tokenId) public override {
        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }
```

```text
    function safeTransferFrom(
        address from,
        address to,
        uint256 id,
        uint256 amount,
        bytes memory data
    ) public override {
        require(to != address(0), "ERC1155: transfer to the zero address");
        require(balanceOf(from, id) >= amount, "ERC1155: insufficient balance for transfer");
        require(
            msg.sender == from || isApprovedForAll(from, msg.sender),
            "ERC1155: caller is not approved to transfer"
        );
```
