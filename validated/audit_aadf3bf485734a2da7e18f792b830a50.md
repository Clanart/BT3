### Title
CLVM canonical-serialization checker reads past end of buffer on crafted atom length prefix, causing an unhandled crash on spend-bundle admission - ([File: chia/full_node/mempool_manager.py])

### Summary
The Eclipse OpenJ9 bug (CVE-2019-10245) is a bytecode *verifier* flaw: the verifier fails to confirm that an instruction stays within the bounds of the method's bytecode array before executing it, so a crafted method can run past the array and crash the VM. Chia's mempool has a directly analogous "verifier": `is_atom_canonical()`/`is_clvm_canonical()` parse a CLVM-serialized buffer's length-prefix header and then index into the buffer using the *decoded* atom length, without ever checking that the decoded length actually fits inside the buffer.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` decodes a variable-length atom-length prefix (1–6 bytes) purely from the header bits, then reads `prefix_len` more bytes by repeatedly indexing `clvm_buffer[offset]` and returns `atom_len` — a value derived solely from the encoded header, never validated against the remaining buffer length: [1](#0-0) 

`is_clvm_canonical()` then advances its cursor by that unchecked `atom_len` (`offset += atom_len`) and, on the next loop iteration, indexes `clvm_buffer[offset]` again: [2](#0-1) 

If an attacker crafts a puzzle reveal or solution whose length-prefix header claims an atom length that extends past the actual bytes present (e.g., a 6-byte prefix encoding a huge length while the buffer is short), `offset` will exceed `len(clvm_buffer)`, and the next `clvm_buffer[offset]` read raises an uncaught `IndexError` in Python. This is functionally the "verifier allows execution past the end of the array" defect from the CVE, transplanted into Chia's own hand-rolled CLVM-serialization bounds checker.

This function is invoked unconditionally, for *every* coin spend in a spend bundle, directly on attacker-supplied bytes, during mempool admission: [3](#0-2) 

`validate_spend_bundle()` is called from `add_spend_bundle()` with no surrounding `try/except`: [4](#0-3) 

so an `IndexError` raised deep inside `is_clvm_canonical()`/`is_atom_canonical()` propagates uncaught out of `add_spend_bundle()`.

### Impact Explanation
A single submitted spend bundle (reachable by any unprivileged wallet/RPC caller pushing a transaction) can trigger an unhandled `IndexError` inside the mempool's spend-bundle admission path. Depending on how the calling task/coroutine is supervised, this can manifest as a crash of the mempool-processing task or an unexpected exception surfacing through the transaction-submission RPC, effectively halting normal processing of that transaction path. This matches the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Reaching this code requires only constructing a `CoinSpend` whose `puzzle_reveal` or `solution` bytes contain a non-canonical atom-length prefix that overstates the atom's length relative to the actual buffer size (e.g. crafted 0xC0–0xFC prefix bytes). No signature validity or special permissions are needed to reach `is_clvm_canonical()`, since it runs before/alongside conflict and cost checks in `validate_spend_bundle()`. The existing tests only exercise non-canonical-but-in-bounds cases (e.g. `test_clvm_not_canonical`), not truncated/overstated-length buffers, so this boundary condition does not appear to be covered.

### Recommendation
In `is_atom_canonical()`, validate that `offset + prefix_len < len(clvm_buffer)` before reading each prefix byte, and validate that `offset + atom_len <= len(clvm_buffer)` before returning, treating an out-of-range length as "not canonical" (return `False`) instead of allowing the caller to advance past the buffer. Likewise, `is_clvm_canonical()` should bound-check `offset` before every `clvm_buffer[offset]` access and fail closed (return `False`) rather than raise. As defense in depth, wrap the `is_clvm_canonical()` calls in `validate_spend_bundle()` (or the exception handling in `add_spend_bundle()`) so that any unexpected exception from this bounds parsing is converted into a rejection (`Err.INVALID_COIN_SOLUTION`) rather than propagating as an unhandled exception.

### Proof of Concept
Construct a `CoinSpend` whose `solution` bytes are a single atom with a long-form length prefix claiming far more payload bytes than are actually present, e.g. (conceptually, mirroring `serialized_atom_overflow()` used in existing deserialization tests) a buffer such as `bytes([0xFC, 0x00, 0x00, 0x00, 0x00, 0x7F])` — a 6-byte prefix (`0xFC` + 5 length bytes) declaring a very large atom length, immediately followed by end-of-buffer. Submit a `SpendBundle` containing this as the `solution` (or `puzzle_reveal`) via the normal RPC push-tx path. `MempoolManager.add_spend_bundle()` → `validate_spend_bundle()` → `is_clvm_canonical(bytes(coin_spend.solution))` → `is_atom_canonical()` will index past the end of the short buffer and raise an uncaught `IndexError`, which is not caught anywhere in this call chain.

**Note on completeness:** I was not able to trace, within the indexed portion of this repository, whether an outer layer (e.g. the full-node RPC handler or the mempool worker's task wrapper) wraps `add_spend_bundle()` calls in a broad `except Exception`. If such a broad catch exists at that outer layer, the practical impact would be reduced to a failed/rejected transaction rather than a full processing halt — this should be verified against the actual full-node RPC/service code (outside what was retrieved here) before treating this as confirmed high-severity.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
