## Title
Git's Built-In Submodule Protocol Protection Is Explicitly Disabled During Clone, Enabling Malicious Repo `.gitmodules` Payloads to Escape the Sandbox - (File: `app/src/lib/git/clone.ts`)

## Summary
The OtterSec report's broken invariant is: **untrusted, attacker-supplied instruction data is forwarded into a privileged downstream operation without validation, and the safety check that should catch the abuse never actually fires because the guard condition degenerates trivially.** The GitHub Desktop analog of this pattern is in the `clone()` function: when cloning a repository, Desktop explicitly disables Git's own built-in protection against malicious submodule configurations, while simultaneously passing `--recursive` so that submodules (whose URLs/settings are fully attacker-controlled content inside the cloned repo) are processed automatically.

## Finding Description
`clone()` builds the environment for the `git clone` child process and explicitly sets: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced (as part of the fix for the class of vulnerabilities tracked as CVE-2022-39253, where a malicious repository's `.gitmodules` file could point a submodule at a `file://` (or other dangerous transport) URL and get it cloned automatically during a recursive clone, allowing local file disclosure or, with helper protocols, worse). Upstream Git's protections (`protocol.file.allow`, path/URL sanity checks) are gated behind this "clone protection" mechanism precisely to stop `.gitmodules` content — which is 100% attacker-controlled in a cloned/fetched repository — from being trusted as safe instruction data for a CPI-style external process invocation (the recursive `git submodule` clone).

By setting `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally for every `clone()` call, Desktop turns off exactly the guard that upstream Git added for this bug class, and this is compounded by `updateSubmodulesAfterOperation()` optionally re-enabling `protocol.file.allow=always` on top of it: [2](#0-1) 

This mirrors the OtterSec pattern precisely: the "instruction data" here is the `.gitmodules` submodule URL/config coming from an untrusted, attacker-controlled repository; it is passed straight through to a privileged sub-operation (submodule clone) without app-level validation; and the one guard that exists (Git's own clone protection) is disabled by the caller, so it can never trigger — just like the `SlippageError` check in the report that could never fail because `from_usd_value` was forced to `0`.

## Impact Explanation
An attacker who controls a repository that a Desktop user clones or fetches (public repo, malicious fork, `git clone` URL shared via link, etc.) can craft a `.gitmodules` file with a submodule URL using a dangerous transport (e.g. `file://` pointing at arbitrary local paths, or other Git transport helpers). Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` and the clone is `--recursive`, Git will attempt to process that submodule without the safety checks it would normally apply, potentially reading/copying files from outside the cloned repository's directory into the working tree (information disclosure / file read outside the repo) — matching the "Impact" criteria of file write/read outside the repo from an attacker-controlled cloned/fetched repository.

## Likelihood Explanation
This is not a theoretical corner case — it fires on the ordinary "Clone repository" flow, which is one of the most common Desktop actions, with no additional user interaction beyond cloning an attacker-supplied URL/fork. No local access, admin rights, or prior compromise is required; the only actor input needed is content inside the cloned repository (`.gitmodules`), which is exactly the kind of untrusted data this report class targets.

## Recommendation
- Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally in `clone()`; only disable Git's built-in submodule protection for trusted, first-party operations (e.g., Desktop's own tutorial repo creation) where the content is known-safe, not for arbitrary user-supplied clone URLs.
- Validate/sanitize `.gitmodules` submodule URLs before allowing recursive submodule processing, rejecting `file://`, `ext::`, and other non-`https`/`ssh` transports by default, consistent with modern Git's default posture.
- Audit all call sites of `updateSubmodulesAfterOperation`'s `allowFileProtocol` flag to ensure it is never `true` for repositories/content the user did not explicitly and knowingly trust.

## Proof of Concept
1. Attacker creates a public repository containing a `.gitmodules` file with an entry such as:
   ```
   [submodule "x"]
     path = x
     url = file:///Users/victim/.ssh
   ```
2. Victim clones the repository via GitHub Desktop ("Clone repository" from URL, or opening a shared clone link).
3. Desktop invokes `clone()` with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and `--recursive` [1](#0-0) , bypassing the guard Git would otherwise use to refuse the `file://` submodule.
4. The submodule contents (potentially sensitive local files) get cloned into the working directory `x/`, where they become visible/readable inside the repository — a read outside the intended repo boundary that a properly-enabled clone protection would have blocked.

*Note: I could not fully trace every call site that sets `allowFileProtocol: true` for `updateSubmodulesAfterOperation` due to the final-iteration limit reached during investigation; confirming whether any additional caller (beyond `clone.ts`'s unconditional environment override) explicitly re-enables `protocol.file.allow=always` for user-initiated operations would require further exploration with a Devin session that has full repository access.*
