I found a genuine analog to the report's bug class: an incomplete action-discriminant handler in `HostManager.sol` that silently no-ops instead of rejecting unrecognized instructions — the same "missing instruction handling" pattern the report describes for `BasePongHandler`.

### Title
`HostManager.onAccept` silently accepts unrecognized `OnAcceptActions` discriminants instead of reverting - (File: `evm/src/core/HostManager.sol`)

### Summary
`HostManager.onAccept()` decodes a governance action byte and dispatches on only two of the enum's members (`Withdraw`, `SetHostParam`) with an `if/else if` chain and no trailing `else revert`. Compare this to `BandwidthManager.sol`'s equivalent handler, which correctly ends with `else revert UnauthorizedAction()`.

### Finding Description
`HostManager.onAccept` at [1](#0-0)  is:
```solidity
function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
    PostRequest calldata request = incoming.request;
    if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

    OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
    if (action == OnAcceptActions.Withdraw) {
        WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
        IHostManager(_params.host).withdraw(withdrawParams);
    } else if (action == OnAcceptActions.SetHostParam) {
        HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
        IHostManager(_params.host).updateHostParams(hostParams);
    }
}
```
There is no `else revert` branch. The sibling `BandwidthManager.sol::onAccept` at [2](#0-1)  handles this correctly with an explicit `else revert UnauthorizedAction();` for any discriminant outside `{SetTiers, Withdraw}`. `HostManager` lacks that final guard.

Because ISMP delivers `onAccept` calls only after full state/consensus proof verification and a message-receipt check (this is a legitimately verified governance message, not attacker-controlled body content), the immediate exploitability is limited: an attacker cannot forge the `request.source` or the message body without compromising consensus. However, this still matches the report's underlying invariant break — an unhandled instruction is silently swallowed rather than explicitly rejected, which is a "silent failure" class bug per the report's description of `DELETE_UINT256`/unhandled-instruction handling.

### Impact Explanation
If `Solidity`'s `enum` cast `OnAcceptActions(uint8(request.body[0]))` ever receives a value outside the declared enum range (0 or 1), Solidity itself reverts on the invalid enum conversion (panic 0x21), so out-of-range values are actually caught by the language runtime, not by application logic. The genuine gap is forward-compatibility / silent no-op risk: if the enum is ever extended (a new action added on the Hyperbridge/pallet-host-executive side without updating this contract in lockstep), a governance message with the new discriminant would decode successfully into the enum but silently no-op in `HostManager`, discarding a legitimate protocol/governance instruction (e.g., a withdrawal or parameter update) without any error, receipt, or event — a "message accepted, nothing done" state divergence between Hyperbridge's dispatch-side bookkeeping and the destination-chain's actual effect. This is a lower-severity, harder-to-trigger analog than the original report (it requires an enum-extension migration bug, not an unprivileged attacker path), so it does not cleanly satisfy the "unprivileged attacker" bar in the impact gate.

### Likelihood Explanation
Low under current conditions: the enum has only two members and Solidity's runtime enum-decode revert already prevents undefined-value execution today. The bug would only manifest on a future upgrade that adds an `OnAcceptActions` variant to the pallet/dispatch side without a coordinated update to `HostManager.sol`, which is an operational/deployment-migration risk rather than an exploitable on-chain path today.

### Recommendation
Add an explicit `else revert UnauthorizedAction();` (mirroring `BandwidthManager.sol`) to `HostManager.onAccept` so any future/unexpected discriminant fails loudly instead of silently no-op'ing, consistent with the "no non-implemented instructions swallowed" remediation direction in the report.

### Proof of Concept
Not independently exploitable by an unprivileged actor today because Solidity's enum-cast revert already blocks out-of-range discriminants, and any valid discriminant is fully handled by the current two-branch chain. The only path to the silent-no-op is a coordinated future protocol upgrade that adds a third `OnAcceptActions` variant on the Hyperbridge dispatch side while `HostManager.sol` is not redeployed with matching logic — at that point, a legitimately delivered governance message for the new action would pass all authentication checks and simply do nothing, with no revert or event, similarly to `_configPongHandler`/`_registryPongHandler` silently ignoring `ADDRESS`/`INCREMENT_UINT256`/etc. in the original report.
