Found a direct analog: the `distribution` precompile's `rewards()` method is the one state-changing/view dispatch case that **omits** the `pcommon.ValidateNonPayable(value)` guard that every other view method in that same `Execute` switch enforces, and it also never calls `pcommon.HandlePaymentUsei` to refund the transferred value (unlike `SetWithdrawAddressMethod`, `WithdrawDelegationRewardsMethod`, etc. which explicitly consume `value` for payment). Since Sei's EVM precompile dispatch performs a standard value transfer into the precompile's account balance as part of the `CALL` before `Execute` runs (the same mechanism `HandlePaymentUsei` exists to reverse for legitimate payable methods), a `msg.value`-bearing call to `rewards()` succeeds and permanently strands the sent SEI/wei at the distribution precompile's associated account, with no code path returning it to the caller.

### Title
Value sent to `distribution` precompile's `rewards()` view method is permanently stranded due to missing non-payable/refund guard - ([File: precompiles/distribution/distribution.go])

### Summary
The `distribution` precompile's `Execute` dispatcher enforces `pcommon.ValidateNonPayable(value)` on several view methods (`WithdrawValidatorCommissionMethod` in later versions) and performs explicit payment handling via `pcommon.HandlePaymentUsei` for real payable methods, but `RewardsMethod` is dispatched directly to `p.rewards(ctx, method, args)` with no non-payable check and no consumption/refund of `value`. [1](#0-0) [2](#0-1) 

### Finding Description
Every value-bearing EVM `CALL` to a precompile address transfers `msg.value` into that precompile's account balance in the StateDB as part of normal EVM semantics, before the precompile's `Execute`/`Run` logic ever inspects `value`. This is precisely why Sei maintains a `payablePrecompiles` allow-list and why legitimate payable precompile methods (e.g. `wasmd.execute`, `staking.delegate`, `gov.deposit`) explicitly call `pcommon.HandlePaymentUsei` to refund the transferred amount back to the payer's SEI account as part of executing the intended payment logic, and why every other non-payable method calls `pcommon.ValidateNonPayable(value)` to reject a nonzero value up front, causing the whole call (and the implicit transfer) to revert. [3](#0-2) [4](#0-3) [5](#0-4) 

`RewardsMethod` breaks this pattern: it neither rejects nor consumes `value`, so a call with nonzero `msg.value` is accepted, the implicit EVM value transfer to the distribution precompile's account is never reverted (no `ValidateNonPayable`) and never refunded (no `HandlePaymentUsei`/similar logic in `rewards()`). [1](#0-0) 

This is explicitly confirmed by the project's own integration-test documentation, which calls out `rewards()` as "the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)". [6](#0-5) 

This mirrors the referenced Notional bug class exactly: a function reachable with attacker/user-supplied `value` that has no logical use for that value and no guard against it, resulting in silent, permanent loss of the sent funds.

### Impact Explanation
Any EVM transaction sender who calls `rewards(address)` on the distribution precompile with a nonzero `value` loses that value permanently — it becomes stuck in the precompile's associated account with no withdrawal path, since the precompile's own code never treats it as a payment and there is no user-facing function to reclaim funds sent to a precompile address. This is a direct, permanent loss-of-funds bug for any wallet, dApp frontend, or contract that (mistakenly or via a crafted transaction) attaches value to this call.

### Likelihood Explanation
Reachable by any public JSON-RPC client or EVM transaction sender; no privileged role, and no multi-step setup is required — a single `eth_sendRawTransaction`/`eth_call` targeting the distribution precompile's `rewards` selector with nonzero `value` triggers it. The other view/withdraw methods in the same file correctly guard against this, making `rewards()` an isolated, easily-triggered omission.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check at the start of `p.rewards(...)` (or in the `RewardsMethod` case of `Execute`), consistent with every other view method's guard in the same dispatcher, so that value-bearing calls to `rewards()` revert instead of stranding funds.

### Proof of Concept
1. Call the distribution precompile's `rewards(delegatorAddr)` method via `eth_sendRawTransaction` with `value` set to a nonzero amount (e.g. 1 SEI equivalent in wei).
2. The transaction succeeds and returns reward data; the value is transferred from the sender to the precompile's account as part of standard EVM `CALL` semantics.
3. Inspect the precompile's SEI balance — the funds remain there with no code path in `distribution.go`'s `rewards()` (or elsewhere) to return them to the sender.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
