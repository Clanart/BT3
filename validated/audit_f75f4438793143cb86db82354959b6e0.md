### Title
Unchecked type assertions on arbitrary CW contract responses in pointer-creation precompiles cause a Go runtime panic reachable by any EVM transaction sender - (File: precompiles/pointer/pointer.go)

### Summary
The `pointer` precompile's `AddCW20`, `AddCW721`, and `AddCW1155` methods let any EVM caller pass an arbitrary bech32 address (`cwAddr := args[0].(string)`) as the contract to create a pointer for, without verifying that it actually implements the CW20/CW721/CW1155 interface. This mirrors the reported Olympus bug pattern of assuming an untrusted address conforms to a specific interface (`ERC4626(asset_)`).

### Finding Description
In `AddCW20`, the precompile queries the caller-supplied wasm contract for `token_info` and unmarshals the JSON response into a generic `map[string]interface{}`, then performs unchecked (non comma-ok) type assertions: [1](#0-0) 
The same unchecked pattern exists in `AddCW721` (`contract_info` query) and `AddCW1155`: [2](#0-1) [3](#0-2) 

There is no check that `formattedRes["name"]` or `formattedRes["symbol"]` exist or are strings. Since `cwAddress` is fully attacker-controlled and only needs to be a valid bech32 address that responds successfully to a `token_info`/`contract_info` query (any wasm contract the attacker deploys and controls can do this, returning `"name": 123` or omitting the field entirely so the map lookup yields `nil`), the single-value type assertion `.( string)` will panic on a type mismatch. This same interface-trust pattern recurs across every legacy version of this precompile (`v552` through `v67`), all reachable via the exact same untrusted, attacker-supplied `cwAddr` argument. [4](#0-3) 

### Impact Explanation
A malicious, unprivileged EVM transaction sender can deploy a trivial CW contract that answers `token_info`/`contract_info` queries with a non-string `name`/`symbol` field (or omits them), then call `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` on the pointer precompile (`0x000000000000000000000000000000000000100b`) pointing at that contract. This triggers an unrecovered Go type-assertion panic inside precompile execution during EVM message processing. I was not able to conclusively verify within this investigation whether a panic originating from this specific call path is caught by a wrapping `recover()` in the EVM ante/message-processing pipeline (`x/evm/ante/preprocess.go`, `x/evm/keeper/msg_server.go`) versus propagating unrecovered to a node-crashing panic; this is a limitation of static analysis and would need to be confirmed by tracing the exact call stack from `StateTransition`/precompile dispatch through to these recover sites, or by reproducing the panic on a local node.

### Likelihood Explanation
High reachability: any address, without special privileges, can deploy a CW contract and call the pointer precompile with it as the target — this requires only a single wasm contract deployment plus one EVM transaction, both of which are available to any public RPC client.

### Recommendation
Replace the unchecked type assertions with the comma-ok form and return an explicit error (rather than panicking) when `name`/`symbol` are missing or not strings, e.g.:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw contract %s does not conform to expected token metadata interface", cwAddr)
}
```
Apply this fix uniformly to `AddCW20`, `AddCW721`, and `AddCW1155` in `precompiles/pointer/pointer.go`, and consider back-porting the same defensive check to the legacy pointer precompile versions (`v552`–`v67`) to eliminate the type-assumption panic surface.

### Proof of Concept
1. Deploy a minimal CoreWasm contract whose `token_info` query handler returns `{"name": 12345, "symbol": "X", "decimals": 6, "total_supply": "0"}` (i.e., `name` is a JSON number, not a string).
2. From any EVM account, call `addCW20Pointer(cwAddr)` on the pointer precompile at `0x000000000000000000000000000000000000100b`, passing the bech32 address of the contract from step 1.
3. Execution reaches `formattedRes["name"].(string)` in `AddCW20`, which panics because the underlying value is `float64`, not `string`. [5](#0-4)
