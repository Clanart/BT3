## Title
GET-timeout dispatch loop re-validates `request_commitment` but not `response_receipt`, allowing a reentrant response delivery mid-batch to be followed by a timeout for the same request - (File: `modules/ismp/core/src/handlers/timeout.rs`)

### Summary
`handlers::timeout::handle` for `TimeoutMessage::Get` performs two passes over the batch. The first (validation) pass rejects any request that already has a `response_receipt` [1](#0-0) . The second (dispatch) pass re-checks only `request_commitment` presence before deleting it and invoking `on_timeout` — it does **not** re-check `response_receipt` [2](#0-1) . Because `handlers::response::handle` stores the `response_receipt` for a request without deleting that request's `request_commitment` [3](#0-2) , a request's `request_commitment` remains present even after it has received a valid response.

### Finding Description
In a batch `TimeoutMessage::Get { requests: [A, B] }`:
1. The validation pass confirms both `A` and `B` have no `response_receipt`, have `request_commitment`, and are timed out.
2. The dispatch pass processes `A` first: it deletes `A`'s `request_commitment` and calls `router.module_for_id(A.from)?.on_timeout(A)`.
3. If the module resolved by `A.from` (an ordinary, unprivileged `IsmpModule`/app that dispatched the original GET request) reenters the host during `on_timeout(A)` — e.g., by invoking the response-handling path for `B` with a legitimate state proof (an unprivileged, permissionless call) — then `handlers::response::handle` for `B` succeeds: `B.request_commitment` still exists (only checked, never deleted by the response path), `B.response_receipt` is still absent, so the receipt gets stored and `on_response(B)` is invoked.
4. Control returns to the outer dispatch loop, which now processes `B`. It re-checks only `host.request_commitment(B)` — which is still present because the response path never deletes it — so the guard comment's intended protection ("a prior on_timeout ... could have caused the commitment ... to be removed ... we must not invoke on_timeout for a request that is no longer pending") does not fire. `B`'s commitment is deleted and `on_timeout(B)` is invoked even though `B` already has a `response_receipt` and already had `on_response` invoked.

This breaks the invariant "a request cannot both receive a response and be timed out," which the top-level validation pass and the existing regression tests (`should_reject_get_timeout_with_existing_response`, `should_reject_get_timeout_batch_when_any_request_has_response`) only verify for receipts that exist *before* the message is submitted, not for receipts created *during* the same message's dispatch loop via reentrancy [4](#0-3) .

### Impact Explanation
`host.on_request_timeout(&request, meta)` is invoked for `B` after it already had a successful `on_response` delivery, which can trigger double logic execution against the app module for a single commitment (once via `on_response`, once via `on_timeout`), and duplicate accounting on the host side (e.g., relayer-fee refund paths keyed by the same commitment metadata being triggered post-response). This directly matches the required impact categories: broken timeout/refund accounting and double settlement for a single commitment.

### Likelihood Explanation
Exploitation requires: (a) an app module registered under `from` that can be influenced or controlled by the attacker to reenter the host during its `on_timeout` callback, and (b) a legitimate response proof for a second in-flight request in the same batch to be available/deliverable during that reentrant call. This is plausible for any unprivileged, attacker-authored `IsmpModule`/application contract that dispatches its own GET requests and implements a callback that calls back into message handling — no privileged or "malicious relayer/node" assumption is required, only a designed reentrant callback in an ordinary app module, which is within the review's unprivileged-call/callback scope.

### Recommendation
In the dispatch loop of `handlers/timeout.rs::handle` (`TimeoutMessage::Get` branch), re-check `host.response_receipt(&response)` immediately before deleting the commitment and invoking `on_timeout`, mirroring the re-check already done for `request_commitment` and for `response_receipt` in `handlers/response.rs`'s dispatch loop. Additionally, consider having the response path delete/consume `request_commitment` at receipt-store time, so mid-batch reentrancy cannot leave a commitment "alive" once a response is stored.

### Proof of Concept
Extend `should_reject_get_timeout_batch_when_any_request_has_response` (or `should_reject_get_timeout_with_existing_response`) in `modules/pallets/testsuite/src/tests/pallet_ismp.rs` to:
1. Dispatch two GET requests, `A` and `B`, from a mock `IsmpModule` registered under `A.from`/`B.from`.
2. Wire the mock module's `on_timeout` implementation so that when invoked for `A`, it re-enters `handle_incoming_message` with a `Message::Response` for `B` carrying a valid state proof (using the existing `store_response_receipt`/mock proof machinery from `get_response_already_received_check`).
3. Submit `Message::Timeout(TimeoutMessage::Get { requests: vec![A, B] })`.
4. Assert that after processing, `B` has both `response_receipt(B).is_some()` and `on_timeout(B)` was invoked (or that `request_commitment(B)` was deleted a second time / `on_request_timeout` ran) — demonstrating the invariant "a request cannot both receive a response and be timed out" is violated [5](#0-4) .

fn should_reject_get_timeout_batch_when_any_request_has_response() {

						context: Default::default(),

						timeout: 1000,

					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)

				ismp::router::GetRequest {
					source: host.host_state_machine(),
					dest: StateMachine::Evm(1),
					nonce: i,
					from: vec![0u8; 32],
					keys: vec![vec![1u8; 32], vec![1u8; 32]],
					height: 2,
					context: Default::default(),
					timeout_timestamp: Duration::from_millis(Timestamp::now()).as_secs() + 1000,
				}
			})
			.collect::<Vec<_>>();

		// store a response receipt for one of the requests
		let responded = GetResponse { get: requests[1].clone(), values: Default::default() };
		host.store_response_receipt(&responded, &vec![0u8; 32]).unwrap();

		// advance past every request's timeout so each request would otherwise be timed-out
		set_timestamp(Some(Duration::from_secs(100_000_000).as_millis() as u64));

		let res = ismp::handlers::handle_incoming_message(
			&host,
			Message::Timeout(TimeoutMessage::Get { requests: requests.clone() }),
		)
		.map_err(|e| e.downcast::<ismp::Error>().unwrap());
		assert!(matches!(res, Err(ismp::Error::GetResponseAlreadyReceived { .. })));

		// the batch was rejected, so no request commitments should have been deleted
		for get in requests {
			let commitment = hash_request::<Ismp>(&ismp::router::Request::Get(get));
			assert!(host.request_commitment(commitment).is_ok());
		}
	})

/// Reject a GET timeout when the request has already received a response. The request's timeout
/// hasn't elapsed either, so without the response-receipt guard the handler would have failed
/// with `RequestTimeoutNotElapsed` — proving the response check runs first.
pub fn get_response_already_received_check<H>(host: &H) -> Result<(), &'static str>
where
	H: IsmpHost + IsmpDispatcher,
	H::Account: From<[u8; 32]>,
	H::Balance: From<u32> + Default,
{
	let intermediate_state = setup_mock_client(host);
	let get =
		dispatch_get_request(host, &intermediate_state, host.timestamp().as_secs() + 1_000_000);

	let response = GetResponse { get: get.clone(), values: Default::default() };
	host.store_response_receipt(&response, &vec![0u8; 32]).unwrap();

	let timeout_message = Message::Timeout(TimeoutMessage::Get { requests: vec![get] });

	let res = handle_incoming_message(host, timeout_message).map_err(|e| e.downcast().unwrap());
	assert!(matches!(res, Err(Error::GetResponseAlreadyReceived { .. })));
	Ok(())
}
