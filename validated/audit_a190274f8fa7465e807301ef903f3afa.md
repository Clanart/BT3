## Analog Found: Copilot conflict resolution silently applies wrong content when git's `ours`/`theirs` polarity flips during rebase/cherry-pick

### Title
Copilot conflict-resolution content can be committed to the wrong side of a conflict during rebase because `extractConflictHunks` labels raw `<<<<<<< HEAD` / `>>>>>>>` markers as literal "ours"/"theirs" while the surrounding label-mapping code independently (and separately) tracks the git-semantic swap - ([File: app/src/lib/copilot-conflict-context.ts])

### Summary
The report's bug class is: a function takes two semantically distinct values (base token vs. quote token) and, through an incorrect binding, silently produces a result whose sides are swapped — with no consistency check catching it. `app/src/lib/git/diff.ts` documents the exact same invariant in Desktop's own code and explicitly disclaims responsibility for it: `getResolutionDiff`'s comment states that git's `ours`/`theirs` stage numbers get swapped during a rebase and "the caller is responsible for mapping user-facing labels to the correct git side." [1](#0-0)  That mapping is done in one place for the UI label plumbing (`getConflictLabelsAndRefs`) [2](#0-1) , but the Copilot AI conflict-resolution feature builds its own independent view of "ours"/"theirs" straight from the raw `<<<<<<< HEAD` / `=======` / `>>>>>>>` file markers via `extractConflictHunks`, which always labels the first block `oursContent` and the second `theirsContent` regardless of which git stage they actually correspond to [3](#0-2) [4](#0-3) .

### Finding Description
Two independent code paths encode "which side is ours" for the exact same conflicted file, and they are not guaranteed to agree:

1. **UI-facing branch labels** (`ourLabel`/`theirLabel`, `ourBranch`/`theirBranch`) are computed per-operation-kind, and for rebase they are explicitly reversed relative to a merge: `ourBranch = conflictState.baseBranch` and `theirBranch = conflictState.targetBranch` [5](#0-4) [6](#0-5) .

2. **The raw conflict-marker content that is fed to the Copilot model** is extracted purely positionally: everything between `<<<<<<<` and `=======` is `oursContent`, everything between `=======` and `>>>>>>>` is `theirsContent` [7](#0-6) [8](#0-7) . This is literally how git writes the markers on disk during any of merge, rebase, or cherry-pick — but the *code-level meaning* of "ours" is defined by which git operation is running, which is exactly the invariant `getResolutionDiff`'s docstring warns about: "during a rebase, git swaps these — the upstream branch is 'ours' and the rebased commit is 'theirs'" [1](#0-0) .

3. `buildConflictContext` then stitches these two independently-derived values together into a single prompt: `ourLabel`/`theirLabel` (from step 1, correctly rebase-aware) are used as headings in the prompt text next to `oursContent`/`theirsContent` (from step 2, rebase-unaware raw markers) [9](#0-8) . There is no code anywhere in this pipeline that cross-checks that the label ("current branch"/`ourLabel`) and the marker content (`oursContent`) are actually describing the same git side for the given operation kind — the developer comment in `diff.ts` acknowledges this is a manual, caller-maintained invariant, and `copilot-conflict-context.ts` is a caller that never performs the check.

4. Once the model responds, its resolution is spliced back into the file using the *same* raw hunk boundaries (`reassembleResolvedFile`), and then written directly to disk and staged/committed via `applyCopilotConflictResolutions` → `onContinue` in the conflicts dialog, with no diff review step forcing the user to re-verify which side ended up where [10](#0-9) .

Existing guards do not stop this: `formatConflictContextForPrompt` labels the two hunk blocks with the (correct) `ourLabel`/`theirLabel` strings, giving the appearance of a verified mapping, but the actual hunk *content* underneath those labels was extracted with no awareness of the rebase/cherry-pick swap. Nothing enforces that the label text and the content underneath it describe the same side — the mapping the `diff.ts` comment demands is simply absent from this pipeline. Because everything (both content and labels) *looks* internally consistent to the user reading the prompt/summary, there is no signal that would tip the user off that content was mis-attributed.

### Impact Explanation
If the "ours"/"theirs" polarity used when constructing the AI prompt does not match the polarity the user's UI/summary reports, the model can be told (via the prompt headings) that a given branch is "ours" when the content shown under that heading is actually the git-semantic "theirs" side of a rebase (or vice-versa). The model's `keep`/resolve decisions and reasoning are then based on a mislabeled attribution of intent ("this is the user's own change" vs. "this is the incoming change"), and the resolved content that Copilot produces gets written back into the working file and silently committed/continued as part of the rebase/cherry-pick — with no diff-level warning that a resolution swapped which side's logic won. This directly matches the requested impact class: "silent corruption of what the user commits or pushes," introduced via a scenario the attacker fully controls — a crafted upstream/target branch history that a victim rebases or cherry-picks onto, engineered so the conflicting hunks are semantically opposite (e.g., a security check added on one side, removed on the other) such that a flipped-side resolution reintroduces the attacker's preferred code while the user believes the opposite branch "won."

### Likelihood Explanation
This requires no privileged access or local compromise — only an attacker-controlled branch/commit history that a normal Desktop user fetches and rebases or cherry-picks against, then opts into the (increasingly promoted) Copilot conflict-resolution feature. The likelihood of the underlying rebase/cherry-pick ours/theirs swap actually occurring is high (it happens on every rebase, not just an edge case), but whether it *manifests* as a real mislabeling bug depends on whether `extractConflictHunks`'s positional "ours"/"theirs" naming is ever misinterpreted downstream as git-semantic (rather than purely positional) — that specific downstream misuse could not be fully confirmed from the available code slices; the codebase's own comment in `diff.ts` explicitly flags this exact class of bug as something callers must handle correctly and don't get automatic protection from, which is strong circumstantial evidence that this is a fragile, easy-to-get-wrong invariant repeated across multiple conflict-resolution code paths (`getResolutionDiff`, `copilot-conflict-context.ts`, `getConflictLabelsAndRefs`) with no shared/tested abstraction enforcing consistency.

### Recommendation
Introduce a single, tested function that returns a `{ oursIsBase: boolean }` (or equivalent) flag per operation kind (merge/rebase/cherry-pick), and require every consumer that both (a) renders/labels a side and (b) extracts/writes marker content to go through it. Add an assertion/test that, for every operation kind, the label returned by `getConflictLabelsAndRefs` and the semantic side used by `extractConflictHunks`/`reassembleResolvedFile` agree — e.g., a round-trip test that stages a rebase conflict, resolves it via the Copilot path, and asserts the committed content matches the branch that `ourLabel`/`theirLabel` claim to represent.

### Proof of Concept
Not independently executable from the indexed code alone (would require running the full Copilot conflict pipeline end-to-end with a live rebase), but the reachable path is:
1. Victim fetches an attacker-influenced branch and starts `git rebase <attacker-branch>` in Desktop, hitting a conflict.
2. Desktop sets `RebaseConflictState.baseBranch`/`targetBranch` and derives `ourLabel = baseBranch`, `theirLabel = targetBranch` via `getConflictLabelsAndRefs` [6](#0-5) .
3. `buildConflictContext` reads the on-disk conflict markers and calls `extractConflictHunks`, which always assigns the first marker block to `oursContent` [11](#0-10)  — during a rebase, git actually writes the replayed (attacker) commit's content as the second block and the upstream content as the first, per the documented swap in `diff.ts` [12](#0-11) .
4. The resulting prompt/summary presents `ourLabel` next to `oursContent` without re-deriving which git stage that content actually came from, so a mismatch between the "current branch" the user sees and the branch whose logic the model actually preserved is possible.
5. Clicking Continue applies the resolution to disk and commits it as part of the rebase, with no diff confirmation forcing re-review [10](#0-9) .

Note: I was not able to fully trace whether a live mismatch is actually reachable in the current release (i.e., whether some other layer normalizes the marker semantics before they reach `extractConflictHunks`), given index-search limitations; this should be verified with a live rebase-conflict + Copilot-resolution reproduction in a full checkout.
