Now I have enough evidence to identify the strongest analog: `resolveWithin` in `app/src/lib/path.ts` performs its safety check against a `realpath`-resolved snapshot of the filesystem, but returns the pre-resolution path for later use, and that returned path is reused for a `writeFile`/`readFile` at a later point in time — a classic check-then-act gap, structurally identical to Astaria's "check computed against the stale stack before the mutation is applied."

### Title
Copilot conflict-resolution writes/reads use a path validated against a stale symlink snapshot (TOCTOU escape of the working directory) - (File: app/src/lib/path.ts)

### Summary
`resolveWithin` validates that a path stays inside the repository by resolving symlinks once via `realpath` and then returns the **unresolved** lexical path for the caller to use. `_applyCopilotConflictResolutions` (in `app/src/lib/stores/app-store.ts`) and `buildConflictContext` (in `app/src/lib/copilot-conflict-context.ts`) call this check and then perform a separate `writeFile`/`stat`/`readFile` on that returned path, exactly as `_buyoutLien` checked `maxPotentialDebt` against the pre-swap lien stack rather than the post-swap one.

### Finding Description
`resolveWithin` computes the check like this: [1](#0-0) 
It returns `resolved` — the pre-symlink path — not `realResolved`, after confirming that at the moment of the check, following any symlinks lands inside the root. That single point-in-time check is then trusted by callers who perform their own filesystem operation afterward on the same string:

- `buildConflictContext` calls `resolveWithin`, then separately calls `stat()` and `readFile()` on `absolutePath`: [2](#0-1) 
- `_applyCopilotConflictResolutions` calls `resolveWithin`, then writes the resolved content with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`: [3](#0-2) 

Both are gated by the awaited Copilot round trip: the file listed for `resolveWithin` is a conflicted path taken from a merge/rebase/cherry-pick against an attacker-supplied branch/remote, so its on-disk representation is fully attacker-controlled content in the working tree. If, between the `resolveWithin` check and the later `stat`/`readFile`/`writeFile`, the filesystem entry at that repository-relative path is swapped from a regular file to a symlink pointing outside the working directory, the guard has already been satisfied and the actual I/O call follows the (now-external) symlink. `writeFile` in Node follows symlinks by default, so the "safe" write actually lands outside the repository. The invariant "content is written to/read from a path under the repository root" is checked against a filesystem snapshot that no longer matches the state at the time of the real operation — the same "check the old state, not the state the action will actually apply to" bug pattern as the Astaria lien buyout.

### Impact Explanation
- On the write path (`_applyCopilotConflictResolutions`), a successful race results in Copilot's "resolved" content being written to an arbitrary file outside the repository that the swapped symlink points to (e.g. overwriting another project's file, a startup script, or shell config the user has write access to) — this is a file write outside the repo driven entirely by data derived from a merge with an attacker-controlled remote/branch, matching the "file write outside the repo" and "silent corruption" impact categories.
- On the read path (`buildConflictContext`), a successful race causes Desktop to read a file outside the repository and forward its content to the Copilot backend as part of the conflict-resolution prompt, which is a credential/secret exfiltration primitive if the swapped symlink targets something like `~/.ssh/id_rsa` or another repository's `.git/config`.

### Likelihood Explanation
Exploitation requires winning a narrow race: the attacker must get code to run to swap the file between the `resolveWithin` check and the subsequent I/O call, which is a nontrivial condition (this is why I flag it as the closest structural analog rather than a proven, easily-triggerable exploit). The Copilot resolution flow does add a natural delay (the model round trip completes before `_applyCopilotConflictResolutions` is invoked from `onContinue`), widening the window between when `resolveWithin` is (re)computed and when `writeFile` executes, compared to a typical tight TOCTOU window. I could not find, within the indexed code, an in-process mechanism (e.g., a filesystem watcher or background job spawned by the attacker's repo content) that would let the attacker actually flip the file without already having code execution on the host outside of the repository content itself — that missing link is what I could not verify.

### Recommendation
Eliminate the check/use gap: perform the actual file operation on a file descriptor obtained without following symlinks (e.g., open with `O_NOFOLLOW`, or use `lstat` immediately before the write/read and re-validate that the target is a regular file, not a symlink) rather than trusting a path string produced by an earlier, now-stale `realpath` check. Alternatively, have `resolveWithin` return the fully resolved (`realResolved`) path and require callers to re-verify with `lstat` immediately prior to `writeFile`/`readFile` that the entry has not been replaced by a symlink since the check.

### Proof of Concept
Not independently verified against a live race — this requires an actual filesystem race between the `resolveWithin` check and the later `stat`/`readFile`/`writeFile` calls in `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:391-431`) and `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7233-7258`), which I could not execute or fully validate through static code review alone.
