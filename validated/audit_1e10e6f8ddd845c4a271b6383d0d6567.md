## Title
Sub-additive weighting in `useGiniCoeff` proposer-list generation lets a staker split stake across multiple validator identities to gain disproportionate proposer-selection weight - (File: `kaiax/valset/impl/getter_proposers.go`)

### Summary
The Gitcoin QV bug lets an allocator manipulate `_getPayout` by splitting the same total "voice credits" across multiple recipients, exploiting the concave `sqrt()` weighting so that `sqrt(a)+sqrt(b) > sqrt(a+b)`. Kaia's `SelectWeightedRandomProposer` scheme (used when `reward.useginicoeff` is enabled) contains the exact same class of bug: it raises each validator's staking amount to a concave power `1/(1+Gini)` before computing proposer-selection weight, so a staker who splits one large stake into several smaller, separately-registered validator identities gets a strictly larger total weight than a single staker holding the same aggregate stake.

### Finding Description
`generateProposerListWeighted` computes, for each qualified validator address, an adjusted stake: [1](#0-0) 

```
exponent = 1.0 / (1 + gini)
stakingAmounts[addr] = round(amount ** exponent)
```

`gini` is in `[0,1]`, so `exponent` lies in `(0.5, 1]`. Whenever `gini > 0` (i.e., whenever validators have unequal effective stakes, essentially always true), `exponent < 1`, making `x -> x^exponent` a strictly concave function. For a concave function with exponent `<1` and `k>1`:

`k * (S/k)^exponent > S^exponent`

This is mathematically identical to the `sqrt()` sub-additivity exploited in the QV report (`sqrt` is just the special case `exponent = 0.5`).

Each qualified validator address is a `RewardAddr`-consolidated node from `StakingInfo.ConsolidatedNodes()`; consolidation only merges entries that already share the same `RewardAddr`: [2](#0-1) 

If the exact same total capital is instead registered across `k` distinct AddressBook entries with `k` distinct `RewardAddr`s (each individually meeting `reward.minimumstake` to be "qualified"), `collectStakingAmounts` will treat them as `k` separate validators rather than one consolidated node: [3](#0-2) 

The Gini-adjustment is then applied independently to each of the `k` smaller stakes, so the staker's summed adjusted weight (and hence summed percentile weight `W_i`, and hence summed occurrences in the proposer list) is strictly larger than if the same capital had been staked under a single validator identity: [4](#0-3) 

The concept is also documented directly in the module README as `S_i = Round(S_i^{1/G})`: [5](#0-4) 

### Impact Explanation
Being present more often in the proposer list translates directly into being selected as block proposer more frequently than a staker's true proportional share of total stake warrants. The proposer:
- receives the proposer's minting reward and (for NDF or excess fee cases) transaction fees, as computed in the reward module,
- controls block assembly, including inclusion/ordering of auction bids and gasless bundles.

By splitting one large stake into several smaller qualifying validator identities (each meeting `reward.minimumstake`), an attacker inflates their aggregate selection probability beyond what their real economic stake should confer, redirecting a disproportionate share of block-proposer rewards and block-building control to themselves at the expense of honest single-identity stakers. This is a direct reward-redirection / unfair value-capture issue analogous to the reported QV exploit.

### Likelihood Explanation
This requires:
- `reward.useginicoeff = true` (an existing immutable governance parameter mentioned in `kaiax/gov/README.md`, so applicable on chains where it's enabled), and
- the pre-Kore `SelectWeightedRandomProposer` code path (used when `!Rules.IsKore`), which remains live in the codebase for chains not yet on Kore (e.g., legacy/private Kaia-based networks, or historical block replay/consensus).
- A staker capable of registering multiple AddressBook validator entries with distinct reward addresses, each individually meeting the minimum stake — an action reachable by any staker/operator without special protocol privilege.

Since Gini > 0 essentially always holds in a real network with any staking-amount heterogeneity, the exploit condition is satisfied by default whenever the feature is active; the only "cost" to the attacker is running multiple validator identities, which is an operational rather than protocol constraint.

### Recommendation
Avoid applying the concave Gini exponent independently per validator identity in a way that is manipulable via identity splitting. Options include:
- Consolidating by ultimate beneficial owner rather than purely by `RewardAddr` where feasible, or
- Capping/normalizing so that the sum of `S_i^exponent` for an economic entity cannot exceed `(sum S_i)^exponent`, or
- Re-deriving the weighting scheme so weight is computed once on aggregate stake fully consolidated before applying any non-linear transform, closing the same sub-additivity gap that caused the original QV issue.

### Proof of Concept
Given `gini = 0.2` → `exponent = 1/1.2 ≈ 0.833`.
- Single validator with stake `S = 100` (KAIA, in staking units above `minStake`): adjusted weight `= 100^0.833 ≈ 46.4`.
- Same staker splits `S` into two validators of `50` each (each independently ≥ `reward.minimumstake`): adjusted weight `= 2 * 50^0.833 ≈ 2 * 25.5 = 51.0`.

The split configuration yields ~10% more aggregate Gini-adjusted weight for the same total economic stake, directly increasing the staker's expected frequency of being selected proposer (and therefore expected proposer rewards/block-building control) relative to a non-splitting staker with identical capital, exactly mirroring the vote-splitting exploit described in the original report against `_getPayout`'s `sqrt()` weighting.

func generateProposerListWeighted(qualified *valset.AddressSet, si *staking.StakingInfo, useGini bool, blockHash common.Hash) []common.Address {
	var (
		addrs          = qualified.List()
		stakingAmounts = collectStakingAmounts(addrs, si)
		gini           = computeGini(stakingAmounts) // si.Gini is computed over every CN. But we want gini among validators, so we calculate here.
		exponent       = 1.0 / (1 + gini)
		totalStakes    = float64(0)
	)

	// Adjust staking amounts and calculate the sum
	if useGini {
		for addr, amount := range stakingAmounts {
			stakingAmounts[addr] = math.Round(math.Pow(float64(amount), exponent))
			totalStakes += stakingAmounts[addr]
		}
	} else {
		for _, amount := range stakingAmounts {
			totalStakes += amount
		}
	}

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

func collectStakingAmounts(nodes []common.Address, si *staking.StakingInfo) map[common.Address]float64 {
	cns := si.ConsolidatedNodes()
	stakingAmounts := make(map[common.Address]float64, len(nodes))
	for _, node := range nodes {
		stakingAmounts[node] = 0
	}
	for _, cn := range cns {
		for _, node := range cn.NodeIds {
			if _, ok := stakingAmounts[node]; ok {
				stakingAmounts[node] = float64(cn.StakingAmount)
			}
		}
	}
	return stakingAmounts

Given "proposer update block" in which all the information below (qualified validators, staking info, block hash) is based on,
1. Adjust the staking amounts of the qualified validators.
    - $S_i = \text{Round}({S_i}^{1/G})$ if Gini option is enabled.
    - $S_i = S_i$ (unchanged) if Gini option is disabled.
    - Gini option is controlled by the `reward.useginicoeff` parameter.
    - G is the Gini coefficient of the staking amounts that are no less than the minimum staking amount (i.e. `G = stakingInfo.Gini(minStake)`).
1. Calculate the total staking amount of the qualified validators. Use the Gini-adjusted amounts, if enabled.
    - $TS = \sum{S_i}$
1. Calculate the percentile weight (integers 1 to 100) of the qualified validators. Every validator has a nonzero chance.
    - $W_i = \text{max}\left(1, \text{round}\left(\frac{100S_i}{TS}\right)\right)$ if TS > 0
    - $W_i = 0$ if TS = 0
1. Construct the "proposer list" where each validator appears $W_i$ (could be 0) times. If the proposer list is empty, put each validator once.
    - $PL = \text{repeat}(0, W_0) || ... || \text{repeat}(k, W_k)$ if $\sum{W_i} > 0$
    - $PL = 0, 1, ..., k$ if $\sum{W_i} = 0$
    - where $\text{repeat}(v,n) = v, v, ..., v\ \ (n\text{ times})$
