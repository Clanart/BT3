### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/fee calculation, so transactions pay less than the requested fee rate and may be un-relayable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying caller-supplied `data` to `tx_outs`, but computes `weight`/`vbytes` — and therefore `needed_fee`, the minimum-fee check, and the change amount — from `calculate_weight_vbytes(inputs, payments, change)`, which only accounts for the payment outputs. The fee actually paid (`sum(inputs) - sum(outputs)`) is sized for a transaction up to ~93 vbytes smaller than the real one, so the effective fee rate is strictly below the `fee_per_vbyte` the caller specified, and can fall below the relay minimum even though the `TooLowFee` check passed.

### Finding Description
The external bug class is "a computed share of value is never actually transferred / is mis-accounted" (the treasury's share in `buyToken`). In Serai's in-scope Bitcoin wallet code, the same accounting-mismatch shape exists between what the fee calculation assumes the transaction contains and what the signed transaction actually contains.

In `networks/bitcoin/src/wallet/send.rs`:

- Lines 193–202 push the OP_RETURN output into `tx_outs` when `data` is provided:
  ```rust
  if let Some(data) = data {
    tx_outs.push(TxOut {
      value: Amount::ZERO,
      script_pubkey: ScriptBuf::new_op_return(...)
    })
  }
  ```
- Line 204 then computes the weight/vbytes used for `needed_fee` via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — passing `payments`, i.e., only the payment outputs, never the already-appended data output.
- Line 211 enforces `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` against that undersized `vbytes`.
- Lines 224–235 compute `fee_with_change` and the change output value (`input_sat - payment_sat - fee_with_change`) from the same undersized estimate.

`calculate_weight_vbytes` (lines 62–127) builds a `Transaction` whose `output` vector is populated from `payments` plus an optional change output; the data output is structurally invisible to it. So for `data` of length `L`, the estimated vsize misses roughly `L + ~9` bytes (8-byte value, script length, `OP_RETURN` + push opcode), up to ~89–93 vbytes for the permitted 80-byte payload.

Because the change output absorbs `input_sat - payment_sat - fee`, the absolute fee paid equals `needed_fee` — but it is spread over a transaction larger than the one measured. The delivered fee rate is `needed_fee / actual_vsize < fee_per_vbyte`.

### Impact Explanation
- A caller requesting `fee_per_vbyte` receives a transaction paying a strictly lower effective rate. At `fee_per_vbyte = 1` with a ~80-byte data payload on a small transaction, the effective rate can drop below 1 sat/vbyte, below `DEFAULT_MIN_RELAY_TX_FEE` — despite the `TooLowFee` guard passing. Such a transaction will not relay or confirm, leaving the wallet's funds effectively stuck in an unconfirmed, unpublishable-by-policy transaction (inputs remain locked until the attempt is abandoned and re-signed).
- The mismatch also means `needed_fee()` reports a fee lower than what the transaction's size actually requires, corrupting any downstream accounting (e.g., `Network::needed_fee`, fee amortization in the processor, which calls `make_signable_transaction` and trusts `signable.needed_fee()`).

### Likelihood Explanation
Reachable by an unprivileged caller: `data` is an arbitrary, length-checked-only (≤80 bytes, line 171) public input to `SignableTransaction::new`. Any transaction built with an OP_RETURN payload — which is the documented mechanism for attaching protocol data — silently underpays its fee. No malicious validator, leaked key, or misbehaving peer is required; only the code path `data = Some(_)`.

### Recommendation
Include the data output in the size estimation. Either pass the already-built `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or add the OP_RETURN output inside `calculate_weight_vbytes` before measuring. Concretely, reorder `SignableTransaction::new` so the data output is appended before the `calculate_weight_vbytes` calls at lines 204 and 226, and change the signature to take `&[TxOut]` (outputs) instead of `&[(ScriptBuf, u64)]` (payments), so that every output in the final transaction — payments, OP_RETURN, and change — is counted. The `TooLowFee` and `NotEnoughFunds` checks will then evaluate the true vsize.

### Proof of Concept
```rust
// Construct a minimal spend: one input, one 1000-sat payment, 80-byte data.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    inputs.clone(),                    // e.g. a single ReceivedOutput
    &payments,                         // [(script, 1000)]
    Some(change_script),               // or None
    Some(data.clone()),
    1,                                 // fee_per_vbyte = 1
).unwrap();

let fee = tx.fee();                    // sum(inputs) - sum(outputs)
let actual_vsize = /* vsize of tx after signing */;
// fee / actual_vsize < 1 sat/vb even though 1 sat/vb was requested,
// because `needed_fee` was computed on a vsize missing the ~89-byte
// OP_RETURN output. The TooLowFee check also used the smaller vsize,
// so a TX below DEFAULT_MIN_RELAY_TX_FEE can be produced.
assert!(fee < actual_vsize);           // effective rate < requested rate
```
The gap equals the serialized size of the OP_RETURN output (~`data.len() + 9` vbytes), unaccounted for by the `calculate_weight_vbytes` calls at lines 204 and 226 of `networks/bitcoin/src/wallet/send.rs`.
