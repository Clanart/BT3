## Analysis

The reported bug class — an on-chain-computed `amountOutMin` (derived from a manipulable pool query) being used to guard a token swap that is automatically triggered by ordinary user actions (deposit/withdraw/claim) — has a direct analog in the in-scope `SmartWomConvert`/`WombatStaking` flow. [1](#0-0) 

Any unprivileged wallet calling `deposit`, `depositLP`, `withdraw`, or `harvest` on `WombatStaking` triggers `_toMasterWomAndSendReward` → `_sendRewards`, which — for pools where the WOM fee is configured to be converted to mWOM — calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` unconditionally on every such call. [2](#0-1) 

`smartConvert()` computes `mWomToWom` via `currentRatio()`, which reads `IWombatRouter(router).getAmountOut(...)` — an on-chain, spot-price-dependent call — to decide how much of the WOM fee to route through a live swap versus straight 1:1 minting. The actual swap executed in `_convertFor` passes a hardcoded `0` as the router's slippage parameter: [3](#0-2) 

The only protection is the aggregate post-swap check `convertAmount + amountRec < _minRec` — and in the `smartConvert` path, `_minRec` is set to `_amountIn` (i.e., only requires break-even, not fair-market-value execution). Because both the swap's actual execution and the ratio/threshold decision rely on the same manipulable spot price, an attacker can sandwich any user's deposit/withdraw/harvest call: front-run to skew `womAsset` cash/liability and the WOM/mWOM pool reserves, let the victim's transaction convert the protocol's accrued WOM yield at the manipulated price (while still passing the break-even check), then back-run to restore price and pocket the difference — extracting value from the yield destined for `vlMGP`/stakers who benefit from the mWOM stream.

### Title
SmartWomConvert.smartConvert()/_convertFor() swaps use manipulable on-chain price and zero-slippage router calls, enabling sandwich extraction of stakers' WOM yield - (File: wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._sendRewards` automatically calls `SmartWomConvert.smartConvert(feeAmount, 0)` on every user-triggered `deposit`, `depositLP`, `withdraw`, or `harvest`. `smartConvert`/`_convertFor` decide the swap-vs-mint split and validate the swap output using prices read live from `IWombatRouter(router).getAmountOut` (`currentRatio()`, `maxSwapAmount()`), while the actual router swap call hardcodes `0` for its minimum-out parameter, relying solely on a break-even post-check. [4](#0-3) 

### Finding Description
The swap executed inside `_convertFor` (`IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)`) passes `0` as `minAmountOut`, so it has no per-swap slippage protection at the router level. The higher-level `_minRec` check only enforces `convertAmount + amountRec >= _minRec`, and for the automatic `smartConvert` path `_minRec` equals the full input amount — a break-even bound, not a fair-price bound. Since `currentRatio()` and `maxSwapAmount()` (used to size `buybackAmount`) are themselves computed from the same live, atomically-manipulable Wombat pool reserves (`IAsset(womAsset).cash()`/`liability()` and `IWombatRouter.getAmountOut`), an attacker can manipulate reserves immediately before the victim's transaction executes, causing the WOM-fee-to-mWOM conversion to execute at a worse-than-fair rate while still satisfying the break-even check, and then reverse the manipulation afterward to capture the spread. This mirrors the reported `USDLStrategy._swapPLSforUSDL()` pattern: any of several routine user actions triggers an unprotected swap of protocol/staker-destined yield. [5](#0-4) 

### Impact Explanation
Every deposit, withdrawal, or harvest against `WombatStaking` for pools with the mWOM fee enabled converts accrued WOM yield through this vulnerable path. Because the swap can be sandwiched, value that should accrue to mWOM/vlMGP-locking stakers is instead extracted by MEV searchers, resulting in theft of unclaimed protocol yield spread across many independent, unprivileged-triggered transactions.

### Likelihood Explanation
The function is invoked automatically and frequently (on essentially every user deposit/withdraw/harvest across active pools with the mWOM fee configured), giving attackers many opportunities to detect and sandwich sizeable conversions, especially when accrued WOM fees are large relative to the WOM/mWOM pool's liquidity.

### Recommendation
Pass a real, caller-supplied or conservatively-computed minimum output to the router swap in `_convertFor` (not `0`), and avoid deriving both the split decision and the acceptance threshold from the same spot-manipulable on-chain price; consider using a TWAP, an external caller-supplied slippage bound with a sanity ceiling, or restricting `smartConvert`'s automatic invocation to trusted keeper flows with tight, pre-set slippage parameters.

### Proof of Concept
1. Attacker monitors the WOM/mWOM Wombat pool and mempool for `WombatStaking.deposit/withdraw/harvest` calls where a nonzero WOM reward will be routed to `smartWomConverter`.
2. Attacker front-runs by swapping in the womAsset pool to manipulate `cash()`/`liability()` and the router's quoted price, shifting `currentRatio()`/`maxSwapAmount()` and worsening the effective output of the pending `buybackAmount` swap.
3. Victim's transaction executes `_sendRewards` → `smartConvert(feeAmount, 0)` → `_convertFor`, which calls `swapExactTokensForTokens(..., 0, ...)` — the swap executes at the manipulated price with no per-swap floor, only needing to clear `convertAmount + amountRec >= feeAmount`.
4. Attacker back-runs, reversing the pool manipulation and capturing the price difference, i.e., value skimmed from the WOM yield destined for mWOM stakers.

        uint256 womCash = IAsset(womAsset).cash();
        uint256 womLiability = IAsset(womAsset).liability();

    // should mainly used by wombat staking upon sending wom
    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
