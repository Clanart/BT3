### Title
Attacker-controlled FROST preprocess with identity nonce commitments panics the secp256k1 signer - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The JasPer CVE is a heap over-read/crash on crafted input. The Serai analog is a panic (process abort) reachable purely through untrusted bytes an unprivileged co-signer supplies via `read_preprocess`: a `Preprocess` whose nonce commitments are crafted so the aggregate nonce `R` is the point at infinity causes `x()`/`hram()` to `expect`/`panic` inside the BIP-340 `Hram`, crashing the signing process before any share is produced.

### Finding Description
`Preprocess::read` (`crypto/frost/src/sign.rs:276`) parses attacker bytes via `Commitments::read` → `NonceCommitments::read` → `GeneratorCommitments::read` (`crypto/frost/src/nonce.rs:34-36`), which accepts any canonical point encoding — including the identity. `C::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only enforces canonicality, not non-identity.

In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283-411`), the supplied commitments feed `BindingFactor::nonces` (`nonce.rs:194-212`), which computes `D + multiexp(E_i * rho_i)` per nonce — i.e. the aggregate `R`. A malicious participant who transmits its preprocess last (or can observe the others' commitments) chooses `D = -(sum of others' bound terms)` and `E = 0`, forcing `nonce_sums[0][0]` to identity.

`Schnorr::sign_share` then calls `H::hram(&nonce_sums[0][0], ...)` (`crypto/frost/src/algorithm.rs:208`). For the Bitcoin `Schnorr` algorithm, `Hram::hram` calls `x(R)` (`networks/bitcoin/src/crypto.rs:59-65`), and `x` does `key.to_encoded_point(true).x().expect("point at infinity")` (`crypto.rs:13-16`) — a panic. The same panic is reachable in `verify`/`verify_share` (`algorithm.rs:215, 226`) since `SchnorrSignature::verify`/`batch_statements` on the secp256k1 BIP-340 path also hit `x`/`x_only`, which `expect` on non-infinity/parity (`crypto.rs:21-23`).

The crate acknowledges this: `Hram` is documented as "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`), but no check rejects identity commitments during `read_preprocess` or before aggregation, so the panic is attacker-reachable rather than a documented caller-MUST.

### Impact Explanation
Any one of the `n` FROST participants can crash the signing process of every honest participant who incorporates their preprocess. Since `complete`/`sign` run inside validator/processor code, a crafted preprocess yields a denial of service (application crash) against threshold-signing sessions — the same availability impact class as CVE-2017-9782 (medium severity).

### Likelihood Explanation
An unprivileged party able to send a preprocess message to a signer (a normal protocol step) can reach this with public input bytes alone. Forcing `R` to identity requires the attacker to send their preprocess after observing others — feasible where preprocess collection is asynchronous — or with probability ~1/2 via odd/even tricks in simpler orderings. No secret or privileged position is required.

### Recommendation
Reject identity points in `GeneratorCommitments::read` / `NonceCommitments::read` (add `is_identity` checks in `crypto/frost/src/nonce.rs:34-79`), or check `nonce_sums[..][..]` for identity in `AlgorithmSignMachine::sign` before calling `sign_share`, returning `FrostError` instead of panicking. Alternatively, make `x()`/`x_only()`/`hram()` return `Option`/`io::Result` so infinity is handled gracefully.

### Proof of Concept
1. Honest signer runs `AlgorithmMachine::new(Schnorr::new(), keys).preprocess(rng)` for the Bitcoin `Schnorr` algorithm and calls `read_preprocess` on attacker bytes.
2. Attacker supplies a serialized `Preprocess` whose `GeneratorCommitments([D, E])` satisfy `E` = identity and `D` = negation of the sum of other participants' bound nonces (attacker waits to be last), making `BindingFactor::nonces` return `R = identity` at `nonce.rs:204-208`.
3. `sign()` calls `sign_share` → `Hram::hram` → `x(R)` → `.expect("point at infinity")` (`networks/bitcoin/src/crypto.rs:15`) — panic/crash, no signature produced.

Caveat: I did not trace every caller to confirm a concrete deployment transmits preprocesses attacker-last, but the panic path itself is fully supported by the cited code; the crash does not depend on ordering for `verify`/`verify_share` if `R` can be driven to identity by any means.
