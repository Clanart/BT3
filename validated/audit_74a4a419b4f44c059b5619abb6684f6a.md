### Title
Cached FROST/MuSig preprocess is never invalidated after use, so re-execution of `share`/`complete` with differing on-chain inputs reuses the same nonces and leaks the validator's private key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
In `SigningProtocol::preprocess_internal`, the preprocess seed is cached under `CachedPreprocesses[context]` the first time it is generated, and every subsequent call reloads *the same seed* via `AlgorithmSignMachine::from_cache`, deterministically reproducing identical nonces (`seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)` → `Commitments::new`). The cache entry is **never deleted or rotated** after a share is produced. `DkgConfirmer::share` and `DkgConfirmer::complete` both funnel through `share_internal` → `preprocess_internal`, so the same nonce set is signed with on every re-execution. This mirrors the reported bug class: a capacity-like state variable (the "preprocess consumed" invariant) is not reduced by the amount it should be (the cache must be invalidated), so a *later* call gets more than it is entitled to — here, a second signature share under an already-spent nonce.

### Finding Description
`crypto/frost/src/sign.rs` states the invariant explicitly: a cached preprocess "MUST only be used once. Reuse of it enables recovery of your private key share" (`SignMachine::from_cache` docs, and `spec/cryptography/FROST.md` "Caching" section). In `coordinator/src/tributary/signing_protocol.rs:123-145`, `CachedPreprocesses::set` is executed only when the entry `is_none()`; nothing ever removes or updates it after `machine.sign(preprocesses, msg)` runs in `share_internal` (line 170).

The safety argument in the file header (lines 25-54) is that fixed nonces are safe because BFT finalization guarantees the received `preprocesses` map and `msg` are identical on every re-execution. That guarantee does not hold across the *different inputs* to the two signing entry points:

- `DkgConfirmer::share(preprocesses, key_pair)` signs `set_keys_message(&set, &removed, key_pair)` — `key_pair` is a caller-supplied parameter (line 296-301).
- `DkgConfirmer::complete(preprocesses, key_pair, shares)` calls `share_internal` *again* with its own `key_pair` and `preprocesses` arguments (line 321-324).

Both calls are driven by data read from finalized tributary blocks in `handle_new_blocks` (`coordinator/src/tributary/scanner.rs:681-715`), i.e., `preprocesses`, `key_pair`, and `shares` are values serialized into transactions that any validator — and the `key_pair` in particular is a value committed in the transaction stream, not fixed by the context key — can cause to vary between the share-triggering and complete-triggering code paths. The `context` used as the cache key is only `(b"DkgConfirmer", attempt)` (line 275); it does **not** bind `key_pair`, the preprocess set, or the message.

Concretely: if `share` runs with `(preprocesses_A, key_pair_A)` and `complete` (or a second `share`, e.g. after a partial rebuild where `CachedPreprocesses` persisted but in-memory machine state did not) runs with `(preprocesses_B, key_pair_B)` under the same `attempt`, our nonces `d_i, e_i` are identical while the aggregate nonce `R` and challenge `c` differ. Each signature share is `s_i = d_i + b·e_i + λ_i·x_i·c`. Two shares with known differing `c` and the same `d_i + b·e_i` yield `x_i = (s_1 − s_2) / (λ_i·(c_1 − c_2))` — direct recovery of the validator's Ristretto secret key, which is the root-of-trust MuSig key used to confirm DKG results on Substrate.

### Impact Explanation
Recovery of a validator's signing key. The header comment itself (line 50-54) flags this as an unimplemented TODO ("check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)"), and FROST.md documents that nonce reuse "would enable a third-party to recover your private key share." Since this key authorizes `set_keys` (the confirmation of new DKG key pairs on-chain), key compromise crosses from one validator's share into control over validator-set key confirmation.

### Likelihood Explanation
Medium. Triggering requires that the coordinator executes the signing path twice for the same `attempt` with non-identical inputs — e.g., differing `key_pair`/`preprocesses` between the `share` and `complete` invocations, or a process restart that drops in-memory deduplication while the DB cache persists (the DB survives rebuilds by design, per lines 43-48). The inputs are public on-chain data, and the protocol deliberately re-executes from the DB; nothing in `preprocess_internal` enforces that re-executions used identical messages. There is no check comparing the newly-received preprocesses/message against what the cached seed previously signed.

### Recommendation
Bind the cached preprocess to its exact usage: store alongside `CachedPreprocesses[context]` a hash of `(sorted_preprocesses, msg)` at first `sign`, and refuse to sign if a later call presents a different tuple — or better, derive `context` to include `key_pair`/message digest so distinct signing intents get distinct seeds. Alternatively, delete the cache entry after producing a share and re-derive the *share* (not just the machine) deterministically for `complete`, so identical inputs replay the identical share rather than re-signing fresh inputs under spent nonces.

### Proof of Concept
1. Attempt `k` of the DKG confirmation runs. `preprocess` is published; `CachedPreprocesses[("DkgConfirmer", k)] = seed` is set.
2. `share(preprocesses_A, key_pair_A)` executes `machine.sign` → publishes share `σ_1 = d + b·e + λ·x·c_1` over `msg_A = set_keys_message(set, removed, key_pair_A)`.
3. Coordinator restarts or `complete` is invoked with a transaction carrying `key_pair_B ≠ key_pair_A` (or a different included preprocess set). `preprocess_internal` reloads the same `seed` → identical `d, e`; `sign` recomputes `R`/`c_2` over `msg_B` → share `σ_2 = d + b·e + λ·x·c_2`.
4. Observer computes `x = (σ_1 − σ_2)·(λ·(c_1 − c_2))^{-1}`, recovering the validator's MuSig secret key from two public signature shares.

Uncertain: whether coordinator call sites in `handle.rs` can actually deliver a divergent `key_pair`/`preprocesses` for the same attempt (I could not fully trace `handle.rs` in the available iterations); if inputs are provably identical on every re-execution, the reuse is benign and this degrades to a latent footgun rather than a live vulnerability.
