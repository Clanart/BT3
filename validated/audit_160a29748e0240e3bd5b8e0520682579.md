Confirmed: this contract imports and uses `SafeERC20`/`safeTransferFrom` elsewhere (for escrow deposits), but the `withdraw()` and `SweepDust` payout paths deliberately bypass `SafeERC20.safeTransfer` and instead use raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only the outer call-success boolean and never decoding the ERC20 return value.

### Title
Escrow withdrawal on Tron IntentGatewayV2 finalizes and burns escrow accounting when a non-standard ERC20 `transfer()` returns `false` without reverting - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2.withdraw()` and its `SweepDust` governance handler pay out escrowed/dust tokens using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treat the payout as successful purely because the *call itself* did not revert (`success == true`). Neither function decodes or checks the boolean value that `IERC20.transfer` is specified to return. This is the exact bug class in the external report (`mintWithPermit` trusting `permit()` succeeded without checking its actual effect): a non-reverting-but-failing external token call is silently treated as success, and the contract proceeds to finalize state as if the asset had moved.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the function that releases escrowed order inputs to a beneficiary on `EscrowReleased`/`EscrowRefunded` settlement, invoked from `onAccept` (RedeemEscrow) and `onGetResponse` (cancellation) — i.e. it is the single funds-release path for cross-chain intent escrow on this deployment: [1](#0-0) 

For every non-native token, the code does:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
`success` here is only `false` if the call *reverts*. Solidity's low-level `call` returns `success = true` any time the callee returns normally, even if the callee's return data decodes to `false` (the legacy non-compliant ERC20 pattern, e.g. tokens historically shipped without a strict revert-on-failure guarantee). Because the return data is never decoded/verified, a token like this can "fail" the transfer (send zero tokens, or send to the wrong effective balance) while the outer call reports success.

Once `success == true`, the function unconditionally:
- decrements `_orders[body.commitment][token] -= amount` (escrow accounting reduced as if the beneficiary got paid),
- sets `_filled[body.commitment] = beneficiary` (order permanently marked filled/settled) — this happens *before* the per-token loop even runs, so it is set on every call regardless of any transfer outcome,
- emits `EscrowReleased`/`EscrowRefunded`.

The elsewhere-imported `SafeERC20` (`using SafeERC20 for IERC20`) is deliberately not used in this path even though the same file uses `safeTransferFrom` for escrow *deposits*: [2](#0-1)  — showing the contract's authors know the pattern but the withdrawal/sweep side reverted to raw `.call` + selector, exactly the "assume permit/transfer succeeded" anti-pattern from the external report. The `SweepDust` governance handler has the identical flaw: [3](#0-2) 

By contrast, the mainline EVM implementation of the same withdrawal logic (`IntentsBase.sol`) correctly uses `IERC20(token).safeTransfer(beneficiary, amount)`: [4](#0-3) , confirming the Tron variant is the outlier that reintroduced the unchecked-external-call pattern.

### Impact Explanation
If an order's input token is a non-compliant ERC20 that can return `false` (or otherwise fail silently) rather than reverting on a failed transfer, `withdraw()` will:
1. Mark the commitment `_filled` (order settlement finalized, blocking any retry/refund/cancellation path for that commitment),
2. Decrement escrow accounting for that token as though it paid out,
3. Emit `EscrowReleased`/`EscrowRefunded`,

— all while the beneficiary receives none of the tokens. The tokens remain trapped in the gateway contract with no accounting entry pointing to them (since `_orders[...]` was already decremented), and the beneficiary has no path to reclaim them because the order is already marked filled. This is a direct, permanent loss of the escrowed asset for the rightful beneficiary — matching the required impact class ("stealing or loss of funds", "false settlement acceptance", state finalized despite no actual transfer).

### Likelihood Explanation
Reaching this path requires only that an order's escrowed input token be a non-standard ERC20 that fails without reverting — a property of the *token contract itself*, not of any relayer, prover, or admin. Anyone who can create an intent order (an unprivileged, permissionless action in this system) chooses the input token, and the token issuer (or the token itself, for known non-compliant legacy tokens) determines this behavior; no compromised infrastructure role is needed. Given IntentGatewayV2 is designed to be generic/permissionless across arbitrary ERC20 assets, and the codebase elsewhere explicitly guards for fee-on-transfer and "actual received" divergences (see `IntentGatewayV2.sol` main EVM deposit logic reconciling `balanceOf` deltas), the withdrawal side of this Tron variant is inconsistent in not applying the same rigor, making this a realistic, locally-provable gap rather than a hypothetical one.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this same file, so that both call-revert and false-return failures are treated identically and rejected before escrow accounting/`_filled` state is mutated.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer()` returns `false` on failure instead of reverting (a known legacy non-compliant pattern; the report's own citation of DAI's `permit()` illustrates the same class of non-standard token behavior in this ecosystem).
2. Create and escrow a cross-chain intent order on the Tron `IntentGatewayV2` using this token as an input asset via the normal `IERC20.safeTransferFrom` deposit path (deposit path works fine since it uses `SafeERC20`).
3. Trigger settlement so `withdraw()` is invoked (e.g. via `onAccept`/RedeemEscrow after the destination fill, or via `onGetResponse` cancellation), with the token contract configured/state such that its `transfer()` call returns `false` (e.g. insufficient internal allowance-like condition specific to the non-standard token) but does not revert.
4. Observe: `withdraw()`'s `(bool success,) = token.call(...)` returns `success = true` (the external call itself did not revert), so execution continues past `if (!success) revert TransferFailed();`.
5. Confirm `_orders[commitment][token]` is decremented and `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — while the beneficiary's on-chain token balance is unchanged, demonstrating funds are locked in the contract and the settlement is falsely finalized.

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

                ++i;
            }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
