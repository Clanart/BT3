## Analog Found: Proportional Escrow Truncation in Same-Chain Partial Fills

### Title
Partial-fill proportional escrow release truncates to zero for small input amounts, causing fund loss to earlier fillers - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The Migration.sol bug's core invariant is: a proportional-share calculation `(contribution × newTotal) / oldTotal` can truncate to zero when the numerator is small relative to the denominator, permanently zeroing out a legitimate participant's entitlement once the operation (`commit()`/Buyout) becomes irreversible. `IntrinsicIntents._fillSameChain` in the Hyperbridge Intent Gateway contains the identical arithmetic pattern for releasing escrowed input tokens proportionally to partial output fills, and it is fully attacker-controllable at order-placement time.

### Finding Description
In `_fillSameChain`, for every partial (non-final) fill, the escrow released to the filling solver is computed as: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

`order.inputs[i].amount` (the escrowed input total) and `totalRequired` (`order.output.assets[i].amount`) are both fully attacker-controlled fields set by the order creator at `placeOrder` time and baked into the commitment hash — the contract enforces no minimum ratio between them. If the order is crafted with a very small `order.inputs[i].amount` (e.g. `1` wei of USDC) against a large `totalRequired` (e.g. `1e18` DAI), then for *any* partial fill where `fillAmount < totalRequired`, `(1 * fillAmount) / totalRequired` floors to `0` regardless of how large `fillAmount` is (short of a full fill). Meanwhile, the solver has already unconditionally transferred real value to the beneficiary: [2](#0-1) 

```solidity
uint256 amountFilled = alreadyFilled + fillAmount;
_partialFills[commitment][outputToken] = amountFilled;
uint256 beneficiaryTotal = fillAmount + beneficiaryShare;
...
IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
```

Because `_partialFills[commitment][outputToken]` is monotonically advanced and the fill event is irrevocable (tokens are already sent to `beneficiary`), the truncated solver has no recourse — exactly as Bob in the Migration.sol report cannot use `leave()`/`withdrawContribution()` once the migration/buyout has started. The undistributed escrow does not disappear; it sits in `_orders[commitment][token]` untouched, and is entirely swept by whichever solver happens to submit the fill that satisfies `amountFilled == totalRequired`:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][...]; // grabs the WHOLE remaining balance
}
```

So the truncated share is not lost from the protocol's perspective — but it is misdirected: it goes to whichever solver lands the final fill rather than to the solver(s) whose earlier fills were rounded to zero. This is a direct "wrong beneficiary/wrong amount" fund-misallocation, not merely dust.

### Impact Explanation
- An unprivileged order creator can, at zero cost, craft `inputs[i].amount` and `totalRequired` ratios that guarantee any non-final partial fill releases `0` escrow to the filling solver.
- Solvers acting on partial fills (a supported, documented feature — same-chain orders explicitly support multi-solver partial fills per `docs/content/developers/evm/intent-gateway/overview.mdx`) can deliver real output tokens to the beneficiary and receive nothing back, a direct loss of funds.
- The remaining escrow balance is instead awarded in full to whichever solver completes the order, giving that solver more than their proportional entitlement — a wrong-amount transfer.
- This falls squarely under the bounty's included impact "stealing or loss of funds ... transaction manipulation ... wrong beneficiary or amount," reached through a fully public, unprivileged entrypoint (`placeOrder` + `fillOrder`), with no reliance on a malicious relayer/prover/admin.

### Likelihood Explanation
Likelihood is high in adversarial conditions: any order creator can set an extreme input/output ratio without violating any contract invariant (no minimum-ratio check exists), and any solver that is unaware of the internal floor-division mechanics and chooses to partially fill such an order will be affected. Because partial fills are an advertised, expected usage pattern (not an edge case), a malicious order creator only needs to wait for competitive solver behavior to trigger the loss.

### Recommendation
Mirror the Migration.sol fix's spirit — protect against silent truncation of legitimate proportional entitlements — by:
1. Requiring `order.inputs[i].amount >= totalRequired` (or otherwise bounding the ratio) at `placeOrder` time so proportional division cannot floor to zero for any valid `fillAmount > 0`, or
2. Using a "credit-then-release" accounting model that tracks cumulative escrow already released per token (`released[commitment][token]`) and computes each release as `floor(inputs[i].amount * amountFilled / totalRequired) - released[commitment][token]`, so each filler is credited their exact fair share and rounding dust only ever benefits the very last filler by at most 1 unit (this is the same technique already applied for the *full-fill* branch, but it needs to be generalized to every partial fill, not just the last one).

### Proof of Concept
1. Order creator places a same-chain order with `inputs[0] = {token: USDC, amount: 1}` (1 wei) and `output.assets[0] = {token: DAI, amount: 1000e18}`.
2. Solver A calls `fillOrder` with `outputs[0].amount = 500e18` (50% fill). `fillAmount = 500e18`, `totalRequired = 1000e18`, so `escrowedAmount = (1 * 500e18) / 1000e18 = 0`. Solver A transfers `500e18` DAI to the beneficiary and receives `0` USDC.
3. Solver B calls `fillOrder` completing the remaining `500e18` DAI. Since `amountFilled == totalRequired`, `escrowedAmount = _orders[commitment][USDC] = 1` (the full, untouched escrow). Solver B receives the entire 1 wei USDC escrow despite only contributing the second half of the fill.
4. Net result: Solver A paid 500e18 DAI and received 0 USDC; Solver B received all of the escrow for contributing only half the output. This is directly analogous to Migration.sol's minority shareholder losing their share to floor-division truncation once `commit()`/the equivalent irreversible fill state advances.
