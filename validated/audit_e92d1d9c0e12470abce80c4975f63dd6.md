### Title
Missing-commitment participant causes panic in `KeyMachine::calculate_share`, aborting DKG - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Analogous to the Debita `getDataByReceipt()` unhandled-nonexistent-token revert, PedPoP's round-2 handler silently tolerates a participant who skipped round 1 (missing commitments) but then performs an unchecked `HashMap` index on `self.commitments[&l]` when that same participant sends a round-2 secret share. The missing-state lookup panics instead of returning a `PedPoPError`, permanently aborting the victim's `KeyMachine` and the key-generation attempt, with no attributable blame.

### Finding Description
In `SecretShareMachine::verify_r1`, commitments are collected per participant, but a participant absent from `commitment_msgs` is silently skipped rather than aborted:

```rust
for l in self.params.all_participant_indexes() {
  let Some(msg) = commitment_msgs.remove(&l) else { continue };
``` [1](#0-0) 

Consequently the returned `commitments` map may legitimately lack entries for valid `Participant` indexes `1..=n`.

In `KeyMachine::calculate_share`, the inbound `shares` map is validated only against `all_participant_indexes()` (key validity/presence), not against the `commitments` map built in round 1:

```rust
validate_map(&shares, &self.params.all_participant_indexes().collect::<Vec<_>>(), self.params.i())?;
``` [2](#0-1) 

Then each sender's share is verified against their commitments via a direct index:

```rust
share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
``` [3](#0-2) 

If a participant `l` never submitted round-1 commitments (skipped via `continue`) but submits a round-2 `EncryptedMessage<C, SecretShare>` to the victim, `self.commitments[&l]` panics (`HashMap` index on absent key). The same unguarded lookup exists in `BlameMachine::blame_internal` (`self.commitments[&sender]`), so a blame accusation naming such a sender also panics rather than resolving fault.

This mirrors the Debita root cause exactly: a legitimate earlier transition (absent round-1 message / receipt burn) leaves state absent, and a later unconditionally-indexed lookup reverts the entire claim/verification path instead of handling the missing case.

### Impact Explanation
`calculate_share` consumes `self` and panics mid-loop after partially mutating `self.secret`. The victim cannot retry the attempt with that machine, cannot produce a blame proof (the panic bypasses `PedPoPError::InvalidShare` and the `blames` map entirely), and the DKG attempt aborts with no faulty party identifiable. A single misbehaving or merely offline-in-round-1 participant can thus deny completion of key generation for every honest participant — the Serai analog of "lenders and borrowers permanently unable to claim", i.e., a liveness/funds-locking failure rather than a clean, blamable abort.

### Likelihood Explanation
Reachable by an unprivileged DKG participant using only public inputs: they simply withhold their `EncryptionKeyMessage<C, Commitments>` in round 1 (which honest code explicitly tolerates via `continue`) and then deliver an `EncryptedMessage<C, SecretShare>` in round 2 — bytes fed to the public `calculate_share` API. No malformed encoding, collusion, or validator compromise is needed; it can also trigger accidentally if a round-1 message is dropped but the round-2 share arrives.

### Recommendation
In `KeyMachine::calculate_share`, treat a sender missing from `self.commitments` as a fault instead of indexing: e.g., `let Some(commitments) = self.commitments.get(&l) else { Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })? };`. Alternatively, tighten `verify_r1`/`validate_map` so a missing commitments message aborts round 1 rather than being skipped, keeping the two rounds' participant sets consistent. Apply the same `.get()`-based handling to `self.commitments[&sender]` in `BlameMachine::blame_internal`.

### Proof of Concept
Conceptual (library-level): instantiate a `PedPoPMachine`/`SecretShareMachine` for participant set `{1,2,3}` as participant 2. In round 1, pass `generate_secret_shares` a `commitment_msgs` map containing only participant 3's `EncryptionKeyMessage` (omit participant 1). It succeeds via the `continue` path. In round 2, pass `calculate_share` a `shares` map containing `EncryptedMessage` entries from both 1 and 3 (participant 1's entry being any `EncryptedMessage` whose `SecretShare` bytes decrypt to a valid `C::F` — obtainable by encrypting an arbitrary scalar share under the ECDH key derived from participant 1's encryption key). `validate_map` accepts the map, and `self.commitments[&Participant(1)]` panics at pedpop/src/lib.rs:490 instead of returning `PedPoPError`, aborting the machine. I was unable to fully execute this PoC (no test harness run in this environment), but the code path — skipped insert at line 314 → missing map key → unchecked index at line 490 — is confirmed by inspection.
