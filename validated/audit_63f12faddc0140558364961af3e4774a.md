### Title
Permissionless forced-claim via `MasterMagpie.multiclaimFor` locks in vlMGP reward forfeiture at attacker-chosen timing - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie.multiclaimFor` has no access control tying the caller to `_account`, and its `_rewardTokens` argument is fully attacker-controlled, allowing an unprivileged caller to force any victim's `vlMGPBaseRewarder` rewards to be realized at a timing of the attacker's choosing. Because the forfeiture percentage in `vlMGPBaseRewarder._calExpireForfeit` is computed from the victim's *current* `getRewardablePercentWAD`, forcing the claim while the victim's ratio is low permanently locks in a larger forfeiture than the victim would have incurred by waiting/relocking before claiming themselves.

### Finding Description
`multiclaimFor` is `external` with no `onlyX` modifier and sets both `_user` and `_receiver` to the attacker-supplied `_account`: [1](#0-0) 

By passing `_rewardTokens[i] = []` for the vlMGP pool, `_claimBaseRewarder` takes the "claim all" branch, calling `rewarder.getReward(_account, _receiver)`: [2](#0-1) 

`vlMGPBaseRewarder.getReward`/`_sendReward` computes forfeiture at claim time using the account's *current* lock state, not a value fixed at accrual time, and zeroes `userRewards` regardless: [3](#0-2) [4](#0-3) 

The forfeiture ratio comes from `VLMGP.getRewardablePercentWAD`, which depends on how much of the account's vlMGP is fully locked vs. in cooldown/unlocked at the moment of the call: [5](#0-4) [6](#0-5) 

Because `getReward` is guarded only by `onlyMasterMagpie` (satisfied since the call is routed through `MasterMagpie`), and `multiclaimFor` itself has no restriction on `msg.sender` vs `_account`, any address can call `masterMagpie.multiclaimFor([vlmgp], [[]], victim)` at will. This forces realization (and thus forfeiture calculation) of the victim's pending vlMGP rewards at a moment the victim did not choose — e.g., right after the victim starts an unlock (lowering their `fullyInLock` share) but before they've had a chance to re-lock/increase their locked balance to raise `getRewardablePercentWAD` back up. The forfeited amount is redistributed pro-rata to all current vlMGP stakers via `_queueNewRewardsWithoutTransfer`, so an attacker who also holds vlMGP captures a slice of the victim's forced forfeiture: [7](#0-6) 

`userRewards[_rewardToken][_account]` is zeroed once sent, so the victim permanently loses the option of waiting to relock before claiming to avoid/reduce that forfeiture on the already-accrued tranche — this loss is not recoverable by the victim afterward.

Existing guards (`whenNotPaused`, `onlyMasterMagpie`, `updateReward`) do not prevent this because they only enforce that the call route through `MasterMagpie` and update reward indexes correctly; none of them restrict who may trigger the claim on behalf of `_account`.

### Impact Explanation
This causes a permanent, quantifiable loss of unclaimed yield for the victim: the forfeited portion (computed via `_calExpireForfeit`) is redistributed to other vlMGP stakers rather than being retained by the victim, and the victim cannot undo this once `getReward` executes. An attacker who is itself a vlMGP staker directly benefits from a share of the redistributed forfeiture, constituting value extraction from the victim without consent. This matches the "theft or permanent freezing of unclaimed yield" impact class. The magnitude scales with the victim's pending reward balance and the depth of their current unlock/cooldown at the time of the forced call.

### Likelihood Explanation
The precondition is only that the victim has a non-trivial unlocked/cooldown position (i.e., `getRewardablePercentWAD(_account) < 1e18`) and unclaimed vlMGP-pool rewards pending. No special capital, privileged role, or complex setup is required — the attacker simply calls a public, unauthenticated function (`multiclaimFor`) with attacker-chosen empty reward-token subarrays. It is trivially repeatable against any victim who has started an unlock (a normal, common action, as seen in `VLMGP.startUnlock` and `mWomSV.unlock`, both of which themselves call `multiclaimFor` for the caller), and can be front-run/monitored via mempool watching to catch victims at their most unfavorable `getRewardablePercentWAD` window.

### Recommendation
Restrict `multiclaimFor` so that only `msg.sender == _account`, or an explicitly authorized operator/contract acting for `_account` (analogous to `multiclaimOnBehalf`'s `_onlyCompounder` restriction), can trigger claims for a given account. Alternatively, if permissionless "claim for" behavior is intentionally kept for UX/keeper reasons, decouple the forfeiture calculation from the caller-controlled timing — e.g., snapshot/accrue the forfeiture ratio continuously per unit of reward accrued (rather than recomputed wholesale at claim time), so that forcing an early claim cannot retroactively worsen the effective forfeiture rate on already-accrued rewards.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder` with a reward token queued via `queueMGP`/`queueNewRewards`.
2. Victim locks MGP, accrues vlMGP-pool rewards over time (`queueNewRewards` called by an authorized manager), then calls `VLMGP.startUnlock` for a portion of their lock (lowering `getRewardablePercentWAD(victim)`).
3. Scenario A (baseline): victim waits, relocks additional MGP to restore `getRewardablePercentWAD(victim)` to near 1e18, then calls `multiclaimFor`/`multiclaimSpec` themselves — record `forfeitAmount_A` (expect ~0 via the 0.1% dust threshold).
4. Scenario B (attack): immediately after `startUnlock` (before victim relocks), an unrelated attacker address (holding some vlMGP itself) calls `masterMagpie.multiclaimFor([vlmgpAddress], [[]], victim)` — record `forfeitAmount_B` from the emitted `ForfeitRewardAdded`/`RewardPaid` events.
5. Assert `forfeitAmount_B > forfeitAmount_A` for the same accrued reward amount, and assert `userRewards[rewardToken][victim] == 0` after Scenario B (victim can no longer avoid the forfeiture by relocking).
6. Assert the attacker's own vlMGP share subsequently entitles them to a nonzero portion of the forfeited amount via `rewardInfo.rewardPerTokenStored` increase, demonstrating value transfer from victim to attacker.

        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
