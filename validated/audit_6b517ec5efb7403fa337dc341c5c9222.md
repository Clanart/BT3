Audit Report

## Title
Unprivileged `DepositDelegatorRewards` griefing permanently locks vote-account funds when the target has zero delegated stake - ([File: programs/vote/src/vote_state/mod.rs])

## Summary
`deposit_delegator_rewards` (SIMD-0123) requires only that the *source* lamport-donor sign; it performs no check that the caller is related to the target vote account, allowing anyone to bump an arbitrary vote account's `pending_delegator_rewards` field. [1](#0-0)  `withdraw()` then treats `pending_delegator_rewards` as an untouchable reserve, refusing to fully close the account while it is nonzero and capping partial withdrawals to `lamports - pending_delegator_rewards - rent_exempt_minimum`. [2](#0-1)  The only mechanism that reduces this value is `calculate_block_reward`, which is a hard no-op whenever the vote account's `total_active_stake == 0`, so a donation to a vote account with no delegated stake poisons the reserve indefinitely. [3](#0-2) 

## Finding Description
`deposit_delegator_rewards` verifies only `source_address` as a signer and unconditionally calls `add_pending_delegator_rewards`, which merely checks for `u64` overflow before incrementing the field — no relationship to the vote account's withdraw authority or its stake-delegation status is checked. [4](#0-3) [5](#0-4)  The `withdraw` instruction subsequently blocks full closure whenever `pending_delegator_rewards > 0`, and, for partial withdrawals, requires `remaining_balance >= rent_exempt_minimum + pending_delegator_rewards`. [6](#0-5)  This is confirmed directly by the existing test suite, which shows a full-close attempt failing with `InstructionError::InsufficientFunds` while `pending_delegator_rewards > 0`, and succeeding only after it is cleared to zero. [7](#0-6) [8](#0-7)  The sole decrement path, `calculate_block_reward`, returns `0` whenever `total_active_stake == 0` for that vote account in the reward epoch, meaning a vote account with no delegated stake (a newly created account, or one whose stake has fully deactivated) never receives any reward distribution to unwind the poisoned reserve. [9](#0-8) 

The code and tests fully substantiate the claim's mechanics: an unrelated signer can deposit as little as 1 lamport into any vote account, permanently increasing `pending_delegator_rewards`, and that reserve amount becomes stuck (unwithdrawable, and blocking full account closure) unless/until the vote account accrues nonzero delegated stake and receives enough block-revenue-sharing distributions to zero it out.

## Impact Explanation
The impact is a fund-lock/loss-of-availability bug reachable by any unprivileged signer of a funded system account — no privileged, leaked-key, or malicious-validator assumption is required. [4](#0-3)  The concrete corrupted value is the vote account's `pending_delegator_rewards` field, which the withdraw-authority-gated `withdraw()` instruction relies on as an accounting invariant to bound withdrawable lamports. [2](#0-1)  The amount permanently locked is bounded by the attacker's deposit (as small as 1 lamport, or larger if they choose), not necessarily the account's full balance — the withdrawer can still withdraw everything down to `rent_exempt_minimum + pending_delegator_rewards`, but can never fully close the account or reclaim that last reserve while stake stays at zero.

## Likelihood Explanation
The claim itself, and the underlying feature (`SIMD-0123: Block Revenue Sharing`), is gated behind the `block_revenue_sharing` feature flag, which is declared with a clearly non-mainnet placeholder ID (`B1ockRevenueSharing111111111111111111111111`) and is one of several features "that have not been activated on all clusters" per the `FeatureSnapshot` documentation. [10](#0-9) [11](#0-10)  This means `DepositDelegatorRewards` is not currently reachable on any live cluster; the vulnerability only becomes live once this and related SIMD-0123/0185/0232/0291 features are activated in the future. The exploit condition (`total_active_stake == 0`) most reliably and repeatably occurs for freshly created vote accounts before any stake delegation — i.e., an attacker griefing the account before its intended first use, which is a front-run-style timing dependency on the target's lifecycle rather than a strictly always-exploitable condition against any arbitrary active validator vote account.

## Recommendation
Restrict `DepositDelegatorRewards` so only the vote account's authorized withdrawer (or another explicitly authorized party) can increase `pending_delegator_rewards`, or require the deposit to be validated against the vote account currently having nonzero delegated/active stake before accepting it. Alternatively, provide an explicit, authorized mechanism for the withdrawer to reclaim `pending_delegator_rewards` when the account has no active stake, so the reserve cannot be poisoned indefinitely by an unrelated third party.

## Proof of Concept
1. Create a V4 vote account `V` with `pending_delegator_rewards == 0` and zero currently-delegated active stake. [12](#0-11) 
2. As an unrelated signer `S`, submit `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` against `V`; this succeeds and sets `V.pending_delegator_rewards = 1`. [13](#0-12) 
3. `V`'s legitimate authorized withdrawer attempts `Withdraw(full_balance)`; this fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0`. [7](#0-6) 
4. Because `V` has no active delegated stake, `calculate_block_reward` returns `0` every epoch, so `pending_delegator_rewards` never decreases and the last reserve amount can never be reclaimed while stake remains zero. [3](#0-2)
