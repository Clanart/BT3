### Title
`EvmHost.dispatch()` and `fundRequest()` swap unspent native ETH into fee tokens but never refund the leftover to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and convert it into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, but none of them capture the `amounts[]` array returned by the router or refund any leftover ETH to the caller, unlike the app-layer intent contracts in this same repo which explicitly do this pattern correctly.

### Finding Description
In `evm/src/core/EvmHost.sol`, the three payable entry points that accept native ETH for fee payment all follow the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

Each calls `swapETHForExactTokens{value: msg.value}(fee/amount, path, address(this), block.timestamp)` and discards the return value. `UniswapV2Router02.swapETHForExactTokens` only consumes the ETH needed to produce exactly `amountOut` tokens and refunds any leftover ETH — but that refund goes back to `msg.sender` of the router call, which in this context is `EvmHost` itself (`address(this)`), not the original external caller who funded the transaction with `msg.value`.

This is the exact analog of the reported `SwapRouter` bug: a contract that receives native ETH up-front for a swap whose actual cost is determined later, and which fails to return the unspent portion to the payer. The codebase's own app-layer contracts demonstrate the correct fix pattern is already known and applied elsewhere: [4](#0-3) [5](#0-4) 
Here `amounts[0]` (actual ETH spent) is captured and `msgValue -= amounts[0]` is refunded to the caller at the end. `EvmHost.dispatch()`/`fundRequest()` lack this accounting entirely.

### Impact Explanation
Any module (e.g. `IntentGatewayV2`, `ExtrinsicIntents`, or any third-party `IApp` integrator) that calls `IDispatcher(host).dispatch{value: msg.value}(...)` or `fundRequest{value: ...}(...)` with more native ETH than the swap actually requires (which is routine, since callers estimate the price with slippage buffers, and `swapETHForExactTokens` only consumes the exact amount needed) permanently loses the difference. That ETH lands in `EvmHost`'s own balance with no tracking, no owner, and no path to reclaim it, since `EvmHost` has no logic that accounts for or forwards this stray native balance back to payers. This is a direct, permanent loss of user/module funds through the primary public dispatch entrypoints of the bridge — the same fund-loss class as the referenced report, but at the core host layer rather than the DEX-router layer.

### Likelihood Explanation
High. This triggers on ordinary usage: any caller (unprivileged, no relayer/prover/admin needed) that overestimates native ETH for `dispatch()`/`fundRequest()` — which is the expected safe practice since exact AMM output pricing can't be known precisely at call time — loses the excess on every such call. It requires no malicious peer or adversarial precondition; it is a pure logic gap in `EvmHost`'s payable dispatch functions.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` to `_msgSender()` (or a designated `payer`), mirroring the pattern already implemented in `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`.

### Proof of Concept
1. Caller `A` (e.g. `IntentGatewayV2.fillOrder` or a direct `IApp` integrator) calls `EvmHost.dispatch{value: 1 ether}(DispatchPost{fee: X, ...})`, where the true ETH cost to acquire `X` fee tokens via Uniswap is only 0.1 ETH.
2. `EvmHost.dispatch()` executes `swapETHForExactTokens{value: 1 ether}(X, path, address(this), block.timestamp)`.
3. Uniswap consumes 0.1 ETH, refunds 0.9 ETH back to `msg.sender` of the swap call — which is `EvmHost`, not `A`.
4. `EvmHost.dispatch()` returns without forwarding any of the 0.9 ETH back to `A`; `A`'s 0.9 ETH is now stranded in `EvmHost`'s balance, permanently lost to `A`.
