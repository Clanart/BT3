### Title
Front-runnable instant reward-per-share accrual lets a zero-duration `vlMGP` locker steal a pro-rata share of newly queued rewards - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder` (and the shared `BaseRewardPoolV2`/`mWOMSVBaseRewarder` pattern) applies incoming rewards as an instantaneous, non-time-weighted bump to `rewardPerTokenStored`, computed against `totalStaked()` at the exact moment `queueNewRewards`/`_queueNewRewardsWithoutTransfer` executes. An attacker can front-run a large reward top-up (or a victim's forfeit-triggering claim) by locking MGP just beforehand, since `MasterMagpie._deposit` -> `_harvestBaseRewarder` -> `updateFor` only checkpoints `userRewardPerTokenPaid` at the pre-increase value, and their freshly locked (not-in-cooldown) balance is exempt from `_calExpireForfeit`'s penalty.

### Finding Description
`vlMGPBaseRewarder.queueNewRewards` / `_queueNewRewardsWithoutTransfer` add the full reward amount to `rewardPerTokenStored` in one shot, weighted by `totalStaked()` at call time, with no per-second streaming/duration mechanism: [1](#0-0) .

When an attacker locks MGP via `VLMGP.lock()/lockFor()`, this reaches `MasterMagpie._deposit`, which calls `_harvestBaseRewarder` -> `rewarder.updateFor(_account)` -> `_updateFor`, which snapshots `userRewardPerTokenPaid[token][account] = rewardPerToken(token)` at the *current* (pre-increase) value before the attacker's `user.amount` is bumped: [2](#0-1) [3](#0-2) .

If a large `queueNewRewards` (or a victim's `unlock()`/claim-triggered forfeit re-queue via `_sendReward`/`_queueNewRewardsWithoutTransfer`) lands afterward in the same or a subsequent block, `rewardPerTokenStored` jumps. On the attacker's next `earned()`/`getReward()` call, `_earned` computes `userShare * (rewardPerToken - userRewardPerTokenPaid)`, which now includes the full post-increase delta multiplied by the attacker's balance, even though that balance existed for effectively zero time before the reward was queued: [4](#0-3) .

Critically, freshly-locked balance is not in a cooldown slot, so `_calExpireForfeit` — which computes `rewardablePercentWAD` based on `amountInCoolDown` fractions — imposes little to no forfeit penalty on this instantly-earned reward, unlike balances mid-unlock: [5](#0-4) [6](#0-5) .

One correction to the stated exploit path: `MasterMagpie.depositVlMGPFor` is gated by an internal-only modifier and is not directly callable by an arbitrary EOA; the attacker must route through `VLMGP.lock()`/`lockFor()`, which internally invokes it. The underlying reward-checkpoint race is otherwise reachable exactly as described. No `nonReentrant`/`whenNotPaused` guard mitigates this since it is a legitimate sequential call ordering (front-run), not reentrancy.

### Impact Explanation
This is theft of unclaimed yield: capital that should accrue only to lockers who held stake while the reward was earned is instead diverted, pro-rata, to a locker who deposited immediately before the reward was queued and withdraws immediately after, with no meaningful holding-duration cost. This matches the "theft of unclaimed yield" Immunefi impact class for the `vlMGP` reward pool.

### Likelihood Explanation
Requires: (1) attacker holds/acquires MGP to lock (real capital, not flash-loanable collateral since `lock()` performs a real token transfer and receipt-token style tracking is internal to `MasterMagpie`/`VLMGP`, not an externally transferable LP token), (2) mempool visibility of a pending large `queueNewRewards`/forfeit-triggering transaction, and (3) the ability to land a lock transaction before it in the same or adjacent block. This is standard MEV/front-running, feasible and repeatable whenever large reward top-ups are visible pre-confirmation; profitability scales with the size of the queued reward relative to gas/capital-lockup cost.

### Recommendation
Move to a time-weighted/streamed reward distribution (e.g., `rewardRate` over a fixed `rewardsDuration`, Synthetix-style `notifyRewardAmount`) instead of an instantaneous `rewardPerTokenStored` bump, so new depositors only accrue a share proportional to elapsed time within the distribution window. Alternatively, checkpoint `_updateFor` for the *previous* holders of the pool right before applying `queueNewRewards`, and/or impose a minimum bonding/lock duration before newly deposited balance becomes eligible for `earned()` accrual on already-queued-but-unclaimed rewards.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder`; register `vlMGP` pool with the rewarder.
2. Seed an existing long-term locker (`victim`) who locks MGP well before the test block and never touches rewards.
3. In a single block: (a) attacker calls `VLMGP.lockFor`/`lock` with a modest MGP amount (triggers `MasterMagpie._deposit` -> `updateFor` checkpoint at pre-increase `rewardPerTokenStored`); (b) a reward manager calls `vlMGPBaseRewarder.queueNewRewards(largeAmount, rewardToken)`.
4. Next block: attacker calls `MasterMagpie` claim path -> `vlMGPBaseRewarder.getReward(attacker, attacker)`.
5. Assert `IERC20(rewardToken).balanceOf(attacker) > 0` and that the received amount is proportional to `attacker.balance / totalStaked()` at the time of `queueNewRewards`, despite `block.timestamp` of lock == `block.timestamp` of claim (zero elapsed staking time), and that `_calExpireForfeit` returned near-zero forfeit for the attacker (since none of their balance was in cooldown), while confirming this dilutes the effective share otherwise available to `victim`.

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        uint256 userVlMGPAmount = balanceOf(_account);

        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
