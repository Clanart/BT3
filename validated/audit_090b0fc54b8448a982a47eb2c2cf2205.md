### Title
Host-parsing discrepancy in `deduced_phishing_attack?` allows backslash/userinfo bypass of the trusted-domain check, enabling attacker-controlled OAuth redirect - ([File: app/controllers/shopify_app/callback_controller.rb])

### Summary
`CallbackController#deduced_phishing_attack?` validates only the `host` component extracted by Ruby's `URI()` from the fully attacker-controlled, base64-decoded `host` param, while the final redirect is built from the *entire* raw `decoded_host` string. Because Ruby's `URI` parser and browsers disagree on how backslashes and userinfo (`user@host`) are delimited, an attacker can craft a `host` value whose `URI(decoded_host).host` resolves to a trusted `*.myshopify.com` domain (passing `ShopifyApp::Utils.sanitize_shop_domain`) while a real browser parses the same string's authority as an attacker-controlled domain.

### Finding Description
`decoded_host` is derived directly from the attacker-controlled base64 `host` query param via `ShopifyAPI::Auth.embedded_app_url(params[:host])` [1](#0-0) . `redirect_to_app` then builds the redirect target as `"#{decoded_host}#{return_to}"` and only guards it with `deduced_phishing_attack?`, which checks `ShopifyApp::Utils.sanitize_shop_domain(URI(decoded_host).host)` [2](#0-1) .

Ruby's `URI` (unlike browsers, which follow the WHATWG URL spec) does not normalize backslashes to forward slashes and splits userinfo/host purely on the last `@` before the path. This means a decoded host string such as `evil.com\@victim.myshopify.com/admin/apps/key` is parsed by `URI()` as userinfo `evil.com\` and host `victim.myshopify.com` — passing `sanitize_shop_domain` — but a real browser normalizes the backslash to `/` first, producing `evil.com/@victim.myshopify.com/admin/apps/key`, whose actual authority is `evil.com`. The `Location` header sent to the browser is built from the raw string, so the browser navigates to `evil.com`, not the validated `victim.myshopify.com`.

Critically, the codebase already recognizes and mitigates this exact bypass class in a sibling code path, `ShopifyApp::EmbeddedApp#safe_embedded_app_url` / `deduced_phishing_attack?`, which explicitly rejects backslashes and userinfo before validating the host [3](#0-2) , and this protection is verified by tests such as "Redirect to root URL when decoded host contains a backslash and userinfo" [4](#0-3) . `CallbackController#deduced_phishing_attack?`, however, has no equivalent `unsafe_embedded_host?`/backslash/control-character check — it relies solely on `URI(decoded_host).host`, which does not reflect real browser parsing semantics [5](#0-4) . The existing test suite for `CallbackController` only covers a plain non-tricky evil host (no `@`/backslash), so this discrepancy is untested and unmitigated there [6](#0-5) .

Note: `ShopifyAPI::Auth.embedded_app_url` itself lives outside this repo (in the `shopify_api` gem), so the exact byte-for-byte transformation it applies to the decoded host before this check runs could not be fully verified from this repo's index; the vulnerability is demonstrated at the level of the `URI()`-vs-browser parsing discrepancy that `deduced_phishing_attack?` relies on, which is unaffected by whatever prefixing `embedded_app_url` performs.

### Impact Explanation
An attacker can cause the post-OAuth callback to issue a redirect (`Location` header, `allow_other_host: true`) whose real navigation target is an attacker-controlled origin, while `deduced_phishing_attack?` reports "not a phishing attack." Since `redirect_to_app` executes after `save_session`/`update_rails_cookie`, and `return_to` (attacker-influenced path fragment appended after the fooled host) is concatenated onto this same URL, sensitive data placed into the redirect path/query (e.g., `return_to` values, tokens embedded by the app in return URLs) can be sent to the attacker's domain. This matches Shopify's "Open Redirect" / phishing impact class enabling merchant credential or token exfiltration via a crafted OAuth callback link.

### Likelihood Explanation
Exploitation requires only that the attacker get a victim merchant to click a crafted `/auth/shopify/callback?host=<payload>&shop=<real-shop>` link (or otherwise trigger this callback), which is a normal unauthenticated GET request — no secrets or elevated privileges are required. The `host` param is fully attacker-supplied base64, so building the discrepant payload is straightforward and repeatable.

### Recommendation
Apply the same input-sanitization guard used in `ShopifyApp::EmbeddedApp` (`unsafe_embedded_host?`, rejecting backslashes, control characters, and `@`/userinfo in the authority) to `CallbackController#deduced_phishing_attack?` before/along with the `URI(decoded_host).host` check, or better, parse `decoded_host` with the same WHATWG-URL-compliant logic used elsewhere and validate the entire authority string (not just the parsed `.host`) against the trusted domain allowlist.

### Proof of Concept
```ruby
test "#callback redirects to root when decoded host contains backslash/userinfo trick" do
  mock_oauth
  evil_host = "evil.com\\@#{SHOP_DOMAIN}/admin"
  encoded_host = Base64.strict_encode64(evil_host)
  hacker_params = @callback_params.merge(host: encoded_host)

  get :callback, params: hacker_params

  # Currently FAILS: deduced_phishing_attack? passes because URI(decoded_host).host == SHOP_DOMAIN,
  # so redirect is NOT sent to root_url, and Location header's real browser-parsed
  # authority is "evil.com".
  assert_redirected_to ShopifyApp.configuration.root_url
end
```
Expected (secure) behavior: redirect to `ShopifyApp.configuration.root_url`. Actual behavior: redirect Location is built from the raw `decoded_host`, whose true (browser-parsed) authority is `evil.com`, despite `deduced_phishing_attack?` returning `false`.

      if ShopifyAPI::Context.embedded?
        return_to = session.delete(:return_to)

    def fully_formed_url?(return_to)
      uri = Addressable::URI.parse(return_to)
      uri.present? && uri.scheme.present? && uri.host.present?
    end

    def safe_embedded_app_url(host)
      decoded_host = Base64.decode64(host.to_s)
      return if deduced_phishing_attack?(decoded_host)

      ShopifyAPI::Auth.embedded_app_url(Base64.strict_encode64(decoded_host))
    end

    def deduced_phishing_attack?(decoded_host)
      sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(decoded_host) unless unsafe_embedded_host?(decoded_host)
      if sanitized_host.nil?
        message = "Host param for redirect to embed app in admin is not from a trusted domain, " \
          "redirecting to root as this is likely a phishing attack."
        ShopifyApp::Logger.info(message)
      end
      sanitized_host.nil?
    end

    def unsafe_embedded_host?(decoded_host)
      return true if decoded_host.empty? || !decoded_host.valid_encoding?
      return true if unsafe_embedded_host_characters?(decoded_host)

      embedded_host_authority(decoded_host).include?("@")
    end

    def unsafe_embedded_host_characters?(decoded_host)
      decoded_host.each_char.any? do |character|
        character_code = character.ord
        character_code <= 0x20 || character_code == 0x7f || character == "\\"
      end
    end

    def embedded_host_authority(decoded_host)
      decoded_host.sub(%r{\Ahttps?://}i, "").split(%r{[/?#]}, 2).first.to_s
    end
