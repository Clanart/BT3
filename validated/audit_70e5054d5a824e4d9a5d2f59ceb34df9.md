Confirmed: `UPGRADEABLE_LOADER_COMPUTE_UNITS` is a fixed **2,370 CU** flat charge for every `bpf_loader_upgradeable` instruction regardless of type or program size [1](#0-0) , while the permissionless `ExtendProgram` path (`check_authority=false`) unconditionally invokes the `deploy_program!` macro — a full ELF re-load, `RequisiteVerifier` verification, and JIT-style reload of the *entire* program — every time it is called [2](#0-1) [3](#0-2) .

### Title
Permissionless `ExtendProgram` instruction lets any account force costly full-program re-verification/recompilation and reset a program's `ProgramData.slot` for a flat, size-independent compute charge - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The external report's bug class is "unsolicited/unauthenticated modification of another party's state via a caller-suppliable target, which resets state that other legitimate flows depend on." The `bpf_loader_upgradeable::ExtendProgram` instruction is the closest unprivileged-user analog reachable in-scope (BPF loader path): it takes a program/programdata account that anyone can name, requires **no signature from the program's upgrade authority**, and as a side effect fully re-verifies/recompiles the program and rewrites the `ProgramData.slot` field to the current clock slot.

### Finding Description
`common_extend_program` is invoked from `UpgradeableLoaderInstruction::ExtendProgram` with `check_authority = false` [2](#0-1) . Inside `common_extend_program`, the `check_authority` branch that verifies the authority key and signature is explicitly skipped for this instruction variant [4](#0-3) , meaning **any account** can submit this instruction for **any** upgradeable program's `ProgramData` account, needing only to supply the (optional) payer for rent.

Regardless of who calls it, the instruction unconditionally:
1. Extends the account's data length [5](#0-4) .
2. Fully reloads, verifies (`RequisiteVerifier`), and recompiles the program via the `deploy_program!` macro/`deploy_program` function, which parses the ELF, registers syscalls, and reloads the executable — the most compute-expensive operation in the loader [6](#0-5) [7](#0-6) .
3. Overwrites `UpgradeableLoaderState::ProgramData.slot` with the current `clock_slot` [8](#0-7) , exactly mirroring the pattern in the esFLUO report where an unauthenticated call rewrites a timestamp field that other logic (deployment cooldowns, delay-visibility windows in the program cache) depends on.
4. Stores a "modified" cache entry, forcing a `DelayVisibility` tombstone for the program in the fork/cache for at least the current slot, per the program-cache visibility rules documented in `program_cache_entry.rs` [9](#0-8) .

The instruction's compute cost is charged as a fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS = 2_370` for the whole loader dispatch [1](#0-0) , independent of the size of the program being re-verified/recompiled. There is a minimum extend size (`MINIMUM_EXTEND_PROGRAM_BYTES`, 10 KiB, added by SIMD-0431) and a one-extend-per-slot cooldown (`InvalidArgument` if `clock_slot == slot`) [10](#0-9) , but these limit *frequency*, not the *cost asymmetry*: a caller pays a flat, size-independent instruction fee/CU cost to force validators to fully re-verify and reload a program that may be arbitrarily large (up to `MAX_PERMITTED_DATA_LENGTH`), once per slot, for any upgradeable program on the network — without the program's owner's consent.

### Impact Explanation
This does not corrupt account data or escalate privileges, but it does let an unrelated, unprivileged actor:
- Force unsolicited, flat-fee-priced re-verification/recompilation work onto every validator processing the transaction for a program the caller does not own, once per slot per program, network-wide, for every upgradeable program in existence.
- Overwrite the `ProgramData.slot` field the true upgrade authority relies on, causing the program to be marked freshly "modified"/deployed at an attacker-chosen slot even though no real code change occurred, and forcing a `DelayVisibility` cache tombstone window that affects any transaction hitting the program during that slot.

This is analogous to the reported esFLUO griefing pattern (unauthenticated call resets a victim-relevant field others rely on), but the concrete, provable technical anchor in-scope is compute-cost asymmetry: fixed native-loader CU accounting vs. size-dependent, expensive re-verification/reload work triggered without the owner's permission.

### Likelihood Explanation
High reachability: `ExtendProgram` requires no privileged signer besides a payer (which can be the attacker itself, or omitted per `test_extend_program_without_payer`) [11](#0-10) , targets any existing upgradeable program's `ProgramData` account, and is fully exercised by existing tests confirming it succeeds without an authority account at all [12](#0-11) . The only throttle is the per-slot cooldown and the SIMD-0431 minimum-extend-size requirement, both of which cap frequency, not the underlying cost-per-call asymmetry.

### Recommendation
- Charge compute units for `ExtendProgram` (and any instruction that triggers `deploy_program!`) proportionally to the size of the programdata being reloaded/verified/compiled, rather than the flat `UPGRADEABLE_LOADER_COMPUTE_UNITS`.
- Consider whether `ProgramData.slot` should be updated at all for a pure-extend (no code change) operation, since it currently conflates "data length increase" with "new deployment," resetting state that downstream logic associates with an actual code upgrade.
- Re-evaluate whether unauthenticated `ExtendProgram` should require some minimal relationship to the program (e.g., only the current upgrade authority, or bounding to cases where extension is strictly necessary for a pending write), consistent with the original SIMD design intent, but hardened against pure griefing/cost-asymmetry abuse.

### Proof of Concept
1. Attacker identifies any upgradeable program `P` with `ProgramData` account not at `MAX_PERMITTED_DATA_LENGTH`.
2. Attacker submits `extend_program(P, Some(attacker_pubkey), MINIMUM_EXTEND_PROGRAM_BYTES)` signed only by the attacker as payer — no signature from `P`'s upgrade authority is required, per `common_extend_program`'s `check_authority = false` path [2](#0-1)  and confirmed by `test_extend_program` succeeding with just the payer keypair [13](#0-12) .
3. This forces a full `deploy_program!` reload/verify/compile of `P`'s entire ELF [6](#0-5)  and rewrites `ProgramData.slot` to the current slot [8](#0-7) , all charged at the flat 2,370 CU rate [1](#0-0) , independent of `P`'s actual size.
4. Attacker repeats once per slot (limited only by the one-extend-per-slot cooldown) against many/large upgradeable programs to impose compute-recompilation load on validators disproportionate to the fee paid.

Note: I could not fully verify from the index whether the transaction-level compute-budget/cost-model layer (outside `programs/bpf_loader`) applies any additional, separate accounting for ELF verification/compilation cost beyond the flat builtin-instruction CU value found here; the `cost-model` and `builtins-default-costs` crates only surfaced a single unrelated match each for this instruction and I was unable to open their full contents in this session. If a background Devin session is available, it would be worth confirming there whether any secondary cost accounting exists for `deploy_program!`-triggered reloads.

async fn test_extend_program() {
    let mut context = setup_test_context(LoaderV3Features {
        minimum_extend_program_size: false,
    })
    .await;
    let program_file = find_file("noop.so").expect("Failed to find the file");
    let data = read_file(program_file);
    let upgrade_authority = Keypair::new();

    let program_address = Pubkey::new_unique();
    let (programdata_address, _) = Pubkey::find_program_address(&[program_address.as_ref()], &id());
    add_upgradeable_loader_account(
        &mut context,
        &program_address,
        &UpgradeableLoaderState::Program {
            programdata_address,
        },
        UpgradeableLoaderState::size_of_program(),
        |_| {},
    )
    .await;
    let programdata_data_offset = UpgradeableLoaderState::size_of_programdata_metadata();
    let program_data_len = data.len() + programdata_data_offset;
    add_upgradeable_loader_account(
        &mut context,
        &programdata_address,
        &UpgradeableLoaderState::ProgramData {
            slot: 0,
            upgrade_authority_address: Some(upgrade_authority.pubkey()),
        },
        program_data_len,
        |account| account.data_as_mut_slice()[programdata_data_offset..].copy_from_slice(&data),
    )
    .await;

    let client = &mut context.banks_client;
    let payer = &context.payer;
    let recent_blockhash = context.last_blockhash;
    const ADDITIONAL_BYTES: u32 = 42;
    let transaction = Transaction::new_signed_with_payer(
        &[extend_program(
            &program_address,
            Some(&payer.pubkey()),
            ADDITIONAL_BYTES,
        )],
        Some(&payer.pubkey()),
        &[payer],
        recent_blockhash,
    );

    assert_matches!(client.process_transaction(transaction).await, Ok(()));
    let updated_program_data_account = client
        .get_account(programdata_address)
        .await
        .unwrap()
        .unwrap();
    assert_eq!(
        updated_program_data_account.data().len(),
        program_data_len + ADDITIONAL_BYTES as usize
    );
