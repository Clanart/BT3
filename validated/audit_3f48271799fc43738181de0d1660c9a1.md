Based on the investigation, I found a strong structural analog in `ledger/src/blockstore.rs`'s coding-shred insertion path. This mirrors the Gravity bug class exactly: misbehavior *evidence* is detected and even logged as "a potential slashing condition," but the code path that would actually forward that evidence into the node's duplicate/slashing pipeline is not exercised in one specific branch, silently dropping the evidence.

### Title
Erasure-config duplicate-leader evidence is dropped instead of routed to the duplicate/slashing pipeline when the original conflicting coding shred cannot be located - (File: `ledger/src/blockstore.rs`)

### Summary
In `check_insert_coding_shred`, when a leader emits two different erasure configurations for the same erasure set (a duplicate/misbehavior indicator explicitly flagged in the code as `"ToDo: This is a potential slashing condition"`), the function attempts to locate the conflicting coding shred via `find_conflicting_coding_shred` and, only if found, pushes a `PossibleDuplicateShred::ErasureConflict` onto `duplicate_shreds`. If the original shred cannot be located, the code simply logs an `error!` and returns `InsertCodingShredError::InvalidErasureConfig` without ever constructing the `PossibleDuplicateShred` evidence.

### Finding Description
The relevant branch is: [1](#0-0) 

When `find_conflicting_coding_shred` returns `Some`, the evidence is stored (`store_duplicate_slot`) and pushed into `duplicate_shreds` as a `PossibleDuplicateShred::ErasureConflict`, which is precisely the "evidence submission" mechanism analogous to Gravity's `MsgSubmitBadSignatureEvidence` — it is what ultimately reaches the handler (`run_check_duplicate` / `check_duplicate_shred`) that notifies the duplicate-consensus state machine (`duplicate_slots_sender`) and gossips the duplicate proof (`cluster_info.push_duplicate_shred`): [2](#0-1) 

However, when `find_conflicting_coding_shred` returns `None` — explicitly noted as happening "only ... in extreme cases where blockstore cleanup has caught up to the root" — the function only logs an `error!` message and returns an error, with **no** `PossibleDuplicateShred` ever constructed: [3](#0-2) 

The insertion is rejected (`Err(InsertCodingShredError::InvalidErasureConfig)`), so the malicious/duplicate shred does not get inserted, but the actual "evidence" that a leader misbehaved (produced conflicting erasure metadata for the same erasure set) never reaches:
- `store_duplicate_slot` (no persisted duplicate proof for that slot),
- the duplicate-consensus channel `duplicate_slots_sender` (no rollback/duplicate-fork handling triggered),
- gossip propagation via `cluster_info.push_duplicate_shred` (other validators never learn about it).

This is structurally the same class of bug as the Gravity report: a mechanism intended to record/report misbehavior evidence (`ErasureConflict` proof, analogous to `MsgSubmitBadSignatureEvidence`) exists in the type system (`PossibleDuplicateShred::ErasureConflict` variant, `check_duplicate_shred` handler for it) but the code path that should produce and forward that evidence is not exercised in the "can't find original shred" branch, silently discarding it instead of registering it for downstream handling.

### Impact Explanation
This weakens the disincentive against leader misbehavior via erasure metadata manipulation: if the historical shred used to establish an erasure config has already been cleaned up by blockstore compaction (the documented case), no duplicate-slot proof is stored, so other components (fork-choice duplicate handling, and gossip-based propagation of duplicate proofs to peers) never see it. This directly parallels the Gravity issue where validators had "no disincentive to attempt to collude" because the evidence mechanism could not be reached in practice.

### Likelihood Explanation
The comment itself states this happens "only in extreme cases where blockstore cleanup has caught up to the root," so the trigger condition is narrow (requires an already-old/near-root erasure set whose original coding shred has been purged before a conflicting one arrives) but is a real reachable code path with no compensating handling elsewhere, not merely a theoretical dead branch.

### Recommendation
When `find_conflicting_coding_shred` returns `None` in the erasure-config-mismatch branch, still construct and forward a duplicate-shred/slot report (e.g. mark the slot for duplicate/dead-slot handling and notify the duplicate-consensus channel) instead of only logging and returning an error, so that this misbehavior evidence is not silently dropped even when the exact conflicting original shred is unavailable.

### Proof of Concept
1. A leader for slot `S` emits a coding shred establishing erasure config `C1` for erasure-set `E`.
2. Blockstore cleanup catches up and removes the original coding shred(s) for `E` from the DB while the erasure meta for `E` is still tracked (edge case acknowledged in the code comment at `ledger/src/blockstore.rs:2757-2759`).
3. The same/colluding leader (or a replay/repair race) submits a second coding shred for `E` with a different erasure config `C2`.
4. `check_insert_coding_shred` detects `!erasure_meta.check_coding_shred(&shred)`, calls `find_conflicting_coding_shred`, which returns `None` because the original shred is gone.
5. Only `error!`/`warn!` logs are emitted; `duplicate_shreds` is never appended to, so `store_duplicate_slot` is never called for this event and no `PossibleDuplicateShred::ErasureConflict` is ever produced or forwarded to `run_check_duplicate`, `duplicate_slots_sender`, or gossip — the misbehavior evidence is lost.

fn run_check_duplicate(
    cluster_info: &ClusterInfo,
    blockstore: &Blockstore,
    shred_receiver: &Receiver<PossibleDuplicateShred>,
    duplicate_slots_sender: &DuplicateSlotSender,
    bank_forks: &RwLock<BankForks>,
) -> Result<()> {
    let (mut root_bank, migration_status) = {
        let bank_forks_r = bank_forks.read().unwrap();
        (bank_forks_r.root_bank(), bank_forks_r.migration_status())
    };
    let mut last_updated = Instant::now();
    let check_duplicate = |shred: PossibleDuplicateShred| -> Result<()> {
        if last_updated.elapsed().as_nanos() > root_bank.ns_per_slot {
            // Grabs bank forks lock once a slot
            last_updated = Instant::now();
            root_bank = bank_forks.read().unwrap().root_bank();
        }
        let shred_slot = shred.slot();
        let no_verify_chained_merkle_root = shred::filter::check_feature_activation_from_bank(
            &feature_set::alpenglow::id(),
            shred_slot,
            &root_bank,
        );

        let Some((shred1, shred2)) =
            check_duplicate_shred(blockstore, shred, no_verify_chained_merkle_root)?
        else {
            return Ok(());
        };

        if migration_status.should_respond_to_ancestor_hashes_requests(shred_slot) {
            // In alpenglow we store the duplicate block proofs in blockstore for the purposes of slashing,
            // however we do not need to propagate the duplicate proof through gossip.
            // We still propagate during the mixed migration epoch, to account for other nodes that are stuck
            // and require a duplicate proof to proceed
            cluster_info.push_duplicate_shred(&shred1, &shred2)?;
        }

        if !migration_status.is_alpenglow_enabled() {
            // The state machine can be exited as soon as alpenglow is enabled.
            // Notify duplicate consensus state machine. If channel is full we wait.
            duplicate_slots_sender.send(shred_slot)?;
        }

        Ok(())
    };
