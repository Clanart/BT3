### Title
Hookify security rules can be silently toggled off and take effect on the very next tool call, letting a compromised/rogue actor instantly disable blocking safety hooks with no confirmation step or grace period - (File: `plugins/hookify/core/config_loader.py`)

### Summary
The `hookify` plugin implements user-defined safety hooks (e.g. "block `rm -rf`") as mutable YAML frontmatter (`enabled`, `action`) inside `.claude/hookify.*.local.md` files. These files are re-read from disk on *every single tool invocation* with no staging, no confirmation dialog, and no grace period between a change and its effect. Anything capable of writing to that file (the agent itself via the `Edit` tool, a plugin/skill instruction, or injected content) can flip a `block` rule to `warn`/`enabled: false` and have the protection vanish for the immediately following dangerous command in the same turn - mirroring the reported DeFi bug class where a privileged actor mutates a safety-critical threshold with instant effect and no notice period for the party who relied on it.

### Finding Description
`load_rules()` globs `.claude/hookify.*.local.md` and parses `enabled`/`action` fresh on each `PreToolUse`/`PostToolUse`/`Stop` invocation: [1](#0-0) 

The `PreToolUse` hook script calls `load_rules()` immediately before evaluating the current tool call, so any rule-file edit is picked up on the *very next* tool use: [2](#0-1) 

The rule engine treats `action: block` rules as hard denials (`permissionDecision: "deny"`), i.e. these are meant to function as a genuine safety boundary, not just cosmetic warnings: [3](#0-2) 

Crucially, the plugin's own documentation and slash commands instruct the model to edit the `enabled`/`action` fields directly via the `Edit` tool, and explicitly advertise that there is no confirmation gate and no delay: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

This is structurally identical to the reported `VaultFacet.updateCollateralizationRatio` bug class: a single write from a semi-trusted party (there: the contract owner; here: the agent's own file-write capability, or any prompt/skill/plugin content that can trigger an `Edit` on `.claude/hookify.*.local.md`) instantaneously and unilaterally changes a protective threshold (`enabled`/`action`) that another party (the human user, who believes the "block dangerous rm" rule is active) is relying on, with no staged/pending state, no notification, and no grace period before the change takes effect - exactly the two missing controls (two-step update + grace period) the original report recommends adding.

### Impact Explanation
If the model is manipulated (e.g. via prompt injection from an untrusted file, malicious skill, or a compromised plugin) into disabling a `block`-type hookify rule (such as one preventing `rm -rf`, secret exfiltration commands, or credential access), the disablement takes effect immediately for the same session's subsequent tool calls. The user has no opportunity to review or approve the rule change before their safety net disappears, and the very next dangerous command can execute unblocked - an unauthorized local action / workspace compromise directly enabled by an instantaneous, unreviewed change to a security-relevant configuration value.

### Likelihood Explanation
Moderate. It requires the model to actually perform an `Edit` on the rule file, which itself would normally be subject to the standard Edit-tool permission prompt/allowlisting in most trust modes - so this is not a fully unauthenticated bypass. However, `/hookify:configure` and `/hookify` are first-party plugin commands that explicitly grant `Edit` in their `allowed-tools` frontmatter and are designed to make exactly this kind of change trivially and immediately, and the plugin's own docs advertise "no restart, no confirmation, effect on next tool use" as a feature. Any prompt-injection payload that gets the agent to run these flows, or to directly edit the `.local.md` file, achieves the bypass with a single write.

### Recommendation
Treat changes to `action: block` / `enabled` fields in hookify rule files as security-sensitive configuration changes rather than ordinary file edits:
- Require a distinct, explicit user confirmation (not just an ordinary Edit-tool prompt) whenever a `block`-type rule is being disabled or downgraded to `warn`.
- Introduce a short debounce/grace window between a rule-file change and it taking effect, and surface a visible notification to the user that a safety rule was just weakened, mirroring the "two-step change + grace period" recommendation from the source report.
- Consider caching rule state at session start and only reloading on an explicit, user-visible `/hookify reload` action, rather than re-reading from disk unconditionally on every tool call.

### Proof of Concept
1. A rule file `.claude/hookify.block-rm.local.md` exists with:
```
---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm\s+-rf
action: block
---
Blocked: dangerous rm -rf command.
```
2. Via prompt injection (e.g., content read from a file, or a malicious skill/plugin) the agent is instructed to run `/hookify:configure` (or directly `Edit` the file) to change `action: block` to `action: warn` or `enabled: true` to `enabled: false`.
3. Per `plugins/hookify/commands/configure.md` lines 92-113 / `plugins/hookify/README.md` lines 26-35, this change is documented to "apply immediately - no restart needed."
4. On the *very next* Bash tool call, `load_rules()` (`plugins/hookify/core/config_loader.py:198-226`) re-parses the file, `RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py:60-79`) no longer emits `permissionDecision: "deny"`, and `rm -rf ...` executes unblocked - with the user never having approved or even seen the rule-weakening change before impact.

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)
```
