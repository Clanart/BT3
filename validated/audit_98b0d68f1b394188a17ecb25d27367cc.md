## Title
Copilot merge-conflict resolution silently deletes/corrupts code when a conflicted file contains an unbalanced marker-like line - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot-assisted conflict resolution feature parses a conflicted file twice with two *different* algorithms: once to build the hunk list sent to the model (`extractConflictHunks`) and once to splice the model's per-hunk resolutions back into the original file (`reassembleResolvedFile`). The two parsers disagree on what counts as a "malformed" (unbalanced) conflict block. This lets a conflicted file that contains an unbalanced marker-like sequence cause `extractConflictHunks` to silently swallow real, well-formed hunks that follow it, while `reassembleResolvedFile` still walks over those swallowed hunks during the actual file rewrite. The count-based validation (`validateResolutionPaths`) checks the wrong (already-undercounted) hunk total, so it passes, and the reassembly step then removes the surviving hunks' content from the committed file without any error — exactly the "the value that was validated differs from the value actually used" pattern in the 1inch report.

### Finding Description
`extractConflictHunks` collects the "ours" side of a hunk in a loop that only breaks on a base marker (`|||||||`) or separator (`=======`) — it never checks for a theirs marker (`>>>>>>>`): [1](#0-0) 

If a conflict block has no `=======` separator (e.g. because the "ours"/"theirs" content itself already contains a line that looks like `<<<<<<<` or `>>>>>>>` — plausible in files that contain example diffs, chat transcripts, previous unresolved merges, etc., which is attacker-controlled content shipped in a fetched branch), this loop keeps consuming lines — including the literal `>>>>>>>` line and everything after it in the file — until it either finds a genuine separator/base marker or reaches end of file. Since no theirs-closing-marker check ever fires, `hunkEnd` stays `-1` and the block (plus everything it swallowed) is dropped via `continue`: [2](#0-1) 

Critically, this swallow can consume subsequent, perfectly well-formed conflict hunks later in the same file, so `extractConflictHunks` returns fewer hunks than physically exist on disk. As long as at least one valid hunk is found *before* the malformed block, the file is not skipped (`hunks.length === 0` check does not trigger) and is sent to Copilot with an undercounted hunk list.

`reassembleResolvedFile`, however, uses a different malformed-detection rule: it looks ahead for a separator anywhere before a theirs marker, and if either is missing it treats only the `<<<<<<<` line itself as regular content and resumes line-by-line scanning — meaning any well-formed hunks *after* the malformed block are still recognized and processed as hunks during reassembly: [3](#0-2) 

`validateResolutionPaths` only checks that the *count* of hunks Copilot returned matches `expectedHunkCounts` derived from `extractConflictHunks` — the already-undercounted number: [4](#0-3) 

This check passes because Copilot's response is consistent with what it was shown. But `reassembleResolvedFile` is run against the *original raw file content* (with all real hunks, including the ones `extractConflictHunks` swallowed), and it matches resolutions to hunks purely by array order (`hunkIndex`), not identity. Once `hunkIndex` reaches the (short) `hunkResolutions.length`, any further well-formed hunk encountered during reassembly is stripped of its markers but has nothing spliced in (`if (hunkIndex < hunkResolutions.length)` is false), silently deleting that hunk's content from the final file: [5](#0-4) 

The broken invariant is the same as in the 1inch report: a value (hunk count) is validated against an expectation that was computed from the *same untrusted/attacker-influenced input* using inconsistent logic, so the check passes even though the actual downstream operation uses a different, larger set of data — resulting in silent, unchecked loss/corruption of the final result.

### Impact Explanation
This causes silent corruption of what the user commits: code from one or more legitimately resolved conflict hunks is deleted from the file that Copilot reports as "fully resolved," with no error, warning, or unresolved-marker artifact left behind. The user reviews a summary/diff that (depending on UI trust in Copilot's `resolvedContent`) may not surface this, stages the file, and commits/pushes broken or truncated code. This falls squarely under "silent corruption of what the user commits or pushes" in the accepted impact list.

### Likelihood Explanation
Exploitation requires the attacker to control content in a branch, PR, or fork that the victim merges/rebases against and that they use the Copilot conflict-resolution feature on — i.e., "attacker controls a cloned/fetched repository," a valid unprivileged precondition. The trigger condition (a file containing an unbalanced `<<<<<<<`/`>>>>>>>`-looking line, or a stray leftover conflict marker from a prior unresolved merge that was accidentally committed) is a realistic, naturally occurring pattern in real repositories (embedded diffs, tutorials about Git conflicts, previously mis-resolved merges), not a contrived edge case, making this reasonably likely to occur in the wild once a repository containing such content is merged.

### Recommendation
Unify the conflict-block parsing logic used to build the Copilot context and the logic used to reassemble the resolved file so both agree on what constitutes a malformed/unbalanced conflict block (ideally share a single hunk-extraction function). Additionally, `reassembleResolvedFile` should match hunks by an explicit identifier/marker-offset pair captured during extraction rather than by positional order, and it should hard-fail (not silently drop content) if the number of hunks encountered during reassembly does not exactly match the number of resolutions provided.

### Proof of Concept
1. Attacker pushes a branch containing a file, e.g. `notes.md`, with content that legitimately conflicts with the victim's branch in two separate regions, but where the *first* conflicting region's "theirs" text already contains a literal line reading `>>>>>>> unrelated` (e.g., copy-pasted from a Git tutorial or leftover from an old unresolved merge) with no matching `=======`/`<<<<<<<` pair inside that block.
2. Victim fetches/merges the attacker's branch, producing a working-tree file with two real Git conflict blocks; the first one now contains the extra unbalanced marker-like line.
3. Victim opens GitHub Desktop's Copilot-assisted conflict resolution. `buildConflictContext` → `extractConflictHunks` scans the file: while collecting the first block's "ours"/"theirs" lines it never finds a `=======`, so it keeps consuming lines — including the second, entirely valid conflict block — until EOF, then discards the malformed first hunk via `continue` (`hunkEnd === -1`). Net effect: `extractConflictHunks` returns 0 or 1 hunks depending on exact layout, always fewer than the true 2 hunks in the file.
4. Because a nonzero number of hunks may remain (if a valid hunk preceded the malformed one), the file is sent to Copilot and gets, say, 1 hunk resolution back. `validateResolutionPaths` compares against `expectedHunkCounts` (also 1, from the same buggy extraction) — passes.
5. `reassembleResolvedFile(rawContent, hunkResolutions)` walks the *original* file: it correctly splices in the one resolution for the first hunk, then encounters the second, well-formed conflict block, recognizes it as a hunk, but `hunkIndex` (1) is not `< hunkResolutions.length` (1) — so its content is stripped of markers with nothing spliced in, silently deleting the entire second conflict region's content.
6. The resulting file is marked "resolved," staged, and committed by the victim with an entire section of legitimate code silently removed, with no error surfaced.
