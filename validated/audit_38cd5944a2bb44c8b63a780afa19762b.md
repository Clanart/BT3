### Title
Daemon WebSocket Server Logs Unredacted Sensitive Command Data for Unrecognized Commands - ([File: chia/daemon/server.py])

### Summary
The daemon's WebSocket message handler applies `redact_sensitive_data()` only in one logging call path (`incoming_connection`), but a second logging call path in `handle_message()` for unrecognized commands logs the raw, unredacted message dictionary — including the full `data` payload — directly to the daemon log. This is the same class of bug as CVE-2023-50291: redaction logic is applied inconsistently across code paths that both expose the same class of sensitive fields (passwords, mnemonics, private keys, secrets).

### Finding Description
`WebSocketServer.incoming_connection()` correctly redacts sensitive fields before debug-logging an incoming message: [1](#0-0) 

using `redact_sensitive_data()`, which masks any key containing `"pass"`, `"key"`, `"secret"`, or `"mnemonic"`: [2](#0-1) 

However, `handle_message()` — the function that actually dispatches on `command` — has a separate, unguarded logging call for the "unknown command" branch: [3](#0-2) 

`self.log.error(f"UK>> {message}")` logs the entire raw `message` dict, including its `data` field, with **no redaction at all**. Any daemon client — a wallet UI, CLI, GUI, or any other local process holding a valid daemon TLS client cert — can send a JSON payload with `command` set to anything not in `keychain_commands`, not `"ping"`, and not one of the keys in `get_command_mapping()` (e.g., a typo'd command name, or a legitimate-looking but misspelled `add_private_key`/`set_keyring_passphrase` command), while still including sensitive fields such as `mnemonic`, `password`, `private_key`, or `passphrase` in `data`. Because the command name doesn't match, execution falls to the `else` branch and the full unredacted payload — including those sensitive values — is written to the daemon's log file at ERROR level.

This mirrors the Solr CVE precisely: one endpoint/path in the codebase implements correct secret redaction (`/admin/info/properties`-equivalent → `incoming_connection` debug log), while a second path handling essentially the same data (`handle_message`'s unknown-command error log) does not apply the same redaction filter, defeating the intended protection.

### Impact Explanation
Successful exploitation writes plaintext mnemonics, passphrases, or private key material into the daemon's log file. Chia daemon logs are typically persisted to disk and may be collected by log aggregation, support bundles, crash reporters, or read by less-privileged users/processes with log read access, resulting in credential/secret disclosure (CWE-522) beyond the sender's own privilege level. This is a confidentiality-only issue (no direct fund movement), consistent with the referenced advisory's CVSS vector (`C:H/I:N/A:N`).

### Likelihood Explanation
Any process capable of connecting to the daemon websocket (holding daemon TLS client certs, which any locally-installed Chia component or CLI/GUI possesses) can trigger this by sending a single malformed/unknown-command message containing sensitive-looking fields in `data`. No race condition or complex chaining is required — a single crafted message payload with a misspelled command name is sufficient. The only barrier is possessing the daemon's private client cert, which is the same trust boundary the intended `redact_sensitive_data()` protection was built to work within (defense-in-depth for logs, not an authentication bypass).

### Recommendation
Apply `redact_sensitive_data()` consistently to every log statement that may emit the full `message` or `data` object, not just the one in `incoming_connection()`. Specifically, change:
```python
self.log.error(f"UK>> {message}")
```
to log a redacted copy, e.g. `self.log.error(f"UK>> {redact_sensitive_data(message)}")`, and audit other `self.log.*` call sites in `chia/daemon/server.py` (and `chia/daemon/keychain_proxy.py`, `chia/daemon/keychain_server.py`) for the same inconsistency. Consider centralizing all daemon message logging through a single wrapper that always redacts before formatting, so future log statements cannot bypass the filter.

### Proof of Concept
1. Establish a daemon websocket connection using valid local daemon TLS client certs (as any installed Chia component would).
2. Send a JSON payload such as:
```json
{
  "command": "add_private_key_typo",
  "data": {"mnemonic": "<24-word secret mnemonic>", "password": "supersecret"},
  "ack": false,
  "origin": "test",
  "destination": "daemon",
  "request_id": "abc123"
}
```
3. Because `add_private_key_typo` matches none of `keychain_commands`, `"ping"`, or `get_command_mapping()` keys, execution reaches the `else` branch in `handle_message()` at [4](#0-3)  and logs the full unredacted `message` (including the mnemonic and password) to the daemon log at ERROR level, unlike the properly redacted DEBUG log produced earlier in `incoming_connection()`.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```
