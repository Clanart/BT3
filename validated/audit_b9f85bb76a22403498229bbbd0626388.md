### Title
Inverted `isActive` check in `unvote()` permanently locks vlMGP voting power for deactivated pools - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.unvote()` is documented as the mechanism that lets a user pull their vote out of a pool that has been deactivated ("Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing" [1](#0-0) ), but the actual guard does the opposite: it reverts unless the pool is still active. This is the same class of bug as the referenced GitLab report — a state that is supposed to gate/allow an action (here, "pool inactive → allow exit") is checked with inverted/incorrect logic, so the protection that should trigger on the restricted state never fires, leaving the user permanently stuck instead of freed.

### Finding Description
`vote()` correctly requires `pool.isActive` to add/reduce a vote, which is expected since new voting activity should only happen on live pools: [2](#0-1) 

`unvote()`, however, is meant for the opposite scenario — letting a user exit a vote from a pool that has been deactivated by governance/pool management — yet it uses the exact same "must be active" condition instead of "must be inactive" or simply "always allowed": [3](#0-2) 

Because `if(!pool.isActive) revert PoolNotActive();` requires the pool to still be active, the one code path whose entire purpose is to free votes from a now-inactive pool is unreachable for the case it was designed for. Once a pool's `isActive` flag is turned off through normal pool-management operations, any user holding `userVotedForPoolInVlmgp[msg.sender][pool]` for that pool can never zero it out.

This directly affects the vlMGP lock/unlock accounting in `VLMGP.sol`. `startUnlock()` enforces that a user cannot reduce their locked MGP below what is currently committed to votes: [4](#0-3) 

Since `userTotalVotedInVlmgp[msg.sender]` can never be decreased for votes cast into a pool that later becomes inactive (the only function that decrements it for that pool, `unvote`, is blocked), the corresponding portion of the user's locked MGP becomes permanently un-unlockable — `startUnlock` will keep reverting with `NotEnoughLockedMPG` for that portion, indefinitely.

### Impact Explanation
This is a direct, permanent freezing of ordinary users' locked MGP tokens (and the associated ability to fully exit vlMGP), triggered purely by a routine pool lifecycle event (pool deactivation), not by any malicious/privileged action. The user has no path in the current contract logic to reduce `userVotedForPoolInVlmgp` for a dead pool, so the affected MGP stays locked forever — satisfying the "permanent freezing of funds" bar.

### Likelihood Explanation
Pools being deactivated (removed, replaced, or having their rewarder swapped) is an expected, normal part of protocol operation as explicitly acknowledged by the function's own docstring, not an edge case requiring a malicious actor. Any user who voted for a pool that is later deactivated is affected, making this highly likely to occur over the protocol's lifetime.

### Recommendation
Fix the condition in `unvote()` to allow unvoting when the pool is inactive (or simply remove the `isActive` gate entirely, since unvoting should always be permitted), e.g.:
```solidity
function unvote(address _lp) public {
    Pool storage pool = poolInfos[_lp];
    uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
    // allow unvoting regardless of pool.isActive, or only when !pool.isActive
    ...
}
```

### Proof of Concept
1. User locks MGP via `VLMGP.lock`, then calls `WombatBribeManager.vote([poolA], [delta])`, setting `userVotedForPoolInVlmgp[user][poolA] = X` and `userTotalVotedInVlmgp[user] += X`.
2. Pool management deactivates `poolA` (`poolInfos[poolA].isActive = false`) as part of normal pool maintenance.
3. User calls `unvote(poolA)` to release their `X` MGP worth of vote — this reverts with `PoolNotActive()` because of the inverted check.
4. User calls `VLMGP.startUnlock(amount)` attempting to unlock MGP that would bring `totalLockAfterStartUnlock` below `userTotalVotedInVlmgp[user]` (which still includes the stuck `X`) — this reverts with `NotEnoughLockedMPG` [4](#0-3) .
5. There is no other function that decrements `userVotedForPoolInVlmgp[user][poolA]`, so the `X` MGP remains permanently locked.
