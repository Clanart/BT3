### Title
Payout attribution (OP_RETURN operator pubkey) is not covered by the user's `SinglePlusAnyoneCanPay` signature, allowing anyone to misattribute reimbursement credit to an arbitrary operator - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The payout transaction that fronts a Citrea withdrawal is signed by the user with `TapSighashType::SinglePlusAnyoneCanPay`, which only commits to input #0 and output #0 (the user payout). The OP_RETURN output that records "which operator fronted this payout" — the sole piece of on-chain data later used by verifiers/operators to decide who gets reimbursed — is outside the signed message and can be freely substituted by anyone who observes the signature, breaking the binding between "the operator credited" and "the party that actually paid."

### Finding Description
`create_payout_txhandler` builds the payout transaction with exactly one signed input (the pre-funded withdrawal UTXO, spent via `user_sig`) and three outputs: the user's payout (output #0), a CPFP anchor, and an OP_RETURN carrying an arbitrary caller-supplied `operator_xonly_pk`: [1](#0-0) 

The witness for the single input is `user_sig`, which the RPC layer enforces must have sighash type `SinglePlusAnyoneCanPay`: [2](#0-1) 

`SIGHASH_SINGLE` only commits the signed input to the output at the *same index* (output #0, the user payout); `SIGHASH_ANYONECANPAY` leaves the signed input free to be combined with any other inputs. Critically, output #2 (the OP_RETURN carrying `operator_xonly_pk`) and output #1 (the anchor) are **not covered** by this signature at all. Once the `input_signature`/`input_outpoint`/`output_script_pubkey`/`output_amount` tuple is known (it is passed as plain `WithdrawParams` to any operator's `Withdraw`/`InternalWithdraw` RPC, and becomes fully public the instant any operator broadcasts the resulting payout transaction to the mempool), anyone can reassemble a byte-identical transaction that pays the same user the same amount, but swaps in a different `operator_xonly_pk` in the OP_RETURN output, and get it confirmed instead (e.g., by CPFP-bumping it with a higher fee before the honest operator's version confirms).

The consequence of this is severe because the OP_RETURN content is the *only* signal the protocol uses to attribute the payout to an operator. `update_finalized_payouts` parses this OP_RETURN directly from the confirmed transaction with no additional authentication and writes it as the "payer": [3](#0-2) 

That value is persisted to `withdrawals.payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk`: [4](#0-3) 

The operator whose key ends up in that column is the one whose node will pick this up as its own unhandled payout and proceed to claim reimbursement: [5](#0-4) 

and the operator RPC path explicitly gates reimbursement-tx generation on this same recorded "payer" field matching the node's own key: [6](#0-5) 

Because the recorded "payer" is derived purely from unauthenticated OP_RETURN bytes that no signature binds to the actual funder of the transaction, an unprivileged party who merely observes a valid `(input_signature, input_outpoint, output_script_pubkey, output_amount)` tuple can construct a competing payout transaction crediting a different, arbitrary operator xonly-pubkey than the one that will actually broadcast/fund the transaction.

### Impact Explanation
This breaks the custody binding "the operator credited versus the party that paid." If the substituted transaction confirms, an operator that never fronted the withdrawal is recorded as `payout_payer_operator_xonly_pk` and its `PayoutCheckerTask` will proceed to build a kickoff and claim reimbursement from its round collateral — i.e., "an operator reimbursed for a payout it never funded." Conversely, the operator that genuinely intended to front the payout (and would have earned reimbursement) is locked out since `validate_payer_is_operator` will reject reimbursement-tx generation once the payer key on file doesn't match its own — "an honest operator permanently unable to be reimbursed" for that deposit.

### Likelihood Explanation
The attacker needs no privileged role (not operator/verifier/aggregator) — only the ability to observe or receive the `WithdrawParams` tuple (via any operator's public `Withdraw`/`InternalWithdraw` RPC, or by watching the mempool once any operator broadcasts) and enough funds to win a fee race for confirmation (the payout tx pays zero direct fee and relies entirely on CPFP, making a fee race straightforward).

### Recommendation
Bind the attributed operator's xonly-public-key cryptographically to the payout transaction rather than trusting an unauthenticated OP_RETURN field — e.g., require the fronting operator's own Schnorr signature over the full transaction (including the OP_RETURN output) as an additional witness/commitment, or change the sighash type used for the user's pre-signature to cover all outputs (`SIGHASH_ALL`) once the fronting operator is fixed at signing time, or otherwise ensure the payer-attribution data is committed to the same signature that authorizes spending the withdrawal UTXO.

### Proof of Concept
1. Operator A intends to front withdrawal `W` and obtains `input_signature` (SIGHASH_SINGLE|ANYONECANPAY) for `input_outpoint`/`output_script_pubkey`/`output_amount` via the standard withdrawal flow, then calls `create_payout_txhandler` with its own `operator_xonly_pk` and broadcasts the resulting `payout_tx` (core/src/builder/transaction/operator_reimburse.rs:407-436).
2. An unprivileged observer captures `(input_signature, input_outpoint, output_script_pubkey, output_amount)` from Operator A's broadcast transaction (public mempool) or from a `WithdrawParams` request it was asked to relay.
3. The observer builds a new transaction with the identical input (same outpoint, same witness `user_sig`), identical output #0 (same script/amount, satisfying `SIGHASH_SINGLE`), but a different OP_RETURN payload containing Operator B's `xonly_pk` instead of Operator A's.
4. The observer CPFP-bumps this alternate transaction with a higher fee than Operator A's version and gets it confirmed first.
5. `update_finalized_payouts` (core/src/verifier.rs:2312-2350) parses the confirmed OP_RETURN and records Operator B as `payout_payer_operator_xonly_pk` for withdrawal `W`.
6. Operator B's `PayoutCheckerTask` (core/src/task/payout_checker.rs:39-53) sees an unhandled payout under its own key and proceeds to claim reimbursement it never funded, while Operator A — who actually paid the user — is permanently blocked from reimbursement by `validate_payer_is_operator` (core/src/operator.rs:1703-1719).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
