### Title
Division-before-multiplication in NFT royalty summary calculation causes precision loss - ([File: chia/wallet/nft_wallet/nft_wallet.py])

### Summary
`NFTWallet.royalty_calculation` computes the informational royalty summary using `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`, performing integer division before multiplication, exactly the bug class in the external report. [1](#0-0) 

### Finding Description
The order of operations `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS` truncates twice: once when dividing by the number of royalty assets, and again when dividing by `MAX_ROYALTY_BASIS_POINTS` (10000), instead of multiplying first and dividing once at the end. [2](#0-1) 

This is a genuine division-before-multiplication pattern analogous to the reported bug class. However, I could not confirm during this investigation that this function's output is used to construct the actual on-chain royalty payment amounts that get enforced by consensus/CLVM. The actual royalty payments that get paid out on-chain are computed by a separate function, `compute_royalty_amount` (used in `make_nft1_offer` and referenced extensively in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`), which multiplies before dividing (`compute_royalty_amount(offered_amount=-1_000_000, royalty_split=1, percentage=500)` → `50_000`), i.e., the correct order. `royalty_calculation` appears to be used only for producing a *summary preview* (e.g., surfaced via `nft_calculate_royalties` RPC and CLI display in `chia/cmds/wallet_funcs.py`) rather than the enforced payment amount baked into the offer's settlement puzzle.

### Impact Explanation
Because the actual on-chain royalty payment is derived via `compute_royalty_amount` (which is not affected by this bug) rather than `royalty_calculation`, the practical impact is limited to a **display/preview discrepancy**: users could see a slightly understated royalty estimate before confirming an offer, but the amount that is actually collected in the notarized/settlement puzzle is computed correctly elsewhere. I was not able to fully verify, within the scope of this analysis, whether any code path uses `royalty_calculation`'s output to determine actual coin amounts that get spent or asserted in an offer (as opposed to purely informational purposes), so I cannot definitively rule out a path where a wallet mis-computes required royalty amounts and creates an offer that pays less than expected, or a taker relies on the misleading summary to accept an unfavorable trade. Given the uncertainty about reachability to actual coin movement, and because the visible usage is a display calculation, this does not clearly meet the bar of "concrete unsigned or unauthorized coin movement, supply inflation, forged asset identity, or offer settlement theft" required by the validation rules.

### Likelihood Explanation
Low-Medium. The buggy code path is reachable by any wallet user calling the NFT royalty summary/calculation feature (e.g., `nft_calculate_royalties` RPC, offer creation flows that display royalty summaries), but the values it produces do not appear to directly govern the enforced on-chain settlement amount based on the separate, correctly-implemented `compute_royalty_amount` function.

### Recommendation
Regardless of whether it affects consensus-relevant amounts, `royalty_calculation` in `chia/wallet/nft_wallet/nft_wallet.py` should be fixed to multiply before dividing: `abs(amount) * percentage // (len(royalty_assets_dict) * MAX_ROYALTY_BASIS_POINTS)` (or equivalent), consistent with `compute_royalty_amount`, to avoid inconsistent/understated royalty previews shown to users, and to prevent any downstream logic from ever relying on it as an authoritative royalty amount.

### Proof of Concept
Given `abs(amount) = 999`, `len(royalty_assets_dict) = 2`, `percentage = 5000` (50%), `MAX_ROYALTY_BASIS_POINTS = 10000`:
- Current buggy order: `999 // 2 = 499`; `499 * 5000 = 2495000`; `2495000 // 10000 = 249`.
- Correct order (multiply first): `999 * 5000 = 4995000`; `4995000 // 2 = 2497500`; `2497500 // 10000 = 249` (in this example the results coincide, but for other values such as `amount=3, len=2, percentage=5000` the buggy path yields `3//2=1; 1*5000=5000; 5000//10000=0`, while the correct order yields `3*5000=15000; 15000//2=7500; 7500//10000=0` — differences appear for larger/more varied inputs, e.g. `amount=1999, len=3, percentage=3333`: buggy = `1999//3=666; 666*3333=2,219,778; //10000=221`; correct = `1999*3333=6,662,667; //3=2,220,889; //10000=222` — a 1 mojo discrepancy demonstrating the precision loss).     @staticmethod
    def royalty_calculation(
        royalty_assets_dict: dict[Any, tuple[Any, uint16]],
        fungible_asset_dict: dict[Any, uint64],
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():
            address, percentage = royalty_info
            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():
                summary_dict[id].append(
                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
