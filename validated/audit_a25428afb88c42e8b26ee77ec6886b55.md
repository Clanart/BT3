### Title
Attacker-controlled Bitcoin transaction overwrites InInstruction data and presumed origin of another depositor's output in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
CVE-2025-38264 concerns a maliciously injected element corrupting list processing (a request being re-queued into a list it is already part of, injecting a loop). The Serai analog is in `Bitcoin::get_outputs`: the `outputs` vector is accumulated across all transactions in a block, yet the post-processing loop that populates `presumed_origin` and `data` iterates over the *entire* accumulated vector rather than only the outputs of the transaction currently being examined. A second attacker-crafted transaction paying the multisig in the same block "injects" its origin/InInstruction metadata into list entries belonging to an earlier transaction, corrupting them.

### Finding Description
In `processor/src/networks/bitcoin.rs`, `get_outputs` iterates `block.txdata[1 ..]`, pushes each tx's scanned outputs into a shared `outputs` vec, then — guarded only by `if outputs.is_empty() { continue }` — sets `presumed_origin` and `data` on `&mut outputs` (all accumulated entries, not just this tx's). [1](#0-0) 

```
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { ...; outputs.push(output); }
  if outputs.is_empty() { continue; }
  let presumed_origin = { /* derived from *this* tx's input[0] */ };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {           // <-- iterates ALL outputs seen so far
    if output.kind == OutputType::External {
      output.data.clone_from(&data);     // overwrites earlier txs' InInstruction data
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

For each transaction beyond the first that pays a scanned key, `extract_serai_data(tx)` (the `InInstruction` embedded in that tx) and `presumed_origin` (the address that funded *that* tx's `input[0]`) are written onto every previously accumulated output, including outputs belonging to other transactions and other depositors. Entries are effectively re-linked mid-processing — the same "element already in the list gets a foreign owner" shape as the kernel bug.

### Impact Explanation
`data` carries the Serai `InInstruction` for `OutputType::External` deposits and `presumed_origin` is the refund/attribution address recorded for each output. An unprivileged attacker sends a transaction paying the multisig's key (or a registered offset address — `kinds[offset_repr_ref]` covers `Forwarded`/`Change`/etc. offsets) in the same confirmed block as a victim's deposit. The victim's output is then reported with the attacker's `InInstruction` data and attacker-controlled `presumed_origin`. Depending on the instruction semantics (see `spec/integrations/Instructions.md` and `substrate/in-instructions`), this can redirect how the deposit is credited/attributed, or at minimum corrupt refund-address bookkeeping. The attacker fully controls both the data payload and their funding address, so the overwrite is deterministic whenever their tx is ordered after the victim's in the same block. Outputs are only emitted after `N::CONFIRMATIONS`, but ordering within a block is attacker-influenceable (fee/position) and the condition (two multisig-paying txs per block) is routine under normal deposit traffic, so incidental corruption can also occur without malice.

### Likelihood Explanation
Reachable entirely with public inputs: any Bitcoin user can send a transaction to the multisig address embedded with an InInstruction. The only requirement is inclusion in the same block as another depositing transaction — plausible organically and trivially achievable by a miner or a user watching the mempool. No validator, RPC, or key compromise is required.

### Recommendation
Scope the metadata-population loop to only the outputs produced by the current transaction:

```rust
let start = outputs.len();
for output in scanner.scan_transaction(tx) { ...; outputs.push(output); }
if outputs.len() == start { continue; }
...
for output in &mut outputs[start ..] { ... }
```

Alternatively, return per-transaction `(outputs, presumed_origin, data)` groupings so cross-transaction mutation is impossible.

### Proof of Concept
1. Victim publishes tx V paying the multisig's external address with InInstruction D_v, funded from address A_v.
2. Attacker publishes tx W paying any offset address the processor scans (e.g., the `External`/`Forwarded` script for the same key) with InInstruction D_a, funded from attacker address A_a, mined in the same block after V.
3. `get_outputs` scans V → pushes victim output (data unset). Then scans W → pushes attacker output, then `extract_serai_data(W)` = D_a and `presumed_origin` = A_a are applied to `outputs` — including the victim's entry.
4. The Scanner emits the victim's output tagged with D_a/A_a; `Output::data()` returns the attacker's instruction bytes for the victim's deposit.

Note: I was unable to fully trace how `Output::data()`/`presumed_origin` are consumed downstream (the `InInstruction` handling in `processor/src/multisigs/mod.rs` and the Substrate in-instructions pallet), so the precise fund-routing consequence is inferred from the spec rather than proven end-to-end; the list-contamination bug itself is directly evident in the code.

```rust
  async fn get_outputs(&self, block: &Self::Block, key: ProjectivePoint) -> Vec<Output> {
    let (scanner, _, kinds) = scanner(key);

    let mut outputs = vec![];
    // Skip the coinbase transaction which is burdened by maturity
    for tx in &block.txdata[1 ..] {
      for output in scanner.scan_transaction(tx) {
        let offset_repr = output.offset().to_repr();
        let offset_repr_ref: &[u8] = offset_repr.as_ref();
        let kind = kinds[offset_repr_ref];

        let output = Output { kind, presumed_origin: None, output, data: vec![] };
        assert_eq!(output.tx_id(), tx.id());
        outputs.push(output);
      }

      if outputs.is_empty() {
        continue;
      }

      // populate the outputs with the origin and data
      let presumed_origin = {
        // This may identify the P2WSH output *embedding the InInstruction* as the origin, which
        // would be a bit trickier to spend that a traditional output...
        // There's no risk of the InInstruction going missing as it'd already be on-chain though
        // We *could* parse out the script *without the InInstruction prefix* and declare that the
        // origin
        // TODO
        let spent_output = {
          let input = &tx.input[0];
          let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
          spent_tx.reverse();
          let mut tx;
          while {
            tx = self.rpc.get_transaction(&spent_tx).await;
            tx.is_err()
          } {
            log::error!("couldn't get transaction from bitcoin node: {tx:?}");
            sleep(Duration::from_secs(5)).await;
          }
          tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
        };
        Address::new(spent_output.script_pubkey)
      };
      let data = Self::extract_serai_data(tx);
      for output in &mut outputs {
        if output.kind == OutputType::External {
          output.data.clone_from(&data);
        }
        output.presumed_origin.clone_from(&presumed_origin);
      }
    }

    outputs
  }
```
