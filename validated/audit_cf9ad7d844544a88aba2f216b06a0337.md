### Title
Unregistered-participant index panic in PedPoP decryption/blame path causes node crash - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` unconditionally when verifying an `EncryptionKeyProof`. `enc_keys` is only populated through `register`, so if the blame/decryption flow is invoked for a participant whose `EncryptionKeyMessage` was never registered (e.g., a malicious DKG participant who withholds or fails the commitments round but whose accusation is still processed), the `HashMap` index panics instead of returning an error. The panic aborts the victim's DKG processing — an availability-only analog of the reported class ("processing maliciously crafted content leads to an unexpected crash").

### Finding Description
The PedPoP encryption module maintains a `Decryption<C>` box holding per-participant encryption public keys in `enc_keys: HashMap<Participant, C::G>`, populated only by `register` (`encryption.rs:351-362`), which itself `assert!`s on duplicate registration. During blame resolution, `decrypt_with_proof` verifies the accused's DLEq proof and then dereferences the decryptor's registered key:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],   // encryption.rs:388
)
```

`HashMap`'s `Index` impl panics when the key is absent. `decrypt_with_proof` only returns `DecryptionError::{InvalidSignature, InvalidProof}`; there is no `get`/fallback for a missing `decryptor` entry, and no upstream check in this crate guarantees `enc_keys` contains every participant for whom a blame/decryption request can be raised. `Participant` values are attacker-controlled protocol data (`Participant::new` at `crypto/dkg/src/lib.rs:29-35`), and `EncryptedMessage::read` / `EncryptionKeyProof::read` accept arbitrary untrusted bytes (`encryption.rs:171-177`, `267-269`).

### Impact Explanation
An unprivileged counterparty in the DKG can drive a peer into `decrypt_with_proof` (by being accused of an invalid share and having the victim evaluate the blame proof) referencing a participant index that was never registered — most simply by ensuring the accusing/decryptor participant's `EncryptionKeyMessage` never completed `register`. The victim's `HashMap` index panics, crashing the signing/DKG task or process. Per the scan class, this is a reachable denial of service (Medium; CVSS 4.3 analog, `A:L` equivalent — availability impact from maliciously crafted protocol input, no integrity or confidentiality breach).

### Likelihood Explanation
The panic triggers whenever the PedPoP driver calls `decrypt_with_proof` for a `decryptor` absent from `enc_keys`. Since `register` asserts on duplicates and only inserts on a valid `EncryptionKeyMessage`, any protocol ordering where accusation handling precedes or skips registration for a given participant (e.g., an accuser who participated in the shares round but whose commitments-round message was rejected/missing) reaches the panic deterministically — no race or probabilistic condition required. The same missing-key hazard exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, `encryption.rs:466`), showing the codebase assumes, but does not enforce, full registration before use.

### Recommendation
Replace infallible `HashMap` indexing with checked lookups in the blame/decryption path:

```rust
let decryptor_key = self
  .enc_keys
  .get(&decryptor)
  .ok_or(DecryptionError::InvalidProof)?;
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[*decryptor_key, *proof.key],
).map_err(|_| DecryptionError::InvalidProof)?;
```

Apply the same treatment to `Encryption::encrypt` (`enc_keys[&participant]`) and convert `Decryption::register`'s `assert!` on duplicate registration into a `Result` so malformed or repeated peer messages yield errors, not panics.
