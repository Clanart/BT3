### Title
Instant, balance-weighted reward distribution allows flash-stake sandwiching of `queueNewRewards()` to steal yield from long-term stakers - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward()` (invoked by `queueNewRewards`/`donateRewards`) distributes the entire incoming reward amount instantly, pro-rata to the pool's current `totalStaked()` balance, with no time-weighting, vesting, or minimum-holding-period mechanism. Because `totalStaked()` is simply `IERC20(stakingToken).balanceOf(operator)` at the instant the reward is queued, and a user's share of that reward is determined solely by their `balanceOf(_account)` (their live `MasterMagpie` staked balance) at harvest time, an attacker can deposit a large amount immediately before the reward is queued and withdraw immediately after, capturing reward proportional to capital rather than staking duration.

### Finding Description
`totalStaked()` reads the live token balance of the `operator` (MasterMagpie) contract: [1](#0-0) 

`_provisionReward()` computes the new `rewardPerTokenStored` using this instantaneous `totalStaked()` value with no streaming/duration mechanism (unlike Synthetix-style `StakingRewards`, which spreads rewards over a `rewardsDuration`): [2](#0-1) 

A user's `earned()` (and thus `userRewards` snapshotted via `updateReward`) is computed from their instantaneous `balanceOf(_account)`, which is read live from `MasterMagpie.stakingInfo`: [3](#0-2) [4](#0-3) 

On the `MasterMagpie` side, `deposit()`/`withdraw()` are unrestricted, uncooled-down, and immediately move real tokens in/out of the operator's balance, and immediately update `userInfo[...].amount` (i.e., `BaseRewardPool.balanceOf`): [5](#0-4) [6](#0-5) 

Exploit flow:
1. Attacker observes a pending `queueNewRewards(A, token)` tx in the mempool and front-runs it with `MasterMagpie.deposit(stakingToken, D)` where `D` is large relative to existing stake `S`. This both increases `totalStaked()` (operator's token balance) and sets the attacker's `userRewardPerTokenPaid` to the pre-reward `rewardPerTokenStored` (via `_harvestBaseRewarder` -> `updateFor` inside `_deposit`).
2. `queueNewRewards(A, token)` executes, updating `rewardPerTokenStored += A * 10**decimals / (S + D)`.
3. Attacker calls `multiclaim`/`multiclaimSpec` (which calls `rewarder.getReward` under `updateReward`), capturing `earned = D * (R1 - R0) / 10**decimals ≈ A * D / (S + D)` — which approaches the entire reward `A` as `D >> S`.
4. Attacker immediately calls `MasterMagpie.withdraw(stakingToken, D)`, retrieving their full principal with zero economic exposure/time held.

No existing check prevents this: there is no minimum staking period, no linear reward streaming, no deposit/withdrawal cooldown, and `nonReentrant` only guards against reentrancy within a single call, not against sequential same-block front-running.

### Impact Explanation
This is a direct theft of unclaimed yield from legitimate long-term stakers: capital that provided zero time-weighted contribution to the pool captures a disproportionate (up to nearly 100%) share of newly queued rewards, permanently diluting the amount legitimate stakers can claim from that `queueNewRewards` event. This matches the Immunefi impact class "theft of unclaimed yield" / "direct theft of user funds."

### Likelihood Explanation
Feasibility is high wherever `queueNewRewards`/`donateRewards` transactions are publicly visible in the mempool prior to inclusion (true for public EVM chains without private ordering). The only precondition is capital sufficient to materially move `totalStaked()`, which the question explicitly grants the attacker. The attack is fully repeatable for every reward-queuing event and requires only unprivileged `deposit`/`withdraw`/`multiclaim` calls — no admin or special role needed.

### Recommendation
Redesign reward distribution to be time-weighted rather than instantly balance-weighted, e.g.:
- Stream rewards linearly over a fixed `rewardsDuration` (Synthetix `StakingRewards` pattern) using a `rewardRate` and `lastUpdateTime`, so `rewardPerToken()` accrues continuously instead of jumping fully at the `queueNewRewards` call.
- Alternatively/additionally, require a minimum staking duration before a deposit is eligible to earn from a given `queueNewRewards` snapshot (e.g., checkpoint balances before allowing them to participate in reward math added within the same block).

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (or `BaseRewardPoolV2`) for a mock `stakingToken`, and a reward token; register the pool via `add`.
2. Long-term staker `LT` deposits `S` tokens via `MasterMagpie.deposit` and waits (accrues no reward yet since none queued).
3. In the same block/transaction sequence:
   - Attacker calls `MasterMagpie.deposit(stakingToken, D)` with `D >> S`.
   - Manager calls `rewarder.queueNewRewards(A, rewardToken)` (reward token pre-funded/approved).
   - Attacker calls `MasterMagpie.multiclaim([stakingToken])` to harvest.
   - Attacker calls `MasterMagpie.withdraw(stakingToken, D)`.
4. Assert `rewarder.earned(attacker, rewardToken)` (captured before harvest, or the reward token balance delta after harvest) is approximately `A * D / (S + D)`, i.e., far exceeds the attacker's fair time-weighted share (which should be ~0 since they staked for effectively zero duration), and assert `LT`'s remaining claimable reward is correspondingly reduced to `A * S / (S + D)` instead of the full `A`.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
