### Title
CPU exhaustion in `Offer.get_cancellation_coins` via attacker-crafted announcement/dependency graph in a taken offer - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_cancellation_coins()` computes the minimal set of coins whose spend cancels an entire offer by building per-coin dependency/announcement maps from the offer's CLVM output and then iteratively resolving those dependencies with nested loops that repeatedly convert lists to sets and rescan the coin-name list. Because every input to this algorithm (number of coin spends, number of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions per coin, and the shape of the dependency graph between coins) is fully attacker-controlled by whoever constructs the offer, a malicious offer counterparty can craft an offer that, once taken by a victim wallet, causes `get_cancellation_coins` to perform quadratic-or-worse work when the victim later cancels the trade.

### Finding Description
`get_cancellation_coins` first walks every non-ephemeral coin spend in the offer bundle and records, per coin, the announcements it creates and the announcements it asserts on other coins: [1](#0-0) 

It then repeatedly calls `detect_dependent_coin(coin_names, dependencies, announcements)` in a `while True` loop, and for every coin removed it re-scans the *entire* `dependencies` dict, converting each coin's dependency list and the removed-announcement list to `set()` objects on every inner iteration, then rebuilding `coin_names` with a full list comprehension: [2](#0-1) 

This structure does not use indexed/O(1) lookups for the attacker-controlled announcement hashes and coin IDs; instead it performs repeated `set(...)`-construction and list scans (`dependencies.items()`, `coin_names = [n for n in coin_names if ...]`) inside nested loops that are each themselves driven by the outer `while True` / `detect_dependent_coin` loop. With `N` coins and `M` announcements per coin under attacker control (offers can bundle many coin spends, e.g. many CAT/NFT/XCH coins each emitting several announcement conditions), the total work is quadratic or worse in `N*M`, directly analogous to the reported `@conform-to/dom` `parseSubmission` issue where repeated linear lookups over attacker-supplied unique keys caused CPU exhaustion instead of using single-pass, indexed iteration.

This computation is triggered purely by wallet-side logic operating on an already-accepted/taken offer's `SpendBundle` — i.e., data that originated from an untrusted offer counterparty — with no bound on the number of coins/announcements the offer may contain beyond mempool/block cost limits (which permit large multi-coin bundles).

### Impact Explanation
A wallet user who takes a maliciously crafted offer (e.g., an offer with many small coin spends and interlocking `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions designed to maximize dependency-graph resolution work) and later attempts to cancel that trade will cause the wallet process to perform disproportionate CPU work inside `get_cancellation_coins`. Because wallet trade cancellation runs synchronously in the wallet's async event loop, this can stall wallet transaction processing (a spend-triggered transaction-processing halt) for the duration of the computation, denying service to the wallet for other pending operations. This is a CPU-exhaustion / availability issue rather than a fund-theft issue.

### Likelihood Explanation
Exploitation requires a victim to take (accept) an attacker-supplied offer and later call trade cancellation on it — a normal, expected wallet workflow (offers are explicitly designed to be exchanged with untrusted counterparties). Crafting an offer with many coin spends and announcement conditions is straightforward using standard offer-construction tooling; the attacker fully controls the number of coins and the announcement/dependency topology within the bundled spends. No special privileges are needed beyond being an offer counterparty.

### Recommendation
Rework `get_cancellation_coins`/`detect_dependent_coin` to use O(1) dict/set lookups indexed by coin ID and announcement hash instead of repeatedly rebuilding `set()` objects from lists and rescanning `dependencies.items()`/`coin_names` on every inner-loop iteration. Precompute a reverse index from announcement hash to the coin(s) that assert it once, and use it to resolve dependency removal in a single pass (e.g., via a queue/BFS over the precomputed index) so the overall algorithm is linear (or near-linear) in the number of coins and announcements. Additionally, consider bounding the number of coin spends/announcements processed by `get_cancellation_coins` for offers taken from untrusted sources, consistent with existing mempool/block cost-based limits.

### Proof of Concept
Not independently executed (analysis is based on static code review of `chia/wallet/trading/offer.py`); a concrete PoC would construct an offer whose bundle contains `N` non-ephemeral coin spends, each emitting a `CREATE_COIN_ANNOUNCEMENT` and asserting the announcement of a different coin to form a long dependency chain (or a many-to-one fan-in of assertions on a small set of announcements), take the offer in a test wallet, and measure the wall-clock time of `Offer.get_cancellation_coins()` as `N` scales, expecting super-linear growth consistent with the nested `set()`-rebuilding loops shown above. I was not able to execute this PoC or inspect the body of `detect_dependent_coin` (only its call sites) within the available tool budget, so the exact asymptotic complexity of that helper is unverified — the quadratic-or-worse behavior demonstrated here is limited to the visible nested-loop/list-rebuilding logic in `get_cancellation_coins` itself.
