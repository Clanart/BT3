### Title
`SmartWomConvert.smartConvert` enforces an unattainable `_minRec` on partial buyback swaps, making `WombatStaking._sendRewards` revert and blocking deposits/withdrawals - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._sendRewards` unconditionally calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` when an `mWOM` fee is active, and `smartConvert` passes `_minRec = _amountIn` into `_convertFor` [1](#0-0) . Whenever the live `mWOM/WOM` price (`currentRatio()`) is below `buybackThreshold`, part of the amount is routed through a real AMM swap that inherently loses value to price impact/fees, so `convertAmount + amountRec` will almost always be less than `_amountIn`, causing `_convertFor` to revert with `MinRecNotMatch` [2](#0-1) . Because `_sendRewards` is called from `_toMasterWomAndSendReward`, which itself is invoked on every `deposit`, `depositLP`, `withdraw`, and `harvest` for that pool, this single revert path DoSes principal deposits and withdrawals for the entire pool [3](#0-2) .

### Finding Description
`_sendRewards` iterates `feeInfos`; for any active fee flagged `isMWOM` on the `wom` token, if `smartWomConverter != address(0)` it calls `smartConvert(feeAmount, 0)` with no try/catch: [4](#0-3) .

Inside `smartConvert`, `_minRec` is hardcoded to `_amountIn` (the full amount), not a value tolerant of expected swap slippage: [1](#0-0) .

`_convertFor` then splits the amount into `convertAmount` (deposited 1:1 into `mWom`) and `buybackAmount` (swapped through the `womMWomPool` router with `minAmountOut = 0`), and only after the swap checks `convertAmount + amountRec >= _minRec`: [2](#0-1) . Because the swap itself has price impact/fees, `amountRec` is structurally almost always less than `amountToSwap` whenever `convertRatio < DENOMINATOR` (i.e., whenever `currentRatio() < buybackThreshold`), so the sum falls short of `_amountIn` and `MinRecNotMatch()` reverts.

An unprivileged attacker can trivially push `currentRatio()` (computed live from `IWombatRouter.getAmountOut` on the `womMWomPool`) below `buybackThreshold` with an ordinary swap on that public AMM pool, or such a state can arise from normal market conditions. Once in that state, any call that triggers `_toMasterWomAndSendReward` for a pool with an active `isMWOM` fee will revert inside `smartConvert`, since there is no fallback/try-catch around it. Since `withdraw(address,uint256,uint256,address)` (called by an unprivileged user via a pool helper, forwarding `_liquidity`/`_minAmount` verbatim) calls `_toMasterWomAndSendReward(_lpToken, _liquidity, false)` before performing the actual pool withdrawal [5](#0-4) , the entire withdrawal reverts — even though the user's own principal withdrawal parameters are perfectly valid. The same applies to `deposit`, `depositLP`, and `harvest` [6](#0-5) .

Existing protections do not help: `nonReentrant`/`whenNotPaused`/`_onlyPoolHelper` only gate access, they do not catch the downstream revert; there is no per-fee try/catch or fallback path if `smartConvert` fails.

### Impact Explanation
Once triggered, every `deposit`, `depositLP`, `withdraw`, and `harvest` for the affected pool reverts as long as the `womMWomPool` price stays below `buybackThreshold` and `smartWomConverter` remains set with an active `isMWOM` fee. This freezes both new deposits and, critically, principal withdrawals for legitimate users. Recovery requires an owner action (`setSmartConvert(address(0))`, `setBuybackThreshold`, or fee reconfiguration via `setFee`), which is outside the attacker's control and not guaranteed to happen quickly — satisfying "High - Temporary freezing of funds for at least 24 hours."

### Likelihood Explanation
The precondition (`currentRatio() < buybackThreshold` with an active `isMWOM` fee and `smartWomConverter` set) is a normal, expected operating state of an AMM-referenced ratio, not an exotic edge case, and can be induced by a single swap on the public `womMWomPool` by any unprivileged actor with modest capital. The bug is deterministic given the state (small harvested `feeAmount` makes it even more likely amountRec < amountToSwap due to fixed swap fee overhead), and can be repeated any time market/pool conditions revert to that state.

### Recommendation
Do not force `_minRec == _amountIn` in `smartConvert`; compute an achievable minimum receive tolerant of the router's own quoted output (e.g., via `estimateTotalConversion`/`getAmountOut` with a slippage buffer), or wrap the `smartConvert` call in `_sendRewards` in a try/catch that falls back to a plain `IMWom.deposit` (1:1) or to leaving the fee in `wom` if conversion fails, so a temporarily unfavorable buyback price cannot block the core deposit/withdraw path.

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatStaking`, `SmartWomConvert`, mock `IWombatRouter`/`womMWomPool` (or fork BSC/Arbitrum with real Wombat pools), register a pool, set `smartWomConverter`, and add an active `isMWOM=true` fee via `addFee`.
2. Seed the pool with LP so a user can deposit and later withdraw.
3. Manipulate `womMWomPool` (via a direct swap call from an unprivileged EOA) so `SmartWomConvert.currentRatio() < buybackThreshold`.
4. Have an unprivileged user call `withdraw` through the pool's `PoolHelper` with valid `_liquidity`/`_minAmount` for their own position.
5. Assert the transaction reverts with `MinRecNotMatch` (bubbled from `SmartWomConvert._convertFor`), confirming principal withdrawal is blocked despite valid, non-malicious withdrawal parameters.
6. Repeat with `deposit`/`depositLP`/`harvest` to show all four paths are blocked identically.
7. Show that only an owner-only action (`setSmartConvert(address(0))` or `setBuybackThreshold(10000)`) restores functionality, demonstrating the freeze persists until admin intervention.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
