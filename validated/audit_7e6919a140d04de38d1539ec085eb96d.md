Based on my investigation, the closest structural analog to the "unrestricted `transfer()`-style primitive with no restriction on the receiving entity" pattern is GitHub Desktop's binary-file "Open in external program" flow, which invokes Electron's `shell.openExternal` on a file path taken directly from a cloned/fetched repository, with no check on the file's type before launching it.

### Title
Attacker-Controlled Repo File Opened via Unrestricted `shell.openExternal` Launch - (File: app/src/ui/lib/open-file.ts)

### Summary
When a user views a binary file that changed in a commit/diff and clicks "Open file in external program," Desktop builds a `file://` URI from the repository-relative path and hands it directly to `shell.openExternal`, with no check on the file's extension/type. Because the path originates from tracked file names inside a cloned or fetched repository (fully attacker-controlled, e.g. via a malicious commit, PR branch, or remote), this mirrors the reported bug class: a powerful, low-level "send/launch" primitive is invoked against untrusted, unrestricted targets, without the kind of guardrail the report demands ("restrictions to non-contract accounts").

### Finding Description
`BinaryFile.open()` computes `fullPath = Path.join(repository.path, this.props.path)` from the diff-changed file path and calls `onOpenBinaryFile(fullPath)` [1](#0-0) . This flows to `openFile`, which calls `shell.openExternal(`file://${fullPath}`)` unconditionally: [2](#0-1) . There is no allow-list/deny-list on file extension, no check for executable bits, and no confirmation dialog distinguishing "safe" document types from potentially-executable ones (e.g. `.exe`, `.scr`, `.bat`, `.cmd`, `.js`, `.vbs`, `.lnk` on Windows, or `.command`/`.app` on macOS). The `path` in this flow is a file name that ships as part of a commit inside a repository the user cloned or fetched — content fully controlled by whoever authored that commit, including in a PR the user is merely reviewing. The `IAppShell` interface itself documents the intended guard but does not enforce it: `openPath`/`showItemInFolder`/`showFolderContents` are annotated "Do not use this method with non-validated paths," yet no validation is actually applied to the path before it reaches `shell.openExternal` [3](#0-2) . This is exactly the "missing restrictions to non-contract accounts" defect pattern: a generic, unrestricted low-level call (`shell.openExternal`/native launch) is used against a target whose nature (executable vs. non-executable) is never inspected.

### Impact Explanation
If the attacker commits (or has fetched into the user's Desktop working copy) a file with an executable extension recognized by the host OS, and the user clicks "Open file in external program" on that changed binary file, the OS will launch/execute that file directly via its default handler — potentially achieving code execution outside of any git/repo sandboxing, using only a click a reviewer would naturally make while inspecting a suspicious binary diff.

### Likelihood Explanation
Reviewing changed binary files by clicking "Open file in external program" is an ordinary, expected Desktop workflow (it exists specifically to let users inspect binary diffs), so the single "unnatural" step required is minimal and plausible in an actual review flow, especially for repositories/PRs from untrusted contributors. No admin rights, local access, or pre-existing malware are required — only that the user open a cloned/fetched repository containing the malicious file and use the documented "open externally" action.

### Recommendation
Before calling `shell.openExternal`/`openPath` on a path derived from repository content, validate the file against a deny-list of executable/script extensions per platform (or an allow-list of known-safe types), and route ambiguous/executable file types through a warning dialog (similar to browser "this file could harm your device" prompts) rather than launching unconditionally. Consider not using `file://` + `shell.openExternal` for binary diff review at all, and instead exposing the file read-only (e.g. `showItemInFolder`) so the user must explicitly choose to run it from their file manager.

### Proof of Concept
1. Attacker adds `payload.exe` (or `.scr`/`.cmd` on Windows) to a repository and commits it as a binary file, then opens a PR or otherwise gets the victim to fetch/clone the branch.
2. Victim opens the repository in GitHub Desktop, views the commit/PR diff, sees `payload.exe` listed as "This binary file has changed," and clicks "Open file in external program" per [1](#0-0) .
3. `openFile` calls `shell.openExternal('file://' + fullPath)` with no type check [4](#0-3) , causing the OS to execute `payload.exe` directly.

Note: I could not fully verify at what stage, if any, Electron's `shell.openExternal` itself imposes additional OS-level confirmation for executables on each platform (this behavior can vary by Electron/OS version), so the exact conditions under which this results in silent execution vs. an OS-level prompt should be confirmed via a live test in a Devin session rather than static code review alone.

```typescript
export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
```
