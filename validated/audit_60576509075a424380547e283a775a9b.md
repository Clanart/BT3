### Title
Shared-token escrow bucket lets a single-pair fill drain funds reserved for another still-open output pair in `IntentGatewayV2` same-chain fills - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntentGatewayV2` escrows a user's input tokens in a mapping keyed only by `(commitment, tokenAddress)` — `_orders[commitment][token]` — not by output-pair index. `_fillSameChain` decides whether to release the *entire* remaining balance of that bucket the moment a single output pair (`i`) reaches its own target (`amountFilled == totalRequired`), using `escrowedAmount = _orders[commitment][order.inputs[i].token]` instead of the proportional/allocated amount for that specific pair. If an order specifies the same input token for two or more output pairs (nothing in the reviewed code rejects duplicate input tokens across pairs), completing the first pair sweeps the combined escrow of *all* pairs that share that token, including the portion that was meant to back a different, still-unfilled output pair.

### Finding Description
Escrow bookkeeping is a single aggregate counter per token, confirmed by the withdrawal code path in `IntentsBase.sol`: [1](#0-0) 
which reads and decrements `_orders[body.commitment][token]` as one pooled balance, with no notion of which output pair a given slice of escrow "belongs" to.

`_fillSameChain` iterates over each output pair independently: [2](#0-1) 

For a pair `i` whose own cumulative fill just reached `totalRequired`, the contract computes the escrow to release like this: [3](#0-2) 

`_orders[commitment][order.inputs[i].token]` is the *whole* bucket for that token, not the sub-amount originally earmarked for pair `i`. If `order.inputs[j].token == order.inputs[i].token` for some other pair `j` that has not yet been (fully) filled, the escrow contributed for pair `j` sits in the very same bucket and gets swept out the moment pair `i` completes — even though `isFullyFilled` for the whole order is `false` and the loop explicitly tracks that (`if (totalRequired > amountFilled) isFullyFilled = false;`).

The order/output/input structures do not enforce distinct input tokens per pair; a user is free to construct an order like:
- `inputs = [ {USDC, 1000}, {USDC, 1000} ]`
- `output.assets = [ {DAI, 900}, {USDT, 900} ]`

which escrows `2000 USDC` total in one bucket keyed by `(commitment, USDC)`.

A solver who fills only the first pair (`900 DAI` to the beneficiary, `0` for the second pair) triggers `amountFilled == totalRequired` for pair 0, and the code releases `_orders[commitment][USDC] == 2000` (the entire bucket) to that solver in a single call, via `_withdraw`: [4](#0-3) 

Because `_orders[commitment][USDC]` is now zero, any later attempt to fill pair 1 or to cancel/refund the order will find `escrowed == 0` and revert with `UnknownOrder()`, permanently locking out the second pair's true beneficiary/refund from ever recovering the funds that were actually paid for the second, unfilled output.

### Impact Explanation
This is a direct, unauthorized transfer of escrowed user funds to an entity (a solver) who has not fulfilled the corresponding obligation, and a corresponding permanent loss/lock of funds legitimately reserved for the second output pair. It matches the bounty's accepted impacts: "stealing or loss of funds," "unauthorized transaction or execution," and "logic attacks" — it requires no relayer, prover, or admin compromise; it is exploitable purely by an unprivileged user/solver pair (which can be the same address self-filling their own same-chain order) crafting an order with a duplicated input token across pairs. The victim is anyone matching the eventual counter-fill or expecting a proportional/complete settlement of a multi-pair order that happens to reuse a token.

### Likelihood Explanation
Medium-to-high. Nothing in the reviewed `Order`/`TokenInfo` structures or `placeOrder` validation (as evidenced by the generic, per-token `_orders` mapping used uniformly across `_fillSameChain`, `_fillCrossChain`, `_cancelSameChain`, and `_withdraw`) rejects or normalizes duplicate input tokens across output pairs. An attacker only needs to be the order's own solver (self-fill is not restricted in the reviewed code) or collude trivially with a solver, and issue a single `fillOrder` call that fully satisfies one output pair while leaving another pair (sharing the same input token) unfilled.

### Recommendation
Track escrow per `(commitment, outputPairIndex)` rather than per `(commitment, tokenAddress)`, or, at minimum, cap the amount released on pair completion to the pair's own proportional allocation (`order.inputs[i].amount`) rather than reading the raw aggregate `_orders[commitment][token]` balance. Alternatively, reject orders at placement time whose `inputs[].token` values are not unique, closing the shared-bucket scenario entirely.

### Proof of Concept
1. User (attacker-controlled) calls `placeOrder` with:
   - `inputs = [ {token: USDC, amount: 1000e6}, {token: USDC, amount: 1000e6} ]`
   - `output.assets = [ {token: DAI, amount: 900e18}, {token: USDT, amount: 900e6} ]`
   - This escrows `2000e6 USDC` total, aggregated in `_orders[commitment][USDC] = 2000e6`.
2. Attacker (as solver, possibly the same EOA) calls `fillOrder(order, options)` with:
   - `options.outputs[0].amount = 900e18` (fully satisfies pair 0, DAI)
   - `options.outputs[1].amount = 0` (skips pair 1 entirely)
3. In `_fillSameChain`, iteration `i = 0`: `amountFilled(900e18) == totalRequired(900e18)` → `escrowedAmount = _orders[commitment][USDC] = 2000e6` is passed to `_withdraw`, which sets `_orders[commitment][USDC] = 0` and transfers the full `2000e6 USDC` to the solver — double what pair 0 alone should have released.
4. Iteration `i = 1`: `solverAmount == 0` and `remaining > 0` → `isFullyFilled = false`; pair 1's `900e6 USDT`/`1000e6 USDC` allocation is never paid, and `_filled[commitment]` is deleted, leaving the order nominally "open."
5. Any subsequent attempt to fill pair 1, or for the user to cancel the order to recover the `1000e6 USDC` meant for pair 1, calls into `_withdraw`/`_cancelSameChain`, which reads `_orders[commitment][USDC] == 0` and reverts `UnknownOrder()` — the second leg's funds are unrecoverable, having already been paid out to the solver in step 3.
