## Finding

### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is silently captured by the Host instead of the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.sol`'s `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept native ETH (`msg.value`) as an alternative fee-payment method and forward the *entire* `msg.value` into `IUniswapV2Router02.swapETHForExactTokens`. Unlike the `IntentGatewayV2.sol`/`ExtrinsicIntents.sol` contracts in this same repo, which explicitly compute `msgValue -= amounts[0]` and refund any leftover ETH to `msg.sender` at the end of the call, `EvmHost.sol` has no such refund step. This is the exact bug class from the external report: any ETH sent above the amount actually required for the fee swap becomes permanently locked as protocol balance rather than being returned to the user who sent it.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

the check is simply `if (msg.value > 0)`, and the router call is:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```
`swapETHForExactTokens` only consumes the exact ETH needed to buy `post.fee` units of the fee token; any unused portion of the `{value: msg.value}` sent to the router is refunded by the router **to its immediate caller**, which is `EvmHost` itself (`msg.sender` inside the router call), not the original end user who called `dispatch()`. The same pattern repeats verbatim in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

Note the contrast with the correct pattern that exists elsewhere in this same repository — `IntentGatewayV2.sol` and `ExtrinsicIntents.sol` explicitly track and refund the ETH remainder after the identical Uniswap swap call: [4](#0-3) [5](#0-4) 

`EvmHost.sol` omits this refund entirely, so any user overpayment on `dispatch()`/`fundRequest()` accumulates as ETH balance inside `EvmHost`, recoverable only through the privileged `IHostManager.withdraw()` path (`function withdraw` restricted to `hostManager`), never back to the depositor.

### Impact Explanation
Every unprivileged caller of `IDispatcher.dispatch()` (POST/GET) or `fundRequest()` who pays with native token and sends any amount over the exact swap requirement (which is virtually guaranteed in practice, since callers cannot predict the AMM's exact input requirement for `swapETHForExactTokens`) has that surplus ETH permanently removed from their control and merged into host-controlled funds. This is a direct, unauthorized loss of user funds on a public entry point, matching the "stealing or loss of funds" impact category.

### Likelihood Explanation
High likelihood: this affects the default/expected usage pattern documented for native-token fee payment (`msg.value`) across `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, all public `payable` entry points on `EvmHost`. No malicious peer, relayer, prover, or admin is required — a normal user simply calling these functions with any ETH amount not exactly matching the AMM's required input triggers the loss.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the returned `amounts[0]` (actual ETH consumed) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented correctly in `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.01 ether` worth of ETH to be swapped for the fee token.
2. Inside `dispatch`, `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes; the router consumes only ~0.01 ether and refunds ~0.99 ether back to `msg.sender` of the router call, i.e., `EvmHost`.
3. `EvmHost` never forwards this refund to the user; the ETH now sits in `EvmHost`'s balance.
4. The user has no function to reclaim the 0.99 ether; only `hostManager` can later extract it via `withdraw()`, confirming permanent loss of funds from the user's perspective. [1](#0-0) [3](#0-2)
