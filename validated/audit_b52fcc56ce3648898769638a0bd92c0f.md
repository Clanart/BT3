### Analysis

The premise of the question—that only a `>= MM_INPUT_START` boundary check is applied to the data pointer—is incorrect. `CallerAccount::from_account_info` performs two separate, more precise checks:

1. **Host-pointer boundary check**: `account_info.data.as_ptr() as u64 >= MM_INPUT_START` rejects if the pointer to the fat-pointer field itself is inside VM input space. [1](#0-0) 

2. **Exact-equality check on the actual data pointer**: after double-translating the `&[u8]` out of the `RefCell`, the resulting `data.as_ptr()` is validated via `check_account_info_pointer` against `account_metadata.vm_data_addr`, which requires **exact equality**, not a threshold comparison: [2](#0-1) [3](#0-2) 

Since `account_metadata.vm_data_addr` is the runtime-computed, per-account address fixed at serialization time (`SerializedAccountMetadata::vm_data_addr`), an attacker cannot make `vm_data_addr` point anywhere near a region boundary of their choosing — any deviation causes `CpiError::InvalidPointer`.

Additionally, the length (`*ref_to_len_in_vm`) is bounds-checked in `get_serialized_data` against `original_data_len.saturating_add(MAX_PERMITTED_DATA_INCREASE)`, which is exactly the size of the region the runtime reserved for that specific account during parameter serialization: [4](#0-3) 

Because `vm_data_addr` is pinned to the exact expected address and `len` is capped to the exact reserved size for that same account, the resulting `[vm_data_addr, vm_data_addr+len)` range is bounded by construction and cannot extend into an adjacent account's serialized region or past `MM_INPUT_START`. This is also exercised by `test_get_serialized_data`, which confirms `InvalidRealloc` is returned when length exceeds the reserved space: [5](#0-4) 

`from_sol_account_info` follows the identical pattern with `check_account_info_pointer` on `account_info.data_addr`: [6](#0-5) 

Thus, the check is not merely a pointer-start validation but an exact-address pin combined with a length cap tied to the same account's original data length — the two together prevent the overrun scenario described in the question.
