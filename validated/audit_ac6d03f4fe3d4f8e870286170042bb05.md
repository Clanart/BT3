### Title
`clone()` explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safety check during recursive clone of untrusted repositories - (File: app/src/lib/git/clone.ts)

### Summary
The external report's broken invariant is "a security-relevant precondition/guard is bypassed at the exact call site that needs it most, negating an upstream safety mechanism and allowing an attacker-controlled input to reach a sensitive operation unguarded." In `BunniHook`, the unlock guard is skipped. In GitHub Desktop's `clone()` function, Git's own `GIT_CLONE_PROTECTION_ACTIVE` guard — which upstream Git added specifically to stop malicious repositories from exploiting `clone --recursive` — is deliberately forced to `'false'` for every clone Desktop performs.

### Finding Description
`clone()` builds the environment for the `git clone --recursive` invocation and sets: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE=false` disables the recursive-clone symlink/case-collision protections that upstream Git introduced (the mitigation for the class of clone-time submodule attacks, e.g. CVE-2024-32002-style issues, where a crafted repository/submodule tree can cause a `.git` directory or hook file to be written outside the intended submodule path via case-insensitive or symlink-based path collisions on a victim's clone). That protection is exactly the guard Git relies on to detect such collisions during `--recursive` clone; Desktop turns it off unconditionally for every clone of a user-supplied `url`, which is by definition attacker-influenced content (any public/private remote URL a user is enticed to clone, including from an "Open in Desktop" deep link handled via `parseAppURL`/`open-repository-from-url`). [2](#0-1) 

Combined with the `--recursive` flag, which auto-initializes and checks out every submodule without prompting, the code path takes a remote URL from an untrusted source (typed in by the user, or supplied via a deep link) straight into a recursive clone with the upstream protection turned off.

### Impact Explanation
If a crafted repository/submodule combination is able to trigger the exact collision condition that `GIT_CLONE_PROTECTION_ACTIVE` is designed to catch, disabling it removes the last line of defense at clone time, potentially allowing a malicious submodule's `.git` contents (including hooks) to be written into an unexpected location on disk on the victim's machine — a file-write-outside-repo primitive that can escalate to code execution when Git or another tool later executes a hook from that location. This directly matches the "attacker controls a cloned/fetched repository ... result is code execution / file write outside the repo" criterion.

### Likelihood Explanation
Likelihood depends on filesystem conditions (case-insensitive/case-mangling filesystems, or symlink support) matching the specific collision Git's protection targets, so it is not universally exploitable on every OS/filesystem combination. However, the trigger requires no special access beyond convincing a user to clone or open (via deep link) a repository the attacker controls or has staged malicious submodules in — no local access, no admin rights, and no prior compromise are needed, matching the valid-impact criteria for this scan.

### Recommendation
Do not unconditionally disable `GIT_CLONE_PROTECTION_ACTIVE`. Determine why it was set to `false` (likely to work around a specific legitimate clone scenario) and instead scope the override narrowly, or better, leave the protection enabled and handle any resulting Git errors/prompts explicitly rather than disabling the safety mechanism for all clones, especially since the `url`/submodule content is fully attacker-controlled in the clone flow.

### Proof of Concept
1. Attacker publishes (or hosts on a controllable git server/proxy) a repository containing a submodule reference engineered to trigger the case-collision/symlink condition that Git's `--recursive` clone protection is designed to reject (the same class of attack `GIT_CLONE_PROTECTION_ACTIVE` was added to guard against).
2. Victim clones the repository through GitHub Desktop's UI, or via an `x-github-client://openRepo/...` deep link handled by `parseAppURL` → `open-repository-from-url`, both of which funnel into `clone()`. [3](#0-2) 
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` and `--recursive` is always passed, Git performs the recursive submodule clone/checkout without the protective check that would otherwise abort or warn on the crafted collision, potentially placing hook/config files where they can later execute.

I could not find any accompanying comment, test, or changelog entry in the indexed code explaining why this variable is disabled, so I cannot rule out that there's a legitimate but narrower reason for it — a Devin session with full repo/history access would be needed to confirm intent and git-blame context before treating this as a confirmed regression versus an intentional (if risky) workaround.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
