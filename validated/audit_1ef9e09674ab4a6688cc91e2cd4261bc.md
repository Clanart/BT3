### Title
App Proxy request signature verification lacks replay protection (no timestamp freshness check) - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates that a request's `signature` query parameter matches an HMAC-SHA256 over the other query params (including `timestamp`), but it never checks that the `timestamp` value is recent. Any signed App Proxy request captured by an attacker (via browser history, referrer leakage, proxy/CDN logs, XSS on the storefront page, etc.) remains valid forever and can be replayed an unlimited number of times against the app.

### Finding Description
`query_string_valid?` extracts the `signature` parameter and recomputes the HMAC over the remaining query parameters, comparing with `secure_compare`: [1](#0-0) 

The `timestamp` field is part of the signed payload (`calculated_signature`) but its value is never compared against the current time or checked for staleness anywhere in this module, nor anywhere else in the codebase (`grep` for `timestamp` handling shows no freshness/expiry check for App Proxy requests, only for OAuth callback and session/token expiry, which are unrelated flows). This mirrors the reported bug class: a signed message (`RestoreData`/App Proxy query string) is not bound to a single use (no nonce, no timestamp-window enforcement), so any captured valid signature can be replayed indefinitely to reach a "privileged" (proxy-authenticated) action.

Any controller including this concern, such as the generated `AppProxyController`, trusts `verify_proxy_request` as its sole authorization gate: [2](#0-1) 

### Impact Explanation
Any endpoint that relies solely on `ShopifyApp::AppProxyVerification` for authorization (the documented, recommended way to protect App Proxy endpoints) can be invoked repeatedly by an unrelated, unauthenticated actor who has obtained a single previously-valid signed request URL. If such an endpoint performs a state-changing or resource-consuming action gated only by "this came from Shopify's proxy," the action can be repeated indefinitely by simply reusing the old URL — a genuine replay vulnerability class, consistent with the reported bug (signed message not bound to a single use).

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimately-signed App Proxy URL (e.g., via browser history/logs/referrer leakage/shared links, since App Proxy URLs are regular GET requests visible in the storefront), after which replay is trivial and unlimited — there is no expiry enforced by the library.

### Recommendation
Add a check in `query_string_valid?` (or a wrapping `before_action`) that rejects requests where `timestamp` is not within an acceptable freshness window (e.g., a few minutes) of the current server time, in addition to the existing HMAC check.

### Proof of Concept
1. Capture one valid, Shopify-signed App Proxy request URL for a shop (e.g., `GET /app_proxy/basic?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=...`), as shown to be accepted in [3](#0-2) .
2. At any later time, replay the exact same URL/query string.
3. `query_string_valid?` recomputes the same HMAC (inputs unchanged) and `secure_compare` succeeds, so `verify_proxy_request` allows the request through with no time-based check, regardless of how much time has elapsed.

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
