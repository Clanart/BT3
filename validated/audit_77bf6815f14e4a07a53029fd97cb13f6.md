## Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the pre-fee requested amount instead of the actual tokens received, corrupting the shared escrow pool for fee-on-transfer/rebasing input tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
The Tron build of `IntentGatewayV2.placeOrder` still contains the exact bug class from the external `EtherFiLib::_initiateWithdrawImpl` report: it assumes `amount transferred == amount received`. The main EVM `IntentGatewayV2.sol` was already patched to measure actual balances before/after each `transferFrom`, but the Tron variant's direct-transfer path was not, so escrow accounting can be inflated relative to the tokens the contract actually holds.

## Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

the contract does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the user-specified `order.inputs[i].amount` computed *before* the transfer even happens: [2](#0-1) 

There is no `balanceOf` snapshot before/after the transfer, unlike the corresponding EVM implementation which was hardened for exactly this class of bug: [3](#0-2) 

`_orders` is a per-`commitment` accounting map, but the actual ERC-20 balance backing it is a single shared pool held by the contract address across *all* orders using that token. If the input token charges a transfer fee or is a share/rebase-based rebasing token (the same class as eETH/stETH cited in the source report — where `transfer(x)` delivers `x` minus a few wei/bps due to internal rounding), the contract credits more escrow than it actually received.

`withdraw()` later trusts this bookkeeping and moves out exactly the escrowed `amount`: [4](#0-3) 

Because the escrow ledger for the affected commitment is now larger than what was actually deposited, satisfying that withdrawal drains tokens that in reality belong to other commitments sharing the same token pool.

## Impact Explanation
This breaks the "escrow must move exactly once and only to the rightful beneficiary and amount" invariant. Two concrete outcomes follow:
1. **Denial of service / fund lock**: once the shared token pool is short by the fee/rounding delta, a subsequent legitimate order's `withdraw()` for the same token reverts because the contract's real balance is insufficient, permanently stranding that user's/solver's funds until governance intervenes.
2. **Cross-order fund loss**: whichever commitment's withdrawal is processed first drains real tokens that were actually deposited by a *different* user's order, since `_orders[commitment][token]` bookkeeping no longer reflects the pooled on-chain balance. This is an unauthorized redirection of funds away from their rightful beneficiary, not merely a revert.

This requires no privileged actor, relayer, or malicious peer — any ordinary user placing an order with a fee-on-transfer or share-based rebasing ERC-20 as an input triggers the corruption for everyone else sharing that token's escrow pool on that gateway instance.

## Likelihood Explanation
Likelihood is moderate to high: the IntentGateway is explicitly documented to support "arbitrary" ERC-20 inputs (the sibling EVM contract even ships dedicated fee-on-transfer test coverage), so deploying/using this pathway with a non-standard ERC-20 is a normal, expected usage pattern, not a contrived edge case. No special permissions or timing are needed — a single `placeOrder` call with such a token is sufficient to desynchronize the escrow ledger from the real balance.

## Recommendation
Mirror the fix already applied to `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom` in the non-predispatch branch, and credit `_orders[commitment][token]` (and the value used to compute `reducedInputs`/commitment) with the actually-received delta rather than the nominal `order.inputs[i].amount`.

## Proof of Concept
1. Deploy a 1% fee-on-transfer ERC-20 and register it as an input token for the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs[0].amount = 1000e18` of this token (no predispatch calldata) — the contract only actually receives `990e18`, but `_orders[commitmentA][token]` is credited with `reducedInputs[0].amount` derived from `1000e18` (e.g. `1000e18` minus protocol fee, still based on the pre-transfer nominal amount).
3. User B places a normal order using the same token, contributing real, correctly-received tokens, growing the pool.
4. When commitment A is settled/cancelled, `withdraw()` transfers the inflated `_orders[commitmentA][token]` amount out of the shared contract balance, consuming tokens that belong to User B's escrow.
5. User B's subsequent `withdraw()` for their own commitment now reverts (`TransferFailed`/insufficient balance) or, depending on ordering, silently pays out less than escrowed — demonstrating the shared-pool corruption and resulting fund loss/DoS.
