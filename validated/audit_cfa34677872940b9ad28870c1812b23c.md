### Title
Unauthenticated third-party account association via `associatePubKey` skips proof-of-key-possession, enabling forced/front-run address association and balance migration - ([File: precompiles/addr/addr.go])

### Summary
The `addr` precompile at `0x0000000000000000000000000000000000001004` exposes two ways to link an EVM address to a Sei address: `associate` (which requires a valid ECDSA signature over a specific message, proving possession of the private key) and `associatePubKey`, which accepts a bare, self-supplied public key and performs the exact same privileged linking/migration logic without ever verifying that the caller controls the corresponding private key.

### Finding Description
`associate()` requires the caller to provide `v/r/s` of a signature over a fixed message ("Please sign this message to link your EVM and Sei addresses...") and recovers the public key from that signature, which cryptographically proves the caller possesses the private key for the address being associated [1](#0-0) .

In contrast, `associatePublicKey()` takes a raw hex-encoded compressed public key directly from `args[0]`, parses it, and derives `evmAddr`/`seiAddr` from it with no signature check whatsoever — proving nothing about who submitted the transaction versus who owns the key: [2](#0-1) .

Both paths converge on `associateAddresses`, which performs the privileged, one-time, irreversible linking and balance migration: [3](#0-2) .

The underlying `AssociateAddresses` helper mutates account state (sets a fresh account pubkey if none exists) and unconditionally migrates all `usei`/wei balance and removes the account at the direct-cast address: [4](#0-3) .

Because a secp256k1 public key is not secret — it is recoverable from any prior ECDSA signature the victim has ever produced (any EVM transaction, or the plaintext pubkey field embedded in Cosmos-SDK signed transactions) — any third party who has observed a single signed transaction from a victim can submit that public key to `associatePubKey` and force the association on the victim's behalf, without the victim's consent, at a time of the attacker's choosing (e.g., front-running the victim's own intended call).

This bypasses the "prove you hold the private key via a fresh signature" authentication step that `associate()` deliberately enforces, mirroring the CVE's root cause: a privileged registration/linking action that should require proof-of-possession of a key accepts a bare, attacker-supplied key material with no cryptographic challenge.

The direct-cast receive gate in the EVM keeper depends on whether an association already exists: `CanAddressReceive` returns `false` for the direct-cast address once a "true" association exists for the corresponding EVM address [5](#0-4) . An attacker who force-associates a victim's address earlier than the victim intended changes this gate's state at a time the victim does not control, flipping in-flight bank sends that target the un-associated cast address from "accepted" to "rejected" mid-flight.

### Impact Explanation
While the migrated funds still land in an address controlled by the same private key (no direct fund theft to the attacker), the attacker fully controls the *timing* of an otherwise victim-initiated, security-relevant state transition:
- It force-migrates all balances sitting at the EVM-address-derived Sei cast address and deletes that intermediate account, which can race with and break the victim's own pending flows (e.g., a deposit send targeting the cast address that has already been broadcast/relied upon, or an integration that assumes the cast address remains receivable until the victim explicitly opts into association).
- It permanently and irreversibly fixes the account's public key/association (the check at addr.go:241-244 makes this non-idempotent — the first party to call it "wins" the association), removing any assurance that the victim, not a third party, controls when/if this migration and account-pubkey-setting occurs.

This is a real authentication gap (unauthenticated third party performs a privileged registration action reserved for the key holder), but I could not confirm within the available context a path leading to unrecoverable fund loss for the victim (funds always end up at an address the victim's own key controls) — only a griefing/front-running effect on transaction timing and unexpected reverts of bank sends. I was not able to fully trace all downstream consumers of `CanAddressReceive` (e.g., IBC/bridge relayer paths) within the indexed context to determine whether a specific atomic external flow could result in a stuck/burned transfer.

### Likelihood Explanation
Trivial and cheap to exploit: any address's raw public key is either directly embedded in that address's own past Cosmos-SDK transactions or recoverable from any ECDSA-signed EVM transaction it has sent. The precompile call itself costs only the flat `50000` gas defined for `Associate`/`AssociatePubKey` [6](#0-5) , and requires no special privilege — any EVM caller can invoke it non-statically.

### Recommendation
Require proof-of-possession for `associatePubKey` the same way `associate()` does — e.g., require a signature (over a nonce/challenge or the calling transaction itself) verifiable against the submitted public key before performing `associateAddresses`, or remove the standalone `associatePubKey` entrypoint and route all public-facing links through the signature-verified `associate()` path.

### Proof of Concept
1. Observe any transaction previously broadcast by victim `V` (EVM tx or Cosmos-SDK tx) and extract `V`'s raw secp256k1 public key (trivial via ECDSA recovery from an EVM tx, or read directly from the plaintext `pub_key` field of a Cosmos-SDK signed tx).
2. As an unrelated attacker `A`, call the `addr` precompile's `associatePubKey(pubKeyHex)` with `V`'s public key, before `V` ever calls `associate`/`associatePubKey` themselves: [2](#0-1) .
3. The transaction succeeds; `V`'s EVM/Sei addresses are now associated as a side effect of `A`'s unrelated transaction, and any balance sitting at `V`'s direct-cast Sei address is migrated per `MigrateBalance` and the account is removed, all without `V`'s participation or consent [7](#0-6) .
4. Any transfer that was in flight to `V`'s cast address (constructed assuming it remained un-associated/receivable) is now rejected by `CanAddressReceive` [5](#0-4) .

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)

func (p PrecompileExecutor) associatePublicKey(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	// Takes a single argument, a compressed pubkey in hex format, excluding the '0x'
	pubKeyHex := args[0].(string)

	pubKeyBytes, err := hex.DecodeString(pubKeyHex)
	if err != nil {
		return nil, 0, err
	}

	// Parse the compressed public key
	pubKey, err := btcec.ParsePubKey(pubKeyBytes)
	if err != nil {
		return nil, 0, err
	}

	// Convert to uncompressed public key
	uncompressedPubKey := pubKey.SerializeUncompressed()

	evmAddr, seiAddr, pubkey, err := helpers.GetAddressesFromPubkeyBytes(uncompressedPubKey)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}
