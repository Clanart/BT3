### Title
Unauthenticated `InternalSendTx` broadcast when `client_verification=false` selects `Interceptors::Noop` - (File: `core/src/rpc/interceptors.rs`, `core/src/servers.rs`, `core/src/rpc/aggregator.rs`)

### Summary
The binding the question asserts — "reaching an `Internal*` method ⇔ holding the aggregator's own client cert (`our_cert`)" — is enforced only inside `only_aggregator_and_self`'s `is_internal` branch, which never runs when the server is started with `config.client_verification == false`. In that mode `create_grpc_server` installs `Interceptors::Noop`, which unconditionally returns `Ok(req)` for every request, including `InternalSendTx`, so any TCP client reaching the aggregator's gRPC port can call `internal_send_tx` and get its own crafted transaction inserted into the aggregator's tx-sender queue.

### Finding Description
Binding claimed: `caller reaches Internal* method` ⇔ `leaf_cert == our_cert` (checked in `only_aggregator_and_self`, `core/src/rpc/interceptors.rs:62-69`). This check exists solely inside the `OnlyAggregatorAndSelf` variant of `Interceptors`; the `Noop` variant at `core/src/rpc/interceptors.rs:30` bypasses it entirely (`Interceptors::Noop => Ok(req)`), so no cert or `is_internal()` check ever executes for that variant. Whether `Noop` or `OnlyAggregatorAndSelf` is installed is decided in `create_grpc_server` (`core/src/servers.rs:106-138`): when `config.client_verification` is `false`, the `ServerTlsConfig` is built without `.client_ca_root(...)` (line 111) and the interceptor is set to `Noop` (line 137), meaning the server does not require/verify a client certificate at the TLS layer at all, and the RPC-layer identity check is also skipped. `internal_send_tx` (`core/src/rpc/aggregator.rs:1270-1312`) parses `raw_tx` and calls `tx_sender.insert_try_to_send(...)`, queuing the caller-supplied transaction for the aggregator's fee-bumping infrastructure with no additional caller/ownership validation of the tx contents. Under `client_verification=false`, any client that can open a TCP/TLS connection to the aggregator's public port (no client cert required) can invoke `InternalSendTx` and have an arbitrary, self-crafted transaction inserted into the queue.

Existing guards do not prevent this: `is_internal()` is purely a metadata-header string check (`core/src/rpc/interceptors.rs:12-20`) that is never invoked under `Noop`; there is no separate authentication inside `internal_send_tx` itself; and `insert_try_to_send` only deduplicates by txid (`crates/clementine-tx-sender/src/client.rs:73-79`), performing no authorization.

### Impact Explanation
This matches the "High — an unauthenticated state-changing or broadcasting call" category: an unauthenticated caller can insert/broadcast a transaction of their choosing into the aggregator's tx-sender queue via `InternalSendTx`, reachable through the aggregator's own bitcoind connection and fee-bumping (CPFP/RBF) machinery. This is repeatable per call and does not depend on any specific deposit or operator. It does not by itself move bridge value, credit a wrong reimbursement, or burn honest collateral — `insert_try_to_send` only queues the attacker's own transaction for sending/fee-management; it doesn't sign or spend any N-of-N-controlled UTXO on the attacker's behalf, since the tx is already fully signed/valid off-protocol by the attacker. The concrete resource-consumption angle (aggregator's fee-payer/CPFP wallet being used to bump an attacker's own transaction) is explicitly out of scope per the rules (denial of service / resource exhaustion). What remains in scope is purely the authentication bypass itself: an unauthenticated party reaching a method labeled and gated as `Internal`.

### Likelihood Explanation
This requires the deployment to run with `config.client_verification = false`, i.e., mTLS-based client authentication disabled on the aggregator's gRPC listener — a real, non-test configuration knob (`core/src/config/mod.rs`, `core/src/servers.rs:106-138`), not a test-only artifact. The proto explicitly names this RPC `InternalSendTx` (`core/src/rpc/clementine.proto:779`) implying an intended trust boundary that is only actually enforced when `client_verification=true`. If an operator misconfigures/deploys with this flag off (or it defaults to off in some environment), the exposure is immediate and repeatable with zero BTC cost beyond a raw TCP/TLS connection to the aggregator's public port.

### Recommendation
Do not tie the `Internal*` authorization exclusively to the `OnlyAggregatorAndSelf` interceptor variant selected by `client_verification`. Either make `is_internal()` checks mandatory regardless of the TLS/interceptor mode (e.g., always require a validated peer identity for any `Internal*`-prefixed method, independent of `Noop`), or disallow selecting `Noop` for any server that exposes `Internal*` RPCs, and/or add explicit application-layer authentication inside `internal_send_tx` and other `Internal*` handlers rather than relying solely on transport-layer interceptors.

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}

    async fn internal_send_tx(
        &self,
        request: Request<clementine::SendTxRequest>,
    ) -> Result<Response<Empty>, Status> {
        #[cfg(not(feature = "automation"))]
        {
            Err(Status::unimplemented("Automation is not enabled"))
        }
        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }
    }
