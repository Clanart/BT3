## Finding: `aptos move verify-package` never checks the actual on-chain bytecode — it only compares self-declared metadata fields

### Title
`aptos move verify-package` claims to verify bytecode but only compares publisher-supplied metadata, allowing malicious/mismatched module bytes to appear "verified" - (File: `aptos-move/cli/src/commands.rs`, `aptos-move/cli/src/stored_package.rs`)

### Summary
The external report is about an EIP712 `TYPE_HASH` that omits a referenced struct type (`V3DutchInput`) and orders types incorrectly, so the value that is "hashed for verification" does not actually cover all the content it claims to attest to — allowing a mismatch between what is signed/verified and what is actually processed. The Aptos-native analog is `VerifyPackage` (`aptos move verify-package`): its doc comment promises it "verifies the bytecode matches a local compilation of the Move code," but the implementation never fetches or hashes the on-chain compiled bytecode at all. It only compares `PackageMetadata` fields (name, deps, module metadata, manifest, upgrade policy, and the publisher-supplied `source_digest`) between two objects that are both effectively derived from the CLI's own local build/metadata pipeline. As with the incomplete EIP712 typehash, the "verification" structure omits the one field that actually matters (the real deployed module bytes), so it cannot detect a mismatch between the source publicly claimed and the bytecode that actually executes on-chain.

### Finding Description
`VerifyPackage::execute` in [1](#0-0)  builds the package locally, then calls:
```rust
let registry = CachedPackageRegistry::create(client, self.account, false).await?;
...
package.verify(&compiled_metadata)?;
```
The `with_bytecode` flag is passed as `false`, so `CachedPackageRegistry::create` [2](#0-1)  never calls `client.get_account_module(...)` to fetch the deployed `.mv` bytecode, leaving the internal `bytecode: BTreeMap` empty.

`CachedPackageMetadata::verify` [3](#0-2)  then only compares `name`, `deps`, `modules` (which is `ModuleMetadata` — name/source/source_map, not bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest` between the on-chain `PackageMetadata` and a freshly-built local `PackageMetadata`. None of these fields is the actual compiled module bytecode that the Move VM executes; `source_digest` in particular is a value computed off-chain by the publisher's own tooling [4](#0-3)  and embedded in `metadata_serialized`, which is never checked on-chain against the actual `code` bytes in `code::publish_package_txn` [5](#0-4) .

Consequently, a publisher can submit a `metadata_serialized` blob whose `source_digest`, `manifest`, and `modules[].source` fields describe an innocuous/expected source tree, while the accompanying `code: vector<vector<u8>>` contains entirely different, malicious bytecode. `code::publish_package` in [6](#0-5)  only checks upgrade policy, module-name conflicts, and dependency policy — it does not tie `source_digest`/`modules[].source` to the actual `code` bundle. Anyone later running `aptos move verify-package` against this account will pull the same forged metadata, compare it to their own honest local build (which they believe matches the source), see all metadata fields match, and be told "Successfully verified source of package" — despite the fact that the deployed bytecode was never even downloaded or compared.

This is the direct analog of the reported bug class: a value ("source_digest"/PackageMetadata, like the EIP-712 typehash) is supposed to be a binding commitment over content that will later be trusted, but the construction/verification path omits the actual content (bytecode) it should cover, so the mismatch goes undetected.

### Impact Explanation
`verify-package` is the tool users, auditors, and dependents are told to rely on for confirming that on-chain code matches its claimed source, per the framework docs: "Build the package locally and verify that the on-chain copy matches" [7](#0-6) , and depending on upgradeable packages is explicitly flagged as risky unless "you know and understand the entity publishing the package" [8](#0-7) . Since `verify-package` never fetches or compares actual bytecode, it provides false assurance: malicious or compromised publishers can present code whose claimed source passes local re-verification while the real deployed bytecode does something entirely different. Anyone (a dependent contract deployer, a governance voter, an integrator) that uses this command as a trust gate before depending on or interacting with a package can be deceived into treating malicious code as verified/legitimate.

### Likelihood Explanation
No special privilege is required — any account can publish a package where the metadata's declared source fields do not correspond to the actual bytecode, since nothing in `code::publish_package` cross-checks `source_digest`/`modules[].source` against `code`. Any user who then runs the documented `aptos move verify-package` workflow trusting its stated guarantee will be silently misled; this requires no race condition or privileged governance action, only ordinary use of the shipped CLI tooling as intended.

### Recommendation
Change `VerifyPackage::execute` to always fetch the on-chain compiled bytecode (`with_bytecode = true`) and compare each downloaded `.mv` module byte-for-byte (or by hash) against the freshly compiled local bytecode, in addition to the existing metadata comparison. Do not rely solely on the publisher-supplied `source_digest`/metadata fields as a stand-in for actual bytecode equality.

### Proof of Concept
1. Compile a benign module `M_good` and compute its metadata (`source_digest`, `manifest`, `modules[].source` reflecting `M_good`'s source).
2. Construct a `metadata_serialized` blob using `M_good`'s metadata fields, but pass a different, malicious compiled module `M_evil` as the `code` argument to `code::publish_package_txn` (or `object_code_deployment::publish`). Nothing in `code.move`'s `publish_package` rejects this combination — see [6](#0-5) .
3. A third party runs `aptos move verify-package --account <addr>` against the local (honest) source of `M_good`.
4. `VerifyPackage::execute` calls `CachedPackageRegistry::create(client, account, false)` [9](#0-8) , which skips downloading module bytecode, and `package.verify(&compiled_metadata)` [3](#0-2)  only compares metadata fields, all of which match `M_good`.
5. The command prints "Successfully verified source of package" even though the actually deployed and executing module is `M_evil`, not `M_good`.

impl CachedPackageRegistry {
    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

    public fun publish_package(owner: &signer, pack: PackageMetadata, code: vector<vector<u8>>) acquires PackageRegistry {
        // Disallow incompatible upgrade mode. Governance can decide later if this should be reconsidered.
        assert!(
            pack.upgrade_policy.policy > upgrade_policy_arbitrary().policy,
            error::invalid_argument(EINCOMPATIBLE_POLICY_DISABLED),
        );

        let addr = signer::address_of(owner);
        if (!exists<PackageRegistry>(addr)) {
            move_to(owner, PackageRegistry { packages: vector::empty() })
        };

        // Checks for valid dependencies to other packages
        let allowed_deps = check_dependencies(addr, &pack);

        // Check package against conflicts
        // To avoid prover compiler error on spec
        // the package need to be an immutable variable
        let module_names = get_module_names(&pack);

        // Record, per module in this package, the object's transitive root owner at (re)publish, so
        // lazy self-init can detect a later transfer of the object or an ancestor since that module
        // was published (see `init::internal_maybe_initialize`). Objects only; feature-gated.
        if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
            let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
            module_names.for_each_ref(|name| {
                init::record_deploy_owner(addr, *name.bytes(), owner);
            });
        };
        let package_immutable = &borrow_global<PackageRegistry>(addr).packages;
        let len = package_immutable.length();
        let index = len;
        let upgrade_number = 0;
        package_immutable.enumerate_ref(|i, old| {
            let old: &PackageMetadata = old;
            if (old.name == pack.name) {
                upgrade_number = old.upgrade_number + 1;
                check_upgradability(old, &pack, &module_names);
                index = i;
            } else {
                check_coexistence(old, &module_names)
            };
        });

        // Assign the upgrade counter.
        pack.upgrade_number = upgrade_number;

        let packages = &mut borrow_global_mut<PackageRegistry>(addr).packages;
        // Update registry
        let policy = pack.upgrade_policy;
        if (index < len) {
            pack.modules.for_each_ref(|m| {
                let m: &ModuleMetadata = m;
                init::reset_initialized(addr, *m.name.bytes());
            });
            *packages.borrow_mut(index) = pack
        } else {
            packages.push_back(pack)
        };

        event::emit(PublishPackage {
            code_address: addr,
            is_upgrade: upgrade_number > 0
        });

        // Request publish
        if (features::code_dependency_check_enabled())
            request_publish_with_allowed_deps(addr, module_names, allowed_deps, code, policy.policy)
        else
        // The new `request_publish_with_allowed_deps` has not yet rolled out, so call downwards
        // compatible code.
            request_publish(addr, module_names, code, policy.policy)
    }
