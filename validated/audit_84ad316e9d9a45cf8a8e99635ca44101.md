### Title
Unbounded Python-level recursion in wallet outer-puzzle driver matching allows attacker-triggered stack exhaustion - (File: chia/wallet/outer_puzzles.py)

### Summary
`chia/wallet/outer_puzzles.py`'s `match_puzzle()` and each `DriverProtocol` implementation (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`) recursively call back into `self._match(...)` on the "inner puzzle" of every matched layer, with no depth limit, in order to reconstruct the `also` chain of nested asset layers. [1](#0-0)  Each driver's `match()` recurses into its own inner puzzle unconditionally: e.g. `CATOuterPuzzle.match()`, `OwnershipOuterPuzzle.match()`, `MetadataOuterPuzzle.match()`, and `CROuterPuzzle.match()` all call `self._match(UnknownPuzzle(known_program=inner_puzzle))` after unwrapping one curried layer. [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

This is analogous to CVE-2019-12213 in FreeImage's `TIFFReadDirectory`: an untrusted, attacker-crafted input structure drives an unbounded recursive parse routine that keeps calling itself, eventually exhausting the call stack of the process performing the parse (Python's default recursion limit / OS stack, as opposed to C's stack in the original CVE).

### Finding Description
A wallet recognizes the layered structure of an asset (CAT wrapped in CR, wrapped in revocation, singleton wrapped in ownership/metadata/singleton for NFTs, etc.) by repeatedly currying/uncurrying a puzzle and recursively calling `match_puzzle()` -> driver `.match()` -> `self._match()` on the next inner layer, once per nested "outer puzzle" layer, with no upper bound on nesting depth. [6](#0-5) 

An attacker can construct a puzzle reveal (a valid CLVM program, cheap to build via nested `curry()` calls with no execution needed) that stacks an arbitrarily large number of matchable outer layers — e.g., thousands of nested CAT layers, or nested singleton/ownership/metadata layers — around some innermost puzzle. This puzzle reveal need only be presented to the victim's wallet as a coin spend that the wallet must classify (for example, a coin received by the wallet, an incoming offer, or a coin spend fetched during sync/interested-puzzle-hash resolution). When the wallet calls `match_puzzle()` to identify the asset type, each layer triggers another Python-level recursive call into `_match`, with no depth check anywhere in `chia/wallet/outer_puzzles.py`, `chia/wallet/cat_wallet/cat_outer_puzzle.py`, `chia/wallet/nft_wallet/*.py`, or `chia/wallet/vc_wallet/cr_outer_puzzle.py`.

Unlike the CLVM interpreter's own tree-hashing code, which was explicitly rewritten to be iterative to avoid "blowing out the python stack" (see `chia/types/blockchain_format/tree_hash.py`'s docstring), [7](#0-6)  the outer-puzzle driver matching code was not given the same treatment and recurses natively in Python. There is no `sys.setrecursionlimit` guard, no explicit depth counter, and no CLVM-cost-based bound on the number of `also` layers a puzzle reveal can encode — the search for `RecursionError`/`setrecursionlimit` handling in the repository returned no results, confirming the absence of any mitigation.

Sufficiently deep nesting will exhaust Python's call stack (`RecursionError: maximum recursion depth exceeded`), which is unhandled at any of these call sites, crashing or hanging the wallet's coin-recognition/sync task when it processes the malicious coin/offer.

### Impact Explanation
This falls into the "spend-triggered transaction-processing halt" category permitted by the validation rules: a single malicious puzzle reveal (delivered via a coin sent to the victim, or via an offer file the victim inspects/accepts) can crash the wallet process or hang its sync loop while trying to classify the asset, denying wallet service to the user (e.g., inability to sync, inability to process further coin states, inability to accept/inspect other offers) until the offending coin/data is manually purged. This is a Medium-severity denial-of-service, matching the CVSS profile of the analog CVE (network-adjacent, low complexity, no privileges, user-interaction required, availability impact only).

### Likelihood Explanation
Likelihood is Medium-High: constructing deeply curried CLVM puzzles is computationally cheap (pure data construction, no execution needed) and does not require broadcasting a spendable/valid transaction — it only requires the victim's wallet to encounter the puzzle reveal (e.g., as a coin sent to a wallet-owned/watched puzzle hash, or as part of an offer file shared with the victim, both of which are explicitly in-scope reachable actions for "wallet user" / "offer counterparty" personas). No signature or on-chain acceptance is required for a puzzle reveal to be processed by the wallet's recognition logic.

### Recommendation
- Add an explicit maximum nesting-depth counter (or CLVM cost accounting) to `match_puzzle()` in `chia/wallet/outer_puzzles.py` and thread it through all `DriverProtocol.match()`/`get_inner_puzzle()`/`get_inner_solution()`/`solve()` implementations, raising a clear error once a sane depth limit (e.g., matching the maximum realistic number of legitimate layers used in the codebase, a small constant) is exceeded.
- Alternatively, convert the recursive matching algorithm into an iterative loop (as was already done for `sha256_treehash` in `chia/types/blockchain_format/tree_hash.py`) to make it immune to stack-depth-based DoS regardless of nesting depth.
- Wrap wallet-side puzzle classification calls (coin recognition during sync, offer inspection) so a `RecursionError` (or newly introduced depth-limit exception) is caught and treated as "unrecognized puzzle" rather than propagating and potentially crashing/hanging the wallet task.

### Proof of Concept
Conceptual PoC (not executed, since no code execution tool is available in ask-only mode):
1. Build an innermost `Program` (e.g., `Program.to(1)`).
2. Repeatedly wrap it N times (N large, e.g. 50,000–100,000) using `construct_cat_puzzle(CAT_MOD, tail, inner)` from `chia/wallet/cat_wallet/cat_utils.py`, producing `puzzle_N`, purely via currying (no CLVM execution required), analogous to the existing test `test_cat_outer_puzzle` which does one level of nesting (`double_cat_puzzle`). [8](#0-7) 
3. Wrap `puzzle_N` as an `UnknownPuzzle` and call `match_puzzle(UnknownPuzzle(known_program=puzzle_N))` from `chia/wallet/outer_puzzles.py`.
4. Observe that `CATOuterPuzzle.match()` recurses N times via `self._match(...)` (line 42 of `cat_outer_puzzle.py`), eventually raising `RecursionError` once N exceeds Python's default recursion limit (~1000), well before N reaches tens of thousands — demonstrating that a wallet given such a puzzle reveal (e.g., from a received coin or an offer) would crash/hang instead of gracefully rejecting the malformed/oversized structure.

def test_cat_outer_puzzle() -> None:
    ACS = Program.to(1)
    tail = bytes32.zeros
    cat_puzzle: Program = construct_cat_puzzle(CAT_MOD, tail, ACS)
    double_cat_puzzle: Program = construct_cat_puzzle(CAT_MOD, tail, cat_puzzle)
    uncurried_cat_puzzle = UnknownPuzzle(known_program=double_cat_puzzle)
    cat_driver: PuzzleInfo | None = match_puzzle(uncurried_cat_puzzle)

    assert cat_driver is not None
    assert cat_driver.type() == "CAT"
    assert cat_driver["tail"] == tail

    assert inside_cat_driver.type() == "CAT"
    assert inside_cat_driver["tail"] == tail
