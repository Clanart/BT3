Based on my investigation, I found a concrete local analog: `BandwidthManager.setHost` accepts a zero address for the critical `_host` binding, with no ability to recover.

### Title
`BandwidthManager.setHost` permanently bricks bandwidth purchases and locks escrowed fee tokens if set to the zero address - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager` mirrors the WstETH pattern exactly: a one-time setter for a critical dependency address performs no `!= address(0)` validation. Unlike `IntentGatewayV2._validateParams` and `EvmHost.updateHostParamsInternal`, which explicitly reject `address(0)`/non-contract values for `host`, `dispatcher`, `hostManager`, `handler`, and `consensusClient`, `BandwidthManager.setHost` has no such guard.

### Finding Description
`setHost` only checks that `_host` hasn't already been set — it never validates the incoming `hostAddr`: [1](#0-0) 

Once `_host` is fixed (to any non-zero value, including `address(0)`), it is single-write and can never be corrected. `host()` returns `_host` unconditionally: [2](#0-1) 

Every fund-moving path depends on `_host` resolving to a live `IDispatcher`/`IHost`: `purchase()` calls `IDispatcher(_host).feeToken()` and `IDispatcher(_host).dispatch(...)` after pulling the buyer's ERC-20 into escrow: [3](#0-2) 

and `onAccept` (the only path that can trigger `Withdraw`, i.e. release escrowed/purchased funds to a beneficiary) is gated by `onlyHost`, which resolves via `host()`: [4](#0-3) 

If `_host` is ever zero (or an EOA with no `feeToken()`/`hyperbridge()` implementation), `purchase()` will revert on the `IDispatcher(_host).feeToken()` call — but only after `safeTransferFrom` has already pulled the buyer's tokens in cases where the revert happens after transfer, or more critically, any prior successful `purchase()` calls that already escrowed tokens in the contract become permanently unrecoverable, because `onAccept`'s `restrict(_params.host)`-equivalent `onlyHost` check can never be satisfied by the real Hyperbridge relayer path (governance `Withdraw` messages route through the real host, which no longer matches). This differs from `EvmHost`/`IntentGatewayV2`, which explicitly enforce `host != address(0) && host.code.length != 0` and check `ERC165` interface conformance before accepting a critical address, and from `HyperFungibleTokenImpl`, which explicitly `require(admin != address(0), ...)`.

### Impact Explanation
This is a fund-loss / lock condition matching the bounty's "stealing or loss of funds" category: fee tokens already escrowed in the `BandwidthManager` contract (from `purchase()`) become permanently unwithdrawable if `_host` is misconfigured to zero or to a non-conforming address, since the only exit path (`onAccept` → `Withdraw`) requires `msg.sender == _host` and `request.source == IHost(_host).hyperbridge()`, both of which are unreachable if `_host` is wrong.

### Likelihood Explanation
`setHost` is `onlyOwner`, so a malicious *unprivileged* actor cannot directly call it. However, unlike `IntentGatewayV2` and `EvmHost` (which use `_disableInitializers()`/one-shot `initializer` patterns with explicit zero/interface checks), `BandwidthManager` provides no defense-in-depth: a single operational mistake (e.g. copy-pasting an unset env var, or a deploy script bug like the `DeploySimplexPaymaster.s.sol` pattern which reads addresses straight from config with no on-chain guard) permanently locks any escrowed buyer funds with no recovery path, in a contract explicitly designed to hold buyer ERC-20 balances pending dispatch. This is materially less safe than the sibling contracts in the same repo that already implement the recommended check, indicating the omission here is a genuine gap rather than an accepted risk.

### Recommendation
Add the same guard already used elsewhere in the codebase (e.g. `IntentsBase._validateParams`, `EvmHost.updateHostParamsInternal`):
```solidity
function setHost(address hostAddr) public onlyOwner {
    if (_host != address(0)) revert UnauthorizedAction();
    if (hostAddr == address(0) || hostAddr.code.length == 0) revert InvalidHost();
    _host = hostAddr;
}
```

### Proof of Concept
1. Deploy `BandwidthManager` via `constructor(owner)`.
2. Owner calls `setHost(address(0))` (or an address with no code) — passes because the only check is `_host != address(0)` (the *current* stored value, not the argument).
3. `_host` is now permanently fixed to a broken value; there is no second `setHost` call possible.
4. Any buyer who calls `purchase()` before this point (or a version where `_host` is briefly valid then never updatable, e.g. a proxy pattern is not used here) has no recovery: `onAccept`'s `onlyHost` modifier can never be satisfied by the legitimate Hyperbridge relay, so the `Withdraw` governance action can never be dispatched to release the escrowed fee tokens back out of the contract.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
