## Title
`SimplexPaymaster.onAccept` authenticates the source chain but not the sending module, allowing any Hyperbridge-originated request to trigger governance actions (upgrade, token registry, fund withdrawal) - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster.onAccept()` is the sole entry point for privileged governance actions (`UpgradeContract`, `UpdateParams`, `RegisterToken`, `DeactivateToken`, `WithdrawAssets`). Its authentication check only verifies that the ISMP request's `source` field matches the Hyperbridge chain identifier — it never checks `incoming.request.from`, i.e. which module/pallet on Hyperbridge actually dispatched the request. This is the same class of "trust the aggregate, not the individual entry" defect the external report flags for unbounded/unchecked collections, mapped here onto Hyperbridge's cross-chain module-binding invariant: request paths must bind chain id **and** module/app identity, not chain id alone.

### Finding Description
`onAccept` is guarded by `onlyHost` (only the local `IHost` may call it) and then performs: [1](#0-0) 

The only content check is:
```solidity
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) {
    revert UnauthorizedCall();
}
```
This confirms the message originated from the Hyperbridge **chain**, but says nothing about which **module** on that chain dispatched it (the `from` field of the ISMP `PostRequest`). Any permissionless or lower-privileged pallet/contract capable of dispatching an ISMP POST request from Hyperbridge to this paymaster's address on the destination EVM chain can craft a body whose first byte selects `RequestKind.WithdrawAssets`, `RequestKind.UpgradeContract`, etc., and it will be executed exactly as if it came from Hyperbridge's actual governance module.

This directly violates the stated pivot: *"Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow."* The contract's own doc-comment states the security model explicitly assumes every administrative action is "authenticated as originating from Hyperbridge governance," but the code only authenticates the chain, not the governance module identity.

Other governance-style apps in this repo bind on `request.from` in addition to `request.source` (e.g. `EvmHost.sol` and `ExtrinsicIntents.sol` reference `request.from` checks), which is the correct pattern that `SimplexPaymaster` is missing.

### Impact Explanation
`WithdrawAssets` sweeps the paymaster's accrued ERC-20 surplus or its entire EntryPoint native deposit to `treasury`: [2](#0-1) 
Combined with `UpgradeContract`'s `ERC1967Utils.upgradeToAndCall`, an attacker able to trigger `onAccept` from any non-governance Hyperbridge module can fully brick or take over the paymaster, or redirect/withdraw all funds intended for gas-sponsorship, without needing a malicious relayer, prover, or leaked key — only the ability to get *some* module on Hyperbridge to originate a POST request whose `from`/body an attacker controls. This is a direct fund-loss / unauthorized-execution primitive matching the bounty's accepted impact classes.

### Likelihood Explanation
Likelihood depends on whether any non-privileged path on Hyperbridge can be induced to dispatch an arbitrary-body POST request with `dest` set to the paymaster's chain/address and reachable to an attacker-controlled encoding of `from`+`body`. Given Hyperbridge hosts many permissionless-dispatch pallets (bandwidth purchases, intents, token-governor, relayer messages) and the missing check is unconditional (no module allowlist at all on the receiving end), this is a structural gap rather than a hypothetical timing/race condition — it is a straightforward missing-authorization bug, independent of proof correctness (the ISMP proof itself is legitimately verified; it's the *identity* inside the verified message that isn't checked).

### Recommendation
Add an explicit check on `incoming.request.from` against a governance module identifier configured at `initialize`/via `UpdateParams` (mirroring how other Hyperbridge apps such as `EvmHost.sol`/`ExtrinsicIntents.sol` bind on `from`), rejecting any request whose `from` does not match the expected Hyperbridge governance module id, in addition to the existing `source` chain check.

### Proof of Concept
1. Identify or deploy any Hyperbridge pallet/module capable of dispatching an ISMP POST request to the destination chain/address of `SimplexPaymaster` (dispatch is a widely available primitive on Hyperbridge, not gated to a single governance module).
2. Construct the request body as `abi.encodePacked(uint8(RequestKind.WithdrawAssets), abi.encode(tokenAddress, amount))`.
3. Dispatch this request from the arbitrary module; `request.source` will correctly equal the Hyperbridge chain identifier (since it genuinely comes from Hyperbridge), satisfying the only check in `onAccept`.
4. Once delivered and proven through the normal `IHost`/handler pipeline (a legitimate proof, since it really is a Hyperbridge-originated message), `onlyHost` and the `source` check both pass, and `_withdrawAssets` executes, sweeping the paymaster's registered token balance or EntryPoint deposit to `treasury` — bypassing the intended "governance-only" restriction because `from` (the actual sending module) was never validated.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
```text
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) {
            revert UnauthorizedCall();
        }

        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        bytes calldata payload = incoming.request.body[1:];

        if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(payload, (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        } else if (kind == RequestKind.UpdateParams) {
            _setParams(abi.decode(payload, (Params)));
        } else if (kind == RequestKind.RegisterToken) {
            (address token, address oracle) = abi.decode(payload, (address, address));
            _registerToken(token, AggregatorV3Interface(oracle));
        } else if (kind == RequestKind.DeactivateToken) {
            _deactivateToken(abi.decode(payload, (address)));
        } else if (kind == RequestKind.WithdrawAssets) {
            (address token, uint256 amount) = abi.decode(payload, (address, uint256));
            _withdrawAssets(token, amount);
        }
    }
```
