### Title
`Scanner::scan_block` reports coinbase outputs as immediately spendable `ReceivedOutput`s — (`networks/bitcoin/src/wallet/mod.rs:221`)

### Summary
`Scanner::scan_block` iterates `block.txdata` including `txdata[0]` (the coinbase transaction) and returns any outputs paying to a registered script as `ReceivedOutput`. `SignableTransaction::new` and `TransactionMachine` then build and sign a spend of that output with no maturity check. The analog to the report is exact: a value reported as received (`amountReceived` / `ReceivedOutput::value()`) is trusted in downstream spend/fee math without verifying the funds are actually spendable, because coinbase outputs are immature for 100 blocks.

### Finding Description
`scan_transaction` matches only `output.script_pubkey` against the registered script map and emits a `ReceivedOutput` containing just `offset`, `output`, and `outpoint` — nothing records whether the parent transaction was a coinbase. `scan_block` unconditionally scans `block.txdata[0]`. `SignableTransaction::new` (send.rs:150) sums `input.output.value` for funding and fee math, and `multisig`/`sign` produce a signed transaction spending the outpoint. A transaction spending an immature coinbase output is consensus-invalid and cannot be relayed or confirmed, yet the library reports it as available balance and produces a fully signed (but unbroadcastable) transaction. `ReceivedOutput` exposes no `is_coinbase`/maturity flag, so callers cannot distinguish these outputs from the `ReceivedOutput` API alone.

### Impact Explanation
Funds reported received that are not spendable: any system crediting scanned outputs (e.g., treating `ReceivedOutput::value()` as balance) overstates its balance and will sign transactions that are invalid at the consensus layer. This can lock up legitimate inputs alongside the immature one in a single signed transaction and misreport vault balances — the same shape as over-reported `amountReceived` feeding reward math.

### Likelihood Explanation
Reachable by an unprivileged party: a miner (or anyone able to get a transaction into a block — coinbase requires winning the block, so this requires mining) can pay the vault's tweaked script in a coinbase output. Unlike the FROST paths, the bytes flow entirely through public block data into `scan_block`, which performs no maturity check. The doc comment acknowledges the caveat, but the API neither filters nor flags the output, so the burden is undocumented in the type itself and trivially missed.

### Recommendation
Have `scan_block` skip `txdata[0]` or tag `ReceivedOutput` with an `is_coinbase` flag; at minimum, have `SignableTransaction::new`/`multisig` reject coinbase-derived inputs until maturity can be proven (e.g., require the caller to supply confirmation height and enforce `height + 100 <= tip`).
