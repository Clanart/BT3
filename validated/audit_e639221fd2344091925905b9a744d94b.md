## Analysis

The C4 report's core issue is a **state-changing operation triggered without owner/user consent**, driven entirely by an attacker-supplied input, whose side effects are silently reflected as if the legitimate user intended them.

The closest analog in GitHub Desktop is the `x-github-client://openRepo/...` protocol handler. Unlike `addLiquidity`, which lacked a caller check, Desktop's flaw is that the deep-link handler performs **consequential git operations (fetch + branch checkout) with zero user confirmation**, based solely on attacker-controlled URL query parameters, and the only validation applied is a superficial "no invalid git ref characters" check — not a trust/intent check.

### Title
Deep-link `openRepo` action silently fetches and checks out an attacker-chosen branch without user confirmation - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The `x-github-client://openRepo/<url>?branch=<name>` protocol action is parsed by `parseAppURL` [1](#0-0)  and dispatched straight into `Dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl`, which fetches the remote and checks out the attacker-specified branch automatically, with no confirmation dialog shown to the user.

### Finding Description
`parseAppURL` validates the `branch` query parameter only against `testForInvalidChars`, a regex that rejects git-illegal ref characters but performs no semantic/ownership validation of the branch name [2](#0-1) [3](#0-2) .

Once parsed, `dispatchURLAction` routes `open-repository-from-url` actions straight to `openRepositoryFromUrl` [4](#0-3) , which — if a `branch` is present — calls `openBranchNameFromUrl`: [5](#0-4) 

This function unconditionally:
1. Opens or clones the repository from the attacker-supplied `url`.
2. Refreshes the repo state.
3. Runs a **user-initiated fetch** against the remote.
4. Calls `checkoutLocalBranch` with the attacker-controlled branch name — all without ever prompting the user to confirm.

There is no check that the branch name corresponds to a branch the user actually intended to work with, no diff/confirmation dialog, and no distinction between a branch that already has uncommitted local changes tracked against it versus a fresh checkout target. The only "access control" in the whole chain is the OS-level fact that the user must click a link; once clicked, Desktop treats the deep link's `branch` parameter as fully trusted intent, exactly the same class of flaw as the missing caller check in `addLiquidity` — the function performs an impactful state change (checkout) driven by attacker-supplied parameters without a "is this what the user wants" gate.

By contrast, note that the `filepath` parameter *is* defended (absolute-path rejection and `resolveWithin` containment) [6](#0-5) , showing the developers recognized deep links need hardening for some parameters but did not apply the same discipline to the `branch` checkout path.

### Impact Explanation
A user who clicks an attacker-crafted `x-github-client://openRepo/<repo-url>?branch=<attacker-branch>` link (e.g., embedded in a webpage, chat message, or malicious README instructing "click to view PR") will have Desktop silently clone/open the target repository, fetch, and switch the working directory to the attacker-chosen branch — with no confirmation UI. If this repository is one the user already has open with uncommitted or staged local work, or if the user subsequently commits/pushes under this silently-switched branch context believing they're still on their previous branch, this constitutes silent corruption of what the user commits or pushes, matching the disclosed impact bucket for this class of finding.

### Likelihood Explanation
The attack requires only that a user click a single external link — a normal, expected interaction pattern Desktop explicitly supports via `app.setAsDefaultProtocolClient` and `open-url`/`--protocol-launcher` handling [7](#0-6) [8](#0-7) . No local access, malware, or leaked credentials are needed, satisfying the valid-impact criteria (attacker-controlled deep link the user clicks).

### Recommendation
Before performing the fetch/checkout in `openBranchNameFromUrl` (and in `openPullRequestFromUrl`'s `_checkoutPullRequest` call), surface an explicit confirmation dialog showing the target repository, remote, and branch, and require the user to approve the action — mirroring the existing safeguards already applied to the `filepath` parameter. Additionally, warn/block if the target repository currently has uncommitted changes on a different branch before switching.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo/https://github.com/victim-org/private-repo?branch=malicious-payload-branch`.
2. Victim, who already has `victim-org/private-repo` cloned locally with uncommitted work, clicks the link (e.g., in a phishing email or malicious webpage).
3. `main.ts`'s `open-url` handler invokes `handleAppURL` → `parseAppURL`, producing `{ name: 'open-repository-from-url', url, branch: 'malicious-payload-branch' }` [9](#0-8) .
4. `dispatchURLAction` routes to `openRepositoryFromUrl` → `openBranchNameFromUrl`, which fetches and checks out `malicious-payload-branch` with no prompt [10](#0-9) .
5. The user's working directory is now silently on an attacker-chosen branch; any subsequent commit/push by the user occurs under unintended context.

Note: I was unable to inspect the full body of `checkoutLocalBranch` within the tool budget available; confirming whether it performs any additional safety check (e.g., dirty-worktree guard) would strengthen or narrow this finding, and I recommend that a follow-up session verify this directly in `app/src/ui/dispatcher/dispatcher.ts`.

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

function handleAppURL(url: string) {
  log.info('Processing protocol url')
  const action = parseAppURL(url)
  onDidLoad(window => {
    // This manual focus call _shouldn't_ be necessary, but is for Chrome on
    // macOS. See https://github.com/desktop/desktop/issues/973.
    window.focus()
    window.sendURLAction(action)
  })
}

    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })
