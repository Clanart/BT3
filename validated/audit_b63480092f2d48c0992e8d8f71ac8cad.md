### Title
Gnosis chain's `IUniswapV2Router02` fee-swap wrapper silently absorbs user overpayment in `IntentGatewayV2.placeOrder`, permanently locking user funds - ([File: evm/src/utils/uniswapv2/GnosisUniswapV2Wrapper.sol])

### Summary
The external report's core broken invariant is: an exact-output-style DEX call is executed without any mechanism to reconcile the actual amount spent against the amount the caller sent, so leftover value that should be refunded to the user is never returned. In Hyperbridge's `IntentGatewayV2.placeOrder`, the fee-payment path performs exactly this kind of exact-output swap through the configured `uniswapV2Router` and relies on the router's return value (`amounts[0]`) to know how much native value was actually spent, refunding the remainder to the user. On Gnosis, that router is not a real Uniswap V2 router but `GnosisUniswapV2Wrapper`, whose `swapETHForExactTokens` implementation ignores the requested `amountOut` and unconditionally consumes and reports the entire `msg.value` as spent — breaking the refund invariant and trapping user funds in the contract.

### Finding Description
In `IntentGatewayV2.placeOrder`, when the user pays the order fee in native token, the contract performs an exact-output swap and then computes the remaining unspent value from the router's reported input amount: [1](#0-0) 

This logic assumes `swapETHForExactTokens` behaves like the real UniswapV2 router: it spends only as much ETH as required to produce exactly `order.fees` output tokens, and `amounts[0]` reflects that (smaller) spent amount, leaving `msgValue - amounts[0]` to be refunded to `msg.sender`.

On Gnosis, `IDispatcher(hostAddr).uniswapV2Router()` points to `GnosisUniswapV2Wrapper`, whose `swapETHForExactTokens` is: [2](#0-1) 

This function does not honor `amountOut` at all — it only checks `amountOut > msg.value` for a sanity revert, then wraps and transfers the **entire** `msg.value` to `msg.sender` (which is `IntentGatewayV2` itself), and returns `out[0] = msg.value`, not the amount actually needed to satisfy `order.fees`.

Consequently, back in `placeOrder`:
- `amounts[0]` always equals the full `msgValue` sent into the swap call, so `msgValue -= amounts[0]` always zeroes out `msgValue`, regardless of whether the user sent more native token than `order.fees` required.
- The refund branch (`if (msgValue > 0) { ... }`) never fires for any leftover, because there is no leftover left to detect — it was already consumed by the wrapper.
- Only `order.fees` is recorded into escrow accounting (`_orders[commitment][TRANSACTION_FEES] = order.fees;`), while the *entire* `msgValue` (which can be arbitrarily larger, e.g. if a user or SDK adds a native-token buffer for slippage/gas price uncertainty as is standard practice for exact-output swaps) is pulled into the contract as WXDAI with no tracking, no `DustCollected` event, and no user-recoverable accounting entry.

This directly breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant: the excess native value the user sent is neither refunded to them nor credited to any escrow/dust bucket they can claim — it is simply lost from the user's perspective.

### Impact Explanation
Any ordinary user placing an order on the Gnosis deployment of `IntentGatewayV2` with `order.fees > 0` and who sends `msg.value` greater than the fee-swap's real requirement (a normal practice to avoid a revert on price movement, since the real UniswapV2 semantics this call site was written against always refund the difference) permanently loses the excess native token. No relayer, prover, or malicious peer is required — this is triggered purely by calling the public `placeOrder` entrypoint with an unprivileged, ordinary transaction and a reasonable value estimate. This constitutes an unconditional, reproducible loss of user funds specific to the Gnosis wrapper's non-compliant router semantics, distinct from a mere revert/DoS.

### Likelihood Explanation
High for Gnosis-chain deployments: any user who overestimates `msg.value` for the fee swap — which is the expected safe practice for exact-output swap calls that can otherwise revert — triggers the loss on every such transaction. It requires no attacker at all; it is a straightforward, unprivileged, deterministic user-fund-loss bug caused by a mismatch between the `IUniswapV2Router02` interface's expected exact-output refund semantics and this chain-specific wrapper's actual behavior.

### Recommendation
Fix `GnosisUniswapV2Wrapper.swapETHForExactTokens` to honor the `amountOut` parameter: transfer only `amountOut` (converting exactly that much of `msg.value` if `WETH()`/native asset is 1:1), refund the unspent `msg.value - amountOut` back to the original caller, and return `amounts[0] = amountOut` (not `msg.value`) so downstream refund logic in `IntentGatewayV2.placeOrder` operates correctly. Alternatively, if a full 1:1 wrap-with-full-value model is intentional for Gnosis, `IntentGatewayV2.placeOrder` must not assume standard UniswapV2 exact-output refund semantics for this chain and should instead require callers to send exactly `order.fees` worth of native token to this code path, with strict pre-swap validation rather than relying on `amounts[0]`.

### Proof of Concept
1. Deploy `IntentGatewayV2` on a Gnosis-chain fork with `uniswapV2Router` set to `GnosisUniswapV2Wrapper`.
2. Call `placeOrder(order, ...)` with `order.fees = 1 ether` (in fee token) and `msg.value = 2 ether` (a reasonable buffer above the fee amount, matching normal exact-output swap practice).
3. Trace execution: `swapETHForExactTokens{value: 2 ether}(1 ether, path, address(this), block.timestamp)` is called on `GnosisUniswapV2Wrapper`.
4. Inside the wrapper: `amountOut (1 ether) > msg.value (2 ether)` is false, so it proceeds; it wraps and transfers the full `2 ether` of WXDAI to `IntentGatewayV2`, returning `out[0] = 2 ether`.
5. Back in `placeOrder`: `msgValue -= amounts[0]` → `2 ether - 2 ether = 0`; the refund branch is skipped.
6. Result: `IntentGatewayV2` now holds `2 ether` worth of WXDAI but only records `order.fees = 1 ether` in `_orders[commitment][TRANSACTION_FEES]`. The extra `1 ether` sent by the user is neither refunded nor tracked as recoverable dust — it is permanently lost to the user. [1](#0-0) [2](#0-1)

    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
    }
