### Title
Division-by-zero in vault `accrue()` treasury-fee minting freezes all vault operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
Every Zest vault's `calc-treasury-lp-preview` (inlined into `accrue`) computes the treasury's newly-minted share of interest as `reserve-inc * total-supply / (total-assets-preview - reserve-inc)`. This is structurally identical to the reported River bug pattern `sharesToMint = num / (assetBalance*BASE - amount*globalFee)`: a subtraction of a fee-derived term from a balance-derived term sits in the denominator with no floor/guard other than a `> 0` check on the numerator term, not on the denominator itself. [1](#0-0) 

### Finding Description
`accrue()` is called at the top of every `deposit`, `redeem`, `system-borrow`, `system-repay`, and flashloan entry point in each vault contract via `(u (try! (accrue)))`. [2](#0-1) 

Inside `accrue`, when `reserve-inc > u0`, the protocol computes:
```
treasury-lp = mul-div-down(reserve-inc, total-supply, (- ta-preview reserve-inc))
```
where `ta-preview` is `total-assets-preview` (current pooled assets + newly accrued interest) and `reserve-inc` is the reserve-fee slice of the freshly accrued interest (`debt-delta * fee-reserve / BPS`). [3](#0-2) 

`mul-div-down` performs raw `(/ (* x y) z)` with no zero-check on `z`: [4](#0-3) 

If `ta-preview` (assets + newly accrued interest) equals `reserve-inc` exactly, the denominator `(- ta-preview reserve-inc)` is `u0`, and Clarity's `/` operator aborts the transaction on division by zero. This is the exact same class of bug as the River `_onEarnings` finding: a fee-scaled numerator subtracted from (or compared to) a balance term lands in a denominator that can reach zero.

Analytically, when the vault is fully utilized (`current-assets = u0`, i.e., all liquidity borrowed out) and no unaccrued interest remains from a prior period (`old-debt == total-borrowed`, i.e., the previous `accrue()` synced state), `ta-preview` reduces to exactly `debt-delta` (this single accrual period's interest) and `reserve-inc = debt-delta * fee-reserve / BPS`. The denominator becomes `debt-delta * (1 - fee-reserve/BPS)`, which is `0` precisely when `fee-reserve == BPS` (i.e., the vault's reserve fee is configured at 100%). Any vault operator-set `fee-reserve` at or effectively at the maximum, combined with the fully-utilized zero-idle-assets state (fully achievable through ordinary borrow/repay usage, not requiring any oracle or DAO registry misconfiguration), reproduces the same zero-denominator condition described in the report.

### Impact Explanation
Because `accrue()` is invoked unconditionally at the start of `deposit`, `redeem`, `system-borrow`, and `system-repay` in all six vault contracts, a division-by-zero revert here blocks every user-facing vault operation for that asset until the on-chain state (block time delta, principal, or index) shifts enough to move the denominator away from zero. This matches the "temporary freezing of funds" impact class: legitimate depositors/borrowers cannot deposit, withdraw, borrow, or repay against the affected vault while the condition holds.

### Likelihood Explanation
Reaching the exact zero-denominator state requires a specific combination: (1) the vault's `fee-reserve` parameter set at or very near 100% via `set-fee-reserve`, and (2) the vault being fully utilized with a just-synced index (no residual unaccrued interest) at the moment `accrue()` is re-invoked. Whether `set-fee-reserve` enforces a hard cap below `BPS` (10000) could not be confirmed from the portions of the setter inspected; if such a cap exists this exact zero case may be unreachable, but the underlying arithmetic pattern (subtracting a fee-derived quantity from a balance-derived quantity in a denominator with no floor) remains present in all six vault contracts and is the same root-cause class flagged in the external report.

### Recommendation
Add an explicit denominator guard in `calc-treasury-lp-preview` (and the inlined copy in `accrue`) analogous to the River fix: assert `(> (- ta-preview reserve-inc) u0)` before dividing, or cap `fee-reserve` strictly below `BPS` at the setter level, and short-circuit `treasury-lp` to `u0` (or clamp) when the denominator would be non-positive.

### Proof of Concept
1. Governance calls `set-fee-reserve` on a vault (e.g. `v0-vault-usdc.clar`) with `fee-reserve = BPS` (10000, i.e., 100%).
2. Borrowers borrow up to `cap-debt`/available liquidity so `current-assets = u0` for that vault.
3. Call `accrue()` (directly, or indirectly via `deposit`/`redeem`) once, letting the current period's interest sync fully (`old-debt == total-borrowed` afterwards).
4. On the next block, call any vault entry point that triggers `accrue()` again. `debt-delta` from the elapsed time is now the entire `ta-preview`, and `reserve-inc = debt-delta` exactly (100% fee), producing `(- ta-preview reserve-inc) = u0` and reverting on the `mul-div-down` division inside `calc-treasury-lp-preview` / `accrue`.
5. All subsequent `deposit`, `redeem`, `system-borrow`, `system-repay` calls against that vault revert until state shifts, freezing user funds temporarily.
