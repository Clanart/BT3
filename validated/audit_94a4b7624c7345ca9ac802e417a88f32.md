## Analog Found

### Title
Missing zero-address validation on `_for` parameter in `SmartWomConvert.convertFor` causes permanent loss of converted WOM/mWOM - (File: `wombat/SmartWomConvert.sol`)

### Summary
`SmartWomConvert.convertFor` is a fully permissionless, user-facing function that lets a caller convert their own `wom` into `mWom` and route the result to an arbitrary `_for` address. Neither `convertFor` nor the internal `_convertFor` it delegates to validates that `_for != address(0)`, mirroring the `FETH.withdrawFrom` bug class where a missing receiver check on a withdrawal-style function can cause funds to be sent to the zero address and permanently lost.

### Finding Description
`convertFor` takes `_for` directly from calldata and forwards it unchecked into `_convertFor`: [1](#0-0) 

Inside `_convertFor`, once the WOM has been pulled from the caller and swapped/converted into `mWom`, the resulting `obtainedmWomAmount` is dispatched to `_for` depending on `_mode`. In the default branch (`_mode` not 1 or 2), it performs a direct, unconditional `safeTransfer` to `_for`: [2](#0-1) 

If `_for` is `address(0)` (accidental input, integration bug in a caller contract, or default zero value), the freshly-minted `mWom` — which was purchased with the caller's own `wom` transferred in at line 181 — is sent to the zero address and is unrecoverable. The same lack of validation also affects mode 1 (`depositFor` into `MasterMagpie`) and mode 2 (`lockFor` into `mWomSV`), where crediting a zero address either reverts deep in accounting or permanently strands the position under an address nobody controls, depending on downstream implementation.

This is the direct analog of the reported `FETH.withdrawFrom` issue: a fund-distributing function exposed to unprivileged callers with a caller-supplied recipient address and no zero-address guard.

### Impact Explanation
A user who calls `convertFor` (directly, or via any front-end/integration that passes through a `_for` parameter) and mistakenly supplies `address(0)` permanently loses the `wom` they deposited, since the converted `mWom` is sent to the burn address. This is a direct, irreversible loss of user funds with no recovery path, matching the "direct theft/permanent freezing of user funds" acceptance criteria.

### Likelihood Explanation
`convertFor` is unauthenticated and callable by any wallet or contract; the only way to trigger the bug is user/integration error in supplying `_for`, which is exactly the same trigger condition as the original Foundation `FETH.withdrawFrom` finding that was confirmed and fixed by the project team. No privileged role or governance action is required.

### Recommendation
Add a zero-address check at the start of `_convertFor` (or in `convertFor`/`convert`/`smartConvert` before calling it):
```solidity
if (_for == address(0)) revert InvalidReceiver();
```

### Proof of Concept
1. Attacker/careless integrator calls `SmartWomConvert.convertFor(amountIn, convertRatio, minRec, address(0), 0)` after approving `wom` to the contract.
2. `_convertFor` pulls `amountIn` of `wom` from `msg.sender` (line 181), converts/buys back into `mWom`.
3. Since `_mode` is 0, execution reaches the `else` branch and calls `IERC20(mWom).safeTransfer(address(0), obtainedmWomAmount)` (line 216), sending the converted funds to the zero address.
4. The caller's `wom` is now irrecoverably lost; no revert occurs anywhere in the path.
