### Title
Git clone security protection (`GIT_CLONE_PROTECTION_ACTIVE`) is explicitly disabled during every clone, re-opening a fixed hook-execution vulnerability class - (File: `app/src/lib/git/clone.ts`)

### Summary
Desktop's `clone()` helper unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every `git clone --recursive` it runs, overriding a security control that upstream Git added specifically to stop attacker-controlled repository/submodule content from triggering hook execution during the initial checkout performed by `clone`.

### Finding Description
`clone()` builds the environment for the clone subprocess like this: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is an internal Git environment variable used by Git itself (added in the May 2024 Git security release, e.g. as part of the fixes bundled with CVE-2024-32002/GHSA-9wvv-vqf9-h7rr and related "hooks executed during clone" issues) to signal that a clone/checkout is happening on a repository whose content is *not yet trusted* — e.g. one where a case-insensitive or symlink collision could smuggle a `.git/hooks` entry or submodule configuration that runs a hook before the user has ever had a chance to inspect the repo. When this flag is active, Git refuses to execute such repo-supplied hooks during the clone.

Desktop's `clone()` explicitly forces this protection to `'false'` for the `--recursive` clone it performs, meaning any submodule structure or repository layout crafted by the party hosting the remote (the exact attacker model allowed by this task — "attacker controls a cloned/fetched repository") can attempt to trigger hook execution during the clone itself, on the exact operation the upstream fix targeted.

No other code path re-enables or narrows this: `isClonePathSensitive` only validates the destination directory [2](#0-1) , and `envForRemoteOperation` only adds proxy/auth env vars [3](#0-2) . Neither of these guards has anything to do with hook/config trust during checkout, so the explicit `'false'` override is the only relevant control in this path and it disables the protection rather than restricting it.

### Impact Explanation
If exploitable on the user's underlying Git/OS combination (e.g. case-insensitive filesystem, or another vector the upstream advisory covers), a malicious remote repository cloned through Desktop (via the normal "Clone repository" URL flow, `--cli-clone`, or the `x-github-client://openRepo/...` deep link handled by `parseAppURL`/`dispatchCLIAction`) could get a repository-supplied hook or configuration executed as part of the very first checkout, resulting in code execution on the victim's machine outside of anything the user explicitly approved (they only clicked "Clone"/a link). This is not confined to the cloned repo directory — hook execution runs arbitrary commands with the user's privileges.

### Likelihood Explanation
Medium. Exploitation depends on the specific underlying Git hook/config-during-clone bug class still being reachable once this Git-provided guard is disabled (filesystem case-sensitivity, symlink handling, or submodule config semantics on the victim's platform/Git version). The attacker-controlled surface (a remote URL or a submodule inside it) is fully within the allowed threat model, and no comment in the code explains why this specific protection is turned off, which is itself a red flag — the value can't be assumed to be a deliberate, safety-reviewed workaround.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Leave Git's default (protection active) for clone operations, especially since Desktop always clones with `--recursive`, which is exactly the scenario the upstream protection was designed to cover (submodule-driven hook/config smuggling). If the override exists to work around a specific compatibility issue, that should be scoped narrowly (e.g., only for verified-safe/local clones) and documented, not applied unconditionally to every user-initiated clone of an arbitrary, untrusted URL.

### Proof of Concept
Because this requires an actual Git-level hook-smuggling exploit chain (case-insensitive filesystem collision or submodule-config trick) that is version/platform dependent, a full working exploit cannot be constructed purely from this repository's source. The concrete, verifiable code evidence is:

1. `clone()` in `app/src/lib/git/clone.ts` line 83 sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally for the `git clone --recursive` invocation.
2. This function is reachable from fully untrusted, attacker-supplied URLs, e.g. through `dispatchCLIAction`/`openOrCloneRepository` when a user opens a `x-github-client://openRepo/...` link or runs `--cli-clone` [4](#0-3) .
3. There is no re-validation or restriction of the cloned repository's content/config before or during this checkout — the only checks present (`isClonePathSensitive`) concern the local destination path, not the remote content.

A Devin agent with terminal access should attempt to reproduce a Git clone-time hook execution PoC (as documented in the Git security advisories this env var was introduced to mitigate) against a Desktop-initiated clone to confirm whether the disabled protection is actually exploitable on the current bundled Git/dugite version.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
