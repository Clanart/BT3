### Title
Missing Timestamp Expiry Check Allows Indefinite Replay of Signed App Proxy Requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#verify_proxy_request` validates only that the `signature` query parameter matches an HMAC computed over the other query parameters (including `timestamp`), but it never checks whether that `timestamp` is recent. As a result, any previously-captured, validly-signed app proxy request remains fully valid and replayable forever.

### Finding Description
The concern's `query_string_valid?` method removes the `signature` param, recomputes the HMAC over the remaining sorted query params (which include `timestamp`), and does a `secure_compare` against the supplied signature. [1](#0-0) 

Although `timestamp` is included in the HMAC-signed data, its value is never validated against the current time anywhere in this module — there is no `Time.now - timestamp < threshold` (or similar) check before the request is authorized. [2](#0-1) 

This exactly mirrors the reported bug class: a signature that should only be valid within an intended time window is instead accepted indefinitely, because the `timestamp` field is treated purely as signed data rather than as an expiry check.

### Impact Explanation
Any request that includes a validly-signed app proxy query string — even one that is months or years old (e.g., leaked via browser history, referrer headers, shared logs, proxy/CDN caches, or intercepted network traffic) — will continue to pass `verify_proxy_request` and reach the protected controller action as if it were a fresh, legitimate request from Shopify's app proxy. This is a genuine "accepted forged/replayed signed request" condition: the signature itself never expires, so a request that was only meant to be valid for a short window can be resubmitted at any point in the future to trigger the same controller logic (e.g., `AppProxyController#index` or any custom controller including this concern).

### Likelihood Explanation
Exploitation requires an attacker to have obtained a previously valid, fully-formed app-proxy query string (including its signature) at some point — for example via a captured URL, log exposure, or browser history/referrer leakage — since a fresh forgery still requires the shared secret. However, once obtained, replay is trivial and requires no further knowledge of secrets, and the current code provides no defense-in-depth against this even though `timestamp` is already present in the signed payload for exactly this purpose.

### Recommendation
Add an expiry check on the `timestamp` parameter before/after HMAC validation in `query_string_valid?`, e.g.:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)

  signature = query_hash.delete("signature")
  return false if signature.nil?

  timestamp = query_hash["timestamp"]
  return false if timestamp.blank? || Time.now.to_i - timestamp.to_i > MAX_SIGNATURE_AGE

  ActiveSupport::SecurityUtils.secure_compare(
    calculated_signature(query_hash),
    signature,
  )
end
```
where `MAX_SIGNATURE_AGE` is a small, configurable window (e.g., a few minutes), consistent with the recommendation in the source report of rejecting signatures once `block.timestamp` (here, `Time.now`) exceeds an expiry bound.

### Proof of Concept
1. Capture (or construct once, if you have temporary legitimate access) a valid app-proxy request URL, e.g.:
   `GET /app_proxy/basic?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid_hmac>`
   as used in the existing test suite. [3](#0-2) 
2. Wait an arbitrary amount of time (days/months) after the original `timestamp`.
3. Replay the exact same URL/query string against the app.
4. Observe that `verify_proxy_request` still returns `head(:ok)`/proceeds normally, because `query_string_valid?` only re-derives and compares the HMAC — it performs no comparison between `timestamp` and the current time. [4](#0-3)
