## Analysis

The Ajna bug class is: a state-mutating action (`memorializePositions`) zeros out a tracked accounting value (LP) as a side effect of handling a "bankrupt" condition, while a separate reward-accounting subsystem (`RewardsManager`) is not made aware of that condition, causing a legitimate holder to permanently lose value that was already accrued to them.

The closest reachable analog in this codebase is in the `x/distribution` reward-withdrawal path combined with Sei's EVM↔Sei address re-association (`SetAddressMapping`). An unprivileged EVM user can trigger `associatePubKey`/`Associate`, which re-maps a Sei address that already has staking/delegation state (created under the "direct-cast" address before association) to a different EVM-derived Sei address. After that, the original direct-cast address is deemed unable to receive funds by `CanAddressReceive`/`CanSendTo` [1](#0-0) , but the delegator/validator's `DelegatorStartingInfo`, `ValidatorOutstandingRewards`, and `ValidatorAccumulatedCommission` records still exist for that address, exactly as Ajna's bucket LP snapshot exists independent of RewardsManager's awareness of bankruptcy.

`GetDelegatorWithdrawAddr`'s fallback still resolves to that now-unreceivable address, so when the validator is later removed, `AfterValidatorRemoved` cannot pay out the commission/outstanding rewards to their rightful owner and instead permanently diverts them to the community pool rather than failing the operation [2](#0-1) . This is confirmed by the test explicitly documenting the scenario: re-associating the EVM address of a validator/delegator "orphans" its distribution state, and the mitigating code forfeits the funds to the community pool instead of the legitimate owner [3](#0-2) . The `canReceiveWithdrawAddr` check exists purely to avoid a chain-halting panic, not to protect the user's entitlement [4](#0-3) .

### Title
Loss of validator commission/delegator rewards when the reward-tracking address is orphaned by EVM address re-association - (File: sei-cosmos/x/distribution/keeper/hooks.go)

### Summary
When a Sei address that already has staking/distribution state (delegation, validator self-bond, accumulated commission) is later re-associated to a different Sei address via the EVM `associatePubKey`/`Associate` precompile flow (`SetAddressMapping`), the original "direct-cast" address becomes permanently unable to receive bank transfers. The distribution module's reward-tracking records for that address are not migrated or purged in step with the association change, so any outstanding, already-accrued rewards or commission owed to that address are forfeited to the community pool instead of the rightful owner when the validator is eventually removed.

### Finding Description
`CanAddressReceive` returns `false` for a direct-cast address once its corresponding EVM address has been associated with a *different* true Sei address [1](#0-0) . This re-association can be performed by any user via the `associate`/`associatePubKey` precompile method or automatically during EVM transaction preprocessing [5](#0-4) , and does not touch or clean up any pre-existing `x/distribution` state keyed by the now-orphaned address (`DelegatorStartingInfo`, `ValidatorOutstandingRewards`, `ValidatorAccumulatedCommission`).

`GetDelegatorWithdrawAddr` still falls back to resolving withdrawals to that orphaned address when no explicit withdraw address was set. When the validator eventually gets removed, `AfterValidatorRemoved` tries to force-withdraw commission and pay it to that withdraw address; finding it non-receivable, it instead permanently routes the funds to the community pool [2](#0-1) , rather than to the account that actually earned it. This mirrors the Ajna bug precisely: a state-changing action elsewhere (re-association) silently invalidates the receivability assumption of a reward-tracking record, and the reward-payout code path has no way to reconcile this, so the value is lost rather than delivered to its rightful owner.

The behavior is exercised and acknowledged directly by the codebase's own regression test, which documents: *"the validator operator address itself cannot receive funds — its EVM address was re-associated... away from the direct-cast Sei address it was created under… the commission is routed to the community pool instead"* [3](#0-2) . The same forfeiture applies to a plain delegator (not just a validator operator) whose direct-cast address delegated stake and was later re-associated — normal `MsgWithdrawDelegatorReward` calls for that address would similarly fail to deliver funds, and any dust/commission swept during `AfterValidatorRemoved`/`prepForZeroHeightGenesis` goes to the community pool rather than the delegator.

### Impact Explanation
Funds legitimately earned by a delegator or validator operator (staking rewards / commission) are irrecoverably redirected to the community pool instead of the account that earned them. This is a concrete, permanent loss of funds for the affected user, reachable purely through normal, unprivileged use of the `associate`/`associatePubKey` EVM precompile — no validator or governance action is required. This matches the "concrete fund loss" acceptance criterion.

### Likelihood Explanation
This requires only two ordinary, permissionless actions from any user: (1) delegate/create a validator using their EVM address's direct-cast Sei address (the default before any explicit association) so it accrues distribution state, and (2) later call `associate`/`associatePubKey` to bind their EVM address to a different, "true" Sei address (e.g. after realizing the direct-cast address has other limitations). This is a normal onboarding pattern encouraged by the dual-address model documented in the module itself [6](#0-5) , making the sequence plausible without any adversarial setup.

### Recommendation
Either (a) have the association flow (`AssociateAddresses`) proactively migrate/reconcile any pre-existing distribution state (outstanding rewards, accumulated commission, withdraw address) from the direct-cast address to the newly associated true address, similar to how it already migrates bank balances in `MigrateBalance` [7](#0-6) ; or (b) block re-association when the direct-cast address still has outstanding distribution state; or (c) when a withdraw address is found unreceivable, hold the funds recoverable (e.g., allow a claim mechanism once receivability is restored) rather than unconditionally donating them to the community pool.

### Proof of Concept
1. Generate a new key pair; derive its EVM address `E1` and direct-cast Sei address `castAddr = AccAddress(E1)`. Fund `castAddr` with `usei` via a normal Cosmos-signed transaction (no explicit association happens yet for a Cosmos-signed staking tx sent directly from `castAddr`).
2. From `castAddr`, submit `MsgCreateValidator` (or `MsgDelegate` to an existing validator) so distribution state (`ValidatorOutstandingRewards`/`ValidatorAccumulatedCommission`/`DelegatorStartingInfo`) accrues under `castAddr`. Let rewards accumulate over several blocks.
3. Using the same private key, call the `associate`/`associatePubKey` precompile (or send any EVM tx) to associate `E1`'s pubkey-derived Sei address `trueSeiAddr` (which differs from `castAddr`) — `SetAddressMapping(trueSeiAddr, E1)` is set, and per `CanAddressReceive`, `castAddr` can no longer receive funds since `trueSeiAddr != castAddr` [1](#0-0) .
4. Trigger validator removal (e.g., full unbonding then completion), causing `AfterValidatorRemoved` to run in `EndBlock`. Observe that outstanding commission/rewards for `castAddr` are added to `feePool.CommunityPool` instead of being paid to `castAddr`'s (or any owner-controlled) account, per the exact code path validated by `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator` [8](#0-7) .
5. Confirm the balance of `castAddr` and `trueSeiAddr` never reflect the forfeited commission — funds are unrecoverable by the user who legitimately earned them.

func (k Keeper) canReceiveWithdrawAddr(ctx sdk.Context, withdrawAddr sdk.AccAddress) bool {
	// BlockedAddr mirrors the gate SendCoinsFromModuleToAccount actually enforces:
	// beyond the module-account blocklist it also rejects dynamically-derived
	// addresses such as the EVM coinbase addresses (an "evm_coinbase"-prefixed
	// address), which CanSendTo does not catch. Consulting it here keeps this
	// predicate in lockstep with the send, so AfterValidatorRemoved never concludes
	// an address is receivable and then panics on the resulting bank error.
	return !k.blockedAddrs[withdrawAddr.String()] &&
		!k.bankKeeper.BlockedAddr(withdrawAddr) &&
		k.bankKeeper.CanSendTo(ctx, withdrawAddr)
}

## Dual Address Model

Every account can have both a Sei (bech32) address and an EVM (hex) address. The module maintains a bidirectional mapping between them.

- **Explicit association** — users can link their addresses via an Associate transaction or by signing any Cosmos/EVM transaction (the EVM address is derived from their secp256k1 public key).
- **Default (cast) addresses** — when no explicit association exists, the module falls back to a deterministic byte-cast. Cast addresses have limitations on receiving funds compared to fully associated addresses.

- **Why** - cast addresses will result in two views of the same account (e.g. two balances, etc.)

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
