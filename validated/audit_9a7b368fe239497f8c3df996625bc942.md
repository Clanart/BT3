### Title
`SignableTransaction` fee/weight calculation omits the OP_RETURN output, understating `needed_fee` and `weight` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Olympus report — where a returned amount was inaccurate because the formula omitted a term (the booster's reward multiplier) — `SignableTransaction::new` computes the transaction weight/vbytes (and therefore `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check) from only the payment outputs, omitting the OP_RETURN data output that is pushed into `tx_outs` beforehand.

### Finding Description
`SignableTransaction::new` appends an OP_RETURN output to `tx_outs` when `data` is provided (send.rs:194-202). However, the weight used for fee calculation is computed by `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204) and `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:225-226). Both calls pass `payments` — not `tx_outs` — so the OP_RETURN output (up to 80 bytes of data plus ~10 bytes of output overhead, ~90+ vbytes) is entirely absent from `weight`, `vbytes`, and `vbytes_with_change`.

Consequences encoded in the code:
- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) underpays relative to the requested `fee_per_vbyte`.
- `fee_with_change = fee_per_vbyte * vbytes_with_change` (send.rs:227) and the change amount `input_sat - payment_sat - fee_with_change` (send.rs:228-230) are computed against the understated size, so change is slightly over-credited and the effective fee rate is lower than specified.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (send.rs:241) uses the understated `weight`, so a transaction can be accepted whose actual weight exceeds the standard limit.
- The `TooLowFee` check at send.rs:211 compares `needed_fee` against the minimum relay fee using the same understated `vbytes`.

### Impact Explanation
Because the serialized output is larger than accounted for, the actual fee paid (`sum(inputs) - sum(outputs)`, per `fee()` at send.rs:138-141) corresponds to a lower sat/vbyte rate than the `fee_per_vbyte` requested. If `fee_per_vbyte` was chosen near the relay minimum, the resulting transaction can fall below the node's minimum relay feerate and be rejected from relay/mempool — i.e., funds reported as sendable are not spendable until reconstructed with a higher fee. In the extreme, the real weight can cross `MAX_STANDARD_TX_WEIGHT` while the understated `weight` passes the check at send.rs:241, producing a non-standard transaction.

### Likelihood Explanation
The `data` parameter is public input to `SignableTransaction::new`, so any caller embedding data (OP_RETURN metadata) triggers the miscalculation deterministically — no edge-case timing required. The magnitude is bounded (~80-90 vbytes), and in-tree callers (`processor/src/networks/bitcoin.rs` `make_signable_transaction`) currently pass `None` for data, which limits realized impact within the processor. For direct users of the wallet API with a low `fee_per_vbyte`, the resulting transaction may be unrelayable.

### Recommendation
Pass the actual output list (payments + OP_RETURN) into `calculate_weight_vbytes`, or build `tx_outs` before sizing and measure weight on the full output set. Concretely: compute `tx_outs` (including the OP_RETURN output) first, then call `calculate_weight_vbytes(tx_ins.len(), &tx_outs-based-payments, ...)` or extend `calculate_weight_vbytes` to accept an optional OP_RETURN script, so `needed_fee`, `fee_with_change`, `weight`, and the min-relay/`MAX_STANDARD_TX_WEIGHT` checks all reflect the final transaction.

// ... but sizing uses `payments`, which excludes it:
