### Title
`solo` precompile's `ClaimSpecific` reverts entire claim when a bundled CW20 asset has zero balance, permanently blocking claim of the signed asset bundle - (File: `precompiles/solo/solo.go`)

### Summary
The `solo` precompile's `ClaimSpecific` handler transfers each CW20 asset listed in a signed `MsgClaimSpecific` by querying the sender's balance and unconditionally executing a CW20 `transfer` with that balance, even when the balance is zero. Standard cw20-base contracts (the reference CosmWasm CW20 implementation) reject zero-amount transfers, so any bundled CW20 asset whose balance has dropped to zero between signing and execution makes the whole `claimSpecific` call revert — losing the ability to claim the other native/CW721 assets bundled in the same signed message, exactly mirroring the reported "developer cannot claim if token reverts on zero-amount transfer" bug class.

### Finding Description
`ClaimSpecific` iterates over the assets embedded in a client-signed `MsgClaimSpecific` tx and dispatches transfers per asset type: [1](#0-0) 

For native assets, the code explicitly guards against a zero balance before calling `SendCoins`: [2](#0-1) 

But for CW20 assets, no such guard exists — the queried `balance` is passed straight into `CW20TransferPayload` and executed unconditionally: [3](#0-2) [4](#0-3) 

Standard CosmWasm cw20-base contracts (the reference CW20 implementation typically deployed for CW20 pointers/tokens on Sei) reject zero-amount `transfer` messages, returning an error. Because `p.wasmKeeper.Execute` here propagates any contract error as a hard failure of `ClaimSpecific`, a zero-balance CW20 entry in the asset list aborts the *entire* claim transaction — including the native-coin and CW721 transfers bundled in the same message — even though those other transfers would have succeeded independently.

This is the same root-cause pattern as the referenced report: a batch/claim operation that indiscriminately attempts a zero-value transfer for one item in a list, causing a token that reverts on zero-value transfers to block the legitimate claim of everything else in the batch.

### Impact Explanation
`MsgClaimSpecific` is a single signed message (list of assets is fixed at signing time by the account holder). If, between the time the claim message is signed and the time it is executed on-chain, the CW20 balance of `sender` for one of the listed assets drops to zero (e.g., balance was already zero, or was spent/transferred out before the claim tx lands), the entire claim reverts. The caller cannot selectively skip only the zero-balance CW20 entry — the message content is fixed by the original signature (`p.sigverify` validates the exact signed tx bytes), so the assets bundled with it (native coins, CW721 tokens) cannot be claimed either, until an entirely new signed `MsgClaimSpecific` is produced by the original sender excluding the problematic asset. This effectively freezes access to co-bundled funds/NFTs for anyone who cannot easily obtain a fresh signature from the original key holder (e.g., custodial/bridge/migration flows that pre-generate and rely on a single signed claim artifact).

### Likelihood Explanation
Reachable by any unprivileged EVM transaction sender calling the `solo` precompile at `0x000000000000000000000000000000000000100C` with a `claimSpecific` call carrying a validly signed `MsgClaimSpecific`. Triggering the zero-balance condition requires no special privilege — it naturally occurs whenever the sender's CW20 balance for a listed asset is (or becomes) zero at execution time, which is a normal, easily reachable state (e.g., listing an asset the sender no longer holds, or a front-run/self-transfer draining the CW20 balance to zero before the claim executes).

### Recommendation
Mirror the native-asset guard for CW20 assets: skip the `wasmKeeper.Execute` transfer call when the queried CW20 `balance` is zero (`balance.IsZero()`), continuing to process the remaining assets in the loop, so a single zero-balance CW20 entry cannot abort transfers of unrelated bundled assets.

### Proof of Concept
1. Sender holds `100 usei` native balance and `0` balance of CW20 contract `C` (either never held any, or balance was moved out after the claim message was signed but before broadcast).
2. Sender signs a `MsgClaimSpecific` bundling `{native: "usei"}` and `{cw20: C}` assets, authorizing `claimer` to pull both.
3. `claimer` submits `claimSpecific(txBytes)` to the `solo` precompile.
4. In `ClaimSpecific`, the native-asset branch would succeed, but the loop first (or subsequently) reaches the CW20 branch for `C`: `ParseCW20BalanceQueryResponse` returns `0`, and `p.wasmKeeper.Execute(..., CW20TransferPayload(callerSeiAddr, 0), ...)` is executed unconditionally per [5](#0-4) .
5. Because the underlying cw20-base contract rejects zero-amount transfers, `wasmKeeper.Execute` returns an error, causing `ClaimSpecific` to return early with `failed to transfer on CW20 contract %s`, per line 194 — the entire tx reverts, and the native `usei` balance that could have been claimed is not transferred, leaving both assets stuck under the original signed message until it is re-signed and resubmitted without the zero-balance CW20 entry.
