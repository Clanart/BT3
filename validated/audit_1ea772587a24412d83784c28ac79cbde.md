### Title
Direct ERC20 donation to `MasterMagpie` permanently and irreversibly inflates `_calLpSupply()`, diluting `accMGPPerShare` and `BaseRewardPoolV2.rewardPerToken` forever - ([File: rewards/MasterMagpie.sol])

### Summary
`_calLpSupply()` uses `IERC20(_stakingToken).balanceOf(address(this))` as the reward-accrual denominator for every pool that is not `vlmgp` or `mWomSV`. Any unprivileged actor can transfer the staking/receipt token directly to `MasterMagpie` (no function call, no credit to any `UserInfo.amount`), which permanently inflates this balance-based denominator for the lifetime of the pool, since nothing ever purges or excludes uncredited balances.

### Finding Description
`updatePool()` computes `lpSupply = _calLpSupply(_stakingToken)` and then does `pool.accMGPPerShare += mgpReward * 1e12 / lpSupply` [1](#0-0) . For any staking token other than `vlmgp`/`mWomSV`, `_calLpSupply` simply returns the raw token balance of the contract: `return IERC20(_stakingToken).balanceOf(address(this));` [2](#0-1) . This balance is never reconciled against the sum of `UserInfo.amount`; the only place `UserInfo.amount` is incremented is in `_deposit`, via `pool.stakingToken.safeTransferFrom` inside a `deposit`/`depositFor` call [3](#0-2) . A plain `IERC20(stakingToken).transfer(masterMagpie, amount)` from an attacker bypasses `_deposit` entirely: no `UserInfo.amount` is credited, but `balanceOf(address(this))` still increases, and there is no mechanism anywhere in the contract to subtract or ignore this excess.

`multiclaimSpec` → `_multiClaim` iterates the caller-supplied `_stakingTokens` and calls `updatePool(_stakingToken)` for each one before harvesting [4](#0-3) . It requires no staking token approval or ownership by the caller — any address can call `multiclaimSpec` for any registered pool to force `updatePool` to consume the inflated (donated) balance and lock in a diluted `accMGPPerShare` increment for that interval. Because the donated balance is permanent (nothing ever removes it from `balanceOf(this)`), every subsequent `updatePool` call (via `deposit`, `withdraw`, `multiclaim`, or `multiclaimSpec`) continues to divide by the inflated denominator forever.

The same balance value is also the source of truth in `BaseRewardPoolV2.totalStaked()`, which returns `IERC20(stakingToken).balanceOf(operator)`, i.e. `balanceOf(MasterMagpie)` [5](#0-4) , while `BaseRewardPoolV2.balanceOf(_account)` reads only `userInfo[stakingToken][_account].amount` via `stakingInfo` [6](#0-5) . After a donation, `sum(balanceOf(user))` no longer equals `totalStaked()` — confirming the stated invariant break — and every future `_provisionReward` call in the base rewarder also divides bonus-token rewards by the inflated `totalStaked()` [7](#0-6) .

No existing check stops this: `updatePool`/`_calLpSupply` have no `whenNotPaused`-adjacent sanity check, no reentrancy issue is involved (the exploit is a plain token transfer), and `multiclaimSpec` only requires `whenNotPaused`.

### Impact Explanation
Both MGP (`accMGPPerShare`) and bonus-token (`rewardPerToken`) reward accrual for the affected pool are permanently diluted, because the denominator is inflated for as long as the contract exists — there is no way to reduce it back down. The portion of MGP/bonus rewards that "should" have accrued to the true stakers based on their actual `UserInfo.amount`/`balanceOf` is instead spread across a larger, partly-fictitious supply, and the shortfall is never recovered by anyone (it doesn't go to the attacker either — it is simply unaccounted-for, permanently frozen yield). This matches the Immunefi "High - Permanent freezing of unclaimed yield" class, and is directly triggerable/observable by calling `multiclaimSpec` (or any other `updatePool`-driving function) on a pool after the donation.

### Likelihood Explanation
The attack requires only owning some of the staking/receipt token (e.g., an LP token of one of the non-`vlmgp`/`mWomSV` pools) and calling a plain `transfer` to `MasterMagpie`, then any unprivileged call that triggers `updatePool` (including `multiclaimSpec`) to lock in the diluted rate. No special role, flash loan, or reentrancy is needed, and it is fully repeatable/incremental (each additional donation compounds the dilution). Cost to the attacker is the donated tokens, which are permanently lost to them as well — making this a pure griefing/DoS vector rather than a profit-extraction one, but the resulting permanent yield freezing for legitimate stakers is real and irreversible.

### Recommendation
Replace balance-based `_calLpSupply()` for non-lock pools with an internally tracked total (e.g., a `totalStaked[_stakingToken]` counter incremented/decremented exactly in `_deposit`/`_withdraw`/`emergencyWithdraw`), so direct token transfers cannot affect the reward-accrual denominator. Apply the same fix to `BaseRewardPoolV2.totalStaked()` (drive it from `IMasterMagpie` internal accounting rather than raw `balanceOf(operator)`).

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, register a pool for an ERC20 staking token (non-vlmgp/mWomSV), deploy its `BaseRewardPoolV2`.
2. User A deposits `1000e18` staking tokens via `deposit()`. Advance time, call `multiclaimSpec` and record `accMGPPerShare` delta and `IBaseRewardPool.balanceOf(A)`/`totalStaked()` — assert they match (`totalStaked() == balanceOf(A)`).
3. Reset state (or new run): Attacker (unprivileged EOA, no deposit) directly calls `stakingToken.transfer(masterMagpieAddress, 1000e18)` before User A's deposit lands (simulating a front-run/sandwich).
4. User A deposits `1000e18` as before; advance the same amount of time; call `multiclaimSpec` again.
5. Assert: `IBaseRewardPool(rewarder).totalStaked()` (== `balanceOf(masterMagpie)`, now `2000e18`) is no longer equal to `IBaseRewardPool(rewarder).balanceOf(A)` (`1000e18`), and that `accMGPPerShare`/MGP actually credited to User A over the interval in run 4 is roughly half of what was credited in step 2 for the identical time period and identical honest stake — demonstrating permanent, unrecoverable dilution of MGP/bonus-token yield caused purely by an unprivileged direct transfer.
