### Title
`GeneratorPromotion::complete` trusts the proof-map length counter without checking membership, leading to an `.unwrap()` panic on a missing participant's proof (reachable DoS from attacker-supplied `GeneratorProof` map) - ([File: crypto/dkg/promote/src/lib.rs])

### Summary
`GeneratorPromotion::complete` validates only that `proofs.len() == n - 1` and that every key is `<= n`, then iterates `1 ..= n` and calls `proofs.get(&i).unwrap()`. Because the map is keyed by `Participant` (a `HashMap`, so duplicate keys are impossible but *wrong* keys are not), an attacker can supply `n - 1` entries that include the local participant `params.i()` (or any other already-covered slot) while omitting a participant `j`. The length check passes, and the loop then hits `proofs.get(&j).unwrap()` on an absent key and panics.

This mirrors CVE-2026-42959's bug class: the *count* of expected entries is validated, but a counter/index mismatch leaves a slot that is never populated, and later code dereferences it unconditionally.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`:

```rust
if proofs.len() != (usize::from(params.n()) - 1) { ... }        // line 125
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }                          // line 132-136
}
...
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();                          // line 146
  proof.proof.verify(...).map_err(...)?;                        // line 147-154
  verification_shares.insert(i, proof.share);
}
```

The pre-checks establish:
- `proofs.len() == n - 1`
- every key is a valid `Participant` with value `<= n` (and `Participant::new` rejects 0)

They do *not* establish that the key set equals `{1..=n} \ {params.i()}`. Since the domain `{1..=n}` has exactly `n` elements, any `(n-1)`-element subset that contains `params.i()` necessarily excludes some other participant `j`. The loop then reaches `proofs.get(&j).unwrap()` with `j` absent → panic.

`proofs` is fully attacker-controlled input: it is built from `GeneratorProof::read` (line 72-77), which parses untrusted bytes into `share`/`proof` — exactly the kind of public-input path in scope.

### Impact Explanation
An unprivileged counterparty in a key-promotion round can crash the victim's process by sending a well-formed `proofs` map of the right length but keyed to include the victim's own index (or a duplicate semantic slot) while omitting a real participant. The panic occurs before any share data is used, at line 146. As a library primitive intended to be driven by peer-supplied messages, an abort on untrusted input is a denial of service identical in shape to the Unbound crash: correct count, missing slot, unconditional dereference.

Additionally, note the reverse direction is safe: a subset of size `n-1` that *omits* `i` is exactly the required set, so no soundness issue arises — the only defect is the unchecked `.unwrap()`.

### Likelihood Explanation
Reachable whenever an integrator feeds a peer-controlled `HashMap<Participant, GeneratorProof>` into `complete`, which is the documented API path (`GeneratorProof::read` exists precisely to deserialize peer messages). Requires no collusion, no threshold assumptions — a single faulty/malicious peer's message map suffices. Severity: Medium (process panic on untrusted input; no secret leakage or forgery).

### Recommendation
Replace the membership assumption with an explicit check, e.g.:

```rust
let proof = proofs.get(&i).ok_or(PromotionError::InvalidProof(i))?;
```

or validate up front that the key set equals `all_participant_indexes().filter(|l| *l != params.i())` (mirroring the `validate_map` helper used in `crypto/frost/src/lib.rs` and `crypto/dkg/pedpop/src/lib.rs`, which would have caught exactly this class of bug).

### Proof of Concept
```rust
// C1/C2: same curve group, e.g. a ciphersuite pair sharing F/G.
// Victim is participant i = 1 in an n = 3, t = 3 promotion (e.g. MuSig-derived keys).
let (promotion, _our_proof) = GeneratorPromotion::<C1, C2>::promote(&mut rng, base_keys);

// Attacker supplies n - 1 = 2 entries, but keyed {1, 2} instead of {2, 3}:
// includes the victim's own index 1, omits participant 3.
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof_a); // victim's own index
proofs.insert(Participant::new(2).unwrap(), attacker_proof_b);
assert_eq!(proofs.len(), 2); // passes the len() == n - 1 check; all keys <= n

// Loop reaches i = 3 -> proofs.get(&3) == None -> .unwrap() panics.
promotion.complete(&proofs); // thread panic: "called Option::unwrap() on a None value"
```

The length counter and the populated slots disagree — the same "wrong counter leaves a slot the later pass dereferences" structure as the Unbound flaw — and the panic is induced entirely by attacker-supplied bytes.
