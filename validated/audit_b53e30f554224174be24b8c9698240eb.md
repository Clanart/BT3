## Title
Reentrant escrow release via unguarded `withdraw()` in the Tron `IntentGatewayV2` — external call precedes escrow-balance debit - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The bug-class in the external report is "state that should be atomically decremented/removed on an operation is instead mutated *after* the side-effect that depends on it, so the same value can be consumed more than once before the bookkeeping catches up." The Hyperbridge analog is in the Tron build of `IntentGatewayV2`: `withdraw()` sends the escrowed asset to the beneficiary via a raw external call/`token.call` **before** decrementing `_orders[commitment][token]`, i.e. it violates checks-effects-interactions in the exact place the audited-and-fixed EVM version (`evm/src/apps/intentsv2/IntentsBase.sol`) already corrects.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol:682-721` does, per token in the loop: [1](#0-0) 
```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();

    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");           // <-- external call FIRST
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }

    _orders[body.commitment][token] -= amount;                        // <-- debit happens AFTER
    unchecked { ++i; }
}
```
Compare this with the parallel, already-hardened implementation in `evm/src/apps/intentsv2/IntentsBase.sol:391-410`, which computes `_orders[body.commitment][token] = escrowed - amount;` **before** making the external transfer/call — the correct checks-effects-interactions ordering. [2](#0-1) 

The only guard that exists in the Tron path is `if (_orders[commitment][token] == 0) revert UnknownOrder()`, which is a *presence* check, not a *sufficiency* check on `amount` — directly mirroring the report's core complaint that the guard validates existence/shape but never validates the bound (`lock_index <= total_investor_count`) against the actual consumable quantity before mutating/removing state. Here the "index" is the per-token escrow balance, and the removal ("decrement") is deferred until after the value has already left the contract.

`_filled[body.commitment]` is set once at the top of `withdraw()`, so a **same-commitment** re-entry into `onAccept`/`onGetResponse`/`fillOrder`/`cancelOrder` is blocked by the `Filled()` check in those entry points. However, this only protects the *single-commitment* re-entry path. Because the state mutation for token `i` happens strictly after its own external call and *before* the loop even reaches token `i+1`, and because `withdraw()` is invoked from `onAccept`, which is reachable from any Hyperbridge-relayed `RedeemEscrow`/`RefundEscrow` message the paired remote `IntentGatewayV2` instance emits, any ERC-777/callback-capable token or a native-ETH beneficiary contract used as `body.beneficiary` gets code execution while `_orders[commitment][token]` for that specific token still reflects the pre-withdrawal balance and while `_orders[commitment][otherToken]` entries for *other* tokens in the same multi-token order have not yet been decremented at all. A reentrant call from the beneficiary into any other public function of the same contract that reads `_orders[commitment][otherToken]` (e.g., a same-chain cancel/fill code path reading escrow for a *different* commitment sharing the token accounting helper, or any future/plugin extension that reads `_orders` for accounting) sees stale, not-yet-debited balances.

### Impact Explanation
This falls squarely in the "stealing or loss of funds" / "transaction manipulation" bucket of the bounty scope: escrowed bridge funds (`_orders[commitment][token]`) are the custody ledger for cross-chain intent settlement. An ordering bug that lets an external call fire while the ledger still shows undebited balance is exactly the historical class of vulnerability (checks-effects-interactions violation) that leads to double-spend of escrowed funds once any code path reads `_orders` mid-withdrawal — which is more likely to be introduced by any future change to this contract (new function, upgrade, or composability with other Tron TRC20/callback tokens) since the unsafe ordering is silently different from the reference EVM implementation that was already fixed.

### Likelihood Explanation
Medium. The `_filled` guard limits the immediate blast radius for the *exact same* commitment being reprocessed through the public entry points that exist today, so a full proof-of-concept double-drain purely within the current file is not demonstrable with certainty from the code alone. What is certain and locally verifiable is that the Tron variant regressed the checks-effects-interactions fix present in the canonical EVM `IntentsBase.sol`, and the reentrancy window (external call before ledger debit, per-token, inside a loop with multiple tokens) is real and independently exploitable the moment a native-ETH/TRC20-with-callback beneficiary, or any future function reading `_orders`, is reachable during that window.

### Recommendation
Mirror `evm/src/apps/intentsv2/IntentsBase.sol`'s ordering in the Tron contract: compute and write `_orders[body.commitment][token] -= amount` (or the full `escrowed - amount` assignment) **before** performing the native `.call` / TRC20 `.call` transfer, for every token in the loop. Additionally add a `nonReentrant` guard to `withdraw()`/`onAccept`/`onGetResponse` as defense-in-depth, and replace the presence-only check with a sufficiency check (`amount <= _orders[commitment][token]`) so the failure mode is an explicit revert rather than relying on unchecked-arithmetic underflow behavior.

### Proof of Concept
Not independently verifiable to full fund-loss without deploying the Tron contract with a malicious TRC20/beneficiary and a second reachable function that reads `_orders[commitment][token]` mid-reentrancy — this is the one aspect I could not fully confirm from static code alone (the `_filled` guard blocks the most direct single-commitment replay). The concrete, verifiable defect is the ordering discrepancy itself:
1. `evm/tron/contracts/apps/IntentGatewayV2.sol:693-701` — external call before debit. [3](#0-2) 
2. `evm/src/apps/intentsv2/IntentsBase.sol:400-409` — the corrected debit-before-call ordering that the Tron file fails to mirror. [2](#0-1)
