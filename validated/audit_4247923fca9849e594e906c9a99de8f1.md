### Title
Cross-domain signature replay lets an attacker redirect a relayer's accumulated fees by reusing a `withdraw_fees` beneficiary signature inside `accumulate_fees` - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-ismp-relayer` has two independent signed flows that authorize sending a relayer's fees to a chosen `beneficiary`: `withdraw_fees` (via `WithdrawalInputData`) and `accumulate_fees`'s optional `beneficiary_details`. Both hash an identical byte-for-byte preimage `(nonce, state_machine, beneficiary).encode()` and are checked against the **same shared `Nonce<T>` counter** for `(address, state_machine)`, with no action-specific domain separator. A signature a relayer produces to authorize one action is therefore valid for the other, and since both extrinsics are unsigned (`ensure_none(origin)`, anyone can submit them), an attacker can intercept a relayer's signed beneficiary message and replay it in the other call before the relayer's own transaction lands.

### Finding Description
`beneficiary_message` in `accumulate.rs` and `message` in `withdrawal.rs` build the signed payload: [1](#0-0) [2](#0-1) 

Both take `(nonce: u64, state_machine/dest_chain: StateMachine, beneficiary: bytes)` and SCALE-encode the exact same tuple shape before hashing with `keccak_256`. Nothing in the preimage identifies which extrinsic ("withdraw a balance" vs. "redirect this specific accumulation batch") the signature is for.

Both flows also read/mutate the **same** `Nonce<T>` storage item for `(delivery_address/address, state_machine)`: [3](#0-2) [4](#0-3) 

Both `accumulate_fees` and `withdraw_fees` are dispatched with `ensure_none(origin)`, i.e. unsigned/permissionless — anyone can submit the call once they have a valid signature: [5](#0-4) 

Because the preimage and the nonce counter are shared, a signature a relayer creates for one purpose is accepted by the other code path. Concretely: a relayer who wants to withdraw their existing `Fees` balance to `beneficiary X` signs `message(nonce, chain, X)` and broadcasts a `withdraw_fees` extrinsic. That signature+payload is visible in the mempool/transaction. An attacker who observes it can instead submit an `accumulate_fees` call — with a `WithdrawalProof` proving a legitimate, unclaimed delivery by that same relayer (`delivery_address`) — and set `beneficiary_details = (X, signature)`. `accumulate()` accepts this because:
1. `nonce = Nonce::<T>::get(&delivery_address, state_machine)` still matches (attacker front-runs before the original `withdraw_fees` consumes it),
2. the reconstructed `beneficiary_message(nonce, state_machine, X)` is byte-identical to the intercepted `message(nonce, chain, X)`,
3. the signature check only verifies the signer equals `delivery_address` — it never checks the intended target extrinsic.

The result: `Fees::<T>::try_mutate(state_machine, X, ...)` credits the newly-proven batch's `total_fee` to `X` instead of to the actual relayer, and `Nonce` is bumped — invalidating and front-running the relayer's original `withdraw_fees` transaction.

### Impact Explanation
This lets an unprivileged third party (no relayer key, no admin/governance access, no malicious peer/prover assumption) redirect a relayer's rightfully-earned protocol fees to an arbitrary address by replaying a signature the relayer published for a different, narrower purpose. This is a direct instance of "wrong beneficiary/amount" fund diversion and matches the bounty's "stealing or loss of funds" / "logic attacks" category — structurally analogous to the Aura `ExtraRewardsDistributor` bug where a caller-controlled parameter let one user forfeit another user's rewards to an unintended recipient.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` calls are unsigned extrinsics visible in the public mempool before inclusion, so intercepting a relayer's signature is trivial for anyone monitoring the chain. The only requirement is that the attacker also supply a valid `WithdrawalProof` for a delivery made by the same relayer — but delivery receipts and source fee proofs are public on-chain/via RPC once a delivery happens, so no privileged information is needed. The race only needs the attacker's transaction to land before the relayer's own `withdraw_fees`, which front-running/transaction-ordering control on an unsigned-extrinsic pool makes very feasible.

### Recommendation
Add a distinct domain separator (e.g. an action tag byte/string such as `b"ACCUMULATE_BENEFICIARY"` vs `b"WITHDRAW_BENEFICIARY"`) to each signed preimage so a signature for one extrinsic can never validate for the other. Additionally, consider using separate nonce namespaces (or including a call-specific discriminant in the nonce key) for the accumulate-redirect flow and the withdraw flow so consuming one does not silently interact with the other.

### Proof of Concept
1. Relayer `R` has delivered a batch and wants to withdraw an existing `Fees[chain][R]` balance to `beneficiary X`. `R` computes `nonce = Nonce[R, chain]`, signs `msg = keccak256((nonce, chain, X).encode())`, and submits `withdraw_fees(WithdrawalInputData{ signature, dest_chain: chain, beneficiary: Some(X) })` (unsigned extrinsic, visible pre-inclusion).
2. Attacker `A` observes this pending extrinsic and extracts `(signature, X)`.
3. `A` separately obtains a valid `WithdrawalProof` for a fresh, still-unclaimed delivery made by `R` on `chain` (source/dest state proofs are public data), and constructs `beneficiary_details = Some((X, signature))` using the *same* `nonce`.
4. `A` submits `accumulate_fees(withdrawal_proof)` with higher priority/earlier inclusion than `R`'s `withdraw_fees`.
5. In `Pallet::accumulate`, `Nonce::<T>::get(&R, chain)` still equals `nonce`; `beneficiary_message(nonce, chain, X)` reproduces the identical hash `R` signed; signature check passes (`signature.verify(...)` recovers `R`); `Nonce[R, chain]` is bumped to `nonce+1`; `Fees[chain][X] += total_fee` is credited to `X` instead of `R`.
6. `R`'s original `withdraw_fees` transaction, still carrying `nonce`, now fails (`Nonce` mismatch/signature no longer matches current nonce), and the newly accumulated fee has already been diverted to `X`, which the attacker chose or colludes with — the relayer never authorized this redirect for this batch.
