### Title
`_calExpireForfeit` in `mWOMSVBaseRewarder` always returns zero forfeit due to self-referential comparison, permanently disabling reward-forfeiture redistribution to other stakers - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` initializes the variable it later compares against to the exact same value it is checked against, structurally identical to the reported `initialProposalId = proposalCount` bug where a guard condition can never trigger. As a result, the "expire forfeit" mechanism that is supposed to claw back a portion of a claimant's reward and redistribute it to the remaining stakers never executes for any caller, for any reward claim.

### Finding Description
`_calExpireForfeit` sets `rewardableAmount = _amount` and then checks `if (rewardableAmount > _amount) revert ...`, which is tautologically false, followed by `forfeitAmount = _amount - rewardableAmount`, which is always `0`: [1](#0-0) 

This function is invoked from `_sendReward`, which runs on every reward claim path (`getReward` / `getRewards`) reachable by any ordinary wallet that has staked mWOMSV and claims rewards through `MasterMagpie`: [2](#0-1) 

Because `forfeitAmount` is always `0`, the branch that would call `_queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken)` — which increases `rewardPerTokenStored` for all remaining stakers via `rewards[_rewardToken].rewardPerTokenStored` — never fires: [3](#0-2) 

This mirrors the report's bug class precisely: a variable is initialized to be identical to the thing it's compared against, making the guarded logic (forfeiture / access condition) permanently unreachable regardless of any real input.

### Impact Explanation
The forfeiture-and-redistribution logic is designed to transfer a portion of a claiming user's reward to the pool of remaining/longer-term stakers (`getReward → _sendReward → _calExpireForfeit → _queueNewRewardsWithoutTransfer`). With this code path permanently dead, that redistributed yield is never generated: it is not sent to the claimant (who only ever gets `toSend = userRewards - 0`, i.e., their full nominal accrual) nor is it added back into `rewardPerTokenStored` for other stakers. The remaining honest stakers therefore permanently lose the yield share they were entitled to receive from other users' forfeitures — this is a permanent, protocol-wide loss/freezing of unclaimed yield for unprivileged users, not contingent on any admin misconfiguration, oracle, or governance action.

### Likelihood Explanation
This triggers on every single reward claim by any staker with zero preconditions — no special setup, no privileged role, and no attacker action required. It is the default, guaranteed behavior of the deployed contract for the entire lifetime of `mWOMSVBaseRewarder`, making the likelihood effectively certain (100%) for any protocol relying on this forfeiture mechanism to correctly redistribute yield among mWOMSV stakers.

### Recommendation
Replace the dead self-referential calculation with the intended rewardable/forfeit-percentage logic (analogous to `getRewardablePercentWAD` used in `wombat/mWomSV.sol`), so that `rewardableAmount` is derived from actual lock/cool-down state rather than being hard-set equal to `_amount`: [4](#0-3) 

### Proof of Concept
1. Any unprivileged user stakes mWOMSV and accrues rewards routed through `mWOMSVBaseRewarder`.
2. User (or the protocol on their behalf) calls `MasterMagpie` → `mWOMSVBaseRewarder.getReward(_account, _receiver)`.
3. `_sendReward` calls `_calExpireForfeit(_account, userRewards[_rewardToken][_account])`.
4. Inside `_calExpireForfeit`, `rewardableAmount` is set equal to `_amount`; the guard `rewardableAmount > _amount` is always false; `forfeitAmount = _amount - rewardableAmount` evaluates to `0` unconditionally, regardless of lock status, time elapsed, or any other state.
5. `toSend = userRewards[_rewardToken][_account] - 0` is transferred in full, and `_queueNewRewardsWithoutTransfer` (which would have credited other stakers) is skipped since `forfeitAmount > 0` is false.
6. Repeat for every claim, by every user, forever — the forfeiture/redistribution feature never functions as designed.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
