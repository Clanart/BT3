### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new` enables CPU-exhaustion DoS via `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a fully attacker-controlled `(t, n)` parameter pair and then calls `ThresholdKeys::new`, which computes the group key as a sum over `1..=t` of Lagrange `interpolation_factor` evaluations. Each Lagrange factor is itself `O(t)` field multiplications plus a field inversion, so deserialization of a crafted key blob triggers `O(t²)` prime-field work plus `t` scalar multiplications — a classic asymmetric-cost denial of service mirroring the Waitress catastrophic-backtracking bug class: small input, superlinear CPU.

### Finding Description
- `ThresholdKeys::read` reads `t`, `n` directly from the untrusted stream (two u16s each, up to 65535) with no sanity bound beyond `ThresholdParams::new`'s checks (`t != 0`, `n != 0`, `t <= n`, `i <= n`) [1](#0-0) [2](#0-1) 
- It then reads `n` verification shares via `read_G` and calls `ThresholdKeys::new` [3](#0-2) 
- `ThresholdKeys::new` computes `group_key` by summing, for each of `t` participants, `verification_shares[i] * interpolation_factor(i, &t)` [4](#0-3) 
- `interpolation_factor` for `Interpolation::Lagrange` loops over the full `included` set performing a field multiply and subtraction per element, plus one field inversion at the end — `O(t)` work per call, called `t` times [5](#0-4) 

With `t = n = 65535`, the payload is ~2 MiB (65535 × 32-byte points for Ristretto/ed25519-class groups) but forces ~4.3×10⁹ field multiplications, ~65535 field inversions (each ~hundreds of multiplications), and 65535 elliptic-curve scalar multiplications — orders of magnitude more CPU than input size, entirely in `no_std`-friendly pure-Rust code with no regex-like escape.

### Impact Explanation
An unprivileged party that can supply bytes to `ThresholdKeys::read` (listed in scope as an untrusted-bytes sink) can pin a CPU core for an unbounded, input-independent-of-network duration, blocking the signing/DKG pipeline thread the same way a single malformed header blocked Waitress. The cost is quadratic-plus-inversions in a u16-controlled parameter, so the worst case is reached with a ~2 MiB input — well within typical message size limits.

### Likelihood Explanation
High wherever serialized `ThresholdKeys` cross a trust boundary (coordinator/processor message exchange, DB reload of externally-influenced blobs, REST/RPC key material). The attacker controls `t`/`n` directly; no signature or authentication is consulted before `ThresholdKeys::new` burns the CPU. The only prerequisite is a reachable `ThresholdKeys::read` on untrusted bytes.

### Recommendation
Bound `n`/`t` to a protocol-realistic maximum (e.g. the actual validator set size) inside `ThresholdParams::new` or before reading the `n` verification shares in `ThresholdKeys::read`; alternatively, precompute Lagrange denominators/numerators incrementally to reduce the work to `O(t)` multiplications plus `t` batched inversions (Montgomery batch inversion), and consider deferring `group_key` computation lazily so deserialization is `O(n)` reads only.

### Proof of Concept
```
// Construct a ThresholdKeys encoding with t = n = u16::MAX for a 32-byte-point ciphersuite:
//   id_len (4B) || C::ID || t=0xffff || n=0xffff || i=1
//   || interpolation tag = 1 (Lagrange)
//   || secret_share (32B)
//   || n * read_G inputs (e.g. repeated valid encodings of the identity/generator, 32B each)
// Total input: ~2 MiB.
// ThresholdKeys::read -> ThresholdKeys::new performs:
//   sum over i in 1..=65535 of (point * Lagrange(i, 1..=65535))
// each Lagrange factor = 65534 field muls + field subs + 1 inversion
// => ~4.3e9 field muls + 65535 inversions + 65535 EC scalar muls on a single thread.
```

```rust
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
```
