### Title
Precompiles that omit `BalanceHandlerFactory` allow native bank-balance mutations to be silently overwritten (minted/burned) by the EVM StateDB commit reconciliation - (File: `precompiles/common/precompile.go`, `x/vm/keeper/statedb.go`)

### Summary
This is the Cosmos EVM analog of the HydraDX "missing hook call" bug class. In HydraDX, `remove_token()` changed Omnipool liquidity but forgot to call the `on_liquidity_changed` hook that keeps the oracle's view of pool state in sync, so the oracle later computed prices from stale liquidity. In this repository, the equivalent synchronization mechanism is the `BalanceHandler.BeforeBalanceChange` / `AfterBalanceChange` pair [1](#0-0) , which is responsible for reflecting real `x/bank` coin-spent/received events (produced by a precompile's native action) back into the EVM `StateDB`'s cached balances. This handler is explicitly optional per precompile [2](#0-1) , and is only invoked around the native action if `p.BalanceHandlerFactory != nil` [3](#0-2) . If a precompile is constructed without wiring a `BalanceHandlerFactory`, any bank-level balance mutation it performs internally (`MintCoins`, `BurnCoins`, `SendCoins*`) will never be reflected into `StateDB`, exactly like Omnipool's liquidity change never reaching the oracle.

### Finding Description
The EVM keeper reconciles native-token balances at commit time by diffing the `StateDB`'s final cached balance against the actual spendable bank coin and minting/burning the delta to force them to match: [4](#0-3) 

This design assumes that `StateDB`'s cached balance for any account touched during the EVM message always reflects every real `x/bank` balance change that happened during that message — a guarantee that is enforced only by the `BeforeBalanceChange`/`AfterBalanceChange` pair parsing `EventTypeCoinSpent`/`EventTypeCoinReceived` (and precisebank fractional events) emitted by the precompile's native action [5](#0-4) .

Because `BalanceHandlerFactory` is optional and only invoked conditionally [3](#0-2) , any precompile that is registered without setting this factory but still performs real bank-coin mutations (mint/burn/send) creates exactly the same class of desynchronization the HydraDX report describes: the "oracle" (here, the EVM's authoritative `StateDB` balance, which is what `SetBalance` uses to reconcile actual bank state at the end of the message) never learns about the real balance change. When `SetBalance` subsequently runs its delta-based mint/burn reconciliation against the stale cached value, it will:
- **mint** the difference back to an account whose real balance was reduced (e.g., burned) without stateDB being informed — resurrecting burned value, or
- **burn** the difference from an account whose real balance was legitimately increased without stateDB being informed — destroying newly received value.

Both outcomes are irreversible accounting corruption of spendable user balances triggered purely by ordinary (unprivileged) precompile calls within a normal EVM transaction, with no privileged actor involved — directly matching the report's root cause pattern (a state-changing operation that must, but does not, propagate through the synchronization hook that a downstream accounting/pricing mechanism depends on).

### Impact Explanation
If confirmed against a specific shipped precompile lacking `BalanceHandlerFactory` wiring, this results in:
- Unauthorized minting/resurrection of previously burned or spent coins, or
- Unauthorized burning/permanent loss of legitimately transferred/minted coins,

both of which are Critical, in-scope impacts (unauthorized minting/burning/resurrection and irreversible accounting corruption of spendable user value) per the allowed impact gate. Unlike the HydraDX oracle case (stale price data), the Cosmos EVM analog directly corrupts account balances rather than just a derived price feed, making it more severe than the original finding.

### Likelihood Explanation
I was not able to fully verify, within the available tool budget, whether any of the currently shipped, non-test precompiles (bank, staking, distribution, ICS20/transfer, werc20, erc20) actually omit setting `BalanceHandlerFactory` while still performing real `x/bank` mutations in their native action — I only confirmed the mechanism is optional and centrally gated (`precompile.go`), and found actual usages wired for `werc20`/general precompile tests, plus the ERC20 module-level `ConvertCoin`/`ConvertERC20` msg-server flows which perform `MintCoins`/`BurnCoins`/`SendCoins` outside of the `BalanceHandler` framework entirely (these run in the Cosmos msg-server path, not as an EVM precompile call, but if triggered from within an EVM contract call via a precompile front-end, the same "balance change not reflected into StateDB" risk applies). Confirming which specific constructor(s) actually omit the factory (or which precompile-invoked paths bypass it) requires reading every precompile's `NewPrecompile` constructor and its native-action bank calls, which exceeded my remaining search budget.

### Recommendation
- Audit every precompile constructor to confirm `BalanceHandlerFactory` is always set whenever the precompile's native action can invoke `MintCoins`, `BurnCoins`, or any `SendCoins*` bank operation.
- Consider making `BalanceHandlerFactory` mandatory (non-optional) in the base `Precompile` struct, or add an invariant check that fails/reverts the precompile call if a balance-changing bank event is emitted without a registered handler to process it.
- Add an integration test asserting that for every registered precompile, `StateDB.GetBalance` for all bank-event-touched addresses matches `x/bank`'s actual spendable balance immediately after the precompile call, before any `SetBalance` reconciliation occurs at commit.

### Proof of Concept
Conceptual PoC (needs verification against the concrete precompile identified in the audit step above):
1. Identify (or add) a precompile `P` registered without `BalanceHandlerFactory` whose native action calls `bankKeeper.BurnCoins`/`MintCoins`/`SendCoins*` directly, e.g. one modeled on the pattern in `x/erc20/keeper/msg_server.go` (`ConvertCoinNativeERC20`/`convertERC20IntoCoinsForNativeToken`) [6](#0-5) .
2. From an EVM transaction, call `P`'s method to burn/mint real bank coins from/to account `X`.
3. Because `P` never calls `BeforeBalanceChange`/`AfterBalanceChange`, `StateDB.GetBalance(X)` remains unchanged in the current EVM message's cache.
4. At the end of the EVM message, the keeper commits state via `SetBalance(ctx, X, staleCachedAmount)` [4](#0-3) , computing `delta = staleCachedAmount - actualBankBalance` and minting or burning the difference to force `X`'s real balance back to the stale cached value — reverting/duplicating the burn/mint that `P` just performed.

```go
// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances
// from the module account to support fractional balance handling.
//
// As a result, even if a module account is marked as a BlockedAddress, a keeper-level SendCoins operation
// can emit an x/bank event in which the module account appears as a spender or receiver.
// If such events are parsed and used to invoke StateDB.AddBalance or StateDB.SubBalance, authorization errors can occur.
//
// To prevent this, balance changes from events involving blocked addresses are not applied to the StateDB.
// Instead, the state changes resulting from the precompile call are applied directly via the MultiStore.
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}
```

```go
// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
```
