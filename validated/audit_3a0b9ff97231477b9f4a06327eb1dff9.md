### Title
Quadratic resource exhaustion in MuSig key aggregation via per-key transcript cloning — (File: crypto/dkg/musig/src/lib.rs)

### Summary
`musig_key_multiexp` / `musig` build a binding-factor transcript of size O(n) over all participant keys, then `clone()` that entire transcript once per key inside `binding_factor`. A participant supplying n keys forces O(n²) byte copying and allocation — up to ~137 GB of `memcpy` work for the maximum `u16::MAX` keys — from an input of only ~2 MB.

### Finding Description
`binding_factor_transcript` allocates a `Vec<u8>` containing `context || keys_len || key_1 || ... || key_n` — size `32 + 2 + 32n` bytes. Then `binding_factor` is invoked once per index `i` with `transcript.clone()`, copying the full O(n) buffer each iteration:

- `crypto/dkg/musig/src/lib.rs:81-84` — `binding_factor` clones its `transcript: Vec<u8>` argument (passed by value via `transcript.clone()` at call sites).
- `crypto/dkg/musig/src/lib.rs:94-96` — loop `for i in 1..=keys_len { multiexp.push((binding_factor::<C>(transcript.clone(), i), ...)) }`.
- `crypto/dkg/musig/src/lib.rs:139-146` — `musig()` repeats the same pattern: `binding_factor::<C>(transcript.clone(), i)` inside the per-key loop.

`check_keys` only bounds `n` by `u16::MAX` (65535), so a single peer in an n-of-n MuSig key aggregation can supply 65535 distinct 32-byte keys (~2 MB of public input). Each of the 65535 iterations then clones a transcript that grows to ~2 MB, for ~137 GB of aggregate allocation/copy, plus the same-cost `hash_to_F` hashing per iteration — analogous to the unbounded-directive amplification in async-graphql: a small, attacker-controlled count drives disproportionate CPU/memory work.

### Impact Explanation
An unprivileged participant in a MuSig key aggregation (`musig_key`, `musig_key_vartime`, or `musig`) causes the victim's process to perform quadratic-time work — potentially allocating and copying over a hundred gigabytes across the loop — making the node unresponsive (CPU starvation / OOM) for the duration of key aggregation. This is a remote denial of service against any party performing MuSig aggregation over an untrusted key list.

### Likelihood Explanation
The attack requires only that the attacker be one of the key contributors whose public key list is aggregated — a normal, unprivileged role. No malformed encodings are needed; all keys may be valid, distinct points. Cost to the attacker is only ~2 MB of data and computing 65535 public keys.

### Recommendation
Avoid cloning the full transcript per iteration: hash the key list once into a fixed-size digest (e.g., `transcript = H(context || keys_len || keys)`) and compute `binding_factor` as `hash_to_F(dst, digest || i)`, or make `binding_factor` take `&[u8]` and extend a reusable buffer. Optionally impose a much smaller `n` bound reflecting realistic multisig sizes.

### Proof of Concept
```rust
use rand_core::OsRng;
use ciphersuite::{group::Group, Ciphersuite};
use ciphersuite_kp256::Secp256k1;
use dkg_musig::musig_key_vartime; // or musig()

// Attacker constructs the maximum permitted key list (~2 MB of input)
let keys: Vec<_> =
  (0 .. u16::MAX).map(|_| <Secp256k1 as Ciphersuite>::G::random(&mut OsRng)).collect();

// Each of the 65535 loop iterations clones a transcript of size ~32*n bytes:
// total copied ~= sum_{i=1..n} (32*n) ~= 32 * n^2 ~= 137 GB
let _ = musig_key_vartime::<Secp256k1>([0; 32], &keys);
```
