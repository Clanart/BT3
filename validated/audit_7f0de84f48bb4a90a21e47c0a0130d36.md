## Analysis

The described "concurrent in-flight transaction" framing isn't accurate for EVM semantics — transactions execute atomically and sequentially within a block (and `placeOrder` is further protected by `nonReentrant`), so two `placeOrder` calls can never be mid-flight at the same instant. However, the underlying mechanism the question points at — the sweep loop pulling the **entire current balance** of the shared `dispatcher` contract rather than only the delta produced by this call's own predispatch execution — is a real, exploitable bug, just via a different concrete path: residual/foreign balances left in the dispatcher by *any* source, swept and credited wholesale to whichever order happens to list that token next.

Key facts:
- `_params.dispatcher` is a single, permanently shared `CallDispatcher` instance used across all orders/users, and `CallDispatcher.dispatch()` is a fully public, unauthenticated function with a `receive()` fallback — anyone can send it ETH/tokens directly at any time. [1](#0-0) 
- In `placeOrder`, the sweep step computes `balance = IERC20(token).balanceOf(dispatcher)` (or `dispatcher.balance` for native) — the dispatcher's *total* current balance — and builds a transfer call moving that entire balance to `address(this)`, only requiring `balance >= requiredAmount`. [2](#0-1) 
- The "received" amount is then measured only as the gateway's own balance delta (`balancesBefore`), and anything above `order.inputs[i].amount` is merely emitted as a `DustCollected` event, not returned to any rightful owner; anything up to `order.inputs[i].amount` — regardless of whether the attacker's own predispatch call actually produced it — is credited straight into `_orders[commitment][token]`. [3](#0-2) [4](#0-3) 

Since nothing ties the swept amount to tokens actually produced by *this* order's predispatch call, any balance sitting in the dispatcher for a given token before this transaction runs (from a prior transaction's unswept dust, from a direct/mistaken transfer to the dispatcher address, or from protocol operations that route tokens through it) is fully attributable to whichever order later lists that token in `order.inputs`. An attacker only needs to satisfy the minimal predispatch requirements (non-zero `predispatch.assets` amount, e.g. 1 wei, and any valid `predispatch.call`) and declare `order.inputs[i].amount` up to the dispatcher's existing balance to have that entire balance credited into their own escrow.

### Title
Full-balance sweep of the shared, permissionless `CallDispatcher` lets an attacker credit foreign/residual token balances into their own order escrow - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder`'s predispatch sweep logic measures "received" tokens by sweeping the dispatcher's *entire* current balance for each input token, not the delta attributable to the calling order's own predispatch execution. Because `CallDispatcher` is one shared, permanently-deployed, unauthenticated contract, any balance already resident there (residual dust from a previous order, or tokens sent directly by anyone) can be swept and credited wholesale into an unrelated attacker's escrow.

### Finding Description
`placeOrder` builds `transferCalls[i]` using `balance = IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance` — the dispatcher's total balance at sweep time — and transfers that entire amount to the gateway. [2](#0-1) 
It then treats anything up to the attacker-declared `order.inputs[i].amount` as legitimately "received" and credits it to `_orders[commitment][token]`. [5](#0-4) [6](#0-5) 
There is no check that the swept amount was produced specifically by *this* order's `predispatch.call`; the invariant "escrow credited to a commitment must equal only the tokens delivered by that specific order's predispatch execution" is broken because credit is based purely on the dispatcher's ambient balance. `CallDispatcher` has no access control and a public `receive()`, so its balance can be seeded by anyone, or can hold leftover dust from a previous order whose predispatch produced a token not enumerated in that order's own `order.inputs`. [1](#0-0) 

### Impact Explanation
An attacker can steal any balance sitting in the shared dispatcher contract — whether it is dust left by a previous legitimate order's predispatch call, or tokens the attacker (or anyone) deliberately or accidentally sends to the dispatcher — by placing a minimal order that lists that token in `order.inputs` with an amount up to the dispatcher's balance. The tokens are credited directly to the attacker's own escrow (`_orders[commitment][token]`), from which they can later be withdrawn via `fillOrder`/refund flows, resulting in outright theft of funds that never passed through the attacker's own predispatch execution.

### Likelihood Explanation
Exploitation requires only a normal, unprivileged `placeOrder` call with a trivial `predispatch.call`/`predispatch.assets` (e.g., 1 wei deposit and a no-op call) and knowledge that the dispatcher currently holds an exploitable balance of some token — which can be created by the attacker themselves (direct transfer to the well-known dispatcher address) with no dependency on other users, timing, or privileged access.

### Recommendation
Bind the swept amount to tokens actually produced by this order's own `predispatch.call` — e.g., snapshot the dispatcher's balance for each input token *before* invoking `dispatch(order.predispatch.call)` and sweep only the delta (`balanceAfterPredispatch - balanceBeforePredispatch`), or deploy a fresh, single-use dispatcher/proxy per `placeOrder` call so no ambient balance from unrelated transactions can ever be present.

### Proof of Concept
1. Attacker sends 1000 `USDC` directly to the known `CallDispatcher` address (no access control required, plain ERC20 transfer).
2. Attacker calls `placeOrder` with:
   - `predispatch.assets = [{token: USDC, amount: 1}]` (minimal, satisfies `amount == 0` check),
   - `predispatch.call` = any benign call the `CallDispatcher` can execute (e.g., an `approve(0,0)` call on some contract),
   - `order.inputs = [{token: USDC, amount: 1000}]`.
3. `placeOrder` transfers attacker's 1 wei USDC into the dispatcher, dispatches the benign predispatch call, then sweeps `IERC20(USDC).balanceOf(dispatcher)` (= 1001) entirely to the gateway. [7](#0-6) 
4. `received = 1001 >= order.inputs[0].amount (1000)`, so the full 1000 USDC is credited to `_orders[commitment][USDC]`, funded almost entirely by tokens the attacker never contributed via their own predispatch. [8](#0-7)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
