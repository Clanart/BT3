### Title
Open Redirect to Dangerous URI Schemes (e.g. `smb://`) via `return_to` in OAuth Callback - (File: `app/controllers/shopify_app/callback_controller.rb`)

### Summary
`CallbackController#redirect_to_app` validates a user-influenced `return_to` value with `fully_formed_url?`, which only checks that the parsed URI has a `scheme` and a `host` — it does not restrict the scheme to `http`/`https`. Combined with `redirect_to(redirect_to, allow_other_host: true)`, this allows a crafted `return_to` value to cause the server to issue a 3xx redirect to a non-HTTP scheme (e.g. `smb://attacker-host/share`), analogous to the reported `shell.openExternal` issue where an unvalidated scheme reaches a sink that acts on arbitrary URIs.

### Finding Description
`redirect_to_app` is reached after a successful OAuth callback in an embedded app context: [1](#0-0) 

`fully_formed_url?` treats any URI with a non-empty `scheme` and `host` as "fully formed" and uses it verbatim as the redirect target with `allow_other_host: true`, bypassing Rails' same-host redirect protection. It does not check `uri.scheme` against an allow-list such as `["http", "https"]`. Only the *host* portion is checked against the trusted Shopify domain list via `deduced_phishing_attack?`, and that check derives its host from `decoded_host` (the `host` param), not from the `return_to` value itself when `fully_formed_url?` returns true — in that branch, `redirect_to` is set directly to `return_to`, and the phishing check independently re-derives `decoded_host` from `params[:host]`, so it does not gate the `return_to`-based branch's chosen scheme/host at all.

The `return_to` value originates from `session[:return_to]`, which is set in `SessionsController#copy_return_to_param_to_session` via `RedirectSafely.make_safe(params[:return_to], "/")`: [2](#0-1) 

`RedirectSafely.make_safe` (from the `redirect_safely` gem) is designed to block cross-host redirects (open redirects to a different HTTP host), but it does not enforce a scheme allow-list; a URI like `smb://evil-host/share` or `file:///path` has no conflicting "host" difference to detect in the way that gem checks, and can pass through unchanged since it is treated as an absolute, well-formed URI. That value is stored in the session, survives the OAuth round trip, and is later read back in `redirect_to_app`, which will treat it as `fully_formed_url?` and issue the redirect verbatim with `allow_other_host: true`.

### Impact Explanation
This produces a genuine, unauthenticated-request-reachable open redirect where the resulting URI's scheme is not restricted to `http(s)`. Depending on gem version behavior of `RedirectSafely.make_safe` and browser/client handling, this can be leveraged for:
- Triggering an OS-level protocol handler (e.g., a `smb://` URI used to force outbound SMB connections for NTLM credential leakage from a victim's machine — the same underlying "unrestricted scheme in an accepted redirect target" bug class as the report's `shell.openExternal` finding).
- General open-redirect abuse to a fully attacker-controlled URI for phishing purposes, since `allow_other_host: true` explicitly opts out of Rails' host-mismatch protection.

This does not achieve remote code execution by itself (unlike Electron's `shell.openExternal`, a Rails `redirect_to` only causes an HTTP 302 the browser must independently interpret), so the severity is lower than the original finding, but it is a legitimate data-validation gap in a security-relevant redirect path.

### Likelihood Explanation
Reaching this path requires an attacker to get a victim (an app installer/admin) to click a link containing a crafted `return_to` parameter that starts the OAuth flow (`/login?shop=...&return_to=smb://evil/share`), then complete the standard Shopify OAuth consent. No secret or privileged access is needed to construct the malicious link — only social engineering, matching the "trick the wallet owner into opening the link" scenario from the analog report. The main uncertainty is whether the installed version of `RedirectSafely.make_safe` fully neutralizes non-`http(s)` absolute URIs (its exact gem source is not present in this repo's index, so scheme-filtering behavior of that dependency could not be independently confirmed here).

### Recommendation
- In `fully_formed_url?`, explicitly allow-list `uri.scheme` to `%w[http https]` (or the app's own scheme) in addition to checking `scheme.present? && host.present?`.
- Do not rely solely on `RedirectSafely.make_safe` for scheme validation before persisting `return_to` in `SessionsController#copy_return_to_param_to_session`; validate the scheme there as well before storing to session.
- Consider removing/limiting `allow_other_host: true` on the `return_to` code path to only the verified Shopify/embedded-app host, rather than any externally supplied absolute URL.

### Proof of Concept
1. Attacker crafts: `https://victim-store.example.com/login?shop=victim-store.myshopify.com&return_to=smb%3A%2F%2Fattacker.example%2Fshare`
2. Victim (a store admin with the app installed or installing it) clicks the link; `SessionsController#copy_return_to_param_to_session` stores `return_to` in the session via `RedirectSafely.make_safe`.
3. Victim completes OAuth; `CallbackController#callback` → `redirect_to_app` is invoked.
4. `fully_formed_url?("smb://attacker.example/share")` returns `true` (scheme `smb`, host `attacker.example` both present), so `redirect_to = "smb://attacker.example/share"`.
5. `redirect_to(redirect_to, allow_other_host: true)` issues a redirect to the `smb://` URI to the victim's browser. [3](#0-2)

```ruby
    def redirect_to_app
      if ShopifyAPI::Context.embedded?
        return_to = session.delete(:return_to)
        redirect_to = if fully_formed_url?(return_to)
          return_to
        else
          "#{decoded_host}#{return_to}"
        end

        redirect_to = ShopifyApp.configuration.root_url if deduced_phishing_attack?
        redirect_to(redirect_to, allow_other_host: true)
      else
        redirect_to(return_address)
      end
    end

    def fully_formed_url?(return_to)
      uri = Addressable::URI.parse(return_to)
      uri.present? && uri.scheme.present? && uri.host.present?
    end
```
