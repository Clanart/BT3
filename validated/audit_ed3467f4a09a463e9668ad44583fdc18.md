### Title
Self-declared, unauthenticated OP_RETURN operator pubkey lets an unprivileged withdrawer assign bridge reimbursement to any operator who never funded the payout - ([File: circuits-lib/src/bridge_circuit/mod.rs], [File: core/src/verifier.rs])

### Summary
The `operator_xonlypk` used everywhere to bind a payout to a reimbursement (`deposit_constant`, `payout_payer_operator_xonly_pk`, `is_kickoff_malicious`) is parsed unconditionally from the payout transaction's OP_RETURN output via `parse_op_return_data`. That output is never covered by the withdrawing user's `SinglePlusAnyoneCanPay` signature and no other input of the payout tx is required to be spendable by the named operator, so any unprivileged party constructing/broadcasting the payout transaction can put an arbitrary operator's x-only pubkey there while funding the transaction with their own money.

### Finding Description
The binding claimed by the protocol is: `deposit_constant.operator_xonlypk == the operator whose funds actually paid output 0 of the payout tx`.

- `create_payout_txhandler` builds the OP_RETURN output from a raw `operator_xonly_pk` argument and only Schnorr-signs input 0 with the *user's* key over a `SinglePlusAnyoneCanPay` sighash: [1](#0-0) . `SIGHASH_SINGLE|ANYONECANPAY` covers only input 0 and output 0 - it does not sign the anchor output or the OP_RETURN output, and it does not prevent anyone from adding further inputs to fund the transaction.
- `Operator::withdraw` normally sets `operator_xonly_pk = self.signer.xonly_public_key` and validates the user's signature only over input 0's sighash: [2](#0-1) . Nothing prevents an attacker from bypassing this RPC entirely and broadcasting their own transaction directly to Bitcoin with the same withdrawal UTXO + user signature but an arbitrary OP_RETURN pubkey and attacker-supplied fee inputs.
- The verifier ingests whatever pubkey appears in the OP_RETURN of the actual on-chain payout tx with no further authentication and stores it as `payout_payer_operator_xonly_pk`: [3](#0-2) .
- `bridge_circuit` computes `deposit_constant` straight from that same unauthenticated `parse_op_return_data` value: [4](#0-3)  and [5](#0-4) . The only Bitcoin-level assertions on the payout tx are that `input[payout_input_index].previous_output` matches the withdrawal outpoint/vout (`assert_eq!` at lines 190–204) - completely independent of the OP_RETURN field.
- The only guard tying "who claims reimbursement" to "who is named in OP_RETURN" is `Verifier::is_kickoff_malicious`, which is a pure equality check between the self-declared OP_RETURN pubkey and the kickoff sender's self-declared `kickoff_data.operator_xonly_pk`: [6](#0-5) . It performs no check that the named operator's wallet actually supplied the payout tx's funding inputs.
- Crucially, presigned kickoff/round transactions are generated for *every* registered operator for *every* deposit at deposit-finalization time (not gated by who later pays out the withdrawal): [7](#0-6) . So any operator already holds valid presigned kickoff transactions for a deposit it never funded a payout for.

Exploit flow: an unprivileged withdrawer (the attacker) requests a withdrawal on Citrea, obtains their own `SinglePlusAnyoneCanPay` signature over input 0/output 0 (as intended by protocol design), then constructs and broadcasts the payout Bitcoin transaction themselves - funding any extra inputs (fees/difference) from their own wallet - with an OP_RETURN naming any registered operator X's x-only pubkey, without X's knowledge or a signature from X anywhere in the transaction. Once confirmed, the verifier's `update_finalized_payouts` records X as `payout_payer_operator_xonly_pk`. Operator X can then submit the (already-presigned) kickoff for this deposit; `is_kickoff_malicious` passes because the OP_RETURN pubkey matches `kickoff_data.operator_xonly_pk`, and X proceeds to `Reimburse`, collecting the deposited BTC from the move-to-vault UTXO despite never having funded the payout.

None of the existing guards catch this: `SPV::verify` and the storage-proof `assert_eq!`s only check the withdrawal outpoint/vout referenced by `payout_spv.transaction.input[payout_input_index]`, not who funded any other input or the OP_RETURN; `is_kickoff_malicious` only compares two self-declared values that both trace back to the same unauthenticated OP_RETURN byte string.

### Impact Explanation
BTC from a move-to-vault UTXO can be reimbursed to an operator that never fronted the withdrawal, i.e. "an operator reimbursed for a payout it never funded" - the exact Critical category listed. This is repeatable for every withdrawal and against every currently-registered operator, since any operator already holds presigned kickoff transactions for every deposit. The blast radius covers the entire operator set and every deposit/withdrawal pair.

### Likelihood Explanation
The attacker only needs to be an ordinary withdrawing user: call Citrea's `withdraw`, obtain the `SinglePlusAnyoneCanPay` signature over their own input/output (a normal, expected step of the protocol), then build and broadcast the Bitcoin transaction themselves instead of going through an operator's gRPC `Withdraw`/`InternalWithdraw`. Cost is limited to the withdrawal amount plus mining fees (which the attacker must pay regardless, since they are the withdrawing party) - no operator, verifier, aggregator, or Citrea cooperation is required, and the attack can be repeated on every withdrawal.

### Recommendation
Cryptographically bind the operator identity to the payout transaction instead of trusting a self-declared OP_RETURN byte string: e.g., require the OP_RETURN output (or the whole set of non-user-signed outputs/inputs) to be committed by an operator signature checked against `kickoff_data.operator_xonly_pk` inside `bridge_circuit`/`is_kickoff_malicious`, or require the extra funding input(s) of the payout tx to spend from an address provably controlled by the named operator (e.g., their known collateral/reimbursement wallet), verified during `update_finalized_payouts`/`is_kickoff_malicious` before recording `payout_payer_operator_xonly_pk`.

### Proof of Concept
In `circuits-lib/src/bridge_circuit/mod.rs` tests (extending `test_operator_xonlypk_from_op_return`) and/or a `core` integration test:
1. Build a payout `Transaction` whose input 0 spends a withdrawal UTXO with a `SinglePlusAnyoneCanPay` signature from a "user" keypair (not any operator key); add an additional input signed/funded by a separate "attacker" keypair to cover the payout amount and fee.
2. Set output 0 to the required withdrawal payout, output 1 to the anchor, and output 2 (OP_RETURN) to an arbitrary "victim operator" x-only pubkey `X` that appears nowhere else in the transaction (no signature from `X`).
3. Assert the transaction is fully valid Bitcoin-consensus-wise (`SECP.verify_schnorr` on input 0 succeeds using only the user's key, exactly as `Operator::withdraw` does at `core/src/operator.rs:630-637`).
4. Call `parse_op_return_data`/`deposit_constant` on this tx (as `bridge_circuit` does at `circuits-lib/src/bridge_circuit/mod.rs:216-229`) and assert `operator_xonlypk == X.serialize()`.
5. Call `Verifier::is_kickoff_malicious`-equivalent logic with `kickoff_data.operator_xonly_pk == X` and payout info sourced from this forged tx; assert it returns `false` (not malicious), i.e., `X`'s equality check (`core/src/verifier.rs:1887`) passes despite `X` never signing or funding any input of the transaction - demonstrating `deposit_constant.operator_xonlypk == X` while the true funder is the "attacker" keypair, breaking the claimed binding.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
