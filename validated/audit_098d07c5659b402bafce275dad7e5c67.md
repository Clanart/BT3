## Title
Recursive clone disables Git's built-in submodule hook-execution protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), allowing a malicious cloned repository to achieve code execution - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` function explicitly overrides Git's own safety environment variable `GIT_CLONE_PROTECTION_ACTIVE`, forcing it to `'false'` for every `git clone --recursive` invocation. [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is a real upstream Git mechanism (introduced as part of the fix for the submodule/hook recursive-clone RCE class, e.g. CVE‑2024‑32002) that Git itself sets to prevent a nested/submodule clone from re-triggering hook execution paths in an unsafe way while a recursive clone is unwinding. By force-setting this to `false` on every invocation, Desktop is deliberately re-enabling the exact code path that upstream Git added protection against, for every single `--recursive` clone it performs — which is the default for all clones done through the app.

### Finding Description
The broken invariant, translated from the smart-contract report's "protection flag that should gate a sensitive action is never in the state the code assumes," is here inverted: Git upstream *sets* `GIT_CLONE_PROTECTION_ACTIVE` internally to guard against unsafe hook execution during recursive submodule clones, but GitHub Desktop actively *disables* that protection unconditionally:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
``` [2](#0-1) 

The attacker's primitive here is full control over the content of a cloned repository (the exact "attacker controls a cloned/fetched repository" scenario in scope). Because `--recursive` is always passed, any submodule the attacker declares in `.gitmodules` will be recursively cloned as part of the operation, and with the protection flag forced off, whatever hardening Git added around hook execution during that recursive submodule clone/checkout is bypassed for every Desktop-initiated clone.

Notably, Desktop's own `submodule.ts` code for post-operation submodule updates does *not* disable this protection — it only conditionally adds `protocol.file.allow=always` when explicitly needed [3](#0-2) , which underlines that the blanket disabling in `clone.ts` is an outlier rather than a consistently-applied, deliberate design decision.

### Impact Explanation
If the underlying Git binary bundled with Desktop relies on `GIT_CLONE_PROTECTION_ACTIVE` to prevent hook/script execution paths from firing unsafely during a recursive submodule clone (the scenario the upstream Git protection was built for), then forcing this variable to `false` reopens that code execution surface for every "Clone repository" action a user performs in Desktop — satisfying the "attacker controls a cloned repository ... result is code execution" impact criterion. This is a supply-chain-style attack: a user only needs to clone (or "Open in Desktop") a malicious repository URL; no other unusual steps are required.

### Likelihood Explanation
Likelihood is high for any Desktop user who clones an untrusted or unfamiliar repository, since:
- `clone()` is the single, unconditional path used for all repository clones initiated from the UI (including the `x-github-client://openRepo/...` deep-link flow parsed in `app/src/lib/parse-app-url.ts` [4](#0-3)  and dispatched via `openRepositoryFromUrl` [5](#0-4) ).
- `--recursive` is always appended, so an attacker only needs to add a submodule entry to their repository to have it recursively cloned during Desktop's clone flow.
- The override is unconditional — there's no code path where the protection remains enabled.

I could not verify from the indexed code exactly which Git/dugite version is bundled or confirm the precise semantics/behavioral consequence of `GIT_CLONE_PROTECTION_ACTIVE=false` against that specific Git version (this depends on the vendored `git`/`dugite` binary, which is outside the indexed source). This is a meaningful gap: without confirming the bundled Git version's exact use of this flag, the severity cannot be fully confirmed as remote code execution versus a narrower behavioral regression.

### Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts`, or gate it behind a narrowly scoped, well-documented justification tied to a specific known-safe Git version.
- Audit why this override exists (git blame / PR history was not available in the indexed snapshot — the repository shows only a single "Initial commit" for this file, so the original intent could not be traced) and confirm against the currently bundled Git/dugite version whether disabling this protection reintroduces the hook-execution issue the flag was designed to prevent.
- Add a regression/security test that performs a clone of a repository containing a submodule with an executable hook payload and asserts that the hook does not execute during the clone.

### Proof of Concept
1. Attacker creates a public repository `evil/repo` containing a `.gitmodules` entry pointing to a submodule whose repository contains a hook-triggering payload consistent with the class of issue `GIT_CLONE_PROTECTION_ACTIVE` was designed to block (e.g., a payload exploiting the recursive-submodule-clone hook execution window fixed by CVE‑2024‑32002‑class changes upstream).
2. Victim clicks a GitHub "Open with GitHub Desktop" link (`x-github-client://openRepo/https://github.com/evil/repo`) or manually clones `evil/repo` in Desktop.
3. Desktop calls `clone()` in `app/src/lib/git/clone.ts`, which runs `git clone --recursive -- https://github.com/evil/repo <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment.
4. Because the protection Git relies on internally is disabled, the payload embedded in the submodule executes during the recursive clone, achieving code execution in the context of the user running Desktop — instead of being blocked as it would be by default (unset) Git behavior.

Note: I was unable to execute or trace this against the actual bundled Git binary from the indexed code alone (no terminal/build access in this mode), so step 3–4 describe the expected mechanism based on the documented purpose of `GIT_CLONE_PROTECTION_ACTIVE` rather than a directly observed exploit trace. A Devin session with full repo/build access would be needed to confirm the exact bundled Git version and reproduce the exploit end-to-end.
