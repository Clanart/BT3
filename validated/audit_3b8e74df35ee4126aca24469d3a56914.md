Based on my investigation, the closest analog to the ERC20 "not all tokens return a boolean" bug class in GitHub Desktop is the fragile success/failure heuristic in `createDesktopStashEntry`, which is exactly the same broken invariant: the code infers operation success from the *absence* of an expected failure signal, rather than from a reliable positive signal, and the author's own comments document that this heuristic is known to be wrong in at least one reachable case. ### Title
`createDesktopStashEntry` infers a successful stash from the absence of an `error:` prefix, misreporting failed stashes as successful on unborn/attacker-crafted repositories - (File: app/src/lib/git/stash.ts)

### Summary
`createDesktopStashEntry` treats `git stash push` exit code `1` as success whenever stderr does not contain a line starting with `error:` [2](#0-1) . The function's own inline comment ("Here be dragons") documents that this assumption is already known to be false for at least one reachable Git state: an unborn repository, where `git stash push` exits with code `1` and prints "You do not have the initial commit yet" — a message that does **not** start with `error:` — yet no stash is actually created [3](#0-2) . In that situation the function still returns `true`, i.e. it reports to its caller that a stash was successfully created when it was not.

### Finding Description
This mirrors the ERC20 bug class exactly: instead of checking a reliable positive "success" signal, the code checks for the *absence* of a specific negative signal (a `stderr` line matching `/^error: /m`) and treats that absence as proof of success. Just as some ERC20 tokens omit the expected boolean return value (causing correct transfers to be misclassified as failures), here Git can omit the expected `error:` prefix on genuine failures (causing failed stashes to be misclassified as successes). The exit-code/stderr contract between Desktop and the underlying `git stash push` command is not actually guaranteed to be as narrow as the code assumes, and the author explicitly flags this as unverified ("I got curious about the assumptions made in the following logic... That didn't hold up to a quick read of the stash code").

The precondition that triggers this — an unborn repository (no initial commit) — is directly reachable by an attacker who controls a repository the victim clones, opens via a GitHub Desktop deep link ("Open in Desktop"), or adds as a remote/fetch target: a repository can trivially be crafted with no commits on the default branch, or the victim can be steered into checking out an orphan/empty branch supplied by the attacker.

### Impact Explanation
`createDesktopStashEntry`'s boolean return value is consumed by higher-level flows (branch switching / checkout in `app-store.ts`) that use it to decide whether uncommitted working-directory changes were safely preserved before further destructive Git operations (e.g., checkout) are carried out. If the function reports `true` while no stash was actually created, any code path that trusts this signal to justify overwriting or discarding the working directory can silently destroy the user's uncommitted changes — a "silent corruption of what the user commits" scenario, since the loss is not surfaced as an error to the user.

### Likelihood Explanation
Medium. The specific case is narrow (unborn repository) and already acknowledged in the code as fragile with the caveat that other unverified Git states may exist. It requires the user to be operating in/switching to a branch context that is unborn/empty — which is unusual but fully attacker-inducible via a crafted repository or branch, and is not gated by any additional Desktop-side validation of the stash's actual existence (e.g., no subsequent `git stash list` check before trusting the returned boolean).

### Recommendation
Do not infer stash success from the *absence* of a specific error string. After a non-zero exit from `git stash push`, verify success positively — e.g., call `git stash list` (or compare it before/after) to confirm a new stash entry actually exists — before returning `true`. Apply the same principle to `popStashEntry`, which uses an analogous heuristic ("exit code `1` and stderr is empty ⇒ assume success") that is subject to the same class of false positive [4](#0-3) .

### Proof of Concept
1. Attacker publishes/hosts a Git repository whose default branch has no commits (unborn HEAD), or gets the victim to create/checkout such a branch via a crafted "Open in Desktop" link or fetch.
2. Victim makes local changes while on this unborn branch and triggers a Desktop action that calls `createDesktopStashEntry` (e.g., switching branches with uncommitted changes present).
3. `git stash push -m <message>` exits with code `1` and stderr `"You do not have the initial commit yet"` (no `error:` prefix).
4. The `.catch` handler in `createDesktopStashEntry` finds no match for `/^error: /m`, logs "a stash was created successfully" and returns `e.result`, and the function ultimately returns `true` [5](#0-4) , even though `git stash list` shows no stash exists.
5. Any subsequent Desktop logic that trusts this `true` return value to proceed with an operation that overwrites the working directory will do so without an actual safety-net stash, risking silent loss of the victim's uncommitted work.

    e => {
      // Note: 2024: Here be dragons. As I converted this code to get rid of the

      // following logic. It assumes that as long as the exit code for `git
      // stash push` is 1 and there are no lines beginning with "error: " then
      // a stash was created. That didn't hold up to a quick read of the stash
      // code. For example, running git stash push in an unborn repository will
      // get you an exit code of 1 but no stash was created:
      //
      // % git stash push -m foo ; echo $?
      // You do not have the initial commit yet
      // 1
      //
      // I'm not going to mess with this now but I felt the need to document
      // my findings should I or any other brave soul choose to tackle this in
      // the future.
      if (e instanceof GitError && e.result.exitCode === 1) {
        // search for any line starting with `error:` -  /m here to ensure this is
        // applied to each line, without needing to split the text
        const errorPrefixRe = /^error: /m

        const matches = errorPrefixRe.exec(coerceToString(e.result.stderr))
        if (matches !== null && matches.length > 0) {
          // rethrow, because these messages should prevent the stash from being created
          return Promise.reject(e)
        }

        // if no error messages were emitted by Git, we should log but continue because
        // a valid stash was created and this should not interfere with the checkout

        log.info(
          `[createDesktopStashEntry] a stash was created successfully but exit code ${result.exitCode} reported. stderr: ${result.stderr}`
        )
        return e.result
      }
      return Promise.reject(e)
    }
  )

  // Stash doesn't consider it an error that there aren't any local changes to save.
  if (result.stdout === 'No local changes to save\n') {
    return false
  }

  return true
