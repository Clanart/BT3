### Title
Unbounded length-prefixed deserialization in `SchnorrAggregate::read` enables remote memory-exhaustion DoS - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::<C>::read` trusts a 4-byte little-endian count (`u32`, up to ~4.29 billion) and then deserializes that many group elements into a `Vec<C::G>` with no upper bound, no cross-check against the remaining input length, and no streaming cap. This is the direct analog of CVE-2020-24736 (attacker-supplied input driving uncontrolled memory consumption / crash): a crafted buffer causes the host process to allocate memory proportional to the attacker's payload, terminating on OOM or aborting on allocation failure. [1](#0-0) 

### Finding Description
`SchnorrAggregate::read` reads `len` as a `u32` and loops `read_G` `len` times, pushing each decoded point onto `Rs`:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }
    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

`read` accepts any `R: Read`, including network/peer streams. An unprivileged party feeding untrusted bytes to this API (the enumerated reachable-read surface in scope) can set `len` to `0xFFFFFFFF` and stream point encodings indefinitely. Each accepted point (e.g., a 32–33 byte compressed encoding) expands into an in-memory `C::G` (an affine/projective representation several times larger than its wire encoding) inside a contiguous `Vec`, so memory grows ~2–3x faster than bytes received, and Rust aborts on allocation failure rather than returning a recoverable error.

The same pattern exists nearby — `ThresholdKeys::read` allocates `Vec::with_capacity(n)` from an attacker-controlled `n` before reading (`crypto/dkg/src/lib.rs:608`) — but `SchnorrAggregate::read` is the stronger instance because the count is a full `u32` and the `Vec` grows without bound for as long as the peer keeps the stream open.

### Impact Explanation
A single malicious peer message causes the verifying/aggregating process to consume memory until the allocator aborts or the OS OOM-killer terminates it — a denial of service of a signing/verification node, matching the CVE's impact class (C:N/I:N/A:H). The writer side even acknowledges counts up to 4 billion are representable (`aggregate.rs:92-98`), so no design assumption limits the field.

### Likelihood Explanation
Reachability requires a code path where `SchnorrAggregate::read` is applied to peer-supplied bytes; the API is public and takes an arbitrary `Read` stream, so any integrator deserializing aggregates from the wire is exposed. The attack needs no valid signatures, no keys, and no cryptographic work — only a large length prefix and a sustained byte stream — so exploitation cost is trivial wherever the API is reachable. Likelihood is gated only by deployment usage of aggregate-Schnorr verification.

### Recommendation
- Before reading `len`, bound it against the remaining input size (`len <= remaining / <C::G as GroupEncoding>::Repr::default().as_ref().len()`) when the reader supports length introspection, or enforce a protocol-level maximum aggregate size.
- Return `io::Error` for counts exceeding the bound instead of attempting allocation.
- Apply the same check to `ThresholdKeys::read`'s `n`-driven loop (`crypto/dkg/src/lib.rs:608-612`) and any other length-prefixed deserialization of untrusted input.

### Proof of Concept
Conceptual (the fix and reachability are in the code path):

```rust
use std::io::Cursor;
use ciphersuite::Secp256k1;
use schnorr::aggregate::SchnorrAggregate;

// Attacker-controlled bytes: u32 count of ~4.29 billion followed by
// a stream of valid compressed point encodings.
let mut bytes = u32::MAX.to_le_bytes().to_vec();
// Append arbitrary valid Secp256k1 encodings indefinitely;
// each accepted point grows Rs by sizeof(C::G) on the heap.
bytes.extend(std::iter::repeat(valid_point_encoding).take(N).flatten());

// Called on peer-supplied bytes; memory grows until abort/OOM.
let _ = SchnorrAggregate::<Secp256k1>::read(&mut Cursor::new(bytes));
```

The vulnerable loop is `aggregate.rs:83-85`; there is no bound between the `u32` read at line 79 and the allocation loop.

Note: I could not fully trace every caller of `SchnorrAggregate::read` in the remaining search budget, so the "unprivileged party reaches this API" assumption rests on it being a public deserialization entry point; if no in-scope caller feeds it untrusted bytes, severity reduces accordingly.
