### Title
Unsigned OP_RETURN operator-attribution output in `payout_tx` lets an unprivileged party hijack reimbursement credit for a fronted withdrawal - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The `payout_tx` created by `create_payout_txhandler` is signed by the user with `SIGHASH_SinglePlusAnyoneCanPay`, which cryptographically commits only to input 0 and output 0 (the withdrawal payout). The anchor output and, critically, the OP_RETURN output that records which operator "fronts" the withdrawal (and therefore who is later credited/reimbursed) are **not covered** by the signature. Any party observing the user's signature can therefore construct a competing transaction spending the same withdrawal UTXO, add their own funding input, keep the same signed output 0, but substitute an arbitrary xonly public key into the OP_RETURN output — redirecting reimbursement credit to an operator that never funded the payout, while the honest operator that actually intended to front it is permanently locked out of matching that withdrawal.

### Finding Description
`create_payout_txhandler` builds the transaction with 1 signed input and 3 outputs: the user payout (output 0, signed), an anchor (output 1), and an OP_RETURN containing `operator_xonly_pk` (output 2), and finalizes the witness with only the user's signature over input 0: [1](#0-0) 

The user's signature is required to use `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params`: [2](#0-1) 

`SinglePlusAnyoneCanPay` commits only to the single input being signed and the output at the same index (output 0). It places **no** commitment on any other input or output — meaning outputs 1 (anchor) and 2 (OP_RETURN operator attribution) are fully malleable by anyone who obtains the raw signature (e.g., from a broadcast/mempool transaction, or from the `Withdraw`/`InternalWithdraw` RPC response which returns the raw signed tx). This is documented in the tx-sender's own RBF/PSBT logic, which explicitly recognizes and preserves only S+AP-style signatures while allowing everything else to be rebuilt: [3](#0-2) 

On the verifier side, when a payout transaction confirms, `update_finalized_payouts` reads whatever xonly public key happens to be embedded in the OP_RETURN of the *mined* transaction and stores it as the authoritative "who fronted this withdrawal" record, with no cross-check against who actually supplied the funding inputs: [4](#0-3) 

This record (`payout_payer_operator_xonly_pk`) is exactly what each operator's `PayoutCheckerTask` polls to discover "its own" unhandled payouts and drive the reimbursement (kickoff) process: [5](#0-4) [6](#0-5) 

**The equality that should hold:** `payout_payer_operator_xonly_pk` (the party credited for reimbursement) `==` the party whose bitcoin actually funded the extra inputs of the confirmed `payout_tx` (the party that paid).

**Before the attack:** Operator A intends to front withdrawal W. It builds `payout_tx` with its own funding inputs and OP_RETURN = A's xonly_pk, and broadcasts it (via `operator.withdraw` → `fund_raw_transaction` + `send_raw_transaction`): [7](#0-6) 

**After the attack:** Before A's transaction confirms, an unprivileged party extracts the S+AP signature (visible in the mempool or in the RPC's `RawSignedTx` response) and constructs a competing, higher-fee transaction spending the same withdrawal UTXO with the same output 0, but funded from its own (or anyone's) wallet, and with OP_RETURN = an arbitrary registered operator B's xonly_pk (or its own, if it wants to disrupt bookkeeping). If this transaction confirms first: (1) the withdrawal is fulfilled from funds not supplied by A or B, (2) the chain-tracker attributes the payout to B, who is now eligible via `get_first_unhandled_payout_by_operator_xonly_pk` to claim reimbursement it never funded, and (3) A's actual funding attempt is double-spent/invalidated, and even if A retries, A can never be matched to this now-attributed withdrawal index (the `withdrawals` table row is keyed by `idx`, one row per withdrawal), permanently preventing A from being reimbursed for work it performed.

### Impact Explanation
This breaks the core custody-attribution binding the protocol relies on for reimbursement bookkeeping. Two Critical outcomes described in the impact taxonomy are directly reachable:
- "an operator reimbursed for a payout it never funded" — operator B gets `is_payout_handled` tracking and can drive `handle_finalized_payout`/kickoff for a withdrawal it did not pay for.
- "an honest operator permanently unable to be reimbursed" — operator A's genuine funding of the withdrawal is preempted and its `withdrawals` row now points to a different payer, with no path to correct the attribution afterward (there is no dispute/report mechanism visible in the reimbursement flow to re-attribute after this record is written).

### Likelihood Explanation
No privileged role is required. The attacker only needs to observe a broadcast (or mempool-visible) S+AP-signed `payout_tx`, or obtain the raw hex from the `Withdraw`/`InternalWithdraw` RPC response, and craft/broadcast a competing transaction with a higher fee (a standard RBF/mempool race). This requires only generic Bitcoin transaction-construction capability, not any verifier/operator/aggregator key material.

### Recommendation
Bind the operator-attribution output cryptographically to the transaction the operator actually funds, e.g. by having the operator's own kickoff/collateral signature also cover the OP_RETURN output (use `SIGHASH_ALL` semantics for the operator-contributed portion, or commit to the operator pubkey inside a script the operator must sign), or by validating at confirmation time that the additional inputs of the mined `payout_tx` are provably controlled by the operator whose pubkey appears in the OP_RETURN before recording `payout_payer_operator_xonly_pk`.

### Proof of Concept
1. Operator A calls `withdraw`/`Withdraw` for withdrawal index `W`; the resulting `payout_tx` has input 0 signed with `SinglePlusAnyoneCanPay`, and OP_RETURN = A's xonly_pk (see `core/src/builder/transaction/operator_reimburse.rs:407-436`, `core/src/operator.rs:620-691`).
2. Attacker extracts the mempool/broadcast transaction (or the RPC's `RawSignedTx`), copies the signed input-0 witness for output 0 (per `crates/clementine-tx-sender/src/rbf.rs:137-147`, which shows exactly this witness is portable/reusable across a rebuilt PSBT).
3. Attacker builds a new transaction: same input 0/witness/output 0, but its own extra funding input(s), its own anchor output, and OP_RETURN = operator B's xonly_pk (any registered operator, chosen by attacker).
4. Attacker broadcasts with a competitive fee; it confirms instead of A's transaction.
5. `update_finalized_payouts` (`core/src/verifier.rs:2311-2350`) parses the OP_RETURN of the confirmed tx and stores B as `payout_payer_operator_xonly_pk` for index `W`.
6. `PayoutCheckerTask`/`get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/task/payout_checker.rs:41-79`, `core/src/database/verifier.rs:282-313`) surfaces this withdrawal to operator B's reimbursement flow, though B funded nothing; operator A can never be matched to index `W` again.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
