## Title
Unsanitized `clone_url` from GitHub API allows `ext::`/`file://` upstream remote → RCE via `git fetch upstream` - ([File: app/src/lib/stores/git-store.ts])

### Summary
`GitStore.addUpstreamRemoteIfNeeded()` (and `updateExistingUpstreamRemote()`) take `repository.gitHubRepository.parent.cloneURL` — a value populated verbatim from the `clone_url` field of a GitHub API JSON response — and pass it straight into `git remote add`/`git remote set-url` with no scheme allow-listing.

### Finding Description
`IAPIRepository.clone_url` is typed as a bare `string` with no validation performed on it anywhere in the ingestion pipeline: [1](#0-0) 

When a repository (or its `parent`, for forks) is upserted from an API response, `clone_url` is copied unmodified into the local database as `cloneURL`: [2](#0-1) 

`GitStore.addUpstreamRemoteIfNeeded()` then force-unwraps `parent.cloneURL` and feeds it directly to `addRemote`: [3](#0-2) 

The same pattern exists in `updateExistingUpstreamRemote()`: [4](#0-3) 

`addRemote` executes `git remote add <name> <url>` with the raw string, with no protocol/scheme check: [5](#0-4) 

Nowhere in the remote-operation environment setup is `GIT_ALLOW_PROTOCOL` or `protocol.allow`/`protocol.ext.allow` explicitly restricted before invoking git; `envForRemoteOperation`/`envForProxy` only deal with authentication and HTTP(S) proxy resolution, entirely ignoring non-`http(s)` schemes: [6](#0-5) 

Because Desktop never restricts allowed protocols, git falls back to its own defaults, under which the `ext::` transport is permitted for commands invoked directly (non-submodule) with `GIT_PROTOCOL_FROM_USER` unset (its default value of `1`), which is exactly how Desktop invokes `git remote add` / `git fetch`. This means if the `clone_url` field returned by the API/GHE endpoint contains a value such as `ext::sh -c "id > /tmp/pwned"`, Desktop will happily create an `upstream` remote pointing at that string, and the next `git fetch upstream` (automatic or user-triggered) will execute the embedded command through git's `ext::` remote helper. A `file://` URL would similarly be accepted and let the attacker force Desktop to read/expose the contents of an arbitrary local git repository path on the victim's machine as the "upstream" of the current repo.

`urlMatchesRemote`/`repositoryMatchesRemote` only compare hostnames/owner/name for de-duplication purposes; they perform no scheme allow-listing either: [7](#0-6) 

### Impact Explanation
If an attacker controls the JSON returned for a repository's `parent` object — e.g. by operating (or compromising) a GitHub Enterprise Server endpoint the victim has added an account for, or by intercepting/tampering with API traffic via a malicious proxy — they can set `clone_url` (or `parent.clone_url` for a fork) to an `ext::` payload. Once the victim's Desktop client upserts that repository/fork and calls `addUpstreamRemoteIfNeeded` (this runs automatically, e.g. during repository load/refresh flows in `app-store.ts`), the malicious URL is stored as the `upstream` git remote. Any subsequent `git fetch upstream` — including ones Desktop triggers automatically in the background — results in local arbitrary command execution via git's `ext::` helper, fully satisfying the "code execution … via remote/proxy response" impact criterion.

### Likelihood Explanation
This requires the attacker to control API/repository metadata content, which is explicitly in-scope ("a GitHub API object … or a git remote/proxy response"). It is realistic for a user who has added a GHE (GitHub Enterprise) account under attacker control, or is behind an attacker-controlled/MITM-capable proxy that can tamper with API responses. No unusual user interaction is required beyond normal use of Desktop with a fork repository (background fetches trigger the payload automatically).

### Recommendation
- Validate `clone_url`/`ssh_url` (and any other attacker-influenced remote URL fields) against an explicit allow-list of schemes (`https:`, `http:`, `ssh:`, `git:`) before persisting them as `GitHubRepository.cloneURL` in `repositories-store.ts`, and again defensively in `addRemote`/`setRemoteURL`.
- Set `GIT_ALLOW_PROTOCOL=file:ssh:git:http:https` (excluding `ext`) in the environment used for all git invocations that touch remote URLs (`envForRemoteOperation`, `spawnGit`, `core.ts`), consistent with how many other git-based tools (e.g. `git clone` wrappers) harden against `ext::`/`file://` abuse.
- Reject non-allow-listed schemes before calling `git remote add`/`git remote set-url`.

### Proof of Concept
1. Configure a GitHub Enterprise account pointing at an attacker-controlled server (or intercept API traffic with a malicious proxy).
2. Have the server return, for `GET /repos/:owner/:repo`, a full repository JSON whose `parent` object has:
   ```json
   "parent": {
     "clone_url": "ext::sh -c \"touch /tmp/pwned\"",
     ...
   }
   ```
3. Add/open this fork repository in GitHub Desktop; `_upsertGitHubRepository` stores this value verbatim as `parent.cloneURL`.
4. Trigger `addUpstreamRemoteIfNeeded` (automatically invoked on repository load per `app-store.ts`), which calls `addRemote(repository, 'upstream', 'ext::sh -c "touch /tmp/pwned"')`, successfully creating the remote with no error.
5. On the next `git fetch upstream` (manual or automatic background fetch), git's `ext::` helper executes the embedded command, creating `/tmp/pwned` — confirming arbitrary command execution.

export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
