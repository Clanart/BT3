## Analysis

I found a legitimate analog to the reported issue. The external report's failed invariant is: **time values are validated against valid ranges elsewhere in the code but the check is missing at a specific site that consumes attacker-controlled input**, causing arithmetic/state operating on out-of-range time values to behave incorrectly. The Protobuf analog is a missing range check in the ProtoJSON `Timestamp` deserializer.

### Title
Missing valid-range check in ProtoJSON `Timestamp` parsing allows out-of-range `seconds` to be silently stored - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
`ParseTimestamp` in the C++ ProtoJSON parser computes the `seconds` field from an RFC 3339 string plus an optional `[+-]hh:mm` timezone offset, but never validates the result against the documented valid range for `google.protobuf.Timestamp` (`-62135596800` to `253402300799`, i.e. `0001-01-01T00:00:00Z` to `9999-12-31T23:59:59Z`) before writing it into the message.

### Finding Description
`timestamp.proto` documents the field invariant explicitly: `seconds` "Must be between -62135596800 and 253402300799 inclusive" [1](#0-0) . The ProtoJSON *serializer* enforces this invariant strictly and errors out if violated: [2](#0-1) .

However, the corresponding *parser*, `ParseTimestamp`, computes `secs` from the year/month/day/hour/min/sec digits, applies the nanos, and then adjusts `secs` by an attacker-supplied timezone offset — but performs **no bounds check at all** before storing the value: [3](#0-2) .

By contrast, the sibling `ParseDuration` function in the very same file *does* perform an explicit range check (`secs > kMaxSeconds || secs < -kMaxSeconds`) immediately after parsing [4](#0-3) , showing that the omission in `ParseTimestamp` is an inconsistency rather than an intentional design choice.

The year component is constrained to 4 digits via `TakeTimeDigitsWithSuffixAndAdvance(data, 4, "-")` [5](#0-4) , which alone would keep `secs` within `[-62135596800, 253402300799]` for a `Z`-suffixed timestamp. But the `+hh:mm`/`-hh:mm` timezone-offset branch can shift `secs` by up to `86340` seconds (23:59) in either direction without any subsequent re-validation [6](#0-5) , allowing the boundary to be crossed.

The upb-based JSON decoder used by Python/PHP/Ruby (`jsondec_timestamp`) has a related but narrower gap: it only checks the *lower* bound (`seconds.int64_val < -62135596800`) and omits the *upper*-bound check entirely on the parse path [7](#0-6) , identical code is duplicated in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`.

### Impact Explanation
An attacker who controls a ProtoJSON payload parsed via the public `ParseTimestamp`/`JsonStringToMessage` API can produce a `Timestamp` message whose `seconds` field silently violates the documented valid range, without any parse error. This breaks the implicit contract that a successfully-parsed `Timestamp` is always valid per `timestamp.proto`. Downstream consumers that rely on this invariant (e.g. `TimeUtil::TimestampToNanoseconds`/`TimestampToMicroseconds`, which only assert validity via `ABSL_DCHECK` — a no-op in release/NDEBUG builds) will silently compute incorrect values [8](#0-7) . Re-serializing the same message back to ProtoJSON via `WriteTimestamp`/`unparser.cc` will then unexpectedly fail with `InvalidArgumentError`, producing an asymmetric parse-succeeds/serialize-fails condition — a genuine integrity break in an application's round-trip and time-comparison logic, analogous to the underflow/overflow behavior described in the external report (values silently computed outside their valid domain due to a missing check at the boundary of attacker control).

### Likelihood Explanation
High likelihood of occurrence in any consuming application that accepts ProtoJSON-encoded `Timestamp` values from untrusted clients (a common and explicitly supported use case for well-known types). The trigger requires only a single crafted string in a JSON body; no privileged access or unusual configuration is needed.

### Recommendation
Add an explicit range check on `secs` in `ParseTimestamp` (mirroring the check already present in `ParseDuration` and in `unparser.cc`/`upb`'s `jsonenc_timestamp`) after the timezone offset has been applied, rejecting values outside `[-62135596800, 253402300799]` with an "out of range" parse error. Apply the equivalent upper-bound check to `jsondec_timestamp` in `upb/json/decode.c` and the duplicated PHP/Ruby copies.

### Proof of Concept
JSON input parsed as a `google.protobuf.Timestamp` (or embedded as a message field of that type) via the ProtoJSON parser:

```json
"0001-01-01T00:00:00+23:59"
```

Trace through `ParseTimestamp`:
1. `year=1, mon=1, day=1, hour=0, min=0, sec=0` → computed `secs = -62135596800` (exactly the documented minimum, corresponding to `0001-01-01T00:00:00Z`).
2. `nanos = 0`.
3. Timezone branch: `data[0] == '+'`, `hour=23, mins=59` → `offset = (23*60+59)*60 = 86340`; `secs += -offset` → `secs = -62135683140`.
4. No bounds check exists before `Traits::SetInt64(..., secs)` [9](#0-8) ; the function returns `absl::OkStatus()`, and the message's `seconds` field is set to `-62135683140`, which is below the documented minimum `-62135596800`.

Confirmed by contrast: passing the resulting message to `WriteTimestamp` (`unparser.cc`) would hit the exact same threshold check and return `absl::InvalidArgumentError("minimum acceptable time value is 0001-01-01T00:00:00Z")` [10](#0-9) , proving the parse path accepted a value the serialize path explicitly forbids — the asymmetry that demonstrates the missing check.

      case '+': {

        data = data.substr(1);

          return str->loc.Invalid("timestamp offset has bad hours and minutes");
        }

        int64_t offset = (*hour * 60 + *mins) * 60;
        secs += (neg ? offset : -offset);
        break;

      // Lowercase z is not accepted, per the spec.

int64_t TimeUtil::TimestampToNanoseconds(const Timestamp& timestamp) {
  ABSL_DCHECK(IsTimestampValid(timestamp))
      << "Timestamp is outside of the valid range";
  return timestamp.seconds() * kNanosPerSecond + timestamp.nanos();
}

int64_t TimeUtil::TimestampToMicroseconds(const Timestamp& timestamp) {
  ABSL_DCHECK(IsTimestampValid(timestamp))
      << "Timestamp is outside of the valid range";
  return timestamp.seconds() * kMicrosPerSecond +
         RoundTowardZero(timestamp.nanos(), kNanosPerMicrosecond);
}
