### Title
Deposits below the share-price rounding threshold mint zero `zft` shares while the underlying is still pulled and credited to `assets`, silently diluting/losing the depositor's principal - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent `v0-vault-*` vaults)

### Summary
`deposit` computes shares to mint via `convert-to-shares-preview`, which performs a floor division (`mul-div-down`). For any deposit whose `amount * total-supply / total-assets` term truncates to zero, the function returns `inkind = u0`. Unlike `redeem`, which explicitly guards against a zero output with `ERR-OUTPUT-ZERO`, `deposit` has no equivalent check on `inkind`, only `(asserts! (> amount u0) ERR-AMOUNT-ZERO)`. This exactly mirrors the reported analog class: a small deposit whose accounting term is divided by a larger base value truncates to zero, so the deposit is not reflected in the user's position, even though the deposit itself succeeds.

### Finding Description
The share-minting path is: [1](#0-0) 

```clarity
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
``` [1](#0-0) 

`mul-div-down` is a plain integer division that always rounds toward zero: [2](#0-1) 

Once the vault has accrued interest (`ta > ts`, i.e. share price > 1), any deposit amount small enough that `amount * ts < ta` produces `inkind = u0`. `deposit` then proceeds: [3](#0-2) 

- `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` only checks the raw underlying amount, not the derived share amount.
- `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially when `min-out` is `u0` (the default/naive caller value), since `0 >= 0`.
- `(try! (receive-underlying amount account))` pulls the underlying tokens from the depositor.
- `(try! (ft-mint? zft inkind recipient))` mints `u0` shares — the depositor receives nothing representing their deposit.
- `(var-set assets (+ current-assets amount))` still increases `assets`, meaning the deposited principal is folded into the pool and backs the *existing* shareholders' `total-assets`, increasing the redeemable value per share for everyone else.

This is the same root cause as the reported `VotingEscrow._checkpoint` bug: an accounting increment (`bias`/`shares`) is divided by a value large enough that a legitimately small increment (`dweight`/`amount`) rounds to zero, so the depositor's contribution is not reflected in their own accounted balance, while the underlying value is still absorbed into the system.

By contrast, `redeem` in the same contract explicitly guards this exact class of rounding-to-zero bug with `ERR-OUTPUT-ZERO`: [4](#0-3) 

showing the protocol authors are aware of the rounding-to-zero risk on one side of the ERC4626-style conversion but omitted the equivalent check on the deposit side.

### Impact Explanation
Value flows from the depositor to the rest of the vault's shareholders: the depositor's underlying tokens increase `assets` (and thus `total-assets`), but they receive zero shares, so they cannot ever redeem the deposited amount. This is worse in kind than the original report (which caused only temporary accounting freeze with no fund loss) — here it's a real, permanent loss of the depositor's principal for that specific transaction, which then accrues to all other zft holders proportionally. Under the reported bug's classification rules, the closest matching in-scope impact bucket is **"Permanent freezing of funds"** for the affected user's deposited amount (the tokens are absorbed by the vault and can never be recovered by that depositor since no share receipt was minted for them).

### Likelihood Explanation
Triggering requires: (1) the vault has already accrued interest so that `total-assets-preview > total-supply-preview` (i.e., share price > 1, `ta`/`ts` ratio not exactly 1), which happens naturally after any lending activity in the vault, and (2) a deposit `amount` small enough that `amount * ts` floor-divides to 0 against `ta`. Because vault decimals for USDC/USDH-style assets are 6 and STX/sBTC assets have higher unit prices, small enough raw-unit deposits (a handful of base units, e.g. micro-USDC or single satoshi-equivalents) are plausible, especially via bots, scripts, or contract-mediated deposits that don't manually validate output shares. The `min-out` slippage parameter does not protect against this because a caller who (reasonably) expects `inkind ≈ amount` at share price ~1 and passes `min-out = 0` or a low value will not be blocked by the `ERR-SLIPPAGE` check.

### Recommendation
Add an explicit zero-shares check in `deposit` (mirroring `redeem`'s `ERR-OUTPUT-ZERO` guard), e.g.:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `ERR-AMOUNT-ZERO`/`ERR-SLIPPAGE` checks in `deposit`, across all vaults (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) that share this `convert-to-shares-preview`/`deposit` pattern.

### Proof of Concept
1. Deploy/initialize a vault (e.g. `v0-vault-usdc.clar`) and let it accrue interest so that `total-assets-preview() > total-supply-preview()` (share price slightly above 1), e.g. `ta = 1_000_000_100`, `ts = 1_000_000_000`.
2. Call `deposit(amount=1, min-out=0, recipient=attacker_or_victim)`.
3. Inside `convert-to-shares-preview`, `mul-div-down(1, ts, ta) = floor(1_000_000_000 / 1_000_000_100) = 0`, so `inkind = u0`.
4. `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` passes (`amount = 1`). `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes (`0 >= 0`).
5. `receive-underlying` pulls `1` unit of the underlying from the caller; `ft-mint? zft 0 recipient` mints zero shares; `assets` is incremented by `1`.
6. The depositor now holds `0` additional `zft` and has irreversibly transferred `1` unit of underlying into the vault's `assets`, which is fully captured by existing shareholders on their next redemption. [3](#0-2)
