## Title
Tron `IntentGatewayV2.placeOrder` swaps the full remaining `msg.value` for solver fees and never refunds the unspent excess to the user - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The core EVM `IntentGatewayV2.placeOrder` correctly captures the actual ETH spent by `swapETHForExactTokens` (`msgValue -= amounts[0]`) and refunds any leftover native token to `msg.sender` at the end of the function. The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, drops both of these steps: it forwards the *entire remaining* `msgValue` into `swapETHForExactTokens` and never captures the returned `amounts[0]`, and the function has no final "refund unspent native token" block at all. This is the same broken invariant as the C4 finding: a swap/conversion consumes less than the amount the user was charged, and the difference is never returned to the payer.

## Finding Description
In the reference EVM implementation, `placeOrder` handles native-token fee payment like this: [1](#0-0) 

Note `msgValue -= amounts[0]` captures the true ETH cost of the swap, and the trailing block refunds any leftover `msgValue` to `msg.sender`.

The Tron variant of the identical function performs the same swap but omits both safeguards: [2](#0-1) 

Immediately after this block, the Tron `placeOrder` function ends with `emit OrderPlaced(...)` and `return` — there is no code anywhere in the function that decrements `msgValue` by the swap's actual cost or forwards any leftover native balance back to the caller: [3](#0-2) 

`swapETHForExactTokens(order.fees, path, address(this), block.timestamp)` only needs `amounts[0] <= msgValue` worth of ETH; UniswapV2Router02 refunds any unused ETH to its immediate caller, which is the `IntentGatewayV2` Tron contract itself (since the contract invoked the router with `{value: msgValue}`), not to the original user who called `placeOrder`. Because the contract never tracks or forwards that refunded ETH, it is stranded in the contract's balance, untracked by `_orders[commitment][...]` and unassociated with any specific user or order.

This mirrors the reported `swap_2_internal_erc20` bug exactly: the contract takes a fixed input amount from the user (`msg.value`), performs an internal swap that may consume far less than what was charged (per the SDK's own comment that `nativeValue` intentionally carries slippage buffer and "the gateway swaps it for the fee token and refunds any unused amount" — see `sdk/packages/sdk/src/types/index.ts`), and fails to return the difference.

## Impact Explanation
Any user placing an order on the Tron deployment and paying `order.fees` in native token (as recommended/quoted by the SDK's `quoteOrderFees()`, which deliberately overestimates `nativeValue` with a margin) permanently loses the unspent portion of their `msg.value`. This is a direct, unauthorized loss of user funds triggered purely through the normal, permissionless `placeOrder` entrypoint — no malicious relayer, prover, or admin is required. The stranded ETH is not credited to the user's escrow, cannot be reclaimed via `cancelOrder`, and is not covered by the existing `DustCollected`/`SweepDust` accounting (that path only covers ERC-20/native amounts explicitly computed as `dust` in the input-escrow logic, not leftover fee-swap change). Every overpaying `placeOrder` call bleeds real value out of the user and into the contract's unaccounted balance.

## Likelihood Explanation
High likelihood: this triggers on the ordinary path any time a user pays the solver fee with native token and the actual AMM cost is lower than the value sent — which the SDK itself documents as the expected case (2% buffer for same/cross-chain fee quotes, refund of unused amount assumed by the SDK docs). Every such placement on Tron loses funds; no adversarial conditions or privileged actors are needed, satisfying the bounty's "stealing or loss of funds" criterion via an ordinary unprivileged user interaction.

## Recommendation
Mirror the main EVM contract's logic in the Tron port:
1. Capture `swapETHForExactTokens`'s return value: `uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp);` and do `msgValue -= amounts[0];`.
2. Add the same trailing refund block found in `evm/src/apps/IntentGatewayV2.sol` lines 364-368 (`if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); if (!sent) revert InsufficientNativeToken(); }`) before `emit OrderPlaced`.

## Proof of Concept
1. On the Tron deployment, quote `order.fees` via the SDK's `quoteOrderFees()`, which returns a `nativeValue` with a margin above the actual expected AMM cost (per SDK doc comments in `sdk/packages/sdk/src/types/index.ts`).
2. Call `placeOrder{value: nativeValue}(order, graffiti)` with `order.fees > 0` and no native-token inputs consuming all of `msgValue`.
3. Inside `placeOrder`, `swapETHForExactTokens{value: msgValue}(order.fees, ...)` executes; the router only pulls `amounts[0] < msgValue` and refunds `msgValue - amounts[0]` ETH to the Tron `IntentGatewayV2` contract (its direct caller).
4. `placeOrder` returns without ever decrementing `msgValue` or sending any ETH back to the user.
5. Compare the user's ETH balance delta (`nativeValue` spent) against `amounts[0]` (actual fee-swap cost): the difference is now sitting in the `IntentGatewayV2` contract's balance, uncredited to the user's order and unrecoverable through any user-facing function.
