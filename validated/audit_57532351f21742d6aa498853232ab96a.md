Based on my investigation, the strongest analog to the ether-fi validation-bypass bug class is in the PR-fork checkout path, where a remote name/branch derived from attacker-supplied PR/API data is used to build git command arguments (`checkout -b <name>`, `remote add <name> <url>`) with a validity check that only rejects a narrow character set and does not defend against argument-injection via a leading `-`.

### Title
Argument Injection via Unsanitized Branch/Ref Values in PR Fork Checkout Flow - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_findPullRequestBranch` and `_checkoutBranch`/`checkoutBranch` build `git` argument arrays using values that originate from a GitHub API pull-request object (`headRepoOwner`, `headCloneUrl`, `headRefName`) or a deep-link/CLI branch argument, with only `testForInvalidChars` (a ref-format-illegal-character filter) applied to some paths and no filter at all guaranteeing the resulting string can't be interpreted as a flag by `git`.

### Finding Description
`openPullRequestFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` (around lines 1998-2048) passes `pullRequest.head.repo.owner.login`, `pullRequest.head.repo.clone_url`, and `pullRequest.head.ref` — all values taken from the GitHub API PR payload — directly into `appStore._checkoutPullRequest`, which forwards them to `_findPullRequestBranch` [1](#0-0) . Inside `_findPullRequestBranch`, `headRepoOwner` is used to build a remote name via `forkPullRequestRemoteName`, and the resulting branch name `pr/${prNumber}` is passed to `_createBranch`, while `remoteRef` (`${remote.name}/${headRefName}`) is used as the start-point [2](#0-1) . Similarly, the deep-link handler `openBranchNameFromUrl` only validates the branch with `testForInvalidChars` (which filters control characters and a fixed punctuation set, but not a leading `-`) before calling `checkoutLocalBranch` [3](#0-2) [4](#0-3) .

The underlying `checkoutBranch` git function builds its argument array as `[..., branch.name, '-b', branch.nameWithoutRemote, '--']`, using `--` as a separator only for the final positional argument, not for intermediate flags like `-b` [5](#0-4) . This differs from other flows like `clone.ts`, which places `--` immediately before the url/path pair to fully neutralize argument injection [6](#0-5) .

### Impact Explanation
If a value derived from an attacker-controlled deep link, PR fork owner login, or ref name can be crafted to start with `-`, it could be interpreted by `git` as a command-line flag rather than a literal branch/ref value, potentially altering checkout behavior or corrupting the resulting working tree/branch state — matching the "silent corruption of what the user commits or pushes" impact category. This requires the user to click a crafted deep link or interact with a PR whose head repo/branch metadata is attacker-supplied (e.g., via a malicious fork), both of which are unprivileged, remote-triggerable conditions consistent with the required attacker model.

### Likelihood Explanation
This is **uncertain and not fully confirmed** with the available tooling. I could not verify, within this session, whether `git-check-ref-format` rejects all leading-dash ref names before `dugite`/`git` ever receives them, nor could I confirm exactly how `owner.login` (a GitHub username, which per GitHub's own username rules cannot start with a hyphen) and `headRefName` are validated upstream by the GitHub API itself, which would neutralize this path in practice for the PR-checkout case. The deep-link `branch` parameter passed through `testForInvalidChars` is the more plausible unsanitized entry point, but I was unable to trace all downstream argument-building code (e.g., `_createBranch`, `checkoutLocalBranch`) within the available iterations to confirm exploitability end-to-end.

### Recommendation
Add an explicit reject/strip rule for ref/branch/remote-name values that begin with `-` (in addition to the existing `invalidCharacterRegex` in `sanitize-ref-name.ts`), and ensure all git argument arrays that include user- or API-derived branch/remote names place a `--` separator immediately before those values (as already done in `clone.ts`), not just before the final positional path argument.

### Proof of Concept
I was not able to construct and verify a concrete end-to-end PoC within this session (e.g., crafting a PR fork whose `owner.login` or `head.ref` begins with `-` and confirming GitHub's API/username constraints don't already block it, or triggering `checkoutLocalBranch` via a deep link with a hyphen-prefixed branch name and observing the resulting `git` invocation). This would need to be validated by starting a Devin session with full read/write and terminal access to trace `_createBranch`/`checkoutLocalBranch` argument construction and to test actual `git` argument parsing behavior, since the ask-only investigation here was limited to static code review of a partially-indexed codebase.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
