### Title
Push-sweep permanently silences attacker-crafted commits by forcing an empty reviewable-diff via a committed `.gitattributes` binary/no-diff marker - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`handle_push_sweep_posttooluse` treats an empty `diff_files` list (returned by `parse_diff_into_files`) as "nothing to review" and unconditionally calls `_append_reviewed_shas(repo_root, tail, vulns_found=0)`, permanently marking the pushed commit range as reviewed. An attacker who can commit ordinary repo content (no elevated privilege needed) can commit a `.gitattributes` entry that forces git to treat a modified source file as binary (e.g. `path -diff`), which makes `git diff -p` emit a "Binary files ... differ" line instead of `@@` hunks for that file. `parse_diff_into_files` only keeps files that contain an `@@` hunk marker, so the file — and its real, malicious content changes — is silently dropped from `diff_files`, and if it is the only changed file in the pushed range, `diff_files` ends up empty even though the diff (`_git_diff_range`) succeeded and returned non-empty, real content.

### Finding Description
`_git_diff_range` (plugins/security-guidance/hooks/gitutil.py:193-210) succeeds (`rc==0`) and returns the real diff text, which for a `-diff`-attributed file contains only `diff --git a/x b/x` / `Binary files a/x and b/x differ` — no `@@` hunk. `parse_diff_into_files` (plugins/security-guidance/hooks/gitutil.py:615-654) only appends a file to its result when `in_hunks` becomes true via a `@@` line; a binary-marked entry with no hunks is silently skipped. In `handle_push_sweep_posttooluse` (plugins/security-guidance/hooks/security_reminder_hook.py:1549-1568), the code distinguishes "diff failed" (`diff_text is None`, tail NOT marked reviewed) from "diff succeeded but nothing to review" (`diff_files` empty, tail IS marked reviewed via `_append_reviewed_shas`). Because the empty-`diff_files` case is reached via `parse_diff_into_files` stripping attacker-controlled binary-flagged content rather than a true no-op diff, the invariant "empty diff ⇒ genuinely nothing to review" is violated: the diff was non-trivial, but the reviewer never saw it, and the range is marked reviewed anyway.

Note the asymmetry with per-commit review: `handle_commit_review_posttooluse` (security_reminder_hook.py:1178-1181) exits on empty `diff_files` at `skip_reason=30` *before* reaching its own `_append_reviewed_shas` call (which happens later, at lines ~1254-1263, only after a review actually ran). So a commit whose only change is to a `.gitattributes`-binary-marked file is correctly left unreviewed and un-recorded by commit-review. But push-sweep's separate empty-`diff_files` branch does record it as reviewed, so the very first push of that commit permanently silences it via `.git/sg-reviewed-shas`, and no future commit-review or push-sweep will ever re-examine that SHA.

### Impact Explanation
An attacker with ordinary commit access to a repository can smuggle malicious code changes into a file whose diff is suppressed by a `-diff` gitattribute, causing push-sweep to falsely record the pushed range as security-reviewed with zero actual LLM/agentic review. This is a trust-boundary bypass of the plugin's own "review must not be silenced by content that merely renders empty" guarantee (explicitly documented in `_git_diff_range`'s docstring), resulting in permanently unreviewed, attacker-controlled code changes being treated as reviewed. Impact is scoped to defeating the security-guidance review pipeline for the affected commits/files.

### Likelihood Explanation
Feasible and repeatable by any unprivileged contributor: committing a `.gitattributes` line (e.g. `secrets.py -diff`) is ordinary repository content, requires no admin/maintainer privilege, no leaked keys, and no external diff driver (so it is unaffected by `--no-ext-diff`). Any subsequent push where the *only* reviewable change is to that attributed file (or where all reviewable changes are similarly suppressed) will trigger the empty-`diff_files` → `_append_reviewed_shas` path deterministically.

### Recommendation
In `handle_push_sweep_posttooluse`, do not treat an empty `diff_files` result as "nothing to review" equivalent to a truly empty diff. Distinguish "diff_text is empty/whitespace" (genuine no-op) from "diff_text is non-empty but parse_diff_into_files dropped all entries" (e.g., binary-marked or hunk-less entries) — in the latter case, do not call `_append_reviewed_shas` for the tail (mirroring commit-review's behavior), or at minimum flag/log such suppressed files so they are not silently marked reviewed.

### Proof of Concept
Integration test:
1. Init a repo; commit a `.gitattributes` containing `payload.py -diff`.
2. Commit `payload.py` with an obviously malicious pattern (e.g. `os.system(user_input)`).
3. Simulate the push-sweep flow: call `_git_diff_range(repo_root, base, "HEAD")` and assert it returns non-empty text containing `Binary files ... differ` (rc==0, non-null).
4. Call `parse_diff_into_files(diff_text)` and assert it returns `[]` (the malicious change is dropped).
5. Drive `handle_push_sweep_posttooluse` (or directly the branch at security_reminder_hook.py:1562-1568) with this state and assert that `_append_reviewed_shas` is called for `tail` / the commit SHA is added to `.git/sg-reviewed-shas` even though `payload.py`'s malicious content was never sent to `analyze_code_security` or the agentic reviewer — demonstrating the range is marked reviewed without any real review occurring.
