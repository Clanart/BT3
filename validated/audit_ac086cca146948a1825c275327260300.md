### Title
Unprivileged bandwidth-purchase spam evicts a victim app's paid-for subscriptions before consumption - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary

### Finding Description
`BandwidthManager.purchase()` is a fully public entrypoint: any caller can pay for a tier and specify **arbitrary** `app` and `chain` bytes — this is by design ("sponsorship": a payer on one chain can top up any app on any chain). [1](#0-0) 

On the pallet side, `on_accept` takes the attacker-supplied `msg.chain`/`msg.app` from the purchase body (not tied to `request.source`) and calls `push_subscription` to append into the `(app_chain, app)` FIFO list: [2](#0-1) 

`push_subscription` caps the list at `MAX_SUBSCRIPTIONS = 1024` and, once full, unconditionally evicts index `0` (the oldest entry) to make room for the new purchase — regardless of how much unconsumed value (`remaining_bytes`) that oldest entry holds relative to the newly-purchased (possibly much cheaper) entry: [3](#0-2) 

This exactly mirrors the H-19 bug class: a balance/allowance a user already paid for is destroyed by an unrelated state-changing action (there, `withdrawETH` zeroing LP balance before paying accrued rewards; here, an unrelated party's cheap purchase zeroing/evicting a victim's expensive, unconsumed, already-paid-for subscription) — with no settlement, refund, or consent from the party who owns the evicted value.

### Impact Explanation
An unprivileged attacker who knows a victim app's `(chain, app)` pair can:
1. Repeatedly call `purchase()` with the cheapest configured tier (`TierOne`, e.g. $50/100KB) targeting the victim's `(app_chain, app)`.
2. Once the victim's FIFO list reaches 1024 entries, each further attacker purchase evicts the victim's oldest live subscription — which could be a large, recently-purchased, high-value tier (e.g., the $1000/8MB tier) that hasn't yet started draining.
3. The evicted subscription's `remaining_bytes` (`lost_bytes` in `SubscriptionEvicted`) are permanently gone; the victim paid real fee-token value for bandwidth it will never get to use, matching "loss of funds" per the impact gate. No relayer, prover, or admin compromise is required — `purchase()` and the eviction path are both reachable by any address with fee tokens.

### Likelihood Explanation
Feasibility depends on cost: to guarantee eviction the attacker must drive the FIFO to the 1024 cap and then push extra purchases, so total cost scales with `(1024 - current_count) × cheapest_tier_price` plus one purchase per additional eviction. This is not free, but is a bounded, entirely permissionless cost paid once to grief potentially far larger repeated victim purchases (each eviction destroys a purchase that may be worth many multiples of the attacker's cheapest-tier cost), and the attack is repeatable indefinitely against any known `(chain, app)` target with no rate limiting, allowlist requirement, or minimum-value protection on which entries can be evicted.

### Recommendation
- Do not evict indiscriminately by pure insertion order. At minimum, before evicting, either refuse the purchase (return an error / require the caller to wait) if the oldest entry still has significant unconsumed `remaining_bytes`, or refund/credit the evicted value back to the entry's original payer (which requires tracking a per-subscription payer/beneficiary, not currently stored).
- Consider bounding the FIFO growth per source/payer (e.g., a per-manager or per-payer purchase-rate cap) so a third party cannot cheaply flood a specific `(chain, app)` bucket that it doesn't own.
- Alternatively, size `MAX_SUBSCRIPTIONS` and eviction policy so that eviction only ever targets already-expired entries, converting `push_subscription`'s eviction into a hard purchase-rejection (`Err`) when no expired entry exists to reclaim, rather than silently destroying unexpired value.

### Proof of Concept
1. Governance configures `TierOne` cheaply (e.g., $50/100KB) and `TierFour` expensively (e.g., $1000/8MB), and registers a `BandwidthManager` for `EVM-1`.
2. Victim (app `V` on `EVM-8453`) purchases `TierFour` bandwidth via `purchase(app=V, tier=4, months=1, chain="EVM-8453")` — pallet appends a large `Subscription{remaining_bytes: 8_000_000, ...}` to `Allowance[EVM-8453][V]`. [2](#0-1) 
3. Before `V` drains any of it, an unrelated attacker calls `purchase(app=V, tier=1, months=1, chain="EVM-8453")` 1024 times (any tier, cheapest available), which the pallet accepts identically since `on_accept` places no restriction tying `msg.app`/`msg.chain` to the purchase's origin caller. [1](#0-0) 
4. Once `Allowance[EVM-8453][V].len() == 1024`, each subsequent attacker purchase triggers `list.remove(0)` in `push_subscription`, evicting the oldest entry — eventually reaching and destroying V's `TierFour` subscription, emitting `SubscriptionEvicted { lost_bytes: 8_000_000, ... }` with no compensation to `V`. [4](#0-3) 

**Note on verification limits:** I was not able to confirm within this session whether any off-chain/relayer-side rate limiting or governance monitoring mitigates this in practice (e.g., alerting on abnormal purchase volume), since that logic — if it exists — likely lives outside the indexed portions of this repository. The on-chain code path itself contains no such protection.

        external
        returns (bytes32 commitment)

        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
