### Title
Untrusted `ThresholdKeys` deserialization permits zero interpolation coefficients that collapse the threshold group key to identity - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts attacker-controlled `Interpolation::Constant` coefficients without requiring them to be nonzero or to encode a nonzero public group key. With `t == n`, an all-zero coefficient vector makes every signing-set interpolation factor zero, causing both the derived group key and every verification share to collapse to the identity. A forged serialized key containing a zero secret share then produces valid Schnorr signatures for the identity key, reducing the signing relation from knowledge of a secret to a known scalar of zero.

### Finding Description
`ThresholdKeys::new` only checks that a `Constant` interpolation is used when `t == n`; it does not validate the coefficient vector's semantic validity, reject all-zero coefficients, or reject an identity group key [1](#0-0) . `ThresholdKeys::read` fully trusts that constructor after decoding `n` caller-supplied coefficients, the secret share, and `n` verification shares [2](#0-1) .

For a minimal `1-of-1` key encoded as `Interpolation::Constant([0])`, `interpolation_factor` returns zero [3](#0-2) . Consequently, the derived group key is `verification_shares[1] * 0`, which is the identity regardless of the supplied public verification share [4](#0-3) . `ThresholdKeys::view` similarly multiplies both the private secret share and the public verification share by the zero coefficient [5](#0-4) .

During FROST signing, Schnorr's share is calculated as `nonce + challenge * secret_share`, so a zero effective secret produces a share independent of any secret material [6](#0-5) . The completed aggregate is then checked with `sG == R + cA`; when `A` is identity, choosing `s` equal to the nonce satisfies the equation [7](#0-6) .

### Impact Explanation
An unprivileged party who can supply `ThresholdKeys::read` bytes can construct a syntactically valid key container whose public verification key is identity and whose effective private share is zero. Any consumer that uses the deserialized group's public key as an authorization or ownership predicate can then accept attacker-produced Schnorr signatures without the attacker knowing a nonzero group secret. This is a concrete signature forgery caused by a semantically invalid key state surviving deserialization.

The analog to the reference issue is state reduction: a security-critical tuple that should contain an unknown secret becomes known, because the interpolation weights force the group secret/public-key relation to zero rather than merely weakening a random variable.

### Likelihood Explanation
The malicious input is entirely public and self-contained. The attacker only needs to encode `t == n`, select interpolation type `0`, provide all-zero field encodings, provide a zero secret share, and provide `n` otherwise valid point encodings. `ThresholdKeys::read` supplies no additional consistency check proving that the secret share matches its verification share or that the resulting group key is nonzero [8](#0-7) .

Exploitation requires a caller to deserialize and trust attacker-supplied `ThresholdKeys`, or to derive a public verifier from such bytes. Within that reachable API path, the malformed object is deterministic and does not require racing, collusion, timing, malformed curve encodings, or access to an honest participant's private share.

### Recommendation
Reject semantically invalid `Interpolation::Constant` vectors in `ThresholdKeys::new`:

- Require `coefficients.len() == n`.
- Require at least one nonzero coefficient, and preferably reject any zero coefficient unless the scheme explicitly defines zero-weight shares.
- Verify `secret_share * C::generator() == verification_shares[params.i()]`.
- Reject `group_key.is_identity()` before constructing `ThresholdKeys`.
- Consider rejecting identity verification shares at this layer as well, even if the generic ciphersuite reader permits them.
- Add regression tests for all-zero coefficients, all-zero verification shares, a mismatched secret share, and an identity derived group key.

### Proof of Concept
For a one-party `1-of-1` object, construct serialized input with:

```text
id_len      = len(C::ID), little-endian u32
curve_id    = C::ID
t           = 1, little-endian u16
n           = 1, little-endian u16
i           = 1, little-endian u16
interp_tag  = 0
coeff[0]    = canonical encoding of scalar 0
secret      = canonical encoding of scalar 0
vshare[0]   = canonical encoding of any valid non-identity point
```

`ThresholdKeys::<C>::read` decodes those exact fields and calls `ThresholdKeys::new` [9](#0-8) . Construction succeeds because `t == n`, while `group_key` is calculated as `vshare[0] * 0`, yielding identity [10](#0-9) .

Equivalently, the direct construction demonstrates the same accepted state:

```rust
let keys = ThresholdKeys::<C>::new(
  ThresholdParams::new(1, 1, Participant::new(1).unwrap()).unwrap(),
  Interpolation::Constant(vec![C::F::ZERO]),
  Zeroizing::new(C::F::ZERO),
  HashMap::from([(Participant::new(1).unwrap(), C::generator())]),
).unwrap();

assert_eq!(keys.group_key(), C::G::identity());
assert_eq!(*keys.view(vec![Participant::new(1).unwrap()]).unwrap().secret_share(),
           C::F::ZERO);
```

A FROST signing machine for these keys produces a share `s = r`, because the challenge-dependent term is `challenge * 0`; the completed signature `(R = rG, s = r)` satisfies the verifier for public key `A = 0` [11](#0-10) .
