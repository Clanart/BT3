### Title
Unauthenticated disclosure of encrypted emergency-stop transactions via `internal_get_emergency_stop_tx` when `client_verification=false` - ([File: core/src/rpc/interceptors.rs], [File: core/src/servers.rs])

### Summary
The `Internal`-prefixed gRPC method naming convention is enforced only inside the `OnlyAggregatorAndSelf` interceptor branch via `is_internal()`; when `client_verification` is disabled, `create_grpc_server` installs `Interceptors::Noop`, which performs no authentication or method-name check at all. Any unauthenticated caller reaching the aggregator's gRPC port can therefore call `internal_get_emergency_stop_tx` directly and retrieve the encrypted emergency-stop transaction for any move-to-vault txid it has observed on-chain.

### Finding Description
The claimed binding is: `caller_authority(request to "Internal*" method) == self (our_cert)`. This binding is enforced by `only_aggregator_and_self` in `core/src/rpc/interceptors.rs`, where `is_internal(&req)` gates access to internal methods and requires `leaf_cert == our_cert`: [1](#0-0) 

However, this check exists only inside the `OnlyAggregatorAndSelf` variant of the `Interceptor::call` match arm. The `Noop` variant simply passes the request through unmodified with no certificate or method-name inspection whatsoever: [2](#0-1) 

`create_grpc_server` in `core/src/servers.rs` selects between these two interceptors based solely on `config.client_verification`: if `client_verification` is `false`, it wires up `Noop` for the service (including the aggregator service), with no fallback restriction on "Internal"-named RPCs: [3](#0-2) 

The naming convention `Internal*` and the `is_internal()` check in `only_aggregator_and_self` are the *only* enforcement mechanism for self-only methods; there is no separate, interceptor-independent guard inside the RPC handler implementation (`internal_get_emergency_stop_tx` in `core/src/rpc/aggregator.rs`) that re-validates caller identity. Thus when `Noop` is active, any unauthenticated caller with the target `move_to_vault_txid` (observable on-chain after a deposit's move-to-vault transaction confirms) can call this RPC and receive `encrypted_emergency_stop_txs`, which were persisted via `verify_and_save_emergency_stop_sigs` -> `insert_signed_emergency_stop_tx_if_not_exists` during `new_deposit`: [4](#0-3) 

None of the guards enumerated in policy (`is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`, `lc_proof_verifier`, presigned tx graph, DB uniqueness) apply here — this is purely a transport/interceptor authorization gap, and existing DB constraints don't restrict *read* access to the encrypted blob.

### Impact Explanation
The exposed artifact is an encryption of the fully-signed emergency-stop transaction (protected by `emergency_stop_encryption_public_key`), which the protocol design keeps confidential until an operator/security-council-driven reveal event. Premature disclosure of this ciphertext (and by extension confirmation that a valid N-of-N signed emergency-stop tx exists for a given deposit) is exactly the "premature disclosure of a protocol commitment" category classified as High impact. It does not directly move funds, credit a false reimbursement, or burn collateral (Critical-tier outcomes), so the correct severity is High, matching the policy's explicit High bucket. The leak is repeatable across every completed deposit whose move-to-vault txid the attacker can observe on public Bitcoin blocks, and requires only one gRPC call per txid — no rate limiting or per-caller restriction exists for this specific data class beyond the (bypassed) interceptor.

### Likelihood Explanation
This requires the deployment to run the aggregator with `client_verification=false` (a supported, non-default-forced configuration path exercised directly in `create_grpc_server`), and requires at least one completed deposit where `verify_and_save_emergency_stop_sigs` has already persisted the encrypted emergency-stop tx. Given those preconditions, exploitation costs nothing beyond a single unauthenticated gRPC call with a publicly observable txid — no BTC spend, no fee payment, and no privileged credential. This is a configuration-dependent but architecturally real gap: the code path enforcing "Internal implies self-only" exists solely inside `OnlyAggregatorAndSelf` and is entirely absent from `Noop`, so any deployment intentionally or accidentally disabling client TLS verification loses all internal-method protection, not just for this RPC.

### Recommendation
Do not rely solely on the interceptor for internal-method gating. Enforce the "Internal" access restriction independently of `client_verification`/`Noop`, e.g., by always applying a lightweight self-only check (even without full mTLS, e.g., via a shared local secret, unix-socket-only exposure, or an unconditional interceptor layer that checks `is_internal` regardless of the `Noop`/`OnlyAggregatorAndSelf` selection). Alternatively, refuse to start the gRPC server with `Noop` if any service exposes `Internal`-prefixed methods, or split internal-only RPCs onto a separate listener bound only to a local/unix socket that is never exposed with `Noop`.

### Proof of Concept
```rust
// cargo test in core/, using existing test harness patterns from core/src/test/common.rs
// (test-only code referenced for setup, not for the vulnerability itself)

#[tokio::test]
async fn poc_unauthenticated_internal_get_emergency_stop_tx_with_noop_interceptor() {
    // 1. Build a BridgeConfig with config.client_verification = false.
    // 2. Start create_aggregator_grpc_server(config) -> confirms Interceptors::Noop is installed
    //    per core/src/servers.rs create_grpc_server logic (client_verification == false branch).
    // 3. Run a full deposit flow (new_deposit) to completion so that
    //    verify_and_save_emergency_stop_sigs persists an encrypted emergency-stop tx
    //    for move_to_vault_txid via db.insert_signed_emergency_stop_tx_if_not_exists.
    // 4. Construct a plain, unauthenticated tonic Channel to the aggregator's public address
    //    (no client certificate presented at all).
    // 5. Call internal_get_emergency_stop_tx(GetEmergencyStopTxRequest { txids: vec![move_to_vault_txid] })
    //    using this unauthenticated client.
    //
    // Assertions (binding check):
    //   BEFORE: caller_authority == self  is assumed true by is_internal()'s design intent.
    //   AFTER:  response.encrypted_emergency_stop_txs is non-empty and contains the ciphertext
    //           for move_to_vault_txid, proving caller_authority == self was NOT actually verified
    //           (Noop never checked peer identity or the "Internal" grpc-method header).
    assert!(response.into_inner().encrypted_emergency_stop_txs.len() == 1);
}
```
This demonstrates that with `client_verification=false` (a real, reachable configuration), the "Internal" designation on `internal_get_emergency_stop_tx` provides no actual access control, and an unprivileged, uncertified caller can retrieve the encrypted emergency-stop transaction/commitment ahead of its intended reveal.
