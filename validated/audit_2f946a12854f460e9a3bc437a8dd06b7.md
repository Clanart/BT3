### Title
Stale manual conflict resolutions carry over into a new, attacker-influenced conflict operation - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` reuses the previous conflict's `manualResolutions` map for the *next* conflict state it builds, without verifying that the new conflict (which may come from a completely different merge/rebase/cherry-pick against attacker-supplied content) is actually the same operation the resolutions were chosen for. This is the same broken-invariant pattern as the Sherlock report: a per-operation flag/state (`inChallenge` there, `manualResolutions` here) is carried forward based on "does *something* still exist" rather than "does this specific challenge/conflict still exist," letting stale state silently apply to a different object.

### Finding Description
In `updateConflictState`: [1](#0-0) 

the function pulls `manualResolutions` from `state.conflictState` (the *previous* conflict) whenever it is non-null, and passes that same map straight into `getConflictState(status, manualResolutions)` to build the *new* conflict state: [2](#0-1) 

`getConflictState` does not key `manualResolutions` by any identity of the conflict (not by `currentTip`, not by target branch, not by SHA of the incoming side) — it simply attaches whatever map was carried in. The only identity checks that exist (`branchNameChanged` in `performEffectsForMergeStateChange` / `performEffectsForRebaseStateChange`) are used solely to bump telemetry counters, not to invalidate the `manualResolutions` map itself: [3](#0-2) 

Downstream, `manualResolutions.get(path)` is the sole gate used to decide whether a conflicted file is "resolved" and can be silently staged/committed without displaying the conflict markers to the user: [4](#0-3) [5](#0-4) 

and it is applied at commit time via `git checkout --ours/--theirs`: [6](#0-5) 

Because the carried-forward map is matched purely by file **path**, not by which merge/rebase/cherry-pick it belongs to, a user who:
1. Resolves `foo.txt` as `theirs` in one conflict (say, a benign merge), and
2. Immediately starts a second, unrelated conflicting operation (e.g. a cherry-pick or rebase against an attacker-controlled branch/remote that also touches `foo.txt`)

will have `foo.txt` in the second operation reported as already-resolved via the stale `theirs` choice — even though "theirs" in the new operation now refers to entirely different, attacker-supplied content that the user never reviewed. The `ConflictsDialog` shows the file with a green checkmark (`renderResolvedFile`) instead of the conflict markers: [7](#0-6) 

so `Continue` is enabled and the file is committed using the attacker's content without the user ever seeing a conflict for it.

### Impact Explanation
This lets an attacker who controls a branch/commit fetched into the repository (e.g. via a PR branch, a remote, or a crafted upstream) get their file content silently substituted into a commit the user believes they reviewed, because Desktop treats the file as already resolved based on an unrelated, prior decision. This is a silent corruption of what the user commits (and subsequently pushes), matching the class of "silent corruption of what the user commits or pushes" in the accepted impact list.

### Likelihood Explanation
The trigger requires no privileged access — only that: the user resolves conflicts manually with `ours`/`theirs` in one operation, then begins a second conflicting operation on the same working copy before the state cache resets `conflictState` to `null` at a status refresh boundary, and that the second (attacker-influenced) conflict happens to touch the same file path. This is a real, if narrow, sequence a normal Desktop user can hit (e.g., resolving a merge conflict, then immediately rebasing/cherry-picking from a malicious fork with colliding file paths), without any local/admin access or leaked credentials.

### Recommendation
Do not carry `manualResolutions` across `updateConflictState` calls unless the new conflict is verified to be the *same* operation as the previous one (e.g., same `kind`, same `currentTip`/`targetBranch`/`baseBranchTip` identity), analogous to using `batchInChallenge` instead of "does something exist" in the referenced fix. When the underlying operation identity changes, `manualResolutions` should be reset to an empty map rather than defaulting to "carry forward from `prevConflictState`."

### Proof of Concept
1. Clone/open a repository in Desktop and merge a branch that conflicts on `shared.txt`; manually resolve it via "Use incoming file" (`theirs`), but do not complete the merge commit.
2. Before Desktop's status cache clears `conflictState` to `null` (e.g., abort quickly and immediately trigger a rebase/cherry-pick from an attacker-controlled branch that also conflicts on `shared.txt`), start the second operation.
3. Because `updateConflictState` reuses `prevConflictState.manualResolutions`, the new conflict state's `manualResolutions` map still contains `shared.txt -> theirs` from the first (unrelated) operation.
4. `getConflictedFiles`/`getResolvedFiles` in `app/src/lib/status.ts` report `shared.txt` as resolved for the new operation, hiding it from `ConflictsDialog`.
5. The user clicks Continue/Commit; `createMergeCommit`/`stageManualConflictResolution` runs `git checkout --theirs` against the attacker's content for the *second* operation, committing it without the user ever seeing the conflict markers for that file.

/**
 * Convert the received status information into a conflict state
 */
function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

function performEffectsForMergeStateChange(
  prevConflictState: MergeConflictState | null,
  newConflictState: MergeConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
): void {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.currentBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.currentBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the merge must have been aborted
  if (branchNameChanged) {
    statsStore.increment('mergeAbortedAfterConflictsCount')
    return
  }

  const { currentTip } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null
  ) {
    const previousTip = prevConflictState.currentTip

    if (previousTip !== currentTip) {
      statsStore.increment('mergeSuccessAfterConflictsCount')
    } else {
      statsStore.increment('mergeAbortedAfterConflictsCount')
    }
  }
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
