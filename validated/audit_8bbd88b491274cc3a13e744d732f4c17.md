## Title
`_fetchRefspec` intentionally bypasses the app-wide "one network op at a time" lock, allowing attacker-triggered fork fetches to race with push/pull/fetch and corrupt refs/working tree - (File: `app/src/lib/stores/app-store.ts`)

### Summary
Every push, pull, and fetch operation in GitHub Desktop is serialized through the `withPushPullFetch` guard, which checks/sets `repositoryStateCache`'s `isPushPullFetchInProgress` flag before touching the repository. `_fetchRefspec` is the one network-mutating git operation that explicitly does **not** acquire this lock, by design, per its own doc comment. This is the same bug class as the Vyper advisory: a special "default"/fallback code path (here, fetching an arbitrary refspec to support viewing a PR from a fork) does not respect the concurrency guard ("nonreentrancy key") that every sibling operation respects.

### Finding Description
`withPushPullFetch` is the sole mutual-exclusion mechanism preventing concurrent Git network operations from touching the same working directory/`.git` state at once: [1](#0-0) 

`_pull` and `performFetch` both route through it: [2](#0-1) [3](#0-2) 

`_fetchRefspec`, however, calls `gitStore.fetchRefspec` directly, with an explicit comment stating it "does not opt-in to checks that prevent multiple concurrent network actions": [4](#0-3) 

`gitStore.fetchRefspec` fetches the refspec from *every configured remote* (`for (const remote of remotes)`), not just a trusted `origin`: [5](#0-4) 

The underlying git call runs `git fetch <remote> <refspec>` with `successExitCodes: new Set([0, 128])`, meaning even a failing/malformed fetch is silently treated as "successful": [6](#0-5) 

The refspec/URL data driving this path comes from GitHub API pull-request objects (`pr.head.ref`, `pr.head.repo.clone_url`) and can be reached via deep links (`x-github-client://openPullRequest`) that resolve to `openPullRequestFromUrl`, which itself fetches and checks out attacker-controlled fork branches: [7](#0-6) 

Because `_fetchRefspec` skips the `isPushPullFetchInProgress` guard, a user who simultaneously (a) opens a PR from a fork (deep link or "Open PR from Desktop" UI) while (b) a push/pull/fetch triggered by the background fetcher or the user is in flight, will have two `git fetch`/`git push` processes running concurrently against the same repository. Concurrent Git processes writing to `.git/refs`, the index, `FETCH_HEAD`, or packed-refs without locking coordination from Desktop's side can interleave in ways git's own file-locking doesn't fully protect against for cross-process ref updates combined with Desktop's own in-memory `gitStore` ref/branch caches, resulting in silently corrupted branch/ref state, a ref pointing to an unexpected fork commit, or a push proceeding against stale ahead/behind data because the fetch that "won" the race updated remote tracking refs the user never reviewed.

### Impact Explanation
The broken invariant is "no two Git network mutation operations run concurrently against a given repository," which the app enforces everywhere else via `withPushPullFetch`. `_fetchRefspec` is invoked with attacker-influenced input (a PR's head ref name and head clone URL, sourced from the GitHub API or a fork the attacker controls) and can execute concurrently with a legitimate push/pull, corrupting the local repository's ref/working-tree state or causing the local checkout to silently track a fork commit the user did not intend to fetch — this maps to the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Requires no privileged access: an attacker who controls a forked repository and gets a victim to open its PR (via UI action or the `x-github-client://openPullRequest` deep link, which is externally triggerable) supplies the refspec/URL. The race window depends on Desktop's periodic background fetch (`shouldBackgroundFetch`) or a manual pull/push occurring at the same time, which is plausible but not guaranteed on every attempt — this is a real but timing-dependent condition, not a certainty on every invocation, so likelihood is moderate rather than high.

### Recommendation
Route `_fetchRefspec` through `withPushPullFetch` (or a compatible per-repository mutex) the same way `_pull`/`performFetch`/push operations do, rather than the documented opt-out. If the PR-from-fork UX requires it to proceed even while another op is in-flight, queue it behind the in-flight operation instead of running unguarded, and remove reliance on the `successExitCodes: [0, 128]` "always accept" behavior in `fetchRefspec` (`app/src/lib/git/fetch.ts`) which currently masks fetch failures as success.

### Proof of Concept
1. Attacker creates a fork and opens a PR against a repository the victim has cloned in GitHub Desktop.
2. Victim's Desktop is idle for background fetch purposes; the periodic background fetch timer fires (`shouldBackgroundFetch`), starting a `performFetch` → `withPushPullFetch` (lock held).
3. Simultaneously, the victim clicks a `x-github-client://openPullRequest/...` link (or the "Open in Desktop" PR button) pointing at the attacker's PR; this resolves via `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` → `_fetchRemote`/`_fetchRefspec` path, which does not wait on or acquire the same lock.
4. Two `git fetch` invocations run concurrently on the same `.git` directory: one from the background fetch, one from the PR-open flow fetching the attacker's fork remote/refspec.
5. Depending on timing, ref updates from the two processes interleave, potentially leaving remote-tracking refs, `packed-refs`, or the in-memory `gitStore` branch cache in an inconsistent state relative to what was actually fetched, which can affect subsequent checkout/push targets without the user reviewing the discrepancy.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)
