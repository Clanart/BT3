### Title
Auction Bid EIP-712 Signature (v0.0.1) Omits `MaxGasPrice`, Allowing Unauthenticated Tampering of a Signed Bid Field - ([File: kaiax/auction/eip712.go])

### Summary
The `bind`/TSIG CVE is a bug class where a cryptographic authentication check does not bind all of the security-relevant fields of the protected message, so a party without the secret can get an altered message accepted as authentic. The Kaia auction bid-verification path has the same structural weakness: `Bid.MaxGasPrice` is a first-class field of `BidData` but is excluded from the EIP-712 struct hash used for the "v2" (`AuctionVersionV2`) searcher-signature typehash, so it can be modified after signing without invalidating `ValidateSearcherSig`.

### Finding Description
`BidData` carries a `MaxGasPrice` field alongside the auction parameters that the searcher signs: [1](#0-0) 

The EIP-712 struct hash for the base/v2 typehash, `auctionType`, and its `EncodeData()` implementation deliberately omit `MaxGasPrice`: [2](#0-1) [3](#0-2) 

Only the newer `auctionTypeV3`/`bidV3.EncodeData()` path includes `maxGasPrice` in the signed digest: [4](#0-3) 

`GetHashTypedData` selects which struct hash (and therefore which fields) gets signed purely based on the `version` string that is passed in at verification time, not based on any property bound to the bid itself: [5](#0-4) 

`ValidateSearcherSig` then recovers the signer strictly from this version-dependent digest and only checks that the recovered address equals `b.Sender` — it never separately validates that fields excluded from the digest (like `MaxGasPrice`) are still what the searcher intended: [6](#0-5) 

Because `MaxGasPrice` lives in the same mutable `Bid`/`BidData` object that is gossiped over the network (`HandleBid`) and stored in the bid pool, any entity that can see or relay a bid — a peer, the auctioneer, or the node itself — can change `bid.MaxGasPrice` after the searcher signed it under the v2 typehash, and `bp.validateBidSigs` will still accept it because it only re-verifies the searcher/auctioneer signatures over the same (MaxGasPrice-excluding) digest: [7](#0-6) 
This is structurally identical to the BIND TSIG flaw: the verifier trusts a signature as attesting to the full message, but the signature does not actually cover a field that materially affects how the message will be processed downstream, allowing an unauthorized modification to slip through as "signed."

### Impact Explanation
`MaxGasPrice` is intended to cap the gas price the searcher is willing to pay/be exposed to for their bid execution (as evidenced by its introduction in the v3 typehash and its presence in `blockchain/system/auction.go` / `kaiax/auction/impl/api.go`). If a bid is validated/relayed under the v2 typehash while `MaxGasPrice` is silently altered, the searcher's actual fee exposure or bid execution constraints can be changed without their authorization — i.e., fee/gas-price manipulation of a value-bearing auction transaction that the searcher never actually signed for. This falls squarely in "fee or fee-delegation abuse" / "auction settlement theft" territory called out in the validation rules, since the field is not just informational metadata but a value-relevant execution parameter of a signed, money-moving bid.

### Likelihood Explanation
Reachable by any unprivileged searcher/bidder or any entity relaying a bid over the p2p `HandleBid` path or through the `auction_submitBid` RPC — no validator/consensus/node compromise is required. The only precondition is a bid pool/verification path currently operating under `AuctionVersionV2` (the fallback/base typehash), since `MaxGasPrice` is excluded from that hash by construction; the bug requires no race condition or malicious peer capability beyond normal bid propagation.

### Recommendation
Include `MaxGasPrice` in the v2 (base) EIP-712 struct hash and typehash as well (or reject/zero it in the v2 code path so it can never be a live, unsigned field at the same time it's honored downstream), so that the searcher's signature always cryptographically commits to every field of `BidData` that influences bid processing, regardless of which `AuctionVersion` is active.

### Proof of Concept
1. Deploy/point the auction module at an `AuctionEntryPoint` reporting `AUCTION_VERSION = "0.0.1"` (`AuctionVersionV2`).
2. A searcher builds a `Bid` with `MaxGasPrice = X`, computes `GetHashTypedData(chainId, entryPoint, AuctionVersionV2)` (which excludes `MaxGasPrice` per `Bid.EncodeData()`), and signs it, producing `SearcherSig`.
3. Before/while the bid is relayed (p2p `HandleBid`) or resubmitted, an intermediary (peer, auctioneer, or malicious component with bid-pool write access) sets `bid.MaxGasPrice = Y` (`Y != X`) without touching any other field.
4. `bp.validateBidSigs` → `bid.ValidateSearcherSig(chainId, entryPoint, AuctionVersionV2)` recomputes the same digest (still excluding `MaxGasPrice`) and recovers the original searcher address — validation succeeds even though `MaxGasPrice` no longer matches what the searcher actually authorized.

Note: I was unable to fully trace, within the current tool budget, exactly how `MaxGasPrice` is consumed at bid-transaction execution time in `blockchain/system/auction.go` / `kaiax/auction/impl/api.go` (e.g., whether it is only honored when the entry point reports v3, which would reduce but not eliminate the practical impact if any v2-signed bid's `MaxGasPrice` is read by a component unaware of versioning). This should be verified before treating the severity as final.

```go
func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}
```

```go
// GetHashTypedData returns the EIP-712 digest for the bid.
// version must match the on-chain AUCTION_VERSION of the entry-point contract
// the bid targets; "0.0.2" selects the v3.0 struct typehash (with maxGasPrice),
// any other value falls back to the v2.1 typehash.
func (b *Bid) GetHashTypedData(chainId *big.Int, verifyingContract common.Address, version string) []byte {
	if chainId == nil {
		return nil
	}

	domain := EIP712Domain{
		EIP712DomainTypeHash: eip712TypeHash,
		NameHash:             auctionNameHash,
		VersionHash:          crypto.Keccak256Hash([]byte(version)),
		ChainId:              chainId,
		VerifyingContract:    verifyingContract,
	}

	domainSeparator := EncodeEIP712(domain)

	var structHash []byte
	if version == AuctionVersionV3 {
		structHash = EncodeEIP712(bidV3{b})
	} else if version == AuctionVersionV2 {
		structHash = EncodeEIP712(b)
	} else {
		// Unknown version: default to v2.1 typehash.
		structHash = EncodeEIP712(b)
	}

	return crypto.Keccak256([]byte{0x19, 0x01}, domainSeparator, structHash)
```

```go
func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
```
