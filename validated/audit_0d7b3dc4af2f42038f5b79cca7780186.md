### Title
Bandwidth subscriptions silently expire (and are permanently lost) while an app is on the Allowlist bypass, mirroring the Claimable-yield fund-loss pattern - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
The external report describes a mode transition (Claimable → any other yield mode) that only carries over the *fixed* part of a balance and drops the *claimable/accrued* part, permanently destroying user funds. The local analog is `pallet-bandwidth`'s Allowlist bypass mode combined with its FIFO subscription expiry model: when an app's gate mode is switched from "bypass" (Allowlist=on) back to "metered" (Allowlist=off), the pallet does not re-anchor or preserve the byte-allowance the app paid for during the bypass window. Because `expires_at` is an absolute wall-clock timestamp fixed at purchase time and keeps advancing regardless of gate mode, any subscription bytes that were never consumed while bypassed are silently swept the next time the gate runs `try_consume` — with no accounting or event tied to that specific mode transition, exactly like the ERC20Rebasing bug where switching away from Claimable mode drops the claimable component of the balance.

### Finding Description
`pallet-bandwidth`'s gate has two operating "modes" per `(source, app)`:

- **Allowlist bypass mode**: `BandwidthGate::try_consume` returns `Ok(())` immediately and never touches the `Allowance` FIFO list. [1](#0-0) 

- **Metered mode**: the gate sweeps expired entries in place (`list.retain(|s| s.expires_at > now)`) before consuming bytes, and this sweep is silent — expired remainder bytes are simply dropped with no dedicated event (only the FIFO-cap eviction path emits `SubscriptionEvicted`). [2](#0-1) 

Each subscription's `expires_at` is fixed at purchase time and "never extends" as explicitly documented in the pallet's own module docs: [3](#0-2) 

The switch between the two modes is a single flag flip with no accounting step: [4](#0-3) 

This is structurally identical to the reported bug: a mode transition ("Claimable" ↔ "any other mode" in ERC20Rebasing; "bypass" ↔ "metered" in `pallet-bandwidth`) needs to reconcile the balance that accrued under the old mode (claimable yield / remaining prepaid bytes) into the new mode's accounting. `_setBalance` in the original report only considered the fixed part and dropped the claimable part; here, flipping `Allowlist` off only resumes gate accounting and does nothing to preserve or re-anchor the unconsumed `remaining_bytes` whose `expires_at` continued ticking the entire time the app was bypassed. Any bytes that expire during (or because of) the bypass window are forfeited the moment the gate runs again, with the loss surfacing as a silent `retain()` filter rather than a tracked, auditable event.

### Impact Explanation
An app that legitimately prepaid for bandwidth (`BandwidthCredited`) loses that paid-for byte allowance purely as a side effect of being placed into (and later taken out of) the bypass mode — funds already paid to the protocol via `BandwidthManager.purchase()` are never delivered as usable service, and there is no compensating mechanism (no extension of `expires_at`, no event marking the specific loss, unlike the FIFO-cap eviction path which at least emits `SubscriptionEvicted` with `lost_bytes`). This matches the bounty's "loss of funds" / "bandwidth balances must move exactly once and only to the rightful beneficiary and amount" criterion: the app paid for bytes that are silently destroyed instead of being usable or refunded.

### Likelihood Explanation
This is a certain, deterministic outcome rather than a probabilistic exploit: any `(source, app)` pair that purchases bandwidth, is later allowlisted (a normal phased-rollout/migration operation per the pallet's own docs), and is then taken off the allowlist after its subscriptions' `duration_secs` window has elapsed will hit this path on the very next inbound message. No malicious relayer, prover, or compromised key is required — it is an automatic consequence of the existing accounting design whenever the two documented allowlist use cases ("phased rollout" and "migration paths … a brief unpaid window during a contract upgrade") are exercised as intended. [5](#0-4) 

### Recommendation
When flipping `Allowlist` off (or, symmetrically, whenever bypass mode ends), the pallet should reconcile the FIFO list's `remaining_bytes`/`expires_at` against the elapsed bypass duration — e.g., extend `expires_at` by the bypass window, or freeze/sweep expiry accrual while bypassed — so that unconsumed, already-paid-for bytes are preserved into the new mode instead of being silently dropped by the next `retain()` call. At minimum, emit a `SubscriptionEvicted`-style event for bytes that expire specifically due to a bypass-mode transition so the loss is auditable, mirroring the recommendation in the source report to account for the full balance (fixed + claimable) when switching modes.

### Proof of Concept
1. Admin calls `set_tier` to configure `TierOne` with `bytes = X`, `duration_secs = D`.
2. App purchases `TierOne` via `BandwidthManager.purchase()` → pallet emits `BandwidthCredited { app_chain, app, tier: TierOne, bytes: X, expires_at: now + D }`. [6](#0-5) 
3. Admin calls `set_allowlist(source, app, true)` — app enters bypass mode. [7](#0-6) 
4. Time advances past `expires_at` (> `D` seconds) while the app is bypassed and sends zero or few messages — the `Allowance` list is never touched because `try_consume` short-circuits on the allowlist check. [8](#0-7) 
5. Admin calls `set_allowlist(source, app, false)` — app returns to metered mode with no reconciliation step.
6. App sends its next non-purchase POST request; `try_consume` runs `list.retain(|s| s.expires_at > now)`, silently dropping the fully-unused, fully-paid-for `X` bytes with no `SubscriptionEvicted`-equivalent event tied to this loss. [2](#0-1) 
7. The app has paid real fee-token value for `X` bytes over `D` seconds and received zero usable bandwidth — a permanent, unrecoverable loss of the funds it spent on the purchase.

### Allowlist bypass

The `Allowlist` storage map is a per-`(source, app)` flag that short-circuits the gate. It exists for two reasons:

- **Phased rollout.** Protocol-sponsored apps (e.g. core token gateways) that haven't yet migrated to the bandwidth model bypass the gate while their integration is in flight.
- **Migration paths.** Apps that need a brief unpaid window during a contract upgrade can be allowlisted and revoked once they're back on the meter.

Allowlist membership is admin-only and emits `AllowlistChanged` on every flip.
