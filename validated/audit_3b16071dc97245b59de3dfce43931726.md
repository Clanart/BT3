## Finding

`clone()` in [1](#0-0)  builds the environment for every `git clone` invocation and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while also always passing `--recursive`: [2](#0-1) 

This is the exact opt-out for Git's built-in clone-time safety check that was added upstream to remediate CVE-2024-32002 — a check that refuses (or warns/aborts) a clone when it detects a malicious repository layout where a symlink is crafted to alias the `.git` directory (exploitable especially on case-insensitive/case-normalizing filesystems such as default macOS/Windows), combined with `--recursive` submodule checkout, to smuggle an executable hook (e.g. `post-checkout`) that Git then runs automatically during the clone, giving the attacker code execution on the victim's machine the moment they clone the repository in Desktop.

By force-disabling this protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) unconditionally, GitHub Desktop reintroduces exactly the vulnerable behavior the upstream Git fix was designed to prevent, and it does so on every clone performed through the app (initial clone, "Clone in Desktop" deep links, `--cli-clone`, "Open in Desktop" URL actions that call `openOrCloneRepository`) — none of which require any local access, admin rights, or pre-existing compromise; the attacker only needs to get the victim to clone/open a crafted public repository URL.

None of the other guards in this file help here: `isClonePathSensitive()` at [3](#0-2)  only validates the destination directory string, not the contents of the cloned repository, so it does not intercept a malicious `.git`-aliasing symlink or submodule payload delivered inside the repo itself.

### Title
Git clone-time protection against malicious `.git`-symlink/submodule repositories is force-disabled (CVE-2024-32002 regression) - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally when invoking `git clone --recursive`, disabling the upstream Git safeguard that prevents a maliciously crafted repository (using a symlink that aliases the `.git` directory together with a submodule) from writing and auto-executing a Git hook during clone.

### Finding Description
Git 2.45.1 introduced a hardening flag (surfaced via the `GIT_CLONE_PROTECTION_ACTIVE` mechanism) to stop a clone-time RCE class where a crafted repository contains a symlink positioned so that, combined with a nested submodule checkout, Git ends up writing a hook file (e.g. `post-checkout`) into the *real* `.git/hooks` directory of the parent clone rather than into the submodule's own hierarchy — that hook then executes automatically as part of the same `clone --recursive` operation, with no user confirmation. GitHub Desktop's `clone()` function at [1](#0-0)  passes `--recursive` (submodules) and simultaneously forces this protection off for every clone the application performs, on every platform.

### Impact Explanation
An attacker who controls a public/shared repository (or a submodule referenced by one) can craft it so that opening it via "Clone in Desktop" (`x-github-client://openRepo/...` deep links parsed in [4](#0-3) ), the `--cli-clone` CLI flag, or `dispatcher.openOrCloneRepository` results in arbitrary code execution on the victim's machine as soon as the clone completes — before the user ever inspects or commits anything. This is full local code execution driven purely by cloning attacker-controlled repository content, matching the valid-impact criteria (attacker controls a cloned repository → code execution).

### Likelihood Explanation
High: no special user behavior beyond the normal, expected action of cloning/opening a repository link is required, submodule recursion (`--recursive`) is always enabled, and the protection is disabled unconditionally rather than being conditionally scoped, so every clone path in the app is affected.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or set it to the safe/enabled value) so Git's built-in symlink/submodule clone protection remains active; if `--recursive` submodule support requires special handling, validate submodule paths post-clone instead of disabling the upstream safety mechanism.

### Proof of Concept
1. Attacker publishes a repository containing a symlink and submodule structured per the CVE-2024-32002 pattern (symlink aliasing `.git`, submodule hook payload).
2. Victim clicks a "Clone in Desktop" link or runs `github-desktop --cli-clone <attacker-url>`.
3. Desktop calls `clone()` in [5](#0-4) , running `git clone --recursive ... <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment.
4. Git, with protection disabled, writes the attacker's hook into the real `.git/hooks` directory during the recursive submodule checkout and executes it automatically, achieving code execution on the victim's system.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

    '-c',

  ]
