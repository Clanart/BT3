### Title
Balance-change double-application via shared event-log diffing in recursive precompile calls - (File: precompiles/common/balance_handler.go)

### Summary
The Cosmos EVM analog of the Kryptonite `swap_denom` bug (which mis-accumulated `total_amount_in`/`total_amount_out` because a shared tracking variable was corrupted across operations) exists in the precompile `BalanceHandler` used to synchronize bank-module balance events into the EVM `StateDB`. The handler tracks state with a single `prevEventsLen` cursor and diffs `ctx.EventManager().Events()[prevEventsLen:]` to decide which bank events to apply to `StateDB`. When a precompile call recursively invokes another precompile call (or itself) on the same context/event manager, the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` pass consumes and applies its slice of events, but the outer call's slice — recorded before the inner call started — still spans across the inner call's events. This causes the same underlying bank `coin_spent`/`coin_received` events to be applied to `StateDB` twice (once by the inner handler and again by the outer handler), corrupting EVM balances, exactly analogous to `total_amount_in`/`total_amount_out` mixing coins from multiple operations in the original report.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())` [1](#0-0)  and `AfterBalanceChange` re-derives balance deltas purely from `events[bh.prevEventsLen:]`, applying `stateDB.AddBalance`/`SubBalance` for each `CoinSpent`/`CoinReceived` (and precisebank fractional) event found in that slice [2](#0-1) .

Each precompile invocation goes through `Precompile.runNativeAction`, which calls `BeforeBalanceChange(ctx)` immediately before executing the native action and `AfterBalanceChange(ctx, stateDB)` immediately after [3](#0-2) . If the native `action(ctx)` itself triggers another precompile call on the same underlying context/event manager (e.g. `evmKeeper.CallEVMWithData` re-entering the precompile dispatcher, as exercised by the debug precompile's `Call0` → recursive `CallEVMWithData` back into itself) [4](#0-3) , that inner call creates its own `BalanceHandler` (via `p.BalanceHandlerFactory.NewBalanceHandler()`) with its own `prevEventsLen` cursor, consumes and applies the events emitted during its own execution, and returns. Execution then resumes in the outer call, whose `prevEventsLen` was captured *before* the inner call ran — so when the outer call's `AfterBalanceChange` executes, its slice `events[outerPrevEventsLen:]` still includes all the events that were already consumed and applied by the inner handler, in addition to any new events. This is the same class of bug as `swap_info.total_amount_in`/`total_amount_out`: a single accumulator (`prevEventsLen`) is not scoped correctly per logical operation, so amounts belonging to one operation "bleed" into another and get double-counted.

This is not a hypothetical: the repository already contains a purpose-built regression test explicitly documenting this exact defect — "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [5](#0-4) 

### Impact Explanation
If bank events emitted during an inner (nested/recursive) precompile call are re-applied by an outer call's `AfterBalanceChange`, `StateDB.AddBalance`/`SubBalance` is invoked twice for the same underlying bank-keeper balance change. Depending on call ordering this can duplicate credited balances in the EVM `StateDB` (unauthorized duplication of spendable value) or double-debit a victim account, causing a permanent desync between the authoritative `x/bank`/`x/precisebank` balances and the EVM-visible balance used for all subsequent `balanceOf`/transfer/precompile logic in that block. Because `StateDB` balances back ERC20-view balances and native token balances exposed to every contract and JSON-RPC caller, this is an accounting-corruption/duplication issue matching the "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across EVM balances" impact class.

### Likelihood Explanation
Reachability is unprivileged: any account can deploy or call a contract that triggers a native/precompile call which itself makes a nested precompile call on the same execution context (e.g., WERC20/ERC20 precompiles invoked from other precompiles, or contracts using `dest_callback`/EVM-to-precompile re-entrant call patterns already present in the ICS20-callbacks flow). The bug is deterministic once the recursive event-log window overlap occurs — it does not depend on adversarial timing, races, or privileged access, only on triggering a nested precompile call. The project's own dedicated regression test for this exact scenario indicates this is a known, previously-identified failure mode of the `BalanceHandler` design, though I could not fully verify in this pass whether a corrective fix (e.g., a global/shared cursor spanning nested calls, or excluding already-processed events) has since been merged elsewhere in `precompile.go` or `balance_handler.go`, since the observed code still relies solely on a per-call event-length diff and does not account for nested consumption.

### Recommendation
Track a globally shared (context-scoped) "already processed" event index instead of a purely per-call `prevEventsLen`. For example, thread a single mutable cursor (or use `stateDB`'s own accounting) through nested `BalanceHandler` instances — e.g., store the last-processed event index in the `sdk.Context` (via a context value/StateDB field) so that when an inner call updates it, the outer call resumes diffing from the inner call's ending index rather than its own stale starting index. Alternatively, tag each bank event with a unique per-call correlation ID and only apply events tagged for the current call, or have nested calls "consume" (remove/mark) events from the shared list once applied so an outer diff cannot see them again. Add coverage ensuring the outer call's post-execution balance-delta application produces the exact same result on `StateDB` as directly querying `x/bank`/`x/precisebank`, both with and without nested precompile calls.

### Proof of Concept
The repository's own test demonstrates the mechanism: `TestRecursivePrecompileCallsWithDebugPrecompile` registers a debug precompile whose `Call0` recursively re-invokes itself via `evmKeeper.CallEVMWithData`, incrementing a counter and emitting a `debug_precompile` event on each recursive level [6](#0-5) ; the caller contract triggers this chain and the test asserts specific event counts to detect the desync [7](#0-6) . To reproduce the balance-duplication impact specifically:
1. Deploy a contract that calls a precompile which internally triggers `SendCoins` (bank event emission) and then, within the same call, invokes another precompile call (or itself) that also triggers a `SendCoins` on the same underlying `ctx`/`EventManager`.
2. Observe that the inner precompile's `AfterBalanceChange` applies the inner `CoinSpent`/`CoinReceived` deltas to `StateDB`.
3. When execution returns to the outer precompile call, its `AfterBalanceChange` re-scans `events[outerPrevEventsLen:]`, which still includes the inner's already-applied events, and reapplies the same `AddBalance`/`SubBalance` deltas — resulting in `StateDB` balances diverging from the true `x/bank` balances (double credit/debit), analogous to `total_amount_in`/`total_amount_out` being polluted with amounts belonging to a different operation in the original report.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

func (p Precompile) Call0(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	// data := crypto.Keccak256([]byte("function callback()"))[:4]
	counter := new(big.Int).SetBytes(contract.Input[1:])
	counter = new(big.Int).Add(counter, big.NewInt(1))

	args := math.U256Bytes(counter)
	selector := []byte{0xff, 0x58, 0x5c, 0xaf}
	data := append(selector, args...)

	caller := contract.Caller()
	fmt.Printf("Execute debug precompile %s, %p\n", caller.String(), p.BalanceHandlerFactory)
	rsp, err := p.evmKeeper.CallEVMWithData(ctx, p.Address(), &caller, data, true, nil)
	fmt.Println("callback response:", rsp.Ret, err)
	if err != nil {
		return nil, err
	}
	return nil, nil
}
