### Title
Quadratic-time denial of service in Bitcoin transaction share aggregation - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`TransactionSignatureMachine::complete` performs `Vec::remove(0)` once for every submitted participant share, for every transaction input, making share aggregation `O(inputs × participants²)` before the submitted participant set is validated. An attacker who can supply or cause collection of malformed share-map entries can therefore consume disproportionate CPU and memory-bandwidth resources and stall Bitcoin transaction completion. [1](#0-0) 

### Finding Description
`TransactionSignMachine::read_share` parses a fixed vector of one scalar share per input. [2](#0-1)  During completion, the wrapper iterates every transaction input and, for each input, iterates every entry in the caller-supplied `shares` map. [3](#0-2)  Each `shares.remove(0)` removes the first element of that participant's share vector and shifts every remaining element one position left. [4](#0-3) 

Consequently, for `m` map entries whose vectors contain `k` shares, constructing the per-input share maps performs roughly `k × m(m − 1) / 2` element moves before the inner `AlgorithmSignatureMachine::complete` call can validate the participant map. [5](#0-4)  The generic FROST validator only checks map cardinality and required participants inside that inner call, so it cannot prevent the wrapper's earlier quadratic work. [6](#0-5) 

### Impact Explanation
A malformed signing response can stall a node completing a Bitcoin transaction by forcing quadratic vector shifting across all transaction inputs. [1](#0-0)  Since `Participant` identifiers can range up to `u16::MAX`, a malformed share map may contain tens of thousands of distinct entries rather than being constrained to an expected small signing committee. [7](#0-6)  Each participant vector needs only enough fixed-size shares to survive the front removals, while the amount of shifted work grows with the square of the submitted map size. [4](#0-3) 

This is a reachable availability vulnerability because the affected `complete` API accepts externally assembled participant-share maps and performs the expensive extraction before validating that those participants belong to the signing set. [5](#0-4) 

### Likelihood Explanation
The issue is exploitable whenever an attacker can submit spoofed or malformed share-map entries to the completion path; no valid signatures, private keys, or consensus privileges are needed. [8](#0-7)  The cost is amplified by transactions with many inputs because the quadratic participant-vector traversal is repeated independently for each input. [4](#0-3) 

The finding is best rated **Medium**: it does not forge a signature or recover key material, but it can consume orders of magnitude more work than the malformed input's useful content and can prevent transaction completion in a signing service. [1](#0-0) 

### Recommendation
Avoid front-removal and validate the map before per-input conversion. Drain each participant vector once by storing an iterator or reversing each vector and using `pop`, or transpose the map into per-input maps in a single linear pass. Reject map lengths and participant IDs that do not match the expected `included` set before entering the input loop, preserving the checks performed by `validate_map`. [6](#0-5) 

### Proof of Concept
The following conceptual Rust test demonstrates the quadratic path; it can be placed inside the crate where the private `TransactionSignatureMachine` fields are accessible, or reached publicly by constructing a `SignableTransaction`, obtaining its `TransactionSignMachine`, and then calling `complete` with a malformed map. [9](#0-8) 

```rust
// Path: networks/bitcoin/src/wallet/send.rs
use std::collections::HashMap;
use frost::{Participant, sign::SignatureMachine};

// `machine` is a TransactionSignatureMachine for a transaction with `input_count`
// Taproot inputs.
fn quadratic_share_completion(
    machine: TransactionSignatureMachine,
    malicious_participants: u16,
    input_count: usize,
) {
    let mut shares = HashMap::new();

    // Each participant vector must contain at least input_count elements because
    // complete() removes index 0 once per transaction input.
    for participant in 1 ..= malicious_participants {
        shares.insert(
            Participant::new(participant).unwrap(),
            vec![valid_signature_share_encoding(); input_count],
        );
    }

    // For m malicious entries and k inputs, this performs approximately
    // k * m * (k - 1) / 2 scalar moves through Vec::remove(0), plus iteration
    // over all m entries for each of the k inputs.
    let _ = machine.complete(shares);
}
```

The key observation is that `complete` rebuilds a `HashMap` of all submitted participants inside the input loop and calls `remove(0)` for every participant vector. [4](#0-3)  With `k` inputs and `m` submitted entries, this causes `O(km²)` element moves even when the map is subsequently rejected as an invalid participant set. [10](#0-9)

/// Validate a map of values to have the expected participants.
pub fn validate_map<T>(
  map: &HashMap<Participant, T>,
  included: &[Participant],
  ours: Participant,
) -> Result<(), FrostError> {
  if (map.len() + 1) != included.len() {
    Err(FrostError::InvalidParticipantQuantity(included.len(), map.len() + 1))?;
  }

  for included in included {
    if *included == ours {
      if map.contains_key(included) {
        Err(FrostError::DuplicatedParticipant(*included))?;
      }
      continue;
    }

    if !map.contains_key(included) {
      Err(FrostError::MissingParticipant(*included))?;
    }
  }

  Ok(())
