### Title
Ed448 point decoding never rejects torsion: `Point::is_torsion_free` always returns true, admitting small-subgroup points into every `read_G`-reachable protocol - (File: crypto/ed448/src/point.rs)

### Summary
`crypto/ed448/src/point.rs` implements the torsion-freeness check required by `GroupEncoding::from_bytes` as `((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()`. `Scalar::ZERO - Scalar::ONE` is `-1`, so the expression is `(-P) + P`, which is the identity for *every* point, regardless of torsion. The check is therefore vacuous and `Point::from_bytes` accepts any decodable Ed448 point, including non-prime-order (cofactor-4) components. This mirrors the external report's class (accepting untrusted crafted input that corrupts downstream integrity): here a peer "injects" a torsioned group element through `C::read_G`, `Commitments::read`, `EncryptedMessage::read`, or `SchnorrSignature::read`, and every in-scope protocol built on Ed448 (PedPoP DKG, FROST, Schnorr verification) treats it as a prime-order element.

### Finding Description
`is_torsion_free` at `crypto/ed448/src/point.rs:295-297` should test `ℓ·P == identity` (or equivalently that `cofactor·P` lies in the prime-order subgroup), where `ℓ` is the Ed448 group order. Instead it computes `-P + P`:

```rust
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

This is identically true, so the `CtOption` returned by `Point::from_bytes` (`point.rs:303-318`) carries a validity bit that only excludes negative-zero encodings and non-decodings — torsion passes unchecked. `C::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) adds only a canonicality re-encode comparison, which cannot remove torsion, and `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) adds only an identity check, which a torsioned-but-non-identity point also passes.

Reachable paths for an unprivileged counterparty:
- `EncryptionKeyMessage::read` / `Commitments::read` (`crypto/dkg/pedpop/src/encryption.rs:57-59`, `crypto/dkg/pedpop/src/lib.rs:109-128`): a DKG participant broadcasts `t` PedPoP commitments; each is read via `C::read_G` and admitted into `verify_r1`'s commitment map (`lib.rs:313-337`) and later summed into `stripes` and per-participant `verification_shares` (`lib.rs:505-521`).
- `EncryptedMessage::read` (`crypto/dkg/pedpop/src/encryption.rs:171-177`): the ephemeral ECDH `key` is a `read_G` point.
- `SchnorrSignature::read` + `verify` (`crypto/schnorr/src/lib.rs:51-53, 108-110`): public keys and nonces taken from wire bytes are verified with `batch_statements`, which has no cofactor clearing (unlike RFC 8032's `8·` form explicitly rejected in the comments).

### Impact Explanation
A malicious DKG participant can append any 4-torsion point `T` to one of their PedPoP commitments (`Am[j] + T`). The PoK `sig` still verifies because the Schnorr check binds only `commitments[0]`'s prime-order behavior loosely — more precisely, the share-verification statements `share_verification_statements` and the interpolation sums in `calculate_share` (`lib.rs:487-521`) are linear in the commitments, so all honest consistency checks still pass while the resulting `ThresholdKeys::new` verification shares and derived `group_key` silently carry a torsion component. The group's public key is then off the prime-order subgroup: signatures produced by honest FROST signers verify under Serai's `R + cA - sG = 0` formula only with attacker-influenced torsion cancellation, and more importantly the torsioned group key is not the key the external verifier/network expects — the key is unusable or produces signatures that fail canonical verification, locking funds controlled by that group key. This is key-share/verifier integrity corruption caused solely by a crafted encoding accepted at deserialization, which is the concrete analog of the XML-injection class (untrusted structured input accepted past the parser altering semantic state).

### Likelihood Explanation
Reachability is high: any counterparty in an Ed448 PedPoP key generation or any party feeding `read_G`/`read_share`/`read_preprocess` bytes to the victim controls the point encodings. Exploitation requires only standard field arithmetic (choose `T` from the 4-torsion subgroup, add to a valid commitment) — no discrete logs or hash collisions. The constraint is scope: the flaw only harms deployments using the Ed448 ciphersuite, and the attacker must participate in (or supply data to) the victim's protocol run. Damage is integrity loss / funds rendered unspendable rather than silent secret recovery, so Medium severity.

### Recommendation
Fix `Point::is_torsion_free` to perform a real subgroup check, e.g. verify `self * Scalar::from(MODULUS_L)` (the prime group order) is identity, or check that `self * cofactor` lies in the prime-order subgroup via a known-correct multiply-by-`ℓ` test:

```rust
fn is_torsion_free(&self) -> Choice {
  (*self * Scalar::ORDER).is_identity()  // ℓ·P == identity
}
```

Alternatively clear the cofactor on decode (`from_bytes` returns `cofactor^{-1}`-scaled or multiply-by-4 result) — but subgroup rejection is the conservative choice matching `dalek-ff-group`'s `$torsion_free` handling. Add a regression test asserting `Point::from_bytes` rejects points with non-zero torsion components (e.g., `Ed448 basepoint + a known 4-torsion point` encoding).

### Proof of Concept
```rust
// crypto/ed448/src/point.rs
// is_torsion_free is always true:
//   (P * (0 - 1)) + P == -P + P == identity  ∀P
//
// Demonstration sketch:
let torsion: Point = /* a known order-2 or order-4 Ed448 point T != identity */;
let valid = EdwardsPoint::generator();
let malicious = valid + torsion.0; // has torsion component
let enc = Point(malicious).to_bytes();
let decoded = Option::<Point>::from(Point::from_bytes(&enc));
// BUG: decoded.is_some() == true even though `malicious` is not in the
// prime-order subgroup; compare with dalek-ff-group where from_bytes
// ANDs the validity bit with `$torsion_free(point)`.
```
Feeding the same encoding as a PedPoP `Commitments` entry or `EncryptionKeyMessage.enc_key` makes `C::read_G` accept a torsioned element that propagates into `verification_shares`/`group_key` in `calculate_share` (`crypto/dkg/pedpop/src/lib.rs:505-521`).
