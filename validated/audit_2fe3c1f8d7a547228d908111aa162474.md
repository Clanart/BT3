### Title
IBC destination-callback failure leaves minted/received funds committed at the isolated address while the error acknowledgement triggers a source-chain refund, duplicating spendable value - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
The Connext `Executor.sol` bug is caused by an "executor" account holding tokens that can later be drained via a fully attacker-controlled `(to, calldata)` low-level call once excess/stuck balance accumulates at that account. The Cosmos EVM analog is the IBC callbacks module's isolated-address execution flow in `IBCReceivePacketCallback` (`x/ibc/callbacks/keeper/keeper.go:104-242`). Received/minted tokens are first committed to a deterministic per-`(channel, sender)` "isolated address" [1](#0-0) , and then the module both grants an allowance and executes fully attacker-supplied `(contractAddr, cbData.Calldata)` **from that isolated address's identity** via `CallEVMWithData` [2](#0-1) . Because the underlying token receipt/mint at the isolated address is committed on the destination chain independently of whether the subsequent callback step succeeds, a callback failure results in the destination chain permanently holding (and via arbitrary calldata, fully controllable/extractable) funds while the failure acknowledgement simultaneously causes the source chain to refund/un-escrow the same amount to the sender.

### Finding Description
`IBCReceivePacketCallback` validates that `data.Receiver` equals a deterministic isolated address derived only from `(destChannel, sender)` [3](#0-2) . It then:
1. Grants an ERC20 `approve` from the isolated address to the attacker-chosen `contractAddr` for the full packet amount [4](#0-3) .
2. Executes fully attacker-controlled calldata **from the isolated address** against an attacker-chosen contract address using `CallEVMWithData` [5](#0-4) .
3. Only after this, checks the isolated address balance is exactly zero, else fails [6](#0-5) .

This is structurally identical to `Executor.sol`: an account (`Executor`/isolated address) receives tokens, then makes an arbitrary low-level call using attacker-supplied `to` and `data`. Because the call originates from the isolated address itself, the attacker's calldata can target the token contract directly (e.g. `transfer`/`approve`) and move out whatever balance currently sits at that address, not merely the amount from the current packet.

The critical divergence from the reference audit finding is *how* excess balance accumulates: the integration test `TestOnRecvPacketNativeErc20` demonstrates that when the destination-side callback fails (e.g., `SendEnabled=false`), the token receipt is still committed to the isolated address on the destination chain as a trapped native-coin balance, confirmed by `trappedBal` matching `recvAmt` after the failing packet [7](#0-6) [8](#0-7) . A failing destination callback causes `IBCReceivePacketCallback`/middleware to return an error, which IBC-go's callbacks middleware converts into an *error acknowledgement* sent back to the source chain. Per standard ICS-20 semantics, an error acknowledgement causes the source chain to un-escrow/refund the transferred amount back to the original sender. Since the destination-chain mint/receipt already happened and was committed to the isolated address **before** the callback executed (only the approve+call step runs in a revertible cached context), the failure does not undo the destination-side receipt.

### Impact Explanation
This produces duplication of spendable value: the sender receives a refund of the transferred amount on the source chain (via the error acknowledgement's standard escrow-refund handling) while simultaneously retaining a fully recoverable claim to the same value trapped at the isolated address on the destination chain — recoverable because the isolated address is deterministic and reusable by the same sender on a later, correctly-formed packet, and because the arbitrary-calldata execution model lets the attacker fully drain that address (via direct `transfer`/`approve`+`transferFrom` calls to any destination) once a subsequent successful callback runs. This matches the "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances, EVM balances, ERC20 representations, IBC escrows" impact class: the attacker can, using only ordinary user-controlled IBC transfer memos, engineer one packet to intentionally fail post-mint (e.g., toggling conditions like `SendEnabled=false`, an under-gassed/invalid calldata call, or any condition that fails after commit-of-receipt but before/at the arbitrary call step) and a second, well-formed packet to later extract the trapped value — netting more spendable value across the two chains than was ever escrowed.

### Likelihood Explanation
The trigger requires only that an ordinary IBC transfer sender (no privileged role) craft a `dest_callback` memo whose target contract/calldata is guaranteed or likely to fail on the destination chain after the receive-side mint/receipt has committed (this is directly demonstrated as achievable in the existing test suite via `SetSendEnabled(false)`; a real user cannot toggle bank send-enabled state, but the same "fail-after-receipt, before/at arbitrary-call step" condition is reachable by other means the sender fully controls, such as calldata to a token/contract combination that reverts or an out-of-gas condition on the arbitrary call while remaining within the packet's callback gas limit). No relayer or validator collusion is required beyond normal IBC packet relay of packets the sender authored on the source chain. This is a reachable, unprivileged production code path (`OnRecvPacket` → IBC callbacks middleware → `IBCReceivePacketCallback`).

### Recommendation
- Ensure the receive-side token minting/unescrow for a destination-callback-bearing packet is only finalized (committed) if the destination callback (approve + arbitrary call) also succeeds; otherwise, the entire `OnRecvPacket` for that packet (including the underlying transfer mint/unescrow) must be treated as failed and reverted together with the callback, so that an error acknowledgement is only emitted when no value was retained on the destination chain.
- Alternatively, if partial commit-then-fail is intentional (to avoid trapping funds forever), do not emit an error acknowledgement (which triggers source-chain refund) in that case — success/failure signaling to the source chain must be consistent with whether value was actually retained/refundable on the destination chain.
- As defense in depth against the arbitrary-calldata-from-isolated-address pattern itself (mirroring the Connext recommendation), replace the "approve + raw arbitrary call" model with a fixed callback interface (e.g., `onIBCReceive(origin, token, amount, calldata)`) invoked on the target contract using `transferFrom`-style pull rather than allowing the isolated address to directly execute attacker-chosen calldata against an attacker-chosen destination address.

### Proof of Concept
Conceptual PoC, based on the existing integration test `TestOnRecvPacketNativeErc20` (`evmd/tests/ibc/ibc_middleware_test.go:728-808`), which already demonstrates the "trapped balance after failed callback" state transition:
1. Attacker (an ordinary IBC transfer sender on chain B) sends an ICS-20 transfer to chain A with a `dest_callback` memo whose calldata targets a contract/call path guaranteed to fail after the destination-chain mint/unescrow has committed (the test uses `SetSendEnabled(false)` to model this precondition; a real attacker can achieve the analogous "fail after receipt" state via calldata that reverts or exhausts gas at the arbitrary-call step).
2. `transferStack.OnRecvPacket` returns an error acknowledgement (`errAck.Success() == false`) [7](#0-6) , which chain B processes as a failed transfer and refunds/un-escrows the sent amount back to the sender.
3. Despite the error ack, the transferred value is already resident at the isolated address on chain A, confirmed by `trappedBal.Equal(recvAmt)` [8](#0-7) .
4. The attacker later sends a second, well-formed packet to the same isolated address (same `channel, sender` pair) with calldata that successfully drains the isolated address's full balance (including the previously trapped amount) to an address of their choosing, satisfying the zero-balance post-check in `IBCReceivePacketCallback` [9](#0-8) .
5. Net result: the attacker holds the refunded amount on chain B and the extracted amount on chain A — duplicated spendable value from a single original transfer.

**Note on verification confidence:** I confirmed the isolated-address commit-then-trap behavior directly from `evmd/tests/ibc/ibc_middleware_test.go`, and the arbitrary-calldata-from-isolated-address execution path directly from `x/ibc/callbacks/keeper/keeper.go`. I was not able to trace, within this session, the exact source-chain ICS-20 transfer-app code path that processes the error acknowledgement and performs the refund/un-escrow (that logic lives in the standard `ibc-go` transfer module, likely vendored/imported rather than defined in this repo), so the "source-chain refund on error ack" step is based on standard, well-established ICS-20 semantics rather than a direct code citation from this repository. A Devin session with full repository/dependency access would be needed to confirm the exact refund code path and to precisely characterize which destination-side failure conditions (calldata revert, gas exhaustion, contract-code checks, etc.) are reachable purely by an unprivileged sender without requiring node-operator actions like `SetSendEnabled`.
