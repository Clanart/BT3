### Title
Gasless swap repay amount computed from stale nominal `GasPrice()` instead of the actual `EffectiveGasPrice` charged during Magma/Kore base-fee execution - ([File: kaiax/gasless/impl/getter.go])

### Summary
The audit finding describes a fee amount computed once from a mutable rate at submission time, then relied upon later (at settlement/cancellation) without re-validating that the rate hasn't changed, causing an incorrect amount to be transferred. In Kaia's `kaiax/gasless` module, the analogous pattern is that `lendAmount`/`repayAmount` are computed purely from the `GasPrice()` field embedded in the user-signed `ApproveTx`/`SwapTx` (a value chosen by the sender at signing time), while the *actual* fee deducted from balances during EVM execution (`StateTransition.buyGas`) is based on `st.gasPrice`, which after the Magma/Kore hard forks becomes the network's dynamic base fee (`baseFee`), not necessarily equal to the nominal `GasPrice()` on the transaction.

### Finding Description
`lendAmount()` and `repayAmount()` in `kaiax/gasless/impl/getter.go` compute the amount the proposer lends to (and later collects from) the gasless-swap sender: [1](#0-0) 

These use `approveTxOrNil.Fee()` and `swapTx.Fee()`, which internally multiply `GasLimit * tx.GasPrice()` — the nominal price field embedded and signed by the user when the transaction was created. The generated `LendTx` (`GetLendTxGenerator`) sends exactly `lendAmount()` KAIA to the sender, and the `SwapTx.AmountRepay` is checked against `repayAmount()`: [2](#0-1) 

However, when these bundled transactions are actually executed in a block, `StateTransition.buyGas()` deducts KAIA from the payer using `st.gasPrice`, which — per the documented fork rules in `node/cn/gasprice/gasprice.go` — equals a network-wide dynamic `baseFee` after the Magma/Kore hard forks, not the transaction's own nominal `GasPrice()` value: [3](#0-2) [4](#0-3) 

Because `ApproveTx`/`SwapTx` are restricted to legacy transactions (`decodeFunctionCall` requires `tx.Type() != types.TxTypeLegacyTransaction` to fail), and legacy transactions after Magma need only satisfy `GasPrice >= BaseFee`, a sender or relayer can sign these transactions with a `GasPrice()` set higher than the base fee that will actually be charged at inclusion time. If the base fee (governance-controlled `UnitPrice`/KIP-71 dynamic pricing) drops or is lower than the sender's chosen `GasPrice()` between signing and bundling/inclusion, `lendAmount`/`repayAmount` (computed from the stale, higher nominal `GasPrice()`) would overstate the actual KAIA cost of executing these transactions, while `buyGas` only deducts the lower, actual `baseFee`-derived amount from the involved accounts.

### Impact Explanation
If `lendAmount`/`repayAmount` diverge from the true `buyGas` cost:
- The proposer (via `LendTxGenerator`) sends the sender more KAIA than the transactions will actually cost when executed, meaning the sender profits the difference (value extraction from the block proposer/protocol) or
- The sender's `SwapTx.AmountRepay` obligation is fixed against a stale, inflated price, over-repaying the proposer relative to the real gas cost incurred, extracting value from the sender in favor of the proposer/protocol.

Either direction constitutes unauthorized value movement between the gasless module's lender (proposer) and borrower (sender), matching the audit's "Either PartyA or protocol will suffer a loss" impact class.

### Likelihood Explanation
Exploitability depends on how much a legacy transaction's signed `GasPrice()` field is allowed to diverge from the base fee at inclusion time (post-Magma, legacy tx just needs `GasPrice >= BaseFee`, with no explicit cap), and on the time/mempool-residency gap between signing (`ApproveTx`/`SwapTx` created off-chain) and bundling/inclusion by the block builder — both of which are plausible in normal operation, especially under legacy-tx submission where the sender doesn't need to track the exact live base fee. I was unable to fully verify within the available search results whether `buyGas`/`returnGas` additionally refunds the difference between the tx's nominal `GasPrice()` and the effective base fee back to the sender for legacy transactions post-Magma (which, if present, would fully neutralize this divergence) — this needs to be confirmed by reading the full legacy-transaction gas-price resolution path in `blockchain/state_transition.go` (`preCheck`/`buyGas` and any effective-gas-price normalization for `TxTypeLegacyTransaction`), which the current index did not fully expose.

### Recommendation
Recompute `lendAmount`/`repayAmount` in `kaiax/gasless/impl/getter.go` using the actual `EffectiveGasPrice` (base fee) that will be charged at execution time (as read from the block builder's current base fee) rather than the transactions' embedded nominal `GasPrice()` field, or explicitly reject/re-validate gasless bundles whose base fee has drifted from the signed `GasPrice()` beyond a safe tolerance before including them in a block.

### Proof of Concept
Not fully constructible from static analysis alone given the uncertainty noted above about whether legacy-tx post-Magma refunds the `GasPrice()`-to-`baseFee` delta. A concrete PoC would require: (1) confirming in `blockchain/state_transition.go` whether `buyGas`/`returnGas` refunds this delta for legacy transactions post-Magma, and if not, (2) constructing an `ApproveTx`+`SwapTx` gasless bundle signed with `GasPrice()` above the base fee at a later block, then observing the resulting `LendTx` amount and `SwapTx.AmountRepay` mismatch against the actual balance deltas recorded by `buyGas`/`returnGas` in a local testnet (e.g., extending `tests/gasless_test.go`).

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
