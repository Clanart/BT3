### Title
Payout operator attribution is not covered by the user's withdrawal signature, allowing reimbursement misattribution - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the `payout_tx` that fronts a Citrea withdrawal. The user's signature over this transaction is required to use `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP-341/BIP-118 semantics only commits input 0 to output 0 (the user's payment). The transaction's second output — the `OP_RETURN` containing the operator's x-only pubkey that the entire reimbursement pipeline uses to decide *who paid* — is **not** covered by that signature at all, nor is the funding input that pays for it. Any party who can complete/fund the transaction (not just the intended operator) can attach an arbitrary or empty `OP_RETURN`, and the protocol's downstream logic treats that self-declared value as ground truth for crediting reimbursement.

### Finding Description
The user grants a `SinglePlusAnyoneCanPay` signature over the withdrawal input, intentionally allowing anyone to add funding inputs/outputs (this is required so operators can front withdrawals using their own UTXOs): [1](#0-0) 

`create_payout_txhandler` builds the payout transaction with the user output at index 0 and appends an `OP_RETURN` at index 2 that names the operator to be credited — but this output is never signed/committed by the user, only chosen by whoever completes/broadcasts the transaction: [2](#0-1) 

The operator-side `withdraw()` function only verifies the user's signature against output 0; it never checks or binds anything about the `OP_RETURN` output to the signature or to the funding party: [3](#0-2) 

Downstream, the verifier's block-sync logic (`update_finalized_payouts`) blindly parses whatever `OP_RETURN` ends up on-chain and stores it as the "payer" of the withdrawal, explicitly noting that malformed/altered `OP_RETURN`s are possible and simply nulls the attribution: [4](#0-3) 

This attribution is then used as the sole ground truth for two Critical/High-impact bridge-custody decisions:

1. **Reimbursement eligibility** — `is_kickoff_malicious` compares the operator named in the on-chain `OP_RETURN` against the operator that later sends the kickoff; if they don't match (or the `OP_RETURN` is missing/garbage), the kickoff is flagged malicious and challenged, denying reimbursement to whoever actually fronted the funds: [5](#0-4) 

2. **Payout-checker task queue** — `get_first_unhandled_payout_by_operator_xonly_pk` only surfaces a payout for automated kickoff/reimbursement processing if `payout_payer_operator_xonly_pk` matches the querying operator; a `NULL` value (no/garbage `OP_RETURN`) makes the payout permanently invisible to every operator's automation: [6](#0-5) 

Because the signature does not commit to the `OP_RETURN` output or to the additional funding input(s), the transaction that ultimately confirms on-chain — and therefore the attribution recorded by the bridge — is determined by whoever finishes funding/broadcasting it, not by whoever the user (or an honest operator) intended. Since Bitcoin transaction propagation/relay/mempool visibility exposes the fully-formed, ANYONECANPAY-signed input before confirmation, any unprivileged party observing it can construct a competing spend of the same withdrawal UTXO that still correctly pays the user's committed output (so it is a valid, standalone, race-winnable transaction) while attaching a different (or no) `OP_RETURN`. This breaks the intended equality **"the operator credited == the party that paid."**

### Impact Explanation
If the honest operator's version of the payout is pre-empted (loses the race/RBF, or the attacker simply fund/broadcasts a valid alternative faster) by a version carrying no `OP_RETURN` or a corrupted one:
- The withdrawal is marked fulfilled (`payout_txid` set) so the optimistic-payout path can no longer be used for the same withdrawal (it explicitly checks `is_utxo_spent` on the withdrawal input before allowing an optimistic payout).
- `payout_payer_operator_xonly_pk` is `NULL`, so `get_first_unhandled_payout_by_operator_xonly_pk` never returns this withdrawal to any operator's automated reimbursement queue, and any operator who manually attempts the kickoff will be flagged malicious by `is_kickoff_malicious` and challenged.
- The corresponding `move-to-vault` UTXO — the actual bridged BTC — can no longer be claimed through the kickoff/round/reimburse chain by the operator who fronted funds, nor recovered via the optimistic path (already consumed). This matches the Critical impact category "a vault UTXO permanently frozen" / "an honest operator permanently unable to be reimbursed."

Alternatively, an attacker could substitute a valid registered operator's own pubkey they do not control, causing that operator's automation to later be flagged malicious and challenged for a kickoff they must attempt (since the payout checker task will eventually surface this to *no one*, but if the attribution names an operator who did not pay, that operator, upon noticing via monitoring, would be forced into a dispute they did not initiate).

### Likelihood Explanation
The attack requires the attacker to complete/fund a competing transaction that still pays the user's exact committed output/amount, meaning the attacker must supply the (typically small) funding difference themselves and win a fee race or first-confirmation race against the honest operator's broadcast transaction — a real but not free-of-cost precondition. It does not require any privileged role (verifier/operator/aggregator key), only Bitcoin mempool visibility and enough capital to fund the fee-bump, which is well within reach of "unprivileged attacker" as scoped. The underlying design defect (unsigned `OP_RETURN` attribution) is deterministic and always present for every payout transaction.

### Recommendation
Bind the operator attribution to the same signature that authorizes spending the withdrawal UTXO. Options:
- Have the user's off-chain message (and Citrea-side commitment) include the operator's x-only pubkey as part of what is EIP-712/Schnorr-signed, so `parse_withdrawal_sig_params`/`sign_withdrawal_verification_signature` validate that the `OP_RETURN` operator matches the pre-committed operator for this specific withdrawal request, rather than accepting whatever ends up on-chain.
- Alternatively, use a sighash flag that also commits to all outputs (e.g. `Default`/`All`) for the payout transaction, or add a taproot annex/covenant that ties the `OP_RETURN` to the signed output, so a third party cannot alter attribution while still satisfying the signed output.
- Add a fallback/admin recovery path (analogous to `MsgRefundAbortedCCTX`) so a `move-to-vault` UTXO whose payout attribution is null/corrupted can still be claimed by the operator who can prove (e.g., via their own wallet's funding inputs in the confirmed payout tx) that they funded it.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the cited code paths):
1. Operator O calls `withdraw()` for a registered Citrea withdrawal; `operator.rs::withdraw` builds and funds `payout_tx` (input 0 = withdrawal UTXO with user's `SinglePlusAnyoneCanPay` signature, output 0 = user payout, output 2 = `OP_RETURN(O_xonly_pk)`), then broadcasts it via `fund_raw_transaction`/RPC — it is now visible, unconfirmed, in the mempool.
2. Attacker A observes the transaction (public mempool data) and extracts the valid signature over input 0/output 0 (still valid for any transaction reproducing that exact input/output pair, since `SinglePlusAnyoneCanPay` only commits to them).
3. A constructs a new transaction reusing input 0 with the same witness and output 0, but supplies their own funding input(s) for the anchor/fee output and sets output 2's `OP_RETURN` to empty/garbage bytes (or a targeted operator's pubkey), then broadcasts with a higher fee to win the race/RBF.
4. Once A's transaction confirms instead of O's, `update_finalized_payouts` (core/src/verifier.rs:2283-2353) records `payout_payer_operator_xonly_pk = NULL` for this withdrawal.
5. `get_first_unhandled_payout_by_operator_xonly_pk` (core/src/database/verifier.rs:282-313) never surfaces this withdrawal to operator O's (or any operator's) automation, and `is_kickoff_malicious` (core/src/verifier.rs:1857-1890) treats any attempted kickoff for it as malicious, permanently blocking reimbursement from the `move-to-vault` UTXO that O (or whichever operator's funds actually reached the user) rightfully funded.

/// Creates a [`TxHandler`] for the `payout_tx`.
///
/// This transaction is sent by the operator to front a peg-out, after which operator will send a kickoff transaction to get reimbursed.
///
/// # Inputs
/// 1. UTXO: User's withdrawal input (committed in Citrea side, with the signature given to operators off-chain)
///
/// # Outputs
/// 1. User payout output
/// 2. OP_RETURN output (with operators x-only pubkey that fronts the peg-out)
///
/// # Arguments
/// * `input_utxo` - The input UTXO for the payout, committed in Citrea side, with the signature given to operators off-chain.
/// * `output_txout` - The output TxOut for the user payout.
/// * `operator_xonly_pk` - The operator's x-only public key that fronts the peg-out.
/// * `user_sig` - The user's signature for the payout, given to operators off-chain.
/// * `network` - The Bitcoin network.
///
/// # Returns
/// A [`TxHandler`] for the payout transaction, or a [`BridgeError`] if construction fails.
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
