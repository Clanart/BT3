### Title
Vacuous torsion-freeness check in `ed448::Point` lets non-prime-order points through `read_G`, breaking the PrimeGroup invariant for every Ed448 consumer - ([File: crypto/ed448/src/point.rs])

### Summary
The Envoy advisory's bug class — untrusted wire bytes accepted without proper sanitization, letting an invalid object flow into a downstream security decision — maps onto Serai as `Point::is_torsion_free` in `crypto/ed448`. The check is mathematically a no-op: it computes `self * (-1) + self`, which is always the identity, so `is_identity()` always returns true. Ed448 has cofactor 4, so 57-byte encodings of points carrying an order-2 or order-4 torsion component are accepted by `GroupEncoding::from_bytes` and consequently by `Ciphersuite::read_G` (the canonical-encoding re-check at `crypto/ciphersuite/src/lib.rs:97` still passes, because a torsioned point re-encodes to its own canonical bytes). Any unprivileged party who can submit a serialized Ed448 point — a DKG `Commitments` message, an `EncryptionKeyMessage`/`EncryptedMessage` `enc_key`/`key`, a `SchnorrSignature`'s `R`, a FROST preprocess/signing package — can inject a point outside the prime-order subgroup, while every downstream verification equation assumes `PrimeGroup` membership.

### Finding Description
At `crypto/ed448/src/point.rs:295-297`:

```rust
impl Point {
  fn is_torsion_free(&self) -> Choice {
    ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
  }
}
```

`Scalar::ZERO - Scalar::ONE` is `-1`, so the expression is `-P + P`, which equals the identity for *every* point. The function therefore always returns `Choice(1)` and never rejects anything. This is called from `Point::from_bytes` (`crypto/ed448/src/point.rs:316`), which is the only subgroup gate in the deserialization path; once a point passes, `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) accepts it as canonical and `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) only additionally rejects the identity — not torsion.

Reachable attacker-controlled entry points include:
- `EncryptedMessage::read` → `C::read_G` for `key` (`crypto/dkg/pedpop/src/encryption.rs:171-177`)
- `EncryptionKeyMessage::read` → `C::read_G` for `enc_key` (`crypto/dkg/pedpop/src/encryption.rs:57-59`)
- `Commitments::read` → `C::read_G` for each commitment (`crypto/dkg/pedpop/src/lib.rs:115-127`)
- `SchnorrSignature::read` → `C::read_G` for `R` (`crypto/schnorr/src/lib.rs:51-53`)

A concrete exploitable consequence in PedPoP VSS share verification: a dealer broadcasts commitments `C_j = a_j·G + T_j` where `T_j` is an order-4 point. An honest recipient `i` checks `s_i·G == Σ_j λ_{i,j}·C_j`, where the Lagrange coefficients `λ_{i,j}` are public. The prime-order part verifies iff the dealer dealt honestly, but the torsion part verifies iff `Σ_j λ_{i,j}·T_j = 0` (mod 4). Since the dealer knows all `λ_{i,j}` in advance, it can choose `T_j` so the check passes for a chosen subset of participants and fails for the rest — producing, from a single broadcast message, an equivocated DKG round where some honest validators accept a key share and others correctly reject it, with no proof that distinguishes dealer fault from recipient fault. Similarly, `EncryptedMessage.key = k·G + T` makes the blame DLEq in `decrypt_with_proof`/`EncryptionKeyProof` (`encryption.rs:381-396`, `487-499`) verify only when the transcript challenge satisfies `c·k·T ≡ 0` — a condition the attacker can grind offline (≈1/4 of challenges per retry) — decoupling "the PoP verified" from "the decryption key is provably correct," breaking the accountable-abort property.

### Impact Explanation
All verification math over Ed448 in the codebase (Schnorr `batch_statements`, PedPoP share checks, DLEq blame proofs, FROST aggregate verification) assumes `C::G` is prime-order. With torsioned inputs admitted, those equations only hold up to a hidden mod-4 component the attacker controls. This enables: (a) DKG equivocation where honest participants reach inconsistent accept/reject outcomes on the same commitments (a correctness/consensus failure on key generation); (b) messages whose proof-of-possession verifies while the associated correctness/blame proof cannot be produced, undermining attributable aborts; (c) grinding-assisted acceptance of points whose torsion component survives verification (challenge mod 4 is controllable by retrying nonce choice). This is at minimum a Medium-severity integrity flaw; where torsion-bearing commitments are carried into a FROST group key or share-verification chain it can also yield validation splits among honest validators.

### Likelihood Explanation
Triggering requires only that an attacker send crafted bytes to a deserialization endpoint — the same reachability as the Envoy bug (untrusted input, no privileges). For PedPoP/FROST over `Ed448`, any participant can encode `P + T` in place of a commitment, encryption key, or signature nonce; `recover_x`/`from_bytes` accepts it and `read_G` re-encodes it to itself. The main constraint is that exploitation currently requires the `Ed448` ciphersuite to be the curve in use; the math itself needs no secret knowledge and the mod-4 challenge grinding is trivially parallelizable offline.

### Recommendation
Replace the vacuous check with a real prime-order-subgroup membership test, e.g. `is_torsion_free` should verify `self * q == identity` (multiply by the group order `q`), or equivalently check `4·P` lands in the subgroup and `P` is not identity — the standard Ed448 approach is to verify `q·P` is the identity (or multiply by cofactor and reject identity). At minimum, correct the formula: the current `self * (ZERO - ONE) + self` can never fail, so either multiply by the prime-order scalar modulus or by the cofactor and check for a non-identity prime-order result. Additionally, have `ciphersuite::read_G`/`frost`'s `Curve::read_G` reject non-prime-order decodings explicitly so the invariant cannot be silently bypassed by a per-curve implementation error.

### Proof of Concept
In `crypto/ed448`, construct any torsion point `T` of order 2 or 4 (e.g., recover a point with the correct `x`/`y` satisfying the curve equation but lying outside the prime subgroup; for Ed448 the point `(0, -1)` has order 2 and encodes as `y = -1` with the appropriate sign bit). Then:

```rust
// order-2 point T = (0, -1): y = p - 1, sign bit 0
let mut t_bytes = [0u8; 57];
let p_minus_1 = FieldElement::ZERO - FieldElement::ONE;
t_bytes.copy_from_slice(p_minus_1.to_repr().as_ref());
let t = <Point as GroupEncoding>::from_bytes(&t_bytes); // CtOption::Some — BUG: should be rejected
```

`is_torsion_free` returns true because `T * (-1) + T = identity` regardless of `T`'s order, so `from_bytes` yields `CtOption::new(point, true)`. Feeding the same bytes through `Ed448::read_G` (via `Ciphersuite::read_G`) succeeds since `to_bytes` reproduces the input. A malicious DKG dealer then writes `a·G + T` into `Commitments` (accepted by `Commitments::read`), selects `T_j` values satisfying `Σ λ_{i,j} T_j = 0` for victim `i` only, and produces a commitments message that verifies for `i` while failing share verification for all other honest participants — a single wire message yielding inconsistent validation outcomes, exactly the "invalid message accepted downstream" shape of CVE-2023-27488.
