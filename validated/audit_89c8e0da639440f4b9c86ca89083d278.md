Confirmed key mechanism: `DiffSelection` tracks committed/staged lines purely by numeric `lineIndex` (a position in the unified diff), not by line content, and this selection object is preserved across working-directory refreshes by matching only on file `id` (path/status), independent of whether the diff content underneath changed.

### Title
Partial-commit/discard line selection is tracked by position, not content, allowing stale index-based selections to be applied to changed diffs - (File: `app/src/lib/stores/updates/changes-state.ts`, `app/src/models/diff/diff-selection.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
GitHub Desktop lets users stage a subset of lines in a modified file for a partial commit (or discard) by checking/unchecking individual lines in the diff view. This selection state (`DiffSelection`) is stored as a `Set<number>` of "diverging" line indices, keyed purely to the **position** of a line in the current unified diff, never to its content. When the working directory status refreshes (`updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts`), the old `DiffSelection` object is carried forward and re-attached to the file purely by matching `file.id` (path + status kind), with no verification that the underlying diff/hunk layout hasn't shifted: [1](#0-0) 

Later, when the commit or discard is executed, `formatPatch`/`formatPatchToDiscardChanges` (`app/src/lib/patch-formatter.ts`) re-fetch a **fresh** diff via `getWorkingDirectoryDiff` and then look up each line's selection using `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is computed purely from `hunk.unifiedDiffStart + lineIndex` of the *new* diff: [2](#0-1) [3](#0-2) 

This is the same broken invariant as the Lens Protocol issue: an object (a diff line / a publication) is identified by a mutable, content-independent index/ID rather than by its content, so if the underlying data shifts between when the identifier is assigned/selected and when it is acted upon, the operation silently applies to the wrong object.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `withRangeSelection`/`withLineSelection` operate exclusively on numeric line indices: [4](#0-3) 

There is no hash, line-text fingerprint, or hunk-header check tying a given index to particular content. The `WorkingDirectoryFileChange.selection` object survives status refreshes as long as the file's `id` still exists in the new status result — the code explicitly re-attaches the *old* selection to the *new* file object: [5](#0-4) 

If the file's on-disk content changes between the time the user made their line-level selection (e.g. checked specific lines to include in a partial commit) and the time the commit is actually executed — for example due to a `post-checkout`/`post-merge`/`post-index-change` hook, an editor auto-format/auto-save, an LFS smudge filter, or any background process modifying the file — the hunk boundaries and line offsets in the fresh diff computed at commit time (`getWorkingDirectoryDiff` inside `applyPatchToIndex`) will no longer correspond to the same lines the user intended. Because selection is keyed by `absoluteIndex` and not content, `formatPatch` will silently apply the old index set to the new hunk layout, causing wrong lines to be staged into the commit (or, in `formatPatchToDiscardChanges`, wrong lines to be discarded from the working tree).

Existing guards do not stop this: `updateChangedFiles` only clears the cached `diff` object when the *selected file id* changes, not when the file's diff content changes while remaining selected (see `state.selection.diff` reuse logic at lines 90–95 of the same file); and the selection (the `DiffSelection` divergingLines set) is unconditionally preserved regardless of diff content drift.

### Impact Explanation
A user could unknowingly commit or discard different lines than the ones they reviewed and explicitly selected in the UI — i.e., silent corruption of what the user commits or discards. In the worst case this could commit unreviewed/attacker-influenced content (e.g. secrets, malicious code, or unintended reverts) that the user believed they had excluded, or discard/lose lines the user intended to keep. This matches the "silent corruption of what the user commits or pushes" impact class from a repository/hook-triggered content change, without requiring local/physical access, admin rights, or pre-existing malware — only a cloned repository configured with a hook or filter that legitimately mutates working-tree content around Desktop's status/diff refresh cycle.

### Likelihood Explanation
Desktop supports running repository-defined Git hooks (`post-checkout`, `post-merge`, `post-index-change`, etc. — see `app/src/lib/hooks/get-repo-hooks.ts`) and honors `.gitattributes` filters (`isTrackedByLFS` in `app/src/lib/git/lfs.ts`), both of which are attacker-controllable via a cloned/fetched repository and can rewrite working-tree files asynchronously relative to Desktop's diff snapshot and commit action. Given Desktop polls/refreshes status periodically and reuses `DiffSelection` across those refreshes, the race window between "user selects lines" and "user clicks commit" is realistic, especially for larger diffs or slower machines. This is not a purely theoretical/DoS-only issue, but it does require a specific timing window and a hook/filter that mutates the exact file being partially staged, so likelihood is moderate rather than trivial.

### Recommendation
Tie `DiffSelection` state to diff content rather than raw line index — e.g., store a hash of each hunk's/line's text alongside the index, and when the working diff is recomputed, remap or invalidate selections whose underlying hunk content has changed instead of blindly reapplying the old index set. At minimum, when `getWorkingDirectoryDiff` is called immediately before `applyPatchToIndex`/`formatPatchToDiscardChanges`, compare the freshly-fetched diff against the diff that was current when the selection was last modified in the UI, and abort/re-prompt the user if they differ, rather than silently applying stale line indices to new hunk boundaries.

### Proof of Concept
1. Clone a malicious repository that has a `.git/hooks/post-index-change` (or similarly triggered) hook enabled and hooks execution allowed (`enableGitHookEnv`/hooks proxy — see `app/src/lib/hooks/hooks-proxy.ts`) which appends/removes a line in `victim.txt` a few seconds after any `git status`/`git add` invocation.
2. In Desktop, open the Changes view, select `victim.txt`, and manually check only specific lines (a partial selection) for the next commit — this builds a `DiffSelection` with diverging indices tied to the current hunk layout, per `withRangeSelection` in `app/src/models/diff/diff-selection.ts`.
3. Before the user clicks "Commit," Desktop's periodic status refresh runs `_loadStatus` → `updateChangedFiles`, which reattaches the old `DiffSelection` to the file entry unchanged (`app/src/lib/stores/updates/changes-state.ts` lines 43–56), while the hook has already shifted the file's line offsets.
4. The user clicks "Commit." `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts`) fetches a fresh diff and calls `formatPatch(file, diff)`, which uses the stale index set against the new hunk boundaries (`app/src/lib/patch-formatter.ts` lines 143–171), producing a patch that stages different lines than what the user visually selected.
5. The resulting commit silently contains lines the user never reviewed/approved, or omits lines they intended to include.

Note: I was unable to fully verify (without running the app) the exact minimum time window / whether Desktop's file-watcher-triggered refresh always precedes the "Commit" click in practice; this depends on OS file-watch timing and hook execution speed, which is not fully observable from static code alone.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
