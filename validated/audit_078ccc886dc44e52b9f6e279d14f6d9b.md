### Title
Untrusted `ReceivedOutput` bytes can report unspendable Bitcoin as wallet funds - ([File: networks/bitcoin/src/wallet/mod.rs](https://github.com/Annirich/serai--021/blob/master/networks/bitcoin/src/wallet/mod.rs))

### Summary

`ReceivedOutput::read` accepts an attacker-controlled scalar offset, `TxOut`, and `OutPoint` independently, without proving that the output exists on-chain or that its `script_pubkey` corresponds to the supplied offset. [1](#0-0)  A serialized output can therefore claim a Bitcoin payment is spendable by a particular offset when the encoded fields do not establish that relationship. [1](#0-0) 

### Finding Description

`ReceivedOutput` represents a spendable output through three fields: the scalar needed to derive the spend key, the claimed transaction output, and the claimed outpoint. [2](#0-1)  Its deserializer only parses those fields and immediately returns `Ok`, performing no scanner lookup, output-to-offset consistency check, or outpoint existence check. [1](#0-0)  By contrast, `Scanner` creates `ReceivedOutput` only after matching a transaction output’s `script_pubkey` against its registered offset-to-script map. [3](#0-2) 

The important authorization invariant is therefore not `msg.sender == _to`, but “the serialized offset must be authorized by the scanned `script_pubkey`.” [4](#0-3)  Deserialization bypasses that invariant and allows arbitrary bytes to manufacture an apparently spendable output under an unrelated offset or nonexistent outpoint. [1](#0-0) 

`SignableTransaction` later trusts the embedded `ReceivedOutput` fields: it uses `input.output` as the prevout, `input.outpoint` as the transaction input, and `input.offset` to select the signing key. [5](#0-4)  Although `multisig` rejects an offset whose derived key does not match the claimed prevout script, this occurs only after the malformed object has already been accepted as a wallet output. [6](#0-5) 

### Impact Explanation

An attacker who can supply serialized `ReceivedOutput` data can cause an application to report received funds that cannot actually be spent. [1](#0-0)  The forged object can combine a valid-looking `TxOut` and `OutPoint` with an offset that does not correspond to the wallet key, or reference an outpoint that was never created. [2](#0-1) 

If the malformed output reaches transaction construction, the spend either fails during multisig initialization because the offset-derived script does not match the claimed prevout, or produces a transaction spending a nonexistent UTXO. [7](#0-6)  This maps to unauthorized treatment of another output as wallet-controlled liquidity rather than direct withdrawal of existing funds. [3](#0-2) 

### Likelihood Explanation

The attack requires only untrusted bytes passed to the public `ReceivedOutput::read` API. [1](#0-0)  No private key, validator privilege, or malformed cryptographic proof is required because every component of the forged record is directly supplied by the caller. [1](#0-0) 

### Recommendation

Do not treat `ReceivedOutput::read` as establishing spendability. [1](#0-0)  Add a scanner-aware validation API that checks `output.script_pubkey` against the `Scanner`’s registered script-to-offset map before accepting the output. [4](#0-3)  Before transaction construction, also resolve each `OutPoint` against chain data and require the confirmed transaction output to equal the embedded `TxOut`. [5](#0-4) 

### Proof of Concept

```rust
use bitcoin::{
  absolute::LockTime,
  transaction::{Transaction, Version},
  OutPoint, TxOut, Amount,
};
use k256::{Scalar, ProjectivePoint};
use frost::curve::Secp256k1;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};
use ciphersuite::{group::GroupEncoding, Ciphersuite};
use zeroize::Zeroizing;

fn forged_output() -> ReceivedOutput {
  // Any valid P2TR script may be used; it need not correspond to `offset`.
  let wallet_key = ProjectivePoint::GENERATOR;
  let txout = TxOut {
    value: Amount::from_sat(10_000),
    script_pubkey: p2tr_script_buf(wallet_key).unwrap(),
  };

  // Claim a spending offset unrelated to the script.
  let wrong_offset = Scalar::from(7u64);

  // The outpoint is not proven to exist or to contain `txout`.
  let fake_outpoint = OutPoint::null();

  let mut bytes = Vec::new();
  bytes.extend(wrong_offset.to_bytes());
  bytes.extend(bitcoin::consensus::serialize(&txout));
  bytes.extend(bitcoin::consensus::serialize(&fake_outpoint));

  // Accepted despite the claimed output not being demonstrably spendable
  // under `wrong_offset`, nor proven to exist at `fake_outpoint`.
  ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}
```

`ReceivedOutput::read` accepts those attacker-controlled fields without checking the offset against the scanned script or checking that the outpoint contains the supplied `TxOut`. [1](#0-0)  The resulting object exposes the forged value through `value()` and can be passed onward as though it were scanner-produced. [8](#0-7)  `SignableTransaction::multisig` subsequently detects only the key/script mismatch and returns `None`, demonstrating that the accepted object represented funds that were not actually spendable. [7](#0-6)
