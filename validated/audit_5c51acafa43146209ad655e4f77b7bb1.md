Gasless module uses standard signed transactions (via `types.Sender(g.signer, tx)`), which already inherit Kaia's chain-ID-bound `SigHash`, so no analog there.

The one concrete analog I found is in the auction (KIP-249 auction/MEV) module's auctioneer approval signature.

### Title
Auctioneer approval signature in the auction bid-pool lacks chain/contract/content binding, enabling signature replay - (File: kaiax/auction/bid.go)

### Summary
Bids submitted to the Kaia auction module require two signatures: a searcher signature (EIP-712, properly bound to chain ID, verifying contract, and full bid content) and an auctioneer signature. Unlike the searcher signature, the auctioneer signature is computed over an unstructured hash that includes none of the bid's economic fields, the chain ID, or the auction contract address.

### Finding Description
`Bid.ValidateSearcherSig` correctly derives an EIP-712 digest including `chainId`, `verifyingContract`, and the full `AuctionTx` struct (targetTxHash, blockNumber, sender, to, nonce, bid, callGasLimit, data) via `GetHashTypedData` [1](#0-0) . However `Bid.ValidateAuctioneerSig` recovers the signer from `GetEthSignedMessageHash()`, which hashes only the raw `SearcherSig` bytes with the plain `"\x19Ethereum Signed Message:\n"` prefix — no chain ID, no verifying contract, no bid fields at all: [2](#0-1) [3](#0-2) .

This is validated in `BidPool.validateBidSigs`, where the auctioneer address is checked only against `bp.auctioneer` with no reference to `bp.ChainConfig.ChainID` or `bp.auctionEntryPoint`: [4](#0-3) .

Because the auctioneer digest is derived only from the byte value of `SearcherSig`, the auctioneer's "approval" carries no independent binding to a specific chain, auction contract version, or even to the semantic content of the bid — it merely certifies "I attest to this specific 65-byte blob." This mirrors the reported bug class: a signature scheme that omits contract-instance/chain-id binding, relying entirely on a different field (here, the searcher's EIP-712 signature) to provide domain separation.

### Impact Explanation
If the same auctioneer key is reused for more than one auction context (e.g., a second `auctionEntryPoint`/version deployed as `AuctionVersionV3` alongside `AuctionVersionV2`, a redeployed entry point after an upgrade, or the node config `updateAuctionInfo` pointing to a different chain/testnet using the identical operator key), the auctioneer's signature validity depends solely on recomputing `keccak256("\x19Ethereum Signed Message:\n65" + SearcherSig)`. This value is not tied to the deployment that the auctioneer intended to approve. Any party capturing an `(SearcherSig, AuctioneerSig)` pair from one bid pool instance can present it to another `BidPool` instance running with the same `auctioneer` address, since `validateBidSigs` never cross-checks the auctioneer digest against `bp.ChainConfig.ChainID` or `bp.auctionEntryPoint`. Because `ValidateSearcherSig` is checked independently and separately binds to the target pool's own chain/contract, the searcher's signature would also need to validate for that pool — this limits, but does not eliminate, risk in scenarios where the *same* entry-point/chain is served by multiple bid pool processes (e.g., a redeployed/migrated instance with the same address) or an intentionally reused key across `AuctionVersionV2`/`AuctionVersionV3` deployments sharing an entry point address. In such configurations, a previously auctioneer-approved bid could be accepted into the pool of the "wrong" instance without a fresh auctioneer approval, potentially causing acceptance of stale/attacker-controlled bid content into block building (`getBidTxGasLimit`, `insertBid`), i.e., auction/bid-settlement manipulation.

### Likelihood Explanation
Exploitability is conditioned on operational reuse of the same auctioneer signing key across more than one `BidPool` instance/version/chain — a configuration decision, not a cryptographic guarantee enforced by the code. The searcher-side EIP-712 binding independently limits blast radius since `ValidateSearcherSig` must also pass for the target instance's chain ID and entry point. Given this, likelihood is Medium: the vulnerable code path is directly reachable by any bidder/auctioneer interacting via the public `auction_submitBid` RPC, but full exploitation requires the operational precondition of key/address reuse across instances.

### Recommendation
- Short term: include the auction domain in the auctioneer digest — bind `AuctioneerSig` to `chainId`, `auctionEntryPoint`/version, and the bid's own hash (e.g., sign over `keccak256(chainId, verifyingContract, bid.Hash())` or reuse the same EIP-712 domain/struct used for `ValidateSearcherSig`), instead of hashing only `SearcherSig` bytes.
- Long term: unify both searcher and auctioneer signatures under the same EIP-712 domain/type used in `eip712.go`, and document/test that no signature scheme in the codebase authorizes state solely from another signature's raw bytes without independently re-asserting chain/contract/content binding.

### Proof of Concept
1. Operator runs two `BidPool` instances (e.g., v2 auction entry point and v3 auction entry point, or two chains) configured with the same `auctioneer` address (via `updateAuctionInfo`) — see `bp.auctioneer` field and its use in `validateBidSigs`: [5](#0-4) [6](#0-5) .
2. A searcher obtains a legitimate `(SearcherSig, AuctioneerSig)` pair for a bid against instance A (`ValidateSearcherSig` passes for A's chainId/entryPoint, `ValidateAuctioneerSig` passes because `AuctioneerSig` only commits to `SearcherSig` bytes, not to A's identity).
3. The searcher also crafts (or already possesses) a `SearcherSig` valid for instance B with the *same raw signature bytes* — not generally possible unless B shares chain/entry-point parameters with A (since EIP-712 domain differs), but is trivially true when A and B are the same domain served by two independently-managed `BidPool` processes/versions with identical `auctionEntryPoint`/`chainId` but different auctioneer-approval workflows.
4. Submit the pair to instance B via `auction_submitBid` → `AuctionAPI.SubmitBid` → `BidPool.AddBid` → `validateBidSigs`, which accepts the auctioneer approval without any B-specific binding: [7](#0-6) .

Note: I could not find code that enforces the auctioneer address itself to be scoped per-chain/per-entry-point beyond `bp.auctioneer` comparison, and I could not fully verify whether any deployment/operational safeguard prevents auctioneer-key reuse across instances — this is a configuration-dependent precondition that would need confirmation from the Kaia team on typical auctioneer key management practices.

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (bp *BidPool) updateAuctionInfo(auctioneer common.Address, auctionEntryPoint common.Address, auctionEntryPointVersion string, bidTxGasBuffer uint64) {
	bp.auctionInfoMu.Lock()
	defer bp.auctionInfoMu.Unlock()

	if bp.auctioneer == auctioneer && bp.auctionEntryPoint == auctionEntryPoint && bp.auctionEntryPointVersion == auctionEntryPointVersion && bp.bidTxGasBuffer == bidTxGasBuffer {
		return
	}

	// Clear the existing auction pool since the auctioneer or auction entry point address is changed.
	bp.clearBidPool()

	bp.auctioneer = auctioneer
	bp.auctionEntryPoint = auctionEntryPoint
	bp.auctionEntryPointVersion = auctionEntryPointVersion
	bp.bidTxGasBuffer = bidTxGasBuffer

	logger.Info("Update auction info", "auctioneer", auctioneer, "auctionEntryPoint", auctionEntryPoint, "auctionEntryPointVersion", auctionEntryPointVersion, "bidTxGasBuffer", bidTxGasBuffer)
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}
