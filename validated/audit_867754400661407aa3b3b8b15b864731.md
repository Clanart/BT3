### Title
Missing participant-index bounds check in PedPoP blame evaluation causes panic on out-of-range index - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

The OctoRPKI advisory (CVE-2021-3761) is a missing *contextual* bounds check: a value (`maxLength`) that is locally well-formed but out of range for the surrounding context propagates and kills the session. The Serai analog is in the PedPoP DKG blame path. `BlameMachine::blame_internal` and `AdditionalBlameMachine::blame` take `sender`/`recipient` `Participant` indexes supplied by an accusing counterparty and use them to index `self.commitments`, a `HashMap` that only contains indexes `1..=n`. There is no `sender <= n` / `recipient <= n` check before the `self.commitments[&sender]` lookup, so any accusation referencing a participant index outside the DKG roster panics instead of returning an error.

### Finding Description

`Commitments::read`, `EncryptedMessage::read`, and `SecretShare::read` all enforce *syntactic* validity of the bytes they parse (canonical points, `Participant::new` non-zero enforcement via borsh), but no contextual bound on the participant index is applied at the point of use in the blame flow:

- `AdditionalBlameMachine::new` populates `commitments` strictly with `Participant` indexes `1..=n` (lib.rs:656-660).
- `blame()` forwards attacker-influenced `sender`/`recipient` to `blame_internal` (lib.rs:674-682, 623-632).
- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, ...)` and then evaluates `self.commitments[&sender]` inside `share_verification_statements` (lib.rs:596-604).

A `Participant` can hold any non-zero `u16` — `Participant::new` only rejects zero — so `sender = Participant(n+1)` (or any value up to 65535) reaches `self.commitments[&sender]`, which panics on the absent key (`HashMap` index operator). The same gap exists for `recipient` in `share_verification_statements::<C>(recipient, ...)` and in the decryption path. Contrast with the properly-checked paths in the same crate: `validate_map` (lib.rs:57-83), `verify_r1`'s iteration over `all_participant_indexes()` (lib.rs:313), and `ThresholdKeys::view`'s explicit `u16::from(last) > n` check in `crypto/dkg/src/lib.rs:487-491`. The blame path is the one place the contextual bound was omitted.

This mirrors OctoRPKI precisely: a syntactically valid, attacker-chosen index (ROA `maxLength` / blame `sender`) that is out of bounds *for the local context* is not rejected, producing a crash-level failure rather than a clean fault attribution.

### Impact Explanation

Any DKG participant (or any party able to submit a blame accusation through the host protocol's `InvalidShare`/`blame` plumbing — see `ProcessorMessage::InvalidShare` handling in `processor/src/key_gen.rs:419-425`) can abort the key-generation / blame-resolution session by naming an out-of-range sender or recipient. Because `AdditionalBlameMachine` is explicitly designed for use by *any* evaluator ("capable of evaluating Blame regardless of if the caller was a member"), even non-participant evaluators can be crashed. The panic aborts the DKG, preventing the affected multisig from completing key generation or resolving fault attribution — an availability impact directly analogous to OctoRPKI's RTR session termination disabling origin validation. Note: the panic also aborts before `result` is consumed, so repeated attempts can keep the protocol stalled.

### Likelihood Explanation

The trigger requires only sending a blame/accusation message with a `Participant` index `> n`. No cryptographic forgery is needed: `Participant` deserialization enforces non-zero only, and `blame()` performs no `<= n` validation. Exploitability depends on the integrator relaying accuser-supplied indexes into `blame()` — the processor's `InvalidShare { faulty: i }` message path carries exactly such a peer-supplied index. One caveat I could not fully resolve within the available search scope: whether the processor sanitizes `faulty`/`accuser` to `1..=n` before invoking `blame()` (`processor/src/key_gen.rs` iterates shares only for `1..=n`, but the downstream blame dispatch was not fully inspected). The library-level defect is unconditional regardless of integrator behavior.

### Recommendation

Validate both `sender` and `recipient` at the top of `blame_internal` (and document it on `AdditionalBlameMachine::blame`):

```rust
// crypto/dkg/pedpop/src/lib.rs, in blame_internal
if (u16::from(sender) > self.commitments.len() as u16) ||
   (u16::from(recipient) > self.commitments.len() as u16)
{
  // treat out-of-range accuser/accused as a protocol fault rather than panicking
  return sender; // or a dedicated InvalidParticipant error
}
```

Prefer returning `Result<_, PedPoPError>` and adding `DkgError::InvalidParticipant` propagation so out-of-range indexes are attributed as faults instead of aborting the process. Apply the same bound inside `Encryption::decrypt_with_proof` if it indexes per-participant key material by `sender`.

### Proof of Concept

```rust
// Setup: a completed t-of-n PedPoP DKG, n = 3
let params = ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap();
// ... run generate_coefficients / generate_secret_shares / calculate_share to
// obtain a BlameMachine `bm` with commitments populated for participants 1..=3 ...

// Attacker-controlled accusation names a participant index outside the DKG
let oob_sender = Participant::new(4).unwrap(); // n = 3, so 4 is out of range
let msg: EncryptedMessage<C, SecretShare<C::F>> = /* any captured/encrypted share */;

// Panics at crypto/dkg/pedpop/src/lib.rs:599 on `self.commitments[&sender]`
// ("key not found") instead of returning a fault-attribution result.
let (_, faulty) = bm.blame(oob_sender, params.i(), msg, None);
```

Same trigger applies to `AdditionalBlameMachine::blame` (lib.rs:674) and to an out-of-range `recipient`. Severity: Medium–High (unauthenticated-in-protocol abort of the DKG; in validator deployments a peer-triggered panic takes the node down, analogous to the RTR session termination in CVE-2021-3761).
