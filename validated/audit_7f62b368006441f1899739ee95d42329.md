### Title
Missing bounds check on attacker-supplied `Participant` indexes in the PedPoP blame path causes a reachable panic (index-out-of-map crash) — (`File: crypto/dkg/pedpop/src/lib.rs`)

### Summary
The analog of ALPINE-CVE-2016-10192 ("failure to check chunk size" → memory corruption/crash) in Serai is a missing bounds/membership check on externally supplied `Participant` indexes in the DKG blame-resolution path. `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and the shared `blame_internal` helper index `self.commitments[&sender]` (and, inside `Decryption::decrypt_with_proof`, `self.enc_keys[&decryptor]`) with attacker-chosen indexes that were never validated against the registered participant set, causing a panic.

### Finding Description
`AdditionalBlameMachine::new` populates `commitments` and `Decryption::enc_keys` only for `Participant(1 ..= n)` (`crypto/dkg/pedpop/src/lib.rs:656-660`). However, `blame`/`blame_internal` accept `sender` and `recipient` from the caller — i.e., from an accusation message attributable to an unauthenticated/unprivileged party — and use them directly as map keys:

- `Decryption::decrypt_with_proof` does `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`), panicking if `recipient` is not a registered participant.
- `blame_internal` does `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`), panicking if `sender` is not in `1 ..= n`.

Unlike the honest share-processing path — which runs `validate_map` to bound the participant set before indexing (`crypto/dkg/pedpop/src/lib.rs:468-472`, `:490`) — the blame entry points perform no equivalent check, exactly mirroring the CVE's "process attacker-chosen size/index without validating it" defect. The result is a `HashMap` index panic in safe Rust (the memory-safe-language equivalent of the overflow/crash primitive).

### Impact Explanation
Any party able to submit a blame accusation (which by design can be raised by any participant, and `AdditionalBlameMachine` exists precisely so non-participants/third parties can evaluate blame) can crash the process evaluating the accusation by naming `sender` or `recipient` outside `1 ..= n` (e.g., `Participant(u16::MAX)`). This denies availability of the validator/processor during DKG fault resolution and prevents legitimate blame adjudication — an abort forced via malformed input, matching the CVE's class (unchecked externally supplied bound → crash).

### Likelihood Explanation
Reachable with public inputs only: the attacker controls the `sender`/`recipient` fields of an accusation, which are fed to `blame_internal` with no membership check. Triggering requires a single malformed accusation naming an out-of-range `Participant`; `Participant::new` accepts any nonzero `u16`, so indexes up to 65535 are representable while `n` is typically small. No collusion, key material, or privileged position is needed. The only mitigating factor is that impact is a panic (DoS), not memory corruption.

### Recommendation
Validate `sender` and `recipient` against the registered participant set at the top of `blame_internal` (e.g., return an error / blame the accuser when `!self.commitments.contains_key(&sender)` or `!self.encryption.enc_keys.contains_key(&recipient)`), mirroring the `validate_map` discipline used in `calculate_share`. Replace indexing (`map[&key]`) with `map.get(&key)` plus an explicit error in `blame_internal` and `Decryption::decrypt_with_proof` so malformed accusations cannot panic the evaluator.

### Proof of Concept
```rust
// In-scope path, e.g. crypto/dkg/pedpop tests:
// After a normal DKG with n participants, build the external blame evaluator:
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// Attacker submits an accusation naming a participant index > n.
// Participant::new accepts any nonzero u16, so this is a publicly craftable input.
let bogus_sender = Participant::new(n + 1).unwrap();
let real_recipient = Participant::new(1).unwrap();

// Path A: blame_internal indexes self.commitments[&sender] -> panic
// crypto/dkg/pedpop/src/lib.rs:599
machine.blame(bogus_sender, real_recipient, msg, proof);

// Path B: attacker claims to be an unregistered recipient;
// Decryption::decrypt_with_proof indexes self.enc_keys[&decryptor] -> panic
// crypto/dkg/pedpop/src/encryption.rs:388
let bogus_recipient = Participant::new(n + 1).unwrap();
machine.blame(real_sender, bogus_recipient, msg, Some(proof));
```

Both calls panic on the `HashMap` index (`map[&key]` returns `None` → panic on `Index` impl), aborting blame evaluation. Root cause: attacker-controlled participant indexes are used as map keys without a membership check, the direct analog of using an unchecked chunk size as a bound.
