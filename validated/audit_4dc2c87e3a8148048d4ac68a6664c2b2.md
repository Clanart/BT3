### Title
`WombatStaking.depositLP` mints receipt tokens based on the requested amount instead of the amount actually received - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.depositLP` transfers LP tokens from the caller and then mints receipt tokens and stakes to Master Wombat using the raw `_lpAmount` parameter, without ever measuring the balance actually received by the contract. This is inconsistent with the adjacent `deposit()` function in the same contract, which correctly measures `lpReceived` via a before/after balance diff before minting or crediting anything.

### Finding Description
In `WombatStaking.deposit()`, the contract correctly accounts for potential balance discrepancies by computing `lpReceived` from the actual before/after LP balance of the contract before minting receipt tokens: [1](#0-0) 

However, `WombatStaking.depositLP()` skips this safety measurement entirely. It calls `safeTransferFrom` and then immediately stakes and mints the receipt token using the raw `_lpAmount` argument as if it were guaranteed to equal the amount actually received: [2](#0-1) 

The staking call itself, `_stakeToWombatMaster`, also blindly approves and deposits `_lpAmount` to Master Wombat rather than the actual balance received: [3](#0-2) 

This is the exact fee-on-transfer/deflationary-token bug class described in the reference report: if the Wombat Asset (LP) token registered via `registerPool` (`wombat/WombatStaking.sol` lines 429-482) ever exhibits a transfer fee or rebasing/deflation on transfer — whether due to a future upgrade of that token or because such a token is later registered as a pool's LP address — the contract will receive `_lpAmount - fee` tokens but will mint `_lpAmount` receipt tokens and attempt to stake `_lpAmount` to Master Wombat, exceeding what it actually custodies.

### Impact Explanation
Receipt tokens are meant to be fully backed 1:1 by staked LP tokens, later redeemable via `withdraw()`/`burnReceiptToken()`. If `depositLP` mints more receipt tokens than LP actually held/staked, the backing invariant breaks: the pool becomes under-collateralized, and eventually some receipt token holders will be unable to redeem their share of LP tokens because the underlying LP balance is insufficient — a protocol insolvency / permanent freezing-of-funds condition affecting other, unrelated depositors, not just the token depositor. This is reachable purely by an ordinary wallet calling `depositLP` through a `PoolHelper` (e.g. `wombat/WombatPoolHelperV2.sol` `depositLP`), with no privileged action required beyond the token itself changing/being registered with fee-on-transfer behavior.

### Likelihood Explanation
Likelihood depends on a pool's LP token acquiring fee-on-transfer/deflationary behavior (or such a token being onboarded), matching the report's threat model exactly. There is no mitigation in `depositLP` (unlike `deposit()`, which already defends against this via balance-diff accounting), so once such a token exists in a pool, every `depositLP` call would silently over-mint receipt tokens.

### Recommendation
Mirror the pattern already used in `deposit()`: measure the actual balance received before and after the `safeTransferFrom` call in `depositLP`, and use that measured amount (not the caller-supplied `_lpAmount`) for staking, reward harvesting, and receipt token minting.

### Proof of Concept
1. Admin registers a pool whose LP/Asset token later becomes fee-on-transfer (or a fee-on-transfer-like token is registered), analogous to the original report's USDT scenario.
2. A user calls `depositLP(_lpAddress, 100, user)` via a `PoolHelper`.
3. `WombatStaking.depositLP` at [4](#0-3)  transfers LP tokens, but the contract only actually receives `100 - fee` due to the token's transfer fee.
4. Despite this, the contract stakes `100` to Master Wombat and mints `100` receipt tokens to the caller, exceeding the actual LP custodied.
5. Repeated deposits progressively decouple receipt token supply from actual LP backing, eventually causing withdrawal failures/insolvency for other receipt token holders.
