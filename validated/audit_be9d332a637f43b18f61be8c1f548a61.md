### Title
Partial-commit line selection is index-position-based and is blindly carried across diff refreshes, causing silent inclusion/exclusion of wrong lines when committing - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`DiffSelection` tracks a partial commit selection purely as a set of numeric line-indices (`divergingLines`) with no binding to the diff content or hash it was computed against. [1](#0-0)  When a fresh `git status`/diff refresh occurs, `updateChangedFiles` re-associates that same selection object onto the new `WorkingDirectoryFileChange` unconditionally via `file.withSelection(existingFile.selection)`, without checking whether the underlying diff (and therefore what each line-index actually refers to) has changed. [2](#0-1)  At commit time, `applyPatchToIndex` re-fetches a brand-new working-directory diff and feeds it to `formatPatch(file, diff)`, which interprets the stale selection's indices against this new diff's hunks via `file.selection.isSelected(absoluteIndex)`. [3](#0-2) [4](#0-3)  If the file's diff shape changed between the moment the user made their selection and the moment the commit runs, the same integer indices now point to different lines, so the wrong hunks/lines get staged and committed — silently, with no error and no re-validation.

### Finding Description
This is the structural analog of the wildcredit bug: a value (the reward share / here, the "selected lines") is computed against one snapshot of shared/mutable state (total supply / here, the diff's line layout) and is later applied against a different, already-mutated snapshot of that same state, without re-synchronizing the two.

Concretely:
1. The user opens a file's diff and makes a partial selection (e.g. via `withLineSelection`/`withRangeSelection`) — this selection is stored purely as line-index offsets (`divergingLines: Set<number>`), with no reference to file content, hash, or the specific diff it was derived from. [5](#0-4) 
2. GitHub Desktop periodically/automatically refreshes repository status (`_loadStatus` → `updateChangedFiles`), and by default preserves the existing selection object across refreshes as long as the file id (its path) is still present, regardless of whether the file's diff has changed shape: `return file.withSelection(existingFile.selection)`. [2](#0-1) 
3. When the commit is finally executed, `_commitIncludedChanges` reads the (possibly stale) `WorkingDirectoryFileChange.selection` from the state cache and hands it to `createCommit` → `stageFiles` → `applyPatchToIndex`. [6](#0-5) [7](#0-6) 
4. `applyPatchToIndex` fetches a **fresh** diff from disk at commit time (`getWorkingDirectoryDiff`) — not the diff the user actually reviewed — and generates the patch by testing `file.selection.isSelected(absoluteIndex)` for every line of the new diff. [8](#0-7)  Since the indices in the stale selection no longer correspond to the same semantic lines, `formatPatch` can select unrelated additions/deletions or drop lines the user actually wanted included. [9](#0-8) 

There is no guard anywhere in this path that detects a diff/selection mismatch — `DiffSelection` has no notion of "this selection is only valid for diff X" and `formatPatch` will happily throw only if the resulting patch is completely empty, not if it partially mismatches. [10](#0-9) 

### Impact Explanation
This can cause silent corruption of what the user commits: lines the user explicitly deselected in the UI can end up staged/committed, and lines they selected can be silently dropped, with no warning, if the on-disk content of a file changes (e.g. via a background process, editor autosave, build tool, or a git filter/hook triggered by the repository itself) between the time the user builds their partial selection and the time they click "Commit". Because Desktop's status/diff refresh cycle is automatic and not tied to user action, this window is realistically reachable without any unusual user steps, and the corrupted commit is pushed as-is unless the user manually re-diffs the resulting commit.

### Likelihood Explanation
Desktop refreshes repository status on a recurring interval, on window focus, and after many git operations, all of which call `_loadStatus`/`updateChangedFiles`, and `clearPartialState` is `false` in most of these refresh paths, meaning partial selections are deliberately preserved across them. [11](#0-10)  Any external process that can modify a tracked file underneath the working directory during the ordinary UI flow (something a malicious repository can arrange via a git hook, a `clean`/`smudge` filter defined in `.gitattributes`, or a checked-in tool the user is expected to run) can shift diff hunk boundaries and trigger this mismatch. No admin rights, local access, or unnatural user interaction is required beyond the normal "select some lines, then commit" workflow.

### Recommendation
Bind a `DiffSelection` to the diff it was computed against (e.g. store a content hash or the diff's structural signature alongside the selection) and invalidate/reconcile the selection whenever the underlying diff for a file changes shape, rather than blindly transplanting `existingFile.selection` onto the new file object in `updateChangedFiles`. At minimum, before generating the commit patch in `applyPatchToIndex`, verify the freshly fetched diff still matches the diff the selection was built against (e.g. compare hunk boundaries/line counts or a hash of the diff text) and refuse to commit / prompt the user to re-review if it does not.

### Proof of Concept
1. Open a repository in GitHub Desktop and modify a tracked file such that the working-directory diff has multiple hunks.
2. In the Changes view, use partial line selection to select only specific lines/hunks (this creates a `DiffSelection` with `divergingLines` referencing specific absolute indices). [5](#0-4) 
3. Before clicking "Commit," have an external process (simulating a malicious repo-provided hook/filter/build script) rewrite the same file so the diff's hunk layout shifts (lines added/removed earlier in the file, changing subsequent line indices). Desktop's periodic/background refresh calls `updateChangedFiles`, which reuses the old selection object unchanged on the new file object. [2](#0-1) 
4. Click "Commit." `applyPatchToIndex` fetches the new diff and applies the stale index-based selection to it via `formatPatch`. [3](#0-2) 
5. Inspect the resulting commit: it will include/exclude lines that do not correspond to what was visually selected in the UI before the file changed, confirming silent corruption of the committed content.

*Note: I was not able to execute this scenario end-to-end in a live Desktop instance (no filesystem/terminal access in this environment); the analysis above is based on tracing the exact code paths (`DiffSelection`, `updateChangedFiles`, `_commitIncludedChanges`, `applyPatchToIndex`, `formatPatch`) that together implement this selection lifecycle. A background Devin session with repo/terminal access would be needed to run the concrete PoC and confirm the exact commit diff produced.*

   *
   * @param from     The line index (inclusive) from where to start
   *                 updating the line selection state.
   *
   * @param to       The number of lines for which to update the
   *                 selection state. A value of zero means no lines
   *                 are updated and a value of 1 means only the
   *                 line given by lineIndex will be updated.
   *
   * @param selected Whether the lines should be marked as selected
   *                 or not.
   */
  // Lower inclusive, upper exclusive. Same as substring
  public withRangeSelection(
    from: number,
    length: number,
    selected: boolean
  ): DiffSelection {
    const computedSelectionType = this.getSelectionType()
    const to = from + length

    // Nothing for us to do here. This state is when all lines are already
    // selected and we're being asked to select more or when no lines are
    // selected and we're being asked to unselect something.
    if (typeMatchesSelection(computedSelectionType, selected)) {
      return this
    }

    if (computedSelectionType === DiffSelectionType.Partial) {
      const newDivergingLines = new Set<number>(this.divergingLines!)

      if (typeMatchesSelection(this.defaultSelectionType, selected)) {
        for (let i = from; i < to; i++) {
          newDivergingLines.delete(i)
        }
      } else {
        for (let i = from; i < to; i++) {
          // Ensure it's selectable
          if (this.isSelectable(i)) {
            newDivergingLines.add(i)
          }
        }
      }

      return new DiffSelection(
        this.defaultSelectionType,
        newDivergingLines.size === 0 ? null : newDivergingLines,
        this.selectableLines
      )
    } else {
      const newDivergingLines = new Set<number>()
      for (let i = from; i < to; i++) {
        if (this.isSelectable(i)) {
          newDivergingLines.add(i)
        }
      }

      return new DiffSelection(
        computedSelectionType,
        newDivergingLines,
        this.selectableLines
      )
    }
  }

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
