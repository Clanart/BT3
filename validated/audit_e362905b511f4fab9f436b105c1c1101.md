### Title
Native-token balance of a CN staking contract is used directly as its consensus staking weight, allowing any unprivileged sender to inflate a validator's proposer weight and reward share by simply transferring KAIA to it - ([File: kaiax/staking/impl/getter.go])

### Summary
The `kaiax/staking` module computes each validator's `StakingAmounts` from the raw native-token balance of the registered CN staking address, not from any internally tracked/locked "staked" amount. Because the corresponding `CnStakingV4`/legacy CN staking contracts expose a public `payable receive()`, any unprivileged account can send a plain value-transfer transaction to a publicly known CN staking address (obtained from the on-chain AddressBook) and thereby increase that node's reported `StakingAmount` used for validator qualification, weighted-random proposer selection, and KIP-82/flex reward distribution — exactly the same balance-based "voting power" flaw described in the external report, just applied to Kaia's staking/consensus weight instead of ERC20Votes.

### Finding Description
`StakingModule.getFromState` builds `StakingInfo.StakingAmounts` by calling the MultiCall contract, which reads the AddressBook's triplets (node/staking/reward addresses) and pulls the staking amount from each `CN_STAKING_ADDRESS_TYPE` entry's balance: [1](#0-0) 

This is confirmed by the unit test that fabricates `StakingInfo` purely by setting `Balance` on the staking addresses in `GenesisAlloc`, with no staking-contract-internal "stake" bookkeeping involved: [2](#0-1) 

The README explicitly documents that `StakingInfo` is derived from "all the staking contracts registered in the AddressBook, and their native token balances": [3](#0-2) 

The staking contract itself (`CnStakingV4`) has a public payable `receive()` function that anyone can call/transfer KAIA to, unrelated to the contract's own accounted `staking`/`unstaking` fields or its `STAKE_LOCKUP`/withdrawal-approval flow: [4](#0-3) 

Because the consensus/reward layer only ever reads `address.Balance` (not the contract's internal `staking` counter or any lockup-gated accounting), a plain KAIA transfer from any account — no special privileges required — permanently (until an admin explicitly withdraws it, subject to `approveStakingWithdrawal`/`STAKE_LOCKUP`) raises the balance-derived `StakingAmount` used by:
- Validator qualification/demotion thresholds (`reward.minstake`), used in `kaiax/valset` to decide `QualifiedValidators`/`DemotedValidators`.
- Weighted-random proposer selection weights, computed directly from `collectStakingAmounts`/`generateProposerListWeighted`: [5](#0-4) 
- KIP-82/Flex staking reward allocation, which distributes the staking-reward budget proportionally to each CN's excess stake over `minStake`/threshold: [6](#0-5) 

Since the multicall/state read (`getFromState`) queries the *live account balance* rather than any application-level ledger, this is bypassable not only via a normal transfer but even via a forced send (e.g. `SELFDESTRUCT` beneficiary) that skips `receive()` entirely — the state read cannot distinguish "intentionally staked" funds from arbitrary donations or forced balance increases.

### Impact Explanation
An unprivileged sender can, with a single ordinary transaction, inflate the reported staking amount of any CN whose staking address is public (visible via the AddressBook). This:
1. Can push a CN over the `reward.minstake` threshold, changing `QualifiedValidators`/`DemotedValidators` and thus the committee/proposer set used for block production and consensus — a state input that all honest nodes must derive identically, so any account can unilaterally alter which validators participate in consensus without those validators' consent.
2. Skews the weighted-random proposer probability distribution (`generateProposerListWeighted`) in favor of whichever CN receives the donation, letting a third party bias block-proposer selection toward a chosen validator (e.g., to help a colluding validator capture more MEV/fees) without any staking lockup or governance approval.
3. Redirects a larger share of the fixed per-block staking-reward budget to the inflated CN at the expense of the other, honest validators' expected rewards (`assignStakingRewards`), since the pool is fixed and split proportionally by excess stake — this is a concrete reward-redirection/value-movement impact between validators triggered purely by a public, unprivileged transaction.

The attacker's own funds sent are not necessarily lost — because the increase is a raw balance increase, it is only reclaimable through the target CN admin's own withdrawal flow (`approveStakingWithdrawal`/`STAKE_LOCKUP`), so a non-colluding attacker griefs by spending real capital, while a colluding attacker/validator pair can deliberately shuttle temporary balance in right before a `StakingInfo` snapshot (once per `StakingInterval` before the Kaia hardfork, or every block after) to game proposer selection or rewards for an entire interval, and reclaim/adjust afterward subject to the lockup.

### Likelihood Explanation
Likelihood is Medium: the mechanism requires no special access — any account can send a value-transfer transaction to a public CN staking address using funds it owns — but exploiting it for material gain requires either (a) collusion with the benefiting validator (to recoup value or split proposer/reward gains) or (b) accepting the cost as pure griefing to demote/promote/skew a target validator's consensus weight. The staking-address list is public via the AddressBook, and no permission checks exist in the balance-reading path (`getFromState`/`parseCallResult`), so the technical barrier to triggering the effect is essentially zero.

### Recommendation
- Derive `StakingAmounts` from an explicit, contract-tracked "staked" ledger value (e.g., the CN staking contract's own `staking` variable, net of pending `unstaking`/withdrawal-approved amounts) rather than the raw account balance, so that funds must go through the contract's staking/lockup accounting to count toward consensus weight.
- If balance-based accounting must be retained for backward compatibility, snapshot/require a minimum holding duration (tied to `STAKE_LOCKUP`) before a balance increase is reflected in `StakingInfo`, preventing just-in-time balance injection around `StakingInfo` snapshot blocks.
- Add monitoring/alerts for CN staking address balance deltas that do not correspond to tracked `staking`/`unstaking` contract state transitions.

### Proof of Concept
1. Query the AddressBook (`0x...0400`) via `getAllAddress()` to obtain the list of `CN_STAKING_ADDRESS_TYPE` entries (all public, e.g. as exercised in `contracts/testing/system_contracts/MultiCallContractMock.sol`).
2. From any unprivileged account, send a plain KAIA transfer (or, more forcefully, deploy a helper contract and call `SELFDESTRUCT` designating the target CN staking address as beneficiary) to one of these staking addresses.
3. Observe that `kaia_getStakingInfo` (backed by `StakingModule.GetStakingInfo` → `getFromState` → `parseCallResult`, which divides the raw balance by `params.KAIA`) reports an increased `councilStakingAmounts` for that CN at the next `SourceBlockNum`, as shown by the balance-driven expectations in `TestGetStakingInfo_Uncached`: [7](#0-6) 
4. This increased amount is then consumed unchanged by `kaiax/valset`'s qualification/demotion logic and weighted proposer generation, and by `kaiax/reward`'s `assignStakingRewards`, changing consensus committee membership eligibility, proposer selection probability, and reward split — all triggered solely by the attacker's single value-transfer transaction.

func generateProposerListWeighted(qualified *valset.AddressSet, si *staking.StakingInfo, useGini bool, blockHash common.Hash) []common.Address {
	var (
		addrs          = qualified.List()
		stakingAmounts = collectStakingAmounts(addrs, si)
		gini           = computeGini(stakingAmounts) // si.Gini is computed over every CN. But we want gini among validators, so we calculate here.
		exponent       = 1.0 / (1 + gini)
		totalStakes    = float64(0)
	)

	// Adjust staking amounts and calculate the sum
	if useGini {
		for addr, amount := range stakingAmounts {
			stakingAmounts[addr] = math.Round(math.Pow(float64(amount), exponent))
			totalStakes += stakingAmounts[addr]
		}
	} else {
		for _, amount := range stakingAmounts {
			totalStakes += amount
		}
	}

	// Calculate percentile weights
	weights := make(map[common.Address]uint64)
	if totalStakes > 0 {
		for _, addr := range addrs {
			weight := uint64(math.Round(stakingAmounts[addr] * 100 / totalStakes))
			if weight <= 0 {
				weight = 1
			}
			weights[addr] = weight
		}
	} else {
		for _, addr := range addrs {
			weights[addr] = 0
		}
	}

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
