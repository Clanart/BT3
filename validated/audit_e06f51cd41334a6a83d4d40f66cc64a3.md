### Title
Cross-shop session confusion via unauthenticated `params[:shop]` in `EnsureInstalled#current_shopify_domain`/`#installed_shop_session` - (File: `app/controllers/concerns/shopify_app/ensure_installed.rb`)

### Summary
When the legacy (non-token-exchange) embedded auth strategy is active, `EnsureInstalled#current_shopify_domain` derives the "installed store" solely from the unauthenticated `params[:shop]` value, with no HMAC or JWT/id_token verification anywhere in the concern. `installed_shop_session` then retrieves and uses the stored offline session for that domain, and `validate_non_embedded_session` immediately performs a real `ShopifyAPI::Clients::Rest::Admin` API call using that session/access token before any signature-based check ever runs.

### Finding Description
The call chain is: `check_shop_domain` → `current_shopify_domain` (sanitizes but does not authenticate `params[:shop]`) [1](#0-0) , then `check_shop_known` → `installed_shop_session` → `SessionRepository.retrieve_shop_session_by_shopify_domain(current_shopify_domain)` [2](#0-1) , then `validate_non_embedded_session`, which — unless the request looks "loaded directly from admin" (`params[:embedded] == "1"`) — builds `ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)` and issues `client.get(path: "shop")` [3](#0-2) .

None of `check_shop_domain`, `check_shop_known`, or `validate_non_embedded_session` verify that the caller actually holds any credential tying it to shop B (no HMAC check, no session-token/id_token verification — that path is only present in the `use_new_embedded_auth_strategy?` branch via `TokenExchange`/`activate_shopify_session`) [4](#0-3) . `embedded_param?`/`loaded_directly_from_admin?` only gate whether the browser is redirected for embedding; they do not gate whether the Admin API call is made — in fact when the request is *not* "loaded directly from admin" (i.e., the more attacker-natural case of a plain top-level GET), the API call in `validate_non_embedded_session` runs unconditionally [5](#0-4) .

Consequently, any anonymous requester who knows (or guesses) a previously-installed shop's `myshopify.com` domain can issue `GET /any_ensure_installed_route?shop=shopB.myshopify.com` and cause the app server to load shop B's stored offline session and perform a real Shopify Admin REST call (`GET /admin/api/.../shop.json`) using shop B's access token — entirely driven by the unauthenticated `shop` query parameter, with no proof that the requester is shop B or is even inside Shopify's admin iframe. This breaks the SESSION_BINDING invariant: the session used to talk to Shopify is derived from a raw request parameter rather than a verified token (id_token/JWT or HMAC-signed OAuth callback).

Comparable protections that exist elsewhere in the gem — `AppProxyVerification#query_string_valid?` (HMAC-signed query string) and `PayloadVerification#hmac_valid?` (webhook HMAC) [6](#0-5) [7](#0-6)  — are not applied in `EnsureInstalled`, confirming that the legacy embedded-app flow relies purely on the assumption that the browser is embedded inside Shopify Admin (an assumption enforced, if at all, only by CSP `frame-ancestors`/`X-Frame-Options` set by `FrameAncestors`, not by anything in this concern, and not effective against a direct non-embedded HTTP request).

### Impact Explanation
An attacker can force the app server to consume a victim shop's real offline access token to make outbound Shopify Admin API calls on demand, purely by supplying that shop's domain as a query parameter to any `EnsureInstalled`-protected route. Concrete impact is bounded by what `validate_non_embedded_session` itself does (a `GET shop` call) plus whatever the wrapping controller action does with `installed_shop_session`/`@shop` for its own business logic — if that action fetches and renders shop-specific data (orders, customers, settings) using the session, this becomes full cross-shop data exposure; at minimum it is unauthorized use of another shop's access token / API quota (a scoped side-channel/rate-limit-exhaustion issue), matching Shopify's "Improper Access Control" / "Broken Authentication" impact class.

### Likelihood Explanation
Preconditions are modest and realistic: the target app must include `EnsureInstalled` (a very common concern for protecting embedded-app routes), must use the legacy embedded auth strategy (`use_new_embedded_auth_strategy?` false — this is still the default/common configuration for existing apps, since the token-exchange strategy is the newer opt-in path) [8](#0-7) , and shop B must have previously installed the app (so a session exists to retrieve). No secrets, tokens, or victim interaction are required — an attacker only needs to guess or discover a shop domain that has installed the app, which is often derivable from public storefronts. This makes the attack trivially repeatable via a single unauthenticated HTTP GET.

### Recommendation
Do not derive `current_shopify_domain`/`installed_shop_session` from raw `params[:shop]` alone in the legacy flow. Require verification of the shop identity before binding to a stored session — e.g., validate an id_token/session token when present, or require an HMAC-signed request (similar to `AppProxyVerification`/OAuth callback validation) for any route that will use `installed_shop_session` to make outbound Admin API calls. At minimum, gate `validate_non_embedded_session`'s API call behind proof that the request originated from Shopify Admin for that specific shop (not just an unauthenticated query parameter), and migrate consumers to `use_new_embedded_auth_strategy?`/`TokenExchange`, which does perform id_token verification.

```ruby
class EnsureInstalledCrossShopController < ActionController::Base

class EnsureInstalledCrossShopTest < ActionController::TestCase
  tests EnsureInstalledCrossShopController

  setup do
    ShopifyApp.configuration.use_new_embedded_auth_strategy = false
    # Pre-install "victim" shop B and store its offline session/token.
    @victim_domain = "shopb.myshopify.com"
    ShopifyApp::SessionRepository.store_shop_session(
      ShopifyAPI::Auth::Session.new(shop: @victim_domain, access_token: "victim-token"),
    )
  end

  test "anonymous request with unrelated shop param triggers Admin API call using victim's session" do
    with_application_test_routes do
      # Attacker never authenticated as shop B, holds no token/id_token/HMAC for shop B.
      admin_client_mock = mock
      admin_client_mock.expects(:get).with(path: "shop") # THIS SHOULD NOT HAPPEN for an unverified caller
      ShopifyAPI::Clients::Rest::Admin.expects(:new)
        .with(session: instance_of(ShopifyAPI::Auth::Session))
        .returns(admin_client_mock)

      get :index, params: { shop: @victim_domain } # no host, no embedded=1, no hmac, no id_token
      # Expected (secure) behavior: request should be rejected/redirected without ever
      # invoking ShopifyAPI::Clients::Rest::Admin with shop B's session.
      # Actual behavior: the mocked Admin client IS invoked with shop B's real session.
    end
  end
end
```
This reproduces the flow described in the finding: `check_shop_domain` → `current_shopify_domain` (trusts `params[:shop]`) → `check_shop_known` → `installed_shop_session` (retrieves shop B's session) → `validate_non_embedded_session` (invokes `ShopifyAPI::Clients::Rest::Admin` with shop B's session) — all without any check binding the request to a verified shop-B credential.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
