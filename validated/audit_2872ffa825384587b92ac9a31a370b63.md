### Title
Untrusted `ReceivedOutput` fields are signed without validation, allowing a fabricated prevout value to burn multisig funds as fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the SymmIO report — where a suspended account's stale quotes were still accepted and used to move funds — `SignableTransaction`/`TransactionSignMachine` accept a `ReceivedOutput` parsed from untrusted bytes (`ReceivedOutput::read`, `networks/bitcoin/src/wallet/mod.rs:122-134`) and sign a Taproot sighash committing to *all* of its fields (`Prevouts::All`, `send.rs:375-386`) after only validating the `script_pubkey`/offset correspondence (`send.rs:277`). The `value` and `outpoint` of the claimed prevout are never checked against anything. A party supplying a serialized `ReceivedOutput` with the multisig's real script but a fabricated `value` causes the threshold to produce a valid BIP-340 signature over a false input amount — an unintended message signature whose consequences range from invalid transactions to real funds being destroyed as excess miner fees.

### Finding Description
- `ReceivedOutput::read` (`wallet/mod.rs:122-134`) deserializes `offset`, an arbitrary `TxOut` (including `value` and `script_pubkey`), and an arbitrary `OutPoint` with zero consistency checks — it is an explicitly exposed untrusted-bytes parser.
- `SignableTransaction::new` (`send.rs:150-256`) consumes these outputs, summing `input.output.value` (`send.rs:175`) to decide payments/change/fee. The claimed values drive `needed_fee`, change computation (`send.rs:224-234`), and are stored verbatim into `prevouts` (`send.rs:253`).
- `SignableTransaction::multisig` (`send.rs:273-285`) is the only validation point, and it checks *only* that `p2tr_script_buf(key + offset·G) == prevout.script_pubkey` (`send.rs:277`). `value` and `outpoint` are unchecked.
- `TransactionSignMachine::sign` (`send.rs:373-397`) then computes `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), Default)` — the BIP-341 sighash commits to every prevout's `script_pubkey` **and `value`**, plus each input's outpoint. Every signer signs whatever values were supplied in the untrusted bytes.

Like the SymmIO finding, a pre-existing artifact (a deposited output / pending quote) is acted upon without re-validating the fields that matter: the suspended account's quotes were honored as-is; here the claimed prevout amount is honored as-is.

### Impact Explanation
If any path in Serai relays serialized `ReceivedOutput`s between parties (coordinator → validators, or any persisted/replayed encoding — `ReceivedOutput::read`/`write`/`serialize` exist precisely for transport), the supplier controls the signed sighash's committed amount:

- **Understated value**: if the real UTXO is worth more than claimed, `sum(inputs) - sum(outputs)` exceeds the intended fee; the signed transaction is valid and burns the difference to miners. Repeated across many inputs this destroys multisig funds — "funds moved out" via an artifact the system accepted without verification.
- **Overstated value**: signatures commit to nonexistent funds; the transaction is invalid — liveness loss and wasted signing rounds.
- The signature itself is a valid BIP-340 signature for `key + offset·G` over a message the signers did not intend — "concrete signing of an unintended message."

This does not require threshold collusion, a malicious validator set, or key compromise — only control of the bytes fed to `ReceivedOutput::read`/`SignableTransaction::new`.

### Likelihood Explanation
`ReceivedOutput::read` is a public, `#[cfg(feature = "std")]` deserialization API explicitly intended for untrusted streams, and `multisig`'s single `script_pubkey` check (`send.rs:277`) demonstrates the authors intended to validate the untrusted object — they simply validated only one of its three security-relevant fields. Whether a reachable coordinator→validator path exists in the full processor is outside the in-scope crates and could not be fully verified; within scope, the signature over attacker-chosen prevout values is unconditional once `read`/`new`/`multisig`/`sign` are invoked, so likelihood hinges on how `ReceivedOutput`s are transported, i.e. Medium-level exposure.

### Recommendation
- Make `SignableTransaction::multisig` (or a `ReceivedOutput` validity check) verify the `outpoint` resolves to a known scanned output — e.g., require `ReceivedOutput`s only be built via `Scanner::scan_transaction`/`scan_block`, or store a keyed hash of `(outpoint, script_pubkey, value)` produced by the scanner and verify on `read`.
- At minimum, have `TransactionSignMachine::sign`/`multisig` cross-check `prevout.value` and `outpoint` against locally confirmed chain data (an RPC `gettxout`-style check) before signing, so the sighash never commits to unverified amounts.
- Document on `ReceivedOutput::read` that the parsed object must be re-validated against chain state before being passed to `SignableTransaction::new`.

### Proof of Concept
1. Obtain a genuine deposit: `Scanner::new(key)` → `scan_transaction` yields a real `ReceivedOutput{offset: 0, output: TxOut{script_pubkey: S, value: 100_000}, outpoint: P}`.
2. Attacker serializes a modified copy via `ReceivedOutput::write`/handcrafted bytes: `offset = 0`, `TxOut{script_pubkey: S, value: 10_000}`, `outpoint: P` — value understated.
3. A consumer does `ReceivedOutput::read(bytes)` → `SignableTransaction::new(vec![ro], payments, change, data, fee)` → `multisig(&keys)` — the check `p2tr_script_buf(key) == S` passes since only the value differs → `Ok(TransactionMachine)`.
4. Normal FROST rounds run; `sign` computes the BIP-341 sighash with `Prevouts::All` committing to `value = 10_000`. The resulting transaction is consensus-valid (real UTXO worth 100_000) but pays `90_000 - outputs` as miner fees — funds destroyed via a signature over an unintended message.
