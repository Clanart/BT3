## Analysis

The Pickle Finance report describes an *uncontrolled, unauthenticated call of another contract's functions*, where an unprivileged actor can pass attacker-controlled `_data`/`_target` and have it executed with the calling contract's own privileges/identity. The direct Hyperbridge analog is the `CallDispatcher` contract, which is a **single, unauthenticated, permissionless executor** shared by every order that flows through `IntentGatewayV2`.

`CallDispatcher.dispatch()` has zero access control — anyone can call it, and it executes `to.call{value}(data)` with `CallDispatcher` itself as `msg.sender`: [1](#0-0) 

`IntentsBase._execute` forwards the **order creator's own attacker-controlled `order.output.call` bytes** straight into this shared dispatcher, then only sweeps back the token addresses that belong to *that specific order's* `outputsLen` set: [2](#0-1) 

Because `order.output.call` is fully attacker-controlled by whoever places the order, and the dispatcher is one shared instance for the whole gateway (`Params.dispatcher`), any user can place an order whose calldata makes `CallDispatcher` grant an ERC20 `approve()` to an attacker-controlled address, for a token that isn't even part of that order's own outputs — so the sweep logic never touches it and the approval is left dangling indefinitely. The test suite confirms this residual-approval behavior is real and persists after execution: [3](#0-2) 

The dispatcher can also be set as the direct `beneficiary` of an order's output tokens (a supported pattern used for swap-then-forward calldata), meaning real user/solver funds transiently land on the same shared contract that the attacker already poisoned with a standing approval: [4](#0-3) 

### Title
Unauthenticated shared `CallDispatcher` allows an attacker to plant a standing token approval and later drain unrelated orders' output tokens - (File: evm/src/utils/CallDispatcher.sol, evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated function that executes arbitrary `Call[]` with the dispatcher's own identity as caller. It is a single shared singleton used across all orders in `IntentGatewayV2` (`Params.dispatcher`). Order creators fully control the `order.output.call` bytes executed against this shared contract via `IntentsBase._execute`. Because the post-execution dust-sweep in `_execute` only inspects the token addresses belonging to the *current* order's `outputsLen`, an attacker can use their own order's calldata to make the dispatcher `approve()` an unrelated token to an attacker-controlled spender, and that approval survives untouched. Whenever the dispatcher later holds a balance of that token — for example, because a different order sets `beneficiary = dispatcher` for swap-then-forward postdispatch logic, or a predispatch swap output isn't yet pulled back — the attacker can call `token.transferFrom(dispatcher, attacker, amount)` directly, with no interaction with `IntentGatewayV2` at all.

### Finding Description
1. `CallDispatcher.dispatch(bytes memory encoded)` has no caller restriction — any account, including the order placer or any solver, can call it directly, and it will `to.call{value: call.value}(call.data)` as itself. [5](#0-4) 
2. `IntentsBase._execute` passes `order.output.call` — data chosen entirely by the (unprivileged) order creator at `placeOrder` time — into `ICallDispatcher(dispatcher).dispatch(...)`. [6](#0-5) 
3. After dispatching, the function only sweeps balances of the tokens listed in `order.output.assets` for that particular order (`outputsLen`). Any other token the malicious calldata touched (e.g. an `approve()` on a completely different ERC20) is left untouched on the dispatcher. [7](#0-6) 
4. The foundry test suite independently confirms that approvals granted via postdispatch calldata remain non-zero on the dispatcher after a fill completes rather than being reset. [8](#0-7) 
5. `dispatcher` can legitimately be set as an order's `beneficiary`, so real settlement funds pass through and rest (even momentarily) on the same shared, unauthenticated contract. [4](#0-3) 

No guard exists that scopes an order's calldata effects/approvals to only the tokens/assets of that order, and no guard exists preventing an unrelated, unprivileged third party from invoking `CallDispatcher` directly outside the gateway's control flow.

### Impact Explanation
This breaks the "bridged assets/order escrow must move exactly once and only to the rightful beneficiary and amount" invariant. A single cheap, self-filled malicious order can plant a standing `approve()` from the shared `CallDispatcher` to an attacker address for an arbitrary token. Any future balance of that token that transits through the same dispatcher — from any other user's order, using the same `IntentGatewayV2` deployment — can be pulled out directly via `transferFrom`, bypassing all of the gateway's beneficiary/amount accounting. This is unauthorized transaction/execution and outright fund theft affecting third parties, not just the attacker's own order.

### Likelihood Explanation
High. Placing an order with attacker-chosen `output.call` and self-filling it (or getting anyone to fill it, since output requirements can be trivially small) is a fully public, unprivileged, single-transaction action requiring no relayer/prover/governance/admin compromise. The dangling-approval condition is directly exercised by the existing test suite, confirming it is not a hypothetical edge case but observed contract behavior.

### Recommendation
- Restrict `CallDispatcher.dispatch()` so it can only be invoked by the specific app/gateway instance that owns it for the current in-flight order (e.g., pass an authorized caller check, or deploy/derive a dispatcher scoped per-order/per-call rather than a shared singleton).
- After executing attached calldata, revoke/zero out any approvals the dispatcher granted during that call (not just sweep known output-asset balances), or restrict what selectors/targets order calldata may invoke (e.g., disallow `approve`/`increaseAllowance` outright).
- Ensure the dust-sweep logic inspects *all* balances/approvals the dispatcher's calls touched, not only the current order's declared output assets.

### Proof of Concept
1. Attacker deploys `EvilSpender` and places `orderA` with a tiny/self-fillable output, setting `output.call = abi.encode([Call{to: TOKEN_X, value: 0, data: approve(EvilSpender, type(uint256).max)}])`.
2. Attacker (or any solver) fills `orderA`. `_execute` invokes `CallDispatcher.dispatch(orderA.output.call)`, which sets `TOKEN_X.approve(EvilSpender, max)` from the dispatcher. Since `TOKEN_X` is not in `orderA.output.assets`, the subsequent sweep loop never touches or revokes it. (Confirmed pattern per `IntentGatewayV2SameChainTest.sol` L1521-1540.)
3. Later, an unrelated `orderB` from a different user specifies `beneficiary = dispatcher` and `output.assets[0].token = TOKEN_X` (a legitimate swap-then-forward pattern, per `IntentGatewayV2Test.sol` L1245-1253). A solver fills `orderB`; `TOKEN_X` briefly sits on the dispatcher before `orderB`'s own postdispatch call forwards it onward — or `orderB` has no calldata at all, in which case `_execute` returns immediately (`order.output.call.length == 0`) and the tokens are never swept/forwarded, remaining on the dispatcher indefinitely.
4. Attacker calls `TOKEN_X.transferFrom(dispatcher, EvilSpender, amount)` directly using the standing approval from step 2 — no interaction with `IntentGatewayV2` needed — draining funds intended for `orderB`'s beneficiary.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
