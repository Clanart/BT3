## Confirmed Local Analog

The `CallDispatcher` contract used by `IntentGatewayV2` / `IntentsBase` for both predispatch (swap-then-escrow) and postdispatch (fill-then-act) calldata execution is a single, shared, unauthenticated contract, and the sweep logic that is supposed to reclaim leftover tokens only sweeps tokens explicitly listed in the order — this is the direct local analog to the Executor.sol "stuck tokens" report, but with a stronger, unprivileged exploitation path.

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain tokens stranded by incomplete sweep lists - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` has no caller restriction at all, and it is a single shared contract referenced by `_params.dispatcher` across every order's predispatch/postdispatch calldata execution. Both `IntentGatewayV2._placeOrder` (predispatch) and `IntentsBase._execute` (postdispatch) only sweep back tokens that appear in the order's declared `inputs`/`output.assets` list. Any token balance the dispatcher ends up holding that is not on that declared list is left behind — exactly the "tokens stuck because the recipient/executor doesn't consume/claim them all" pattern from the external report — except here the leftover balance can be swept by literally anyone, since `dispatch()` is a public external function with no access control.

### Finding Description
`evm/src/utils/CallDispatcher.sol:44-62`: [1](#0-0) 
`dispatch()` decodes an attacker-supplied `Call[]` and executes each call with the dispatcher's own balance/allowance, with **no `msg.sender` check whatsoever** — anyone can call it directly (it is not restricted to `IntentGatewayV2` or any owner).

Meanwhile, the sweep logic in `IntentsBase._execute` (postdispatch) only iterates over the tokens declared in `order.output.assets`: [2](#0-1) 

And the predispatch sweep in `IntentGatewayV2._placeOrder` likewise only sweeps tokens declared in `order.inputs`: [3](#0-2) 

Both flows execute **arbitrary, order-author-controlled calldata** (`order.predispatch.call` / `order.output.call`) through the dispatcher. If that calldata routes through a DEX, lending protocol, or any external contract that produces a byproduct token, refund, reward, or dust in a token not enumerated in `inputs`/`output.assets`, that balance is never included in the sweep-back `Call[]` construction and is left sitting on the dispatcher indefinitely.

Because `dispatch()` has no access control, that stranded balance is not merely "unclaimed protocol dust" (as in Connext's Executor, where the team explicitly decided "any funds left ... are claimable by anyone" but at least required deliberate governance/owner action) — it is immediately and permanently grabbable by any unprivileged external account, at any time, by calling `CallDispatcher.dispatch()` directly with `Call{to: strandedToken, data: transfer(attacker, balance)}`. No proof, no relayer, no gateway interaction is required.

### Impact Explanation
This is a direct fund-loss / wrong-beneficiary primitive: value that should ultimately belong either to the protocol (as dust, later reclaimed via the `SweepDust` governance path) or to legitimate order participants can be permanently diverted to an arbitrary unprivileged attacker's address. Because `CallDispatcher` is shared across every order that uses predispatch/postdispatch calldata (not one-per-order), any interaction that leaves an unaccounted-for token behind — a DEX swap that yields a slightly different token than requested, a fee rebate, an airdrop triggered by the call, or even ETH dust from a `Call.value` that a downstream contract partially refunds — becomes a standing bounty for anyone monitoring the dispatcher's balances.

### Likelihood Explanation
High. `dispatch()` requires zero privilege to call and the vulnerability doesn't depend on a malicious relayer, prover, or admin — any address can watch the dispatcher's token balances (all public via `balanceOf`) and race to call `dispatch()` the moment a residual balance appears. The precondition (an order whose predispatch/postdispatch calldata interacts with an external contract that can leave behind a token not in the declared `inputs`/`output.assets` list) is realistic given the documented "swap-then-escrow" and "fill-then-act" composability use cases (Uniswap swaps, DeFi routing) explicitly called out in the docs.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by an authorized/registered `IntentGatewayV2` instance (e.g., an `onlyGateway` modifier or constructor-fixed caller), removing the ability for arbitrary external accounts to invoke it directly.
- Alternatively/additionally, deploy a dedicated, ephemeral `CallDispatcher` per order execution (e.g., via CREATE2, self-destructing or otherwise isolated) so no cross-order residual balance can ever accumulate on a shared, publicly-reachable contract.
- Make the sweep step balance-based rather than declared-token-based: after executing the order's calldata, enumerate the actual token balances present on the dispatcher (or at minimum widen the sweep to any token touched by the executed calldata) rather than only the tokens named in `order.inputs`/`order.output.assets`.

### Proof of Concept
1. Attacker deploys `MaliciousTarget`, a contract that, when called by the dispatcher's predispatch/postdispatch `Call`, performs a swap on a DEX that yields token `X` (not equal to any token in `order.inputs` or `order.output.assets`) and leaves `X` sitting on `address(dispatcher)`.
2. A user places an order (or a solver fills one) whose `predispatch.call`/`output.call` routes through `MaliciousTarget`. `IntentGatewayV2`/`IntentsBase` executes the call via `ICallDispatcher(dispatcher).dispatch(...)`, then builds its sweep `Call[]` only for the declared `inputs`/`output.assets` tokens — token `X` is never included and remains on the dispatcher.
3. Any unrelated attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: X, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(X).balanceOf(address(dispatcher)))})]))` directly against the publicly deployed `CallDispatcher` address (obtained from `_params.dispatcher`).
4. Since `dispatch()` performs no caller check, the call succeeds and transfers all of token `X` held by the dispatcher to the attacker, with no relationship to the original order, gateway, or governance.

**Caveat / uncertainty:** I could not fully trace whether `CallDispatcher` is deployed as a true long-lived singleton per-gateway-deployment versus potentially redeployed per-order in some code path not surfaced by my searches (I found no `new CallDispatcher(...)` call inside `evm/src/apps/**`, and `_params.dispatcher` is set via governance `UpdateParams`/`initialize`, consistent with a single persistent address, but I did not locate the exact deployment script for the intents contracts to confirm 100%). If a future Devin session investigates, it should confirm the deployment topology (single shared address vs. per-order) in `evm/script/*IntentGateway*` before finalizing severity, since a per-order-isolated dispatcher would eliminate the cross-order theft angle (though the same-transaction reentrancy variant, where malicious order-declared calldata reenters `dispatch()` mid-execution to redirect the very assets being escrowed, would still apply due to the lack of a `msg.sender`/reentrancy guard on `dispatch()`).

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }

                        value: 0,

                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }

                ++i;
            }
