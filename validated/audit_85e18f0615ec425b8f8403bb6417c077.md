### Title
OP_RETURN data is excluded from Bitcoin fee and weight calculations - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output for caller-supplied `data`, but `calculate_weight_vbytes` estimates the transaction using only payment outputs and an optional change output. [1](#0-0) [2](#0-1)  The resulting `needed_fee` and transaction-size checks therefore omit up to 80 bytes of attacker-controlled transaction data. [3](#0-2) [4](#0-3) 

### Finding Description
`calculate_weight_vbytes` builds a synthetic transaction whose outputs consist only of `payments` and, when requested, `change`. [5](#0-4)  Before fee estimation, `SignableTransaction::new` appends a zero-valued OP_RETURN output containing `data`, but neither call to `calculate_weight_vbytes` passes that output or otherwise accounts for its length. [1](#0-0) [6](#0-5) 

The constructor sets `needed_fee = fee_per_vbyte * vbytes` and enforces Bitcoin's minimum relay fee against that underestimated vsize. [4](#0-3)  The signed transaction nevertheless includes the OP_RETURN output, so its actual serialized size and required fee are larger than the values used for funding, fee-rate accounting, and the maximum-weight check. [7](#0-6) 

### Impact Explanation
A caller able to cause Serai to sign a transaction with nonzero `data` can cause the transaction's realized fee rate to be lower than the requested `fee_per_vbyte`. [8](#0-7)  At the minimum relay fee, the omitted OP_RETURN weight can make the signed transaction fall below Bitcoin's relay minimum even though the constructor accepted it, causing an otherwise correctly signed transaction to be rejected or delayed. [9](#0-8)  The omitted weight can also allow a transaction near `MAX_STANDARD_TX_WEIGHT` to pass Serai's check while exceeding the standard transaction limit after the data output is added. [10](#0-9) 

### Likelihood Explanation
The `data` parameter is a public transaction input to `SignableTransaction::new`, and every nonzero value up to 80 bytes deterministically increases the final transaction weight without increasing `needed_fee`. [11](#0-10) [3](#0-2)  Exploitation does not require malicious validators, leaked keys, or invalid cryptographic inputs because the estimator structurally omits the data output. [2](#0-1) [1](#0-0) 

### Recommendation
Pass the complete output set, including the OP_RETURN output and optional change output, into `calculate_weight_vbytes`, or add a `data_len` parameter and construct the same OP_RETURN script in the synthetic transaction. [2](#0-1) [1](#0-0)  Calculate `needed_fee`, the minimum relay check, and `MAX_STANDARD_TX_WEIGHT` against that complete transaction shape for both the no-change and with-change cases. [4](#0-3) [12](#0-11) 

### Proof of Concept
For any nonempty `data`, `SignableTransaction::new` constructs `tx_outs` as `payments + OP_RETURN(data)` before optionally appending change. [13](#0-12) [14](#0-13) 

Let `vbytes_est` be the value returned from a transaction containing only `payments`, and let `vbytes_actual` be the final signed transaction's virtual size. [15](#0-14)  Because the actual transaction contains an additional OP_RETURN output, `vbytes_actual > vbytes_est`, while the code still sets `needed_fee = fee_per_vbyte * vbytes_est`. [8](#0-7) 

With `fee_per_vbyte` equal to the minimum relay rate, the relay check evaluates `fee_per_vbyte * vbytes_est`, not `fee_per_vbyte * vbytes_actual`, so the broadcast transaction has less than the required fee per actual virtual byte. [9](#0-8)  The signing flow then signs and returns the already-constructed transaction without recalculating the fee or weight. [16](#0-15) [17](#0-16)
