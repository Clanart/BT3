### Title
Legacy commit-status `target_url` with arbitrary URI scheme reaches `shell.openExternal` unfiltered - (File: app/src/lib/ci-checks/ci-checks.ts)

### Summary
`apiStatusToRefCheck` copies the legacy commit-status API's `target_url` field verbatim into `IRefCheck.htmlUrl` with no scheme validation. That value is later handed to `shell.openExternal` via the IPC `open-external` handler, which also performs no scheme enforcement — it only conditionally logs when the URL is http(s), but calls `shell.openExternal(path)` regardless of what scheme the string has.

### Finding Description
`apiStatusToRefCheck` in [2](#0-1)  sets `htmlUrl: apiStatus.target_url` directly from the API response's `target_url` field, which is typed as `string | null` with no format constraint [3](#0-2) . This value is fetched via `fetchCombinedRefStatus` [4](#0-3)  and mapped through `commit-status-store.ts`'s `refreshSubscription` [5](#0-4)  and `notifications-store.ts`'s `getChecksForRef` [6](#0-5) , becoming part of the `IRefCheck` model consumed by UI components.

`CICheckRunListItem.onViewCheckExternally` forwards the click through its `onViewCheckExternally` prop [7](#0-6) , ultimately reaching `CICheckRunPopover.onViewCheckDetails`, which does `const url = checkRun.htmlUrl ?? ...; this.props.dispatcher.openInBrowser(url)` — with no scheme validation of any kind [8](#0-7) .

`Dispatcher.openInBrowser` forwards to `AppStore._openInBrowser`, which directly calls `shell.openExternal(url)` [9](#0-8) . That renderer-side `shell` proxy invokes the `open-external` IPC channel [10](#0-9) , handled in the main process by:

The http(s) check here is purely for logging — it does not branch on or reject non-http(s) schemes before calling `shell.openExternal(path)`. Contrast this with `enterprise-validate-url.ts`'s `validateURL`, which explicitly throws `InvalidProtocolErrorName` for any non-`https:` protocol when validating GitHub Enterprise server addresses [11](#0-10)  — demonstrating that the codebase does have a pattern for protocol allow-listing, but it is not applied to check-run/commit-status URLs before they reach `openExternal`.

### Impact Explanation
Electron's `shell.openExternal` will hand off any URI to the OS's default handler for that scheme. A malicious or compromised GitHub Enterprise/API endpoint (or a GitHub App reporting a commit status) can set `target_url` to `file:///some/path`, a custom-registered protocol handler (e.g. an installed application's URI scheme), or platform-specific URIs. This can lead to opening local files, or handing arbitrary strings/arguments to third-party protocol handlers registered on the user's system — a known Electron/OS attack surface (e.g. argument injection into some protocol handlers). This does not achieve arbitrary code execution within GitHub Desktop itself, but it silently violates the intended "http(s)-only" invariant strongly implied by the main-process logging code, and hands attacker-controlled URIs to OS-level handlers outside the app's process/sandbox.

### Likelihood Explanation
Legacy commit statuses (`target_url`) are commonly set by third-party CI integrations posting to the Status API, which is attacker-influenceable if a malicious or compromised CI integration is authorized on a repository the victim has connected to GitHub Desktop. The user must click "View check details" / "View on GitHub" for a specific check run in the CI checks popover or a checks-failed notification, which is a normal, expected user action in this flow (checking on a PR's CI status), not an unnatural user step.

### Recommendation
Enforce an http(s)-only allow-list at the point closest to the trust boundary: either in `apiStatusToRefCheck` when constructing `htmlUrl` from `target_url` (rejecting/nulling non-http(s) values), or centrally in the `open-external` IPC handler in `app/src/main-process/main.ts`, changing the existing http(s) check from a logging-only condition into an actual gate that rejects other schemes before calling `shell.openExternal`.

### Proof of Concept
1. Mock `API.fetchCombinedRefStatus` to return a status object with `target_url: 'file:///etc/passwd'`.
2. Render the PR checks popover so that `apiStatusToRefCheck` produces `IRefCheck.htmlUrl = 'file:///etc/passwd'`.
3. Click "View check details" for that check run, triggering `CICheckRunPopover.onViewCheckDetails` → `dispatcher.openInBrowser('file:///etc/passwd')`.
4. Assert that `shell.openExternal` (via the `open-external` IPC handler in `app/src/main-process/main.ts`) is invoked with `'file:///etc/passwd'` unmodified — i.e. it is not blocked by any scheme check.
