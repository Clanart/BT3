Based on the code I found for `x/erc20/ibc_middleware.go:OnAcknowledgementPacket` and its downstream keeper logic, the exploit scenario as framed in the question (a reordering that produces **unauthorized minting/burning** by desyncing coin vs. ERC20 balances) is **not substantiated**. The happy-path conversion logic in `ConvertCoinNativeERC20` enforces strict ordering and invariant checks (escrow coin → unescrow/transfer ERC20 → verify balance delta via `ErrBalanceInvariance` → burn coin only after the transfer is confirmed), so a genuine 1:1 backing violation via double-mint/double-burn is not reachable through this path. [1](#0-0) 

However, I did identify a **related but distinct defect** in the same call chain: when `OnAcknowledgementPacket`/`OnTimeoutPacket` triggers automatic re-conversion via `ConvertCoinToERC20FromPacket`, any failure inside `ConvertCoinNativeERC20` that occurs **after** the coin has already been escrowed (`SendCoinsFromAccountToModule` succeeded) but **before** the burn step (e.g., the native ERC20 `transfer` call reverts because the contract is paused/self-destructed/blacklisted) is silently swallowed and the function returns `nil`: [2](#0-1) 

Because there is no `CacheContext` branching around this call, the already-executed `SendCoinsFromAccountToModule` state write is **not rolled back**, while the outer function reports success (`nil` error). This leaves the sender's coin permanently escrowed in the `erc20` module account — neither burned nor matched by a minted ERC20 balance for the receiver — contradicting the function's own doc comment that says "the user receives the corresponding bank token instead" (which would only be true if the escrow itself were reverted). [3](#0-2) 

This does not create a supply-level mint/burn desync (total coin and ERC20 supply are unaffected), but it does produce a **permanent fund lock** for the affected user, since there is no invariant-breaking mint, only mis-custodied escrow with no documented recovery path in the reviewed code. Triggering it requires the underlying native ERC20 contract's `transfer` to fail at that specific moment (e.g., a legitimate `pause()` call on the `Pausable` `ERC20MinterBurnerDecimals` contract, or a self-destructed contract) coinciding with an IBC ack-error/timeout for a packet using that token pair's denom. [4](#0-3) 

I was not able to fully confirm from the indexed code whether registering a "native ERC20" token pair (`MsgRegisterERC20`) requires governance-only authority or can be done permissionlessly — the `msg_server.go` snippets I retrieved for `RegisterERC20` did not show an explicit authority check, and I could not locate the full function body within the index. This matters for likelihood: if pair registration is governance-gated, the "malicious token owner deliberately pauses to grief" scenario mostly reduces to an honest contract's operational pause, which is a narrower and lower-likelihood trigger; if registration is permissionless, an attacker could register their own pausable ERC20 and trap any counterparties who transact with it via IBC.

### Title
Escrowed coin permanently stuck (fund lock) when automatic IBC-triggered ERC20 re-conversion fails after escrow but before burn - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
`ConvertCoinToERC20FromPacket`, called from `OnAcknowledgementPacket`/`OnTimeoutPacket`, swallows errors from `ConvertCoinNativeERC20` without rolling back the coin escrow that already occurred, leaving user funds permanently stuck in the `erc20` module account with no matching ERC20 mint and no refund.

### Finding Description
`ConvertCoinNativeERC20` first escrows the Cosmos coin from the sender into the module account, then attempts to unescrow/transfer the corresponding ERC20 token to the receiver, and only burns the escrowed coin if that transfer succeeds and passes a balance-invariance check. [1](#0-0) 

When this function is invoked from `ConvertCoinToERC20FromPacket` (the IBC ack-error/timeout auto-reconversion path), any error returned after the escrow step is caught, logged as a telemetry/event, and the function returns `nil` — signaling success to `OnAcknowledgementPacket`/`OnTimeoutPacket` even though the coin was moved out of the sender's account without being burned or replaced by ERC20 tokens. [2](#0-1) 

No `CacheContext` is used to branch and discard the partial state changes on this failure path, so the escrow write persists in the committed state.

### Impact Explanation
This falls under "Critical permanent freezing/locking of user funds" — the user's coin is removed from their spendable balance and left stranded in module custody, unrecoverable through any code path shown in the reviewed files.

### Likelihood Explanation
Likelihood is moderate/uncertain: it requires the native ERC20 contract's `transfer` call to fail specifically during the automatic reconversion step (e.g., contract paused or self-destructed) at the moment an IBC ack-error or timeout arrives for a packet in that token pair's denom. I could not confirm whether `MsgRegisterERC20` is governance-only or permissionless, which materially affects whether an unprivileged attacker can set up this trap for arbitrary victims or whether it only manifests as an operational hazard for legitimate, pausable native ERC20 tokens.

### Recommendation
Wrap the escrow-and-convert sequence in `ConvertCoinNativeERC20` (or its caller `ConvertCoinToERC20FromPacket`) in a `ctx.CacheContext()`/branch-and-commit pattern so that any failure after the escrow step reverts the escrow, restoring the coin to the sender instead of stranding it in the module account.

### Proof of Concept
Not independently executed; based on static code review. A Go integration test could: (1) register a native ERC20 token pair with a pausable ERC20MinterBurnerDecimals-style contract, (2) perform an IBC transfer of that pair's coin, (3) pause the contract, (4) deliver an error acknowledgement or timeout so `ConvertCoinToERC20FromPacket` executes, and (5) assert that the sender's coin balance is permanently reduced with no corresponding ERC20 balance increase and no coin burn, confirming the fund-lock.

// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}
