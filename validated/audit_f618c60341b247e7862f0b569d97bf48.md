### Title
Marker-text spoofing in `reassembleResolvedFile` desynchronizes conflict-hunk splicing, causing Copilot-assisted merge resolution to silently corrupt the committed file - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
When Desktop's Copilot merge/rebase/cherry-pick conflict resolution feature reassembles a resolved file, it locates conflict blocks purely by scanning for lines that *textually* match `<<<<<<< `, `=======`, and `>>>>>>> ` regexes, and splices the model's per-hunk resolutions into those blocks strictly by **ordinal position**, not by any structural anchor tied to the actual git conflict boundaries. [1](#0-0) 
Because one side of a merge conflict (`theirs`) is fully attacker-controlled content coming from a fetched/merged branch or PR, an attacker who contributes a branch that a Desktop user merges can plant conflict-marker-shaped text inside ordinary file content (e.g. a doc, changelog, or string literal that itself contains example `<<<<<<<`/`=======`/`>>>>>>>` lines). This desynchronizes the line-scanning state machine used to identify "the next" conflict block from the hunk list the model was asked to resolve.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file (still containing real conflict markers from git) line by line. When it sees a line matching `^<{7}(?:\s|$)`, it looks ahead for the *next* line matching `^={7}$` and then the *next* line matching `^>{7}(?:\s|$)`, and treats everything in between as one conflict block to be replaced by `hunkResolutions[hunkIndex]`. [2](#0-1) 

This lookahead is unconstrained: it does not verify that the `=======` and `>>>>>>>` lines it finds actually belong to the same git-generated conflict region (git always emits these three markers together for a given conflict, at the outer boundaries of the "ours"/"theirs" text). If the "ours" or "theirs" body of a *real* conflict — attacker-supplied content on the "theirs" side — happens to contain a line that matches the ours-marker regex again (e.g. text like `<<<<<<< some example` embedded in a markdown/code sample), the scanner can lock onto a `=======`/`>>>>>>>` pair that is unrelated to the actual conflict, silently consuming and discarding real code that lies between the spoofed marker and the genuine closing marker, and advancing `hunkIndex` out of step with what the model actually resolved.

The upstream defenses do not catch this:
- `validateResolutionPaths` only checks that the **count** of hunks returned by the model matches the **count** of hunks found when building the prompt context — if both the context-extraction parser and `reassembleResolvedFile` are fooled by the same spoofed markers in the same way, the counts still match while the content boundaries are wrong. [3](#0-2) 
- The per-hunk “still contains conflict markers” check only rejects a `resolvedContent` string if it independently contains **both** an ours-marker line **and** a separator line; it does nothing to validate that the reassembled *file* preserved the correct span of original text around each real conflict. [4](#0-3) 
- The one guard that exists ("malformed marker — copy through as regular content") only fires when *no* separator/closing marker is found at all; it provides no protection when spoofed markers happen to be well-formed as a triple, which is exactly the case that misdirects splicing. [5](#0-4) 

The resulting `resolvedContent` is what gets written to disk and shown to the user in the resolution dialog as the fully resolved file; the user is expected to review and then commit it via the normal commit path. [6](#0-5) 

### Impact Explanation
This breaks the invariant that the reassembled file is a faithful merge of "ours" and "theirs" outside of the actually-conflicting regions. An attacker who controls one side of a merge (a PR/branch the victim merges in Desktop) can cause legitimate, non-conflicting code between a spoofed marker triple to be silently dropped from the file the user believes they resolved and are about to commit/push — i.e., silent corruption of what the user commits, one of the explicitly in-scope impact categories. Depending on where the desynchronization lands, this could delete security checks, alter logic, or reintroduce vulnerable code without any error or warning surfaced to the user, since the pipeline treats a matching hunk count as proof of correctness.

### Likelihood Explanation
This requires the Copilot merge-conflict-resolution feature to be enabled and used on a merge/rebase/cherry-pick against attacker-influenced content (a forked PR branch, a shared feature branch, or any git remote the user pulls from). No local access, admin rights, or pre-existing compromise is required — only that the user merges a branch containing crafted marker-lookalike text and accepts the auto-resolution, which is the intended normal workflow for this feature. The main uncertainty (not fully verified due to tool/time limits) is the exact parsing logic on the context-extraction side (`app/src/lib/copilot-conflict-context.ts`, which builds the `hunks` list `reassembleResolutions` cross-checks against) — I was unable to fully inspect it to confirm it uses the identical unconstrained scanning strategy, which would be needed for the hunk *count* check to also pass silently. Absent that confirmation, likelihood should be treated as reasonably high but not fully proven end-to-end.

### Recommendation
- Anchor conflict-block boundaries using the actual byte/line offsets git reports for each conflict (or the structured hunk boundaries already computed during context gathering in `copilot-conflict-context.ts`) instead of re-scanning raw text with regexes independently in `reassembleResolvedFile`.
- Reject or explicitly flag any `resolvedContent`/file pair where the number of marker-shaped lines encountered during reassembly does not exactly match the expected, pre-computed conflict boundaries (not just counts) for that file.
- Add content-level validation (e.g. diffing total non-conflict-region line counts before/after reassembly against the original file) so an unexpected loss of non-conflicted lines fails safe and forces manual resolution instead of silently committing.

### Proof of Concept
1. Set up a repository where `README-git-tutorial.md` (or similar) is modified on both `main` (ours) and `feature` (theirs, attacker-controlled) such that a real merge conflict occurs on an unrelated line.
2. On the `feature` branch, additionally insert into the file (outside the real conflict, further down) an *example* git-conflict-marker triple as ordinary text content, e.g.:
   ```
   Example of a conflict marker in git:
   <<<<<<< HEAD
   real feature code A
   real feature code B
   =======
   real feature code C
   >>>>>>> feature
   ```
   This is legitimate content the attacker wants preserved.
3. Victim merges `feature` into `main` in GitHub Desktop, triggering Copilot conflict resolution.
4. During context extraction and later reassembly, `reassembleResolvedFile`'s lookahead treats the *first* `<<<<<<<`-shaped line it meets (whether the real conflict opener or the example text's opener) and pairs it with the *next* `=======`/`>>>>>>>` lines it finds — which, depending on ordering, can span across the real conflict and the example block, causing genuine resolved content for the real conflict to be dropped or the example block's legitimate code to be silently deleted from the final file.
5. The user is shown a "fully resolved" file in the dialog and commits/pushes it, unaware that content was silently lost — matching the "silent corruption of what the user commits or pushes" impact class.

(Note: full confirmation of the exact desync trigger conditions would require inspecting `app/src/lib/copilot-conflict-context.ts`'s hunk-extraction parser, which I could not fully retrieve before this response; the vulnerable splicing logic itself, shown above, is confirmed directly in `copilot-conflict-resolution.ts`.)

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
