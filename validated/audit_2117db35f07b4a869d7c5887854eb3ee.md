### Title
Interactions-before-effects in `withdraw()` lets escrow accounting be finalized after external transfer, reintroducing the escrow-theft pattern that was already fixed in the sibling EVM contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Basket report's core defect is: check state once, perform an external call in the middle of a token loop, then keep mutating protected state as if nothing changed. The exact same defect pattern — "interactions before effects" inside a token-transfer loop guarded by a single early ownership/state check — exists in `IntentGatewayV2.withdraw()` on the Tron build, while the equivalent mainline EVM contract (`IntentsBase._withdraw`) was already hardened against precisely this class of bug (per the CEI fix documented in `IntrinsicIntentsReentrancyTest.sol`).

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol:682-721` iterates the withdrawal request's token list and, for each token:
1. Checks only that `_orders[body.commitment][token] == 0` (a "has any escrow" check, not "has enough escrow"),
2. Performs the external transfer (`beneficiary.call{value: amount}("")` for native token, or a raw `token.call(...)` for ERC-20) — this is the reentrancy/callback point,
3. **Only afterward** decrements `_orders[body.commitment][token] -= amount;` [1](#0-0) 

Compare this to the corresponding logic in the mainline EVM app, `IntentsBase._withdraw`, which was fixed to decrement escrow **before** making the external call: [2](#0-1) 

The Tron contract also discards the boolean return value of `IERC20.transfer` from the raw `.call`, checking only that the low-level call itself succeeded (`success`), not that the token actually reports a successful transfer: [3](#0-2) 

This means: (a) the escrow ledger slot `_orders[body.commitment][token]` is left stale (not yet decremented) for the entire duration of the external call, which is exactly the reentrancy window the Basket bug exploited by transferring ownership mid-loop and continuing to draw down the now-orphaned resource; and (b) a token whose `transfer()` returns `false` without reverting will still cause the escrow to be marked spent and finalized even though the beneficiary received nothing, permanently locking/losing the escrowed funds (`_filled[body.commitment]` is set unconditionally at the top of `withdraw`, so the order can never be retried).

### Impact Explanation
This falls squarely under "loss of funds" / "false state acceptance" in the bounty scope: escrowed bridge assets can be marked released/refunded (`_filled` set, `_orders` decremented, `EscrowReleased`/`EscrowRefunded` emitted) without the beneficiary actually receiving the corresponding value, or with the accounting window open to reentrant manipulation during the callback. It directly undermines the invariant "bridged assets ... must move exactly once and only to the rightful beneficiary and amount," which is one of the explicit Hyperbridge pivots.

### Likelihood Explanation
`withdraw()` is reached from `onAccept` (RedeemEscrow/RefundEscrow, `onlyHost`) and from `cancelOrder`'s same-chain branch, which is a public, unprivileged entrypoint reachable directly by the order owner (`order.user == msg.sender`), requiring no relayer, prover, or admin action: [4](#0-3) 
Since `order.inputs`/`body.tokens` and the beneficiary are attacker-controlled for the attacker's own order (they can specify arbitrary token addresses and a malicious beneficiary contract), the attacker fully controls both the reentrant callback surface (native-token `.call` or a malicious ERC-20's `transfer`) and which token address will silently "succeed" with a false return. Note: `_filled[body.commitment]` is set at the very top of `withdraw`, before the loop, which blocks a second top-level call into `cancelOrder`/`withdraw` for the *same* commitment — this reduces (but does not eliminate) the likelihood of a full double-withdrawal via straightforward re-entry into `cancelOrder`, and I could not find, within the code retrieved, an unguarded second entrypoint that reads/mutates the same `_orders[commitment][token]` slot without checking `_filled`. The unchecked-return-value accounting bug (finalizing on a `false`-returning `transfer`), however, requires no reentrancy at all and is independently and reliably triggerable by any order that escrows a non-standard ERC-20.

### Recommendation
- In `withdraw()`, decrement `_orders[body.commitment][token]` (and set `_filled` per relevant state) strictly before performing any external call, matching the CEI ordering already applied in `IntentsBase._withdraw`.
- Validate the actual transfer amount against the escrowed balance (`amount <= escrowed`), not just `escrowed != 0`.
- Check the ABI-decoded boolean return value of `IERC20.transfer` (or use `SafeERC20.safeTransfer` as the mainline EVM contract does) instead of only checking that the low-level `.call` succeeded.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs` containing a non-standard ERC-20 token `T` whose `transfer()` implementation returns `false` (no revert) when a specific condition is met, and sets `order.user = attacker`.
2. Attacker calls `cancelOrder` for their own same-chain order; this reaches the same-chain branch (`order.user == msg.sender` passes) and calls `withdraw(body, true)`.
3. Inside `withdraw`'s loop, `_orders[commitment][T] == 0` check passes (escrow is non-zero), `token.call(transfer(...))` returns `success = true` (call succeeded) even though the encoded return data is `false`, and the code never inspects that boolean: [3](#0-2) 
4. `_orders[commitment][T] -= amount` executes, `_filled[commitment]` was already set, and `EscrowRefunded` is emitted — the order is permanently marked settled while token `T`'s balance was never actually moved to the beneficiary, resulting in silent fund loss and a false settlement record.
