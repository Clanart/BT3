### Title
`rewards()` on the distribution precompile accepts `msg.value` without validation or forwarding, permanently stranding funds - ([File: precompiles/distribution/distribution.go])

### Summary
The `rewards()` view method on Sei's distribution precompile (`0x0000000000000000000000000000000000001007`) is dispatched without the `pcommon.ValidateNonPayable` guard that every other read-only method in the same `Execute` switch applies, and without the `pcommon.HandlePaymentUsei` refund logic that payable state-changing methods (`deposit`, `setWithdrawAddress`, `submitProposal`, etc.) use to return attached value to the caller. Any `usei`/`wei` sent alongside a `rewards()` call is transferred by the EVM core into the precompile's underlying account balance and then never moved anywhere — an exact analog of the `donateETH` issue in the reported `OptimismPortal`, where funds sent to a function are accepted but there is no path to spend or reclaim them.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute` dispatches methods based on `method.Name`: [1](#0-0) 

Every other query method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) is passed `value` and internally can validate it, matching the pattern used elsewhere, e.g. `validateInput` which calls `pcommon.ValidateNonPayable(value)`: [2](#0-1) 

`RewardsMethod` is the one exception: it is dispatched as `p.rewards(ctx, method, args)` — no `value` parameter is even passed to the handler, so no non-payable check nor refund can occur: [3](#0-2) 

The unit test suite and integration spec explicitly document this as a known quirk rather than a validated behavior: [4](#0-3) 

In go-ethereum's EVM `Call` path, `value` transfer from caller to the target address (including precompile addresses) happens in the core EVM logic before the precompile's `Run`/`RunAndCalculateGas` executes — this is how payable precompile methods are able to later call `HandlePaymentUsei` to send the credited `usei` back to the payer: [5](#0-4) 

Because `rewards()` never calls this refund logic, and never rejects nonzero value, any `usei`/`wei` sent with a `rewards()` call is credited into the Sei account associated with the distribution precompile's address (via `GetSeiAddressOrDefault`) and permanently stranded there — there is no keeper method, precompile method, or governance action that sweeps or reclaims balance held at the precompile's mapped Sei address.

### Impact Explanation
Any unprivileged EVM caller who mistakenly (or via a buggy front-end/wallet integration) attaches `value` to a `rewards()` call on the distribution precompile permanently loses those funds — a real, concrete case of fund freezing/loss reachable by a plain transaction, matching the "permanent freezing of funds" acceptance criterion. This is a genuine bug-class match to the reported `donateETH` issue (funds accepted by a contract function with no corresponding withdrawal/refund path).

### Likelihood Explanation
Likelihood is moderate: `rewards()` is documented in Sei's own ABI/tooling as a `view`-style query, so well-formed clients should not attach value; however, nothing in the precompile enforces this, and the existing test/spec comments confirm the team is aware a value-bearing call "would succeed and strand the funds." Any wallet, SDK, or hand-crafted transaction that (incorrectly) sends `msg.value` with this call — e.g. due to ABI misuse, fee estimation issues, or intentional griefing/waste-of-funds by a user — results in permanent loss with no recovery path.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check to `rewards()` in `precompiles/distribution/distribution.go` (and all versioned copies) consistent with every other read-only method, so that value-bearing calls revert instead of stranding funds. Alternatively, if `rewards()` should stay payable, forward the received value back to the caller via `pcommon.HandlePaymentUsei` before returning.

### Proof of Concept
1. Call the distribution precompile at `0x0000000000000000000000000000000000001007` with the `rewards(address)` selector and `msg.value = 1 SEI` (in wei terms).
2. The EVM core transfers the 1 SEI from the caller's balance to the precompile's associated Sei account balance before `Execute` runs.
3. `Execute` dispatches to `p.rewards(ctx, method, args)` (no `value` argument at all), which performs no validation and no refund; the call succeeds and returns the rewards data.
4. The 1 SEI credited to the precompile's Sei address is now unreachable by any keeper/precompile method — it is permanently stuck, exactly as described for `donateETH` in `OptimismPortal`.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
}
