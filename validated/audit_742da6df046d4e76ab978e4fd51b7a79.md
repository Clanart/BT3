## #ValidVulnerabilityFound (tentative) — Duplicate signature entries inflate the BEEFY participation threshold

### Title
Unsigned Duplicate Signature Padding Bypasses BEEFY Supermajority Threshold — (File: `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof`)

### Summary
`verify_mmr_update_proof` computes the participation-threshold count directly from the raw length of the attacker-supplied `signed_commitment.signatures` vector, without deduplicating by authority index or signature bytes, before checking supermajority participation.

### Finding Description
In `verify_mmr_update_proof`, the number of signatures used for the 2/3+1 supermajority check is taken as-is from the wire-format vector: [1](#0-0) 

`signatures_length` is simply `mmr.signed_commitment.signatures.len()`, and it is passed unmodified into `check_participation_threshold`. There is no `BTreeSet`/dedup step over `sig.index` (or over the recovered `authority_address_hash`) before this count is used, unlike the analogous request/response paths elsewhere in the codebase which explicitly guard against batch duplication, e.g. `dedup_requests`: [2](#0-1) 

After the threshold check, the loop that recovers authority addresses and builds `authority_leaves`/`authority_indices` for the merkle multi-proof also performs no deduplication — it pushes one leaf/index pair per signature entry, including duplicates: [3](#0-2) 

Because `pallet_ismp::handle_unsigned` accepts unsigned `ConsensusMessage`s from anyone and forwards the attacker-controlled `signed_commitment.signatures` array straight into this function, an attacker can duplicate an already-included `(authority_index, signature)` pair (or replay the byte-identical entry, or a malleable ECDSA variant that recovers to the same address at the same index) to inflate `signatures_length` above the 2/3+1 threshold while the number of *unique* authenticated validators backing the commitment remains below quorum. Whether this ultimately produces a false-accept depends on whether the downstream merkle multi-proof verification (`MerkleProof::verify` from the external merkle-trees crate) tolerates repeated `(index, hash)` entries pointing at the same real tree position — this crate is external to the repo and its exact duplicate-handling semantics could not be confirmed from the indexed sources here.

### Impact Explanation
If the merkle multi-proof step accepts (or silently collapses) duplicate index/leaf entries — a common pattern for multiproof verifiers that key membership checks by tree position — then an attacker can force acceptance of a BEEFY commitment signed by fewer than 2/3+1 of the current/next authority set, i.e., false consensus-state acceptance. This directly undermines the "unique proof items authenticate weight" invariant and could unlock acceptance of a forged relay-chain state root, from which forged parachain header/state commitments and thus unauthorized cross-chain execution/withdrawals could follow — matching the Critical impact class in the question.

### Likelihood Explanation
Likelihood is moderate and gated entirely on the (unverified-here) behavior of the third-party merkle multi-proof crate when given duplicate `(index, hash)` inputs. The entry point (`handle_unsigned`, unsigned/unprivileged) and the missing in-function dedup on `signatures_length` are confirmed facts in this repo; the merkle library's tolerance of duplicates is the unresolved variable that determines actual exploitability.

### Recommendation
Deduplicate `mmr.signed_commitment.signatures` by `sig.index` (rejecting the message on any duplicate index, mirroring `dedup_requests`) before computing `signatures_length`, and reject the proof outright if duplicate indices are present — independent of what the merkle proof library does internally. This closes the gap regardless of the external crate's semantics.

### Proof of Concept
1. Take a genuine BEEFY commitment signed by `k < 2n/3+1` distinct authorities.
2. Duplicate one or more `(authorityIndex, signature)` entries already present in `signed_commitment.signatures` until `signatures.len() >= 2n/3+1`.
3. Submit via `pallet_ismp::handle_unsigned(origin=None, [Message::Consensus(...)])`.
4. Assert whether `check_participation_threshold` and the subsequent merkle-proof check both pass despite only `k` unique authenticated signers — if so, the state update is accepted with sub-quorum real participation. [4](#0-3)

/// Reject duplicate requests within a batch. Each request's ISMP
/// canonical commitment (via `hash_request`) is tracked in a `BTreeSet`;
/// the first repeat short-circuits with `DuplicateRequest` and names the
/// offending request in the error meta. Wire format for batches is a
/// `Vec`, so this is the line of defence against an attacker padding a
/// batch with identical requests to inflate its apparent size.
pub fn dedup_requests<H: Keccak256>(requests: &[Request]) -> Result<(), Error> {
	let mut seen = alloc::collections::BTreeSet::new();
	for req in requests {
		if !seen.insert(hash_request::<H>(req)) {
			return Err(Error::DuplicateRequest { meta: req.clone().into() });
		}
	}
	Ok(())
}
