### Title
`ReceivedOutput::read` accepts an unauthenticated `offset`/`TxOut`/`OutPoint` triple with no binding to the wallet key, so fabricated or mismatched "received" outputs are indistinguishable from real ones — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report's bug class is an API that returns a value with no way for the consumer to distinguish a valid result from a stale/invalid one (`latestAnswer()` returning a price or zero). The Serai analog is `ReceivedOutput::read`, which deserializes an attacker-controlled `(offset, output, outpoint)` triple and returns it as a first-class "spendable output" object without verifying that `offset` actually maps the threshold group key to `output.script_pubkey`, or that the `outpoint`/`value` correspond to anything real. Consumers receive a `ReceivedOutput` that is structurally identical to one produced by `Scanner::scan_transaction`, with no signal distinguishing valid from fabricated data.

### Finding Description
`ReceivedOutput` couples three pieces of attacker-supplied data:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output;
  let outpoint;
  {
    let mut buf_r = BufReader::with_capacity(0, r);
    output = TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
    outpoint =
      OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

The only checks are canonical-scalar decoding (`read_F`, which rejects non-canonical encodings but accepts any scalar) and syntactic consensus decoding of `TxOut`/`OutPoint`. There is no verification that:

1. `key + offset*G` (after the even-Y walk performed by `Scanner::register_offset`) actually produces `output.script_pubkey`. A legitimately produced `ReceivedOutput` is only spendable because `offset` maps the group's tweaked key to the output script; an arbitrary scalar breaks that silently.
2. The `outpoint` refers to an existing confirmed output, or that `output.value` is not inflated.

The honest path — `Scanner::new`/`register_offset`/`scan_transaction` — builds `ReceivedOutput`s where `offset` is guaranteed to correspond to the script (`scripts.get(&output.script_pubkey)`). Once serialized and re-read, or received from a peer, that guarantee disappears entirely, yet the returned type is identical. A consumer calling `output.value()` or feeding the output into the signer path in `wallet/send` will treat the fabricated claim as real.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (any channel that transports serialized `ReceivedOutput`s — peer messages, coordinator data, stored state) can cause a node/coordinator to:

- Record deposits that never existed (arbitrary `outpoint` + inflated `TxOut::value`), corrupting balance/accounting — "funds reported received that are not spendable."
- Attach a wrong `offset` to a *real* deposit output. The output exists and appears correctly attributed, but the signing view derived from `offset` cannot produce a valid spend — a real deposit becomes silently unspendable, indistinguishable at deserialization time from a valid one.

This is exactly the reported failure mode: a getter (`offset()`, `output()`, `value()`) returns attacker-shaped data with no validity signal, and the defect surfaces only later when the funds cannot be spent or accounting diverges.

### Likelihood Explanation
Reachability requires an attacker to supply bytes to `ReceivedOutput::read`, which is a public deserialization API explicitly designed for transporting these objects between parties; any deployment that receives scanned outputs from untrusted peers or loads unauthenticated state is exposed. Constructing the malicious bytes is trivial — any scalar plus any consensus-valid `TxOut`/`OutPoint` encoding is accepted. The attack does not require validator status, collusion, or key material. Impact is bounded to accounting corruption and deposits rendered unspendable (requiring re-scanning/recovery to fix) rather than direct theft or key recovery, consistent with Medium severity.

### Recommendation
Bind the `offset` to the claimed output at construction/deserialization time. Either:

- Have `ReceivedOutput::read` take the `Scanner`'s key and recompute/verify that walking `offset` (per the even-Y increment rule in `register_offset`) yields `output.script_pubkey`, rejecting mismatches; or
- Make `ReceivedOutput` unconstructible/deserializable outside `Scanner` (return the verification from `scan_transaction` only), so every `ReceivedOutput` provably came from a real script match.

At minimum, document that a deserialized `ReceivedOutput` carries no integrity guarantee and callers must re-verify `offset` against `output.script_pubkey` before treating it as spendable.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read:
//  - offset: any scalar (e.g., 1) — read_F accepts it
//  - output: TxOut { value: 100_000_000, script_pubkey: <honest wallet's script> }
//  - outpoint: OutPoint of a tx that never paid this script, or doesn't exist
let mut bytes = Scalar::ONE.to_bytes().to_vec();
bytes.extend(serialize(&forged_txout));
bytes.extend(serialize(&forged_outpoint));

let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// ro.value() == 100_000_000 — indistinguishable from a real deposit.
// Spending fails: G*offset + tweaked_key does not equal the key behind
// script_pubkey, so the signature view derived from offset is wrong.
// No error or flag distinguishes this from Scanner::scan_transaction output.
```
