## Title
Stale line-selection indices re-applied to a freshly fetched diff during partial commits can silently corrupt commit contents — ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop's partial-commit ("stage select lines/hunks") flow separates *when a diff is shown and lines are selected* from *when that diff is actually used to build the patch that gets applied to the index*. The former happens in the renderer (`app-store.ts`), the latter happens independently at commit time in `applyPatchToIndex`, which re-fetches a brand-new diff of the working directory rather than reusing/validating against the diff the user actually reviewed and selected lines from. If the tracked file's content changes between those two points, the user's line selection (encoded as absolute line indices) is silently re-interpreted against different diff content, and the wrong lines can end up in the commit.

### Finding Description
When a user makes a partial selection (some added/removed lines but not others) on a modified file, Desktop stores that selection as a set of absolute line indices (`DiffSelection`), computed relative to a specific diff object that was fetched and rendered in the Changes view [1](#0-0) .

The application is aware that a previously-loaded diff can go stale relative to a new one and attempts to reconcile this **only for UI rendering**, by recomputing the set of "selectable lines" against a freshly-loaded diff and dropping selections that no longer correspond to includable lines: [2](#0-1) 

However, when the user actually commits, the code path is entirely different and does **not** go through this reconciliation. `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff from scratch and builds the patch straight from the (possibly stale) `file.selection`: [3](#0-2) [4](#0-3) 

`formatPatch` then walks the *new* diff's hunks and decides what to include based purely on the absolute line index (`hunk.unifiedDiffStart + lineIndex`) matching the old selection — it has no way to know whether the content at that index is the same content the user actually reviewed and selected: [5](#0-4) 

So the invariant that's broken is: *"the set of lines a user visually selected for inclusion in a commit is the same set of lines that ends up in the commit."* There is no check that the working-directory diff used to build the patch at commit time is the same diff (or even structurally equivalent) to the one the selection was made against, and no content/blob comparison guarding `applyPatchToIndex`.

### Impact Explanation
If content in a tracked file changes between the last diff render in the Changes view and the moment `_commitIncludedChanges` actually executes (e.g. because of an automated process bundled with/triggered by the repository — a Git LFS smudge/clean filter declared in a cloned repo's `.gitattributes`, a checked-in file watcher/build step, or any other automated rewrite of a tracked file that runs without a fresh UI diff reload), the user can end up silently committing (and subsequently pushing) content they never reviewed or intended to include — or omitting content they explicitly selected. This is a silent corruption of what the user commits, which can leak unintended content into history or drop intended changes without any error being surfaced.

### Likelihood Explanation
This requires a narrow timing window (between the last diff refresh and clicking "Commit") plus some external mechanism to alter tracked file content in that window. Desktop's own code comments acknowledge this general class of staleness risk exists ("The diff might have changed dramatically since last we loaded it...") but the mitigation is incomplete: it only covers UI rendering, not the actual patch-building path used for the real `git apply --cached` at commit time. This makes the likelihood moderate rather than trivial — it depends on an external trigger for the working-directory mutation, which limits it to specific tooling/workflow setups rather than a universally reachable primitive.

### Recommendation
Before generating and applying a partial-commit patch in `applyPatchToIndex`, revalidate that the diff used to build the patch is unchanged relative to what the selection was made against — e.g., by comparing file mtime/size or by recomputing the diff immediately prior to selection use in the UI's commit trigger, aborting/re-prompting the user if it differs (mirroring the "selectable lines" reconciliation already done for rendering, but applied to the actual staging path as a hard gate rather than a best-effort UI-only adjustment).

### Proof of Concept
Conceptual reproduction path based on code:
1. User opens a modified file in Desktop's Changes view; Desktop calls `getWorkingDirectoryDiff` and renders hunks; user partially selects specific added lines (index-based selection stored).
2. Before the user clicks "Commit", an external process tied to the repository (e.g. an LFS smudge filter or a repo-bundled watch/build script) rewrites the same tracked file, shifting or changing line content without the Changes view being force-refreshed/re-validated for that file's selection.
3. User clicks "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a **new** diff of the now-modified file and calls `formatPatch(file, diff)` using the **stale** `file.selection` indices.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`) includes/excludes lines purely based on absolute index matches in the new diff, producing a patch that no longer corresponds to what the user visually selected, which is then applied via `git apply --cached` and committed without any warning.
