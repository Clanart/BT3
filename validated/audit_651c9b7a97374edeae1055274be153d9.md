## Title
Unbounded WebSocket Handshake Read in RPC PubSub Server Enables Slowloris-Style Resource Exhaustion - (rpc/src/rpc_pubsub_service.rs)

## Summary
`listen()` accepts every incoming TCP connection to the PubSub port and spawns a task running `handle_connection()`, which calls `server.receive_request().await?` to perform the WebSocket handshake with no read deadline. A remote, unauthenticated client can open a connection, withhold or trickle handshake bytes, and keep the spawned tokio task and its socket file descriptor alive indefinitely, exhausting file-descriptor/task/memory budgets dedicated to the PubSub service.

## Finding Description
`listen()` binds the pubsub TCP listener and on each accepted connection spawns `handle_connection` without any per-connection read-timeout policy; the only bookkeeping is a `TokenCounter` metrics counter that merely reports connection counts via `datapoint_info!` and enforces no cap. [1](#0-0) [2](#0-1) 

Inside `handle_connection`, `Server::new(socket.compat())` followed by `server.receive_request().await?` reads the HTTP-style WebSocket upgrade request from the socket, with no surrounding `tokio::time::timeout`/`timeout_at`. [3](#0-2) 

By contrast, the sibling `net-utils/src/ip_echo_server.rs` bounds every read with a `timeout_at(deadline, ...)` derived from a fixed `IO_TIMEOUT` constant, and additionally caps concurrency via `MAX_CONCURRENT_CONNECTIONS`. [4](#0-3) [5](#0-4) 

This confirms the gap: the PubSub handshake path has no equivalent timeout or concurrency guard, so a client that opens the TCP connection and sends handshake bytes at a trickle (or never) keeps the task parked at `receive_request().await?` indefinitely, retaining the socket file descriptor and task memory.

## Impact Explanation
An unprivileged remote client reachable to the RPC PubSub port can open many TCP connections and stall each handshake indefinitely, exhausting the validator's file-descriptor limit or tokio task/memory budget for the PubSub runtime, degrading or crashing the RPC PubSub subsystem. This falls under the "single-client low-rate RPC crash/degradation" and "non-RPC remote exhaustion" allowed impact categories, requiring no authentication, valid keys, or privileged role — only the ability to open a TCP connection to the exposed PubSub listener bound in `listen()`. [6](#0-5) 

## Likelihood Explanation
High for any validator exposing the RPC PubSub endpoint publicly, a common supported configuration. The attack requires no authentication, no valid keys, and no protocol trust — only the ability to open a TCP connection and withhold/slow-send the handshake bytes, trivially scriptable, and repeatable at scale limited only by attacker connection count.

## Recommendation
Wrap `server.receive_request()` (and ideally the handshake response send) in `tokio::time::timeout`/`timeout_at` with a bounded duration, mirroring `IO_TIMEOUT`/`timeout_at` in `net-utils/src/ip_echo_server.rs`, dropping the connection on expiry. Additionally, consider bounding total concurrent pre-handshake connections similar to `MAX_CONCURRENT_CONNECTIONS`.

## Proof of Concept
1. Start a validator with the RPC PubSub service enabled and reachable at the address bound in `listen()`.
2. From an attacker host, open N TCP connections to the pubsub port.
3. For each connection, send only a few bytes of the WebSocket handshake request (or none), then hold the socket open without completing the header data expected by `server.receive_request()`.
4. Because `receive_request().await?` in `handle_connection` (line 356) has no timeout, each task spawned in `listen()`'s `tokio::spawn` block (lines 458-467) remains parked indefinitely, retaining its socket and task resources; `TokenCounter` only reports the growing count, without limiting it.
5. Repeat until the validator's file-descriptor limit or tokio task/memory ceiling for the PubSub runtime is reached, causing new legitimate PubSub connections to fail or the service to degrade/crash, achievable from a single unprivileged low-rate client.
