### Title
Payout output amount is never bound to the bridge/withdrawal amount, allowing a near-zero-value payout to still be fully reimbursed - ([File: circuits-lib/src/bridge_circuit/mod.rs], [File: core/src/verifier.rs], [File: core/src/operator.rs])

### Summary
`journal_hash` (computed in `circuits_lib::bridge_circuit::journal_hash`, `circuits-lib/src/bridge_circuit/mod.rs:665-684`) only commits to `payout_tx_blockhash`, `latest_blockhash`, `challenge_sending_watchtowers` and `deposit_constant` — no output amount ever enters the circuit's public output. The verifier's fraud check, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`), likewise only compares the OP_RETURN operator pubkey and the committed payout blockhash, never an amount. The only amount sanity check in the whole repo, `Operator::is_profitable` (`core/src/operator.rs:503-537`), is a relative-difference check that can be satisfied by a near-zero output when the input UTXO value is also near-zero, regardless of the absolute amount actually delivered to the withdrawer.

### Finding Description
Binding claimed: `payout_output_amount_paid_to_withdrawer(withdrawal_i) == bridge_amount_reimbursed_at_Reimburse(withdrawal_i)`.

Tracing the path:
- `verify_storage_proofs` (`circuits-lib/src/bridge_circuit/storage_proof.rs:44-133`) extracts only `(withdrawal_outpoint_txid, vout, move_txid)` from Citrea storage — no amount field exists in the committed data at all.
- `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:137-244`) asserts the payout tx's referenced input txid/vout match the storage-proved withdrawal outpoint, and later folds `payout_tx_blockhash`, `latest_blockhash`, `challenge_sending_watchtowers`, `deposit_constant` into `journal_hash` (`circuits-lib/src/bridge_circuit/mod.rs:237-244`, `665-684`). No output value of the payout transaction is ever read or hashed.
- On the verifier side, `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) scans the chain for whichever transaction spends the recorded withdrawal UTXO, extracts only the OP_RETURN-embedded operator xonly pubkey, and stores it — again, no amount.
- `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only checks that this stored operator pubkey matches the kickoff's claimed operator and that the committed blockhash matches — no amount comparison exists.
- The only place an amount is checked at all is `Operator::withdraw` → `Operator::is_profitable` (`core/src/operator.rs:560-612`, `503-537`), which computes `withdrawal_diff = out_amount - input_amount` and requires `bridge_amount_sats - withdrawal_diff >= fee`. If both `input_amount` (the withdrawal UTXO's on-chain value, chosen by whoever registers the withdrawal) and `out_amount` (chosen at withdraw-RPC time) are near zero, `withdrawal_diff ≈ 0`, so `net_profit ≈ bridge_amount_sats`, which trivially passes the "profitable" check even though the withdrawer is paid ~0 BTC.

Because none of the circuit, the storage-proof commitment, or the verifier's `is_kickoff_malicious` fraud check ever inspect the actual value paid to the withdrawer, an operator that follows the standard `withdraw()` → kickoff → Assert → ChallengeTimeout → Reimburse path for a withdrawal whose registered UTXO/output happen to be near-zero value will pass every check in the codebase and still be reimbursed the full `bridge_amount` (e.g., 10 BTC) at Reimburse.

### Impact Explanation
This breaks the "BTC released at Reimburse == BTC fronted to the withdrawer" invariant: the Reimburse transaction pays the full bridge amount out of the move-to-vault UTXO's kickoff-derived reimbursement path while the withdrawer received essentially nothing. This is repeatable for every deposit/withdrawal pair where the registered withdrawal UTXO and requested output amount are both small, and applies to any operator, since none of the affected checks (`is_profitable`, `is_kickoff_malicious`, `journal_hash`) are operator-specific. Matches the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal."

### Likelihood Explanation
No mainnet or live Citrea dependency is required to reach the underlying logic gap: `is_profitable`'s math, `journal_hash`'s composition, and `is_kickoff_malicious`'s checks are all pure/unit-level logic reachable in this repo's own test harness. Exploiting it end-to-end additionally requires the withdrawal registration path (Citrea) to allow a near-zero-value withdrawal UTXO/output amount pairing, which is partly outside this repo, but the missing-amount-binding defect itself is fully demonstrable and located entirely within this repo's circuit/verifier/operator code.

### Recommendation
Commit the payout output amount into the bridge circuit's public journal (alongside blockhash/watchtower data), and enforce in `verify_storage_proofs`/Citrea storage that a withdrawal's registered/required amount is included and checked against the payout tx's actual output value. Additionally fix `Operator::is_profitable` to require `out_amount` be within an acceptable range of `bridge_amount_sats` directly (not just the diff relative to an attacker-influenced `input_amount`), and add an explicit amount check to `Verifier::is_kickoff_malicious`.

### Proof of Concept
```
cargo test -p circuits-lib is_profitable_accepts_near_zero_payout   // shows Operator::is_profitable(0,0,bridge_amount,fee) == true
cargo test -p circuits-lib journal_hash_amount_independence          // shows journal_hash unchanged when payout tx output value is varied while blockhash/watchtower/deposit_constant held fixed
cargo test -p core is_kickoff_malicious_ignores_amount               // constructs two payout txs differing only in output amount but with identical OP_RETURN operator pk and blockhash commit, asserts is_kickoff_malicious returns false (not malicious) for both
```
Assert on both sides of the binding: `payout_tx.output[0].value == 0` (withdrawer balance unchanged) while `Reimburse_tx` pays `bridge_amount` out of the `DepositInMove` output, i.e. `assert_ne!(payout_amount_paid, reimburse_amount_released)`.
