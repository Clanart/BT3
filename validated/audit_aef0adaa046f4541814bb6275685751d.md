### Title
Unbounded Buffer Read in CLVM Canonical-Encoding Check Can Crash Mempool Validation on a Malicious Spend Bundle - ([File: chia/full_node/mempool_manager.py])

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse a raw CLVM-serialized buffer (an attacker-supplied puzzle reveal / solution byte string from a submitted `SpendBundle`) by indexing directly into the `bytes` object with an `offset` that is only ever incremented, never validated against `len(clvm_buffer)`. A truncated or malformed length-prefix (e.g. a multi-byte atom length prefix that claims more length bytes than actually remain in the buffer) causes `clvm_buffer[offset]` to be evaluated with `offset >= len(clvm_buffer)`, raising an unhandled `IndexError` instead of a normal, expected `ValueError`/parsing error.

### Finding Description
`is_atom_canonical` reads the length-prefix byte and, depending on its high bits, computes a `prefix_len` (0–5) of additional bytes that must be consumed to decode the atom length: [1](#0-0) 

The loop `for i in range(prefix_len): ... offset += 1; atom_len |= clvm_buffer[offset]` blindly reads `clvm_buffer[offset]` for each of the `prefix_len` iterations with no check that `offset` remains within `len(clvm_buffer)`. If the buffer ends exactly where a multi-byte length prefix begins (e.g. the last byte of the buffer is `0xF8`, which signals a 4-byte length prefix should follow, but no further bytes exist), the very next `clvm_buffer[offset]` access is out of range.

`is_clvm_canonical` drives this by walking a CLVM-serialized program token by token: [2](#0-1) 

It has an `assert clvm_buffer != b""` guard for the fully-empty case, but no bound check inside the `while True` loop before `b = clvm_buffer[offset]`, nor before calling `is_atom_canonical(clvm_buffer, offset)`. A truncated buffer (e.g., a valid-looking start-of-atom byte at the very last position of the buffer) reaches `is_atom_canonical` with `offset == len(clvm_buffer) - 1`, and the internal prefix-reading loop then indexes past the end.

This is the same bug class as CVE-2025-32397 (an out-of-bounds/overflow read triggered by attacker-controlled, malformed length-prefixed data during packet/byte-buffer parsing): the code trusts a length field embedded in untrusted, attacker-supplied bytes to drive further buffer reads without verifying the buffer is actually long enough, so a python `IndexError` is raised instead of a controlled validation error.

### Impact Explanation
`is_clvm_canonical` is invoked from mempool-related code paths that check whether a submitted spend bundle's CLVM programs (puzzle reveal / solution) use canonical serialization (a mempool-mode/soft-fork rule). Because a submitter fully controls the raw bytes of `puzzle_reveal`/`solution` inside a `CoinSpend`, an attacker can craft a spend bundle whose CLVM buffer ends immediately after a byte that signals a multi-byte atom-length prefix, forcing an `IndexError` to be raised deep inside consensus/mempool code rather than the expected `ValueError`. If this exception is not specifically caught alongside `ValueError` at every call site (unverified due to limited call-site visibility beyond the two references found in `mempool_manager.py`), it can propagate as an unhandled exception in the transaction validation path, which is capable of halting/aborting a single spend-bundle validation and, depending on the surrounding error handling, disrupt the mempool worker for that call — a spend-triggered transaction-processing halt reachable purely from an unprivileged, unauthenticated spend-bundle submitter.

### Likelihood Explanation
Likelihood is high for triggering the code path: constructing a CLVM byte buffer whose final byte is a valid "start of atom, N extra length bytes required" prefix byte (e.g. `0xC0`–`0xFF` range) with the buffer truncated right there is trivial and entirely within a spend-bundle submitter's control (no signature or execution validity is required to reach the byte-level canonical check, since the buffer is inspected directly, not run). The main uncertainty — and the reason this is not marked Critical — is that I could not fully confirm from the indexed portion of the codebase whether every caller of `is_clvm_canonical` wraps the call in a broad `except Exception`/`except (ValueError, IndexError)` block that would absorb the crash without disrupting the service; this should be verified directly in the repository.

### Recommendation
- In `is_atom_canonical`, before each `clvm_buffer[offset]` access inside the prefix-reading loop (and before the initial `b = clvm_buffer[offset]` reads in both functions), check `offset < len(clvm_buffer)` and raise/return a normal validation failure (e.g. treat as non-canonical / raise `ValueError`) instead of allowing `IndexError` to propagate.
- In `is_clvm_canonical`, add an explicit remaining-length check before each `clvm_buffer[offset]` access in the `while True` loop.
- Add unit tests with deliberately truncated buffers ending on 1-, 2-, 3-, 4-, and 5-byte length-prefix bytes to ensure a graceful, typed error is produced rather than an `IndexError`.
- Audit every caller of `is_clvm_canonical`/`is_atom_canonical` to confirm `IndexError` is caught (or eliminate the possibility entirely via the bound checks above) so malformed submitter-controlled buffers cannot produce unhandled exceptions in the mempool/consensus validation path.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
