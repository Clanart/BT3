### Title
Dead forfeiture logic in `mWOMSVBaseRewarder._calExpireForfeit` lets cooldown users keep 100% of rewards that should be forfeited - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is hard-coded to always compute `rewardableAmount = _amount`, making `forfeitAmount = _amount - rewardableAmount` always `0`, regardless of the caller's lock/cooldown state. Because `_sendReward` relies entirely on this function to withhold rewards from users sitting in cooldown, no forfeiture ever occurs, and any user (including one who locks and immediately starts unlocking 100% of their balance) receives their full, unpenalized share of rewards for as long as their balance remains registered in `MasterMagpie`.

### Finding Description
`getReward`/`getRewards` in `mWOMSVBaseRewarder.sol` call `_sendReward` (rewards/mWOMSVBaseRewarder.sol:362-376), which computes the amount to forfeit via `_calExpireForfeit(_account, userRewards[...])` (line 363). Looking at the implementation: [1](#0-0) 

`rewardableAmount` is initialized to `_amount` and never modified before the forfeit calculation, so `forfeitAmount = _amount - rewardableAmount` is always `0`. The function never calls `mWomSV.getRewardablePercentWAD(_account)` — the function that actually encodes the intended penalty for balances sitting in cooldown vs. fully locked: [2](#0-1) 

Meanwhile, `balanceOf(_account)` in the rewarder (used for reward accrual via `_earned`) simply reads the user's raw staked amount from `MasterMagpie`, which is the sum of locked + cooldown balances in `mWomSV` (`getUserTotalLocked + getUserAmountInCoolDown`, wombat/mWomSV.sol:101-103,113-117) — no lock-state weighting is applied there either. So the reward-accrual rate is identical whether tokens are fully locked or 100% in cooldown, and the (only) mechanism meant to differentiate the two — forfeiture at claim time — is dead code.

An attacker can therefore: `lock()` mWOM to mint `mWomSV`/register stake in MasterMagpie → `startUnlock(fullAmount)` to move 100% into cooldown → wait for reward accrual (balance is still counted in MasterMagpie until `unlock()` finalizes withdrawal) → call `getReward`/`getRewards` and receive exactly the same reward-per-token as a user who kept everything locked, with zero forfeiture. No existing modifier (`onlyMasterMagpie`, `updateReward`, `nonReentrant`) prevents this, because they only gate access/ordering, not the (missing) penalty computation.

### Impact Explanation
This is a systemic breakage of the intended reward-differential/forfeiture mechanism (Immunefi class: theft of unclaimed yield / permanent misallocation of protocol yield). Every claim by every cooldown participant captures 100% of rewards that the system was designed to partially forfeit back into the pool (via `_queueNewRewardsWithoutTransfer`) for redistribution to fully-locked holders. Over time this results in continuous, protocol-wide yield leakage away from long-term lockers to any user willing to sit in cooldown, undermining the lock/cooldown incentive design for `mWomSV` holders.

### Likelihood Explanation
This requires no privilege and no capital beyond whatever mWOM the user wants to lock/claim rewards on. Preconditions are trivial and repeatable by any of the pool's own participants on every reward cycle: lock → start unlock for full balance → let cooldown run → claim, then repeat indefinitely for as long as their balance stays registered in `MasterMagpie` before finally withdrawing. Because `_calExpireForfeit` unconditionally returns 0 for every account, this is not a probabilistic or edge-case exploit — it is the deterministic behavior for 100% of claims through this rewarder.

### Recommendation
Wire `_calExpireForfeit` to actually apply `ILocker(mWOMSV).getRewardablePercentWAD(_account)` to compute `rewardableAmount = _amount * percent / 1e18`, mirroring the intended design already implemented in `mWomSV.getRewardablePercentWAD`. Add tests asserting that a 100%-in-cooldown user's `calExpireForfeit` returns a proportionally forfeited amount (not zero) whenever `getRewardablePercentWAD` < 100%.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder` with a reward token.
2. User A: `lock(1000e18)` and never unlocks (fully locked, `getRewardablePercentWAD == 1e18`).
3. User B: `lock(1000e18)`, then `startUnlock(1000e18)` immediately (100% cooldown, `getRewardablePercentWAD` should be < 1e18 until cooldown ends, and still < 1e18 if computed correctly even while unlocked-but-registered before withdraw).
4. Manager calls `queueNewRewards(rewardAmount, rewardToken)` to accrue rewards proportional to `totalStaked()`.
5. Both A and B call `getReward(self, self)` (via `MasterMagpie`, satisfying `onlyMasterMagpie`).
6. Assert: `calExpireForfeit(B, rewardToken)` returns `0` even though `getRewardablePercentWAD(B) < 1e18` — proving the dead code.
7. Assert: `RewardPaid` amounts for A and B are identical despite B's cooldown status, violating the intended reward differential/conservation invariant. [3](#0-2) [4](#0-3)

    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userMWOMSVShare) internal view returns (uint256) {
        return ((_userMWOMSVShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**mWOMSVDecimal) + userRewards[_rewardToken][_account];
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
