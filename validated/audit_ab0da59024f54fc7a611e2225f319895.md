### Title
Attacker-supplied `ReceivedOutput` values cause arithmetic overflow panic in `SignableTransaction::new`/`fee`, DoS-ing transaction construction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Panoptic bug class is "arithmetic on accumulated user-controlled amounts overflows the destination type and reverts, permanently DoS-ing a code path." The Serai analog lives in `SignableTransaction`: `ReceivedOutput` values are fully attacker-controlled 64-bit quantities (decoded without any `MAX_MONEY` bound in `ReceivedOutput::read`), and `SignableTransaction::new`/`fee()` sum them and add fees with unchecked `u64` arithmetic that panics on overflow.

### Finding Description
`ReceivedOutput::read` accepts arbitrary bytes: it reads a scalar offset and then `TxOut::consensus_decode`s the output [1](#0-0) . `TxOut::consensus_decode` reads a raw `u64` satoshi value; no check constrains it to 21M BTC, so a malicious byte stream yields a `ReceivedOutput` whose `output.value` is near `u64::MAX`.

That untrusted value flows into `SignableTransaction::new`, which computes the input total (`input_sat`, used at `networks/bitcoin/src/wallet/send.rs:215,228`) as a `u64` sum over the supplied `inputs: Vec<ReceivedOutput>`, and into `fee()`:

```rust
// networks/bitcoin/src/wallet/send.rs:139-140
self.prevouts.iter().map(|prevout| prevout.value.to_sat()).sum::<u64>() -
  self.tx.output.iter().map(|prevout| prevout.value.to_sat()).sum::<u64>()
``` [2](#0-1) 

`sum::<u64>()` over two outputs each ≥ `u64::MAX/2` wraps or panics (debug builds panic; this code is used in processor signing paths compiled with assertions in several places). Independently, `payment_sat + needed_fee` (line 215) and `payment_sat + fee_with_change` (line 228) are unchecked additions that panic on overflow before `checked_sub` is ever reached [3](#0-2) . Similarly `needed_fee = fee_per_vbyte * vbytes` (line 206) is an unchecked multiplication; `fee_per_vbyte` derives from `median_fee` which computes `(in_value - out) / vsize` over block transactions — `in_value` itself is a `u64` sum of prevout values that can underflow/overflow [4](#0-3) .

### Impact Explanation
A party able to supply serialized `ReceivedOutput`s (or outputs whose values propagate into a plan) can force a panic inside transaction construction/fee accounting, halting the signing pipeline for that key — the same self/permanent DoS shape as the Panoptic premia cast overflow, where a locally-computed value exceeds its type and the whole operation reverts. Funds are not stolen, but the multisig cannot produce the intended transaction.

### Likelihood Explanation
Reachable with public inputs: `ReceivedOutput::read` is on the untrusted-bytes list, and only two crafted outputs with large `value` fields are needed to overflow the `u64` sum. Requires the corrupted outputs to be fed into `SignableTransaction::new`, which is a plausible integrator/processor flow, hence Medium rather than High.

### Recommendation
Use `checked_add`/`saturating_add` (or a `u128` accumulator) when summing `prevout`/`output` values and when computing `payment_sat + needed_fee`; validate `TxOut` values against `Amount::MAX_MONEY` in `ReceivedOutput::read` so absurd values are rejected at decode time rather than overflowing downstream.

### Proof of Concept
```rust
// Craft two ReceivedOutputs each carrying value close to u64::MAX.
// ReceivedOutput::read accepts them since TxOut::consensus_decode
// performs no MAX_MONEY bound check (wallet/mod.rs:129).
let mut bytes = vec![];
bytes.extend(Scalar::ONE.to_bytes());               // offset
bytes.extend(u64::MAX.to_le_bytes());               // TxOut.value = u64::MAX sats
bytes.extend(0u64.to_le_bytes());                   // script_pubkey len = 0
bytes.extend([0u8; 32]); bytes.extend(0u32.to_le_bytes()); // outpoint
let a = ReceivedOutput::read(&mut &bytes[..]).unwrap();
let b = ReceivedOutput::read(&mut &bytes[..]).unwrap();

// input_sat = a.value() + b.value() overflows u64 -> panic / wrap,
// and fee() underflows on the subtraction, DoS-ing construction.
let _ = SignableTransaction::new(vec![a, b], &[], None, None, 1);
```
