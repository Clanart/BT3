### Title
Mtime-only "unchanged since baseline" heuristic lets attacker-controlled untracked-file edits bypass Stop-hook security review - (File: plugins/security-guidance/hooks/diffstate.py)

### Summary
`compute_v2_review_set`'s `_unchanged_since_baseline` helper decides whether a pre-existing untracked file is excluded from the Stop-hook review set purely by comparing `st_mtime_ns` to the value captured at `UserPromptSubmit` time. Any process capable of writing to that file (e.g., an attacker-influenced Bash command executed during the turn) can trivially restore the original mtime (`touch -r`, `os.utime`) after overwriting the content, causing the file to be silently classified as unchanged and excluded from vulnerability review.

### Finding Description
`_list_untracked` (`plugins/security-guidance/hooks/diffstate.py:319-351`) snapshots `{repo-relative path: st_mtime_ns}` for all untracked files at UPS time and stores it as `untracked_at_baseline`. At Stop time, `compute_v2_review_set` (lines 353-438) computes:

```
def _unchanged_since_baseline(p):
    base_mtime = untracked_at_baseline.get(p)
    if base_mtime is None:
        return False
    try:
        return os.stat(os.path.join(repo, p)).st_mtime_ns == base_mtime
    except OSError:
        return False
``` [1](#0-0) 

Files where this returns `True` are added to `preexisting_unchanged` and subtracted out before `new_untracked` is unioned into `dirty_now`, and ultimately into `review_set` [2](#0-1) . There is no content-hash or size fallback anywhere in this path — mtime equality is the sole signal used to decide "unchanged."

Because `git stash create` never captures untracked files (as the docstring itself notes at lines 171-174 [3](#0-2) ), untracked content changes are detected only through this mtime-diffing mechanism, and once a file is misclassified there is no secondary check (`changed_since` is derived from `git diff <stash_sha>`, which by construction has no knowledge of untracked-file content).

Exploit flow: an attacker who achieves any file-write capability during a Claude Code turn (e.g., via a prompt-injection-driven Bash command from a malicious repo/PR/issue, or a build script executed as part of normal automation) can:
1. Ensure a target file already exists as untracked before the turn starts (so it's captured in `untracked_at_baseline`).
2. During the turn, stat/copy the file to record its exact mtime (or simply keep a reference copy).
3. Overwrite the file content with malicious payload.
4. Restore the original mtime with nanosecond precision (`touch -r <reference> <file>` or `os.utime(path, ns=(atime_ns, mtime_ns))`).

Since setting a file's mtime is a normal, unprivileged filesystem operation available to whatever process already has write access to the file (no extra privilege required beyond the write access that is itself the actual precondition), this "attacker-controlled mtime" precondition is trivially satisfied whenever the primary write-capability precondition is met.

### Impact Explanation
A successfully forged file is excluded from `review_set` entirely, meaning the Stop hook's vulnerability scan never inspects its (malicious) content. This defeats the intended invariant that "the review set must reflect actual content changes, not spoofable mtime state," allowing attacker-authored/modified code in untracked files to slip past the plugin's Stop-hook security review undetected — a direct security-control bypass of the plugin's core protection mechanism.

### Likelihood Explanation
Feasibility is high: the only preconditions are (a) the target file already existing as untracked before the current turn's UPS baseline capture, and (b) the attacker having some write execution path during the turn (most plausibly Bash tool execution influenced by prompt injection from repository/PR/issue content, which is an explicitly in-scope reachable vector). Restoring an exact `st_mtime_ns` value is a one-line shell operation (`touch -r`) requiring no timing race or guessing — it is deterministic, not probabilistic, once the attacker has any write access to the file at all.

### Recommendation
Replace or augment the mtime-equality check with a content-hash comparison (e.g., SHA-256 of file bytes) computed at baseline capture and re-checked at Stop time; only treat a file as "unchanged" if both mtime and content hash match, or rely on content hash alone. This removes the spoofable single-signal dependency while preserving the intent of not re-reviewing untouched pre-existing WIP files.

### Proof of Concept
Unit test in the spirit of the existing `diffstate.py` test suite:
1. Create a temp git repo with an initial commit.
2. Create an untracked file `evil.txt` with benign content; call `_list_untracked(cwd)` to capture `untracked_at_baseline = {"evil.txt": mtime_ns}`.
3. Overwrite `evil.txt` with malicious content (e.g., a fake "vulnerable" marker string), then call `os.utime("evil.txt", ns=(mtime_ns, mtime_ns))` to restore the exact baseline mtime.
4. Call `compute_v2_review_set(cwd, baseline_sha, head_at_capture, untracked_at_baseline)`.
5. Assert `evil.txt` is **excluded** from the returned `review_paths` under current code (`_unchanged_since_baseline` returns `True`), demonstrating the bypass.
6. As the fix validation, add a content-hash check to `_unchanged_since_baseline` and assert that with the fix, `evil.txt` **is** included in `review_paths` because its content hash differs from the baseline-captured hash despite identical mtime.
