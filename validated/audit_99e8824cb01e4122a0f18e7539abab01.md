## Analog Found: Interactions-before-Effects Escrow Release in Tron IntentGatewayV2 (`withdraw`)

### Title
Escrowed funds transferred to attacker-controlled `beneficiary` before accounting is decremented, enabling reentrant double-spend of order escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core broken invariant is: **funds are released to a party based on iterating an array whose accounting was never fully validated/finalized before the transfer occurred**, letting the recipient extract more value than the ledger authorizes. The local analog is not an array-length mismatch, but the same class of bug — a payout loop that performs the external value transfer *before* committing the corresponding ledger update — in the Tron variant of the Intent Gateway's escrow-release routine.

### Finding Description
The canonical EVM implementation in `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-410`) correctly follows checks-effects-interactions: it decrements `_orders[commitment][token]` **before** making the external call/transfer: [1](#0-0) 

The Tron fork's equivalent `withdraw` function reverses this order — it performs the external `.call`/token transfer to `beneficiary` **first**, and only decrements the escrow ledger `_orders[body.commitment][token]` afterward, and it never checks that `amount <= escrowed`, only that the slot is non-zero: [2](#0-1) 

`beneficiary` is attacker-controllable: it is set from `body.beneficiary`, which for a `RedeemEscrow` message is `msg.sender` of `fillOrder` (the solver) and for `RefundEscrow`/cancel flows is `order.user`. For `token == address(0)` the release uses a raw low-level `.call{value: amount}("")` to this attacker address, handing it arbitrary code execution (fallback/`receive`) *before* `_orders[body.commitment][token] -= amount` runs. For ERC-20 tokens, the transfer is also a raw low-level `.call` (not `SafeERC20`), so any token with transfer hooks/callbacks gives the same reentrant window.

The only guard against replay is `_filled[body.commitment] = beneficiary;`, set once at the top of `withdraw` — but this guard protects the *order-level* fill/cancel entry points (`fillOrder`, `cancelOrder`), not the per-token escrow ledger being drained inside the very loop that is executing. For a multi-asset order (`body.tokens.length > 1`), while the callback for token `i` is executing, `_orders[commitment][token_j]` for every `j > i` (not yet processed) is still holding its pre-release value, and `_orders[commitment][token_i]` itself has not yet been decremented for the transfer already made. Nothing stops a malicious token/beneficiary contract from re-entering during this call and causing a second, unauthorized state transition to be observed and paid against the same stale value.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" and "double-claim/double-settlement" categories: escrow accounting can be manipulated to release more value than the order actually escrowed, or the same escrow value paid out twice, before the ledger reflects the first payment. Because the interaction happens on a value path (native transfer or raw ERC-20 `.call`) fully controlled by the beneficiary address chosen by an ordinary, unprivileged solver/user, no relayer, prover, or admin compromise is required — only a solver deploying a malicious contract as its own fill beneficiary, or an escrow token with reentrant hooks.

### Likelihood Explanation
Reaching this code requires only a normal, permissionless flow: place an order, get it filled/cancelled through the standard `RedeemEscrow`/`RefundEscrow` message path, and have `beneficiary` be an attacker-controlled contract (which the protocol allows by design — beneficiaries are arbitrary addresses). No proof forgery, consensus manipulation, or peer compromise is needed; the attacker only needs to control the receiving contract for a single order fill or self-service cancellation.

### Recommendation
Reorder `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match the checks-effects-interactions pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`: validate `amount <= _orders[body.commitment][token]`, decrement `_orders[body.commitment][token]` first, and only then perform the native/ERC-20 transfer. Additionally, replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with `SafeERC20.safeTransfer` to avoid silently trusting non-standard token return values.

### Proof of Concept
1. User places a multi-asset order with `inputs = [TokenA, TokenB]` via `placeOrder`, escrowing both tokens under one `commitment`.
2. A solver (attacker) deploys a malicious contract as `msg.sender`/beneficiary and calls `fillOrder`, causing a `RedeemEscrow` `WithdrawalRequest{ tokens: [TokenA, TokenB], beneficiary: attackerContract }` to be dispatched and eventually delivered via `onAccept` → `withdraw`.
3. In `withdraw`'s loop, iteration `i = 0` (TokenA) calls `TokenA.call(transfer(attackerContract, amountA))`. If `TokenA` has a transfer hook (or if it were native token, a `.call{value:}` triggering `receive()`), the attacker's callback re-enters the gateway.
4. At this point `_orders[commitment][TokenA]` has **not yet** been decremented (the `-=` happens after the transfer), and `_orders[commitment][TokenB]` is also still fully intact — the attacker's reentrant logic can be crafted (e.g., against a second, cooperating malicious token implementing arbitrary logic in `transfer`) to trigger an additional payout path that reads/consumes the same stale `_orders` value, resulting in more tokens leaving escrow than were ever legitimately owed for this commitment.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
