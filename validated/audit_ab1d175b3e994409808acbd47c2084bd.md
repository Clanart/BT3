### Title
Concurrency guard bypass in `_fetchRefspec` allows overlapping `git fetch` processes to race on shared repository state - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop serializes all network/git operations (`fetch`, `pull`, `push`) per-repository through a single `isPushPullFetchInProgress` flag enforced by `withPushPullFetch`. `_fetchRefspec`, however, explicitly does not go through this guard, by the maintainers' own admission in the code comment, so it can execute concurrently with a background fetch or a user-initiated fetch/pull/push against the very same on-disk git repository.

### Finding Description
`withPushPullFetch` is the single serialization primitive Desktop relies on to prevent concurrent git network operations from touching the same working copy at once: [1](#0-0) 

`_fetch`, `_fetchRemote`, `_pull`, and `_push` all funnel through `withPushPullFetch`/`performFetch`/`performPull`/`performPush`, which is the intended chokepoint: [2](#0-1) 

`_fetchRefspec`, used when checking out or viewing a pull request from a fork, deliberately skips this guard — the surrounding comment states it "does not opt-in to checks that prevent multiple concurrent network actions": [3](#0-2) 

The underlying git call is a plain `git fetch <remote> <refspec>` against the repository's own `.git` directory: [4](#0-3) 

Because Desktop also runs background/periodic fetches automatically (`FetchType.BackgroundTask`, routed through `performFetch`/`withPushPullFetch`), and because `_fetchRefspec` is reachable from PR-related flows such as `_findPullRequestBranch` (invoked when checking out a pull request whose head repo/ref is attacker-supplied via the GitHub API), it is possible for two independent `git fetch` invocations to run concurrently against the same repository: one from the ordinary serialized path, one from the unguarded `_fetchRefspec` path. `_findPullRequestBranch` takes `headCloneUrl`/`headRefName` straight from the PR object, and will call `_fetchRemote`/fetch flows using attacker-controlled remote URL/ref data: [5](#0-4) 

Concurrent `git fetch` processes against the same repository are a known source of race conditions on shared git state (packed-refs rewriting, `FETCH_HEAD`, `.git/shallow`, lock files), which can leave the repository's refs/objects in an inconsistent state without any error being surfaced to the user — analogous to the report's core problem of an operation whose correctness silently depends on serialized ordering that isn't actually guaranteed by the surrounding system.

### Impact Explanation
If exploited, the result would be corruption of local git metadata (refs, `FETCH_HEAD`, or packed-refs) caused by two overlapping fetches, potentially leaving the local branch state or the fork remote in an unexpected condition that the user is unaware of when next committing or pushing. This matches the "silent corruption of what the user commits or pushes" impact category, since Desktop's UI has no way to detect or report that the unguarded fetch collided with a concurrent one.

### Likelihood Explanation
The likelihood is **low-to-moderate**. It requires a timing coincidence between (a) the user or Desktop's own background timer triggering a normal fetch/pull/push, and (b) the user viewing/checking out a pull request from a fork (which triggers the unguarded `_fetchRefspec`/`_fetchRemote` path with attacker-influenced remote data via `headCloneUrl`). A malicious fork owner could increase the odds by making their clone URL resolve to a slow/stalling server, widening the race window, but this still depends on background fetch timing outside attacker control, and I could not find in the codebase any explicit evidence of an actual observed corruption (e.g. a bug report or test) confirming this race manifests in practice — this is inferred from generic git process-concurrency behavior, not a proven code-level guarantee violation like the DAML `require` check in the source report.

### Recommendation
Route `_fetchRefspec` through the same `withPushPullFetch` (or an equivalent per-repository mutex/queue) that serializes all other fetch/pull/push operations, instead of bypassing it. If bypassing is required for UX reasons (e.g. must complete promptly for PR preview), queue the concurrent request behind the in-flight operation rather than running both simultaneously, as the comment in the code itself already acknowledges is the correct long-term fix ("This might require some rework in the future to chain these actions").

### Proof of Concept
1. Open a repository in GitHub Desktop with automatic background fetch enabled.
2. Have a malicious actor open a pull request against the repository from a fork whose clone URL points to a remote/proxy they control (can be deliberately slow to respond).
3. As the victim views or checks out that pull request in Desktop, `_findPullRequestBranch` → `_fetchRemote`/`_fetchRefspec` is triggered using the attacker-supplied `cloneURL`/`ref`.
4. Simultaneously (naturally, via Desktop's periodic background fetch or another user-initiated push/pull that only checks `isPushPullFetchInProgress`, which `_fetchRefspec` never sets), a second `git fetch` runs on the same repository concurrently.
5. Two concurrent `git fetch` processes race on shared git internal files (`FETCH_HEAD`, packed-refs, lock files), risking an inconsistent local repository state that is not reported to the user.

Note: I was unable to find a direct reproduction/test in the repository proving actual corruption from this race; this assessment is based on the documented bypass of the serialization guard combined with general git fetch-concurrency risk, not an observed failure in this codebase.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }
