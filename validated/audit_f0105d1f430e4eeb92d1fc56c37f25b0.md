### Title
Association can orphan pre-existing staking delegation and distribution rewards under a direct-cast identity - ([File: utils/helpers/associate.go])

### Summary
Sei's EVM address-association flow (`AssociationHelper.AssociateAddresses` / `MigrateBalance`) mirrors the bug class in the external report: when a user's identity is "migrated" from one on-chain address representation to another, only bank/wei balances are swept to the new (true) address, while any staking delegation and its accrued distribution rewards that were created under the old (direct-cast) address are left behind and become permanently unreachable once the association is finalized.

### Finding Description
`AssociationHelper.AssociateAddresses` and `MigrateBalance` [1](#0-0)  move only `SpendableCoins` and the wei balance from the direct-cast address (`sdk.AccAddress(evmAddr[:])`) to the newly associated "true" sei address. There is no code path that moves staking delegations, unbonding entries, or distribution `DelegatorStartingInfo`/rewards from the cast address to the associated address.

The keeper explicitly documents this asymmetry: once an EVM address is associated with a sei address, `CanAddressReceive` permanently blocks that direct-cast address from receiving further bank funds [2](#0-1) , yet nothing similarly prevents or repairs staking/distribution state that already exists under that cast identity.

The staking precompile's own code comments acknowledge this exact failure mode and work around it only by *refusing to delegate from an unassociated caller*, not by fixing migration if a delegation already exists under the cast identity: "if delegator is associated, then it must have Account set already; if delegator is not associated, then it can't delegate anyway (since there is no good way to merge delegations if it becomes associated)" [3](#0-2) , and more explicitly in `delegateFor`: "the delegator must be explicitly associated because a later association cannot safely merge a delegation created under its cast address" [4](#0-3) .

The EIP-7702 `SetCode` pre-association helper documents the concrete attack/loss surface directly: "Without this, SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey call can remap, orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)" [5](#0-4)  and again in `utils/helpers/address.go`: "a publicly-visible authorization a user signed for another chain ... could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their direct-cast balance and orphaning staking/distribution state" [6](#0-5) .

This is functionally identical to the reported bug class: a "migration" operation (association) transfers the primary asset (bank balance / voting power) to the new address, but forgets to move the auxiliary reward/stake state (staking delegation + distribution rewards) tied to the old address, permanently orphaning it.

### Impact Explanation
If a direct-cast address (`sdk.AccAddress(evmAddr[:])`) accumulates a staking delegation and its distribution rewards before that EVM address becomes associated with its true pubkey-derived sei address, the delegation and any accrued/future rewards remain keyed to the cast address. Once association occurs (either voluntarily via `Associate`/`AssociatePubKey` precompile calls, or via SetCode authority pre-association, or automatically via the ante-handler's `EVMAddressDecorator` on the user's next signed transaction), the cast address's bank balance is swept, but the delegation is not moved. The user has no supported way to unstake/withdraw rewards from the cast address afterward, since the cast address is not really a key-controlled address for producing valid Cosmos signatures (the associated pubkey/signature scheme resolves to the true, hash-derived sei address, not the raw EVM-byte cast address), and any attempt to interact with the delegation through the precompile requires the caller be already associated — permanently freezing the delegated funds and any distribution rewards.

### Likelihood Explanation
Reaching this state requires funds/delegations to exist under the direct-cast address prior to association, which is an edge case the code authors were clearly aware of (see the extensive comments above) and partially defended against by blocking new delegations from unassociated callers and by pre-associating SetCode authorities. However, the underlying "association doesn't migrate staking/distribution state" gap itself is not remediated — only some entry points into it are blocked. Any remaining code path that lets a cast address end up with a delegation (e.g., a raw Cosmos `MsgDelegate` broadcast with `DelegatorAddress` set to the cast address bytes before that account is ever associated, or IBC/wasm-originated delegations to a cast address) still triggers permanent loss upon later association.

### Recommendation
When `AssociationHelper.AssociateAddresses`/`MigrateBalance` associates a cast address with its true sei address, also detect and migrate any existing staking delegations, unbonding delegations, and pending distribution rewards from the cast address to the new address (e.g., withdraw rewards to the associated address, then re-delegate/transfer the delegation record), or explicitly block association entirely while the cast address still holds any delegation, mirroring the existing check for `LockedCoins` before removing the cast account.

### Proof of Concept
Conceptual, since a live PoC would need a path that gets a delegation recorded against a cast address (raw `sdk.AccAddress(evmAddr[:])`) prior to association:
1. Obtain a fresh EVM address `E` whose corresponding cast address `C = sdk.AccAddress(E[:])` is not yet associated with any sei address.
2. Get `C` to hold a staking delegation and let distribution rewards accrue (e.g., via a raw Cosmos `MsgDelegate` with `DelegatorAddress = C`, bypassing the staking precompile's association check which only guards its own entry point).
3. Trigger association for `E` (e.g., sign any Sei transaction with the key deriving `E`, or call `Associate`/`AssociatePubKey`), which invokes `AssociationHelper.AssociateAddresses` → `MigrateBalance` [1](#0-0) .
4. Observe that `SpendableCoins`/wei balance move to the new sei address, but the delegation and its distribution `DelegatorStartingInfo`/rewards remain under `C`.
5. Because `C` cannot be a valid signer once association exists and because delegation-affecting precompile calls require the caller already be associated [4](#0-3) , the delegated stake and rewards under `C` become permanently unreachable.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// from an EVM address AND the originating EVM address has already been associated with

func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}
