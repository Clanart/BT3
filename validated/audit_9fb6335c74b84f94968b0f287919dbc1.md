### Title
Silent zero-value fallback in collateral valuation lookup instead of reverting causes an incorrect health verdict on withdrawal - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`find-and-resolve-asset-value()` mirrors the same anti-pattern flagged in the external report: instead of reverting when a required lookup fails, it silently returns a default value (`u0`) and lets execution continue as if nothing were withdrawn. Just as `isAffiliatedWithProof()` quietly returned `false` on a broken/incorrect affiliate proof (skipping payment rather than reverting), `find-and-resolve-asset-value()` quietly returns `u0` when the target asset cannot be found in the caller-supplied `assets` list (skipping valuation rather than reverting), and this value feeds directly into the post-withdrawal health check.

### Finding Description
In `collateral-remove`, when the withdrawn asset is currently collateral-enabled, the code computes the USD value of the asset being removed via: [1](#0-0) 

```
(removed-asset-value (find-and-resolve-asset-value assets asset-id amount true))
...
(post-removal-collateral-value (- collateral-value removed-asset-value))
...
(is-healthy post-removal-collateral-value debt-value current-ltvb)
```

`find-and-resolve-asset-value` is defined to fall back to `u0` if the target asset id is not present in the `assets` list, rather than reverting: [2](#0-1) 

```
(define-private (find-and-resolve-asset-value ...)
  (match (find-asset asset-id assets)
    asset (normalize (* amount (get price asset)) (get decimals asset) round-up)
    u0))
```

`assets` is derived from `get-assets position-mask`, which intersects the user's position mask with the globally *enabled* bitmap (`user-safe-mask`) before resolving prices: [3](#0-2) 

If the withdrawn asset-id is excluded from that intersected set for any reason (e.g., a timing/consistency gap between the asset's live `collateral` flag read via `get-asset` and the state of the enabled bitmap used to build `assets`), `find-asset` returns `none`, and `find-and-resolve-asset-value` silently substitutes `u0` for the value actually being withdrawn. The health check then subtracts `0` instead of the true withdrawal value, so `post-removal-collateral-value` remains at the pre-withdrawal collateral value and the `is-healthy` check is evaluated against a value that does not reflect the asset leaving the position.

This is the same bug class as the affiliate report: a lookup that can plausibly fail is treated as "fall back to a safe-looking default" instead of "abort the whole operation," and the silently-substituted default feeds directly into a financial decision (there: whether to pay a fee; here: whether a withdrawal keeps the position healthy).

### Impact Explanation
If reachable, this allows a user to withdraw enabled collateral without that collateral's value being deducted from `collateral-value` in the health check, letting an otherwise-unhealthy withdrawal pass as healthy. This is a direct path to under-collateralized positions and protocol insolvency (theft of user/protocol funds at rest), landing in the Critical impact category (protocol insolvency / theft of funds).

### Likelihood Explanation
Likelihood is uncertain and could not be fully confirmed with the available static analysis: it hinges on whether there exists a realistic state where `(get collateral asset)` (read live via `get-asset`) is `true` while the same asset-id is simultaneously excluded from the `mask-enabled` bitmap used inside `get-assets`. I was not able to conclusively trace whether these two signals are always kept in lockstep by the `assets`/registry contract, or whether an intervening admin action (e.g., disabling an asset in the enabled bitmap without atomically flipping the `collateral` flag, or vice versa) can desynchronize them within a single transaction. This should be verified directly against `mainnet/contracts/registry/v0-assets.clar` (bitmap and status-flag update logic) before treating this as confirmed-exploitable.

### Recommendation
Change `find-and-resolve-asset-value` (and any other value-lookup helper that currently defaults to `u0` on a missed lookup and feeds a health/LTV computation) to revert with a dedicated error (e.g. `ERR-ASSET-NOT-FOUND`) instead of returning `u0`, mirroring the fix applied in PR #42 for the affiliate case (revert instead of silently skipping):

```
(define-private (find-and-resolve-asset-value ...)
  (match (find-asset asset-id assets)
    asset (normalize (* amount (get price asset)) (get decimals asset) round-up)
    (unwrap-panic (err ERR-ASSET-NOT-FOUND))))
```

Additionally, audit `mainnet/contracts/registry/v0-assets.clar` to confirm whether the `collateral` status flag and the enabled bitmap can ever diverge for the same asset id within `collateral-remove`'s execution window, and if so, ensure `get-assets`/`is-collateral-enabled` derive from a single consistent source of truth.

### Proof of Concept
Not independently reproduced — a concrete PoC requires confirming (via `mainnet/contracts/registry/v0-assets.clar`) a reachable state where `(get collateral asset)` is `true` for `asset-id` while that same `asset-id`'s bit is absent from the bitmap consumed by `get-assets position-mask` at the time `collateral-remove` executes. If such a state is confirmed reachable, the PoC would be: get the asset into that desynchronized state, call `collateral-remove` for the full amount of that asset while holding debt, and observe `removed-asset-value` computed as `0`, allowing the health check to pass despite the real collateral value leaving the position.
