### Title
Scanner accepts zero-value and dust outputs as spendable funds, allowing unspendable/dust UTXOs to be registered as received balance - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
In the reference bug, the absence of a *minimum* size check lets anyone create a size-0 protection, polluting a set iterated by critical logic. The analog in Serai's Bitcoin wallet is the same class: `Scanner::scan_transaction` performs a single check — whether `output.script_pubkey` matches a registered script — and pushes a `ReceivedOutput` regardless of `output.value`. Any party who sends a 0-value or below-dust-threshold output to the tweaked deposit key causes the wallet to register it as a received, "spendable" output.

### Finding Description
`scan_transaction` iterates `tx.output` and accepts any output whose `script_pubkey` is in `self.scripts`, built from `Scanner::new` and `register_offset`. There is no check on `output.value` before constructing `ReceivedOutput`:

```rust
// networks/bitcoin/src/wallet/mod.rs
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

`ReceivedOutput::value()` simply returns `self.output.value.to_sat()`, so downstream consumers (fee selection, `send` logic, any balance accounting) see a 0-sat or 1-sat output as a legitimate input candidate. Zero-value outputs are consensus-valid (`value >= 0`), so a miner — or anyone cooperating with one — can include a transaction paying 0 sats to the Serai address. Ordinary dust (e.g., a few hundred sats) is creatable through normal relay depending on the script size.

### Impact Explanation
- Funds reported received that are not economically spendable: a dust/zero output can never be spent without paying a fee larger than its value. Balance reporting overstates usable funds.
- Fee drainage / signing griefing: if the `send` path selects these outputs as inputs, each one consumes input weight (~57.5 vbytes for a key-spend input) while contributing nothing, inflating the fee the multisig must sign — and potentially producing transactions that fail mempool dust/feerate policy, stalling withdrawals.
- This mirrors the external report directly: an unprivileged party injects a zero-value entry into a set the wallet iterates over, degrading the spend path. Note: I did not fully verify the `send.rs` input-selection logic due to tool limits; the impact assumes it consumes all `ReceivedOutput`s rather than filtering uneconomical ones — if it already filters dust inputs, the residual impact is only incorrect balance reporting.

### Likelihood Explanation
Creating a dust output to the tweaked P2TR address requires only a standard Bitcoin transaction — no validator status, no key material. A zero-value output needs miner inclusion (non-standard but consensus-valid). This is reachable by any external party, matching "anyone can buy a size-0 protection".

### Recommendation
Enforce a minimum-value check in `Scanner::scan_transaction` (or when constructing `ReceivedOutput`): skip outputs with `output.value` below the dust threshold for the script type (`script_pubkey.dust_value()` from rust-bitcoin). At minimum, expose the value filter so callers cannot treat dust as spendable balance.

### Proof of Concept
```rust
// Conceptual: attacker crafts tx paying 0 sats to Serai's tweaked key
let tx = Transaction {
  // ...
  output: vec![TxOut {
    value: Amount::ZERO,          // or Amount::from_sat(1)
    script_pubkey: serai_p2tr_script, // matches Scanner's registered script
  }],
};
let received = scanner.scan_transaction(&tx);
assert_eq!(received.len(), 1);
assert_eq!(received[0].value(), 0); // registered as "received funds" worth 0 sats
// Any downstream spend that includes this input pays a fee for a worthless input
```

The analog holds on the root cause — absent lower-bound validation on a publicly-injectable element entering a set the protocol iterates — and is reachable purely by a public Bitcoin transaction.
