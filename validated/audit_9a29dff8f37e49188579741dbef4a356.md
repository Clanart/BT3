### Title
Unbounded recursive memo parsing in `PuzzleWithRestrictions.from_memo()` allows a crafted CREATE_COIN memo to crash wallet coin-processing via uncaught `RecursionError` - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs an `MofN` custody tree from an attacker-controlled CLVM memo with no depth limit, mirroring the Scriban `ExpressionDepthLimit`-is-non-enforcing bug class (CWE-674): there is no cap on recursion depth before Python's parser exhausts the call stack. The only caller found in this codebase that consumes untrusted, attacker-supplied memo data — `PlotNFT.get_next_from_coin_spend()` in `chia/pools/plotnft_drivers.py` — only catches `ValueError`, not `RecursionError`, so a coin whose `CREATE_COIN` memo encodes a deeply nested `MofN` custody structure can raise an uncaught `RecursionError` when a wallet processes that coin during sync.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is defined as: [1](#0-0) 

When `further_branching` is true (the memo declares an `MofN` node), it parses `MofNHint.member_memos` and recurses into `PuzzleWithRestrictions.from_memo(memo)` once per member — with no bound on how many `MofN` layers can be nested:

```
puzzle: MIPSComponent = MofN(
    m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
)
```

The memo blob being parsed here is not consensus-checked data — it is the `memo_blob` attached to a `CREATE_COIN` condition, which any spender can set to an arbitrary CLVM value at essentially no extra CLVM cost relative to its byte size (unlike puzzle execution cost, nesting depth in a memo atom/list structure is cheap). The reachable, in-scope caller is: [2](#0-1) 

which unwraps `singleton_create_coin.memo_blob.rest()` and feeds it straight into `PuzzleWithRestrictions.from_memo()`, guarding only against `ValueError`:

```

    unknown_inner_puzzle = PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())
except ValueError:
    raise GetNextPlotNFTError("Invalid memoization of PlotNFT")
```

A `RecursionError` raised inside the deeply nested `from_memo` recursion is **not** a `ValueError`, so it propagates past this handler uncaught. `get_next_from_coin_spend()` is exercised from wallet-side PlotNFT/pool sync code (`chia/wallet/plotnft_wallet/plotnft_wallet.py`), which processes plot-NFT singleton coin spends observed on-chain — data that originates from spends any actor can construct and have accepted, since the singleton's `CREATE_COIN` memo content is not consensus-validated CLVM logic, only opaque bytes attached to the coin.

This is the same bug class as the reported Scriban issue: a documented "depth limit" concept exists informally in the recursive-descent style of `from_memo`, but nothing enforces or catches an excessive-depth condition before the interpreter's native/py call-stack limit is hit. Unlike .NET's uncatchable `StackOverflowException`, CPython raises a catchable `RecursionError` — but the catching code here does not catch it, so from the caller's point of view the effect is equivalent: an unhandled exception that aborts processing of that coin/spend.

### Impact Explanation
A malicious or malformed singleton spend whose `CREATE_COIN` memo encodes a sufficiently deep nested `MofN` custody hint causes `PuzzleWithRestrictions.from_memo()` to raise an uncaught `RecursionError` inside `PlotNFT.get_next_from_coin_spend()`. Because the enclosing `try/except` only catches `ValueError`, this exception propagates into wallet plot-NFT/pool-sync processing, which is a spend-triggered processing halt for any wallet client that walks that singleton's lineage (repeated on every resync attempt until the offending coin/spend is skipped or the code is patched). This matches the "spend-triggered transaction-processing halt" impact category for wallet/pool-participant reachable code.

The severity is bounded by two facts I could not eliminate given index limitations: (1) I could not fully trace every code path that reaches `PuzzleWithRestrictions.from_memo()` at scale (e.g., whether this is invoked automatically and unconditionally during ordinary wallet sync of any coin, or only when explicitly following known plot-NFT/pool coin lineages), and (2) CPython's default recursion limit (~1000) means the required nesting is much shallower than the C-level stack-overflow scenario in the original report, so the "process termination" severity of the .NET CVE does not directly transfer — the Python failure mode is a catchable-but-uncaught exception, not guaranteed process death.

### Likelihood Explanation
Constructing the malicious memo requires only crafting a `CREATE_COIN` condition with a deeply nested list-of-lists memo blob shaped like the `MofNHint`/`PuzzleWithRestrictions` memo format — this is cheap in CLVM terms and does not require any privileged role, matching the "unprivileged spend-bundle submitter" reachability bar. However, likelihood of actually being hit depends on whether other wallets/pool participants actively walk that specific coin's plot-NFT lineage, which I could not fully confirm from the available context.

### Recommendation
- Add an explicit depth counter/limit parameter to `PuzzleWithRestrictions.from_memo()` (and its recursive `MofN` branch) and raise a well-defined, caught exception type (e.g. `ValueError`) once the limit is exceeded, rather than relying on the interpreter's default recursion limit.
- In `PlotNFT.get_next_from_coin_spend()`, broaden the `except ValueError` around `PuzzleWithRestrictions.from_memo(...)` to also catch `RecursionError` (or, better, catch the new bounded-depth exception type raised by the hardened `from_memo`), converting it into `GetNextPlotNFTError` so malformed/hostile memos fail gracefully instead of crashing sync.
- Audit all other callers of `PuzzleWithRestrictions.from_memo()` for the same missing-catch pattern before this code is exposed to untrusted on-chain memo data more broadly.

### Proof of Concept
Construct a `CREATE_COIN` memo blob nested as:
```
(CHIP-0043
  [nonce, [], 1,
   [1, [ (CHIP-0043 [nonce, [], 1, [1, [ ... nested MofNHint ... ]]]) ]]
  ]
)
```
repeated ~1000+ times (bounded by CPython's default `sys.getrecursionlimit()`), and attach it as the `memo_blob` of a `CREATE_COIN` condition on a plot-NFT-style singleton spend. Feeding the resulting `CoinSpend` through `PlotNFT.get_next_from_coin_spend()` (as exercised by `chia/wallet/plotnft_wallet/plotnft_wallet.py` during pool/plot-NFT sync) causes `PuzzleWithRestrictions.from_memo()` to recurse through each nested `MofNHint.member_memos` entry until Python's recursion limit is hit, raising an uncaught `RecursionError` that is not handled by the surrounding `except ValueError:` block in `chia/pools/plotnft_drivers.py`.
