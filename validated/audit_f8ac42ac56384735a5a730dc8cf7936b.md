### Title
`burn_with_instruction` succeeds on Serai while the Bitcoin wallet can never construct the payment — burned funds are permanently lost (and can stall the payment scheduler) - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The source-side burn (`Coins::burn_with_instruction` in `substrate/coins/pallet/src/lib.rs:243-255`) executes unconditionally — it burns the user's sriBTC and emits a `BurnWithInstruction` event without validating that the resulting `Payment` is constructible on Bitcoin. The destination-side constraint (a payment must be ≥ dust, 546 sats) is only enforced later inside `SignableTransaction::new` at `networks/bitcoin/src/wallet/send.rs:165-169`, which returns `TransactionError::DustPayment` *after* the coins are already burned. Because the burn is irreversible and the payment can never be built, the user loses the burned funds — the same shape as the EYWA report where `BURN_UNLOCK_CODE` succeeds on the source chain but the destination check fails.

### Finding Description
An unprivileged user calls `burn_with_instruction` with `balance.coin = ExternalCoin::Bitcoin` and `amount < 546` (or any amount that makes the payment non-constructible, e.g., pushing the transaction over `MAX_STANDARD_TX_WEIGHT` at `send.rs:241-243`, or making `needed_fee` exceed available inputs). `burn_internal` succeeds and the `BurnWithInstruction` event is emitted (`substrate/coins/pallet/src/lib.rs:252-253`). The processor converts burns to `Payment`s in `burns_to_payments` (`processor/src/multisigs/mod.rs:295-310`), which performs only `N::Address::try_from` — no amount validation. The scheduler then passes `payments` to `SignableTransaction::new`, which rejects any `amount < DUST` at `send.rs:165-169` and returns `Err(TransactionError::DustPayment)`. Every `SignableTransaction::new` call containing the dust payment fails, so the transaction is never signable, yet the sriBTC was already burned and supply/balance were zeroed. Additionally, because payments are batched into a single `SignableTransaction`, one dust payment poisons the entire payment set: every attempt to build the batch transaction errors before signing, preventing *all* queued payments from being constructed until the poisoned payment is resolved.

### Impact Explanation
Two impacts, both reachable with public inputs:
1. **Permanent fund loss**: the user's sriBTC is burned on Serai while no Bitcoin output can ever be created — the funds are unrecoverable, matching the "burn succeeds / destination fails" class. There is also no refund path: `burns_to_payments` has no mechanism to re-credit failed payments.
2. **Withdrawal liveness DoS**: a single dust burn poisons `SignableTransaction::new` for the entire `payments` slice, so every legitimate withdrawal queued alongside it fails transaction construction repeatedly — a griefing vector that stalls the network's payout pipeline for the cost of a dust burn.

### Likelihood Explanation
Any Serai account holder can call `burn_with_instruction` with arbitrary `amount` and `address` — no special privileges required. The spec explicitly states "No validation of external addresses/data is performed on-chain" (`spec/integrations/Instructions.md:57`), confirming the burn path intentionally performs no destination-side checks. Nothing in the burn call chain reverts on a sub-dust amount; the only check is `burn_internal`'s balance check. The failure only manifests on the processor side where `send.rs` enforces Bitcoin consensus/policy limits — precisely the asymmetric-validation pattern of the reference bug.

### Recommendation
Mirror the destination-side invariants on the burn side, analogous to the report's recommendation to check the whitelist in `Synthesis`:
- In `Coins::burn_with_instruction` (or via a per-network `OutInstruction` validator), reject `amount < DUST` for Bitcoin-network coins and enforce `Data` length limits so a burn can only emit payments that `SignableTransaction::new` would accept.
- Alternatively, in `burns_to_payments`, filter non-constructible payments (dust amounts, oversized aggregate batches) the same way invalid addresses are dropped, and re-credit or escrow the burned balance rather than silently losing it — the current silent-drop of invalid addresses already loses user funds, only the dust case additionally stalls the whole batch.

### Proof of Concept
1. User acquires any amount of sriBTC (e.g., via an `InInstruction::Transfer` mint).
2. User submits `SeraiCoins::burn_with_instruction(OutInstructionWithBalance { balance: ExternalBalance { coin: ExternalCoin::Bitcoin, amount: Amount(545) }, instruction: OutInstruction { address: <valid p2wpkh ExternalAddress>, data: None } })`.
3. `burn_with_instruction` succeeds: balance and supply are zeroed, `BurnWithInstruction` event emitted (`substrate/coins/pallet/src/lib.rs:251-254`; identical pattern verified in `substrate/coins/pallet/src/tests.rs:47-97`).
4. Processor sees the burn in a `SubstrateBlock`, `burns_to_payments` creates `Payment { address, balance: 545 sats }` since the address parses (`processor/src/multisigs/mod.rs:307-308`).
5. Scheduler calls `SignableTransaction::new(inputs, payments, change, data, fee_per_vbyte)` → `*amount < DUST` → `Err(TransactionError::DustPayment)` (`networks/bitcoin/src/wallet/send.rs:165-169`). The transaction is never constructed, never signed by `TransactionMachine`, and never broadcast.
6. The user's 545 sats of backing BTC remain in the multisig while their sriBTC is destroyed — permanent loss. Any other payments batched with this one also fail `SignableTransaction::new` on every attempt, stalling all withdrawals until intervention.

Uncertainty note: the exact scheduling/retry behavior of the processor around a `TransactionError` (whether the poisoned payment is eventually dropped or blocks the queue indefinitely) lives in `processor/`, which is outside the enumerated in-scope files; the drop itself is confirmed at `processor/src/multisigs/mod.rs:307-309` and the unconditional rejection at `networks/bitcoin/src/wallet/send.rs:165-169`. Either outcome preserves the core finding — burned funds that can never be paid out.
