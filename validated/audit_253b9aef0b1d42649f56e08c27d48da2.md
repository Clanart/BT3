### Tampered `ThresholdKeys` deserialization lets an attacker enroll a victim share in a rogue signing set - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary

`ThresholdKeys::read` accepts serialized parameters, a secret share, and arbitrary verification shares, but neither authenticates the serialized state nor verifies that the supplied secret share corresponds to that participant’s public verification share. `ThresholdKeys::new` then derives `group_key` solely from the attacker-controlled verification shares for participants `1..=t`. An attacker who can feed modified bytes to `ThresholdKeys::read` can preserve a victim’s secret-share field while replacing the participant metadata and other verification shares, causing the victim to participate in a FROST signature for an attacker-constructed group key. [1](#0-0) [2](#0-1) 

### Finding Description

The vulnerable sequence is:

1. `ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation method, the secret share, and every verification share from caller-controlled bytes. [3](#0-2) 
2. It delegates to `ThresholdKeys::new`, which checks only the number and participant range of verification shares. It does not check that `verification_shares[i] == G * secret_share`, does not authenticate the serialized state, and does not bind the public metadata to the secret share. [4](#0-3) 
3. `ThresholdKeys::new` computes the group key from verification shares `1..=t`, regardless of which participant’s secret share was supplied. [5](#0-4) 
4. During signing, `ThresholdKeys::view` interpolates the supplied secret share for the attacker-selected signing set. [6](#0-5) 
5. `AlgorithmSignMachine::sign` derives the signing set from attacker-supplied preprocess participant IDs and calls `view(included)`. [7](#0-6) 
6. `AlgorithmSignatureMachine::complete` validates the aggregate signature against the tampered `view.group_key()`. [8](#0-7) 

Because the verification shares are arbitrary points, the attacker can choose values satisfying a rogue interpolation identity even though the victim secret share remains unchanged. In particular, the attacker can keep the victim’s legitimate public share at participant `i`, place attacker-known shares in the actual signing set, and place a correction point in an index used for the `1..=t` group-key calculation but excluded from the signing set.

For example, with serialized `t = 2`, `n = 3`, victim `i = 3`, and signing set `{2, 3}`:

- `V3 = G * s3` is the victim’s original public share.
- `V2 = G * s2`, where `s2` is known to the attacker.
- `V1` is chosen as the correction point satisfying:

```text
λ'(1,2,1) * V1 + λ'(1,2,2) * V2
  = λ(2,{2,3}) * V2 + λ(3,{2,3}) * V3
```

Then `ThresholdKeys::new` computes a group key whose discrete logarithm equals:

```text
λ(2,{2,3}) * s2 + λ(3,{2,3}) * s3
```

The attacker does not know `s3`, but does not need to know it: participant `3` supplies the valid share using the preserved victim secret, while participant `2` supplies a valid share using `s2`.

### Impact Explanation

An attacker able to modify serialized `ThresholdKeys` before `ThresholdKeys::read`, and then supply preprocesses through `read_preprocess` and `sign`, can cause the holder of an existing secret share to produce a valid threshold signature under an attacker-constructed group key. This is concrete signing under an unintended key/state, not merely deserialization malleability. The signing path accepts the rogue participant set and validates the result against the rogue group key. [9](#0-8) [10](#0-9) 

### Likelihood Explanation

The attack requires attacker-controlled bytes to reach `ThresholdKeys::read` and attacker-controlled preprocesses to reach `read_preprocess`/`sign`. Those are exposed input surfaces. It does not require knowledge of the victim’s secret share: only the victim’s public verification share must be retained or recreated. The attacker must also choose a signing set for which they can produce the remaining threshold shares.

The core issue is that deserialization is treated as sufficient authority to redefine the participant set, threshold, group key, and all other verification shares without authentication or consistency checks tying the preserved secret share to the original key state. [2](#0-1) 

### Recommendation

- Treat serialized `ThresholdKeys` as privileged state requiring integrity/authenticity protection, such as an authenticated storage format or a keyed MAC over the complete serialization.
- At minimum, add a consistency check in `ThresholdKeys::new` that `verification_shares[params.i()] == C::generator() * secret_share`. This catches malformed shares but is not sufficient to prevent rogue substitution of all other participants’ shares.
- Cryptographically bind the serialized state to an externally established session identity and original group key so an attacker cannot replace unrelated verification shares.
- Consider including a commitment to the complete participant public-share set in the serialization and verifying it against a trusted source before signing.
- Ensure signing callers do not accept participant sets or preprocesses that differ from the authenticated signing session.

### Proof of Concept

The following construction demonstrates the state substitution mathematically. It assumes the attacker can patch the serialized public metadata while leaving the victim’s secret-share field unchanged.

```rust
// Starting from valid serialized ThresholdKeys for victim participant 3:
//   t = 2, n = 3, i = 3, secret = s3,
//   V1 = G*s1, V2 = G*s2_original, V3 = G*s3.
//
// The attacker selects s2 and sets:
//
//   V2' = G*s2
//
// The attacker solves for correction point V1':
//
//   lagrange(1, {1,2}) * V1' + lagrange(2, {1,2}) * V2'
//     = lagrange(2, {2,3}) * V2' + lagrange(3, {2,3}) * V3
//
// Therefore:
//
//   V1' = (
//     lagrange(2, {2,3}) * V2'
//     + lagrange(3, {2,3}) * V3
//     - lagrange(2, {1,2}) * V2'
//   ) / lagrange(1, {1,2})
//
// The attacker serializes:
//   t = 2, n = 3, i = 3, interpolation = Lagrange,
//   secret = s3, verification_shares = [V1', V2', V3].
//
// ThresholdKeys::read accepts this state.
//
// A matching fabricated participant-2 key contains secret s2 and
// the same verification shares [V1', V2', V3].
//
// FROST is then run with included set {2,3}. Participant 3 uses the
// preserved victim secret s3; participant 2 uses attacker-known s2.
// The aggregate signature verifies under the rogue group key computed
// from [V1', V2'].
```

The relevant missing check is that `read` never establishes authenticity or semantic consistency for the deserialized key before it is used to construct a `ThresholdView` and produce a FROST share. [11](#0-10) [12](#0-11)

  pub fn view(&self, mut included: Vec<Participant>) -> Result<ThresholdView<C>, DkgError> {
    if (included.len() < self.params().t.into()) ||
      (usize::from(self.params().n()) < included.len())
    {
      Err(DkgError::IncorrectAmountOfParticipants {
        t: self.params().t,
        n: self.params().n,
        amount: included.len(),
      })?;
    }
    included.sort();
    {
      let mut found = included[0] == self.params().i();
      for i in 1 .. included.len() {
        if included[i - 1] == included[i] {
          Err(DkgError::DuplicatedParticipant(included[i]))?;
        }
        found |= included[i] == self.params().i();
      }
      if !found {
        Err(DkgError::NotParticipating)?;
      }
    }
    {
      let last = *included.last().unwrap();
      if u16::from(last) > self.params().n() {
        Err(DkgError::InvalidParticipant { n: self.params().n(), participant: last })?;
      }
    }

    // The interpolation occurs multiplicatively, letting us scale by the scalar now
    let secret_share_scaled = Zeroizing::new(self.scalar * self.original_secret_share().deref());
    let mut secret_share = Zeroizing::new(
      self.core.interpolation.interpolation_factor(self.params().i(), &included) *
        secret_share_scaled.deref(),
    );

    let mut verification_shares = HashMap::with_capacity(included.len());
    for i in &included {
      let verification_share = self.core.verification_shares[i];
      let verification_share = verification_share *
        self.scalar *
        self.core.interpolation.interpolation_factor(*i, &included);
      verification_shares.insert(*i, verification_share);

      The offset is included by adding it to the participant with the lowest ID.

      This is done after interpolating to ensure, regardless of the method of interpolation, that

      add the offset to every key share before interpolating, yet for Constant interpolation, we
      _have_ to add it as we do here (which also works even when we intend to perform Lagrange
      interpolation).
    */
    if included[0] == self.params().i() {
      *secret_share += self.offset;
    }
    *verification_shares.get_mut(&included[0]).unwrap() += C::generator() * self.offset;
