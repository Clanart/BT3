### Title
`SignableTransaction::new` omits the OP_RETURN data output from weight/vsize estimation, underpaying fees and under-enforcing the standard-weight limit — ([File: networks/bitcoin/src/wallet/send.rs](send.rs))

### Summary
The bug class is a hard-coded/under-provisioned resource limit that makes a protocol-critical transfer fail, leaving funds stuck. In Serai's `bitcoin-serai` wallet, `SignableTransaction::new` computes transaction weight, vsize, the required fee, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check using a template transaction that contains only the payment and change outputs — the OP_RETURN data output appended to the real transaction is never included in the size model. Any transaction carrying `data` therefore pays a fee computed on a smaller-than-actual vsize and passes the dust/relay-fee and size-limit checks against an underestimate. A transaction built at exactly the minimum relay fee, or near `MAX_STANDARD_TX_WEIGHT`, will be rejected by Bitcoin nodes (insufficient fee / non-standard weight), making the wallet unable to move the committed inputs — the same "transfer fails because the resource limit was set too low" shape as the reference finding.

### Finding Description
`SignableTransaction::new` first pushes the OP_RETURN output onto `tx_outs` (lines 194–202), but then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), which builds a template `Transaction` containing only `inputs` and `payments` (lines 68–94) plus optionally `change` (lines 95–99). The `data`/`OP_RETURN` output is absent from every call site (lines 204 and 226). Consequently:

- `vbytes` / `vbytes_with_change` underestimate the real virtual size by the full serialized size of the OP_RETURN output (8-byte amount + compact-size script length + 1–2 opcode bytes + pushdata length + up to 80 data bytes ≈ 13–93 bytes).
- `needed_fee = fee_per_vbyte * vbytes` (line 206, 227) underpays by `fee_per_vbyte * missing_vbytes`.
- The minimum-relay-fee guard (line 211) compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so a transaction that is genuinely below the node's minimum feerate for its real size is accepted.
- The change-drop decision (line 228) uses `fee_with_change` also computed without the data output, and the `MAX_STANDARD_TX_WEIGHT` check (line 241) is evaluated against `weight` that excludes the data output's weight, so a transaction that is actually non-standard-heavy can be constructed.

The multisig path then signs the real (larger) `tx` via `taproot_key_spend_signature_hash` in `TransactionSignMachine::sign` (lines 373–390), producing a valid signature for a transaction Bitcoin Core will not relay or confirm at the paid feerate — mirroring the reference bug where a too-low hard limit makes a required transfer revert and funds become stuck.

### Impact Explanation
Funds "received" by the scanner cannot be moved: any withdrawal/forward transaction that includes an `OutInstruction`/`InInstruction` payload via `data` pays less than the intended feerate and, at boundary values, less than the network minimum feerate for its true size, or exceeds `MAX_STANDARD_TX_WEIGHT` undetected. The transaction is built, signed by the threshold multisig, and broadcast, then rejected/stranded by the mempool. Because `SignableTransaction::new` deterministically reproduces the same underestimation, simply rebuilding the transaction does not recover — the inputs remain locked until the code is fixed, analogous to rewards being stuck behind the hard-coded `10_000` gas limit in `Asset::transferETH`.

### Likelihood Explanation
`SignableTransaction::new` is reachable with unprivileged input: `data` is integrator/user-supplied and `fee_per_vbyte` can legitimately be the minimum relay rate (the constructor only enforces `>=` the minimum). Any caller combining a near-80-byte `data` payload with a minimal feerate, or many inputs near the standard-weight cap, hits the discrepancy. Exploitation doesn't need malformed input — just maximum-size data or a large input count — so the condition arises in normal operation, though only at boundary parameterizations.

### Recommendation
Include the OP_RETURN output in the size model. Change `calculate_weight_vbytes` to accept the full output list (or `data: Option<&[u8]>`) and append the same `TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }` constructed in `new`, and call it after `data` is known (lines 204 and 226). Alternatively, return `Result` and add the serialized OP_RETURN size (`8 + varint(script_len) + script_len`) to the computed weight/vbytes. Re-derive `needed_fee`, the min-relay-fee check, the change calculation, and the `MAX_STANDARD_TX_WEIGHT` check from the corrected size.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new(inputs, &payments, None, Some(vec![0; 80]), MIN_FEE_RATE)`:

1. `tx_outs` gains an OP_RETURN output at lines 194–202 (≈93 serialized bytes).
2. `calculate_weight_vbytes` at line 204 builds a template tx without that output; `vbytes` is short by ~23 vbytes.
3. With `fee_per_vbyte` chosen so `needed_fee == DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, line 211 passes, yet the real transaction's fee is below the node's `minrelaytxfee` for its actual vsize → `sendrawtransaction` fails with "min relay fee not met" / the tx never confirms.
4. The signed inputs are committed (`offsets`, `prevouts`) and the multisig produces a valid signature for a non-relayable transaction — funds stuck, same failure shape as `recipient.call{gas: 10_000}` reverting on reward distribution.

The same omission lets `weight` (line 241) exclude the data output, so a transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT` can be constructed and signed when the data output pushes it over the limit.
