Found a direct on-chain analog in `EvmHost.sol` and `HyperApp.sol`: native-token fee payment for dispatch relies on live Uniswap V2 spot execution rather than a manipulation-resistant price source.

### Title
Native-fee dispatch path uses live Uniswap V2 swap execution for fee-token conversion, letting an attacker manipulate the WETH→feeToken price to under/overpay relayer fees or grief message dispatch - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()` (POST and GET) and `EvmHost.fundRequest()` accept native token payment and immediately execute `IUniswapV2Router02.swapETHForExactTokens` against the pool configured in `_hostParams.uniswapV2` to raise the exact `feeToken` amount recorded as the request's relayer fee. `HyperApp.quote()` (used by all apps built on `HyperApp`, e.g. `HyperFungibleToken`) separately calls `getAmountsIn` on the same pool to tell callers how much native token to send. Both the quote and the actual conversion read the pool's instantaneous reserves/spot price with no TWAP, no deviation guard, and no minimum-liquidity check.

### Finding Description
`dispatch(DispatchPost)` and `dispatch(DispatchGet)` swap `msg.value` for exactly `post.fee` / `get.fee` units of `feeToken()` via a single-block AMM swap: [1](#0-0) [2](#0-1) 

`fundRequest()` (used to top up a relayer fee, including recovering the full fee on timeout) performs the identical unguarded swap: [3](#0-2) 

Callers determine how much native token to send by calling `HyperApp.quote()`, which reads `getAmountsIn` from the very same pool immediately beforehand: [4](#0-3) 

Because both the quote and the settlement swap read the same pool's instantaneous price in the same transaction context, an attacker who can move the WETH/feeToken pool price within the same block (a standard AMM sandwich: swap immediately before the victim's `dispatch`/`fundRequest` call, then swap back after) can:
- Force the victim's `msg.value` (computed off a manipulated `quote()`) to be insufficient, causing `swapETHForExactTokens` to revert and the request to fail (denial of dispatch), or
- Cause the swap to consume far more ETH than the fair-value fee would require, effectively transferring value from the dispatching contract/user into the attacker's pool position, since the router pulls exactly `post.fee`/`get.fee` output tokens regardless of the true market price paid in.

Nothing in `dispatch()`, `fundRequest()`, or `HyperApp.quote()` bounds the acceptable price against a reference/TWAP, unlike the `FXFiller`'s solver-side `checkPriceGuard` mechanism which was built specifically to defend against "a manipulated, stale, or thin pool" quote: [5](#0-4) 

That guard exists only in the off-chain solver strategy layer — the on-chain `EvmHost` fee-payment path (a protocol-wide, unprivileged entry point reachable by any dispatching app or user) has no equivalent protection.

### Impact Explanation
This is a public, unprivileged, on-chain entry point (`dispatch`, `fundRequest`) used by every app that wants to pay Hyperbridge dispatch fees in native token. A manipulated spot price directly changes how much ETH is extracted from the caller for a fixed feeToken output, and can also cause outright reverts of legitimate cross-chain dispatches (relayer fee not delivered, request never gets committed with correct fee, or `fundRequest`/timeout-refund flows fail). This affects fund custody (native ETH sent by users/apps) and request delivery reliability, which are both within the bounty's "loss of funds" and "logic attacks" categories.

### Likelihood Explanation
Medium: any Uniswap V2 pool used as `_hostParams.uniswapV2` is a normal, permissionless AMM pool with finite liquidity; sandwiching a same-block price move around a `dispatch{value:...}` or `fundRequest{value:...}` call is a well-understood, unprivileged MEV technique requiring no special access (no relayer/prover/admin compromise, no front-run-only race — the attacker can simply be the block builder or use flashbots-style bundling around a known pending transaction).

### Recommendation
Do not rely on the AMM's instantaneous reserves for fee-critical conversions. Use a TWAP oracle (or an external price feed with a bounded deviation check similar to the `FXFiller.checkPriceGuard` pattern already used elsewhere in the codebase) before executing `swapETHForExactTokens`, and/or add a caller-supplied `maxNativeIn` slippage bound checked against the actual amount spent so users are protected from being overcharged, while a stale/manipulated quote simply reverts instead of overpaying.

### Proof of Concept
1. Attacker observes a pending `EvmHost.dispatch{value: v}(DispatchPost{...})` (or `fundRequest`) transaction in the mempool, where `v` was computed by the caller via `HyperApp.quote()` against the current pool state.
2. Attacker front-runs with a large swap on the same `_hostParams.uniswapV2` pool (WETH ↔ feeToken) to skew the spot price.
3. Victim's transaction executes `swapETHForExactTokens{value: v}(post.fee, [WETH, feeToken], ...)`; because the pool price has moved, this either reverts (`v` insufficient to buy `post.fee` tokens) or consumes the full `v` for far fewer effective USD-value tokens than intended, while the attacker back-runs to restore the pool and captures the difference.
4. Repeated against `fundRequest` (used to top up/refund relayer fees) the same manipulation can distort how much native ETH is required to fund/refund a given feeToken amount, at the expense of the dispatching contract or user.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
