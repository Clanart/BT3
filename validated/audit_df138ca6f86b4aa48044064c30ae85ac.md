### Title
Unauthenticated `ReceivedOutput` bytes are accepted as confirmed deposits — fabricated `outpoint`/`value` pass all verification and drive signing - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The ash_authentication advisory is a "confirmation-by-GET" flaw: a state-changing action (account confirmation) executes merely because a link was *fetched*, with no proof of deliberate, verified intent. The analog in Serai is `ReceivedOutput`: the wallet's representation of "funds confirmed received". A `ReceivedOutput` is produced purely by matching `script_pubkey` in `Scanner::scan_transaction` — no proof that the referenced outpoint exists, is unspent, is mature, or carries the claimed value — and `ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` from raw untrusted bytes with zero integrity or consistency checks. Downstream, `SignableTransaction::multisig` validates only that `offset.group_key()`'s P2TR script equals `prevouts[i].script_pubkey`; the `outpoint` and `value` inside the supplied `TxOut` are never verified. A fabricated `ReceivedOutput` is therefore indistinguishable from a genuinely scanned deposit — the mere *receipt* of attacker-controlled bytes auto-"confirms" a deposit, exactly the GET-link auto-confirmation shape.

### Finding Description
Two facts combine into the flaw:

1. `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) reads `offset` (`read_F`), `output` (`TxOut::consensus_decode` — attacker-controlled `value` and `script_pubkey`), and `outpoint` (`OutPoint::consensus_decode` — attacker-controlled txid/vout) with no authentication, no cross-check that the outpoint refers to a real UTXO, and no binding between the three fields.
2. `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs:273-285`) gates signing on exactly one check: `p2tr_script_buf(offset.group_key())? == self.prevouts[i].script_pubkey` — i.e., the claimed `script_pubkey` corresponds to the claimed `offset`. It never verifies the `value` nor that the `outpoint` exists on-chain.

Likewise `Scanner::scan_transaction` (`mod.rs:199-214`) emits a `ReceivedOutput` for *any* output whose `script_pubkey` is in `self.scripts`, and `scan_block` (`mod.rs:221-227`) additionally scans `block.txdata[0]` — the coinbase — so an immature (100-block-locked, unspendable) coinbase output is reported as received funds. The mitigation comment exists, but the returned `Vec<ReceivedOutput>` carries no marker distinguishing mature from immature outputs, so any consumer treating the result as spendable is trivially misled — mirroring a confirmation that succeeds without interaction.

### Impact Explanation
An unprivileged attacker who can feed bytes to `ReceivedOutput::read` (explicitly in-scope) or send Bitcoin transactions can cause funds to be reported as received that are not spendable, and can drive the threshold group to sign unintended transactions:

- **Phantom deposit / unspendable funds**: deserialize a `ReceivedOutput` with the group's real offset (recoverable from a known registered script) and a `TxOut` with the matching script but an arbitrary `value` and a fabricated `outpoint`. It serializes byte-identically to a real deposit; `multisig` accepts it, and fee/change/dust math in `SignableTransaction::new` is computed over the fabricated `value` — the wallet builds and FROST-signs a spend of a nonexistent input. If the attacker references a *real* group-owned outpoint but inflates `value`, the sighash (`Prevouts::All`, `send.rs:375-390`) commits to the false amount — participants sign a message premised on phantom funds.
- **Immature coinbase credited**: `scan_block` reports coinbase outputs as spendable `ReceivedOutput`s; a transaction built on them is unbroadcastable, yet was emitted as "received" without any confirmation step.

### Likelihood Explanation
Medium-to-low as a network attack, since exploitation requires the integrator to accept `ReceivedOutput`s over an unauthenticated channel (which the crate's own `read`/`serialize` API explicitly supports and which the task scope admits as a public input path), or for a consumer to use `scan_block` unfiltered. No keys are recovered and no valid spend is forged — analogous to the advisory's own Medium severity (integrity impact only, no confidentiality breach): the consequence is the threshold signing machinery committing to an unintended, ultimately-unspendable transaction and a corrupted view of received funds.

### Recommendation
- Give `ReceivedOutput` a checkable integrity story: either require construction only via `Scanner::scan_*` (make fields private-constructed, and drop/scope-gate the public `read`), or add an authenticated serialization (MAC/version tag) so externally supplied bytes cannot impersonate a scanned output.
- In `SignableTransaction::new`/`multisig` or the scanning layer, verify the outpoint resolves on-chain (or carry a maturity/confirmation flag inside `ReceivedOutput`), rather than trusting `TxOut::value`.
- Split `scan_block` into `scan_coinbase` and `scan_block` semantics, or annotate each `ReceivedOutput` with a `matures_at`/`confirmed` field so unspendable outputs can't be auto-credited without an explicit consumer decision — the equivalent of the advisory's `require_interaction? true`.

### Proof of Concept
```rust
// Attacker knows a registered script (public on-chain data) and its offset's
// group key: key + G*offset is the P2TR internal key embedded in the script.
let offset: Scalar = /* the real offset for a known registered script */;
let real_script = p2tr_script_buf(group_key + ProjectivePoint::GENERATOR * offset).unwrap();

// Fabricate a deposit: real script, fake outpoint, inflated value
let forged = {
    let mut buf = vec![];
    buf.extend(offset.to_bytes());                                     // offset
    buf.extend(serialize(&TxOut {                                      // output
        value: Amount::from_sat(1_000_000_000),                        // claimed value
        script_pubkey: real_script,
    }));
    buf.extend(serialize(&OutPoint::new(Txid::all_zeros(), 0)));       // fake outpoint
    ReceivedOutput::read(&mut buf.as_slice()).unwrap()                 // succeeds: no checks
};

// The threshold multisig accepts it: only the script_pubkey/offset match is checked
// (send.rs:277), so SignableTransaction::new(vec![forged], payments, change, None, fee)
// builds a TX whose Prevouts::All sighash commits to the fabricated value, and every
// honest participant produces a valid signature share for a spend of a nonexistent
// input — an unintended message signed, and phantom funds recorded as received.

// Separately: a coinbase paying to the group's script is reported spendable:
let outputs = scanner.scan_block(&block); // includes block.txdata[0] — immature for 100 blocks
```
