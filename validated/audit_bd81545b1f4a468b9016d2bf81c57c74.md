## Title
Mutable `_params.host` in `IntentGatewayV2` permanently strands escrowed orders when governance updates the host address mid-flight - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` (and its `IntentsBase`/`ExtrinsicIntents` mixins) stores a single mutable `host` address inside `_params`, read dynamically via `host()` at the time any cross-chain message is authenticated. Governance can change this address wholesale via `_updateParams()` while orders are already escrowed and in-flight (placed, awaiting `RedeemEscrow`/`RefundEscrow` settlement). Because the gateway never pins the host address that was authoritative at order-placement time, a mid-flight host change breaks authentication for already-dispatched settlement/cancellation messages, exactly mirroring the `setStakingContract()` bug pattern in the external report: a global, mutable dependency address is swapped while stateful, per-item commitments (games / orders) still rely on the old address for completion.

### Finding Description
`_params.host` is the single source of truth for the ISMP host contract used by the gateway: [2](#0-1) 

`host()` is used both to authenticate inbound messages (via `HyperApp`'s `onlyHost` modifier, inherited by `ExtrinsicIntents`/`IntentGatewayV2`) and to compute the source chain identity written into every `Order` at placement time: [3](#0-2) 

Governance updates `_params` (including `host`) atomically and unconditionally via `_updateParams()`, with no check for outstanding escrowed orders: [4](#0-3) 

The validation function `_validateParams` only checks that the new host has code and is non-zero — it never checks whether pending orders exist that still depend on the *previous* host for settlement: [5](#0-4) 

When an order is placed, escrowed tokens are locked under `_orders[commitment][token]` and the order is only released via `_withdraw()`, which is invoked from `onAccept()` after the local host delivers the `RedeemEscrow`/`RefundEscrow` message: [6](#0-5) 

If `_params.host` is changed by governance while an order is escrowed and its settlement/cancellation message is already committed on the source or destination chain (proof already generated against the old host's state), the delivery path for that in-flight message is now authenticated against a *different* host address than the one it was generated for. `onAccept` is gated by `onlyHost`, which checks `msg.sender == host()` — after the update, `host()` returns the new address, so a message routed to/via the old host contract can no longer successfully call `onAccept` on this gateway. The escrowed tokens in `_orders[commitment][...]` become permanently unreachable: `_withdraw()` is only invoked from the authenticated `onAccept` path, and there is no alternate code path that lets a user or solver reclaim the escrow once the recorded host no longer matches the host used at dispatch time.

This is structurally identical to the `Flip.setStakingContract()` issue: a single mutable global address (`staking contract` / `_params.host`) is referenced by pending, uncompleted state (`PendingGame` / escrowed `Order`), and changing that global address orphans the pending items — funds can no longer be refunded or released through the intended completion path.

### Impact Explanation
Escrowed order funds (arbitrary user-supplied ERC-20/native tokens) can become permanently locked in the `IntentGatewayV2` contract if governance updates `_params.host` while any order is between `placeOrder`/`fillOrder` and final settlement. This is a direct loss/lock of user funds with no recovery path other than another privileged (Hyperbridge governance) intervention, which itself may not be able to reconstruct the exact prior host binding for orders whose cross-chain proofs were already generated. Given the protocol's intended design (escrow → cross-chain settle → release), this breaks the fund-safety invariant that escrowed assets move exactly once to the rightful beneficiary.

### Likelihood Explanation
Requires a legitimate governance action (`UpdateParams` via Hyperbridge) to change `host` while orders are pending — this is not attacker-triggered from an unprivileged position, but it is a realistic operational scenario (host contract upgrades/migrations are an expected lifecycle event for Hyperbridge deployments) and the contract provides no safeguard, pending-order check, or grace/migration mechanism to prevent it, unlike `EvmHost.updateHostParamsInternal` which at least blocks `feeToken` changes while a balance is outstanding.

### Recommendation
Before allowing `_params.host` to change in `_updateParams`, require that there are no outstanding escrowed orders (or provide an explicit migration mechanism), or alternatively record the authoritative host address per-order (in the `Order`/commitment or in a side mapping) at `placeOrder` time and use that recorded address — rather than the live `_params.host` — when authenticating `onAccept` calls tied to that specific commitment, mirroring the report's recommendation to snapshot the dependency address at creation time rather than reading it live from mutable global state.

### Proof of Concept
1. User calls `placeOrder()` on `IntentGatewayV2`, escrowing input tokens; `order.source` is stamped using the current `host()` (old host address), and the order's commitment is recorded.
2. Solver fills the order on the destination chain (`fillOrder`), triggering a `RedeemEscrow` post dispatched back toward the source chain via the old host.
3. Before the settlement message is relayed/finalized on the source chain, Hyperbridge governance calls `update_host_params`/`UpdateParams` on the source-chain gateway, changing `_params.host` to a new host contract address (e.g., a host migration).
4. When the relayer submits the proof and the (old) host attempts to deliver the `RedeemEscrow` message by calling `onAccept()` on the gateway, `onlyHost` now compares `msg.sender` against the *new* `host()` value and reverts with `Unauthorized`.
5. The escrowed tokens for that commitment remain locked in `_orders[commitment][token]` indefinitely — `_withdraw()` is unreachable because the only entrypoint into it (`onAccept`, or the cross-chain cancel/refund GET-response path, both gated by the same host binding) can never be authenticated for this order again.

    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
