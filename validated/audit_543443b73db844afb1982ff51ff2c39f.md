## Title
Path traversal in `revealInFileManager` allows a malicious repository's file path to reveal/select files outside the repository - ([File: app/src/lib/app-shell.ts])

## Summary
The reported vulnerability's broken invariant is: a caller-controlled identifier that should be constrained to "the current user/repository scope" is instead used verbatim to target a resource outside that scope, with no server/app-side containment check. In GitHub Desktop, the closest analog is the `revealInFileManager` helper, which builds a filesystem path by joining the trusted repository root with an attacker-influenced relative path (`file.path`, sourced from diff/commit/status data of a cloned or fetched repository) without verifying the joined result stays inside the repository. This is the same class of bug as `depositEUR`'s unchecked `from`: an untrusted, externally-derived value is trusted to scope a privileged operation.

## Finding Description
`revealInFileManager` computes the target path via a plain `Path.join` with no boundary check: [1](#0-0) 

```
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
```

`path` here is `file.path`, a value that originates from the file entries of a commit/diff/status of a repository the user cloned or fetched — data that is attacker-controlled if the user is browsing a hostile repository. This function is wired up from multiple UI surfaces that build the menu item directly from `file.path` without any containment validation: [2](#0-1) [3](#0-2) [4](#0-3) 

Critically, GitHub Desktop's own codebase demonstrates the developers are aware of exactly this hazard and already implement the correct fix elsewhere: when resolving a `filepath` query parameter from an "Open in Desktop" deep link (also untrusted, attacker-influenced input), the dispatcher explicitly rejects absolute paths and uses `resolveWithin` to canonicalize and verify containment before calling the same `shell.showItemInFolder`: [5](#0-4) 

```
if (filepath !== null) {
  if (isAbsolute(filepath)) {
    log.error(`Refusing to open absolute path: ${filepath}`)
    return
  }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } else {
    log.error(
      `Prevented attempt to open path outside of the repository root: ${filepath}`
    )
  }
}
```

`resolveWithin` is the intended guard, normalizing/resolving the path and verifying (via `realpath`) that the result is still nested under the repository root: [6](#0-5) 

`revealInFileManager` (and its several call sites) do not use `resolveWithin` or reject absolute/traversal paths, so if `file.path` can ever resolve to something like `../../../../.ssh/id_rsa` or an absolute path via a crafted tree entry name from a malicious/fetched repository, the app will happily call `shell.showItemInFolder` on a path outside the repository.

## Impact Explanation
`shell.showItemInFolder` opens/reveals the resolved path in the OS file explorer. If the resolved path escapes the repository sandbox, this can expose the existence and location of sensitive files outside the repo (e.g., dotfiles, credential files, other users' data) to a user who merely opened a right-click context menu item in a repository they cloned — the same "operate outside the intended scope because of unchecked untrusted input" issue as the audited `depositEUR` bug, adapted to file-system scope instead of token scope. It falls short of remote code execution, but does constitute an "outside-repo" filesystem interaction driven purely by repository content.

## Likelihood Explanation
Likelihood is lower than the original finance bug because it depends on whether Git tree/diff parsing in this codebase can surface a `file.path` value containing `..` segments or an absolute path (upstream Git generally blocks `..` path components on checkout, but Desktop's diff/status parsing operates on raw `git diff`/`git status` porcelain output, which is not guaranteed to enforce the same protections as `git checkout`). This is unverified against the current parser implementation within the tool budget available, so likelihood should be treated as uncertain/moderate rather than confirmed exploitable — it is asserted as a code-invariant gap (missing containment check) rather than a demonstrated end-to-end exploit.

## Recommendation
Apply the same containment check used in `dispatcher.ts`'s `openRepositoryFromUrl` to `revealInFileManager` (and any other helper in `app-shell.ts` that joins `repository.path` with a repo-relative path derived from git data): reject absolute paths, and use `resolveWithin(repository.path, path)` before calling `shell.showItemInFolder`, refusing to proceed if the resolved path is `null`.

## Proof of Concept
Not independently verified end-to-end (would require confirming that Desktop's diff/status parser can yield a `CommittedFileChange.path` containing directory-traversal segments or an absolute path from a crafted repository/tree). Conceptually:
1. Attacker crafts/publishes a Git repository whose tree or diff output causes Desktop to compute a `file.path` such as `../../../../../etc/passwd` (or platform equivalent) for a "changed file".
2. Victim clones/fetches this repository and opens the Changes/History view, then right-clicks the file and selects "Reveal in Finder/Explorer".
3. `revealInFileManager(repository, file.path)` performs `Path.join(repository.path, '../../../../../etc/passwd')`, escaping the repo root, and `shell.showItemInFolder` reveals the out-of-repo file — with no `resolveWithin`/`isAbsolute` guard as exists in the deep-link code path. [1](#0-0)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
