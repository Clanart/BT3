### Title
Missing `chain_id` and `verifying_contract` in EIP-712 Domain Separator Enables Cross-Deployment Replay of Aggregator Withdrawal Authorization Signatures — (`File: core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is constructed with only `name` and `version`, omitting `chain_id` and `verifying_contract`. A valid aggregator ECDSA verification signature produced for one Citrea deployment (e.g., testnet) is cryptographically identical to a valid signature for any other deployment that shares the same aggregator key, because the domain hash does not bind the signature to a specific chain or contract. This signature is the sole authorization gate for operator withdrawals and optimistic payouts when `aggregator_verification_address` is configured.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as a compile-time static:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 specification defines the domain separator as a hash of `(name, version, chainId, verifyingContract, salt)`. The `chainId` and `verifyingContract` fields exist precisely to prevent cross-chain and cross-contract replay. Both are available in `BridgeConfig` (`citrea_chain_id: u32` and `bridge_contract_address: String`) but are never incorporated into the domain. [2](#0-1) 

This domain is used in `recover_address_from_ecdsa_signature` to reconstruct the signed hash and recover the signer's address:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [3](#0-2) 

This recovered address is then compared against `aggregator_verification_address` in two places:

1. **Verifier — optimistic payout path** (`Verifier::sign_optimistic_payout`): [4](#0-3) 

2. **Operator — normal withdrawal path** (`ClementineOperator::withdraw`): [5](#0-4) 

Because the domain separator does not include `chain_id`, the EIP-712 hash of `OptimisticPayoutMessage` or `OperatorWithdrawalMessage` with identical field values is identical across all Citrea deployments. A signature that passes verification on testnet (chain ID 5655) will also pass on any other deployment using the same aggregator key.

---

### Impact Explanation

When `aggregator_verification_address` is configured (the production-intended mode per the module doc comment and `.env.example`), the ECDSA verification signature is the only authorization gate preventing an arbitrary caller from triggering an operator withdrawal or optimistic payout. A replayed signature from a different Citrea deployment bypasses this gate entirely.

A successful replay causes the operator to execute `withdraw()` — spending operator-controlled BTC UTXOs to pay out a withdrawal — for a request that was never authorized for the target deployment. The operator loses the payout amount (up to `bridge_amount`, configured at 1 BTC in the example paramset) from their own funds, with no recourse. [6](#0-5) 

---

### Likelihood Explanation

The attack requires:
1. The same aggregator ECDSA key (`aggregator_verification_address`) is configured on two or more Citrea deployments (e.g., testnet and mainnet, or two parallel bridge instances).
2. The attacker obtains a valid aggregator signature for a withdrawal on one deployment (e.g., by being a legitimate user on testnet, or by observing a signed withdrawal request in transit).
3. A deposit with a matching `withdrawal_id` and `input_outpoint` exists on the target deployment.

Condition 1 is realistic during staged rollouts and multi-environment operations. Condition 2 is achievable by any user who has ever received a legitimate optimistic payout on a non-production deployment. Condition 3 is the binding constraint but is satisfiable when deposit IDs are sequential and the same user has deposits on both deployments.

---

### Recommendation

Construct the domain separator at runtime using the per-deployment `citrea_chain_id` and `bridge_contract_address` from `BridgeConfig`, rather than a compile-time static:

```rust
pub fn clementine_eip712_domain(chain_id: u64, verifying_contract: Address) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
        verifying_contract: verifying_contract,
    }
}
```

Pass this domain into `recover_address_from_ecdsa_signature` and update all signing paths (including `sign_withdrawal_verification_signature` in tests) to use the same runtime domain. This matches the pattern already used in `BatchProofMethodIdBody`, which explicitly includes `chain_id` to prevent cross-network replay: [7](#0-6) 

---

### Proof of Concept

1. Deploy two Clementine bridge instances: **Instance A** (testnet, `citrea_chain_id=5655`) and **Instance B** (mainnet, `citrea_chain_id=5115`), both configured with the same `aggregator_verification_address`.

2. On Instance A, the aggregator signs an `OptimisticPayoutMessage` for `withdrawal_id=42`, `input_outpoint=<txid:vout>`, `output_script_pubkey=<attacker_script>`, `output_amount=99900000`. The resulting ECDSA signature `S` is observed (e.g., from a gRPC call or log).

3. On Instance B, deposit ID 42 exists with a matching `input_outpoint` (possible when both instances process the same user's deposits).

4. The attacker calls `optimistic_payout` on Instance B's aggregator RPC, supplying the same withdrawal params and signature `S`.

5. `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` computes `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` — the domain is identical on both instances because it contains no chain-specific data. The recovered address matches `aggregator_verification_address`. The check passes.

6. The verifiers sign the optimistic payout transaction on Instance B. The operator pays out BTC to the attacker's address on mainnet without a legitimate mainnet authorization. [1](#0-0) [8](#0-7)
