### Title
Pattern-warning dedup key ignores content, permanently suppressing re-introduced dangerous edits within a session - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`atomic_check_and_mark_warning` dedups PostToolUse pattern warnings using a key of only `f"{file_path}-{rule_name}"` [1](#0-0) . Because this key carries no content/line/hash component and `shown_warnings` is never reset mid-session, once a dangerous pattern fires for a given file+rule, any later edit that reintroduces the same category of dangerous code in that same file (after a real or apparent fix, an amend, or a retry) is silently skipped for the rest of the session.

### Finding Description
`main()` computes `warning_key = f"{file_path}-{rule_name}"` for every pattern match on `Edit`/`Write`/`MultiEdit`/`NotebookEdit` PostToolUse events and calls `atomic_check_and_mark_warning(session_id, warning_key)` [2](#0-1) . That helper atomically checks/marks `state["shown_warnings"]`, a flat list keyed on this string, returning `False` (suppress) if the key was ever seen before in this session [3](#0-2) .

The only mechanism that inspects whether a pattern was actually fixed is `sweep_pending_warnings`, which runs once at Stop and re-checks `pending_warnings` for a fixed/unresolved telemetry tally [4](#0-3) . Critically, that sweep clears `pending_warnings` but does **not** clear or reconcile `shown_warnings`. So the suppression state persists for the life of the session regardless of whether the flagged code was subsequently removed.

Exploit flow:
1. Attacker (or unwitting developer under Claude's control) makes an edit to `file.py` that trips rule `hardcoded-secret` → `warning_key = "file.py-hardcoded-secret"` is new → warning shown and key recorded.
2. Claude/the user "fixes" it (removes the secret) — sweep at Stop tallies it as fixed and clears `pending_warnings`, but `"file.py-hardcoded-secret"` remains in `shown_warnings`.
3. Later in the same session — a retry, an amend, or simply a new edit — the exact same class of dangerous code (a different hardcoded secret, a different `eval()` call, etc., matching the same `rule_name` in the same `file_path`) is reintroduced.
4. `atomic_check_and_mark_warning` sees the key already present and returns `False`, so `all_guidance` stays empty and no PostToolUse warning/additionalContext is emitted for the reintroduced dangerous code [1](#0-0) .

Because `session_id` persists across turns and edits in a normal Claude Code session (retries, amends, follow-up edits to the same file all reuse the same session state file via `with_locked_state`), this is squarely within an unprivileged attacker's control: crafting diff content that repeats a previously-warned (file, rule) combination is a normal edit operation, not a privilege escalation. No approval prompt, allowlist, or workspace guard exists to catch this — the pattern-warning path is a fire-once-per-session-per-key mechanism with no re-arm logic tied to fix verification.

Note: the LLM-based diff review path (`_dedup_against_state` for commit-review/push-sweep) is content-aware via `(filePath, category)` plus prompt hints and explicitly instructs the LLM to re-flag if "the code at that location was CHANGED since the prior review and the change is an incomplete fix or introduces a new issue" [5](#0-4) . That mitigates the same class of bypass for the commit/push-sweep flows, but the pattern-based PostToolUse path (`atomic_check_and_mark_warning`) has no equivalent re-arm logic, so the bypass is specific to per-edit pattern warnings, not the stop-hook/commit-review LLM analyses.

### Impact Explanation
This breaks the stated invariant that "dangerous edits and commands must stay reviewable and blockable even across retries, amends, and pushes" for the pattern-based warning layer specifically. A dangerous pattern (e.g., hardcoded secret, insecure eval, disabled TLS verification) that is reintroduced into the same file after an earlier occurrence of the same rule was shown/dismissed will silently produce no PostToolUse warning for the remainder of the session — a session-scoped, silent security-control bypass. This matches "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries," though the severity is bounded: it degrades only the pattern-warning notification layer (informational/nudge, not a hard block), and the Stop-hook/commit-review LLM-based diff analysis (which is content/category-aware and has an explicit re-flag-on-incomplete-fix instruction) still runs independently and may still catch the reintroduced issue.

### Likelihood Explanation
High feasibility, no special privilege required: any normal editing sequence within one Claude Code session (edit → fix → re-edit, or retry/amend of the same file) that happens to trip the same `rule_name` twice reproduces the suppression deterministically. It requires only a repeated pattern match on the same file path, which is common in iterative development/retry flows and trivially reproducible by an attacker crafting repo content or diffs.

### Recommendation
Include a content-sensitivity component in the pattern-warning dedup key (e.g., a hash of the matched snippet or line, or track "last known match state" per file+rule) so that the warning can re-arm once the sweep observes the issue was fixed, rather than permanently suppressing after the first occurrence of a given (file_path, rule_name) pair. Alternatively, have `sweep_pending_warnings`'s fixed-detection also clear the corresponding entries out of `shown_warnings` so a rule can fire again if reintroduced after being confirmed fixed.

### Proof of Concept
Unit test plan (in the style of existing hook tests):
1. Simulate a PostToolUse `Edit` on `foo.py` that matches a known pattern rule (e.g., a hardcoded secret regex) — assert `atomic_check_and_mark_warning` returns `True` and `all_guidance` is non-empty for the first call.
2. Simulate a second PostToolUse `Edit` on `foo.py` that removes the pattern (clean content) — call `sweep_pending_warnings(session_id)` directly (simulating Stop) and assert it reports `fixed=1, unresolved=0` and clears `pending_warnings`.
3. Simulate a third PostToolUse `Edit` on `foo.py` that reintroduces a *different* secret value matching the *same rule* — call `atomic_check_and_mark_warning(session_id, "foo.py-<rule_name>")` again.
   - Expected (buggy) behavior: returns `False`, no warning emitted in `main()`'s `all_guidance`/`additionalContext`.
   - Expected (fixed) behavior: returns `True` and the warning is re-emitted since the earlier occurrence was confirmed fixed.
4. Assert on the JSON printed by `main()` for step 3 to confirm no `hookSpecificOutput.additionalContext` is produced under current code, demonstrating the silent suppression of a genuinely new dangerous edit.

def atomic_check_and_mark_warning(session_id, warning_key):
    """
    Atomically check if a warning has been shown and mark it as shown if not.
    Returns True if this is the first time seeing this warning (should show it),
    False if it was already shown (should skip it).
    """
    def _check(state):
        warnings = state["shown_warnings"]
        if warning_key in warnings:
            return False
        warnings.append(warning_key)
        return True

    result = with_locked_state(session_id, _check)
    return result if result is not None else True
```

def sweep_pending_warnings(session_id):
    """
    Stop-hook final sweep. Re-read every file in pending_warnings, re-check
    patterns, and return (fixed, unresolved, unresolved_mask). Clears state.
    A file that's been deleted counts as fixed — the dangerous code is gone.
    Never raises — this is telemetry and must not break the Stop hook.
    """
    def _sweep(state):
        try:
            pending = state.get("pending_warnings")
            if not isinstance(pending, dict) or not pending:
                return 0, 0, 0

            by_file = {}
            for key in pending:
                if not isinstance(key, str) or ":" not in key:
                    continue
                fp, _, rule = key.rpartition(":")
                by_file.setdefault(fp, set()).add(rule)

            unresolved = []
            fixed = 0
            for fp, rules in by_file.items():
                try:
                    with open(fp, "r", errors="replace") as f:
                        still_matching = {r for r, _ in check_patterns(fp, f.read())}
                except (OSError, IOError):
                    still_matching = set()
                for rule in rules:
                    if rule in still_matching:
                        unresolved.append(rule)
                    else:
                        fixed += 1

            state["pending_warnings"] = {}
            # Filter to known rules so a renamed/removed rule in old state
            # doesn't KeyError rule_names_to_mask.
            known = [r for r in unresolved if r in _RULE_NAME_TO_ID]
            return fixed, len(unresolved), rule_names_to_mask(known)
        except Exception as e:
            debug_log(f"sweep_pending_warnings failed: {e}")
            return 0, 0, 0

    result = with_locked_state(session_id, _sweep)
    return result if result is not None else (0, 0, 0)
```
