### Title
Prompt-injectable, order-only hunk validation lets a malicious merge source silently corrupt Copilot-resolved conflict files - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
Like the Sherlock finding, where `minTokenAmounts_` only checks an aggregate invariant (enough total wstETH out of the pool) but never validates the *specific value the user actually receives* after the treasury skim, GitHub Desktop's Copilot conflict-resolution pipeline only validates a coarse, aggregate invariant — the returned hunk **count** per file — and never validates that each `resolvedContent` entry actually corresponds to the conflict it claims to resolve. The final value spliced into the user's file is trusted purely by array position.

### Finding Description
`validateResolutionPaths` in `app/src/lib/copilot-conflict-resolution.ts` only checks that the model returned the right file paths and the right *number* of hunks per file: [1](#0-0) 

The actual splice step, `reassembleResolvedFile`, explicitly matches resolutions to on-disk conflict blocks "by order, not by line number": [2](#0-1) [3](#0-2) 

There is no check that binds `hunkResolutions[hunkIndex]` to conflict block `hunkIndex` other than sequential order — if the count matches, `validateResolutionPaths` passes regardless of whether the content is correctly attributed. The prompt itself embeds attacker-influenced material verbatim: PR titles/bodies and commit messages from both sides of the merge are inlined into the same message that carries the "Conflict N of M" ordering instructions: [4](#0-3) [5](#0-4) 

`sanitizeForMarkdown` only strips `\r`, `\n`, and backticks from file-path labels — PR bodies and commit summaries (attacker-controlled: any contributor who opens a PR or writes a commit message that later gets merged controls this text) flow into the prompt unescaped: [6](#0-5) 

Finally, the write path (`_applyCopilotConflictResolutions`) takes the stored `resolution.resolvedContent` at face value and writes/stages it once the user clicks "Continue": [7](#0-6) 

The only defenses in that path are a path-traversal guard (`resolveWithin`) and a check that the file still has unresolved markers on disk — neither protects against a resolution being correctly *counted* but incorrectly *ordered/attributed*: [8](#0-7) 

### Impact Explanation
An attacker who controls one side of a merge (a malicious branch/fork, or just a PR/commit whose title, body, or message is later merged) can craft conflicting content plus adversarial prompt text designed to make the model return the *right number* of hunks but with resolutions swapped, mismatched, or otherwise misattributed relative to the actual on-disk conflict order. Because validation is count-only and splicing is order-only, this passes every automated check and the user is shown/commits a file whose merged content silently differs from what each side's "Conflict N of M" block actually was intended to resolve — i.e., silent corruption of what the user commits and pushes, potentially reintroducing vulnerable/backdoored code that was supposed to be replaced, or dropping security-relevant changes from one side while representing the diff as reviewed.

### Likelihood Explanation
Requires an attacker to only contribute a mergeable branch/PR/commit — no local access, no leaked credentials, no malware. Large-language-model outputs are known to be susceptible to ordering/content confusion, especially when adversarial natural-language content (PR body/commit message) is deliberately crafted and interleaved with the structured instructions in the same prompt. The count-only validation provides no structural protection against this class of misordering, so the likelihood is non-trivial for a user who merges from an untrusted or compromised branch and relies on the "Continue" action after a cursory review of a multi-hunk file.

### Recommendation
Bind each returned hunk resolution to an explicit, stable identifier (e.g., an index or content hash of the original ours/theirs/base block) rather than array position, and validate that identifier at `validateResolutionPaths` time instead of only counting hunks. Consider hashing each `oursContent`/`theirsContent` pair and requiring the model to echo back a matching identifier, rejecting the response if any hunk's identifier doesn't match the corresponding on-disk block. Additionally, delimit/escape untrusted PR body and commit message text distinctly from the structural JSON-contract instructions to reduce prompt-injection surface.

### Proof of Concept
1. Attacker opens a PR/branch that will conflict with the victim's branch in a file with two independent conflicts (hunk A: benign change, hunk B: security-relevant change).
2. Attacker's PR description/commit message contains adversarial text (embedded within the material passed unescaped through `formatConflictContextForPrompt`) attempting to bias the model into swapping or misattributing resolution content between hunk A and hunk B while still returning exactly 2 hunks.
3. Victim merges, triggers Copilot conflict resolution; `validateResolutionPaths` sees `resolutions.length === 2 === expectedHunkCounts`, passes.
4. `reassembleResolvedFile` splices `hunkResolutions[0]` into the first on-disk marker block and `hunkResolutions[1]` into the second purely by order.
5. Victim reviews the "Changes" tab, sees a diff that looks plausible, clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the misattributed content to disk and stages it — corrupted merge result is committed/pushed without any validation catching the mismatch.

Note: I was not able to execute the actual Copilot SDK to confirm empirically that a model can be steered to misorder resolutions while preserving the correct count — that portion relies on the documented, inherent unreliability of LLM output ordering under adversarial prompt content, not on a directly observed code defect. The code-level gap (count-only validation, order-only splicing, unsanitized PR/commit text in the same prompt) is directly verified in the cited files.

export function formatConflictContextForPrompt(
  context: IConflictResolutionContext
): string {
  const parts: Array<string> = []

  parts.push(
    `Merge conflict between "${context.ourLabel}" (ours) and "${context.theirLabel}" (theirs).`
  )
  parts.push('')

  if (context.pullRequests.length > 0) {
    parts.push('## Pull Request Context')
    parts.push(
      'These pull requests were referenced in the commit history and may explain the intent behind either side:'
    )
    parts.push('')
    for (const pr of context.pullRequests) {
      appendPullRequest(parts, pr)
    }
  }

  if (context.ourCommits.length > 0 || context.theirCommits.length > 0) {
    parts.push('## Recent Commits')
    parts.push('')

    if (context.ourCommits.length > 0) {
      parts.push(`### Ours (${context.ourLabel}) commits:`)
      for (const commit of context.ourCommits) {
        parts.push(`- ${commit.shortSha}: ${commit.summary}`)
      }
      parts.push('')
    }

    if (context.theirCommits.length > 0) {
      parts.push(`### Theirs (${context.theirLabel}) commits:`)
      for (const commit of context.theirCommits) {
        parts.push(`- ${commit.shortSha}: ${commit.summary}`)
      }
      parts.push('')
    }
  }

/** Append a single pull request's title and (truncated) body to the prompt. */
function appendPullRequest(
  parts: Array<string>,
  pr: IConflictContextPullRequest
): void {
  parts.push(`PR #${pr.number}: ${pr.title}`)
  if (pr.body) {
    parts.push('Description:')
    parts.push(makeFencedBlock(truncateBody(pr.body)))
  }
  parts.push('')
}

/** Truncate an over-long PR body so a single PR can't dominate the prompt. */
function truncateBody(body: string): string {
  if (body.length <= MAX_PR_BODY_LENGTH) {
    return body
  }
  return `${body.slice(0, MAX_PR_BODY_LENGTH)}\n…(truncated)`
}
