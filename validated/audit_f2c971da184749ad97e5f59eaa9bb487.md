### Title
Positional-alignment assumption between `--raw` and `--numstat` sections lets a crafted commit misattribute file paths and change stats - (File: `app/src/lib/git/log.ts`)

### Summary
The reported Huff bug reduces to a broken invariant: *the code assumes an implicit ordinal correspondence between two independently-encoded, attacker-influenceable data sections, instead of validating that correspondence, and uses one section's already-decoded field (an offset/kind marker) to decide how to consume the other section.* When the two sections' lengths or item order diverge, values from one logical record leak into another.

The same broken-invariant pattern exists in GitHub Desktop's `parseRawLogWithNumstat`, which parses `git log --raw --numstat -z` output. It walks the `--raw` block to build `files[]` (path + status), and separately walks the interleaved `--numstat` block to attach add/delete counts, using `isCopyOrRename(files[numStatCount].status)` — a value taken from the *raw* block — to decide whether the *numstat* block's next 1 or 3 tokens belong to the current record: [1](#0-0) 

### Finding Description
`getChangedFiles` runs `git log ... --raw --numstat -z --` against a commit supplied by an attacker-controlled remote/fork/clone [2](#0-1) . `parseRawLogWithNumstat` then walks the combined, NUL-delimited stdout in a single pass with a shared index `i`. For `:`-prefixed raw entries it decodes the file status and path and pushes a `CommittedFileChange` into `files[]` [3](#0-2) . For numstat lines it increments a **separate** counter `numStatCount` and decides how many extra NUL-separated tokens to skip purely by re-reading `files[numStatCount].status` from the already-parsed raw section: [1](#0-0)

This mirrors exactly the TSender flaw: instead of decoding each dynamic-length numstat record independently and self-describing its own boundaries, the code hard-assumes that record `N` of the `--numstat` stream is positionally identical to record `N` of the `--raw` stream, and reuses a value decoded from the *other* stream to determine how many tokens to skip. Git does not guarantee this 1:1 positional identity in all cases: the two report modes can diverge in entry count for the same commit — e.g. pure file-mode changes, `--raw`-only submodule/typechange entries, and combined-diff output for merge commits (`-m` is used here) can appear in one section and not the other, or in different relative order once rename/copy detection (`-M`/`-C`) is layered on. Any such divergence desynchronizes `numStatCount` from `files`'s index for every subsequent record in the commit: line-count totals and the copy/rename token-skip decision get applied to the wrong `CommittedFileChange`, and stray numstat tokens can be consumed as if they were the next raw entry's data (or vice versa), corrupting `linesAdded`/`linesDeleted` and the `path`/`oldPath` correspondence used throughout the history/diff/PR UI (`app-store.ts`, `selected-commits.tsx`, `open-pull-request-dialog.tsx`).

No guard re-validates that the raw-derived path/status for index `numStatCount` actually matches the numstat line currently being consumed (unlike, say, `status-parser.ts`, which fully decodes each record's own fields via anchored regexes rather than borrowing a "shape" decision from a separate, independently-indexed array).

### Impact Explanation
Because the input commit is entirely attacker-controlled (any commit in a cloned/fetched repository, fork, or PR branch a victim opens in Desktop), a crafted commit can desynchronize the parser so that:
- line-added/line-deleted stats and rename/copy classification are attributed to the wrong file, and
- the wrong `oldPath`/`path` pair is associated with a `CommittedFileChange`.

This is the "silent corruption of what the user sees/acts on" category: the History view, commit-summary, and Open-PR dialogs consume this data (`app-store.ts`, `selected-commits.tsx`, `expandable-commit-summary.tsx`, `open-pull-request-dialog.tsx`) to decide which file's diff to render and which path to treat as renamed-from/renamed-to. A user could be shown an incorrect diff/stat attribution for a file, or the tool could misreport what a commit actually changed. This is a data-integrity/UI-trust issue rather than direct code execution or credential exfiltration, so severity is bounded — it does not by itself let an attacker write outside the repo, but it can cause the app to lie about a commit's contents.

### Likelihood Explanation
Requires a specific, crafted commit shape (mix of rename/copy detection with entries that are asymmetric between `--raw` and `--numstat`, e.g. mode-only changes, submodule entries, or merge-diff edge cases with `-m`) inside a repository the victim clones/fetches or a PR they open — an unprivileged, no-extra-user-action-beyond-normal-usage path. However, triggering an actual count mismatch depends on specific git edge cases that were not verified against a live git binary in this review (index is source-only, no execution available), so likelihood of a concretely exploitable divergence is uncertain without further empirical testing.

### Recommendation
Do not use a counter/index derived from one independently-parsed section to decide how many tokens to consume from a different independently-parsed section. Instead:
- Parse the `--raw` and `--numstat` streams into self-describing records independently (each numstat record already signals rename/copy shape via its own token count/NUL structure), or
- Emit a single format that ties stats and status together per file (e.g. use `--raw` combined with `--name-status` keyed by path, or a custom `--format` with per-file line stats) so no positional-correspondence assumption is required, or
- At minimum, assert that `files.length === totalNumstatRecordsParsed` after parsing and fail loudly (as the code already does elsewhere with `forceUnwrap`) instead of silently indexing into a possibly-misaligned array.

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}
