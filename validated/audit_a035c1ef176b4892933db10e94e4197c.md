### Title
Path traversal in "Reveal in File Manager" / "Open in External Editor" / "Open with Default Program" via unsanitized repository-supplied file paths - (File: `app/src/lib/app-shell.ts`, `app/src/ui/changes/sidebar.tsx`, `app/src/ui/app.tsx`)

### Summary
GitHub Desktop has a validated reference implementation for turning a repository-relative path into a filesystem path safely: `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts:1940-1972` rejects absolute paths and calls `resolveWithin(repository.path, filepath)` (`app/src/lib/path.ts`) before calling `shell.showItemInFolder`. That guard exists precisely to stop a path from escaping the repository root (verified by the symlink-escape tests in `app/test/unit/path-test.ts:65-101`). However, the much more commonly used code paths that turn a *file-change path coming from git status/diff/log output* into a full filesystem path never apply this same check.

### Finding Description
`revealInFileManager` in `app/src/lib/app-shell.ts:61-64` does:
```ts
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
``` [1](#0-0) 

This function is called throughout the UI with `file.path` taken directly from `WorkingDirectoryFileChange`/`CommittedFileChange` objects that originate from parsing `git status --porcelain=2`, `git diff`, and `git log --name-status` output (e.g. `app/src/ui/changes/filter-changes-list.tsx:628-636`, `app/src/ui/history/selected-commits.tsx:407-410`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx:187-190`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx:212-233`). [2](#0-1) [3](#0-2) 

Similarly, `onOpenItem` in `app/src/ui/changes/sidebar.tsx:282-285` and `onOpenInExternalEditor` in `app/src/ui/app.tsx:3429-3437` do `Path.join(repository.path, path)` with no traversal check before invoking `openFile(...)` / `dispatcher.openInExternalEditor(...)`, which shell out to the OS default handler or the user's configured external editor. [4](#0-3) [5](#0-4) 

The broken invariant is the same class as H-02: the codebase has one hardened implementation of "resolve a relative path safely under the repo root" (`resolveWithin`, used by the deep-link handler) but the far more frequently used call sites that build filesystem paths out of attacker-influenced content (file entries reported by `git status`/`git diff`/`git log` for a cloned/fetched repository, or files listed in a PR diff) never reuse it — exactly mirroring how `GameItems` guarded `safeTransferFrom` but forgot `safeBatchTransferFrom`.

### Impact Explanation
If an attacker can get a path string containing `..` traversal segments to surface as a `file.path`/`oldPath` in git's own porcelain/diff/log output for a repository the victim clones, fetches, or opens a PR diff for, then a normal user action — right-click → "Reveal in Finder/Explorer", "Open in External Editor", or "Open with Default Program" — would resolve outside the repository working directory. Since `shell.showItemInFolder`/`openPath`/external-editor invocation operate on the OS default handler, this is a path-write/read-outside-repo primitive with no additional confirmation dialog. I was not able to fully verify (within the current investigation) whether upstream `git status`/`git log` parsing in this codebase (`app/src/lib/status-parser.ts`, `app/src/lib/get-old-path.ts`) performs any additional sanitization of the raw path strings it receives from git plumbing before constructing `WorkingDirectoryFileChange`/`CommittedFileChange` — grep of those files did not show explicit `..`/absolute-path filtering, but I could not read their full contents to confirm conclusively.

### Likelihood Explanation
Getting git itself to emit a `..`-containing path via `status`/`diff`/`log` typically requires either a repository whose tree objects were crafted outside the normal `git add`/`commit` path-safety checks (e.g., via `git hash-object`/`mktree`/`fast-import`, or corrupted/hand-built pack data) or reliance on git's own historical path-safety bugs (the class covered by CVE-2019-1349/1350/1352/1387 and similar). This is a real, previously-exploited bug class in Git tooling, but it depends on git plumbing actually surfacing such an entry through porcelain output, which I could not fully confirm from the indexed files alone (`status-parser.ts` internals were not fully retrievable). Given this uncertainty, likelihood is best characterized as "requires an unusual malicious tree/pack construction that bypasses git's own protections," not "trivially reachable with an ordinary commit."

### Recommendation
Route every place that turns a repository-relative, git-reported path into a filesystem path through `resolveWithin(repository.path, path)` (the same helper already used in `openRepositoryFromUrl`), rejecting the operation (with a log message, mirroring `dispatcher.ts:1966-1971`) whenever the resolved path is `null` (i.e., outside the repo root). This should be applied at minimum in `revealInFileManager` (`app-shell.ts`), `onOpenItem`/`onOpenInExternalEditor` (`sidebar.tsx`, `app.tsx`, `filter-changes-list.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `copilot-conflicts-dialog.tsx`), and any other `Path.join(repository.path, file.path)` call site that isn't already covered by git's own checkout-time path validation.

### Proof of Concept
Because I could not fully confirm (given tool-call limits) whether `git status`/`git log --name-status` in this codebase's parsing layer would actually surface a `..`-containing path from a maliciously crafted tree/pack, I cannot provide a fully verified end-to-end PoC. The concrete, verifiable code-level gap is:
1. `resolveWithin` exists and is proven (by `app/test/unit/path-test.ts:47-101`) to correctly reject/neutralize traversal and symlink-escape attempts. [6](#0-5) 
2. It is used in exactly one place that turns an externally-influenced path into a filesystem path (`dispatcher.ts:1957-1972`). [7](#0-6) 
3. `revealInFileManager` and the `onOpenItem`/`onOpenInExternalEditor` handlers perform the equivalent `Path.join` operation on git-status/diff/log-derived paths without ever calling `resolveWithin`, so if such a path could ever contain `..` segments, it would escape the repository root undetected. [1](#0-0) 

Given the unresolved question of whether git's own porcelain output can be made to emit such a path in this codebase's parsing pipeline, I'm flagging this with reduced confidence rather than as a fully confirmed exploit chain.

    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {

    })

    })
