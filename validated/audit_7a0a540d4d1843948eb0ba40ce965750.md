## Title
Unversioned concurrent `_loadStatus` writes can silently discard merge-conflict resolutions before commit - ([File: app/src/lib/stores/app-store.ts])

### Summary
`app-store.ts`'s `_loadStatus` is invoked from many independent, uncoordinated call sites (repository selection, `_refreshRepository`, `abortMerge`, file-watcher-triggered refreshes, post-fetch/pull refresh, etc.). Each invocation does an `await gitStore.loadStatus()` (a `git status` spawn) and only afterwards writes the resulting `conflictState`/`workingDirectory` into `RepositoryStateCache` via `updateChangesState`. There is no generation/version check comparing the snapshot that was used to compute the write against the *current* state at write time — exactly the invariant that was missing in the Lighthouse CGC bug (no "expected == current" check before overwriting shared custody-requirement state).

### Finding Description
`_loadStatus` (`app/src/lib/stores/app-store.ts:2969-3004`) does: [1](#0-0) 
1. `await gitStore.loadStatus()` — an async external git process call whose duration is attacker/OS-influenceable.
2. Writes `updateChangedFiles(...)` and `updateConflictState(...)` into the shared `RepositoryStateCache`.

`updateConflictState` (`app/src/lib/stores/updates/changes-state.ts:263-311`) carries forward `manualResolutions` from `state.conflictState` — but `state` is read at write time from the cache, not from a snapshot taken when the corresponding `git status` call began: [2](#0-1) 

`RepositoryStateCache.update()` (`app/src/lib/stores/repository-state-cache.ts:47-72`) performs an unconditional last-write-wins merge with no CAS/generation guard: [3](#0-2) 

Because `_loadStatus` is called from many independent triggers — `_refreshRepository` (`app-store.ts:4093`), `abortMerge` (`dispatcher.ts:1515-1518`), and other refresh paths — with no mutex or "only the latest call may write" guard (contrast with `withPushPullFetch`/`withIsCommitting`, which *do* guard against concurrent execution but only for push/pull/fetch and commit, not for `_loadStatus`), two overlapping `_loadStatus` invocations can complete out of order. An earlier-started, later-finishing call can write a *stale* status/conflict snapshot after a newer call already reflected the user's in-progress manual conflict resolution, silently reverting `conflictState.manualResolutions` (e.g., dropping entries the user set via `_updateManualConflictResolution`, `app-store.ts:8796-8828`) or the whole `conflictState` to `null` if the stale git status snapshot was taken before `MERGE_HEAD` was fully materialized on disk.

The user-facing merge-finish flow (`Merge.onContinueAfterConflicts` in `merge.tsx` → `Dispatcher.finishConflictedMerge`, `dispatcher.ts:1533-1565`) reads `manualResolutions` fresh from the cache at click time and passes it straight to `_finishConflictedMerge` → `createMergeCommit` (`app/src/lib/git/commit.ts:82-97`), which stages "ours"/"theirs" only for paths present in `manualResolutions` and otherwise just `stageFiles` on whatever the working tree/index currently holds. If a stale, racing `_loadStatus` write has just cleared or altered `manualResolutions`, the commit silently uses whatever content git's index happens to contain instead of what the user selected in the UI, with no error surfaced.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug class: a user resolving a merge conflict (which may have been triggered by fetching from an attacker-controlled/compromised remote or proxy that supplies conflicting refs) could have their explicit "ours"/"theirs" resolution choice silently dropped by a concurrently completing, stale `_loadStatus` write, causing the final merge commit to include unintended (potentially attacker-influenced "theirs") content without any warning banner or error — the UI still reports success (`SuccessfulMerge` banner). This falls squarely in the "silent corruption of what the user commits or pushes" impact category, since the committed/pushed content can diverge from what the user believed they resolved to.

### Likelihood Explanation
The likelihood is **low-to-moderate**. It requires precise timing: a background/automatic status refresh (file-watcher, post-fetch refresh, tab focus, etc.) must be in flight and complete *after* the user's manual resolution update but the underlying `git status` call for that stale refresh must have been *started* before the resolution/merge state existed, and it must land after the newer state. This is a genuine TOCTOU race but not trivially triggerable on demand by a remote attacker; a hostile/compromised remote that induces slow or repeated fetch-triggered refreshes during an active merge-conflict resolution session increases the window, but exact reproduction requires favorable scheduling. I was not able to fully verify from static reading how tightly the file-watcher/background-fetch refresh cadence overlaps with the merge-conflict UI flow in practice (dynamic behavior, timers) — this should be confirmed with a live repro.

### Recommendation
Add a monotonically increasing "status generation" (or an in-flight guard similar to `withPushPullFetch`) around `_loadStatus`, so that a `_loadStatus` call whose underlying `git status` was started before the currently-applied generation is dropped rather than written to `RepositoryStateCache`. Concretely: capture a generation counter before calling `gitStore.loadStatus()`, and in `updateChangesState`/`updateConflictState` refuse to overwrite `conflictState`/`manualResolutions` if the cache's generation has advanced past the one captured at call start (mirroring the Lighthouse fix's "expected cgc == current cgc" check before writing `epoch_validator_custody_requirements`).

### Proof of Concept
Not independently reproduced; the following describes the theorized repro sequence for a background agent to validate:
1. Start a merge that produces a conflict, and in `_updateManualConflictResolution` set a resolution (e.g. `theirs`) for a conflicted file.
2. Concurrently trigger another `_loadStatus`/`_refreshRepository` call (e.g. via a fetch/pull, or by simulating a slow `git status` in the older call using a delay/mock) whose underlying `gitStore.loadStatus()` was issued before the resolution was set but resolves after it.
3. Observe that the delayed call's `updateConflictState` write overwrites the current `conflictState.manualResolutions` (reverting the user's `theirs` choice), and that clicking "Continue merge" (`Merge.onContinueAfterConflicts`) then commits content that doesn't reflect the user's manual choice, with no error shown to the user.   public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

    this.updateMultiCommitOperationStateAfterManualResolution(repository)

    this.emitUpdate()
  }

  public update<K extends keyof IRepositoryState>(
    repository: Repository,
    fn: (state: IRepositoryState) => Pick<IRepositoryState, K>
  ) {
    const currentState = this.get(repository)
    const newValues = fn(currentState)
    const newState = merge(currentState, newValues)

    const currentTip = currentState.branchesState.tip
    const newTip = newState.branchesState.tip

    // Only keep the "is amending" state if the head commit hasn't changed, it
    // matches the commit to amend, and there is no "fixing conflicts" state.
    const isAmending =
      newState.commitToAmend !== null &&
      newTip.kind === TipState.Valid &&
      currentTip.kind === TipState.Valid &&
      currentTip.branch.tip.sha === newTip.branch.tip.sha &&
      newTip.branch.tip.sha === newState.commitToAmend.sha &&
      newState.changesState.conflictState === null

    this.repositoryState.set(repository.hash, {
      ...newState,
      commitToAmend: isAmending ? newState.commitToAmend : null,
    })
