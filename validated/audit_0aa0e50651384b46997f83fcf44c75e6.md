### Title
Deterministic CachedPreprocess reuse across signing sessions causes FROST nonce reuse and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a single FROST preprocess seed keyed only by `context`, then reconstructs every future signing machine from that same cached seed via `AlgorithmSignMachine::from_cache`. This makes the nonce — and hence the broadcast preprocess commitments — fully deterministic per context, so every call to `share_internal` for the same context signs with an identical nonce. Two shares produced for different messages under the same nonce allow algebraic recovery of the participant's secret key share, the threshold-signing equivalent of the CVE-2013-7455 double-free pattern (a one-time-use resource consumed twice on a repeated path).

### Finding Description
The upstream bug class is reuse/free of the same resource twice through a repeated code path. In Serai, the analogous one-time resource is the FROST nonce/preprocess seed. `preprocess_internal` generates a fresh preprocess only once per `self.context` and persists it in `CachedPreprocesses`: [1](#0-0) 

Every subsequent call loads the identical cached seed and calls `from_cache`, which deterministically derives the same `nonces` and returns the same serialized preprocess: [2](#0-1) 

`share_internal` invokes `preprocess_internal` on every share request, so if the coordinator asks for shares on more than one message (or repeated attempts) under the same context, the machine signs with the reused nonce: [3](#0-2) 

The `SignMachine::cache` contract explicitly warns this seed "MUST only be used once" and that reuse "enables recovery of your private key share" — a contract `preprocess_internal` violates by design: [4](#0-3) 

In `AlgorithmSignMachine::sign`, the effective nonce is `base + actual * binding_factor`; the `base`/`actual` values come from `self.nonces`, which are seeded identically on each reuse: [5](#0-4) 

### Impact Explanation
With two signature shares `z₁`, `z₂` produced over different messages `m₁`, `m₂` but the same nonce `k` and the same interpolation factor `λ`, the verifier equation `z = k + H(R, m)·λ·s` gives `z₁ − z₂ = (c₁ − c₂)·λ·s`, recovering `λ·s` and thus the validator's secret key share `s` (λ is public). For the Ristretto MuSig-style tributary signing this compromises the validator's signing key, enabling forgery of future tributary signatures. This is reachable by an unprivileged party: any observer (or a coordinator peer requesting a second attempt under the same context) collects two public shares — no collusion, leaked key, or malicious validator required.

### Likelihood Explanation
`share_internal` unconditionally rebuilds the machine from the cached seed on every invocation and never rotates or deletes `CachedPreprocesses` after use. Any second signing attempt under the same `context` (e.g., a reattempt after a failed round, which the protocol explicitly supports via `attempt` handling elsewhere) deterministically reuses the nonce. The only mitigation is that the context may differ per message; nothing in the code guarantees that, and the cache is keyed purely by `context.encode()`.

### Recommendation
Delete or rotate `CachedPreprocesses` after each successful `share_internal`, or mix a per-signing-session nonce/attempt counter into the seed preimage and `from_cache` derivation so nonce material is unique per signature. Enforce the documented single-use contract of `CachedPreprocess` at the call site rather than relying on context uniqueness.

### Proof of Concept
1. Validator processes `CoordinatorMessage` requiring a share for context `C` → `preprocess_internal` stores seed `S = CachedPreprocess(k)` in `CachedPreprocesses[C]` and emits preprocess commitments `B = k·G`.
2. A second share request arrives for the same context `C` with a different `msg` → `preprocess_internal` loads the same `S` and produces identical `nonces` and identical commitments `B`.
3. Observer collects shares `z₁ = k + c₁·λ·s` and `z₂ = k + c₂·λ·s` with `cᵢ = H(B, mᵢ, …)`.
4. Compute `s = (z₁ − z₂) / (λ·(c₁ − c₂))` — full secret key share recovery of the signing validator.
