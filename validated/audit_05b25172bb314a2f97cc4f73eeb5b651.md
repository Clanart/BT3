### Title
Attacker-controlled first input misattributes deposit origin, redirecting refunds to an arbitrary address - ([File: processor/src/networks/bitcoin.rs])

### Summary
`Bitcoin::get_outputs` assigns a single `presumed_origin` — derived solely from `tx.input[0]`'s spent output — to every Serai-bound output found in a transaction. Because transaction input ordering and CoinJoin-style multi-party funding are entirely controlled by the parties constructing the transaction, an unprivileged user can cause a deposit (or a dust/unparseable deposit later refunded via `refund_plan`) to be attributed to an origin address they chose, rather than the actual funder of the Serai output. This is the Serai analog of CVE-2018-18506: an attacker-influenced routing field overrides the true origin/destination, so value intended to be associated with one party is redirected to another endpoint.

### Finding Description
In `get_outputs`, after scanning a transaction's outputs, the processor fetches the output spent by `tx.input[0]` and uses its `script_pubkey` as `presumed_origin` for **all** matched outputs in that transaction:

```rust
// processor/src/networks/bitcoin.rs:714-736
let spent_output = {
  let input = &tx.input[0];
  let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
  spent_tx.reverse();
  ...
  tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
};
Address::new(spent_output.script_pubkey)
...
for output in &mut outputs {
  if output.kind == OutputType::External {
    output.data.clone_from(&data);
  }
  output.presumed_origin.clone_from(&presumed_origin);
}
```

The in-code comment already concedes the heuristic can be wrong ("This may identify the P2WSH output *embedding the InInstruction* as the origin"), but the deeper issue is structural: `input[0]` is attacker-selected ordering, and in a multi-party transaction (CoinJoin, PayJoin, batch spend) the funder of input[0] need have no relationship to whoever created the output paying Serai's key. `Output::read`/`write` persist `presumed_origin` (lines 136-156), and downstream refund logic routes funds to `output.presumed_origin()` via `Scheduler::refund_plan` (`processor/src/multisigs/scheduler/utxo.rs:587-605`), which emits a `Plan` paying `refund_to` — a threshold-signed transaction.

### Impact Explanation
When a received output must be refunded (e.g., below usable threshold, unparseable/absent `InInstruction` data, or an output Serai declines to process), the multisig signs a payment to the `presumed_origin` address. An attacker who arranges `input[0]` to resolve to an address they control — while the Serai-bound output is actually funded by another party's input in a collaborative transaction — causes the threshold signature to send the refunded balance to the attacker. This is a concrete signing of an unintended payment: funds are redirected to an attacker endpoint purely through the attacker-controlled transaction structure, mirroring the PAC-file redirect of CVE-2018-18506 where attacker-supplied routing overrides the intended destination.

### Likelihood Explanation
Exploitation requires a multi-input transaction paying a Serai address where the victim funds the Serai output but the attacker controls `input[0]`, plus a subsequent refund path. CoinJoin/PayJoin-style constructions are the natural vehicle and are common in Bitcoin. It does not require compromising any validator, key share, or RPC. Severity is bounded because it only reroutes refund-bound value (not direct mints/burns already committed via `data`), so Medium is appropriate.

### Recommendation
Do not derive a single `presumed_origin` from `tx.input[0]` for all outputs. At minimum, only attribute an origin when the transaction has exactly one input owner, or when the depositor proves origin via the `InInstruction`/data payload (which is already bound into `OP_SHA256 ... OP_EQUALVERIFY` scripts for External outputs). Refunds should only be issued to an origin authenticated by the deposit instruction, or to a claimant signature, not inferred from input ordering.

### Proof of Concept
1. Victim V and attacker A construct a collaborative (CoinJoin-style) transaction. A places their own UTXO as `input[0]`; V contributes an input funding an output paying Serai's external/branch/change script (publicly derivable: `key + G*offset`, offsets from `Secp256k1::hash_to_F(KEY_DST, b"...")` at `processor/src/networks/bitcoin.rs:308-344`).
2. The transaction confirms. `get_outputs` scans it, matches the Serai script, and sets `presumed_origin = Address::new(script_pubkey_of(input[0]_prevout))` = A's address (bitcoin.rs:714-736).
3. The output lacks/ignores valid Serai deposit data or is otherwise refund-bound; the scheduler emits `refund_plan(output, presumed_origin)` (scheduler/utxo.rs:587-605), and the FROST multisig signs a transaction paying A.
4. A receives funds whose true economic origin was V — value redirected to an attacker-chosen endpoint via attacker-controlled transaction layout.

Note: I did not exhaustively trace every consumer of `presumed_origin` in `processor/src/multisigs/mod.rs` (5 references exist there); the refund path above is the reachable signing consequence, and any other origin-based crediting inherits the same misattribution.
