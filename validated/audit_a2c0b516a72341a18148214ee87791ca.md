## Finding

### Title
Outbound request delivery reward is priced at claim time, not delivery time, letting relayers retroactively capture reward increases for already-completed deliveries - (File: modules/pallets/relayer/src/outbound_request.rs)

### Summary
`process_outbound_request_delivery_claim` looks up the payout amount from the *current* value of `OutboundRequestDeliveryReward[module_id]` at the moment the claim is processed, not the value that was in effect when the relayer actually delivered the request. This is the same broken invariant as the `UpliftOnlyExample` bug: a value that should be locked in at the time of the qualifying action (delivery) is instead re-read from live, mutable governance state at settlement time, letting the price of already-rendered work change retroactively.

### Finding Description
The claim handler reads the reward with no historical binding to the request's dispatch or delivery time: [1](#0-0) 

Compare with the storage definition, which is a live governance-mutable map with no versioning or snapshotting: [2](#0-1) 

`set_outbound_request_delivery_reward` can be called by governance (`RelayerOrigin`) at any time to change `OutboundRequestDeliveryReward[module_id]`, and there is no deadline or delivery-height binding in `OutboundRequestDeliveryClaim` that ties the claim to the reward that existed at delivery time — only `RequestCommitments`, idempotency (`OutboundRequestsClaimed`), source-chain, module-id-allowlist, and state-proof-of-delivery checks are performed: [3](#0-2) 

A relayer that delivered a hyperbridge-originated request under a low (or even not-yet-enabled) reward regime can simply defer submitting `claim_outbound_request_delivery_reward` until governance raises `OutboundRequestDeliveryReward[module_id]`, then submit the claim and be paid the new, higher rate for work performed under the old rate — exactly mirroring how a user in the `UpliftOnlyExample` report could transfer their NFT after the admin lowered `upliftFeeBps` to retroactively benefit from the new value. There is no per-commitment snapshot of the reward rate at dispatch time (unlike `RequestCommitments`, which is written once at dispatch and never mutated), so nothing prevents the claim from reading a value that postdates the actual service.

### Impact Explanation
Because the reward is paid from the treasury PalletId account on every successful claim, an inflated reward relative to what governance intended for the delivered epoch results in direct, unrecoverable loss of treasury funds (BRIDGE) — the same fund-loss category as the original report's "loss of funds to the Quant Admin / LP providers." This is a systemic, protocol-level (not peer/relayer-compromise-dependent) fund drain: any relayer holding an already-proven, not-yet-claimed delivery receipt benefits automatically whenever governance increases a module's reward, without doing any additional work.

### Likelihood Explanation
This requires no malicious relayer, prover, or governance actor — it is triggered by the completely ordinary, expected sequence of events: relayer delivers → some time passes → governance later adjusts `OutboundRequestDeliveryReward` (which the documentation explicitly describes as adjustable, e.g. was set to 10 tBRIDGE via a sudo call) → relayer submits its still-valid, still-unclaimed claim. There is no time-boundedness anywhere in the pipeline forcing prompt claims, so any relayer that is simply slow (or deliberately patient) captures the new rate.

### Recommendation
Bind the reward rate to the request at dispatch time rather than reading a live governance value at claim time. For example, snapshot the reward amount into `RequestCommitments` (or a parallel per-commitment storage entry) when the request is dispatched, or explicitly require `OutboundRequestDeliveryClaim` to carry a delivery/dispatch height and reject claims whose commitment predates the currently configured reward, so a claim always pays what was configured when the qualifying delivery occurred.

### Proof of Concept
1. Governance leaves `OutboundRequestDeliveryReward[b"host-exec"]` at 0 (module not yet incentivized). A relayer delivers a `host-executive` originated `PostRequest` to its destination; `RequestReceipts[commitment]` is written on the destination with the relayer's address.
2. The relayer does not claim yet — the claim has no deadline.
3. Governance later calls `set_outbound_request_delivery_reward(b"host-exec", 10_000_000_000_000)` to enable rewards for that module going forward (as documented for `b"ismp-ast"` in `docs/outbound-request-incentivization.md`).
4. The relayer now submits `claim_outbound_request_delivery_reward` for the commitment from step 1. `process_outbound_request_delivery_claim` passes every check (`RequestCommitments` present, not yet claimed, allowlist now non-zero, state proof of the old receipt still verifies) and pays out the new 10 tBRIDGE reward for a delivery that happened while the module had zero configured reward — reward the treasury never intended to pay for that specific delivery. 	pub fn process_outbound_request_delivery_claim(
		claim: OutboundRequestDeliveryClaim,
	) -> DispatchResult {
		let OutboundRequestDeliveryClaim { request, state_proof, payee, signature } = claim;
		let destination = state_proof.height.id.state_id;

		let commitment = hash_request::<<T as Config>::IsmpHost>(&Request::Post(request.clone()));

		let host = <T as Config>::IsmpHost::default();
		ensure!(
			request.source == host.host_state_machine(),
			Error::<T>::OutboundRequestSourceNotHyperbridge,
		);

		ensure!(
			RequestCommitments::<T>::get(commitment).is_some(),
			Error::<T>::OutboundRequestNotKnown,
		);

		ensure!(
			!OutboundRequestsClaimed::<T>::contains_key(commitment),
			Error::<T>::OutboundRequestAlreadyClaimed,
		);

		let module_id: BoundedVec<u8, ModuleIdBound> = request
			.from
			.clone()
			.try_into()
			.map_err(|_| Error::<T>::OutboundRequestModuleIdTooLong)?;
		let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
		ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);

		ensure!(destination == request.dest, Error::<T>::MismatchedStateMachine);

		let state_machine = ismp::handlers::validate_state_machine(&host, state_proof.height)
			.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let receipt_key = state_machine
			.receipts_state_trie_key(vec![commitment])
			.into_iter()
			.next()
			.ok_or(Error::<T>::OutboundRequestUnsupportedDestination)?;
		let proof_results =
			Self::verify_withdrawal_proof(&*state_machine, &state_proof, vec![receipt_key.clone()])
				.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let raw = proof_results
			.get(&receipt_key)
			.cloned()
			.flatten()
			.ok_or(Error::<T>::OutboundDeliveryNotProven)?;

		let delivered_by = Self::decode_receipt_relayer(destination, &raw)?;

		let msg = outbound_request_delivery_message(commitment, destination, payee);
		let recovered = signature.verify(&msg, None).map_err(|_| Error::<T>::InvalidSignature)?;
		ensure!(recovered == delivered_by, Error::<T>::OutboundRequestSignerMismatch);

		let treasury: T::AccountId =
			<T as Config>::TreasuryPalletId::get().into_account_truncating();
		let payee_account: T::AccountId = payee.into();
		<<T as pallet_ismp::Config>::Currency as Mutate<T::AccountId>>::transfer(
			&treasury,
			&payee_account,
			reward,
			Preservation::Preserve,
		)
		.map_err(|_| Error::<T>::OutboundRequestRewardTransferFailed)?;

		OutboundRequestsClaimed::<T>::insert(commitment, ());

		Self::deposit_event(Event::OutboundRequestDeliveryRewarded {
			commitment,
			state_machine: destination,
			module_id,
			relayer: payee_account,
			amount: reward,
		});

		Ok(())
	}
