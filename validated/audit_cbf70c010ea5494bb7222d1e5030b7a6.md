### Title
Unauthenticated denom-injection into an unassociated EVM address's cast account causes an unbounded, gas-unmetered coin migration loop in the association ante handler - ([File: x/evm/ante/preprocess.go])

### Summary
Any unprivileged user can permissionlessly create unlimited tokenfactory denoms, mint them to themselves, and `bank send` a small amount of each to the "cast address" (`sdk.AccAddress(evmAddr[:])`) of any not-yet-associated Sei/EVM address. When the victim later sends their first EVM transaction, `EVMPreprocessDecorator.AnteHandle` automatically and unavoidably triggers an address-association flow that calls `bankKeeper.SpendableCoins` and `bankKeeper.SendCoins` over *all* denoms held by the cast address — under an **infinite gas meter** — so the attacker fully controls the size of this unbounded, unmetered loop that runs synchronously in every node's ante handler (CheckTx and DeliverTx) for the victim's transaction.

### Finding Description
`EVMPreprocessDecorator.AnteHandle` sets an infinite gas meter for EVM ante processing and, when the sender is not yet associated, unconditionally calls `associateHelper.AssociateAddresses`: [1](#0-0) 

`AssociateAddresses` in turn calls `MigrateBalance`, which pulls **every** denom the "cast address" (`sdk.AccAddress(evmAddr[:])`) holds via `SpendableCoins` and transfers all of them in one `SendCoins` call to the newly associated Sei address: [2](#0-1) 

`SendCoins`/balance mutation is implemented as a per-denom loop (`SubUnlockedCoins`/`AddCoins`) over the `sdk.Coins` slice returned by `SpendableCoins`, with a store read/write per denom: [3](#0-2) 

The number of denoms in that slice is entirely attacker-controlled: the tokenfactory module lets **any account** permissionlessly create denoms of the form `factory/{creator}/{subdenom}`, and the creator is the default admin who can mint and send them to any address without the recipient's consent: [4](#0-3) [5](#0-4) 

Because the EVM ante handler runs under an infinite gas meter (`ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))`), the normal gas-based cost limiting that would otherwise bound how much CPU/storage work a single transaction can trigger is disabled for this step, so the migration loop's cost scales purely with however many denoms the attacker chose to inject into the victim's cast address — with no consensus-enforced ceiling.

This is directly analogous to the reported Teller `commitCollateral` bug: an unauthenticated third party can unilaterally append attacker-controlled "collateral"/state entries to another party's account, which are later iterated over during that party's own (unavoidable, automatically triggered) critical operation, producing unbounded/DoS-prone work that the victim cannot prevent or opt out of.

### Impact Explanation
Every full node processes this migration loop during CheckTx and again during DeliverTx for the victim's first EVM transaction. If the attacker seeds thousands of distinct denoms into the cast address before the victim ever transacts, the ante handler must perform thousands of unmetered KV store reads/writes synchronously as part of ordinary transaction admission, which can materially delay block production (potentially beyond the 2.5s threshold) and can be repeated against many victim addresses simultaneously, amplifying load network-wide. Because the gas meter is infinite for this step, there is no fee/gas cost to the attacker that scales proportionally with the damage inflicted on the network, and no cost recovery mechanism protects validators from the extra processing.

### Likelihood Explanation
The attack requires only permissionless, unprivileged actions available to any account: `MsgCreateDenom` (tokenfactory), `MsgMint` (as the denom's own admin), and `MsgSend` (bank) to the victim's cast address — none of which require the victim's cooperation, admin/governance privileges, or any race condition. The victim need only submit any ordinary EVM transaction (an action every new EVM user performs) for the poisoned migration to trigger.

### Recommendation
- Bound the number of denoms/coins migrated in `AssociationHelper.MigrateBalance` (and the equivalent legacy versions), e.g., cap the number of distinct denoms processed per association, or defer/park excess denoms rather than attempting to migrate everything in the cast address atomically.
- Meter (do not use an infinite gas meter for) the balance-migration portion of `EVMPreprocessDecorator.AnteHandle`, so cost scales with and is limited by real gas accounting rather than being unmetered.
- Consider validating/limiting how many distinct denoms a single account (especially an EVM cast address) may accumulate before association, or performing the migration incrementally across multiple blocks/transactions instead of a single ante-handler call.

### Proof of Concept
1. Attacker generates victim's deterministic EVM cast address `castAddr = sdk.AccAddress(evmAddr[:])` for a target `evmAddr` that has not yet associated with a Sei address (e.g., a brand-new EVM wallet about to be funded/used for the first time).
2. Attacker repeatedly submits `MsgCreateDenom` (tokenfactory) to create `N` unique denoms `factory/{attacker}/{i}` for `i in [1..N]`.
3. Attacker submits `MsgMint` for each denom to mint to themselves (they are the default admin), then `MsgSend` (bank) 1 unit of each of the `N` denoms to `castAddr`.
4. `SpendableCoins(ctx, castAddr)` now returns `N` distinct denom entries.
5. When the victim submits their first EVM transaction, `EVMPreprocessDecorator.AnteHandle` detects the sender is unassociated and calls `AssociateAddresses` → `MigrateBalance`, which fetches all `N` coins and calls `SendCoins`, iterating and performing store writes for each of the `N` denoms under an infinite gas meter — with `N` chosen arbitrarily large by the attacker, this synchronous per-transaction work is unbounded and unmetered.

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

# Token Factory

The tokenfactory module allows any account to create a new token with
the name `factory/{creator address}/{subdenom}`. Because tokens are
namespaced by creator address, this allows token minting to be
permissionless, due to not needing to resolve name collisions. A single
account can create multiple denoms, by providing a unique subdenom for each
created denom. Once a denom is created, the original creator is given
"admin" privileges over the asset. This allows them to:

- Mint their denom to any account
- Burn their denom from any account
- Create a transfer of their denom between any two accounts
- Change the admin. In the future, more admin capabilities may be added. Admins
  can choose to share admin privileges with other accounts using the authz
  module. The `ChangeAdmin` functionality, allows changing the master admin
  account, or even setting it to `""`, meaning no account has admin privileges
  of the asset.
