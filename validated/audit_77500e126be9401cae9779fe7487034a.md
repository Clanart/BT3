### Title
Duplicate encryption-key registration panics the node mid-DKG, denying service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2020-14568 is an availability-only bug class: a network-reachable input causes a hang or repeatable crash. The direct analog in Serai is the `assert!` in `Decryption::register`, which aborts the process if a participant submits a second `EncryptionKeyMessage`. The registration message is an unauthenticated, peer-supplied input during the PedPoP DKG round, so a single malicious participant can crash an honest validator's DKG session.

### Finding Description
`Decryption<C>::register` inserts a per-participant ECDH encryption key into `self.enc_keys` and enforces uniqueness with a hard `assert!`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-361
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
```

`EncryptionKeyMessage::read` (same file, lines 57-59) accepts arbitrary peer bytes — a `Message` plus a `C::read_G` point — so the attacker controls both when and how many messages they send. `Encryption::register` (lines 452-458) forwards each received message directly into `Decryption::register`. Because the panic is an `assert!` on untrusted protocol input rather than a returned `Err`, the duplicate-registration condition unwinds/aborts instead of being handled, killing the key-generation session (and the thread/process hosting it).

The MySQL advisory describes exactly this shape: high-privileged network access, no confidentiality or integrity impact, a repeatable crash/hang for complete denial of service.

### Impact Explanation
Availability loss. A participant in a PedPoP key-generation ceremony sends two `EncryptionKeyMessage`s bound to their own `Participant` index. The second call to `register` hits the `assert!` and panics, aborting the victim's DKG run. Since DKG runs are coordinated and threshold-bound, repeatedly crashing honest participants prevents key generation from completing — a repeatable, remotely-triggered denial of service analogous to the InnoDB crash.

### Likelihood Explanation
Any DKG participant can reach this path with a public protocol message; no key material, collusion, or BFT fault assumptions are required. The only constraint is whether the caller deduplicates messages by sender before calling `register`; if the driving loop processes received messages in order (as the encryption-box design suggests, since `Decryption` maintains its own `HashMap`), a duplicated registration reaches the `assert!` directly. Even if upstream partially deduplicates, the `assert!` documents that re-registration was considered reachable enough to guard — but guards it with a crash rather than an error.

### Recommendation
Replace the `assert!` with a fallible check returning a `Result`/`Err` (e.g., a `DuplicatedParticipant` error propagated to the DKG layer), so a misbehaving peer's message is rejected and blamed instead of crashing the node:

```rust
if self.enc_keys.contains_key(&participant) {
  Err(...DuplicatedParticipant(participant))?;
}
```

The same audit should be applied to other `assert!`/indexing sites reachable from peer input in this module (e.g., `self.enc_keys[&decryptor]` and `self.decryption.enc_keys[&participant]` at lines 388 and 466, which panic on an unregistered index if a blame/decryption path is reached before registration completes).
