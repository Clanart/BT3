## Title
Conflict-marker look-alike lines let attacker-controlled branch content desynchronize Copilot's hunk splicing, silently corrupting the committed merge result - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted conflict resolution extracts conflict "hunks" from a file purely by regex-matching line prefixes (`<<<<<<<`, `=======`, `|||||||`, `>>>>>>>`), sends each hunk to the model, and later splices the model's per-hunk resolutions back into the original file **by order, not by identity**. The only integrity check before splicing is that the returned hunk *count* matches the expected count. Just like the Vault's `adjustmentsMade == adjustmentsRequired` check that let an attacker satisfy an aggregate counter without the individual events actually corresponding, `validateResolutionPaths` only verifies `resolution.hunks.length === expectedCount` per file — it never verifies that a given resolution actually corresponds to the same conflict region it was generated for. Because the hunk boundaries themselves are derived from naive regex matching on arbitrary attacker-supplied file content (from the "theirs" branch of a merge), a crafted file can cause the parser to mis-detect hunk boundaries, and the count-only guard has no way to catch the resulting misalignment before it's written to disk.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks a conflicted file line-by-line, treating *any* line that matches `oursMarker`, `baseMarker`, `separatorMarker`, or `theirsMarker` as a structural conflict boundary: [1](#0-0) 

These regexes only check that a line *starts with* 7+ of the corresponding character (`^={7}$` for the separator, `^<{7}` / `^>{7}` for ours/theirs) — they do not verify that the line is an actual git-generated marker (e.g. verifying uniqueness/pairing across the whole file, or that it was inserted by the merge machinery rather than being pre-existing file content). The hunk-collection loop stops "ours" content at the first line matching the base or separator pattern, and stops "theirs" content at the first line matching the closing marker: [2](#0-1) 

Any attacker-controlled branch that introduces a line looking like `=======` (a common Markdown setext-heading underline or changelog/ASCII separator) or `>>>>>>> something` inside legitimate "ours"/"theirs" content will cause a *real* conflict block to be mis-split or truncated early, silently shifting hunk boundaries and/or hunk count relative to what the developer actually sees rendered in a diff viewer.

After the model responds, `validateResolutionPaths` is the only structural safety check, and it validates purely by count: [3](#0-2) 
(see `app/src/lib/copilot-conflict-resolution.ts:509-520`)

Then `reassembleResolvedFile` re-scans the *same* raw file independently and splices resolutions back in strictly by sequential index, a design explicitly called out in its own doc comment: [4](#0-3) 

with the actual splice loop matching purely on `hunkIndex` order: [5](#0-4) 

Because extraction (for the prompt) and reassembly (for writing to disk) both rely on the same ambiguous regex-based boundary detection over attacker-influenced content, and the only cross-check is a hunk *count* equality (not per-hunk identity/content verification), the invariant "each resolution is spliced into the exact region it was generated for" can silently break whenever the merged content contains marker-like lines that aren't real git conflict markers.

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes." A misparsed hunk boundary means the resolved content the model returns for "conflict N" gets spliced into the wrong span of the file (or with wrong surrounding context), while the actual conflict-marker-count validation still passes because it only checks aggregate counts. The user, trusting the AI-resolved diff, may commit and push a file where code was silently dropped, duplicated, or displaced — without any error or warning surfaced by `validateResolutionPaths` or `reassembleResolvedFile`, since both only guard against gross malformation (missing closing marker, wrong total count), not misidentified boundaries.

### Likelihood Explanation
This requires only that the victim merges/rebases/cherry-picks a branch containing attacker-authored file content and then uses Desktop's built-in "resolve conflicts with Copilot" feature — a normal, expected workflow, not an unnatural user action. Lines that incidentally match the marker regexes (`=======` as a Markdown separator, `>>>>>>> ` as blockquote/log-style text, embedded diff/patch text in documentation or test fixtures) are plausible in real-world files, especially docs, changelogs, or files that themselves contain example diffs.

### Recommendation
Do not rely on naive line-prefix regex matching plus a downstream hunk-count check as the sole correctness guarantee. Either (a) validate that the *content* between detected markers deterministically round-trips (e.g., disambiguate real markers using git's own conflict-style output metadata rather than re-deriving them from raw text), or (b) pass a stable per-hunk identifier (e.g., a hash of `oursContent`/`theirsContent`) through the prompt/response round trip and have `reassembleResolvedFile` match resolutions to hunks by that identifier instead of positional order, failing loudly on any mismatch instead of silently splicing by index.

### Proof of Concept
1. Attacker pushes a branch that modifies `README.md` (or any text file) such that its content, on the "theirs" side of a future merge, contains a legitimate-looking line consisting of exactly `=======` (e.g., a Markdown H1 underline) directly inside a region that will conflict with the victim's local changes.
2. Victim merges the attacker's branch, producing a real conflict in that file; the actual git-inserted markers surround a hunk whose "theirs" content also contains the fake `=======` line.
3. Victim invokes Desktop's Copilot conflict-resolution feature. `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) prematurely terminates the "ours"/"theirs" collection at the fake `=======` line, producing a hunk whose `oursContent`/`theirsContent` boundaries do not match what's rendered in Desktop's diff viewer, and potentially producing an extra spurious hunk.
4. Copilot resolves each parsed hunk faithfully to the (already-corrupted) boundaries it was given; `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:509-520`) accepts the response because the hunk count matches what was sent.
5. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) splices the resolutions back in by index into the same mis-detected boundaries, producing a file that is missing or duplicates real code the developer never intended to change — and this is committed/pushed as if it were a correct resolution.
