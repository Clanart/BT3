### Title
Payout OP_RETURN operator identity is unauthenticated (SIGHASH_SINGLE|ANYONECANPAY) yet solely determines the reimbursed operator via `deposit_constant` - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`bridge_circuit` derives `operator_xonlypk` purely from the first OP_RETURN output of `input.payout_spv.transaction` and feeds it into `deposit_constant`, which becomes part of the committed `journal_hash`. Because the user's payout signature uses `TapSighashType::SinglePlusAnyoneCanPay`, it commits only to input 0 and output 0 of the payout transaction, leaving the OP_RETURN output (index 2) and the anchor output (index 1) completely unauthenticated and mutable by anyone who observes the unconfirmed transaction on the network.

### Finding Description
Binding claimed by the protocol: `operator_xonlypk` committed in `DepositConstant` == the operator that actually broadcast/funded `input.payout_spv.transaction`.

Code path:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with output[0]=user payout, output[1]=anchor (CPFP), output[2]=OP_RETURN(operator_xonly_pk), and signs only with `user_sig` over input 0 via `SpendPath::KeySpend`. [1](#0-0) 
- The user's signature is required to use `SinglePlusAnyoneCanPay`, both when generated (`core/src/rpc/parser/operator.rs:174-187`) and verified in `Operator::withdraw` (`core/src/operator.rs:630-637`). [2](#0-1) [3](#0-2) 
- `SinglePlusAnyoneCanPay` (`SIGHASH_SINGLE | ANYONECANPAY`) commits the signature only to input 0 and the single output at the same index (output 0). Outputs 1 (anchor) and 2 (OP_RETURN with operator pubkey) are *not* covered by the sighash, as confirmed by `calculate_pubkey_spend_sighash`'s handling of `Prevouts::One` for these sighash types. [4](#0-3) 
- In the circuit, `bridge_circuit` reads `operator_xonlypk` straight from that unauthenticated OP_RETURN and feeds it into `deposit_constant`, with no check that this key belongs to whoever funded/broadcast the transaction, nor any cryptographic tie to the witness that spent the UTXO. [5](#0-4) [6](#0-5) 

Because the OP_RETURN and anchor outputs are unsigned, an unprivileged attacker who observes the operator's broadcast (but unconfirmed) payout transaction in the mempool can construct a *different* transaction spending the exact same input with the exact same witness (the SINGLE|ANYONECANPAY signature remains valid for any output[1]/output[2] content), replacing output[2]'s OP_RETURN with arbitrary bytes and replacing output[1] with their own anchor for their own CPFP fee-bump, then race this alternative transaction into confirmation ahead of the operator's original broadcast. The mutated, confirmed transaction is what `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) will scan and store as the officially "confirmed" OP_RETURN operator for that withdrawal, and it is this on-chain-confirmed OP_RETURN value that both `bridge_circuit`'s `deposit_constant` and the off-chain `is_kickoff_malicious` heuristic consume. [7](#0-6) 

The only existing guard against this divergence is `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`), which compares the DB-recorded (i.e. confirmed on-chain, potentially attacker-mutated) OP_RETURN `operator_xonly_pk` against `kickoff_data.operator_xonly_pk` of whoever later submits the kickoff tx for that deposit, and flags a mismatch as malicious. This check is asymmetric and insufficient: it operates purely off the already-mutated, confirmed chain state and cannot distinguish "genuinely dishonest operator" from "honest operator whose OP_RETURN credit was malleated away pre-confirmation by an unrelated attacker." When the mismatch is detected, the honest operator who actually fronted the withdrawal (and who alone holds the private key required to build the presigned round/kickoff tx graph) gets challenged and loses collateral, even though they did fund the payout. [8](#0-7) 

### Impact Explanation
The confirmed on-chain OP_RETURN value — which the bridge/off-chain logic and the zk circuit both trust as ground truth for "who fronted this withdrawal" — can be rewritten by any unprivileged party before confirmation, without needing the real operator's or any operator's private key. This produces:
- An honest operator who genuinely fronted a withdrawal is later flagged malicious by `is_kickoff_malicious` because the confirmed OP_RETURN no longer matches their key, causing them to be challenged and lose collateral (Critical: "an honest operator's collateral burned") and/or be permanently unable to be reimbursed (Critical: "an honest operator permanently unable to be reimbursed").
- Because `deposit_constant` (committed into `journal_hash`) is derived from this same manipulable OP_RETURN value, the zk proof's public output can assert an operator identity that never actually funded the payout, i.e. a false claim proved by the bridge circuit (Critical: "a false claim proved... by the bridge... circuit").
- Repeatable across any withdrawal/operator pair; the attacker's cost per attempt is limited to Bitcoin transaction fees needed to win the confirmation race, and requires no bridge role or key material.

### Likelihood Explanation
Preconditions: an operator must broadcast a payout transaction (standard flow) using `SinglePlusAnyoneCanPay`, and it must remain unconfirmed for at least one block interval (which is normal since the anchor output requires a separate CPFP transaction to be broadcast and confirmed together). During that window, any mempool-observing party can construct and attempt to confirm a competing spend of the same input with a different OP_RETURN/anchor. Feasibility depends on Bitcoin-network-level factors (RBF signaling, relay policy, miner selection) that are outside this repo's control, but the underlying cryptographic weakness — the OP_RETURN identity claim being completely outside the signed message — is a certain, reproducible fact independent of network conditions, and is directly demonstrable in a `cargo test` by computing `deposit_constant` twice with different `operator_xonlypk` values pasted into the OP_RETURN of an otherwise-identical, still-validly-signed payout transaction.

### Recommendation
Bind the operator's identity cryptographically into the signed data of the payout transaction (e.g. require the OP_RETURN/anchor outputs to be covered by the sighash by using `SIGHASH_ALL` or by having the operator additionally co-sign/commit to the specific payout transaction bytes including OP_RETURN before broadcast), or otherwise authenticate the operator claim (e.g., require an operator signature over the full payout tx, verified by the circuit) rather than trusting raw OP_RETURN bytes lifted from an SIGHASH_SINGLE|ANYONECANPAY-signed transaction.

```
fn test_deposit_constant_op_return_malleability() {
    // Build a payout tx with SinglePlusAnyoneCanPay witness (as create_payout_txhandler does),
    // with output[0]=user payout, output[1]=anchor, output[2]=OP_RETURN(real_operator_xonlypk).
    let tx_real = build_payout_tx_with_op_return(real_operator_xonlypk);

    // Attacker mutates ONLY output[1] (anchor) and output[2] (OP_RETURN) - reusing the same
    // witness/signature, since SinglePlusAnyoneCanPay does not cover these outputs.
    let tx_attacker = build_payout_tx_with_op_return(attacker_chosen_arbitrary_xonlypk);

    // Same input/witness validity for both (SinglePlusAnyoneCanPay signature check passes for both).
    assert_valid_signature(&tx_real);
    assert_valid_signature(&tx_attacker);

    let dc_real = deposit_constant(real_operator_xonlypk, ..., round_txid, kickoff_round_vout, genesis_state_hash);
    let dc_attacker = deposit_constant(attacker_chosen_arbitrary_xonlypk, ..., round_txid, kickoff_round_vout, genesis_state_hash);

    // Both differ only in the OP_RETURN-sourced key, both are structurally valid inputs to bridge_circuit;
    // nothing in bridge_circuit rejects the attacker's version.
    assert_ne!(dc_real.0, dc_attacker.0);
    // Running bridge_circuit(guest, work_only_image_id) with either input succeeds identically
    // apart from the differing deposit_constant/journal_hash value, proving the OP_RETURN operator
    // claim is unauthenticated.
}
```

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
```
