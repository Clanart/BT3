### Title
PedPoP encrypted secret shares are not bound to their intended recipient, enabling replay of another recipient's ciphertext to falsely blame an honest sender - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The PedPoP DKG encrypts each secret share to a recipient-selected ECDH key, but neither the per-message proof-of-possession transcript nor the ChaCha20 cipher transcript binds the *recipient* identity (participant index or registered encryption key). A ciphertext produced for participant A is therefore a validly authenticated "message from sender S" for any recipient. Combined with `blame_internal`, which declares the sender faulty whenever a presented message fails to decrypt to a canonical, valid share, a malicious participant can take a ciphertext S addressed to a different participant (the coordinator publishes all `DkgShare` ciphertexts) and submit it as their own share, causing the blame protocol to condemn an honest sender.

### Finding Description
`encrypt` in `crypto/dkg/pedpop/src/encryption.rs` derives the ChaCha20 stream key from `cipher(context, ecdh(key, to))` and signs a PoP via `pop_challenge(context, nonce, key, from, msg)`. The transcript includes the context, the ephemeral public key, the *sender* index (`from`), and the ciphertext — but never the recipient's participant index or the recipient's registered encryption key (`to`). [1](#0-0) [2](#0-1) 

`Decryption::decrypt_with_proof` and `Encryption::decrypt` verify that PoP with the caller-supplied `from`, then decrypt with the local `enc_key` (or the accuser's revealed `proof.key` checked against `enc_keys[decryptor]`). There is no check that the message was ever intended for `decryptor`. [3](#0-2) [4](#0-3) 

In `KeyMachine::calculate_share`, a share that decrypts to a non-canonical or commitment-inconsistent scalar produces `PedPoPError::InvalidShare { participant: l, blame: ... }`. `BlameMachine::blame_internal` then re-decrypts the presented message and, on `InvalidSignature`/non-canonical/verification failure, returns the *sender* as faulty — with no way to distinguish "S sent garbage to me" from "this is a ciphertext S produced for a different participant." [5](#0-4) [6](#0-5) 

The ciphertexts are not confidential to the attacker: the coordinator persists every `DkgShare` from every sender to every participant on-chain via `DkgShare::set(self.txn, genesis, from, to, share)`, so any participant can retrieve the S→A ciphertext and present it as S→B. [7](#0-6) 

### Impact Explanation
A single malicious DKG participant B can obtain sender S's encrypted share intended for participant A (publicly committed share bytes), submit it in their `shares` map under `S`, and let `calculate_share` produce `InvalidShare`. B then generates a blame proof with their own `enc_key` — which is valid, since `decrypt_with_proof` only checks the DLEq against `enc_keys[B]` — and `blame_internal` decrypts the S→A ciphertext with B's key, gets non-canonical bytes, and returns `S` as the faulty party. This is an incorrect blame verdict against an honest participant, reachable by an unprivileged protocol participant using only public inputs, and it stems from a missing identity/scope check (the recipient is never bound to the message) — the same class as the reference advisory where a tool failed to enforce which session's state a caller may access. Note the attacker cannot learn the share contents (no key/share recovery), so the concrete impact is honest-party false blame and forced protocol abort/removal rather than secret leakage.

### Likelihood Explanation
The attack requires only one malicious participant and read access to another recipient's ciphertext, which the coordinator makes trivially available by storing all shares on-chain. No collusion, threshold control, or key compromise is needed. It does require the attacker to participate in the DKG and trigger a blame resolution, and the payoff is limited to misattributed blame/abort rather than theft, which tempers the severity to Medium.

### Recommendation
Bind the recipient into the encryption domain. In `encrypt`, include the recipient's participant index and/or registered `enc_key` in `pop_challenge` (e.g., `transcript.append_message(b"recipient", to_index.to_bytes())` and/or `append_message(b"recipient_key", enc_pub_key.to_bytes())`), and include the same in the `cipher` transcript. Then have `decrypt`/`decrypt_with_proof`/`blame_internal` reconstruct the challenge with the asserted recipient so a ciphertext produced for A fails PoP verification when presented as B's share — classifying the presenter, not the original sender, as faulty.

### Proof of Concept
1. Participants run PedPoP; honest sender S encrypts shares `s_A`, `s_B` to A and B via `Encryption::encrypt(rng, A/B, share)`, producing `EncryptedMessage` values `m_A`, `m_B`. `m_A`'s PoP covers `(context, R, key, from=S, msg)` only — no recipient field (crypto/dkg/pedpop/src/encryption.rs:135-167, 302-324).
2. Malicious B reads `m_A` from the publicly committed `DkgShare{S,A}` record (coordinator/src/tributary/handle.rs:352-362) and calls `machine.calculate_share(rng, shares)` with `shares[S] = m_A` instead of `m_B`.
3. `Encryption::decrypt` verifies `m_A`'s PoP against `from=S` — it passes, since the PoP never names a recipient — then XORs with `cipher(context, ecdh(enc_key_B, m_A.key))` producing garbage; `from_repr` fails and `calculate_share` returns `InvalidShare { participant: S, blame: Some(proof_B) }` (crypto/dkg/pedpop/src/lib.rs:476-499).
4. B calls `blame(sender=S, recipient=B, msg=m_A, proof=proof_B)`. `decrypt_with_proof` verifies the PoP (passes), verifies `proof_B.dleq` against `enc_keys[B]` (B legitimately knows `enc_key_B`, so it passes), decrypts to garbage, and `blame_internal` returns `S` — condemning the honest sender (crypto/dkg/pedpop/src/lib.rs:575-608; encryption.rs:366-397).

```rust
fn encrypt<R: RngCore + CryptoRng, C: Ciphersuite, E: Encryptable>(
  rng: &mut R,
  context: [u8; 32],
  from: Participant,
  to: C::G,
  mut msg: Zeroizing<E>,
) -> EncryptedMessage<C, E> {
  /*
  The following code could be used to replace the requirement on an RNG here.
  It's just currently not an issue to require taking in an RNG here.
  let last = self.last_enc_key.to_bytes();
  self.last_enc_key = C::hash_to_F(b"encryption_base", last.as_ref());
  let key = C::hash_to_F(b"encryption_key", last.as_ref());
  last.as_mut().zeroize();
  */

  // Generate a new key for this message, satisfying cipher's requirement of distinct keys per
  // message, and enabling revealing this message without revealing any others
  let key = Zeroizing::new(C::random_nonzero_F(rng));
  cipher::<C>(context, &ecdh::<C>(&key, to)).apply_keystream(msg.as_mut().as_mut());

  let pub_key = C::generator() * key.deref();
  let nonce = Zeroizing::new(C::random_nonzero_F(rng));
  let pub_nonce = C::generator() * nonce.deref();
  EncryptedMessage {
    key: pub_key,
    pop: SchnorrSignature::sign(
      &key,
      nonce,
      pop_challenge::<C>(context, pub_nonce, pub_key, from, msg.deref().as_ref()),
    ),
    msg,
  }
```

```rust
fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
```

```rust
  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }
```

```rust
  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
```
