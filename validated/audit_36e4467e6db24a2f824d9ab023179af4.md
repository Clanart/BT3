### Title
Stale per-order fee escrow accounting lets `feeToken` migrations pay order fees in the wrong token, draining other orders' escrow - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase` records escrowed order fees as a **bare numeric amount** keyed only by commitment (`_orders[commitment][TRANSACTION_FEES]`), with no record of *which* ERC-20 token that amount was actually collected in. At payout time the contract re-resolves the fee token dynamically from the host (`IDispatcher(host()).feeToken()`). Because `EvmHost.feeToken` is an intentionally configurable governance parameter (`HostParams.feeToken`, "we allow it to be configurable to prevent future regrets" - `evm/src/core/EvmHost.sol:42-44`), any fee-token change that occurs between `placeOrder` and order settlement causes the escrowed fee amount recorded for an *old* token to be paid out of the *new* token's balance — a fund-accounting break structurally identical to the original report's core flaw: a legitimate address-changing admin function decoupling "amount owed" bookkeeping from the token that actually backs it, letting value be extracted without matching input.

### Finding Description
- At order placement, `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:345-362`) reads the *current* fee token, pulls `order.fees` of that token from the user, and stores only the numeric amount:
```145:evm/src/apps/IntentGatewayV2.sol
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    ...
    IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```
- At settlement (`IntentsBase._withdraw`, `evm/src/apps/intentsv2/IntentsBase.sol:412-417`), the fee token is re-resolved **dynamically** and the same numeric amount is paid out of it, without any indication that this is the token the fee was originally escrowed in:
```412:417:evm/src/apps/intentsv2/IntentsBase.sol
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
```
- `EvmHost.updateHostParams` only guards against changing `feeToken` while the **Host contract itself** holds a nonzero balance (`evm/src/core/EvmHost.sol:617-621`); it has no visibility into balances held by downstream apps like `IntentGatewayV2`/`IntentsBase`. So the fee-token switch can be performed while the gateway still holds outstanding escrowed fees denominated in the old token, and while other, unrelated orders' escrow accumulates the new token.
- After such a switch, every pending order's `TRANSACTION_FEES` slot silently repricing into the new token: solvers/beneficiaries settling those orders receive `fees` (a quantity denominated in the old token) transferred out of the gateway's balance of the **new** token — a balance that was funded by entirely different users' orders, not by this order's escrow.

### Impact Explanation
This breaks the "bridged assets, order escrow ... must move exactly once and only to the rightful beneficiary and amount" invariant. The numeric fee amount recorded for one token silently becomes a claim on a different token's pool, causing:
- Wrong-token / wrong-amount payouts to solvers/beneficiaries.
- Fund loss for the protocol/other order owners whose escrowed new-feeToken balance backs payouts they never authorized.
- No token identity check exists anywhere in the withdraw path (`_withdraw`) to detect or prevent this drift — the mismatch is silent and reverts only if the gateway lacks sufficient balance of the resolved token (`safeTransfer` would revert), otherwise it succeeds and misallocates funds.

### Likelihood Explanation
`feeToken` is explicitly documented as configurable "to prevent future regrets" (`evm/src/core/EvmHost.sol:42-44`), meaning fee-token migrations (e.g., DAI → USDC) are an expected, normal, non-malicious governance operation over the protocol's lifetime — not a compromised-admin scenario. Any order placed before such a migration and settled after it will trigger the mismatch automatically, with no attacker action required beyond normal order placement/fill flow. Given intents/order flow is high-volume and governance parameter updates are a supported, intended feature, the window for pending orders to straddle a fee-token change is realistic.

### Recommendation
Store the fee token address alongside the fee amount at escrow time (e.g., `mapping(bytes32 => mapping(address => uint256)) _orders` already keys by token — simply escrow fees under the actual `feeToken` address used at placement rather than the synthetic `TRANSACTION_FEES` key, or store `(token, amount)` pairs explicitly for fees). At withdrawal, pay out the token that was actually escrowed for that specific order rather than re-resolving `host().feeToken()` dynamically. Additionally, mirror the `CannotChangeFeeToken` style guard in `EvmHost` at the app level (or block fee-token migrations from proceeding while downstream apps report outstanding balances) so governance changes cannot silently break app-level escrow invariants.

### Proof of Concept
1. User A places an order via `IntentGatewayV2.placeOrder` with `order.fees = 100`, while `EvmHost.feeToken == DAI`. `100` DAI is pulled from User A and `_orders[commitmentA][TRANSACTION_FEES] = 100` is recorded (no token identity stored).
2. Governance later calls `EvmHost.updateHostParams` with `params.feeToken = USDC` (legitimate operation; guard only checks the Host's own DAI balance, not the gateway's).
3. Meanwhile, User B places another order, whose `100` in fees is now escrowed in USDC and transferred to the gateway.
4. Order A settles (`_withdraw` finalize path): `fees = _orders[commitmentA][TRANSACTION_FEES] = 100`; the code calls `IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, 100)`, which now resolves to **USDC**, not the DAI that was actually escrowed for order A. The beneficiary of order A receives 100 USDC drawn from User B's escrowed fee balance, while the 100 DAI originally escrowed for order A remains stuck in the gateway, unaccounted for.
