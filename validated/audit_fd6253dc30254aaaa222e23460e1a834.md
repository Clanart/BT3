### Title
Tokenfactory Denom Allow-List Enforcement Bypass via MsgMultiSend / Direct SendCoins Callers - (File: sei-cosmos/x/bank/keeper/send.go)

### Summary
The tokenfactory "restricted denom" access-control gate (`IsInDenomAllowList`) is enforced only inside the bank module's `MsgServer.Send` handler, not inside the underlying primitives (`SendCoins`, `InputOutputCoins`) that back every other transfer path. Any transaction plane that reaches these primitives directly — `MsgMultiSend`, CosmWasm contract-initiated bank sends, and (in legacy precompile versions) the EVM bank precompile — moves tokens of an allow-list-restricted tokenfactory denom without the allow-list check ever running, exactly mirroring the Capgo bug class where an enforcement flag is honored on one access plane (the authenticated API endpoint) but silently skipped on an alternate plane (the PostgREST/RLS layer) reaching the same protected resource.

### Finding Description
`BaseSendKeeper.IsInDenomAllowList` is the sole gate that restricts transfers of a tokenfactory denom to addresses on its `DenomAllowList`: [1](#0-0) 

This check is invoked exactly once, inside the bank module's message-server `Send` handler: [2](#0-1) 

However, the lower-level primitives that actually move balances — `SendCoins` and `InputOutputCoins` (the function backing `MsgMultiSend`) — do not call `IsInDenomAllowList` at all: [3](#0-2) 

Because `SendKeeper` exposes `SendCoins`/`InputOutputCoins` as generic, unguarded primitives (see interface definition), every other caller of these functions inherits the same bypass: [4](#0-3) 

Concretely reachable bypass surfaces include:
- **`MsgMultiSend`**, which is dispatched to `InputOutputCoins` and, unlike `MsgSend`, has no equivalent allow-list guard shown in the message server for `Send`. Any unprivileged tx sender can submit a `MsgMultiSend` moving a restricted tokenfactory denom to/from an address that is *not* on the denom's allow list.
- **CosmWasm contracts**, which route `BankMsg::Send`/`BankMsg::MultiSend` execution through the wasm bank plugin down to the same `SendCoins`/`InputOutputCoins` primitives rather than through `bank.MsgServer.Send`.
- **Legacy EVM bank-precompile versions**, which call `p.bankKeeper.SendCoins` directly instead of routing through `bankMsgServer.Send` — the same pattern the current precompile fixed by switching to `p.bankMsgServer.Send`: [5](#0-4) 
versus the corrected current implementation: [6](#0-5) 

The presence of a dedicated corrected `Send` implementation in the current precompile (routing through `bankMsgServer.Send` to pick up `IsInDenomAllowList`) confirms that the direct-`SendCoins` pattern used in `MsgMultiSend`/wasm/legacy-precompile paths is the same class of oversight: the enforcement point lives in one specific handler, and any other path into the shared low-level primitive silently skips it.

### Impact Explanation
Tokenfactory denom allow lists exist to restrict who may hold/transfer a given asset (e.g., compliance-gated or permissioned tokens). Bypassing this via `MsgMultiSend` or CosmWasm-initiated sends lets any address move a restricted denom to or from an address that was never authorized, defeating the module's access-control guarantee and enabling unauthorized transfer of the restricted asset — a fund-control/authorization violation on bank/tokenfactory-managed assets.

### Likelihood Explanation
`MsgMultiSend` is a standard, always-enabled bank message reachable by any unprivileged transaction sender with no special permission; CosmWasm `BankMsg` execution is reachable by any wasm contract user. No governance, validator, or operator privilege is required — only a restricted tokenfactory denom with an active allow list needs to exist, which any tokenfactory denom creator can set up permissionlessly.

### Recommendation
Move the `IsInDenomAllowList` check down into the shared primitives (`SendCoins`/`InputOutputCoins`) rather than only in `MsgServer.Send`, or explicitly re-apply the same check in `MsgMultiSend`'s handler, the wasm bank plugin's send path, and any remaining code path (legacy precompiles included) that calls `SendCoins`/`InputOutputCoins` directly, so the allow-list gate is enforced uniformly regardless of entry point.

### Proof of Concept
1. Create a tokenfactory denom `factory/{creator}/restricted` and set a `DenomAllowList` containing only `addrA`.
2. As `addrB` (not on the allow list) holding some `restricted` balance (obtained before the allow list was set, or minted directly by the admin), submit a `MsgMultiSend` (not `MsgSend`) transferring `restricted` tokens to `addrC` (also not on the allow list).
3. Observe the transfer succeeds because `InputOutputCoins`/`SendCoins` never calls `IsInDenomAllowList`, whereas the same transfer attempted via `MsgSend` would be rejected with `ErrUnauthorized`. [7](#0-6)

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}
