## Analysis

The external report's core issue is: **an unbounded loop of external calls to an untrusted/attacker-controlled address that must all succeed, with no way to skip or recover a permanently-failing entry**, causing a fund-management path to brick.

The local analog is in `IntentsBase.sol`'s `_withdraw()`, used by the cross-chain intent-settlement flow (`ExtrinsicIntents.sol`).

### Corrupted value / broken invariant
`WithdrawalRequest.beneficiary` is derived from `msg.sender` at fill time on the **destination chain** — i.e., it is set by whichever unprivileged solver calls `fillOrder`: [1](#0-0) 

That value is carried, unauthenticated with respect to "is this a safe receiver," across Hyperbridge in a `RedeemEscrow` post request. On the source chain, `onAccept` → `_withdraw()` loops over every escrowed token for the commitment and unconditionally does a raw `call{value: amount}("")` (for native token) or `safeTransfer` (for ERC20) to that same `beneficiary`, reverting the *entire* function if any single transfer fails: [2](#0-1) 

The host retries a failed `onAccept` indefinitely by deleting the request receipt on failure rather than reverting the whole batch: [3](#0-2) 

### Why existing guards don't stop this
- `_authenticate()` only checks that the request came from the registered gateway instance on the source chain — it says nothing about whether `beneficiary` is a safe receiving address.
- There is no `isContract`/receive-capability check on `beneficiary` before the transfer loop, unlike `CallDispatcher.dispatch()` which does check `extcodesize` before calling arbitrary targets.
- `_filled[body.commitment] = beneficiary` is written *before* the token loop, but since a failed transfer reverts the whole `onAccept` call, this write (and everything else) rolls back — so the order commitment is never finalized on the source chain and the escrow can never be swept by any other path.
- Because the order was already marked filled on the *destination* chain (`_filled[commitment] = msg.sender` in `_fillCrossChain`), the source-chain cancellation path (`cancelOrder` querying destination `_filled` via GET) will see a non-empty slot and revert with `Filled()`, so the user cannot recover via cancellation either.

### Attack primitive
An unprivileged "solver" can:
1. Deploy a contract that reverts on receiving ETH (or is blocklisted for a specific ERC20 used as the order's input, e.g. USDC).
2. Call `fillOrder` on the destination chain for a victim's cross-chain order whose input assets include native ETH (or the blocklist-capable token), setting `msg.sender` (their reverting contract, via a proxy/relay) as the effective beneficiary.
3. The solver correctly delivers output tokens to the user on the destination chain (so the fill itself succeeds and looks legitimate), then dispatches `RedeemEscrow` back to the source chain.
4. On the source chain, `onAccept` → `_withdraw()` permanently reverts on the native transfer to the solver's reverting contract, and retries forever fail identically.

Result: the user's escrowed input tokens are permanently locked on the source chain (no cancellation possible, no retry path succeeds), and the solver forfeits their own reimbursement — a griefing/fund-lock vector reachable by any unprivileged actor, matching the report's "uncontrolled address in an iterated fund-release loop bricks the release path" pattern.

### Title
Solver-Controlled Beneficiary Enables Permanent Escrow Lock in `_withdraw()` — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw()` releases escrowed order funds to a `beneficiary` address that originates from `msg.sender` at fill time on the destination chain and is propagated unauthenticated (with respect to receive-safety) through a `RedeemEscrow`/`RefundEscrow` cross-chain message. Since the transfer loop reverts entirely on any single failed transfer, and the underlying ISMP host retries the failed callback indefinitely rather than working around it, a solver who fills an order using a receive-reverting contract as their address permanently locks the order's escrowed tokens with no recovery path.

### Finding Description
`_fillCrossChain` sets `beneficiary: bytes32(uint256(uint160(msg.sender)))` in the outgoing `WithdrawalRequest` [4](#0-3) . On the source chain this value drives every ERC20/native transfer in `_withdraw()`'s loop [5](#0-4) , with no validation that the target can actually receive funds. `EvmHost.dispatchIncoming` treats a reverting `onAccept` as retryable rather than permanently failed [6](#0-5) , so the failure recurs on every relayer retry attempt with no way to change the beneficiary or force partial release.

### Impact Explanation
This breaks the invariant that "bridged assets... must move exactly once and only to the rightful beneficiary and amount" — here they move to *no one*, permanently, i.e. loss/lock of user funds triggered by an unprivileged solver's choice of receiving contract. Because the destination-chain fill already succeeded (user got output tokens), the source-chain cancellation path is also blocked (`Filled()` revert), leaving no recovery mechanism.

### Likelihood Explanation
Any address can act as a solver and call `fillOrder`; deploying a contract that reverts on `receive()` (or is blocklisted for a stablecoin) is trivial. No malicious relayer, prover, or governance actor is required — this is a pure unprivileged-actor griefing/fund-lock vector on orders using native ETH or blocklist-capable tokens as input.

### Recommendation
Do not let the release path revert atomically on a single failed transfer. Use a pull-based withdrawal pattern (credit `beneficiary` an internal balance and let them `claim()` separately) or wrap each transfer in a try/catch that, on failure, escrows the amount to a recoverable holding balance for that beneficiary rather than reverting the whole `_withdraw()` call and blocking `_filled` finalization.

### Proof of Concept
1. Attacker deploys `RevertingReceiver` with no `receive()`/`fallback()` (or one that always reverts).
2. User places a cross-chain order with native ETH as input asset (`order.inputs[0].token == address(0)`), destination chain B, source chain A.
3. Attacker (as solver) calls `fillOrder` on chain B directly from `RevertingReceiver` (or a proxy contract that forwards as itself), correctly supplying output tokens to the user's beneficiary — the fill succeeds and `RedeemEscrow` is dispatched to chain A with `beneficiary = RevertingReceiver`.
4. On chain A, `onAccept` decodes the request and calls `_withdraw()`; the `beneficiary.call{value: amount}("")` fails, `InsufficientNativeToken()` reverts the whole call.
5. `EvmHost.dispatchIncoming` deletes the request receipt, allowing indefinite relayer retries — all of which fail identically. The escrowed ETH for this order is permanently stuck in the gateway contract, and `cancelOrder` on chain A cannot succeed because chain B's `_filled[commitment]` is already non-empty.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
