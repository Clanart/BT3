## Finding: `CallDispatcher.dispatch()` Has No Access Control — Anyone Can Drain Funds Held By The Shared Dispatcher

### Title
Unrestricted `CallDispatcher.dispatch()` allows any caller to move funds held by the dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The external report's core broken invariant is: a function that is *documented/intended* to be restricted to a specific privileged caller path has **no on-chain check at all**, letting an arbitrary caller invoke value-moving logic. The direct Hyperbridge analog is `CallDispatcher.dispatch()`, which executes arbitrary `Call[]` (including `value`-bearing calls) against arbitrary targets with **zero caller restriction**, even though the whole design intent of the contract (per `IntentsBase._execute`) is that only the intent-gateway's internal accounting logic should ever trigger transfers out of the dispatcher's balance.

### Finding Description
`CallDispatcher` is a shared, address-invariant utility contract used by `IntentGatewayV2`/`IntentsBase` to execute untrusted order calldata (`predispatch`/`postdispatch`), as documented in `docs/content/developers/evm/intent-gateway/overview.mdx:83-110`. The intended flow is:

1. `IntentsBase._execute` (`evm/src/apps/intentsv2/IntentsBase.sol:438-484`) transfers order output assets to the dispatcher, then calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`.
2. After execution, it queries the dispatcher's remaining balances for each token in `order.output.assets` and issues a second `dispatch()` call to sweep them back to the gateway as "dust."

`CallDispatcher.dispatch()` itself is: [1](#0-0) 

There is no `onlyGateway`/`restrict` modifier, no `msg.sender` check, and the contract even has an unrestricted `receive() external payable` (`evm/src/utils/CallDispatcher.sol:36-39`), meaning it can accumulate native token balance from anyone. Because the same `CallDispatcher` instance is shared across all orders for a gateway deployment (`_params.dispatcher`, `evm/src/apps/intentsv2/IntentsBase.sol:441`), and the sweep in `_execute` only accounts for tokens explicitly listed in `order.output.assets` (`evm/src/apps/intentsv2/IntentsBase.sol:447-473`), any value that ends up in the dispatcher outside that enumerated set — leftover ETH from a partial swap, a token not in `order.output.assets` produced by the executed calldata, or ETH sent directly via `receive()` — is never swept and sits as a spendable balance that **any unrelated address** can immediately withdraw by calling `dispatch()` directly with a `Call[]` targeting themselves.

This mirrors the `FCFSMint()` pattern exactly: the contract assumes callers only reach the fund-moving function through a controlled path (the gateway's internal accounting), but enforces that assumption nowhere in code.

### Impact Explanation
Any residual balance in `CallDispatcher` — native or ERC-20 — is unconditionally drainable by an unprivileged, unauthenticated caller, since `dispatch()` performs `to.call{value: call.value}(call.data)` for attacker-supplied `to`/`value`/`data` with no ownership or origin check. This is a direct "stealing or loss of funds" / "unauthorized execution" primitive per the bounty's impact gate: no malicious relayer, prover, or governance actor is required — a plain EOA calling the public `dispatch()` function suffices.

### Likelihood Explanation
Likelihood is contingent on the dispatcher actually holding a non-zero balance outside the swept `order.output.assets` set (e.g. dust from swaps, un-enumerated output tokens, or accidental ETH transfers via the payable `receive()`), which is a realistic and recurring operational condition for a "swap-then-escrow"/"fill-then-act" calldata execution pattern that explicitly anticipates leftover "dust." The docs (`docs/content/developers/evm/intent-gateway/overview.mdx:99-110`) confirm dust accumulation is expected/normal, and each occurrence is a race any bot can win since no privileged relationship gates the withdrawal call.

### Recommendation
Add a caller restriction to `CallDispatcher.dispatch()` (e.g., an immutable/authorized-caller allowlist set at construction, or make `CallDispatcher` non-shared/one-shot per invocation), so only the intent gateway (or other authorized `IDispatcher`/`IApp` contracts) can trigger fund movement out of the dispatcher. Alternatively, refactor `_execute` to avoid leaving any residual balance addressable by a second, separately-callable `dispatch()` invocation — e.g., perform the calldata execution and full balance sweep atomically inside a single privileged call that cannot be invoked externally.

### Proof of Concept
1. Any transaction (a normal order fill, a misconfigured `order.output.call`, or a stray `receive()` ETH transfer) leaves ETH or an ERC-20 token balance in the `CallDispatcher` contract that is not part of the current order's `order.output.assets` enumeration (so `_execute`'s sweep loop never queries/moves it).
2. An attacker observes the nonzero balance on `CallDispatcher` (a single well-known, shared, address).
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: <balance>, data: ""})]))` directly — no `msg.sender` check exists in `dispatch()` (`evm/src/utils/CallDispatcher.sol:44-62`), so the call succeeds and transfers the funds to the attacker.
4. Loss is realized: any protocol integrator or user whose assets transiently pass through the shared dispatcher outside the exact `order.output.assets` set can have those funds unilaterally withdrawn by an unrelated third party.

**Uncertainty note:** I was not able to fully verify from the indexed code whether, in current production configuration, residual/dust balances routinely persist in `CallDispatcher` between transactions (this depends on runtime behavior of arbitrary `order.output.call` calldata, which is not statically bounded). The vulnerable code path (unrestricted `dispatch()`) is confirmed directly in the repository; the exact frequency/conditions under which exploitable dust accumulates could not be fully confirmed without deeper on-chain/integration testing, which a Devin session with repo execution access could verify.

     * @dev Receive function to accept ETH transfers

    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
