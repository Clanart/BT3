### Title
Spoofable `WWW-Authenticate: realm="GitHub"` header lets a malicious remote trigger an Enterprise sign-in flow bound to an attacker-controlled endpoint - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
`getEndpointKind()` in the Git credential-helper trampoline classifies a remote host as a "GitHub" endpoint by trusting an unauthenticated `WWW-Authenticate` header value that Git forwards from the remote server, instead of always performing the authoritative network check (`isGitHubHost`). Like the `_depositAndSwap()` case where the "safe" 5-parameter overload was skipped in favor of a cheaper path that didn't account for a required value, this code takes a "happy-path" shortcut that skips verification, letting attacker-controlled server responses steer Desktop into a security-sensitive flow (prompting the user to sign in to what looks like a legitimate GitHub Enterprise host).

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential helper, which calls `getCredential()` → `getEndpointKind()`: [1](#0-0) 

The function first tries authoritative checks (`isGist`, `isDotCom`, `isGHE`), then falls back to inspecting `wwwauth[...]` entries in the credential map — values that originate from the `WWW-Authenticate` HTTP response header sent by the remote git server (or any proxy/MITM sitting in front of it) — and trusts a `realm="GitHub"` string to classify the endpoint as `'enterprise'` without ever contacting the host: [2](#0-1) 

Only when none of the `wwwauth` headers match does the code fall back to the real verification via `isGitHubHost(endpoint)`: [3](#0-2) 

Because Git faithfully forwards whatever `WWW-Authenticate` header the server (or a proxy standing in for it) returns, an attacker who controls the remote/proxy for a repository the victim clones or fetches from can respond with `WWW-Authenticate: realm="GitHub"` on a 401, causing `getEndpointKind` to short-circuit to `'enterprise'` for a completely unrelated origin.

That classification then feeds directly into `getCredential()`: [4](#0-3) 

Since no stored account matches the spoofed `apiEndpoint`, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which starts the real Enterprise sign-in flow bound to the attacker's origin: [5](#0-4) 

`promptForGitHubSignIn` calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the attacker-controlled `origin`, then shows the standard `PopupType.SignIn` dialog with `isCredentialHelperSignIn: true` and `credentialHelperUrl: endpoint` set to that same untrusted origin. From the user's perspective this is indistinguishable from a legitimate "Sign in to your GitHub Enterprise instance" prompt raised in the middle of an ordinary `git fetch`/`clone`/`push` operation.

### Impact Explanation
This breaks the invariant that Desktop only initiates authenticated sign-in/OAuth flows against endpoints it has verified to actually be GitHub (via `isGitHubHost`, `isDotCom`, `isGHE`, or a stored account). By trusting an attacker-suppliable header as a "happy path," a malicious or compromised git server/proxy can cause Desktop to bind the Enterprise sign-in flow (and any subsequent OAuth/PAT submission) to an attacker-controlled host. If the user completes the resulting sign-in prompt, their PAT or OAuth token is sent to the attacker's endpoint — a credential/token exfiltration and unauthorized-account-binding outcome, without the user doing anything more unusual than fetching/cloning from a repository under the attacker's control (satisfying the "attacker controls a git remote/proxy response" criterion).

### Likelihood Explanation
The trigger requires only that the victim perform a normal HTTPS git operation against a repository whose server or transparent proxy is attacker-controlled or compromised, and that the server return a 401 with a crafted `WWW-Authenticate` header — no unusual user interaction, elevated privileges, or pre-existing compromise of the host is needed. The `wwwauth[]` shortcut exists specifically to *avoid* the authoritative `isGitHubHost` check, so the spoofed classification is reachable on the first credential request for any unknown host.

### Recommendation
Do not trust the `WWW-Authenticate` realm value alone to classify a host as GitHub/Enterprise for the purposes of initiating a sign-in/credential flow. Either drop the `wwwauth` shortcut entirely and always fall back to the authoritative `isGitHubHost(endpoint)` network check before prompting for Enterprise sign-in, or require an additional authenticated signal (e.g., a valid `X-GitHub-Request-Id`/API metadata response) before trusting a host as GitHub-flavored, mirroring how the report's fix ensured the "safer" code path (the one that performs real verification) is always used rather than the cheaper shortcut.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a MITM proxy in front of any git remote) that, on an unauthenticated request, responds with `401` and header `WWW-Authenticate: realm="GitHub"`.
2. Victim adds this remote in GitHub Desktop (e.g., clones `https://evil.example.com/repo.git`) and performs a fetch.
3. Git invokes Desktop's trampoline credential helper with the `wwwauth[]=realm="GitHub"` field populated from the attacker's header.
4. `getEndpointKind()` returns `'enterprise'` for `evil.example.com` without any real verification.
5. Since no account exists for that host, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com')`, which pops the standard "Sign in to GitHub Enterprise" dialog bound to `evil.example.com`.
6. If the victim enters credentials/PAT or completes OAuth, the resulting token is submitted to the attacker's origin.

Note: I was not able to fully trace the downstream `SignInStore`/`Dispatcher.beginEnterpriseSignIn` implementation (`app/src/lib/stores/sign-in-store.ts`, `app/src/ui/dispatcher/dispatcher.ts`) in this pass to confirm whether any additional endpoint-verification step exists later in that flow before an OAuth/PAT submission is actually sent; this would be worth confirming with a full read of those files before treating the PoC as fully end-to-end verified.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
