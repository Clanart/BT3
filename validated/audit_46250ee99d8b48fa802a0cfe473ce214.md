### Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL from untrusted GitHub API data - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop periodically refreshes the cached `GitHubRepository` metadata for a repository by calling the GitHub API and, if the API's `clone_url` differs from the current local remote, silently rewrites the local `origin` remote URL via `git remote set-url`. This happens with no user prompt, confirmation dialog, or visible log entry in the app UI — the exact "critical parameter changed with no event/notification" pattern described in the seed report, translated to Desktop's trust model where the GitHub API response is the attacker-influenced input.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  takes an `IAPIRepository` object fetched from the GitHub/GHES API and compares its `clone_url` to the repository's current `origin` remote. If the protocol matches and the previously-cached clone URL still matches the current remote (i.e., the user hasn't manually customized it), the function calls `gitStore.setRemoteURL(...)`, which shells out to `git remote set-url` unconditionally: [2](#0-1) .

`setRemoteURL` at the `GitStore` layer performs the change and only emits an internal React store update (`emitUpdate`) — there is no toast, banner, dialog, or persistent log entry surfaced to the user: [3](#0-2) .

This is invoked from `repositoryWithRefreshedGitHubRepository`, which fetches the repository object from the API (`api.fetchRepository(owner, name)`) and, whenever a `gitHubRepository` association already exists, calls `updateRemoteUrl` before the fetched data is otherwise used: [4](#0-3) .

The guard logic in `updateRemoteUrl` only checks that:
1. The URL *protocol* is unchanged (http vs ssh), and
2. The previously cached GitHub `cloneURL` still matches the current git remote (i.e. no manual edit was made).

Neither check validates the *hostname* or *owner/name* of the new `clone_url` against anything trusted — an API response can freely change the target host, owner, or repo name of `origin` as long as the protocol string matches, and the rewrite happens automatically and silently. Compare this to the explicit, user-initiated path for changing a remote URL through Repository Settings, which at least requires manual user action and goes through the same silent `setRemoteURL` (no event either), shown here: [5](#0-4) .

The `IAPIRepository`/`IAPIFullRepository` object is produced by `API.fromAccount(account).fetchRepository(owner, name)` — for accounts pointed at a GitHub Enterprise Server, this endpoint is fully controlled by whatever server the user has configured, and for GitHub.com it is subject to any response-integrity failure (e.g., a malicious/compromised proxy or MITM on that connection). In either case, the report's "attacker controls a GitHub API object" primitive directly applies.

### Impact Explanation
An attacker who controls the API endpoint/response for a matched `GitHubRepository` (self-hosted GHES account under attacker control, or MITM of an API response) can set `clone_url` to an attacker-chosen host with the same protocol. Desktop will then silently retarget the user's `origin` remote to that host with no user awareness. The next time the user pushes, their source code — potentially private/proprietary — is sent to the attacker's server instead of the legitimate GitHub remote, and subsequent fetches/pulls could feed attacker-controlled history/objects into the user's working repository. Because there is no event, log, banner, or diff surfaced anywhere, the corruption is silent: the user believes they are still pushing to/pulling from origin as configured, and there is no on-screen artifact prompting them to notice the change (mirroring the seed report's "users lose funds/confidence... no events are emitted").

### Likelihood Explanation
This path fires automatically as part of routine GitHub-repository metadata refresh (`repositoryWithRefreshedGitHubRepository`), not on a rare or user-initiated action, so it triggers passively whenever Desktop refreshes repository info for an account whose API endpoint is attacker-influenced. The only preconditions are (a) the repository has an associated `GitHubRepository`/account, and (b) the user has not manually diverged the remote from the last-known API clone URL — both are the common, default case for most Desktop users using GitHub.com or a GHES account. No local access, malware, or leaked credentials are required — only an attacker-influenced API response.

### Recommendation
- Do not silently auto-rewrite `origin` (or any remote) based on API data; at minimum, prompt the user with a visible confirmation dialog showing old vs. new remote URL before applying the change.
- Emit a durable, visible record (banner/notification/log entry) whenever `setRemoteURL` changes a remote as a side effect of a background operation, distinguishing it from explicit user edits in Repository Settings.
- Additionally validate that the new `clone_url`'s hostname is consistent with the account's configured endpoint (not just that the protocol string matches), rejecting silent host changes even if attacker-controlled API data claims otherwise.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointing to `https://ghes.attacker.example` (an account the attacker fully controls, satisfying "attacker controls a GitHub API object").
2. Clone/add a repository whose `origin` is `https://ghes.attacker.example/owner/repo.git`, so Desktop associates it with a `GitHubRepository` on that endpoint.
3. On a subsequent background refresh, have the attacker's server return `fetchRepository` responses whose `clone_url` is `https://ghes.attacker.example/owner/renamed-target.git` (or any other repo/path on the same host/protocol).
4. Observe `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` → `gitStore.setRemoteURL` silently rewrite `origin` via `git remote set-url` with no dialog, banner, or log visible to the user [6](#0-5) [7](#0-6) .
5. The next `git push`/`git fetch` from Desktop's UI silently targets the new URL instead of what the user configured, with no on-screen indication the remote changed.
