### Title
Copilot conflict resolution writes stale AI-generated content over live edits, silently corrupting merge results - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions()` writes Copilot's AI-generated conflict resolutions to disk using file content that was captured *before* the (up to 10‑minute) Copilot turn started. The only staleness guard checks whether the file has become **fully resolved** on disk; it does nothing to detect that the user **edited** the still-conflicted file while Copilot was thinking. As a result, a user's manual edits to a conflicted file made during conflict resolution can be silently overwritten and staged, exactly mirroring the reported bug class: a value computed from a stale snapshot is applied without accounting for an intervening state transition, penalizing/undermining the party that should have been protected.

### Finding Description
The Copilot conflict-resolution flow works like this:
1. `buildConflictContext()` reads every conflicted file's content into `rawContent` up front [1](#0-0) .
2. That `rawContent` is later combined with the model's per-hunk output in `reassembleResolutions()` to produce the full `resolvedContent` for each file [2](#0-1) .
3. The turn itself can run for a long time — the timeout defaults to 600 seconds — during which the conflicts dialog can be dismissed to a banner and the user can keep working in an external editor while resolution continues in the background [3](#0-2) [4](#0-3) .
4. When the user clicks "Continue Merge," `_applyCopilotConflictResolutions()` writes the reassembled content straight to disk for every resolution not covered by a manual override [5](#0-4) .

The only protection against a stale write is:
```
const onDiskFile = state.changesState.workingDirectory.files.find(f => f.path === resolution.path)
if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
  continue
}
``` [6](#0-5) 

This only skips the write when the file has become **fully** resolved (no remaining conflict markers). It does not re-read or diff the current on-disk content against the `rawContent` that was captured minutes earlier. If the user partially edits the conflicted file during the wait — e.g. tweaks code inside one hunk but the file git-status is still `Conflicted` because other files/markers remain — `hasUnresolvedConflicts` still returns true, the guard does not trigger, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` overwrites the user's in-progress edits with content reassembled from the stale snapshot [7](#0-6) . The overwritten path is then `git add`-ed automatically [8](#0-7) , so the user's edits never make it into the commit, with no warning that they were discarded.

This is the same broken invariant as the Solidity report: a derived value (early-exit fee / here, "resolved file content") is computed from state captured before a waiting period (timelock / Copilot turn), and the guard meant to protect the affected party during that waiting period (no-fee-after-timelock / "don't clobber if user changed the file") only covers one narrow terminal condition instead of the general case of "state changed since the value was computed."

### Impact Explanation
The corrupted value is the on-disk content of a conflicted file the user was actively resolving. The result is silent corruption of what the user stages and ultimately commits/pushes — their manual edits are dropped without any diff, prompt, or notification, and Desktop reports the operation as successful. This can reintroduce bugs the user just fixed, resurrect one side of a conflict the user rejected, or push code the user never reviewed, which is explicitly listed as a valid impact category (silent corruption of what the user commits or pushes).

### Likelihood Explanation
Medium. It requires the user to actually edit the same conflicted file while a Copilot resolution turn is in flight (a normal, encouraged workflow, since the dialog can be dismissed to a banner while resolution continues) rather than any attacker action; the longer the model turn takes (large conflicts, slow provider, retries — up to ~10 minutes with an internal retry), the wider the race window becomes. No malicious repository, credentials, or elevated access are required — only a repository whose merge/rebase produces conflicts large or numerous enough to keep Copilot busy while the user keeps working.

### Recommendation
Before writing `resolution.resolvedContent` to disk, re-check that the current on-disk content still matches the snapshot (`rawContent`) that was sent to the model, not merely that the file is still flagged as "conflicted." If the file has changed at all since the snapshot was taken, skip the write (or re-prompt the user) instead of silently overwriting it, mirroring the existing "don't clobber externally-resolved files" guard but generalized to any content drift, not just full resolution.

### Proof of Concept
1. Create a merge/rebase conflict in a repository, e.g. two files conflicting or one file with two conflict hunks.
2. Trigger "Resolve with Copilot"; this snapshots `rawContent` for each conflicted file via `buildConflictContext` at start of the turn.
3. While the Copilot turn is running (dismiss the dialog to the background banner is possible), open the still-conflicted file in an external editor and make a manual edit inside (or near) one of the hunks, without removing all conflict markers — the file status remains `Conflicted`.
4. Wait for Copilot to finish and reopen the result dialog; click "Continue Merge."
5. `_applyCopilotConflictResolutions` finds `onDiskFile.status` is `Conflicted` and `hasUnresolvedConflicts` is still true (since the user's edit didn't fully clear markers everywhere), so the staleness guard does not fire.
6. The file is overwritten with `resolution.resolvedContent` built from the pre-edit `rawContent`, silently discarding the user's manual change, and the file is staged and later committed as if the user's edit never happened.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
