## Title
Automatic remote-URL rewrite from unauthenticated GitHub API `clone_url` bypasses hostname pinning - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Vault.vy bug is about a state transition (`migrateStrategy`) that is triggered by a privileged actor but whose destination is only partially validated, letting the vault silently drift into an inconsistent state. The Desktop analog is `updateRemoteUrl`, which silently rewrites the `origin` remote's URL to whatever `clone_url` the GitHub API returns for a repository, based on a hostname/owner/name equality check performed by `urlMatchesRemote`/`parseRemote` rather than a strict, security-sensitive comparison. This function runs unattended as part of repository refresh and mutates the git remote that all future `fetch`/`push`/`pull` operations depend on, similar to how `migrateStrategy` mutates the vault's live strategy pointer without full invariant checks.

### Finding Description
`updateRemoteUrl` is invoked to reconcile a repository's `origin` remote with the GitHub API's view of the repository: [1](#0-0) 

The guard logic is:
- `protocolsMatch`: only requires that the *protocol* (`https` vs `ssh`) of the old and new URL match — it does not compare hostnames.
- `remoteUrlUnchanged`: uses `urlMatchesRemote`, which only checks that hostname/owner/repo-name match via regex parsing, not that the URL is byte-identical or from a trusted host.
- If both hold and the URL differs, it calls `gitStore.setRemoteURL(...)`, which directly executes `git remote set-url`: [2](#0-1) 

The equality check (`urlMatchesRemote`) is implemented purely via regex-based parsing of hostname/owner/name components: [3](#0-2) 

Nothing in this path re-verifies that the `apiRepo.clone_url` corresponds to a repository the user actually still trusts, or that the *GitHubRepository* record (`gitHubRepository.cloneURL`) used for the "unchanged" check is itself derived from a still-valid, non-stale API response. The GitHub API is treated as fully trusted, so this function's precondition is "the repository record we cached earlier still matches the current remote," not "the destination is safe" — exactly the kind of un-vetted migration path called out in the report: the target of the mutation is decided by external data (an API-returned `clone_url`) with only structural, not security, validation, and the vault-equivalent state (git remote configuration that governs push/fetch destinations) is changed without confirming the operation is safe end-to-end.

### Impact Explanation
If an attacker controls the GitHub-side repository object returned to Desktop for a repo the victim has already added (e.g., via a compromised/attacker-owned fork the victim tracks, a renamed/transferred repository, or a malicious GitHub Enterprise Server that speaks the same API to Desktop), they can influence `clone_url` seen by Desktop and cause the local `origin` remote to be silently rewritten to a different `owner/name` under the same host and protocol without any user prompt or confirmation dialog. Since `origin` is the primary push/fetch target, an unnoticed rewrite means the user's next `push` silently goes to a different (attacker-influenced) repository than the one they believe they're working with, and subsequent `fetch`/`pull` may pull attacker-controlled history into the working tree — directly matching the "silent corruption of what the user commits/pushes" impact category, since it happens with no UI confirmation, unlike the explicit `git remote set-url` prompt one would expect for such a sensitive change.

### Likelihood Explanation
This runs automatically during background repository refresh (any time the app fetches the associated `IAPIRepository` for a repo), not behind an explicit user gesture, and the only barriers are the loose structural checks in `urlMatchesRemote` — there is no revalidation against a pinned/expected host allowlist or a user confirmation step, so any attacker capable of influencing the API response object for a tracked repository (e.g., via a malicious GHES endpoint bound to an added account) can trigger it repeatedly and unattended.

### Recommendation
- **Short term:** Require explicit user confirmation before rewriting an existing `origin` remote URL as a result of an API-driven repository refresh, rather than doing it silently; only do this automatically for genuinely benign transitions (e.g., verified rename by the exact same repo ID) and surface everything else as a prompt, mirroring how `repository-settings.tsx` already handles manual remote URL edits with explicit user action.
- **Long term:** Track repository identity by the immutable GitHub repository ID (already stored as `dbID`/`gitHubRepository.dbID`) rather than only owner/name/hostname string matching, and treat any remote-URL auto-update as a high-risk operation gated on that stable identity match plus explicit opt-in, consistent with the report's recommendation to simplify and gate high-risk state mutations.

### Proof of Concept
1. Add a repository in Desktop whose `origin` points at `https://github.com/victim-org/victim-repo`, associated with a `GitHubRepository` record fetched from the API.
2. Cause the API to return an `IAPIRepository`/`IAPIFullRepository` for that same tracked repo with a different `clone_url`, e.g. `https://github.com/victim-org/renamed-or-attacker-repo` (achievable if the attacker controls the API-serving endpoint — e.g. a GHES account — or if the upstream repo is renamed/transferred to a namespace with a similarly-structured owner/name that still parses to matching hostname).
3. On the next background refresh, `updateRemoteUrl` is invoked with the stale `gitHubRepository` and the new `apiRepo`; because `protocolsMatch` is true (both `https`) and `remoteUrlUnchanged` is true (old cached cloneURL still structurally matches current remote), and `urlsMatch` is false (owner/name differ), the condition at: [4](#0-3) 
fires and silently runs `git remote set-url origin https://github.com/victim-org/renamed-or-attacker-repo` with no dialog shown to the user, confirmed by the existing unit test that exercises exactly this rewrite path: [5](#0-4) 
4. The user's subsequent `git push`/`git pull` in Desktop now targets the new remote without their explicit awareness.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
