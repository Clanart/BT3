## Finding [1](#0-0) 

### Title
Permanent lock of refunded IBC funds when re-converting Coin→ERC20 fails during `OnTimeoutPacket`/`OnAcknowledgementPacket` (missing atomicity / missing self-destruct check) - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/msg_server.go`)

### Summary
This is the same bug class as the reported issue: a state-mutating operation (escrow of funds) is allowed to proceed even though a required precondition for the matching "unescrow"/completion step was never (re-)validated, and there is no atomic rollback or recovery path once the completion step fails. In the Cosmos EVM `x/erc20` module, `ConvertCoinNativeERC20` unconditionally escrows the user's Cosmos coins into the module account *before* attempting to unescrow the corresponding ERC20 tokens via an EVM call. When this function is invoked from the IBC timeout/acknowledgement-failure refund path (`ConvertCoinToERC20FromPacket`), any failure of the EVM "unescrow" step (e.g. a self-destructed or transfer-restricted native ERC20 contract) is silently swallowed — only an event is emitted and `nil` is returned — leaving the already-escrowed coins permanently stuck in the `x/erc20` module account with no path for the user to reclaim them.

### Finding Description
`ConvertCoinNativeERC20` performs the coin→ERC20 conversion in two ordered, non-atomic steps:
1. Escrow Coins from the user to the module account: `k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins)` [2](#0-1) 
2. Unescrow ERC20 tokens from the module address to the receiver via an EVM call: `k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())` [3](#0-2) 

When invoked directly through `MsgConvertCoin` (`x/erc20/keeper/msg_server.go`), the caller first checks whether the backing ERC20 contract has self-destructed and, if so, deletes the token pair and returns *before* calling `ConvertCoinNativeERC20`, so escrow never happens: [4](#0-3) 

However, this same precondition check is **not** performed in `ConvertCoinToERC20FromPacket`, which is the function used to convert refunded IBC coins back to ERC20 after a timeout or failed acknowledgement: [5](#0-4) 

If `ConvertCoinNativeERC20` fails at step 2 (self-destructed contract, paused/blacklisting ERC20 logic, or any other transfer failure), the error is caught here and only an event is emitted — the function returns `nil`: [6](#0-5) 

Because the surrounding `OnAcknowledgementPacket`/`OnTimeoutPacket` callbacks also just propagate this `nil` back to `x/erc20/ibc_middleware.go`, ibc-go treats the whole timeout/ack processing as fully successful [7](#0-6)  — there is no `CacheContext`/rollback around the call, so the escrow performed in step 1 is committed to state permanently, while the user never receives the ERC20 tokens.

The net effect: a user who initiated an ordinary IBC transfer that later times out or receives an error acknowledgement gets their coins refunded by the core ICS20 logic, and then — completely outside their control, with no additional signature required — the `x/erc20` middleware immediately re-escrows those same coins into the module account attempting an automatic ERC20 conversion. If that conversion's EVM call fails (any native ERC20 contract can be self-destructed by its own deployer, or otherwise coded to reject the module's `transfer`), the coins are consumed from the user's balance and are never seen again — they sit in the `x/erc20` module account with no message or code path capable of moving them back out to the affected user.

### Impact Explanation
This is a Critical, unprivileged, permanent loss/freezing of user funds:
- Trigger requires no privileges: any user can register a native ERC20 token pair (permissionless registration is configurable and commonly enabled), self-destruct it (or otherwise cause its `transfer` to revert/behave abnormally for the module address), and then simply perform a normal `MsgTransfer` over IBC that ends up timing out or receiving an error ack (which can also be forced by not completing the relay, or naturally through any relayer/channel failure).
- Impact: user's coins are irreversibly moved into the `x/erc20` module account and are unrecoverable — a direct 1:1 accounting break between the native coin and its ERC20 representation and a permanent freeze of spendable user value, matching "Critical permanent freezing, locking...of user funds...token-pair-backed balances."

### Likelihood Explanation
Likelihood is realistic: an attacker only needs to control (deploy/self-destruct) their own registered native ERC20 contract and initiate an ordinary IBC transfer of the corresponding coin that they can arrange to time out or fail acknowledgement (e.g., using a channel to a chain/relayer they influence, or simply letting the timeout elapse). No governance or validator collusion is required, and the flow is part of the standard "receiver got refunded coins, protocol auto re-converts them to ERC20" UX path documented in the code comments themselves.

### Recommendation
- In `ConvertCoinNativeERC20` (or before calling it from `ConvertCoinToERC20FromPacket`), first verify the backing ERC20 contract still exists and has code (the same self-destruct check already used in `ConvertCoin`/`ConvertERC20` in `msg_server.go`) before performing the coin escrow.
- More generally, make the escrow and unescrow steps atomic: perform the escrow and the EVM "unescrow" call within a `CacheContext`, and only commit (`writeFn()`) once the EVM transfer/mint has been confirmed successful; on failure, discard all changes so the coins remain with the original sender instead of being moved into the module account.
- Ensure `ConvertCoinToERC20FromPacket` applies the same `MintingEnabled`-style prerequisite checks used elsewhere before attempting escrow.

### Proof of Concept
1. Deploy and permissionlessly register a native ERC20 contract as a token pair via `MsgRegisterERC20`.
2. Convert some ERC20 balance to native Coin via `MsgConvertERC20` so the user holds `pair.Denom` coins.
3. Self-destruct the ERC20 contract (owner-controlled `selfdestruct`), or otherwise make the contract revert/misbehave on `transfer` calls from the module address.
4. Initiate an IBC transfer of `pair.Denom` coins (`MsgTransfer`) to another chain, and force the packet to time out (or force an error acknowledgement).
5. When ibc-go processes the timeout/ack-error, it refunds the coins to the sender, then `x/erc20/ibc_middleware.go` invokes `k.keeper.OnTimeoutPacket`/`OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20`.
6. `SendCoinsFromAccountToModule` succeeds (escrow), but `CallEVM(...).transfer` fails because the contract has no code / reverts.
7. The error is swallowed; the sender's coins remain permanently in the `x/erc20` module account, and no message exists to recover them.

func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}

// OnTimeoutPacket implements the IBCModule interface.
// It refunds the token transferred and then automatically converts the
// Cosmos Coin to their ERC20 token representation.
func (im IBCMiddleware) OnTimeoutPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) error {
	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet data: %s", err.Error())
	}

	if err := im.Module.OnTimeoutPacket(ctx, channelVersion, packet, relayer); err != nil {
		return err
	}

	return im.keeper.OnTimeoutPacket(ctx, packet, data)
}
