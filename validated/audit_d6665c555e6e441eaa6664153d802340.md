### Title
Identity ("uninitialized") group elements are accepted by `read_G` and treated as valid public keys, enabling trivial signature forgeries and attacker-controlled threshold keys - (File: crypto/ciphersuite/src/lib.rs)

### Summary
The analog of "an implementation contract left uninitialized so anyone can initialize it with malicious inputs" in Serai is the zero/identity state of group elements and threshold structures. `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) validates only that a point encoding is *canonical*; it never rejects the identity element. Every downstream deserializer — `SchnorrSignature::read`, `Commitments::read`, `ThresholdKeys::read`, `DLEqProof::read`, MuSig/aggregate keys — therefore happily ingests the identity point from untrusted bytes, and no verification path re-checks for it. The identity is precisely the "uninitialized" state of a public key: an attacker who can cause one to be installed gets a key they fully control without knowing any discrete log.

### Finding Description
`read_G` deserializes via `GroupEncoding::from_bytes` and rejects only non-canonical encodings (crypto/ciphersuite/src/lib.rs:91-101). The identity encodes canonically on every supported curve, so it passes.

`SchnorrSignature::verify` evaluates `R + c·A − s·G == 0` via `batch_statements`/`multiexp_vartime` (crypto/schnorr/src/lib.rs:88-110). When `A` is the identity, the equation reduces to `R == s·G`. An attacker picks arbitrary `s`, sets `R = s·G`, and the signature verifies — a universal forgery under the identity key, regardless of how strongly the challenge `c` binds the key and message. The same hole exists in `SchnorrAggregate::verify` (crypto/schnorr/src/aggregate.rs:127-146): a term `z·R + z·c·identity − s·G` contributes nothing key-dependent, so any attacker-chosen `R = s·G` satisfies it.

For threshold state, `ThresholdKeys::new` (crypto/dkg/src/lib.rs:355-378) checks only the *count* of `verification_shares` and that participant indexes satisfy `u16::from(participant) <= params.n()`. It performs no identity check on the share points themselves, and computes `group_key` as the interpolated sum over participants `1..=t`. An attacker who feeds crafted bytes into a `ThresholdKeys::read`/`Commitments::read` path can therefore install identity or maliciously-composed verification shares, yielding a `group_key` under their control — the direct parallel of calling `initialize()` on an uninitialized implementation with attacker-chosen inputs.

### Impact Explanation
- **Forged signatures**: any verifier accepting an attacker-supplied or attacker-influenced public key that resolves to identity accepts arbitrary forged Schnorr signatures (individual, batched, and half-aggregated), since `(R = s·G, s)` is always valid under `A = identity`.
- **Attacker-controlled group key**: crafted verification shares produce a `ThresholdKeys` whose `group_key()` the attacker controls, so downstream signing/scanning treats attacker-keyed outputs as belonging to the set — analogous to funds reported under an implementation an attacker initialized.

### Likelihood Explanation
Medium. Exploitation requires a reachable path where untrusted bytes supply a point that is used as a public key or verification share without a separate identity/validity check. That precondition is realistic: `read_G` is the common deserialization funnel for `Commitments::read`, `ThresholdKeys::read`, MuSig keys, and proof inputs, and none of the observed constructors (`ThresholdKeys::new`) or verifiers (`SchnorrSignature::verify`, `SchnorrAggregate::verify`) compensate for `read_G`'s missing identity rejection. I did not fully trace a specific production callsite where attacker bytes land as a signature-verification key, so the reachability of the strongest impact is conditional on such a path existing in the surrounding protocol.

### Recommendation
Reject the identity element in `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs) — `if bool::from(point.is_identity()) { Err(...) }` — so no deserialized point can silently represent the "zero" key. Additionally, defensively reject identity `public_key`/`Rs`/verification shares in `SchnorrSignature::verify`, `SchnorrAggregate::verify`, and `ThresholdKeys::new`, mirroring the report's `_disableInitializers()` advice: make the degenerate state unusable rather than relying on every caller to avoid it.
