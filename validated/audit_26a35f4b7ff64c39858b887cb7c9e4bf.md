### Title
`cancelUnlock` skips reward settlement before resetting `amountInCoolDown`, allowing forfeiture-avoidance on rewards accrued during cooldown - ([File: VLMGP.sol])

### Summary
`VLMGP.cancelUnlock` zeroes `slot.amountInCoolDown` without first calling `IMasterMagpie.multiclaimFor` to force a reward settlement, unlike `unlock()` and `startUnlock()` which both call `multiclaimFor` before mutating cooldown state. Because `vlMGPBaseRewarder._calExpireForfeit` computes the forfeit ratio using the *current* `vlMGP.getRewardablePercentWAD(_account)` at claim time (not a value locked in at accrual time), an attacker can call `cancelUnlock` to instantly restore `getRewardablePercentWAD` toward 100% before claiming, reducing or eliminating forfeiture that should have applied to rewards/MGP that accrued while the slot was in cooldown.

### Finding Description
`getRewardablePercentWAD` computes a rewardable ratio that is reduced whenever a user has `amountInCoolDown > 0` [1](#0-0) . This ratio is used at claim time inside `vlMGPBaseRewarder._sendReward` -> `_calExpireForfeit`, which multiplies whatever `userRewards[token][account]` has accumulated by the *current* percent, not a historically-weighted one [2](#0-1) .

`unlock()` correctly forces settlement of rewards via `IMasterMagpie(masterMagpie).multiclaimFor(...)` **before** zeroing `slot.amountInCoolDown`, so the forfeit computed inside that forced claim still reflects the account being in cooldown [3](#0-2) . `startUnlock()` does the same before creating/resetting a slot [4](#0-3) .

`cancelUnlock()`, however, does **not** call `multiclaimFor` — it directly decrements `totalAmountInCoolDown` and sets `slot.amountInCoolDown = 0` [5](#0-4) . Since `userRewards` for the account is only updated lazily (via the `updateReward`/`updateRewards` modifiers, which call `_earned`/`_updateFor` using `balanceOf(_account)` — a value that does **not** distinguish locked vs. cooldown MGP, see `vlMGPBaseRewarder.balanceOf`/`_earned`/`_updateFor` [6](#0-5) [7](#0-6) ), the reward token amount owed to the user keeps accruing at the full staked rate regardless of cooldown status, and is only ever penalized at the moment of `_sendReward`, based on real-time `getRewardablePercentWAD`.

Exploit flow:
1. Attacker locks MGP in `vlMGP` and lets rewards (`userRewards`) accumulate.
2. Attacker calls `startUnlock(X)` to place part of the balance in cooldown; from this point `getRewardablePercentWAD` returns a value below 1e18, meaning the forfeit fraction on any pending/accruing rewards should apply.
3. Attacker waits — during this window rewards continue to accrue at the full (non-discounted) rate under `_earned`.
4. Instead of calling `unlock()` (which forces a proper forfeit-inclusive settlement), attacker calls `cancelUnlock(slotIndex)`. This resets `amountInCoolDown` to 0 for that slot **without** triggering any reward settlement, so `getRewardablePercentWAD(attacker)` snaps back toward 1e18 immediately.
5. Attacker calls `MasterMagpie.multiclaim([vlMGP])` (or `getReward`/`getRewards`) — this reaches `vlMGPBaseRewarder.getReward`/`getRewards`, which calls `_sendReward` → `_calExpireForfeit` using the now-restored ~100% rewardable percent, so `forfeitAmount` is computed as ~0 even though a portion of the claimed `userRewards` accrued while the attacker's slot was in cooldown and should have been forfeited to `_queueNewRewardsWithoutTransfer` for other lockers.

No modifier (`nonReentrant`, `whenNotPaused`, or reward-index checkpointing) prevents this, because `cancelUnlock` is a legitimate, unprivileged, non-reentrant-relevant state change that is simply missing the forced-settlement call that its sibling functions (`unlock`, `startUnlock`) have.

### Impact Explanation
This is a theft-of-unclaimed-yield vulnerability: the forfeiture mechanism exists specifically to redistribute a cooling-down user's proportional share of rewards to other lockers (via `_queueNewRewardsWithoutTransfer`). By using `cancelUnlock` as a "reset switch" immediately before claiming, an attacker can bypass forfeiture on rewards that legitimately accrued during the cooldown period, capturing value that should have gone to the remaining, fully-locked stakers. This matches the "theft of unclaimed yield that should have been forfeited to other lockers" impact class.

### Likelihood Explanation
This requires no special privileges — any locker with an active unlock slot can perform this sequence at will, repeatedly, for every unlock/cancel cycle they choose to run, using only their own locked MGP and standard public functions (`startUnlock`, `cancelUnlock`, `multiclaim`/`getReward`). It requires no flash loans, front-running, or governance access, and is fully repeatable each time the account has a nonzero unlock slot and pending rewards. The only capital needed is the MGP already locked by the user.

### Recommendation
Add the same forced-settlement pattern used in `unlock()`/`startUnlock()` to `cancelUnlock()`: call `IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender)` (settling/forfeiting rewards at the pre-cancel `getRewardablePercentWAD`) before mutating `slot.amountInCoolDown` and `totalAmountInCoolDown`. Alternatively, refactor forfeiture to be computed and locked in incrementally per reward-per-token checkpoint (so that forfeiture reflects the cooldown state at the time rewards accrued rather than at claim time), removing the dependency on callers happening to force a settlement before changing cooldown state.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `vlMGPBaseRewarder`, `MasterMagpie` per existing test harness/fixtures.
2. Attacker locks `1000 MGP`; owner/manager queues MGP or bonus rewards into `vlMGPBaseRewarder` via `queueNewRewards`/`queueMGP` so `rewardPerTokenStored` increases.
3. Attacker calls `startUnlock(500)` to place half in cooldown; assert `vlMGP.getRewardablePercentWAD(attacker) < 1e18`.
4. Advance time partway through `coolDownInSecs` (still within cooldown) and have manager queue more rewards so `userRewards` accrues at the full (undiscounted) `balanceOf`-weighted rate.
5. **Branch A (no cancel)**: call `MasterMagpie.multiclaim([vlMGP])` directly at this point; record `forfeitAmountA = calExpireForfeit(attacker, rewardToken)` — expect `forfeitAmountA > 0`.
6. **Branch B (exploit)**: instead, call `vlMGP.cancelUnlock(0)` first, then call `MasterMagpie.multiclaim([vlMGP])`; record `forfeitAmountB` and the amount actually transferred to attacker.
7. Assert `forfeitAmountB == 0` (or `forfeitAmountB << forfeitAmountA`) and that the attacker's received reward amount in Branch B exceeds what they should be entitled to based on the pre-cancel `getRewardablePercentWAD`, demonstrating improper zeroing of the forfeiture and theft of yield that should have been redistributed via `_queueNewRewardsWithoutTransfer`.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }

    function cancelUnlock(uint256 _slotIndex) external override whenNotPaused {
        _checkIdexInBoundary(msg.sender, _slotIndex);
        UserUnlocking storage slot = userUnlockings[msg.sender][_slotIndex];

        _checkInCoolDown(msg.sender, _slotIndex);

        totalAmountInCoolDown -= slot.amountInCoolDown; // reduce amount to cool down accordingly
        slot.amountInCoolDown = 0; // not in cool down anymore

        emit ReLock(msg.sender, _slotIndex, slot.amountInCoolDown);

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        uint256 userVlMGPAmount = balanceOf(_account);

        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;

            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userVlMGPAmount);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
    }

    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userVlmgpShare) internal view returns (uint256) {
        return ((_userVlmgpShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**vlMGPDecimal) + userRewards[_rewardToken][_account];
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
