This confirms the analog exists: Kaia's EIP-7702 `SetCodeAuthorization` mechanism validates authorizations by their `authority`'s current account nonce, and applying an authorization increments that same nonce — while the tx pool only reserves "one in-flight transaction" per authority, not per (authority, nonce) pair binding to a specific sponsoring transaction.

### Title
Front-running of EIP-7702 SetCode authorizations allows a third party to invalidate a pending sponsor's `SetCodeTx`, silently dropping the delegation payload - (File: blockchain/state_transition.go)

### Summary
An unprivileged user who observes a pending `TxTypeEthereumSetCode` transaction in the mempool can extract the embedded `SetCodeAuthorization` tuple(s) (which are plain, replayable signed objects independent of the sponsoring transaction's signature) and resubmit them inside the attacker's own `SetCodeTx`. If the attacker's transaction lands first, the authority's nonce is incremented, causing the original sponsor's authorization to fail `validateAuthorization`'s nonce check and be silently skipped rather than applied.

### Finding Description
`SetCodeAuthorization` is a detachable, independently signed payload: `ChainID`, `Address`, `Nonce`, and a signature over just those three fields [1](#0-0) . Any transaction sender can embed any authority's valid authorization tuple in their own `AuthList`, because nothing binds the authorization to a specific sponsoring transaction or sender — `Authority()` only recovers the signer address, and the tx pool similarly does not tie authorizations to any particular pending transaction hash. `applyAuthorization`/`validateAuthorization` check the authorization strictly against the authority's *current* on-chain nonce: `if have := st.state.GetNonce(authority); have != auth.Nonce { return authority, ErrAuthorizationNonceMismatch }` [2](#0-1) , and successful application increments that nonce: `st.state.IncNonce(authority)` [3](#0-2) .

Because an authorization's validity depends purely on the authority's live nonce (not on inclusion of a specific transaction hash or a commitment to the sponsor), a malicious third party can:
1. Observe a pending `SetCodeTx` (sponsor S includes authority A's tuple with `nonce = N`) broadcast to the mempool/gossiped p2p network.
2. Construct their own `SetCodeTx` (or any tx) embedding the same authority A's authorization tuple with `nonce = N`, and get it mined first (e.g., with higher gas price).
3. Once applied, A's nonce becomes `N+1`, so when S's original transaction is later processed, `validateAuthorization` fails on the now-stale nonce and the framework "simply skips invalid authorizations here": `st.applyAuthorization(&auth, rules)` inside a comment stating errors are ignored [4](#0-3) .

Unlike a value-transfer nonce collision (which reverts the whole tx and is visible/rejected), an invalid authorization inside a `SetCodeTx` does **not** revert the enclosing transaction — the sender's fee is still paid and the tx succeeds, but the intended delegation/undelegation never takes effect. This matches the report's bug class: a publicly-observable signed payload can be consumed by an unrelated party to invalidate a pending, legitimately-submitted operation, denying the original submitter their intended on-chain effect while they still pay gas.

The tx-pool-level mitigation only limits in-flight transactions *per authority address* (`ErrAuthorityReserved` if more than one pending/queued tx references the same authority) [5](#0-4) , but this does nothing to stop an attacker's freshly-crafted transaction (not previously known to the pool) from consuming the authorization first — the check only guards against multiple pool-known transactions for the same authority, not against a race for who reaches the state transition first with the same signed tuple.

### Impact Explanation
This is a griefing/DoS vector against sponsors and authorities relying on EIP-7702 delegation (e.g., wallet upgrade flows, gasless relaying setups built atop delegated accounts). A malicious actor can repeatedly deny targeted delegation-installation transactions from taking effect while the fee-paying sponsor still incurs gas costs, and dependent flows (e.g., relayers expecting delegation code to exist at `authority` before executing further logic) can silently fail or behave unexpectedly since no revert occurs. This does not directly steal funds by itself, but it enables consistent denial of an on-chain state change the account holder explicitly authorized, and it can be leveraged to grief accounts in the middle of relayer-driven or gasless flows that assume the delegation transaction either succeeds or reverts loudly.

### Likelihood Explanation
Likelihood is significant: mempool transactions (including `AuthList` contents) are public before inclusion in Kaia (consistent with standard EVM mempool visibility), extracting an authorization tuple requires no special access, and front-running by paying a higher gas price is a widely available capability for any unprivileged, unauthenticated transaction submitter. No malicious node, peer, or validator behavior is required — a single competing transaction sender suffices.

### Recommendation
Consider one or more of the following:
- Bind `SetCodeAuthorization` semantics so that once an authorization for a given `(authority, nonce)` is consumed by any transaction, the framework surfaces an explicit, attributable failure (e.g., emit a receipt-level indicator) rather than a silent skip, so sponsors/relays can detect and react to griefed authorizations.
- Extend the tx-pool's authority reservation (`validateAuth`/`checkDelegationLimit`) to also protect against externally-crafted competing authorizations for an authority already referenced by a pool-known pending transaction, e.g., by tracking known `(authority, nonce)` pairs across the whole pool and prioritizing/protecting the first-seen sponsor.
- Document this footgun clearly for downstream systems (wallets/relayers) so that they treat `SetCodeTx` inclusion success as necessary but not sufficient to confirm the specific authorization was applied — they should verify the authority's code/delegation post-execution rather than assuming success from the receipt status alone.

### Proof of Concept
1. Authority A signs `SetCodeAuthorization{ChainID, Address: target, Nonce: N}` and gives it to sponsor S, who broadcasts `SetCodeTx_S` embedding it (as tested in `TestSignSetCodeAndAuthority7702`/`sendSetCodeTx`) [6](#0-5) .
2. Attacker M observes `SetCodeTx_S` in the mempool, extracts the `SetCodeAuthorization` tuple (ChainID, Address, Nonce, V, R, S), and crafts `SetCodeTx_M` (any `to`, any minimal payload) embedding the identical authorization tuple, using a higher gas price so it's included first.
3. Block includes `SetCodeTx_M` first: `applyAuthorization` succeeds, calling `st.state.IncNonce(authority)` for A, moving A's nonce from N to N+1 and installing the delegation from `SetCodeTx_M`'s embedded tuple (same address as intended, so on the surface state now "looks correct", but attribution/control of *when and via which sponsor* it was applied is stolen) [7](#0-6) .
4. When `SetCodeTx_S` is later processed, `validateAuthorization` computes `have := st.state.GetNonce(authority)` = N+1 ≠ `auth.Nonce` (N), returning `ErrAuthorizationNonceMismatch`; per the caller's contract ("errors are ignored, we simply skip invalid authorizations here"), `SetCodeTx_S` still succeeds (gas is charged to S) but S's authorization step is silently dropped [4](#0-3) .
5. Repeat for every subsequent attempt by S, since M can always resubmit intercepted tuples faster with a marginally higher gas price, resulting in persistent denial of S's intended sponsored delegation while S continues to pay fees.

func (st *StateTransition) applyAuthorization(auth *types.SetCodeAuthorization, rules params.Rules) (err error) {
	authority, err := st.validateAuthorization(auth)
	if err != nil {
		return err
	}

	// If the account already exists in state, refund the new account cost
	// charged in the initrinsic calculation.
	if st.state.Exist(authority) {
		// If the account is not AccountKeyTypeLegacy, setcode is not allowed.
		accountKeyType := st.state.GetKey(authority).Type()
		if !accountKeyType.IsLegacyAccountKey() {
			return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
		}
		st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
	}

	// Update nonce and account code.
	st.state.IncNonce(authority)
	delegation := types.AddressToDelegation(auth.Address)
	if common.EmptyAddress(auth.Address) {
		// Delegation to zero address means clear.
		st.state.SetCodeToEOA(authority, []byte{}, rules)
		return nil
	}

	// Otherwise install delegation to auth.Address.
	// We treat EOA and SCA as separate objects and therefore need to use
	// distinct methods.
	st.state.SetCodeToEOA(authority, delegation, rules)

	return nil

// validateAuth verifies that the transaction complies with code authorization
// restrictions brought by SetCode transaction type.
func (pool *TxPool) validateAuth(tx *types.Transaction) error {
	// Allow at most one in-flight tx for delegated accounts or those with a
	// pending authorization.
	if err := pool.checkDelegationLimit(tx); err != nil {
		return err
	}

	// For symmetry, allow at most one in-flight tx for any authority with a
	// pending transaction.
	for _, auth := range tx.SetCodeAuthorities() {
		var count int
		if pending := pool.pending[auth]; pending != nil {
			count += pending.Len()
		}
		if queue := pool.queue[auth]; queue != nil {
			count += queue.Len()
		}
		// Replace the existing in-flight transaction for delegated accounts
		// are still supported
		if count > 1 {
			return ErrAuthorityReserved
		}
	}
	return nil
}
