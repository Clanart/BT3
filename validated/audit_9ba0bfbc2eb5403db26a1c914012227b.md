### Title
Unchecked subtraction in mempool fee calculation can throw an unhandled exception instead of the intended `MINTING_COIN` rejection - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `removal_amount - addition_amount` and immediately casts it to `uint64` without first verifying that `removal_amount >= addition_amount`, unlike the equivalent, safe check that exists in block-body validation.

### Finding Description
While building the `MempoolItem` for a submitted spend bundle, the function sums the value of all `CREATE_COIN` outputs into `addition_amount` and the value of all consumed coins into `removal_amount`: [1](#0-0) [2](#0-1) 

It then does:
```
fees = uint64(removal_amount - addition_amount)
```
with no preceding check comparing the two amounts, exactly the same "subtract-then-cast" pattern flagged in the external report (`D3UserQuota.getUserQuota()` computing `quota - usedQuota` without verifying `quota > usedQuota`).

By contrast, block-body validation — which runs on already-accepted blocks — explicitly guards this exact subtraction: [3](#0-2) 
```
if removed < added:
    return Err.MINTING_COIN
fees = removed - added
assert fees >= 0
```
That is, the consensus layer treats "additions exceed removals" (an attempt to mint coins from nothing) as an expected, handled error (`Err.MINTING_COIN`). The mempool layer (`mempool_manager.py`), which is the first thing an unprivileged submitter's spend bundle hits, has no equivalent guard before the `uint64()` cast on line 814. If a submitter crafts a spend bundle whose `CREATE_COIN` conditions sum to more than the value of the coins being spent, `removal_amount - addition_amount` is negative, and constructing a `uint64` from a negative Python `int` raises an exception (`ValueError`/`OverflowError` from the underlying sized-int implementation) instead of the graceful `Err.*` return that every other validation step in this function uses.

### Impact Explanation
Every other failure path in `validate_spend_bundle` returns a well-defined `(Err, None, [])` tuple that the caller handles cleanly (rejecting the transaction, optionally banning/logging). An uncaught exception thrown mid-function instead propagates up through the mempool admission call chain for that spend bundle. This is a spend-bundle-triggered anomaly in the core transaction-admission path reachable by any unprivileged party who can submit a spend bundle (wallet RPC `push_tx` or the p2p transaction protocol), and it deviates from the intended, already-implemented `MINTING_COIN` handling that exists one layer up (block validation). At minimum it causes unstructured error propagation instead of the intended `Err.MINTING_COIN` rejection for the mempool-admission code path; depending on how the caller of `validate_spend_bundle` handles unexpected exceptions, this can manifest as inconsistent/unhandled request failures for that specific spend-bundle validation call.

### Likelihood Explanation
High: this requires no special coin, no signature, and no privileged party — it only requires assembling a spend bundle (submitted via the mempool/RPC path) whose declared `CREATE_COIN` outputs exceed the value of the coins actually being spent. Any external submitter can trigger this deterministically.

### Recommendation
Mirror the `block_body_validation.py` guard in `mempool_manager.py` before computing fees:
```python
if removal_amount < addition_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This makes the mempool-admission path consistent with block-body validation and avoids relying on an unchecked cast to surface an error.

### Proof of Concept
1. Construct a spend bundle that spends coin(s) totaling `X` mojos but includes `CREATE_COIN` conditions whose amounts sum to `> X` (i.e., an attempted supply-inflation/minting spend).
2. Submit the bundle through the normal unprivileged path (wallet RPC `push_tx` / peer `transaction` message) so it reaches `MempoolManager.validate_spend_bundle`.
3. Execution reaches `addition_amount` (sum of `CREATE_COIN` amounts) > `removal_amount` (sum of spent-coin amounts) at line 814, and `uint64(removal_amount - addition_amount)` raises on the negative value instead of the code returning `Err.MINTING_COIN` as block validation would.

Note: I was not able to trace, within the available context, whether the immediate caller of `validate_spend_bundle` wraps this call in a broad `try/except`, which would determine the exact blast radius (silent transaction drop vs. an unhandled exception surfacing further up the stack). This should be verified directly against `chia/full_node/mempool_manager.py` (callers of `validate_spend_bundle`) before treating this as more than the currently-provable issue: a missing, already-precedented `MINTING_COIN`-style guard in the mempool admission path.
