### Title
Missing-participant check bypass in `GeneratorPromotion::complete` causes reachable panic (DoS) - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
The CVE-2019-5717 bug class is "a crafted input passes superficial validation and reaches code that fatally errors on the invalid value" (a dissector crash on sequence number zero). The analog in Serai is `GeneratorPromotion::complete` in the in-scope `crypto/dkg/promote` crate: it validates only the *quantity* and *upper bound* of the attacker-supplied `proofs` map, then indexes it with `unwrap()`, so a malformed map containing a duplicate-role entry (e.g., a proof keyed to the local participant `params.i()` instead of a required distinct participant) passes validation and causes a panic when the missing participant's proof is fetched.

### Finding Description
`complete` performs two checks on the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

1. `proofs.len() == params.n() - 1` (crypto/dkg/promote/src/lib.rs:125)
2. every key `<= params.n()` (crypto/dkg/promote/src/lib.rs:132-136)

It then iterates `i in 1..=n` (skipping `params.i()`) and calls `proofs.get(&i).unwrap()` (crypto/dkg/promote/src/lib.rs:146). Nothing verifies that the map actually contains every required participant. An unprivileged party submitting a promotion proof set can include a proof keyed to `params.i()` itself — which is counted toward the `n - 1` total and passes the `<= n` bound — while omitting some other participant `j`. At `i == j`, `proofs.get(&j)` returns `None` and `.unwrap()` panics.

This is directly reachable through the library's own untrusted-input surface: `GeneratorProof::read` (crypto/dkg/promote/src/lib.rs:72-77) parses the attacker-controlled bytes fed into `complete`, matching the prompt's `*_read`/`complete` sink class. The same class of panic exists elsewhere reachable from crafted `ThresholdKeys` (`ThresholdKeys::original_verification_share` / `ThresholdView::verification_share` index a `HashMap` with `[&l]` and "will panic if the participant index is invalid", crypto/dkg/src/lib.rs:457-459, 680-682), but the `proofs.get(&i).unwrap()` path is the cleanest unprivileged trigger.

### Impact Explanation
A panic in `complete` aborts the promotion ceremony for every honest participant that processes the malformed proof set, and in a hosting node (e.g., the processor driving key rotation between generators) unwinds into a crash of the calling task — denial of service against the threshold-key infrastructure, the same availability impact class as the Wireshark dissector crash. No secret material is exposed.

### Likelihood Explanation
Any participant in a generator-promotion round can submit the malformed map; the trigger requires only supplying `n - 1` proofs where one is keyed to the victim's own index instead of the full distinct set `1..=n \ {params.i()}`. The validation gap is unconditional — it does not depend on timing, collusion, or invalid curve encodings — so the panic is deterministic whenever an unprivileged party chooses to send the malformed input.

### Recommendation
Replace the length-plus-upper-bound checks with exact-set validation, mirroring `validate_map` in `crypto/frost/src/lib.rs:50-73`: require `proofs` to contain every `Participant` in `params.all_participant_indexes()` except `params.i()`, reject `params.i()` itself with `InvalidParticipant`/`DuplicatedParticipant`, and return `PromotionError::IncorrectAmountOfParticipants` (or a new `MissingParticipant` variant) rather than panicking. Concretely, change `proofs.get(&i).unwrap()` to `proofs.get(&i).ok_or(PromotionError::IncorrectAmountOfParticipants { .. })?` or pre-validate the key set before iterating.

// Given ThresholdParams { t, n, i } for the local party (params.i() = i):
let mut proofs: HashMap<Participant, GeneratorProof<C>> = HashMap::new();
// Insert a validly-parsed proof keyed to the VICTIM's own index i ...
proofs.insert(params.i(), attacker_proof);
// ... and proofs for all participants 1..=n except i and except j
for l in 1..=n {
    if l == params.i() || l == j { continue; }
    proofs.insert(Participant::new(l).unwrap(), valid_proof_for(l));
}
// proofs.len() == n - 1  → passes the quantity check
// all keys <= n          → passes the bounds check
promotion.complete(&proofs); // proofs.get(&j).unwrap() → panic
