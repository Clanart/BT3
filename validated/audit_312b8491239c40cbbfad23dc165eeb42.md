## Finding: Excess Native `msg.value` Sent to `EvmHost.dispatch()` Is Permanently Lost (Not Refunded)

### Title
`EvmHost.dispatch()` swallows excess native `msg.value` during fee-token swap, causing permanent fund loss - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core broken invariant is: *a function accepts a `msg.value` from an untrusted caller and executes downstream logic without validating/reconciling that value against what was actually intended, leading to loss of funds or unintended state.* The direct local analog is in `EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)`, which forward the caller's entire `msg.value` to a Uniswap V2 swap but never validate or refund any leftover amount to the original sender.

### Finding Description
When a caller pays for a dispatch fee in native token, `EvmHost.dispatch()` forwards the **entire** `msg.value` into `swapETHForExactTokens`: [1](#0-0) 

`swapETHForExactTokens` only consumes as much ETH as needed to obtain exactly `post.fee` tokens; the Uniswap V2 router refunds any unused ETH to `msg.sender` of the swap call — which, because `EvmHost` itself calls the router, is `EvmHost`, not the original end user. The same pattern exists for GET requests: [2](#0-1) 

Unlike the analogous `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` contracts, which explicitly track a local `msgValue` variable, decrement it per spend, and **explicitly refund any unspent amount back to `msg.sender`** at the end of execution: [3](#0-2) [4](#0-3) 

`EvmHost.dispatch()` has **no equivalent accounting or refund step**. There is no check that `msg.value` equals (or is bounded near) `post.fee`'s native-token equivalent before the swap, and no logic afterward to return unused native tokens to the caller. This mirrors the report's core theme — a value discrepancy between what a caller intends to spend and what actually gets consumed/state-changed is never checked or reconciled — except here the consequence is not a governance-replay risk but a direct, guaranteed loss of user funds for any overpayment.

### Impact Explanation
Any user who overestimates required native fee (e.g., due to slippage buffers, price fluctuation between quote and execution, or simply sending a round number greater than the exact fee) permanently loses the excess ETH into the `EvmHost` contract balance, with no path to reclaim it. This is a direct "loss of funds" impact matching the bounty's accepted impact category, and is reachable by any unprivileged caller of the public `dispatch()` entrypoints — no relayer, prover, or admin involvement is required.

### Likelihood Explanation
High: any normal usage pattern where a client doesn't compute the exact Uniswap swap input amount (which depends on live pool reserves at execution time) will result in leftover `msg.value` being silently absorbed. This is not an edge case — it is the default behavior for any overpayment, and the docs even instruct users to "estimate fees" client-side, which inherently invites imprecision.

### Recommendation
Track the actual ETH consumed by the swap (`swapETHForExactTokens` returns `amounts[0]` as the ETH spent) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the refund pattern already implemented in `IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain`:

```solidity
// evm/src/core/EvmHost.sol
if (msg.value > 0) {
    address[] memory path = new address[](2);
    ...
    uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
    uint256 refund = msg.value - amounts[0];
    if (refund > 0) {
        (bool sent, ) = _msgSender().call{value: refund}("");
        require(sent, "refund failed");
    }
}
```

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(DispatchPost)` (or via `IDispatcher(host).dispatch{value: X}(post)`) with `msg.value = X`, where `X` is greater than what's needed to swap for `post.fee` fee-tokens (e.g., due to price movement or a generous buffer).
2. `swapETHForExactTokens{value: X}(post.fee, path, address(this), ...)` executes; the router consumes only `amounts[0] < X` ETH and refunds `X - amounts[0]` back to `EvmHost` (the caller of the router), not to the user.
3. `EvmHost.dispatch()` returns normally with the request emitted; the user's transaction succeeds, but `X - amounts[0]` ETH remains stuck in `EvmHost`'s balance permanently, with no compensating logic to return it.
4. Repeatable by any caller on every dispatch call that supplies native token payment, with no way for the sender to recover the difference.
