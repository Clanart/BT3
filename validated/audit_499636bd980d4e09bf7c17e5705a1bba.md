### Title
Stale absolute-line-index selection is silently re-applied to a re-fetched diff during partial commit, causing wrong hunks/lines to be staged or discarded - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop tracks which diff lines a user has selected for a partial commit or discard using a `DiffSelection` object that is keyed by **absolute line index** into the current diff's hunks, not by the actual line content. When the working directory diff is refreshed (`updateChangesWorkingDirectoryDiff`), the code explicitly acknowledges that it does **not** revalidate whether a previously selected line still corresponds to the same content — it only strips selection from indices that are no longer "includeable" (i.e. turned into context/hunk lines). If the underlying file changes between the time the user makes a line selection and the time the diff is regenerated (e.g., due to a background status refresh, an external editor, a build/watch script, or a git hook triggered by a Desktop-initiated git operation on a hostile repository), a selected index can silently come to reference a *different* addition/deletion than the one the user actually selected. This selection is then fed unmodified into `formatPatch` / `formatPatchToDiscardChanges`, which blindly trusts `selection.isSelected(absoluteIndex)` to build the patch applied via `git apply --cached` or `git apply` (discard). The result is a patch that includes/excludes lines the user never reviewed, silently corrupting what is committed or discarded.

### Finding Description
`updateChangesWorkingDirectoryDiff` re-fetches the diff for the selected file and then reconciles the existing partial-selection state against the new diff: [1](#0-0) 

The comment is explicit about the limitation: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines such that any previously selected line which now no longer exists or has been turned into a context line isn't still selected."* In other words, the guard only removes a selection when the line at that absolute index is no longer includeable — it does **not** verify that the line at that index is still the *same* line the user selected. If the diff shifts (lines added/removed above the selected hunk, or hunk boundaries change) but the index still happens to land on an Add/Delete line, the stale selection remains "selected" and is silently carried forward onto unrelated content.

This selection state is later consumed verbatim by the patch generators, which trust `absoluteIndex` without any content-based verification: [2](#0-1) [3](#0-2) 

Notably, `applyPatchToIndex` (used for committing) does fetch a fresh diff immediately before formatting the patch: [4](#0-3) 

...but it reuses the `file.selection` object that was computed against a *previous* diff snapshot (the one the user interacted with in the UI), not the freshly-fetched one used to build the patch. There is no re-validation that the selection's absolute indices still line up with the same content in this fresh diff. The same untrusted-selection pattern applies to discard, where `discardChangesFromSelection` takes the `diff`/`selection` pair straight from UI component props (`this.props.diff`, `this.props.selection` in `discard-selection-dialog.tsx`) and applies the resulting reverse patch directly to the working tree via `git apply`, with no re-diff/re-validation step: [5](#0-4) [6](#0-5) 

This mirrors the structure of the reported smart-contract bug: a value (`existingPnlCollateral`/`positionSizeCollateralDelta`) is computed and reused across an operation without accounting for state that changed since it was first captured (previously realized/withdrawn PnL). Here, the "value" is the set of selected diff-line indices, and the "state that changed since capture" is the actual diff content — the code updates *some* invariants (removing entries that are no longer includeable) but not the core one (that the index still points at the same logical change), so stale selection state is silently re-applied to different underlying content.

### Impact Explanation
A repository whose tracked files are modified between the moment Desktop renders/loads a diff and the moment the user commits or discards (via Desktop-triggered git operations, hook execution, filter/smudge processes, or any file-system event that races with Desktop's periodic background status refresh) can cause the user to commit or discard lines they never selected, or fail to commit/discard lines they did select. This is silent corruption of what the user commits or pushes — one of the explicitly valid impact categories — because the resulting commit/working-tree state does not match the user's actual intent and no error or warning is surfaced.

### Likelihood Explanation
Exploiting this reliably requires a timing window between diff generation and the commit/discard action, which in practice can be induced by content in the repository itself (e.g., a git hook that runs during a Desktop-initiated operation and touches tracked files, or build/watch tooling the repository instructs the user to run). Desktop's own background refresh cycle (periodic status polling) increases the likelihood of a race even without deliberate exploitation, since the diff shown to the user can be regenerated at any time while a partial selection is pending. The likelihood is lower than a direct, always-reproducible bug because it depends on a timing race, but the guard comment in the code confirms the developers were aware the selection-preservation logic is not fully sound, indicating this is a real, previously-acknowledged gap rather than a theoretical concern.

### Recommendation
When reconciling `DiffSelection` state against a freshly loaded diff, validate that the line content at each previously selected absolute index is unchanged (e.g., compare line text/type, not just includeability) before preserving its selected state; if content differs, clear the selection for that index and flag the file for re-review. Additionally, `applyPatchToIndex` and `discardChangesFromSelection` should re-derive/verify the diff used to build the patch against the same diff the selection was computed from (e.g., via a content hash or `git diff` blob comparison) immediately before applying, and abort with a clear error if the working tree has changed underneath, rather than silently applying a possibly-mismatched patch.

### Proof of Concept
1. Open a repository in Desktop and select a modified file with multiple hunks; select only specific added/deleted lines for a partial commit (leave the commit box open, uncommitted).
2. While Desktop's diff view is open, externally modify the same file so that lines are inserted/removed above the hunk containing the user's selection (e.g., via an editor, a script, or — in the hostile-repo scenario — a `post-checkout`/`post-merge` hook that Desktop's own operations trigger and that rewrites a tracked file).
3. Wait for (or trigger) Desktop's background status/diff refresh (`updateChangesWorkingDirectoryDiff`), which reconciles the old selection with the new diff using only the "still includeable" check (`app/src/lib/stores/app-store.ts:3478-3497`) rather than content equality.
4. Commit the file with the (now-stale) selection. `applyPatchToIndex`/`formatPatch` build the patch using `file.selection.isSelected(absoluteIndex)` against the newly-fetched diff (`app/src/lib/git/apply.ts:52-61`, `app/src/lib/patch-formatter.ts:143-161`), silently including/excluding lines that no longer correspond to what the user originally reviewed and clicked.
5. Inspect the resulting commit/diff: it contains different content than what the user selected in the UI, with no warning shown.

Note: I was not able to fully trace every intermediate call path (e.g., exact conditions under which `applyPatchToIndex`'s freshly-fetched diff can diverge in shape from the diff used to build the UI's `DiffSelection` within a single commit action) due to tool/iteration limits; a Devin session with full repository access would be needed to build and run an end-to-end reproduction to confirm exploitability with high confidence.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
