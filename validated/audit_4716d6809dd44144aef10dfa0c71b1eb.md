### Title
Unbounded, unmetered EIP-7702 authorization-list loop in the EVM preprocessing ante decorator enables CPU-exhaustion DoS - (File: x/evm/ante/preprocess.go)

### Summary
`EVMPreprocessDecorator.AnteHandle` switches the context to an infinite gas meter and then, for `SetCode` (EIP-7702, type 4) transactions, iterates over every entry in the transaction's `AuthList` doing ECDSA signature recovery and a full address-association attempt for each one — before the transaction's declared gas limit or intrinsic gas cost is ever validated. Because the loop runs under an infinite gas meter and the authorization count is attacker-controlled (bounded only by max tx size, not by gas), a single crafted transaction can force every node's `CheckTx` and `DeliverTx` path to perform thousands of expensive cryptographic recoveries essentially for free, mirroring the reported "unbounded loop on user-controlled array" DoS pattern.

### Finding Description
`EVMPreprocessDecorator.AnteHandle` sets `ctx = ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))` and then calls `p.associateAuthorizationAuthorities(ctx, msg, associateHelper)`: [1](#0-0) [2](#0-1) 

That helper unconditionally loops over `ethTx.SetCodeAuthorizations()` — the raw, unbounded `AuthList` decoded straight from the transaction bytes — invoking `helpers.AuthorityToPreAssociate` (which performs ECDSA public-key recovery per entry) and, for entries that pass, opening a cache context and running a full `AssociateAddresses` (account/bank state read+write) for each authorization: [3](#0-2) 

The identical unbounded pattern also exists in the legacy ante path used by `EvmDeliverTxAnte`/`EvmCheckTxAnte`: [4](#0-3) [5](#0-4) 

Crucially, this happens *before* the transaction's basic validation / intrinsic gas checks (which include the go-ethereum `PER_EMPTY_ACCOUNT_COST` charge per authorization, confirmed by the `eth_estimateGas` test expecting `≥25_000` gas per authorization) are performed later in the ante chain, per the module's documented pipeline: [6](#0-5) [7](#0-6) 

The Cosmos SDK ante gas meter (used elsewhere to charge gas for expensive operations) is bypassed here because the context already carries an infinite meter, so none of the ECDSA recoveries or state cache operations performed in this loop consume any accounted gas. There is no explicit cap on `AuthList` length found in `SetCodeTx.Validate()` (only an empty-list rejection is enforced): [8](#0-7) 

Given the mempool's per-tx byte limit (`max-tx-bytes = 2048576`, i.e. ~2 MiB): [9](#0-8) 

and that each `SetCodeAuthorization` (chain ID, address, nonce, v/r/s) serializes to roughly 100–150 bytes, a single transaction can carry on the order of 10,000+ authorizations, each demanding a secp256k1 recovery and (for authorizations with distinct valid chain/nonce/account state) a full account-association attempt.

### Impact Explanation
This loop runs on **every node** that receives the transaction during `CheckTx` (mempool admission, executed by all validators/full nodes) and again during `DeliverTx`/block execution — all before gas-based rejection can occur. An attacker submitting a small number of such maximally-sized SetCode transactions can force widespread, synchronized CPU spikes across the validator set performing thousands of uncompensated ECDSA recoveries and account-association state operations per transaction. This can push block processing time beyond the network's expected block cadence (a "block delay beyond 2.5 seconds" style impact) or, at volume, degrade validator throughput broadly — a compute-exhaustion Denial-of-Service reachable by any unprivileged EVM transaction sender, matching the audit report's underlying bug class (an attacker-sized array driving an unmetered/unbounded loop).

### Likelihood Explanation
Likelihood is high for anyone able to submit EVM transactions: crafting a `SetCodeTx` with a large `AuthList` requires no special privilege, no prior association, and no significant funds (only enough to pay the base fee floor check, since the expensive loop executes before fee/gas validation fully gates the tx). The pattern is directly reachable via the public EVM JSON-RPC (`eth_sendRawTransaction`) and mempool admission path used by every unprivileged EVM client.

### Recommendation
- Cap the number of `SetCodeAuthorizations` processed in `associateAuthorizationAuthorities` / `AssociateAuthorizationAuthorities` to a small, protocol-defined maximum (or reject transactions whose `AuthList` length exceeds a sane bound) before any recovery/association work is attempted.
- Perform (or duplicate) intrinsic/basic gas and size validation for the transaction *before* running the authorization pre-association loop, so a transaction with excessive authorizations is rejected on gas/intrinsic grounds prior to any expensive per-entry work.
- Meter this specific loop with a finite gas meter (or a fixed CPU budget check) rather than running it under `NewInfiniteGasMeterWithMultiplier`, so the cost is either charged to the sender or rejected early.

### Proof of Concept
1. Craft an EIP-7702 `SetCodeTx` sized near the mempool's `max-tx-bytes` limit (~2 MiB) with as many distinct, validly-signed `SetCodeAuthorization` entries as fit (~10,000+), each targeting a fresh/never-associated authority address with a matching chain ID and correct nonce so `AuthorityToPreAssociate` returns `ok=true` for as many entries as possible (maximizing both recovery and `AssociateAddresses` state work).
2. Submit the transaction via `eth_sendRawTransaction` to a Sei RPC node.
3. Observe that `CheckTx` (and later `DeliverTx`) spends CPU time proportional to the authorization count performing ECDSA recoveries and per-authority association writes under an infinite gas meter — work fully incurred before the intrinsic-gas/authorization-cost check (`PER_EMPTY_ACCOUNT_COST` per auth) can reject the transaction for insufficient gas.
4. Repeat with multiple such transactions/senders to measure aggregate CPU impact on block processing time across the validator set.

Note: I was unable to fully confirm whether a length limit on `AuthList` exists in a validation path outside the file/functions reviewed (e.g., a possible cap enforced in intrinsic-gas computation prior to the preprocessing step, or in mempool-level tx decoding) since the full call graph around `EvmStatelessChecks`/`x/evm/ante/basic.go` was not completely inspected. This should be verified before treating the finding as fully unmitigated.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}

**File:** x/evm/AGENTS.md (L52-60)
```markdown
The EVM ante chain performs, in order:

1. **Cosmos field rejection** — EVM txs must not use Cosmos-specific fields (memo, timeout, fees, etc.).
2. **Preprocessing** — unpacks the inner Ethereum tx, recovers the sender via ECDSA, populates derived metadata. Associate transactions are handled here.
3. **Address derivation** — for Cosmos-signed txs, derives the EVM address from the public key and sets up mappings.
4. **Basic validation** — init code size, non-negative value, intrinsic gas.
5. **Signature/nonce verification** — validates chain ID and nonce. CheckTx uses pending nonce logic for mempool ordering; DeliverTx requires exact match.
6. **Fee validation** — checks against base fee and minimum fee, executes gas purchase, stores any fee surplus.
7. **Gas metering** — sets the Sei gas meter using the converted EVM gas limit.
```
