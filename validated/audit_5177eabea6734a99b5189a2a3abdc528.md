## Analysis

The external report's core broken invariant: **an arbitrary minimum-amount gate on a withdrawal path with no partial-withdrawal or top-up escape hatch, causing already-owned value to become permanently stuck.** The closest real analog in Hyperbridge is the relayer fee-withdrawal flow in `pallet-ismp-relayer`, and it is actually a stronger case than the original report because — unlike GiantPool's ETH deposit, which a user can top up — a relayer has **no way at all to add funds** to a given `(StateMachine, address)` fee balance except by delivering more messages to that specific destination.

### Title
Relayer minimum-withdrawal threshold can permanently strand already-accrued, already-claimed fees - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` requires the relayer's accrued balance for a specific destination `StateMachine` to be at least `MinimumWithdrawalAmount` (default $10-equivalent, governance-adjustable per chain via `set_minimum_withdrawal`) before it will dispatch the payout request: [1](#0-0) 

This mirrors the reported `GiantPoolBase.withdrawETH` pattern of gating a withdrawal on an unrelated minimum-amount check. Here it is worse: the balance being gated is not a fresh deposit the user controls, it is the result of an **irreversible on-chain proof-of-delivery** recorded via `accumulate()`, which permanently marks the underlying `RequestCommitments[...].claimed = true` the moment the fee is credited: [2](#0-1) 

### Finding Description
- `Fees<T>` is a `StorageDoubleMap<StateMachine, address, U256>` — a per-destination-chain ledger of what a relayer is owed: [3](#0-2) 
- The only way this balance grows is via `accumulate()`, which verifies delivery proofs and, in the same call, marks the source-chain commitment as `claimed` so it can never be reprocessed: [4](#0-3) 
- `withdraw()` operates on a **single `dest_chain`** at a time and requires the entire per-chain balance to clear the threshold before it will dispatch anything; there is no partial-withdrawal path and no cross-chain merge of balances: [5](#0-4) 
- Governance can independently raise the threshold per state machine at any time via `set_minimum_withdrawal`, retroactively stranding balances that were previously withdrawable: [6](#0-5) 

Because the balance is keyed strictly per destination `StateMachine` and the only credit path (`accumulate`) both consumes the balance and permanently marks the source commitment claimed, a relayer whose deliveries to a given destination never generate enough cumulative fee to cross the (possibly admin-raised) threshold has **no recourse whatsoever** to retrieve funds it has already earned and that Hyperbridge has already recorded as owed to it.

### Impact Explanation
This is a loss/lock-of-funds condition on already-settled relayer rewards — falling squarely under the accepted "stealing or loss of funds" impact category. Once a commitment is accumulated, its value is removed from the reprocessable state (claimed=true) but can become permanently unreachable in `Fees<T>` if it never crosses `MinimumWithdrawalAmount` for that specific `dest_chain`, with no deposit/top-up or partial-withdrawal mechanism to rescue it.

### Likelihood Explanation
No malicious actor, relayer, or admin action is required for the ordinary case — this triggers naturally for any relayer that only occasionally/lightly serves a lower-traffic or low-fee destination chain. It is guaranteed to be reachable by an honest, unprivileged relayer through normal use of the public `accumulate_fees`/`withdraw_fees` extrinsics, and is made worse by the fact that `set_minimum_withdrawal` (governance-only, but externally observable) can retroactively increase the bar above previously-accrued balances.

### Recommendation
Remove the blanket "must clear minimum" gate on `withdraw()` in favor of either:
1. Allowing withdrawal of any nonzero `available_amount` (drop the check, matching the original report's fix), or
2. Supporting a caller-specified withdrawal amount up to `available_amount` (no floor), or
3. Providing a governance/relayer-triggered "sweep" that lets sub-threshold balances be merged/paid out regardless of the configured minimum.

### Proof of Concept
1. Relayer delivers a single low-fee message to destination chain `X` and calls `accumulate_fees` with a valid `WithdrawalProof`; this credits `Fees::<T>::get(X, relayer) = $1` and marks the source `RequestCommitments` entry `claimed = true` (irreversible) — [7](#0-6) .
2. Relayer calls `withdraw_fees` for `dest_chain = X`. `available_amount` ($1) is compared against `min_withdrawal_amount(X).unwrap_or(MinWithdrawal::get())` (default $10); the call reverts with `Error::NotEnoughBalance` — [1](#0-0) .
3. If chain `X` is low-traffic (or governance later raises the threshold for `X`), the relayer never accumulates another delivery to `X`, so the $1 remains in `Fees<T>` forever with no deposit path, no partial-withdraw path, and no way to reprocess the already-`claimed` source commitment.
