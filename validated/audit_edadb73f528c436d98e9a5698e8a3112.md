### Title
Background fetch can silently fast-forward a branch that is mid-rebase, corrupting the branch ref out from under an in-progress rebase - ([File: app/src/lib/stores/helpers/background-fetcher.ts], [File: app/src/lib/git/for-each-ref.ts], [File: app/src/lib/git/fetch.ts])

### Summary
The original report's core invariant is: *a guard exists on the user-facing "repair" action (repay), but the underlying state mutation (interest accrual) is never paused, so the guarded action becomes unreachable while the unguarded mutation keeps moving the ground state toward an unrecoverable outcome.* The same shape exists in GitHub Desktop: the periodic `BackgroundFetcher` and `fastForwardBranches` routine are gated only by a "push/pull/fetch in progress" flag, never by whether a rebase/cherry-pick/merge operation (`conflictState` / `multiCommitOperationState`) is active on the same repository. Because the "current branch" exclusion used to decide which local branches are eligible for silent fast-forwarding relies on `%(HEAD)` symbolic-ref matching, it fails to exclude the branch being rebased once `HEAD` is detached (which is exactly the state Desktop puts the repo in while a rebase is in progress).

### Finding Description
`BackgroundFetcher.performAndScheduleFetch` runs unconditionally on a timer as long as `shouldPerformFetch` returns true; it has no awareness of `IChangesState.conflictState` or `multiCommitOperationState`. [1](#0-0) 

The fetch it triggers goes through `_fetch` → `performFetch`, whose only concurrency guard is `withPushPullFetch`, which checks `state.isPushPullFetchInProgress` — nothing related to rebase/merge/cherry-pick state. [2](#0-1) 

After the actual `fetch`, `performFetch` unconditionally calls `this.fastForwardBranches(repository)`, which computes "eligible" branches via `getBranchesDifferingFromUpstream` and then rewrites their refs with `git fetch . --stdin`. [3](#0-2) [4](#0-3) 

The exclusion of the "current branch" from that fast-forward set depends on `%(HEAD)` returning `*` for the branch ref that HEAD symbolically points to: [5](#0-4) 

During a rebase, Desktop's own rebase-flow documentation confirms `HEAD` becomes detached and the target branch is not checked out again until the rebase completes or is aborted: [6](#0-5) 

Because a detached `HEAD` does not symbolically point at `refs/heads/<branch>`, `%(HEAD)` will not report `*` for the branch under rebase, so `getBranchesDifferingFromUpstream` does **not** exclude it. If the branch being rebased still has commits from its pre-rebase tip diverging from a newer upstream tip (e.g. an attacker pushes new commits to the tracked remote, or a compromised/MITM'd git remote/proxy serves altered ref data during the periodic background fetch that fires mid-rebase), the subsequent `fastForwardBranches` call will force the local `refs/heads/<branch>` ref to match the (possibly attacker-influenced) upstream ref — while `git rebase` machinery in `.git/rebase-merge`/`REBASE_HEAD` is still relying on the pre-rebase tip recorded in `RebaseConflictState.originalBranchTip`. [7](#0-6) 

None of `withPushPullFetch`, `withIsCommitting`, or the rebase/multi-commit-operation state machine in `app-store.ts` cross-check each other before this ref rewrite happens. [8](#0-7) 

### Impact Explanation
This falls into "silent corruption of what the user commits or pushes": the branch pointer that the in-progress rebase (or cherry-pick) is tracking can be moved by a background network operation the user never initiated and cannot see or cancel, based on ref data supplied by a remote/proxy that is attacker-controlled per the allowed threat model (malicious or compromised git remote/proxy response). When the rebase later finishes, Desktop updates the branch ref based on stale assumptions (`originalBranchTip`/`baseBranchTip`) captured at rebase start, so the final state of the branch can silently diverge from what the user intended to commit, potentially discarding commits or splicing in attacker-supplied history without any error surfaced to the user.

### Likelihood Explanation
This requires no local/physical access, no admin rights, and no pre-existing malware — only that the victim has an active periodic background fetch (default-on) against a repository whose remote/proxy is attacker-influenced, and starts a rebase/cherry-pick that takes long enough (large history, conflict resolution pause, etc.) for the next scheduled background fetch tick (or a manually triggered fetch) to fire during that window. This is a plausible, if narrow, timing window rather than a certainty, and I was not able to trace the exact downstream rebase-completion code (`multi-commit-operation` finalization) in this pass to confirm the precise on-disk corruption outcome — that would need to be verified with a live repro before treating this as fully confirmed.

### Recommendation
Gate both `BackgroundFetcher`'s scheduled runs and `fastForwardBranches`'s ref-rewriting on the presence of an active `conflictState`/`multiCommitOperationState` (rebase, merge, cherry-pick) for the repository, and additionally exclude from `getBranchesDifferingFromUpstream` any branch referenced by `.git/rebase-merge`/`.git/rebase-apply`/`CHERRY_PICK_HEAD`, not just the symbolically-current `HEAD` branch. As with the smart-contract recommendation, avoid making the "should I mutate ref state" computation a precursor that can itself be safely skipped — checking for an in-progress multi-commit operation should be a cheap, always-available guard independent of any interest/ref calculation.

### Proof of Concept
1. Clone a repo with a remote pointing at an attacker-controlled/MITM'able proxy or server.
2. Start an interactive/long rebase of `feature` onto `main` in Desktop (`HEAD` becomes detached; `refs/heads/feature` still exists at its pre-rebase tip).
3. While the rebase is paused on a conflict, have the attacker-controlled remote update `refs/heads/feature` upstream (or otherwise cause `origin/feature` to differ from local `feature`).
4. Wait for (or trigger) the next scheduled `BackgroundFetcher` tick / manual fetch; `performFetch` → `fastForwardBranches` → `getBranchesDifferingFromUpstream` fails to exclude `feature` (HEAD is detached, not symbolically on `feature`) and force-updates `refs/heads/feature` to the attacker-supplied upstream sha via `git fetch . --stdin`.
5. Complete or abort the rebase in Desktop; observe that the resulting `feature` state/reflog reflects the injected upstream content rather than the branch state the user began rebasing, with no error or warning shown.

Note: step 4/5's exact end-to-end corruption behavior depends on rebase-finalization code not fully traced in this session; a Devin session with full repo access should verify by instrumenting `RebaseConflictState` finalization against a concurrently-updated `refs/heads/<branch>`.

```typescript
export async function fastForwardBranches(
  repository: Repository,
  branches: ReadonlyArray<ITrackingBranch>
): Promise<void> {
  if (branches.length === 0) {
    return
  }

  const refPairs = branches.map(branch => `${branch.upstreamRef}:${branch.ref}`)

  await git(
    [
      'fetch',
      '.',
      // Make sure we don't try to update branches that can't be fast-forwarded
      // even if the user disabled this via the git config option
      // `fetch.showForcedUpdates`
      '--show-forced-updates',
      // Prevent `git fetch` from touching the `FETCH_HEAD`
      '--no-write-fetch-head',
      // Take branch refs from stdin to circumvent shell max line length
      // limitations (mainly on Windows)
      '--stdin',
    ],
    repository.path,
    'fastForwardBranches',
    {
      // Fetch exits with an exit code of 1 if one or more refs failed to update
      // which is what we expect will happen
      successExitCodes: new Set([0, 1]),
      env: {
        // This will make sure the reflog entries are correct after
        // fast-forwarding the branches.
        GIT_REFLOG_ACTION: 'pull',
      },
      stdin: refPairs.join('\n'),
    }
  )
}
```

```markdown
## Encountering conflicts

Once the `git rebase <upstream> <branch>` has completed Desktop inspects the
output returned by `git`. The rebase will end up in one of two states:

 - the commits from the target branch were applied cleanly, and the reference
   associated with the target branch now points  to the rewritten history on top
   of the base branch.
 - the rebase could not complete because one of the commits had conflicts when
   it was applied to the base branch, and the user needs to resolve these
   conflicts if the user wishes to resolve them

This section will focus on the second scenario, and what Desktop does to surface
this context to the user to help them figure out how to resolve conflicts.

When a rebase is in a conflicted state, the `.git` directory has
a bunch of helpful context to help the user orient themselves and to figure out
what is next.

#### Is a rebase in progress?

The `.git/REBASE_HEAD` file exists when the rebase is stopped because of
conflicts, and contains the commit ID of the current patch that cannot be
applied cleanly to the working directory

#### Details about the rebase

The information about what changes are being rebased can be identified found
from a few files:

 - `.git/rebase-merge/head-name` - the name of the target branch associated with
    the current rebase - may be prefixed with `refs/heads/`
```
