### Title
Deserialized `ReceivedOutput` value/outpoint consistency is never checked, letting a forged output corrupt fee/change math and produce permanently invalid signed transactions — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`ReceivedOutput::read` (in `networks/bitcoin/src/wallet/mod.rs`) deserializes three independent fields — `offset`, `output` (`TxOut`), and `outpoint` — from untrusted bytes without verifying that `output` is actually the output referenced by `outpoint`. `SignableTransaction::new` then trusts `input.output.value` for all balance, fee, and change calculations, and `SignableTransaction::multisig` only checks that the `script_pubkey` derives from the key offset — never the value or the outpoint linkage. This is the Serai analog of the unchecked `transferFrom`: the code assumes the "received" claim succeeded and builds consensus-invalid transactions / wrong change amounts on top of it.

### Finding Description
In `ReceivedOutput::read`, `Secp256k1::read_F`, `TxOut::consensus_decode`, and `OutPoint::consensus_decode` are decoded independently and assembled into `ReceivedOutput { offset, output, outpoint }` with no check that `outpoint` actually resolves to `output` on-chain.

`SignableTransaction::new` then uses `input.output.value.to_sat()` as ground truth:

- `input_sat` is summed from `input.output.value` (send.rs:175) and used for the `NotEnoughFunds` check (send.rs:215).
- The change amount is computed as `input_sat.checked_sub(payment_sat + fee_with_change)` (send.rs:228).

`multisig` validates only the `script_pubkey` against `offset.group_key()` (send.rs:277); the `value` and the `outpoint`/`output` pairing are never verified. At signing, `Prevouts::All(&self.tx.prevouts)` commits the forged `TxOut` values into each Taproot sighash (send.rs:375–390).

### Impact Explanation
- If a forged `ReceivedOutput` carries an inflated `value`, `SignableTransaction::new` computes change/leftover that does not exist, emitting a change output funded by phantom sats. Because `SIGHASH_DEFAULT`/`Prevouts::All` commits to the inflated amount, every input signature is invalid — the transaction can never confirm, and the produced change is fictional.
- If the value is deflated, the transaction still produces invalid signatures and fails.
- In either case a signing round completes "successfully" (each `schnorr.complete` returns `Ok`) yet yields an unbroadcastable transaction, mirroring the original bug's "function assumes the transfer succeeded → stuck funds" pattern.

### Likelihood Explanation
Requires untrusted bytes reaching `ReceivedOutput::read` and then `SignableTransaction::new`/`multisig` — i.e., the caller accepts `ReceivedOutput`s from a source other than its own `Scanner::scan_transaction`. `scan_transaction` builds `ReceivedOutput`s from the real chain (mod.rs:205–211) and is safe; the vulnerability exists specifically in the serialized/deserialized path, which is an explicitly exposed public API.

### Recommendation
Bind the `output` to the `outpoint`: either (a) have callers re-fetch the `TxOut` for each `outpoint` from the chain/RPC rather than trusting the serialized `TxOut`, or (b) store only `(offset, outpoint)` in the serialized form and resolve the output at spend time. At minimum, document that `ReceivedOutput::read` must only consume bytes produced by `serialize` on data originally obtained from `scan_transaction`/`scan_block`.

### Proof of Concept
```rust
// Construct a genuine output via scan, then tamper before serialization.
let mut output: ReceivedOutput = scanner.scan_transaction(&tx).remove(0);
// Attacker rewrites the serialized TxOut value to a huge amount
let mut bytes = output.serialize();
// ... patch the TxOut value field in `bytes` to u64::MAX ...
let forged = ReceivedOutput::read(&mut &bytes[..]).unwrap();

// SignableTransaction trusts forged.output.value for funding math
let stx = SignableTransaction::new(
    vec![forged], &payments, Some(change_script), None, fee_rate,
).unwrap();
// multisig passes (script_pubkey still matches), signatures are produced,
// but every sighash commits to a prevout value that doesn't exist on chain:
// the completed Transaction is consensus-invalid and can never confirm.
```
