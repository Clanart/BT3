### Title
Hunk-merge line-index desync in `expandTextDiffHunk`/`mergeDiffHunks` can cause wrong lines to be staged/discarded - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The Panoptic bug is a class of "silent accounting corruption": a counter used to track state (`removedLiquidity`) drifts from reality due to an arithmetic edge case, and later consumers of that counter (burns) act on the wrong value without any error being raised. The closest verifiable analog in this codebase is the `unifiedDiffStart`/`unifiedDiffEnd` line-index bookkeeping that `DiffSelection`, `patch-formatter.ts`, and the diff-expansion code all rely on to map a UI line selection back to an actual diff line when staging (`formatPatch`) or discarding (`formatPatchToDiscardChanges`) changes. When hunks are merged during "expand hunk" operations (`mergeDiffHunks` in `app/src/ui/diff/text-diff-expansion.ts:29-76`), the index recomputation for hunks *after* the merged pair is derived from `numberOfNewDiffLines`, a value that is adjusted ad-hoc (`numberOfNewDiffLines - 1` for merges) rather than recomputed structurally from the actual new line array lengths.

### Finding Description
`DiffSelection` (`app/src/models/diff/diff-selection.ts:41-320`) stores selection state purely as a `Set<number>` of "diverging" absolute line indices with no knowledge of what those indices actually correspond to — it trusts the caller to supply consistent indices. Both the interactive diff UI (`app/src/ui/diff/side-by-side-diff.tsx:1335-1354, 1386-1402`) and the patch generator (`app/src/lib/patch-formatter.ts:143-144, 266-267`, `const absoluteIndex = hunk.unifiedDiffStart + lineIndex`) key off `hunk.unifiedDiffStart`/`unifiedDiffEnd` to translate between "row in the rendered diff" and "line to select/patch."

`expandTextDiffHunk` (`app/src/ui/diff/text-diff-expansion.ts:170-400`) mutates this indexing when a user expands context (a repo-controlled action, since the number/size of hunks and surrounding file content come entirely from the cloned/fetched repository's file contents and the diff Git produces for it). When expansion causes a merge with an adjacent hunk (`shouldMergeWithAdjacent`, lines 219-236, 333-350), the code computes:

```
numberOfNewDiffLines = updatedHunkLines.length - hunk.lines.length
...
numberOfNewDiffLines = numberOfNewDiffLines - 1   // one less line: merged hunk header
```

and then reindexes every hunk after the merge point using this single scalar offset (`hunk.unifiedDiffStart + numberOfNewDiffLines`, lines 375-376). This offset is not derived from a full recomputation of `updatedHunk.lines.length` relative to the sum of the two original hunks' lengths; it is `(new expansion lines) - 1`. If a malicious/crafted upstream file causes the "adjacent" hunk to already be the bottom dummy hunk in some code paths, or if `mergeDiffHunks` is invoked with hunks whose line counts were computed under a different assumption than the `-1` correction accounts for (e.g., due to `isAdjacentDummyHunk` interacting with `shouldMergeWithAdjacent` in edge combinations not covered by existing tests), the `previousHunksEndIndex`/`followingHunksStartIndex` slicing (lines 336-337 vs 339-340, asymmetric for up vs down expansion) combined with the flat `numberOfNewDiffLines` offset can desynchronize `unifiedDiffStart`/`unifiedDiffEnd` for hunks beyond the merge point from the actual position of their lines in the reconstructed diff text (`getDiffTextFromHunks`, lines 19-27, which just concatenates hunk lines positionally — the source of truth).

Once `unifiedDiffStart` for a later hunk is off relative to the true position of its lines in the rebuilt diff, any selection the user makes on lines in that later hunk (checkbox clicks, drag-select, "discard line") is stored under the wrong absolute index in `DiffSelection`. `patch-formatter.ts` then uses that same (now-inconsistent) `unifiedDiffStart` to decide `isSelected(absoluteIndex)` per line when building the patch that is fed to `git apply --cached` (`app/src/lib/git/apply.ts:80-81`) or to `discardChangesFromSelection`. There is no invariant check anywhere that `unifiedDiffStart` for hunk *n* actually equals the cumulative line count of hunks `0..n-1`; the value is just carried forward arithmetically, exactly like the `unchecked { removedLiquidity += chunkLiquidity }` in the Panoptic report — an accounting field that is trusted without re-derivation from ground truth.

### Impact Explanation
If the offset desyncs, the effect is silent corruption of what the user commits or discards: a checkbox the user believes selects "line X" actually selects a different line (in a different hunk), so `mintTokenizedPosition`'s Desktop analogue — `applyPatchToIndex` / `discardChangesFromSelection` — stages or discards content the user did not intend, with no error surfaced. This matches the explicitly valid impact category "silent corruption of what the user commits or pushes," and the attacker-controlled input is the content of a cloned/fetched repository (its file contents and resulting diff/hunk structure), which is exactly the kind of untrusted external input the task scopes as valid.

### Likelihood Explanation
This requires no special repo permissions — only that the user clone/open a repository containing a file whose diff structure triggers the specific hunk-expand-and-merge code path, then use the "expand hunk" UI followed by partial line selection in the affected downstream hunk. This is a normal, expected user interaction (expanding context around a change is a documented feature), so the "unnatural user steps" bar is not raised. However, I could not construct or run a concrete reproduction (no test harness access), and existing unit tests in `text-diff-expansion-test.ts`/`patch-formatter-test.ts` exercise many expansion/merge scenarios, so it's uncertain whether the specific combination that breaks the invariant is actually reachable or is already implicitly prevented by the `shouldMergeWithAdjacent`/`isAdjacentDummyHunk` guards. This is a suspected latent-invariant issue rather than a confirmed exploit.

### Recommendation
- Recompute `unifiedDiffStart`/`unifiedDiffEnd` for every hunk after an expansion/merge by summing `lines.length` of all preceding hunks from the rebuilt `newHunks` array, rather than propagating a manually adjusted scalar offset (`numberOfNewDiffLines`) forward.
- Add an assertion/invariant check (at least in development/test builds) that for every hunk, `unifiedDiffStart` equals the sum of `lines.length` of all previous hunks in the final `newHunks`/`diff.hunks` array, and that `unifiedDiffEnd - unifiedDiffStart + 1 === lines.length`. Fail loudly (throw) rather than silently applying a wrong patch.
- Add targeted unit tests combining `expandTextDiffHunk` "down" expansion that merges with an already-merged/short adjacent hunk followed immediately by partial `withLineSelection`/`formatPatch` on a hunk beyond the merge point, asserting the generated patch touches exactly the intended source lines.

### Proof of Concept
Could not be executed (no runtime access in this session). Suggested manual reproduction for a follow-up session:
1. Craft a text file with three change hunks such that hunks 2 and 3 are close enough (`distanceToPrevious <= DefaultDiffExpansionStep`) to be merge-eligible when hunk 1 is expanded down, and hunk 3 is far enough from hunk 2 to remain separate before expansion.
2. In `SideBySideDiff`, expand hunk 1 downward until it triggers `shouldMergeWithAdjacent` with hunk 2 (verify via `getHunkHeaderExpansionType`/`expandTextDiffHunk` return value).
3. After the merge, select a single added/deleted line inside hunk 3 (the hunk after the merged pair) via `withLineSelection`.
4. Call `formatPatch`/`formatPatchToDiscardChanges` with that selection and diff `assert` the resulting patch's hunk header and line content against the actual file line the user visually selected in the row list; a mismatch demonstrates the desync.
