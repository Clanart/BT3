Confirmed: there is no `removeSafeDirectory` or "untrust repository" function anywhere in the codebase — only `addSafeDirectory` exists, with no corresponding revoke path.

### Title
Path-scoped "Trust Repository" consent is permanent and unrevocable, silently re-applied to future untrusted content at the same path - (File: `app/src/lib/git/config.ts`)

### Summary
GitHub Desktop's unsafe-repository flow mirrors the `MutualConsent` bug class: a one-time trust decision, once granted, is persisted forever with no in-app way to revoke it, and it is not bound to the specific repository identity or content that triggered the prompt — only to a literal filesystem path. Just as the audited `MutualConsent` modifier lets one party's earlier "yes" be replayed against a later, different proposal, Desktop's `safe.directory` trust exception lets a decision made for one repository's content be silently replayed against whatever different, potentially attacker-controlled, content later occupies that same path.

### Finding Description
When Desktop detects a repository whose directory is owned by a different user than the current one, `getRepositoryType` returns `{ kind: 'unsafe', path }` [1](#0-0)  and the UI (`AddExistingRepository`, `MissingRepository`) offers a "Trust Repository" action [2](#0-1) .

Clicking it calls `addSafeDirectory(path)`, which appends the path to the **global**, machine-wide `safe.directory` Git config list: [3](#0-2) 

```
export async function addSafeDirectory(path: string) {
  ...
  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```

This consent has three properties that reproduce the report's broken invariant:
1. **It never expires and cannot be revoked from the UI.** There is no `removeSafeDirectory`, "untrust", or equivalent function anywhere in the app — trust is a one-way ratchet, exactly like `MutualConsent`'s lack of a revoke function.
2. **It is keyed only on a path string, not on repository identity or content.** Git's dubious-ownership check itself only compares current directory ownership against the config value; once a path is whitelisted, Git will never re-flag it, no matter what commits/hooks/content exist there afterward.
3. **The consent silently authorizes future, different objects at the same location.** If the path is later reused (e.g., repo removed and a different repo cloned to the same path, a symlink swapped, a shared machine, a re-mounted network share — Desktop explicitly added UNC/network-share support for this in `2.9.15`), any subsequently-placed repository at that path is treated as trusted without a new prompt, since `getRepositoryType` will simply return `kind: 'regular'` and never surface the unsafe warning again.

This is the direct analog of the report's exploitation path: the borrower/lender "5% now, 5.1% later, 5% forever" replay works because consent is not scoped to the exact proposal. Here, "trust this directory" (proposal A) persists and is silently reused to implicitly bless "whatever git repository exists at this path now" (proposal B), which the user never explicitly reviewed.

### Impact Explanation
An attacker who can eventually control the content at a path the user previously trusted (shared workstation, mounted network drive, container/VM snapshot reuse, or any workflow where a path is repurposed) gets automatic execution of Git hooks/config for that new, attacker-controlled repository, because Desktop/Git will never re-prompt for that path. This satisfies the "attacker controls a cloned/fetched repository ... result is code execution" impact category: the whole purpose of the unsafe-ownership check is to gate against exactly this "different owner may have written malicious hooks" scenario, and the permanent, path-only consent defeats that gate for future content.

### Likelihood Explanation
Moderate. It requires a path to be reused by different repository content after being trusted once — plausible on shared/multi-user machines, CI-style ephemeral checkout directories reused by Desktop, or network shares (a scenario Desktop explicitly built support for). No admin rights, malware, or leaked credentials are needed; the user only needs to have legitimately trusted a directory once in the past, which is an expected, non-contrived interaction with the app's own unsafe-repo warning.

### Recommendation
- Add a UI/action to remove entries from `safe.directory` (an "untrust" counterpart to `addSafeDirectory`), and prompt users to re-confirm trust when Desktop notices that the actual repository content/identity at a previously-trusted path has changed (e.g., different `.git` object or remote URL) rather than trusting the path unconditionally.
- Consider not persisting the exception globally/forever by default — surface it as a per-repository, revocable setting inside Desktop's own repository list rather than delegating entirely to Git's global config, and re-validate at least the origin/remote fingerprint bound to the path before treating it as still trusted.

### Proof of Concept
1. User clones/opens repository R1 at path `P` (owned by another user on a shared machine or mounted share) and clicks "Trust Repository", calling `addSafeDirectory(P)` [4](#0-3) . This writes `P` into `~/.gitconfig`'s `safe.directory` list permanently.
2. User removes R1 from Desktop (or it's deleted) but the global Git config entry for `P` is never cleaned up (no revoke code path exists in `app/src/lib/git/config.ts`).
3. Later, an attacker (a different user account on the shared machine, or a compromised network share) places a different, malicious Git repository R2 at the same path `P`, containing malicious hooks/config.
4. When the user reopens or re-adds a repository at path `P`, `getRepositoryType(P)` runs `git rev-parse` [5](#0-4) ; because `P` is already in the global `safe.directory` list, Git returns `kind: 'regular'` instead of `kind: 'unsafe'`, so Desktop never re-prompts the user and treats R2 as if it were still the originally-trusted R1, allowing R2's hooks/config to execute silently.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
