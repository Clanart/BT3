### Title
Global, endpoint-unscoped `cachedRepoRulesets` cache lets a ruleset ID collision from one GitHub host silently mask real repo-rule enforcement on another repository - (File: app/src/lib/stores/app-store.ts)

### Summary
The external report's bug class is "an identifier that is not sufficient/unique for the lookup it's used for is used to fetch security-relevant config, causing the wrong config to be applied." In GitHub Desktop, the closest analog is `AppStore`'s `cachedRepoRulesets` cache, which is keyed **only by the numeric GitHub repo-ruleset `id`**, with no scoping to the account/endpoint or owner/repo the ruleset actually belongs to.

### Finding Description
`AppStore` maintains a single process-wide cache: [1](#0-0) 

populated in `_updateCachedRepoRulesets`, keyed purely by `rs.id`: [2](#0-1) 

`refreshBranchProtectionState` fetches the slim rulesets for the *current* `owner/name` repo, then only fetches full ruleset detail for ids **not already present** in the cache — it never checks whether the cached entry for that id actually belongs to the current repository or endpoint: [3](#0-2) 

The stale/foreign cached entry is then handed to `parseRepoRules`, which uses `ruleset.current_user_can_bypass` to decide whether required-signature, commit-message, branch-name, and creation rules are enforced or bypassable for the *current* repo/commit: [4](#0-3) 

GitHub ruleset IDs are database row IDs that are only guaranteed unique **within a single GitHub instance** (dotcom vs. each self-hosted GHES/GHE instance has its own ID sequence). Desktop supports multiple simultaneously signed-in accounts across dotcom, ghe.com, and arbitrary GHES servers (`AccountsStore`/`Account.endpoint`), and this cache is shared across all of them with no per-endpoint namespacing. Existing guards (`useRepoRulesLogic`, `hasWritePermission`) only decide *whether* to query rules at all — they do nothing to validate that a cached ruleset id actually corresponds to the repository being evaluated, so once `cachedRepoRulesets.has(id)` returns true for the wrong entry, the real ruleset for the current repo is never fetched, and the stale, foreign-repo data is used silently.

The identical unscoped cache is reused for the interactive branch/rename-name check path as well: [5](#0-4)  — same `cachedRepoRulesets` object is passed straight into `parseRepoRules` and into the bypass check loop.

### Impact Explanation
This corrupts what the app tells the user about the safety of what they are about to commit/push: it can make required-signed-commits, commit-message-pattern, branch-name-pattern, or "cannot bypass" rules for RepoB *silently appear satisfied/bypassable* because a ruleset entry with the same numeric ID was previously cached from RepoA on a different GHES/GHE/dotcom endpoint (attacker-controlled if the attacker owns/administers that other repo/instance and can set `current_user_can_bypass: "always"` on a ruleset with a colliding low ID). Because Desktop uses this client-side state to decide what warning banners to show before commit/push (e.g., "you can bypass this required signature rule"), a user can be misled into skipping precautions they would otherwise take. This is a "silent corruption of the safety context of what the user commits/pushes" primitive, driven entirely by attacker-controlled repository/ruleset objects fetched over the network — no local access, admin rights, or social engineering beyond normal use of Desktop with multiple accounts/orgs is required.

### Likelihood Explanation
Requires the user to have Desktop signed into ≥2 GitHub endpoints/orgs with repo rulesets whose numeric IDs collide (plausible since GHES instances restart IDs from 1, and even dotcom repos across orgs are commonly interacted with in the same Desktop session), and for the attacker to control one such ruleset. This is a realistic but non-trivial precondition (multi-tenant Desktop sessions are common in enterprise use, and low-numbered ruleset IDs on GHES are far more likely to collide than dotcom's global counter). This lowers likelihood relative to a universally-triggerable bug, but the same broken invariant (unscoped global cache keyed by a non-globally-unique ID) is unconditionally present in the code regardless of collision odds.

### Recommendation
Key `cachedRepoRulesets` (and its consumers) by a composite of `(endpoint, id)` instead of bare `id`, e.g. a `Map<string, IAPIRepoRuleset>` keyed by `` `${gitHubRepo.endpoint}:${rs.id}` ``, and pass the endpoint through `_updateCachedRepoRulesets`, `refreshBranchProtectionState`, and `checkBranchNameRules`/`parseRepoRules` call sites so a cache hit can never resolve to a ruleset belonging to a different GitHub host.

### Proof of Concept
1. Sign into Desktop with two GitHub accounts: one on `github.mycompany-a.ghe.com` (attacker-influenced) and one on `github.mycompany-b.ghe.com` (victim org with a "required signed commits" ruleset, id `7`, `current_user_can_bypass: "never"`).
2. Open/select a repo on org A whose ruleset id happens to also be `7` (attacker sets `current_user_can_bypass: "always"` on it). Desktop calls `refreshBranchProtectionState` → `_updateCachedRepoRulesets` and stores `cachedRepoRulesets.set(7, {..., current_user_can_bypass:"always"})` (`app-store.ts:1524-1577`).
3. Switch to the victim repo on org B. `refreshBranchProtectionState` sees `this.cachedRepoRulesets.has(7)` is already true (`app-store.ts:1536`) and skips fetching org B's real ruleset 7.
4. `parseRepoRules` computes `enforced` from the stale org-A entry (`current_user_can_bypass === 'always'` → `'bypass'`) instead of org B's actual `'never'` (`repo-rules.ts:86-87`), so the required-signed-commits warning is shown as bypassable (or suppressed) even though the org's real policy forbids it.

export async function checkBranchNameRules(
  branchName: string,
  accounts: ReadonlyArray<Account>,
  repository: Repository,
  cachedRepoRulesets: ReadonlyMap<number, IAPIRepoRuleset>
): Promise<IBranchRuleError | null> {
  if (
    accounts.length === 0 ||
    !isRepositoryWithGitHubRepository(repository) ||
    branchName === ''
  ) {
    return null
  }

  const account = getAccountForRepository(accounts, repository)

  if (account === null || !useRepoRulesLogic(account, repository)) {
    return null
  }

  const api = API.fromAccount(account)
  const branchRules = await api.fetchRepoRulesForBranch(
    repository.gitHubRepository.owner.login,
    repository.gitHubRepository.name,
    branchName
  )

  // filter the rules to only the relevant ones and get their IDs. use a Set to dedupe.
  const toCheck = new Set(
    branchRules
      .filter(
        r =>
          r.type === APIRepoRuleType.Creation ||
          r.type === APIRepoRuleType.BranchNamePattern
      )
      .map(r => r.ruleset_id)
  )

  // there are no relevant rules for this branch name
  if (toCheck.size === 0) {
    return null
  }

  // check for actual failures
  const { branchNamePatterns, creationRestricted } = await parseRepoRules(
    branchRules,
    cachedRepoRulesets,
    repository
  )

  const { status } = branchNamePatterns.getFailedRules(branchName)

  if (creationRestricted !== true && status === 'pass') {
    return null
  }

  // check cached rulesets to see which ones the user can bypass
  let cannotBypass = false
  for (const id of toCheck) {
    const rs = cachedRepoRulesets.get(id)

    if (rs?.current_user_can_bypass !== 'always') {
      cannotBypass = true
      break
    }
  }
