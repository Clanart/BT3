### Title
OP_RETURN `data` output excluded from weight/vbytes and fee calculation, so the signed transaction pays a lower fee rate than requested and may fall below the relay minimum — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Derby report where `exchangeRate()` unconditionally returned `1` (making the dependent `rewardPerLockedToken` always zero), `SignableTransaction::new` computes `needed_fee` and the transaction weight from a synthetic transaction that never includes the OP_RETURN output derived from the caller-supplied `data`. The data output therefore contributes zero to the fee calculation, so the transaction's effective fee rate is silently lower than `fee_per_vbyte` — the same bug class of a fixed/omitted term zeroing out part of a value computation.

### Finding Description
`SignableTransaction::new` pushes an `OP_RETURN` output to `tx_outs` when `data` is `Some` (send.rs:194-202), but both weight/fee computations only consider `payments` and an optional `change`:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (send.rs:204) — the `data` output is not in `payments` and the synthetic `Transaction` built in `calculate_weight_vbytes` (send.rs:68-99) has no OP_RETURN output.
- The change path (send.rs:224-235) recomputes with `Some(&change)` but still omits `data`.

Consequences in the same function:

1. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) undercounts by roughly `data.len() + ~11` bytes (up to ~91 bytes / ~364 WU for the allowed 80-byte payload).
2. The `TooLowFee` check (send.rs:211) compares `fee_per_vbyte` against `DEFAULT_MIN_RELAY_TX_FEE` using the understated `vbytes`, so a caller passing `fee_per_vbyte = 1` with a large `data` produces a transaction whose *actual* sat/vbyte rate is below the 1 sat/vbyte relay minimum.
3. The `MAX_STANDARD_TX_WEIGHT` check (send.rs:241) uses `weight` that excludes the data output, so a near-limit transaction can exceed standardness once signed.

Since the actual fee paid is `sum(inputs) - sum(outputs)` (`fee()`, send.rs:138-141) and outputs include the zero-valued OP_RETURN, the real fee equals the understated `needed_fee`, spread over a larger transaction — the effective rate is strictly below what the caller specified.

### Impact Explanation
An unprivileged caller who controls the `data` parameter (e.g., an InInstruction/OP_RETURN payload on a bridge send) can cause the multisig to produce and sign a transaction with a real fee rate below the Bitcoin relay minimum. The signed transaction will not propagate through standard relay, leaving the spent inputs' funds locked in an unconfirmed transaction — funds moved into an output that is effectively not spendable via normal relay, matching the "incorrect formula silently zeroes out part of a computation, causing value loss" impact of the source report. Even when relay succeeds, every transaction with `data` systematically underpays versus the intended fee rate.

### Likelihood Explanation
The `data` path exists for user-supplied payloads (`SignableTransaction::new(.., data, fee_per_vbyte)`); anyone able to attach data to a payment (up to 80 bytes) triggers it deterministically. The miscalculation is unconditional whenever `data.is_some()` — no attacker racing or special state is required. Severity is bounded (Medium): the shortfall is at most ~91 vbytes, so the transaction is only pushed below relay minimum when `fee_per_vbyte` is already near the floor; otherwise the impact is a reduced (not zero) fee rate.

### Recommendation
Include the `data`/OP_RETURN output in the synthetic transaction used by `calculate_weight_vbytes` — e.g., build `tx_outs` (payments + data + change) first and pass it into `calculate_weight_vbytes` instead of reconstructing outputs from `payments` alone. Also evaluate `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` against the final output set so the checks reflect the transaction actually signed.

### Proof of Concept
```rust
// networks/bitcoin, wallet tests
let inputs = vec![received_output];           // some ReceivedOutput
let data = vec![0xAA; 80];                     // maximum allowed payload

let with_data = SignableTransaction::new(
    vec![input.clone()], &payments, change.clone(), Some(data.clone()), 1,
).unwrap();
let without_data = SignableTransaction::new(
    vec![input], &payments, change, None, 1,
).unwrap();

// needed_fee does not increase despite ~91 extra serialized bytes
assert_eq!(with_data.needed_fee(), without_data.needed_fee());

// Yet the signed transaction is larger:
assert!(with_data.transaction().vsize() >
        without_data.transaction().vsize());
// effective rate = needed_fee / actual vsize < 1 sat/vbyte -> below relay minimum
```
With `fee_per_vbyte = 1` and an 80-byte payload, `TooLowFee` passes (computed `vbytes` excludes the OP_RETURN), while the broadcast transaction's true rate is `needed_fee / (vbytes + ~91)`, i.e., under 1 sat/vbyte — non-relayable under `DEFAULT_MIN_RELAY_TX_FEE`.
