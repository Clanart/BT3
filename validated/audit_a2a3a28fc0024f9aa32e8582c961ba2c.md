### Title
Referral rebates in `MasterMagpie._multiClaim` are computed on pre-forfeiture `totalReward` instead of the amount actually paid out, letting a self-referred attacker extract inflated MGP from the referral reward pool - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie._multiClaim` sums `vlMGPPoolAmount + mWOmPoolAmount + defaultPoolAmount` into `totalReward` *before* the vlMGP-pool portion is reduced by `_calExpireForfeit` inside `vlMGPBaseRewarder.queueMGP`, and passes this gross figure to `IReferralStorage(referral).trigger(_user, totalReward)`. Because `trigger` credits both referrer and referee `rewardAmount` proportionally to this gross amount, a user who forfeits some or all of a vlMGP-pool claim still generates full-value referral rebates, breaking the intended conservation between reward actually received and referral rebate paid.

### Finding Description
In `_multiClaim` [1](#0-0) , `vlMGPPoolAmount` is the *pre-forfeiture* claimable MGP for the vlMGP pool. It is forwarded to `_sendMGPForVlMGPPool`, which calls `IvlmgpPBaseRewarder(vlMGPRewarder).queueMGP(_amount, _account, _receiver)` with that same gross amount [2](#0-1) .

Inside `queueMGP`, `_calExpireForfeit` computes a `forfeitAmount` based on `vlMGP.getRewardablePercentWAD(_account)` and only transfers `rewardableAmount = _amount - forfeitAmount` to the receiver; the forfeited portion is redirected back into the rewarder's pool via `_queueNewRewardsWithoutTransfer` rather than paid to the user [3](#0-2) [4](#0-3) .

However, back in `_multiClaim`, `totalReward` was already fixed as `vlMGPPoolAmount + mWOmPoolAmount + defaultPoolAmount` (the gross, pre-forfeit figure) and is passed unmodified to `referral.trigger(_user, totalReward)` [5](#0-4) . `ReferralStorage.trigger` then computes `refererAmount` and `refereeAmount` as fixed percentages of this gross `_amount` and credits them into `refererInfo.rewardAmount` / `refereeInfo.rewardAmount`, which are later paid out in real MGP via `claimReward` (`MGP.safeTransfer(msg.sender, userInfo.rewardAmount)`) [6](#0-5) [7](#0-6) .

No existing check reconciles the amount used for `trigger` with the amount actually transferred out of `queueMGP`. `nonReentrant` on `_multiClaim` and `queueMGP` prevents reentrancy, but it does nothing to fix the accounting mismatch, since the two computations (`totalReward` in `MasterMagpie` and `rewardableAmount` in `vlMGPBaseRewarder`) are independent and never synchronized.

An unprivileged attacker can trigger this deterministically:
1. Deploy/control two addresses, A (referrer) and B (referee).
2. A calls `registerCode` to get a code; B calls `useCode` to link to A.
3. B stakes into the vlMGP pool through normal flows, then claims via `multiclaim`/`multiclaimSpec` at a time when `getRewardablePercentWAD(B)` is low (e.g., immediately after locking, before any vesting/rewardable period accrues), causing a large or 100% forfeiture on the vlMGP-pool claim.
4. `_multiClaim` still computes `totalReward` using the full pre-forfeit `vlMGPPoolAmount` and calls `referral.trigger(B, totalReward)`, crediting A and B rebates based on an amount B never actually received.
5. A and B call `claimReward()` on `ReferralStorage` to redeem real MGP tokens from the referral pool balance, disproportionate to what was truly earned/paid out.

### Impact Explanation
This is a direct conservation violation: referral rebates (real, transferable MGP) are minted/credited against a reward figure that was never fully paid to the referee, because part of it was forfeited and redirected elsewhere. This drains the shared referral incentive pool (`ReferralStorage`'s MGP balance) faster than intended and lets a self-referring attacker extract MGP disproportionate to the value actually created/distributed by their claim, which matches "direct theft of user/protocol funds" (excess referral MGP paid out relative to real reward transferred).

### Likelihood Explanation
Low capital and no special privileges are required: any EOA can register two addresses, set up a referral relationship between them, stake, and claim early to maximize forfeiture. This is repeatable across pools/epochs and does not require flash loans, front-running, or governance access — only a scenario where `getRewardablePercentWAD` yields a nonzero forfeiture on a vlMGP claim while a referral relationship is active for the claimer.

### Recommendation
Compute the `totalReward` passed to `referral.trigger` using the *actual* amount transferred to the user, not the pre-forfeiture gross figure. Concretely, have `_sendMGPForVlMGPPool`/`queueMGP` return the `rewardableAmount` actually paid out, and use that value (instead of the raw `vlMGPPoolAmount`) when accumulating `totalReward` in `_multiClaim`, so referral rebates are conserved against real disbursed rewards.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `vlMGPBaseRewarder`, `VLMGP`, `ReferralStorage`, and MGP token with standard wiring (referral set on `MasterMagpie`, `masterMagpie` set on `ReferralStorage`).
2. Address A calls `registerCode(codeA)`; Address B calls `useCode(codeA)`.
3. B stakes MGP into the vlMGP pool via `MasterMagpie`, then locks in `VLMGP` such that `getRewardablePercentWAD(B)` returns a value less than `1e18` (e.g., immediately after lock, before vesting).
4. B calls `multiclaim` (or `multiclaimSpec`) including the vlMGP pool staking token.
5. Capture: (a) actual ERC20 `Transfer` amount of MGP received by B from `vlMGPBaseRewarder.queueMGP` (the `rewardableAmount`), and (b) the `_amount` argument logged/inferable from `RefererRewardHarvested`/`RefereeRewardHarvested` events emitted by `ReferralStorage.trigger`.
6. Assert `refererAmount + refereeAmount` (derived from the trigger `_amount`) corresponds to a base amount strictly greater than the actual MGP transferred to B in step 5 whenever `forfeitAmount > 0`, demonstrating the referral rebate was computed on an inflated basis relative to funds actually distributed.

```text
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;

            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }
```

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
```
