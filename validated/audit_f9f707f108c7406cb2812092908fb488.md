### Title
Empty `getRewards` implementation permanently silences targeted reward claims - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.sol` is the default rewarder contract instantiated by `MasterMagpie` (`new BaseRewardPool(...)`, referenced in `rewards/MasterMagpie.sol`) and wired up for LP-staking pools through helpers such as `WombatStaking`, `WombatPoolHelper`, `WombatPoolHelperV2`, `AnkrBNBPoolHelper`, and `SimplePoolHelper`. Its `getRewards(address _account, address _receiver, address[] memory _rewardTokens)` function — the path an ordinary staker reaches via `MasterMagpie.multiclaimSpec` / `multiclaimFor` when specifying particular reward tokens — is an empty stub that performs no logic at all.

### Finding Description
In `rewards/BaseRewardPool.sol`: [1](#0-0) 

```
function getRewards(address _account, address _receiver, address[] memory _rewardTokens) override external {

}
```

Compare this to the working sibling implementations in `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`, and `vlMGPBaseRewarder.sol`, all of which correctly loop over `_rewardTokens`, apply the `updateReward`/`updateRewards` modifier, zero out `userRewards`, and transfer the tokens: [2](#0-1) 

`BaseRewardPool.getRewards` is called from `MasterMagpie._claimBaseRewarder` whenever a user passes a non-empty reward-token array through `multiclaimSpec`/`multiclaimFor`/`multiclaimOnBehalf`: [3](#0-2) 

Because the function body is empty:
- It never applies `_updateFor`/`updateReward`, so `userRewards`/`userRewardPerTokenPaid` are not refreshed for the specified account.
- It never transfers any ERC20 reward tokens to `_receiver`.
- It does not revert, so the transaction silently "succeeds" while doing nothing.

This is functionally the same bug class described in the report: reward accounting exists (`queueNewRewards`/`donateRewards` deposit rewards into the pool, `earned`/`allEarned` correctly compute the pending amount), but the specific withdrawal path exposed to users (`getRewards`, the targeted-claim variant) does not move funds — it is a no-op stand-in for a withdrawal function that should exist but effectively doesn't.

### Impact Explanation
Reward accounting itself is not corrupted (since nothing updates state, the user's rewards keep accruing via `earned()`/`rewardPerToken()`), so a user can eventually recover their rewards by calling `multiclaim` (which internally calls the working `getReward` — the "claim all" variant) instead of `multiclaimSpec`/`multiclaimFor` with an explicit token list. This limits impact to a griefing/no-op UX bug rather than a guaranteed permanent freeze, because an alternate unprivileged code path (`multiclaim`) exists to retrieve the same rewards.

### Likelihood Explanation
Any staker interacting with a `BaseRewardPool`-backed pool (the default rewarder deployed by `MasterMagpie`/Wombat pool helpers) who calls `multiclaimSpec` or `multiclaimFor` with a non-empty `_rewardTokens` array for that pool will trigger the empty stub and receive nothing, with no revert to signal failure.

### Recommendation
Implement `getRewards` in `rewards/BaseRewardPool.sol` identically to the working pattern in `BaseRewardPoolV2.sol`/`mWOMSVBaseRewarder.sol`/`vlMGPBaseRewarder.sol`: apply an `updateRewards`-style modifier, iterate `_rewardTokens`, zero `userRewards[rewardToken][_account]`, and `safeTransfer` the reward to `_receiver`, emitting `RewardPaid`.

### Proof of Concept
1. A user stakes LP tokens in a pool whose rewarder is a `BaseRewardPool` instance (deployed via `MasterMagpie`'s pool-add flow / Wombat pool helpers).
2. Rewards accrue via `queueNewRewards`/`donateRewards`.
3. The user calls `MasterMagpie.multiclaimSpec([stakingToken], [[rewardTokenAddr]])`.
4. This reaches `_claimBaseRewarder`, which calls `rewarder.getRewards(_account, _receiver, _rewardTokens)` since `_rewardTokens.length > 0` [4](#0-3) .
5. `BaseRewardPool.getRewards` executes its empty body [1](#0-0) : the transaction succeeds, no tokens are transferred, and `userRewards` is left unmodified/stale relative to what the user believed they claimed.

    function getRewards(address _account, address _receiver, address[] memory _rewardTokens) override
        external
        onlyMasterMagpie
        updateRewards(_account, _rewardTokens)
    {
        uint256 length = _rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = _rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                _sendReward(rewardToken, _account, _receiver, reward);
            }
        }
    }

    /// @notice Harvest reward token in BaseRewarder for an account. NOTE: Baserewarder use user staking token balance as source to
    /// calculate reward token amount
    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
