### Title
Soulbound `ReputationAsset` transfer restriction is bypassed by `pallet-hyper-fungible-token`'s programmatic burn/escrow path - (File: `parachain/runtimes/nexus/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
The Nexus runtime enforces that the `ReputationAsset` is soulbound — holders must never be able to move it out of their account — by rejecting every *dispatched* `pallet_assets` call (`transfer`, `transfer_keep_alive`, `transfer_all`, `approve_transfer`, `transfer_approved`) that targets the reputation asset ID via `ReputationCallFilter`. The runtime's own comment explicitly acknowledges the gap: "Programmatic `fungible::Mutate` (mint / burn from runtime pallets) bypasses dispatch and is therefore unaffected." `pallet-hyper-fungible-token`'s `send` extrinsic calls `Assets::transfer` (escrow) or `Assets::burn_from` directly through the `fungibles::Mutate`/`Transfer` trait, not through a dispatched `RuntimeCall::Assets::*` call, and is therefore invisible to `ReputationCallFilter` — exactly the class of bypass described in the external report, where the transfer-hook/policy path is enforced on the normal transfer route but not on the burn/mint bridge route.

### Finding Description
`ReputationCallFilter` is defined to keep reputation tokens non-transferable at the extrinsic dispatch layer: [1](#0-0) 

The filter only inspects `RuntimeCall::Assets(...)` variants and explicitly does not (and cannot) see calls made by other pallets through the `fungibles::Mutate`/`Transfer` trait implementation, as its own doc comment states.

`pallet-hyper-fungible-token::send` moves a caller-specified `asset_id` cross-chain by directly invoking `<T as Config>::Assets::transfer(...)` (when the asset is locally native) or `<T as Config>::Assets::burn_from(...)` (when it is not), both of which are programmatic `fungibles` trait calls on the same `Assets` pallet instance used by the runtime: [2](#0-1) 

Because these calls are made in-runtime (not as a dispatched `RuntimeCall`), `BaseCallFilter`/`ReputationCallFilter` never runs against them. If the reputation asset ID is ever reachable as a valid `asset_id` in this pallet's `TokenContracts`/`NativeAssets` storage (i.e., anyone with `CreateOrigin` registers it, or it is registered for any legitimate purpose), an unprivileged holder can call `send` with `asset_id = ReputationAssetId` to move their soulbound balance into the pallet's custody account (native branch) or burn it locally while minting a transferable wrapped representation on the destination chain (non-native branch) — recreating exactly the "burn/remint path bypasses the transfer policy" pattern from the report.

### Impact Explanation
Reputation tokens are documented as soulbound and consumed only by `pallet-collator-manager`'s per-session reset — the entire collator-incentive/slashing accounting model assumes a holder cannot relocate this balance. If the bridge burn/escrow path bypasses that invariant, a holder can extract the token onto another chain as a freely transferable asset (via the destination `WrappedHyperFungibleToken`/HFT contract), defeating the soulbound guarantee and letting reputation-linked incentive logic be manipulated or laundered across chains — a logic attack on host-management/incentive execution, matching the impact gate's "logic attacks" / "unauthorized transaction or execution" categories.

### Likelihood Explanation
This requires only an ordinary signed `send` call, with no privileged, relayer, prover, or governance role needed. The blocking condition is whether the reputation asset ID is actually registered as a bridgeable `asset_id` in `pallet-hyper-fungible-token`'s storage on the Nexus runtime — I could not confirm within the available searches whether this registration exists or is reachable by a non-privileged actor, since the pallet's asset-registration call and its origin gating in the Nexus runtime configuration were not fully retrieved. If registration is admin-gated and the reputation asset is never registered, the path is currently latent rather than exploitable; the runtime comment nonetheless flags this exact class of bypass as a known, intentional gap in the current design (mirroring Securitize's "acknowledged, intentional" stance in the source report), which is why it merits mitigation.

### Recommendation
Do not rely solely on `BaseCallFilter` for asset-level transfer restrictions. Instead, add an explicit check inside `pallet-hyper-fungible-token::send` (and any other pallet that performs programmatic `fungibles::Mutate`/`Transfer` calls) that rejects protected/soulbound asset IDs before escrowing or burning, or expose a shared "is this asset transfer-restricted" hook that both the call filter and the bridge pallet consult. Alternatively, ensure the reputation asset ID can never be registered into `TokenContracts`/`NativeAssets` for `pallet-hyper-fungible-token`, and add a runtime test asserting that `send` fails for the reputation asset ID.

### Proof of Concept
1. Confirm (or, as a precondition, have `CreateOrigin` register) `ReputationAssetId` as a valid `asset_id` in `pallet-hyper-fungible-token`'s `TokenContracts`/`NativeAssets` storage for some destination chain.
2. As an unprivileged holder of `ReputationAsset`, call `Ismp::send` (or the equivalent `HyperFungibleToken::send` extrinsic) via a normal signed extrinsic — this bypasses `ReputationCallFilter` since it is not a `RuntimeCall::Assets(...)` variant.
3. Observe the reputation balance is transferred to the pallet's escrow account (or burned) via `<T as Config>::Assets::transfer`/`burn_from` in [3](#0-2) , succeeding despite `ReputationCallFilter` normally rejecting any direct `Assets::transfer` extrinsic targeting the same asset ID, as documented in [1](#0-0) .
4. On the destination chain, the minted/wrapped token is freely transferable, completing the soulbound-bypass.

/// Reputation tokens are soulbound — credited via the incentive pallets
/// and consumed only by `pallet-collator-manager`'s per-session reset.
/// The holder must not be able to send them anywhere, so this filter
/// rejects every dispatched `Assets` call that could move balance out
/// of a holder's account when the target asset is the reputation asset.
/// Programmatic `fungible::Mutate` (mint / burn from runtime pallets)
/// bypasses dispatch and is therefore unaffected.
///
/// `force_transfer` is left allowed because it already requires the
/// asset's admin origin (privileged escape hatch). `cancel_approval` is
/// allowed because `approve_transfer` is blocked, so there shouldn't be
/// any approvals to cancel; if one slips through, letting the holder
/// undo it is strictly safer.
pub struct ReputationCallFilter;
impl Contains<RuntimeCall> for ReputationCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		let rep = ReputationAssetId::get();
		match call {
			RuntimeCall::Assets(
				pallet_assets::Call::transfer { id, .. } |
				pallet_assets::Call::transfer_keep_alive { id, .. } |
				pallet_assets::Call::transfer_all { id, .. } |
				pallet_assets::Call::approve_transfer { id, .. } |
				pallet_assets::Call::transfer_approved { id, .. },
			) => *id != rep,
			_ => true,
		}
	}
}
