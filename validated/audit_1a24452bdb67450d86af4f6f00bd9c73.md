### Title
Unrestricted outbound fetch to attacker-controlled Mirror/DataLayer URLs enables SSRF against DataLayer client nodes - ([File: chia/data_layer/download_data.py])

### Summary
The `MIRROR_PUZZLE_HASH` coin mechanism lets **any wallet owner** publish arbitrary URL strings on-chain for **any existing DataLayer store `launcher_id`**, with no ownership check tying the mirror-creating coin to the store owner. Every other node subscribed to (or syncing) that store will pull these URLs via `dl_get_mirrors`/`update_subscriptions_from_wallet()` and issue outbound HTTP requests to them through `http_download()` / `download_file()` in `chia/data_layer/download_data.py`, with no validation that the resolved host/IP is not an internal/private address. This mirrors the bug class in BIT-gitlab-2021-39867 (CVE-2021-39867): an untrusted, attacker-supplied URL is fetched by a service backend without restricting the destination, enabling SSRF.

### Finding Description
`create_mirror_puzzle()` in `chia/wallet/db_wallet/db_wallet_puzzles.py:90-94` defines a fixed, well-known puzzle hash (`MIRROR_PUZZLE_HASH`). `DataLayerWallet.create_new_mirror()` in `chia/data_layer/data_layer_wallet.py:687-704` lets any wallet spend its own coins to create a coin with this puzzle hash whose memo is `[launcher_id, *urls]` [1](#0-0)  — the `launcher_id` is attacker-supplied and is **not required to be a store owned by the caller**; it can name any store id that exists on chain. `get_mirror_info()` in `chia/wallet/db_wallet/db_wallet_puzzles.py:97-110` parses any coin spend that creates a `MIRROR_PUZZLE_HASH` coin and extracts `launcher_id`/URLs regardless of who spent the coin [2](#0-1) .

Any DataLayer client (or another peer's wallet) that later queries `dl_get_mirrors` for that `launcher_id` gets back the attacker's URLs (`DLGetMirrors` RPC, `chia/wallet/wallet_rpc_api.py:3247-3253`). `DataLayer.update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979-985`) copies those URLs directly into `DataStore` subscriptions with no filtering, and `fetch_and_validate()` (`chia/data_layer/data_layer.py:606-705`) later iterates these `server_info.url` values and calls `insert_from_delta_file()` → `download_file()` → `http_download()` in `chia/data_layer/download_data.py:110-169,298-346`. `http_download()` performs an unauthenticated `aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)` [3](#0-2)  with no IP/hostname allow-listing, no rejection of private/loopback/link-local ranges (e.g. `127.0.0.1`, `169.254.169.254`, RFC1918 ranges), and no re-validation after DNS resolution. The plugin downloader path (`download_file`, lines 147-168) similarly forwards attacker-controlled `server_info.url` as JSON to a local plugin, which itself performs further requests (e.g. `s3_plugin_service.py` `download()` uses `urlparse(url)` on attacker data before fetching).

This matches the underlying bug class of CVE-2021-39867: a service accepts an attacker-controlled URL/host as input and performs an outbound fetch on it without constraining the destination, allowing the requester to make the victim's server originate requests to arbitrary (including internal) network locations.

### Impact Explanation
An unprivileged user who can submit a normal spend bundle (creating a `MIRROR_PUZZLE_HASH` coin with any `launcher_id` memo and any URL memo, e.g. pointing at `http://127.0.0.1:<internal_rpc_port>/...`, cloud metadata endpoints, or other internal-only services reachable from a victim's DataLayer node) can cause every other participant's DataLayer service that syncs that store to issue outbound HTTP requests to attacker-chosen destinations. This is a classic SSRF: it can be used to probe/attack internal services co-located with a DataLayer node (local RPC ports, other internal HTTP services, cloud metadata services), potentially leaking secrets or triggering unintended actions on those internal services, and can also be leveraged for resource exhaustion/DoS against victim nodes (repeated retries per `ServerInfo` ban-timer logic).

### Likelihood Explanation
Likelihood is high for any node that runs a DataLayer service and subscribes to third-party stores (the default sync behavior described in `.cursor/context/data-layer.md`): mirror creation only requires a standard signed spend of the attacker's own coins for a small fee, no special privilege, no relationship to the target store's ownership, and the resulting mirror is picked up automatically by `periodically_manage_data()`/`update_subscription()` for any subscriber.

### Recommendation
- Validate/allow-list mirror and subscription URLs before use: reject `http(s)` URLs resolving to private/loopback/link-local/multicast ranges (and re-check the resolved IP at connection time, not just the literal string, to defeat DNS rebinding) in `http_download()` (`chia/data_layer/download_data.py`) and in the S3/plugin downloader paths.
- Consider requiring mirror coins to be created only for stores the spender owns/controls, or otherwise binding mirror publication rights to store ownership.
- Add configuration to opt out of automatically following on-chain mirror URLs, or require explicit user allow-listing of mirror hosts before the DataLayer service will fetch from them.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror` (`DLNewMirror(launcher_id=<victim_store_id>, amount=1, urls=["http://127.0.0.1:19999/", ...internal target...], fee=...)`) via `chia/wallet/wallet_rpc_api.py:3255-3274`, creating a `MIRROR_PUZZLE_HASH` coin memoing the victim store's `launcher_id` and the malicious URL — no ownership of `victim_store_id` required.
2. Once confirmed on chain, any node's DataLayer service that subscribes to `victim_store_id` calls `update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979-985`), pulling the malicious URL into its local `DataStore` subscription table.
3. On the next sync cycle, `fetch_and_validate()` (`chia/data_layer/data_layer.py:606-705`) selects the malicious `server_info.url` and calls `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py`), causing the victim node to issue an outbound GET to the attacker-chosen internal address.

```python
def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```
