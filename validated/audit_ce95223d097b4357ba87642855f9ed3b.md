### Title
Unbounded `maxBuffer: Infinity` on `encoding: 'buffer'` Git invocations allows remote memory exhaustion via a malicious diff/blob - (File: app/src/lib/git/core.ts)

### Summary
The `git()` wrapper in `app/src/lib/git/core.ts` sets `maxBuffer: options?.encoding === 'buffer' ? Infinity : kStringMaxLength` as its default execution option. [1](#0-0) 
Any call site that requests `encoding: 'buffer'` without separately overriding `maxBuffer` therefore has **no cap at all** on how much stdout data the underlying `exec` (dugite/`child_process`) will accumulate in memory before returning. This is architecturally the same defect as the Stratum bug: a byte stream sourced from untrusted/attacker-influenced input (in this case, a `git diff`/`git show` invocation against blob content that originates from a cloned/fetched remote repository) is buffered without a size limit, and any size validation happens only *after* the entire buffer has already been collected in memory.

### Finding Description
Several diff/blob-reading functions call `git(...)` with `encoding: 'buffer'` and do not pass an explicit `maxBuffer`, so they inherit the `Infinity` default:

- `getWorkingDirectoryDiff` — `git(args, repository.path, 'getWorkingDirectoryDiff', { successExitCodes, encoding: 'buffer' })` [2](#0-1) 
- `getCommitRangeDiff` — `git(args, repository.path, 'getCommitsDiff', { encoding: 'buffer', expectedErrors: ... })` [3](#0-2) 
- `getResolutionDiff` — `git(args, repository.path, 'getResolutionDiff', { successExitCodes: new Set([0, 1]), encoding: 'buffer' })` [4](#0-3) 
- `getFilesDiffText` — `git(args, repository.path, 'getFilesDiffText', { successExitCodes, encoding: 'buffer' })` [5](#0-4) 
- `getBlobContents` (used for image previews via `getBlobImage`) — `git(['show', ...], repository.path, 'getBlobContents', { successExitCodes: new Set([0, 1]), encoding: 'buffer' })`, again with no `maxBuffer` [6](#0-5) 

All of these ultimately produce a `Buffer` (`stdout`) that is only checked for size *after* the fact, e.g. `isValidBuffer(buffer)` in `buildDiff`/`getResolutionDiff` compares against `MaxDiffBufferSize = 70e6` [7](#0-6)  — but that check happens on the already-fully-materialized buffer, exactly like the Stratum fix's problem: "the buffer had no size limit ... this occurred before ... any check."

By contrast, the codebase clearly demonstrates the *correct* pattern elsewhere: `getPartialBlobContentsCatchPathNotInRef` explicitly passes `maxBuffer: length` so that Node's/dugite's execution machinery enforces the cap as data streams in and throws an `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` error that is caught and truncated via `coerceToBuffer(e.stdout)`. [8](#0-7)  This shows the maintainers know the correct bounded pattern but did not apply it consistently to `getBlobContents`, `getWorkingDirectoryDiff`, `getCommitRangeDiff`, and `getResolutionDiff`.

The attacker-controlled input reaching this unbounded path is a blob's raw content or a diff's raw patch text stored inside a git object database that the user has cloned/fetched/checked out — content fully controlled by whoever hosts the remote (or a malicious proxy/MITM tampering with fetched objects). Opening the Changes/History view, viewing a commit's diff, previewing an image, or GitHub Desktop's own AI conflict-resolution diff path (`getResolutionDiff`) will shell out to `git diff`/`git show` and buffer the entire (attacker-sized) object into a single Node.js `Buffer` in the renderer/main process with no upper bound.

### Impact Explanation
An attacker who controls a repository the victim clones or fetches (or a git remote/proxy that can inject a large blob/tree) can commit an extremely large file (gigabytes) and rely on the fact that GitHub Desktop routinely runs `git diff`/`git show` against changed/committed files to render the Changes and History views, as well as the Copilot conflict-resolution feature. Because `maxBuffer` is `Infinity`, Node's child_process layer will keep accumulating stdout chunks without any early termination, allowing a single file/diff view to consume attacker-chosen amounts of memory in the Electron process, leading to renderer/app crash or host-wide memory exhaustion — a legitimate remote-triggered DoS/crash primitive distinct from the excluded "DoS/rate-limit-only" server-side category, because it is a client-side unbounded-allocation flaw reachable purely by viewing content from an untrusted repository (no local access, no malware, no credentials needed).

### Likelihood Explanation
Likelihood is moderate-to-high: viewing diffs/commits/images is a completely ordinary user action performed automatically as soon as a user opens a cloned/fetched repository and looks at the Changes or History tab, or opens the Copilot merge-conflict UI. No unusual user steps are required beyond normal repository browsing, and the attacker only needs to control the content of a single tracked file in the repository (or a MITM position for the git transport). The existing `isValidBuffer`/`MaxDiffBufferSize` guard does not stop the underlying attack because it inspects the buffer *after* it has already been fully read into memory — it protects the UI from *rendering* an oversized diff, not from *allocating* it.

### Recommendation
Pass an explicit, bounded `maxBuffer` (e.g., a few hundred MB, matching or tighter than `MaxDiffBufferSize`) to every `git()` call that uses `encoding: 'buffer'` and currently omits `maxBuffer`, specifically `getWorkingDirectoryDiff`, `getCommitRangeDiff`, `getResolutionDiff`, `getFilesDiffText`, and `getBlobContents`/`getBlobImage`. Mirror the existing `getPartialBlobContentsCatchPathNotInRef` pattern: set a hard cap and gracefully handle the resulting `ERR_CHILD_PROCESS_STDIO_MAXBUFFER`/`isMaxBufferExceededError` by truncating or surfacing an "unrenderable/too large" diff state, rather than defaulting to `Infinity`.

### Proof of Concept
1. Attacker creates a public repository containing one file with several GB of unique content (or a huge patch-worthy text file) and commits it.
2. Victim clones the repository with GitHub Desktop and selects the commit or working-directory change containing that file (or the file is auto-selected on repository open).
3. GitHub Desktop calls `getWorkingDirectoryDiff`/`getCommitRangeDiff`/`getBlobContents` with `encoding: 'buffer'` and no `maxBuffer` override [2](#0-1) , causing the spawned `git diff`/`git show` process's entire stdout to be buffered in a single Node `Buffer` with no cap (`maxBuffer: Infinity` from the `git()` default) [1](#0-0) .
4. Memory usage of the Electron main/renderer process grows unbounded in proportion to the attacker-chosen file/diff size, well before `isValidBuffer`'s 70MB check is ever reached, resulting in an OOM crash or severe slowdown of the app.

**Note on verification:** I was unable to inspect the `dugite`/`child_process` exec implementation itself in the indexed code to confirm the exact low-level buffering mechanism (no `node_modules/dugite` source was retrievable via search), so the claim that `maxBuffer: Infinity` disables Node's built-in buffer-size enforcement is based on the well-documented behavior of `child_process.exec`'s `maxBuffer` option combined with the codebase's own explicit use of `maxBuffer: length` + `isMaxBufferExceededError` elsewhere as the intended mitigation pattern. If more certainty is needed, a Devin session with full filesystem access to `node_modules/dugite` could confirm the exact runtime behavior.

export async function getPartialBlobContentsCatchPathNotInRef(
  repository: Repository,
  commitish: string,
  path: string,
  length: number
): Promise<Buffer | null> {
  const args = ['show', `${commitish}:${path}`]

  return git(args, repository.path, 'getPartialBlobContentsCatchPathNotInRef', {
    maxBuffer: length,
    expectedErrors: new Set([GitError.PathExistsButNotInRef]),
    encoding: 'buffer',
  })
    .then(r =>
      r.gitError === GitError.PathExistsButNotInRef ? null : r.stdout
    )
    .catch(e =>
      isMaxBufferExceededError(e) ? coerceToBuffer(e.stdout) : Promise.reject(e)
    )
