## Analysis Summary

The Pareto bug's core broken invariant is: **a shared pooled balance pays out claims without clearing/verifying the claimed entitlement's already-consumed state, letting the same underlying entitlement be paid out more than once (or be paid out of a pot that should belong to others).**

Searching for a local analog in fee/reward accounting across request, response, and timeout paths surfaced a concrete asymmetry in `EvmHost.sol`'s GET-request lifecycle handlers.

### Title
Relayer fee for a delivered GET response is never cleared from `_requestCommitments`, unlike the timeout path - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` pays the relayer the fee stored in `_requestCommitments[commitment].fee` on successful delivery, but never deletes that mapping entry afterward. [1](#0-0) 

Contrast this with the sibling GET-timeout handler, which explicitly deletes `_requestCommitments[commitment]` **before** doing anything else, precisely for replay protection: [2](#0-1) 

### Finding Description
`_requestCommitments[commitment]` is the single source of truth for a dispatched request's `FeeMetadata { sender, fee }`, set once at dispatch time: [3](#0-2) 

Both completion paths for a GET request — the success path (`dispatchIncoming(GetResponse,...)`) and the timeout path (`dispatchTimeOut(GetRequestTimeout,...)`) — read this same fee record to pay out a reward funded from the host's shared `feeToken()` balance (a pool that holds fees from *every* pending request across all users, not an escrow scoped to a single commitment). The timeout path treats "record still present" as its own replay guard and deletes it up front. The response path has no equivalent deletion: after paying the relayer, `_requestCommitments[commitment]` is left intact with the same non-zero `fee`. `_responseReceipts[commitment]` is written unconditionally (no prior "already set" check) right before the app callback, which is the comment-labeled "replay protection" but performs no read-then-guard against a prior receipt: [4](#0-3) 

Because the fee record for this commitment is never invalidated after a successful response delivery, any downstream code path that still treats a non-empty `_requestCommitments[commitment]` as "this request is still open and its fee is still payable" (which is exactly the state the timeout branch checks for before it will pay `meta.fee` back out and invoke `onGetTimeout`) can be satisfied a second time for the same commitment. This breaks the "commitment uniqueness and one-time receipt handling" invariant explicitly called out as required for request/response/timeout paths, because the state needed to prove "already settled" is asymmetric between the two completion branches instead of being unified.

### Impact Explanation
The exact corrupted value is `_requestCommitments[commitment].fee`, which remains truthy/non-zero after it has already been disbursed once. Since `feeToken()` balance on `EvmHost` is a shared pot funded by fees from all outstanding GET/POST requests (not a per-commitment escrow verified against total backing before payout — the same class of gap as Pareto's `requestRedeem` not checking `totalCollateralsScaled`), any double-consumption of a stale fee record drains funds that are actually earmarked for other, unrelated pending requests' relayer rewards or refunds. This is a direct violation of the "moved exactly once, only to the rightful beneficiary and amount" bounty pivot for relayer rewards/bridged fee balances.

### Likelihood Explanation
This requires the calling `IHandlerV2` (not shown/available in the indexed code for this session) to permit invoking the timeout branch for a commitment whose response was already successfully delivered, i.e., that the handler's own gating for the timeout proof path uses `_requestCommitments[commitment]` non-emptiness (rather than `_responseReceipts[commitment]` emptiness) as its "not yet settled" check. I was **not able to confirm or rule out** this specific handler-side gating logic within the available index, so the full double-payment exploit path (triggerable by an unprivileged relayer submitting both a valid response proof and a valid timeout proof for the same commitment) is a plausible but not fully closed-loop-verified reachability claim. What is confirmed directly from `EvmHost.sol` is the asymmetric bookkeeping itself: the success path is missing the same defensive deletion the timeout path performs, which is inconsistent with "one-time receipt handling" and is the root condition that would let such a double payment occur if the handler's pre-check doesn't independently close the gap.

### Recommendation
Delete `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse memory response, address relayer)` immediately after reading/using the fee, mirroring the pattern already used in `dispatchTimeOut`, so a settled commitment can never again be read as "fee still payable" by any other code path:
```solidity
uint256 fee = _requestCommitments[commitment].fee;
delete _requestCommitments[commitment];
if (fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
```
Additionally, `dispatchIncoming(GetResponse,...)` should explicitly guard against a pre-existing `_responseReceipts[commitment]` entry (revert if already set) instead of unconditionally overwriting it, so "replay protection" is an actual check rather than a same-slot overwrite.

### Proof of Concept
Not independently reproducible from the indexed code alone because the `IHandlerV2` implementation that gates which branch (`dispatchIncoming(GetResponse,...)` vs `dispatchTimeOut(GetRequestTimeout,...)`) can be invoked for a given proof, and under what commitment-state precondition, was not available in this session's index. The concrete, code-confirmed defect is the missing `delete _requestCommitments[commitment]` in the success path shown above at lines 841-847, contrasted with the deletion present at line 862 in the timeout path — a Devin session with full repository/handler access should trace `IHandlerV2`'s call sites into `dispatchIncoming`/`dispatchTimeOut` to confirm whether both branches can be satisfied for one commitment, and add a Foundry test that (1) delivers a valid `GetResponse` for a commitment, collecting the fee, then (2) submits a valid `GetRequestTimeout` state proof for the same commitment before/without the fix, asserting the fee is paid out a second time from the host's `feeToken()` balance.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
