### Title
`ThresholdKeys::read` accepts a maliciously crafted serialized key blob whose attacker-chosen verification shares redefine the reported `group_key` without consistency to the secret share - (File: crypto/dkg/src/lib.rs)

### Summary
The external report (CRI-O checkpoint restore: a maliciously structured serialized blob grants unintended control because deserialization skipped validation of internal consistency) maps onto Serai's `ThresholdKeys::read`. This function deserializes `t`, `n`, `i`, the interpolation method, the secret share, and `n` verification shares, then passes them to `ThresholdKeys::new`, which computes `group_key` solely as a weighted sum of the supplied verification shares for participants `1..=t`. No check anywhere verifies that `C::generator() * secret_share == verification_shares[i]` (i.e., that the loaded secret share actually corresponds to the loaded verification shares), so the group key derived from a crafted blob is entirely attacker-controlled.

### Finding Description
`ThresholdKeys::<C>::read` at `crypto/dkg/src/lib.rs:574-632` reads `n` arbitrary points via `Ciphersuite::read_G` (canonical, but identity-permitting) into `verification_shares`, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) only validates:

- `verification_shares.len() == n` and every key `<= n` (lines 355-365),
- `Interpolation::Constant` requires `t == n` (lines 367-374),
- `ThresholdParams::new` rejects `t == 0`, `n == 0`, `t > n`, `i > n` (`crypto/dkg/src/lib.rs:166-179`).

It then derives `group_key = sum_{i in 1..=t} verification_shares[i] * interpolation_factor(i, 1..=t)` (lines 376-378). Because `view()` later interpolates only over `included ⊆ 1..=n` and adds the ephemeral offset to `included[0]` (lines 463-533), the loaded structure is internally consistent for any signer set — the only thing never validated is that the deserialized `secret_share` matches `verification_shares[i]`, or equivalently that the claimed verification shares are the ones the DKG actually produced.

An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as an in-scope untrusted-byte sink; e.g., a "checkpoint"/key-backup restore path, mirroring the checkpoint-file vector of the advisory) supplies `verification_shares` of their choosing — e.g., `G * y_i` for known `y_i`. The resulting `ThresholdKeys` reports `group_key()` equal to a point whose discrete log the attacker knows, while the victim node's real `secret_share` is retained and used.

### Impact Explanation
The deserialized `ThresholdKeys` is self-consistent yet bound to an attacker-selected group key:

- The node will report/operate under a `group_key()` (and hence deposit address / external key) whose underlying secret the attacker controls, so funds "received" to that key are spendable by the attacker, not by the honest share.
- Alternatively, mixing a real `secret_share` with foreign `verification_shares` makes every FROST signature share the node produces verify against the wrong `Y_i` (or fail), a silent key-substitution rather than an honest error — the deserialization API returns `Ok`, indistinguishable from a genuine backup.
- For `Interpolation::Constant` (MuSig-style n-of-n), attacker-chosen coefficients are read at lines 607-613 and blindly applied in `interpolation_factor` (line 228), further decoupling the effective share from any committed value.

This is the same bug class as the advisory: structured data accepted at restore/deserialize time grants the crafter control over security-relevant state (there, node filesystem access; here, the threshold identity/group key a signer operates under).

### Likelihood Explanation
Reachability requires an attacker to supply bytes to `ThresholdKeys::read`, which is a storage/restore path rather than a live wire path — analogous in spirit to the checkpoint file in the CRI-O report (which required the checkpoint/restore feature to be exercised). Consistent with the original's Medium severity and `AC:H`, this is conditional on a deployment that accepts externally influenced key blobs. The cryptographic exploitation itself is deterministic: no collisions or races are needed, only the missing consistency check.

### Recommendation
In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. For `Interpolation::Lagrange`, additionally consider checking `n` verification shares are non-identity (`Curve::read_G` instead of `Ciphersuite::read_G`) and, for `Constant`, that coefficients are non-trivially bound to the claimed shares. This turns a crafted blob into a hard deserialization error instead of a silent key substitution.

### Proof of Concept
Conceptual: construct a buffer accepted by `ThresholdKeys::<C>::read` — valid `C::ID`, `t = n = 1`, `i = 1`, `interpolation = Lagrange` (tag `1`), an arbitrary scalar `s` as the secret share, and one verification share `Y = G * y` for attacker-known `y`. `ThresholdParams::new(1, 1, Participant(1))` passes; `group_key` becomes `Y` (Lagrange factor over the singleton set is 1). `read` returns `Ok` with `group_key() == G*y` although the embedded `s` has no relation to `y` — `complete()`-side consumers will treat `G*y` as this node's group key. Note: I was unable to confirm within the iteration budget which production caller feeds network-influenced bytes to `ThresholdKeys::read`; the impact claim holds wherever the deserialized `group_key()` is used to advertise a receive address or validate signatures.
