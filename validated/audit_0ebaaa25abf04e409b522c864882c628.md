### Title
Unauthenticated `InternalWithdraw` RPC allows bypassing the aggregator's verification-signature check on `Operator::withdraw` - ([File: core/src/rpc/operator.rs])

### Summary
`OptimismHubConnector.processMessageFromRoot()` had two paths reaching `_processMessage()`, where only the "fast path" verified the message's origin and the AMB-direct path did not, letting fraudulent messages be inserted. In this repository, the operator payout logic `Operator::withdraw` (`core/src/operator.rs:560`) is reachable via two distinct gRPC methods: `withdraw` (`core/src/rpc/operator.rs:193`), which checks `aggregator_verification_address` against an ECDSA `verification_signature`, and `internal_withdraw` (`core/src/rpc/operator.rs:169`), which performs no such check at all before calling the identical state-changing `self.operator.withdraw(...)`.

### Finding Description
`internal_withdraw` directly forwards to `Operator::withdraw` without any verification-signature check: [1](#0-0) 

By contrast, `withdraw` performs the ECDSA verification against `aggregator_verification_address` before calling the same underlying function: [2](#0-1) 

The proto explicitly documents that `InternalWithdraw` is intended "for operator's own use, so it doesn't include a signature from aggregator", while `Withdraw` is the one gated by the verification signature: [3](#0-2) 

`Operator::withdraw` itself only checks that the withdrawal UTXO matches Citrea's registered withdrawal and that the user's Schnorr signature over the payout input is valid — it never checks who called the RPC: [4](#0-3) 

The binding this is meant to enforce is: `caller-of-withdraw == aggregator/citrea-authorized-party` (when `aggregator_verification_address` is configured). `internal_withdraw` breaks that binding, since it lets any caller with gRPC access to the operator (i.e., anyone who is not a verifier/operator/aggregator, matching the "unprivileged-attacker" framing) trigger the exact same payout broadcast that `withdraw` gates behind an aggregator signature.

### Impact Explanation
This matches the "unauthenticated state-changing or broadcasting call" High-impact category: an attacker who can reach the operator's gRPC surface can call `InternalWithdraw` to force the operator to fund and broadcast a payout transaction (`fund_raw_transaction`/RBF send in `core/src/operator.rs:639-674`) for any withdrawal registered on Citrea, entirely bypassing the aggregator-authorization gate that `Withdraw` enforces. This does not require a verifier, operator, watchtower, or key compromise — only network/gRPC access to an operator node, which is the same class of access the `Withdraw` RPC is exposed to.

### Likelihood Explanation
Likelihood is high wherever `InternalWithdraw` is reachable by the same network parties that can reach `Withdraw` (e.g., over the same gRPC listener), since it requires no signature, no special role, and no race condition — just calling the RPC with valid withdrawal parameters (UTXO + user Schnorr signature), which an outside party could construct from any legitimately observed withdrawal request.

### Recommendation
Remove the unauthenticated `internal_withdraw` path from externally reachable gRPC surface (restrict to loopback/internal-only transport), or require the same `aggregator_verification_address` check inside `internal_withdraw` (or a shared internal-auth mechanism) before it delegates to `Operator::withdraw`, mirroring the fix pattern from the referenced report of removing the unchecked second path.

### Proof of Concept
1. An external caller obtains a valid `WithdrawParams` (withdrawal id, user Schnorr `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) for a withdrawal registered in Citrea's bridge contract — this data is not secret (it is the same data submitted to `Withdraw`, and is also visible in the Citrea withdrawal registration).
2. The caller sends this data directly to the operator's `InternalWithdraw` RPC instead of `Withdraw`.
3. `internal_withdraw` (`core/src/rpc/operator.rs:169-190`) skips the `aggregator_verification_address`/ECDSA check block present only in `withdraw` (`core/src/rpc/operator.rs:209-239`) and calls `self.operator.withdraw(...)` directly.
4. `Operator::withdraw` (`core/src/operator.rs:560`) only validates the Citrea-registered UTXO match and the user's payout-input signature, then funds and returns the payout transaction for broadcast — with no verification that the request came from the aggregator, exactly analogous to the AMB-direct `_processMessage()` path in the Optimism connector bug that skipped origin verification.

Note: I could not fully confirm from the index whether `InternalWithdraw` is actually exposed on a network-reachable listener versus a loopback-only "internal" RPC service in the deployed configuration — the doc-comment framing ("for operator's own use") suggests it may be intended as an internal-only endpoint. If it is documented/enforced as loopback-only at the transport layer, this would fall under the excluded "deployment ignoring documented configuration" category; verifying the actual listener/ACL configuration for `Internal*` RPCs would require inspecting deployment/transport-layer code not indexed here.
