### Title
C# ProtoJSON parser silently accepts numeric values for closed (proto2) enum fields without validating them against the enum's declared value set - (File: `csharp/src/Google.Protobuf/JsonParser.cs`)

### Summary
The Chainlink bug is fundamentally a data-integrity failure: a value returned by an external source is used without validating it against its full documented valid range (only a superficial sanity check — `price > 0` — is performed), causing the consuming application to silently accept and act on a semantically invalid value. The closest genuine analog in this protobuf checkout is the C# ProtoJSON parser's handling of numeric JSON values for **closed** (proto2-semantics) enum fields: `ParseSingleNumberValue` performs only a superficial "is this an integer" check (`CheckInteger`) and then explicitly, admittedly, skips validating that the number is one of the enum's declared values, unlike every other supported implementation (C++, Java, Python, upb) and unlike C#'s own binary-wire parsing path.

### Finding Description
For closed enums, the wire-format contract in this codebase is: an out-of-range/unknown numeric enum value must never be materialized into the strongly-typed field — it must be diverted to `UnknownFieldSet` (see the reference C++ implementation of binary parsing): [1](#0-0) 

The equivalent enforcement is present in every other ProtoJSON implementation examined:
- Java's `JsonFormat` explicitly branches on `enumDescriptor.isClosed()` and rejects unknown numeric values for closed enums: [2](#0-1) 
- Python's `json_format` rejects unknown numeric enum values when `field.enum_type.is_closed`: [3](#0-2) , confirmed by the conformance/unit test showing proto2 (closed) enums reject `12345` while proto3 (open) enums accept it: [4](#0-3) 
- The canonical C++ ProtoJSON parser calls `EnumNumberByName`/enum registry lookups that are enforced against the descriptor.

In contrast, C#'s `ParseSingleNumberValue` — the routine invoked when a JSON *number* is supplied for an enum field — does the opposite by design: [5](#0-4) 

The comment is explicit: *"Note that we deliberately don't check that it's a known value."* This means that for a closed enum field, an attacker-controlled ProtoJSON payload can set the field to **any** `int32` value, including values entirely outside the enum's declared/valid set — exactly analogous to Chainlink's price oracle accepting any value that merely passes the shallow `price > 0` gate instead of being validated against the full documented min/max band. The corresponding C# unit test demonstrates this concretely: passing the numeric value `100` for `ForeignEnum` (a proto2/closed-style enum) is accepted and materialized as `(TestProtos.ForeignEnum)100` without error: [6](#0-5) 

This diverges from the same library's own binary-parsing invariant (a closed enum's out-of-range values must not be stored as if valid — they belong in unknown fields) and from all sibling-language ProtoJSON implementations, which do perform this exact check (`isClosed()` / `is_closed` gating).

### Impact Explanation
Application code that trusts a strongly-typed enum field (e.g., a `switch` over all declared enum constants, or code that assumes the field's value is always one of the finite declared states) can silently receive an out-of-band integer disguised as that enum type when parsing untrusted ProtoJSON via C#. Depending on how the generated C# enum type and application logic interact with an undeclared numeric value (e.g., default-less switch statements, array/lookup-table indexing by enum ordinal, or security/authorization decisions keyed off enum identity), this can lead to incorrect business logic, bypassed default-deny branches, or undefined behavior — mirroring the "wrong price used because the out-of-range check that should have gated acceptance was missing" pattern from the Chainlink report. This is a logic/data-integrity defect rather than a memory-safety one, consistent with the character of the original finding (M-2, valid Medium).

### Likelihood Explanation
The condition is trivially reachable: any attacker who can submit ProtoJSON to a public C# `JsonParser.Parse`/`ParseJson` entry point (bounded, ordinary payload — no privileged access needed) can supply an arbitrary integer for any closed enum field and have it accepted, as directly demonstrated by the existing first-party test `EnumValid` with the `"100"` case. No malformed schema, plugin, or special permissions are required — this is a supported, documented public parsing API being fed a small, well-formed JSON number.

### Recommendation
Align the C# ProtoJSON numeric-enum path with the behavior already implemented in Java, Python, C++, and upb: when the target enum field is closed (proto2/legacy-closed semantics), validate the parsed integer against the enum's declared value set (e.g., via the field's `EnumType` value list) before accepting it, and reject (or route to unknown-fields handling per the `ignoreUnknownFields` setting) values that are not declared — removing the "we deliberately don't check" shortcut in `ParseSingleNumberValue` for the closed-enum case.

### Proof of Concept
Given a proto2 message with a closed enum field `ForeignEnum` (only having declared values such as `FOREIGN_FOO = 4`, `FOREIGN_BAR = 5`, `FOREIGN_BAZ = 6`):
```csharp
string json = "{ \"singleForeignEnum\": 100 }";
var parsed = TestAllTypes.Parser.ParseJson(json);
// parsed.SingleForeignEnum == (TestProtos.ForeignEnum)100
// No exception thrown, no unknown-field diversion — an undeclared enum value
// is now stored in a field application code treats as one of the finite,
// declared enum constants.
```
This exact scenario is codified in the existing repository test [6](#0-5) , and the intentional omission of the enum-membership check is documented in-line at [5](#0-4) .
