## Analysis

The reported bug class — untrusted, uncached `decimals()` reads being re-queried live and thus mutable intra-transaction — has a direct analog in Sei's EVM↔CosmWasm pointer bridge.

`CW20ERC20Pointer.sol` is an ERC-20-compatible facade that any user can deploy over an arbitrary CW20 contract via the pointer precompile, allowing EVM contracts to treat CosmWasm tokens as ERC-20s. Its `decimals()` implementation does **not** cache the token's decimals at pointer creation; instead it performs a live wasmd query on every single call: [1](#0-0) 

Compare this to the native-token pointer (`AddNative`), which reads `decimals` once from bank denom metadata and bakes it in as an **immutable constructor argument** of the generated ERC-20 contract: [2](#0-1) 

That immutability guarantee does not hold for the CW20 pointer path. Since CW20 contract deployment is permissionless (any CosmWasm user can instantiate one), an attacker can write a malicious CW20 contract whose `token_info` query handler returns a different `decimals` value depending on block height, an internal counter, or `execute` calls interleaved between queries — exactly the "EvilToken" pattern from the external report, just implemented in CosmWasm instead of Solidity. Any downstream EVM contract (DEX, lending protocol, price oracle, wrapper) that integrates the pointer as a standard ERC-20 and assumes `decimals()` is constant (as mandated by EIP-20 conventions) can be made to read two different `decimals()` values within the same transaction — e.g., once during a deposit/mint calculation and again during a valuation/withdrawal calculation — because each call triggers an independent wasmd query rather than returning a cached constant.

This mirrors the audit finding's exact root cause (repeated external calls to a "constant" that isn't actually enforced to be constant) and is reachable by an ordinary CosmWasm user deploying a token and an EVM contract caller invoking any downstream contract that composes with the pointer — no privileged or validator access required.

### Title
CW20-to-ERC20 pointer's `decimals()` performs a live, uncached wasmd query allowing a malicious CW20 to return inconsistent decimals intra-transaction - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer.decimals()` re-queries the underlying CW20 contract's `token_info` on every call instead of caching the value once at pointer creation, unlike the native-token pointer which bakes `decimals` in as an immutable constructor argument.

### Finding Description
The pointer precompile lets any CosmWasm user register a permissionless CW20 contract and get back an ERC-20-compatible EVM pointer contract for it via `AddCW20`, which only fetches `name`/`symbol` at creation time and does not cache `decimals`: [3](#0-2) 

Consequently, `CW20ERC20Pointer.decimals()` issues a fresh `WasmdPrecompile.query` against the underlying CW20 address on every invocation: [1](#0-0) 

Because CW20 contract instantiation and execution are permissionless CosmWasm operations, the attacker fully controls the query handler logic behind the `token_info` message. The attacker can make `decimals` depend on mutable contract state (e.g., an internal flag flipped by an `execute` message, block time, or call count), so two calls to `pointer.decimals()` within the same EVM transaction can legitimately return different values. This breaks the EIP-20 assumption — relied upon by essentially all downstream integrators (DEXes, lending markets, wrappers, price converters) — that `decimals()` is a fixed constant for the lifetime of the token.

This is the same root-cause pattern as the referenced report: an "external constant" that should be fixed and cached is instead fetched via an untrusted external call every time it's needed, and nothing in the codebase enforces or verifies that the returned value doesn't change between calls.

### Impact Explanation
Any Sei EVM contract that composes with a CW20 pointer as a normal ERC-20 (assuming standard immutable decimals) and reads `decimals()` more than once in a single transaction — e.g., once to normalize a deposit amount and again to compute a valuation, exchange rate, or withdrawal amount — can be manipulated into using two different decimal scalings within the same operation. Depending on the downstream contract's math, this can cause under/over-valuation of the token, leading to fund loss for the protocol or its users (e.g., minting more shares/collateral credit than deposited value, or withdrawing more than entitled). Since anyone can permissionlessly instantiate the malicious CW20 and register it as a pointer, and any EVM contract can be tricked or designed to integrate it, this qualifies as a High-severity fund-loss vector against composing protocols, not merely a display bug.

### Likelihood Explanation
Likelihood is contingent on a downstream EVM contract actually calling `decimals()` more than once per transaction and using the results in security-relevant math (a common pattern in DeFi integrations, e.g. reading decimals for input normalization then again for output/price calculation). Given that CW20 pointer contracts are explicitly designed to be composed with by third-party EVM contracts (that is their entire purpose), and CW20 deployment is fully permissionless, an attacker only needs to author one malicious CW20 contract and find (or build) a victim contract that reads `decimals()` twice — a realistic and unprivileged attack path.

### Recommendation
Cache `decimals` (and, ideally, `name`/`symbol`) once at pointer creation time in `AddCW20`, exactly as is already done for `AddNative`, and store it as an immutable value in the generated `CW20ERC20Pointer` contract rather than re-querying the CW20 contract on every `decimals()` call. If pointer decimals must reflect live CW20 state, document clearly that the pointer's decimals value is not guaranteed to be constant, so that integrators do not rely on the ERC-20 assumption of immutability.

### Proof of Concept
1. Attacker instantiates a malicious CW20 contract whose `token_info` query handler returns `decimals: 6` on odd-numbered calls and `decimals: 18` on even-numbered calls (tracked via a `Item<u64>` counter incremented on each query, or gated on `env.block.time`).
2. Attacker (or anyone) registers a pointer for this CW20 via the pointer precompile's `addCW20Pointer`, producing a `CW20ERC20Pointer` instance.
3. Attacker interacts with a victim EVM DeFi contract that accepts the pointer token as collateral/deposit and internally calls `IERC20Metadata(token).decimals()` twice in one transaction — once to scale the deposit amount into an internal 18-decimal unit, and again later in the same call to compute a withdrawal or valuation amount.
4. Because each `decimals()` call independently triggers `WasmdPrecompile.query(Cw20Address, "token_info")`, the two calls can return different values, letting the attacker deposit under one scaling factor and withdraw/borrow under a more favorable one, resulting in the victim contract mis-crediting value and the attacker profiting at the protocol's expense.

func (p PrecompileExecutor) AddCW20(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	cwAddr := args[0].(string)
	cwAddress, err := sdk.AccAddressFromBech32(cwAddr)
	if err != nil {
		return nil, 0, err
	}
	res, err := p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"token_info\":{}}"))
	if err != nil {
		return nil, 0, err
	}
	formattedRes := map[string]interface{}{}
	if err := json.Unmarshal(res, &formattedRes); err != nil {
		return nil, 0, err
	}
	name := formattedRes["name"].(string)
	symbol := formattedRes["symbol"].(string)
	contractAddr, err := p.evmKeeper.UpsertERCCW20Pointer(ctx, evm, cwAddr, utils.ERCMetadata{Name: name, Symbol: symbol})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
