### Title
Forged `EncryptedMessage` with identity encryption key frames an honest DKG participant — the sender-binding PoP is trivially satisfiable under an identity public key - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptedMessage::read` accepts `key = C::G::identity()` because it uses `Ciphersuite::read_G`, which performs canonical/torsion checks but does not reject the identity point (only `Curve::read_G` in FROST does). The proof-of-possession `pop` is a Schnorr signature verified against `msg.key`. Under an identity public key, the discrete log is 0, so anyone can produce a valid PoP for any claimed `sender` and any message (`s = r`, since `c·0 = 0`). Because the PoP is the only root of trust binding a message to its sender ("the per-message keys have no root of trust other than their existence in the assumed-to-exist external authenticated channel"), an unprivileged participant can inject a share message attributed to an honest participant that decrypts to garbage, causing that honest participant to be blamed and slashed.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs:171-177`, `EncryptedMessage::read` reads `key` via `C::read_G(reader)`. The default `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-100`) only checks decodability and canonicality — it explicitly allows the identity point.

`Decryption::decrypt_with_proof` (`encryption.rs:374-379`) verifies `msg.pop` as a Schnorr signature with public key `msg.key` and challenge `pop_challenge(context, R, key, sender, msg)`. A Schnorr signature under public key `0·G` is forgeable by anyone: pick any nonce `r`, set `R = rG`, `s = r`, and the verification equation `sG = R + c·(0G)` holds for every challenge `c`. The challenge binds `sender`, but the forgery works for any `sender` value — no knowledge of any secret is needed.

This defeats the protection the PoP was added for (documented at `encryption.rs:84-91` and in `spec/cryptography/Distributed Key Generation.md:28-35`): preventing a malicious party from causing blame that reveals another participant's messages or attributes fault incorrectly. The mitigation assumed the PoP requires knowledge of `key`'s discrete log; identity bypasses that assumption entirely.

Additionally, with `key = identity`, the ECDH in `Encryption::decrypt` (`encryption.rs:487`) is `enc_key · identity = identity`, so the cipher key is a public constant — the recipient deterministically decrypts to attacker-chosen bytes, guaranteeing a `from_repr` failure or share-verification failure at `crypto/dkg/pedpop/src/lib.rs:480-499`, producing `PedPoPError::InvalidShare { participant: victim, blame: Some(..) }`. In `processor/src/key_gen.rs:416-425`, this is emitted as `ProcessorMessage::InvalidShare { faulty: victim }`, and `VerifyBlame` (`key_gen.rs:504-563`) confirms the victim at fault because the forged PoP and the accuser's DLEq (`proof.key = enc_pub_accuser · identity = identity`) both verify.

### Impact Explanation
Any party able to supply or route a secret-share message to a DKG participant (e.g., the share-aggregator in `CoordinatorMessage::Shares`) can permanently frame an honest participant: the victim is blamed for a message they never sent, the DKG aborts, and the victim faces fatal slashing per the blame path in `processor/src/key_gen.rs`. This is a framing/slashing attack against honest validators and a guaranteed DKG liveness break, reachable purely with crafted public bytes fed to `EncryptedMessage::read` → `calculate_share`.

### Likelihood Explanation
Trivial to execute: the forgery requires only choosing `key = identity`, `R = rG`, `s = r`. No secret knowledge, no hash grinding, no collusion — a single malicious share-message suffices, and `blame_internal` deterministically assigns fault to `sender` (`lib.rs:590-604`).

### Recommendation
Reject the identity point for `msg.key` in `EncryptedMessage::read` (use an identity-rejecting reader, as `Curve::read_G` does), and similarly reject identity for `enc_key` in `EncryptionKeyMessage::read` (`encryption.rs:57-58`) and for `proof.key` in `EncryptionKeyProof::read` (`encryption.rs:267-269`). Additionally, verify PoP validity inline (or reject identity keys) before computing/releasing `EncryptionKeyProof` blame material.

### Proof of Concept
```
// Attacker crafts a share message attributed to honest participant `victim`:
let key = C::G::identity();                       // passes C::read_G
let r = C::F::random(rng);
let pop = SchnorrSignature { R: C::generator() * r, s: r };
// verifies: s·G = R + c·key = R + c·0 = R  for ANY challenge/sender binding
let forged = EncryptedMessage::<C, SecretShare<C::F>> { key, pop, msg: arbitrary_bytes };
// Deliver `forged` as victim's share to some recipient.
// Recipient's calculate_share: PoP batch-verifies OK, ECDH = identity,
// plaintext garbage -> InvalidShare { participant: victim, blame: Some(proof) }
// VerifyBlame/blame_internal confirms victim -> victim slashed, DKG aborts.
```
