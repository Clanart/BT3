### Title
Unvalidated `sender`/`recipient` indexes in PedPoP blame handling cause a reachable panic (remote DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The bug class of CVE-2025-30699 is an attacker-reachable hang/crash (availability impact). The analog in Serai is `BlameMachine::blame` / `AdditionalBlameMachine::blame`, which accept caller-supplied `sender` and `recipient` `Participant` indexes and pass them to `blame_internal`, which indexes `self.commitments[&sender]` without checking membership. A blame request naming a `sender` outside the DKG set triggers a `HashMap` index panic, crashing the thread handling it.

### Finding Description
`blame_internal` resolves blame between two parties. After decrypting the disputed message, it verifies the share against `self.commitments[&sender]`:

- `crypto/dkg/pedpop/src/lib.rs:599` — `&self.commitments[&sender]` inside `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)`
- `crypto/dkg/pedpop/src/lib.rs:623-632` — `BlameMachine::blame` takes `sender` and `recipient` from the caller and invokes `blame_internal` with no validation that `sender ∈ commitments` (or that `sender`/`recipient` are within `1 ..= n`, or that `sender != recipient`).

The same path is reachable via `AdditionalBlameMachine::blame` (lines 674-682), which is explicitly designed to be usable by a party that "was not a member in the DKG protocol" — i.e., an observer reachable by arbitrary external input. `AdditionalBlameMachine::new` (lines 649-662) only populates `commitments` for `1 ..= n`; any `sender` index outside that range, or a well-formed `Participant` not in the map, panics on the `HashMap` index.

Contrast with the non-blame path: `calculate_share` guards all map lookups with `validate_map` (lines 468-472) before indexing `self.commitments[&l]` at line 490. `blame_internal` has no equivalent guard — `sender` is only "authenticated as having come from the sender in question" per the doc comment, but nothing enforces that `sender` was a protocol participant before indexing.

### Impact Explanation
A panic in `blame_internal` unwinds (or aborts, depending on panic strategy) the caller. In a processor/coordinator deployment, a blame adjudication request naming a non-participant `sender` crashes the handler — a repeatable, attacker-triggered denial of service on the node evaluating blame. This matches the CVE's shape: a privileged-protocol operation (blame adjudication) reachable with attacker-supplied participant indexes causing a repeatable crash (CVSS-equivalent availability impact). It is not a "malicious-validator" analog because the crashing party is an honest node fed an untrusted index; the attacker only needs to submit a blame request, which is a public input path (accusations are gossiped between parties/observers).

### Likelihood Explanation
Blame adjudication exists precisely for adversarial conditions — it is invoked when some party is suspected faulty, i.e., exactly when malformed/unexpected participant indexes are most likely to appear. Any integration that routes blame requests with untrusted `sender`/`recipient` fields into `BlameMachine::blame` or `AdditionalBlameMachine::blame` is exposed; the panic requires only a `sender` not present in `commitments`, which an accuser can name freely.

### Recommendation
In `blame_internal`, validate before indexing:

```rust
// crypto/dkg/pedpop/src/lib.rs, in blame_internal before line 596
if !self.commitments.contains_key(&sender) {
  return sender; // accusing a non-participant: the accuser's claim is malformed; fault the sender claim or return a dedicated error
}
```

More robustly, validate both `sender` and `recipient` against `self.commitments` (or the `ThresholdParams` participant range) at the top of `blame`/`AdditionalBlameMachine::blame` and return `Result<_, PedPoPError>` rather than panicking. Indexing maps with `[]` on protocol-derived keys should be replaced with `.get()` + early return throughout `blame_internal`.

### Proof of Concept
```rust
// Setup: an honest party completed PedPoP for params t=2, n=3, i=1,
// producing BlameMachine via KeyMachine::calculate_share, or a third party
// built AdditionalBlameMachine::new(context, 3, commitment_msgs) (commitments
// only contain Participants 1..=3).

// Attacker submits a blame request accusing a participant index that was
// never in the DKG (e.g. Participant(7)), or a valid-range index absent
// from the map after prior removals.
let sender = Participant::new(7).unwrap();
let recipient = Participant::new(1).unwrap();
let msg = /* any EncryptedMessage<C, SecretShare<C::F>> */;
let proof = None;

// blame_internal reaches:
//   self.commitments[&sender]   // line 599 — HashMap index on missing key
// → thread panics: "no entry found for key"
blame_machine.blame(sender, recipient, msg, proof);
```

Even with `sender` in range, if `decrypt_with_proof` fails with `InvalidSignature`/`InvalidProof` the function returns early — the panic specifically requires `decrypt_with_proof` to succeed (or the sender to be absent from `commitments` while the proof path reaches the share check). The `AdditionalBlameMachine` variant is the cleanest reach: it processes blame statements over a fixed `1 ..= n` map with attacker-chosen `sender`, making any out-of-set index a deterministic crash.

Note: whether `decrypt_with_proof` can be made to succeed for an out-of-set `sender` depends on `Decryption::decrypt_with_proof`'s handling of unknown senders (in `crypto/dkg/pedpop/src/encryption.rs`), which I did not fully verify; if it rejects unknown senders first, the reachable panic reduces to `sender` values inside `1 ..= n` that are absent from `commitments` (still possible via `AdditionalBlameMachine` constructed with partial maps it accepts, or stale keys). The `HashMap::index` panic on untrusted protocol indexes is confirmed in code regardless.
