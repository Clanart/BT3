### Title
Association balance migration orphans staking/distribution state left under the pre-association direct-cast address - (File: utils/helpers/associate.go)

### Summary
The Sei EVM association flow migrates only spendable bank balances (and the wei remainder) from a user's pre-association "direct-cast" Sei address (`sdk.AccAddress(evmAddr[:])`) to their real Sei address when association happens. It never migrates or re-points staking delegations, unbonding entries, or distribution reward state that may have accrued under the direct-cast identity before association. Once migration completes, the direct-cast account is deleted (if it has no locked coins), permanently orphaning any staking/distribution positions still indexed by that address — mirroring the GoGoPool `finishFailedMinipoolByMultisig` bug class where a state transition into a "finished"/terminal state leaves no valid path back to withdraw funds.

### Finding Description
Every EVM transaction from an address that is not yet associated triggers automatic association in the ante handler: [1](#0-0) 

This unconditionally calls `AssociateAddresses`, which performs the account-swap and balance migration: [2](#0-1)

`MigrateBalance` moves only `SpendableCoins` and the wei balance from `castAddr` to `seiAddr`, and then **removes the `castAddr` account entirely** if it has no locked bank coins: [3](#0-2) 

Nothing in this path touches the staking module's delegation records, unbonding-delegation queue entries, or the distribution module's withdraw-address / outstanding-rewards state, all of which are keyed by the raw `castAddr` bytes as delegator/depositor address. Any tokens that reached a bonded/unbonding state under `castAddr` before association (e.g., via a Cosmos-side interaction, a precompile call, or any process that records `castAddr` as the delegator prior to the owner ever associating) are not migrated. Bank's `LockedCoins` check used to decide whether to delete the account does not reflect staking-bonded tokens (those already left the free balance and moved to the bonded pool), so the shadow account is deleted even though staking/distribution state referencing it still exists.

The codebase itself acknowledges this exact risk class for the related SetCode-authority path, describing it as "orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)": [4](#0-3) 

That comment shows the SetCode-authority case was explicitly patched with pre-association (`AssociateAuthorizationAuthorities`) precisely because the plain balance-migration path does not handle staking/distribution state — but the same underlying gap (delegations/rewards recorded under the direct-cast address, never migrated, and the shadow account deleted on association) exists for the ordinary "first EVM tx auto-associates the sender" path, which is reachable by any unprivileged user simply by sending a normal EVM transaction after having accrued staking state under their pre-association address.

### Impact Explanation
If staking or distribution state exists under a user's pre-association `castAddr` (direct EVM-address cast) at the moment their EVM address becomes associated, that state becomes permanently unreachable: the account object for `castAddr` is deleted, no key exists that can produce a valid Cosmos signature for `castAddr` (it was never populated with a real pubkey — its only owner is the EVM private key, whose signature is verified against `seiAddr` post-association), and precompile calls after association resolve the caller to `seiAddr`, not `castAddr`. This is a permanent freezing of user funds (bonded/unbonding tokens and accrued rewards), matching the "funds trapped by an invalid state transition" class from the reference report.

### Likelihood Explanation
Likelihood depends on how staking/distribution state can be created under the direct-cast address before real association occurs (e.g., via a precompile call routed through the "default Sei address" resolution for an unassociated EVM caller). The exact entry point that creates delegations under `castAddr` prior to association could not be fully confirmed within available tool budget — the staking precompile's delegate/undelegate address-resolution helper (`GetSeiAddressOrDefault` in `x/evm/keeper/address.go`) and its exact behavior for unassociated callers were located but not fully traced to conclusively prove a delegation can be created under `castAddr`. This is flagged as an open verification item for a full audit pass; the balance-migration gap itself (staking/distribution state never migrated on association) is confirmed directly from `utils/helpers/associate.go`.

### Recommendation
Before deleting the `castAddr` account during `MigrateBalance`, check for and migrate/re-point any staking delegations, unbonding-delegation entries, and distribution reward/withdraw-address state associated with `castAddr` to `seiAddr`, or refuse to delete the account (and instead leave a mapping/redirect) whenever such state exists — mirroring the fix already applied for SetCode authorities (pre-associating before any state can be created under the direct-cast identity) but generalized to the standard auto-association path in `x/evm/ante/preprocess.go`.

### Proof of Concept
Not independently verified end-to-end; based on direct code reading of `utils/helpers/associate.go` (balance-only migration, unconditional account deletion) and `x/evm/ante/preprocess.go` (unconditional auto-association on first EVM tx). Confirming a concrete PoC requires demonstrating a code path that creates a staking delegation or distribution reward keyed by `castAddr` while the account remains unassociated (candidate: the staking precompile's delegate call from an unassociated EVM sender) — this final link was not conclusively traced before the tool budget was exhausted.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// AssociateAuthorizationAuthorities pre-associates every EIP-7702 SetCode authorization
// authority in the transaction with its true (pubkey-derived) Sei address before EVM
// execution installs delegation code for it. Authorities are distinct accounts from the tx
// sender, so the sender association performed by the caller does not cover them. Without
// this, SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey
// call can remap, orphaning any staking/distribution state created under the direct-cast
// identity (which can then halt the chain via the distribution validator-removal hook).
//
// This is the legacyabci counterpart of x/evm/ante's EVMPreprocessDecorator so both ante
// paths associate authorities identically. It is best-effort: only authorities whose
// authorization the EVM will actually apply are pre-associated — helpers.AuthorityToPreAssociate
// enforces the same chain-id/nonce/account-code checks go-ethereum uses, which also prevents
// replaying a publicly-visible authorization a user signed for another chain to force-associate
// them. Each association runs in its own cache context and is only committed on success, so an
// already-associated, skipped, or failing authority affects only itself and never rejects the
// transaction (matching go-ethereum, which would still accept it). Non-SetCode transactions
// carry no authorizations and are a no-op.
