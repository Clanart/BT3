## Title
Stale-State OAuth Completion Enables Cross-Flow Account Binding in `SignInStore` - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.resolveOAuthRequest()` validates the CSRF `state` parameter against `this.state.oauthState` *before* making two network calls (`requestOAuthToken`, `fetchUser`), but then completes the flow by invoking `this.state.oauthState.onAuthCompleted(account)` — re-reading the **live**, mutable `this.state` field instead of a value captured at validation time. If the store's `state` is replaced by a second, concurrent sign-in flow while the first flow's network calls are still in-flight, the account resolved from the *first* flow's (attacker-influenced) OAuth exchange is bound to the *second* flow's completion callback. This is structurally identical to the reported Solidity bug: a check is performed, then an external/asynchronous interaction occurs, and the code that follows acts on state that can have been mutated during that interaction instead of the state that was actually validated.

### Finding Description [1](#0-0) 

```
public async resolveOAuthRequest(action: IOAuthAction) {
  if (!this.state || this.state.kind !== SignInStep.Authentication) return
  if (!this.state.oauthState) return
  if (this.state.oauthState.state !== action.state) { ... return }

  const { endpoint } = this.state
  const token = await requestOAuthToken(endpoint, action.code)   // <-- external call #1
  if (token) {
    const account = await fetchUser(endpoint, token)             // <-- external call #2
    this.state.oauthState.onAuthCompleted(account)                // <-- re-reads live state!
  } else {
    this.state.oauthState.onAuthError(...)
  }
}
```

The CSRF check (`this.state.oauthState.state !== action.state`) is the "checks" step. The two `await`s are the "interactions" (network requests to a GitHub.com/Enterprise endpoint, which for GHE is attacker-influenceable). The completion (`onAuthCompleted`/`onAuthError`) is the "effect", but it operates on `this.state.oauthState` read *after* the interactions rather than a captured reference obtained *at* validation time.

`this.state` can legitimately be mutated while these awaits are pending: `reset()` (invoked from `beginDotComSignIn`/`beginEnterpriseSignIn` whenever `this.state !== null`) replaces `this.state` and installs a brand-new `oauthState` (with a new `csrfToken` and new `resolve`/`reject` closures) for a second sign-in attempt: [2](#0-1) 

Each call to `authenticateWithBrowser()` creates a fresh `Promise` and stores its `resolve`/`reject` as `onAuthCompleted`/`onAuthError` inside a newly assigned `this.state.oauthState`: [3](#0-2) 

Because `resolveOAuthRequest` never re-captures or re-validates `oauthState` after its awaits, a slow/delayed response to the *first* flow's OAuth exchange will, upon completion, invoke `this.state.oauthState.onAuthCompleted(account)` against whatever flow is *currently* active — i.e. the second flow's resolver — silently binding an account obtained through the first (attacker-controllable) endpoint into the second flow's success path. The dispatcher passes every incoming `oauth` deep link straight into this function without additional guarding: [4](#0-3) 

### Impact Explanation
This breaks the invariant that an OAuth completion is always bound to the exact sign-in flow whose CSRF `state` was validated. A malicious/compromised GitHub Enterprise instance the user has pointed Desktop at (a "GitHub API object"/"remote endpoint" attacker per the valid-impact criteria) can delay its `login/oauth/access_token` or `/user` responses, then return an attacker-chosen account. If the user cancels that Enterprise sign-in and starts a second, legitimate sign-in (e.g. to GitHub.com) before the delayed response arrives, the attacker's account gets bound as the result of the *second* flow via `emitAuthenticate`/`setState({kind: SignInStep.Success, ...})` in `authenticateWithBrowser`'s `.then()` handler — an unauthorized OAuth/account binding into the application state, without further user interaction or awareness of the substitution.

### Likelihood Explanation
Requires: (1) the user has added or is signing into an attacker-controlled/compromised GitHub Enterprise endpoint, and (2) the user restarts a sign-in attempt (a normal, expected user action — e.g. cancel-and-retry, or switch to signing in with a different account) while the first flow's network round trip is still outstanding. No local, admin, or pre-existing malware access is needed; the only capability required is control over the response timing/content of an already-configured remote endpoint, which is within the accepted "attacker controls a git remote/proxy response" primitive.

### Recommendation
Capture the validated `oauthState` object into a local constant immediately after the CSRF check, and use that captured reference (not `this.state.oauthState`) for both the success and error paths, mirroring the checks-effects-interactions fix from the original report (snapshot state before external calls, then act only on the snapshot):

```ts
public async resolveOAuthRequest(action: IOAuthAction) {
  if (!this.state || this.state.kind !== SignInStep.Authentication) return
  const oauthState = this.state.oauthState
  if (!oauthState || oauthState.state !== action.state) return

  const { endpoint } = this.state
  const token = await requestOAuthToken(endpoint, action.code)
  if (token) {
    const account = await fetchUser(endpoint, token)
    oauthState.onAuthCompleted(account)
  } else {
    oauthState.onAuthError(new Error('Failed retrieving authenticated user'))
  }
}
```
Additionally consider tagging each in-flight OAuth attempt with a unique id and verifying `this.state.oauthState === oauthState` before invoking completion, to detect (and drop) responses for a superseded flow instead of silently completing the current one.

### Proof of Concept
1. User adds a malicious/compromised GitHub Enterprise endpoint `E1` and clicks "Sign in" → `authenticateWithBrowser()` creates `oauthState₁` with `csrfToken₁`, opens browser to `E1`'s OAuth authorize URL.
2. `E1`'s authorize page immediately redirects back with a valid `code₁`/`state=csrfToken₁`; Desktop's protocol handler invokes `dispatchURLAction` → `resolveOAuthRequest({code: code₁, state: csrfToken₁})`. The CSRF check passes and `requestOAuthToken(E1, code₁)` is issued — `E1` (attacker-controlled) intentionally delays its HTTP response.
3. Before `E1` responds, the user cancels and clicks "Sign in to GitHub.com" → `beginDotComSignIn()` → `reset()` (rejects `oauthState₁` via `onAuthError`, which is harmless) then `authenticateWithBrowser()` creates `oauthState₂`/`csrfToken₂` and replaces `this.state`.
4. User completes the legitimate GitHub.com OAuth flow with `code₂`/`state=csrfToken₂`; this `resolveOAuthRequest` call also awaits `requestOAuthToken`/`fetchUser` (fast, legitimate).
5. `E1` now finally responds to step 2's pending request with a token for an **attacker-controlled account**. `fetchUser(E1, token₁)` resolves with the attacker's account, and the code executes `this.state.oauthState.onAuthCompleted(account_attacker)` — but `this.state.oauthState` is now `oauthState₂` (the GitHub.com flow), whose `resolve` settles the GitHub.com `authenticateWithBrowser()` promise with `account_attacker`.
6. The `.then()` handler in `authenticateWithBrowser()` sees `this.state.kind === SignInStep.Authentication` (still true) and calls `emitAuthenticate(account_attacker)`, adding the attacker's account to Desktop under the guise of the user's intended GitHub.com sign-in.

        error: null,

  public async authenticateWithBrowser() {
    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.Authentication &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with browser authentication`
      )
    }

    this.setState({ ...currentState, loading: true })

    if (currentState.kind === SignInStep.ExistingAccountWarning) {
      const { existingAccount } = currentState
      // Try to avoid emitting an error out of AccountsStore if the account
      // is already gone.
      if (this.accounts.find(x => x.endpoint === existingAccount.endpoint)) {
        await this.accountStore.removeAccount(existingAccount)
      }
    }

    const csrfToken = crypto.randomUUID()

    new Promise<Account>((resolve, reject) => {
      const { endpoint, resultCallback } = currentState
      log.info('[SignInStore] initializing OAuth flow')
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        resultCallback,
        error: null,
        loading: true,
        oauthState: {
          state: csrfToken,
          endpoint,
          onAuthCompleted: resolve,
          onAuthError: reject,
        },
      })
      shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))
    })
      .then(account => {
        if (!this.state || this.state.kind !== SignInStep.Authentication) {
          // Looks like the sign in flow has been aborted
          log.warn('[SignInStore] account resolved but session has changed')
          return
        }

        log.info('[SignInStore] account resolved')
        this.emitAuthenticate(account)
        this.setState({
          kind: SignInStep.Success,
          resultCallback: this.state.resultCallback,
        })
      })
      .catch(e => {
        // Make sure we're still in the same sign in session
        if (
          this.state?.kind === SignInStep.Authentication &&

          log.info('[SignInStore] error with OAuth flow', e)
          this.setState({ ...this.state, error: e, loading: false })
        } else {
          log.info(`[SignInStore] OAuth error but session has changed: ${e}`)
        }
      })
  }
