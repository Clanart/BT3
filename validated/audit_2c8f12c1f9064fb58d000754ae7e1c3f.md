### Title
Attacker-controlled wire-type/field mismatch triggers unreachable `CHECK`/`FATAL` abort in `UntypedMessage::Decode` - (File: `json/internal/untyped_message.cc`)

### Summary
`UntypedMessage::Decode`, used by protobuf's schema-driven binary→JSON conversion path (the same class of code that backs `Any` resolution / typeless JSON printing), contains a wire-type dispatch switch with a case that the author believed was unreachable and guarded only with `ABSL_LOG(FATAL) << "unreachable";` instead of a normal error return. Attacker-supplied wire bytes can reach that case, causing the process to abort — the same class of failure as the TensorFlow report: an unchecked/incorrectly-assumed-impossible value from untrusted input reaches a `CHECK`/`FATAL`, producing a crash-based denial of service instead of a graceful decode error.

### Finding Description
`UntypedMessage::Decode` reads a tag, splits it into `field_number` and `wire_type`, and looks up `field` by number only — the lookup does **not** verify that the wire type on the wire matches the wire type implied by the field's declared type: [1](#0-0) 

The function first checks whether it should treat the tag as "unknown/skippable" via `if (!group_stack.empty() || field == nullptr)`. Only when this guard is false — i.e., `group_stack` is empty (we are not inside a group) **and** a known `field` was found for that field number — does execution fall through directly into the second switch that dispatches on the raw wire type: [2](#0-1) 

That second switch has a case for `WIRETYPE_END_GROUP` that is expected to never be hit and is guarded only by an `ABSL_LOG(FATAL) << "unreachable";`: [3](#0-2) 

The invariant the author assumed — "a resolved, known top-level field can never have wire type `END_GROUP` on the wire" — is not actually enforced anywhere before this point. Field lookup is purely by field number, and there is no check that a byte-stream tag using wire type 4 (`END_GROUP`) at the top level, for a field number that happens to match a real field in the schema, gets rejected before reaching the second switch. This is directly analogous to the TensorFlow bug: `Save`/`SaveSlices` dispatched on `dtype` without checking it against the set of types the `CHECK`-guarded switch actually supports, so an attacker-chosen `dtype` reached the "impossible" `default`/`CHECK` path. Here, an attacker-chosen wire type (4) for a field number that resolves successfully reaches the "impossible" `FATAL` path.

### Impact Explanation
This is a reachable `ABSL_LOG(FATAL)` (a `CHECK`-fail equivalent) driven purely by attacker-supplied bytes handed to a public binary-parsing/JSON-conversion code path (consuming application feeds untrusted binary protobuf data, e.g. for `Any` resolution or type-resolver–driven JSON printing). Hitting it aborts the process — a crash/denial-of-service, consistent with the Medium severity of the TensorFlow analog (`CWE-617: Reachable Assertion`), not memory corruption or RCE.

### Likelihood Explanation
Likelihood is high for any code path that constructs an `UntypedMessage` and calls `Decode` on attacker-supplied binary bytes without validating wire-type/field-type consistency ahead of time. The precondition is simple to satisfy: an empty `group_stack` (top-level tag, not nested in a group) and a field number that resolves to a schema-known field, combined with wire type 4 in the tag byte. No packed/oneof/map dispatch complexity is required — a single crafted tag byte suffices.

### Recommendation
Replace the `ABSL_LOG(FATAL) << "unreachable";` for the `WIRETYPE_END_GROUP` case in the second switch of `UntypedMessage::Decode` with a proper decode error return (e.g. `return MakeUnexpectedEndGroupError(field_number);`), mirroring how the sibling "skip" switch already treats `END_GROUP` as a data-dependent, checkable condition rather than an assumed-impossible state. More generally, validate that the wire type read from the tag is consistent with the resolved field's expected wire type before entering the second (non-skip) switch, so that any invalid combination is turned into a `absl::Status` error rather than a `FATAL` log.

### Proof of Concept
Conceptual reproduction (exact byte-level PoC requires exercising `UntypedMessage::Decode` directly, which I could not execute in this read-only analysis):
1. Build a schema with a top-level message containing at least one field, e.g. field number `1` of type `int32`.
2. Craft a binary buffer whose first tag byte encodes field number `1` with wire type `4` (`END_GROUP`), i.e. `tag = (1 << 3) | 4 = 0x0C`.
3. Feed this buffer to `UntypedMessage::Decode` (reached via the `Any`/type-resolver JSON-printing path that constructs `UntypedMessage` from raw bytes and a schema).
4. Because `group_stack` is empty and `field` (number `1`) resolves successfully, the code skips the "skip" switch and falls into the second switch on `wire_type == WIRETYPE_END_GROUP`, hitting `ABSL_LOG(FATAL) << "unreachable";` at [3](#0-2)  and aborting the process.

Note: I was not able to trace the exact public API entry point that constructs `UntypedMessage` with attacker-controlled bytes (e.g. the specific `BinaryToJsonString`/`Any` resolver call site) within the available tool budget; confirming the full call chain from a documented public parsing API to `UntypedMessage::Decode` would strengthen this finding and should be verified with a live Devin session that can grep the full call graph and run a concrete crash reproduction.
