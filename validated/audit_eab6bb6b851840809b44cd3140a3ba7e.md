### Title
List-shaped daemon RPC fields bypass `redact_sensitive_data()` and leak mnemonics/secrets in daemon debug logs - ([File: chia/daemon/server.py])

### Summary
The Chia local daemon (`chia/daemon/server.py`) logs every incoming websocket message at debug level after passing it through `redact_sensitive_data()` to strip secrets such as passphrases, private keys, and mnemonics before they hit the log file. The redaction function only recurses into `dict` values; any value that is a `list` — including lists that themselves contain dictionaries with sensitive keys, or a top-level field whose name doesn't match the trigger substrings — is returned unchanged. This is the same bug class as CVE-2026-68970/CVE-2026-59244 in Apache Airflow: masking is applied only for one JSON shape (there: dict/string; here: dict-recursion only) and silently skipped for the list shape, so secrets survive in cleartext logs.

### Finding Description
`redact_sensitive_data()` in [2](#0-1)  only redacts a value when its *key name* matches one of the trigger substrings (`"pass"`, `"key"`, `"secret"`, `"mnemonic"`), and only recurses into the value further if it is a `dict`:

```python
def redact_sensitive_data(obj, redaction_triggers=("pass", "key", "secret", "mnemonic")):
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***" if any(trigger in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```

If `obj` (or a nested value) is a `list`, the function hits the `else` branch and returns it verbatim — it never iterates into list elements to redact nested dict keys. This function is invoked in `incoming_connection()` right before debug-logging every raw daemon message: [3](#0-2) .

Daemon RPC requests are dispatched to `KeychainServer.handle_command()` for keychain operations, including `add_private_key`/`add_key`, which pulls the mnemonic straight from the raw request dict: [4](#0-3) . Any request field whose value is a JSON list — e.g. a mnemonic represented as `list[str]` (as `AddKey.mnemonic: list[str]` is typed in [1](#0-0) ), or a request field wrapping a list of dicts each carrying a `password`/`passphrase`/`secret` sub-key under a container key that doesn't itself match a trigger substring (e.g. `"entries"`, `"items"`, `"users"`) — is logged in cleartext at DEBUG level, defeating the intended purpose of `redact_sensitive_data()`. The existing regression test only exercises string- and dict-shaped sensitive fields (`password`, `private_key`, nested `passphrase`, `api_key`), never a list-shaped or list-of-dicts sensitive field, so this gap is untested: [5](#0-4) .

### Impact Explanation
This affects the local daemon/keychain RPC boundary rather than the P2P chain-state protocols in the exclusion list, but it directly matches the requested scope item "daemon/keychain/RPC authorization" and results in cleartext leakage of wallet mnemonics/private-key material in on-disk log files when DEBUG logging is enabled — the exact outcome the CHANGELOG itself warns about for passphrases: [6](#0-5) . Any local user/process able to read the daemon log file (which is broader than the set of users permitted to hold the daemon's mTLS client certificate) could recover key material for wallets managed through that daemon, enabling unauthorized signing/spending — a concrete unauthorized coin movement primitive once the mnemonic is exfiltrated.

### Likelihood Explanation
Requires the daemon to be running with DEBUG logging enabled (documented as a known, real-world configuration in the project's own CHANGELOG) and a client sending an `add_key`/`add_private_key` (or any future keychain command) with a list-shaped or list-wrapped sensitive field. No authentication bypass is needed beyond already having a daemon client TLS cert (same trust level as any legitimate wallet/CLI/GUI client), so likelihood is moderate — comparable to the "no special configuration required" characterization in the Airflow advisory, since DEBUG logging is a normal troubleshooting mode, not an exotic one.

### Recommendation
Fix `redact_sensitive_data()` to recurse into `list` (and other sequence) values, redacting/recursing on each element, mirroring how the Airflow fix extended masking to cover both dict and list JSON shapes rather than only one:

```python
def redact_sensitive_data(obj, redaction_triggers=(...)):
    if isinstance(obj, dict):
        return {key: ... for key, value in obj.items()}
    if isinstance(obj, list):
        return [redact_sensitive_data(item, redaction_triggers) for item in obj]
    return obj
```
Add a regression test with a list-of-dicts sensitive payload (analogous to `test_message_logging_redaction`) to close the coverage gap.

### Proof of Concept
1. Start the Chia daemon with `log_level: DEBUG`.
2. Connect a websocket client and send a `test_command`/`add_key`-style payload whose `data` contains a list-wrapped sensitive field not caught by top-level key matching, e.g.:
```json
{"command": "add_key", "data": {"entries": [{"password": "secret_password", "mnemonic": "leaked mnemonic words"}]}, "ack": false, "origin": "test", "destination": "daemon"}
```
3. Observe the daemon debug log entry `Received message: ...` — the `entries` list and its nested `password`/`mnemonic` values are logged in cleartext, unlike top-level `password`/`mnemonic` fields which are correctly redacted per [7](#0-6) .
