### Title
Missing slippage protection in `WombatPoolHelperV2.depositFor` due to hardcoded `_minimumLiquidity = 0` - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor` allows an ordinary wallet to deposit stable tokens into a Wombat pool on behalf of a beneficiary (`_for`), but unlike the sibling `deposit`/`depositNative` functions, it hardcodes the `_minimumLiquidity` parameter to `0` when calling the internal `_deposit` helper, which forwards it unchecked to `WombatStaking.deposit` and ultimately to the underlying Wombat pool's `deposit(...)` call.

### Finding Description
`WombatPoolHelperV2.deposit(uint256 _amount, uint256 _minimumLiquidity)` lets the caller specify a `_minimumLiquidity` slippage bound that is passed all the way to `IWombatPool.deposit(... minimumLiquidity ...)`: [1](#0-0) 

However, `depositFor(uint256 _amount, address _for)` — reachable by any unprivileged wallet wanting to deposit on behalf of another address — ignores caller input entirely and hardcodes the minimum liquidity to `0`: [2](#0-1) 

This value is forwarded unchanged through `_deposit` to `WombatStaking.deposit`: [3](#0-2) 

and from there directly into the underlying Wombat pool's `deposit` function as the `minimumLiquidity` argument: [4](#0-3) 

The Wombat pool computes `lpTokenToMint`/`liabilityToMint` from the pool's current `cash`/`liability` ratio (an AMM-style bonding curve), so the amount of LP/receipt tokens minted per unit of deposited asset is not fixed 1:1 and can be manipulated by preceding trades or other deposits/withdrawals in the same block (e.g., via a sandwich attack), exactly matching the bug class described in the referenced `ERC4626DepositOnly.deposit`/`mint` report where slippage-sensitive vault operations lack minimum-output protection. [5](#0-4) 

Because `_minimumLiquidity` is hardcoded to `0` in `depositFor`, a depositor calling this function has no way to bound the minimum receipt tokens received, and the transaction cannot revert even if the received LP/receipt tokens are far below fair value.

### Impact Explanation
A depositor using `depositFor` (or a wallet routed through it, e.g. batch deposit flows in `AnkrBNBPoolHelper`) can be sandwiched by an attacker who manipulates the target Wombat pool's cash/liability ratio immediately before the deposit executes, causing the caller/beneficiary to receive fewer receipt tokens (hence fewer `bHermes`-equivalent shares of value) than the deposited assets are worth. This is a direct loss of user funds during deposit with no possibility to protect against it, since the transaction cannot be configured to revert on unfavorable execution.

### Likelihood Explanation
`depositFor` is a public, unprivileged, ordinary-wallet-callable function reachable directly by any depositor or by any integrating contract (e.g., `AnkrBNBPoolHelper.batchDeposit` style flows) that wants to deposit on behalf of another address. Because pool ratios naturally fluctuate and can be pushed by any other market participant's transaction, exploitation only requires an attacker to front-run or co-locate a transaction in the same block as the victim's `depositFor` call — no privileged access is required.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`) and pass the caller-supplied value through to `WombatStaking.deposit` instead of hardcoding `0`, so the underlying Wombat pool's `require`/revert-on-slippage logic can actually protect the depositor.

### Proof of Concept
1. Alice calls `WombatPoolHelperV2.depositFor(amount, aliceAddress)` intending to deposit `amount` of `depositToken`.
2. Because `_minimumLiquidity` is hardcoded to `0` at `wombat/WombatPoolHelperV2.sol:106`, no minimum-output check is enforced.
3. Immediately before Alice's transaction, an attacker executes a trade or deposit that shifts the pool's `cash`/`liability` ratio unfavorably.
4. Alice's deposit executes and mints significantly fewer LP/receipt tokens than expected for her `amount`, yet the transaction succeeds because there is no revert condition.
5. Alice has unexpectedly received receipt tokens worth less than the `depositToken` she supplied, with no recourse.
