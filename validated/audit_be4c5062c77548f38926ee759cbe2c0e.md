Based on my research, I found a strong analog in GitHub Desktop's line-based diff selection/patch-generation pipeline, which is the direct functional equivalent of the Solidity `addToPosition()` math bug: both take user-facing partial state (partial margin / partial line selection) and compute a downstream artifact (new price / commit patch) using positional arithmetic that can desynchronize from the actual underlying data.

### Title
Diff-hunk expansion shifts absolute line indices without remapping the persisted `DiffSelection`, causing partial commits/discards to include the wrong lines - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
Desktop's partial-staging feature ("stage individual lines/hunks") represents selection state as a `DiffSelection` object keyed by an *absolute line index* into the diff, and reconstructs the patch to hand to `git apply` by re-deriving each line's inclusion via `hunk.unifiedDiffStart + lineIndex` [1](#0-0) . Separately, the "expand hunk" feature inserts new context lines into a hunk and explicitly re-numbers every downstream hunk's `unifiedDiffStart`/`unifiedDiffEnd` by adding `numberOfNewDiffLines` [2](#0-1) . Because the persisted `DiffSelection` is a plain index→boolean/diverging-set structure that does not know about hunk boundaries, once indices shift due to expansion, the same index number now points at a different physical line than when the user selected it.

### Finding Description
`formatPatch()` computes whether a line is included in the patch purely from its numeric position: `const absoluteIndex = hunk.unifiedDiffStart + lineIndex` then `file.selection.isSelected(absoluteIndex)` [1](#0-0) . `DiffSelection.isSelected()` looks the index up in a `divergingLines` set relative to a `defaultSelectionType`, with no concept of which line of text that index originally referred to [3](#0-2) .

`expandTextDiffHunk()` (triggered when the user clicks the up/down hunk-expansion handle) inserts `numberOfNewDiffLines` new context lines into the diff and then shifts every hunk that comes after the expanded one:
```
hunk.unifiedDiffStart + numberOfNewDiffLines,
hunk.unifiedDiffEnd + numberOfNewDiffLines,
``` [4](#0-3) 

This is architecturally the same class of bug as the Tigris report: a formula (`oldStartLine`/`newStartLine`/index math) that is recomputed for one side of the system (the diff hunks) but not consistently propagated to the other side that depends on it (the previously recorded per-index selection state). In Tigris, `_newPrice` used `_trade.margin`/`_newMargin` as if the underlying position sizes stayed proportionally consistent, when they didn't; here, `isSelected(absoluteIndex)` is used as if line indices stay stable across hunk-expansion, when `expandTextDiffHunk` proves they explicitly do not for hunks below the expansion point.

### Impact Explanation
If a user selects/deselects specific lines for a partial commit, then expands a hunk above those lines (e.g., to review more context before committing) without first re-confirming or clearing their line selection, the indices used internally to build the `git apply` patch in `applyPatchToIndex()`/`discardChangesFromSelection()` [5](#0-4) [6](#0-5)  no longer point at the lines the user actually looked at and checked. This falls squarely under "silent corruption of what the user commits or pushes": the resulting commit can include content the user never selected, or omit content the user did select, with no error or warning — `git apply` will happily accept a syntactically valid patch built from mismatched line/selection indices as long as the hunk header counts are internally consistent (which they are, since `formatPatch` recomputes `oldCount`/`newCount` from the hunk's own lines, masking the fact that the *selection* keys no longer line up).

### Likelihood Explanation
This does not require local/physical access, admin rights, or leaked credentials — it's triggered purely by normal UI interaction (select lines → expand a hunk → commit/discard) on a file whose diff has multiple hunks, which is a completely ordinary workflow for any file the user is committing, including ones freshly checked out from a cloned/fetched remote. The severity depends on exactly how/whether the selection-adjustment logic (which I could not fully inspect given the read-only iteration budget — specifically the handler wiring between `onHunkExpansionRef`/`side-by-side-diff.tsx` and any selection remap) compensates for the shift. I was not able to confirm within the available tool budget whether `side-by-side-diff.tsx` clears or remaps the `DiffSelection` on every expansion (which would fully mitigate this) or leaves it untouched (which would confirm the exploitable path).

### Recommendation
- When a hunk is expanded (or hunks are merged during expansion), remap the `DiffSelection` bit-set/diverging-lines alongside the shifted `unifiedDiffStart`/`unifiedDiffEnd` values, the same way `numberOfNewDiffLines` is already propagated to hunk boundaries in `expandTextDiffHunk` [2](#0-1) .
- Alternatively, key `DiffSelection` by content-stable identifiers (e.g., original file line number + hunk anchor) instead of an absolute diff-wide line index that is invalidated by any expansion/merge operation.
- Add a regression test that selects specific lines, expands a hunk above/between them, and asserts the resulting `formatPatch()` output still corresponds to the originally selected content.

### Proof of Concept
Conceptual reproduction (I could not execute this in the current read-only session, so treat as a test plan rather than confirmed output):
1. Create a file with 3+ separated hunks of changes.
2. In the Changes view, deselect one specific added line in the *second* hunk via `withLineSelection` (this records its absolute index).
3. Click "expand hunk" on the *first* hunk to pull in extra context lines, which invokes `expandTextDiffHunk` and shifts the `unifiedDiffStart`/`unifiedDiffEnd` of the second hunk downward by `numberOfNewDiffLines` [7](#0-6) .
4. Commit the partial selection; call `formatPatch()` and inspect the produced patch.
5. Verify whether the line that ends up included/excluded in the patch is the one the user originally clicked, or a different line that now occupies that same absolute index — confirming the exploitable index desync.
