### Title
Escrow withdrawal and dust-sweep in `IntentGatewayV2` (Tron variant) ignore the ERC20 return-value/data, permanently locking escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` imports and uses `SafeERC20`/`safeTransferFrom` when *pulling* tokens into escrow, but the withdrawal path (`withdraw()`), the fee-release path, and the `SweepDust` handler inside `onAccept()` release tokens using a raw low-level `.call` with `IERC20.transfer.selector` and only check that the call itself did not revert — they never decode/require the boolean return value. [1](#0-0) 

### Finding Description
`withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages (settlement/refund) and from `onGetResponse()` (cancellation). It finalizes the order (`_filled[commitment] = beneficiary`), decrements the internal escrow accounting (`_orders[body.commitment][token] -= amount`), and then attempts to move the actual tokens with:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same pattern is used for fee release:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [3](#0-2) 

and in the `SweepDust` handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

The bug-class from the external report is "protocol reverts on tokens that don't return a bool" — the fix there was to use `SafeERC20.safeTransfer`, which both tolerates missing return data **and** requires that any returned boolean be `true`. Here the code took the low-level `.call` route instead of `safeTransfer`, which solves the "no-return-value revert" problem but reintroduces the opposite and more dangerous defect: `success` from `.call(...)` only reflects whether the callee **reverted**. It says nothing about the ERC20's own success/failure semantics. Any ERC20 (deliberately malicious, or simply one that follows the historic pattern of returning `false` instead of reverting on failure, e.g. insufficient balance/blocklist/paused conditions) will make the `.call` return `success = true` while the token balance never moves.

Because `withdraw()` performs its escrow-accounting mutations (`_orders[...] -= amount`, `_filled[commitment] = beneficiary`, `EscrowReleased`/`EscrowRefunded` events) unconditionally once `success == true`, a transfer that silently fails (returns `false`) causes the protocol to treat the order as settled/refunded even though the tokens are still held by the gateway contract. Since the order is already marked `_filled` and the escrow ledger already zeroed, there is no remaining code path to retry or reclaim those tokens — they become permanently stuck in the contract (loss of funds for the intended beneficiary), while the on-chain events falsely report a successful release.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories: the escrow-release primitive accepts a false success signal from an untrusted external token contract and finalizes irreversible state (order-filled flag, escrow decrement, event emission) without confirming the beneficiary actually received the funds. An unprivileged party (any order counterparty using a token that returns `false` on failure, or a token deliberately crafted to do so) can trigger this on the settlement/refund/cancel/dust-sweep paths, causing legitimate beneficiaries to permanently lose access to their escrowed assets while the on-chain record shows the transfer succeeded.

### Likelihood Explanation
This is reachable through the standard, unprivileged order lifecycle (`fillOrder` → cross-chain `RedeemEscrow`/`RefundEscrow` → `onAccept` → `withdraw`, or `cancelOrder` → `onGetResponse` → `withdraw`, or governance-triggered `SweepDust`). The only requirement is that one of the escrowed tokens is a non-standard/return-false ERC20 (a well-documented and non-exotic category of tokens), not a malicious relayer, prover, or admin. No proof forgery or privileged role is needed — the flaw is in how the contract interprets an ordinary external call's result.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` release paths in `withdraw()`, the fee-release block, and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (the contract already imports and uses `SafeERC20` elsewhere for `safeTransferFrom`). This ensures both non-standard (void-return) tokens and tokens that return `false` are handled correctly and that a failed transfer always reverts before escrow accounting/state is finalized.

### Proof of Concept
1. Deploy a token `T` whose `transfer()` returns `false` (instead of reverting) whenever an internal condition fails (e.g., a blocklist check, a paused flag, or simply `return false;` unconditionally to model a buggy/malicious ERC20).
2. User places a cross-chain order escrowing `T` via `placeOrder` (uses `safeTransferFrom`, so escrow succeeds normally).
3. Solver fills the order on the destination chain; the `RedeemEscrow` message is relayed back and `onAccept()` calls `withdraw(body, false)` on the source chain.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call does not revert) even though `T.transfer` internally returned `false` and moved no tokens.
5. `_orders[commitment][token] -= amount` executes, `_filled[commitment] = beneficiary` is set, and `EscrowReleased` is emitted — the protocol now considers the order fully settled.
6. The beneficiary's `T` balance is unchanged; the escrowed `T` tokens remain locked in the `IntentGatewayV2` contract with no code path to retrieve them, since the commitment is already finalized as filled.

Note: I confirmed this exact `.call`-based release pattern only in `evm/tron/contracts/apps/IntentGatewayV2.sol`; I did not have the tool budget remaining to fully verify whether the mainline `evm/src/apps/IntentGatewayV2.sol` (which also has `IERC20.transfer.selector` matches) uses the same vulnerable pattern versus `safeTransfer` — this should be checked as part of remediation to determine whether the fix needs to be applied to both variants.
