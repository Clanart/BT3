### Title
Payout tx OP_RETURN operator attribution is unauthenticated under `SinglePlusAnyoneCanPay`, allowing malleation of which operator is credited for a payout - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/operator.rs`, `core/src/verifier.rs`)

### Summary
The payout transaction's user signature is required to use `TapSighashType::SinglePlusAnyoneCanPay`, which commits only to input 0 and output 0 (the user's payout output); it never commits to the OP_RETURN output that names the fronting operator's x-only pubkey. Because that OP_RETURN is the *sole* source of truth both for `core/src/verifier.rs`'s `update_finalized_payouts`/`is_kickoff_malicious` DB attribution and for `circuits-lib/src/bridge_circuit/mod.rs`'s `deposit_constant`/`journal_hash` computation, an unprivileged party who observes the broadcast-but-unconfirmed payout transaction can rebroadcast a fee-bumped variant with an identical input 0 and output 0 but an arbitrary OP_RETURN, misattributing (or nullifying) which operator fronted the withdrawal once that variant confirms.

### Finding Description
Binding claimed to hold: `operator_xonly_pk` embedded in the payout transaction's OP_RETURN (as read by `get_first_op_return_output`/`parse_op_return_data` in `circuits-lib/src/bridge_circuit/mod.rs:206-219` and again in `core/src/verifier.rs:2312-2321`) == the operator whose Bitcoin funds actually funded input 0/output 0 of that payout.

Root cause: `Operator::withdraw` (`core/src/operator.rs:560-637`) builds the payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which places the operator's x-only pubkey in an OP_RETURN output (`op_return_txout(...)` at line 418) that is separate from output 0 (user payout) and output 1 (anchor). The *only* cryptographic check performed is: [1](#0-0) 
which validates the user's Schnorr signature over `in_signature.sighash_type`. The sighash type is enforced elsewhere to be `SinglePlusAnyoneCanPay`: [2](#0-1) 
Per BIP-341/143, `SIGHASH_SINGLE` commits only to the output whose index equals the signed input's index (index 0 = user payout), and `ANYONECANPAY` restricts input commitment to only that one input. Consequently, the OP_RETURN output (added after the anchor output, i.e., not index 0) and any other outputs/inputs are entirely outside the signature's commitment. This means a transaction with the *same* input 0, witness, and output 0 can be rebuilt with an arbitrary OP_RETURN value and remains validly signed.

Both consumers trust this unauthenticated field unconditionally:
- `circuits-lib/src/bridge_circuit/mod.rs` `bridge_circuit()` extracts `operator_xonlypk` straight from `get_first_op_return_output(&input.payout_spv.transaction)` and feeds it into `deposit_constant(...)`, which is committed into `journal_hash` [3](#0-2) .
- `core/src/verifier.rs`'s `update_finalized_payouts` extracts the same field from the confirmed on-chain transaction and persists it as `payout_payer_operator_xonly_pk` [4](#0-3) , which `is_kickoff_malicious` later compares against the kickoff's claimed operator [5](#0-4) .

Exploit flow: attacker observes operator P's broadcast (but unconfirmed) payout tx, extracts input 0 (withdrawal outpoint) + its `SinglePlusAnyoneCanPay` witness + output 0 (unchanged, since it's covered by SIGHASH_SINGLE), constructs a new transaction reusing them but with a different OP_RETURN (naming a different/garbage pubkey X), adds their own fee-paying input(s) (permitted by ANYONECANPAY) with higher fee, and broadcasts to replace P's transaction via RBF before confirmation. If the attacker's version confirms, `update_finalized_payouts` records `X` (or `NULL`, if the pubkey is malformed) as `payout_payer_operator_xonly_pk` for that withdrawal, even though P is the one who actually paid the user. When P later sends its legitimate kickoff, `is_kickoff_malicious` finds `operator_xonly_pk (X or None) != kickoff_data.operator_xonly_pk (P)` and marks P's kickoff malicious, denying P reimbursement. Equivalently, in a bridge-circuit-driven Reimburse dispute, `deposit_constant`/`journal_hash` would embed the wrong operator identity, since `host_deposit_constant`/`bridge_circuit` read the same manipulated OP_RETURN from the transaction that ends up in `payout_spv.transaction`.

Existing guards do not close this gap: `SECP.verify_schnorr` in `core/src/operator.rs:632-637` only validates input/output-0 integrity, not the OP_RETURN; `is_kickoff_malicious` merely compares (already-corrupted) DB data against kickoff data and cannot detect that the DB data itself was poisoned via on-chain malleation; nothing in the circuit or verifier code independently re-derives/authenticates operator attribution from a source outside the OP_RETURN.

### Impact Explanation
This directly hits two Critical categories: "an operator reimbursed for a payout it never funded" (if X's OP_RETURN is chosen and X later kicks off) and "an honest operator permanently unable to be reimbursed" (P's legitimate kickoff is marked malicious because the DB/circuit now attributes the payout to someone else or to nobody). It is repeatable across every payout/deposit/operator because the mechanism (SIGHASH_SINGLE|ANYONECANPAY not covering the attribution OP_RETURN) is structural, not tied to a specific deposit. Blast radius: any withdrawal for which the payout tx has not yet confirmed is exploitable by any network observer with fee-bumping capability; each successful malleation nullifies or misattributes exactly one operator's reimbursement path for that withdrawal, and can be repeated per withdrawal.

### Likelihood Explanation
Preconditions: attacker must observe the operator's payout transaction while unconfirmed (mempool visibility, which is public), and must be able to construct/broadcast a competing, higher-fee transaction reusing the SIGHASH_SINGLE|ANYONECANPAY-signed input and witness — both are standard Bitcoin capabilities requiring no special key material, matching the stated unprivileged attacker capabilities (broadcast transactions, pay fees). Cost is limited to the fee premium needed to win the RBF race. No mainnet or live Citrea is needed to demonstrate the signature/commitment gap itself (it can be shown purely via sighash construction), though full end-to-end confirmation-race demonstration would need a regtest/mempool. This is feasible and repeatable per withdrawal.

### Recommendation
Change the payout transaction's user signature to cover the OP_RETURN output as well — e.g. require `SIGHASH_ALL` (or a custom sighash covering all outputs) instead of `SinglePlusAnyoneCanPay`, or otherwise cryptographically bind the operator's x-only pubkey into the input authorization (e.g., include it as part of the signed message/tagged commitment) so it cannot be altered without invalidating the user's signature. Alternatively, require operator attribution to be established via a source that cannot be malleated (e.g., a pre-committed operator identity submitted through the trusted deposit/kickoff signing flow) rather than solely trusting the OP_RETURN of the on-chain payout transaction.

### Proof of Concept
```rust
// cargo test in core/, demonstrating the sighash does not commit to the OP_RETURN output.
#[tokio::test]
async fn test_payout_op_return_malleable_under_single_anyonecanpay() {
    // 1. Build a payout tx exactly like create_payout_txhandler with operator P's xonly pk in OP_RETURN.
    let payout_p = builder::transaction::create_payout_txhandler(
        input_utxo.clone(), output_txout.clone(), operator_p_xonly_pk, user_sig, network,
    ).unwrap();

    // 2. Compute sighash for input 0 with SinglePlusAnyoneCanPay - this is what user_sig commits to.
    let sighash_p = payout_p.calculate_sighash_txin(0, TapSighashType::SinglePlusAnyoneCanPay).unwrap();

    // 3. Build an alternate payout tx with SAME input_utxo/output_txout/user_sig but a DIFFERENT
    //    OP_RETURN naming operator X (an unrelated, or garbage, pubkey).
    let payout_x = builder::transaction::create_payout_txhandler(
        input_utxo, output_txout, operator_x_xonly_pk, user_sig, network,
    ).unwrap();
    let sighash_x = payout_x.calculate_sighash_txin(0, TapSighashType::SinglePlusAnyoneCanPay).unwrap();

    // ASSERTION 1 (binding LHS==RHS before): sighash used by user_sig is identical regardless of
    // which operator pubkey is placed in the OP_RETURN, proving the OP_RETURN is unauthenticated.
    assert_eq!(sighash_p, sighash_x);

    // ASSERTION 2: both txs are independently valid (schnorr verification succeeds for user_sig
    // against both variants), confirming the malleation preserves signature validity.
    SECP.verify_schnorr(&user_sig.signature, &Message::from_digest(*sighash_p.as_byte_array()), &user_xonly_pk).unwrap();
    SECP.verify_schnorr(&user_sig.signature, &Message::from_digest(*sighash_x.as_byte_array()), &user_xonly_pk).unwrap();

    // 4. Feed payout_x into update_finalized_payouts-equivalent logic (get_first_op_return_output +
    //    parse_op_return_data) and show it returns operator_x_xonly_pk, not operator_p_xonly_pk,
    //    even though input 0/output 0 (the actually-funded value) are unchanged from P's tx.
    let extracted = parse_op_return_data(&get_first_op_return_output(&CircuitTransaction::from(payout_x.get_cached_tx().clone())).unwrap().script_pubkey).unwrap();
    assert_eq!(extracted, operator_x_xonly_pk.serialize());
    assert_ne!(extracted, operator_p_xonly_pk.serialize());
}
```
This demonstrates the equality `sighash(payout tx signed by user) == sighash(payout tx with mutated OP_RETURN)` holds, i.e., the binding "OP_RETURN operator == actual funder" is not enforced by any signature, and that `get_first_op_return_output`/`parse_op_return_data` (used identically by both `update_finalized_payouts` and `bridge_circuit`) will report whichever operator pubkey ends up in the confirmed transaction's OP_RETURN, regardless of who actually funded input 0/output 0.
