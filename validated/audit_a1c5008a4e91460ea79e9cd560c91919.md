## Title
State-commitment veto on `EvmHost` resets `_latestStateMachineHeight` to a fixed sentinel instead of the real previous height, permitting silent overwrite of already-verified, non-vetoed state commitments — (File: `evm/src/core/EvmHost.sol`)

### Summary
`deleteStateMachineCommitmentInternal` in `evm/src/core/EvmHost.sol` (lines 714-732) is the EVM analog of the reported "un-finalization" bug: when a state commitment that happens to be the *latest* one is vetoed, the code does not restore the pointer to the actual prior-valid height — it hard-resets `_latestStateMachineHeight[stateMachineId]` to the sentinel value `1`, unconditionally. [1](#0-0) 

This is the exact same class of bug as the report: a single "restore" value/pointer is applied without regard to what the *actual* correct prior value should be for that specific target. Hyperbridge's own Substrate implementation fixes this correctly by tracking a dedicated `PreviousStateMachineHeight` map and restoring that real value on veto: [2](#0-1) [3](#0-2) 

The EVM `EvmHost.sol` has no equivalent `_previousStateMachineHeight` map — it only ever has "the latest" (`_latestStateMachineHeight`) and, on veto of that latest height, blindly clamps to `1` rather than to the real last-known-good height (e.g. 1000).

### Finding Description
`HandlerV2.handleConsensus` gates acceptance of a new intermediate state purely on it being greater than the stored "latest height", with **no check that a commitment doesn't already exist at that height**: [4](#0-3) 

Compare this to the Substrate consensus handler, which explicitly skips any height where a commitment is already stored (`if host.state_machine_commitment(state_height).is_ok() { continue; }`): [5](#0-4) 

The EVM handler has no such de-duplication — it relies entirely on `latestStateMachineHeight` being a correct high-water mark to prevent re-processing of already-finalized heights. Once a fisherman vetoes the *latest* commitment (height N), `_latestStateMachineHeight` is reset to `1` instead of to the real previous height (say, N-1000). Every height in the range `[1, N-1000)` — heights that were legitimately verified, are not vetoed, and are actively relied upon by relayers/apps for message delivery and withdrawal-proof verification — becomes re-writable: any subsequent consensus proof can supply "intermediate states" for those heights and `storeStateMachineCommitment` will silently overwrite `_stateCommitments[stateMachineId][height]` for them, because the only guard (`intermediate.height > latestHeight`) now trivially passes. [6](#0-5) 

This breaks the core Hyperbridge invariant that "consensus proofs, state proofs, challenge periods, and state commitments must never let false remote state become trusted": a previously-finalized, un-vetoed `StateCommitment` for a height can be replaced by a different (potentially attacker-influenced, since it comes from whatever the next verified consensus proof happens to contain for that height) commitment, without ever going through the normal append-only, monotonic-height acceptance path or a fresh challenge period tied to that specific height's original acceptance. Any request/response/withdrawal proof that had already been verified and delivered against the old commitment for that height becomes replaceable, and new proofs (e.g. `handlePostRequests`, `handleGetResponses`) can be forged against the new, overwritten commitment for a height that observers believed was long settled — a false-state-acceptance / state-manipulation primitive.

### Impact Explanation
This falls squarely in "false proof/state acceptance" and "transaction manipulation": once the sentinel reset occurs, an attacker who can also produce (or wait for) an intermediate state at one of the now-reopened lower heights can substitute a different `StateCommitment` for that height. Anything gated by `stateMachineCommitment(height).overlayRoot` — `handlePostRequests`, `handleGetResponses`, and downstream fund-moving flows (relayer fee payouts, intent-gateway fills/refunds, bandwidth credits, paymaster asset flows) that trust a Merkle proof against that root — can then be proven against attacker-favorable leaves for a height range that was supposed to be immutable and already past its challenge period. This is a protocol-level state-integrity break, not merely a queue/DoS wart (the Substrate-side test suite explicitly documents the DoS-only side effect of the analogous reset; the EVM side additionally lacks the anti-replay `is_ok()` duplicate-commitment check, making the consequence a full overwrite rather than just wasted queue capacity).

### Likelihood Explanation
Triggering the reset itself requires only one veto of the current latest height via the handler's fraud-proof path (this is the intended, permissionless "fisherman" flow for reverting bad state — not a malicious-operator assumption; it is normal operation of the veto mechanism working as designed against a bad commitment). No malicious relayer, prover, or governance actor is required — the flaw is purely in what the *correct* protocol code does after an honest veto: it mis-restores the pointer. Any subsequent, otherwise-valid consensus update that includes an intermediate height in the reopened range will trigger the overwrite automatically, since `HandlerV2` performs no existing-commitment check.

### Recommendation
Add a `_previousStateMachineHeight` mapping on `EvmHost`, updated every time `storeStateMachineCommitment` advances `_latestStateMachineHeight` (mirroring `store_latest_commitment_height` in `modules/pallets/ismp/src/host.rs`), and have `deleteStateMachineCommitmentInternal` restore that tracked value instead of the constant `1`. Additionally, add a duplicate-commitment guard in `HandlerV2.handleConsensus` (skip/reject intermediate states for heights that already have a non-empty `StateCommitment`), matching the Substrate consensus handler's behavior, so that even a mis-tracked pointer cannot cause silent overwrites of already-verified state.

### Proof of Concept
1. Consensus proofs advance `stateMachineId` X to height 1000 legitimately; `_latestStateMachineHeight[X] = 1000`, with valid commitments stored for heights 1..1000.
2. A fisherman detects the commitment at height 1000 is fraudulent and calls the veto path, which invokes `deleteStateMachineCommitmentInternal(height=1000, fisherman)`.
   - Since `_latestStateMachineHeight[X] == 1000`, it is reset to `1` (not to 999 or any real prior height). [7](#0-6) 
3. A subsequent, otherwise-valid `ConsensusMessage` is submitted via `HandlerV2.handleConsensus` containing an intermediate state for height 500 (a height that already holds a legitimately verified, un-vetoed `StateCommitment`).
4. Because the only gate is `intermediate.height > latestHeight` (now `1`), height 500 passes and `host.storeStateMachineCommitment` overwrites `_stateCommitments[X][500]` with a new commitment — with no check that a commitment already existed there. [4](#0-3) 
5. Any later `handlePostRequests`/`handleGetResponses` call referencing `height=500` now verifies proofs against the newly substituted `overlayRoot`, allowing acceptance of requests/responses that were never part of the originally-finalized state at that height.

Note: I was not able to locate the exact caller of `deleteStateMachineCommitment` (the fisherman/fraud-proof entrypoint on `HandlerV2`) within the available index before the iteration limit was reached, so the precise permission model of the veto trigger on the EVM side is inferred from the Substrate-side `fishermen` pallet's equivalent (`veto_state_commitment`, gated by `IsCollator`) and from the `EvmHost.sol` comments referencing "fisherman" as the caller identity recorded in `_vetoes`. This does not affect the core finding — the storage-pointer mis-restoration and the missing duplicate-commitment check in `HandlerV2` are both directly confirmed in the cited code.

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
