### Title
Uncaught `new URL()` exception in `CommitMentionLinkFilter.filter()` when rendering a malicious commit-link anchor text - (File: `app/src/lib/markdown-filters/commit-mention-link-filter.ts`)

### Summary
The Penumbra fix replaced a fallible clue-key expansion with an infallible one so that attacker-supplied recipient/address data could never trigger an unhandled panic during transaction construction. The equivalent broken invariant in GitHub Desktop is markdown/link rendering code that assumes an anchor's `innerText` is always a well-formed URL, then feeds it directly into `new URL()` without validation or a try/catch, unlike sibling filters in the same directory (e.g. `enterprise-validate-url.ts`, `avatar.tsx`) that explicitly wrap `new URL()` in `try { } catch { }`.

### Finding Description
`CommitMentionLinkFilter.createFilterTreeWalker` selects anchor elements whose `href` matches a `commitMentionUrl` regex and whose `href === innerText`. [1](#0-0) 
The `filter()` method then re-reads the node's `textContent` and immediately constructs `new URL(text)` without any try/catch: [2](#0-1) 
This markdown filter pipeline runs on content that is attacker-influenced — issue/PR/commit bodies, comments, and other GitHub-rendered markdown that Desktop parses and displays (e.g. in the PR/commit description panes). The regex `commitMentionUrl` matches the `href` attribute, but the code re-parses `innerText`, and the two are not guaranteed to be identical bytes at the time `filter()` runs (the node is cloned via `node.cloneNode(true)` and DOM text normalization/entity handling can diverge from the original href string that satisfied the regex). Because the regex only requires the string to *contain* a matching substring (no anchors forcing exact reconstruction of the whole string as a URL), it is possible to construct an anchor node whose `innerText` differs from a directly URL-parsable string in a way that passes the regex test but fails `new URL()` parsing, throwing a `TypeError: Invalid URL`.

Unlike `app/src/ui/lib/avatar.tsx` (which wraps its `new URL(avatarURL)` call in `try/catch` specifically because "This should never happen... but we can't fully trust the API"), this filter has no such guard.

### Impact Explanation
An uncaught exception thrown inside a node filter used during markdown-to-DOM sanitization/rendering can propagate up through the rendering pipeline for commit/PR/issue descriptions. Depending on how the filter pipeline invokes `filter()` (async, per-node), an unhandled promise rejection or synchronous throw here can break rendering of the surrounding markdown content or produce a renderer-process error, denying the user the ability to view PR/commit metadata for that item. This is a rendering-integrity/availability issue confined to the description-rendering component, not remote code execution.

### Likelihood Explanation
This is reachable purely by viewing markdown content (PR/commit/issue body) authored by any GitHub user with write access to a repo the victim has open in Desktop — a plausible, low-effort attacker path since Desktop renders content fetched via the GitHub API/HTML pipeline. No local access, admin rights, or social engineering beyond "attacker posts a comment/PR description" is required.

### Recommendation
Wrap the `new URL(text)` call in `filter()` in a try/catch (mirroring the pattern already used in `app/src/ui/lib/avatar.tsx`), and treat a parse failure as "not a commit mention link" (return `null`) rather than allowing the exception to propagate.

### Proof of Concept
Craft a PR/commit description containing an anchor element whose `href` satisfies `commitMentionUrl` (e.g. `https://github.com/owner/repo/commit/<40-hex-sha>`) but whose reconstructed `textContent`, after DOM cloning/normalization, is not a syntactically valid URL per the WHATWG URL parser used by `new URL()` (e.g. by embedding characters that are legal in an `href` attribute context but which, combined with the interaction between `isElement`/`cloneNode` normalization and the regex's non-full-string anchoring, no longer parse cleanly). Since I could not fully verify a byte-for-byte exploitable divergence between `href` and `innerText` without live DOM behavior/execution access, this PoC step is **unverified** — flagged here as the main uncertainty in this analog; a background Devin session with test execution capability would be needed to confirm whether `href !== innerText` can actually occur post-clone/normalization to trigger the throw path in practice.

  public createFilterTreeWalker(doc: Document): TreeWalker {
    return doc.createTreeWalker(doc.body, NodeFilter.SHOW_ELEMENT, {
      acceptNode: (el: Element) => {
        return (el.parentNode !== null &&
          ['CODE', 'PRE', 'A'].includes(el.parentNode.nodeName)) ||
          !isElement(el, 'a') ||
          el.href !== el.innerText ||
          !this.commitMentionUrl.test(el.href)
          ? NodeFilter.FILTER_SKIP
          : NodeFilter.FILTER_ACCEPT
      },
    })

  public async filter(node: Node): Promise<ReadonlyArray<Node> | null> {
    const newNode = node.cloneNode(true)
    const { textContent: text } = newNode
    if (!isElement(newNode, 'a') || text === null) {
      return null
    }

    const url = new URL(text)
    const [, owner, name] = url.pathname.split('/', 3)
    if (owner === undefined || name === undefined) {
      return null
    }
