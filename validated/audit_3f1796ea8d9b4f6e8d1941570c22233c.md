Audit Report

## Title
Precompile signature-count accounting trusts an unvalidated `data[0]` byte, decoupling declared CU/fee cost from real verification work - ([File: runtime-transaction/src/signature_details.rs])

## Summary
`get_num_signatures_in_instruction` derives the "signature count" for secp256k1/ed25519/secp256r1 precompile instructions solely from `instruction.data.first()`, with no validation that the remaining instruction data can actually contain that many signature-offset structures. [1](#0-0)  This unvalidated value is fed into `PrecompileSignatureDetailsBuilder::process_instruction`, which accumulates it into per-transaction signature counters before the real precompile verifier ever checks the data length. [2](#0-1)  Those counters are then multiplied by fixed per-signature CU costs in `CostModel::get_signature_cost`, so an attacker can inflate the reported signature-verification cost far beyond what the (necessarily failing) instruction actually performs. [3](#0-2) 

## Finding Description
`get_num_signatures_in_instruction` reads only `data[0]` and treats it as authoritative: [1](#0-0) 

This value is unconditionally added to the running total in `process_instruction` based purely on program-id matching, with no data-length check at this point: [2](#0-1) 

The real validation exists only inside the precompile `verify()` functions, which compute `expected_data_size` from the same `data[0]` byte and reject the instruction if the data is too short: [4](#0-3) 

This confirms the structural gap the claim describes: the cost/fee accounting layer consumes `data[0]` before the length-consistency check that the real verifier performs, so the two can diverge — a minimal, malformed instruction (`data = [255]`) is guaranteed to fail `verify()` immediately while still contributing `255 * SECP256K1_VERIFY_COST` (or the ed25519/secp256r1 equivalents) to the computed `signature_cost`, as seen in `CostModel::get_signature_cost`: [3](#0-2) 

I additionally verified that `CostModel::calculate_cost_for_executed_transaction`, which is used for post-execution cost accounting, still calls the same `get_signature_cost(transaction)` derived from the static, unvalidated `data[0]` value — it is not reconciled against whether the precompile actually verified anything, since only `programs_execution_cost` and `loaded_accounts_data_size_cost` are supplied as "actual" values. [5](#0-4)  This means the inflated signature cost is not corrected even after the transaction/precompile instruction fails.

## Impact Explanation
This is a real, reachable decoupling between "declared" and "actual" work for the precompile-signature-count accounting value, confirmed by direct code inspection of `signature_details.rs`, `cost_model.rs`, and the precompile `verify()` implementations. However, I was unable to fully trace, within the remaining tool budget, whether this inflated `signature_cost` actually translates into a block-cost-limit exhaustion or scheduler-degradation effect strong enough to meet the "non-RPC remote exhaustion/crash" bar required by the target scopes. Specifically, I could not confirm within available iterations how `cost_tracker.rs` combines `signature_cost` with `MAX_BLOCK_UNITS`/`MAX_WRITABLE_ACCOUNT_UNITS`, nor whether per-block cost reservations for such degenerate transactions are released or reconciled after a failed precompile instruction, nor how much practical throughput degradation this can cause given a leader's actual block-packing behavior (transactions are also bounded by declared `compute_unit_limit`, packet size, and other independent limits). Without that missing link, this remains a real accounting-integrity gap in principle (the value used for `signature_cost` genuinely does not reflect real verification work), but I cannot confirm from the code I reviewed that it rises to a concrete, exploitable "resource exhaustion/degradation" impact under the stated target scopes without further verification of `cost_tracker.rs`'s block-limit enforcement and consumer-side reconciliation behavior — this is a known limitation of my investigation, not a claim that the impact does not exist.

## Likelihood Explanation
Constructing an instruction with `data[0]` set to a large value and truncated remaining payload requires no privilege and no cryptographic material — this part of the claim is fully substantiated by the code and trivially reproducible. [1](#0-0) [4](#0-3) 

## Recommendation
Validate that `instruction.data.len()` is sufficient to hold `count * OFFSETS_SERIALIZED_SIZE + DATA_START` bytes in `get_num_signatures_in_instruction` (or its caller), mirroring the `expected_data_size` check already performed inside each precompile's `verify()`, before using `data[0]` for cost/fee accounting. Alternatively, clamp the counted signatures to the maximum count structurally supportable by the instruction's actual data length.

## Proof of Concept
1. Build a transaction with a single instruction targeting `solana_sdk_ids::secp256k1_program::ID` with `data = vec![255]` and no additional payload.
2. Observe that `get_precompile_signature_details` sets `num_secp256k1_instruction_signatures = 255` purely from `data[0]`. [1](#0-0) 
3. Observe that `CostModel::get_signature_cost` multiplies this by `SECP256K1_VERIFY_COST`, producing a signature_cost on the order of ~1.7M CU. [3](#0-2) 
4. Observe that `agave_precompiles::secp256k1::verify` computes `expected_data_size = 255 * SIGNATURE_OFFSETS_SERIALIZED_SIZE + 1`, sees `data.len() == 1`, and returns `PrecompileError::InvalidInstructionDataSize` immediately — no real verification work occurs. [4](#0-3) 
5. Further investigation is needed in `cost-model/src/cost_tracker.rs` and `core/src/banking_stage/consumer.rs` to determine whether this inflated cost causes measurable block-cost-limit exhaustion or scheduling degradation in practice, which I was unable to complete within the available tool budget.

    /// Returns signature details and the total signature cost
    fn get_signature_cost(transaction: &impl TransactionMeta) -> u64 {
        let signatures_count_detail = transaction.signature_details();

        signatures_count_detail
            .num_transaction_signatures()
            .saturating_mul(SIGNATURE_COST)
            .saturating_add(
                signatures_count_detail
                    .num_secp256k1_instruction_signatures()
                    .saturating_mul(SECP256K1_VERIFY_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_ed25519_instruction_signatures()
                    .saturating_mul(ED25519_VERIFY_STRICT_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_secp256r1_instruction_signatures()
                    .saturating_mul(SECP256R1_VERIFY_COST),
            )
    }
