Confirmed: `placeOrder()` never bounds the number of `order.inputs` (or `order.output.assets`) entries — the only checks are `order.inputs.length == 0` revert and per-entry `amount == 0` checks. [1](#0-0) [2](#0-1) 

### Title
Unbounded `order.inputs`/output-token array lets `withdraw()` permanently exceed the block gas limit, locking escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` loops over `body.tokens` (derived directly from an order's `inputs`/output assets) and performs one external `call`/`transfer` per token. Because `placeOrder()` imposes no upper bound on the number of input or output tokens a user can specify, an order can be crafted with an arbitrarily large token array. When the corresponding `RedeemEscrow`/`RefundEscrow` message comes back through the host (`onAccept` → `withdraw`), or through `onGetResponse` → `withdraw`, the loop's gas cost scales with that array length and can exceed the block gas limit, causing the transaction to always revert — permanently locking the escrowed tokens. This is the exact bug class from the referenced report (unbounded loop with external calls, no ability to batch), just relocated from FactoryDAO's reward withdrawal to Hyperbridge's intent-escrow redemption/refund path.

### Finding Description
`placeOrder()` only validates `order.inputs.length == 0` and duplicate output tokens; it never caps `inputs.length` or `output.assets.length`. [3](#0-2) 
Every input token triggers a `safeTransferFrom` at order placement time, so the attacker (the order creator) pays the escrow-side gas cost themselves, and there is no gas-limit check preventing an order with hundreds of low-value input tokens from being placed. [2](#0-1) 

Later, when the order is filled or refunded, the escrow contract must release/refund those same tokens via `withdraw()`, which is invoked either from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests coming from the host, or from `onGetResponse()` for GET-response-driven refunds: [4](#0-3) [5](#0-4) 

`withdraw()` iterates the full `body.tokens` array with one external call per element and no batching/offset parameter: [6](#0-5) 

Unlike the original C4 finding where the caller controls the withdrawal batch and can retry with different reward-array subsets, here `withdraw()` is only reachable via the ISMP message-handling entrypoints (`onAccept`/`onGetResponse`), which decode `body.tokens` directly from the cross-chain message and never allow specifying an offset/length. If the array is large enough that the loop's gas cost (many `CALL` opcodes, one per token, each with its own 2300+ gas stipend/cold-account-access cost) exceeds the block gas limit, the transaction can never succeed regardless of how it is retried — there is no code path to redeem/refund a subset of `body.tokens`.

### Impact Explanation
Because the escrowed input tokens are held by the gateway contract and the only release path is the atomic `withdraw()` loop, an order with a sufficiently large `inputs` array causes both the "fill" settlement (`RedeemEscrow`) and the "refund" settlement (`RefundEscrow`) to permanently revert. This results in a genuine, permanent loss/lock of user (and solver) funds in escrow — matching the bounty's "stealing or loss of funds" / "logic attacks" impact category, since neither the order creator can be refunded nor can a solver's rightful fill payout be released.

### Likelihood Explanation
Any unprivileged user calling `placeOrder()` can construct this condition — no permission, relayer collusion, or admin action is required, satisfying the "unprivileged attacker" requirement. The number of tokens needed to exceed a target chain's block gas limit is bounded but achievable with cheap ERC20/native token entries (the only cost to the attacker is gas for `placeOrder()` and enough token balance for tiny per-token amounts, or address(0) native-token entries requiring no balance transfer at all beyond `msg.value` bookkeeping). This makes the attack self-funded and cheap relative to the value it can permanently lock.

### Recommendation
- Enforce a maximum length on `order.inputs` and `order.output.assets` in `placeOrder()` (and equivalently in `ExtrinsicIntents`/`IntrinsicIntents` order-creation paths) sized so that `withdraw()`'s per-token loop can never approach the block gas limit.
- Alternatively (or additionally), redesign `withdraw()` to support partial/batched redemption — e.g., track per-token claimed status keyed by `(commitment, token)` and allow `withdraw()` to be invoked repeatedly for a bounded subset of `body.tokens`, mirroring the C4 recommendation of adding offset/length parameters — so a large order can still be fully settled across multiple transactions even if a single pass would exceed gas limits.

### Proof of Concept
1. Attacker calls `placeOrder()` with `order.inputs` containing e.g. 2,000 distinct ERC20 tokens (or the native-token sentinel `address(0)` entries mixed with dust-amount ERC20 approvals), each entry with a minimal non-zero `amount`. `placeOrder()` accepts this with no length cap. [1](#0-0) 
2. A solver fills the order (or the deadline passes and a refund is requested), producing a `RedeemEscrow`/`RefundEscrow` message that is eventually delivered back to `IntentGatewayV2` via `onAccept`. [4](#0-3) 
3. `withdraw()` executes the per-token loop over all 2,000 entries, each doing a `CALL`/ERC20 `transfer`; the cumulative gas cost exceeds the destination chain's block gas limit, and the transaction reverts unconditionally, on every retry. [6](#0-5) 
4. Because there is no alternate code path to redeem a subset of `body.tokens`, the escrowed tokens for this order remain locked in the `IntentGatewayV2` contract indefinitely.

        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;

            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
