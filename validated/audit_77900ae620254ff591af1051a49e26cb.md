### Title
`resolveWithin()` returns a valid path instead of `null` for sibling-directory traversal, exposed via the `x-github-client://openRepo` deep link's `filepath` parameter - ([File: app/src/lib/path.ts])

### Summary
Like the Compound-oracle finding — where `getUnderlyingPrice()` was expected to return a safe sentinel (`0`) on failure but instead behaved unexpectedly, breaking the caller's error-handling invariant — GitHub Desktop's `_resolveWithin()` helper is expected to return `null` whenever a resolved path escapes the given root directory, so callers can safely reject it. Its containment check uses a raw string-prefix comparison that does not enforce a path-separator boundary, so it can return a *non-null, "safe-looking"* path for targets that are actually outside the intended repository root.

### Finding Description
`_resolveWithin()` in `app/src/lib/path.ts` validates that a resolved path is contained within `rootPath` like this: [1](#0-0) 

The containment check `realResolved.startsWith(realRoot)` treats any path whose string representation begins with `realRoot` as "inside" the root — without requiring that the next character be a path separator. This means a resolved path such as `/Users/alice/Projects/myrepo-secrets/notes.txt` passes the check against a root of `/Users/alice/Projects/myrepo`, even though `myrepo-secrets` is a sibling directory, not a subdirectory.

This function is relied upon by `Dispatcher.openRepositoryFromUrl()` to gate the `filepath` action of the `x-github-client://openRepo/...` deep link — a value fully controlled by whoever crafts the link (an attacker-controlled web page, README, or "Open in Desktop" button): [2](#0-1) 

The `filepath` value originates directly from `parseAppURL()`'s query-string parsing with no path-shape validation beyond the `isAbsolute()` check: [3](#0-2) 

Because `resolveWithin` is the *only* guard preventing `filepath` (relative, containing `../` segments) from escaping the cloned repository directory, and its containment check is a naive `startsWith`, a `filepath` such as `../myrepo-something/secret.txt` (crafted relative to the resolved repository directory name) will be treated as "inside" the repository and passed on to `shell.showItemInFolder(resolved)` — revealing/opening a file outside the repository the user actually intended to browse.

### Impact Explanation
The broken invariant is: "a validator that is supposed to return `null`/fail-closed on an out-of-bounds path may instead return a seemingly valid path." Concretely this can cause Desktop, in response to a link the user clicks, to reveal/open a file that lives outside the cloned repository, in a sibling directory whose name happens to share the repository directory name as a prefix. This matches the accepted impact class "a link or deep link the user clicks... results in... file read outside the repo." The severity is bounded by the requirement that a suitably-named sibling directory exist on disk (e.g. `myrepo` next to `myrepo-old`, `myrepo-backup`, `myrepo2`, `myrepo.bak`), which is a common real-world naming pattern for cloned/forked/backup repositories.

### Likelihood Explanation
Exploitation requires no local access, malware, or credentials — only that the victim click an attacker-supplied `x-github-client://openRepo/...&filepath=...` (or `github-mac://`/`github-windows://` equivalent) URL while they already have a repository cloned whose sibling directory naming happens to satisfy the prefix collision. This is a plausible but not universal precondition, so likelihood is moderate rather than guaranteed on every target, but the underlying code defect (missing separator check in a security-sensitive path-containment primitive) is unconditional and affects every call site of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, not just this one.

### Recommendation
Fix `_resolveWithin()` in `app/src/lib/path.ts` to require an exact match or a boundary separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(with the equivalent `sep` for the `win32`/`posix` variants). Audit all call sites (`dispatcher.ts` `openRepositoryFromUrl`, and any other consumers) to confirm they only proceed when a non-null value is returned, and add regression tests asserting that a root of `.../myrepo` rejects `.../myrepo-evil/...` targets.

### Proof of Concept
1. Locally have two directories side by side, e.g. `~/Projects/myrepo` (a Desktop-tracked repository) and `~/Projects/myrepo-secret/passwords.txt` (any sibling whose name is prefixed by the repo's directory name).
2. Craft a malicious link: `x-github-client://openRepo/https://github.com/<owner>/myrepo?filepath=../myrepo-secret/passwords.txt`.
3. Victim, who already has `myrepo` open in Desktop, clicks the link (e.g. from a webpage or a "Open in Desktop" button on a malicious site).
4. `parseAppURL` extracts `filepath = '../myrepo-secret/passwords.txt'`; `isAbsolute()` returns `false` so the absolute-path guard is bypassed; `resolveWithin(repository.path, filepath)` normalizes/resolves to `~/Projects/myrepo-secret/passwords.txt`, whose `realpath` starts with the string `realRoot` (`~/Projects/myrepo`) despite being a sibling directory, so the function incorrectly returns the resolved path instead of `null`.
5. `shell.showItemInFolder(resolved)` reveals/opens `passwords.txt`, a file outside the intended repository, confirming the containment bypass predicted by the `startsWith` prefix flaw.
