## Analysis

The zlib CVE is a heap buffer over-read where a length field parsed from untrusted input (the gzip header "extra field" length) is used to drive further reads without validating that the declared length actually fits within the remaining buffer. The closest reachable analog in this repo is the unbounded length-prefix walk in `is_atom_canonical()` / `is_clvm_canonical()` in `chia/full_node/mempool_manager.py`, which parses attacker-controlled CLVM atom length prefixes byte-by-byte without ever checking the computed offset against `len(clvm_buffer)`. [1](#0-0) 

Unlike the well-bounded helpers in `chia/full_node/full_block_utils.py` (`skip_bytes`, `skip_list`, the version-1 generator length check), which explicitly validate `n > len(buf)` before slicing: [2](#0-1) 

`is_atom_canonical()` reads `clvm_buffer[offset]` in a loop for `prefix_len` (0–5) additional bytes, where `prefix_len` and the resulting `atom_len` are entirely derived from the untrusted buffer's own high-order bits, with no bounds check that `offset` remains within `len(clvm_buffer)`: [3](#0-2) 

`is_clvm_canonical()` then advances `offset` by the returned `atom_len` (which can itself be attacker-inflated) and keeps indexing `clvm_buffer[offset]` on each loop iteration without a bounds check before dereferencing: [4](#0-3) 

This function is invoked during mempool spend-bundle validation to determine DEDUP/fast-forward eligibility of solutions, per the project's own documentation: [5](#0-4) 

Because `bytes.__getitem__` with an out-of-range integer index raises `IndexError` in Python (there is no silent short-read the way memoryview slicing tolerates), a crafted solution/atom whose trailing length-prefix byte declares a `prefix_len` that runs past the end of the buffer will raise an unhandled `IndexError` from inside `is_atom_canonical`. I was not able to fully trace, within the remaining tool budget, whether the caller of `is_clvm_canonical` in the DEDUP-eligibility path wraps this call in a broad exception handler; that is the one piece of uncertainty in this finding, and it should be verified directly against `pre_validate_spendbundle()` / `can_fast_forward_singleton` call sites before treating this as confirmed-exploitable rather than merely a defensive gap.

### Title
Unbounded length-prefix walk in `is_atom_canonical()` can read past buffer end on attacker-supplied CLVM solutions - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` parse CLVM atom length prefixes directly from attacker-controlled solution bytes and advance an offset using values taken from that same untrusted buffer, without validating the offset against the buffer length before each dereference — the same "trust the embedded length field" bug class as CVE-2022-37434's gzip extra-field parsing in zlib.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads `b = clvm_buffer[offset]`, derives `prefix_len` (0–5) from the top bits of `b`, and then loops `prefix_len` times doing `offset += 1; atom_len |= clvm_buffer[offset]` with no check that `offset < len(clvm_buffer)` at any point in that loop (`chia/full_node/mempool_manager.py:177-183`). Its caller, `is_clvm_canonical()`, keeps advancing `offset` by the (attacker-influenced) `atom_len` and re-reads `clvm_buffer[offset]` each iteration, again without a bounds check preceding the dereference (`chia/full_node/mempool_manager.py:196-221`). Every other buffer-walking helper in the codebase that processes untrusted, length-prefixed wire data (e.g. `skip_bytes`, `skip_list`, and the versioned generator-buffer parsing in `chia/full_node/full_block_utils.py:27-34, 256-267`) explicitly checks the declared length against the remaining buffer before slicing. `is_clvm_canonical`/`is_atom_canonical` lack this check entirely.

### Impact Explanation
A malformed length prefix near the end of a submitted spend bundle's CLVM solution can cause `clvm_buffer[offset]` to index past the end of the buffer, raising an unhandled `IndexError`. If this exception is not caught by the caller performing DEDUP/fast-forward eligibility checks during spend-bundle admission, it propagates as an unhandled exception in mempool processing, which is a spend-triggered transaction-processing disruption reachable from a single unprivileged spend-bundle submission.

### Likelihood Explanation
Any wallet user or spend-bundle submitter can construct a solution whose trailing atom encodes a truncated multi-byte length prefix; this requires no special privileges, peer position, or timing, only crafting the byte sequence of a coin spend's solution.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access inside the `prefix_len` loop (mirroring the `n > len(buf)` checks used in `chia/full_node/full_block_utils.py`), and add the same length validation in `is_clvm_canonical()`'s main loop before dereferencing `clvm_buffer[offset]`, returning "not canonical" (or raising a caught/handled error) instead of allowing an `IndexError` to escape. Additionally, confirm that all call sites of `is_clvm_canonical` in the spend-bundle admission path catch and convert any parsing exception into a normal validation rejection.

### Proof of Concept
Construct a CLVM buffer whose final byte is `0xFC` (indicating a 5-byte extended length prefix, the `elif (b & 0b11111110) == 0b11111100` branch) with fewer than 5 bytes following it before the buffer ends, e.g. `bytes([0x81, 0xFC])`. Calling `is_clvm_canonical(bytes([0x81, 0xFC]))` (or feeding this as part of a submitted spend bundle's solution to whatever code path invokes `is_clvm_canonical` for DEDUP eligibility) drives `is_atom_canonical` to increment `offset` past index 1 and index `clvm_buffer[offset]` out of range, raising `IndexError: index out of range` instead of returning a graceful "not canonical" result.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def skip_bytes(buf: memoryview) -> memoryview:
    if len(buf) < 4:
        raise ValueError(f"byte length prefix requires 4 bytes, remaining buffer {len(buf)}")
    n = int.from_bytes(buf[:4], "big", signed=False)
    buf = buf[4:]
    if n > len(buf):
        raise ValueError(f"byte length {n} exceeds remaining buffer {len(buf)}")
    return buf[n:]
```
