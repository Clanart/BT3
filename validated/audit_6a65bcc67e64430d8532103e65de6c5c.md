### Title
`SignableTransaction::new` excludes the OP_RETURN data output from weight/fee estimation, underestimating the needed fee and bypassing the max-weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the MozBridge bug — where the LayerZero fee was quoted on a shorter placeholder payload than the message actually sent — `SignableTransaction::new` builds the real transaction with an OP_RETURN output carrying up to 80 bytes of caller-supplied `data`, but computes `vbytes`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check on a skeleton transaction that omits that output entirely. The fee is therefore charged for a transaction smaller than the one actually broadcast.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is pushed into `tx_outs` before any size estimation occurs:

- The OP_RETURN output is appended to `tx_outs` at send.rs:194-202.
- Weight/vbytes are then computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204 — note it is passed `payments`, not `tx_outs`, so the data output is invisible to the estimator.
- `needed_fee = fee_per_vbyte * vbytes` and the minimum-relay-fee check use that underestimated `vbytes` (send.rs:206-213).
- The change path repeats the same mistake: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at send.rs:225-226 again omits the data output, and the change amount is computed as `input_sat - (payment_sat + fee_with_change)` (send.rs:228-230), locking in the undercharged fee.
- Finally, `weight > MAX_STANDARD_TX_WEIGHT` is checked against the underestimated `weight` (send.rs:241-242), so a transaction whose true weight exceeds the standardness limit is accepted.

Inside `calculate_weight_vbytes` (send.rs:62-127), the mock transaction's `output` list is built solely from `payments` plus optional `change` (send.rs:85-99); there is no parameter by which the data output could be included. An 80-byte OP_RETURN adds roughly 91+ bytes of real transaction weight (~91 weight units for the script plus fixed output overhead) that is never priced. This mirrors the report exactly: the estimation payload is structurally shorter than the payload actually sent, and the fix (like the audited fix) must estimate on the true output set.

### Impact Explanation
When `data` is supplied, the transaction is created with a `needed_fee` (and, if change exists, a change amount) corresponding to a smaller vsize than the broadcast transaction. The effective fee rate of the signed transaction is below the caller-specified `fee_per_vbyte` — with a full 80-byte OP_RETURN, roughly 15-25% below depending on transaction size — which can push it below relay/mining thresholds or delay confirmation, leaving funds in-flight in a transaction that won't confirm at the intended rate. Additionally, the `TooLargeTransaction` guard can be bypassed: a transaction near the weight limit plus a data output may exceed `MAX_STANDARD_TX_WEIGHT` without error, producing a non-standard, unrelayable transaction. The direct consequence is a transaction paying materially less than the intended fee rate and potentially being unbroadcastable, degrading to a liveness/funds-stuck issue for outputs it spends.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is called with a non-`None` `data` argument — no attacker sophistication is required, only use of the documented `data` parameter (up to 80 bytes is explicitly permitted by the `TooMuchData` bound at send.rs:171-173). Callers who pass `None` (as `processor/src/networks/bitcoin.rs` currently does) are unaffected, which bounds the current exposure, but the public API explicitly supports data-carrying transactions and any such call misprices the fee and skips part of the weight check.

### Recommendation
Compute weight/vbytes over the exact output set that will be broadcast. Either pass the final `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or add the data output to the `payments`-style slice used for estimation before calling it — i.e., estimate on the true payload rather than a placeholder subset, matching the "use the correct payload for estimating fees" remediation. The same corrected weight must feed both `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check, and the change path must use the corrected `vbytes_with_change`.

### Proof of Concept
```rust
// networks/bitcoin: construct a SignableTransaction carrying 80 bytes of OP_RETURN data
let data = Some(vec![0u8; 80]);
let tx = SignableTransaction::new(inputs, &payments, Some(change_addr), data.clone(), FEE).unwrap();

// The broadcast transaction includes the OP_RETURN output ...
assert!(tx.tx.output.iter().any(|o| o.script_pubkey.is_op_return()));

// ... but needed_fee was priced from a skeleton WITHOUT it.
// Recompute the true vsize including the data output:
let skeleton_vbytes = SignableTransaction::calculate_weight_vbytes(inputs.len(), &payments, Some(&change_addr)).1;
let actual_vbytes = /* vsize of tx.tx after signing, including the OP_RETURN output */;
assert!(actual_vbytes > skeleton_vbytes);            // ~90+ vbytes unpriced
assert_eq!(tx.needed_fee(), FEE * skeleton_vbytes);  // fee for the smaller tx
// Effective fee rate of the broadcast tx: needed_fee / actual_vbytes < FEE
```
Similarly, choosing `payments`/`inputs` such that the skeleton weight is just below `MAX_STANDARD_TX_WEIGHT` and adding the 80-byte data output yields `Ok(SignableTransaction)` whose real weight exceeds the standardness limit, demonstrating the bypassed `TooLargeTransaction` check at send.rs:241.
