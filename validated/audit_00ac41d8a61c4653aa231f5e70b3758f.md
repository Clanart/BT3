## Analysis

The confirmed mechanism: `matchGitHubRepository` derives an `owner`/`name` purely by regex-parsing the local remote's URL text [1](#0-0) , and `repositoryWithRefreshedGitHubRepository` then blindly calls `api.fetchRepository(owner, name)` on that endpoint on every periodic refresh [2](#0-1) . Whatever repository object the GitHub API returns for that `owner/name` pair at that point in time is trusted, and if the remote hasn't been "manually changed" (i.e., `remoteUrlUnchanged` still holds) and protocols match, `updateRemoteUrl` will silently execute `git remote set-url` to the API's `clone_url` — with no user prompt, confirmation dialog, or diff shown [3](#0-2) . This exactly mirrors the `setMultisig` pattern: a "receiving address" (here, the push/fetch destination) that is *supposed* to only be adjusted for a legitimate reason (repo renames), but the code enforces no time bound or ownership check — it will happily follow the `owner/name` slug forever, silently, as long as the user never touches the remote manually.

### Title
Automatic silent remote-URL rewrite (`updateRemoteUrl`) trusts GitHub API `clone_url` for `owner/name`, enabling repo-name-squatting redirection of push/fetch targets - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` automatically calls `git remote set-url` on the user's `origin` remote whenever the periodic GitHub API refresh (`repositoryWithRefreshedGitHubRepository`) returns a `clone_url` that differs from the current remote, provided the remote "hasn't been manually changed" and the protocol matches. The `owner/name` used to query the API is derived only by regex-parsing the existing remote URL text, not by any persistent, unforgeable repository ID. There is no user confirmation before the rewrite occurs.

### Finding Description
The flow is:
1. `matchGitHubRepository(accounts, remoteURL)` parses `owner`/`name` textually from the current git remote URL [1](#0-0) .
2. `repositoryWithRefreshedGitHubRepository` uses that `owner`/`name` to call `api.fetchRepository(owner, name)` and, if a repo is returned, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [4](#0-3) .
3. `updateRemoteUrl` compares the API's `clone_url` to the current remote. If the protocol is unchanged and the remote "hasn't diverged" from the previously-known GitHub `cloneURL`, and the new URL differs, it calls `gitStore.setRemoteURL(...)` — which shells out to `git remote set-url` — with **no confirmation dialog and no diff shown to the user** [5](#0-4) [6](#0-5) .

Because GitHub allows a repository name to be freed up (via rename or deletion) and re-registered by anyone (a well-documented "repo-jacking"/name-squatting technique), an attacker who reclaims the exact `owner/name` slug that a victim's local `origin` remote still points to can cause the GitHub API to return a `clone_url` pointing at the attacker's new repository. On the victim's next background refresh, `updateRemoteUrl`'s only checks are protocol-equality and "remote URL structurally unchanged from what Desktop last recorded" — neither of which detects that the underlying repository identity has changed. The victim's `origin` is silently rewritten to the attacker's repository. This corrupts the value that governs where the next `git push` sends code and where the next fetch/pull pulls code from — precisely analogous to `setMultisig` silently altering where funds are directed, with no admission-of-emergency gate.

### Impact Explanation
If exploited, this causes:
- **Silent corruption of what the user pushes**: the next push from GitHub Desktop sends the user's commits (potentially containing proprietary/private code) to the attacker-controlled repository instead of the intended one.
- **Malicious code ingestion**: the next fetch/pull brings the attacker's history into the user's local branches, which the user may build/run.

This falls squarely under the "Valid Impact" criteria: the attacker controls a GitHub API object (the repository resolved for a given `owner/name`) and the result is silent corruption of what the user commits/pushes — no local access, no admin rights, and no social engineering step is required beyond the victim previously having added the repository (a completely normal action).

### Likelihood Explanation
Moderate. It requires:
1. A victim who has an `origin` remote pointing at `owner/name` on GitHub.com or an Enterprise instance.
2. That exact `owner/name` slug later becoming available for re-registration (rename/deletion/org transfer) and reclaimed by an attacker before the victim's Desktop performs its periodic background refresh (`repositoryWithRefreshedGitHubRepository` runs continuously, not just "shortly after setup" — unlike the original bug there's no time window narrowing the attack surface, arguably widening it).
3. The victim not having manually edited the remote URL in the interim (the common case, since most users never touch `Repository Settings > Remote`).

This is a known, actively-exploited technique in the broader GitHub ecosystem (dependency/action repo-jacking), which raises real-world plausibility.

### Recommendation
- Do not silently rewrite the remote URL based solely on `owner/name` string matching and "URL unchanged" heuristics. Track and compare a durable, unforgeable identifier (e.g., the GitHub repository's numeric `id`, already available in `IAPIFullRepository`) between the previously-recorded `GitHubRepository` and the newly-fetched `apiRepo` before treating it as "the same repository that was merely renamed."
- If the repository `id` differs from what was previously associated, treat this as an entirely different repository and require explicit user confirmation before altering `origin`, rather than performing an automatic `git remote set-url`.
- Surface a non-blocking but visible notification/banner when `updateRemoteUrl` changes a remote so the user is not unaware of the redirection.

### Proof of Concept
1. Victim adds a repository in Desktop with `origin` = `https://github.com/organization/example`.
2. `organization` renames/deletes `example` (or the repo is transferred out), freeing the name.
3. Attacker creates a new repository at `https://github.com/organization/example` (or, if `organization` itself is renamable/reusable, registers the same slug elsewhere reachable via the same `owner/name` match — the critical constraint is only that `matchGitHubRepository`'s textual `owner/name` match still succeeds).
4. On Desktop's next periodic refresh, `api.fetchRepository('organization', 'example')` returns the attacker's repo's `clone_url`.
5. Because `urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)` still evaluates true (same `owner/name` textually) and protocols match, `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` with no prompt [7](#0-6) .
6. Victim's next `git push` from Desktop sends commits to the attacker's repository; next fetch pulls attacker-controlled content into the local repo.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see

      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
