### Title
EVM ante-fee surplus is permanently lost for transactions that fail after gas is purchased - (File: x/evm/keeper/abci.go)

### Summary
`EVMFeeCheckDecorator.AnteHandle` charges gas from the sender, computes an ante "surplus" (the dust between the fee cap charged and the fee actually required), and stashes it in a **transient** store via `AddAnteSurplus`. At `EndBlock`, `GetAnteSurplusSum` is supposed to fold all of that block's surpluses into the EVM module's balance. However, the loop in `EndBlock` `continue`s early for any transaction whose `DeferredInfo.Error != ""` (i.e. it failed a later ante step or execution after fees were already purchased), skipping the line `surplus = surplus.Add(deferredInfo.Surplus)`. Because the ante-surplus is stored in a transient store that Cosmos SDK wipes every block, that per-tx surplus can never be recovered once `EndBlock` fails to fold it in — it is permanently lost, mirroring the Blend `remove_from_reward_zone` bug where a value is computed/accrued but never rolled into the aggregate before the accounting window closes.

### Finding Description
`EVMFeeCheckDecorator.AnteHandle` (x/evm/ante/fee.go) runs `st.BuyGas()` which debits the sender's full `feeCap * gasLimit` and credits the deterministic per-transaction coinbase address (`state.GetCoinbaseAddress(idx)`) with the base-fee+tip portion, `Finalize()`s the state DB, and stores the leftover as an "ante surplus" in a transient store: [1](#0-0) 

`AddAnteSurplus`/`GetAnteSurplusSum` are the only place this value is aggregated, and both operate on `ctx.TransientStore`, which is reset on every block: [2](#0-1) 

In `Keeper.EndBlock`, the deferred-info loop is meant to (a) sweep each per-tx coinbase address balance to the real coinbase/fee-collector and (b) fold each tx's ante surplus into the running total that is later credited to the EVM module account. But whenever `deferredInfo.Error != ""` (any post-fee-charge ante or execution failure whose tx hash is not the empty-txs sentinel), the loop unconditionally `continue`s — for both the "nonce not bumped" and "nonce bumped" sub-cases — before ever reaching `surplus = surplus.Add(deferredInfo.Surplus)`: [3](#0-2) 

Per the module's own documented ante ordering (fee validation/gas purchase happens at step 6, before gas metering at step 7), a transaction can legitimately reach `BuyGas()` (and thus generate a real, non-zero ante surplus and populate the per-tx coinbase address) and still fail later in the pipeline with its nonce already bumped: [4](#0-3) [5](#0-4) 

For every such transaction, the `continue` at line 121 causes:
1. `surplus.Add(deferredInfo.Surplus)` to never execute for that tx, so the dust value already computed and stashed via `AddAnteSurplus` is dropped once the transient store resets on the next block boundary — it is never credited to the EVM module account.
2. The per-tx coinbase address's balance is not swept in that block (only delayed, not lost, since the same `state.GetCoinbaseAddress(idx)` slot is reused by whatever transaction lands at that index in a later block) — but the associated *surplus accounting* is unconditionally and permanently destroyed regardless.

### Impact Explanation
This is a direct fund-loss/accounting bug: value that a user overpaid (the fee-cap-minus-required-fee dust) is computed and reserved during the ante phase but is silently dropped from the ledger instead of being credited to the EVM module account, whenever the originating transaction fails after `BuyGas()` but is still nonce-bumped. This is reachable by any ordinary public transaction submitter — no privileged access required — simply by crafting or naturally producing an EVM transaction that passes fee validation but fails a later ante/execution stage. Over time and at scale this constitutes real, unrecoverable value leakage from the protocol's fee accounting, analogous in class to the Blend "loss of ungulped emissions" issue (value accrued but never folded into the final aggregate before the accounting window is closed).

### Likelihood Explanation
Any transaction that reaches gas purchase (ante step 6) but fails on a subsequent ante step or otherwise ends up with a non-empty `DeferredInfo.Error` while its nonce has already been bumped will trigger this path deterministically — this is not a rare or adversarial-only condition, it is a normal error path in transaction processing (e.g., failures introduced by later ante decorators or execution-time issues that still record an error with a bumped nonce). No special privileges, validator collusion, or malicious network behavior are needed; a single submitted transaction is sufficient to trigger the loss.

### Recommendation
In `Keeper.EndBlock` (x/evm/keeper/abci.go), fold `deferredInfo.Surplus` into the `surplus` accumulator (and/or ensure the per-tx coinbase balance sweep runs) for every `DeferredInfo` entry with a non-zero ante surplus, regardless of whether the transaction ultimately errored, before `continue`-ing out of the error-handling branch. The receipt-writing behavior (skipping when nonce not bumped) should be kept separate from the surplus/coinbase accounting so that fee dust already charged from the sender is never dropped.

### Proof of Concept
Not run against a live node (index-only tooling); conceptually:
1. Submit an EVM transaction with a `gasFeeCap` sufficiently above the required effective gas price so `BuyGas()` in `EVMFeeCheckDecorator.AnteHandle` computes a positive `surplus` and calls `AddAnteSurplus(ctx, txHash, surplus)`.
2. Ensure a later ante stage (post fee-validation) fails for this transaction while the nonce has already been incremented (so `GetNonceBumped` returns true) — e.g., by exploiting timing/state such that gas metering or a subsequent decorator errors after `BuyGas` succeeded.
3. Observe in `EndBlock` that `deferredInfo.Error != ""` and `GetNonceBumped(...) == true`, so the loop hits the second `continue` at x/evm/keeper/abci.go:121, skipping `surplus.Add(...)`.
4. Confirm the transient `AnteSurplusPrefix` entry for that tx hash is not reflected in the EVM module account's balance and is unrecoverable after the next block's transient-store reset.

func (k *Keeper) AddAnteSurplus(ctx sdk.Context, txHash common.Hash, surplus sdk.Int) error {
	store := prefix.NewStore(ctx.TransientStore(k.transientStoreKey), types.AnteSurplusPrefix)
	bz, err := surplus.Marshal()
	if err != nil {
		return err
	}
	store.Set(txHash[:], bz)
	return nil
}

func (k *Keeper) GetAnteSurplusSum(ctx sdk.Context) sdk.Int {
	iter := prefix.NewStore(ctx.TransientStore(k.transientStoreKey), types.AnteSurplusPrefix).Iterator(nil, nil)
	defer func() { _ = iter.Close() }()
	res := sdk.ZeroInt()
	for ; iter.Valid(); iter.Next() {
		surplus := sdk.Int{}
		_ = surplus.Unmarshal(iter.Value())
		res = res.Add(surplus)
	}
	return res
}

## Ante Handler Pipeline

EVM transactions go through a dedicated ante handler chain, separate from the standard Cosmos ante chain. A router decorator at the front decides which chain to use based on whether the message is a `MsgEVMTransaction`.

The EVM ante chain performs, in order:

1. **Cosmos field rejection** — EVM txs must not use Cosmos-specific fields (memo, timeout, fees, etc.).
2. **Preprocessing** — unpacks the inner Ethereum tx, recovers the sender via ECDSA, populates derived metadata. Associate transactions are handled here.
3. **Address derivation** — for Cosmos-signed txs, derives the EVM address from the public key and sets up mappings.
4. **Basic validation** — init code size, non-negative value, intrinsic gas.
5. **Signature/nonce verification** — validates chain ID and nonce. CheckTx uses pending nonce logic for mempool ordering; DeliverTx requires exact match.
6. **Fee validation** — checks against base fee and minimum fee, executes gas purchase, stores any fee surplus.
7. **Gas metering** — sets the Sei gas meter using the converted EVM gas limit.

### Receipts for Failure Scenarios

Unlike Ethereum, an EVM transaction on Sei could fail before it reaches the EVM (i.e. during ante handling).
- **Nonce Mismatch** - such failures would not result in any receipt, because they involve no state change
- **Others Ante Failures** - such failures would result in a status-0 receipt, because nonce for the sender will be incremented in such cases.
