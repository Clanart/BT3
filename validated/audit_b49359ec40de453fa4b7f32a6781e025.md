### Title
`Scanner::scan_block` reports immature coinbase outputs as received funds that cannot yet be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The MISP CVE is an information-disclosure flaw: a query API returns metadata about an object that correlates with the request but is not actually accessible to the requester. The closest analog in Serai's in-scope code is the Bitcoin `Scanner`, which is a query/scan API over untrusted blockchain data. `scan_block` scans every transaction in a block — including `txdata[0]`, the coinbase — and returns matching outputs as `ReceivedOutput`s indistinguishable from ordinary spendable outputs, even though consensus rules make coinbase outputs unspendable for 100 blocks.

### Finding Description
`Scanner::scan_transaction` matches purely on `output.script_pubkey` membership in the `scripts` map and constructs a `ReceivedOutput` with a spendable key offset (networks/bitcoin/src/wallet/mod.rs:199-214). `scan_block` iterates `block.txdata` in full, so the coinbase transaction is included (mod.rs:221-227). The inline comment admits the flaw:

```
// This will also scan the coinbase transaction which is bound by maturity. If received outputs
// must be immediately spendable, a post-processing pass is needed to remove those outputs.
```

No maturity check is performed — `scan_block` does not even inspect whether `tx.is_coinbase()`. The returned `ReceivedOutput` carries a valid `offset` and `outpoint`, so downstream callers (the processor crediting deposits/change) cannot distinguish it from a normally spendable output except by re-implementing the maturity filter the comment merely suggests. This is exactly the reported bug class: the scan returns a *correlating but unreachable* object — an output matching the wallet's script that cannot be spent.

### Impact Explanation
If a miner (or anyone able to influence a coinbase, e.g., via a mining pool payout address) directs a coinbase payout to a Serai-registered script, `scan_block` reports it as a received output. A downstream consumer that treats scanner results as spendable will attempt to build/sign a spend transaction consuming it; any such transaction is consensus-invalid for 100 blocks, and accounting that credits the amount immediately reports funds "received" that are not spendable — the accepted impact class. Additionally, a coinbase output later reorged or spent-by-maturity rules produces accounting/UTXO divergence between what the scanner reported and what is actually spendable.

### Likelihood Explanation
Requires a coinbase paying to a Serai address, which is uncommon but entirely feasible for an unprivileged miner and costs nothing beyond normal payout configuration — miners routinely pay arbitrary scripts. Exploitation does not require collusion, leaked keys, or invalid curve inputs; it uses only public on-chain data, satisfying the reachability constraint. The window of incorrectness is bounded (100 blocks), capping severity at Medium.

### Recommendation
In `scan_block`, skip `block.txdata[0]` (or filter via `Transaction::is_coinbase()`), or mark returned `ReceivedOutput`s from coinbases as immature so callers can enforce the 100-block rule rather than relying on an undocumented post-processing step.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs scenario
let mut scanner = Scanner::new(key).unwrap();
// A block whose coinbase pays to scanner's p2tr script
let outputs = scanner.scan_block(&block);
// outputs contains a ReceivedOutput for the coinbase outpoint;
// signing a spend of it produces a tx rejected by consensus (BIP-113 maturity).
```
