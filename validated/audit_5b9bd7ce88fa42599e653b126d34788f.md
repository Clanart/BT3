### Title
Unverified externally-supplied `Derived` sender identity in `MsgEVMTransaction` allows transaction impersonation - (File: `app/ante/evm_delivertx.go`)

### Summary
`EvmDeliverHandleSignatures` in `app/ante/evm_delivertx.go` and `PreprocessUnpacked` in `x/evm/ante/preprocess.go` both special-case a `MsgEVMTransaction` whose `Derived` field is already non-nil: instead of recovering the sender from the enclosed Ethereum transaction's ECDSA signature, they trust the `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` values already present on the message. The only validation performed is that `PubKey != nil`; the code never checks that the supplied `PubKey` actually derives `SenderEVMAddr`/`SenderSeiAddr`, nor that any valid signature over the enclosed transaction data corresponds to that identity. This mirrors the Istio CVE-2022-39388 pattern, where an identity claim delivered over a "trusted" internal channel is accepted without cryptographic proof, enabling impersonation of any workload/identity.

### Finding Description
`MsgEVMTransaction.Derived` (`x/evm/types/message_evm_transaction.go:44-56`) is validated only for non-nil `PubKey`: [1](#0-0) 

The same shallow check is repeated at the stateless-check layer used by both `EvmCheckTxAnte` and `EvmDeliverTxAnte`: [2](#0-1) 

Crucially, `EvmDeliverTxAnte` → `EvmDeliverHandleSignatures` short-circuits full signature recovery whenever `msg.Derived != nil`, trusting the embedded `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` directly instead of calling `CheckAndDecodeSignature`, which is the function that actually recovers the sender from the ECDSA signature over the transaction hash: [3](#0-2) 

Compare this to the "else" branch a few lines below, which is the only place `CheckAndDecodeSignature` (real signature recovery) is invoked: [4](#0-3) 

The equivalent ante-pipeline preprocessing step (`x/evm/ante/preprocess.go`) contains the identical shortcut, explicitly commented as handling data that could have been "set from the outside": [5](#0-4) 

Once `evmAddr`/`seiAddr` are accepted from `Derived` without proof, they flow directly into fee charging, nonce handling, association, and the EVM execution context (`ctx.WithEVMSenderAddress(sender)` in `DecorateContext`, `app/ante/evm_checktx.go:162-179`), meaning the state transition executes with `msg.sender` set to whatever address the attacker chose in `Derived`, and fees/value are debited from that (victim) account. `AssociateAddress`/`AssociateAddresses` (`utils/helpers/associate.go:34-55`) likewise write the attacker-chosen `(seiAddr, evmAddr, pubkey)` tuple into the address-mapping store without validating that `pubkey` actually derives either address: [6](#0-5) 

`EvmCheckTxAnte` (the mempool entry path) does perform genuine signature recovery via `CheckAndDecodeSignature` and never reads `msg.Derived`: [7](#0-6) 

but that is irrelevant to whether the wire-encoded `Derived` field the attacker embedded survives into the block: the DeliverTx-time decode of the committed block re-parses `msg` from the transaction bytes, and if `Derived` is part of the message's protobuf encoding, the attacker-controlled values reappear at `EvmDeliverTxAnte` time and are trusted verbatim by the vulnerable shortcut described above.

### Impact Explanation
If the crafted `Derived` payload survives serialization into the committed transaction bytes, an attacker can submit an `MsgEVMTransaction` whose `Data` carries a self-signed (attacker's own) Ethereum transaction but whose `Derived.SenderEVMAddr`/`SenderSeiAddr` name an arbitrary victim account and whose `Derived.PubKey` is any syntactically valid (but unrelated) public key. During `DeliverTx`, the chain then: (1) associates the victim's Sei address with the attacker-chosen bogus pubkey/EVM address if not already associated, corrupting the dual-address mapping, and (2) executes the enclosed EVM call/transfer with `msg.sender == victim`, charging fees and debiting value from the victim's balance while running arbitrary contract logic as the victim's identity. This is unauthorized transfer/impersonation and fee abuse originating from a single crafted transaction — meeting the High severity bar (fund loss, unauthorized transfer, identity corruption).

### Likelihood Explanation
Likelihood depends entirely on whether the `Derived` struct is serialized as part of `MsgEVMTransaction`'s wire format (so that an externally-crafted raw transaction can populate it) versus being a purely in-memory/runtime-only field excluded from protobuf marshaling and only ever set by the node itself during its own signature recovery. I was not able to conclusively verify this from the available `.pb.go`/`.proto` definitions within the indexed content; the explicit "set from the outside" comments in both `preprocess.go` and `evm_checktx.go` strongly suggest the authors were aware this is a real, externally-reachable input path they intended to guard against, but the guard (`PubKey != nil`) does not verify correspondence between `PubKey`, `SenderEVMAddr`, and `SenderSeiAddr`, so if the field is externally settable this is directly exploitable by any transaction submitter.

### Recommendation
Never trust an externally/wire-supplied `Derived` value. Either (a) exclude `Derived` entirely from `MsgEVMTransaction`'s serialized/consensus-visible representation and only ever populate it from a fresh, verified signature recovery at each ABCI stage (never cache/reuse across CheckTx→DeliverTx via the decoded object if that object can originate from untrusted wire bytes), or (b) if caching across stages is required for performance, cryptographically re-derive and verify that `Derived.PubKey` produces both `Derived.SenderEVMAddr` and `Derived.SenderSeiAddr`, and that `Derived.PubKey`'s corresponding private key actually signed the enclosed transaction/message, before ever trusting it in `EvmDeliverHandleSignatures` or `PreprocessUnpacked`.

### Proof of Concept
Conceptual (requires confirming `Derived` is wire-serializable, which is the open verification point):
1. Craft `txData`: any Ethereum transaction validly self-signed by attacker key `K_attacker` (passes `txData.Validate()`), e.g., a 0-value legacy tx to some low-cost target.
2. Construct `MsgEVMTransaction{ Data: txData, Derived: &derived.Derived{ SenderEVMAddr: victimEvmAddr, SenderSeiAddr: victimSeiAddr, PubKey: attackerPubKey, Version: derived.Cancun, IsAssociate: false } }`.
3. Broadcast via a full node's RPC; `EvmStatelessChecks`/`ValidateBasic` accept it because `PubKey != nil`.
4. Node's own `EvmCheckTxAnte` recomputes the real signer (attacker) via `CheckAndDecodeSignature` and admits it to mempool/gossips it, or it is placed in a block by any proposer.
5. At `DeliverTx`, the freshly-decoded `msg.Derived` (from block bytes) is non-nil, so `EvmDeliverHandleSignatures` skips signature recovery and uses `evmAddr=victimEvmAddr, seiAddr=victimSeiAddr` directly; fees/value are charged against the victim, and the EVM executes with `msg.sender == victim`.

func EvmDeliverHandleSignatures(ctx sdk.Context, ek *evmkeeper.Keeper, txData ethtx.TxData, chainID *big.Int, msg *evmtypes.MsgEVMTransaction) (common.Address, sdk.AccAddress, derived.SignerVersion, error) {
	if msg.Derived != nil {
		if msg.Derived.PubKey == nil {
			return common.Address{}, nil, 0, sdkerrors.ErrInvalidPubKey
		}
		evmAddr := msg.Derived.SenderEVMAddr
		seiAddr := msg.Derived.SenderSeiAddr
		version := msg.Derived.Version
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, msg.Derived.PubKey); err != nil {
			return evmAddr, seiAddr, version, err
		}
		if ek.EthReplayConfig.Enabled {
			ek.PrepareReplayedAddr(ctx, evmAddr)
		}
		return evmAddr, seiAddr, version, nil
	}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}
