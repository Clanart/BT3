### Title
Silent Remote-URL Repointing from Untrusted GitHub API `clone_url` - (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop automatically rewrites a repository's local git remote URL whenever the associated GitHub API repository object reports a different `clone_url`, without any user confirmation and with only a same-protocol check. If an attacker controls the API response for a linked repository (e.g., a malicious/compromised GitHub Enterprise Server the user has added an account for, or any endpoint whose `fetchRepository` response Desktop trusts), they can point the local `origin` remote at an attacker-controlled host, silently corrupting where the user's future `git push`/`fetch`/`pull` operations go.

### Finding Description
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts:7-45` is invoked on every GitHub-repository refresh via `AppStore.repositoryWithRefreshedGitHubRepository` at `app/src/lib/stores/app-store.ts:4874-4914`, which is itself called from background/user-initiated fetch, pull, and push flows (`_fetch`, `_fetchRemote`, `performFetch` in `app-store.ts:5895-5988`, and `_publishRepository`/`withRefreshedGitHubRepository`). On each of these operations, Desktop calls `api.fetchRepository(owner, name)` and passes the returned `IAPIRepository` object straight into `updateRemoteUrl`.

Inside `updateRemoteUrl` the only checks performed before calling `gitStore.setRemoteURL` are:
- `protocolsMatch` — compares `URL.parse(remoteUrl).protocol` to `URL.parse(updatedRemoteUrl).protocol` (i.e., both `https:` or both unparseable/ssh), [1](#0-0) 
- `remoteUrlUnchanged` — whether the *current* remote still matches the previously cached `gitHubRepository.cloneURL` [2](#0-1) 
- `!urlsMatch` — the new URL differs from the current remote [3](#0-2) 

None of these checks validate that the new `clone_url` still points to the same host, owner, or endpoint. If all three conditions hold, Desktop calls `gitStore.setRemoteURL(...)` which shells out to `git remote set-url <name> <url>` [4](#0-3)  with zero user interaction — no dialog, no diff shown, nothing logged to the UI.

The broken invariant: the API-supplied `clone_url` field is trusted as an authoritative source for rewriting a security-relevant local git configuration value (the push/fetch destination), based only on "same protocol, different from current" — not "same host/repository identity." This is exactly the "GitHub API object" attacker-controlled input category: any endpoint whose `fetchRepository`/`fetchRepositoryCloneInfo` response Desktop consumes (most concretely a GitHub Enterprise Server instance the user has added as an account, which the user does not control the code of and which could be compromised or malicious) can return an arbitrary `clone_url` for a repository the user already has cloned and associated. The next background fetch/refresh (which runs automatically, not just on explicit user action) will then silently repoint `origin` to that attacker-chosen URL.

### Impact Explanation
Once `origin` is silently repointed:
- Subsequent `git push` sends the user's local commits (with their identity/config) to the attacker's remote, and simultaneously the app is likely to source-of-truth in Desktop's UI as if it succeeded against the "same" repo, while the legitimate repository on GitHub silently stops receiving updates — silent corruption of what the user pushes, with no user awareness.
- Subsequent `git fetch`/`pull` pulls code from the attacker's server into the user's working tree, effectively feeding attacker-controlled history/content into the local clone under the guise of the original repository (a supply-chain vector).
- Because credential/proxy environment is derived from `remote.url` via `envForRemoteOperation(remote.url)` at push/fetch/pull call sites (`app/src/lib/git/push.ts`, `pull.ts`, `fetch.ts`, `remote.ts`), redirecting the remote host can also change which credential helper/proxy config is applied for that operation, creating a path toward credential handling against an unintended host.

This satisfies "silent corruption of what the user commits or pushes" and touches "git remote/proxy response"/"GitHub API object" attacker classes explicitly listed as valid impact.

### Likelihood Explanation
Requires the user to have added an account for a GitHub Enterprise (or otherwise attacker-influenced) endpoint that is later malicious or compromised, or any scenario where the `fetchRepository`/`fetchRepositoryCloneInfo` response for an already-linked repository is attacker-influenced. This is not local access, not admin rights, and not pre-existing malware — it is a remote server response consumed automatically during routine background refresh (`FetchType.BackgroundTask`) with no user action required beyond having previously linked the repository to that account/endpoint. Likelihood is moderate: it depends on the endpoint being attacker-controlled/compromised, but the code path itself has no additional gate (no confirmation dialog, no host-pinning) once that precondition is met.

### Recommendation
In `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts`), do not silently call `setRemoteURL` based solely on protocol match. Require that the new `clone_url`'s hostname matches the endpoint's expected host (derived from `gitHubRepository.endpoint`/the account used to fetch it), and/or surface a user-facing confirmation before rewriting an existing remote URL, similar to the explicit-consent flow already used in `RepositorySettings` (`app/src/ui/repository-settings/repository-settings.tsx:296-313`) where the user manually edits and submits a remote URL change.

### Proof of Concept
1. User adds a GitHub Enterprise account for `https://ghe.example.com` and clones/links a repository `org/repo` from it; Desktop stores `gitHubRepository.cloneURL = https://ghe.example.com/org/repo.git` and `origin` is set to the same URL.
2. The GHE server (attacker-controlled or later compromised) is queried during a routine background fetch via `api.fetchRepository('org','repo')` (`app-store.ts:4890`), and returns an `IAPIRepository` with `clone_url: "https://attacker-evil.com/org/repo.git"`.
3. `repositoryWithRefreshedGitHubRepository` passes this object to `updateRemoteUrl` (`app-store.ts:4904-4906`).
4. `protocolsMatch` is true (both `https:`), `remoteUrlUnchanged` is true (origin still equals the previously cached `cloneURL`), and `urlsMatch` is false (new host differs) — all three conditions in `update-remote-url.ts:42` are satisfied.
5. `gitStore.setRemoteURL('origin', 'https://attacker-evil.com/org/repo.git')` runs `git remote set-url origin ...` with no dialog shown to the user (`app/src/lib/git/remote.ts:56-64`).
6. The next time the user pushes/pulls/fetches in Desktop, git silently operates against `attacker-evil.com` instead of the legitimate GHE server.
