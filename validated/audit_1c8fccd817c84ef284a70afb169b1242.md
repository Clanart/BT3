### Title
Dust-valued deposits are reported as spendable yet can never be spent due to the DUST minimum in `SignableTransaction::new` - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The external report describes a minimum-amount check (`_amount >= MIN_STAKING_AMOUNT`) that serves no real purpose and strands a user's residual balance below the minimum. In `bitcoin-serai`, the analogous shape is the dust minimum: `Scanner` will happily report any output paying to a registered script as a `ReceivedOutput`, but `SignableTransaction::new` refuses to construct a spend when any payment falls below `DUST = 546` sats or when inputs can't cover `payment + fee`. An unprivileged party who sends a sub-dust (or fee-submerging) output to a registered offset address creates funds that the wallet reports as received yet can never be spent.

### Finding Description
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` matches outputs purely on `script_pubkey` and returns a `ReceivedOutput` regardless of `output.value`. `register_offset` (`mod.rs:180-196`) lets integrators register arbitrary derived scripts; anyone who learns such a script (e.g., a deposit address) can send it an output of any value, including 1 sat.

On the spend side, `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` enforces two floors:

- `send.rs:165-169` — `for (_, amount) in payments { if *amount < DUST { Err(DustPayment) } }`, so no output below 546 sats can be created.
- `send.rs:211-221` — `TooLowFee` if the computed fee is below the minimum relay fee, and `NotEnoughFunds` if `input_sat < payment_sat + needed_fee`.

Consequently, any `ReceivedOutput` whose value is ≤ the minimum spendable payment plus required fee is permanently unspendable through this API: it cannot fund a valid payment output (any payment must be ≥ 546 sats), and it cannot meaningfully contribute toward one (its value is less than the marginal fee to include it as an input, and the builder provides no way to add it as fee-donation-only — every input in `tx_ins` is unconditionally included and its value counted in `input_sat`). Adding such an input strictly *reduces* spendable value, because it adds ~57.5 vbytes of weight while contributing fewer sats than the fee its inclusion costs.

This mirrors the reported bug class exactly: a minimum-amount policy check combined with unconditional acceptance of sub-minimum deposits produces a balance that is visible but unreachable. The GiantPool check stranded `0.99 * MIN_STAKING_AMOUNT`; here the dust floor strands any output below ~`DUST + marginal fee`, and the scanner gives the depositor (an unprivileged sender) full control to create such stranded outputs on the multisig's books.

### Impact Explanation
- Funds are reported received (`Scanner::scan_transaction` returns them as `ReceivedOutput`s) that are not spendable, matching the accepted impact "funds reported received that are not spendable".
- An attacker can pollute the wallet's UTXO set: each dust output sent to a registered offset script is permanently recorded, and automated coin-selection that includes it in `inputs` either fails with `NotEnoughFunds`/`DustPayment` or silently burns more fee than the input contributes (the leftover after `payment_sat + needed_fee` just enlarges the fee via `sum(inputs) - sum(outputs)`, `send.rs:138-141`).
- If no `change` address is given (`send.rs:146-147`), the entire leftover — including any dust inputs pulled in — becomes fee, amplifying the loss.

### Likelihood Explanation
Medium. Creating a dust output costs the attacker only the dust value plus fee, and deposit addresses/offset scripts are intended to be publicly distributable (that is their purpose). Whether this becomes exploitable harm depends on the caller's coin selection: a naive "use all `ReceivedOutput`s" strategy — which the API shape encourages since `SignableTransaction::new` takes `Vec<ReceivedOutput>` with no filtering helper — will wedge or overpay. Deliberate malicious dusting of known addresses is a well-documented real-world tactic on Bitcoin.

### Recommendation
- Have `Scanner::scan_transaction` (or a post-processing helper) filter out outputs with `value < DUST` so they are never reported as spendable, mirroring how the builder already refuses to *create* them.
- Alternatively/additionally, allow inputs to be marked fee-only or expose the marginal-input cost so coin selection can exclude inputs whose value is below their fee contribution, preventing dust inputs from silently inflating the fee.
- Document on `register_offset`/`Scanner` that received dust outputs are unspendable and must be excluded by the caller.

### Proof of Concept
Conceptual, using only public inputs:

1. A multisig registers offset `o` via `Scanner::register_offset`, yielding script `s` (`mod.rs:180-196`). The deposit address derived from `s` is given to users.
2. Attacker broadcasts a Bitcoin transaction paying 300 sats (< `DUST = 546`) to `s`.
3. `Scanner::scan_transaction` returns `ReceivedOutput { offset: o, value: 300, outpoint }` (`mod.rs:205-211`). The wallet now reports 300 sats received.
4. Any spend attempt: `SignableTransaction::new(inputs=[that output], payments=[(dest, 300)], ...)` fails with `DustPayment` (`send.rs:166-167`). Increasing the payment to ≥ 546 fails with `NotEnoughFunds` since `300 < 546 + needed_fee` (`send.rs:215-220`). There is no code path that spends the output.
5. Repeat with N dust outputs: the reported balance grows while remaining permanently unspendable, and any coin-selection that includes these inputs inflates `needed_fee` past their combined value, causing either repeated `NotEnoughFunds` failures or fee overpayment equal to `sum(inputs) - sum(outputs)`.

The root cause is the asymmetric policy: the scanner accepts outputs below the spendability floor that `SignableTransaction::new` then enforces on every exit path, leaving no route — analogous to GiantPool's withdrawal floor stranding a sub-`MIN_STAKING_AMOUNT` residual.   pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
