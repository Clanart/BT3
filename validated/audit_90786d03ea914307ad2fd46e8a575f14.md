## Title
Path-containment check in `resolveWithin` uses unanchored `String.startsWith`, allowing filepath deep-links to escape the repository directory into sibling folders - (`File: app/src/lib/path.ts`)

## Summary
`resolveWithin()` is the guard that is supposed to guarantee a filesystem path stays "at or underneath" a given root before it is used. Its final check, `realResolved.startsWith(realRoot)`, is logically the same class of bug as the reported PlexusIDO issue: a guard that looks like it enforces an invariant but, due to how the comparison is built, does not actually enforce it for every input, letting attacker-controlled data slip past a check the code believes is protective.

## Finding Description
`resolveWithin` computes the real, canonicalized root and resolved paths and then decides containment purely with a string prefix test: [1](#0-0) 

`String.prototype.startsWith` has no concept of path separators, so any resolved path whose *string* begins with the root string passes, even if it is actually a sibling directory rather than a descendant. For example, root `/Users/victim/Documents/GitHub/desktop` and resolved `/Users/victim/Documents/GitHub/desktop-secrets/token.txt` satisfy `startsWith`, even though `desktop-secrets` is not inside `desktop` at all. The correct check needs an explicit separator boundary (e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)`), which is missing.

This function is the only defense used when Desktop handles the `filepath` query parameter of the `x-github-client://openRepo/...` deep link. The parser extracts `filepath` from an attacker-controlled URL with no path-traversal filtering: [2](#0-1) 

and the dispatcher relies solely on `isAbsolute` + `resolveWithin` before revealing the resolved file to the user: [3](#0-2) 

Because Desktop's default clone base directory (e.g. `~/Documents/GitHub`) commonly holds multiple repositories with overlapping name prefixes (forks, `-old`, `-backup`, `-2` copies, etc.), a crafted `filepath` such as `../sibling-repo-with-prefix/secret.txt` can resolve to a path outside the intended repository while still passing the flawed `startsWith` check.

## Impact Explanation
A malicious link (e.g. embedded in a webpage, README, or chat message) using the `x-github-client://openRepo/<repo-url>?filepath=..%2F<sibling-dir>%2F<file>` scheme can, when clicked, cause Desktop to call `shell.showItemInFolder()` on a file outside the target repository if a sibling directory sharing a name prefix exists. This is a file-path confinement bypass triggered purely by a link the user clicks, matching the "read outside the repo" impact category — no local/physical access or prior compromise is required, only that another folder with a colliding name prefix exists alongside the repo (a common real-world layout).

## Likelihood Explanation
Exploitation requires: (1) the victim to click an `x-github-client://` deep link (a normal, expected Desktop interaction), and (2) a sibling folder whose name is a prefix-extension of the target repo's folder name to exist in the same parent directory — a routine occurrence given how developers clone multiple related/forked repositories side by side. No credentials, elevated privileges, or existing malware are needed, making this a plausible, low-effort attack chain limited only by the specific directory-naming coincidence needed for a given target.

## Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require a path-separator boundary or exact equality, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This closes the prefix-collision gap for all four exported helpers (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) and any other current/future callers relying on this guard.

## Proof of Concept
1. Ensure two folders exist side by side, e.g. `~/Documents/GitHub/desktop` (a Desktop-tracked repo) and `~/Documents/GitHub/desktop-secrets/token.txt`.
2. Craft a deep link: `x-github-client://openRepo/https://github.com/desktop/desktop?filepath=..%2Fdesktop-secrets%2Ftoken.txt`.
3. User clicks the link; `handleAppURL` → `parseAppURL` (`app/src/lib/parse-app-url.ts:98-124`) parses `filepath=../desktop-secrets/token.txt`, which is not absolute so it bypasses the `isAbsolute` check in `dispatcher.ts:1958-1961`.
4. `resolveWithin(repository.path, filepath)` normalizes/resolves to `~/Documents/GitHub/desktop-secrets/token.txt`, whose string representation starts with `~/Documents/GitHub/desktop`, so `realResolved.startsWith(realRoot)` is `true` and the path is returned as valid.
5. `shell.showItemInFolder(resolved)` reveals `token.txt`, a file outside the intended repository root, confirming the containment guard is bypassable.
