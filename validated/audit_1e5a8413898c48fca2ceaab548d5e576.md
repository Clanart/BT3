## Title
Relayer fee balance is zeroed before destination-side payout is confirmed, permanently destroying accumulated rewards if delivery fails - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::withdraw` in `pallet-ismp-relayer` dispatches a `WithdrawRelayerFees` / `WithdrawalParams` ISMP POST request to the destination chain's host manager, and then unconditionally zeroes the relayer's `Fees` entry on Hyperbridge in the same call — before the destination chain has actually processed and paid out the withdrawal. This is the same broken invariant as the "Maker loses all tokens" report: an accumulated reward balance is destroyed on a state transition without giving the beneficiary a way to reclaim it if the corresponding payout never lands.

### Finding Description
The withdrawal flow is: [1](#0-0) 

1. `available_amount` is read from `Fees::<T>::get(dest_chain, address)`.
2. A `DispatchPost` (with `timeout: 0`, i.e. it never times out) is dispatched to the destination chain's host manager (`HYPERBRIDGE_MODULE_ID` on Substrate, `params.host_manager` on EVM), encoding a `WithdrawalRequest`/`WithdrawalParams` instructing it to pay `available_amount` to the beneficiary.
3. Immediately afterward, in the very same extrinsic, `Fees::<T>::insert(dest_chain, address, U256::zero())` unconditionally zeroes the relayer's balance — regardless of whether the message is ever delivered, or whether the destination-side handler (`HostManager.sol` / `WithdrawalParams` receiver) actually succeeds in transferring funds.

`dispatch_request` at this point on Hyperbridge only enqueues the outbound POST request commitment; it says nothing about the eventual execution outcome on the destination chain. Because `timeout: 0` is used, the request can never time out and be refunded via the normal `on_request_timeout` fee-refund path used elsewhere in the codebase (`modules/pallets/ismp/src/host.rs`, `on_request_timeout`) — that mechanism only exists for the ISMP protocol fee attached to a request, not for the payload amount encoded inside a `WithdrawalRequest`. If the destination-side handler ever fails permanently to disburse the funds (e.g., the EVM `HostManager`/paymaster is out of `feeToken` balance, `safeTransfer` reverts, the beneficiary address is malformed, or the destination chain's fee-token address configuration has since changed), there is no code path that restores the zeroed `Fees` entry on Hyperbridge. The relayer's already-accumulated cross-chain delivery rewards are gone with no recourse — exactly analogous to the Maker's stake being burned by `removeListing` before the Maker gets a chance to withdraw.

This mirrors the reference bug's exploit shape: value is credited/accumulated over time (Maker's listing tokens ↔ relayer's accumulated fees from `accumulate_fees`), and a single state-transition function (`removeListing` ↔ `withdraw`) destroys that balance unconditionally, decoupled from confirmation that the beneficiary actually receives value.

### Impact Explanation
This falls under "stealing or loss of funds" from the bounty's accepted impact list. A relayer who has honestly earned fees through `accumulate_fees` (state-proof-verified deliveries) can lose their entire balance permanently if the corresponding cross-chain payout message fails to execute on the destination chain, with no retry/refund mechanism visible in `withdrawal.rs`. Given relayers are core, permissionless economic participants (any account can become a relayer and accumulate fees), this is not a privileged-actor-only scenario — it affects the base "earn fees → withdraw fees" flow used by every relayer.

### Likelihood Explanation
Medium. This requires a destination-side failure after the Hyperbridge-side state has already been finalized — e.g. the EVM host manager not holding enough `feeToken` liquidity at the exact time the withdrawal message is delivered, a reverting beneficiary/token configuration, or any other execution failure in the destination-side receiver. Such conditions are plausible in production (liquidity/balance mismatches, config changes, contract upgrades) without requiring a malicious actor — it can occur as a natural consequence of normal operational conditions, unlike the request/response timeout paths elsewhere in the codebase, which do have refund guarantees.

### Recommendation
- Short term: Do not zero `Fees` until delivery/execution on the destination chain is confirmed (e.g., via the receipt/ack path already used for other ISMP request/response semantics), or keep the amount in an intermediate "pending" bucket that can be reclaimed/retried if the destination call fails.
- Alternatively, add a genuine timeout (not `timeout: 0`) to the withdrawal `DispatchPost` so that on failure the normal ISMP timeout-refund pipeline (`on_request_timeout`) can restore the balance, mirroring the relayer-fee refund pattern already implemented for ordinary POST requests in `modules/pallets/ismp/src/host.rs`.
- Long term: Add an explicit "withdrawal failed" callback/ack from the destination host manager back to Hyperbridge that re-credits `Fees` on failure, so the zero-out is conditioned on proven destination-side success rather than optimistic dispatch.

### Proof of Concept
Conceptual sequence (cannot be fully validated without executing the destination-chain `HostManager`/paymaster contract, which is out of scope of static review):
1. Relayer accumulates `available_amount` fees via `accumulate_fees` for `dest_chain = EVM(X)`.
2. Relayer calls `withdraw_fees` with a valid signature; `Pallet::withdraw` dispatches `WithdrawalParams{beneficiary, amount, token}` to `HostParams::<T>::get(dest_chain).host_manager` and immediately sets `Fees::<T>::insert(dest_chain, address, U256::zero())` at `modules/pallets/relayer/src/withdrawal.rs:177`.
3. Suppose the destination `HostManager`'s balance of `feeToken` at delivery time is insufficient (or the withdrawal handler reverts for any reason) when a relayer submits the proof/calldata to execute the message on the destination chain.
4. Because `timeout: 0` means the request never expires and there is no re-credit mechanism observed in this pallet, the relayer's fee balance remains zero on Hyperbridge forever, while the payout on the destination chain was never actually received.

I was unable to fully trace the EVM-side `HostManager.sol` withdrawal handler logic (only located via `grep`, not fully read) to confirm whether it has any independent guarantee of eventual success (e.g. an internal escrow that can never run dry) that might mitigate this; this should be verified by a background agent with full repository access before treating this as conclusively exploitable in the current EVM `HostManager` implementation.
