### Title
Single broken/stale price feed for any asset in a user's position permanently blocks withdrawal of unrelated, healthy collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s cross-collateral health-check pipeline resolves prices for **every** asset a user has ever used as collateral or debt in a single all-or-nothing batch (`get-assets` → `price-multi-resolve`). If price resolution fails for just one of those assets — e.g. its oracle feed becomes permanently stale, its Pyth/DIA identifier is deprecated, or its callcode dependency (ztoken liquidity index, stSTX ratio) breaks — the whole call panics, and the user cannot withdraw or otherwise touch *any* of their other, perfectly healthy collateral. This is the same failure mode as the Perennial `BalancedVault` M-16 finding: one broken "market" (here, one broken asset price feed) permanently locks funds that have nothing to do with the failure.

### Finding Description
`get-assets` builds the list of every asset id present in a user's collateral+debt mask and resolves all of their prices together: [1](#0-0) 

`user-safe-mask` combines the user's collateral bits and debt bits (shifted down) into one bitmap, so `mask-to-list-collateral` returns *all* asset ids the position touches, not just the one the caller cares about: [2](#0-1) 

Price resolution for that whole list happens in one all-or-nothing batch. Any single failure (stale timestamp, illegal price, callcode failure) sets `valid: false` for the batch, and `price-multi-resolve` asserts and the caller uses `unwrap-panic`, aborting the entire transaction with no error code: [3](#0-2) [4](#0-3) 

This `get-assets(mask)` call is on the critical path of `collateral-remove` (health-check branch), `borrow`, and `liquidate`, all of which need the position's full collateral/debt valuation before allowing any state change: [5](#0-4) [6](#0-5) 

Consequently, if a user holds collateral in two assets — e.g. STX (healthy, live Pyth feed) and stSTXbtc (whose oracle callcode/vault liquidity-index cache becomes permanently broken, or whose Pyth/DIA feed is discontinued) — `collateral-remove`, `borrow`, and `liquidate` for that account will *always* revert, because `get-assets` insists on pricing stSTXbtc too, even though the caller only wants to withdraw STX. There is no partial/degraded valuation path that excludes the broken asset from the health computation, and no admin/emergency override visible in this pricing path to force a valuation that skips one broken feed.

### Impact Explanation
This causes freezing of user funds unrelated to the actual failure: a user's entire multi-asset position becomes un-withdrawable and un-borrowable as soon as one asset's price resolution can no longer succeed (feed deprecated/paused, `max-staleness` permanently exceeded, or a callcode dependency like the ztoken liquidity-index cache/`stSTX` ratio call failing). Liquidators are likewise blocked from liquidating such positions (`liquidate` hits the same `get-assets`/`price-multi-resolve` call), so bad debt from the broken asset cannot even be cleared, and the healthy collateral in the same position is frozen alongside it. This matches "temporary freezing of funds" (or permanent, if the feed never recovers) under the impact taxonomy.

### Likelihood Explanation
Any of the six supported assets depends on external Pyth/DIA feeds plus, for ztokens, cached vault liquidity indexes and, for stSTX, an external ratio call — any one of these six independent dependencies failing (deprecated feed id, staleness misconfiguration discovered only after long inactivity, a broken downstream contract call in `resolve-ztoken`/`resolve-ststx`) is enough to trip this. Because `get-assets` never narrows its scope to only the assets relevant to the current operation, the likelihood of at least one of a user's held assets eventually hitting this all-or-nothing failure grows with the number of distinct collateral/debt assets they hold and with time.

### Recommendation
Do not require a successful price resolution for assets that are not needed for the specific operation being performed (e.g. when withdrawing/repaying/adding a specific asset that keeps the position healthier or unchanged, or when the asset being withdrawn is unrelated to a broken feed). Alternatively, add a governance-controlled "asset marked broken" path in `assets.clar`/`market.clar` that lets a broken asset be excluded from `get-notional-evaluation`/health checks (at zero valuation, biased against the user) so remaining, healthy collateral in unrelated assets can still be withdrawn or liquidated.

### Proof of Concept
1. Alice supplies STX and stSTXbtc as collateral (both enabled and encoded in her position mask), and takes no debt or minimal debt.
2. stSTXbtc's vault liquidity-index cache becomes stuck/broken (or its underlying Pyth feed id is retired and no longer returns fresh prices), so `resolve-ztoken`/`price-resolve` for stSTXbtc starts failing `oracle-timestamp-fresh`/`oracle-price-legal` checks permanently (see `mainnet/contracts/market/v0-4-market.clar:373-395`).
3. Alice calls `collateral-remove` to withdraw only her STX. Because she has debt, execution enters the `has-debt` branch, which calls `get-assets position-mask` — this mask still contains the stSTXbtc asset id (`mainnet/contracts/market/v0-4-market.clar:1120-1134`).
4. `get-assets` → `price-multi-resolve` attempts to resolve stSTXbtc's price as part of the batch; it fails, `valid` becomes `false`, `price-multi-resolve` returns `(err ERR-ORACLE-MULTI)`, and `unwrap-panic` at `mainnet/contracts/market/v0-4-market.clar:491` aborts the whole transaction.
5. Alice's STX withdrawal is now permanently blocked, exactly as her healthy collateral is trapped by an unrelated asset's oracle failure — with no code path to exclude stSTXbtc and proceed.

  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))

(define-private (user-safe-mask (mask-user uint) (mask-enabled uint))
  (let ((enabled-collateral (bit-and mask-enabled MAX-U64))
        (user-collateral (bit-and mask-user MAX-U64))
        (user-debt (/ (bit-and mask-user DEBT-MASK) (pow u2 DEBT-OFFSET)))
        (collateral-match (bit-and user-collateral enabled-collateral)))
    (bit-or collateral-match user-debt)))
