## Finding

### Title
Incomplete proof-of-inclusion count validation in DataLayer graftroot offer solving allows under-proven singleton value assertions - (File: `chia/data_layer/data_layer_wallet.py`)

### Summary
`DataLayerWallet.finish_graftroot_solutions()` is the taker-side function that completes a DataLayer (DL) offer by injecting Merkle proofs of key/value inclusion into the `GRAFTROOT_DL_OFFERS` puzzle solution before the spend bundle is submitted on-chain. The function validates the supplied `solver["proofs_of_inclusion"]` against each DL singleton's on-chain root, but the final sufficiency check compares the wrong quantities, which can let it accept an incomplete set of proofs as if it were complete.

### Finding Description
For each DL singleton leg of a graftroot offer, the code iterates the singleton's list of `values` (the values the offer requires proven inclusion for) and, for each value, searches attacker/taker-supplied `solver["proofs_of_inclusion"]` for a Merkle proof that both reconstructs to the expected leaf and matches the singleton's actual current root: [1](#0-0) 

After collecting `all_proofs` (a list of per-singleton proof lists), the code performs a single aggregate sufficiency check: [2](#0-1) 

`sum(len(proofs) for proofs in all_proofs)` is the **total number of individually verified value-proofs across all singleton legs**, while `sum(1 for _ in values_to_prove.as_iter())` is only the **number of singleton legs (groups)**, not the total number of values requiring proof. When an offer involves multiple DL singletons and/or a singleton requires proofs for more than one value, the leg-count threshold is far smaller than the true number of required proofs. This means the aggregate check can pass even though some individual values in `values` never obtained a matching, root-verified proof — those values simply have no entry in the corresponding `proofs_of_inclusion` sub-list for that singleton.

The resulting `new_solution` is built directly from this incompletely-validated `all_proofs` structure and fed into the `GRAFTROOT_DL_OFFERS` puzzle: [3](#0-2) 

Whether this translates into an accepted (invalid) spend depends on how the compiled `GRAFTROOT_DL_OFFERS` CLVM puzzle consumes a shorter-than-expected proof list per singleton — the puzzle source is precompiled (`chia_puzzles_py.programs.GRAFTROOT_DL_OFFERS`) and its exact per-leg length enforcement could not be verified from the Python-level driver alone. Regardless, the Python-side sufficiency gate that is supposed to be the safety net before submission is provably using the wrong count, so it does not reliably reject offers where required inclusion proofs are missing for some values.

### Impact Explanation
This is the DataLayer analog of the reported "arbitrary message/token transfer verification" issue: instead of an Ethereum bridge accepting a malformed Merkle-proven message, a Chia DL offer taker could construct/accept a spend bundle whose graftroot conditions assert inclusion of key/values that were never actually proven against the current on-chain DL root for one or more of the involved singletons, because the completeness check only scales with the number of singleton legs rather than the number of values needing proof. This directly touches the "offers and trades" and "Data Layer roots and proofs" attack surface reachable by an unprivileged offer counterparty.

### Likelihood Explanation
Reachable purely through the offer take flow (`chia/wallet/trade_manager.py` calling `finish_graftroot_solutions`) — no privileged or network-level access is required, only crafting/accepting a multi-singleton or multi-value DataLayer offer with attacker-controlled `solver["proofs_of_inclusion"]` data. The count-mismatch is deterministic whenever more than one value or singleton leg is present, which is a common configuration for DL offers with multiple `values_to_prove` per dependency.

### Recommendation
Change the sufficiency check to compare per-singleton (or total) proven-value counts against the true count of values required, e.g. verify `len(proofs_of_inclusion) == len(values)` inside the per-singleton loop, or compute the total values needed as `sum(len(values) for values in values_to_prove.as_python())` instead of counting `values_to_prove.as_iter()` groups.

### Proof of Concept
Construct a DL offer solver with two singleton legs where leg A requires 3 proven values and leg B requires 0 values (2 groups total). Supply `solver["proofs_of_inclusion"]` containing only 2 valid proofs for leg A's first two values (missing proof for the third value). `sum(len(proofs) for proofs in all_proofs)` = 2, and `sum(1 for _ in values_to_prove.as_iter())` = 2 (number of groups), so `2 < 2` is `False` and the `ValueError("One or more proofs of inclusion were invalid")` is never raised, even though leg A is missing a proof for one of its three required values.
