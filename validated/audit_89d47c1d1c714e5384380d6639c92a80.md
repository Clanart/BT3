## Analysis

The DEX report's broken invariant is: **a value the user implicitly "signs off on" (expected output amounts) is silently recomputed against live, attacker-influenceable state at execution time, with no re-validation against what the user actually approved.**

The closest structural analog in GitHub Desktop is the **partial-commit / line-selection staging path**, not the push/force-push path (which already has an explicit, well-built mitigation via `--force-with-lease` and the `WarnForcePushDialog`/`ConfirmForcePush` flow [1](#0-0) [2](#0-1) ).

### Title
Partial-commit line selection is re-applied against a freshly re-read working-directory diff, allowing silent inclusion of unreviewed content in a commit - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user selects individual lines/hunks to stage ("partial commit"), Desktop stores the selection as a set of **absolute line indices** into the diff that was rendered in the UI. When the commit is actually executed, `applyPatchToIndex` does not reuse that reviewed diff — it re-fetches the diff from disk fresh and reapplies the old index-based selection to the new hunk structure.

### Finding Description
`applyPatchToIndex` regenerates the diff at execution time and formats a patch using the file's stored `selection` object against that new diff: [3](#0-2) . The selection itself is index-based (`file.selection.isSelected(absoluteIndex)`), and `formatPatch` walks the **new** diff's hunks/lines using these old absolute indices to decide what to include: [4](#0-3) .

Desktop's own code acknowledges that diffs can change between when the selection was made and when it's used, but only partially compensates for it in the *UI display* path, not the staging/commit execution path: [5](#0-4) . That reconciliation only prunes now-invalid indices from a `Set` maintained for rendering; it does not block or re-confirm the commit if the underlying file content changed between the user's selection action and `stageFiles`/`applyPatchToIndex` actually running: [6](#0-5) .

This mirrors the DEX bug class exactly: reserves (here, the diff/hunk structure) are computed at execution time rather than pinned to what the user reviewed, and no "slippage" check exists to detect that the committed result diverges from the reviewed one.

### Impact Explanation
If tracked file content changes between the moment a user finalizes a line-level selection (e.g., clicks "Commit") and the moment Desktop actually executes `git apply --cached` (a window that can be seconds, e.g. while the summary/description dialog is open, CI/format-on-save tools run, or a repo-bundled watch/build script executes), the recomputed diff's hunk boundaries and line offsets can shift. Because the stale absolute-index selection is blindly reapplied to the new hunk layout, the resulting patch can:
- Silently include lines the user explicitly deselected (never reviewed), or
- Silently omit/corrupt lines the user selected,

resulting in a commit (and subsequent push) containing content the user never approved — a direct case of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires no elevated privileges, malware, or leaked credentials — only a cloned/opened repository whose tooling (build watcher, formatter-on-save, linter auto-fix, or attacker-supplied script triggered by normal developer workflows such as `npm install`/`postinstall` scripts) modifies tracked files during the ordinary window between selecting diff lines and clicking Commit. This is a realistic and common developer workflow (auto-formatters, file watchers) rather than a contrived scenario, making the likelihood moderate; however, exploiting it deterministically to inject a *specific* malicious change requires some timing control by the attacker-controlled tooling, which lowers confidence for a fully weaponized PoC without further testing in the actual application (I was not able to trace the exact `createCommit`/dispatcher call path from UI selection to `stageFiles` within the remaining tool budget, so the precise time window and whether any additional guard exists closer to the commit-invocation call site could not be fully confirmed).

### Recommendation
- Capture the diff content (or a hash/blob OID of the working file) at the moment the user makes their line selection, and store it alongside the `DiffSelection`.
- At commit time, before calling `applyPatchToIndex`, re-diff the file and compare against the stored hash; if it differs, abort and force the user to re-review/re-select lines against the new diff (analogous to Uniswap's `amountOutMin`/deadline check — pin the "expected state" and refuse execution if it has drifted).
- Alternatively, apply the patch using content-anchored context (already done by `git apply`'s fuzzy matching) but explicitly surface a warning/dialog when the hunk headers/line counts computed from the fresh diff do not match what was originally selected, rather than silently proceeding.

### Proof of Concept
1. Open a repository in Desktop with a tracked file `foo.js` containing lines A, B, C.
2. In the Changes view, select only line B for inclusion in the next commit (deselect A and C), and enter a commit message but do not yet click "Commit" (or click it while a slow hook/dialog delays execution).
3. Concurrently, a background process bundled with the repo (e.g. a formatter task or file watcher declared in `package.json`) rewrites `foo.js`, shifting line offsets (e.g., inserting a new line at the top) without changing the semantic content of B.
4. When Desktop proceeds to stage via `applyPatchToIndex`, it re-diffs `foo.js` and reapplies the stale absolute-index selection to the new hunk layout, producing a patch that no longer corresponds to "only line B" — potentially including the attacker-modified content or omitting line B.
5. The resulting commit (and any subsequent push) silently contains content the user never visually approved.

*(Note: I could not fully verify the exact timing window in the UI dispatcher between "Commit" click and `stageFiles` execution within the available search budget — this would need direct testing against a running Desktop build to confirm the precise exploitation window.)*
