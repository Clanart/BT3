## Title
Path traversal via tracked symlink — `revealInFileManager` follows repo symlinks to files outside the repository - (File: `app/src/lib/app-shell.ts`)

### Summary
The HackerOne report describes `harp` following a symlink placed inside the served project directory to list/read files outside the intended web root. GitHub Desktop has the same broken invariant in its "Show/Reveal in Finder/Explorer" feature: a file path taken straight from a cloned repository's working tree is joined onto the repository root with plain `Path.join` and handed to the OS shell, which transparently follows the entry if it is a symlink.

### Finding Description
`revealInFileManager` builds the full path with a lexical join only, and forwards it to `shell.showItemInFolder`: [1](#0-0) 

Note that `showItemInFolder` is explicitly documented in the same file as unsafe for unvalidated input: *"Do not use this method with non-validated paths."* [2](#0-1) 

`revealInFileManager` is invoked directly with `file.path`, which is a repository-relative path reported by `git status` for a `WorkingDirectoryFileChange` — content fully controlled by whoever authored the cloned/fetched repository: [3](#0-2) 

Git tracks symlinks natively (mode `120000`). An attacker can commit a tracked file, e.g. `notes.txt`, that is actually a symlink pointing to a sensitive location outside the repo (`~/.ssh/id_rsa`, `/etc/passwd`, another user's project, etc.). After the victim clones/fetches this repository and it appears as a changed/new file in the Changes list, `Path.join(repository.path, "notes.txt")` yields a path that is lexically inside the repo but, once handed to the OS (Finder/Explorer via `shell.showItemInFolder`), resolves through the symlink to the attacker-chosen external target — revealing/selecting a file the user never intended to expose.

The same unguarded pattern (`Path.join(repository.path, filePath)` with no symlink/root check) also appears in:
- `onOpenInExternalEditor` in `app.tsx`, which opens the resolved path directly in the user's configured external editor (a stronger primitive — the editor will display the *contents* of the symlink target, not just its location): [4](#0-3) 
- `getResolutionDiff` and `getWorkingDirectoryImage` in `diff.ts`, which read file bytes directly for diff/image rendering: [5](#0-4) [6](#0-5) 

This is notable because the codebase clearly already recognizes this exact bug class and has fixed it in two other call sites using `resolveWithin`, which does a `realpath`-based containment check to reject symlink escapes: [7](#0-6) [8](#0-7) [9](#0-8) 

`revealInFileManager`, `onOpenInExternalEditor`, `getResolutionDiff`, and `getWorkingDirectoryImage` were never updated to use `resolveWithin`, so the guard that stops the deep-link (`x-github-client://openRepo`) and Copilot-conflict-context paths does nothing for the ordinary Changes-list "Show in Finder"/"Open in external editor"/diff/image-preview flows.

### Impact Explanation
An attacker who controls a repository the victim clones or pulls (a public repo, a PR branch, a fork, etc.) can plant a tracked symlink that:
- Causes "Show in Finder/Explorer" to open/select an arbitrary file/directory on the victim's filesystem outside the repo, disclosing its existence and location.
- Causes "Open in external editor" to load and display the full contents of an arbitrary out-of-repo file (e.g., SSH private keys, `.netrc`, other repositories' source) inside the user's editor — a direct out-of-repo content-read primitive.
- Causes the diff/image-preview machinery to read out-of-repo file bytes into the app's memory and potentially render them in the UI.

This matches the "Valid Impact" criteria: the attacker controls a cloned/fetched repository, no local/physical access or prior malware is needed, and the result is file read outside the repo.

### Likelihood Explanation
Likelihood is moderate-to-high: committing a symlink to a git repo is trivial (`ln -s /path/to/target file`, `git add`, `git commit`), requires no special permissions, and any user who clones the repo and interacts with the Changes list context menu ("Show in Finder"), opens the file in an external editor, or previews its diff/image triggers the vulnerable code path. It requires a normal user action (right-click → reveal, or open-in-editor) but no unnatural or unusual steps — these are core, frequently used Desktop features.

### Recommendation
Route every repository-relative path derived from git status/diff data through `resolveWithin` (already implemented in `app/src/lib/path.ts` and used in `copilot-conflict-context.ts` and `dispatcher.ts`) before it is joined and passed to filesystem or shell APIs. Specifically:
- `revealInFileManager` in `app/src/lib/app-shell.ts` should call `resolveWithin(repository.path, path)` and refuse the action (or log/error) if the result is `null`.
- `onOpenInExternalEditor` in `app/src/ui/app.tsx` should perform the same containment check before calling `openInExternalEditor`.
- `getResolutionDiff` (`app/src/lib/git/diff.ts`) and `getWorkingDirectoryImage` (`app/src/lib/git/diff.ts`) should validate the resolved path stays within `repository.path` before reading file contents.

### Proof of Concept
1. Attacker creates a repository containing a symlink tracked by git: `ln -s ~/.ssh/id_rsa leak.txt && git add leak.txt && git commit -m "add notes"`.
2. Victim clones the repository in GitHub Desktop.
3. `leak.txt` shows up in the Changes list (or history) as a file.
4. Victim right-clicks `leak.txt` and selects "Show in Finder"/"Show in Explorer" (`getRevealInFileManagerMenuItem` → `revealInFileManager`), or opens it in an external editor.
5. The OS/editor follows the symlink and reveals/displays `~/.ssh/id_rsa` (or any other target path chosen by the attacker), even though that file is entirely outside the cloned repository. [3](#0-2) [1](#0-0)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
