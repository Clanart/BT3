## Title
Single reverting token in a multi-asset order permanently locks *all* escrowed tokens in `IntentsBase._withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` releases every escrowed token for an order commitment in a single atomic loop. If any one token transfer in that loop reverts, the whole function reverts, and since this function is the only path that decrements `_orders[commitment][token]` and marks `_filled[commitment]`, none of the other (perfectly fine) tokens escrowed for that same order can ever be released. This is the same "parent transaction rides on the success of every child leg" pattern flagged in TRST-H-2, applied to Hyperbridge's cross-chain intent settlement instead of `ComplexRewarder`.

### Finding Description
`_withdraw` iterates over `body.tokens` and performs an unconditional `IERC20.safeTransfer` (or native `.call`) per token: [1](#0-0) 

This is invoked from `ExtrinsicIntents.onAccept` for both `RedeemEscrow` (pay the solver) and `RefundEscrow` (refund the user), and from `onGetResponse` for source-side cancellation: [2](#0-1) [3](#0-2) 

An `Order` can escrow multiple distinct input tokens (`order.inputs` is a `TokenInfo[]`), and the entire array is redeemed/refunded in one call. If transfer of *any single token* in that array reverts — e.g. the token is an ERC20 with owner-controlled blacklisting/pausing (common in USDC-style tokens), or is deliberately chosen by the order creator to be blockable for the eventual beneficiary — `_withdraw` reverts entirely. Because `_orders[commitment][token]` is only decremented inside the same loop and nothing is decremented on revert, the transaction can be retried indefinitely but will always fail at the same token, and the other legitimate tokens in the same order (already proven redeemable, already delivered on the destination side by the solver) are permanently stuck in escrow.

This mirrors the audited bug exactly: like `ComplexRewarder.onReward()` bundling the parent payout with child-rewarder payouts so that one failing child blocks the whole reward flow (and thus blocks `V3 Vault.withdraw()`), `_withdraw()` bundles unrelated per-token transfers into one all-or-nothing call so that one poisoned token blocks release of all other tokens for that order.

Unlike `EvmHost.dispatchIncoming`, which explicitly guards against a permanently failing `onAccept` by deleting the request receipt on failure so the request can be retried by a relayer, retrying here does not help — the failure is deterministic (the token itself blocks the beneficiary), so the request is stuck forever, permanently freezing the co-escrowed assets.

### Impact Explanation
An unprivileged order creator can escrow a multi-asset order where one input token is one they (or a cooperating admin of that token) can later block for the solver's address (e.g., blacklist function), while the other input token is high-value and legitimate. Once a solver fully fills the cross-chain order (required, since cross-chain fills are all-or-nothing) and the `RedeemEscrow` message reaches the source chain, `_withdraw` will permanently revert on the blocked token, freezing the solver's rightful proceeds of the legitimate token as well. The same applies to `RefundEscrow`/`onGetResponse` cancellation paths — a single stuck token can freeze a refund of otherwise-refundable assets. This is a direct loss/lock of bridged funds triggered purely by public entrypoints (`fillOrder`, `cancelOrder`), matching the bounty's "stealing or loss of funds" / "logic attack" category.

### Likelihood Explanation
Moderate-to-high: it only requires constructing an order with a multi-token input set that includes one blockable/failing ERC20 — no relayer, prover, or admin compromise is needed. Tokens with owner-controlled blacklists or pause functionality are common enough (stablecoins, wrapped assets) that this is a realistic, attacker-reachable condition, and the order creator fully controls which tokens are included in their own order.

### Recommendation
Make per-token release independent: wrap each token transfer in `_withdraw` with try/catch (or use a pull-based accounting model where failed transfers leave a claimable balance instead of reverting the whole batch), so a single non-transferable token cannot block release of the other escrowed assets. Emit an event/track a "stuck" amount for the failing token so it can be retried or swept separately, similar to the mitigation recommended for `ComplexRewarder.onReward()`.

### Proof of Concept
1. User creates a cross-chain `Order` with `order.inputs = [TOKEN_A (1000 legit_token), TOKEN_B (1 blacklist_token)]`, where `TOKEN_B` is an ERC20 whose owner can later blacklist arbitrary addresses.
2. Solver calls `fillOrder` on the destination chain, fully satisfying `order.output`, triggering `_fillCrossChain` → dispatch of `RedeemEscrow` back to source chain, per [4](#0-3) .
3. Before the `RedeemEscrow` message is delivered, `TOKEN_B`'s owner blacklists the solver's address (or the token is simply paused).
4. On the source chain, `onAccept` decodes `RedeemEscrow` and calls `_withdraw(body, false, true)` per [2](#0-1) .
5. `_withdraw`'s loop successfully sends `TOKEN_A` to the solver, then reverts on `TOKEN_B`'s `safeTransfer` per [5](#0-4) ; the whole transaction (including the `TOKEN_A` transfer) is rolled back.
6. Every retry of the same `RedeemEscrow` request hits the same revert. `TOKEN_A`, fully earned by the solver, remains permanently escrowed and unretrievable — funds are frozen with no recovery path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }
