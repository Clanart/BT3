### Title
Opt-in re-enablement of `protocol.file.allow=always` during submodule update can reintroduce the git `file://` submodule hardlink/arbitrary-file-read primitive - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` boolean that, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. [1](#0-0) 
This flag is threaded through from `checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts`, which both default the parameter to `false` but allow callers to override it to `true`. [2](#0-1) [3](#0-2) 

### Finding Description
Upstream git disabled `file://` protocol support for recursive submodule clones by default (the `protocol.file.allow` hardening introduced after CVE-2022-39253) specifically because a malicious repository can declare a `.gitmodules` entry with a `file://` URL pointing at an attacker-chosen local path. When such a submodule is cloned/updated, git can use hardlinks from that local path into the resulting working tree, which historically allowed reading or exposing files outside the boundary the user intended to trust (the cloned/fetched repository content). Desktop's `allowFileProtocol` parameter is a deliberate escape hatch that re-enables this behavior for specific flows (per the doc comment "Whether to allow file:// protocol for submodules"). Whenever a call site passes `true` for this parameter while operating on a repository whose content (including `.gitmodules`) was populated from an untrusted fetch/clone (e.g., checking out a fork's PR branch, or checking out a commit from a remote the user does not fully trust), the invariant that git's own protocol restriction is supposed to guarantee — that submodule URLs in fetched content cannot silently pull in or hardlink arbitrary local files — is defeated by application logic rather than by git's default posture. The `parseRemote`/`sanitizeCloneName` guards in `app/src/lib/remote-parsing.ts` [4](#0-3)  only protect the clone target directory name; they do nothing to validate submodule URLs embedded in `.gitmodules`, so they do not stop this path.

### Impact Explanation
If `allowFileProtocol: true` is reachable from a flow that checks out attacker-controlled content (a branch/commit from a repository or fork the attacker controls, whose `.gitmodules` is under attacker control), the attacker can point a submodule URL at a `file://` path on the victim's machine and have git create hardlinks from that location into the submodule working tree during `git submodule update --init --recursive`, potentially exposing file content outside the intended repository boundary onto disk where the user might inadvertently commit/share it, or exploiting git's hardlink/symlink handling on the local filesystem.

### Likelihood Explanation
I could not confirm during this session which specific UI/dispatcher call sites pass `true` for `allowFileProtocol` (the `app/src/lib/stores/app-store.ts` and `app/src/ui/dispatcher/dispatcher.ts` matches for `checkoutBranch`/`checkoutCommit` were located but not opened before tool budget was exhausted). If all call sites pass `false` (the parameter default) for any flow touching untrusted/forked content, this reduces to a non-issue since the vulnerable code path is never taken. This should be verified by inspecting every caller of `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` to determine whether `allowFileProtocol=true` is ever used for content originating from an untrusted remote/fork/PR checkout rather than purely local, user-initiated actions.

### Recommendation
Audit every call site that passes `allowFileProtocol: true` and confirm it is only used for repositories/commits the user directly and explicitly trusts (not forks, not PR checkouts, not content pulled from arbitrary URLs). Where untrusted content might flow through these code paths, always use the default git-hardened behavior (omit `protocol.file.allow=always`) and instead surface an explicit warning/consent dialog if a submodule genuinely requires `file://` access.
