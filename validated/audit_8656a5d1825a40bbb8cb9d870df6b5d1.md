### Title
`resolveWithin` containment check uses substring `startsWith` instead of a path-boundary comparison, allowing sibling-directory escape - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` (used by `resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) is Desktop's central guard against path traversal and symlink escapes when resolving attacker-influenced relative paths (conflicted file paths from a cloned repo, `filepath` from an `x-github-client://` deep link, etc.). Its final containment check is a raw string-prefix test, `realResolved.startsWith(realRoot)` [1](#0-0) , with no verification that the character following the root prefix is a path separator. This is the exact bug class of the seed report: a boundary comparison that is "off by one" element (missing separator boundary) admits a value one step past the intended limit — here, a sibling path such as `<root>-evil/...` is treated as being "inside" `<root>`.

### Finding Description
`_resolveWithin` is documented and relied upon throughout the app as the safety gate that guarantees "the resolved path is guaranteed to reside at, or underneath" `rootPath` [2](#0-1) . It joins/normalizes the root and the untrusted relative segments, resolves symlinks with `realpath` on both sides, and then checks containment purely with:

```
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

`String.prototype.startsWith` performs a literal character-prefix match, not a path-segment match. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and, after resolving a symlink placed inside the attacker's repository, `realResolved` becomes `/Users/victim/Documents/GitHub/repo-secrets/config.json`, the check passes because the entire string `realRoot` is a literal prefix of `realResolved` — even though `repo-secrets` is a completely different directory, not a subdirectory of `repo`. The unit tests for this function only cover `..`-traversal and symlink-to-parent cases [4](#0-3) ; there is no test (and no code) enforcing that the byte after the shared prefix is `Path.sep` or the end of string, so the sibling-directory case is unguarded.

Callers treat a non-`null` return from `resolveWithin` as proof the path is safely inside the repository and then perform read/open operations without any further boundary check:
- `buildConflictContext` in `copilot-conflict-context.ts` calls `resolveWithin(workingDirectory, file.path)` for every conflicted file path taken from git conflict metadata, then reads file contents from the resolved path and forwards them to the Copilot SDK as prompt context [5](#0-4) .
- `openRepositoryFromUrl` in `dispatcher.ts` calls `resolveWithin(repository.path, filepath)` for the `filepath` parameter of an `x-github-client://` deep link and, if non-null, calls `shell.showItemInFolder(resolved)` [6](#0-5) .

Neither caller re-validates that the resolved path is actually a descendant of the intended root beyond trusting `resolveWithin`'s return value, so the flawed boundary check is the sole line of defense.

### Impact Explanation
For the conflict-context path, an attacker who controls a repository the victim clones/fetches (or a merge/rebase the victim triggers against attacker-controlled branches) controls a symlink inside the working tree. If a real directory adjacent to the repo's working directory shares the repo directory name as a literal prefix (e.g. multiple repos cloned side-by-side into the default "GitHub Desktop" clone root, such as `repo` and `repo-internal`, or a bare/worktree pairing that Desktop itself creates with predictable sibling names), a symlink resolving into that sibling directory would be accepted as "within" the repository, and its file contents would be read and exfiltrated to the Copilot API as part of automated conflict-resolution context — a read-outside-repo plus potential credential/config exfiltration if the sibling directory contains sensitive files. For the deep-link path, a malicious link with a crafted `filepath` combined with an on-disk sibling directory could cause Desktop to reveal/open a file outside the intended repository via `shell.showItemInFolder`.

### Likelihood Explanation
Exploitability is conditional: the attacker must control the untrusted path component (which they do — repo content or deep-link click), but they also need a suitable sibling path on the victim's filesystem whose name is a superstring of the repository root path with no separator, since the attacker does not directly control the victim's directory layout. This makes the bug a real, reachable, unguarded logic flaw (matching the report's off-by-one boundary theme precisely), but the practical trigger depends on filesystem layout coincidences (e.g., Desktop's own habit of cloning multiple similarly-prefixed repos into one parent "GitHub" folder, or user-created sibling folders), which lowers likelihood relative to a fully attacker-controlled traversal.

### Recommendation
Fix the containment check to require a path-separator boundary (or exact equality), e.g.:
```ts
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the platform-appropriate separator from the `options` passed into `_resolveWithin` (posix `'/'` or win32 `'\\'`), and add regression tests covering the sibling-directory case (`root` vs `root-evil`) for both `resolveWithin` and the platform-specific variants.

### Proof of Concept
1. On disk, have `/Users/victim/Documents/GitHub/repo` (the cloned repository) and a sibling directory `/Users/victim/Documents/GitHub/repo-secrets/config.json` that exists for unrelated reasons (e.g., another cloned repo or app data folder with a prefix-colliding name).
2. As the repository owner (attacker), commit a conflicting file whose content, when checked out mid-merge, is actually a symlink named e.g. `link` pointing to `../repo-secrets/config.json` (or craft the merge so the working tree contains this symlink at conflict time).
3. Victim opens the repo in Desktop and triggers a merge/rebase that conflicts on that path; Desktop's Copilot conflict-resolution flow calls `buildConflictContext`, which calls `resolveWithin('/Users/victim/Documents/GitHub/repo', 'link')` [7](#0-6) .
4. `_resolveWithin` computes `realResolved = /Users/victim/Documents/GitHub/repo-secrets/config.json`, `realRoot = /Users/victim/Documents/GitHub/repo`; `realResolved.startsWith(realRoot)` evaluates `true` because `repo` is a literal prefix of `repo-secrets`, so the function returns the resolved path instead of `null` [1](#0-0) .
5. `buildConflictContext` reads `config.json`'s contents and includes them as `rawContent` in the payload sent to the Copilot SDK [8](#0-7) , exfiltrating data from outside the repository the user believes they are working in.

      try {
        const fileStat = await stat(absolutePath)
        if (fileStat.size > MAX_CONFLICT_FILE_READ_SIZE) {
          return {
            path: file.path,
            hunks: [],
            skippedReason: 'File too large to resolve automatically',
          }
        }
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File could not be read',
        }
      }

      let content: string
      try {
        content = await readFile(absolutePath, 'utf8')
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File could not be read',
        }
      }

      const hunks = extractConflictHunks(content)
      if (hunks.length === 0) {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'No conflict markers found',

      const hunkSkipReason = getHunkSkipReason(hunks)

          path: file.path,
