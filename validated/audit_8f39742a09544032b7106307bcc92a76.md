### Title
`SignableTransaction::new` omits the OP_RETURN data output from fee/weight estimation, letting a crafted `data` field push the real fee rate below the checked minimum - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying caller-supplied `data` to `tx_outs` *before* computing the transaction weight, but then calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which only accounts for `payments` (and optionally `change`) — never the data output. The `needed_fee` and the minimum-relay-fee check are therefore computed against a smaller virtual size than the signed transaction actually has.

### Finding Description
- The `data` output is pushed to `tx_outs` at `send.rs:194-202` (a `ScriptBuf::new_op_return` output adds ~11 bytes of script + 9-byte `TxOut` header + the pushed data, up to ~100+ serialized bytes / ~100 WU for the max 80-byte payload).
- Fee estimation at `send.rs:204` calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`. Inside `calculate_weight_vbytes` (`send.rs:62-127`), the mock transaction's outputs are built solely from `payments` and the optional `change`; the OP_RETURN output is never represented, so both `weight` and `vbytes` are undercounted.
- Consequently `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) and the `TooLowFee` minimum-relay check (`send.rs:211`) are validated against the wrong vsize. The signed transaction (`self.tx`) does include the OP_RETURN output, so its true vsize — and the vsize the Bitcoin network will measure — is larger.
- Because the OP_RETURN output has `Amount::ZERO`, the absolute satoshi fee (`fee()`, `send.rs:138-141`) is unchanged; what is silently degraded is the *fee rate* and the *validity of the `TooLowFee` guarantee*. A caller selecting `fee_per_vbyte` at the margin (e.g., `fee_per_vbyte = 1`, or any value where `needed_fee` just passes the `DEFAULT_MIN_RELAY_TX_FEE` floor) produces a transaction whose actual relay fee rate is below the minimum, so it will be rejected/dropped by nodes.
- `data` is attacker-influenced: in the Serai protocol it carries the out-instruction payload derived from user-submitted `InInstruction`s, so an unprivileged external user controls up to 80 bytes here.

### Impact Explanation
The class of CVE-2023-4907 — attacker-crafted input that causes a security-relevant property to be misrepresented to the system/user — maps here onto a crafted `data` payload that makes `SignableTransaction` misrepresent the transaction's true size to its own fee-safety checks. The result is a signed Bitcoin transaction with an effective fee rate lower than requested and potentially below `DEFAULT_MIN_RELAY_TX_FEE`, i.e., a transaction the network will not relay, locking up the protocol's inputs (they are committed via `Prevouts::All` in the produced signatures, `send.rs:375`) until a replacement is negotiated. This is a reachable correctness/safety failure in the in-scope wallet code.

### Likelihood Explanation
Any signing flow that supplies `data` (out-instructions) plus a low `fee_per_vbyte` hits this deterministically — no race, no collusion, just arithmetic. With the max 80-byte payload the undercount is ~25 vbytes, enough to push a boundary-fee transaction under the relay floor. Impact is bounded (stuck transaction rather than theft), consistent with Medium/Low severity.

### Recommendation
Include the OP_RETURN output in the size estimate: either add it to the outputs built inside `calculate_weight_vbytes` (pass `data` through or compute the weight on the already-assembled `tx_outs`), or construct the final `Transaction` first and measure `tx.weight()`/`vsize()` directly before deriving `needed_fee` and performing the `TooLowFee` check.

### Proof of Concept
```rust
// In networks/bitcoin context:
let inputs = vec![received_output];            // any scanned ReceivedOutput
let payments = &[(payment_script, 546u64)];    // minimal dust payment
let data = Some(vec![0u8; 80]);                // max allowed OP_RETURN payload

let tx = SignableTransaction::new(inputs, payments, None, data, /*fee_per_vbyte=*/1).unwrap();
// needed_fee was computed without the ~46-byte OP_RETURN output:
assert!(tx.needed_fee() < u64::try_from(tx.transaction().vsize()).unwrap());
// The real vsize exceeds the estimated one, so the actual fee rate < 1 sat/vbyte
// and the tx can fall under DEFAULT_MIN_RELAY_TX_FEE despite passing TooLowFee.
```
