## Analog Found: CEI-violation + missing `nonReentrant` in the Tron `IntentGatewayV2.withdraw()` escrow release path

### Title
Escrow balance decremented after external token transfer, with no reentrancy guard, in the Tron `IntentGatewayV2` contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The BathBuddy bug is a checks-effects-interactions (CEI) violation: the "released" accounting is updated *after* the external token transfer, so a callback-capable token can re-enter and drain more than it is owed. The Tron fork of Hyperbridge's Intent Gateway reintroduces exactly this pattern in `withdraw()`, and — unlike the canonical/audited EVM contract — omits the `nonReentrant` guard entirely on the public entry point that reaches it.

### Finding Description
In the canonical EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol` `_withdraw`, lines 390-410), the escrow mapping is decremented **before** the token transfer:
```
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) { beneficiary.call{value: amount}(""); ... }
else { IERC20(token).safeTransfer(beneficiary, amount); }
``` [1](#0-0) 

and its public `cancelOrder` entry point carries `nonReentrant`: [2](#0-1) 

The Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) inverts this ordering — the transfer happens first, and `_orders[body.commitment][token] -= amount;` runs **after**:
```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    ...
}
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

and its public same-chain `cancelOrder` entry point has **no `nonReentrant` modifier at all**: [4](#0-3) 

A `grep` across this file confirms zero occurrences of `nonReentrant`/`ReentrancyGuard` anywhere in the Tron contract, whereas the mainline EVM contract explicitly guards `cancelOrder`.

The only defense-in-depth present is `_filled[body.commitment] = beneficiary;`, which is set *before* the token loop [5](#0-4) . This blocks a naive re-entrant call into `cancelOrder`/`withdraw` for the *same* commitment, but it does **not** protect the per-token `_orders[commitment][token]` balance itself, which remains stale (un-decremented) for the whole duration of the external call. Any other unguarded function that reads or acts on that same live escrow value (e.g. the documented same-chain partial-fill logic, which "releases the proportional share of escrowed inputs immediately" by reading `_orders[commitment][token]`, per `docs/content/developers/evm/intent-gateway/overview.mdx:31-33`) can observe and act on the pre-decrement balance during the reentrant callback window.

### Impact Explanation
`order.inputs` — the tokens escrowed and later refunded/paid out through `withdraw()` — are chosen entirely by the order-placing user at `placeOrder()` time [6](#0-5) . This makes the token contract fully attacker-controlled: nothing prevents a user from escrowing a callback-capable ERC-777-style or "evil" ERC-20 as an input. When that same user later self-cancels a same-chain order via the public, unguarded `cancelOrder()` (only requires `order.user == msg.sender`, no `nonReentrant`), the malicious token's transfer-hook fires mid-`withdraw()`, with `_orders[commitment][token]` still un-decremented. This is the direct on-chain analog of BathBuddy's `release()`: fund-accounting mutation happens strictly after interaction, on a path reachable by any unprivileged user, in a contract that (unlike its sibling implementation) carries no reentrancy guard.

### Likelihood Explanation
High confidence that the code pattern exists exactly as described (verified by direct reading of both the mainline and Tron variants side by side). The exploitability is confined to same-chain orders escrowing attacker-supplied malicious tokens, and the strongest guaranteed guard (`_filled`) does block the most direct double-`withdraw()` replay for the identical commitment — the residual risk is any other logic (same-chain partial fills, dust sweeping, or future functions) that reads `_orders[commitment][token]` without accounting for reentrancy, which is plausible given the codebase's documented partial-fill design but could not be fully confirmed within the available `fillOrder` code for the Tron variant.

### Recommendation
- Decrement `_orders[body.commitment][token]` before performing the external transfer in `withdraw()` (same fix as already applied in the mainline `_withdraw`).
- Add `nonReentrant` to `cancelOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match the mainline EVM contract.
- Audit the Tron fork end-to-end for other CEI/guard divergences from the maintained `evm/src` contracts, since this file appears to be a stale/regressed copy.

### Proof of Concept
1. Attacker deploys a malicious ERC-20-like token `M` whose `transfer()` implementation calls back into arbitrary contracts.
2. Attacker calls `placeOrder` with `order.inputs = [{token: M, amount: X}]`, `order.source == order.destination` (same-chain), escrowing `X` of `M`: `_orders[commitment][M] = X`.
3. Attacker calls `cancelOrder(order, options)` as `order.user`. This sets `_filled[commitment] = attacker` then enters the token loop.
4. `withdraw()` calls `M.call(transfer(attacker, X))` — inside `M`'s `transfer`, the attacker's callback fires while `_orders[commitment][M]` is still `X` (not yet decremented).
5. Any other function reachable from that callback which trusts the still-unset `_orders[commitment][M]` balance (e.g. a partial-fill or dust path reading the same mapping) can act on funds that are nominally already being paid out in the outer call, corrupting the escrow accounting for `_orders[commitment][M]`.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);

                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});
