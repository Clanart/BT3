### Title
Sybil-splitting a vlMGP lock across many referral-registered addresses inflates aggregate boost factor and steals BoostPoint share from honest referrers - (File: `libraries/DSMath.sol`, `rewards/ReferralStorage.sol`)

### Summary
`ReferralStorage.updateTotalFactor` sets each user's `factor = DSMath.sqrt(lockedAmount)` [1](#0-0)  and `_calBoosted` distributes a fixed `BoostPoint` pool proportionally to `factor / totalBoostFactor` [2](#0-1) . Because `sqrt` is concave, `sqrt(a) + sqrt(b) > sqrt(a+b)`, so an attacker who splits one vlMGP lock across `n` self-controlled addresses—each registering its own referral code via `registerCode` [3](#0-2) —generates an aggregate factor of `sqrt(n)·sqrt(L)` instead of `sqrt(L)`, which grows unboundedly with `n` and lets the attacker capture a disproportionate, ever-increasing share of the fixed `BoostPoint` pool at the expense of honest single-address referrers.

### Finding Description
`VLMGP._lock` calls `IReferralStorage(referralStorage).updateTotalFactor(_for)` on every lock [4](#0-3) , which recomputes `userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt)` from `IVLMGP(vlMGP).getUserTotalLocked(_account)` and updates the global `totalBoostFactor` by removing the old factor and adding the new one [1](#0-0) .

`DSMath.sqrt` is a standard Babylonian-method integer square root [5](#0-4) , which is concave: for any split `L = l_1 + l_2 + ... + l_n`, `sqrt(l_1) + sqrt(l_2) + ... + sqrt(l_n) >= sqrt(L)`, with strict inequality whenever the lock is split into more than one non-trivial piece. In the maximal case of an even split across `n` addresses, the sum becomes `sqrt(n) * sqrt(L/n) * n / sqrt(n)`... concretely `n * sqrt(L/n) = sqrt(n*L)`, which is unbounded as `n` grows.

The exploit path requires only unprivileged actions:
1. Attacker deploys/controls `n` addresses.
2. Each address calls `registerCode` to set `userInfo.myCode != bytes32(0)` (a precondition for `updateTotalFactor` to actually update anything — line 199: `if (userInfo.myCode == bytes32(0)) return;`).
3. Attacker splits a total lock amount `L` across the `n` addresses (locking `L/n` in each via `VLMGP.lock`, or lock/unlock/relock cycles to move balance around), each triggering `updateTotalFactor`.
4. Each address's `factor = sqrt(L/n)`; total attacker-controlled factor = `sqrt(nL)`, growing with `sqrt(n)` versus a single un-split lock's `sqrt(L)`.
5. Since `_calBoosted` divides each address's individual `factor` by the *global* `totalBoostFactor` (which includes the attacker's own inflated contribution alongside honest referrers' factors), the attacker's aggregate boosted share (`sum over attacker addresses of BoostPoint * factor_i / totalBoostFactor`) grows toward capturing the majority of the fixed `BoostPoint` allocation as `n` increases, diluting the share available to honest, single-address referrers.
6. This inflated `boostesd` value feeds directly into `trigger()`'s reward split math (`refererPercentage`/`refereePercentage` derived from `basic + boostesd`), increasing the referral reward cut paid out to the attacker's addresses when their referees claim rewards [6](#0-5) .

No existing check prevents this: there is no per-account cap on `factor`, no linear (non-concave) aggregation, no minimum lock size, no Sybil/address-uniqueness enforcement in `registerCode`, and `updateTotalFactor` is permissionlessly triggerable by anyone locking/unlocking vlMGP (`_onlyVlMGP` only restricts the caller to the `VLMGP` contract, not the beneficiary).

### Impact Explanation
The `BoostPoint` pool is a shared, finite allocation among all referrers with an active code. By Sybil-splitting one economic position into many, an attacker mechanically increases their aggregate participation weight beyond what a single position would earn, capturing yield that would otherwise accrue to honest referrers' `rewardAmount` via `trigger()`. This matches "Theft of unclaimed yield" (High) since the diverted amount is a quantifiable share of the fixed `BoostPoint` percentage applied to real referee reward claims, and it comes directly at the expense of other legitimate referral participants' expected share.

### Likelihood Explanation
Feasible and repeatable at low cost: the attacker needs only (a) unique `bytes32` codes for each Sybil address (`registerCode` has no cost beyond gas and no per-code fee), (b) the ability to distribute their existing vlMGP lock across many addresses (their own capital, not lost — vlMGP remains unlockable/withdrawable later), and (c) each address triggering `updateTotalFactor` via a lock. The benefit (share of `BoostPoint`) scales with `sqrt(n)`, so the attack is more profitable with more Sybils, and can be repeated/increased over time as long as the attacker keeps adding split addresses.

### Recommendation
Replace the account-level concave weighting with a mechanism that is invariant to position-splitting, e.g.:
- Track and cap `factor` per unique KYC/identity or per referral-code-registrant using a linear function of locked amount (`factor = lockedAmount`, not `sqrt`), so splitting a fixed total across addresses yields the same aggregate factor.
- Alternatively, if the diminishing-returns design (`sqrt`) is intentional to reduce whale dominance, aggregate `lockedAmount` per attacker-linked address set before applying `sqrt` — but this requires Sybil resistance (e.g., minimum lock duration/size thresholds, one code per verified identity, or bonding requirements) which is hard to enforce on-chain without additional identity infrastructure.
- At minimum, enforce a floor lock amount for `registerCode`/`updateTotalFactor` eligibility high enough that splitting into many addresses is not sqrt-profitable relative to gas + opportunity costs, and consider capping `totalBoostFactor` contribution per unique address cluster.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `ReferralStorage` with a fixed `BoostPoint` and register two honest referrer accounts `R1`, `R2`, each locking `1000e18` MGP as a single lock and registering a referral code; record `userInfos[R1].factor`, `userInfos[R2].factor`, `totalBoostFactor`.
2. Attacker locks `1000e18` MGP across `n = 50` freshly created addresses (`20e18` each), each address calling `registerCode` with a unique code, each triggering `VLMGP.lock` → `updateTotalFactor`.
3. Assert: sum of attacker addresses' `factor` (`sum(sqrt(20e18))*50`) is strictly greater than `sqrt(1000e18)` (the amount a single lock would have produced), and greater than `userInfos[R1].factor` despite equal locked capital.
4. Assert: `_calBoosted` (via `boosted(address)`) summed across attacker addresses exceeds `_calBoosted(R1)` despite equal total locked capital, confirming disproportionate share capture.
5. Simulate a referee claim triggering `trigger()` for both an attacker address and `R1` with identical `_amount`; assert attacker's aggregate `refererAmount` exceeds `R1`'s despite equal locked principal, demonstrating diverted/stolen unclaimed yield.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
