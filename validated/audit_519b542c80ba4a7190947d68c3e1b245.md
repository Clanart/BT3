### Title
Relayer fee metadata is never cleared after a successful GET response is delivered, enabling a duplicate fee payout via the timeout path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` pays the relayer fee for a GET request by reading `_requestCommitments[commitment].fee` **after** the external call to the destination app's `onGetResponse` succeeds, but it never deletes `_requestCommitments[commitment]` afterward. Every other cleanup path in the same contract (`dispatchIncoming(PostRequest, ...)`, `dispatchTimeOut(GetRequestTimeout, ...)`, `dispatchTimeOut(PostRequestTimeout, ...)`) explicitly deletes the corresponding replay-protection/fee-metadata entry as part of committing the outcome, restoring it only if the external call reverts. The GET-response success path breaks this pattern, leaving stale fee-metadata state in storage that a later, independent code path can still act on.

### Finding Description
Compare the two sibling functions in `evm/src/core/EvmHost.sol`: [1](#0-0) 

`dispatchIncoming(GetResponse ...)` sets `_responseReceipts[commitment]` before the external call (good — mirrors the "commit before external effects" pattern the H-2 report calls for), calls `onGetResponse`, and — only on success — pays `relayer` the fee recorded in `_requestCommitments[commitment].fee`. It never clears `_requestCommitments[commitment]`.

Contrast with the timeout handler for the very same request type: [2](#0-1) 

`dispatchTimeOut(GetRequestTimeout ...)` treats `_requestCommitments[commitment]` as the single source of truth for whether a fee is still owed: it `delete`s the entry up front for replay protection, restores it only on failure, and pays out `meta.fee` to `meta.sender` on success.

Because the GET-response success path leaves `_requestCommitments[commitment]` populated with the original `fee`, the two code paths are not mutually exclusive at the `EvmHost` storage level: nothing in `EvmHost.sol` itself prevents `dispatchTimeOut(GetRequestTimeout, meta, commitment)` from later being invoked for the same `commitment` and paying the fee out a second time (this time as a "timeout refund" to `meta.sender`), since the fee value is still sitting in `_requestCommitments[commitment]` exactly as before the response was processed. This is the same broken invariant as H-2: a value that should have been zeroed out immediately after being consumed is left "dirty" in storage, so a second, independently-triggered code path re-consumes it.

The only thing that would stop this is a check, elsewhere in the request-handling stack (e.g. `HandlerV2`), that the request has not already been responded to before it will accept a timeout proof for it. `EvmHost.sol` — the contract holding the actual funds and paying them out — does not perform or rely on any such check itself; it treats `_requestCommitments[commitment]` as authoritative and pays whatever is stored there, with no `_responseReceipts` cross-check in `dispatchTimeOut`.

### Impact Explanation
If a GET request's fee can be paid out twice — once as a relayer reward on response delivery, once again as a "refund" on a subsequently accepted timeout — this is a direct double-payment/loss-of-funds bug from the host's fee-token balance, falling squarely under the bounty's "double-claim/double-settlement" and "stealing or loss of funds" categories. The `feeToken()` balance held by `EvmHost` for relayer incentives is drained by an extra, unauthorized payout for a request that was already fully settled.

### Likelihood Explanation
The precondition is that the module responsible for admitting timeout proofs (`HandlerV2`/pallet-ismp verification) does not itself gate on `_responseReceipts[commitment]` before accepting a `GetRequestTimeout` proof for a commitment that already has a response receipt recorded. I was not able to fully inspect `HandlerV2.sol`'s timeout-acceptance logic before running out of investigation budget, so I cannot conclusively rule out that an equivalent guard exists one layer up. What is fully verifiable from `EvmHost.sol` alone is the code-level fact that the contract's own storage does not enforce mutual exclusivity between the two payout paths, unlike the symmetric delete/restore discipline used everywhere else in the same file — this is the same class of defect (uncommitted/uncleared state consumed twice) as the seed report, and it should be fixed regardless of whether an upstream check currently happens to prevent exploitation.

### Recommendation
In `dispatchIncoming(GetResponse memory response, address relayer)`, delete `_requestCommitments[commitment]` immediately after (or as part of) paying the relayer fee, mirroring the delete/restore-on-failure discipline already used in `dispatchTimeOut`:
```solidity
if (fee != 0) {
    delete _requestCommitments[commitment];
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
```
This ensures the fee-metadata entry cannot be read/paid again by any later code path, closing the gap regardless of what upstream proof-acceptance logic does.

### Proof of Concept
Concrete PoC requires confirming whether `HandlerV2`/pallet-ismp will admit a timeout proof for a commitment that already has a `_responseReceipts` entry — I could not complete this verification within the available tool budget. The verifiable, code-level defect is the asymmetry shown above: `_requestCommitments[commitment]` is populated at dispatch time (`evm/src/core/EvmHost.sol` `dispatch()` line 948), consumed and left un-cleared on the response-success path (lines 841-846), and independently consumed again on the timeout path (lines 861-877) with no cross-check against `_responseReceipts`.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
