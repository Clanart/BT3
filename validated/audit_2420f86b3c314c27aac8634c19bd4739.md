[1](#0-0) ### Title
Invalid-PoP DKG message can extract another participant's encrypted share through blame proof disclosure - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`EncryptedMessage::read` accepts attacker-controlled encryption key, proof-of-possession, and ciphertext bytes. [2](#0-1)  During `calculate_share`, the implementation queues PoP verification but still decrypts the message and constructs an `EncryptionKeyProof` before the batch result is checked. [3](#0-2)  If the decrypted share is non-canonical, `calculate_share` returns early with that proof attached, bypassing the queued PoP check entirely. [4](#0-3) 

### Finding Description
The code explicitly recognizes that an attacker who reuses another message's encryption key could induce the recipient to reveal the ECDH shared key through blame handling. [5](#0-4)  The PoP is intended to prevent that attack, but `decrypt` only queues it into a batch verifier rather than synchronously verifying it. [6](#0-5) 

It then computes the ECDH shared point, decrypts the supplied ciphertext, and returns an `EncryptionKeyProof` containing the shared point and a DLEq proof. [7](#0-6)  `calculate_share` checks whether the decrypted bytes are a canonical scalar before calling `batch.verify_with_vartime_blame`; on failure, it returns `InvalidShare` with `blame: Some(blame)` even when the queued PoP would have failed. [8](#0-7) 

Because `EncryptionKeyProof` serializes the ECDH shared point, an attacker receiving the blame can derive the same ChaCha20 stream as the recipient. [9](#0-8)  The cipher derivation uses only the public DKG context, that shared point, and a fixed IV. [10](#0-9) 

### Impact Explanation
A malicious DKG participant can copy the public ephemeral key from another participant's encrypted share to the victim, submit a forged `EncryptedMessage` reusing that key with an invalid PoP and ciphertext chosen to decrypt to a non-canonical scalar, and receive a blame proof revealing the ECDH shared key. [4](#0-3) 

That shared key decrypts the original victim-directed ciphertext, disclosing another participant's secret DKG share. [7](#0-6)  This is concrete key-share recovery and violates the encryption layer's stated protection against revealing `bX` for an observed message. [5](#0-4) 

### Likelihood Explanation
The attacker needs the ability to supply one share message to a target `calculate_share` call and observe or submit the resulting blame, which is consistent with the library's authenticated-participant protocol model. [11](#0-10)  Processor error propagation serializes and reports the returned blame, making the proof externally observable when invalid shares are reported. [12](#0-11) 

For scalar fields whose modulus is substantially below the encoding space, such as the Ristretto scalar field, random forged ciphertext has a high probability of decoding to a non-canonical scalar; failed attempts merely cause the normal invalid-message path. [13](#0-12) 

### Recommendation
Do not expose an `EncryptionKeyProof` until the corresponding PoP has been successfully verified. [3](#0-2) 

The decryption flow should separate ECDH-key derivation from proof release: first verify the message PoP, then only return or publish the blame proof after that verification succeeds. Alternatively, make the non-canonical-share error return `blame: None` unless a PoP-only verification has already succeeded. [14](#0-13) 

Add a regression test that copies a legitimate message's `key`, supplies an invalid PoP and ciphertext decrypting to a non-canonical scalar, and asserts that no serialized `EncryptionKeyProof` is returned. [2](#0-1) 

### Proof of Concept
Conceptually, for a Ristretto DKG with public context `context`:

1. Observe a victim share message `victim_msg` sent to participant `bob`.
2. Extract its serialized ephemeral-key encoding `K` from the beginning of `victim_msg.serialize()`.
3. Build attacker bytes with layout `K || fake_R || fake_s || forged_ciphertext`, matching `EncryptedMessage::read`. [2](#0-1) 
4. Use any canonical point for `fake_R`, zero for `fake_s`, and random bytes for `forged_ciphertext`.
5. Submit it as the attacker's share to Bob's `KeyMachine::calculate_share`.
6. When the forged plaintext is non-canonical, Bob returns `PedPoPError::InvalidShare` containing `EncryptionKeyProof`, despite the invalid PoP. [4](#0-3) 
7. Deserialize the proof, extract its first encoded point as the ECDH shared point, reproduce `cipher(context, shared_point)`, and decrypt the ciphertext portion of `victim_msg` to recover the victim's scalar share. [10](#0-9)

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
