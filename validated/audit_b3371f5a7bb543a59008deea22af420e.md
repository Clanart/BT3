## Title
Global mutable `challengePeriod`/`ChallengePeriod` retroactively shortens the veto window for already-pending state commitments, allowing premature action on unvetted/fraudulent state - (File: `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol`, `modules/pallets/ismp/src/host.rs`, `modules/ismp/core/src/handlers.rs`)

### Summary
The Nouns report's core broken invariant is: a value treated as a permanent, "final" safety boundary (`GRACE_PERIOD`) is actually a mutable global parameter, and updating it retroactively changes the effective state of *already-existing* entries, allowing an unprivileged actor to act on an entry that should still be blocked. Hyperbridge has the same broken invariant in its challenge-period design: the `challengePeriod` used to gate processing of requests/responses/timeouts is looked up dynamically at call time (`host.challengePeriod()` on EVM, `host.challenge_period(state_machine)` on Substrate), not the period that was in force when the specific `StateMachineHeight` was first committed. Since `challengePeriod`/`ChallengePeriod` can be lowered via governance (`updateHostParams` on EVM, `update_consensus_state` extrinsic on Substrate), a state commitment stored under a long challenge period (fisherman veto window) becomes immediately actionable by any permissionless caller the instant the parameter is reduced — even though the original veto window it was submitted under has not elapsed.

### Finding Description
On EVM, `HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` all gate execution with:
```solidity
uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
``` [1](#0-0) [2](#0-1) 

`stateMachineCommitmentUpdateTime` is fixed once at the time the state commitment for that height was stored, but `challengePeriod` is re-read as the *current* global host parameter on every call, not the value that was configured when that specific commitment was accepted. `challengePeriod` is a single mutable field in `HostParams`, updatable via `updateHostParamsInternal`, which is reachable only through `_hostParams.hostManager` (a cross-chain-governance-controlled `IApp`) — this is a normal, in-scope, expected protocol operation, not an attacker/admin key compromise: [3](#0-2) [4](#0-3) 

The equivalent Substrate path shows the identical pattern: `challenge_period` is looked up by `StateMachineId` via `verify_delay_passed`/`validate_state_machine`, and is compared against a fixed `state_machine_update_time`: [5](#0-4) 

It can be changed at any time for an already-active consensus client/state machine via `update_consensus_state` (`T::AdminOrigin`), which stores directly into `ChallengePeriod::<T>` without any per-height snapshot: [6](#0-5) [7](#0-6) 

Because the check only ever consults the *live* `challengePeriod` value, reducing it (a legitimate, rare governance action — precisely analogous to the Nouns `GRACE_PERIOD` upgrade) instantly reduces the effective challenge/veto window for every state commitment already stored and awaiting its original longer window, not just future ones. There is no field recording "the challenge period in effect when this height was committed," which is the exact structural gap the Nouns report calls out for `proposal.eta + GRACE_PERIOD()` versus a fixed `proposal.exp`.

### Impact Explanation
The challenge period exists specifically so fishermen/watchers have a guaranteed window to detect and veto a fraudulent or erroneous state commitment before it can be relied upon to dispatch requests/responses or process timeouts (false-state-acceptance protection). If governance reduces `challengePeriod`/`ChallengePeriod` while a state commitment is still pending inside its originally-intended (longer) veto window, any unprivileged caller can immediately invoke `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts` (all public, permissionless entrypoints) against that commitment before it has actually been vetted for the duration users and fishermen expected. This can let a not-yet-finalized (and potentially fraudulent) state root be trusted to dispatch messages or clear timeout/request receipts — directly matching the "false proof/state acceptance" and "unauthorized execution" impact categories, since messages that should still be blocked pending review become executable.

### Likelihood Explanation
Low-but-plausible, matching the medium-severity classification the judges converged on for the original Nouns finding: the trigger (a challenge-period reduction) is a legitimate, in-scope governance/host-management action rather than a compromised key or malicious relayer, and once it occurs the exploitation step (calling the permissionless handler functions) requires no special privilege at all — it is a pure protocol-logic gap, not a peer/relayer/prover assumption violation.

### Recommendation
Snapshot the challenge period that was in effect at the moment a `StateMachineHeight`'s commitment is stored (analogous to the Nouns fix of storing `proposal.exp = eta + GRACE_PERIOD()` instead of recomputing it against the live `GRACE_PERIOD()`), and use that stored, per-height value in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`, and `verify_delay_passed`, instead of re-reading the live global `challengePeriod`/`ChallengePeriod`. Alternatively, enforce a rule that challenge-period reductions apply only to state commitments submitted after the update takes effect.

### Proof of Concept
1. Governance is configured with `challengePeriod = 7 days` on `EvmHost`.
2. Hyperbridge (source chain) commits `StateMachineHeight(h)` to `EvmHost`; `stateMachineCommitmentUpdateTime(h)` is set to `T0`.
3. Before `T0 + 7 days`, no one can call `handlePostRequests`/`handlePostRequestTimeouts` for height `h`, per `evm/src/core/HandlerV2.sol` lines 181-185/258-260, because `challengePeriod > delay`.
4. At `T0 + 1 day`, cross-chain governance legitimately lowers `challengePeriod` to `0` (or `1 hour`) via a `PostRequest` processed by `HostManager.onAccept` → `EvmHost.updateHostParams` (`evm/src/core/EvmHost.sol` lines 573-645), which the test `evm/tests/rust/src/tests/host_manager.rs` lines 174-215 confirms is an accepted, functioning flow for updating `challengePeriod`.
5. Immediately afterward (still only `T0 + 1 day`, well inside the originally-promised 7-day veto window), any unprivileged address calls `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` for height `h`; the check `challengePeriod != 0 && challengePeriod > delay` now passes trivially, and the requests/timeouts tied to that still-unvetted state commitment are dispatched — 6 days earlier than fishermen were guaranteed to have to detect and veto fraud.         uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

/// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}
