### Title
Outputs received that can never fund their own spend are accepted as spendable, permanently stranding deposited funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The external report's bug class is "the interface accepts value transfers the design does not support, so accidentally/incorrectly sent funds become irretrievable." The Serai analog lives in the Bitcoin wallet scanner/transaction builder: `Scanner::scan_transaction` reports *any* output paying to a registered script as a `ReceivedOutput`, and `SignableTransaction::new` never verifies that an input's value can even pay for its own spend. Any party can send a small-but-above-dust P2TR output to the deposit address (or an offset-derived script, whose offsets are public `hash_to_F` values), producing a `ReceivedOutput` that is permanently unspendable — the funds are stuck exactly like ETH sent to a non-payable-intended resolver.

### Finding Description
`Scanner::scan_transaction` pushes every output whose `script_pubkey` matches a registered script into the result set with no economic filter (networks/bitcoin/src/wallet/mod.rs:199-213):

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), outpoint: ... });
}
```

`register_offset` derives scripts from `key + G*offset`, and the standard offsets used downstream are deterministic (`Secp256k1::hash_to_F(KEY_DST, b"branch"/"change"/"forward")`), so an unprivileged sender can craft a payment to them. `SignableTransaction::new` then treats all supplied `inputs` as spendable, summing `input.output.value` and only erroring with `NotEnoughFunds` for the *aggregate* (networks/bitcoin/src/wallet/send.rs:175, 223-235). There is no check that an individual input is worth more than the ~68 vbytes of signature/witness weight it adds; an input worth less than its marginal fee contribution can never be included in a viable transaction. A `ReceivedOutput` below that threshold is therefore reported as received while being economically unspendable — permanently stuck, mirroring ETH locked in a resolver that cannot refund it.

The `multisig` offset/script check (send.rs:277) prevents *mismatched-key* signing but does nothing about uneconomic inputs.

### Impact Explanation
Deposited BTC is credited as a received output yet can never be moved: including the input in a transaction always fails `NotEnoughFunds`/raises the fee above its value, and there is no refund path. This permanently strands user funds and inflates the wallet's reported spendable balance. Severity: **Medium** (loss of funds for the depositor, no recovery path, reachable by any external party sending to a known script).

### Likelihood Explanation
Any Bitcoin user can send to the external address or to offset-derived scripts. Accidental small deposits, dust-limit confusion, or deliberate griefing all trigger it; the cost to an attacker is only the value of the stuck output itself.

### Recommendation
Reject or flag `ReceivedOutput`s whose value cannot cover the marginal fee of spending them. Concretely: in `Scanner::scan_transaction` (or at `ReceivedOutput` ingestion), drop outputs with `output.value` below `fee_estimate * marginal_input_vbytes`, and in `SignableTransaction::new` return an error/ignore inputs where `input.output.value` is less than the fee attributable to that input — the wallet-side equivalent of the `notPayable` fix.

### Proof of Concept
```rust
// Any external party computes the deposit script (offset = 0) or a public
// hash_to_F-derived offset script and broadcasts a tx paying it `DUST` sats.
let mut scanner = Scanner::new(group_key).unwrap();

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

          offset: *offset,
          output: output.clone(),

    }
