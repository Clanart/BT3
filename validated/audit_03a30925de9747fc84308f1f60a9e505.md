### Title
Fee calculated on a transaction missing the OP_RETURN output, causing underpaid/under-estimated fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to computing a fee on a quantity that does not reflect the actual assets involved (in the report: fee on total balance rather than the newly received delta), `SignableTransaction::new` computes `needed_fee` and the change amount from a weight estimate built on `payments` alone, while the caller-supplied `data` OP_RETURN output — up to 80 bytes plus output overhead — is added to the real transaction but excluded from the weight/vbytes used for pricing.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` before the weight is measured, but `calculate_weight_vbytes` is invoked with only `payments` (and later `payments` + `change`), never with the data output:

- `tx_outs.push(TxOut { value: ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` at `networks/bitcoin/src/wallet/send.rs:194-202`
- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` at line 204, and the change branch at lines 224-235 recomputes with `Some(&change)` — both exclude the OP_RETURN output already appended.

Consequences:
1. `needed_fee = fee_per_vbyte * vbytes` uses a vbytes that omits ~11–93 vbytes (output base + pushdata + up to 80-byte payload).
2. The minimum-relay-fee check (`TooLowFee`, lines 206-213) is evaluated against the underestimated vbytes, so a transaction whose *actual* fee rate is below the relay minimum can pass.
3. The change output value (`input_sat - payment_sat - fee_with_change`) is therefore over-allocated by the missing fee — the analog of over-allocating value because the calculation used the wrong quantity. The on-chain transaction ends up paying `needed_fee` while being physically larger, i.e., a lower effective sat/vbyte than the caller requested.

The `data` parameter is public caller input to `SignableTransaction::new`, so this is reachable purely through public transaction data.

### Impact Explanation
The wallet produces a signed transaction whose real fee rate is lower than the requested `fee_per_vbyte`, and potentially below `DEFAULT_MIN_RELAY_TX_FEE` for its true vsize, making it unbroadcastable / stuck in mempool limbo. The change output is also inflated (over-allocated) relative to what the intended fee policy dictates, skewing all downstream accounting that trusts `needed_fee`/`fee()` (e.g., `SignableTransaction::fee()` at lines 138-141 reports the true paid fee only after the fact). Medium: distorted fee/change math and potentially unspendable-in-practice change, but funds are not burned — inputs remain unspent if the tx never confirms.

### Likelihood Explanation
Triggers whenever `SignableTransaction::new` is called with a non-`None` `data` argument and any `fee_per_vbyte`. Whether the tx falls below relay minimum depends on the margin between the requested rate and the minimum; the underestimation itself (wrong `needed_fee` and oversized change) occurs deterministically on every call with `data`.

### Recommendation
Include the OP_RETURN output in the weight estimation: pass the fully constructed output set (payments + OP_RETURN + optional change) into `calculate_weight_vbytes`, or add the serialized size of the data output to the weight/vbytes before computing `needed_fee`, the `TooLowFee` check, and the change value.

### Proof of Concept
```rust
// networks/bitcoin context
let inputs = vec![received_output];            // one scanned ReceivedOutput
let payments = vec![(dest_script, 10_000)];
let data = vec![0u8; 80];                      // max allowed OP_RETURN payload

let tx = SignableTransaction::new(inputs, &payments, None, Some(data), fee_per_vbyte).unwrap();

// needed_fee was priced from payments-only vbytes
let priced_vbytes = tx.needed_fee() / fee_per_vbyte;
// actual vsize includes the ~91-byte OP_RETURN output
let actual_vsize = tx.transaction().vsize() as u64;
assert!(actual_vsize > priced_vbytes);          // effective sat/vb < fee_per_vbyte
// With fee_per_vbyte near the relay minimum, the real fee rate drops below
// DEFAULT_MIN_RELAY_TX_FEE yet TooLowFee was not raised.
```
