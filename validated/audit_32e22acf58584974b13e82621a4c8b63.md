### Title
Non-removable reward token whose transfer reverts permanently DoSes `getReward` for all reward tokens - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`rewardTokens` in `rewards/BaseRewardPoolV2.sol` can only grow (pushed to in the constructor and in `queueNewRewards()`), with no admin or unprivileged function to remove an entry [1](#0-0) . `getReward()` and `_updateFor()` iterate the full `rewardTokens` array in a single loop with no try/catch, so if `_sendReward()` reverts for any one token (e.g., because the pool's balance of that token is insufficient, or the token itself blocks transfers), the whole call reverts and no staker can claim any reward token via `getReward` again [2](#0-1) [3](#0-2) .

### Finding Description
`queueNewRewards()` pushes any new reward token into `rewardTokens` and marks `isRewardToken[_rewardToken] = true` permanently — there is no counterpart function to unset this or remove the token from the array [1](#0-0) . `_provisionReward()` performs `safeTransferFrom` for the requested `_amountReward` and then unconditionally credits the *full requested amount* into `historicalRewards` / `queuedRewards` / `rewardPerTokenStored`, without checking the actual balance received [4](#0-3) . If the reward token charges a transfer fee (fee-on-transfer / deflationary token), the pool's real balance of that token will be less than what the accounting believes was distributed. Consequently, when a legitimate staker's `_earned()`-computed reward for that token is later paid out via `_sendReward()`'s `safeTransfer`, the pool can lack sufficient balance and the transfer reverts.

Because `getReward()` loops over `rewardTokens` in one transaction with no isolation (no try/catch, no skip-on-failure), a single reverting reward token blocks settlement of every other, healthy reward token in the same call [5](#0-4) . Since the affected token can never be removed from `rewardTokens`, this is a permanent condition: `getReward(address _account, address _receiver)` (and by extension `MasterMagpie.multiclaim`, which is `onlyMasterMagpie`-gated and invoked by any staker) will revert forever for every account that has a nonzero pending balance in the broken token, freezing all unclaimed rewards (including from unaffected tokens) indefinitely.

No existing modifier (`onlyMasterMagpie`, `updateReward`) prevents this — they only gate *who* can call the function and update accounting state, they do not isolate per-token transfer failures.

### Impact Explanation
This is a High-severity **permanent freezing of unclaimed yield**: once one reward token in the pool becomes fee-on-transfer/deflationary (or otherwise reverts on transfer, e.g. blacklist-capable token), all stakers of that pool lose the ability to claim *any* reward token through `getReward`, since the array cannot be pruned and the loop is all-or-nothing. This matches the target's "one misbehaving reward token must not be able to block settlement of the remaining reward tokens" invariant, which is violated.

### Likelihood Explanation
The precondition (a fee-on-transfer/deflationary reward token being added to the pool) requires that such a token was queued via `queueNewRewards()`, which is only callable by `onlyManager` (a privileged role: `managers[_rewardManager]`). The unprivileged attacker cannot add an arbitrary malicious reward token themselves — they can only trigger the eventual claim through `getReward`/`MasterMagpie.multiclaim` once the pool already holds such a token. This makes the finding conditioned on a manager having queued a defective/fee-charging token (a governance/config precondition), not something purely triggerable by an unprivileged attacker end-to-end. The array-growth/no-removal design flaw itself is real and unprivileged-callable claim reverts are real, but the root cause requires manager action to introduce the bad token in the first place, which the rules for this audit exclude ("misconfiguration-only paths").

### Recommendation
- Track actual received balance in `_provisionReward()` (`balanceBefore`/`balanceAfter` delta) rather than trusting `_amountReward`, to avoid overstating `rewardPerTokenStored` for fee-on-transfer tokens.
- Wrap each `_sendReward()` call in `getReward()`/`getRewards()` in a try/catch (or low-level call) so a single failing token does not block distribution of the others.
- Add a manager/owner-gated mechanism to deactivate (`isRewardToken[token] = false`) and skip a known-broken token in the iteration, or swap-and-pop it out of `rewardTokens` once its balance is fully settled.

### Proof of Concept
Hardhat test plan:
1. Deploy `BaseRewardPoolV2` with a staking token and MasterMagpie mock.
2. Deploy a fee-on-transfer ERC20 mock (`FeeToken`) that takes e.g. 5% on `transfer`/`transferFrom`.
3. As `manager`, call `queueNewRewards(1000e18, FeeToken)` — pool believes it received 1000e18 but actually holds 950e18.
4. Have two stakers accrue rewards in `FeeToken` such that cumulative `userRewards` claims exceed 950e18 pool balance.
5. First staker calls `getReward(staker1, staker1)` via MasterMagpie successfully (balance still sufficient).
6. Second staker calls `getReward(staker2, staker2)`; assert this call reverts due to insufficient `FeeToken` balance in `_sendReward`'s `safeTransfer`.
7. Assert that this second staker's claim of *other, healthy* reward tokens (if queued in the same pool) also reverts in the same `getReward` call, proving cross-token blocking.
8. Assert there is no available function to remove `FeeToken` from `rewardTokens`, confirming the condition is permanent for as long as the shortfall persists.

        override
        external
        onlyManager
        returns (bool)
    {
        if (!isRewardToken[_rewardToken]) {
            rewardTokens.push(_rewardToken);
            isRewardToken[_rewardToken] = true;
        }

        _provisionReward(_amountReward, _rewardToken);
        return true;

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
