### Title
Access-scope coverage check treats an empty/unset `scope` as "covers everything," bypassing reauthorization on scope reduction - (File: `lib/shopify_app/access_scopes/user_strategy.rb`)

### Summary
`ShopifyApp::AccessScopes::UserStrategy.covers_scopes?` uses `current_shopify_session.scope.to_a.empty?` as a short-circuit to decide the stored session already covers all scopes required by the app. This mirrors the M-07 pattern of trusting an externally-derived value being empty/zero as proof of a security-favorable state ("last collateral"/"scope already sufficient") instead of verifying the underlying condition directly.

### Finding Description
`covers_scopes?` is defined as: [1](#0-0) 

```ruby
def covers_scopes?(current_shopify_session)
  # NOTE: this not Ruby's `covers?` method, it is defined in ShopifyAPI::Auth::AuthScopes
  current_shopify_session.scope.to_a.empty? || current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
```

This is consumed directly in the session-activation gate of `LoginProtection`: [2](#0-1) 

If `current_shopify_session.scope` is empty (e.g. a legacy stored session that predates the app storing `access_scopes`, or any storage path that leaves the `scope` attribute blank/nil), `covers_scopes?` unconditionally returns `true` — the code assumes an empty scope value means "no restriction, therefore sufficient," exactly like the reported bug assumed a zero `collateralValueCached` meant "vault is empty." In both cases the zero/empty value is used as a proxy for a favorable security state without confirming that the underlying condition (all required scopes actually granted / no collateral left) is true.

The CHANGELOG confirms this "empty scope" state is realistic in practice, since scope persistence for user/online sessions was only recently made automatic: [3](#0-2) 

Sessions stored before this change, or any session record where `scope` was never populated (nil/blank column), will have `scope.to_a.empty?` evaluate to `true`, causing the reauth-on-scope-change protection to be skipped entirely for that session.

### Impact Explanation
When `reauth_on_access_scope_changes` is enabled specifically to force merchants to re-grant scopes after the app's required scope list changes, a session with an empty stored `scope` silently bypasses that protection: `activate_shopify_session` continues to use the existing (potentially now-insufficient) access token instead of clearing the session and redirecting to OAuth for re-consent. This defeats the intended access-scope enforcement and could let a stale/under-scoped token keep being used against the current, expanded scope requirements.

### Likelihood Explanation
This does not require attacker control of any external oracle — it is triggered purely by ordinary data states (legacy sessions, any code path that stores a session without populating `scope`). Any shop/user whose session record has a blank `scope` attribute automatically satisfies `covers_scopes?`, so the condition is plausible and not a contrived edge case, consistent with how the original finding was judged (plausibility of the external value being empty was enough to warrant a valid Medium).

### Recommendation
Do not treat an empty/blank `scope` as automatically satisfying scope coverage. Instead, if `scope` is missing, explicitly treat the session as needing reauthorization (return `false`), or perform an authoritative live check (e.g., query Shopify for the token's current scopes) rather than inferring sufficiency from an empty local field:

```ruby
def covers_scopes?(current_shopify_session)
  return false if current_shopify_session.scope.to_a.empty?

  current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
```

### Proof of Concept
1. Configure `ShopifyApp.configuration.reauth_on_access_scope_changes = true` and set `ShopifyAPI::Context.scope` to require `["read_products", "write_orders"]`.
2. Have (or migrate) a stored user session whose `scope` attribute is empty/nil (e.g., a legacy record created before scope persistence was added, as referenced in the CHANGELOG entry).
3. Make an authenticated request using that session through a controller including `ShopifyApp::LoginProtection`/`activate_shopify_session`.
4. Observe that `covers_scopes?` returns `true` (because `scope.to_a.empty?` is `true`), so `clear_shopify_session`/`redirect_to_login` is never triggered, and the request proceeds using the outdated/under-scoped session — even though the session does not actually possess the currently required scopes.
