### Title
Divergent conflict-marker parsers cause Copilot AI resolutions to be spliced into the wrong conflict block, silently corrupting committed content - (File: `app/src/lib/copilot-conflict-context.ts` / `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The reported VADER bug is a **credited-value vs. actual-value mismatch**: the contract trusts a reported/expected amount instead of re-deriving it from the same authoritative source, and an attacker exploits the gap between the two independent accounting paths. GitHub Desktop's AI conflict-resolution feature has the same structural flaw: the file is scanned for conflict markers **twice**, by **two independently-written parsers** with subtly different failure semantics, and the final on-disk/committed content is assembled using the second parser's block boundaries while validation only checked counts produced by the first parser.

### Finding Description
`buildConflictContext` extracts conflict hunks with `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` and sends only those hunks to the Copilot model: [1](#0-0) 

Note the malformed-hunk handling: if no closing `>>>>>>>` is found, the inner collection `while` loops have already advanced `i` all the way to `lines.length` before the `continue` executes, so the parser silently gives up on the **rest of the file**, potentially never surfacing later, well-formed conflict blocks: [2](#0-1) 

`validateResolutionPaths` only checks that the model returned the *same count* of hunks as `expectedHunkCounts` (derived from `extractConflictHunks`) - it never checks which specific marker block each hunk corresponds to: [3](#0-2) 

The actual write path, `reassembleResolvedFile`, re-parses the **same raw file content** from scratch with its own copy of the marker regexes, but with different malformed-block handling: an unterminated/malformed `<<<<<<<` is simply pushed through as ordinary content and scanning resumes at `i+1` - it does **not** consume to EOF: [4](#0-3) 

Because the two parsers can disagree on where "malformed" markers end and normal scanning resumes, they can produce a different ordered list of conflict blocks for the very same file. `reassembleResolutions` feeds `raw.hunks` (validated only by count, produced against `extractConflictHunks`' boundaries) into `reassembleResolvedFile`, which splices them by position (`hunkIndex`) into blocks it detects independently: [5](#0-4) 

The result: resolution text the model generated for "conflict K" (based on content from `extractConflictHunks`) can be spliced into a different, unrelated conflict block that `reassembleResolvedFile` labels as its K‑th block. No validation catches this because count matching is the only cross-check performed.

### Impact Explanation
This is a **silent corruption of what the user commits or pushes** - exactly the impact class described in the fee-on-transfer analog (credited amount ≠ actual amount transferred). The user sees Copilot's `reasoning`/`summary` describing an apparently sensible merge decision, but the file actually written to disk (and subsequently staged/committed via the multi-commit-operation conflict flow) can contain code from the wrong side of an unrelated conflict hunk spliced in, or an incorrect resolution silently applied to the wrong region of a file. Since the write path performs no post-hoc semantic verification that the reassembled file matches what the model reasoned about, this can introduce logic errors, reintroduce vulnerable code, or drop the user's own changes without any error being surfaced - and the corrupted result is what gets committed and pushed to the remote.

### Likelihood Explanation
Triggering this requires only that a repository (attacker-controlled branch/PR merged, rebased, or cherry-picked by the victim) contains a file whose "ours"/"theirs" side legitimately includes a line that begins with 7 `<` characters (or another malformed/incomplete marker sequence) ahead of one or more real conflict blocks - fully achievable by any contributor who can get such content into either side of the merge, with no local access, admin rights, or social engineering required. The victim only needs to use GitHub Desktop's Copilot-assisted conflict-resolution feature on the resulting conflict, which is a normal, expected workflow action.

### Recommendation
Use a single, shared parsing function for both context extraction (`extractConflictHunks`) and reassembly (`reassembleResolvedFile`) so both stages agree exactly on marker boundaries and malformed-block handling (e.g., have `reassembleResolvedFile` consume the block list produced by `extractConflictHunks` directly, keyed by marker line offsets rather than a name-free `hunkIndex`, instead of re-deriving boundaries independently). Additionally, validate not just hunk *count* but that reassembly consumed exactly the same number of conflict blocks that were sent to the model, and fail closed (skip the file / surface an error) rather than silently splicing on any mismatch.

### Proof of Concept
1. Attacker contributes a file to a branch whose content includes a line consisting of literally `<<<<<<<` followed by ordinary text with no matching `=======`/`>>>>>>>` before end of file, immediately followed later by a legitimate divergent edit region.
2. Victim merges/rebases that branch, producing a real git conflict in that file (git adds real `<<<<<<<`/`=======`/`>>>>>>>` markers around the legitimate divergent edit region, in addition to the attacker's pre-existing stray marker text).
3. Victim invokes GitHub Desktop's Copilot conflict-resolution flow. `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:186-242`) hits the attacker's malformed marker, its collection loop runs to EOF looking for a closing `>>>>>>>`, and it never surfaces the real, well-formed conflict block that follows — so the model is asked to resolve fewer/different hunks than actually exist in the raw file.
4. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:559-596`) re-scans the same raw content but treats the malformed marker as ordinary text and keeps scanning, discovering conflict blocks in a different position/order than what the model resolved.
5. `reassembleResolutions`/`validateResolutionPaths` only check hunk *counts* match, not identity, so the model's resolved content for what it thought was "conflict 1" is spliced by index into whatever block `reassembleResolvedFile` calls block 1 — potentially unrelated real content — and that corrupted file is written to disk and can be committed/pushed without any error being shown.

Note: this analysis is based on static code review of the two parsers; I was not able to execute the code to confirm a concrete divergent line-count example end-to-end, so exact minimal reproduction inputs should be validated experimentally (e.g. with a Devin session) before treating this as fully confirmed.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
