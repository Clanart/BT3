### Title
Silent partial-commit corruption via stale line-index diff selection re-applied to a freshly re-diffed working tree - ([File: app/src/lib/git/apply.ts])

### Summary
When a user stages a *partial* selection of a file's changes (individual lines/hunks), Desktop stores that selection purely as a set of numeric line indices (`DiffSelection`), decoupled from the diff content it was computed against [1](#0-0) . At actual commit time, `applyPatchToIndex` re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and blindly re-applies the old index-based selection to it with no check that the file content/hunk layout is unchanged [2](#0-1) . If the working-directory file is mutated between the moment the user reviewed/selected lines and the moment `_commitIncludedChanges` executes, the line indices silently point to different content, and `formatPatch` builds a patch from stale offsets against the new diff [3](#0-2) .

### Finding Description
The invariant that should hold is: "what the user visually reviewed and selected for inclusion is exactly what gets committed." This mirrors the StakeWise bug class where a state snapshot (share price / oracle) used for a user decision can diverge from the authoritative state by the time the action executes, and the app trusts the stale snapshot.

In Desktop's commit flow:
1. The user opens the Changes view; `getWorkingDirectoryDiff` computes hunks/line offsets and the UI lets the user select specific lines via `DiffSelection`, which only tracks integer line indices with no binding to file content or a hash of the diff it was generated from [4](#0-3) .
2. When the user clicks "Commit," `_commitIncludedChanges` passes the working-directory `WorkingDirectoryFileChange` objects (carrying the old `DiffSelection`) straight into `createCommit` → `stageFiles` → `applyPatchToIndex` [5](#0-4) [6](#0-5) .
3. `applyPatchToIndex` does **not** reuse the diff the user actually looked at — it calls `getWorkingDirectoryDiff` again, fresh, right before staging [7](#0-6) , then hands that fresh diff plus the stale `DiffSelection` to `formatPatch`, which uses `file.selection.isSelected(absoluteIndex)` purely by numeric offset against the new hunk data [8](#0-7) .
4. There is no re-validation step (e.g., diffing against a hash of the reviewed diff, or aborting if the file changed) anywhere between review and staging: `_loadStatus`/`refreshChangesSection` only runs *before* the commit or asynchronously after it, not synchronously gating the staged content against what was shown [9](#0-8) .

This is exploitable by anything that can modify a tracked file in the working directory between "user reviews/selects lines" and "user clicks Commit" — e.g., a build tool/watcher/formatter triggered by opening a cloned repository (task runners, editor auto-format-on-save, a `post-checkout`/`post-merge` hook writing to a tracked file, or any background process the repo's tooling spawns). Because the corrupted line indices are silently reused against new content, the result is **silent corruption of what the user commits/pushes**: lines the user explicitly excluded can be included (or vice versa) without any diff-mismatch warning, and the commit succeeds normally.

### Impact Explanation
This falls squarely in the accepted impact category "silent corruption of what the user commits or pushes." A user reviewing a partial-commit diff believes they are excluding certain lines (e.g., a secret, a debug statement, or an unintended change accidentally introduced by tooling in an attacker-influenced repo). Because the selection is index-based and unverified against the actual content staged, those lines can end up in the commit (and subsequently pushed) without the user noticing, or conversely intended changes can be dropped, undermining commit integrity guarantees the UI implies.

### Likelihood Explanation
The race window is realistic: partial commits with hunk/line selection are a core, commonly used Desktop feature, and it is common for repositories to have file-watchers, formatters-on-save, linters, or hooks (`post-checkout`, `post-merge`) that rewrite tracked files shortly after a checkout/pull — actions well within the attacker's control if they supply the repository content/config. No local/physical access, admin rights, or social engineering beyond normal repository interaction is required; the “attacker” only needs to control repository content/tooling that fires on checkout/fetch, matching the accepted primitive of an attacker-controlled cloned/fetched repository.

### Recommendation
- Bind `DiffSelection` (or the `WorkingDirectoryFileChange`) to an immutable representation of the diff it was computed from (e.g., a hash of the diff text or of `IStatusResult`'s per-file blob/mtime), and re-validate at commit time in `applyPatchToIndex`/`stageFiles` that the freshly-fetched diff matches before applying the stale selection.
- If the file has changed since the selection was captured, refuse to silently reuse line indices — force a UI refresh/re-confirmation of the partial-selection before allowing the commit to proceed.
- Alternatively, capture and cache the diff at selection time and reuse that exact diff (instead of re-fetching) when building the patch, only re-fetching status to detect the mismatch and abort the commit if content diverged.

### Proof of Concept
1. Modify a tracked file (e.g., `secrets.txt`) with two changes: Line A (safe) and Line B (contains a secret).
2. In Desktop, open the partial-commit diff view and select only Line A for inclusion (unselect Line B).
3. Before clicking "Commit," trigger a background write to the same file that reorders/interleaves lines relative to the reviewed diff (e.g., an editor "format on save," a `post-checkout` hook writing into the file, or a build tool the attacker's repo config spawns) so that the line at the same numeric offset previously occupied by "Line A" now contains "Line B" content, without the UI re-diffing before commit.
4. Click "Commit." `applyPatchToIndex` re-diffs the file (now altered) and `formatPatch` applies the old numeric selection (`isSelected(absoluteIndex)`), staging the secret line into the commit even though the user never selected it and the UI showed it as excluded — verifiable by inspecting the resulting commit's diff and confirming it doesn't match what was displayed pre-commit.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

  // If we get into this state we should never have been called in the first
  // place. Someone gave us a faulty diff and/or faulty selection state.
  if (!patch.length) {
    log.debug(`formatPatch: empty path for ${file.path}`)
    throw new Error(`Could not generate a patch, no changes`)
  }

  patch = formatPatchHeaderForFile(file) + patch

  return patch
}
