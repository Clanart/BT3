## Title
Copilot conflict-resolution apply path overwrites current working-directory content with a stale, pre-computed snapshot, silently corrupting what the user commits — ([File: app/src/lib/stores/app-store.ts])

### Summary
`RevenueCounter::attestRevenue` corrupts a monotonic counter because it performs a SET from a value computed at proposal-creation time without checking whether the underlying source of truth (`lastSyncedCumulative`/stable-fee accrual) advanced during the delay window before execution. The Desktop analog is `AppStore._applyCopilotConflictResolutions`: it writes file content that was reassembled from a `rawContent` snapshot captured minutes earlier (during `_resolveConflictsWithCopilot`), and its only staleness guard is a coarse boolean ("is this file still conflicted?"), not a check that the file's actual content still matches what the resolution was computed from. If the working-directory file changes during the async LLM turn — via the user's own edit, an external tool, or another background git operation — while it *remains* in a conflicted state, the stale reassembled content is written verbatim over the current file and staged with `git add`, and none of the intervening changes make it into the commit.

### Finding Description
The Copilot conflict-resolution flow is split into two phases:

1. `AppStore._resolveConflictsWithCopilot` (`app/src/lib/stores/app-store.ts:6505-6633`) reads each conflicted file from disk once via `buildConflictContext`, capturing `rawContent` (`app/src/lib/copilot-conflict-context.ts:429-438`), extracts hunks, and sends them to the model. This can take up to `timeoutMs ?? 600_000` (10 minutes) per chunk, and multiple chunks run for larger conflict sets (`app/src/lib/stores/copilot-store.ts:1246-1285,1437`).
2. The reassembled full-file resolutions (spliced from that original `rawContent`, see `reassembleResolutions`/`reassembleResolvedFile` at `app/src/lib/copilot-conflict-resolution.ts:549-642`) are stored in `multiCommitOperationState.copilotResolutions` and only written to disk later, when the user clicks "Continue Merge" (`app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx:128-141` → `AppStore._applyCopilotConflictResolutions`, `app/src/lib/stores/app-store.ts:7169-7269`).

The only concurrency guard in the apply step is:

```
const onDiskFile = state.changesState.workingDirectory.files.find(
  f => f.path === resolution.path
)
if (
  onDiskFile !== undefined &&
  isConflictedFileStatus(onDiskFile.status) &&
  !hasUnresolvedConflicts(onDiskFile.status)
) {
  continue
}

await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [1](#0-0) 

This only detects the case where the file is *fully* resolved (no more conflict markers at all). It never re-reads or hashes the current on-disk content to confirm it still equals the `rawContent` that `resolvedContent` was spliced from. A file can still satisfy `isConflictedFileStatus && hasUnresolvedConflicts` (i.e., still has `<<<<<<<`/`>>>>>>>` markers somewhere) while its content has otherwise changed — e.g., the user resolved one of several hunks manually in their editor, added new lines, or another process (extension, second merge, `git checkout` on that path) touched the file — during the multi-minute window while Copilot was working or while the result dialog was open. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` then performs a full-file overwrite using content computed against the old snapshot, discarding the user's intervening edits entirely, and the file is immediately staged with `git add` (`app/src/lib/stores/app-store.ts:7262-7268`).

This mirrors the reported bug-class precisely: a value computed against a stale baseline is used to SET current state, and the "has state moved since we captured/predicted it?" check that exists is too coarse (`hasUnresolvedConflicts` boolean vs. the report's `lastSyncedCumulative` check) to prevent the overwrite. Just as `attestRevenue` doesn't compare against `lastSyncedCumulative`, `_applyCopilotConflictResolutions` doesn't compare the just-read `onDiskFile`'s actual content/hash against the `rawContent` the resolution was built from — it only checks a derived status flag that can still be true even after the file's content diverges from the snapshot.

### Impact Explanation
This directly matches the "silent corruption of what the user commits or pushes" impact category. The user's own conflict-resolution edits (potentially made specifically to fix something Copilot got wrong, or to resolve a hunk it left untouched) can be silently discarded and replaced with the stale AI-generated version at the moment the merge/rebase/cherry-pick is finalized and staged — with no warning, since the skip condition only fires when the file is *fully* clean. Because the write happens right before `git add` and the subsequent commit, this can land unreviewed/unintended content in the resulting commit and any push that follows, without the user's later edits ever being visible in git history.

The attacker angle: repository content is attacker-controlled in the standard "malicious PR/branch merge" threat model. A crafted branch that produces many/large/slow-to-resolve conflicts increases the multi-minute window in which the race can occur, and file content in that same window is exactly what a user editing conflicts would naturally touch — so the attacker doesn't need any unnatural steps from the victim, only for them to do normal conflict work while Copilot resolution is in flight or its result dialog is open.

### Likelihood Explanation
Moderate. It requires the user to touch the same conflicted file (or have some other process touch it) between resolution generation and clicking "Continue Merge" — a window that is explicitly long by design (up to 600s per chunk, longer for many files) and explicitly surfaced to the user as an interactive result dialog they can leave open ("The user can navigate to ConfirmAbort while we're awaiting the resolution", `app/src/lib/stores/app-store.ts:7026-7028`). No privileged access or social engineering is needed beyond normal use of the merge conflict resolution feature on an attacker-authored branch.

### Recommendation
Before writing `resolution.resolvedContent`, re-read the file's current on-disk content (or retain the content hash captured in `IFileConflictContext.rawContent`) and compare it against the snapshot the resolution was reassembled from. If it differs, treat the file the same way as the "resolved externally" case — skip the write and surface it for manual resolution — rather than relying solely on the `hasUnresolvedConflicts` status flag. This closes the gap the same way the report's suggested `addRevenue`/reserved-SET pattern does: never SET/overwrite shared state without first confirming the baseline it was derived from is still current.

### Proof of Concept
1. Set up a merge/rebase with multiple conflicted files, at least one containing several conflict hunks in one file (to keep it in "conflicted" status even after partial edits).
2. Trigger "Resolve with Copilot" (`_startCopilotConflictResolution` → `_resolveConflictsWithCopilot`, `app/src/lib/stores/app-store.ts:6912-6968`); this snapshots `rawContent` for each file at request time.
3. While the request is in flight (or after it completes and the result dialog is showing, before clicking "Continue Merge"), manually edit the multi-hunk file in an external editor to resolve one hunk correctly while leaving another hunk's conflict markers in place, so `git status`/`hasUnresolvedConflicts` still reports it as conflicted.
4. Click "Continue Merge", invoking `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7169-7269`). Because the file is still `isConflictedFileStatus && hasUnresolvedConflicts`, the skip check at lines 7250-7256 does not trigger.
5. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` overwrites the file with content reassembled from the pre-edit `rawContent` snapshot, silently discarding the manual edit made in step 3; the file is then `git add`ed and ultimately committed with content the user never approved.   public async _applyCopilotConflictResolutions(
    repository: Repository
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    const { multiCommitOperationState } = state
    if (multiCommitOperationState === null) {
      return
    }

    const { copilotResolutions, step } = multiCommitOperationState
    if (copilotResolutions === null || copilotResolutions.length === 0) {
      return
    }

    // Respect any manual overrides the user chose in the result dialog
    const manualResolutions =
      step.kind === MultiCommitOperationStepKind.ShowCopilotConflicts
        ? step.conflictState.manualResolutions
        : new Map<string, ManualConflictResolution>()

    this.statsStore.increment('copilotConflictResolutionAcceptedCount')
    if (manualResolutions.size > 0) {
      this.statsStore.increment('copilotConflictResolutionWithOverridesCount')
    }

    const pathsToStage: string[] = []

    for (const resolution of copilotResolutions) {
      if (manualResolutions.has(resolution.path)) {
        continue
      }

      // Delete-vs-modify conflicts are resolved by setting a manual
      // resolution (ours/theirs) rather than writing file content.
      // The existing stageManualConflictResolution flow handles the
      // actual git checkout --ours/--theirs and staging at commit time.
      if (resolution.deleteConflictAction !== undefined) {
        const file = state.changesState.workingDirectory.files.find(
          f => f.path === resolution.path
        )
        if (file === undefined) {
          continue
        }
        const deletedSide = getDeletedSideFromStatus(file)
        if (deletedSide === undefined) {
          continue
        }
        // "keep" → choose the non-deleted side, "delete" → choose the deleted side
        const manualChoice =
          resolution.deleteConflictAction === 'keep'
            ? deletedSide === 'ours'
              ? ManualConflictResolution.theirs
              : ManualConflictResolution.ours
            : deletedSide === 'ours'
            ? ManualConflictResolution.ours
            : ManualConflictResolution.theirs
        this._updateManualConflictResolution(
          repository,
          resolution.path,
          manualChoice
        )
        continue
      }

      const absolutePath = await resolveWithin(repository.path, resolution.path)
      if (absolutePath === null) {
        log.warn(
          `Copilot resolution skipped: path outside repository: ${resolution.path}`
        )
        continue
      }

      // If the user resolved this file externally (e.g. in their editor) while
      // the result dialog was open, git status will report it with no remaining
      // conflict markers. Overwriting it with Copilot's stored content would
      // silently clobber their work, so skip it and let their resolution stand.
      // This mirrors how the manual conflicts dialog determines a file is
      // resolved (`hasUnresolvedConflicts`).
      const onDiskFile = state.changesState.workingDirectory.files.find(
        f => f.path === resolution.path
      )
      if (
        onDiskFile !== undefined &&
        isConflictedFileStatus(onDiskFile.status) &&
        !hasUnresolvedConflicts(onDiskFile.status)
      ) {
        continue
      }

      await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
      pathsToStage.push(resolution.path)
    }

    if (pathsToStage.length > 0) {
      await git(
        ['add', '--', ...pathsToStage],
        repository.path,
        'copilotConflictResolution'
      )
    }
  }

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
