### Title
Copilot conflict-resolution write path can silently overwrite a file the user manually resolved, using a stale working-directory snapshot - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated resolved file content to disk when the user clicks "Continue Merge" after a Copilot-assisted conflict resolution. The function is supposed to skip any file the user has *already resolved manually/externally* while the result dialog was open, but the guard only fires when the file is still present in a cached `workingDirectory.files` snapshot **and** reports a conflicted status. If that cached snapshot no longer contains the entry (stale state, or the file was touched/removed by the user or another process between chunk generation and "Continue Merge"), the skip check silently evaluates to "not resolved" and the function overwrites the file with the model's stored `resolvedContent` anyway [1](#0-0) .

### Finding Description
`_startCopilotConflictResolution` explicitly defers file writes: resolutions are only *stored* in `multiCommitOperationState.copilotResolutions`, with the comment "Files are NOT written to disk yet — that happens when the user clicks 'Continue Merge'" [2](#0-1) . This creates a real time window between "Copilot analyzed the conflict" and "content is committed to disk."

When the user actually confirms, `_applyCopilotConflictResolutions` iterates the stored resolutions and, for each one, tries to protect the user's own edits:

```
const onDiskFile = state.changesState.workingDirectory.files.find(
  f => f.path === resolution.path
)
if (
  onDiskFile !== undefined &&
  isConflictedFileStatus(onDiskFile.status) &&
  !hasUnresolvedConflicts(onDiskFile.status)
) {
  continue
}

await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
``` [3](#0-2) 

The guard is written as a positive check ("skip only if we can prove it's resolved"), not a positive re-validation ("write only if we can prove it's still conflicted"). `state` here is `this.repositoryStateCache.get(repository)` captured at the top of the function [4](#0-3)  — it is not a fresh `git status` call. If `onDiskFile` is `undefined` (path missing from the cached working-directory listing, e.g. status hasn't refreshed yet, or the file was deleted/renamed/staged in the interim), the `if` short-circuits to `false` and the function falls straight through to `writeFile`, unconditionally clobbering whatever the user currently has on disk for that path with the model's stored content.

This mirrors the structural flaw in the Kinetiq report: an amount/state is "taken" (buffer decremented / conflict marked as pending-write) at one point in time, a state-changing user action happens in between (cancel withdrawal / manual conflict fix), and the code that later consumes the stored value never re-derives ground truth before acting — it trusts a snapshot instead of live state, so the outcome (locked HYPE / silently overwritten file) doesn't match the user's actual, current intent, and there is no way to detect or reverse it after the fact.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." An attacker who controls the repository content being merged (a crafted branch/PR designed to produce a specific, or even prompt-injected, model resolution) can rely on this gap to have Desktop reintroduce attacker-chosen file content even after the user believed they overrode it (e.g. picked "ours"/"theirs" manually or hand-edited the file), because the write path never re-checks git's live conflict state before writing — it only trusts a cached snapshot for the skip decision.

### Likelihood Explanation
The write only happens for files that were already part of a real, validated conflict (`validateResolutionPaths` restricts model output to the `expectedFiles` set gathered when building the prompt) [5](#0-4) , so this is not an arbitrary-file-write primitive. It requires the specific race where the cached `workingDirectory.files` no longer contains the entry for a path the user just resolved by hand — plausible given the async, multi-step (loading → result dialog → continue) Copilot flow and the comment acknowledging this exact race exists but assuming the cache is always fresh enough for the check to fire correctly ("this mirrors how the manual conflicts dialog determines a file is resolved").

### Recommendation
Re-fetch live `git status` for the affected paths (or at minimum verify presence in a fresh working-directory snapshot) immediately before writing in `_applyCopilotConflictResolutions`, and default to *skipping* the write when the file's on-disk conflict status cannot be positively confirmed, rather than defaulting to write when the cached lookup misses.

### Proof of Concept
1. Attacker crafts a branch that, when merged, produces a conflicted file whose content is designed to steer the Copilot resolution model's output for that path.
2. User starts a merge in Desktop; Copilot conflict resolution runs and shows the `CopilotConflictsDialog`.
3. While the dialog is open, the user manually resolves the conflicted file in an external editor and the app's cached `workingDirectory.files` in `repositoryStateCache` becomes stale relative to disk (e.g., status hasn't been refreshed, or the entry temporarily drops from the list).
4. User clicks "Continue Merge" → `applyCopilotConflictResolutions` → `_applyCopilotConflictResolutions` runs; `onDiskFile` lookup misses, the skip condition at `app-store.ts:7250-7256` is false, and `writeFile` at `app-store.ts:7258` overwrites the user's manual fix with the attacker-influenced `resolvedContent`.
5. The overwritten content is then staged (`git add`) and included in the merge commit without further prompt, corrupting what the user believed they committed.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
