### Title
`ArrayDecoders.skipField` infinite-loop analog to Wireshark's LLTD dissector integer-type bug - Already fixed/regression-tested ([File: java/core/src/main/java/com/google/protobuf/ArrayDecoders.java])

### Summary
The CVE-2018-7326 root cause is: an attacker-controlled length/size field is read into a signed integer type without validating for negative values, and that value is subsequently used to drive a loop (subtracting/advancing) with the wrong sign, so the loop never terminates. The exact same bug shape (an attacker-supplied varint length decoded into a Java `int`, going negative, being fed into a skip loop) is present in the Protobuf Lite parsing path via `ArrayDecoders`, but this checkout already contains an explicit regression test proving the fix is in place.

### Finding Description
`ArrayDecoders.decodeVarint32` decodes an attacker-controlled varint directly into a Java `int` (`registers.int1`), which can legitimately end up negative for a maliciously-crafted 5-byte varint encoding (e.g. `0xFA 0xFF 0xFF 0xFF 0x0F` decodes to `-6`) [1](#0-0) . This is the same "wrong/insufficient integer type for a length field driving a loop" invariant violation as the Wireshark LLTD dissector bug. If that negative "length" were used unchecked to bound a `while` loop that decrements/advances a position counter, the loop could run indefinitely or wrap, exactly analogous to CVE-2018-7326.

The codebase already anticipates and tests for this exact failure mode: `ArrayDecodersTest.testException_skipField_infiniteLoop` constructs a payload `{0x0B, 0x12, 0xFA, 0xFF, 0xFF, 0xFF, 0x0F}` — a start-group tag followed by a length-delimited field whose length varint decodes to `-6` — and asserts (with a `timeout = 1000` ms JUnit guard) that `ArrayDecoders.skipField` throws `InvalidProtocolBufferException` rather than looping forever [2](#0-1) . A companion test `testException_skipField_negativeSize_crafted` uses the identical malicious varint to confirm negative-size detection [3](#0-2) .

Similarly, `decodeLengthPrefixVarint` explicitly checks `if (length < 0) throw InvalidProtocolBufferException.negativeSize();` before using the length for any bound arithmetic [4](#0-3) . In the C++ `EpsCopyInputStream`/`ParseContext` path, `ReadSize` results are similarly checked against `end - ptr` before being used to advance a pointer, and depth/limit tracking uses signed `int depth` decremented with an explicit `if (--depth < 0) return true;` early-exit guard rather than an unbounded loop [5](#0-4) . The Java `CodedInputStream.skipRawBytesSlowPath` also explicitly rejects negative sizes (`if (size < 0) throw InvalidProtocolBufferException.negativeSize();`) before entering any skip loop [6](#0-5) .

### Impact Explanation
If the negative-size check were missing or bypassed, an attacker sending a bounded, malformed Protobuf binary payload through a public `parseFrom`/`mergeFrom` API could cause the parser to enter an infinite (or extremely long) loop, resulting in a denial-of-service (CPU hang) for the consuming application — directly analogous to the Wireshark infinite-loop DoS. However, in this checkout the relevant paths (`ArrayDecoders`, `CodedInputStream`, C++ `parse_context.cc`, upb `reader.c`) all contain explicit negative-size/negative-depth guards and are covered by targeted regression tests with execution timeouts.

### Likelihood Explanation
Low/Not exploitable in this checkout. All identified skip/decode loops that consume attacker-controlled length or depth values (`ArrayDecoders.decodeLengthPrefixVarint`, `CodedInputStream.skipRawBytesSlowPath`, C++ `ParsingEndsInBuffer`/depth counter, upb `_upb_WireReader_SkipGroup` depth-limit check) perform the necessary sign/bounds check before the loop executes [7](#0-6) . The presence of a dedicated `testException_skipField_infiniteLoop` test with a hard timeout strongly suggests this exact bug class was previously identified and fixed upstream, and a regression test was added specifically to prevent reintroduction.

### Recommendation
No code change appears necessary based on current evidence; the negative-size checks and regression tests already guard the transferable invariant from CVE-2018-7326. As a defense-in-depth measure, ensure any new skip/decode helpers added in the future that consume a length or depth value from the wire always validate sign/bounds *before* using the value to drive a loop, and add a timeout-bound test analogous to `testException_skipField_infiniteLoop` for each new code path.
