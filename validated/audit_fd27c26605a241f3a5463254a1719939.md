### Title
Unbounded length-prefixed loop in `SchnorrAggregate::read` enables CPU/memory DoS - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
The external report describes an unbounded loop whose iteration count is controlled by attacker-supplied data (a delegator's unbounded unstaking records). The direct analog in Serai's in-scope code is `SchnorrAggregate::read`, which reads a fully attacker-controlled `u32` count from untrusted bytes and then loops that many times performing elliptic-curve point decompression, with no cap, pagination, or pre-validation. A second loop over the same attacker-controlled length exists in `SchnorrAggregate::verify`, which additionally performs a transcript challenge (`weight`) and a `multiexp_vartime` contribution per element.

### Finding Description
`SchnorrAggregate::read` reads a 4-byte little-endian length and iterates `u32::from_le_bytes(len)` times, pushing the result of `C::read_G(reader)` into a `Vec` ( [1](#0-0) ). The declared count may be up to 2^32 - 1, entirely attacker-chosen. Each iteration performs a non-trivial point decoding (`read_G`), so the parsing cost per aggregate is linear in the attacker's claimed/appended count with no protocol-level bound — unlike other `read` functions in scope (e.g., `Commitments::read`, which is bounded by `params.t()` [2](#0-1) ).

The cost is compounded on the verification path: `verify` iterates `keys_and_challenges` (which must equal `Rs.len()`), calling `weight()` — a digest challenge plus a shift-and-add scalar reconstruction loop — and pushing two multiexp pairs per element ( [3](#0-2) ). So a single untrusted byte string can force arbitrarily expensive CPU work proportional to its embedded length/payload, with no early size check.

### Impact Explanation
An unprivileged party feeding crafted bytes to `SchnorrAggregate::read` / `SchnorrAggregate::verify` can cause CPU exhaustion and memory growth proportional to the attacker-controlled count, stalling or crashing the calling component (a verifier processing aggregate signatures). This is the same denial-of-service bug class as the reported unbounded unstaking loop: loop bound derived from untrusted data, expensive per-iteration work, no limit.

### Likelihood Explanation
Any caller that accepts serialized `SchnorrAggregate`s from untrusted peers and calls `read` then `verify` is exposed. The attacker only needs to supply bytes — no key material, validator status, or collusion required. Cost is bounded by the byte stream length for `read` (it errors at EOF), but `verify`'s per-element work (transcript + multiexp) is paid for whatever number of elements the attacker actually encodes, and no maximum aggregate size is enforced anywhere in the crate.

### Recommendation
Enforce a protocol-level maximum on the aggregate size before looping: reject `len` values exceeding the maximum plausible signer/statement count (or a hard constant) prior to the `read_G` loop, ideally with a checked allocation (`Vec::try_reserve` / `Vec::with_capacity` on a validated bound). If callers legitimately need variable sizes, expose a paginated/chunked verify, mirroring the report's pagination recommendation.

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
