Based on my review of this Cosmos EVM fork, I found a genuine analog to the report's "cross-chain credit exceeds cap → lock" bug class, but manifesting as a **value-duplication** issue rather than a simple lock, in the `x/erc20` IBC middleware's ERC20 auto-conversion path.

### Title
IBC `OnRecvPacket` ERC20 auto-conversion failure overrides a successful ICS20 acknowledgement, causing duplicated spendable value across chains - (File: x/erc20/ibc_middleware.go, x/erc20/keeper/ibc_callbacks.go)

### Summary
The `x/erc20` IBC middleware wraps the standard ICS20 transfer module to automatically convert received Cosmos coins into their ERC20 representation. The wrapper first lets the inner ICS20 `OnRecvPacket` run to completion — which mints/unescrows spendable bank coins to the receiver and returns a **success** acknowledgement — and only afterward attempts an additional ERC20 conversion step. If that secondary conversion step fails (e.g. `MintingEnabled` check or `ConvertCoinNativeERC20` invariant check fails), the middleware discards the already-successful acknowledgement and returns a brand-new **error** acknowledgement instead.

### Finding Description
`IBCMiddleware.OnRecvPacket` calls the underlying ICS20 application first: [1](#0-0) 

The inner `im.Module.OnRecvPacket` call is the real ICS20 transfer logic that mints/unescrows the transferred coin into the receiver's spendable bank balance and returns success. Only after that state change is made does the erc20 keeper's own `OnRecvPacket` attempt to convert the coin to its ERC20 form: [2](#0-1) 

If `MintingEnabled` or `ConvertCoinNativeERC20` fails at this point, an `ErrorAcknowledgement` is returned, replacing the prior success. This is the same underlying invariant class as the reported `L2cmETH._credit` bug — a downstream cap/limit check that reverts after value has effectively already been credited — except that here the credit (the ICS20 mint to the receiver's bank balance) has already been committed by the inner module call before the failing check runs. Cosmos SDK message handling only rolls back state on a Go-level `error` return from the message handler, not on a "logical" error `Acknowledgement` value produced by a nested handler; so the bank credit made by `im.Module.OnRecvPacket` is not automatically undone by the subsequent `ErrorAcknowledgement`.

When the sending chain later processes that `ErrorAcknowledgement`, its standard ICS20 `OnAcknowledgementPacket` refund logic unescrows/returns the original amount back to the original sender. The net effect is that the same value now exists twice: once as a real bank-coin balance credited to the receiver on the destination chain, and once refunded back to the sender on the source chain.

### Impact Explanation
This would constitute unauthorized duplication of spendable user value across an IBC transfer (receiver keeps a credited balance and sender is separately refunded the same amount), which falls under the "Critical unauthorized minting/duplication ... across native balances, EVM balances, ERC20 representations, IBC escrows" impact category.

### Likelihood Explanation
Triggering the ERC20 conversion failure path only requires an IBC relayer to deliver a packet for a registered, but momentarily mint-disabled/invariant-breaking, token pair (e.g. governance temporarily disabling a pair, `IsSendEnabledCoin` toggled off, or the invariant check in `ConvertCoinNativeERC20` failing) after the underlying ICS20 receive has already succeeded — a condition reachable by ordinary unprivileged transaction/packet flow, not requiring a malicious relayer or validator.

### Recommendation
Whether the double-credit actually reaches production state depends on details of the Cosmos SDK/IBC-go message-handling commit semantics for `MsgRecvPacket` (i.e., whether the per-message branch/cache-store commit happens regardless of the final acknowledgement's success flag) — this part of the control flow lives in the `cosmos-sdk`/`ibc-go` dependencies rather than in this repository's own code, and I was not able to verify from the indexed repository content whether the inner ICS20 call's writes are committed independently of the final returned acknowledgement, or whether the whole handler is wrapped in a branch that gets discarded together with an error ack.

Given this uncertainty about the precise commit/rollback boundary (which lives in vendored `ibc-go` code, outside this repo's scope), I cannot confirm with full certainty that this produces the duplicated-balance outcome versus a correctly-atomic revert. If a Devin session with full dependency access is available, the next step would be to trace `ibc-go`'s `Keeper.RecvPacket`/`WriteAcknowledgement` handling to confirm whether state written by `im.Module.OnRecvPacket` before the erc20 middleware's override is committed or discarded when the final acknowledgement is an error.

### Proof of Concept
Not constructed — the finding depends on external (`ibc-go`) commit semantics that require verification beyond what the indexed repository content allows me to confirm.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
