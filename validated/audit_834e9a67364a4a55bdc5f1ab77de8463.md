### Title
Wallet `sign_message_by_address`/`sign_message_by_id` RPC acts as a raw BLS signing oracle over the coin-authorizing secret key - (File: chia/wallet/wallet_rpc_api.py, chia/wallet/util/signing.py)

### Summary
This is a direct analog of the reported bug class: a service signs a message without validating or domain-separating its structure, letting the message be reinterpreted as an authorization for a different, unintended purpose. In `elixir_api.py` the strategy executor blindly signed a server-supplied payload with its private key. In `chia-blockchain`, `WalletRpcApi.sign_message_by_address`/`sign_message_by_id` sign a **caller-supplied, unstructured message** using the wallet's real coin-controlling `synthetic_secret_key`, and expose a signing mode (`BLS_MESSAGE_AUGMENTATION_HEX_INPUT`/`UTF8_INPUT`) that omits any CHIP-0002 prefix or other domain separation.

### Finding Description
`sign_message_by_address` derives the *same* `synthetic_secret_key` used to authorize on-chain spends (via `convert_secret_key_to_synthetic`) and signs the caller's message directly: [3](#0-2) . The actual signing happens in `sign_message`, which for `BLS_MESSAGE_AUGMENTATION_HEX_INPUT`/`UTF8_INPUT` modes computes `AugSchemeMPL.sign(secret_key, hex_message)` over the raw bytes with **no CHIP-0002 prefix, no coin id, and no `AGG_SIG_*` additional data suffix** [2](#0-1) .

This is the same BLS signing primitive and same key material used to authorize `AGG_SIG_UNSAFE`/`AGG_SIG_ME` conditions in real coin spends: [4](#0-3) . In particular, `AGG_SIG_UNSAFE` conditions are signed with `AugSchemeMPL.sign(secret_key, msg)` over the **raw condition message with no suffix at all** — this is precisely why the opcode is named "unsafe": any signature obtained elsewhere over the identical raw bytes is valid for it. The only mitigation in the codebase against `AGG_SIG_UNSAFE` message collisions is a check that rejects `AGG_SIG_UNSAFE` messages that collide with the reserved `AGG_SIG_*_ADDITIONAL_DATA` suffixes [5](#0-4)  — this protects only against cross-opcode replay using the network's reserved suffix constants, not against a message that an attacker fully controls and asks the wallet's RPC to sign via `sign_message_by_address`.

Because the `signing_mode` is caller-selectable and the wallet's CLI/RPC exposes exactly this raw, unstructured mode (`is_hex=True, safe_mode=False`) [1](#0-0) , a malicious dApp/website/local RPC caller can present a user or an automated tool with an "innocuous-looking" hex string to sign that is actually crafted to equal `(pubkey, msg)` needed to satisfy an `AGG_SIG_UNSAFE` condition placed by the attacker inside their own spend bundle. This mirrors the report's exploit path exactly: the signer never validates that the payload has the expected internal structure (a benign message) before signing, so the resulting BLS signature can be repurposed as if it had been produced during a legitimate on-chain authorization flow.

### Impact Explanation
An attacker who can get a target's wallet to sign an attacker-chosen raw message via `sign_message_by_address`/`sign_message_by_id` (with `is_hex=True, safe_mode=False`) obtains a valid `AugSchemeMPL` signature over `(pubkey, msg)` that can be inserted into any spend bundle as satisfaction of an `AGG_SIG_UNSAFE` condition referencing that pubkey and message — independent of any coin, height, or amount binding. Any puzzle or protocol layer that relies on `AGG_SIG_UNSAFE(known_pubkey, msg)` as an authorization gate (offers, custom multisig/authorization puzzles, DID/NFT flows using `AGG_SIG_UNSAFE`) can be forged this way, resulting in unauthorized coin movement or forged authorization signatures without ever touching the target's real coins.

### Likelihood Explanation
Requires social-engineering or a malicious integrating application (dApp/CLI script) to induce the target to sign a specific attacker-chosen hex payload with `safe_mode=False`, and requires a downstream puzzle/consensus consumer that trusts a bare `AGG_SIG_UNSAFE(pubkey, msg)` as sufficient authorization. This is plausible but requires two components to line up (an unsafe-mode signing request plus a suitable `AGG_SIG_UNSAFE`-gated puzzle), so likelihood is moderate rather than trivial.

### Recommendation
- Remove or gate behind explicit, prominent warnings the `BLS_MESSAGE_AUGMENTATION_HEX_INPUT`/`UTF8_INPUT` ("safe_mode=False") signing paths in `sign_message_by_address`/`sign_message_by_id`, since they produce raw, unprefixed BLS signatures indistinguishable from `AGG_SIG_UNSAFE` authorizations.
- Always domain-separate wallet message signing (default to CHIP-0002 prefixed signing, as `safe_mode=True` already does) and disallow arbitrary raw-mode signing from RPC/CLI without strong confirmation.
- Consider deprecating `AGG_SIG_UNSAFE` reliance in any new puzzle designs in favor of `AGG_SIG_ME`/coin-bound opcodes that include coin-specific and domain-specific suffixes.

### Proof of Concept
1. Attacker crafts a spend bundle spending an attacker-controlled coin whose puzzle includes condition `(AGG_SIG_UNSAFE victim_pubkey msg)`.
2. Attacker gets the victim (e.g., through a malicious dApp or script) to call the wallet RPC `sign_message_by_address` (or the `chia wallet sign_message` analog) with `is_hex=True, safe_mode=False` and `message = msg.hex()`, using the victim's address that maps to `victim_pubkey` [3](#0-2) .
3. The RPC returns `AugSchemeMPL.sign(victim_synthetic_secret_key, msg)` [6](#0-5) .
4. Attacker aggregates this signature into their own spend bundle satisfying the `AGG_SIG_UNSAFE(victim_pubkey, msg)` condition and submits it to the mempool, since `AGG_SIG_UNSAFE` verification only checks pubkey/message match, not coin binding [7](#0-6) .

def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )
