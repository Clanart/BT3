### Title
Retroactive application of current-lock-state forfeiture percentage to entire accumulated pending reward balance allows theft of forfeited yield - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
The reported Beefy bug describes a fee parameter (`beefyFeeConfig`) that can be changed and then retroactively applied to pending, unclaimed rewards at the next harvest, unfairly redistributing value. The `vlMGPBaseRewarder` contract exhibits the same bug class through an unprivileged, user-controlled parameter: the "forfeiture percentage" (`getRewardablePercentWAD`), which is derived from the caller's *current* lock/cooldown state and is applied in full to the caller's *entire* accumulated pending reward balance at the moment of claim, not to the portion that accrued under that state.

### Finding Description
`vlMGPBaseRewarder._earned` accumulates a user's pending reward balance (`userRewards[rewardToken][account]`) over time based on `rewardPerToken` deltas, independent of the user's lock composition [1](#0-0) . When the user finally claims via `getReward`/`getRewards`, `_sendReward` computes a forfeiture amount by calling `_calExpireForfeit`, which reads `vlMGP.getRewardablePercentWAD(_account)` **at claim time** and applies that single percentage to the **whole** accumulated `userRewards` balance [2](#0-1) .

`getRewardablePercentWAD` is entirely determined by the user's current lock/unlock composition (`getUserTotalLocked`, `getUserAmountInCoolDown`, and the decaying weight of each cooldown slot) [3](#0-2) . This composition is fully within the ordinary user's control via the permissionless `lock`/`lockFor` and `startUnlock` functions [4](#0-3) .

Because the forfeiture percentage is recomputed fresh at claim time and applied to the entire historical pending balance, a user can manipulate their own lock composition immediately before calling `getReward` to inflate `rewardablePercentWAD` (e.g., by locking additional MGP right before claiming), thereby minimizing forfeiture on rewards that actually accrued earlier while their locked ratio was lower and should have incurred a higher forfeit. This forfeited amount would otherwise be redistributed to other users via `_queueNewRewardsWithoutTransfer`, which increases `rewardPerTokenStored` for all remaining stakers [5](#0-4) . The same pattern exists in the parallel `mWomSV`/`SmartWomConvert` lock system, since `getRewardablePercentWAD` is duplicated there [6](#0-5) .

This mirrors the reported bug class exactly: a mutable state variable (fee config / forfeiture percent) is changed over the accrual period and then retroactively applied in full to previously-accrued-but-unclaimed rewards, rather than being applied only to the reward accrued while that state was in effect.

### Impact Explanation
Users can reduce or evade the forfeiture that is meant to be redistributed to other vlMGP/mWomSV holders, directly stealing yield that should have gone to the pool of remaining stakers. This is a theft of unclaimed yield reachable by any ordinary wallet holding locked MGP, requiring no admin or governance action.

### Likelihood Explanation
The exploit only requires standard, permissionless actions (`lock`, `startUnlock`, `getReward`) available to any vlMGP holder, and the timing (locking more tokens or waiting for a cooldown slot's decay characteristics before claiming) is fully within the attacker's control, making this straightforward and repeatable.

### Recommendation
Track the forfeiture-eligible percentage per accrual period (similar to how `rewardPerTokenStored` is checkpointed) rather than applying a single "current" percentage to the entire lifetime-accumulated pending balance. At minimum, `_updateFor`/`updateRewards` should settle (checkpoint and apply forfeiture immediately) each period's earned rewards using the `rewardablePercentWAD` in effect during that period, instead of deferring the entire forfeiture calculation to claim time using only the final state.

### Proof of Concept
1. User locks a small amount of MGP into `VLMGP`, then over an extended period lets the majority of their locked balance flow into cooldown via `startUnlock` (lowering `getRewardablePercentWAD` for most of that period) while `vlMGPBaseRewarder.rewardPerToken` accrues rewards into `userRewards[rewardToken][user]` via `_updateFor`/`updateRewards` calls (e.g. triggered by other stake/unstake actions) [7](#0-6) .
2. Immediately before calling `getReward`, the user calls `lock`/`lockFor` with a large amount of MGP, sharply raising `fullyInLock` relative to `userTotalVlmgp`, which raises `getRewardablePercentWAD` close to 100% [8](#0-7) .
3. The user then calls `getReward`, so `_sendReward` computes `_calExpireForfeit` using the newly inflated percentage against the entire historical `userRewards` balance, resulting in little or no forfeiture despite most of the reward having accrued while the user's locked ratio was low [2](#0-1) .
4. The amount that should have been forfeited (and redistributed to other stakers via `_queueNewRewardsWithoutTransfer`) is instead claimed directly by the attacker, at the expense of other vlMGP holders.

        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;

    function _earned(address _account, address _rewardToken, uint256 _userVlmgpShare) internal view returns (uint256) {
        return ((_userVlmgpShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**vlMGPDecimal) + userRewards[_rewardToken][_account];
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
