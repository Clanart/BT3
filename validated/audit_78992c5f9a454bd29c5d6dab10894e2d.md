### Title
Manual conflict resolutions silently carried over from an aborted merge/rebase into an unrelated new merge/rebase - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateConflictState` in [1](#0-0)  decides whether to keep the previous `manualResolutions` map (file path → "ours"/"theirs" resolution) based solely on whether the *kind* of the previous and new conflict state match ("merge" vs "merge", "rebase" vs "rebase") — it never checks whether the new conflict is actually a continuation of the same operation. It's the same bug class as the GMX report: a piece of state tied to a prior "position" (here, a prior merge/rebase operation) is not invalidated/cancelled when that operation actually terminates, and later gets silently re-attached to a brand-new operation that happens to share the same "key" (conflict kind), corrupting its outcome.

### Finding Description
`getConflictState` builds the new conflict state using whatever `manualResolutions` map was carried in from the caller: [2](#0-1) . That map is only reset to a fresh empty `Map` when `prevConflictState` is `null` [3](#0-2) . Otherwise the old map is reused verbatim.

The branching logic in `updateConflictState` only compares `kind` (merge vs merge, rebase vs rebase) to decide whether to propagate the previous `manualResolutions`: [4](#0-3) . Inside `performEffectsForMergeStateChange`, the code even detects that the underlying branch changed and comments that "the merge must have been aborted" [5](#0-4)  — but this detection is used only to increment a telemetry counter (`mergeAbortedAfterConflictsCount`), not to clear the stale `manualResolutions`. The function unconditionally returns `newConflictState`, which already embeds the recycled (now obsolete) resolutions.

This mirrors the GMX invariant break exactly: the "order" (manual resolution) tied to a specific "position" (a specific merge/rebase session, identified by `currentBranch`/`currentTip`/`targetBranch`) is not cancelled when that position closes (abort or completion), and instead is silently reattached to a new "position" (a new merge/rebase) that happens to match on a coarser key (just the conflict `kind`), because Desktop only ever samples `git status` periodically via `_loadStatus`/`updateConflictState` rather than tracking operation identity, and there is no explicit "cancel"/reset step analogous to canceling the phantom decrease order.

The project's own tests confirm this is happening in normal operation, not just as an edge case: `preserves manual resolutions between updates in the same merge` shows resolutions surviving even when `currentBranch`/`currentTip` change between polls [6](#0-5) , and similarly for rebase, `preserves manual resolutions when a rebase is detected` carries `manualResolutions` across a change in `targetBranch`/`baseBranchTip`/`originalBranchTip` [7](#0-6) . There is no test asserting resolutions get cleared when the operation actually changes identity (e.g., a different `targetBranch` for rebase, or a merge whose `currentTip` moved because a *different* merge started).

These `manualResolutions` are subsequently consumed by the conflicts UI flow to auto-populate the resolved-files list and drive `git commit`/continuation logic in [8](#0-7)  and [9](#0-8) , meaning a stale resolution for a file path is treated as "the user already chose 'theirs'/'ours' for this file" in the new operation without re-prompting.

### Impact Explanation
If Desktop's status poll happens to skip observing the transient `null` conflict state between when one merge/rebase ends and a new one begins on the same repository (e.g., background app, quick user actions, or automation triggering two operations in rapid succession), a manual resolution the user made for a file path in the *old* operation (e.g., choosing "theirs" for `config.json` while resolving a merge from a benign branch) will be silently reused for a *new, unrelated* merge/rebase that also conflicts on a file at the same path — even though the user never reviewed or approved that resolution for the new operation's actual conflicting content. Because a git remote or a repository's branches are fully attacker-controlled content (the report's valid-impact class explicitly includes "a cloned/fetched repository" or "a git remote"), an attacker who can influence which branches/content a victim merges or rebases against can engineer a same-path conflict to have their attacker-controlled "theirs" content silently accepted into a commit the user did not knowingly stage — a silent corruption of what the user commits and potentially pushes.

### Likelihood Explanation
Likelihood is moderate, not high: it requires the previous conflict operation's state to still be cached in `changesState.conflictState` (i.e., not yet observed as resolved/aborted by a status refresh) at the moment the new conflicting operation is detected, and it requires a same-kind (merge-to-merge or rebase-to-rebase) transition with the same conflicting file path. This can occur naturally when the app polls infrequently, is backgrounded, or the user performs a rapid abort+retry, and is made easier to trigger deliberately for an attacker who controls the branch/remote content that produces the conflicting path names.

### Recommendation
Reset `manualResolutions` to an empty map whenever the new conflict state does not correspond to the *same* logical operation as the previous one — not merely the same `kind`. For merges, compare `currentTip`/`currentBranch` identity (i.e., treat any change as a brand-new merge, not just for stats); for rebases, compare `targetBranch`/`originalBranchTip`/`baseBranchTip`; for cherry-picks, compare the relevant identifying fields. Only propagate `manualResolutions` when these identifying fields are unchanged from the previous poll.

### Proof of Concept
1. In `app/test/unit/stores/updates/update-conflict-state-test.ts`, take the existing test `preserves manual resolutions between updates in the same merge` [6](#0-5) , but change the `status.currentTip` to a wholly unrelated SHA and `currentBranch` to a different branch than `prevState`'s, simulating that the previous merge was aborted and a different merge on a different branch is now conflicted on the same file path.
2. Observe that `updateConflictState` still returns the old `manualResolutions` map (containing `{'foo': ManualConflictResolution.theirs}`) attached to the new merge's conflict state, instead of a fresh empty map.
3. In the app, this flows into `updateMultiCommitOperationConflictsIfFound`/`updateMultiCommitOperationStateAfterManualResolution` in `app-store.ts` [10](#0-9) , which treats `foo` as already resolved to "theirs" for the new (unrelated) merge, letting it be silently included in the commit without the user reviewing the new merge's actual conflicting content for that path.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  if (
    (prevConflictState == null || isRebaseConflictState(prevConflictState)) &&
    (newConflictState == null || isRebaseConflictState(newConflictState))
  ) {
    performEffectsForRebaseStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  private updateMultiCommitOperationStateAfterManualResolution(
    repository: Repository
  ): void {
    const currentState = this.repositoryStateCache.get(repository)

    const { changesState, multiCommitOperationState } = currentState

    if (
      changesState.conflictState === null ||
      multiCommitOperationState === null ||
      (multiCommitOperationState.step.kind !==
        MultiCommitOperationStepKind.ShowConflicts &&
        multiCommitOperationState.step.kind !==
          MultiCommitOperationStepKind.ShowCopilotConflicts)
    ) {
      return
    }
    const { step } = multiCommitOperationState

    const { manualResolutions } = changesState.conflictState
    const conflictState = { ...step.conflictState, manualResolutions }
    this.repositoryStateCache.updateMultiCommitOperationState(
      repository,
      () => ({
        step: { ...step, conflictState },
      })
    )
  }
