### Title
Future-Dated Oracle Timestamps Bypass Staleness Gating in `oracle-timestamp-fresh` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` is meant to reject stale oracle prices, but its handling of the "timestamp is ahead of the chain clock" case silently forces the staleness delta to `u0` instead of rejecting the update. This mirrors the reported bug class of an incorrectly-directed timestamp comparison: instead of requiring the price timestamp to be in the past (or within a bounded staleness window of the past), any timestamp greater than `stacks-block-time` is treated as maximally fresh.

### Finding Description
The freshness gate used by every oracle price resolution is: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

When `ts` (the oracle-reported `publish-time`) is greater than the current `stacks-block-time`, `delta` is forced to `u0` rather than being rejected. `(<= u0 max-staleness)` is always true, so a future-dated timestamp always satisfies the freshness check regardless of how far in the future it claims to be, and regardless of `max-staleness`. This is used directly in the price resolution path: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Because the future timestamp is accepted, it is also written into the `last-update` map as the new "latest known" timestamp for that feed. The monotonic check `(>= ts prev)` then requires all subsequent, correctly-dated price updates for that feed to have a timestamp `>= ` this future value, which they cannot have until real chain time catches up — so the erroneously accepted future price effectively becomes stuck as the "fresh" quote for that feed until `stacks-block-time` passes it.

This is the same bug class as the external report: the code should be validating that the oracle event happened in the past (`ts <= stacks-block-time`, with a correctly computed staleness delta) but instead special-cases the "timestamp is not yet in the past" branch to bypass the check entirely rather than reject it.

### Impact Explanation
`price-resolve`/`oracle-timestamp-fresh` gates every price that market.clar uses for borrow, health-factor, and liquidation calculations via `price-multi-resolve`/`iter-price-multi`. If a feed value with a future `publish-time` is ever ingested (e.g. from clock skew on the Pyth/DIA relayer, or a value crafted to have a future timestamp), that price is accepted as "fresh" unconditionally and then persists as the reference price for the feed until the chain's `stacks-block-time` catches up to it, since later legitimate updates with correct (lower) timestamps fail the `(>= ts prev)` monotonic check. During that window, positions are valued using a stale/incorrect price rather than the real market price, which can let an unhealthy position appear healthy (avoiding liquidation) or a healthy position appear unhealthy (subject to wrongful liquidation) — i.e., a wrong health verdict driven purely by this code's own timestamp-comparison logic, not by third-party oracle data being wrong per se.

### Likelihood Explanation
Triggering this requires only that some accepted oracle write for a feed carries a `publish-time` slightly ahead of the current Stacks block time — a condition that can arise from normal clock drift between the oracle relayer and the chain, and is not blocked by any check in `market.clar` itself (the `oracle-timestamp-fresh` function has no upper bound rejecting future timestamps at all).

### Recommendation
Rewrite `oracle-timestamp-fresh` so a timestamp strictly ahead of `stacks-block-time` is rejected outright (or clamped in a way that does not zero out the staleness delta), e.g.:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This preserves the "not too old" and "monotonic" invariants while removing the branch that lets future-dated timestamps bypass the staleness gate.

### Proof of Concept
1. A price update for feed `ident` is written with `publish-time = stacks-block-time + N` (future).
2. `price-resolve` calls `oracle-timestamp-fresh(ts, prev, max-staleness)`; since `ts > stacks-block-time`, `delta = u0`, so the check passes and the price is accepted, and `last-update` is set to this future `ts`.
3. Any position valuation call in the same or later block uses this accepted price as the current reference price for the asset.
4. Subsequent legitimate updates with real (lower) `publish-time` values fail `(>= ts prev)` and are rejected until real chain time exceeds the previously stored future `ts`, so the stale/incorrect price remains authoritative for borrowing/health/liquidation decisions during that window.
