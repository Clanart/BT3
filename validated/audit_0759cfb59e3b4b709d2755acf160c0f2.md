### Title
Nil-pointer dereference panic in legacy precompile `HandlePrecompileError` when `state.GetDBImpl` returns nil - ([File: precompiles/common/legacy/v610/precompiles.go])

### Summary
Multiple legacy precompile wrapper packages (`v552` through `v610`, plus sibling per-module legacy packages such as `pointer/legacy/v552`, `pointer/legacy/v555`, `bank/legacy/v552`, `bank/legacy/v555`, `distribution/legacy/v552`, `distribution/legacy/v555`, `gov/legacy/v555`, `json/legacy/v552`, `json/legacy/v555`, `oracle/legacy/v555`, `staking/legacy/v555`, `wasmd/legacy/v552`, `wasmd/legacy/v555`, `pointerview/legacy/v555`, `addr/legacy/v555`) call `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)` without checking whether `GetDBImpl` returned `nil`, unlike later versions (`v614+`) which correctly guard with `if sdb := state.GetDBImpl(evm.StateDB); sdb != nil`.

### Finding Description
`Precompile.Prepare` in these legacy files explicitly anticipates that `state.GetDBImpl(evm.StateDB)` can return `nil`: [1](#0-0) 

When that happens, `Prepare` returns the error `"cannot get context from EVM"`. That error propagates back through `Run`/`RunAndCalculateGas`, both of which `defer HandlePrecompileError(err, evm, operation)`: [2](#0-1) 

`HandlePrecompileError` unconditionally dereferences the same nil result: [3](#0-2) 

So the exact condition that `Prepare` was written to detect and handle gracefully (`ctxer == nil`) causes an unguarded nil pointer dereference one call up the stack in the deferred error handler — the same bug class as the kernel CVE, where a cached reference (`page->mapping`) could become nil between the time it was set and the time it was dereferenced, and the fix was to add the missing nil check. Here the "cache" is `evm.StateDB`'s association with a `*state.DBImpl`, and the check exists in one place (`Prepare`) but is missing in the sibling code path (`HandlePrecompileError`). The same unguarded pattern also exists directly in `RunAndCalculateGas` for the affected pointer-precompile legacy versions, e.g. `precompiles/pointer/legacy/v552/pointer.go` and `v555/pointer.go`: [4](#0-3) 

The later, fixed pattern (present from `v614` onward) demonstrates the maintainers recognized and patched this exact class of bug: [5](#0-4) 

### Impact Explanation
These legacy precompile packages are retained specifically to replay/execute historical transactions at their original upgrade height (a common sei-chain pattern of versioned precompile packages for deterministic historical replay). Any code path that re-executes a historical block/transaction with one of these legacy precompile versions — including full-node state sync/replay, `debug_traceTransaction`/`debug_traceBlockByNumber` on the public JSON-RPC surface, or `eth_call`/simulate against a historical height — that manages to trigger a nil `DBImpl` (e.g., a simulation/tracer statedb not wired as `*state.DBImpl`, or any caller invoking the precompile with `evm.StateDB` not implementing the getter path expected by `GetDBImpl`) causes an unrecovered nil pointer dereference panic. Since precompile execution occurs deep inside EVM message handling for a single transaction, this can crash the RPC/full node process handling that request — a crash of a default-configuration RPC node, which is an accepted impact class under the validation criteria.

### Likelihood Explanation
Reaching this exact nil condition requires `evm.StateDB` to not resolve to a `*state.DBImpl` via `GetDBImpl` while executing one of the affected legacy precompile addresses — most plausible via debug/trace or simulation RPC entry points that construct alternate `vm.StateDB` implementations, since `Prepare` for these very versions was explicitly written to detect and return an error for that scenario, showing the maintainers knew it can occur (otherwise the check in `Prepare` would be dead code). This is a public-RPC-reachable, no-privilege-needed trigger, though it depends on which StateDB implementation is wired for the calling context (e.g., tracer/simulation paths), so it is not necessarily reachable on every code path.

### Recommendation
Apply the same fix that was already applied to `v614+`: guard `HandlePrecompileError` (and the inline calls in `RunAndCalculateGas` for the affected pointer/legacy files) with a nil check before calling `SetPrecompileError`, e.g.:
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
	if err != nil {
		if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
			sdb.SetPrecompileError(err)
		}
		metrics.IncrementErrorMetrics(operation, err)
	}
}
```
Apply consistently across all remaining legacy versions still missing the guard: `v552`, `v555`, `v562`, `v575`, `v580`, `v600`, `v605`, `v606`, `v610`, and the sibling per-module legacy packages listed above.

### Proof of Concept
1. Invoke any affected legacy precompile (e.g. the `pointer` precompile at its `v552`/`v555` historical upgrade version, or any of the `common/legacy/v552..v610` wrapped precompiles) from a context where `evm.StateDB` does not resolve to a `*state.DBImpl` via `state.GetDBImpl` (e.g., a tracer/simulation StateDB implementation used by `debug_traceTransaction`/`eth_call` replay at the corresponding historical height).
2. `Prepare` returns `err = errors.New("cannot get context from EVM")` because `ctxer == nil`.
3. The deferred `HandlePrecompileError(err, evm, operation)` in `Run`/`RunAndCalculateGas` executes `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)`, re-evaluating `GetDBImpl` to `nil` and dereferencing it, causing a nil pointer dereference panic that crashes the serving node process for that request.
