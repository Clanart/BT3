Based on my research, I found that the CL (Consensus Liquidity) staking amount is read directly from the `CLPool` contract's live native-token balance at the snapshot block, without any deposit-duration or vesting requirement, similar to how the SNK exploit multiplied a `rewardPerToken` by a manipulable, momentarily-inflated balance.

### Title
Flash-deposit into CLPool inflates staking reward share via un-vested balance snapshot - (File: `kaiax/staking/impl/getter.go`, `kaiax/reward/impl/getter.go`)

### Summary
`StakingInfo.CLStakingAmount` is derived directly from the CLPool contract's KAIA balance at the snapshot block [1](#0-0) , and this amount is added on top of `StakingAmount` to compute each validator's `excess` stake used to proportionally split minting/staking rewards in `assignStakingRewards`/`assignStakingRewardsFlex` [2](#0-1) [3](#0-2) . Because the balance is a point-in-time snapshot with no minimum holding period or vesting, a delegator can deposit into a `PublicDelegation`/CLPool contract right before the snapshot block and withdraw shortly after, capturing a share of that epoch's reward disproportionate to their real economic exposure — the same "balance snapshot manipulation for reward calculation" bug class as the SNK exploit, where the attacker inflated the balance right before the reward-multiplying read.

### Finding Description
The staking module snapshots `StakingInfo` (including `CLStakingAmount`) from the state at `sourceNum = num - 1` (post-Kaia hardfork) [4](#0-3) . The CL staking amount is populated straight from `CLRegistry`/`multiCallDPStakingInfo`, which returns the CLPool's current balance divided by KAIA units [5](#0-4) . This value directly feeds `consolidatedNode.CLStakingInfo.CLStakingAmount`, which is summed with `StakingAmount` to compute `excess` stake and hence each validator/CLPool's proportional cut of the block's staking reward:

```go
amount := cn.StakingAmount
if isPrague && cn.CLStakingInfo != nil {
    amount += cn.CLStakingInfo.CLStakingAmount
}
``` [6](#0-5) 

The `PublicDelegation` contract (the standard CLPool implementation) exposes ERC-4626-style `deposit`/`withdraw`/`requestWithdrawal` functions [7](#0-6) [8](#0-7) . Unlike the SNK case where a parent's `rewardPerToken` was multiplied by the sum of manipulated children balances, here the reward split multiplies the *momentary* CLPool balance by the block's staking reward budget. Nothing in the reward calculation path (`assignStakingRewards`, `assignStakingRewardsFlex`, `consolidatedNode.Split`) accounts for how long the deposit has been held; only the balance at the single snapshot block matters.

### Impact Explanation
An attacker who deposits a large amount into a CLPool immediately before the snapshot block (`num - 1`) is captured as `CLStakingAmount` for the *entire* subsequent staking interval/block of reward calculation, and can withdraw immediately after, extracting a share of validator staking rewards that is disproportionate to genuine economic risk taken (no real lock-up period was honored). This effectively siphons rewards away from legitimate long-term CL depositors and other validators competing for the same `stakersReward` budget, since `totalExcess` and each validator's `excess` share are zero-sum within the block's fixed reward pool [9](#0-8) .

### Likelihood Explanation
This requires only an unprivileged public transaction sender able to call `deposit`/`withdraw` on a public `PublicDelegation` (CLPool) contract — no validator or governance privilege needed. The one-block-prior snapshot rule is public knowledge (documented in `kaiax/staking/README.md`), so an attacker can precisely time a deposit to land in the snapshot block and withdraw right after, repeating every staking interval for continuous extraction.

### Recommendation
Compute `CLStakingAmount` (and `StakingAmount` generally) using a time-weighted or minimum-holding-period balance (e.g., average balance over the staking interval, or require a minimum deposit duration such as delegation withdrawal delay) rather than a single point-in-time balance read at the snapshot block. Alternatively, apply a cooldown before newly deposited CL stake becomes reward-eligible, analogous to typical anti-flash-loan protections in reward-bearing staking pools.

### Proof of Concept
1. Attacker (or colluding validator operator) monitors current block number and determines the staking-info snapshot block for the next reward interval (`sourceNum = num - 1` per the documented rule) [10](#0-9) .
2. Just before `sourceNum` is finalized, attacker calls `PublicDelegation.deposit()` (via the CLPool) with a large KAIA amount, inflating `CLPool.balance`.
3. At `sourceNum`, `getFromState` reads this balance via `multiCallDPStakingInfo` into `CLStakingInfo.CLStakingAmount` [11](#0-10) .
4. During block `num`'s reward finalization, `assignStakingRewards`/`assignStakingRewardsFlex` computes `excess = (StakingAmount + CLStakingAmount) - minStake` and allocates a proportional share of `stakersReward` to the CLPool address via `cn.Split(reward)` [12](#0-11) .
5. Attacker calls `PublicDelegation.withdraw()`/`requestWithdrawal()` immediately after the reward is credited to the CLPool, extracting their disproportionate share and removing their stake before the next snapshot, with no penalty since no lock-up period was enforced by the reward-calculation logic itself.

func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers

			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
