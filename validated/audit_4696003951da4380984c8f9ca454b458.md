### Title
Unsynchronized cross-context caching of `validatedSender`/`validatedFeePayer` identity on the shared `*Transaction` object allows fee-payer/sender identity confusion under concurrent validation - (File: blockchain/types/transaction.go)

### Summary
`blockchain/types/transaction.go` caches the *result* of sender/fee-payer identity validation directly on the shared, pointer-referenced `Transaction` struct (`validatedSender`, `validatedFeePayer`, `validatedGas`), instead of scoping it to a per-call, per-context value. Multiple independent execution contexts (tx-pool admission, block building/worker, re-validation, etc.) can hold and operate on the *same* `*Transaction` pointer concurrently, exactly as CVE-2019-3894 describes a shared, pooled thread that retains a stale `SecurityIdentity` from a prior task and executes a later, unrelated task under the wrong identity. Here, the "thread" is the shared `*Transaction` object and the "SecurityIdentity" is the cached `validatedFeePayer`/`validatedSender` pair.

### Finding Description
`Transaction` stores mutable "validated" identity fields directly on the object: [1](#0-0) 

`ValidateSender` sets `validatedSender` and, as a default, `validatedFeePayer = validatedSender` — but only inside a lock scoped to *this call*: [2](#0-1) [3](#0-2) 

`ValidateFeePayer` is a *separate* critical section that only overwrites `validatedFeePayer` with the real, cryptographically-derived fee payer if it still equals `validatedSender` (i.e., the "default"/unset placeholder value): [4](#0-3) 

`AsMessageWithAccountKeyPicker` calls these two functions sequentially, each taking and releasing `tx.mu` independently, with an unguarded gap between them: [5](#0-4) 

Because `validatedSender`/`validatedFeePayer` live on the shared `*Transaction` object (the same pointer sitting in the tx pool's `all` map, in `pending`, and referenced by the block-building `worker`), any other goroutine that reads `tx.ValidatedFeePayer()` or calls `tx.Execute()` in the window between the `ValidateSender` write and the `ValidateFeePayer` write observes `validatedFeePayer == validatedSender` — the *sender*, not the real, signature-verified fee payer: [6](#0-5) [7](#0-6) 

`Execute()` then attributes both value-transfer accounting and (via the caller) fee accounting using whichever stale/interim identity happened to be cached on the object at read time, i.e. potentially the sender instead of the delegated fee payer.

This exact race class is acknowledged by the codebase's own regression test, which spins up two concurrent `AsMessageWithAccountKeyPicker` calls on the *same* `*Transaction` pointer for a fee-delegated transaction and asserts the fee payer is not corrupted: [8](#0-7) 

and a second test file explicitly documents a race between tx-pool admission and `commitNewWork` (block building) touching shared transaction state concurrently, confirming that the same `*Transaction` pointer is legitimately reachable from more than one concurrent execution context in production code paths (`work/worker.go`'s `commitNewWork`/`ApplyTransactions` vs. `blockchain/tx_pool.go`'s `addTx`/`checkAndAddTxs`): [9](#0-8) [10](#0-9) 

### Impact Explanation
If the interim/default state (`validatedFeePayer == validatedSender`) is observed by the execution path (`tx.Execute()` via `NewAccountRefWithFeePayer(tx.ValidatedSender(), tx.ValidatedFeePayer())`) instead of the correct, delegated fee payer, a fee-delegated transaction can be committed while attributing gas/fee debits to the wrong account:
- The sender could be charged for gas that should have been paid by the fee-delegation counterparty (fee-delegation abuse / unauthorized value movement out of the sender's account), or
- The real fee payer could unexpectedly avoid paying fees it authorized, shifting cost onto the sender or breaking the fee-delegation guarantee that was cryptographically signed for.
Because this depends on non-deterministic goroutine scheduling around a shared mutable object, different validating/executing nodes could reach different fee-attribution results for the identical transaction/block, which is a state-divergence risk between otherwise-honest nodes — a consensus-critical concern, not just a local accounting bug.

### Likelihood Explanation
Exploitability requires the same `*Transaction` pointer to be processed by two logically distinct contexts concurrently (e.g., simultaneous pool re-validation and block building, or repeated re-entrant calls to `AsMessageWithAccountKeyPicker`/`ValidateFeePayer` on the same object as already exercised in `tests/race_test.go`'s `TestRaceAsMessageWithAccountPickerForFeePayer` and `TestRaceBetweenTxpoolAddAndCommitNewWork`). This is not attacker-controlled timing in the classic sense, but any unprivileged user submitting an ordinary fee-delegated transaction (`TxTypeFeeDelegated*`) is enough to put the vulnerable object into circulation; the race window is a property of the node's own internal concurrency, so a sufficiently loaded node (high tx throughput, frequent re-orgs/re-validation) increases the odds of hitting the window without any special crafting of the transaction itself.

### Recommendation
- Do not cache validation results (`validatedSender`, `validatedFeePayer`, `validatedGas`) on the shared `*Transaction` object across independent call contexts. Instead, return them as values from `AsMessageWithAccountKeyPicker` (as already partially done) and require callers to use only the locally-returned values, never re-reading them back off the shared pointer.
- If caching must remain on the object for performance, make the entire `ValidateSender` + `ValidateFeePayer` update sequence atomic under a single lock acquisition (one critical section, not two), so no intermediate "feePayer==sender" state is ever externally observable.
- Add a "generation"/"epoch" or context token so that a concurrently-running validation from a stale block-building context cannot silently write results into a `Transaction` object being read by a newer/different context.

### Proof of Concept
The codebase's own test demonstrates the underlying race condition: [11](#0-10) 
Running many concurrent `tx.AsMessageWithAccountKeyPicker(signer, stateDB, 0)` calls on one shared fee-delegated `*Transaction` and checking `msg.ValidatedFeePayer()` shows the field is subject to a write/write and write/read race stemming from the two-step (`ValidateSender` then `ValidateFeePayer`) locked-but-non-atomic update in `blockchain/types/transaction.go`. A production trigger is any fee-delegated transaction that is concurrently touched by tx-pool admission (`blockchain/tx_pool.go:addTx`) and block building (`work/worker.go:commitNewWork`/`ApplyTransactions`), a scenario the repository already flags as racy in `tests/race_test.go:TestRaceBetweenTxpoolAddAndCommitNewWork`.

func (tx *Transaction) AsMessageWithAccountKeyPicker(s Signer, picker AccountKeyPicker, currentBlockNumber uint64) (*Transaction, error) {
	intrinsicGas, err := tx.IntrinsicGas(currentBlockNumber)
	if err != nil {
		return nil, err
	}

	gasFrom, err := tx.ValidateSender(s, picker, currentBlockNumber)
	if err != nil {
		return nil, ErrSender(err)
	}

	tx.mu.Lock()
	tx.checkNonce = true
	tx.mu.Unlock()

	gasFeePayer := uint64(0)
	if tx.IsFeeDelegatedTransaction() {
		gasFeePayer, err = tx.ValidateFeePayer(s, picker, currentBlockNumber)
		if err != nil {
			return nil, ErrFeePayer(err)
		}
	}

	sigValidationGas := gasFrom + gasFeePayer
	intrinsicGas = intrinsicGas + sigValidationGas

	tx.mu.Lock()
	tx.validatedGas = &ValidatedGas{IntrinsicGas: intrinsicGas, SigValidateGas: sigValidationGas}
	tx.mu.Unlock()

	return tx, err
}

// ValidateFeePayer finds a fee payer from a transaction.
// If the transaction is not a fee-delegated transaction, it returns an error.
func (tx *Transaction) ValidateFeePayer(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	tf, ok := tx.data.(TxInternalDataFeePayer)
	if !ok {
		return 0, errUndefinedTxType
	}

	pubkey, err := SenderFeePayerPubkey(signer, tx)
	if err != nil {
		return 0, err
	}

	feePayer := tf.GetFeePayer()
	accKey := p.GetKey(feePayer)

	gasKey, err := accKey.SigValidationGas(currentBlockNumber, accountkey.RoleFeePayer, len(pubkey))
	if err != nil {
		return 0, err
	}

	if err := accountkey.ValidateAccountKey(currentBlockNumber, feePayer, accKey, pubkey, accountkey.RoleFeePayer); err != nil {
		return 0, ErrInvalidAccountKey
	}

	tx.mu.Lock()
	if tx.validatedFeePayer == tx.validatedSender {
		tx.validatedFeePayer = feePayer
	}
	tx.mu.Unlock()

	return gasKey, nil
}
