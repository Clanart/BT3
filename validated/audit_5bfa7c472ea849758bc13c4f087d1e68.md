Forgery of `SchnorrAggregate` signatures: aggregation weights do not bind the nonces or public keys, letting an attacker solve for a free term — (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs` implements Schnorr half-aggregation per eprint 2021/350, but derives the per-signature weight `z_i` from a transcript that commits only to the caller-supplied challenges — not to the attacker-controlled nonces `R_i` or the public keys being "proven" against. Because the `Rs` (read verbatim from untrusted bytes via `SchnorrAggregate::read` → `C::read_G`, which permits any canonical point including identity) are not bound into the weight derivation, an attacker learns all weights first and then adaptively chooses the `Rs` and `s` to satisfy the single linear verification equation for any `(key, challenge)` list. Any aggregate claiming a victim key signed a challenge it never signed verifies as valid.

This is the direct structural analog of the reference bug class: attacker-supplied content (`Rs`, `s`) is substituted unsanitized/unbound into a trusted framing context (the weight transcript and verification equation) and rendered as a platform-authentic output (an aggregate signature that "proves" arbitrary keys signed arbitrary challenges).

### Finding Description
`SchnorrAggregate::read` deserializes an attacker-controlled length-prefixed list of points `Rs` and a scalar `s` (`crypto/schnorr/src/aggregate.rs:77-88`). `verify` then:

1. Builds `DigestTranscript::<C::H>::new(dst)`, applies `domain_separate(b"signatures")`, and appends only each `challenge` scalar (`aggregate.rs:132-136`).
2. For each entry, computes `z = weight(&mut digest)` and queues `pairs.push((z, self.Rs[i]))` and `pairs.push((z * challenge, *key))` (`aggregate.rs:138-143`).
3. Accepts if `Σ_i z_i·R_i + Σ_i z_i·c_i·A_i − s·G = identity` (`aggregate.rs:144-145`).

`weight` (`aggregate.rs:22-65`) derives `z_i` purely from the transcript state, which contains only `dst`, the `"signatures"` domain, and the ordered challenge scalars. Neither `self.Rs[i]` nor `key` is ever hashed into the digest. Per the half-aggregation paper, the random weights must be unpredictable *and* the prover must commit to all signature components before weights are known; otherwise the linear combination is freely satisfiable. Here, with `n ≥ 2` entries the attacker has `n` free points plus the scalar `s` satisfying one group equation — solve for any one term after computing all `z_i`.

The same defect exists on the producing side: `SchnorrAggregator::aggregate`/`complete` (`aggregate.rs:163-186`) build the identical challenge-only digest, so the weight sequence is fully public and deterministic — no secret or commitment gap prevents pre-computation.

### Impact Explanation
- `SchnorrAggregate` is used by Tendermint commit verification in `coordinator/tributary/src/tendermint/mod.rs` (uses `SchnorrAggregate`/`SchnorrAggregator` for aggregating validator signatures). A party who controls the aggregate bytes (e.g., a block producer submitting an aggregate of validator commits) can fabricate an aggregate claiming honest validators signed commits they never issued — i.e., an unprivileged party with only public inputs produces a forged proof of consensus participation. Within the in-scope rules, this is a forged signature reachable via `SchnorrAggregate::read`/`verify` on untrusted bytes.
- Standalone, the API's contract ("verify that every `(key, challenge)` pair was signed") is violated for any list of length ≥ 2, and even a single entry is forgeable when the attacker already holds any one valid signature (trivial re-weighting: `s' = z·s₀` with `Rs = [sig.R]` passes as an "aggregate" of that pair — a milder malleability but not the core issue).
- Severity: High — universal forgery of aggregate signatures under the stated API contract, computable with a few scalar operations and one modular inversion.

### Likelihood Explanation
Exploitation requires only the public inputs to `verify`: the `dst`, and the `(key, challenge)` pairs the verifier will check — all public (keys are public; challenges are deterministic functions of public data). The attacker calls `SchnorrAggregate::read` on bytes they construct, or supplies `Rs`/`s` through whatever channel feeds `verify`. No knowledge of any discrete log or secret share is needed; the forgery cost is linear algebra over the scalar field. Reachability in production is concrete wherever untrusted aggregate bytes are verified (Tendermint commits), though the crate itself is the vulnerable component regardless of caller.

### Recommendation
Bind all statement components into the weight transcript before any weight is drawn, matching the paper's requirement that the aggregation coefficients be unpredictable to the prover at the time components are committed:

```rust
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
  digest.append_message(b"nonce", self.Rs[i].to_bytes());   // bind attacker-controlled R_i
  digest.append_message(b"public_key", key.to_bytes());      // bind the key being proven
  digest.append_message(b"challenge", challenge.to_repr());
}
```

Apply the identical change to `SchnorrAggregator::new`/`aggregate` so weights on the proving side commit to the same transcript (note: this requires deferring weight derivation — `aggregate` currently computes weights incrementally — or hashing the full `(R, A, c)` list in one pass in `complete`). Additionally, reject identity `R` values in `SchnorrAggregate::read` (as `frost::Curve::read_G` does at `crypto/frost/src/curve/mod.rs:125-131`) to remove the trivial `R = 0` free-variable slot, and consider rejecting `c_i = 0` challenges.

### Proof of Concept
For any `Ciphersuite` `C` (e.g., `Secp256k1`), any `dst`, and any target list of `n ≥ 2` pairs `[(A_1, c_1), …, (A_n, c_n)]` that victim keys never signed:

1. Reproduce the verifier's weight sequence offline:
   ```rust
   let mut digest = DigestTranscript::<C::H>::new(dst);
   digest.domain_separate(b"signatures");
   for (_, c) in &pairs { digest.append_message(b"challenge", c.to_repr()); }
   let z: Vec<C::F> = (0..pairs.len()).map(|_| weight::<_, C::F>(&mut digest)).collect();
   ```
   This is fully computable by the attacker because nothing secret or attacker-committed is hashed.

2. Pick arbitrary `R_1..R_{n-1}` (e.g., generator multiples) and arbitrary `s` (e.g., zero), then solve the last nonce for the single group equation `Σ z_i R_i + Σ z_i c_i A_i = s·G`:
   ```
   R_n = z_n^{-1} · ( s·G − Σ_{i<n} z_i·R_i − Σ_i z_i·c_i·A_i )
   ```
   `z_n` is nonzero with overwhelming probability; the scalar inverse and the right-hand point are all public operations — no discrete log required.

3. Emit `SchnorrAggregate { Rs: [R_1..R_n], s }`, serialize via `write`, and submit. `SchnorrAggregate::read` accepts it (any canonical points pass `C::read_G`), and `verify` computes `multiexp_vartime(pairs).is_identity() == true` by construction — a forged aggregate attesting that each `A_i` signed challenge `c_i`.

Concretely for `n = 2` with victims `(A_1, c_1)`, `(A_2, c_2)`: set `s = 0`, `R_1 = G`, then `R_2 = z_2^{-1}·(−z_1·G − z_1 c_1·A_1 − z_2 c_2·A_2)`. The check `z_1·R_1 + z_1 c_1·A_1 + z_2·R_2 + z_2 c_2·A_2 − s·G = 0` holds identically, and `verify` returns `true` for two signatures that were never produced.

Uncertain aspects: I did not fully trace how tendermint obtains the `(key, challenge)` list and `dst` at verify time, so the exact on-path reachability of a forged aggregate into consensus acceptance (vs. the crate-level API forgery, which is proven above) is not completely confirmed; the crate-level forgery stands on `crypto/schnorr/src/aggregate.rs:77-145` alone, which is in scope.
