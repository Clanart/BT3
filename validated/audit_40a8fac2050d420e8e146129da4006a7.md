### Title
Repository content with fake conflict-marker lines hijacks Copilot conflict resolution and silently corrupts committed code - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The external report's broken invariant is: a value that is supposed to be derived from a well-defined, structurally-verified state (fee-accrual time) is instead computed from a naive formula with no bounds/consistency checks, letting attacker-influenced input (elapsed time) push the result far outside its intended range and corrupt a financial outcome. The Desktop analog is `extractConflictHunks`/`reassembleResolvedFile`, which both derive "what is a conflict" purely from a positional regex scan (`/^<{7}(?:\s|$)/`, `/^={7}$/`, `/^>{7}(?:\s|$)/`) over raw file text, with no cross-check against git's own record of which lines are actually part of a merge conflict. A file whose content (attacker-supplied) happens to contain lines that match these patterns can hijack hunk boundaries, so the AI-generated resolution is spliced into the wrong region of the file.

### Finding Description
`extractConflictHunks` in [1](#0-0)  walks a file's raw text line-by-line and treats any line matching `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` as a real git conflict boundary. It has no way to confirm these lines were actually emitted by git for this merge (e.g. by cross-referencing `git diff --check`/`git ls-files -u` conflict ranges) — it is pure text pattern matching.

`reassembleResolvedFile` in [2](#0-1)  re-parses the same raw file with the identical marker regexes and splices the model's per-hunk `resolvedContent` back in **by ordinal position, not by content identity** — explicitly documented: "matched by order, not by line number" [3](#0-2) .

Because both functions only look for 7-character marker sequences at the start of a line, any file that already contains such sequences as ordinary text (e.g. a Markdown/README documenting Git conflict syntax, a test fixture, generated diff/patch content checked into the repo, or a source string literal aligned to column 0) will be misinterpreted as a second (or shifted) conflict block once a *real* conflict is introduced by a later merge on that same file. This shifts hunk boundaries and/or hunk **count** between what is shown to the model and/or what actually needs replacing, so the ordinal splice in `reassembleResolvedFile` associates the model's resolution with the wrong region of the file.

The write path performs no independent verification that resolved content only replaces the exact byte ranges git flagged as conflicted: `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` straight to disk and stages it with `git add` [4](#0-3) . Existing guards (`resolveWithin` path check, "file was resolved externally" skip, size caps in `copilot-conflict-context.ts`) all address different concerns (path traversal, external edits, memory limits) — none validate that the *content boundaries* used for hunk splitting match git's actual conflict ranges.

### Impact Explanation
This is a silent corruption of what the user commits: attacker-controlled repository content (a file merged in from an untrusted branch, PR, or simply present in a cloned repo) causes the AI-assisted conflict-resolution feature to overwrite/delete unrelated, non-conflicted code inside the same file with model-generated text intended for a different (or nonexistent) conflict. The user reviews an AI summary/diff in the result dialog and clicks "Continue Merge," at which point the corrupted content is written to disk and staged/committed [5](#0-4) . Depending on which unrelated code is clobbered, this can silently strip security checks, alter build/CI configuration, or introduce logic errors that ship as if they were normal merge output.

### Likelihood Explanation
Requires: (1) the victim to use the opt-in "Resolve with Copilot" feature (a normal supported user action, not an unnatural step), and (2) a file with attacker-crafted marker-like text to exist in history and later be involved in a real merge conflict — both are realistic for any repository that accepts external contributions (PRs, forks) merged by the maintainer. No local access, admin rights, or pre-existing malware is required; the trigger is purely repository content the attacker controls, which is exactly the "attacker controls a cloned/fetched repository" primitive named in the impact criteria.

### Recommendation
Do not rely solely on textual regex scanning to define hunk boundaries. Cross-validate detected conflict regions against git's own conflict metadata (e.g. `git diff --check`, index stage information from `git ls-files -u`, or `git merge-file` markers reported with `--conflict=diff3` combined with hunk offsets from `git diff`) before sending hunks to the model and before splicing resolutions back. At minimum, reject/flag files where the number of `<<<<<<<`/`=======`/`>>>>>>>` triples found textually does not match the number of conflicted regions git reports for that path, and fail closed (skip the file, require manual resolution) rather than guessing an ordinal mapping.

### Proof of Concept
1. Attacker contributes (via PR or a branch that will later be merged) a file `notes.md` containing, at column 0, a block that is not a real conflict but matches the marker regex, e.g.:
   ```
   Example of git markers for training purposes:
   <<<<<<< HEAD
   decoy-ours
   =======
   decoy-theirs
   >>>>>>> feature
   ```
2. The maintainer later performs a real merge that produces a genuine conflict elsewhere in the same file, so the file on disk contains two `<<<<<<<...>>>>>>>` blocks: the attacker's pre-existing decoy block and the real one from git.
3. The maintainer clicks "Resolve with Copilot." `extractConflictHunks` [1](#0-0)  detects **two** hunks (decoy + real) and sends both to the model as "Conflict 1 of 2" / "Conflict 2 of 2".
4. `reassembleResolvedFile` [2](#0-1)  splices the model's two resolutions back in ordinal order — into the decoy block and the real block respectively — silently rewriting the decoy region.
5. The maintainer accepts the suggestion and clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the file and runs `git add` [6](#0-5) , committing altered "documentation" content the maintainer never intended to change, without any diff/warning distinguishing it from the real conflict resolution.

Note: I was not able to fully verify, from the available index, every downstream review-UI code path (e.g., whether the result dialog's diff view would visually surface the decoy-block change before commit) since some UI rendering files were outside what the search returned; a Devin session with full repo access would be needed to confirm whether the review dialog would make this discrepancy visible to the user before they click "Continue Merge."

      i++
    }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
