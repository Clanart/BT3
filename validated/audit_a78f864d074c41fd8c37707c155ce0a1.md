### Title
Unbounded growth of `TxPool.beats` per-sender heartbeat map — never pruned when an account's queue entry is removed - (File: blockchain/tx_pool.go)

### Summary
`TxPool.beats` is a `map[common.Address]time.Time` created to track the last-activity heartbeat of every account that has ever had a transaction in the non-executable queue. The CVE describes Xen's MSR-emulation `vcpu` tracking structure that is allocated on vcpu creation but never freed on vcpu destruction, letting a low-privileged guest exhaust host memory by repeatedly rebooting. The Kaia `TxPool.beats` map shows the same allocate-without-free lifecycle: the entry is created the first time an address gets a queued transaction, but is never deleted when that address's queue entry is later removed.

### Finding Description
When a transaction is enqueued for a brand-new sender, the pool both creates the queue list and records a heartbeat entry: [1](#0-0) 

When that account's queue (or pending) later becomes empty, the pool deletes the account's `queue`/`pending` map entries, but not the corresponding `beats` entry: [2](#0-1) [3](#0-2) [4](#0-3) 

`pool.beats` is only ever read for eviction-ordering when the global queue limit is exceeded: [5](#0-4) 

None of the transaction-removal, promotion, demotion, or eviction paths (`removeTx`, `promoteExecutables`, `demoteUnexecutables`) delete stale entries from `pool.beats`. Since `common.Address` (Ethereum-style accounts) is unlimited and free to generate, any unprivileged sender can create an arbitrary number of distinct addresses, get each one a single queued (non-executable, future-nonce) transaction admitted into the pool (which only requires the tx to pass basic admission checks, not payment or balance), and thereby permanently grow `pool.beats` by one entry per fresh address — even after the transaction is dropped, replaced, evicted, or times out and its `queue`/`pending` map entry is deleted.

### Impact Explanation
This causes unbounded, permanent host memory growth from any address that ever transiently appears in the queue, driven entirely by an unprivileged public-RPC transaction sender submitting cheap/no-cost future-nonce transactions from freshly generated addresses. This is a denial-of-service condition against node memory (analogous to the CVE's host OOM DoS from repeated vcpu reboot), reachable purely through the transaction submission surface without requiring the transactions to ever be included in a block or to cost the attacker real KAIA (a future-nonce tx from a fresh unfunded account can still be enqueued and later dropped by `Filter`/`demoteUnexecutables`, leaving the `beats` entry behind).

### Likelihood Explanation
High reachability: any public RPC caller can call `eth_sendRawTransaction` repeatedly with fresh keypairs and non-sequential nonces, which the pool accepts into the future queue (subject to global/per-account queue-size caps that limit list size, not the number of distinct historical addresses tracked in `beats`). No consensus, staking, or special privileges are needed — this is a pure txpool admission-path issue.

### Recommendation
Delete the corresponding `pool.beats[addr]` entry everywhere an account's `queue` (and/or `pending`) map entry is removed because it became empty — specifically in `removeTx`, `promoteExecutables`, and `demoteUnexecutables` — so the heartbeat map's cardinality is bounded by the number of currently-tracked accounts, not the historical total of ever-seen addresses.

### Proof of Concept
1. Generate N fresh ECDSA keypairs / addresses (free, no on-chain cost).
2. For each address, submit (via public RPC `eth_sendRawTransaction`) a single transaction with a non-zero (future) nonce so it lands in `pool.queue[addr]`, triggering `pool.beats[addr] = time.Now()`.
3. Let the transaction time out / get evicted / get filtered out for insufficient balance so `demoteUnexecutables`/`promoteExecutables` deletes `pool.queue[addr]` (list becomes empty).
4. Observe that `pool.beats[addr]` is never removed; repeat steps 1–3 with new addresses indefinitely to grow `pool.beats` without bound, consuming node memory over time — no exploitation of consensus or peer trust required, purely via the public transaction-submission RPC.

Note: I was not able to run the code to directly measure memory growth; this analysis is based on static review of the cited functions in `blockchain/tx_pool.go`, which show `beats` insertion on account creation but no corresponding deletion path in any of the reviewed cleanup functions (`removeTx`, `promoteExecutables`, `demoteUnexecutables`).
