### Title
`SignableTransaction::new` omits the OP_RETURN output from the fee/weight calculation, so data-carrying transactions are signed with an underpaid fee and may never relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The vbyte/weight estimate used to derive `needed_fee` is computed from only the inputs and payments, while the `data` OP_RETURN output (up to 80 bytes of payload plus overhead) is appended to `tx_outs` but never passed into `calculate_weight_vbytes`. The signed transaction therefore pays `fee_per_vbyte * vbytes_underestimated` over a larger real vsize — an effective feerate below the one requested, potentially below the 1 sat/vbyte relay minimum — so the signed spend can be unconditionally unrelayable, mirroring the "call made without paying the required execution fee, so it always fails" class.

### Finding Description
`SignableTransaction::new` builds `tx_outs`, pushes the OP_RETURN output when `data` is `Some` (`send.rs:194-202`), and only afterwards calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`). `calculate_weight_vbytes` constructs a mock `Transaction` whose `output` vector is built solely from `payments` (`send.rs:85-93`), so the OP_RETURN output — which can add ~90 vbytes (80-byte push + script + 8-byte amount + count overhead) — is excluded from both `weight` and `vbytes`. The same omission occurs in the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (`send.rs:225-226`) again ignores the already-pushed OP_RETURN output.

Because `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) and the change amount is `input_sat - (payment_sat + fee_with_change)` (`send.rs:228-230`), the actual fee paid (`fee() = sum(inputs) - sum(outputs)`, `send.rs:138-141`) equals `needed_fee` — a value calibrated to a vsize the real transaction exceeds. The `TooLowFee` check (`send.rs:211`) compares `needed_fee` against the same understated `vbytes`, so it cannot catch the shortfall.

### Impact Explanation
An unprivileged party who can get transaction `data` signed (the `data` parameter of `SignableTransaction::new` is arbitrary caller-supplied bytes for the OP_RETURN output) produces a transaction whose true feerate is `needed_fee / actual_vsize`, strictly less than the intended `fee_per_vbyte`. When `fee_per_vbyte` is at or near the minimum (e.g., 1 sat/vb — the wallet only enforces `DEFAULT_MIN_RELAY_TX_FEE` against the understated vsize), adding ~90 unpriced vbytes pushes the actual feerate below 1 sat/vb for typical transaction sizes, making the transaction non-standard/unrelayable. The threshold signing round completes and produces a validly signed transaction that can never confirm — locking the consumed `ReceivedOutput` inputs until the plan is abandoned — the same failure shape as an `anyCall` dispatched without its execution gas fee. Even above the relay floor, the transaction systematically pays less than the negotiated feerate, degrading confirmation reliability.

### Likelihood Explanation
Any plan that includes OP_RETURN `data` triggers the miscalculation; the closer the requested feerate is to the minimum, the more likely the result is permanently unrelayable. Since the fee check and the change math both use the same understated vsize, no internal check catches it, and the defect is deterministic given `data.is_some()`.

### Recommendation
Include the OP_RETURN output in the weight/vsize estimate. Build the mock transaction inside `calculate_weight_vbytes` from the actual `tx_outs` (or pass `data`/the OP_RETURN `TxOut` into it) rather than only from `payments`, for both the no-change and with-change estimates at `send.rs:204` and `send.rs:225-226`. Alternatively, compute `vbytes` after all outputs (payments, change candidate, OP_RETURN) are known, and re-check `TooLowFee` against the final vsize.

### Proof of Concept
From `networks/bitcoin/src/wallet/send.rs`:

```rust
// OP_RETURN output is added to the real outputs (lines 194-202)
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...), // up to ~83 bytes
  })
}

// ...but the fee is priced from payments only (line 204)
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;

// relay check uses the same understated vbytes (line 211)
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

For a 1-input/1-payment transaction with `data = [0u8; 80]` and `fee_per_vbyte = 1`: `vbytes` ≈ 150 is priced, but the broadcast transaction is ≈ 240 vbytes, so the real feerate is ≈ 0.63 sat/vb < 1 sat/vb relay minimum. `SignableTransaction::new` returns `Ok`, the transaction is fully signed, and the network rejects it — the send always fails despite "paying" the required fee.
