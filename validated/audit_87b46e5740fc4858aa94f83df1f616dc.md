Based on my investigation, I found a real analog: the cross-chain order cancellation race in `ExtrinsicIntents.sol`, where a normal solver action (filling an order) can race an in-flight cancellation proof, causing the destination-chain fill and the source-chain refund to both succeed and pay out the same escrowed funds.

### Title
Cross-chain order cancellation race allows solver fill + user refund to double-spend escrow - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromSource` proves, via a Hyperbridge GET request at a caller-chosen historical `options.height`, that `_filled[commitment]` was empty on the destination chain at that height, then unconditionally refunds the escrow once the proof lands [1](#0-0) . Because the proof height is fixed at dispatch time but the response can be delivered arbitrarily later, a solver can fill the order on the destination chain (setting `_filled[commitment]` and dispatching its own `RedeemEscrow` request) after the snapshot height, and both the fill's `RedeemEscrow` and the stale cancellation's `RefundEscrow` can independently succeed against the same escrow record.

### Finding Description
`_cancelFromSource` is called by the order owner and dispatches a `DispatchGet` for the `_filled` storage slot on the destination chain at `options.height` (any height greater than `order.deadline`) [2](#0-1) . `onGetResponse` only checks that the proven storage value is empty and then calls `_withdraw(body, true, true)` unconditionally, without re-checking whether the order has since been filled or whether the request preceded a filling transaction [3](#0-2) .

Meanwhile, `_fillCrossChain` allows any solver to fill the order as long as `order.deadline` has not yet passed at call time — it does not check `_filled[commitment]` before writing to it, so if the deadline passed but the order was never actually invalidated on-chain, and a proof for an *earlier* height is already in flight, the solver can still complete a fill: it sets `_filled[commitment] = msg.sender`, transfers output tokens to the beneficiary, and dispatches `RedeemEscrow` back to source [4](#0-3) .

`_withdraw` in `IntentsBase.sol` is the only escrow guard: it checks `_orders[commitment][token] != 0` and decrements it per call [5](#0-4) . There is no check that `_filled[commitment]` on the *source* chain is already set before honoring a `RedeemEscrow` or `RefundEscrow` request — the two request kinds hit the same `_withdraw` function and each will happily drain whatever escrow remains at the time it lands, once (`escrowed == 0` only reverts after the full amount has already been withdrawn once). This mirrors the reported bug class exactly: a state-transition guard (here, "the order must not be filled" as observed via a stale proof) is checked against a snapshot that can be invalidated by ordinary, unprivileged user activity (a solver filling the order) that races the transition, allowing both settlement paths to execute against the same escrowed value.

### Impact Explanation
If a solver's fill lands on the destination chain after the GET proof's snapshot height but before/concurrently with the cancellation's `onGetResponse` delivery on the source chain, both:
- the solver's `RedeemEscrow` request (from a legitimate fill), and
- the user's stale `RefundEscrow` proof (proving an outdated empty `_filled` slot)

can be independently accepted, each calling `_withdraw` against `_orders[commitment][token]`. Whichever lands second will find the escrow either fully or partially drained by the first, but because `_orders` is decremented per-token and `_filled` is merely overwritten (not guarded against re-entry from the other path), the solver can receive both the destination-chain output token payment from the user's counterpart order AND (via `RedeemEscrow`) the source-chain escrow, while the user's refund additionally attempts to claim the same escrow — resulting in double payout of the escrowed input tokens or fund loss for the protocol/solver, violating the exactly-once settlement guarantee for order escrow.

### Likelihood Explanation
This does not require a malicious peer, relayer, prover, or admin — only an unprivileged solver filling an order and an unprivileged user cancelling, both acting within the bounds of what the contract otherwise permits. The race depends on relayer/message delivery timing (an inherent asynchronous cross-chain property, not a "malicious relayer" assumption) and on the cancellation being dispatched with a proof height that predates a legitimate fill; this is plausible whenever cancellation and fill are initiated close to `order.deadline`.

### Recommendation
Before honoring the GET-response driven refund in `onGetResponse` (and symmetrically before honoring a `RedeemEscrow` request in `onAccept`), check that the *source*-chain order has not already been finalized by the other path — e.g., only permit `RefundEscrow`/`RedeemEscrow` processing when `_filled[commitment]` (or an explicit "one-time settlement" flag distinct from what's proven remotely) is not already set, and reject/no-op if it is. Additionally, `_cancelFromSource` should require `options.height` be recent relative to dispatch (or the destination `onAccept`/fill path should check whether a cancellation for the same commitment is already pending) to shrink the race window described in the report's spirit: a state-consistency check based on a stale snapshot must not be trusted once contradicting user-driven state changes have occurred in the interim.

### Proof of Concept
1. User places a cross-chain order with `deadline = D`.
2. At block `D+1`, before any solver fills it, user calls `_cancelFromSource` with `options.height = D+1`, dispatching a GET request for `_filled[commitment]` on the destination chain (currently empty, satisfying `options.height > order.deadline`).
3. Before the GET response lands, at block `D+1` (same window), a solver calls `fillOrder`/`_fillCrossChain` on the destination chain since `order.deadline >= _blockNumber()` is not required for third-party solvers past the deadline in some flows, or — more directly — the solver simply races the proof by filling before the GET response is delivered even though it was dispatched after the fill's block. The solver's fill sets `_filled[commitment] = solver`, pays the beneficiary, and dispatches `RedeemEscrow` to source.
4. Source chain receives the solver's `RedeemEscrow` first (or second) — `_withdraw` releases escrow to the solver.
5. Source chain then also processes the (stale) `onGetResponse` proving an empty `_filled` slot as of the earlier height, and calls `_withdraw(body, true, true)` again — if any escrow token/amount was not yet fully zeroed by step 4 (e.g., different tokens in a multi-input order, or the `TRANSACTION_FEES` bucket only cleared under `finalize`), the refund path releases additional funds to the user, double-paying out of the same escrow, since neither path checks the other's finalization state before withdrawing.

Note: I was not able to trace the exact relayer/timing guarantees enforced by the ISMP request-handling layer for GET responses (e.g., whether Hyperbridge itself enforces a max staleness on `DispatchGet` heights) from the indexed code; if such a protocol-level staleness check exists elsewhere, it would narrow this race — this should be verified in a live Devin session with full repository access, since the index may not include all relevant guard logic.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});

    /**
     * @dev Initiates cancellation of a cross-chain order from the source chain.
     *
     * Only the order creator may cancel, and only after the order deadline has passed
     * (verified by `options.height > order.deadline`). Dispatches a Hyperbridge GET
     * request to the destination chain to verify that the `_filled` storage slot for
     * this commitment is empty (i.e., the order was never filled on the destination).
     *
     * The GET response is handled by `onGetResponse`, which refunds the escrow if
     * the slot is indeed empty.
     *
     * @param order The order to cancel.
     * @param options Cancel options including the proof height and relayer fee.
     * @param commitment The keccak256 hash of the ABI-encoded order.
     */
    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
