### Title
Positional (index-based) line-selection is re-applied to a freshly regenerated diff at commit/patch time, allowing silent corruption of partial commits when working-tree content shifts between review and commit - (File: `app/src/lib/git/apply.ts`)

### Summary
Analogous to the Lavarage bug (a value the user relied on when consenting to an action can drift before the action executes, harming the user despite them acting immediately/correctly), GitHub Desktop's partial-staging flow lets a user select individual lines of a diff to commit, but the selection is stored purely as **line indices** (`DiffSelection`), not tied to the content of those lines. When the commit is actually created, Desktop regenerates the diff from disk and re-applies the old index-based selection to it. If the file's line layout has shifted in the meantime (e.g., due to a `clean`/`smudge` git filter, `.gitattributes` EOL/text conversion, a hook, or an external tool writing to the file — all of which are influenced by content that a malicious/cloned repository can control), the user can silently commit and push different lines than the ones they reviewed and checked off.

### Finding Description
`DiffSelection.isSelected(lineIndex)` operates purely on line index/offset, with no verification that the content at that index is what the user actually saw: [1](#0-0) 

The partial-commit code path in `applyPatchToIndex` fetches a **fresh** diff from the working directory right before building the patch, then reuses `file.selection` (computed against a *previous* diff render) to decide which lines go into the patch: [2](#0-1) 

`formatPatch` builds the patch strictly by `absoluteIndex` (`hunk.unifiedDiffStart + lineIndex`) against `file.selection.isSelected(absoluteIndex)`, with no check that the line at that index is the same line the user selected: [3](#0-2) 

Desktop is aware that diffs can change out from under a stale selection — the comment in `updateChangesWorkingDirectoryDiff` explicitly acknowledges this ("The diff might have changed dramatically since last we loaded it") but only prunes lines that no longer exist; it does **not** invalidate selection when the file's content has shifted (e.g., added/removed lines earlier in the file), which changes what each *index* now refers to: [4](#0-3) 

`createCommit` and `getFilesDiffText` follow the same unstage→stage(`stageFiles`)→diff-or-commit pattern, so the same stale-selection issue applies at the moment of commit creation, not just when the diff is first rendered: [5](#0-4) [6](#0-5) 

**Attacker path (matches valid-impact criteria — "silent corruption of what the user commits or pushes"):** an attacker who controls repository content (via a `.gitattributes` filter/`clean` script, a checked-in build tool invoked by a hook, or any process that rewrites tracked files under normal repo operation) can cause a file's line layout to shift between (a) the moment the user reviews a diff and checks specific lines/hunks for partial commit, and (b) the moment Desktop actually re-diffs and stages the file for the commit. Because Desktop's selection state is index-based and not content-anchored, the user's careful "commit only these lines" intent can silently resolve to a different, attacker-influenced set of lines being staged and committed (and later pushed) — without any error, since `git apply` will happily apply a syntactically valid but semantically wrong hunk built from the current diff's context lines.

### Impact Explanation
This breaks the core trust guarantee of Desktop's line-level staging feature: what the user visually selects is not guaranteed to be what gets committed. Depending on timing, this could:
- Commit/push unintended lines (including attacker-influenced content) that the user never reviewed or approved.
- Cause a user to unknowingly leak or persist content they explicitly chose to exclude (e.g., partially-redacted secrets, unfinished code) into a shared commit/push.
- Produce silently incorrect history, which is hard for the user to detect after the fact (the app shows no warning; the operation "succeeds").

This matches "silent corruption of what the user commits or pushes" in the stated valid-impact category, without requiring local/admin access, leaked credentials, or social engineering — the trigger is repository/content-controlled (attacker-authored `.gitattributes`/filter/hook shipped in the cloned repo).

### Likelihood Explanation
Moderate-to-low but realistic: it requires a window between diff render and commit execution during which the file's on-disk line layout shifts (via a git filter/hook driven by repo content, or a background tool). Desktop already anticipates and partially handles a similar race (see `updateChangesWorkingDirectoryDiff`'s "diff might have changed dramatically" comment) but only defends against lines disappearing, not lines shifting position while remaining selectable — leaving the core index-based reuse in `applyPatchToIndex`/`formatPatch` unguarded. Repositories with `clean` filters, `.gitattributes`-driven line-ending normalization, or pre-commit/smudge hooks are common enough that this is not a contrived scenario.

### Recommendation
- Anchor line selections to content (e.g., hash or diff-hunk identity) rather than raw index, or re-validate that the diff used to build the selection state is byte-identical (or at least structurally identical, hunk-for-hunk) to the diff used to build the patch immediately before staging/commit.
- If the diff has changed since the user's last selection, refuse the partial commit and force a diff refresh + re-confirmation before applying, rather than silently applying possibly-mismatched positional selections.
- At minimum, compare a checksum/etag of the file (or the diff hash) between selection time and `applyPatchToIndex` time, and abort the commit with a user-facing error if they differ.

### Proof of Concept
Conceptual (concrete file/function evidence, not independently executed):
1. User modifies a tracked file and opens the Changes view; Desktop computes and displays a diff, and the user selects specific lines (indices) for partial commit via `DiffSelection.withLineSelection` (`app/src/models/diff/diff-selection.ts:205-282`).
2. Before the user hits "Commit," a repository-controlled mechanism (e.g., a `clean` filter defined in the repo's `.gitattributes`, or a hook script shipped with the cloned repo) rewrites the file on disk, inserting/removing lines earlier in the file so that line indices shift.
3. User clicks "Commit." `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` (now reflecting the shifted content) and calls `formatPatch(file, diff)`, which re-applies the *old* index-based `file.selection` to the *new* diff (`app/src/lib/git/apply.ts:52-84`, `app/src/lib/patch-formatter.ts:143-171`).
4. Because indices no longer correspond to the same visual lines the user reviewed, the resulting patch stages/commits different content than intended, and `git commit`/`git apply` completes without error (`app/src/lib/git/commit.ts:26-31`).

I was not able to execute this against a live Desktop build/tests in this environment, so the exact timing window and any additional guardrails elsewhere in the staging pipeline (e.g., possible file-mtime checks not surfaced in the indexed code) should be verified by a Devin agent with full repository and runtime access before filing as a confirmed, reproducible finding.
