### Title
Fee-on-transfer LP tokens break internal accounting in `WombatStaking.depositLP` - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.depositLP` mints receipt tokens 1:1 with the caller-supplied `_lpAmount` parameter instead of measuring the LP tokens actually received via `safeTransferFrom`. If the underlying LP token (or any token registered as a pool's `lpAddress`) charges a transfer fee, the contract receives less than `_lpAmount` but still mints the full `_lpAmount` of receipt tokens and stakes/credits the full `_lpAmount` downstream.

### Finding Description
In `deposit()`, the contract correctly guards against amount mismatches by measuring the actual LP tokens received before minting receipt tokens: [1](#0-0) 

However, `depositLP()` does not apply the same before/after balance check. It transfers `_lpAmount` from `_for`, then immediately uses the raw `_lpAmount` value both to route into `_toMasterWomAndSendReward` and to mint the receipt token: [2](#0-1) 

The pool helpers that call this function (`WombatPoolHelper.depositLP`, `WombatPoolHelperV2.depositLP`, `AnkrBNBPoolHelper.depositLP`) do measure the receipt-token delta on their own side via before/after balance of `stakingToken`, but that only tracks what `WombatStaking` mints them — it does not fix the root issue, since `WombatStaking` already minted receipt tokens matching the pre-fee `_lpAmount`, not the actual LP balance it holds: [3](#0-2) 

If a fee-on-transfer token were registered as a pool's `lpAddress` (via `registerPool`, an admin action, but the resulting mismatch is triggered and exploited by any ordinary user calling `depositLP`), every `depositLP` call would mint receipt tokens for more LP than the contract actually custodies. Receipt tokens back withdrawals via `burnReceiptToken` and `withdraw`, which rely on the pool actually holding the LP amount being withdrawn: [4](#0-3) 

### Impact Explanation
Each `depositLP` call under a fee-on-transfer LP token creates a permanent, compounding shortfall between minted receipt tokens (and thus staked/lockable balances credited to users) and the actual LP tokens held by `WombatStaking`. This is a protocol-insolvency bug class: eventually withdrawals by legitimate depositors will fail or drain the LP balance leaving later withdrawers unable to redeem, i.e., permanent freezing/loss of user funds for at least a subset of depositors reachable purely by ordinary wallet calls to `depositLP`.

### Likelihood Explanation
Exploitability depends on a pool being registered with a fee-on-transfer LP token via `registerPool`, which is an admin action and out of scope for privileged-analog exclusion — however, the actual accounting break and resulting fund freeze is triggered purely by ordinary users calling the unprivileged `depositLP` function repeatedly, with no admin action required at the time of exploitation. If any currently or future registered LP token behaves as fee-on-transfer (or is upgraded to add a fee, as in rebasing/deflationary token upgrade patterns), the issue activates automatically for all subsequent depositors.

### Recommendation
Mirror the pattern used in `deposit()`: measure the LP token balance of `WombatStaking` before and after the `safeTransferFrom` call in `depositLP`, and use that measured delta (not the raw `_lpAmount` parameter) for both `_toMasterWomAndSendReward` and the receipt token minting.

### Proof of Concept
1. Admin registers a pool whose `lpAddress` is a fee-on-transfer token (e.g., 1% fee on transfer).
2. User A calls `WombatPoolHelperV2.depositLP(1000)` → `WombatStaking.depositLP(lpAddress, 1000, userA)`.
3. `safeTransferFrom(userA, address(this), 1000)` only delivers 990 LP tokens to `WombatStaking` due to the fee.
4. `WombatStaking` still calls `_toMasterWomAndSendReward(lpAddress, 1000, true)` and mints `1000` receipt tokens to the caller (the pool helper), even though only 990 LP were received.
5. The pool helper's `_stake` credits the user with shares based on its own receipt-token delta, which reflects the full 1000 minted — so the user is credited for 1000 LP-equivalent stake although only 990 LP physically backs it.
6. Repeated across users, `WombatStaking`'s outstanding receipt-token supply for that pool exceeds its actual LP holdings, so a later `withdraw` call will fail (insufficient LP balance) or drain funds meant for other depositors, permanently freezing part of user funds.

    function depositLP(
        address _lpAddress,
        uint256 _lpAmount,
        address _for
    ) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {
        // Get information of the Pool of the token
        Pool storage poolInfo = pools[_lpAddress];

        // Transfer lp to this contract and stake it to wombat
        IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);

        _toMasterWomAndSendReward(_lpAddress, _lpAmount, true); // triggers harvest from wombat exchange
        IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);

        emit NewLPDeposit(_for, poolInfo.lpAddress, _lpAmount, poolInfo.receiptToken, _lpAmount);
    }
