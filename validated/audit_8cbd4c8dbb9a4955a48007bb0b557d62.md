### Title
Unverified client-supplied `gas_estimate` allows bypassing the block-gas resource cap enforced by `checkTotalBlockGas` - (File: `app/app.go`, `x/evm/ante/gas.go`)

### Summary
Sei's `checkTotalBlockGas` uses a per-transaction `GasEstimate` field to decide how much of the block gas budget (`ConsensusParams.Block.MaxGas`) an EVM transaction consumes, preferring this "estimate" over the transaction's actual `Gas()` (gasWanted) whenever the estimate is `>= MinGasEVMTx` and `<= gasWanted`. That `GasEstimate` field lives in the signed `AuthInfo.Fee.gas_estimate` of the transaction and is entirely attacker-controlled — the ante-pipeline's `GasDecorator` accepts it verbatim as long as it clears the fixed floor of `21000`, without ever comparing it to a real simulation of the transaction's expected execution cost. This lets a transaction sender declare a low `gas_estimate` while setting an arbitrarily larger `gasWanted`, causing the "best estimate of total gas" that gates block admission to systematically undercount the real compute a proposed/admitted block will require — directly analogous to the LobeHub bug where a client-declared `size` value was trusted for quota accounting without validation against the real payload.

### Finding Description
`x/evm/ante/gas.go`'s `GasDecorator.AnteHandle` sets the context's gas estimate straight from the transaction body: [1](#0-0) 
There is no check that this value bears any relation to how much gas the EVM execution will actually need — the only gate is `>= MinGasEVMTx` (`21000`), the minimum intrinsic gas of any EVM tx.

This `GasEstimate` is round-tripped through `ResponseCheckTx`/mempool (`app/legacyabci/check_tx.go`, `sei-tendermint/internal/autobahn/producer/mempool.go`) and, crucially, is read straight back off the decoded transaction body during proposal validation in `app/app.go`'s `checkTotalBlockGas`: [2](#0-1) 
Because `decodedTx.GetGasEstimate()` is a field embedded and signed by the sender in `AuthInfo.Fee` (`sei-cosmos/proto/cosmos/tx/v1beta1/tx.proto` lines 186-188, `sei-cosmos/x/auth/tx/builder.go` `SetGasEstimate`), any attacker who signs their own transaction can set `gas_estimate = 21000` (the floor) while setting `gasWanted` (the tx's real `Gas()` field) to something much larger, e.g. the per-tx cap. `checkTotalBlockGas` will then charge only `21000` toward `totalGas`, not the real gas the transaction may consume during execution, even though nothing prevents the transaction from actually executing up to its full `gasWanted` if its EVM logic (e.g., storage writes, loops, precompile calls) genuinely needs that much gas.

This is the same bug class as the referenced LobeHub advisory: a client-declared metadata value used for a server-side resource-accounting/quota decision (there: file `size` for storage billing; here: `gas_estimate` for block gas budget enforcement) is trusted without validating it against the real, measured resource consumption, letting the client understate its true footprint and evade the enforcement mechanism.

### Impact Explanation
`checkTotalBlockGas` exists specifically to bound the total real compute work a block can require, both in `PrepareProposal`/mempool-packing and `ProcessProposal` validation, so nodes do not accept blocks whose total real gas usage would blow past `ConsensusParams.Block.MaxGas`. By gaming `gas_estimate`, an attacker (or colluding senders) can pack a block whose *declared* aggregate gas is well under `MaxGas`, while the *actual* aggregate EVM gas consumed during execution is far higher (bounded only by each tx's real `gasWanted`, sum of which can exceed `MaxGas` many times over, subject only to `MaxGasWanted`, which is a separate, typically much larger cap intended to bound worst-case gas, not typical/average execution time). This breaks the intended invariant of the block-gas heuristic and can cause blocks to take significantly longer to execute than the chain's compute budget anticipates, resulting in validator processing delays. Given block-time targets on Sei, sufficiently large real-vs-declared gas gaps (multiplied across many transactions in one block) can push block execution time beyond the 2.5-second threshold, causing chain-wide slowdown/validator halt symptoms.

### Likelihood Explanation
Exploitation requires nothing beyond the ability to sign and submit an ordinary EVM transaction — no special privilege, no validator/proposer role, and no cooperation from the chain operator. The `gas_estimate` field is a normal, documented part of the Cosmos SDK `Fee` message that any wallet/tx-builder can set arbitrarily since it's part of the sender's own signed transaction. The only constraint enforced anywhere in the ante pipeline is `est >= MinGasEVMTx`, a trivial floor to satisfy. This makes the condition straightforward to trigger deliberately by any unprivileged sender who understands the `checkTotalBlockGas` heuristic.

### Recommendation
Do not trust the client-declared `gas_estimate` for resource-cap enforcement. Either:
- Remove the `GetGasEstimate()` preference path from `checkTotalBlockGas` and always charge `gasWanted` (the safe, provably-bounded value) toward `totalGas`, or
- Recompute/validate the estimate server-side (e.g., via the same simulation path already used in `evmrpc/send.go`'s `simulateTx`) before it is persisted into the tx that gets gossiped/proposed, and reject transactions at CheckTx if the declared `gas_estimate` deviates materially (beyond some tolerance) from a locally recomputed estimate, rather than accepting any value `>= MinGasEVMTx`.

### Proof of Concept
1. Craft a legacy/dynamic-fee EVM transaction whose `Gas` (gasWanted) field is large, e.g. close to the per-tx cap, with call data/logic that will legitimately consume close to that much gas when executed (e.g., a contract call doing many `SSTORE`s).
2. Build the wrapping Cosmos tx via `txBuilder.SetGasEstimate(21000)` (the `MinGasEVMTx` floor) while leaving `Gas`/gasWanted at the large value — this mirrors exactly what `app/check_total_block_gas_test.go`'s `buildSignedLegacyEVMTx(t, a, nonce, gasWanted, gasEstimate)` helper constructs, and is exercised by `TestCheckTotalBlockGas_GasEstimatePreferredOverGasWanted` (`app/check_total_block_gas_test.go` lines 121-134), which explicitly demonstrates that three txs with `gasWanted=100_000` but `gasEstimate=21_000` pass `checkTotalBlockGas` under a `MaxGas=80_000` cap that they would fail if `gasWanted` were counted instead.
3. Sign and broadcast several such transactions in the same block. `checkTotalBlockGas` (invoked from `ProcessProposal`/`PrepareProposal`) will accept the block because `totalGas` (sum of declared `21000`s) stays under `MaxGas`, even though the real EVM execution of these transactions can consume up to their full `gasWanted` each, exceeding the `MaxGas` budget the check was meant to enforce. // Called at the end of the ante chain to set gas limit and gas used estimate properly
```go
func (gl GasDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	msg := evmtypes.MustGetEVMTransactionMessage(tx)
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return ctx, err
	}

	txGas := txData.GetGas()
	if txGas > math.MaxInt64 {
		return ctx, errors.New("tx gas exceeds max")
	}
	adjustedGasLimit := gl.evmKeeper.GetPriorityNormalizer(ctx).MulInt64(int64(txGas)) //nolint:gosec
	gasMeter := sdk.NewGasMeterWithMultiplier(ctx, adjustedGasLimit.TruncateInt().Uint64())
	ctx = ctx.WithGasMeter(gasMeter)
	if tx.GetGasEstimate() >= MinGasEVMTx {
		ctx = ctx.WithGasEstimate(tx.GetGasEstimate())
	} else {
		ctx = ctx.WithGasEstimate(gasMeter.Limit())
	}
	return next(ctx, tx, simulate)
}
```

```go
// checkTotalBlockGas checks that the block gas limit is not exceeded by our best estimate of
// the total gas by the txs in the block. The gas of a tx is either the gas estimate if it's an EVM tx,
// or the gas wanted if it's a Cosmos tx. typedTxs must align with proposal order (nil = decode failure).
func (app *App) checkTotalBlockGas(ctx sdk.Context, typedTxs []sdk.Tx) (_result bool) {
	defer func() {
		if r := recover(); r != nil {
			logger.Error("panic recovered in checkTotalBlockGas", "panic", r)
			_result = false
		}
	}()

	var totalGas, totalGasWanted uint64
	for _, decodedTx := range typedTxs {
		if decodedTx == nil {
			return false
		}

		isEVM, evmErr := evmante.IsEVMMessage(decodedTx)

		// EVM classification failed (e.g. multi-msg containing an EVM message); such a tx won't be
		// processed and so contributes no gas to the block.
		if evmErr != nil {
			continue
		}

		var gasWanted uint64
		if isEVM {
			msg := evmtypes.MustGetEVMTransactionMessage(decodedTx)
			if msg.IsAssociateTx() {
				continue
			}
			etx, _ := msg.AsTransaction()
			gasWanted = etx.Gas()
		} else {
			feeTx, ok := decodedTx.(sdk.FeeTx)
			if !ok {
				// Non-fee tx won't be processed and thus won't consume gas. Skipping.
				continue
			}
			gasWanted = feeTx.GetGas()
		}

		// Overflow guards: gasWanted must fit in int64, and adding it to either accumulator
		// must not wrap uint64.
		if int64(gasWanted) < 0 || //nolint:gosec
			totalGasWanted > math.MaxUint64-gasWanted ||
			totalGas > math.MaxUint64-gasWanted {
			return false
		}

		totalGasWanted += gasWanted

		// Prefer the gas estimate when it's a valid EVM estimate (>= MinGasEVMTx) and not
		// inflated above gasWanted; otherwise charge full gasWanted.
		if est := decodedTx.GetGasEstimate(); est >= MinGasEVMTx && est <= gasWanted {
			totalGas += est
		} else {
			totalGas += gasWanted
		}

		blockParams := ctx.ConsensusParams().Block
		maxGasWanted := uint64(blockParams.MaxGasWanted) //nolint:gosec
		maxGas := uint64(blockParams.MaxGas)             //nolint:gosec
		if totalGasWanted > maxGasWanted || totalGas > maxGas {
			return false
		}
	}

	appMetrics.blockGasWanted.Record(ctx.Context(), int64(totalGasWanted)) //nolint:gosec
	if cp := ctx.ConsensusParams(); cp != nil && cp.Block != nil && cp.Block.MaxGasWanted > 0 {
		appMetrics.blockGasWantedRatio.Record(ctx.Context(), float64(totalGasWanted)/float64(cp.Block.MaxGasWanted))
	}
	return true
}
```

```go
// TestCheckTotalBlockGas_GasEstimatePreferredOverGasWanted exercises the branch where a
// valid gas estimate (>= MinGasEVMTx and <= gasWanted) is charged instead of full gasWanted.
// With MaxGas=80_000, three txs at gasWanted=100_000 would clearly exceed if counted by
// gasWanted (300_000) but fit comfortably when counted by estimate (63_000).

	ctx := newBlockGasCtx(t, a, 80_000, 1_000_000)

	txs := make([]sdk.Tx, 0, 3)

	require.True(t, a.checkTotalBlockGas(ctx, txs))
}
```
