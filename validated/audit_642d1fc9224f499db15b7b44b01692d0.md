## Finding: Stale diff-selection indices reused against a freshly re-fetched diff during partial commit

### Title
Partial-commit line selection is applied to an independently re-fetched working-directory diff, allowing silent inclusion/exclusion of unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
`StoneBTCVault` assumed a 1:1 equivalence between different BTC tokens without re-validating that assumption at withdrawal time, letting an attacker exploit the gap between "what was deposited" and "what is redeemed." GitHub Desktop has a structurally identical bug in its partial-commit path: it assumes the line-selection indices a user built while reviewing one diff still correspond 1:1 to the diff hunks that exist when the commit patch is actually generated, without re-validating that the two diffs describe the same content.

### Finding Description
When a user reviews a file's changes for partial staging, Desktop loads a diff and lets the user select individual lines via `DiffSelection`, keyed purely by absolute line index (`file.selection.isSelected(absoluteIndex)`), as seen in `formatPatch`: [1](#0-0) 

That selection is stored on the `WorkingDirectoryFileChange` in application state, refreshed by `updateChangesWorkingDirectoryDiff`, which only reconciles *selectable* line indices when a newer diff is loaded - it explicitly does not verify that previously selected lines still correspond to the same content: [2](#0-1) 

When the user actually commits, `_commitIncludedChanges` passes the same `files` (with their in-memory `selection`) into `createCommit` → `applyPatchToIndex`: [3](#0-2) 

Critically, `applyPatchToIndex` does **not** use the diff the user actually reviewed on screen. It independently re-fetches the working directory diff at commit time: [4](#0-3) 

and then calls `formatPatch(file, diff)` using the *stale* `file.selection` (built against the earlier, UI-displayed diff) against this brand-new diff. The `absoluteIndex`-based selection model has no notion of hunk content — it only knows line indices — so if the underlying diff hunks shift (different line counts, different context, different hunk boundaries) between the moment the user made their selection and the moment `applyPatchToIndex` re-diffs the file, the same indices now point at different lines. `formatPatch` will silently include lines the user never selected, or drop lines the user did select, based purely on positional coincidence.

This is the same broken invariant as the report: an assumed 1:1 correspondence (selected-line-index ↔ reviewed-content) is relied upon across a window where the underlying value (the diff) can change, and there is no delay, re-validation, or content hash check bridging that window — exactly the missing "delay/verification" the report recommends for the vault.

### Impact Explanation
If the working tree content for the file changes between the diff shown during selection and the diff re-fetched by `applyPatchToIndex` (e.g., due to a background process, editor autosave, a build/watch tool, or non-deterministic content produced by a repository-configured diff/clean filter), the resulting commit can silently contain different content than what the user visually reviewed and approved via the partial-staging UI. This is a "silent corruption of what the user commits" scenario: the user believes they are committing only the lines they checked, but git-index content is generated from mismatched (index, diff) pairs. Since Desktop trusts `file.selection` positional indices without ever diffing them against a content fingerprint of the diff they were computed from, there is no code path in `apply.ts` or `patch-formatter.ts` that detects or rejects this mismatch.

### Likelihood Explanation
The window between when a diff is displayed/selected (`updateChangesWorkingDirectoryDiff`) and when it's re-fetched for patch construction (`applyPatchToIndex`) is a normal part of every partial commit — it requires no special user action beyond making a partial selection and clicking Commit. The bug is triggered by ordinary conditions that are entirely plausible in real usage (file watchers, formatters-on-save, build tools writing to tracked files) and does not require elevated privileges, additional git operations to be aware of, or explicit malicious intent from the local user — only a change to the file's on-disk content occurring during that window. I was not able to fully verify whether Desktop's `getWorkingDirectoryDiff` disables all repository-controlled diff customization (e.g., `.gitattributes` `textconv`/clean filters) in every code path, so I cannot confirm with certainty whether a fully repo-only (no local process) trigger exists; that remains unverified given index limits on `app/src/lib/git/diff.ts`.

### Recommendation
Bind the `DiffSelection` to a content fingerprint (e.g., a hash of the diff/hunks it was computed against) rather than raw line indices, and have `applyPatchToIndex` re-fetch the diff, compare the fingerprint to the one used to build the selection, and abort (or force the user to re-review) if they differ, instead of silently reapplying stale indices to new content.

### Proof of Concept
1. Open a file with local changes in Desktop and make a partial line selection in the diff view (this triggers `updateChangesWorkingDirectoryDiff`, computing `DiffSelection` against diff D1).
2. Before clicking "Commit", modify the file on disk in a way that shifts hunk boundaries/line counts but keeps the file "changed" (e.g., an editor autosave, formatter, or background script inserts/removes lines above the hunk the user selected).
3. Click "Commit". `_commitIncludedChanges` → `createCommit` → `applyPatchToIndex` re-fetches the diff (now D2) via `getWorkingDirectoryDiff`.
4. `formatPatch(file, D2)` applies the D1-derived `file.selection` indices to D2's hunks, producing a patch whose staged lines no longer correspond to what the user visually reviewed and checked in step 1 — resulting in a commit containing unreviewed/unintended content. [5](#0-4) [6](#0-5)
