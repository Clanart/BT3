### Title
Silent, unconfirmed remote-URL rewrite driven by unverified GitHub API repository match ("repo-jacking" hijack of push/fetch target) - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically "refreshes" the association between a local repository and its GitHub-hosted counterpart, and as part of that refresh it will silently rewrite the local `origin` remote URL to whatever `clone_url` the GitHub API now returns for the `owner/name` pair parsed out of the *current* remote URL. The `owner/name` pair used to query the API is derived purely from string-parsing the existing remote (`matchGitHubRepository`), with no verification that the repository returned by the API is the same repository (by id) that Desktop previously associated with this clone. If an attacker gains control of that `owner/name` slug on the GitHub host (e.g., by claiming a vacated/renamed name — classic "repo-jacking"), Desktop will automatically retarget the user's `origin` remote to the attacker's repository without any prompt or confirmation.

### Finding Description
`matchGitHubRepository` (`app/src/lib/repository-matching.ts:29-46`) matches an account to a remote purely by comparing the remote's hostname to the account's endpoint hostname, and returns `{ name, owner }` taken straight from parsing the remote URL string — it never consults the previously stored `GitHubRepository.dbID`/API id. [1](#0-0) 

That `owner`/`name` pair is then used in `repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4874-4913`) to call `api.fetchRepository(owner, name)` and fetch a fresh `apiRepo` object from the GitHub API for that path — again with no identity check against the previously known repository id. [2](#0-1) 

The returned `apiRepo` is then passed into `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:7-45`), which will call `gitStore.setRemoteURL(...)` and rewrite the on-disk git remote whenever:
- the protocol of the old and new clone URL match, and
- the current remote URL still matches what was previously stored as `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited the remote), and
- the newly fetched `clone_url` differs from the current remote URL. [3](#0-2) 

Nothing in this chain validates that the `apiRepo` returned by `/repos/{owner}/{name}` is the *same* repository (by GitHub repo id) that was originally cloned. If the original `owner/name` becomes available again on the host (renamed away by its owner, deleted, or the account name itself changed hands) and an attacker registers that exact `owner/name`, the next background refresh will fetch the attacker's repository metadata and Desktop will silently call `setRemoteURL` to point the user's `origin` remote at the attacker-controlled URL — with no event, no confirmation dialog, and no diff shown to the user, mirroring the `AbstractRewardMine.setRewardToken` pattern of “update to attacker-influenced data while dependent state (the trust relationship with `owner/name`) is not properly invalidated/reset.”

`setRemoteURL` itself performs the change unconditionally at the git level: [4](#0-3) 

and `GitStore.setRemoteURL` (`app/src/lib/stores/git-store.ts:1533-1543`) applies it without any user-facing confirmation step; the only place a human sees a remote-URL change is the manual Repository Settings dialog (`app/src/ui/repository-settings/repository-settings.tsx:292-313`), which is not on this automated path. [5](#0-4) 

### Impact Explanation
Once `origin` is silently repointed to the attacker's repository, subsequent Desktop operations against "the same" remote (fetch, pull, and especially push) go to the attacker-controlled host/repository instead of the legitimate one. This satisfies the "silent corruption of what the user commits or pushes" impact bucket: a user's local commits could be pushed to a repository the user never intended to push to, and any credentials/tokens sent as part of that HTTPS push (Basic Auth headers, if a generic/non-GitHub.com credential path is in use) would be exposed to the attacker's server. Because this happens on a periodic background refresh (`repositoryWithRefreshedGitHubRepository`) rather than any explicit user action, the user is not required to click anything for the remote to change.

### Likelihood Explanation
The prerequisite is that the attacker be able to register the exact `owner/name` slug that a legitimate repository previously occupied and that Desktop still associates with the user's local clone. This can occur naturally through name reuse after an account rename/deletion or repository rename — a well-known "repo-jacking" pattern on hosted git platforms — and requires no privileged access, no local/physical access, and no credential theft on the attacker's part; the attacker only needs to control content served by the GitHub API for a name they can legitimately claim. The existing guards (protocol match, "remote unchanged since last known clone URL") do not stop this path because they check consistency with the *local* state, not the *identity* (repository id) of the remote object being fetched from the API.

### Recommendation
- Do not silently auto-update the remote URL from API-provided `clone_url` data. At minimum, gate `updateRemoteUrl` on verifying `apiRepo`'s repository id matches the previously stored `GitHubRepository` id/dbID before treating it as the same repository.
- If an auto-update is still desired for legitimate renames, surface an explicit confirmation UI (similar to the manual Repository Settings flow) showing the old and new URL before applying `setRemoteURL`, rather than applying it transparently in a background refresh.
- Emit a log/telemetry event whenever `updateRemoteUrl` changes a remote so users/support can audit unexpected remote changes.

### Proof of Concept
1. User clones `https://github.com/victim/project`; Desktop stores this as a `GitHubRepository` with `cloneURL` = that URL and some `dbID`/API id.
2. The `victim/project` repository is later renamed or the `victim` account is deleted/renamed, freeing up the `victim/project` path on the host.
3. Attacker registers an account/organization such that they now control the exact URL `https://github.com/victim/project`, and sets `clone_url` for it to their own attacker-controlled clone URL (e.g., a different repo they own, or the same slug now pointing at their fork).
4. On the next periodic refresh, `repositoryWithRefreshedGitHubRepository` (`app/src/lib/stores/app-store.ts:4874-4913`) calls `matchGitHubRepository` → derives `owner=victim, name=project` from the *existing local remote string* → calls `api.fetchRepository('victim','project')`, which now returns the attacker's repo data.
5. `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:18-44`) sees protocol match and `remoteUrlUnchanged` is true (user never edited the remote), and the fetched `clone_url` differs from the local remote → calls `gitStore.setRemoteURL(...)`, silently rewriting `origin` to the attacker's clone URL.
6. The user's next `git push` from Desktop goes to the attacker's repository without any warning shown. [6](#0-5) [1](#0-0) [7](#0-6)

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
