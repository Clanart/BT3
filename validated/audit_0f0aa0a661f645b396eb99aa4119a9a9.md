## Title
Unbounded quadratic/near-quadratic coin-dependency resolution in offer cancellation enables local wallet processing halt from a malicious offer - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` (and its helper `detect_dependent_coin()`) in `chia/wallet/trading/offer.py:53-63,425-470` resolves inter-coin `ASSERT_COIN_ANNOUNCEMENT`/`CREATE_COIN_ANNOUNCEMENT` dependency chains across every non-addition coin spend in an offer's bundle, using nested Python loops with no bound on the number of coins, dependencies, or announcements. This mirrors the GitLab PyPI-endpoint bug class (BIT‑gitlab‑2022‑1431 / CVE‑2022‑1431): a request built from attacker-controlled structure is processed by an algorithm whose cost is not bounded relative to the structure's size, allowing uncontrolled resource consumption on the receiving side. [1](#0-0) [2](#0-1) 

### Finding Description
`detect_dependent_coin()` performs `O(names × deps[name] × announcement_dict)` work per call: for every coin name, it iterates every dependency, and for every dependency it scans the entire announcement dictionary. [1](#0-0) 

`get_cancellation_coins()` calls `detect_dependent_coin()` repeatedly inside an outer `while True` loop, and for each match it runs an inner `while True` loop that re-scans the full `dependencies` dict looking for coins whose dependency set intersects the removed coin's announcements, propagating removal transitively. [3](#0-2) 

Because an offer's `WalletSpendBundle` (`self._bundle.coin_spends`) is attacker/counterparty-supplied data (an offer file received from an untrusted trading counterparty), the number of coin spends, the length of each coin's `ASSERT_COIN_ANNOUNCEMENT` dependency list, and the size of the `announcements` map are all fully controlled by whoever crafts the offer. A crafted offer with many coin spends chained through announcement conditions (each coin asserting a distinct announcement from another coin, forming a dependency graph) drives the combined outer/inner-loop, per-call `O(n)`-scan algorithm toward `O(n^3)`–`O(n^4)` behavior in the number of offer coins `n`. This computation runs entirely in Python on the wallet/RPC side, with no CLVM cost accounting and no size cap on the number of coin spends processed by this routine (CLVM execution cost limits bound puzzle execution, not this post-processing graph walk). [4](#0-3) 

This is functionally analogous to the GitLab CVE: a client-supplied, attacker-shaped structure (there, PyPI package/version identifiers; here, an offer's set of coin spends and their announcement dependency graph) is fed into a processing routine whose complexity scales super-linearly with attacker-controlled input size, with no independent resource ceiling enforced before or during that processing.

### Impact Explanation
`get_cancellation_coins()` is used by the wallet's trade-cancellation flow (`chia/wallet/trade_manager.py`, exposed via `wallet_rpc_api.py`'s cancel-offer RPC and `chia/cmds/wallet.py`). A wallet user who has accepted (or is about to cancel) a maliciously crafted offer from a counterparty can have their wallet process hang or consume excessive CPU while computing which coins must be spent to cancel the trade, halting further transaction processing on the wallet/RPC side for that call. This matches the accepted "spend-triggered transaction-processing halt" impact category: it is a wallet-action-triggered denial of local transaction processing, reachable by an ordinary offer counterparty without any privileged access, mirroring the "uncontrolled resource consumption" class from the source advisory.

### Likelihood Explanation
Medium. Exploitation requires convincing a wallet user to receive/hold a maliciously structured offer (a normal trading flow event, not privileged access), and requires the attacker to construct an offer whose coin spends form a large, densely-chained announcement dependency graph. Building such an offer is straightforward CLVM/condition construction and does not require any signature forgery, since the assertions/announcements only need to be syntactically present in the puzzle's output conditions for `run_with_cost` to enumerate them; the offer's validity for on-chain settlement is a separate matter from whether the wallet chooses to process it locally for cancellation.

### Recommendation
Bound the amount of work `get_cancellation_coins()`/`detect_dependent_coin()` can perform relative to the number of coin spends in an offer (e.g., impose a cap on the number of non-addition coin spends processed, or index announcements/dependencies with hash maps and single-pass graph traversal instead of repeated full-dictionary scans within nested loops) so that runtime scales linearly (or near-linearly) with `n` rather than cubically/quartically. Additionally, consider rejecting or truncating processing of offers whose coin-spend count exceeds a sane bound before invoking this routine.

### Proof of Concept

2. For each coin `i`, include a `CREATE_COIN_ANNOUNCEMENT` (opcode 60) with a unique message, and an `ASSERT_COIN_ANNOUNCEMENT` (opcode 61) referencing the announcement hash produced by coin `i+1`, forming a long dependency chain (or, worse, have many coins each depend on announcements from many other coins to maximize the `deps[name] × announcement_dict` product).
3. Call `Offer.get_cancellation_coins()` on this offer (as done internally by `trade_manager.py` when preparing a cancellation transaction, reachable via the wallet RPC "cancel offer" endpoint).
4. Observe that runtime grows super-linearly with `N` due to the nested `while True` loops in `get_cancellation_coins()` re-scanning `dependencies`/`announcements` on every removal, and the `O(names × deps × announcements)` cost of `detect_dependent_coin()` on every outer-loop iteration, consistent with the `chia/wallet/trading/offer.py:425-470` and `chia/wallet/trading/offer.py:53-63` code paths cited above.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None

    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
