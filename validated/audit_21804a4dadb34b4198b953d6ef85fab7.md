### Title
Attacker-controlled `ThresholdKeys` parameters trigger quadratic Lagrange interpolation during deserialization - (File: `crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::read` accepts attacker-supplied `t` and `n` values as large as `u16::MAX`, reads `n` verification shares, then `ThresholdKeys::new` computes a Lagrange interpolation coefficient for each of the first `t` participants. Each coefficient calculation iterates over all `t` participants and performs a field inversion, making a validly encoded key with `t = n = 65,535` require more than 4 billion field multiplications plus 65,535 inversions.

### Finding Description
`ThresholdKeys::read` reads two attacker-controlled `u16` values for `t` and `n`, reads `n` field/group elements, and then passes them to `ThresholdKeys::new` without imposing a practical protocol bound beyond `t <= n`. [1](#0-0) [2](#0-1) [3](#0-2) 

`ThresholdParams::new` explicitly permits this worst case because it only rejects zero, `t > n`, or `i > n`; `Participant::new` only rejects zero. [4](#0-3) [5](#0-4) 

For Lagrange keys, `ThresholdKeys::new` constructs `1..=t` and calls `interpolation_factor` once per participant. [6](#0-5)  Each call loops over every included participant and then unconditionally performs a field inversion. [7](#0-6)  Consequently, deserialization performs `O(n^2)` field arithmetic for a small serialized input, analogous to the reported excessive-iteration flaw.

### Impact Explanation
An unprivileged party who can supply serialized threshold-key bytes to `ThresholdKeys::read` can cause a validly formatted object of only a few megabytes to consume CPU work proportional to approximately `65,535^2`. [8](#0-7)  The object does not need malformed points or invalid parameters; it only needs `t = n = 65,535`, `i = 1`, Lagrange interpolation, a scalar, and `65,535` valid point encodings. [5](#0-4) [2](#0-1) 

This can stall the deserializing party's key-processing path and prevent it from reaching signing or verification work, leaving associated key material operationally unavailable.

### Likelihood Explanation
The attacker controls the serialized `t`, `n`, `i`, interpolation tag, scalar, and verification-share encodings because `ThresholdKeys::read` consumes them directly from an arbitrary `Read`. [9](#0-8)  The maximum `u16` value is accepted, so no protocol participation, invalid signature, leaked secret, or malformed encoding is required. [5](#0-4) 

The issue requires a caller to deserialize attacker-supplied `ThresholdKeys`, which is one of the explicitly reachable untrusted-byte paths. Its impact is bounded by the `u16` representation, but the permitted bound is still large enough to induce excessive quadratic work.

### Recommendation
Before reading `n` group elements, validate `t` and `n` against the caller's expected or protocol-mandated threshold parameters rather than accepting every `u16` pair. More generally, avoid recomputing each Lagrange coefficient independently: compute coefficients with an `O(n)` prefix/suffix-product formulation, batch inversions, and/or enforce a conservative serialized participant limit.

### Proof of Concept
```rust
// Conceptual serialization accepted by ThresholdKeys::<C>::read.
let t: u16 = u16::MAX;
let n: u16 = u16::MAX;
let i: u16 = 1;

let mut encoded = Vec::new();
encoded.extend((C::ID.len() as u32).to_le_bytes());
encoded.extend(C::ID);
encoded.extend(t.to_le_bytes());
encoded.extend(n.to_le_bytes());
encoded.extend(i.to_le_bytes());
encoded.push(1); // Interpolation::Lagrange
encoded.extend(C::F::ONE.to_repr().as_ref());

// Supply every required verification share.
for _ in 1..=n {
    encoded.extend(C::generator().to_bytes().as_ref());
}

// This reads all points and then performs ~65,535 * 65,535 scalar-loop work.
let _ = ThresholdKeys::<C>::read(&mut encoded.as_slice());
```

The expensive path is `read` -> `ThresholdKeys::new` -> `Interpolation::Lagrange::interpolation_factor`, where `interpolation_factor` is invoked `t` times and itself scans all `t` participants. [6](#0-5) [7](#0-6)
