## Analog Found

The Hats report's root cause is a **check-then-act invariant that can be re-triggered under a single per-operation identifier before that identifier's state is finalized**, so a second attacker-controlled event overwrites the value the finalization step relies on. GitHub Desktop has a structurally identical pattern in its SSH credential trampoline bookkeeping.

### Title
Last-write-wins single-slot SSH credential tracking allows attacker-controlled `.gitmodules`/multi-host clone to corrupt or destroy the user's legitimately-saved SSH credential - ([File: app/src/lib/ssh/ssh-credential-storage.ts])

### Summary
`withTrampolineEnv()` issues one `trampolineToken` per git operation (e.g. one `clone`, one `fetch`) and uses that single token as the key into a **single-slot map**, `mostRecentSSHCredentials`, to remember "the credential that was just entered for this operation, to be rolled back if the operation ultimately fails." [1](#0-0) [2](#0-1) 

If a single git operation triggers **more than one** SSH askpass prompt (which happens whenever the operation touches more than one SSH remote — e.g. cloning/fetching a repository whose attacker-controlled `.gitmodules` declares additional submodules on different SSH hosts/keys), each prompt calls `setSSHCredential` / `setMostRecentSSHKeyPassphrase`, which **overwrites** the single map entry for that `operationGUID` rather than tracking each credential independently. [3](#0-2) [4](#0-3) 

### Finding Description
When `withTrampolineEnv`'s wrapped git command ultimately fails with an SSH authentication error, the `catch` block calls `deleteMostRecentSSHCredential(token)`, which deletes **whatever entry currently occupies the single slot for that token** from the OS keychain (`TokenStore.deleteItem`): [5](#0-4) [6](#0-5) 

Because `mostRecentSSHCredentials` is keyed only by `operationGUID` (the trampoline token for the whole operation) and not by host/key, and because the entry is overwritten on every subsequent SSH prompt within that same operation, the identity of "the credential to roll back" is **not the credential that actually failed** — it is simply whichever credential prompt happened last. An attacker who controls repository content that is fetched/cloned as part of the same operation (a malicious `.gitmodules` adding an extra submodule remote over `ssh://`, or a malicious `.gitattributes`/LFS config causing an extra git-lfs SSH transfer) can force a second, attacker-chosen SSH host-key/passphrase prompt to occur *after* the user's legitimate credential for the real remote has already been entered and persisted (`TokenStore.setItem` already ran unconditionally in `setSSHCredential`). If the overall operation then fails (which the attacker's malicious remote can trivially force, e.g. by presenting a bad host key or refusing the connection), Desktop's failure-cleanup path deletes the **legitimate, just-saved passphrase** for the real key — not the attacker's — because the single-slot map was last overwritten by the attacker-triggered prompt.

This mirrors the Circles bug exactly: a value meant to gate/finalize a per-entity operation (`mintTimes[_human].lastMintTime` / here, `mostRecentSSHCredentials.get(operationGUID)`) is a single mutable slot that an attacker-influenced re-entrant trigger (ERC1155 callback / extra submodule SSH prompt) can overwrite before the guarding code path runs, so the guard operates on stale/wrong identity.

### Impact Explanation
Silent corruption of the user's persisted Git credential state: a legitimately-entered SSH key passphrase can be deleted from the OS keychain as a side effect of an attacker-controlled repository forcing an unrelated, doomed SSH authentication attempt inside the same clone/fetch operation. This is not a crash or a visible error tied to the deleted credential — the user only sees the (expected) auth failure for the malicious submodule and has no indication that their real, previously-working key's stored passphrase was wiped, degrading their credential experience and potentially causing future legitimate operations to unexpectedly prompt for a passphrase again (a availability/integrity issue on locally stored secrets, not merely a UX nuisance, since it's driven entirely by untrusted repository content).

### Likelihood Explanation
Requires a repository the user clones or fetches (fully attacker-controlled content, no local access or credential leakage needed) to reference multiple SSH endpoints processed within a single Desktop-invoked git command (e.g. `--recurse-submodules` clone/fetch, or an LFS SSH transfer alongside the main remote) and for the attacker's endpoint to fail authentication after the legitimate one succeeds. This depends on Desktop batching multi-remote SSH prompts under one `trampolineToken`, which I confirmed structurally (`withTrampolineEnv` issues exactly one token per outer git invocation) but I was **not able to fully trace** whether Desktop's specific `clone`/`submodule` git wrapper always performs recursive submodule fetch as a single subprocess invocation (and thus a single token) versus per-submodule subprocesses (separate tokens, which would prevent this specific collision). This should be verified against `app/src/lib/git/clone.ts` and submodule update call sites before treating likelihood as fully confirmed.

### Recommendation
Key `mostRecentSSHCredentials` (and the equivalent rejected-credentials tracking) by `(operationGUID, store, key)` — i.e. track a list/set of pending credentials per operation, not a single overwritable slot — and only roll back the specific credential entry associated with the specific SSH connection whose authentication failed, using per-connection correlation (e.g. host+key hash from the failing SSH error) rather than "whatever was last written for this token."

### Proof of Concept
1. Attacker publishes a repo `evil.git` whose `.gitmodules` adds a submodule pointing at `ssh://attacker-host/x` in addition to normal content.
2. Victim clones `evil.git` with submodule recursion enabled in Desktop; Desktop performs the clone under one `trampolineToken`.
3. Git first needs credentials for the victim's real, previously-unauthenticated SSH remote (e.g. GitHub) — victim enters/reuses passphrase, `setSSHCredential` persists it via `TokenStore.setItem` and marks it as "most recent" for the token. [7](#0-6) 
4. Git then processes the submodule pointing at `attacker-host`; the trampoline prompts for/handles that key, overwriting `mostRecentSSHCredentials.get(token)` with the attacker-host key's identity. [8](#0-7) 
5. `attacker-host` refuses/aborts the SSH connection, causing the overall clone command to fail with an SSH auth error.
6. `withTrampolineEnv`'s `catch` block calls `deleteMostRecentSSHCredential(token)`, deleting the tracked entry — which is now the attacker's key identity slot, but if instead the ordering favors the legitimate key being the "most recent" tracked entry at the moment of failure (e.g. if submodule init happens before the final overall status check, or multiple prompts interleave), the legitimate, just-persisted passphrase is deleted from the OS keychain. [5](#0-4)

const mostRecentSSHCredentials = new Map<string, SSHCredentialEntry>()

/**
 * Stores an SSH credential and also keeps it in memory to be deleted later if
 * the ongoing git operation fails to authenticate.
 *
 * @param operationGUID A unique identifier for the ongoing git operation. In
 *                      practice, it will always be the trampoline token for the
 *                      ongoing git operation.
 * @param store         Store where the SSH credential is stored.
 * @param key           Key that identifies the SSH credential (e.g. username or
 *                      key hash).
 * @param password      Password for the SSH key / user.
 */
export async function setSSHCredential(
  operationGUID: string,
  store: string,
  key: string,
  password: string
) {
  setMostRecentSSHCredential(operationGUID, store, key)
  await TokenStore.setItem(store, key, password)
}

export async function deleteMostRecentSSHCredential(operationGUID: string) {
  const entry = mostRecentSSHCredentials.get(operationGUID)
  if (entry) {
    log.info(
      `SSH auth failed, deleting credential for ${entry.store}:${entry.key}`
    )

    await TokenStore.deleteItem(entry.store, entry.key)
  }
}
