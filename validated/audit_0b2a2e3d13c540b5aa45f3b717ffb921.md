## Analysis Result

I traced the external report's core pattern — an **attacker-controlled input that bypasses validation and is written into a "time" field consumed by downstream business logic without the documented range/format being enforced** — to Protobuf's public ProtoJSON parsing path for the well-known `Timestamp` type in upb.

### Title
Missing upper-bound and calendar-field range validation in upb JSON `Timestamp` decoder allows out-of-spec seconds/date values to pass parsing - (File: `upb/json/decode.c`)

### Summary
`jsondec_timestamp()` in upb's JSON decoder parses a RFC3339-like timestamp string into `seconds`/`nanos` fields of `google.protobuf.Timestamp`. It validates only that the resulting `seconds` is not below `-62135596800` (the documented minimum, `0001-01-01T00:00:00Z`), but never checks the documented upper bound (`253402300799`, `9999-12-31T23:59:59Z`), nor does it validate that the individual calendar components (`month`, `day`, `hour`, `min`, `sec`) are within their valid ranges (1-12, 1-31, 0-23, 0-59, 0-59) before they are fed into `jsondec_unixtime()`/`jsondec_epochdays()`.

### Finding Description
`jsondec_tsdigits()` only enforces digit-count and separator-character matching — it does not perform range checks on the parsed integer value. [1](#0-0) 

These unchecked components are passed straight into date-arithmetic: [2](#0-1) 

`jsondec_timestamp()` then only checks the *lower* bound of the resulting `seconds`, never the upper bound documented for `Timestamp` (`9999-12-31T23:59:59Z` / `253402300799`): [3](#0-2) [4](#0-3) 

By contrast, the corresponding JSON **encoder** for `Timestamp` correctly enforces both bounds, confirming the decoder's asymmetric/incomplete validation is a real gap rather than an intentional design choice: [5](#0-4) 

The upb JSON codec is shared by the core C runtime and is compiled directly into the PHP and Ruby native extensions, so this same code path is reachable from those language bindings as well: [6](#0-5) [7](#0-6) 

The conformance suite exercises the *documented* boundary conditions (5-digit year, which fails earlier due to the fixed 4-digit/separator scan in `jsondec_tsdigits`), but does not exercise malformed month/day/hour/min/sec values or seconds that exceed the upper bound via offset arithmetic, so this gap is not caught by existing tests: [8](#0-7) 

### Impact Explanation
This is the closest structural analog to the DSWarp report: a value meant to represent a bounded, validated point in time is accepted by the parser without enforcing the documented invariant (the valid `Timestamp` range), and the corrupted/out-of-range value is silently stored into the message that a trusted consuming application later reads via `getSeconds()`/`getNanos()` and uses for time-based business logic (expiry checks, cache invalidation, stability/cooldown-style computations, etc.). Unlike DSWarp's public `warp()` (an unprotected write to global mutable state), here the untrusted "time write" comes through the normal, public ProtoJSON parse API on a single message field — well within the assumed attacker capability (bounded JSON input via a supported public parse API). The impact is confined to producing a `Timestamp`/date value outside its documented contract; it does not itself cause memory corruption, so it should be scoped as a data-integrity/spec-conformance issue rather than memory safety.

### Likelihood Explanation
Low complexity: constructing a JSON string like `"9999-99-99T99:99:99Z"` requires no special access and matches the digit-count/separator pattern `jsondec_tsdigits` checks, but 99 for month/day/hour/min/sec are never range-checked, and the resulting computed `seconds` is never checked against the upper bound. This is reachable by any consumer of the public `JsonToMessage`/`Message::FromJson`-style APIs in C, PHP, and Ruby that use the shared upb JSON decoder.

### Recommendation
- In `jsondec_tsdigits()` (or immediately after each call in `jsondec_timestamp()`), validate `mon` (1-12), `day` (1-31, ideally per-month/leap-year aware), `hour` (0-23), `min` (0-59), `sec` (0-59) and reject out-of-range values with `jsondec_err(d, "Malformed timestamp")`.
- Add the missing upper-bound check symmetric to the encoder: reject `seconds.int64_val > 253402300799` in `jsondec_timestamp()`, mirroring the check already present in `jsonenc_timestamp()`.
- Add conformance tests for out-of-range calendar components (e.g., month 13, day 32, hour 25) and for timestamps whose computed seconds exceed the documented maximum via valid-looking digit counts.

### Proof of Concept
Feeding the following JSON into a trusted schema's `Timestamp`-typed field via the public ProtoJSON parse API of the upb-backed runtimes (C core, PHP, Ruby) is accepted without error, even though it is not a valid calendar date and is not rejected against the documented `Timestamp` range:
```json
{"optionalTimestamp": "9999-99-99T99:99:99Z"}
```
Tracing execution: `jsondec_tsdigits` accepts `year=9999, mon=99, day=99, hour=99, min=99, sec=99` (digit-count/separator checks only) [9](#0-8)  → `jsondec_unixtime`/`jsondec_epochdays` compute an arbitrary `seconds` value from these out-of-range components [2](#0-1)  → only the lower-bound check is applied before the value is committed to the message [4](#0-3) , so no `jsondec_err` is raised and the resulting out-of-spec `Timestamp` is returned to the caller.

static int jsondec_tsdigits(jsondec* d, const char** ptr, size_t digits,
                            const char* after) {
  uint64_t val;
  const char* p = *ptr;
  const char* end = p + digits;
  size_t after_len = after ? strlen(after) : 0;

  UPB_ASSERT(digits <= 9); /* int can't overflow. */

  if (jsondec_buftouint64(d, p, end, &val) != end ||
      (after_len && memcmp(end, after, after_len) != 0)) {
    jsondec_err(d, "Malformed timestamp");
  }

  UPB_ASSERT(val < INT_MAX);

  *ptr = end + after_len;
  return (int)val;
}

/* jsondec_epochdays(1970, 1, 1) == 1970-01-01 == 0. */
int jsondec_epochdays(int y, int m, int d) {
  const uint32_t year_base = 4800; /* Before min year, multiple of 400. */
  const uint32_t m_adj = m - 3;    /* March-based month. */
  const uint32_t carry = m_adj > (uint32_t)m ? 1 : 0;
  const uint32_t adjust = carry ? 12 : 0;
  const uint32_t y_adj = y + year_base - carry;
  const uint32_t month_days = ((m_adj + adjust) * 62719 + 769) / 2048;
  const uint32_t leap_days = y_adj / 4 - y_adj / 100 + y_adj / 400;
  return y_adj * 365 + leap_days + month_days + (d - 1) - 2472632;
}

static int64_t jsondec_unixtime(int y, int m, int d, int h, int min, int s) {
  return (int64_t)jsondec_epochdays(y, m, d) * 86400 + h * 3600 + min * 60 + s;
}
