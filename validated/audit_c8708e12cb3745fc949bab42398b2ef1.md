### Title
Tier-based 2x lock bonus in `ArbWomUp3.incentiveDeposit` can be farmed by transiently inflating `mWomSV.getUserTotalLocked` right before the call - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.getUserTier`, `calDoubledCounted`, and `getRewardAmount` compute a user's reward tier purely from the *current* instantaneous balance returned by `mWomSV.getUserTotalLocked(_account)`, with no time-weighting, snapshotting, or minimum holding period. An attacker can lock a large amount of mWOM into `mWomSV` in one transaction, immediately call `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, false, 2)` to be assessed at an inflated tier (receiving the `rewardToSend * 2` lock bonus), and then call `mWomSV.startUnlock` right after to begin exiting that lock, since `getUserTotalLocked` already excludes cooling-down balances.

### Finding Description
`ArbWomUp3.getRewardAmount` for `_lock == true` (mode 2) computes:
```
uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
``` [1](#0-0) 
and `calDoubledCounted`/`getUserTier` likewise key off `mWomSV.getUserTotalLocked(_account)` alone [2](#0-1) .

Crucially, `getRewardAmount` is invoked in `incentiveDeposit` **before** `_deposit` is executed, so the balance used for tier calculation is whatever the attacker already has parked in `mWomSV` prior to this transaction - it does not need to be "real" long-term stake:
```
uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2);
if (_mode == 2) rewardToSend = rewardToSend * 2;
_deposit(msg.sender, _convertRatio, _amount, _mode);
``` [3](#0-2) 

`mWomSV.getUserTotalLocked` simply reads the current staking balance from `MasterMagpie`, minus whatever is already in cooldown:
```
function getUserTotalLocked(address _user) override public view returns (uint256 _lockAmount) {
    (uint256 _amountInMasterMagpie, ) = IMasterMagpie(masterMagpie).stakingInfo(address(this), _user);
    _lockAmount = _amountInMasterMagpie - getUserAmountInCoolDown(_user);
}
``` [4](#0-3) 

`mWomSV.lockFor`/`lock` immediately increase this balance with no vesting delay [5](#0-4) , and `startUnlock` immediately moves the amount into the cooldown mapping, which is subtracted from `getUserTotalLocked` right away (though actual token withdrawal via `unlock` still requires waiting `coolDownInSecs`) [6](#0-5) .

Exploit flow:
1. Attacker calls `mWomSV.lockFor(largeAmount, attacker)` (or `lock`), inflating `getUserTotalLocked(attacker)`.
2. In a following transaction (can be same block via bundling), attacker calls `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, false, 2)`. `getRewardAmount` sees the inflated `accumulated` value, computes reward using higher-tier multipliers for the marginal portion, and `incentiveDeposit` doubles it (`rewardToSend * 2`) before locking MGP for the attacker via `vlMGP.lockFor`.
3. Attacker calls `mWomSV.startUnlock(largeAmount)` to begin unwinding the temporary lock. `getUserTotalLocked` drops immediately, but the inflated MGP reward has already been paid/locked to the attacker in step 2 and cannot be clawed back.
4. After `coolDownInSecs` elapses, attacker calls `unlock` to retrieve the mWOM, suffering no permanent capital loss (aside from opportunity cost during cooldown).

No existing modifier (`whenNotPaused`, `nonReentrant`) prevents this because it is a legitimate multi-transaction sequence, not reentrancy - `nonReentrant` only guards against re-entering within a single call. There is no check that the qualifying `mWomSV` balance has been held for any minimum duration, nor any snapshotting of tier eligibility prior to the deposit call.

### Impact Explanation
This allows an attacker to receive MGP rewards (via `vlMGP.lockFor`) corresponding to a stake tier they do not genuinely/durably hold, disproportionately draining `ArbWomUp3`'s available MGP balance relative to the actual, sustained qualifying deposits from other users. This matches the "theft of unclaimed yield" / protocol insolvency impact class, since the contract's finite `mgp` balance (checked via `mgpleft` cap in `getRewardAmount`) is distributed based on manipulable instantaneous state rather than genuine commitment.

### Likelihood Explanation
- Requires only unprivileged actions: acquiring/holding mWOM/WOM and calling public functions (`mWomSV.lockFor`, `ArbWomUp3.incentiveDeposit`, `mWomSV.startUnlock`/`unlock`).
- Capital is temporarily locked (subject to `coolDownInSecs`) but not permanently lost, so the strategy is repeatable across cooldown cycles or with multiple funded accounts/pooled capital (e.g., via a flash-loan-funded lock if a lending market for mWOM/WOM tokens exists, though not strictly required).
- The reward tiers/multipliers (`rewardTier`, `rewardMultiplier`) determine the magnitude of gain; larger gaps between tiers make the attack more lucrative.
- No special privileges or governance access needed, making this feasible for any sufficiently capitalized attacker.

### Recommendation
Base tier/bonus eligibility on a time-weighted or minimum-duration-held balance (e.g., require the qualifying `mWomSV` lock to have existed for a minimum period before the `incentiveDeposit` call, or use `getRewardablePercentWAD`-style weighting), or snapshot/lock the qualifying balance at the time of deposit and forfeit/claw back the bonus if the account starts unlocking that balance within a cooldown-linked vesting window. Alternatively, restrict the multiplier calculation to only the mWOM being locked as part of the same `incentiveDeposit` transaction (mode 2's own `_deposit` lock), rather than any externally-held `mWomSV` balance.

### Proof of Concept
Foundry test outline:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie`, `vlMGP`, and mock `mWOM`/`wom`/`mgp` tokens; fund `ArbWomUp3` with `mgp`.
2. Configure `rewardTier`/`rewardMultiplier` with a meaningful gap between tier 0 and a higher tier.
3. As attacker: mint/acquire mWOM, call `mWomSV.lockFor(largeAmount, attacker)` to push `getUserTotalLocked(attacker)` past the higher tier threshold.
4. Call `ArbWomUp3.incentiveDeposit(smallAmount, ratio, false, 2)`; capture `rewardToSend` from emitted `VLMGPRewarded` event and the resulting `vlMGP` balance for attacker.
5. Immediately call `mWomSV.startUnlock(largeAmount)`, then warp past `coolDownInSecs` and call `mWomSV.unlock(slotIndex)` to retrieve the original mWOM.
6. Assert: (a) `getUserTotalLocked(attacker)` after step 5 is back near zero, contradicting the tier used to compute the reward in step 4; (b) the MGP amount locked for attacker in step 4 corresponds to the inflated tier multiplier, not the tier attacker holds moments later; (c) compare against a control run where attacker never held the large `mWomSV` lock, showing a materially smaller reward for the identical `smallAmount` deposit.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
