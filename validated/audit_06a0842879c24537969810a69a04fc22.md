Based on my research, the test evidence at `evmd/tests/ibc/ibc_middleware_test.go:1888-1900` explicitly confirms that a callback with insufficient gas produces `expError: "out of gas"` that propagates through `transferStack.OnAcknowledgementPacket` / `OnTimeoutPacket` as a hard error, not a swallowed/best-effort failure. This confirms the relevant code path is a real analog to the HMX "stuck queue" bug class.

### Title
Attacker-controlled `src_callback` gas griefing can permanently stall ICS-20 ack/timeout processing and freeze escrowed funds - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`IBCOnAcknowledgementPacketCallback` and `IBCOnTimeoutPacketCallback` execute an EVM call to a contract address chosen by the original IBC packet **sender** (via the `src_callback` memo field), using a gas limit also chosen by the sender (`cbData.CommitGasLimit`). Unlike the HMX queue processing (which wraps operations in try/catch so a bad actor cannot brick the whole queue), errors from these callback calls — including `"out of gas"` — are returned as hard errors that propagate up through `OnAcknowledgementPacket`/`OnTimeoutPacket` into the IBC channel/packet-commitment-deletion logic itself.

### Finding Description [1](#0-0)  and [2](#0-1)  show that:
- The callback contract address and gas limit come from the packet's `memo` field, fully controlled by the original packet sender: [3](#0-2) .
- A dedicated infinite gas meter is created bounded by `cbData.CommitGasLimit` [4](#0-3) , then `CallEVM` is invoked and its resulting gas usage is deducted from the *original* `ctx.GasMeter()` [5](#0-4)  and [6](#0-5) .
- Critically, in `IBCOnTimeoutPacketCallback`, the actual `CallEVM` executes against `ctx` (the real relayer transaction gas meter), not `cachedCtx`, while the requested gas cap is read from `cachedCtx.GasMeter().GasRemaining()` (a freshly-created meter that simply returns `cbData.CommitGasLimit`) — [7](#0-6) . This decouples the requested EVM gas cap from the real transaction's remaining gas.
- If either callback errors (including "out of gas"), the function returns a non-nil error [8](#0-7) , and the confirmed test behavior shows this manifests as a hard `"out of gas"` failure of the whole ack/timeout message: [9](#0-8) .
- This error is not swallowed anywhere up the stack — `x/erc20/ibc_middleware.go`'s `OnAcknowledgementPacket` immediately returns any error from the underlying `im.Module.OnAcknowledgementPacket` call (which wraps the callbacks middleware) without any fallback: [10](#0-9) . Note this is unlike the erc20-conversion-only failure path in `x/erc20/keeper/ibc_callbacks.go`, which is explicitly designed to never fail (falls back to bank coin) [11](#0-10) .

This is directly analogous to the HMX bug class: a queue-like sequential process (IBC packet lifecycle processing per channel) can be forced to always revert by an attacker who controls an external call's target and gas budget, without the surrounding code applying an `ExcessivelySafeCall`-style bound or a try/catch that guarantees forward progress regardless of callback outcome.

### Impact Explanation
A malicious IBC packet sender deploys a source-chain contract as the `src_callback` target that always burns gas (e.g., an infinite/expensive loop bounded only by the block gas limit) and sets a large `gas_limit` in the memo. When the packet acknowledgement or timeout is relayed:
- The acknowledgement/timeout message processing fails with "out of gas" every time it is retried, because the same malicious contract logic and gas requirement is replayed deterministically each relay attempt.
- If this occurs on an **ORDERED** channel, the packet commitment can never be cleared, permanently halting all subsequent packet flow (sends/receives) on that channel — a permanent freeze of channel throughput and of the escrowed tokens tied to that channel, since the underlying transfer-module escrow refund logic (which depends on `OnAcknowledgementPacket`/`OnTimeoutPacket` succeeding) never executes.
- Even on unordered channels, the sender's own escrowed tokens for that specific packet become permanently unrecoverable (the refund only happens after this callback path succeeds).

This matches the required Critical impact: "permanent freezing, locking ... of user funds ... escrowed assets."

### Likelihood Explanation
- The trigger is fully unprivileged: any account can send an ICS-20 transfer with a `src_callback` memo pointing to a self-deployed contract they control, per the documented design ("only the IBC packet sender can set the callback") [12](#0-11) .
- The gas-griefing pattern is deterministic and repeatable on every relay attempt (unlike race-condition bugs), so it reliably produces the same "out of gas" failure each time, guaranteeing the stuck state persists.
- Confirmed by existing test coverage showing insufficient/mis-sized gas already produces a propagated `"out of gas"` error rather than a caught/ignored one [13](#0-12) .

### Recommendation
- Wrap the `CallEVM` invocations in `IBCOnAcknowledgementPacketCallback` and `IBCOnTimeoutPacketCallback` so that callback failures (including out-of-gas) never propagate as a hard error that blocks the underlying IBC ack/timeout state transitions (escrow refund, packet commitment deletion) — mirror the fail-safe pattern already used in `x/erc20/keeper/ibc_callbacks.go`, where conversion failures are swallowed and a fallback path taken.
- Cap the gas actually chargeable to the parent transaction's gas meter independent of the attacker-supplied `cbData.CommitGasLimit`, and ensure `CallEVM` executes against the intended `cachedCtx` (not the live `ctx`) consistently in both ack and timeout paths.
- Consider bounding revert-data size and applying an explicit, hard gas stipend (e.g., a fixed portion of the tx's remaining gas) rather than trusting sender-controlled `gas_limit` values.

### Proof of Concept
1. Attacker deploys `MaliciousCallback` implementing `ICallbacks.onPacketAcknowledgement`/`onPacketTimeout` that runs an unbounded/expensive loop consuming all forwarded gas.
2. Attacker sends an ICS-20 transfer (`MsgTransfer`) over an ORDERED channel with memo:
   ```json
   {"src_callback": {"address": "<MaliciousCallback>", "gas_limit": "10000000"}}
   ```
3. The counterparty chain relays back an acknowledgement (or the packet times out).
4. Any relayer submitting `MsgAcknowledgement`/`MsgTimeout` triggers `IBCOnAcknowledgementPacketCallback`/`IBCOnTimeoutPacketCallback`, which calls into `MaliciousCallback`, exhausting gas and returning `"out of gas"` [5](#0-4) .
5. The error propagates through `x/erc20/ibc_middleware.go` `OnAcknowledgementPacket`/`OnTimeoutPacket` [14](#0-13) , causing the message to fail every time it is retried — the packet commitment is never cleared and (on an ordered channel) the channel is permanently stalled, freezing the escrowed funds for that transfer and blocking all subsequent traffic on the channel.

**Note on verification limits:** I was unable to directly inspect the vendored `ibc-go` `callbacks` middleware source in this index (only this repo's own `x/ibc/callbacks` wrapper was available), so I cannot fully confirm at the ibc-go library level whether `ProcessCallback` in some ibc-go versions independently recovers/swallows contract-keeper errors before they reach the channel keeper. However, the test suite in this repository explicitly asserts that an underprovisioned/gas-griefed callback surfaces as a propagated `"out of gas"` error at the `OnAcknowledgementPacket`/`OnTimeoutPacket` return value, which is the observable behavior that drives the impact described above.

func (k ContractKeeper) IBCOnAcknowledgementPacketCallback(
	ctx sdk.Context,
	packet channeltypes.Packet,
	acknowledgement []byte,
	relayer sdk.AccAddress,
	contractAddress,
	packetSenderAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.SourceCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	if len(cbData.Calldata) != 0 {
		return errorsmod.Wrap(types.ErrInvalidCalldata, "acknowledgement callback data should not contain calldata")
	}

	sender, err := utils.HexAddressFromBech32String(packetSenderAddress)
	if err != nil {
		return errorsmod.Wrapf(err, "unable to parse packet sender address %s", packetSenderAddress)
	}

	contractAddr := common.HexToAddress(contractAddress)

	// Check if the contract address contains code.
	// This check is required because if there is no code, the call will still pass on the EVM side,
	// but it will ignore the calldata and funds may get stuck.
	if !k.evmKeeper.IsContract(ctx, contractAddr) {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "provided contract address is not a contract: %s", contractAddr)
	}

	abi, err := callbacksabi.LoadABI()
	if err != nil {
		return err
	}

	// Call the onPacketAcknowledgement function in the contract
	// NOTE: use the cached ctx for the EVM calls.
	res, err := k.evmKeeper.CallEVM(cachedCtx, *abi, sender, contractAddr, true, math.NewIntFromUint64(cachedCtx.GasMeter().GasRemaining()).BigInt(), "onPacketAcknowledgement",
		packet.GetSourceChannel(), packet.GetSourcePort(), packet.GetSequence(), packet.GetData(), acknowledgement)
	if err != nil {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "EVM returned error: %s", err.Error())
	}

	// Consume the actual gas used on the original callback context.
	ctx.GasMeter().ConsumeGas(res.GasUsed, "callback onPacketAcknowledgement")
	if ctx.GasMeter().IsOutOfGas() {
		return errorsmod.Wrapf(types.ErrCallbackFailed, "out of gas")
	}

	writeFn()

	return nil
}

func (im IBCMiddleware) OnAcknowledgementPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	acknowledgement []byte,
	relayer sdk.AccAddress,
) error {
	var ack channeltypes.Acknowledgement
	if err := transfertypes.ModuleCdc.UnmarshalJSON(acknowledgement, &ack); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet acknowledgement: %v", err)
	}

	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet data: %s", err.Error())
	}

	if err := im.Module.OnAcknowledgementPacket(ctx, channelVersion, packet, acknowledgement, relayer); err != nil {
		return err
	}

	return im.keeper.OnAcknowledgementPacket(ctx, packet, data, ack)
}

// OnAcknowledgementPacket responds to the success or failure of a packet
// acknowledgement written on the receiving chain. If the acknowledgement was a
// success then nothing occurs. If the acknowledgement failed, then the sender
// is refunded and then the IBC Coins are converted to ERC20.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}
