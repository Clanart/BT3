### Title
Verifier::is_deposit_valid never binds a ReplacementDeposit's outpoint to old_move_txid's actual spend, allowing multiple self-funded replacements per old_move_txid - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` validates a `ReplacementDeposit` purely by checking that the CURRENT `deposit_outpoint`'s own script pubkey, value, and confirmation height match the `ReplacementDepositScript(nofn_xonly_pk, old_move_txid)` + security-council-multisig address. It never verifies that `deposit_outpoint` is actually the transaction output that the security council produced when spending `old_move_txid`'s move-to-vault UTXO. This lets anyone self-fund an arbitrary second (or first) UTXO with that same script, citing any `old_move_txid`, and have it signed as a legitimate replacement.

### Finding Description
The claimed binding is: `deposit_outpoint == spending_output(old_move_txid_vault_utxo)`, i.e., a `ReplacementDeposit`'s `deposit_outpoint` must be the actual output created when the security-council multisig spent the old move-to-vault transaction's vault output. This binding is never checked.

In `core/src/verifier.rs`, `is_deposit_valid` (lines 541-732) computes `expected_scriptpubkey` from `deposit_data.get_deposit_scripts(...)`, which for `DepositType::ReplacementDeposit` builds `ReplacementDepositScript::new(nofn_xonly_pk, replacement_deposit_data.old_move_txid)` plus `Multisig::from_security_council(...)` [1](#0-0) . It then fetches the transaction at `deposit_outpoint.txid` on chain and checks only: (1) `deposit_txout_in_chain.value == bridge_amount`, (2) `deposit_txout_in_chain.script_pubkey == expected_scriptpubkey`, and (3) block height `>= start_height` [2](#0-1) . Nowhere does this function look up `old_move_txid`'s vault output, determine whether/how it was spent, or compare that spend's resulting outpoint/txid to the `deposit_outpoint` under validation.

Because `nofn_xonly_pk`, `old_move_txid`, and the security council's public keys are all public, anyone can independently compute the exact same Taproot address via `generate_replacement_deposit_address` / `ReplacementDepositScript::to_script_buf` [3](#0-2) [4](#0-3) , fund it themselves with exactly `bridge_amount`, wait for confirmation past `start_height`, and submit it via `Aggregator::new_deposit` with `DepositData::ReplacementDeposit{ old_move_txid }` (parsed in `core/src/rpc/parser/mod.rs:363-374`). `is_deposit_valid` will pass every check identically to the way it would for the legitimate security-council-produced replacement, because the checks are entirely local to the candidate outpoint's own script/value/height and do not trace lineage back to `old_move_txid`.

The persistence layer does not close this gap either: `insert_deposit_data_if_not_exists` and the `deposits` table enforce uniqueness only on `deposit_outpoint` (`deposit_outpoint text unique not null`), not on `old_move_txid` or on `move_to_vault_txid` being replaced [5](#0-4) [6](#0-5) . So a second, unrelated outpoint citing the same `old_move_txid` inserts as a brand-new row/deposit_id with no conflict and no cross-check against any prior replacement of the same `old_move_txid`.

Both `deposit_sign` and `deposit_finalize` call `is_deposit_valid` before proceeding to N-of-N signing [7](#0-6) [8](#0-7) , so this local-only check is the sole gate standing between an attacker-controlled outpoint and full verifier signature collection for a "replacement" move-to-vault transaction.

### Impact Explanation
A move-to-vault UTXO for the attacker's self-funded `replacement_B` obtains full N-of-N verifier signatures while carrying no genuine backing relationship to `old_move_txid`'s real security-council-authorized successor (`replacement_A`, or even no real spend at all). This matches the Critical category "N-of-N partial signatures for an unauthorised spend" and enables the Citrea Bridge to double-count vault backing for a single historical deposit, since `Citrea Bridge`'s deposit acceptance keys off the committed `old_move_txid` prefix/suffix in the replacement script rather than a specific verified chain of custody. This is repeatable for every `old_move_txid` that has ever existed (replaced or not) and is not limited to a single deposit or operator — any historical move-to-vault txid can be targeted by any unprivileged attacker willing to fund `bridge_amount` BTC into a computable address.

### Likelihood Explanation
Exploitation requires only: knowledge of `nofn_xonly_pk`, the security council's public keys (both public/config values), and any `old_move_txid` (which is either a real deposit or an already-replaced one, all public on-chain). No verifier, operator, or council collaboration is needed. The attacker's cost is one Bitcoin transaction funding a UTXO with exactly `bridge_amount`, confirmed above `start_height`, and a gRPC call to `Aggregator::new_deposit`/`send_move_to_vault_tx`. This is fully deterministic and requires no race condition or timing luck — the check is structurally absent, not merely weak.

### Recommendation
In `Verifier::is_deposit_valid`, for `DepositType::ReplacementDeposit`, resolve `old_move_txid`'s vault output on chain, determine its actual spending transaction (if any), and require that the spending transaction's output at the relevant vout equals `deposit_outpoint` exactly. Additionally enforce, at the database layer, that at most one accepted `ReplacementDeposit` may reference a given `old_move_txid` (e.g., a uniqueness constraint or an explicit lookup/rejection in `insert_deposit_data_if_not_exists` keyed on the `old_move_txid` extracted from `deposit_params`).

### Proof of Concept

1. Use `run_single_replacement_deposit` to legitimately replace `old_move_txid` with `replacement_A`; confirm `is_deposit_valid` passes and verifiers sign, matching `deposit_outpoint_A == spending_output(old_move_txid)`.
2. Independently compute `generate_replacement_deposit_address(old_move_txid, nofn_xonly_pk, network, security_council)` and self-fund a fresh UTXO `deposit_outpoint_B` (not derived from spending `old_move_txid`'s vault output) with `bridge_amount`; mine to `start_height`.
3. Submit `ReplacementDeposit{ old_move_txid }` with `deposit_outpoint_B` via `Aggregator::new_deposit`.
4. Assert: current code — `Verifier::is_deposit_valid` returns `Ok(())` for `deposit_outpoint_B` even though `deposit_outpoint_B != spending_output(old_move_txid)` (i.e., `deposit_outpoint_B != deposit_outpoint_A`), demonstrating the missing binding.
5. After the fix, assert `is_deposit_valid` returns `Err(BridgeError::InvalidDeposit(..))` for `deposit_outpoint_B` once `deposit_outpoint_A` is recognized as the legitimate spend of `old_move_txid`.

/// Struct for deposit script that replaces an old move tx with a replacement deposit (to update bridge design on chain)
/// It commits to the old move txid inside the script.
#[derive(Debug, Clone)]
pub struct ReplacementDepositScript(pub(crate) XOnlyPublicKey, Txid);

impl SpendableScript for ReplacementDepositScript {
    fn as_any(&self) -> &dyn Any {
        self
    }

    fn kind(&self) -> ScriptKind {
        ScriptKind::ReplacementDepositScript(self)
    }

    fn to_script_buf(&self) -> ScriptBuf {
        let citrea_replace: [u8; 13] = "citreaReplace".as_bytes().try_into().expect("length == 13");

        Builder::new()
            .push_x_only_key(&self.0)
            .push_opcode(OP_CHECKSIG)
            .push_opcode(OP_FALSE)
            .push_opcode(OP_IF)
            .push_slice(citrea_replace)
            .push_slice(self.1.as_byte_array())
            .push_opcode(OP_ENDIF)
            .into_script()
    }
}

    pub async fn insert_deposit_data_if_not_exists(
        &self,
        mut tx: Option<DatabaseTransaction<'_>>,
        deposit_data: &mut DepositData,
        paramset: &'static ProtocolParamset,
    ) -> Result<u32, BridgeError> {
        // compute move to vault txid
        let move_to_vault_txid = create_move_to_vault_txhandler(deposit_data, paramset)?
            .get_cached_tx()
            .compute_txid();

        let query = sqlx::query_as::<_, (i32,)>(
            "INSERT INTO deposits (deposit_outpoint, deposit_params, move_to_vault_txid)
                VALUES ($1, $2, $3)
                ON CONFLICT (deposit_outpoint) DO NOTHING
                RETURNING deposit_id",
        )
        .bind(OutPointDB(deposit_data.get_deposit_outpoint()))
        .bind(DepositParamsDB(deposit_data.clone().into()))
        .bind(TxidDB(move_to_vault_txid));

        let result =
            execute_query_with_tx!(self.connection, tx.as_deref_mut(), query, fetch_optional)?;

        // If we got a deposit_id back, that means we successfully inserted new data
        if let Some((deposit_id,)) = result {
            return Ok(u32::try_from(deposit_id).wrap_err("Failed to convert deposit id to u32")?);
        }

        // If no rows were returned, data already exists - check if it matches
        let existing_query = sqlx::query_as::<_, (i32, DepositParamsDB, TxidDB)>(
            "SELECT deposit_id, deposit_params, move_to_vault_txid FROM deposits WHERE deposit_outpoint = $1"
        )
        .bind(OutPointDB(deposit_data.get_deposit_outpoint()));

        let (existing_deposit_id, existing_deposit_params, existing_move_txid): (
            i32,
            DepositParamsDB,
            TxidDB,
        ) = execute_query_with_tx!(self.connection, tx, existing_query, fetch_one)?;

        let existing_deposit_data: DepositData = existing_deposit_params
            .0
            .try_into()
            .map_err(|e| eyre::eyre!("Invalid deposit params {e}"))?;

        if existing_deposit_data != *deposit_data {
            tracing::error!(
                "Deposit data mismatch: Existing {:?}, New {:?}",
                existing_deposit_data,
                deposit_data
            );
            return Err(BridgeError::DepositDataMismatch(
                deposit_data.get_deposit_outpoint(),
            ));
        }
