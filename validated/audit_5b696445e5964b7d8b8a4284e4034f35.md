### Title
DKG-confirmation MuSig participant indexes are not remapped after membership changes, causing shares to be evaluated under inconsistent indexes and potentially slashing an innocent validator - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The GitLab bug class is stale membership state: an authorization/participation decision computed from a member list that no longer reflects current membership. In Serai's `DkgConfirmer` flow, the MuSig `ThresholdKeys` are constructed over the *entire* `spec.validators()` set, while the preprocess/share maps are re-indexed over only the *submitting* participants by `threshold_i_map_to_keys_and_musig_i_map`. When `removed` is non-empty — i.e., membership changed mid-attempt — the two index spaces diverge, so each signer's MuSig index used during `sign`/`complete` no longer matches the index under which its key was aggregated.

### Finding Description
`SigningProtocol::preprocess_internal` builds the signing keys via `musig(musig_context(...), key, participants)` where `participants` is `self.spec.validators()` — the full, unmodified validator list, regardless of removals. [1](#0-0) [2](#0-1) 

Separately, `threshold_i_map_to_keys_and_musig_i_map` rewrites the preprocess/share map: it sorts the *submitted* threshold indexes, enumerates them, and assigns fresh contiguous MuSig indexes `raw_i + 1` — a rank among submitters only, skipping removed/absent members. [3](#0-2) 

`DkgConfirmer::share_internal` then feeds that re-indexed map into `share_internal`/`sign`, while the machine's own `i` and `n` still derive from the all-validators MuSig construction. [4](#0-3)  The set of included signers in `AlgorithmSignMachine::sign` is taken directly from these mismatched map keys and used for the binding-factor transcript and the Lagrange/`view` computation. [5](#0-4) 

When `removed` is empty and every validator submits, submitter rank coincides with validator position and everything is consistent. As soon as membership changes (a validator is removed by `RemoveParticipantDueToDkg`/`removed_as_of_dkg_attempt` before confirmation), the submitter-ranked MuSig indexes no longer equal the aggregation indexes: signer `l`'s preprocess/share is bound and interpolated at an index that belongs to a different validator's key share.

### Impact Explanation
Two concrete consequences, both reachable in normal protocol flow once any removal occurs during a DKG attempt:

1. The `set_keys` confirmation signature is assembled from shares evaluated under an inconsistent index set, producing an invalid signature or failing with `FrostError::InvalidShare(p)`/`InvalidPreprocess(p)`.
2. On `Err(p)`, the coordinator calls `spec.reverse_lookup_i(&removed, p)` and publishes `RemoveParticipantDueToDkg` for that validator — a fatal slash. Because `p` is a mismatched index, the lookup can resolve to an honest validator, fatally slashing an innocent party. [6](#0-5) 

### Likelihood Explanation
Any validator can trigger the precondition by voting `Transaction::RemoveParticipantDueToDkg` (fatal slash requires `t` votes) or by a legitimately faulty participant being removed during the attempt; removals during DKG are an anticipated path (`DkgConfirmer::removed` exists precisely for this). The divergence is deterministic — it does not require racing or collusion beyond an ordinary removal coinciding with confirmation. Rated Medium: the outcome is a broken confirmation signature and an erroneous fatal-slash vote rather than key recovery.

### Recommendation
Build the MuSig `ThresholdKeys` in `preprocess_internal` over the *filtered* participant set (validators minus `removed`, in the same order `threshold_i_map_to_keys_and_musig_i_map` produces), or make `threshold_i_map_to_keys_and_musig_i_map` preserve each submitter's original MuSig aggregation index instead of re-enumerating. Additionally, don't fatal-slash on `complete` errors whose participant index came from a remapped space without revalidating it against the aggregation ordering.

### Proof of Concept
1. A `n`-validator set runs a DKG attempt; validator `V` is removed via `RemoveParticipantDueToDkg` before `DkgConfirmed` shares accumulate, so `removed_as_of_dkg_attempt` returns `[V]`.
2. Every remaining validator publishes `DkgShares` + confirmation nonces and calls `generated_key_pair` → `DkgConfirmer::share`; `keys` is built over all `n` validators (`i` = position among all `n`), while the preprocess map keys are submitter ranks `1..=n-1` — off-by-one-shifted for every validator whose position followed `V`.
3. `sign` succeeds (or fails at `complete`), but the binding factors/Lagrange view are computed for the wrong index set; when `complete` returns `Err(p)`, `reverse_lookup_i(&removed, p)` names a validator that may have submitted perfectly valid data, and the coordinator fatally slashes them.

Caveat: I could not fully read `musig()`/`TributarySpec::validators()`/`removed_as_of_dkg_attempt` bodies within the available iterations, so the exact index-shift behavior (whether `validators()` already excludes removed members, or MuSig uses `t = n`) is inferred from the call sites; if `validators()` is already removal-aware, the mismatch and the finding collapse.
