## Title
Reward accrual for `WomUp` is permanently lost whenever `totalSupply()` is zero - (File: `wombat/WomUp.sol`)

### Summary
`WomUp.sol` implements a Synthetix-style, time-based reward accrual scheme (`rewardRate`, `lastUpdateTime`, `rewardPerTokenStored`) for users who deposit WOM in exchange for streamed MGP rewards. The `updateReward` modifier unconditionally advances `lastUpdateTime` even when `totalSupply() == 0`, so any reward time that elapses while no one has WOM staked is permanently skipped and can never be re-captured by later depositors, exactly matching the root cause described in the referenced Blueberry report.

### Finding Description
The `updateReward` modifier runs on every state-changing user action (`stake`, `withdraw`, `migrate`, `getReward`): [1](#0-0) 

It always sets `lastUpdateTime = lastTimeRewardApplicable()`, i.e. `block.timestamp` (capped at `periodFinish`), regardless of whether there is any stake to account against. `rewardPerToken()` explicitly bails out and returns the stale `rewardPerTokenStored` value without accruing anything when `totalSupply() == 0`: [2](#0-1) 

Because `rewardRate` keeps counting down against wall-clock time once `initializeRewards()` sets `periodFinish`/`rewardRate`, any interval in which `_totalSupply == 0` (before the very first `stake()`, or after all stakers have fully `withdraw()`n/`migrate()`d out) is a period during which reward tokens are conceptually "streaming" but `rewardPerTokenStored` is never incremented for it. As soon as the next user calls `stake()`/`withdraw()`/`migrate()`/`getReward()`, the modifier snaps `lastUpdateTime` forward to `block.timestamp`, silently discarding that unaccounted period forever — no future call can ever recover it, since `rewardPerToken()` only ever looks at `lastTimeRewardApplicable() - lastUpdateTime` going forward.

This is triggered purely by ordinary, unprivileged user actions (`stake`/`withdraw`/`migrate`), reachable by any wallet holding WOM/mWOM — the same reachable-by-anyone pattern as the original Blueberry finding.

### Impact Explanation
MGP reward tokens already pulled from the owner via `initializeRewards()` remain locked in the contract with no accounting path to ever be claimed by any user for the skipped interval — this is a permanent freezing/loss of yield that was already funded and earmarked for stakers. The magnitude scales with how long the pool sits at zero total supply (e.g., the gap between `initializeRewards()` and the first `stake()`, or any period where all depositors fully exit via `withdraw`/`migrate` before someone else stakes again).

### Likelihood Explanation
This requires no adversarial behavior — it happens under normal, expected usage: any delay between reward initialization and the first deposit, or any full-exit-then-re-entry cycle, guarantees a permanent loss of rewards for that window. It is not attacker-triggered, but is a systemic accounting flaw guaranteed to occur to some degree on every deployment.

### Recommendation
Skip advancing `lastUpdateTime` in the `updateReward` modifier when `totalSupply() == 0`, mirroring the fix applied to `BlueberryStaking.sol` (only checkpoint `lastUpdateTime` when there is an active total supply to attribute rewards to), or alternatively queue/roll over undistributed rewards similar to the `_provisionReward` queuing pattern already used in `rewards/BaseRewardPool.sol`/`BaseRewardPoolV2.sol`.

### Proof of Concept
1. Owner calls `initializeRewards()`, setting `rewardRate = rewardsAvailable / duration`, `lastUpdateTime = block.timestamp`, `periodFinish = block.timestamp + duration` — at this point `_totalSupply == 0`. [3](#0-2) 
2. No one stakes for `T` seconds (e.g., half the reward duration).
3. A user calls `stake()`. The `updateReward` modifier computes `rewardPerToken()` — since `totalSupply() == 0` at this point (checked before the stake amount is added), it returns the unchanged `rewardPerTokenStored`. It then sets `lastUpdateTime = lastTimeRewardApplicable()` = current `block.timestamp`. [4](#0-3) 
4. The `T` seconds worth of `rewardRate`-based rewards are never reflected in `rewardPerTokenStored` and, because `lastUpdateTime` has jumped forward, can never be recovered by any subsequent staker — the corresponding MGP tokens are permanently stuck/unclaimable in the contract.

    function rewardPerToken() public view returns (uint256) {
        if (totalSupply() == 0) {
            return rewardPerTokenStored;
        }
        return
            rewardPerTokenStored + (
                (lastTimeRewardApplicable() - (lastUpdateTime)) * rewardRate * (1e18) / (totalSupply())
            );
    }

    function initializeRewards() external onlyOwner returns (bool) {
        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();

        rewardRate = rewardsAvailable / (duration);

        lastUpdateTime = block.timestamp;
        periodFinish = block.timestamp + (duration);

        emit RewardAdded(rewardsAvailable);

        return true;
    }
