### Title
Malicious/compromised git remote can inject an arbitrary "Bypass" URL that Desktop opens via `shell.openExternal` without validation - ([File: app/src/ui/dispatcher/error-handlers.ts])

### Summary
The report's core pattern is: an attacker-influenced, externally-triggerable input is trusted to drive a security-relevant UI action without validating that the input actually originates from — or points to — a legitimate/expected source. In GitHub Desktop, the closest analog is the secret-scanning push-protection error handler, which parses the raw `stderr` text returned by the git remote on push and extracts a `bypassURL` via regex, then renders that attacker-controlled string as a clickable external link.

### Finding Description
When a `git push` fails, Desktop inspects the underlying `GitError` and, if `gitError.result.gitError === DugiteError.PushWithSecretDetected`, extracts the raw remote message text and regex-parses it for secret-scanning results: [1](#0-0) 

The regex greedily captures everything after `https` up to a space as `bypassURL`, and a `requiresApproval` flag is derived from whether the message text contains `'request an exemption'`: [2](#0-1) 

This data comes straight from the git remote's response (the `remote:` lines Git relays as part of push stderr) — a value fully controlled by whatever host or proxy the `push` was directed at. Desktop performs no validation that `bypassURL` is a `github.com`/enterprise host, nor any URL-scheme/origin allow-listing.

If `requiresApproval` is true, the UI renders the extracted `bypassURL` directly as a clickable `LinkButton`: [3](#0-2) 

and `LinkButton` unconditionally calls `shell.openExternal(uri)` on click with no scheme/host checks: [4](#0-3) 

`shell.openExternal` is proxied to the Electron main process and invoked with no allow-list beyond logging whether it starts with `http(s)://`: [5](#0-4) 

### Impact Explanation
An attacker who controls the git remote/proxy a victim pushes to (e.g., a malicious or compromised Git server, or a MITM proxy on an HTTP remote) can fabricate a fake "push protection" rejection message mimicking GitHub's real format. Desktop's regex-based parser has no cryptographic or origin-based verification tying the message to GitHub — it only checks that dugite classified the exit as `PushWithSecretDetected` (a heuristic based on stderr text pattern-matching, not signed/authenticated data). By crafting the stderr accordingly, the attacker can:
- Control the displayed `description` and secret `id` shown in the dialog (UI spoofing/confusion), and
- Fully control the `bypassURL`, which Desktop will open via `shell.openExternal` when the user clicks "Bypass" — enabling redirection to attacker-controlled phishing infrastructure (e.g., a fake GitHub login page for credential/token harvesting) presented under the trusted, contextually-relevant guise of a legitimate secret-scanning bypass flow.

This does not achieve remote code execution or a renderer/IPC sandbox escape by itself, but it does allow an attacker-controlled remote response to induce the client to navigate to an attacker-chosen external URL as part of what looks like a routine, trusted GitHub Desktop workflow — a credential-phishing primitive that fits the "attacker controls a git remote/proxy response" threat model.

### Likelihood Explanation
Requires the victim to push to a repository whose remote is attacker-controlled or attacker-intercepted (e.g., a compromised internal/self-hosted git server, or an HTTP(S) remote behind a hostile/misconfigured proxy) and to click "Bypass" in the resulting dialog. No local access, malware, or leaked credentials are needed — only crafting a plausible stderr response mimicking GitHub's secret-scanning push-protection format, which is documented/observable behavior.

### Recommendation
- Do not trust `bypassURL` (or any part of the parsed secret-scanning message) from arbitrary remote stderr; only surface this dialog/flow when the push target is confirmed to be a known GitHub.com/GHE endpoint associated with an authenticated account.
- Validate that `bypassURL`'s origin matches the expected `htmlURL`/API endpoint for the repository's GitHub host before rendering it as a clickable link.
- Consider having `LinkButton`/`shell.openExternal` enforce an allow-list of expected hosts for security-sensitive flows, or require confirmation showing the actual destination host before opening.

### Proof of Concept
1. Attacker controls (or MITMs, for an `http://` remote) a git server that a Desktop user pushes to.
2. On `git push`, the attacker's server returns a rejection with a fabricated `remote:` message matching Desktop's `secretsRegex` format, including a `bypassURL` field set to `https://attacker.example/fake-login `.
3. dugite classifies the failure with `DugiteError.PushWithSecretDetected` (based on stderr pattern matching), triggering `secretScanningPushProtectionErrorHandler` → `PopupType.PushProtectionError`.
4. Desktop shows the "Push Protection" dialog with the attacker-controlled description and a "Bypass" link.
5. If the crafted message includes "request an exemption" text, `requiresApproval` is `true` and the dialog renders a `LinkButton uri={secret.bypassURL}`.
6. When the user clicks "Bypass", `shell.openExternal('https://attacker.example/fake-login')` is invoked, opening the attacker's phishing page in the system browser.

Note: I could not fully verify from the indexed code the exact dugite-side logic that classifies stderr into `DugiteError.PushWithSecretDetected` (only its usage sites in `app/src/lib/git/core.ts` and `error-handlers.ts` were found, not the classification regex itself), so the precise conditions an attacker's fake message must satisfy to trigger this path are inferred rather than fully confirmed. Verifying this would require inspecting `app/src/lib/git/core.ts` and dugite's error-parsing tables directly, which may exceed the indexed content available here.

```typescript
function extractSecretScanningResults(
  remoteMessage: string
): ReadonlyArray<ISecretScanResult> {
  const secretsRegex =
    /—— (?<description>.*?) —+[\s\S]*?locations:(?<locationsGroup>(?:\s+- commit: [a-f0-9]{40}\s+path: [\s\S]*?)+).*?(?<bypassURL>https[\s\S]*?) /g

  const matches = [...remoteMessage.matchAll(secretsRegex)]

  const secrets: Array<ISecretScanResult> = []
  if (matches.length === 0) {
    return secrets
  }

  for (const match of matches) {
    if (match.groups === undefined || match.index === undefined) {
      continue
    }

    const { bypassURL, description, locationsGroup } = match.groups

    const locationsRegex =
      /- commit: (?<commitSha>[a-f0-9]{40})\s+path: (?<path>.*?):(?<lineNumber>\d+)/g
    const locationMatches = [...locationsGroup.matchAll(locationsRegex)]

    const locations: ISecretLocation[] = []

    locationMatches.forEach(locationMatch => {
      if (locationMatch.groups === undefined) {
        return
      }
      const { commitSha, path, lineNumber } = locationMatch.groups
      locations.push({
        commitSha,
        path,
        lineNumber: parseInt(lineNumber, 10),
      })
    })

    secrets.push({
      id: bypassURL.split('/').pop() || '',
      description,
      bypassURL,
      locations,
      requiresApproval: !!match.at(0)?.includes('request an exemption'),
    })
  }

  return secrets
```
