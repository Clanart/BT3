### Title
`harvest(address _lpToken)` DoS via `SmartWomConvert.smartConvert` strict `_minRec` check blocks deposits/withdrawals - (File: wombat/WombatStaking.sol)

### Summary
`harvest`, `deposit`, `depositLP`, and `withdraw` all route through `_toMasterWomAndSendReward` → `_sendRewards`, which — when the `isMWOM` fee is active and `smartWomConverter` is set — calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`. `smartConvert` calls `_convertFor` with `_minRec = _amountIn`, an exact-parity check that can fail whenever the wom/mWom pool is pushed off-peg, causing the whole transaction (including deposits/withdrawals) to revert. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`harvest` is unprivileged (only gated by `whenNotPaused` and `_onlyActivePool`, no role check) and simply calls `_toMasterWomAndSendReward(_lpToken, 0, true)`. [4](#0-3) 

`_toMasterWomAndSendReward` measures WOM rewards harvested from `IMasterWombat` and forwards them through `_sendRewards`: [5](#0-4) 

Inside `_sendRewards`, if the `isMWOM` fee is active and a `smartWomConverter` is configured, the WOM fee slice is sent to `smartConvert`: [6](#0-5) 

`SmartWomConvert.smartConvert` reads `currentRatio()` (mWom→wom quote from the `womMWomPool`) and derives a `convertRatio`; if the pool is below `buybackThreshold` it swaps part of the WOM through the router for mWom instead of straight 1:1 minting, but crucially it hardcodes `_minRec = _amountIn` — i.e., it demands the converted mWom output equal or exceed the WOM input 1:1, regardless of legitimate AMM slippage: [2](#0-1) 

`_convertFor` then reverts with `MinRecNotMatch()` if `convertAmount + amountRec < _minRec`: [7](#0-6) 

Because the router swap's execution price depends on the pool's cash/liability skew (and gets worse with size/skew), an attacker who pushes the wom/mWom pool off-peg (or exploits an already-skewed/thin pool) can make the buyback swap return less mWom than the WOM spent, tripping this exact-parity check. There is no try/catch around `smartConvert` in `_sendRewards`, so the revert propagates all the way up through `harvest`, `deposit`, `depositLP`, and `withdraw` for that specific `_lpToken`'s fee routing — none of these functions have any fallback path (e.g., skip conversion, mint mWom directly, or catch-and-continue) if the converter reverts. [8](#0-7) 

### Impact Explanation
If the off-peg condition on the wom/mWom pool persists on-chain (not merely within one atomic reverted transaction), every subsequent `harvest`, `deposit`, `depositLP`, or `withdraw` call for that pool that accrues nonzero WOM rewards will revert at the `_sendRewards`→`smartConvert` step, since the check is unconditional and has no bypass. This blocks principal deposits and withdrawals for the affected pool until either the price recovers on its own, or the owner intervenes (disabling `smartWomConverter`, marking the pool `isPoolFeeFree`, or deactivating the `isMWOM` fee) — matching the "Temporary freezing of funds" impact class, provided the off-peg state or the affected `feeInfo`/`smartWomConverter` configuration is not corrected within 24 hours.

### Likelihood Explanation
The premise that an attacker can push the pool off-peg "in the same transaction" is important: if the price manipulation and the `harvest` call sit in the same reverting transaction, the manipulation itself gets rolled back along with the revert, so no state persists to block other users' later, independent transactions — only the attacker's own gas is wasted. For this to become a genuine ≥24h freeze of other users' funds, the off-peg state (or a persistently thin/skewed pool) must survive on-chain across blocks so that unrelated `harvest`/`deposit`/`withdraw` calls made by others independently hit the same `MinRecNotMatch()` revert. That requires either continuous re-manipulation by the attacker in every relevant block (capital-intensive and repeatable but not free, since AMM swaps aren't automatically unwound without loss) or a naturally illiquid/skewed pool. This is a real reachable code defect (no owner/role permissions needed to trigger `harvest`), but its exploitability at the "≥24h freeze" severity bar depends on external AMM liquidity/arbitrage conditions that are outside `WombatStaking.sol` itself.

### Recommendation
Do not hardcode `_minRec = _amountIn` in `smartConvert`; use a slippage-tolerant threshold (e.g., percentage-based, computed from `estimateTotalConversion`) instead of demanding exact 1:1 parity against AMM execution. Additionally, wrap the `IConverter(smartWomConverter).smartConvert(...)` call in `_sendRewards` in a try/catch (or add an explicit fallback to mint mWom 1:1 via `IMWom(mWom).deposit`) so that a reverting converter cannot block the WOM reward distribution path, and by extension `harvest`, `deposit`, `depositLP`, and `withdraw`.

### Proof of Concept
Hardhat/Foundry fork test plan:
1. Fork BSC/network state where `WombatStaking`, `SmartWomConvert`, `masterWombat`, and the wom/mWom `IWombatPool`/router are deployed and configured with an active `isMWOM` fee and `smartWomConverter` set.
2. Advance blocks so pending WOM rewards accrue on `masterWombat` for a target `_lpToken`'s `pid`.
3. As the attacker (unprivileged EOA), swap a large amount through the wom/mWom pool (or directly manipulate `IAsset(womAsset).cash()`/`liability()` if a test double is used) to push `currentRatio()` below `buybackThreshold` and skew execution price so that `convertAmount + amountRec < _amountIn` for the pending fee amount.
4. Call `WombatStaking.harvest(_lpToken)` (or have the victim call `deposit`/`depositLP`/`withdraw`) and assert the transaction reverts with `MinRecNotMatch()`.
5. Confirm no state (receipt token `totalSupply`, `IMasterWombat` staked balance) changed as a result of the reverted call — establishing pure denial-of-service rather than an accounting desync.
6. To test persistence/severity, keep the pool off-peg across multiple subsequent blocks/transactions (not reverted) and show that independent victim calls to `deposit`/`withdraw` continue to revert until either the price recovers or admin disables the converter/fee — measuring elapsed time to quantify whether the freeze reaches the 24-hour bar.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
