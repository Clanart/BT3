## Title
Unpermissioned `purchase()` sponsorship lets an attacker evict a victim's paid bandwidth subscriptions via the FIFO cap — loss of prepaid funds - (File: `modules/pallets/bandwidth/src/lib.rs`, `evm/src/apps/BandwidthManager.sol`)

### Summary
The external report's core broken invariant is: a value-limiting function (`maxDeposit`) doesn't account for value already owed/committed elsewhere, so a legitimate later action (fee withdrawal) is destructively blocked/lost. The Hyperbridge local analog is `pallet-bandwidth`'s FIFO subscription cap: `push_subscription()` unconditionally evicts the oldest live subscription once a `(chain, app)` bucket hits `MAX_SUBSCRIPTIONS` (1024), with no accounting for how much prepaid value (`remaining_bytes`) the evicted entry represents, and no restriction on who can push into that bucket.

### Finding Description
`BandwidthManager.purchase()` in `evm/src/apps/BandwidthManager.sol` (lines 148–193) lets **any caller** credit bandwidth to **any `app`/`chain` pair** — this "sponsorship" model is by design, documented in `docs/content/developers/evm/bandwidth/overview.mdx` ("a buyer on Ethereum can credit an app on Base"). The only cost is the tier price.

On the pallet side, `on_accept` (`modules/pallets/bandwidth/src/lib.rs:454-489`) decodes the purchase message and calls: [1](#0-0) 

`push_subscription` then appends unconditionally, evicting index 0 (the oldest, not the smallest/cheapest) once the bucket is at cap, with no check on the evicted entry's remaining value: [2](#0-1) 

Because `Allowance` is keyed by `(app_chain, app)` taken from the attacker-controlled message body — not by `request.source` — and `is_purchase_message`/`on_accept` never restricts who the payer is or caps per-payer contribution to a bucket, an attacker can:
1. Target a victim `(app_chain, app)` pair that already holds a large, non-expired subscription (e.g. the victim just bought the $1000/8MB tier).
2. Repeatedly call `purchase()` with the cheapest configured tier (`TierOne`, minimal `months`) for that exact `(app, chain)` pair, 1024 times (minus current queue length).
3. Each purchase appends a new tiny subscription; once the bucket reaches the 1024 cap, every subsequent purchase evicts the oldest entry — including the victim's large, unexpired, already-paid-for subscription — emitting `SubscriptionEvicted` with the victim's `lost_bytes`.

The `push_subscription` eviction logic treats every entry identically regardless of value; there is no requirement that eviction only removes entries of low/expired value, and no per-buyer/per-payer quota on `(app_chain, app)` bucket writes. This exactly mirrors the report's core flaw: a cap/limit mechanism that ignores already-committed value belonging to someone else, causing that value to be destroyed by an unrelated, low-cost, unprivileged action.

### Impact Explanation
This is a direct, permanent loss of prepaid funds for the victim app/buyer: their paid-for byte allowance (`remaining_bytes`) is silently evicted before expiry by an attacker who never interacted with the victim's account. Given tier pricing (`docs/content/developers/evm/bandwidth/overview.mdx`: $50 tier buys 100KB), an attacker can spend roughly 1024×$50 ≈ $51,200 in the worst case to fully flush a victim bucket — but if the victim's bucket already has few entries (the common case per the docs: "one purchase per cycle"), the attacker only needs to fill the remaining slots up to 1024, and cheaper/smaller tiers reduce this cost per evicted slot. Since evictions always target the oldest entry (not the attacker's own cheap entries), the attacker's minimal purchases displace whatever was already queued, including large legitimate purchases, at a cost far below the value destroyed if the victim had bought several months of an expensive tier. This satisfies the "loss of funds" impact gate via a fully unprivileged, public entry point (`purchase()`), no relayer/prover/admin trust needed.

### Likelihood Explanation
`purchase()` has no allowlist, no payer restriction, and no relationship check between the caller and the `app`/`chain` being credited — this is explicit, documented behavior ("Sponsorship"). The FIFO+cap+evict-oldest logic in `push_subscription` is unconditional. The only friction is the fee-token cost of repeated purchases, which is bounded and calculable, not a governance/relayer/prover assumption. This makes the attack fully executable by any funded, unprivileged EVM account today.

### Recommendation
- Track remaining/queue capacity per-payer or require the pallet to reject evicting subscriptions whose `remaining_bytes` exceeds a value threshold, or refuse to evict entries that aren't expired unless the eviction is triggered by an actual purchase paid by the same beneficiary/app owner.
- Alternatively, aggregate subscriptions of the same tier instead of queuing unboundedly, and/or increase `MAX_SUBSCRIPTIONS` cost-of-attack by charging non-linearly, or require `force_credit`/governance-only paths for cross-chain sponsorship of high-value buckets while restricting third-party `purchase()` sponsorship to append-only-if-not-evicting-unexpired-value.
- At minimum, emit a hard error (reject the purchase) instead of silently evicting a live, unexpired subscription with significant `remaining_bytes`, rather than emitting `SubscriptionEvicted` as an acceptable/expected outcome.

### Proof of Concept
1. Governance calls `set_manager` and `set_tier` for `TierOne` (cheap, e.g. $50/100KB) and `TierFour` ($1000/8MB) on `pallet-bandwidth`, matching prices on `BandwidthManager.sol` via `dispatch_set_tiers`.
2. Victim buys `TierFour` for their own app on chain X via `purchase(app=victimApp, tier=4, months=12, chain="EVM-X")`. This appends one `Subscription { remaining_bytes: 8MB*12, expires_at: +1yr }` to `Allowance[X][victimApp]`.
3. Attacker, on any chain with a `BandwidthManager` registered, calls `purchase(app=victimApp, tier=1, months=1, chain="EVM-X")` 1024 times (or however many slots remain to fill the cap), each a valid low-cost purchase — nothing in `purchase()` or `on_accept` prevents targeting someone else's `app`.
4. Once `Allowance[X][victimApp].len() == 1024`, the next attacker purchase evicts index 0. If timed such that the victim's `TierFour` entry is the oldest (or by continuing until it becomes index 0 as older attacker entries drain/expire), the victim's entry is evicted — reflected in `push_subscription`: [3](#0-2) 
`SubscriptionEvicted { app_chain: X, app: victimApp, tier: TierFour, lost_bytes: remaining_bytes }` fires, and the victim's paid-for, unexpired bandwidth is permanently gone while the attacker paid only cheap `TierOne` prices to force the eviction — confirmed by the existing eviction unit test showing the mechanism fires deterministically on the 1024th push: [4](#0-3)

					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.

fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.

				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");
