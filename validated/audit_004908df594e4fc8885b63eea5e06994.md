### Title
Infinite loop in `Offer.get_root_removal()` via a crafted 2-coin removal cycle - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_root_removal()` walks up a chain of "removal" coins by matching `coin.parent_coin_info` to another removal's `Coin.name()`, with no cycle detection or bound on iterations. Because `parent_coin_info` is an attacker-controlled field of a `Coin` object embedded in an offer's `WalletSpendBundle`, and is never required to be consistent with any real on-chain lineage before this method runs, a crafted offer can contain two "ephemeral-looking" removals whose `parent_coin_info` fields point at each other, creating a 2-cycle that the `while` loop never escapes.

### Finding Description
`get_root_removal()` is implemented as: [1](#0-0) 

```
def get_root_removal(self, coin: Coin) -> Coin:
    all_removals: set[Coin] = set(self.removals())
    all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
    non_ephemeral_removals: set[Coin] = {
        c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
    }
    if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
        raise ValueError("The specified coin is not a coin in this bundle")

    while coin not in non_ephemeral_removals:
        coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

    return coin
```

`self.removals()` derives from the coin-spend list of the offer's `WalletSpendBundle`, whose `Coin` objects come directly from data supplied when constructing/parsing an `Offer` (e.g. `Offer.from_spend_bundle` / `Offer.from_bech32`, used when a wallet loads a counterparty's offer file). `Coin.parent_coin_info` is a free-form 32-byte field that need not match any real, previously-validated coin — it is not the coin's own `name()` hash, so an attacker does not need a hash preimage to set it to an arbitrary value.

An attacker can therefore construct two coin-spends A and B inside the offer bundle such that:
- `A.parent_coin_info == B.name()`
- `B.parent_coin_info == A.name()`

Both A and B then satisfy `parent_coin_info in {r.name() for r in all_removals}` (each other's name), so neither is placed into `non_ephemeral_removals`. When `get_root_removal` is called on A: the loop condition `A not in non_ephemeral_removals` is true, so `coin = next(... c.name() == A.parent_coin_info)` resolves to B; then `B not in non_ephemeral_removals` is also true, so `coin` resolves back to A — and so on forever. This is directly analogous to the ImageMagick subimage-search bug: a search/traversal loop over crafted structured input with no termination guarantee or cycle check.

This method is also called transitively by `get_primary_coins()` (via `get_offered_coins()`) and indirectly relates to the sibling `get_cancellation_coins()` logic used when computing offer state (offered coins, cancellation coins) during offer acceptance/inspection in `TradeManager` (`chia/wallet/trade_manager.py`). ### Impact Explanation
Any code path that processes an untrusted, attacker-supplied offer bech32/file (e.g. viewing an offer summary, computing offered/primary coins, or preparing to accept/cancel it) and calls `get_primary_coins()`/`get_root_removal()` will hang the calling task indefinitely on a crafted offer, causing a spend-triggered denial of service in the wallet's offer-processing flow. This matches the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Any user who loads/opens a malicious offer file (a standard, expected wallet interaction — inspecting an offer before deciding whether to accept it) can trigger this. No signature or on-chain validity of the crafted coins is required, because `get_root_removal`/`get_primary_coins` operate purely on the client-supplied `WalletSpendBundle` structure before any real consensus validation occurs. This makes it a low-effort, high-reliability DoS against a wallet inspecting a hostile offer.

### Recommendation
Add cycle detection (e.g., track visited coin ids in a set and raise a `ValueError` if a coin is revisited) or bound the loop by the number of removals in the bundle (`len(all_removals)`), raising an error once that many iterations occur without reaching a non-ephemeral root. Additionally, validate offer removal chains for structural consistency (no self-referential or mutually-referential `parent_coin_info` values) before running any traversal.
