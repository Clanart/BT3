### Title
Cached FROST preprocess is never deleted, allowing nonce reuse and secret-share recovery when `share`/`complete` re-derive it - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the kernel bug (a one-shot context whose cleanup was deferred to a callback that error paths never reached), `SigningProtocol::preprocess_internal` generates a FROST `CachedPreprocess` seed, stores it in `CachedPreprocesses`, and reconstructs the sign machine via `AlgorithmSignMachine::from_cache` — but never deletes the cached entry. The FROST `SignMachine::from_cache` contract explicitly requires deleting the cached preprocess after use because reuse leaks the private key share. Every subsequent call for the same `context` deterministically re-derives the same nonces, so any code path that calls `share_internal` twice with different preprocess sets emits two signature shares under identical nonces.

### Finding Description
In `preprocess_internal`, if `CachedPreprocesses::get(self.txn, &self.context)` already returns a value, the existing seed is decrypted and reused; if absent, a fresh one is written and also reused — the entry is never removed [1](#0-0) . The seed deterministically drives `ChaCha20Rng` in `seeded_preprocess`, so `nonces` and `commitments` are identical on every call for a given context [2](#0-1) . The API documents that the cache "MUST only be used once. Reuse will enable third-party recovery of your private key share" and that after `from_cache` "the preprocess must be deleted so it's never reused" [3](#0-2) .

`DkgConfirmer::share` calls `share_internal`, and `DkgConfirmer::complete` calls `share_internal` *again* via `.expect("trying to complete a machine which failed to preprocess")` [4](#0-3) . Both calls rebuild a machine from the same cached seed (context `(b"DkgConfirmer", self.attempt)`) but consume the `preprocesses`/`key_pair` supplied at that round [5](#0-4) . If the preprocess bytes presented at completion differ from those presented at share time — e.g., a different signing set or a malformed-but-parseable preprocess submitted via tributary data — `machine.sign(preprocesses, msg)` produces a second share `s = d + e·rho + λ_i·s_i·c` with the same `(d, e)` but a different binding factor `rho`, Lagrange coefficient `λ_i`, or challenge `c` [6](#0-5) . Any error path that causes a retry (`share` returning `Err` on a bad preprocess, then a re-invocation with a corrected set) hits the same reuse.

### Impact Explanation
Two shares under reused nonces let an observer solve for the signer's secret key share `s_i` (standard FROST/Schnorr nonce-reuse algebra: subtract shares to cancel `d + e·rho` terms when `rho` collides, or solve the linear system when `lambda`/`c` differ). Recovery of the Ristretto MuSig key share compromises the tributary's signing key for that context. Severity: Medium–High (key-share recovery, conditional on a second signing attempt over a distinct preprocess set).

### Likelihood Explanation
The leak requires two `sign` invocations for the same `(b"DkgConfirmer", attempt)` context with non-identical preprocess maps. `complete` unconditionally re-executes `share_internal` [7](#0-6) , so any divergence between the preprocess map seen at share time and at complete time — including preprocess bytes parsed through `read_preprocess` from peer-supplied data [8](#0-7)  — triggers a second share over reused nonces. Error/retry paths (a failed `share` re-attempted with an updated set) make this reachable without collusion beyond feeding crafted preprocess bytes.

### Recommendation
Delete `CachedPreprocesses` for `context` immediately after a successful `from_cache` (or before `sign`), so a second attempt generates a fresh seed; alternatively key the cache by a nonce bumped per actual signing session rather than per context, and refuse to reuse a consumed entry.

### Proof of Concept
1. Trigger `DkgConfirmer::share(preprocesses_A, key_pair)` — returns share `s_A` computed with nonces `(d, e)` derived from the cached seed.
2. Submit a different valid preprocess map `preprocesses_B` (different participant subset or altered commitment bytes) so `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` internally calls `share_internal` again — same `(d, e)`, new share `s_B` over different `rho`/included set.
3. From public shares `s_A`, `s_B`, known `rho_A`, `rho_B`, Lagrange coefficients, and the group nonce `R = D + E·rho` (identical in both sessions since commitments are identical), solve the two linear equations for the secret share `s_i`.
