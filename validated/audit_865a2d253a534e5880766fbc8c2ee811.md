### Title
CSRF exemption in `CsrfProtection#valid_session_token?` accepts any valid-but-unbound JWT from `params[:id_token]`, allowing cross-origin CSRF bypass - (File: lib/shopify_app/controller_concerns/csrf_protection.rb)

### Summary
`valid_session_token?` exempts a request from `protect_from_forgery` whenever `jwt_payload` is present, and `jwt_payload` is derived from `shopify_id_token`, which falls back to `params["id_token"]` when no `Authorization` header is present. Since JWT verification only checks signature/expiry/audience and not any binding to the current browser session or request origin, an attacker who has captured any not-yet-expired, validly-signed JWT (e.g., from browser history, a referrer leak, logs, or a shared/public demo app) can attach it as a `id_token` request parameter in a cross-origin form POST to bypass CSRF protection entirely.

### Finding Description
The exemption path is: `protect_from_forgery with: :exception, unless: :valid_session_token?` [1](#0-0) , where `valid_session_token?` simply checks `jwt_payload.present?`. `jwt_payload` builds `ShopifyAPI::Auth::JwtPayload.new(shopify_id_token)` from `shopify_id_token`, and `shopify_id_token` is `id_token_from_authorization_header || id_token_from_url_param`, with `id_token_from_url_param` reading directly from `params["id_token"]` — a value fully attacker-controlled in any cross-origin form submission (no header, no cookie, no origin check involved) [2](#0-1) .

`ShopifyAPI::Auth::JwtPayload` (from the `shopify_api` gem, not in this repo) validates signature, `exp`, `nbf`, and `aud`, but has no concept of "current session" or CSRF/origin binding — a signed token remains valid for its full unexpired lifetime regardless of who submits it or from where. This means any previously-issued, still-unexpired JWT — even one obtained via referrer leakage, browser history, shared screenshots, or a public sandbox/demo app using the same API key — is replayable as a URL/body parameter to satisfy `jwt_payload.present?` and disable CSRF checks for that request, even though the token is not bound to the actual session cookie or request that Rails' CSRF protection is meant to protect.

The design intent (per `CHANGELOG.md`: "Skip CSRF protection if a valid signed JWT token is present as we trust Shopify to be the only source that can sign it securely") assumes the presence of *any* validly-signed token is equivalent to a legitimate same-origin request from App Bridge. This assumption breaks specifically for the URL-param path (`id_token_from_url_param`), since URL/body params are trivially replayable cross-origin (unlike the `Authorization` header, which JavaScript on a different origin cannot set without CORS permission, and which is not automatically sent by a plain HTML form). The header path is effectively CSRF-safe because a cross-origin form cannot inject an `Authorization: Bearer <token>` header; the URL-parameter path has no equivalent protection.

### Impact Explanation
This maps to a CSRF vulnerability on state-changing actions of any controller including `ShopifyApp::CsrfProtection` (or `EnsureHasSession`/`LoginProtection` derivatives that include it). Concretely, an attacker who possesses (not forges — captures) a valid unexpired JWT for a shop/user can trick that same browser (or replay it themselves against any endpoint accepting `id_token` as a param) into performing a state-changing POST without the normal CSRF token, since `protect_from_forgery` is skipped. This corresponds to Shopify's HackerOne "Cross-Site Request Forgery (CSRF)" impact class scoped to state-changing endpoints.

### Likelihood Explanation
Exploitability requires the attacker to already possess a valid, unexpired JWT string for the target — this token has a short lifetime (typically ~1 minute per Shopify session token defaults) and is not secret-key derivable by the attacker, so the practical attack surface is narrow: it requires token leakage (referrer header exposure, browser history, logs, shared screenshots) or use of a JWT signed with a shared/public API key in a demo/sandbox app. Given the short expiry window, this is a lower-likelihood but non-zero exploitation path, primarily reducible to the general risk that "any non-expired token, however obtained, defeats CSRF" rather than the header-based approach where cross-origin injection isn't feasible at all.

### Recommendation
Restrict the URL-param `id_token` exemption path so it cannot be used to bypass CSRF on its own: either (a) only allow `valid_session_token?` to skip CSRF when the token came from the `Authorization` header (`id_token_from_authorization_header`), since a cross-site attacker cannot set that header via a browser form/fetch without CORS, or (b) additionally validate that `id_token` (if sourced from URL param) is tied to the existing Rails session (e.g., compare against a session-bound nonce or require it only for XHR requests that also pass Rails' own CSRF token). Do not treat mere presence of a validly-signed but freely-replayable URL parameter as sufficient to disable `protect_from_forgery`.

### Proof of Concept
```ruby
# test/shopify_app/controller_concerns/csrf_protection_test.rb (conceptual addition)
class CsrfProtectionTest < ActionController::TestCase
  test "cross-origin POST with only id_token url param and no Authorization header bypasses CSRF" do
    jwt_payload = {
      iss: "https://test-shop.myshopify.com/admin",
      dest: "https://test-shop.myshopify.com",
      aud: ShopifyAPI::Context.api_key,
      sub: "1",
      exp: (Time.now + 30).to_i, # still valid, e.g. captured from a leaked referrer
      nbf: 1234, iat: 1234, jti: "leaked-token", sid: "abc123",
    }
    old_but_valid_jwt = JWT.encode(jwt_payload, ShopifyAPI::Context.api_secret_key, "HS256")

    with_application_test_routes do
      # No Authorization header set -- simulating a plain cross-site <form method="POST"> submission
      post :create, params: { id_token: old_but_valid_jwt, malicious: "state-change" }

      # Expected (secure) behavior: request should be rejected as a forgery
      # Actual (vulnerable) behavior: request succeeds because valid_session_token? returns true
      assert_response :success # demonstrates CSRF protection was skipped
    end
  end
end
```
This demonstrates that supplying any signed, unexpired JWT as `params[:id_token]` — without an `Authorization` header and without a matching Rails CSRF token — is sufficient to satisfy `valid_session_token?` and bypass `protect_from_forgery`, per [1](#0-0)  and [3](#0-2) .

    def shopify_id_token
      return @shopify_id_token if defined?(@shopify_id_token)

      @shopify_id_token = id_token_from_authorization_header || id_token_from_url_param
    end

    def jwt_payload
      return @jwt_payload if defined?(@jwt_payload)

      @jwt_payload = shopify_id_token.present? ? ShopifyAPI::Auth::JwtPayload.new(shopify_id_token) : nil
    end

    def jwt_shopify_domain
      return @jwt_shopify_domain if defined?(@jwt_shopify_domain)

      @jwt_shopify_domain = if jwt_payload.present?
        ShopifyApp::Utils.sanitize_shop_domain(jwt_payload.shopify_domain)
      end
    end

    def jwt_shopify_user_id
      jwt_payload&.shopify_user_id
    end

    def jwt_expire_at
      expire_at = jwt_payload&.expire_at
      return unless expire_at

      expire_at - 5.seconds # 5s gap to start fetching new token in advance
    end

    private

    def id_token_from_authorization_header
      request.headers["HTTP_AUTHORIZATION"]&.match(/^Bearer (.+)$/)&.[](1)
    end

    def id_token_from_url_param
      params["id_token"]
    end
