### Title
Privileged admin/upgrade opcodes in `IntentGatewayV2.onAccept` authenticate only the source **chain**, not the source **module** - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The Biconomy H-04 root cause is that `checkSignatures` validates *a* value (that some `_signer` returns the EIP-1271 magic value) but never checks that the validated identity is actually the wallet's `owner`. The local analog is in `ExtrinsicIntents.onAccept`: for the privileged branches (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`) the code checks that `request.source` equals the Hyperbridge relay chain, but never checks `request.from` — i.e. *which module on that chain* sent the message. Any module on the Hyperbridge state machine (not just a designated governance/admin module) can trigger these state-changing branches, including a full proxy implementation swap.

### Finding Description
`onAccept` dispatches on the first byte of the incoming POST body (`RequestKind`): [1](#0-0) 

For `RedeemEscrow`/`RefundEscrow` it correctly calls `_authenticate(request)`, which checks that `request.from` (the specific sending module/address) equals the registered gateway instance for `request.source`: [2](#0-1) 

But for `NewDeployment`, `UpdateParams`, `SweepDust`, and `UpgradeContract`, the *only* check performed is:

```solidity
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
``` [3](#0-2) 

This proves only that the message originated from the Hyperbridge relay chain as a *state machine* — it does not bind `request.from` to any specific privileged/governance module address on that chain. Any pallet/module deployed on the Hyperbridge chain that is able to dispatch an ISMP POST request to `to = IntentGatewayV2` (with its own module id as `from`, which is standard ISMP dispatch semantics) can produce a fully-provable, real, correctly-proven ISMP message that reaches this branch. The comparable pattern in the same file (`_authenticate`) shows the developers know that "source chain matches" is not sufficient authentication — module identity must also be checked — yet the admin path omits that second check, exactly mirroring the Biconomy bug where the signer's *validity* was checked but not its *identity/ownership*.

The corrupted/under-validated value is `incoming.request.from` for the `NewDeployment | UpdateParams | SweepDust | UpgradeContract` opcodes: it is never compared against an expected governance module id.

### Impact Explanation
Reaching the `UpgradeContract` branch lets an attacker fully replace the gateway's implementation via `ERC1967Utils.upgradeToAndCall(newImpl, initData)`: [4](#0-3) 
— a direct, unauthorized transaction/execution takeover of the whole gateway contract (equivalent to Biconomy's Impact #2, "update implementation and lock out/steal from the wallet"), since the new implementation can drain all escrowed order funds and fee-token balances held by `IntentGatewayV2`.

`SweepDust` and `UpdateParams` similarly allow an unprivileged module to redirect accumulated protocol dust to an arbitrary beneficiary or rewrite fee/host/dispatcher parameters, and `NewDeployment` lets an attacker register a malicious `_instance` mapping for a state machine id, which is later trusted by `_authenticate()` to accept forged `RedeemEscrow`/`RefundEscrow` requests — chaining into direct theft of escrowed order tokens. All of these match the bounty's accepted impacts: stealing/loss of funds, unauthorized execution, false module-binding acceptance.

### Likelihood Explanation
This does not require a malicious relayer, prover, or leaked key — the ISMP proof/consensus machinery works exactly as designed and the message is a genuine, correctly verified cross-chain message. The only requirement is that *some* module on the Hyperbridge relay chain (not necessarily a privileged/governance one) can dispatch a POST request with `to` set to the gateway's address and a body of the attacker's choosing. Given Hyperbridge hosts multiple pallets (e.g. `pallet-ismp-demo`, `pallet_bandwidth`, `pallet_hyper_fungible_token`, and any future permissionless pallet), and per the documented ISMP module routing model any registered `IsmpModule` sets its own `from`, an unprivileged pallet reachable by ordinary users is a realistic dispatch source. The vulnerability is a direct missing-check in production Solidity code, not a theoretical or peer-compromise scenario.

### Recommendation
In the privileged branch of `onAccept`, authenticate the specific sending module identity (`request.from`), not merely the source chain — analogous to `_authenticate()`'s per-module check. Maintain an explicit "governance module" address (or module id) per remote chain and require `keccak256(request.from) == keccak256(expectedGovernanceModule)` in addition to (or instead of) the chain-only check, mirroring the recommendation in the seed report to validate the actual signer/identity, not just that some check "passes."

### Proof of Concept
1. On the Hyperbridge relay chain, any registered pallet/module `M` (not the intended governance module) dispatches an ISMP `PostRequest` with:
   - `from = M`'s module id
   - `to = <IntentGatewayV2 address on EVM chain X>`
   - `body = abi.encodePacked(uint8(RequestKind.UpgradeContract), abi.encode(attackerImpl, initCalldata))`
2. The request is relayed, proven, and delivered normally through the standard ISMP handler/host pipeline (`EvmHost.dispatchIncoming`), which calls `IApp.onAccept` on `IntentGatewayV2`.
3. In `onAccept`, `kind == RequestKind.UpgradeContract`, and the only guard is `keccak256(incoming.request.source) == keccak256(hyperbridge())`, which is true (the request genuinely came from the Hyperbridge chain). `request.from` (module `M`) is never checked.
4. `ERC1967Utils.upgradeToAndCall(attackerImpl, initCalldata)` executes, replacing `IntentGatewayV2`'s implementation with attacker-controlled code, giving full control over all escrowed funds and future order flow. [1](#0-0)

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        }
    }
