Based on my research, I found a strong local analog to the H-5 bug class in Hyperbridge's Substrate fee-handling path.

### Title
Single malicious fee-payer in a batch reverts the entire message-processing extrinsic, rolling back all other users' successfully executed requests - (File: modules/pallets/ismp/src/fee_handler.rs)

### Summary
`WeightFeeHandler::on_executed` iterates over every message in a batch and calls `C::transfer` from the message's signer to the treasury using the `?` operator to propagate any transfer failure. This function runs as the final step of the same extrinsic that already executed `IsmpModule::on_accept` for every request in the batch (state changes, escrow releases, token transfers, mints, etc., as seen in `modules/ismp/core/src/handlers/request.rs::handle`). Because FRAME wraps a dispatchable extrinsic's storage writes in a single transactional context, an `Err` returned anywhere in the call — including from this per-message fee-transfer loop — rolls back **every** storage mutation performed earlier in that same extrinsic, not just the offending message's.

### Finding Description [1](#0-0) 

The loop charges a fee from the recovered signer account to the treasury:
```rust
for message in &messages {
    ...
    if let Some(account) = AccountId::decode(...) {
        C::transfer(&account, &treasury_account, fee, ExistenceRequirement::KeepAlive)
            .map_err(|_| DispatchError::Other("Failed to transfer fee to treasury"))?;
    }
}
```
`ExistenceRequirement::KeepAlive` means the transfer fails if paying the fee would drop the signer's account below the existential deposit. Any account whose free balance is not comfortably above `fee + ExistentialDeposit` at execution time causes this call to fail.

This is structurally the same defect as the Y2K H-5 report: a shared, first-in batch of independent user operations (deposits in Y2K; ISMP requests/responses here) is processed together, and one participant's ability to make a single sub-call revert breaks settlement for everyone else sharing that batch — because the whole operation is atomic and the "receiver" (here, the fee-charge target account) is attacker-controlled input (the relayer-recovered signer of one of the batched messages).

Unlike the isolated per-request dispatch in `EvmHost.dispatchIncoming` (which explicitly avoids reverting the whole batch on a single `onAccept` failure — [2](#0-1) ) and unlike `ismp::handlers::request::handle` which isolates a failing `on_accept` per-request via `Result` collection without early return ( [3](#0-2) ), the fee-handler path uses `?` inside a loop over the whole batch, which is a hard, all-or-nothing failure mode for the surrounding extrinsic.

### Impact Explanation
If the message-processing extrinsic that invokes `WeightFeeHandler::on_executed` after `ismp::handlers::request::handle` (or the response/timeout equivalents) is a single FRAME dispatchable, any `Err` returned causes the whole extrinsic's storage changes to be discarded. Since `on_accept` for every request in the batch already ran and mutated state (token mints/burns/transfers, escrow releases, receipts) before the fee handler runs, a revert here erases all of that for every user whose request was batched alongside the attacker's message — a direct, provable "loss of funds / unauthorized rollback of executed settlement" for legitimate users, matching the required impact class (logic attack causing transaction manipulation / loss of funds for affected batch participants).

### Likelihood Explanation
An unprivileged relayer or user can trigger this without any special assumptions: they only need to submit (or have relayed) one `PostRequest`/`Response` signed by an account they control and keep at or near its existential deposit so the `KeepAlive` fee transfer fails. Since relayers batch multiple unrelated users' requests into a single `RequestMessage`/`ResponseMessage` for gas efficiency (as documented in `docs/content/protocol/ismp/requests.mdx`), an attacker can cheaply and repeatedly grief any batch their message lands in, with no relayer/prover/admin collusion required — this is a pure unprivileged-attacker/public-entrypoint path.

### Recommendation
Do not propagate a `Currency::transfer` failure with `?` inside the per-message loop of `WeightFeeHandler::on_executed`. Instead, log/skip the failed charge for that specific message (mirroring the pattern already used in `pallet-messaging-incentives`, which explicitly logs a `WARN` on `mint_into` failure and continues the batch rather than aborting), or use `Preservation::Expendable`/best-effort semantics so a fee-payer with a low balance cannot roll back already-executed message effects for unrelated users in the same batch.

### Proof of Concept
1. Attacker crafts (or is the sender of) one `PostRequest` whose signer account balance is exactly `ExistentialDeposit` (or `fee + ExistentialDeposit - 1`).
2. A relayer batches this request together with N legitimate, unrelated users' requests into a single `RequestMessage` and submits `handle`.
3. `ismp::handlers::request::handle` executes `on_accept` for all N+1 requests, causing real state changes (e.g., token mints/transfers/escrow releases) for the legitimate users.
4. `WeightFeeHandler::on_executed` then iterates the batch; when it reaches the attacker's message, `C::transfer(..., ExistenceRequirement::KeepAlive)` fails, `.map_err(...)?` propagates the error out of the extrinsic.
5. FRAME's transactional dispatch wrapper rolls back all storage writes made during the extrinsic, undoing every legitimate user's already-executed `on_accept` effects — while the relayer still burned resources attempting to submit the proof/message, and the legitimate requests must be resubmitted (subject to the same repeatable griefing).

        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

		.into_iter()
		.map(|request| {
			let wrapped_req = Request::Post(request.clone());
			let mut lambda = || {
				let cb = router.module_for_id(request.to.clone())?;
				// Re-check the receipt right before dispatch. The up-front pass above
				// runs before any callback executes; a prior request's on_accept in
				// this same batch could have stored a receipt for this request
				// (directly or by re-entering the handler), and we must not invoke
				// on_accept a second time.
				if host.request_receipt(&wrapped_req).is_some() {
					Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
				}
				// Store request receipt to prevent reentrancy attack
				let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
				let res = cb.on_accept(request.clone()).map(|weight| {
					total_weights.saturating_accrue(weight);

					let commitment = hash_request::<H>(&wrapped_req);
					Event::PostRequestHandled(RequestResponseHandled {
						commitment,
						relayer: signer,
					})
				});
				// Delete receipt if module callback failed so it can be timed out
				if res.is_err() {
					host.delete_request_receipt(&wrapped_req)?;
				}
				Ok(res)
			};

			let res = lambda().and_then(|res| res);
			res
		})
		.collect::<Vec<_>>();

	Ok(MessageResult::Request { events: result, weight: total_weights })
}
