### Title
Mode-2 doubling in `incentiveDeposit` is applied after the MGP-balance cap, allowing `lockFor` to be called for more MGP than the contract holds - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount()` correctly caps the reward it returns to `IERC20(mgp).balanceOf(address(this))`, but `incentiveDeposit()` then multiplies that already-capped value by 2 whenever `_mode == 2` before calling `vlMGP.lockFor()`. This means the balance check that is supposed to guarantee the contract can pay is performed on the pre-bonus amount, not the final amount actually approved and locked, breaking the "cap-before-bonus" invariant.

### Finding Description
In `incentiveDeposit`: [1](#0-0) 

`getRewardAmount()` computes the tier-based reward and clamps it: [2](#0-1) 

The clamp (`mgpReward > mgpleft ? mgpleft : mgpReward`) is evaluated on the un-doubled `mgpReward`. Back in `incentiveDeposit`, if `_mode == 2` the returned (already possibly-capped) value is multiplied by 2 with no re-check against the current MGP balance, and the doubled figure is approved and passed straight into `vlMGP.lockFor(rewardToSend, msg.sender)`. Any legitimate tier reward computed as more than half of the contract's current MGP balance (e.g. `mgpleft = 100`, uncapped reward `= 80` for the user's tier — no clamp triggers since `80 < 100`) becomes `rewardToSend = 160`, which exceeds the 100 MGP actually held.

The mapping `bracketRewarded` that would otherwise be used to reconcile granted bonuses per account is explicitly dead code: [3](#0-2) 

so there is no persistent state tying `calDoubledCounted(account)` accounting to what was actually paid out with the mode-2 bonus, confirming the invariant described in the question ("`bracketRewarded` must stay reconciled with `calDoubledCounted(account)`") is not maintained — the field is unused entirely.

The order-of-operations bug is real and directly reachable by any unprivileged caller supplying `_mode == 2`, no special role required.

### Impact Explanation
The concrete, verifiable on-chain consequence is that `IERC20(mgp).safeApprove(address(vlMGP), rewardToSend)` followed by `vlMGP.lockFor(rewardToSend, msg.sender)` will attempt to move more MGP out of `ArbWomUp3` than it holds. Because `mgp` is a standard ERC20 and the locker consumes the approved allowance via `transferFrom` (as evidenced by the `safeApprove` immediately preceding the call), a request for more tokens than the contract's balance will fail at the ERC20 balance check inside that transfer, reverting the whole `incentiveDeposit` call (including the WOM deposit performed earlier in `_deposit`). I was not able to fully inspect `VLMGP.lockFor`'s internal implementation to rule out a path where locked/voting-power accounting is updated independently of the actual token transfer (which would turn this into genuine insolvency inside the `vlMGP` accounting rather than a plain revert). Based on the code available in `ArbWomUp3.sol`, the confirmed defect is a broken cap-then-bonus ordering, and the most directly provable impact is a denial-of-service on reward claiming for users whose doubled tier reward exceeds the remaining MGP balance, rather than a demonstrated unconditional insolvency/theft. I flag this uncertainty explicitly rather than asserting Critical impact without being able to trace `VLMGP.lockFor`'s bookkeeping.

### Likelihood Explanation
No privileged role is required — any account can call `incentiveDeposit` with `_mode == 2` and enough locked `mWomSV` balance/`_amount` to be assigned a tier reward greater than half of the contract's current MGP balance. This is fully attacker-controlled (via `_amount`, `_convertRatio`, and prior `mWomSV` locks) and requires only owning WOM tokens to deposit; it is trivially repeatable as the pool's MGP balance drains over time from legitimate reward payouts, making the condition ("doubled reward exceeds remaining balance") increasingly easy to trigger, not harder.

### Recommendation
Compute the mode-2 doubled reward first, then apply the `balanceOf(address(this))` cap once, on the final (post-bonus) figure, inside `getRewardAmount` (e.g. pass `_mode` through and apply the multiplier before the `mgpReward > mgpleft` comparison), so the invariant "the contract must be able to pay after all multipliers are applied" holds. Additionally, either remove the unused `bracketRewarded` mapping or use it to track/reconcile bonus already granted per account against `calDoubledCounted`, rather than leaving it as dead state.

### Proof of Concept
Hardhat test plan:
1. Deploy `ArbWomUp3`, mock `mWom`, `mWomSV` (`ILocker`), `vlMGP` (`ILocker`), `wom`, `mgp` ERC20 mocks, and `smartWomConvert` converter mock.
2. Configure `rewardMultiplier`/`rewardTier` via `setMultiplier` with at least 2 tiers.
3. Fund `ArbWomUp3` with a small, known MGP balance `B` (e.g. 100e18).
4. Have an unprivileged EOA lock enough `mWomSV` (or supply `_amount` in the same call) so that `getRewardAmount(_amount, account, true)` returns an uncapped value `R` such that `B/2 < R < B` (clamp does not trigger).
5. Call `incentiveDeposit(_amount, _convertRatio, false, 2)`.
6. Assert: `rewardToSend = R * 2 > B`; the call reverts inside `vlMGP.lockFor` due to insufficient MGP balance (or, if `vlMGP` mock naively records amounts without checking transfer success, assert that `vlMGP`'s recorded locked amount for the account now exceeds `ArbWomUp3`'s actual remaining MGP balance, demonstrating insolvency).
7. Repeat across boundary table rows (`_amount`, tier boundaries, `_mode` in {0,1,2}) to show the defect is isolated to `_mode == 2`, and that `bracketRewarded` remains `0` for all accounts (proving it is dead/unreconciled) via direct storage read.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
