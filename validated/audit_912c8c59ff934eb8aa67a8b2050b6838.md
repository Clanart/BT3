Confirmed local analog. `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all forward the full `msg.value` to Uniswap's `swapETHForExactTokens` without validating or refunding excess to the caller.### Title
Excess native-token overpayment on `EvmHost.dispatch`/`fundRequest` is refunded to the Host contract, not the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all accept native `msg.value` and forward the entire amount to Uniswap's `swapETHForExactTokens`, using `post.fee` / `get.fee` / `amount` as the exact desired token output. This mirrors exactly the pattern flagged in the external Starklane report: a payable entrypoint that accepts arbitrary `msg.value` for a cross-chain fee without validating the amount against what is actually required, and without refunding any overpayment to the original caller.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 

and identically for the GET path: [2](#0-1) 

and for `fundRequest`: [3](#0-2) 

In each case, the full `msg.value` is passed as the value of the external call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(feeAmount, path, address(this), block.timestamp)`. Uniswap V2 Router02's `swapETHForExactTokens` implementation computes the exact ETH input required (`amounts[0]`) to buy `feeAmount` output tokens, performs the swap, and then refunds any leftover ETH (`msg.value - amounts[0]`) via `TransferHelper.safeTransferETH(msg.sender, ...)`. Critically, from the Router's perspective, `msg.sender` in that refund is the **caller of the Router**, i.e. `EvmHost` itself (`address(this)` in `EvmHost`'s context) — not the original transaction sender (`_msgSender()`) who called `dispatch`/`fundRequest`.

This means:
- If a user sends more native ETH than the exact fee requires, the Uniswap refund lands in the `EvmHost` contract's own balance, not back to the user.
- `EvmHost` has no logic in `dispatch`/`dispatch`/`fundRequest` to track or return this refunded ETH to `_msgSender()` or `post.payer`.
- Unlike the ERC20 fee-token path (`safeTransferFrom(_msgSender(), address(this), fee)`, an exact-amount pull), the native-token path has no upper-bound check on `msg.value`, no quoting/estimation enforced on-chain, and no excess-refund mechanism — the same missing invariant identified in the Starklane `depositTokens` report ("no `msg.value` check ... if a user sends more ether than necessary, the excess will not be refunded, leading to a loss of funds").

Existing guards do not stop this: `notFrozen` only checks the freeze/pause state, and there is no `require(msg.value == quotedFee)` or refund-of-excess step anywhere in these three functions.

### Impact Explanation
Any user who overestimates the ETH needed (e.g. due to slippage buffers, using stale price quotes, or simply rounding up to be safe) permanently loses the difference — the excess ETH becomes stuck in the `EvmHost` contract's balance with no user-facing mechanism to reclaim it, and is effectively a passive loss of funds for the caller on every dispatch. This directly matches the required impact class "stealing or loss of funds" since native funds move to an unintended destination (the Host's own balance) rather than back to the rightful depositor. Because this triggers on every user-supplied overpayment across `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, the exposure surface is broad and systemic, not a one-off edge case.

### Likelihood Explanation
High likelihood: this is not a malicious-actor path — it requires no privileged access, no relayer/prover assumptions, and no front-running. It triggers under completely normal usage whenever a caller supplies `msg.value` even slightly larger than the exact fee token amount needed (which is common practice for gas/price-buffering in cross-chain fee estimation, as documented in the SDK's `quote()`/fee-estimation guidance shown in the docs). Every dispatching contract built on top of `IDispatcher` (e.g., `HyperApp`-based apps, `HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`) forwards `msg.value` directly to `EvmHost.dispatch`, so the bug is reachable through many public entrypoints across the SDK.

### Recommendation
- After calling `swapETHForExactTokens`, compute the actual ETH spent (`amounts[0]` returned by the swap) and refund `msg.value - amounts[0]` to `_msgSender()` (or `post.payer`) directly within `EvmHost`, rather than allowing Uniswap's refund to land on `address(this)`.
- Alternatively, call `getAmountsIn` before the swap to determine the exact `amounts[0]` needed, only forward that exact value to `swapETHForExactTokens{value: amounts[0]}`, and separately refund `msg.value - amounts[0]` to the caller in the same transaction.
- Add an on-chain `quote`/fee-estimation view function (or leverage `getAmountsOut`) that dApp integrators can call before dispatch, plus a `require`/event trail so client callers can verify actual vs. quoted fee.

### Proof of Concept
1. Deploy `EvmHost` with a configured Uniswap V2 router and fee token.
2. Call `dispatch(DispatchPost)` with `post.fee = X` (feeToken amount) and `msg.value = 2 * requiredEthForX` (deliberately overpaying, e.g., due to price-buffer slippage protection commonly recommended in client-side fee estimation).
3. Observe: `swapETHForExactTokens` executes successfully, buys exactly `X` fee tokens, and refunds the excess ETH — but the refund target is `address(this)` (the `EvmHost` contract), verifiable via balance delta on `EvmHost` before/after the call versus the caller's ETH balance before/after.
4. Confirm `_msgSender()`'s ETH balance decreases by the full `msg.value` sent, while `EvmHost`'s ETH balance increases by the excess amount, with no subsequent transfer-out event or accounting entry crediting that excess back to the caller.
