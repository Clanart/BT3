## Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone steal funds transiently held by the shared intent-gateway dispatcher — ([File: evm/src/utils/CallDispatcher.sol])

### Summary

`IntentGatewayV2` routes all `predispatch`/`postdispatch` calldata through a single, protocol-wide `CallDispatcher` instance (`_params.dispatcher`), the same address for every order and every user [1](#0-0) . `CallDispatcher.dispatch()` is a fully public, unauthenticated function that executes arbitrary `Call[]` using whatever native ETH / ERC-20 balance the contract currently holds, with no `msg.sender` check [2](#0-1) . Because the contract also has a permissive `receive()` and the gateway's escrow-sweep logic pulls funds from it by balance snapshot rather than by a caller-authenticated allocation, any ETH/token that is briefly (or permanently, if not part of `order.inputs`) held by the dispatcher can be swept out by an unrelated third party.

### Finding Description

`placeOrder` transfers the order's `predispatch.assets` to the shared `dispatcher`, executes the (fully attacker-controlled) `predispatch.call`, then sweeps whatever balance the dispatcher holds for each `order.inputs[i].token` back to the gateway as escrow, treating the swept amount as "actual received" [3](#0-2) . This is the same broken pattern as the Loop `PrelaunchPoints` bug: the credited/escrowed amount is derived from a shared contract's raw balance instead of a value strictly attributable to the current caller's flow.

The `dispatcher` contract itself is the weaker link: `dispatch(bytes memory encoded)` decodes a `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry with **no access control at all** [4](#0-3) . Anyone — not just `IntentGatewayV2` — can call `dispatch()` directly. Combined with the unguarded `receive() external payable {}` [5](#0-4) , this means:

- Any ETH sent to the dispatcher as part of a `predispatch` swap that isn't fully consumed/converted (e.g. predispatch swaps native ETH into a token, but `order.inputs` doesn't include `token == address(0)`, so the sweep loop never touches the leftover native balance) sits in the dispatcher indefinitely.
- Any ERC-20 sent as a `predispatch.assets` entry whose token is not also listed in `order.inputs` (a legitimate "swap A → escrow B" pattern) leaves the untouched token A balance stuck in the dispatcher, since only `order.inputs[i].token` balances are swept.
- Because `dispatch()` has no caller restriction, a third party can call `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: transfer(attacker, balance)})]))` directly and drain any such balance to themselves, at any time, with no relationship to the order that funded it.

This is structurally identical to the reported invariant break: a shared contract's balance — fed by transfers that are logically earmarked for one purpose — becomes claimable by anyone via a permissionless "claim" entrypoint, exactly like donating ETH to `PrelaunchPoints` and then claiming it through `convertAllETH`/`claim()`.

### Impact Explanation

Funds transiently or permanently held by `CallDispatcher` (native ETH from partial predispatch/postdispatch swaps, or ERC-20 remnants not part of `order.inputs`) can be stolen by any unprivileged address calling `dispatch()` directly, bypassing `IntentGatewayV2` entirely and its `nonReentrant` guard (which only protects the gateway, not the dispatcher). This is unauthorized execution/fund theft against a production bridge contract that is shared across every order and every chain deployment of `IntentGatewayV2`.

### Likelihood Explanation

No privileged role, relayer, prover, or malicious peer is required — any address can call the public `dispatch()` function on the known, deployed `CallDispatcher` address at any time. The only precondition is that the dispatcher currently holds a non-zero balance of some asset, which naturally occurs whenever a `predispatch`/`postdispatch` flow leaves dust (partial fills, slippage, swap-then-escrow of a different token than the one advertised in `order.inputs`), or whenever anyone (attacker included) sends value to the dispatcher's unguarded `receive()`.

### Recommendation

- Restrict `CallDispatcher.dispatch()` to be callable only by the authorized `IntentGatewayV2` (or an explicit allowlist of callers), e.g. an `onlyCaller`/`Ownable` check set at construction.
- Do not rely on raw balance snapshots (`address(this).balance`, `balanceOf(dispatcher)`) to determine "received" amounts from a shared, permissionless contract; scope dispatcher usage per-order (ephemeral clone/CREATE2 instance) or track exact deltas tied to a specific call's inputs/outputs.
- Sweep *all* assets touched by `predispatch`/`postdispatch`, not only those enumerated in `order.inputs`/`output`, so no token can accumulate unclaimed in the shared dispatcher.

### Proof of Concept

1. A legitimate user places an order whose `predispatch.assets` sends 1 ETH to the shared `CallDispatcher`, and whose `predispatch.call` swaps ETH → USDC via Uniswap, but the swap only consumes 0.9 ETH (slippage/partial), or `order.inputs` only lists the USDC token (not native ETH) — 0.1 ETH remains in `CallDispatcher` after `placeOrder` returns, since the sweep loop in `IntentGatewayV2.placeOrder` only iterates `order.inputs` tokens [6](#0-5) .
2. Attacker (any address, no relation to the order) calls `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: 0.1 ether, data: ""})]))` directly.
3. `dispatch()` performs `to.call{value: 0.1 ether}("")` with no check on `msg.sender`, sending the leftover ETH to the attacker [4](#0-3) .

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;

                size := extcodesize(to)
            }

                revert NotContract(to);
            }
