### Title
Git clone protection explicitly disabled during recursive clone re-enables submodule RCE class (CVE-2024-32002 style) - ([File: app/src/lib/git/clone.ts])

### Summary
The upstream report describes an "old" access-control mechanism (`_ALLOW_ALL_` flag on a deprecated component) that was left enabled and combined with an operator/allow-list that still trusted it, letting an attacker route execution through the disabled-but-still-wired path. The closest structural analog in GitHub Desktop is `clone()` in [1](#0-0) , which unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while issuing a `--recursive` clone of a URL that is fully attacker-controlled (a repository URL the user is opening/cloning).

### Finding Description
`clone()` builds the execution environment as: [2](#0-1) 
`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to guard against the class of vulnerabilities where a maliciously crafted repository (with case-confusable or symlinked `.git` paths inside submodules, or clashing directory names) can escape the intended working tree during a recursive clone and execute or overwrite files outside of it — the exact bug class fixed upstream in Git as CVE-2024-32002. By forcing this variable to `'false'` for every clone, GitHub Desktop deliberately turns off the built-in Git protection for all recursive clones, regardless of whether the remote is trusted. Similar to the old BOC in the report — a legacy safety switch (`_ALLOW_ALL_`) that remains wired into a still-trusted execution path (`paymaster.isOperatorAllowed(OLD_BOC)`) — this code path takes a security guard that git-core added specifically to stop attacker-controlled repository content from escaping the checkout boundary, and neutralizes it for every clone GitHub Desktop performs, including clones of arbitrary attacker-supplied URLs (via UI "Clone repository", CLI `--cli-clone`, or `x-github-client://openrepo` deep links resolved through `parseAppURL`/`handleCLIAction`) [3](#0-2) [4](#0-3) .

The only mitigation present is `isClonePathSensitive()`, which blocks a small hardcoded list of destination directories (home dir, `.ssh`, `.gnupg`, `.config`, `.gitconfig`) [5](#0-4) . This guards against path-traversal on the *destination* argument the user supplies, but does nothing to stop a malicious *submodule* inside the cloned repository from exploiting the disabled clone-protection during the recursive `--recursive` submodule checkout that follows — that is a distinct attack surface than the one `isClonePathSensitive` addresses.

### Impact Explanation
If Git's disabled protection is in fact still relied upon by the installed Git version to prevent submodule path confusion attacks, an attacker who controls a repository (the exact "attacker controls a cloned/fetched repository" scenario named as in-scope) could craft a repository with a submodule whose name/path collides with `.git` in a case-insensitive or symlink-aware way. When a victim clones it via GitHub Desktop's `clone --recursive` with clone protection off, this could allow writing files outside the intended working directory or achieving code execution via hook injection during checkout.

### Likelihood Explanation
Likelihood depends on the exact Git version bundled with Desktop and whether the case-sensitivity/symlink primitives that CVE-2024-32002 relied on are still exploitable against that version; I could not confirm the bundled Git's patch level or verify whether `GIT_CLONE_PROTECTION_ACTIVE` still gates a real vulnerability in that version from local code alone. The environment variable is only meaningful if the underlying Git binary still contains the guarded code path, so this should be verified against the vendored Git version before treating it as confirmed remote code execution. `updateSubmodulesAfterOperation` conditionally opts into `protocol.file.allow=always` for `checkoutBranch`/`checkoutCommit` [6](#0-5) [7](#0-6) , but `clone.ts` unconditionally disables clone protection for every clone regardless of `allowFileProtocol`.

### Recommendation
Do not unconditionally set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Only disable it, if at all, for verified/first-party clone sources, and otherwise let Git's native protections run during `--recursive` clone. If the setting was added to work around a compatibility issue, scope it narrowly and document why the mitigation is safe to disable, since it removes an upstream-supplied defense against attacker-controlled repository content.

### Proof of Concept
Not independently verified against the bundled Git version — this requires confirming (1) which Git version is vendored, (2) whether `GIT_CLONE_PROTECTION_ACTIVE=false` reactivates the CVE-2024-32002 submodule-checkout escape in that version, and (3) constructing a malicious repository with a colliding submodule path/case that would be cloned via Desktop's "Clone repository" flow or `x-github-client://openrepo` deep link. I flag this as an unverified/likely finding rather than a confirmed exploit due to inability to inspect the vendored Git binary version from the code index.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
