## Analog Found: `maybe_burn_vat_from_staked_accounts` unconditionally `.unwrap()`/`.expect()`s on values it assumes were pre-validated

### Title
Unconditional `.unwrap()`/`.expect()` on vote-account balance during VAT burn causes validator panic if the pre-filtering invariant is violated - (File: `runtime/src/bank.rs`)

### Summary
The external report's root cause is a value-movement operation (`send{value: msg.value}`) that is assumed to always succeed because of an implicit invariant ("the refund recipient can receive ETH"), but the invariant is never actually checked at the point of the transfer, so the operation reverts and the whole message-processing path dies. `maybe_burn_vat_from_staked_accounts` in Agave has the same shape: it assumes every vote account it iterates has "already been filtered ... to contain enough balance for the VAT" and unconditionally calls `.expect()`/`.unwrap()` on the lamport subtraction and account lookup instead of defensively handling the failure the way the rest of the fee/reward-distribution code in this same codebase does.

### Finding Description
`maybe_burn_vat_from_staked_accounts` burns a fixed "Validator Admission Ticket" (VAT) amount from every staked vote account each epoch: [1](#0-0) 

```
fn maybe_burn_vat_from_staked_accounts(&mut self, epoch_stakes: &VersionedEpochStakes) {
    ...
    for (vote_pubkey, _stake) in vote_accounts.delegated_stakes() {
        let mut account = self.get_account(vote_pubkey).unwrap();
        total_vat += vat_to_burn_per_epoch;
        account.set_lamports(
            account
                .lamports()
                .checked_sub(vat_to_burn_per_epoch)
                .expect(
                    "Vote accounts should have already been filtered to contain enough \
                     balance for the VAT",
                ),
        );
        ...
    }
    ...
}
```

Both the `self.get_account(vote_pubkey).unwrap()` and the `checked_sub(...).expect(...)` are unconditional — they trust two separate assumptions that were established somewhere else, at a different time:

1. That the vote account still exists at `self.get_account(vote_pubkey)`.
2. That `account.lamports() >= vat_to_burn_per_epoch` — an invariant supposedly guaranteed by `clone_and_filter_for_vat`, which filters vote accounts by `minimum_vote_account_balance_for_vat()`: [2](#0-1) 

`minimum_vote_account_balance_for_vat()` is itself derived from `vat_to_burn_per_epoch()`, which is re-derived per call from `self.current_slot_params()`: [3](#0-2) [4](#0-3) 

The filtered vote-account snapshot used for the burn loop (`vote_accounts` from `epoch_stakes`/`filtered_distribution_vote_accounts`) is produced earlier, via `compute_new_epoch_caches_and_rewards` → `clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, self.minimum_vote_account_balance_for_vat())`: [5](#0-4) 

Nothing in this path re-validates the balance/existence of each vote account at the point `maybe_burn_vat_from_staked_accounts` actually performs the subtraction — the guard is purely "trust the filter that ran earlier." This is structurally identical to the ZROToken bug: a value-moving operation is coded as if success is guaranteed by an earlier, disconnected check, with no defensive re-check or graceful failure path at the point of execution.

Critically, this codebase demonstrates elsewhere that the *correct* pattern for lamport-moving side effects during bank freeze/epoch-boundary processing is to fail gracefully rather than panic: `deposit_or_burn_fee`/`deposit_fees` explicitly catch `LamportOverflow`, `InvalidAccountOwner`, and `InvalidRentPayingAccount` and fall back to burning the fee instead of unwrapping: [6](#0-5) 

`maybe_burn_vat_from_staked_accounts` does not follow this same defensive pattern; it panics instead.

### Impact Explanation
A `.expect()`/`.unwrap()` panic inside bank-freeze/epoch-boundary processing (`update_epoch_stakes`, invoked while advancing to a new epoch) is not a per-transaction failure — it aborts the whole validator process at a point that every validator on the network must execute identically. If the invariant "every vote account passed to this loop still has `lamports() >= vat_to_burn_per_epoch`" can be violated for any reason (mismatch between the time/state used for `clone_and_filter_for_vat` and the state read via `self.get_account()` at burn time, or the vote account being closed/reassigned between those two points), this is a **consensus-halt-class bug**: it forces every validator that reaches this epoch boundary to crash simultaneously, rather than a single node degrading.

### Likelihood Explanation
This is Medium likelihood/confidence given the scope of investigation possible here. I was able to confirm:
- The `.unwrap()`/`.expect()` calls are indeed unconditional with no runtime re-check.
- The threshold used for filtering (`minimum_vote_account_balance_for_vat` → `vat_to_burn_per_epoch` → `current_slot_params()`) is a function of slot-dependent parameters, not a fixed constant baked into the filtered snapshot.
- The filtered `VoteAccounts` snapshot (`filtered_distribution_vote_accounts`) is produced once per epoch transition and cached in `epoch_stakes`, while `maybe_burn_vat_from_staked_accounts` re-derives `vat_to_burn_per_epoch()` fresh from `self` (the child bank) at burn time.

What I could **not** fully confirm from local code alone, due to index/tool limits, is the exact call ordering guarantee between `compute_new_epoch_caches_and_rewards` (which produces the filtered snapshot) and `maybe_burn_vat_from_staked_accounts` (which consumes it) relative to any code path that could change `vat_to_burn_per_epoch()`'s value or a vote account's lamports between those two points within the same epoch-boundary processing. If such a path exists (e.g., a governance/feature-activated change to VAT parameters taking effect exactly at that boundary, or a vote-account close/withdraw racing with the epoch-boundary code before the burn loop runs), the panic is reachable by any validator naturally producing/replaying that slot — no malicious actor is required. This should be verified against the full call graph before treating it as certain, but the code as written contains no defensive check.

### Recommendation
Replace the unconditional `.unwrap()`/`.expect()` calls in `maybe_burn_vat_from_staked_accounts` with graceful handling that mirrors the pattern already used in `deposit_or_burn_fee`/`deposit_fees`: if `self.get_account(vote_pubkey)` returns `None`, or `checked_sub(vat_to_burn_per_epoch)` fails, skip/burn-log that account instead of panicking, and only assert defensively (with `debug_assert!`) outside of any code path that is reachable during normal, non-adversarial cluster operation.

### Proof of Concept
Not runnable from static analysis alone — reproducing this requires constructing an epoch boundary where a vote account included in `filtered_distribution_vote_accounts` has, at the moment `maybe_burn_vat_from_staked_accounts` executes, either been removed from accounts-db or has a lamport balance below `self.vat_to_burn_per_epoch()`, e.g. by exploiting a timing gap between when `clone_and_filter_for_vat` computed the snapshot (using the value of `vat_to_burn_per_epoch()` at that point) and when the burn loop re-reads `vat_to_burn_per_epoch()`/`self.get_account()` on the child bank. Confirming a concrete trigger requires tracing `update_epoch_stakes`'s call sites and `slot_params_at_slot` semantics (in `runtime/src/slot_params.rs`), which was not fully explorable within available tool budget.

```rust
    /// Burn the Validator Admission ticket from each vote account if Alpenglow is enabled
    ///
    /// Note: This must ONLY be called after the vote accounts have been filtered (`clone_and_filter_for_vat`)
    /// to the top `MAX_ALPENGLOW_VOTE_ACCOUNTS` that contain enough balance for admission.
    fn maybe_burn_vat_from_staked_accounts(&mut self, epoch_stakes: &VersionedEpochStakes) {
        let feature_snapshot = self.feature_set.snapshot();
        if !feature_snapshot.alpenglow {
            return;
        }

        let vat_to_burn_per_epoch = self.vat_to_burn_per_epoch();
        let vote_accounts = epoch_stakes.stakes().vote_accounts();
        debug_assert!(vote_accounts.len() <= 2000);
        // +1 for the incinerator account
        let mut accounts_to_store: Vec<(Pubkey, AccountSharedData)> =
            Vec::with_capacity(vote_accounts.len() + 1);
        let mut total_vat = 0u64;

        // Vote accounts have already been filtered by clone_and_filter_for_vat to only include
        // accounts with non-zero stake and sufficient balance.
        for (vote_pubkey, _stake) in vote_accounts.delegated_stakes() {
            let mut account = self.get_account(vote_pubkey).unwrap();
            total_vat += vat_to_burn_per_epoch;
            account.set_lamports(
                account
                    .lamports()
                    .checked_sub(vat_to_burn_per_epoch)
                    .expect(
                        "Vote accounts should have already been filtered to contain enough \
                         balance for the VAT",
                    ),
            );
            accounts_to_store.push((*vote_pubkey, account));
        }

        // Per SIMD-0357, transfer collected VAT to the incinerator account.
        let mut incinerator_account = self.get_account(&incinerator::id()).unwrap_or_default();
        incinerator_account.set_lamports(
            incinerator_account
                .lamports()
                .checked_add(total_vat)
                .unwrap(),
        );
        accounts_to_store.push((incinerator::id(), incinerator_account));

        self.store_accounts((self.slot, accounts_to_store.as_slice()), None);
        info!(
            "Transferred total VAT of {total_vat} lamports to incinerator from staked vote \
             accounts"
        );
    }
```

```rust
    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
        }
```
