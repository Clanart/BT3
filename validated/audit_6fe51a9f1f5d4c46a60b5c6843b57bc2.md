## Analysis

The concern is valid: `Keeper.OnRecvPacket`'s native-ERC20 branch calls `k.ConvertCoinNativeERC20` directly on the live `ctx`, and that function performs its escrow, EVM unescrow-transfer, and burn as three sequential, independently-committed state mutations with no internal branching/rollback guard: [1](#0-0) 

If the `CallEVM(..., "transfer", ...)` step fails (contract paused, blacklisted receiver, out-of-gas, self-destructed logic, etc.), the function returns the error *after* `SendCoinsFromAccountToModule` has already escrowed the coins, and *before* `BurnCoins` ever runs: [2](#0-1) 

`OnRecvPacket` then simply converts this into an error acknowledgement: [3](#0-2) 

The critical fact is that this callback is invoked from `ibc-go`'s `MsgRecvPacket` handler, which does **not** treat a failed/error acknowledgement as a Go-level error for the surrounding message — the message itself is considered successfully processed regardless of `ack.Success()`, and the write acknowledgement, not a rollback, is what differs. Since `ctx` is mutated in place (no `ctx.CacheContext()`/`writeFn()` pattern is used here, unlike the analogous defensive pattern the codebase already uses elsewhere for EVM callbacks): [4](#0-3) 

...the escrow performed before the EVM failure is committed together with the rest of the transaction, while the burn never happens. This differs from the direct `MsgConvertCoin` path, where `ConvertCoin`'s error is propagated as a genuine `error` return from the msg handler, letting baseapp's per-message branched store discard the partial escrow automatically: [5](#0-4) 

That automatic protection does not exist on the IBC receive-callback path, because the erc20 keeper's `OnRecvPacket`/`ConvertCoinNativeERC20` never returns a Go `error` to the ibc-go message handler — only an acknowledgement object.

### Impact and scope caveats

This is a genuine atomicity gap in scoped code (`x/erc20/keeper/msg_server.go` `ConvertCoinNativeERC20`, `x/erc20/keeper/ibc_callbacks.go` `OnRecvPacket`), not merely relayer/validator misbehavior — an honest relayer forwarding a legitimate packet is sufficient to trigger it. Exploitability requires a way to make the EVM `transfer` call fail *after* the pair has already gone through `MintingEnabled` (i.e., a native-ERC20 token pair whose underlying contract can be made to revert `transfer` for a chosen recipient — e.g., a pausable/blacklist-capable "native" ERC20 that was permissionlessly registered, or an out-of-gas/self-destruct condition). When that happens, the escrowed bank-coin balance is permanently trapped in the `x/erc20` module account with no burn and no automatic refund path (unlike the sender-side `ConvertCoinToERC20FromPacket`, which explicitly tolerates and logs conversion failure without mutating state destructively beforehand).

### Title
Non-atomic escrow/burn in `ConvertCoinNativeERC20` permanently traps IBC-received value when the EVM unescrow-transfer fails mid-conversion - (File: `x/erc20/keeper/msg_server.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`Keeper.OnRecvPacket`'s native-ERC20 case calls `ConvertCoinNativeERC20`, which escrows bank coins to the `erc20` module account, then attempts an EVM `transfer` call to unescrow the corresponding ERC20 tokens to the recipient, and only afterwards burns the escrowed coins. If the EVM call fails, the function returns an error without rolling back the escrow, and because this path runs through `ibc-go`'s `MsgRecvPacket` handler (which commits state regardless of acknowledgement success/failure), the escrow is committed permanently while the corresponding burn and ERC20 unescrow never occur.

### Finding Description
`ConvertCoinNativeERC20` (`x/erc20/keeper/msg_server.go:237-306`) performs escrow → EVM unescrow-transfer → burn directly against the passed-in `sdk.Context`, with no `ctx.CacheContext()`/`writeFn()` branch protecting the sequence. When invoked from `Keeper.OnRecvPacket` (`x/erc20/keeper/ibc_callbacks.go:137-139`), any EVM-call failure at the "unescrow tokens and send to receiver" step returns after the escrow (`SendCoinsFromAccountToModule`) has already succeeded, and before `BurnCoins` runs. `OnRecvPacket` converts this failure into `channeltypes.NewErrorAcknowledgement(err)`, but this only changes what acknowledgement is written to the channel — it does not undo prior state mutations in the same `ctx`, since `MsgRecvPacket`'s handler treats the packet as successfully processed (from baseapp's perspective) irrespective of ack success/failure. The codebase elsewhere (`x/ibc/callbacks/keeper/keeper.go`) demonstrates awareness of exactly this hazard by explicitly using `ctx.CacheContext()`/`writeFn()` to guard EVM-callback state changes, but that pattern is absent from `ConvertCoinNativeERC20`.

### Impact Explanation
Escrowed value becomes permanently stuck in the `erc20` module account: the bank coin was moved out of the recipient's balance but never burned, and the corresponding ERC20 tokens remain locked in the contract under module custody, never transferred to the recipient. There is no compensating refund/retry mechanism for this path (unlike `ConvertCoinToERC20FromPacket`, used for sender-side ack/timeout, which tolerates conversion failure without first mutating balances destructively). This matches the "permanent freezing/locking of user funds" Critical impact criterion.

### Likelihood Explanation
Triggering requires a native-ERC20 token pair whose contract's `transfer` function can be made to revert for a chosen recipient after tokens are already escrowed on the module address (e.g., pausable/blacklistable ERC20 contracts, which can be permissionlessly registered when `PermissionlessRegistration` is enabled) or genuine EVM execution failures (e.g., gas exhaustion in complex token logic). No validator, relayer, or governance privilege is required — an ordinary IBC round-trip of a native-ERC20-backed coin combined with a contract-level condition causing the unescrow transfer to fail is sufficient.

### Recommendation
Wrap the escrow → EVM-unescrow → burn sequence in `ConvertCoinNativeERC20` in an internal `ctx.CacheContext()` and only call `writeFn()` after the EVM call and burn both succeed, mirroring the pattern already used in `x/ibc/callbacks/keeper/keeper.go`. This ensures partial escrow never persists when the conversion cannot complete atomically.

### Proof of Concept
1. Permissionlessly register (or otherwise obtain) a native-ERC20 token pair whose contract's `transfer` function can be paused/blacklisted for a target address after deployment.
2. Convert ERC20 tokens to the bank-coin representation and IBC-transfer them out to another chain, escrowing the coin on the origin chain and locking the ERC20 tokens under the module address.
3. Pause/blacklist the intended recipient in the ERC20 contract.
4. Relay the coin back to the origin chain via IBC; `OnRecvPacket`'s native-ERC20 branch runs `ConvertCoinNativeERC20`, which escrows the just-unescrowed bank coin to the module account, then fails the EVM `transfer` call due to the pause/blacklist.
5. Observe that the module account holds an escrowed, un-burned balance of `pair.Denom` that is never freed, while the recipient never gets the ERC20 tokens back — the funds are permanently stuck with no compensating refund path.
