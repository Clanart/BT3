### Title
Unregistered-chain module authentication falls back to trusting the gateway's own address — allows forging governance/withdrawal requests - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` authenticates incoming cross-chain `PostRequest`s by comparing the sender (`request.from`) against `instance(request.source)`. Unlike the mainline EVM implementation, this `instance()` function does not revert for unregistered/unknown source chains — it silently falls back to returning `address(this)`. Combined with the fact that the gateway is deployed at a deterministic CREATE2 address that is intentionally identical across all chains, this lets an unprivileged attacker deploy a lookalike contract at that same address on any chain that Hyperbridge can relay from (even one never explicitly registered as a peer) and dispatch a forged `PostRequest` whose `from` equals `address(this)`. The message passes `authenticate()` because `module == instance(request.source) == address(this)`, letting the attacker's message execute as if it originated from the gateway's trusted counterpart.

### Finding Description
`instance()` is defined as: [1](#0-0) 

```
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
```

`authenticate()` uses this fallback-prone lookup to validate the sender of an incoming request: [2](#0-1) 

```
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

For any `request.source` state-machine id that has never been registered via `NewDeployment`/`initialize`, `instance()` returns `address(this)` instead of reverting. This contradicts the mainline (non-Tron) implementation, whose `_instance()` explicitly reverts with `UnknownInstance` when a peer is not registered: [3](#0-2) 

The gateway is deployed via deterministic CREATE2 specifically so its address is identical on every chain (documented in the initializer's own comment): [4](#0-3) 

Because `address(this)` is public knowledge and reproducible via CREATE2, an attacker can deploy an arbitrary contract at that exact address on any chain that is not registered as a peer in `_instances` (e.g., a chain that was never intended to interoperate with this instance, or a chain added to Hyperbridge later without the gateway operator registering it here). From that contract, the attacker dispatches a `PostRequest` toward the victim `IntentGatewayV2`, with `from = abi.encodePacked(address(this))`. Since Hyperbridge only requires a valid consensus/state proof for the *dispatching chain itself* (not that the IntentGateway module has approved that chain as a peer), the request reaches `onAccept`, `authenticate()` passes (`module == instance(unregistered_source) == address(this)`), and the request body is dispatched to privileged handlers such as `NewDeployment`, `UpdateParams`, `SweepDust`, or `RefundEscrow`.

### Impact Explanation
This breaks the "cross-chain admin or host-management effects must not be reachable through … wrong module bindings" invariant. Concretely, an attacker who can deploy a contract at the deterministic gateway address on some unregistered/foreign chain (any EVM chain that shares the same CREATE2 factory/salt/bytecode, or that simply lacks bytecode collision protection) can:
- Register a rogue `Deployment` for another chain via `RequestKind.NewDeployment`, redirecting all future cross-chain trust for that chain to an attacker-controlled address.
- Trigger `RequestKind.RefundEscrow` or `RedeemEscrow` to release escrowed funds to an attacker-chosen beneficiary, causing direct fund loss.
- Overwrite `Params` (fees, dispatcher, price oracle) via `UpdateParams`.
This is unauthorized execution / false module-binding acceptance leading to loss of escrowed funds and manipulation of protocol parameters — squarely within the bounty's accepted impact categories.

### Likelihood Explanation
The path requires only that the attacker control a contract deployed at the known deterministic gateway address on a chain Hyperbridge can relay proofs from but that was never registered as a peer for this specific `IntentGatewayV2` instance. No relayer, prover, or governance compromise is needed — the attacker is an ordinary chain participant dispatching a normal ISMP `PostRequest` from their own deployed contract. The likelihood hinges on whether such an "off-list" chain/CREATE2-address collision is realistically obtainable (e.g., new EVM chains are onboarded to Hyperbridge before the gateway operator explicitly calls the peer-registration flow, or a chain's CREATE2 factory permits the same deployer/salt/bytecode combination), which is plausible given the explicit design goal of identical addresses across chains.

### Recommendation
Change `instance()` (and any caller relying on it for authentication) to revert on an unregistered `stateMachineId` instead of silently returning `address(this)`, matching the safe behavior already implemented in `IntentsBase._instance()`. If the `address(this)` fallback is intentionally needed for the "same-chain" case (i.e., where a request genuinely originates from the local chain), that case should be handled by explicitly checking `request.source == host()` rather than through a permissive default in a generic instance-lookup function that is also used for authenticating arbitrary remote sources.

### Proof of Concept
1. Attacker inspects `IntentGatewayV2`'s bytecode/salt (public) and deploys an identical contract via CREATE2 at the same address `A` on Chain X, a state machine that Hyperbridge can generate consensus/state proofs for but that the victim `IntentGatewayV2` deployment has never registered in `_instances` (no `NewDeployment` call for Chain X).
2. From that contract on Chain X, attacker calls the local ISMP dispatcher to send a `PostRequest`:
   - `source = ChainX_id`, `dest = victim_chain_id`, `from = abi.encodePacked(A)`, `to = abi.encodePacked(victimGatewayAddress)`
   - `body = bytes.concat(bytes1(uint8(RequestKind.RefundEscrow)), abi.encode(WithdrawalRequest({commitment: knownOrderCommitment, tokens: victimEscrowedTokens, beneficiary: attackerAddress})))`
3. Hyperbridge relays and proves the request (only a valid Chain X consensus/state proof is required — no IntentGatewayV2-level peer check happens at the protocol layer).
4. Victim `IntentGatewayV2.onAccept` is invoked; `authenticate()` computes `module = A`, `instance(ChainX_id)` returns `address(this)` because Chain X was never registered, and `address(this) == A` by construction, so authentication succeeds.
5. `_withdraw` executes, releasing escrowed tokens to `attackerAddress` — funds theft without compromising any relayer, prover, or admin key.
