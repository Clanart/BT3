### Title
Consumed scheduler inputs are permanently lost when `prepare_send` produces no transaction — funds reported received but never spendable - (File: processor/src/multisigs/mod.rs)

### Summary
The kernel bug class here is "a resource is destroyed on the assumption an operation completed, when in fact it failed" (rehash assumed migration complete because credits were non-negative, and destroyed a region still referenced by filters). In Serai's multisig rotation/planning code, `processor/src/multisigs/mod.rs` exhibits the same shape: a `Plan`'s inputs are removed from the `Multisig`'s scheduler and the plan is persisted via `PlanDb::save_active_plan`, but when `prepare_send` returns `tx: None` no transaction is created and the consumed inputs are never returned to the scheduler. The in-code TODO explicitly acknowledges this: "If the TX is None, restore its inputs to the scheduler for efficiency's sake" (line ~792). Those outputs are therefore dropped from all future planning even though they remain on-chain and were already counted as handled.

### Finding Description
In `plans_from_block`/`sign plans` loop (`processor/src/multisigs/mod.rs`, ~lines 716–794):

1. For each `plan`, `PlanDb::save_active_plan` records the plan as active and `prepare_send` is invoked (~line 744).
2. `prepare_send` takes ownership of the plan's selected inputs (they have already been removed/marked-consumed in the scheduler as part of plan construction).
3. If the returned `PreparedSend` has `tx == None`, no transaction is broadcast and `register_eventuality` is skipped (the `if let Some((tx, eventuality))` guard at ~line 778), so no completion tracking exists either.
4. The TODO at ~line 792 confirms the consumed inputs are not restored: "If the TX is None, restore its inputs to the scheduler for efficiency's sake. If this TODO is removed, also reduce the operating costs."

`prepare_send` can yield `tx: None` when the prepared transaction is not worth/able to be sent (e.g., fee/dust constraints on the constructed transaction — reachable when an unprivileged party sends a small Bitcoin transaction to the multisig address that gets folded into a `Plan` but cannot economically be spent). The result is the analog of the CVE: the "region" (the output's scheduling state) is destroyed while still "referenced" (the UTXO still exists on-chain and was treated as consumed), because `tx == None` was not treated as a failed migration of those inputs.

### Impact Explanation
Outputs consumed into a `Plan` whose `prepare_send` yields `tx: None` are permanently removed from the scheduler and never revisited: they are excluded from future `Batch`es (the scheduler considers them spent), and during rotation (`RotationStep::ForwardFromExisting` / `ClosingExisting`, ~lines 922–932) only scheduler-tracked outputs are forwarded — an output the scheduler forgot will not be forwarded to the new multisig. The deposit was scanned and accounted (the plan was saved as active), but the underlying coins become effectively unspendable/unrecoverable by the multisig: funds reported received that are not spendable. Repeated dust deposits can strand arbitrary small amounts across many outputs.

### Likelihood Explanation
Reachable by an unprivileged party: anyone can send a Bitcoin transaction to the current multisig address (Scanner matches `script_pubkey` only), creating a `PlanFromScanning`/`Plan` consuming that output. If fee conditions make `prepare_send` decline to produce a transaction (`tx: None`), the input is stranded without any error path restoring it. Likelihood is moderate: it requires a plan whose prepared send is declined, which is a normal economic edge case rather than requiring collusion or privileged access.

### Recommendation
Mirror the kernel fix — "don't destroy the region if migration failed": when `prepare_send` returns `tx: None`, restore the plan's inputs to the originating scheduler (`existing.scheduler` or `new.scheduler` per `plan.key`), roll back the `OperatingCostsDb` accumulation for that plan, and do not leave the plan recorded as active in `PlanDb` (or record it distinctly so a later block can retry). At minimum, implement the existing TODO so a failed send leaves the output schedulable.

### Proof of Concept
Source-level argument (execution unavailable):

1. Attacker sends a minimal/dust-value Bitcoin transaction to the current multisig `script_pubkey`.
2. `Scanner` detects it; `plans_from_block` builds a `Plan` with that output as input, removing it from `self.existing.scheduler`/`new.scheduler` availability.
3. `prepare_send` computes the transaction and determines the fee makes the send non-viable, returning `PreparedSend { tx: None, ... }`.
4. `PlanDb::save_active_plan` was already committed (~line 726) and `OperatingCostsDb::set_operating_costs` already updated (~line 757); the `if let Some((tx, eventuality))` guard (~line 778) skips eventuality registration, and the TODO at ~line 792 leaves the input unrestored.
5. The output is now untracked by the scheduler: no future `Batch` will spend it and rotation forwarding only walks scheduler outputs (~lines 922–932), so the deposited coins are stranded despite having been counted as received.

Uncertainty: the exact set of conditions under which `prepare_send` returns `tx: None` was not fully enumerated (its body in `processor/src/networks/mod.rs` was not read in detail before finalizing); the confirming evidence is the in-code TODO acknowledging inputs are not restored on `tx == None`.
