### Title
Missing double-check in `InternalLazyField.ensureInitialized()` allows racing threads to re-parse and overwrite an already-initialized lazy field value - (File: `java/core/src/main/java/com/google/protobuf/InternalLazyField.java`)

### Summary
The external report's failed invariant is a shared, mutable field (`s.proposal`) that is checked-then-set by concurrent callers without a lock, letting a second caller act on state that the first caller is concurrently establishing. In Java protobuf's `InternalLazyField`, the field `value` (holding a lazily-parsed sub-message/extension) is likewise checked-then-set in `ensureInitialized()`, and the synchronized block that performs the actual parse-and-assign is missing the inner re-check of `value != null` that the sibling class `LazyFieldLite.ensureInitialized()` correctly performs. This lets two threads racing on `getValue()`/`hashCode()`/`equals()`/`toString()` both perform the parse and successively overwrite `value`, violating the class's own documented invariant ("once value ... is set, they will not be changed").

### Finding Description
`InternalLazyField` documents its own invariant explicitly: [1](#0-0) 

`getValue()` calls `ensureInitialized()`, which is the only gate protecting `value`: [2](#0-1) 

The outer check `if (value != null) return;` at line 203 is unsynchronized, so multiple threads can pass it simultaneously while `value` is still `null`. Once inside the `synchronized (this)` block, the code only re-checks `corrupted` (line 208) — it never re-checks `value != null` before parsing and assigning `value` (lines 211–227). Consequently, if thread A wins the lock, parses, sets `value`, and exits the block, a thread B that had also passed the outer check and is waiting on the lock will still execute the full parse-and-assign body again, overwriting `value` a second time.

Compare this to the sibling class `LazyFieldLite.ensureInitialized(MessageLite defaultInstance)`, which correctly implements double-checked locking with the re-check inside the lock: [3](#0-2) 

That inner `if (value != null) return;` (lines 474–476) is exactly the check missing from `InternalLazyField.ensureInitialized()`. This is a structural/functional regression relative to the established pattern used elsewhere in the same codebase for the identical problem (lazy, once-only initialization of a shared field under concurrent read access), which is the direct analog to the external report's "check-then-act on shared field without synchronization" bug class.

`InternalLazyField` is used by `FieldSet`/`MessageReflection`/`GeneratedMessage`/`DynamicMessage`/`MessageSetSchema` to back lazily-parsed extension/message fields (28, 36, 7, 5, 4, 2 references respectively). Any code path where an application shares a parsed message across threads and lets multiple threads independently trigger `getValue()`/`hashCode()`/`equals()`/`toString()` on the same lazy extension field is a realistic concurrent-read scenario — the class's own javadoc for `getValue()` implies it is meant to be safely callable concurrently ("Returns the parsed message value"), unlike `LazyFieldLite`, which explicitly documents itself as thread-compatible for concurrent reads.

I was not able to fully confirm within this session which specific parsing entry points construct an `InternalLazyField` for extensions during binary parse (the concrete call sites in `FieldSet.java`/`MessageSetSchema.java` were not resolved by the grep patterns tried), so the exact generated-code trigger conditions (e.g., `[lazy=true]` extension fields or MessageSet items) should be verified with a broader search before filing, but the field's constructor and the surrounding class comments make clear that `bytes`→`value` lazy parsing is meant to happen post-parse, on first access from application code — i.e., in the untrusted-client-exposure model, this is triggered by ordinary reads of a message that was produced from bounded, attacker-supplied bytes with a lazy sub-message, not by any privileged operation.

### Impact Explanation
The direct, provable consequence is a redundant parse of the same bytes (CPU waste, not itself security-critical) and — more importantly — a genuine correctness/integrity violation of the class's documented immutability invariant: `value` can be silently replaced by a second, distinct parsed `MessageLite` instance after other code has already observed and potentially retained a reference to the first instance (e.g. via `mergeFrom`'s `lazyField.value.toBuilder()` pattern at lines 118 and 172 of the same file, or via any external caller holding a previously returned `getValue()` reference). Two threads (or a thread and a later caller) can therefore end up observing/using two different object identities for what should be one immutable, once-parsed value, breaking reference-equality assumptions and general repeatable-read/immutability expectations relied on by callers throughout `FieldSet`, `MessageReflection`, `DynamicMessage`, and `MessageSetSchema`. This is a data-integrity/correctness bug reachable purely through normal concurrent reads of parsed messages containing lazy fields — not a crash, RCE, or resource-exhaustion primitive, and no confidentiality bypass was identified. Severity is therefore best characterized as Medium: a genuine, provable double-checked-locking defect with a concrete correctness impact, but bounded to identity/consistency corruption of an in-process object graph rather than memory safety or disclosure.

### Likelihood Explanation
Likelihood is high in any application that (a) parses attacker-supplied bytes into a message containing a lazily-parsed extension/message-set field, and (b) shares the resulting message object across threads for concurrent reads (a normal, encouraged usage pattern for immutable protobuf messages) hitting `getValue()`, `hashCode()`, `equals()`, or `toString()` at nearly the same time before the field is first materialized. This mirrors exactly the pattern the Python and C++ codebases in this same repository already have dedicated regression tests for (`thread_safe_test.py`'s `testConcurrentLazyUnpackAndRead`, `hpb`'s `message_lock_test.cc` concurrent-extension tests), underscoring that "concurrent first access to a lazy field" is a recognized, previously-hardened race-condition class in protobuf — but `InternalLazyField.java` (a very recently added file per its 2026 copyright header) omits the inner re-check that the equivalent, older `LazyFieldLite` class already has.

### Recommendation
Add the missing double-check inside the synchronized block of `InternalLazyField.ensureInitialized()`, mirroring `LazyFieldLite.ensureInitialized()`:
```java
private void ensureInitialized() throws InvalidProtocolBufferException {
  if (value != null) {
    return;
  }
  synchronized (this) {
    if (value != null) {   // <-- missing re-check, add this
      return;
    }
    if (corrupted) {
      throw new InvalidProtocolBufferException("Repeat access to corrupted lazy field");
    }
    ... // existing parse logic
  }
}
```
Additionally, add a concurrency regression test analogous to `thread_safe_test.py`'s `testConcurrentLazyUnpackAndRead` / the `hpb` `ConcurrentAccessDoesNotRace*` tests, targeting `InternalLazyField` specifically, to lock in the fix and catch future regressions of this pattern.

### Proof of Concept
Conceptual reproduction (not executed in this session — the finding is based on direct code reading of the two methods below):
1. Construct an `InternalLazyField` from bounded, attacker-controlled bytes representing a valid sub-message, e.g. `new InternalLazyField(defaultInstance, registry, bytes)` (as done by generated/reflection code when parsing a lazy or MessageSet extension field).
2. Spawn two threads that both call `field.getValue()` at (approximately) the same time, before either has observed a non-null `value`.
3. Both threads pass the unsynchronized guard `if (value != null) return;` (`InternalLazyField.java:203`) because `value` is still `null`.
4. Thread A acquires the monitor, parses `bytes`, assigns `value = ...` (`InternalLazyField.java:219-222`), and releases the lock.
5. Thread B, already blocked waiting for the same monitor, then enters the block and — because there is no `if (value != null) return;` inside the synchronized block — re-parses the same bytes and reassigns `value` to a second, distinct `MessageLite` instance (`InternalLazyField.java:207-228`), even though the invariant at lines 18–20 says `value` must not be changed once set.
6. Any caller that captured a reference to the first `value` (e.g. via `mergeFrom`'s `lazyField.value.toBuilder()` at line 118) now holds a stale/orphaned object relative to subsequent `getValue()` calls, which return the second instance — demonstrating the invariant break and identity inconsistency.

```java
  /**
   * Guarantees that `this.value` is non-null or throws.
   *
   * @throws InvalidProtocolBufferException If `bytes` cannot be parsed.
   */
  private void ensureInitialized() throws InvalidProtocolBufferException {
    if (value != null) {
      return;
    }

    synchronized (this) {
      if (corrupted) {
        throw new InvalidProtocolBufferException("Repeat access to corrupted lazy field");
      }
      try {
        // `bytes` is guaranteed to be non-null since `value` was null.
        CodedInputStream input = bytes.newCodedInput();
        input.enableAliasing(/* enabled= */ true);
        // When lazyExtensionEnabled() returns true, it means all extensions including MessageSet's
        // will be fully parsed. When it returns false, it basically implies this can only be a
        // MessageSet extension, and we should fall back to the old behavior of silently returning
        // the default instance on corrupted extensions i.e. a full parse.
        value =
            extensionRegistry.lazyExtensionEnabled()
                ? defaultInstance.getParserForType().parsePartialFrom(input, extensionRegistry)
                : defaultInstance.getParserForType().parseFrom(input, extensionRegistry);
        input.checkLastTagWas(0);
      } catch (InvalidProtocolBufferException e) {
        corrupted = true;
        throw e;
      }
    }
  }
```

```java
  /** Might lazily parse the bytes that were previously passed in. Is thread-safe. */
  protected void ensureInitialized(MessageLite defaultInstance) {
    if (value != null) {
      return;
    }
    synchronized (this) {
      if (value != null) {
        return;
      }
      try {
        if (delayedBytes != null) {
          // The extensionRegistry shouldn't be null here since we have delayedBytes.
          MessageLite parsedValue =
              defaultInstance.getParserForType().parseFrom(delayedBytes, extensionRegistry);
          this.value = parsedValue;
          this.memoizedBytes = delayedBytes;
        } else {
          this.value = defaultInstance;
          this.memoizedBytes = ByteString.EMPTY;
        }
      } catch (InvalidProtocolBufferException e) {
        // Nothing is logged and no exceptions are thrown. Clients will be unaware that this proto
        // was invalid.
        this.corrupted = true;
        this.value = defaultInstance;
        this.memoizedBytes = ByteString.EMPTY;
      }
    }
  }
```
