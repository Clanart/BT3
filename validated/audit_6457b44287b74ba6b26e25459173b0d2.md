### Title
Missing binding of `message.height.stateMachineId` to request `dest`/`source` in EVM `handlePostRequestTimeouts`/`handleGetRequestTimeouts` allows non-membership proofs from an unrelated chain to falsely trigger timeouts - (File: `evm/src/core/HandlerV2.sol`)

### Summary
The Arbitrum bug's core broken invariant is that a piece of state (a timer) is inherited by an entity based on a generic relationship check (level + `mutualId`) that does not verify the entity is *actually* the specific one that produced the state, letting a dishonest sibling borrow legitimacy meant for another edge. The Hyperbridge analog is in `HandlerV2.sol`'s timeout handlers: a request's timeout is validated using a caller-supplied `StateMachineHeight` whose `stateMachineId` is never checked against the request's actual `dest` (for POST) or `source` (for GET), so a non-membership proof taken from a completely unrelated, never-targeted chain is accepted as proof that the request was never delivered.

### Finding Description
`handlePostRequestTimeouts` and `handleGetRequestTimeouts` in [1](#0-0)  and [2](#0-1)  fetch a `StateCommitment` purely from the caller-provided `message.height` (a `StateMachineHeight{stateMachineId, height}`) and then verify a non-membership proof of the request-receipt (or response-receipt) key against that commitment's `stateRoot`. Nowhere in either function is `message.height.stateMachineId` checked to equal `request.dest` (POST case) or `request.source` (GET case).

Contrast this with the Rust/Substrate core implementation, which explicitly enforces this binding: [3](#0-2) 
Here `dest_chain != timeout_proof.height.id.state_id` is checked (unless an allowed proxy relationship exists) before the non-membership proof is accepted. The EVM `HandlerV2.sol` timeout handlers have no equivalent check — the only guards are:
1. `request.timeout() > state.timestamp` → revert `MessageNotTimedOut` (timestamp taken from the attacker-chosen `state`, not necessarily the real destination's clock)
2. `meta.sender == address(0)` → revert `UnknownMessage`, described in-code as also serving as "source check" [4](#0-3) , but this only proves the request commitment (hash of the *whole* request struct, including its real `dest`) still exists on the *source* chain — it says nothing about which chain the supplied non-membership proof was taken from.
3. Non-membership of the receipt key in the *chosen* state root.

Because the receipt storage prefix/key layout (`REQUEST_RECEIPTS_STORAGE_PREFIX` / `RESPONSE_RECEIPTS_STORAGE_PREFIX` + commitment) is identical across all configured Substrate-based (Polkadot-trie) state machines that the host tracks commitments for, and because a request only ever produces a receipt on its true destination chain, the non-membership proof trivially succeeds against the storage root of *any other configured chain* that was never the request's destination — since that chain never had a receipt for this commitment to begin with.

### Impact Explanation
This is a false-state-acceptance / double-settlement bug: a POST or GET request that has genuinely been delivered and processed on its correct destination chain can still be "timed out" on the source chain using a state commitment belonging to a different, unrelated (but legitimately configured) state machine, whose challenge period has already elapsed. `host.dispatchTimeOut()` [5](#0-4)  then invokes `IApp.onPostRequestTimeout` (or `onGetTimeout`) on the source-chain application and refunds the relayer fee, deleting the request commitment. If the source application's timeout handler reverses escrowed state (refunds a bridged asset, releases collateral, credits a paymaster balance, etc.) as most bridge/intent applications do, this results in the same cross-chain action being settled twice: once by the legitimate delivery on the real destination, and once by the bogus timeout reversal on the source — a direct loss/duplication of funds. This falls squarely within the bounty's listed impacts: "false proof acceptance," "duplicate settlement," and "loss/duplication of bridged funds."

### Likelihood Explanation
The path is fully permissionless: `handlePostRequestTimeouts`/`handleGetRequestTimeouts` are documented as callable by anyone [6](#0-5) . No malicious relayer, prover, or admin is required — an ordinary user only needs (a) a request they control that has genuinely been delivered to its real destination but whose commitment is still pending on the source (common, since POST requests without an app-level response keep their commitment until timeout/response), and (b) any other already-finalized, challenge-period-elapsed `StateCommitment` for a different configured state machine, which is routinely available since Hyperbridge tracks commitments for many chains. Constructing the non-membership proof for the wrong chain is trivial because the key simply never existed there.

### Recommendation
Add an explicit binding check mirroring the Rust core logic before verifying the non-membership proof:
- In `handlePostRequestTimeouts`: require `message.height.stateMachineId == request.dest` (or matches an explicitly configured/allowed proxy for `request.dest`, analogous to `is_allowed_proxy`/`check_state_machine_client` in `modules/ismp/core/src/handlers/timeout.rs`).
- In `handleGetRequestTimeouts`: require `message.height.stateMachineId == request.source` under the same proxy exception rules.
Reject the message otherwise, so a non-membership proof can only be sourced from the state machine that was actually the request's real counterparty.

### Proof of Concept
1. User A dispatches `DispatchPost{dest: ChainX, ...}` via `EvmHost.dispatch`, escrowing funds on the source chain and creating `_requestCommitments[commitment]`.
2. The request is legitimately relayed and delivered to `ChainX` (`handlePostRequests` there stores a request receipt and the destination app executes its logic, e.g. releases bridged tokens to the recipient).
3. Because the destination app doesn't emit a response, `_requestCommitments[commitment]` remains on the source chain.
4. Attacker waits for the request's `timeout_timestamp` to be less than the `timestamp` field of *any other* already-finalized `StateCommitment` the source host holds for a different `StateMachineHeight` (e.g. `ChainY`, unrelated to this request), whose challenge period has elapsed.
5. Attacker calls `handlePostRequestTimeouts(host, message)` with `message.height` set to that `ChainY` height and a (trivially valid) non-membership proof of key `REQUEST_RECEIPTS_STORAGE_PREFIX || commitment` against `ChainY`'s state root — this key never existed on `ChainY` because the request was never destined there.
6. All checks pass (`request.timeout() > state.timestamp` uses `ChainY`'s clock; `meta.sender != 0`; non-membership proof valid), so `host.dispatchTimeOut` fires, calling `onPostRequestTimeout` on the source app, which reverses/refunds the escrow — even though the funds were already released on `ChainX` in step 2, producing a double payout/duplicate settlement.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
