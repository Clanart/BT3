### Title
Stale-state OAuth completion due to missing re-validation after external network calls in `resolveOAuthRequest()` - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.resolveOAuthRequest()` validates the in-flight OAuth session (`this.state.oauthState.state !== action.state`) *before* making two external network calls (`requestOAuthToken`, `fetchUser`), but never re-validates `this.state`/`this.state.oauthState` *after* those awaits complete before invoking `this.state.oauthState.onAuthCompleted(account)`. This is the same "check happens before the external interaction, but the effect is applied using freshly-read state after the interaction" anti-pattern described in the report (checks-effects-interactions violated by doing the external call, then trusting mutable shared state afterward instead of the state captured at check-time).

### Finding Description
`resolveOAuthRequest()` is invoked from the deep-link handler (`x-github-client://oauth?code=...&state=...`) via `main.ts`'s `open-url`/protocol-launcher handling and `Dispatcher.dispatchURLAction` [1](#0-0) , ultimately calling into `SignInStore`: [2](#0-1) 

The check `this.state.oauthState.state !== action.state` (line 341) only guards the *start* of the async operation. After the two `await`s (`requestOAuthToken`, `fetchUser` — both external calls to an attacker-influenceable endpoint, since GitHub Enterprise endpoints are user/attacker-supplied via `setEndpoint()`), the code re-reads `this.state.oauthState.onAuthCompleted` live from the store instead of using a reference captured at check time. If, during those two awaits, a *new* sign-in flow is started (e.g. `beginEnterpriseSignIn`, `beginDotComSignIn`, or a second `authenticateWithBrowser()` call), `this.state` is overwritten with a new `oauthState` (new CSRF token, new `endpoint`, new `resolve`/`reject` closures) by `authenticateWithBrowser()` [3](#0-2) . When the delayed callback then fires, it calls the *new* flow's `onAuthCompleted` with the *account fetched from the old flow's endpoint/token*, completing the currently-displayed (new) sign-in dialog with an account that never actually authenticated to that endpoint.

The corrupted value is `this.state.oauthState.onAuthCompleted` / the `account` object bound to it: the account resolved is bound to whichever sign-in session happens to be active at completion time, not the session that actually validated the CSRF `state` and initiated the request.

### Impact Explanation
An attacker who controls (or can proxy) a GitHub Enterprise-style OAuth endpoint (the deep link/API object described as an allowed attacker vector) can deliberately delay the `login/oauth/access_token` and user-fetch responses. If the victim, while waiting, retries or starts a second sign-in attempt (to GitHub.com or another Enterprise instance) — a very natural recovery action after an apparently "stuck" sign-in — the delayed, attacker-influenced response is stitched into the *new* session's success path via stale `onAuthCompleted`. This can result in an account being silently added/bound under the wrong sign-in context, without the CSRF `state` check ever having been satisfied for the session that ultimately consumes the result. This is an unauthorized OAuth/account-binding class impact.

### Likelihood Explanation
Medium-low but concrete: it requires (1) an attacker-controlled or attacker-delayable OAuth endpoint, and (2) the victim initiating a second sign-in flow while the first is still in flight (retry-after-timeout is a normal, expected user action, not "unnatural"). No local access, admin rights, or pre-existing malware is required — only network-response timing control over an endpoint the user is already signing into, and one extra natural UI action (retry). The existing CSRF `state` check does not stop this because it is only performed once, before the awaits, not re-checked against the freshly-read `this.state.oauthState` used to deliver the result.

### Recommendation
Capture the `oauthState` (or at minimum `onAuthCompleted`/`onAuthError`/`state` token) in a local variable *before* the `await` calls and use that captured reference exclusively, then re-validate that `this.state.oauthState` still refers to the same session (matching CSRF `state`) immediately before invoking the completion/error callback — mirroring the checks-effects-interactions pattern: perform all checks, capture the effect targets, then do the external interaction, and finally re-verify before applying any effect.

### Proof of Concept
1. User begins Enterprise sign-in to `https://evil.example.com` (attacker-controlled GHE-like endpoint); `authenticateWithBrowser()` sets `oauthState = { state: csrfA, endpoint: evil, onAuthCompleted: resolveA, ... }` and opens the browser.
2. Attacker's authorize page redirects back to `x-github-client://oauth?code=X&state=csrfA`. `resolveOAuthRequest` passes the CSRF check and calls `requestOAuthToken(evil, X)`, which the attacker's server delays.
3. Before the response arrives, user gives up, clicks "Cancel"/back and starts a fresh sign-in to `https://github.com`. `beginDotComSignIn()` → `authenticateWithBrowser()` overwrites `this.state.oauthState` to `{ state: csrfB, endpoint: github.com, onAuthCompleted: resolveB, ... }`.
4. Attacker's delayed response for step 2 finally resolves; `resolveOAuthRequest`'s pending `await` completes, `fetchUser(evil, token)` returns an account tied to `evil.example.com`.
5. The code executes `this.state.oauthState.onAuthCompleted(account)` — but `this.state.oauthState` is now flow B's `resolveB` — completing the GitHub.com sign-in dialog (session B) with an account object obtained from `evil.example.com` (session A), without session B's CSRF check ever having matched the delivered code/state.   public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
