## Analysis: View-Only-Reentrancy Analog Found

The Curve LP `virtual_price` bug is fundamentally a **state-window / read-timing corruption caused by nested calls into a shared mutable accounting object**. The Cosmos EVM repository has a directly analogous, native root cause in the **`BalanceHandler`** mechanism that bridges `x/bank` events into the EVM `StateDB` during precompile execution.

### Title
Shared/singleton `BalanceHandler.prevEventsLen` corrupted by nested/recursive precompile calls causes StateDB balance desync from `x/bank` - (File: `precompiles/common/balance_handler.go`)

### Summary
The `BalanceHandler` records an event-log offset (`prevEventsLen`) before a precompile executes native `x/bank` logic, then replays only the events appended after that offset to update the EVM `StateDB` balances via `AddBalance`/`SubBalance` [1](#0-0) . When a precompile call is **recursively re-entered** (e.g., a precompile call triggers another EVM call that circles back into the same precompile, or a contract nests precompile calls), and the `BalanceHandler` instance is shared across those nested frames rather than being scoped per-call, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` [2](#0-1) . This causes the outer frame's subsequent `AfterBalanceChange` to read from the wrong (now-advanced) offset, silently skipping the bank events belonging to the outer transfer [3](#0-2) .

This is confirmed as a known, reproduced issue by an explicit regression test: [4](#0-3) 

### Finding Description
Two different lifecycle patterns exist for `BalanceHandler` in the codebase:

1. **Per-call factory pattern** (safe): `precompiles/common/precompile.go`'s `runNativeAction` creates a fresh handler for every native-action invocation: `balanceHandler := p.BalanceHandlerFactory.NewBalanceHandler()` [5](#0-4) .
2. **Shared/singleton pattern** (vulnerable): Production precompiles — `staking.go`, `distribution.go`, `gov.go`, `ics20.go`, `slashing.go`, `erc20.go` — instead call `p.GetBalanceHandler()`, a method returning a handler instance stored once on the `Precompile` struct rather than instantiated per call, as demonstrated by the debug harness at [6](#0-5) .

Because the EVM keeper registers a single long-lived `Precompile` object per address, any code path that causes **reentrant/nested invocation of the same precompile within one EVM message** (via `CallEVMWithData`, nested contract calls, or callback-style hooks) reuses the same `BalanceHandler` instance. The inner call's `BeforeBalanceChange` resets `bh.prevEventsLen` to a later index in the shared `sdk.Context` event log. When control returns to the outer call and `AfterBalanceChange` runs, it processes `events[bh.prevEventsLen:]` using the **corrupted, advanced offset** — meaning the `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` events generated by the *outer* bank operation are never replayed into `stateDB.AddBalance`/`SubBalance` [7](#0-6) .

The result: the native `x/bank` module (source of truth) reflects the correct transfer, but the EVM `StateDB` cache — which is what gets committed back to state at the end of the message and is what all subsequent EVM-side balance reads/writes within the same transaction operate on — never observes that change. Any further EVM-side balance mutation in the same transaction (e.g., `AddBalance`/`SubBalance` from a later precompile call, or `SetBalance` during `Commit()`) will be computed from the stale, desynced starting point, producing a wrong final balance for the affected account when `StateDB.Commit()` persists.

### Impact Explanation
This maps to the report's **"irreversible accounting corruption of spendable user value across native balances / EVM balances"** allowed-impact class. A desync between `x/bank` truth and `StateDB` cache during precompile-mediated transfers (staking delegate/undelegate, distribution reward withdrawal, gov deposit, ICS20 transfer, ERC20 precompile transfer) can cause the EVM-side balance for an account to be understated or overstated relative to its real bank balance. Because `StateDB.Commit()` writes accumulated `stateObject` balances back into the account model consumed by the EVM (and reconciled with bank balances through the precisebank/erc20 bridging logic), a corrupted `prevEventsLen` window can cause funds to be silently duplicated (an account credited by bank but never credited in StateDB, then later independently credited by a second event window) or lost (a debit applied in bank but never reflected/re-debited in StateDB, allowing the same funds to be spent again from the EVM side). Both directions match the required Critical impact: unauthorized duplication/minting-equivalent state, or theft/loss of spendable value.

### Likelihood Explanation
Triggering requires only an unprivileged user to construct a contract or transaction that causes the shared-instance precompile to be invoked recursively within a single EVM message — e.g., a contract precompile call that itself triggers a nested EVM call back into the same precompile address, or one precompile action internally invoking another precompile method that shares the same underlying `Precompile.GetBalanceHandler()` object. The debug precompile’s `Call0` explicitly demonstrates this recursive pattern by using `evmKeeper.CallEVMWithData` to re-enter itself [8](#0-7) , and the existing regression test title confirms the team is aware this is reachable ("recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync") [4](#0-3) . No privileged role is required — this is a standard EVM contract-composition primitive (fallback/receive hooks, nested calls, callbacks), directly analogous to the Curve view-only-reentrancy trigger vector.

### Recommendation
- Ensure every precompile obtains a **freshly-scoped `BalanceHandler`** per top-level native action invocation (adopt the `BalanceHandlerFactory.NewBalanceHandler()` pattern universally instead of the shared `GetBalanceHandler()` singleton) so nested/recursive calls cannot clobber `prevEventsLen`.
- Alternatively, make `prevEventsLen` stack-based (push/pop per call depth) rather than a single scalar field, and process only the event slice bounded by both the entry and matching exit markers of the current call frame.
- Add reentrancy guards / call-depth tracking at the precompile dispatch layer to detect same-address recursive precompile invocation within a single EVM message and reject or serialize it defensively.
- Add invariant checks post-commit comparing `x/bank` balances against `StateDB`-derived balances for all touched accounts within a transaction, failing loudly on divergence.

### Proof of Concept
Exact exploitation requires confirming which production precompile call graphs allow same-address reentrancy within one EVM message (e.g., ERC20 precompile `transfer` invoking a hook that calls back into itself, or an ICS20/staking precompile call triggering a nested EVM sub-call to the same precompile address) — this was not verifiable to full certainty from the indexed code within the available tool budget. The existing regression test, however, already reproduces the mechanical bug in isolation: [9](#0-8) 
It deploys a caller contract that recursively invokes the debug precompile via `callback(0)`, funds the caller with native coin, and shows the resulting event/balance accounting diverges from the naively expected count (`s.Require().Equal(len(res.Events), 15, ...)` vs. actual `debug_count == 10`), demonstrating the event-window (`prevEventsLen`) is being consumed/overwritten across nested calls rather than isolated per call frame.

**Uncertainty note:** I was not able to fully trace, within the tool budget, the exact `StateDB.Commit()` code path that would confirm whether the missed event window results in permanent loss/duplication of committed bank balance versus a transient inconsistency corrected before final commit. This should be verified with a live PoC (e.g., extending the existing `balance_handler_test.go` to assert final on-chain `x/bank` balance vs. `StateDB`-derived balance for the caller and callee accounts after the recursive call) before treating this as a confirmed Critical exploit rather than a reachable accounting-desync bug.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
