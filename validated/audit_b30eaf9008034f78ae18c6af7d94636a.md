### Title
Attacker can send dust/zero-value outputs to a Serai-scanned address to pollute the input set and DoS transaction creation - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes an attacker unilaterally injecting balance (a 1-unit token transfer) into a pool's accounting denominator so the first depositor's share computation returns 0 and the pool is permanently DoS'd. The analog in bitcoin-serai is that an unprivileged party can inject unrequested "balance" into the wallet's accounting by sending dust or zero-value outputs to any script the `Scanner` watches. `Scanner::scan_transaction` records *any* output paying a registered `script_pubkey` as a `ReceivedOutput` with no minimum-value check, so the attacker controls entries in the received-output set. When those outputs are later used as inputs in `SignableTransaction::new`, each one adds ~57.5 vbytes of weight and a signing step while contributing (near-)zero value, which can push spends into `NotEnoughFunds` / `TooLargeTransaction` failure, and any output worth less than its marginal fee is a fund reported received that cannot be spent without a net loss. [1](#0-0) [2](#0-1) 

### Finding Description
`Scanner` indexes watched outputs purely by `script_pubkey` in `self.scripts`, and `scan_transaction` pushes a `ReceivedOutput` for every matching output, regardless of `output.value`. There is no check against `DUST` (defined as 546 sats in `send.rs`) or against zero on the receive path — the only dust check in the codebase is on *payments* (outgoing outputs) in `SignableTransaction::new`. [3](#0-2) [4](#0-3) 

Consequences on the spend path:

1. `input_sat` sums all provided inputs, and `needed_fee` grows linearly with `tx_ins.len()` via `calculate_weight_vbytes`. An attacker-supplied 1-sat input adds ~57.5 vbytes but only 1 sat of value; including it makes the transaction strictly worse and can flip `input_sat < payment_sat + needed_fee`, causing `TransactionError::NotEnoughFunds`. [5](#0-4) 
2. Each injected input also adds a full FROST `AlgorithmMachine` signing round in `multisig()`, and a fixed weight contribution — enough attacker outputs push the tx over `MAX_STANDARD_TX_WEIGHT`, causing `TooLargeTransaction`, a DoS on spends that include the polluted set. [6](#0-5) [7](#0-6) 
3. Unlike the deposit script itself, these outputs arrive unbidden — the attacker does not need the offset to be freshly registered; `scan_transaction` credits outputs to any script already in `scripts` (the base key script registered in `Scanner::new`, plus every `register_offset` result). The base deposit script is registered at construction with offset `Scalar::ZERO`, so dusting the main deposit address always lands. [8](#0-7) 

This mirrors the report's root cause exactly: the accounting treats balance the protocol never requested as real, and downstream math (fee sufficiency, weight limit) breaks because of it — the attacker needs only to broadcast ordinary Bitcoin transactions, which is an explicitly reachable public input.

### Impact Explanation
- Funds reported received that are not (economically) spendable: a `ReceivedOutput` worth less than the ~57.5-vbyte fee needed to spend it is a net liability, yet is surfaced identically to a genuine deposit.
- DoS of transaction creation: any spend path that consumes the polluted output set reverts with `NotEnoughFunds` or `TooLargeTransaction`; there is no API on `ReceivedOutput` or `Scanner` to distinguish attacker dust from legitimate deposits, so an integrator that must spend all outputs of a retired key (e.g., during multisig rotation sweeping) is forced to include them.
- Severity: Medium — requires a spender that includes the injected outputs, but the injection itself is unilateral and cheap (attacker can even craft sub-dust/zero-value outputs, which miners may still include).

### Likelihood Explanation
Moderate. Sending transactions to a watched address requires no privileges and costs only the dust itself. Whether the DoS manifests depends on the consuming code sweeping all received outputs; for key-rotation sweeps that is the natural behavior. I could not fully verify how `processor/src/networks/bitcoin.rs` selects inputs for `SignableTransaction::new` (out of scope and only partially inspected), so the "mandatory inclusion" half of the impact is inferred rather than proven end-to-end.

### Recommendation
Enforce a minimum value on the receive path: in `Scanner::scan_transaction` (or immediately post-scan), drop outputs with `output.value.to_sat() < DUST`, mirroring the payment-side dust check in `SignableTransaction::new`. Alternatively/additionally, expose the value on `ReceivedOutput` (already available via `value()`) and have spend-construction skip inputs whose value is below the marginal fee they add (`fee_per_vbyte * per_input_vbytes`).

### Proof of Concept
1. Deploy/observe a `Scanner` for a Serai group key `K`; the base script `p2tr_script_buf(K)` is registered with offset `Scalar::ZERO` in `Scanner::new`.
2. Attacker broadcasts a Bitcoin transaction with N outputs, each paying that `script_pubkey` with value 1 sat (or any value < `DUST`).
3. `scan_transaction`/`scan_block` returns N `ReceivedOutput`s indistinguishable from real deposits.
4. Construct a spend consuming them: `SignableTransaction::new(inputs, payments, change, None, fee_per_vbyte)` computes `vbytes` including all N inputs; with enough injected inputs either `input_sat < payment_sat + needed_fee` → `NotEnoughFunds`, or `weight > MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction`, and each surviving input is worth less than the fee it adds — funds reported received that are not spendable without loss.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
