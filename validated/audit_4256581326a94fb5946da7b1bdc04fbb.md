### Title
ProtoJSON Timestamp parser accepts offset-adjusted seconds outside the valid `Timestamp` range - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
The external report's core failed invariant is: an externally-supplied numeric/time value is consumed and used in arithmetic without validating that the *final* value stays within the bounds the rest of the system assumes are always true, allowing an out-of-range value to be silently accepted. The Protobuf analog is `ParseTimestamp` in the C++ ProtoJSON parser (`src/google/protobuf/json/internal/parser.cc`), which builds `secs` from date/time digits and then adds a client-controlled timezone offset without ever re-validating the result against the documented `Timestamp` bounds `[kTimestampMinSeconds, kTimestampMaxSeconds]` (`-62135596800`..`253402300799`). This is confirmed as a known conformance failure for the C++ backend (and several other language backends).

### Finding Description
`ParseTimestamp<Traits>` ( [1](#0-0) ) computes `secs` from the year/month/day/hour/min/sec fields taken directly from the attacker-controlled JSON string via `TakeTimeDigitsWithSuffixAndAdvance`. The only bound enforced on the date components is that `year`, `mon`, `day` are non-zero; year is limited to 4 digits (so `0001`-`9999`), which keeps `secs` inside the valid range *before* the timezone offset is applied.

The timezone offset is then parsed and applied directly to `secs` with no subsequent bounds check: [2](#0-1) 

Unlike `TimeUtil::FromString` for `Timestamp`, which explicitly validates the computed seconds before constructing the message — [3](#0-2) 
— `ParseTimestamp` in `json/internal/parser.cc` calls `Traits::SetInt64(...)` directly on the raw `secs` value with no equivalent check against `kTimestampMinSeconds`/`kTimestampMaxSeconds` ( [4](#0-3) ).

This is a genuine, tracked defect: the conformance suite explicitly encodes the expectation that boundary-crossing offsets must be rejected — [5](#0-4) 
— for example `"9999-12-31T23:59:59-00:01"` (a valid date/time whose offset pushes the resulting UTC seconds one past `kTimestampMaxSeconds`) is expected to fail parsing. This test case (`TimestampJsonInputOffsetBoundaryOverflow`/`...Underflow`) is present in `conformance/failure_list_cpp.txt`, meaning the C++ implementation currently is a known/accepted failure of this conformance expectation, i.e., it accepts the out-of-range value instead of rejecting it. Related failure-list entries for PHP, Ruby, JRuby-FFI, PHP-C, and upb confirm the same class of gap exists across multiple `upb`-based JSON decoders (`jsondec_timestamp` in `upb/json/decode.c`, `php-upb.c`, `ruby-upb.c`), which also only check the lower bound (`seconds.int64_val < -62135596800`) and never check the upper bound after timezone-offset adjustment: [6](#0-5) 

### Impact Explanation
A trusted schema containing a `google.protobuf.Timestamp` field, when populated via the public ProtoJSON parsing API from an ordinary/bounded client payload, can end up with a `seconds` value outside the documented valid range `[-62135596800, 253402300799]`. Downstream code that (reasonably) assumes all parsed `Timestamp` messages satisfy `TimeUtil::IsTimestampValid` (a documented invariant of the well-known type) may then hit assertion failures (`ABSL_DCHECK`/`EXPECT_DEATH` paths shown in `time_util_test.cc`) or produce incorrect date/time computations if such a message is later re-serialized to text, converted to `absl::Time`, or fed into `TimeUtil` conversions that assume validity. This is a data-integrity violation, not a memory-safety bug — it does not by itself yield RCE or memory corruption, matching the Medium severity of the source report, which was about unchecked bounds leading to unreliable/incorrect state rather than direct exploitation.

### Likelihood Explanation
High likelihood of the input reaching this parser in normal usage: any consuming application that calls `google::protobuf::util::JsonStringToMessage` (or `JsonToBinary` internally, which goes through the same `ParseTimestamp`) on a message with a `Timestamp` field, and that accepts near-boundary date/time strings from an external client, will trigger this path. No special privileges, malicious schema, or huge/unbounded input is required — a single, small, well-formed-looking JSON string with a legal-looking (but boundary-crossing) offset is sufficient. The bug is also already documented via the conformance-suite's `failure_list_cpp.txt`, confirming it is real and currently unresolved in this codebase, not merely theoretical.

### Recommendation
- After computing `secs` (post timezone-offset adjustment) in `ParseTimestamp` (`src/google/protobuf/json/internal/parser.cc`), add an explicit range check against `TimeUtil::kTimestampMinSeconds` / `kTimestampMaxSeconds` (or the equivalent literal bounds `-62135596800` / `253402300799`) and return `str->loc.Invalid(...)` if the value falls outside that range, mirroring the check already present in `TimeUtil::FromString` (`src/google/protobuf/util/time_util.cc:192-195`).
- Apply the equivalent upper-bound check to the `upb`-based JSON decoders (`upb/json/decode.c`, `php-upb.c`, `ruby-upb.c`), which currently check only the lower bound.
- Remove the corresponding conformance-suite entries from `failure_list_cpp.txt`, `failure_list_php.txt`, `failure_list_ruby.txt`, `failure_list_jruby_ffi.txt`, `failure_list_php_c.txt`, and `upb/conformance/conformance_upb_failures.txt` once fixed, so regressions are caught automatically.

### Proof of Concept
Using the public ProtoJSON parsing entry point on a trusted schema containing an `optional_timestamp` field of type `google.protobuf.Timestamp`, supply:
```json
{"optionalTimestamp": "9999-12-31T23:59:59-00:01"}
```
Per RFC 3339 semantics this is `9999-12-31T23:59:59` at UTC-00:01, i.e. UTC time `10000-01-01T00:00:59`, one minute past the maximum representable `Timestamp`. The conformance suite encodes exactly this case as `TimestampJsonInputOffsetBoundaryOverflow`, expecting `ExpectParseFailureForJson` ( [7](#0-6) ), yet this test is listed as an accepted/known failure for the C++ backend in `conformance/failure_list_cpp.txt`, confirming the parser instead accepts the value and stores an out-of-range `seconds` field in the resulting message — reproducing the analog of the external report's "unvalidated externally supplied numeric/time value used without bounds checking."

template <typename Traits>
absl::Status ParseTimestamp(JsonLexer& lex, const Desc<Traits>& desc,
                            Msg<Traits>& msg) {
  if (lex.Peek(JsonLexer::kNull)) {
    return lex.Expect("null");
  }

  absl::StatusOr<LocationWith<MaybeOwnedString>> str = lex.ParseUtf8();
  RETURN_IF_ERROR(str.status());

  absl::string_view data = str->value.AsView();
  if (data.size() < 20) {
    return str->loc.Invalid("timestamp string too short");
  }

  int64_t secs;
  {
    /* 1972-01-01T01:00:00 */
    auto year = TakeTimeDigitsWithSuffixAndAdvance(data, 4, "-");
    if (!year.has_value() || *year == 0) {
      return str->loc.Invalid("bad year in timestamp");
    }
    auto mon = TakeTimeDigitsWithSuffixAndAdvance(data, 2, "-");
    if (!mon.has_value() || *mon == 0) {
      return str->loc.Invalid("bad month in timestamp");
    }
    auto day = TakeTimeDigitsWithSuffixAndAdvance(data, 2, "T");
    if (!day.has_value() || *day == 0) {
      return str->loc.Invalid("bad day in timestamp");
    }
    auto hour = TakeTimeDigitsWithSuffixAndAdvance(data, 2, ":");
    if (!hour.has_value()) {
      return str->loc.Invalid("bad hours in timestamp");
    }
    auto min = TakeTimeDigitsWithSuffixAndAdvance(data, 2, ":");
    if (!min.has_value()) {
      return str->loc.Invalid("bad minutes in timestamp");
    }
    auto sec = TakeTimeDigitsWithSuffixAndAdvance(data, 2, "");
    if (!sec.has_value()) {
      return str->loc.Invalid("bad seconds in timestamp");
    }

    uint32_t m_adj = *mon - 3;  // March-based month.
    uint32_t carry = m_adj > *mon ? 1 : 0;

    uint32_t year_base = 4800;  // Before min year, multiple of 400.
    uint32_t y_adj = *year + year_base - carry;

    uint32_t month_days = ((m_adj + carry * 12) * 62719 + 769) / 2048;
    uint32_t leap_days = y_adj / 4 - y_adj / 100 + y_adj / 400;
    int32_t epoch_days =
        y_adj * 365 + leap_days + month_days + (*day - 1) - 2472632;

    secs = int64_t{epoch_days} * 86400 + *hour * 3600 + *min * 60 + *sec;
  }

bool TimeUtil::FromString(absl::string_view value, Timestamp* timestamp) {
  int64_t seconds;
  int32_t nanos;
  if (!ParseTime(value, &seconds, &nanos)) {
    return false;
  }
  // Validate before CreateNormalizedTimestamp, which has a DCHECK on range.
  if (seconds < kTimestampMinSeconds || seconds > kTimestampMaxSeconds) {
    return false;
  }
  *timestamp = CreateNormalizedTimestamp(seconds, nanos);
  if (!IsTimestampValid(*timestamp)) {
    timestamp->Clear();
    return false;
  }
  return true;
}

static void jsondec_duration(jsondec* d, upb_Message* msg,
                             const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;
  const int64_t max = (uint64_t)3652500 * 86400;
  bool neg = false;

  /* "3.000000001s", "3s", etc. */
  ptr = jsondec_buftoint64(d, ptr, end, &seconds.int64_val, &neg);
  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  if (end - ptr != 1 || *ptr != 's') {
    jsondec_err(d, "Malformed duration");
  }

  if (seconds.int64_val < -max || seconds.int64_val > max) {
    jsondec_err(d, "Duration out of range");
  }

  if (neg) {
    nanos.int32_val = -nanos.int32_val;
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
}
