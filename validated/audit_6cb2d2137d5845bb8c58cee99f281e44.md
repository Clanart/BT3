### Title
Staleness Gate Silently Disabled When Oracle Publish-Time Is Ahead of Stacks Block-Time - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` in the market contract is supposed to be the tight gate that rejects a stale Pyth/DIA price before it is used to price collateral or debt. When the oracle's `publish-time` is ahead of the chain's own `stacks-block-time` — which is the normal case, since Pyth publish times are close to real-world UTC while Stacks block timestamps lag behind it — the function short-circuits `delta` to `u0`, i.e. treats the price as maximally fresh regardless of how old it actually is. This mirrors the report's bug class exactly: a value is accepted against a loose/no-op bound instead of the tighter bound the protocol intends, and the real limit is effectively never enforced in the common case.

### Finding Description
`price-resolve` calls `oracle-timestamp-fresh` as the sole staleness gate before returning `final-price` for use in every collateral/debt valuation: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

`ts` is the oracle's `publish-time` (Pyth wall-clock seconds) and `stacks-block-time` is the current Stacks block timestamp. When `ts > stacks-block-time`, `delta` is forced to `u0` — the code treats "the future" as "perfectly fresh" instead of computing the actual staleness or rejecting the anomaly. Because Stacks block timestamps are known to lag real time (Bitcoin-anchored ~10 minute cadence plus propagation delay), any legitimately-pushed Pyth update whose `publish-time` reflects real-world time will routinely satisfy `ts > stacks-block-time`. This means `delta <= max-staleness` is trivially satisfied every time this branch is taken, independent of how long ago the price was actually last refreshed — the `max-staleness` cap (set via `set-price-staleness` governance, see `local-testing/contracts/proposals/proposal-set-price-staleness.clar`) is effectively bypassed rather than enforced. Only the second half, `(>= ts prev)`, still gates monotonicity; the actual "is this price recent enough" check is neutralized.

This is the same root-cause shape as the external report: the deserializer/validator computes against a permissive placeholder (here, `u0`) instead of the real, tighter quantity (`stacks-block-time - ts`), so the intended limit (`max-staleness`) is checked against the wrong number.

### Impact Explanation
`price-resolve` feeds directly into collateral valuation, debt valuation, LTV/health-factor computation, and liquidation eligibility throughout `v0-4-market.clar`. If the staleness gate is a no-op whenever `ts > stacks-block-time` (the routine case given Stacks/Pythnet clock skew), a price that has not actually been refreshed in a long time can still be accepted as "fresh," yielding a wrong health verdict:
- Borrowers can be under-collateralized against a stale (favorable) price that should have been rejected, letting them extract more debt than their real collateral value supports.
- Positions that should be liquidatable under the true current market price can remain unliquidatable because the stale price still passes the freshness check.

Either path can produce bad debt once the true price is eventually reflected, which is a protocol-insolvency-class impact, or, in the liquidation-avoidance direction, a temporary freezing-of-funds outcome for depositors who cannot be made whole from an under-collateralized position.

### Likelihood Explanation
This does not require attacker control of oracle data or DAO/registry misconfiguration — it is a property of the comparison logic given normal Stacks/Pythnet clock behavior. Any period where Stacks block time trails Pyth publish time (routine under network delay or slow block production) causes the bypass to activate on the very next `price-resolve` call, for every asset, with no special crafting needed beyond waiting for or benefiting from an existing stale price.

### Recommendation
Do not special-case `ts > stacks-block-time` as `delta = u0`. Either:
- Reject the update outright when `ts > stacks-block-time` (future-dated timestamps are themselves suspicious and should fail closed), or
- Compute staleness using an absolute difference (`if ts > stacks-block-time then (- ts stacks-block-time) else (- stacks-block-time ts)`) and still bound it by `max-staleness`, so a large forward skew cannot be laundered into "fresh."

### Proof of Concept
1. Push a Pyth update for an asset via `verify-and-update-price-feeds` at a time when the update's `publish-time` (`ts`) is greater than the current `stacks-block-time` (the routine case since Pyth timestamps track real UTC while Stacks block time lags).
2. Do not push any further update for that feed for longer than `max-staleness` seconds of Stacks block time.
3. Call any market entrypoint that triggers `price-resolve` for that asset (e.g., borrow, withdraw-collateral check, or a liquidation attempt against the position).
4. Observe `oracle-timestamp-fresh` still returns `true` because `ts > stacks-block-time` continues to force `delta = u0`, so `ERR-ORACLE-INVARIANT` is never raised even though the price has not been refreshed for far longer than `max-staleness` — the stale price is used to compute health/LTV, producing an incorrect health verdict.

        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
