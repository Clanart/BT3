### Title
`resolveWithin()` uses prefix-only `startsWith` check, allowing deep-link `filepath` to escape the repository root - (File: `app/src/lib/path.ts`)

### Summary
`app/src/lib/path.ts`'s `_resolveWithin()` validates that a resolved path stays inside a repository by testing `realResolved.startsWith(realRoot)` [1](#0-0) . This is a classic prefix-matching flaw: it does not require a path separator boundary after `realRoot`, so any sibling directory whose name merely starts with the repository's directory name (e.g. `repo` vs `repo-secrets`) is incorrectly treated as "inside" the repository. This function gates the `filepath` parameter of the `x-github-client://openrepo` deep link handled in `openRepositoryFromUrl()` [2](#0-1) , so a malicious link can cause Desktop to reveal/open a file outside the cloned repository.

### Finding Description
The report's broken invariant is "a value/boundary check is evaluated using state that hasn't been fully/atomically established, letting an attacker slip past the intended containment." In StakeWise, `migrate()` could be called against pre-harvest share-price state to grab more shares than intended — the guard (harvest) hadn't fully "sealed" the invariant before the state was used.

In GitHub Desktop, the analogous broken invariant is path containment: "the resolved path must be *inside* rootPath." The implementation is:

```ts
// app/src/lib/path.ts:64-71
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` performs a raw character-prefix comparison, not a path-segment comparison. If `realRoot` is `/Users/dev/repo` and an attacker-supplied relative path resolves (after `realpath`) to `/Users/dev/repo-secrets/config.json`, the check `"/Users/dev/repo-secrets/config.json".startsWith("/Users/dev/repo")` evaluates to `true`, even though `repo-secrets` is a completely different, sibling directory. The missing check is a trailing separator (or exact-equality) requirement, e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + path.sep)`.

This function is the sole authorization boundary used in `openRepositoryFromUrl`, the handler for the `open-repository-from-url` deep-link action parsed by `parseAppURL` from URLs such as `x-github-client://openRepo/<url>?filepath=...` [3](#0-2) . The handler only rejects absolute paths and otherwise trusts `resolveWithin` completely:

```ts
// app/src/ui/dispatcher/dispatcher.ts:1957-1972
if (filepath !== null) {
  if (isAbsolute(filepath)) {
    log.error(`Refusing to open absolute path: ${filepath}`)
    return
  }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } else {
    log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
  }
}
```

Unlike the `branch` parameter, which is validated with `testForInvalidChars` [4](#0-3) , `filepath` has no character/traversal validation at parse time — it is passed through verbatim and relies entirely on the flawed `resolveWithin` boundary check.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openRepo/...` link (e.g., embedded in a webpage, README, or chat message — a normal, unprompted user action of clicking a link) can cause Desktop to call `shell.showItemInFolder()` on a file located in a sibling directory to a repository the victim already has cloned, as long as that sibling directory's name shares the target repo directory's name as a prefix (a very common real-world pattern: `myrepo` / `myrepo-private`, `myrepo` / `myrepo.bak`, `myrepo` / `myrepo-secrets`, org monorepo forks, etc.). This reveals/exposes a file the attacker should not have access to via the app's file-reveal action, i.e. file read/disclosure outside the intended repository boundary — matching the "file … read outside the repo" impact class from a link the user clicks.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the victim to already have a locally cloned repository whose containing folder has, or can be predicted to have, a sibling with a matching name prefix, and (2) the victim to click an attacker-supplied deep link (a standard delivery vector already treated as in-scope, e.g. via GitHub comments/READMEs that Desktop can open). No local/physical access, no elevated privileges, and no prior malware are needed — only the existing protocol-handler entry point that Desktop already registers and dispatches through `dispatchURLAction` → `openRepositoryFromUrl`.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to require a path-segment boundary, not just a string prefix:

```ts
import { sep } from 'path'
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
(use the platform-appropriate separator for the `win32`/`posix` variants). Additionally consider validating `filepath` similarly to `branch` (reject `..` segments, null bytes, drive-letter tricks) at parse time in `parse-app-url.ts` as defense-in-depth.

### Proof of Concept
1. Victim has previously cloned a repository to `/Users/victim/Documents/GitHub/acme-app`.
2. Suppose (as is common) a sibling directory `/Users/victim/Documents/GitHub/acme-app-internal/notes.txt` exists (e.g., another cloned repo, a backup folder, or a folder created by other tooling with a related name).
3. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/acme/acme-app?filepath=../acme-app-internal/notes.txt`
4. `parseAppURL` parses this into an `open-repository-from-url` action with `filepath = "../acme-app-internal/notes.txt"` [5](#0-4) .
5. `openRepositoryFromUrl` resolves `acme-app` (already cloned, matched via `openOrCloneRepository`), then calls `resolveWithin(repository.path, filepath)` [6](#0-5) .
6. Inside `_resolveWithin`, `resolve('/Users/victim/Documents/GitHub/acme-app', '../acme-app-internal/notes.txt')` yields `/Users/victim/Documents/GitHub/acme-app-internal/notes.txt`, and `realResolved.startsWith(realRoot)` is `true` because `"acme-app-internal"` starts with `"acme-app"` [1](#0-0) .
7. Desktop calls `shell.showItemInFolder(resolved)`, revealing/opening `notes.txt` from a directory the attacker never should have been able to target — outside the actual `acme-app` repository — via a single clicked link.
