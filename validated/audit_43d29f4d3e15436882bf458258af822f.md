### Title
Deterministic nonce reuse across signing attempts enables secret-share recovery via `CachedPreprocess` - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The analog to the "account compromise" bug class in Serai is secret-key/share compromise caused by an unprivileged party controlling which messages get signed. In `coordinator/src/tributary/signing_protocol.rs`, the coordinator's MuSig/FROST preprocess nonce seed is cached deterministically under a context of `(b"DkgConfirmer", attempt)` only, and every call to `share` / `complete` re-derives the *same* nonces from that cached seed via `AlgorithmSignMachine::from_cache`. If `share_internal` is invoked twice for the same attempt with a different received-preprocess set or a different message, two signature shares are produced over identical nonces with different binding factors/challenges — allowing direct algebraic recovery of the validator's secret share.

### Finding Description
`preprocess_internal` loads (or lazily creates) a `CachedPreprocess` seed keyed solely by `self.context` and rebuilds the signing machine deterministically:

```rust
// coordinator/src/tributary/signing_protocol.rs:137-147
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
...
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

`from_cache` feeds the seed into `ChaCha20Rng::from_seed`, so the nonces `d, e` produced by `Commitments::new` are identical every time (crypto/frost/src/sign.rs:121-144). The context is `(b"DkgConfirmer", self.attempt)` (line 275) — it binds neither the message (`set_keys_message` over `key_pair`/`removed`) nor the received preprocess/commitment set.

`share_internal` then signs attacker-influenced inputs with those fixed nonces (lines 150-180): the `preprocesses` map and `msg` determine the binding factors `rho` (via `B.calculate_binding_factors` over `rho_transcript` containing `hash_msg(msg)` and hashed commitments, crypto/frost/src/sign.rs:362-371) and the final challenge. Two calls with different received preprocess maps — or a different signer subset, which also remaps our `musig_i` and Lagrange coefficient through `threshold_i_map_to_keys_and_musig_i_map` (lines 208-250) — yield two shares

`z_i = d + rho_i·e + lambda_i·s·c_i`

over the same `d, e` but distinct `rho_i`/`c_i`. This is a classic nonce-reuse/ROS-style disclosure: the system of linear equations recovers `s` (the MuSig secret key share).

The file's own safety argument (lines 25-54) admits this is "explicitly unsafe" and relies entirely on BFT finality so that `sign` is never called on distinct received messages. However `share` and `complete` each independently call `share_internal` with whatever preprocess map is passed in at that moment (lines 288-327), and the code contains an explicit TODO acknowledging the missing check that published shares correspond to the decided nonces (lines 50-54: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)"). Nothing enforces that the preprocess set seen by `share` equals the set seen by `complete`, or that repeated calls use identical inputs.

### Impact Explanation
Recovery of a coordinator validator's secret key share. For the MuSig confirmer this is the validator's root-of-trust key used to confirm DKG results on Substrate; combined with threshold shares elsewhere in the codebase, reuse of a FROST nonce leaks the private share outright (documented in crypto/frost/src/sign.rs:85-87 and spec/cryptography/FROST.md:51-55: "Reusing preprocesses would enable a third-party to recover your private key share"). A recovered share plus knowledge of other shares enables forging the validator-set confirmation signature — the on-chain "account" is effectively compromised, matching the incident class (untrusted content causing loss via a compromised signing identity).

### Likelihood Explanation
Likelihood is gated by the coordinator actually invoking `share`/`complete` more than once per attempt with non-identical inputs. This does not require a broken BFT or a malicious validator: the preprocess set passed to `share` depends on which tributary transactions have arrived, and `complete` re-executes `share_internal` with a possibly larger/different map. Partial rebuilds/re-execution (explicitly accepted as within the threat bound at lines 46-48) can also produce divergent received sets while the cached seed persists in the DB. The entropy of triggering is low (ordinary message ordering/timing), but exploitation requires two differing sign invocations under one `(DkgConfirmer, attempt)` context, so Medium is appropriate rather than High.

### Recommendation
Bind the cached preprocess to everything it will sign: include the serialized participant set and message digest (or the on-chain preprocess/commitment hash) in the `CachedPreprocesses` key, or store the decided preprocess alongside the seed and refuse to sign when the received set/message differs from the one bound at preprocess time. Implement the acknowledged TODO (lines 50-54): before publishing a share, verify the locally derived commitments match the coordinator's on-chain preprocess, and ensure `share` and `complete` operate over an identical, finalized preprocess map for a given attempt.

// Attempt N, context = (b"DkgConfirmer", N)

// 1) Coordinator sees preprocess set P1 (subset of validators arrived),
//    calls share(P1, key_pair):
//    - preprocess_internal: CachedPreprocesses[(b"DkgConfirmer", N)] -> seed S
//    - from_cache(S) -> nonces (d, e) [deterministic via ChaCha20Rng]
//    - sign(...) -> z1 = d + rho1*e + lambda1*s*c1   (PUBLISHED on-chain)

// 2) More preprocesses finalize; complete(P2, key_pair, shares) with P2 != P1
//    re-runs share_internal:
//    - same context -> same seed S -> SAME (d, e)
//    - different participant set -> different musig_i mapping, rho2, c2
//    - sign(...) -> z2 = d + rho2*e + lambda2*s*c2   (used internally / published)

// 3) Attacker collects z1, z2 and solves:
//    z1 - z2 = rho1*e - rho2*e' ... standard two-nonce-reuse linear solve
//    -> recover e (and d), then recover lambda*s -> the validator secret share.
