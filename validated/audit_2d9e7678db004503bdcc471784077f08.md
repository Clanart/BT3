### Title
CR-CAT funds sent to a "pending approval" address become permanently locked with no rerouting mechanism if the recipient's VC is revoked - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
When a CR-CAT (credential-restricted CAT) payment is made to a receiver that does not have a matching Verified Credential (VC) at trade time (e.g., during an offer settlement), the funds are diverted to a "pending approval" puzzle hash whose eventual owner is fixed at creation time. The only way to move that coin out of the pending state and into the recipient's spendable balance is to present a valid, unrevoked VC issued by one of the `authorized_providers`. If the intended recipient's VC is revoked (a legitimate, provider-authorized action) after the pending payment was created but before it is claimed, the recipient loses the ability to satisfy that check and the funds become stuck at the fixed, hardcoded destination puzzle hash — directly analogous to a `USDT`/`USDC` receiver being blocklisted after a withdrawal request was already queued.

### Finding Description
CR-CAT payments made "to" a party without a currently valid VC are redirected to a `pending_approval` inner puzzle hash constructed with the intended final owner's puzzle hash baked in: [1](#0-0) 

Reclaiming these coins requires the current CR-CAT wallet to have some valid VC matching `authorized_providers`/`proofs_checker`; if none exists, `claim_pending_approval_balance` fails outright: [2](#0-1) 

The VC lookup itself raises if no matching, valid-proof VC is found in the recipient's own VCWallet store: [3](#0-2) 

Crucially, the final destination puzzle hash used when the pending coin is eventually claimed is the one recorded in the coin's metadata at creation time (`metadata.inner_puzzle_hash`) — it cannot be redirected to a new/alternate address at claim time: [4](#0-3) 

A VC can legitimately be revoked at any time by its issuing DID provider via the backdoor/revocation layer: [5](#0-4) [6](#0-5) 

If a user's VC is revoked (or simply expires/becomes unusable) after a CR-CAT payment addressed to them has already entered the "pending approval" state, that user has no path to satisfy the VC-presence check for that specific pending coin unless they can obtain a brand-new, still-valid VC from one of the same `authorized_providers`. If no such provider is willing or able to reissue a VC, the CR-CAT coin remains permanently un-spendable at its predetermined puzzle hash — the coin-set state diverges from a "healthy" state and the transferred value is effectively frozen, with no admin/emergency address override analogous to `claimForWithdrawRequest`'s inability to redirect to an alternate `receiver`.

### Impact Explanation
This is a Medium-severity liveness/lock-of-funds issue: value legitimately transferred to a counterparty in a CR-CAT trade/offer can become permanently unspendable through no fault of the sender or of malicious behavior by any party, purely as a consequence of routine VC lifecycle management (revocation) intersecting with the fixed-destination design of the pending-approval mechanism. It does not enable theft or supply inflation, but it does produce a spend-triggered halt on legitimately owned funds, mirroring the reported analog exactly (funds locked at a hardcoded address because there is no mechanism to substitute an alternate valid receiver/credential at claim time).

### Likelihood Explanation
Reachable by any unprivileged CR-CAT offer counterparty/wallet user: any receiver of a CR-CAT via an offer settlement whose VC becomes revoked or otherwise invalid before they call `crcat_approve_pending`/`claim_pending_approval_balance`. VC revocation is a normal, expected, on-chain operation exposed via CLI/RPC (`chia wallet vcs revoke`) and requires no special network position — only routine timing between a payment and a revocation, both of which are ordinary user/provider actions.

### Recommendation
Provide a mechanism to re-target or recover CR-CAT coins stuck in the `pending_approval` state, for example by:
- Allowing the sender or the recipient to supply an updated destination puzzle hash when claiming a pending-approval CR-CAT, provided a currently valid VC (issued by any authorized provider, not necessarily the original one) is presented, and/or
- Adding a fallback/timeout path (analogous to clawback) that lets the original sender recover pending, unclaimed CR-CAT coins after a defined delay if no authorized VC materializes.

### Proof of Concept
1. Alice holds a VC issued by DID provider `P`, which is in the `authorized_providers` list of a CR-CAT asset.
2. Bob sends Alice a CR-CAT payment via an offer; because the trade manager detects Alice's VC state at build time (or Alice's VC isn't presented in time), the payment is routed to the `pending_approval` puzzle hash keyed to Alice's inner puzzle hash, per `check_for_requested_payment_modifications` (`chia/wallet/trade_manager.py:1047-1069`).
3. Before Alice calls `crcat_approve_pending`, provider `P` revokes Alice's VC using `activate_backdoor`/`revoke_vc` (`chia/wallet/vc_wallet/vc_drivers.py:757-797`, `chia/wallet/vc_wallet/vc_wallet.py:376-410`).
4. Alice calls `claim_pending_approval_balance`; `get_vc_with_provider_in_and_proofs` finds no valid VC for `authorized_providers` and raises (`chia/wallet/vc_wallet/vc_wallet.py:610-625`), so the claim spend cannot be built.
5. Because `crcats_and_puzhashes` always targets the originally recorded `inner_puzzle_hash` (`chia/wallet/vc_wallet/cr_cat_wallet.py:730-745`), there is no way to redirect the coin to a different (still-VC-valid) address; the funds remain locked at Alice's pending-approval puzzle hash indefinitely unless she can obtain a brand-new VC from an authorized provider.

    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover
