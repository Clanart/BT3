## Title
Unbounded `RepeatedField` growth via `int`-sized `size()` when merging a packed field into an already near-`INT_MAX`-sized field bypasses the "full" check, disabled by protobuf's own `DISABLED_MergeFromPacked` regression test - (File: `src/google/protobuf/repeated_field_unittest.cc`)

## Summary
The Sherlock report's core failed invariant is: an attacker-controlled counter (`healCount`) is fed into arithmetic performed with `unchecked`/wrap-around semantics (`UnsafeMathUint256`), so a bounded, attacker-reachable value can silently overflow and corrupt state that gates a security-relevant limit (heal cost, escaping accounting). The closest concrete Protobuf analog is not a wrap-around bug in the hot varint/tag parsers (those are explicitly overflow-checked, see below) but a **known, still-open** integer-overflow gap in the C++ `RepeatedField`/packed-field merge path, which protobuf's own test suite documents as unfixed via `DISABLED_MergeFromPacked` and `DISABLED_MergeFrom` in `src/google/protobuf/repeated_field_unittest.cc:1787-1819`.

## Finding Description
The attacker-controlled value here is the *cumulative* size of a repeated/packed field across multiple `MergeFrom`/`ParseFrom` calls into the same message object (a pattern explicitly supported and expected by the public parsing API — repeatedly merging deserialized messages into an accumulator message, e.g. streaming aggregation). `RepeatedField<T>::size()` and `Capacity()` are `int`, and the fast/packed parsing paths (`generated_message_tctable_lite.cc`, `TcParser::RepeatedVarint`, `TcParser::PackedEnumSmallRange`, `EpsCopyInputStream::ReadPackedVarintArrayWithField`) compute the new element count as `field.size() + len` before reserving: [1](#0-0) [2](#0-1) 

These particular fast-path call sites do use `internal::CheckedAdd()` to guard the addition: [3](#0-2) [4](#0-3) 

However, protobuf's own regression-test file documents that the equivalent "is-full" / merge-overflow scenario for `RepeatedField` (both non-packed `MergeFrom` and packed `MergeFromPacked`) is **known but currently disabled/unfixed**, with an explicit `// TODO: Re-enable once parsing overflow is fixed.` comment directly above both tests: [5](#0-4) 

The scenario: a message already holds `INT_MAX` elements in a repeated/packed field (reachable by an application that repeatedly merges attacker payloads into a long-lived accumulator message, which is exactly the intended, supported "MergeFrom" pattern, not privileged/internal misuse). A subsequent, small, fully valid merged payload (`payload.add_packed_bool(true)` — one bit) is then merged in. The test asserts the correct/expected behavior would be `MergeFromString` returning `false` (rejecting the merge because the result would exceed representable `int` capacity), but the test is disabled, meaning current behavior deviates from that expectation — i.e., the size bookkeeping does not correctly detect/reject this overflow-adjacent condition end-to-end for the merge path, even though point-fixes (`CheckedAdd`) exist in some but not all size-accumulation call sites.

## Impact Explanation
This is the direct structural analog of the Solidity finding: an attacker-influenced counter that grows across supported operations (heals; here, repeated `MergeFrom` calls) is combined via `int`-width arithmetic that is not uniformly overflow-checked across all code paths that touch `RepeatedField::size()`/`Capacity()`. If the "is full"/overflow check is bypassed, the practical consequences mirror the report's category: corrupted `size()`/`Capacity()` bookkeeping for a `RepeatedField`, potentially causing under-sized buffer accounting relative to actual element count — the C++ analog of the game's "state corruption" impact, and a memory-safety-adjacent condition (wrong reported size vs actual backing storage) rather than a purely cosmetic issue.

## Likelihood Explanation
Reaching `INT_MAX` elements in one field requires either an enormous number of `MergeFrom` calls or (for `bool`/1-byte packed types) a very large but bounded allocation, which is more of a resource-heavy scenario than a single small payload — this constrains real-world exploitability compared to the Solidity report's trivial "256 heals" trigger. This is the reason the report's rule about excluding "unbounded-allocation/huge-input" analogs is relevant, and reduces confidence that this is a High-severity, single-request-triggerable issue for an "ordinary bounded client" as scoped by the prompt. I flag this explicitly as a caveat: I could not find, within the indexed code, an authoritative confirmation of exactly *which* size computation in the merge path remains unguarded (only test-level evidence that the scenario is disabled/unfixed), nor a minimal bounded-payload PoC that avoids large allocations.

## Recommendation
Audit every `RepeatedField`/packed-field merge and reserve call path (not just the fast-parse-table paths already using `internal::CheckedAdd`) to ensure `size() + incoming_count` is computed and checked with saturating/checked arithmetic before any reserve/resize, and re-enable `DISABLED_MergeFrom`/`DISABLED_MergeFromPacked` in `repeated_field_unittest.cc` once fixed, so that merges which would overflow `int` capacity are rejected (return `false`) rather than silently mis-accounted.

## Proof of Concept
I was not able to construct or run a minimal bounded-payload reproduction within the scope of this investigation; the only concrete evidence available is protobuf's own currently-disabled tests, which describe the reproduction shape (grow a `RepeatedField`/packed field to `INT_MAX` elements via repeated legitimate merges, then merge one more small valid element and observe that overflow-safe rejection does not occur as expected): [5](#0-4)
