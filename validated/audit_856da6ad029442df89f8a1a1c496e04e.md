Based on my investigation, I found a strong analog. The mechanism directly parallels the reported bug: a "stale-state used to compute a critical decision" pattern, but rather than TCR/ICR it's the line-index selection used to build a partial commit's patch.

Key facts found:
- `updateChangesWorkingDirectoryDiff` in `app-store.ts` explicitly acknowledges that a file's diff "might have changed dramatically since last we loaded it" and only prunes now-invalid selectable lines by intersecting them with `selectableLines`, without invalidating the selection's semantic meaning. [1](#0-0) 
- `_commitIncludedChanges` reads `file.selection` straight from the cached `repositoryStateCache` (set at UI-selection time) and passes it, unmodified, into `createCommit`. [2](#0-1) 
- `createCommit` → `stageFiles` → `applyPatchToIndex` **re-fetches a fresh diff** via `getWorkingDirectoryDiff` right before staging, but then formats the patch by re-applying the *old* `file.selection.isSelected(absoluteIndex)` bit-set against this brand-new diff's line indices. [3](#0-2) [4](#0-3) 

This is exactly the same invariant violation as the report: a downstream, security-relevant decision (which bytes get committed) is computed by combining a *stale* selection (computed against an old diff snapshot) with a freshly synced diff, without validating that the old selection still corresponds to the same logical lines in the new diff.

### Title
Partial-commit line selection is replayed against a re-diffed working tree without revalidation, allowing silent commit of unintended content - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
When a user stages a partial selection of lines in a file (checking/unchecking individual diff lines) and later clicks "Commit," Desktop does not guarantee that the line-selection bitmap it captured while rendering the diff still corresponds to the same lines in the file at commit time. `applyPatchToIndex` re-computes a **fresh** `git diff` for the file right before staging [5](#0-4) , then `formatPatch` walks that fresh diff's hunks and asks `file.selection.isSelected(absoluteIndex)` [6](#0-5)  — but `file.selection` is the selection object captured against the *previous* diff. If the working-tree file changes between the time the user made their line selection and the time `_commitIncludedChanges` actually runs (e.g., a build tool, linter/formatter, git hook, or file watcher rewrites the file, or a background repository refresh interleaves), the hunk/line layout of the fresh diff can differ from the one the user visually reviewed, so the same absolute line indices now point at different content.

### Finding Description
The invariant that is broken is: "the set of lines a user visually selected for inclusion must be re-validated against the exact diff state used at commit time." Desktop does perform a similar staleness check for the *rendering* path — `updateChangesWorkingDirectoryDiff` explicitly detects that "the diff might have changed dramatically since last we loaded it" and prunes selectable lines accordingly [7](#0-6)  — but that check only fires as a side effect of the periodic status/diff refresh loop while the Changes tab is open with that file selected; it does not run, and there is no equivalent guard, immediately before `_commitIncludedChanges` stages files via `createCommit` → `stageFiles` → `applyPatchToIndex`. `_commitIncludedChanges` simply reads whatever `file.selection` currently sits in `repositoryStateCache` [2](#0-1) , without re-diffing and re-validating the selection immediately beforehand. The staging code path itself performs a **fresh** `getWorkingDirectoryDiff` call inside `applyPatchToIndex` at commit time [5](#0-4) , so the guarantee that "the diff last shown to the user" and "the diff used to build the patch" are the same object is broken by design — `formatPatch` mechanically applies old line indices to a new hunk structure [8](#0-7) .

### Impact Explanation
This can silently corrupt what the user commits and subsequently pushes: lines the user explicitly excluded from a partial commit could be included (leaking content the user intended to keep out of history, e.g., a secret or debug line they unchecked), or lines the user intended to include could be dropped/misapplied, producing a commit that doesn't match the reviewed diff. Because the user has already reviewed and approved the diff in the UI before clicking Commit, they have no reason to re-verify content, and the corruption happens without any error or warning — meeting the "silent corruption of what the user commits or pushes" impact criterion.

### Likelihood Explanation
The attacker primitive required is: something that modifies tracked working-tree file content between the user's line selection and the click of the Commit button. This is realistic in normal, unprivileged workflows already supported by Desktop — e.g. a repository-configured pre-commit/format-on-save tool, an editor auto-format-on-save extension, or another process (build watcher) rewriting the file while Desktop is open — none of which require local/admin access beyond what a developer normally has, and none of which are "attacker installs malware" scenarios. The repository's build tooling or hooks (which are attacker-controllable if the repo itself is attacker-supplied, matching the "attacker controls a cloned/fetched repository" impact category) can be the trigger.

### Recommendation
Immediately before staging (`_commitIncludedChanges`/`applyPatchToIndex`), re-fetch the diff for each partially-selected file and validate that the hunk/line layout used to build `file.selection` still matches the fresh diff (the same integrity check already implemented in `updateChangesWorkingDirectoryDiff` for the render path). If the diff has changed, abort the commit for the affected file (or all files) and force the user to re-review the selection, rather than silently replaying stale line indices onto a new diff.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`, producing a diff with, e.g., 10 added lines.
2. In the Changes view, use line-level selection to check only lines 1–5 for inclusion (unselecting 6–10), matching the `DiffSelection` bitmap captured against the current diff [9](#0-8) .
3. Before clicking "Commit," have an external process (e.g., a pre-existing file watcher/formatter, or simply editing the file directly outside Desktop) change `file.txt` so that the new diff has a different hunk layout (e.g., additional lines inserted near the top, shifting subsequent line numbers).
4. Click "Commit." `_commitIncludedChanges` uses the stale `file.selection` [2](#0-1) ; `applyPatchToIndex` re-diffs the now-changed file [5](#0-4)  and `formatPatch` applies the old absolute-line-index selection to the new hunks [6](#0-5) .
5. Inspect the resulting commit: it contains content that does not match what the user selected in step 2 (extra/different lines included or excluded), with no warning shown to the user.

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
```
