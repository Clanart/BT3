### Title
Malformed `git status --porcelain=2` entries from a crafted repository can abort status refresh and leave Desktop committing against stale working-directory state - ([File: app/src/lib/status-parser.ts])

### Summary
`getStatus()` in Desktop is the functional analog of `get_vault_borrowing_power()`: it is invoked before every commit/refresh and loops over every entry returned by `git status --porcelain=2 -z`, parsing each one with a strict, fixed-format regex. If a single entry fails to match the expected pattern, the parser throws, the exception propagates out of the entire status computation, and the caller silently swallows it — leaving the UI and the data used for the next commit based on the **previous, stale** working-directory snapshot rather than the repository's actual current state.

### Finding Description
`parsePorcelainStatus()` dispatches each NUL-separated status line to one of three strict parsers: [1](#0-0) [2](#0-1) [3](#0-2) 

Each of these functions throws an `Error` (`Failed to parse status line for ...`) if the fixed regex (`changedEntryRe`, `renamedOrCopiedEntryRe`, `unmergedEntryRe`) doesn't match the line exactly, including the submodule status field `(N\.\.\.|S[C.][M.][U.])`. Any status line git emits that doesn't fit these hard-coded shapes — e.g. an unusual submodule state, a corrupted/nested `.git` link, or output produced from a specially crafted tree/submodule configuration inside a cloned or fetched repository — causes the whole `parsePorcelainStatus()` call, and therefore `getStatus()`, to throw: [4](#0-3) 

This is structurally identical to the `get_vault_borrowing_power()` pattern: a single loop over records that are influenced by external/untrusted state (here, the contents of a repository the user cloned or fetched, since submodule status codes and tree layout are attacker-controlled), where one bad record aborts the whole computation instead of being isolated.

The failure is not surfaced as a hard error to the user in a way that blocks the action; it is caught and swallowed: [5](#0-4) 

and the caller in `app-store.ts` simply returns without updating any of the changes state when `status` is `null`/undefined: [6](#0-5) 

Because `repositoryStateCache.updateChangesState` is never called on this path, `state.changesState.workingDirectory.files` keeps whatever it held before the failed refresh. That stale list is exactly what `_commitIncludedChanges` uses to decide what to stage and commit: [7](#0-6) 

### Impact Explanation
If an attacker crafts a repository (e.g., a submodule tree or repository layout that produces a `git status --porcelain=2` submodule/status field combination outside the parser's hard-coded regexes) and the victim clones/fetches/opens it in Desktop, every subsequent status refresh in that repository can throw and be swallowed. From then on, Desktop's Changes view and the commit action operate on the last successfully computed (stale) working-directory diff instead of the real one. This can cause the user to commit or push content that does not match what they believe they are committing — silently corrupting what gets committed — without any indication beyond a background error being emitted (which may not block or clearly explain the actual risk to the user). This matches the accepted impact class: attacker controls a cloned/fetched repository and the result is silent corruption of what the user commits/pushes.

### Likelihood Explanation
The likelihood depends on finding a concrete repository layout that reliably makes `git` emit a `status --porcelain=2` line outside the three regexes in `status-parser.ts` (for example an edge-case submodule status combination not covered by `(N\.\.\.|S[C.][M.][U.])`, or unusual typechange/conflict encodings). I could not fully verify from the indexed code whether such a git-emitted line is producible purely from repository content (as opposed to requiring a corrupted local git installation), so likelihood is uncertain/medium — it requires further empirical testing against real `git status --porcelain=2` output for adversarial submodule/tree layouts, which is outside what the static index can confirm.

### Recommendation
Make `parsePorcelainStatus()` resilient to unrecognized/malformed lines: skip and log the offending entry instead of throwing, so one anomalous entry cannot abort the entire status computation. Additionally, `_loadStatus()` should not silently retain stale `changesState` when a refresh fails — it should surface a hard, blocking error state (or clear/mark the working directory as unknown) so the commit/push actions cannot proceed against out-of-date data.

### Proof of Concept
Conceptual PoC (not fully verified against live `dugite`/git output, see likelihood caveat):
1. Attacker creates a repository containing a submodule (or gitlink) configured so that `git status --porcelain=2 -z` in a clone of it emits a submodule status field combination not matching `N\.\.\.` or `S[C.][M.][U.]` (e.g., via an unusual/incomplete submodule initialization state).
2. Victim clones this repository in GitHub Desktop.
3. On the first/any subsequent status refresh, `parseChangedEntry`/`parsedRenamedOrCopiedEntry` throws inside `parsePorcelainStatus()` → `getStatus()` rejects.
4. `gitStore.loadStatus()` → `performFailableOperation` catches and emits a background error, returning `undefined`.
5. `_loadStatus()` sees a falsy status and returns without updating `changesState`; the Changes list keeps showing whatever was computed before (or an empty/initial state).
6. Victim commits based on this stale/incorrect view via `_commitIncludedChanges`, which stages `state.changesState.workingDirectory.files` — silently mismatched from the true repository state. [8](#0-7)

function parseChangedEntry(field: string): IStatusEntry {
  const match = changedEntryRe.exec(field)

  if (!match) {
    log.debug(`parseChangedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for changed entry`)

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],

function parsedRenamedOrCopiedEntry(

  if (!match) {
    log.debug(`parsedRenamedOrCopiedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for renamed or copied entry`)
  }

    throw new Error(
      'Failed to parse renamed or copied entry, could not parse old path'

    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    oldPath,

}

    fn: () => Promise<T>,
    errorMetadata?: IErrorMetadata
  ): Promise<T | undefined> {
    try {
      const result = await fn()
      return result
    } catch (e) {
      e = new ErrorWithMetadata(e, {
