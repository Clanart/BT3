Based on the investigation, the closest structural analog to the reversed-token-order bug (a function that silently swaps two conceptually opposite sides of an operation) is the "ours/theirs" side mapping used in GitHub Desktop's Copilot conflict-resolution diff preview during a rebase.

### Title
Copilot conflict-resolution diff preview can mislabel "ours"/"theirs" during rebase, causing users to silently commit the wrong side - ([File: app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx])

### Summary
`getResolutionDiff()` explicitly documents that git's `ours`/`theirs` stage semantics invert during a rebase (upstream = "ours", the commit being replayed = "theirs"), and states that "the caller is responsible for mapping user-facing labels to the correct git side." [1](#0-0) 
`CopilotConflictsChanges.loadDiffForFile()` takes the raw `ManualConflictResolution` choice ('ours' | 'theirs') and forwards it unchanged as the `stage` option to `getResolutionDiff`, with no rebase-specific remapping visible in this call site. [2](#0-1) 

### Finding Description
`getResolutionDiff`'s stage mode always reads git's raw index stages `:2:` (ours) and `:3:` (theirs) directly. [3](#0-2) 
The dialog derives the on-screen labels for these two options ("current branch" vs "incoming branch" style text) from `ourBranch`/`theirBranch` via `getOursTheirsLabels`, and the reasoning text shown next to a selected choice is built the same way, e.g. `Using changes from ${this.props.conflictState.ourBranch ?? 'current branch'}` for choice `'ours'`. [4](#0-3) 
Because git swaps the meaning of stage 2/3 specifically during rebase (as called out in the `getResolutionDiff` doc comment), a label pipeline that maps `ourBranch`/`theirBranch` straight onto `'ours'`/`'theirs'` without a rebase-specific swap will show the diff/reasoning for the wrong branch: a user picking what the UI calls "current branch" during a rebase would actually be selecting the upstream/target branch's content (stage 2), not their own commit's content, and vice versa.

### Impact Explanation
If the label-to-stage mapping is not swapped for rebase (as the doc comment warns is required), a user resolving a conflict during `git rebase` who intentionally picks "keep my changes" would instead have the diff preview (and, if the same unresolved mapping feeds the final resolution write path via `ManualConflictResolution.ours`/`.theirs`) apply the upstream branch's content. This silently corrupts what gets committed/rebased without any error or warning, and the user has no way to detect it because the label they trusted was itself wrong.

### Likelihood Explanation
This triggers under a completely ordinary, unprivileged workflow — any rebase with a Copilot-assisted conflict resolution where the user manually overrides Copilot's suggestion with "ours" or "theirs" — no attacker-controlled repo content, malware, or special permissions are required beyond what the report's bug class (parameter-order confusion) implies. Likelihood is data-dependent on whether `getOursTheirsLabels` (not fully inspectable in the available index) performs the rebase swap; based on the direct, unconditional pass-through observed in `copilot-conflicts-changes.tsx` and the absence of any `isRebase`/`MultiCommitOperationKind.Rebase` branching found in the resolution-helpers search results, it appears no such swap occurs.

### Recommendation
In `copilot-conflicts-changes.tsx` and `copilot-conflicts-dialog.tsx`, when `operationKind === MultiCommitOperationKind.Rebase`, swap the `stage` value passed to `getResolutionDiff` (map `'ours'` → `'theirs'` and vice versa) and swap which of `ourBranch`/`theirBranch` is used to build labels/reasoning text, matching git's actual rebase semantics as already documented in `getResolutionDiff`. Verify the same swap is applied consistently wherever `ManualConflictResolution.ours`/`.theirs` is written to disk (e.g. `checkout-index.ts`) so the previewed diff and the actually-applied resolution never diverge.

### Proof of Concept
Not independently verified end-to-end (would require exercising the full Copilot conflict-resolution flow during an active `git rebase` and comparing the previewed diff/label against the git stage actually staged on `Continue`). The evidence gathered is limited to the source-level mismatch between the documented requirement in `getResolutionDiff` and the unconditional pass-through in `CopilotConflictsChanges.loadDiffForFile`; I could not confirm within the available index whether `getOursTheirsLabels` (app/src/ui/multi-commit-operation/dialog/copilot-resolution-helpers.ts) or the final apply path (`checkout-index.ts`) perform the necessary rebase-side swap, so this should be treated as a likely-but-unconfirmed analog rather than a fully reproduced bug.
