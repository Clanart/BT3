### Title
Unbounded recursive parsing in `PuzzleWithRestrictions.from_memo()` allows a crafted on-chain memo to crash wallet/plotnft sync via Python `RecursionError` - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody structure from a CLVM `Program` memo. When the memo encodes an `MofN` member, it recurses into `PuzzleWithRestrictions.from_memo()` again for every member, with no depth or size limit on the input `Program`. This mirrors the RabbitMQ `ValueReader.readTable()`/`readArray()` bug class (CWE-674, unbounded recursive deserialization of an attacker-influenced nested structure), except here the "deeply nested table" is a CLVM memo attached to a `CREATE_COIN` output that any coin creator controls.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses a `Program` and, if the puzzle hint indicates further branching (an `MofN` node), calls itself once per member: [1](#0-0) 

This is structurally identical to `ValueReader.readTable()`/`readArray()` calling `readFieldValue()` recursively with no depth counter — each `MofN` "member" in the memo is one recursion level, and the format allows arbitrarily deep nesting of `MofN(members=[PuzzleWithRestrictions(puzzle=MofN(...))])` chains.

Critically, this parser is not confined to test code. It is invoked from production plotnft-sync logic when a client processes a `CREATE_COIN` on chain that carries a custody-style memo: [2](#0-1) 

`get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` on the memo attached to whatever coin the singleton's inner puzzle created — that memo content is entirely controlled by whoever constructs the spend (e.g. a pool operator, a peer running a plotnft-compatible singleton, or anyone crafting a coin spend that a plotnft wallet later has to sync/parse). `chia/wallet/plotnft_wallet/plotnft_wallet.py` and `chia/wallet/wallet_state_manager.py` reference `get_next_from_coin_spend`, meaning normal wallet sync of an existing plotnft singleton lineage will run this parser against on-chain data that is not otherwise validated for structural depth.

Each `MofN` recursion level only costs a handful of bytes in the memo program (an `m` value, one or more member sub-programs, and a nesting tag), and `Program` parsing itself goes through the Rust CLVM parser (bounded), but the **Python-level** `from_memo` recursion has no equivalent bound. A sufficiently deep chain of nested `MofN` members will exhaust the Python call stack in the process performing wallet/plotnft sync, killing that thread/process — the same denial-of-service mechanism as the RabbitMQ advisory.

### Impact Explanation
A wallet (or any client syncing a plotnft singleton lineage, including `wallet_state_manager.py`/`plotnft_wallet.py`) that processes an on-chain coin whose memo contains a deeply nested `MofN` custody structure will hit unbounded Python recursion in `PuzzleWithRestrictions.from_memo()`, raising `RecursionError` (or crashing the interpreter on some builds) during normal sync. This is a spend-triggered transaction-processing halt of the syncing client — an unprivileged coin creator can knock a wallet's plotnft-sync path offline by simply spending a coin with a malicious memo, matching the report's "impact: denial of service" class and the finding criteria's "spend-triggered transaction-processing halt."

### Likelihood Explanation
Likelihood is moderate-to-high for any wallet actively tracking a plotnft/singleton whose spend chain includes a malicious or compromised counterparty (e.g., a pool, a shared custody co-signer, or any party able to influence what memo is attached to the singleton's created coin). The attacker does not need special privileges — only the ability to get a coin spend with a crafted memo included in a block, which is an ordinary unprivileged transaction. The main uncertainty is exactly how deep an in-block memo can be pushed before mempool/block size or CLVM cost limits stop it, and I could not fully verify the maximum achievable Python recursion depth from within these limits without running an exploit — this bounds the confidence but does not eliminate the vulnerability, since the recursive code path itself has zero depth checking regardless of what practical depth is reachable.

### Recommendation
Add an explicit depth counter/limit to `PuzzleWithRestrictions.from_memo()` (and the mutually-recursive `MofNHint.from_program()` path) and raise a clear `ValueError` once a maximum nesting depth (e.g., 32–64) is exceeded, mirroring the fix pattern used in the RabbitMQ advisory. Alternatively, convert the recursive descent into an iterative worklist/stack-based implementation, consistent with the project's own precedent in `chia/types/blockchain_format/tree_hash.py`'s `sha256_treehash()`, which is deliberately iterative "so we don't have to worry about blowing out the python stack."

### Proof of Concept
Construct a memo `Program` encoding nested `MofN` structures many levels deep, e.g. build:
```
inner = MemberHint(puzhash=..., memo=Program.to(None))
level0 = PuzzleWithRestrictions(nonce=0, restrictions=[], puzzle=UnknownMember(inner))
for i in range(N):  # N large enough to exceed Python's recursion limit, e.g. 2000+
    level0 = PuzzleWithRestrictions(
        nonce=i, restrictions=[],
        puzzle=MofN(m=1, members=[level0]),
    )
memo = level0.memo()
```
Then call `PuzzleWithRestrictions.from_memo(memo)` (or drive it through `get_next_from_coin_spend()` by putting `memo` as the memo on a `CREATE_COIN` output of a plotnft singleton spend). This raises `RecursionError` in the parsing client. Full end-to-end wiring through an actual mined coin spend and plotnft wallet sync was not executed in this analysis; the recursive code path and its production call site were confirmed by direct code inspection only.
