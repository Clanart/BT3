### Title
Gasless swap deadline is validated against `CurrentBlock().Time()` at mempool admission, not at execution time - allowing stale swaps to be promoted/included after the deadline has effectively passed - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The `checkBalanceForSwap` function in the gasless module validates the KIP-247 `GaslessSwapTx.deadline` field by comparing it against `g.Chain.CurrentBlock().Time()` at the moment the transaction is checked for pool admission/promotion, rather than at the time the transaction is actually included and executed in a block. [1](#0-0) 

### Finding Description
This is the same bug class as the reported "shouldn't use block.timestamp as deadline" issue, adapted to Kaia's gasless swap admission logic instead of a Solidity AMM adapter. `checkBalanceForSwap` performs:
```go
// tx.deadline >= currentTimestamp
deadline := swapArgs.Deadline
if deadline.Cmp(g.Chain.CurrentBlock().Time()) < 0 {
    return fmt.Errorf("insufficient deadline: ...")
}
``` [1](#0-0) 

This check is invoked via `GetCheckBalance()`, which is called from the core tx pool both at initial validation (`validateTx`) and again during `txList.Filter` when re-evaluating queued/pending transactions for promotion. [2](#0-1) [3](#0-2) 

Because `CurrentBlock().Time()` reflects the timestamp of the last mined block (not the timestamp the transaction will have when it is actually assembled into a future block), a `GaslessSwapTx` with `deadline` slightly greater than the current block time can pass this check and be promoted into the pending pool. It can then remain queued/pending (a gasless bundle is only pruned after `QueueTimeout`/`PendingTimeout` of 10 seconds, and `KnownTxTimeout` of 30 seconds) and may or may not be re-validated depending on pool re-filtering cadence, before it is ultimately picked up by the block proposer for inclusion in a bundle (`[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]`) as described in the module's README. [4](#0-3) [5](#0-4) 

Unlike the original Sherlock finding (miner deliberately holding a swap tx to extract MEV against an AMM pool with an on-chain `block.timestamp` deadline check that always passes), here the risk is inverted but structurally analogous: the **admission-time check uses a timestamp that is not the timestamp of execution**, so the guarantee "deadline >= execution time" that the sender/proposer economic model depends on (bounding how stale the exchange-rate assumption and `amountRepay`/`minAmountOut` commitment can be) is not actually enforced at execution time by the node's mempool logic. If the on-chain `GaslessSwapRouter.swapForGas` contract itself re-validates `deadline` at execution (which could not be confirmed from the available Solidity source, only Go bindings were found), the failure mode degrades to wasted lending: the block proposer's `LendTxGenerator` fronts gas for a bundle whose swap subsequently reverts on-chain due to an expired deadline, burning the proposer's lent KAIA with no successful repayment.

### Impact Explanation
If the on-chain contract does enforce the deadline strictly, the impact is that a stale gasless swap can pass the node's admission/promotion checks and get bundled by the block proposer (who fronts real KAIA gas via `LendTxGenerator`) only to revert on execution, causing the proposer to lose the lent gas fee with no repayment - a fee-delegation/gasless abuse and value-loss vector reachable by any ordinary gasless-swap sender who crafts a swap transaction with a deadline that is valid relative to the last block but will be stale by the time of actual inclusion (e.g., during periods of slow block production, high tx pool congestion, or if the sender intentionally submits many such swaps to grief block proposers). This directly falls under "fee-delegation abuse" / "gasless settlement theft" in the accepted analog categories.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) a gap between `CurrentBlock().Time()` at admission and the actual timestamp of the block that finally includes the bundle (network congestion, slow promotion, or the pool's periodic re-filtering not catching a tx before proposer picks it up), or (b) intentional submission of borderline-deadline swap transactions by a malicious sender to grief the block proposer. Since gasless transactions skip the ordinary sender balance/fee checks and rely entirely on `GetCheckBalance()` for admission gating, an attacker fully controls the submitted `deadline` value and can tune it to just barely pass admission while risking staleness by the time of block assembly.

### Recommendation
Re-validate the swap's `deadline` at the moment the block proposer actually assembles/executes the bundle (i.e., in the builder logic that generates `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]`), not only during pool admission using `CurrentBlock().Time()`. Additionally, ensure the on-chain `GaslessSwapRouter.swapForGas` enforces its own deadline check independent of the node's mempool logic, and have the block-building/bundle-selection code drop or re-check any gasless bundle whose `deadline` is stale relative to the timestamp of the block currently being built, before committing the `LendTxGenerator` funds.

### Proof of Concept
1. Attacker crafts a `GaslessSwapTx` with `deadline = CurrentBlock().Time() + 1` (minimum value that passes `checkBalanceForSwap`). [1](#0-0) 
2. Tx pool admits/promotes the transaction into pending because the check only compares against the last mined block's timestamp, not the timestamp of the block that will eventually include it. [2](#0-1) 
3. Due to congestion or bundle scheduling delay, the block proposer only picks up and builds the bundle `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` several seconds later, by which time the real block timestamp exceeds `deadline`. [5](#0-4) 
4. The proposer's `LendTxGenerator` fronts gas KAIA to the sender; if the underlying `GaslessSwapRouter` contract enforces the deadline on-chain, `swapForGas` reverts, the sender's repayment does not occur, and the proposer's lent value is lost while gas is still consumed by the failed transaction.
