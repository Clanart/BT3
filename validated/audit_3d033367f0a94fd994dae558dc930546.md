## Title
Malicious `.gitattributes` `text` override + embedded NUL byte causes `diffFromRawDiffOutput` to silently show an empty/corrupted diff for a modified file - (File: `app/src/lib/git/diff.ts`)

### Summary
`diffFromRawDiffOutput` parses the output of `git diff --patch-with-raw -z` by naively splitting the *entire* stdout buffer on every NUL byte and feeding only the last fragment to `DiffParser.parse`: [1](#0-0) 

This logic assumes NUL bytes only ever occur as raw-format field/line terminators produced by `-z`, and that the trailing patch text is always NUL-free plain text. An attacker who controls repository content (including `.gitattributes`) can violate that assumption.

### Finding Description
Git's binary-vs-text classification for diff purposes can be overridden per-path via the `.gitattributes` `text` attribute. When a path is explicitly marked `text` (e.g. `payload.bin text`), Git skips its normal `NUL-byte-in-buffer` binary heuristic and unconditionally treats the blob as text for `git diff`, emitting a normal unified-diff hunk instead of `Binary files ... differ` — even if the blob's actual bytes contain an embedded `\0`.

Because `diffFromRawDiffOutput` calls `output.toString('utf-8').split('\0')` over the whole buffer and keeps only `pieces.at(-1)`: [2](#0-1) 

any NUL byte embedded in the actual diff hunk content (which appears *after* the `--- a/...` / `+++ b/...` header lines) causes the split to cut the buffer inside the patch body. The fragment handed to `DiffParser.parse` no longer begins with the `diff --git` / `+++` header. `DiffParser.parseDiffHeader` then scans to the end of that truncated text without ever finding a `+++` or `Binary files` marker and returns `null`: [3](#0-2) 

which `parse()` treats as a legitimate "empty diff" state and returns zero hunks with empty `contents`: [4](#0-3) 

The net effect: Desktop's diff view shows the file as having no changes at all (or a truncated/shifted set of hunks, depending on NUL placement), even though the working tree/commit genuinely differs from `HEAD`.

Note that `getWorkingDirectoryDiff`, `getCommitDiff`, `getCommitRangeDiff`, and `getBranchMergeBaseDiff` all invoke `git diff`/`git log` with `--patch-with-raw -z` and feed the buffer straight into `diffFromRawDiffOutput`/`buildDiff`, so this path is reachable for ordinary working-directory and history review flows: [5](#0-4) 

### Impact Explanation
This does not directly let the attacker write outside the repo or execute code, but it does let a malicious repository **silently corrupt what the user reviews before committing/pushing**: a file that actually changed (potentially maliciously, e.g. a hidden backdoor appended after the NUL) will render in the Changes/diff pane as unchanged or with hunks missing. A user who trusts the diff view to decide what to stage/commit/merge can be misled into committing or merging content they never actually saw, which matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Requires the attacker to control a cloned/fetched repository containing:
1. A `.gitattributes` entry forcing `text` on a specific path (fully attacker-controlled, no user interaction needed).
2. That path's committed/working-tree content containing an embedded NUL byte positioned inside a diff hunk.

Both are ordinary repository content the attacker fully controls; no privileged access, social engineering beyond "the user opens/works in the cloned repo", or unnatural steps are required. The main uncertainty is git-version-dependent internals of the `text` attribute override, but this is documented, stable Git behavior.

### Recommendation
Do not rely on a global `split('\0')` over the whole buffer. Instead:
- Locate the boundary between the raw section and the patch section deterministically (e.g. find the first occurrence of `\ndiff --git ` / the empty line that separates `--raw` output from patch text, or use `--no-abbrev`/parse raw entries with a bounded number of NUL splits based on the known raw-record shape) rather than assuming everything after the *last* NUL is the entire patch.
- Alternatively, avoid `--patch-with-raw` entirely for file-scoped diff calls (since the raw part isn't used) and just use `--patch -z`, then only use `indexOf`/`substring` between the known raw header and rest, and validate that parsed header info reflects the full patch (e.g. treat a `null` `headerInfo` returned for a file that git reported as changed as an error condition instead of "empty diff, no problem").

### Proof of Concept
1. Create a directory `repo/.gitattributes` with:
   ```
   payload.bin text
   ```
2. Commit `payload.bin` with content `A`.repeat(50) (no NUL).
3. Modify `payload.bin` to `("A".repeat(50) + "\0" + "MALICIOUS_APPENDED_CONTENT")` in the working tree (do not commit).
4. Run `git diff --no-ext-diff --patch-with-raw -z HEAD -- payload.bin` (simulating `getWorkingDirectoryDiff`) — verify the output is a normal (non-binary) unified diff hunk containing the literal NUL byte inside a `+`/context line rather than `Binary files ... differ`.
5. Feed that buffer into `diffFromRawDiffOutput` (or run Desktop against this repo and open the file in Changes): compare `parser.parse(pieces.at(-1)).hunks.length` (expected: `0`, i.e. no visible change) against manually parsing the true, un-split patch text (expected: `1` hunk showing the appended malicious content) — demonstrating the change is hidden from the diff view. export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}

function diffFromRawDiffOutput(output: Buffer): IRawDiff {
  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')

  const pieces = result.split('\0')
  const parser = new DiffParser()
  return parser.parse(forceUnwrap(`Invalid diff output`, pieces.at(-1)))
}
