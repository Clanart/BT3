### Title
Unvalidated `kip71.gastarget` governance parameter enables division-by-zero panic in `NextMagmaBlockBaseFee`, halting block production/validation on every node - ([File: params/kip71_config.go])

### Summary
Analogous to the Perennial `updateUtilizationCurve` bug (a privileged parameter-update function that fails to validate the new value before it is consumed by downstream math), Kaia's governance parameter framework accepts a `kip71.gastarget` (and related KIP-71) value with essentially no bounds/format validation, and that raw value is later used as a divisor in the base-fee calculation performed on the hot block-processing path.

### Finding Description
The `kip71.gastarget`, `kip71.basefeedenominator`, and `kip71.maxblockgasusedforbasefee` governance parameters are registered with a no-op format checker that accepts any `uint64`, including `0`: [1](#0-0) 

Contrast this with `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which at least get a relative cross-check against each other in `checkConsistency`, while `GasTarget`, `BaseFeeDenominator`, and `MaxBlockGasUsedForBaseFee` are explicitly passed through with "no more checks": [2](#0-1) 

The unvalidated `GasTarget` value flows into `KIP71Config.NextMagmaBlockBaseFee`, which is called on every block to compute the required base fee: [3](#0-2) 

The function only special-cases `BaseFeeDenominator == 0` (substituting 64), but has no equivalent guard for `GasTarget == 0`: [4](#0-3) 

When `parentGasUsed > gasTarget` (true whenever `gasTarget == 0` and any gas was used in the parent block), the code computes:
```
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
```
which is a division by zero on a `math/big.Int`, which panics in Go. This same computation is invoked both when building a new block (in `work/worker.go`) and when validating a received block header's `baseFee` field (`VerifyMagmaHeader`), so once such a value is activated, every node computing or validating the next block panics.

The parameter is set on-chain either via `GovParam.setParamIn`/`setParam` (owner-only contract call producing an on-chain transaction) or via header governance vote — both are "submitted transactions" that pass through the vulnerable format-check pipeline in `kaiax/gov`. [5](#0-4) [6](#0-5) 

### Impact Explanation
Once the parameter activates at a given block, `NextMagmaBlockBaseFee` will panic for every honest node that attempts to build or validate the affected block (worker, block validator, gas price estimation, fee history APIs, tx pool base fee checks all call into this path). This is not merely a revert of an admin call (as in the original low-impact report) — it is an unrecoverable panic reachable from consensus-critical code once a bad governance value is accepted, resulting in a full chain halt (all nodes reaching an invalid/panicking state simultaneously) rather than a graceful rejection of the parameter change.

### Likelihood Explanation
Likelihood depends on the GovParam contract owner (or a validator submitting a governance vote) submitting `kip71.gastarget = 0`. This is a single "submitted transaction" mistake or malicious governance action; because there is zero format validation on this specific parameter (`noopFormatChecker`), nothing in the code path prevents it from being accepted and later activated.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) requiring `v > 0`, mirroring the existing cross-check pattern already used for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` in `checkConsistency`. Additionally, add a defensive `gasTarget == 0` guard directly in `NextMagmaBlockBaseFee` (similar to the existing `BaseFeeDenominator == 0` fallback) so that even if an invalid value is ever activated, the node cannot panic.

### Proof of Concept
1. GovParam contract owner (or governing-node validator) submits a transaction/vote setting `kip71.gastarget` to `0`. [1](#0-0) 
2. The value passes `Add()`'s canonicalizer/format-check pipeline unchanged because `FormatChecker: noopFormatChecker`. [6](#0-5) 
3. At activation, any block whose parent used > 0 gas triggers `parentGasUsed > gasTarget` branch in `NextMagmaBlockBaseFee`, executing `x.Div(x, new(big.Int).SetUint64(0))`. [7](#0-6) 
4. `math/big.Int.Div` panics on division by zero, crashing the block-building/validating goroutine on every node that reaches this code, halting the chain.

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]
	if !ok {
		return ErrInvalidParamName
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
}
