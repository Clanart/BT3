## Analysis Summary

The Sherlock report describes a **broken identity invariant after removal**: `CouncilMember.burn()` removes an element from the `balances` array without correctly recomputing the tokenId→index mapping for all subsequent tokenIds, so a later `claim(tokenId, ...)` reads the wrong slot or reverts <cite repo="bsaldua/protobuf--015" path="" start="" end="" />. The failed invariant is: *"logical identifier (tokenId) must map to correct backing-storage index after any removal operation."*

## Protobuf analog located

`upb`'s internal open-chained hash table (`upb_inttable`/`upb_strtable`, used for `upb_Map`, `upb_ExtensionRegistry`, and `upb_DefPool`) implements exactly this "removal must preserve identity→slot mapping while iterating" invariant in `removeiter()`: [1](#0-0) 

This function is explicitly documented and unit-tested as **broken** for a specific collision-chain shape. The test suite contains two back-to-back tests — one that passes (`RemoveIterHeadOfChain`) and one explicitly named to document the defect: [2](#0-1) 

The bug is in the decision of whether to decrement the iterator (`*iter = i - 1;`) after moving a chained entry into the head slot — it uses **pointer comparison** (`move > ent`) rather than the entries' true table-index/bucket relationship, mirroring the Solidity bug's core defect of relying on a stale/incorrect index after a swap-based removal: [3](#0-2) 

`removeiter` backs the public `upb_inttable_removeiter`/`upb_strtable_removeiter`, which are used from `upb/message/internal/map.h` and `upb/message/convert.c` (map/value conversion code), and the same non-iterating sibling `rm()` (same head-of-chain "move" logic) is used unconditionally by every `upb_inttable_remove`/`upb_strtable_remove`/`upb_exttable_remove` call, including the ones backing `upb_Map_Delete` and `upb_ExtensionRegistry_AddArray`'s rollback path [4](#0-3) [5](#0-4) .

## What I could confirm vs. what remains uncertain

- **Confirmed**: The defect is real, reproducible, and explicitly acknowledged in-repo by a test named `RemoveIterHeadOfChainDemonstratesBug`, which is the same class of bug as the Sherlock report (index/identity invariant broken by an in-place "swap on removal" optimization).
- **Not fully confirmed**: I was unable to trace, within the available tool budget, a concrete call path from an ordinary bounded `ParseFromString`/ProtoJSON decode of untrusted bytes through to `removeiter` specifically (as opposed to the simpler `rm()` used by normal map key overwrite during parsing). The iterate-and-remove pattern in `message/internal/map.h` and `message/convert.c` appears used for map/value conversion utilities rather than the hot decode path for duplicate map keys, and I could not verify within budget whether any public, unprivileged, bounded-input API (e.g., merging two messages containing map fields with colliding keys, or `Any` unpacking into a map) drives iteration-with-removal over the same table rather than simple lookup+insert.

Given this, I can state confidently that this is a genuine internal correctness defect matching the report's bug class (index/identity mismatch after removal), but I cannot certify with the same confidence that it is reachable purely through a bounded, unprivileged binary/ProtoJSON parse call without deeper tracing of `message/internal/map.h` and `message/convert.c`, which a follow-up session with full read access should verify before treating this as a definitively exploitable Medium.

### Title
Index-identity mismatch in `removeiter()` head-of-chain removal - (File: `upb/hash/common.c`)

### Summary
`upb`'s hash-table `removeiter()` uses a pointer comparison (`move > ent`) instead of correct bucket/logical-index tracking to decide whether the just-moved chain entry needs to be revisited by the iterator, an invariant violation analogous to the reported Solidity `burn`/`claim` index-mismatch bug.

### Finding Description
`rm()`/`removeiter()` in `upb/hash/common.c` implement open-chained hash-table removal by moving the "next" element of a collision chain into the slot of the removed head element to keep the chain compact [6](#0-5) [1](#0-0) . In `removeiter`, when the head-of-chain entry is deleted during iteration, the algorithm attempts to keep the iterator "index" consistent with the moved entry's provenance by comparing pointers (`move > ent`), but this does not correctly express which entries the iterator has or hasn't visited relative to true position in the backing array, unlike the entries' actual table index. This is confirmed defective by an in-repo test explicitly named `RemoveIterHeadOfChainDemonstratesBug` [2](#0-1) , which sets up a chain (keys 1 and 9 colliding) and shows the iteration/removal sequence fails to reliably keep the remaining key reachable/counted correctly, in the same way `CouncilMember.burn()` fails to keep `tokenId → balances[index]` reachable/correct after removal.

### Impact Explanation
If reachable through code paths that iterate-and-delete over the same `upb_inttable`/`upb_strtable` backing a `upb_Map`, `upb_ExtensionRegistry`, or `upb_DefPool` (e.g., map merge/prune logic in `message/convert.c` / `message/internal/map.h`), this could cause map entries or extension/def entries to be silently skipped, double-visited, or become unreachable — a data-integrity failure comparable to the reported contract's "council member never receives claimable funds" impact, but manifesting as dropped/incorrect map entries in-memory.

### Likelihood Explanation
Low-to-Medium. The defective `removeiter` requires a specific hash-collision chain shape (head-of-chain removal during iteration) to manifest, and this exact pattern is exercised only by a narrow set of internal iterate-and-delete callers. I could not confirm within the available investigation that ordinary bounded binary/ProtoJSON parsing of untrusted input (as opposed to internal map-merge/schema-registration code) reaches this specific function rather than the simpler non-iterating removal path.

### Recommendation
Fix `removeiter()` in `upb/hash/common.c` to track iterator continuation based on the true table index of the moved-from and moved-to entries rather than raw pointer comparison, and add regression coverage exercising `removeiter` reachable from `upb_Map` iteration/merge and `upb_ExtensionRegistry` mutation paths to rule out attacker-observable data loss.

### Proof of Concept
The existing in-repo test is itself the minimal reproduction, demonstrating the defect deterministically: [2](#0-1) 
A follow-up session with full repository access should extend this PoC to confirm (or rule out) whether any public, bounded, unprivileged parse/merge API (e.g., merging two decoded messages containing map fields with colliding keys) drives execution into this exact `removeiter` code path, to fully satisfy the "reachable via public parse API" requirement.

```c
static void removeiter(upb_table* t, intptr_t* iter) {
  intptr_t i = *iter;
  upb_tabent* ent = &t->entries[i];
  upb_tabent* prev = NULL;

  // Linear search, not great.
  upb_tabent* end = &t->entries[upb_table_size(t)];
  for (upb_tabent* e = t->entries; e != end; e++) {
    if (!upb_tabent_isempty(e) && upb_tabent_hasnext(e) &&
        upb_tabent_next(e) == ent) {
      prev = e;
      break;
    }
  }

  if (prev) {
    if (upb_tabent_hasnext(ent)) {
      upb_tabent_setnext(prev, upb_tabent_next(ent));
    } else {
      upb_tabent_clearnext(prev);
    }
  } else {
    // ent is the head of the chain, so we need to move its next element into
    // its slot if there is one.
    if (upb_tabent_hasnext(ent)) {
      upb_tabent* move = upb_tabent_next(ent);
      ent->key = move->key;
      ent->val = move->val;
      if (upb_tabent_hasnext(move)) {
        upb_tabent_setnext(ent, upb_tabent_next(move));
      } else {
        upb_tabent_clearnext(ent);
      }

      // If we moved an element from a higher index to a lower index, then we've
      // moved an element we haven't visited yet into the slot of the one that
      // was just removed; decrement iter so that the iterator visits it.
      if (move > ent) {
        *iter = i - 1;
      }

      ent = move;
    }
  }

  t->count--;
  upb_tabent_clear(ent);
}
```

```text
TEST(IntTableTest, RemoveIterHeadOfChainDemonstratesBug) {
  upb::Arena arena;
  upb_inttable t;
  EXPECT_TRUE(upb_inttable_init(&t, arena.ptr()));

  // Insert two keys that collide on the initial table size of 8 (mask 7).
  // Keys 1 and 9 are used so that they fall into the hash part of the table,
  // forming a chain where 1 is at the head and 9 is its next element.
  EXPECT_TRUE(upb_inttable_insert(&t, 1, upb_value_bool(true), arena.ptr()));
  EXPECT_TRUE(upb_inttable_insert(&t, 9, upb_value_bool(true), arena.ptr()));

  intptr_t iter = UPB_INTTABLE_BEGIN;
  uintptr_t key;
  upb_value val;

  // Iterate through the table. When we encounter 1, remove it via removeiter.
  while (upb_inttable_next(&t, &key, &val, &iter)) {
    if (key == 1) {
      upb_inttable_removeiter(&t, &iter);
    }
  }

  // The remaining element 9 should still be in the table and reachable.
  EXPECT_EQ(upb_inttable_count(&t), 1);
  EXPECT_TRUE(upb_inttable_lookup(&t, 9, &val));
}
```
