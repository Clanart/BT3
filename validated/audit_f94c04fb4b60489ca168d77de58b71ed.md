### Title
Quadratic-complexity DoS in `Offer.to_valid_spend()` sibling computation during offer acceptance - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.to_valid_spend()` builds a `siblings`/`sibling_spends`/`sibling_puzzles`/`sibling_solutions` string for every offered coin of a CAT-family asset by iterating over *all other* offered coins of the same asset for every offered coin, i.e. a nested `for coin in offered_coins: for sibling_coin in offered_coins:` loop. This is the same algorithmic-complexity weakness class as the reported js-yaml `!!omap` issue (CWE-407): work grows O(n²) in the number of coins an untrusted offer-maker puts into one asset side of an `Offer`, and the computation runs synchronously inside the wallet RPC call path that accepts/validates an incoming offer.

### Finding Description
`Offer.to_valid_spend()` iterates the `offered_coins` list for the asset being completed: [1](#0-0) 
For every `coin` in `offered_coins` (outer loop), and only when `asset_id` is truthy (i.e. any CAT/CR-CAT/asset requiring the CAT ring/"siblings" mechanism), the code re-scans the *entire* `offered_coins` list again (inner loop) to build hex-encoded sibling descriptors:
```
for coin in offered_coins:
    if asset_id:
        ...
        for sibling_coin in offered_coins:
            if sibling_coin != coin:
                siblings += ...
                sibling_spends += "0x" + bytes(coin_to_spend_dict[sibling_coin]).hex() + " "
                ...
``` [2](#0-1) 

Each inner-loop iteration does string concatenation and `bytes(...).hex()` encoding of a full `CoinSpend` (puzzle reveal + solution), so the cost per pair is not O(1) — it scales with spend size as well as with `n²` pair count. `offered_coins` for one asset comes directly from `self.get_offered_coins()` / `_get_offered_coins()`, which is derived from the untrusted, attacker-supplied `Offer` bytes/bech32 that a counterparty sends to a wallet user; there is no cap found in `offer.py` or `Offer.from_bytes` on how many coins can be aggregated under one asset id before `to_valid_spend()` is invoked (via `TradeManager` / `wallet_rpc_api.py` "take offer" flow and `chia/wallet/vc_wallet/vc_wallet.py`).

### Impact Explanation
An offer counterparty can construct a malicious offer file that spends/offers a large number of coins for a single CAT (or CR-CAT/DID-restricted CAT, etc.) asset ID. When the victim's wallet attempts to accept/validate that offer (`to_valid_spend()`), the wallet performs O(n²) work with per-pair `bytes(...).hex()` encoding of full coin spends, synchronously blocking the wallet process. Because wallet RPC handling is largely single-threaded per request, this can stall the wallet's ability to process other RPC calls or sync events while the offer is being processed, denying service to the legitimate wallet owner attempting a normal trade action. This matches the CWE-407/"spend-triggered transaction-processing halt" impact category, reachable purely by an unprivileged offer counterparty crafting an oversized offer and sending it to a wallet user — no privileged access or malicious node/peer behavior required.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: any wallet user who is sent an untrusted `.offer` file (a normal, expected interaction pattern in Chia's offer/DEX ecosystem) and attempts to inspect/accept it via `take_offer`/`respond_to_offer` triggers `to_valid_spend()` on attacker-controlled data. However, this could not be fully confirmed against a hard offer-size limit — I was unable to locate an upper bound on the number of coins per asset within an `Offer` object in the indexed code (e.g., in `Offer.from_bytes`, `from_spend_bundle`, or the RPC layer that parses/validates offers before acceptance), so it's possible some other layer (e.g., an overall spend bundle byte-size cap or RPC timeout) partially mitigates the practical severity; this could not be verified with the tools available.

### Recommendation
Precompute the sibling data once per asset (O(n)) instead of recomputing the full sibling set inside the outer per-coin loop (O(n²)): build the `sibling_spends`/`sibling_puzzles`/`sibling_solutions` fragments for the whole offered-coins list a single time, then for each `coin` simply omit its own contribution when assembling its solver input, or restructure using pre-hashed/pre-hexed byte caches keyed by coin so each coin's sibling string is assembled by string-joining precomputed fragments rather than re-serializing every other coin's `CoinSpend` again. Additionally, consider imposing an explicit maximum coin count per asset within an `Offer` before invoking `to_valid_spend()`, so that offers exceeding a sane bound are rejected early rather than accepted for processing.

### Proof of Concept
Not independently executed (no runtime access), but derivable from the code path: construct an `Offer` (via `Offer.from_bytes`) whose `requested_payments`/underlying `_bundle` offers, say, several thousand coins of the same CAT `asset_id` (all routed through `OFFER_MOD`/`SETTLEMENT_PAYMENT`), then call `offer.to_valid_spend()` (as done by `TradeManager`/`wallet_rpc_api.py` when accepting an offer). The nested loop at [1](#0-0) 
performs `n·(n-1)` sibling-string constructions, each re-hex-encoding a full `CoinSpend`, causing wall-clock time to grow quadratically with the number of same-asset offered coins — mirroring the js-yaml PoC's doubling-input/4x-runtime signature, though exact timing figures could not be measured in this environment.
