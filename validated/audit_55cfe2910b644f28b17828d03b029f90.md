This confirms the mechanism: `bitcoin_syncer_spent_utxos` records whichever transaction actually spends the `withdrawal_utxo_txid`/`vout` outpoint on-chain [1](#0-0) , and that recorded `spending_txid` is looked up in the block to find its OP_RETURN and extract the payer operator's xonly pubkey [2](#0-1) . This confirms the attack is real: whichever transaction wins the confirmation race for that input determines `payout_payer_operator_xonly_pk`, independent of whose funds the P2TR key-spend signature actually authorizes.

### Title
Payout OP_RETURN attribution is unauthenticated, allowing reimbursement credit theft via RBF/first-broadcast of a mutated `payout_tx` — (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the withdrawal input with `SIGHASH_SINGLE|ANYONECANPAY`, which only commits to input 0 and output 0 (the user payout), leaving output 2 (the OP_RETURN carrying `operator_xonly_pk`) completely unauthenticated. An attacker can copy the signed input and output 0 into a new transaction, replace the OP_RETURN with an arbitrary or a rival operator's xonly pubkey, and win the confirmation race, causing the bridge to permanently misattribute the reimbursement credit.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk` stored for a withdrawal idx == `xonly_pk` of the operator whose funds paid output 0. This binding is never actually enforced by any signature or on-chain constraint.

`create_payout_txhandler` builds the payout transaction with three outputs — user payout (0), anchor (1), OP_RETURN with `operator_xonly_pk.serialize()` (2) — and only signs input 0 with the user's taproot key-spend signature: [3](#0-2) . Because the sighash type is `SIGHASH_SINGLE|ANYONECANPAY`, the signature commits only to input 0 and the output at the same index (output 0); output 2 (OP_RETURN) and output 1 (anchor) are unauthenticated and can be freely swapped by anyone re-assembling a transaction from the same signed input, as long as it's still a valid witness for input 0.

On the verifier side, `update_finalized_payouts` determines the payer operator purely by inspecting whichever transaction is recorded in `bitcoin_syncer_spent_utxos` as the one that spent the `withdrawal_utxo` outpoint in a confirmed block — see `get_payout_txs_for_withdrawal_utxos`, which joins on `withdrawal_utxo_txid`/`withdrawal_utxo_vout` and returns `bsu.spending_txid` [4](#0-3) . It then reads that confirmed transaction's first OP_RETURN, parses it as an xonly pubkey with no signature check against it, and stores it as `payout_payer_operator_xonly_pk` [5](#0-4) , [6](#0-5) .

Exploit flow:
1. Honest operator A broadcasts `payout_tx_A` spending `input_utxo` (the registered withdrawal UTXO) with `user_sig`, output0=user payout, output2=OP_RETURN(A's xonly_pk).
2. Before confirmation, attacker constructs `payout_tx_evil`: same input 0 + witness (valid `user_sig`, unmodified since ANYONECANPAY|SINGLE doesn't cover other inputs/outputs), same output 0, but output 2 replaced with either garbage bytes or another honest operator B's real xonly_pk (someone who never funded anything).
3. Attacker broadcasts `payout_tx_evil` with a higher fee (RBF or race), and it confirms instead of `payout_tx_A`.
4. `bitcoin_syncer_spent_utxos` records `payout_tx_evil`'s txid as the one that spent the withdrawal outpoint; `update_finalized_payouts` reads OP_RETURN from `payout_tx_evil` and stores B's (or nobody's) xonly_pk as `payout_payer_operator_xonly_pk`.
5. Operator A, who actually funded the user's payout, is never credited: `get_first_unhandled_payout_by_operator_xonly_pk` will never surface this withdrawal for A [7](#0-6) .
6. When A later sends a `Kickoff` to claim reimbursement, `is_kickoff_malicious` compares `kickoff_data.operator_xonly_pk` (A) against the DB's `payout_payer_operator_xonly_pk` (B or None) and flags A's honest kickoff as malicious [8](#0-7) , leading verifiers to sign a Disprove that burns A's collateral.

Existing guards do not stop this: there's no check anywhere in this path that the OP_RETURN pubkey corresponds to a signature or to a specific spend authorized by the operator; the only "authentication" of the payout is the user's own signature over output 0, which is orthogonal to who is credited for funding it.

### Impact Explanation
This is Critical: an honest operator who fronted a withdrawal can be permanently denied reimbursement (their payout is never found by `get_first_unhandled_payout_by_operator_xonly_pk`), and if they later attempt to claim it via a `Kickoff`, `is_kickoff_malicious` will flag it as malicious, resulting in their collateral being burned via Disprove. The attack is repeatable for every future withdrawal race and does not require any privileged role — any transaction-broadcasting attacker with fee funds can attempt it (subject to winning the mempool/RBF race against the honest operator's broadcast).

### Likelihood Explanation
Preconditions: a withdrawal must be registered via Citrea's `withdraw()`, an operator must have signed and be about to broadcast the corresponding `payout_tx`, and the attacker must win the propagation/RBF race by paying a higher fee on the OP_RETURN-mutated clone. This is feasible for any unprivileged network participant with modest BTC for fees; no key compromise or special access is required. The race condition nature (mempool visibility, fee bumping) makes it probabilistic per attempt, but repeatable indefinitely across withdrawals and operators, making it a persistent systemic risk rather than a one-off.

### Recommendation
Bind the OP_RETURN operator attribution to the payout authorization. Options: (1) change the payout signature scope to cover the OP_RETURN output (e.g. `SIGHASH_ALL` for a decoupled operator-identity input/output, or a `SIGHASH_SINGLE|ANYONECANPAY` per-output commitment covering output 2 as well by reordering so OP_RETURN is output 0's paired index and payout output ends up elsewhere), (2) require operators to additionally sign a commitment message (via aggregator/verifier off-chain protocol) binding `withdrawal_index -> operator_xonly_pk` before crediting, verified independently of the mutable OP_RETURN, or (3) have verifiers only accept the OP_RETURN-derived operator attribution if it was pre-registered by that operator with the aggregator (e.g., an operator "intent to pay" record) prior to seeing it confirmed, rejecting/flagging first-seen mismatches.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
