## Analysis

The reported Vader bug class is: **a "credited" identity is derived from an unauthenticated slot rather than the party that actually funded/executed the transfer**. The closest analog in Clementine is how operator reimbursement is attributed for a `Payout` transaction.

### Root cause

`create_payout_txhandler` builds a `Payout` transaction with the withdrawal input/output, an anchor output, and a third **OP_RETURN output carrying the fronting operator's x-only pubkey** — this pubkey is plain data, not a signature over anything: [1](#0-0) 

The only signature checked on this transaction is the withdrawing user's signature over the payout, and it explicitly must use `SinglePlusAnyoneCanPay` (SIGHASH_SINGLE|ANYONECANPAY): [2](#0-1) 

SIGHASH_SINGLE|ANYONECANPAY only commits the signer to input `0` and output `0` (the withdrawal input/output pair). It does **not** cover the OP_RETURN output (index 2) or any additional funding inputs added later via `fund_raw_transaction`/`sign_raw_transaction_with_wallet`: [3](#0-2) 

Because of this, the OP_RETURN operator-attribution field is entirely unauthenticated by the on-chain protocol: whoever ends up broadcasting (and funding) the confirmed payout transaction can put **any** x-only pubkey into that OP_RETURN — including a pubkey they don't control.

That unauthenticated field is then trusted as ground truth for attributing "who paid" the withdrawal. `update_finalized_payouts` parses the OP_RETURN and stores it as `payout_payer_operator_xonly_pk` with no further verification that the named operator actually signed/funded any part of the transaction: [4](#0-3) 

This value then drives two critical automated flows:
1. `PayoutCheckerTask` looks up **its own operator's** unhandled payouts purely by this DB column and automatically triggers `handle_finalized_payout` → kickoff/reimbursement: [5](#0-4) [6](#0-5) 

2. `is_kickoff_malicious` uses the same unauthenticated field as the sole check of "does the kickoff sender match who actually paid": [7](#0-6) 

### Title
Unauthenticated OP_RETURN operator attribution in the Payout transaction allows misattributed reimbursement credit - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `Payout` transaction's OP_RETURN output, which names the operator to be credited/reimbursed for fronting a withdrawal, is not covered by the withdrawing user's `SinglePlusAnyoneCanPay` signature. Any party able to construct and confirm a valid payout transaction (satisfying only the signed input/output pair) can insert an arbitrary operator x-only pubkey into that OP_RETURN. The verifier/operator software trusts this field as the authoritative record of "who paid," breaking the binding: `operator credited == operator who actually funded the payout`.

### Finding Description
`create_payout_txhandler` places `operator_xonly_pk` in a plain OP_RETURN output with no signature binding it to anything [1](#0-0) . The user's authorizing signature over the payout transaction is required to use `SinglePlusAnyoneCanPay` [8](#0-7) , which by BIP-341 sighash semantics commits only to input 0 and the corresponding output 0 — never to the OP_RETURN output or to any additional inputs later attached by `fund_raw_transaction`/`sign_raw_transaction_with_wallet` [3](#0-2) .

Consequently, the equality the protocol needs — `payout_payer_operator_xonly_pk (recorded from OP_RETURN) == xonly_pk of the entity whose funds/signature actually paid the user` — is not enforced anywhere on-chain. `update_finalized_payouts` parses this untrusted field directly from the mined transaction and persists it verbatim [4](#0-3) . Downstream, this same value is used (a) to select "my unhandled payouts" for automatic reimbursement in `PayoutCheckerTask` [5](#0-4)  and (b) to decide whether a kickoff sender is honest in `is_kickoff_malicious` [7](#0-6) .

An unprivileged party who can reconstruct or intercept the withdrawal's `SinglePlusAnyoneCanPay` signature (transmitted "off-chain" to operators per the doc comment on `withdraw`) can build a competing payout transaction that reuses the signed input/output pair, supplies their own funding inputs, and stamps an arbitrary operator's x-only pubkey (rather than their own) into the OP_RETURN before broadcasting/confirming it.

### Impact Explanation
- If the attacker embeds a bogus/garbage or malformed pubkey, `payout_payer_operator_xonly_pk` becomes `None`; `is_kickoff_malicious` then unconditionally treats the eventual honest operator's kickoff as malicious ("No operator xonly pk found ... assuming malicious"), which can lead to that honest operator's kickoff/collateral being challenged and burned for a legitimate reimbursement it should have received — matching the Critical class "an honest operator's collateral burned" / "an honest operator permanently unable to be reimbursed."
- If the attacker names a specific *other* real operator's xonly pubkey, that operator's own `PayoutCheckerTask` will autonomously detect an "unhandled payout" it never funded and trigger `handle_finalized_payout`/kickoff for reimbursement it did not actually front, matching the Critical class "an operator reimbursed for a payout it never funded."

### Likelihood Explanation
Exploitation requires only the ability to construct and get mined a standard Bitcoin transaction that reuses the user's `SinglePlusAnyoneCanPay`-signed input/output — no verifier, operator, or aggregator privilege is needed, and no cryptographic secret beyond generic Bitcoin wallet capability to fund the extra inputs. The main practical constraint is timing/fee-racing to get the crafted transaction confirmed instead of (or before) the intended operator's version, and access to the off-chain-transmitted user signature, both of which are realistic given the documented "signature given to operators off-chain" flow.

### Recommendation
Cryptographically bind the fronting operator's identity to the payout transaction so it cannot be altered by a third party, e.g. commit to the operator xonly pubkey inside the sighash the user signs (extend sighash coverage, or require the operator's own signature over the whole transaction including the OP_RETURN and the additional funding inputs), rather than trusting an unauthenticated OP_RETURN byte string as the source of truth for reimbursement attribution.

### Proof of Concept
1. Wait for (or intercept) the off-chain `(in_signature, in_outpoint, out_script_pubkey, out_amount)` tuple that a user sent intending operator A to front their withdrawal, as consumed in `Operator::withdraw` [9](#0-8) .
2. Independently call `create_payout_txhandler` with the same `input_utxo`/`output_txout`/`user_sig`, but pass a different `operator_xonly_pk` (e.g., an arbitrary or a targeted honest operator B's pubkey) [1](#0-0) .
3. Fund the extra inputs from the attacker's own wallet, sign, and broadcast this transaction ahead of / instead of operator A's version (the ANYONECANPAY signature remains valid because it only commits to input/output 0).
4. Once confirmed, `update_finalized_payouts` records `payout_payer_operator_xonly_pk` = the attacker-chosen value [4](#0-3) .
5. Observe operator B's `PayoutCheckerTask` pick up this "unhandled payout" via `get_first_unhandled_payout_by_operator_xonly_pk` and automatically initiate reimbursement it never funded [5](#0-4) , or observe operator A's later legitimate kickoff for this deposit being flagged malicious by `is_kickoff_malicious` due to the mismatched/missing attribution [7](#0-6) .

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
