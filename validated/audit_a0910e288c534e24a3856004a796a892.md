### Title
Unbounded attacker-controlled length prefix in `SchnorrAggregate::read` enables blocking/CPU-exhaustion DoS analogous to slowloris - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report describes a per-operation timeout with no bound on total response duration, letting a malicious peer keep all workers busy indefinitely (slowloris). Serai's in-scope code contains the same structural flaw: `SchnorrAggregate::<C>::read` trusts an attacker-supplied `u32` element count and then enters a loop performing a full group-element deserialization (`C::read_G`) per element, with no upper bound, no aggregate size limit, and no deadline. An unprivileged party who can cause these bytes to be read (the `read`/`read_G`/`read_F` family is the intended ingestion path for untrusted preprocess/signature material) can keep the deserializer — and hence the calling worker — occupied for as long as they choose to sustain input.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, lines 77–88:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
        Rs.push(C::read_G(reader)?);
    }
    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

Three properties combine into the vulnerability:

1. **Attacker-controlled iteration count**: `len` is a raw `u32` taken directly from the wire with no maximum. A 4-byte prefix can claim up to ~4.3 billion `R` points.
2. **No bound on total work or duration**: `read_exact` blocks until data arrives or the reader errors. On any `Read` backed by a stream (the exact shape the external CVE exploits — per-read blocking with no total timeout), the attacker dribbles bytes and holds the loop open indefinitely, the direct analog of resetting the per-read timeout in the Mastodon bug. There is no chunking, no deadline, and no `Vec::with_capacity` sanity bound.
3. **CPU amplification per byte**: each iteration runs `C::read_G`, which performs full point decoding and validity checks (non-canonical/identity/torsion handling depending on the ciphersuite — e.g., `dalek-ff-group` / `ed448` / `schnorrkel` in-scope curves). Roughly 32 bytes of input buys one complete elliptic-curve decompression-plus-validation, so the attacker converts a small amount of input into unbounded verifier-side computation.

The same read-then-loop pattern without caps appears elsewhere in scope (e.g., length-prefixed loops in `crypto/dkg` reads and `ThresholdKeys::read`'s `1 ..= n` loop over `read_G` at `crypto/dkg/src/lib.rs:620-623`, bounded only by `u16`), but `SchnorrAggregate::read` is the most severe because the count field is a full `u32` with zero validation.

### Impact Explanation
An unprivileged party able to feed bytes into `SchnorrAggregate::read` (which is exactly the untrusted-bytes-into-`read` ingestion surface the FROST signing pipeline exposes for aggregate signature material) can:

- Pin a worker inside a blocking `read_exact` loop for an arbitrary duration by trickling bytes — the precise worker-starvation mechanism of the Mastodon slowloris CVE.
- Force up to 2^32 group deserializations from a tiny claimed-length header combined with a sustained stream, exhausting CPU.
- When replicated across connections/requests, keep all signing/verification workers busy, making the node unresponsive — matching the High-severity availability impact of the reference advisory.

### Likelihood Explanation
The function takes `R: Read` generically and performs no size gating, so any caller that wires it to a transport-backed reader inherits the exposure directly. The write side (`write`, lines 93–104) proves the format is attacker-mirrorable: the `u32` length is the only metadata needed to trigger the loop. No collusion, key material, or privileged position is required — only the ability to submit bytes to a deserialization path, which is the minimum capability of a protocol participant.

### Recommendation
- Enforce a hard upper bound on the element count before the loop (e.g., reject `len` exceeding a protocol-defined maximum such as the number of signatures an aggregate may legitimately contain), mirroring the `MAX_LIBP2P_REQRES_MESSAGE_SIZE` guard already present in `coordinator/src/p2p.rs:264`.
- Validate that the claimed count is consistent with the remaining input length where determinable, rather than discovering underflow element-by-element via `read_G` failures.
- Callers streaming from a network should wrap the reader with an overall deadline/total-byte budget, not just per-read timeouts.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;

// Claim ~4.3 billion R points, then provide a slow/truncated stream.
let mut malicious = vec![0xFF, 0xFF, 0xFF, 0xFF]; // u32::MAX element count
// Append any partial/trickled point data; each 32 bytes triggers a full
// decompression + validation in C::read_G, and read_exact blocks for more.
let res: io::Result<SchnorrAggregate<dalek_ff_group::Ristretto>> =
    SchnorrAggregate::read(&mut malicious.as_slice());
// On a stream-backed reader the loop never terminates until the attacker
// stops supplying bytes; on a slice it performs len/32 decompressions.
```

Note on confidence: the deserialization flaw at `aggregate.rs:77-88` is verified verbatim. Whether a given production caller connects it to a streaming `Read` is an integration property; the unbounded-count CPU amplification holds regardless of reader type, while the indefinite-blocking (pure slowloris) variant requires a blocking stream reader.
