### Title
Deterministic nonce reuse via persisted `CachedPreprocess` seed enables share/key recovery across repeated FROST signing sessions - (File: crypto/frost/src/sign.rs, coordinator/src/tributary/signing_protocol.rs)

### Summary
FROST's `AlgorithmSignMachine::from_cache` regenerates nonces deterministically from a caller-supplied `CachedPreprocess` seed via `ChaCha20Rng::from_seed`. The coordinator stores this seed per signing context and reuses it on every signing attempt for that context, so each retry emits the identical nonce pair `(d, e)` (and identical commitments). Repeated shares produced under the same reused nonces form a linear system that lets an observer recover a victim participant's interpolated secret share, and eventually the group key.

### Finding Description
`AlgorithmMachine::seeded_preprocess` seeds a `ChaCha20Rng` with `*seed.0` and feeds it to `Commitments::new`, which calls `Curve::random_nonce`. `random_nonce` draws 32 bytes from that RNG and computes `hash_to_F(b"nonce", seed || secret_share)` — fully deterministic in `(seed, secret_share)` (crypto/frost/src/sign.rs:127-132, crypto/frost/src/curve/mod.rs:94-121).

`from_cache` simply re-runs `seeded_preprocess` on the stored seed (crypto/frost/src/sign.rs:268-274), so every invocation with the same cache produces identical `d`, `e` and identical published commitments `(D, E)`.

In the coordinator, `preprocess_internal` writes the cache only if `CachedPreprocesses::get` is `None`, then always loads and decrypts the stored seed for every call (coordinator/src/tributary/signing_protocol.rs:123-145). `share_internal` calls `preprocess_internal` each time a share is needed (line 156), so a retry of signing under the same `context` reuses the same nonces. `sign` then computes the share as `s = d + e·ρ_i + c·λ_i·x_i` (crypto/frost/src/sign.rs:385-398), where `ρ_i` and `c` are public functions of the transcript, message, and signing set — all observable in the preprocess/share messages.

There is no "used" marker, no deletion of `CachedPreprocesses` after `share_internal`, and no check in `sign` that the preprocess was consumed, so nothing prevents reuse of the seed across attempts.

### Impact Explanation
Each share a participant emits is `s_j = d + e·ρ_j + c_j·(λ_j·x)`. The unknowns are `d`, `e`, and the (fixed for a given included-set) product `λx`. Because `d` and `e` are identical across sessions, three signing sessions under the same cached seed with distinct `(ρ_j, c_j)` yield three independent linear equations in three unknowns. Solving recovers `λx`, i.e. the participant's interpolated secret share. Collecting `t` such shares (or combining with the victim's share over varying sets) recovers the group private key — complete confidentiality loss and the ability to forge threshold signatures for arbitrary messages. Even a single recovered interpolated share is a secret leak for the value that was supposed to remain threshold-protected.

### Likelihood Explanation
Any unprivileged party who can cause a message to be signed (a valid protocol input — transactions/messages the group is asked to sign) triggers a `share_internal` call. If the coordinator retries a failed signing attempt, or more than one message is ever signed under the same `context`, the same cached seed is reused automatically and deterministically — no malicious validator is required; honest nodes leak their shares by design. Observation requires seeing preprocesses and shares, which are protocol messages exchanged in the open among the signing set (and in the tributary case, posted publicly). Likelihood is bounded by whether the same `context` is ever signed more than once; the code makes reuse the default path (`from_cache`), and nothing enforces single-use.

### Recommendation
- Treat a `CachedPreprocess` as single-use: after `share_internal` produces a share, delete/rotate the `CachedPreprocesses` entry for that context so a subsequent attempt generates a fresh seed.
- Alternatively, derive nonces bound to the full session: mix the seed with the sorted `included` set and `hash_msg(msg)` inside the nonce-generation path so retries produce session-unique `(d, e)`, or generate nonces from fresh RNG and store only commitments.
- At minimum, add a consumed/used flag to `CachedPreprocesses` and refuse to sign twice with the same seed.

### Proof of Concept
1. Fix a threshold participant `i` with secret share `x_i` whose coordinator holds a `CachedPreprocesses` entry for context `ctx`.
2. Cause three signatures under `ctx` for messages `m1`, `m2`, `m3` (e.g., repeated signing attempts). Each `share_internal` call runs `preprocess_internal`, which loads the same cached seed, so `ChaCha20Rng::from_seed` produces the same bytes and `Commitments::new` yields the same `(d, e)` and the same published `(D, E)`.
3. From the wire, record the victim's three shares `s_j` and compute, from the public transcripts, `ρ_j = hash_binding_factor(participant ‖ rho_transcript)` and `c_j = HRAM(R_j, group_key, m_j)` where `R_j = D + ρ_j·E` summed over the set.
4. Solve the linear system over the scalar field:
   `s_j = d + e·ρ_j + X·c_j` for `j ∈ {1,2,3}`, unknowns `(d, e, X)` where `X = λ·x_i` (λ constant if the included set is constant).
5. `X` is the victim's interpolated secret share. Repeating for `t` victims (or across varying included sets to peel `λ`) yields enough shares to reconstruct the group key via Lagrange interpolation at 0, producing valid signatures on arbitrary messages.

Key code points: `seeded_preprocess` deterministic RNG seeding (crypto/frost/src/sign.rs:127-141), `from_cache` unconditional re-derivation (sign.rs:268-274), share equation `actual = base + actual·ρ` then `sign_share` (sign.rs:385-398, crypto/frost/src/algorithm.rs:201-211), and coordinator cache reuse without invalidation (coordinator/src/tributary/signing_protocol.rs:123-145).

Caveat: I could not fully verify whether the coordinator ever invokes `share_internal` more than once per distinct `context` value (e.g., on retries); the finding holds wherever a context is signed repeatedly, and the lack of any single-use guard makes the reuse structural rather than incidental.
