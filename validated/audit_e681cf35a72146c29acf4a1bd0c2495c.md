Based on the investigation, the closest structural analog to the reported bug class — "a default/hardening behavior introduced upstream that projects silently re-enable or bypass, producing a security regression that only manifests when interacting with untrusted external content" — is Desktop's handling of the `allowFileProtocol` flag that re-enables Git's `protocol.file.allow` for submodule operations.

### Title
Submodule updates can re-enable `protocol.file.allow=always`, reintroducing the local-file-read protection Git disabled by default - (File: app/src/lib/git/submodule.ts)

### Summary
Git 2.38.1 disabled the `file://` transport for submodules by default (as a fix for CVE-2022-39253) because a malicious repository can embed a submodule whose URL points at an arbitrary local filesystem path, letting `git submodule update --init --recursive` pull the contents of another local directory (potentially containing sensitive files, via hardlinks/relative paths) into the working tree under attacker control. Desktop's `updateSubmodulesAfterOperation` explicitly overrides this hardening by passing `-c protocol.file.allow=always` whenever it is invoked with `allowFileProtocol = true`.

### Finding Description
`updateSubmodulesAfterOperation` builds its `git submodule update --init --recursive` arguments as: [1](#0-0) 
When `allowFileProtocol` is `true`, the `-c protocol.file.allow=always` flag is unconditionally added, which is exactly the setting Git itself defaults to `user` (deny for recursive submodule fetches) as a security fix. `checkoutBranch` and `checkoutCommit` both thread an `allowFileProtocol: boolean = false` parameter straight through to this function: [2](#0-1) [3](#0-2) 
Because this parameter defaults to `false` but can be set `true` by any caller, the safety of this mechanism depends entirely on every call site correctly scoping when `allowFileProtocol=true` is appropriate (e.g., only for repositories the user already trusts and only for submodule URLs that were already vetted). If a caller enables it broadly (e.g., to support local/dev workflows) it applies globally to `git submodule update`, meaning any submodule declared in `.gitmodules` of a branch/commit being checked out — including one introduced by a remote branch or a commit fetched from an untrusted remote — will be honored even if it uses a `file://` URL pointing outside the repository.

### Impact Explanation
If `allowFileProtocol` is enabled for a checkout of attacker-influenced content (e.g., checking out a branch/commit fetched from a remote or PR the user did not fully control), a `.gitmodules` entry with a `file://` URL pointing to an arbitrary path on the local disk (or a path reachable via symlink/hardlink tricks) can be cloned into the working directory. This is a direct file-read-outside-the-repo primitive — the exact vulnerability class Git's own default hardening (`protocol.file.allow=user`) is designed to stop. The desktop-controlled override defeats that guard for any commit/branch checkout that flows through this code path with `allowFileProtocol=true`.

### Likelihood Explanation
The `false` default parameter is a safe fallback, but the fact that `checkout.ts` exposes and forwards this override at all means whatever UI/dispatcher logic passes `true` (not captured in the excerpts reviewed) determines the actual exposure. I was not able to fully trace every caller of `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` within the available iterations, so I cannot confirm the exact triggering condition (e.g., whether it's gated behind "only local/file-based remotes" or a broader feature flag). This is a material gap — confirming likelihood requires locating all call sites that pass `true` for this flag, which should be done in a full codebase review (e.g., via a Devin session with complete file access) since the ask-mode index may not surface every reference.

### Recommendation
Any code path that sets `allowFileProtocol = true` should independently re-validate that the submodule URLs actually being updated are constrained to same-repository/trusted-remote contexts before allowing `protocol.file.allow=always`, rather than relying on caller intent. Ideally, the override should be narrowed to inspect the specific submodule URL(s) in the target commit rather than blanket-enabling the flag for the whole `submodule update` invocation.

### Proof of Concept
Conceptual PoC (exact trigger site not confirmed): a repository/branch is checked out via `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`; its `.gitmodules` contains `url = file:///Users/victim/some/other/local/repo`. Because `protocol.file.allow=always` is passed, `git submodule update --init --recursive` will accept the local-file transport and clone that path into the working directory, exfiltrating file contents that would otherwise have been blocked by Git's default `protocol.file.allow=user` restriction for submodules.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
