### Title
Address squatting on the deterministic IBC-voucher ERC20 address turns a failed dynamic-precompile registration into an ack-vs-state mismatch, allowing double-crediting of IBC value - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/token_pairs.go`)

### Summary
`x/erc20`'s ICS20 middleware (`x/erc20/ibc_middleware.go`) runs the standard `transfer` module's `OnRecvPacket` first (which credits the receiver's bank balance and returns a **success** acknowledgement), and only afterward calls `k.keeper.OnRecvPacket` to auto-register/convert the coin into its ERC-20 representation. For a brand-new `ibc/...` denom, that keeper call invokes `RegisterERC20Extension` → `CreateNewTokenPair` → `NewTokenPairSTRv2`, which derives the ERC-20 contract address **deterministically** from the IBC denom hash via `utils.GetIBCDenomAddress`. If an account already has code at that deterministic address, `CreateNewTokenPair` returns `ErrTokenPairAlreadyExists`, and `OnRecvPacket`'s "Case 1" branch converts the *already-successful* acknowledgement into an **error acknowledgement**. ### Finding Description
This is the same bug class as the report: an ID/registration-slot ("questID"/token-pair address) can be pre-empted by an unprivileged actor because a downstream consumer of that ID (`createQuest`/`RegisterERC20Extension`) assumes it is unclaimed, but nothing prevents an outside party from claiming it first through an ordinary, permissionless transaction.

Root cause chain:
1. `GetIBCDenomAddress` derives the ERC-20 address purely from `sha256/hash(ibcDenomTraceHash)` (the last 20 bytes of the denom hash). This is fully predictable off-chain by anyone who knows the source chain/channel/base-denom triple that will be used for a future transfer (channel IDs are public IBC metadata, and denom traces for popular assets are guessable/enumerable). [5](#0-4) 
2. Any unprivileged EVM user can send an ordinary `CREATE` transaction that happens to land at that exact address (bruteforcing nonce/sender via CREATE2 factories, or simply deploying with an EOA/nonce combination that yields the target address — deterministic CREATE addresses are a function of `sender+nonce`, and CREATE2 addresses are a function of `sender+salt+initcodehash`, both fully attacker-controlled) before the honest IBC transfer for that denom ever arrives.
3. When the real transfer later arrives, `x/erc20`'s middleware has already let `transfer.OnRecvPacket` execute and **credit the receiver's bank balance** with the voucher coins (the underlying successful `ack`). [6](#0-5) 
4. `k.keeper.OnRecvPacket` then attempts registration via `RegisterERC20Extension` → `CreateNewTokenPair`, which finds the squatted contract code at the deterministic address and returns `ErrTokenPairAlreadyExists`. [7](#0-6) 
5. `OnRecvPacket`'s Case 1 branch converts this into `channeltypes.NewErrorAcknowledgement(err)` and returns it as the packet's final acknowledgement. [8](#0-7) 
6. There is no cache-context/branch-and-discard mechanism wrapping steps 3–5 (no `CacheContext`/`Write()` pattern present in `x/erc20/ibc_middleware.go` or `x/erc20/keeper/ibc_callbacks.go`) — the bank credit from step 3 is committed to the destination chain's state regardless of the final acknowledgement outcome.
7. The counterparty chain (source of the transfer) receives this error acknowledgement and, per standard ICS-20 semantics, unescrows/refunds the sender's original tokens there.

Net effect: the same value now exists twice — once refunded on the source chain, and once already credited (irreversibly, since the ack override doesn't roll back the bank transfer) as bank coins on the destination chain (Cosmos EVM chain) to the receiver, who additionally is not blocked from spending/transferring those coins even though the registration path is permanently broken for that specific IBC denom (every future retry of `RegisterERC20Extension` for that denom will hit the same `ErrTokenPairAlreadyExists`, permanently preventing conversion to the ERC-20 representation but not preventing the bank coin from being freely used/transferred elsewhere).

### Impact Explanation
This satisfies "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances ... or IBC escrows" — an unprivileged attacker can, at zero cost beyond deploying a contract to a predictable address, cause the same IBC-transferred value to be simultaneously refunded on the source chain and retained as spendable bank balance on the Cosmos EVM chain, i.e., a duplication of user value across two chains connected via IBC escrow accounting. This is exactly the "questID gets consumed early, later legitimate registration silently breaks, but by then damage is irreversible" pattern from the source report, but here the broken invariant is bank-balance vs. ICS-20 escrow consistency rather than a DoS on quest creation.

### Likelihood Explanation
Rated Medium-likelihood in terms of attacker effort (must precompute/deploy to a specific address before a target IBC transfer of a specific denom trace occurs — feasible via CREATE2 factories or vanity-address grinding, and channel/denom-trace metadata is public), but the report is included because the *impact*, if triggered, is Critical (double-spend of IBC value) and the root cause (deterministic, attacker-guessable, and squattable ID/address feeding into an unconditional non-atomic ack-and-state-write flow) is a direct structural analog of the reported `addQuest`/`questID` collision bug. I could not fully verify from the indexed files whether ibc-go's core packet-handling wraps the entire `OnRecvPacket` call chain (including `x/erc20`'s wrapper) in an automatically-discarded cache context on any downstream error — if such a wrapping exists at the ibc-go core level (outside this repo's indexed code), the double-credit would not persist and this finding would be invalidated. This should be verified against the actual `ibc-go` core `RecvPacket` handler behavior, which is outside this repository.

### Recommendation
- Wrap the `k.keeper.OnRecvPacket` post-processing (registration/conversion) in a `ctx.CacheContext()` branch and only `Write()` it back when the acknowledgement remains successful; if `RegisterERC20Extension` fails, discard the branch and return the **original successful ack with the bank token retained** exactly once (which matches the doc comment's stated intent: "If conversion fails, then the user will receive the bank token instead"), rather than overriding to an error ack after the underlying transfer already committed.
- Alternatively/additionally, do not fail with `ErrTokenPairAlreadyExists` when the colliding address is not itself a legitimate previously-registered pair; instead, detect address squatting and either salt the derivation function to include chain-specific/private entropy not predictable pre-transfer, or fall back to a bank-only representation without erroring the packet.
- Audit all other call sites that can flip an already-applied, successful state change into an error acknowledgement after external effects have occurred (native ERC20 case, minting-enabled checks, etc.) for the same non-atomicity issue.

### Proof of Concept
1. Attacker computes the IBC denom trace that will be used for a future transfer of asset X from chain B to this chain over channel-N (public information — channel ids and typical base denoms are known in advance, e.g. before a new IBC connection goes live or before a known asset gets bridged for the first time).
2. Attacker computes `ibcDenom = ibc/hash(trace)` and `targetAddr = utils.GetIBCDenomAddress(ibcDenom)` (last 20 bytes of the hash) — same function used on-chain in `x/erc20/types/token_pair.go` `NewTokenPairSTRv2`. [4](#0-3) 
3. Attacker deploys arbitrary bytecode to `targetAddr` using a CREATE2 factory (grinding salt) or a CREATE with a controlled nonce, an ordinary permissionless EVM transaction.
4. A legitimate IBC transfer of asset X arrives; `transfer.OnRecvPacket` credits the receiver's bank balance with the `ibc/...` voucher and returns a success ack. [9](#0-8) 
5. `Erc20Keeper.OnRecvPacket` calls `RegisterERC20Extension(ctx, ibcDenom)` → `CreateNewTokenPair` finds code at `targetAddr` and returns `ErrTokenPairAlreadyExists`. [7](#0-6) 
6. `OnRecvPacket` converts this into an error acknowledgement and returns it, while the bank credit from step 4 remains committed on this chain. [10](#0-9) 
7. Source chain B, upon relaying/observing the error acknowledgement, unescrows/refunds the sender's original tokens.
8. Result: value exists both as a refund on chain B and as a spendable bank balance credited to the receiver on the Cosmos EVM chain — a duplication of the transferred amount.

// CreateNewTokenPair creates a new token pair and stores it in the state.
func (k Keeper) CreateNewTokenPair(ctx sdk.Context, denom string) (types.TokenPair, error) {
	pair, err := types.NewTokenPairSTRv2(denom)
	if err != nil {
		return types.TokenPair{}, err
	}
	account := k.evmKeeper.GetAccount(ctx, pair.GetERC20Contract())
	if account != nil && account.HasCodeHash() {
		return types.TokenPair{}, errorsmod.Wrapf(types.ErrTokenPairAlreadyExists, "token already exists for token %s", pair.Erc20Address)
	}
	err = k.SetToken(ctx, pair)
	if err != nil {
		return types.TokenPair{}, err
	}
	return pair, nil
}

// NewTokenPairSTRv2 creates a new TokenPair instance in the context of the
// Single Token Representation v2.
//
// It derives the ERC-20 address from the hex suffix of the IBC denomination
// (e.g. ibc/DF63978F803A2E27CA5CC9B7631654CCF0BBC788B3B7F0A10200508E37C70992).
func NewTokenPairSTRv2(denom string) (TokenPair, error) {
	address, err := utils.GetIBCDenomAddress(denom)
	if err != nil {
		return TokenPair{}, err
	}
	return TokenPair{
		Erc20Address:  address.String(),
		Denom:         denom,
		Enabled:       true,
		ContractOwner: OWNER_MODULE,
	}, nil
}

// GetIBCDenomAddress returns the address from the hash of the ICS20's Denom Path.
func GetIBCDenomAddress(denom string) (common.Address, error) {
	if !strings.HasPrefix(denom, "ibc/") {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s does not have 'ibc/' prefix", denom)
	}

	if len(denom) < 5 || strings.TrimSpace(denom[4:]) == "" {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s is not a valid IBC voucher hash", denom)
	}

	// Get the address from the hash of the ICS20's Denom Path
	bz, err := ibctransfertypes.ParseHexHash(denom[4:])
	if err != nil {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrap(err.Error())
	}

	return common.BytesToAddress(bz), nil
}
