### Title
Automatic `origin` remote URL rewrite based on repo owner/name match, with no ownership-continuity check, enables silent remote hijack ("repo-jacking") — (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently rewrites the local `origin` remote to whatever `clone_url` the GitHub API returns for the repository Desktop believes is associated with the working copy, gated only by string-based owner/name matching and protocol equality — never by a check that the API-returned repository is still the *same* underlying repository the user originally connected to.

### Finding Description
`updateRemoteUrl` compares the locally configured remote URL to the API's `clone_url` using `urlMatchesRemote`, which only compares `hostname` + case-insensitive `owner`/`name` strings parsed out of the URL [1](#0-0) . If the protocol matches and the previously cached `gitHubRepository.cloneURL` still matches the local remote (`remoteUrlUnchanged`), but the freshly-fetched API `clone_url` differs from the local remote, Desktop calls `gitStore.setRemoteURL` to overwrite `origin` automatically, with no user prompt: [2](#0-1) .

This logic exists to auto-follow legitimate GitHub repo renames, but the identity check is purely nominal (owner/name string equality), not an ownership-continuity or repo-ID check. GitHub repository names can be freed and re-registered ("repo-jacking"): if the repository the user is tracking is deleted or its owner account/org is renamed away, and an attacker re-creates a repository under the now-available `owner/name`, the next periodic API refresh Desktop performs will return an `IAPIRepository` object whose `clone_url` points at the attacker's newly-created repository. Because `urlMatchesRemote`/`urlsMatch` only ever compare `hostname/owner/name` strings [3](#0-2)  and never a stable repository ID, this attacker-controlled object passes the same "match" that a legitimate rename would, and `updateRemoteUrl` silently repoints `origin` at it.

This is the same class of bug as the report: an action (rewriting the trust anchor for all future fetch/push) is performed using externally-supplied data (the GitHub API's `clone_url`) without any check that the data still refers to the same real-world target the user originally established a relationship with — analogous to executing a swap using a stale price with no deadline/slippage guard.

### Impact Explanation
Once `origin` is silently repointed, all subsequent Desktop-driven `git push` operations for that repository — including the user's code and, depending on remote scheme, embedded credentials in HTTPS URLs — go to the attacker-controlled repository. This is a "silent corruption of what the user pushes" scenario: the user believes they are pushing to their known project, but the destination has been changed without their awareness or consent. It could also be used to redirect `fetch`, causing local history to fetch attacker refs merged into the user's assumptions about upstream state.

### Likelihood Explanation
Requires the tracked repository/owner name to become available for re-registration (deletion, rename, or transfer away) and an attacker to claim it before Desktop's next background API refresh — a known, previously-exploited real-world technique ("repo-jacking"/"repojacking"). No local access, admin rights, or social engineering of the victim is needed beyond the victim having previously used Desktop with that repository; the change happens automatically in the background.

### Recommendation
Do not automatically rewrite `origin` based solely on owner/name string matching. At minimum:
- Require the GitHub repository's immutable numeric `id` (not owner/name) to match between the cached `GitHubRepository` and the freshly fetched `IAPIRepository` before treating a `clone_url` change as a legitimate rename.
- Prompt the user for explicit confirmation before altering `origin`, similar to how a swap requires an explicit `deadline`/slippage acknowledgement rather than blind auto-execution on stale/attacker-influenced input.

### Proof of Concept
1. User adds `https://github.com/victim-owner/project` as `origin` and uses Desktop normally; Desktop caches the associated `GitHubRepository` with `cloneURL` matching this URL.
2. `victim-owner/project` becomes available (account renamed/deleted, or repo deleted) and an attacker registers a new repository at the same `owner/name`.
3. On Desktop's next periodic API refresh, `updateRemoteUrl` is invoked with the new `apiRepo.clone_url` pointing at the attacker's repository: [4](#0-3) .
4. Since `urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)` is still true (nothing local changed) and protocols match, but `urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)` is false, the condition at line 42 triggers and `origin` is silently rewritten to the attacker's URL: [5](#0-4) .
5. The user's next `git push` from Desktop sends commits (and any credentials handled by the configured protocol) to the attacker-controlled repository without any warning.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
