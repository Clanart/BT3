## Analysis: `is_atom_canonical` / `is_clvm_canonical` — unbounded buffer read on attacker-controlled spend bundle

### Title
Out-of-bounds read / crash in mempool CLVM canonical-encoding check via truncated puzzle/solution atom - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` reads a multi-byte length prefix from a `bytes` buffer using an unchecked `offset`/loop that never verifies the buffer is long enough to contain the declared prefix length. It is called from `is_clvm_canonical()`, which is invoked directly on the untrusted, attacker-supplied `puzzle_reveal` and `solution` bytes of every coin spend during mempool admission in `MempoolManager.validate_spend_bundle()`.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the high bits of `clvm_buffer[offset]` to determine `prefix_len` (0–5 additional bytes), then loops `prefix_len` times reading `clvm_buffer[offset]` without ever checking that `offset` stays within `len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()` walks the CLVM buffer token-by-token and, whenever it hits a large-atom marker byte (`b > 0x80`), calls `is_atom_canonical(clvm_buffer, offset)` with no length validation prior to the call: [2](#0-1) 

This is called directly on the caller-supplied, unvalidated `puzzle_reveal`/`solution` bytes for every coin spend in a submitted bundle in `validate_spend_bundle()`: [3](#0-2) 

This is the same bug class as CVE-2017-9954: a length-prefixed record parser (`tekhex.c`'s `getvalue`) that trusts an encoded length/prefix field and reads past it without bounds-checking against the actual buffer size, causing an over-read. Here, a crafted atom whose declared prefix byte indicates a 5-byte extended length (`0xFC`/`0xFE` pattern) but whose buffer is truncated right after the marker byte causes `clvm_buffer[offset]` to be indexed past the end of the `bytes` object.

### Impact Explanation
In CPython, indexing a `bytes` object past its end raises `IndexError` rather than causing memory corruption, so this does not directly yield RCE or a true stack over-read as in the C/BFD case. However, the practical effect matches the "spend-triggered transaction-processing halt" impact category called out in scope: an unhandled `IndexError` propagating out of `is_clvm_canonical()` during `validate_spend_bundle()` is not caught anywhere in the visible call chain (`validate_spend_bundle` → `is_clvm_canonical` → `is_atom_canonical`), so a single malicious spend bundle can raise an unexpected exception in the mempool admission path instead of returning the intended `Err.INVALID_COIN_SOLUTION`. Depending on where/how `add_spend_bundle`/`validate_spend_bundle` errors are handled higher up, this can manifest as a crash or unhandled-exception path for the full-node's transaction processing on that request, i.e., a mempool-reachable DoS vector triggered purely by an unprivileged spend-bundle submitter.

### Likelihood Explanation
Any unprivileged peer/RPC caller can submit a `SpendBundle` with an arbitrarily crafted `puzzle_reveal`/`solution` byte string. Constructing an atom-length-prefix byte (e.g., `0xFC` or similar) followed immediately by end-of-buffer is trivial and requires no special permissions, no valid signatures beyond what mempool tests already exercise (the existing negative tests such as `test_mempool_requires_canonical_clvm` demonstrate that malformed/non-canonical solutions are already a tested, reachable code path): [4](#0-3) 

The existing tests cover non-canonical *but well-formed-length* encodings; they do not appear to cover a *truncated* multi-byte length prefix that runs off the end of the buffer, which is the specific condition that triggers the missing bounds check in `is_atom_canonical`.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before reading each length-prefix byte, and in `is_clvm_canonical()`'s dispatch to it, mirroring the bounds-checked patterns used elsewhere in this codebase for untrusted buffer parsing, e.g. `skip_bytes`/`skip_list` in `chia/full_node/full_block_utils.py`, which explicitly check `n > len(buf)` before slicing. Raise a clear, caught exception (or return "not canonical") instead of allowing an `IndexError` to propagate out of the mempool validation path.

### Proof of Concept
Conceptually (cannot execute code in this environment, so this is a description of the crafted input, not an executed exploit):
1. Construct a `puzzle_reveal` or `solution` byte string that starts with a large-atom marker requiring the maximum 5-byte extended length prefix (a byte matching the `0b11111100` bit pattern per `is_atom_canonical`), e.g. `bytes([0xFC])`.
2. Submit a `CoinSpend`/`SpendBundle` where this byte string is the entire `puzzle_reveal` or `solution` (i.e., no further bytes follow the marker).
3. Call `MempoolManager.validate_spend_bundle()` (reachable via normal transaction submission) with this spend bundle.
4. `is_clvm_canonical()` sees `b > 0x80`, calls `is_atom_canonical(clvm_buffer, offset)`; the function determines `prefix_len = 5` and loops, incrementing `offset` and indexing `clvm_buffer[offset]` beyond the 1-byte buffer, raising `IndexError` instead of the expected `Err.INVALID_COIN_SOLUTION` rejection. def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
