### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` values allows stack-overflow Denial of Service - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively re-invokes RLP decoding of `AccountKeySerializer` for each sub-key without any depth limit or "no nested composite type" check at decode time. A transaction sender (or any public-RPC caller of `kaia_decodeAccountKey`) can craft an `AccountKey` payload consisting of many levels of nested `RoleBased` keys, forcing the decoder into deep, attacker-controlled recursion before any semantic validation (`CheckInstallable`) runs, potentially exhausting the goroutine stack and crashing the node — the same bug class as CVE-2021-43519 (Lua `lua_resume` stack overflow via crafted, deeply nested input).

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a key type tag and then decodes the concrete `AccountKey` value via `s.Decode(serializer.key)`: [1](#0-0) 

When the type tag is `AccountKeyTypeRoleBased`, this dispatches to `AccountKeyRoleBased.DecodeRLP`, which decodes a `[][]byte` and, for **each** byte string, calls `rlp.DecodeBytes(b, &serializer)` into a fresh `AccountKeySerializer` — which can itself be another `RoleBased` key, re-entering the same function: [2](#0-1) 

Nowhere in this decode path is nesting depth checked or rejected. The only defense against nested `RoleBased` keys — `ErrNestedCompositeType` in `CheckInstallable`/`CheckUpdatable` — runs strictly **after** the entire (already recursively decoded) structure exists in memory: [3](#0-2) 

This decode path is reached automatically as soon as raw transaction bytes are parsed — well before signatures or account-key semantics are validated. For example, `TxInternalDataAccountUpdate.fromSerializable` (invoked from the transaction's `DecodeRLP`) immediately calls `rlp.DecodeBytes(serialized.Key, serializer)` on the raw key bytes taken directly from the wire: [4](#0-3) 

The same unguarded pattern exists for `TxTypeAccountCreation` and `TxTypeFeeDelegatedAccountUpdate` (and variants), and is also directly reachable via the public RPC method `kaia_decodeAccountKey`: [5](#0-4) [6](#0-5) 

Each nesting level only costs a small constant number of RLP prefix bytes (a list/string length header), so within typical transaction-size limits an attacker can construct many thousands of nesting levels, each of which consumes a Go call-stack frame across multiple function calls (`DecodeRLP` → `rlp.DecodeBytes` → reflection-based struct/interface decoding → `AccountKeySerializer.DecodeRLP` → `NewAccountKey` → `s.Decode` → back into `AccountKeyRoleBased.DecodeRLP`). This mirrors the CVE-2021-43519 bug class: unbounded interpreter/decoder recursion driven entirely by attacker-supplied structure, leading to a stack overflow.

### Impact Explanation
A stack overflow in Go is a fatal, unrecoverable runtime error (`runtime: goroutine stack exceeds ... — fatal error: stack overflow`) that cannot be caught by `recover()` and crashes the entire process. Since this decode path executes:
- during p2p transaction propagation/decoding (any node that receives the malicious transaction bytes),
- during `eth_sendRawTransaction`/`AddRemote` transaction pool admission, and
- via the public `kaia_decodeAccountKey` RPC method,

a single unprivileged transaction sender or RPC caller can crash any node that processes the crafted payload, including validator/consensus nodes that relay or include the transaction. This is a network-wide Denial of Service reachable via a single submitted transaction, which the scan rules classify as Medium/High severity.

### Likelihood Explanation
High. No special privileges, valid signature, or contract deployment is required — the recursive decode occurs purely as part of RLP structural parsing, prior to any signature or `CheckInstallable` validation. Constructing nested `RoleBased` byte strings is straightforward with any RLP encoding library; the attacker only needs to nest `AccountKeySerializer`-encoded bytes within the outer `[][]byte` recursively.

### Recommendation
- Enforce a hard recursion/nesting-depth limit in `AccountKeyRoleBased.DecodeRLP` (and generally in `AccountKeySerializer.DecodeRLP`) before recursively decoding nested keys — e.g., track and pass down a depth counter, or reject any `AccountKeyTypeRoleBased` value type-tag encountered while already decoding a `RoleBased`/composite key, at decode time rather than only at `CheckInstallable` time.
- Alternatively, perform an inexpensive pre-scan of the raw bytes to reject inputs whose RLP nesting depth exceeds the maximum meaningful depth (`RoleLast`, i.e., 3 roles, each holding only non-composite keys) before invoking the general reflection-based RLP decoder.
- Apply the same depth-limiting principle generally to `rlp.DecodeBytes`/`Stream.Decode` for any type that can recursively contain itself (interfaces, self-referential `Decoder` implementations), consistent with how upstream go-ethereum bounds RLP list nesting.

### Proof of Concept
1. Construct an `AccountKeySerializer` payload for `AccountKeyTypeRoleBased` whose role slice contains a single element that is itself an RLP-encoded `AccountKeySerializer` of type `AccountKeyTypeRoleBased`, and repeat this nesting recursively N times (e.g., N = 50,000), each level adding only a few bytes of RLP list/string framing.
2. Embed the resulting byte blob as the `Key` field of a `TxTypeAccountUpdate` (or `TxTypeAccountCreation`) transaction, or submit it directly via `kaia_decodeAccountKey(encodedAccKey)`.
3. Submit the transaction via `eth_sendRawTransaction`/p2p broadcast, or call the RPC method directly.
4. Observe that `rlp.DecodeBytes` → `AccountKeyRoleBased.DecodeRLP` recurses N times before any `CheckInstallable`/signature validation occurs, exhausting the goroutine stack and crashing the node process with `fatal error: stack overflow`.

*(Note: the exact recursion depth needed to trigger a Go stack overflow depends on Go runtime stack-growth limits and was not empirically measured in this analysis; confirming the precise N required, along with any transaction/RLP size caps that might bound it in practice, would require running the harness in a live environment.)*

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
