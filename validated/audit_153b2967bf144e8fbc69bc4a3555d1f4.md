## Analog Found: Same class of bug — decimal-precision scaling silently skipped in one direction

The Balancer/Notional bug was about ignoring a "precision" value needed to normalize a raw number, causing an overvalued (or undervalued) result. The exact same defect pattern exists in `pallet-hyper-fungible-token`'s decimal-scaling helpers, which convert amounts between the local asset's decimals and the remote EVM contract's decimals.

### Title
Asymmetric decimal-scaling in `convert_to_erc20`/`convert_to_balance` causes massively wrong bridged amounts when the remote token has fewer decimals than the local asset - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_erc20` and `convert_to_balance` both compute the exponent via `erc_decimals.saturating_sub(local_decimals)` and only ever *multiply*/*divide* by that exponent. This only works correctly when `erc_decimals >= local_decimals`. When `erc_decimals < local_decimals` (a perfectly legitimate token registration — e.g. bridging a 6-decimal EVM stablecoin against an 18-decimal local asset), `saturating_sub` silently clamps to `0`, so the scaling factor becomes `10^0 = 1` and no correction is applied at all in the direction that actually matters. [1](#0-0) 

### Finding Description
- `convert_to_erc20(value, erc_decimals, local_decimals)` is used in `send()` to convert the just-escrowed/burned local amount into the ERC20-precision amount embedded in the outgoing `Message.amount` that is dispatched to the remote chain: `let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);` [2](#0-1) 
- `convert_to_balance(value, erc_decimals, local_decimals)` is used symmetrically in `on_accept` and `on_timeout` to convert an incoming/refunded ERC20-precision amount back into local-asset units before minting/releasing funds: [3](#0-2)  and [4](#0-3) 
- Both helpers use `erc_decimals.saturating_sub(local_decimals)` as the *only* exponent, regardless of which side has more decimals: [5](#0-4) 

This is precisely the bug class of the seed report: a decimals/precision relationship exists between two representations of the same value, but the code path only correctly handles one direction (`erc_decimals >= local_decimals`) and silently no-ops in the other, producing an "overvalued" or "undervalued" result exactly like the AMP-precision-not-divided issue.

`Precisions` (the per-`(asset, chain)` EVM decimals) is set by governance via `register_token`/`update_token`, but the *combination* of `erc_decimals < local_decimals` is not an admin error or malicious governance action — it is a completely normal, expected configuration (e.g., bridging a 6-decimal USDC-style EVM token against a locally-registered 18-decimal wrapped asset, or any native-EVM token with fewer decimals than the Substrate `Assets` pallet's configured decimals for that asset). No malicious peer, relayer, or governance actor is required — an ordinary user calling the public `send()` extrinsic triggers the flawed math.

### Impact Explanation
When `erc_decimals < local_decimals`:
- In `send()`: `convert_to_erc20` fails to scale the amount **down**, so the ERC20 amount encoded in the outbound message is left at full local-decimals magnitude instead of being divided by `10^(local_decimals - erc_decimals)`. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will then mint/release an amount up to `10^(local_decimals - erc_decimals)` times larger than what was actually escrowed/burned on the source chain — direct theft/drain of the destination-side custody pool or unlimited minting of the wrapped token.
- In `on_accept`/`on_timeout`: `convert_to_balance` fails to scale the amount **up** in the same scenario, causing massive under-crediting of the beneficiary (loss of funds for legitimate cross-chain transfers) — or, on the timeout/refund path, under-refunding the original sender.

Either direction is an "accounting issue" that moves funds to the wrong amount, matching the bounty's "stealing or loss of funds" / "unauthorized … execution" / "transaction manipulation" categories.

### Likelihood Explanation
This triggers under a token registration that is entirely realistic and within the pallet's documented use case — bridging any ERC20 with fewer than 18 (or fewer than the local asset's configured) decimals against a local asset of higher decimal precision, or vice versa for the `on_accept` direction. It requires no privileged or malicious actor: a normal user calling the public `send` extrinsic (or a normal inbound message from the paired contract) exercises the vulnerable path once such a token pair exists.

### Recommendation
Fix both helpers to handle both directions explicitly instead of relying on `saturating_sub` collapsing to zero:
```rust
if erc_decimals >= local_decimals {
    value * 10^(erc_decimals - local_decimals)   // convert_to_erc20 case
} else {
    value / 10^(local_decimals - erc_decimals)
}
```
and the mirrored logic (multiply/divide swapped) for `convert_to_balance`. Add unit tests covering `erc_decimals < local_decimals` for both `send` and `on_accept`/`on_timeout` paths, matching how the seed report recommended actually applying the ignored precision value.

### Proof of Concept
1. Governance registers asset `X` as non-native with `Precisions::<T>::insert(X, dest_chain, 6)` (destination ERC20 has 6 decimals), while the local `Assets` pallet reports `decimals(X) == 18`.
2. A user calls `send(SendParams { asset_id: X, amount: 1_000_000_000_000_000_000 /* "1.0" token at 18 dp */, destination: dest_chain, .. })`.
3. Inside `send`, `erc_decimals = 6`, `decimals = 18`. `convert_to_erc20(1e18, 6, 18)` computes `saturating_sub(6,18) = 0` → multiplier `10^0 = 1` → `erc20_amount = 1e18` (unchanged), instead of the correct `1e18 / 10^12 = 1_000_000` (i.e. "1.0" USDC at 6 dp).
4. The outbound `Message.amount` field therefore encodes `1_000_000_000_000_000_000` raw units of a 6-decimal token — a trillion times more than intended.
5. On the destination EVM contract, this raw amount is released/minted to the recipient, draining the destination custody pool (or minting a trillion-times-inflated wrapped balance) for the cost of locking a single local token unit. [6](#0-5) [2](#0-1)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
