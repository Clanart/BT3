### Title
`ssh://` remote URL parsing miscomputes `owner`/`name` for multi-segment paths, causing wrong GitHub identity resolution - (File: `app/src/lib/remote-parsing.ts`)

### Summary
`parseRemote` in `app/src/lib/remote-parsing.ts` uses a fixed set of regexes to split an attacker/repo-supplied git URL into exactly three parts: `hostname`, `owner`, `name`. This is structurally the same bug pattern as the Yeti Finance `buyBack` issue: code assumes a return value (there, `amounts[0]`/`amounts[1]`; here, capture groups 1/2/3) always corresponds one-to-one with a fixed semantic meaning, but the actual shape of the attacker-influenced input (a swap `path` there, a remote URL here) can vary, silently shifting which value ends up in which slot.

### Finding Description
The `ssh://` regex is: [1](#0-0) 

`^ssh://git@(.+)/(.+)/(.+?)(?:/|\.git)?$` uses two greedy `(.+)` groups for hostname and owner and only a lazy group for `name`. For a URL with more than the expected two path segments after the host (e.g. `ssh://git@github.com/a/b/c.git`), regex backtracking assigns the *extra* path segment to the greedy `hostname` group rather than failing or preserving the intended `owner/name` semantics — i.e. `hostname="github.com/a"`, `owner="b"`, `name="c"`, instead of any well-defined error. `parseRemote` returns exactly whichever three groups it finds without validating that `hostname` looks like a hostname or that `owner`/`name` are the true GitHub `owner/name`: [2](#0-1) 

This wrongly-parsed `{hostname, owner, name}` triple then propagates into:
- `findAccountForRemoteURL`, which uses `parsedURL.hostname` to select which signed-in `Account` to use for API calls: [3](#0-2) 
- `matchGitHubRepository`, which returns `{name, owner, account}` for a remote purely from `parsedRemote.hostname` matching: [4](#0-3) 
- `urlMatchesRemote`, used by the dispatcher to decide which local repository a PR's `head`/`base` `clone_url` belongs to: [5](#0-4) [6](#0-5) 

None of these consumers re-validate that `owner`/`name` are actually two clean path segments of a `github.com`/GHE host; they trust whatever `parseRemote` handed back.

### Impact Explanation
Because `hostname` can silently absorb an extra path segment, `owner`/`name` extracted from a maliciously-shaped remote URL (e.g. a URL embedded in `.git/config`, a submodule URL, or a PR API `clone_url` supplied by an attacker-controlled fork) can be misattributed. Consequences include:
- Wrong account selection for API calls (`findAccountForRemoteURL`), potentially causing Desktop to use the wrong authenticated account/token context for a repository lookup.
- Wrong repository matching in `doesRepositoryMatchUrl`/`urlMatchesRemote`, which is used by the "Open PR in Desktop" flow (`getRepositoryFromPullRequest` in `app/src/ui/dispatcher/dispatcher.ts`) to decide which existing local repository to reuse for checking out a pull request. Silent misattribution here plausibly leads to checking out an attacker-influenced PR branch into an unintended local repository/working directory (a "silent corruption of what the user commits" style outcome), though I could not fully trace whether GitHub's actual `clone_url` format can ever contain more than two path segments in practice (GitHub disallows `/` in repo/owner names), which limits real-world reachability from genuine github.com URLs. It would be reachable through GitHub Enterprise or non-standard remotes/mirrors where extra path segments are permitted.

### Likelihood Explanation
Medium-low confidence/likelihood: I verified the regex ambiguity is real (traced manually) and that downstream consumers do not add extra validation, matching the structural weakness in the reported bug class (silent misuse of positionally-trusted, attacker-shaped data). However, I was not able to confirm within the available context whether GitHub.com itself can ever produce a `clone_url`/remote path with more than the expected two segments (which is the main way an unprivileged attacker would control this without local file/config tampering); if it cannot, the practical trigger is narrower (GHE/custom remotes, or an attacker who can influence `.gitmodules`/remote config content that Desktop later parses). This uncertainty means the analog is plausible but not conclusively proven exploitable purely from index coverage.

### Recommendation
- Do not rely on greedy capture groups to delimit `hostname` vs `owner` vs `name`; validate that `owner` and `name` do not themselves contain additional `/` characters that indicate mis-split segments, and reject ambiguous URLs (return `null`) rather than guessing.
- Add explicit tests for `ssh://` URLs (and the `https://` regex, which has the same greedy-hostname pattern) with more than two trailing path segments to lock in intended behavior.
- Audit downstream consumers (`findAccountForRemoteURL`, `matchGitHubRepository`, `urlMatchesRemote`) to ensure they fail closed (treat as "no match"/"unknown account") rather than silently proceeding with a possibly-wrong `owner`/`name`.

### Proof of Concept
```ts
import { parseRemote } from '../../src/lib/remote-parsing'

const remote = parseRemote('ssh://git@github.com/a/b/c.git')
// Expected (if URL had extra unintended segment): hostname should not silently
// swallow "/a" while owner/name shift to "b"/"c".
console.log(remote)
// => { protocol: 'ssh', hostname: 'github.com/a', owner: 'b', name: 'c' }
```
This demonstrates that the regex silently reinterprets a 4-segment SSH path as `hostname/owner/name` = `github.com/a`, `b`, `c` rather than failing or preserving the first segment as `owner`. Full confirmation that this is reachable via a genuinely externally-controlled value (rather than a locally-edited remote) would require further investigation with a Devin session that can run the test suite and trace the exact origin of `IAPIPullRequest.head.repo.clone_url` formatting on GitHub Enterprise, which is outside what the index could confirm.

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
