### Title
Governance vote can set `kip71.gastarget` to zero, causing a division-by-zero panic in `NextMagmaBlockBaseFee` and halting block production/validation - (File: `params/kip71_config.go`)

### Summary
The `Kip71GasTarget` governance parameter has no format validation (a `noopFormatChecker`) and no cross-parameter consistency check, unlike its sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero. A governance voter (the governing node in single mode, or any council member) can therefore vote `kip71.gastarget = 0` into the chain configuration. Once active, `NextMagmaBlockBaseFee` divides by `gasTarget` unconditionally whenever `parentGasUsed != gasTarget`, which will be true for essentially any non-empty block once `gasTarget` is 0, causing a `big.Int` division-by-zero panic in every node computing or verifying the base fee — a consensus-halting bug.

### Finding Description
`Kip71GasTarget` is declared in the governance parameter table with `FormatChecker: noopFormatChecker`, meaning any `uint64` value including 0 is accepted: [1](#0-0) 

Compare this with `Kip71BaseFeeDenominator`, which explicitly guards against zero (`v != 0`): [2](#0-1) 

The vote-consistency checker in header governance also does not validate `Kip71GasTarget`'s value against any bound — it is simply included in the pass-through case that returns `nil` (valid) unconditionally, unlike `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` which do get cross-checked: [3](#0-2) 

Once `GasTarget` is 0, `NextMagmaBlockBaseFee` (used both to verify header base fee and to construct the next block's base fee) computes: [4](#0-3) 

and the symmetric decreasing-fee branch: [5](#0-4) 

Note that `BaseFeeDenominator` has an explicit zero-fallback (defaulting to 64) at lines 71-76, but `gasTarget` has no equivalent protection. If `parentGasUsed == gasTarget` (both zero, i.e., an empty block), the function returns early without dividing; but for any block with `gasUsed > 0`, `parentGasUsed > gasTarget` (0) is true, and the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, which panics on division by zero in `math/big`.

This function is invoked both during header verification (`VerifyMagmaHeader`) and during block assembly: [6](#0-5) 

so both proposers building a block and all nodes verifying it will crash/panic once this governance value takes effect and any transaction is included in a block.

### Impact Explanation
This is a direct analog of the reported `StakingRewards.setRewardsDuration` class of bug: a privileged setter accepts a value (duration/target) that, when zero, breaks a downstream division used in core accounting/pricing logic, with no min/max validation. Here the impact is more severe than the original finding because it is consensus-critical: once `gasTarget = 0` is voted in and takes effect (at the next epoch boundary via header governance), every full node computing or verifying the block base fee for any non-empty block will panic, halting block production and chain liveness network-wide. This constitutes acceptance of an invalid configuration that leads to state-transition failure/crash across all honest nodes.

### Likelihood Explanation
Reaching this requires a single vote from a governance council member (or the sole governing node under "single" mode, which is Kaia mainnet's default `GovernanceMode`, per `kaiax/gov/README.md`). No majority or multi-round confirmation beyond the standard epoch-based vote application is required, and neither the parameter's format checker nor its consistency checker rejects zero — this mirrors the "admin privilege but no bound check" scenario judged Medium severity in the original report, while here the blast radius is a full-network liveness failure rather than a single reward pool becoming inoperable.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (and any other value that would produce degenerate base-fee dynamics), analogous to the existing check on `Kip71BaseFeeDenominator`. Additionally, add defensive zero-handling inside `NextMagmaBlockBaseFee` for `gasTarget` (mirroring the existing fallback logic for `baseFeeDenominator`) so that a misconfigured chain config cannot crash node software even if a bad value slips through governance.

### Proof of Concept
1. Under `GovernanceMode: "single"`, have the governing node cast a header vote `kip71.gastarget = 0` (canonicalized via `uint64Canonicalizer`, which accepts 0, and validated via `noopFormatChecker`, which accepts anything).
2. `VerifyVote`/`checkConsistency` treats `gov.Kip71GasTarget` as always valid (`kaiax/gov/headergov/impl/header.go:214-220`), so the vote is accepted and applied at the next epoch boundary.
3. Once `GasTarget = 0` is active and any subsequent block includes at least one transaction (`GasUsed > 0`), `NextMagmaBlockBaseFee` (`params/kip71_config.go:99-121`) executes `x.Div(x, new(big.Int).SetUint64(0))`, panicking with a division-by-zero error inside both the block-producing worker (`work/worker.go:382`) and every verifying node's `VerifyMagmaHeader` call, halting the chain.
