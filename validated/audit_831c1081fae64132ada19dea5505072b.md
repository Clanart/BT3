### Title
Automatic, unconfirmed remote-URL rewrite based on GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently rewrites a repository's `origin` git remote URL whenever the GitHub API reports a different `clone_url` for the tracked repository, without any user confirmation, as long as a same-protocol heuristic check passes.

### Finding Description
The broken invariant mirrors the PSP22 report's core problem: a security-relevant value (the *allowance* in PSP22; here, the *destination remote URL* that all future `git push`/`git fetch` operations target) is mutated automatically from an external, attacker-influenceable source without an explicit re-confirmation step from the party who is trusting that value.

`updateRemoteUrl` reads the currently configured remote URL and compares it to `apiRepo.clone_url`, a field that comes straight from a GitHub API response object: [1](#0-0) 

If the protocol scheme matches and the current remote still matches the *previously cached* `gitHubRepository.cloneURL`, Desktop calls `gitStore.setRemoteURL` to overwrite `origin` with whatever `clone_url` the API returned this time: [2](#0-1) 

The only two safeguards are:
1. `protocolsMatch` — only checks that both URLs use the same scheme (`https` vs `ssh`), not that they point to the same trusted host/owner.
2. `remoteUrlUnchanged` — only checks the user hasn't manually edited the remote since Desktop last cached it; it does **not** verify that the new `clone_url` still refers to the same underlying repository identity (e.g., by comparing GitHub's immutable repository ID), only that the hostname/owner/name components differ per `urlMatchesRemote`: [3](#0-2) 

This is analogous to PSP22's `approve`: a background refresh (`gitStore.loadRemotes()` / periodic GitHub metadata refresh, analogous to Bob's pending spend) can race with, or simply trust, a value supplied externally (the API's `clone_url`, analogous to Alice's new allowance) and apply it without the user (Alice) being aware the underlying trust anchor changed.

### Impact Explanation
If a repository is renamed/transferred on GitHub (owner or name change) and Desktop's cached `GitHubRepository.cloneURL` still matches what's configured locally, the next background refresh will silently rewrite `origin` to the new `clone_url` value reported by the API — with no dialog, confirmation, or diff shown to the user. Because subsequent pushes and fetches use `gitStore.defaultRemote` (populated from `git remote -v`, now pointing at the rewritten URL), this can silently redirect where the user's commits are pushed and where "incoming" history is fetched from, corrupting the destination of what the user believes they are pushing to.

### Likelihood Explanation
I could not fully confirm, from the indexed code, the exact resolution path that produces the `apiRepo` object passed into `updateRemoteUrl` (i.e., whether it is always looked up by GitHub's immutable numeric repository ID, which would make a hostile substitution hard, or can be re-resolved via owner/name lookup, which would be attacker-influenceable if a repository name/owner is reused after deletion/transfer). Without that confirmation, likelihood is uncertain — this is the main gap in the analysis. The mechanism itself (auto-rewrite with only a protocol-and-previous-URL heuristic, no explicit identity pinning or user prompt) is present in the code and is the closest analog to the reported "silent invariant change" bug class in PSP22.

### Recommendation
- Pin repository identity across refreshes using GitHub's immutable repository ID rather than (or in addition to) owner/name/hostname string comparison, so a renamed/transferred repo is only auto-followed if the ID matches the previously recorded ID.
- Prompt the user for confirmation before rewriting `origin`'s URL, rather than doing it silently as a side effect of a background refresh.
- Log/audit remote URL changes so users can detect unexpected redirection.

### Proof of Concept
Not able to construct a concrete, fully-verified end-to-end PoC without confirming how `apiRepo` is resolved relative to the cached `GitHubRepository` record (see Likelihood Explanation). The conceptual trigger is:
1. User adds/clones a GitHub repository; Desktop caches `GitHubRepository.cloneURL` and configures `origin` to match.
2. The tracked repository's `clone_url` changes on the GitHub side (rename/transfer) in a way that `apiRepo.clone_url` reflects.
3. On the next background metadata refresh, `updateRemoteUrl` sees `remoteUrlUnchanged === true`, `protocolsMatch === true`, `urlsMatch === false`, and calls `setRemoteURL`, rewriting `origin` without any user prompt: [4](#0-3) 

Given the unresolved uncertainty about attacker control over step 2, this should be treated as a **candidate** finding requiring further verification (e.g., via a Devin session with full repo access) rather than a confirmed exploit.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
