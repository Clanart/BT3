### Title
Missing `chain_id` in EIP-712 Domain Separator Enables Cross-Network Replay of Withdrawal Authorization Signatures — (`core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is defined as a static constant with only `name` and `version` fields, omitting `chainId`. This means any EIP-712 signature produced by the aggregator to authorize an optimistic payout or operator withdrawal on one Citrea network is cryptographically valid on every other Citrea network that uses the same aggregator key, because the domain separator does not bind the signature to a specific chain.

---

### Finding Description

In `core/src/rpc/ecdsa_verification_sig.rs`, the EIP-712 domain is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 specification requires `chainId` in the domain separator precisely to prevent cross-chain replay. Without it, the hash produced by `params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` is identical across all Citrea deployments (mainnet, testnet4, devnet, any fork). [2](#0-1) 

This domain is used in two authorization paths:

1. **Verifier — optimistic payout signing** (`Verifier::sign_optimistic_payout`): verifiers check the aggregator's ECDSA signature before contributing a MuSig2 partial signature that, when aggregated, spends BTC from the vault. [3](#0-2) 

2. **Operator — withdrawal execution** (`rpc/operator.rs` `withdraw` handler): operators check the same signature before executing the payout transaction. [4](#0-3) 

The `aggregator_verification_address` is described in the config as the primary authorization gate for optimistic payouts and withdrawals, and is set by default: [5](#0-4) [6](#0-5) 

The config already carries `citrea_chain_id: u32` (read from `CITREA_CHAIN_ID` env var), which is the correct value to bind the domain to a specific network: [7](#0-6) 

The developers are explicitly aware of cross-network replay: `BatchProofMethodIdBody` in the tx-sender crate includes `chain_id: u64` with the comment *"Network identifier to prevent cross network replay attacks"* — but this protection was not applied to the EIP-712 domain. [8](#0-7) 

---

### Impact Explanation

If the same aggregator ECDSA key is used across multiple Citrea deployments (mainnet + testnet, or across a hard fork), a signature produced for a withdrawal on network A is accepted verbatim on network B. An attacker who can observe a valid signature on one network (e.g., from a public gRPC call or a replayed transaction) can submit it to operators/verifiers on another network. If the withdrawal parameters (ID, UTXO, amount, script) also match state on the target network — which is plausible at fork time or in mirrored test deployments — the verifiers will sign the optimistic payout and the operator will execute the payout transaction, spending BTC from the vault without a legitimate withdrawal on that chain.

---

### Likelihood Explanation

The preconditions are:
- Same aggregator ECDSA key across networks (common in practice; the default config ships a single hardcoded address).
- Matching withdrawal state on the target network (most likely at fork time or in mirrored deployments).
- The attacker must pass mTLS (a separate layer), but the EIP-712 check is the only application-layer authorization for the withdrawal params themselves.

---

### Recommendation

Include `citrea_chain_id` from `BridgeConfig` in the EIP-712 domain separator. Because `CLEMENTINE_EIP712_DOMAIN` is currently a `static`, it must be changed to a function or lazy-initialized value that incorporates the runtime chain ID:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` wherever `recover_address_from_ecdsa_signature` is called, and update `sign_withdrawal_verification_signature` in tests to use the same chain-ID-bound domain.

---

### Proof of Concept

1. Deploy Clementine on mainnet Citrea (chain_id = X) and testnet Citrea (chain_id = Y) with the same aggregator ECDSA key.
2. On testnet, submit a valid `OptimisticWithdrawParams` with a correctly signed `verification_signature` (signed by the aggregator key over the EIP-712 hash using `CLEMENTINE_EIP712_DOMAIN`).
3. Capture the `verification_signature` string.
4. On mainnet, submit the identical `OptimisticWithdrawParams` + captured `verification_signature` to the aggregator's `optimistic_payout` RPC.
5. `recover_address_from_ecdsa_signature` recomputes `params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` — because the domain contains no `chainId`, the hash is identical on both networks, and the recovered address matches `aggregator_verification_address`.
6. The authorization check passes; verifiers sign the MuSig2 partial signatures; the aggregator assembles the final signature and the optimistic payout transaction spends BTC from the mainnet vault. [9](#0-8) [10](#0-9)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
