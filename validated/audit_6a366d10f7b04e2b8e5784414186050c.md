### Title
Fee-on-transfer ERC20 tokens break Bridge's internal accounting, causing cross-chain value mismatch and stuck/insolvent transfers - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom` and then unconditionally uses the nominal `_value`/`_feeLimit` amounts for fee payment, refund, optional burning, and the cross-chain `RequestValueTransfer` event, without ever checking how many tokens the Bridge actually received. If a registered token charges a transfer fee (deflationary/fee-on-transfer token), the Bridge's real balance is smaller than the accounted amount, breaking the invariant that the emitted/burned/collateralized amount matches actual holdings.

### Finding Description
In `requestERC20Transfer`:
```
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The contract never measures its own balance before/after the transfer; it assumes `_value + _feeLimit` tokens landed in the Bridge. `_requestERC20Transfer` then:
- calls `_payERC20FeeAndRefundChange`, which sends out `fee` to `feeReceiver` and `feeRefund = _feeLimit - fee` back to the sender, both taken from the nominal `_feeLimit`, not the actually-received amount: [2](#0-1) 
- if `modeMintBurn` is enabled, burns the full nominal `_value` via `ERC20Burnable(_tokenAddress).burn(_value)`: [3](#0-2) 
- emits `RequestValueTransfer(..., _value, ..., fee, ...)`, which is the exact value the counterpart chain's operators will mint/transfer to `_to` via `handleERC20Transfer`: [4](#0-3) 

If the underlying token deducts a fee on transfer, the Bridge actually holds less than `_value + _feeLimit`:
- In `modeMintBurn` mode, `burn(_value)` can revert (Bridge doesn't have `_value` tokens), breaking the transfer entirely (DoS on that token), or if the token also fee-taxes the burn call, could still leave dust discrepancies.
- In lock/release (non mint-burn) mode, the Bridge simply retains fewer tokens than `_value` credited to the destination chain. Since `RequestValueTransfer` reports the full nominal `_value`, `handleERC20Transfer` on the counterpart chain will still transfer/mint the full nominal `_value` to `_to`: [5](#0-4) 
Repeated over multiple requests, this steadily drains the Bridge's real token collateral below what has been "promised" cross-chain, eventually causing the Bridge to be unable to honor `safeTransfer(_to, _value)` for legitimate withdrawals (reverts) or, if partially backed, allows a subset of users to receive their full nominal amount at the expense of others whose withdrawal later fails.

### Impact Explanation
This is unauthorized value/accounting divergence between the source and destination chains of the service-chain Bridge: the Bridge under-collects real tokens relative to what it promises to deliver on the other side, and fee refunds are computed against a phantom (uncollected) balance. This can lead to Bridge insolvency for that token (inability to service withdrawals) and/or reverting transactions that should otherwise succeed, both of which are concrete state-divergence / value-movement problems rather than a purely cosmetic issue. Severity is bounded to whichever ERC20 tokens are registered on the Bridge (`onlyRegisteredToken`), so the practical exposure depends on the deployer whitelisting a fee-on-transfer token — but once such a token is registered, any unprivileged holder of that token triggers the accounting break with a single `requestERC20Transfer` call.

### Likelihood Explanation
Likelihood is Medium: it requires that a fee-on-transfer / deflationary ERC20 be registered as a supported bridge token (an admin/operator action via `BridgeTokens.registerToken`, not attacker-controlled), but registration is a normal operational action that doesn't require deep security review of transfer semantics, and this class of ERC20 is common in the wild. Once registered, exploitation is trivial and reachable by any ordinary user simply calling the public `requestERC20Transfer` function — no privileged role or malicious peer/validator behavior is needed.

### Recommendation
In `requestERC20Transfer` (and the 1-step `onERC20Received` path), measure the Bridge's actual token balance before and after `safeTransferFrom`/receipt, and use the actually-received delta (rather than the nominal `_value + _feeLimit`) for fee deduction, refund, burn, and the `RequestValueTransfer` event amount. Alternatively, explicitly reject registration/use of fee-on-transfer tokens by verifying `balanceOf` deltas match expected amounts and reverting otherwise.

### Proof of Concept
1. Admin registers a fee-on-transfer ERC20 token `T` (e.g., 5% fee) on the Bridge via `registerToken`.
2. User calls `requestERC20Transfer(T, to, value=100, feeLimit=0, extraData)`.
3. `safeTransferFrom(msg.sender, bridge, 100)` actually delivers only 95 `T` to the Bridge due to the token's fee-on-transfer logic.
4. `_requestERC20Transfer` proceeds as if the Bridge holds 100 `T`:
   - If `modeMintBurn == true`: `ERC20Burnable(T).burn(100)` reverts because Bridge only holds 95 — transfer permanently fails (DoS), or if Bridge holds surplus from earlier transfers, it burns tokens that should have backed a different request, corrupting collateral for other pending transfers.
   - If `modeMintBurn == false`: event `RequestValueTransfer(..., value=100, ...)` is emitted; the counterpart chain operator later calls `handleERC20Transfer(..., value=100, ...)`, releasing/minting 100 tokens to `to` on the destination chain even though only 95 were actually escrowed on the source chain.
5. Repeating this drains real collateral relative to the promised amounts, eventually causing legitimate `handleERC20Transfer` calls (for other users) to revert due to insufficient Bridge balance in lock/release mode. [6](#0-5) [2](#0-1)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
