### Title
Vote-weight sniping via `vote()`/`castVotes()`/`claimBribe()` allows theft of unclaimed bribe yield from long-term voters - ([File: rewards/BaseRewardPoolV2.sol], [File: rewards/BribeRewardPool.sol], [File: wombat/WombatBribeManager.sol])

### Summary
`BaseRewardPoolV2._provisionReward` distributes newly-queued bribe rewards by dividing the incoming amount by the **current** `totalStaked()` at the moment of the call, rather than by a time-weighted stake. Because `WombatBribeManager.vote()` lets any vlMGP holder instantly reallocate already-locked vote weight into a target pool's rewarder with no cooldown, an attacker can move weight into a pool immediately before `castVotes()` forwards a harvested bribe to that pool's `BribeRewardPool`, then call `claimBribe()` to capture a proportional share of a reward that was actually earned by other voters who held the vote allocation for the whole epoch.

### Finding Description
`WombatBribeManager.vote()` calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, delta)` for any positive delta the caller submits, with only a total-locked-amount check and no minimum holding period: [1](#0-0) 

`BribeRewardPool.stakeFor` runs the `updateRewards` modifier (which snapshots `userRewardPerTokenPaid` to the *current* `rewardPerToken` using the account's *pre-increase* balance) and only afterward increases `_balances`/`totalSupply`: [2](#0-1) [3](#0-2) 

`WombatBribeManager.castVotes()` then calls `wombatStaking.vote()`, which harvests the real Wombat bribe and calls `queueNewRewards` on the pool's rewarder: [4](#0-3) 

`queueNewRewards` → `_provisionReward` updates `rewardPerTokenStored` using the reward amount divided by `totalStaked()` **at that exact moment** — a discrete, non-time-weighted index update: [5](#0-4) 

Because the attacker's `stakeFor` call (inside `vote()`) executes before `castVotes()` triggers `_provisionReward`, the attacker's freshly-added balance is already counted in `totalStaked()` when the reward index is bumped, and their `userRewardPerTokenPaid` was frozen at the pre-bump value. Consequently `earned()` (`_earned`, `BaseRewardPoolV2.sol:316-321`) computes a nonzero share for the attacker for a reward period during which they held the vote weight for essentially zero time, while diluting/reducing the effective share that accrues to voters who held that weight for the entire epoch that generated the underlying Wombat bribe: [6](#0-5) 

`claimBribe()`/`claimBribeFor()` → `_claimBribeFor()` immediately calls `getReward` to pay out this amount: [7](#0-6) 

No modifier, cooldown, vesting, or minimum-staking-duration check exists anywhere in this path to prevent last-block reallocation of vote weight prior to a reward provisioning event; `vote()` and `castVotes()` are both public/unprivileged.

### Impact Explanation
This is a theft of unclaimed yield from other voters: the bribe deposited into a pool's `BribeRewardPool` was earned by users who held Wombat-facing vote allocation to that pool for the full epoch, but the internal reward-per-token accounting pays out proportionally to whoever holds the internal `BribeRewardPool` balance at the instant the bribe is queued. An attacker with substantial vlMGP voting power can repeatedly reallocate into whichever pool is about to have a harvested bribe forwarded (or trigger `castVotes()` themselves), extracting a share of rewards without having contributed the corresponding real-world vote weight to Wombat during the accrual period, at the expense of long-term voters of that pool.

### Likelihood Explanation
- Attacker only needs to already hold locked vlMGP (unprivileged, permissionless) and be able to call the public functions `vote()`, `castVotes()`, and `claimBribe()`.
- No cooldown or minimum-lock-duration exists between reallocating vote weight and being credited reward index at `castVotes()` time.
- The attack is atomic and repeatable every voting/cast cycle (e.g., every epoch or whenever `castVotes()` is invoked), and can be executed as a self-contained sequence (`vote(delta>0)` → `castVotes(true)` → `claimBribe(lps)`) in one transaction, with no need to front-run a third party's mempool transaction.

### Recommendation
Change the reward distribution model in `BaseRewardPoolV2`/`BribeRewardPool` to a time-weighted accrual (e.g., checkpoint-based reward-per-second accounting, or require a minimum lock/vesting period before newly staked balance becomes eligible for a reward snapshot), and/or add a cooldown in `WombatBribeManager.vote()` preventing reallocation of vote weight within the same epoch/block window as `castVotes()`'s reward forwarding for the affected pool.

### Proof of Concept
Hardhat test outline:
1. Deploy `BribeRewardPool` (via `WombatBribeManager`/`WombatStaking` harness) with two voters, A and B, plus attacker C.
2. Have B (and not C) vote for pool P at epoch start and hold that vote allocation for the full epoch.
3. Just before invoking `castVotes(true)` (which triggers `queueNewRewards` on P's rewarder), have attacker C call `vote([P], [largeDelta])` to instantly add weight to P.
4. Call `castVotes(true)` to forward the harvested/simulated bribe into P's rewarder (`_provisionReward`).
5. Immediately call `claimBribe([P])` from C.
6. Assert: `earned(C, rewardToken) > 0` despite C's `userVotedForPoolInVlmgp[C][P]` having existed for 0 blocks prior to the reward provisioning, and assert B's realizable share (`earned(B, rewardToken)`) is lower than it would have been had C not diluted `totalStaked()` at the provisioning moment — confirming reward capture disproportionate to time-weighted contribution, per `_earned` in `BaseRewardPoolV2.sol:316-321`.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
