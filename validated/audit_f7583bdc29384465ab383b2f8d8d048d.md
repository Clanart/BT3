Based on the code paths examined, `getGitHubCredential`/`getCredential` do host-scope credential lookup by matching the requested endpoint against a stored `Account.endpoint`, so a stored GitHub.com/GHE token is only handed to git for the *same* endpoint it was issued for. However, this scoping happens at the moment git actually asks for credentials for whatever remote URL is currently configured — it does not protect against the remote URL itself having been silently changed to point somewhere the user never intended. If `updateRemoteUrl` rewrites `origin` to a new `https://` URL under the *same* GitHub/GHE host (e.g. because the API says the repo was renamed/transferred), then the very next `getCredential('get', ...)` call will legitimately resolve and hand over the account's real token for that host to the new URL — which may now point to a completely different repository (e.g., after a hostile rename/transfer) that the attacker controls.

### Title
Automatic, unconfirmed remote-URL rewrite on repository refresh can silently redirect pushes/credentials to an attacker-controlled repository - (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` is invoked on essentially every routine repository refresh (`repositoryWithRefreshedGitHubRepository`, called from focus refresh, background fetch, fetch/pull/push flows) with `apiRepo` data taken directly from a live GitHub API response for the currently tracked repository. If the conditions `protocolsMatch && remoteUrlUnchanged && !urlsMatch` are met, Desktop calls `gitStore.setRemoteURL(...)` and silently rewrites the user's `origin` remote to whatever `clone_url` the API returned — with no user prompt, diff, or confirmation of any kind.

### Finding Description [1](#0-0) 

The check only verifies that the **protocol** matches and that the **previously cached** clone URL (itself sourced from the same API) still matches the current remote — it never verifies that the new host/owner/name is one the user actually intended to keep working with (e.g. via an explicit consent dialog, as exists for `RepositorySettings` remote edits [2](#0-1) ). Anyone who controls the value returned for a tracked repo's `clone_url` — a compromised/malicious repository owner who renames/transfers the repo, or, more critically, an attacker positioned to alter the API response for a self-hosted GitHub Enterprise endpoint the user trusts — can steer this field to an arbitrary repository/host under the same scheme.

Once the remote URL is rewritten, the trampoline credential helper will legitimately hand over the user's real stored token for that host to the new URL on the next git operation, because credential lookup is scoped by endpoint/host, not by the specific owner/repo path: [5](#0-4) [6](#0-5) 

The corrupted value is the local `origin` remote URL (and the `IRemote` used for subsequent push/pull/fetch), which is overwritten without the "return old value / require explicit confirmation before replacing" safeguard that the report's smart-contract analog calls for.

### Impact Explanation
Because the rewrite happens automatically on background refresh/fetch/push cycles, a user who continues normal workflow after a hostile rename/transfer (or a compromised/MITM'd GHES API response) will have their next `git push` silently target the new remote. Their code (potentially private/proprietary) is pushed to a destination they didn't choose, and — because credential resolution is host-scoped rather than repo-scoped — this happens using the account's real token if the new URL happens to remain on the same host but different owner/repo, or exposes the token to a fully attacker-controlled host if the attacker can inject an arbitrary `clone_url` into the API response (e.g., via a compromised/spoofed GHES server). This matches the "silent corruption of what the user commits or pushes" / "credential exfiltration" impact classes in the given valid-impact list.

### Likelihood Explanation
Likelihood depends on the attacker's ability to control the `IAPIFullRepository.clone_url` returned for the tracked repository — straightforward for a malicious/compromised repo owner performing a rename or ownership transfer of a repo the victim has cloned, and plausible for a compromised or spoofed Enterprise Server endpoint (a "git remote/proxy response" scenario, per the accepted attacker model). No user interaction beyond normal, expected app usage (staying logged in, doing routine fetch/pull/push) is required, and there is no confirmation dialog whatsoever — unlike the manual `RepositorySettings` remote-editing flow, which does show the change to the user before applying it.

### Recommendation
Require explicit user confirmation before automatically rewriting an existing remote URL based on API data (surface a notice/dialog similar to the manual repository-settings flow), and/or scope the auto-update to only the owner/name segment while still validating the resulting host against a user-approved allowlist. At minimum, log/notify the user prominently when `origin`'s URL changes as a side effect of a background refresh, and consider re-scoping credential lookup to be repo-path aware rather than purely host-based so a redirected remote cannot silently reuse the previously issued token.

### Proof of Concept
1. Victim clones `https://github.com/owner/repo` (or an equivalent GHES-hosted repo) into Desktop and it becomes the tracked `origin` with a cached `gitHubRepository.cloneURL` equal to that URL.
2. Attacker (repo owner, or an entity able to influence the API response for that endpoint) renames/transfers the repository, or in the GHES case a malicious/compromised server response changes `clone_url` for the same `owner/name` lookup to `https://github.com/attacker/repo` (host/protocol still matching what `updateRemoteUrl` checks).
3. Victim performs any routine operation that triggers a repository refresh (app regains focus, background fetch, `git pull`, `git push`) — see `app/src/lib/stores/app-store.ts:4886-4907` and `5895-5899`.
4. `updateRemoteUrl` finds `protocolsMatch === true`, `remoteUrlUnchanged === true` (matches the old cached URL), `urlsMatch === false` (new URL differs), and calls `gitStore.setRemoteURL(...)` with **no prompt to the user**.
5. Victim's next `git push` (still believing they're pushing to the original repo) is silently redirected to the attacker's repository, and the trampoline credential helper transparently supplies the victim's stored account token for that host, per `trampoline-credential-helper.ts:50-57`/`182-193`.

Note: I could not execute this scenario live (no runtime/network access), so the exact triggering conditions for a compromised GHES endpoint (TLS/cert handling specifics) are inferred from static code review rather than confirmed via a running exploit; a Devin session with full repo/runtime access would be needed to validate end-to-end exploitability.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
