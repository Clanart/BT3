I've mapped the Truebit bug class (unchecked integer overflow bypassing a price/cost check) to Serai's in-scope code. In `SignableTransaction::new`, several `u64` additions on attacker-influenced amounts are unchecked, mirroring the "one unguarded addition" pattern.

Key code in `networks/bitcoin/src/wallet/send.rs`:

- `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` (line 187) — unchecked sum, wraps mod 2^64.
- `if input_sat < (payment_sat + needed_fee)` (line 215) — unchecked addition; if `payment_sat + needed_fee` wraps below `input_sat`, the `NotEnoughFunds` guard is bypassed.
- `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228) — `checked_sub` guards the subtraction but the inner `payment_sat + fee_with_change` is still a plain unchecked `+` that wraps before the check.
- `fee_per_vbyte * vbytes` (lines 206, 227) — unchecked multiplication.
- `fee()` (line 139) — `sum(inputs) - sum(outputs)` underflows/panics when outputs exceed inputs, i.e. precisely the state the overflow above permits.

An unprivileged party who can cause payments to be scheduled (a withdrawal request flows through `Bitcoin::make_signable_transaction` → `BSignableTransaction::new` in `processor/src/networks/bitcoin.rs:446`) supplies the `(ScriptBuf, u64)` payment amounts — public transaction data, within the allowed reach. Payment amounts near `u64::MAX` were never possible in Truebit-style "reasonable input" assumptions, exactly like the exploit.

### Title
Unchecked u64 overflow in payment/fee sums bypasses `NotEnoughFunds`, causing the threshold multisig to sign a consensus-invalid transaction — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` computes `payment_sat` and the `payment_sat + needed_fee` / `payment_sat + fee_with_change` sums with plain wrapping `u64` arithmetic. Rust release builds wrap silently, so a payment amount near `u64::MAX` makes the sufficiency check `input_sat < payment_sat + needed_fee` wrap to a small value and pass even though the payment vastly exceeds all inputs. The resulting `SignableTransaction` is then threshold-signed by `TransactionMachine`, producing a FROST-authorized Bitcoin transaction whose outputs exceed its inputs.

### Finding Description
- `send.rs:187`: `payment_sat` is `sum::<u64>()` over caller-influenced amounts; multiple large payments wrap the sum.
- `send.rs:215`: `input_sat < (payment_sat + needed_fee)` — the addition overflows for `payment_sat > u64::MAX - needed_fee`, wrapping to near-zero so the `NotEnoughFunds` error is skipped.
- `send.rs:228`: `input_sat.checked_sub(payment_sat + fee_with_change)` — the inner addition wraps first; the `checked_sub` then succeeds and yields a change output consuming almost all input value while a payment of ~2^64 sats is emitted.
- `send.rs:139`: `fee()` subtracts `sum(outputs)` from `sum(inputs)` with plain `-`; with the overflowed state this underflows and panics, or reports a nonsensical fee.
- `send.rs:206,227`: `fee_per_vbyte * vbytes` unchecked multiplication (secondary; fee is node-derived).

### Impact Explanation
The multisig signs a transaction the Bitcoin network will reject (outputs > inputs), i.e. a signature over an unintended, consensus-invalid message. Any honest signer calling `fee()` on the resulting `SignableTransaction` panics on underflow (liveness DoS of the signing path), and the invalid transaction stalls the payment queue until it is cleared. This is the same shape as Truebit: one unguarded addition lets an absurd input evade a solvency check.

### Likelihood Explanation
Payment amounts originate from withdrawal/scheduling requests — public input — and no bound below `u64::MAX` is enforced inside `SignableTransaction::new` before the wrapping arithmetic (only the wrapped comparison is performed). Reaching it requires scheduling a large payment (e.g., a dust-bypassing branch output or malformed plan); feasibility depends on upstream balance checks, but the wallet crate itself is the solvency enforcement point and fails open here. Severity Medium: provable signing of an invalid message plus deterministic panic in `fee()`, but no direct theft since consensus rejects the overspend.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`: `checked_sum`/`fold` for `payment_sat` and `input_sat`, `checked_add` for `payment_sat + needed_fee` and `payment_sat + fee_with_change` (returning `NotEnoughFunds`/`TooLargeTransaction` on overflow), `checked_mul` for `fee_per_vbyte * vbytes`, and `checked_sub` in `fee()`. Reject individual payment amounts exceeding Bitcoin's `MAX_MONEY` (21M BTC in sats) up front.
