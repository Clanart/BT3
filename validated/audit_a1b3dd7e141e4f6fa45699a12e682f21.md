### Title
Spent same-block Bitcoin outputs remain reported as spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` reports a `ReceivedOutput` for every transaction output matching a registered script, but never removes outputs spent by later transactions in the same block. An unprivileged sender can place a funding transaction and a child transaction spending that funding output in one block, causing Serai to report funds as received even though the resulting outpoint is no longer spendable.

### Finding Description
`Scanner::scan_transaction` iterates only over `tx.output`, checks `output.script_pubkey`, and constructs a `ReceivedOutput` from the transaction ID and output index. [1](#0-0)  `Scanner::scan_block` simply concatenates these results for every transaction and does not inspect `tx.input` or maintain a set of outpoints consumed during the block. [2](#0-1)  This is significant because `ReceivedOutput` is explicitly documented as “a spendable output,” yet the scanner can return an outpoint that was spent in a later transaction of the same block. [3](#0-2) 

### Impact Explanation
An attacker can cause the scanner to report a received Bitcoin output that cannot be spent because a same-block child transaction already consumed it. Downstream accounting or deposit crediting based on `scan_block` results can therefore treat unavailable funds as available, matching the reported class where state representing owned funds is credited but not corrected when those funds are removed.

### Likelihood Explanation
Bitcoin transaction ordering permits a transaction to spend an output created by an earlier transaction in the same block. The attacker only needs to publish an ordinary funding transaction paying a scanned P2TR script and a valid child transaction spending that output to an unrelated destination; no validator compromise, malformed curve encoding, or privileged input is required.

### Recommendation
Track scanned outpoints while processing each block and remove any scanned outpoint that appears as `input.previous_output` in a later transaction. Alternatively, document and enforce that `scan_block` results are only candidate receipts and must be filtered against all inputs in the block before being considered spendable. The result should be indexed by transaction order and should also consider duplicate output detection before reporting receipts.

### Proof of Concept
1. Initialize `Scanner::new(multisig_key)` and obtain its base P2TR script through `p2tr_script_buf`; `Scanner::new` registers this script with offset zero. [4](#0-3) 
2. Broadcast transaction `funding_tx` with `output[0].script_pubkey` equal to that P2TR script.
3. In the same block, broadcast valid transaction `spend_tx` whose `input[0].previous_output` is `OutPoint { txid: funding_tx.compute_txid(), vout: 0 }` and whose output pays an attacker-controlled address.
4. Call `scanner.scan_block(&block)`. The funding transaction causes `scan_transaction` to append `ReceivedOutput { outpoint: funding_tx:0, ... }` because the script matches. [5](#0-4) 
5. The subsequent `spend_tx` is scanned only for its outputs; its input is ignored, so the already-spent `funding_tx:0` remains in the returned vector. [6](#0-5)
