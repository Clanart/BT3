### Title
Hookify legacy-pattern `block` rules silently no-op on `Write` tool content, permanently bypassing the block gate for the exact data they were meant to inspect - (File: `plugins/hookify/core/config_loader.py`)

### Summary
The `hookify` plugin's legacy `pattern:` rule format infers a single hard-coded field name (`new_text`) for every `event: file` rule in `Rule.from_dict()` (`plugins/hookify/core/config_loader.py:56-73`), regardless of which tool (`Write`, `Edit`, `MultiEdit`) ultimately triggers it. The `RuleEngine._extract_field()` resolver (`plugins/hookify/core/rule_engine.py:235-244`) maps `field == 'new_text'` to `tool_input.get('new_string', '')` only — a key that exists on `Edit`/`MultiEdit` inputs but never on `Write` inputs (which carry the payload in `content`). This is directly analogous to the ZetaChain Solana bug: a security-relevant target/value is defined in one format/field by the author of the rule, but the enforcement path reads a structurally different field, so the check silently evaluates against the wrong (empty) data and the intended protection never fires.

### Finding Description
When a user (or plugin/marketplace-shipped rule) authors a legacy-style hookify block rule such as:
```markdown
---
name: block-secret-write
enabled: true
event: file
action: block
pattern: (API_KEY|SECRET|TOKEN)\s*=\s*["']
---
Blocking write of hardcoded credential.
```
`Rule.from_dict()` unconditionally infers `field = 'new_text'` for any `event == 'file'` rule (`plugins/hookify/core/config_loader.py:64-65`), with no distinction between `Write`, `Edit`, and `MultiEdit`, which use different `tool_input` key names for the new content (`content` for `Write`, `new_string` for `Edit`/`MultiEdit`).

At evaluation time, `RuleEngine._extract_field()` is called with this `field='new_text'` and the actual `tool_name`. For `tool_name == 'Write'` it falls into the `elif tool_name in ['Write', 'Edit']:` branch (`plugins/hookify/core/rule_engine.py:235`) and, because the field equals `'new_text'`, returns `tool_input.get('new_string', '')` (`rule_engine.py:239-240`). Since `Write` tool calls never populate `new_string` (they populate `content`), this always returns the empty string `''` rather than `None`.

Because the returned value is `''` and not `None`, `_check_condition()` does **not** short-circuit on the `field_value is None` check (`rule_engine.py:159-160`); instead it proceeds to run the regex/contains/etc. match against an empty string, which can never match the rule's `pattern`. The block condition therefore always evaluates to `False` for every `Write` tool call, and `_rule_matches()` returns `False` (`rule_engine.py:121-123`), so the rule's `action: block` is never enforced — with no error, warning, or any signal to the user that the intended check is a no-op.

The rule silently protects only `Edit`/`MultiEdit` operations while being completely inert for `Write` operations, even though the rule's author intended it to guard "file" events generically. This mirrors the ZetaChain root cause exactly: a control that is defined against one representation of the target (a Pubkey / a `new_string`-shaped payload) is enforced against a different representation used by another code path (an EVM address / a `content`-shaped payload), and the mismatch is invisible until exploited.

### Impact Explanation
`hookify` is explicitly a security/policy-enforcement mechanism — its documented purpose (`plugins/hookify/README.md`, `plugins/hookify/skills/writing-rules/SKILL.md`) is to let users author `PreToolUse` rules with `action: block` to prevent dangerous writes (hardcoded secrets, `.env` edits, credential leakage, dangerous code patterns, etc.). Because Claude Code's own agent decides whether to use `Write` vs `Edit` for a given file operation, an attacker-influenced or model-driven action that creates a new file via `Write` (instead of editing an existing one via `Edit`) will bypass any legacy-style `event: file` block rule targeting file content. This is a full, silent defeat of a locally-configured safety control (`--dangerously-skip-permissions`-adjacent guarantee: the rule author believes dangerous writes are blocked; in practice they are never blocked for `Write`), enabling unauthorized write of sensitive/prohibited content that the user explicitly attempted to fence off.

### Likelihood Explanation
This triggers on the default/legacy rule authoring format that the plugin's own `SKILL.md` and `hookify.md` command scaffolding present as the simple/first-class way to write rules (`pattern:` + `event: file`), with the more precise multi-condition (`conditions: [{field: ...}]`) syntax presented as the "advanced" alternative. Any user who follows the basic documented workflow to add a `block` rule for file writes is affected without any special attacker action required — the bypass fires deterministically any time the guarded content arrives via the `Write` tool rather than `Edit`.

### Recommendation
In `Rule.from_dict()` (`plugins/hookify/core/config_loader.py`), stop inferring a single static field name for `event: file`; either emit multiple conditions covering all tool-specific payload fields (`content` for `Write`, `new_string`/`old_string` for `Edit`, and the `edits[].new_string` shape for `MultiEdit`) combined with OR semantics, or resolve the field dynamically per-tool at evaluation time in `_extract_field()` instead of trusting a single field name computed at load time. Additionally, `_extract_field()` should distinguish "field not applicable to this tool" (return `None`) from "field applicable but empty" (return `''`), so `_check_condition()` can correctly treat the former as non-matching in a way that surfaces the config problem (e.g., via a debug/warning log) rather than being indistinguishable from legitimate non-matching content.

### Proof of Concept
1. Create `.claude/hookify.block-secret.local.md`:
```markdown
---
name: block-secret-write
enabled: true
event: file
action: block
pattern: SECRET_KEY\s*=
---
Blocking hardcoded secret.
```
2. Ask Claude Code to create a **new** file containing `SECRET_KEY = "abc123"` — it will use the `Write` tool. Hookify's `PreToolUse` hook (`plugins/hookify/hooks/pretooluse.py`) loads the rule, `RuleEngine._extract_field('new_text', 'Write', {'file_path':..., 'content': 'SECRET_KEY = "abc123"'})` returns `''` (via the `new_string` lookup), the regex never matches, and the write proceeds unblocked.
3. Ask Claude Code to **edit** an existing file to insert the same string via `Edit` — the identical rule now correctly matches `new_string` and blocks it, confirming the field-mapping mismatch is the sole cause of the bypass and is tool-path dependent rather than content dependent.     def _check_condition(self, condition: Condition, tool_name: str,
```python
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
```
