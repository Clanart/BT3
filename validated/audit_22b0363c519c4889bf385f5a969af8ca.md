### Title
Malformed/overshadowed `OP_RETURN` causes Serai deposit instruction data to be silently dropped, stranding received funds - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Analogous to `printenv` silently skipping environment entries it cannot decode, `Bitcoin::extract_serai_data` silently discards the Serai instruction payload attached to a deposit transaction whenever the `OP_RETURN` output fails *minimal* instruction parsing or the last instruction is not a data push. The associated P2TR output is still credited by `get_outputs`/`Scanner::scan_transaction`, but with empty `data`, so the deposit is reported received while the instruction it carried is irrecoverably lost.

### Finding Description
`get_outputs` scans each non-coinbase transaction with `Scanner::scan_transaction`, which matches purely on `script_pubkey` and returns a `ReceivedOutput` for every matching output regardless of what the rest of the transaction looks like [1](#0-0) . Separately, `extract_serai_data` extracts the instruction data by taking `instructions_minimal().last()` of the *last instruction* of each `OP_RETURN` output and returns on the first `PushBytes` it sees, `continue`-ing past anything else [2](#0-1) . Three silent-skip conditions exist:

1. Any non-minimally-encoded push anywhere in the `OP_RETURN` script makes `instructions_minimal()` yield `Err`, so `last()` returns `Some(Err(..))` and the `_ => continue` arm drops the whole output [3](#0-2) .
2. Any trailing non-push opcode (e.g. `OP_RETURN <data> OP_NOP`) makes `last()` a non-`PushBytes` instruction, dropping the output even though a perfectly valid data push precedes it.
3. A preceding `OP_RETURN` whose last instruction *is* a push causes early `return`, so a second `OP_RETURN` carrying the real instruction is never examined.

The fallback witness path has the same shape: `segwit_data_pattern` uses `ins.next()?.ok()?`, so any instruction-decoding failure makes it return `None` and the input is silently skipped [4](#0-3) . In every case the extracted data is empty, and `get_outputs` then emits the `Output` normally with `data: vec![]` [5](#0-4) . There is no error, no rejection path, and no log distinguishing "no data" from "data failed to parse" — identical to the advisory's pattern of malformed content evading inspection rather than being surfaced.

### Impact Explanation
An unprivileged depositor (or anyone constructing a transaction paying a Serai address) can produce a consensus-valid transaction whose instruction payload is dropped by the parser. The Bitcoin output is scanned, marked seen, and reported to the protocol as received funds [6](#0-5) , but the `InInstruction`/metadata that determines how the deposit is routed or credited is gone. The result is funds reported received that the owner cannot claim or direct — value is locked under the multisig key with no associated instruction. This also lets a sender craft deposits whose attached data evades any inspection/attribution logic operating on `Output::data()`, since malformed framing yields empty data rather than a visible anomaly. Reachable entirely with public inputs (a self-created Bitcoin transaction), so it satisfies the medium-severity bar for loss of funds via silent input dropping.

### Likelihood Explanation
The trigger is trivial: any transaction template or wallet that emits a multi-part `OP_RETURN`, a non-minimal `PUSHDATA`, or a trailing opcode produces it accidentally, and an attacker can craft it deliberately to burn or mis-attribute deposits. No privileged position, collusion, or malformed chain data is required — only control of the deposit transaction. Likelihood is moderate because correctly-formed Serai tooling emits the expected single-push `OP_RETURN`.

### Recommendation
Treat unparseable framing as an error rather than empty data:
- In `extract_serai_data`, iterate `instructions_minimal()` over the whole script and either accept the first `PushBytes` payload anywhere in the `OP_RETURN` (not only the last instruction) or explicitly reject/log scripts containing non-push instructions or `Err` items.
- Reject (or log at `warn`/`error` and mark) transactions where an `OP_RETURN` output exists but yields `Err` from the minimal-instruction iterator, instead of falling through to `continue`.
- Apply the same treatment to the witness path: distinguish "pattern absent" (`None`) from "pattern present but malformed" in `segwit_data_pattern`, and surface the latter.
- Consider making `get_outputs` emit outputs with an explicit "data parse failure" marker so downstream processors can quarantine rather than silently credit unattributed deposits.

### Proof of Concept
Conceptual transaction a user/attacker can broadcast:

```
Inputs:  any spendable input
Outputs:
  vout 0: P2TR to Serai deposit address (matches Scanner.scripts, e.g. offset ZERO)
  vout 1: OP_RETURN script:  OP_RETURN PUSHDATA(<valid InInstruction bytes>) OP_NOP
          # or equivalently: OP_RETURN PUSHDATA1(1-byte push of the same data)  (non-minimal)
```

`Scanner::scan_transaction` returns the vout-0 `ReceivedOutput` [7](#0-6) . `extract_serai_data` then evaluates the `OP_RETURN` script: `instructions_minimal().last()` yields `Instruction::Op(OP_NOP)` (or `Err` for the non-minimal push), hits `_ => continue`, finds no other `OP_RETURN`, and returns `vec![]` [8](#0-7) . `get_outputs` emits `Output { kind: External, output: <received output>, data: [] }` [9](#0-8) , the scanner marks the outpoint seen [10](#0-9) , and the deposit is credited with no instruction attached — the encoded data was present on-chain yet silently skipped, exactly paralleling `printenv` omitting unparseable environment entries.

One caveat I could not fully verify within scope: whether an empty `data` on an `External` output ultimately makes the deposit permanently unrecoverable versus merely mis-attributed depends on downstream processor logic outside the listed in-scope files. The silent-drop behavior itself and the credited-but-instructionless output are confirmed in the cited code.

  fn segwit_data_pattern(script: &ScriptBuf) -> Option<bool> {
    let mut ins = script.instructions();

    // first item should be SHA256 code
    if ins.next()?.ok()?.opcode()? != OP_SHA256 {
      return Some(false);
    }

    // next should be a data push
    ins.next()?.ok()?.push_bytes()?;

    // next should be a equality check
    if ins.next()?.ok()?.opcode()? != OP_EQUALVERIFY {
      return Some(false);
    }

    Some(true)
  }
