## Finding confirmed [1](#0-0) 

### Title
Missing `_filled[commitment]` check in `_cancelFromDest` allows destination-side cancellation of an already-filled order, corrupting settlement state and enabling solver fund loss - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` never checks whether `_filled[commitment]` is already non-zero (i.e., that the order was already settled by `_fillCrossChain`) before overwriting it and dispatching a `RefundEscrow` message. Combined with the post-deadline bypass of the caller-authorization check, any unprivileged address can trigger this once `order.deadline < _blockNumber()`, even for an order that a solver has already legitimately filled.

### Finding Description
`_fillCrossChain` sets `_filled[commitment] = msg.sender` (the solver) and dispatches a `RedeemEscrow` `WithdrawalRequest` to the source chain: [2](#0-1) [3](#0-2) 

`_cancelFromDest` only gates the caller with `order.user` when `order.deadline >= _blockNumber()`; once the deadline has passed, anyone may call it. It then unconditionally overwrites `_filled[commitment] = order.user` and dispatches a `RefundEscrow` request, with no check that `_filled[commitment]` is already set to a solver address: [4](#0-3) 

Both `RedeemEscrow` and `RefundEscrow` messages funnel into `_withdraw` on the source chain via `onAccept`: [5](#0-4) 

`_withdraw` decrements `_orders[commitment][token]` and reverts with `UnknownOrder` once the escrow balance for that token is already zero: [6](#0-5) 

This means the *second* message to arrive on the source chain will revert (not double-pay), but *whichever message arrives first wins the race* and finalizes the escrow to its own beneficiary. Because `_fillCrossChain` already transferred the output tokens to the beneficiary on the destination chain *before* dispatching `RedeemEscrow` (solver has already paid out), if the competing `RefundEscrow` (triggered permissionlessly via `_cancelFromDest`) is processed first on the source chain, the escrowed input tokens go back to `order.user` and the solver's legitimate `RedeemEscrow` request later reverts with `UnknownOrder`, permanently denying the solver reimbursement for tokens it already delivered.

### Impact Explanation
This breaks the one-time settlement invariant: `_filled[commitment]` is silently overwritten from the solver's address to `order.user`, and two conflicting `WithdrawalRequest` messages (`RedeemEscrow` and `RefundEscrow`) are put in flight for the same commitment/escrow. Depending on message delivery order (a race not controlled or prevented by the contract), the solver can lose the funds they already delivered on the destination chain while the order's `user` receives the escrow refund — a genuine loss-of-funds / wrongful-beneficiary outcome triggered entirely by an unprivileged, permissionless call.

### Likelihood Explanation
Exploitability requires the attacker (which can simply be the order's own user, an unprivileged party) to invoke `_cancelFromDest` after the deadline has passed but such that the resulting `RefundEscrow` message reaches and is processed on the source chain before the solver's already-dispatched `RedeemEscrow` message. Since Hyperbridge cross-chain delivery/proof timing is attacker-observable and not synchronized between the two dispatches, a user who is also willing to act as (or collude with) a filler, or who simply calls `_cancelFromDest` immediately after a fill lands, has a realistic opportunity to win this race.

### Recommendation
`_cancelFromDest` (and ideally `_fillCrossChain`) should check `_filled[commitment] == address(0)` before proceeding, reverting with `Filled()` if the order has already been finalized by a fill (mirroring the existing `Filled` guard used elsewhere in the codebase, e.g. in `onGetResponse`). This closes the window where a permissionless post-deadline cancel can race an already-dispatched redeem.

### Proof of Concept
1. Solver calls `fillOrder` → `_fillCrossChain` for `order` with `order.deadline` already `< _blockNumber()` (or right at expiry) — sets `_filled[commitment] = solver` and dispatches `RedeemEscrow(commitment, order.inputs, solver)` to `order.source`.
2. Immediately, any unprivileged address calls `cancel`/`_cancelFromDest` with the same `order`/`commitment` — since `order.deadline < _blockNumber()`, the `msg.sender == order.user` check is skipped; it sets `_filled[commitment] = order.user` and dispatches `RefundEscrow(commitment, order.inputs, order.user)` to `order.source`.
3. If the `RefundEscrow` message is relayed/processed on the source chain before the `RedeemEscrow` message, `_withdraw` finalizes the refund to `order.user`, zeroing `_orders[commitment][token]`.
4. When the solver's `RedeemEscrow` message is later processed, `_withdraw` reverts with `UnknownOrder()` — the solver, who already transferred output tokens to the beneficiary in step 1, never receives the escrowed input tokens back.

Note: I was unable to fully verify (tool budget exhausted) whether the public entry point wrapping `_fillCrossChain` in `evm/src/apps/IntentGatewayV2.sol` imposes its own pre-deadline check that would prevent step 1 from occurring after `order.deadline`. Even if fills are normally restricted to before the deadline, the same race is exploitable in the narrow window where a fill transaction is mined at/just before the deadline while its `RedeemEscrow` message is still in flight, and `_cancelFromDest` becomes callable by anyone the instant the deadline block is reached.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
