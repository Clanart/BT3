## Analog Found: Cross-Session Account Confusion in `SignInStore` OAuth Callback Race

The CometBFT bug is a "late response gets delivered to the wrong/reused waiter" race: a shared response slot (`reqRes`) is torn down and reassigned while an async wait is still in flight, so a stale in-flight completion can be misrouted. The Desktop analog is in `SignInStore`'s browser-based OAuth flow, where the "waiter" (`oauthState.onAuthCompleted`/`onAuthError`) is stored on `this.state` and can be silently overwritten by a second `authenticateWithBrowser()` call while an earlier `resolveOAuthRequest()` is still awaiting a network round-trip.

### Title
Race condition in `SignInStore.resolveOAuthRequest` allows a stale/attacker-influenced OAuth completion to be delivered to a different, concurrently-started sign-in session - ([File: app/src/lib/stores/sign-in-store.ts])

### Summary
`authenticateWithBrowser()` creates a per-invocation `Promise<Account>` and stashes its `resolve`/`reject` closures as `oauthState.onAuthCompleted`/`onAuthError` on the mutable `this.state` object [1](#0-0) . `resolveOAuthRequest()`, invoked from the deep-link handler when the OS delivers an `x-github-client://oauth?code=...&state=...` callback [2](#0-1) , validates the CSRF `state` against the request that is current *at call time*, then performs two awaited network calls (`requestOAuthToken`, `fetchUser`) before finally re-reading `this.state.oauthState` to invoke the completion callback: [3](#0-2) 

Because `this.state.oauthState` is read *after* the await, and not the specific `oauthState` object that was validated against `action.state` before the await, a second, unrelated `authenticateWithBrowser()` call that overwrites `this.state` in the meantime (which happens by direct `setState()`, with no rejection or cancellation of the earlier in-flight `oauthState`) causes the first flow's fetched `Account` to be delivered to the second flow's `resolve` function.

### Finding Description
1. User (or the app) calls `authenticateWithBrowser()` for flow #1 against endpoint A. This sets `this.state.oauthState = { state: csrfToken1, endpoint: A, onAuthCompleted: resolve1, onAuthError: reject1 }` and opens the browser [4](#0-3) .
2. The OS delivers the deep link for flow #1 (`code1`, `state=csrfToken1`). `resolveOAuthRequest` validates `state` against the *current* `this.state.oauthState.state` (still `csrfToken1`, so it passes) and starts `await requestOAuthToken(...)` / `await fetchUser(...)` [5](#0-4) . Because endpoint A can be an attacker-controlled/enterprise-configurable endpoint, or its HTTP responses can simply be slow/adversarially delayed, this window can be arbitrarily widened by the attacker.
3. Before that resolves, `authenticateWithBrowser()` is invoked a second time while the store is still in the `Authentication` step (e.g. the user or UI re-triggers "Continue with browser", or an Enterprise-sign-in-then-dotcom-sign-in sequence lands back in `Authentication`). This path does **not** call `reset()` — it directly overwrites `this.state` with a brand-new `oauthState` (`csrfToken2`, `resolve2`, `reject2`) for endpoint B [6](#0-5) . Note: `reset()` (called by `beginDotComSignIn`/`beginEnterpriseSignIn`) *does* explicitly call `currentState.oauthState?.onAuthError(...)` on the outgoing state [7](#0-6) , but `authenticateWithBrowser` bypasses that teardown entirely.
4. Flow #1's `resolveOAuthRequest` finally resolves its awaits and executes `this.state.oauthState.onAuthCompleted(account)` — but `this.state.oauthState` now belongs to flow #2, so **flow #2's `resolve2` is invoked with the Account object fetched from endpoint A** using flow #1's authorization code.
5. Flow #2's `.then()` handler in `authenticateWithBrowser` checks only `this.state.kind === SignInStep.Authentication` (still true) — not whether the resolved account actually corresponds to the endpoint/csrfToken of flow #2 — and proceeds to `emitAuthenticate(account)` and transitions to `Success` [8](#0-7) . `emitAuthenticate` fires `did-authenticate` and invokes `resultCallback({ kind: 'success', account })` [9](#0-8) , which is consumed by the app to add the account to `AccountsStore` and treat the user as signed in.

The corrupted value is the `Account` object bound to flow #2's `resultCallback`/`did-authenticate` event: it is the account resolved via flow #1's endpoint/token exchange, not one verified against flow #2's own CSRF `state`/endpoint. The existing guard — the `oauthState.state !== action.state` check — only protects against a forged/replayed deep link at the moment `resolveOAuthRequest` starts; it does nothing to ensure the *same* `oauthState` object is still current when the callback finally fires after the awaited network calls.

### Impact Explanation
This is an "unauthorized OAuth or account binding" issue: a user who believes they are completing sign-in to one endpoint (e.g., github.com) can have their session silently bound to an `Account` object retrieved via a *different*, potentially attacker-influenced endpoint or code-exchange response, without any CSRF-state mismatch being detected (the state check happens before the race window, not after). Depending on how the caller's `resultCallback`/`did-authenticate` consumer trusts the returned `Account`, this can result in the wrong account being persisted to `AccountsStore` and used for subsequent Git/API operations under the user's Desktop session — i.e., silent account substitution driven entirely by response timing rather than by the state token the user actually approved.

### Likelihood Explanation
Triggering requires: (a) a sign-in flow in flight whose token/user-fetch response can be slowed or is naturally slow (fully controllable if the target endpoint is a GitHub Enterprise instance under attacker influence, or simply exploitable opportunistically over a slow/lossy network), and (b) a second `authenticateWithBrowser()` invocation landing while the store is still in `SignInStep.Authentication` before the first resolves. The second condition is plausible via ordinary UI retry actions or via a combined Enterprise→dotcom sign-in sequence, but it does need a specific timing window and a caller-driven second attempt, so likelihood is moderate rather than trivially exploitable by a purely passive external attacker.

### Recommendation
Capture the specific `oauthState` object (or at minimum its `state` token and `resolve`/`reject` closures) in a local variable at the top of `resolveOAuthRequest` before the `await`s, and use that captured reference — not `this.state.oauthState` — when invoking `onAuthCompleted`/`onAuthError` after the awaits. Additionally, have `authenticateWithBrowser` explicitly invalidate (reject) any pre-existing `oauthState` before installing a new one, the same way `reset()` already does, so a superseded flow's in-flight callback cannot be mistaken for the new flow's callback.

### Proof of Concept
1. User selects "Sign in to GitHub Enterprise", enters an attacker-influenced/slow endpoint A, and clicks "Continue with browser" → `authenticateWithBrowser()` sets `oauthState` with `csrfToken1`/`resolve1` for endpoint A.
2. The deep link `x-github-client://oauth?code=CODE1&state=csrfToken1` arrives; `resolveOAuthRequest` passes the state check and begins `requestOAuthToken`/`fetchUser` against endpoint A, which the attacker delays (e.g., slow HTTP response).
3. While step 2 is pending, the user (or app flow) invokes `authenticateWithBrowser()` again for legitimate endpoint B (github.com) — `this.state.oauthState` is overwritten with `csrfToken2`/`resolve2`, no rejection of the previous state occurs.
4. Endpoint A's delayed response arrives; `resolveOAuthRequest`'s `this.state.oauthState.onAuthCompleted(account)` fires `resolve2` with the Account fetched from endpoint A.
5. Flow #2's `.then()` executes `emitAuthenticate(accountFromA)` and transitions to `Success`, even though the user never completed a valid OAuth round-trip for endpoint B with a code the app itself verified end-to-end against `csrfToken2`.

```typescript
  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
```
