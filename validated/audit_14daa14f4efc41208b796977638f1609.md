### Title
`SignableTransaction::new` underestimates the transaction fee when an OP_RETURN data output is present — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class in the external report is "the caller supplies more value than is forwarded/needed, and the remainder is mishandled." The Serai analog lives in `SignableTransaction::new`: when a `data` payload is supplied, an OP_RETURN output is appended to `tx_outs`, but the fee is computed via `calculate_weight_vbytes(tx_ins.len(), payments, ...)` which rebuilds the transaction **only from `payments`** — the OP_RETURN output (up to ~80 bytes of data plus script/amount overhead) is never included in the weight/vbytes used to compute `needed_fee`.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
``` [1](#0-0) 

`calculate_weight_vbytes` constructs the measurement transaction from `payments` alone, so the data output contributes zero weight to `vbytes`: [2](#0-1) 

The same omission occurs on the change path (`fee_with_change` at lines 224–234). Consequently `needed_fee` is underestimated by roughly `fee_per_vbyte * (9 + 1 + len(data) + push overhead)` vbytes — up to ~`fee_per_vbyte * 95` satoshis.

### Impact Explanation
Two concrete harms, both reachable by an unprivileged caller passing `data` to `SignableTransaction::new`:

1. **Actual fee rate below the intended rate.** The real fee is `sum(inputs) - sum(outputs)` (`fee()`, lines 138–141). With a change output, the change value is computed as `input_sat - payment_sat - fee_with_change`, so the *actual* paid fee equals the underestimated `needed_fee` spread over a transaction that is larger than measured. The effective sat/vbyte is strictly less than `fee_per_vbyte`. For boundary values the real fee can fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check (line 211, itself computed on the underestimated `vbytes`) passed — producing a transaction that will not relay/confirm and whose inputs are effectively locked until replaced.

2. **`needed_fee` does not reflect the true required fee**, corrupting any caller that relies on it for accounting (e.g., `processor`'s `needed_fee`/`prepare_send` amortization path, which subtracts `tx_fee` from payments and computes expected change assuming the estimate is exact).

This mirrors the report's pattern: the amount of value committed to the operation does not match what the operation actually requires/consumes, silently breaking downstream assumptions.

### Likelihood Explanation
Any user of `SignableTransaction::new` with `data: Some(..)` (an explicitly supported, public feature — OP_RETURN data up to 80 bytes is accepted at lines 171–173 and 194–202) triggers the underestimation deterministically. Whether it causes a non-relayable transaction depends on how close `fee_per_vbyte` is to the minimum, but the accounting discrepancy (reported `needed_fee` ≠ economically correct fee) occurs every time `data` is used.

### Recommendation
Include the data/OP_RETURN output in the weight calculation. Either pass the fully-built `tx_outs` into `calculate_weight_vbytes` (i.e., measure the actual transaction being constructed), or add the data output to the payment list used for measurement before computing `vbytes`. Apply the same fix to the `fee_with_change` computation so the change path also accounts for the OP_RETURN output.

### Proof of Concept
```rust
// Conceptual: for any inputs/payments/fee_per_vbyte where a tx succeeds,
let without_data = SignableTransaction::new(inputs.clone(), payments, change.clone(), None, f).unwrap();
let with_data    = SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), f).unwrap();

// needed_fee is identical even though the second tx is ~90 vbytes larger:
assert_eq!(without_data.needed_fee(), with_data.needed_fee()); // BUG: should be larger

// Effective fee rate of with_data is < f sats/vbyte:
//   actual fee = with_data.fee() == needed_fee
//   actual vsize > vbytes used in the calculation
```
Tracing the code: `data` pushes an extra `TxOut` into `tx_outs` (send.rs:194–202), then `calculate_weight_vbytes` is invoked with `payments` (send.rs:204) which only maps `payments` into `tx.output` (send.rs:85–93) — the OP_RETURN output is absent from the measured transaction, so `vbytes` and hence `needed_fee` exclude it.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
