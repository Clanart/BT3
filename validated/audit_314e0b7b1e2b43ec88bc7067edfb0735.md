### Title
`convert_to_balance` truncating division zeroes out minted balance for cross-chain fungible token transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler converts an incoming ERC-20 `U256` amount into a local Substrate balance by naive integer division, with no check that the result is non-zero before minting/transferring. This is the direct local analog of the H-05 `IdleYieldSource` bug: division without mantissa/precision-safe handling can truncate a real, non-zero deposit down to `0`, silently destroying bridged value while the source-chain leg of the transfer has already been consumed.

### Finding Description
`convert_to_balance` scales an ERC-20 amount down to local decimals via plain integer division: [1](#0-0) 

`on_accept` calls this to compute `amount` and then unconditionally mints/transfers it to the beneficiary, with no `amount == 0` guard: [2](#0-1) 

When `erc_decimals` is large relative to `decimals` (e.g. an 18-decimal ERC-20 token bridged to a 6- or 10-decimal local asset), the divisor `10^(erc_decimals - local_decimals)` can exceed the raw `message.amount` for small-but-real transfers, so the division truncates to `0`. `mint_into`/`transfer` are then called with `amount = 0`, which in `pallet-assets`/`Currency` succeeds as a no-op (there is no `EnsureNonZero` style check anywhere in this path). The result: the beneficiary is credited nothing, yet the corresponding value was already locked/burned on the EVM source side before the message was dispatched (the EVM `HyperFungibleToken` contract escrows/burns tokens prior to sending the `Message`), so the value is permanently lost from the user's perspective — it is not automatically refunded, because from the protocol's point of view the message was successfully processed (`on_accept` returned `Ok`, so no `on_timeout` refund path is ever triggered).

The same unguarded division pattern also exists in the `on_timeout` refund path: [3](#0-2) 

Both call sites depend entirely on caller-controlled decimals configuration (`Precisions::<T>::get`) and message content (`message.amount`), both of which originate from an unprivileged relayer delivering a proven cross-chain message — no admin, malicious peer, or governance action is required, only a normal small-value transfer through a token pair with a large decimals gap.

### Impact Explanation
This is a genuine "false state acceptance / loss of funds" bug within the Impact Gate: a legitimate on-chain deposit that already moved real value out of user custody on the source chain results in the destination-chain beneficiary receiving **zero** tokens, with the request marked successfully accepted (no timeout/refund triggered). This is unauthorized loss of user funds through normal, permissionless bridge usage — exactly the class of bug the original report describes (mantissa-less division zeroing shares/tokens on deposit).

### Likelihood Explanation
Likelihood depends on the deployed decimals configuration for a given `(local_asset_id, source contract)` pair, tracked in `Precisions::<T>`. If any bridged asset pair has `erc_decimals - local_decimals` large (a plausible real-world configuration, e.g. bridging an 18-decimal token to a 6-decimal local asset, a 12-decimal gap = divisor `1e12`), any transfer with a raw `message.amount < 10^gap` (which is still a genuine non-dust amount in the source token's own decimals, e.g. anything under roughly `1e-6` of a token at 18 decimals) truncates to zero. This requires no malicious actor — an ordinary user bridging a small amount, or a UI defaulting to a "minimum transfer" that doesn't account for the destination's coarser precision, triggers it.

### Recommendation
- In `convert_to_balance`, reject (return an error) when the input amount is non-zero but the divided output is zero, instead of silently minting `0`.
- Alternatively, enforce a minimum-transfer amount on the EVM sender side (`HyperFungibleToken`) proportional to the configured decimals gap, so dust amounts that would round to zero can never be dispatched in the first place.
- Add symmetric handling for the `local_decimals > erc_decimals` case in both `convert_to_balance` and `convert_to_erc20` — currently `erc_decimals.saturating_sub(local_decimals)` silently becomes `0` in that direction, meaning no upscaling occurs and raw units are copied 1:1, which is a related mis-scaling risk for that decimals configuration.

### Proof of Concept
1. Register a local asset (or the native asset) in `pallet-hyper-fungible-token` with `decimals = 6`, and configure `Precisions::<T>::insert(local_asset_id, source_contract, 18)` (the ERC-20 token has 18 decimals) via the normal governance/config flow for that asset pair — this is a realistic deployment configuration for e.g. USDC (6 decimals) bridged against an 18-decimal wrapped/native token.
2. On the EVM side, a user calls the `HyperFungibleToken` bridge-out function with `amount = 500_000` wei (5e5), a real, non-zero, intentional transfer of `0.0000000000005` token in 18-decimal terms — the contract locks/burns this amount and dispatches a `PostRequest` carrying `Message.amount = 500_000`.
3. On Hyperbridge, `on_accept` runs:
   `convert_to_balance(U256::from(500_000), erc_decimals=18, local_decimals=6)` → divisor `= 10^(18-6) = 10^12` → `500_000 / 10^12 = 0` (integer division truncation).
4. `amount = 0` is passed to `mint_into`/`transfer`, which succeeds with a `TokenReceived { amount: 0 }` event; `on_accept` returns `Ok`, so the request is marked delivered and **no timeout/refund is ever triggered**.
5. The user's escrowed/burned ERC-20 value on the source chain is permanently unrecoverable, while the beneficiary's local balance is unchanged — net loss of funds with no compensating mechanism.

(Note: I could not fully trace the exact EVM `HyperFungibleToken.sol` send-side function signature/line numbers in this pass to confirm there is no separate minimum-amount check on that side; this should be verified directly against `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` before treating the PoC as fully confirmed end-to-end.)

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
