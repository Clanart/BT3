### Title
Quadratic Lagrange interpolation over attacker-controlled participant set enables amplified CPU DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`Interpolation::Lagrange::interpolation_factor` is O(|included|) field operations, and both `ThresholdKeys::new` and `ThresholdKeys::view` invoke it once per participant — yielding O(n²) work. Because `ThresholdParams::n` is an attacker-controlled `u16` (up to 65535) deserialized by `ThresholdKeys::read` — a function the project explicitly exposes to untrusted bytes — a ~4 MB input triggers ~4.3 billion field operations plus up to 65535 field inversions.

### Finding Description
`interpolation_factor` iterates the full `included` list to compute the Lagrange numerator/denominator [1](#0-0) . It is called in two quadratic contexts:

1. `ThresholdKeys::new` computes `group_key` by calling `interpolation_factor` for each of participants `1..=t`, each call O(t): O(t²) [2](#0-1) .
2. `ThresholdKeys::view` calls it once per included signer (up to n): O(n²) [3](#0-2) ; `view` also recomputes it via `interpolation_factor(participant)` for external callers [4](#0-3) .

`ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s, then loops `1 ..= n` calling `read_G` — the only checks are `t <= n` and `i <= n` via `ThresholdParams::new` [5](#0-4) . So a single serialized blob with `n = t = 65535` forces `ThresholdKeys::new` (invoked at the end of `read`) to perform ~65535² ≈ 4.3·10⁹ scalar field multiplications for the `Constant`/`Lagrange` group-key computation — with `Lagrange` also performing 65535 inversions in `view`. Each inversion is a ~256-bit exponentiation, so the amplification factor over input size is enormous.

The same quadratic wall is reachable at signing time: `AlgorithmSignMachine::sign` builds `included` from an attacker-supplied `HashMap<Participant, Preprocess>` of up to n entries and calls `keys.view(included)` [6](#0-5) , re-triggering O(n²) interpolation on top of the already-expensive per-signer `process_addendum`/`binding_factors` work.

### Impact Explanation
A single small, syntactically valid `ThresholdKeys` serialization (~65k × 33-byte points ≈ 2–4 MB) pins a CPU core for orders of magnitude longer than the input size warrants, starving signing/DKG processing — an amplified denial of service matching the bug class (quadratic complexity on crafted input). No secret leakage, but sustained CPU exhaustion against any node feeding untrusted bytes to `ThresholdKeys::read` or hosting large-n multisigs where peers supply `preprocesses`/`shares` maps.

### Likelihood Explanation
Medium. `ThresholdKeys::read`/`view`/`sign` are explicitly in-scope entry points for untrusted bytes. The only precondition is that deserialization of a large-n `ThresholdKeys` blob (or a sign session with many preprocesses) is reachable; there is no length cap on `n` beyond `u16::MAX`.

### Recommendation
Cap `n`/`t` to a sane maximum (e.g., the protocol's `MAX_KEY_SHARES_PER_SET`) inside `ThresholdParams::new`/`ThresholdKeys::read`, and/or precompute Lagrange denominators via prefix products (the standard O(n) batch-inversion trick: accumulate prefix products, invert once, then unwind) so `view`/`new` run in O(n) instead of O(n²).

```rust
buf.extend(&(Ristretto::ID.len() as u32).to_le_bytes());

buf.extend(&65535u16.to_le_bytes()); // t
buf.extend(&65535u16.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(1);                          // Interpolation::Lagrange
buf.extend(Scalar::ONE.to_repr());    // secret_share
for _ in 0 .. 65535 {
    buf.extend(RistrettoPoint::generator().to_bytes()); // verification shares
}
// ~2.1 MB input; read() -> ThresholdKeys::new computes group_key with
// 65535 * O(65535) interpolation_factor calls => ~4.3e9 field muls + inversions.
let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
```

Equivalently, in a FROST session with a legitimately large `n`, submitting a `preprocesses`/`shares` map covering all `n` participants makes `keys.view(included)` perform O(n²) interpolation before any signature math rejects it.

```rust
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
```
