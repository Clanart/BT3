## Title
Off-by-framing bug in `createLogParser`'s fixed field-count parsing loop can silently drop or corrupt commit history entries when a commit message contains embedded NUL bytes - (File: `app/src/lib/git/git-delimiter-parser.ts`)

## Summary
The core technical premise is correct for `getCommits()`, but it is **factually wrong for `getChangedFiles()`**, which does not use `createLogParser` at all. I confirm a real parsing-desync bug in `createLogParser`'s `parse()` function that is reachable via `getCommits()` (and `getStashes()`), triggerable by a crafted commit/reflog message containing embedded NUL bytes.

## Finding Description
`createLogParser` builds a `git log --format=...` string joining fields with the literal byte sequence `%x00`, and instructs git to terminate each record with NUL (`-z`). The parser then does: [1](#0-0) 

The loop bound `records.length - keys.length` combined with a fixed step of `keys.length` implicitly assumes that the NUL-delimited stream contains **exactly** `N * keys.length + 1` fields (N commits × K keys, plus one trailing empty string produced by the final `-z` terminator). This assumption breaks if any field's *content* itself contains a NUL byte, since `%x00`/`-z` output is indistinguishable at parse time from a legitimate field boundary once split.

Git commit messages (`%b`, `%s`) are read from the raw commit object body. While Desktop's own `git commit` porcelain path won't let a user type an embedded NUL through the OS shell, an attacker crafting a malicious repository is not limited to porcelain: they can build the commit object directly (e.g. via `git hash-object`/`git commit-tree` with piped stdin or a repacked pack file) and put an arbitrary NUL byte inside the message body, then push/publish that ref. When that repository is cloned/fetched and `getCommits()` runs `git log -z --format=...%x00...` over it, splitting on `\0` produces extra "fields" wherever the malicious NUL appears.

Tracing the arithmetic with `K = keys.length` used in `getCommits()` (currently 9 keys: sha, shortSha, summary, body, author, committer, parents, trailers, refs): injecting exactly `K - 1` extra NUL bytes into an early commit's field keeps `entries.length` numerically equal to the legitimate commit count (`N`), but shifts every field index from that point forward by `K - 1`. Working through the index arithmetic shows the parser's window walks past the true final record before reaching it — the last legitimate commit's fields are consumed into a corrupted/misaligned entry (or fall entirely outside the loop's upper bound) and are never emitted as a clean entry. All commits after the injection point end up with fields drawn from the wrong keys (e.g., a `sha` value that is actually a `body` fragment). [2](#0-1) 

However, the question's second half — that `getChangedFiles()` is affected via this same code path — is incorrect. `getChangedFiles()` does not use `createLogParser`; it uses `--raw --numstat -z` output parsed by the independent, line-oriented `parseRawLogWithNumstat()` function, which has its own (different) parsing logic and loop bound (`lines.length - 1`): [3](#0-2) [4](#0-3) 

So the specific claim "getChangedFiles()/getCommits() silently omitting a commit's file changes" conflates two unrelated parsers. `createLogParser`'s bug can corrupt/drop entries returned by `getCommits()` (and `getStashes()` in `app/src/lib/git/stash.ts`), but has no code path into `getChangedFiles()`. [5](#0-4) 

## Impact Explanation
This is a data-integrity/display-corruption bug in the commit history rendering path, not code execution, file-system escape, credential exfiltration, or IPC/sandbox escape. Its practical effect is that a maliciously crafted commit (present in a repository the user clones or fetches) can cause the History view to display a wrong or missing commit (e.g., dropping the last commit in a listed range, or scrambling SHAs/authors/parents for subsequent commits), potentially confusing the user about repository provenance. This does not clearly map onto any of the explicitly enumerated "Valid Impact" categories (code execution, file write/read outside repo, credential/OAuth compromise, sandbox/IPC escape, or corruption of what the user *commits or pushes*) — it corrupts what is *displayed*, not what the user actually commits/pushes, and it requires the attacker to already control repository content the victim is inspecting rather than granting any new capability.

## Likelihood Explanation
Requiring a crafted commit object with an embedded NUL byte is achievable via git plumbing tools by an attacker who controls a repository, so triggering the underlying parser desync is plausible. However, actually landing exactly `keys.length - 1` NUL bytes to precisely reproduce a "silently drop the last commit" scenario (versus more general, more visibly garbled output across many commits) is a narrow, deliberately engineered condition, and the resulting symptom is a garbled/incorrect history view rather than an in-scope security impact.

## Recommendation
`createLogParser`'s `parse()` should not rely on a fixed field-count arithmetic derived purely from total NUL count. Recommend validating that `records.length % keys.length === 1` (i.e., reject/log unparseable output) before iterating, or switching to a more robust framing scheme (e.g., using a two-level delimiter as `createForEachRefParser` does with its `%00...%00` record wrapper plus explicit newline record separators) so that an embedded NUL inside a single field cannot silently shift the boundary of all subsequent records.

## Proof of Concept
Not verified end-to-end (no sandbox access to actually construct a malicious commit object and run `getCommits()` against it), but the desync can be demonstrated purely via the parser's arithmetic:
- Keys: `K = 2` (`a`, `b`); three legitimate commits.
- Normal `-z` output split on `\0`: `["a1","b1","a2","b2","a3","b3",""]` (length 7). Loop bound `7-2=5` correctly yields 3 entries: `(a1,b1)`, `(a2,b2)`, `(a3,b3)`.
- Inject `K-1 = 1` NUL byte into `b1`'s content, producing `b1part1\0b1part2`: split output becomes `["a1","b1part1","b1part2","a2","b2","a3","b3",""]` (length 8). Loop bound `8-2=6` now yields 3 entries but misaligned: `(a1,"b1part1")`, `("b1part2","a2")`, `("b2","a3")` — the true last record `(a3,b3)` (index 6) falls outside `i<6` and is **never produced**, confirming the loop-bound assumption in `app/src/lib/git/git-delimiter-parser.ts` lines 29-33 is unsafe against embedded NUL bytes in field content. [6](#0-5)

export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

  return { formatArgs, parse }
}

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
