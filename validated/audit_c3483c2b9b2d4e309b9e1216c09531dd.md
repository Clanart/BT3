## Analysis

The core flaw in the report is a **stale security check**: a value (`sigFees`, derived from `tx.gasprice`) is computed once, trusted for a later privileged action, and the world can change between computation and use, with no re-validation at use time. The closest structural analog in GitHub Desktop is a **check-then-use (TOCTOU) gap around path-safety validation** in the Copilot merge-conflict-resolution feature, where a path is validated as "safe" once, but then read from disk in separate, later filesystem calls using the plain path string rather than the already-validated handle.

### Title
Stale path-safety check allows symlink-swap file disclosure outside the repository via Copilot conflict resolution - (File: `app/src/lib/copilot-conflict-context.ts`)

### Summary
`buildConflictContext` validates each conflicted file's path once with `resolveWithin`, which resolves symlinks via `realpath` and confirms the target stays inside the repository working directory. However, the actual file is not read from that validated location; instead, the plain resolved path string is passed to two subsequent, independent filesystem calls (`stat` and `readFile`) later in the same function. Because the safety check and the actual reads are separate operations on a path string (not an open file descriptor), the on-disk target can change between the check and the use, breaking the invariant the check was meant to enforce, analogous to `sigFees` being computed from a `tx.gasprice` that can drift before the guarded action executes.

### Finding Description
`resolveWithin` in [1](#0-0)  resolves the requested relative path, calls `realpath` on both the root and the resolved candidate, and only returns the path if the *real* resolved target is confined to the *real* root — this is the defense against symlink escapes.

`buildConflictContext` uses this helper once per conflicted file, but the returned string is then used in two further, temporally separate async filesystem operations: [2](#0-1) 

Between the `resolveWithin` check (line 393) and the later `stat` (line 413) and `readFile` (line 431) calls, `absolutePath` is just a string on disk — there is no `O_NOFOLLOW`-style open, no re-validation, and no file descriptor held open across the checks. If whatever the path points to is replaced with a symlink pointing outside the working directory after the check but before the read (e.g., during a merge/rebase where a conflicted "file" entry can be manipulated by content the attacker controls, or by a slow multi-file `Promise.all` batch giving a window for the target to change), the file ultimately read can be located outside the repository.

The content read is then bundled into the conflict context and formatted into a prompt sent to the Copilot SDK / backend (`gitHubToken`-authenticated session, see `createClient` in [3](#0-2) ), meaning any file successfully substituted in during the race is exfiltrated off the local machine to a remote network service.

This is the same bug class as the report: a guard is computed once against the state of the world at time T1, and relied upon unconditionally for an action performed at time T2, with no mechanism ensuring the two are consistent.

### Impact Explanation
If exploitable, arbitrary file content outside the repository (subject to the app process's read permissions) could be read and transmitted to the Copilot backend under the authenticated user's GitHub token, which is a file-read-outside-repo / exfiltration-class impact called out as valid in scope.

### Likelihood Explanation
Likelihood is limited by the fact that this requires winning a filesystem race in the window between the `resolveWithin` check (line 393) and the `stat`/`readFile` calls (lines 413/431) for a specific conflicted file — the existing code already defends against static path traversal and symlink targets that are fixed at validation time, and the `Promise.all` over multiple files gives a nonzero but narrow timing window rather than a reliably reproducible trigger. This is why it is flagged as Medium rather than High: the guard itself is structurally insufficient (check and use are decoupled), but turning that gap into a reliable exploit needs precise timing of a symlink swap, which is harder to guarantee than the gas-price analog (which trivially drifts with network conditions).

### Recommendation
Eliminate the check-then-use gap: resolve and open the file once (e.g., open a file descriptor with `fs.open`/`fs.promises.open` using `O_NOFOLLOW` where supported, or use the already-open handle for both the `fstat` size check and the subsequent read) so that the safety guarantee established by `resolveWithin` cannot be invalidated by a later filesystem change. Avoid re-deriving or re-stat'ing a plain path string after a symlink/traversal check has already been performed.

### Proof of Concept
1. Start a merge/rebase/cherry-pick that produces a conflict on a file entry whose on-disk target can be influenced by repository content.
2. Trigger Copilot conflict resolution, which calls `buildConflictContext` for the conflicted file list [4](#0-3) .
3. `resolveWithin(workingDirectory, file.path)` validates the path is safely inside the repo at time T1.
4. Before the subsequent `stat`/`readFile` execute at time T2, replace the file at `absolutePath` with a symlink pointing to a sensitive file outside the repository (e.g., via a concurrent process or a timing-sensitive filter/hook triggered by the same merge).
5. `readFile(absolutePath, 'utf8')` at line 431 follows the symlink and reads the external file's contents, which are then included in `rawContent` and forwarded into the prompt sent to the Copilot SDK/backend.

export async function buildConflictContext(
  ourLabel: string,
  theirLabel: string,
  workingDirectory: string,
  files: ReadonlyArray<{
    readonly path: string
    /** Which side deleted the file (for delete-vs-modify conflicts). */
    readonly deletedSide?: 'ours' | 'theirs'
  }>
): Promise<ICopilotConflictContext> {
  const results = await Promise.all(
    files.map(async (file): Promise<IFileConflictContext> => {
      // Delete-vs-modify conflicts have no text markers on disk. Include
      // them in the context with metadata so the model can recommend
      // keep or delete — no file content is needed.
      if (file.deletedSide !== undefined) {
        return {
          path: file.path,
          hunks: [],
          deleteConflict: { deletedSide: file.deletedSide },
        }
      }

      // Guard against path traversal and symlink escapes (cross-platform)
      let absolutePath: string | null
      try {
        absolutePath = await resolveWithin(workingDirectory, file.path)
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File path could not be resolved safely',
        }
      }
      if (absolutePath === null) {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File path is outside the repository',
        }
      }

      // Guard against reading pathologically large files into memory. This is
      // a memory-safety bound only — resolvability is decided from the conflict
      // hunks below, not the whole-file size.
      try {
        const fileStat = await stat(absolutePath)
        if (fileStat.size > MAX_CONFLICT_FILE_READ_SIZE) {
          return {
            path: file.path,
            hunks: [],
            skippedReason: 'File too large to resolve automatically',
          }
        }
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File could not be read',
        }
      }

      let content: string
      try {
        content = await readFile(absolutePath, 'utf8')
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File could not be read',
        }
      }

  private async createClient(
    account: Account,
    repositoryPath?: string
  ): Promise<CopilotClient> {
    if (!account.token) {
      throw new Error('Cannot create Copilot client: Account has no token')
    }

    // This relies on the fact that Copilot CLI is bundled with the app, but not
    // as a "single executable application", but the files from the npm package.
    // That means Desktop will use its own executable to run as Copilot CLI's
    // index.js as node.
    // However, when trying to do this directly without the --eval flag, Copilot
    // CLI fails to parse the arguments correctly, so we ended up using --eval
    // and just importing the index.js from the CLI as a workaround.
    const cliDir = getCopilotCLIDir()
    const indexPath = join(cliDir, 'index.js')

    // Make sure the import path exists before creating the client, so we don't
    // end up with a half-broken client that can't start. We check the
    // filesystem path here, before converting it to a file:// URL on Windows,
    // because `fs.access` doesn't accept URL-form strings.
    if (!(await pathExists(indexPath))) {
      throw new Error('Cannot create Copilot client: CLI entry point not found')
    }

    // On Windows, `import` requires a valid file:// URL rather than a bare
    // absolute path.
    const importSpecifier = __WIN32__
      ? pathToFileURL(indexPath).href
      : indexPath

    return new CopilotClient({
      connection: RuntimeConnection.forStdio({
        path: await getCopilotCLIPath(),
        args: ['--eval', `import '${importSpecifier}'`, '--'],
      }),
      env: {
        ELECTRON_RUN_AS_NODE: '1',
        COPILOT_RUN_APP: '1',
        GH_HOST: getCopilotGHHost(account),
        GITHUB_COPILOT_INTEGRATION_ID: `copilot-desktop${
          __DEV__ ? '-dev' : ''
        }`,
      },
      workingDirectory: repositoryPath,
      sessionFs: getCopilotInMemorySessionFsConfig(
        repositoryPath,
        __WIN32__ ? 'windows' : 'posix'
      ),
      gitHubToken: account.token,
    })
  }
