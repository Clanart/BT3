### Title
WERC20 precompile permanently locks native coin value sent alongside non-deposit ERC20 calls - (File: precompiles/werc20/werc20.go)

### Summary
The WERC20 precompile wraps the ERC20 precompile to expose a WETH-style interface for the chain's native EVM coin. Unlike the plain `erc20` precompile, which explicitly rejects any call carrying `msg.value` to avoid stranding funds [2](#0-1) , `werc20.Execute` only special-cases `deposit`/`receive`/`fallback`/`withdraw` and routes everything else (including `transfer`, `transferFrom`, `approve`) straight to `HandleMethod` without ever checking or refunding `contract.Value()` [3](#0-2) .

### Finding Description
Because the EVM's block context uses go-ethereum's native `Transfer` function for value transfers on every `CALL` [1](#0-0) , any call to the WERC20 precompile address that attaches `value` (e.g. `WERC20.transfer{value: X}(to, amount)` via a low-level `.call{value: X}(data)` — Solidity's `payable` marker is a compile-time restriction only, not enforced by the EVM or the precompile) will first move `X` native-denom balance from the caller into the WERC20 precompile's own account balance at the state-transition level, exactly as a normal EOA-to-EOA transfer would. Execution then proceeds to `werc20.Execute`, which for a `transfer`/`approve`/`transferFrom` call dispatches to `p.HandleMethod` (the ERC20 logic) [4](#0-3) , performing the ERC20 accounting `SendCoins` but never touching or refunding the `value` that was separately transferred into the precompile's account.

Only the dedicated `Deposit` handler refunds `contract.Value()` — and it does so using `contract.Value()` of the *current* call only, not the precompile's actual outstanding balance [5](#0-4) . There is no mechanism anywhere in the precompile to sweep or reclaim value that was sent into the precompile account through a non-`deposit` call path. Because the WERC20 precompile address is not a real, spendable EOA and has no code path that reads/refunds an arbitrary residual balance, any native coin routed to it via this path becomes permanently locked — a direct structural analog of the Furo/WETH bug: the payable “deposit” signal (call to `deposit()`) and the actual native value movement (any call with `value`) are decoupled, so a mismatch between the two silently strands funds instead of reverting.

### Impact Explanation
This causes permanent, irrecoverable loss of the caller's native-denom balance — value that is deducted from the sender's spendable balance but never credited to any account able to spend it (the WERC20 precompile address is not backed by a private key and has no sweep function). This matches the in-scope "Critical permanent freezing/locking/theft of user funds" impact category, since ordinary unprivileged EVM users (or any contract performing low-level calls, e.g. via `BoringBatchable`-style multicall patterns or DeFi integrations that blindly forward `msg.value` to whatever function selector they're calling) can trigger it without any privileged access.

### Likelihood Explanation
The trigger requires only a standard EVM `CALL` with non-zero `value` targeting the WERC20 precompile address with a payload selecting `transfer`, `transferFrom`, or `approve` instead of `deposit`. Solidity's own `payable` compile-time check would normally prevent naive contracts from doing this accidentally when using the typed `IWERC20` interface, but any assembly-level call, proxy/relayer contract, or contract using `.call{value: x}(abi.encodeWithSelector(...))` (a common pattern for generic multicall/batch execution across many WETH-integrated protocols) can trivially hit this path, and no ABI-level or precompile-level guard prevents it.

### Recommendation
Mirror the guard already present in the base `erc20` precompile: reject (or immediately refund) `contract.Value()` for any WERC20 method other than `deposit`/`fallback`/`receive`, i.e. add a check equivalent to `erc20.Execute`'s `ErrCannotReceiveFunds` check at the top of `werc20.Execute` before dispatching to `HandleMethod` for non-deposit methods [2](#0-1) [3](#0-2) .

### Proof of Concept
1. Deploy a helper contract (or use an EOA via a raw transaction) that issues a low-level call: `WERC20_ADDRESS.call{value: 1 ether}(abi.encodeWithSignature("transfer(address,uint256)", recipient, amount))`.
2. The EVM state-transition subtracts `1 ether` of native coin from the caller's balance and credits it to the WERC20 precompile account via `core.Transfer` before `Run` executes [1](#0-0) .
3. `werc20.Execute` sees `method.Name == "transfer"`, which is not `deposit`/`withdraw`/fallback/receive, and falls to the `default` branch calling `p.HandleMethod`, performing only the ERC20 token accounting transfer and never referencing the `1 ether` of native value [6](#0-5) .
4. The `1 ether` remains credited to the WERC20 precompile's account. No later call can recover it: `Deposit` only ever refunds the value of its own current invocation [7](#0-6) , and there is no query/sweep method for the precompile's residual balance — the funds are permanently frozen.

**Uncertainty note:** I was not able to fully trace the `BalanceHandler.AfterBalanceChange` reconciliation logic against this exact scenario (whether the `CoinReceived`/`CoinSpent` bank events generated by `core.Transfer` at the precompile address get intercepted and reversed) [8](#0-7) ; confirming whether any generic balance-handler mechanism neutralizes this stray value (as opposed to only reconciling StateDB with bank-keeper-driven `SendCoins` calls invoked inside `HandleMethod`) would require deeper tracing of how `core.Transfer`'s underlying `StateDB.SubBalance/AddBalance` calls interact with the bank keeper for precompile addresses specifically, which the current index does not fully expose. A Devin session with full repo/test access could confirm this end-to-end via an integration test exercising the exact call sequence described above.

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch {
	case method.Type == abi.Fallback,
		method.Type == abi.Receive,
		method.Name == DepositMethod:
		bz, err = p.Deposit(ctx, contract, stateDB)
	case method.Name == WithdrawMethod:
		bz, err = p.Withdraw(ctx, contract, stateDB, args)
	default:
		// ERC20 transactions and queries
		bz, err = p.HandleMethod(ctx, contract, stateDB, method, args)
	}

	return bz, err
}

// Deposit handles the payable deposit function. It retrieves the deposited amount
// and sends it back to the sender using the bank keeper.
func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}
