### Title
Unbounded recursive parsing of untrusted coin memos causes stack-exhaustion DoS in PlotNFT/custody sync - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a `MofN` custody tree from an on-chain coin's memo without any depth/size bound, mirroring the Miniscript CVE-2024-44073 root cause (recursive tree traversal that "does not properly track tree depth"). Because this memo originates from a `CREATE_COIN` condition's memo field — data fully controlled by whoever creates the coin — an attacker can craft a deeply nested `MofN` memo that, when parsed by `get_next_from_coin_spend()` in the PlotNFT driver (or any other consumer of `from_memo`), exhausts the Python call stack and crashes the parsing process.

### Finding Description
`PuzzleWithRestrictions.from_memo()` recurses once per `MofN` branching level: [1](#0-0) 

```
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
```

There is no limit on the number of nested `MofN` levels a memo can encode, and each `MofN.__post_init__` also eagerly builds a `MerkleTree`/`MofNMerkleTree`, whose own `_root`/`_proof` helpers are similarly unbounded recursive functions: [2](#0-1) [3](#0-2) 

This differs from other tree-walking code in the same codebase that was deliberately made iterative to avoid Python recursion-limit crashes on attacker-influenced trees, e.g. `sha256_treehash`: [4](#0-3) 

The memo consumed by `from_memo` is not validator-checked data; it is the raw memo attached to a `CREATE_COIN` output, and `PlotNFT.get_next_from_coin_spend()` calls `from_memo()` directly on it while syncing plotNFT/pool state from a coin spend: [5](#0-4) 

Any spend that creates a coin memoized as a deeply-nested `MofN` custody hint (e.g., hundreds/thousands of `further_branching` levels) will drive `from_memo` recursion depth proportional to attacker-chosen nesting, well past Python's default recursion limit, raising an uncaught/uncontrolled `RecursionError` (this is *not* the `ValueError` the caller catches).

### Impact Explanation
Because `get_next_from_coin_spend()` only catches `ValueError` around the `from_memo()` call, an uncaught `RecursionError` propagates up and halts whatever process is walking the PlotNFT/pool chain history (wallet sync, pooling tooling, or any similar consumer of `PuzzleWithRestrictions.from_memo`). This matches the "spend-triggered transaction-processing halt" impact category: a single maliciously-memoized coin, once spent/created, can crash the client attempting to interpret it, denying service to a pool operator, wallet, or tool that must process that coin's lineage.

### Likelihood Explanation
Likelihood is high for any counterparty who can create a coin with an attacker-chosen memo (trivial — memos are arbitrary bytes attached via `CREATE_COIN`) that some other party's node/wallet/pooling client will later parse with `PuzzleWithRestrictions.from_memo` (e.g., during PlotNFT next-state resolution). No privileged position is required; only a single spend bundle with a crafted memo is needed.

### Recommendation
- Add an explicit recursion/nesting depth limit to `PuzzleWithRestrictions.from_memo()` (and reject memos exceeding it with a `ValueError`, which is already caught by callers such as `get_next_from_coin_spend()`).
- Convert `from_memo()` and the `MofNMerkleTree`/`MerkleTree` recursive helpers (`_root`, `_proof`, `_m_of_n_proof`) to iterative, explicitly stack-bounded implementations, following the same non-recursive pattern already used in `sha256_treehash`.
- Bound the total number of `MofN` members / nesting levels accepted from untrusted memos before constructing `MofN` objects.

### Proof of Concept
1. Construct a nested memo program of depth N (e.g., N = 5,000) representing `MofN(m=1, members=[MofN(m=1, members=[... MofN(m=1, members=[UnknownMember(...)]) ...])])`, encoded via `PuzzleWithRestrictions.memo()`-compatible structure (`CHIP-0043` namespace, `further_branching=1` at every level, each `MofNHint` wrapping exactly one child memo).
2. Attach this program as the memo (`memo_blob`) of a `CREATE_COIN` condition inside any spend bundle that creates a coin observable by the target (e.g., a plotNFT-style singleton spend, or any coin a target wallet/tool will later call `PuzzleWithRestrictions.from_memo` / `PlotNFT.get_next_from_coin_spend()` on).
3. Submit the spend bundle; once the coin/spend is processed by a client calling `from_memo()` on that memo (e.g. via `get_next_from_coin_spend`), the recursive parsing exceeds Python's stack/recursion limit and raises an uncaught `RecursionError`, crashing that processing path — a spend-triggered denial of service, analogous to the unbounded Miniscript tree-depth stack exhaustion in the reference advisory.

@dataclass(kw_only=True, frozen=True)
class MofN:  # Technically matches Puzzle protocol but is a bespoke part of the architecture
    m: int
    members: list[PuzzleWithRestrictions]

    def __post_init__(self) -> None:
        if self.m > self.n:
            raise ValueError("M cannot be greater than N")
        if self.m < 1:
            raise ValueError("M must be greater than 0")
        if len(list(set(self._merkle_tree.nodes))) != len(self._merkle_tree.nodes):
            raise ValueError("Duplicate nodes not currently supported by MofN drivers")

    @property
    def n(self) -> int:
        return len(self.members)

    @property
    def _merkle_tree(self) -> MerkleTree:
        nodes = [member.puzzle_hash(_top_level=False) for member in self.members]
        if self.m > 1:
            return MofNMerkleTree(nodes)
        else:
            return MerkleTree(nodes)
