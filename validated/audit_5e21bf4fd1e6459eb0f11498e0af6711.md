## Title
Payout attribution (`OP_RETURN` operator xonly-pk) is unauthenticated, letting anyone reassign reimbursement credit away from the party who actually funds the withdrawal — ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs only the user's withdrawal input/output with a `SIGHASH_SINGLE|ANYONECANPAY`-style signature [1](#0-0) , while the `OP_RETURN` output that names the "operator that fronts the peg-out" is completely unsigned and unauthenticated [2](#0-1) . The verifiers' bookkeeping trusts this `OP_RETURN` alone to decide which operator gets credited as the payer [3](#0-2) , and an operator's own reimbursement pipeline trusts the same DB value without any additional proof that it actually broadcast the funding inputs [4](#0-3) [5](#0-4) .

### Finding Description
The `withdraw` flow signs the withdrawal UTXO with the user's `taproot::Signature` using a partial sighash (input 0 + output 0 only — the "single + anyone-can-pay" style used elsewhere in the codebase) [6](#0-5) . Because this signature does not commit to the rest of the transaction, whoever holds the presigned bytes can freely:
- add arbitrary funding inputs (this is literally what `fund_raw_transaction`/`create_funded_psbt` do to pay the actual withdrawal amount) [7](#0-6) [8](#0-7) , and
- set the `op_return_txout(operator_xonly_pk)` output to any x-only public key of their choosing [9](#0-8) .

Downstream, `update_finalized_payouts` parses this `OP_RETURN` straight off the confirmed transaction and stores it as `payout_payer_operator_xonly_pk` with no cross-check that the named operator actually supplied the funding inputs [3](#0-2) . The verifier's fraud check (`is_kickoff_malicious`) and the operator's own `validate_payer_is_operator` both use this DB value as ground truth for "who fronted this payout," rather than any cryptographic evidence tying the operator's key to the actual spend [10](#0-9) [11](#0-10) .

This exactly mirrors the reported bug class: an accounting/attribution invariant ("burn depends on the actor's own balance" in the report, "reimbursement credit depends on who fronted the payout" here) can be satisfied by a party other than the intended actor because the mechanism that is supposed to bind identity to the economic act (private-mode transfer restriction in the report; a signature over the `OP_RETURN` output here) is absent. Once a payout transaction with a given input+output(0) signature is visible (e.g., in the mempool, or because the same off-chain signature was shared with several operators), any actor — including a non-participating operator or a pure griefer — can construct a competing spend of the same withdrawal UTXO that pays the user (satisfying "withdrawal fronted") but attributes credit to a different operator xonly-pk, breaking the equality `operator_credited == party_that_funded`.

### Impact Explanation
If this equality is broken, an operator that never funded a payout can be credited as the payer on-chain, causing its automated `PayoutCheckerTask`/`handle_finalized_payout` pipeline to proceed through the kickoff/round/reimburse flow and claim reimbursement funds from the vault/round transactions for a withdrawal it did not pay for [5](#0-4) [12](#0-11) . This falls under the Critical category "an operator reimbursed for a payout it never funded." It can also be used to grief a targeted operator, forcing its automation to spend collateral/kickoff connectors reacting to a payout it never made.

### Likelihood Explanation
Exploitation requires only observation/possession of a presigned withdrawal signature (which by design is shared "off-chain" and is not bound to a specific operator identity) and the ability to broadcast a competing, malleable transaction spending the same withdrawal UTXO before/instead of the intended operator's broadcast — no verifier, operator, or aggregator privilege is required to construct such a transaction, only ordinary transaction relay/broadcast access.

### Recommendation
Bind the `OP_RETURN` operator attribution to the same signature that authorizes spending the withdrawal UTXO (e.g., require the operator's own signature over the full payout transaction, or have the `OP_RETURN` payload be part of the sighash that a legitimate committing party controls), so that the identity credited as "payer" cannot be decoupled from the party that actually supplies the funding inputs.

### Proof of Concept
Not executed; this is inferred purely from static code inspection of `create_payout_txhandler` (unsigned `OP_RETURN`, partial sighash over input/output 0 only) [1](#0-0) , `operator.withdraw`'s use of RBF wallet funding for the payout tx [13](#0-12) , and `update_finalized_payouts`'s unauthenticated attribution parsing [3](#0-2) . I was not able to fully verify within the index what exact sighash flags/`SighashType` are actually enforced end-to-end on the withdrawal signature (i.e., whether the codebase truly permits `ANYONECANPAY`-style malleability for this specific signature, or restricts it elsewhere via `parse_withdrawal_sig_params`), since `core/src/rpc/parser/operator.rs` content was not retrieved in full. A Devin session with full repository access would be needed to confirm the exact sighash type constant used and reproduce a concrete transaction-malleability PoC end-to-end.

/// 2. OP_RETURN output (with operators x-only pubkey that fronts the peg-out)
///
/// # Arguments
/// * `input_utxo` - The input UTXO for the payout, committed in Citrea side, with the signature given to operators off-chain.
/// * `output_txout` - The output TxOut for the user payout.
/// * `operator_xonly_pk` - The operator's x-only public key that fronts the peg-out.
/// * `user_sig` - The user's signature for the payout, given to operators off-chain.
/// * `network` - The Bitcoin network.
///
/// # Returns
/// A [`TxHandler`] for the payout transaction, or a [`BridgeError`] if construction fails.
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
