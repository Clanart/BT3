### Title
Missing participant check in `GeneratorPromotion::complete` enables remote panic/DoS via malicious proof map - (File: crypto/dkg/promote/src/lib.rs)

### Summary
The external report (CVE-2025-21490) describes an availability flaw: a crash/hang of a server reachable over the network. The strongest reachable analog in Serai's in-scope code is in `GeneratorPromotion::complete`, which indexes the attacker-influenced `proofs` map with `.unwrap()` after checks that do not actually guarantee every required key is present. A participant that submits a proof keyed under the victim's own index causes the victim's node to panic, a repeatable crash (complete DoS) of the promotion protocol.

### Finding Description
`GeneratorPromotion::complete` validates the peer-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>` with only two checks:

```rust
if proofs.len() != (usize::from(params.n()) - 1) { ... IncorrectAmountOfParticipants ... }
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... InvalidParticipant ... }
}
``` [1](#0-0) 

It then iterates `1 ..= params.n()`, skips `params.i()`, and unconditionally unwraps each entry:

```rust
let proof = proofs.get(&i).unwrap();
``` [2](#0-1) 

The checks verify the *count* (`n - 1` entries) and that every key is `<= n`, but never verify that the map does not contain `params.i()` itself, nor that every participant `1..=n` other than `i` is present. Compare with the equivalent map validator in PedPoP, which explicitly rejects a map containing the local participant and requires every included participant to be present (`validate_map`, `DkgError::DuplicatedParticipant` / `MissingParticipant`). [3](#0-2) 

So a map of length `n - 1` containing key `params.i()` (a duplicate/self entry) and missing some other participant `l` passes both checks, then panics at `proofs.get(&l).unwrap()`.

### Impact Explanation
`Participant` is attacker-controlled protocol data (it is a public index, not secret). Any participant in a generator-promotion ceremony can send their `GeneratorProof` keyed under the victim's participant index instead of their own. The victim's `complete` call then panics rather than returning an error. This is a remotely triggerable, easily repeatable crash — the same availability-impact class (CVSS A:H, hang/repeatable crash) as the referenced advisory — denying the victim completion of the promotion, which gates key rotation on the same curve. The panic occurs before any secret material is mishandled, so impact is limited to availability.

### Likelihood Explanation
The trigger requires only that a single ceremony participant malform their proof map key — a trivially constructed public input (one `u16`). No threshold collusion, no valid proofs, and no privileged position are needed; any participant reachable in the `proofs` map suffices. The panic is deterministic and repeatable on every retry while the malformed key remains.

### Recommendation
In `GeneratorPromotion::complete`, replace the unwrap with a checked lookup and add an explicit self-entry rejection, mirroring `pedpop::validate_map`:

```rust
if proofs.contains_key(&params.i()) {
  Err(PromotionError::InvalidParticipant { n: params.n(), participant: params.i() })?;
}
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i)
    .ok_or(PromotionError::MissingParticipant(i))?;
  ...
}
```
This converts the panic into a returned error and rejects the malformed map before indexing.

### Proof of Concept
```rust
// n = 3, victim is participant 1. Attacker (participant 2) registers
// their proof under key Participant(1) — the victim's own index.
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof); // self-entry, not rejected
proofs.insert(Participant::new(3).unwrap(), p3_proof);       // valid third-party proof
// proofs.len() == 2 == n - 1  -> passes the count check
// all keys <= n                -> passes the range check
// Loop i = 1: skipped (i == params.i())
// Loop i = 2: proofs.get(&Participant(2)) -> None -> unwrap() panics
promotion.complete(&proofs); // thread panic: repeatable remote DoS
```
Root cause: `crypto/dkg/promote/src/lib.rs:125-146` performs membership-by-count validation but indexes by identity; the map may contain `params.i()` and omit a required participant, making `proofs.get(&i)` return `None` and `.unwrap()` panic.
