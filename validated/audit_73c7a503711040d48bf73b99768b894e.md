### Title
GitHub Enterprise sign-in spoofing via forged `WWW-Authenticate: realm="GitHub"` header from a malicious git remote - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
Like the llhttp bug where an unexpected token delimiter (`\t`) caused the parser to silently drop the `CONNECTION_CLOSE` security state and reclassify subsequent bytes as a new trusted request, GitHub Desktop's credential-helper endpoint classifier makes a security-relevant trust decision (`'enterprise'` vs `'generic'`) based on a naive substring match against attacker-controlled data, causing a non-GitHub git remote to be misclassified as a genuine GitHub Enterprise host.

### Finding Description
When Git performs HTTP authentication against a remote, it captures any `WWW-Authenticate` response headers and forwards them to the configured credential helper (Desktop's `git-credential-desktop`) as `wwwauth[]=<value>` entries. This header content is fully attacker-controlled — any git server the user adds as a remote can return an arbitrary `WWW-Authenticate` value.

In `getEndpointKind` [1](#0-0) , once the hostname-based checks (`isGist`, `isDotCom`, `isGHE`) fail to identify the endpoint as a known GitHub host, the code falls back to inspecting the forwarded `wwwauth[...]` values:

```
if (v.includes('realm="GitHub"')) {
  return 'enterprise'
}
```

This is a simple substring check with no validation that the response actually originates from a real GitHub Enterprise server (no TLS/cert binding, no API probe, no cryptographic proof) — it's purely trusting attacker-supplied header text, analogous to how llhttp trusted a `close` token match without validating the full expected delimiter set.

If this check returns `'enterprise'` and no existing account matches the attacker's endpoint, `getCredential` [2](#0-1)  calls `ui.promptForGitHubSignIn(endpoint)`, where `endpoint` is the attacker's own origin.

`promptForGitHubSignIn` then does: [3](#0-2) 

```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
```

Since `hostname` is the attacker's domain (not `github.com`), Desktop launches the real "Sign in to GitHub Enterprise" flow, pre-populated/scoped with the attacker's origin as the enterprise server address, and shows a `SignIn` popup with `credentialHelperUrl: endpoint` (the attacker's URL) — with no visual distinction indicating this originated from an untrusted, unauthenticated header rather than a deliberate user action to add a GHE account.

### Impact Explanation
This satisfies "unauthorized OAuth or account binding" and potential "credential/token exfiltration": a user who simply adds/fetches from a malicious git remote (no unusual steps beyond a normal `git fetch`/`clone`/HTTP auth attempt) can be silently steered into a legitimate-looking GitHub Enterprise sign-in dialog scoped to the attacker's server. Depending on the enterprise sign-in flow's implementation (PAT entry or OAuth device/browser flow against the attacker-controlled origin), this can result in the user's GitHub Enterprise credentials/PAT being submitted to, or an OAuth token being minted/exchanged against, a server the attacker controls — while Desktop UI presents it as an authentic GHE sign-in, not an unauthenticated credential prompt from a third-party remote.

### Likelihood Explanation
The attacker only needs to control the git server responding to an HTTP request from Git (any generic git remote the user configures), and cause it to answer with a `401`/`WWW-Authenticate` header containing `realm="GitHub"`. This is fully within control of any HTTP server operator and requires no special network position, no prior account, and no unnatural user action beyond a normal clone/fetch against a hostile remote. The only gating condition is that no existing account already matches that endpoint origin.

### Recommendation
Do not trust the `wwwauth[]` realm string alone to classify an endpoint as `'enterprise'`. At minimum, require an authenticated verification step (e.g., probing `/api/v3/meta` or similar with TLS certificate/hostname pinning) before treating an arbitrary remote as GitHub Enterprise, and/or clearly warn the user in the sign-in popup that the enterprise server URL was auto-detected from an untrusted header rather than user-entered, allowing them to cancel before any credentials are sent.

### Proof of Concept
1. Attacker sets up an HTTP git server at `https://evil.example.com/repo.git` that, on any unauthenticated request, responds with:
   ```
   HTTP/1.1 401 Unauthorized
   WWW-Authenticate: Basic realm="GitHub"
   ```
2. Victim adds this URL as a remote / clones it in GitHub Desktop.
3. Git invokes the desktop credential helper; `wwwauth[]=Basic realm="GitHub"` is forwarded in the credential request `stdin`, parsed by `parseCredential` [4](#0-3) .
4. `getEndpointKind` matches `realm="GitHub"` and classifies `evil.example.com` as `'enterprise'` [5](#0-4) .
5. Since no account exists for `evil.example.com`, Desktop calls `promptForGitHubSignIn('https://evil.example.com')`, launching the Enterprise sign-in flow bound to the attacker's origin [6](#0-5) .
6. The victim, believing this is a legitimate GHE sign-in prompt, enters credentials/completes OAuth against the attacker's server.

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}
