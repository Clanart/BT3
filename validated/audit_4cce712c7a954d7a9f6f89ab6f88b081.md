### Title
Permissionless `CallDispatcher.dispatch()` lets anyone drain unswept/leftover token or ETH balances from the shared IntentGateway dispatcher — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is the single, shared, permanently-deployed contract that `IntentGatewayV2` uses to run untrusted predispatch/postdispatch calldata for **every** order. Its `dispatch()` function has no access control whatsoever — any address can call it directly with an arbitrary `Call[]` array. Since `IntentsBase._execute()` (postdispatch) and `IntentGatewayV2.placeOrder()` (predispatch) only sweep back the tokens explicitly listed in `order.output.assets` / `order.inputs`, any other token or ETH balance that ends up on the dispatcher (reward tokens from an arbitrary DeFi call, dust from an intermediate swap, or tokens someone mistakenly sends to the known dispatcher address) is left there and can be withdrawn by any unprivileged caller — this is the exact bug class from the external `SwapExecutor` report.

### Finding Description
`CallDispatcher.dispatch()` executes an ABI-encoded array of arbitrary `Call{to, value, data}` structs with no `msg.sender` check: [1](#0-0) 

`IntentsBase._execute()` uses this same dispatcher instance (`_params.dispatcher`) to run the order's postdispatch calldata, then sweeps back **only** the tokens listed in `order.output.assets` (`outputsLen`): [2](#0-1) 

`IntentGatewayV2.placeOrder()` similarly routes predispatch assets through the dispatcher, executes `order.predispatch.call`, and sweeps back **only** the tokens listed in `order.inputs`: [3](#0-2) 

`_params.dispatcher` is a single fixed address shared across all orders (set once in gateway `Params`), not a fresh per-order contract, so its address is discoverable/predictable on-chain.

Because the sweep logic enumerates only the token set declared in the order (`order.output.assets` or `order.inputs`), any token balance the dispatcher acquires that is *not* in that declared set is never swept and remains sitting on the dispatcher indefinitely. This mirrors all three causes in the external report:
1. Arbitrary predispatch/postdispatch calldata can interact with protocols that reward the dispatcher with tokens not declared in the order (e.g., liquidity-mining rewards, airdropped tokens, swap dust of an intermediate hop token).
2. A user/solver can accidentally send tokens directly to the known, shared dispatcher address outside of any order flow.
3. Since `dispatch()` has zero access control, once any token balance sits on the dispatcher, **any external account** — not the gateway, not a relayer, not an admin — can call `CallDispatcher.dispatch()` directly with a `Call` that transfers that ERC20 balance or ETH to itself.

Existing guards do not stop this: there is no `onlyGateway`/`onlyOwner` modifier on `dispatch()`, and the "sweep" performed by `IntentsBase._execute()`/`placeOrder()` is not an exhaustive balance sweep — it only zeroes out the specific tokens named in the order structure.

### Impact Explanation
This is a direct, unauthorized fund-theft primitive matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories. Any unprivileged attacker can permanently exfiltrate:
- Reward/incidental tokens accrued on the dispatcher from arbitrary predispatch/postdispatch calldata that are not part of the order's declared input/output token set.
- Any tokens or ETH mistakenly sent to the dispatcher's address, since it is a long-lived, address-known, shared contract rather than an ephemeral per-order escrow.

No malicious relayer, prover, admin, or peer is required — the attacker only needs to call the public `dispatch()` function on the well-known dispatcher contract with a self-serving `Call[]`.

### Likelihood Explanation
High for tokens accidentally or incidentally left on the dispatcher: because the dispatcher is a single shared contract used by every order (rather than a fresh, isolated executor per order), any leftover balance from any past or future order, or from calldata side effects, is exploitable by a completely unprivileged actor watching the dispatcher's token balances and front-running/racing to sweep it out via a directly-submitted `dispatch()` call. The attack requires no special conditions beyond a nonzero balance appearing on the dispatcher outside the tokens enumerated by the order that produced it.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to be callable only by the registered `IntentGatewayV2` (or other authorized gateway) address, e.g. an `onlyGateway` modifier checked against `_params.dispatcher`'s configured owner/caller.
- Alternatively, deploy an ephemeral/minimal-proxy `CallDispatcher` per order (or per call) so no cross-order or externally-sent balance can accumulate on a long-lived, publicly known address.
- After executing arbitrary calldata, sweep the dispatcher's *entire* balance of any token that could plausibly be received (or restrict what the calldata is allowed to interact with), rather than only the tokens declared in `order.inputs`/`order.output.assets`.

### Proof of Concept
1. Read the gateway's public `dispatcher` address via `IntentGatewayV2` params (or observe it in `_params.dispatcher` used by `placeOrder`/`_execute`).
2. Wait for (or induce, e.g. via an order whose postdispatch calldata claims a reward token not listed in `order.output.assets`) a nonzero balance of any ERC20/ETH to appear on the `CallDispatcher` contract.
3. From any unprivileged EOA, call:
   ```solidity
   CallDispatcher(dispatcherAddr).dispatch(
       abi.encode([Call({
           to: rewardToken,
           value: 0,
           data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(rewardToken).balanceOf(dispatcherAddr))
       })])
   );
   ```
4. `dispatch()` executes the call with no caller check, transferring the dispatcher's token balance to the attacker — funds that were never part of any order's escrow accounting are stolen with no privileged access required.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
