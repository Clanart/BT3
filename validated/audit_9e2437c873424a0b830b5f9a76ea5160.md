### Title
`performPush` can push to a stale/mismatched remote URL due to unsynchronized `remote.name`/`branch.upstreamRemoteName` state (soft-fail guard is telemetry-only) - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`AppStore.performPush` reads the "remote" used for a push from two independently-refreshed pieces of state: the cached `remote` object (`state.remote`, containing both `.name` and `.url`) and `branch.upstreamRemoteName` (derived from the branch's tracking config). These two values are not guaranteed to be captured at the same instant, and the code explicitly documents this as a known risk, guarding it only with a non-fatal telemetry event rather than refusing to proceed or re-resolving a consistent pair. [1](#0-0) 

### Finding Description
`performPush` builds the "remote" it will push to as follows:
- `remote` comes from `repositoryStateCache.get(repository).remote` (a snapshot).
- `remoteName` is `branch.upstreamRemoteName || remote.name` — i.e., it prefers the branch's own upstream tracking name, which is refreshed on a separate cadence (via git-store branch/ref refreshes) from `remote`.
- It then constructs `safeRemote = { name: remoteName, url: remote.url }`, explicitly pairing the *branch's* remote name with the *old cached remote object's* URL. [2](#0-1) 

The comment block preceding this code acknowledges the exact broken invariant: "there's no guarantee that they'll be refreshed at the exact same time so there's a theoretical possibility that `branch.remote` and `remote.name` could be out of sync," and states the fix is temporary and only there "out of an abundance of caution." [3](#0-2) 

When the mismatch is detected (`safeRemote.name !== remote.name`), the only action taken is `sendNonFatalException('remoteNameMismatch', ...)` — a telemetry call. The push still proceeds using the Frankenstein `safeRemote` object combining a possibly-current `name` with a possibly-stale `url`. [4](#0-3) 

This is the same broken-invariant class as the report: an entity is composed of two fields (`token`/`amount` in the contract; `name`/`url` here) that are supposed to always describe the same "position," but each field can be updated by a different, independently-timed code path (front-running the check in the contract; background remote/branch refreshes here — e.g. `updateRemoteUrl`, which silently rewrites `gitStore.defaultRemote.url` based on GitHub API data such as a repository rename/transfer surfaced through `apiRepo.clone_url`) between the time the invariant is checked and the time it's acted upon. [5](#0-4) 

`envForRemoteOperation`/proxy resolution and the actual `pushRepo` call are then driven by this inconsistent `safeRemote`, meaning the URL used to resolve credentials/proxy and the name used by git to select the remote can refer to two different underlying remotes. [6](#0-5) 

### Impact Explanation
If `remote.url` (captured before a background rewrite) does not correspond to `remoteName` (captured after an update), the push can be resolved against the wrong URL/credentials/proxy target for the given remote name, or vice-versa. This falls under "silent corruption of what the user commits or pushes" — the user believes they are pushing to their configured remote/branch upstream, but the actual network target used for proxy/credential resolution can be a URL that no longer matches that remote name. The report's guard here is observability-only (a non-fatal exception sent for telemetry), not a corrective or blocking control, so the mismatched push is allowed to continue exactly as the vulnerable `participate` function still recorded the corrupted `position.amount`/`position.token` pair despite the invariant violation.

### Likelihood Explanation
The trigger requires only ordinary Desktop background activity plus attacker-controlled GitHub API data (e.g., a repository rename/transfer reflected in `clone_url`, which `updateRemoteUrl` uses to auto-rewrite the local remote's URL) racing with a fetch/branch refresh that updates `branch.upstreamRemoteName`, followed by the user pressing "Push" while these two states are transiently out of sync. Desktop performs these background refreshes automatically and non-deterministically relative to user actions, so the race window, while narrow, is not something requiring local/physical access, admin rights, or social engineering — it is a normal consequence of asynchronous background repository refresh interacting with a user-triggered push.

### Recommendation
Do not construct a mixed `{ name, url }` remote from two independently-sourced fields. Re-resolve the remote by name at push time (single authoritative lookup, e.g. `gitStore.remotes.find(r => r.name === remoteName)`), and if no remote with that exact name can be found, fail the push (prompting the user or falling back to publish flow) instead of proceeding with a `sendNonFatalException` telemetry-only warning. This mirrors the report's own recommendation: eliminate the ability for two racing updates to produce an internally inconsistent "position" (here, remote identity) that is used to authorize a state-changing action (a push).

### Proof of Concept
1. Open a repository in Desktop where the current branch has an upstream tracking branch on `origin`.
2. Trigger a background GitHub repository refresh (this happens automatically, e.g. on repository selection / periodic background refresh calling `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`), where the associated GitHub repository's `clone_url` has changed (e.g., the repo was renamed/transferred upstream) such that `updateRemoteUrl` rewrites `origin`'s URL via `gitStore.setRemoteURL`. [7](#0-6) 
3. Immediately before that background write completes/propagates to `repositoryStateCache`'s `remote` state, trigger a push. `performPush` captures `state.remote` (with the pre-update `.url`) while `branch.upstreamRemoteName` may already reflect updated tracking info from a concurrently completed fetch/refresh. [8](#0-7) 
4. `safeRemote = { name: remoteName, url: remote.url }` is built, mismatching name and url; the mismatch is only reported via `sendNonFatalException`, and the push proceeds with the inconsistent remote. [9](#0-8) 

Note: Reproducing the exact timing window requires instrumenting/delaying the async refresh calls (e.g. via test mocks) to force the race deterministically; this was not independently executed against a running Desktop instance as part of this analysis — the finding is based on static code evidence including the developers' own comment acknowledging the race and its non-blocking mitigation.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
