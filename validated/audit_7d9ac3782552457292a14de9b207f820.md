### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read` enables CPU denial of service - ([File: crypto/dkg/src/lib.rs])

### Summary
An attacker-controlled serialized `ThresholdKeys` blob can declare `t = n = u16::MAX` and select Lagrange interpolation, causing deserialization to perform approximately `t²` scalar operations while reconstructing the group key. This is a medium-severity computational denial-of-service analog reachable through the explicitly exposed `ThresholdKeys::read` parser.

### Finding Description
`ThresholdKeys::read` reads attacker-controlled `t`, `n`, and `i` directly from the input, then selects Lagrange interpolation when the interpolation byte is `1`. [1](#0-0)  It subsequently reads `n` verification shares and passes those parameters into `ThresholdKeys::new`. [2](#0-1) 

For Lagrange interpolation, `ThresholdKeys::new` computes the group key by evaluating `interpolation_factor` independently for every participant in `1..=t`. [3](#0-2)  Each `interpolation_factor` call iterates over the complete `included` set and performs scalar multiplication for every other participant. [4](#0-3)  Therefore, `t = n = 65,535` causes roughly `65,535²` inner-loop iterations from an input containing only `65,535` fixed-size verification-share encodings.

### Impact Explanation
An unprivileged party able to submit serialized threshold keys to `ThresholdKeys::read` can make a victim spend CPU time quadratic in the serialized participant count. With maximum `u16` parameters, the parser performs billions of field operations and tens of thousands of point multiplications before returning a usable key, allowing a small serialized input to stall a signing, key-management, or verification thread.

### Likelihood Explanation
The required input is structurally valid: `t`, `n`, and `i` satisfy `ThresholdParams::new`, participant indexes cover `1..=n`, and every encoded scalar and point can be canonical. [5](#0-4)  The participant iterator also explicitly handles `u16::MAX`, so the maximum-sized participant set is accepted rather than rejected or short-circuited. [6](#0-5)  Exploitability depends on an integration accepting serialized `ThresholdKeys` from an untrusted source, but that parser is one of the intended untrusted-input boundaries for this audit scope.

### Recommendation
Enforce a protocol-level maximum `n` and expected `ThresholdParams` before allocating or performing interpolation, rather than allowing serialized `t`/`n` to reach `u16::MAX`. Alternatively, compute Lagrange factors using an algorithm with sub-quadratic total complexity, or store/recover the already-computed group key under authenticated key metadata so deserialization does not repeat quadratic reconstruction.

### Proof of Concept
```rust
use ciphersuite::{
  Ciphersuite,
  group::{ff::PrimeField, GroupEncoding},
};
use dalek_ff_group::Ristretto;
use dkg::ThresholdKeys;

let n = u16::MAX;

let mut input = Vec::new();

// Ristretto's C::ID is b"ristretto".
input.extend_from_slice(&9u32.to_le_bytes());
input.extend_from_slice(b"ristretto");

// Valid parameters: t = n = u16::MAX, i = 1.
input.extend_from_slice(&n.to_le_bytes());
input.extend_from_slice(&n.to_le_bytes());
input.extend_from_slice(&1u16.to_le_bytes());

// Select Lagrange interpolation.
input.push(1);

// Canonical scalar encoding for the secret share.
input.extend_from_slice(
  <<Ristretto as Ciphersuite>::F as PrimeField>::ONE.to_repr().as_ref(),
);

// One canonical verification-share point for each participant.
let point = <Ristretto as Ciphersuite>::generator().to_bytes();
for _ in 0..n {
  input.extend_from_slice(point.as_ref());
}

// Enters ThresholdKeys::new and performs O(n²) Lagrange work.
let _keys = ThresholdKeys::<Ristretto>::read(&mut input.as_slice());
```

`C::read_F` and `C::read_G` consume fixed-size canonical encodings, so the preceding buffer is linear in size while triggering quadratic work. [7](#0-6) [8](#0-7)
