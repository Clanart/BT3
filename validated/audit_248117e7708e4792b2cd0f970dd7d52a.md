## Title
Silent Escrow-Release on Failed ERC-20 Transfer in Tron `IntentGatewayV2::withdraw` / `SweepDust` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The Tron build of `IntentGatewayV2` releases escrow, sweeps dust, and pays relayer fees using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the *call itself* did not revert (`success`). It never decodes/validates the ERC-20 `transfer` return value. This is the exact bug class from the external report (unchecked ERC20 return value), reproduced locally in the bridge's escrow-release path rather than a gacha payout.

## Finding Description
In `withdraw()`: [1](#0-0) 
tokens are sent to the beneficiary via a raw `.call`, and the escrow ledger `_orders[body.commitment][token]` is decremented and `_filled[body.commitment] = beneficiary` is set unconditionally once `success` is true — regardless of what boolean the token's `transfer` function actually returned: [2](#0-1) 

The same pattern repeats for transaction-fee redemption and for `SweepDust`: [3](#0-2) [4](#0-3) 

For a non-standard ERC-20 token (common on TRON/TVM, e.g. tokens that return `false` on failure instead of reverting — paused tokens, blacklist-gated tokens, tokens with insufficient balance guarded by a `require`-free `if` branch), the low-level `call` succeeds (returns `success == true`) even though the encoded return data is `false`. The contract has no code path checking that returned boolean, unlike the SafeERC20-based sibling implementations, which correctly use `safeTransfer`/`safeTransferFrom`: [5](#0-4) 

Note the inconsistency within the same Tron contract: token *deposits* into escrow correctly use `safeTransferFrom` (which does check the boolean via OpenZeppelin's SafeERC20): [6](#0-5) 
but the *release* path (`withdraw`, fee redemption, dust sweep) reverted to the unchecked pattern. This asymmetry is exactly the "transfer succeeds silently while returning false" defect described in the external report, now sitting on the escrow-release leg of bridge custody rather than a reward payout.

## Impact Explanation
This is a fund-loss/false-settlement bug in bridge custody:
- `_orders[body.commitment][token] -= amount` and `_filled[body.commitment] = beneficiary` are committed as if the payout succeeded, permanently marking the order filled/refunded and emitting `EscrowReleased`/`EscrowRefunded` events, even though the beneficiary received zero tokens.
- Because the escrow accounting is already decremented and the commitment is already marked filled, the tokens the contract never actually delivered are irrecoverably locked/stranded inside `IntentGatewayV2` — the beneficiary has no further path to reclaim them since `UnknownOrder()` will trigger on any retry (escrow already zeroed) and `_filled[commitment]` blocks resubmission.
- The same defect on the fee-redemption leg silently drops relayer/protocol fee payouts.
- The same defect on `SweepDust` silently "sweeps" dust that actually stays on the contract, misleading the `DustSwept` event/accounting.

This matches the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories: the on-chain escrow state falsely records a successful release for an unprivileged intent originator/beneficiary using a non-compliant input/fee token, and the loss is unrecoverable through any code path in this contract.

## Likelihood Explanation
Likelihood is Low, matching the report's own rating — it requires the escrowed token (input token or the fee token configured via `IDispatcher(host()).feeToken()`) to be a non-standard ERC-20 that returns `false` on failure rather than reverting. Given that IntentGateway is designed to be token-agnostic (arbitrary tokens per intent), and TRON's TRC-20 ecosystem contains several such non-compliant tokens, this is a realistic configuration rather than a purely theoretical one, and it triggers on the normal, permissionless `onAccept`/`withdraw` flow driven by legitimate cross-chain responses — no malicious relayer/prover assumption is required.

## Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw`, the fee-redemption block, and `SweepDust`) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used for `safeTransferFrom` on the deposit side and used by `IntentsBase.sol`'s `_withdraw`/`_execute`. This ensures a `false` return value reverts the whole `withdraw`/`onAccept` call instead of silently marking escrow released.

## Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and register an intent whose input token, or the configured `feeToken()`, is a TRC-20 token `T` where `transfer()` returns `false` on failure instead of reverting (e.g., a token that checks balance with `if (balance[from] < amount) return false;` rather than `require`).
2. Have a solver fill the order; escrow is recorded via `safeTransferFrom` (deposit path is fine).
3. Drain/blacklist the gateway's balance of `T` (or otherwise make the transfer condition fail) so that `T.transfer(beneficiary, amount)` returns `false` without reverting.
4. Trigger `onAccept` with `RequestKind.RedeemEscrow`/`RefundEscrow` (or the GET-response path via `onGetResponse`), calling `withdraw()`.
5. Observe: `token.call(...)` returns `success == true` (outer call succeeded) even though inner `transfer` returned `false`; `_orders[commitment][token] -= amount` executes, `_filled[commitment] = beneficiary` is set, and `EscrowReleased` is emitted — but `beneficiary`'s `T` balance never increased. The tokens are now stranded in the contract with no recorded claim on them.
