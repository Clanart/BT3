### Title
Git's built-in recursive-clone submodule protection is force-disabled during clone, re-opening the file/ext protocol submodule attack that `protocol.file.allow` gating elsewhere is meant to prevent - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` function unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and always passes `--recursive` when cloning. `GIT_CLONE_PROTECTION_ACTIVE` is Git's own built-in safeguard (added as part of the CVE-2022-39253 fix) that blocks a recursively-cloned submodule from using unsafe transports (e.g. `file://`, `ext::`) or symlinked repository directories that can be used to read/write files outside the intended clone target. Desktop deliberately turns this protection off for every clone, while a *different* code path in the codebase (`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts`) treats "allow file protocol for submodules" as something that must be explicitly and narrowly opted into via an `allowFileProtocol` parameter. This is the same "invariant enforced in one code path, silently missing in the other" pattern as the original report (EOA check enforced at creation, missing at rotation): the file/unsafe-protocol submodule guard is respected as an opt-in gate in the submodule-update path but is structurally disabled for the initial `git clone --recursive` path.

`GIT_CLONE_PROTECTION_ACTIVE=false` explicitly opts out of Git's built-in protection that inspects `.gitmodules` entries during a recursive clone and refuses to process submodule URLs/paths that could escape the intended destination (unsafe protocols such as `file://`/`ext::`, or symlink-based submodule paths).

Contrast this with `updateSubmodulesAfterOperation`, used for submodule updates after checkout/pull, which only allows the `file://` protocol when an explicit `allowFileProtocol` flag is passed by the caller: [3](#0-2) 

So the codebase clearly treats "allow unsafe/local submodule protocols" as a sensitive, opt-in capability elsewhere, but the initial clone path bypasses Git's own equivalent protection entirely and for every clone, regardless of whether the target repository is trusted.

### Impact Explanation
The attacker's primitive here is a cloned repository the attacker fully controls (matches the accepted threat model: "attacker controls a cloned/fetched repository"). By committing a `.gitmodules` file with a submodule URL that uses `ext::` (arbitrary command execution via Git's `ext::` transport) or a submodule path that is a symlink pointing outside the working tree, the attacker can get code executed or files written/read outside the intended clone directory the moment the victim clones the repository in Desktop - because `GIT_CLONE_PROTECTION_ACTIVE=false` disables the exact Git-side check designed to stop this. This is a corruption of the value that matters most in this scenario: the integrity/scope of the clone destination and the trust boundary between "files the user asked Desktop to fetch" and "arbitrary paths/processes on the host."

### Likelihood Explanation
Every single clone performed through Desktop's UI runs through this code path with the protection off, and cloning arbitrary/public repositories (including ones from links, forks, or untrusted sources) is a core, everyday feature of the app. No special user action beyond "clone this repository" is required, which is consistent with the accepted "unprivileged, attacker-controlled repository" impact category and does not require local/physical access, prior malware, or leaked credentials.

### Recommendation
Do not unconditionally disable `GIT_CLONE_PROTECTION_ACTIVE`. Only opt out of it (if ever) using the same narrow, explicit gating pattern already used in `submodule.ts`'s `allowFileProtocol` parameter, and only for trusted/local scenarios (e.g. local-repository test fixtures), not for arbitrary user-initiated clones of remote/untrusted URLs. At minimum, keep Git's default clone protection active for all `clone --recursive` operations initiated against non-local/untrusted remotes.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file with an entry such as:
   ```
   [submodule "evil"]
       path = evil
       url = ext::sh -c "id > /tmp/pwned"
   ```
2. Victim uses Desktop's "Clone repository" feature to clone the attacker's URL.
3. `clone()` in `app/src/lib/git/clone.ts` runs `git ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment, disabling Git's own guard against processing the unsafe `ext::` submodule URL during the recursive clone.
4. Because the protection is disabled at the environment level for this call (unlike the opt-in `allowFileProtocol` gating used for submodule updates elsewhere), the submodule URL is processed and the embedded command executes on the victim's machine as part of the clone.
