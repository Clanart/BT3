## Title
Recursive precompile calls share a single `BalanceHandler` instance, causing StateDB/bank balance desync via corrupted `prevEventsLen` tracking — (File: `precompiles/common/balance_handler.go`, `testutil/testdata/debug/debug.go`)

## Summary
This is a structural analog of the `LlamaRelativeQuorum.validateActionCreation` bug: a value meant to be captured as a **local snapshot per call/scope** (there: `actionApprovalSupply`/`actionDisapprovalSupply` at action-creation time; here: `prevEventsLen` marking "where in the event log this precompile invocation started") is instead stored on a **shared, reusable object** whose state can be overwritten by an unprivileged, ordinary re-entrant/recursive call before the original scope reads it back. This breaks the invariant that each precompile invocation's post-processing (`AfterBalanceChange`) only reconciles the bank events emitted *by that specific invocation* into the EVM `StateDB`.

## Finding Description
`BalanceHandler` records a snapshot index into the event log so it can later slice out exactly the bank events produced by one precompile call: [1](#0-0) 

```
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int
}

func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}
```

`AfterBalanceChange` then only looks at `events[bh.prevEventsLen:]` to update `stateDB.AddBalance`/`SubBalance`: [2](#0-1) 

The "correct" pattern (used generically for stateful precompiles) allocates a **fresh** `BalanceHandler` per call via a factory inside `runNativeAction`: [3](#0-2) 

However, the repository itself documents and has a dedicated regression test proving that when a `BalanceHandler` is **not** freshly instantiated per call — i.e. when it is held as a single shared field on a precompile struct and the precompile is invoked recursively/re-entrantly (a contract calling the precompile, which calls back into EVM code that calls the precompile again, as in `testutil/testdata/debug/debug.go`) — the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` while the outer call is still pending. When the outer call's `AfterBalanceChange` finally runs, it slices the event log from the *inner* call's start index, not its own, causing bank events to be mis-attributed, double-applied, or dropped when reconciling into `StateDB`: [4](#0-3) 

This is exactly analogous to the Llama bug: an unprivileged actor (any contract that triggers a nested precompile call, e.g. via `call`/`delegatecall`/`staticcall` re-entering a precompile) can cause a shared "snapshot" value to be overwritten mid-flight, corrupting a downstream accounting computation that other code paths rely on being consistent.

## Impact Explanation
`StateDB.AddBalance`/`SubBalance` are the balances the EVM uses for all subsequent value-transfer and balance-check logic within the same transaction (and are what get committed to the native bank balances at the end of the EVM message). If bank events are mis-sliced across nested precompile calls:
- Balance updates from an inner call could be replayed again into `StateDB` when the outer call's `AfterBalanceChange` also includes them (double-application), or
- Balance updates from the outer call could be silently dropped (events consumed once and not applied at all),
- leading to `StateDB` balances diverging from the `x/bank` keeper's actual balances for the accounts involved.

This falls squarely under the Critical impact of "irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets," since a discrepancy between StateDB and bank-keeper balances directly enables either unauthorized value creation (inflated `StateDB` balance usable for subsequent spends within the same tx before commit) or loss/freezing of funds (bank balance changed but not reflected/reflected twice in EVM state), and can also produce AppHash divergence if such state ends up inconsistently derived across nodes.

## Likelihood Explanation
Reachability depends on whether any **production** (non-test/non-debug) static or dynamic precompile keeps a `BalanceHandler` as a persistent field rather than obtaining a fresh one per call via the `BalanceHandlerFactory` pattern in `runNativeAction`, and whether that precompile can be re-entered recursively by ordinary unprivileged contract calls (e.g., staking/distribution/gov/bank/ICS20 precompiles calling back into the EVM, or a caller contract using `call`/`delegatecall`/`callcode` to re-enter the same precompile, as demonstrated in `precompiles/staking/testdata/StakingCaller.sol`). The regression test in `evmd/tests/integration/balance_handler/balance_handler_test.go` uses the `testutil/testdata/debug` precompile specifically to reproduce this, which is test-only scaffolding — I was not able to fully confirm within the available iterations whether any production precompile (staking, distribution, gov, ICS20, bank, erc20) instantiates its `BalanceHandler` in the same unsafe (shared-instance) pattern versus the safe per-call factory pattern in `precompiles/common/precompile.go`. This is the key open question that determines whether this is exploitable in production.

## Recommendation
- Confirm that every production precompile obtains a **new** `BalanceHandler` per `Run`/`Execute` invocation (as `precompiles/common/precompile.go`'s `runNativeAction` already does via `BalanceHandlerFactory.NewBalanceHandler()`), never a struct field reused across calls.
- If any production precompile currently holds `BalanceHandler` as a shared/singleton field (as the debug precompile pattern does), refactor it to allocate a fresh handler per call, or make `prevEventsLen` re-entrancy-safe (e.g., a stack of snapshot indices instead of a single scalar) so nested calls cannot clobber an outer call's starting offset.
- Add a re-entrancy/nesting regression test equivalent to `TestRecursivePrecompileCallsWithDebugPrecompile` against each production precompile that supports recursive invocation, asserting `StateDB` balances match `x/bank` balances after nested calls.

## Proof of Concept
The repository already contains a working PoC demonstrating the underlying mechanism (shared `BalanceHandler` instance across recursive precompile calls desyncing balances): [5](#0-4) 

This test deploys a caller contract that recursively invokes the debug precompile (`callback`), and the suite comment explicitly states the intended outcome: "This leads to balance desync between native bank keeper and EVM stateDB." Full confirmation that a **production** (non-debug) precompile is vulnerable to the same shared-instance pattern would require directly inspecting each precompile's struct definition (staking, distribution, gov, bank, erc20, ICS20) for a `balanceHandler` field versus factory-based instantiation, which I could not complete before running out of tool iterations.

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index

		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
