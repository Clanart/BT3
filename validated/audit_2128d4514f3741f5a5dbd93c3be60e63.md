### Title
FROST cached-preprocess seed is never removed from `CachedPreprocesses`, enabling nonce reuse and secret-share recovery - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
Analogous to the Linux bug (an `hctx` reused while still registered in a callback list, causing use-after-free), `SigningProtocol::preprocess_internal` stores the FROST preprocess seed in `CachedPreprocesses` keyed only by `context` and **never deletes it**. Every subsequent call to `preprocess`, `share`, or `complete` for the same context re-derives identical nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`ChaCha20Rng::from_seed(seed)`). If `share_internal` is driven twice with distinct preprocess sets (different `included` participants → different FROST binding factor ρ) or a different message, two signature shares are produced under the same secret nonces, which the FROST docs in this repo state enables recovery of the signer's private key share.

### Finding Description
- `create_db!` declares `CachedPreprocesses: (context: &impl Encode) -> [u8; 32]` — a persistent map with no deletion path (`coordinator/src/tributary/signing_protocol.rs:86-90`).
- `preprocess_internal` only writes the seed when absent, then always reloads and reuses it (`coordinator/src/tributary/signing_protocol.rs:123-145`). There is no `CachedPreprocesses::del`/remove after a share is produced — the stale entry is "reused while not removed", exactly matching the CVE's bug shape.
- `share_internal` calls `preprocess_internal` again (`:156`), and `DkgConfirmer::complete` re-executes `share_internal` with a caller-supplied `preprocesses` map (`:312-327`), so `sign()` is reached multiple times under one cached seed.
- In `crypto/frost/src/sign.rs:127-141`, `seeded_preprocess` derives `nonces` deterministically from the seed, so repeated `sign()` calls reuse `d, e`. In `sign`, `rho` is computed over the per-participant `preprocesses` set and `msg` (`crypto/frost/src/sign.rs:283-318`), so a different participant set or message yields the same nonces bound to a different challenge — the classic FROST nonce-reuse equation pair `share_i = d + e·ρ_i + λ_i·s·c_i` that solves for `s`.
- The file's own header (`:25-54`) acknowledges nonce reuse is "explicitly unsafe" and relies purely on BFT message ordering rather than a code-level once-guard; it even carries a TODO admitting the preprocess-consistency check is missing.

### Impact Explanation
A recovered secret share `s` for the validator's MuSig key breaks the threshold signing root of trust: with a recovered share (or shares across validators), an attacker can forge Schnorrkel/MuSig signatures over `set_keys_message` / batch confirmations, i.e., concrete signing of unintended messages and key-share recovery — explicitly listed as acceptable impact. Severity: High.

### Likelihood Explanation
The trigger requires `share`/`complete` to run more than once per `(context)` with non-identical preprocess sets or messages. `preprocesses` and `shares` maps are populated from externally supplied tributary data (participant-indexed byte blobs read via `read_preprocess`), so a participant can cause the coordinator to attempt signing under different included sets (e.g., shares arriving in a later block than the original preprocesses, or a second data item for the same attempt). I could not fully verify the dedup behavior in `coordinator/src/tributary/handle.rs` within the iteration budget; if handle.rs does not suppress the second invocation, the leak is directly reachable from public inputs, matching the CVE pattern of a stale entry reused because it was never deregistered.

### Recommendation
Delete `CachedPreprocesses[context]` immediately after the first successful `sign()` (i.e., inside `share_internal`, after `machine.sign` succeeds), or record a `SharePublished` flag per context and refuse to call `preprocess_internal`/`share_internal` again. Additionally, before publishing a share, verify the locally derived preprocess equals the one committed on-chain (the existing TODO) so a re-executed machine cannot emit a second share under a different binding set.

### Proof of Concept
1. Validator participates in `DkgConfirmer` for `attempt = a`; `share(preprocesses_A, key_pair)` publishes share `σ1` over the included set `I_A` → binding factor `ρ_A`, nonce `R = d·G + e·H` reused from the cached seed.
2. A second data item supplies `shares`/preprocesses for a different included set `I_B` (any participant who did not submit in round one submits later), causing `complete` → `share_internal` → `machine.sign(preprocesses_B, msg)` — the same seed regenerates identical `d, e`, producing share `σ2` with `ρ_B ≠ ρ_B`.
3. Solve: `σ1 = d + e·ρ_A + λ_A·s·c`, `σ2 = d + e·ρ_B + λ_B·s·c`. Two equations in `d, e` (ρ and λ are public) yield `d, e`; then `s = (σ1 − d − e·ρ_A)/(λ_A·c)` recovers the validator's private key share — precisely the leak the `CachedPreprocess` docs warn against (`crypto/frost/src/sign.rs:84-87`).
