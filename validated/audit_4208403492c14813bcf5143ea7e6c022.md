### Title
Scanner reports immature coinbase outputs as spendable, producing unspendable funding transactions - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Footium issue where rewards are sent to a destination that cannot actually receive them, `Scanner::scan_block` credits coinbase outputs to the wallet indistinguishably from normal outputs. The resulting `ReceivedOutput`s are not spendable for 100 blocks, so any `SignableTransaction` built from them is consensus-invalid.

### Finding Description
`Scanner::scan` matches outputs purely on `script_pubkey` against its registered script table and pushes a `ReceivedOutput` carrying only `{offset, output, outpoint}` — no maturity or coinbase flag is recorded (`mod.rs:199-214`). `scan_block` then iterates `block.txdata` starting at index 0, i.e. it includes the coinbase transaction (`mod.rs:221-227`). Coinbase outputs cannot be spent until 100 confirmations (BIP/consensus rule `COINBASE_MATURITY`).

Downstream, `SignableTransaction::new` consumes `ReceivedOutput`s and `TransactionSignMachine::sign` produces BIP-341 key-spend signatures committing to `Prevouts::All` (`send.rs:150-256`, `send.rs:373-397`). A transaction spending an immature coinbase prevout will be rejected by every full node regardless of signature validity — the threshold signing round completes "successfully" but yields a transaction that can never confirm, and the wallet/accounting layer has no way to distinguish the offending output since `ReceivedOutput` exposes only `offset()`, `output()`, `outpoint()`, `value()` (`mod.rs:99-118`). The only mitigation is a doc comment advising callers to "scan `block.txdata[1 ..]`" or post-filter — nothing in the type system or API enforces it.

### Impact Explanation
Any coins a miner directs to the Serai vault script in a coinbase output are reported as received and immediately enter the spendable UTXO set. A spend attempted before maturity burns a full FROST signing ceremony and produces a permanently invalid transaction; if the coordinator retries or treats the failure as final, funds appear received yet are unspendable — matching the accepted "funds reported received that are not spendable" impact class. Re-org of a matured-then-orphaned coinbase produces the same failure at any depth < 100.

### Likelihood Explanation
Medium. It requires a miner (unprivileged third party) to pay the vault's Taproot script in a coinbase output — unusual but possible, and indistinguishable to the scanner from a legitimate deposit. Integrators using `scan_block` as the natural whole-block API get no error or marker; the hazard exists only in a docstring.

### Recommendation
Have `scan_block` skip `block.txdata[0]` by default, or annotate `ReceivedOutput` with a `coinbase`/maturity flag and have `SignableTransaction::new` reject immature coinbase inputs.

### Proof of Concept
```rust
// A miner pays the vault's p2tr script_pubkey in the coinbase of block B.
let scanner = Scanner::new(tweaked_vault_key).unwrap();
let received = scanner.scan_block(&block_b);           // includes txdata[0]
// received[0] is a ReceivedOutput with no maturity marker.
let stx = SignableTransaction::new(received, &payments, None, None, fee).unwrap();
// Signing completes, producing a tx whose input prevout is an immature coinbase.
// Every node rejects it: "bad-txns-premature-spend-of-coinbase".
```
