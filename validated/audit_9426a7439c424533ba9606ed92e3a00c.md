### Title
Non-atomic mint-before-fallible-dispatch in `HyperFungibleToken::on_accept` allows unbounded token duplication via replay-on-failure - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-ismp`'s design explicitly documents that if an `IsmpModule::on_accept` returns `Err`, the request receipt is deleted so the request can be retried/replayed later, and puts the burden on the module to "maintain all invariants before modifying its internal state to prevent partial state changes." `HyperFungibleToken::on_accept` violates this contract: it mints/transfers the bridged `amount` to the beneficiary *before* executing the optional, fallible `call_data` payload. If that payload dispatch fails deterministically, `on_accept` returns `Err`, the receipt is deleted, and the identical `PostRequest` (with its original membership proof) can be resubmitted, re-minting the same `amount` again — with no cap on the number of replays before the request times out.

### Finding Description
`modules/pallets/hyper-fungible-token/src/module.rs::on_accept` (lines 50-212) performs, in order:
1. Resolve `local_asset_id`, decode `message`, convert `amount`.
2. **Mint or transfer `amount` to `beneficiary`** [1](#0-0) 
3. If `message.data` is non-empty, decode `SubstrateCalldata`, optionally verify a signature, decode a `RuntimeCall`, check `BaseCallFilter`, and `dispatch()` it — any failure here (`CalldataDecodeError`, `SignatureDecodeError`, `SignatureVerificationFailed`, `RuntimeCallDecodeError`, `CallFiltered`, `CallDispatchError`) returns `Err` via `?` [2](#0-1) .

The framework-level caller, `modules/ismp/core/src/handlers/request.rs::handle`, stores a request receipt before calling `on_accept`, and on `Err` **deletes the receipt so the request can be retried** — there is no rollback of storage mutations performed inside `on_accept` itself: [3](#0-2) 

This deliberate "delete-on-failure" behavior is officially documented as safe only if the module avoids state changes before points that can fail: [4](#0-3) 

Since the mint/transfer happens in step 2, *before* the fallible calldata-execution step 3, any message whose `call_data` is engineered to always fail deterministically (e.g. a `runtime_call` filtered by `BaseCallFilter`, a malformed call that fails `Decode`, or a bogus/garbage signature that always fails `ed25519_verify`/`sr25519_verify`/ECDSA recovery) will cause the mint to execute, and then `on_accept` to return `Err` on every single replay. Because the receipt is deleted each time, the same `PostRequest` + membership proof can be resubmitted to `pallet-ismp`'s `handle` extrinsic (publicly callable, permissionless up to timeout) an arbitrary number of times before `timeout_timestamp` elapses, each time re-minting/re-transferring the same `amount` to `beneficiary`.

I was not able to find an explicit `#[transactional]` wrapper around the per-request `on_accept` invocation in `handlers/request.rs` or `pallets/ismp/src/lib.rs` that would automatically roll back the mint on `Err` (the only `transactional` match in the ismp pallet is unrelated to this call path); this is stated as an area of residual uncertainty since I could not fully audit every layer of the pallet dispatch machinery, but no rollback mechanism protecting `on_accept`'s partial mutations was found.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant. A single escrowed deposit on the source chain (paid once via `send()`) can, on the destination chain, be minted/credited to the beneficiary an unbounded number of times by repeatedly resubmitting the same proven request while the attached calldata is engineered to always fail. This is unauthorized creation of value / double-settlement of a single cross-chain transfer, directly matching the bounty's "stealing or loss of funds" and "replay/double-claim/double-settlement" categories.

### Likelihood Explanation
Any unprivileged user can trigger this: they only need to (a) send a normal cross-chain token transfer through `HyperFungibleToken` with a `call_data` field encoding a `SubstrateCalldata` whose `runtime_call` is guaranteed to fail deterministically (e.g., filtered by the base call filter, or with a garbage signature that will never verify), and (b) resubmit the resulting `PostRequest`'s message + membership proof to `pallet-ismp::handle` multiple times before the request's timeout. No relayer collusion, admin privilege, or leaked keys are required — submitting proven ISMP messages is a standard permissionless relayer action, and the proof for an already-observed request remains valid for replay until timeout.

### Recommendation
Reorder `on_accept` so any irreversible state mutation (mint/transfer to beneficiary) occurs only after all fallible steps (calldata decoding, signature verification, call filtering, and the actual runtime-call dispatch) have succeeded, or make the whole `on_accept` execution transactional (e.g., wrap it in `frame_support::storage::with_transaction` and only commit if the entire function, including the optional calldata dispatch, returns `Ok`). Alternatively, execute the token credit and the calldata dispatch as a single atomic action so that a calldata failure fully reverts the mint before `Err` is returned to the caller.

### Proof of Concept
1. On the source chain, Attacker calls `send()` on the HFT origin (EVM `HyperFungibleToken`/pallet) with:
   - `amount = X`
   - `call_data` = SCALE-encoded `SubstrateCalldata { signature: Some(garbage_65_bytes), runtime_call: <valid transfer call encoded bytes> }` where `garbage_65_bytes` is not a valid signature for any key (guarantees `SignatureVerificationFailed` every time), or simpler: a `runtime_call` targeting a dispatchable excluded by `BaseCallFilter` (guarantees `CallFiltered` every time, independent of nonce).
2. Attacker (or any relayer) submits the resulting `PostRequest` with a valid membership proof via `pallet-ismp::handle` (`modules/ismp/core/src/handlers/request.rs`).
3. `HyperFungibleToken::on_accept` runs:
   - Mints/transfers `X` tokens to `beneficiary` [1](#0-0) .
   - Attempts calldata dispatch, hits `CallFiltered` or `SignatureVerificationFailed`, returns `Err`.
4. `handlers/request.rs::handle` sees `res.is_err()` and deletes the request receipt [5](#0-4) .
5. Attacker resubmits the identical `PostRequest` + proof to `handle` again (same commitment, no `DuplicateRequest` error since receipt was deleted). Step 3 repeats: `beneficiary` receives another `X` tokens, and the calldata fails deterministically again.
6. Repeat step 5 as many times as desired before `timeout_timestamp`, minting `N * X` tokens on the destination chain for a single `X`-token deposit on the source chain.
