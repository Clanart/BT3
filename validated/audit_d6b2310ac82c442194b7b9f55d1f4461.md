## Title
`validateResolutionPaths` fails to confirm a returned `action` corresponds to an actual delete-vs-modify conflict, letting Copilot silently delete or resolve a normal merge-conflict file - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The reported bug class is a validation/invariant check that compares the wrong variable, letting a guard silently pass when it shouldn't. The analogous flaw in GitHub Desktop is in `validateResolutionPaths` (used by the Copilot-assisted merge-conflict-resolution feature). When the model returns a resolution entry with an `action` field (`"keep"` / `"delete"`), the validator unconditionally treats it as a delete-vs-modify resolution and skips the hunk-count check entirely, regardless of whether the corresponding `expectedFiles` entry actually represents a delete-vs-modify conflict (i.e., has a `deleteConflict` field).

### Finding Description
`validateResolutionPaths` is supposed to check that Copilot's JSON response matches the expected set of conflicted files and hunk counts: [1](#0-0) 

The check is:
```ts
for (const resolution of resolutions) {
  // Delete-vs-modify resolutions use action instead of hunks — skip count check
  if (resolution.action !== undefined) {
    continue
  }
  const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
  if (resolution.hunks.length !== expectedCount) {
    throw new CopilotValidationError(...)
  }
}
```
This branches solely on `resolution.action !== undefined` — a value entirely controlled by the LLM's JSON output — instead of checking the *expected* file's own `deleteConflict` metadata (`expectedFiles.find(f => f.path === resolution.path)?.deleteConflict`). The equivalent of the audited bug is present here: the guard compares/branches on the wrong side of the invariant (attacker-controlled model output) rather than the trusted expected value (the actual conflict context built from disk state).

Upstream, `parseCopilotConflictResolution` also accepts `action` for any resolution entry without cross-checking it against the file's real conflict type: [2](#0-1) 

Downstream, `reassembleResolutions` passes an `action`-bearing resolution straight through as a `deleteConflictAction`, bypassing the normal hunk-splicing/reassembly path entirely: [3](#0-2) 

Because `validateResolutionPaths` never verifies that `expectedFiles` actually marked this path as a `deleteConflict` [4](#0-3) 
a model response that (mistakenly, or as a result of a compromised/attacker-influenced repository prompting adversarial model output — e.g. via crafted commit messages, PR titles/bodies, or file contents fed into the prompt at `formatConflictContextForPrompt`) emits `{"path": "normal-file.ts", "action": "delete"}` for a file that is a genuine three-way text conflict will pass validation. This is then applied as `deleteConflictAction: "delete"` for a file whose real conflict state has actual content on both sides, resulting in either the file's content being effectively discarded or a "keep" action being applied without ever validating/reassembling per-hunk resolved content — silently corrupting what the user commits.

### Impact Explanation
This breaks the invariant "the resolution behavior applied to a file must match the actual conflict type extracted from the working tree," resulting in silent corruption of the user's merge output for a file that in reality required careful line-level resolution. Since `reassembleResolutions` performs no content reconciliation for `action`-based resolutions (it just returns `resolvedContent: ''` plus the action, applied via the manual conflict resolution path), the user could end up committing a file whose real conflicting content was neither preserved nor properly merged — meeting the "silent corruption of what the user commits" impact criterion.

### Likelihood Explanation
Requires the Copilot conflict-resolution feature to be enabled and the model's JSON response to include a spurious `action` field for a file that isn't a delete-vs-modify conflict. Given that prompt content includes attacker-influenced repository data (PR titles/bodies, commit messages, file content) formatted via `formatConflictContextForPrompt`, and that LLM output is not strictly schema-constrained beyond this validator, this is plausible without any local/admin access — it only requires the user to run automatic conflict resolution on a repository containing adversarial content. The existing "retry once on `CopilotValidationError`" logic in `resolveChunk` does not help here because this exact case doesn't throw: [5](#0-4) 

### Recommendation
In `validateResolutionPaths`, cross-check `resolution.action` against the corresponding `expectedFiles` entry's `deleteConflict` field rather than trusting the model-supplied `action` field alone:
```ts
const fileCtx = expectedFiles.find(f => f.path === resolution.path)
if (resolution.action !== undefined) {
  if (fileCtx?.deleteConflict === undefined) {
    throw new CopilotValidationError(
      `Copilot returned an "action" for "${resolution.path}" but it is not a delete-vs-modify conflict`
    )
  }
  continue
}
if (fileCtx?.deleteConflict !== undefined && resolution.action === undefined) {
  throw new CopilotValidationError(
    `Copilot did not return an "action" for delete-vs-modify conflict "${resolution.path}"`
  )
}
```

### Proof of Concept
1. Trigger a merge with at least one real text conflict (e.g. `src/app.ts` with genuine `<<<<<<<`/`=======`/`>>>>>>>` hunks) and no delete-vs-modify conflicts, so `expectedFiles` for `src/app.ts` has `deleteConflict === undefined` and `hunks.length > 0`.
2. Craft (or induce via adversarial PR/commit content in the prompt) a Copilot response:
```json
{
  "resolutions": [
    { "path": "src/app.ts", "hunks": [], "reasoning": "discarding", "action": "delete" }
  ]
}
```
3. `parseCopilotConflictResolution` accepts this because `action` is `"keep"|"delete"` and `reasoning` is non-empty (`app/src/lib/copilot-conflict-resolution.ts:403-421`).
4. `validateResolutionPaths` sees `resolution.action !== undefined` and `continue`s, never checking `resolution.hunks.length` against the real hunk count for `src/app.ts` (`app/src/lib/copilot-conflict-resolution.ts:511-513`).
5. `reassembleResolutions` returns `{ path: 'src/app.ts', resolvedContent: '', deleteConflictAction: 'delete' }` (`app/src/lib/copilot-conflict-resolution.ts:619-625`), which is applied as a manual "delete" resolution for a file that was never actually a delete-vs-modify conflict — silently discarding the user's real merge content instead of resolving the text conflict.
