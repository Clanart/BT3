### Title
Missing slippage enforcement in `incentiveDeposit`'s bull-mode swap allows self-sandwiching to inflate `vlMGP` bonus payout - (File: wombat/ArbWomUp2.sol)

### Summary
`incentiveDeposit` lets the caller freely choose `_minMGPRec` and `_bullMode`, and passes `_minMGPRec` unchecked into `_bullMGP`'s `ROUTER.swapExactTokensForTokens` call. Because the caller executes the router swap in the same transaction they initiate, they can sandwich the pool to control the reported `amounts[1]` output, which directly and multiplicatively determines `mgpAmountToLcok` (including the `bullBonusRatio` bonus) locked to their own address via `vlMGP.lockFor`.

### Finding Description
In `incentiveDeposit`, `rewardToSend` (a fixed BUSD amount derived deterministically from the caller's own deposited WOM via `getRewardAmount`) is passed to `_bullMGP` when `_bullMode` is true: [1](#0-0) 

`_bullMGP` swaps this fixed BUSD amount for MGP using a caller-controlled `_minRec` (i.e. `_minMGPRec`), with no contract-side floor or oracle check: [2](#0-1) 

Because `_minMGPRec` can be `0`, the swap has no effective slippage protection. The attacker can, within their own transaction (or via a bundled front-run/back-run around it), move the BUSD/MGP pool price on `ROUTER` before calling `incentiveDeposit`, causing the fixed `_busdAmount` to be swapped into an inflated `amounts[1]` MGP output, then restore the price afterward. Since `mgpAmountToLcok = amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR` is locked to `_account` (the attacker, since `_account == msg.sender`), the attacker directly benefits from the inflated MGP amount and the proportionally inflated bonus, both computed from a manipulable spot price rather than a fair market rate. `whenNotPaused` and `nonReentrant` do not prevent this because the manipulation happens via external pool trades in the same transaction, not reentrancy into this contract.

### Impact Explanation
The contract's `bullBonusRatio` bonus is paid from MGP the contract holds beyond what the swap output alone would require (the bonus is `amounts[1] * bullBonusRatio/DENOMINATOR` extra on top of the raw swap output). Since `amounts[1]` is manipulable by the caller through pool-price sandwiching, an attacker can extract a larger real-value MGP lock (principal + bonus) than the fair-market conversion of their earned BUSD reward would justify, at the expense of the shared MGP reserve used to fund bonuses for other legitimate depositors. This corresponds to theft of protocol-owned MGP intended as bonus for the wider depositor pool, realized through repeated same-block sandwich manipulation.

### Likelihood Explanation
This requires no privileged role — any EOA holding enough WOM/BUSD/MGP (or flash-loaned capital) to move the pool briefly can call `incentiveDeposit` with `_bullMode = true` and `_minMGPRec = 0`, sandwiching the router trade themselves. It is fully repeatable per deposit and scales with pool liquidity depth and available capital, making it practically exploitable whenever `bullBonusRatio > 0` and the router pool has modest liquidity.

### Recommendation
Do not let the caller freely set `_minMGPRec`; instead compute an expected output from a time-weighted or oracle price with an enforced maximum slippage tolerance set by governance, or require the router's quoted output to fall within a bounded deviation from a trusted reference price before applying the `bullBonusRatio` bonus. Alternatively, base `mgpAmountToLcok`'s bonus portion on the BUSD input value via a trusted price feed rather than directly on the manipulable `amounts[1]` swap output.

### Proof of Concept
Hardhat test plan:
1. Deploy `ArbWomUp2`, mock `wom`, `busd`, `mgp` ERC20s, a mock `IVLMGP` (`lockFor` just records amount/account), and a mock/real Uniswap-V2-style router with a BUSD/MGP pool seeded with liquidity.
2. Configure `setMultiplier` and `setup` so a deposit of a known WOM amount yields a known `rewardToSend`.
3. As the attacker (single EOA), in one transaction: (a) swap a large amount of MGP into the pool to depress MGP price, (b) call `incentiveDeposit(_amount, 0, true)`, (c) swap back to restore pool price.
4. Compare `mgpAmountToLcok` recorded by the mock `vlMGP.lockFor` against the amount that would result from an unmanipulated pool price for the same `rewardToSend`; assert the manipulated lock is materially larger, demonstrating the attacker captured excess MGP/bonus funded from the shared reserve.
5. Repeat with `_minMGPRec` set to a nonzero, oracle-bound value (post-fix) and assert the transaction reverts or the discrepancy disappears.

    function _bullMGP(uint256 _busdAmount, uint256 _minRec, address _account) internal {
        IERC20(busd).safeApprove(address(ROUTER), _busdAmount);
        
        address[] memory path = new address[](2);
        path[0] = busd;
        path[1] = mgp;
        uint256[] memory amounts = ROUTER.swapExactTokensForTokens(
            _busdAmount,
            _minRec,
            path,
            address(this),
            block.timestamp
        );

        uint256 mgpAmountToLcok = amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR; // get bull mode bonus
        IERC20(mgp).approve(address(vlMGP), mgpAmountToLcok);
        vlMGP.lockFor(mgpAmountToLcok, _account);

        emit VLMGPRewarded(_account, _busdAmount, mgpAmountToLcok);
    }
