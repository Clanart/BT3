### Title
Silent, unauthenticated repointing of a repository's local `origin` remote via identity-string matching instead of stable repository identity - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The report's broken invariant is: an authorization/trust decision (HoneyLocker's codehash-based migration) is made on one piece of identity data while other security‑relevant state (`unlocked`, `HONEY_QUEEN`, `referral`) is not re‑validated for consistency, letting an attacker substitute a different, malicious "destination" object that inherits trust it never earned. The Desktop analog of this bug class is `updateRemoteUrl()`, which decides to silently rewrite a repository's local git `origin` remote based purely on string equality of hostname/owner/name parsed from URLs, never checking the GitHub repository's stable identifier.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` (around lines 4874-4914) periodically refreshes the association between a local repository and its GitHub API record. It calls `matchGitHubRepository()` (`app/src/lib/repository-matching.ts:29-46`), which finds an account purely by comparing the *hostname* of the local `origin` remote to an account's endpoint, and takes the `owner`/`name` straight out of the parsed remote URL text. It then calls `api.fetchRepository(owner, name)` and passes the result to: [1](#0-0) 

`updateRemoteUrl` decides whether to rewrite the on-disk remote URL using only:
- `urlMatchesRemote` — case-insensitive string comparison of hostname/owner/name [2](#0-1) 
- protocol-string equality between old and new URL
- whether the *previously cached* `gitHubRepository.cloneURL` still textually matches the current remote (i.e., "has the user manually edited this remote")

None of these checks ever consult a stable, unforgeable identifier for the GitHub repository (e.g., the numeric `id`/`node_id` returned by the API). The whole trust chain — "is this still the same repository?" — is anchored entirely to the mutable `owner/name` text that was scraped out of the remote URL, exactly the same class of gap as the HoneyLocker bug: identity is authorized via one signal (codehash / owner-name string) while the rest of the trusted configuration (unlocked/queen/referral / actual repository identity) is never re-verified before an authoritative action (fund release / remote rewrite) is performed.

If the `owner/name` slot referenced by a previously-tracked repository is later reused by a different, unrelated GitHub repository — for example after the original owner renames their account or deletes/transfers the repo, and a different party subsequently registers that now-free `owner` login and creates a repository with the same `name` — the next background refresh will:
1. `matchGitHubRepository` still returns a match because the hostname/owner/name string is unchanged.
2. `api.fetchRepository(owner, name)` now legitimately returns the *new*, unrelated (attacker-controlled) repository object, since GitHub's API resolves paths, not identities.
3. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (the current remote still equals the previously cached `cloneURL` text) and, if `apiRepo.clone_url` differs (e.g., different case, protocol-compatible variant, or the attacker's repo has a different canonical clone URL string), calls `gitStore.setRemoteURL(...)` to rewrite the user's `origin` remote to point at the attacker-controlled repository — with no user confirmation and no check that the underlying GitHub repository is actually the "same" resource the user originally added.

Existing guards (protocol match, "remote unchanged from last known cloneURL" check) only guard against *format drift* and *manual local edits*; they do nothing to guard against *the remote endpoint itself having changed ownership on the server side*, because they never look at anything but text derived from the URL.

### Impact Explanation
A subsequent `git push`/`git fetch` performed by Desktop (or by the user, since Desktop wrote the new `origin` URL into `.git/config`) will silently talk to a different, attacker-controlled remote instead of the repository the user believes they're working with. This can result in: pushing the user's commits/credentials-bearing HTTPS URL to an attacker's repository, fetching attacker-controlled history/refs into the user's checkout, and silent corruption of what the user believes they are committing/pushing to, matching the "Valid Impact" criteria (silent corruption of what a user pushes, attacker controls a git remote/API object).

### Likelihood Explanation
Medium: it requires a real-world "name reuse" condition (owner/user renames account or repo is deleted/transferred and the freed slug is squatted by another party) that is outside the app's control and has previously been a known GitHub-wide "repo-jacking" risk. The attacker does not need any special access to the victim's machine — only to control the GitHub-side repository/owner that ends up occupying the previously-associated `owner/name` path — satisfying the "attacker controls a GitHub API object" criterion. It's not "High" because it depends on this name-reuse race occurring for a repository the victim already has cloned in Desktop.

### Recommendation
`updateRemoteUrl` (and `matchGitHubRepository`/`repositoryWithRefreshedGitHubRepository`) should anchor repository identity to the immutable GitHub repository `id` (already fetched from the API and stored as `GitHubRepository.dbID`/API `id`) rather than re-deriving trust solely from owner/name/hostname text. Before silently rewriting `origin`, verify that `apiRepo.id` equals the previously stored GitHub repository id; if the id differs, treat it as a different repository and require explicit user confirmation (similar to the existing `UpstreamAlreadyExists` dialog flow) rather than performing the URL update automatically.

### Proof of Concept
Conceptual PoC (analogous to the Solidity PoC's "migrate to a maliciously-initialized locker"):
1. User clones `https://github.com/victim/repo` in Desktop; Desktop stores `GitHubRepository.cloneURL = https://github.com/victim/repo` and the associated numeric `id`.
2. The `victim` account is later renamed/deleted and a different party registers the `victim` login, creating a new repository named `repo` (different `id`, different content).
3. On the next background refresh, `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` matches by hostname string (`github.com`) and takes `owner="victim"`, `name="repo"` from the still-unchanged local remote URL.
4. `api.fetchRepository('victim', 'repo')` returns the *new* attacker-owned repository (different `id`, but same URL text/shape as before, potentially even the same `clone_url` string).
5. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (local remote text still equals cached `cloneURL` text) and, if any string diverges (e.g., protocol‑compatible clone_url), silently calls `setRemoteURL`, repointing the user's `origin` to the attacker's repository without any prompt — because no step in the chain ever checked whether it is still the *same* repository (`id`), only whether the text superficially matches. export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
