### Title
Unbounded `Kip71GasTarget` governance parameter causes divide-by-zero panic in `NextMagmaBlockBaseFee`, halting block header validation on all honest nodes - ([File: params/kip71_config.go])

### Summary
`FixedRateIrm.setBorrowRate` accepted an unbounded `newBorrowRate` (only checking non-zero), which allowed a value large enough to make `_accrueInterest` revert, permanently locking user funds in the affected Morpho market. The analogous defect in this codebase is the `kip71.gastarget` governance parameter (`Kip71GasTarget`), whose `FormatChecker` is a no-op that accepts any `uint64` value, including `0`, unlike its sibling parameters that have some bound checking. This value is fed directly as a divisor into `KIP71Config.NextMagmaBlockBaseFee`, the function that computes the required base fee for every block and is invoked from `VerifyMagmaHeader` during header verification.

### Finding Description
`Kip71GasTarget` is defined with `Canonicalizer: uint64Canonicalizer` and `FormatChecker: noopFormatChecker`, meaning any `uint64` — including `0` — passes validation: [1](#0-0) 

Unlike `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which have a cross-field consistency check in `checkConsistency` (`ErrLowerBoundBaseFee`/`ErrUpperBoundBaseFee`), `Kip71GasTarget` falls through to the "no more checks" case and is accepted unconditionally: [2](#0-1) 

The accepted value then flows into `KIP71Config.NextMagmaBlockBaseFee`, which uses `gasTarget` as a divisor in both the "increase" and "decrease" branches of the base-fee update: [3](#0-2) 

If `gasTarget == 0` and `parentGasUsed > 0` (the common case, since almost every block uses some gas), execution enters the branch:
```
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // Div by 0 -> panic
```
`math/big.Int.Div` panics on division by zero. This function is invoked from `VerifyMagmaHeader`, which is called on every block header during consensus/header verification. A `gasTarget=0` therefore causes a deterministic panic on every honest node processing any subsequent block (except the edge case where `parentGasUsed == 0`), which is functionally analogous to the Morpho case where an out-of-bounds parameter makes the interest-accrual path permanently revert and lock the market. Here it makes header validation permanently panic, halting block processing across the network.

Note the `BaseFeeDenominator` parameter has a defensive fallback in this same function (`if kc.BaseFeeDenominator == 0 { baseFeeDenominator = 64 }`), showing the codebase authors were aware zero-divisor governance inputs are a risk — but this same defensive pattern was not applied to `GasTarget`.

### Impact Explanation
Once a malicious or erroneous `kip71.gastarget = 0` vote is finalized through governance (KIP-81 GovParam contract or header vote), every node that processes a block header referencing that parameter set will panic inside `VerifyMagmaHeader`/`NextMagmaBlockBaseFee`. Since this is deterministic and reached by all honest nodes identically, it results in a full network halt (all validators/full nodes crash at the same block), which is a chain-availability failure that also blocks all pending transactions, deposits, and withdrawals network-wide until the parameter/software is fixed — a critical, single-point-of-failure impact triggered by one governance vote.

### Likelihood Explanation
`Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, so no additional on-chain code change is required to accept the value — only a successful governance vote reaching quorum needs to set it to `0`. This is lower likelihood than a fully "unprivileged single transaction" trigger (governance changes require reaching quorum among governance council members / GovParam contract voting per KIP-81), but the acceptance-side validation gap is unconditional and exists purely in client code, with no additional runtime safety net (unlike `BaseFeeDenominator`, which has a `==0` fallback).

### Recommendation
Add an explicit lower bound (`v != 0`, mirroring the `Kip71BaseFeeDenominator` FormatChecker) to the `Kip71GasTarget` parameter definition in `kaiax/gov/param.go`, and/or add a defensive zero-check with fallback logic directly inside `KIP71Config.NextMagmaBlockBaseFee` in `params/kip71_config.go`, consistent with the existing `BaseFeeDenominator == 0` fallback, to prevent a division-by-zero panic regardless of how the parameter was set (genesis config, contract governance, or header vote).

### Proof of Concept
1. Set (via header vote or GovParam contract, per KIP-81) `kip71.gastarget = 0` for a block range after Magma is active.
2. Any subsequent block with `parentGasUsed > 0` (essentially any block with transactions) causes `NextMagmaBlockBaseFee` to execute the `Mul`/`Div` sequence with `gasTarget = 0`, hitting `big.Int.Div(x, 0)`.
3. `math/big.Int.Div` panics with "division by zero" inside `VerifyMagmaHeader`, called during header verification on every node — the chain halts.
