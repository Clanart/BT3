### Title
Divergent conflict-marker parsers let a crafted repository file silently corrupt Copilot-assisted merge resolutions - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
GitHub Desktop's Copilot-powered conflict-resolution feature uses **two independently implemented conflict-marker parsers** on the same on-disk file: `extractConflictHunks` (in `app/src/lib/copilot-conflict-context.ts`) determines how many hunks exist and what content is shown to the model, while `reassembleResolvedFile` (in `app/src/lib/copilot-conflict-resolution.ts`) independently re-walks the raw file to decide *where* to splice the model's resolved content back in. The only cross-check between the two paths, `validateResolutionPaths`, compares hunk **counts**, not hunk **positions/content** [1](#0-0) . Because a repository file can be crafted (by anyone contributing a branch/PR that later conflicts) to contain lines that incidentally match the marker regexes as ordinary content, the two parsers can agree on the hunk *count* while disagreeing on hunk *boundaries*, causing Copilot's resolution for one conflict to be spliced at the wrong location — corrupting the file that is then staged, committed, and potentially pushed, without any error surfaced to the user.

### Finding Description
`extractConflictHunks` walks a conflicted file and, for each `<<<<<<<` marker, terminates the "ours" section on the first line matching either the base marker (`|||||||`) or the separator (`=======`), then terminates the "theirs" section on the first line matching the closing marker (`>>>>>>>`) [2](#0-1) . This count feeds `IFileConflictContext.hunks.length`, which is used both to render "Conflict N of M" in the prompt [3](#0-2)  and as the `expectedCount` that `validateResolutionPaths` enforces against the model's response [4](#0-3) .

`reassembleResolvedFile`, however, re-scans the *same raw file content from disk* with a separate, simplified look-ahead that only recognizes `<<<<<<<`, `=======`, and `>>>>>>>` — it has no awareness of the `|||||||` base marker at all — and marks a block well-formed as soon as it sees any `=======` followed eventually by any `>>>>>>>` [5](#0-4) . It then splices `hunkResolutions[hunkIndex]` in strictly by ordinal position, not by matching content or line offsets [6](#0-5) .

Because a source file's legitimate content is completely attacker-controlled (any contributor can add a file containing a markdown horizontal rule `=======`, documentation containing example conflict-marker text, or a string literal shaped like a marker line), it is possible to craft file content such that:
- `extractConflictHunks` groups/terminates hunks at one set of boundaries (driving what is shown to the model and the *count* used for validation), while
- `reassembleResolvedFile`, on its independent re-parse of the identical raw bytes, agrees on the total hunk *count* but disagrees on which physical block of lines corresponds to hunk N.

`validateResolutionPaths` only checks that the returned hunk count per file equals the expected count [4](#0-3)  — it never verifies that the reassembly parser's block boundaries match the boundaries the extraction parser used to build the prompt. This is structurally identical to the original report's flaw: a downstream "count/shape" guard (`require(res >= 0)` in the Solidity report; `resolution.hunks.length !== expectedCount` here) stands in for a full semantic-equivalence check between two independently-implemented but supposedly identical algorithms, and the guard doesn't actually detect divergence between them.

### Impact Explanation
When the two parsers disagree on hunk boundaries while agreeing on count, the LLM's resolved content for conflict N gets spliced into the wrong physical location of the reassembled file [7](#0-6) . This is a silent corruption of the file content GitHub Desktop presents as "resolved" and that the user subsequently commits/pushes via the multi-commit-operation flow (`reassembleResolutions` → `IFileResolution.resolvedContent`) [8](#0-7) . Depending on the crafted content, this could drop/duplicate/misplace code — e.g., silently reintroducing removed security checks, dropping validation logic, or splicing unrelated code fragments into sensitive files — with no error, exception, or visible diff-marker leftover in the common case, since both parsers still "succeed" (they just disagree on where the splice happens). This matches the report's "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
Exploitation requires only that: (1) the victim uses the Copilot conflict-resolution feature (an ordinary, unprivileged UI action), and (2) a merge/rebase/cherry-pick against an attacker-influenced branch produces a real conflict in a file whose *non-conflicting* regions the attacker was able to shape (e.g., a documentation file, README, or fixture the attacker added/edited in a prior, innocuous-looking PR). No local access, elevated privileges, or pre-existing compromise is required — the attacker only needs ordinary contribution access to content that later collides. The main uncertainty is the precise byte-for-byte crafting needed to make the two independent parsers count-match yet boundary-diverge in a reliable, reproducible way; this could not be fully verified end-to-end within the available tools (no ability to execute the parsers against a concrete crafted fixture), but the structural divergence between the two implementations (specifically, `reassembleResolvedFile`'s ignorance of the `|||||||` base marker and its different stopping conditions versus `extractConflictHunks`) is directly observable in the source and is the same class of "two implementations of one invariant that don't actually agree" flaw as the seed report.

### Recommendation
- Eliminate the duplicate parsing logic: have `reassembleResolvedFile` reuse `extractConflictHunks` (or a single shared marker-walking primitive) instead of maintaining an independent, slightly different implementation.
- Strengthen `validateResolutionPaths` (or a new check) to verify that the hunk boundaries used for reassembly are byte-for-byte the same conflict blocks that were shown to the model — not merely that the counts match — e.g., by hashing/recording each hunk's original marker-span offsets at extraction time and asserting reassembly consumes the exact same spans.
- After reassembly, verify the result contains no residual conflict markers and, ideally, diff the reassembled file against the original outside of the recorded hunk spans to confirm non-conflicted regions were preserved unchanged.

### Proof of Concept
Conceptual reproduction (exact byte-level crafting to force count-match/boundary-mismatch was not verified via execution, only via source-code trace):
1. Attacker contributes (in an earlier, unrelated commit) a source/doc file containing an ordinary line that is exactly `=======` (e.g. a markdown horizontal rule) inside content that will later become one side of a real git merge conflict.
2. Victim merges/rebases a branch that produces a genuine conflict in that file, so git inserts real `<<<<<<<`, `=======`, `>>>>>>>` markers around the attacker's pre-existing `=======` line.
3. `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:200-237`) and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:560-579`) — having different stop conditions/marker sets (notably `reassembleResolvedFile`'s lack of `|||||||` handling and different look-ahead break conditions) — parse the surrounding block boundaries differently while still agreeing on the total hunk count for the file.
4. `validateResolutionPaths` passes because only the count is checked [4](#0-3) .
5. `reassembleResolvedFile` splices the model's per-hunk `resolvedContent` at the boundaries it computed, which differ from the boundaries the model actually reasoned about (from `extractConflictHunks`'s output), corrupting the resulting file that Desktop stages for commit.

Given the "final iteration" constraint, this could not be validated against a concrete running instance of the parsers; a Devin session with code execution should build a minimal `.ts` harness feeding a crafted fixture through both `extractConflictHunks` and `reassembleResolvedFile` to confirm a concrete boundary-mismatch input before filing upstream.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
