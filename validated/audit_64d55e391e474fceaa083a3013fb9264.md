### Title
`Scanner::scan_block` reports immature coinbase outputs as received funds that cannot be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The GALA "false top-up" incident is a bug class where a receiver credits a deposit of an asset that is not what it appears to be — value is booked as spendable when it is not. The analog in Serai's Bitcoin wallet is `Scanner::scan_block`, which scans every transaction in a block including `block.txdata[0]` (the coinbase). Coinbase outputs are encumbered by a 100-block maturity rule under Bitcoin consensus, so `scan_block` reports `ReceivedOutput`s that are unspendable at the time they are reported — a deposit credited that cannot actually be moved.

### Finding Description
`Scanner::scan_transaction` iterates over `tx.output` and returns a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` then calls it on `block.txdata` unconditionally (`networks/bitcoin/src/wallet/mod.rs:221-227`):

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

The doc comment concedes the flaw: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" — but no such pass exists in this crate, and nothing in `ReceivedOutput` carries a maturity flag. Downstream, `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) accepts any `Vec<ReceivedOutput>` and builds inputs directly from `input.outpoint`, with no check that the referenced prevout is mature. The resulting transaction will be consensus-invalid for 100 blocks, and — more importantly for the false-deposit class — a consumer of the scanning API treats the output's `value()` as received balance.

The only maturity-aware usage is outside the wallet crate: `processor/src/networks/bitcoin.rs:691` manually skips the coinbase via `block.txdata[1 ..]`, confirming the hazard is real and was worked around at the call site rather than fixed in the library. Any other consumer calling the public `scan_block` (or a processor path change) inherits the bug.

### Impact Explanation
An output paying to a Serai key inside a coinbase transaction is returned to the caller as a fully-formed `ReceivedOutput` with `offset`, `TxOut`, and `OutPoint` populated, indistinguishable from a normal deposit. A coordinator crediting balances from `scan_block` reports funds as received that no signature can move: spending them produces a transaction rejected by every node (BIP-30/coinbase-maturity consensus rule), so any withdrawal funded by such an input silently fails until maturity. This matches the incident's shape — a "deposit" that books value which is not actually available — and satisfies the "funds reported received that are not spendable" impact class.

### Likelihood Explanation
Requires a miner to place a payout to the scanned P2TR script in a coinbase output — an unprivileged, public on-chain action (miners routinely include arbitrary outputs; anyone mining a block or paying a pool to do so can trigger it). Exploitation additionally requires a consumer that spends or credits `scan_block` results without the maturity filter — the crate's own API offers no protection, and the only safe usage exists in out-of-scope processor code. Rated Medium: real incorrect-balance reporting, but conditional on miner action and on the integrator relying on `scan_block` rather than `scan_transaction` over `txdata[1 ..]`.

### Recommendation
In `Scanner::scan_block`, iterate `block.txdata[1 ..]` (skipping the coinbase), matching the handling already present in `processor/src/networks/bitcoin.rs`. If scanning coinbase outputs is desired, `ReceivedOutput` should carry a maturity marker so `SignableTransaction::new` can reject immature inputs instead of building a consensus-invalid transaction.

### Proof of Concept
1. Instantiate `Scanner::new(key)` for a threshold key `key` (`networks/bitcoin/src/wallet/mod.rs:162`).
2. A miner mines a block whose coinbase (`block.txdata[0]`) pays `p2tr_script_buf(key)` with amount `v`.
3. Call `scanner.scan_block(&block)` — it returns a `ReceivedOutput` with `outpoint = (coinbase_txid, vout)` and `value() = v`, identical in form to a confirmed spendable deposit.
4. Pass that `ReceivedOutput` to `SignableTransaction::new` — it succeeds (`send.rs:156`), and `TransactionMachine`/`Schnorr` produce a valid BIP-340 signature over the input.
5. Broadcasting the signed transaction fails: every Bitcoin node rejects it because the coinbase prevout is immature (needs 100 confirmations). The scanner-credited balance was never spendable — a false deposit.
