## Analysis

The report's broken invariant: a single settlement event distributes rewards accrued from many independent contributions in bulk, but the code identifies "who gets paid" using only a single sample point rather than attributing each contribution's reward to its actual contributor — letting an opportunistic actor capture rewards for work/state it did not itself produce.

The direct local analog is in `pallet-consensus-incentives`, the pallet that pays relayers a `CostPerBlock`-scaled reward whenever a `ConsensusMessage` advances a state machine's height. [1](#0-0) 

`FeeHandler::on_executed` is invoked once per batch of processed ISMP messages with the full `messages: Vec<MessageWithWeight>` and `events: Vec<IsmpEvent>` for that batch: [2](#0-1) 

It derives `maybe_relayer_account` by decoding the **signer of only `messages.get(0)`** — the first message in the batch — and ignores the signer of every other message in the same batch. It then scans **all** `IsmpEvent::StateMachineUpdated` events across the whole batch (collapsing to the highest height per state machine) and pays the calculated reward for *every* one of those state-machine advances to that single first-message signer: [3](#0-2) 

Since `handle`-style message submission on `pallet-ismp` is a permissionless entry point that accepts an arbitrary `Vec<Message>`, and each `Message::Consensus` carries its own internal signature (`consensus_msg.signer` / `consensus_msg.consensus_proof`) used purely to attribute the reward — not tied to the extrinsic's actual sender — anyone can bundle messages that were authored/signed by different relayers into one call. Consensus proofs are explicitly documented as public and "freely provided by connected chains", so an attacker doesn't need to compromise or collude with another relayer; they only need to observe an already-broadcast, publicly-verifiable `ConsensusMessage` and repackage it. [4](#0-3) 

## Title
Reward misattribution in `pallet-consensus-incentives::on_executed` pays the entire batch's rewards to the first message's signer - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`on_executed` identifies the relayer to reward by decoding the signature of only `messages[0]`, then pays that single account the reward for every `StateMachineUpdated` event produced anywhere in the batch — including advances caused by other, independently-signed `ConsensusMessage`s bundled in the same call.

### Finding Description
The reward-payout logic:
1. Extracts a single `relayer_account` from `messages.get(0)` only. [5](#0-4) 
2. Builds `highest_per_state_machine` from **all** events in the batch, regardless of which message produced them. [6](#0-5) 
3. Pays the treasury-funded reward (and mints reputation) for every one of those state-machine advances to the single `relayer_account` derived in step 1. [7](#0-6) 

Because ISMP message submission is permissionless and each `Message::Consensus` embeds its own signature independent of who submits the transaction, an unprivileged actor can:
- Grab a valid, already-signed `ConsensusMessage` from another relayer (proofs are public per protocol design).
- Compose their own `handle` call with their own trivial `ConsensusMessage` placed at index 0, followed by the victim relayer's message for a different (or the same) state machine.
- Both messages process successfully and both emit `StateMachineUpdated`, but the whole batch's reward is attributed to the attacker because only `messages[0]`'s signer is read.

This is a wrong-beneficiary bug in a treasury-funded reward path: `T::Currency::transfer` moves funds from `TreasuryAccount` to the attacker instead of the relayer who actually produced/delivered the proof, and `ReputationAsset::mint_into` similarly credits the wrong account. [8](#0-7) 

### Impact Explanation
Direct, repeatable theft of protocol treasury funds (and reputation-asset minting) intended for relayers who actually deliver consensus proofs. The `LastRewardedHeight` watermark (added specifically to prevent double-payment on rollback) does not protect against this because the reward is legitimately owed for that height span — it is simply paid to the wrong account. [9](#0-8) 

### Likelihood Explanation
Medium-to-high: no special privileges, no relayer/prover/admin compromise, and no front-running assumption are required — the attacker only needs to observe a publicly broadcast consensus proof (which the protocol documentation states is freely available) and repackage it as part of their own submission with their own message placed first.

### Recommendation
Attribute each `StateMachineUpdated` event's reward to the signer of the specific `Message::Consensus` that produced it, rather than sampling only `messages[0]`. Pair each consensus message with the events it generated (e.g., by tracking message index/state-machine correlation during dispatch) before computing and transferring rewards.

### Proof of Concept
1. Relayer B broadcasts (or has pending) a valid `Message::Consensus` `M_B` that advances `state_machine_id = X` from height 100 to 200, signed with B's key.
2. Attacker A crafts their own trivial `Message::Consensus` `M_A` for `state_machine_id = Y` (or a minimal no-op-sized advance), signed with A's key, and submits a `handle` extrinsic with `messages = [M_A, M_B]`.
3. Both messages process; `IsmpEvent::StateMachineUpdated` fires for both X (100→200) and Y.
4. `on_executed` decodes only `M_A`'s signer as `relayer_account = A`, then in the `highest_per_state_machine` loop calculates and pays A the reward for **both** X's 100-block advance and Y's advance, plus mints the corresponding `ReputationAsset` to A — even though B did the work for X.

Note: I was unable to fully trace the exact call path that constructs `messages: Vec<MessageWithWeight>` before it reaches `on_executed` (e.g., in `pallet-ismp`'s message handler in `modules/pallets/ismp/src/lib.rs`) to confirm there is no earlier per-message signer/sender check that would prevent unrelated messages from a different submitter being included in the same batch call. This should be verified with a Devin session that can read the full `pallet-ismp::handle` extrinsic and message-processing pipeline to confirm the batch composition is indeed attacker-controlled end-to-end.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
