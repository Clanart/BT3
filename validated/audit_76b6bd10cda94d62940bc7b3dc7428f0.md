### Title
Unsanitized attacker-controlled CW20/CW721 name/symbol used as immutable metadata for permissionless EVM pointer contracts enables token spoofing/phishing - (File: precompiles/pointer/pointer.go)

### Summary
The `AddCW20`/`AddCW721` pointer-creation flow reads `name` and `symbol` straight out of a CosmWasm contract's `token_info`/`contract_info` query response — data fully controlled by whoever deployed that CW20/CW721 contract — and bakes those strings unmodified into a newly created ERC20/ERC721 pointer contract that is then permanently, permissionlessly registered on-chain and exposed via standard `name()`/`symbol()` calls that wallets, explorers, and DEX front-ends trust to identify a token.

### Finding Description
`AddCW20` (and the analogous `AddCW721`) is reachable by any EVM caller through the `pointer` precompile. It queries the target CW20 contract for `token_info`, extracts `name`/`symbol` from the JSON response, and passes them unchecked into the pointer's constructor arguments before deploying the pointer with `evm.Create`: [1](#0-0) 

The same unchecked pattern exists across every legacy version of the precompile (`v552` through the current `v640`), e.g.: [2](#0-1) 

Unlike the `x/tokenfactory` module and `sdk.Coin` denom validation, which enforce strict character/length constraints on user-supplied token identifiers (`ValidateDenom`, `GetTokenDenom`): [3](#0-2) [4](#0-3) 

there is no equivalent validation, length cap, or character filter applied to the `name`/`symbol` values obtained from an arbitrary CW20 contract before they are permanently embedded as immutable pointer contract metadata. Any account can (1) instantiate a CW20 contract whose `token_info` returns `name`/`symbol` equal to (or confusingly similar to, including with control characters, RTL-override characters, or zero-width characters) a legitimate, high-value token such as "USDC" or "USDT", and then (2) call the `pointer` precompile's `addCW20` method to register a permanent ERC20 pointer contract carrying that spoofed identity. Because pointer contract addresses are deterministic/on-chain artifacts trusted by the ecosystem's EVM tooling, this is directly analogous to the reported bug class: attacker-controlled, unsanitized string data flows into a component whose entire purpose is to be trusted and displayed to end-users (here, the EVM `name()`/`symbol()` fields used by wallets and explorers to identify tokens), enabling users to be deceived into interacting with (approving, sending funds to, or trading against) a malicious contract believing it is the legitimate asset.

### Impact Explanation
Successful exploitation lets an attacker mint a look-alike/spoofed ERC20 or ERC721 pointer with a legitimate-sounding `name`/`symbol`, which can be used to phish users or automated integrations (wallets that auto-populate token lists by symbol, price bots, bridges) into transferring funds to or trading against the malicious pointer/backing CW20 contract, leading to concrete fund loss for victims who rely on the spoofed identity rather than the contract address.

### Likelihood Explanation
Likelihood is high in terms of reachability: CW20 contract instantiation and pointer creation via `addCW20Pointer` are both fully permissionless, require no privileged role, and cost only ordinary gas/fees. The only constraint is social engineering effort to make the spoof convincing, which is inherent to this well-known "fake token" bug class and does not reduce technical reachability.

### Recommendation
Validate and sanitize `name`/`symbol` retrieved from CW20/CW721 `token_info`/`contract_info` before using them in pointer construction: enforce a strict allow-listed character set (comparable to `sdk.ValidateDenom`), cap length, strip/reject control characters and non-printable/bidi-override Unicode, and/or clearly disambiguate pointer-derived metadata (e.g., prefix/suffix indicating it is a wrapped/pointer asset) so it cannot be visually confused with canonical token identifiers.

### Proof of Concept
1. Deploy a CW20 contract (e.g., via `sei-wasmd` `MsgInstantiateContract`) whose `token_info` query returns `name: "Tether USD"`, `symbol: "USDT"` (or the same strings embedded with zero-width/control characters for closer visual spoofing).
2. Call the `pointer` precompile's `addCW20Pointer(cwAddress)` method from any EVM account, per `AddCW20`: [5](#0-4) 
3. Observe that a new ERC20 contract is deployed and registered via `SetERC20CW20Pointer`, whose `name()`/`symbol()` return the attacker-supplied "USDT" strings verbatim, indistinguishable at the metadata level from a legitimate USDT pointer, and permanently discoverable by wallets/explorers as `pointer_registered` event data: [6](#0-5) 

Note: I could not fully verify whether any downstream wallet/explorer integration used by Sei performs additional address-based disambiguation that would mitigate real-world phishing risk; that layer is outside this repository's index and would need to be assessed separately (consider a Devin session with full repo/browser access if deeper validation of the downstream UX impact is required).

// GetTokenDenom constructs a denom string for tokens created by tokenfactory
// based on an input creator address and a subdenom
// The denom constructed is factory/{creator}/{subdenom}
func GetTokenDenom(creator, subdenom string) (string, error) {
	if len(subdenom) > MaxSubdenomLength {
		return "", ErrSubdenomTooLong
	}
	if len(creator) > MaxCreatorLength {
		return "", ErrCreatorTooLong
	}
	if strings.Contains(creator, "/") {
		return "", ErrInvalidCreator
	}
	denom := strings.Join([]string{ModuleDenomPrefix, creator, subdenom}, "/")
	return denom, sdk.ValidateDenom(denom)
}
