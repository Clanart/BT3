### Title
`git clone` explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` symlink/hooks safeguard, reopening submodule-hooks RCE (CVE-2024-32002-class) - (File: app/src/lib/git/clone.ts)

### Summary
`GebProxyActions`-style "return value/guard is bypassed, allowing an attacker-supplied input to slip through" maps directly onto `clone()` in `app/src/lib/git/clone.ts`, which builds the environment for every Desktop clone with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while also passing `--recursive` to `git clone`. [1](#0-0) 

### Finding Description
Upstream Git added the `GIT_CLONE_PROTECTION_ACTIVE` safeguard (paired with `clone.protectNTFS`/`clone.protectHFS`) as the fix for the case-insensitive/symlinked-`.git`-directory submodule RCE class (the bug class publicly tracked as CVE-2024-32002), where a malicious repository with a specially-crafted submodule (using symlinks or case-folding tricks on HFS+/NTFS filesystems) can cause `git clone --recursive` to write files into the parent repository's `.git/hooks` directory, which are then executed. The protection is *on by default* in fixed Git versions specifically to stop this attacker-controlled-clone → code-execution path.

Desktop's `clone()` function unconditionally sets:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```
and always adds `--recursive` to the `clone` arguments:
```
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
``` [1](#0-0) 

This is the exact analog of the "unchecked transfer" bug class: a safety check that exists specifically to stop an untrusted, attacker-controlled object (here, a malicious clone/submodule) from corrupting state outside the intended scope (here, `.git/hooks`, i.e. code execution) is deliberately turned off, and nothing downstream re-validates the submodule layout before recursively cloning it. The only other safeguard present in this file, `isClonePathSensitive()`, only checks the *top-level destination path* against a short list of sensitive folders (`~/.ssh`, `~/.gnupg`, `~/.config`, `~/.gitconfig`) — it does nothing to validate paths that submodules resolve to during the recursive clone step, so it does not compensate for the disabled protection. [2](#0-1) 

The recursive submodule update path (`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts`) similarly runs `submodule update --init --recursive` without re-enabling or otherwise checking `GIT_CLONE_PROTECTION_ACTIVE`, and even allows `protocol.file.allow=always` in some code paths, further widening what a malicious `.gitmodules` can point to. [3](#0-2) 

### Impact Explanation
If Git's version-specific protection would otherwise reject or sanitize a malicious submodule path (symlink, case-collision with `.git`, etc.), Desktop's explicit opt-out removes that backstop for every single clone the user performs (initial clone, "Clone repository" UI flow, CLI `github clone`, and any recursive submodule update). A user who clones or fetches-and-updates-submodules for an attacker-controlled repository could have files written into `.git/hooks` of the resulting working copy, which git then executes on subsequent hook-triggering operations (commit, checkout, etc.) performed inside Desktop or from a regular terminal — i.e., unprivileged code execution triggered purely by cloning a hostile repository, matching the report's "attacker deposits for free"/broken-invariant pattern translated to "attacker gets code execution for free."

### Likelihood Explanation
Cloning arbitrary/attacker-supplied URLs is a core, expected Desktop workflow (`clone-repository.tsx`, CLI `github clone <owner>/<repo>`), so the vulnerable code path is reached on essentially every clone with no unusual user action beyond entering/clicking a URL — squarely within scope (attacker controls a cloned/fetched repository). The mitigating factor is that actual exploitability depends on the underlying Git binary bundled with Desktop actually containing the fixed behavior that this flag disables; without being able to confirm the Git/dugite version pinned by this build in the codebase, I cannot verify whether the flag maps to real protective behavior in the shipped Git, only that Desktop is intentionally disabling a security-named git variable for every clone with no compensating validation of recursively-fetched submodule paths.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (and confirm `clone.protectNTFS`/`clone.protectHFS` are left at Git's secure defaults), or if there is a legitimate compatibility reason to disable it, add explicit post-clone validation that submodule paths/symlinks written under `.git` do not escape or overwrite `hooks/`, `config`, or other sensitive files before allowing further operations on the clone. Apply the same scrutiny to `updateSubmodulesAfterOperation`'s use of `--recursive` and `protocol.file.allow=always`.

### Proof of Concept
Not independently executable from the indexed code alone — the concrete PoC would be a crafted upstream repository containing a submodule entry whose path is a symlink to (or case-insensitive collision with) `.git/hooks` on the victim's filesystem, such that `git clone --recursive <url>` on Desktop (which runs with `GIT_CLONE_PROTECTION_ACTIVE=false`) writes an executable hook file (e.g. `post-checkout`) into the cloned repo's real `.git/hooks`, which then runs the next time Desktop performs a checkout in that repository. Because the local Git binary/version bundled with Desktop was not directly inspectable through the indexed files, I could not confirm end-to-end that this specific Git build's `GIT_CLONE_PROTECTION_ACTIVE` behavior is exploitable versus a no-op on the bundled `dugite`/Git version — flagging this as the key remaining uncertainty. If the user needs to verify the exact bundled Git version and its handling of this variable, a Devin session with full repository/checkout access (including `package.json`/`dugite` lockfiles and vendored Git binaries) would be required.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
