### Title
Unregistered/unspecified reward tokens pulled into ManualCompound during compound() become permanently unrecoverable - ([File: rewards/ManualCompound.sol])

### Summary
`compound()` in `ManualCompound.sol` only refunds "non-compoundable" tokens that the caller explicitly lists in `_rewards[i]`, and only processes/forwards tokens that are registered in the `rewards[]` array. Any ERC20 token that is transferred into the contract by `IMasterMagpie(masterMagpie).multiclaimOnBehalf(...)` but is **neither** listed by the caller in `_rewards[i]` **nor** present in `ManualCompound.rewards[]` will be silently retained by the contract with no code path to move it out, since the contract has no generic sweep/rescue function.

### Finding Description
`compound()` performs three steps:

1. It claims rewards on behalf of `msg.sender` for the given `_lps`: [1](#0-0) 

2. It only refunds tokens explicitly present in the caller-supplied `_rewards[i]` array that are not in `compoundableRewards`: [2](#0-1) 

3. It only forwards/converts tokens that are pre-registered by the owner in `rewards[]`: [3](#0-2) 

The refund loop (step 2) is bounded by `rewardLength = _rewards[i].length` — i.e., it can only ever refund a token that the caller already named in `_rewards[i]`. The compound loop (step 3) is bounded by `rewardTokensLength = rewards.length` — i.e., it can only ever touch a token that the owner already registered via `addReward`. There is no third path (no `sweep`, `rescue`, or fallback `else` branch) that handles a token which is (a) actually transferred into the contract by the underlying claim, but (b) omitted from both `_rewards[i]` and `rewards[]`.

If a pool's underlying rewarder distributes an additional/bonus reward token that the caller's `_rewards[i][i]` entry does not enumerate (e.g., the caller passes an empty or partial `_rewards[i]` while the underlying claim mechanism still transfers all reward tokens held by that rewarder to `ManualCompound`), that token balance lands in the contract with `compoundableRewards[token] == false` and no matching entry anywhere in the two loops. It is then permanently stuck: no owner-only or public function in `ManualCompound.sol` can move arbitrary ERC20 balances out of the contract — `setHelper`, `setConvertor`, `setLocker`, `addReward`, `removeReward` only mutate the `rewards[]` struct array and do not transfer tokens. Only tokens matching `rewards[i].tokenAddress` are ever moved via `safeApprove`/`safeTransfer` in the compound loop.

This is a genuine gap in `ManualCompound.sol`'s own accounting logic: the caller-controlled `_rewards[i]` parameter and the owner-controlled `rewards[]` registry are the only two sets of tokens the contract "knows" how to handle, and any token falling outside their intersection with the actually-received tokens is orphaned.

Note: I was unable to fully re-verify within the tool budget the exact internal semantics of `IMasterMagpie.multiclaimOnBehalf` (specifically whether it always transfers every reward token held by a pool's rewarder to the caller regardless of the `_rewards[i]` filter, or whether `_rewards[i]` restricts which tokens are actually claimed). The vulnerability inside `ManualCompound.sol` itself — the absence of any sweep mechanism for tokens outside `rewards[]` and outside the caller-supplied `_rewards[i]` — is independently confirmed from the code shown above and holds as long as it is possible for some ERC20 to land in the contract's balance without being named in either set (e.g. through a rewarder emitting a bonus token, or a user simply forgetting/mis-specifying `_rewards[i]` while the aggregator's claim function still pulls all tokens for that pool).

### Impact Explanation
If exploitable end-to-end (i.e., if `multiclaimOnBehalf` can indeed deposit a token into `ManualCompound` that is absent from both `_rewards[i]` and `rewards[]`), the impact is permanent freezing of that reward token for every user whose compound transaction routed through the affected pool, matching the Immunefi "permanent freezing of unclaimed yield" impact class, since the frozen tokens belong collectively to users who compounded and had that bonus reward swept into the shared `ManualCompound` contract rather than returned or converted to them.

### Likelihood Explanation
Exploitability depends entirely on external factors not confirmed here: (1) whether any integrated rewarder distributes an extra/bonus reward token beyond what `ManualCompound.rewards[]` tracks, and (2) whether `multiclaimOnBehalf` transfers such a token to `ManualCompound` even when it is absent from the caller's `_rewards[i]` entry. No malicious action by the caller is required — an honest user calling `compound()` with an incomplete `_rewards[i]` (or a pool whose rewarder later adds a new bonus token that the owner hasn't yet registered via `addReward`) is sufficient to trigger the freeze. This is a passive/latent bug rather than an actively "exploitable" one by an attacker seeking direct profit, but it can freeze value belonging to legitimate compounders.

### Recommendation
Add an owner-restricted `sweep(address token, address to, uint256 amount)`-style rescue function in `ManualCompound.sol` to recover tokens that end up in the contract outside the tracked `rewards[]` set, or change the refund loop to iterate over the actual token balances received rather than only the caller-supplied `_rewards[i]` array, ensuring any leftover balance is always returned to `msg.sender` after both loops run.

### Proof of Concept
Given that the exact claim semantics of `IMasterMagpie.multiclaimOnBehalf` could not be fully re-confirmed within this session, a full PoC needs a Foundry test that: (1) deploys `ManualCompound` with `rewards[]` registering only tokens A and B; (2) mocks/deploys a `MasterMagpie`+rewarder combination whose pool distributes tokens A, B, and an additional bonus token C; (3) calls `compound(_lps, _rewards, ...)` with `_rewards[i]` listing only A and B (omitting C); (4) asserts `IERC20(C).balanceOf(address(ManualCompound)) > 0` after the call; and (5) asserts no external/public function on `ManualCompound` can move that balance out (i.e., calling every non-view function does not reduce token C's balance). This last step confirms the "no sweep" claim directly from the code shown above, while step (3)'s premise (that C is transferred despite being excluded from `_rewards[i]`) depends on `MasterMagpie`/rewarder behavior that should be verified against the live `multiclaimOnBehalf`/`BaseRewardPool` implementation before treating this as a confirmed, exploitable finding rather than a defense-in-depth gap.
