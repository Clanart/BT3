Confirmed: `mWomSV.lockFor` is a public, permissionless function `(external whenNotPaused nonReentrant)` callable by any address on behalf of any beneficiary, with no restriction limiting callers to `ArbWomUp3` or `SmartWomConvert` [1](#0-0) . This confirms the attack path is genuinely reachable by any unprivileged actor.

### Title
Attacker can artificially inflate mWomSV lock balance via SmartWomConvert.convert(mode=2) to game ArbWomUp3's tiered MGP reward and extract MGP disproportionate to WOM actually routed through ArbWomUp3 - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getUserTier`/`calDoubledCounted`/`getRewardAmount` determine a user's reward tier and "already counted" baseline solely from `mWomSV.getUserTotalLocked(_account)` [2](#0-1) , but that balance can be freely inflated by calling `SmartWomConvert.convert(..., _mode=2)` directly, which locks obtained mWOM into `mWomSV` via `mWomSV.lockFor` without ever going through `ArbWomUp3` [3](#0-2) . An attacker can therefore lock a large mWOM position externally (paying no MGP-tracking cost through `ArbWomUp3`), reach a top reward tier for free from `ArbWomUp3`'s perspective, then repeatedly call `ArbWomUp3.incentiveDeposit` with tiny WOM amounts and `_mode=2` to harvest MGP rewards at the inflated tier's multiplier (doubled again for mode 2) [4](#0-3) , draining `ArbWomUp3`'s MGP balance out of proportion to the tiny WOM amounts actually contributed through the contract.

### Finding Description
`ArbWomUp3.incentiveDeposit` computes the reward via `getRewardAmount(_amount, msg.sender, _mode==2)` before performing `_deposit`, and for `_lock=true` computes:
```
accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
... tier walk over accumulated ...
mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
```
`calDoubledCounted` re-reads the *same* `mWomSV.getUserTotalLocked(_account)` value (pre-deposit) to compute the "already rewarded" baseline [5](#0-4) . This design implicitly assumes `mWomSV.getUserTotalLocked(_account)` only grows through prior calls to `ArbWomUp3.incentiveDeposit` itself (mirroring the self-tracked `userWOMDeposited` mapping used in the earlier `ArbWomUp2.sol`, e.g. lines 99-117 of that file) [6](#0-5) . That assumption is false: `mWomSV.getUserTotalLocked` is external, mutable state that any account can move by calling `SmartWomConvert.convert(_amountIn, _convertRatio, _minRec, _mode=2)` directly, which locks obtained mWOM straight into `mWomSV` on the caller's behalf, completely bypassing `ArbWomUp3` [7](#0-6) [8](#0-7) . `mWomSV.lockFor` itself has no caller restriction — any address can lock mWOM for any beneficiary [1](#0-0) .

Exploit flow:
1. Attacker calls `SmartWomConvert.convert(largeAmount, _convertRatio, 0, 2)`, locking a large mWOM position directly into `mWomSV` for themselves, placing `mWomSV.getUserTotalLocked(attacker)` deep into a high reward tier — with zero MGP earned from `ArbWomUp3` since it was never touched.
2. Attacker calls `ArbWomUp3.incentiveDeposit(dustAmount, _convertRatio, false, 2)`. `getRewardAmount` reads `accumulated = dust + X` and `calDoubledCounted` reads baseline `X` (the pre-inflated balance), so `mgpReward ≈ dust * rewardMultiplier[topTier]`, then doubled for mode 2.
3. Attacker repeats step 2 with additional dust deposits, each time harvesting MGP at the top-tier multiplier rate, since their `mWomSV` balance never needs to have been earned through `ArbWomUp3`'s own accounting.

This differs materially from the legitimate flow, where a user reaching the same tier entirely through `ArbWomUp3.incentiveDeposit` would have their full deposited volume subject to the tier walk (earning the tiered reward once, proportivately, on the whole amount they routed through the contract) — the exploiting user instead earns high-tier-rate MGP repeatedly on trivial amounts while the bulk of their locked capital was routed around the contract's own deposit/reward accounting.

### Impact Explanation
This is a theft of unclaimed MGP yield held in `ArbWomUp3`'s MGP balance (used via `vlMGP.lockFor(rewardToSend, msg.sender)` at line 102) [9](#0-8) . An attacker with capital to lock in `mWomSV` (which they could unlock later, subject to `mWomSV`'s cooldown mechanism) can repeatedly extract MGP rewards computed at an inflated tier multiplier rate for trivial WOM contributions, draining the reward pool meant to incentivize genuine tiered WOM deposits into the buyback program. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Feasible for any unprivileged actor holding WOM: they need capital to convert/lock via `SmartWomConvert.convert` (real but recoverable capital, since it's only locked, not burned, and can later be unlocked through `mWomSV.startUnlock`/`unlock` after cooldown), plus trivial WOM for each `incentiveDeposit` dust call. The attack is fully repeatable (multiple dust deposits) and requires no privileged role, oracle manipulation, or governance action — only two already-public function calls (`SmartWomConvert.convert` and `ArbWomUp3.incentiveDeposit`) in sequence.

### Recommendation
`ArbWomUp3` should not rely on the externally-mutable `mWomSV.getUserTotalLocked(_account)` as the sole basis for tier determination and double-counting protection. Instead, track cumulative WOM/mWOM volume routed through `ArbWomUp3.incentiveDeposit` in an internal mapping (as `ArbWomUp2` does with `userWOMDeposited`), and use that internally-tracked value for `getUserTier`, `calDoubledCounted`, and the `accumulated` computation in `getRewardAmount`, rather than reading a balance that can be inflated by direct, out-of-band calls to `SmartWomConvert.convert` or `mWomSV.lockFor`.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `SmartWomConvert`, `vlMGP`, and mock `mWom`/`wom`/`mgp` tokens with realistic wiring (`masterMagpie`, tier/multiplier setup via `setMultiplier`).
2. Fund `ArbWomUp3` with a large MGP balance to simulate the reward pool.
3. **Baseline user B**: calls `ArbWomUp3.incentiveDeposit(TOTAL, ratio, false, 2)` once, depositing the entire `TOTAL` WOM amount directly through `ArbWomUp3`. Record `rewardToSend_B` (from `VLMGPRewarded` event or `vlMGP` locked balance delta).
4. **Attacker A**: 
   - Calls `SmartWomConvert.convert(TOTAL - dust, ratio, 0, 2)` directly, locking `TOTAL - dust` mWOM equivalent into `mWomSV` for themselves (bypassing `ArbWomUp3` entirely).
   - Calls `ArbWomUp3.incentiveDeposit(dust, ratio, false, 2)` for a small `dust` amount. Record `rewardToSend_A`.
5. Assert `rewardToSend_A / dust >> rewardToSend_B / TOTAL` — i.e., the attacker's MGP reward rate per unit of WOM actually routed through `ArbWomUp3` is disproportionately higher than the legitimate depositor's rate, despite both ending with the same total `mWomSV` locked balance.
6. Optionally repeat step 4's second call multiple times with additional dust amounts to show cumulative extraction of MGP at the top-tier multiplier, quantifying total MGP drained from `ArbWomUp3`'s balance versus WOM actually contributed through the contract.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

    function calDoubledCounted(address _account) public view returns (uint256) {
        uint256 accuIn1 = mWomSV.getUserTotalLocked(_account);
        uint256 rewardAmount = 0;

            i++;
        }
