### Title
Unbounded manual CLVM atom-length parsing in `is_atom_canonical` can raise an unhandled `IndexError` and crash mempool spend-bundle validation - (File: chia/full_node/mempool_manager.py)

### Summary
`is_clvm_canonical()`/`is_atom_canonical()` in [1](#0-0)  is a hand-rolled, second CLVM-serialization parser that re-implements atom length-prefix decoding in pure Python, independent of the Rust `chia_rs` parser that already validated/executed the same bytes. It is invoked on attacker-supplied `puzzle_reveal`/`solution` bytes for every coin spend inside `MempoolManager.validate_spend_bundle()`, which runs on every submitted `SpendBundle` before mempool admission. Like the YARA lexer bug (a hand-written low-level byte scanner that didn't validate buffer bounds before dereferencing), this Python re-parser walks `clvm_buffer[offset]` without checking `offset < len(clvm_buffer)` while decoding multi-byte atom length prefixes, so a mismatch between the two parsers' notion of "well-formed" can make it read past the end of the buffer and throw an uncaught `IndexError`.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads `b = clvm_buffer[offset]` and then, based on the atom's leading-byte bit pattern, computes `prefix_len` (0 to 5) and loops `for i in range(prefix_len): offset += 1; atom_len |= clvm_buffer[offset]` [2](#0-1) . None of these array accesses are bounds-checked against `len(clvm_buffer)`.

`is_clvm_canonical()` drives this loop over the whole buffer, again indexing `clvm_buffer[offset]` directly with no length check before each read [3](#0-2) , only checking `assert clvm_buffer != b""` at the very start.

This function is called directly on raw, attacker-controlled bytes of every spend's puzzle reveal and solution inside the mempool's authoritative validation path: [4](#0-3) 

`validate_spend_bundle()` is called from `add_spend_bundle()` [5](#0-4) , which is the standard entry point full-node/RPC code uses to admit a spend bundle into the mempool for every submitted transaction, singleton spend, offer settlement, or CAT/NFT/DID spend.

The buffer passed in has already been successfully parsed and executed by the Rust CLVM engine (via `pre_validate_spendbundle` → `validate_clvm_and_signature`), which produced the `SpendBundleConditions` used earlier in the pipeline. `is_clvm_canonical` exists specifically because the Rust parser *accepts* non-canonical (redundant, overlong) length-prefix encodings that this Python function is meant to reject. Because it is a second, independently-hand-maintained implementation of the same low-level atom/pair decoding grammar, any divergence between its prefix-length/bit-mask logic and the "true" grammar accepted by `chia_rs` (e.g., in handling the boundary values for the 5-length-prefix-byte back-reference-adjacent encoding at `0xFC`-`0xFD`, or a buffer that is well-formed by the Rust parser but whose final atom's declared prefix length walks the Python loop past the buffer end) results in `clvm_buffer[offset]` being indexed out of range, raising an unhandled `IndexError`.

There is no `try/except` around the `is_clvm_canonical(...)` call site in `validate_spend_bundle`, and no bounds validation inside `is_atom_canonical`/`is_clvm_canonical` themselves — the only defensive check present is the `assert clvm_buffer != b""` guard for the empty-buffer case.

### Impact Explanation
An uncaught `IndexError` raised from within `MempoolManager.validate_spend_bundle()` — a function documented as running "with the mempool locked (blockchain lock)" — is not one of the `ValidationError`/`ValueError` cases that calling code (`add_spend_bundle`, and its full-node RPC/API callers) is written to catch. This mirrors the YARA CVE's bug class exactly: a hand-written low-level scanner over attacker-controlled bytes that omits an end-of-buffer check, causing a crash/exception on a crafted input rather than a clean rejection. In chia-blockchain's asyncio-based full node, an unhandled exception surfacing from a task processing an incoming transaction can abort in-flight mempool processing for that spend bundle and, depending on the calling task's exception handling, propagate into the peer/RPC message-processing task, producing a spend-triggered transaction-processing halt/DoS for the local node from a single attacker-crafted spend bundle. This is reachable by any unprivileged spend-bundle submitter — no privileged keys, peer role, or node compromise required.

### Likelihood Explanation
The pathway is reached by ordinary, permissionless use: any wallet/RPC client can craft a `CoinSpend`'s `puzzle_reveal`/`solution` byte buffer and submit it as a `SpendBundle`. Exploitability hinges on finding a specific byte sequence that (a) is accepted as valid, executable CLVM by the Rust `chia_rs` deserializer/interpreter (so it reaches `validate_spend_bundle`) but (b) causes the independent Python `is_atom_canonical` prefix-length walk to advance past the buffer boundary. I was not able to fully construct or verify such a byte sequence within this analysis — confirming exploitability requires directly comparing the exact atom-length grammar accepted by the `chia_rs` deserializer against the bit masks in `is_atom_canonical` for edge cases in the 4/5-length-prefix-byte encodings, and testing crafted buffers against a running mempool. This is the main uncertainty in this finding; the code pattern (unbounded indexing while manually parsing untrusted bytes, duplicating an already-validated parser) is a proven bug class per the referenced CVE, but a concrete divergent input was not confirmed here.

### Recommendation
Add explicit bounds checks in `is_atom_canonical`/`is_clvm_canonical` before every `clvm_buffer[offset]` access (raising a normal `Err.INVALID_COIN_SOLUTION`-style rejection instead of indexing out of range), and wrap the call site in `validate_spend_bundle` in a `try/except (IndexError, ValueError)` that maps any parsing failure to `Err.INVALID_COIN_SOLUTION` rather than letting it propagate as an unhandled exception. Longer term, consider replacing this duplicated hand-written canonical-encoding check with a canonicality flag/return value from the Rust CLVM deserializer itself, eliminating the second parser implementation entirely.

### Proof of Concept
Not fully constructed — see Likelihood Explanation. Conceptually: submit a `SpendBundle` whose `CoinSpend.puzzle_reveal` (or `solution`) ends in an atom encoded with one of the multi-byte length-prefix forms (`0xC0`–`0xFD` leading byte) positioned so that the declared `prefix_len` bytes needed by `is_atom_canonical`'s loop extend past the actual end of the serialized buffer, while the overall buffer still parses as valid, executable CLVM under `chia_rs`. Submitting this via the standard `push_tx`/mempool-add RPC path would drive execution into `is_clvm_canonical()` inside `MempoolManager.validate_spend_bundle()` and trigger the unbounded `clvm_buffer[offset]` read.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value


def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
