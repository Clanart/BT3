### Title
Quadratic CPU exhaustion in `ThresholdKeys::new` interpolation-factor computation from attacker-supplied keys blob - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts an untrusted serialized key blob declaring `n` up to `u16::MAX` (65535). `ThresholdKeys::new` then computes the group key by evaluating `interpolation_factor` for each of `t` participants, and each factor evaluation iterates over the full `included` set — an O(n²) field-arithmetic blowup triggered by a ~4 MiB input, analogous to the regex catastrophic-backtracking class (small controlled input → disproportionate CPU work during verification).

### Finding Description
In `crypto/dkg/src/lib.rs`:

- `ThresholdKeys::read` reads `t`, `n`, `i` from the byte stream, then reads `n` scalars (for `Interpolation::Constant`) and `n` verification-share points via `C::read_G`, before calling `ThresholdKeys::new` (lines 591-631).
- `ThresholdKeys::new` builds `t = 1..=params.t()` and computes `group_key` as the sum of `verification_shares[i] * interpolation_factor(*i, &t)` (lines 376-378).
- `interpolation_factor` (lines 226-249) for both `Constant` and `Lagrange` performs a loop over `included` (`for l in included`) doing two `F` multiplications per element, plus a field `invert` for Lagrange — i.e., O(t) work per participant, O(t²) total.

With `t = n = 65535`, `interpolation_factor` is invoked 65535 times, each looping over 65535 participants: ~4.3 × 10⁹ field multiplications, and under Lagrange interpolation each call additionally performs a Fermat inversion (~256 squarings/multiplications), adding ~1.7 × 10⁷ more. The attacker-controlled blob only needs to be about `n × (|F| + |G|)` ≈ 4 MiB — a small input producing minutes-scale CPU consumption on a single-threaded verifier, mirroring the ReDoS pattern where verification time grows superlinearly in attacker-controlled size.

The same quadratic path is re-triggered by `ThresholdView` construction: `view()` calls `interpolation_factor` for every element of `included` (lines 500-507), and `ThresholdView::interpolation_factor` recomputes over `self.included` per query (lines 657-662).

### Impact Explanation
Any component that feeds untrusted bytes to `ThresholdKeys::read` (listed as reachable input) can be forced into ~10⁹–10¹⁰ field operations from a few megabytes of input, blocking the thread performing key loading/verification — the same CPU-exhaustion/DoS outcome as the fast-jwt ReDoS (event-loop/throughput degradation in an authenticated or token-bearing context, since the blob itself is structurally valid).

### Likelihood Explanation
Requires a context where an unprivileged party can cause `ThresholdKeys::read`/`ThresholdKeys::new` to be invoked on bytes they control with `n` near `u16::MAX`. Parameters are not length-prefixed against actual data beyond `n` itself, and there is no bound check on `n` relative to the deployment's real threshold size — `ThresholdParams::new` only enforces `t <= n` and `i <= n` (lines 166-179). Medium likelihood: the class requires a deserialization endpoint accepting these blobs, but no exotic conditions beyond that.

### Recommendation
- Cap `n`/`t` at a protocol-appropriate maximum (e.g., the real multisig bound) inside `ThresholdParams::new` rather than allowing the full `u16` range.
- Precompute Lagrange denominators/numerators once and share the O(t) prefix products across participants, reducing `group_key` derivation to O(t) field work.
- Reject `Interpolation::Constant` blobs where `n` differs from the expected ciphersuite deployment parameters before performing interpolation.
