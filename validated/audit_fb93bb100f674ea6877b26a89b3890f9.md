## Analysis

The report's core pattern — a single authorization check that is too weak, letting funds be withdrawn without proper attribution of *who* is asking — has a direct structural analog in Hyperbridge's cross-chain governance withdrawal path for `EvmHost` revenue.

### Title
Missing module-identity check in `HostManager.onAccept` allows any Hyperbridge-side dispatcher to trigger unauthorized `EvmHost` fund withdrawal - (File: `evm/src/core/HostManager.sol`)

### Summary
`EvmHost.withdraw()` moves the host's fee-token/native-token balance to an attacker-supplied beneficiary and amount, but is only reachable through `HostManager.onAccept`, whose authentication checks solely the **source chain** of the incoming ISMP request, not the **source module** (`request.from`) that dispatched it.

### Finding Description
`HostManager.onAccept` is the sole gate in front of `IHostManager.withdraw`/`updateHostParams`: [1](#0-0) 

The only authentication performed is:
```
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
```
This validates that the request originated from *the Hyperbridge parachain as a chain*, but never checks `request.from` — i.e. it does not verify that the specific pallet/module on that chain which produced the message is the intended governance module (e.g. `host-executive`'s `PALLET_ID = b"hostexec"`). Once `request.source` matches, any `body` beginning with byte `0` decodes as a `WithdrawParams{beneficiary, amount, token}` and is forwarded straight to `EvmHost.withdraw`: [2](#0-1) 

`EvmHost.withdraw` itself is only `restrict`ed to `_hostParams.hostManager`, i.e. it trusts `HostManager.onAccept` completely to have done the real authorization: [3](#0-2) 

The documentation for the structurally identical `BandwidthManager.onAccept` explicitly confirms this is the accepted design, calling out that there is **no module-id lookup** on the pallet→manager direction: [4](#0-3) 

On the Substrate side, `IsmpDispatcher::dispatch_request` (the low-level primitive every pallet uses to send a `PostRequest`) places no restriction on the `from`/`to`/`body` fields supplied by the caller pallet — it simply forwards whatever `DispatchPost` it is given: [5](#0-4) 

The codebase itself documents and demonstrates a generic pattern for pallets to let a *signed, unprivileged* user pick the destination `to` (contract address) and the dispatch `from` module id directly, with the outbound `body` fully controlled by the pallet call: [6](#0-5) [7](#0-6) 

Because `HostManager.onAccept` never checks `request.from`, **any** pallet on the Hyperbridge parachain capable of dispatching a `PostRequest` whose `to` equals a target `HostManager`/`BandwidthManager` address, with a `body` shaped like `[0x00] || abi.encode(WithdrawParams)`, is treated as legitimate governance — regardless of which pallet or origin actually produced it. The only thing standing between "some pallet dispatched a message" and "EvmHost drains funds to an attacker" is the chain-level `source` check, not a module-level one.

### Impact Explanation
If any pallet in the production Hyperbridge runtime can be driven (by a normal signed user, not privileged governance) to dispatch an ISMP `PostRequest` with attacker-influenced `to` and `body` bytes matching this layout, the attacker can drain `EvmHost`'s fee-token/native balance to an address of their choosing — a direct, unauthorized loss of bridge revenue on every connected EVM chain. This is exactly the "admin/withdraw" bug class from the report, except here the flaw is a missing check rather than a trusted-but-risky admin key.

### Likelihood Explanation
Medium/uncertain. I confirmed the authorization gap exists as designed (`HostManager.onAccept` / `BandwidthManager.onAccept` check only chain identity, explicitly documented as "no module-id lookup"). However, I was **not able to confirm**, within the scope of this review, a currently-deployed, non-privileged production pallet that gives a user simultaneous free-form control of both the ISMP `to` address and raw `body` bytes needed to hit the exact `[actionByte, WithdrawParams]` encoding against a `HostManager`/`BandwidthManager` contract address. The pallets I inspected that *do* let a signed user pick a destination address (`pallet-hyper-fungible-token::send`, `pallet-token-gateway::teleport`) constrain `to` to a registered token-contract address and constrain `body` to a fixed application message format, not raw attacker bytes. The only pallets demonstrating fully free `to`+arbitrary dispatch are documentation/tutorial examples (`docs/content/developers/polkadot/dispatching.mdx`, `modules/pallets/demo`), which may not represent code deployed in the live runtime.

Given the index size limits noted in my tooling, I could not exhaustively verify every pallet configured in the actual Hyperbridge/Gargantua runtime for this exact primitive; a Devin session with full repository access would be needed to enumerate all `IsmpDispatcher::dispatch_request` call sites and confirm whether any permit unprivileged, fully attacker-controlled `to`/`body`.

### Recommendation
Add a module-identity check to `HostManager.onAccept` (and `BandwidthManager.onAccept`) requiring `request.from` to equal the expected privileged pallet id (e.g. `host-executive`'s `PALLET_ID`/`b"hostexec"`, or the bandwidth pallet's module id), mirroring the inbound-purchase check already used in the opposite direction (`BandwidthManager::get(request.source)` verifying `request.from`). This closes the gap regardless of what other pallets in the runtime are capable of dispatching ISMP messages.

### Proof of Concept
Not fully demonstrable from local evidence alone — the missing `request.from` check in `HostManager.onAccept`/`BandwidthManager.onAccept` is confirmed, but a concrete unprivileged trigger path requires a production pallet that grants attacker control of `to` and raw `body` bytes for a POST dispatch, which I could not locate with certainty in this codebase.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

	fn dispatch_request(
		&self,
		request: DispatchRequest,
		fee: FeeMetadata<T>,
	) -> Result<H256, anyhow::Error> {
		// collect payment for the request
		if fee.fee != Zero::zero() {
			T::Currency::transfer(
				&fee.payer,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				fee.fee,
				Preservation::Expendable,
			)
			.map_err(|err| IsmpError::Custom(format!("Error withdrawing request fees: {err:?}")))?;
		}

		let request = match request {
			DispatchRequest::Get(dispatch_get) => {
				let get = GetRequest {
					source: self.host_state_machine(),
					dest: dispatch_get.dest,
					nonce: self.next_nonce(),
					from: dispatch_get.from,
					keys: dispatch_get.keys,
					height: dispatch_get.height,
					context: dispatch_get.context,
					timeout_timestamp: if dispatch_get.timeout == 0 {
						0
					} else {
						<T::TimestampProvider as UnixTime>::now()
							.as_secs()
							.saturating_add(dispatch_get.timeout)
					},
				};
				Request::Get(get)
			},
			DispatchRequest::Post(dispatch_post) => {
				let post = PostRequest {
					source: self.host_state_machine(),
					dest: dispatch_post.dest,
					nonce: self.next_nonce(),
					from: dispatch_post.from,
					to: dispatch_post.to,
					timeout_timestamp: if dispatch_post.timeout == 0 {
						0
					} else {
						<T::TimestampProvider as UnixTime>::now()
							.as_secs()
							.saturating_add(dispatch_post.timeout)
					},
					body: dispatch_post.body,
				};
				Request::Post(post)
			},
		};

		let commitment = Pallet::<T>::dispatch_request(request, fee)?;

		Ok(commitment)
	}
