### Title
Blame evaluation panics on missing decryption-key entry, enabling a repeatable crash from a faulty secret-share message - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys` with the accused decryptor's `Participant` using `HashMap`'s `Index` operator, which panics if no entry exists. In the PedPoP flow, a participant's own encryption key is never inserted into `enc_keys` — `Encryption::registration` returns the public key without registering it, and `verify_r1`/`generate_secret_shares` only call `register` for *other* participants' commitment messages (own index is explicitly skipped when iterating `all_participant_indexes` for share distribution). When a party completes `calculate_share` and then invokes `BlameMachine::blame`/`AdditionalBlameMachine::blame` with itself as `recipient` (the normal accusation flow: "sender l sent me a bad share"), `blame_internal` calls `decrypt_with_proof(sender, recipient = i, msg, Some(proof))`, which reaches `self.enc_keys[&decryptor]` and panics. A malicious DKG participant can reliably trigger this by sending any malformed `EncryptedMessage` that fails share verification, causing the honest victim's blame resolution to abort the process. ### Finding Description
- `decrypt_with_proof` performs `self.enc_keys[&decryptor]` (encryption.rs:388). `HashMap::index` panics on absent keys.
- `enc_keys` is only populated via `Decryption::register` (encryption.rs:351–362), called from `Encryption::register` during `verify_r1` for each *received* commitment message (pedpop/src/lib.rs:315). The local participant's own key comes from `Encryption::registration` (encryption.rs:448–450), which constructs the message without inserting into `enc_keys`. Since `generate_secret_shares`/`calculate_share` skip `l == self.params.i()` for incoming shares (pedpop/src/lib.rs:362–364), index `i` is never a key in `enc_keys`.
- During blame, `blame_internal(sender, recipient, msg, proof)` → `decrypt_with_proof(sender, decryptor=recipient, msg, proof)`. The honest accuser is the `recipient`, i.e., `decryptor == i`, which has no `enc_keys` entry → panic, whenever `proof.is_some()` (the normal case — the accuser supplies their `EncryptionKeyProof` produced by `decrypt` at encryption.rs:478–500).
- The panic occurs before the DLEq verification result matters, so any trigger of blame evaluation suffices.

### Impact Explanation
Complete denial of service of the DKG blame/abort path: a single faulty participant causes every honest party that attempts to adjudicate blame to crash (library panic unwinding through `blame`/`AdditionalBlameMachine::blame`). This mirrors CVE-2024-20963's availability-only impact: low-privileged network-adjacent input (a DKG peer's share message) deterministically crashes the victim. It also means faulty participants cannot be blamed/evicted, stalling key generation.

### Likelihood Explanation
Reachable by any DKG participant who submits an invalid or non-canonical `EncryptedMessage<C, SecretShare>` — crafted entirely from attacker-controlled bytes via `EncryptedMessage::read`/`Commitments::read` paths. Triggering blame is the *designed* response to a bad share, so the crash is deterministic once the accusation flow runs. Caveat: if an integrator also registers the local participant's own `EncryptionKeyMessage` into `Decryption` (non-standard, since the API doesn't expose that for self), the panic would not occur — the standard PedPoP flow does not do this. Severity Medium per the CVSS 6.5 analog (availability impact only, requires participating in the protocol).

### Recommendation
Replace `self.enc_keys[&decryptor]` with a checked lookup returning `DecryptionError::InvalidProof` (or a dedicated error) on absence:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  Err(DecryptionError::InvalidProof)?
};
... &[enc_key, *proof.key] ...
```

Alternatively, register the local participant's own encryption public key in `Decryption` during `Encryption::new`, so the accuser's key is always present. The former is safer since it also covers `AdditionalBlameMachine::new`, where `enc_keys` holds the *senders'* keys and `decryptor` may legitimately be an arbitrary index.

### Proof of Concept
```rust
// Conceptual: t-of-n PedPoP, victim is participant i.
// Attacker (participant j) sends victim an EncryptedMessage whose
// PoP signature is valid but whose decrypted bytes are a non-canonical scalar
// (or an invalid share). Victim:
let (mut share_bytes, blame) = encryption.decrypt(rng, &mut batch, id, j, msg);
// share fails verification -> PedPoPError::InvalidShare { blame: Some(blame) }
// Victim then adjudicates, or post-calculate_share calls:
blame_machine.blame(j /* sender */, i /* recipient = self */, msg, Some(blame_proof));
// Inside blame_internal -> decrypt_with_proof(j, i, msg, Some(proof))
// -> self.enc_keys[&i] : HashMap Index panic — i was never registered.
```

`Encryption::encrypt`/`register` show `enc_keys` is keyed by counterparty only (encryption.rs:360, 466), and `decrypt_with_proof` needs the *decryptor's* public key (encryption.rs:388), which for self-blame is the unregistered local index — a guaranteed panic.

  pub fn generate_secret_shares<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    commitments: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<
    (KeyMachine<C>, HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>),
    PedPoPError<C>,
  > {
    let commitments = self.verify_r1(&mut *rng, commitments)?;

    // Step 1: Generate secret shares for all other parties
    let mut res = HashMap::new();
    for l in self.params.all_participant_indexes() {
      // Don't insert our own shares to the byte buffer which is meant to be sent around
      // An app developer could accidentally send it. Best to keep this black boxed
      if l == self.params.i() {
        continue;
      }

      let mut share = polynomial(&self.coefficients, l);
      let share_bytes = Zeroizing::new(SecretShare::<C::F>(share.to_repr()));
      share.zeroize();
      res.insert(l, self.encryption.encrypt(rng, l, share_bytes));
    }

    // Calculate our own share
    let share = polynomial(&self.coefficients, self.params.i());
    self.coefficients.zeroize();

    Ok((
      KeyMachine { params: self.params, secret: share, commitments, encryption: self.encryption },
      res,
    ))
  }
