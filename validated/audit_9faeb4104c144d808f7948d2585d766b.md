### Title
Missing zero-value validation on governance parameter `Kip71GasTarget` causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
The `Kip71GasTarget` governance parameter (`reward.kip71.gastarget` / `governance.kip71.GasTarget`) is registered with a `noopFormatChecker` in `kaiax/gov/param.go`, meaning any `uint64` value, including `0`, is accepted as a valid governance vote value. This value (`GasTarget`) is later used as a divisor in `KIP71Config.NextMagmaBlockBaseFee` without any zero-check, unlike the sibling parameter `BaseFeeDenominator`, which explicitly validates `v != 0` both at the governance-parameter level and defensively inside the function itself.

### Finding Description
`Kip71GasTarget` is defined with a no-op format checker that performs no bounds/nonzero validation: [1](#0-0) 

This is in stark contrast to the neighboring `Kip71BaseFeeDenominator` parameter, which explicitly enforces `v != 0` in its `FormatChecker`, and which `NextMagmaBlockBaseFee` also defensively re-checks (`if kc.BaseFeeDenominator == 0 { ... }`): [2](#0-1) 

`GasTarget` has no such defensive check in `NextMagmaBlockBaseFee`. It is used directly as a divisor in both the "gas used above target" and "gas used below target" branches: [3](#0-2) 

Specifically:
- `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` (used-above-target branch)
- `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` (used-below-target branch)

If `GasTarget == 0` and `parentGasUsed != 0` (i.e., not equal to `gasTarget`, so the early-return shortcut at line 90 is skipped), `big.Int.Div` will panic with a division-by-zero runtime error, since Go's `math/big` package panics (rather than returning an error) when dividing by zero.

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` are consensus-critical functions invoked on essentially every block after the Magma hardfork (header preparation during block assembly in `work/worker.go`, and header verification in the block validation path, as well as `node/cn/gasprice/gasprice.go` and `feehistory.go` for RPC gas-price estimation). A governance-approved (or attacker-influenced misconfiguration of) `GasTarget = 0` would cause every node computing or verifying the next base fee to panic and crash, since the check is entirely absent for this parameter while it exists for the structurally identical `BaseFeeDenominator`.

This is precisely analogous to the reported `MainVault.transferFunds` bug: a fee-related governance parameter that starts/gets set to `0` is used unguarded as a divisor, and the codebase's own inconsistency (guarding `BaseFeeDenominator` but not `GasTarget`) demonstrates that this is an overlooked validation gap rather than an intentional design decision.

### Impact Explanation
A zero `GasTarget` would cause a runtime panic in `NextMagmaBlockBaseFee`, which is called during block production (`work/worker.go`), block header verification, and RPC fee estimation (`node/cn/gasprice`). A panic in header verification/production paths would crash all nodes attempting to process/verify the affected block, resulting in a chain-wide halt/DoS — a severe availability impact reachable through the standard, in-scope governance-parameter update mechanism, matching the "governance parameters" category explicitly allowed in scope.

### Likelihood Explanation
`Kip71GasTarget` is set through the ordinary governance-vote mechanism using `PartialParamSet.Add`, which invokes `param.FormatChecker` before storing the value: [4](#0-3) 

Since `Kip71GasTarget`'s checker is a no-op, `0` (or any other uint64, including values causing other edge-case arithmetic issues) passes validation silently. The only barrier is that a legitimate governance vote (by a GC member or via `governance.governancemode == "single"` configuration) is required to set the value — this is the same class of privileged-but-in-scope actor (Guardian in the original report) that can trigger the issue, consistent with governance-parameter misconfiguration/no-validation bug class.

### Recommendation
Add an explicit nonzero (and reasonably-bounded) `FormatChecker` for `Kip71GasTarget`, mirroring the existing `Kip71BaseFeeDenominator` check:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth (consistent with the existing `BaseFeeDenominator == 0` fallback in `NextMagmaBlockBaseFee`), add a zero-guard for `gasTarget` inside `NextMagmaBlockBaseFee` itself before it is used as a divisor.

### Proof of Concept
1. Submit/approve a governance vote (or configure genesis/governance contract, depending on governance mode) setting `reward.kip71.gastarget` (`Kip71GasTarget`) to `0`. This passes validation because `FormatChecker: noopFormatChecker` accepts any value. [1](#0-0) 
2. Once this governance value is applied to the chain config epoch, at the next block after Magma is active, if `parentGasUsed != gasTarget` (trivially true since `gasTarget == 0` and any block with gas usage `> 0`), `NextMagmaBlockBaseFee` proceeds to the `parentGasUsed > gasTarget` branch (since any positive gas usage is `> 0`). [5](#0-4) 
3. `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` executes `Div(x, 0)`, causing a runtime panic in `math/big`, crashing every node computing the block's base fee (in `work/worker.go` during block assembly and during header verification of the produced block), halting the chain.

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]
	if !ok {
		return ErrInvalidParamName
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
}
