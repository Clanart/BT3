### Title
Non-collision-resistant equality-hash used as cache key for per-repository state can be forged, causing GitStore/UI state for one repository to be silently reused for another - (File: app/src/models/equality-hash.ts)

### Summary
The bug class in the Vyper advisory is a *storage-slot collision*: two logically distinct pieces of state (a `@nonreentrant` lock and a user-declared storage variable) were mapped onto the same underlying slot because the slot-derivation scheme did not guarantee uniqueness, so writing one silently corrupted the other. GitHub Desktop's `createEqualityHash` helper has the same structural weakness: it derives a single string "key" for a `Repository` (and for `GitHubRepository`) by naively joining several fields with `'+'` without escaping, and that string is used verbatim as the `Map` key for two important per-repository caches: `GitStoreCache` and `RepositoryStateCache`. If two different `Repository` objects can be made to produce the same joined string, one repository's cached `GitStore`/`IRepositoryState` (working directory changes, in-progress commit message, selection, git status, etc.) is returned or overwritten for the other, silently mixing state between repositories.

### Finding Description
`createEqualityHash` builds the key by simple string concatenation with `'+'` as the only delimiter and no escaping of the field values: [1](#0-0) 

This function is used to compute `Repository.hash`, folding together `path`, `id`, the nested `gitHubRepository?.hash`, `missing`, `alias`, `forkContributionTarget`, and `isTutorialRepository` into one string: [2](#0-1) 

That `hash` value is then used, unescaped, as the sole `Map` key in two stores that hold sensitive per-repository session state:

- `GitStoreCache`, which caches the `GitStore` instance (git status, commits, remotes, tags-to-push, etc.) per repository: [3](#0-2) 

- `RepositoryStateCache`, which caches `IRepositoryState` (working directory changes, commit message draft, branches state, compare state, amend state, etc.) keyed the same way: [4](#0-3) 

Because the join delimiter (`'+'`) is not escaped in any of the concatenated values, two structurally different tuples of `(path, id, gitHubRepository.hash, missing, alias, forkContributionTarget, isTutorialRepository)` can produce an identical joined string whenever a field boundary is ambiguous (e.g. a value ending in the literal character used as delimiter shifting where the next field "starts" in the resulting string). Since `path`, `alias`, and the fields folded into `gitHubRepository.hash` (owner login, repo name, HTML URL, etc.) are ultimately derived from data that can be influenced by what a user clones/adds (e.g., the suggested clone directory name is derived from the GitHub repository name returned by the GitHub API) ` [5](#0-4) ` [6](#0-5) `, this is the same class of defect as the Vyper issue: a key-derivation function assumed to be collision-free is not, and the resulting collision silently swaps two supposedly independent "storage slots" — here, two repositories' cached working-directory/commit state — with no validation or fallback that would detect the collision.

There is no guard anywhere in `GitStoreCache.get`/`RepositoryStateCache.get`/`.update` that verifies the returned entry actually corresponds to the requested `Repository` beyond the hash match; both `get(repository)` implementations trust the hash unconditionally: [7](#0-6) [8](#0-7) 

### Impact Explanation
If two `Repository` records collide on `hash`, `RepositoryStateCache.get`/`update` will read/write the wrong `IRepositoryState`, meaning:
- A committed message being drafted for repository A could be silently attributed to / displayed for repository B.
- Working-directory selection/staged-file state for one repo can leak into another, potentially causing the user to unknowingly commit or push changes for the wrong repository ("silent corruption of what the user commits or pushes").
- `GitStoreCache` returning the wrong `GitStore` would misattribute git status, current remote, and tags-to-push between repositories, which affects what actually gets pushed.

This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitability depends on an attacker being able to influence one of the joined fields (most plausibly `path`, via a GitHub-repository name used to build the local clone directory, or the nested `gitHubRepository.hash`) such that it contains the `'+'` delimiter or otherwise creates an ambiguous concatenation with an adjacent numeric field (`id`). GitHub's repository/owner naming rules restrict allowed characters (alphanumerics, hyphen, underscore, period), which likely blocks a literal `+` in `name`/`login`; I was not able to fully verify all fields folded into `gitHubRepository.hash` (e.g. `htmlURL`, `defaultBranch`) or whether any of them could carry an attacker-chosen `'+'` or numeric-looking suffix that creates a boundary collision with `id`. Given this uncertainty, I can confirm the underlying primitive (non-escaping join-based key used for cache identity) is real and present in shipped code, but I cannot fully confirm, from local code alone, a concrete attacker-controlled string that reaches `'+'` inside `path` or `gitHubRepository.hash` without further tracing of the clone-directory-suggestion code and `GitHubRepository`'s own `createEqualityHash` call.

### Recommendation
Replace the naive `'+'.join(...)` in `createEqualityHash` with a scheme immune to field-boundary ambiguity — e.g., length-prefixing each field, using `JSON.stringify` on the tuple, or hashing each field independently before combining (e.g. SHA-256 of a canonical, escaped representation). Additionally, `GitStoreCache.get` and `RepositoryStateCache.get`/`update` should assert that the cached entry's identifying fields (at least `path` and `id`) match the requested `Repository` before returning/mutating it, rather than trusting the derived hash alone.

### Proof of Concept
Conceptually (pending confirmation of a concrete attacker-controlled `'+'`-bearing field):
1. `createEqualityHash('a+1', 2, ...)` → `'a+1+2+...'`
2. `createEqualityHash('a', '1+2', ...)` → `'a+1+2+...'`
Both produce the identical string despite representing different `(path, id)` tuples, so `Repository.hash` collides for two distinct repositories. Any place in `GitStoreCache`/`RepositoryStateCache` that uses `repository.hash` as a `Map` key (cited above) would then serve/overwrite one repository's cached `GitStore`/`IRepositoryState` for the other on the next `get`/`update` call.

```typescript
export class GitStoreCache {
  /** GitStores keyed by their hash. */
  private readonly gitStores = new Map<string, GitStore>()

  public constructor(
    private readonly shell: IAppShell,
    private readonly statsStore: IStatsStore,
    private readonly onGitStoreUpdated: (
      repository: Repository,
      gitStore: GitStore
    ) => void,
    private readonly onDidError: (error: Error) => void
  ) {}

  public remove(repository: Repository) {
    if (this.gitStores.has(repository.hash)) {
      this.gitStores.delete(repository.hash)
    }
  }

  public get(repository: Repository): GitStore {
    let gitStore = this.gitStores.get(repository.hash)
    if (gitStore === undefined) {
      gitStore = new GitStore(repository, this.shell, this.statsStore)
      gitStore.onDidUpdate(() => this.onGitStoreUpdated(repository, gitStore!))
      gitStore.onDidError(error => this.onDidError(error))

      this.gitStores.set(repository.hash, gitStore)
    }

    return gitStore
  }
```
