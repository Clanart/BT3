### Title
Meaningless `deadline = block.timestamp` on WOM→mWom buyback swap allows sandwich/MEV extraction with no real deadline protection - (File: wombat/SmartWomConvert.sol)

### Summary
`SmartWomConvert._convertFor()` routes the "buyback" portion of a user's WOM through `IWombatRouter.swapExactTokensForTokens`, passing `block.timestamp` as the `deadline` argument and `0` as the swap's own `minimumamountOut`. Because `block.timestamp` is evaluated at the moment the transaction is finally mined (not when it is signed/submitted), this "deadline" imposes no real time bound — the transaction remains executable indefinitely while sitting in the mempool, exactly the anti-pattern described in the referenced report for `Reth.sol`'s missing-deadline Uniswap swap.

### Finding Description
`convert()`, `convertFor()`, and `smartConvert()` are all external, unprivileged entry points that ultimately call the internal `_convertFor()`: [1](#0-0) 

Inside `_convertFor()`, the buyback swap is executed with a zero per-swap minimum output and a deadline of `block.timestamp`: [2](#0-1) 

The only slippage guard is the aggregate check performed *after* the swap has already executed: [3](#0-2) 

Because the router call's own `minimumamountOut` is hardcoded to `0` and the "deadline" is computed at execution time rather than fixed by the caller, a block producer/searcher can withhold a user's `convert`/`smartConvert` transaction in the mempool and replay it whenever market conditions (pool imbalance, a preceding attacker swap, etc.) make the WOM→mWom leg most unfavorable for the user — a validator/searcher can always satisfy `deadline == block.timestamp` no matter how long the transaction is delayed, so this parameter provides zero protection against exactly the scenario described in the referenced report. The user's only backstop is the coarse `_minRec` check on `convertAmount + amountRec`, which bounds total loss but does not prevent value extraction from the buyback leg specifically, since a user who sets a loose or default `_minRec` (or relies on `smartConvert`, which auto-derives `_minRec = _amountIn`, an even weaker global bound) receives no protection at the per-swap level.

### Impact Explanation
A user submitting WOM to `SmartWomConvert` for buyback/minting of `mWom` can have the WOM→mWom leg sandwiched by an MEV actor at a time of the actor's choosing (transaction can be delayed arbitrarily because the deadline check is always trivially satisfied), extracting value that would otherwise accrue to the user as `mWom`/locked value. This is a direct theft of user funds via price manipulation on every call, analogous to the cited Uniswap `deadline`-less swap issue, but here worsened by the router-level `minimumamountOut` being hardcoded to `0`.

### Likelihood Explanation
Any of the exposed conversion functions (`convert`, `convertFor`, `smartConvert`) are unprivileged and reachable by any wallet holding WOM; the contract itself is stated to be primarily invoked by WombatStaking on user WOM flows, meaning most/typical usage runs through this vulnerable path. Exploitation only requires mempool visibility and the ability to delay/replay a transaction (or sandwich it), which is standard MEV tooling — no privileged role or protocol misconfiguration is required.

### Recommendation
Add a user-supplied `deadline` parameter to `convert`/`convertFor`/`smartConvert` and pass it through to `_convertFor()` and the underlying `IWombatRouter.swapExactTokensForTokens` call instead of computing `block.timestamp` at execution time. Additionally, derive a real per-swap `minimumamountOut` for the buyback leg (e.g., from an off-chain quote/slippage tolerance passed in by the caller) instead of hardcoding `0`, so slippage is bounded on the specific swap rather than only on the aggregate `_minRec` check.

### Proof of Concept
1. Attacker monitors the mempool for pending `SmartWomConvert.convert()`/`smartConvert()` calls.
2. Since the swap's `deadline` argument is `block.timestamp` (evaluated only when mined), the attacker/validator can delay inclusion of the victim's transaction indefinitely without it ever failing the deadline check.
3. The attacker front-runs with a swap that worsens the WOM/mWom pool price, then lets the victim's WOM→mWom leg execute at `minimumamountOut = 0` (no protection), then back-runs to restore price and capture the spread.
4. As long as `convertAmount + amountRec >= _minRec` (the victim's/`smartConvert`'s loose aggregate bound), the transaction succeeds despite the victim receiving materially less `mWom` than fair value — the extracted value goes to the attacker instead of the victim's locked/minted `mWom` position.
