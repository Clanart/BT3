## Title
Hardcoded zero slippage protection in `ArbWomUp3._deposit` (mode 2) swap path allows MEV sandwich theft of user WOM - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit` is a public, unprivileged entry point that lets any user deposit WOM to receive vlMGP/mWomSV rewards. When `_mode == 2`, half of the user's deposited WOM is routed through `SmartWomConvert.convert` with the `_minRec` parameter hardcoded to `0`, completely disabling slippage protection for that swap leg, even though `SmartWomConvert` itself supports and enforces a caller-supplied minimum output.

### Finding Description
In `_deposit`, for `_mode == 2`: [1](#0-0) 
the `toSwap` portion of the user's WOM is sent to `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` — note the third argument, `_minRec`, is a literal `0`.

Inside `SmartWomConvert._convertFor`, this `_minRec` is exactly the value used to gate the whole conversion: [2](#0-1) 
The buyback portion is swapped through the Wombat router with the internal per-swap `minimumAmountOut` also hardcoded to `0` (`swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, ...)`), so the only protection against an adverse price is the aggregate check `convertAmount + amountRec < _minRec`. Because `ArbWomUp3` calls this with `_minRec = 0`, that check can never revert regardless of how unfavorable the swap execution price is.

This is the same bug class as the referenced report: the contract that actually executes the price-sensitive trade offers a caller-configurable slippage limit, but the calling wrapper (`ArbWomUp3`) discards the user's real acceptable-rate intent and substitutes a value that provides no protection at all, letting the trade execute at an arbitrarily bad rate.

### Impact Explanation
Any unprivileged user calling `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` has half of their deposited WOM swapped for mWOM via `SmartWomConvert` with zero minimum-output enforcement. An attacker (or generalized MEV bot) can sandwich this transaction on the Wombat WOM/mWOM pool, driving the swap's execution price arbitrarily far from fair value and extracting the difference, directly reducing the amount of mWOM locked into `mWomSV` on behalf of the depositing user. This is a direct, quantifiable theft of user funds via price manipulation, not merely a inconvenience.

### Likelihood Explanation
`incentiveDeposit` is a normal, unprivileged user-facing function with no special preconditions beyond a nonzero amount and the contract not being paused. Sandwiching an on-chain AMM swap with zero slippage protection is a well-known, low-cost, and reliably executable MEV strategy, making exploitation highly likely whenever a user deposits with `_mode == 2` and the deposit size is large enough to be profitable to attack.

### Recommendation
Propagate a genuine user-supplied minimum-received parameter from `incentiveDeposit`/`_deposit` through to `IConverter(smartWomConvert).convert(...)` instead of hardcoding `0`, and/or have `SmartWomConvert._convertFor` enforce a non-zero minimum output on the individual router swap call (`swapExactTokensForTokens`) rather than only on the aggregated post-swap total.

### Proof of Concept
1. User calls `incentiveDeposit(amount, convertRatio, bullMode, 2)` on `ArbWomUp3`.
2. `_deposit` computes `toSwap = amount - amount/2` and calls `smartWomConvert.convert(toSwap, _convertRatio, 0, 0)`.
3. An attacker observes this pending transaction in the mempool, front-runs it with a large WOM→mWOM (or mWOM→WOM) swap on the same Wombat pool to skew the price, lets the victim's swap execute at the skewed rate (with `minimumAmountOut = 0` in the router call inside `SmartWomConvert`), then back-runs to restore the pool price and capture the spread.
4. Because `_minRec` passed all the way from `ArbWomUp3` is `0`, `_convertFor`'s check `convertAmount + amountRec < _minRec` never reverts, so the victim's transaction succeeds despite receiving far less mWOM than a fair-price execution would produce, and this reduced amount is what gets locked into `mWomSV` on the user's behalf.
