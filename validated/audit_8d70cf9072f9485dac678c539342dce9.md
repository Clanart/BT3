### Title
Unprivileged sender can claim reserved internal output namespace, causing misclassification of received funds — ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Analogous to CVE-2017-14389 ("Application Subdomain Takeover"), where a space developer could attach a subdomain to a route owned by a different org because ownership of the namespace was not enforced, Serai's Bitcoin processor lets any unprivileged on-chain sender place outputs into the reserved internal output namespace (Branch, Change, Forwarded). The scanner classifies received outputs purely by `script_pubkey` match against offsets derived from the group key and *public, deterministic* offset scalars, with no binding to who legitimately created the output.

### Finding Description
`scanner(key)` in `processor/src/networks/bitcoin.rs` (lines 308–347) registers four offsets for every multisig key: `Scalar::ZERO` (External), plus `hash_to_F(KEY_DST, "branch")`, `hash_to_F(KEY_DST, "change")`, and `hash_to_F(KEY_DST, "forward")`. `KEY_DST` (`b"Serai Bitcoin Output Offset"`) and the labels are public constants, so any external party can compute the internal P2TR addresses `key + G*offset` for `Branch`, `Change`, and `Forwarded` from the (public) group key alone.

`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches outputs only on `output.script_pubkey` → offset, and `get_outputs` (`processor/src/networks/bitcoin.rs:686-740`) then maps the offset back through `kinds[offset_repr]` to assign `OutputType`. An attacker who sends funds to the `Change` or `Forwarded` script causes the processor to emit an `Output` whose `kind` is `Change`/`Forwarded`, not `External`. The `data` field is only populated for `External` outputs (lines 731-734), so the attacker's output is reported under the internal namespace — exactly the cross-org subdomain claim pattern: an unprivileged party creates an entry in a namespace reserved for another purpose.

This is reachable entirely with public inputs: the attacker only needs the group key (public) and must broadcast a valid Bitcoin transaction.

### Impact Explanation
Misclassified outputs flow into the multisig scheduler/`ack_block` path as internal `Change`/`Forwarded`/`Branch` outputs rather than deposits. Consequences depend on downstream handling (not fully verified due to iteration limits), but include: attacker-injected UTXOs being treated as protocol-owned change eligible for scheduling/spending logic without deposit attribution; `data` (Serai deposit instructions) being silently dropped for outputs sent to reserved addresses; and corruption of the `presumed_origin`/kind bookkeeping used to distinguish user deposits from internal flows. This is a funds/misattribution-class issue consistent with a Medium severity (integrity impact, no direct key/share compromise).

### Likelihood Explanation
Requires only knowledge of the public group key and crafting a standard P2TR transaction to a deterministically computable internal address — trivially repeatable by any Bitcoin sender at the cost of the deposited funds plus fees. The obstacle is that impact severity is bounded by how downstream code trusts `kind`; the attacker spends their own funds to perform the injection.

### Recommendation
Bind output classification to provenance, not just script matching: only accept `Change`/`Forwarded` outputs that appear in transactions created by the protocol (e.g., match against expected outpoints/txids the scheduler emitted, or record created internal outpoints and only classify those as internal kinds). Alternatively, treat all unsolicited payments to reserved scripts as `External` or reject them, and document the reserved-namespace assumption in `register_offset`'s caller contract.

// key = victim multisig's tweaked group key (public)
let change_addr_script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * change_offset)).unwrap();
// Broadcast a tx paying `change_addr_script`. 
// Processor get_outputs(): scanner.scan_transaction matches the script_pubkey,

Relevant code: `processor/src/networks/bitcoin.rs:308-347` (public offset derivation and `kinds` mapping), `networks/bitcoin/src/wallet/mod.rs:180-214` (`register_offset`, `scan_transaction` matching on `script_pubkey` alone), `processor/src/networks/bitcoin.rs:686-740` (`get_outputs` kind assignment and `External`-only `data` population).

Caveat: I could not fully trace how `OutputType::Change`/`Forwarded` outputs are consumed by the scheduler in `processor/src/multisigs/`, so the worst-case downstream consequence (e.g., whether misclassified UTXOs are auto-spendable as protocol change) is inferred rather than fully verified.
