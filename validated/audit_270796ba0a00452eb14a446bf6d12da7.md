## Finding: Shared `BalanceHandler` state across nested/recursive precompile calls causes native↔EVM balance desynchronization

### Title
Shared per-precompile `BalanceHandler` singleton is clobbered by nested/recursive precompile calls, corrupting EVM `stateDB` balances relative to the bank keeper - (File: `precompiles/common/balance_handler.go`, `precompiles/distribution/distribution.go`, `precompiles/erc20/erc20.go`, `precompiles/staking/staking.go`, `precompiles/gov/gov.go`, `precompiles/slashing/slashing.go`, `precompiles/ics20/ics20.go`)

### Finding Description
This is the same bug class as the report's CEI violation: a piece of shared mutable bookkeeping state (`lastClaimedEpochForAddress` in the external report; `prevEventsLen` here) is read/finalized in the wrong order relative to a nested/reentrant call, so the "effect" gets computed against stale or clobbered state.

`BalanceHandler.BeforeBalanceChange` records a baseline `prevEventsLen = len(ctx.EventManager().Events())` [1](#0-0)  and `AfterBalanceChange` later replays only the events emitted after that baseline to update `stateDB` balances via `AddBalance`/`SubBalance` [2](#0-1) .

The codebase contains two different lifecycles for this handler:
- The newer/safer pattern in `precompiles/common/precompile.go` (`runNativeAction`) creates a **fresh** `BalanceHandler` for every single precompile invocation via `p.BalanceHandlerFactory.NewBalanceHandler()` [3](#0-2) , so nested calls each get their own isolated `prevEventsLen`.
- Several precompiles instead call `p.GetBalanceHandler()` directly (a single handler instance held per-Precompile), as seen in `distribution.go`, `erc20.go`, `gov.go`, `ics20.go`, `slashing.go`, `staking.go`, and the test/debug precompile `testutil/testdata/debug/debug.go` [4](#0-3) .

The test suite itself documents this exact bug: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [5](#0-4) 

The reachable attack path exists in production: contracts recursively invoking precompiles from within an ERC-20 transfer hook are demonstrated repeatedly in the repo (`ERC20RecursiveNonRevertingPrecompileCall.sol`/`ERC20RecursiveRevertingPrecompileCall.sol` call `claimRewards()` on the Distribution precompile recursively inside `_beforeTokenTransfer`) [6](#0-5) , and there is an IBC/ICS20 integration test explicitly exercising "recursive precompile call with reverts" through the same mechanism [7](#0-6) . If any production precompile using the singleton `GetBalanceHandler()` pattern (Distribution, ERC20, Staking, Gov, Slashing, ICS20) is called re-entrantly/nested within the same EVM transaction (e.g., precompile A calls a contract, which calls precompile B, or precompile A calls itself through a Solidity `try`/callback pattern), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` set by the outer call. When the outer call's `AfterBalanceChange` runs, it replays the event window starting at the *inner* call's baseline instead of its own — causing native bank-keeper balance-changed events to be missed or mis-attributed when updating `stateDB.AddBalance`/`SubBalance`.

### Impact Explanation
This directly matches the "Critical unauthorized minting/duplication/... irreversible accounting corruption... across native balances, EVM balances, ERC20 representations" impact category. A desync between `stateDB` (what the EVM/JSON-RPC/`balanceOf` reports) and the actual bank-keeper-held coins means:
- A user's EVM-visible balance can become permanently inflated relative to their real spendable bank balance (or vice versa), because some `CoinSpent`/`CoinReceived` events from the inner precompile call are silently dropped from the outer call's processed window (or double counted if the inner window overlaps).
- Since EVM balance and precompile-mediated ERC20/staking/distribution balances are supposed to be 1:1 with bank-keeper coins, this breaks that invariant irreversibly for the affected account within the transaction, and the corrupted `stateDB` balance is what gets committed to state.
- Because Solidity contracts are free to trigger nested precompile calls (there is no guard preventing re-entrant precompile execution across different precompile addresses or via callback patterns), an unprivileged user who deploys a contract exercising this pattern can trigger the desync deterministically.

### Likelihood Explanation
The repository already implements a safer per-call `BalanceHandlerFactory` pattern in `precompile.go`'s `RunNativeAction`, showing the team was aware nested precompile calls need isolated windows — but several production precompiles use the older singleton `GetBalanceHandler()` accessor instead of going through `RunNativeAction`/`BalanceHandlerFactory`. Given the extensive dedicated test file explicitly built to reproduce "recursive precompile calls sharing the same BalanceHandler instance," this is a known, reproducible condition, not a theoretical one. However, I was not able to fully verify from the available index whether `GetBalanceHandler()` truly returns one shared instance across all calls to a precompile (vs. some other mitigation not visible in the indexed snippets), since `precompile.go`'s `GetBalanceHandler` method body itself was not returned by search. This should be verified directly in the full source before triage.

### Recommendation
Ensure every precompile execution path obtains a **fresh** `BalanceHandler` scoped to that single call (matching the `RunNativeAction`/`BalanceHandlerFactory.NewBalanceHandler()` pattern), rather than sharing a `BalanceHandler` field across the lifetime of a `Precompile` struct. Concretely: audit `GetBalanceHandler()` usages in `distribution.go`, `erc20.go`, `gov.go`, `ics20.go`, `slashing.go`, `staking.go`, and `testutil/testdata/debug/debug.go`, and migrate them to use per-call `BalanceHandlerFactory.NewBalanceHandler()` instances (as `werc20.go`/`precompile.go` already do), and add a regression test that asserts final EVM `stateDB` balances match bank-keeper balances after nested/recursive precompile calls (not just event counts, as the current `balance_handler_test.go` does).

### Proof of Concept
Conceptual PoC based on existing test infrastructure:
1. Deploy `ERC20RecursiveNonRevertingPrecompileCall.sol`, whose `_beforeTokenTransfer` hook calls `distribution.DISTRIBUTION_CONTRACT.claimRewards(address(this), 100)` in a loop [6](#0-5) .
2. Trigger an outer precompile call (e.g., `WithdrawDelegatorReward` or `Transfer` on a precompile using `GetBalanceHandler()`), which itself triggers a token transfer whose hook recursively invokes another precompile method that also calls `GetBalanceHandler().BeforeBalanceChange`/`AfterBalanceChange`.
3. Because both calls share the same handler instance, the inner call's `BeforeBalanceChange` resets `prevEventsLen`, so the outer call's `AfterBalanceChange` processes the wrong slice of `ctx.EventManager().Events()`.
4. Compare `stateDB.GetBalance()` for the affected account against `bankKeeper.GetBalance()` post-transaction (as done in `tests/integration/precompiles/werc20/test_utils.go`'s `ExpectBalanceChange` [8](#0-7) ) — a mismatch demonstrates the desync.

Note: I could not fully trace `GetBalanceHandler()`'s definition (only its call sites were retrieved), so full confirmation that this reaches production (non-test) precompiles as a singleton requires reading `precompiles/common/precompile.go`'s `GetBalanceHandler` method directly in a follow-up session before final triage.

// ExpectBalanceChange verifies expected balance changes after operations
func ExpectBalanceChange(
	addr sdk.AccAddress,
	beforeSnapshot *BalanceSnapshot,
	expectedIntegerDelta *big.Int,
	expectedFractionalDelta *big.Int,
	description string,
	grpcHandler grpc.Handler,
) {
	afterSnapshot, err := GetBalanceSnapshot(addr, grpcHandler)
	Expect(err).ToNot(HaveOccurred(), "failed to get balance snapshot for %s", description)

	actualIntegerDelta := new(big.Int).Sub(afterSnapshot.IntegerBalance, beforeSnapshot.IntegerBalance)
	actualFractionalDelta := new(big.Int).Sub(afterSnapshot.FractionalBalance, beforeSnapshot.FractionalBalance)

	Expect(actualIntegerDelta.Cmp(expectedIntegerDelta)).To(Equal(0),
		"integer balance delta mismatch for %s: expected %s, got %s",
		description, expectedIntegerDelta.String(), actualIntegerDelta.String())

	Expect(actualFractionalDelta.Cmp(expectedFractionalDelta)).To(Equal(0),
		"fractional balance delta mismatch for %s: expected %s, got %s",
		description, expectedFractionalDelta.String(), actualFractionalDelta.String())
}
