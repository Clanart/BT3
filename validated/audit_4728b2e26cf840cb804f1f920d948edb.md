## Confirmed vulnerability: stale `manualResolutions` map is carried across successive rebase/cherry-pick stops and applied to different files sharing the same path

### Title
Stale per-path manual conflict resolutions carry over across successive commits in a rebase/cherry-pick, causing silent auto-resolution of unrelated conflicts - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState()` preserves the `manualResolutions: Map<string, ManualConflictResolution>` from the previous conflict state as long as the conflict "kind" (`rebase`/`cherryPick`/`merge`) hasn't changed, without ever clearing entries whose paths have already been resolved and processed in a prior commit of the same multi-commit operation. [1](#0-0) 
This mirrors the audited bug's root cause: a batch operation (multiple CDPs / multiple commits) is processed using a value carried forward from earlier steps (bad debt / a manual resolution) instead of being invalidated once that step's specific conflict has actually been consumed and moved past.

### Finding Description
During a multi-commit rebase or cherry-pick, each commit in the sequence can independently produce a conflict on the *same file path* (e.g. `src/config.json` conflicts in commit #2, gets resolved by the user choosing "theirs", then `src/config.json` conflicts again in commit #5 for entirely different content). The `ManualConflictResolution` selections are stored in a `Map<string, ManualConflictResolution>` keyed purely by file `path` string, and this map is threaded through:

- `getConflictState()` / `updateConflictState()`, which reuse `prevConflictState.manualResolutions` verbatim whenever the state is still of the same conflict kind: [2](#0-1) 
- `continueRebase()`/`continueCherryPick()`, which look up the resolution purely `manualResolutions.find(f.path === path)`/`.get(path)` and immediately call `stageManualConflictResolution()`/`checkoutConflictedFile()` for that path without checking whether the underlying conflicted blob is the same one the user actually reviewed: [3](#0-2) [4](#0-3) 
- The store-level plumbing in `updateMultiCommitOperationConflictsIfFound()` explicitly pulls `manualResolutions` off the (potentially stale) `conflictState` and re-pushes it into the active step every time new conflicts are detected, again keyed only by path: [5](#0-4) 

Nothing in this chain checks that the conflicted content being auto-resolved at commit N is the *same* conflict the user reviewed and chose "ours/theirs" for at an earlier commit. The map is never pruned after a resolution has been consumed/staged, and the `ConflictsDialog` never re-shows a resolution decision to the user once it exists for a given path.

### Impact Explanation
Because the resolution decision persists purely by path across the whole multi-commit sequence, a maliciously crafted commit series (fully attacker-controlled, e.g. a branch/PR the user fetches and rebases onto or cherry-picks) can be built so that:
1. An early "decoy" commit touches `path/X` and produces a trivial, obviously-safe conflict that the user resolves once (e.g. picks "theirs").
2. A later commit in the *same* rebase/cherry-pick run reintroduces a conflict on the exact same `path/X`, but with entirely different, attacker-crafted content (e.g. a build script, CI config, or dependency lockfile).
3. Desktop silently reapplies the earlier resolution to the new conflict without re-prompting, staging and eventually committing attacker-chosen content that the user never actually reviewed for that specific hunk.

This is a silent-corruption-of-what-the-user-commits scenario: the user believes they only approved resolution for the first conflict but Desktop's git history ends up containing unreviewed, attacker-influenced content for a second, different conflict on the same path. It requires no local/admin access and works entirely from content in a fetched/rebased repository — matching the requested "unprivileged" attacker model of a crafted repository history.

### Likelihood Explanation
Any repository the user is willing to rebase onto or cherry-pick from (a fork, a PR branch, an untrusted remote) can be structured with this two-commit collision pattern on any path already known to exist in the target repo (e.g. `package.json`, `.github/workflows/*.yml`). Multi-commit rebases/cherry-picks with repeated conflicts on the same path are a normal, everyday occurrence, so the required conditions (same path, kind unchanged across the operation) are easy and unsuspicious to trigger; the user does not need to do anything unusual besides resolving conflicts as prompted.

### Recommendation
- Key `manualResolutions` by `(path, blobOID-of-conflicted-entry)` or otherwise invalidate/delete a path's entry from `conflictState.manualResolutions` as soon as it is consumed and staged in `continueRebase`/`continueCherryPick`, rather than letting it persist for the life of the whole operation.
- In `updateConflictState`, when the `currentTip` (commit position) changes within the same rebase/cherry-pick, drop stale entries whose underlying conflict content no longer matches what the resolution was made against.
- Re-render/re-prompt the `ConflictsDialog` whenever a new conflict on a previously-resolved path is detected, rather than silently auto-applying the old decision.

### Proof of Concept
1. Attacker prepares `feature` branch with two commits:
   - Commit A: modifies `config.yml` in a way that conflicts trivially with `main` (e.g., whitespace) — designed to be resolved quickly by the victim choosing "theirs".
   - Commit B (later in the same branch): modifies `config.yml` again, this time injecting a malicious build step, crafted to also conflict with `main`.
2. Victim opens Desktop, rebases `feature` onto `main` (or cherry-picks both commits in order).
3. Desktop stops at commit A's conflict; victim opens `ConflictsDialog`, selects `ManualConflictResolution.theirs` for `config.yml`, and clicks Continue. `_updateManualConflictResolution` stores `manualResolutions.set('config.yml', theirs)` [6](#0-5) , and `updateMultiCommitOperationConflictsIfFound` carries this map forward into the next round [5](#0-4) .
4. Git advances to commit B, `config.yml` conflicts again with the attacker's malicious content. `updateConflictState` reuses `prevConflictState.manualResolutions` because the conflict `kind` is still `'rebase'` [7](#0-6) , so the map still contains `config.yml -> theirs`.
5. `continueRebase` (or `continueCherryPick`) is called by the "no new conflicts to show" path and finds `manualResolutions.has('config.yml')`, calling `stageManualConflictResolution(repository, file, theirs)` automatically for commit B's conflict, without ever re-prompting the user [4](#0-3) .
6. The rebase/cherry-pick completes and commits the attacker's malicious `config.yml` content without the user ever reviewing it, then the branch is pushed as normal.

I was unable to fully trace the exact UI code path that decides whether `ShowConflicts` is re-displayed for a newly-conflicted commit versus silently calling `continueRebase`/`continueCherryPick` directly (this logic lives across several UI components under `app/src/ui/multi-commit-operation/` that were only partially indexed). A Devin session with full repository access would be needed to confirm precisely which caller re-invokes the dialog versus auto-continuing, but the core data-flow defect — the path-keyed `manualResolutions` map surviving across distinct per-commit conflicts without invalidation — is confirmed directly in the cited files.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })
