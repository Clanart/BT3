### Title
Untrusted-length allocation in `ReceivedOutput::read` via Bitcoin consensus decoding enables remote memory-exhaustion DoS - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The libxml2 CVE-2021-3541 class (small input causing disproportionate resource consumption via expansion/allocation driven by attacker-controlled length fields) maps onto `ReceivedOutput::read` in `networks/bitcoin`, which is explicitly in scope as an API fed untrusted bytes. It delegates `TxOut` and `OutPoint` parsing to `bitcoin::consensus::encode::Decodable` on an unbounded reader.

### Finding Description
`ReceivedOutput::read` reads a fixed-size scalar via `Secp256k1::read_F`, then calls `TxOut::consensus_decode` and `OutPoint::consensus_decode` on the raw reader [1](#0-0) . `TxOut` consensus decoding reads a CompactSize (varint) length prefix for `script_pubkey` and allocates a `Vec`/buffer of that size before/while attempting to read it. A CompactSize prefix as small as 9 bytes can declare a `u64` length, so a handful of attacker bytes can force an allocation attempt of up to the addressable memory space — the same unbounded-allocation-amplification shape as the entity-expansion bug. No size cap exists in `ReceivedOutput::read`, and the `BufReader` wrapper only avoids buffered over-read, not the allocation.

By contrast, the neighboring in-scope readers are defensible: `SchnorrAggregate::read` loops `C::read_G` per declared element, so each iteration requires real input bytes (linear cost, errors abort early) [2](#0-1) , and PedPoP `Commitments::read`/`EncryptedMessage::read` bound their loops by the locally-configured `ThresholdParams`, not by attacker bytes [3](#0-2) . `ReceivedOutput::read` is the outlier where the length field itself is attacker-controlled and trusted.

### Impact Explanation
An unprivileged party who can cause serialized `ReceivedOutput` bytes to be read (this function is on the enumerated untrusted-input attack surface) can send a short buffer whose varint declares a multi-gigabyte `script_pubkey`. This forces a huge allocation / OOM abort or excessive memory churn, denying service. Effect is analogous to the upstream CVE: availability loss via input size far smaller than the consumed resource.

### Likelihood Explanation
Reachable whenever `ReceivedOutput::read` consumes bytes influenced by an external party. Requires no secrets, no valid signatures, and no collusion — only a crafted byte stream. Exploitation requires the allocation path to actually reserve the memory (rust-bitcoin allocates a sized buffer for scripts), which is standard behavior for `Vec`-backed `consensus_decode`.

### Recommendation
Cap the declared script length before decoding: enforce a maximum (e.g., Bitcoin's standard `MAX_SCRIPT_SIZE` of 10,000 bytes, or a conservative bound like `MAX_STANDARD_TX_SIZE`) by decoding the CompactSize prefix yourself and rejecting oversized values before `TxOut::consensus_decode` allocates. Alternatively, wrap the reader in `reader.take(limit)` or read the `TxOut` into a bounded intermediate buffer first.

### Proof of Concept
```rust
use bitcoin::consensus::encode::Decodable;
use bitcoin::TxOut;

// 8 bytes value + CompactSize 0xFF + u64::MAX length = ~17 bytes of input
// requesting a ~18 exabyte allocation.
let mut bytes: &[u8] = &{
    let mut v = vec![0u8; 8];      // value (sats)
    v.push(0xff);                  // CompactSize => u64 follows
    v.extend(u64::MAX.to_le_bytes()); // declared script length
    v
};

// Aborts/OOMs attempting allocation before any real bytes are read.
let _ = TxOut::consensus_decode(&mut bytes);
```

Feeding the equivalent bytes (a valid 32-byte scalar prefix followed by this `TxOut` encoding) into `ReceivedOutput::read` triggers the same path at `networks/bitcoin/src/wallet/mod.rs:129` — a ~41-byte input demanding an allocation orders of magnitude larger, causing denial of service to the reader.

Caveat: the exact allocation size achieved depends on rust-bitcoin's internal `consensus_decode` buffering, which I could not inspect from this repository; the structural issue (untrusted CompactSize length with no cap) is confirmed in the call site itself.
