## Title
Improper prefix-only validation in `githubAssetVideoRegex` allows non-CDN hosts to bypass the video-source allowlist - (File: `app/src/lib/markdown-filters/video-url-regex.ts`)

## Summary
`githubAssetVideoRegex` is built as `^` + `escapeRegExp(user_images_cdn_url)` + `.+` + extension-suffix, with no requirement that the character immediately following the literal `https://user-images.githubusercontent.com` be `/` (path separator) or that it terminate the authority component. This is a classic "prefix match instead of authority match" flaw.

## Finding Description
The regex is defined as:
```js
export const githubAssetVideoRegex = new RegExp(
  '^' + escapeRegExp(user_images_cdn_url) + '.+' + videoExtensionRegex.source,
  'i'
)
``` [1](#0-0) 

It performs a raw string `.test()` against the string form of `el.src` / `a.href`, never against a parsed `URL().host`. Because the `.+` directly follows the literal domain string with no anchor (e.g. `[/?#]` or end-of-string), any string that merely *starts with* the literal `https://user-images.githubusercontent.com` text satisfies the "trusted host" branch, regardless of what the browser actually resolves as the authority.

For a URL such as `https://user-images.githubusercontent.com.mp4@evil.com/index.mp4`, the string is a literal prefix match on `https://user-images.githubusercontent.com`, so the regex returns true. However, per the WHATWG URL spec, `user-images.githubusercontent.com.mp4` before the `@` is parsed as userinfo, and the actual host resolved by the browser (and by `el.src`, which reflects the browser-normalized absolute URL) is `evil.com`. The regex-derived "trusted" verdict and the browser's actual authority diverge — the wrong value being trusted is the raw literal-prefixed string instead of the parsed authority/host.

This value is consumed directly by `VideoTagFilter.createFilterTreeWalker`'s `acceptNode`:
```js
acceptNode: function (el: Element) {
  return !isElement(el, 'video') || githubAssetVideoRegex.test(el.src)
    ? NodeFilter.FILTER_SKIP
    : NodeFilter.FILTER_ACCEPT
}
``` [2](#0-1) 
and by `filter()` in the same file, and by `VideoLinkFilter.getGithubVideoLink`: [3](#0-2) [4](#0-3) 

Both filters exist specifically to strip `<video>` elements/links whose source is *not* a GitHub-hosted user asset — the code comment states the intent explicitly: "If the url for the src does NOT match the pattern of a github user asset, we remove the video tag." [5](#0-4)  The bypass defeats that intended allowlist.

Separately (compounding this), `videoExtensionRegex` includes an empty alternative (`...|mpeg|)$`), so the extension check is a no-op and does not add any real constraint. [6](#0-5) 

## Impact Explanation
Because `SandboxedMarkdown`'s iframe is only sandboxed with `allow-same-origin` (no `allow-scripts`), the practical effect of a surviving attacker-controlled `<video src="...evil.com/...">` is not script execution — it is that the iframe will issue a network request to the attacker-controlled host when the markdown (PR/issue/commit body, comment, etc.) is rendered, since browsers by default preload video metadata. [7](#0-6)  This leaks the victim's IP address/User-Agent to an attacker-chosen server without any user interaction, and defeats the specific allowlist the maintainers built to prevent exactly this ("dotcom regenerates the tag because it verifies via DB that the asset exists" — Desktop instead relies solely on this regex as the trust boundary). It does not, by itself, achieve code execution, file access outside the repo, or credential exfiltration.

## Likelihood Explanation
Any attacker who can post repository content that Desktop renders as markdown (PR description/comment, issue, commit message rendered via `SandboxedMarkdown`) can trivially craft such a URL; no unusual user interaction is required beyond the victim viewing the markdown-rendered content in Desktop.

## Recommendation
Replace the string-prefix check with proper URL parsing: construct a `URL` object from the candidate src/href and verify `url.protocol === 'https:'` and `url.host === 'user-images.githubusercontent.com'` (exact match, not prefix), then separately validate the path/extension. Also remove the empty alternative from `videoExtensionRegex` so the extension check is meaningful.

## Proof of Concept
```js
import { githubAssetVideoRegex } from '../../src/lib/markdown-filters/video-url-regex'

test('bypasses host allowlist via userinfo trick', () => {
  const malicious = 'https://user-images.githubusercontent.com.mp4@evil.com/index.mp4'
  expect(githubAssetVideoRegex.test(malicious)).toBe(true) // wrongly trusted
})
```
When set as a `<video>` element's `src`, `el.src` reflects the browser-normalized absolute URL whose actual host is `evil.com`; feeding this element into `VideoTagFilter.createFilterTreeWalker`'s `acceptNode` yields `NodeFilter.FILTER_SKIP` (the video is left in place) instead of being removed, because `githubAssetVideoRegex.test(el.src)` returns `true`.
