## Title
Repeated lock→startUnlock→forceUnLock cycling allows an attacker to recover more than the intended 20% base amount, effectively diverting protocol penalty revenue - (File: VLMGP.sol)

## Summary
`forceUnLock` computes the penalty split independently per unlock slot using `slot.amountInCoolDown` at the moment of the call, with `baseAmountToUser = amountInCoolDown / 5` and an `unlockFactor` that is `0` when `forceUnLock` is called in the same block as `startUnlock`. Because nothing prevents an attacker from immediately relocking the `amountToUser` they just received and repeating the cycle within a single transaction, they can extract a geometrically compounding series of "20% rebates" that converges toward 25% of their original principal instead of the intended 20%, reducing the effective penalty from 80% down toward 75%.

## Finding Description
In `expectedPenaltyAmount`, at `t == slot.startTime` (i.e., `forceUnLock` called in the same block as `startUnlock`), `unlockFactor` evaluates to `0`: [1](#0-0) 

so `amontToUser = baseAmountToUser = coolDownAmount / 5` exactly, and `penaltyAmount = coolDownAmount * 4 / 5`.

`forceUnLock` transfers `amountToUser` to the caller and adds `penaltyAmount` to `totalPenalty`, then zeroes the slot: [2](#0-1) 

Nothing prevents the caller from immediately calling `lock()` with the just-received `amountToUser`, then `startUnlock()` and `forceUnLock()` again on the new (or reused) slot, all within the same transaction via a helper contract, since `lock`, `startUnlock`, and `forceUnLock` are independent `nonReentrant` functions called sequentially (not nested), which is not blocked by reentrancy guards: [3](#0-2) 

Because the penalty formula is computed fresh from `slot.amountInCoolDown` each cycle with no memory of prior cycles, each iteration returns 20% of the *current* remaining amount rather than 20% of the *original* principal. Recursively, if `X_0` is the original amount:

- Cycle 1: user receives `0.2 * X_0`, relocks it.
- Cycle 2: user receives `0.2 * (0.2 * X_0) = 0.04 * X_0`.
- Cycle n: user receives `0.2^n * X_0`.

Cumulative amount received after `N` cycles is `X_0 * 0.2 * (1 - 0.2^N) / 0.8`, which converges to `0.25 * X_0` as `N` grows (a handful of cycles gets within a fraction of a percent of this limit). This is strictly greater than the `0.2 * X_0` a single one-shot `forceUnLock` at `t=0` would yield, meaning `totalPenalty` accrues only ~75% of `X_0` instead of the intended 80%. The token accounting per call is conserved (`amountToUser + penaltyAmount == coolDownAmount`), so there is no double-spend of tokens — the issue is that the *penalty rate itself* is degraded by looping, letting the attacker keep a larger share of principal than the protocol's economic design (an 80% forced-exit penalty) intends, at the expense of `penaltyDestination`.

## Impact Explanation
This does not create insolvency or double-spend of MGP tokens (transfers are internally conserved per call), but it does let any unprivileged user erode the intended 80% early-exit penalty down to roughly 75% by looping `lock → startUnlock → forceUnLock` within one transaction via a batching contract. The difference (up to 5 percentage points of the locked principal) is value that the protocol design intends to route to `penaltyDestination` via `transferPenalty()` but instead is retained by the attacker. This is a real, quantifiable diversion of protocol penalty revenue away from its intended destination, undermining the penalty mechanism's economic guarantee.

## Likelihood Explanation
Fully permissionless and repeatable: the attacker only needs MGP tokens they already hold and a simple helper contract to sequence calls within one transaction (no time delay required since `unlockFactor` is `0` at `t == startTime`). Gas cost scales linearly with the number of cycles, but the gain converges quickly (within ~10 cycles the attacker is already close to the 25% asymptote), so it is cheap and practical to execute for any lock size.

## Recommendation
Track cumulative penalty state across relock cycles per user (e.g., a running "penalized principal" counter, or a cooldown-linked delay/lockout preventing immediate re-`startUnlock` of freshly force-unlocked funds), or enforce a minimum elapsed time / cap on the number of `startUnlock`/`forceUnLock` cycles per user per epoch so that the effective penalty cannot be diluted below the intended 80% through same-block relocking.

## Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, and MGP token; mint `X` MGP to an attacker-controlled helper contract.
2. Helper contract function `exploit(uint256 cycles)`:
   - `MGP.approve(VLMGP, type(uint256).max)`.
   - Loop `cycles` times: call `VLMGP.lock(currentAmount)`, `VLMGP.startUnlock(currentAmount)`, `VLMGP.forceUnLock(slotIndex)`; track `amountToUser` returned via `ForceUnLock` event/return balance delta; set `currentAmount = amountToUser` for next iteration; accumulate `totalReceived += amountToUser`.
3. Assert: `totalReceived` after `cycles >= 10` approaches `0.25 * X` (within rounding), strictly greater than `0.2 * X` (the result of a single one-shot `forceUnLock` baseline computed separately for comparison).
4. Assert: `totalPenalty` accumulated is less than `0.8 * X` (i.e., strictly less than the single-shot baseline penalty), demonstrating the protocol collected less penalty revenue than intended due to looping.

    function expectedPenaltyAmount(uint256 _slotIndex) public view returns(uint256 penaltyAmount, uint256 amontToUser) {
        UserUnlocking storage slot = userUnlockings[msg.sender][_slotIndex];

        uint256 coolDownAmount = slot.amountInCoolDown;
        uint256 baseAmountToUser = slot.amountInCoolDown / 5;
        uint256 waitingAmount = coolDownAmount - baseAmountToUser;

        uint256 unlockFactor = 1e12;
        if((block.timestamp - slot.startTime) <= (slot.endTime - slot.startTime))
            unlockFactor = ((block.timestamp - slot.startTime) * 1e12 / (slot.endTime - slot.startTime)) ** 2 / 1e12;

        uint256 unlockAmount = waitingAmount * unlockFactor / 1e12;
        amontToUser = baseAmountToUser + unlockAmount;
        penaltyAmount = coolDownAmount - amontToUser;
    }
