### Title
Users lose excess ETH permanently when dispatching requests with native token payment — no refund of Uniswap swap change ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and swap it for an exact amount of `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`. This router call is a "buy exact output, spend up to `msg.value`" swap: any unused ETH is refunded by the router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original caller (`_msgSender()`). `EvmHost` never forwards or refunds that leftover ETH back to the user. Any ETH sent beyond the exact amount needed for the swap is permanently retained by the Host contract, with no `maxAmount`/slippage-style guard and no refund path, unlike the sibling contract `IntentGatewayV2.sol` which performs the identical swap but explicitly tracks `amounts[0]` and refunds the unspent native balance to `msg.sender`.

The same pattern repeats in `dispatch(DispatchGet)` and `fundRequest()`. In every case, the caller must send enough ETH to cover `post.fee`/`get.fee`/`amount` at current Uniswap price plus a margin, since there is no `quote()` guarantee of exact pricing at execution time (price can move between the client-side `quote()` call and the on-chain swap, exactly analogous to the reported "vault price crosses a threshold" scenario — here the price moves due to slippage/AMM curve). `swapETHForExactTokens` returns unused ETH to the caller of the router (i.e., `EvmHost`), but `EvmHost` has no code afterward to forward that unused ETH back to `_msgSender()`.

Contrast this with the sibling contract that performs the exact same operation correctly: [4](#0-3)

`EvmHost.sol` has no equivalent `msgValue -= amounts[0]` tracking or refund call anywhere in `dispatch()`/`fundRequest()`.

### Impact Explanation
Any user or `HyperApp` dispatching a request with native-token payment (the officially documented and encouraged path per `docs/content/developers/evm/messaging/post-requests.mdx` and `IDispatcher.sol`) permanently loses any ETH sent beyond the exact swap requirement. There is no `maxAmount` cap, no refund, and no way to reclaim it — it silently accrues in the `EvmHost` contract balance. Since the client-side fee quoting (`quote()` in `HyperApp.sol` via `getAmountsIn`) is inherently stale by the time the transaction lands (block delay, AMM price movement, MEV), users are structurally incentivized/forced to over-supply ETH as a safety margin, and 100% of that margin is lost every single dispatch. This is a direct, repeatable loss of user funds on every native-token dispatch path in production.

### Likelihood Explanation
High likelihood and continuous exposure: this is the documented, default flow for native-token payment (`docs/content/developers/evm/messaging/post-requests.mdx` explicitly recommends sending native value and letting the Host swap). Any unprivileged user calling `dispatch()` or `fundRequest()` with `msg.value` even slightly above the exact swap requirement (which is normal, since exact pricing cannot be known in advance) triggers the loss — no attacker or malicious actor is needed, and no privileged role, relayer, or prover involvement is required.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the returned `amounts[0]` (actual ETH spent) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented correctly in `IntentGatewayV2.sol`. Alternatively/additionally, expose an explicit `maxAmount`/slippage-bound parameter so callers can cap the ETH they are willing to spend and revert rather than silently forfeiting the difference.

### Proof of Concept
1. A `HyperApp` calls `host().dispatch{value: X}(post)` where `X` is the ETH amount estimated via `quote(post)` plus a safety buffer (standard practice since block delay/slippage means the exact quote is unreliable).
2. `EvmHost.dispatch` calls `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`.
3. Uniswap spends only `amounts[0] <= X` ETH to acquire exactly `post.fee` fee tokens, and refunds `X - amounts[0]` ETH to the caller of the router — which is the `EvmHost` contract address, not the original `msg.sender`.
4. `EvmHost.dispatch` never reads `amounts[0]` and never transfers any ETH back to `_msgSender()`; the refunded `X - amounts[0]` ETH remains permanently in the `EvmHost` contract balance.
5. Repeating this for every dispatch call continuously drains user-supplied ETH margin into the Host contract with no recovery mechanism.
