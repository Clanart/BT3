### Title
`handleGetResponses` accepts GET responses proven against **any** trusted state machine, not just the request's actual destination chain - ([File: evm/src/core/HandlerV2.sol])

### Summary
This is the same bug class as the reported `static_validate_system_transaction` chain-ID gap: a piece of protocol state (a transaction's implicit chain, or here a response's implicit source chain) is never checked against the identifier actually used to authorize it, so an attacker can substitute proof data anchored to a different, still-trusted context and have it accepted as if it belonged to the correct one.

### Finding Description
`handleGetResponses` in [1](#0-0)  verifies a `GetResponseLeaf` batch by:
1. Checking the wrapped `GetRequest` hash is a known, previously-dispatched request (`host.requestCommitments(...)`, comment: "known request? also serves as source check").
2. Verifying merkle membership of `leaf.response.hash()` against `host.stateMachineCommitment(message.proof.height)`.
3. Checking for a duplicate response receipt, then calling `host.dispatchIncoming(leaf.response, _msgSender())`.

Nowhere does this function check that `message.proof.height.stateMachineId` is the expected chain that is authorized to *produce* `GetResponse`s for that request (i.e., the coprocessor/Hyperbridge chain, or the request's `dest`). Contrast this with:
- `handlePostRequests` in the same file, which explicitly enforces `leaf.request.dest.equals(host.host())` [2](#0-1) .
- The Substrate response handler, which explicitly binds the request's destination chain to the proof's state machine id: `if req.dest_chain() != proof.height.id.state_id { Err(...) }` [3](#0-2) .
- `pallet-state-coprocessor`, which enforces both source and destination binding explicitly: `if full.source_chain() != source.height.id.state_id ... if full.dest_chain() != response.height.id.state_id` [4](#0-3) , with dedicated regression tests [5](#0-4) .

An `IHost` instance can hold state-machine commitments for multiple distinct `stateMachineId`s simultaneously — `handleConsensus` stores a commitment for every `intermediate.stateMachineId` returned by the configured consensus client in a single update, and the codebase's own consensus clients (BEEFY/GRANDPA producing many parachain `StateMachineId`s, or a host wired to more than one light client) populate `stateMachineCommitment` for chains other than the one the response is claimed to originate from (see `IntermediateState`/`storeStateMachineCommitment` loop) [6](#0-5) . `handleGetResponses` will happily accept `message.proof.height` pointing at *any* of those trusted state machine ids as long as the leaf hashes verify against that chain's root — it never requires `message.proof.height.id` to equal the `GetRequest.dest` (or the designated response-producing chain) the way the Substrate/coprocessor paths do.

### Impact Explanation
Because the source-chain binding for the GET-response proof is missing, a relayer/caller can supply a `GetResponseMessage` whose merkle proof is anchored to a state machine that is *not* the one that was actually queried, but which the host still trusts for some other purpose. If that alternate state machine's overlay root can be influenced or already contains attacker-reachable, permissionlessly-inserted leaves (e.g., via any ISMP dispatch from an unprivileged contract on that other tracked chain), the attacker can manufacture a `GetResponse.values` payload of their choosing for a real, pending `GetRequest` and have it delivered to the destination module's `onGetResponse` callback via `host.dispatchIncoming`. This is exactly the "false proof / false state acceptance" failure mode the bounty targets: a module (e.g., a price oracle, cross-chain balance check, or intent-settlement path relying on `GetResponse.values`) will act on forged state, potentially releasing funds, unlocking escrow, or making a settlement decision based on data that never came from the real destination chain.

### Likelihood Explanation
Triggerable by any unprivileged relayer submitting a permissionless `handleGetResponses` call — no admin, governance, prover, or malicious-peer assumption is required, only that the target `IHost` deployment tracks more than one `stateMachineId` (a normal, documented configuration given the multi-consensus-client architecture in this codebase). The check that is missing elsewhere in the same codebase (Substrate `response.rs`, `state-coprocessor`) confirms the invariant is expected and enforced there, making its absence here a real regression rather than a design choice.

### Recommendation
In `handleGetResponses`, before accepting the batch, validate that `message.proof.height.id` (`stateMachineId`) equals the chain authorized to produce the `GetResponse` for each `leaf.response.request` — mirroring the Substrate handler's `req.dest_chain() != proof.height.id.state_id` check and the coprocessor's explicit source/destination binding — rather than relying solely on "request commitment exists" as an implicit source check.

### Proof of Concept
1. Deploy/observe an `IHost` configured with two trusted state machine ids: `A` (the real destination chain a `GetRequest` was sent to) and `B` (some other chain the host also trusts commitments for, e.g., via a secondary consensus client).
2. Dispatch a legitimate `GetRequest` with `dest = A`; its commitment is stored via `host.requestCommitments`.
3. On chain `B`, as an unprivileged actor, get an arbitrary leaf inserted into `B`'s tracked overlay/MMR root whose content equals `abi.encode(GetResponse{request: <the GetRequest from step 2>, values: <attacker-chosen>})` hash.
4. Once `B`'s state commitment is updated on the host via `handleConsensus`, call `handleGetResponses` with `message.proof.height = {stateMachineId: B, height: h}` and `message.responses = [{response: GetResponse{...attacker values...}, index}]`.
5. `handleGetResponses` passes: `requestCommitments` lookup succeeds (request from step 2 is known), the merkle proof verifies against `B`'s legitimate root, and no check ever compares `B` to `A`. `host.dispatchIncoming` delivers the forged `GetResponse` to the destination module.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }
