### Title
Aggregator's `InternalSendTx` RPC is reachable without any authentication when `client_verification=false` - ([File: core/src/servers.rs], [File: core/src/rpc/aggregator.rs])

### Summary
`create_grpc_server` (`core/src/servers.rs`) picks the `Interceptors::Noop` interceptor whenever `config.client_verification` is `false`, and for the aggregator's server that path is only ever logged with a `tracing::warn!` when verification is *enabled* — never enforced when disabled. `Interceptors::Noop::call` (`core/src/rpc/interceptors.rs`) unconditionally returns `Ok(req)`, so any caller reaching the aggregator's public TCP port can invoke `AggregatorServer::internal_send_tx` (`core/src/rpc/aggregator.rs`), which forwards the request straight to `insert_try_to_send` with no independent caller check.

### Finding Description
The binding that should hold is: *the set of callers who can reach `internal_send_tx` == the set of callers the "Internal" naming convention and the `is_internal()` gRPC-method check are meant to restrict to (i.e., the aggregator's own trusted peers, verified via `req.peer_certs()`)*.

Tracing the call path:
- `create_grpc_server` [1](#0-0)  wraps the service in `InterceptedService::new(service, Noop)` whenever `config.client_verification` is false, with no TLS client-cert requirement at all (`ServerTlsConfig::new().identity(server_identity)` only, no `client_ca_root`) [2](#0-1) .
- `Interceptors::Noop::call` returns `Ok(req)` unconditionally, performing no check of `is_internal()` or peer certs at all [3](#0-2) .
- `create_aggregator_grpc_server` only emits a warning when `client_verification` is *true*; it does nothing to force verification on or reject the RPC surface when it is *false* [4](#0-3) .
- `AggregatorServer::internal_send_tx` (in `core/src/rpc/aggregator.rs`) calls `insert_try_to_send(...)` directly, relying entirely on the interceptor layer for authorization; it performs no additional sender-identity check of its own.

Because the `is_internal()`/peer-cert check (`only_aggregator_and_self`, `core/src/rpc/interceptors.rs` lines 36-77) is the *only* mechanism enforcing the "Internal" naming contract, and that mechanism is fully bypassed under `Noop`, any unauthenticated network peer that can reach the aggregator's gRPC port can call `internal_send_tx` with an arbitrary `raw_tx`/`fee_type`, and it will be accepted and inserted into the tx_sender queue exactly as if it came from a trusted internal caller.

### Impact Explanation
This is an unauthenticated state-changing/broadcasting call: an attacker can make the bridge's own fee-bumping tx_sender infrastructure track and RBF-bump an attacker-chosen Bitcoin transaction, which can be used to interfere with the timing of reimbursement/challenge transactions that share the same fee-bumping resources. This matches the "High" impact category for an unauthenticated state-changing or broadcasting call defined in the rules. It does not, on the evidence gathered, demonstrate a Critical-level outcome (no move-to-vault UTXO drain, no wrongful reimbursement credit, no forced collateral burn is shown) — the reachable consequence is limited to unauthenticated interaction with the tx_sender queue, which is an internal-only surface being exposed.

### Likelihood Explanation
The precondition is a specific deployment configuration: `client_verification=false` on the aggregator. The code's own behavior (warning only when verification is *enabled*, never enforcing it when disabled) indicates that running the aggregator with `client_verification=false` is the anticipated/common configuration, since the aggregator's server is meant to accept public, non-mTLS connections from users while still expecting `Internal*`-prefixed methods to be protected. Under this realistic configuration, exploitation requires nothing more than a plain TCP/TLS connection (no client certificate) to the aggregator's port and a single `InternalSendTx` gRPC call — no BTC cost, no privileged key material, fully repeatable.

### Recommendation
Do not rely solely on the TLS-based `Interceptors` layer to protect `Internal*`-prefixed RPC methods. Either (a) always enforce `client_verification`/peer-cert checks for methods whose gRPC method name starts with `Internal`, regardless of the `client_verification` config flag, or (b) expose `internal_send_tx` only on a separate, non-public-facing listener (e.g., a loopback/Unix-socket-only service) that is never reachable from the public TCP port used for user-facing aggregator RPCs.

### Proof of Concept
```rust
// core/src/rpc/aggregator.rs or a new integration test module (not under core/src/test per scope rules,
// but the logic below documents the exact assertion needed)
#[tokio::test]
async fn internal_send_tx_unauthenticated_when_client_verification_disabled() {
    let mut config = test_config(); // client_verification = false
    let (addr, _shutdown) = create_aggregator_grpc_server(config).await.unwrap();

    // Dial with a plain TLS client presenting NO client certificate.
    let channel = tonic::transport::Channel::from_shared(format!("https://{addr}"))
        .unwrap()
        .tls_config(ClientTlsConfig::new()) // no identity() call => no client cert
        .unwrap()
        .connect()
        .await
        .unwrap();

    let mut client = ClementineAggregatorClient::new(channel);
    let resp = client
        .internal_send_tx(SendTxRequest {
            raw_tx: attacker_signed_tx_bytes(),
            fee_type: FeeType::default() as i32,
        })
        .await;

    // BEFORE fix: resp is Ok(...) — request accepted with no authentication.
    // AFTER fix: resp should be Err(Status::unauthenticated(_)).
    assert!(resp.is_err(), "internal_send_tx must reject unauthenticated callers");
}
```
Both sides of the binding — "caller reaching `internal_send_tx`" vs. "caller the `Internal*` naming convention/`is_internal()` check is meant to allow" — diverge before the fix (Noop accepts any caller) and match after the fix (unauthenticated callers rejected regardless of `client_verification` setting).
