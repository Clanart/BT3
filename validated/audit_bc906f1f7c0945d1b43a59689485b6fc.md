### Title
Discard Changes moves untracked/malicious-path files to Trash via unsanitized `Path.resolve` before checking they remain inside the repository - ([File: app/src/lib/stores/git-store.ts])

### Summary
The Sherlock report's root cause is that a destructive action (`token.authBurn`) executes unconditionally on attacker/user-controllable state without first validating that the precondition it depends on (`holdings[u][m]` populated by the sibling `redeem` call) actually holds — the ordering/validation guard lives in a different function than the one performing the destructive action. The generalizable primitive is: *a destructive operation resolves a path/identifier taken from external/attacker-influenced data and acts on it without re-validating that the resolved target is the one the caller actually intended, and no containment check exists at the point of the destructive call.*

The closest Desktop analog is `GitStore.discardChanges()`, which computes the on-disk path to delete/trash directly from `file.path` (sourced from `git status`, i.e., from whatever is present in a cloned/fetched working directory) using a plain `Path.resolve`, with no verification that the resolved path stays inside the repository root, unlike other destructive-path operations in the same codebase (e.g., `resolveWithin` used in `openRepositoryFromUrl` and `buildConflictContext`).

### Finding Description
`GitStore.discardChanges` builds the trash target as: [1](#0-0) 
```
if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
  if (moveToTrash) {
    try {
      await this.shell.moveItemToTrash(
        Path.resolve(this.repository.path, file.path)
      )
```
`file.path` comes from working-directory status entries, which are populated from whatever git reports for the working tree of a repository that can have been cloned from, or had its working tree contents introduced by, an untrusted remote (e.g., a symlinked file/directory checked into the tree, or a path containing traversal-like components on filesystems where `core.symlinks`/protections don't fully normalize it). `Path.resolve` will happily follow such a path outside `this.repository.path`; there is no subsequent check that the resolved path is still contained within the repository, unlike the pattern established elsewhere in the codebase for handling paths derived from external/URL input: [2](#0-1) [3](#0-2) 
which explicitly resolves a path with `resolveWithin(repository.path, filepath)` and rejects it if it escapes the repository, or `copilot-conflict-context.ts`'s explicit "Guard against path traversal and symlink escapes": [4](#0-3) 

`discardChanges` has no equivalent guard. The invariant "the path we are about to destroy/move-to-trash must be inside the repository" is enforced in other code paths (`openRepositoryFromUrl`, Copilot conflict context) but not in this one — mirroring exactly the report's pattern of a guard existing in a sibling function but missing from the function that performs the actual destructive operation.

### Impact Explanation
If an attacker can get a victim to open/clone a repository (or fetch content into an existing repository's working tree) containing a symlink or crafted path entry that `git status` reports as a modified/untracked "file" whose resolved location escapes the repository root, then when the victim uses Desktop's "Discard changes"/"Discard all changes" feature, `moveItemToTrash(Path.resolve(...))` will act on a path outside the repository. Depending on the symlink target this can move/delete files elsewhere on the victim's filesystem (e.g., other project files, config, or — in the `moveToTrash === false` branch — outright `rm` them via `await rm(Path.join(this.repository.path, file.path))`, which has the same unguarded join), producing a file-delete-outside-repo primitive with no privileged access, malware, or leaked credentials required — the trigger is simply opening a hostile repository and clicking a normal, everyday UI action.

### Likelihood Explanation
Requires the victim to add/clone an attacker-authored repository and to run "Discard changes" on the affected path, which is a common, expected user action once changes exist. Whether this is fully exploitable depends on how `core.symlinks` and the platform filesystem resolve such entries during `git status`/`Path.resolve`, and whether git itself would have already materialized the symlink/traversal path into the working tree in a way `Path.resolve` can walk through — this could not be fully verified from the index alone (git's own symlink checkout protections may partially mitigate this on some platforms/configs), so likelihood should be validated with a live repro rather than treated as certain.

### Recommendation
In `GitStore.discardChanges` (and the parallel `rm(Path.join(...))` fallback branches), resolve every `file.path` with the same `resolveWithin(this.repository.path, file.path)` containment check already used in `dispatcher.ts`'s `openRepositoryFromUrl` and in `copilot-conflict-context.ts`, and skip/reject (rather than trash/delete) any path whose resolved target escapes the repository root before calling `moveItemToTrash` or `rm`.

### Proof of Concept
Not independently reproducible from the static index alone — confirming exploitability requires: (1) constructing a test repository containing a symlink or crafted path entry that `git status` reports as a changed file whose real path resolves outside the repo root on the target platform, (2) adding it as a repository in Desktop, and (3) invoking "Discard changes" and observing whether `moveItemToTrash`/`rm` acts on the out-of-repo target. This should be validated with a live Devin session against the actual filesystem/git behavior before treating it as confirmed exploitable.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
