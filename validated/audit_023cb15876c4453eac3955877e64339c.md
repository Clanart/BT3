### Title
Gasless module's EOA-only check (`ShouldCheckSenderCode`) is validated once at mempool admission and is not re-checked against the sender's code state at execution time, allowing an EIP-7702 delegation to be installed in the same block just before an approve/swap transaction executes - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The Gasless module implements the exact "EOA-only" defense the external report warns about: it rejects an approve/swap transaction whose sender already has contract code, specifically to prevent flash-loan-style abuse of the gasless drain path. Kaia already has the "AUTH/AUTHCALL"-equivalent functionality live in production (EIP-7702 `TxTypeEthereumSetCode`), which is precisely the mechanism the report predicted would eventually undermine `tx.origin`/EOA-based checks. The `hasCode` check is evaluated against `g.currentState`, which is only refreshed once per block (`PostInsertBlock`), so the check reflects state as of the *previous* block, not the state produced by other transactions from the same sender executing earlier in the *same* block.

### Finding Description
`GaslessConfig.ShouldCheckSenderCode()` gates a check that is meant to guarantee only genuine EOAs can use the gasless approve/swap flow: [1](#0-0) 

This check is performed in `checkBalanceForApprove` / `checkBalanceForSwap`, called from `GetCheckBalance`, which runs during transaction-pool admission: [2](#0-1) [3](#0-2) 

The code check itself reads `g.currentState`, a snapshot set only after a block is fully inserted: [4](#0-3) [5](#0-4) 

Kaia's EIP-7702-style `TxTypeEthereumSetCode` transaction lets an EOA (self-)author a `SetCodeAuthorization` that installs delegated code on its own account as soon as the transaction executes: [6](#0-5) 

The project's own test explicitly demonstrates that once a `SetCodeTx` has been *mined*, a subsequent swap from the same address is correctly rejected because `getCurrentHasCode` now reports code: [7](#0-6) [8](#0-7) 

However, that test only proves the defense works *after* the delegating transaction has already been committed to a prior block. It does not exercise the case where the `SetCodeTx` (nonce N) and the Approve/Swap transactions (nonce N+1, N+2) are all admitted into the pool and mined together in the *same* block. Because `GetCheckBalance` is evaluated at admission time against `pool.currentState`/`g.currentState` (i.e., state as of the last confirmed block), the Approve/Swap transactions pass the "sender with code is not allowed" gate while the sender's account still has no code — even though the SetCodeTx that will install delegated code executes immediately before them in the same block, once nonce order is respected. There is no analogous "hasCode" re-validation performed inside the actual `TransitionDb()` execution path for approve/swap transactions; the only enforcement point is `GetCheckBalance`, called from the tx-pool.

This is structurally the same weakness flagged in the external report: an EOA/contract distinction is enforced only at one point in time (transaction submission), and an attacker can restructure a single logical operation into multiple sequenced transactions (SetCode → Approve → Swap) so that the state used for the check does not match the state that exists when the guarded logic actually runs.

### Impact Explanation
If the check-time/execution-time mismatch is real (i.e., the tx pool allows sequential nonces N, N+1, N+2 from the same sender to be admitted and mined together, which is the normal, supported nonce-ordering behavior of the pool), an attacker can:
1. Submit a `TxTypeEthereumSetCode` transaction delegating their own EOA to an attacker-controlled contract (nonce N).
2. Submit the gasless ApproveTx (nonce N+1) and SwapTx (nonce N+2) in the same bundle.
3. Have all three mined in the same block; the ApproveTx/SwapTx pass admission-time validation (sender still coreless at admission), but at execution time the sender is a delegated/contract-backed account — exactly the class of actor the check exists to exclude.

This would let a "contract" identity participate in the gasless swap-for-gas settlement path that is supposed to be restricted to EOAs, reintroducing the flash-loan/atomic-composition risk the check was designed to prevent, and constitutes gasless-settlement abuse of the safeguard.

### Likelihood Explanation
Medium. The attacker fully controls the sequence and content of their own transactions (no privileged access needed) and EIP-7702 authorization can be self-signed by the sender in the same key used for the transaction, as shown in the codebase's own helper `sendSetCodeTx`. The main uncertainty is whether `TxPool.checkDelegationLimit`/`validateAuth` (which restrict "in-flight" transactions for delegated/pending-delegation accounts) prevent three sequential nonces from the same account from being queued simultaneously; I could not fully verify the exact interaction between `checkDelegationLimit`'s pending/queue semantics and normal sequential-nonce admission within the available exploration budget: [9](#0-8) [10](#0-9) 

### Recommendation
- Re-validate `hasCode`/EOA status for the gasless sender at actual execution time (inside `TransitionDb`/block-assembly, immediately before the approve/swap logic runs), not only at mempool admission against a stale snapshot.
- When building a block, re-run `GetCheckBalance` against the state produced after each preceding transaction in the same block for the same sender, or explicitly disallow bundling a `TxTypeEthereumSetCode` transaction with an approve/swap transaction from the same sender within one block.
- Add a regression test that specifically submits `SetCodeTx (N) + ApproveTx (N+1) + SwapTx (N+2)` all unconfirmed in the pool at once (rather than mining the SetCodeTx first), and assert that the swap is still rejected once all three are included in the same block.

### Proof of Concept
1. Generate a fresh EOA `attacker` with sufficient balance and an ERC20 token balance eligible for the gasless swap-for-gas flow.
2. Construct `SetCodeTx` at `attacker.Nonce` delegating `attacker`'s own address to an arbitrary deployed contract, self-signed exactly as in `tests/gasless_test.go`'s `sendSetCodeTx` helper.
3. Construct `ApproveTx` at `attacker.Nonce+1` and `SwapTx` at `attacker.Nonce+2` using the existing `sendApproveTx`/`sendSwapTx` helpers, without waiting for `SetCodeTx` to be mined.
4. Submit all three transactions to the pool in one batch (or in quick succession) so they are all pending before the next block is produced, then mine a block containing all three.
5. Observe whether `ApproveTx`/`SwapTx` are accepted into the block despite `attacker` having delegated code by the time they execute — if so, `GetCheckBalance`'s "sender with code is not allowed" guard failed to prevent contract-backed accounts from using the gasless path within a single block.

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

func (st *StateTransition) applyAuthorization(auth *types.SetCodeAuthorization, rules params.Rules) (err error) {
	authority, err := st.validateAuthorization(auth)
	if err != nil {
		return err
	}

	// If the account already exists in state, refund the new account cost
	// charged in the initrinsic calculation.
	if st.state.Exist(authority) {
		// If the account is not AccountKeyTypeLegacy, setcode is not allowed.
		accountKeyType := st.state.GetKey(authority).Type()
		if !accountKeyType.IsLegacyAccountKey() {
			return fmt.Errorf("%w: %v", ErrAuthorizationNotAllowAccountKeyType, accountKeyType)
		}
		st.state.AddRefund(params.CallNewAccountGas - params.TxAuthTupleGas)
	}

	// Update nonce and account code.
	st.state.IncNonce(authority)
	delegation := types.AddressToDelegation(auth.Address)
	if common.EmptyAddress(auth.Address) {
		// Delegation to zero address means clear.
		st.state.SetCodeToEOA(authority, []byte{}, rules)
		return nil
	}

	// Otherwise install delegation to auth.Address.
	// We treat EOA and SCA as separate objects and therefore need to use
	// distinct methods.
	st.state.SetCodeToEOA(authority, delegation, rules)

	return nil
}

func (pool *TxPool) checkDelegationLimit(tx *types.Transaction) error {
	from, _ := types.Sender(pool.signer, tx) // validated

	// Short circuit if the sender has neither delegation nor pending delegation.
	if pool.currentState.GetCodeHash(from) == types.EmptyCodeHash && !pool.all.hasAuth(from) {
		return nil
	}
	pending := pool.pending[from]
	if pending == nil {
		// Transaction with gapped nonce is not supported for delegated accounts
		if pool.getPendingNonce(from) != tx.Nonce() {
			return ErrOutOfOrderTxFromDelegated
		}
		return nil
	}
	// Transaction replacement is supported
	if pending.Contains(tx.Nonce()) {
		return nil
	}
	return ErrInflightTxLimitReached
}

// validateAuth verifies that the transaction complies with code authorization
// restrictions brought by SetCode transaction type.
func (pool *TxPool) validateAuth(tx *types.Transaction) error {
	// Allow at most one in-flight tx for delegated accounts or those with a
	// pending authorization.
	if err := pool.checkDelegationLimit(tx); err != nil {
		return err
	}

	// For symmetry, allow at most one in-flight tx for any authority with a
	// pending transaction.
	for _, auth := range tx.SetCodeAuthorities() {
		var count int
		if pending := pool.pending[auth]; pending != nil {
			count += pending.Len()
		}
		if queue := pool.queue[auth]; queue != nil {
			count += queue.Len()
		}
		// Replace the existing in-flight transaction for delegated accounts
		// are still supported
		if count > 1 {
			return ErrAuthorityReserved
		}
	}
	return nil
}
