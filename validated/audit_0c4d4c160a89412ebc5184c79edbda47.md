### Title
Manual conflict resolutions are silently reapplied to unrelated conflicts across rebase/cherry-pick steps by file path - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState()` keys a user's manual conflict resolution (`ours`/`theirs`) by file **path** and unconditionally carries that decision forward across every subsequent `git status` poll for the same conflict *kind* (merge or rebase), without checking whether the underlying conflict content (i.e. the actual commit being applied) has changed. In a multi-commit rebase/cherry-pick where the same path conflicts against multiple, unrelated commits in sequence, the resolution the user approved for step N's conflict is silently reused for step N+1's conflict on the same path, whose content the user never reviewed. This mirrors the `PublicAllocator`/`EulerEarn` bug class: one component (`manualResolutions` map, an internal "tracking" structure keyed by identifier/path) is treated as authoritative while the other component (the real, current conflict content per step, i.e. `status.entry`) has diverged from it.

### Finding Description
`getConflictState()` builds the new `ConflictState` object and stamps it with whichever `manualResolutions` map already exists in the previous state: [1](#0-0) 

`updateConflictState()` then decides whether to keep this same map based only on whether the conflict *kind* transitioned between `merge`/`rebase`/`null` — it never compares `currentTip`, `baseBranchTip`, or the identity of the commit currently being applied: [2](#0-1) 

This is exercised and confirmed by the existing unit test, which asserts that a manual resolution recorded while `currentTip: 'old-sha'` is preserved verbatim after the rebase progresses to `currentTip: 'first-sha'` (i.e., a different commit/step in the rebase): [3](#0-2) 

At apply time, `stageManualConflictResolution()` looks up the stored choice for the path and stages whichever side (`us`/`them`) the **current** `git status` entry reports for that resolution, without checking that the resolution was ever shown to the user for *this* conflict's content: [4](#0-3) 

The only existing guard against staleness only covers text conflicts with markers (`conflictMarkerCount === 0` means the user hand-edited the file), and explicitly does nothing for `ours`/`theirs` style resolutions that never involve markers (e.g. binary files, or files the user chose not to open): [5](#0-4) 

`getResolvedFiles`/`getConflictedFiles` (used to decide whether a step can be continued) likewise only check presence of a resolution for the path in the map, not whether it corresponds to the currently displayed conflict content: [6](#0-5) 

**Attacker path:** a repository controlled/crafted by an attacker (a branch the victim rebases onto, cherry-picks from, or merges) can be constructed so the *same file path* conflicts against several sequential commits, each with different — and in the final step, malicious — content. If the victim resolves the first conflict with "theirs" (accepting the attacker's content, which is a normal, expected action during a rebase against an untrusted branch) and continues the rebase, Desktop reuses that same "theirs" decision for the next step's conflict on that path without ever showing the victim the new conflicting content. The victim's continue-rebase action silently commits attacker-supplied content they never saw or approved for that step.

### Impact Explanation
This allows silent corruption of what the user ultimately commits: content the user never reviewed for a specific conflict gets staged and committed as part of a rebase/cherry-pick continuation, because the "source of truth" for the resolution decision (the stale `manualResolutions` map) has diverged from the real, current conflict content being applied at that step — the same class of defect as the `PublicAllocator`/`EulerEarn` share-tracking mismatch. Impact is medium because it affects commit integrity/provenance rather than direct code execution, but it can inject attacker-chosen file content into the user's repository/history without their knowledge.

### Likelihood Explanation
Medium likelihood: it requires the victim to be rebasing/cherry-picking onto an attacker-influenced branch that intentionally reconflicts the same path across multiple commits — a realistic and unremarkable git workflow (rebasing a feature branch onto a hostile upstream, or applying a series of malicious patches), not an "unnatural" or privileged step. No local access, credentials, or social engineering beyond normal collaboration is required.

### Recommendation
Invalidate or re-validate `manualResolutions` per conflict *step*, not just per conflict *kind*. Concretely:
- Key resolutions by `(path, currentTip/step-identifying value)` instead of `path` alone, or
- Clear `manualResolutions` whenever `currentTip` (rebase) / the commit being applied (cherry-pick) changes between polls even if the conflict kind is unchanged, and
- In `stageManualConflictResolution`, verify that the specific conflict entry the resolution applies to is unchanged (e.g. compare blob OIDs of "ours"/"theirs" sides) since the resolution was recorded, not merely that a resolution exists for the path.

### Proof of Concept
1. Attacker prepares a branch with three commits, `A`, `B`, `C`, each of which modifies the same file `shared.txt` at the same lines, guaranteed to conflict against the victim's branch tip.
2. Victim rebases their branch onto the attacker's branch (`git rebase attacker-branch` via Desktop).
3. Desktop shows conflict on `shared.txt` for commit `A`; victim reviews and picks "Use their version" — `manualResolutions.set('shared.txt', theirs)` is recorded in `IChangesState.conflictState`.
4. Victim clicks "Continue rebase". `updateConflictState()` runs again for commit `B`'s conflict; because the conflict kind is still `rebase`, the previous `manualResolutions` map (with `shared.txt -> theirs`) is preserved verbatim (per `update-conflict-state-test.ts:233-269`), even though `currentTip` has moved to commit `B` and `shared.txt`'s conflicting content is now entirely different (and could be attacker-crafted malicious content).
5. `stageManualConflictResolution` stages "their" side of the *new*, unreviewed conflict for `shared.txt`, and the rebase continues to completion, committing content for `shared.txt` at commit `B` that the victim never saw or approved.

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

/** Filter working directory changes for resolved files  */
export function getResolvedFiles(
  status: WorkingDirectoryStatus,
  manualResolutions: Map<string, ManualConflictResolution>
) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&
      !hasUnresolvedConflicts(f.status, manualResolutions.get(f.path))
  )
}

/** Filter working directory changes for conflicted files  */
export function getConflictedFiles(
  status: WorkingDirectoryStatus,
  manualResolutions: Map<string, ManualConflictResolution>
) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&
      hasUnresolvedConflicts(f.status, manualResolutions.get(f.path))
  )
}
