### Title
Trust granted via `addSafeDirectory` is permanent and path-bound, with no revocation path — ([File: app/src/lib/git/config.ts])

### Summary
The Sherlock report's broken invariant is: a privileged exception, once granted to unblock a legitimately-untrusted resource, can never be revoked even after the risk context changes — because the codebase provides a "grant" primitive but no corresponding "revoke" primitive. The closest verified analog in GitHub Desktop is the `safe.directory` trust mechanism used to bypass Git's ownership-mismatch protection.

### Finding Description
When Desktop detects a repository whose directory is "unsafe" (owned by a different user than the current process), it offers the user a one-time "Trust Repository" action. This calls `addSafeDirectory()`, which permanently appends the path to the **global** `safe.directory` git config: [1](#0-0) 

This function is invoked from both the "Add Existing Repository" dialog and the "Missing Repository" recovery view: [2](#0-1) [3](#0-2) 

Grepping the entire codebase for any counterpart function (`removeSafeDirectory`, an "untrust" action, or any code that strips an entry from `safe.directory`) returns no matches — only `addSafeDirectory` / `addGlobalConfigValueIfMissing` exist. There is no UI, menu item, or preference to revoke a previously granted trust exception.

Critically, `safe.directory` is a **path-based** allowlist, not an identity/ownership-based one: Git's ownership check (`GIT_TEST_ASSUME_DIFFERENT_OWNER` / directory-owner comparison) is what the exception exists to bypass, as confirmed in the unit test: [4](#0-3) 

Once a path is trusted, Desktop and the underlying Git binary will never re-warn about that path, regardless of whether the directory contents or ownership subsequently change (e.g. the folder is deleted and recreated by a different, malicious actor — a common scenario on shared build machines, temp directories, CI runners, or reused clone-again paths via `MissingRepository.cloneAgain`, which reuses the exact same `repository.path`): [5](#0-4) 

This is structurally identical to the Hats Protocol bug: a bit is set once ("trust this path"/"eligibility disabled") with no mechanism to clear it when the underlying relationship (ownership, linkage) that justified the exception no longer holds.

### Impact Explanation
If an attacker gains control of a path previously marked as safe (e.g. a shared/multi-tenant machine, a network share, a CI workspace reused across jobs, or a directory that a user previously trusted and later "Removed" from Desktop without deleting on disk), Git will silently honor that trust exception forever. Since the entire purpose of the ownership check being bypassed is to prevent execution of repository-controlled configuration/hooks from a directory the current user doesn't own, a stale trust entry allows an attacker who later controls that path to have their repository content (e.g. `core.fsmonitor`, hooks, includeIf-triggered config) trusted and potentially executed without any Desktop warning — i.e., a permanent, non-revocable elevation of trust, exactly analogous to the tophat's un-revocable eligibility.

### Likelihood Explanation
Moderate/Low-to-moderate: it requires a scenario where a previously-trusted path is later repopulated by a different, malicious owner (shared machines, reused CI/build directories, network shares, or a user removing-then-recreating a repo at the same path). It does not require local/physical access by the attacker at the moment of exploitation — only that the path be reused later, which is a realistic operational pattern (CI runners, shared workstations, `cloneAgain` reusing the exact same path). No code in the repo re-validates ownership after the initial trust grant, nor provides a way for the user to prune stale entries.

### Recommendation
Provide a `removeSafeDirectory()` counterpart and expose it in Desktop's UI (e.g., in Preferences or repository settings) so users can revoke previously granted trust exceptions. Additionally, consider re-validating current directory ownership/content fingerprint at the time of use rather than relying solely on a permanent path-based allowlist, and automatically pruning `safe.directory` entries when a repository is removed from Desktop via `removeRepository`.

### Proof of Concept
1. Add and trust a repository at path `P` owned by user A (`addSafeDirectory(P)` is called once via `onTrustDirectory`) — verified in `add-existing-repository.tsx`/`missing-repository.tsx`.
2. Remove the repository from Desktop's list (path `P` is not deleted from disk, and no code path clears `safe.directory`).
3. On a shared machine/CI runner, path `P` is deleted and recreated by a different (malicious) owner, containing attacker-controlled git config/hooks.
4. User re-adds/re-opens `P` in Desktop (e.g., via "Clone Again" reusing the same path in `missing-repository.tsx`, or manually via "Add Existing Repository").
5. `getRepositoryType(P)` never reports `unsafe` because `safe.directory` still contains `P` — no warning is shown, and Git operations proceed against attacker-controlled repository content as if fully trusted.

Note: I was not able to execute this end-to-end in a live environment; this PoC is derived from static code evidence (absence of any revoke function, and the path-based nature of `safe.directory`, both confirmed above). If a background Devin session is available, it could set up the described shared-path scenario to empirically confirm the exploitation.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```

```typescript
    if (unsafePath) {
      await addSafeDirectory(unsafePath)

      if (type.kind !== 'unsafe') {
```

```typescript
  private cloneAgain = async () => {
    const gitHubRepository = this.props.repository.gitHubRepository
    if (!gitHubRepository) {
      return
    }

    const cloneURL = gitHubRepository.cloneURL
    if (!cloneURL) {
      return
    }

    try {
      await this.props.dispatcher.cloneAgain(
        cloneURL,
        this.props.repository.path
      )
    } catch (error) {
      this.props.dispatcher.postError(error)
    }
  }
```
