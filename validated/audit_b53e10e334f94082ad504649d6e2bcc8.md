### Title
Cached FROST preprocess reused across distinct signing sessions enables secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` persists a single FROST preprocess seed in the database keyed only by a `context` value (e.g., `(b"DkgConfirmer", attempt)`). Every call to `preprocess`, `share`, and `complete` within the same attempt regenerates *the same* FROST nonces and commitments from that cached seed via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `Commitments::new(ChaCha20Rng::from_seed(seed), ...)`. Because `share()` and `complete()` each invoke `share_internal`, and `share()` can be driven by externally supplied preprocess bytes, a counterparty can cause the node to emit multiple signature shares computed over the same nonces but under different binding factors and challenges, allowing algebraic recovery of the node's MuSig secret share — i.e., the validator's Ristretto private key.

### Finding Description
In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148), the code does:

- `if CachedPreprocesses::get(self.txn, &self.context).is_none() { ...generate fresh seed via OsRng, encrypt, store... }`
- then unconditionally loads the cached seed and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`.

`from_cache` calls `seeded_preprocess`, which seeds `ChaCha20Rng` with the cached 32-byte seed and deterministically regenerates the same `nonces` and `commitments` (crypto/frost/src/sign.rs:121-144). The FROST spec file explicitly warns: "Reusing preprocesses would enable a third-party to recover your private key share... you MUST not reuse preprocesses" (spec/cryptography/FROST.md:51-54), and `SignMachine::from_cache` documents "the preprocess must be deleted so it's never reused" (crypto/frost/src/sign.rs:217-220). `CachedPreprocesses::set/get` never deletes the entry, so the seed persists for the whole attempt.

Two distinct reachable paths reuse the nonce:

1. `DkgConfirmer::share()` and `DkgConfirmer::complete()` both call `share_internal`, which calls `preprocess_internal` (lines 156, 288-327). `complete` re-signs the message with whatever `preprocesses` map the caller passes — there is no check that it equals the map used for `share`.
2. `share()` itself takes `preprocesses: HashMap<Participant, Vec<u8>>` deserialized from counterparty-supplied bytes via `read_preprocess` (line 165). Each distinct set of other-party preprocess bytes produces a distinct `preprocesses` challenge and distinct per-participant binding factors `rho` (crypto/frost/src/sign.rs:325-371), while the local nonces `d, b` stay identical.

The signature share has the form `z = d + rho_i * b + lambda_i * s * c`, where `d, b` are fixed by the cached seed, `rho_i` and `c` are public functions of the attacker-influenced preprocess set and message, and `s` is the secret share. Each call yields one linear equation; with the nonces fixed, two equations suffice to eliminate `s` (or three to solve `d`, `b`, `s` directly), after which additional shares pin down `s` — the validator's MuSig key share, which `musig(...)` derives directly from `self.key` (line 118-121).

This is the direct analog of CVE-2019-11748's class: a credential granted for one context (a one-time FROST preprocess) is persisted and silently honored in subsequent, different contexts (different signing sets/messages), where reuse is catastrophic.

### Impact Explanation
Recovery of `s` is recovery of the validator's private key material backing its MuSig threshold identity. Within `DkgConfirmer`, that key signs `set_keys_message` confirmations that install validator-set key pairs on the Substrate side; compromise of a validator's key share contributes to threshold compromise of the set key and lets the attacker impersonate that validator in the Tributary signing protocol. The leaked material is `self.key` itself (the encryption key in `preprocess_internal` is derived as `Blake2s256("Cached Preprocess Encryption Key" || context || key)`, confirming `key` is the long-lived secret). This is key-share recovery — the strongest acceptance criterion — reachable purely from untrusted `read_preprocess` bytes.

### Likelihood Explanation
Reachability requires the attacker to be a participant whose preprocess bytes are fed to `share()`/`complete()`, and to get `share()` invoked more than once per attempt (e.g., an initially rejected/retried set, or differing preprocess maps between the `share` and `complete` calls, or triggering multiple `share` invocations with distinct participant subsets). `threshold_i_map_to_keys_and_musig_i_map` sorts and remaps whatever map is provided, so an attacker controls which participants appear and can vary the serialized preprocess contents of their own slot freely. No collusion threshold or protocol break is needed — one malicious or even malfunctioning counterparty emitting inconsistent preprocess sets suffices. Medium-high likelihood consistent with a Medium/High rating.

### Recommendation
Delete the `CachedPreprocesses` entry before first use rather than persisting it for the whole context: the cache exists to survive a crash between generating and publishing the preprocess, not to survive across sign rounds. Concretely:

- In `preprocess_internal`, after loading the cached seed, call a `CachedPreprocesses::remove(self.txn, &self.context)` so that a subsequent `share_internal`/`complete` cannot re-derive the nonces; carry the already-built `AlgorithmSignMachine`/`preprocess` forward from `preprocess()` to `share()` instead of rebuilding it.
- Alternatively, make the cache key unique per signing session (e.g., include a hash of the committed preprocess set and message), so any change in inputs yields a different seed — and add an assertion that `share_internal` is only executed once per context.

### Proof of Concept
Conceptual reproduction against the in-scope code paths:

1. Attacker (a validator in the set) participates in `DkgConfirmer` for `attempt = k`. The victim node calls `preprocess()`, storing seed `S` under context `("DkgConfirmer", k)` and emitting commitments `(D, E)`.
2. Attacker submits preprocess set `P1` → victim `share()` computes `z1 = d + rho1*b + lambda*s*c1` using `from_cache(S)`.
3. Attacker submits a second, distinct preprocess set `P2` (e.g., different bytes in its own `Commitments`, or a different participant subset) → victim `share()`/`complete()` again runs `from_cache(S)`, producing `z2 = d + rho2*b + lambda*s*c2` over the same `d, b`.
4. With `rho1, rho2, c1, c2, lambda` all public and `D = dG`, `E = bG` known, the attacker solves the linear system for `s` (additional shares make the system overdetermined and robust).
5. Verify: `s * G` equals the victim's MuSig verification share / validator public key obtained from `spec.validators()`.
