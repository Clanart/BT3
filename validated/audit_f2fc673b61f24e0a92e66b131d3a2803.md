### Title

Multiple FROST nonces reuse the same per-participant binding factor - ([File: crypto/frost/src/nonce.rs](crypto/frost/src/nonce.rs))

### Summary

`BindingFactor::calculate_binding_factors` is intended to derive an independent binding factor for every logical nonce in a signing session. Instead, each element of the returned vector hashes the same cloned transcript challenge, so every nonce index receives the identical `rho`. For multi-nonce algorithms, this weakens the binding between each submitted `(D, E)` commitment pair and its distinct nonce position.

### Finding Description

`Algorithm::nonces` explicitly supports multiple nonces, and the FROST specification notes that each additional nonce should have a per-participant binding factor. In `crypto/frost/src/nonce.rs`, the factor vector is generated as:

```rust
(0 .. binding.commitments.nonces.len())
  .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
  .collect()
```

No nonce index or transcript state is incorporated inside the loop. Consequently:

```text
rho[l][0] == rho[l][1] == ... == rho[l][n]
```

Those factors are then used to transform each private nonce as `d_n + rho_n * e_n` in `AlgorithmSignMachine::sign`, and to transform the public commitments in `BindingFactor::bound` / `BindingFactor::nonces`. A participant-controlled preprocess can therefore supply multiple commitment pairs knowing that all nonce positions will be bound by the same scalar.

This is analogous to the referenced “extra state remains active after exit” issue: the public signing API appears to isolate each nonce commitment position, but the implementation silently reuses the same binding factor across all positions. The result is not the intended independent multi-nonce FROST construction.

### Impact Explanation

The strongest confirmed impact is an incorrect verifier/signing formula for any `Algorithm` implementation requesting more than one nonce. Multi-nonce FROST relies on independent `rho` values to prevent an adversarial signer from correlating the `e` components across nonce positions. Reusing one `rho` creates a deterministic algebraic relation between every nonce’s bound commitment:

```text
R_i,l = D_i,l + rho_l * E_i,l
R_j,l = D_j,l + rho_l * E_j,l
```

A participant can choose `E_i,l` and `E_j,l` to create linear relations between `R_i,l` and `R_j,l` that would be computationally infeasible if `rho_i,l` and `rho_j,l` were independent. Algorithms using multiple nonces to represent distinct proof components or generator commitments can therefore receive nonce sums with unintended cross-component relations.

Whether this becomes a universally exploitable signature forgery depends on the multi-nonce algorithm using the primitive. The only production in-scope algorithm inspected, `Schnorrkel`, delegates to the ordinary single-generator Schnorr nonce list, while the repository’s multi-nonce algorithm is test code. Thus, this is a real formula violation in the reusable FROST implementation, but a concrete production signature forgery could not be established from the inspected call sites.

### Likelihood Explanation

The defect is deterministic and is reached whenever `Algorithm::nonces()` returns more than one nonce. Every preprocess accepted through `AlgorithmSignMachine::read_preprocess` supplies attacker-controlled point bytes for those nonce positions, and `calculate_binding_factors` deterministically assigns the same `rho` to each.

Likelihood of cryptographic exploitation is lower for the presently inspected production algorithm because it requests only one nonce. It is higher for downstream or future algorithms relying on the advertised multi-nonce interface.

### Recommendation

Bind the nonce index into every `rho` derivation. For example, clone the participant-specific transcript, append a nonce index message, and derive the challenge from that distinct transcript state:

```rust
binding.binding_factors = Some(
  (0 .. binding.commitments.nonces.len())
    .map(|n| {
      let mut transcript = transcript.clone();
      transcript.append_message(b"participant", C::F::from(u64::from(u16::from(*l))).to_repr());
      transcript.append_message(
        b"nonce",
        C::F::from(u64::try_from(n).unwrap()).to_repr(),
      );
      C::hash_binding_factor(transcript.challenge(b"rho").as_ref())
    })
    .collect(),
);
```

The transcript’s existing domain separation should be preserved. A regression test should instantiate the existing multi-nonce algorithm and assert that `rho[participant][0] != rho[participant][1]`, while also checking that malicious correlated `(D, E)` preprocesses cannot force unintended relations between the resulting nonce sums.

### Proof of Concept

The defect can be demonstrated directly from the implementation path:

1. `Algorithm::nonces` returns `Vec<Vec<C::G>>`, explicitly allowing multiple nonce positions.
2. `Commitments::read` reads one `(D, E)` pair for each nonce/generator position from public preprocess bytes.
3. `AlgorithmSignMachine::sign` inserts each participant’s preprocess into `BindingFactor`.
4. `BindingFactor::calculate_binding_factors` iterates over each nonce but evaluates `transcript.challenge(b"rho")` on an unchanged cloned transcript.
5. `AlgorithmSignMachine::sign` applies `binding_factors[n]` to the private nonce `e_n`.
6. `BindingFactor::bound` and `BindingFactor::nonces` apply the same repeated scalar to the corresponding public commitments.

The decisive code is:

```rust
binding.binding_factors = Some(
  (0 .. binding.commitments.nonces.len())
    .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
    .collect(),
);
```

Since the iterator item is ignored and the transcript is not advanced or indexed, every generated element is the same scalar. This contradicts the intended per-nonce binding and removes the separation between distinct nonce positions. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
