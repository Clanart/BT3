**VWAPOracle spread pricing feeds `IIntentPriceOracle.spread()`, used to price same-token intents — division-then-multiplication truncation biases the reported spread** - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle.recordSpread` computes `spreadBps` via `(amountDiff * BPS_DENOMINATOR) / inputAmountNormalized` (correct multiply-before-divide order for that single term), but then immediately multiplies the *already-truncated* `spreadBps` by `inputAmountNormalized` to accumulate `weightedSpreadSum`: [1](#0-0) 
This is the same "divide, then multiply" pattern flagged in the external report: the intermediate `spreadBps` loses precision from integer division, and that loss is baked into every subsequent multiplication that produces `weightedSpreadSum`. `spread()` later divides the accumulated sum by `totalVolume` to produce a value external contracts read as the market price/discount for same-token swaps: [2](#0-1) 

### Finding Description
The mathematically correct way to accumulate a volume-weighted spread is to keep the exact numerator (`amountDiff * inputAmountNormalized`, scaled by `BPS_DENOMINATOR`) and only divide once at the very end when the caller needs a ratio. Instead, `recordSpread` divides early to get `spreadBps`, rounding toward zero, and then multiplies that rounded integer back up by `inputAmountNormalized`: [3](#0-2) 
Because `spreadBps` is an integer basis-points value truncated down at the division step, every fill contributes a slightly-understated (for positive spreads) or slightly-overstated (for negative spreads, since truncation toward zero on negative division in Solidity still discards a fraction) weighted amount to `weightedSpreadSum`. Over many small-volume, near-integer-boundary fills — exactly the "1.2 ~ 2x magnitude" scenario described in the seed report — the aggregate error compounds because each term independently loses up to `1` bps-unit of precision before being scaled by potentially large volumes.

### Impact Explanation
`spread()` is exposed as the canonical read path of `IIntentPriceOracle` and is the only oracle Hyperbridge ships for the `IntentGatewayV2` price-oracle hook (`_params.priceOracle`). Any external logic (fillers, off-chain quoting, or on-chain gates that consult `priceOracle`) that treats this value as an authoritative same-token exchange-rate signal receives a systematically biased read. However, `recordSpread` is caller-restricted to `_intentGateway` only, and nothing in the current `IntentGatewayV2` path routes escrowed funds or fee computation through `VWAPOracle.spread()` directly — it is currently a reporting/telemetry surface. I could not find, within the indexed portion of the codebase, a live on-chain code path where `spread()`'s output directly gates a fund transfer, escrow release, or fee determination inside the Solidity contracts. That link would need to exist in dapp-side or off-chain filler logic to translate this into direct fund loss.

### Likelihood Explanation
Triggering the precision-loss pattern requires no privileged access — any solver filling same-token orders through `IntentGatewayV2` (a normal, permissionless action) causes `recordSpread` to run with attacker-influenced `input`/`output` amounts, so the erroneous accumulation is trivially and repeatedly triggerable. What is *not* established locally is that any current production contract consumes `spread()` in a way that moves funds, which is required by the impact gate ("stealing or loss of funds… logic attacks"). Without that consuming path, this stays a data-integrity/precision bug in an oracle rather than a demonstrated fund-loss primitive.

### Recommendation
Refactor `recordSpread` to defer the division until `spread()` is read, mirroring the report's fix: accumulate the exact numerator `(amountDiff * inputAmountNormalized * BPS_DENOMINATOR)` (or track `Σ(amountDiff * inputAmountNormalized)` and `ΣinputAmountNormalized` separately) and only perform the single final division inside `spread()`. This eliminates the repeated truncate-then-scale error accumulation.

### Proof of Concept
Given the current code:
```solidity
int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
```
For `inputAmountNormalized = 1_500` and `amountDiff = 1` (a 1-unit positive spread), the true weighted contribution is `(1 * 10_000 * 1_500) / 1_500 = 10_000`. But the code computes `spreadBps = (1*10_000)/1500 = 6` (truncated from `6.66`), then `weightedSpread = 6 * 1500 = 9_000` — a ~10% understatement of that fill's contribution to the cumulative average, matching the class of error demonstrated for `feeAmount` in the seed report. [4](#0-3) 

**Caveat:** Given the strict impact gate requiring demonstrated fund loss/unauthorized execution and the search-tool limits reached this session, I was unable to confirm any current on-chain consumer of `VWAPOracle.spread()` that moves funds based on this value — this finding should be treated as a verified precision-loss defect with unconfirmed direct fund-loss impact, pending a fuller trace of all `priceOracle` integrations (including any not indexed here).
