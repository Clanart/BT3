### Title
Line-index-based diff selection is silently reused across working-tree content changes, causing unreviewed lines to be committed - (File: app/src/lib/stores/updates/changes-state.ts)

### Summary
GitHub Desktop tracks per-file, per-line "included in commit" state (`DiffSelection`) keyed by absolute line index, and re-associates this state to newly-fetched status/diff data by a content-independent file ID (`status.kind + path`). When the working-tree content of a file changes between the moment the user makes a partial line selection and the moment the commit patch is generated, the stale line-index selection is carried forward and applied against the *new* diff content, exactly mirroring the reported bug's root cause: state (accounting/selection) captured against one snapshot is applied unchanged after the underlying data has already moved.

### Finding Description
The reward-contract bug's core defect was: a per-account value (`balanceOf`) is mutated, and only *afterwards* is a reward snapshot computed with `_updateReward`, so the new balance is retroactively applied against a reward-per-token delta that predates the deposit — the snapshot and the balance it is checked against are for two different points in time, and nothing re-validates that the balance used for the calculation still corresponds to the state the snapshot was taken against.

The Desktop analog is the `DiffSelection` line-index model combined with how it's carried across refreshes:

- `FileChange.id` is derived purely from `status.kind + path` (and `oldPath` for renames), not from content/hash: [1](#0-0) 

- When git status is reloaded (`_loadStatus`, fired on every file-system-watcher event, background fetch, or manual refresh), `updateChangedFiles` matches the new `WorkingDirectoryFileChange` objects to the old ones purely by this content-independent `id` and reuses `existingFile.selection` verbatim via `withSelection`, regardless of whether the file's actual diff content changed underneath: [2](#0-1) 

- `updateChangesWorkingDirectoryDiff` re-fetches the diff after a refresh, but only *narrows* `selectableLines` (dropping indices that no longer exist), it does **not** clear or invalidate `divergingLines` (the specific line numbers the user selected) when the content at that line number has changed to something else: [3](#0-2) [4](#0-3) 

  The comment even acknowledges this: "Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..."

- At actual staging/commit time, `applyPatchToIndex` fetches a **fresh** diff from disk and applies the (potentially stale) `file.selection` to it by absolute line index via `formatPatch`: [5](#0-4) [6](#0-5) 

So exactly as in the reward bug — where `balanceOf`/`earned()` was computed by combining an already-mutated balance with a stale reward-per-token snapshot — here `formatPatch` combines an already-mutated (freshly reloaded) diff with a stale index-based selection that was computed against the previous diff. No invariant re-checks that "line index N in the new diff represents the same reviewed content as line index N in the old diff."

### Impact Explanation
If the on-disk content of a tracked file changes between (a) the user reviewing a diff and checking/unchecking specific lines and (b) the user clicking "Commit," the commit can silently include lines the user never reviewed/selected, or exclude lines they did select, because the selection is keyed to line position, not content. This is "silent corruption of what the user commits" — the exact class of impact called out as valid. The change can be introduced by anything that rewrites the working tree non-interactively while Desktop is open and status polling is active (e.g., a `post-checkout`/`post-merge`/clean-smudge filter defined in a fetched repository's tracked `.gitattributes`/hooks that Desktop will happily invoke as part of routine fetch/checkout/pull operations it performs automatically or on user request), i.e. content controlled by the repository the user cloned/fetched.

### Likelihood Explanation
Desktop refreshes status/diff automatically and frequently (file-watcher-driven `_loadStatus`, background fetcher, focus events), so the window in which a user has made a partial selection but not yet committed is realistically exposed to a refresh cycle. The merge logic in `updateChangedFiles` is unconditional (only `clearPartialState`, used in specific refresh paths, clears partial selections) — a background refresh triggered by an ordinary git operation (fetch/pull/checkout completing and re-running filters) does not go through `clearPartialState=true` in the common case, so the stale selection persists. This does not require local/physical access or malware — only a repository whose fetched/checked-out content can shift while Desktop is open, which is squarely within the "attacker controls a cloned/fetched repository" trust boundary from the task's valid-impact criteria.

### Recommendation
Tie `DiffSelection` state to diff content identity rather than absolute line index alone (e.g., hash the hunk/line content at selection time and re-validate on every diff reload, invalidating/clearing `divergingLines` whose underlying line content no longer matches what was originally reviewed) — mirroring the reward-contract fix of tracking internal state (`_balances`) instead of trusting an externally-mutable, potentially-stale source (`stakeTracker.balanceOf`). Concretely: in `updateChangesWorkingDirectoryDiff` / `updateChangedFiles`, when the freshly loaded diff's hunk content differs from what was captured when the selection was made, force the file's selection back to `DiffSelectionType.None` (or `All`, but never silently reuse a byte-for-byte-unverified partial selection), rather than merely pruning `selectableLines`.

### Proof of Concept
1. In Desktop, open a repository with a tracked file `foo.txt` containing multiple lines; make a modification and open the diff view.
2. Select only line 3 for inclusion in the commit (partial `DiffSelectionType.Partial`, `divergingLines = {3}`).
3. Before committing, cause the working tree content to change at the same line position without the user re-reviewing the diff — e.g., have a `post-checkout` hook or clean/smudge filter defined in the repository (attacker-controlled, delivered via clone/fetch) rewrite `foo.txt` when Desktop performs its next automatic `fetch`/status refresh (`_loadStatus`/`BackgroundFetcher`).
4. Observe: `updateChangedFiles` (app/src/lib/stores/updates/changes-state.ts:56) reuses the old `DiffSelection` (still `divergingLines={3}`) on the new `WorkingDirectoryFileChange`; `updateChangesWorkingDirectoryDiff` only prunes now-nonexistent selectable indices, not content-changed ones.
5. Click "Commit." `applyPatchToIndex` re-diffs the file from disk (now containing the attacker's rewritten line 3) and `formatPatch` includes/excludes line 3 based on the stale selection — the attacker's unreviewed content is committed as if the user had reviewed and approved it.

Note: I was unable to fully trace an existing, in-repo hook/filter execution path that Desktop invokes automatically post-fetch/checkout to conclusively verify the exact timing window end-to-end (i.e., how quickly a hook-triggered rewrite lands before the next status refresh vs. before commit); this piece relies on general git hook/filter semantics rather than a specific line of Desktop code triggering hook execution, so I recommend a Devin session with full repo/test access to confirm the precise race window and hook invocation points if a stronger PoC is required.
