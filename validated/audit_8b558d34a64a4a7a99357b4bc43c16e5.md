### Title
Bandwidth allowance keyed by `request.source` in the gate while credited by `msg.chain` (sponsored app) lets the gate silently under/over-charge — cross-chain sponsorship desyncs subscription accounting - (File: `parachain/runtimes/gargantua/src/ismp.rs`, `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` intentionally supports sponsorship: a purchase message carries its own `chain` field (the "credit chain"), which can differ from `request.source` (the chain that actually sent the purchase). Credits are written to `Allowance[msg.chain][app]` [1](#0-0) , but the gate that drains bandwidth on every subsequent request is invoked with `request.source` as the key, not the app's actual sponsored chain: `try_consume(&request.source, &request.from, bytes)` [2](#0-1) .

### Finding Description
This mirrors the reported Solana bug precisely: a single local field (`pool.amount` there, `Allowance[source][app]` here) is checked to gate an action, but the actual funds/credit can live in a different location (`shared_escrow` there, `Allowance[app_chain][app]` here) that the check never consults.

Concretely:
- Purchases credit `Allowance::<T>::mutate(&msg.chain, &key, ...)`, where `msg.chain` is attacker/buyer-controlled data from the purchase message body, independent from `request.source` [3](#0-2) .
- The gate drains from `Allowance::<T>::get(app_chain, app)` where `app_chain` is whatever `source` was passed by the caller [4](#0-3) .
- The only caller, `ProxyModule::on_accept`, always passes `&request.source` (the chain that dispatched *this specific request*), not the `app_chain` that was actually credited [2](#0-1) .

Because `Allowance` is a `StorageDoubleMap<StateMachine, AppKey, ...>` and the same `AppKey` (an EVM address, 20 bytes) can plausibly collide or simply differ across `StateMachine` values used as `source` vs `app_chain`, any app that is sponsored (bought bandwidth credited to chain B while paid from chain A, as the docs explicitly describe as the primary multi-tenant use case: "a buyer on Ethereum can credit an app on Base") will have its `Allowance[B][app]` balance sit unused while the gate keeps consuming/checking `Allowance[A][app]` for every request the app actually sends from chain A. Two concrete outcomes:
1. **Denial of bandwidth despite a valid paid subscription**: the app dispatches ISMP requests from chain A (its real deployment) but the credited entry lives under `Allowance[B]` (the `app_chain` in the purchase message); `try_consume` looks under `Allowance[A]` and finds nothing, rejecting a paying customer's legitimate messages (`GateError::NoAllowance`).
2. **Unbounded/free bandwidth for an unrelated `(source, app)` pair**: if the same `AppKey` bytes happen to already have (or later acquire) a subscription under a *different* `StateMachine`, the `try_consume` call may unintentionally interact with credits that were never purchased for that source chain — because nothing in the gate ties the consumed key back to the chain the payment was actually attributed to. Given `app_chain` in the purchase body is fully attacker-controlled at purchase time (`msg.chain`), an attacker can deliberately set `chain` in `BandwidthPurchaseMsg` to any `StateMachine`, potentially crediting bandwidth to a `(chain, app)` tuple that does not match where they will actually consume it, or where a victim app operates, corrupting that app's future gate accounting (either draining/dirtying a bucket that another legitimate sponsor intended to fund, or making the gate check the wrong bucket for messages dispatched on the sponsor's behalf).

The invariant broken: the gate's check-and-deduct key (`source` = dispatch chain) must always equal the credit key (`app_chain` = sponsorship-message chain) for the accounting to be meaningful, exactly as `pool.amount` must reflect the actual custody location in the Solana report. Nothing in `try_consume`, `is_purchase_message`, or `on_accept` enforces `msg.chain == request.source`, so sponsorship (an explicitly supported, unprivileged, user-triggered feature reachable by any buyer calling `BandwidthManager.purchase()`) structurally decouples the credited bucket from the debited bucket.

### Impact Explanation
This falls under "logic attacks" / "bandwidth accounting must move exactly once and only to the rightful beneficiary." An app that paid for a subscription can be locked out of the bridge (bandwidth denial, effectively transaction manipulation/DoS on a paying customer) while an unrelated `(chain, app)` bucket is corrupted by attacker-chosen `msg.chain` values, breaking the "atomic check-and-deduct" invariant the docs claim [5](#0-4) . It does not require a malicious relayer, prover, or admin — any buyer calling the public `purchase()` entrypoint with an arbitrary `chain` value can trigger this misattribution.

### Likelihood Explanation
High: sponsorship (`app_chain != request.source`) is a first-class, documented, and encouraged use case ("a buyer on Ethereum can credit an app on Base"), not an edge case [6](#0-5) . Any legitimate sponsorship purchase already produces the mismatch between the credited key and the consumed key described above, so the bug is triggered by ordinary intended use, not just adversarial input.

### Recommendation
Ensure the gate is always consulted with the same key that credits use. Either:
- Restrict purchases so `msg.chain == request.source` unless the caller is explicitly delegating consumption rights, and pass the effective `app_chain` (resolved consistently) into `try_consume` from `ProxyModule::on_accept`, or
- Have the router determine the correct `app_chain` to charge against (e.g., by tracking which chain the app is actually registered/deployed on) rather than defaulting to `request.source`, and reject/flag purchases whose `msg.chain` doesn't match a registered relationship for `app`.

### Proof of Concept
1. Buyer on `EVM-1` calls `BandwidthManager.purchase(app=APP, tier=1, months=1, chain="EVM-8453")`, paying full price. The dispatched `BandwidthPurchaseMsg.chain = "EVM-8453"`.
2. `pallet-bandwidth::on_accept` credits `Allowance[EVM-8453][APP]` with the purchased bytes [1](#0-0) .
3. APP is actually deployed and sends its real ISMP messages from `EVM-1` (its home chain), so every subsequent request has `request.source = EVM-1`.
4. `ProxyModule::on_accept` calls `try_consume(&EVM-1, APP, bytes)`, which reads `Allowance[EVM-1][APP]` — empty — and returns `GateError::NoAllowance`, rejecting the message despite the buyer having just paid for bandwidth [2](#0-1) , [7](#0-6) .
5. Conversely, an attacker can set `chain` to any `StateMachine` value at purchase time (fully attacker-controlled `msg.chain`) to push credits into `Allowance[chosen_chain][victim_app]`, a bucket the victim app never expected to be touched, corrupting its later `try_consume` behavior if `victim_app`'s real traffic ever originates from `chosen_chain`.

```text
## The Gate

Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.

The "no mutation on insufficient" property is load-bearing: it means a top-up race is safe — if a message arrives between when an app notices it's short and when the top-up lands, the message stays rejectable rather than half-consuming the subscription.
```

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```
