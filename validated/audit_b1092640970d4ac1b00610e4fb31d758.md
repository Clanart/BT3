### Title
`IntentGatewayV2.instance()` defaults unregistered source chains to the gateway's own address, allowing forged escrow redemption/refund via address-collision spoofing - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Fantium report's core flaw is "missing existence checks" that make administrative logic fall back to unsafe defaults when an identifier (`collectionId`) has never been configured. The same defect class exists in `IntentGatewayV2`'s cross-chain module-binding logic: when no gateway instance has been registered for a given source `stateMachineId`, `instance()` silently defaults to `address(this)` instead of rejecting the unknown chain, and `authenticate()` accepts any incoming message whose `from` field equals that default.

### Finding Description
`instance()` looks up the registered peer-gateway address for a state machine and, if none exists, returns the local contract's own address: [1](#0-0) 

`authenticate()` then treats any incoming request whose `from` field decodes to that value as coming from a "known instance": [2](#0-1) 

There is no existence check equivalent to Fantium's missing `collectionId` validation — `_instances[keccak256(stateMachineId)] == address(0)` is treated as "trust myself" rather than "this chain has no registered peer, reject." Because `PostRequest.from` is chain-controlled (set by the *source* chain's ISMP host to the dispatching contract's own address), any contract deployed at the same address as this gateway on a state machine that the `IsmpHost` already trusts/whitelists (via `updateHostParams`/`state_machines`, independent of whether `IntentGateway` has registered a `Deployment` there) can dispatch a `RedeemEscrow` or `RefundEscrow` message that authenticates successfully here, because `instance(unregisteredChain)` resolves to `address(this)` and the attacker's contract on the other chain is deployed to that exact address (deterministic CREATE2 deployment addresses are the norm in this codebase, as documented for `EvmHost`/`TestnetHost`: "CREATE2 deployments under a shared salt produce a deterministic address per host type").

`withdraw()` then blindly honors the forged `WithdrawalRequest`, transferring escrowed tokens to an attacker-chosen `beneficiary`: [3](#0-2) 

This directly violates the stated pivot: "Request, response, and timeout paths must bind chain id, module/app identity, commitment uniqueness, and one-time receipt handling."

### Impact Explanation
A successful forgery lets an attacker redeem or refund escrowed order inputs to an arbitrary beneficiary without ever having filled a real order or without any legitimate settlement message being dispatched — this is unauthorized execution and theft of escrowed bridge funds, matching the bounty's "stealing or loss of funds" / "false proof/state acceptance" / "unauthorized transaction or execution" categories.

### Likelihood Explanation
Exploitability is gated on two facts holding simultaneously: (1) the `IsmpHost` already whitelists a state machine for which `IntentGateway` has not yet registered a `Deployment` (a realistic operational sequencing gap — hosts are provisioned centrally while per-app instance registration is a separate governance action), and (2) the attacker can get code deployed at the exact same address as the victim `IntentGateway` on that chain (achievable if that state machine uses the same CREATE2 factory/salt convention documented elsewhere in this repo, or is a permissionless/attacker-controlled chain). Given the deterministic-address design pattern is explicit project convention (`EvmHost`/`TestnetHost` constructors), this is a locally-provable, non-trivial-but-realistic path, not one requiring a malicious relayer, prover, or governance actor — the attacker only needs their own deployer key on the source chain.

### Recommendation
Change `instance()`'s unregistered-chain fallback from `address(this)` to an explicit revert/zero, and require `authenticate()` to reject any request from a `stateMachineId` with no registered `Deployment`, mirroring the existence checks Fantium's report recommends adding for `collectionId`-keyed operations.

### Proof of Concept
1. Governance whitelists chain `X` on the local `EvmHost` (`updateHostParams` with `X` in `state_machines`), but no `NewDeployment` has yet been processed by `IntentGatewayV2` to register `_instances[keccak256(X)]`.
2. Attacker deploys a minimal ISMP-dispatching contract on chain `X` at the same address as the victim `IntentGatewayV2` proxy (achievable via a shared CREATE2 factory/salt, per the project's own deterministic-deployment convention).
3. Attacker's contract calls `IDispatcher(hostOnX).dispatch(...)` targeting the victim gateway, with body `bytes1(RequestKind.RedeemEscrow) || abi.encode(WithdrawalRequest{commitment: <victim's real order commitment>, tokens: <victim's escrowed tokens>, beneficiary: <attacker>})`.
4. A relayer (permissionless, no special trust) delivers this proven request; `onAccept` → `authenticate()` computes `instance(X) == address(this)` (unregistered fallback) `== module` (attacker's contract address, which equals `address(this)` by construction) → passes.
5. `withdraw()` transfers the victim's escrowed tokens to the attacker's `beneficiary`. [4](#0-3) [3](#0-2)

    /**
     * @dev Fetch the IntentGateway contract instance for a chain.
     */
    function instance(bytes calldata stateMachineId) public view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        return gateway == address(0) ? address(this) : gateway;
    }

    /**
     * @dev Checks that the request originates from a known instance of the IntentGateway.
     */
    function authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        // IntentGateway only accepts incoming assets from itself or known instances
        if (instance(request.source) != module) revert Unauthorized();
    }
