### Title
`send_raw_transaction` classifies ambiguous broadcast outcomes as failure, enabling double-spend of inputs on retry - (File: networks/bitcoin/src/rpc.rs)

### Summary
The bug class in GHSA-3j4h-h3fp-vwww is premature failure classification: an operation that is still in flight (or already succeeded) is reported as failed, so a retry performs it a second time. `Rpc::send_raw_transaction` in `networks/bitcoin/src/rpc.rs:189-208` has the same shape: it only treats Bitcoin Core error `-27` ("already in chain") as success, and surfaces every other `RpcError` — including `ConnectionError` from a timeout or a dropped connection after the node accepted the transaction — as a definitive publication failure, without ever checking whether the transaction actually reached the mempool or a block. A caller that retries the payment constructs a fresh `SignableTransaction`/`TransactionMachine` over the same `ReceivedOutput`s; nothing in `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256) prevents the same outpoints from being reused in a second transaction. If both transactions are eventually accepted, the recipient is paid twice, or if the retry pays a different destination the intended accounting diverges — a direct loss-of-funds analog of the LNbits bug.

### Finding Description
- `Rpc::send_raw_transaction` (`networks/bitcoin/src/rpc.rs:189`) calls `sendrawtransaction` and maps the HTTP-layer failure to `RpcError::ConnectionError` (`rpc.rs:121-128`) and any JSON-RPC error other than `-27` to `Err` (`rpc.rs:196-201`). There is no "unknown / maybe in-flight" outcome.
- A connection error or non-`-27` error does not imply the transaction was rejected: the node may have already accepted the transaction into its mempool (and relayed it) before the response was lost, mirroring Eclair's `Ask timed out ... after [30000 ms]` case where the payment remained in flight.
- The wallet API provides no in-flight tracking: `Scanner::scan_transaction`/`scan_block` (`networks/bitcoin/src/wallet/mod.rs:199-227`) only observe confirmed/block data and matching `script_pubkey`s; `SignableTransaction` is documented as "clone-able across attempts" (`send.rs:52`), i.e. deliberately retryable, so the natural retry path re-selects and re-spends the same `ReceivedOutput`s with a fresh FROST signing session (`send.rs:273-285`).
- `Rpc::get_transaction` (`rpc.rs:211`) and `getrawtransaction` exist and could be used to query mempool/chain status after an ambiguous error, but `send_raw_transaction` never does so, and nothing forces a caller to.

### Impact Explanation
Concrete loss of funds for the threshold wallet. When publication fails ambiguously, a retry signs and broadcasts a second transaction spending the same inputs (the library is explicitly designed to allow this). In the worst case both transactions confirm — e.g., the first was already in miners' mempools and the retry pays the same recipient again — yielding a double payment, or the retry includes different outputs/change, causing the wallet's books to diverge from what the threshold key actually authorized. This is identical in consequence to the Eclair backend issue: an in-flight spend treated as failed leads to a second spend.

### Likelihood Explanation
Reachable by an unprivileged party able to influence timing: the trigger is any transient fault (timeout, proxy/connection reset, non-`-27` RPC error such as mempool-policy rejections that race a prior acceptance) occurring while `sendrawtransaction` is processed. No malicious node, leaked key, or colluding threshold is required — only the ordinary ambiguity that a failed response does not prove the request failed. Integrators driven to retry (the common UX pattern the API invites via its cloneable `SignableTransaction`) hit this whenever a node hiccups mid-broadcast.

### Recommendation
Make publication failure unambiguous, mirroring the advisory's fix ("check the payment status after an error; when not sure, always consider a payment still in flight"):
- On `ConnectionError` or any non-definitive `RpcError` from `sendrawtransaction`, call `getrawtransaction`/`get_transaction` to check whether the txid is in the mempool or a block before returning an error; return a distinct `RpcError::Ambiguous`/`MaybePublished` variant instead of a flat error so callers cannot mistake it for a clean rejection.
- Handle Bitcoin Core's mempool-duplicate result (`txn-already-in-mempool`, currently not covered by the `-27` special case at `rpc.rs:194-199`) as success.
- Document in `send_raw_transaction` that callers must not re-sign/re-broadcast a payment for the same `ReceivedOutput`s until the ambiguous transaction is known absent from mempool and chain.

### Proof of Concept
1. Build a `SignableTransaction` over `ReceivedOutput`s found by `Scanner`, sign it via `TransactionMachine`, and broadcast with `Rpc::send_raw_transaction`.
2. Induce a lost/late response (connection reset or timeout after the node accepts the transaction into its mempool — analogous to the hold-invoice timeout PoC in the advisory).
3. `send_raw_transaction` returns `Err(RpcError::ConnectionError)` even though the tx is in the mempool/being relayed.
4. Caller retries: `SignableTransaction::new` over the same `ReceivedOutput`s succeeds, `TransactionSignMachine::sign` produces a second valid transaction spending the same outpoints.
5. The original transaction confirms (it was already accepted); the retry either confirms as a duplicate payment or forces the wallet into an inconsistent state — funds are spent beyond what a single intended payment authorized.
