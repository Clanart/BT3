## Title
Reward misattribution in `pallet_consensus_incentives::on_executed` lets a batch composer steal another relayer's consensus-update reward - ([File: modules/pallets/consensus-incentives/src/impls.rs])

## Summary
`FeeHandler::on_executed` credits the **entire** reward for every state machine advanced in a `handle_unsigned` batch to the signer recovered from `messages[0]` only, while the reward amount is computed from the aggregated `StateMachineUpdated` events produced by **all** messages in that batch. Since `handle_unsigned` is a permissionless, unsigned extrinsic that accepts an attacker-chosen `Vec<Message>`, an attacker can prepend a trivially cheap `ConsensusMessage` signed with their own key to a batch that also contains a legitimate, independently valid consensus proof (which anyone can resubmit, since `ConsensusMessage` embeds its own self-declared signer/signature and is not tied to the extrinsic's actual submitter), and collect the reward that should have gone to whichever relayer actually produced/signed that other proof.

## Finding Description
`process_message`/`calculate_reward` compute a reward per `(state_machine_id, latest_height)` pair based on the watermark `LastRewardedHeight`, which correctly prevents double-payment for the *same* height span: [1](#0-0) 

However, `on_executed` determines **who** gets paid for **all** of these rewards from only the first message in the batch: [2](#0-1) 

It then aggregates `StateMachineUpdated` events across the *entire* batch (which may correspond to multiple independent `ConsensusMessage`s, each with its own embedded `signer`), and pays every one of those aggregated rewards to the single relayer recovered from `messages[0]`: [3](#0-2) 

The `signer` field is not a cryptographic proof of "who submitted this transaction" — it is an arbitrary field embedded inside each `ConsensusMessage` by whoever constructed it, and the extrinsic itself is unsigned/permissionless: [4](#0-3) 

Because the consensus proof and the reward-claim signature are decoupled from tx authorship, anyone observing a broadcast/mempool `ConsensusMessage` (or any already-produced valid proof for a high-cost state machine) can:
1. Craft their own trivial `ConsensusMessage` for any cheap/low-cost state machine (or reuse a stale one that yields events but whose signature they control), placing it at index 0 of the batch.
2. Append the legitimate high-value `ConsensusMessage` (whose signer is another relayer) as a later element of the same `Vec<Message>` passed to `handle_unsigned`.
3. Both messages are independently verified and both advance state normally (consensus verification does not depend on batch position), producing `StateMachineUpdated` events for both state machines.
4. `on_executed` sums the rewards for *every* state machine advanced in the batch and pays the whole amount to the signer of `messages[0]` — the attacker — not to the relayer whose proof actually advanced the high-value chain.

The watermark (`LastRewardedHeight`) protects against re-paying the *same* height span twice, but it does nothing to ensure the reward for a given state-machine's advance goes to the party whose message produced it. The check `maybe_relayer_account = messages.get(0)...` is exactly the kind of "parameter recomputed at check time instead of bound to the actual actor" pattern from the H-9 report: the guard exists (pay the signer) but the value it operates on (which signer) can be manipulated by the caller composing the batch, decoupling payment from the actual contribution.

## Impact Explanation
This is a direct theft-of-funds primitive from the `TreasuryAccount`: an unprivileged actor can redirect relayer rewards (both the `Currency::transfer` payout and the `ReputationAsset` mint) that rightfully belong to another relayer to themselves, simply by controlling how they batch messages in a call to `handle_unsigned`. Given consensus incentive rewards can be substantial for high-`cost_per_block` state machines and large height spans, this allows systematic siphoning of treasury funds intended to compensate honest relayers, and it directly violates the "reward must go to the rightful beneficiary" bar in the impact gate.

## Likelihood Explanation
`handle_unsigned` is callable by anyone (no origin check, `RuntimeOrigin::none()`), and constructing a batch containing more than one `ConsensusMessage` requires no special privilege or cooperation from the victim relayer — the attacker only needs to observe or reconstruct one already-valid consensus proof (these are broadcast data, not secrets) and prepend their own cheap message. No malicious relayer/prover collusion is required; the attacker acts entirely alone using otherwise-honest, independently-valid proofs.

## Recommendation
Attribute each state machine's reward to the signer embedded in the specific `ConsensusMessage` that produced its `StateMachineUpdated` event, rather than defaulting to `messages[0]`'s signer for the whole batch. Concretely, iterate messages, recover the signer per `ConsensusMessage`, and only credit that signer for the specific `state_machine_id`(s) whose advance is attributable to that message (e.g., by threading the source message index/consensus_state_id through to the event, or by processing consensus messages and their resulting events one-at-a-time instead of via two separately-indexed collections).

## Proof of Concept
1. Configure `StateMachinesCostPerBlock` with a high `cost_per_block` for state machine `B` and a low/any value for `A`.
2. Relayer R legitimately produces a valid `ConsensusMessage` `m_B` (embedding R's `signer`) advancing `B` from height `h` to `h+N` (large `N`, large reward).
3. Attacker observes `m_B` (public/broadcast data) and crafts their own trivial `ConsensusMessage` `m_A` for state machine `A` (embedding their own `signer`), which is cheap to construct and valid.
4. Attacker submits `pallet_ismp::handle_unsigned(RuntimeOrigin::none(), vec![m_A, m_B])`.
5. Both messages verify and produce `StateMachineUpdated` events for `A` and `B`. `on_executed` computes `maybe_relayer_account` from `messages.get(0)` (attacker), then loops over the aggregated `highest_per_state_machine` map (containing both `A` and `B`) and pays the **attacker** the reward for both `A`'s and `B`'s advance — including the large reward that should have gone to relayer R for `m_B`.
6. `LastRewardedHeight` is updated as if correctly paid, so R can never claim this reward again (the watermark has already advanced), permanently diverting the funds.

This can be validated deterministically by extending the existing test `test_incentivize_relayer`/`reward_covers_only_unpaid_heights_after_rollback` in `modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs` to submit a batch of two `MessageWithWeight`/`IsmpEvent::StateMachineUpdated` pairs with different embedded signers, and asserting that the account credited in `Balances::balance` matches `messages[0]`'s signer for both state machines' rewards. [5](#0-4)

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
