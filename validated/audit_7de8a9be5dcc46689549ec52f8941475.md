### Title
Untrusted `ReceivedOutput` prevout data is committed into the Taproot sighash without verifying value/outpoint authenticity, yielding signatures for transactions that cannot confirm - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

Analogous to the JUSD liquidation that reverts when the repayment leg to an untrusted counterparty fails, `SignableTransaction::multisig` / `TransactionSignMachine::sign` produce a threshold-signed Bitcoin transaction whose validity depends entirely on untrusted `ReceivedOutput` fields. Only the `script_pubkey` is authenticated; the `value` and `outpoint` supplied via `ReceivedOutput::read` are committed into the BIP-341 sighash via `Prevouts::All` and are never checked against the chain.

### Finding Description

`SignableTransaction::new` takes `Vec<ReceivedOutput>` and stores `input.output` (a `TxOut` with an attacker-controlled `value`) as `prevouts` and `input.outpoint` as the `TxIn` previous output [1](#0-0) [2](#0-1) . `ReceivedOutput::read` deserializes `offset`, `TxOut`, and `OutPoint` from raw bytes with no consistency check that the `OutPoint` exists or that the `TxOut` matches the referenced UTXO [3](#0-2) .

When the multisig machine is built, the only validation is that `p2tr_script_buf(offset.group_key())` equals `prevouts[i].script_pubkey`; the value and outpoint are unauthenticated [4](#0-3) . `sign` then computes `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), TapSighashType::Default)`, committing each signature to the fabricated amounts and outpoints [5](#0-4) .

Because Taproot key-spend signatures commit to the spent outputs' amounts, any `ReceivedOutput` whose `TxOut.value` or `OutPoint` does not exactly match the real UTXO produces a fully-valid-looking signed transaction that every Bitcoin node rejects — the equivalent of the JUSD liquidation transaction that cannot succeed. Unlike the source bug, where one uncooperative recipient (a blacklisted liquidated user) poisons the entire batch operation, here one malformed input among many poisons every input's signature in the transaction.

### Impact Explanation

An unprivileged party who can feed serialized `ReceivedOutput` bytes into a signing session (the rules explicitly designate `ReceivedOutput::read` an untrusted-bytes sink) can cause the threshold group to expend a full FROST signing round on a transaction that is guaranteed unbroadcastable: consensus requires the sighash-committed amounts to equal the actual UTXO values, and the outpoint must reference a live UTXO. Repeated submissions burn preprocesses/signing bandwidth and can stall withdrawals, since the signed artifact must be detected as invalid and discarded after `complete` returns [6](#0-5) . Severity: Medium (operational DoS of the signing pipeline; no direct fund theft since the script_pubkey check prevents redirection).

### Likelihood Explanation

Triggering requires the caller's pipeline to accept `ReceivedOutput`s that did not come from `Scanner::scan_transaction` — e.g., peer-supplied or DB-tampered encodings — a documented untrusted input surface. Constructing the malicious bytes is trivial (`write`/`serialize` round-trip with edited fields) [7](#0-6) . However, the honest scanner path already binds outputs to on-chain data [8](#0-7) , so exploitation depends on an integrator or peer path accepting externally serialized outputs, which lowers likelihood.

### Recommendation

Authenticate each `ReceivedOutput` before constructing the sighash. Options mirroring the JUSD fix's "don't let one untrusted leg sink the transaction" spirit:

1. In `SignableTransaction::multisig` (or `new`), verify each input against the node: fetch the outpoint via RPC and require the returned `TxOut` to equal `input.output` (script and value).
2. Alternatively, use `TapSighashType::All` semantics honestly by only trusting `ReceivedOutput`s produced internally by `Scanner::scan_transaction`/`scan_block`, and refuse to sign `ReceivedOutput`s deserialized through `read` without re-validation.
3. Make `ReceivedOutput::read` fallible-checkable by carrying a commitment to the confirmed UTXO, or add a `verify_against(&self, rpc)` helper so callers validate before spending a signing round.
