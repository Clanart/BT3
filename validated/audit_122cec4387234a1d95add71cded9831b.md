## Analysis

The core defect is real, but the "auto-checkout chains into disclosure" framing in the question is not quite accurate — the two primitives are actually independent, not sequentially dependent.

### The boundary bug in `resolveWithin`

`_resolveWithin` computes the real, symlink-resolved paths of both the root and the candidate, then does:

```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

This is a classic prefix-boundary bug: `startsWith` has no trailing path-separator check, so a sibling directory whose name merely begins with the same string as the repository's directory name (e.g. `repo` vs `repo-2`, `repo-private`, `repo-backup`) will pass the check even though it is not actually nested inside the root. This bug is present in all three exported wrappers (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) since they all funnel through `_resolveWithin`.

### The sink: `openRepositoryFromUrl`

The `open-repository-from-url` deep-link action (reachable from the `x-github-client://openRepo/...` protocol, parsed by `parseAppURL`) carries an attacker-controlled `filepath` query parameter that is only checked for being non-absolute — no traversal (`../`) sanitization is performed [2](#0-1) . It is then passed straight into `resolveWithin(repository.path, filepath)`, and if the check passes, the resolved path is handed to `shell.showItemInFolder`:

```ts
if (filepath !== null) {
  if (isAbsolute(filepath)) { ... return }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } ...
}
``` [3](#0-2) 

So a filepath like `../repo-private/secret.txt`, combined with a local repo cloned at `.../repo` sitting next to `.../repo-private`, will pass the buggy `startsWith` check (`".../repo-private/secret.txt".startsWith(".../repo")` is `true`) and cause `shell.showItemInFolder` to reveal the file in the Finder/Explorer window — outside the intended repository root.

### Why the "PR head branch takeover" part of the chain doesn't actually contribute

`openPullRequestFromUrl` (invoked when the deep link includes a `pr` parameter) only affects which branch gets checked out inside the *matched or cloned* repository; it does not change `repository.path`, which is the root passed to `resolveWithin` [4](#0-3) . The subsequent `filepath` handling in `openRepositoryFromUrl` runs unconditionally regardless of whether `pr`, `branch`, or neither was supplied [5](#0-4) . In other words, an attacker does not need to control the PR's head branch or get it auto-checked-out at all — a plain `x-github-client://openRepo/<url>?filepath=../sibling-dir/file` deep link (no `pr` parameter needed) triggers the same `shell.showItemInFolder` call on the escaped path. The "attacker controls the head branch" primitive is a red herring for this particular sink; it's a separate (and already-intended) feature of "Open in Desktop"-style PR links, not a chained escalation step.

### Practical caveat on exploitability

The attack requires that a directory whose name is a **string-prefix superset** of the target repository's local folder name already exists on disk next to it (e.g., `repo` and `repo-1`, which is a realistic layout since GitHub Desktop itself appends numeric suffixes like `-1`, `-2` when cloning repos with colliding folder names) or that the attacker knows/guesses such a name. The disclosure is also local-only: `shell.showItemInFolder` opens a Finder/Explorer window on the victim's own machine highlighting the file — it does not exfiltrate content to the attacker directly. This limits impact to local, revealed-to-the-victim file/path disclosure (existence and location of a file outside the intended repo), not a remote data exfiltration primitive.

### Title
Path-boundary bypass in `resolveWithin` allows deep-link `filepath` parameter to escape the repository root and reveal files from sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin`'s containment check uses `realResolved.startsWith(realRoot)` without verifying a trailing path separator, so any sibling directory whose name is a superstring-prefix of the repository directory name is treated as "inside" the repo. This is reachable via the attacker-controlled `filepath` parameter of the `x-github-client://openRepo/...` deep link, which is passed to `shell.showItemInFolder` after the (broken) containment check in `openRepositoryFromUrl`.

### Finding Description
`_resolveWithin` in `app/src/lib/path.ts` resolves the real (symlink-free) paths of the root and the joined candidate path and performs a plain string `startsWith` comparison instead of verifying the resolved path is `root` itself or `root + path.sep + ...`. `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` uses this function to validate a `filepath` deep-link parameter (sourced from `parseAppURL`, which does no traversal sanitization) before calling `shell.showItemInFolder(resolved)`.

### Impact Explanation
An attacker who can get a victim to click a crafted `x-github-client://openRepo/<repo-url>?filepath=../sibling-dir-name-sharing-prefix/target-file` link can cause Desktop to open the OS file manager pointed at a file outside the intended repository, in any adjacent directory whose name begins with the exact repository directory name string (a layout GitHub Desktop itself can produce, e.g. `repo`, `repo-1`, `repo-2` for duplicate clone names). This discloses the existence/location of files in a sibling folder, which may itself be another (possibly private) local repository.

### Likelihood Explanation
Requires the victim to click an attacker-supplied deep link and to have (or be induced to create, via the same or a prior "Clone in Desktop" link) a directory layout where a sibling folder's name is a prefix-superstring of the target repo's folder name — a plausible but not universal local disk state.

### Recommendation
Fix the boundary check in `_resolveWithin` to require an exact match or a match followed by the platform path separator, e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`, in `app/src/lib/path.ts`.

### Proof of Concept
1. Create two local folders: `~/Documents/repo` (a git repo cloned/opened by Desktop) and `~/Documents/repo-secret` containing `passwords.txt`.
2. Click (or navigate the app to) `x-github-client://openRepo/<url-of-repo>?filepath=..%2Frepo-secret%2Fpasswords.txt`.
3. Observe `openRepositoryFromUrl` → `resolveWithin(".../repo", "../repo-secret/passwords.txt")` returns a non-null resolved path because `".../repo-secret/passwords.txt".startsWith(".../repo")` is `true`, and `shell.showItemInFolder` opens Explorer/Finder highlighting `passwords.txt` from the sibling `repo-secret` folder. async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
