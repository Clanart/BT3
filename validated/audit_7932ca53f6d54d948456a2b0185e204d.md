### Title
Diff-hunk expansion shifts absolute line indices used for partial-commit selection, causing silent inclusion/exclusion of unintended lines - (File: `app/src/ui/diff/text-diff-expansion.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
GitHub Desktop tracks which diff lines a user has selected for a partial commit not by content, but by an **absolute integer index** (`hunk.unifiedDiffStart + lineIndex`) stored in a `Set<number>` inside `DiffSelection` [1](#0-0) . When the "expand hunk" feature recomputes `unifiedDiffStart`/`unifiedDiffEnd` for all hunks after (or before) the one being expanded, it derives the new offsets from a locally computed `numberOfNewDiffLines` delta rather than re-deriving selection state from the new hunk contents [2](#0-1) [3](#0-2) . This is structurally the same class of bug as the Fuji `burnBatch` finding: an index/scale value (`unifiedDiffStart`) is propagated forward through a stateful transformation, and if that recomputed value doesn't exactly match the value the stored selection `Set` was built against, unrelated lines end up matching the stale indices — with no validation guard rejecting the mismatch.

### Finding Description
`patch-formatter.ts`'s `formatPatch()` (used to build the exact patch applied to the git index for a partial commit) computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` for every line and asks `file.selection.isSelected(absoluteIndex)` to decide whether to include an added/deleted line [4](#0-3) . `DiffSelection.isSelected` is a pure integer-index lookup with no knowledge of what content that index originally referred to [5](#0-4) .

`expandTextDiffHunk` (invoked when a user clicks to reveal more context in a diff, e.g. after opening a file from a fetched/cloned repository with unusual hunk boundaries) rewrites the hunk list: it merges hunks, inserts new context lines, and then re-stamps every *following* hunk's `unifiedDiffStart`/`unifiedDiffEnd` by adding `numberOfNewDiffLines` [6](#0-5) . That delta is computed from `updatedHunkLines.length - hunk.lines.length`, adjusted by `-1` only in the merge branch [7](#0-6) . The existing `DiffSelection` object attached to `WorkingDirectoryFileChange`, however, is not rebuilt against the new indices — it is carried over as-is with its `divergingLines` set of raw integers referring to positions in the *pre-expansion* numbering scheme.

The only place the code re-derives `selectableLines` from `unifiedDiffStart` is in `app-store.ts`, and that path runs when the diff is reloaded from disk/git after a file-system change, not when a hunk is expanded interactively in the UI [8](#0-7) . There is no equivalent re-validation step hooked into `expandTextDiffHunk`'s callers that guarantees the previously diverging line indices still point at the same content after the shift. If the recomputed offset for any hunk in the new numbering does not exactly match what the stale `Set<number>` assumes (off-by-one from the merge branch's `-1` adjustment, or a hunk being dropped/added during merging), `isSelected(absoluteIndex)` in `formatPatch`/`formatPatchToDiscardChanges` will silently resolve to the wrong boolean for a real content line, and `applyPatchToIndex` will `git apply --cached` a patch that stages/discards a line the user never selected [9](#0-8) .

### Impact Explanation
This falls squarely in the "silent corruption of what the user commits" impact bucket: a user who has deliberately deselected sensitive lines (e.g., a credential accidentally left in a diff, or lines they intend to keep uncommitted) could have them silently staged and committed — or, symmetrically, intended changes silently dropped — after expanding a hunk, with no error or warning. Because the expansion feature is routinely used when reviewing diffs from any repository (including a maliciously crafted one designed to produce many small/adjacent hunks to force merge-branch offset arithmetic), the attacker-controlled repository content indirectly influences hunk boundaries and thus the likelihood of hitting the offset drift, even though the attacker cannot directly choose which line gets mis-included.

### Likelihood Explanation
Undetermined/Low-to-Medium. I could not find, within the indexed portion of the codebase, an explicit re-synchronization of `DiffSelection`'s `divergingLines` against the newly shifted `unifiedDiffStart` values after `expandTextDiffHunk`/`expandWholeTextDiff` run, nor conclusive evidence in the unit tests (`text-diff-expansion-test.ts`, `patch-formatter-test.ts`) that this exact interaction (partial selection + hunk expansion + merge-with-adjacent) is covered end-to-end. This mirrors the original report's "Undetermined" severity — the arithmetic path exists and the guard that would catch a mismatch is not visible, but I was not able to fully trace whether some other layer (e.g., `SeamlessDiffSwitcher`/`side-by-side-diff.tsx`) forces a full selection reset on every expansion, which would neutralize the issue.

### Recommendation
- Whenever hunks are expanded/merged and `unifiedDiffStart`/`unifiedDiffEnd` are recomputed, deterministically rebuild the `DiffSelection`'s diverging-line set by re-mapping each previously selected/deselected absolute index through the same offset transformation used for the hunks themselves, rather than leaving the `Set<number>` untouched.
- Add an invariant check (e.g., in `formatPatch`) that a mismatch between `selection.selectableLines` cardinality/content and the current hunk layout throws rather than silently defaulting to "not selected" or "selected".
- Add a regression test that expands a hunk with an existing partial selection and merges it with an adjacent hunk, then asserts `formatPatch` output still reflects the originally selected content lines by text, not by position.

### Proof of Concept
Not independently executable from static analysis alone; conceptual repro path:
1. Open a repository with a modified file producing at least two hunks close enough together to trigger the "Short"/merge expansion path in `getHunkHeaderExpansionType` [10](#0-9) .
2. Deselect a specific added/deleted line in the second hunk for partial commit.
3. Expand the first hunk downward until `shouldMergeWithAdjacent` becomes true, causing `mergeDiffHunks` and the `numberOfNewDiffLines - 1` adjustment to shift subsequent hunks' `unifiedDiffStart` [11](#0-10) .
4. Commit the partial selection and inspect the actual patch generated by `formatPatch`/applied via `applyPatchToIndex` to check whether the line that was deselected before expansion is still excluded, versus a different line at the same numeric offset now being excluded instead.

Verifying step 4's actual outcome requires running the app/test suite, which I could not do from the indexed code alone.

export function getHunkHeaderExpansionType(
  hunkIndex: number,
  hunkHeader: DiffHunkHeader,
  previousHunk: DiffHunk | null
): DiffHunkExpansionType {
  const distanceToPrevious =
    previousHunk === null
      ? Infinity
      : hunkHeader.oldStartLine -
        previousHunk.header.oldStartLine -
        previousHunk.header.oldLineCount

  // In order to simplify the whole logic around expansion, only the hunk at the
  // top can be expanded up exclusively, and only the hunk at the bottom (the
  // dummy one, see getTextDiffWithBottomDummyHunk) can be expanded down
  // exclusively.
  // The rest of the hunks can be expanded both ways, except those which are too
  // short and therefore the direction of expansion doesn't matter.
  if (hunkIndex === 0) {
    // The top hunk can only be expanded if there is content above it
    if (hunkHeader.oldStartLine > 1 && hunkHeader.newStartLine > 1) {
      return DiffHunkExpansionType.Up
    } else {
      return DiffHunkExpansionType.None
    }
  } else if (distanceToPrevious <= DefaultDiffExpansionStep) {
    return DiffHunkExpansionType.Short
  } else {
    return DiffHunkExpansionType.Both
  }
}
