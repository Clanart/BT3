## Finding confirmed

`getNewFileContent` in `app/src/ui/diff/syntax-highlighting/index.ts` reads the working-directory "new" side of a diff by joining the repo path with the file's relative path and calling `readPartialFile`: [1](#0-0) 

`readPartialFile` is implemented with Node's `fs.createReadStream(path, { start, end })`, which by default resolves symlinks (it does not use `lstat`/`O_NOFOLLOW` or otherwise refuse to traverse a symbolic link): [2](#0-1) 

Git natively supports tracking symlinks (mode `120000`) whose blob content is the link *target string*. When such a file is checked out on a symlink-capable platform (macOS/Linux, and Windows with Developer Mode/symlink privilege), the working tree contains a real OS symlink that can point anywhere on the local filesystem, including outside `repository.path`. Because `getNewFileContent` never checks whether `file.path` resolves to a symlink (no `lstat`, no realpath containment check against `repository.path`, no comparison against the codebase's own `resolveWithin` helper used elsewhere for this exact purpose, e.g. in `app/src/lib/copilot-conflict-context.ts:390-407`), `createReadStream` will happily follow the link and stream bytes from whatever file it points to.

Those bytes are then decoded, split into lines, and fed to `highlight()`/`getTokens()` (`app/src/ui/diff/get-tokens.ts:9-24`), and rendered as syntax-highlighted diff content in the renderer — this is distinct from the git-level diff shown by `getWorkingDirectoryDiff` (`app/src/lib/git/diff.ts:342-401`), which invokes real `git diff` and therefore only ever shows the *link target string* as content, never the linked file's actual bytes, since git's object model stores symlinks as their target text, not as a dereferenced blob.

This matches the codebase's own security pattern used elsewhere (`resolveWithin` guard in `copilot-conflict-context.ts`) that this code path lacks.

### Title
Working-tree symlink is dereferenced during diff syntax highlighting, allowing off-repo file read - (`app/src/ui/diff/syntax-highlighting/index.ts`)

### Summary
`getNewFileContent` reads the on-disk "new" content of a working-directory file change with `readPartialFile(Path.join(repository.path, file.path), ...)`. This uses `fs.createReadStream`, which follows symbolic links. A cloned repository can commit a tracked symlink (git mode `120000`) whose target resolves outside the repository working tree. When Desktop displays that file's diff, the syntax-highlighting pipeline dereferences the symlink and streams the *target* file's real bytes (not the symlink's link-text), which are then tokenized and rendered in the diff view — a repo-content-controlled off-repo file read.

### Finding Description
`getNewFileContent` (`app/src/ui/diff/syntax-highlighting/index.ts:89-94`) never validates that `file.path` is a regular file confined to `repository.path`; it doesn't `lstat` the path or use a containment/`resolveWithin`-style check like the one already present in `app/src/lib/copilot-conflict-context.ts:390-407`. `readPartialFile` (`app/src/lib/file-system.ts:61-77`) opens the path with `fs.createReadStream`, which transparently follows symlinks. Since git tracks and checks out symlinks as normal filesystem symlinks, a malicious/compromised repository can ship a tracked symlink pointing at an arbitrary absolute path outside the repo (e.g. a sensitive config or credentials file reachable by the OS user). Viewing that file's diff in the Changes list triggers `getFileContents` → `getNewFileContent` → `readPartialFile`, dereferencing the link and returning the target file's bytes, which flow into `highlight()` and are indexed by `getTokens()` for rendering.

### Impact Explanation
This allows an attacker who controls repository content (a cloned/fetched repo) to read arbitrary files outside the repository that are accessible to the local OS user account running Desktop, and have their contents rendered inside the app's diff viewer. This satisfies the program's listed valid impact of "file... read outside the repo" originating from attacker-controlled repository content, without any git/committed-diff mechanism revealing it (a plain `git diff` of the same file would only ever show the symlink's link-text, not the target's contents), so this is a genuine gap beyond what git itself would expose.

### Likelihood Explanation
Requires only that the victim clones/opens an attacker-authored repository containing a tracked symlink pointing outside the repo, and then selects that file in the Changes tab of Desktop (a normal user action, no special privileges). On Windows, checkout of symlinks additionally requires Developer Mode or the `SeCreateSymbolicLinkPrivilege`, so likelihood there is lower; on macOS/Linux symlink checkout works by default with core.symlinks enabled (the default).

### Recommendation
Before calling `readPartialFile` in `getNewFileContent`, resolve `file.path` safely against `repository.path` (e.g. `lstat`/`realpath` and reject if the resolved real path escapes `repository.path`, mirroring the `resolveWithin` guard already used in `app/src/lib/copilot-conflict-context.ts`), or skip syntax highlighting entirely for paths whose `lstat` indicates a symbolic link.

### Proof of Concept
1. Attacker creates a repo containing a symlink, e.g. `ln -s /etc/passwd leak.txt`, commits it, and pushes it.
2. Victim clones the repo with Desktop, then modifies `leak.txt`'s target contents indirectly is not needed — simply having the tracked symlink checked out and showing as a change (e.g., by touching another file, or the initial "New" state) triggers `getFileContents`.
3. Victim selects `leak.txt` in the Changes list; Desktop's diff pane calls `getNewFileContent` → `readPartialFile(Path.join(repo.path, 'leak.txt'), 0, ...)`, which follows the symlink and streams `/etc/passwd` contents, rendered as syntax-highlighted diff text in the UI.

```typescript
export async function readPartialFile(
  path: string,
  start: number,
  end: number
): Promise<Buffer> {
  return await new Promise<Buffer>((resolve, reject) => {
    const chunks = new Array<Buffer>()
    let total = 0

    createReadStream(path, { start, end })
      .on('data', (chunk: Buffer) => {
        chunks.push(chunk)
        total += chunk.length
      })
      .on('error', reject)
      .on('end', () => resolve(Buffer.concat(chunks, total)))
  })
```
