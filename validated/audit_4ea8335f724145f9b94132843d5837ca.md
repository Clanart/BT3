### Title
Repair-nonce eviction allows unauthenticated remote DoS of shred repair — ([File: core/src/repair/outstanding_requests.rs])

### Summary
The external report describes an unprivileged actor calling a public guard function (`checkTransaction`) to overwrite a shared "last execution" timestamp, invalidating the multisig's cooldown state and blocking a legitimate transaction. The Agave analog is `OutstandingRequests::register_response` [1](#0-0)  combined with `verify_repair_nonce` in the shred-repair receive path [2](#0-1) . Any unauthenticated remote packet that supplies a matching (or brute-forced) 32-bit nonce can evict/invalidate a node's pending outstanding repair request before the real response arrives, exactly like front-running the multisig's cooldown reset.

### Finding Description
`OutstandingRequests` tracks pending shred-repair requests keyed by a random 32-bit `nonce` in an LRU cache of only 16,384 entries [3](#0-2) [4](#0-3) . When any packet arrives on the repair-response path, `verify_repair_nonce` extracts the shred and its trailing nonce, then calls `register_response` without checking that the packet came from the peer the request was originally sent to [2](#0-1) .

Inside `register_response`, if the nonce is found but the response fails `verify_response` or the request has expired, the code explicitly deletes ("invalidates") the outstanding entry:
```
if now >= status.expire_timestamp || !status.request.verify_response(response) {
    // Invalid/expired response should invalidate this nonce.
    should_delete = true;
    return None;
}
``` [5](#0-4) 

This is the corrupted-state analog to `checkTransaction` resetting the BORG_SAFE cooldown: the guard state that gates whether the legitimate repair response will be accepted (`requests.get_mut(&nonce)`) can be destroyed by an unprivileged, unauthenticated third party. Because the nonce space is a full `u32` (~4.3 billion values) but at most 16,384 requests are outstanding at once, an attacker who floods the repair UDP port with garbage/duplicate shred packets carrying arbitrary nonces has a `16384/2^32 ≈ 1/262144` chance per packet of hitting a live nonce — a trivially crossable brute-force ratio at typical flood rates achievable by a single low-cost sender. Once a hit occurs, the entry is deleted before the genuine repair peer's response arrives, and that later legitimate response is then dropped as "unexpected nonce" (`register_response` returns `None` and `.is_some()` in `verify_repair_nonce` is `false`) [6](#0-5) .

No signature or address check protects this: the routine only checks nonce + response content shape, not sender identity, unlike the BORG_SAFE issue where at least a signature over the multisig transaction exists — here the repair-response path is intentionally permissive to accept UDP responses from arbitrary IPs while relying solely on the nonce as the trust boundary.

The same pattern (`register_response` invalidating the nonce on any failed verification, called from an unauthenticated packet-receive path) repeats in `core/src/repair/ancestor_hashes_service.rs` [7](#0-6)  and `core/src/repair/block_id_repair_service.rs` [8](#0-7) .

### Impact Explanation
A remote, unprivileged attacker can silently and repeatedly invalidate a victim validator's in-flight shred/ancestor-hash/block-id repair requests before the legitimate peer's response is processed, forcing repeated request timeouts (`DEFAULT_REQUEST_EXPIRATION_MS` = 60s) and re-requests [9](#0-8) . This degrades the victim's ability to catch up on missing shreds/ancestors, delaying block replay/voting and, at scale, contributing to non-RPC remote exhaustion/degradation of the repair subsystem — the valid impact class for this bug hunt (non-RPC remote exhaustion/crash).

### Likelihood Explanation
The attack requires no stake, no valid keypair, and no privileged position — only the ability to send arbitrary UDP packets to the target's repair-response port. The reduced brute-force ratio (bounded outstanding-request cache of 16,384 vs. a 32-bit nonce space) makes nonce collision with a live request statistically feasible under moderate flood rates, and the code path performs no sender-authentication before deleting matched entries.

### Recommendation
- Bind the response validation to the address/pubkey the corresponding request was actually sent to, and reject responses from unexpected peers before touching `register_response` state.
- Do not eagerly delete (`should_delete = true`) an outstanding request purely because a single response failed `verify_response`; only decrement/expire on verified success or on the existing expiration timer, so that one spoofed/garbage packet cannot pre-empt the legitimate response.
- Consider widening/rekeying the nonce scheme (e.g., include a per-request secret or larger effective entropy relative to cache size) to make guessing an active nonce impractical.

### Proof of Concept
1. Attacker observes (or infers from repair socket traffic patterns) that a validator has repair requests outstanding (a small number relative to the possible nonce space, since only 16,384 can be live at once).
2. Attacker crafts UDP packets shaped like repair responses (a parseable shred payload plus a trailing nonce) and sends them at high rate with sequentially/randomly varied 32-bit nonce values to the victim's repair-response UDP port, without any valid signature tied to the actual repair peer.
3. For any packet whose nonce happens to match a currently outstanding request, `verify_repair_nonce` → `register_response` finds the entry; because the injected shred does not satisfy `verify_response` (it's not the real requested shred), `should_delete` is set and the entry is deleted [10](#0-9) .
4. The real repair peer's genuine response subsequently arrives; `register_response` no longer finds the nonce, so it is dropped as invalid [6](#0-5) , and the victim must wait for the 60s expiration/retry cycle to re-request the missing shred.
5. Repeating this continuously against a target validator's repair socket suppresses effective shred repair, analogous to how `checkTransaction` could be front-run to reset the BORG_SAFE cooldown and block legitimate execution.

Note: I was unable to fully read `ServeRepair::verify_response`/`ShredRepairType::verify_response` implementations in `core/src/repair/serve_repair.rs` and `core/src/repair/request_response.rs` before the tool budget ran out, so the exact per-type verification strictness (e.g., whether it also checks slot/index bounds tightly enough to make garbage packets trivially reach this code path) could not be fully confirmed from the index; a Devin session with full file access would be needed to verify the precise minimal packet shape required to reach `register_response` for each repair-request type.

    pub fn register_response<R>(
        &mut self,
        nonce: u32,
        response: &S,
        now: u64,
        success_fn: impl Fn(&T) -> R,
    ) -> Option<R> {
        let mut should_delete = false;
        let response = self.requests.get_mut(&nonce).and_then(|status| {
            if status.num_expected_responses == 0 {
                // No more expected responses
                return None;
            }

            if now >= status.expire_timestamp || !status.request.verify_response(response) {
                // Invalid/expired response should invalidate this nonce.
                should_delete = true;
                return None;
            }

            status.num_expected_responses -= 1;
            if status.num_expected_responses == 0 && status.metadata.is_none() {
                // No metadata, and no more expected responses safe to delete eagerly.
                should_delete = true;
            }
            Some(success_fn(&status.request))
        });

        if should_delete {
            self.requests
                .pop(&nonce)
                .expect("request must exist when marked for deletion");
        }
        response
    }
```

// Returns false if repair nonce is invalid and packet should be discarded.
#[must_use]
fn verify_repair_nonce(
    packet: PacketRef,
    now: u64, // solana_time_utils::timestamp()
    outstanding_repair_requests: &mut OutstandingShredRepairs,
) -> bool {
    debug_assert!(packet.meta().flags.contains(PacketFlags::REPAIR));
    let Some((shred, Some(nonce))) = shred::layout::get_shred_and_repair_nonce(packet) else {
        return false;
    };
    outstanding_repair_requests
        .register_response(nonce, shred, now, |_| ())
        .is_some()
}
