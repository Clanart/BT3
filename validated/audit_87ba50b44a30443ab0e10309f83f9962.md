Given the evidence gathered, the strongest local analog to the "no upper bound on an attacker-influenceable value" bug class is the unrestricted `protocol.file.allow=always` override enabled by the `allowFileProtocol` flag in submodule updates, which removes an existing Git security guard rather than merely lacking a numeric ceiling.

### Title
Submodule updates unconditionally re-enable `protocol.file.allow=always`, allowing malicious `.gitmodules` `file://` URLs to clone arbitrary local paths - (File: app/src/lib/git/submodule.ts)

### Summary
`checkoutBranch`/`checkoutCommit` accept a boolean `allowFileProtocol` flag that is forwarded to `updateSubmodulesAfterOperation`, which — when `true` — prepends `-c protocol.file.allow=always` to `git submodule update --init --recursive`. This is the same override Git 2.38+ deliberately restricted (via the default `protocol.file.allow=user`) to stop malicious repositories from using `file://` submodule URLs to make a victim's client silently clone arbitrary local directories into the working tree. There is no bound/allow-list on which submodule URLs are permitted when this flag is set — it is an all-or-nothing override, analogous to the report's "no upper limit" flaw: a caller-controlled boolean unlocks unrestricted behavior with no validation of the actual attacker-controlled input (`.gitmodules` submodule URL) that flows through it. [1](#0-0) [2](#0-1) 

### Finding Description
`updateSubmodulesAfterOperation` builds the submodule-update arguments as:
```
['-c', 'protocol.file.allow=always', 'submodule', 'update', '--init', '--recursive']
```
when `allowFileProtocol` is `true`, with no filtering of the submodule URLs that `.gitmodules` declares. [3](#0-2) 

`.gitmodules` is fully attacker-controlled content in a cloned/forked repository. Git's own hardening (the `protocol.file.allow=user` default introduced after CVE-2022-39253) exists precisely because a submodule URL of `file:///some/local/path` lets a "clone" silently pull the contents of any local directory the user has access to into the repository working tree. Desktop's `allowFileProtocol=true` path re-enables this behavior wholesale (`=always`) instead of validating or restricting *which* URLs are trusted — the analog of the smart-contract bug's missing upper bound: a single flag removes the protective ceiling entirely rather than constraining the attacker-controlled input that flows through the guarded operation.

The flag defaults to `false` in the public API surface (`checkoutBranch`, `checkoutCommit`), and is deliberately flipped to `true` in some call sites (confirmed by test fixtures) for scenarios like checking out branches/PRs that rely on local file-based remotes (e.g., forked repos cloned locally). Once flipped, the override applies to the *entire* recursive submodule update for that operation, meaning nested submodule URLs defined by the untrusted repository content are honored without restriction. [4](#0-3) 

### Impact Explanation
If the boolean is enabled for a checkout/pull path that also processes attacker-supplied repository content (a cloned/fetched repo whose `.gitmodules` an attacker controls, e.g. a malicious PR or fork), `git submodule update --init --recursive` will honor `file://` submodule URLs unconditionally. This can cause Desktop to silently clone the contents of arbitrary local directories/paths accessible to the current OS user into the repository's working tree as a "submodule." Those cloned files then become visible/committable inside the repository (potential local file read/exfiltration into version control, or corruption of what the user later commits/pushes) — matching the requested impact class of "file read outside the repo" or "silent corruption of what the user commits."

### Likelihood Explanation
Likelihood depends entirely on which call sites set `allowFileProtocol=true` in `app/src/lib/stores/app-store.ts` (confirmed to reference this flag) when handling PR/fork checkouts. I was not able to fully trace, within the remaining investigation budget, every caller in `app-store.ts` that sets this to `true` for untrusted (non-local, e.g., true GitHub fork PR) checkouts versus purely local-fork test scaffolding. This is the key uncertainty: if `allowFileProtocol=true` is only used for genuinely local, already-trusted repositories (as in the test helpers), the exploitability is low; if it is also used for checking out PRs from *arbitrary GitHub forks*, the exploitability is high, since the fork owner fully controls `.gitmodules`.

### Recommendation
- Do not use `protocol.file.allow=always` as a blanket override. If a legitimate local-fork use case needs `file://` submodule support, scope the override narrowly (e.g., allow only for a specific, already-verified local path) rather than unconditionally enabling it for `--recursive` submodule resolution.
- Validate/sanitize submodule URLs declared in untrusted `.gitmodules` content before allowing `file://` (or any non-http(s)/ssh) schemes, rather than gating purely on a boolean supplied by the caller.
- Audit all call sites that pass `allowFileProtocol=true` (in `app/src/lib/stores/app-store.ts`) to confirm none of them are reachable from checkout of attacker-controlled forks/PRs.

### Proof of Concept
1. Attacker creates/forks a public repository and adds `.gitmodules` with:
   ```
   [submodule "leak"]
     path = leak
     url = file:///Users/victim/Documents
   ```
2. Victim opens the PR/branch in GitHub Desktop through a flow that ultimately calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which clones `/Users/victim/Documents` into the `leak/` submodule directory inside the repository working tree.
4. The victim's local files are now embedded in the repository and can be viewed, diffed, or accidentally committed/pushed by GitHub Desktop. [5](#0-4)

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
