### Title
Unchecked reward transfer amounts in `BaseRewardPool` can permanently freeze unclaimed yield for fee-on-transfer reward tokens - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool` has no reward-token whitelist. Any address configured as a reward token (via `queueNewRewards`, called by a manager, or accepted for `donateRewards`) is trusted to transfer exactly the nominal `_amountReward` into and out of the contract. Both `_provisionReward` (crediting) and `getReward` (paying out) operate purely on ledger accounting (`rewardPerTokenStored`, `userRewards`) without ever reconciling against the contract's actual token balance, unlike the fixed pattern described in the reference report where `_safeRewardTransfer` now caps the payout to the real balance delta.

### Finding Description
`_provisionReward` pulls tokens with `safeTransferFrom` and immediately credits the full nominal `_amountReward` into `rewardInfo.rewardPerTokenStored`, regardless of how many tokens actually landed in the contract: [1](#0-0) 

`getReward` later pays out to users strictly based on that internal accounting, transferring `userRewards[rewardToken][_account]` with a plain `safeTransfer` and no check that the contract's balance actually covers it: [2](#0-1) 

Because there is no whitelist restricting which ERC20 can become `rewardTokens[i]` (any token supplied to `queueNewRewards`/`donateRewards` becomes `isRewardToken[_rewardToken] = true`), a deflationary/fee-on-transfer reward token will cause the credited `rewardPerTokenStored` to overstate the pool's real balance. Over time (or immediately for a single provisioning), the sum of all `userRewards` for that token can exceed `IERC20(rewardToken).balanceOf(address(this))`. When any user then calls `getReward` (via `MasterMagpie._claimBaseRewarder` → `BaseRewardPool.getReward`), the `safeTransfer` for the deficient token reverts because the contract doesn't hold enough balance, reverting the entire `getReward` call — which iterates and pays out *all* reward tokens in the same transaction: [3](#0-2) 

This is exactly the bug class flagged in the reference report: rewards are transferred based on the requested/accounted amount rather than the verified before/after balance delta, and the system does not whitelist tokens to guard against this discrepancy.

### Impact Explanation
Since `getReward` loops over *every* registered reward token and reverts entirely if any single token's transfer fails, a single under-collateralized reward token permanently blocks every user of that pool from claiming *all* of their rewards (MGP claims routed through `MasterMagpie._multiClaim` → `_claimBaseRewarder` are similarly blocked), constituting a permanent freeze of unclaimed yield for all stakers of that pool, satisfying the "theft or permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
Triggering this requires a reward token whose transfer behavior doesn't match its nominal amount (fee-on-transfer/rebasing/deflationary tokens), which is plausible given the codebase performs no reward-token whitelisting or validation of token transfer semantics anywhere in `BaseRewardPool`, `queueNewRewards`, or `donateRewards`. Once such a token is registered as a reward token for a pool (an ordinary configuration action, not a malicious/privileged exploit), any ordinary user's `getReward` call can trip the permanent freeze — no attacker privilege is needed beyond normal reward claiming.

### Recommendation
Mirror the referenced fix: in `getReward` (and any other reward payout path), measure `IERC20(rewardToken).balanceOf(address(this))` before and after `safeTransfer`, and cap the amount actually deducted from `userRewards` to the real balance delta, so a shortfall on one token cannot block distribution of other reward tokens or freeze legitimate accounting. Additionally, verify actual received amounts in `_provisionReward` (before/after balance) before crediting `rewardPerTokenStored`, to prevent phantom reward inflation for non-standard tokens.

### Proof of Concept
1. Pool manager (via `queueNewRewards`) or any user (via `donateRewards`, since it only requires `isRewardToken[_rewardToken]` to already be true) registers/funds a fee-on-transfer ERC20 as a reward token for a `BaseRewardPool`.
2. `_provisionReward` credits the *nominal* `_amountReward` to `rewardPerTokenStored`, but the actual balance received is less due to the transfer fee.
3. As users accrue `earned()`/`userRewards` for that token based on the inflated `rewardPerTokenStored`, the total claimable amount across users exceeds the pool's actual token balance.
4. Any user calls `deposit`/`withdraw`/`multiclaim` on `MasterMagpie`, which internally calls `BaseRewardPool.getReward`; the `safeTransfer` for the deficient token reverts because `balanceOf(address(this)) < reward`.
5. Because `getReward` reverts as a whole, every reward token payout for that call reverts too — the user (and every other user attempting to claim, since the debt persists) is permanently unable to claim any accrued rewards from that pool until the contract is manually top-supplied out-of-band, which is not a function of the contract itself.

    function getReward(address _account, address _receiver)
        override
        public
        onlyMasterMagpie
        updateReward(_account)
        returns (bool)
    {
        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

        return true;
    }

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
