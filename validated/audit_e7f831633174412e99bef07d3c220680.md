### Title
Unbounded recursive parsing of untrusted `PuzzleInfo`/`Solver` data causes Python stack-overflow DoS when processing offers - (File: `chia/wallet/puzzle_drivers.py`)

### Summary
`chia.wallet.puzzle_drivers.decode_info_value()` recursively deserializes attacker-supplied dictionary/list structures without any depth limit. This function backs `PuzzleInfo` and `Solver`, which are populated directly from JSON/CLVM data embedded in an `Offer` (`driver_dict: dict[bytes32, PuzzleInfo]` on the `Offer` dataclass), i.e., data supplied by an untrusted offer counterparty. A crafted offer with a deeply nested `driver_dict` (nested `"also"` chains, or deeply nested lists/dicts as values) can drive unbounded Python recursion during `PuzzleInfo.__getitem__`/`decode_info_value`/`PuzzleInfo.check_type`, causing a `RecursionError`/native stack overflow when a wallet parses, displays, or validates the offer via RPC (`take_offer`, `get_offer_summary`, etc.). This mirrors the Helm `strvals` bug class: attacker-controlled string/structured input parsed by a recursive parser with no depth bound, causing a crash in the parsing process.

### Finding Description
`PuzzleInfo`/`Solver` (`chia/wallet/puzzle_drivers.py:21-123`) wrap plain Python `dict`s built straight from external data (offer files, RPC JSON) via `PuzzleInfo.from_json_dict()` (`chia/wallet/puzzle_drivers.py:89-91`). Field access (`__getitem__`, line 38-40 and 100-102) calls `decode_info_value(cls, value)`: [1](#0-0) 

`decode_info_value` recurses into every nested `dict` (wrapping it back into a new `PuzzleInfo`/`Solver`, whose own `__getitem__` will again call `decode_info_value`) and every nested `list` element, with no depth or size limit. `PuzzleInfo.also()` (line 60-64) and `PuzzleInfo.check_type()` (line 66-79) are explicitly designed to support recursive `"also"` chaining and recurse themselves without any bound.

The `driver_dict: dict[bytes32, PuzzleInfo]` field on `Offer` (`chia/wallet/trading/offer.py:98`) is populated from the offer's `OfferSummary.infos` — data that comes from the bech32m/CLVM-encoded offer file provided by the counterparty (`Offer.from_bech32`/summary parsing paths in the same module). Any code path that inspects an offer's driver info (constructing/validating summaries, `outer_puzzles.construct_puzzle`/`match_puzzle`, CLI/RPC offer-summary endpoints, or `PuzzleInfo.__eq__` comparisons used during offer validation) will trigger `decode_info_value` recursion over attacker-chosen nesting depth.

Because CPython's default recursion limit (typically 1000) is exceeded quickly by trivially nested JSON/dict structures, an attacker can build a `driver_dict`/`also` chain a few thousand levels deep (or nested lists) that overflows the interpreter's call stack, raising an unrecoverable `RecursionError` (or, in the presence of C-level recursion e.g. in equality/repr, a hard interpreter crash) in the wallet process handling the offer.

### Impact Explanation
This is a Denial-of-Service against the wallet process (or any RPC/CLI tool) that inspects an untrusted offer's `driver_dict`/`Solver` fields — analogous to Helm's `strvals` DoS where a malicious `--set` string caused an unrecoverable panic. An unprivileged offer counterparty (or anyone submitting an offer for the victim's wallet to evaluate, e.g., over `take_offer`/`get_offer_summary` RPC or a shared offer file) can crash or hang the requesting wallet process without spending any coins or presenting a valid signature. This matches the "spend-triggered transaction-processing halt" impact category (offers and trades flow) permitted by the validation rules.

### Likelihood Explanation
Likelihood is high for triggering the crash: constructing a deeply nested JSON dict/list or chained `"also"` `PuzzleInfo` requires no special privileges, no fee, and no valid coin spend — only a plausible-looking offer or driver-info payload that reaches `PuzzleInfo`/`Solver` field access. The bar to reach this recursive parser (offer summary, driver-dict comparison during offer validation) is low because wallets are expected to summarize/validate any offer received from a counterparty before deciding to take it.

### Recommendation
- Impose an explicit maximum nesting depth (and/or total node count) when constructing `PuzzleInfo`/`Solver` from untrusted dict/list data, rejecting inputs beyond a safe bound before recursive processing.
- Convert `decode_info_value`, `PuzzleInfo.check_type`, and `PuzzleInfo.also`-chain traversal to iterative implementations with an explicit stack and depth counter, mirroring the existing iterative `sha256_treehash` pattern already used elsewhere in the codebase for CLVM tree traversal.
- Validate offer-derived `driver_dict`/`OfferSummary.infos` structures at the earliest ingestion point (offer decode / bech32m parsing) rather than lazily during attribute access, so malformed/deeply nested payloads are rejected before being handed to wallet business logic.

### Proof of Concept
1. Construct a malicious offer (or raw `driver_dict`/`Solver` JSON payload) whose `PuzzleInfo` value contains a deeply nested `"also"` chain, e.g. programmatically build
   `info = {"type": "X"}`; then repeat `info = {"type": "X", "also": info}` several thousand times to produce a chain far exceeding CPython's default recursion limit.
2. Call `PuzzleInfo(info).also()` repeatedly, or invoke `PuzzleInfo(info).check_type(["X"] * N)`, or simply request the wallet to summarize/validate an offer whose `driver_dict` embeds this structure (e.g. via the `get_offer_summary` / `take_offer` RPC).
3. Observe the wallet process raise an unrecoverable `RecursionError` (or crash) while evaluating `decode_info_value`/`PuzzleInfo.check_type`, denying the wallet's offer-processing capability without any valid signed spend. [2](#0-1) [3](#0-2)
