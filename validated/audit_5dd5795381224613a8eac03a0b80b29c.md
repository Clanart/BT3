## Title
`TendermintClient::state_machine()` treats explicitly-disabled state machines as supported by checking `contains_key` instead of the stored boolean value - (File: `modules/ismp/clients/tendermint/src/lib.rs`)

### Summary
`SupportedStateMachines` is a `StorageMap<StateMachine, bool, OptionQuery>` whose value is meant to encode whether a given `StateMachine` is currently trusted [1](#0-0) . `AdminOrigin` can toggle this flag with `set_supported_state_machine(state_machine, supported)`, which simply inserts `(state_machine, supported)` into storage regardless of the boolean value [2](#0-1) . However, `TendermintClient::state_machine()` only checks `SupportedStateMachines::<T>::contains_key(id)` rather than verifying the stored value is `true`: [3](#0-2) 

Since `contains_key` returns `true` for any key present in the map — including one explicitly set to `false` — calling `set_supported_state_machine(sm, false)` has no actual effect on whether `sm` is treated as supported. Only `remove_supported_state_machine` (which calls `SupportedStateMachines::<T>::remove`) genuinely revokes trust [4](#0-3) .

### Finding Description
`ConsensusClient::state_machine()` is documented as security-critical: "Must return an error if the identifier is unknown or risk a critical vulnerability" [5](#0-4) . It is invoked from `validate_state_machine()` in the core ISMP handler path, which is the gate used by request, response, and timeout message handlers before proof verification proceeds: [6](#0-5) . The returned `StateMachineClient` is then used to run `verify_membership`/`verify_state_proof` against the claimed state root, e.g. in `request::handle` [7](#0-6) .

Because `TendermintClient::state_machine()` uses `contains_key` instead of `get(id) == Some(true)`, an admin's intent to disable a Tendermint-consensus EVM chain by calling `set_supported_state_machine(sm, false)` is silently ineffective — the key remains present, so `contains_key` still returns `true`, and a `TendermintEvmStateMachine` is still constructed and used to verify proofs for that chain id. The state-machine-support binding invariant is broken: the effective "supported" flag stored on-chain (`false`) is not honored by the consensus client's trust decision.

### Impact Explanation
Any unprivileged relayer can continue to submit request/response/timeout proofs for a `StateMachineId` that governance believed it had disabled via `set_supported_state_machine(sm, false)`. As long as the corresponding EVM ISMP contract address mapping (`EvmHosts`) is still configured, proofs against that chain's root will be verified and accepted as trusted, allowing messages/state to be processed for a chain that is supposed to be untrusted — false state/proof acceptance and potential unauthorized execution of cross-chain messages, matching the "false proof/state acceptance" and "unauthorized transaction or execution" impact categories.

### Likelihood Explanation
Exploitation requires no special relayer privilege on the attacker's part; the only precondition is a governance action using the `supported=false` variant instead of `remove_supported_state_machine` — a realistic operational path since both calls appear designed to disable a chain (per the emitted `StateMachineSupportUpdated { supported: false }` event, which is identical in both call paths [8](#0-7) ). An operator relying on `set_supported_state_machine(sm, false)` to disable a compromised or deprecated chain would not achieve the intended effect, and this is not obviously exposed by tests or naming — the bug is silent until exploited.

### Recommendation
Change `TendermintClient::state_machine()` to check the stored value rather than key presence, e.g. `SupportedStateMachines::<T>::get(id) == Some(true)` (or `.unwrap_or(false)`), matching the documented safety contract in `ConsensusClient::state_machine`. Audit and fix the analogous pattern in `modules/ismp/clients/sync-committee/src/beacon_client.rs` (`SupportedStatemachines::<T, I>::contains_key(id)`), which shares the same flaw [9](#0-8) .

### Proof of Concept
1. As `AdminOrigin`, call `TendermintPallet::set_supported_state_machine(StateMachine::Evm(chain_id), false)` — storage now holds `SupportedStateMachines[Evm(chain_id)] = Some(false)`.
2. As an unprivileged relayer, submit an ISMP `Message::Request` (or Response/Timeout) with `proof.height.id.state_id = StateMachine::Evm(chain_id)` through `handlers::handle_incoming_message`.
3. `validate_state_machine` calls `consensus_client.state_machine(Evm(chain_id))`; because `SupportedStateMachines::<T>::contains_key` returns `true` (the entry exists with value `false`), the function returns `Ok(Box::new(TendermintEvmStateMachine::default()))` instead of `Err(...)`.
4. `verify_membership` proceeds normally against the (still trusted) EVM state root, and the request/response/timeout is processed — demonstrating that the admin's explicit `false` disablement was bypassed.
5. Expected/fixed behavior: step 3 should return `Err(Error::Custom("State machine not supported: ..."))` once `state_machine()` checks `get(id) == Some(true)`.

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
