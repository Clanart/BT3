### Title
Deserialized `ReceivedOutput` is never re-bound to its claimed spend key: attacker-supplied bytes yield outputs reported as received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The MinSwap LP minting-policy bug verified the *quantity* of minted tokens without verifying their *destination*. The direct analog in `bitcoin-serai` is `ReceivedOutput`: it is a `(offset, TxOut, outpoint)` triple whose implicit security invariant is `output.script_pubkey == p2tr_script_buf(group_key + offset * G)`. `Scanner::scan_transaction` establishes that invariant by construction, but `ReceivedOutput::read` — explicitly reachable with untrusted bytes — accepts any `offset` and any `script_pubkey` without checking they are related. A malformed `ReceivedOutput` is then treated as a spendable wallet output.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` keyed by the P2TR script of `key + offset*G` (networks/bitcoin/src/wallet/mod.rs:155, 180-196). `scan_transaction` only produces a `ReceivedOutput` when `output.script_pubkey` is a registered script, so the attached `offset` is guaranteed to be the scalar that turns the group key into the output's internal key (lines 199-214). Spending correctness depends entirely on this binding.

`ReceivedOutput::read` (lines 122-134), however, decodes `offset`, `output`, and `outpoint` independently:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no check that `output.script_pubkey` is even a P2TR script, let alone the one corresponding to `key + offset*G`. The struct exposes no `key` back-reference, so downstream code cannot re-derive the binding either — `Output::key()` in the processor *recomputes* the base key as `x_only(script_pubkey) - offset*G`, which for an attacker-crafted pair yields a meaningless point while `balance()` still reports `output.value`.

This mirrors MinSwap exactly: the credential (minted LP / spendable output) is validated as an object, but its binding to the intended destination (the pool / the threshold key that can actually spend it) is never enforced on the deserialization path.

### Impact Explanation
Any consumer that accepts serialized `ReceivedOutput`s (e.g., outputs relayed between scanners, coordinators, or watch-only components, or restored from untrusted storage) can be fed a `ReceivedOutput` claiming value `v` at some outpoint while:

- the `script_pubkey` pays to an attacker-controlled address (or an unrelated script), or
- the `offset` does not correspond to the embedded key, so the FROST multisig signature produced via `SignableTransaction`/tweaked keys will not satisfy the output's key-path spend.

Result: funds are reported as received/creditable to the Serai vault while being unspendable by the threshold key (or actually owned by the attacker). This is the accepted impact class "funds reported received that are not spendable." Reachability is public-input-only: the attacker just needs to supply bytes to `ReceivedOutput::read`.

### Likelihood Explanation
Exploitation requires a code path where `ReceivedOutput`s cross a trust boundary in serialized form rather than being produced locally by `scan_transaction`/`scan_block`. Within `bitcoin-serai` itself the scanner path is safe by construction; the exposure exists for integrators/processors that persist or relay `ReceivedOutput`s (the `#[cfg(feature = "std")]` `read`/`serialize` pair exists precisely for that). Given that limitation, likelihood is moderate; severity is bounded to Medium since it corrupts accounting/spendability rather than directly leaking key material.

### Recommendation
Bind the output to its key on the trust boundary:

- Store the base `key` in `ReceivedOutput` (or pass it into `read`), and in `read` verify `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)`, rejecting otherwise.
- Alternatively, make `ReceivedOutput` construction private-ish and provide `ReceivedOutput::read_and_verify(key, r)` so deserialization cannot bypass the scanner's invariant; document that raw `read` is only for trusted, self-produced data.
- At minimum, reject non-P2TR `script_pubkey`s in `read` so downstream `is_p2tr` assertions and key extraction cannot be driven on attacker-chosen scripts.

### Proof of Concept
Conceptual Rust against `bitcoin-serai`:

```rust
use bitcoin_serai::wallet::{ReceivedOutput, p2tr_script_buf};
use bitcoin_serai::bitcoin::{TxOut, OutPoint, Amount, ScriptBuf, Txid};
use frost::curve::Secp256k1;
use ciphersuite::Ciphersuite;
use k256::{ProjectivePoint, Scalar};
use std::io::Write;
use bitcoin::hashes::Hash;

// Attacker crafts bytes: offset = 0, script_pubkey = attacker's own P2TR address
let attacker_key = ProjectivePoint::GENERATOR * Scalar::from(42u64);
let attacker_script = p2tr_script_buf(attacker_key).unwrap();

let mut buf = vec![];
buf.write_all(&Scalar::ZERO.to_bytes()).unwrap();                 // offset = 0 (vault key)
buf.extend(bitcoin::consensus::serialize(&TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: attacker_script,                                 // pays to attacker, not vault
}));
buf.extend(bitcoin::consensus::serialize(&OutPoint {
  txid: Txid::all_zeros(), vout: 0,
}));

let recv = ReceivedOutput::read(&mut buf.as_slice()).unwrap();    // accepted
assert_eq!(recv.value(), 100_000);                                // reports funds received
// recv.offset() == 0 implies spendable by the untweaked vault key — false.
// Any signature produced for group_key + 0*G cannot spend attacker_script.
```

The same primitive with `script_pubkey = p2tr_script_buf(vault_key + offset'*G)` for an unregistered `offset'` produces an output that "belongs" to the scanner's key space but whose attached `offset` is wrong, again yielding unspendable "received" funds. Root cause is confined to `ReceivedOutput::read` at networks/bitcoin/src/wallet/mod.rs:122-134 lacking the binding check enforced implicitly by `scan_transaction` at lines 205-211.

*Caveat:* whether a production Serai component actually feeds attacker-controlled bytes into `ReceivedOutput::read` could not be fully verified within the iteration budget (the processor paths I sampled, e.g. `processor/src/networks/bitcoin.rs` `Output::read`, read `ReceivedOutput`s whose provenance is DB/local). If no such crossing exists, this degrades to a hardening issue rather than a live exploit path.
