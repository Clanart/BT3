### Title
Malicious DKG/signing participant forces O(n·t·log n) multiexponentiation CPU exhaustion via batch-verifier blame search - (File: crypto/multiexp/src/batch.rs)

### Summary
CVE-2018-16844 is an attacker-reachable excessive-CPU-consumption flaw in a protocol handler. The analog in Serai is the blame-search path of `BatchVerifier`: whenever any queued statement fails, `verify_vartime_with_vartime_blame` / `verify_with_vartime_blame` invokes `blame_vartime`, which performs a binary search over the queued statements, running a full `multiexp_vartime` on each halved slice. A single unauthenticated, untrusted statement that fails verification therefore upgrades one multiexp over `n·t` pairs into `~log2(n)` additional multiexps over `n·t` pairs, a CPU amplification reachable entirely from public protocol messages sent by an unprivileged PedPoP/FROST participant.

### Finding Description
`BatchVerifier::verify_vartime_with_vartime_blame` first runs `multiexp_vartime(&flat(&self.0))` over all queued pairs; on failure it calls `blame_vartime`, which iteratively halves the statement slice and re-runs `multiexp_vartime` until a single faulty statement is isolated [1](#0-0) . The total work on a failing batch is `O(total_pairs · log2(num_statements))` variable-time scalar multiplications, versus `O(total_pairs)` for the honest path.

This path is driven by attacker-controlled bytes in two in-scope flows:

1. **PedPoP round 1** — `SecretShareMachine::verify_r1` queues one Schnorr PoK statement per participant and calls `batch.verify_vartime_with_vartime_blame()` [2](#0-1) . Any participant can send a well-formed `EncryptionKeyMessage` (parsed via `EncryptionKeyMessage::read` / `Commitments` of length `t`) whose `sig` fails, forcing the blame search.
2. **PedPoP round 2** — `KeyMachine::calculate_share` queues, per participant `l`, a decryption PoP statement plus `share_verification_statements`, which itself emits `t + 1` pairs via `exponential` [3](#0-2)  then verifies with `batch.verify_with_vartime_blame()` [4](#0-3) . A single invalid `EncryptedMessage` PoP or share makes the victim perform the aggregate `O(n·t)` multiexp plus `log2(2n)` extra multiexps over up to `n·(t+1)` pairs each.
3. **FROST signing** — `AlgorithmSignatureMachine::complete` falls back to per-share batch verification with `verify_vartime_with_vartime_blame` whenever the aggregate signature check fails [5](#0-4) . A participant submitting an invalid `SignatureShare` (a single `read_F` scalar) forces a `verify_share` batch plus blame search over the whole signing set.

Because `ThresholdParams` permits `n, t` up to 65535 [6](#0-5) , the round-2 batch can contain ~4 billion (scalar, point) pairs; a single garbage share multiplies the victim's scalar-multiplication work by ~18× over an already large multiexp, and the attacker pays only the cost of generating one small message.

### Impact Explanation
An unprivileged participant in a PedPoP DKG or FROST signing session can repeatedly submit malformed PoP signatures or shares, each time imposing an order-of-magnitude CPU amplification on every honest party running `verify_r1`, `calculate_share`, or `complete`. With large multisig parameters the per-incident cost is billions of variable-time scalar multiplications, exhausting CPU and stalling DKG/signing — the same class of impact as the nginx HTTP/2 CPU-exhaustion advisory. Additionally, `blame_vartime` is variable-time over data ordered by attacker influence, though the statements themselves are public.

### Likelihood Explanation
Any party able to join a DKG or signing session can trigger this on every attempt, at negligible cost (one invalid Schnorr signature or scalar). It requires no collusion, no key material, and no special position; the only mitigating factor is that deployments with small `n`/`t` see proportionally less amplification, and each trigger aborts the session so repetition requires re-initiation — which is typically cheap for the attacker.

### Recommendation
Bound the total blame-search work: e.g., pre-screen statements cheaply (per-statement `is_identity` checks are equally expensive, so instead cap `blame_vartime` to run only when the caller has authenticated the set), limit `n`/`t` for PedPoP sessions, or make the blame search optional and non-automatic so callers can decide whether identifying the faulty party justifies `O(log n)` additional multiexps. Rate-limit or penalize participants whose statements fail batch verification so repeated triggers are not free.

### Proof of Concept
1. Join a PedPoP session with parameters `t = n` large (e.g., `n = 1024`) as participant `l`.
2. In round 2, send the victim a well-formed `EncryptedMessage` (valid `key`, `pop` encoding via `EncryptedMessage::read`) but with `pop.s += 1`, or encrypt a non-canonical `SecretShare`.
3. The victim's `KeyMachine::calculate_share` runs the `O(n·(t+1))` multiexp, fails, and then `blame_vartime` executes ~`log2(2n)` additional multiexps over slices summing to `~n·(t+1)` pairs each — roughly an order of magnitude more group operations than the honest path, induced by one short attacker message.
4. Repeat per session to continually waste CPU on all honest participants.

  pub fn blame_vartime(&self) -> Option<Id> {
    let mut slice = self.0.as_slice();
    while slice.len() > 1 {
      let split = slice.len() / 2;
      if multiexp_vartime(&flat(&slice[.. split])).is_identity().into() {
        slice = &slice[split ..];
      } else {
        slice = &slice[.. split];
      }
    }

    slice
      .first()
      .filter(|(_, value)| !bool::from(multiexp_vartime(value).is_identity()))
      .map(|(id, _)| *id)
  }

  /// Perform constant time batch verification, and if verification fails, identify one faulty

fn exponential<C: Ciphersuite>(i: Participant, values: &[C::G]) -> Vec<(C::F, C::G)> {
  let i = C::F::from(u16::from(i).into());
  let mut res = Vec::with_capacity(values.len());
  (0 .. values.len()).fold(C::F::ONE, |exp, l| {
    res.push((exp, values[l]));
    exp * i
  });
  res
}

fn share_verification_statements<C: Ciphersuite>(
  target: Participant,
  commitments: &[C::G],
  mut share: Zeroizing<C::F>,
) -> Vec<(C::F, C::G)> {
  // This can be insecurely linearized from n * t to just n using the below sums for a given
  // stripe. Doing so uses naive addition which is subject to malleability. The only way to
  // ensure that malleability isn't present is to use this n * t algorithm, which runs
  // per sender and not as an aggregate of all senders, which also enables blame
  let mut values = exponential::<C>(target, commitments);

  // Perform the share multiplication outside of the multiexp to minimize stack copying
  // While the multiexp BatchVerifier does zeroize its flattened multiexp, and itself, it still
  // converts whatever we give to an iterator and then builds a Vec internally, welcoming copies
  let neg_share_pub = C::generator() * -*share;
  share.zeroize();
  values.push((C::F::ONE, neg_share_pub));

  values
}
