### Title
`mWOMSVBaseRewarder._calExpireForfeit` never applies forfeiture, allowing partially-unlocked lockers to steal 100% of yield meant for fully-locked lockers - (File: wombat/ArbWomUp2.sol / rewards/mWOMSVBaseRewarder.sol)

### Summary
`_calExpireForfeit` in `mWOMSVBaseRewarder.sol` sets `rewardableAmount = _amount` and never queries `mWomSV.getRewardablePercentWAD(_account)`, so `forfeitAmount = _amount - rewardableAmount` is always `0`. Any locker who has called `startUnlock` for a large portion of their `mWomSV` (leaving `rewardablePercentWAD < 1e18`) still receives 100% of accrued rewards via `getReward`/`getRewards`, with none of the "forfeited" share redistributed to fully-locked lockers.

### Finding Description
`_calExpireForfeit` is defined at [1](#0-0) . The intent (confirmed by the sibling contract's naming pattern and the `ForfeitRewardAdded` event/`_queueNewRewardsWithoutTransfer` redistribution path) is to compute `rewardableAmount` as a fraction of `_amount` scaled by the locker's `rewardablePercentWAD` (obtained from `mWomSV`, which exposes `getRewardablePercentWAD` per `wombat/mWomSV.sol`). Instead, the function does:

```
uint256 rewardableAmount = _amount;
if (rewardableAmount > _amount) revert InvalidRewardableAmount();
uint256 forfeitAmount = _amount - rewardableAmount;
```

Since `rewardableAmount` is hard-set to `_amount`, `forfeitAmount` is always `0` regardless of the caller's lock status. This value flows directly into `_sendReward` ( [2](#0-1) ), which is called from `getReward`/`getRewards` ( [3](#0-2) ), reachable by any unprivileged account through `MasterMagpie.claim` (`onlyMasterMagpie` modifier only restricts caller to `MasterMagpie`, not caller identity within it). No reentrancy guard or paused check would block this since it's the expected, unmodified logic path.

An attacker locks `mWomSV`, calls `mWomSV.startUnlock` for most of their stake to reduce `rewardablePercentWAD` far below 100%, waits for `queueNewRewards`/`donateRewards` to accrue `rewardPerTokenStored`, then calls `getReward`. Because `forfeitAmount` is always zero, the entire accrued reward for their (still counted) `balanceOf` amount is paid out with no forfeiture redistributed to fully-locked lockers, violating the intended conservation invariant that partially-unlocked positions forfeit reward proportional to their unlocked percentage.

### Impact Explanation
This is a direct theft of unclaimed yield: fully-locked lockers who are supposed to receive redistributed forfeited rewards (via `_queueNewRewardsWithoutTransfer`) never receive them, because forfeiture never occurs. The affected reward pool (mWOMSV yield distribution in the Wombat integration) always pays claimants 100% of the reward-per-token accrued on their staked balance regardless of their commitment/lock status, undermining the "partial-unlock forfeits reward" design of the mWomSV lock mechanism. This matches the "theft or permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
High likelihood and trivially repeatable: no special capital or privilege is required beyond normal `mWomSV` locking and calling `startUnlock`, both public/permissionless user actions. The bug is deterministic and always triggers (`rewardableAmount > _amount` can never be true, so the code always falls into the "forfeitAmount == 0" branch), making it exploitable by any locker on every claim.

### Recommendation
Fix `_calExpireForfeit` to actually compute `rewardableAmount` using the caller's current `mWomSV.getRewardablePercentWAD(_account)`, e.g.:
```
uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
uint256 rewardableAmount = (_amount * rewardablePercentWAD) / 1e18;
uint256 forfeitAmount = _amount - rewardableAmount;
```
ensuring `forfeitAmount` scales correctly with the account's unlocked percentage, and that the dust-forgiveness threshold (`_amount / 1000`) is preserved for gas efficiency only when the forfeiture truly is negligible.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` in test harness (or reuse existing test fixtures for the Wombat staking module).
2. Have two users, `fullLocker` and `partialLocker`, each lock equal amounts of `mWomSV`.
3. `partialLocker` calls `mWomSV.startUnlock(largeAmount)` such that `mWomSV.getRewardablePercentWAD(partialLocker) < 1e18` (e.g., 20%).
4. As `rewardManager`, call `queueNewRewards(rewardAmount, rewardToken)` to accrue `rewardPerTokenStored`.
5. Call `mWOMSVBaseRewarder.calExpireForfeit(partialLocker, rewardToken)` — assert it returns `0` even though `rewardablePercentWAD = 0.2e18` (expected forfeit ≈ `earnedAmount * 0.8`).
6. Call `getReward(partialLocker, partialLocker)` through `MasterMagpie.claim` and assert `partialLocker` receives the full `earned` amount, not the expected `20%`.
7. Assert `fullLocker`'s subsequent `earned` does not include any forfeited redistribution (i.e., `rewardPerTokenStored` was never incremented via `_queueNewRewardsWithoutTransfer`), confirming the loss of yield that should have accrued to fully-locked users.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
