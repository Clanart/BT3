Confirmed: tokenfactory `CreateDenom` is permissionless — anyone can pay a small fee and create unlimited `factory/{creator}/{subdenom}` denoms [1](#0-0) , and the module's own docs confirm this is by design ("permissionless, due to not needing to resolve name collisions") [2](#0-1) . Combined with the unbounded `MigrateBalance`/`SpendableCoins` loop invoked on every unassociated Cosmos-signed transaction, this produces a directly reachable, high-severity analog of the reported "unbound loop with state change → out-of-gas → permanent failure" bug class.

### Title
Unbounded per-denom balance migration in the EVM address-association ante decorator lets an attacker permanently gas-lock a victim's Cosmos transactions - (File: `x/evm/ante/preprocess.go`, `utils/helpers/associate.go`)

### Summary
Every Cosmos-signed transaction from a not-yet-associated account passes through `EVMAddressDecorator.AnteHandle`, which calls `helpers.AssociationHelper.AssociateAddresses` → `MigrateBalance` for that signer [3](#0-2) . `MigrateBalance` computes `p.bankKeeper.SpendableCoins(ctx, castAddr)` and then `SendCoins` all of them from the cast address to the real Sei address [4](#0-3) . `SpendableCoins`/`GetAllBalances` internally iterate every denom balance entry stored for that address with no upper bound [5](#0-4) . Because tokenfactory denom creation is permissionless and cheap (a flat fee, no whitelist) [6](#0-5) , an attacker can mint an unbounded number of distinct denoms and send dust amounts of each to a victim's un-associated cast address (`sdk.AccAddress(evmAddr[:])`). This runs entirely under the ante pipeline's normal (non-infinite) gas meter set by `SetUpContextDecorator`/`ConsumeGasForTxSizeDecorator` for standard Cosmos transactions — unlike the EVM-tx association path, which switches to an infinite gas meter before calling the same helper [7](#0-6) .

### Finding Description
The root cause mirrors the reported OpenQ bug: an unbounded loop with per-iteration state mutation (`SendCoins` for each denom) is embedded in a code path that must complete for an unrelated core operation (here, "sign a Cosmos tx while unassociated" instead of "claim a bounty"). If the number of denoms held by the victim's cast address is large enough, the gas consumed by `SpendableCoins` iteration plus per-denom `SendCoins` bookkeeping can exceed the gas limit the victim set for their own transaction, causing the ante handler itself to run out of gas before the victim's intended message logic ever executes. Since the decorator runs unconditionally for any un-associated signer on essentially any Cosmos message type, the victim cannot bypass it by choosing a different message — every future Cosmos tx from that address will re-trigger the same unbounded iteration and again exhaust gas, unless the victim manages to push a transaction with a very high (and expensive) gas limit that still exceeds the growing polluted-denom-set cost.

### Impact Explanation
This can permanently prevent an account from submitting *any* successful Cosmos-signed transaction (freezing the ability to associate, transfer, or otherwise use the account) until/unless an operator manually intervenes, since the failure occurs deterministically inside a mandatory ante decorator rather than user-controllable business logic. This matches "permanent freezing" of an account's ability to transact — a fund/functionality freezing impact reachable purely by an unprivileged third party sending arbitrary tokenfactory-denom dust to the victim's known cast address (derived deterministically from their EVM address, discoverable without any interaction from the victim).

### Likelihood Explanation
Likelihood is moderate-to-high: tokenfactory denom creation is cheap and permissionless, cast addresses are deterministically derivable from any known EVM address (no cooperation from the victim required), and any account that has interacted with the EVM (thus revealing an EVM address) but has not yet sent a Cosmos-signed tx to associate is a viable target. The number of denoms needed to exceed a typical transaction's gas budget is bounded but non-trivial to precisely quantify without live gas-cost measurement, which is why this is flagged for validation rather than asserted as trivially cheap.

### Recommendation
Bound the balance-migration loop: cap the number of denoms migrated per association pass and defer the remainder (e.g., via a follow-up governance/keeper-triggered batch job, as noted for other unbounded iterations like `MigrateERCNativePointers`), or charge/require the caller to cover the real gas cost of the migration proportional to the number of denoms discovered before attempting the full transfer, and/or exempt this decorator from failing the entire transaction if migration itself cannot complete within a fixed gas sub-budget.

### Proof of Concept
1. Attacker learns/derives victim's EVM address (public knowledge) and computes `castAddr = sdk.AccAddress(evmAddr[:])`.
2. Attacker submits `N` `MsgCreateDenom` transactions (arbitrarily large `N`, permissionless per `x/tokenfactory/keeper/createdenom.go`) and mints/sends 1 unit of each new denom to `castAddr`.
3. Once `castAddr` holds enough distinct denoms, victim (who has never sent a Cosmos-signed tx before, e.g. only interacted via EVM) submits any ordinary Cosmos tx (e.g., a `MsgSend`) with a normal gas limit.
4. `EVMAddressDecorator.AnteHandle` → `AssociateAddresses` → `MigrateBalance` (`utils/helpers/associate.go:57-72`) iterates and attempts to move all `N` balances; gas consumption from repeated `SpendableCoins`/`SendCoins` store operations exceeds the tx's gas limit, and the ante handler returns an out-of-gas error, rejecting the transaction before the victim's actual message is even processed.
5. Every subsequent Cosmos tx from the victim repeats step 4, permanently blocking that account from any Cosmos-signed activity until the polluted balances are somehow cleared by an operator-level intervention.

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}

	store := ctx.KVStore(k.storeKey)
	balancesStore := prefix.NewStore(store, types.BalancesPrefix)

	iterator := balancesStore.Iterator(nil, nil)

		var balance sdk.Coin
		k.cdc.MustUnmarshal(iterator.Value(), &balance)

		if cb(address, balance) {
			break
		}
	}
}
