### Title
`ReceivedOutput::read` accepts an offset/script_pubkey pair without checking they correspond, allowing crafted bytes to register outputs the key cannot spend — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The UnizenIO2 exploit's bug class is *attacker-supplied instructions executed as trusted actions*: the aggregator interpreted attacker-provided `(target, calldata)` as a legitimate call, so a `transferFrom` drained a victim's allowance. The analog in Serai's in-scope code is `ReceivedOutput::read`, which deserializes an `(offset, output, outpoint)` triple from untrusted bytes and treats it as a spendable output without ever verifying that `script_pubkey` of `output` actually equals the P2TR script derived from `key + offset·G`. The only place that binding is established is `Scanner::scan_transaction` (script→offset map lookup); `read` reconstructs the struct from raw bytes and skips it entirely.

### Finding Description
`ReceivedOutput` couples three facts: a scalar `offset`, a `TxOut`, and an `OutPoint`. Legitimate construction goes through `Scanner`, which maintains `scripts: HashMap<ScriptBuf, Scalar>` keyed by P2TR script and only yields an output when `self.scripts.get(&output.script_pubkey)` hits [1](#0-0) . That lookup is the sole proof that the returned `offset` actually corresponds to the output's script.

`ReceivedOutput::read` performs no such check. It reads `Secp256k1::read_F` for the offset and then consensus-decodes an arbitrary `TxOut` and `OutPoint`, returning them as a coupled "spendable output" [2](#0-1) . Any byte string of the form `scalar || TxOut || OutPoint` is accepted, including pairs where `offset` does not derive `output.script_pubkey` — or where the outpoint references a transaction output that doesn't exist, doesn't match `output`, or isn't the one the script was scanned from.

This mirrors UnizenIO2 precisely: attacker-controlled bytes are interpreted as an actionable specification ("this output is spendable at this offset") with the validation that legitimately binds the fields bypassed.

### Impact Explanation
Two concrete harms, matching the accepted impact criteria:

1. **Funds reported received that are not spendable.** An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., any serialized output list round-tripped through an untrusted channel) can attach a wrong offset to an output, or fabricate an `output`/`outpoint` pair entirely. Downstream code treats the result as a spendable input (it exposes `offset()`, `output()`, `outpoint()`, `value()` directly [3](#0-2) ), so the wallet/coordinator will attempt to sign a spend for a key-path that doesn't control the script — producing an invalid transaction that still burns the threshold-signing session and, depending on the consumer's fee handling, the transaction fees.

2. **Confusion across registered offsets.** Because `register_offset` is surjective, not bijective (it increments until an even point is found and collisions return `None` [4](#0-3) ), a crafted `ReceivedOutput` can pair an output paying to one offset's script with a different offset value, breaking the intended one-to-one accounting between scanned scripts and signing offsets.

Severity: Medium. It cannot directly steal funds (the attacker cannot forge a discrete log), but it causes mis-credited/unspendable "received" outputs and wasted signing rounds/fees from bytes an unprivileged party supplies.

### Likelihood Explanation
The rules explicitly scope `ReceivedOutput::read` as an untrusted-bytes sink, so reachability is presumed wherever serialized outputs transit an untrusted medium. Exploitation only requires assembling bytes — no signature, no key material, no validator position. The limiting factor is impact rather than feasibility: the forgery yields invalid spends, not theft.

### Recommendation
Bind the fields at parse time or remove the footgun:

- Have `ReceivedOutput::read` verify `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` (requires storing/carrying the base key, or adding a `read_with_key(key, reader)` variant), rejecting bytes where the offset doesn't derive the script.
- Alternatively, serialize only `(outpoint)` or `(script_pubkey)` and re-derive `offset` and `output` via `Scanner` at read time, so deserialization can never create a pairing `scan_transaction` wouldn't produce.
- At minimum, document on `read` that the offset–script binding is unverified and callers must re-check against `Scanner`.

### Proof of Concept
```rust
// networks/bitcoin context: attacker crafts bytes for ReceivedOutput::read
// where `offset` does not derive `output.script_pubkey`.

use bitcoin::{TxOut, OutPoint, ScriptBuf, Amount, Txid, hashes::Hash};
use k256::Scalar;

// Any script NOT equal to p2tr_script_buf(scanner_key + offset*G)
let forged = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    // attacker-chosen tweaked key; chosen so offset doesn't map to it
    /* ... */
  ),
};

let mut bytes = vec![];
bytes.extend(Scalar::ONE.to_bytes());              // arbitrary offset
bytes.extend(bitcoin::consensus::encode::serialize(&forged));
bytes.extend(bitcoin::consensus::encode::serialize(
  &OutPoint::new(Txid::all_zeros(), 0),            // arbitrary outpoint
));

// Accepted unconditionally:
let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap();
// ro.offset() == 1, but scanner_key + 1*G does not control ro.output().script_pubkey
// -> downstream treats this as a spendable 100k-sat input; the resulting
//    threshold-signed transaction is invalid and the input is unspendable.
```
Confirmed code facts: `read` performs no script check [5](#0-4) , and the binding exists only in `scan_transaction`'s map lookup [6](#0-5) . Caveat: the exact downstream consumer path from `read` into a signing attempt lives outside the in-scope crates, so the severity rests on the documented intent of `ReceivedOutput` as "a spendable output" [7](#0-6) .

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
