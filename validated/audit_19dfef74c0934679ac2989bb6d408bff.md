## Finding

### Title
Uncontrolled recursion in `PuzzleWithRestrictions.from_memo()` allows a crafted coin memo to crash a wallet client via Python stack exhaustion - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody arrangement (used by the M-of-N/"MIPS" custody framework and by `PlotNFT` pool-singleton sync) directly from an on-chain coin's memo `Program`. When the memo indicates a nested `MofN` structure, the function recurses once per member, and each member's memo can itself encode another nested `MofN`, with no bound on nesting depth. This mirrors the xgrammar bug class (CWE-674, uncontrolled recursion triggered by attacker-controlled nesting depth), except here the "grammar" is a CLVM memo blob parsed by pure Python recursion instead of a bounded/iterative parser.

### Finding Description
`from_memo()` is defined as: [1](#0-0) 

The recursive call at line 285 (`PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos`) is driven entirely by data taken from the untrusted `memo` `Program` passed in — specifically `further_branching_prog`/`puzzle_hint_prog`, decoded via `MofNHint.from_program()`: [2](#0-1) 

There is no depth limit, node-count limit, or CLVM-cost accounting anywhere in this path — unlike `sha256_treehash()` elsewhere in the codebase, which the project's own contracts note is "deliberately iterative to avoid Python recursion limits on deeply nested CLVM." `from_memo()` has no such protection.

This code is reachable from a wallet syncing on-chain state for a custody/PlotNFT singleton: `PlotNFT.get_next_from_coin_spend()` takes the `memo_blob` straight off a `CREATE_COIN` condition produced by a coin spend and feeds it into `PuzzleWithRestrictions.from_memo()`: [3](#0-2) 

The memo content of a `CREATE_COIN` condition is entirely attacker-controlled CLVM output — any party able to produce or influence a spend whose output the syncing wallet must parse (e.g., a counterparty in an M-of-N/pooling arrangement, or a malicious pool/travel spend) can embed an arbitrarily deep chain of nested `MofN` hints in the memo. Since `from_memo()` is exactly the function documented as needing to "reconstruct unknown members/restrictions, including recursive `MofN`, so later wallet code can fill known puzzle implementations by puzzle hash," it is squarely on the path that untrusted, attacker-shaped memo data reaches during normal wallet sync.

### Impact Explanation
A sufficiently deep chain of nested `MofN` member memos causes unbounded Python-level recursion in `from_memo()`. Each level performs `Program.at()`/`as_iter()` calls and constructs new dataclasses before recursing further, so the attacker only needs to encode enough nesting levels to exceed the interpreter's recursion limit (and, since CPython recursion also consumes C stack, deep enough nesting can produce a hard `Segmentation fault` rather than a catchable `RecursionError`, exactly as in the xgrammar PoC). This can crash or hang the wallet process parsing the malicious memo — a spend-triggered denial of service against a wallet client, without requiring signature or full-node cooperation beyond having the crafted spend visible to the victim wallet during sync.

### Likelihood Explanation
Constructing the malicious memo requires no special privilege: a `CREATE_COIN` memo is arbitrary program data chosen by whoever creates the spend. Any counterparty in a custody/pool arrangement that a wallet is tracking (or any transaction whose outputs the wallet must parse to recognize/reconstruct custody state) can supply such a memo. No consensus rule inspects or bounds memo nesting depth before the wallet-side Python parser recurses into it.

### Recommendation
Rewrite `PuzzleWithRestrictions.from_memo()` (and `MofNHint.from_program()`) to use an explicit iterative work-stack instead of Python recursion, following the same pattern used by `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py`. Additionally, enforce an explicit maximum nesting depth (and/or total node count) before descending into a memo's `MofN` structure, raising a clean `ValueError` once the bound is exceeded instead of allowing unbounded recursion.

### Proof of Concept
Construct a memo `Program` shaped like the legitimate output of `PuzzleWithRestrictions.memo()` (namespace `"CHIP-0043"`, restrictions list, `further_branching=1`, and an `MofNHint` with `m=1`), but make its single `member_memos` entry itself be another such memo of the same shape, nested N times (e.g. N = 50,000, analogous to the 30,000-paren xgrammar PoC). Emit this as the `memo_blob` on a `CREATE_COIN` condition of a coin the victim wallet is tracking (e.g. a plot-NFT/pool singleton travel spend, or any custody-framework singleton). When the victim wallet calls `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()` to sync that spend, the recursive descent through N nested `MofN` levels exhausts the Python/C stack, raising `RecursionError` or crashing the process, exactly mirroring the xgrammar `'(' * 30000` PoC pattern.

@dataclass(kw_only=True, frozen=True)
class MofNHint:
    m: int
    member_memos: list[Program]

    def to_program(self) -> Program:
        return Program.to([self.m, self.member_memos])

    @classmethod
    def from_program(cls, prog: Program) -> MofNHint:
        m, member_memos = prog.as_iter()
        return MofNHint(
            m=m.as_int(),
            member_memos=list(member_memos.as_iter()),
