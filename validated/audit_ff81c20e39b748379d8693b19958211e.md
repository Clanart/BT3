### Title
Unvalidated `Participant` indices in PedPoP blame handling cause a HashMap-index panic (remote DoS) — analog of CVE-2018-8740 NULL-deref-on-crafted-input - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2018-8740 is a NULL-pointer dereference triggered when corrupted, attacker-supplied structure feeds internal lookups without validation. The direct analog in Serai is a reachable panic (Rust's equivalent crash) in PedPoP's blame path: `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with `Participant` values taken verbatim from an accusation, with no bounds check against the registered participant set.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take attacker-supplied `sender` and `recipient` `Participant` indices plus a message/proof and call `blame_internal` [1](#0-0) . Inside, two unchecked map lookups exist:

1. `self.enc_keys[&decryptor]` in `decrypt_with_proof` [2](#0-1) . `enc_keys` only contains entries registered in `verify_r1`/`Decryption::register` — i.e., the other `n - 1` participants, never `i` itself and never any out-of-range index [3](#0-2) .
2. `self.commitments[&sender]` in `blame_internal` [4](#0-3) , which panics for any `sender` not in the `1..=n` commitment map.

Unlike `sign()` in FROST, which explicitly validates `included` for bounds, duplicates, and count before any indexing [5](#0-4) , the blame path performs zero validation of `sender`/`recipient` — `Participant::new` only rejects zero [6](#0-5) . A `HashMap` index on a missing key panics in Rust.

Reachability: an accuser controls `sender`, `recipient`, `msg` (an `EncryptedMessage` readable via `EncryptedMessage::read` [7](#0-6) ), and `proof`. To reach the `enc_keys[&decryptor]` lookup, `msg.pop` must verify — trivially satisfiable since the attacker can craft a valid `SchnorrSignature` over a key they chose — and `proof` must be `Some` (any bytes parseable by `EncryptionKeyProof::read` [8](#0-7) ). Setting `recipient` to the victim's own index `i` (never registered, since `register` is only called for other parties [9](#0-8) ) or to any value `> n` triggers the panic before DLEq verification runs.

### Impact Explanation
A single crafted blame accusation crashes the victim's key-generation process (`panic!` in `HashMap` indexing). This aborts the DKG/reshare session and, depending on the host, the node itself — mirroring the CVE's availability-only impact (CVSS A:H). Since each DKG participant can submit accusations, any one party can reliably deny the protocol to everyone.

### Likelihood Explanation
Triggering requires only sending a structurally valid accusation naming an unregistered `recipient` (e.g., the victim's own `i`, or `Participant(n+1)`), with a self-signed `EncryptedMessage` and any syntactically valid `EncryptionKeyProof`. No collusion, stolen keys, or invalid-curve inputs needed — pure index confusion, exactly the "corrupted schema → unchecked lookup → crash" shape of the CVE.

### Recommendation
Validate `sender` and `recipient` in `BlameMachine::blame`/`AdditionalBlameMachine::blame`/`blame_internal` — e.g., reject indices not present in `commitments`/`enc_keys` (or outside `1..=n`, and `recipient == i`) and return a defined error instead of indexing. Replace `map[&k]` with `map.get(&k)` returning `PedPoPError`/`DecryptionError` on absence.

### Proof of Concept
Conceptual: after a PedPoP round completes into `BlameMachine`, submit a blame accusation `blame(sender = honest_p, recipient = self.i /* or Participant(n+1) */, msg = attacker_signed_encrypted_message, proof = Some(parsed_proof))`. `msg.pop.verify` passes (attacker knows the key); the `proof.is_some()` branch evaluates `self.enc_keys[&decryptor]` where `decryptor` was never registered → `HashMap` index panic → process abort. Same for `self.commitments[&sender]` if `sender ∉ 1..=n`.

Caveat: I verified the panic sites and their reachability from code inspection; whether the surrounding processor layer sanitizes accusation indices before calling `blame` was not confirmable within scope — if the caller already bounds-checks, impact reduces to a latent library panic.

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
