### Title
`ThresholdKeys::read` pre-allocates a `Vec` of `n` field elements from an attacker-controlled length before consuming a single scalar, enabling a deserialization memory-exhaustion bomb - (File: crypto/dkg/src/lib.rs)

### Summary
The decompression-bomb class (a small input expands into disproportionate memory consumption, CWE-400) maps onto `ThresholdKeys::<C>::read`. The serialized format starts with a 4-byte curve-ID length, the curve ID, then three `u16`s (`t`, `n`, `i`), then a 1-byte interpolation tag. When the tag is `0` (`Interpolation::Constant`), the reader executes `Vec::with_capacity(usize::from(n))` for field elements — up to `n = 0xFFFF = 65535` scalars — *before* reading any scalar bytes from the stream [1](#0-0) . An unprivileged party feeding untrusted bytes to `ThresholdKeys::read` (an explicitly in-scope reachable API) can therefore force a multi-megabyte heap allocation with only ~10 bytes of input.

### Finding Description
`ThresholdKeys::read` reads the header fields `t`, `n`, `i` [2](#0-1)  and then, for interpolation byte `0`, immediately calls `Vec::with_capacity(usize::from(n))` and loops `n` times calling `C::read_F(reader)` [3](#0-2) . The capacity reservation happens before the first `read_F`, so the allocation succeeds even if the stream then immediately returns EOF — `read_exact` errors unwind *after* the ~2 MiB (65535 × 32-byte `F`, more for curves with wider representations such as `ed448`) buffer has been committed. No validation of `n` occurs before the allocation; `ThresholdParams::new`/`ThresholdKeys::new` checks only run at the end of `read` [4](#0-3) .

For contrast, `SchnorrAggregate::read` uses `vec![]` with `push` — memory there is proportional to bytes actually present, so it is not exploitable [5](#0-4) . The `ThresholdKeys::read` path is unique in allocating on a declared length prior to input consumption.

### Impact Explanation
An attacker who can submit serialized `ThresholdKeys` blobs (e.g., key material distributed during DKG re-shares, recovery, or coordinator flows) achieves an amplification of roughly 4–5 orders of magnitude: a ~10-byte payload forces a ~2 MiB+ allocation. Repeated submissions — or simply spraying many such blobs in one batch of key uploads — drive allocator pressure, GC/allocator churn, and eventual OOM abort of the signing node. This is a remote, unauthenticated denial of service against availability of a validator/signer, mirroring the original advisory's memory-consumption DoS.

### Likelihood Explanation
Any context where `ThresholdKeys::read`/`deserialize` is applied to bytes from other participants or peers is reachable by an unprivileged protocol party — no secret material or validator status is required, just the ability to send a blob that gets deserialized. Cost to the attacker is a handful of bytes per allocation. Impact is capped per-request (n is a `u16`, so max ~2–4 MiB per call rather than unbounded), and no secret leakage or incorrect math results — the process simply allocates then errors — so the realistic severity is Medium.

### Recommendation
Do not size allocations from unvalidated lengths. Either:
- Drop the `Vec::with_capacity(usize::from(n))` pre-reservation and let `push` grow with bytes actually read (memory then stays proportional to input), or
- Validate `t`/`n`/`i` via `ThresholdParams::new` *before* any allocation, and cap `n` at a sane protocol maximum (e.g., a few hundred participants) before allocating.

The same pattern should be checked anywhere else a declared count drives `with_capacity` ahead of the reads (none found elsewhere in scope: `Commitments::read` sizes by caller-supplied `params.t()`, not stream data [6](#0-5) ; `MultiDLEqProof::read` grows incrementally [7](#0-6) ).

### Proof of Concept
```rust
// For any C: Ciphersuite with C::ID = e.g. b"ristretto" / ed25519-dalek
let mut payload = Vec::new();
payload.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
payload.extend(C::ID);                      // curve ID must match so we pass the check
payload.extend(1u16.to_le_bytes());         // t = 1
payload.extend(u16::MAX.to_le_bytes());     // n = 65535  <-- attacker-controlled count
payload.extend(1u16.to_le_bytes());         // i = 1 (non-zero Participant)
payload.push(0u8);                          // Interpolation::Constant
// NO scalar bytes follow.

// Executes Vec::with_capacity(65535) of C::F (~2+ MiB) before the first read_F
// hits EOF and returns Err — the allocation already happened.
let _ = ThresholdKeys::<C>::read(&mut &payload[..]); // Err, after ~2 MiB alloc
```
Repeated calls amplify attacker bytes → heap memory at a ratio of roughly 10 bytes in : 2 MiB allocated, exhausting memory on any node that deserializes attacker-supplied `ThresholdKeys`.
