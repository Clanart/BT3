### Title
`ReceivedOutput::read` performs no consistency check between the claimed key offset and the output's `script_pubkey`, so untrusted bytes can fabricate an unspendable "received" output - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_transaction` only emits a `ReceivedOutput` after confirming `output.script_pubkey` matches a registered tweaked key (`self.scripts.get(&output.script_pubkey)`, `networks/bitcoin/src/wallet/mod.rs:205`). However, `ReceivedOutput::read` — the deserialization path used to reload scanned outputs from persisted/untrusted bytes — reads `offset`, `TxOut`, and `OutPoint` and returns the struct without re-checking that `p2tr_script_buf(key + G*offset) == output.script_pubkey`, or that the outpoint is real. This is a missing validation check on an attacker-influenced input path, analogous to the missing permission check in CVE-2019-10465.

### Finding Description
`ReceivedOutput::read` at `networks/bitcoin/src/wallet/mod.rs:122-134` deserializes three independent fields:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

The critical invariant established at scan time — that the `offset` field is the discrete-log tweak which makes `key + G*offset` equal the tweaked key encoded in `output.script_pubkey` — is never re-verified on this path. There is no `Scanner`/`key` context available in `read`, and no check that `outpoint` references an existing UTXO paying to that script. `ReceivedOutput::serialize`/`write` (`mod.rs:137-148`) show this type is intended to cross a trust boundary (disk/network), so bytes from an untrusted source reach `read` directly.

### Impact Explanation
An attacker who can feed crafted bytes to `ReceivedOutput::read` (e.g., malicious or corrupted persistence, an untrusted peer supplying scanned outputs) causes the wallet to report an output as received and spendable when it is not:

- The `TxOut` may carry an arbitrary `script_pubkey` unrelated to `key + G*offset`, so `ReceivedOutput::value()` reports funds that downstream signing cannot actually unlock — the produced signature is for the wrong tweaked key and the spend fails script verification.
- The `OutPoint` may reference a nonexistent or third-party UTXO, causing the node to construct and broadcast transactions that are guaranteed invalid, corrupting balance accounting and liveness of the spend pipeline.

This matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Reachable by any unprivileged party able to supply bytes to the `ReceivedOutput::read` path with no secret knowledge required — purely a serialization-format attack. The concrete exposure depends on how integrators transport/store `ReceivedOutput`s (the provided `serialize`/`read` pair makes such transport a designed use). Likelihood is moderate: it requires a byte-injection vector, but needs no cryptographic capability.

### Recommendation
Bind the offset to the key context on deserialization. Either (a) move deserialization onto `Scanner` (e.g., `Scanner::read_output`) so it can verify `self.scripts.contains_key(&output.script_pubkey)` and that the stored offset equals the registered one, or (b) serialize and verify a commitment to the scanner key inside `ReceivedOutput` and recompute `p2tr_script_buf(key + G*offset)` on read. Additionally, consumers should confirm the referenced outpoint exists on-chain with the expected script before treating the output as spendable (as `scan_block` already warns for coinbase maturity at `mod.rs:216-220`).

### Proof of Concept
1. Build a `Scanner` for group key `K` and register offset `o`; obtain script `S = p2tr(K + G·o)`.
2. Craft bytes: `offset = o' (≠ o)` followed by `TxOut{ script_pubkey: S' }` where `S'` pays to an attacker key, plus an `OutPoint` pointing to any real UTXO of the attacker's choosing.
3. Feed to `ReceivedOutput::read` — it succeeds and yields a `ReceivedOutput` reporting `value()` as wallet funds.
4. The wallet attempts to spend outpoint `O` using tweaked key `K + G·o'`; the signature does not satisfy `S'` (and `O` may not even pay to `S'`), so the output is unspendable despite being reported received.
