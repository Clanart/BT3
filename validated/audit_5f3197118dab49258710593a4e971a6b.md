### Title
`ReceivedOutput::read` accepts an offset never validated against the output's `script_pubkey`, allowing unspendable funds to be reported as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The referenced issue is a Chainlink adaptor that reads `latestRoundData()` but fails to validate all returned fields (`roundId`/`answeredInRound`), so a stale/inconsistent result is accepted. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`: it deserializes the three fields of a `ReceivedOutput` (`offset`, `output`, `outpoint`) but never checks that `output.script_pubkey` is actually the P2TR script derived from `key + offset * G`. The value is accepted as "funds received" even though the claimed offset cannot spend it — the same failure shape as accepting a price without checking the round fields that prove it's the answer to the query.

### Finding Description
`Scanner::scan_transaction` is the only honest producer of `ReceivedOutput`s, and it guarantees the invariant `p2tr_script_buf(key + offset*G) == output.script_pubkey` by construction, since it only emits an output when `self.scripts.get(&output.script_pubkey)` returns a registered offset [1](#0-0) . However, `ReceivedOutput::read` accepts untrusted bytes and reconstructs `offset`, `output`, and `outpoint` independently, with no consistency check binding the offset to the `script_pubkey` [2](#0-1) . Any byte string containing a canonical scalar, a decodable `TxOut`, and a decodable `OutPoint` is accepted as a spendable received output, regardless of whether the offset corresponds to the script.

The discrepancy is only detected later: `SignableTransaction::multisig` recomputes `p2tr_script_buf(keys.offset(offset).group_key())` and returns `None` if it doesn't equal `prevouts[i].script_pubkey` [3](#0-2) . By then, however, `SignableTransaction::new` has already accounted the forged output's `value` as spendable input balance [4](#0-3) . Like the oracle bug, a multi-field result is consumed while only some fields (decodability, canonicality) are validated and the field that proves consistency is skipped.

### Impact Explanation
An attacker who can feed bytes to `ReceivedOutput::read` (a deserialization entry point on untrusted data) can cause funds to be reported as received that are not spendable: the wallet/scanner accounting records an output with attacker-chosen `value`, `script_pubkey`, and `offset`, but the offset will not authorize a signature for that script. Downstream transaction construction then selects these phantom inputs (`input_sat` includes them [4](#0-3) ), producing a `SignableTransaction` whose `multisig` construction fails, or worse, a transaction whose declared `fee()`/`needed_fee` math is computed against balance that does not exist. This matches the "funds reported received that are not spendable" impact class.

### Likelihood Explanation
Reachability requires an adversary-controlled byte stream reaching `ReceivedOutput::read` rather than outputs produced by `Scanner::scan_transaction` itself. When `ReceivedOutput`s are round-tripped through storage or messages written by anything other than the local scanner (e.g., forwarded output records), the missing invariant check is exercised with no honest-but-unlucky precondition — it is a deterministic missing validation, like the missing `answeredInRound` check. Severity is Medium: the forged output cannot be spent (the `multisig` binding check prevents actual fund theft), so the impact is incorrect accounting / stuck funds rather than key recovery or forgery.

### Recommendation
Bind the offset to the script at the deserialization boundary, mirroring the check `Scanner` and `multisig` already perform. `ReceivedOutput::read` needs the scanner's base key (or the expected `script_pubkey`) passed as a parameter, and should verify `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset) == Some(output.script_pubkey)` before returning — analogous to the recommendation to check `answeredInRound >= roundId` so every consumed field is validated. Alternatively, derive the script from the offset rather than trusting the serialized `TxOut`'s `script_pubkey` for ownership purposes.

```rust
use bitcoin::{Amount, TxOut, OutPoint, ScriptBuf, Txid, hashes::Hash};
use k256::{Scalar, ProjectivePoint};

// Build a ReceivedOutput whose `offset` does not correspond to `script_pubkey`:
// offset = 0 claims ownership by the base key, but script_pubkey pays to an
// arbitrary attacker key the validator set cannot sign for.
let mut buf = vec![];
buf.extend(Scalar::ZERO.to_bytes()); // offset: claims base-key spendability
let attacker_script = p2tr_script_buf(attacker_controlled_even_key).unwrap();
let fake_out = TxOut { value: Amount::from_sat(1_000_000), script_pubkey: attacker_script };
buf.extend(bitcoin::consensus::serialize(&fake_out));
buf.extend(bitcoin::consensus::serialize(
    &OutPoint::new(Txid::from_raw_hash(...), 0),
));

// Accepted without error — no check that offset 0 matches the script
let received = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(received.value(), 1_000_000); // reported as received

// Yet it can never be signed for:
// SignableTransaction::multisig returns None because
// p2tr_script_buf(keys.offset(0).group_key()) != attacker_script
```

```rust
    let output;

  }
```

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
