### Title
Certificate-error suppression is keyed only by URL and never re-validated against the approved certificate, allowing silent MITM bypass for the life of the session - (File: `app/src/lib/suppress-certificate-error.ts`)

### Summary
The reported veRAACToken bug is a case of "grant a security bypass once, then never scope/reset it, so it silently keeps applying to future, different situations." The closest analog found in this Desktop codebase is the certificate-error suppression mechanism: once a user clicks through an untrusted-certificate warning for a given URL, GitHub Desktop remembers that decision in a `Set<string>` keyed **only by URL string**, with no binding to the specific certificate (fingerprint/serial) that was approved, and no re-validation on subsequent requests.

### Finding Description
`suppressCertificateErrorFor`, `clearCertificateErrorSuppressionFor`, and `isCertificateErrorSuppressedFor` operate on a single module-level `Set<string>` of URLs: [1](#0-0) 

The intent (visible from the UI flow) is that when a certificate error occurs, the user is shown an `UntrustedCertificate` dialog and, if they choose to continue, the *native OS* certificate-trust dialog is invoked: [2](#0-1) [3](#0-2) 

The corrupted invariant is the same as in the veRAAC report: an authorization/bypass state (`suppressedUrls` entry, analogous to `emergencyWithdrawDelay`) is created by one specific approval event (one specific certificate, at one specific time) but the guard that later consumes it (`isCertificateErrorSuppressedFor(url)`) only checks the URL, not the certificate identity that was actually approved. Just as `cancelEmergencyAction()` deleted the timelock entry but forgot to also reset `emergencyWithdrawDelay` — leaving the downstream check (`emergencyWithdrawDelay == 0`) satisfied indefinitely — here the suppression check has no certificate-scoping "reset," so it stays satisfied indefinitely for that URL regardless of which certificate is presented afterward.

### Impact Explanation
An attacker who can intercept traffic to a host the user has previously (legitimately, e.g. a GitHub Enterprise self-signed cert) approved once — for example via a rogue Wi‑Fi AP, corporate-network MITM proxy, or DNS/routing hijack later in the same app session — can present an entirely different, forged certificate for that same URL. Because the guard only compares the URL string and not the certificate fingerprint, Desktop will treat the connection as already trusted and continue talking to the attacker-controlled endpoint without ever re-prompting the user. This can lead to credential/token exfiltration (Git HTTPS credentials, API tokens) and tampering with API/Git traffic for that host, i.e. silent corruption of what gets fetched/pushed and unauthorized capture of authentication material — squarely in the "credential exfiltration" / "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The precondition (one legitimate cert warning previously accepted for a host, e.g. an Enterprise server with a self-signed/expired cert, which the docs show is an anticipated real-world scenario — see `docs/technical/proxies.md`) is common enough in GitHub Enterprise / MITM-proxy environments. Once that precondition is met, exploitation only requires the attacker to intercept a subsequent connection to the same URL — no additional user action, no local access, and no leaked credentials are required, matching the "attacker controls a git remote/proxy response" scope in the task.

### Recommendation
Bind the suppression decision to the certificate identity, not just the URL — e.g., key the `Set` (or map) by `${url}|${certificate.fingerprint}` (or store the fingerprint and compare it on every check), and/or clear the suppression whenever the presented certificate's fingerprint changes from the one originally approved. This mirrors the report's fix of explicitly resetting the persisted bypass state so a new instance of the same certificate check must be re-approved rather than inheriting a stale, indefinite exception.

### Proof of Concept
1. User connects to `https://ghe.example.com` which presents a self-signed certificate; Desktop shows the `UntrustedCertificate` dialog and the user clicks "Add certificate" once (a legitimate first-time trust decision for their own server).
2. `suppressCertificateErrorFor('https://ghe.example.com')` is recorded for that URL (exact call site is in `app/src/lib/api.ts`, which I was not able to fully inspect within the available iterations — this should be verified in a follow-up session).
3. Later in the same app session, an attacker performs a MITM (rogue AP / hijacked route / malicious proxy) against `https://ghe.example.com` and presents a completely different, forged certificate.
4. `isCertificateErrorSuppressedFor('https://ghe.example.com')` returns `true` because only the URL was checked, so Desktop proceeds with the connection to the attacker's certificate without prompting the user again.

Note on confidence: I was able to fully confirm the `Set<string>` design and its URL-only keying in `suppress-certificate-error.ts`, and the dialog/IPC flow that produces the user's initial trust decision. I could not, within the tool budget, fully trace every call site in `app/src/lib/api.ts` that invokes `suppressCertificateErrorFor`/`clearCertificateErrorSuppressionFor` to confirm whether `clearCertificateErrorSuppressionFor` is ever invoked in a way that would mitigate this (e.g., on process restart only, or per-request). That remaining verification should be done by reading `app/src/lib/api.ts` in full before treating this as a confirmed, ready-to-fix issue.

```typescript
const suppressedUrls = new Set<string>()

export function suppressCertificateErrorFor(url: string) {
  suppressedUrls.add(url)
}

export function clearCertificateErrorSuppressionFor(url: string) {
  suppressedUrls.delete(url)
}

export function isCertificateErrorSuppressedFor(url: string) {
  return suppressedUrls.has(url)
}
```
