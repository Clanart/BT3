## Finding: NFT approval granting bypasses ownership check in the CW721-wraps-ERC721 example contract

### Title
Unauthorized ERC721 `approve` granting due to missing ownership check in `execute_approve` - (File: `example/cosmwasm/cw721/src/contract.rs`)

### Summary
In the sei-chain `ERC721toCW721Pointer` wrapping mechanism, any CosmWasm account can call the wrapper's `Approve` execute message for a `token_id` it does not own, because — unlike `execute_transfer_nft` — `execute_approve` never validates that the CW message sender (`info.sender`) is the actual owner of the token before forwarding an `approve` call to the underlying ERC721 contract.

### Finding Description
The `execute_approve` handler builds a delegatecall payload using only `spender` and `token_id`, discarding `info.sender` entirely: [1](#0-0) 

Compare this to `transfer_nft`, which explicitly resolves the real owner by querying `erc721_owner(info.sender.to_string(), ...)` before constructing the transfer payload, ensuring the caller's authorization is checked against the actual token owner: [2](#0-1) 

The `erc721_approve_payload` querier function only forwards `spender` and `token_id` — it has no `caller`/`from`/owner parameter at all, so there is no channel through which the CosmWasm message sender's identity can be checked against token ownership before the payload is generated: [3](#0-2) 

Because the resulting call is executed as `EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload }`, the underlying real `ERC721.approve()` executes with `msg.sender` equal to the wrapper contract's own EVM identity (the pointer/wrapper contract that custodies all underlying tokens), not the identity of the CW message sender. The real `ERC721.approve()` only checks `msg.sender == owner || isApprovedForAll[owner][msg.sender]`: [4](#0-3) 

Since the wrapper contract itself is always the on-chain owner (or perpetually authorized caller) at the real-ERC721 level regardless of which CW account issues the `Approve` message, this check trivially passes for *any* CW sender. There is no equivalent of Solidity's `_isApprovedOrOwner` performed against `info.sender` inside `execute_approve` prior to delegatecalling.

This mirrors the reported `CouncilMember.sol` bug class: a state-mutating "grant transfer rights" operation (`approve`/`transferFrom`) is reachable without the permission check that the design intends (only the actual token owner should be able to approve a spender for their token).

### Impact Explanation
Any account can call the `Approve` execute message on an `ERC721toCW721Pointer`-style wrapper contract for a `token_id` it does not own, granting an attacker-controlled `spender` address approval over that token. The `spender` can subsequently call `transferFrom` on the underlying ERC721 (or the pointer) to steal the NFT from its rightful owner. This is a direct, unauthorized-transfer/fund-loss vulnerability affecting any NFT collection wrapped through this pattern.

### Likelihood Explanation
High reachability: any public EVM/CosmWasm user who can submit a `MsgExecuteContract` (`Approve{spender, token_id}`) against a deployed instance of this wrapper contract can trigger the flow, no special privileges or association state beyond a funded account are required.

### Recommendation
`execute_approve` must resolve and validate the real owner of `token_id` using `info.sender` (as `erc721_owner` already does for `transfer_nft`) before constructing/forwarding the approve payload, rejecting the call if `info.sender` is not the owner or an existing approved operator. The `erc721_approve_payload`/`Erc721ApprovePayload` query interface should be extended to accept and enforce a `caller`/`from` parameter analogous to `Erc721TransferPayload`.

### Proof of Concept
1. Deploy an `ERC721toCW721Pointer`-style wrapper for an ERC721 collection owned by Alice's account (`tokenId=1`).
2. Attacker (unrelated account, e.g. Mallory) sends `MsgExecuteContract` with `ExecuteMsg::Approve { spender: mallory_evm_addr, token_id: "1" }` to the wrapper contract.
3. `execute_approve` (contract.rs:106-132) never checks that Mallory owns `tokenId=1`; it builds `erc721_approve_payload(mallory_evm_addr, "1")` and issues `EvmMsg::DelegateCallEvm` to the real ERC721 contract.
4. Because the delegatecall's `msg.sender` at the real ERC721 level is the wrapper contract's own address (which is the recorded owner/operator for all wrapped tokens), `ERC721.approve()`'s owner check passes trivially.
5. Mallory (or her `spender` address) now calls `transferFrom(alice, mallory, 1)` and steals Alice's NFT.

I could not fully trace the Go-side keeper implementation of `Erc721ApprovePayload` (in `x/evm/client/wasm/bindings/queries.go` / `wasmbinding/queries.go`) within the available iterations to confirm there is no additional server-side authorization check bolted onto that query handler; this final link should be verified directly in the codebase to conclusively confirm exploitability.

```rust
pub fn execute_approve(
    deps: DepsMut<EvmQueryWrapper>,
    info: MessageInfo,
    spender: String,
    token_id: String,
    approved: bool,
) -> Result<Response<EvmMsg>, ContractError> {
    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let mut payload_spender = spender.clone();
    let mut action = "approve";
    if !approved {
        payload_spender = "".to_string();
        action = "revoke";
    }
    let payload = querier.erc721_approve_payload(payload_spender, token_id.clone())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("action", action)
        .add_attribute("token_id", token_id)
        .add_attribute("sender", info.sender)
        .add_attribute("spender", spender.clone())
        .add_message(msg);

    Ok(res)
}
```

```rust
fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
```
