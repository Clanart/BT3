Based on my research, I found a reachable analog to the "division-by-zero via total-amount rounding to zero" bug class in the Kaia reward-distribution code path.

### Title
Unvalidated zero-denominator division in `consolidatedNode.Split()` can panic node during deferred reward distribution - (File: `kaiax/staking/staking_info.go`)

### Summary
The reported bug is a classic "total amount rounds to zero, causing a division-by-zero" DoS. The Kaia analog exists in `consolidatedNode.Split()`, used when consensus-liquidity (CL) staking rewards are split between a validator's CN stake and its CL pool stake during deferred reward computation.

### Finding Description
`consolidatedNode.Split()` divides by the sum of a validator's CN staking amount and its CL staking amount without checking that the sum is nonzero: [1](#0-0) 

Both `StakingAmount` and `CLStakingInfo.CLStakingAmount` are derived by rounding down raw wei amounts to whole KAIA units: [2](#0-1) [3](#0-2) 

If a validator's on-chain staking amount and its CL staking amount are both below 1 KAIA (or otherwise round down to 0 while still being included in `ConsolidatedNodes()`), `totalAmount` in `Split()` becomes `0`, and `big.Int.Div(x, 0)` panics in Go (unlike Solidity's `require`/`revert`, this is an unrecoverable runtime panic).

`Split()` is invoked from the deferred-reward flow (both classic and Flex reward calculation) whenever a consolidated node passes the staking eligibility gate and has a non-nil `CLStakingInfo`: [4](#0-3) [5](#0-4) 

The eligibility gate (`cn.StakingAmount >= minStake`) is controlled by the `reward.minstake` governance parameter: [6](#0-5) 

Under default mainnet parameters `MinimumStake` is large (5,000,000 KAIA), so `StakingAmount` cannot be simultaneously `>= minStake` and `0`. However, on any network/testnet/permissionless configuration where `reward.minstake` is set low (including `0`, which is a format-valid governance value) or under the permissionless/effective-stake path where amounts are computed differently, a validator (an otherwise unprivileged staking/CL participant, not requiring any special privilege beyond normal staking and CL-pool registration) can arrange both its CN and CL stakes to round down to `0` KAIA while still appearing in `ConsolidatedNodes()`, triggering the panic during `FinalizeState`/reward computation for that block on every full node.

### Impact Explanation
A panic during block finalization (`FinalizeState`) is a chain-halting event: every honest node that processes the affected block crashes, since Go's `big.Int.Div` does not return an error — it panics the goroutine, which is not gracefully recoverable if uncaught in the block-processing hot path. This is analogous to the original finding's DoS (permanent inability to proceed) but is more severe because it does not merely deadlock one contract — it can crash consensus/full nodes processing the block, producing a chain-wide liveness failure rather than a contract-scoped one.

### Likelihood Explanation
Likelihood is Medium: it requires a specific, non-default governance/network configuration (`reward.minstake` set low or `0`, or an effective-stake/permissionless configuration where sub-1-KAIA stakes are retained as reward-eligible) combined with a validator arranging both CN and CL rounding to zero. This is not exploitable against Kaia Mainnet's default parameters directly, but is reachable on any chain instance (e.g., private/permissionless networks, or after a future governance parameter change) without needing any privileged action beyond ordinary staking/CL registration — hence it remains a code-level defect independent of the specific parameter values used at any given time.

### Recommendation
Add an explicit zero-check in `consolidatedNode.Split()` before dividing, e.g., if `totalAmount.Sign() == 0`, return `(amount, big.NewInt(0))` (or `(big.NewInt(0), big.NewInt(0))`) instead of performing the division. Additionally, consider validating in `assignStakingRewards`/`assignStakingRewardsFlex` that a consolidated node's total staking amount (CN+CL) is strictly positive before calling `Split()`, decoupled from the `minStake` governance parameter value.

### Proof of Concept
Conceptual reproduction (not executable against mainnet defaults):
1. Configure/observe a chain where `reward.minstake` (governance `MinimumStake`) is `0` or otherwise low enough that a node with `StakingAmount == 0` KAIA (rounded down) is still returned by `ConsolidatedNodes()`.
2. Have that validator register a `CLStakingInfo` via the CL registry with a staked amount below `1 KAIA` so `CLStakingAmount` also rounds down to `0` in `parseCallResult`/`parsePermissionlessCallResult`.
3. When a block is finalized with `IsPrague` active, `assignStakingRewards` (or the Flex variant) will include this node with `cnTotalStakingAmount = 0`, and if it also has `excess/reward > 0` from the shared budget's rounding, `cn.Split(reward)` is invoked with `totalAmount = 0`, causing `big.Int.Div` to panic and crash the node's block-processing goroutine. func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
```go
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
