## Analysis

The external report's core broken invariant: an unconditional native-ETH push (`.call{value}("")`) whose failure reverts the *entire* state-changing function, letting a single uncooperative recipient block settlement/refund for everyone bundled in that call.

Hyperbridge's `IntentsBase._withdraw` (called from `ExtrinsicIntents.onAccept` for both `RedeemEscrow` and `RefundEscrow`, and from `onGetResponse`) has exactly this pattern: it iterates all escrowed tokens for a commitment and reverts the whole loop, and thus the whole `onAccept`, if the beneficiary can't accept a native transfer. [1](#0-0) 

### Title
`IntentsBase._withdraw` reverts on non-ETH-receiving beneficiary, permanently blocking escrow release/refund - (evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`onAccept` handles `RedeemEscrow`/`RefundEscrow` requests by calling `_withdraw`, which does a raw `beneficiary.call{value: amount}("")` for the native-token leg and reverts with `InsufficientNativeToken` if that call fails. [2](#0-1) 

### Finding Description
`order.user` and `order.output.beneficiary` are attacker-controlled `bytes32` addresses supplied when the order is placed/filled on either chain — there is no restriction requiring an EOA or a contract implementing `receive`/`fallback`. If a user places (or a solver fills) an order where the eventual beneficiary of the *input-side* escrow is a contract with no payable fallback (deliberately or incidentally), the cross-chain `RedeemEscrow`/`RefundEscrow` message that Hyperbridge delivers via `EvmHost.dispatchIncoming` will call `onAccept → _withdraw`, and the native-ETH transfer to that beneficiary will fail, reverting the whole function. [3](#0-2)  shows that `EvmHost.dispatchIncoming` treats a reverting `onAccept` call as retryable by deleting the request receipt rather than reverting the whole batch — but because the calldata itself is fixed (the same `WithdrawalRequest` derived from the immutable on-chain `Order`), retrying calls the identical `_withdraw` with the identical non-payable beneficiary, so the call fails on every retry forever. The escrow for that commitment (`_orders[commitment][token]`) is never decremented and the `_filled[commitment]` mapping is never set, so the funds are permanently stuck in the `IntentGateway`/`IntentsBase` contract with no admin sweep path for a *specific user's* escrow (only `SweepDust` for protocol dust exists).

This differs from the mitigated `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which explicitly fall back to a WETH-wrapped ERC-20 transfer when the native push fails [4](#0-3)  — the intentsv2 escrow-release path (`IntentsBase._withdraw`) has no such fallback for the native-token leg.

### Impact Explanation
This matches the bounty's "loss/lock of funds" and "logic attack" categories: an unprivileged actor (the order creator, who fully controls `order.user`/beneficiary addresses at order-placement time) can cause their own native-token escrow — or, more importantly, cause a *solver's* redeemed escrow (beneficiary = solver's `msg.sender` on fill, embedded into the `RedeemEscrow` request by `_fillCrossChain`) — to become permanently unretrievable if that address happens to be/becomes a non-payable contract. Because `_withdraw` loops over *all* `body.tokens` in a single transaction and reverts atomically on any single leg's failure, ERC-20 legs bundled in the same commitment are locked alongside the native leg even though they would have succeeded independently.

### Likelihood Explanation
Reaching this path requires no relayer/prover/admin collusion — it is a pure consequence of native asset transfer via low-level `call` in a delivery path that is otherwise fully permissionless (any order creator picks `order.user`; any solver's `msg.sender` becomes the beneficiary in `_fillCrossChain`/`ExtrinsicIntents`). A solver operating from a smart-contract wallet without a payable fallback, or a griefer deliberately using a non-payable contract as an order's beneficiary/user address, triggers it directly. Likelihood is Medium: it requires the affected party's address to lack a receive/fallback for ETH, which is a realistic but not universal condition (matches the C4 judge's "Medium risk" classification for the analogous PartyDAO bug).

### Recommendation
Add a WETH-wrap fallback in `IntentsBase._withdraw` for the `token == address(0)` branch, mirroring `WrappedHyperFungibleToken.onAccept`: on `!sent`, wrap the ETH (`IWETH.deposit{value: amount}()`) and `safeTransfer` the WETH to the beneficiary instead of reverting. Alternatively, decouple failed native transfers into a per-beneficiary pull-based escrow (store failed amount, let beneficiary call a separate `claim()` later) so one bad beneficiary cannot block the whole withdrawal loop, and so that other tokens in the same `body.tokens` array are not blocked by one failing leg.

### Proof of Concept
1. Deploy a `Beneficiary` contract with no `receive()`/`fallback()` (or one that reverts).
2. Place a cross-chain `Order` with `order.user = address(Beneficiary)` and an input asset of `token == address(0)` (native ETH escrow).
3. On the destination chain, a solver calls `fillOrder`, which dispatches a `RedeemEscrow` `WithdrawalRequest{beneficiary: filler}` back to source — or, to hit the `order.user` path, let the order expire and call `_cancelFromDest`, which dispatches `RefundEscrow` with `beneficiary: order.user = Beneficiary`.
4. Hyperbridge delivers this POST to the source-chain `IntentGateway`; `EvmHost.dispatchIncoming` calls `onAccept`, which calls `_withdraw`, which attempts `Beneficiary.call{value: amount}("")`.
5. The call fails (`!sent`), `_withdraw` reverts with `InsufficientNativeToken`; `dispatchIncoming` catches the revert and deletes the request receipt, allowing (only) unlimited retries of the exact same failing call.
6. The escrowed ETH remains locked in the gateway indefinitely — `_orders[commitment][address(0)]` is never decremented and `_filled[commitment]` is never set, with no alternate recovery path exposed to the beneficiary or governance for this specific commitment. [5](#0-4) [6](#0-5)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
