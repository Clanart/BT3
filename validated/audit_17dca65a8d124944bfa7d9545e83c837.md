### Title
`SignableTransaction::new` omits the OP_RETURN data output from weight/fee calculation, producing transactions that underpay the required fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the BlueBerryBank report (an alternate withdrawal path that skips the required fee), `SignableTransaction::new` lets a caller attach an OP_RETURN `data` output to the transaction while the weight, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check are all computed from `payments` only — the data output's bytes are never counted. The resulting transaction is larger than accounted for yet pays only the fee computed for the smaller transaction, so its effective fee rate falls below `fee_per_vbyte` and can fall below the minimum relay fee.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is appended to `tx_outs` before any weight accounting:

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

But the size calculation at line 204 passes `payments` (which excludes the data output) to `calculate_weight_vbytes`:

```rust
// networks/bitcoin/src/wallet/send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62-127) builds its mock transaction solely from `payments` plus an optional `change` output — there is no parameter for extra outputs. The same omission occurs in the change path at line 225-226, which again passes `payments` rather than the actual output set. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed for a transaction missing up to ~91 vbytes (80-byte push + OP_RETURN script + 8-byte value + overhead).
- The `TooLowFee` check at lines 211-213 validates `needed_fee` against the underestimated `vbytes`, so a `fee_per_vbyte` at exactly `DEFAULT_MIN_RELAY_TX_FEE` passes even though the real transaction underpays the relay minimum.
- The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 uses a weight that excludes the data output, so a transaction slightly under the limit on paper can exceed it in reality.

The actual fee paid is `sum(inputs) - sum(outputs)` (lines 138-141), which equals the undercomputed `needed_fee`; the extra bytes are pushed onto the transaction for free.

### Impact Explanation
The signer produces a transaction whose real fee rate is strictly lower than the caller-specified `fee_per_vbyte`. At boundary fee rates the transaction falls below `DEFAULT_MIN_RELAY_TX_FEE` and will be rejected by standard Bitcoin relay, leaving inputs locked in an unpropagatable transaction and requiring an RBF/new signing round to recover. More generally, callers relying on `needed_fee()` for fee budgeting get a systematically wrong value whenever `data` is present, and the weight-limit check can be bypassed. This mirrors the reported class: a feature path (data-carrying transactions) evades the fee charged to every other transaction of equivalent size.

### Likelihood Explanation
Any caller of `SignableTransaction::new` that supplies `data` triggers the miscalculation deterministically; the function accepts up to 80 bytes of caller-controlled data and never re-measures the transaction. No special conditions beyond passing `data` are required — the underpayment is guaranteed, and whether the transaction is merely underpriced or outright unrelayable depends only on how close `fee_per_vbyte` is to the relay minimum.

### Recommendation
Include the OP_RETURN output in the size accounting: extend `calculate_weight_vbytes` to take the full `tx_outs` vector (or an additional `data`/`extra_outputs` parameter) so `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the final transaction, in both the no-change and change branches (lines 204 and 225-226).

### Proof of Concept
```rust
// Conceptual, in networks/bitcoin
let inputs = vec![received_output];           // e.g. worth 100_000 sats
let payments = vec![(dest_script, 50_000)];    // any payment
let data = vec![0u8; 80];                      // maximum allowed OP_RETURN payload
let fee_rate = 1;                              // 1 sat/vB == DEFAULT_MIN_RELAY_TX_FEE boundary

let stx = SignableTransaction::new(inputs, &payments, None, Some(data), fee_rate).unwrap();

// stx.needed_fee() == 1 * vbytes(inputs+1 payment output), e.g. ~110 sats
// The real transaction carries an extra ~91 vB OP_RETURN output,
// so its true size is ~201 vB while it pays only ~110 sats,
// an effective ~0.55 sat/vB — below the 1 sat/vB relay minimum,
// despite the TooLowFee check at send.rs:211 having passed.
assert!(stx.needed_fee() < stx.fee()); // fee() == needed_fee, but real vsize > accounted vsize
```

The discrepancy is visible directly: `calculate_weight_vbytes` is invoked with `payments` at `send.rs:204`/`226`, while the OP_RETURN `TxOut` was already pushed into `tx_outs` at `send.rs:195-201` and is included in the final `Transaction` at `send.rs:250`.
