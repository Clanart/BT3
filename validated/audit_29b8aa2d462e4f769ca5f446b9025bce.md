## Finding: Path traversal in `revealInFileManager` due to missing containment check

### Summary
`revealInFileManager` joins an attacker-influenceable relative `path` (a file path taken from a diff/changed-file entry) with `repository.path` using `Path.join` and passes the result straight to the privileged `shell.showItemInFolder` IPC call, without ever normalizing the result or verifying it stays inside the repository directory.

### Finding Description
`revealInFileManager` computes the target path by naive concatenation and forwards it to the main process: [1](#0-0) 

The `path` argument comes from UI components (changed-file / commit-file lists, conflict lists, PR files-changed views) that pass a repo-relative file path directly to `revealInFileManager` — e.g. `filter-changes-list.tsx`, `selected-commits.tsx`, `unmerged-file.tsx`, `pull-request-files-changed.tsx`. These paths ultimately originate from parsed git diff/status/PR-file data, which is data that can, in principle, come from repository content, so there is no explicit sanitization step between "file path as reported by git/PR API" and `Path.join(repository.path, path)`.

`Path.join` does **not** prevent `..` segments from escaping the base directory — `Path.join('/repo', '../../etc')` legitimately resolves to `/etc`. There is no subsequent check (e.g. comparing the resolved path against `repository.path` via `Path.relative`/`startsWith`) before the value is sent across the IPC boundary: [2](#0-1) 

The renderer-side proxy for `showItemInFolder` only checks that the path **exists** on disk (`pathExists`) before invoking the main-process `show-item-in-folder` channel — it performs no containment/allow-list check relative to any repository root: [2](#0-1) 

### Impact Explanation
If an out-of-bounds `path` reaches `revealInFileManager` with `../` segments, `shell.showItemInFolder` will open the OS file manager and highlight an arbitrary file elsewhere on the user's filesystem (bounded by whatever path actually exists — since `pathExists` still gates the call). This is an information-disclosure/UI-confusion primitive (reveals the existence and location of files outside the repository, e.g. `~/.ssh/id_rsa` or `%APPDATA%` files) rather than direct code execution or file content exfiltration, since `showItemInFolder` merely selects a file in Explorer/Finder — it does not open/execute it and does not return file contents to the renderer.

### Likelihood Explanation
Practical exploitability is limited by how the `path` value is actually produced upstream. In this codebase the callers of `revealInFileManager` pass paths derived from git's own diff/status output (`CommittedFileChange`/`WorkingDirectoryFileChange`, PR files-changed lists) or from `.gitmodules`-style conflict entries. Modern Git enforces `fsck` protections that reject tree/index entries containing `..` or other path-traversal components, which normally prevents a "crafted diff/file-list entry with `../../`" from being introduced via a cloned/fetched repository through ordinary git object handling. I was not able to fully verify, within the available tool budget, whether any of the upstream producers (e.g. PR API JSON file lists, submodule path handling, or conflict-resolution UI) skip this git-level protection and could hand `revealInFileManager` a raw, unsanitized string containing `..` — that would need to be checked in the callers listed above (`pull-request-files-changed.tsx`, `unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`) and in the PR file-list parsing code to confirm an end-to-end reachable path from a malicious/attacker-controlled remote object.

### Recommendation
Regardless of whether current callers can reach this with a hostile path today, `revealInFileManager` should defensively normalize and verify containment before calling `shell.showItemInFolder`, e.g.:
```ts
const resolved = Path.resolve(repository.path, path)
const relative = Path.relative(repository.path, resolved)
if (relative.startsWith('..') || Path.isAbsolute(relative)) {
  throw new Error('Path escapes repository root')
}
```
This closes the gap even if a future or currently-unverified caller supplies a path containing `..`.

### Proof of Concept
1. Call `revealInFileManager(repository, '../../../../etc')` (or a Windows equivalent) directly, simulating a caller passing an unsanitized file-list entry.
2. Observe `Path.join(repository.path, '../../../../etc')` resolves outside `repository.path`.
3. `shell.showItemInFolder` (via `main-process-proxy.showItemInFolder` → IPC `show-item-in-folder`) is invoked with the out-of-repo path, and — since the path exists — the OS file manager opens/highlights the out-of-repo location, confirming no containment check exists in `revealInFileManager` or in the IPC proxy.

Given the uncertainty about whether any real caller can currently inject a `..`-containing path (Git's own fsck protections normally block this at the source), I'm reporting this as a **defense-in-depth gap with unconfirmed end-to-end reachability** rather than a fully proven exploit chain — a Devin session with the ability to fetch a crafted malicious repo/PR and step through the actual file-list parsing code would be needed to confirm whether the git-level protections can be bypassed for any of the listed callers.
