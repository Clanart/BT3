### Title
Unauthenticated forwarded outputs can replay the first queued deposit instruction, stealing later depositors’ minted balance - (File: processor/src/multisigs/db.rs)

### Summary

During multisig rotation, a forwarded Bitcoin output is accepted as proof that an earlier external deposit completed based only on its `OutputType::Forwarded` address and its balance. `ForwardedOutputDb::take_forwarded_output` then returns the first queued instruction for that balance but writes the original queue back instead of the unconsumed remainder. If two deposits produce the same forwarded amount, every forwarded output re-executes the first instruction. An attacker can place their own instruction first and cause a victim’s same-valued forwarded deposit to mint to the attacker.

### Finding Description

When an old-multisig external output is forwarded, Serai stores its adjusted `InInstructionWithBalance` under only the expected forwarded balance. Multiple instructions for the same balance are concatenated under that key. [1](#0-0) 

Later, every scanned `OutputType::Forwarded` output calls `take_forwarded_output(txn, output.balance())`, with no check that the output came from the intended forwarding transaction or corresponds to a particular original outpoint. [2](#0-1) 

`take_forwarded_output` decodes only the first serialized instruction, but when more instructions remain it writes `outputs`—the original full buffer—rather than `outputs_ref`, the remaining bytes. [3](#0-2) 

The forwarded address is deterministic and publicly derivable from the new multisig key. [4](#0-3)  `scanner` registers that address as `OutputType::Forwarded`, so any ordinary Bitcoin transaction paying it is interpreted as a forwarded output. [5](#0-4) 

### Impact Explanation

An attacker can steal a victim’s bridged balance representation. If the attacker’s instruction is queued first for the same post-fee forwarded balance as a victim’s instruction, both forwarded outputs execute the attacker’s instruction. The victim’s real Bitcoin is received by the new multisig, but their mint credit is replaced by a second credit to the attacker.

### Likelihood Explanation

This is reachable during the `ForwardFromExisting` rotation phase using only public Bitcoin deposits. The attacker controls their deposit amount and instruction, and can select an amount resulting in the same adjusted forwarded balance as a pending victim deposit. Queue ordering must place the attacker’s instruction first, which is feasible when the attacker observes pending deposits and orders their transaction earlier in the same processing flow.

### Recommendation

Persist each expected forwarded output by a unique identifier, preferably the expected forwarding transaction ID/outpoint or original output ID, rather than by amount alone. When consuming a queue entry, write back `outputs_ref` rather than `outputs`. Additionally, associate the observed forwarded output with the specific planned forwarding eventuality before emitting its saved instruction.

### Proof of Concept

1. Let `K_old` be the rotating-out Bitcoin multisig key and `K_new` the rotating-in key.
2. During `ForwardFromExisting`, the attacker deposits amount `X` to `K_old` with a refundable instruction crediting the attacker’s Serai address.
3. A victim deposits the same amount `X` to `K_old` with an instruction crediting the victim.
4. For each deposit, Serai creates a forwarding plan to `forward_address(K_new)`. After deducting the forwarding fee, suppose both expected forwarded balances are `B`.
5. `ForwardedOutputDb::save_forwarded_output` stores the attacker instruction followed by the victim instruction under key `B`.
6. When the first forwarded output paying `B` is scanned, `take_forwarded_output(B)` returns the attacker instruction. Because it writes back the original `outputs` buffer, the victim instruction remains behind it rather than becoming the next entry.
7. When the victim’s forwarded output paying `B` is scanned, `take_forwarded_output(B)` again returns the attacker instruction.
8. The resulting batch contains two attacker-crediting instructions: one backed by the attacker’s deposit and one backed by the victim’s deposit. The victim loses their expected minted balance.

impl ForwardedOutputDb {
  pub fn save_forwarded_output(txn: &mut impl DbTxn, instruction: &InInstructionWithBalance) {

    existing.extend(instruction.encode());
    Self::set(txn, instruction.balance, &existing);
  }
