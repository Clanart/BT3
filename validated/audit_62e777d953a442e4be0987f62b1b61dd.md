### Title
`ReceivedOutput::read` accepts attacker-controlled offset/script/outpoint with no consistency check, injecting unspendable or misattributed inputs into the wallet - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The NoSQL-injection bug class (unsanitized input accepted into a trusted query/structure and later acted on) maps onto `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` (lines 122-134). The deserializer reads a scalar `offset`, a `TxOut`, and an `OutPoint` straight from untrusted bytes and returns a `ReceivedOutput` without verifying the one invariant that makes a `ReceivedOutput` meaningful: that `output.script_pubkey` is actually the P2TR script for `key + offset*G` (which `Scanner` guarantees internally via its `scripts` map at lines 185-211). A forged `ReceivedOutput` is therefore "funds reported received that are not spendable", matching the accepted impact.

### Finding Description
`ReceivedOutput` is the wallet's record of a spendable input. When produced by `Scanner::scan_transaction`, the `offset` is looked up from the `scripts: HashMap<ScriptBuf, Scalar>` map, so the invariant `p2tr_script_buf(self.key + GENERATOR * offset) == output.script_pubkey` holds by construction (`networks/bitcoin/src/wallet/mod.rs:205-211`). `ReceivedOutput::read` bypasses that check entirely:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output = TxOut::consensus_decode(&mut buf_r)...;
  let outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Any untrusted byte string that parses is accepted as a claim "this output is spendable by tweaking our key with this offset". There is no key/context parameter, so the function *cannot* verify the binding — but nothing documents this, and the type gives the caller no way to distinguish a scanner-produced output from an injected one.

Downstream, `SignableTransaction::new` consumes `Vec<ReceivedOutput>` and produces per-input signature messages using `output.offset()` to re-key for each input (`networks/bitcoin/src/wallet/send` and the test usage at `networks/bitcoin/tests/wallet.rs:95`, `157-161`). The offset is treated as authoritative: the input is signed with `key + offset`.

### Impact Explanation
An attacker who can feed bytes into `ReceivedOutput::read` (deserialized inputs to a spend/sign path) can inject:

- An output paying to an attacker-chosen `script_pubkey` paired with `offset = Scalar::ZERO`. The wallet reports value received and builds a `SignableTransaction` spending it, but signs with the unmodified group key — the signature does not match the script, so the transaction is invalid and any funds "received" are not spendable.
- An output whose script *is* a valid tweaked key but paired with the wrong `offset` (e.g., script for `key + o1*G` with claimed offset `o2`). Same result: the produced BIP-340 signature is invalid for that input.
- An outpoint/script pair referencing a real third-party output, causing the wallet to construct transactions attempting to spend outputs it does not control (guaranteed-invalid signatures, or attempts to double-spend already-spent UTXOs).

Because Serai performs threshold signing per input, an injected `ReceivedOutput` also drags the FROST signing set into producing a signature over a transaction committing to a forged input set (sighash commits to all prevouts via `Prevouts::All`), corrupting an otherwise legitimate spend.

### Likelihood Explanation
Reachability requires untrusted bytes reaching `ReceivedOutput::read` — i.e., any deployment that persists, relays, or accepts received-output records rather than deriving them exclusively from `Scanner::scan_transaction`/`scan_block` in the same process. The prompt's own reachability model includes `ReceivedOutput::read`. No cryptographic break is needed; the attacker only crafts bytes. Impact is capped at misattributed/unspendable inputs and wasted/aborted signing sessions rather than key recovery, so this rates Medium under the stated criteria (no secret leakage, but a concrete "funds reported received that are not spendable" violation plus signing of an unintended transaction).

### Recommendation
Bind the offset to the script at deserialization. Either:

- Change `ReceivedOutput::read` to take the scanner key (or the `Scanner` itself) and verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)`, rejecting otherwise; or
- Store only the `OutPoint`/`TxOut` in serialized form and re-derive `offset` from `scripts` at use time, mirroring `scan_transaction`; or
- At minimum, rename/document `read` as trusted-only and add a `verify(key)` method that callers must invoke before passing the output to `SignableTransaction::new`.
