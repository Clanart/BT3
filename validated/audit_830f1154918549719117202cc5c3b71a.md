## Analysis

The Curve report's core invariant is: **storage that tracks "how much of a token this contract actually holds" must be updated with the actual post-fee amount received, not the pre-transfer requested amount.** The exact same class of bug exists in the Tron deployment of `IntentGatewayV2`.

### Title
Escrow ledger credited with pre-transfer amount instead of actual received amount for fee-on-transfer tokens — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In `placeOrder`, the Tron `IntentGatewayV2` computes the escrowed amount (`reducedInputs[i].amount`) purely as `order.inputs[i].amount - protocolFee`, using the caller-supplied `order.inputs[i].amount` as the base. It then pulls tokens with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — without ever measuring what the contract actually received. [1](#0-0) 

### Finding Description
For a fee-on-transfer ERC20 token, `safeTransferFrom` delivers less than the requested `order.inputs[i].amount` to the gateway, but `reducedInputs[i].amount` is derived from the pre-transfer `originalAmount = order.inputs[i].amount`: [2](#0-1) 

There is no balance-before/balance-after measurement anywhere in this code path (unlike the fixed EVM mainnet `IntentGatewayV2.sol`, which explicitly snapshots gateway balances and mutates `order.inputs[i].amount` to the actual received amount before computing `reducedInputs` — see `evm/src/apps/IntentGatewayV2.sol` lines 281–298 and the accompanying fee-on-transfer regression tests at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2256–2308). The Tron contract skips this correction entirely, so `_orders[commitment][token]` is credited with more tokens than the contract actually holds against that commitment.

Later, `withdraw()` (invoked from `cancelOrder`/`onAccept` for `RedeemEscrow`/`RefundEscrow`) pays out exactly the amount encoded in the caller-supplied `body.tokens[i].amount` (which must equal the stored `reducedInputs` to reproduce the commitment hash), only checking that `_orders[commitment][token] != 0`, never that it equals the actual escrowed/held balance: [3](#0-2) 

### Impact Explanation
Because the contract pools tokens from multiple concurrent orders, an inflated per-commitment ledger entry for a fee-on-transfer token does not simply "fail" — it lets a withdrawal for that overstated commitment pull real tokens that belong to *other* orders/users out of the shared contract balance. This is unauthorized movement of escrowed funds to the wrong beneficiary/amount and can cause loss of funds for unrelated order owners, exactly the class of harm the bounty scope calls out ("stealing or loss of funds," "transaction manipulation," "wrong beneficiary or amount").

### Likelihood Explanation
This requires no privileged actor, relayer, or prover — any unprivileged user can call `placeOrder` on the Tron gateway with a fee-on-transfer token as input, and the corrupted `_orders[commitment][token]` value is created automatically as a side effect of normal contract logic. No malformed proof or malicious peer is needed; it is purely an accounting bug reachable via a public entry point.

### Recommendation
Mirror the fix already present in the mainnet EVM `IntentGatewayV2.sol`: snapshot the gateway's token balance before `safeTransferFrom`, measure the actual delta afterward, and compute `reducedInputs`/the commitment/the escrow credit from that actual received amount rather than from the caller-supplied `order.inputs[i].amount`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee) as an order input, mirroring the existing EVM test `testPlaceOrder_FeeOnTransferToken_WithProtocolFee` [4](#0-3) .
2. Call `placeOrder` with `inputs[0].amount = 1000e18`; the gateway actually receives `990e18` (1% transfer fee), but `_orders[commitment][token]` is credited with `~994.7e18` (1000e18 minus only the protocol fee), overstating the real balance.
3. Repeat with a second, unrelated order using the same token so the pooled contract balance includes funds from another user.
4. Trigger `withdraw()` for the first commitment (via `cancelOrder` same-chain path); it pays out the inflated `reducedInputs[i].amount`, which exceeds what that order actually contributed, draining tokens escrowed for the second order.

    /// @notice Fee-on-transfer with protocol fees: both deductions applied correctly.
    function testPlaceOrder_FeeOnTransferToken_WithProtocolFee() public {
        IntentGatewayV2 gatewayWithFees = _deployGatewayProxy();
        Params memory intentParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: SURPLUS_SHARE_BPS,
            protocolFeeBps: PROTOCOL_FEE_BPS, // 30 bps
            priceOracle: address(0)
        });
        gatewayWithFees.initialize(intentParams, new bytes[](0));

        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 receivedAfterTransferFee = inputAmount - (inputAmount * 100) / 10000; // 990
        uint256 protocolFee = (receivedAfterTransferFee * PROTOCOL_FEE_BPS) / 10000;
        uint256 expectedEscrow = receivedAfterTransferFee - protocolFee;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(gatewayWithFees), inputAmount);
        gatewayWithFees.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Reconstruct commitment: inputs mutated to received, then reduced by protocol fee
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedEscrow; // commitment is hashed with reduced amount
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            gatewayWithFees._orders(commitment, address(fot)),
            expectedEscrow,
            "Escrow should equal received minus protocol fee"
        );
    }
