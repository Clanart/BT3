### Title
Copilot-generated conflict resolutions are written and staged with no verification the content actually reflects the conflicted hunks - ([File: app/src/lib/stores/app-store.ts])

### Summary
The reported bug is a "trust without verification" pattern: `adminInjectBacking` records no state that `adminWithdrawBacking` is later checked against, so an unrestricted write path exists with no tracking or bound. The Desktop analog is `AppStore._applyCopilotConflictResolutions`, which takes `resolution.resolvedContent` produced by an LLM turn seeded with data pulled directly from a fetched/cloned repository (commit messages, conflict hunks, PR bodies) and writes it straight to the working tree and `git add`s it, with the only guard being a path-containment check — never a content-integrity check that the written bytes are actually a valid resolution of the real conflict markers.

### Finding Description
`_applyCopilotConflictResolutions` iterates `copilotResolutions`, resolves each target path with `resolveWithin(repository.path, resolution.path)` to prevent path traversal, skips files the user resolved manually, and then unconditionally does: [1](#0-0) 

That containment check only proves the destination path is inside the repo — it says nothing about whether `resolution.resolvedContent` is a faithful merge of "ours"/"theirs", or whether it introduces attacker-influenced content. The content itself comes from `gatherConflictResolutionContext`, which pulls conflicted-file hunks, commit metadata, and PR titles/bodies from the repository/remote being merged and feeds them to the Copilot model as prompt context: [2](#0-1) [3](#0-2) 

The code comment even acknowledges the model's citations are looked up against attacker-influenced gathered context with no re-fetch/re-verification step: `"The model can only cite data we placed in the prompt, so resolving its references is a simple lookup against the gathered context — no re-fetching or re-hydration required."` — this is the same class of unrestricted-trust problem as `adminWithdrawBacking`: a value (`resolvedContent`) is produced from injected, attacker-influenced input, and then consumed and persisted (written + staged) with no tracked/verified relationship to the original input it was supposed to represent.

### Impact Explanation
If a user merges/pulls a branch from an untrusted remote that contains crafted conflicting content (e.g., commit messages or PR-style text engineered to manipulate the model via prompt injection), the Copilot resolution flow can write attacker-steered file content into the user's working directory and immediately `git add` it. Because the write and staging happen unconditionally once the containment check passes, this can silently corrupt what the user is about to commit or push — matching the "silent corruption of what the user commits or pushes" impact category. This is distinct from a normal AI-hallucination risk because the trigger is attacker-controlled repository content, not user intent.

### Likelihood Explanation
This requires the user to have Copilot conflict resolution enabled and to accept the dialog's "Continue Merge" action after resolving conflicts against a repository/branch that contains attacker-crafted conflict material — a plausible flow for anyone merging PRs/branches from external contributors. I was not able to fully verify, within the available tool budget, whether the result dialog surfaces a full line-by-line diff of `resolution.resolvedContent` per file before the user clicks "Continue Merge," or only the aggregate `summary`/`references` shown in `resolveConflictsWithCopilot`'s return value. If only the summary is shown (as the code structure suggests, since `summary.markdown` and `references` are the dialog's stated content), the user has limited ability to catch subtle malicious edits despite technically "confirming."

### Recommendation
- Before writing `resolution.resolvedContent`, validate it against the actual conflict hunks (e.g., diff it against `ours`/`theirs` content) rather than trusting the model's output outright.
- Surface a mandatory per-file diff view in the result dialog so the user visibly reviews the exact bytes about to be written/staged, not just an AI-generated summary derived from the same untrusted context.
- Treat repository-sourced text (commit messages, PR bodies) fed into the prompt as untrusted input and sanitize/delimit it to reduce prompt-injection influence over `resolvedContent`.

### Proof of Concept
Conceptual (not executed, no filesystem/terminal access in this session):
1. Attacker publishes a branch/PR with a merge conflict where the conflict hunks and surrounding commit messages contain crafted instructions/content aimed at the resolution model.
2. Victim fetches/merges this branch in Desktop and enables "Resolve conflicts with Copilot."
3. `gatherConflictResolutionContext` bundles the attacker's commit messages/PR text alongside the real hunks and sends them to the model.
4. Model returns `resolvedContent` influenced by the attacker's injected text; user reviews only the summary/references and clicks "Continue Merge."
5. `_applyCopilotConflictResolutions` writes the content via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and stages it with `git add`, after which the user commits/pushes the corrupted result. [4](#0-3)
