### Title
Missing Minimum-Value Validation for Critical Timelock Parameters in `ProtocolParamset` — (File: `crates/clementine-config/src/protocol.rs`)

### Summary

`ProtocolParamset` contains seven security-critical block-count timelock fields that are embedded verbatim into pre-signed Bitcoin scripts. Neither `from_toml_file` nor `from_env` validates any of them for a minimum value. A zero (or near-zero) value for `operator_challenge_timeout_timelock`, `disprove_timeout_timelock`, or `assert_timeout_timelock` removes the corresponding Bitcoin script timelock entirely, collapsing the challenge/disprove window and enabling fraudulent withdrawals or immediate collateral burning.

### Finding Description

`ProtocolParamset` declares seven `u16` timelock fields: [1](#0-0) 

Both parsing paths — `from_toml_file` and `from_env` — perform exactly one bounds check: `finality_depth >= 1`. No check is made on any timelock field: [2](#0-1) [3](#0-2) 

These values are consumed directly by `TimelockScript` and `Sequence::from_height` when building pre-signed Bitcoin transactions:

- `operator_challenge_timeout_timelock` → `Sequence::from_height(...)` in `create_challenge_timeout_txhandler`: [4](#0-3) 

- `assert_timeout_timelock` → `Sequence::from_height(...)` in `create_assert_timeout_txhandlers`: [5](#0-4) 

- `assert_timeout_timelock` → `TimelockScript` in kickoff builder: [6](#0-5) 

`TimelockScript::to_script_buf` pushes the raw integer directly into `OP_CSV`: [7](#0-6) 

Per BIP-68/BIP-112, `OP_CSV 0` is a no-op and `Sequence::from_height(0)` imposes no relative timelock. The pre-signed transaction becomes immediately broadcastable the moment its parent UTXO confirms.

`check_general_requirements` also does not validate any timelock: [8](#0-7) 

### Impact Explanation

**`operator_challenge_timeout_timelock = 0`** is the most severe case. The `ChallengeTimeout` transaction is pre-signed by all verifiers during the MuSig2 session with `sequence = 0`. After the operator broadcasts a fraudulent kickoff, they can immediately broadcast the pre-signed `ChallengeTimeout` tx in the same block, spending the `Challenge` UTXO before any watchtower can submit a challenge. The challenge window is completely eliminated. The operator then proceeds through the reimbursement path and collects bridged BTC they did not legitimately pay out.

**`disprove_timeout_timelock = 0`** collapses the disprove window: even if a challenge is submitted, the operator can immediately broadcast `DisproveTimeout` after submitting asserts, giving verifiers zero blocks to construct and broadcast a disprove transaction.

**`assert_timeout_timelock = 0`** allows anyone to immediately broadcast `AssertTimeout` after a kickoff, burning the operator's `BurnConnector` collateral and `KickoffFinalizer` UTXO without giving the operator any time to submit asserts.

### Likelihood Explanation

Low — requires a fat-finger or copy-paste error in the TOML/env configuration. However, the protocol is designed to be deployed by multiple independent operators and verifiers, and the paramset is loaded from external files or environment variables without any runtime guard on these fields. A single misconfigured deployment propagates the zero timelock into all pre-signed transactions that all verifiers co-sign, making the damage irreversible once the signing session completes.

### Recommendation

Add minimum-value guards for all security-critical timelock fields in both `ProtocolParamset::from_toml_file` and `ProtocolParamset::from_env` (and mirror them in `BridgeConfig::check_general_requirements`). At minimum:

```rust
if paramset.operator_challenge_timeout_timelock == 0 {
    return Err(BridgeError::ConfigError(
        "operator_challenge_timeout_timelock must be > 0".into()));
}
if paramset.disprove_timeout_timelock == 0 {
    return Err(BridgeError::ConfigError(
        "disprove_timeout_timelock must be > 0".into()));
}
if paramset.assert_timeout_timelock == 0 {
    return Err(BridgeError::ConfigError(
        "assert_timeout_timelock must be > 0".into()));
}
// ... similarly for watchtower_challenge_timeout_timelock,
//     operator_challenge_nack_timelock, latest_blockhash_timeout_timelock
```

Additionally, enforce ordering invariants (e.g., `operator_challenge_timeout_timelock < disprove_timeout_timelock`) to prevent logically inconsistent configurations that compress the challenge/disprove windows to near-zero.

### Proof of Concept

1. Set `OPERATOR_CHALLENGE_TIMEOUT_TIMELOCK=0` in the environment (or `operator_challenge_timeout_timelock = 0` in the TOML file).
2. Start all actors. `ProtocolParamset::from_env()` / `from_toml_file()` accepts the value without error.
3. The MuSig2 signing session produces a `ChallengeTimeout` transaction whose first input carries `nSequence = 0x00000000` (no relative timelock).
4. Operator broadcasts a fraudulent kickoff transaction.
5. In the same block (or the next), operator broadcasts the pre-signed `ChallengeTimeout` tx. Bitcoin consensus accepts it immediately because `nSequence = 0` satisfies `OP_CSV 0`.
6. The `KickoffFinalizer` UTXO is spent; no watchtower challenge is possible. The operator proceeds to the reimbursement path and drains bridged BTC. [9](#0-8) [10](#0-9)

    fn to_script_buf(&self) -> ScriptBuf {
        let script_builder = Builder::new()
            .push_int(self.1 as i64)
            .push_opcode(OP_CSV)
            .push_opcode(OP_DROP);

        if let Some(xonly_pk) = self.0 {
            script_builder

                .push_opcode(OP_CHECKSIG)

            script_builder.push_opcode(OP_TRUE)

    /// Check general requirements for the configuration irrespective of the network.
    pub async fn check_general_requirements(&self) -> Result<(), BridgeError> {
        // check genesis state hash
        let rpc = ExtendedBitcoinRpc::connect(
            self.bitcoin_rpc_url.clone(),
            self.bitcoin_rpc_user.clone(),
            self.bitcoin_rpc_password.clone(),
            None,
        )
        .await
        .wrap_err("Failed to connect to Bitcoin RPC while checking general requirements")?;

        let genesis_chain_state = HeaderChainProver::get_chain_state_from_height(
            &rpc,
            self.protocol_paramset().genesis_height.into(),
            self.protocol_paramset().network,
        )
        .await
        .wrap_err("Failed to get genesis chain state while checking general requirements")?;

        let mut reasons = Vec::new();

        if genesis_chain_state.to_hash() != self.protocol_paramset().genesis_chain_state_hash {
            reasons.push(format!(
                "Genesis chain state hash mismatch, state hash generated from Bitcoin RPC ({}) does not match value in config ({})",
                hex::encode(genesis_chain_state.to_hash()),
                hex::encode(self.protocol_paramset().genesis_chain_state_hash)
            ));
        }

        if self.protocol_paramset().start_height < self.protocol_paramset().genesis_height {
            reasons.push(format!(
                "Start height is less than genesis height: {} < {}",
                self.protocol_paramset().start_height,
                self.protocol_paramset().genesis_height
            ));
        }

        if self.protocol_paramset().finality_depth < 1 {
            reasons.push(format!(
                "Finality depth ({}) cannot be less than 1",
                self.protocol_paramset().finality_depth
            ));
        }

        if !reasons.is_empty() {
            return Err(BridgeError::ConfigError(format!(
                "Invalid configuration due to: {}",
                reasons.join(" - ")
            )));
        }

        Ok(())
    }
