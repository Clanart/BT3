### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` allows stack-exhaustion DoS via public RPC / transaction submission - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`kaia_sendRawTransaction`, `eth_sendRawTransaction`, `SendRawTransactions`, `auction_submitBid`, and `IsGaslessTx` all call `rlp.DecodeBytes` on attacker-controlled bytes before any semantic validation occurs [1](#0-0) . When the decoded transaction is an `AccountUpdate`/`FeeDelegatedAccountUpdate*` transaction, the embedded `AccountKey` is decoded via `AccountKeySerializer.DecodeRLP`, which for the `AccountKeyRoleBased` type recursively calls `rlp.DecodeBytes` on each nested key blob with no depth limit or composite-type check [2](#0-1) [3](#0-2) .

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte blobs, then for every blob independently invokes `rlp.DecodeBytes(b, &serializer)`, where `serializer` is a fresh `AccountKeySerializer` that dispatches to `NewAccountKey(keyType)` and recursively decodes into that key type [2](#0-1) . Nothing in this decode path prevents one of those nested blobs from itself encoding another `AccountKeyRoleBased` (i.e., a composite type nested inside a composite type), so decoding recurses without a depth bound.

The only place composite-type nesting is rejected is `CheckInstallable`/`CheckUpdatable`, which explicitly test `IsCompositeType()` to reject nested role-based/multisig keys [4](#0-3) . Critically, these checks run only *after* the transaction (and its account key) has already been fully RLP-decoded — decoding itself happens unconditionally at the RPC boundary, well before `CheckInstallable`/`CheckUpdatable` or signature validation are reached [1](#0-0) .

This is directly analogous to the reported go-git bug class: parsing of untrusted, maliciously crafted structured data with no recursion/size limits leads to panics or excessive resource consumption before any validity check of the data is applied.

### Impact Explanation
An unauthenticated caller (any transaction sender, including someone who never needs to hold a private key matching the crafted data) can submit a single RLP payload — via `kaia_sendRawTransaction`, `eth_sendRawTransaction`, `SendRawTransactions`, an auction bid's `TargetTxRaw` [5](#0-4) , or a gasless-tx pre-check [6](#0-5)  — that encodes deeply nested `AccountKeyRoleBased` blobs. Each nesting level requires only a handful of extra RLP-encoding bytes, so a payload well under any max-tx-size limit can produce very large recursion depth, driving excessive CPU/memory consumption in the decoding goroutine on every full node that receives or re-validates the transaction (mempool relay, RPC front end, auction bid pool). This matches CWE-400 (uncontrolled resource consumption) and is reachable purely from a submitted transaction/bid, satisfying the "unprivileged transaction sender" reachability requirement.

### Likelihood Explanation
High likelihood: the vulnerable code path (`rlp.DecodeBytes` on raw input) is the very first step performed on every `sendRawTransaction`/`sendRawTransactions`/auction-bid/gasless-check call, with no upfront depth or complexity limiting of the account-key substructure before recursive decode begins. No signature, nonce, or `CheckInstallable` validation gates this decode step.

### Recommendation
- Enforce a maximum decode/recursion depth for `AccountKeySerializer`/`AccountKeyRoleBased` (and any other composite `AccountKey` types) during `DecodeRLP`, rejecting composite-within-composite nesting at decode time rather than only in `CheckInstallable`/`CheckUpdatable`.
- Alternatively, track and pass down a nesting-depth counter through `AccountKeySerializer.DecodeRLP` and fail fast once a small fixed depth (e.g., 1, matching the existing `IsCompositeType` restriction) is exceeded.
- Apply the same recursion-depth guard uniformly across all entry points that call `rlp.DecodeBytes` on user-supplied transaction bytes (`api/api_kaia_transaction.go`, `kaiax/auction/impl/api.go`, `kaiax/gasless/impl/api.go`).

### Proof of Concept
1. Construct account key blob `K0` = RLP-encoded `AccountKeyRoleBased` containing one entry that is itself the RLP encoding of another `AccountKeyRoleBased` (`K1`), which contains another (`K2`), and so on for N levels — each level only needs the type tag + wrapping bytes, so a compact ~few-hundred-byte payload can realize deep nesting.
2. Wrap `KN` (outermost) as the `Key` field of an `TxInternalDataAccountUpdate` (or `FeeDelegatedAccountUpdate*`) transaction, RLP-encode the full transaction as done in `TestWronglyEncodedAccountKey` [7](#0-6)  (signature content can be arbitrary/invalid since decode happens before sig check).
3. Submit via `kaia_sendRawTransaction`/`eth_sendRawTransaction` (`api/api_kaia_transaction.go:384-390`) or as `TargetTxRaw` in `auction_submitBid` (`kaiax/auction/impl/api.go:107-116`).
4. Observe that `rlp.DecodeBytes` recurses through `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` for each nesting level with no bound, consuming CPU/stack proportional to N before any error is ever returned.

Note: I could not fully verify at what exact recursion depth (in terms of Go stack growth limits) a hard panic vs. just heavy CPU/memory usage would occur, since that depends on runtime stack-growth behavior and the exact encoding size chosen; a live PoC run against a running node would be needed to measure concrete resource impact.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
