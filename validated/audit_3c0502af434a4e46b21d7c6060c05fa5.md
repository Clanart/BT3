### Title
Panic (unreachable-code crash) in `blame`/`decrypt_with_proof` when the accused/accuser `Participant` index is not a registered DKG member - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame`, `AdditionalBlameMachine::blame`, and the underlying `Decryption::decrypt_with_proof` perform unchecked `HashMap` indexing (`self.enc_keys[&decryptor]`, `self.commitments[&sender]`) on caller-supplied `Participant` values. Since `Participant::new` accepts any nonzero `u16`, an unprivileged party can pass an index outside the `1..=n` DKG set (or an index with no registered commitments) and crash the process — the same bug class as CVE-2016-7052 (attacker-reachable crash in a verification-path operation).

### Finding Description
`Decryption::decrypt_with_proof` looks up the decryptor's encryption key with `self.enc_keys[&decryptor]` before using it in the DLEq verification (crypto/dkg/pedpop/src/encryption.rs:381-390). If `decryptor` was never registered, this indexing panics.

If that step is passed, `BlameMachine::blame_internal` evaluates the decrypted share against `self.commitments[&sender]` (crypto/dkg/pedpop/src/lib.rs:596-603). `commitments` only contains entries for registered participants (inserted for `1..=n` in `AdditionalBlameMachine::new` at crypto/dkg/pedpop/src/lib.rs:649-661, or during `verify_r1` at crypto/dkg/pedpop/src/lib.rs:313-337). `sender` and `recipient` are raw `Participant` arguments to `blame()` with no membership or `<= n` validation anywhere on this path.

An attacker can fully control the inputs:

- `msg` is read via `EncryptedMessage::read` (encryption.rs:170-177), which only enforces canonical encodings.
- The PoP challenge binds `sender` (`pop_challenge` at encryption.rs:302-324), but the attacker knows the ephemeral scalar for `msg.key` and can produce a valid `SchnorrSignature` for *any* claimed `sender` index, since the PoP only proves knowledge of that scalar.
- With `proof: Some(EncryptionKeyProof)` (read via `EncryptionKeyProof::read`, encryption.rs:267-269), the attacker controls `proof.key`, so the ChaCha20 keystream output — the "decrypted" share — is attacker-chosen and can be made a canonical scalar, reaching the `self.commitments[&sender]` index.
- Alternatively, setting `recipient`/`decryptor` to an unregistered index panics earlier at `self.enc_keys[&decryptor]`.

Both paths are `HashMap` `Index` impls, i.e., unconditional process aborts on untrusted input — identical in effect to the NULL-pointer dereference in `x509_vfy.c`.

### Impact Explanation
A single crafted blame accusation (or accusation naming a nonexistent accuser) crashes the node evaluating blame. In Serai this code is invoked on network-received blame messages (`CoordinatorMessage::VerifyBlame` → `AdditionalBlameMachine::new(...).blame(accuser, accused, ...)` in processor/src/key_gen.rs:504-549), where `accuser` and `accused` are attacker-supplied fields. A crashed processor halts signing/key-gen participation and forces operator intervention — a denial of service directly analogous to the OpenSSL application crash. Severity: High-impact DoS (Medium under conservative scoring given it requires the blame-evaluation path to be exercised).

### Likelihood Explanation
The `blame` APIs take `sender: Participant, recipient: Participant` with no validation that either is a member of `1..=n`. `Participant::new` (crypto/dkg/src/lib.rs) only rejects zero. Any party able to submit a blame message — or to trigger blame evaluation naming arbitrary indexes — triggers the panic deterministically. No special conditions (valid shares, threshold collusion, timing) are needed: a syntactically valid `EncryptedMessage` plus a self-consistent PoP suffices, both trivially constructible.

### Recommendation
In `Decryption::decrypt_with_proof`, replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`. In `BlameMachine::blame_internal`, replace `self.commitments[&sender]` with a `get` that returns an explicit blame/abort result (or `PedPoPError::MissingParticipant`-style error) when the sender is unregistered. More broadly, `blame`/`BlameMachine::blame`/`AdditionalBlameMachine::blame` should validate `sender` and `recipient` against `1..=n` (and registered-key membership) before any map indexing, mirroring the `validate_map` discipline used by `verify_r1`/`calculate_share`.

### Proof of Concept
```rust
// crypto/dkg/pedpop context
// Setup: run a normal PedPoP DKG with params t=2, n=3, obtain AdditionalBlameMachine
// (or BlameMachine via KeyMachine::calculate_share).
let machine: AdditionalBlameMachine<Ristretto> =
    AdditionalBlameMachine::new(CONTEXT, params.n(), commitment_msgs).unwrap();

// Attacker-controlled fields:
let bogus_sender = Participant::new(params.n() + 1).unwrap(); // not a DKG member
let recipient = Participant::new(1).unwrap();

// Craft EncryptedMessage with a key the attacker knows the discrete log of:
let k = Zeroizing::new(<Ristretto as Ciphersuite>::random_nonzero_F(&mut OsRng));
let pub_key = RistrettoPoint::generator() * *k;
let nonce = Zeroizing::new(<Ristretto as Ciphersuite>::random_nonzero_F(&mut OsRng));
let pub_nonce = RistrettoPoint::generator() * *nonce;
let plaintext = <Ristretto as Ciphersuite>::F::ONE.to_repr(); // canonical scalar bytes
let mut msg_bytes = Zeroizing::new(SecretShare(plaintext));
// encrypt_with attacker-chosen proof.key is unnecessary for the panic on `sender`:
// use proof = Some(...) so decrypt_with_proof proceeds, or simply supply a valid PoP
// and let `commitments[&bogus_sender]` be reached after a canonical-scalar decrypt.
let pop = SchnorrSignature::<Ristretto>::sign(
    &k, nonce,
    /* pop_challenge(CONTEXT, pub_nonce, pub_key, bogus_sender, plaintext) - computable by attacker */
);
let msg = EncryptedMessage { key: pub_key, pop, msg: msg_bytes };

// Supply a proof built on recipient 1's real enc_key (public data) with an
// attacker-chosen proof.key so the DLEq verify either passes or, alternatively,
// pass `recipient = bogus` to panic at `self.enc_keys[&decryptor]` immediately.
machine.blame(bogus_sender, recipient, msg, Some(attacker_proof));
// => panics: `self.commitments[&sender]` (lib.rs:599), HashMap index out of bounds
// or earlier: `self.enc_keys[&decryptor]` (encryption.rs:388) if `decryptor` is bogus.
```

Root cause is the documented-but-unenforced invariant that `sender`/`recipient`/`decryptor` are registered participants; `blame`'s public API accepts arbitrary `Participant` values and indexes maps built only for `1..=n`, turning attacker-chosen indexes into an unconditional panic — the Rust analog of the CVE's null dereference.
