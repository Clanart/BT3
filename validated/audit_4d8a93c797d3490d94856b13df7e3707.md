### Title
Missing header causes unhandled `NoMethodError` in `hmac_valid?` instead of controlled 401 - ([File: lib/shopify_app/controller_concerns/payload_verification.rb])

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` as a `before_action` on any controller including the concern. [1](#0-0) . `hmac_valid?` reads the header via `shopify_hmac`, which simply returns `request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]` with no nil-check, and passes it directly into `ActiveSupport::SecurityUtils.secure_compare` as the first argument. [2](#0-1) . If the attacker omits the `X-Shopify-Hmac-Sha256` header entirely, `shopify_hmac` is `nil`, and `ActiveSupport::SecurityUtils.secure_compare(nil, computed_base64_digest)` raises `NoMethodError: undefined method 'bytesize' for nil` because `secure_compare` unconditionally calls `.bytesize` on both arguments before comparing. This exception is not rescued anywhere in `verify_request` or `hmac_valid?`, so it propagates out of the `before_action` filter, resulting in an unhandled 500 error instead of the intended `head(:unauthorized)`.

Notably, the sibling concern `AppProxyVerification#query_string_valid?` explicitly guards against this exact class of bug with `return false if signature.nil?` before calling `secure_compare`. [3](#0-2) . `PayloadVerification#hmac_valid?` has no equivalent guard, confirming this is a genuine oversight rather than an intentional design choice.

### Impact Explanation
This is a public, unauthenticated route (webhook endpoints skip CSRF protection and require no session), so any anonymous attacker can trigger a `NoMethodError` by simply omitting the HMAC header on a POST to a webhook route. The direct, concretely provable impact is a crash of the request instead of a controlled `401`, i.e. an availability/error-handling defect (each malformed request costs one 500 instead of one 401 — no amplification, memory exhaustion, or resource leak is demonstrated). It does not bypass HMAC verification (the request is still rejected, just via an exception instead of `:unauthorized`), does not grant access to shop data/tokens, and does not enable session or signature forgery. It does not map to a concrete Shopify HackerOne impact class such as auth bypass, token theft, or forged webhook acceptance — those all still fail closed here.

### Likelihood Explanation
Trivial to trigger (a single POST with a missing/garbage HMAC header, base64-garbage of a length that fails `bytesize` assumptions is not even required for `nil`), and 100% repeatable for any controller including `WebhookVerification`. However, whether this manifests as a real security issue depends entirely on the host app's error-handling configuration: in production, `config.consider_all_requests_local = false` returns a generic 500 with no stack trace disclosure, and the request is still ultimately rejected (fails closed), not authenticated.

### Recommendation
Add a nil/blank guard in `hmac_valid?`/`shopify_hmac` before calling `secure_compare`, mirroring the pattern used in `AppProxyVerification#query_string_valid?`:
```ruby
def hmac_valid?(data)
  return false if shopify_hmac.blank?
  ...
end
```

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
