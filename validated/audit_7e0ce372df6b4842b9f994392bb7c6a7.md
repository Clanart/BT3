### Title
`git submodule update --init --recursive` combined with `protocol.file.allow=always` lets an attacker-controlled `.gitmodules` entry read arbitrary local paths when Desktop opts into the file-protocol override - ([File: app/src/lib/git/submodule.ts])

### Summary
Git ships a built-in restriction (`protocol.file.allow=user`, i.e. disabled by default for submodules) precisely to stop a malicious repository from using a submodule URL like `file:///home/victim/.ssh` to make the client "clone" arbitrary local filesystem paths into the working tree. GitHub Desktop's `updateSubmodulesAfterOperation` exposes an `allowFileProtocol` switch that, when set, blanket re-enables `file://` for the entire, recursively-resolved submodule graph rather than validating each submodule URL individually. [1](#0-0) 

### Finding Description
`updateSubmodulesAfterOperation` builds the `git submodule update --init --recursive` invocation and, when `allowFileProtocol` is true, prepends `-c protocol.file.allow=always` to the argument list: [2](#0-1) 

This function is invoked from `checkoutBranch` and `checkoutCommit`, both of which accept `allowFileProtocol` as a caller-supplied boolean that flows straight through to the submodule update: [3](#0-2) [4](#0-3) 

The safety property this bypasses is git's own submodule protocol allowlist, which is supposed to be the sole barrier preventing a hostile `.gitmodules` file (fully attacker-controlled content that ships inside any cloned/fetched repository) from declaring a submodule pointed at `file:///…` and thereby cloning arbitrary local directories (SSH keys, gitconfig, other repos) into the working tree during checkout. Because the override is passed as a single global `-c` flag to a `--recursive` update, it applies uniformly to every submodule and every nested sub-submodule reachable from the checkout — there is no per-URL vetting analogous to a "publisher allowlist" check performed only at the top level while the underlying primitive (arbitrary submodule URL resolution) remains unrestricted underneath. This is structurally the same broken invariant as the report's Create/Create2 issue: a restriction is enforced only at the outer, directly-observed operation, while a deeper/indirect mechanism reachable from the same call graph (nested submodules) inherits the disabled protection and can be driven entirely by attacker-supplied data (`.gitmodules`).

### Impact Explanation
If `allowFileProtocol` is ever set to `true` for a checkout/branch-switch operation on a repository whose content is not fully trusted (e.g. a freshly cloned or fetched branch containing a modified `.gitmodules`), an attacker who controls that repository content can define a submodule URL as an absolute local path (e.g. `file:///Users/victim/.ssh` or a UNC path on Windows) so that `git submodule update --init --recursive` copies the contents of that local directory into the checked-out working tree. Because the override is applied for the whole recursive submodule graph rather than scoped to specific already-vetted submodules, an attacker only needs to control one submodule entry, at any depth, to trigger a local file/directory read into a location the user will subsequently see, commit, or push — i.e. file read outside the intended repository boundary and potential credential/token exfiltration if the copied content is later committed and pushed.

### Likelihood Explanation
Exploitation requires no local access, no admin rights, and no prior compromise: it only requires the victim to check out a branch/commit from a repository or fork whose `.gitmodules` is attacker-controlled while Desktop's checkout path passes `allowFileProtocol: true`. The exact production call sites that set this flag to `true` (versus leaving the default `false`) were not fully traceable within the available index — this is the primary open question and would need to be confirmed by a developer with full repository access (e.g. via `grep` across `app-store.ts`/`dispatcher.ts` for calls to `checkoutBranch`/`checkoutCommit` with a truthy third/fifth argument). If such a call path exists for untrusted forked/fetched branches, likelihood is high because the trigger is a single ordinary "check out this branch" action.

### Recommendation
- Scope any `protocol.file.allow` override to specific, already-verified submodule URLs instead of passing a blanket `-c protocol.file.allow=always` for a `--recursive` update.
- Before enabling the override, resolve and validate every submodule URL (including nested ones) to ensure none resolve to `file://`/local absolute paths that escape the intended clone root, similar to the existing `resolveWithin` guard used for `filepath` in `dispatcher.ts`.
- Audit all callers of `checkoutBranch`/`checkoutCommit` to confirm `allowFileProtocol` is only ever `true` for operations Desktop itself controls (e.g. its own local test fixtures), never for checkouts sourced from a remote/fork/PR the user does not implicitly trust.

### Proof of Concept
1. Attacker publishes/forks a repository and adds a `.gitmodules` entry: `url = file:///home/victim/.ssh` (or an OS-appropriate sensitive path).
2. Victim clones/fetches this repository in Desktop and checks out the branch containing that `.gitmodules`.
3. If the checkout path that runs passes `allowFileProtocol=true` down to `updateSubmodulesAfterOperation`, Desktop executes `git -c protocol.file.allow=always submodule update --init --recursive`, which happily "clones" `/home/victim/.ssh` into the submodule path inside the working tree.
4. The victim's local sensitive files are now materialized inside the repository's working directory, visible in Desktop's UI, and available to be staged, committed, and pushed — completing local file exfiltration through the recursive submodule mechanism, analogous to how the reported factory contract silently inherits an unrestricted underlying `CREATE`.

    'update',
    '--init',
    '--recursive',
  ]

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
