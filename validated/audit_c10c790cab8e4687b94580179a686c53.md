## Finding: `aptos move verify-package` never actually verifies bytecode, despite claiming to

### Title
`VerifyPackage` CLI command only compares `PackageMetadata` fields and never fetches or compares on-chain bytecode, despite documenting itself as bytecode verification - (File: `aptos-move/cli/src/commands.rs`, `aptos-move/cli/src/stored_package.rs`)

### Summary
The `aptos move verify-package` CLI command is documented as downloading "the package from onchain and verif[ying] the bytecode matches a local compilation of the Move code". In practice it never downloads or compares any bytecode at all — it only compares the `PackageMetadata` struct fields (name, deps, module source text/source-map, manifest, upgrade policy, extension, source digest), none of which are cryptographically bound to the actual on-chain module bytes.

### Finding Description
`VerifyPackage::execute` builds the package locally, extracts `PackageMetadata`, then fetches the on-chain registry **without bytecode**: [1](#0-0) 

```rust
let registry = CachedPackageRegistry::create(client, self.account, false).await?;
...
package.verify(&compiled_metadata)?;
Ok("Successfully verified source of package")
```

`CachedPackageRegistry::create` takes a `with_bytecode` flag which, when `false`, skips fetching any module bytecode from the chain at all: [2](#0-1) 

`CachedPackageMetadata::verify` then only diffs the two `PackageMetadata` structs field by field — name, deps, module metadata (source/source_map/extension), manifest bytes, upgrade policy, extension, and `source_digest`: [3](#0-2) 

None of these fields are derived from or bound to the actual `vector<vector<u8>>` module bytecode that gets stored on-chain via `code::publish_package`. `PackageMetadata.modules[i]` only holds `name`, gzipped `source`, gzipped `source_map`, and an `extension` — never a hash of the compiled bytes: [4](#0-3) 

On the publish path itself, `code::publish_package_txn` accepts `metadata_serialized` and `code` as two independent, publisher-supplied arguments; the Move code and the native `request_publish`/`request_publish_with_allowed_deps` only check module *names* match `expected_modules`, dependency addresses/names against `allowed_deps`, and compatibility of the new bytecode against the old bytecode — never that the bytecode is a faithful compilation of `pack.modules[i].source`: [5](#0-4) 

So there is no on-chain or off-chain mechanism that ties the human-readable `source`/`source_digest` metadata to the actually-deployed bytecode — and the one tool whose explicit purpose is to perform that check (`verify-package`) silently skips it.

### Impact Explanation
Any account (or object/resource account under the permissionless object-code-deployment and resource-account publish flows) can publish a package whose `PackageMetadata` (name, source text, source_digest, manifest) describes benign, auditable Move source, while the actual bytecode bundle passed to `code::publish_package_txn`/`object_code_deployment::publish` implements arbitrary, different logic. A downstream consumer who runs `aptos move verify-package` to confirm the deployed dependency matches its published source will get "Successfully verified source of package" even though the executing bytecode is unrelated to that source. This directly matches the "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" impact category and undermines the trust model the `code_dependency_check` / `allowed_deps` upgrade-policy system relies on (i.e., that a package's declared upgrade policy and dependency graph reflect what is actually running).

### Likelihood Explanation
High likelihood of being hit unintentionally (anyone relying on `verify-package` gets a false sense of security), and straightforward to exploit deliberately: an attacker publishing a package under any permissionless deployment path (object code deployment, resource account) only needs valid-looking metadata; no special privilege or race condition is required, and the discrepancy is invisible to the standard verification tool.

### Recommendation
Make `VerifyPackage` actually fetch on-chain bytecode (`CachedPackageRegistry::create(..., true)` / `get_bytecode`) and compare each on-chain module's bytes against the freshly-built local `compiled_units`, in addition to the existing metadata comparison in `CachedPackageMetadata::verify`. Consider also binding a bytecode hash into `PackageMetadata` (or documenting explicitly that `verify-package` cannot and does not check bytecode equivalence) so downstream tooling and users are not misled.

### Proof of Concept
1. Compile a benign Move package `A` with public source `foo.move`, publish it via `object_code_deployment::publish` (or `code::publish_package_txn`) with metadata (`name`, `source`, `source_digest`, `manifest`) that accurately describes `foo.move`, but pass a different, malicious compiled bytecode blob (same module name, satisfying `expected_modules`, dependency policy, and standard compatibility/verifier checks) instead of the bytecode actually compiled from `foo.move`.
2. As a downstream user, run `aptos move verify-package --account <addr>` against a local checkout of the (benign) `foo.move` source.
3. Observe the command prints "Successfully verified source of package" because `CachedPackageRegistry::create(client, addr, false)` never fetches bytecode, and `CachedPackageMetadata::verify` only compares metadata fields, which match by construction.
4. The malicious bytecode, however, is what actually executes on-chain — completely undetected by the "verification".
