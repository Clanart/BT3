Based on my research, the strongest concrete Protobuf analog to this Sherlock finding is a **wire-type validation gap in the Java Lite/GeneratedMessageLite fast-path extension decoder** (`ArrayDecoders.java`), where a field's *declared* extension type — resolved purely by field number — is trusted to determine how subsequent bytes are consumed, without cross-checking the type against the *actual* wire type byte the attacker encoded on the wire. This mirrors the root cause of the Sherlock bug: a value/type inferred from one part of attacker-controlled input is used downstream without validating it matches what was actually encoded, letting the attacker desynchronize what the parser "thinks" it is decoding from what is actually on the wire.

### Title
Extension decoding in `ArrayDecoders.decodeExtension` trusts declared extension type without validating the encoded wire type - (File: `java/core/src/main/java/com/google/protobuf/ArrayDecoders.java`)

### Summary
`ArrayDecoders.decodeExtensionOrUnknownField`/`decodeExtension`, the extension-parsing path used by the `GeneratedMessageLite` table-driven schema decoder, resolves an unknown field number to a registered extension and then dispatches parsing purely on `extension.getLiteType()`/`extension.descriptor.isPacked()`, never checking `WireFormat.getTagWireType(tag)` against the extension's expected wire type. This is inconsistent with every other extension-merge path in the same codebase — the slower `GeneratedMessageLite.ExtendableMessage.parseExtension` and the full-runtime `MessageReflection.mergeFieldFrom` both explicitly validate the wire type before treating bytes as a known field, falling back to "unknown field" (safe skip) on mismatch, exactly as C++'s `ExtensionSet::FindExtensionInfoFromFieldNumber` does with its `expected_wire_type == wire_type` check.

### Finding Description
- `ArrayDecoders.decodeExtensionOrUnknownField` (lines 763-784) looks up the extension solely via `registers.extensionRegistry.findLiteExtensionByNumber(defaultInstance, number)` — a lookup keyed only by field number — and, if found, unconditionally calls `decodeExtension`, passing the raw `tag`. [1](#0-0) 
- `decodeExtension` (lines 786-1004) never inspects `WireFormat.getTagWireType(tag)` to confirm it matches `extension.getLiteType()`'s expected wire type. It switches purely on `extension.getLiteType()` and `extension.descriptor.isPacked()` to decide how many bytes to consume and how to interpret them (varint, fixed32/64, length-delimited message/group, etc.). [2](#0-1) [3](#0-2) 
- Compare this to the two "safe" extension-merge implementations in the same repo, which both perform the wire-type-matches-declared-type invariant before consuming any payload bytes, treating a mismatch as an unknown field (safely skipped, not misinterpreted):
  - `GeneratedMessageLite.ExtendableMessage.parseExtension`: explicitly compares `wireType` against `FieldSet.getWireFormatForFieldType(extension.descriptor.getLiteType(), isPacked)` for both packed and unpacked cases before dispatching. [4](#0-3) 
  - `MessageReflection.mergeFieldFrom` (full runtime) performs the identical check for both regular fields and extensions. [5](#0-4) 
  - C++'s extension registry lookup enforces the analogous invariant natively: `FindExtensionInfoFromFieldNumber` requires `expected_wire_type == wire_type` (or the packed-repeated special case) before returning a match. [6](#0-5) 

The failed invariant transferring from the Sherlock report is: **"a value read from attacker-controlled input must be validated to be the same value/type used earlier in the computation before it is trusted for a security-relevant action."** In the Solidity bug, the token address used for balance math and the token address used for the actual transfer were allowed to diverge because the contract never checked they were the same. Here, the *type used to decide how many bytes to consume and how to interpret them* (from the extension registry, keyed by field number only) is allowed to diverge from *the type the attacker actually encoded on the wire* (the tag's wire-type bits), because `decodeExtension` never checks the two match. A crafted payload can put a field number that maps to a message/group extension, but encode a VARINT (or FIXED32/64) wire type for it; `decodeExtension`'s `MESSAGE`/`GROUP` branch will still call `decodeMessageField`/`decodeGroupField`, treating the following raw bytes as a length-delimited payload with an implied length prefix, when the actual encoding never intended that interpretation. This desynchronizes the parser's cursor from what a spec-compliant, wire-type-checking decoder (e.g., the C++/full-Java reflection path) would compute for the identical byte stream — producing decoder differentials and field/type confusion within the trusted schema, entirely from a bounded, well-formed-looking payload.

### Impact Explanation
Because parsing proceeds according to the *assumed* (registry-resolved) type rather than the *encoded* wire type, the number of bytes consumed for the mismatched field is wrong relative to what a correct decoder would consume. This can cause:
- Misattribution of subsequent bytes to unrelated tags/fields, corrupting the parsed message state in ways invisible to the caller (the parse does not fail, it silently produces a structurally different, attacker-steered message than what a compliant decoder — or the sender's own encoder — intended).
- A decoder differential between `GeneratedMessageLite`'s Lite/Android fast schema path and the "safe" reflection/full-runtime paths for byte-identical input, which is a direct integrity violation of Protobuf's contract that wire type must gate field interpretation.

I was not able to fully verify, within the remaining tool budget, whether array bounds checks elsewhere in `ArrayDecoders` (e.g., in `decodeMessageField`/`decodeVarint32`) turn every exploitation attempt into a caught `InvalidProtocolBufferException` rather than an exploitable corruption of application-visible message content — this is the main open question and should be validated with a live proof-of-concept in a full Devin session with build/test tooling.

### Likelihood Explanation
Any application on Android/Lite runtime using extensions is reachable: an ordinary client can submit a bounded, syntactically valid binary Protobuf payload through any public `parseFrom` API for a message that declares extensions, with a chosen field number that collides with a known extension but an intentionally mismatched wire-type nibble. No privileged access, hostile schema, or huge/unbounded input is required — this fits the stated threat model precisely.

### Recommendation
Add the missing wire-type validation to `ArrayDecoders.decodeExtensionOrUnknownField`/`decodeExtension`, mirroring the check already present in `GeneratedMessageLite.ExtendableMessage.parseExtension` and `MessageReflection.mergeFieldFrom`: before dispatching on `extension.getLiteType()`, compute `WireFormat.getTagWireType(tag)` and compare it to the extension's expected wire type (accounting for the packed/unpacked distinction), routing any mismatch to `decodeUnknownField` instead of `decodeExtension`.

### Proof of Concept
A conceptual PoC (requires a build environment to execute, which was unavailable in this ask-only session):
1. Define a `.proto` with a message `M` that supports extensions, and an extension field `ext` of type `message` (or any non-varint type) on field number `N`.
2. Hand-craft raw bytes for `M` containing a tag for field number `N` with wire type `VARINT` (instead of `LENGTH_DELIMITED`), followed by a short varint, followed by legitimate bytes for other fields of `M`.
3. Parse this payload via `M.parseFrom(bytes, extensionRegistryContainingExt)` using the `GeneratedMessageLite` (Lite) runtime, and separately via the full-runtime `DynamicMessage`/reflection path with the same registry.
4. Compare the two parse results: the Lite/`ArrayDecoders` path is expected to attempt `decodeMessageField` on the mismatched-wire-type bytes (since `decodeExtension` never checks wire type), likely consuming a different number of bytes than the full/reflection path (which safely treats the mismatch as unknown and skips only the varint), yielding a decoder differential or corrupted subsequent-field state.

I could not run this PoC in this session; a background Devin session with the Bazel/Gradle build for `java/core` would be needed to compile and execute it and confirm the exact runtime outcome (exception vs. silent corruption vs. differential).

  template <typename ExtensionFinder>
  static bool FindExtensionInfoFromFieldNumber(
      int wire_type, int field_number, ExtensionFinder* extension_finder,
      ExtensionInfo* extension, bool* was_packed_on_wire) {
    if (!extension_finder->Find(field_number, extension)) {
      return false;
    }

    ABSL_DCHECK(extension->type > 0 &&
                extension->type <= WireFormatLite::MAX_FIELD_TYPE);
    auto schema_type = static_cast<WireFormatLite::FieldType>(extension->type);

    WireFormatLite::WireType expected_wire_type =
        WireFormatLite::WireTypeForFieldType(schema_type);

    // Check if this is a packed field.
    *was_packed_on_wire = false;
    if (extension->is_repeated &&
        wire_type == WireFormatLite::WIRETYPE_LENGTH_DELIMITED &&
        is_packable(expected_wire_type)) {
      *was_packed_on_wire = true;
      return true;
    }
    // Otherwise the wire type must match.
    return expected_wire_type == wire_type;
  }
