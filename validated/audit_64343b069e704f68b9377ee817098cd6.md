### Title
Unauthenticated `ReceivedOutput` deserialization permits arbitrary unspendable-wallet-balance injection - ([File: `networks/bitcoin/src/wallet/mod.rs`])

### Summary
`ReceivedOutput::read` converts attacker-controlled bytes into an object Semantically asserted to be spendable wallet funds without proving that its `outpoint`, `TxOut`, and key offset describe an output actually observed on-chain. [1](#0-0)  `SignableTransaction::multisig` later validates only that the supplied `TxOut` script can be reproduced from the threshold key plus offset, leaving the claimed amount and `OutPoint` unbound to the real UTXO. [2](#0-1) 

### Finding Description
`Scanner::new` automatically registers the base wallet script with offset zero, so an attacker only needs a known wallet address rather than knowledge of a private offset. [3](#0-2)  `ReceivedOutput::read` accepts a scalar offset, consensus-encoded `TxOut`, and consensus-encoded `OutPoint`, then constructs the spendable-output object without checking that the `OutPoint` resolves to that exact `TxOut`. [1](#0-0) 

`SignableTransaction::new` trusts the injected `TxOut` amount for input accounting, copies the attacker-controlled offset, and turns the attacker-controlled `OutPoint` into a transaction input. [4](#0-3)  It also stores the supplied `TxOut` as the prevout later committed into the Taproot signature. [5](#0-4) 

During signing, the only ownership check is `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey`; no check can or does establish that the referenced outpoint exists, belongs to the wallet, or carries the claimed value. [2](#0-1)  The signing machine then commits to the forged input position and the forged prevout list through `taproot_key_spend_signature_hash`. [6](#0-5) 

### Impact Explanation
An attacker can inject an apparently spendable wallet output whose `value()` reports arbitrary funds even though no such UTXO exists or the supplied `TxOut` does not match the referenced outpoint. [7](#0-6)  The wallet can then select that forged output, calculate fees and payments against its false value, and cause threshold participants to produce shares for a transaction Bitcoin will reject because the input does not exist or its committed prevout differs from the actual UTXO. [6](#0-5)  This is a Medium-severity integrity and availability issue because it corrupts the wallet’s spendable-output set and can consume or stall signing attempts, but it does not make nonexistent Bitcoin spendable. [8](#0-7) 

### Likelihood Explanation
The public attack input is only a serialized `ReceivedOutput`: a canonical zero offset, a `TxOut` containing a known wallet script and arbitrary amount, and an arbitrary `OutPoint`. [9](#0-8)  Because the zero-offset script is always registered for a scannable key, the forged record can satisfy the later script check without secret information. [10](#0-9)  Exploitation requires an integration to deserialize untrusted `ReceivedOutput` bytes and feed the result into `SignableTransaction::new` and `multisig`, which is the exposed untrusted-read path considered here. [11](#0-10) [2](#0-1) 

### Recommendation
Do not let `ReceivedOutput::read` mint a spendable-output claim from unauthenticated bytes alone; bind each serialized output to authenticated scanner provenance, such as an integrity-protected wallet database record or an authenticated checkpoint/block inclusion proof. [1](#0-0)  Before constructing or signing a transaction, revalidate the `OutPoint` against the chain and compare the retrieved UTXO’s full `TxOut`, including value and `script_pubkey`, with the supplied record. [2](#0-1)  If full-chain validation is unavailable, treat deserialized records as unverified candidates rather than spendable `ReceivedOutput`s and keep the real `ReceivedOutput` constructor private to the scanner. [12](#0-11) [13](#0-12) 

### Proof of Concept
A conceptual reproduction is:

```rust
let mut forged = Vec::new();
forged.extend([0u8; 32]); // Secp256k1 scalar offset = 0
forged.extend(serialize(&TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: known_wallet_script,
}));
forged.extend(serialize(&OutPoint::new(attacker_chosen_txid, 0)));

let injected = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
let signable =
  SignableTransaction::new(vec![injected], &payments, None, None, fee_per_vbyte).unwrap();
let machine = signable.multisig(&wallet_threshold_keys).unwrap();
```

The zero offset selects the automatically registered base wallet script, while the supplied `TxOut` and `OutPoint` are attacker-chosen. [9](#0-8) [10](#0-9)  `SignableTransaction::new` accepts the forged one-million-satoshi input as funding and uses the fake `OutPoint` as the transaction input. [4](#0-3)  `multisig` returns `Some` because the supplied script matches `p2tr_script_buf(keys.offset(0).group_key())`, even though the claimed `OutPoint`/`TxOut` pair was never authenticated. [14](#0-13)  Continuing the state machine produces a transaction witness for a spend Bitcoin cannot validate because the referenced input is fabricated or its prevout commitment does not match the real UTXO. [15](#0-14)
