## Finding: Path-boundary check in `resolveWithin` uses a naive `startsWith` instead of a separator-aware comparison [1](#0-0) 

### Title
Path traversal via `startsWith` prefix confusion in `resolveWithin()` used to gate deep-link/AI file access - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is Desktop's generic guard used to make sure a user/attacker-supplied relative path can't escape a trusted root directory (analogous to the report's "cooldown check" that's supposed to gate a risky action but is evaluated against stale/insufficient state). The final containment check is a plain string comparison, `realResolved.startsWith(realRoot)`, with no check that the next character after the root is a path separator. This is the same class of bug as the original report: a boundary/validity check that looks correct but doesn't actually enforce the invariant it claims to (staked-RPL still withdrawable / "resolved path is inside root" still bypassable).

### Finding Description [2](#0-1) 
```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
```
Because `startsWith` performs a raw character comparison, any resolved path whose string representation happens to begin with the root's string will pass, even if it is actually a *sibling* path, e.g.:

- `realRoot = "/Users/victim/Documents/GitHub/myrepo"`
- `realResolved = "/Users/victim/Documents/GitHub/myrepo-secrets/config.json"`

`"…/myrepo-secrets/config.json".startsWith("…/myrepo")` is `true`, so the function returns a path that is **not actually inside the repository**, defeating the entire purpose of the guard.

This helper is relied upon as the sole containment check in at least two real attacker-influenced call sites:

1. **Deep link handler** — `filepath` is taken verbatim from the URL query string of an `x-github-client://openrepo/...` link (`parseAppURL` in `app/src/lib/parse-app-url.ts`, lines 98-125) and only checked for being non-absolute before being passed to `resolveWithin`: [3](#0-2) 

2. **AI conflict-resolution context builder** — file paths from a conflicted merge are resolved the same way before their contents are read and sent as Copilot context: [4](#0-3) 

The unit tests for `resolveWithin` (`app/test/unit/path-test.ts`) cover `..` traversal and symlink escape, but never test the "sibling directory sharing a name prefix" case, confirming this specific boundary condition is unverified. [5](#0-4) 

### Impact Explanation
If a victim's filesystem contains a directory adjacent to the opened repository whose name has the repository's directory name as a prefix (a common occurrence: `myrepo`, `myrepo-old`, `myrepo.bak`, `myrepo (copy)`, `myrepo-secrets`, etc.), a crafted `x-github-client://openrepo/<url>?filepath=../myrepo-secrets/<file>` deep link — something the user clicks, satisfying the "link a user clicks" attacker model — can cause Desktop to treat an out-of-repository path as safely contained. Depending on the call site this can:
- Reveal (via `shell.showItemInFolder`) the existence/location of files outside the intended repository root, or
- Cause file content outside the repo to be read and forwarded to the Copilot conflict-resolution flow, i.e., a "read outside the repo" primitive.

### Likelihood Explanation
Exploitation depends on a coincidental/attacker-arranged sibling-directory name overlap, which lowers likelihood versus a pure logic flaw, but the check itself is unconditionally broken (it is a string-prefix bug, not a probabilistic race), and the two identified call paths (deep link `filepath`, AI conflict context) are both reachable without any git remote or local trust prompt in front of them.

### Recommendation
Change the final comparison in `_resolveWithin` (`app/src/lib/path.ts`) to require a path-separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
and add a regression test asserting that a sibling directory sharing the root's name as a prefix (e.g. `root = /tmp/x/repo`, target `/tmp/x/repo-secret/file`) is rejected.

### Proof of Concept
1. Victim has `~/Documents/GitHub/myrepo` (opened in Desktop) and `~/Documents/GitHub/myrepo-secrets/token.txt` on disk.
2. Attacker sends the victim a link: `x-github-client://openrepo/https://github.com/owner/myrepo?filepath=../myrepo-secrets/token.txt`.
3. Desktop's protocol handler calls `handleAppURL` → `parseAppURL` → `openRepositoryFromUrl` → `resolveWithin(repository.path, '../myrepo-secrets/token.txt')`.
4. `resolve()` correctly computes `.../myrepo-secrets/token.txt`, but the containment check `realResolved.startsWith(realRoot)` evaluates `true` because `"…/myrepo-secrets/token.txt".startsWith("…/myrepo")`.
5. `resolveWithin` returns the out-of-repo path instead of `null`, and Desktop calls `shell.showItemInFolder()` on it, exposing a file outside the repository that the "inside repo" guard was supposed to block.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
