### Title
PedPoP blame proofs publicly expose ECDH decryption keys, letting any party decrypt secret shares intended for others - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class in the report is "an unauthenticated endpoint that returns a secret credential to anyone who can enumerate/poll it." PedPoP has the same shape: `Encryption::decrypt` unconditionally produces an `EncryptionKeyProof` whose `key` field is the raw ECDH shared point (the ChaCha20 decryption key preimage), and `Decryption::decrypt_with_proof` acts as a public decryption oracle for anyone holding that proof plus the ciphertext — including non-participants via `AdditionalBlameMachine::new`, which is explicitly usable by parties who were never in the DKG.

### Finding Description
- `Encryption::decrypt` computes `key = ecdh(self.enc_key, msg.key)` and returns it inside `EncryptionKeyProof { key, dleq }` for every share, not only faulty ones (`crypto/dkg/pedpop/src/encryption.rs:487-500`). The DLEq only proves `key = enc_key_recipient * msg.key`; it does not protect `key`, which is the exact shared secret fed to `cipher()` (`encryption.rs:95-133`, static IV, raw ChaCha20 keystream).
- `calculate_share` stores this proof per sender in `blames` and hands it out inside `PedPoPError::InvalidShare { blame: Some(blame) }` (`crypto/dkg/pedpop/src/lib.rs:477-499`).
- `Decryption::decrypt_with_proof` then takes `proof.key` directly as the ECDH result and applies the keystream, returning plaintext (`encryption.rs:381-396`). It is reachable from `blame_internal` (`lib.rs:575-609`), and `AdditionalBlameMachine::new` builds a blame evaluator "capable of evaluating blame regardless of if the caller was a member in the DKG protocol" from only public commitment messages (`lib.rs:639-662`).

Concretely: when a recipient raises blame against sender `l` by publishing `(msg, EncryptionKeyProof)`, `msg` decrypts to `share_{l→recipient}`. If the share was valid (a lying accuser, or an accuser who mis-mapped the message), `blame` resolves `recipient` as faulty — but the proof is already public, so any observer runs `decrypt_with_proof` and recovers a valid secret share. Because a participant's final secret is `Σ_l share_{l→i}` (`lib.rs:484`), a malicious recipient who accuses all senders publishes decryption keys for every per-sender share, making its full secret share publicly recoverable to unauthenticated observers.

### Impact Explanation
This is the analog of the SignalK "poll the request ID, receive the issued token" primitive: possessing a public identifier (the blame proof, which is *designed* to be published for adjudication) yields the secret payload (the ECDH output / decrypted share) with zero authorization. It causes (a) public disclosure of a threshold secret share — reducing effective threshold security by a full share for every leaked victim, since any observer gains `s_i` needed toward `t`-of-`n` reconstruction — and (b) disclosure of per-sender share contributions that were intended to remain confidential to the recipient.

### Likelihood Explanation
A single malicious recipient (or a fault-injecting network that mislabels authenticated ciphertexts, provoking an honest recipient to blame) triggers proof publication; blame data is inherently broadcast to all parties for adjudication. `AdditionalBlameMachine` exists precisely so third parties can evaluate it, so the ciphertext is expected to circulate. No collusion, no privileged position, and no cryptography breakage is required — just one accusation against an honest sender.

### Recommendation
`EncryptionKeyProof` should not carry the raw ECDH point. Either (a) make blame a two-phase commit/reveal where the key is revealed only after the accused ciphertext is authenticated and the accusation validated, or (b) replace `key` disclosure with a verifiable-decryption proof (e.g., a Chaum-Pedersen proof of correct plaintext relative to commitments) so `decrypt_with_proof` never needs the shared point. At minimum, do not return `EncryptionKeyProof` from `decrypt` unconditionally; derive it only inside the blame path after the share is known-invalid, so honest valid shares can never be unmasked.

### Proof of Concept
```

1. Honest senders l send EncryptedMessage<C, SecretShare> to i.

5. Observer computes s_i = Σ_l share_l — recovering participant i's ThresholdKeys secret_share
   [lib.rs:484, and ThresholdKeys::new at lib.rs:528].
```
