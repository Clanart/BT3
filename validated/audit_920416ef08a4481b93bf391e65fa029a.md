### Title
GitHub-host classification trusts attacker-controlled `WWW-Authenticate` header before performing real verification, allowing a malicious git remote to trigger a spoofed GitHub sign-in/OAuth flow - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
`getEndpointKind` classifies a remote as an `'enterprise'` (i.e. trusted GitHub) host purely from the `WWW-Authenticate` header that git forwards from the remote's HTTP 401 response, before it ever reaches the real network-based verification (`isGitHubHost`) later in the same function.

### Finding Description
When git needs credentials for an HTTPS remote, it captures any `WWW-Authenticate` response headers and forwards them to the credential helper as `wwwauth[n]` fields. `getEndpointKind` iterates these and, if the value contains the literal substring `realm="GitHub"`, immediately returns `'enterprise'`: [1](#0-0) 

This check runs *before* the function's own network-based confirmation step, `isGitHubHost(endpoint)`, which exists specifically to verify unknown hosts are genuinely GitHub Enterprise instances: [2](#0-1) 

Because the header value is fully attacker-controlled (it comes from the HTTP response of whatever server the user's git operation is talking to), any HTTPS git remote can respond with `WWW-Authenticate: Basic realm="GitHub"` and be classified as `'enterprise'` regardless of its actual hostname or identity.

That classification feeds `getCredential`, which - since no stored account exists for the fabricated `apiEndpoint` - automatically pops the "Sign in to GitHub" dialog, without the user having asked to sign in: [3](#0-2) 

`trampolineUIHelper.promptForGitHubSignIn` then binds an Enterprise sign-in flow to the attacker's own origin: [4](#0-3) 

If the user proceeds with "Sign in using your browser," `authenticateWithBrowser` opens the OAuth authorize URL built from that attacker-controlled endpoint, and on completion `resolveOAuthRequest`/`requestOAuthToken` POSTs the app's OAuth `client_id`/`client_secret` and the authorization code to that same attacker-controlled origin: [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who controls an HTTPS git remote (e.g. a repo the user clones/fetches/pushes to) can cause Desktop to spuriously classify their server as a genuine GitHub/Enterprise host and auto-launch a branded "Sign in to GitHub" dialog scoped to an arbitrary attacker origin, without the user requesting sign-in. Completing that flow sends the app's OAuth `client_id`/`client_secret` and authorization code to the attacker's server, and any "account" the attacker's fake OAuth endpoint returns gets stored locally as a bound GitHub account for that endpoint. This matches the in-scope impact category of "unauthorized OAuth or account binding."

However, note two mitigating factors: (1) GitHub Desktop's OAuth `client_secret` is a value shipped inside every installed client and is not a true secret (it is extractable by reverse-engineering the app), so its exfiltration here adds little beyond what is already obtainable; (2) exploitation requires the user to notice and click through the "Sign in using your browser" prompt in their system browser, where the non-github.com address bar is visible, which is a meaningful practical mitigation and pushes part of this toward user-awareness/social-engineering territory that the scope says to reject.

### Likelihood Explanation
Triggering the flawed classification itself requires no user interaction beyond a normal git fetch/push/clone against an attacker-controlled remote returning a crafted `WWW-Authenticate` header - this part is fully attacker-controlled and automatic. Completing the more damaging OAuth exchange, however, requires the user to actively click through the sign-in dialog and complete an OAuth grant in their browser without noticing the mismatched domain, which lowers overall likelihood of the full high-impact chain.

### Recommendation
Reorder `getEndpointKind` so that unauthenticated hosts are never classified as `'enterprise'` from header content alone without the same `isGitHubHost` network verification applied to the fallback path, or drop the header-based shortcut and always confirm via `isGitHubHost`/an authoritative GitHub-specific probe (e.g. checking a signed/verifiable response) before treating an unknown host as GitHub-branded and before auto-launching any sign-in UI.

### Proof of Concept
1. Attacker sets up an HTTPS git server (e.g. `https://evil.example.com/repo.git`) that responds to unauthenticated Git HTTP requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote in GitHub Desktop and performs a fetch/push.
3. Git forwards the header to the trampoline credential helper; `getEndpointKind` (app/src/lib/trampoline/trampoline-credential-helper.ts:157-165) classifies it as `'enterprise'` without contacting the host to verify.
4. Since no account exists for `getEnterpriseAPIURL('https://evil.example.com')`, Desktop automatically shows `PopupType.SignIn` bound to `https://evil.example.com`.
5. If the victim clicks "Sign in using your browser," the browser is sent to `https://evil.example.com/login/oauth/authorize?client_id=<Desktop client id>&...`, and on completion Desktop POSTs `client_id`/`client_secret`/`code` to `https://evil.example.com/login/oauth/access_token`, with the attacker able to return an arbitrary fake account payload that Desktop stores as a bound GitHub account.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

        type: PopupType.SignIn,

      })

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
