### Title
Git argument/option injection via unsanitized branch names in `getBranchMergeBaseChangedFiles` - (File: `app/src/lib/git/diff.ts`)

### Summary
`getBranchMergeBaseChangedFiles` builds a `git diff` argv where `baseBranchName` and `comparisonBranchName` are inserted as positional arguments *before* the `--` separator, and the separator has nothing after it. Because the ref names are not validated to disallow a leading `-`, a ref whose name starts with `-` would be parsed by `git` as an option rather than as a revision.

### Finding Description
The argv is constructed as: [1](#0-0) 

`baseBranchName` and `comparisonBranchName` occupy positions immediately after `--merge-base`, and the `--` terminator is appended at the very end of the array with no pathspec following it. In git's CLI argument grammar, `--` only prevents *arguments after it* from being treated as options; it does nothing to protect the two branch-name arguments that come before it. If either branch name begins with `-` (e.g. `--output=/tmp/x`, or any other `diff`-recognized flag), git will parse it as an option to `git diff` rather than as a revision, changing the command's behavior.

`getMergeBase` (in `app/src/lib/git/merge.ts`) is called with the same two names and has the identical weakness — `['merge-base', firstCommitish, secondCommitish]` with no `--` at all: [2](#0-1) 

For the injection to be reachable, the attacker needs to get a ref/branch name onto the user's machine that begins with `-` and have GitHub Desktop pass that name into this function as `baseBranchName`/`comparisonBranchName`. Branch names beginning with `-` cannot normally be created with `git branch`/`git checkout -b` locally (git's porcelain refuses them), but git's `check-ref-format` does not universally forbid this pattern in refs received over the wire in every historical/edge case, and third-party tooling / crafted repositories have in the past been used to smuggle such refs. I was not able to fully verify, within this review, the exact upstream call chain in `app-store.ts` that supplies these two branch-name parameters (i.e., whether they always originate from `Branch.name` objects that Desktop itself derived from `for-each-ref`/API branch lists, and whether those sources reject leading dashes before this function is ever reached). That verification would require tracing every caller of `getBranchMergeBaseChangedFiles` in `app/src/lib/stores/app-store.ts` and confirming there is no earlier sanitization step.

### Impact Explanation
If reachable with an attacker-supplied branch name, the impact matches the class described in the question: the injected flag could suppress or corrupt `--raw`/`--numstat` output (hiding or fabricating file entries in the merge-base changed-files list used to build commit/PR comparison summaries), or, in the worst case, cause git to write to an attacker-chosen path via an option like `--output=<path>` if that flag is accepted in this diff invocation. This would count as "silent corruption of what the user commits/pushes" and potentially "file write outside the repo," which are in-scope impacts.

### Likelihood Explanation
Likelihood is uncertain rather than confirmed. The known blocking factor is that git generally prevents creating local branches with names starting with `-` via normal porcelain, which is why this specific injection class is usually mitigated at the ref-creation layer rather than at each call site. Whether GitHub Desktop's branch enumeration (from local refs or GitHub API branch lists) could ever surface a hostile name of this shape into `baseBranchName`/`comparisonBranchName` was not verified in this pass — I could not locate strong evidence in the indexed code that such validation happens before these two functions are invoked, nor definitive proof that it doesn't. This should be confirmed with a proof-of-concept against a live checkout (attempt to fetch/create a ref named `--output=/tmp/x` and drive it into `getBranchMergeBaseChangedFiles`) before treating this as confirmed-exploitable.

### Recommendation
Regardless of the exact likelihood, this is a latent defensive gap that should be hardened: insert `--` immediately before the revision arguments as well (i.e., `['diff', '--merge-base', '--', baseBranchName, comparisonBranchName, ...]` is not valid git syntax for `--merge-base`, so instead qualify the refs, e.g. pass them as `` `${baseBranchName}^{commit}` `` or validate/reject ref names that start with `-` before use), and apply the same fix to `getMergeBase` in `app/src/lib/git/merge.ts`. A generic guard (e.g., a shared `assertValidRefName`/`isSafeRevision` check rejecting leading `-`) applied to every function that interpolates a caller-supplied branch/ref name into `git` argv would close this class of issue codebase-wide.

### Proof of Concept
Not independently verified in this review. Suggested reproduction: create/fetch a repository containing a ref that resolves to the name `--output=/tmp/pwned` (or another `git diff`-recognized flag), trigger the code path in `app-store.ts` that calls `getBranchMergeBaseChangedFiles` with that name as `baseBranchName` or `comparisonBranchName`, and check whether the resulting `git diff --merge-base` invocation creates/truncates the target file or returns malformed/empty changed-file data instead of erroring out as an invalid revision.
