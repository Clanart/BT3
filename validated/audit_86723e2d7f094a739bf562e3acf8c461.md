## Analysis

The external report's core broken invariant: **a "no value assigned yet" sentinel (zero address) is treated as if it were a legitimate value requiring/producing a valid signature check**, letting an attacker cheaply satisfy or subvert an authorization check that should have been skipped/rejected for that sentinel.

The direct local analog is the **relayer delivery-receipt decoder** used for both fee accumulation and delivery-reward claims in `pallet-ismp-relayer`.

### Title
Missing zero-address guard in `decode_receipt_relayer` lets an unset/zero delivery receipt be treated as a valid relayer identity - (File: modules/pallets/relayer/src/accumulate.rs)

### Summary
`Pallet::decode_receipt_relayer` decodes the `RequestReceipts[commitment]` value proven from a destination chain into "the delivering relayer's address/bytes," for use both in `accumulate()` (fee distribution) and `process_outbound_request_delivery_claim()` (reward payout). [1](#0-0) 

### Finding Description
The Pharos branch of `decode_receipt_relayer` accepts any 32-byte raw value and slices out `raw[12..]` as the address with no check that it is non-zero:
```
s if crate::is_pharos(&s) =>
    if raw.len() == 32 {
        Ok(Address::from_slice(&raw[12..]).0.to_vec())
    } else {
        Err(Error::<T>::ProofValidationError)
    },
``` [2](#0-1) 

This is structurally identical to `decode_epochs_slot_address`, used by the sibling `outbound_consensus.rs` claim path, except that function explicitly special-cases the zero value and rejects it as "not proven":
```
if crate::is_pharos(&state_id) && raw.len() == 32 {
    let addr = Address::from_slice(&raw[12..]);
    return if addr == Address::ZERO { None } else { Some(addr) };
}
``` [3](#0-2) 

The team's own test suite documents *why* this guard exists — "Defence-in-depth: an explicitly RLP-encoded zero address is rejected the same way an unset slot is, so a malicious actor can't claim a reward by writing zeros," and separately notes the Pharos format is a *raw 32-byte ABI-padded word* rather than RLP, which does not get the same "EVM prunes zero-valued slots into non-membership proofs" guarantee that protects the standard EVM/RLP branches: [4](#0-3) [5](#0-4) 

`decode_receipt_relayer`'s output feeds directly into `validate_results`, which uses it as the map key for fee accumulation with no subsequent zero check, and into `accumulate()`'s `Fees::try_mutate(state_machine, delivery_address, ...)`/`Nonce` bookkeeping, and into `process_outbound_request_delivery_claim`'s `ensure!(recovered == delivered_by, ...)` comparison: [6](#0-5) [7](#0-6) [8](#0-7) 

Unlike the EVM/RLP branch (where a genuinely-unset storage slot is normally pruned to a non-membership proof and never reaches the decoder as `Some(all-zero)`), the Pharos branch reads a fixed-width raw word whose zero-value case is exactly the "not yet delivered" state on that chain family — yet the decoder here has no `== ZERO` rejection mirroring `decode_epochs_slot_address`.

### Impact Explanation
If a Pharos destination's `RequestReceipts[commitment]` slot can be membership-proven as all-zero (i.e., commitment exists on-chain but delivery has not actually happened, or the format allows a provable zero word distinct from true non-membership), `accumulate()` will:
- Attribute the source-side fee to `delivery_address = address(0)` bytes, permanently locking that fee in `Fees[state_machine][0x00...]`, unclaimable by any real relayer, and
- Mark the underlying `RequestCommitments[req].claimed = true`, permanently barring the legitimate delivering relayer from ever accumulating the fee for that commitment once delivery is later completed.

This is a fund-loss / logic-attack class outcome (irrecoverable fee lock plus griefing of the legitimate relayer's future claim) reachable through the unsigned, permissionless `accumulate` extrinsic and the delivery-claim extrinsic, without needing a malicious relayer, prover, or admin — matching the required "loss of funds" / "logic attacks" impact categories.

### Likelihood Explanation
Likelihood is chain-format-dependent: the standard EVM/RLP branches are protected by the underlying Merkle-Patricia-Trie's "prune zero-valued slots into non-membership proofs" property, so this is not reachable there. The Pharos branch's raw fixed-width-word format explicitly does not inherit that guarantee (as the codebase's own comments/tests point out when justifying the equivalent guard in `decode_epochs_slot_address`), making the missing check in `decode_receipt_relayer` a real gap for that state-machine family, and an inconsistency versus the sibling function that was already hardened for the exact same bug class.

### Recommendation
Mirror `decode_epochs_slot_address`'s explicit zero-value rejection inside `decode_receipt_relayer` for the Pharos (and, defensively, the substrate `<=32`-byte) branch: treat an all-zero decoded address/bytes as "not proven" (`Err(Error::<T>::ProofValidationError)` / equivalent to non-membership) rather than as a valid relayer identity, so that neither `accumulate()` nor `process_outbound_request_delivery_claim()` can attribute fees or mark commitments claimed against the zero sentinel.

### Proof of Concept
1. On a Pharos destination chain, the `RequestReceipts[commitment]` slot for a given `commitment` is provably a 32-byte all-zero word (not yet delivered, but the slot yields a membership proof rather than non-membership due to Pharos's raw-word storage format).
2. An unprivileged caller submits `accumulate()` with a `WithdrawalProof` whose `dest_proof` proves this all-zero slot for that `commitment`.
3. `verify_withdrawal_proof` returns `Some(all-zero 32 bytes)` for the dest key; `validate_results` calls `decode_receipt_relayer`, which (Pharos branch) happily returns `address(0)` bytes with no rejection.
4. `accumulate()` sets `delivery_address = address(0)` bytes, credits `Fees[state_machine][0x00..00]` with the source-side fee, and marks the commitment `claimed = true` in `RequestCommitments`.
5. The fee is now permanently stranded at the zero-address bucket, and the real relayer who later actually delivers the request can never accumulate that fee, since the commitment is already flagged `claimed`.

impl<T: Config> Pallet<T> {
	/// Decode a proven `RequestReceipts[commitment]` value into the delivering
	/// relayer's bytes. EVM stores the address RLP encoded, substrate stores the
	/// signer bytes or a signature to recover the signer from. Used by both fee
	/// accumulation and the outbound request delivery claim.
	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
			s if s.is_substrate() => {
				use codec::Decode;
				let bytes =
					<Vec<u8>>::decode(&mut &*raw).map_err(|_| Error::<T>::ProofValidationError)?;
				Ok(if bytes.len() > 32 {
					Signature::decode(&mut &*bytes)
						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
	}
