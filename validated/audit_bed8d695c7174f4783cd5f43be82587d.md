### Title
`ThresholdKeys::read`/`new` accepts a claimed participant index and group key without verifying the secret share binds to them - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to Hail trusting an unverified `email` claim instead of the bound `sub`, `ThresholdKeys` (constructed directly or via `ThresholdKeys::read` from untrusted bytes) accepts a claimed `Participant` index `i`, an arbitrary `secret_share`, and an arbitrary `verification_shares` map, then derives `group_key` solely from `verification_shares[1..=t]` — never checking that `C::generator() * secret_share == verification_shares[i]`. The holder thereby "claims" membership in a group (analogous to claiming an org domain via email) with no cryptographic proof that their share actually belongs to the claimed key.

### Finding Description
- `ThresholdKeys::new` in `crypto/dkg/src/lib.rs:349-391` validates only `verification_shares.len() == n` and that indexes are `<= n`. It computes `group_key` by interpolating `verification_shares` over participants `1..=t` and stores the supplied `secret_share` verbatim. There is no check binding `secret_share` to `verification_shares[params.i()]`.
- `ThresholdKeys::read` in `crypto/dkg/src/lib.rs:573-633` reads `t`, `n`, `i`, the interpolation mode, `secret_share`, and `n` verification shares entirely from attacker-supplied bytes, then calls `new`. It uses `<C as Ciphersuite>::read_G` (not the FROST `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131` which rejects the identity), so identity points in `verification_shares` are accepted.
- Consequently, crafted bytes can claim any participant index `i` and any `group_key` (e.g., a victim multisig's group key by setting `verification_shares[1] = victim_key` with `t = 1` and identity/other points for the rest) while holding a `secret_share` that does not correspond.

### Impact Explanation
An unprivileged party who can feed serialized `ThresholdKeys` (e.g., keys transmitted for registration/scanning) can cause a node to adopt a key set whose `group_key()` / `params().i()` claim an identity the secret does not satisfy:
- If `group_key` is registered as a deposit address, outputs scanned to it are credited to a key set the holder cannot sign for — funds are reported received but are unspendable through this `ThresholdKeys` (the offset/scalar tweaks in `tweak_keys`, `networks/bitcoin/src/wallet/mod.rs:46-75`, only make it worse).
- If the claimed `i` collides with an honest index, `view()`/`sign` produce shares that fail `verify_share` (`crypto/frost/src/algorithm.rs:89-94`), causing blame/abort during signing sessions.

### Likelihood Explanation
Medium. Exploitation requires an untrusted party to supply serialized `ThresholdKeys` to a `read`/registration path, which is plausible in coordinator/processor flows where key material is transported. The cryptographic safety net (share verification in FROST) prevents forged signatures, but the unverified identity claim still permits misattribution of funds/identity before that check is reached — mirroring the Hail report's "account created under an unverified domain claim, usable until audited" profile.

### Recommendation
In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`, the untrusted boundary), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject identity verification shares (use the identity-rejecting `read_G` semantics). This binds the claimed participant index to the secret, as binding the OAuth `sub` does in the Hail fix.

### Proof of Concept
```rust
// Crafted bytes for ThresholdKeys::<Secp256k1>::read:
//   t = 1, n = 1, i = 1
//   interpolation = 1 (Lagrange)
//   secret_share = random s            // NOT related to verification share
//   verification_shares[1] = victim_group_key  // arbitrary claimed key
//
// ThresholdKeys::new then computes:
//   group_key = verification_shares[1] * lagrange(1,{1}) = victim_group_key
// and never asserts G * s == verification_shares[1].
//
// Result: keys.group_key() == victim_group_key while
// keys.original_secret_share() == s is unrelated. Any deposit scanned to
// victim_group_key is credited to this key set yet no valid FROST share can be
// produced: verify_share(victim_key, ..., s_derived_share) fails in
// Algorithm::verify_share.
```
