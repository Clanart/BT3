### Title
OP_RETURN data output omitted from weight/vbytes and fee calculation in `SignableTransaction::new` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the health-factor precision bug — where a computed value missing a scaling term is compared against a threshold, making the check silently wrong — `SignableTransaction::new` computes `weight`, `vbytes`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check using only `payments` (and optionally `change`), while the actual signed transaction also includes an `OP_RETURN` output carrying up to 80 bytes of data. The data output is pushed to `tx_outs` before the weight is ever measured, but `calculate_weight_vbytes` is never given the data output, so the entire fee/size accounting silently omits it.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- Lines 193-202: if `data` is specified, an `OP_RETURN` `TxOut` is appended to `tx_outs`.
- Line 204: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` is called with only `payments` — the OP_RETURN output (present in the final tx) is not represented.
- Lines 224-235: the change-recalculation path calls `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — again, the OP_RETURN output is omitted.
- Line 206: `needed_fee = fee_per_vbyte * vbytes` uses the under-measured `vbytes`.
- Line 241: `weight > MAX_STANDARD_TX_WEIGHT` is checked against the under-measured `weight`.

`calculate_weight_vbytes` (lines 62-127) builds a template `Transaction` and calls `tx.weight()`; since the OP_RETURN output is never added to that template, its weight (~90+ vbytes for 80 bytes of data) is excluded from every downstream computation, even though the OP_RETURN is included in the actual transaction constructed at lines 245-255 and signed in `TransactionSignMachine::sign` (lines 373-397, sighash over `Prevouts::All`).

Just as the missing `DECIMALS` factor made every `healthFactor` compare incorrectly against `DECIMAL`, the missing data-output term makes `needed_fee` and the weight check compare incorrectly against reality: the transaction is systematically larger than what the fee rate was applied to, and the max-weight guard can pass for a transaction that actually exceeds the standard weight limit.

### Impact Explanation
The signed transaction pays `fee_per_vbyte * vbytes` where `vbytes` excludes the OP_RETURN output, so the effective on-chain feerate is lower than requested and can fall below the mempool minimum relay feerate even though the `TooLowFee` check (line 211) passed. The resulting transaction may not relay or confirm, leaving funds locked in an unconfirmable spend — outputs reported as spent/planned but not actually spendable on-chain. Additionally, a transaction at the `MAX_STANDARD_TX_WEIGHT` boundary plus an OP_RETURN can exceed the standard weight limit while passing the `TooLargeTransaction` check, producing a non-standard transaction that no default node will relay.

### Likelihood Explanation
Any `SignableTransaction::new` call with `data.is_some()` triggers the miscalculation; the data path is a documented feature (OP_RETURN up to 80 bytes) reachable from ordinary transaction construction. No attacker sophistication is needed — the fee underpayment occurs on every transaction carrying data, proportional to the data length.

### Recommendation
Include the OP_RETURN output in the weight/vbytes estimation: either pass the data output into `calculate_weight_vbytes` (e.g., an `Option<&ScriptBuf>` for the OP_RETURN script appended to the template transaction), or call it on the fully-constructed `tx_outs`/`data` so that `weight`, `vbytes`, `needed_fee`, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, change, Some(vec![0; 80]), fee_per_vbyte)`. The returned `SignableTransaction`'s `tx` contains an OP_RETURN `TxOut` (~90 bytes serialized), yet `needed_fee()` equals `fee_per_vbyte * vbytes` computed without it. Comparing `tx.weight()` / `get_virtual_tx_size` of the final `Transaction` against the `weight`/`vbytes` used shows a ~90-vbyte discrepancy: the real feerate is `(fee_per_vbyte * vbytes) / (vbytes + ~90)`, below the specified rate and potentially below `DEFAULT_MIN_RELAY_TX_FEE`, which the code intended to enforce.
