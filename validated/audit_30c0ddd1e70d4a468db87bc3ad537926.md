### Title
Path-containment check in `resolveWithin` uses unanchored prefix match, allowing symlink-based escape from the repository root when opening deep-link file paths - (File: app/src/lib/path.ts)

### Summary
`resolveWithin` (used by the `x-github-client://openRepo` deep-link handler to open a `filepath` supplied in the URL relative to the target repository) validates containment with `realResolved.startsWith(realRoot)`. This is a classic unanchored-prefix check: it does not verify that `realResolved` is followed by a path separator (or is exactly equal to `realRoot`), so any real path that merely shares `realRoot` as a string prefix (e.g. a sibling directory `foo-secrets` when `realRoot` is `.../foo`) is treated as "inside" the repository. [1](#0-0) 

### Finding Description
`_resolveWithin` normalizes the requested relative path, resolves it against the root, and then calls `realpath` on both the root and the resolved candidate to defeat symlink tricks that stay purely within path syntax: [1](#0-0) 

The final containment test, however, is a plain string `startsWith`, not a boundary-aware comparison (`realResolved === realRoot || realResolved.startsWith(realRoot + sep)`). If a repository (which is attacker-controlled content the victim cloned, or content fetched via `git pull`/`fetch` from an attacker-controlled remote) contains a symlink that resolves to a real, existing path on the victim's machine whose name has `realRoot` as a literal prefix (for example `realRoot = /Users/victim/Documents/GitHub/foo` and the symlink target realpath is `/Users/victim/Documents/GitHub/foo-secrets/config.json`), the check passes even though the resolved path is a completely different, sibling directory outside the repository.

This function is reached from the deep-link handler `openRepositoryFromUrl`, which takes an attacker-controlled `filepath` from a `x-github-client://openRepo?...` URL that the user clicks, resolves it against the matched local repository's path, and then reveals it in the OS file manager: [2](#0-1) 

The existing guards — the `isAbsolute(filepath)` rejection and `resolveWithin`'s null-byte/realpath checks — do not stop this path, because the bypass happens entirely inside the `startsWith` boundary check itself; the attacker never needs `..` segments or absolute paths, only a symlink whose *resolved* target string happens to prefix-match the root.

### Impact Explanation
A successful bypass lets an attacker-crafted repository, combined with a deep link the victim clicks, cause GitHub Desktop to read/reveal a filesystem path outside the intended repository root — the exact "read outside the repo" class called out as valid impact. Because `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are the app's general-purpose containment primitive (not only used for the deep link, but documented as the guard against "path traversal attacks where a crafted URL tricks the UI into deriving a clone path outside the intended base directory" per `app/src/lib/git/clone.ts`), any other current or future caller that relies on this primitive inherits the same unanchored-prefix flaw.

### Likelihood Explanation
Exploitability is constrained: the attacker needs (a) the victim to clone/open a malicious repository containing a symlink, and (b) a real, pre-existing sibling path on the victim's disk whose name is `realRoot`'s name plus an extra suffix (since Node's `realpath` requires the target to exist). This is a real but narrow condition — plausible in shared/team directory layouts where repos with related prefixed names commonly coexist (e.g. `project` and `project-internal`), but not universally guaranteed. The underlying code defect (missing separator check) is unconditionally present regardless of how often the precondition is met.

### Recommendation
Change the final comparison in `_resolveWithin` to an anchored check, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the same `join`/`normalize`/`resolve`-family separator convention already passed via `options`, and add a regression test with a sibling directory sharing a prefix name (mirroring the existing symlink tests in `app/test/unit/path-test.ts`).

### Proof of Concept
1. Attacker publishes a repository containing a symlink `escape -> /Users/victim/Documents/GitHub/foo-secrets/config.json` (a path that plausibly exists on many dev machines, e.g. an adjacent "-internal"/"-secrets" checkout).
2. Victim clones this repository to `/Users/victim/Documents/GitHub/foo` (GitHub Desktop's default clone location convention).
3. Attacker sends the victim a deep link: `x-github-client://openRepo/https://github.com/attacker/foo?filepath=escape`.
4. `openRepositoryFromUrl` matches the local repo by URL, sees `filepath = "escape"` is not absolute, and calls `resolveWithin(repository.path, "escape")`.
5. `realpath(resolve(root, "escape"))` follows the symlink to `/Users/victim/Documents/GitHub/foo-secrets/config.json`; `realResolved.startsWith(realRoot)` is `true` because `"foo-secrets"` starts with `"foo"`, so the function returns the escaped path instead of `null`.
6. `shell.showItemInFolder(resolved)` reveals the out-of-repo file to the attacker's target, confirming the containment check was bypassed. [3](#0-2)

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
