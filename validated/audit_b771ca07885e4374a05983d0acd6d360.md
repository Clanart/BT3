## Title
Unvalidated attacker-controlled `clone_url` from PR head repository is used to add a git remote and fetch during PR checkout - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The Alchemix report is about a function (`notifyRewardAmount`) that lacks the access control its sibling function (`addRewardToken`) enforces, letting an unprivileged caller inject attacker-chosen data (a token address) into contract state that a privileged workflow (`swapOutRewardToken`) later relies on. The GitHub Desktop analog is `AppStore._findPullRequestBranch`, which takes `headCloneUrl`/`headRepoOwner` straight from a pull request's `head` object (an attacker-influenced GitHub API object, since anyone can open a PR from their own fork) and uses it, unvalidated, to call `addRemote()` and then `_fetchRemote()` against the local repository — with no scheme/format check comparable to the `isWhitelisted` gate the contract at least has for `notifyRewardAmount`.

### Finding Description
`_findPullRequestBranch` is reached both via the `x-github-client://openRepo?pr=...` deep-link handler and via the in-app "Checkout via Desktop" PR flow: [1](#0-0) 

and: [2](#0-1) 

`headCloneUrl` and `headRepoOwner` come directly from `pullRequest.head.repo.clone_url` / `pullRequest.head.repo.owner.login`, values reported by the GitHub API for the PR's head repository. Any unprivileged GitHub user can open a pull request against a target repo and thereby control what value the app eventually passes to `addRemote()`: [3](#0-2) 

No validation of the URL's scheme or shape happens before it reaches `git remote add name <url>`, and immediately afterwards the app performs an unattended `git fetch` against that same URL: [4](#0-3) 

This mirrors the reported bug class exactly: a caller who should not have privileged influence over app state (the PR author, analogous to "anyone" calling `notifyRewardAmount`) causes attacker-supplied data to be written into state used by a "trusted" operation (the maintainer's/PR-reviewer's own `_checkoutPullRequest`/`_fetchRemote`/branch checkout, analogous to the admin's `swapOutRewardToken`) without the equivalent of the `isWhitelisted` check that the contract's `_addRewardToken` at least performs.

### Impact Explanation
Because the app adds a remote and immediately fetches from `headCloneUrl` with no restriction on the URL's transport/scheme, whatever guard git itself provides (default protocol allowlist in modern git) is the *only* mitigation — GitHub Desktop adds none of its own (no scheme allowlist, no host restriction, no `GIT_ALLOW_PROTOCOL` set in `envForRemoteOperation`). If that URL ever resolves to a transport git treats as valid but Desktop does not expect (e.g. a `file://`/local path style URL — which is not blocked by git's default protocol allowlist), the checkout flow will silently fetch and merge/checkout that content into the user's real, trusted repository, matching the listed valid impact of "silent corruption of what the user commits or pushes" and "attacker controls ... a fetched repository." At minimum this is a state-injection primitive functionally identical to the reported bug: an unprivileged party can force the addition of attacker-chosen remote state into a repository that the app subsequently treats as legitimate, without any of the equivalent whitelist gate the underlying report calls out as missing.

### Likelihood Explanation
Any GitHub user can open a pull request against a public repository from their own fork, so triggering `headCloneUrl`/`headRepoOwner` to be attacker-controlled requires no special privilege — the same "attacker doesn't need privileged access" precondition as the original report. The path is reachable both silently in-app (when a repository owner checks out a PR) and via a deep link the victim clicks (`x-github-client://openRepo?...&pr=...`), which fits the task's allowed impact class ("a link or deep link the user clicks" / "a GitHub API object").

### Recommendation
Before calling `addRemote()`/`_fetchRemote()` with `headCloneUrl`, validate that the URL uses an expected `https://`/`ssh://`/`git@` scheme matching the account's known API endpoint (dotcom or the configured GHES host), reject anything else, and consider explicitly setting `GIT_ALLOW_PROTOCOL`/`protocol.*.allow=never` in `envForRemoteOperation` as defense-in-depth rather than relying solely on git's own defaults, mirroring the report's recommendation to add an explicit whitelist check rather than trusting unvalidated caller-supplied input.

### Proof of Concept
1. Attacker forks a public repository tracked in GitHub Desktop and opens a pull request from the fork.
2. Victim (repository maintainer, using Desktop) clicks "Checkout via Desktop" for the PR, or attacker sends the victim a `x-github-client://openRepo?url=<repo>&pr=<n>` deep link.
3. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` is invoked with `headCloneUrl = pullRequest.head.repo.clone_url` taken verbatim from the GitHub API response for the attacker's fork. [5](#0-4) 
4. `addRemote(repository, forkRemoteName, headCloneUrl)` and `_fetchRemote(repository, remote, FetchType.UserInitiatedTask)` execute with no scheme/host allowlist check applied by Desktop. [6](#0-5) 

Note: I was unable to fully verify, from the indexed code alone, whether Desktop's bundled git build restricts risky transports (e.g. via a compiled-in default `protocol.*.allow` deny list) — no explicit `GIT_ALLOW_PROTOCOL`/protocol allowlist configuration was found in `app/src/lib/git/environment.ts` or `remote.ts`, meaning the app itself provides no independent safeguard on this input; verifying the exact exploitable transport would require testing against the actual git binaries Desktop ships.

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)

/** Add a new remote with the given URL. */
export async function addRemote(
  repository: Repository,
  name: string,
  url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')

  return { url, name }
}
