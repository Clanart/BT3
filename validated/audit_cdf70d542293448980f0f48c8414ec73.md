### Title
Marker-scanning divergence between `extractConflictHunks` and `reassembleResolvedFile` lets attacker-controlled conflict content desynchronize hunk indices and splice wrong/leftover marker text into the committed file - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` re-scans the raw on-disk file for conflict marker blocks using its own independent look-ahead loop, which is **not** algorithmically identical to `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` — the function that produced the hunk list sent to the model and whose count/order `reassembleResolvedFile` assumes lines up 1:1 with `hunkResolutions`. When a real conflict's `theirs` section (which is attacker-controlled content on the incoming/merged branch) contains a line that itself matches the theirs-marker pattern (`^>{7}(?:\s|$)`), the two scanners locate the "closing" marker of the same hunk in a consistent way with each other in the case I traced, but both end up treating an embedded look-alike line as the real closing marker instead of git's true closing marker — leaving orphaned attacker content and a literal `>>>>>>> <label>` line un-consumed in the file. More importantly, the two loops diverge structurally in how they classify malformed sequences: `extractConflictHunks`'s "ours" collector only breaks on a `=======`/`|||||||` line and otherwise absorbs everything (including a stray `>>>>>>>`-looking line) as ordinary hunk content, while `reassembleResolvedFile`'s look-ahead breaks the moment it sees *any* line matching the theirs-marker regex, even if no separator has been seen yet. This means a crafted sequence such as:

```
<<<<<<< fake
stuff
>>>>>>> no-separator-yet
=======
oops
>>>>>>> real
```

is parsed by `extractConflictHunks` as **one real hunk** (`ours = "stuff\n>>>>>>> no-separator-yet"`, `theirs = "oops"`), which is sent to Copilot and gets a corresponding entry in `hunkResolutions`, but is parsed by `reassembleResolvedFile` as **zero hunks** (it judges the block malformed because it finds the theirs-marker before ever observing the separator, so `hasSeparator` is `false`) and copies every line through as plain text, including the literal `=======` and `>>>>>>> real` strings. The extra `hunkResolutions` entry that was allocated for this phantom hunk is never consumed at this point — it is instead consumed by the *next* real conflict block later in the file, silently shifting `hunkIndex` by one and splicing that hunk's model-generated resolution into the wrong conflict location.

### Finding Description
`reassembleResolvedFile` at [1](#0-0)  walks `rawContent` line by line and matches `hunkResolutions` to conflict blocks purely by order (`hunkIndex++`), with no positional or content cross-check against the hunks that were originally extracted to build the prompt. The block-boundary detection logic: [2](#0-1) 

is a *separate, re-implemented* scanner from `extractConflictHunks`: [3](#0-2) 

Both use the identical marker regexes (`oursMarker`, `separatorMarker`, `theirsMarker`) [4](#0-3) [5](#0-4) , but their control flow around ordering of "separator seen" vs "closing marker seen" is not equivalent: `extractConflictHunks`'s ours-collection loop ignores a theirs-marker line entirely (treating it as ordinary content) until a separator is found, whereas `reassembleResolvedFile`'s look-ahead terminates on the *first* theirs-marker line regardless of whether a separator preceded it. Since the "theirs" side of a real conflict is attacker-controlled content (the incoming branch that the victim merges/rebases), an attacker can plant a line matching `^>{7}(?:\s|$)` inside their own branch content to trigger this divergence, causing:
- Miscounted/misclassified hunks between the two scanners for the crafted region, and
- A cascading off-by-one in `hunkIndex` for every subsequent real conflict hunk in the same file, so `hunkResolutions[hunkIndex]` no longer corresponds to the conflict block it is spliced into.

The only marker-leftover check present is scoped to a single hunk's `resolvedContent` returned by the model, requiring *both* an ours-marker line and a standalone separator line to trip (`/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)`) at [6](#0-5) ; it never re-validates the fully reassembled file for leftover/misplaced markers produced by the splicing logic itself, so a corrupted final `resolvedContent` (with a misaligned hunk or an orphaned literal `>>>>>>> ...` line) is not caught before being surfaced to the user for commit.

### Impact Explanation
This lets an unprivileged attacker who controls the remote branch/content that the victim merges or rebases cause GitHub Desktop's Copilot-assisted conflict resolution to silently splice the wrong resolved hunk into a different (real) conflict location, or leave attacker-authored/orphaned marker-like text embedded in the file that the user is asked to commit — corrupting `resolvedContent` in a way that is not flagged by the existing "still contains conflict markers" guard, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitation requires the attacker only to control the content of a branch/commit that will conflict with the victim's local changes (a normal, unprivileged scenario — no special git server behavior or credentials needed) and to include an innocuous-looking line beginning with 7 `>` characters (e.g. an email-quote block, ASCII banner, or embedded diff/patch text) inside that branch's version of a conflicting region. This is a plausible, naturally occurring pattern (patch/diff snippets, log excerpts, chat quote blocks) and does not require any unusual git operations, making the precondition realistic though it does depend on Copilot conflict resolution being enabled and the file actually reaching a real conflict.

### Recommendation
Make `reassembleResolvedFile` consume the *exact same* hunk-extraction algorithm as `extractConflictHunks` (ideally by sharing one implementation) so hunk counts/boundaries can never diverge between prompt construction and reassembly. Additionally, after reassembly, re-scan `resolvedContent` for any residual line matching the ours/separator/theirs marker regexes and treat a match as a hard failure (falling back to manual conflict resolution / skipping the file) rather than allowing it to reach the write/commit path unchecked.

### Proof of Concept
Unit-test sketch for `reassembleResolvedFile`:
```ts
const raw = [
  'before',
  '<<<<<<< fake',
  'stuff',
  '>>>>>>> no-separator-yet',
  '=======',
  'oops',
  '>>>>>>> real',
  'middle',
  '<<<<<<< HEAD',
  'ours-2',
  '=======',
  'theirs-2',
  '>>>>>>> feature',
  'end',
].join('\n')

// extractConflictHunks(raw) reports 2 hunks (the crafted block + the real one),
// so Copilot is prompted with "Conflict 1 of 2" / "Conflict 2 of 2" and returns
// 2 hunkResolutions: [resolutionForFakeBlock, resolutionForRealBlock2].

const result = reassembleResolvedFile(raw, [
  { resolvedContent: 'RESOLVED_FAKE' },
  { resolvedContent: 'RESOLVED_REAL' },
])

// Expected if aligned: RESOLVED_FAKE spliced for the first block, RESOLVED_REAL for hunk "ours-2/theirs-2".
// Actual: reassembleResolvedFile finds 0 hunks in the first (fake) region (copies
// "=======" / ">>>>>>> real" through verbatim) and instead consumes
// hunkResolutions[0] ("RESOLVED_FAKE") for the real "ours-2/theirs-2" conflict,
// leaving hunkResolutions[1] ("RESOLVED_REAL") unused and literal marker text
// ("=======", ">>>>>>> real") embedded in the committed output.
```
This demonstrates the hunk-to-block misalignment described: `hunkIndex` in `reassembleResolvedFile` becomes desynchronized from the hunk ordering used by `extractConflictHunks`/Copilot, corrupting the final `resolvedContent`.
