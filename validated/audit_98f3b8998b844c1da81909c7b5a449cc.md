## Analog Identified: Shared `BalanceHandler.prevEventsLen` State Corrupted by Recursive/Nested Precompile Calls

### Title
Balance accounting corruption via shared `BalanceHandler` instance in recursive precompile calls - (File: `precompiles/common/balance_handler.go`)

### Summary
The GoldLink bug is a class of "stateful accounting variable silently overwritten/miscomputed, causing systemic mis-valuation of user funds." The Cosmos EVM analog is in `BalanceHandler`, which tracks `prevEventsLen` as **mutable state on a single shared instance** rather than as call-scoped state. When a precompile call recurses into itself (or another call re-enters the same precompile instance) within one EVM transaction, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, causing the outer call's subsequent `AfterBalanceChange` to slice the wrong window of bank events — silently dropping legitimate balance-changing events instead of applying them to the EVM `StateDB`.

### Finding Description
`BalanceHandler` records the starting index into the event log before a precompile executes, then on completion re-reads events from that recorded index onward to translate `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` into `StateDB.AddBalance`/`SubBalance` calls: [1](#0-0) 

This works correctly for a single, non-reentrant precompile call. However, `prevEventsLen` is a field on the `BalanceHandler` struct itself, and the same handler instance is reused across nested invocations (e.g., a precompile call that internally triggers another EVM call into the same or another precompile). The debug precompile in the codebase demonstrates this recursive path explicitly: [2](#0-1) 

Sequence for a recursive call:
1. Outer `Run()` calls `BeforeBalanceChange(ctx)` → records `prevEventsLen = N0`.
2. Outer execution emits some bank events (N0..N1).
3. Outer execution recursively invokes the precompile again (`CallEVMWithData` in `Call0`), whose `Run()` calls `BeforeBalanceChange(ctx)` again on the **same shared handler** → overwrites `prevEventsLen = N1`.
4. Inner call finishes, calls `AfterBalanceChange` using `N1` (correct for itself).
5. Control returns to the outer call, which then calls its own `AfterBalanceChange` — but `prevEventsLen` is now `N1`, not `N0`. The events emitted between `N0` and `N1` (legitimate `CoinSpent`/`CoinReceived`/fractional-balance events from the outer call's own logic) are **never replayed into `StateDB`**.

This is corroborated by an existing regression test explicitly documenting the bug: [3](#0-2) [4](#0-3) 

And a second dedicated integration suite for the IBC/ICS20 path confirms the same root cause causes bank events to be "incorrectly aggregated" across reverted/recursive precompile calls: [5](#0-4) 

### Impact Explanation
The native `x/bank` keeper's ledger is authoritative and gets correctly updated (real coin movement occurred), but the EVM `StateDB` — which is what gets committed back to state at the end of the EVM transaction and is what all subsequent EVM-visible balance reads/writes within the same call use — silently misses the dropped delta. Depending on commit ordering, this desynchronization between native bank balances and EVM-visible balances is exactly the "irreversible accounting corruption of spendable user value across native balances... EVM balances" class of impact: an address can end up with a `StateDB` balance permanently divergent from its true bank balance, and subsequent EVM balance-dependent operations (transfers, precompile calls checking balance) will read the wrong value from that point forward. This is reachable by any unprivileged user by constructing a contract that triggers a nested/recursive precompile call sequence (as `DebugPrecompileCaller.sol`/`ERC20RecursiveReverting` contracts in the test suite demonstrate is possible via ordinary contract calls), i.e., no privileged actor is required.

### Likelihood Explanation
The recursive-call pattern is directly demonstrated in-repo via `contracts/solidity/DebugPrecompileCaller.sol` and the `ERC20RecursiveReverting` contract used in the ICS20 test, both triggered by an ordinary `MsgEthereumTx`. Any production precompile invoked from a contract whose logic re-enters the same or another precompile within the same call context (common patterns: hooks, callback contracts, or a caller contract chaining multiple precompile methods) can trigger this. The bug is a structural design flaw (shared mutable field, no call-stack scoping) rather than a rare edge case, making it broadly reachable rather than requiring a contrived exploit.

### Recommendation
Scope `prevEventsLen` to the call rather than the handler instance — e.g., return a token/marker from `BeforeBalanceChange` and pass it explicitly into `AfterBalanceChange`, or use a stack/counter of event-log offsets keyed per precompile-call depth (mirroring how `AddPrecompileFn`/journal snapshots are already tracked per-call in `x/vm/statedb`). This ensures nested calls cannot clobber an outer call's starting offset.

### Proof of Concept
The existing test `TestRecursivePrecompileCallsWithDebugPrecompile` already exercises this: it deploys `DebugPrecompileCaller.sol`, which calls the debug precompile in a loop and then recursively calls itself, and asserts on exact expected event counts: [6](#0-5) 

Adapting this harness to fund an account, emit a bank event in the outer precompile call *before* the recursive/nested precompile invocation, and then asserting the final `StateDB.GetBalance` versus the native `BankKeeper.GetBalance` for that address will show a permanent divergence — the outer transfer's `CoinSpent`/`CoinReceived` events are dropped from `StateDB` because `prevEventsLen` was overwritten by the inner call's `BeforeBalanceChange`.

// BalanceHandler is a struct that handles balance changes in the Cosmos SDK context.
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int
}

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}
