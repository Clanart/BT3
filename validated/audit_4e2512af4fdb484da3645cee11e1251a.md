### Title
Unbounded-size Bech32 decoding in `Offer.from_bech32()` allows attacker-controlled input size to bypass DoS protections - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.from_bech32()` calls `bech32_decode(offer_bech32, max_length=len(offer_bech32))`, which deliberately overrides the normal 90-character cap that every other bech32 caller in the codebase relies on (e.g. `decode_puzzle_hash()`, `AddressParamType.convert()`, `ensure_valid_address()` all call `bech32_decode()` with the library default `max_length=90`). By passing `max_length=len(offer_bech32)`, the size check in `bech32_decode()` becomes a no-op — any string length is "valid" as far as the length check is concerned — so an attacker can submit an arbitrarily large offer string that is fully processed (character validation, `rfind`, charset membership checks, and full Bech32 checksum computation) before any cost or size limiting occurs. [1](#0-0) [2](#0-1) 

### Finding Description
`bech32_decode()` is defined with a default `max_length: int = 90`, matching the expected size of bech32-encoded addresses (32-byte payload) as used throughout the codebase (`decode_puzzle_hash`, `AddressParamType.convert`, `ensure_valid_address`). [2](#0-1) [3](#0-2) 

`Offer.from_bech32()`, however, explicitly discards this protection:
```python
@classmethod
def from_bech32(cls, offer_bech32: str) -> Offer:
    _hrpgot, data = bech32_decode(offer_bech32, max_length=len(offer_bech32))
``` [1](#0-0) 

Because `max_length` is set equal to the input's own length, `len(bech) > max_length` in `bech32_decode()` can never trigger a rejection, regardless of how large the string is. The full decode routine — case/char-range validation over every character, `rfind("1")`, a membership test against the 32-character `CHARSET` for every remaining character, and the `bech32_polymod`/`bech32_verify_checksum` computation that iterates the entire data list — runs unconditionally over the whole attacker-supplied string in pure Python before any cost accounting takes place. [4](#0-3) 

This entry point is reachable from multiple unauthenticated/low-trust paths:
- The wallet RPC `TakeOffer` request's `parsed_offer` cached property calls `Offer.from_bech32(self.offer)` directly on caller-supplied text. [5](#0-4) 
- `WalletRpcApi.check_offer_validity()` and `WalletRpcApi.get_offer_summary()` (via `request.parsed_offer`) similarly decode caller/counterparty-supplied offer strings before doing any further work. [6](#0-5) 
- CLI/offer-file flows (`Offer.from_bech32(offer_file.read_text())`) feed the exact same unbounded path. [7](#0-6) 

After the oversized decode succeeds (or is rejected only by checksum mismatch after full processing), the resulting bytes go into `try_offer_decompression()` → `decompress_object_with_puzzles()`, which does cap the *decompressed output* at 6 MiB via `zlib.decompressobj().decompress(blob, max_length=6*1024*1024)`, but this cap only bounds the zlib output — it does not bound the size of the *compressed input* nor the cost already paid decoding the bech32 string itself. [8](#0-7) 

This mirrors the CVE-2019-1002100 bug class: a caller-supplied, structurally valid but arbitrarily large payload is processed by expensive Python-level parsing/validation logic with no size cap enforced ahead of that processing, unlike the analogous, correctly-bounded code path (regular addresses) elsewhere in the same module.

### Impact Explanation
Any party that can get a wallet, RPC client, or CLI process to call `Offer.from_bech32()` — a wallet-RPC caller (`take_offer`, `check_offer_validity`, `get_offer_summary`), an offer counterparty sending a crafted offer file/string, or a Data Layer client relaying an offer — can force that process to spend disproportionate CPU/memory on a single string before any consensus-level cost metering (comparable to `mempool_manager.py`'s `max_tx_clvm_cost` checks) is ever reached. Because wallet RPC handling runs on a single asyncio event loop, a sufficiently large payload can stall that loop and the transaction-processing path for the affected wallet/RPC service — a spend/RPC-triggered processing halt, matching the CVE-2019-1002100 bug class (excessive resource consumption on a specially crafted, size-unbounded structured input).

### Likelihood Explanation
High reachability: `Offer.from_bech32()` is called directly on unauthenticated/low-trust string input in several RPC endpoints and CLI helpers without any prior size gate. No signature, cost, or authorization check precedes the decode, and no other caller of `bech32_decode()` in the codebase disables the length cap this way — making this an isolated, easily reachable deviation from the codebase's own established pattern.

### Recommendation
Restore a bounded `max_length` in `Offer.from_bech32()` (e.g. a fixed reasonable cap sized to the maximum expected compressed+encoded offer size) instead of `max_length=len(offer_bech32)`, and reject/short-circuit oversized input before invoking `bech32_decode()`/`convertbits()`/decompression at all. Apply the same defensive size check at the RPC/CLI boundary (`TakeOffer`, `CheckOfferValidity`, `GetOfferSummary`) so a caller-controlled string can be rejected cheaply prior to any parsing work.

### Proof of Concept
1. Construct a very large string (e.g. tens/hundreds of MB) consisting of lowercase bech32-charset characters with a valid `hrp` + `"1"` separator anywhere after position 1, so it passes the character-range/case checks in `bech32_decode()`.
2. Call `Offer.from_bech32(large_string)` (e.g. via the wallet RPC `check_offer_validity` or `take_offer` endpoint, passing the string as the `offer` field).
3. Because `max_length=len(offer_bech32)` is passed, the `len(bech) > max_length` guard in `bech32_decode()` never trips, and the function proceeds to run `all(x in CHARSET for x in bech[pos+1:])` and `bech32_verify_checksum(hrp, data)` (which calls `bech32_polymod`) over the entire string. [9](#0-8) 
4. Observe that CPU time and memory scale with the attacker-chosen input size rather than being capped near the expected offer size (~90 chars for addresses, or a bounded offer size), demonstrating the missing size gate before expensive parsing.

def bech32_polymod(values: list[int]) -> int:
    """Internal function that computes the Bech32 checksum."""
    generator = [0x3B6A57B2, 0x26508E6D, 0x1EA119FA, 0x3D4233DD, 0x2A1462B3]
    chk = 1
    for value in values:
        top = chk >> 25
        chk = (chk & 0x1FFFFFF) << 5 ^ value
        for i in range(5):
            chk ^= generator[i] if ((top >> i) & 1) else 0
    return chk


def bech32_hrp_expand(hrp: str) -> list[int]:
    """Expand the HRP into values for checksum computation."""
    return [ord(x) >> 5 for x in hrp] + [0] + [ord(x) & 31 for x in hrp]


M = 0x2BC830A3


def bech32_verify_checksum(hrp: str, data: list[int]) -> bool:
    return bech32_polymod(bech32_hrp_expand(hrp) + data) == M


def bech32_create_checksum(hrp: str, data: list[int]) -> list[int]:
    values = bech32_hrp_expand(hrp) + data
    polymod = bech32_polymod([*values, 0, 0, 0, 0, 0, 0]) ^ M
    return [(polymod >> 5 * (5 - i)) & 31 for i in range(6)]


def bech32_encode(hrp: str, data: list[int]) -> str:
    """Compute a Bech32 string given HRP and data values."""
    combined = data + bech32_create_checksum(hrp, data)
    return hrp + "1" + "".join([CHARSET[d] for d in combined])


def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
    bech = bech.lower()
    pos = bech.rfind("1")
    if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length:
        return (None, None)
    if not all(x in CHARSET for x in bech[pos + 1 :]):
        return (None, None)
    hrp = bech[:pos]
    data = [CHARSET.find(x) for x in bech[pos + 1 :]]
    if not bech32_verify_checksum(hrp, data):
        return (None, None)
    return hrp, data[:-6]
```
