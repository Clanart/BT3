### Title
Unauthenticated OP_RETURN payer attribution lets any confirmed payout tx credit an arbitrary operator's `payout_payer_operator_xonly_pk` regardless of who funded the withdrawal - (File: core/src/verifier.rs, core/src/operator.rs)

### Summary
`update_finalized_payouts`/`update_payout_txs_and_payer_operator_xonly_pk` in `core/src/verifier.rs` attribute a confirmed payout transaction to whichever operator's `XOnlyPublicKey` is embedded in the transaction's OP_RETURN, parsed via `get_first_op_return_output`/`parse_op_return_data`. Because the withdrawal input is signed by the user with `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` (enforced in `Operator::withdraw`, `core/src/operator.rs:630-637`), a third party can replace the fee-paying inputs, change output, and OP_RETURN of an in-flight payout transaction via RBF while keeping the correctly-paid withdrawal output intact, thereby swapping in an arbitrary operator's public key as the "payer" with no cryptographic link between that key and the actual source of funds.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk[i] == the operator whose own BTC funded withdrawal_prevout for withdrawal index i`.

- `Operator::withdraw` (`core/src/operator.rs:560-692`) builds the payout tx with `create_payout_txhandler` embedding the calling operator's own `self.signer.xonly_public_key`, then calls `fund_raw_transaction` (adding fee/funding inputs from the operator's own wallet) and `sign_raw_transaction_with_wallet`. The user's withdrawal input is signed with `SIGHASH_SINGLE|ANYONECANPAY` (`in_signature.sighash_type`, verified at `core/src/operator.rs:630-637`), which commits only to input 0 and the correspondingly-indexed output (the payout to the user). It does **not** commit to the OP_RETURN output or to any of the additional funding inputs.
- Because of this sighash flag, the withdrawal input's signature remains valid if reused in a completely different transaction that pays the same amount to the same withdrawal address at the same output index, but with different funding inputs, a different fee, and a different OP_RETURN payload.
- An unprivileged attacker (who is allowed to broadcast Bitcoin transactions and pay fees per the threat model) can therefore construct a replacement transaction for an operator A's unconfirmed payout tx: reuse A's `SIGHASH_SINGLE|ANYONECANPAY`-signed withdrawal input, supply their own (or operator B's public) funding inputs/fee, and embed operator B's `XOnlyPublicKey` in the OP_RETURN, then broadcast it as a higher-fee RBF replacement before A's original tx confirms.
- `update_finalized_payouts`/`update_payout_txs_and_payer_operator_xonly_pk` (`core/src/verifier.rs`) then reads whichever transaction actually confirms, extracts the OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`, and records `payout_payer_operator_xonly_pk = B` with no check that B (or its funds) were actually used to pay the fee/change inputs of the confirmed transaction.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:41-47`) later calls `get_first_unhandled_payout_by_operator_xonly_pk(operator.signer.xonly_public_key)`, so whichever operator's key was embedded (here B) picks up the payout and calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839-970`), which calls `get_unused_and_signed_kickoff_connector` keyed on `self.signer.xonly_public_key` — i.e. B's own kickoff/round — and drives the Reimburse transaction from B's own collateral-anchored round.
- None of the listed guards (`Verifier::is_deposit_valid`, `Operator::is_profitable`, `SECP.verify_schnorr`, `only_aggregator_and_self`, `Verifier::is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`) verify that the OP_RETURN-embedded key corresponds to the actual signer/funder of the confirmed transaction's non-user inputs; they only validate the withdrawal input/output correctness and downstream kickoff/challenge logic, not payer attribution.

### Impact Explanation
Operator B is credited via `payout_payer_operator_xonly_pk` and successfully proceeds through `handle_finalized_payout` → kickoff → Reimburse for a withdrawal it never actually funded with its own capital, matching the Critical category "an operator reimbursed for a payout it never funded." The honest operator A who broadcast the original signed transaction is left with nothing (their tx was replaced and never confirmed), and the vault's bridge BTC is released to B via the presigned Reimburse path without a legitimate fronting operator. This is repeatable per withdrawal as long as the original payout tx is still unconfirmed and replaceable, and does not require compromising any operator key, verifier key, or the aggregator — only the ability to broadcast a conflicting higher-fee Bitcoin transaction, which is explicitly within the unprivileged attacker's capabilities.

### Likelihood Explanation
Preconditions: the legitimate operator's payout transaction must still be unconfirmed/replaceable (a normal window given Bitcoin's confirmation latency and that `Operator::withdraw` explicitly sends the tx with RBF-eligible funding via `fund_raw_transaction`). Attacker cost is limited to constructing a valid, sufficiently higher-fee alternative transaction that reuses the `ANYONECANPAY` withdrawal input — a modest, deterministic fee bump, no proof-of-work, no key compromise, and no privileged role required. The attack is repeatable across every withdrawal/payout as long as the same signature-scoping pattern is used.

### Recommendation
Do not derive `payout_payer_operator_xonly_pk` solely from an unauthenticated OP_RETURN field. Require the OP_RETURN commitment (or an equivalent operator identity claim) to be cryptographically bound to the actual funding/signing party of the confirmed transaction — e.g., by requiring the operator to sign the OP_RETURN commitment together with the withdrawal input using a signature that also covers the OP_RETURN output (removing reliance on `ANYONECANPAY` for that binding), or by validating that the additional funding inputs' scriptPubkeys resolve to the claimed operator's known collateral/reimbursement key before crediting `payout_payer_operator_xonly_pk`.

### Proof of Concept
```
cargo test -p core --features automation payer_attribution_hijack_via_op_return_replacement -- --nocapture
```
Test outline:
1. Set up a regtest deposit and withdrawal so `withdrawal_utxo` and `withdrawal_prevout` are known, matching Citrea withdrawal index `i`.
2. As operator A, call `Operator::withdraw` to build and broadcast a fully valid, unconfirmed payout tx `tx_A` (OP_RETURN embeds A's `XOnlyPublicKey`, additional funding inputs come from A's wallet).
3. As attacker, construct `tx_evil` reusing `tx_A`'s `SIGHASH_SINGLE|ANYONECANPAY`-signed withdrawal input (input 0, same output amount/script to the withdrawal address), but with attacker-supplied funding inputs, a higher fee, and an OP_RETURN embedding operator B's `XOnlyPublicKey`. Broadcast `tx_evil`, mine it to confirmation (replacing `tx_A`).
4. Run `update_finalized_payouts`/`update_payout_txs_and_payer_operator_xonly_pk` and assert `payout_payer_operator_xonly_pk == B` (violating `payout_payer_operator_xonly_pk == A`, the operator whose capital was originally intended/queued to fund the withdrawal).
5. As operator B, run `PayoutCheckerTask::run_once` and assert it picks up the payout and successfully calls `handle_finalized_payout`/`get_unused_and_signed_kickoff_connector` for B's own round, producing a signed Kickoff/Reimburse path for B despite B having contributed none of `tx_evil`'s funding inputs.
