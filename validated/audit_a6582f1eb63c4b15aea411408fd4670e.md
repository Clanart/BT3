### Title
Missing upper-bound on oracle price timestamp allows future-dated publish-time to poison the monotonic `last-update` cache and permanently freeze price resolution - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`oracle-timestamp-fresh` in `v0-4-market.clar` is supposed to gate stale prices, but its "delta" calculation silently treats any price whose reported `publish-time` is *greater than* the current `stacks-block-time` as having zero staleness (`delta = u0`), instead of rejecting or bounding it. Combined with the monotonic check `(>= ts prev)` and the fact that `last-update` is unconditionally advanced to any `timestamp` greater than the stored value, a single price update carrying a timestamp set in the future permanently raises the floor that all subsequent, correctly-timed price updates must clear. Until real `stacks-block-time` catches up to that poisoned value, every later legitimate price update for that feed fails `ERR-ORACLE-INVARIANT`, freezing all market operations that depend on that asset's price.

### Finding Description
The freshness/monotonicity gate is: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

and it is invoked/updated in `price-resolve`: [2](#0-1) 

If `ts > stacks-block-time` (a future-dated `publish-time`), `delta` is forced to `u0`, so `(<= delta max-staleness)` is trivially satisfied no matter how far in the future `ts` is — the staleness gate is effectively disabled for future timestamps. The same `price-resolve` function then does:

```clarity
(if (> timestamp last-update-time)
    (map-set last-update key timestamp)
    false)
```

so `last-update` for that `{type, ident}` key gets permanently set to the poisoned future timestamp. On the very next call for that feed, the real (correct, current) `publish-time` from Pyth/DIA will be `< prev` (the poisoned future value), so `(>= ts prev)` fails and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for every subsequent transaction touching that asset's price — until `stacks-block-time` naturally advances past the poisoned value.

This mirrors the report's root cause exactly: a missing bound-check on a timestamp field (there, vesting `_startTimestamp`/`_endTimestamp` not required to be `> block.timestamp`; here, oracle `publish-time` not required to be `<= stacks-block-time`), letting an out-of-range timestamp be silently accepted and then relied upon by downstream logic in a way that was never intended.

This is a bug in Zest's own gating logic (`oracle-timestamp-fresh`/`price-resolve`), not a third-party oracle data-integrity issue: the vulnerability exists regardless of which feed type is used, because the Zest-side check fails to enforce an upper bound before trusting and persisting the reported timestamp into `last-update`.

### Impact Explanation
Once `last-update` is poisoned with a future timestamp for an asset, every operation in the market that must resolve that asset's price (deposits, borrows, repayments, withdrawals, liquidations, health-factor checks) will revert via `ERR-ORACLE-INVARIANT` until real time exceeds the poisoned value. Depending on how far in the future the timestamp is set, this can freeze user funds and liquidations for that asset for an extended or indefinite period — this lands on the in-scope "temporary/permanent freezing of funds" impact class. It can also block liquidations of at-risk positions collateralized/borrowed in the affected asset, increasing protocol insolvency risk if prices move adversely while the feed is stuck.

### Likelihood Explanation
Triggering this requires a single accepted price update whose `publish-time` is ahead of the current `stacks-block-time`. The write-path staleness check in `pyth-storage-v4.clar` (`read-price-with-staleness-check` / `write-batch-entry`) only enforces a *lower* bound on `publish-time` (rejecting prices that are too old) — there is no corresponding upper-bound check preventing an accepted `publish-time` from being ahead of the chain's current time. Clock skew between the Pyth/DIA off-chain publishing network and Stacks block time, or a malicious/compromised relayer submitting a slightly-ahead timestamp, is sufficient to trigger the condition; no privileged access to Zest's own contracts is required.

### Recommendation
In `oracle-timestamp-fresh`, reject (rather than zero out) timestamps that exceed `stacks-block-time` by more than a small allowed clock-skew tolerance, e.g.:

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts (+ stacks-block-time MAX-CLOCK-SKEW))
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```

Additionally, add an explicit upper-bound check in `pyth-storage-v4.clar`'s `write-batch-entry`/`read-price-with-staleness-check` so future-dated `publish-time` values are rejected at the write layer as well, rather than only checking staleness in one direction.

### Proof of Concept
1. A price update for asset X is submitted (via Pyth relay or DIA) with `publish-time` set slightly (or arbitrarily) ahead of the current `stacks-block-time`.
2. `resolve-pyth`/`resolve-dia` returns this future `timestamp`; `price-resolve` calls `oracle-timestamp-fresh(ts, prev, max-staleness)`, where `ts > stacks-block-time` forces `delta = u0`, so the check passes trivially regardless of `max-staleness`.
3. `price-resolve` executes `(map-set last-update key timestamp)` since `timestamp > last-update-time`, storing the future value as the new floor for asset X's feed.
4. On the next legitimate price update for asset X (with correct, current `publish-time`), `(>= ts prev)` fails because `prev` is the poisoned future value, so `price-resolve` returns `ERR-ORACLE-INVARIANT`.
5. Every subsequent deposit/borrow/repay/withdraw/liquidate call that needs asset X's price now reverts until real `stacks-block-time` advances past the poisoned timestamp, freezing user funds and liquidations tied to that asset. [3](#0-2)
