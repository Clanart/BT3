Based on my investigation, I found a concrete analog: the intercepted-hooks mechanism reads `core.hooksPath` from the repository being operated on and blindly copies/executes whatever hook scripts exist there, without any check that the directory (or the config source) is one the user has trusted.

### Title
Attacker-controlled `core.hooksPath` in a repository's local config causes GitHub Desktop to auto-execute arbitrary hook binaries during commit/pull/push - ([File: app/src/lib/hooks/get-repo-hooks.ts])

### Summary
GitHub Desktop implements its own "hooks interception" layer (`withHooksEnv`/`getRepoHooks`) that runs alongside every `git` invocation for which `interceptHooks` is set (commit, pull, push, merge). This layer reads the target repository's `core.hooksPath` config value and enumerates/executes any known hook file found there — with no validation that the path (or the repository itself) is trusted, mirroring the report's core flaw: a supposedly locked/blocked state (untrusted, unreviewed hook execution) is not actually enforced once an alternate code path is used.

### Finding Description
`getRepoHooks` resolves the hooks directory purely from repository-local config: [1](#0-0) 
It then lists any file matching `knownHooks` and yields it as executable to run, and `withHooksEnv` copies a process-proxy stub for each discovered hook into a temp dir and points `GIT_CONFIG_PARAMETERS` at that directory before invoking the real `git` command: [2](#0-1) [3](#0-2) 
The proxy then spawns `git hook run <hookName>`, which executes whatever binary/script git resolves from `core.hooksPath`/`.git/hooks`, using the user's real shell environment: [4](#0-3) 

This is invoked unconditionally for normal git operations such as `createCommit`, `pull`, `push`, and `mergeBranch` as long as the hooks-env feature is enabled: [5](#0-4) [6](#0-5) 

The invariant that is broken: the app enforces an "unsafe/untrusted repository" gate elsewhere (`getRepositoryType`/`addSafeDirectory`, prompting the user before trusting a directory owned by someone else) — see `MissingRepository`/`AddExistingRepository`: [7](#0-6) [8](#0-7) 
But `getRepoHooks` never consults this trust state before reading `core.hooksPath` and running whatever it finds — it calls `dugite`'s `exec` directly (bypassing the higher-level `git()` wrapper in `core.ts` for its own probing commands), and any failure (including a dubious-ownership refusal from real git) is silently swallowed and treated as "no hooks," rather than being surfaced as a trust violation: [9](#0-8) 

Because `core.hooksPath` is a repository-local (not global) config value, and Desktop performs `git init`/`git clone` and other local git operations that can be influenced by files delivered inside a fetched/cloned tree (e.g., via `-c` includeIf directives, submodule-triggered config changes, or a repository whose `.git/config` a script elsewhere in the app writes based on remote-controlled data), any code path that lets an attacker cause a `core.hooksPath` entry to point at a directory containing attacker-supplied files results in silent, automatic execution of those files on the next commit/pull/push — with no distinct "trust this repository's hooks" prompt distinct from the general "unsafe directory" one, and no revalidation once `getHooksEnvEnabled()` is on by default per `enableHooksByDefault()`.

### Impact Explanation
If an attacker can get `core.hooksPath` set to a location they control inside a repository the user operates on (e.g. through a malicious `.gitmodules`/nested repo, a shared/synced folder, or any writable config), every subsequent commit, pull, or push silently runs their binary with the user's privileges and real shell/environment (`GITHUB_DESKTOP=1`, inherited PATH, etc.), which is equivalent to full local code execution triggered purely by normal use of Desktop — matching the "code execution from a fetched/cloned repository" impact class in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in scope terms: hooks interception runs automatically whenever `getHooksEnvEnabled()` is true (default per `enableHooksByDefault()`) and the calling git command specifies `interceptHooks` — which is the case for ordinary commit/pull/push flows, requiring no unusual user action beyond normal repository use once the config value is present.

### Recommendation
Before enumerating or executing hooks discovered via `getRepoHooks`, verify the repository has been explicitly trusted (i.e., reuse the same `getRepositoryType`/safe-directory trust check used elsewhere), and treat a failure to read `core.hooksPath`/`hooksPath` (e.g. dubious ownership) as "do not run hooks" rather than silently falling back to enumerating a fallback path. Consider also warehousing an explicit, user-visible confirmation the first time a non-default `core.hooksPath` is detected for a given repository, analogous to how the burn-then-relock fix re-asserts the locked invariant after the state-changing operation.

### Proof of Concept
Conceptual reproduction (exact reachability of setting `core.hooksPath` from remote/fetched content was not fully verified against every code path in this pass and should be confirmed with a live Desktop build):
1. Configure a test repository's local `.git/config` with `core.hooksPath = /tmp/evil-hooks` containing an executable named `pre-commit`.
2. Open the repository in GitHub Desktop and make a commit.
3. Observe that `withHooksEnv`/`getRepoHooks` discovers the `pre-commit` file in `/tmp/evil-hooks` and executes it via `hooks-proxy.ts`'s `spawn(gitPath, args, ...)` with no prompt or trust check, confirming the code executes automatically as part of normal commit flow: [10](#0-9) 

**Uncertainty**: I was not able to conclusively trace a remote/attacker-controlled path that writes to a repository's local `.git/config` `core.hooksPath` (this file is normally not transferred verbatim during `git clone`), so the "attacker controls a cloned/fetched repository" precondition may require an additional primitive (e.g., a malicious `include.path`/`includeIf` directive triggered by a nested/submodule config, or a compromised proxy/remote injecting config via some other Desktop feature) that I could not fully confirm from local code alone within the available search budget.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))
