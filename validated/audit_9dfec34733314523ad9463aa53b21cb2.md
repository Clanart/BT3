### Title
Silent corruption of partial-commit line selection after diff hunk expansion — (File: `app/src/lib/patch-formatter.ts`, `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
`formatPatch`/`formatPatchToDiscardChanges` in `app/src/lib/patch-formatter.ts` compute the index used to check whether a diff line is selected as `hunk.unifiedDiffStart + lineIndex` (its position within the *current*, possibly-expanded, `hunk.lines` array), while the UI records the user's selection using `DiffLine.originalLineNumber`, a value fixed at parse time [1](#0-0) . When a hunk is expanded upward via the "expand diff" feature, new context lines are spliced into the *front* of the hunk's `lines` array while `hunk.unifiedDiffStart` is left unchanged [2](#0-1) , breaking the invariant that `originalLineNumber === unifiedDiffStart + lineIndex` for every pre-existing line in that hunk. The result is that `formatPatch` looks up the wrong index in the user's `DiffSelection`, silently including or excluding a different line than the one the user actually selected when building the commit patch.

### Finding Description
Two independent code paths compute "the absolute index of a diff line" differently, and both are treated as interchangeable keys into the same `DiffSelection` object:

1. In the UI layer, a row's `diffLineNumber` used for `isSelected` and for recording clicks (`onEndSelection` → `selection.withLineSelection(diffLineNumber, ...)`) is taken from `line.originalLineNumber` [3](#0-2) , a value assigned once when the diff is parsed via a monotonically incrementing counter (`diffLineNumber++` in `parseHunk`) [4](#0-3) .

2. In the patch-building layer, `formatPatch` (used to build the actual `git apply`-able patch for partial commits) computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` from the current position of each line in `hunk.lines`, and uses that to call `file.selection.isSelected(absoluteIndex)` [5](#0-4) . The same pattern is used in `formatPatchToDiscardChanges` [6](#0-5) .

For an un-expanded diff these two values coincide. However, `expandTextDiffHunk` mutates a hunk's `lines` array by inserting newly-fetched context lines from disk while keeping `hunk.unifiedDiffStart` fixed for an upward expansion (`hunk.unifiedDiffStart` is reused as-is on the updated hunk) [7](#0-6) :

```
let updatedHunk = new DiffHunk(
    newHunkHeader,
    updatedHunkLines,
    hunk.unifiedDiffStart,
    hunk.unifiedDiffEnd + numberOfNewDiffLines,
    expansionType
)
```

For `isExpandingUp`, `updatedHunkLines = [newDiffHunkLine, ...newLineDiffs, ...allHunkLinesButFirst]` [8](#0-7) . This pushes every previously-existing `Add`/`Delete`/`Context` line further down in the array by `numberOfLinesToAdd` positions, while their `originalLineNumber` field (set at parse time, immutable) stays the same. Consequently:
- `originalLineNumber` for a given `Add`/`Delete` line no longer equals `unifiedDiffStart + lineIndex` for that same line after expansion.
- The `DiffSelection` bit-set was populated using `originalLineNumber` (via the UI).
- `formatPatch` reads it back using `unifiedDiffStart + lineIndex`.

The corrupted value is which lines are treated as "selected for commit" inside `formatPatch`/`formatPatchToDiscardChanges` — after an upward hunk expansion, the selection check silently targets a different physical line (shifted by `numberOfLinesToAdd`) than the one the user actually toggled in the UI.

### Impact Explanation
This directly matches "silent corruption of what the user commits" — after expanding a hunk upward and making a partial-line selection (or discard-changes selection), the generated patch (fed to `git apply --cached`/discard) can include an unintended line (e.g. an added secret, an unfinished edit, or the wrong hunk of a multi-line change) or exclude a line the user meant to commit, without any error or warning. Because `git apply` operates on the crafted patch text rather than on the selection bitmap directly, there is no secondary validation step that would catch the mismatch — the wrong content is committed/discarded exactly as constructed.

### Likelihood Explanation
Diff expansion ("Load more"/"expand hunk") is a normal, commonly used feature for reviewing/committing changes with limited context, and partial-line selection for committing/discarding is core Desktop functionality. Any user who (a) expands a hunk upward, and (b) makes or changes a partial line selection within the same hunk before committing/discarding, can hit this path without any unusual or "unnatural" steps, elevated privileges, or attacker-supplied malicious content — it is purely an internal indexing defect triggered by ordinary application usage.

### Recommendation
Use a single, stable line-identity scheme consistently between the selection UI and the patch/discard formatters. Concretely, `patch-formatter.ts` should compute the selection lookup key from `line.originalLineNumber` (the same value the UI uses to record selections) rather than recomputing `hunk.unifiedDiffStart + lineIndex`, or alternatively `expandTextDiffHunk` should renumber `originalLineNumber` to match the new positional indexing for all lines in the hunk after expansion. Add a regression test that: expands a hunk upward, selects a specific line, and asserts that `formatPatch`'s resulting patch includes exactly that line's content and no other.

### Proof of Concept
1. Open a modified file with a diff hunk that is eligible for upward expansion (i.e., `hunkIndex === 0` and `oldStartLine/newStartLine > 1`, see `getHunkHeaderExpansionType`) [9](#0-8) .
2. Click "Expand Up" to trigger `expandHunk`/`expandTextDiffHunk`, which inserts `numberOfLinesToAdd` context lines ahead of the existing lines while keeping `unifiedDiffStart` fixed [10](#0-9) .
3. In the now-expanded hunk, select (check) a specific `Add`/`Delete` line for partial commit; the UI records this using `line.originalLineNumber` [11](#0-10) .
4. Trigger a partial commit; `formatPatch` iterates `hunk.lines` computing `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and checks `file.selection.isSelected(absoluteIndex)` [5](#0-4) . Because `absoluteIndex` is now offset by `numberOfLinesToAdd` relative to `originalLineNumber`, the constructed patch selects/deselects the line at the shifted index instead of the one the user actually clicked.

Note: I was unable to fully inspect `app/src/models/diff/diff-line.ts` (constructor/field docs) with the remaining tool budget to double-confirm every detail of `originalLineNumber`'s semantics beyond what's shown in `diff-parser.ts` and `text-diff-expansion.ts`; the analysis above is based on the call sites actually observed (`getDataFromLine`, `formatPatch`, `expandTextDiffHunk`). A Devin session with full repo access should verify `diff-line.ts` directly and add the regression test described above before treating this as fully confirmed.
