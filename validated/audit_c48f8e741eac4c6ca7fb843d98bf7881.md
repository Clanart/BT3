This confirms `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) blindly picks up any withdrawal where `payout_payer_operator_xonly_pk` in the DB equals the operator's own key, taken straight from `update_finalized_payouts`'s OP_RETURN parsing (`core/src/verifier.rs:2319-2321`), with no on-chain check that the operator itself broadcast/funded that specific payout transaction. The operator's automation then unconditionally calls `handle_finalized_payout` → `create_and_sign_txs`/kickoff submission (`core/src/operator.rs:839-916`), spending real N-of-N-secured bridge funds, whenever it finds such a record — the only gate is `is_kickoff_malicious`'s comparison of `operator_xonly_pk` (from OP_RETURN) against `kickoff_data.operator_xonly_pk` (`core/src/verifier.rs:1887-1890`), which trivially matches because the attacker deliberately wrote the target operator's real public key into the OP_RETURN.

### Title
Operator reimbursed for a payout it never funded via unauthenticated `operator_xonlypk` OP_RETURN forgery - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/verifier.rs`, `core/src/task/payout_checker.rs`)

### Summary
The payout transaction's `operator_xonlypk` OP_RETURN field is never bound to any signature or proof that the named operator actually funded the withdrawal; it is written by whoever constructs the payout tx (`create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`) and later read back verbatim by `update_finalized_payouts` (`core/src/verifier.rs:2319-2321`) into the `withdrawals.payout_payer_operator_xonly_pk` column. Because the withdrawal UTXO belongs to the withdrawing user (an unprivileged attacker under this threat model) and is spent via `SpendPath::KeySpend` with only the user's own signature, that same user can construct and broadcast their own payout transaction — paying themselves — while embedding a legitimate operator's real x-only public key in the OP_RETURN instead of their own.

### Finding Description
Broken binding (equality that should hold but doesn't): `deposit_constant.operator_xonlypk == identity_of_the_party_whose_BTC_funded_output_0`. In fact the code enforces only `deposit_constant.operator_xonlypk == bytes_pushed_after_OP_RETURN_in_output_N`, an attacker-controlled value.

Path: A user withdrawing from the bridge (an "attacker" under the given threat model, since anyone can hold a withdrawal UTXO and its Schnorr key) constructs their own payout transaction spending their own withdrawal UTXO (`create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`), paying themselves the withdrawal amount, but sets the OP_RETURN push data to a legitimate operator's real `XOnlyPublicKey` instead of their own. They broadcast it directly to Bitcoin, bypassing the operator's gRPC `withdraw`/`internal_withdraw` entirely.

When this block is synced, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) finds the confirming payout tx for the withdrawal outpoint, extracts `operator_xonly_pk` purely via `parse_op_return_data` (`core/src/verifier.rs:2319-2321`) with no signature check, and persists it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`). The framed operator's own `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) later queries `get_first_unhandled_payout_by_operator_xonly_pk` matching its own key (`core/src/database/verifier.rs:282-313`), finds this entry, and unconditionally calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839-916`), which builds and signs a real kickoff transaction to claim reimbursement from the N-of-N-secured bridge funds — with no check anywhere that the operator itself broadcast or funded that specific payout.

The only cross-check, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`), compares the OP_RETURN-derived `operator_xonly_pk` against `kickoff_data.operator_xonly_pk` and the committed payout blockhash against the kickoff's Winternitz-committed blockhash. Both checks pass trivially here: the attacker deliberately wrote the target operator's real key, and the payout blockhash is a real, correctly-confirmed block, since the attacker's transaction is a genuine confirmed payout — it merely wasn't funded by that operator.

### Impact Explanation
The framed operator's automation (`PayoutCheckerTask`) will construct and broadcast a real kickoff transaction and, absent challenge/disprove, eventually spend the `Reimburse` UTXO secured by verifiers' N-of-N presigned signatures — obtaining bridge funds for a withdrawal it never fronted with its own BTC. This matches the Critical category "an operator reimbursed for a payout it never funded." It is repeatable: any user with a pending withdrawal UTXO can perform this for any deposit they withdraw, against any operator whose public x-only key is known (public information from `deposit_data.actors.operators`), each time draining bridge value equal to one bridge deposit amount.

### Likelihood Explanation
The attacker only needs to be a normal user requesting a withdrawal from the Citrea bridge contract and control of the withdrawal UTXO's private key (which they inherently have as the withdrawing user) — no operator, verifier, or aggregator privilege is required. They construct the payout tx themselves (bypassing the operator's RPC) and simply place a target operator's public key in the OP_RETURN before broadcasting. The only cost is normal Bitcoin transaction fees. It works against any operator whose automation (`PayoutCheckerTask`) is enabled and blindly trusts DB-derived payer attribution, which is the default automated flow described in `core/src/task/payout_checker.rs`.

### Recommendation
Bind `operator_xonlypk` cryptographically to the actual funding of the payout — e.g., require the operator's Schnorr signature (or a second, operator-controlled input) covering the whole payout transaction (including the OP_RETURN output) with `SIGHASH_ALL`/`SIGHASH_ALL|ANYONECANPAY` from the operator's key, and have both the bridge circuit and `update_finalized_payouts`/`PayoutCheckerTask` verify that signature before trusting the OP_RETURN-embedded identity, instead of accepting unauthenticated OP_RETURN bytes as proof of funding.
