### Title
Fail-open default in `fetchPushControl` treats an API/network failure as full push permission - ([File: app/src/lib/api.ts])

### Summary
`API.fetchPushControl` is meant to tell Desktop whether the branch protection rules on the remote allow the current push (deletions, force-pushes, required status checks/reviews). When the underlying GitHub API request throws (timeout, network error, malicious/failing proxy response), the function's `catch` block does not propagate a "unknown" state — it fabricates a maximally-permissive `IAPIPushControl` object. This mirrors the report's root cause: an oracle/data source becomes unavailable, the code swallows the failure in a `catch`, and the fallback value is treated by downstream logic as a normal, trustworthy, and in this case maximally-permissive result rather than a safe/conservative one.

### Finding Description
`fetchPushControl` explicitly documents the fail-open behavior and implements it: [1](#0-0) 

```
/**
 * Get branch protection info to determine if a user can push to a given branch.
 *
 * Note: if request fails, the default returned value assumes full access for the user
 */
public async fetchPushControl(...): Promise<IAPIPushControl> {
  ...
  try {
    const response = await this.ghRequest('GET', path, { customHeaders: headers })
    return await parsedResponse<IAPIPushControl>(response)
  } catch (err) {
    log.info(`[fetchPushControl] unable to check if branch is potentially pushable`, err)
    return {
      pattern: null,
      required_signatures: false,
      required_status_checks: [],
      required_approving_review_count: 0,
      required_linear_history: false,
      allow_actor: true,
      allow_deletions: true,
      allow_force_pushes: true,
    }
  }
}
```

This fabricated object is then consumed by `isBranchPushable`, which checks `allow_actor !== false` and whether there are merge requirements: [2](#0-1) 

Because the catch branch sets `allow_actor: true`, `allow_deletions: true`, `allow_force_pushes: true`, and empty `required_status_checks`, `isBranchPushable` will report the branch as freely pushable/force-pushable/deletable any time the push-control request fails — which is exactly the scenario an attacker who can disrupt or delay the GitHub API response (a malicious/failing proxy on the network path, or a slow/erroring API endpoint) can trigger. This is structurally identical to the reported Curve bug: `tryPairedPrice`'s empty `catch {}` turns an oracle timeout into `highPaired = FIX_MAX`, a maximal/permissive value that downstream code (`_metapoolBalancesValue`) treats as legitimate.

### Impact Explanation
Because `fetchPushControl` is a client-side/UI signal (GitHub's server ultimately still enforces branch protection rules on the actual push), the concrete impact is that Desktop's local decisioning (`isBranchPushable`) and any warnings/confirmations gated on it become unreliable exactly when an attacker controls the network path to the GitHub API (proxy tampering, connection resets, timeouts). This can cause Desktop to silently treat a protected/force-push-restricted branch as pushable and skip user-facing warnings that would otherwise stop a destructive force-push or deletion from being attempted, i.e., a form of "silent corruption of what the user pushes" caused by an attacker-influenced remote/proxy response. I was not able to fully trace, within the remaining tool budget, every UI call site in `app/src/lib/stores/app-store.ts` (4 references) that consumes `fetchPushControl`/`isBranchPushable` to confirm exactly which confirmation dialogs are gated by it, so the precise blast radius (e.g., whether it only affects an informational banner versus actually suppressing a force-push confirmation prompt) is not fully confirmed from the index alone.

### Likelihood Explanation
Triggering the fallback only requires making the `push_control` API call fail or time out, which is plausible for any actor that can interfere with the network path to GitHub (or GitHub Enterprise) — e.g., a malicious/failing proxy, a flaky enterprise endpoint, or targeted request disruption. No credentials, local access, or social engineering are required beyond the attacker's control over the network/API path, which is within the accepted threat model ("attacker controls ... a git remote/proxy response").

### Recommendation
Change `fetchPushControl`'s failure path to return a conservative/unknown-permission signal (e.g., `null`/`undefined` or a maximally-restrictive default with `allow_actor: false`, `allow_deletions: false`, `allow_force_pushes: false`) rather than an "assume full access" object, and update `isBranchPushable`/its callers to treat "unknown" as "do not skip protections" rather than silently proceeding. This mirrors the general fix for the reported issue: on oracle/data-fetch failure, propagate an explicit "unavailable" state instead of substituting an extremal, maximally-permissive value that downstream logic implicitly trusts.

### Proof of Concept
1. User initiates a force-push or deletion of a branch on a repository that has branch protection configured to disallow it.
2. An attacker positioned on the network path (e.g., a compromised/failing corporate proxy, unreliable GHE endpoint, or deliberate connection reset targeting `repos/{owner}/{name}/branches/{branch}/push_control`) causes the `ghRequest` call in `fetchPushControl` to throw.
3. `fetchPushControl`'s `catch` block returns `{ allow_actor: true, allow_deletions: true, allow_force_pushes: true, required_status_checks: [], required_approving_review_count: 0, ... }`. [3](#0-2) 
4. `isBranchPushable` evaluates this object and returns `true` (pushable, no merge requirements), even though the real branch protection rules would forbid the action. [2](#0-1) 
5. Any Desktop logic that gates a protection warning/confirmation on this result treats the branch as unrestricted, based purely on an attacker-influenced network failure rather than the actual server-side rule.

```typescript
export function isBranchPushable(pushControl: IAPIPushControl) {
  const {
    allow_actor,
    required_status_checks,
    required_approving_review_count,
  } = pushControl

  // See https://github.com/desktop/desktop/issues/9054#issuecomment-582768322
  // We'll guard against this being undefined until we can determine the
  // root cause and fix that.
  const requiredStatusCheckCount = Array.isArray(required_status_checks)
    ? required_status_checks.length
    : 0

  // If user is admin and branch is not admin-enforced,
  // required status checks and reviews get zeroed out in API response (no merge requirements).
  // If user is admin and branch is admin-enforced,
  // required status checks and reviews do NOT get zeroed out in API response.
  // If user is allowed to push based on `Restrict who can push` setting, they must still
  // respect the merge requirements, and can't push if checks or reviews are required for merging
  const noMergeRequirements =
    requiredStatusCheckCount === 0 && required_approving_review_count === 0

  // We check for !== false so that if a future version of the API decides to
  // remove or rename that property we'll revert to assuming that the user
  // _does_ have access rather than assuming that they _don't_.
  return allow_actor !== false && noMergeRequirements
```
