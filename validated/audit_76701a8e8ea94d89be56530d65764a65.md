Found the analog. The Tron `IntentGatewayV2` escrow accounting diverges from actual token custody for fee-on-transfer (or any non-standard-transfer) tokens, exactly mirroring the `USDMPegRecovery` pattern where internal ledger balances are credited based on a nominal/expected amount instead of the amount actually received by the contract.

### Title
Escrow ledger in Tron `IntentGatewayV2.placeOrder` credited with nominal amount instead of actual tokens received, causing under-collateralized escrow and stuck withdrawals - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder`'s non-predispatch escrow path pulls tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount` — a value derived from `order.inputs[i].amount` (the nominal, user-declared amount) rather than the tokens the contract actually received.

### Finding Description
`placeOrder` in the non-predispatch branch does: [1](#0-0) 
It calls `safeTransferFrom` for `order.inputs[i].amount` and then increments the escrow ledger `_orders[commitment][token]` by `reducedInputs[i].amount`, which is arithmetically derived (`originalAmount - protocolFee`) purely from the caller-supplied `order.inputs[i].amount`: [2](#0-1) 
There is no balance-delta check (`balanceOf(this) before/after transfer`) in this branch, unlike the predispatch branch a few lines above, which explicitly reads `IERC20(token).balanceOf(dispatcher)` and reverts if `balance < requiredAmount` before crediting escrow: [3](#0-2) 

This is the same broken invariant as the external report: the contract's internal accounting (`_orders` mapping) is credited based on a value that is not guaranteed to equal the tokens the contract actually custodies. Any ERC-20 with a fee-on-transfer, rebasing, or deflationary mechanism (or any future token used as `order.inputs[i].token`) will cause the contract to hold strictly less than what `_orders[commitment][token]` claims. The companion EVM contract (`evm/src/apps/intentsv2`) was hardened against exactly this class of bug — its test suite explicitly verifies "Escrow should equal actual received amount, not the user-specified amount" for fee-on-transfer tokens: [4](#0-3) 
but the Tron contract's non-predispatch escrow path was never updated to match, leaving the discrepancy live there.

### Impact Explanation
When `withdraw()` is later called (on fill, refund, or cancellation) it releases `body.tokens[i].amount` from `_orders[commitment][token]` and attempts an actual token transfer of that amount: [5](#0-4) 
Since the ledger overstates the real token balance, the last order(s) relying on that inflated escrow balance will either revert (the contract literally doesn't hold enough tokens to transfer, reverting the settlement/refund and permanently locking the ISMP-delivered request/GET-response flow that depends on this call succeeding) or, in multi-order scenarios sharing the same token, cause an implicit reallocation of funds — later orders effectively pay for the shortfall left by an earlier fee-on-transfer order, i.e. one user's escrow is silently drained to cover another's inflated ledger entry. This matches the required "loss/lock of funds due to false internal accounting" impact and directly triggers the `UnknownOrder`/transfer-revert failure mode described in the source report, since `withdraw` cannot deliver the exact amount recorded.

### Likelihood Explanation
This is reachable by any unprivileged user: an attacker (or even an unwitting user) simply calls `placeOrder` with `order.inputs[i].token` set to a fee-on-transfer/deflationary ERC-20. No relayer, prover, or admin cooperation is required — the discrepancy is created purely by the token's own transfer semantics interacting with the contract's unconditioned bookkeeping. Given that Tron's ecosystem includes several TRC-20 tokens with transfer taxes/rebasing behavior, and the gateway does not restrict which tokens can be used as `order.inputs[i].token`, likelihood is high once such a token is used.

### Recommendation
Mirror the fix already present in the predispatch branch and in the EVM `evm/src/apps/intentsv2` contracts: measure `balanceOf(address(this))` immediately before and after `safeTransferFrom` in the non-predispatch escrow loop, and credit `_orders[commitment][token]` (and compute `reducedInputs`/protocol fee) from the actual received delta rather than from `order.inputs[i].amount`.

### Proof of Concept
1. Deploy Tron `IntentGatewayV2` with a fee-on-transfer TRC-20 token (e.g., 1% transfer tax) registered as a valid input token, `protocolFeeBps = 0` for simplicity.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, taking the non-predispatch branch.
3. `safeTransferFrom(user, gateway, 1000e18)` triggers the token's fee, so the gateway actually receives `990e18`, but `_orders[commitment][FOT] += 1000e18` (full nominal amount, since `protocolFeeBps == 0` means `reducedInputs[i].amount == order.inputs[i].amount`).
4. A solver later fills/cancels the order; `withdraw()` attempts to transfer `1000e18` FOT out of the gateway, but the gateway holds only `990e18` (plus whatever residual balance from prior unrelated orders) — the transfer either reverts (`TransferFailed`), permanently stalling the settlement callback from `onAccept`/`onGetResponse`, or succeeds by drawing down tokens escrowed for a different, unrelated order's commitment, causing that other order's later withdrawal to revert with `UnknownOrder`/insufficient balance.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }
