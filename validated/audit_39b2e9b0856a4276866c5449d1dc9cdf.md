## Title
Hardcoded bridge-contract address in `LibUsdOracle`-style binding breaks storage-proof verification on any deployment that uses a different Citrea bridge contract address - (File: `circuits-lib/src/bridge_circuit/storage_proof.rs`, `core/src/citrea.rs`)

### Summary
The bridge circuit and the host-side Citrea client both bind the EVM storage-proof verification (which proves a withdrawal/deposit UTXO is registered in Citrea's bridge contract) to a **hardcoded** contract address, `0x3100000000000000000000000000000000000002`, instead of the value configured in `bridge_config.toml`/env (`bridge_contract_address`). This is the same bug class as the reported `LibUsdOracle` issue: a protocol constant that only works for one specific deployment target is baked into logic that is supposed to be portable across deployments, and the configuration surface that suggests portability is silently ignored.

### Finding Description
`circuits-lib/src/bridge_circuit/storage_proof.rs` defines: [1](#0-0) 
and uses this constant `ADDRESS` inside `storage_verify` to compute the account key that the Merkle/JMT storage proof is checked against: [2](#0-1) 

The host-side equivalent, `core/src/citrea.rs`, independently hardcodes the same address as a Rust `const` rather than reading it from `self.config.bridge_contract_address`: [3](#0-2) 
and uses this constant both to instantiate the ABI contract binding used for deposit/withdrawal collection: [4](#0-3) 
and to fetch the EIP-1186 storage proof that is later fed into the ZK circuit above: [5](#0-4) 

Meanwhile, the deployment configuration format explicitly exposes `bridge_contract_address` as a *configurable* field (present in `bridge_config.toml` for regtest/testnet4 and in `.env`), implying it can be changed per deployment: [6](#0-5) 

Because neither the circuit (`ADDRESS` constant in `storage_proof.rs`) nor the host client (`BRIDGE_CONTRACT_ADDRESS` constant in `citrea.rs`) actually consult this configuration value when computing storage keys or fetching proofs, any deployment whose Citrea bridge contract is deployed at a different address than the hardcoded one will have its storage-key derivation permanently mismatched: `storage_verify` computes `keccak(ADDRESS || slot)` against a contract address that does not correspond to the real bridge contract for that deployment, so the JMT/Merkle proof can never validate against the actual state root of the real bridge contract.

### Impact Explanation
This breaks the core custody-attestation binding the bridge circuit exists to enforce: "a withdrawal recorded in the Citrea bridge contract equals the withdrawal the operator is claiming to have fronted." If the real, deployed bridge contract address differs from the hardcoded constant (e.g., any deployment other than the specific instance the constant was written for), `verify_storage_proofs`/`storage_verify` will panic/fail for every legitimate withdrawal, because the storage key is derived from the wrong contract address. Concretely:
- The additional-disprove/bridge circuit path (`bridge_circuit`) can never successfully prove a legitimate payout was backed by a real Citrea withdrawal, i.e., "a true [claim] made unprovable" — this permanently prevents proving correct operator behavior and permanently prevents proving disprove conditions, since both directions rely on the same broken storage-key derivation.
- This is a hardcoded value that cannot be fixed by an operator/verifier through configuration alone (the config field is inert), so the bug reproduces the exact deployment-portability failure described in the reference report.

### Likelihood Explanation
This triggers deterministically (100% of the time) for any deployment where the Citrea bridge contract is not deployed at exactly `0x3100000000000000000000000000000000000002` — which is guaranteed to occur whenever Clementine is redeployed for a new Citrea network/rollup instance, since Citrea system contracts are deployed per-genesis and the address is not guaranteed to be preserved. No attacker action is required; it is purely a function of deployment configuration mismatch versus hardcoded circuit/host logic.

### Recommendation
Thread `config.bridge_contract_address` through to both the host's `CitreaClient` (`core/src/citrea.rs`) storage-proof fetch and contract binding construction, and pass the same address as a circuit input (committed to the journal alongside the light-client proof or as a build-time/verified constant matching the specific target chain) to `circuits_lib::bridge_circuit::storage_proof::verify_storage_proofs`/`storage_verify`, instead of using compiled-in constants in both places. At minimum, fail loudly at startup if the configured `bridge_contract_address` does not match the compiled-in circuit constant, so a deployment mismatch is caught before it silently makes the bridge circuit permanently unprovable.

### Proof of Concept
1. Deploy Clementine against a Citrea (or Citrea-compatible) rollup instance whose bridge system contract is deployed at an address other than `0x3100000000000000000000000000000000000002` (a realistic scenario for any new L2/testnet genesis, since this address is genesis-specific).
2. Set `bridge_contract_address` in `bridge_config.toml`/`BRIDGE_CONTRACT_ADDRESS` in `.env` to the actual deployed address, per the documented configuration surface.
3. Observe that `core/src/citrea.rs::CitreaClient::new` and `get_storage_proof` still construct/query against the hardcoded `BRIDGE_CONTRACT_ADDRESS` constant (`core/src/citrea.rs:41`, `:285`, `:389`) — the configured value is never read.
4. Any withdrawal storage proof produced this way, when fed into `circuits_lib::bridge_circuit::storage_proof::storage_verify` (`circuits-lib/src/bridge_circuit/storage_proof.rs:146-177`), is checked against `keccak(ADDRESS=0x3100...0002 || slot)`, which does not correspond to the real bridge contract's account key in the state trie for that deployment. The proof (`storage_proof.verify(...)`) will fail/panic, permanently blocking the bridge circuit from validating any withdrawal for this deployment.
