## Title
Withdraw in `IntentGatewayV2` (Tron) transfers escrowed funds before decrementing escrow accounting, enabling reentrant double-redemption on a single relayed message - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The core broken invariant in the external report is a non-atomic read-modify-write on a shared balance/list: state is read, mutated in memory, and only written back afterward, with an unguarded gap in between that a second concurrent actor can exploit to duplicate or lose an update. In `IntentGatewayV2.withdraw` (Tron variant) the analogous gap is created by performing the token/ETH transfer (an external call) *before* decrementing the `_orders` escrow accounting, instead of updating storage first as the mainline EVM implementation does.

### Finding Description
`onAccept` (only callable by the host) dispatches `RedeemEscrow`/`RefundEscrow` messages into `withdraw()`: [1](#0-0) 

`withdraw()` sets `_filled[commitment]` up front (a partial CEI fix copied from the reentrancy-hardened same-chain path), but for the per-token escrow accounting it does the opposite: it performs the external transfer first and only decrements `_orders[commitment][token]` afterward: [2](#0-1) 

Compare this with the corresponding function in the mainline (non-Tron) implementation, `IntentsBase._withdraw`, which correctly decrements `_orders` *before* making the external transfer: [3](#0-2) 

In the Tron contract, the guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only checks non-zero, and the storage write `_orders[body.commitment][token] -= amount;` happens strictly after the low-level `.call`/`token.call` transfer. Because the transfer uses a raw `.call` (not `SafeERC20`) to an attacker-controlled `beneficiary` (taken directly from the cross-chain `WithdrawalRequest.beneficiary` for `RedeemEscrow`, or from `order.output.beneficiary`), an attacker who controls the beneficiary contract or a malicious hook-bearing token can re-enter during that external call. At the point of re-entry, `_orders[commitment][token]` still holds the pre-decrement value, so any reentrant path that reaches `withdraw()`/`onAccept` again for the same commitment before the decrement lands would pass the `== 0` check a second time and cause a duplicate transfer against the same escrowed balance — exactly the "second operation overwrites/duplicates before the first write lands" pattern from the reported bug class, just realized via a synchronous external call instead of async concurrency.

### Impact Explanation
If reachable, this allows draining escrowed input tokens beyond what was actually deposited for an order — a direct "stealing or loss of funds" and "double-settlement" outcome on bridge custody funds, which matches the required impact gate. The blast radius is scoped to the Tron deployment of `IntentGatewayV2`, since the mainline EVM `IntentsBase._withdraw` (and the reentrancy-hardened `_fillSameChain`/`_fillCrossChain` paths, confirmed by `IntrinsicIntentsReentrancyTest.sol`) already apply state-before-external-call ordering.

### Likelihood Explanation
This can only be assessed as **unconfirmed / lower-confidence** given the limits of static review: `withdraw()` itself is `internal` and only reachable through `onAccept` (`onlyHost`) or `onGetResponse` (`onlyHost`), both gated to the trusted host contract. Whether an actual reentrant call path exists from a malicious `beneficiary`/token callback back into a *second* `onAccept`/`onGetResponse` invocation for the same commitment within one transaction depends on how the Tron host processes batched incoming messages and whether it marks a request "consumed" before or after invoking the module callback — code I was not able to inspect in this pass. I could not verify the host's message-consumption ordering or find a Tron-side reentrancy guard equivalent to the mainline `Filled()`/CEI protections beyond the `_filled` write. This is a structural analog worth flagging, not a fully proven exploit chain.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) *before* issuing the external transfer, mirroring `IntentsBase._withdraw`'s checks-effects-interactions ordering. Additionally, verify/confirm the Tron host marks incoming request commitments as consumed (receipt written) before invoking `onAccept`, and consider adding an explicit reentrancy guard on `withdraw`/`onAccept` as defense in depth, consistent with the CEI fix already applied to `_fillSameChain`/`_fillCrossChain`.

### Proof of Concept
Could not be constructed/verified within this pass — a concrete PoC requires confirming (a) the Tron host's exact message-consumption/receipt-marking order relative to the `onAccept` callback, and (b) a reachable reentry path from the `beneficiary.call{value:}("")` / malicious-token `transfer` callback back into a second `withdraw` invocation for the same `commitment`/`token` before the decrement executes. I recommend a background engineering pass to: (1) trace the Tron host's inbound-message dispatch loop for receipt-before-call ordering, and (2) write a Foundry/Tron test analogous to `IntrinsicIntentsReentrancyTest.sol` targeting `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw` with a malicious beneficiary/ERC777-style token to confirm whether double redemption is achievable.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
