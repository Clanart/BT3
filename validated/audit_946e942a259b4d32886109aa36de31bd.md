## Title
Asymmetric `PuzzleInfo.__eq__` lets an offer counterparty smuggle extra/forged driver keys past identity checks, causing wallets to trust attacker-controlled puzzle drivers - (File: chia/wallet/puzzle_drivers.py)

### Summary
`PuzzleInfo` is the dictionary-of-strings wrapper used everywhere a CAT/NFT/DID/singleton "driver" is represented — including `driver_dict` values that arrive directly from an untrusted offer counterparty. Its `__eq__` implementation only iterates the keys present on `self`, never validating that `other` doesn't carry additional (or different-shaped) keys. This is the same class of bug as the reported `deepMerge()` prototype pollution: a keyed, recursive data structure that is populated from attacker-controlled input without validating/normalizing the full key set, and whose result is then trusted by downstream logic that assumes structural integrity.

### Finding Description
`PuzzleInfo.__eq__` at [1](#0-0)  is:
```python
def __eq__(self, other: object) -> bool:
    for key, value in self.info.items():
        try:
            if self[key] != other[key]:
                return False
        except Exception:
            return False
    return True
```
This only checks that every key `self` has also exists and matches in `other`. It never checks the reverse direction — extra keys that exist only in `other.info` (or, recursively, inside an `also()` sub-driver) are completely unexamined. Since `PuzzleInfo` recursion is driven entirely by the `"also"` magic key [2](#0-1) , this is structurally the same "special/reserved key not sanitized during merge/compare" flaw as the merge-guard advisory, just expressed via equality instead of assignment.

This dict is populated straight from wallet-user or offer-counterparty controlled input in `TradeManager._create_offer_for_ids`, which is reached from `create_offer_for_ids` / `respond_to_offer` — both driven by externally supplied `driver_dict` (from `CreateOfferForIDs.driver_dict` over RPC, or from a decoded `Offer.driver_dict` supplied by the other trading party) [3](#0-2) . Inside `_create_offer_for_ids`:
```python
if asset_id in driver_dict and driver_dict[asset_id] != puzzle_driver:
    if self.check_for_owner_change_in_drivers(puzzle_driver, driver_dict[asset_id]):
        driver_dict[asset_id] = puzzle_driver
    else:
        raise ValueError(...)
else:
    driver_dict[asset_id] = puzzle_driver
``` [4](#0-3) 

`driver_dict[asset_id]` on the left is the **attacker-supplied** value (from `offer.driver_dict` when responding to a counterparty's offer, per `respond_to_offer` at [5](#0-4) ); `puzzle_driver` on the right is the value the wallet computed locally and trusts. Because `!=` calls `driver_dict[asset_id].__eq__(puzzle_driver)`, and `__eq__` only walks the attacker-controlled `self.info` keys, an attacker can craft a `PuzzleInfo` whose visible key set is a strict subset of the true structure (or omits a differentiating nested `"also"` layer) so that the comparison reports equality even though the underlying puzzle is materially different. When that happens, the `else: driver_dict[asset_id] = puzzle_driver` correction branch is skipped and the wallet keeps using the **attacker-forged** driver entry.

This forged driver is then used to compute the settlement puzzle hash that announcements are asserted against:
```python
settlement_ph: bytes32 = construct_puzzle(driver_dict[asset_id], OFFER_MOD).get_tree_hash()
``` [6](#0-5) 
and it is also what `Offer.aggregate()` relies on to detect disagreeing drivers across combined offers via the same asymmetric `!=` check [7](#0-6) . `check_for_owner_change_in_drivers` further compounds this by directly writing into a nested `also().also().info["owner"]` key based on attacker-provided driver data [8](#0-7) , i.e., attacker-controlled key content is spliced into the object used for subsequent identity/equality decisions — the same "unsanitized special-key write into a trusted structure" pattern as `deepMerge()`'s `__proto__` injection, adapted to this codebase's driver/identity model.

### Impact Explanation
If the equality bypass lets a forged/incomplete `PuzzleInfo` survive the reconciliation step, the wallet can build and sign a settlement spend whose announcement assertions, settlement puzzle hash, or asset-id association are computed from the attacker's forged driver rather than the wallet's own verified puzzle info. That directly threatens the "offer settlement theft" and "forged asset identity" outcomes called out as in-scope impact: a taker/maker can be tricked into asserting/paying against a puzzle hash that does not correspond to the asset the wallet believes it is trading, or into accepting a driver that misrepresents ownership/lineage-relevant fields for NFTs/DIDs/CATs during offer aggregation and acceptance.

### Likelihood Explanation
Both `create_offer_for_ids` and `respond_to_offer` accept the vulnerable `driver_dict` as ordinary, wallet-user/offer-counterparty-facing input over RPC and offer files — no special privilege is needed, and the check exists specifically to reconcile attacker input against trusted local computation, meaning it is exercised on every offer-accept path involving non-XCH assets.

### Recommendation
Make `PuzzleInfo.__eq__` (and `Solver.__eq__`, which has the identical pattern) symmetric and complete: compare the full key sets of both `self.info` and `other.info` (recursing through `"also"`), not just `self`'s keys, so that extra/hidden keys on either side force inequality rather than being silently ignored. Reject/normalize unknown keys before trusting an externally supplied `driver_dict` entry in `TradeManager._create_offer_for_ids` and `Offer.aggregate()`.

### Proof of Concept
```python
from chia.wallet.puzzle_drivers import PuzzleInfo

trusted = PuzzleInfo({
    "type": "singleton",
    "launcher_id": "0xaa..",
    "also": {"type": "metadata", "metadata": "...", "updater_hash": "0xbb.."},
})

# Attacker constructs a driver with a strict subset of trusted's keys,
# e.g. omitting the differentiating "also" metadata layer or a field
# whose absence isn't asserted by __eq__'s self-only iteration.
forged = PuzzleInfo({
    "type": "singleton",
    "launcher_id": "0xaa..",
})

assert forged == trusted  # True: forged.info only has keys that also match trusted,
                           # extra/mismatched fields on `trusted` are never checked.
```
When `forged` is placed in an offer's `driver_dict` and `trusted` is the wallet's locally computed `puzzle_driver`, `driver_dict[asset_id] != puzzle_driver` evaluates `False`, so `TradeManager._create_offer_for_ids` skips overwriting `driver_dict[asset_id]` with the trusted value and proceeds to build announcements/settlement puzzle hashes from the attacker's `forged` driver.

    def check_for_owner_change_in_drivers(self, puzzle_info: PuzzleInfo, driver_info: PuzzleInfo) -> bool:
        if puzzle_info.check_type(
            [
                AssetType.SINGLETON.value,
                AssetType.METADATA.value,
                AssetType.OWNERSHIP.value,
            ]
        ) and driver_info.check_type(
            [
                AssetType.SINGLETON.value,
                AssetType.METADATA.value,
                AssetType.OWNERSHIP.value,
            ]
        ):

            puzzle_info.also().also().info["owner"] = old_owner  # type: ignore
            if driver_info == puzzle_info:
                return True
        return False
