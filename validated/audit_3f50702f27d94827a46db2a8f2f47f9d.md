## Analysis

The reported bug class is: an emergency "disable" flag intended to stop new risky actions also incorrectly blocks the withdrawal/exit path that users need most during an incident.

The direct analog in this codebase is in `evm/src/core/EvmHost.sol`, which defines:

```solidity
modifier notFrozen() {
    if (_frozen == FrozenStatus.Outgoing || _frozen == FrozenStatus.All) revert FrozenHost();
    _;
}
``` [1](#0-0) 

This modifier gates the host's outgoing `dispatch(...)` entrypoints — the single choke point used both to *place* new cross-chain intents and to *cancel/refund* existing ones.

### Finding

`IntentsBase._cancelFromSource` and `IntentsBase._cancelFromDest` (and their equivalents in `IntentGatewayV2.sol` / Tron's `IntentGatewayV2.sol`) both route the cancellation/refund flow through `IDispatcher(hostAddr).dispatch(...)`: [2](#0-1) [3](#0-2) 

Because that `dispatch` call carries the `notFrozen` modifier on `EvmHost`, when the host is placed in `FrozenStatus.Outgoing` or `FrozenStatus.All` (the exact emergency states an operator would activate in response to an incident, e.g. a compromised consensus client or a discovered exploit), **users lose the ability to cancel cross-chain orders and reclaim their escrowed tokens** via `_cancelFromSource`/`_cancelFromDest`, exactly like the pool-disabled case blocking liquidity removal in the seed report. Only the same-chain cancellation path (`_cancelSameChain`, which does not call `dispatch`) remains usable — cross-chain escrow refunds are locked for as long as the freeze persists.

This is the same broken invariant as the seed finding: the "pause new outgoing activity" switch and the "let users exit/refund" switch are wired to the same guard, so an incident-response freeze (needed precisely when funds might be at risk) simultaneously strands user funds in cross-chain escrow with no way to trigger `RefundEscrow`/`RedeemEscrow` messages until the freeze is lifted by an admin.

### Title
Outgoing-frozen host state blocks cross-chain intent cancellation, locking escrowed user funds — (File: `evm/src/core/EvmHost.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`EvmHost`'s `notFrozen` modifier reverts on any outgoing `dispatch` while `FrozenStatus` is `Outgoing` or `All`. `IntentsBase._cancelFromSource`/`_cancelFromDest`, used by `cancelOrder`, rely on this same `dispatch` call to issue the GET/POST messages that refund escrowed tokens cross-chain. Freezing the host — the intended incident-response action — therefore also disables the user's only escape hatch for cross-chain order cancellation, leaving escrowed funds stuck.

### Finding Description
`cancelOrder` dispatches to `_cancelFromSource` (GET request to verify non-fill) or `_cancelFromDest` (POST `RefundEscrow` to source), both of which call `IDispatcher(hostAddr).dispatch{...}(request)`. That call target is `EvmHost.dispatch`, decorated with `notFrozen`, which reverts with `FrozenHost` whenever `_frozen` is `Outgoing` or `All`. No branch in the cancellation flow bypasses this modifier for refund-intent traffic, unlike the recommended fix in the seed report (differentiate by direction/intent rather than blanket status).

### Impact Explanation
During any period where the host is frozen for outgoing traffic — which is exactly the scenario in which users would want to cancel pending intents and reclaim funds — cross-chain order cancellation is unconditionally unavailable, causing user-owned escrowed tokens to be locked in the `IntentsBase`/`IntentGatewayV2` contracts for the duration of the freeze, with no user-controlled recovery path.

### Likelihood Explanation
This triggers deterministically any time the host enters `Outgoing`/`All` frozen state while cross-chain orders are outstanding — no malicious actor, race condition, or malformed proof is required. It is a direct architectural consequence of routing both order placement and order cancellation through the same `notFrozen`-gated `dispatch` function.

### Recommendation
Distinguish cancellation/refund dispatches from new order-placement dispatches, e.g. expose a `dispatch` (or dedicated refund path) that is exempt from `notFrozen`, or only enforce `notFrozen` for state-changing intent creation, mirroring the recommended fix in the seed report (gate only "add"/new actions on the enabled/frozen flag, not "remove"/refund actions).

### Proof of Concept
1. Admin (or automated circuit breaker) sets `_frozen = FrozenStatus.Outgoing` on `EvmHost` in response to an incident.
2. A user with a pending cross-chain order calls `IntentGatewayV2.cancelOrder(order, options)`.
3. Execution reaches `_cancelFromSource`/`_cancelFromDest`, which calls `IDispatcher(hostAddr).dispatch(...)`.
4. `EvmHost.dispatch`'s `notFrozen` modifier reverts with `FrozenHost` [4](#0-3) .
5. The user's escrowed tokens remain locked in the gateway contract until the freeze is lifted by governance/admin, with no alternative on-chain recovery route for cross-chain orders.
