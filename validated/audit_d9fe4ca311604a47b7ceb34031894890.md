### Title
`host_deposit_constant` Passes `deposit_value_bytes` Instead of `move_txid` to `deposit_constant()`, Corrupting `BridgeCircuitBitvmInputs` and Breaking the Disprove Mechanism — (`File: bridge-circuit-host/src/structs.rs`)

---

### Summary

`host_deposit_constant()` in `bridge-circuit-host/src/structs.rs` passes `deposit_value_bytes` (the EIP-1186 storage proof deposit amount) as the `move_txid` argument to `deposit_constant()`. The bridge circuit (zkVM guest) correctly passes `*move_txid` derived from `verify_storage_proofs()`. Because these are entirely different 32-byte values, the host-computed `DepositConstant` diverges from the one the circuit commits to the zkVM journal. The corrupted value propagates into `BridgeCircuitBitvmInputs.deposit_constant`, which is used to reconstruct the Groth16 public input for on-chain disprove verification, breaking the challenge-response mechanism for every deposit.

---

### Finding Description

The `deposit_constant()` function is defined in `circuits-lib/src/bridge_circuit/mod.rs` with the following signature:

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],        // ← 4th param: move transaction ID
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant
``` [1](#0-0) 

**Bridge circuit (zkVM guest) — correct call:**

Inside `bridge_circuit()`, `move_txid` is obtained from `verify_storage_proofs()` and passed correctly:

```rust
let (user_wd_outpoint, vout, move_txid) =
    verify_storage_proofs(&input.sp, light_client_circuit_output.l2_state_root);
...
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,          // ← correct: actual move-to-vault txid
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
``` [2](#0-1) 

**Host side — incorrect call:**

`host_deposit_constant()` in `bridge-circuit-host/src/structs.rs` instead passes `deposit_value_bytes`, which is the U256 deposit amount encoded as big-endian bytes from the EIP-1186 storage proof:

```rust
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,   // ← WRONG: deposit amount, not move_txid
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
``` [3](#0-2) 

`host_deposit_constant()` is called from `SuccinctBridgeCircuitPublicInputs::new()`: [4](#0-3) 

The resulting `deposit_constant` field is then referenced as `public_inputs.deposit_constant` inside `prove_bridge_circuit()` and flows into `BridgeCircuitBitvmInputs`: [5](#0-4) 

`BridgeCircuitBitvmInputs.deposit_constant` is used in `calculate_groth16_public_input()` to reconstruct the Groth16 public input for on-chain verification: [6](#0-5) 

For comparison, `creator.rs` and `verifier.rs` both compute `deposit_constant` correctly with `move_txid`: [7](#0-6) [8](#0-7) 

---

### Impact Explanation

The `deposit_constant` is the binding commitment that ties a bridge circuit proof to a specific deposit. It is hashed into the `journal_hash` committed by the zkVM: [9](#0-8) 

The `journal_hash` becomes the Groth16 public input. The on-chain disprove script (pre-signed during deposit setup using the correct `move_txid`-based `deposit_constant` from `creator.rs`) verifies the Groth16 proof against this public input.

Because `host_deposit_constant()` produces a different `deposit_constant` than the circuit commits, `BridgeCircuitBitvmInputs.deposit_constant` is wrong. The operator's Assert transactions commit to a Groth16 public input that does not match what the circuit actually proved. The disprove script, which uses the correct `deposit_constant`, will detect this mismatch and allow any challenger to successfully disprove a legitimate operator and burn their collateral.

**Concrete impact:**
- Any challenger can burn a legitimate operator's collateral by challenging a valid payout — the operator's Assert transactions will always commit to the wrong Groth16 public input.
- Operators cannot obtain reimbursement for valid withdrawals they fronted, permanently locking their collateral.
- The bridge's liveness guarantee is broken for every deposit.

---

### Likelihood Explanation

This is a deterministic code bug. It triggers on every invocation of `prove_bridge_circuit()` for every deposit on every network. No special attacker capability is required — any party who can post a challenge transaction (an unprivileged on-chain action) can exploit this.

---

### Recommendation

Fix `host_deposit_constant()` to derive `move_txid` from the storage proof the same way the bridge circuit does — by calling the host-side equivalent of `verify_storage_proofs()` and using the returned `move_txid` as the 4th argument to `deposit_constant()`. The `deposit_value_bytes` variable is not a valid substitute and should be removed from this call.

---

### Proof of Concept

1. Operator makes a valid payout for deposit D, fronting the BTC.
2. Challenger posts a challenge transaction against the operator's kickoff.
3. Operator calls `prove_bridge_circuit()`:
   - zkVM circuit computes `deposit_constant` with `move_txid` = `0xABCD...` → `journal_hash_A`
   - `host_deposit_constant()` computes `deposit_constant` with `deposit_value_bytes` = `0x0000...bridge_amount` → `journal_hash_B ≠ journal_hash_A`
   - `BridgeCircuitBitvmInputs.deposit_constant` encodes `journal_hash_B`
4. Operator posts Assert transactions committing to the Groth16 public input derived from `journal_hash_B`.
5. Challenger calls the disprove script, which uses the pre-signed `deposit_constant` (correct, based on `move_txid`) to reconstruct the expected public input from `journal_hash_A`.
6. The operator's committed public input (`journal_hash_B`) does not match the expected (`journal_hash_A`).
7. Disprove succeeds: operator's collateral is burned despite the operator having acted honestly.
8. Operator loses collateral; bridge liveness is broken.
