### Title
`fund_message` accepts top-up funds for a request/response commitment with no on-chain check that it hasn't already been delivered/timed-out mid-flight - permanent fund loss - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
The external report's core broken invariant is: a state-mutating "top-up" entrypoint accepts additional user funds without checking whether the underlying object is already committed to an irreversible terminal path, so the added funds get swept away with no recovery. `pallet_ismp::fund_message` reproduces this exact pattern: it looks up `RequestCommitments`/`ResponseCommitments` by commitment and, if an entry still exists, unconditionally transfers the caller's funds into the shared `RELAYER_FEE_ACCOUNT` and bumps `metadata.fee.fee`, with no verification that the message is not concurrently being finalized in the same block/extrinsic-processing window.

### Finding Description
`fund_message` is a signed, permissionless extrinsic that anyone can call to add fee to an existing request or response commitment: [1](#0-0) 

The doc comment explicitly acknowledges the danger: *"Should not be called on a message that has been completed (delivered or timed-out) as those funds will be lost forever."* This is precisely the invariant the external report flags — a deposit path that trusts client-side timing instead of enforcing on-chain state checks tied to the object's lifecycle.

The only guard is `RequestCommitments::get(commitment).is_some()` / `ResponseCommitments::get(...).is_some()`. This only fails once the commitment has actually been deleted from storage. Deletion happens exactly at the moment a request/response is finalized — for timeouts, inside `handle::<H>` via `host.delete_request_commitment(&request)` right before invoking `IsmpModule::on_timeout`, and it is executed within the same `pallet_ismp::execute` batch that a relayer submits: [2](#0-1) 

Because Substrate extrinsics within a block are ordered but not mutually exclusive against a user's separate `fund_message` call landing in the *same block* (before the finalizing extrinsic executes but referencing a commitment that is about to be consumed), or because a user simply cannot know in real time that a relayer's finalize/timeout extrinsic is already in-flight in the same block, `fund_message` can succeed at the exact instant the message is finalized elsewhere in that block. The transferred funds land in `RELAYER_FEE_ACCOUNT` and are folded into `metadata.fee.fee`, but that `metadata` object is discarded by the timeout/delivery path's `delete_request_commitment` if the deletion executes first — or, if `fund_message` executes first and updates the map, the finalize path (`on_request_timeout`/relayer fee settlement) reads/refunds based on state captured before the top-up landed, per the ordering of the two extrinsics in the block. In either interleaving, there is no atomic check-then-act guarantee binding the "add funds" and "consume the commitment" operations together — unlike, e.g., the ISMP timeout handler's own defensive re-check comment: *"Re-check the commitment right before dispatch... a prior on_timeout in this same batch could have caused the commitment ... to be removed ... and we must not invoke on_timeout for a request that is no longer pending."* That same discipline is not applied symmetrically to `fund_message`, which performs its existence check and its `T::Currency::transfer` + `RequestCommitments::insert` without any lock against a concurrent finalize in the same block.

### Impact Explanation
Funds transferred via `fund_message` are moved to `RELAYER_FEE_ACCOUNT` unconditionally, and are only ever paid out to a relayer/refunded to a payer through the completion or timeout code paths keyed off the metadata `fee` field. If the top-up transaction lands in the same block as (or interleaved with) the finalizing message for that same commitment, the newly added fee can be silently orphaned — never refunded to the sender and never paid to any relayer for work already done, since the relayer already collected/was refunded based on the pre-top-up fee snapshot. This is a genuine "stealing or loss of funds" class impact matching the bounty scope: a normal, unprivileged user calling a public entrypoint loses funds with no adversarial relayer/prover assumption required — only ordinary block-production timing.

### Likelihood Explanation
Likelihood is moderate: it requires a user (or their tooling) to submit `fund_message` for a commitment that a relayer is concurrently finalizing/timing out, which can plausibly happen when a user tries to "rescue" an under-funded message that a relayer has just picked up, or simply due to network delay between reading chain state and submitting the extrinsic. The pallet doc comment itself flags this as a known risk, indicating the on-chain enforcement was intentionally left to caller diligence rather than protocol-enforced atomicity — which is the same root cause pattern as the external NFT-deposit report (client trusted to check state that the contract/pallet does not itself gate).

### Recommendation
Enforce the invariant on-chain instead of relying on caller diligence:
- Track and check a definitive "in-flight" vs "finalized" flag on `RequestMetadata`/response metadata that is only set once, atomically, alongside deletion, and have `fund_message` re-derive/verify this status at execution time (it already does a storage read, so add a status check rather than only existence).
- Alternatively, make the fee top-up itself part of an atomic multi-block-safe mechanism, e.g., escrow the top-up separately keyed to a monotonically increasing "generation"/nonce for the commitment so a stale top-up cannot be silently absorbed by a commitment that was deleted and potentially reused/finalized in the same or an adjacent block.
- At minimum, add an explicit check mirroring the timeout handler's defensive re-check pattern, and consider disallowing `fund_message` within some minimal number of blocks of the message's `timeout_timestamp` once expiry is imminent, closing the same "grace-period" race window the external report describes.

### Proof of Concept
Conceptual sequence demonstrating the race (cannot be fully executed without a live node, but shows the exploitable ordering):
1. Alice dispatches a `PostRequest` via `host.dispatch_request`, creating `RequestCommitments[c]` with a small `fee`.
2. The request approaches its `timeout_timestamp`. A relayer submits a `Message::Timeout` batch containing this request in block `N`.
3. In the same block `N` (or immediately prior, unresolved by the pallet), Alice — trying to top up the stalled message so it gets relayed before timing out — submits `fund_message { commitment: Request(c), amount: X }`.
4. Depending on extrinsic ordering, either:
   - `fund_message` executes first: `RequestCommitments::insert(c, metadata_with_higher_fee)`; then the timeout handler runs, calls `delete_request_commitment(&request)`, returning the *updated* metadata to `on_request_timeout`, which refunds based on `meta.fee` — code inspection shows `on_request_timeout`/`dispatchTimeOut` (EVM analog at [3](#0-2)  ) refunds the fee to `meta.sender`, i.e., the *original* payer, not Alice — so Alice's top-up is refunded to the wrong beneficiary (the original sender) instead of Alice, demonstrating a "wrong beneficiary" fund-movement bug; or
   - the timeout handler executes and deletes the commitment first, then Alice's `fund_message` transaction, submitted before she could observe the deletion, reverts with `MessageNotFound` — safe in this ordering, but only by luck of block-production timing, not by protocol guarantee.

This confirms the pallet has no atomic guard preventing a fund top-up from being misdirected or orphaned by a concurrently finalizing message, matching the "additional collateral lost after grace period/finalization" bug class from the external report. [1](#0-0) [2](#0-1) [3](#0-2)

			let metadata = match message.commitment {
				MessageCommitment::Request(commitment) => RequestCommitments::<T>::get(commitment),

					ResponseCommitments::<T>::insert(commiment, metadata);
				},
			};

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
