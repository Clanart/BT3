### Title
Quadratic Lagrange interpolation driven by attacker-controlled `n`/`t` causes CPU exhaustion in `ThresholdKeys::read`/`ThresholdKeys::new` - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` deserializes `t` and `n` as raw `u16`s from the input stream, then `ThresholdKeys::new` computes the group key as `sum(verification_shares[i] * interpolation_factor(i))` for `i` in `1..=t`. Each `interpolation_factor` call under `Interpolation::Lagrange` loops over all `included` participants, making group-key derivation O(t²) in field multiplications plus `t` field inversions, with `t` fully attacker-controlled up to 65535.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), `t`, `n`, and `i` are read directly from the untrusted byte stream. `ThresholdParams::new` only checks `t <= n` and `i <= n` (lib.rs:166-179); there is no cap tying `n` to the real validator-set size. For `Interpolation::Lagrange` the reader then only needs to supply `n` serialized points plus one scalar (~`66*n` bytes ≈ 4.2 MB for `n = 65535`).

`ThresholdKeys::new` (lib.rs:376-378) then evaluates:
```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```
`Interpolation::Lagrange::interpolation_factor` (lib.rs:229-247) iterates over every element of `included`, performing a numerator and denominator field multiplication per element plus a full field inversion per participant. With `t = n = 65535` this is ~4.3×10⁹ field multiplications and 65535 batched inversions — hours of CPU for a ~4 MB input. The same quadratic cost is reachable again through `ThresholdKeys::view` (lib.rs:500-507), which recomputes `interpolation_factor` for every included signer.

This mirrors the advisory's bug class: a small attacker-declared size parameter (`/Size` in pypdf; `t`/`n` here) causes runtime wildly disproportionate to the input, and the expensive work happens before/without any proof that the declared structure corresponds to a real key set.

### Impact Explanation
Anywhere `ThresholdKeys::read` (or `ThresholdKeys::new`/`view` on deserialized parameters) is applied to bytes influenced by an untrusted party, a single message can pin a CPU core for an extended period. Repeated submissions amplify this into a full denial of service of the signing/coordinator path. Availability impact only; no key material is exposed — consistent with Medium severity under the source advisory's `CWE-834`/`A:H` profile.

### Likelihood Explanation
- Reachability: `ThresholdKeys::read` accepts all of `t`, `n`, `i`, and the interpolation discriminant from the stream; `n = 65535` and `t = 65535` satisfy every check in `ThresholdParams::new`, and `Lagrange` (tag `1`) skips the `t == n` restriction imposed on `Constant` interpolation (lib.rs:367-374), though even `Constant` with `t = n` hits the same quadratic path.
- Cost asymmetry: payload is `O(n)` bytes; compute is `O(t²)` field ops plus `t` inversions (an inversion alone costs hundreds of multiplications).
- Mitigating factor: the attacker must supply the `n` points' worth of bytes, and deployments may bound message sizes, which is why this is Medium rather than High.

### Recommendation
- Bound `n`/`t` in `ThresholdKeys::read`/`ThresholdParams::new` to a protocol-maximum (e.g., `MAX_KEY_SHARES_PER_SET`) before any group-key computation.
- Reorder `ThresholdKeys::new` so cheap validation occurs before the `O(t²)` group-key derivation, and/or compute the group key via a single Lagrange evaluation against participant `0` semantics instead of per-participant factorization.
- Where `view()` is called on deserialized key material, pre-validate `included.len()` against the same bound.
