### Title
`ThresholdKeys::read`/`ThresholdKeys::new` accepts attacker-chosen verification shares and secret share without any consistency or possession check, enabling group-key substitution - (File: crypto/dkg/src/lib.rs)

### Summary
The "missing allowlist/validation on a stored artifact" bug class maps onto Serai as missing validation on deserialized threshold key material. `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574) reads `t`, `n`, `i`, an interpolation method, a `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new` (line 349), which validates only parameter ranges (`t <= n`, participant indices `<= n`, correct share count) — never that `secret_share * G == verification_shares[i]`, never that the shares are non-identity, and never that the resulting `group_key` (line 377–378, computed as `Σ verification_shares[j] * interpolation_factor(j, 1..=t)`) corresponds to any secret known by legitimate key generation. An attacker who feeds crafted bytes to `ThresholdKeys::read` can substitute arbitrary verification-share points whose discrete logarithms they know, making `group_key()` an attacker-controlled key.

### Finding Description
- `ThresholdKeys::read` (crypto/dkg/src/lib.rs:591–632) parses the interpolation variant, `secret_share`, and a `HashMap` of `n` verification shares via `C::read_G`, then delegates to `ThresholdKeys::new`.
- `ThresholdKeys::new` (line 349) checks: share count equals `n` (line 355), keys are `<= n` (line 361), and `Constant` interpolation requires `t == n` (line 368). It then derives `group_key` solely from the attacker-supplied verification shares (line 376–378). There is no check that `secret_share` is consistent with `verification_shares[i]`, and no check that shares are non-identity or honestly generated.
- Because Lagrange interpolation factors over `1..=t` are public constants, an attacker can choose verification shares such that the weighted sum equals `G * x` for a known `x` (e.g., set `verification_shares[1] = G * x / λ_1` and all others to identity, which `read_G` accepts as canonical torsion-free points). The victim's `ThresholdKeys` then reports `group_key() = G * x`.
- `ThresholdKeys::view` (line 463) further scales every verification share by `scalar` and the interpolation factor and adds the offset to `included[0]` (line 518–521), preserving self-consistency — partial signatures produced by this node will verify against the attacker-chosen shares under FROST verification.

### Impact Explanation
Two concrete accepted-impact outcomes:
1. **Funds reported received that are not spendable (by Serai):** any wallet/scanner deriving deposit addresses from `group_key()` (e.g., bitcoin-serai outputs keyed by the tweaked group key) will report funds as received under a key whose discrete log only the attacker knows. The threshold group cannot spend them; the attacker can.
2. **Signing under an attacker-chosen key:** because the verification shares are internally consistent, the node's FROST `sign`/`complete` path produces partial signatures that verify against the substituted shares and aggregate into valid Schnorr signatures for the attacker's key — the validator attests to messages under a group key that was never generated by the DKG.

### Likelihood Explanation
Reachability is granted by the threat model: `ThresholdKeys::read` consumes a fully attacker-controlled byte stream (the serialized-key blob is exactly the "file uploaded to a storage backend" analog — arbitrary point encodings are accepted with only canonicality checks). The attack requires no collusion, no valid DKG transcript, and no knowledge of any honest secret — only the ability to supply the byte encoding that gets deserialized. Exploitation is deterministic once loaded, since `group_key` derivation is a pure function of the substituted shares.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), add a consistency proof: require `C::generator() * secret_share == verification_shares[&params.i()]` and reject identity (`is_identity`) verification shares. Additionally, at the protocol level, serialized `ThresholdKeys` should carry (or be reconstructible from) the DKG commitments so that `group_key` and each verification share are bound to the verified PedPoP transcript rather than trusted from raw bytes.

### Proof of Concept
1. Attacker picks `x` and threshold params `t = n` (e.g., 2-of-2). Computes Lagrange factor `λ_1` for participant 1 over set `{1, 2}`.
2. Sets `verification_shares[1] = G * (x * λ_1^{-1})`, `verification_shares[2] = identity`; sets `secret_share` to any scalar (inconsistency is undetected).
3. Serializes via the `write` format (ID, `t`, `n`, `i = 1`, interpolation byte `1`, `secret_share` repr, both point encodings) and supplies the bytes to the victim's `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574).
4. `read` succeeds; `keys.group_key()` returns `G * x`. Any deposit sent to an address derived from this key is spendable only by the attacker, while the victim's view/signing operations proceed normally against the substituted shares.

Note on residual uncertainty: whether an attacker can realistically deliver a crafted `ThresholdKeys` blob depends on integrator key-loading paths (e.g., node key restore), which live outside the in-scope crates; the cryptographic defect — absence of the share/secret consistency and identity checks in `ThresholdKeys::new` — is present regardless.
