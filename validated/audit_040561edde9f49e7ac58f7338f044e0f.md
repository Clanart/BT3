## Title
Conflict-file path traversal/symlink escape guard is bypassed by the Copilot conflicts overflow menu - (File: app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx)

## Summary
Desktop explicitly treats conflicted-file paths (`file.path` values surfaced from `git status` during a merge/rebase/cherry-pick) as untrusted input that can escape the repository root via symlinks, and guards against it in exactly one place: `buildConflictContext`. The same conflicted-file paths are also handed to the Copilot Conflicts dialog's overflow menu ("Open in External Editor" / "Open with Default Program" / "Reveal in File Manager"), which resolves them with a raw `Path.join` and never applies the guard, silently reintroducing the exact escape the guard was built to close.

## Finding Description
`buildConflictContext` resolves every conflicted file's path with `resolveWithin(workingDirectory, file.path)` specifically to stop a maliciously crafted merge from tricking Desktop into reading a file outside the repository: [1](#0-0) 

The comment is explicit: *"Guard against path traversal and symlink escapes (cross-platform)"*. `resolveWithin` performs a `realpath`-based check, and the project's own tests demonstrate the threat model it defends against — a symlink checked out inside the repo pointing outside of it: [2](#0-1) 

The same untrusted `file.path` values (sourced from `getConflictedFiles(workingDirectory, ...)`, i.e. `git status` for the active merge/rebase/cherry-pick) are passed into `CopilotConflictsDialog`, whose overflow menu handler resolves them with a plain `join`, with no `resolveWithin`/symlink check at all: [3](#0-2) 

`revealInFileManager` — invoked from the same handler with the un-resolved relative path — likewise does a raw `Path.join` with no traversal/symlink check: [4](#0-3) 

The identical unguarded pattern exists for other manual-conflict UI (`unmerged-file.tsx`), confirming this is the general path used for conflicted files everywhere except the one place that was hardened for AI ingestion: [5](#0-4) 

This is the same class of bug as the seed report: a protective invariant (`takerInvariant` / here, `resolveWithin`) is enforced on one entry point that operates on a piece of state, while a second entry point that manipulates/consumes the exact same state has no equivalent check, letting an attacker reach the outcome the guard was meant to prevent.

## Impact Explanation
If a merge/rebase/cherry-pick from an attacker-controlled branch or fork produces a conflicted "file" whose repository-relative path traverses through a symlink (e.g. a tracked symlink component introduced by one side of the merge that points outside the working directory, combined with a type-change/rename conflict on the other side), the resulting `WorkingDirectoryFileChange.path` is shown in the Copilot Conflicts dialog. Clicking the overflow menu's "Open with Default Program", "Open in External Editor", or "Reveal in File Manager" resolves that path with an unguarded `Path.join`, causing Desktop to open/reveal an arbitrary file on the user's disk (e.g. SSH keys, credentials, dotfiles) outside the repository — exactly the escape `buildConflictContext` was written to stop, but reachable via a sibling UI action operating on the same attacker-supplied state.

## Likelihood Explanation
Requires the victim to merge/rebase/cherry-pick a branch containing an attacker-crafted symlink/type-change conflict and to use the Copilot Conflicts dialog's overflow menu on the resulting conflicted entry — no special privileges, no local access, and no unnatural steps beyond normal conflict-resolution workflow with an untrusted branch/PR, matching the "attacker controls a cloned/fetched repository" criterion. It does require that Git's own checkout/merge protections don't independently block the symlink-through-conflict scenario, which is a nontrivial but historically demonstrated attack surface (the app's own `resolveWithin` symlink test exists precisely because this class of escape is real).

## Recommendation
Route every path derived from `WorkingDirectoryFileChange.path` (or any conflicted-file path) through `resolveWithin`/`resolveWithinPosix` before joining with `repository.path`, mirroring the guard already present in `buildConflictContext`. At minimum, apply the same check inside `CopilotConflictsDialog.onOverflowMenuClick` and `revealInFileManager`, and refuse to open/reveal the file (surfacing an error banner instead) when the resolved path falls outside the repository root.

## Proof of Concept
1. Attacker prepares a branch that, when merged with the victim's branch, produces a conflict where one side's tree contains a tracked symlink `evil -> /Users/victim` at a path that collides with a directory/file on the other side (type-change conflict), so the checked-out working tree ends up with `evil` resolving outside the repo while git still reports a path such as `evil/.ssh/id_rsa` as conflicted.
2. Victim fetches/merges this branch in Desktop; the merge produces conflicts and, with Copilot conflict resolution enabled, opens `CopilotConflictsDialog`.
3. Victim clicks the overflow menu (kebab icon) next to the conflicted entry and selects "Reveal in File Manager" or "Open in External Editor".
4. `onOverflowMenuClick` computes `join(repository.path, path)` with no symlink/traversal check and calls `revealInFileManager`/`openFileInExternalEditor`, which follows the symlink and exposes/opens the file at `/Users/victim/.ssh/id_rsa` instead of anything inside the repository — the same input that `buildConflictContext`'s `resolveWithin` would have rejected.
