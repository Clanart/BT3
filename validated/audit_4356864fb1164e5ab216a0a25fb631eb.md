### Title
Premature `writeFn()` Commit Before Post-Condition Check Allows Unrecoverable Approval State on IBC Receive Callback Failure - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`IBCReceivePacketCallback` executes an EVM `approve` call and a destination contract call inside a cached context, then calls `writeFn()` to persist those changes to `ctx` *before* validating that the receiver's ERC20 balance was fully consumed by the callback contract. If the post-check fails, the function returns an error, but the state written by `writeFn()` (notably the `approve` allowance granted to the target contract over the isolated receiver's tokens, and any other contract-visible side effects) has already been committed and is not undone.

### Finding Description
Similar to the trove-manager bug where reward/state changes were computed via `apply_pending_rewards` but the enclosing cancellation path failed to reconcile stakes and the sorted list — leaving inconsistent state — here the function performs `writeFn()` [1](#0-0)  to persist EVM state changes from the cached execution context, and only afterward checks the invariant that the receiver holds zero leftover tokens: [2](#0-1) 

Because the `approve` call to the target contract for the full token amount already occurred and was committed via `writeFn()`, if the target contract does not `transferFrom` the full amount (e.g. it transfers only part, or manipulates its own logic to leave a residual balance while still returning success from its callback logic), the function returns `ErrEVMCall` — causing the outer IBC-Go callback dispatcher to treat this as a failed callback and fall back to default recv-packet behavior (crediting the isolated receiver with the bank/ERC20 tokens directly). However, the `approve` allowance granted to the arbitrary destination `contractAddress` over the isolated receiver's tokens remains live in committed state, since `writeFn()` already merged it into `ctx`.

This leaves an unauthorized standing ERC20 allowance for an attacker-controlled contract to drain the isolated receiver address (which now separately holds the fallback-credited tokens) at any later point, since the ContractKeeper never revokes or zeroes the approval on the failure path.

### Impact Explanation
This falls under "Critical unauthorized ... extraction of user funds ... or token-pair-backed balances." An IBC packet sender fully controls `contractAddress` and `cbData.Calldata` via the packet memo (see `x/ibc/callbacks/README.md`), so an attacker can craft a destination contract that: (1) returns success from the callback's entrypoint without transferring the full approved amount, deliberately triggering the post-check failure; (2) the failed callback causes the middleware to fall back and credit the isolated address with the received tokens per normal ICS-20/erc20 flow; (3) the attacker's contract retains a valid, uncanceled `approve` allowance for the full amount and can later call `transferFrom` to steal the isolated receiver's tokens — funds that the legitimate sender/receiver believed were safely held or auto-converted.

### Likelihood Explanation
Likelihood is high given the trigger requires only crafting an IBC packet with a `dest_callback` memo pointing to an attacker-deployed EVM contract — no privileged access, relayer collusion, or validator control needed. The isolated-address design in `x/ibc/callbacks/README.md` intends to keep funds recoverable/safe if callback logic misbehaves, but this ordering issue undermines that safety guarantee specifically in the failure path.

### Recommendation
Perform the "receiver has unrecoverable tokens" balance check inside `cachedCtx` (before `writeFn()`), or explicitly revoke the `approve` allowance (set allowance to 0) as part of the failure path before returning the error, ensuring no state is persisted to `ctx` when the post-condition invariant fails. Alternatively, snapshot/rollback via `stateDB.RevertToSnapshot`-style handling instead of an unconditional `writeFn()` prior to validation.

### Proof of Concept
1. Attacker submits an IBC transfer packet with `memo.dest_callback` pointing to `MaliciousContract` and includes `calldata` for a benign-looking entrypoint.
2. `MaliciousContract`'s callback entrypoint does not call `transferFrom` for the full `amountInt` (or transfers zero), but otherwise executes successfully (no revert).
3. `IBCReceivePacketCallback` proceeds: `approve` succeeds and is committed via `writeFn()` [3](#0-2) , then the post-check at line 234-239 finds `receiverTokenBalance != 0` and returns an error.
4. IBC-Go callback middleware treats the destination callback as failed and the packet falls through to default recv-packet handling, crediting `isolatedAddr` with the token balance.
5. `MaliciousContract` still holds a live `approve` allowance over `isolatedAddr`'s ERC20 balance (granted in step 3) and calls `transferFrom(isolatedAddr, attacker, amount)` to steal the tokens credited in step 4.

Note: I was unable to fully verify from the indexed code whether `ctx` here is itself a `CacheMultiStore` that gets discarded entirely on error by an outer caller (which would neutralize this issue), since `IBCReceivePacketCallback`'s caller lives in the external `ibc-go` callbacks middleware module (not part of this repo). If the outer IBC-Go `ProcessCallback` wraps `ctx` itself in a cache-and-discard-on-error pattern, this finding would be neutralized; confirming this requires inspecting the `ibc-go` `v10/modules/apps/callbacks` middleware source, which is outside this repository's indexed contents.
