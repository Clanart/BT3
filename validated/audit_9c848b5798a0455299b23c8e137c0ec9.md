### Title
Bandwidth allowance is debited on every retry of an undelivered request, allowing repeated/multiple debits of a single logical message - ([File: parachain/runtimes/gargantua/src/ismp.rs])

### Summary
`pallet-bandwidth` is supposed to move an app's paid byte allowance "exactly once" per delivered message. In practice, `BandwidthGate::try_consume` runs *before* the destination module callback in `ProxyModule::on_accept`, and the ISMP message handler treats a callback failure as retryable (it deletes the request receipt) while still returning `Ok(..)` for the overall batch dispatch. This means the bandwidth debit is never rolled back when the callback fails, and the same never-delivered request can be resubmitted by anyone holding the proof, debiting the allowance again on every attempt.

### Finding Description
In the runtime's ISMP router, the bandwidth gate is consulted and mutated *before* the request is handed to the destination module: [1](#0-0) 

Note the ordering: `try_consume` (a storage mutation that drains bytes from the app's `Allowance` FIFO) runs first, and only afterwards is the request routed to `pallet_ismp_demo`, `pallet_bandwidth`, or `pallet_hyper_fungible_token`'s own `on_accept`. If that inner call returns `Err` (malformed body, decode failure, a paused token contract, mint-cap exceeded, etc.), the error propagates out of `ProxyModule::on_accept` unchanged - nothing un-does the `try_consume` mutation that already happened.

Nexus runtime has the identical pattern: [2](#0-1) 

The generic ISMP request handler treats a failing `on_accept` as a *retryable* condition rather than a terminal one: it deletes the just-stored request receipt so the message is not treated as a duplicate on a future submission, explicitly so it "can be timed out" (i.e., retried or eventually timed out): [3](#0-2) 

Critically, `handle()` collects each request's `Result` into a `Vec` and returns the whole batch as `Ok(MessageResult::Request { events: result, weight })` regardless of whether individual entries failed: [4](#0-3) 

Because the top-level dispatchable extrinsic that invokes this handler returns success, Substrate's default (non-transactional) call semantics commit all storage writes made during that call - including the `Allowance` mutation from `try_consume` - even though the logical request was never actually delivered to the destination module. Since the request receipt was deleted specifically so the message remains re-submittable, any party holding the original proof (this is a permissionless relay operation; delivering an ISMP message requires no special privilege beyond having the proof of the source-chain event) can resubmit the identical request. Each resubmission re-enters `ProxyModule::on_accept`, re-runs `try_consume`, and drains the app's paid bandwidth balance again - for a single logical message that has still never been successfully delivered.

The allowance ledger being drained is real, purchased value: an app buys bytes via `BandwidthManager.purchase()` on the source chain, which credits a `Subscription` in `pallet-bandwidth`'s `Allowance` FIFO: [5](#0-4) 

The design documentation states the gate is meant to be "atomic check-and-deduct" and states explicitly that mutation should only happen on a successful consume ("No mutation happens in this case" for insufficient balance) - but there is no equivalent non-mutation guarantee for the case where consumption succeeds and the *downstream* delivery subsequently fails: [6](#0-5) 

### Impact Explanation
This directly violates the invariant that "bandwidth balances must move exactly once." An app's prepaid, real-money bandwidth subscription can be drained by repeatedly resubmitting the same undelivered proof whenever the destination callback is failing (a paused token contract, a temporarily misconfigured module, or a deliberately malformed body chosen so the callback reliably errors while a retry loop runs). Every resubmission burns real paid-for bytes against the app's ledger without the request ever landing, which is a loss-of-funds condition on a resource that was purchased with on-chain payment (`BandwidthManager.purchase()` pulls ERC-20 from the buyer). Because delivering ISMP messages is a permissionless action (any holder of the source-chain event/proof can submit it to the destination handler), an unprivileged actor - not necessarily a compromised or malicious "trusted" relayer - can trigger this repeatedly.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where `pallet-bandwidth` enforcement is enabled (the `no-bandwidth` feature flag is off): destination module callbacks can fail for many mundane, attacker-reachable reasons (pausing, decode errors on malformed bodies, mint caps), and resubmission of a previously-failed message is an intended, first-class retry mechanism in the protocol (the receipt is deliberately deleted to allow it). No consensus fraud, admin key, or special relayer trust is required - only the ability to resubmit a message whose proof is public.

### Recommendation
Make the bandwidth debit conditional on ultimate delivery, or defer it until after the destination module's `on_accept` succeeds, e.g.:
- Move `BandwidthGate::try_consume` to run only after `cb.on_accept(request)` returns `Ok`, or
- Snapshot/reserve the allowance before dispatch and only finalize the deduction on success, rolling back the reservation if the callback errors, or
- Track a "charged" flag per commitment so a resubmission of the same request commitment cannot debit the gate a second time, mirroring the idempotency pattern already used for reward claims (`OutboundRequestsClaimed`).

### Proof of Concept
1. App `A` purchases a bandwidth tier for `(app_chain, app=A)` via `BandwidthManager.purchase()`; `pallet-bandwidth` credits a `Subscription` with `remaining_bytes = N`.
2. `A` (or anyone) dispatches an ISMP POST request from a source chain to a destination module that is guaranteed to fail `on_accept` - e.g., target `pallet_hyper_fungible_token` while it is paused, or send a body that fails to decode.
3. A relayer submits the message with its proof to the destination handler. `ProxyModule::on_accept` runs `try_consume(source, from=A, bytes)` first, deducting `bytes` from `A`'s subscription, then calls the destination module's `on_accept`, which errors.
4. `modules/ismp/core/src/handlers/request.rs` deletes the request receipt (allowing retry) but the enclosing extrinsic still returns `Ok`, so the `Allowance` mutation from step 3 is committed.
5. Any party resubmits the identical proof/request. Step 3 repeats: another `bytes` are deducted from `A`'s subscription, even though the message has still never been delivered.
6. Repeating step 5 drains `A`'s entire paid allowance without a single successful delivery.

Note: I was not able to inspect the exact body of `BandwidthGate::try_consume`/`impl BandwidthGate for Pallet` in `modules/pallets/bandwidth/src/types.rs` (only its existence was located via grep, not its full source) or the top-level `pallet-ismp` dispatchable that ultimately wraps `handlers::request::handle`, due to running out of tool iterations. These would further confirm (a) that `try_consume` unconditionally writes to `Allowance` before returning `Ok`, and (b) that the enclosing pallet-ismp extrinsic is not wrapped in `#[frame_support::transactional]` at a granularity that would roll back per-message storage on an inner `Err`. Based on the code inspected, the extrinsic-level handler already treats individual message failures as non-fatal (`Ok(MessageResult::Request{..})` with per-message `Result`s inside), which is the load-bearing evidence for this finding; a Devin session with full repository access should verify the `types.rs` implementation and pallet-ismp's outer extrinsic to close this last gap before filing.

```rust
	let result = msg
		.requests
		.into_iter()
		.map(|request| {
			let wrapped_req = Request::Post(request.clone());
			let mut lambda = || {
				let cb = router.module_for_id(request.to.clone())?;
				// Re-check the receipt right before dispatch. The up-front pass above
				// runs before any callback executes; a prior request's on_accept in
				// this same batch could have stored a receipt for this request
				// (directly or by re-entering the handler), and we must not invoke
				// on_accept a second time.
				if host.request_receipt(&wrapped_req).is_some() {
					Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
				}
				// Store request receipt to prevent reentrancy attack
				let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
				let res = cb.on_accept(request.clone()).map(|weight| {
					total_weights.saturating_accrue(weight);

					let commitment = hash_request::<H>(&wrapped_req);
					Event::PostRequestHandled(RequestResponseHandled {
						commitment,
						relayer: signer,
					})
				});
				// Delete receipt if module callback failed so it can be timed out
				if res.is_err() {
					host.delete_request_receipt(&wrapped_req)?;
				}
				Ok(res)
			};

			let res = lambda().and_then(|res| res);
			res
		})
		.collect::<Vec<_>>();

	Ok(MessageResult::Request { events: result, weight: total_weights })
```

```text
## The Gate

Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.

The "no mutation on insufficient" property is load-bearing: it means a top-up race is safe — if a message arrives between when an app notices it's short and when the top-up lands, the message stays rejectable rather than half-consuming the subscription.
```
