## Finding Analysis

The Halborn bug is structurally an **inadequate sufficiency check before subtraction**: the code checked one boundary condition (`timelockedTokens[who] == 0`) but never verified the actual operand relationship needed for the subtraction to succeed, so `balanceOf(who) - timelockedTokens[who]` could underflow and revert, permanently blocking token transfers until an unrelated timer expired. The core broken invariant is: *"a balance-release function checks that a value is non-zero, but not that it is large enough for the subtraction it's about to perform."*

The closest local analog in Hyperbridge is the escrow-release path in the Intent Gateway.

### Title
Missing sufficiency check in escrow withdrawal subtraction can permanently brick settlement of an order - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` releases escrowed order funds and finalizes settlement (marks `_filled`, releases relayer fees, emits `EscrowReleased`/`EscrowRefunded`) in a single atomic loop over `body.tokens`. For each token it does: [1](#0-0) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
```

The guard only checks `escrowed == 0`; it never checks `escrowed >= amount`. Because the contract compiles under Solidity `^0.8.24` (checked arithmetic), if `amount` ever exceeds `escrowed` for any single token index, `escrowed - amount` reverts the entire transaction — including the token transfer that already happened moments earlier in the same call, `_filled[commitment]` marking, and fee release for every other token in the batch. This is the same failure shape as the Halborn finding: a `uint` subtraction with an incomplete precondition check that reverts and denies the legitimate, entitled action, rather than silently wrapping.

The identical unguarded pattern (checking only `_orders[...][token] == 0`, then subtracting) also exists in the Tron variant: [2](#0-1) 

### Finding Description
`_withdraw` is the single settlement chokepoint for both same-chain fills/cancels (`IntrinsicIntents.sol`) and cross-chain fills/cancels (`ExtrinsicIntents.sol`, driven by `RedeemEscrow`/`RefundEscrow` ISMP messages). The `amount` released per token is computed independently, per call site, via proportional/rounding math against `_orders[commitment][token]` (e.g. `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` in the same-chain partial-fill path). The same-chain path (`IntrinsicIntents.sol`) was patched to special-case the *final* fill of a given output leg to release the literal remaining `_orders` balance instead of the rounded proportional value (see the `amountFilled == totalRequired` branch), specifically to avoid leaving dust locked. That fix, however, is local to one call site and does not change the shared, generic guard in `_withdraw` itself, which still only asserts `escrowed != 0` and never asserts `amount <= escrowed`.

Any other call path into `_withdraw` that computes `amount` independently of the exact live `_orders[commitment][token]` value — most importantly the cross-chain settlement path, where the amount to release on the **source** chain is derived from a message assembled on the **destination** chain and delivered later via ISMP — is not guaranteed to respect this invariant. If that computed `amount` ever exceeds the actual escrowed balance on the source chain (due to rounding drift across independently-computed legs, a stale/partial view of `_orders`, or multiple fill/cancel messages targeting the same commitment), `_withdraw` reverts unconditionally.

Because the ISMP request/response backing that release is commitment-bound and, once delivered, typically cannot be re-submitted with a different, correct amount (its content and commitment are fixed by the source event that produced it), a persistent revert here does not just fail one transaction — it can permanently strand the escrowed funds for that order commitment, since there is no code path that lets a user or solver retry the release with a corrected amount once the authenticated message computation is fixed.

### Impact Explanation
If triggered, the affected order's `TokenInfo[]` escrow becomes permanently unreleasable: the settlement transaction that is supposed to pay the solver (fill) or refund the user (cancel/timeout) always reverts, for every token in that request, including tokens whose individual amounts would have been fine. This is a direct fund-lock condition matching the bounty's "stealing or loss of funds" / "logic attacks" category — the beneficiary is entitled to the funds under the protocol's own accounting but is structurally denied access to them.

### Likelihood Explanation
The guard weakness (`escrowed == 0` instead of `escrowed >= amount`) is unconditionally present in the shared `_withdraw`/`withdraw` function, so any caller that computes `amount` even slightly incorrectly relative to live `_orders` state will hit it. The same-chain fill path has been hardened against the one rounding case that was found and fixed (final-leg dust), which is itself evidence that this exact class of bug has already manifested once in this codebase. Whether an *unpatched* trigger currently exists on the cross-chain path (`ExtrinsicIntents.sol`) could not be fully confirmed within the available investigation — this is the main open question that would need direct code review of `ExtrinsicIntents.sol`'s amount computation and the `RedeemEscrow`/`RefundEscrow` message construction on the destination side to establish a concrete input that produces `amount > escrowed` on the source side.

### Recommendation
- Add an explicit sufficiency check in `_withdraw` (and the Tron `withdraw`): `if (amount > escrowed) revert InsufficientEscrow();` before the subtraction, and make callers use `min(computed_amount, escrowed)` where partial/rounded releases are legitimate (mirroring the same-chain final-leg fix already applied).
- Audit every call site that assembles a `WithdrawalRequest.tokens[].amount` cross-chain (destination-computed values later replayed to the source chain) to confirm the amount can never exceed the source chain's live `_orders[commitment][token]`, accounting for message reordering, duplicate delivery, or partial fills interleaved with cancellation.
- Add a recovery path (e.g., an amount-capped/idempotent variant of `_withdraw`) so that if a delivered message's `amount` cannot be honored exactly, the maximum available escrow is still released rather than the whole settlement reverting.

### Proof of Concept
A fully concrete, minimal repro requires confirming a specific cross-chain amount-computation mismatch in `ExtrinsicIntents.sol`, which was not completed before the tool budget was exhausted. The structural PoC pattern, confirmed directly from code, is:

1. An order escrows `E` units of `token` under `commitment` (`_orders[commitment][token] == E`).
2. A withdrawal is triggered (fill completion, or destination-driven `RefundEscrow`) whose `body.tokens[i].amount` is computed by a path independent of the live `_orders` value and evaluates to `A > E` (e.g., due to rounding drift across multiple partial legs, or a stale amount baked into an already-committed cross-chain message).
3. `_withdraw`/`withdraw` passes the `escrowed == 0` check (since `E > 0`) and executes `_orders[commitment][token] = E - A`, which reverts under Solidity 0.8 checked arithmetic.
4. The whole transaction — token transfer, `_filled` marking, and fee payout for every other token in `body.tokens` — reverts. If the message driving this call is one-shot/commitment-bound, this failure repeats on every future attempt, permanently locking the order's escrow. [3](#0-2)
