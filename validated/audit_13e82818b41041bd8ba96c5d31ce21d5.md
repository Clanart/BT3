### Title
`deposit_constant` Computed with Wrong Field in Host vs. Circuit Causes Permanent Proof-Generation Failure and Broken Disprove Verification — (`bridge-circuit-host/src/structs.rs`)

---

### Summary

The `deposit_constant` hash is computed with a different 4th argument in the bridge-circuit guest (zkVM) versus the bridge-circuit host. The guest uses `move_txid` (the move-to-vault transaction ID recovered from the storage proof); the host uses `deposit_value_bytes` (the raw deposit amount). Because `deposit_constant` feeds directly into the committed `journal_hash`, the host's expected journal hash never matches the one the circuit actually commits. This breaks the entire assert/disprove flow for every challenged withdrawal.

---

### Finding Description

**Circuit side** (`circuits-lib/src/bridge_circuit/mod.rs`):

```rust
let (user_wd_outpoint, vout, move_txid) =
    verify_storage_proofs(&input.sp, light_client_circuit_output.l2_state_root);
// ...
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,          // ← move-to-vault txid from storage proof
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
``` [1](#0-0) 

**Host side** (`bridge-circuit-host/src/structs.rs`, `host_deposit_constant`):

```rust
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,   // ← deposit amount (WRONG — should be move_txid)
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
``` [2](#0-1) 

The shared `deposit_constant` function hashes all seven arguments together:

```rust
let pre_deposit_constant = [
    &move_txid,          // ← 4th positional arg
    &watchtower_pubkeys_digest,
    &operator_xonlypk,
    ...
].concat();
DepositConstant(Sha256::digest(&pre_deposit_constant).into())
``` [3](#0-2) 

Because `deposit_value_bytes` (a big-endian BTC amount, e.g. `0x000…05F5E100` for 1 BTC) is structurally unrelated to `move_txid` (a 32-byte SHA-256d hash), the two `deposit_constant` values will always differ.

`deposit_constant` is then fed into `journal_hash`, which is what the circuit commits:

```rust
let journal_hash = journal_hash(
    payout_tx_blockhash, latest_blockhash,
    challenge_sending_watchtowers, deposit_constant,
);
guest.commit(journal_hash.as_bytes());
``` [4](#0-3) 

The host independently recomputes `host_journal_hash()` from `SuccinctBridgeCircuitPublicInputs` (which uses the wrong `deposit_constant`) and checks it against the receipt journal. The function's own doc-comment lists "The journal hash does not match the expected hash" as an explicit error condition: [5](#0-4) 

The wrong `deposit_constant` also propagates into `BridgeCircuitBitvmInputs`, which is what the operator commits on-chain and what the disprove script uses to reconstruct the Groth16 public input:

```rust
BridgeCircuitBitvmInputs {
    ...
    deposit_constant: public_inputs.deposit_constant.0,  // ← wrong value
    combined_method_id: combined_method_id_constant,
}
``` [6](#0-5) 

`calculate_groth16_public_input` and `verify_bridge_circuit` both hash `deposit_constant` into the scalar used for Groth16 verification: [7](#0-6) 

---

### Impact Explanation

Two concrete, mutually-reinforcing impacts:

1. **Proof-generation always fails (liveness / operator-collateral loss).** The host's journal-hash check compares the circuit's committed hash (computed with `move_txid`) against the host's expected hash (computed with `deposit_value_bytes`). They never match. Every call to `generate_bridge_circuit_proof` returns an error. An operator who has fronted a legitimate withdrawal and sent a kickoff transaction cannot produce the assert proof required to claim reimbursement. Their collateral UTXO is permanently locked.

2. **Disprove verification always fails (safety / slashing bypass).** Even if the journal-hash check were bypassed, the `BridgeCircuitBitvmInputs.deposit_constant` stored on-chain is wrong. The disprove script reconstructs the Groth16 public input from these on-chain inputs. Because `deposit_constant` is wrong, the reconstructed scalar differs from the one the proof was generated against, so `ark_groth16::Groth16::verify_proof` returns false for every valid proof. A malicious operator who posts a fraudulent assert cannot be disproved; challengers always lose the disprove game.

---

### Likelihood Explanation

This is triggered on every challenged withdrawal that reaches the assert/disprove stage. No special attacker capability is required — the mismatch is structural and deterministic. Any operator running the production host code against any deposit will hit it.

---

### Recommendation

In `host_deposit_constant` (`bridge-circuit-host/src/structs.rs`), replace `deposit_value_bytes` with the move-to-vault txid recovered from the storage proof, matching the circuit exactly:

```rust
// Recover move_txid from the storage proof (same source as the circuit uses)
let move_txid: [u8; 32] = /* extract from deposit_storage_proof, matching verify_storage_proofs */;

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    move_txid,   // ← corrected
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

Add a test that runs `host_deposit_constant` and the circuit's `deposit_constant` call on the same `BridgeCircuitInput` and asserts they produce identical `DepositConstant` values.

---

### Proof of Concept

1. Operator fronts a withdrawal and sends a kickoff transaction.
2. A challenger challenges; operator must assert.
3. Operator calls `generate_bridge_circuit_proof` with valid `BridgeCircuitInput`.
4. Circuit commits `journal_hash` = `blake3(deposit_constant(…, move_txid, …), …)`.
5. Host computes `host_journal_hash` = `blake3(deposit_constant(…, deposit_value_bytes, …), …)`.
6. `move_txid` ≠ `deposit_value_bytes` → `deposit_constant` values differ → `journal_hash` values differ.
7. Host returns error "journal hash does not match"; proof is never produced.
8. Operator cannot submit assert transactions; collateral is slashed or permanently locked.
9. Alternatively, if the check is skipped: `BridgeCircuitBitvmInputs.deposit_constant` is wrong on-chain; every disprove attempt computes the wrong Groth16 scalar and fails; malicious operator escapes slashing.

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}

    pub fn calculate_groth16_public_input(&self) -> blake3::Hash {
        let concatenated_data = [
            self.payout_tx_block_hash,
            self.latest_block_hash,
            self.challenge_sending_watchtowers,
        ]
        .concat();
        let x = blake3::hash(&concatenated_data);
        let hash_bytes = x.as_bytes();

        let concat_journal = [self.deposit_constant, *hash_bytes].concat();

        let journal_hash = blake3::hash(&concat_journal);

        let hash_bytes = journal_hash.as_bytes();

        let concat_input = [self.combined_method_id, *hash_bytes].concat();

        blake3::hash(&concat_input)
    }

    /// Verifies a bridge circuit Groth16 proof.
    ///
    /// This method verifies that a given Groth16 proof is valid for this bridge circuit
    /// by computing the expected public input and verifying the proof against it.
    ///
    /// # Arguments
    ///
    /// * `proof` - The Groth16 proof to verify
    ///
    /// # Returns
    ///
    /// Returns a `Result` containing `true` if the proof is valid, or an error if verification fails.
    ///
    /// # Errors
    ///
    /// This function will return an error if:
    /// - Proof verification fails
    /// - Public input calculation fails
    /// - Verifying key retrieval fails
    pub fn verify_bridge_circuit(
        &self,
        proof: ark_groth16::Proof<Bn254>,
    ) -> Result<bool, BridgeCircuitHostParamsError> {
        let mut hasher = blake3::Hasher::new();
        hasher.update(&self.payout_tx_block_hash);
        hasher.update(&self.latest_block_hash);
        hasher.update(&self.challenge_sending_watchtowers);
        let x = hasher.finalize();
        let x_bytes: [u8; 32] = x.into();

        let mut hasher = blake3::Hasher::new();
        hasher.update(&self.deposit_constant);
        hasher.update(&x_bytes);
        let y = hasher.finalize();
        let y_bytes: [u8; 32] = y.into();

        let mut hasher = blake3::Hasher::new();
        hasher.update(&self.combined_method_id);
        hasher.update(&y_bytes);
        let public_output = hasher.finalize();

        let public_output_bytes: [u8; 32] = public_output.into();
        let public_input_scalar =
            ark_bn254::Fr::from_be_bytes_mod_order(&public_output_bytes[0..31]);

        let ark_vk = get_ark_verifying_key_prod();
        let ark_pvk = ark_groth16::prepare_verifying_key(&ark_vk);

        ark_groth16::Groth16::<ark_bn254::Bn254>::verify_proof(
            &ark_pvk,
            &proof,
            &[public_input_scalar],
        )
        .map_err(|_| BridgeCircuitHostParamsError::ProofVerificationFailed)
    }
