### Title
App Proxy signed requests never expire, permitting indefinite replay of captured requests - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies only that the HMAC `signature` matches the other query parameters (including `timestamp`). It never checks that `timestamp` is recent, so a signed App Proxy request captured once (e.g. via logs, browser history, a proxy, or network observation) remains valid and acceptable forever, exactly analogous to the ULTI report's missing "deadline not expired" check that let stale parameters be silently accepted.

### Finding Description
`verify_proxy_request` calls `query_string_valid?(request.query_string)`, which:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)
  signature = query_hash.delete("signature")
  return false if signature.nil?
  ActiveSupport::SecurityUtils.secure_compare(
    calculated_signature(query_hash),
    signature,
  )
end
``` [1](#0-0) 

The `timestamp` param is included in the signed data via `calculated_signature`, but that only proves the timestamp value hasn't been tampered with — it does not prove the request is fresh. There is no comparison of `timestamp` against `Time.now` (no equivalent of `block.timestamp > deadline` from the ULTI report). As a result, any previously valid, fully-signed App Proxy URL (query string + signature) can be replayed by an anonymous actor at any point in the future and will still pass verification and reach the controller action. [2](#0-1) 

This is the same bug class as the report: a time-bound parameter (`deadline`/`timestamp`) is transmitted and even cryptographically covered, but its expiry is never enforced, so stale/outdated values are accepted where fresh ones were intended.

### Impact Explanation
An attacker who has captured one legitimately-signed App Proxy request (which can leak via browser history, shared links, server logs, referrer headers, or a compromised network intermediary) can replay it indefinitely against the merchant's app_proxy-backed controller action, even long after the original session/interaction should have expired. Depending on what the app proxy action does (e.g., placing a review, redeeming a promo, modifying app-owned data tied to that shop), this enables state-changing replay by an unrelated/anonymous party. This maps to the "accepted forged/stale signed request" acceptance criterion.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the attacker to first obtain a valid signed URL (not access to the secret itself), which typically requires interception or leakage of a URL that was already generated by Shopify for a legitimate storefront request. This mirrors the report's own low-likelihood/high-impact classification — the flaw is real and reachable, but exploitation requires a captured artifact rather than a from-scratch forgery.

### Recommendation
Add an explicit freshness check on the `timestamp` query parameter in `query_string_valid?`/`verify_proxy_request`, rejecting (returning `false`/`head(:forbidden)`) when `Time.now.to_i - timestamp.to_i` exceeds a small allowed skew (e.g. a few minutes), mirroring the report's recommendation to "revert when `block.timestamp > deadline`."

### Proof of Concept
1. Legitimately trigger an App Proxy request from a storefront; capture the full query string, e.g. `shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-hmac>` (structurally identical to the fixtures used in `test/shopify_app/controller_concerns/app_proxy_verification_test.rb`). [3](#0-2) 
2. Wait an arbitrary amount of time (days/weeks) after `timestamp` has clearly "expired" for any reasonable freshness window.
3. Replay the exact same captured request against the app's `/app_proxy/...` route.
4. `verify_proxy_request` recomputes the HMAC over the same (unchanged) query hash, `secure_compare` succeeds, and the request is processed as if it were current — despite the `timestamp` being stale, exactly as `increaseLiquidity`'s outdated `deadline` was silently accepted in the referenced report.

# frozen_string_literal: true

module ShopifyApp
  module AppProxyVerification
    extend ActiveSupport::Concern
    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_proxy_request
    end

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end
