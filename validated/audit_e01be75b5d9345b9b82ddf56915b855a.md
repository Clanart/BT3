## Title
`git clone` disables Git's CVE-2024-32002 recursive-submodule protection via `GIT_CLONE_PROTECTION_ACTIVE: 'false'` - (File: app/src/lib/git/clone.ts)

### Summary
The Sherlock report's broken invariant is: a security-relevant configuration value is applied without validating that it preserves the safety guarantees the underlying system relies on. In GitHub Desktop, the analogous case is in the `clone()` helper, which explicitly forces the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for every `git clone --recursive` invocation, unconditionally disabling a Git-native safety check with no validation of the repository being cloned.

### Finding Description
`clone()` in `app/src/lib/git/clone.ts` builds the environment for the `git clone` child process as: [1](#0-0) 

Note the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override, combined with `'--recursive'` always being passed to `git clone`. `GIT_CLONE_PROTECTION_ACTIVE` is the environment flag Git itself introduced to guard against CVE-2024-32002 ("git clone --recursive" arbitrary code execution when cloning a malicious repository), where a crafted submodule path can collide case-insensitively (or via unresolved symlinks) with `.git`, causing hook files inside the submodule to be treated as executable hooks in the top-level worktree during the recursive clone/checkout. Git's fix relies on this protection being active during the clone/checkout of nested submodules; by forcing it to `'false'` in the spawned process environment, GitHub Desktop unconditionally strips that protection for every clone it performs, regardless of the trustworthiness of the remote or submodule structure.

This is unvalidated, unconditional weakening of a safety default — directly analogous to `BondBaseSDA.setDefaults` accepting arbitrary values without checking they preserve required invariants (`minDepositInterval <= minMarketDuration`, etc.). Here, the "default" being set (`GIT_CLONE_PROTECTION_ACTIVE=false`) is never validated against the invariant it exists to protect (safe handling of nested `.git` paths in submodules during recursive clone).

### Impact Explanation
An attacker who controls a repository (or a submodule referenced by a repository) that a Desktop user clones — via "Clone repository" URL, "Open in Desktop" deep link, or CLI `github clone <url>` — can supply a crafted submodule whose path collides with `.git` on case-insensitive/case-normalizing filesystems (macOS default, Windows). Because `GIT_CLONE_PROTECTION_ACTIVE` is forced off and `--recursive` is always used, Desktop's clone bypasses Git's own defense, allowing a hook script from the malicious submodule to execute in the context of the outer repository during the clone — i.e., arbitrary code execution on the user's machine triggered purely by cloning an attacker-controlled repository. This matches the "Valid Impact" bar: attacker controls a cloned/fetched repository, result is code execution outside the intended repo boundary.

### Likelihood Explanation
Every code path that results in a clone (manual "Clone repository" dialog, `openOrCloneRepository` triggered from `x-github-client://openRepo/...` deep links, and the `github clone <url>` CLI) funnels through this same `clone()` function with the hardcoded, unconditional override: [2](#0-1) [3](#0-2) 

No user interaction beyond clicking a clone/deep-link is required, and `--recursive` is always forced on, so any submodule contained in the attacker's repository is automatically fetched and checked out. There is no code path in `clone.ts` that re-enables or conditionally sets this protection based on trust level of the source.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override so Git's own protection (added specifically for CVE-2024-32002) remains active during `git clone --recursive`, and audit for the reason this override was introduced (e.g., if it was added to work around a benign warning/error, address that root cause instead of disabling the security check). If disabling is ever necessary for a specific known-safe scenario, gate it behind explicit validation of the source (e.g., only for local, already-vetted paths) rather than applying it unconditionally to all clones, including those from untrusted remote URLs.

### Proof of Concept
1. Attacker publishes a Git repository containing a submodule whose `.gitmodules` path is crafted to collide with `.git` under case-insensitive path resolution (the CVE-2024-32002 pattern), with a malicious hook payload in the submodule.
2. Victim opens a link such as `x-github-client://openRepo/https://github.com/attacker/repo`, which is parsed by `parseAppURL` and routed to `openOrCloneRepository` → `showPopup(PopupType.CloneRepository, { initialURL })`, and the user proceeds with the clone: [4](#0-3) 
3. Desktop calls `clone()` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE: 'false'` set on the child process, disabling Git's own guard against the case-collision/symlink attack: [1](#0-0) 
4. During the recursive submodule checkout, the malicious submodule's hook executes in the outer repository context, achieving code execution on the victim's machine — without the victim doing anything beyond confirming a normal-looking clone.

*Note: I could not execute Git directly to confirm the exact current CVE-2024-32002 collision conditions on this environment, so the exact filesystem-specific trigger (case-insensitive vs. symlink-based collision) should be validated in a sandboxed test, but the code-level fact — that Desktop unconditionally disables the dedicated Git protection variable for every clone — is directly confirmed in `app/src/lib/git/clone.ts`.*
