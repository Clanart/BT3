## Title
`updateRemoteUrl` silently rewrites a repository's git remote to whatever `clone_url` the GitHub API returns, with no host/identity verification beyond a loose hostname/owner/name match - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported bug's broken invariant is: a value that is supposed to come from an authoritative, freshly-verified source is instead accepted at face value and used to make a consequential decision (fund extraction). The GitHub Desktop analog is `updateRemoteUrl`, which is called every time a selected GitHub-backed repository is refreshed [1](#0-0) , and which will silently execute `git remote set-url` against whatever `clone_url` value the GitHub API (or GHES/attacker-controlled endpoint) returns for that repository, as long as a few loose heuristics pass [2](#0-1) .

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository`, which runs `api.fetchRepository(owner, name)` and then immediately calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` before the API response has even been persisted as the new `GitHubRepository` record [3](#0-2) . This refresh path is exercised on ordinary events such as selecting a repository or an account change [4](#0-3) , i.e. it is not a rare/manual operation.

Inside `updateRemoteUrl`, the decision to call `gitStore.setRemoteURL(...)` (which shells out to `git remote set-url`) is gated by three checks:
1. `protocolsMatch` — computed using the legacy, deprecated `URL.parse` API to compare only the *scheme* (`http:`/`https:`) of the current remote vs. the new `clone_url` [5](#0-4) . It does **not** compare host, so `https://github.com/...` and `https://attacker.example/...` are considered "matching protocols."
2. `remoteUrlUnchanged` — checks that the *previous* remote URL still matches the *previously cached* `gitHubRepository.cloneURL` via `urlMatchesRemote`, which itself only compares hostname/owner/name parsed with a permissive regex-based `parseRemote` [6](#0-5) .
3. `!urlsMatch` — the new `clone_url` differs from the current remote.

If all three hold, the function calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` unconditionally and without any user confirmation [7](#0-6) , which executes `git remote set-url origin <apiRepo.clone_url>` [8](#0-7) .

Critically, `apiRepo` is trust-on-first-use data from a GitHub API response (`IAPIRepository.clone_url`), which is attacker-influenceable in several realistic scenarios:
- A GitHub Enterprise Server instance the user is signed into can be malicious/compromised and can return an arbitrary `clone_url` for a `repos/{owner}/{name}` lookup [9](#0-8) .
- A man-in-the-middle/interception proxy scenario is explicitly acknowledged elsewhere in the docs as a risk Desktop already has to account for [10](#0-9) .
- On GitHub.com itself, repository rename/transfer flows change `clone_url` legitimately, meaning the code path is specifically designed to auto-adopt whatever URL the API supplies, without additional integrity checks tying it back to a specific repository ID or checking that the new host is one the user has an authenticated relationship with.

This means the exact corrupted value is the local git remote URL for `origin` — the destination that all subsequent `git fetch`/`git pull`/`git push` operations target — and it is corrupted silently, with no dialog, warning, or diff shown to the user.

### Impact Explanation
If an attacker can influence the `clone_url` returned for a repository the user has open in Desktop (malicious/compromised GHES server, or any other means of injecting a crafted API response for a repo the user already trusts), Desktop will automatically rewrite the user's `origin` remote to point at the attacker's host as soon as the repository is refreshed (e.g., simply switching back to that repository tab). All future fetches/pulls will pull code from the attacker's server, and any future push will silently send the user's commits/credentials-bearing HTTPS requests to the attacker's endpoint instead of GitHub — matching the "git remote/proxy response... silent corruption of what the user commits or pushes" and "credential exfiltration" categories in the given valid-impact criteria, since Desktop will also present the attacker's host with the user's stored git credential helper output during the next push.

### Likelihood Explanation
The refresh path is triggered routinely (selecting a repository, account refresh) rather than requiring any unusual user action [4](#0-3) . The only barrier is that the current remote's protocol scheme must match and that the previously-stored `cloneURL` matched the existing remote — both of which are satisfied in the common case (user is on `https://` and hasn't manually diverged their remote from what the GitHub API previously reported). No host-identity check, TLS/host pinning, or user confirmation exists to stop the swap once those loose conditions are met. This is a realistic, code-only path relying on an attacker-controlled/compromised GitHub API endpoint response object — one of the explicitly valid attacker primitives.

### Recommendation
- Before silently rewriting `origin`, verify the new `clone_url`'s hostname matches the current remote's/endpoint's expected host (or explicitly prompt the user when the host changes), rather than only checking that the protocol scheme string matches.
- Replace the legacy `URL.parse` usage with the WHATWG `URL` API and compare `hostname` in addition to `protocol`.
- Consider requiring explicit user confirmation (a dialog similar to `InvalidatedToken`) whenever the remote URL is about to change host, especially for repositories associated with GitHub Enterprise Server endpoints.
- Tie the update to a stable repository identifier (e.g., the numeric GitHub repository ID) rather than trusting `clone_url`/owner+name matching alone, so a same-named but attacker-controlled repository cannot spoof the match.

### Proof of Concept
1. User has repository R cloned locally with `origin` pointing at `https://ghe.example.com/org/repo` (a GHES endpoint they are signed into).
2. Attacker compromises (or MITMs) `ghe.example.com`'s API and, when Desktop calls `GET repos/org/repo` via `fetchRepository`, returns a JSON body identical to the legitimate one except `clone_url: "https://attacker.example.com/org/repo"` [9](#0-8) .
3. User simply reselects the repository in Desktop (or Desktop performs its normal periodic/account-change refresh), triggering `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` [1](#0-0) .
4. `protocolsMatch` is true (`https:` === `https:`), `remoteUrlUnchanged` is true (previous cached `cloneURL` still matches current remote), and `urlsMatch` is false (new URL differs) — so `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo')` executes without any prompt [2](#0-1) .
5. The existing unit tests confirm this exact "URL changes → remote auto-updates" behavior is by design [11](#0-10) , with the only safeguards being the coarse protocol/hostname-and-owner-name heuristics shown above — none of which distinguish a legitimate GitHub-initiated rename from an attacker-supplied URL for the same nominal owner/repo pair on a different host that still round-trips the same protocol string.

  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // clone url retrieved from the GitHub API previously

    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

```markdown
## Windows caveats for MITM proxies

Some Enterprises and organizations use "regular" proxies which only forwards traffic but doesn't actively inspect it. Some, however, use what's commonly referred to as man-in-the-middle proxies, snooping proxies, or https intercepting proxies.

These proxies issue fake ssl certificates when clients make request to https sites and rely on the clients trusting their "fake" certificate authority certificate. See [MITM-proxies](https://ec.haxx.se/usingcurl/usingcurl-proxies#mitm-proxies) in the cURL documentation for a better explanation.

When these snooping proxy servers issue their fake certificate they rarely include any certificate revocation list details. In other words they're not telling the clients who they should contact to see if a particular certificate has been revoked. This is called Certificate Revocation List Distribution Points or CRL DP. The lack of distribution points in a certificate is normally ignored by http(s) clients and that's the case for Git on macOS and linux. On Windows however there's two SSL backends to choose from; `openssl` and `schannel`. OpenSSL is a cross-platform SSL/TLS implementation whereas `schannel` uses the built-in SSL/TLS subsystem in Windows.

Unfortunately the `schannel` backend in cURL throws an error when failing to check for certificate revocation. We've seen this error [so many times](https://github.com/desktop/desktop/issues/3326) that it's made our "known issues" document. To combat this a new configuration option (`http.schannelCheckRevoke`) was added to Git which lets users disable certificate revocation checks entirely. This certainly isn't ideal and we'd like to see a solution to allow best effort certificate revocation checks which always attempts to check for revocation but doesn't throw an error if it fails to do so (see the Future improvements section below).

For now though this is our only workaround and as such [#9188](https://github.com/desktop/desktop/pull/9188) was introduced which detects this specific error and allow the user to disable revocation checks. **Note: the toggle to turn this setting on or off in the options dialog is hidden unless this condition has been encountered before**
```
