### Title
Commit-review hook's reflog-fallback freshness check uses attacker-controlled git commit timestamps instead of wall-clock time, allowing malicious commits to evade async security review - ([File: plugins/security-guidance/hooks/gitutil.py])

### Summary
`_git_reflog_recent_commits`, used by the `commit-review` PostToolUse hook as a fallback when a `git commit`'s stdout is hidden (`-q`, pipes, redirection), decides whether a reflog entry is "fresh" (and therefore reviewable) by comparing `now = int(time.time())` (the hook's wall clock) against `ct`, the git commit's own `%ct` committer timestamp — a value fully controllable by whoever runs the `git commit` command via `--date`/`GIT_COMMITTER_DATE`. This mirrors the H-1 root cause: two different timestamp domains (one taken from an independent, "real" clock, the other from a value the initiating action controls) are compared/matched for the same logical event, and a mismatch invalidates the lookup instead of the intended check.

### Finding Description
The commit-review flow works as follows: on `Bash(git commit:*)`, `handle_commit_review_posttooluse` first tries to parse the `[branch sha]` line from the command's captured stdout/stderr [1](#0-0) . If that fails (output suppressed with `-q`, piped, or redirected) it falls back to `_git_reflog_recent_commits`, which walks the last `max_n` reflog entries and classifies each as "fresh" or "stale" using an age gate: [2](#0-1) 

The exemption for `idx == 0` was deliberately added so the most recent commit is always caught regardless of its timestamp, but every earlier entry in the scanned window (`idx >= 1`, up to `max_n - 1 = 4`) is gated purely by `now - ct <= max_age_s (120s)`, where `ct` is the git commit's own recorded time — a value the command that created the commit fully controls (`git commit --date=... `, `GIT_COMMITTER_DATE=...`, or a manipulated system clock at commit time). Only `fresh` entries are eligible for security review (`shas = fresh not already in reviewed set`) [3](#0-2) [4](#0-3) .

An attacker (or a prompt-injected/compromised skill causing the agent to run bash) who chains three or more quiet commits in one `Bash` call, e.g.:
```
git commit -q -m "a" && git commit -q -m "malicious payload" --date="2000-01-01T00:00:00" && git commit -q -m "c"
```
produces a reflog where the malicious commit lands at `idx=1` with an artificially old `%ct`. Because only `idx==0` is exempt, `age = now - ct` for the malicious commit is enormous, it is classified `stale`, and it is silently dropped from the `fresh` list — never reaching `git show`/`analyze_code_security` for review, while the surrounding decoy commits (`idx=0`, `idx=2`) are reviewed normally, making the omission inconspicuous.

### Impact Explanation
This is a direct hook-bypass of the security-guidance plugin's core protection: the async commit-review hook is meant to scan every new commit's diff for injected vulnerabilities (secrets, backdoors, command injection, etc.) and force the model to address findings via `sys.exit(2)`. An attacker can smuggle a malicious commit past this control entirely by controlling its committer timestamp, defeating the intended "review every commit" guarantee without needing any special privilege beyond being able to influence a `Bash` command (e.g., via prompt injection content that gets executed).

### Likelihood Explanation
The reflog fallback path only activates when stdout is fully suppressed for the git commit invocation(s) (`-q`, redirection, or piping) — a common and unremarkable pattern that doesn't itself look suspicious. Setting `--date` on a `git commit` is a standard, unprivileged git feature. Chaining 3+ commits in a single tool call is also unremarkable. No special access or race condition is required, only that stdout-based detection fails for the whole chain, which the attacker fully controls by simply appending `-q`.

### Recommendation
Do not use the git commit's self-reported `%ct` as the freshness signal for anything beyond `idx==0`. Instead, either exempt all entries produced within the current Bash invocation's chain (e.g., by counting `git commit` occurrences in the command string and treating that many leading reflog entries as fresh regardless of `%ct`), or use a timestamp source outside the attacker's control (e.g., the reflog entry's own recording time, or `git reflog` selector timestamps) rather than the commit object's author/committer time, to determine freshness.

### Proof of Concept
1. In a git repo with the security-guidance plugin's commit-review hook enabled, have Claude execute a single Bash call:
   ```
   git commit -q -m "benign 1" && \
   git commit -q -m "INTRODUCE_BACKDOOR" --date="2000-01-01T00:00:00" && \
   git commit -q -m "benign 2"
   ```
2. Because all three commits use `-q`, `_COMMIT_SHA_RE` finds no `[branch sha]` line in Bash's stdout, so `commit_succeeded` is `False` and `_git_reflog_recent_commits` is invoked [5](#0-4) .
3. In the reflog scan, `idx=0` ("benign 2", fresh timestamp) and `idx=2` ("benign 1", fresh timestamp) pass the age check trivially; `idx=1` ("INTRODUCE_BACKDOOR", `%ct` = year 2000) fails `age <= max_age_s` and is added to `stale` instead of `fresh` [6](#0-5) .
4. `shas = _reflog_shas` therefore contains only the two benign commits; `git show -p` is run only on those, and `analyze_code_security` never sees the diff introducing the backdoor commit, so no findings are raised and the model is never blocked [7](#0-6) .

    import time as _time
    now = int(_time.time())
    fresh, stale = [], 0
    for idx, line in enumerate(r.stdout.splitlines()):
        parts = line.split("|", 2)
        if len(parts) != 3:
            continue
        sha, ct, subject = parts
        # `commit: msg`, `commit (amend): msg`, `commit (initial): msg`,
        # `commit (merge): msg` — all create a reviewable commit object.
        if not subject.startswith("commit"):
            continue
        try:
            age = now - int(ct)
        except ValueError:
            continue
        # HEAD@{0} (idx==0) is exempt from the age gate. The gate exists to
        # bound the WIDENED HEAD@{1..max_n-1} scan from picking up commits
        # made by *prior* Bash calls; HEAD@{0} is by definition the most
        # recent reflog entry and was previously accepted unconditionally
        # (_git_reflog_head_if_just_committed previously had no age check).
        # Applying max_age_s to idx==0 made the not-yet-visible-HEAD skip
        # noticeably more frequent on chained
        # `git commit && <slow command>` where %ct is >120s old by the
        # time the async PostToolUse hook fires.
        if idx == 0 or age <= max_age_s:
            fresh.append(sha)
        else:
            stale += 1
    return fresh, stale
