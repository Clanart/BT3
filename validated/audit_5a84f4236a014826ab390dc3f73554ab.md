Found the analog. `is_atom_canonical()` in `chia/full_node/mempool_manager.py` indexes into an attacker-controlled `bytes` buffer without bounds checking, exactly mirroring the Wire `skipGroup()` root cause: a length/prefix field is trusted and used to index/advance through a buffer without validating that the computed offsets stay within bounds, so a crafted length can drive an out-of-range index access that raises an unchecked `IndexError` instead of the expected, caught validation error.

### Title
Unbounded buffer indexing in `is_atom_canonical()` lets a crafted puzzle/solution atom header crash mempool spend-bundle validation - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` reads a CLVM atom's multi-byte length-prefix header by indexing directly into `clvm_buffer[offset]` for `prefix_len` additional bytes without ever checking that `offset` stays within `len(clvm_buffer)`. [1](#0-0)  This is called from `is_clvm_canonical()`, which loops over the buffer walking these atom headers, and is invoked directly against attacker-supplied `coin_spend.puzzle_reveal` / `coin_spend.solution` bytes during spend-bundle admission in `validate_spend_bundle()`. [2](#0-1) 

### Finding Description
`validate_spend_bundle()` runs `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` and `is_clvm_canonical(bytes(coin_spend.solution))` for every coin spend in a submitted `SpendBundle`, and treats a `False` result as `Err.INVALID_COIN_SOLUTION` (a normal, caught rejection path). [2](#0-1) 

`is_clvm_canonical()` walks the raw serialized bytes token by token. When it encounters an atom header byte greater than `0x80`, it calls `is_atom_canonical(clvm_buffer, offset)` to compute the atom's declared length and advances `offset` by the returned amount. [3](#0-2) 

Inside `is_atom_canonical()`, the function determines `prefix_len` (0–5 extra bytes) from the high bits of the header byte, then loops `prefix_len` times reading `clvm_buffer[offset]` while incrementing `offset`, with **no bounds check** against `len(clvm_buffer)`: [4](#0-3) 

This is the same bug class as the Wire advisory: a length/discriminant byte controls how many further bytes are consumed from the buffer, and the consuming code trusts that value without validating it fits in the remaining data, so out-of-range access throws an unchecked exception (`IndexError`) rather than a documented/handled error. In Wire's case it was `skip(negative_length)` underflowing a position counter; here it's a multi-byte length-prefix header whose `prefix_len` byte-reads can walk `offset` past the end of `clvm_buffer` if the buffer ends immediately after (or within) a partial multi-byte atom-length header — e.g. a puzzle reveal or solution that ends with a byte like `0xFC` (declaring a 5-byte extended length prefix) but supplies fewer than 5 trailing bytes.

`is_clvm_canonical()` itself also indexes `clvm_buffer[offset]` in its main loop without an explicit remaining-length check before dereferencing, and only validates full-buffer consumption (`offset == len(clvm_buffer)`) at the very end, after the walk already completed. [5](#0-4) 

### Impact Explanation
`validate_spend_bundle()` is executed for every spend bundle in `add_spend_bundle()`, which is the core mempool admission path reachable by any peer or RPC caller submitting a transaction. [6](#0-5)  An unhandled `IndexError` raised from `is_atom_canonical()`/`is_clvm_canonical()` during this call is not one of the documented/handled `Err` values that `add_spend_bundle()` expects from `validate_spend_bundle()`; it would propagate as an unexpected exception out of the mempool add path. Depending on how the call site surrounding mempool add is wrapped (RPC handler, gossip handler, block-building loop), this can crash or destabilize the full node's transaction-processing task from a single malicious/malformed spend bundle — a spend-triggered transaction-processing halt, which is one of the explicitly accepted impact categories.

### Likelihood Explanation
High likelihood of reachability: any unprivileged party who can submit a spend bundle (via RPC `push_tx`, wallet, or gossip) controls the exact bytes of `puzzle_reveal` and `solution`, and `is_clvm_canonical()` is called unconditionally on both for every coin spend before signature/cost validation. Constructing a serialized program whose last atom header byte is one of the multi-byte length prefix markers (e.g. `0xC0`–`0xFC` range) with insufficient trailing bytes is a simple, deterministic way to drive `offset` out of bounds — directly analogous to the 10-byte crafted payload in the Wire advisory.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (both the initial `clvm_buffer[offset]` and the `prefix_len` loop reads), raising/returning a handled "not canonical" or malformed-input result instead of letting `IndexError` escape. Apply the same check in `is_clvm_canonical()`'s main loop before dereferencing `clvm_buffer[offset]`, so a truncated/malformed buffer results in a controlled rejection (e.g. treated as non-canonical / `INVALID_COIN_SOLUTION`) rather than an unhandled exception.

### Proof of Concept
Construct a `CoinSpend` whose `solution` (or `puzzle_reveal`) serialized bytes end with a truncated multi-byte atom length header, e.g.:
```
solution_hex = "fc"          # 0xFC declares a 5-byte extended length prefix
                              # but 0 trailing bytes are supplied
```
Submitting a `SpendBundle` containing a `CoinSpend` with this `solution` via `push_tx`/RPC causes `validate_spend_bundle()` to call `is_clvm_canonical(bytes(coin_spend.solution))`, which calls `is_atom_canonical(clvm_buffer, offset)` on the final byte; the `for i in range(prefix_len)` loop then attempts `clvm_buffer[offset]` past the end of the (length-1) buffer, raising an unhandled `IndexError` instead of being caught as `Err.INVALID_COIN_SOLUTION`. This mirrors the Wire PoC's approach of embedding a malformed length field that the skip/read logic trusts without bounds validation. [1](#0-0) [2](#0-1)

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
