Based on my research, I found the strongest local analog in the same-chain intent-fill escrow release logic, which mirrors the external report's core defect pattern: an amount is read/removed using a key that does not uniquely correspond to the specific unit being finalized, letting the wrong (in this case, aggregated) value be pulled out.

### Title
Escrow over-release on full-leg completion when an order's `inputs` share a token across multiple output legs - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` releases input escrow keyed by `order.inputs[i].token` using the **whole** `_orders[commitment][token]` balance whenever leg `i` reaches `amountFilled == totalRequired`, instead of the amount escrowed specifically for leg `i`. Because `_orders[commitment][token]` aggregates escrow by token across the *entire* order (as documented in `IntentsBase.sol`), any order whose `inputs` array references the same token at more than one index lets a filler fully complete one output leg and, in doing so, drain the combined escrow meant to back every other leg that shares that token — while only paying the solver-side cost for the single leg they completed.

### Finding Description
`_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:116-122`) computes the escrow amount to withdraw for leg `i` as: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

`_orders[commitment][token]` is a per-`(commitment, token)` balance, not per output-leg index — it is documented as "the escrowed amount for that token" aggregated across the whole order: [2](#0-1) 

When leg `i` finishes (`amountFilled == totalRequired` for that leg only), the code assumes the *entire* remaining balance under `order.inputs[i].token` belongs exclusively to leg `i`. If a second leg `j != i` in the same order also uses `order.inputs[j].token == order.inputs[i].token` (nothing in `_fillSameChain`, `_withdraw`, or the escrow bookkeeping enforces distinct tokens per input index), then completing leg `i` first pulls the combined escrow for both legs into a single withdrawal, and `_withdraw` unconditionally decrements the shared balance to (near) zero: [3](#0-2) 

Leg `j`, when later completed, is left with an emptied or reduced `_orders[commitment][token]` and receives nothing (or a truncated amount) for its own genuine input contribution, while the filler who closed leg `i` already collected the aggregate.

### Impact Explanation
An unprivileged filler who is the first to complete any leg sharing a token receives escrow that was meant to also cover other unfilled legs of the same order, at no extra cost beyond the amount required to satisfy that single leg's output. This is a direct "wrong beneficiary or amount" / fund-loss condition on bridge-adjacent order settlement: the filler is overpaid relative to what they delivered, and the remaining, rightful escrow entitlement for other legs of the same order is drained or reduced to zero, effectively stealing value from the order (ultimately the user who escrowed the funds, or any other filler attempting to complete the remaining legs).

### Likelihood Explanation
Nothing in `placeOrder`/`_fillSameChain`/`_orders` bookkeeping (as reviewed) enforces that `order.inputs[]` cannot repeat the same token at multiple indices, and a filler fully controls how it sequences its `options.outputs[i].amount` per call, i.e., it can choose to complete the token-sharing leg first. This makes the path reachable by any solver with no special privileges, given an order (created by any user) that has repeated input tokens across legs. I was not able to further verify with 100% certainty (no more tool calls available) whether `placeOrder` elsewhere enforces uniqueness of `order.inputs[].token`; if such a constraint exists it would eliminate this path, so this should be validated against the full `placeOrder` implementation before treating this as confirmed.

### Recommendation
Track escrow per `(commitment, inputIndex)` (or per `(commitment, outputIndex)`) rather than aggregating purely by token, or explicitly compute the leg's proportional share of `_orders[commitment][token]` even on the "amountFilled == totalRequired" branch (e.g., cap release to `order.inputs[i].amount` minus what has already been released for that specific index), so that one leg's completion can never consume escrow belonging to a different leg that merely happens to reference the same token.

### Proof of Concept
1. User places an order where `order.inputs = [ {token: X, amount: 100}, {token: X, amount: 50} ]` and `order.output.assets = [ {token: A, amount: 100}, {token: B, amount: 50} ]` (two legs sharing input token `X`, escrowing `150` of `X` total under `_orders[commitment][X]`).
2. A filler calls fill with `options.outputs[0].amount = 100` (fully satisfying leg 0) and `options.outputs[1].amount = 0` (skip leg 1).
3. In `_fillSameChain`, leg 0 hits `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][X]` reads `150` (the full combined balance) instead of `100`.
4. `_withdraw` sends all `150` of `X` to the filler and sets `_orders[commitment][X] = 0`.
5. When leg 1 is later filled, its proportional/`amountFilled==totalRequired` computation reads `_orders[commitment][X] == 0`, so the second output's rightful `50` of `X` is unavailable — the first filler captured escrow that should have backed leg 1.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
