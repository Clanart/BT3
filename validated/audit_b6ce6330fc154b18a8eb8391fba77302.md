### Title
Copilot conflict resolution trusts model-reassembled file content and PR-sourced prompt context without verifying the result against the actual conflict structure before writing/staging it - (File: app/src/lib/copilot-conflict-resolution.ts, app/src/lib/stores/app-store.ts)

### Summary
The C4 finding's broken invariant is: *"the code assumes an externally-controlled operation (`transferFrom`) produced exactly the requested effect, and never checks the actual resulting state before trusting/using it."* The GitHub Desktop analog is in the Copilot merge-conflict-resolution feature: the app feeds attacker-influenceable data (PR titles/bodies gathered from the GitHub API, see `appendPullRequest`) into an LLM prompt, receives back a JSON payload of per-hunk `resolvedContent` strings, splices them into the on-disk file via `reassembleResolvedFile`, and then writes that result straight to the working tree and stages it with `git add` — all without validating that the reassembled output is actually a correct, marker-free, hunk-count-matching resolution of the real conflict.

### Finding Description
- PR bodies are attacker-controlled: any user who can open a pull request against a public/forked repo controls `pr.body`/`pr.title`, which is embedded verbatim (fenced, but not neutralized as instructions) into the prompt sent to the model. [1](#0-0) 
- The system prompt instructs the model to return `hunks` "matching the Conflict 1 of N... order from the input," but nothing in `reassembleResolutions`/`reassembleResolvedFile` verifies that the model actually returned the same number of hunks as conflict markers found in the file, nor that no conflict markers remain after splicing. [2](#0-1) 
- `reassembleResolvedFile` walks the raw file and splices `hunkResolutions[hunkIndex]` in purely by *position*, with no cross-check against the actual number of well-formed conflict blocks it found versus `hunkResolutions.length`; if the model returns fewer hunks than actual conflicts, remaining conflicts are simply left as-is silently (hunkIndex advances past the array bound and `hunkIndex < hunkResolutions.length` becomes false for the rest of the file), and if it returns extra/misordered hunks, wrong content is spliced into unrelated conflict blocks. [3](#0-2) 
- The reassembled `resolvedContent` — model output — is written directly to the file and staged for commit, with the only integrity check being a path-traversal guard (`resolveWithin`) and a check that a user hasn't independently resolved the file already. There is no diff/verification of the *content correctness* (e.g., no re-check that the write actually resulted in a conflict-marker-free file matching the model's intended hunks) before `git add` stages it. [4](#0-3) 
- `validateResolutionPaths` (referenced in `copilot-store.ts`) validates that returned *paths* match `expectedFiles`, but this only guards path identity, not hunk-count/content correctness of the reassembly. [5](#0-4) 

This is the direct structural analog of the C4 bug: just as the pool contract trusted `amount` (the value asked for) instead of checking the actual balance delta, Desktop trusts the model's `hunks` array to correctly and completely represent "conflict 1..N" instead of verifying the reassembled file's actual conflict-marker state (i.e., checking the "balance" — remaining conflict markers / hunk count — before and after the splice).

### Impact Explanation
If a malicious PR author crafts a PR body designed to manipulate the model's per-hunk resolution (prompt injection) into omitting hunks, misordering them, or returning content that silently drops one side's changes, `reassembleResolvedFile` will silently produce a corrupted file — potentially leaving a subset of the *other* conflicts unresolved-but-undetected as markers, or splicing wrong content into an unrelated hunk — which is then written to disk and `git add`ed for commit. This matches the "silent corruption of what the user commits" impact category: the victim reviews a shortened/incorrect diff or summary, accepts, and commits/pushes code that does not match the actual merge intent, without git or Desktop's own guards ever detecting the mismatch between "hunks expected" and "hunks supplied."

### Likelihood Explanation
This requires only that the attacker can put content into a PR title/body or commit message that later becomes part of a merge conflict context reviewed with Copilot — no local access, no credentials, no malware, and no unnatural user steps beyond a normal "resolve conflicts with Copilot" click, which is an explicit built-in feature of the app. The likelihood of a *successful* prompt injection depends on model behavior (outside this codebase's control), but the code itself does nothing to detect or reject a hunk-count mismatch or residual conflict markers even in obviously malformed cases, so there is no code-level backstop once the model is influenced.

### Recommendation
In `reassembleResolvedFile` / `reassembleResolutions`, assert that the number of detected well-formed conflict blocks in the raw file equals `hunkResolutions.length` for that file, and fail (or fall back to a skipped/manual-resolution path) rather than silently truncating/misaligning splices. After reassembly, verify the resulting content contains no residual `<<<<<<<`/`=======`/`>>>>>>>` markers before it is ever written to disk or staged, mirroring how the balance-based mitigation in the report checks the *actual resulting state* rather than trusting the claimed amount.

### Proof of Concept
1. Attacker opens a PR (or crafts commit messages) with a body containing prompt-injection text instructing the model to return fewer `hunks` entries than actual conflicts in a targeted file, or to reorder them. [6](#0-5) 
2. Victim merges/rebases and clicks "Resolve with Copilot"; `gatherConflictResolutionContext` includes the attacker's PR body in the prompt sent via `formatConflictContextForPrompt`. [7](#0-6) 
3. Model returns a JSON payload with a `hunks` array shorter than the actual conflict count (nothing in the parser/validator rejects this) — see `parseCopilotConflictResolution` only checking that `resolutions` is a non-empty array, not per-file hunk-count correctness. [8](#0-7) 
4. `reassembleResolvedFile` splices available hunks by position; any conflict blocks beyond the supplied hunk count are passed through with an out-of-range `hunkIndex`, and `hunkIndex < hunkResolutions.length` guards silently skip inserting content for the "missing" resolutions rather than raising an error. [9](#0-8) 
5. The resulting content is written and staged without further correctness checks. [10](#0-9) 

Note: I was not able to fully inspect `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx` (106 matches, not read in depth) to confirm exactly how much per-hunk diff review the UI forces before "accept," so the precise degree of user visibility into a truncated/misaligned resolution before commit is uncertain — a Devin session with full file access would be needed to confirm whether the review UI would visibly expose a hunk-count mismatch to the user before they accept.

function appendPullRequest(
  parts: Array<string>,
  pr: IConflictContextPullRequest
): void {
  parts.push(`PR #${pr.number}: ${pr.title}`)
  if (pr.body) {
    parts.push('Description:')
    parts.push(makeFencedBlock(truncateBody(pr.body)))
  }
  parts.push('')
}

/** Truncate an over-long PR body so a single PR can't dominate the prompt. */
function truncateBody(body: string): string {
  if (body.length <= MAX_PR_BODY_LENGTH) {
    return body
  }
  return `${body.slice(0, MAX_PR_BODY_LENGTH)}\n…(truncated)`
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }
