### Title
Unbounded, unbatched `PlotNFT2Wallet.claim_rewards()` can grow past mempool/block cost limits, permanently stranding accumulated pool rewards - (File: `chia/wallet/plotnft_wallet/plotnft_wallet.py`)

### Summary
`PlotNFT2Wallet.claim_rewards()` fetches *every* unclaimed pool-reward coin for a PlotNFT singleton and builds a single `SpendBundle` that spends the singleton once while chaining an `AssertCoinAnnouncement`/reward-forwarding spend for each individual reward coin, with no batching or cap on the number of rewards processed at once. This mirrors the reported StakeDAO pattern where a user-specific "claim from last-checkpoint to now" loop has no upper bound and can grow large enough to make the resulting transaction unsubmittable, permanently trapping the user's rewards in the contract/coin set.

### Finding Description
`claim_rewards()` reads all outstanding reward coins with `self.wallet_state_manager.plotnft2_store.get_pool_rewards(plotnft_id=self.plotnft_id)` and, without any size limit, builds one `coin_spend` per reward coin via `plotnft.claim_pool_rewards(...)`, chaining them together with `AssertCoinAnnouncement`/`CreateCoinAnnouncement` conditions so they must all be spent atomically in the same bundle: [1](#0-0) 

Compare this to the *old* `PoolWallet.claim_pool_rewards()`, which explicitly caps the number of absorb spends per transaction via `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS` specifically "so the SpendBundle fits into the block": [2](#0-1) [3](#0-2) 

`PlotNFT2Wallet.claim_rewards()` has no equivalent `max_spends_in_tx`/batching parameter. If a PlotNFT owner is inactive for a long time (or is a large self-pooling/pooling farmer whose plots keep winning blocks, or a low-value farmer whose reward coins simply accumulate over months/years), `rewards_to_claim` can grow to hundreds or thousands of coins. Because all of these reward-coin spends and the singleton spend must be included in one `WalletSpendBundle` (they are chained together with coin announcements so they are only valid together), the resulting bundle's CLVM execution cost and total spend count scale linearly with the number of unclaimed rewards. This directly analogizes the SdtStakingPositionService `claimCvgRewards()` bug: a per-position "claim everything since last time" loop with no incremental/batched checkpointing, which becomes unexecutable once enough cycles/coins accumulate.

The `pw_absorb_rewards` RPC is the reachable entry point for any wallet owner, dispatching to `PlotNFT2Wallet.claim_rewards` for PLOTNFT_2 wallets: [4](#0-3) 

Chia's mempool/block enforce hard CLVM cost and spend-count ceilings that a single spend bundle cannot exceed (`max_tx_clvm_cost` is half of `MAX_BLOCK_COST_CLVM`, and `MAX_SPENDS_PER_BLOCK` bounds spends per block): [5](#0-4) 

Once the number of pending reward coins for a single PlotNFT singleton grows large enough that the resulting `claim_rewards()` bundle's cost or spend count would exceed `max_tx_clvm_cost` or `MAX_SPENDS_PER_BLOCK`, the mempool will reject the spend bundle outright (`cost > max_tx_clvm_cost` → reject), and there is no code path in `PlotNFT2Wallet` to claim only a subset of the accumulated rewards, unlike the legacy `PoolWallet` implementation.

### Impact Explanation
This is a Medium-severity, user-fund-availability issue rather than a theft/inflation bug: reward coins remain on-chain and are not destroyed, but they can become practically unclaimable by the singleton owner using the wallet's only claim code path, because `claim_rewards()` always attempts to sweep *all* outstanding rewards in one atomic bundle and there is no way to instruct it to claim a bounded subset. This can indefinitely lock a legitimate user's farming/pooling rewards behind an unsubmittable transaction, matching the "rewards may become locked in the contract" impact class from the source report (locked funds due to an unbounded, un-batchable claim operation).

### Likelihood Explanation
Likelihood is limited by how many reward coins must accumulate before the bundle becomes too large to fit the mempool/block cost and spend-count limits — this requires either very long inactivity or an unusually prolific self-pooling/pooling PlotNFT accumulating many separate reward coins without ever calling `pw_absorb_rewards`. It does not require any adversarial input; the affected user's own inaction is sufficient to trigger it, and no privileged access or malicious peer/network behavior is needed to reach the vulnerable code path (`pw_absorb_rewards` → `PlotNFT2Wallet.claim_rewards`).

### Recommendation
Add a batching mechanism to `PlotNFT2Wallet.claim_rewards()` analogous to the legacy `PoolWallet.claim_pool_rewards()`'s `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS`: accept an optional cap on the number of reward coins processed per call, sort/select a bounded subset of `rewards_to_claim`, and allow the singleton spend + announcement chain to be built only over that subset, leaving the remainder claimable in subsequent calls. Expose this cap through the `pw_absorb_rewards` RPC request for `PlotNFT2Wallet` the same way it already exists for `PoolWallet`.

### Proof of Concept
Conceptual reproduction (cannot be executed without a live wallet/test harness in this session):
1. Create a `PlotNFT2Wallet` (self-pooling or pooled) and let it accumulate a very large number of unclaimed reward coins over time (e.g., by farming many blocks or simulating a long period without calling `claim_rewards`), so `plotnft2_store.get_pool_rewards()` returns hundreds+ entries.
2. Call `pw_absorb_rewards` (or `PlotNFT2Wallet.claim_rewards` directly) — observe that `coin_spends` in `claim_rewards()` (`chia/wallet/plotnft_wallet/plotnft_wallet.py:164-198`) is built for every entry in `rewards_to_claim` with no truncation.
3. Submit the resulting `WalletSpendBundle` to the mempool; once total cost/spend count exceeds `max_tx_clvm_cost`/`MAX_SPENDS_PER_BLOCK`, `MempoolManager` rejects it (`cost > max_tx_clvm_cost` → reject, per `.cursor/context/mempool.md:73-76`).
4. Because `claim_rewards()` has no way to request a subset of rewards, the owner cannot construct any valid smaller bundle through the wallet API, and the rewards remain unclaimed indefinitely.

    async def pw_absorb_rewards(
        self,
        request: PWAbsorbRewards,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> PWAbsorbRewardsResponse:
        """Perform a sweep of the p2_singleton rewards controlled by the pool wallet singleton"""
        wallet = self.service.wallet_state_manager.wallets[request.wallet_id]

        if isinstance(wallet, PoolWallet):
            async with self.service.wallet_state_manager.lock:
                await wallet.claim_pool_rewards(request.fee, request.max_spends_in_tx, action_scope)
                state: PoolWalletInfo = await wallet.get_current_state()
        elif isinstance(wallet, PlotNFT2Wallet):
            await wallet.claim_rewards(action_scope=action_scope, fee=request.fee, extra_conditions=extra_conditions)
            state = await wallet.get_current_state()
        else:
            raise ValueError("`pw_absorb_rewards` called on a non-pooling wallet")
