### Title
IntentGatewayV2 (Tron) `withdraw()`/`SweepDust` ignore ERC20 return data, letting non-conforming or malicious input tokens fake a successful settlement while escrow state is marked settled - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` uses raw low-level `.call` with `IERC20.transfer.selector` for every outbound token payout (`withdraw()` and the `SweepDust` branch of `onAccept()`), and only checks that the *call itself* did not revert (`success`). It never decodes/validates the boolean return value of `transfer()`. This is the direct structural analog of the frxETH `recoverERC20` bug (M-06): code assumes ERC20 `transfer` semantics that not all tokens honor. Here the failure mode is inverted and worse — instead of reverting on non-conforming tokens (locking funds but leaving state consistent), a token that returns `false` without reverting is silently treated as a *successful* transfer, while the escrow accounting (`_orders[...] -= amount`) and settlement flags (`_filled[commitment] = beneficiary`) are unconditionally updated as if the payout succeeded.

The same pattern recurs in the `SweepDust` handler inside `onAccept`, and in the fee-redemption tail of `withdraw`: [4](#0-3) [5](#0-4) 

By contrast, elsewhere in the very same contract, inbound transfers correctly use OpenZeppelin's `safeTransferFrom`, which reverts on both call failure and a `false` return: [6](#0-5) 

`withdraw()` is reachable from three call paths, none of which require a malicious relayer, prover, or admin:
- `onAccept` for `RedeemEscrow`/`RefundEscrow`, gated only by proof-authenticated cross-chain messages: [7](#0-6) 
- `cancelOrder` same-chain path, directly callable by the order owner with no relayer involved: [8](#0-7) 
- `cancelOrder` destination-chain refund dispatch path: [9](#0-8) 

The order's `inputs` token list — including which ERC20/TRC20 contract is used as the escrowed asset — is fully attacker-controlled at order-creation time (any unprivileged user can create an order specifying an arbitrary token address). TRC20 tokens on Tron are well known for not strictly conforming to the boolean-return convention (some silently return `false` on failure, some don't revert on insufficient balance in unusual configurations), which is exactly the "non-conforming ERC20" class the original report warns about.

### Impact Explanation
Because the code advances internal accounting state (`_filled`, `_orders[...] -= amount`) regardless of whether the token transfer truly succeeded, a token whose `transfer()` returns `false` on failure (rather than reverting) causes the contract to durably record an order as **filled/settled** and the escrow balance as **spent**, while the actual tokens remain locked in the `IntentGatewayV2` contract and are never delivered to the beneficiary. This is a false-state-acceptance / fund-loss condition: the beneficiary (solver who filled the order, or user being refunded) permanently loses their entitled payout, the tokens become unrecoverable through the normal settlement path, and there is no re-entry point to retry the transfer once `_orders[commitment][token]` has been zeroed and `_filled` has been set. This falls squarely under the bounty's "unauthorized transaction or execution" / "loss of funds" / "false ... state acceptance" categories, since the contract's on-chain bookkeeping diverges from the true token balances without any attacker needing privileged access.

### Likelihood Explanation
Likelihood is realistic but conditional: it requires an order to be created using a token contract that returns `false` on failed `transfer` instead of reverting. Since order `inputs` (and hence which token is escrowed and later paid out via `withdraw`) are chosen by the unprivileged order creator, and Tron/TRC20 tokens are notorious for non-standard boolean-return behavior (mirroring the exact USDT-style class of tokens cited in the original report), this is not a hypothetical edge case for a Tron deployment — it is the expected token landscape on that chain. No relayer, prover, governance, or leaked-key assumption is needed; the only inputs are a normal order placement (public entrypoint `newOrder`/order struct) and a normal settlement call (`onAccept`/`cancelOrder`, both standard, non-privileged flows already exercised in the protocol's happy path).

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, matching the `safeTransferFrom` already used for inbound transfers in the same contract. `SafeERC20` correctly handles both revert-on-failure tokens and boolean-return tokens (including no-return tokens like USDT), reverting the whole state transition — including the `_filled` write and `_orders` decrement — if the transfer did not actually succeed, so escrow accounting can never diverge from real token custody.

### Proof of Concept
1. Attacker deploys a TRC20-style token `EvilToken` whose `transfer()` returns `false` when `to == someBlacklistedOrPredeterminedAddress` (or simply always returns `false` without reverting on any call from `IntentGatewayV2`), while never reverting.
2. Attacker creates a same-chain order via `newOrder`, using `EvilToken` as an input asset, escrowing real value from the attacker (or an unwitting solver, depending on the flow being targeted) into the gateway.
3. Attacker or a solver invokes the code path that ultimately calls `withdraw(body, ...)` (e.g., `cancelOrder` for the same-chain case, or an ISMP-triggered `RedeemEscrow` after the order is filled).
4. Inside `withdraw`, `_filled[commitment] = beneficiary` is set, then `token.call(...transfer...)` returns `success = true` (the call didn't revert) but the ABI-decoded return value is `false` — the contract does not check it: [10](#0-9) 
5. `_orders[commitment][token] -= amount` executes, marking the escrow spent; `EscrowReleased`/`EscrowRefunded` is emitted.
6. The beneficiary's on-chain token balance is unchanged (no tokens were actually moved), yet the protocol considers the order fully and correctly settled with no path to retry or reclaim the stuck balance — a permanent, unauthorized-state loss of the escrowed funds.
