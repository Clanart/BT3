### Title
Out-of-range participant indexes in PedPoP blame evaluation cause a process panic via unchecked `HashMap` indexing - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
The PedPoP DKG's blame-resolution path (`BlameMachine::blame`, `AdditionalBlameMachine::blame`) accepts caller-supplied `sender` and `recipient` `Participant` values and uses them as unchecked `HashMap` index keys. Analogous to CVE-2025-43430 (maliciously crafted input → unexpected process crash), an unprivileged protocol participant can submit a blame claim naming a participant index that was never registered, turning blame evaluation into a panic that aborts the calling process instead of returning a fault attribution.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` take `sender`/`recipient` arguments that ultimately originate from an accusing participant's message — i.e., attacker-controlled. `blame_internal` passes them to `Decryption::decrypt_with_proof`, which indexes `self.enc_keys[&decryptor]` [1](#0-0) . `enc_keys` only contains entries for participants `1..=n` registered via `Decryption::register`, which itself asserts uniqueness but is never given out-of-range keys [2](#0-1) . If `recipient` is `Participant(n+1)` (or any unregistered index), the `HashMap` index operator panics.

A second panic site exists in `blame_internal`, which indexes `self.commitments[&sender]` [3](#0-2) . `commitments` is populated only for the `n` real participants (either via `verify_r1` over `all_participant_indexes` or `AdditionalBlameMachine::new` over `1..=n`) [4](#0-3) . Neither `blame` entry point bounds-checks `sender`/`recipient` against `params`/`n` before indexing [5](#0-4) .

Note `AdditionalBlameMachine::new` is explicitly designed to be usable by a non-member evaluating third-party blame claims [6](#0-5) , so the attacker-controlled accusation path is a documented, reachable use case — not a documented-MUST misuse.

### Impact Explanation
A single crafted blame submission (or an accusation forwarded by an honest party relaying a malicious claim) panics the thread running blame resolution. In a validator/processor deployment this is a remote, unauthenticated-input-driven crash of the DKG key-generation/blame subsystem — the same impact class as the CVE (process crash on maliciously crafted content). It can be used to abort DKG completion or to crash an arbiter evaluating blame proofs, denying key-generation liveness for the whole set. Consistent with the scan rules this is reported as Medium: availability loss only, no secret leakage.

### Likelihood Explanation
Triggering requires an attacker to be a DKG participant (or to get a claim relayed) who names an out-of-range `sender`/`recipient`, and to supply a `msg` whose `pop` Schnorr signature verifies — which any real participant can produce since they encrypt their own shares — plus an `EncryptionKeyProof` whose `DLEqProof` is well-formed enough to reach the `enc_keys[&decryptor]` lookup. Since the panic occurs at the indexing expression before or during verification-dependent branches, the barrier is low for any authenticated participant.

### Recommendation
Validate `sender` and `recipient` against the known participant set (`1..=n` / `params.all_participant_indexes()`) at the top of `blame`/`blame_internal`, and replace `map[&key]` indexing with `map.get(&key)` plus an explicit `Err`/fallback (e.g., treating an unknown `recipient` as faulty accuser, or returning an error variant). Do the same for `self.commitments[&l]`-style indexing elsewhere (`calculate_share` is currently safe only because `validate_map` constrains `l` — keep that invariant enforced).

### Proof of Concept
```rust
// Context: PedPoP DKG completed for n participants; a third party (or a
// participant) evaluates blame claims via AdditionalBlameMachine.
let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// Attacker-controlled claim naming a recipient outside 1..=n.
let evil_recipient = Participant::new(n + 1).unwrap();

// `msg` is a genuine EncryptedMessage the attacker produced (valid `pop`),
// `proof` is an EncryptionKeyProof the attacker can construct.
// Inside blame_internal -> decrypt_with_proof:
//   proof.dleq.verify(..., &[self.enc_keys[&decryptor], *proof.key])
//                           ^^^^^^^^^^^^^^^^^^^^^^^^^ panics: key not in map
machine.blame(honest_sender, evil_recipient, msg, Some(proof));
```

Equivalent panic via the sender side: once decryption succeeds, `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)` panics if `sender` isn't among `1..=n` [3](#0-2) .

One caveat I could not fully verify within this session: whether upstream callers in `processor`/`coordinator` already filter blame claims to in-range participants before invoking `blame` — if they do, the panic remains a latent library-level crash reachable whenever an integrator forwards unvalidated claims, which the crate's own API contract does not prohibit.
