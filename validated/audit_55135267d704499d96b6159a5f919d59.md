### Title
Untrusted `ReceivedOutput` bytes can report unspendable Bitcoin as wallet funds - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts the spend offset, `TxOut`, and `OutPoint` as independent serialized fields without verifying that the output’s `script_pubkey` is actually controlled by the wallet key after applying the claimed offset. The field is private and normally populated only by `Scanner`, but deserialization lets an attacker set it directly. [1](#0-0) [2](#0-1) 

### Finding Description
The scanner maintains the necessary invariant internally: `register_offset` maps a script to an offset, and `scan_transaction` constructs `ReceivedOutput` only after matching `output.script_pubkey` against that registered map. [3](#0-2) [4](#0-3) 

`ReceivedOutput::read` bypasses that construction path. It reads:

1. A secp256k1 scalar into `offset`
2. An arbitrary consensus-encoded `TxOut` into `output`
3. An arbitrary consensus-encoded `OutPoint` into `outpoint`

It then returns all three as a valid `ReceivedOutput` without knowing or checking the wallet key. [2](#0-1) 

`SignableTransaction::new` trusts the supplied object as an input: it sums `input.output.value` as available funds, copies `input.offset` into the signing offsets, and uses `input.outpoint` as the transaction input. [5](#0-4)  The mismatch is only detected later by `SignableTransaction::multisig`, which rejects the transaction when `p2tr_script_buf(keys.offset(offset).group_key())` does not equal the claimed previous output script. [6](#0-5) 

### Impact Explanation
An attacker who can supply bytes to `ReceivedOutput::read` can cause wallet state to report attacker-chosen outputs and amounts as received funds even though the wallet cannot spend them. This matches the bug class of deserialization restoring a private/internal field without enforcing the invariant normally imposed by the public construction path.

The result is incorrect balance accounting and potentially permanently unavailable reported funds. It does not directly forge a transaction signature because `multisig` rejects mismatched offset/script pairs before constructing the signing machines. [6](#0-5) 

### Likelihood Explanation
Exploitation requires an attacker-controlled serialized `ReceivedOutput` to reach `ReceivedOutput::read`. The attacker does not need a validator key, threshold collusion, leaked secrets, or malformed curve encodings: `Secp256k1::read_F`, `TxOut::consensus_decode`, and `OutPoint::consensus_decode` all accept canonical values while preserving the semantic mismatch. [7](#0-6) 

### Recommendation
Do not expose a bare `ReceivedOutput::read` that accepts semantic trust relationships as serialized data. Prefer one of:

- Store only the `OutPoint` and rescan the referenced transaction output through `Scanner`, deriving `offset` and `output` locally.
- Include the wallet/view key in the read operation and verify `output.script_pubkey == p2tr_script_buf(key + G * offset)`.
- Treat deserialized `ReceivedOutput` values as untrusted candidates and perform the same script check before exposing their value as balance or passing them to `SignableTransaction::new`.

### Proof of Concept
The following conceptual input demonstrates the issue:

```rust
// An arbitrary scalar which does not correspond to the output below.
let malicious_offset = Scalar::ZERO.to_bytes();

// A real or merely well-formed TxOut paying an unrelated script_pubkey.
let unrelated_output = bitcoin::consensus::encode::serialize(&TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_op_return(PushBytesBuf::new()),
});

// Any syntactically valid outpoint.
let claimed_outpoint = bitcoin::consensus::encode::serialize(&OutPoint::default());

let mut bytes = Vec::new();
bytes.extend(malicious_offset);
bytes.extend(unrelated_output);
bytes.extend(claimed_outpoint);

// Accepted despite the offset/output relationship never being checked.
let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 100_000);

// Wallet/accounting code now sees 100_000 sats as an input.
let signable = SignableTransaction::new(
  vec![received],
  &[(destination_script, 50_000)],
  None,
  None,
  1,
).unwrap();

// Signing fails because key.offset(0) does not control the unrelated script.
assert!(signable.multisig(&wallet_keys).is_none());
```

The deserialized object reports value and is accepted as an input candidate, but it is unspendable under the wallet’s `ThresholdKeys`.
