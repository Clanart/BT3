### Title
Panic on unregistered participant key in PedPoP `Encryption::encrypt` causes node crash from withheld DKG message - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2020-23313 is a reachable assertion failure (`assert` triggered by attacker-controlled input) causing a process crash in JerryScript. The analogous shape in Serai is a panic reachable purely from an unprivileged counterparty's message behavior: in PedPoP, `SecretShareMachine::verify_r1` registers an encryption key only for participants present in the caller-supplied `commitment_msgs` map (`let Some(msg) = commitment_msgs.remove(&l) else { continue }` at `crypto/dkg/pedpop/src/lib.rs:314`), but `generate_secret_shares` then unconditionally calls `self.encryption.encrypt(rng, l, ...)` for every participant index at `crypto/dkg/pedpop/src/lib.rs:369`. `encrypt` indexes `self.decryption.enc_keys[&participant]` at `crypto/dkg/pedpop/src/encryption.rs:466`, which panics (`HashMap` index on absent key) if that participant never provided an `EncryptionKeyMessage`. A sibling panic exists at `crypto/dkg/pedpop/src/encryption.rs:356` (`assert!(!self.enc_keys.contains_key(&participant))`) for duplicate registration.

### Finding Description
`Decryption::register` inserts per-participant ECDH public keys into `enc_keys` (`encryption.rs:356-360`). `verify_r1` tolerates a missing entry by skipping registration (`else { continue }`), so `enc_keys` can lack a participant that `generate_secret_shares` still iterates over via `self.params.all_participant_indexes()` (`lib.rs:359`). `Encryption::encrypt` then performs `self.decryption.enc_keys[&participant]` (`encryption.rs:466`), panicking instead of returning a `PedPoPError`. Whether this is reachable depends on `validate_map` (`lib.rs:305-309`) not enforcing completeness of the participant set; the explicit `else { continue }` path suggests omission is tolerated at that layer. If completeness is enforced there, the remaining reachable panic is the duplicate-registration `assert!` at `encryption.rs:356`, triggered if the same participant's registration is processed twice across rounds on a shared `Encryption`/`Decryption` box.

### Impact Explanation
A single DKG participant who withholds their commitment/encryption-key message from one victim (or causes a second registration) crashes the victim's processor rather than producing a `PedPoPError`. This is an unprivileged-party-reachable availability failure of the same class as the upstream assertion: attacker-controlled input hits a panic path in production code. It can abort the key generation ceremony and, in a long-running processor, kill the whole process, taking down signing for all other multisigs it serves.

### Likelihood Explanation
Requires only being one participant in a PedPoP session and omitting (or duplicating) a round-1 message to a target — no key material or collusion needed. Exploitability is conditional on `validate_map` permitting an incomplete map; if it requires the full set, the withheld-message path returns an error before the panic, reducing this to the duplicate-registration assertion, which depends on how the integrator drives the machine.

### Recommendation
Replace `self.decryption.enc_keys[&participant]` in `Encryption::encrypt` and `self.enc_keys[&decryptor]` in `decrypt_with_proof` with `get()` returning a `PedPoPError`/`DecryptionError`, and downgrade the duplicate-registration `assert!` in `Decryption::register` to a returned error. Confirm `validate_map` rejects maps missing expected participants so `verify_r1` fails cleanly before `encrypt` is reached.

### Proof of Concept
In a `ThresholdParams` with `n >= 2`, run `KeyGenMachine::new(...).generate_coefficients(rng)`, then call `generate_secret_shares(rng, commitments)` where `commitments` omits participant `l`'s `EncryptionKeyMessage` (assuming `validate_map` accepts the omission). `verify_r1` skips registering `l`, then `encrypt(rng, l, ...)` panics at `self.decryption.enc_keys[&l]` with `key not found`. Alternatively, invoking `register` twice for the same participant on a reused `Decryption` box triggers `assert!(... "Re-registering encryption key for a participant")`.
