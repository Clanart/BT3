### Title
Missing rate limit on keyring passphrase validation in daemon RPC allows unthrottled brute-force of the master passphrase - (File: chia/daemon/server.py)

### Summary
The Chia daemon's websocket RPC server exposes `unlock_keyring` and `validate_keyring_passphrase` commands that check a supplied passphrase against the on-disk encrypted keyring, with no attempt counting, lockout, or delay between failed attempts, unlike the CLI passphrase prompt path which enforces `MAX_RETRIES = 3` and a `FAILED_ATTEMPT_DELAY`.

### Finding Description
`WebSocketServer.unlock_keyring` and `WebSocketServer.validate_keyring_passphrase` accept a `key` field, call `Keychain.master_passphrase_is_valid(key, force_reload=True)`, and immediately return a success/failure boolean, with no throttling logic between calls. [1](#0-0) [2](#0-1) 

Underneath, `master_passphrase_is_valid` simply delegates to `KeyringWrapper.master_passphrase_is_valid` → `FileKeyring.check_passphrase`, a stateless check with no counter or backoff. [3](#0-2) [4](#0-3) 

By contrast, the *interactive CLI* prompt path (`obtain_current_passphrase`) does enforce a bounded number of retries with a delay, showing the daemon codebase is aware of brute-force risk in this exact area but only mitigates it for one entry point. [5](#0-4) [6](#0-5) 

A caller with a valid daemon websocket connection (the daemon is protected by mTLS via `ssl_context_for_server`, i.e. any process holding one of the locally-issued Chia certs — this includes any local service, GUI, or CLI-launched client on the machine, not just the machine owner) can send unlimited `unlock_keyring`/`validate_keyring_passphrase` requests back-to-back to brute-force the master passphrase protecting the encrypted keyring that holds all wallet private keys.

### Impact Explanation
If an attacker who holds daemon connectivity (a "local RPC caller" per the in-scope actor list) but does not know the master passphrase can brute-force it via unthrottled `unlock_keyring`/`validate_keyring_passphrase` calls, they gain the ability to decrypt the keyring and obtain private keys for all wallets managed by that keychain. This directly enables unauthorized coin movement — forging valid signed spends for any coin controlled by those keys — since possession of the private keys defeats the entire AGG_SIG-based authorization model for standard puzzles and any derived puzzles (CATs, singletons, etc.).

### Likelihood Explanation
Exploitability depends on the passphrase's strength; a weak or short user-chosen master passphrase (which is the common case since it's user-set outside the keyring's own key material) can be brute-forced quickly with no rate limit slowing the attacker, versus the deliberate `FAILED_ATTEMPT_DELAY`/`MAX_RETRIES` design intentionally used elsewhere in the same codebase for the identical operation. The precondition (an attacker having a connection to the local daemon RPC) is more restrictive than a purely remote/network attacker, which lowers likelihood somewhat, but this is explicitly one of the actor classes the scope treats as reachable ("daemon/keychain/RPC authorization" / "local RPC caller").

### Recommendation
Add attempt throttling (exponential backoff or a bounded lockout window) to the daemon's `unlock_keyring` and `validate_keyring_passphrase` RPC handlers in `chia/daemon/server.py`, mirroring the `MAX_RETRIES`/`FAILED_ATTEMPT_DELAY` protections already present in `chia/util/keyring_wrapper.py`'s CLI path, and/or count failed attempts per-connection/per-process and disconnect or ban after repeated failures.

### Proof of Concept
1. Establish a websocket connection to the daemon with a valid local client certificate (as any locally-running Chia service/CLI does).
2. Repeatedly send `create_payload("unlock_keyring", {"key": "<guess>"}, ...)` or `validate_keyring_passphrase` payloads with different passphrase guesses in a tight loop.
3. Observe that `chia/daemon/server.py`'s handlers respond immediately to every attempt with no increasing delay, lockout, or attempt cap — as demonstrated by the test harness sending consecutive `unlock_keyring`/`validate_keyring_passphrase` requests with no observed throttling. [7](#0-6) 

**Note on uncertainty:** I was not able to fully confirm whether any additional layer (e.g., connection-level rate limiting configured elsewhere, OS-level cert issuance restrictions, or GUI-imposed throttling) mitigates this at a level outside `chia/daemon/server.py`; the RPC handler and underlying keyring-check code itself contain no such control based on what was inspected.

```python
    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"
```
