### Title
Gasless bundle admission control uses a read-lock while mutating the shared `knownTxs` map, allowing an unprivileged tx sender to bypass the `MaxBundleTxsInQueue` cap and force unbounded resource growth / concurrent-map-write DoS - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.PreAddTx` is the admission gate that limits how many "gasless bundle" transactions (approve/swap pairs) can sit in a node's `knownTxs` bookkeeping map at once, mirroring the same class of missing-resource-accounting bug as ALPINE-CVE-2017-5578 (repeated attach commands not properly bounded/reclaimed, leading to unbounded host memory consumption). Here, the admission check-then-act sequence is protected only by a **read** lock while it performs a write (map insertion), so the quota can be raced and bypassed by concurrent transaction submissions from a single unprivileged sender/RPC caller.

### Finding Description
`PreAddTx` acquires `g.knownTxsMu.RLock()` (a shared/read lock, not exclusive) and then, if the tx is not already known and quota allows, calls `g.knownTxs.add(tx, TxStatusQueue)`, which writes directly into the `knownTxs` map (a plain `map[common.Hash]*knownTx`): [1](#0-0) 

The mutation happens inside `knownTxs.add`, which unconditionally indexes into the map (`k[tx.Hash()] = &knownTx{...}`): [2](#0-1) 

By contrast, every other mutator of the same map (`IsReady`, `PreReset`, `PostReset`) takes the **exclusive** write lock `g.knownTxsMu.Lock()`: [3](#0-2) [4](#0-3) [5](#0-4) 

`sync.RWMutex.RLock()` allows multiple goroutines to hold the lock concurrently. Since transaction validation/admission (`PreAddTx`) is a per-tx hook invoked for every transaction entering the pool, an attacker submitting many gasless bundle transactions concurrently (e.g., via a batch of `eth_sendRawTransaction`/`eth_sendRawTransactions` calls processed in parallel before the pool's own account-level locking) can have multiple goroutines simultaneously:
1. Read `g.knownTxs.numQueue()` and see it below `MaxBundleTxsInQueue` (the check in `PreAddTx`, line 47), and
2. Concurrently write new entries into the shared Go map via `knownTxs.add`.

This is a genuine unsynchronized concurrent map write in Go, which either (a) silently bypasses the configured `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` caps (`kaiax/gasless/config.go`), letting `knownTxs` grow without the intended bound, analogous to the QEMU bug where repeated `VIRTIO_GPU_CMD_RESOURCE_ATTACH_BACKING` commands were not capped/reclaimed and caused unbounded host memory growth; or (b) triggers Go's runtime fatal error "concurrent map writes", crashing the node process outright — a stronger, node-availability-impacting outcome than the original CVE. [6](#0-5) 

### Impact Explanation
Any unprivileged party able to submit transactions to a Kaia node's public RPC (the same actor class as "gasless user"/"public-RPC caller" in scope) can:
- Force unbounded growth of the in-memory `knownTxs` accounting structure past its configured admission cap, consuming node memory over time (resource-exhaustion DoS), directly analogous to the referenced CVE's memory-consumption impact; or
- Trigger a concurrent map write panic, crashing the node process (denial of service), which is a materially worse outcome than the reference CVE since it affects node availability network-wide rather than a single guest VM.

Both outcomes degrade or halt block production/tx processing for the affected node, which is a Medium-severity availability impact consistent with the referenced advisory's CVSS profile (local/low-privilege attacker, no special access required, availability impact).

### Likelihood Explanation
The trigger requires only sending ordinary, validly-formed gasless bundle-shaped transactions (approve/swap sequences recognized by `IsBundleTx`) in sufficient concurrent volume — a capability any unprivileged transaction sender or public RPC client already has. No consensus, validator, or peer compromise is needed; exploitation is purely a race on shared in-process module state during normal transaction admission.

### Recommendation
Change `PreAddTx` in `kaiax/gasless/impl/tx_pool.go` to acquire the exclusive `g.knownTxsMu.Lock()` (matching `IsReady`, `PreReset`, `PostReset`) instead of `RLock()`, so the quota check-and-insert sequence is atomic with respect to all other mutators of `knownTxs`. Additionally, consider making the quota check and the `add` call a single atomic operation inside `knownTxs` itself (e.g., an `addIfUnderLimit` method) to remove any remaining TOCTOU window, and add a race-detector test that concurrently calls `PreAddTx` from multiple goroutines to catch regressions.

### Proof of Concept
Conceptual repro (would require running under Go's race detector or with sufficient goroutine scheduling variance):
1. Configure a node with `--gasless.max-bundle-txs-in-queue 1`.
2. From an external client, concurrently submit N (>1) distinct valid gasless "approve" transactions from N different accounts in the same instant (parallel HTTP/WS RPC calls to `eth_sendRawTransaction`), such that their `PreAddTx` invocations overlap.
3. Because `PreAddTx` only takes `RLock()`, multiple goroutines can simultaneously observe `numQueue() < 1` and each proceed to call `knownTxs.add`, resulting in more than 1 bundle tx admitted into `knownTxs` (cap bypass) or a `fatal error: concurrent map writes` panic terminating the node — observable via node logs/crash dump.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
