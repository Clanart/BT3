## Title
`testForInvalidChars` uses a stateful global `RegExp` whose `.test()` calls leak `lastIndex` state, letting a malicious branch name from a clicked deep link silently bypass git ref-name validation - (File: `app/src/lib/sanitize-ref-name.ts`)

## Summary
This mirrors the stellar-xdr bug class: a validation routine that is supposed to reject an out-of-invariant value (here, a git ref name containing characters forbidden by `git-check-ref-format`) can instead return "valid" for genuinely invalid input due to an implementation defect, letting the bad value propagate downstream unchecked.

## Finding Description
`invalidCharacterRegex` is declared once at module scope with the global (`g`) flag [1](#0-0) , and `testForInvalidChars` calls `.test()` directly on that shared regex object: [2](#0-1) 

Per the ECMAScript spec, `RegExp.prototype.test` on a regex with the `g` flag is stateful: when a match is found, `lastIndex` is advanced past the match and *not* reset; the next call to `.test()` on that same object begins searching from that leftover `lastIndex`. If the next string being tested is shorter than the previous `lastIndex`, the search position is already past the end of the string, so `exec`/`test` returns `false` immediately — reporting "no invalid characters" even when the new string plainly contains one (e.g. starts with `..`, contains `~`, `^`, `:`, `?`, `*`, control characters, or ends in `.lock`).

`testForInvalidChars` is the sole guard used by `parseAppURL` to validate the `branch` query parameter coming from an untrusted deep link (`x-github-client://` / `github-mac://openRepo/...?branch=...`), an attacker-controlled input per the "link or deep link the user clicks" category: [3](#0-2) 

Because `invalidCharacterRegex` is module-level and shared across all calls (every deep-link/protocol invocation in the process reuses the same object instance and therefore the same `lastIndex`), a prior successful validation call (one that matched and advanced `lastIndex`) can poison the outcome of a subsequent, unrelated `testForInvalidChars(branch)` call for a different deep link handled later in the same app session — causing a branch value that actually violates the ref-name invariant to be accepted and returned unmodified as `branch` in the `open-repository-from-url` action.

## Impact Explanation
Unlike the sanitization path used elsewhere in the app (`sanitizedRefName`, used e.g. for worktree names [4](#0-3) ), the deep-link branch value that slips past a bypassed `testForInvalidChars` check is not further sanitized before being handed to the rest of the app as `IOpenRepositoryFromURLAction.branch`, per the tests documenting the expected reject-on-invalid-chars behavior [5](#0-4) . A branch value containing sequences the guard is meant to block (consecutive dots, control characters, `.lock` suffix, etc.) is exactly the class of ref name that `git-check-ref-format` forbids because such names can be used to escape the intended `.git/refs/...` namespace or otherwise corrupt ref storage/locking when passed to subsequent git operations that consume this value. This satisfies the report's core theme: a broken length/format invariant guard that lets an out-of-spec value flow downstream into logic that assumes the invariant holds.

## Likelihood Explanation
Triggering the stale-`lastIndex` condition only requires two invocations of `testForInvalidChars` within the process lifetime where the first call's match leaves `lastIndex` beyond the length of the second string being validated — plausible any time a user handles more than one crafted deep link (or the same link twice) during a session, since `invalidCharacterRegex` persists as a singleton for the app's lifetime. No local access, admin rights, or prior malware is required — only that the victim click an attacker-supplied `x-github-client://` / `github-mac://` link, which is within the accepted "link/deep link" attacker primitive.

## Recommendation
- Do not reuse a `g`-flagged `RegExp` object across independent `.test()` calls for validation. Either strip the `g` flag for `testForInvalidChars` (using a non-global regex, or clone the pattern without `g`), or explicitly reset `invalidCharacterRegex.lastIndex = 0` before/after each `.test()` call.
- Add a regression test that calls `testForInvalidChars` twice in a row — first with a longer string that matches near the end, then with a shorter genuinely-invalid string — and assert both calls correctly return `true`.

## Proof of Concept
```ts
import { testForInvalidChars } from '../../src/lib/sanitize-ref-name'

// First call: matches a forbidden character near the end of a long string,
// advancing the shared regex's lastIndex well past position 5.
testForInvalidChars('a'.repeat(50) + '~') // returns true, lastIndex now ~51

// Second call: a short, genuinely invalid branch name from a *different*
// deep link handled afterwards in the same process.
testForInvalidChars('..')                 // BUG: returns false (lastIndex > length)
```
Because `parseAppURL` only gates the deep-link `branch` value on `testForInvalidChars`, the second, malicious `branch=..` value (or one containing `~^:?*[\|"<>` / control chars / `.lock`) would be accepted and returned unchanged in the `open-repository-from-url` action, exactly analogous to `StringM::from_str` returning `Ok` for an over-limit value instead of `Err(LengthExceedsMax)`.
