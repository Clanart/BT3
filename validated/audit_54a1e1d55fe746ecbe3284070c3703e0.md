### Title
`ThresholdKeys::read` accepts attacker-controlled verification shares and secret share with no consistency check, letting forged key material produce signatures under an attacker-chosen group key - (File: crypto/dkg/src/lib.rs)

### Summary

Analogous to Indy-Node's `pool-upgrade` handler processing an unauthenticated transaction, `ThresholdKeys::read` deserializes and fully trusts an untrusted key blob: it never verifies that `secret_share` corresponds to `verification_shares[i]`, never checks that the verification shares form a consistent sharing, and derives `group_key` solely from the shares of participants `1..=t` via `ThresholdKeys::new`. Points are read with `Ciphersuite::read_G` (canonical/torsion checks only), not `Curve::read_G`, so identity points are also accepted.

### Finding Description

`ThresholdKeys::read` parses `t, n, i`, an interpolation method, `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new`. `new` only validates `verification_shares.len() == n` and that indexes are `<= n`, then computes `group_key = sum_{i in 1..=t} verification_shares[i] * interpolation_factor(i, 1..=t)`. Verification shares for participants `t+1..=n` are never bound into the group key, and no equation `G * secret_share == verification_shares[i]` (or an interpolated equivalent) is checked. The comment in `crypto/frost/src/sign.rs` acknowledges this: "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys" — the library knows semantically invalid keys can be fed in but performs no check.

Concretely, an attacker supplying a `ThresholdKeys` blob can:
- Choose arbitrary `verification_shares[1..=t]` so `group_key` becomes a point whose discrete log they know (e.g., shares of a polynomial with a constant term they selected).
- Choose `verification_shares[j]` for `j > t` to be `G * s_j` for any `s_j` they know, letting them forge valid FROST signature shares "as participant j" that pass `verify_share`/`batch_statements` in `AlgorithmSignatureMachine::complete`.
- Set the victim's `secret_share` to a known value, making every subsequent signature share leak nothing while validating cleanly.

### Impact Explanation

An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g., key-share blobs exchanged during reshare/recovery flows that call `recover_key`/`view`/`sign`) causes the victim to hold keys for a group key the attacker fully controls. FROST signing via `AlgorithmSignMachine::sign`/`complete` then emits valid signatures under that attacker-known key — concrete signing under an unintended group key — and `recover_key` in `crypto/dkg/recovery/src/lib.rs` will "successfully" recover a secret the attacker already knows. If the group key backs Bitcoin outputs (the intended usage), funds addressed to it are spendable by the attacker, not the honest set.

### Likelihood Explanation

Reachability is limited to flows where a node accepts serialized `ThresholdKeys` from peers rather than generating them locally via `key_gen`/PedPoP. Where such a flow exists, the attack needs no threshold collusion — a single crafted blob suffices — since the checks in `ThresholdParams::new`/`ThresholdKeys::new` pass trivially. Where keys are only locally produced, exposure is low.

### Recommendation

In `ThresholdKeys::new` (so `read` inherits the check), verify the secret share against its verification share (`C::generator() * secret_share == verification_shares[&i] * interpolation_factor^{-1}` or the equivalent for the configured interpolation), and bind all `n` verification shares — not just `1..=t` — into the serialized form's integrity, e.g., by requiring the interpolant through shares `1..=n` to be degree `< t` consistent, or by including an authentication tag/signature over the blob. Reject identity verification shares on read for FROST usage by using `Curve::read_G` semantics.

### Proof of Concept

```rust
// Attacker crafts a blob for curve C, params t=2, n=3, i=1.
// Choose attacker secret a, and shares s2, s3 arbitrarily.
let a = C::F::random(&mut OsRng);            // attacker-known "group secret"
let s2 = C::F::random(&mut OsRng);
let s3 = C::F::random(&mut OsRng);

// Pick a victim share the attacker also knows (blob is attacker-written)
let victim_share = C::F::random(&mut OsRng);

// verification_shares[1..=t] define group_key; make them consistent with `a`
// such that sum over 1..=t of share_i * lagrange_i = a. Simplest: encode the
// polynomial a + b*x, share_i = a + b*i, with b chosen; verification share i = G*share_i.
let b = C::F::random(&mut OsRng);
let share = |i: u64| a + b * C::F::from(i);

let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(2u16.to_le_bytes());              // t
buf.extend(3u16.to_le_bytes());              // n
buf.extend(1u16.to_le_bytes());              // i = victim participant
buf.push(1);                                 // Interpolation::Lagrange
buf.extend(victim_share.to_repr().as_ref()); // attacker-known secret_share
for i in 1..=3u64 {
  buf.extend((C::generator() * share(i)).to_bytes().as_ref());
}

let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut buf.as_ref()).unwrap();
// group_key == G * a, whose discrete log `a` the attacker knows.
assert_eq!(keys.group_key(), C::generator() * a);
// Signatures produced by FROST machines over `keys` verify under G*a —
// spendable by the attacker; recover_key yields `a` (attacker-known).
```

The only check preventing this today is that honest flows never deserialize `ThresholdKeys` from a peer — nothing in `read`/`new` detects the forgery.
