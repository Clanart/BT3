### Title
Attacker-controlled `WWW-Authenticate` header from a malicious git remote triggers an unsolicited GitHub Enterprise sign-in flow bound to an arbitrary host - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
The credential-helper trampoline classifies a git remote as a genuine "GitHub Enterprise" endpoint based solely on the content of an HTTP `WWW-Authenticate` header returned by the remote server itself, without verifying that the host is an actual GitHub/GHE instance. A malicious or compromised git server can forge this header to make Desktop believe it is talking to an enterprise GitHub host, causing it to automatically open the built-in GitHub Enterprise sign-in flow and bind the resulting OAuth/PAT account object to the attacker-controlled origin — all without the user ever choosing to "Add Enterprise Account".

### Finding Description
When git needs credentials for a remote, it invokes Desktop's credential helper (`createCredentialHelperTrampolineHandler`) with a credential description built from the actual request, including any `wwwauth[n]` fields captured from the server's HTTP response headers. [1](#0-0) 

`getEndpointKind` uses these attacker-controlled header values to classify the endpoint: [2](#0-1) 

Specifically, if any `wwwauth[...]` header value contains `realm="GitHub"`, the endpoint is unconditionally classified as `'enterprise'` — there is no cross-check against a known/allow-listed GitHub Enterprise host, TLS certificate, or `/meta` API response; the classification trusts a single string emitted by the same untrusted server that is being authenticated against.

That classification then drives `getCredential`, which — if no existing Desktop account matches the endpoint — automatically calls `ui.promptForGitHubSignIn(endpoint)`: [3](#0-2) 

`promptForGitHubSignIn` then begins the real "Enterprise sign in" flow, setting the sign-in endpoint to the attacker's own origin and showing the "GitHub Enterprise" sign-in UI: [4](#0-3) 

This mirrors the pattern in the source report: a peripheral/auxiliary piece of attacker-supplied data (there, the un-validated `RekeyTo`/`Tx2` fee transaction; here, the un-validated `WWW-Authenticate` header) is trusted to authorize a privileged action (there, draining vault funds; here, triggering and branding an OAuth account-binding flow) that the primary validation path never anticipated needed checking.

### Impact Explanation
An attacker who controls a git remote/proxy response (e.g. a malicious or compromised git server the victim clones/fetches from, or a MITM proxy on an HTTP remote) can cause Desktop to spontaneously launch a "GitHub Enterprise" branded sign-in dialog pointed at the attacker's own host during an otherwise ordinary fetch/clone operation, rather than the user explicitly choosing to add that account. If the user completes the flow (entering credentials or completing OAuth against what appears to be a legitimate, Desktop-endorsed "Enterprise" sign-in surface), the resulting account is silently persisted in Desktop's account store bound to the attacker's origin, and future credential requests to that host will auto-fill from it. This is an unauthorized/attacker-influenced OAuth account binding triggered purely by content the remote server controls, without any explicit user intent to add that server as an enterprise account.

### Likelihood Explanation
The trigger only requires the victim to interact with a git remote that returns a crafted `WWW-Authenticate` header during authentication (e.g. an HTTP 401 response with `WWW-Authenticate: Basic realm="GitHub"`), which is fully within an attacker's control if they operate the remote/proxy — no local access, admin rights, or pre-existing malware is needed. However, exploitation still depends on user interaction with the resulting sign-in dialog to complete an account binding, and the endpoint classification code contains other narrowing conditions (`isDotCom`/`isGHE`/`isGitHubHost` checks precede the `wwwauth` fallback), so this is only reached when those don't already resolve the endpoint — moderate rather than trivial likelihood.

### Recommendation
**Short term:** Do not classify a remote as `'enterprise'` (GitHub-branded) based solely on a self-reported `WWW-Authenticate` realm string. At minimum, corroborate it with an independent signal such as a successful call to the host's `/api/v3/meta` (or equivalent) endpoint, or require explicit user confirmation before switching into the "Enterprise sign in" UI flow for a previously-unknown host.

**Long term:** Never let untrusted, remote-controlled response data (headers, redirects, etc.) directly select which trust-sensitive UI/OAuth flow is invoked; treat all such classification hints as advisory only, and gate any account-binding action behind explicit, unambiguous user consent that clearly displays the actual host being authenticated against.

### Proof of Concept
1. Stand up a git-over-HTTP server (e.g. using `git http-backend`/nginx) at `https://evil.example.com/victim/repo.git`.
2. Configure it to require authentication and respond to unauthenticated requests with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Get the victim to clone or fetch this repository in GitHub Desktop (e.g. via `Clone repository` → "URL" tab, or by adding it as a remote to an existing repository — no special permissions required).
4. Git invokes Desktop's credential helper; `getEndpointKind` sees the forged `wwwauth[...]` value containing `realm="GitHub"` and returns `'enterprise'`. [5](#0-4) 
5. Since no existing Desktop account matches `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')`. [6](#0-5) 
6. Desktop opens the real "Enterprise sign in" popup with the sign-in endpoint set to `https://evil.example.com`, presenting it with the same trusted UI used for legitimate GitHub Enterprise Server instances. [7](#0-6) 
7. If the user completes sign-in, an `Account` bound to `evil.example.com` is created and stored, all triggered purely by the attacker's HTTP response header rather than deliberate user action to add that host as an account.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

    return undefined

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
