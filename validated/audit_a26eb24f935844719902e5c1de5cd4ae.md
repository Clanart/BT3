### Title
DID recovery attestation signature (`AGG_SIG_UNSAFE`) omits recovering-coin identity, enabling signature replay across different DID recoveries - ([File: chia/wallet/did_wallet/did_wallet_puzzles.py])

### Summary
`create_recovery_message_puzzle` builds a backup/attestation coin whose only cryptographic binding is an `AGG_SIG_UNSAFE` condition over `newpuz` (the target puzzle hash), with no coin ID, launcher ID, or other per-recovery nonce baked into the signed message.

### Finding Description
The DID recovery attestation puzzle is:
```
[[ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
 [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz]]
``` [1](#0-0) 

Unlike the standard `AGG_SIG_ME`/`AGG_SIG_PARENT`/etc. conditions, which the consensus layer forces to append coin-specific data (`coin_id`, `parent_id`, `puzzle_hash`, `amount`) plus network `ADDITIONAL_DATA` before hashing — the exact "nonce"-style domain separation described in the reported bug class [2](#0-1)  — `AGG_SIG_UNSAFE` signs only the raw `msg` bytes with no coin binding, which is precisely why the codebase disallows it from ending in any of the reserved `ADDITIONAL_DATA` suffixes to prevent cross-context collisions [3](#0-2) . Here the backup DID's signature is only over `newpuz`, i.e., `sign(backup_sk, newpuz)`, with no `recovering_coin_id` in the signed payload — the coin ID is merely announced via `CREATE_COIN_ANNOUNCEMENT` (a plaintext, unsigned condition), not incorporated into the signature itself. This means the aggregate signature produced for one recovering DID's attestation is a valid signature for `(pubkey, newpuz)` regardless of which DID coin is doing the recovering.

I was unable to fully verify the DID inner puzzle (`DID_INNERPUZ_MOD`, loaded from a compiled `chia_puzzles_py` binary) or `did_wallet.py`'s recovery-spend construction within this session to confirm whether the puzzle-level `ASSERT_COIN_ANNOUNCEMENT`/backup-ID-list check independently re-binds the attestation to the specific recovering coin in a way that would block reuse of the exposed signature against a *different* DID that shares the same backup ID and wants to recover to the same `newpuz`. The `did_wallet_puzzles.py`, `did_wallet.py`, and `wallet_state_manager.py` recovery code paths reference `attest`/`recovery_list_hash` logic extensively [4](#0-3)  but the compiled inner puzzle logic itself was not retrievable through the available search tools, so I cannot state with certainty that the signature-replay path bypasses puzzle-level protections.

### Impact Explanation
If the puzzle-level check does not itself bind the signature to the specific recovering coin (only the announcement does, and announcements are unsigned/attacker-forgeable data included in the attacker's own coin_spend), an attacker who is a valid backup ID for two different DIDs (or who can obtain a broadcast/observed attestation signature for `(pubkey, newpuz)` from any DID recovery) could replay that same `AGG_SIG_UNSAFE` signature to satisfy the "backup DID attested" requirement for an unrelated victim DID that lists the same backup pubkey, redirecting control of the victim's DID to attacker-chosen `newpuz` without the backup key holder's fresh consent for that specific DID. This would constitute unauthorized coin ownership transfer of the DID singleton — a High-severity, spend-triggered authorization bypass, matching the reported bug class of signature reuse due to a missing per-action nonce/identity binding.

### Likelihood Explanation
Exploitability strictly depends on whether `DID_INNERPUZ_MOD`'s Chialisp recovery branch cryptographically re-derives or checks the recovering coin's identity as part of what is signed (rather than relying solely on the unsigned `CREATE_COIN_ANNOUNCEMENT`, which the attacker fully controls in their own spend bundle). Given I could not inspect the compiled inner-puzzle logic to confirm this binding, likelihood is uncertain — this should be validated against the actual `DID_INNERPUZ` CLVM/CLSP source before treating this as confirmed exploitable.

### Recommendation
Verify in `DID_INNERPUZ` (chialisp source, not just the compiled binary referenced by `did_wallet_puzzles.py`) whether the recovery/backup-attestation check binds the signed message to the recovering singleton's coin ID (e.g., by requiring the `AGG_SIG_UNSAFE` message to include `recovering_coin_id`, or by deriving the announcement assertion in a way that makes signature reuse across coins impossible). If it does not, include `recovering_coin_id` (and ideally the DID's `launcher_id`) directly inside the signed `msg` in `create_recovery_message_puzzle` (`chia/wallet/did_wallet/did_wallet_puzzles.py:138-155`), analogous to how `AGG_SIG_PARENT`/`AGG_SIG_ME` bind signatures to coin-specific data, so a backup ID's attestation signature cannot be replayed against a different DID's recovery.

### Proof of Concept
Not constructed — a working PoC requires confirming the exact Chialisp validation logic in `DID_INNERPUZ_MOD` (not available in the indexed codebase), specifically whether the puzzle's recovery-solution processing cross-checks the announced `recovering_coin_id` against anything other than its own coin ID in a way that would already prevent this reuse.

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle
```
