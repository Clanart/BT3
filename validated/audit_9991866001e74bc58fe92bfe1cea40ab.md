### Title
`is_deposit_valid` never checks the deposit outpoint is unspent, letting verifiers presign a move-to-vault for a spent/RBF'd deposit UTXO - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` only checks that the deposit transaction is confirmed, has the correct amount/script, and is above `start_height`; it never checks that `deposit_outpoint` is still unspent. An attacker who broadcasts a spendable deposit output, submits `DepositParams` via `NewDeposit`, then double-spends (via RBF or a conflicting spend) the same outpoint before/while verifiers presign, can get all N-of-N signatures produced and a move-to-vault transaction recorded whose input can never confirm.

### Finding Description
The invariant that should hold is: `deposit_outpoint` referenced by a recorded move-to-vault txid == a confirmed, currently **unspent** transaction output matching the expected bridge amount/script. `is_deposit_valid` (`core/src/verifier.rs:541-732`) enforces only:
- amount and scriptPubKey match (`core/src/verifier.rs:675-705`, using `self.rpc.get_tx_of_txid(&deposit_txid)` then reading `deposit_tx.output[vout]`),
- the containing block height is `>= start_height` via `get_raw_transaction_info`/`get_block_info` (`core/src/verifier.rs:706-730`).

There is no call to `is_utxo_spent`/`get_tx_out(..., include_mempool=false)` anywhere in this path to confirm the UTXO is still spendable at the time of signing [1](#0-0) . Compare with `ExtendedBitcoinRpc::is_utxo_spent`, which exists in the codebase and is used elsewhere (e.g. operator collateral checks) but is never invoked for the deposit outpoint in `is_deposit_valid` [2](#0-1) .

`is_deposit_valid` is called from both `deposit_sign` (`core/src/verifier.rs:876`) and `deposit_finalize` (`core/src/verifier.rs:994`), each independently re-fetching the deposit tx from the node with `get_tx_of_txid`, but neither re-verifies unspentness. Because these are two separate RPC round trips (nonce generation → `deposit_sign` streaming → aggregator collects partial sigs → `deposit_finalize`), there is a window during which the depositor can RBF-replace or double-spend the deposit transaction's input, invalidating the original deposit output, while verifiers still presign against the now-dead/mutated deposit outpoint. Once N-of-N signatures are collected, the aggregator calls `Aggregator::create_movetx` and publishes the move-to-vault transaction, which will never confirm because its declared input is not a real unspent UTXO — yet the bridge (via `insert_deposit_data_if_not_exists` at `core/src/verifier.rs:880-886`) has already recorded the deposit as processed.

No other guard closes this gap: `verify_storage_proofs`, `SPV::verify`, `lc_proof_verifier` and `check_nofn_correctness` validate Citrea-side state and nofn keys, not Bitcoin UTXO liveness; there is no database uniqueness constraint that requires the outpoint to be unspent, only that the same `deposit_outpoint` isn't inserted twice.

### Impact Explanation
The direct effect is a move-to-vault UTXO that can never be spent/confirmed, matching the Critical impact category "a move-to-vault UTXO permanently frozen." If bridge accounting (deposit bookkeeping/finalization) treats the deposit as recorded once N-of-N signs are collected and the movetx is broadcast, funds that were never actually locked in the vault can be treated as bridged, creating a permanent accounting/liveness mismatch between Bitcoin state and bridge state. This is repeatable per deposit attempt at the attacker's discretion (only cost is Bitcoin transaction fees), and does not require a compromised verifier, operator, or aggregator.

### Likelihood Explanation
Preconditions are minimal: the attacker needs to fund a deposit transaction with an RBF-signaled or otherwise replaceable input, submit `NewDeposit`/`DepositParams` to the public aggregator gRPC endpoint, and race a conflicting spend of the same outpoint against the verifiers'/aggregator's asynchronous multi-round signing protocol (nonce generation, `deposit_sign`, `deposit_finalize`). This requires no protocol key material and costs only ordinary Bitcoin fees for the deposit and the conflicting/replacement transaction. Feasibility depends on the length of the window between `is_deposit_valid` checks in `deposit_sign` and `deposit_finalize` and how much time elapses in a live multi-verifier round — this is plausible but not instantaneous, and I could not fully verify from the indexed code the exact timing bounds of the round-trip (`collect_operator_sigs`, nonce distribution, etc.) that would determine practical exploitation speed against mempool propagation of a replacement transaction.

### Recommendation
In `Verifier::is_deposit_valid` (`core/src/verifier.rs`), after confirming the deposit transaction and output match, add an explicit unspent check on `deposit_outpoint` (e.g., using `is_utxo_spent`/`get_tx_out` with `include_mempool = false`) both in `deposit_sign` and again immediately before finalization/broadcast in `deposit_finalize`, rejecting the deposit if the UTXO is already spent. Consider re-validating unspentness one more time immediately before the aggregator broadcasts the move-to-vault transaction in `Aggregator::create_movetx`.
