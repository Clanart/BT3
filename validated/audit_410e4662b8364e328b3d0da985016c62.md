### Title
Forfeit mechanism in mWOMSVBaseRewarder is broken, permanently freezing/misdistributing yield - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` is intended to compute a forfeit amount that is deducted from a user's rewards on claim and redistributed to remaining stakers, mirroring `vlMGPBaseRewarder._calExpireForfeit`, which calculates `rewardableAmount` from an external ratio (`vlMGP.getRewardablePercentWAD(_account)`) and only pays out the rewardable portion. In `mWOMSVBaseRewarder`, the equivalent function hardcodes `rewardableAmount = _amount`, so `forfeitAmount` is mathematically always `0`. [1](#0-0) [2](#0-1) 

### Finding Description
`_calExpireForfeit` in `mWOMSVBaseRewarder.sol` is:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
```
Because `rewardableAmount` is set equal to `_amount` unconditionally, `forfeitAmount = _amount - rewardableAmount` is always `0`, regardless of the caller `_account` or any lock/slot state. Every call to `_sendReward` (line 362-376) and `getReward`/`getRewards` therefore transfers the full `userRewards[...]` amount to the user and never routes any portion into `_queueNewRewardsWithoutTransfer`, which is the function responsible for redistributing forfeited yield back into `rewardPerTokenStored` for the benefit of the remaining stakers. [3](#0-2) [4](#0-3) 

This is the same class of bug as the referenced report: a state/logic path that is supposed to gate/reduce a payout based on a variable never gets a real value plugged in (in the Bond report it was a missing setter for `createFeeDiscount`; here it's a hardcoded self-assignment that mathematically zeroes the intended penalty calculation), so the discount/forfeit feature can never activate. The sibling contract `vlMGPBaseRewarder` shows what the correct implementation looks like — it derives `rewardableAmount` from `vlMGP.getRewardablePercentWAD(_account)`, an external, per-account, time-dependent ratio — confirming that the `mWOMSVBaseRewarder` version is missing the equivalent computation entirely. [5](#0-4) 

### Impact Explanation
The forfeit-and-redistribute mechanism exists so that unclaimed/early-exit portions of yield are captured and redistributed as extra `rewardPerTokenStored` to the pool of remaining mWOMSV stakers (`_queueNewRewardsWithoutTransfer`). Because the calculation is dead code that always returns zero, this redistribution never occurs for the mWOMSV reward pool: legitimate stakers who are entitled to receive forfeited yield from other users' early exits permanently never receive it — that yield leaks out fully to every claimant instead of being shared, indefinitely (not a temporary freeze but a permanent loss of the redistribution mechanism for the pool's remaining stakers). This is a permanent, protocol-wide miscalculation reachable by any ordinary staker simply calling `getReward`/`getRewards`, with no privileged action required to trigger it.

### Likelihood Explanation
High likelihood: this triggers on every single reward claim from `mWOMSVBaseRewarder` by any unprivileged wallet holding mWOMSV rewards — there is no special precondition, admin action, or exceptional state needed. The bug is deterministic and always present due to the hardcoded self-assignment.

### Recommendation
Implement the intended forfeit calculation analogous to `vlMGPBaseRewarder._calExpireForfeit`, deriving `rewardableAmount` from the actual unlock/vesting state of the mWOMSV holder (e.g., via a rewardable-percent function specific to mWOMSV lock/slot state) rather than assigning it equal to `_amount`.

### Proof of Concept
1. Any staker deposits mWOMSV and reward tokens are queued via `queueNewRewards`/`donateRewards`.
2. Staker calls `getReward`/`getRewards` (via MasterMagpie), invoking `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`.
3. `_calExpireForfeit` returns `0` in all cases because `rewardableAmount = _amount` is set before any comparison, so `forfeitAmount = _amount - rewardableAmount = 0` always.
4. The full `userRewards[...]` amount is transferred to the user; `_queueNewRewardsWithoutTransfer` (the redistribution path) is never invoked with a nonzero value, so remaining stakers never receive any redistributed forfeited yield. [6](#0-5)

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;

            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**mWOMSVDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
