### Title
Missing lower-bound validation on `Kip71GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`, `kaiax/gov/param.go`)

### Summary
`NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget` as a divisor in two branches. The governance parameter `Kip71GasTarget` that supplies this value uses `noopFormatChecker`, unlike the sibling parameter `Kip71BaseFeeDenominator`, which explicitly rejects zero. A governance vote setting `GasTarget` to `0` reaches this unguarded division and panics every node validating or assembling a block, mirroring the external report's "unchecked corner case in a bounded/divisor computation used by core protocol logic" bug class.

### Finding Description
`NextMagmaBlockBaseFee` divides by `gasTarget` when the parent block's gas usage differs from the target: [1](#0-0) 

Specifically:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // divides by gasTarget
``` [2](#0-1) 
and the symmetric decrease branch: [3](#0-2) 

The code explicitly guards against `BaseFeeDenominator == 0` by substituting a fallback value ("To avoid panic, set the fluctuation range small"), showing the authors were aware that a zero divisor causes a panic: [4](#0-3) 

However, no equivalent guard exists for `gasTarget`. If `GasTarget == 0` and `parentGasUsed > 0`, the code takes the `parentGasUsed > gasTarget` branch and calls `x.Div(x, new(big.Int).SetUint64(0))`, which panics at runtime in Go's `math/big` package (unlike Solidity's `SafeMath.div`, which reverts gracefully — this crashes the process).

The `GasTarget` value originates from the governance parameter `Kip71GasTarget`, whose format checker is a no-op that performs no validation at all: [5](#0-4) 

Compare this to `Kip71BaseFeeDenominator`, which is protected: [6](#0-5) 

This is a direct analog of the external report: an unchecked corner case (a divisor allowed to reach zero) in a formula that governs a core protocol value (the base fee / KIP-71 dynamic gas pricing), reachable through the governance parameter path, causing a hard failure of the computation.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked during block validation (`blockchain/block_validator.go`) and block assembly (`work/worker.go`, `blockchain/chain_makers.go`), and in transaction-pool/gas-price logic (`blockchain/tx_pool.go`, `node/cn/gasprice/*`). A governance vote setting `GasTarget` to `0` — once activated — would cause **every node** to panic while computing or verifying the base fee for the very next block whose gas usage is nonzero, since this is unconditionally executed on the mainline block-processing path. Unlike a Solidity `revert`, a Go panic in this context crashes the node process (or at minimum halts block processing network-wide if unrecovered), producing a chain-wide denial of service rather than a single blocked transaction — a higher-severity variant of the pattern in the original report.

### Likelihood Explanation
Reaching this bug requires a successful governance vote to set `Kip71GasTarget` to `0`. This requires governance-level access, but the "governance parameters" attack surface is explicitly listed as in-scope in the rules provided. Given the asymmetry with `Kip71BaseFeeDenominator` (which is validated) versus `Kip71GasTarget` (which is not), this is a genuine, provable validation gap rather than a speculative issue — the code explicitly demonstrates awareness of this exact class of bug for the denominator but omits it for the target.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) analogous to the one used for `Kip71BaseFeeDenominator`, rejecting `0` (and any other value that could zero out `min(parentGasUsed, upperGasLimit)` interactions leading to division by zero). Additionally, add a defensive runtime guard inside `NextMagmaBlockBaseFee` itself — mirroring the existing `BaseFeeDenominator == 0` fallback — so that `gasTarget == 0` cannot reach the `Div` call regardless of how the value was set (config file, hard-coded default, or governance).

### Proof of Concept
1. Governance votes to set parameter `Kip71GasTarget` to `0` (the `FormatChecker` at `kaiax/gov/param.go:324-333` is a no-op and will accept it, unlike `Kip71BaseFeeDenominator` which is protected at `kaiax/gov/param.go:310-322`).
2. Once the new `ParamSet` becomes active, any block whose `parentGasUsed > 0` is processed via `ToKip71Config()` → `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)`.
3. Since `parentGasUsed (>0) > gasTarget (0)`, execution enters the increase branch at `params/kip71_config.go:97-109`, executing `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`.
4. `big.Int.Div` by zero panics at runtime, crashing block validation/assembly on every node that processes this block — halting the chain.
