### Title
`create_payout_txhandler` OP_RETURN operator attribution can be hijacked by anyone who front-runs the mempool spend of the withdrawal UTXO - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The Payout transaction's operator attribution is entirely determined by an unauthenticated OP_RETURN output (`operator_xonly_pk.serialize()`) appended by whoever assembles the final transaction, while the withdrawal-to-payout binding in the database is keyed only on which transaction spends the withdrawal outpoint on-chain. Since the OP_RETURN output is not covered by the user's `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` signature (which only commits to input 0 and output 0), anyone can graft a different, real operator's pubkey onto a transaction that reuses O's signed input/output and get that operator credited with the reimbursement instead.

### Finding Description
The claimed binding is: `stored operator_xonly_pk for withdrawal i == identity of the party who funded output 0 of the payout tx that spends withdrawal_utxo(i)`.

`create_payout_txhandler` builds the Payout tx with input 0 = withdrawal outpoint (`SpendPath::KeySpend`, signed by the user's `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` signature), output 0 = the withdrawer's `TxOut`, and output 2 = `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))` [1](#0-0) . Because the sighash is `SinglePlusAnyoneCanPay`, the signature only commits to input 0 and output 0; the OP_RETURN operator-pubkey output and any additional inputs/fee are unconstrained and can be freely substituted by anyone who can see the broadcast (mempool) or the signed data, as confirmed by the verification comment in `Operator::withdraw` [2](#0-1) .

On the verifier side, the association between a withdrawal index and its "payout tx" is made purely by which transaction is observed spending the DB-recorded `withdrawal_utxo_txid`/`withdrawal_utxo_vout`, via a join against `bitcoin_syncer_spent_utxos`, with no cross-check against who funded/authored the transaction: [3](#0-2) 

`Verifier::update_finalized_payouts` then reads whichever transaction actually confirmed for that outpoint, extracts the OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`, and stores that pubkey as the payer operator with no additional validation that this operator actually funded the outputs: [4](#0-3) 

`PayoutCheckerTask::run_once` for operator P then picks up the row via `get_first_unhandled_payout_by_operator_xonly_pk(P)` and calls `Operator::handle_finalized_payout`, which allocates one of P's own kickoff connectors and proceeds through the kickoff/Reimburse flow to pay P the `bridge_amount`: [5](#0-4) [6](#0-5) 

Attacker's exact transaction: copy input 0 (withdrawal outpoint + witness containing O's valid `SinglePlusAnyoneCanPay` signature) and output 0 (withdrawer's `TxOut`) verbatim from O's broadcast Payout tx, add attacker-funded inputs to cover the output value and fee, and replace output 2 with `op_return_txout(P.serialize())` instead of O's pubkey. This new transaction is fully valid Bitcoin-consensus-wise (the signature only constrains input 0/output 0), and if it confirms first (higher feerate), it becomes "the payout tx" for withdrawal `i` as far as `get_payout_txs_for_withdrawal_utxos` is concerned — permanently, since O's now-conflicting transaction can never confirm afterward.

None of the existing guards catch this: `SECP.verify_schnorr` in `Operator::withdraw`/`sign_optimistic_payout` only checks the user's signature over input 0/output 0, not who else contributed inputs or what the OP_RETURN says; `Verifier::is_kickoff_malicious` only checks that the OP_RETURN's operator pubkey matches the kickoff's claimed operator, which is trivially true here since the attacker set output 2 to P's own (real, correctly-derived) pubkey [7](#0-6) ; there is no code path anywhere that ties the OP_RETURN pubkey to provenance of the funding inputs.

### Impact Explanation
Operator P is reimbursed `bridge_amount` from the bridge (via Kickoff → Reimburse flow) for a payout it never funded, while the actual funder (the attacker) receives no credit or repayment, and honest operator O — despite having correctly and lawfully constructed and broadcast the Payout tx first — is permanently unable to be attributed or reimbursed for that withdrawal index because the DB/consensus-state binding is keyed on the confirmed spend of the withdrawal outpoint, which is now the attacker's substituted transaction. This is repeatable for every registered withdrawal that has an outstanding unconfirmed Payout tx in the mempool, against any real active operator the attacker chooses to name in the substituted OP_RETURN, matching the Critical category "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
Preconditions are attacker-reachable without any privileged role: a withdrawal must already be registered (attacker can even initiate the Citrea `withdraw` call itself if desired, or simply wait for any real withdrawal), and O's Payout tx must be observable in the mempool before it confirms (the attacker only needs to see the broadcast transaction, extract input 0's witness/signature and output 0). The attacker must front the withdrawal amount plus a higher fee than O's transaction to win the race, which is a real BTC cost but requires no key compromise, no majority hashrate, and no privileged access — feasible with standard mempool-monitoring and RBF/relay tooling.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the transaction's actual funding, e.g., have the withdrawal-authorization signature (or a separate commitment already known to verifiers, such as the operator pubkey chosen at `Operator::withdraw` time and stored in the DB when the payout is first prepared) be checked against the operator pubkey embedded in whichever transaction ultimately spends `withdrawal_utxo`, or require the OP_RETURN pubkey to be committed under the same sighash as the user's signature (e.g. by using `SIGHASH_ALL` for the payout, or otherwise covering output 2). Alternatively, reject/ignore any confirmed spend of `withdrawal_utxo` whose OP_RETURN pubkey does not match a pubkey pre-registered by the operator that constructed and requested that specific payout.

### Proof of Concept
`cargo test` plan (no mainnet/live Citrea, using existing regtest E2E test harness under `core/src/test`):
1. Register a withdrawal (via Citrea mock client) and have operator O call `withdraw` to build/broadcast O's Payout tx (input 0 = W, output 0 = withdrawer TxOut, output 2 OP_RETURN = O's xonly pk), do not mine it.
2. Extract O's broadcast raw tx; construct a second raw transaction with an attacker-controlled wallet: copy input 0 (with O's `witness`/signature intact) and output 0 verbatim, add attacker-funded input(s) sufficient to cover value+fee, set output 2's OP_RETURN to a second real operator P's xonly pk, and set a higher feerate.
3. Broadcast the attacker's tx and mine it (confirming before O's now-conflicting tx, which the mempool will evict).
4. Advance blocks past finality depth so `update_finalized_payouts` runs; assert `get_payout_txs_for_withdrawal_utxos` / DB shows the withdrawal's payer operator xonly pk == P's key (not O's), i.e. `db.get_payout_info_from_move_txid(...).0 == Some(P_xonly_pk)`.
5. Run `PayoutCheckerTask::run_once` for P; assert it returns `true` and `db.get_handled_payout_kickoff_txid(payout_txid)` returns Some for P's kickoff, and subsequently that P's Reimburse tx confirms on regtest, crediting P with `bridge_amount` while O's DB entry for the same deposit shows no payer/no reimbursement path.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
