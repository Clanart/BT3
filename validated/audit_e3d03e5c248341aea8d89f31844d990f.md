### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new` enables CPU-exhaustion DoS via crafted `ThresholdKeys::read` input - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The ReDoS bug class (a small attacker-controlled input triggering disproportionate CPU work) maps onto `ThresholdKeys::read` → `ThresholdKeys::new`. Deserialization accepts attacker-chosen `t`/`n` (each a `u16`, up to 65535) and `ThresholdKeys::new` then computes the group key by evaluating a Lagrange `interpolation_factor` for each of the `t` first participants, where each factor is itself an O(t) loop over the participant set. The result is Θ(t²) field multiplications plus `t` field inversions — ~4.3 billion field operations for a ~4 MB input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the byte stream, then reads `n` verification shares and calls `ThresholdKeys::new` with `ThresholdParams::new(t, n, i)` [1](#0-0) .

Inside `ThresholdKeys::new`, the group key is computed by summing, for every participant in `1..=t`, `verification_shares[i] * interpolation.interpolation_factor(i, &t)` [2](#0-1) . For `Interpolation::Lagrange`, `interpolation_factor` loops over all `t` included participants performing a field multiply for numerator and denominator, and finishes with a full field inversion `denom.invert().unwrap()` [3](#0-2) .

The same O(k²) pattern reappears in `ThresholdKeys::view`, which calls `interpolation_factor` once per included signer — any subsequent signing attempt over a large reconstructed set repeats the quadratic blowup [4](#0-3) .

### Impact Explanation
An unprivileged party supplying bytes to `ThresholdKeys::read` (an allowed untrusted entry point) with `t = n = 65535` forces ~65k field inversions (each an exponentiation over the scalar field) plus ~4.3·10⁹ field multiplications — minutes of single-threaded CPU per invocation — while the input itself is only ~4 MB. Repeated submissions amplify into sustained CPU exhaustion of the process performing the deserialization/reconstruction. The available surface also includes `view`/`sign` on legitimately-large parameter sets, where the same quadratic interpolation applies per signing session.

### Likelihood Explanation
No bound below `u16::MAX` is enforced on `t`/`n` inside `ThresholdKeys::read`/`new`; the only checks are `t <= n`, non-zero participant, and share count matching `n` [5](#0-4) . Triggering requires only delivering the serialized blob; no valid cryptographic content is needed — the shares don't have to correspond to a real key, since the quadratic work happens unconditionally during group-key derivation.

### Recommendation
Cap `n`/`t` at deserialization (e.g., the real protocol maximum such as `MAX_KEY_SHARES_PER_SET`), or compute Lagrange denominators in O(t) via a prefix/suffix product with a single batched inversion instead of a per-participant inversion loop.

### Proof of Concept
Serialize a `ThresholdKeys` blob: `id_len || C::ID || t=0xFFFF || n=0xFFFF || i=1 || interpolation=1 (Lagrange) || 32-byte secret_share || 65535 encoded group elements` (any canonical points, e.g., the generator repeated). Feeding it to `ThresholdKeys::<C>::read` causes `ThresholdKeys::new` to execute 65535 iterations of `interpolation_factor`, each iterating 65535 participants and performing one `invert()` — quadratic CPU burn per ~4 MB of input, directly analogous to ReDoS amplification.
