### Title
Missing "already-filled" guard in `_cancelFromDest` allows a filled order to be cancelled, causing `RefundEscrow` and `RedeemEscrow` to race and pay the wrong beneficiary - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromDest` never checks whether `_filled[commitment]` is already non-zero (i.e., the order was already filled by a solver via `_fillCrossChain`) before overwriting it and dispatching a `RefundEscrow` message to the source chain. Since both `_fillCrossChain` (dispatching `RedeemEscrow`) and `_cancelFromDest` (dispatching `RefundEscrow`) can independently fire cross-chain messages for the same `commitment`, and the source-chain `_withdraw` function is a simple "first message wins" drain of `_orders[commitment][token]`, whichever message reaches `onAccept` first finalizes the escrow to that message's beneficiary while the second one reverts with `UnknownOrder`.

### Finding Description
`_fillCrossChain` (evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171) sets `_filled[commitment] = msg.sender` at line 92, transfers output tokens to the beneficiary, then dispatches a `RedeemEscrow` post request to the source chain.

`_cancelFromDest` (lines 240-267) allows any caller once `order.deadline < _blockNumber()` (line 241), and unconditionally executes `_filled[commitment] = address(uint160(uint256(order.user)))` at line 245, followed by dispatching a `RefundEscrow` post request — **without ever checking whether `_filled[commitment]` is already set** (i.e., whether the order was already filled). [1](#0-0) 

On the source chain, `onAccept` routes both `RedeemEscrow` and `RefundEscrow` to the same `_withdraw` function without any ordering or mutual-exclusion check between the two message kinds: [2](#0-1) 

`_withdraw` simply decrements `_orders[commitment][token]` and pays whichever `beneficiary` is in the incoming message, reverting with `UnknownOrder` only if the escrow is already zero: [3](#0-2) 

Because a solver fills the order on the destination chain right at/after the deadline, and `_cancelFromDest` is deliberately open to "anyone" post-deadline specifically to help the user (per the doc comment "After the deadline, anyone may trigger the cancellation"), a race window exists: if a solver fills at block `deadline+1` and a `_cancelFromDest` call also lands (e.g., relayed independently, or the two transactions land in the same or nearby blocks before either cross-chain message is delivered/proven on the source chain), two competing withdrawal messages (`RedeemEscrow` beneficiary = solver, `RefundEscrow` beneficiary = `order.user`) are both dispatched for the same `commitment`. Whichever message's proof is finalized and delivered to the source chain first drains `_orders[commitment][token]` to its beneficiary; the second message then reverts with `UnknownOrder` in `_withdraw` (line 401), permanently failing since there's no retry path that changes outcome. If the `RefundEscrow` wins the race, the solver has already delivered output tokens to the user's beneficiary on the destination chain but receives nothing on the source chain — the escrow is stolen from the solver.

This breaks the "exactly-once, rightful-beneficiary" invariant because `_cancelFromDest` should be blocked once `_filled[commitment]` indicates the order was already filled by a solver (non-`order.user` value), similar to how `onGetResponse`'s cancel-from-source path checks the destination `_filled` slot via a storage proof before refunding (lines 319-324). `_cancelFromDest`, unlike `_cancelFromSource`, has no equivalent check against a prior fill.

### Impact Explanation
A solver who legitimately delivers output tokens to a user's beneficiary can lose the escrowed input tokens to a wrongful refund to the same user, resulting in direct loss of funds for the solver and duplicate/incorrect settlement of the order (the user effectively receives both the destination output tokens and the source-chain refund). This matches the "stealing or loss of funds" / "wrong beneficiary" / "duplicate settlement" impact categories in scope.

### Likelihood Explanation
Likelihood depends on the race window: it requires a fill transaction and a "cancel" transaction (callable by anyone once `deadline < _blockNumber()`) to both be dispatched cross-chain for the same commitment before either message is finalized on the source chain, with the refund message being processed first. Because cancellation is deliberately permissionless post-deadline and fills can also land right around/at the deadline boundary, this is plausible without requiring any privileged or malicious relayer/prover behavior — an ordinary unprivileged actor (or even an honest but hasty relayer for the cancel path) can trigger it by calling `_cancelFromDest` on an order that was just filled, since there is no on-chain state preventing that call.

### Recommendation
In `_cancelFromDest`, check that `_filled[commitment] == address(0)` before proceeding (mirroring the guard's absence being the root cause), reverting with `Filled()` if the order was already filled by a solver. This closes the race entirely by making the destination-chain fill state authoritative and mutually exclusive with cancellation, rather than relying on race-dependent delivery order of two independently dispatched cross-chain messages.

### Proof of Concept
1. User places a cross-chain order with `deadline = D`.
2. At block `D+1`, Solver calls `fillOrder` → `_fillCrossChain`, which sets `_filled[commitment] = solver` and dispatches `RedeemEscrow(commitment, beneficiary=solver)` to the source chain.
3. Also at/after block `D+1`, since `order.deadline < _blockNumber()`, any unprivileged caller invokes `_cancelFromDest(order, options, commitment)`. There is no check of the current `_filled[commitment]` value, so it overwrites `_filled[commitment] = order.user` (line 245) and dispatches `RefundEscrow(commitment, beneficiary=order.user)` to the source chain.
4. Both messages traverse Hyperbridge consensus/state proofs independently; suppose `RefundEscrow` is proven/delivered to `onAccept` on the source chain first.
5. `_withdraw(body, isRefund=true, finalize=true)` executes: `_orders[commitment][token]` is drained to `order.user` and `_filled[commitment]` is set to `order.user`.
6. When the earlier-dispatched `RedeemEscrow` message is later delivered, `_withdraw` finds `_orders[commitment][token] == 0` and reverts with `UnknownOrder` (evm/src/apps/intentsv2/IntentsBase.sol:401).
7. Result: solver already paid the user's beneficiary on the destination chain but receives no input-token payout on the source chain — escrow wrongfully refunded to `order.user` instead of the rightful solver beneficiary. [4](#0-3) [3](#0-2)

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
