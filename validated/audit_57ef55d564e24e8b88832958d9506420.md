## Analysis

The external report's core broken invariant: **a contract that must sometimes hold bridged funds pending further processing, but which also allows an arbitrary/uncontrolled call to be executed *as that contract*, lets any unprivileged actor issue a call that drains whatever balance is currently sitting in it** (in the original bug: an unrestricted target in `relayMessage` let an attacker force an `approve` from the messenger).

The direct local analog is Hyperbridge's `CallDispatcher` contract, which is deployed **once per chain and shared across multiple apps** (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`/`IntentsBase`) — confirmed by the deployment scripts and docs. Its `dispatch()` function has **no access control whatsoever** and executes attacker-supplied `Call[]` with the `CallDispatcher` itself as `msg.sender`: [1](#0-0) 

By design, multiple apps route bridged tokens/ETH *through* this shared dispatcher (setting the bridge `to` field to the `CALL_DISPATCHER` address so it can execute solver/DEX calls that spend the tokens): [2](#0-1) 

`IntentsBase._execute` explicitly acknowledges that the dispatcher can be left holding a balance after running solver-supplied calls, and only sweeps back the balances of the tokens explicitly listed as `order.output.assets` for that specific order: [3](#0-2) 

Because the sweep is scoped only to the known `order.output.assets[0..outputsLen)`, any *other* token or intermediate balance the dispatcher ends up holding after a solver's arbitrary `order.output.call` (e.g. a Uniswap route that yields excess of an unlisted token, dust from a multi-hop swap, or a partial-fill remainder) is never recovered by the protocol and remains sitting on the `CallDispatcher`. The same custody pattern applies to `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept`, which forward `message.data` straight to the shared dispatcher: [4](#0-3) 

Since `CallDispatcher.dispatch()` is public and unauthenticated, and the dispatcher's own balance is not tied to any specific caller or app, **any unprivileged account can call `CallDispatcher.dispatch()` directly** with a `Call{to: <leftoverToken>, data: transfer(attacker, dispatcher.balanceOf(dispatcher))}` and steal any residual ETH/ERC20 balance sitting on the shared dispatcher — regardless of which app or order left it there. This requires no malicious relayer, prover, or peer; it is a pure public-entrypoint fund-theft path exactly analogous to the reported messenger bug, where the fix was to restrict what the privileged holder-contract could be made to call, or restrict who can drive its arbitrary-call execution.

### Title
Unrestricted, Permissionless `CallDispatcher.dispatch()` Allows Theft of Any Residual Funds Left on the Shared Dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, unauthenticated utility contract used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`IntentsBase` to execute attacker/solver-supplied calls while temporarily custodying bridged tokens or native ETH. Its `dispatch()` entrypoint has no caller restriction and executes calls with the dispatcher itself as `msg.sender`. Any token or ETH balance that ends up parked on the dispatcher and is not swept back by the calling app in the same transaction (e.g. unlisted intermediate/output tokens from a solver's swap route in `IntentsBase._execute`) can subsequently be drained by any unprivileged account, since they can call `dispatch()` themselves with a `Call` transferring out the dispatcher's balance.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry with no access control on who may invoke `dispatch()` [5](#0-4) . The contract also has a `receive()` explicitly meant to accept ETH [6](#0-5) .

Multiple apps deliberately route funds to this shared address as an intermediate holder before executing user/solver-controlled calls:
- `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept` mint/unlock tokens to a beneficiary that can be set to the `CallDispatcher` address, then forward `message.data` to it [7](#0-6) .
- `IntentsBase._execute` dispatches solver-supplied `order.output.call` through the same dispatcher, then attempts to sweep back only the balances of tokens explicitly listed in `order.output.assets` [8](#0-7) .

Because the sweep logic is scoped to a fixed, known asset list per order/message, any other asset that ends up on the dispatcher (a different token produced by a DEX route, WETH remainder from a partial unwrap, excess from slippage, etc.) is left unswept. Since `CallDispatcher` is a single shared instance across apps (per the TRON and mainnet deployment scripts), and its `dispatch()` is fully permissionless, any external account can call it directly with `Call{to: <leftoverToken>, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(leftoverToken).balanceOf(dispatcher))}` to seize that balance — the dispatcher has no owner, no allow-list of callers, and no notion of "whose funds these are."

This mirrors the reported bug's exact broken invariant: a contract expected to only transiently hold funds pending a follow-up step, whose arbitrary-call execution path is not restricted against draining its own balance to an attacker-chosen destination.

### Impact Explanation
Any leftover ETH or ERC20 balance temporarily parked on the shared `CallDispatcher` (from `HyperFungibleToken`, `WrappedHyperFungibleToken`, or `IntentGatewayV2`/`IntentsBase` flows) can be permanently stolen by any unprivileged account, satisfying the "stealing or loss of funds" and "unauthorized transaction or execution" impact categories. Because the dispatcher is shared across all apps that use it on a given chain, the blast radius covers every app configured with the same `CallDispatcher` address.

### Likelihood Explanation
No privileged actor, relayer, prover, or peer collusion is required — the attacker only needs to observe (or predict) that the dispatcher holds a non-zero balance (e.g., after a solver's swap route produces an unlisted token, or mid-execution before/if a sweep step is skipped) and submit a single permissionless `dispatch()` call. The likelihood scales with how often solver-supplied `Call[]` in `IntentsBase._execute` or cross-chain `data` payloads in `HyperFungibleToken`/`WrappedHyperFungibleToken` produce token balances outside the tracked/swept asset list.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by pre-authorized app contracts (e.g., an allow-list of configured callers set at construction/admin time), and/or make the dispatcher a per-call, ephemeral/disposable proxy (e.g., minimal proxy created and destroyed per invocation) so no shared balance can persist between unrelated calls. Additionally, harden the sweep logic in `IntentsBase._execute` (and the HFT/WHFT `onAccept` dispatch paths) to sweep the dispatcher's *entire* balance of any token touched by the executed calls, not just the pre-declared `order.output.assets` list.

### Proof of Concept
1. A solver fills an order via `IntentGatewayV2`/`IntentsBase`, and `order.output.call` performs a multi-hop swap or DEX interaction that leaves a residual balance of a token not present in `order.output.assets` on the shared `CallDispatcher` (see the sweep loop bound to `outputsLen`/`order.output.assets` at [9](#0-8) ).
2. Attacker observes the leftover balance via `IERC20(leftoverToken).balanceOf(callDispatcherAddress)`.
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — this succeeds because `dispatch()` has no caller restriction [5](#0-4) .
4. The leftover tokens are transferred to the attacker, with `CallDispatcher` as the (unrestricted) caller of `transfer`.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function _execute(Order calldata order, uint256 outputsLen) internal {

        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
