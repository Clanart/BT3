### Title
Attacker-supplied `ReceivedOutput` can poison batched Bitcoin spends with an unspendable input - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the referenced UTXO exists or that its on-chain amount/script match the supplied values. `SignableTransaction::new` then treats every supplied `ReceivedOutput` as spendable and atomically incorporates all inputs into one transaction, so one forged input makes the entire signed transaction invalid.

### Finding Description
`ReceivedOutput::read` performs only scalar and Bitcoin consensus decoding; it does not bind the decoded outpoint to a confirmed transaction output. [1](#0-0)  `SignableTransaction::new` trusts `input.output.value` as available balance and copies `input.outpoint` directly into the transaction inputs. [2](#0-1) 

The later multisig check only verifies that the supplied prevout’s `script_pubkey` matches the key derived from the supplied offset; it does not verify the UTXO’s existence or committed amount against the blockchain. [3](#0-2)  Signing commits to all supplied prevouts with `Prevouts::All`, and completion produces one transaction containing every input. [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker can encode a `ReceivedOutput` containing a valid Serai-controlled script/offset pair but a nonexistent outpoint or an inflated amount. The wallet can sign the resulting transaction, but Bitcoin consensus will reject it because the input does not exist or the Taproot prevout amount does not match the actual UTXO. If payments are batched or processed FIFO, this single poisoned output invalidates the whole transaction and blocks otherwise valid payments behind it.

### Likelihood Explanation
The required script/offset pair can be copied from a legitimate deposit to Serai. The attacker can also make a real deposit first, then submit a forged encoding that changes its amount or outpoint while preserving the valid script relationship. Any caller that accepts untrusted serialized `ReceivedOutput` values and passes them into `SignableTransaction::new` reaches the issue.

### Recommendation
Do not treat `ReceivedOutput::read` as chain-validated input data. Require decoded outputs to be re-derived by `Scanner`, resolved against a confirmed block/transaction, and checked for exact `outpoint`, amount, `script_pubkey`, and spendability before entering the spendable-output pool. Reject malformed or unconfirmed outputs individually rather than allowing them to poison an entire batched transaction.

### Proof of Concept
1. Observe a legitimate Serai deposit and copy its valid `offset`/`script_pubkey` relationship.
2. Submit crafted bytes to `ReceivedOutput::read` containing:
   - the legitimate `offset`;
   - a `TxOut` with the legitimate Serai `script_pubkey` but an inflated `value`;
   - a fabricated `OutPoint`, or the real outpoint while retaining the inflated amount.
3. Pass the decoded value into `SignableTransaction::new` alongside payment outputs.
4. `SignableTransaction::new` accepts the forged amount and creates an input referencing the fabricated/mismatched outpoint.
5. `multisig`, signing, and `complete` succeed because they validate only the script relationship and signatures, not the UTXO’s actual existence or amount.
6. Broadcasting the completed transaction fails Bitcoin validation, invalidating every payment batched with the forged input.

  /// Read a ReceivedOutput from a generic satisfying Read.
  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
