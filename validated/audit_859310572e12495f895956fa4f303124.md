### Title
`_fetchRefspec` bypasses the network-operation concurrency guard, allowing an attacker-influenced PR-from-fork fetch to race with push/pull/fetch and corrupt repository refs/index - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop serializes all network git operations (`fetch`, `pull`, `push`) through a single per-repository lock, `withPushPullFetch`, which checks `state.isPushPullFetchInProgress` before allowing a new operation to start. [1](#0-0) 
However, `_fetchRefspec` — the code path used when a user opens/views a Pull Request that comes from a fork — explicitly does **not** go through `withPushPullFetch`, and the source code documents this as an intentional (but risky) exception: [2](#0-1) 

This is the closest Desktop analog to the Sherlock finding: a missing reentrancy/mutual-exclusion guard around a state-mutating operation (deposit/mint in the Solidity report ≈ fetch/checkout writing refs and the index here), where an attacker-influenced input (a PR head ref/refspec from a fork) can be triggered while another privileged operation on the same repository is in flight.

### Finding Description
Every other network operation (`_pull`, `_fetch`, `_fetchRemote`, and the push path) is wrapped in `withPushPullFetch`, which sets `isPushPullFetchInProgress` and refuses to start a second concurrent operation: [1](#0-0) [3](#0-2) 

`_fetchRefspec`, used for PR-from-fork preview/checkout flows, calls `gitStore.fetchRefspec(refspec)` directly without acquiring that lock, and the refspec ultimately reaches `git fetch <remote> <refspec>` in `fetchRefspec` (`app/src/lib/git/fetch.ts`): [4](#0-3) 
`GitStore.fetchRefspec` loops over all configured remotes and issues the fetch against each one via `performFailableOperation`, which only guards against *another* fetchRefspec call on the same `GitStore`/queue, not against a concurrently-running push/pull/fetch initiated from `withPushPullFetch` (since that's a different gate entirely): [5](#0-4) 

This flow is directly reachable from an attacker-controlled deep link: `x-github-client://openRepo/.../pull/<n>` opens a PR (`openPullRequestFromUrl`) and ultimately calls `_checkoutPullRequest` → `_findPullRequestBranch`, which can add a new remote for the fork (`addRemote`) and fetch it (`_fetchRemote`) or, via other flows, `_fetchRefspec`: [6](#0-5) [7](#0-6) 

Because a fork's owner, clone URL, and head ref name are all attacker-supplied (an attacker opens a PR from their own fork against a public repo, or crafts a deep link pointing at that PR), the refspec/remote used in `_fetchRefspec` is effectively attacker-controlled input feeding into a `git fetch` invocation that is not protected by the same mutual-exclusion state as ordinary pushes/pulls/fetches.

### Impact Explanation
If a user triggers a normal push/pull/fetch (e.g. clicking "Push origin") while simultaneously (or via a background/auto-fetch or a maliciously timed deep-link-triggered PR view) `_fetchRefspec` runs concurrently, both operations write to the same `.git` directory (packed-refs, loose refs, FETCH_HEAD, index/objects) without app-level serialization. This can lead to:
- Interleaved git subprocess writes to refs, producing a repository state that doesn't match what the user intended to push/pull (silent corruption of what gets committed/pushed, analogous to the "distribution of shares" corruption in the reentrancy report).
- A window where `_refreshRepository`, which is called at the end of both flows, reads a transiently inconsistent ref/branch state and updates the UI's `tip`/branch selection to reflect the attacker's fork ref rather than the legitimate operation the user initiated, potentially causing the user to unknowingly commit on top of or push to an unexpected ref.

The impact is capped by git's own internal locking (`.git/index.lock`, ref-transaction locks) which generally prevents literal file corruption, but the application-level race can still produce user-facing state confusion, failed/partial fetches surfaced as unrelated errors, and unexpected branch/remote state changes tied to attacker-controlled fork data — closely mirroring the original finding's core problem: an unguarded state-mutating entry point that can be invoked while another mutating operation on the same object is in progress.

### Likelihood Explanation
The comment in the source code itself acknowledges the guard is intentionally skipped for this path, confirming this isn't accidental dead code but a known gap ("This might require some rework in the future to chain these actions"): [8](#0-7) 
The PR-from-fork flow is reachable via ordinary user action (viewing/opening a PR from any public fork, or a maliciously crafted `x-github-client://` deep link that a victim clicks), requiring only that the user has the target repository open in Desktop — no local access, elevated privileges, or leaked credentials are needed. Reliably winning the race requires timing (the user or a background task performing a push/pull/fetch at the same moment), which lowers likelihood from "high" to "medium," but the reachable path and attacker-controlled input are concretely demonstrable in the code.

### Recommendation
Route `_fetchRefspec` through the same `withPushPullFetch` (or an equivalent shared mutex keyed by repository) used by `_pull`/`_fetch`/push, queuing the refspec fetch instead of allowing it to run concurrently with other network git operations. If immediate execution is required for responsiveness when viewing a PR, serialize it behind the existing lock (await until any in-progress push/pull/fetch completes) rather than bypassing the guard entirely, and clearly validate/sanitize the refspec derived from PR/fork metadata before passing it to `git fetch`.

### Proof of Concept
1. Open a repository in GitHub Desktop that has a pending push or fetch (e.g., start a push to `origin` on a large repository so the operation takes a few seconds).
2. While the push/fetch progress bar is active (`isPushPullFetchInProgress = true`), trigger a PR-from-fork view/checkout — e.g., click an `x-github-client://openRepo/...&pr=<attacker-PR-number>` deep link pointing at a PR opened by an attacker from their own fork of the same repository (`openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`/`_fetchRefspec`). [6](#0-5) 
3. Observe that `_fetchRefspec`'s call to `gitStore.fetchRefspec` executes immediately, unaffected by the ongoing `isPushPullFetchInProgress` flag, because it does not call `withPushPullFetch`: [9](#0-8) 
4. Both git subprocesses run concurrently against the same working directory; the second `_refreshRepository()` call (from whichever operation finishes last) can overwrite the UI/app state (`branchesState.tip`, `currentRemote`) with values reflecting the attacker's fork fetch rather than the user's own push/pull, illustrating the corrupted/interleaved state resulting from the missing concurrency guard.

**Note:** I was unable to fully trace `withRefreshedGitHubRepository`'s internal locking behavior (its body wasn't retrievable within the available search results), so I cannot rule out that it provides some additional indirect serialization; this should be verified directly in `app/src/lib/stores/app-store.ts` before treating the race window as unconditionally exploitable.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }

/** Fetch a given refspec from the given remote. */
export async function fetchRefspec(
  repository: Repository,
  remote: IRemote,
  refspec: string
): Promise<void> {
  await git(['fetch', remote.name, refspec], repository.path, 'fetchRefspec', {
    successExitCodes: new Set([0, 128]),
    env: await envForRemoteOperation(remote.url),
  })
}

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
