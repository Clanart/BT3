### Title
Missing duplicate-receipt recheck in `EvmHost.dispatchIncoming` allows double execution of `onAccept` for the same request — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)` writes `_requestReceipts[commitment] = relayer` and then invokes the destination module's `onAccept` via a low-level `.call()`, but it never checks whether a receipt for that same commitment already exists before doing so. The Substrate/pallet-ismp implementation of the exact same step explicitly guards against this: `modules/ismp/core/src/handlers/request.rs` re-checks `host.request_receipt(&wrapped_req)` immediately before invoking `on_accept`, with a comment stating this is specifically to prevent a prior `on_accept` call in the *same batch* — including one that re-enters the handler — from getting invoked twice for the same request. `EvmHost.sol` has no equivalent recheck, so the invariant "a request's module callback is invoked at most once" is enforced on Substrate but not on EVM. This is the same overwrite-without-guard defect class as the `VotingEscrowSidechain._executeMessage()` report: a state-mutating entry point (`_setNewUserPosition`/here, module `onAccept`) can be invoked more than once for the same identity (user position / request commitment) because the guard state is written unconditionally rather than checked-then-set atomically against reentry.

### Finding Description [1](#0-0) 

`dispatchIncoming` for `PostRequest`:
1. Computes `commitment = request.hash()`.
2. Unconditionally sets `_requestReceipts[commitment] = relayer` (no `if (_requestReceipts[commitment] != address(0)) revert` guard).
3. Calls the destination module's `onAccept` via `.call(...)`.
4. Only rolls back the receipt (`delete`) if the call failed.

Compare to the Substrate handler, which explicitly documents and defends against this exact hazard: [2](#0-1) 

The Rust code re-reads `host.request_receipt(&wrapped_req)` right before invoking `cb.on_accept(...)`, specifically because "a prior request's on_accept in this same batch could have stored a receipt for this request (directly or by re-entering the handler), and we must not invoke on_accept a second time." `EvmHost.dispatchIncoming` performs the equivalent receipt write but has no analogous recheck-before-invoke step.

`dispatchIncoming` is restricted to `_hostParams.handler` (`restrict(_hostParams.handler)`), i.e. it is called by `HandlerV2` while processing a batch of requests verified under one membership proof. If:
- the destination module's `onAccept` implementation re-enters the host (directly, or indirectly through an external call it makes, e.g. `ICallDispatcher.dispatch()` in `HyperFungibleToken`/`ExtrinsicIntents`, or any third-party `IApp` a relayer can route requests to), and that reentrant path reaches `EvmHost.dispatchIncoming` again for the *same* `commitment` before the first call returns, or
- the handler's batch-processing loop (in `HandlerV2.sol`) does not itself deduplicate the requests being proven/dispatched in a single call (unverified from context available, but this is precisely the scenario the Substrate code was patched for),

then `onAccept` on the destination `IApp` executes twice for the same logical request, with no host-side state preventing the second invocation because the receipt is only ever set, never checked.

### Impact Explanation
For state-mutating `IApp` implementations that do not implement their own idempotency check beyond relying on the host's request-receipt uniqueness (which is the documented replay-protection primitive of ISMP), a second `onAccept` invocation directly duplicates value transfer:
- `HyperFungibleToken.onAccept` / `HyperFungibleTokenUpgradeable.onAccept` unconditionally call `_mint(beneficiary, message.amount)` on every invocation with no per-commitment "already processed" check of their own [3](#0-2) . A second `onAccept` call for the same bridged message would mint the transferred amount twice — pure token inflation / fund creation from a single burn-and-relay event, i.e. unauthorized fund creation via bridge custody logic.
- `ExtrinsicIntents.onAccept` (`RedeemEscrow`/`RefundEscrow`) is comparatively more resilient because `_withdraw` decrements `_orders[commitment][token]` and reverts with `UnknownOrder` once the escrow is exhausted [4](#0-3) , so a duplicate call there degrades to a revert/DoS rather than a double-payout — but this defense is incidental to this specific application's accounting, not a host-level guarantee, and is not present in every `IApp`.

This satisfies the bounty's "false state acceptance / unauthorized execution / duplicate settlement / stealing or loss of funds" categories, because the host's request-commitment receipt — the primitive every `IApp` is meant to be able to rely on for exactly-once delivery — can be bypassed without any malicious relayer, prover, or admin: the trigger is a destination `IApp`'s own external call path re-entering the host during the (unprotected) window between receipt-write and callback-completion.

### Likelihood Explanation
The precondition is a destination `IApp` (an ordinary user/protocol-deployed contract routed to via `request.to`) whose `onAccept` makes an external call before returning — which is completely normal (e.g. `ICallDispatcher.dispatch()` used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and the intents apps). No relayer collusion, prover compromise, or governance action is required — only that some registered/reachable `IApp` performs an external call reachable back to `EvmHost.dispatchIncoming` for the same commitment within the same call frame, or that the handler's batch verification/dispatch loop does not itself deduplicate commitments (the exact scenario the Rust code was hardened against). Given the Substrate side needed an explicit patch and comment for this, it is a demonstrated real attack surface for this codebase's ISMP request-processing model, and the EVM host mirrors the vulnerable pre-patch shape.

### Recommendation
Add the same check-before-write guard used in `modules/ismp/core/src/handlers/request.rs` to `EvmHost.dispatchIncoming` (and the analogous `GetResponse`/timeout dispatch functions): revert (or return without invoking the callback) if `_requestReceipts[commitment] != address(0)` before setting the receipt and calling `onAccept`. This restores the "receipt write and callback invocation are effectively check-then-act atomic per commitment" invariant on EVM to match the Substrate implementation, closing the reentrant/duplicate-batch double-invocation window.

### Proof of Concept
1. Deploy an `IApp` whose `onAccept` performs an external call to a helper contract before returning (a normal pattern, as used by `HyperFungibleToken.onAccept` via `ICallDispatcher.dispatch(message.data)`).
2. Craft `message.data` such that the dispatched call re-enters `EvmHost` in a way that results in `dispatchIncoming` being invoked again for the identical `PostRequest` (e.g., via a handler batch that verifies/dispatches the same commitment twice, or via a reentrant path back into the handler → host during the callback).
3. Observe `_mint(beneficiary, message.amount)` executing twice for a single bridged transfer, because `EvmHost.dispatchIncoming` never checked `_requestReceipts[commitment]` before writing it and invoking `onAccept` the second time — exactly the class of unconditional overwrite ("`_setNewUserPosition`/`_setNewTotalSupply`-style" reentry) flagged in the source report, materializing here as double token minting.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
