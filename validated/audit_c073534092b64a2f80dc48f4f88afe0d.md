### Title
Truncation of long diff lines bypasses hunk-line-count and selection-index consistency, allowing a crafted repository diff to desync partial-commit line selection - (File: app/src/lib/git/diff.ts, app/src/lib/patch-formatter.ts)

### Summary
GitHub Desktop's partial-commit ("stage this hunk/line") feature relies on a strict positional invariant: every `DiffLine` produced by `DiffParser.parseHunk` occupies a fixed index inside `hunk.lines`, and the UI's line-selection state is keyed purely by `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [1](#0-0) . The patch that is actually applied to the index via `git apply --cached` is rebuilt line-by-line from this same array in `formatPatch` [2](#0-1) . Nothing in `diffFromRawDiffOutput`/`buildDiff` re-validates that the hunk's declared `oldLineCount`/`newLineCount` still matches the number of `+`/`-`/context lines actually parsed, so any divergence between what git reports in the hunk header and what Desktop parses per-line silently propagates into the generated patch used for staging.

### Finding Description
`isDiffTooLarge` only inspects each already-parsed line's `text.length` against `MaxCharactersPerLine` (5000) to decide whether to fall back to `DiffType.LargeText` [3](#0-2) , but it never revalidates that `hunk.header.oldLineCount`/`newLineCount` still agrees with `hunk.lines.length`. `DiffParser.parseHunk` trusts the numbers in the `@@ -l,s +l,s @@` header purely for populating `rollingDiffBeforeCounter`/`rollingDiffAfterCounter` [4](#0-3) , and stops consuming lines the moment `parseLinePrefix(this.peek())` returns `null` (i.e., the next physical line doesn't start with `+`, `-`, ` ` or `\`) [5](#0-4) . Git can legitimately emit unified diffs where the counts in the header and the number of body lines are internally consistent from git's point of view but where a line's *content* embeds characters that Desktop's simplistic `\n`-based line splitter (`nextLine()`) or `diffHeaderRe` regex mis-tokenizes — for example content containing a literal `\n@@ -` sequence coming from a binary-looking but text-classified blob, or lines crafted so that stripping the "no newline" marker (`withNoTrailingNewLine`) attaches to the wrong preceding line when the previous line was itself an artifact of a miscount. When such a mismatch occurs, `hunk.unifiedDiffStart`/`unifiedDiffEnd` (used everywhere for line selection: `getDiffRowsFromHunk`, `formatPatch`, `formatPatchToDiscardChanges`, `findInteractiveDiffRange`) no longer point at the same logical line the user visually selected in the UI, because the UI renders from `hunk.lines` positionally [6](#0-5)  while `formatPatch` re-derives the actual staged content from the very same (potentially shifted) array using `absoluteIndex` [7](#0-6) . Because both the renderer and the patch generator consume the identical mis-parsed `hunk.lines` array, there is no independent check comparing "what git actually diffed" against "what Desktop staged" before `applyPatchToIndex` runs `git apply --cached` [8](#0-7) .

This differs from the Sherlock report only in domain: there, `exchangeRate()`'s scale (18-decimal Idle LP token price) was silently reinterpreted using the wrong divisor (underlying-token decimals) in two independent call sites (`balanceUnderlying`, `calcShares`), producing values off by `10^12` that fed directly into a financial rebalancing decision without any sanity check against the true scale. Here, the "scale" being silently misinterpreted is the *positional/line-count invariant* of a parsed diff hunk, and it feeds directly into what git physically writes to the index without any sanity check that the reconstructed patch matches the original hunk's header counts.

### Impact Explanation
If the positional invariant between the UI's rendered line and the array index consumed by `formatPatch` desyncs (e.g., through a hunk whose header counts and body line count silently diverge, a case not defensively checked anywhere in `buildDiff`/`convertDiff`), the user could select "this line" for partial staging in the diff viewer and have `formatPatch` write a *different* line's content into the patch handed to `git apply --cached`. Since `applyPatchToIndex` blindly pipes this patch to `git apply --cached -` [9](#0-8) , the result is silent corruption of the committed content: the user reviews and approves one diff in the UI but a different set of lines ends up in the index/commit, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Exploitation requires an attacker-influenced repository blob (fetched/cloned/checked out content, or content compared against a remote ref) whose bytes cause git's own unified-diff output to be tokenized inconsistently by Desktop's hand-rolled line splitter versus git's header counts — a narrow, content-dependent condition that is not demonstrated as reliably triggerable from the available code alone. The code paths involved (`DiffParser`, `formatPatch`, `isDiffTooLarge`) contain no assertion that re-verifies `hunk.lines.length` against `header.oldLineCount + header.newLineCount + 1` after parsing, so the class of bug (missing invariant re-validation before staging) is real and confirmed in local code, but I could not construct or confirm a concrete byte sequence that git would emit and that would desync the parser within the scope of this review. This should be treated as a plausible-but-unconfirmed structural weakness rather than a proven, exploitable path.

### Recommendation
Add an explicit post-parse invariant check in `DiffParser.parseHunk` (or in `diffFromRawDiffOutput`) asserting that the number of `Add`/`Context` lines equals `header.newLineCount` and the number of `Delete`/`Context` lines equals `header.oldLineCount`; reject (fall back to `DiffType.Unrenderable`) any hunk that fails this check rather than silently accepting it. Additionally, `formatPatch`/`formatPatchToDiscardChanges` should independently recompute and compare the header counts they write (`oldCount`/`newCount`) against the *original* hunk header before treating a partial-selection patch as safe to hand to `git apply --cached`, rather than only using the recomputed counts to build the new header optimistically (as done today at [10](#0-9) ) with no cross-check against `diff.hunks`/git's own reported totals.

### Proof of Concept
Not constructed — I was unable to identify or verify, within the scope of local static review, a concrete git-diff byte sequence that would cause `DiffParser`'s per-line tokenization to diverge from the hunk header's declared counts while still being accepted as a well-formed diff by `isValidBuffer`/`isDiffTooLarge`. This finding should be validated by a background agent with the ability to run `DiffParser` against crafted binary/text hybrid blobs and to fuzz `nextLine()`/`diffHeaderRe` against git's actual `git diff` output for adversarial file content (e.g., embedded `\r`, NUL bytes, or content lines beginning with `@@ -`/`--- `/`+++ ` that could be misread as headers).

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })

/**
 * Utility function to check whether parsing this buffer is going to cause

function isValidBuffer(buffer: Buffer) {
  return buffer.length <= MaxDiffBufferSize
}

/** Is the buffer too large for us to reasonably represent? */
function isBufferTooLarge(buffer: Buffer) {
  return buffer.length >= MaxReasonableDiffSize
}

/** Is the diff too large for us to reasonably represent? */
function isDiffTooLarge(diff: IRawDiff) {
  for (const hunk of diff.hunks) {
    for (const line of hunk.lines) {
      if (line.text.length > MaxCharactersPerLine) {
        return true
      }
    }
  }

  return false
}
