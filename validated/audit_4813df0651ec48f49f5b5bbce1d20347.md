### Title
Webhook Shop Identity Not Bound to HMAC Signature Allows Cross-Shop Webhook Forgery — (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates an incoming webhook solely by validating the HMAC over the raw POST body, but the shop identity that downstream code uses to decide *which merchant's data to act on* is read from the `X-Shopify-Shop-Domain` request header, which is never included in that HMAC computation. This mirrors the reported analog bug: an identifier that determines which account/record is affected (there, the wallet's account ID taken unchecked from user-supplied JSON; here, the shop domain taken unchecked from an unauthenticated header) is trusted without being cryptographically bound to the verified data, allowing one party's authenticated payload to be attributed to a different, unrelated shop.

### Finding Description
`PayloadVerification#hmac_valid?` computes/verifies the signature only over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` calls this and, on success, exposes the shop identity via a completely separate, unsigned header: [2](#0-1) 

The `shop_domain` helper is the officially documented way for app developers to route webhook processing, and it is exactly what the gem's generated privacy/webhook job templates rely on to select which shop record to act on: [3](#0-2) [4](#0-3) [5](#0-4) 

Because `X-Shopify-Shop-Domain` is not part of the signed payload, any actor who obtains one genuinely-signed webhook (body + `X-Shopify-Hmac-Sha256`) — for example a malicious merchant who installed the app on their own store and received a real, validly-signed webhook — can resend that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header. `verify_request` still succeeds because only the body is checked, yet the job is dispatched using the attacker-controlled `shop_domain`. This is the same class of failure as the ethstore bug: the value that determines *whose record is touched* (account ID / shop domain) is taken directly from attacker-influenced input with no cross-check against the cryptographically-verified data (JSON contents / HMAC-signed body).

### Impact Explanation
Any code following the gem's documented pattern — including the shipped generator templates for `shop_redact`, `customers_data_request`, `customers_redact`, and generic webhook jobs — looks up and acts on a `Shop` record by `shopify_domain: shop_domain` where `shop_domain` is taken from the unauthenticated header. An attacker who has legitimately installed the app on their own store (or has otherwise captured one valid signed webhook) can forge the shop-attribution of that webhook to point at any other installed shop, causing shop-scoped actions (e.g. privacy redaction workflows, `shop.with_shopify_session` API calls) to be executed against a shop they do not control. This is a cross-shop trust-boundary violation: an accepted forged/replayed signed request is misattributed to a victim merchant.

### Likelihood Explanation
Exploitation requires only a single legitimately-signed webhook (trivially obtainable by installing the app on one's own store) and the ability to send an HTTP POST with a custom header — no secret disclosure or special privilege is needed beyond having the app installed somewhere. Since `verify_request` never checks the header against the signed body, the attack is straightforward and repeatable for any webhook topic the app processes using this documented pattern.

### Recommendation
- Do not trust `X-Shopify-Shop-Domain` (or any other header) as an authoritative source of shop identity for a webhook. Instead, derive/validate shop identity from data that is itself covered by the HMAC (i.e., from the parsed webhook body, as `ShopifyAPI::Webhooks::Request` does internally) or bind the header value into the HMAC verification (verify it against the shop that owns the currently active webhook subscription).
- Update `WebhookVerification#shop_domain` and the generator templates to cross-check the header-derived shop against the shop identifiable from the signed payload/registered webhook, rejecting requests where they diverge.
- Add regression tests asserting that a replayed valid HMAC with a mismatched `X-Shopify-Shop-Domain` header is rejected.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook topic the app handles (e.g. `shop/redact` or any custom topic), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — both valid and signed with the app's shared secret.
2. Attacker replays the exact same request to the app's webhook endpoint, but changes only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb`) calls `hmac_valid?(request.raw_post)`, which succeeds since the body is unchanged.
4. The controller/job (per the documented pattern or generated templates such as `shop_redact_job.rb.tt`) looks up `Shop.find_by(shopify_domain: "victim-shop.myshopify.com")` and executes shop-scoped logic against the victim shop, even though the actual signed webhook content originated from the attacker's own shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
