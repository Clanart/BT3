### Title
Unauthenticated tx-sender JSON-RPC `send_tx` Endpoint Allows Any Caller to Drain Fee-Paying UTXOs and Disrupt Bridge Operations — (File: `crates/clementine-tx-sender/src/jsonrpc/server.rs`)

### Summary

The `clementine-tx-sender` JSON-RPC server exposes a `send_tx` method with zero authentication. The server explicitly supports binding to `0.0.0.0`, and when so configured, any network-reachable attacker can submit arbitrary transactions with `CPFP` or `RBF` fee types. The tx-sender will then spend its own fee-paying UTXOs to fund and sign those attacker-controlled transactions, draining the tx-sender-managed balance. Once exhausted, all legitimate bridge operations that depend on fee-paying capacity (kickoff, payout, reimbursement) are starved and fail to broadcast.

### Finding Description

`start_jsonrpc_server` in `crates/clementine-tx-sender/src/jsonrpc/server.rs` builds a plain `jsonrpsee` HTTP server with `ServerBuilder::default()` — no authentication middleware, no token check, no IP allowlist beyond the bind address itself:

```rust
let server: Server = ServerBuilder::default()
    .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
    .build(bind_addr)
    .await ...;
```

The `send_tx` handler immediately processes any well-formed request:

```rust
module.register_async_method("send_tx", |params, client, _| async move {
    let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;
    ...
    let try_to_send_id = client.insert_try_to_send(
        &mut dbtx,
        req.tx_metadata,
        &signed_tx,
        req.fee_paying_type,   // attacker-controlled: CPFP, RBF, or NoFunding
        req.rbf_signing_info,
        &req.cancel_outpoints, // attacker-controlled: can cancel legitimate bridge txs
        &req.cancel_txids,
        &req.activate_txids,
        &req.activate_outpoints,
    ).await ...;
```

The configuration layer explicitly permits binding to `0.0.0.0`:

```rust
let bind = env_optional("TX_SENDER_JSONRPC_BIND")
    .unwrap_or_else(|| "127.0.0.1".to_string());
if bind != "127.0.0.1" && bind != "0.0.0.0" {
    return Err(BridgeError::EnvVarMalformed(...));
}
```

When `TX_SENDER_JSONRPC_BIND=0.0.0.0` (a supported, documented production option), the server is reachable from any host on the network. There is no mTLS, no API key, no IP allowlist, and no caller identity check of any kind.

**Contrast with the gRPC layer**: the operator/verifier gRPC servers enforce mTLS via `OnlyAggregatorAndSelf` in `core/src/rpc/interceptors.rs`, pinning the leaf certificate to either the aggregator's or the entity's own certificate. The tx-sender JSON-RPC has no equivalent guard.

**Attack path**:

1. Attacker discovers the tx-sender JSON-RPC port (default `3030`) on a host where `TX_SENDER_JSONRPC_BIND=0.0.0.0`.
2. Attacker sends repeated `send_tx` requests with `fee_paying_type: "CPFP"` and a minimal syntactically-valid transaction (as demonstrated in the project's own test at line 167 of `src/jsonrpc/server.rs`).
3. For each request, the tx-sender selects one of its own fee-paying UTXOs, adds it as an input, signs it with its `secret_key`, and broadcasts the transaction.
4. The tx-sender's fee-paying UTXO pool is drained.
5. Legitimate bridge transactions (kickoff, payout, reimbursement) that require CPFP fee-bumping fail to broadcast because no fee-paying UTXOs remain.
6. Additionally, the attacker can supply `cancel_outpoints` pointing to legitimate bridge UTXOs, causing the tx-sender to mark those UTXOs as cancelled and refuse to send the corresponding bridge transactions.

### Impact Explanation

**Severity: Medium**

- **Tx-sender-managed balance loss**: The tx-sender's fee-paying UTXOs are spent on attacker-controlled transactions. These are bridge-controlled UTXOs within the allowed impact gate.
- **Bridge liveness disruption**: Kickoff, payout, and reimbursement transactions that depend on CPFP fee-bumping cannot be broadcast once the fee-paying pool is exhausted. This can cause operators to miss challenge windows or fail to claim reimbursements, resulting in material fund impact.
- **Cancellation of legitimate bridge transactions**: The `cancel_outpoints` parameter allows the attacker to suppress specific bridge transactions from being sent, enabling targeted disruption of the withdrawal or challenge flow.

### Likelihood Explanation

The `0.0.0.0` bind is an explicitly supported and documented configuration option. In containerized deployments (Docker, Kubernetes), services are routinely bound to `0.0.0.0` to be reachable within the cluster. The `run.sh` smoke-test script itself demonstrates calling the endpoint with a plain `curl` command — no credentials required. Any attacker with network access to the tx-sender port can exploit this immediately.

### Recommendation

Add caller authentication to the JSON-RPC server. Options in increasing strength:

1. **Shared secret / Bearer token**: Require a configurable secret header on every request; reject requests missing or presenting the wrong token.
2. **IP allowlist**: Restrict accepted connections to a configurable set of source IPs (e.g., only the aggregator's IP).
3. **mTLS**: Mirror the gRPC layer's `OnlyAggregatorAndSelf` pattern — require a client certificate signed by the bridge CA and pinned to the aggregator's identity.

At minimum, document that `TX_SENDER_JSONRPC_BIND=0.0.0.0` must never be used without network-level access controls (firewall rules, VPC security groups) that restrict access to trusted callers only.

### Proof of Concept

The project's own test (lines 165–180 of `crates/clementine-tx-sender/src/jsonrpc/server.rs`) demonstrates that a completely unauthenticated client can enqueue a transaction:

```rust
pub async fn start_jsonrpc_server(
    tx_sender_client: TxSenderClient,
    bind_addr: SocketAddr,
) -> Result<TxSenderJsonRpcServer, BridgeError> {
    let server: Server = ServerBuilder::default()
        .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
        .build(bind_addr)
        .await
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let local_addr = server
        .local_addr()
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let mut module = RpcModule::new(tx_sender_client.clone());
    module
        .register_async_method("send_tx", |params, client, _| async move {
            let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;

            let raw_tx = hex::decode(&req.signed_tx_hex).map_err(jsonrpc_err)?;
            let signed_tx: Transaction = consensus::deserialize(&raw_tx).map_err(jsonrpc_err)?;

            let mut dbtx = client.db.begin_transaction().await.map_err(jsonrpc_err)?;

            let try_to_send_id = client
                .insert_try_to_send(
                    &mut dbtx,
                    req.tx_metadata,
                    &signed_tx,
                    req.fee_paying_type,
                    req.rbf_signing_info,
                    &req.cancel_outpoints,
                    &req.cancel_txids,
                    &req.activate_txids,
                    &req.activate_outpoints,
                )
                .await
                .map_err(jsonrpc_err)?;

            client
                .db
                .commit_transaction(dbtx)
                .await
                .map_err(jsonrpc_err)?;

            Ok::<u32, ErrorObjectOwned>(try_to_send_id)
        })
        .map_err(|e| BridgeError::Eyre(e.into()))?;
```

```rust
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}
```
