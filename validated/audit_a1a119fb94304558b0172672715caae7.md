This confirms the mechanism: `createCommit` (`app/src/lib/git/commit.ts:15-72`) calls `unstageAll` then `stageFiles`, which for any partially-selected file calls `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`). That function re-invokes `getWorkingDirectoryDiff` to fetch a **brand-new** diff from disk right before formatting the patch, but reuses the `file.selection` object that was computed against whatever diff was rendered earlier in the UI. `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`) blindly maps `file.selection.isSelected(absoluteIndex)` onto this freshly-fetched diff's hunk/line layout without validating that the hunk structure/content still matches what the user actually reviewed.

The only place Desktop performs reconciliation between an old selection and a newer diff is in `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3404-3497`), which explicitly acknowledges: *"The diff might have changed dramatically since last we loaded it... we'll settle on just updating the selectable lines"* — but this reconciliation only prunes now-invalid line indices from the UI-facing selection; it does **not** run on the independent diff fetched inside `applyPatchToIndex` at actual commit/stage time, and it does not verify line **content**, only index membership.

### Title
Stale line-selection reused against a freshly re-fetched diff causes silent mis-commit of unreviewed content - (File: app/src/lib/git/apply.ts)

### Summary
`applyPatchToIndex` re-queries `git diff` for the file immediately before staging, but applies the user's previously computed `DiffSelection` (line indices) to this new diff without validating that the hunk layout/content is unchanged. If the working tree content for the file changes between the moment the user reviewed/selected lines in the Changes view and the moment they click Commit, the absolute line indices in `DiffSelection` can now point at different lines than what the user selected.

### Finding Description
The commit pipeline is:
1. UI loads a diff and lets the user select lines; the resulting `WorkingDirectoryFileChange.selection` (a `DiffSelection`) stores selection state keyed by **absolute line index** within the hunks of that diff ( [1](#0-0) ).
2. On commit, `createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex` [2](#0-1) .
3. `applyPatchToIndex` performs a **fresh** `getWorkingDirectoryDiff` call — a brand-new `git diff` invocation against the current on-disk state — and immediately feeds it, together with the stale `file.selection`, into `formatPatch` [3](#0-2) .
4. `formatPatch` walks the new diff's hunks and, for every non-context line, checks `file.selection.isSelected(absoluteIndex)` purely by index, with no comparison of the line's text/type against what was originally selected [4](#0-3) .

The only safeguard in the codebase that reconciles selection state against a newer diff is in `updateChangesWorkingDirectoryDiff`, and that logic only trims indices that no longer exist (turned into context or removed) — it does not detect the case where the hunk structure is stable in shape but the meaning of a given index has shifted content-wise, and critically it does not run at all before `applyPatchToIndex`'s own independent diff fetch [5](#0-4) .

This mirrors the reported Maple pattern exactly: the code trusts a previously-observed/cached quantity (`collateral()` snapshot / here, `DiffSelection` index positions) instead of re-deriving trust from the authoritative, freshly-fetched state (`balanceOf` / here, the newly generated diff's actual line content), and silently proceeds as if they still correspond.

### Impact Explanation
If a working directory file is modified externally between diff-render time and commit time — for example, by a background process spawned from a malicious repository (a `post-checkout`/`post-merge` hook installed by a cloned repo, a Git LFS smudge filter, or a `clean`/`smudge` filter defined in a malicious `.gitattributes` shipped by the cloned repository) that rewrites the file's content or line arrangement right before the user hits Commit, the staged patch built from the stale selection can silently include or exclude different lines than the user intended. This is "silent corruption of what the user commits," matching the report's disallowed-impact carve-out exactly on point: it doesn't need code execution, just a mismatch between reviewed intent and staged content, potentially committing/pushing attacker-influenced content the user never saw or approved.

### Likelihood Explanation
This requires precise timing: the working tree content must actually change during the (typically short) window between the user's last diff render and clicking Commit, and the change must be driven by something the attacker controls (e.g., a smudge/clean filter or hook shipped in a cloned/fetched repository) rather than the user's own edits. Desktop does have partial mitigations (selectable-line pruning on the UI diff refresh), reducing — but not eliminating — the likelihood, since that mitigation doesn't cover the independent diff fetch inside `applyPatchToIndex`.

### Recommendation
Before formatting/applying the patch in `applyPatchToIndex`, verify that the freshly-fetched diff's hunk headers/content still match what the selection was computed against (e.g., by comparing the diff's hash/hunk signatures, or by re-validating that each selected/unselected line's raw text matches the originally-rendered diff) before trusting the index-based `DiffSelection`. If a mismatch is detected, abort staging that file and force the user to re-review the diff, analogous to using an authoritative freshly-measured value (`balanceOf`) rather than a stale cached one in the original report.

### Proof of Concept
1. Attacker publishes/hosts a repository containing a `.gitattributes` entry wiring a `clean`/`smudge` filter (or a `post-checkout`/pre-stage hook, depending on which lifecycle event is reachable) that non-deterministically rewrites a tracked file's contents shortly after checkout/fetch.
2. Victim clones/opens the repo in Desktop, edits the file, and in the Changes view selects only specific lines to commit (leaving others unselected) — `DiffSelection` now stores selection by absolute index against that diff snapshot.
3. Before the victim clicks "Commit," the attacker-controlled filter/process fires and alters the file's line layout on disk (e.g. reordering/inserting lines while preserving hunk count).
4. Victim clicks Commit. `applyPatchToIndex` re-fetches the diff (now reflecting step 3's altered content) and applies the same index-based selection via `formatPatch`, producing a patch whose selected/unselected lines no longer correspond to what the victim actually reviewed and intended, so the resulting commit silently contains different content/lines than the user approved.
