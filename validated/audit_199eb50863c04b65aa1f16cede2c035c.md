### Title
Oneof selector (`oneofFieldCase_`) committed before payload write in Java "full" runtime string-oneof parser causes case/value type-mismatch — ([File: src/google/protobuf/compiler/java/full/string_field.cc])

### Summary
In the Java "full" (non-Lite) runtime generator, `ImmutableStringOneofFieldGenerator::GenerateBuilderParseMethod` emits code that sets the oneof discriminator (`oneofFieldCase_`) to the string field's case number **before** the actual payload read (`input.readStringRequireUtf8()`) has completed. `readStringRequireUtf8()` can throw `InvalidProtocolBufferException` on malformed UTF-8 supplied by an ordinary caller of the public `parseFrom`/`mergeFrom` API. When it throws, the discriminator has already been switched to "string" while `oneofField_` retains its previous, differently-typed value (e.g. an `Integer`, `ByteString`, or nested `Message` from an earlier field of the same `oneof`). This is the direct analog of the Linux `iommufd` bug: an identifier/selector (`iopt_access_list_id` / `oneofFieldCase_`) is written into shared state before the operation that is supposed to make it valid (`iopt_calculate_iova_alignment` / `readStringRequireUtf8`) has succeeded, leaving a stored id/selector that does not match the associated payload.

### Finding Description
Generated parse code (current codegen, `src/google/protobuf/compiler/java/full/string_field.cc:761-798`):
```
switch ($oneof_name$Case_) {
default:
  clear$oneof_capitalized_name$HasBits(); // fallthrough
case 0:
  $set_oneof_case_message$;      // sets oneofFieldCase_ = STRING case NOW
  $set_has_field_bit$            // fallthrough
case $number$:
  break;
}
$oneof_name$_ = input.readStringRequireUtf8();   // may throw AFTER case already committed
``` [1](#0-0) 

`CodedInputStream.readStringRequireUtf8()` throws `InvalidProtocolBufferException` on invalid UTF-8 (this is the `STRICT` validation mode, selected whenever `CheckUtf8(descriptor_)` is true, i.e. `features.utf8_validation = VERIFY` or legacy `java_string_check_utf8`): [2](#0-1) [3](#0-2) 

If a message serializes two fields belonging to the same `oneof` — first a non-string member (setting `oneofField_` to e.g. an `Integer`), then the string member with an invalid-UTF-8 payload — the generated switch statement unconditionally commits `oneofFieldCase_` to the string case before the read that can fail. The exception then propagates up through the standard parse wrapper, which attaches the half-built object as the "unfinished message": [4](#0-3) [5](#0-4) 

The resulting object is internally inconsistent: `oneofFieldCase_ == STRING` but `oneofField_` holds a non-`String`, non-`ByteString` object left over from the prior field. The corresponding accessor unconditionally casts the non-`String` branch to `ByteString`:
```
java.lang.Object ref = $oneof_name$_;
if (ref instanceof java.lang.String) {
  return (java.lang.String) ref;
} else {
  com.google.protobuf.ByteString bs = (com.google.protobuf.ByteString) ref;   // unchecked cast
``` [6](#0-5) 
The identical unconditional-cast pattern exists in the Builder accessor: [7](#0-6) 

Because `getUnfinishedMessage()`/`getUnfinishedMessage()`-style best-effort parsing is a documented, intended usage pattern (javadoc: "to support best-effort parsing"), a caller invoking the string getter on the returned partial message with `ref` actually holding e.g. an `Integer` or nested `Message` triggers a `ClassCastException` instead of the expected `InvalidProtocolBufferException`/graceful degradation.

### Impact Explanation
This is a state-consistency violation directly analogous to the kernel CVE: a selector/id (`oneofFieldCase_`, analogous to `access->iopt_access_list_id`) is committed to the "new" value before the associated data write (`readStringRequireUtf8`, analogous to `iopt_calculate_iova_alignment`) is verified to succeed. On failure, the selector and the backing value diverge. In the kernel this manifested as a `WARN_ON`/list mismatch; here it manifests as an uncaught `ClassCastException` (ClassCastException is a `RuntimeException`, not caught by the `InvalidProtocolBufferException`/`IOException` handling in the generated parse wrapper) when application code exercises the documented best-effort-parsing recovery path on the returned partial message. This is a reachable crash/denial-of-service condition triggered purely by a bounded, attacker-supplied binary Protobuf payload through the public `parseFrom`/`mergeFrom` API — no privileged access, hostile schema, or unbounded input required. It does not by itself grant memory corruption or code execution; the failure mode is a Java-level type confusion producing an uncaught exception.

### Likelihood Explanation
Reachable whenever: (1) a message defines a `oneof` containing a `string` field alongside at least one other field type, (2) that file/field enables strict UTF-8 validation (`features.utf8_validation = VERIFY`/legacy `java_string_check_utf8`, which is common for proto2 "required"/checked strings and increasingly for editions), and (3) the caller uses the standard/idiomatic pattern of catching `InvalidProtocolBufferException` and inspecting `getUnfinishedMessage()` (a documented recovery mechanism). Constructing the two-field, malformed-UTF-8 payload is trivial and fully attacker-controlled and bounded in size.

### Recommendation
In `ImmutableStringOneofFieldGenerator::GenerateBuilderParseMethod` (and the analogous immutable-message generator), read the string value into a local variable first, and only update `oneofField_`/`oneofFieldCase_`/has-bits after `readStringRequireUtf8()` returns successfully — mirroring the ordering already used by the primitive-oneof generator (`ImmutablePrimitiveOneofFieldGenerator::GenerateBuilderParseMethod`, which reads first, then updates the case), so a thrown `InvalidProtocolBufferException` never leaves the case discriminator pointing at unwritten/mismatched data.

### Proof of Concept
Not executed in this session (no code-execution tooling available in ask-only mode); however, the reproduction is derivable directly from the cited generated-code order and `CodedInputStream` behavior:
1. Define a proto2/edition message with `oneof o { int32 a = 1; string b = 2; }` where field `b` has `features.utf8_validation = VERIFY` (or the file sets `java_string_check_utf8 = true`).
2. Serialize bytes: tag for field 1 (varint, e.g. value `7`) followed by tag for field 2 with length 1 and payload byte `0x80` (a lone continuation byte — invalid UTF-8, confirmed to throw per `CodedInputStreamTest.testReadStringRequireUtf8InvalidUtf8`, `java/core/src/test/java/com/google/protobuf/CodedInputStreamTest.java:1602-1627`).
3. Call `Message.parseFrom(bytes)`; catch `InvalidProtocolBufferException`; call `e.getUnfinishedMessage()`, cast to the message type, and call `getB()` — the getter’s `else` branch casts the retained `Integer` (from field `a`) to `ByteString`, expected to throw `ClassCastException` instead of returning gracefully.

**Uncertainty**: I was not able to execute this PoC to confirm the runtime `ClassCastException` empirically in this environment, nor verify definitively that every currently shipped/supported Java "full" version still preserves this exact ordering outside the cited generator source (I confirmed the ordering in `src/google/protobuf/compiler/java/full/string_field.cc`, the current codegen source, and in multiple historical `compatibility/smoke/*` generated snapshots for other oneof member types, but did not find a generated *string*-oneof example with strict UTF-8 checking enabled in the indexed smoke-test corpus to cross-check byte-for-byte). This should be validated with an actual build/run before treating it as fully confirmed.

    public String readStringRequireUtf8() throws IOException {
      final int size = readRawVarint32();
      if (size > 0 && size <= (limit - pos)) {
        String result = Utf8.decodeUtf8(buffer, pos, size);

    return true;

         // For legacy syntax. This is not allowed under Editions.
