### Title
Unhandled underflow when computing mempool transaction fees for inflationary spend bundles - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` without first checking that `removal_amount >= addition_amount`. Any unprivileged party can submit a spend bundle whose total created-coin value exceeds its total removed-coin value (an inflation/minting attempt), causing this subtraction to go negative and the `uint64()` cast to raise an unhandled `ValueError`, instead of the mempool cleanly rejecting the bundle with a dedicated error code as consensus validation does for blocks.

### Finding Description
In `MempoolManager.validate_spend_bundle`, `addition_amount` is accumulated from every `CREATE_COIN` condition across all coin spends in the bundle [1](#0-0) , and `removal_amount` is accumulated from the amounts of the coins actually being spent [2](#0-1) . The resulting fee is computed as:

```python
fees = uint64(removal_amount - addition_amount)
``` [3](#0-2) 

Nowhere before this line does `validate_spend_bundle` verify that `addition_amount <= removal_amount`. This is unlike full block validation, where `validate_block_body` explicitly performs this check before computing fees and returns a clean `Err.MINTING_COIN` if additions exceed removals:

```python
if removed < added:
    return Err.MINTING_COIN
fees = removed - added
assert fees >= 0
``` [4](#0-3) 

Because the puzzle reveal and solution for a spender's own coin are entirely attacker-controlled, an unprivileged submitter can craft a spend bundle whose `CREATE_COIN` conditions sum to more than the coin(s) being spent (e.g. a standard coin spend with a `CREATE_COIN` output larger than the input coin's amount). This is exactly the same underflow bug class as the reported `LiquidityManager.borrow()` issue: a subtraction of two attacker-influenceable values that is expected to always be non-negative, but is not actually guarded, causing a revert/exception in a permissionless code path.

### Impact Explanation
When `addition_amount > removal_amount`, the `uint64()` cast raises an unhandled `ValueError` inside `validate_spend_bundle`, which is called directly (without a surrounding try/except) from `add_spend_bundle` [5](#0-4) . Instead of the mempool cleanly returning `MempoolInclusionStatus.FAILED` with an appropriate `Err`, the exception propagates out of `add_spend_bundle`. Depending on the caller (e.g. RPC "push_tx", or full-node peer transaction-relay handling), this results in an unhandled exception disrupting normal transaction-processing flow for that spend bundle instead of a graceful rejection — a spend-triggered transaction-processing halt reachable by any unprivileged spend-bundle submitter, matching the accepted impact category.

### Likelihood Explanation
High reachability: any wallet user or RPC caller can submit a spend bundle with a self-crafted puzzle/solution whose `CREATE_COIN` conditions total more than the spent coin(s)' amount. No special privileges, cooperating peers, or race conditions are required — a single `push_tx`/`respond_transaction` call is sufficient to trigger the code path.

### Recommendation
Mirror the consensus-level check performed in `validate_block_body` before computing fees in `validate_spend_bundle`:
```python
if addition_amount > removal_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This ensures invalid/inflationary spend bundles are rejected with a well-defined error instead of raising an unhandled exception during mempool validation.

### Proof of Concept
1. Create a standard coin `C` with amount `A` owned by the attacker's own key.
2. Build a coin spend for `C` whose solution issues a `CREATE_COIN` condition with amount `A + 1` (or any amount greater than `A`), signed validly by the attacker's own key (they are spending their own coin, so they can sign it).
3. Submit this single-spend `SpendBundle` via the wallet/full-node RPC (`push_tx`) or peer transaction relay.
4. In `MempoolManager.validate_spend_bundle`, `addition_amount` (`A+1`) exceeds `removal_amount` (`A`), so `fees = uint64(removal_amount - addition_amount)` at [3](#0-2)  raises `ValueError` instead of returning a controlled `Err.MINTING_COIN`-style rejection, since no such guard exists prior to this line (contrast with the guarded version in [4](#0-3) ).
