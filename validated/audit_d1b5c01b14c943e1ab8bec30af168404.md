### Title
`ReceivedOutput::read` deserializes an unverified offset/output/outpoint triple, letting untrusted bytes fabricate "received" outputs that are not actually spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The LangGraph advisory class — a deserialization path that reconstructs objects beyond what the application expects from attacker-influenced bytes — maps onto `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134`. The only in-band producer of a `ReceivedOutput` is `Scanner::scan_transaction`/`scan_block`, which guarantees an invariant: `output.script_pubkey == P2TR(key + offset·G)` for the scanner's `key`, and `outpoint` is the real UTXO identifier. The `read`/`write` pair serializes `offset`, `output`, and `outpoint` as three independent fields and reconstructs them with **no consistency check** — `Secp256k1::read_F` only enforces canonical scalar encoding, and `TxOut`/`OutPoint` are consensus-decoded without any binding to the scanner's key or to each other (`mod.rs:122-133`). Any byte string therefore reconstructs a structurally valid `ReceivedOutput` carrying an arbitrary scalar offset, an arbitrary `TxOut` (any `script_pubkey`, any value), and an arbitrary `OutPoint` — an object the only legitimate constructor could never produce.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` keyed by script and returns `ReceivedOutput`s whose `offset` is exactly the scalar satisfying `output.script_pubkey == p2tr_script_buf(self.key + offset·G)` (`mod.rs:185`, `mod.rs:205-211`). Downstream spending (`networks/bitcoin/src/wallet/send.rs` via `offset()`/`output()`/`outpoint()` getters) relies on this relation to build the tweaked signing key. `ReceivedOutput::read` consumes `offset` (line 123), `output` (line 129), and `outpoint` (line 131) from the stream independently — it never recomputes `p2tr_script_buf(key + offset·G)`, never checks that `outpoint` corresponds to a confirmed UTXO, and has no access to the scanner key needed for such a check. An attacker who can supply bytes to this reader (stored/forwarded scan results, which the crate treats as round-trippable untrusted bytes) produces a `ReceivedOutput` where:

1. `outpoint`/`output` describe an output that does not exist on-chain, or belongs to a different script, while still being accepted and reported as a received, spendable output, or
2. `offset` does not correspond to `output.script_pubkey`, so the resulting tweak produces a key that cannot sign for the output — the wallet reports and may attempt to spend funds that are unspendable.

### Impact Explanation
Wallet/accounting consumers treat a deserialized `ReceivedOutput` as proof of a spendable received output. Fabricated bytes cause funds to be reported received which either do not exist on-chain or cannot be spent by the threshold key (wrong offset ⇒ wrong tweaked key ⇒ signature can never satisfy the real script). This matches the "escalation from store/input write access to incorrect runtime state" shape of the advisory: the deserialize path grants more than the caller expects. Severity: Medium (no direct key leakage; requires write access to the byte stream feeding `read`, mirroring the checkpoint-store prerequisite in the source report).

### Likelihood Explanation
Exploitation requires an untrusted party to influence bytes passed to `ReceivedOutput::read` — the same trust boundary as the source advisory (modification of serialized data at rest/in transit). Where scan results are persisted or relayed without integrity protection, the attack is a pure byte-level write with no cryptographic work required. Where the stream is integrity-protected, it is not reachable, which is why this is defense-in-depth rather than a live exploit path.

### Recommendation
Either bind the fields cryptographically at read time — e.g., pass the expected `Scanner`/`key` into `read` and verify `p2tr_script_buf(key + offset·G) == output.script_pubkey`, erroring otherwise — or scope `ReceivedOutput::read`/`write` to explicitly trusted storage and document that the bytes are integrity-sensitive. Adding an authenticated envelope (MAC/signature) over serialized scan results would also suffice.

### Proof of Concept
1. Create a `Scanner` for key `K`, register offset `o`, obtain a legitimate `ReceivedOutput` for some on-chain output, and serialize it with `write`.
2. Attacker modifies the stream: replace the 32-byte `offset` with a canonical encoding of `o' = o + 1`, or replace the `TxOut`/`OutPoint` consensus fields with a fabricated output paying an unrelated `script_pubkey`.
3. `ReceivedOutput::read` accepts the bytes (`mod.rs:122-133` performs no cross-field check) and returns an object whose `offset()` no longer satisfies `p2tr_script_buf(K + offset·G) == output.script_pubkey`.
4. The consumer reports the fabricated `output.value` as received funds; any spend attempt using `offset()` produces a key that does not correspond to the real UTXO's script, so the reported funds are unspendable (or the reported output never existed).
