### Title
Owner can front-run/rug gasless swap users by unilaterally changing `commissionRate` between tx-pool admission and block execution in GaslessSwapRouter (KIP-247) - (File: kaiax/gasless/impl/tx_pool.go, contracts/bindings/kip247/GaslessSwapRouter.go)

### Summary
The `GaslessSwapRouter` contract used by the `kaiax/gasless` module exposes an owner-only `updateCommissionRate(uint256)` function with no upper bound, no timelock, and no freeze mechanism, analogous to the unfrozen `publicMintPrice`/`presaleMintPrice` in the referenced NFTCollection report. Since the gasless module validates a swap transaction's economics (`amountIn`, `minAmountOut`, `amountRepay`) against the router's *current* on-chain state at tx-pool admission time, but the router owner can change `commissionRate` at any point before the transaction is actually included, the pricing basis used to admit the gasless transaction can silently diverge from the pricing basis used to execute it.

### Finding Description
The gasless tx-pool validation in `checkBalanceForSwap` computes `requiredAmountIn` via a *live call* to the router (`GetAmountIn`) and compares it to the user-declared `AmountIn`/`MinAmountOut`/`AmountRepay` at the moment the transaction is checked for promotion: [1](#0-0) 

This pricing/quote call is not pinned to the block in which the transaction will ultimately execute — it is a `nil`-context view call performed whenever the pool re-validates the pending transaction: [2](#0-1) 

The router itself allows its `owner` to call `updateCommissionRate(uint256 _commissionRate)` at any time, with no bound check, no timelock, and no freeze flag visible in the exposed ABI/bindings: [3](#0-2) 

The router also emits a `CommissionRateUpdated(oldRate, newRate)` event and a `SwappedForGas` event carrying `Commission` and `FinalUserAmount`, confirming that the commission taken from the user's token repayment directly depends on `commissionRate` at execution time: [4](#0-3) 

Because the gasless module's pool-admission check (`GetCheckBalance`/`checkBalanceForSwap`) and `VerifyExecutable`'s repay-amount check only validate that `AmountRepay` matches the value computed from the current pending state at validation time, and because the owner is not required to freeze or timelock the commission rate, the owner (or anyone colluding with the owner) can:
1. Set a low/zero `commissionRate` so that a user's gasless swap tx (with `amountRepay` computed off that low rate) is admitted to the pool and appears economically fair.
2. Before the swap tx is included by a block proposer, raise `commissionRate` sharply.
3. At execution, the same `AmountIn`/`MinAmountOut`/`AmountRepay` the user signed are used, but the router's internal commission logic (unseen in this repo, only in bindings) will take a different — larger — cut out of the swapped proceeds, or cause the swap to revert/behave unfavorably for the `finalUserAmount`, effectively rug-pulling the gasless user's economics without violating any of the module's static admission checks that ran against stale state.

This mirrors exactly the pattern in the referenced report: a critical economic parameter (mint price / commission rate) is mutable by a privileged party with no freeze/timelock protection, and users who commit to a transaction based on the parameter's current value can be rugged by a subsequent unilateral change before their transaction settles.

### Impact Explanation
A malicious or compromised router owner can manipulate `commissionRate` to extract more value from unsuspecting gasless-swap users than what was quoted/validated when their transaction was admitted to the pool, directly resulting in unauthorized value extraction from an unprivileged transaction sender (the gasless swap user) at settlement time. This satisfies the "fee or fee-delegation abuse" / "unauthorized value movement" bar for Medium severity, since the actual token amount debited from the user's swap proceeds can differ from what they agreed to based on stale pricing information used by the gasless tx-pool checks.

### Likelihood Explanation
This requires the router's `owner` (an EOA/admin key controlling the deployed `GaslessSwapRouter`, which is registered via `kip149`/`Registry` and consumed by the `kaiax/gasless` module) to actively call `updateCommissionRate`. It does not require any node/validator/consensus compromise — only a single transaction from the contract owner — making it reachable purely through normal transaction submission, consistent with the "unprivileged... gasless user" and "fee-delegation counterparty" reachability constraints. Likelihood is Medium: it requires an owner action timed against pending gasless transactions, but no cryptographic or consensus-level barrier prevents it.

### Recommendation
- Add a timelock (e.g., minimum delay between `updateCommissionRate` calls and their effect) or a maximum-rate cap enforced in the `GaslessSwapRouter` contract.
- Alternatively, allow the commission rate to be frozen once finalized (mirroring the `publicMintPriceFrozen`/`presaleMintPriceFrozen` pattern recommended in the referenced report), or emit the rate as part of `swapForGas`'s pre-conditions so a mismatch aborts the swap instead of silently applying a new rate.
- In `kaiax/gasless/impl/tx_pool.go`, pin the `GetAmountIn` quote check to be re-validated immediately before inclusion (or have `VerifyExecutable` explicitly re-check that `commissionRate` at execution equals the rate assumed when the user signed `amountRepay`), and reject the transaction if the rate has changed since admission.

### Proof of Concept
1. Owner deploys `GaslessSwapRouter` with `commissionRate = 0`.
2. User submits an approve+swap gasless transaction pair; `kaiax/gasless`'s `checkBalanceForSwap` computes `requiredAmountIn` via `GetAmountIn` at `commissionRate = 0` and admits the tx to the pool (`kaiax/gasless/impl/tx_pool.go` lines 128-141).
3. Before a block proposer includes the swap tx, the owner submits `updateCommissionRate(newHighRate)` (`contracts/bindings/kip247/GaslessSwapRouter.go` lines 596-608), which is included in an earlier block.
4. The gasless swap tx executes against the new elevated `commissionRate`; per `SwappedForGas` event semantics (`Commission`, `FinalUserAmount`), the user receives a smaller `FinalUserAmount` / pays a larger effective commission than what was assumed when their `AmountRepay` was computed and their tx admitted, without any code path in `kaiax/gasless` rejecting the stale quote at inclusion time.

Note: the actual Solidity source of `GaslessSwapRouter.sol` (where `swapForGas`/`updateCommissionRate` internal logic lives) was not found in this repository's index — only its compiled bindings (`contracts/bindings/kip247/GaslessSwapRouter.go`) are available, so the exact internal enforcement of `amountRepay` vs. live `commissionRate` inside the contract itself could not be fully verified from the indexed code. If a full audit of the settlement logic is needed, a Devin session with full repository access should inspect the actual `.sol` source (if present elsewhere) to confirm whether `swapForGas` re-derives commission from the current rate or uses a rate committed at call time.

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}
