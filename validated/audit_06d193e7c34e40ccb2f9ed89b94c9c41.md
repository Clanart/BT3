### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/fee calculation, underpaying the fee and bypassing the max-weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds the fee estimate and the `TooLargeTransaction` check from `payments` only, even though a caller-supplied `data` payload adds a real OP_RETURN output to `tx_outs`. The produced transaction therefore pays a lower effective fee rate than the requested `fee_per_vbyte`, can dip below the minimum relay fee without triggering `TooLowFee`, and can exceed `MAX_STANDARD_TX_WEIGHT` while passing the `TooLargeTransaction` check. This is the same bug class as the reference finding: a minimum-cost (`minExecCost` / `needed_fee`) computation that silently drops one of the components the protocol actually charges for.

### Finding Description
The fee logic lives in `calculate_weight_vbytes`, which synthesizes a `Transaction` from `inputs` + `payments` + optional `change` and returns its weight/vbytes [1](#0-0) . Inside `new`, the OP_RETURN output is pushed onto `tx_outs` before the fee is computed, but it is pushed to `tx_outs`, not `payments` [2](#0-1) . Both weight calls then use `payments` [3](#0-2) , so the data output (up to 80 bytes of payload plus amount/script overhead) is never priced. The minimum-relay-fee guard and the `NotEnoughFunds` check both consume this understated `vbytes`/`needed_fee` [4](#0-3) , and the standardness guard uses the same understated `weight` [5](#0-4) . The final `Transaction` is built from `tx_outs`, which does include the unpriced output [6](#0-5) .

### Impact Explanation
Because the change amount is `input_sat - payment_sat - fee_with_change`, the change absorbs the shortfall and the signed transaction's real fee rate is strictly below `fee_per_vbyte`. With an 80-byte data payload the mispricing is ~80+ vbytes; at marginal fee rates the transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` on its true vsize and never relay, stalling the inputs (and any change). Worse, the `MAX_STANDARD_TX_WEIGHT` check passes on weight that excludes the OP_RETURN output, so a transaction at the boundary becomes non-standard and unbroadcastable — signed inputs/outputs effectively locked. This mirrors H-14's "user underpays the minimum execution cost": the caller (or any downstream scheduler using this wallet) is charged less than the true minimum, and the defect surfaces only as a transaction the network refuses.

### Likelihood Explanation
The `data` parameter is a public input to `SignableTransaction::new` [7](#0-6) ; any caller that attaches data triggers the undercharge deterministically, no race or collusion required. Severity is bounded: the wallet is a library and the in-repo processor calls it with `data: None` [8](#0-7) , so exploitation requires a deployment path that forwards user data — consistent with a Medium-severity analog rather than High.

### Recommendation
Include the data output in the weight calculation. The simplest fix is to compute weight from the actual output list: call `calculate_weight_vbytes(tx_ins.len(), &tx_outs-as-payments, ...)` or refactor `calculate_weight_vbytes` to accept `&[TxOut]` and pass `&tx_outs` (including the OP_RETURN output) so that `needed_fee`, the `TooLowFee`/`NotEnoughFunds` checks, the change-amount derivation, and the `MAX_STANDARD_TX_WEIGHT` check all price the real transaction. Also re-check the OP_RETURN value (`Amount::ZERO`) doesn't affect the payment dust loop — it already doesn't, since that loop runs over `payments` only [9](#0-8) .

### Proof of Concept
In `SignableTransaction::new`:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {                        // L195: output added to tx_outs ...
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: op_return });
}
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None); // L204: ... but not priced
let mut needed_fee = fee_per_vbyte * vbytes;      // L206: fee excludes data output
```

`calculate_weight_vbytes` builds its template tx solely from `payments` (L85-L93); `tx_outs`' OP_RETURN entry is absent, so `vbytes` and `weight` are understated by the full serialized size of the data output. Concretely, `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0; 80]), fee_per_vbyte)` returns a `SignableTransaction` whose `needed_fee()` equals `fee_per_vbyte * (true_vsize - ~90)` and whose `tx.weight()` can exceed `MAX_STANDARD_TX_WEIGHT` without `TooLargeTransaction` ever being returned.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
