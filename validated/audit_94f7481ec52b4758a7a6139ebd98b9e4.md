## Finding

`resolveWithin` in `app/src/lib/path.ts` is the shared guard used to keep attacker-influenced paths confined to a repository root, but its boundary check is a plain string-prefix test with no path-separator boundary: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` treats a sibling directory whose name merely *begins with* the root directory's name as "inside" the root (e.g. root `/Users/victim/Documents/GitHub/repo` and `realResolved` `/Users/victim/Documents/GitHub/repo-secrets/config` both satisfy `startsWith`), even though `repo-secrets` is not nested under `repo` at all.

This guard is consumed by the "Open in Desktop" deep-link handler, where the only additional check on the attacker-supplied `filepath` query parameter is that it isn't an absolute path — relative traversal segments (`..`) are not rejected: [2](#0-1) 

`filepath` itself comes straight from `parseAppURL`, which performs no traversal sanitization on it (only `branch` is checked via `testForInvalidChars`): [3](#0-2) 

Because the attacker also controls the cloned repository's name via `sanitizeCloneName` (used to derive the clone directory under the user's default clone base path), the resulting root directory name is attacker-influenced, making it feasible to choose a directory name that is a string-prefix of an existing sibling directory the victim already has on disk, and then supply `filepath=../<sibling-suffix>/<target>` to have `resolveWithin` incorrectly accept it, after which `shell.showItemInFolder(resolved)` is invoked on the escaped path.

### Why existing guards don't stop this
- `isAbsolute(filepath)` only blocks absolute-path payloads, not `..`-relative traversal.
- `resolveWithin`'s traversal collapsing via `normalize`/`resolve` correctly prevents *most* `..` escapes (paths that don't share a prefix with root are rejected), but the final `startsWith` check has no separator check, so any resolved path sharing root's directory name as a prefix silently passes.
- `realpath()` resolution defeats symlink tricks but does nothing about the prefix-matching flaw itself.

I could not fully verify whether `app/test/unit/path-test.ts` already covers this exact sibling-prefix scenario (I ran out of tool calls before reading its contents), so it's possible there is partial test coverage or a mitigating check elsewhere that I did not find; this should be checked before relying on the analysis, ideally in a full Devin session with complete repo access.

### Assessment against required impact criteria
This matches the "link or deep link the user clicks" attacker primitive and results in file read/reveal outside the intended repository directory (via `shell.showItemInFolder`), which fits the allowed impact class (file read outside the repo triggered by a malicious link). It is a genuine analog of the reported bug class: an equality/boundary check (`===0` in the Solidity report, `startsWith` here) that is subtly too permissive, letting an edge-case value slip through a guard intended to be exact/complete.

### Caveat
The practical exploitability depends on the attacker being able to predict or influence a sibling directory name on the victim's machine that shares a prefix with the (attacker-chosen) cloned repo name — this is a real but non-trivial precondition, and I was not able to fully trace all call sites (`app/src/lib/stores/app-store.ts` and `app/src/lib/copilot-conflict-context.ts` also call `resolveWithin`) to confirm whether any of them provide a more directly attacker-controlled path to trigger this without requiring a lucky/guessed sibling directory name. Given this residual uncertainty about a fully deterministic exploitation chain, I'm flagging this as a probable-but-not-fully-confirmed finding rather than a certain one.
