### Title
Unbounded governance parameter values (e.g. `reward.mintingamount`) accepted without magnitude/decimal validation — ([File: kaiax/gov/param.go])

### Summary
Kaia governance parameters that are `*big.Int`-typed monetary values (`reward.mintingamount`, `reward.minimumstake`, `reward.stakingrewardthreshold`) are canonicalized via `bigIntCanonicalizer` [1](#0-0)  and validated only by lightweight `FormatChecker`s that check non-negativity, not realistic magnitude/decimal scale, e.g. `RewardStakingRewardThreshold`'s checker only verifies `v.Sign() >= 0` [2](#0-1) . This mirrors the reported bug class: config setters that assume a specific fixed-point/decimal scale but never enforce it, allowing an off-by-many-orders-of-magnitude value to be accepted and then directly consumed by downstream arithmetic that assumes correctness.

### Finding Description
The governance vote/param pipeline (`headergov.checkConsistency` and `ParamSet.Set`) validates only structural type via a `Canonicalizer`/`FormatChecker` pair and does not bound the numeric magnitude of monetary governance parameters. For `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` there is cross-field consistency checking (lower ≤ upper) [3](#0-2) , but for the reward-related big-int parameters (`RewardMintingAmount`, `RewardMinimumStake`, `RewardStakingRewardThreshold`) the only listed check in `header.go`'s `checkConsistency` default-passes them (`return nil`) for names not covered by specific case branches [4](#0-3) , meaning no magnitude bound is enforced by consensus code either. The value flows unmodified into `RewardConfig.MintingAmount` [5](#0-4)  and is used directly as the per-block minted amount added to validator/fund balances in `getRewardSummary` and `getDeferredRewardFull*` [6](#0-5) .

### Impact Explanation
If `reward.mintingamount` (denominated in peb, 1 KAIA = 1e18 peb) is governance-voted with an incorrect decimal scale (e.g., intending "6.4 KAIA" but supplying a value 1e10–1e19 times too large due to a unit mistake, analogous to the reported 19-decimal-place error), the chain will mint and distribute a massively inflated reward every block to the proposer, stakers, and KIF/KEF/KPF funds — a direct native-token supply inflation and reward redistribution vulnerability, matching the "unauthorized value movement / supply inflation / reward redirection" impact class explicitly in scope.

### Likelihood Explanation
This requires a governance vote (from the governing node / council in single mode, or council majority in ballot mode) to set the parameter — an analogous "owner" role to the reported MarginCalculator bug. There is no automated node-side sanity bound (e.g., max minting amount relative to current value or a hardcoded ceiling) comparable to what exists for `Kip71LowerBoundBaseFee`/`UpperBoundBaseFee`. A single mistaken or malicious vote is sufficient once it reaches quorum; likelihood is Medium given it needs governance access but the validation gap is concrete and directly reachable via the standard `governance.setParamIn`/header-vote transaction path used by any council member.

### Recommendation
Add `FormatChecker` bounds for `RewardMintingAmount`, `RewardMinimumStake`, and `RewardStakingRewardThreshold` that reject values outside a sane range (e.g., a maximum multiple of the current/default value, or an absolute ceiling expressed in peb), similar to the existing lower/upper bound cross-check for KIP-71 base fee parameters. Document the expected unit/decimal scale explicitly in `param.go` and enforce it programmatically rather than relying on voter diligence, consistent with the "validate all data provided by owners/governance" recommendation in the referenced report.

### Proof of Concept
Conceptual: a council member submits a `governance.setParamIn("reward.mintingamount", true, <big.Int bytes for 6.4e28 instead of 6.4e18>, activation)` vote. `bigIntCanonicalizer` accepts any parseable non-negative integer [1](#0-0) ; `checkConsistency` has no magnitude-specific branch for `RewardMintingAmount` and defaults to accepting it [4](#0-3) . Once activated, `NewRewardConfig` reads this value verbatim into `MintingAmount` [5](#0-4) , and every subsequent block mints and distributes the inflated amount via `getRewardSummary`/`getDeferredRewardFull*` [6](#0-5) , permanently inflating supply until governance corrects it (requiring another vote/activation delay).

Note: I was unable to fully verify the exact `FormatChecker` body for `RewardMintingAmount` itself (only located `RewardMinimumStake`/`RewardStakingRewardThreshold` definitions) before the tool budget was exhausted; a Devin session with full file access should confirm this specific checker's implementation to finalize certainty.
