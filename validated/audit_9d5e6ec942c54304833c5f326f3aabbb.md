### Title
Malformed Bitcoin preprocess vector causes a panic during transaction signing - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`TransactionSignMachine::read_preprocess` accepts a serialized vector of one preprocess per transaction input without independently validating that the decoded vector has the expected length. `TransactionSignMachine::sign` then indexes each participant's vector by input index. A participant who supplies a syntactically valid but empty or truncated vector can therefore cause an out-of-bounds panic on the signing node.

### Finding Description
`TransactionSignMachine::read_preprocess` deserializes exactly `self.sigs.len()` preprocesses for each remote participant and returns them as `Vec<Preprocess<Secp256k1, ()>>`. [1](#0-0) 

During signing, the machine transforms the participant map by indexing `commitments[c]` for every transaction-input index `c`, without checking that each vector contains `self.sigs.len()` elements. [2](#0-1) 

Although `read_preprocess` reads a fixed number of items, the public `sign` API accepts the resulting `HashMap<Participant, Vec<...>>` directly and does not enforce the per-participant length invariant itself. The documented panic condition is passing a non-empty message or using unsupported cache APIs; malformed preprocess vectors are not documented as caller obligations. [3](#0-2) 

A similar unchecked invariant exists in `TransactionSignatureMachine::complete`, which calls `shares.remove(0)` on every participant-provided share vector and panics if one is empty. [4](#0-3) 

### Impact Explanation
An unprivileged signing participant can submit malformed protocol data that causes an indexing panic while another signer attempts to construct or complete a Bitcoin threshold transaction. If this code runs inside a validator, coordinator, or other process responsible for signing, the panic terminates that execution path and may halt the signing service rather than producing a recoverable `FrostError::InvalidParticipant` or `FrostError::InvalidPreprocess`.

### Likelihood Explanation
The attacker only needs to cause their party's `Preprocess` or `SignatureShare` value to be represented as an empty or short vector when `sign` or `complete` is called. No valid cryptographic material, private-key knowledge, threshold collusion, or malformed elliptic-curve encoding is required. Exploitation depends on the integration constructing a malformed vector programmatically or using a deserializer that permits length variation; `TransactionSignMachine::read_preprocess` itself always produces the expected length.

### Recommendation
Validate protocol-message lengths at the trust boundary and again in `sign`/`complete`. For every participant, require `commitments.len() == self.sigs.len()` and `shares.len() == self.sigs.len()` before indexing or removing elements. Return `FrostError::InvalidPreprocess(participant)` or `FrostError::InvalidShare(participant)` instead of indexing malformed input.

### Proof of Concept
The vulnerable operation is equivalent to:

```rust
// networks/bitcoin/src/wallet/send.rs
for c in 0 .. self.sigs.len() {
  for (_, commitments) in commitments.iter() {
    // Panics for an empty/truncated participant vector.
    let _ = commitments[c].clone();
  }
}
```

A minimal triggering state is a `TransactionSignMachine` with at least one input and a participant entry whose preprocess value is `vec![]`. Calling `sign` reaches `commitments[c]` with `c == 0`, producing an index-out-of-bounds panic. Likewise, `TransactionSignatureMachine::complete` panics when a participant's share vector is empty and `shares.remove(0)` is reached. [5](#0-4)
