### Title
Fee and transaction-weight checks omit the attacker-controlled OP_RETURN output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts up to 80 bytes of caller-controlled `data`, appends it as a zero-value `OP_RETURN` output to `tx_outs`, and includes that output in the transaction which is ultimately signed. [1](#0-0) [2](#0-1) 

However, both fee estimation calls pass only `payments` and the optional change script into `calculate_weight_vbytes`; the `data` output is not represented in either size calculation. [3](#0-2) [4](#0-3) 

### Finding Description
`calculate_weight_vbytes` models a transaction whose outputs are only the payment outputs and, optionally, one change output. [5](#0-4) [6](#0-5) 

The returned `SignableTransaction` nevertheless stores the complete `tx_outs` vector, including the `OP_RETURN` output. [7](#0-6) 

Consequently, `needed_fee`, the minimum-fee rejection, and the `MAX_STANDARD_TX_WEIGHT` check are evaluated against a smaller transaction than the one whose sighashes are later generated and signed. [8](#0-7) [9](#0-8) 

This mirrors the report’s checked-value/effective-value mismatch: the security policy is applied to a modeled transaction while authorization produces a larger transaction containing additional attacker-controlled bytes. [10](#0-9) [11](#0-10) 

### Impact Explanation
An approximately 80-byte payload adds the output’s serialized size to the actual transaction without increasing `needed_fee`, so the signed transaction can have a materially lower fee rate than requested and can fall below Bitcoin’s default minimum relay fee. [3](#0-2) 

For transactions already near the standard-weight boundary, the omitted output can also make the actual signed transaction exceed `MAX_STANDARD_TX_WEIGHT` even though the constructor accepted it. [8](#0-7) 

The result is an unintended threshold-signed transaction which ordinary Bitcoin nodes may refuse to relay, delaying or preventing spending of the selected wallet outputs until another signing attempt is coordinated. [12](#0-11) 

### Likelihood Explanation
The `data` field is a public constructor argument, requires no malformed encoding, and is accepted whenever it is at most 80 bytes. [13](#0-12) [1](#0-0) 

Any caller which supplies transaction metadata as data can trigger the mismatch on an otherwise valid signing request, and all honest signers can still produce the resulting transaction because the constructor reports success. [7](#0-6) [14](#0-13) 

### Recommendation
Calculate weight and virtual size from the complete output set, including the `OP_RETURN` output, or construct the candidate transaction first and derive `weight`, `vsize`, `needed_fee`, and the standardness check from that final transaction. [15](#0-14) 

The same complete transaction should be used for the minimum-fee and maximum-weight checks before returning `SignableTransaction`. [16](#0-15) 

### Proof of Concept
A minimal check is to construct two otherwise identical transactions, one without data and one with an 80-byte payload:

```rust
// Conceptual PoC for networks/bitcoin/src/wallet/send.rs.
let fee_rate = 1;
let without_data =
  SignableTransaction::new(inputs.clone(), &payments, change.clone(), None, fee_rate)
    .unwrap();
let with_data =
  SignableTransaction::new(inputs, &payments, change, Some(vec![0; 80]), fee_rate)
    .unwrap();

// The omitted output produces identical fee accounting.
assert_eq!(with_data.needed_fee(), without_data.needed_fee());

// The signed transaction is nevertheless larger.
assert!(with_data.transaction().vsize() > without_data.transaction().vsize());

// Therefore the actual fee rate is below the requested rate.
assert!(
  with_data.fee() <
    u64::try_from(with_data.transaction().vsize()).unwrap() * fee_rate
);
```

The equality holds because `needed_fee` is derived only from the payment/change model, while `transaction()` returns the final transaction containing the `OP_RETURN` output. [10](#0-9) [7](#0-6)
