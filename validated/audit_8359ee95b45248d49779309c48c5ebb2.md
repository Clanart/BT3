### Title
`ThresholdKeys::new`/`ThresholdKeys::read` accept a secret share with no proof it matches the participant's verification share, letting crafted bytes declare an arbitrary group key - (File: crypto/dkg/src/lib.rs)

### Summary

The external report describes an orphan endpoint that performs a state-changing action without any authorization check binding the caller to the object being modified. The analog in Serai is `ThresholdKeys::read` (a listed untrusted-bytes entry point) feeding into `ThresholdKeys::new`: the constructor validates the *count* and *index range* of `verification_shares`, but never checks that `secret_share` actually belongs to the claimed participant — i.e. it never verifies `C::generator() * secret_share == verification_shares[params.i()]`. The group key is then derived solely from the attacker-controlled `verification_shares` map (`crypto/dkg/src/lib.rs:376-378`). The result is a fully "valid" `ThresholdKeys` object asserting membership in an arbitrary group key while holding a secret share that corresponds to a different key entirely.

### Finding Description

`ThresholdKeys::new` performs only two checks before building the key set:

- `verification_shares.len() == params.n()` (`crypto/dkg/src/lib.rs:355-360`)
- every participant index `<= params.n()` (`crypto/dkg/src/lib.rs:361-365`)

It then computes `group_key` by interpolating `verification_shares[1..=t]` (line 376-378) and stores `secret_share` verbatim. Nowhere is the consistency relation `G * secret_share == verification_shares[i]` checked. `ThresholdParams::new` likewise only checks `t <= n` and `i <= n` (`crypto/dkg/src/lib.rs:166-179`).

`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) deserializes `t`, `n`, `i`, the interpolation mode, the secret share, and all `n` verification shares directly from the reader, then calls `ThresholdKeys::new`. Every field is attacker-controlled:

- `verification_shares` can encode shares of a polynomial whose intercept is an attacker-chosen group key (or honest key shares copied from a real multisig, combined with a mismatched `secret_share`/`i` pair).
- `secret_share` can be an arbitrary scalar unrelated to `verification_shares[i]`.

By comparison, the honest generators do enforce this relation implicitly: `dkg::dealer::key_gen` computes each verification share as `G * polynomial(i)` (`crypto/dkg/dealer/src/lib.rs:51-53`), and PedPoP verifies each received share against the sender's committed polynomial via `share_verification_statements` in a `BatchVerifier` (`crypto/dkg/pedpop/src/lib.rs:487-499`). The deserialization path is the unguarded orphan: it reconstructs the same trust-critical invariant from wire bytes with zero verification.

The downstream signing code even anticipates this failure mode: `AlgorithmSignatureMachine::complete` falls back to per-share blame verification only when the aggregate signature fails, and comments "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (`crypto/frost/src/sign.rs:492-494`) — acknowledging that `read` can produce semantically invalid keys, yet no check exists to reject them at the boundary.

### Impact Explanation

An attacker who can supply bytes to `ThresholdKeys::read` produces keys where `group_key()` reports an attacker-chosen key while `original_secret_share()` is inconsistent with it. Concretely:

- **Funds reported received that are not spendable.** An integrator (e.g. a processor loading keys and registering `group_key` with its scanner, as in `processor/src/key_gen.rs` and `processor/src/multisigs/scanner.rs`) will accept deposits to the declared group key. At signing time, `view()` interpolates the mismatched `secret_share`, producing a signature share that fails `verify_share` against `verification_shares[i]` (`crypto/frost/src/sign.rs:476-484`). No valid signature can ever be produced for the declared group key, so received funds are permanently unspendable.
- **False blame / framing.** In `complete`, the inconsistent holder's own share fails batch verification and is surfaced as `FrostError::InvalidShare(l)` attributed by participant index — the deserialization victim is blamed as a faulty signer, indistinguishable from a malicious participant.
- **Silent key substitution.** Because `read` also accepts `Interpolation::Constant` vectors of arbitrary length coefficients and arbitrary verification shares, an attacker fully controls which group identity a deserialized key claims, with no integrity anchor to the secret material.

### Likelihood Explanation

Likelihood depends on the deployment exposing `ThresholdKeys::read` to untrusted input — e.g. key import/recovery flows, replicated key databases, or any channel where serialized `ThresholdKeys` cross a trust boundary. The prompt's threat model explicitly designates `ThresholdKeys::read` as a reachable untrusted-bytes surface, and the fix requires no protocol interaction: a single crafted byte buffer suffices. Severity is High (integrity loss / permanent fund lockup) rather than Critical because it requires a path that feeds attacker bytes into key deserialization and does not leak secret material.

### Recommendation

In `ThresholdKeys::new` (so all constructors and `read` are covered), add the binding check:

```rust
if (C::generator() * secret_share.deref()) != verification_shares[&params.i()] {
  Err(DkgError::InvalidShare)?  // new error variant
}
```

Optionally also verify the `verification_shares` map is self-consistent for `Interpolation::Constant` (each share equals `c[i] * G`-derived expectations is N/A since shares are arbitrary points, but the secret-share check is the necessary and sufficient binding). Rejecting mismatched keys at deserialization prevents the semantically-invalid-keys state the FROST code comments already acknowledge.

### Proof of Concept

```rust
use rand_core::OsRng;
use ciphersuite::{group::ff::Field, Ciphersuite};
use dkg::*;
use std_shims::collections::HashMap;
use zeroize::Zeroizing;

// For any PrimeGroup ciphersuite C:
fn poc<C: Ciphersuite>() {
  let t: u16 = 2;
  let n: u16 = 3;
  let i = Participant::new(1).unwrap();

  // Attacker-chosen verification shares describing a DIFFERENT key
  // than the secret_share below.
  let attacker_secret = C::F::random(&mut OsRng);
  let mut verification_shares = HashMap::new();
  for l in 1 ..= n {
    let l = Participant::new(l).unwrap();
    // Shares of a polynomial with intercept = attacker-chosen group key
    verification_shares.insert(l, C::generator() * C::F::random(&mut OsRng));
  }

  // A secret share inconsistent with verification_shares[i]
  let secret_share = Zeroizing::new(C::F::random(&mut OsRng));
  assert_ne!(
    C::generator() * *secret_share,
    verification_shares[&i],
  );

  // Accepted: no binding check between secret_share and verification_shares[i]
  let keys = ThresholdKeys::<C>::new(
    ThresholdParams::new(t, n, i).unwrap(),
    Interpolation::Lagrange,
    secret_share,
    verification_shares,
  )
  .expect("inconsistent keys accepted without verification");

  // group_key() now reports the attacker-declared key; any signature share
  // produced from `keys.view(...)` will fail verification against
  // original_verification_share(i), leaving funds sent to group_key()
  // permanently unspendable.
  let _ = keys.group_key();
}
```

The equivalent wire-level PoC serializes the same inconsistent fields and passes them to `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), which succeeds for the same reason.
