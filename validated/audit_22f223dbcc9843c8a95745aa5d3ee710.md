## Title
Partial-commit line selection is silently re-mapped to the wrong lines when the working-tree file changes between diff render and staging (TOCTOU on `DiffSelection` indices) - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual lines/hunks of a modified file to stage ("partial commit"). The line selection (`DiffSelection`) is keyed by **absolute line index** into a specific diff snapshot. That snapshot can go stale between the moment it is rendered and the moment it is used to build the patch that is `git apply --cached`'d into the index, and the code path that reconciles staleness only prunes indices that no longer exist — it does not verify that the surviving indices still refer to the *same content* the user actually clicked on.

### Finding Description
The diff shown to the user is stored and periodically refreshed by `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts`. When a refresh happens, the code explicitly acknowledges the staleness problem: [1](#0-0) 

```
// The diff might have changed dramatically since last we loaded it.
// Ideally we would be more clever about validating that any partial
// selection state is still valid by ensuring that selected lines still
// exist but for now we'll settle on just updating the selectable lines
// such that any previously selected line which now no longer exists or
// has been turned into a context line isn't still selected.
```

This only filters the `selectedLines` bitset down to indices that are still `isIncludeableLine()` in the *new* diff — it does **not** re-verify that index N in the new diff corresponds to the same source line the user selected in the old diff. If the file changes in a way that shifts line positions without eliminating them (e.g., another line is added/removed above the hunk, or an editor auto-format/line-ending normalization occurs, or a background process — an IDE, a git hook, a file watcher, or a build tool spawned from an untrusted repo like a `.vscode` task or `husky`/`lint-staged` pre-commit hook — rewrites the file), the previously-selected index numbers remain "valid" (still includeable lines) but now point at *different* text.

When the commit is finally created, `stageFiles` (`app/src/lib/git/update-index.ts`) calls `applyPatchToIndex` for any file with a partial selection: [2](#0-1) 

`applyPatchToIndex` re-fetches a *fresh* diff right before formatting the patch: [3](#0-2) 

`formatPatch` then walks this fresh diff and decides what to include purely based on `file.selection.isSelected(absoluteIndex)`: [4](#0-3) 

Nowhere in this pipeline is there a content-based re-validation (e.g., hashing the selected hunk text, or diffing the diff) comparable to the missing `reAccrueBigBangMarkets()` call in the Tapioca report — the state used to make a security/integrity-relevant decision (which bytes get committed) is trusted without being freshly reconciled against what the user actually saw and clicked.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug class. If an attacker can influence file contents in the working tree between the user's diff review and the click on "Commit" (e.g., via a build/watch task defined in a freshly cloned malicious repository, a Husky/lint-staged pre-commit-like hook, or a race with another tool operating on the same file), the user's carefully curated "select only these lines" partial commit can end up staging/committing attacker-inserted or attacker-altered lines that the user never reviewed or intended to include — while the UI shows the (now stale) old selection as if it were still accurate. This can smuggle unreviewed code into a commit that is later pushed, without any error or warning surfaced to the user.

### Likelihood Explanation
Medium-low. It requires a window where the working copy changes between diff load and commit, and requires that change to preserve enough "includeable" line slots to avoid the pruning safeguard while still shifting content — realistic with common developer tooling (auto-formatters, watch-mode builds, pre-commit hooks) that a malicious/compromised repository can bundle and that commonly run on save or on a timer without the user manually invoking them. It does not require local/physical access, admin rights, or social engineering beyond opening/using a repository that ships such tooling, which is normal GitHub Desktop usage.

### Recommendation
Before applying a partial-selection patch, re-validate the previously selected diff/hunks against the fresh diff by content (not just index existence) — e.g., re-map selections using a text/hash comparison of the corresponding old vs. new lines, and if a mismatch is detected, invalidate the stale selection and force the user to re-review/re-select before allowing the commit to proceed, rather than silently trusting index-based `DiffSelection` bitsets across diff refreshes.

### Proof of Concept
Conceptual repro (not fully executed against the live app in this session):
1. Open a repository containing a modified file with multiple hunks, and a task/hook configured to run on file save or periodically (e.g., a formatter or lint-staged style hook) that rewrites lines in that file without changing the total number of diff-relevant/includeable lines (e.g., reordering two adjacent changed lines, or normalizing whitespace).
2. In Changes view, select only specific lines/hunks to commit (partial selection), leaving other hunks unselected.
3. Before clicking "Commit," let the background task rewrite the file so that the line at the previously-selected absolute index now contains different content, while `updateChangesWorkingDirectoryDiff` refreshes the diff and only prunes now-nonexistent indices (per the code at `app-store.ts:3478-3497`).
4. Click "Commit." `stageFiles`/`applyPatchToIndex` (`app/src/lib/git/update-index.ts:163-168`, `app/src/lib/git/apply.ts:52-81`) builds the patch from the fresh diff using the stale `DiffSelection` indices, staging/committing content the user did not review as "selected."

Because the exact end-to-end UI timing and hook-triggering mechanics were not verified by running the app (only static code inspection), this should be validated dynamically by a Devin session with a checkout of the repo and a live app build before treating it as a confirmed, reproducible finding rather than a code-level design gap.
