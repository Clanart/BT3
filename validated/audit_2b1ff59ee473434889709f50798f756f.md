## Analog Found: Shared, Persistent `dispatcher` Balance Lets Order Settlement Absorb Foreign/Attacker-Injected Funds in `IntentGatewayV2.placeOrder`

### Title
Balance-based sweep of a shared `dispatcher` contract in `placeOrder` misattributes externally-injected or cross-order token balances into the current order's escrow/dust accounting - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
The PoolTogether report's core broken invariant is: *a state-mutating admin action is gated by a live `token.balanceOf(address(this))` check that any unprivileged actor can move, so the guard measures a value that is not exclusively under the caller's control.* The local analog in Hyperbridge is structurally the same primitive but applied to fund accounting rather than an admin guard: `IntentGatewayV2.placeOrder()`'s predispatch flow computes how much of each input token the gateway "received" for an order by reading `IERC20(token).balanceOf(dispatcher)` / `address(dispatcher).balance` on a single, shared `_params.dispatcher` contract, then sweeps the *entire* balance rather than the amount attributable to that specific order. [1](#0-0) 

### Finding Description
In the predispatch branch of `placeOrder`, the gateway:
1. Transfers exactly `order.predispatch.assets[i].amount` to the shared `dispatcher` address (`_params.dispatcher`). [2](#0-1) 
2. Invokes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — arbitrary, order-supplied calldata (e.g., a swap) executed by the dispatcher.
3. Builds `transferCalls` using `balance = IERC20(token).balanceOf(dispatcher)` (or `address(dispatcher).balance` for native) — the dispatcher's *full current balance*, not the amount produced by this order's own predispatch call — and sweeps that entire balance to the gateway. [3](#0-2) 
4. Computes `received` as the delta in the gateway's own balance and treats anything above `order.inputs[i].amount` as "dust," while treating anything at or below it as the order's actual escrowed `amount`, which subsequently drives fee computation and the commitment hash. [4](#0-3) 

Because `dispatcher` is one shared, persistent contract address reused across every `placeOrder` call (it is read from storage via `_params.dispatcher`, not deployed fresh per order), its balance is not scoped to a single order. Any of the following can leave a balance sitting in `dispatcher` before an unrelated order's sweep step runs:
- A prior order's predispatch call (e.g., a swap) leaving residual/leftover output tokens in the dispatcher (slippage, partial fills, rounding).
- Any unprivileged party directly transferring tokens to the known `dispatcher` address (a plain ERC-20 `transfer`, which is entirely public and requires no special permission).

Whichever order's `placeOrder` executes the sweep next will pull the dispatcher's *entire* balance of that token via `balanceOf(dispatcher)`, exactly mirroring the VaultBooster pattern where `balanceOf(address(this))` is read live and can be altered by an outside call between when the value is expected and when it is consumed. The difference from the seed report is that here the corrupted value (`balance`) doesn't merely block a config update — it is fed directly into the protocol's settlement/dust logic, so a stale or externally-donated balance in the shared dispatcher gets absorbed into whichever order happens to sweep it next, misattributing value between orders/users rather than only causing a revert-based griefing effect.

### Impact Explanation
This falls under "logic attacks" / "wrong beneficiary or amount" in the accepted impact set: the amount the gateway records as `received` for a specific order's input — which flows into the commitment hash, protocol fee computation, and the escrowed `order.inputs[i].amount` used for downstream settlement — is derived from a balance read on a shared contract that is not exclusively populated by that order's own predispatch call. Legitimate leftover value belonging to one order (or a user's own overpayment) can be swept and permanently reclassified as "dust" absorbed by a completely different, unrelated order's transaction, and conversely a caller can engineer their own predispatch call to leave a residual balance timed to land inside another order's sweep window.

### Likelihood Explanation
Exploiting this requires only standard permissionless actions already exposed by the contract: calling `placeOrder` with predispatch calldata (which every user of this flow already does) or sending an ordinary ERC-20 transfer to the publicly-known `dispatcher` address — no relayer, prover, admin, or governance role is needed, and no proof forgery is involved. The main uncertainty (noted below) is the exact concurrency/temporal window: whether typical predispatch calls (e.g., swaps with slippage) reliably leave nonzero residual balances in the shared dispatcher within the same block cycle as other orders, and whether `CallDispatcher.sol`'s `dispatch()` provides any isolation. I was not able to fully review `evm/src/utils/CallDispatcher.sol`'s implementation in this session, so I cannot confirm whether it self-clears balances per call or truly persists state across independent `placeOrder` transactions from different users. This should be verified against the actual `CallDispatcher.sol` source before treating this as confirmed-exploitable in production.

### Recommendation
Do not size the sweep by the dispatcher's total live balance. Either:
- Have `dispatch()` return the exact amount produced by the executed predispatch call (rather than being inferred later from balance deltas on a shared contract), or
- Deploy an ephemeral, order-scoped executor (e.g., a minimal proxy/clone per order) so its balance is provably attributable to only that order's predispatch call, or
- At minimum, snapshot the dispatcher's balance immediately before step 1 (the initial transfer-in) and cap the swept amount to `balanceAfterPredispatch - balanceBeforeAnyTransferIn`, so any balance that existed in the dispatcher prior to this specific order's involvement is excluded from this order's accounting.

### Proof of Concept
Conceptual sequence (pending confirmation against `CallDispatcher.sol`'s actual semantics):
1. Attacker (or a preceding order's slippage) leaves `X` extra units of `tokenA` sitting in the shared `_params.dispatcher` address, e.g. via a plain `tokenA.transfer(dispatcher, X)`.
2. A user submits `placeOrder` for an order whose `predispatch.assets` includes `tokenA` with `requiredAmount = Y`.
3. The gateway transfers `Y` of `tokenA` to `dispatcher`, runs the order's predispatch call, then reads `balance = tokenA.balanceOf(dispatcher)`, which now equals `Y + X` (plus whatever the predispatch call itself produced) instead of just the order's own output.
4. The full `Y + X` (+ produced amount) is swept to the gateway; per lines 270–275, any amount above the order's declared `order.inputs[i].amount` is emitted as `DustCollected` and absorbed by the protocol rather than returned to whoever the `X` actually belonged to, while the order's own accounted amount can also be skewed depending on how the predispatch output and injected balance interact. [5](#0-4)
