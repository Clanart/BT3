### Title
Malicious preprocess nonce commitments force the aggregate nonce `R` to the point at infinity, deterministically panicking `Hram::hram` during FROST signing (DoS) - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
A participant in a FROST signing session for a Bitcoin transaction can submit a crafted `Preprocess` whose nonce commitments cancel the entire aggregate nonce, making `nonce_sums[0][0]` the point at infinity. When the honest signer computes the BIP-340 challenge inside `sign_share`, `Hram::hram` calls `x(R)`, which calls `ProjectivePoint::to_encoded_point` and `.expect("point at infinity")`, panicking and crashing the signing node. This mirrors the bug class of CVE-2018-2640 (low-privileged, network-reachable availability loss). [1](#0-0) 

### Finding Description
`AlgorithmSignMachine::sign` computes per-participant bound nonces `D_l + rho_l * E_l` summed into `B.nonces`, then calls `sign_share` with `nonce_sums` (`&Rs`). [2](#0-1)  For the Bitcoin `Schnorr` algorithm, `sign_share` delegates to `IetfSchnorr::sign_share`, which calls `Hram::hram(&nonce_sums[0][0], &params.group_key(), msg)`. [3](#0-2)  `Hram::hram` unconditionally calls `x(R)`, which does `key.to_encoded_point(true)` then `.x().expect("point at infinity")` — a hard panic when `R` is the point at infinity. [4](#0-3)  The doc comments explicitly acknowledge this panic ("If either `R` or `A` is the point at infinity, this will panic") but assume it has "a negligible probability ... even with malicious participants present". [5](#0-4)  That assumption is wrong when the peer's point encoding accepts the point at infinity: the attacker fixes their `E` commitment to the identity point, making their rho-weighted contribution `rho_a * E_a = identity` regardless of `rho_a` (which is bound to their commitments and therefore not freely choosable otherwise), and sets `D_a = -(sum of everyone else's D_j + rho_j * E_j)`, which is computable because all other preprocesses are public and `rho_j` is a deterministic hash. [6](#0-5)  `Commitments`/`Preprocess` bytes are attacker-controlled via `read_preprocess`. [7](#0-6) 

### Impact Explanation
An unprivileged co-signer (any participant index accepted into the signing set — `sign` only validates set membership and indices, not commitment contents) [8](#0-7)  causes a deterministic panic in every honest participant's `sign` call for that session, crashing the signing task/node rather than merely returning `FrostError`. On Rust code paths where panics abort or unwind past async boundaries this is a complete, repeatable availability loss of the multisig signing service — the same "hang or frequently repeatable crash" impact class as CVE-2018-2640.

### Likelihood Explanation
The attack requires (a) the attacker being a declared participant able to deliver preprocesses (true in every FROST deployment — preprocesses are the public round-1 input), and (b) `Secp256k1::read_G` accepting a SEC1 identity encoding (`0x00`) — k256's `EncodedPoint`/`ProjectivePoint::from_bytes` decodes `0x00` to the identity point, so unless `read_G` adds an explicit `is_identity` rejection (none is visible in the `read_preprocess` path), the crafted preprocess is accepted. [7](#0-6)  The attacker must submit their preprocess last or adaptively, which is realistic since preprocess collection is ordered/iterative at callers (`signer.rs`, `cosigner.rs` process peer preprocesses after generating their own). [9](#0-8)  Deterministic, repeatable, low cost.

### Recommendation
Reject identity points in `Commitments::read`/`C::read_G` for FROST nonce commitments (each `D`/`E` must be non-identity), and/or defensively check `nonce_sums` and `group_key` for identity before calling `hram`, returning `FrostError::InvalidPreprocess(participant)` for the contributor instead of panicking. The `x()`/`x_only()` helpers should also return `Option`/`Result` rather than panicking. [10](#0-9) 

### Proof of Concept
1. Establish a t-of-n Secp256k1 `ThresholdKeys` set and run `TransactionSignMachine`/`AlgorithmSignMachine<Schnorr>` signing where the attacker controls participant `a`.
2. Collect the honest preprocesses. For each other participant `j`, compute `rho_j` from the `FROST_rho` transcript (`group_key || hash_msg(msg) || hash_commitments(preprocesses transcript)`). [11](#0-10) 
3. Build attacker's `Preprocess` with `E_a = identity` (single `0x00` SEC1 encoding) and `D_a = -Σ_{j≠a}(D_j + rho_j·E_j)`; serialize so `read_preprocess` accepts it.
4. Honest signer's `B.nonces` yields `nonce_sums[0][0] = identity`; `Schnorr::sign_share` → `Hram::hram` → `x(R)` → `.expect("point at infinity")` panics, crashing the signer. Repeatable on every attempt while the attacker participates.

Caveat: if the deployed `Secp256k1::read_G` implementation explicitly rejects the identity encoding, the fixed-point of `rho_a` over `D_a, E_a` makes the forced-identity nonce infeasible and this reduces to the documented negligible-probability panic; verification of the exact `read_G` identity handling for the kp256/curve backend was not confirmed within the indexed sources.
