### Title
Untrusted `ReceivedOutput` deserialization allocates attacker-declared script memory - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

`ReceivedOutput::read` accepts an arbitrary byte stream, deserializes the embedded `TxOut` with Bitcoin consensus decoding, and permits the transaction-output script's declared length to control allocation before any bytes are read. An attacker can supply a compact encoding that requests approximately the Bitcoin decoder's maximum vector allocation while providing little or no script data. [1](#0-0) 

### Finding Description

`ReceivedOutput` is Serai's representation of a spendable Bitcoin output and consists of an HDKD scalar offset, a `TxOut`, and an `OutPoint`. [2](#0-1)  During deserialization, `ReceivedOutput::read` first consumes the scalar and then calls `TxOut::consensus_decode` and `OutPoint::consensus_decode` on the remaining unbounded reader. [1](#0-0)  A `TxOut` contains a compact-size-prefixed `script_pubkey`; the consensus decoder interprets that untrusted length and prepares storage for the declared script before the script bytes have necessarily arrived. [3](#0-2) 

The production read path has no Serai-imposed serialized-size limit and no incremental/chunked-read strategy. It also wraps the caller's reader in a zero-capacity `BufReader`, so `BufReader` itself does not provide a memory bound or bounded prefetching. [4](#0-3) 

This is directly comparable to the Scrapy bug class: attacker-controlled size metadata causes memory allocation/read amplification for data that is not actually present or that need not be retained.

### Impact Explanation

An unprivileged party that can feed bytes to `ReceivedOutput::read` can repeatedly request the largest allocation accepted by the Bitcoin consensus decoder while sending only the small prefix needed to declare that length. This creates transient multi-megabyte allocations per tiny input. Repeated parsing attempts can increase allocator pressure, fragment memory, and—in constrained or concurrently loaded processes—contribute to process termination or service unavailability.

### Likelihood Explanation

The vulnerable function is public and explicitly intended for byte deserialization. [5](#0-4)  No authentication, message-size cap, or protocol context is required by the function signature. The triggering encoding is only a valid scalar, an output amount, and a compact-size script length; parsing can fail immediately afterward, while still retaining the attacker-selected allocation until the read error unwinds.

### Recommendation

Do not pass the untrusted reader directly into `TxOut::consensus_decode`. Instead:

- Enforce a strict `ReceivedOutput` serialization limit appropriate for Serai's Taproot outputs.
- Decode the `TxOut` amount and script length manually before allocating.
- Reject script lengths exceeding a fixed bound; Serai-created outputs are expected to be small Taproot scripts, while `write` serializes the whole `TxOut` through the generic consensus format. [6](#0-5) 
- If variable output forms must remain supported, read the declared script incrementally and abort once the Serai bound is exceeded.
- Add regression tests asserting that a declared multi-megabyte script followed by EOF fails without allocating the full declared amount.

### Proof of Concept

The following payload uses a zero scalar, an eight-byte amount, and a Bitcoin compact-size `0xff` prefix declaring a four-million-byte script. The remainder of the `TxOut` is absent:

```rust
use bitcoin_serai::wallet::ReceivedOutput;

#[test]
fn received_output_declared_script_allocation() {
    // Canonical serialized scalar offset: 0.
    let mut payload = [0; 32].to_vec();

    // TxOut value, little-endian.
    payload.extend(0u64.to_le_bytes());

    // CompactSize uint64 encoding declaring a 4,000,000-byte script.
    payload.push(0xff);
    payload.extend(4_000_000u64.to_le_bytes());

    // No script body or OutPoint follows. The decoder receives a request for the
    // maximum-sized script allocation before discovering EOF.
    let result = ReceivedOutput::read(&mut payload.as_slice());
    assert!(result.is_err());
}
```

The precise memory behavior depends on the resolved `bitcoin` decoder implementation, but Serai's code provides no independent bound before invoking that decoder. [7](#0-6)
