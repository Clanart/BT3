### Title
Same-chain partial-fill "final-leg" rounding fix over-releases escrow when two output legs share an input token - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The rounding-dust fix added to `_fillSameChain` (documented in tests as "Finding #4") makes the *last* fill of an output-token pair release the *entire remaining balance* of `_orders[commitment][inputToken]` instead of the proportional amount for that leg. Because `_orders` is keyed only by `(commitment, tokenAddress)` and not by output-index, an order whose two (or more) output legs happen to escrow the **same input token** lets a solver complete one leg first and drain the whole shared escrow bucket — including the portion that should still back the other, unfilled leg.

### Finding Description
`_orders[commitment][token]` aggregates escrow across *all* `order.inputs[i]` entries that use the same token address [1](#0-0) . Nothing in `placeOrder`/`_fillSameChain` enforces that each index `i` uses a distinct input token, so a user-authored order with `inputs[0].token == inputs[1].token` is valid and legal.

In `_fillSameChain`, the per-leg escrow release is computed as:
```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [2](#0-1) 

When leg `i` reaches `amountFilled == totalRequired`, the code reads the *entire current balance* of `_orders[commitment][token]` rather than the proportional share belonging to leg `i`. If a second leg `j` (still unfilled or only partially filled) shares the same input token, its backing funds are included in that "entire balance" and get paid to the solver who only completed leg `i`. All `escrowedInputs[]` amounts are computed in the same loop *before* `_withdraw` decrements anything [3](#0-2) , so the read is against the pre-decrement pool.

`_withdraw` then transfers this over-counted amount to the solver and decrements the shared bucket by that full amount [4](#0-3) . Any subsequent attempt to fill or cancel the still-open leg reads `_orders[commitment][token] == 0` and reverts with `UnknownOrder()` — the remaining funds are already gone, transferred to the first solver as an unearned bonus, and the user/beneficiary of the unfilled leg permanently loses their share.

### Impact Explanation
This is a direct loss-of-funds bug reachable by any unprivileged solver through the public `fillOrder` entrypoint, matching the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" impact category. A solver can construct or wait for (or even induce, since orders are user-authored and public) an order with duplicated input tokens across legs, fill only the cheapest/fastest leg to completion, and walk away with escrow that belonged to the other leg. The victim (order user or the intended beneficiary of the other leg) cannot recover the drained portion — cancellation of the remaining leg reverts with `UnknownOrder()`, permanently locking/losing those funds.

### Likelihood Explanation
Likelihood is moderate: it requires an order with two or more output legs backed by the same input token, which is a legitimate configuration (e.g., a single USDC input split across two different output-token legs) not prevented by the contract. Any solver — not a privileged or malicious-relayer role — can trigger the exploit simply by choosing fill order and amounts on a normal `fillOrder` call, so no compromised infrastructure or governance access is needed.

### Recommendation
Track escrow per `(commitment, outputIndex)` instead of aggregating purely by `(commitment, token)`, or compute the "last-fill" release as `min(_orders[commitment][token], proportionalRemainder)` using a per-leg remaining-amount ledger rather than reading the shared token bucket directly. Alternatively, reject orders at `placeOrder` time whose `inputs[i].token` repeats across indices, eliminating the shared-bucket ambiguity that the rounding fix silently assumes away.

### Proof of Concept
1. User places a same-chain order with two output legs: `outputs[0] = {DAI, 100}`, `outputs[1] = {USDT, 100}`, both backed by `inputs[0] = {USDC, 60}` and `inputs[1] = {USDC, 40}` (same token, `_orders[commitment][USDC] = 100` total).
2. Solver A calls `fillOrder` providing exactly `100 DAI` for leg 0 only (`solverOutputs[1].amount = 0` or omitted/zero so leg 1 stays untouched — `remaining>0 && solverAmount==0` keeps `isFullyFilled=false` for leg 1 per line 76-79 of `IntrinsicIntents.sol`).
3. For leg 0, `amountFilled == totalRequired` is true, so `escrowedAmount = _orders[commitment][USDC] = 100` (the full bucket, not the intended 60). Solver A receives all 100 USDC even though only leg 0 (nominally backed by 60 USDC) was completed.
4. `_orders[commitment][USDC]` is now 0.
5. Any later attempt to fill leg 1 (USDT) or to cancel the order reverts with `UnknownOrder()` in `_withdraw`/`_cancelSameChain`, permanently losing the 40 USDC that should have backed leg 1.
