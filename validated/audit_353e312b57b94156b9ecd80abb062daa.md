### Title
Cross-shop online session/scope collision via `shopify_user_id`-only lookup - ([File: lib/shopify_app/session/user_session_storage_with_scopes.rb])

### Finding Description
`ShopifyApp::UserSessionStorageWithScopes::ClassMethods#store` performs `user = find_or_initialize_by(shopify_user_id: user.id)` and then unconditionally overwrites `shopify_token`, `shopify_domain`, `access_scopes`, and `expires_at` on that single record. [1](#0-0) 
This lookup key is `shopify_user_id` alone, with no `shopify_domain`/shop component, so any two OAuth callbacks whose `AssociatedUser#id` collides will resolve to the *same* row regardless of which shop the session belongs to. `retrieve_by_shopify_user_id` then reconstructs the session (`shop`, `access_token`, `scope`, `expires`) purely from that shared row. [2](#0-1) 

This is invoked from `ShopifyApp::SessionRepository.store_session`/`store_user_session`, which is called by `CallbackController#save_session` after every OAuth callback for an online session (`session.associated_user`), and `retrieve_user_session_by_shopify_user_id`/`load_session` is used to look sessions back up keyed only by `shopify_user_id`. [3](#0-2) [4](#0-3) [5](#0-4) 

This is structurally identical to the already-known collision in `ShopifyApp::UserSessionStorage#store`, which the code comments even acknowledge is the reason this concern is deprecated in favor of the non-scoped one ("UserSessionStorage instead, which now handles access_scopes and expires_at automatically") — but the deprecated concern is still shipped and can still be included by any app. [6](#0-5) 

No shop-scoped uniqueness constraint, secure-compare check, or scope-binding validation exists anywhere in this file or in `SessionRepository` to prevent a `shopify_user_id`-only collision from clobbering `access_scopes`/`expires_at`/`shopify_token`/`shopify_domain` written for a different shop.

### Impact Explanation
If two distinct shops' associated users end up with the same `shopify_user_id` value in the host app's database (e.g., duplicate/synthetic IDs from development/partner stores, or any app-level path that lets the numeric id collide), the last `store` call overwrites `access_scopes`, `expires_at`, `shopify_token`, and `shopify_domain` for both shops on one shared row. A subsequent `retrieve_by_shopify_user_id` for the "victim" shop's user then returns the "attacker" shop's `access_token` and scope string (e.g. `write_orders`), i.e., cross-shop session/scope confusion and token disclosure — matching Shopify's "cross-shop data access" / session confusion impact class.

### Likelihood Explanation
This requires `shopify_user_id` collisions to occur across distinct shops, which is not attacker-forgeable through a single HTTP request against the callback endpoint — the `associated_user.id` embedded in `api_session` comes from Shopify's own OAuth/token-exchange response validated via `ShopifyAPI::Auth::Oauth.validate_auth_callback`, not from raw request params. Exploitability therefore depends on the pool of `shopify_user_id` values actually colliding across shops (e.g., development stores, staff accounts reused across partner orgs, or an app model that doesn't enforce composite uniqueness), which is an environment/model precondition rather than something forgeable purely by request tampering.

### Recommendation
Scope the lookup/uniqueness by `(shopify_domain, shopify_user_id)` instead of `shopify_user_id` alone in `store`, `retrieve_by_shopify_user_id`, and `destroy_by_shopify_user_id`, and add a composite DB uniqueness constraint. Since the concern is deprecated, the stronger recommendation is to remove/stop shipping `UserSessionStorageWithScopes` (per its own deprecation notice) rather than patch it, and steer apps to `UserSessionStorage`, which should itself also be scoped by shop domain, not just `shopify_user_id`.

### Proof of Concept
```ruby
class UserSessionStorageWithScopesCollisionTest < ActiveSupport::TestCase
  test "colliding shopify_user_id across shops overwrites access_scopes/expires_at" do
    shop_a_user = ShopifyAPI::Auth::AssociatedUser.new(id: 42, first_name: "", last_name: "",
      email: "", email_verified: false, account_owner: false, locale: "", collaborator: false)
    shop_b_user = ShopifyAPI::Auth::AssociatedUser.new(id: 42, first_name: "", last_name: "",
      email: "", email_verified: false, account_owner: false, locale: "", collaborator: false)

    session_a = ShopifyAPI::Auth::Session.new(shop: "shop-a.myshopify.com", access_token: "tok-a",
      scope: "read_orders", expires: 1.hour.from_now)
    session_b = ShopifyAPI::Auth::Session.new(shop: "shop-b.myshopify.com", access_token: "tok-b",
      scope: "write_orders", expires: 2.hours.from_now)

    User.store(session_a, shop_a_user)
    User.store(session_b, shop_b_user) # same shopify_user_id => same row overwritten

    restored = User.retrieve_by_shopify_user_id(42)

    assert_equal "shop-b.myshopify.com", restored.shop      # shop-a's row was clobbered
    assert_equal "write_orders", restored.scope             # shop-a now "has" shop-b's scope
    assert_equal "tok-b", restored.access_token              # shop-a's token replaced by shop-b's
  end
end
```
Expected (buggy) result: retrieving by `shopify_user_id` for what was shop A's user returns shop B's `access_token`/`scope`/`expires`, demonstrating cross-shop overwrite via the unscoped `find_or_initialize_by(shopify_user_id: user.id)`.
