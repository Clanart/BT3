## Analysis

The reported bug pattern (accounting/state committed **before** verifying that the underlying transfer/operation actually succeeded) has a direct analog in the IBC callbacks module's receive-packet callback handler.

### Title
Premature state commit (`writeFn()`) before validating callback token drain in `IBCReceivePacketCallback` permanently locks tokens in an unrecoverable isolated address - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` runs the destination-callback contract logic (an `approve` + arbitrary `CallEVMWithData` to an attacker-specified contract/calldata from the packet memo) inside a cached context, then calls `writeFn()` to persist all resulting EVM state changes to the real context, and **only afterwards** checks whether the isolated receiver address still holds a nonzero token balance — the exact check the code's own comment says exists "to prevent funds from getting stuck in the isolated address, since they would become irretrievable." [1](#0-0) 

### Finding Description
`IBCReceivePacketCallback` performs the callback's ERC20 `approve` and the arbitrary contract call using a `cachedCtx` derived from `ctx.CacheContext()`: [2](#0-1) 

The approve and calldata-invocation results are validated for gas/EVM errors, but `writeFn()` — which flushes all cached-context state (balances, allowances, storage, logs from the arbitrary contract call) into the real `ctx` — is invoked immediately after the contract-call gas check, **before** the invariant check that verifies the isolated receiver's ERC20 balance is fully drained: [3](#0-2) 

The isolated address (`types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)`) is a deterministic pseudo-address with no corresponding private key, used purely to scope the callback's token allowance. If the target contract's calldata (fully attacker-controlled via the packet memo, since `contractAddress` and `cbData.Calldata` come from the transfer memo) does not call `transferFrom` for the entire approved amount — whether due to a bug, partial execution, or a contract intentionally leaving a remainder — the post-check `receiverTokenBalance.Cmp(big.NewInt(0)) != 0` fails and the function returns `ErrEVMCall`. However, by that point `writeFn()` has already committed the state, including the granted allowance and any partial/side-effect transfers executed by the untrusted contract. IBC-callback processing (`ibc-go`'s callbacks middleware) treats the destination-callback error as best-effort/non-reverting with respect to the packet's own acknowledgement — the underlying ICS20 receive (which already minted/escrowed the tokens to the isolated address prior to this callback) is not undone. Consequently, any tokens the callback failed to drain remain stranded at the isolated address, which nobody can access.

This mirrors the reported bug class exactly: an accounting/state commit (`writeFn()`) happens unconditionally before the code verifies that the corresponding value-transfer actually completed successfully, so a failure path still leaves the "success" state applied.

### Impact Explanation
Any token amount left un-drained by the callback contract becomes permanently locked in an address with no known private key — this matches the required Critical impact "permanent freezing, locking, theft, or unauthorized extraction of user funds ... token-pair-backed balances," triggerable by an ordinary unprivileged user simply by sending an ICS20 transfer with a destination-callback memo pointing at a contract that does not (or cannot, due to gas limits/logic bugs) fully consume the approved allowance.

### Likelihood Explanation
Likelihood is high: the destination contract address and calldata are entirely attacker/user-supplied via the transfer memo (`src_callback`/`dest_callback` fields), so any user can trigger this by pointing the callback at a contract that leaves a partial balance (intentionally or via an honest bug in that user's own contract) — no privileged actor or malicious relayer is required.

### Recommendation
Move the `receiverTokenBalance` drain-check to run against `cachedCtx` **before** calling `writeFn()`, and only call `writeFn()` if the check passes; otherwise propagate the error without persisting the cached state changes. This mirrors the fix recommended in the source report: only commit state once success has been fully verified.

### Proof of Concept
1. User initiates an ICS20 transfer to the chain with a memo specifying `dest_callback.address = <ContractX>` and enough `gas_limit`.
2. `ContractX` is a simple contract whose callback entrypoint calls `transferFrom` for less than the full approved/transferred amount (or does nothing at all).
3. `IBCReceivePacketCallback` executes `approve` then invokes `ContractX`; `writeFn()` commits state.
4. The subsequent `receiverTokenBalance` check finds a nonzero balance and returns `ErrEVMCall`, but the state (including any effects from `ContractX`'s partial execution and the underlying already-minted tokens at the isolated address) remains committed.
5. The leftover ERC20 balance sits at `isolatedAddr`, a deterministic address with no private key, permanently unrecoverable by the sender or receiver. [4](#0-3)
