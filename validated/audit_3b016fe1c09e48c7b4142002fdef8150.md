### Title
Malicious remote's `WWW-Authenticate` header can be spoofed to trick Desktop's credential-helper trampoline into treating an arbitrary host as an "enterprise" GitHub endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The `getEndpointKind` function in `trampoline-credential-helper.ts` decides whether an authenticating host should be treated as `'github.com' | 'ghe.com' | 'enterprise' | 'generic'`. When the URL doesn't match a known GitHub/GHE domain and there's no existing account already tied to that origin, it falls back to trusting a `WWW-Authenticate` header value (forwarded by Git as a `wwwauth[...]` credential field) that was returned by the remote server itself: if it contains `realm="GitHub"` the host is classified as `'enterprise'`. [1](#0-0) 

### Finding Description
This is the same broken-invariant pattern as the Beedle report: a value that gates a security-relevant decision (`auctionLength` there, `endpointKind` here) is derived from data supplied by an untrusted counterparty (the pool/lender there, the remote git server/proxy here) with no independent validation or user-defined minimum/allowlist before the trusting party relies on it.

`getCredential` first checks for an existing first-party account match via `getGitHubCredential`/`findGitHubTrampolineAccount`, which only matches when the credential URL's origin exactly equals an already-signed-in account's endpoint origin. [2](#0-1)  If there's no match yet (first-time contact with a new host, or a spoofed subdomain/typo-domain), the code falls into `getEndpointKind`, whose decision order is: known dotcom → known GHE domain → **remote-supplied `WWW-Authenticate` header** → existing account lookup → HTTP probe fallback. [3](#0-2) 

The `WWW-Authenticate` header is not something Desktop's own trusted party sets - it's produced by whatever server answers the HTTPS request for the git remote URL the user is fetching/pushing to (i.e., the "attacker controls...a git remote/proxy response" case explicitly named in the Valid Impact criteria). If that server responds with a `WWW-Authenticate: Basic realm="GitHub"` header, `getEndpointKind` returns `'enterprise'` for the *arbitrary* host, with no verification that the host is actually GitHub-owned (no certificate/domain pinning check, no consultation of the accounts list for that specific host - `existingAccount` lookup only happens afterward and only matters if it finds a match).

Once classified as `'enterprise'`/non-`'generic'`, `getCredential` will, if no account exists for that specific endpoint, prompt the user via `ui.promptForGitHubSignIn(endpoint)` for that host. [4](#0-3)  More importantly, `storeCredential` and `eraseCredential` use the exact same `getEndpointKind` gate to decide storage semantics: for anything not `'generic'`, they explicitly skip storing/erasing the credential in the app's own generic credential store because "GitHub.com/GHE creds are only stored internally." [5](#0-4) [6](#0-5)  This behavior is entirely steered by the header the remote chose to send, not by an independently-verified relationship between the host and a GitHub identity.

Existing guards do not stop this path:
- The `isDotCom`/`isGHE` checks only cover the small set of known first-party domains; anything else (a homoglyph domain, a compromised/attacker-run mirror, a MITM proxy on an internal network, a "git protocol" proxy) falls straight through to the header-trust branch.
- `findGitHubTrampolineAccount` is an *origin-exact-match* lookup against already-signed-in accounts, so it provides no protection the first time a user's Desktop instance talks to a spoofed host - the header wins by being checked first.
- The final `isGitHubHost(endpoint)` network probe is only reached if the header didn't already short-circuit the branch, so a malicious server can just always send the `realm="GitHub"` header to avoid ever being probed truthfully.

### Impact Explanation
Because the classification also gates whether Desktop will surface a GitHub sign-in prompt for that arbitrary host, a user cloning/fetching from (or being MITM'd/redirected to) an attacker-controlled remote can be prompted to sign in to "GitHub" for a host that isn't actually GitHub. Depending on how `promptForGitHubSignIn` resolves accounts, this can lead to Desktop treating a non-GitHub endpoint as enterprise-classified, altering credential storage/retrieval decisions and expanding the attack surface for credential/account-binding confusion for that origin - exactly the "unauthorized OAuth or account binding" / "credential exfiltration" categories called out as valid impact. The severity is bounded by the fact that Desktop still keys first-party account matching by origin elsewhere, but the misclassification itself is a genuine broken invariant reachable purely from a remote server response.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to perform a git network operation (fetch/push/clone) against a host controlled or spoofed by the attacker (e.g., a malicious git server, a compromised proxy, or a network position that can intercept a plain-HTTP redirect before the request reaches the real GitHub host), and it only affects the classification for hosts the user hasn't already bound to an existing account. It does not require local/physical access, admin rights, or pre-existing malware, matching the required attacker model (control of a git remote/proxy response).

### Recommendation
Do not let the `WWW-Authenticate` realm string alone determine trust classification for hosts that aren't already known first-party domains. At minimum, require the `isGitHubHost(endpoint)` probe (or equivalent certificate/known-endpoint verification) to corroborate the header claim before classifying an arbitrary host as `'enterprise'`, and never skip storing/erasing credentials for a host based solely on unverified header content.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a MITM/proxy) at `https://evil.example.com/repo.git`, which is neither `github.com` nor a domain the victim has ever signed into.
2. Victim adds this remote in Desktop and performs a `fetch`/`push`; Git issues the HTTP request and the attacker's server responds `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
3. Git forwards this as a `wwwauth[0]=...realm="GitHub"...` field to Desktop's credential helper trampoline (`createCredentialHelperTrampolineHandler` → `getCredential`).
4. `getEndpointKind` reaches the loop at [7](#0-6)  and returns `'enterprise'` for `evil.example.com` purely because of the spoofed header, bypassing the trailing `isGitHubHost` network verification that would otherwise have correctly classified it as `'generic'`.
5. Desktop then applies enterprise-specific behavior (sign-in prompting, refusal to persist credentials via the generic/external credential store) to this attacker-controlled host based solely on unverified, remote-supplied data.

```typescript
const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```

```typescript
/** Implementation of the 'store' git credential helper command */
async function storeCredential(cred: Credential, store: Store, token: string) {
  if ((await getEndpointKind(cred, store)) !== 'generic') {
    return
  }

  return useExternalCredentialHelper()
    ? storeExternalCredential(cred, token)
    : setGenericCredential(
        urlWithoutCredentials(getCredentialUrl(cred)),
        forceUnwrap(`credential missing username`, cred.get('username')),
        forceUnwrap(`credential missing password`, cred.get('password'))
      )
}

const storeExternalCredential = (cred: Credential, token: string) => {
  const path = getTrampolineEnvironmentPath(token)
  return approveCredential(cred, path, getGcmEnv(token))
}

/** Implementation of the 'erase' git credential helper command */
async function eraseCredential(cred: Credential, store: Store, token: string) {
  if ((await getEndpointKind(cred, store)) !== 'generic') {
    return
  }

  return useExternalCredentialHelper()
    ? eraseExternalCredential(cred, token)
    : deleteGenericCredential(
        urlWithoutCredentials(getCredentialUrl(cred)),
        forceUnwrap(`credential missing username`, cred.get('username'))
      )
}
```
