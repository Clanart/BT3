Based on my research, I found a concrete asymmetry in the object-ownership code that is used by the new lazy-module-initialization / publish-owner-tracking mechanism, but I want to be upfront that I could not fully view the body of `object::transfer_raw` (the file excerpt returned blank lines for it), so one link in the exploit chain is not 100% confirmed from the index. I present the finding with that caveat noted explicitly.

### Title
Unbounded loop in `object::root_owner()` used to gate publish-time ownership recording and lazy self-init authorization - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`aptos_framework::code::publish_package` and `aptos_framework::init::assert_may_self_initialize` both rely on `object::root_owner()` to determine — and later re-verify — the "true" owning address of an object hosting published modules, in order to gate whether a module may mint a signer for itself via `init::internal_maybe_initialize`. Unlike every other ownership-chain traversal in `object.move` (`owns()`, `verify_ungated_and_descendant()`), `root_owner()` has no bound on the number of hops it will follow.

### Finding Description
`object::root_owner()` walks the ownership chain with an **unbounded** `while` loop: [1](#0-0) 

Compare this to the two other chain-walking functions in the same file, both of which explicitly bound iteration to `MAXIMUM_OBJECT_NESTING` (8) and assert if exceeded: [2](#0-1) [3](#0-2) 

The module-level doc comment for `MAXIMUM_OBJECT_NESTING` explicitly acknowledges that objects "can technically have infinite nesting" and that bounded checks are an approximation: [4](#0-3) 

`root_owner()` is invoked directly on the **publish path**, in `code::publish_package`, to compute the owner recorded for every module in the package being (re)published to an object address: [5](#0-4) 

It is invoked again, at call time, in `init::assert_may_self_initialize`, which gates whether `init::internal_maybe_initialize` may mint a signer for the object's address: [6](#0-5) 

Because `root_owner()` has no depth bound, if an ownership cycle exists among objects (e.g., object A owned by object B and object B owned by object A), calling `root_owner()` on any object in that cycle never terminates through normal means — it will loop until the transaction runs out of gas. This directly contrasts with the codebase's own established pattern (`owns`, `verify_ungated_and_descendant`) of defending against exactly this scenario with a bounded counter and `EMAXIMUM_NESTING` abort.

**Caveat / what I could not fully confirm:** whether an ownership cycle is actually reachable through the public entry points `object::transfer`/`object::transfer_call` (which go through `transfer_raw`), i.e., whether `transfer_raw` itself calls `verify_ungated_and_descendant` (as `transfer_to_object` does) or omits it. The source excerpt I retrieved for `transfer_raw`'s body did not render, so I cannot state with certainty that address-based transfers omit the cycle check that `transfer_to_object` performs. If `transfer_raw` does perform the same check as `transfer_to_object`, then cycles cannot be formed and this issue reduces to defense-in-depth/hardening rather than an exploitable bug.

### Impact Explanation
If a cycle can be constructed (via `transfer_raw`/`transfer_call`, which operate on raw addresses without the `Object<T>` typed cyclic-descendant check that `transfer_to_object` enforces), then:
- Any call to `code::publish_package` for a module hosted at an address inside/behind the cycle would hang and burn gas rather than resolving deterministically to an owner, since `is_lazy_module_initialization_enabled() && object::is_object(addr)` triggers `root_owner()` unconditionally.
- Any call to `init::internal_maybe_initialize` for such a module would similarly hang in `assert_may_self_initialize`, permanently denying that module the ability to self-initialize (a Denial-of-Service on the module's initialization capability, and gas griefing on any transaction that reaches this code).

This falls under the gate's "native validation ... failure that reaches protected state mutation" and "Object code deployment ... flows must not leak upgrade or freeze authority" categories in spirit (it corrupts the publish-time owner-recording step that the whole `EOWNER_CHANGED_SINCE_DEPLOY` authorization mechanism depends on), but the concrete, provable impact is availability (DoS/gas-griefing) on publish/init, not fund loss or code-ownership takeover — so it should be scoped as Medium unless the cycle-formation step can be confirmed reachable from unprivileged callers.

### Likelihood Explanation
Low-to-Medium, contingent entirely on the unconfirmed question of whether `object::transfer_raw` permits creating an ownership cycle. All other cycle-defensive code in this same file assumes cycles ARE possible ("objects may have cyclic dependencies," "technically have infinite nesting"), which suggests the authors did not consider cycles fully prevented at the transfer layer, making it plausible that `root_owner()` was simply missed when the depth-bound pattern was applied elsewhere.

### Recommendation
- Add the same `MAXIMUM_OBJECT_NESTING`-bounded loop and `EMAXIMUM_NESTING`-style abort to `root_owner()` that already exists in `owns()` and `verify_ungated_and_descendant()`.
- Independently verify whether `object::transfer_raw` enforces an anti-cycle/descendant check identical to `transfer_to_object`; if not, either add one or explicitly document that raw-address transfers can create cycles and that all consumers of ownership-chain traversal must be bounded.
- Add an explicit regression test that constructs (or attempts to construct) an object ownership cycle and calls `code::publish_package` / `init::internal_maybe_initialize` against it, verifying a clean abort rather than a gas-exhausting infinite loop.

### Proof of Concept
Could not be fully constructed/confirmed within this investigation because the exact behavior of `object::transfer_raw` with respect to cycle prevention could not be verified from the available index. The conceptual PoC, pending that confirmation, is:
1. Create object `A` and object `B`, both owned by attacker account `@cafe`.
2. Call `object::transfer_call(@cafe, A, B_address)` — if unchecked, `A` is now owned by `B`.
3. Call `object::transfer_call(@cafe, B, A_address)` — if unchecked, `B` is now owned by `A`, forming a cycle `A → B → A`.
4. Publish a module to address `A` (or `B`) with `LAZY_MODULE_INITIALIZATION` enabled, or call `init::internal_maybe_initialize` from a module hosted there. Both paths call `root_owner()`, which never terminates, exhausting the gas budget.

Given the unresolved caveat above, I recommend this be treated as a lead for a Devin agent with terminal/repo access to confirm `transfer_raw`'s implementation and run the PoC, rather than a fully confirmed finding.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
