### Title
Diff-hunk expansion desynchronizes absolute line indices from the persisted `DiffSelection`, silently corrupting partial-commit contents - ([File: app/src/ui/diff/text-diff-expansion.ts])

### Summary
The report's core theme — a system that derives a value from a positional/quantity mapping (asset amount ↔ shares) without correctly tracking how that mapping shifts over time, leading to silent value corruption — has a structural analog in GitHub Desktop's partial-staging feature. Desktop's `DiffSelection` model tracks which lines a user has chosen to stage/unstage using *absolute line indices* into a diff's hunks [1](#0-0) . When a hunk is expanded in the UI, `expandTextDiffHunk` inserts new context lines and rewrites hunk boundaries, but the persisted selection state is never remapped to the new index space [2](#0-1) .

### Finding Description
`DiffSelection` stores "diverging" line selections keyed purely by an integer `absoluteIndex = hunk.unifiedDiffStart + lineIndex`, with no reference to the actual line content or a stable line identity [3](#0-2) . This is the direct analog of the "shares" abstraction in the report: an index is used as a proxy for "how much of this file the user wants staged," similar to how shares are used as a proxy for token amount, and both proxies are only valid as long as the mapping between proxy and real quantity stays fixed.

`expandTextDiffHunk` breaks that fixed mapping. When a hunk is expanded upward, `numberOfLinesToAdd` new `DiffLine`s are prepended to the hunk's `lines` array while `hunk.unifiedDiffStart` is left unchanged [4](#0-3) . Consequently, every line that existed in the hunk before expansion now sits at a *new* array offset (shifted by `numberOfLinesToAdd`), so its absolute index (`unifiedDiffStart + index`) changes even though `unifiedDiffStart` itself did not move. Downstream hunks are explicitly shifted by `numberOfNewDiffLines` [5](#0-4) , confirming the index space itself is mutated by expansion — but the `DiffSelection.divergingLines` set on the `WorkingDirectoryFileChange`, which was built against the pre-expansion index space, is not translated.

The expansion is performed purely as local component state in `side-by-side-diff.tsx`'s `expandHunk`, which only calls `this.setState({ diff: updatedDiff })` and never calls `onIncludeChanged` to update/remap the file's selection [6](#0-5) . Any subsequent line-selection action (`onLineNumberCheckedChanged`, `onClickHunk`, `onEndSelection`) computes `absoluteIndex` against the *expanded* hunk layout and writes it into the same `DiffSelection` object that `formatPatch`/`applyPatchToIndex` later reads [3](#0-2) [7](#0-6) . Because the two hunk layouts (the one under selection edits and the one the store reconciles against via `withSelectableLines` when reloading the diff) can diverge, `isSelected(absoluteIndex)` can silently resolve to the wrong `DiffLine`.

The existing guard, `withSelectableLines`, only prunes indices that fall outside the new selectable set — it does nothing to detect that an index number now refers to a *different* line than the one the user actually selected [8](#0-7) . That guard runs on diff reload (`updateChangesWorkingDirectoryDiff`), not on hunk-expansion, and even if it did run it could not distinguish "line 42 no longer exists" from "line 42 now means something else."

### Impact Explanation
`formatPatch` and `formatPatchToDiscardChanges` both drive `git apply --cached` / discard operations purely from `file.selection.isSelected(absoluteIndex)` [9](#0-8) [10](#0-9) . If the index-to-line correspondence shifts due to hunk expansion while a user is doing granular partial-staging (a core, actively-used Desktop feature), the user can end up staging/committing a change they explicitly deselected, or omitting one they intended to include — a silent corruption of what gets committed or discarded, matching the report's Impact category ("silent corruption of what the user commits").

### Likelihood Explanation
Hunk expansion ("Expand Up"/"Expand Down"/"Expand All") is a normal, discoverable UI action available whenever a diff has collapsed context, and partial line/hunk selection is a heavily used first-class feature. Any user who expands a hunk to see more context and continues to select/deselect individual lines is exercising exactly this code path. No malicious repository content, elevated privileges, or unusual steps are required — a repository author could also engineer commit history/diff shapes (e.g., many small hunks close together, since `mergeDiffHunks` further compounds index shifts during merges) to make this misalignment more likely to occur.

### Recommendation
`DiffSelection`'s selection state should not be tied to an ephemeral, expansion-mutable absolute index. Either:
- Remap `divergingLines` (and `selectableLines`) whenever a hunk is expanded/merged, translating old absolute indices to their new positions using the same offset/merge logic already computed in `expandTextDiffHunk`/`mergeDiffHunks`, and route this through `onIncludeChanged` so the persisted selection tracks the visible diff; or
- Key selection state by a stable line identity (e.g., `(oldLineNumber, newLineNumber)` pair or original-diff line number) instead of a positional index that changes when unrelated lines are inserted elsewhere in the diff.

### Proof of Concept
1. Open a modified file with a diff containing at least two hunks separated by a collapsed context region.
2. In the Changes view, deselect a single line inside the second hunk (unchecking it so it will NOT be committed) — this stores its current `absoluteIndex` in `divergingLines`.
3. Click "Expand Up" on the second hunk to pull in hidden context lines above it. This calls `expandTextDiffHunk`, which prepends new `DiffLine`s to the hunk while keeping `unifiedDiffStart` fixed, shifting the relative index of every previously existing line in that hunk [11](#0-10) .
4. Without touching the checkbox again, commit only this file.
5. Inspect the resulting commit: verify whether the line at the originally-recorded `absoluteIndex` (now a different, previously-context line) is the one actually excluded, while the line the user intended to exclude is included — confirming `formatPatch`'s `isSelected(absoluteIndex)` check operated on a desynchronized index.

(Note: full runtime confirmation of the exact off-by-`numberOfLinesToAdd` behavior requires exercising the UI/store integration end-to-end, which was not runnable in this read-only investigation; the code-level evidence above establishes the missing remap step as the root cause.)

export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}

  private expandHunk(hunk: DiffHunk, kind: DiffExpansionKind) {
