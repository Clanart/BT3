### Title
Panic on unregistered `sender`/`recipient` in PedPoP blame evaluation crashes the process - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame`, `AdditionalBlameMachine::blame`, and the shared `blame_internal` helper accept attacker-influenced `sender`/`recipient` `Participant` indexes and an untrusted `EncryptedMessage`, then index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` (in `Decryption::decrypt_with_proof`) without checking membership. A `blame()` call naming a participant index that never registered an encryption key or commitments causes a `HashMap` index panic — a denial of service analogous to CVE-2018-20802's "specially crafted input triggers server abort" bug class, reachable via protocol messages (blame accusations carrying attacker-controlled participant indexes and message bytes through `EncryptedMessage::read`).

### Finding Description
The DKG blame path never validates that the accused `sender` or accusing `recipient` are members of the registered participant set before indexing maps:

- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` [1](#0-0) , which does `self.enc_keys[&decryptor]` — panicking if `decryptor` (the `recipient` argument) never registered an `EncryptionKeyMessage` [2](#0-1) .
- `blame_internal` then does `self.commitments[&sender]` — panicking if `sender` is not a key in `self.commitments` [3](#0-2) .
- Both `BlameMachine::blame` and `AdditionalBlameMachine::blame` pass `sender`/`recipient` straight through with no `Participant` bounds or membership check [4](#0-3) [5](#0-4) .

`AdditionalBlameMachine::new` explicitly supports non-member evaluators taking all commitment messages, so `commitments`/`enc_keys` only contain `1 ..= n` indexes — yet `blame()` accepts any `Participant` (any non-zero `u16`, up to 65535) for `sender`/`recipient`. A `Participant::new(n + k)` value that is well-formed but absent from both maps hits the `HashMap` indexing panic. The only documented precondition is that `msg` "must have been authenticated as actually having come from the sender" — nothing constrains `sender`/`recipient` to be registered indexes, and the `msg` bytes themselves are attacker-controlled via `EncryptedMessage::read` [6](#0-5) .

Note the contrast with `Decryption::register`, which asserts on re-registration (documented caller responsibility), and `generate_secret_shares`/`calculate_share`, whose `self.commitments[&l]` indexing is safe because `validate_map` enforces the map keys match `all_participant_indexes` [7](#0-6) . The blame path has no equivalent validation.

### Impact Explanation
A party able to submit a blame accusation — or a `sender`/`recipient` pair — into the blame-evaluation flow can specify a non-member participant index and panic the evaluating machine. In a system using these crates to adjudicate DKG faults (e.g., a coordinator or node evaluating blame statements submitted as protocol evidence), a single crafted blame statement referencing e.g. `recipient = n + 1` aborts the process via panic instead of returning an error. This is an availability-only impact matching the CVE's profile (A:H, no confidentiality/integrity impact): an unauthenticated-to-the-blame-protocol input crashes the evaluator, halting fault adjudication and whatever else shares the process.

### Likelihood Explanation
Blame statements are inherently adversarial inputs: they exist precisely because some party is accused of fault, so hostile or malformed blame data is the expected operating condition. The API signature takes raw `Participant` values from the caller with no documented requirement that they be members (only that the message be authenticated), and `AdditionalBlameMachine` is explicitly designed for third-party evaluation where the evaluator cannot necessarily bound which indexes an accuser names. Any path that forwards protocol-supplied participant indexes and `EncryptedMessage` bytes to `blame()` is exploitable. Exploitation is trivial — a single blame call with an out-of-range index.

### Recommendation
Validate membership before indexing: in `blame_internal`, return the accuser (or a dedicated error) if `!self.commitments.contains_key(&sender)`; in `Decryption::decrypt_with_proof`, use `enc_keys.get(&decryptor)` and map `None` to `DecryptionError` or blame the accuser. More robustly, bound `sender`/`recipient` against the known `n` at the `blame()` entry points, consistent with the `validate_map` pattern already used for `commitment_msgs`/`shares`.

### Proof of Concept
```rust
// crypto/dkg/pedpop context; C = e.g. Ristretto ciphersuite.
// Setup: n = 3, all three participants publish valid commitment messages.
let mut machine =
  AdditionalBlameMachine::<C>::new(context, 3, commitment_msgs).unwrap();

// An accusation names a recipient who was never part of the DKG (4 > n = 3).
let attacker = Participant::new(1).unwrap();          // a real participant
let fake_recipient = Participant::new(4).unwrap();    // never registered an enc key

// msg is an EncryptedMessage read from attacker-controlled bytes;
// pop signature need not even be valid for the panic when a proof is supplied.
let msg: EncryptedMessage<C, SecretShare<C::F>> =
  EncryptedMessage::read(&mut forged_bytes.as_slice(), params).unwrap();
let proof: EncryptionKeyProof<C> =
  EncryptionKeyProof::read(&mut forged_proof.as_slice()).unwrap();

// Panics inside decrypt_with_proof at `self.enc_keys[&decryptor]`
// ("key not found") — denial of service instead of a blame verdict.
let _ = machine.blame(attacker, fake_recipient, msg, Some(proof));
```

The same panic is reachable via `sender`: `machine.blame(Participant::new(4).unwrap(), Participant::new(1).unwrap(), msg, None)` returns `sender` early only if the signature is invalid; with a `sender`-index panic occurring at `self.commitments[&sender]` once signature/proof checks pass or via the `enc_keys[&decryptor]` path first. Exact behavior depends on which check is hit first, but no input validation prevents reaching the indexing operations.

fn validate_map<T, C: Ciphersuite>(
  map: &HashMap<Participant, T>,
  included: &[Participant],
  ours: Participant,
) -> Result<(), PedPoPError<C>> {
  if (map.len() + 1) != included.len() {
    Err(PedPoPError::IncorrectAmountOfParticipants {
      expected: included.len(),
      found: map.len() + 1,
    })?;
  }

  for included in included {
    if *included == ours {
      if map.contains_key(included) {
        Err(PedPoPError::DkgError(DkgError::DuplicatedParticipant(*included)))?;
      }
      continue;
    }

    if !map.contains_key(included) {
      Err(PedPoPError::MissingParticipant(*included))?;
    }
  }

  Ok(())
}
