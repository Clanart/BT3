### Title
Invalid PedPoP messages reveal reusable ECDH decryption keys before PoP verification - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` for a malformed encrypted share before verifying the queued proof-of-possession batch statement. An attacker can replay the ephemeral key from an observed `EncryptedMessage`, submit an invalid ciphertext/PoP, and receive the ECDH point needed to decrypt that observed message.

### Finding Description
`Encryption::decrypt` queues the message PoP for later batch verification, computes `ecdh = victim_enc_key * msg.key`, decrypts the ciphertext with it, and immediately returns an `EncryptionKeyProof` containing that ECDH point and a DLEq proof. [1](#0-0) 

`calculate_share` then attempts to decode the decrypted bytes as a scalar and returns `PedPoPError::InvalidShare { blame: Some(blame) }` before calling `batch.verify_with_vartime_blame()`. [2](#0-1) 

Consequently, a syntactically valid `EncryptedMessage` whose plaintext decodes to a non-canonical scalar causes the blame proof to be returned even if its Schnorr PoP is invalid. The PoP exists specifically to prevent reuse of another message’s encryption key from causing a blame proof to disclose that message’s ECDH key. [3](#0-2) 

Because `EncryptedMessage::read` accepts the attacker-controlled `key`, `pop`, and ciphertext fields directly from untrusted bytes, the attacker can set `key` to the ephemeral public key from an observed encrypted share while supplying garbage ciphertext and PoP bytes. [4](#0-3) 

### Impact Explanation
A DKG participant who can observe an encrypted share addressed to the victim can recover the victim’s ECDH point for that share’s ephemeral key and decrypt the share. This leaks a PedPoP secret share to an unauthorized party, undermining threshold-key confidentiality even though the malformed submission itself is rejected.

The returned proof also contains a DLEq proof binding the disclosed ECDH point to the victim’s registered encryption key and the replayed ephemeral key, so third parties can authenticate that the disclosed point is the correct decryption key. [5](#0-4) 

### Likelihood Explanation
The attack only requires an attacker who can send a PedPoP share to the victim and observe an encrypted share containing the target ephemeral key. The malicious share can use random ciphertext, since random field encodings frequently fail canonical scalar decoding; the attacker can retry with another malformed message if the first decryption happens to decode successfully.

No valid PoP is required because the queued PoP verification is bypassed by the early non-canonical-scalar return. [6](#0-5) 

### Recommendation
Verify the queued PoP before decrypting or before returning any `EncryptionKeyProof`. Structurally, split `Encryption::decrypt` into:

1. Queue and verify the PoP.
2. Only if the PoP is valid, derive the ECDH key and decrypt.
3. Only if share verification fails, reveal the corresponding `EncryptionKeyProof`.

At minimum, `calculate_share` must not return `blame` on scalar-decoding failure until the batch containing the PoP has been successfully verified. The blame proof should remain `None` for an invalid PoP.
