### Title
Irreversible destination-side order cancellation with no-timeout cross-chain refund message can permanently lock escrowed funds - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromDest` permanently marks a cross-chain order as settled (`_filled[commitment] = order.user`) on the destination chain *before* the corresponding `RefundEscrow` message is confirmed delivered and processed on the source chain, and that message is dispatched with `timeout: 0` (never times out). If that single message never lands successfully — because it is never relayed, or because `onAccept` deterministically reverts on delivery — the user has no way to retry the cancellation (the top-level `cancelOrder` guard `if (_filled[commitment] != address(0)) revert Filled();` now blocks any further action), and the escrowed input tokens on the source chain remain locked forever. This is the same broken invariant as the reported Atlas BTC bug: an irreversible external-facing state commitment is made before the associated fund movement is guaranteed, with no timeout/retry/refund fallback for the case where that fund movement can never complete.

### Finding Description
In `_cancelFromDest`, once the deadline has passed anyone can trigger cancellation, and the function immediately sets: [1](#0-0) 

`_filled[commitment]` is now permanently non-zero, which is checked at the very top of the public `cancelOrder` entrypoint documented in the SDK docs: [2](#0-1) 

Any future call to `cancelOrder` for this commitment — from any route (source, dest, same-chain) — reverts with `Filled()`. The only remaining path to recover the escrowed input tokens on the source chain is for the dispatched `RefundEscrow` `DispatchPost` message (with `timeout: 0`, i.e. it never expires under ISMP semantics) to eventually be delivered and successfully processed by `onAccept` on the source chain: [3](#0-2) 

`onAccept` calls `_authenticate`, which requires the sender module to still match the currently registered gateway instance for the source chain: [4](#0-3) 

On the host side, `dispatchIncoming` treats a failed `onAccept` call as "retry later" by deleting the request receipt and returning, with no cap on retries and no alternative code path: [5](#0-4) 

If the message is simply never relayed (e.g., `relayerFee` too low, no relayer willing to deliver, or the caller never self-relays), there is no timeout to fall back on because the request was dispatched with `timeout: 0`. If it is relayed but `_authenticate` (or `_withdraw`'s escrow-balance bookkeeping) fails deterministically — for example because the registered gateway instance for the source state machine was updated via `RequestKind.UpdateParams`/`NewDeployment` between the time the cancel was dispatched and the time it is delivered — `onAccept` reverts identically on every retry, forever. Either way, the destination has already permanently recorded the order as cancelled/filled, and the source-chain escrow can never be withdrawn: the funds are provably and permanently stuck with no admin, user, or protocol-level recovery mechanism, exactly analogous to the Atlas report's "no recovery mechanism" gap.

### Impact Explanation
This directly causes permanent loss/lock of user escrowed funds (input tokens) on the source chain — a direct "stealing or loss of funds" / fund-lock impact under the bounty's accepted impact categories. The path requires no malicious relayer, prover, or admin collusion: it is triggered by ordinary conditions (a message that is never picked up for relay, or a benign parameter update racing with an in-flight cancellation) combined with the protocol's own design choice of `timeout: 0` and the irreversible `_filled` write happening before delivery is confirmed.

### Likelihood Explanation
Likelihood is moderate: it requires the cross-chain `RefundEscrow` message to fail to be delivered/processed, which can happen from ordinary liveness gaps (no relayer economically incentivized, since `relayerFee` is user/caller supplied and can be set to zero or too low) or from a benign gateway parameter update landing between dispatch and delivery. No attacker action beyond calling the already-public, permissionless (post-deadline) `cancelOrder` from the destination side is required to create the irreversible state.

### Recommendation
- Do not set `_filled[commitment]` permanently before the refund is confirmed; use an intermediate "cancellation pending" state that can still route to a fallback claim/refund path if the refund message is not delivered within a bounded window.
- Set a non-zero `timeout` on the `RefundEscrow` `DispatchPost` so that a genuine ISMP timeout can be triggered and drive an explicit recovery/refund flow via `onPostRequestTimeout`, rather than relying indefinitely on eventual relay delivery.
- Add a governance/user-triggerable emergency withdrawal for orders whose `_filled` state has been set to "cancelled" but whose corresponding source-chain escrow has not been released after a configurable grace period.

### Proof of Concept
1. User places a cross-chain order, escrowing input tokens on chain A, with destination on chain B.
2. Deadline passes; a third party (or the user) calls `cancelOrder(order, options)` targeting the destination route on chain B. `_cancelFromDest` executes: `_filled[commitment] = order.user;` is set, and a `RefundEscrow` `DispatchPost` (with `timeout: 0`, `payer: msg.sender`, `fee: options.relayerFee`) is dispatched toward chain A.
3. No relayer delivers this message (e.g., `options.relayerFee` set to 0 and no one self-relays), or the message is delivered but chain A's `IntentGatewayV2` instance mapping (`_instance(order.source)`) was updated via `RequestKind.UpdateParams`/`NewDeployment` in the interim, causing `_authenticate` to revert on every delivery attempt.
4. On chain A, the escrowed input tokens remain locked under `_orders[commitment][token]` indefinitely; `dispatchIncoming` keeps deleting/retrying the receipt on every failed delivery with no cap.
5. Any subsequent call to `cancelOrder(order, options)` for this commitment on any chain reverts with `Filled()` because `_filled[commitment] != address(0)`, closing off any alternative recovery path. Funds are permanently unrecoverable.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
