### Title
Unmarked hard truncation of diff text in `build_refute_prompt` lets attacker-padded diffs push real findings past the cutoff, causing the self-refute stage to falsely reject valid vulnerabilities as "not in diff" - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` truncates the diff passed to the stage-2 "adversarially disprove" LLM call with a raw `diff_text[:8000]` slice, unlike `cap_diff_for_prompt` used in stage 1 which caps per-file/total bytes and inserts explicit truncation markers. An attacker who controls the diff content (e.g. a large PR with padding files before the actually dangerous hunk) can push the genuinely vulnerable `+` lines past byte 8000 with no marker indicating truncation occurred, causing the refute-stage model to invoke its own "PRE-EXISTING" rule and wrongly refute (drop) a true finding that stage 1 correctly flagged.

### Finding Description
`build_refute_prompt` (`plugins/security-guidance/hooks/review_api.py:210-283`) builds the stage-2 self-refute prompt by embedding the raw diff via `diff_text[:8000]` (line 214) with no per-file structure, no truncation marker, and no attempt to keep the cited `vulnerableCode`/file in view. Contrast with `cap_diff_for_prompt` (lines 31-64), which is used for the stage-1 investigate prompt and explicitly appends `"...[truncated by security-guidance: ...]"` markers so the model knows content is incomplete, and caps per-file at `DIFF_PER_FILE_BYTES` while distributing remaining budget across files up to `DIFF_TOTAL_BYTES`.

The refute-stage system instructions (`build_refute_prompt`, lines 232-236) direct the model to REFUTE a candidate as `PRE-EXISTING` when "the cited vulnerableCode does NOT appear on any + line in the DIFF block above." Because the DIFF block the model sees is silently cut at 8000 raw characters with no anchor guaranteeing the flagged file/line survives, an attacker who authors (or influences, e.g. via a large auto-generated file, vendored dependency diff, or padding commits) a diff where benign/large content precedes the true vulnerable hunk can force the actual `+` lines containing the dangerous code out of the visible window. The refute-stage model then has no evidence the vulnerability is present in the diff and, following its own instructions, marks it `PRE-EXISTING`/refuted — even though stage 1 (`build_investigate_prompt`, which does use the byte-capped-with-markers `cap_diff_for_prompt`) correctly identified it as a genuine `+`-line change.

This breaks the stated invariant that truncation must not consistently drop the high-risk lines the user expects reviewed: the two stages use inconsistent truncation strategies (structured/marked vs. raw/unmarked), and the raw slice has no ordering guarantee tied to which file/hunk is "first" — an attacker fully controls diff ordering and size in their own PR/branch.

### Impact Explanation
A successfully refuted finding is dropped before `filter_by_severity`/`format_findings` ever surface it to the user (per `security_reminder_hook.py`'s two-stage flow: investigate → refute → render). This lets an attacker who can shape the diff (any normal contributor pushing a PR/commit set that the agentic reviewer processes) suppress detection of their own dangerous `+` lines — directly undermining the security-guidance plugin's purpose and causing sensitive/dangerous code to pass review silently, matching "review/export logic" trust-boundary bypass and effectively a disclosure/skip-review outcome for the injected vulnerable code.

### Likelihood Explanation
This requires no special privilege beyond normal ability to author a diff/PR that the agentic reviewer processes — an ordinary contributor or attacker-controlled branch is sufficient. It is deterministic given the fixed 8000-character cutoff and depends only on diff ordering/size, both fully attacker-controlled. The stage-1 prompt already demonstrates the project is aware truncation needs explicit markers (`cap_diff_for_prompt`), making the omission in `build_refute_prompt` a straightforward, reproducible oversight rather than a theoretical corner case.

### Recommendation
Replace the raw `diff_text[:8000]` slice in `build_refute_prompt` with the same structured capping used in stage 1 (`cap_diff_for_prompt`), or better, anchor the refute-stage diff view specifically around the files/lines referenced by each candidate's `filePath`/`vulnerableCode` (ensuring those hunks are always included even if other file content must be dropped), and always append an explicit `[... truncated ...]` marker so the model cannot treat a truncated absence as evidence of non-existence. Additionally, the `PRE-EXISTING` refutation rule should require the model to confirm truncation markers are absent near the candidate's file before applying that rule.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py`:
1. Construct a synthetic diff where file `benign/padding.py` contains >8000 characters of innocuous `+` lines, followed by a second file `app/auth.py` containing a `+` line with a clearly dangerous pattern (e.g. `+    subprocess.run(cmd, shell=True)`).
2. Call `build_refute_prompt(candidates=[{"filePath": "app/auth.py", "vulnerableCode": "subprocess.run(cmd, shell=True)", ...}], diff_text=full_diff_string)`.
3. Assert that the dangerous line/file from `app/auth.py` is present within the first 8000 characters of the returned prompt string (i.e., `"subprocess.run(cmd, shell=True)" in prompt` and no truncation marker precedes it without including the target hunk).
4. Expected current behavior (failing/vulnerable): assertion fails — the dangerous line is absent from the prompt sent to the refute model, and no truncation marker is present to warn the model, demonstrating the model would be told (implicitly) the pattern doesn't appear in the diff.
5. Expected fixed behavior: the dangerous hunk is always present (via anchored/structured capping) or an explicit truncation marker is emitted alongside any omission, and the `PRE-EXISTING` refutation cannot fire based on absence caused by truncation.
