### Title
POST request timeouts can be processed after a response was already delivered, enabling double-settlement of the same request - ([File: modules/ismp/core/src/handlers/timeout.rs])

### Summary
The ISMP timeout handler enforces a "response already received" guard for GET requests, but the equivalent guard is missing for POST requests. This asymmetry lets a POST request that has already completed the normal request→response settlement path also be pushed through the timeout path, triggering the application's `on_timeout` callback (and any associated refund/unlock logic) a second time for the same commitment — a direct analog of the TBTC report's core defect: a state machine that allows a stale/competing transition to be pushed through after the "correct" transition already occurred, because the guard exists for one code path but not its sibling.

### Finding Description
In `modules/ismp/core/src/handlers/timeout.rs`, the `TimeoutMessage::Get` branch explicitly guards against timing out a request that already received a response: [1](#0-0) 

This check is deliberate — it is exercised by dedicated tests: [2](#0-1) [3](#0-2) 

However, the `TimeoutMessage::Post` branch performs no such check. It only verifies that the commitment exists, that the timeout timestamp has elapsed, and a non-membership proof against the destination request-receipt trie: [4](#0-3) 

Nowhere in this branch does it check `host.response_receipt(...)` or equivalent bookkeeping to reject a timeout for a POST request whose response has already been delivered and processed by the module. The same asymmetry exists in the EVM handler: `HandlerV2.sol::handlePostRequestTimeouts` checks only a non-membership proof of the *request receipt* on the destination chain, never whether a response was already delivered and consumed on the source chain: [5](#0-4) 

Because the destination-side non-membership proof only proves the request was never *delivered* to the destination app — it says nothing about whether the *response* was already accepted back on the source chain — a request can legitimately complete its full request→response lifecycle (module unlocks funds / marks the request fulfilled) and still remain eligible, from the timeout handler's point of view, to be timed out later, since nothing deletes/guards the `request_commitment` against this specific race the way GET requests are protected.

This mirrors exactly the TBTC finding's pattern: a state machine offers two competing valid transitions (`on_response` completion vs. `on_timeout` reversal) for the same underlying object, and only one of the two sibling code paths (GET) enforces mutual exclusivity — the other (POST) does not.

### Impact Explanation
If a downstream `IsmpModule`'s `on_timeout` implementation performs any state-reverting action (refunding escrowed assets, releasing bonded collateral, restoring balances, unlocking a paymaster grant, etc.) that mirrors what `on_response`/successful delivery already did, then successfully delivering a POST request's response and *then* also timing it out results in that reverting action being executed twice for a single logical transfer — i.e., a double-settlement / double-refund of funds that belong to only one beneficiary. This falls squarely under the bounty's "double-claim/double-settlement" and "funds move exactly once" impact categories, since it is a purely code-level guard gap rather than a malicious-relayer or governance assumption.

### Likelihood Explanation
The path is reachable by any permissionless caller of `handle_timeouts`/`handlePostRequestTimeouts` once the request's `timeout_timestamp` has elapsed — no privileged role, prover collusion, or governance action is required. The only prerequisite is that a response is delivered *close to* or *after* the nominal timeout window on the destination (e.g., due to network delay, congestion, or a relayer submitting the response near the timeout boundary), which is an ordinary, expected operational condition rather than an attacker-controlled precondition — exactly the "participants not always pushing forward through the state machine in lockstep" scenario the original report describes. Exploitability further depends on whether a given application's `on_timeout` handler is not itself idempotent/defensive against replay — the framework's own documentation explicitly warns that `on_timeout` must be written defensively, but does not itself close this gap at the protocol layer for POST requests the way it does for GET.

### Recommendation
Add an explicit guard in the `TimeoutMessage::Post` branch of `modules/ismp/core/src/handlers/timeout.rs` (and the corresponding EVM `handlePostRequestTimeouts` in `evm/src/core/HandlerV2.sol`) that rejects timing out a request for which a response has already been recorded/consumed on the source chain, mirroring the `GetResponseAlreadyReceived` check used for GET requests. This closes the asymmetry and guarantees mutual exclusivity between the response-delivery and timeout transitions for POST requests, matching the invariant already enforced for GET.

### Proof of Concept
1. Dispatch a `PostRequest` from chain A to chain B with `timeout_timestamp = T`.
2. Relayer delivers the request to chain B slightly before `T`; chain B processes it and dispatches a `PostResponse` back toward chain A.
3. Due to normal network/finality delay, the response arrives and is processed on chain A at time `T + Δ` (after `T` has technically elapsed), causing the source module's `on_response`-equivalent callback to run and release/settle funds.
4. Separately, any actor now submits a `PostRequestTimeoutMessage`/`TimeoutMessage::Post` for the same request commitment: the code only checks (a) `request.timeout() <= state.timestamp` (true) and (b) `host.request_commitment` still exists and (c) non-membership of the *destination request receipt* (also true, since the request truly was delivered — but this proof does not attest to the *response* status on the source chain).
5. `host.dispatchTimeOut(...)` is invoked and the module's `on_timeout` callback executes a second, redundant refund/unlock for the same logical transfer, achieving double-settlement.

/// Reject a GET timeout when the request has already received a response. The request's timeout
/// hasn't elapsed either, so without the response-receipt guard the handler would have failed
/// with `RequestTimeoutNotElapsed` — proving the response check runs first.
pub fn get_response_already_received_check<H>(host: &H) -> Result<(), &'static str>
where
	H: IsmpHost + IsmpDispatcher,
	H::Account: From<[u8; 32]>,
	H::Balance: From<u32> + Default,
{
	let intermediate_state = setup_mock_client(host);
	let get =
		dispatch_get_request(host, &intermediate_state, host.timestamp().as_secs() + 1_000_000);

	let response = GetResponse { get: get.clone(), values: Default::default() };
	host.store_response_receipt(&response, &vec![0u8; 32]).unwrap();

	let timeout_message = Message::Timeout(TimeoutMessage::Get { requests: vec![get] });

	let res = handle_incoming_message(host, timeout_message).map_err(|e| e.downcast().unwrap());
	assert!(matches!(res, Err(Error::GetResponseAlreadyReceived { .. })));
	Ok(())
}

		set_timestamp(Some(Duration::from_secs(100_000_000).as_millis() as u64));

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
