### Title
Forged serialized `ReceivedOutput` causes unspendable deposits to be treated as spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an offset, `TxOut`, and `OutPoint` supplied by the caller without verifying that the claimed outpoint actually contains the claimed output. A malicious party can therefore submit bytes describing a wallet-controlled Taproot output at a nonexistent or mismatched outpoint, causing deposit tracking or transaction construction to treat unavailable funds as spendable. [1](#0-0) 

### Finding Description
`ReceivedOutput` combines three independently supplied fields: the scalar offset, the claimed `TxOut`, and the claimed `OutPoint`. The read implementation parses all three and returns the object directly. [2](#0-1) [1](#0-0) 

Unlike `Scanner::scan_transaction`, which constructs `ReceivedOutput` only after matching a transaction output's script against the registered wallet scripts and binds it to the real transaction ID and output index, deserialization performs no equivalent consistency check. [3](#0-2) 

`SignableTransaction::new` subsequently trusts the supplied values: it sums the claimed output values as available inputs, uses the claimed outpoints as transaction inputs, and preserves the claimed outputs as `prevouts`. [4](#0-3) [5](#0-4) 

`SignableTransaction::multisig` checks only that `offset.group_key()` produces the claimed output's `script_pubkey`; it cannot and does not establish that the claimed `OutPoint` actually refers to that `TxOut`. [6](#0-5) 

### Impact Explanation
An attacker who can submit a serialized `ReceivedOutput` can falsely report a deposit. Because the object carries both the output data and its alleged location, the attacker can claim an arbitrary amount at an arbitrary outpoint while using a valid wallet script so the transaction machine accepts the input. [7](#0-6) 

The resulting spend is either consensus-invalid because the outpoint does not exist, or invalid because the real UTXO's amount/script differs from the claimed `TxOut` committed through `Prevouts::All`. [8](#0-7) 

This maps to the report's forged-request/account-state class: unauthenticated input is interpreted as an authenticated account action or state transition. Here, forged bytes are interpreted as a verified wallet receipt, causing funds to be reported received that are not actually spendable.

### Likelihood Explanation
The attack only requires public knowledge of the wallet's Taproot script or public key and the ability to supply serialized `ReceivedOutput` bytes to a code path that consumes `ReceivedOutput::read`. No private key, validator privilege, malformed curve encoding, or malicious threshold participant is needed.

The wallet script can be produced from the public group key through `p2tr_script_buf`, or copied from an observed output. [9](#0-8) 

### Recommendation
Do not expose or consume `ReceivedOutput::read` as an authoritative receipt format without authentication and UTXO validation. A deserialized output should be treated only as a claim until the corresponding transaction output is retrieved from a trusted Bitcoin source and checked to have exactly the claimed `TxOut`.

Prefer reconstructing `ReceivedOutput` exclusively through `Scanner::scan_transaction` or `Scanner::scan_block`, since those paths bind the output to the containing transaction and derive the real outpoint. [10](#0-9) 

If serialized outputs must cross a trust boundary, authenticate them and revalidate `outpoint -> TxOut`, including value and `script_pubkey`, before feeding them to `SignableTransaction::new`.

### Proof of Concept
Conceptually:

```rust
// Networks/bitcoin/src/wallet/mod.rs
let scanner = Scanner::new(group_key).unwrap();
let wallet_script = scanner
  .scripts
  .keys()
  .next()
  .unwrap()
  .clone();

let forged = ReceivedOutput::read(&mut bytes_for(
  Scalar::ZERO,
  TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: wallet_script,
  },
  OutPoint::null(), // Or any outpoint not containing the claimed TxOut.
)).unwrap();

let signable = SignableTransaction::new(
  vec![forged],
  &[(payment_script, 100_000)],
  None,
  None,
  1,
).unwrap();

// This succeeds because the claimed script corresponds to offset zero.
let machine = signable.multisig(&keys).unwrap();
```

The machine can proceed to sign the transaction because `multisig` verifies only that the claimed script matches the offset key. [11](#0-10)  The signed transaction remains unspendable if `OutPoint::null` or any mismatched outpoint was used, while its claimed input value was already accepted into the wallet's funding calculation. [4](#0-3)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
