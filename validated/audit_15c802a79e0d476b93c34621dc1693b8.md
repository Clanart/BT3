## Title
`updateRemoteUrl` silently repoints the trusted `origin` remote to any host supplied by the GitHub API response, without checking that the new host matches the account's endpoint - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Llama report's broken invariant is: a trust-critical configuration value (bootstrap role/strategy) can be silently changed or misconfigured by an authorized-looking actor, permanently altering the security posture with no additional confirmation, and existing guards don't catch it. The GitHub Desktop analog is `updateRemoteUrl()`, which rewrites the local git `origin` remote URL using `clone_url` taken straight from a `fetchRepository` API response, with no check that the new URL's hostname belongs to the same GitHub/GHE endpoint the account is signed into.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` (around lines 4904-4907) every time Desktop refreshes a repository's associated GitHub metadata via `api.fetchRepository(owner, name)`. [1](#0-0) 

The function itself performs only three checks before rewriting the remote: [2](#0-1) 

1. `protocolsMatch` — only compares the URL *scheme* (`http:`/`https:`), not the host.
2. `remoteUrlUnchanged` — checks that the *current* remote still matches the *previously stored* `cloneURL` for the repo (via `urlMatchesRemote`).
3. `!urlsMatch` — the new URL differs from the current remote.

None of these validate that the new `clone_url` is on the same hostname as the account's API endpoint. `urlMatchesRemote`/`parseRemote` (in `app/src/lib/repository-matching.ts` and `app/src/lib/remote-parsing.ts`) are generic regex parsers that accept **any** hostname — they were only ever used to compare two candidate URLs for internal consistency, not to pin a URL to a trusted origin. [3](#0-2) 

If the value of `clone_url` returned by the GitHub API (a value the attacker controls per the task's valid-impact criteria — "attacker controls ... a GitHub API object") is anything other than the previously known clone URL, but shares the same URL scheme, Desktop will call `gitStore.setRemoteURL()` and silently repoint `origin` to that value — even to a completely different domain. [4](#0-3) 

This mirrors the Llama bug class precisely: a trust anchor (bootstrap role / origin remote) can be reconfigured through an ordinary, expected code path (role removal / API refresh) without any additional confirmation or invariant check that the new configuration is still safe, and there is no analog to the recommended "must remain valid" guard.

### Impact Explanation
Once the `origin` remote is silently changed, every subsequent `git push`/`git fetch`/`git pull` the user performs from the GitHub Desktop UI targets the attacker-supplied host instead of the repository the user believes they are working with. This satisfies "silent corruption of what the user commits or pushes" from the valid-impact list: commits the user believes are going to their legitimate repository can instead be pushed to an attacker-controlled endpoint, and future fetched history/branches come from that attacker endpoint with no visual warning (the Repository Settings dialog would show the new URL, but nothing prompts the user at the time of the change — compare with the explicit `UpstreamAlreadyExists` confirmation dialog used for upstream remotes, which this code path lacks entirely). [5](#0-4) 

### Likelihood Explanation
The trigger condition is realistic: it fires automatically any time Desktop refreshes GitHub metadata for a repository (e.g. background refresh, reopening the app, switching repos) and the account's API server (GitHub.com or, more plausibly, a GitHub Enterprise Server the user has added) returns a `clone_url` for the same `owner/name` that differs from what's currently cached. A malicious or compromised GHE instance, or a man-in-the-middle capable of tampering with just this one JSON field on an otherwise valid TLS session to a server the user already trusts, is sufficient — no local access, no leaked credentials, and no unusual user action are required. The check exists specifically to auto-correct for legitimate rename/transfer flows, so the code path is exercised in normal operation, not a rare edge case.

### Recommendation
Before applying `updatedRemoteUrl`, validate that its hostname matches the hostname of the account's API endpoint (`getHTMLURL(account.endpoint)`) that produced the response, the same way `matchGitHubRepository` already does when initially associating a remote with an account. If the hostname differs, do not auto-update the remote silently — surface an explicit confirmation dialog (similar to `UpstreamAlreadyExists`) so the user can accept or reject the change.

### Proof of Concept
1. User has a GHE repository configured, with `origin` pointing at `https://ghe.corp.example.com/team/app.git`, tracked by Desktop as `IGitHubRepository.cloneURL`.
2. The GHE server (compromised, or an MITM able to tamper with that one API response) returns, in response to `GET repos/team/app`, a JSON body whose `clone_url` field is `https://ghe.corp.example.com.attacker.tld/evil/app.git` (same `https:` scheme, different host).
3. On the next background metadata refresh, `repositoryWithRefreshedGitHubRepository` calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.
4. `protocolsMatch` is true (both `https:`), `remoteUrlUnchanged` is true (current remote still equals the last known good `cloneURL`), and `urlsMatch` is false (new host differs) — all conditions for silent update are met.
5. `gitStore.setRemoteURL('origin', 'https://ghe.corp.example.com.attacker.tld/evil/app.git')` executes without any user prompt.
6. The user's next push/fetch silently targets the attacker's host.

```typescript
  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
