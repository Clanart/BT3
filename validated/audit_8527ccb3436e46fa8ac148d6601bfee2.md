### Title
Copilot merge‑conflict auto‑resolution silently mis‑splices resolved content when a conflicting file contains attacker‑controlled text that mimics git conflict markers - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
GitHub Desktop's Copilot conflict‑resolution feature parses conflict markers twice, with two independently written, regex‑based state machines: `extractConflictHunks` (used to build the LLM prompt) and `reassembleResolvedFile` (used to splice the LLM's per‑hunk output back into the file that is ultimately written to disk and committed). Both detect hunk boundaries using naive line‑level regexes (`^<{7}`, `^={7}$`, `^>{7}`) with no way to distinguish a real git‑inserted marker from identical‑looking literal text that is simply part of one side's file content. Neither function validates hunk *positions*, only hunk *counts* (`validateResolutionPaths`), and `reassembleResolvedFile` explicitly splices resolutions "matched by order, not by line number."

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the raw file text line by line, treats the first `<{7}` as an opening marker, and closes the hunk at the first subsequent line matching `>{7}` — any intervening line that happens to match `^={7}$`, `^\|{7}` or even another `^<{7}` is simply absorbed as ordinary "ours"/"theirs" text: [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) re‑implements essentially the same boundary search independently, using its own copies of the marker regexes, and again just looks for the first `=======`‑like line and the first `>>>>>>>`‑like line after an opening marker: [2](#0-1) 

Because these are two hand‑maintained copies of the same fragile parsing logic (`oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` in `copilot-conflict-context.ts` vs. `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` in `copilot-conflict-resolution.ts`), any file whose real content contains a line that incidentally matches one of these 7‑character marker patterns (e.g. a source file, tutorial, or test fixture that itself contains literal example git‑conflict‑marker text, or a banner/divider comment of exactly seven `=` characters) will shift where each parser thinks a conflict hunk starts and ends. This is structurally the same class of bug as the EthRouter report: a loop/algorithm assumes a piece of shared, externally‑influenced state (here, "where are the conflict boundaries in this file") stays consistent across two separate consumers of that state, when in fact attacker‑controlled input can desynchronize it.

The only safety net, `validateResolutionPaths`, checks that the LLM returned the same *number* of hunks that `extractConflictHunks` found — it never re‑verifies that `reassembleResolvedFile`'s independent re‑scan of `rawContent` agrees on the *same boundaries*: [3](#0-2) 

Since `reassembleResolvedFile` splices strictly "by order, not by line number" (as its own doc comment states), any boundary miscount or misalignment caused by attacker‑crafted marker‑lookalike content results in the model's resolved hunk content being spliced into the wrong location of the file — potentially dropping, duplicating, or relocating code the user never intended — with no error surfaced to the user before the resolved content is written to disk and offered up as the merge/rebase/cherry‑pick resolution to commit and push.

### Impact Explanation
This can silently corrupt the exact content that ends up in the user's commit/push (the same "silent corruption of what the user commits" category flagged as valid impact), without requiring local access, admin rights, or leaked credentials — only that the victim merges/rebases/cherry‑picks a branch or PR whose content was crafted by an attacker (a completely ordinary Desktop workflow: reviewing/merging a pull request). Because conflict resolution is presented as an AI convenience feature, a user is less likely to line‑by‑line re‑review the reassembled file before committing, making this a plausible vector for smuggling unintended changes into a shipped commit.

### Likelihood Explanation
Exploitation requires: (1) the victim to have Copilot conflict resolution enabled and use it on a merge/rebase/cherry‑pick that touches an attacker‑influenced file, and (2) that file to contain, or be crafted to contain, a line matching one of the four marker regexes in a position that shifts hunk boundaries relative to what the two parsers agree on. This is a narrower likelihood than a blanket "always triggers" bug, since it depends on incidental or deliberately crafted marker‑lookalike content landing inside a real conflicting region, but it is entirely attacker‑controllable content (not a rare corner case) and does not require any unusual user action beyond a normal merge conflict resolution.

### Recommendation
- Have `reassembleResolvedFile` reuse the exact same tokenizer/boundary logic as `extractConflictHunks` (ideally the same function, not a duplicated regex set), so hunk boundaries can never diverge between prompt construction and file reassembly.
- Track hunk boundaries by absolute line offsets computed once by `extractConflictHunks` and pass those offsets through to reassembly instead of re‑scanning `rawContent` from scratch and matching "by order."
- After reassembly, diff the reassembled file against the original non‑conflicted regions to assert that only the exact conflict‑marker spans were replaced, and refuse (fail closed, prompting manual resolution) if unexpected regions changed.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
