### Title
Deep-link `filepath` parameter is not validated for path traversal while sibling parameters (`branch`, `pr`) are - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL()` is the entry point for GitHub Desktop's custom protocol handlers (`x-github-client://`, `github-mac://`, `github-windows://`, `x-github-desktop-auth://`, etc.), which are attacker-influenceable: any link a user clicks (e.g., embedded in a webpage, email, or malicious repo README) can invoke them. For the `openrepo` action, the parser validates the `pr` and `branch` query parameters against strict regexes, but it accepts the `filepath` query parameter completely unvalidated and forwards it verbatim into the `open-repository-from-url` action.

### Finding Description
In `parseAppURL`, the `openrepo` handler reads three untrusted query values — `pr`, `branch`, `filepath` — from the URL: [1](#0-0) 

`pr` is checked against `/^\d+$/`, `branch` is checked against `/^pr\/\d+$/` (when tied to a PR) and passed through `testForInvalidChars`, but `filepath` has no equivalent check before being placed into the returned `IOpenRepositoryFromURLAction`: [2](#0-1) 

This is the exact shape of the seed bug class: a set of sibling inputs that are supposed to share the same validation "signature," but one of them (`filepath`) silently diverges from the guard applied to the others (`branch`), just as the Uniswap `UniV3Controller` allow-listed four function signatures assuming they matched the deployed router while one parameter shape silently diverged. Here the broken invariant is "all attacker-controlled parts of an `openrepo` deep link are sanitized before being handed to the rest of the app" — `filepath` breaks that invariant.

The unit tests confirm `branch` is exercised against char-validation (`testForInvalidChars`) but there is no analogous test asserting `filepath` rejects `../`, absolute paths, or other traversal sequences: [3](#0-2) 

The `open-repository-from-url` action (and its `filepath` field) is consumed downstream in `app/src/ui/dispatcher/dispatcher.ts`, which is expected to open the given file relative to the resolved repository once cloned/located — but I was unable to fully inspect that consumption code path within this session's tool budget to confirm exactly how `filepath` is joined to the repository's filesystem path (e.g., whether `Path.join`/`Path.resolve` is used without a containment check afterward). This is the one piece of the chain I could not verify directly from the index and would need to be confirmed in a full checkout.

### Impact Explanation
If the downstream consumer in `dispatcher.ts` builds a filesystem path by joining the repository root with the unsanitized `filepath` (e.g. `Path.join(repository.path, filepath)`) and then opens that path in the user's default editor/file manager, a crafted deep link such as:

```
x-github-client://openRepo/https://github.com/someorg/somerepo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa
```

could cause Desktop to open/read a file outside the intended repository directory when the victim clicks the link — matching the in-scope impact category "file write or read outside the repo" driven by "a link or deep link the user clicks."

### Likelihood Explanation
Likelihood is high for the trigger (any attacker can construct and distribute a `github-mac://`/`x-github-client://` link, and Desktop registers itself as the OS-level handler for these schemes so no other prerequisite is needed), but the ultimate severity is contingent on the unverified behavior of the `filepath`-consuming code in `dispatcher.ts`. If that code already performs a resolved-path containment check, the impact is limited to opening an unexpected but bounded value; if it does not, the traversal is directly exploitable. This uncertainty is called out explicitly above.

### Recommendation
- Apply the same validation used for `branch` (e.g., `testForInvalidChars`, plus explicit rejection of `..`, absolute paths, and drive-letter/UNC prefixes) to `filepath` in `parseAppURL` before constructing the `open-repository-from-url` action.
- Wherever `filepath` is consumed (in `dispatcher.ts`), resolve the final path with `path.resolve()` and assert the result is still contained within the repository's working directory before opening it, mirroring the containment logic already implemented for clone-name sanitization in `sanitizeCloneName` in `app/src/lib/remote-parsing.ts`. [4](#0-3) 

### Proof of Concept
1. Register/observe that Desktop is the default handler for `x-github-client://` (or `github-mac://` on macOS) per `possibleProtocols` in `app/src/main-process/main.ts`. [5](#0-4) 
2. Craft a link: `x-github-client://openRepo/https://github.com/victim/repo?branch=main&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`.
3. Have the victim click the link (e.g., embedded in a web page or chat message).
4. `main.ts`'s `open-url`/protocol handler invokes `handleAppURL` → `parseAppURL`, which returns `{ name: 'open-repository-from-url', url, branch: 'main', filepath: '../../../../.ssh/id_rsa' }` without any traversal check. [6](#0-5) 
5. This action is forwarded to the renderer via `window.sendURLAction(action)`; confirming the exact file-open/join logic in `dispatcher.ts` requires further inspection of that file's handling of the `open-repository-from-url` action, which should be validated in a full local checkout.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

function handleAppURL(url: string) {
  log.info('Processing protocol url')
  const action = parseAppURL(url)
  onDidLoad(window => {
    // This manual focus call _shouldn't_ be necessary, but is for Chrome on
    // macOS. See https://github.com/desktop/desktop/issues/973.
    window.focus()
    window.sendURLAction(action)
  })
}
