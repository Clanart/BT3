## Finding: Missing source-module (`from`) authentication in `SimplexPaymaster.onAccept`

### Summary
`SimplexPaymaster.onAccept` validates that an incoming cross-chain governance message originates from the Hyperbridge chain, but never validates *which module on that chain* sent it. Any contract/pallet on the Hyperbridge chain can dispatch a POST request whose destination module is this paymaster; as long as the request's `source` field matches `IDispatcher(host()).hyperbridge()`, the message is accepted and the encoded `RequestKind` (upgrade, param update, token register/deactivate, or asset withdrawal) is executed unconditionally.

### Finding Description
`onAccept` is gated only by:
1. `onlyHost` — restricting the caller to the local host contract [1](#0-0) 
2. A chain-level check comparing `incoming.request.source` to `IDispatcher(host()).hyperbridge()` [2](#0-1) 

There is no corresponding check of `incoming.request.from` (the source module/app identity on the Hyperbridge chain) against an expected, hard-coded governance module address. The contract's own documentation states the security model relies on authenticating that requests come from "Hyperbridge governance" specifically [3](#0-2) , but the code as written only authenticates the source *chain*, not the source *module*. Once that single chain-id check passes, `onAccept` dispatches directly into privileged branches: contract upgrade via `ERC1967Utils.upgradeToAndCall`, parameter updates, token registration/deactivation, and asset withdrawal — with no further authorization gate [4](#0-3) .

This means any module/pallet/contract deployed on the Hyperbridge chain (which is a permissionless smart-contract/pallet-hosting chain, not solely the governance system) that can dispatch an ISMP POST request destined for this paymaster's address would have its message accepted as legitimate governance, because the code never checks `incoming.request.from`.

### Impact Explanation
If unauthenticated as to source module, an attacker who can get *any* Hyperbridge-chain-resident contract to dispatch a POST request to the paymaster's address (with attacker-controlled body) can:
- Upgrade the paymaster's implementation (`UpgradeContract`) — full contract takeover.
- Register a malicious token/oracle pair (`RegisterToken`) — enabling price manipulation for gas payment.
- Deactivate legitimate tokens (`DeactivateToken`) — denial of service.
- Withdraw all accrued surplus/EntryPoint deposit to an attacker-controlled `treasury` if `UpdateParams` is first used to redirect `treasury`, then `WithdrawAssets` is called.

This matches "Critical: unauthorized upgrade, token registration, token deactivation, or asset withdrawal" as described in the target impact.

### Likelihood Explanation
Exploitability depends on whether an attacker can cause an arbitrary module on the Hyperbridge chain to dispatch a POST request whose `dest`/`to` targets this specific paymaster contract address with attacker-chosen `body` bytes, and whether the ISMP relay/host on the destination EVM chain will deliver it via `handlePostRequests -> onAccept` once proofs are valid (chain-level proof of state, not module-level authentication). Given the destination-chain contract performs no `from` check, this reduces to whether any permissionless dispatch path exists on the Hyperbridge chain that lets an unprivileged party set an arbitrary `body` and arbitrary destination module — this needs confirmation against the Hyperbridge-chain-side ISMP router/dispatch implementation, which was not available for direct inspection in this session.

### Recommendation
Add an explicit check of `incoming.request.from` against an immutable/governance-set expected module identity (e.g., the specific governance pallet's account/module id on Hyperbridge), in addition to the existing `source` chain-id check, mirroring the stated security model ("delivered by the local host" + "originating from Hyperbridge governance").

### Proof of Concept
Not directly demonstrable without access to the Hyperbridge-chain-side dispatch code to confirm whether an unprivileged module can set an arbitrary `from`/destination pairing recognized as valid at the relayer/host proof-verification layer; this is a structural gap in `onAccept`'s authentication logic that should be validated against the full request-routing path (`HandlerV2.handlePostRequests` → `Host.dispatchIncoming` → module resolution) to confirm whether `from` is attacker-influenceable end-to-end.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) {
            revert UnauthorizedCall();
        }

        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        bytes calldata payload = incoming.request.body[1:];

        if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(payload, (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        } else if (kind == RequestKind.UpdateParams) {
            _setParams(abi.decode(payload, (Params)));
        } else if (kind == RequestKind.RegisterToken) {
            (address token, address oracle) = abi.decode(payload, (address, address));
            _registerToken(token, AggregatorV3Interface(oracle));
        } else if (kind == RequestKind.DeactivateToken) {
            _deactivateToken(abi.decode(payload, (address)));
        } else if (kind == RequestKind.WithdrawAssets) {
            (address token, uint256 amount) = abi.decode(payload, (address, uint256));
            _withdrawAssets(token, amount);
        }
    }
