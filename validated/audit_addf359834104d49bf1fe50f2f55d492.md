### Title
Stale matured cool-down slots retain decaying (never-zero) rewardable weight in `getRewardablePercentWAD`, allowing yield theft on already-withdrawable funds - ([File: VLMGP.sol])

### Summary
`getRewardablePercentWAD` computes a weighted percentage of a user's vlMGP balance considered "rewardable," but for slots whose `endTime` has already passed it applies a time-decaying formula `amountInCoolDown * (endTime-startTime) / (timeNow-startTime)` instead of setting the contribution to zero. An attacker who lets a matured cool-down slot sit unclaimed (never calling `unlock()`) keeps earning a shrinking-but-never-zero share of rewards on funds that are already fully withdrawable, effectively double-dipping vs. a user who withdraws promptly.

### Finding Description
In `VLMGP.sol`, `getRewardablePercentWAD` (lines 193-218) iterates a user's `userUnlockings` slots: [1](#0-0) 
For a slot with `block.timestamp > endTime` (fully matured), it adds `amountInCoolDown * 1e18 * (endTime - startTime) / userTotalVlmgp / (timeNow - startTime)`. This term equals the full in-cooldown weight (`amountInCoolDown * 1e18 / userTotalVlmgp`) exactly at `timeNow == endTime`, and asymptotically decays toward (but never reaches) zero as `timeNow` grows, since `(endTime-startTime)/(timeNow-startTime) > 0` for any finite `timeNow`.

The user becomes eligible to fully withdraw the slot via `unlock()` once `block.timestamp > endTime` (checked in `unlock()` at line 319: `if (slot.endTime > block.timestamp) revert StillInCoolDown();`). Nothing forces the user to call `unlock()` promptly — `amountInCoolDown` for that slot remains nonzero in storage until `unlock()`, `cancelUnlock()`, or `forceUnLock()` is explicitly invoked. Because `getRewardablePercentWAD` is used by `vlMGPBaseRewarder` to determine how much of a user's balance is eligible for reward accrual (i.e., not fully forfeited), an attacker can:
1. `startUnlock()` a slot.
2. Wait until `block.timestamp > endTime`.
3. Repeatedly call `MasterMagpie.multiclaimFor(vlMGPBaseRewarder)` without ever calling `unlock()`.

Each claim, the matured slot still contributes a nonzero (decaying) fraction of `amountInCoolDown` to `percent`, meaning the reward pool treats those already-withdrawable MGP tokens as if partially still "locked and earning," when a fully honest user who withdrew at `endTime` would have that principal outside the vlMGP system and not earn any further reward on it. This lets the attacker accrue reward yield they should not be entitled to, taken from the pool of rewards that should otherwise be distributed to genuinely locked stakers (or forfeited/redistributed).

Existing checks (`whenNotPaused`, `nonReentrant`, boundary checks in `_checkIdexInBoundary`/`_checkInCoolDown`) do not address this because the flaw is in the reward-weight *formula* itself, not access control — the attacker never needs privileged calls, just delaying an unlock call which is entirely within a normal EOA's control.

### Impact Explanation
This falls under **theft of unclaimed yield**: an unprivileged staker keeps collecting rewards on funds that have already fully matured and are eligible for withdrawal, diverging from the intended "forfeiture on maturity" semantics implied by `getFullyUnlock` (which correctly treats any `amountInCoolDown` slot past `endTime` as fully unlocked, i.e., not entitled to further lock-based rewards). The magnitude scales with `amountInCoolDown` and inversely with elapsed time since `endTime`, so it decays but is nonzero for an economically meaningful window (potentially very large window given `coolDownInSecs` could be small relative to time delayed), representing real, quantifiable extra reward capture at the expense of the shared reward pool.

### Likelihood Explanation
Very feasible: requires only a regular lock + `startUnlock()` + waiting past `endTime` + repeated `multiclaimFor` calls, no capital beyond normal staking amounts, no special permissions, fully repeatable by any staker, and does not require racing or reentrancy. The exploit is essentially "just don't call unlock promptly," a strategy any rational staker could adopt to maximize yield.

### Recommendation
Zero out the rewardable weight for slots once `block.timestamp > endTime` in `getRewardablePercentWAD`, matching the semantics used in `getFullyUnlock` — i.e., remove the decaying `else`-branch contribution for matured slots (or explicitly set that term to 0) so that funds past `endTime` immediately stop earning further reward weight regardless of when `unlock()` is eventually called.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` with a reward token funded into the rewarder.
2. User A: `lock()` X MGP, `startUnlock(X)` to open a cool-down slot with `coolDownInSecs = T`.
3. User B (control): `lock()` X MGP, never starts unlock (fully locked comparator), or alternatively starts unlock and calls `unlock()` exactly at `endTime`.
4. Warp time to `endTime + 1`.
5. Call `getRewardablePercentWAD(userA)` and assert it is still > 0 (non-zero), matching the near-full in-cooldown weight.
6. Warp further (e.g., `endTime + 10*T`) without calling `unlock()` for User A; call `getRewardablePercentWAD(userA)` again and assert it is still > 0 (decaying but nonzero).
7. Trigger `MasterMagpie.multiclaimFor([vlMGPBaseRewarder], ..., userA)` at each step and record reward token balance delta.
8. Compare cumulative rewards captured by User A (who never unlocks) against a baseline user who withdrew immediately at `endTime` and thus should earn zero further reward on that principal — assert User A's cumulative reward is strictly greater than zero post-maturity, demonstrating the conservation violation (extra yield extracted from the shared pool without corresponding continued lock).
