### Title
Tokenfactory denom allow-list is enforced only in Msg handlers, not in `SendCoins`/`InputOutputCoins` — bypassable via any other bank transfer path - (File: sei-cosmos/x/bank/keeper/send.go, sei-cosmos/x/bank/keeper/msg_server.go)

### Summary
The tokenfactory "allow list" permission feature (used to restrict who may hold/transfer a given `factory/...` denom) is validated with `IsInDenomAllowList` only inside `msgServer.Send` and `msgServer.MultiSend` [4](#0-3) . The actual fund-movement primitives `BaseSendKeeper.SendCoins` and `BaseSendKeeper.InputOutputCoins` in `sei-cosmos/x/bank/keeper/send.go` do not call `IsInDenomAllowList` themselves [5](#0-4) . This mirrors the reported Set Protocol issue: a whitelist is "hard coded" into one calling function's definition instead of being enforced centrally at the resource being protected, so any other caller of the primitive skips the restriction.

### Finding Description
`IsInDenomAllowList` is defined on `BaseSendKeeper` and documented as restricting transfers of tokenfactory-prefixed denoms to addresses on a per-denom allow list [6](#0-5) . It is exposed via the `SendKeeper` interface [7](#0-6) , but it is invoked only from `msg_server.go`'s `Send`/`MultiSend` gRPC handlers before calling `SendCoins`/`InputOutputCoins`. The lower-level `SendCoins` and `InputOutputCoins` functions — which are also called directly by many other subsystems (module keepers such as tokenfactory Mint/Burn via `SendCoinsFromModuleToAccount`, IBC transfer, wasmd bank bindings, and EVM `bank` precompile logic) — perform no allow-list check at all. Because the check is duplicated at each call site ("in-method validation" style) rather than centralized in the primitive, it is trivial for any new or existing caller to omit it, exactly matching the report's description of inconsistent, hard-coded whitelist validation.

### Impact Explanation
If any reachable code path invokes `SendCoins`/`InputOutputCoins` (or `SendCoinsFromModuleToAccount`) for a tokenfactory-restricted denom without going through the `x/bank` MsgServer — e.g. a CosmWasm contract's bank send binding, the EVM `bank` precompile, or an IBC transfer receive handler — an attacker could move restricted-denom tokens to/from addresses that are supposed to be blocked by the denom's allow list, defeating the compliance/permission control the token issuer relies on. This is an unauthorized-transfer-class impact (bypassing an intended access control on fund movement), which is why it's evaluated at Medium+ rather than as low/informational.

### Likelihood Explanation
Likelihood depends entirely on whether a non-MsgServer path to `SendCoins`/`InputOutputCoins` is reachable by an unprivileged sender for tokenfactory-allow-listed denoms (e.g., via the CW/EVM bank precompile, wasmd `BankMsg::Send` binding, or IBC transfer). I was unable to fully confirm within the available tool budget whether those specific call sites for wasmd/EVM/IBC funnel back through `msgServer.Send` (which would keep the check enforced) or call `SendCoins` directly (which would bypass it). Given the number of independent callers of `SendCoins` across `precompiles/`, `x/wasm`, and `x/ibc` observed in the codebase, and the fact that the same allow-list check has already needed to be duplicated in `giga/deps/xbank/keeper/send.go` (a separate keeper fork) [8](#0-7) , this appears architecturally likely to have at least one bypass, but this should be confirmed by tracing each caller before treating it as a proven exploit.

### Recommendation
- Short term: Move the `IsInDenomAllowList` (and `IsSendEnabledCoins`/`BlockedAddr`) checks into `BaseSendKeeper.SendCoins` and `InputOutputCoins` themselves, rather than only in the `msgServer.Send`/`MultiSend` handlers, so that every caller of these primitives is subject to the same restriction.
- Long term: Audit all callers of `SendCoins`, `InputOutputCoins`, and `SendCoinsFromModuleToAccount` (precompiles, wasmd bindings, IBC transfer, tokenfactory) to confirm none bypasses the allow-list, and add regression tests asserting that a restricted-denom transfer fails regardless of entry point.

### Proof of Concept
Not independently reproduced — this requires enumerating and testing every non-MsgServer caller of `SendCoins`/`InputOutputCoins` (CW bank bindings, EVM bank precompile, IBC transfer) with a tokenfactory denom that has a `DenomAllowList` set via `SetDenomAllowList` [9](#0-8) , to confirm at least one path lets a non-allow-listed address send/receive the coin. This step was not completed due to tool-call limits and should be validated with a live Devin session before treating this as a confirmed exploit.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (k BaseSendKeeper) getAllowedAddresses(ctx sdk.Context, cache map[string]AllowedAddresses, denom string) AllowedAddresses {
	allowedAddresses, exists := cache[denom]
	if !exists {
		allowList := k.GetDenomAllowList(ctx, denom)
		allowedAddresses = k.buildAllowedAddressesMap(allowList)
		// we cache even if the allowList is empty to avoid multiple db reads
		cache[denom] = allowedAddresses
	}
	return allowedAddresses
}
