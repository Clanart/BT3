### Title
Parser Desync Between `extractConflictHunks` and `reassembleResolvedFile` Causes Silent Deletion of Conflicted Code When Applying Copilot Merge-Conflict Resolutions - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot-assisted merge conflict resolution feature computes the number/boundaries of conflict "hunks" twice, using two different parsers over the same raw file content: `extractConflictHunks` (strict, used to build the prompt/context and the expected hunk count) and `reassembleResolvedFile` (loose, used later to splice the model's per-hunk resolutions back into the file on disk). These two parsers disagree on what counts as a well-formed conflict block, so a file containing an attacker-supplied line that merely *looks like* a conflict marker (`<<<<<<<` at column 0) — unrelated to any real git conflict — can desynchronize hunk indices between the two passes. The result is that `reassembleResolvedFile` silently drops a real conflicted region (both "ours" and "theirs" content) from the file it writes back to disk, with no error, warning, or diff shown to the user before they commit/push.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file once, and when it finds an `oursMarker` (`^<{7}(?:\s|$)`) that is never followed by a matching `theirsMarker` before EOF, it treats the rest of the file as consumed and yields **no further hunks past that point**: [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), which later re-parses the *same raw file content independently* to splice the model's `hunkResolutions` back in, uses a much looser lookahead: on hitting a `<<<<<<<`-like line, it scans forward for *any* `=======` line and then the *first* `>>>>>>>` line anywhere after it — with no requirement that they belong to the same block: [2](#0-1) 

If a file contains (a) a real, well-formed conflict, followed later by (b) an orphaned `<<<<<<<`-style line that never closes, followed later still by (c) another real conflict:
- `extractConflictHunks` stops at (b) and only returns hunk (a). `expectedHunkCounts` (used in `validateResolutionPaths`, `app/src/lib/copilot-conflict-resolution.ts:473-521`) and the prompt sent to the model therefore only describe 1 hunk for this file, so the model returns exactly 1 `IHunkResolution`.
- `reassembleResolvedFile`, scanning independently, correctly matches hunk (a) first, then hits orphaned marker (b), and its lookahead finds the `=======`/`>>>>>>>` belonging to real conflict (c) — treating the entire span from (b) through the end of (c) as a single "hunk" block. Since `hunkIndex` is now `1` but `hunkResolutions.length === 1` (only one resolution exists), the bounds check `if (hunkIndex < hunkResolutions.length)` fails and **nothing is spliced in** for that span: [3](#0-2) 

The net effect: the orphaned marker line, real conflict (c)'s ours/theirs content, and any surrounding lines caught between (b) and (c)'s `>>>>>>>` are silently removed from the reassembled file that `reassembleResolutions` (`app/src/lib/copilot-conflict-resolution.ts:609-642`) returns and that the app subsequently writes to disk and stages for commit.

This is a real GitHub Desktop analog of the report's root cause: two calculations over the same input (there, `msg.value`/`_paymentAmount` vs. the actual computed NMT quantity; here, `extractConflictHunks`'s hunk count vs. `reassembleResolvedFile`'s independently re-derived hunk boundaries) go out of sync, and the code that "fixes" the mismatch (bounds check `hunkIndex < hunkResolutions.length`) drops the excess rather than validating/erroring, causing silent loss — directly mirroring how NETM-25's fix "returns the incorrect [resource]" instead of the right one.

### Impact Explanation
This is a silent-corruption-of-committed-content bug reachable from an attacker-controlled cloned/fetched branch: a malicious contributor crafts a file (e.g., documentation, a test fixture, a comment) containing a bare, unterminated `<<<<<<<`-style line at column 0. When the victim later merges/rebases/cherry-picks that branch and a real, unrelated conflict occurs later in the same file, and the victim uses Desktop's "Resolve with Copilot" feature to resolve conflicts, the written-to-disk resolved file can have an entire real conflict region (the victim's or the incoming branch's actual code) silently deleted — with no visible error. If the user trusts the AI resolution and commits/pushes without carefully diffing, this corrupts what they commit, potentially removing security-relevant code, logic, or configuration without any indication of failure.

### Likelihood Explanation
The precondition (a file containing a plain-text `<<<<<<<`-prefixed line that is never properly closed, sitting before a real conflict block in the same file) is easy for a malicious repository/branch to construct — e.g., embedding literal, illustrative git-conflict-marker text in a README, comment, or fixture. It only becomes exploitable when the victim (1) merges/rebases against the malicious branch, (2) that produces a real conflict later in the same file, and (3) the victim uses the Copilot conflict-resolution feature and doesn't manually diff the AI's output before committing. This requires the optional AI-assisted merge feature to be enabled/used, which narrows likelihood, but no privileged access or local compromise is needed — only a hostile git history that an unsuspecting user merges.

### Recommendation
Unify the two parsers so hunk boundaries are computed once and shared: have `extractConflictHunks` compute the exact hunk marker positions once (not just extracted content), and pass those positions through to the reassembly step instead of having `reassembleResolvedFile` re-derive boundaries independently with a different (looser) matching algorithm. At minimum:
1. Make `reassembleResolvedFile`'s malformed-block detection at least as strict as `extractConflictHunks` (require the separator to appear with no intervening bare `<<<<<<<`/`>>>>>>>` marker, matching `isConflictMarker`'s guard used elsewhere).
2. After reassembly, assert that the number of hunk blocks found equals `hunkResolutions.length` exactly; throw a `CopilotValidationError` (fail closed) instead of silently omitting content when the counts disagree.
3. Add a post-reassembly sanity check verifying no conflict markers remain and that no unexpectedly large content deletion occurred relative to the original file, refusing to apply the resolution instead of silently dropping data.

### Proof of Concept
1. Attacker pushes a branch containing `victim-file.ts` with content such as:
```
function real() {
<<<<<<< HEAD
  return 1;
=======
  return 2;
>>>>>>> feature
}

// Example of a git conflict marker for docs purposes:
<<<<<<< example-orphan

function another() {
<<<<<<< HEAD
  return "ours";
=======
  return "theirs";
>>>>>>> feature
}
```
2. Victim merges/rebases the attacker's branch into a branch where `function another()` also independently conflicts (both sides modify it), producing the second real conflict block shown above through normal git merge machinery, while the orphaned `<<<<<<< example-orphan` line was already present verbatim in the attacker's committed file content.
3. Victim opens the conflicted file in Desktop and invokes "Resolve with Copilot".
4. `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179`) parses only 1 hunk for this file (the first `real()` conflict) because the orphaned marker consumes the remainder of the file without a valid closing marker in *its* strict parse, so only one resolution is requested from and returned by the model.
5. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549`) independently re-parses the same file: it resolves hunk 1 correctly, then at the orphaned marker its lookahead finds the *second* real conflict's `=======`/`>>>>>>>` and treats the whole span as a second "hunk". Since only one resolution exists, `hunkIndex (1) < hunkResolutions.length (1)` is false, so nothing is spliced in.
6. The resulting file written to disk (and staged) is missing `function another() { ... }` and its conflicting content entirely — silently — with no error surfaced to the user before they commit and push.
