## Analog Found: Value sent to distribution precompile's `rewards()` is permanently stranded

### Title
Value sent with `rewards()` calls to the distribution precompile is permanently locked - ([File: precompiles/distribution/distribution.go])

### Summary
The distribution precompile at `0x0000000000000000000000000000000000001007` dispatches the `rewards` method without validating or refunding any attached `msg.value`, unlike every other view/transaction method in the same dispatcher. A caller who mistakenly (or via a buggy integrator contract) sends native value alongside a `rewards()` call has that usei permanently transferred into the precompile's associated Sei account with no code path to reclaim it.

### Finding Description
`PrecompileExecutor.Execute` in `precompiles/distribution/distribution.go` dispatches methods based on `method.Name`. Every other transaction/query method calls `pcommon.ValidateNonPayable(value)` (directly or via `p.validateInput`) before proceeding, e.g. `WithdrawValidatorCommissionMethod`: [1](#0-0) 
and `delegationRewards`, which uses `p.validateInput(value, args, 2)` → `pcommon.ValidateNonPayable(value)`: [2](#0-1) 

However, `RewardsMethod` is dispatched with no such check: [3](#0-2) 

And the `rewards()` implementation itself never inspects or rejects `value`, never refunds it, and never forwards it anywhere — it just queries `DelegationTotalRewards` and returns: [4](#0-3) 

This gap has persisted across the precompile's legacy versions (v555 through v640) — `rewards()` never calls `ValidateNonPayable`, while sibling methods consistently do: [5](#0-4) 

Because the EVM->bank bridge (StateDB) transfers `msg.value` (converted usei/wei) into the precompile's associated Sei account as part of normal EVM value-transfer semantics before/around precompile execution, and the distribution precompile is **not** in the `payablePrecompiles` allowlist that receives special payment-refund handling (only `bank`, `staking`, `gov`, `wasmd` are registered there): [6](#0-5) 
the value sent to `rewards()` is not refunded by `HandlePaymentUsei`/`HandlePaymentUseiWei` (which other payable methods explicitly invoke to move funds back to the payer), nor is it consumed for any purpose. It simply lands in the precompile's Sei-mapped account and there is no withdrawal/sweep mechanism exposed by the distribution module or precompile to recover it. This directly mirrors the reported Gitcoin issue: an unverified/unused `msg.value` in a callable function results in funds being irrecoverably locked in the receiving contract.

### Impact Explanation
Any unprivileged EVM caller (EOA or contract) can send native SEI value along with a `rewards(address)` call to the distribution precompile. That value is debited from the caller and credited to the precompile's Sei account, but is never refunded, spent, or exposed via any recovery method — resulting in permanent fund loss for the sender. This satisfies "concrete fund loss or permanent freezing" from the validation criteria, reachable via a single submitted EVM transaction to a public precompile without any special privilege.

### Likelihood Explanation
Likelihood is moderate: this requires a caller (or an integrating dApp/contract) to mistakenly attach `msg.value` to a call whose interface is declared as a view/query (most tooling would not attach value to a `view`-labeled call, but the Solidity ABI for the precompile does not necessarily mark `rewards` `payable` vs non-payable in a way that prevents an arbitrary low-level `call{value: x}(...)` from succeeding). Since the EVM does not restrict calls with value to only `payable` Solidity functions at the raw-call/precompile-dispatch layer, any raw transaction or a buggy proxy/router contract forwarding value can trigger this loss.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` case in `precompiles/distribution/distribution.go`'s `Execute` dispatcher (matching the pattern of every other query/transaction method in the same file), so that any attached value causes an immediate revert instead of being silently absorbed and stranded.

### Proof of Concept
1. An EVM account associated with a Sei address calls the distribution precompile at `0x0000000000000000000000000000000000001007` with:
   - function selector for `rewards(address)`
   - `value = 1 SEI` (or any nonzero amount)
2. `Execute` routes to `case RewardsMethod: return p.rewards(ctx, method, args)` at `precompiles/distribution/distribution.go:204-205` with no `ValidateNonPayable` check.
3. `rewards()` at `precompiles/distribution/distribution.go:543-579` runs the query and returns successfully; the attached value is never referenced, refunded, or reverted.
4. Because `distribution` is absent from `payablePrecompiles` in `x/evm/keeper/precompile.go:13-18`, no special payment-refund flow triggers either.
5. The caller's 1 SEI is now held by the precompile's associated Sei account with no exposed function to withdraw or reclaim it — permanent loss.

```go
func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
```
