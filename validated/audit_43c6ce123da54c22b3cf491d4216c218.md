## Analysis

The EIP-4758 report's core broken invariant is: *a shared, address-keyed custody mechanism has no authentication on who can trigger it, so whoever races the mechanism first captures value that was meant to flow to someone else.* The Hyperbridge analog is `CallDispatcher.sol`, a single shared, unauthenticated contract used both by `IntentGatewayV2` (predispatch/postdispatch flows) and by `HyperFungibleToken`/`WrappedHyperFungibleToken` (destination-chain calldata execution) to route funds through arbitrary calls.

`CallDispatcher.dispatch()` has **no access control at all** — no `onlyGateway`, no `onlyHost`, nothing gating who may call it: [1](#0-0) 

Any balance the dispatcher happens to hold at any point between transactions can be swept by an unrelated caller. The HFT flow explicitly relies on the dispatcher "holding tokens temporarily during execution" with no automatic sweep-back for leftovers: [2](#0-1) 

Tokens are minted (or unlocked) directly to `to` — which the docs recommend setting to the `CallDispatcher` address — and then the dispatcher executes the attached `Call[]`: [3](#0-2) 

By contrast, `IntentGatewayV2`'s own predispatch/postdispatch flows always sweep the *entire* residual balance for the specific input/output tokens back to the gateway after executing calldata through the same shared dispatcher: [4](#0-3) [5](#0-4) 

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone sweep residual token/native balances left by HyperFungibleToken calldata execution - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, permissionless contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute arbitrary attacker/user-supplied `Call[]` on behalf of these apps. Its `dispatch(bytes)` entrypoint is `external` with no caller restriction whatsoever. `IntentGatewayV2` mitigates the risk by always sweeping the full residual balance of the relevant tokens back to itself in the same transaction after every `dispatch()` invocation. The HFT calldata-execution path, however, mints/unlocks bridged tokens directly to the dispatcher and executes user-supplied calldata with no such mandatory full sweep. Any token or native balance left over on the dispatcher after that calldata runs — from slippage-bounded swaps, partial consumption of an approval, or a call that doesn't spend the full minted amount — sits in a contract anyone can drain, because `dispatch()` does not check `msg.sender` or scope which balance belongs to which pending flow.

### Finding Description
`CallDispatcher.dispatch()` decodes an arbitrary `Call[]` and executes each entry with `to.call{value: call.value}(call.data)`, with the only check being that `to` has code: [1](#0-0) 

There is no restriction limiting who may invoke `dispatch()` — not `onlyHost`, not an allowlist of calling apps, not even a check that `msg.sender` is one of the registered HFT/IntentGateway contracts. The contract is meant to be a temporary pass-through: HFT mints tokens to it and then immediately calls `dispatch()` with the user's cross-chain calldata payload so the tokens can be swapped/staked/deposited atomically. Because the dispatcher holds a real, spendable ERC20/native balance for the duration of that calldata execution (and potentially after it, if the calldata doesn't consume the full amount — e.g. a swap with slippage protection, or approve-then-partial-spend patterns explicitly called out as needed in the docs), any balance it is currently holding is available to be redirected by an unrelated third party simply by calling `dispatch()` directly with a `Call` that transfers the token/ETH elsewhere.

`IntentGatewayV2` is aware of this exact risk class and defends against it by unconditionally sweeping 100% of the relevant token balances back to itself after every dispatcher interaction (both for predispatch and postdispatch calldata): [6](#0-5) 

The HFT flow has no equivalent contract-enforced guarantee — the "sweep any leftover" responsibility is pushed onto the user's own calldata design, and nothing prevents a third party from front-running/racing that cleanup, or exploiting the case where the user's calldata legitimately leaves dust (e.g. `swapExactTokensForETH`-style calls with `amountOutMin` slippage bounds necessarily leave the unspent input token or excess output on the dispatcher when the trade executes better than the minimum).

### Impact Explanation
Any unspent balance left in `CallDispatcher` after an HFT cross-chain calldata execution (or any other integrator that routes value through it without an atomic, mandatory full sweep) can be permissionlessly redirected to an attacker's address instead of the intended recipient. This is a direct, unauthorized-execution fund-loss path: the attacker needs no relayer, prover, or privileged role — just a normal transaction calling the public `dispatch()` function with a `Call` targeting the token contract's `transfer`/`transferFrom` or a raw ETH send to themselves.

### Likelihood Explanation
The dispatcher is a well-known, publicly documented, permanently deployed address (listed on the contract-addresses page), so attackers can trivially monitor its balance and race any transaction that leaves a non-zero balance there. The documented usage pattern (mint/unlock to `CallDispatcher`, then execute calldata that swaps/stakes/deposits) makes non-zero leftover balances a realistic, even routine occurrence whenever the executed calldata includes slippage-bounded swaps or partial-consumption approvals — exactly the pattern shown in the official HFT documentation examples.

### Recommendation
Add access control to `CallDispatcher.dispatch()` restricting callers to an allowlisted set of authorized apps (e.g. the registered `IntentGatewayV2`, `HyperFungibleToken`/`WrappedHyperFungibleToken` instances), or make the dispatcher single-use/ephemeral per invocation (e.g. deploy a fresh minimal-proxy dispatcher per call and self-destruct-free sweep pattern), or require the HFT calldata path to mandatorily sweep any residual balance for the message's token back to the sender/beneficiary in the same transaction, mirroring the pattern already implemented in `IntentsBase._execute`.

### Proof of Concept
1. Attacker monitors the `CallDispatcher` contract address (public, listed in docs) for non-zero token/ETH balance.
2. A legitimate cross-chain HFT transfer arrives via `onAccept`, minting `amount` of `DEST_TOKEN` to `CALL_DISPATCHER`, then calling `CallDispatcher.dispatch(data)` with the user's swap calldata (`approve` + `swapExactTokensForTokens` with `amountOutMin < expected`).
3. The swap executes successfully but produces more output than `amountOutMin`/leaves unspent approval dust, or the swap only partially consumes the approved amount, leaving residual `DEST_TOKEN`/output-token balance sitting on `CallDispatcher` after the `onAccept` transaction completes.
4. Attacker immediately submits a transaction calling `CallDispatcher.dispatch(abi.encode([Call({to: DEST_TOKEN, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)})]))`.
5. Since `dispatch()` performs no caller check, the call succeeds and the residual balance intended for the bridge recipient is transferred to the attacker instead.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```

```text
        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
```
