Based on the evidence I was able to gather, the closest structural analog to the Sherlock ADL bug — "a security-relevant decision computed from a value that is cached/aggregated at the wrong scope" — is the global, cross-account `cachedRepoRulesets` map used to evaluate GitHub repo rules (branch protection / signed-commit / push restrictions).

### Title
Repo-ruleset cache is keyed only by numeric ruleset ID with no per-endpoint scoping, allowing rules from one GitHub host to be silently applied to a repository on a different host - (File: app/src/lib/stores/app-store.ts)

### Summary
`IAppState.cachedRepoRulesets` is declared as `ReadonlyMap<number, IAPIRepoRuleset>` [1](#0-0) , a single global map shared by the whole application state, not scoped per account/endpoint/repository. It is populated in `refreshBranchProtectionState` by fetching `fetchAllRepoRulesets`/`fetchRepoRuleset` for the currently selected repository's `owner`/`name` and inserting results keyed only by `rs.id`:

public _updateCachedRepoRulesets(rulesets: Array<IAPIRepoRuleset | null>) {

### Finding Description
The invariant that should hold is: "a repo-rule/ruleset object used to evaluate whether the current repository/branch is subject to a rule must belong to that same repository and GitHub instance." Instead, the cache lookup `this.cachedRepoRulesets.has(id)` is scoped only by the bare numeric `id` returned by the API [3](#0-2) . GitHub ruleset IDs are small sequential integers assigned independently per GitHub instance (github.com vs. each GitHub Enterprise Server the user is signed into) — the same numeric ID is not unique across hosts. Because Desktop supports simultaneously signing into multiple accounts/endpoints, and this cache is a single app-wide map that is consulted before making a per-repo API call and never invalidated when the "current" repository/endpoint changes, a ruleset fetched for repository A on host X can be returned (via the cache hit) as if it were the ruleset for repository B on host Y whenever their numeric ruleset IDs coincide. This is structurally the same defect as the ADL bug: a value meant to be scoped to a specific entity (per-emode-group debt / per-endpoint ruleset) is instead read from an unscoped/aggregate store (global reserve debt / global-by-id cache), so the security decision is computed against the wrong entity's data.

The consumers of this cache (`parseRepoRules`, branch-name validation in `create-branch-dialog.tsx`/`rename-branch-dialog.tsx`, and rule-bypass checks in `multi-commit-operation.tsx`/`cherry-pick.tsx`) trust whatever `IAPIRepoRuleset` object is returned for a given ID without re-verifying it actually belongs to the target owner/name/endpoint [4](#0-3) . No existing guard cross-checks the cached ruleset's repository/endpoint before use — the only "stop condition" analog (checking `owner`/`name` when fetching) is bypassed entirely on a cache hit.

### Impact Explanation
If an attacker controls or compromises a GitHub Enterprise Server instance the victim is signed into (an allowed "GitHub API object / remote response" attacker per the task's valid-impact list), they can craft ruleset responses whose `id` intentionally collides with a ruleset ID already cached for the victim's real, security-sensitive repository (e.g., a repo requiring signed commits or restricting force-pushes). Once cached, that forged/mismatched ruleset silently satisfies the cache check for the legitimate repository and is used to compute `currentRepoRulesInfo`, `repoRulesEnabled`, and rule-bypass status shown in the commit box and multi-commit-operation flows. This can silently suppress an enforcement warning/bypass check that should have blocked or flagged an operation (e.g., signed-commit requirement, protected branch name pattern), i.e., "silent corruption of what the user commits or pushes" as defined in the task's valid-impact criteria. Conversely, it can also spuriously report rule failures on an unrelated repository.

### Likelihood Explanation
This requires: (1) the victim to have at least two active GitHub accounts (e.g., github.com plus an Enterprise Server, or two Enterprise Server instances) — a common, unprivileged, ordinary Desktop configuration, and (2) numeric ruleset ID collision between the attacker-influenced host and the target repo, which the attacker can engineer by creating/deleting rulesets on their own (attacker-controlled) server to land on the desired ID, since ruleset IDs are simply sequential integers under server control. No local access, malware, or leaked credentials are needed — only that the app has previously fetched rules for the target repo and later fetches/caches rules from the attacker's server for a repo sharing an active session. I was not able to fully trace `app/src/lib/helpers/repo-rules.ts` (`parseRepoRules`) in this session, so I could not fully confirm every downstream consumer's exact bypass logic; this should be verified before treating impact severity as final.

### Recommendation
Scope `cachedRepoRulesets` (and its lookup/insert keys) by a composite key that includes the GitHub endpoint plus owner/name (or at minimum the endpoint), e.g. `` `${endpoint}:${id}` ``, instead of the bare numeric `id`, mirroring how `protectionEnabledForBranchCache`/`branchProtectionSettingsFoundCache` are already correctly scoped by `dbID` in `RepositoriesStore` [5](#0-4) . Additionally, validate that any cached `IAPIRepoRuleset` used for a repository still corresponds to that repository's owner/name before applying it.

### Proof of Concept
Not independently reproduced with a runnable test in this session (would require standing up two mock GitHub API endpoints returning colliding ruleset IDs and driving `refreshBranchProtectionState` for two repositories on different endpoints to observe cross-contamination of `IAppState.cachedRepoRulesets`). Given the read-only nature of this investigation and iteration limits, I could not execute or fully trace `parseRepoRules` and every UI consumer to confirm the exact user-visible bypass; this is flagged as a code-evidence-based finding requiring runtime verification rather than a fully demonstrated exploit.
