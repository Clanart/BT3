## Title
Stale partial-commit line selections can cause GitHub Desktop to silently stage/commit different lines than the user reviewed and approved - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The `Fee on transfer tokens` report is really about a mismatch between the *amount a caller assumes was transferred* and the *amount that was actually transferred*, with the contract then acting (approving) on the stale/assumed value instead of the real one. The GitHub Desktop analog is the partial-commit ("stage selected lines") pipeline: the app records a user's line selection against one snapshot of a file's diff, but re-fetches the diff (and the line indices it depends on) at commit time without validating that the previously selected indices still refer to the same underlying content. The patch used to update the index/commit is then built from this stale selection, so the app can silently stage/commit lines the user never reviewed or approved.

### Finding Description
When a file is selected in the Changes view, Desktop loads a diff and lets the user pick individual lines via `DiffSelection`. When the working directory changes while that diff is displayed, `updateChangesWorkingDirectoryDiff` explicitly acknowledges that the diff "might have changed dramatically since last we loaded it" and only prunes selection bits for lines that are no longer selectable — it does **not** verify that a still-selected absolute index still points at the same logical line/content: [1](#0-0) 

At commit time, `applyPatchToIndex` fetches the diff **again** (a second, independent `getWorkingDirectoryDiff` call, temporally separate from whatever diff the user actually looked at in the UI) and hands it straight to `formatPatch`: [2](#0-1) 

`formatPatch` builds the patch purely by indexing into this freshly-fetched diff's hunks using `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and asking `file.selection.isSelected(absoluteIndex)` — it never checks that the line at that index is the same content the user selected when they made their choice: [3](#0-2) 

This is structurally identical to the fee-on-transfer bug: the code approves/acts on an *assumed* quantity (the selection bitmap tied to an old diff layout) instead of validating it against the *actual* current state (the new diff's hunks/lines), and the guard that exists (`withSelectableLines`) only removes selections for lines that vanished — it does not re-validate that surviving indices still map to the same line content when hunks shift (insertions/deletions earlier in the file, hunk boundary changes, etc.).

### Impact Explanation
If the tracked file's content changes between the time the user visually reviews/selects diff lines and the time Desktop re-diffs the file to build the commit patch — for example due to another process, a build tool, or content mutated by the repository's own tooling (e.g., generated files, filters, or a build step the repo's own scripts trigger) — the absolute line indices can silently now refer to different lines than the ones the user selected. `git apply --cached` will then stage a patch representing the wrong hunks/lines relative to user intent. This falls squarely into "silent corruption of what the user commits or pushes": the user believes they are committing exactly the lines they clicked, but the actual staged/committed content can differ without any error or warning, since `git apply` will happily succeed as long as context lines still match.

### Likelihood Explanation
The window between diff-render and commit-time re-diff is small but real in normal Desktop usage (diff panel stays open while a background process modifies the file, or the user takes time selecting individual lines while file-watchers/build tools/linters/format-on-save tools in their editor rewrite the file). The existing mitigation explicitly documents that it is incomplete ("Ideally we would be more clever about validating that any partial selection state is still valid... but for now we'll settle on just updating the selectable lines"), meaning the developers were aware selection validity could drift but chose not to fully guard against it.

### Recommendation
Before building the commit patch, re-validate that each selected absolute line index in `file.selection` still corresponds to the same line content/hash as when the selection was made (not just that the index is within `selectableLines`). If the diff has changed since the last selection snapshot, either re-map the selection against the new hunk structure by content/context matching, or clear/re-prompt the user to reselect rather than silently reusing indices computed against a stale diff.

### Proof of Concept
1. Open Desktop, modify a tracked file, and open its diff in the Changes view.
2. Select only specific lines (partial commit) via the line-by-line UI, leaving the diff panel open.
3. Before clicking "Commit", have an external process (e.g., an editor's format-on-save, a linter, or a script) insert/remove a line earlier in the same file, shifting the hunk's line numbering without necessarily invalidating the specific selected indices under `withSelectableLines`.
4. Click "Commit". Observe (via `git show`/`git diff --staged` on the resulting commit) that the committed hunk content corresponds to different lines than what was visually selected in step 2, because `formatPatch` (`app/src/lib/patch-formatter.ts`) indexed into the freshly-fetched diff using the old absolute indices from `file.selection`.
