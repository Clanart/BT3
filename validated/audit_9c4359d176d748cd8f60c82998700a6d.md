Based on my analysis, the strongest local analog to the Passage.sol premature-counter bug is in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`'s cross-chain cancellation flow.

### Title
Premature irreversible `_filled` finalization on destination before confirmed source-chain escrow release permanently locks user funds - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The external report's core defect is a state variable (`inCnt`/`outCnt`) being finalized as "complete" before the underlying operation (a full match) actually completed, with no way to reverse it, causing permanent lockup once other guarded functions rely on that finalized value. The same broken invariant — a durable "done" flag written before the corresponding fund-movement is confirmed, with no retry path — exists in `_cancelFromDest`.

### Finding Description
`_cancelFromDest` unconditionally writes the terminal state `_filled[commitment] = address(uint160(uint256(order.user)))` on the destination chain, then fires a one-shot `RefundEscrow` POST request to the source chain to actually release the escrow: [1](#0-0) 

This dispatch is created with `timeout: 0`: [2](#0-1) 

Every entry point that could retry or reconcile this order is blocked once `_filled[commitment]` is non-zero. `cancelOrder` unconditionally reverts if `_filled[commitment] != address(0)`: [3](#0-2) 

and `fillOrder` likewise reverts with `Filled()` for the same reason: [4](#0-3) 

The only path that actually releases the source-chain escrow is `onAccept` decoding a `RedeemEscrow`/`RefundEscrow` body and calling `_withdraw`: [5](#0-4) 

Because `timeout` is hard-coded to `0`, there is no ISMP-level timeout callback (`on_timeout`) that can ever fire for this request to trigger an alternate refund path — the system has exactly one shot at delivering the `RefundEscrow` message. If that single in-flight POST is never accepted on the source chain (dropped, expired relayer incentive, temporary congestion, or any non-delivery not requiring relayer malice), the source-chain `_orders[commitment][token]` escrow balances are never zeroed by `_withdraw`, yet the destination has already made `_filled[commitment]` permanent and irreversible. The user has no remaining call that can re-trigger the refund: `cancelOrder` on the destination re-enters `_cancelFromDest` short-circuiting is not possible since `_filled` is already set at the top-level guard, and the source-chain `_cancelFromSource` path (a GET-based verification) was never invoked and requires the user to initiate cancellation from the source before the destination cancel — a path that's now moot since the order is already "cancelled" on the destination.

### Impact Explanation
This is a direct, unrecoverable loss of user funds: the input tokens escrowed at `placeOrder` time on the source chain remain locked in the `IntentGatewayV2` contract's `_orders` mapping forever, with every reachable public function (`cancelOrder`, `fillOrder`) permanently gated shut by the destination's `_filled[commitment]` flag having already flipped. This mirrors the reported bug class exactly: a terminal accounting flag is committed before the operation it represents is actually complete end-to-end, and downstream guards that trust that flag then permanently block recovery.

### Likelihood Explanation
No malicious relayer, prover, or admin action is required — any legitimate, non-adversarial failure to deliver the single `RefundEscrow` POST (the only in-flight instance is `timeout: 0`, i.e., no automatic recovery window exists at all) results in the fund lock. This is reachable by any ordinary user simply calling `cancelOrder` from the destination chain of a normal cross-chain order.

### Recommendation
Do not write `_filled[commitment]` to a terminal, irreversible value in `_cancelFromDest` until the paired `RefundEscrow` message is confirmed delivered/executed on the source chain (e.g., use a distinct "cancel-pending" state, or only finalize `_filled` on the source chain in `_withdraw` upon receipt), and/or give the dispatched `RefundEscrow` request a real non-zero timeout with an `on_timeout` handler that reopens the ability to retry dispatch or reconciles state, so a single failed delivery cannot make the lock permanent.

### Proof of Concept
1. User places a cross-chain order via `placeOrder` on chain A, escrowing input tokens.
2. Order deadline passes without a solver filling it.
3. User calls `cancelOrder` from chain B (destination). This enters `_cancelFromDest`, which sets `_filled[commitment]` on chain B and dispatches a `RefundEscrow` POST to chain A with `timeout: 0`.
4. The dispatched message is never accepted on chain A (e.g., dropped by infrastructure, insufficient relayer fee, or any legitimate non-delivery condition) — there is no timeout callback to recover since `timeout == 0`.
5. User calls `cancelOrder` again (from either chain) or attempts `fillOrder` — both revert with `Filled()` because `_filled[commitment]` is already set on chain B.
6. Chain A's `_orders[commitment][token]` escrow balance remains non-zero indefinitely; no function exists that both bypasses the `Filled()` guard and can re-trigger delivery of the refund, permanently locking the user's escrowed tokens.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
