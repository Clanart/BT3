Based on my investigation, I've confirmed the exact analog to the reported bug class.

### Title
Relayer withdrawal and beneficiary-redirect signatures omit any Hyperbridge-instance domain separator, enabling cross-deployment replay of fee-claim signatures - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-ismp-relayer`'s `withdraw_fees` and the beneficiary-redirect path of `accumulate_fees` authenticate relayer-authored signatures with a payload that only binds `(nonce, dest_chain/state_machine, beneficiary?)` — never anything identifying *which* Hyperbridge chain deployment the signature is valid for. This is structurally the same flaw as the reported Forwarder bug: the signed digest lacks a domain separator component (a chain/instance identifier) tying it to one specific runtime, so a signature valid on one Hyperbridge deployment can be replayed verbatim on another deployment that runs the identical pallet and tracks the identical `StateMachine` id.

### Finding Description
`message()` in [1](#0-0)  computes the signed digest as `keccak256((nonce, dest_chain, beneficiary).encode())`. Likewise, `beneficiary_message()` in [2](#0-1)  computes `keccak256((nonce, state_machine, beneficiary).encode())`. Neither payload includes any value that is unique to the specific Hyperbridge runtime instance verifying it (e.g. a genesis hash, parachain/instance id, or other domain tag) — only a relayer-chosen `nonce` scoped per `(address, state_machine)` and the externally-tracked `StateMachine` identifier of the *destination/source chain being bridged to*, not of Hyperbridge itself.

`Pallet::withdraw` looks up the nonce purely from local storage — `Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain)` — and dispatches based on it: [3](#0-2) . Similarly, `accumulate_fees`'s beneficiary-redirect check reads `Nonce::<T>::get(&delivery_address, state_machine)` and verifies the signature against `beneficiary_message` before crediting the beneficiary: [4](#0-3) . Both call paths are reachable as unsigned extrinsics validated only by `validate_unsigned`, which tags calls purely by `claim.encode()`/`withdrawal_data.encode()` for txpool dedup — it performs no chain-identity check either: [5](#0-4) .

Because Polytope Labs operates multiple production/parallel Hyperbridge chain deployments (mainnet "Nexus" and various testnets such as Gargantua/Paseo) that run the exact same pallet code and track the exact same set of `StateMachine` ids (e.g. `StateMachine::Evm(1)`, `StateMachine::Evm(8453)`, etc. — confirmed by the shared chain registry in [6](#0-5) ), a relayer's signature broadcast publicly on-chain in one deployment (both `withdraw_fees` extrinsics and `accumulate_fees`'s `beneficiary_details` are fully visible on-chain) is trivially replayable by any observer on another deployment where that same `(address, state_machine)` pair happens to share the same nonce value — a state that is virtually guaranteed immediately after a new deployment launches (`Nonce` defaults to 0 everywhere).

This mirrors the reported bug precisely: the domain separator (there, EIP-712's chainId; here, any Hyperbridge-instance identifier) is absent from the signed payload, so a legitimately-produced signature is not bound to the chain it was intended for.

### Impact Explanation
An unprivileged observer who copies a publicly-broadcast `withdraw_fees` or `accumulate_fees` beneficiary-redirect signature from one Hyperbridge deployment can resubmit it verbatim to another Hyperbridge deployment (as an unsigned extrinsic, requiring no private key) as long as the `(address, state_machine, nonce)` triple lines up. For `accumulate_fees`, this redirects the relayer's freshly-accumulated fee on the replay-target chain to whatever `beneficiary_address` the attacker copied from the original signature — an unauthorized fund reroute that the relayer never authorized on that chain. For `withdraw_fees`, replaying triggers an unauthorized cross-chain withdrawal dispatch to whatever beneficiary was named in the original message, on a chain the relayer's signature was never intended for. Both are direct "unauthorized transaction / logic attack / fund redirection" outcomes matching the bounty's impact gate.

### Likelihood Explanation
Likelihood is moderate: it requires (a) multiple live Hyperbridge deployments sharing pallet code and `StateMachine` ids (confirmed architecturally), and (b) nonce coincidence for the targeted `(address, state_machine)` pair — most easily satisfied right after a new network launches, when nonces are still at or near zero, or opportunistically whenever nonces happen to realign. No relayer private key, prover, or governance action is needed; only publicly-visible on-chain data and an unsigned extrinsic submission.

### Recommendation
Include a Hyperbridge-instance-specific domain separator (e.g. the runtime's genesis hash, or a configured unique instance/chain identifier) as an additional field in both `message()` and `beneficiary_message()` before hashing, so a signature produced for one Hyperbridge deployment cannot verify against the payload construction of another deployment, analogous to including `chainId` in an EIP-712 domain separator.

### Proof of Concept
1. Deployment A (e.g. mainnet) and Deployment B (e.g. testnet) both run `pallet-ismp-relayer` and both track `StateMachine::Evm(8453)`.
2. Relayer address `R` has nonce `0` for `(R, Evm(8453))` on both deployments (true at genesis, or after nonce resets/new chain launches).
3. On Deployment A, `R` submits `accumulate_fees` with `beneficiary_details = Some((attacker_or_new_beneficiary, sig))` where `sig` signs `beneficiary_message(0, Evm(8453), beneficiary)` — this is broadcast and visible in the extrinsic.
4. An observer copies this exact `(beneficiary, sig)` pair and submits an `accumulate_fees` (or crafts an equivalent `withdraw_fees`) call to Deployment B for the same relayer `R`'s freshly-accumulated fee under `Evm(8453)`.
5. Because `beneficiary_message(0, Evm(8453), beneficiary)` is identical on both chains and `R`'s nonce is also `0` on Deployment B, `signature.verify(&msg, ...)` succeeds, crediting/redirecting `R`'s fee on Deployment B to the copied beneficiary without any authorization specific to Deployment B.
