### Title
Stale GitHub-repository refresh silently rewrites tracked repo's git remote to an attacker-controlled repository - (File: app/src/lib/stores/app-store.ts, app/src/lib/stores/updates/update-remote-url.ts, app/src/lib/stores/repositories-store.ts)

### Summary
GitHub Desktop periodically "refreshes" the `GitHubRepository` metadata for a tracked local repository by re-deriving `owner`/`name` from the repository's local git remote URL text and querying the GitHub API for whatever repository currently exists at that `owner/name`. The result is trusted unconditionally to update the persisted `cloneURL` and, in some cases, is used to actually rewrite the repository's `origin` remote URL on disk — all without ever verifying that the API repository returned is the *same* GitHub repository (by immutable ID) that was originally associated with the local clone.

### Finding Description
`repositoryWithRefreshedGitHubRepository` derives `owner`/`name` purely from parsing the local git remote's URL text via `matchGitHubRepository`, then calls `api.fetchRepository(owner, name)` and treats whatever comes back as authoritative for that local repository: [2](#0-1) 

The identifier used to look up/write into the local repositories database is `[ownerID+name]`, a pair of human-readable, mutable strings, with no cross-check against the previously known repository (e.g. GitHub's immutable numeric repo ID): [3](#0-2) [4](#0-3) [5](#0-4) 

This is the same broken-invariant class as the PoolManager bug: an attacker-influenced identifier (`owner/name`, analogous to `poolId/trancheId`) is used to overwrite existing persisted state (`cloneURL`/`htmlURL`, analogous to `pools[poolId].tranches[trancheId].token`) without checking that the identifier still legitimately belongs to the entity that was originally bound to it. The `GitHubRepository` model itself documents that its local `dbID` has "no relation to the API ID" [1](#0-0) , meaning there is no durable, unspoofable anchor tying a local record to a specific GitHub repository across renames/deletions/re-creations of the `owner/name` pair.

The consequence is not just metadata corruption: `updateRemoteUrl` uses the freshly fetched (unverified) `apiRepo.clone_url` to actually call `gitStore.setRemoteURL`, rewriting the on-disk git remote, whenever the protocol matches and the previously stored `cloneURL` still matches the current remote (i.e., the common/default case for any repo the user hasn't manually edited): [6](#0-5) 

Because GitHub allows a repository name to be freed up and reused by a different owner/repo after deletion or rename, an attacker who can get a namesake `owner/name` slot to exist on the API (e.g., after the legitimate repo is deleted, transferred, or renamed) can cause Desktop to silently:
1. Overwrite the persisted `GitHubRepository.cloneURL/htmlURL` for the victim's tracked repository with the attacker's repo's data.
2. Rewrite the victim's actual `origin` remote in `.git/config` to point at the attacker's repository via `setRemoteURL`.

No part of this path checks that the returned `apiRepo` corresponds to the same underlying repository that was previously associated with the local clone.

### Impact Explanation
Silent redirection of a tracked repository's remote to an attacker-controlled repository means subsequent `git push`/`git fetch`/`git pull` operations performed via Desktop's UI target the wrong destination without any user-visible warning — this is a "silent corruption of what the user commits or pushes" per the impact criteria. Depending on the credentials Desktop uses (its own token/keychain-backed auth), this can leak the victim's future commits (including potentially sensitive code) into an attacker's repository, or cause the user to unknowingly pull attacker-supplied history/refs into local branches perceived as the legitimate upstream.

### Likelihood Explanation
This requires the `owner/name` slot referenced by the local remote's URL text to end up pointing at a different, attacker-controlled repository on the GitHub API side (e.g., the original repository is deleted/renamed and the attacker claims the freed name, or the local remote was set from a link/deep-link/CLI action pointing at an owner/name the attacker can claim). Desktop performs this refresh automatically/periodically as part of normal repository housekeeping (`_refreshRepository`/`repositoryWithRefreshedGitHubRepository`), i.e., without any special user action beyond normal use of the app, and `updateRemoteUrl`'s guard conditions (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) are satisfied in the common case where the user hasn't manually edited their remote. Exploitation depends on external, non-local conditions (renaming/deleting/reusing a GitHub repo name), which is realistic but not fully within the attacker's control at all times, so likelihood is moderate rather than certain.

### Recommendation
Anchor `GitHubRepository` records to GitHub's immutable numeric repository ID (already present in `IAPIRepository`/`IAPIFullRepository` payloads) rather than the mutable `owner/name` pair, and verify that ID matches the previously stored one before overwriting `cloneURL`/`htmlURL` or calling `setRemoteURL`. If the ID differs from what was previously recorded, treat it as a new/different repository (e.g., flag as "repository moved/renamed" and require explicit user confirmation, similar to the existing `UpstreamAlreadyExists` confirmation flow) rather than silently overwriting state and rewriting the on-disk remote.

### Proof of Concept
1. Victim clones/adds `https://github.com/victim-org/project` in Desktop; Desktop persists a `GitHubRepository` row keyed by `[ownerID(victim-org)+name(project)]` with `cloneURL = https://github.com/victim-org/project.git`.
2. The `victim-org/project` repository is later deleted or renamed (e.g., organization ownership lapses, or repo is renamed away) — attacker registers/creates a new repository at the now-free `victim-org/project` slot (or an owner name reachable by the attacker, e.g. via org transfer/claim), or more directly, if a fork owner's account name changes, the same original `owner/name` slot could be claimed by someone else.
3. Victim's Desktop periodically calls `_refreshRepository` → `repositoryWithRefreshedGitHubRepository`, which re-parses the local `origin` remote text to get `owner=victim-org, name=project` and calls `api.fetchRepository('victim-org','project')`, receiving the attacker's new repository object: [7](#0-6) 
4. Since the previously stored `cloneURL` still textually matches the local remote and the protocol is unchanged, `updateRemoteUrl` calls `gitStore.setRemoteURL(...)`, rewriting the victim's `origin` remote to the attacker's `clone_url`: [8](#0-7) 
5. The victim's next push/fetch via Desktop silently goes to the attacker's repository, with no dialog or warning shown (unlike the existing `UpstreamAlreadyExists` dialog, which only covers a narrower fork-upstream mismatch case).

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
