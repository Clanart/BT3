## Title
`clone()` explicitly disables Git's built-in submodule `file://` protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling arbitrary local file read/exfiltration via a malicious recursive clone — (`File: app/src/lib/git/clone.ts`)

### Summary
Git introduced `GIT_CLONE_PROTECTION_ACTIVE` as part of the fix for CVE-2022-39253 to stop a recursive `git clone` from following submodule URLs that use the `file://` protocol (or other local-path forms) to read arbitrary files/directories from the victim's filesystem into the cloned working tree. GitHub Desktop's `clone()` function unconditionally sets this variable to `'false'`, which turns that protection back off for every clone Desktop performs, including `--recursive` clones of arbitrary/untrusted URLs the user types or opens via `x-github-client://openRepo/...` deep links. [1](#0-0) 

### Finding Description
`clone()` builds the Git invocation with `--recursive` and injects a custom environment that includes `GIT_CLONE_PROTECTION_ACTIVE: 'false'`: [1](#0-0) 

This is the exact mechanism Git added upstream to gate `protocol.file.allow` enforcement during a clone: while a `clone --recursive` is "active," Git refuses to fetch submodules whose recorded URL uses `file://` (or other locally-resolvable schemes) unless the user explicitly opts in. By forcing this flag to `'false'`, Desktop tells the embedded Git binary that no such protection window is in effect, so any submodule entries in the attacker's repository's `.gitmodules` that point at `file:///some/local/path` will be followed and "cloned" from the local filesystem into the working directory — copying files/directories from wherever the URL points (e.g. another local repo, `~/.ssh`, `~/.aws`, source trees of other projects on disk) into the freshly cloned repo.

Unlike `updateSubmodulesAfterOperation`, which only widens `protocol.file.allow` when a caller opts in via `allowFileProtocol` (used for legitimate, already-known-safe operations such as pulling a repo whose own submodules are already trusted/local test fixtures) [2](#0-1) , `clone()` has no equivalent gate — the override is unconditional and applies to first-time clones of untrusted, attacker-supplied URLs, which is precisely the scenario the upstream CVE fix was meant to protect.

This is reachable without any local/physical access: a victim can trigger it simply by cloning a malicious public repository URL (via the "Clone repository" dialog, a pasted URL, or the `x-github-client://openRepo/<url>` protocol handler that Desktop registers) [3](#0-2) [4](#0-3) . The repository's `.gitmodules` is fully attacker-controlled content that Desktop fetches and acts on automatically as part of `--recursive` cloning — exactly the "attacker controls a cloned/fetched repository" primitive called out as in-scope.

Note: the recently-added `isClonePathSensitive()` guard in the same file only blocks the *destination* directory of the top-level clone from landing in a sensitive location (e.g. `~/.ssh`) [5](#0-4) ; it does nothing to stop a submodule *source* URL from reading from a sensitive local path, since that check never inspects `.gitmodules` contents or intervenes in the recursive submodule fetch step. The two mechanisms operate on different axes (destination path vs. submodule source URL) so this existing guard does not mitigate the issue.

### Impact Explanation
A crafted repository can define a submodule with `url = file:///home/<user>/.ssh` (or any other locally-accessible path such as another cloned repo containing secrets, browser profile directories, etc.). When a victim clones that repository with Desktop (which always passes `--recursive` and disables clone protection), Git will copy the contents of that local path into the submodule's checkout directory inside the new repository's working tree. This exposes file contents outside the intended repository boundary directly into the user's working copy, where they can be viewed, and — because Desktop is a Git client oriented around committing and pushing — inadvertently staged, committed, and pushed to a remote the attacker or others can read, resulting in credential/secret exfiltration. This matches the in-scope impact of "file... read outside the repo" and "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Likelihood is high for any Desktop user who clones a link from an untrusted source (a common workflow: opening a "Clone in Desktop" link, or pasting a URL from an issue/PR/README). No special interaction beyond a normal clone is required, no admin rights, no pre-existing malware, and no credentials need to be leaked beforehand — the entire attack surface is the attacker-controlled `.gitmodules` file inside a repository the victim voluntarily clones. This exactly reverses a fix (CVE-2022-39253) that Git shipped specifically because this attack pattern was previously exploited in the wild against Git GUIs and CI systems that recursively clone untrusted repos.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override from `clone()` (or explicitly set it to `'true'`/leave it unset) so Git's native clone-time submodule protocol restrictions remain active for all first-time, potentially-untrusted clones. If recursive submodule fetching over `file://` is genuinely required for some internal/test flow, gate it the same way `updateSubmodulesAfterOperation` does via an explicit, narrowly-scoped `allowFileProtocol` parameter that defaults to `false` for user-initiated clones of arbitrary URLs.

### Proof of Concept
1. Attacker creates a public repository `evil/repo` containing a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
   (with a corresponding gitlink entry committed at `leak`).
2. Attacker shares the clone URL, or crafts a deep link `x-github-client://openRepo/https://github.com/evil/repo`.
3. Victim clicks the link or pastes the URL into GitHub Desktop's "Clone repository" dialog and clones it.
4. Desktop calls `clone()` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE=false` [1](#0-0) , so Git does not block the `file://` submodule URL and copies the contents of `/home/victim/.ssh` into `evil/repo/leak/` inside the victim's newly cloned working directory, where it is now visible in Desktop's file/history views and can be committed/pushed.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
