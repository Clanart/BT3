### Title
Unhandled `AssertionError` crash when parsing a malicious offer with a repeated coin - Denial of Service in `Offer.__post_init__` (`chia/wallet/trading/offer.py`)

### Summary
The CVE-2018-17096 bug class is a reachable, attacker-triggerable `assert()` in third-party input-parsing code (`BPMDetect`) that aborts the whole process when fed malformed input. The chia-blockchain analog is the bare `assert` in `Offer.__post_init__`, which runs whenever a wallet parses an offer (e.g. a counterparty-supplied offer file/bech32 blob). A spend bundle containing two `CoinSpend` entries for the identical `Coin` (same parent, puzzle hash, and amount) trips `assert cs.coin not in adds`, raising an uncaught `AssertionError` instead of a handled `ValidationError`/`ValueError`.

### Finding Description
`Offer.__post_init__` iterates over `self._bundle.coin_spends` and enforces the invariant "you can't spend the same coin twice in the same SpendBundle" using a bare `assert`: [1](#0-0) 

Everywhere else in this same method, malformed/adversarial input is turned into `ValueError`/`ValidationError` (e.g. duplicate requested payments, missing driver info, cost overflow), which callers such as `TradeManager` and the wallet RPC layer are prepared to catch and convert into a rejected-offer response. The coin-uniqueness check, however, uses a raw `assert cs.coin not in adds`, which raises a plain `AssertionError` that is not part of that expected error-handling surface.

Because `Offer` is a `frozen` dataclass, `__post_init__` runs unconditionally any time an `Offer` object is constructed — including when deserializing an untrusted offer received from a counterparty (via `Offer.from_bytes`/`from_bech32` style entry points used by `TradeManager`, `wallet_rpc_api.py`, and the CLI/RPC "get offer summary" / "take offer" code paths). A malicious counterparty can craft a `WalletSpendBundle` containing two identical `CoinSpend`s (same coin, differing only in `puzzle_reveal`/`solution`, or byte-for-byte identical) and package it as an "offer" to send to a victim wallet. Nothing in the SpendBundle serialization format prevents constructing such a bundle — this check is precisely what is supposed to reject it, but it does so by crashing rather than failing cleanly.

### Impact Explanation
An unhandled `AssertionError` thrown from offer parsing can propagate out of the offer-processing code path (offer summary retrieval, trade preview, or `take_offer`) as an unexpected exception. Depending on where it's caught (or not caught) in the RPC/task-processing layer, this can manifest as a crashed processing task, a failed RPC call that differs from the intended graceful-rejection behavior, or in the worst case an application-level halt of the transaction/offer-processing flow for that wallet — mirroring the "assertion failure and application exit" denial-of-service pattern from the CVE. This matches the accepted impact category of a "spend-triggered transaction-processing halt" reachable purely from a wallet user receiving/processing an offer supplied by an untrusted counterparty.

### Likelihood Explanation
Likelihood is high for any wallet user who opens/evaluates an offer file received from an untrusted third party (a normal, expected wallet workflow — offers are explicitly designed to be exchanged with counterparties before being accepted). Constructing a `SpendBundle` with a duplicated `CoinSpend` requires no special privilege, signature validity, or network access — it is a pure data-construction issue at the Python object level, before any CLVM execution or signature check even occurs.

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__` with an explicit, catchable error (e.g. `raise ValidationError(Err.DOUBLE_SPEND, "Bundle spends the same coin twice")` or `raise ValueError(...)`), consistent with how the rest of the method already reports malformed offer input, so that malicious/malformed offers are rejected gracefully rather than causing an unhandled `AssertionError`.

### Proof of Concept
```python
from chia.wallet.trading.offer import Offer, NotarizedPayment
from chia.wallet.wallet_spend_bundle import WalletSpendBundle
from chia_rs import G2Element
from chia.types.coin_spend import make_spend
from chia.types.blockchain_format.coin import Coin
from chia.types.blockchain_format.program import Program

coin = Coin(b"\x00" * 32, b"\x01" * 32, 100)
cs1 = make_spend(coin, Program.to(1), Program.to(1))
cs2 = make_spend(coin, Program.to(1), Program.to(2))  # same coin, different solution

bundle = WalletSpendBundle([cs1, cs2], G2Element())

# This raises an uncaught AssertionError instead of a handled ValidationError:
offer = Offer(requested_payments={}, _bundle=bundle, driver_dict={})
```
This is exactly the code path a victim wallet exercises when parsing an offer supplied by a counterparty, and it demonstrates the crash without needing the offer to be signed correctly or broadcast to the network.

Note: I was not able to fully trace every intermediate call site (`Offer.from_bech32`, `TradeManager.get_offer_summary`, `wallet_rpc_api.py` handlers) down to confirm whether any outer `try/except Exception` wrapper currently swallows this `AssertionError` before it reaches the user; that would only affect whether the practical symptom is a "silent failure" versus a full crash, not the underlying root-cause defect of using a bare `assert` for attacker-controlled input validation.
