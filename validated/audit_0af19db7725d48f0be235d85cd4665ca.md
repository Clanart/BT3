### Title
`ReceivedOutput::read` skips the script-to-offset binding check performed by `Scanner`, reporting unspendable/mismatched outputs as received - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The PrimeX bug class is a protective check (oracle tolerable-limit / slippage check) that is enforced on some execution paths but silently omitted on others, letting an attacker route around the invariant the check was supposed to maintain. In `bitcoin-serai`, the analogous check is the binding between a received output's `script_pubkey` and the scalar `offset` needed to spend it. That binding is established only inside `Scanner::scan_transaction`/`register_offset`, which populate `ReceivedOutput` exclusively for scripts proven to equal `p2tr(key + offset·G)`. The deserialization path, `ReceivedOutput::read`, accepts the `offset`, the `TxOut`, and the `OutPoint` as three independent, unauthenticated fields and never re-derives that `output.script_pubkey == p2tr_script_buf(scanner_key + offset·G)`. Any party that can supply serialized `ReceivedOutput` bytes can therefore cause funds to be reported as received-to-the-wallet that are not actually spendable with the claimed offset — the exact shape of "a check applied on the honest path, absent on the attacker-supplied path".

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping each known Taproot script to the offset that spends it (`networks/bitcoin/src/wallet/mod.rs:153-196`). `scan_transaction` only produces a `ReceivedOutput` after `self.scripts.get(&output.script_pubkey)` succeeds, guaranteeing the output pays to `p2tr(key + offset·G)` (`networks/bitcoin/src/wallet/mod.rs:199-214`).

`ReceivedOutput::read` (lines 122-134) decodes `offset` via `Secp256k1::read_F`, then `TxOut` and `OutPoint` via consensus decoding, and constructs `ReceivedOutput { offset, output, outpoint }` unconditionally. There is no check that `output.script_pubkey` corresponds to `offset`, that the outpoint references a real UTXO, or that the script is even P2TR. Downstream consumers use `offset()`/`output()`/`outpoint()`/`value()` directly to build spends (`wallet/send.rs`), so the deserialized object is treated with the same trust as one produced by scanning a confirmed block.

### Impact Explanation
An attacker who can feed serialized `ReceivedOutput`s to a wallet/processor instance can:
- Report deposits that were never received to a spendable script (offset/script mismatch), inflating accounted balance — funds reported received that are not spendable.
- Redirect change/detection logic: an output that *is* owned by the key but paired with a *wrong* offset causes the wallet to attempt signing with a key that doesn't correspond to the output, producing unbroadcastable/invalid spends or, worse, signing under the wrong tweaked key.
- Fabricate `OutPoint`s pointing at victim UTXOs, causing the wallet to construct transactions spending inputs it doesn't control (consensus-invalid, but burned fees on the real inputs it does include).

This mirrors the PrimeX issue directly: the safety property ("this output is spendable by key+offset") is enforced on the scanning path just as the oracle check was enforced on margin paths, but is absent on the deserialization path just as it was absent for swap/spot orders.

### Likelihood Explanation
Reachability depends on an integrator deserializing `ReceivedOutput` from bytes an unprivileged party controls — the prompt's threat model explicitly admits `ReceivedOutput::read` as an untrusted-byte sink (e.g., outputs relayed between scanner and signer components, or restored from untrusted storage). The `Scanner` does not retain its `key` in `ReceivedOutput`, so the struct cannot self-validate; the omission is structural, not a one-line oversight. Impact is bounded to accounting/consensus failure rather than key leakage, placing this at Medium.

### Recommendation
Either (a) bind the check by serializing/verifying `p2tr_script_buf(key + offset·G) == output.script_pubkey` at read time (requiring the scanner key to be supplied to `read`, e.g., `ReceivedOutput::read(reader, &key)`), or (b) keep `ReceivedOutput` construction private to `Scanner` and serialize a proof-free format only over authenticated channels, documenting that `read` input must be fully trusted. Option (a) restores the invariant on all paths, matching the PrimeX fix of applying the check unconditionally.

### Proof of Concept
```rust
// Construct a ReceivedOutput claiming ownership of an arbitrary mainnet UTXO
// with an offset that does NOT derive the output's script_pubkey.
let mut buf = Vec::new();
buf.extend(Scalar::ONE.to_bytes());              // arbitrary offset
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: ScriptBuf::new_p2tr_tweaked(
        TweakedPublicKey::dangerous_assume_tweaked(victim_xonly)),
}));                                            // script not = p2tr(key + 1*G)
buf.extend(serialize(&OutPoint::new(victim_txid, 0)));

let stolen = ReceivedOutput::read(&mut &buf[..]).unwrap(); // succeeds
assert_eq!(stolen.value(), 1_000_000);           // reported as wallet funds
// spending `stolen` with `stolen.offset()` produces a signature under the
// wrong tweaked key: output is unspendable by this wallet.
```

Uncertain: whether any in-repo component actually deserializes `ReceivedOutput` from network-controlled bytes (serialization plumbing is in `processor`-adjacent, out-of-scope code); the finding stands on the library API admitting the unchecked path.
