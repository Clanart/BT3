### Title
Aggregate-commit verification accepts duplicated validator identities, enabling forged quorum signatures - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs), [File: coordinator/tributary/src/tendermint/mod.rs](coordinator/tributary/src/tendermint/mod.rs))

### Summary
Serai’s Tendermint aggregate-signature verifier does not reject duplicated validator IDs. An attacker with one valid validator signature can construct an aggregate that mathematically verifies as though the same validator signed multiple times. Because commits carry an attacker-supplied `validators` list, this can inflate apparent signing weight and authenticate a block without the required quorum.

### Finding Description
`Commit` exposes `validators` as a public `Vec` and defines it as the list of validators participating in the signature, without requiring uniqueness in the interface. [1](#0-0) 

`Validators::verify_aggregate` only checks that the number of signer IDs equals the number of nonce points, computes one challenge per listed ID, and passes those pairs to `SchnorrAggregate::verify`. [2](#0-1)  Unlike single-signature verification, it does not first check that every listed ID is a validator or that IDs are unique. [3](#0-2) 

The underlying verifier binds each randomized weight to the ordered challenge list, but it does not bind or reject the signer IDs themselves. [4](#0-3)  Therefore, repeating the same `(key, challenge)` pair produces an equation over repeated copies of the same signature.

### Impact Explanation
For a valid Schnorr signature `(R, s)` under validator key `A` and challenge `c`, the relation is `sG = R + cA`. [5](#0-4) 

If the attacker lists `A` `k` times, `verify_aggregate` supplies `k` identical `(A, c)` pairs but derives distinct weights `z_i`. [6](#0-5)  The attacker can publish `R_i = R` and `s_agg = s * Σ z_i`; verification then computes `Σ z_i * (R + cA) - s_agg*G = 0`. [7](#0-6) 

If the surrounding consensus tally counts each entry in `commit.validators`, one real signature can be counted repeatedly toward BFT quorum. This is an authentication/forgery analog: an unauthenticated list element controls the claimed signing identity and multiplicity.

### Likelihood Explanation
The required inputs are a public commit containing a duplicated validator ID and an aggregate signature constructed from one valid signature for the same message. The verifier performs all steps needed for acceptance without checking uniqueness or validator membership. Exploitation depends on whether the Tendermint layer independently deduplicates `commit.validators` before weighting it; that deduplication is not enforced by the signature scheme or `Commit` API.

### Recommendation
Reject duplicate signer IDs in `Validators::verify_aggregate` and reject IDs absent from `self.weights` before cryptographic verification. `SchnorrAggregate::verify` should also document or enforce that `keys_and_challenges` must contain unique public keys for a given message context.

### Proof of Concept
Conceptually, for validator `A`, message `m`, and valid signature `(R, s)`:

1. Submit `commit.validators = [A, A, ..., A]` with `k` entries.
2. Deserialize `aggregate.Rs = [R, R, ..., R]`.
3. Let `z_i` be the verifier’s sequential `weight()` outputs for the repeated challenge.
4. Set `aggregate.s = s * (z_1 + ... + z_k)`.
5. Verification evaluates:
   `Σ_i z_i*R + Σ_i z_i*c*A - s*Σ_i z_i*G`
   `= (Σ_i z_i)*(R + cA - sG) = 0`.

No additional validator signatures or private keys are needed.
