### Title
Unauthenticated Access to `internal_handle_kickoff` via `Noop` Interceptor When `client_verification=false` — (`core/src/servers.rs`, `core/src/rpc/interceptors.rs`, `core/src/rpc/verifier.rs`)

### Summary

When `client_verification=false`, the gRPC server uses `Interceptors::Noop`, which passes every request through without any authentication. The `internal_handle_kickoff` RPC method is designed to be callable only by the verifier itself (enforced by `only_aggregator_and_self` when mTLS is active), but this protection is entirely absent in the `Noop` path. Any TCP client that can reach the verifier's port can invoke `internal_handle_kickoff` with any txid that already exists in the verifier's DB.

### Finding Description

**Authentication bypass path:**

In `core/src/servers.rs`, the interceptor selection is:

```rust
if config.client_verification {
    OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
} else {
    Noop
}
``` [1](#0-0) 

`Interceptors::Noop` unconditionally returns `Ok(req)` for every call: [2](#0-1) 

When `client_verification=true`, `only_aggregator_and_self` enforces that for any method whose name starts with `"Internal"`, only the verifier's own certificate is accepted: [3](#0-2) 

`internal_handle_kickoff` matches this `"Internal"` prefix check (via the `grpc-method` header injected by `AddMethodMiddlewareLayer`), so it is explicitly intended to be self-only. That guard is completely absent when `Noop` is active.

**What the method does:**

`internal_handle_kickoff` takes a `Txid`, looks it up in the DB via `get_deposit_data_with_kickoff_txid`, and if found, calls `handle_kickoff` with an **empty `Witness::new()`**: [4](#0-3) 

The txid must already exist in the verifier's DB (so fully forged txids are rejected with `not_found`), but any **known kickoff txid** — one that has been registered during the deposit/kickoff flow — can be replayed or triggered prematurely by an unauthenticated caller.

### Impact Explanation

- An attacker who can reach the verifier's TCP port (no certificate required) can replay any known kickoff txid, triggering `handle_kickoff` out of sequence or multiple times.
- `handle_kickoff` is called with `Witness::new()` (empty), which differs from the witness that would be present in a legitimate on-chain kickoff event. This can corrupt the challenge-flow DB state (kickoff handling record) and cause the verifier to submit watchtower challenges based on incorrect or stale state.
- Unauthorized watchtower challenge submission can disrupt the payout/challenge outcome, constituting an unauthorized state transition in the challenge flow with potential material bridge impact.

### Likelihood Explanation

`client_verification=false` appears in the testnet4 Docker config (`scripts/docker/configs/testnet4/bridge_config.toml`) and is a first-class config option. Any deployment — including production-like testnet deployments — that sets this flag is fully exposed. The attacker only needs network access to the verifier's gRPC port.

### Recommendation

1. **Never use `Noop` for production deployments.** Enforce `client_verification=true` for all non-test environments.
2. Add a secondary application-level guard inside `internal_handle_kickoff` (and all other `Internal*` methods) that rejects calls when the request does not originate from localhost or does not carry a valid self-signed token, independent of the TLS interceptor.
3. Consider removing `client_verification=false` from production config templates entirely, or at minimum emit a hard error (not just a `tracing::warn`) when it is set.

### Proof of Concept

Start a verifier with `client_verification=false`. Connect a plain gRPC client (no certificate) and call `internal_handle_kickoff` with a txid that was registered during a prior deposit flow. Assert the call succeeds (returns `Ok`) and that the DB kickoff-handling record has been mutated — confirming the authentication bypass and unauthorized state transition.

    async fn internal_handle_kickoff(
        &self,
        request: Request<clementine::Txid>,
    ) -> Result<Response<Empty>, Status> {
        let txid = request.into_inner();
        let txid = bitcoin::Txid::try_from(txid).map_err(|e| {
            Status::invalid_argument(format!("Failed to convert txid to bitcoin::Txid: {e}"))
        })?;
        tracing::warn!(
            "Called internal_handle_kickoff for kickoff txid: {:?}",
            txid
        );
        let mut dbtx = self.verifier.db.begin_transaction().await?;
        let kickoff_data = self
            .verifier
            .db
            .get_deposit_data_with_kickoff_txid(None, txid)
            .await?;
        if let Some((deposit_data, kickoff_id)) = kickoff_data {
            self.verifier
                .handle_kickoff(&mut dbtx, Witness::new(), deposit_data, kickoff_id, false)
                .await?;
        } else {
            return Err(Status::not_found("Kickoff txid not found"));
        }
        dbtx.commit()
            .await
            .wrap_err("Failed to commit transaction")
            .map_to_status()?;
        Ok(Response::new(Empty {}))
    }
