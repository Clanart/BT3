### Title
Unprivileged senders can inject fake "internal" outputs by paying publicly-derivable offset addresses, corrupting the processor's output accounting - (File: networks/bitcoin/src/wallet/mod.rs; processor/src/networks/bitcoin.rs)

### Summary
`BondNFT::_transfer` gated an otherwise-valid action on an unrelated staleness condition (`epoch == today`), letting external circumstances brick transfers. The Serai analog lives in the Bitcoin output scanner: the `Scanner` identifies received outputs **only** by `script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:205`), and the processor assigns each match a semantic `OutputType` (`External`, `Branch`, `Change`, `Forwarded`) derived from a fixed set of registered offsets (`processor/src/networks/bitcoin.rs:316-346`). Because the `Branch`/`Change`/`Forwarded` offsets are deterministically derived from a public domain separator (`b"Serai Bitcoin Output Offset"`, `processor/src/networks/bitcoin.rs:308`), any Bitcoin user can compute those internal addresses and send funds to them. The scanner cannot distinguish "a change output the protocol itself created" from "an arbitrary third-party payment to the same script," so externally-funded outputs are reported to the scheduler as protocol-internal outputs.

### Finding Description
- `Scanner::register_offset` maps offset scalars to tweaked P2TR scripts (`networks/bitcoin/src/wallet/mod.rs:180-196`).
- `Scanner::scan_transaction` reports any tx output whose `script_pubkey` is in that map, with no check that the output was created by the multisig (`networks/bitcoin/src/wallet/mod.rs:199-214`).
- The processor's `scanner()` helper registers `Branch`, `Change`, and `Forwarded` offsets via `hash_to_F(KEY_DST, …)` — a public, deterministic derivation (`processor/src/networks/bitcoin.rs:308-346`).
- `get_outputs` then tags every scanned output with `kinds[offset]` and pushes it as a received `Output` (`processor/src/networks/bitcoin.rs:686-700`); only `External` outputs get instruction data populated (lines 730-735).

An attacker who sends ≥ `N::DUST` satoshis to the derived `Forwarded`, `Branch`, or `Change` address causes the processor to emit an `Output` of that kind with empty `data` and attacker-controlled amount/origin — indistinguishable from a genuine internal output.

### Impact Explanation
Outputs typed `Forwarded`/`Change`/`Branch` are handled by the multisig scheduler as protocol-owned funds and internal bookkeeping, not as user deposits. An attacker-injected `Forwarded` output carries no `InInstruction`/`data`, so forwarding logic has no destination to forward to; a `Change`-kind output is treated as change the protocol "made," entering the UTXO set under the wrong classification. Depending on downstream handling, this yields scheduler stalls (a forward with no destination), mis-attributed balances, or the multisig spending attacker-funded inputs under sighash/commitment assumptions intended for self-created outputs — i.e., funds reported received that are not spendable as their assumed type, plus forced inclusion of attacker-chosen inputs into future transactions.

### Likelihood Explanation
The cost is one ordinary Bitcoin transaction paying a computable address. No privileged position, collusion, or invalid encodings are needed — the offsets are `hash_to_F` of a hardcoded public DST, and the resulting addresses can also be observed on-chain once the multisig produces its first change/forward outputs. `register_offset`'s parity increment (adding `Scalar::ONE` until the point is even) does not protect against this: the *resulting* script is what is matched, and it is fully public.

### Recommendation
Distinguish internally-created outputs from externally-received ones: e.g., commit to the set of outpoints the multisig itself produced (match `outpoint` against transactions the multisig signed/broadcast), or embed a per-output secret in internal offset derivation rather than a fixed `hash_to_F` DST. At minimum, `get_outputs` should not classify unsolicited payments to `Branch`/`Change`/`Forwarded` scripts as internal outputs without confirming they descend from a multisig-created transaction.

### Proof of Concept
1. Compute `offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")`, then increment until `key + offset·G` is even-parity (mirroring `register_offset`), and derive `p2tr_script_buf(key + offset·G)` — the multisig's `Forwarded` address.
2. Broadcast any valid Bitcoin transaction paying ≥ dust to that script.
3. `Scanner::scan_transaction` returns a `ReceivedOutput` with `offset` = the forwarded offset; `get_outputs` tags it `OutputType::Forwarded` with `data: vec![]` and attacker-set `presumed_origin` (from `tx.input[0]`), then emits it through the scanner's `ScannerEvent::Block` pipeline as a protocol output.

Caveat: I was unable to fully trace the `Forwarded`/`Change` consumption path in `processor/src/multisigs/scheduler/` within the available iterations, so the exact downstream failure mode (scheduler stall vs. mis-spend) is inferred rather than line-verified; the misclassification itself is confirmed at `processor/src/networks/bitcoin.rs:691-699`.
