### Title
Native ERC20 pointer bakes in immutable `decimals` at deploy time while the underlying tokenfactory denom's bank metadata `decimals` can be changed later, with no automatic re-sync - ([File: precompiles/pointer/pointer.go], [File: x/evm/keeper/pointer_upgrade.go], [File: x/tokenfactory/keeper/msg_server.go])

### Summary
This is the same bug class as the reported UXDController/RageOnDepository issue: a dependent contract permanently caches a decimals value taken from a "source of truth" at creation time, but the source of truth can later be changed by its owner/admin through a normal message, and nothing forces (or even notifies) the dependent contract to refresh. In sei-chain, the "source of truth" is the tokenfactory denom's bank `Metadata` (which contains the decimal exponent), and the "dependent contract" is the auto-deployed native ERC20 pointer contract whose `decimals()` is fixed forever at construction.

### Finding Description
When a native ERC20 pointer is created (via `pointer.addNativePointer` precompile call, `RegisterPointer` msg, or governance proposal), the precompile executor reads the denom's current bank `DenomMetaData`, extracts the decimal exponent, and passes it as an immutable constructor argument to the deployed pointer contract: [1](#0-0) 

That value is then baked into the pointer via `UpsertERCNativePointer`, which packs `metadata.Decimals` into the constructor arguments used to (re)deploy the pointer's bytecode: [2](#0-1) 

The deployed pointer (`NativeSeiTokensERC20`/`native` artifact) stores this as an immutable field returned by `decimals()`: [3](#0-2) 

Separately, the tokenfactory denom's admin can unilaterally change the bank `Metadata` for that same denom — including its `DenomUnits`/decimal exponent — at any time via `MsgSetDenomMetadata`, with no interaction with the EVM pointer registry: [4](#0-3) 

There is no hook from `SetDenomMetadata` (or any other bank-metadata mutation path) that triggers `UpsertERCNativePointer` to refresh an already-deployed pointer's cached `decimals`. The only way to bring the pointer back in sync is for someone to notice the drift and manually re-invoke the pointer precompile's `AddNativePointer`/`RegisterPointer` path so that `UpsertERCPointer` redeploys the pointer bytecode with the new decimals: [5](#0-4) 

Until that manual re-sync happens, `pointer.decimals()` silently reports a stale value that no longer matches the denom's canonical (and possibly newly-corrected or newly-set) decimal exponent — exactly the "lack of method to update the dependent contract's cached decimals when the source token's decimals changed" pattern from the reported UXD finding.

### Impact Explanation
Any EVM contract or off-chain integrator (DEX router, lending market, bridge, price oracle) that treats the native pointer as a standard ERC20 and calls `decimals()` to convert between human-readable amounts and raw token units will compute amounts using the stale exponent. Because tokenfactory decimal exponents commonly differ by many orders of magnitude (e.g. 0, 6, 18), a mismatch directly translates into orders-of-magnitude over- or under-valuation of transferred/swapped amounts — the same "severely over-value or under-valued" impact called out in the original report — which can be leveraged by a counterparty to drain funds from any protocol pricing the token via the pointer's `decimals()` while the admin (or a race between the admin's metadata update and callers) has updated the true decimal exponent.

### Likelihood Explanation
Changing a tokenfactory denom's metadata is a normal, unprivileged-relative-to-the-token-admin action reachable by a single `MsgSetDenomMetadata` transaction from the denom's own admin — no governance, no multi-party coordination, no node/validator compromise required. Any tokenfactory denom that already has a deployed native pointer (a common, encouraged integration path for CW/tokenfactory assets to be usable in the EVM ecosystem) is exposed the moment its admin updates metadata for any legitimate reason (correcting a mistake, rebranding, migrating decimals) without also remembering to re-register the pointer.

### Recommendation
Either (a) make the pointer's `decimals()` a live query against `GetDenomMetaData` at call time (mirroring how the CW20 pointer resolves `decimals()` via a live `WasmdPrecompile.query` rather than caching it), or (b) have `SetDenomMetadata` (and any other bank metadata mutation for a denom that already has a registered native pointer) automatically invoke `UpsertERCNativePointer` to redeploy/refresh the existing pointer's immutable metadata in the same transaction, so the pointer and the canonical bank metadata can never diverge.

### Proof of Concept
1. Create a tokenfactory denom `factory/{admin}/demo` and set its bank metadata with decimal exponent 6.
2. Call the pointer precompile's `addNativePointer(denom)` — this deploys a native ERC20 pointer whose `decimals()` returns `6`, per `AddNative`/`UpsertERCNativePointer`.
3. A DEX/lending protocol integrates the pointer, reading `decimals()` once (or repeatedly) to convert user-facing amounts to raw token units for swaps/collateral valuation.
4. The denom admin submits `MsgSetDenomMetadata` changing the same denom's decimal exponent to `18` (e.g., to correct an initial mistake) — this succeeds unconditionally per `SetDenomMetadata`'s admin check, with no interaction with the EVM keeper.
5. The pointer contract still returns `decimals() == 6` because that value is immutable in its deployed bytecode; no automatic re-sync occurs.
6. Any protocol still using the stale `decimals()` value computes conversions off by 10^12, causing it to systematically over/under-value the token, which an attacker can exploit for outsized withdrawals/swaps until someone manually re-invokes `AddNativePointer` to redeploy the pointer with the corrected decimals.

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
	if err != nil {
		return
	}
	ctx.GasMeter().ConsumeGas(k.GetCosmosGasLimitFromEVMGas(ctx, suppliedGas-remainingGas), "ERC pointer deployment")
	if err = setter(liveCtx(), pointee, contractAddr); err != nil {
		return
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypePointerRegistered, sdk.NewAttribute(types.AttributeKeyPointerType, typ),
		sdk.NewAttribute(types.AttributeKeyPointerAddress, contractAddr.Hex()), sdk.NewAttribute(types.AttributeKeyPointee, pointee)))
	return
}

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
