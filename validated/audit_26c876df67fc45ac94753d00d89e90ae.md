### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/vbyte estimate, so `needed_fee` underestimates the real fee — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `SafeCall.callWithMinGas()`, which asserted a minimum-resource bound with a formula that omitted additive costs (`CALL` base gas, EIP-2929 cold-access cost) so the callee received less than the guaranteed `_minGas`, `SignableTransaction::new` computes `needed_fee` from a weight estimate that omits the caller-supplied OP_RETURN data output. The constructed transaction is larger than estimated, so the actual fee rate (`fee / real_vsize`) is lower than the caller-specified `fee_per_vbyte` — potentially below the minimum relay fee — while `needed_fee()` and the `TooLowFee` check both attest the underestimated figure.

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` *before* computing the weight estimate, but calls `calculate_weight_vbytes` with `payments` rather than the final `tx_outs` list:

```rust
// networks/bitcoin/src/wallet/send.rs
193:    if let Some(data) = data {
194:      tx_outs.push(TxOut {
195:        value: Amount::ZERO,
196:        script_pubkey: ScriptBuf::new_op_return(...),
197:      })
198:    }
204:    let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds its template transaction's outputs solely from `payments` (plus the optional `change`), so the `data` output — up to ~9 + 2 + 80 ≈ 91 bytes, i.e. ~91 vbytes — is never counted:

```rust
85:    output: payments
86:      .iter()
89:      .map(|payment| TxOut { ... })
93:      .collect(),
95:    if let Some(change) = change { ... }
```

The same omission occurs in the change path (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at line 225-226). Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is short by `fee_per_vbyte * data_output_vbytes`.
- The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`, so a transaction whose *true* fee rate is below the relay minimum can pass the check.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 also uses the underestimated `weight`, so a transaction exceeding the standardness weight limit (400,000 WU) by up to the size of the data output will be produced instead of rejected.

This is exactly the SafeCall bug shape: a "guaranteed minimum" computed from a formula missing a dynamic additive term, where the shortfall scales with attacker/caller-controlled input (here, `data` length up to 80 bytes; there, cold-access and value-transfer costs).

### Impact Explanation
An unprivileged caller supplies `data` to `SignableTransaction::new`. The signed transaction pays `inputs - outputs`, which equals at least the *underestimated* `needed_fee`, but its real feerate is lower than the requested `fee_per_vbyte`. At boundary fee rates (e.g. `fee_per_vbyte` chosen to just satisfy min-relay), the broadcast transaction's effective feerate falls below Bitcoin Core's default minimum relay fee and it is dropped by the mempool — the threshold-signed transaction never confirms, freezing the spend until a new signing round can be produced (which FROST preprocesses cannot be reused for, per `cache()` being unimplemented). Additionally, at the top of the size range, an actually-nonstandard transaction (weight > 400,000 WU) is emitted despite the `TooLargeTransaction` guard. This is a funds-availability impact reachable purely from public inputs.

### Likelihood Explanation
Requires the caller to use the `data` parameter (admittedly optional; Serai's own processor passes `None`), and either a near-minimal fee rate or near-maximal transaction size. The underestimation is deterministic whenever `data` is present, scaling linearly with `data.len()`. Medium likelihood within the in-scope wallet API.

### Recommendation
Include the data output in the weight estimate — e.g. pass the fully built `tx_outs` (or a `data: Option<&ScriptBuf>` argument) into `calculate_weight_vbytes` for both the no-change and with-change estimates, so `needed_fee`, `TooLowFee`, `TooLargeTransaction`, and the change-amount calculation all account for the OP_RETURN output.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs context — conceptual test
let data = vec![0xff; 80];
let tx = SignableTransaction::new(
  vec![output], &payments, None, Some(data.clone()), fee_per_vbyte,
).unwrap();

// The real transaction contains an extra OP_RETURN output of ~91 vbytes
let real_vsize = /* vsize of tx.transaction() with witnesses */;
assert!(real_vsize > tx.needed_fee() / fee_per_vbyte);
// Therefore actual feerate < fee_per_vbyte:
assert!(tx.fee() / real_vsize < fee_per_vbyte);
// With fee_per_vbyte = 1 sat/vB and vsize ≈ needed_fee, the real feerate is
// ~ (vbytes)/(vbytes+91) of min relay — below DEFAULT_MIN_RELAY_TX_FEE,
// yet TooLowFee was not raised.
```

The same gap lets `weight` pass the `MAX_STANDARD_TX_WEIGHT` check while the real transaction exceeds it whenever the omitted data output pushes the weight over the boundary.
