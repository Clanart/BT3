### Title
`SignableTransaction` fee/change math omits the `OP_RETURN` output, yielding under-priced (potentially unbroadcastable) transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds the `OP_RETURN` data output to `tx_outs` *before* computing the transaction's weight/vbytes, but `calculate_weight_vbytes` is only ever passed `payments` — never `tx_outs`. The data output (up to ~91 serialized bytes for the 80-byte data limit) is therefore excluded from the size estimate used to derive `needed_fee`, the `TooLowFee`/`NotEnoughFunds` checks, and the change amount. Like the reference bug (paying out the wrong thing and leaving the intended asset locked), the change output here is computed against the wrong output set: the change receives the residual of an underestimated fee while the real transaction silently pays a lower effective fee rate than the `fee_per_vbyte` the caller specified.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed at lines 194–202, immediately before the vsize calculation at line 204:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62–127) builds its template transaction's `output` vector from `payments` plus the optional `change` — it has no parameter for the `OP_RETURN` output, so the data output is never counted. The same omission occurs for the change-path recomputation at lines 225–227:

```rust
let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

Consequences along the code path:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a vsize that is up to ~91 vbytes too small (8 bytes value + script overhead + up to 80 bytes data, counting at base weight).
2. The minimum-relay-fee gate at lines 211–213 uses the same underestimated `vbytes`, so it can pass a transaction whose true fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`.
3. The solvency check `input_sat < payment_sat + needed_fee` (line 215) and the change split `input_sat - (payment_sat + fee_with_change)` (line 228) both consume the underestimated fee.
4. When change is created (lines 228–233), the actual fee paid is exactly the underestimated `fee_with_change` — so the broadcast transaction's effective sat/vbyte is strictly lower than `fee_per_vbyte`, while `needed_fee()` (line 133) still reports the wrong value to the caller.

### Impact Explanation
Every transaction carrying `data` pays a fee rate below the caller-specified `fee_per_vbyte`. In the worst case — a caller deliberately requesting the minimum relay fee, which the code's own `TooLowFee` check purports to guarantee — the signed transaction falls under `DEFAULT_MIN_RELAY_TX_FEE`, cannot be relayed or confirmed, and the selected UTXOs are effectively locked until the transaction is rebuilt. Because `multisig`/`TransactionMachine` bind signatures via `Prevouts::All` and per-input `taproot_key_spend_signature_hash`, the mistake is baked into the signed transaction itself rather than recoverable by fee-bumping the witness.

### Likelihood Explanation
Any caller that supplies `data` (the documented mechanism for attaching `OutInstruction` payloads to Bitcoin outputs) and funds the transaction so that the residual lands exactly at the underestimated `needed_fee` produces an under-priced transaction. The underestimation is deterministic — it happens on every `SignableTransaction` with `data.is_some()` — only the severity (degraded rate vs. unbroadcastable) depends on how close the requested rate is to relay minimums.

### Recommendation
Pass the full output list (payments + `OP_RETURN` + optional change) into `calculate_weight_vbytes`, or compute the template transaction from the already-assembled `tx_outs`/`tx_ins` rather than from `payments`. The change-path recomputation at lines 225–227 must likewise include the data output so `fee_with_change` reflects the real serialized size.

### Proof of Concept
1. Call `SignableTransaction::new` with one input of value `payment + fee_per_vbyte * true_vbytes`, a single payment, a change script, `data = vec![0; 80]`, and `fee_per_vbyte` equal to the minimum relay rate.
2. `calculate_weight_vbytes` builds its template from `payments` only (line 204), so `vbytes` excludes the ~91-byte `OP_RETURN` output pushed at lines 194–202.
3. `needed_fee` and the `TooLowFee` check at lines 206–213 pass on the underestimated size.
4. The change output at line 230 is set to `input_sat - payment_sat - fee_with_change`, locking the *actual* fee to `fee_with_change`.
5. The resulting signed `Transaction` (`TransactionSignatureMachine::complete`, lines 413–428) contains all outputs including the `OP_RETURN`, so its real vsize is ~91 bytes larger than estimated — its effective fee rate is below `fee_per_vbyte`, and below `DEFAULT_MIN_RELAY_TX_FEE` when `fee_per_vbyte` was chosen at the minimum, rendering the transaction unrelayable and the inputs unspendable through it.
