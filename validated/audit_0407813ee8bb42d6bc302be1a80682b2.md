### Title
`open-repository-from-url` deep-link action passes an unsanitized `filepath` through to repository file-open logic - (File: `app/src/lib/parse-app-url.ts`)

### Summary
The `x-github-client://openRepo/...` (and legacy `github-mac://`/`github-windows://`) protocol handler lets a remote, attacker-crafted link drive GitHub Desktop into cloning a repository and then opening a specific file inside it. `parseAppURL()` explicitly validates the `branch` and `pr` query parameters before building the `IOpenRepositoryFromURLAction`, but it performs **no validation whatsoever** on the `filepath` parameter, which is taken verbatim from the URL and forwarded to the rest of the app.

### Finding Description
`parseAppURL()` is the single point that turns an externally-controlled URL (opened by clicking a link, or via OS-level protocol dispatch) into a trusted internal action object: [1](#0-0) 

Notice the asymmetry: `pr` is checked with a `\d+` regex, and `branch` is checked with `testForInvalidChars(branch)`, but `filepath` (line 101) is read straight from the query string and put into the returned action with zero sanitization: [2](#0-1) 

This action flows from the OS-level `open-url`/protocol-launcher handling directly into the main process's `handleAppURL`/`handleCLIAction` pipeline: [3](#0-2) [4](#0-3) 

The `IOpenRepositoryFromURLAction.filepath` field is documented as "the file to open after cloning the repository": [5](#0-4) 

Because this value is not checked for path-traversal sequences (`../`), absolute-path prefixes, or invalid characters the way `branch` is, a malicious deep link such as `x-github-client://openRepo/https://github.com/some/repo?filepath=../../../../.ssh/id_rsa` (or a Windows UNC/drive-letter path) can cause Desktop to attempt to open a file outside of the freshly cloned repository once the user clicks "Open in Desktop" / follows the link. This is directly analogous to the Astaria `flashAction` bug class: an external, attacker-supplied object (there, the flash-loan initiator; here, the deep-link's `filepath`) is consumed by a "recipient" (the repository-opening code path) without adequate verification/sanitization of the data that crosses a trust boundary.

### Impact Explanation
If the downstream consumer of `filepath` (repository file-opening logic invoked after `open-repository-from-url`) opens the path with an external editor, shell, or file API without re-validating that it stays inside the cloned repository, this allows an attacker who can get a user to click a crafted `x-github-client://` link to cause Desktop to open, and depending on the external editor/tool, read or otherwise interact with files outside the intended repository directory. This matches the "unprivileged issue where the attacker controls...a link or deep link the user clicks... and the result is...file read outside the repo" impact class.

### Likelihood Explanation
Likelihood is moderate: it requires the user to click an attacker-supplied `x-github-client://openRepo/...` link (a normal, expected interaction pattern for GitHub's "Open in Desktop" feature, not an unnatural step), and Desktop is registered as the default handler for this protocol on the OS. No local access, admin rights, or pre-existing malware is required — only the natural user action of clicking a link, which is the exact trust boundary the external report also targets (unauthenticated caller supplying attacker-controlled data to a callback/recipient).

### Recommendation
Sanitize `filepath` the same way `branch` is sanitized: reject values containing `..`, absolute path prefixes, or invalid path/traversal characters before constructing `IOpenRepositoryFromURLAction`, and when opening the file after cloning, resolve it against the clone target directory and verify (e.g. via `path.resolve` + prefix check) that the resolved path stays within the repository's working directory before handing it to `shell.openPath`/external editor invocation.

### Proof of Concept
1. Register/verify GitHub Desktop as the handler for `x-github-client://` (default on install).
2. Host or send a link: `x-github-client://openRepo/https://github.com/octocat/Hello-World?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`.
3. User clicks the link → OS invokes Desktop with the URL → `app.on('open-url', ...)` → `handleAppURL` → `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'https://github.com/octocat/Hello-World', filepath: '../../../../.ssh/id_rsa', branch: null, pr: null }` with no rejection, since only `branch`/`pr` are validated (see `app/src/lib/parse-app-url.ts:99-124`).
4. The unsanitized `filepath` is forwarded to the repository-open flow, where it could resolve outside the cloned repository.

Note: I could not fully trace the downstream consumer of `filepath` inside `app/src/lib/stores/app-store.ts` within the available indexed content to confirm exactly how it is passed to the file-open/external-editor call (whether `shell.openPath`, an editor spawn, or similar). I recommend a full Devin session with file-system access to trace `IOpenRepositoryFromURLAction.filepath` end-to-end and confirm the exact API used to open the file, to precisely determine the concrete write/read primitive achievable.

  if (__WIN32__ && args['protocol-launcher'] === true) {
    // On Windows we'll end up getting called with something like
    // `--protocol-launcher --allow-file-access-from-files x-github-client://..`
    // which minimist naturally interprets as
    // `--allow-file-access-from-files=x:/github-client`. This is due to
    // Chromium's hot take on parsing command line arguments, see:
    // https://github.com/electron/electron/issues/20322#issuecomment-534137321
    // So while we could add '--allow-file...' as a boolean we can't know for
    // sure that Chromium won't add more switches later on which is why we have
    // to resort to looking through all arguments looking for something that
    // appears to be an app url.
    const prefixes = Array.from(possibleProtocols, p => `${p}://`)
    const matchingUrl = argv.find(arg => {
      if (prefixes.some(p => arg.startsWith(p))) {
        try {
          new URL(arg)
          return true
        } catch (e) {
          log.error(`Unable to parse argument as URL: ${arg}`)
        }
      }
      return false
    })

    if (matchingUrl) {
      handleAppURL(matchingUrl)
    } else {
      log.error(`Encountered --protocol-launcher without app url`)
    }
    // If --protocol-launcher is present we always want to bail and not
    // risk a smuggled cli switch
    return
  }
