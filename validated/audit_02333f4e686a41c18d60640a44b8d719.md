### Title
Unbounded Python Recursion in Nested Outer-Puzzle Driver Matching Leads to Wallet Denial of Service - ([File: chia/wallet/outer_puzzles.py])

### Summary
`match_puzzle()` and the layer drivers it dispatches to (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`) recursively call back into `match_puzzle`/`get_inner_puzzle` once per curried puzzle "layer" with no depth limit. Because these drivers are invoked while parsing an untrusted offer file's `puzzle_reveal`s in `Offer.from_spend_bundle()` [1](#0-0) , a counterparty can hand a wallet user an offer containing a puzzle reveal with thousands of nested outer-puzzle layers (e.g. CAT-in-CAT-in-CAT…), driving Python's call stack past its recursion limit and crashing the process handling the offer — the same bug class (CWE-400/CWE-674, unbounded recursion from untrusted input) as the reported LlamaIndex `get_article_urls` issue.

### Finding Description
`match_puzzle()` iterates over `driver_lookup` and returns the first matching `PuzzleInfo`: [2](#0-1) 

Each concrete driver's `match()` method, on finding a match, unwraps one puzzle layer and recurses into the *inner* puzzle by calling `self._match(...)` again (`self._match` is bound to `match_puzzle` itself via `function_args`), with no depth counter or recursion guard:
- `CATOuterPuzzle.match()` recurses on the CAT's inner puzzle: [3](#0-2) 
- `SingletonOuterPuzzle.match()` / `get_inner_puzzle()` recurse the same way: [4](#0-3) 
- `MetadataOuterPuzzle` and `OwnershipOuterPuzzle` follow the identical recursive pattern: [5](#0-4) [6](#0-5) 
- `CROuterPuzzle.match()` also recurses: [7](#0-6) 

This chain of `match`/`get_inner_puzzle` calls is exercised whenever a wallet parses an offer's coin spends to build a summary or to reconstruct requested payments/driver dictionary, i.e. `Offer.from_spend_bundle()` calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` for every coin spend in an untrusted, attacker-supplied `WalletSpendBundle` (parsed from an offer file/bech32m blob a counterparty shares): [1](#0-0) 

A malicious counterparty can construct a `puzzle_reveal` consisting of thousands of nested recognized outer-puzzle layers (curried CAT/singleton/metadata/ownership/CR mod wrappers, one around the next). Since Chialisp `curry()` composition and CLVM tree construction have negligible per-layer cost/size overhead compared to Python's default recursion limit (~1000 frames), it is straightforward to build a puzzle reveal whose layer count exceeds the interpreter's recursion limit, well before hitting realistic mempool/CLVM cost limits (note this path — offer parsing/display — does not run the puzzle through the CLVM cost-metered interpreter at all before recursion occurs; the recursion happens purely in the Python-side layer-matching logic).

This mirrors the reported LlamaIndex vulnerability exactly: a recursive Python function (`get_article_urls`) walks attacker-influenced nested data with no `max_depth` enforcement, exhausting the recursion limit and crashing the process. Here, `match_puzzle`/`get_inner_puzzle` walk attacker-crafted nested puzzle layers with no depth bound.

### Impact Explanation
Any user who loads/inspects/accepts an offer file from an untrusted counterparty (a normal, expected wallet workflow) can trigger a `RecursionError` in the wallet process. Depending on where this is invoked (RPC handler for offer summary/take-offer, or CLI), this can crash or hang the wallet daemon/RPC worker, denying service to the wallet user for that session — a spend-triggered/offer-triggered transaction-processing halt, consistent with the requested "spend-triggered transaction-processing halt" acceptance criterion. This is High-severity in the sense that it is an unauthenticated, reliably reproducible remote DoS delivered via a routine wallet action (opening an offer), requiring no on-chain broadcast or fees from the attacker.

### Likelihood Explanation
Likelihood is high: constructing a puzzle reveal with many nested curried "outer puzzle" layers recognized by `match_puzzle` (CAT/singleton/metadata/ownership/CR) is inexpensive and does not require broadcasting a transaction or paying fees — the attacker only needs to send an offer file (a standard, off-chain artifact users routinely accept from untrusted counterparties) to the victim's wallet.

### Recommendation
- Add an explicit maximum recursion/layer-depth parameter to `match_puzzle`, `get_inner_puzzle`, and each driver's `match`/`get_inner_puzzle` implementation (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`), rejecting puzzles whose outer-layer nesting exceeds a sane bound (e.g. 20–50 layers) before recursing further.
- Alternatively, convert the layer-unwrapping loop in `match_puzzle`/driver chain to an iterative (stack-based) implementation, similar to the pattern already used for `sha256_treehash` in `chia/types/blockchain_format/tree_hash.py`, to avoid relying on the Python call stack entirely.
- Validate/limit puzzle-reveal structural depth as part of `Offer.from_spend_bundle()`/`Offer.from_bech32()` parsing before it is handed to `match_puzzle`, so malformed/adversarial offers are rejected early with a clean error rather than crashing the interpreter.

### Proof of Concept
Conceptually (exact PoC would need to be built and run in a Devin session to confirm the precise depth needed given the current Python recursion limit and any wrapping try/except in the RPC layer):
1. Build an `UnknownPuzzle` whose curried structure is `CAT_MOD.curry(..., CAT_MOD.curry(..., CAT_MOD.curry(..., ... N times ..., ACS)))` for N ≈ 2000–5000 (or interleave CAT/singleton/metadata/ownership layers, all of which are recognized by `driver_lookup`).
2. Embed this puzzle as the `puzzle_reveal` of a `CoinSpend` inside a `WalletSpendBundle`, and serialize it into an offer file via the standard offer-compression path (`chia/wallet/trading/offer.py`).
3. Have the victim wallet load this offer (e.g. via `chia wallet get_offer_summary` / `wallet_rpc_api` offer-inspection endpoint), which invokes `Offer.from_spend_bundle()` → `match_puzzle()` → recursive `_match` chain.
4. Observe a `RecursionError` propagating out of the deeply nested `match`/`get_inner_puzzle` calls, crashing or hanging the RPC call/wallet process.
