### Title
`cap_diff_for_prompt` truncates/omits diff files in unprioritized list order, allowing attacker-controlled file ordering/padding to drop the actually-vulnerable file from the security review prompt - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_investigate_prompt` calls `cap_diff_for_prompt`, which applies a per-file byte cap (`DIFF_PER_FILE_BYTES`) and a total byte cap (`DIFF_TOTAL_BYTES`) strictly in the order `diff_files` is passed in, with no risk-based prioritization. [1](#0-0)  The only risk-aware reordering in the pipeline, `_prioritize_diff_files`, is invoked exclusively when the *file count* exceeds `MAX_DIFF_FILES`; it never runs for the byte-budget path inside `cap_diff_for_prompt`/`_cap_files_for_prompt`. [2](#0-1)  An attacker who controls repository content (a committed/staged diff) can therefore pad or add a large, alphabetically-earlier, low-risk file so that the true vulnerable file — which appears later in `diff_files` — is truncated or fully omitted (`"[omitted by security-guidance: total diff byte cap reached]"`) before it ever reaches the review-model prompt.

### Finding Description
`build_investigate_prompt` builds the Stage-1 investigate prompt by calling `cap_diff_for_prompt(diff_files)`, which walks the list in order, applying: (1) a per-file cap (`DIFF_PER_FILE_BYTES`, default 80000 bytes) that truncates any single file's content, and (2) a running total cap (`DIFF_TOTAL_BYTES`, default 400000 bytes) that either truncates or completely replaces later files' content with an "omitted" placeholder once the total budget is exhausted. [3](#0-2)  Both truncation and omission happen purely based on position in the `diff_files` list — there is no sorting by risk, path signal, or added-line count inside this function.

The only place in the pipeline that reorders files by security relevance is `_prioritize_diff_files`, gated by `if len(diff_files) > cap` (i.e., only engaged when the number of *files* exceeds `MAX_DIFF_FILES`). [4](#0-3)  When the file count is under that cap — the common case for a small, targeted malicious commit — `diff_files` retains whatever order `parse_diff_into_files` produced from `git diff`/`git show` output (effectively path order), and `cap_diff_for_prompt`/`_cap_files_for_prompt` apply the byte caps against that unordered list. [5](#0-4) 

An attacker who can shape the diff content (e.g., a contributor's commit, or code an agent is instructed to write from repository-controlled content) can add or modify a large file with a path that sorts before the file containing the real vulnerability, and pad it with enough content to consume the `DIFF_TOTAL_BYTES` budget. The genuinely vulnerable file — appearing later in the list — is then either truncated away or replaced entirely with the "omitted" placeholder before `AGENTIC_INVESTIGATE_SYSTEM`/the reviewer model ever sees it. Because this happens purely mechanically in `cap_diff_for_prompt`, it is deterministic and repeatable, not merely a probabilistic LLM-judgment failure.

This is distinct from (and simpler/more reliable than) a pure prompt-injection attack against the reviewer model: the dangerous lines are never even included in the prompt, so no amount of model diligence, "distrust safety claims" instructions, or self-refute adversarial verification can catch it — those stages only operate on candidates that survive Stage 1, and Stage 1 never receives the omitted content in the first place.

### Impact Explanation
This breaks the invariant that truncation must not consistently drop the high-risk lines the user expects reviewed. Both the Stop hook (`handle_stop_hook`) and commit-review (`handle_commit_review_posttooluse`) pipelines rely on `analyze_code_security`/`agentic_review` findings to force Claude to continue and address issues (`sys.exit(2)`); if the vulnerable content never reaches the LLM, the review silently reports no vulnerabilities and the Stop/commit hooks exit cleanly. [6](#0-5)  This is a security-control bypass: dangerous changes committed alongside an oversized filler file silently skip the intended review/blocking gate, matching "security-control bypass that silently disables or routes around blocking, review, or permission boundaries."

### Likelihood Explanation
Feasible with only ordinary repository write access (a normal commit/PR) — no privilege escalation, no key leakage, and no reliance on tricking the LLM via crafted instructions. It requires knowing the byte caps (`DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES`, both configurable via env vars but with well-known defaults of 80000/400000 bytes) and producing a diff whose earlier-ordered files exceed that budget — a mechanical, deterministic condition rather than a probabilistic model-behavior exploit. It is reliably reproducible across repeated runs since it depends only on byte counting and list order, not model judgment.

### Recommendation
Apply the same risk-based prioritization (`_SECURITY_RISK_PATH_TOKENS`-style scoring, as already used in `_prioritize_diff_files`) inside `cap_diff_for_prompt`/`_cap_files_for_prompt` before applying the total-byte cap, so that byte-budget consumption always favors higher-risk files regardless of file count. Alternatively, allocate the total budget proportionally per file (e.g., a fair-share minimum per file before greedily filling remaining budget) instead of first-come-first-served, so no file can be fully starved by an earlier large one.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py::build_investigate_prompt` / `cap_diff_for_prompt`:

1. Construct `diff_files = [("aaa_filler.py", "X" * (DIFF_TOTAL_BYTES + 1000)), ("zzz_vuln.py", "+ os.system(user_input)")]` — filler file sorts first and alone exceeds `DIFF_TOTAL_BYTES`.
2. Call `cap_diff_for_prompt(diff_files)` and assert that `zzz_vuln.py`'s content in the returned list equals `"[omitted by security-guidance: total diff byte cap reached]"` (i.e., the dangerous `os.system(user_input)` line is absent).
3. Call `build_investigate_prompt(["aaa_filler.py","zzz_vuln.py"], diff_files)` and assert the resulting prompt string does NOT contain `"os.system(user_input)"`.
4. Repeat with the order reversed (`zzz_vuln.py` first) and assert the dangerous line IS present — demonstrating the outcome depends entirely on list order, not on actual risk, confirming truncation is not risk-aware.
5. Expected assertion failure on the current implementation: dangerous content is dropped in scenario (2)/(3) whenever it is not first in `diff_files`, proving the invariant "truncation must not consistently drop the high-risk lines" is violated.

```python
def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```

```python
def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,

        + "\n".join(f"  - {p}" for p in touched_paths[:50])

        + diff_text
        + extensibility.guidance_block()
```

```python
def _prioritize_diff_files(diff_files, cap):
    """When `diff_files` exceeds `cap`, return the top-`cap` by security
    relevance plus the count dropped. Otherwise return (diff_files, 0).

    Score = (risk_tokens_in_path, not_low_priority, added_lines). The
    added-lines proxy is `content.count('\\n+')` which counts diff additions
    cheaply without re-parsing hunks. This is a heuristic, not a guarantee —
    the goal is to review the likely-dangerous subset of an over-cap diff
    instead of reviewing nothing. Diffs that exceed the cap are typically
    large multi-file scaffolds, and the cross-file source→sink vulnerabilities
    in them concentrate in a handful of api/client/route files.
    """
    if len(diff_files) <= cap:
        return diff_files, 0

    def _score(item):
        fp, content = item
        low = fp.lower()
        # Prepend "/" so leading-slash patterns in _LOW_PRIORITY_PATH_TOKENS
        # match top-level dirs (git diff paths are repo-root-relative, e.g.
        # `migrations/001.py` not `/migrations/001.py`). Same trick as
        # _is_reviewable_source.
        low_slashed = "/" + low
        risk = sum(1 for t in _SECURITY_RISK_PATH_TOKENS if t in low)
        low_prio = (
            fp.endswith(_LOW_PRIORITY_SUFFIXES)
            or any(t in low_slashed for t in _LOW_PRIORITY_PATH_TOKENS)
        )
        # added_lines: count('\n+') over-counts by including '+++' header and
        # any literal '+' at line start in context, but it's a consistent
        # ordinal across files in the same diff which is all we need.
        added = content.count("\n+")
        return (risk, not low_prio, added)

    ranked = sorted(diff_files, key=_score, reverse=True)
    return ranked[:cap], len(diff_files) - cap
```

```python
def parse_diff_into_files(diff_output):
    """
    Parse unified diff output into a list of (file_path, diff_content) tuples.
    Only includes files with source code extensions.
    """
    if not diff_output or not diff_output.strip():
        return []

    files = []
    file_diffs = diff_output.split("diff --git ")

    for file_diff in file_diffs:
        if not file_diff.strip():
            continue

        # Extract filename from first line: "a/path/to/file b/path/to/file"
        lines = file_diff.split('\n')
        header_match = re.match(r'^a/(.+?) b/(.+)$', lines[0])
        if not header_match:
            continue

        file_path = header_match.group(2) or header_match.group(1) or ''

        # Filter to source code files only
        if not _is_reviewable_source(file_path):
            continue

        # Extract the diff content (from first @@ onwards)
        diff_lines = []
        in_hunks = False
        for line in lines[1:]:
            if line.startswith('@@'):
                in_hunks = True
            if in_hunks:
                diff_lines.append(line)

        if diff_lines:
            files.append((file_path, '\n'.join(diff_lines)))

    return files
```
