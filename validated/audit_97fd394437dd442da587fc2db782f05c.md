## Title
`X-Shopify-Shop-Domain` header used for shop attribution is not covered by the webhook HMAC signature, allowing cross-shop impersonation of webhook payloads - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` validates an inbound webhook solely by checking that `X-Shopify-Hmac-Sha256` matches an HMAC computed over `request.raw_post` [1](#0-0) [2](#0-1) . The module also exposes a `shop_domain` helper that simply reads the `X-Shopify-Shop-Domain` header [3](#0-2) . This header is never included in the HMAC digest, so it is not authenticated at all — exactly the same root cause as the referenced M-19 report, where the `sender` argument was used for downstream authorization but excluded from the signed message.

### Finding Description
The gem's own documentation instructs developers to use this pattern for custom webhook controllers:
```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end
end
``` [4](#0-3) 

`verify_request` only checks the HMAC over the raw body; it never checks that the `X-Shopify-Shop-Domain` header is consistent with, or tied to, that HMAC-signed body [5](#0-4) . Because `hmac_valid?` is a pure function of `secret` and `data` (the body) [2](#0-1) , any request with a previously-valid `(body, hmac)` pair will pass verification regardless of what value is placed in the `X-Shopify-Shop-Domain` header. An attacker who owns/controls their own shop (an unprivileged, unrelated merchant — no special privilege needed to install a public app or trigger a webhook-worthy event on their own store) can:

1. Trigger a legitimate webhook event on their own shop, capturing the raw body and its valid `X-Shopify-Hmac-Sha256` value (the shared secret is fixed per-app, not per-shop, so the same secret validates webhooks for every shop that installs the app).
2. Replay that exact `(body, hmac)` pair directly to the app's webhook endpoint via a forged HTTP POST, but with the `X-Shopify-Shop-Domain` header changed to any other shop domain (e.g., a victim/unrelated merchant's shop).
3. `verify_request` accepts the request because the HMAC still matches the (unchanged) body.
4. The consuming code (per the gem's documented pattern) attributes the webhook — and any job/side effects it triggers — to the attacker-chosen `shop_domain` rather than the shop that actually originated the event.

This is a forged/accepted signed request whose authenticated payload can be attributed to an arbitrary shop.

### Impact Explanation
Applications that follow the gem's documented pattern of using `shop_domain` (from the unauthenticated header) to route webhook data to shop-specific records, jobs, billing changes, or data mutations can have their per-shop data integrity broken by cross-shop payload/attribution confusion — data belonging to shop A can be recorded/acted upon as if it belonged to shop B, purely by re-sending a captured request with a swapped header, with no need to know any shop's session token or forge any additional signature.

### Likelihood Explanation
The attacker only needs to run a public app on any shop they control (a normal, unprivileged merchant capability) to obtain a valid `(body, hmac)` pair, then send one crafted HTTP POST to a known/public webhook endpoint URL. No collusion, no leaked secret, and no elevated access is required, though the header value affects only the metadata used to route/attribute the job, not the HMAC-protected payload contents itself, which limits impact to consumers that key business logic off the header value.

### Recommendation
Bind the shop identity into the authenticated payload instead of trusting the `X-Shopify-Shop-Domain` header on its own: verify the shop referenced in the header (or webhook body's own shop field, if present) against a shop that is expected to be receiving this webhook (e.g., cross-check against `params[:shop]`/webhook body content), or include the header value as part of the data over which the HMAC is computed, mirroring the ZetaChain fix of including the previously-unauthenticated field in the signed hash.

### Proof of Concept
1. Install a target app on shop `attacker.myshopify.com` and trigger a webhook event (e.g., `orders/create`).
2. Capture the raw POST body and its `X-Shopify-Hmac-Sha256` header value sent to the app's webhook endpoint.
3. Send a new POST request to the same endpoint with the identical body and HMAC header, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. Observe that `verify_request` returns success (HMAC only checks the body) [1](#0-0) , and any controller using the documented `shop_domain` pattern processes/attributes the payload to `victim-shop.myshopify.com` instead of the originating shop [6](#0-5) .

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
