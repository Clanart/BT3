### Title
SignableTransaction rejects valid payments below a hardcoded dust bound and enforces immutable relay-policy limits — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `ClearingHouse` baking `minInterest`/`maxInterest`/… into immutable constants, `SignableTransaction::new` hardcodes Bitcoin relay-policy values (`DUST = 546`, `DEFAULT_MIN_RELAY_TX_FEE`, `MAX_STANDARD_TX_WEIGHT`, the 80-byte `OP_RETURN` cap) with no way to parameterize them. Payments below 546 satoshis are unconditionally rejected with `DustPayment`, and fee-viable transactions failing the baked-in policy checks can never be constructed, even when the values are valid and spendable on the Bitcoin network.

### Finding Description
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` enforces several policy bounds compiled into the library:

```rust
// networks/bitcoin/src/wallet/send.rs:32
pub const DUST: u64 = 546;
```

```rust
// networks/bitcoin/src/wallet/send.rs:165-169
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

```rust
// networks/bitcoin/src/wallet/send.rs:171-173
if data.as_ref().map_or(0, Vec::len) > 80 {
  Err(TransactionError::TooMuchData)?;
}
```

```rust
// networks/bitcoin/src/wallet/send.rs:206-213
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

```rust
// networks/bitcoin/src/wallet/send.rs:241-243
if weight > u64::from(bitcoin::policy::MAX_STANDARD_TX_WEIGHT) {
  Err(TransactionError::TooLargeTransaction)?;
}
```

The caller (`fee_per_vbyte` is a parameter, but every threshold is fixed). These bounds are relay policy, not consensus, and the library itself acknowledges they may change ("Currently, these are … and may be raised", `processor/src/networks/bitcoin.rs:626-627`).

An unprivileged caller reaches these checks directly by supplying `payments`, `change`, `data`, and `fee_per_vbyte` to `SignableTransaction::new`. Any payment below `DUST` fails with `DustPayment` before any further processing, so the transaction — and the FROST signing machine derived from it via `multisig` — can never be produced for that payment.

The bound is wrong in both directions:
- Bitcoin's actual dust threshold depends on output type. For SegWit/Taproot spends it is ~294 sat (proportional to the input's spend weight), not 546, so payments in `[294, 546)` are valid and standard yet unconditionally rejected — the class's "bounds that made sense at one point" being applied globally.
- If relay policy raises the dust limit or min relay fee (as happened historically and is acknowledged in `processor/src/networks/bitcoin.rs:622-627`), the constants cannot be updated; transactions built to satisfy the new environment cannot be produced, and conversely payments ≥546 that are dust under the new policy are accepted and produce unrelayable transactions after FROST signing work is spent.

### Impact Explanation
Callers needing to move received `ReceivedOutput`s cannot construct a spend for any payment below 546 sat, permanently blocking small-value transfers/refunds regardless of on-chain validity. If Bitcoin Core's dust/min-relay parameters drift from the compiled constants (as has occurred and is anticipated by the code's own comments), `SignableTransaction` becomes unable to produce relayable transactions for legitimate payments — rendering the wallet functionality inoperable until a code redeploy, exactly the ClearingHouse failure mode, and also risks emitted transactions that are non-standard and stranded.

### Likelihood Explanation
Fully reachable by any unprivileged caller of `SignableTransaction::new` with public inputs (`payments`, `change`, `data`, `fee_per_vbyte`). Small payments are routine for refunds/change consolidation, and Bitcoin's dust/relay constants have changed across releases, so both the over-restrictive and under-restrictive failure modes are realistic.

### Recommendation
Make `DUST`, the minimum relay fee, the `OP_RETURN` data cap, and the max weight parameters of `SignableTransaction::new` (or of a configurable policy struct) rather than hardcoded constants, and compute the dust bound per output type (spend-weight-aware) instead of using a single 546 value.

### Proof of Concept
Call `SignableTransaction::new` with a single `ReceivedOutput` of, e.g., 10,000 sat and a payment `(p2tr_script, 400)` with `fee_per_vbyte = 10`. Even though 400 sat exceeds the ~294-sat dust limit for a Taproot output (standard and relayable under current Bitcoin Core policy), the function returns `Err(TransactionError::DustPayment)` at `networks/bitcoin/src/wallet/send.rs:165-169`, and no fee rate, change output, or other input can make the payment constructible — the bound is immutable and unoverridable.
