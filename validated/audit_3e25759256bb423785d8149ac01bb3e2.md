## Finding: IBC ERC20 auto-conversion failure returns an error acknowledgement after the underlying transfer has already been committed, causing double-crediting of escrowed value

### Title
Native-ERC20 IBC receive-conversion failure returns an error ACK after funds are already unescrowed/credited, causing duplicate value across chains - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
This is the same failure class as the ZetaChain M-26 report: a state mutation (asset release/mint) is committed to storage as part of one logical operation, but a *later* sub-step in the same call chain fails and the code treats that later failure as if the whole operation failed — triggering compensating logic (a refund on the counterparty) without undoing the already-committed mutation. In the ZetaChain case this was ZETA minted to the fungible module without being burned on `onReceive()` revert. Here, the analogous invariant break is in the `x/erc20` IBC middleware's `OnRecvPacket`.

### Finding Description
`IBCMiddleware.OnRecvPacket` in [1](#0-0)  first calls the underlying ICS-20 transfer application's `OnRecvPacket` (`im.Module.OnRecvPacket`). For a "native ERC20" token pair returning to its origin chain, this step unescrows the bank coin from the IBC escrow account and credits it to the recipient — a real, committed release of previously locked value. Only after that succeeds does it call `im.keeper.OnRecvPacket` to *additionally* auto-convert the bank coin into its ERC20 representation.

Inside `Keeper.OnRecvPacket`, case 2 ("native ERC20 token") in [2](#0-1)  calls `k.MintingEnabled` and `k.ConvertCoinNativeERC20`. If either fails (e.g., minting restricted, or the ERC20 contract reverts/self-destructed), the function returns `channeltypes.NewErrorAcknowledgement(err)` instead of the already-successful `ack`.

Both the mint/unescrow performed by `im.Module.OnRecvPacket` and the subsequent conversion attempt execute within the *same* Cosmos SDK message context — there is no separate commit boundary between them. Because a Cosmos SDK message handler commits all state changes as long as it returns a nil Go `error` (the acknowledgement value itself, success or failure, does not undo prior state mutations within the same execution), the bank-coin credit to the recipient from the first step is permanently committed regardless of what acknowledgement content is ultimately returned.

However, the acknowledgement **content** (success vs. error) is what is relayed back to the counterparty chain. If it is an `Acknowledgement_Error`, the counterparty's `OnAcknowledgementPacket` refunds the original sender there (standard ICS-20 semantics), i.e. it mints/unescrows the value back to the sender on the source chain.

This is inconsistent with the sibling functions `OnAcknowledgementPacket`/`OnTimeoutPacket` → `ConvertCoinToERC20FromPacket`, which correctly treat a failed `ConvertCoinNativeERC20` as non-fatal and `return nil` (success) after only emitting a telemetry event: [3](#0-2) . The doc comment on `OnRecvPacket` in `ibc_middleware.go` explicitly states the intended behavior: "If conversion fails, then the user will receive the bank token instead" [4](#0-3) , but the actual case-2 implementation in `ibc_callbacks.go` does not honor that — it downgrades a purely cosmetic conversion failure into a full packet failure.

### Impact Explanation
This breaks the IBC escrow 1:1 invariant (Asset-representation path invariant explicitly listed in the Smart Audit Pivots): the receiving chain has already released/credited the escrowed bank coin to the recipient (a legitimate, permanent state change), while the sending chain independently refunds/re-mints the same value to the original sender because it received an error acknowledgement. The net effect is duplication of spendable value across the two chains for every affected packet — a Critical unauthorized-duplication impact matching the Allowed Impact Gate ("Critical unauthorized minting, burning, duplication...of spendable user value across...IBC escrows"). Any unprivileged user who is also the recipient of a native-ERC20 IBC packet (or who controls conditions that make `ConvertCoinNativeERC20`/`MintingEnabled` fail, such as sending to a self-destructed/reverting ERC20 contract or a minting-restricted target) can trigger this deterministically and repeatedly.

### Likelihood Explanation
The trigger conditions are entirely attacker/user controlled and require no privileged access:
- The attacker (as recipient) can register or use a native-ERC20 token pair whose underlying contract can be made to revert on `transfer` (e.g., pausable/blacklist logic, or a self-destructed contract), which is exactly what `ConvertCoinNativeERC20`'s `CallEVM("transfer", ...)` in [5](#0-4)  depends on.
- Alternatively, `MintingEnabled` failing (e.g., minting disabled/paused for that pair) is also purely a function of chain state, reachable by ordinary users triggering ordinary IBC transfers back to the origin chain.
- No relayer/validator/governance collusion is required — a standard relayer simply relays the resulting error acknowledgement.

### Recommendation
In `Keeper.OnRecvPacket` (case 2, native ERC20), mirror the behavior already used in `ConvertCoinToERC20FromPacket`: on `MintingEnabled`/`ConvertCoinNativeERC20` failure, do **not** return an error acknowledgement. Instead, emit the failure event/telemetry and `return ack` (the original success acknowledgement from the underlying transfer), leaving the recipient with the bank-coin representation, consistent with the documented design intent ("the user will receive the bank token instead").

### Proof of Concept
1. Register a native ERC20 token pair on chain A whose ERC20 contract can be made to revert its `transfer` function for a chosen recipient (e.g., a pausable/blacklistable mock ERC20, or trigger `MintingEnabled` to fail for that pair).
2. From chain A, send `sendAmt` of the corresponding bank coin via IBC to chain B (escrowing `sendAmt` in the ICS-20 escrow account on chain A).
3. From chain B, send the voucher back to chain A, addressed to the attacker's recipient address.
4. On chain A, `im.Module.OnRecvPacket` unescrows `sendAmt` from the escrow account and credits it to the recipient (committed state change).
5. `Keeper.OnRecvPacket` then attempts `ConvertCoinNativeERC20`, which fails due to the malicious/paused ERC20 contract; the function returns `channeltypes.NewErrorAcknowledgement(err)`.
6. Chain B receives the error acknowledgement and refunds/re-mints `sendAmt` back to the original sender on chain B via its standard `OnAcknowledgementPacket` refund logic.
7. Result: the recipient on chain A holds `sendAmt` in bank-coin form (from step 4), and the sender on chain B has been refunded `sendAmt` (from step 6) — `sendAmt` of value now exists on both chains simultaneously, i.e., duplicated.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
