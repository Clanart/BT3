### Title
Data race between `BidPool.AddBid` writing `Bid.GasLimit` and concurrent block-building readers accessing the same published `*Bid` pointer without synchronization - (File: kaiax/auction/impl/bid_pool.go)

### Summary
The ksmbd CVE-2025-37899 bug class is a use of a shared object by one thread while another thread is still mutating/freeing it, because the object was made reachable to other readers before its lifecycle/state was finalized, and no reference counting/locking protects the field access. The Kaia analog is in `BidPool.AddBid`, which publishes a `*auction.Bid` object into the shared, mutex-protected maps (`bidMap`, `bidTargetMap`, `bidWinnerMap`) via `insertBid`, but only afterwards mutates a field on that same already-published object (`bid.SetGasLimit(gasLimit)`) **outside** of `bidMu`, allowing a concurrent reader (the block builder path, `AuctionModule.ExtractTxBundles` -> `BidPool.GetTargetTxMap`) to observe the `Bid` in an inconsistent, partially-initialized state.

### Finding Description
`BidPool.AddBid` in [1](#0-0)  performs:
1. `bp.validateBid(bid)` 
2. `bp.insertBid(bid)` — takes `bp.bidMu.Lock()` and stores the `bid` pointer into `bp.bidMap`, `bp.bidTargetMap[blockNumber][targetTxHash]`, and `bp.bidWinnerMap[blockNumber][sender]` (see [2](#0-1) ), then releases the lock.
3. **After** the lock is released and the bid is already reachable through the shared maps, `AddBid` calls `bp.getBidTxGasLimit(bid)` and `bid.SetGasLimit(gasLimit)` — mutating the same `*Bid` object with no lock held at all.

Meanwhile, `AuctionModule.ExtractTxBundles` (called concurrently by the block-building/mining goroutine on every block) reads bids for the target block via `BidPool.GetTargetTxMap`, which only copies the map of pointers under `bidMu.RLock` (see [3](#0-2) ) — it does **not** copy or lock the individual `Bid` object's fields. The returned `*auction.Bid` pointers are the exact same objects that `AddBid`'s calling goroutine may still be mutating via `SetGasLimit`. The builder then reads `bid` fields (including the just-written `GasLimit`) via `a.GetBidTxGenerator(tx, bid)` in [4](#0-3)  with no synchronization at all.

This is structurally the same class of defect as CVE-2025-37899: an object is made visible/reachable to other concurrent consumers through a shared, lock-protected index (analogous to ksmbd's session table) before it is fully initialized/finalized, and a field of that object continues to be written outside the lock that protects the index, so a concurrent reader can observe a torn/incomplete object — and in Go's memory model this is an unsynchronized data race with undefined visibility guarantees (the read side may see a stale zero-value `GasLimit`, not the just-computed one).

### Impact Explanation
If the block-building path (`ExtractTxBundles`) races with `AddBid`'s post-insertion `SetGasLimit` call, the bundle builder can read the bid's `GasLimit` field before it is set (zero value) or in a torn state. `GetBidTxGenerator` uses this gas limit to build the settlement transaction that executes the auction bid on-chain (value transfer/settlement to the auctioneer/searcher). An incorrect (zero or stale) gas limit used for the auction settlement transaction could cause the settlement transaction to run out of gas or execute with a limit that does not match what was validated for the bid, leading to acceptance of an inconsistent/invalid bid execution into the block, and potential state divergence between nodes that happen to observe the race differently (some nodes read the finalized `GasLimit`, others read the stale one), or a discrepancy between the bid actually bonded/signed by the searcher/auctioneer and the one settled on-chain.

### Likelihood Explanation
`AddBid` is reachable directly from a public entry point: `BidPool.HandleBid`, which any peer/unprivileged submitter of a bid can trigger, and it runs concurrently with the miner/block-builder goroutine that calls `ExtractTxBundles` once per block on the hot path. Because bid submission and block building happen continuously and concurrently on every running node with the auction module enabled, the race window (between `insertBid` publishing the bid and `SetGasLimit` completing) is hit routinely under load, not merely in a rare theoretical scenario.

### Recommendation
Move the gas-limit computation and `bid.SetGasLimit()` call to occur **before** `insertBid` publishes the `Bid` into the shared maps, or protect the `Bid.GasLimit` field itself with its own mutex/atomic and have all readers (`GetBidTxGenerator`, `ExtractTxBundles`) acquire it before use. Alternatively, treat `Bid` as immutable once published: compute the gas limit first, construct a fully-initialized `Bid` (or a copy), and only then call `insertBid`.

### Proof of Concept
1. Enable the auction module and register an auctioneer/entry point.
2. Have goroutine A repeatedly submit valid signed bids via `BidPool.HandleBid`/`AddBid` for the next block.
3. Have goroutine B repeatedly call `AuctionModule.ExtractTxBundles` for the same upcoming block number (simulating the miner's per-block bundle extraction, which happens continuously in a running node).
4. Run with `-race` (as already partially exercised by tests such as [5](#0-4)  `BenchmarkAddBidParallel`, which does not currently cross-check concurrent reads by `ExtractTxBundles`/`GetBidTxGenerator` against `SetGasLimit`) — the race detector flags the unsynchronized read/write of `Bid.GasLimit`, and functionally goroutine B can observe `GasLimit == 0` for a bid that goroutine A is still finalizing.

**Note on confidence**: I was not able to fully trace whether `GetBidTxGenerator`/`GetGasLimit` is invoked strictly on the miner's single goroutine (which could serialize with `AddBid` through some other implicit mechanism not visible in the reviewed files) or whether additional locking exists elsewhere in the mining pipeline that I did not locate via search. If a background Devin session is used to confirm this, it should trace all callers of `ExtractTxBundles` and `GetBidTxGenerator` to confirm there is no implicit serialization with `BidPool.AddBid`.

```go
	bp.bidMu.RLock()
	defer bp.bidMu.RUnlock()

	targetTxMap := make(map[common.Hash]*auction.Bid)

}
```

```go
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}
```

```go
func benchmarkAddBidParallel(b *testing.B, numBids int) {
	var (
		mockCtrl = gomock.NewController(b)
		chain    = chain_mock.NewMockBlockChain(mockCtrl)
	)
	defer mockCtrl.Finish()

	block := types.NewBlockWithHeader(&types.Header{Number: big.NewInt(1)})
	chain.EXPECT().CurrentBlock().Return(block).AnyTimes()

	pool := NewBidPool(testChainConfig, chain, &auction.AuctionConfig{MaxBidPoolSize: int64(numBids * 10)}) // Increase pool size for concurrent adds

	pool.auctioneer = testAuctioneer
	pool.auctionEntryPoint = testAuctionEntryPoint
	pool.auctionEntryPointVersion = auction.AuctionVersionV2

	// Start the auction
	pool.start()
	atomic.StoreUint32(&pool.running, 1)
	defer pool.stop()

	// Pre-generate bids
	bids := make([]*auction.Bid, numBids)
	for i := range numBids {
		searcherKey, _ := crypto.GenerateKey()
		tx := types.NewTransaction(uint64(i), testSearcher1, big.NewInt(10000000), 10000000, big.NewInt(10000000), []byte{})
		bid := &auction.Bid{BidData: auction.BidData{
			TargetTxHash: tx.Hash(),
			BlockNumber:  2,
			Sender:       crypto.PubkeyToAddress(searcherKey.PublicKey),
			To:           crypto.PubkeyToAddress(searcherKey.PublicKey),
			Nonce:        uint64(i),
			Bid:          big.NewInt(10),
			CallGasLimit: 100,
			Data:         common.Hex2Bytes("d09de08a"),
		}}

		// Generate searcher signature (EIP-712)
		digest := bid.GetHashTypedData(testChainConfig.ChainID, testAuctionEntryPoint, auction.AuctionVersionV2)
		sig, _ := crypto.Sign(digest, searcherKey)
		sig[crypto.RecoveryIDOffset] += 27
		bid.SearcherSig = sig

		// Generate auctioneer signature
		searcherSig := bid.SearcherSig
		msg := fmt.Appendf(nil, "\x19Ethereum Signed Message:\n%d%s", len(searcherSig), searcherSig)
		digest = crypto.Keccak256(msg)
		sig, _ = crypto.Sign(digest, testAuctioneerKey)
		sig[crypto.RecoveryIDOffset] += 27
		bid.AuctioneerSig = sig

		bids[i] = bid
	}

	b.ResetTimer()
	b.RunParallel(func(pb *testing.PB) {
		bidIndex := 0
		for pb.Next() {
			// Round-robin through bids
			bid := bids[bidIndex%numBids]
			pool.AddBid(bid)
			bidIndex++
		}
	})
```
