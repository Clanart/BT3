### Title
Unbounded recursive AccountKey decoding allows stack-overflow DoS via nested RoleBased keys - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
The WBXML CVE-2016-6513 root cause is an unbounded recursion depth during parsing of nested structures, leading to a crash. `AccountKeyRoleBased.DecodeRLP` in this repo performs the analogous unbounded, self-referential recursive decode: it decodes a `RoleBased` key as a list of RLP byte-blobs, and for each blob invokes a brand-new `rlp.DecodeBytes` call through `AccountKeySerializer.DecodeRLP`, which itself can resolve to another `AccountKeyTypeRoleBased` and repeat the process, with no depth counter anywhere in the call chain.

### Finding Description
`AccountKeyType` includes `AccountKeyTypeRoleBased` as a valid, constructible key type returned by `NewAccountKey` [1](#0-0) . `AccountKeySerializer.DecodeRLP` reads a `keyType`, constructs the corresponding `AccountKey` via `NewAccountKey`, and delegates decoding to that key's own `DecodeRLP`: [2](#0-1) .

`AccountKeyRoleBased.DecodeRLP` decodes its contents as `[][]byte`, then for **each** byte slice creates a brand-new `AccountKeySerializer` and calls `rlp.DecodeBytes` on it independently: [3](#0-2) . Because `rlp.DecodeBytes` re-enters the full decode pipeline (`Decode` β†’ `makeDecoder`/`decodeDecoder` β†’ `AccountKeySerializer.DecodeRLP` β†’ `AccountKeyRoleBased.DecodeRLP` β†’ ...), a `RoleBased` key that embeds another `RoleBased` key (embedding another, etc.) causes genuine Go-level function-call recursion, unbounded by any depth counter. This is architecturally different from ordinary RLP list nesting in this package, where `Stream.List`/`Stream.ListEnd` track nesting via an explicit `s.stack` slice rather than pure call-stack recursion [4](#0-3) ; the `AccountKeyRoleBased` custom decoder bypasses that bookkeeping entirely by spinning up independent `rlp.DecodeBytes` invocations.

The only guard against nested `RoleBased` keys, `IsCompositeType`/`CheckInstallable` (which rejects a `RoleBased` key that contains another composite key) [5](#0-4) , is applied only **after** decoding fully completes β€” it cannot prevent the recursive decode itself from exhausting the stack. This exact reject-after-decode pattern is explicitly exercised by `TestAccountUpdateRoleBasedKeyNested`, which confirms nested `RoleBased` keys are only rejected at the validation stage (`txpool.AddRemote`/block application), not at decode time [6](#0-5) .

### Impact Explanation
An attacker can craft an RLP-encoded `AccountKeyRoleBased` value that nests thousands of `RoleBased` keys inside one another and submit it as the `Key` field of a `TxTypeAccountUpdate` transaction via the public RPC (`eth_sendRawTransaction`)/`DecodeAccountKey` API [7](#0-6) , or embed it inside a fee-delegated account-update transaction decoded by `TxInternalDataAccountUpdate.DecodeRLP` [8](#0-7) . Decoding this transaction (which every node must do to reach the tx-pool admission or block-validation stage) triggers deep recursive `rlp.DecodeBytes` calls before any composite-type check runs, risking a goroutine stack-overflow fatal error and crashing the node process β€” a remote, unauthenticated denial-of-service, directly analogous to the WBXML dissector crash in the source CVE.

### Likelihood Explanation
Any unprivileged transaction sender or public-RPC caller can submit or decode arbitrary raw transaction bytes without needing a valid signature check up front, since RLP decoding happens before or independently of signature verification, and `DecodeAccountKey` is a publicly exposed RPC method with no depth restriction. Constructing sufficiently deep nesting only requires modest additional bytes per recursion level (a type byte plus a short list wrapper), so the overhead is small relative to typical transaction/RPC payload size limits, making a crash achievable with a reasonably sized payload.

### Recommendation
Add and enforce an explicit maximum nesting depth for `AccountKeyRoleBased` decoding (e.g., pass a depth counter through `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP` and reject decoding once a small limit, such as 1, is exceeded, since only one level of `RoleBased` is ever valid). This check should happen during decode, not only in the post-decode `CheckInstallable`/`IsCompositeType` validation, so a malicious payload cannot exhaust the stack before validation has a chance to run.

### Proof of Concept
Conceptually (cannot be executed in ask-only mode):
1. Build an `AccountKeyPublic` (or `AccountKeyNil`) leaf key and RLP-encode it via `AccountKeySerializer`.
2. Wrap it in an `AccountKeyRoleBased` containing that single serialized key, RLP-encode via `AccountKeySerializer` β†’ blob₁.
3. Repeat step 2 thousands of times, each iteration wrapping the previous blob in a new `AccountKeyRoleBased`/`AccountKeySerializer` encoding, producing blobβ‚™.
4. Submit blobβ‚™ as the `key` field of a `TxTypeAccountUpdate` transaction (or call `kaia_decodeAccountKey` with blobβ‚™ directly).
5. Observe that decoding recurses through `AccountKeySerializer.DecodeRLP` β†’ `AccountKeyRoleBased.DecodeRLP` β†’ `rlp.DecodeBytes` n times, consuming stack frames unboundedly and potentially crashing the node with a goroutine stack-overflow fatal error before `CheckInstallable`'s composite-type rejection is ever reached.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// List starts decoding an RLP list. If the input does not contain a
// list, the returned error will be ErrExpectedList. When the list's
// end has been reached, any Stream operation will return EOL.
func (s *Stream) List() (size uint64, err error) {
	kind, size, err := s.Kind()
	if err != nil {
		return 0, err
	}
	if kind != List {
		return 0, ErrExpectedList
	}

	// Remove size of inner list from outer list before pushing the new size
	// onto the stack. This ensures that the remaining outer list size will
	// be correct after the matching call to ListEnd.
	if inList, limit := s.listLimit(); inList {
		s.stack[len(s.stack)-1] = limit - size
	}
	s.stack = append(s.stack, size)
	s.kind = -1
	s.size = 0
	return size, nil
}
