## Analysis

The Inverse Finance bug is fundamentally a **stale-check-then-act / TOCTOU** flaw: a value (`deficit`) is captured, a partial action against it is allowed to happen out-of-band, and the subsequent "complete" action either fails or silently operates on a different underlying state than the caller believed. Reducing it to its primitive: *"an operation combines a previously-observed value/selection with a value that is re-read at execution time, and the two can diverge without any consistency check."*

GitHub Desktop has an exact structural analog in its **partial-commit staging pipeline**, where a line-based selection captured against one diff snapshot is blindly re-applied to a freshly re-fetched diff at staging time.

### Title
Stale line-selection indices are replayed against a freshly re-fetched diff during staging, silently corrupting partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user partially stages/commits a file (selecting only some diff lines), Desktop stores the selection as a set of **line-index offsets** (`DiffSelection`) computed against the diff that was rendered in the UI. At commit time, `applyPatchToIndex` re-fetches the diff **fresh from disk** and reuses the old index-based selection against the new hunk layout, with no validation that the two correspond to the same logical lines.

### Finding Description
The staging path is:
1. UI renders a diff and the user marks specific lines for inclusion via `DiffSelection` (`app/src/models/diff/diff-selection.ts`), which stores selected/deselected line numbers as *absolute indices into a specific diff's hunks* [1](#0-0) .
2. On commit, `_commitIncludedChanges` reads the working-directory file objects (with their `.selection`) straight out of state and hands them to `createCommit` [2](#0-1) .
3. `createCommit` → `stageFiles` → `applyPatchToIndex` **re-fetches the diff at staging time** via `getWorkingDirectoryDiff(repository, file)`, i.e. a brand new hunk layout is computed from whatever is currently on disk [3](#0-2) .
4. `formatPatch` then walks the **new** hunk lines and decides inclusion using `file.selection.isSelected(absoluteIndex)` [4](#0-3)  — but `absoluteIndex` values only have meaning relative to the diff that existed when the selection was made. If the file's line layout has shifted (lines added/removed above the selected region) between the moment the user made the selection and the moment `applyPatchToIndex` runs, the same numeric indices now point at **different lines**.

The codebase itself acknowledges this exact gap in a different code path (diff refresh for display), stating explicitly that stale selections are *not* validated against new hunk content: "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines" [5](#0-4) . Critically, this "best effort" reconciliation only runs opportunistically when the diff-loading pipeline pushes a refresh into `changesState`; it is **not** invoked as a pre-condition inside `applyPatchToIndex`/`stageFiles`/`createCommit`, so the staging path has no equivalent safety net at all.

### Impact Explanation
This causes **silent corruption of what the user commits**: the diff panel shows the user one set of additions/deletions, they select a subset of lines to include, but the bytes that actually get staged and committed (via `git apply --cached` in `applyPatchToIndex`) can correspond to a different region of the file than what was reviewed — with no error, warning, or diff re-confirmation. Because `git apply` operates purely on hunk context/line numbers, a shifted-but-still-context-matching hunk will apply "successfully," producing a wrong but plausible-looking commit that ships to the remote when pushed.

### Likelihood Explanation
The window is the time between rendering a diff/making a partial selection and the user clicking "Commit" — commonly several seconds while a commit message is typed. A malicious/cloned repository can arrange for tracked file content to change during this window through standard, no-extra-privilege developer tooling it ships (e.g., editor format-on-save configuration in `.vscode/settings.json`, an npm `prepare`/`postinstall` watcher, or a lint-staged/husky-style setup that rewrites files on save) — none of which requires local malware, admin rights, or leaked credentials, only that the victim opened/built the attacker-authored repository as normal. This is a `Market::forceReplenish`-style TOCTOU: the "amount" (line-selection) is trusted from an earlier snapshot instead of being reconciled with the live target (`min(deficit, amount)` in the original bug ⇔ "re-validate selection against current hunks" here).

### Recommendation
Before calling `applyPatchToIndex`/`stageFiles`, re-diff each file and verify that the previously selected line indices still map to equivalent content (or re-derive the patch from a diff snapshot taken atomically with the commit action, e.g. by diffing against a `git stash`/temporary index captured at "Commit" click time). At minimum, abort the commit for a file and surface an error/refresh prompt if the file's on-disk hash changed since the diff shown to the user was generated, rather than silently reapplying stale indices.

### Proof of Concept
1. Open a repository in Desktop and modify `file.md`, producing a diff with hunks `A` (lines 1–10) and `B` (lines 50–60).
2. Select only hunk `B` for inclusion (uncheck hunk `A`), leave the commit summary box open.
3. While Desktop is idle (no explicit "refresh diff" triggered), an external process (e.g., a formatter/watcher shipped with the repo) rewrites `file.md`, inserting 20 new lines before the original hunk `A`, shifting all downstream line numbers by 20 while keeping surrounding context text similar.
4. Click "Commit". `applyPatchToIndex` re-fetches the diff (now reflecting the shifted file) but reuses the old `DiffSelection` index set for "hunk B", which now falls inside what used to be a different region of the file.
5. `git apply --cached` succeeds (context lines still match locally), and the resulting commit contains different, unreviewed line ranges instead of the originally selected hunk `B` — with Desktop reporting a normal successful commit. [3](#0-2) [6](#0-5) [7](#0-6)
