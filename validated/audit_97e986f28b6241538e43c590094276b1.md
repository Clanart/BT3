## Title
`update_token` chain removal permanently blocks refunds for in-flight sends, freezing user escrow — ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet-hyper-fungible-token`'s `update_token` lets `CreateOrigin` remove a chain's contract mapping (`remove_chains`) at any time, with no check for outstanding cross-chain transfers still in flight to that chain. The removal deletes both `TokenContracts` and the `ContractToAsset` reverse mapping. `on_timeout`, the pallet's refund path for a timed-out `send`, resolves the local asset purely from `ContractToAsset::<T>::get(dest, &to)`. If that entry has been removed in the interim, the timeout handler unconditionally errors with `UnknownContractOnTimeout` instead of falling back to some other lookup, so the escrowed/burned funds behind that specific in-flight request can never be refunded. This mirrors the reported Morpho-Aave issue: a legitimate, narrowly-scoped configuration change (disabling an asset/chain) does not propagate to already-committed user positions, and those users are penalized (there: liquidated; here: funds permanently locked) purely as a side effect of the toggle, with no way to recover.

### Finding Description
- `send()` locks/burns the user's asset and dispatches a POST request to the destination chain's `TokenContracts[dest][asset_id]` address, with a caller-chosen `timeout` [1](#0-0) .
- `update_token`'s `remove_chains` branch deletes `TokenContracts` **and** `ContractToAsset` for `(chain, asset_id)` unconditionally, with no check for requests already dispatched to that chain that have not yet resolved: [2](#0-1) 
- `on_timeout`, the only refund path for a send that never gets accepted by the destination, resolves the asset solely from the reverse map: `ContractToAsset::<T>::get(dest, &to).ok_or(HftError::UnknownContractOnTimeout)?`. There is no alternate lookup and no way to identify the asset once this mapping is gone. [3](#0-2) 
- The error `UnknownContractOnTimeout` is a hard failure of the ISMP module callback — it is not a case that can be retried successfully later, because the very storage the refund depends on has already been deleted by governance.

Sequence:
1. Alice calls `send()` to `StateMachine::Evm(X)`, escrowing/burning her tokens, with a non-trivial timeout window (e.g. minutes to hours).
2. Before her request is delivered or times out, `CreateOrigin` calls `update_token` with `remove_chains: [Evm(X)]` — a routine, benign operation (e.g., decommissioning a stale/misconfigured EVM deployment, migrating to a new contract address), exactly the kind of adjustment the Morpho-Aave report flags as unsafe when it doesn't account for already-committed positions.
3. The relayer never delivers the request (or it genuinely times out because Evm(X) is being decommissioned), and the timeout message is submitted to Hyperbridge.
4. `on_timeout` is invoked; `ContractToAsset::<T>::get(Evm(X), &to)` returns `None` because the entry was deleted in step 2.
5. The module returns `Err(HftError::UnknownContractOnTimeout)`. Alice's escrowed/burned funds are never refunded — the pallet retains custody indefinitely with no other path to release them.

This is not a case of a malicious actor: like the original report, the harmful interaction arises purely from a legitimate configuration update interacting with pre-existing user state that the update path does not account for.

### Impact Explanation
Direct, permanent loss of user funds under the "Hyperbridge Impact Gate" criteria (loss of funds / broken settlement guarantee), triggered by an ordinary governance operation rather than any adversarial behavior, relayer misbehavior, or malformed proof. Any user with a `send()` in flight at the moment a chain is deregistered loses access to their escrowed/burned balance with no recovery mechanism in the pallet.

### Likelihood Explanation
Chain/contract migrations and decommissions are an expected, routine operational event for a multi-chain bridge (the pallet's own `add_chains`/`remove_chains` split exists specifically to support re-pointing or dropping contracts). Any in-flight `send()` at that moment — which is entirely plausible given timeout windows are user-configurable and can be long — is silently and permanently broken. No special conditions or malicious actors are required; only ordinary timing overlap between a governance update and a normal user transaction.

### Recommendation
- Do not delete `ContractToAsset` (or at minimum, retain a tombstoned mapping) when a chain is removed from `TokenContracts`; keep it available for `on_timeout` refund resolution independent of whether the chain is still an active send destination.
- Alternatively, have `on_timeout` resolve the asset from data embedded in the original dispatched request/commitment (e.g., record `asset_id` at dispatch time) rather than depending on a mutable, admin-controlled reverse-lookup table that can be deleted after the fact.
- Add a safety check to `update_token`'s `remove_chains` path that either blocks removal while pending requests to that chain exist, or provides a dedicated drain/settlement flow before removing the mapping, mirroring the Morpho-Aave recommendation to reconsider whether such a toggle should be permitted once positions/commitments already depend on the old configuration.

### Proof of Concept
Rust-level reproduction against `pallet-hyper-fungible-token`'s test harness (mirrors existing tests `should_timeout_request_correctly` and `should_register_and_update_token`):
```rust
// 1. Register token with chain Evm(1) contract C.
HyperFungibleToken::register_token(origin, TokenRegistration {
    local_id: asset_id, native: false,
    chains: [(StateMachine::Evm(1), ChainConfig { token_contract: C, decimals: 18 })].into(),
}).unwrap();

// 2. Alice sends tokens to Evm(1); tokens escrowed/burned, dispatch commitment recorded.
HyperFungibleToken::send(RuntimeOrigin::signed(ALICE), SendParams {
    asset_id, destination: StateMachine::Evm(1), recipient: BOB, timeout: 1000, amount: SEND_AMOUNT, ..
}).unwrap();

// 3. Governance removes Evm(1) before the request is delivered or timed out.
HyperFungibleToken::update_token(origin, TokenUpdate {
    asset_id, add_chains: Default::default(), remove_chains: vec![StateMachine::Evm(1)],
}).unwrap();
// ContractToAsset::<Test>::get(StateMachine::Evm(1), C) is now None.

// 4. Timeout message for Alice's original request arrives.
let module = HyperFungibleToken::default();
let result = module.on_timeout(Request::Post(PostRequest {
    dest: StateMachine::Evm(1), to: C, body: <original message>, ..
}));

// Expected (bug): Err(HftError::UnknownContractOnTimeout)
// Alice's escrowed/burned SEND_AMOUNT is never returned to her — funds are permanently stuck.
assert!(result.is_err());
```
This directly extends the existing `should_timeout_request_correctly` and `should_register_and_update_token` tests in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs` — running the update between the send and the timeout demonstrates the stuck-fund condition.
