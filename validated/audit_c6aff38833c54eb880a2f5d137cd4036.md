### Title
Quadratic CPU exhaustion via attacker-controlled `n`/`t` in `ThresholdKeys::read` → `ThresholdKeys::new` Lagrange group-key interpolation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from the input stream, then calls `ThresholdKeys::new`, which computes `group_key` by evaluating `interpolation_factor` once per participant `1..=t`. Under `Interpolation::Lagrange`, each `interpolation_factor` call iterates over the full `included` set of length `t`, making group-key derivation O(t²) in field multiplications plus O(t) scalar–point multiplications, while the input itself is only O(n) bytes. A reader who feeds untrusted bytes to `ThresholdKeys::read` can be forced into billions of field operations from a few megabytes of input — the same asymmetric resource-consumption class as GHSA-jj6m-r8jc-2gp7 (improper limits on a per-request resource).

### Finding Description
In `ThresholdKeys::read`, `t` and `n` are read as attacker-controlled `u16`s with no size limit beyond `t <= n <= 65535` enforced later by `ThresholdParams::new` [1](#0-0) . `ThresholdKeys::new` then derives the group key as a sum over `1..=t` of `verification_shares[i] * interpolation_factor(i, &t)` [2](#0-1) . For `Interpolation::Lagrange` (byte `1`), `interpolation_factor` runs a loop over all `t` included participants performing one field multiply each for the numerator and denominator [3](#0-2) . This yields O(t²) field multiplications (~4.3·10⁹ at t = 65535) plus 65535 scalar–point multiplications, all triggered by a serialized input of only ~n·(F_len + G_len) ≈ 4 MB.

### Impact Explanation
An unprivileged party who can cause a node/processor to deserialize `ThresholdKeys` bytes they control (the report's accepted surface includes `ThresholdKeys::read`) can pin a CPU core for an extended period per message. Repeated submissions amplify into denial of service of the signing/DKG path — analogous to the Wings advisory where missing limits let a low-privilege user exhaust shared hardware resources. No secrets are needed; the input is entirely public bytes.

### Likelihood Explanation
The byte stream is fully attacker-controlled: two `u16`s set `t = n = 65535`, one byte selects Lagrange, and the remainder is `n` field elements and `n` group elements that need not even be valid keys — the O(t²) interpolation happens inside `ThresholdKeys::new` before any semantic key check beyond share count/index bounds [4](#0-3) . Points must decode (each `read_G` must succeed), but validity is the only requirement — identity or generator points suffice.

### Recommendation
Cap `n`/`t` at a sane maximum (e.g., the protocol's actual validator-set bound, far below `u16::MAX`) inside `ThresholdKeys::read`/`ThresholdParams::new`, or precompute Lagrange denominators/numerators in O(t) total via prefix/suffix products so group-key derivation is O(t) field ops. Reject deserialization inputs whose declared `n` exceeds the configured participant limit before allocating or interpolating.

### Proof of Concept
Construct a serialized `ThresholdKeys` blob for any in-scope `Ciphersuite` `C`:
- `u32` LE `C::ID.len()`, then `C::ID` bytes
- `t = 65535` (`u16` LE), `n = 65535`, `i = 1` (`u16` LE, valid `Participant`)
- interpolation byte `0x01` (Lagrange)
- secret share: `C::F::ONE.to_repr()`
- 65535 × `C::generator().to_bytes()` as verification shares

Feed it to `ThresholdKeys::<C>::read`. `ThresholdParams::new` accepts (`t <= n`, `i <= n`), and `ThresholdKeys::new` then performs ~65535² ≈ 4.3·10⁹ field multiplications in `interpolation_factor` plus 65535 scalar–point multiplications — billions of cycles — for ~4 MB of input (at 32-byte F and 32-byte G encodings), a ~10³–10⁴× CPU-per-byte amplification reachable by an unprivileged sender.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
