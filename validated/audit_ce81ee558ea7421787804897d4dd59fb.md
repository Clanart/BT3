### Title
Missing minimum boundary check on `EndTime` in `MsgCreateVestingAccount` allows creation of already-vested (unlocked) vesting accounts - ([File: sei-cosmos/x/auth/vesting/msg_server.go])

### Summary
`MsgCreateVestingAccount.ValidateBasic` only checks that `EndTime > 0`, and the message handler `msgServer.CreateVestingAccount` never compares `EndTime` against `ctx.BlockTime()`. A sender can submit an `EndTime` that is already in the past (or equal to the current block time), producing a vesting account whose coins are treated as fully vested/unlocked immediately.

### Finding Description
`MsgCreateVestingAccount.ValidateBasic` in [1](#0-0)  validates addresses and coin amounts but only requires `msg.EndTime <= 0` to fail — it never checks `EndTime` relative to current time.

In `CreateVestingAccount`, the handler builds a `BaseVestingAccount` with the caller-supplied `EndTime` and, for continuous vesting, sets `StartTime = ctx.BlockTime().Unix()` [2](#0-1) . There is no assertion that `EndTime > StartTime` (i.e. `EndTime > ctx.BlockTime().Unix()`).

The vesting math treats a `blockTime >= EndTime` as fully vested: `ContinuousVestingAccount.GetVestedCoins` returns the entire `OriginalVesting` once `t >= cva.EndTime` [3](#0-2) , and the account's own `Validate()` only enforces `StartTime < EndTime`, not that either is in the future [4](#0-3) . Consequently, if `EndTime <= ctx.BlockTime().Unix()`, the newly created vesting account is fully vested (unlocked) the instant it's created.

This differs from genesis-time vesting account creation (`add-genesis-account`), which is operator/CLI-only and out of scope; `MsgCreateVestingAccount` is a normal signed transaction any account can submit (to send vesting funds to any recipient address), making it reachable exactly as in the reported Solidity analog (`VestingEscrowFactory.deployVestingContract`).

Note: this message path is gated by `creationDeprecated` — it is rejected everywhere except on `pacific-1`, `atlantic-2`, and `arctic-1` while below the height of the `v6.7` deprecation upgrade [5](#0-4) . On networks/heights where the gate is active, this path is not reachable, but pre-upgrade replay of historical chain state on those three networks is affected, and the vulnerability is real wherever the gate is not yet active.

### Impact Explanation
An attacker (any transaction sender acting as the "vesting grantor") can create a `MsgCreateVestingAccount` with `EndTime` set to a timestamp in the past. The recipient account is immediately treated by `LockedCoins`/`GetVestedCoins` as fully vested, meaning the "locked" framing of the transfer is a no-op — the funds are spendable right away, and any downstream logic relying on the vesting lock (e.g. delegation restrictions gated on vesting status, or external tooling assuming a real lock/vesting schedule) is bypassed. This is a fund-lock/logic-bypass bug rather than pure inflation, but it represents unauthorized removal of the "locked" invariant the vesting-account primitive is supposed to guarantee, matching the "unauthorized transfer/no-lock enforcement" category.

### Likelihood Explanation
High likelihood wherever the message is reachable: it requires only a single signed transaction with a `sdk.Coins` balance to send and an attacker-chosen `EndTime`, no special privileges, no race condition. The only gating factor is the deprecation switch, which is chain-ID- and height-dependent, not a general fix for the missing bound check itself.

### Recommendation
In `MsgCreateVestingAccount.ValidateBasic` (or in the handler using `ctx.BlockTime()`), reject `EndTime <= currentBlockTime` (and, for continuous vesting, ensure `EndTime > StartTime` where `StartTime` is derived from `ctx.BlockTime()`), consistent with the general recommendation to require vesting boundaries to lie in the future relative to block time.

### Proof of Concept
1. Attacker holds funds and calls `MsgCreateVestingAccount{FromAddress: attacker, ToAddress: victim, Amount: coins, EndTime: <ctx.BlockTime().Unix() - 1>, Delayed: false}`.
2. `ValidateBasic` passes because `EndTime > 0`.
3. Handler executes: sets `StartTime = ctx.BlockTime().Unix()`, `EndTime` = attacker-chosen past timestamp [2](#0-1) .
4. Because `StartTime >= EndTime`, `ContinuousVestingAccount.Validate()` should actually reject this specific case (`GetStartTime() >= GetEndTime()` check) — but if `Delayed=true` is used instead, `NewDelayedVestingAccountRaw` has no `StartTime` field and only checks `EndTime`, so setting `EndTime` to a past timestamp succeeds and the account is immediately fully vested via `DelayedVestingAccount.GetVestedCoins` semantics (all coins vested once `EndTime` is reached).
