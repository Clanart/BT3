### Title
Silent swallowing of `InvalidProtocolBufferException` during lazy-field re-merge masks corrupt/attacker-controlled data instead of failing parse - (File: `java/core/src/main/java/com/google/protobuf/LazyFieldLite.java`)

### Summary
The external report's failed invariant is: a function that is supposed to fully apply/credit attacker-supplied data (both deposits and internal balances) after validating it, but silently omits part of that data, so the caller believes the operation succeeded when critical state was actually dropped. The closest verified analog in this Protobuf checkout is in `LazyFieldLite.mergeFrom(CodedInputStream, ExtensionRegistryLite)`, where a second wire-format occurrence of a lazily-parsed message field is merged into the already-parsed value, but a resulting `InvalidProtocolBufferException` is caught and discarded, leaving the field in a state the client believes is validly merged when it is not.

### Finding Description
`LazyFieldLite` stores certain (extension/lazy) message fields as raw bytes and defers parsing. When a field number recurs in the wire stream — a legal, attacker-controllable condition for singular message fields, where standard merge semantics require the second occurrence to be merged into the first — `mergeFrom` is invoked a second time on the same `LazyFieldLite` instance: [1](#0-0) 

Specifically, when both sides already hold a parsed `value` (or one side does), the code merges by calling `value.toBuilder().mergeFrom(input, extensionRegistry).build()` and wraps this in a `try/catch` that swallows `InvalidProtocolBufferException` without setting any error/corrupted flag visible to the top-level caller and without rethrowing: [2](#0-1) 

The comment directly acknowledges the intent but also the resulting gap: *"We won't drop any extensions here directly... Nothing is logged and no exceptions are thrown. Clients will be unaware that a proto was invalid."* A parallel, more explicit admission of dropped data exists in the sibling `merge(LazyFieldLite other)` method, which documents *"In some cases may drop some extensions if both fields contain data"* and, in the bytes-concatenation fallback path, *"this may result in some extensions being lost that shouldn't have been"*: [3](#0-2) 

This maps onto the report's invariant failure precisely: the outward-facing contract ("parsing this message either succeeds with fully-merged content, or fails with `InvalidProtocolBufferException`") is violated — the second occurrence's malformed bytes are discarded, but the top-level `parseFrom()`/`mergeFrom()` call returns normally as if the merge had fully succeeded, exactly as `redeemDepositsAndInternalBalances` returns success while silently never crediting the internal-balances portion of validated input.

### Impact Explanation
An ordinary client parsing a bounded, attacker-supplied binary Protobuf message that uses lazy message fields (fields backed by `LazyFieldLite`, used for `MessageLite`-based lazy/extension fields) can craft a payload where a message field occurs twice: once with valid content, once with corrupted/truncated content. Instead of the parse failing with `InvalidProtocolBufferException` (the invariant applications rely on to reject malformed input), the corrupted second occurrence is silently dropped and the call returns a message object that appears to have parsed cleanly and merged both occurrences, but in fact reflects a partial/undefined merge state. Downstream application code that trusts "no exception ⇒ fully valid, fully merged data" (a very common assumption) will silently operate on inconsistent state — this is a data-integrity failure class, analogous in kind (silent loss of validated input) to the reported smart-contract bug, though the severity ceiling here is bounded by the fact it affects only lazily-encoded fields and does not itself corrupt memory or leak data.

### Likelihood Explanation
Reaching this path requires: (1) a message schema using lazy fields (a supported, if narrower, Protobuf Java feature for `MessageLite`/extensions), (2) a client calling a public parse API (`parseFrom`, `mergeFrom`) on attacker-controlled bytes, and (3) the attacker crafting a duplicate field-number occurrence where the first is valid and the second is corrupt. All three conditions are attacker-reachable via a single bounded input on the public parsing surface, with no privileged access needed, making the likelihood moderate for applications that use lazy fields on attacker-facing inputs.

### Recommendation
Do not silently swallow `InvalidProtocolBufferException` in `LazyFieldLite.mergeFrom(CodedInputStream, ExtensionRegistryLite)`. Either propagate the exception (failing the overall `parseFrom`/`mergeFrom` call, consistent with normal parse-failure semantics) or set the existing `corrupted` flag and ensure all accessors (`getValue`, `toByteString`, etc.) check it and throw/report the corruption to the caller, so that "no exception" reliably means "fully merged, valid data."

  /**
   * Merges another instance's contents. In some cases may drop some extensions if both fields
   * contain data. If the other field has an {@code ExtensionRegistry} but this does not, then this
   * field will copy over that {@code ExtensionRegistry}.
   *
   * <p>LazyField is not thread-safe for write access. Synchronizations are needed under read/write
   * situations.
   */
  public void merge(LazyFieldLite other) {
    if (other.containsDefaultInstance()) {
      return;
    }
    if (this.containsDefaultInstance()) {
      set(other);
      return;
    }

    // If the other field has an extension registry but this does not, copy over the other extension
    // registry.
    if (this.extensionRegistry == null) {
      this.extensionRegistry = other.extensionRegistry;
    }

    // The above checks guarantee that both `other` and `this` have `value` and/or `delayedBytes`
    // set. When both are unset it is considered a containsDefaultInstance==true case.

    // If both sides have delayed bytes we simply concatenate the bytes to save time, but we can
    // only safely do this if the extension registries are the same.
    if (this.delayedBytes != null
        && other.delayedBytes != null
        && this.extensionRegistry == other.extensionRegistry) {
      this.delayedBytes = this.delayedBytes.concat(other.delayedBytes);
      return;
    }

    // If either side is parsed, we merge on parsed instances.
    if (this.value != null || other.value != null) {
      mergeValue(other);
      return;
    }

    // If we have reached this far, both sides have `delayedBytes` set and neither have `value` set.

    // If `this.defaultInstance` is not known, we can't trigger a parse of `this` and so the
    // best we can do is concat the bytes. Since other side's extension registry is different
    // this may result in some extensions being lost that shouldn't have been, but its the
    // best that we can do if we reach this point and is not expected to occur in real use.
    if (defaultInstance == null) {
      // TODO: b/467739361 - Consider throwing an exception here.
      this.delayedBytes = this.delayedBytes.concat(other.delayedBytes);
      return;
    }

    setValue(mergeValueAndBytes(getValue(), other.delayedBytes, other.extensionRegistry));
  }

  public void mergeFrom(CodedInputStream input, ExtensionRegistryLite extensionRegistry)
      throws IOException {
    if (this.containsDefaultInstance()) {
      setByteString(input.readBytes(), extensionRegistry);
      return;
    }

    // If the other field has an extension registry but this does not, copy over the other extension
    // registry.
    if (this.extensionRegistry == null) {
      this.extensionRegistry = extensionRegistry;
    }

    // In the case that both of them are not parsed we simply concatenate the bytes to save time. In
    // the (probably rare) case that they have different extension registries there is a chance that
    // some of the extensions may be dropped, but the tradeoff of making this operation fast seems
    // to outway the benefits of combining the extension registries, which is not normally done for
    // lite protos anyways.
    if (this.delayedBytes != null) {
      setByteString(this.delayedBytes.concat(input.readBytes()), this.extensionRegistry);
      return;
    }

    // We are parsed and both contain data. We won't drop any extensions here directly, but in the
    // case that the extension registries are not the same then we might in the future if we
    // need to serialize and parse a message again.
    try {
      setValue(value.toBuilder().mergeFrom(input, extensionRegistry).build());
    } catch (InvalidProtocolBufferException e) {
      // Nothing is logged and no exceptions are thrown. Clients will be unaware that a proto
      // was invalid.
    }
  }
