## Analog Found: Divergent conflict-marker parsers cause Copilot's hunk resolutions to be silently misapplied or dropped

### Title
Independent, inconsistent conflict-marker parsers cause AI-resolved hunk content to be spliced into the wrong location (or dropped entirely) - (File: `app/src/lib/copilot-conflict-resolution.ts`, `app/src/lib/copilot-conflict-context.ts`)

### Summary
The Sherlock report's root cause is a stale/inconsistent index: an array element is removed by a swap-with-last operation but a side-table (`voucherIndexes`) that maps into the array is not kept in sync, so a lookup by index silently resolves to the wrong logical object. GitHub Desktop's Copilot-based merge conflict resolver has the same broken-invariant shape: two different functions each independently re-implement a state machine over the same raw file bytes to enumerate conflict-marker blocks, and the "index" used to marry a model-produced resolution to a location in the file is a bare positional counter (`hunkIndex`) rather than a shared, verified boundary. When the two parsers disagree about where a block starts/ends, the "next resolution" gets spliced into the wrong place or never applied — with the write path never detecting the mismatch.

### Finding Description
`extractConflictHunks` in [1](#0-0)  walks the raw file and, while collecting the "ours" section, only breaks out of that loop on a base marker (`|||||||`) or separator (`=======`) — it does not check for a theirs marker (`>>>>>>>`) at all during this phase, so a stray `>>>>>>>`-looking line appearing before the real separator is absorbed as ordinary "ours" content.

`reassembleResolvedFile`, used later to splice the model's per-hunk output back into the original file, implements a *different* lookahead in [2](#0-1) : it scans forward for the first line matching the theirs-marker regex and immediately treats that as the block's `closingIndex`, then only afterwards checks whether a separator was seen (`hasSeparator`). If a `>>>>>>>`-shaped line occurs *before* the true `=======` separator, this loop locks onto it as the closing marker while `hasSeparator` is still `false`, and the whole block is then classified as **malformed** (line 574: `if (!hasSeparator || closingIndex === -1)`), so it is pushed through verbatim, `i` only advances by one line, and `hunkIndex` is never incremented for that block.

Because `validateResolutionPaths` ( [3](#0-2) ) only checks that the *number* of hunks the model returned equals `extractConflictHunks`'s count for that file — it never validates that `reassembleResolvedFile`'s independent walk agrees on the same boundaries — this discrepancy is not caught anywhere in the pipeline. The mapping from "hunk N as seen by the model" to "block N as found during reassembly" is exactly the kind of unguarded index the Sherlock report flags: an object (the conflict block) is renumbered/reclassified without the consumer (`hunkIndex`/`hunkResolutions`) being kept consistent with it.

### Impact Explanation
The raw file content that both parsers walk comes directly from the working tree after a merge/rebase/cherry-pick of a remote branch — i.e., it is attacker-controlled whenever the user merges in a branch/PR from an untrusted remote. A `theirs` (or `ours`) side of a conflicting hunk that contains an innocuous-looking line such as `>>>>>>> something` (plausible inside documentation, test fixtures describing git conflict markers, string literals, or minified content — the project's own test fixtures in `app/test/unit/copilot-conflict-context-test.ts` show such literal marker text is a normal thing to embed in files) is enough to desynchronize the two parsers. The observable results are:
- The model's carefully resolved content for that hunk is silently never spliced in; the file written back to disk (and potentially committed by the user via the "accept AI resolution" flow) still contains raw `<<<<<<<`/`=======`/`>>>>>>>` markers and both sides' content concatenated.
- For files with multiple hunks, this shift can also cause a *later* hunk's model resolution to be spliced into an *earlier or unrelated* conflict block, because `hunkIndex` keeps counting even though block boundaries no longer line up 1:1 with what the model was shown.

This is a silent corruption of what the user commits, matching the requested impact class: the user believes a conflict was safely resolved by Copilot, but the actually-written file mixes attacker-controlled and local content in unintended ways with no error surfaced.

### Likelihood Explanation
No local access, admin rights, or social engineering beyond Desktop's already-supported "Resolve conflicts with Copilot" feature is required — an attacker only needs to control the content of one side of a real merge conflict (a PR branch, a fork, or any pushed branch the victim later merges/rebases against). Because the trigger is a single crafted line resembling a conflict marker embedded anywhere before the real `=======` separator, it is trivial to construct and easy to hide inside legitimate-looking file content (comments, docs, fixtures, string literals).

### Recommendation
Replace the duplicated, drifting state machines with a single shared parser: have `extractConflictHunks` return not just hunk content but each hunk's precise line-range boundaries (start/separator/base/end indices), and have `reassembleResolvedFile` consume those same boundaries directly instead of re-deriving them from scratch. If re-deriving is unavoidable, make both functions apply identical marker-priority rules (in particular, both should treat a `>>>>>>>`-shaped line encountered before a `=======` as ending the *ours* section scan, not silently absorbing or misclassifying it) and add a defensive check in `reassembleResolutions` that asserts the number of well-formed blocks found during reassembly equals `hunkResolutions.length`, throwing a `CopilotValidationError` (and refusing to write the file) on any mismatch rather than silently dropping or misplacing content.

### Proof of Concept
Given the following file content on disk (as would exist after a real merge conflict where the incoming branch's hunk happens to contain a `>>>>>>>`-shaped line before the true separator, e.g. from documentation about git markers):
```
A
<<<<<<< ours-label
oursLine1
>>>>>>> fake-closer
oursLine2
=======
theirsLine1
>>>>>>> real-label
B
```
- `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179`) reports exactly **one** hunk: `oursContent = "oursLine1\n>>>>>>> fake-closer\noursLine2"`, `theirsContent = "theirsLine1"`. This is what gets sent to the model and what `validateResolutionPaths` expects back (hunk count = 1).
- `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549`), scanning the same content, hits the `>>>>>>> fake-closer` line first and sets `closingIndex` there while `hasSeparator` is still `false`; the `!hasSeparator` branch fires, the block is classified as malformed, and `hunkIndex` is never advanced.
- Net effect: the model's single resolved-hunk content (`hunkResolutions[0]`) is **never spliced in**, and the reassembled "resolved" file that gets written to disk (and can be committed) still contains the literal conflict markers and both sides' raw content, with no error raised anywhere in the pipeline.

      i++
      continue

    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break

        i++
        break
      }

      i++

        i++
        break

      theirsLines.push(lines[i])
      i++
    }

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
