# CallDispatcher Is a Fully Permissionless Shared Custodian — Any Residual Bridged Funds Left On It Can Be Stolen By Any Unrelated Caller

### Title
Unauthenticated `CallDispatcher.dispatch()` lets any attacker sweep residual bridged tokens left by `HyperFungibleToken`/`WrappedHyperFungibleToken` compose calls - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The external H-02 report's core broken invariant is: a function meant to execute privileged, pre-authorized logic (`executeOperation`) can be invoked directly by an attacker with attacker-chosen parameters because the only guard is a `msg.sender` check on the *initiator* (the lending pool), not on whether the call is a legitimate part of a controlled flow. The Hyperbridge analog is `CallDispatcher.dispatch()`, which has **no access control at all** and executes arbitrary `Call[]` using whatever token/ETH balance the shared singleton contract currently holds.

### Finding Description
`CallDispatcher` is a shared, cross-app singleton used for "calldata execution" by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`IntentsBase`. Its `dispatch()` function is unauthenticated and simply executes whatever `Call[]` is passed: [1](#0-0) 

For `IntentGatewayV2`/`IntentsBase`, every invocation of `dispatch()` is immediately followed in the same atomic transaction by an explicit sweep of any residual balance back to the gateway (`DustCollected` events): [2](#0-1) 

However, `HyperFungibleToken.onAccept()` and `WrappedHyperFungibleToken.onAccept()` (and their upgradeable variants) mint/unlock tokens directly to the `beneficiary`, and then — for the documented compose pattern where `message.to` is set to the `CallDispatcher` address so it can spend the bridged tokens — call `dispatch(message.data)` with **no sweep-back logic whatsoever**: [3](#0-2) [4](#0-3) 

The documentation itself confirms `to = CallDispatcher` is the officially recommended pattern for composable transfer-and-swap/stake/deposit flows, and that the `Call[]` (i.e., `message.data`) is fully attacker/sender-controlled at `send()` time on the source chain: [5](#0-4) 

If the calldata does not fully consume the tokens delivered to `CallDispatcher` (e.g. a partial swap, a swap that reverts for only part of the batch, or calldata that is simply incomplete/buggy), the leftover tokens sit in `CallDispatcher`'s balance with **no owner bookkeeping**. Because `dispatch()` has zero `msg.sender` restriction — exactly like the flash-loan analog where `executeOperation()` trusted only that the caller was the lending pool and not that the *content* of the call belonged to a legitimate, self-initiated operation — **any unrelated third party** can subsequently call `CallDispatcher.dispatch()` directly with a `Call{to: token, data: transfer(attacker, balance)}` and drain the residual funds that rightfully belong to the original message's beneficiary.

### Impact Explanation
This is direct fund theft: any bridged tokens or ETH left temporarily on the shared `CallDispatcher` due to a partial/incomplete compose call become permissionlessly stealable by any address, not just the intended beneficiary or the original relayer. Because `CallDispatcher` is a single deployed address reused by multiple apps and chains, the residual-balance attack surface accumulates across every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment that uses the compose pattern.

### Likelihood Explanation
No privileged actor, relayer collusion, or governance action is required — only an unprivileged EOA calling a public function with no access control, after any imperfect/partial compose calldata leaves dust on the dispatcher. Given that `IntentsBase`/`IntentGatewayV2` needed to add explicit sweep logic to avoid exactly this outcome, it demonstrates the protocol authors are aware dust can accumulate on `CallDispatcher` — yet the HFT/WrappedHFT `onAccept` paths, which explicitly document routing tokens to `CallDispatcher`, have no equivalent protection.

### Recommendation
Add the same sweep-back-to-caller logic used in `IntentsBase._execute`/`IntentGatewayV2.placeOrder` to `HyperFungibleToken.onAccept`/`WrappedHyperFungibleToken(Upgradeable).onAccept` whenever `message.data.length > 0`, sweeping any post-dispatch residual balance in `CallDispatcher` back to the intended `beneficiary` before completing the callback. Alternatively, restrict `CallDispatcher.dispatch()` to a caller allow-list (the apps that use it) and have it forward any leftover balance to `msg.sender` at the end of every `dispatch()` call so nothing can persist across transactions.

### Proof of Concept
1. Attacker (or any user) calls `HyperFungibleToken.send()` on chain A with `params.to = <CallDispatcher address on chain B>` and `params.data` encoding a `Call[]` that only partially spends the bridged amount (e.g., swaps 50% via UniswapV2 and leaves the rest untouched, or targets a call that reverts silently for the remainder due to slippage).
2. A relayer delivers the message; `onAccept()` on chain B mints/unlocks the full `amount` to the `CallDispatcher` address, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` — see [6](#0-5) . The unspent tokens remain on `CallDispatcher`.
3. Any unrelated third-party attacker then calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, CallDispatcher.balanceOf(token))})]))` directly — `dispatch()` performs no `msg.sender` check, so this succeeds and moves the leftover tokens to the attacker, permanently depriving the intended beneficiary of the remainder of their bridged funds.

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
