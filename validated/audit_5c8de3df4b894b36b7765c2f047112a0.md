### Title
`SignableTransaction` excludes the OP_RETURN output from weight/fee calculation, misdirecting the fee budget into change - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the ELFi finding (fees accounted into the wrong pool after a state transition), `SignableTransaction::new` computes the transaction weight and required fee using only `payments`, while unconditionally appending the attacker-influenced `data` OP_RETURN output to `tx_outs` beforehand. The result is that the fee is undercharged and the shortfall is silently absorbed by the change output — value that should have gone to the miner fee is left in the change "pool". In the worst case the transaction's effective feerate drops below the minimum relay fee, making the signed transaction unbroadcastable.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` builds `tx_outs` including the OP_RETURN `data` output (lines 194-202), then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204. `calculate_weight_vbytes` (lines 62-127) constructs a synthetic `Transaction` whose `output` vector contains only `payments` (lines 85-93) plus optionally `change` (line 98) — the `data` output is never included.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed over a smaller vbytes than the real transaction, so `needed_fee` undervalues the true required fee by `fee_per_vbyte * (OP_RETURN output vbytes)` (an OP_RETURN output is ~9-90+ bytes depending on data length, up to 80 bytes of data by the check at line 171).

2. The minimum-relay-fee guard at lines 211-213 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, again using the underestimated `vbytes`. A caller-specified `fee_per_vbyte` that satisfies the check can produce a real transaction whose actual feerate (`fee() / real_vsize`) is below the relay minimum, so `sendrawtransaction` rejects it.

3. The change-credit path at lines 224-234 has the identical defect: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` still omits `data`, so `fee_with_change` is too small and the change output `value = input_sat - payment_sat - fee_with_change` (lines 228-230) is over-credited by exactly the missing OP_RETURN fee — the fee that should have left the "pool" stays in change.

4. `fee()` (lines 138-141) reports the actual paid fee, which diverges from `needed_fee()` whenever `data` is `Some` — the two accounting views disagree, mirroring the report's "fees reported in one pool while sitting in another".

### Impact Explanation
`data` is a public/untrusted input to `SignableTransaction::new` (in Serai it carries eventuality/cross-network metadata accompanying a payment, i.e., bytes that cause a transaction to be signed). With a sufficiently large `data` payload (up to 80 bytes + output overhead, ~30+ vbytes), the produced transaction:

- pays less than the intended `fee_per_vbyte`, and can fall under `DEFAULT_MIN_RELAY_TX_FEE` despite passing the `TooLowFee` check, causing node rejection of a threshold-signed transaction — a liveness/funds-stuck condition requiring a new signing round; or
- overpays the change output relative to the declared budget, misreporting accounting between "fee paid" (`needed_fee`) and actual.

Medium severity: deterministic miscalculation of the fee and change amounts reachable purely through the `data` input; no secret leakage, but breaks the invariant that `fee()` reflects `needed_fee` and can produce non-relayable signed transactions.

### Likelihood Explanation
Any call path that supplies non-empty `data` triggers the miscalculation deterministically — the OP_RETURN branch is a normal, intended feature (lines 149, 194-202), not an edge case. The relay-failure outcome additionally requires `fee_per_vbyte` near the minimum, which is exactly the regime the `TooLowFee` guard exists for and which production callers target when minimizing fees.

### Recommendation
Include the OP_RETURN output in the weight model: change `calculate_weight_vbytes` to accept the fully-formed output list (or an extra `data: Option<&[u8]>` parameter that pushes `TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }` into the synthetic transaction), and call it with `data` accounted at both call sites (lines 204 and 226). Alternatively, build the synthetic transaction from `tx_outs` directly so all real outputs — payments, OP_RETURN, and change — contribute to `weight`/`vbytes`.

### Proof of Concept
Textual:

- Inputs: one `ReceivedOutput` worth `I` sats; `payments = [(addr, P)]`; `change = Some(change_addr)`; `data = Some(vec![0; 80])`; `fee_per_vbyte = f`.
- Line 194-202: `tx_outs` = [payment, OP_RETURN(0)].
- Line 204: `vbytes` computed on tx with output = [payment] only — missing ~93 weight units (~24 vbytes) for the OP_RETURN output plus its share of output-count varint.
- Line 206: `needed_fee = f * vbytes` is `~24*f` sats too low.
- Lines 225-233: `fee_with_change` is equally too low, so `value = I - P - fee_with_change` credits the change output `~24*f` sats more than the intended budget — fee value retained in the change "pool" instead of leaving the wallet.
- Final `fee() = I - (P + 0 + value) = needed_fee_actual`, but the transaction's real vsize is `vbytes + ~24`, so effective feerate is `needed_fee / (vbytes + 24) < f`. If `f` was chosen just above the min-relay threshold enforced at line 211, the actual feerate is below `DEFAULT_MIN_RELAY_TX_FEE`, and Bitcoin Core rejects the signed transaction with `min relay fee not met` / `mempool min fee not met`.

This mirrors the external report's shape: after settlement (transaction construction), the amounts that should have been allocated to the fee remain credited inside the system (change output / understated `needed_fee`), and the misaccounting is provable by comparing `needed_fee()` against `fee() / actual_vsize` for any `data.is_some()` transaction.
