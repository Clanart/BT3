Payout tx's OP_RETURN operator-attribution output is unsigned, letting anyone replace/malleate it and frame the fronting operator as malicious - ([File: core/src/verifier.rs])

### Summary
`create_payout_txhandler` signs the withdrawal input with `TapSighashType::SinglePlusAnyoneCanPay`, which under BIP341 only commits to the single output at the same index as the signed input (output 0, the user's payout) and excludes all other inputs from the sighash. The anchor output (index 1) and, critically, the OP_RETURN output (index 2) that encodes `operator_xonly_pk` are completely outside the signed message. Anyone who observes the broadcast/mempool transaction can construct an alternative, still-validly-signed transaction spending the same withdrawal UTXO with the same output-0 payment but an arbitrary OP_RETURN payload, and win the race to get it confirmed.

### Finding Description
Binding claimed: for every honest operator whose kickoff matches the payout it actually funded, `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) must return `false`, i.e. `payout_payer_operator_xonly_pk == kickoff_data.operator_xonly_pk`.

Trace:
1. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the Payout tx with input 0 = withdrawal UTXO (key-spend), output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(`operator_xonly_pk`). Only output 0 is signed via `set_p2tr_key_spend_witness(&user_sig, 0)`.
2. The signature is checked in `Operator::withdraw` (`core/src/operator.rs:630-637`) via `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)`, which for `SinglePlusAnyoneCanPay` uses `Prevouts::One` and BIP341's taproot key-spend sighash (`core/src/builder/transaction/txhandler.rs:210-233`, standard `taproot_key_spend_signature_hash`). Per BIP341, `SIGHASH_SINGLE` commits `sha_single_output` (only output index == input index, i.e. output 0) and `ANYONECANPAY` excludes `sha_prevouts`/other inputs entirely — outputs 1 and 2 are never hashed into the message.
3. This means the *exact same signature* remains valid for any transaction that: spends the same withdrawal UTXO as input 0 with the same sequence, and keeps output 0 identical — but can have an arbitrary output 1 and output 2 (or extra outputs/inputs, since ANYONECANPAY permits new inputs too).
4. Once the honest operator broadcasts/relays this transaction (it must hit the public Bitcoin mempool/network to get mined), any attacker (an "unprivileged" network participant per the threat model, who can broadcast Bitcoin transactions and pay fees) can construct a replacement transaction with the identical signed input/output-0 but a forged OP_RETURN encoding 32 arbitrary bytes that parse as *some* valid `XOnlyPublicKey` not belonging to the fronting operator (or belonging to a different, uninvolved operator), and get it confirmed first (e.g., by attaching extra fee-paying inputs allowed under ANYONECANPAY, i.e., a standard fee-bump replacement).
5. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) reads whichever payout tx actually confirmed from `block_cache.txids`/`block.txdata`, extracts the OP_RETURN via `get_first_op_return_output`/`parse_op_return_data`, and parses it into `operator_xonly_pk` (`verifier.rs:2311-2321`). This bogus pubkey is persisted via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) into `withdrawals.payout_payer_operator_xonly_pk`.
6. `Verifier::is_kickoff_malicious` (`verifier.rs:1859-1915`) later reads this poisoned value via `get_payout_info_from_move_txid` and compares it against `kickoff_data.operator_xonly_pk` from the honest operator's actual kickoff (`verifier.rs:1887-1890`). Since the stored pubkey no longer matches, the check falsely returns `true` ("malicious"), and `handle_kickoff` (`verifier.rs:1969-2027`) queues a `Challenge` transaction against the honest operator who genuinely fronted the withdrawal, burning their collateral.

No existing guard prevents this: `parse_withdrawal_sig_params` only enforces that the sighash type equals `SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:161-203`) — it does not, and structurally cannot, protect the unsigned OP_RETURN output. `SECP.verify_schnorr` in `Operator::withdraw` only validates the signature against the sighash that already excludes outputs 1/2. Nothing re-derives or re-checks the operator attribution against the actual UTXO spender's identity/collateral at settlement time before trusting the OP_RETURN content.

### Impact Explanation
This directly maps to the Critical category "an honest operator's collateral burned": an unprivileged attacker can, for the cost of a single higher-fee replacement transaction, cause the confirmed Payout tx's OP_RETURN to misattribute the payout, making a truthful operator's later kickoff be classified as malicious and challenged/disproved, burning that operator's round collateral. It is repeatable per withdrawal/operator — every payout is vulnerable at the moment it's broadcast and sits in the mempool until confirmed, so this can be executed against any operator on any withdrawal. It could also be aimed the other direction: crafting an OP_RETURN naming a different, uninvolved real operator, potentially letting that operator be wrongly credited/reimbursed for a payout it never funded (a second Critical category: "an operator reimbursed for a payout it never funded") — though the latter path requires that operator's own kickoff to reference the deposit, which is a separate check (`send_asserts` also validates `payout_op_xonly_pk != kickoff_data.operator_xonly_pk`, `operator.rs:1290-1295`, so an uninvolved operator would simply fail that assertion rather than receive funds — the more directly exploitable outcome is framing the true payer, which the question also focuses on).

### Likelihood Explanation
Feasibility is high: the attacker only needs standard Bitcoin mempool visibility (no privileged access), the ability to broadcast a transaction, and enough sats to outbid the original transaction's fee (RBF/fee-bump economics), since `ANYONECANPAY` lets them freely add extra fee-paying inputs. No aggregator/verifier/operator key material, no majority hashrate, and no protocol-level trust is needed — only public mempool monitoring and normal transaction relay, matching the specified unprivileged attacker capabilities (broadcast transactions, choose bytes of a withdrawal UTXO's spending tx, an OP_RETURN). This is repeatable across every withdrawal and every operator, since the signing scheme (`SinglePlusAnyoneCanPay` over only output 0) is fixed by protocol design in `create_payout_txhandler`.

### Recommendation
Change the Payout transaction's signature scheme so that the operator-attribution OP_RETURN output (and ideally the anchor output) is committed by the sighash — e.g., require the operator to co-sign with a second signature covering `SIGHASH_ALL` semantics for the full output set (via an additional key/commitment path), or otherwise bind the OP_RETURN content cryptographically to the specific UTXO spend so it cannot be altered post hoc without invalidating the transaction. Alternatively, stop trusting the OP_RETURN entirely as sole determinant of "which operator fronted the payout" and instead require an operator-specific pre-committed identifier (e.g., part of the taproot output script or a covenant-enforced output) that cannot be freely malleated by third parties observing the mempool.
