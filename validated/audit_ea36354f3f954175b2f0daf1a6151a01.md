Based on my investigation, I found a genuine analog to the PoolTogether TWAB-overwrite bug in Hyperbridge's Phantom Order pricing pipeline, where a **balance-weighted price oracle is sampled instantaneously rather than time-weighted**, exactly mirroring the underlying flaw class ("an attacker can manipulate the value that is recorded/read at a single critical settlement moment by controlling their own state right before the read").

### Title
Phantom Order price snapshot uses instantaneous (non-time-locked) solver liquidity as price weight, letting a solver bias the settlement quote at the exact measurement moment - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
The PoolTogether bug's core primitive was: a balance used to determine a user's economic entitlement at draw-close was read at an instant the user could control, rather than being time-weighted/locked across the whole window, letting the user inflate the recorded value right before the critical read. Hyperbridge's Phantom Order pricing pipeline reproduces this same anti-pattern: the weight used to compute the `medianPrice` that becomes the executed swap rate is the solver's **live, instantaneous** on-chain balance queried at aggregation time, not a balance locked or averaged over the whole bid window.

### Finding Description
When a phantom order's bid window closes (`PhantomBidWindowExhausted`), `aggregatePhantomBids` computes a liquidity-weighted median price from all verified solver bids: [1](#0-0) 

The weight for each solver is fetched via `getTotalSolverBalance`, a **point-in-time** RPC balance read (native + ERC-4626 vault positions) taken whenever the indexer/SDK processes the triggering event — not a value locked at bid-submission time or averaged over the window: [2](#0-1) 

The resulting `medianPrice` is persisted as the canonical price for the token pair: [3](#0-2) 

and is consumed directly to compute the real `amountIn`/`amountOut` used to build the user's actual cross-chain order (funds that get locked/escrowed and settled via the IntentGateway): [4](#0-3) 

Because the weight is a naïve current-balance snapshot rather than a time-weighted or bond-locked measure, a solver that temporarily moves large capital into a tracked vault/token just before the snapshot fires can dominate the weighted median (`weightedMedian` picks the price whose cumulative weight crosses 50%, so a single large, temporary balance can force the outcome to that solver's quoted price), then withdraw the capital immediately afterward. This is structurally identical to PoolTogether users depositing/withdrawing to control which balance an observation captured right before draw-close — except here the "draw close" is `PhantomBidWindowExhausted` and the manipulated value flows directly into the price used to size real user orders.

### Impact Explanation
A solver that inflates its measured liquidity for the single window in which the price is sampled can force the settlement price toward its own (potentially worse-for-user) quote, causing users to receive less output / pay more input for a swap than the honest liquidity-weighted market would dictate — a direct transaction-manipulation / wrong-amount impact on real bridged funds, since the manipulated `medianPrice` feeds the actual `amountIn`/`amountOut` used to construct and settle the cross-chain order.

### Likelihood Explanation
Exploitability depends on being able to move capital into/out of the tracked vault/token within a narrow window around the aggregation read, and requires capital (temporary, not permanently at risk) plus knowledge of when the indexer/SDK samples balances relative to `PhantomBidWindowExhausted`. This is achievable by any well-capitalized market participant (no privileged role, prover, or relayer collusion needed), similar to how the original PoolTogether exploit only required an ordinary user timing deposits/withdrawals — but the precise timing/latency of the off-chain indexer sampling introduces some uncertainty about how tightly an attacker can align the manipulation with the exact read, which I was not able to fully verify from the code alone (the indexer's exact block-vs-RPC-call timing).

### Recommendation
Replace the instantaneous balance read with a time-weighted or bonded/locked liquidity measure over the full bid window (mirroring PoolTogether's fix of aligning balance queries to period boundaries) — e.g., require solvers to lock collateral for the window duration, or average balance samples across multiple blocks within the window, so a single-block capital injection cannot dominate `weightedMedian`.

### Proof of Concept
1. Solver observes a phantom order's bid window is about to close (`PhantomBidWindowExhausted` imminent).
2. Solver flash-borrows or temporarily transfers a large balance of the tracked output token/vault into an address delegated to its `SolverAccount`.
3. Indexer/SDK aggregation (`aggregatePhantomBids`) runs `getTotalSolverBalance`, which reads the inflated balance and assigns it disproportionate weight in `weightedMedian`.
4. The solver's own (unfavorable-to-user) quoted price wins the weighted median and becomes `PhantomOrderPriceSnapshot.medianPrice`.
5. Solver withdraws/returns the temporary capital.
6. Subsequent users querying a quote via `PhantomSnapshotIntentQuoteStrategy.quote` receive `amountOut`/`amountIn` computed from the manipulated `medianPrice`, locking real funds into an order priced against the attacker's favor. [5](#0-4)

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing; if every weight is zero it falls back to the unweighted
// median so a price is still reported.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
