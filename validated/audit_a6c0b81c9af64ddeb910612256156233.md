### Title
Credential-protocol smuggling via bare-CR values that bypass `formatCredential`'s newline guard - (File: app/src/lib/git/credential.ts)

### Summary
`formatCredential` re-serializes a `Map<string,string>` into the line-oriented `key=value\n` format used by Git's credential-helper protocol, which is then piped as stdin to an external process (`git credential fill/approve/reject -c credential.helper=manager`, i.e. Git Credential Manager). Its only injection guard rejects values containing `\n` or `\0`, but not a bare `\r`. `parseCredential`, symmetrically, only recognizes `\r?\n` as a line terminator. Because GCM (a .NET application) commonly reads stdin line-by-line with APIs that treat a lone `\r` as a line terminator on its own, a value that contains a raw `\r` but no `\n` will pass Desktop's guard untouched yet still be interpreted by GCM as a line break, letting an attacker splice an extra, attacker-controlled `key=value` record into the credential record GCM receives.

### Finding Description [1](#0-0) 
`parseCredential` builds the `Credential` map from `command.stdin` sent by real Git, splitting strictly on `/\r?\n/` — a lone `\r` is *not* a delimiter here, so it is preserved verbatim inside whatever field it appeared in. [2](#0-1) 
`formatCredential` is the only place that guards against protocol injection when re-emitting the map as `key=value\n` lines, and it explicitly checks only for `\n` and `\0`:
```
if (v.includes('\n') || v.includes('\0')) {
  throw new Error(`forbidden characters in credential value: ${k}`)
}
```
A value containing `\r` (without `\n`) sails through this check.

This formatted string is fed directly as `stdin` to a spawned Git process configured with `credential.helper=manager` (Git Credential Manager) in `app/src/lib/git/credential.ts` lines 50-79 (`exec`, `fillCredential`, `approveCredential`, `rejectCredential`), and is invoked from `getExternalCredential` / `storeExternalCredential` / `eraseExternalCredential` in [3](#0-2)  and [4](#0-3) .

The `cred` map that reaches `formatCredential` is the same map originally received from real Git (`input = parseCredential(command.stdin)` in [5](#0-4) ), whose fields (`protocol`, `host`, `path`, `username`, and particularly the raw, attacker-influenceable `wwwauth[]` entries copied from a remote server's `WWW-Authenticate` response header) are round-tripped back out unchanged except when Desktop overwrites `username`/`password` via `credWithAccount`. Any field Desktop doesn't overwrite (e.g. `path`, `wwwauth[]`, or `host`) is passed straight through to `formatCredential`.

This is the same broken invariant as the reported llhttp bug: one parser treats `CRLF`/`LF` as the only legal record terminator while the consuming parser downstream (GCM's .NET stdin reader) is more lenient and also breaks records on a bare `CR`. `formatCredential`'s guard was written against the wrong (Desktop-side) delimiter definition instead of the real consumer's (GCM's) more permissive one, so it fails to close the gap.

### Impact Explanation
If an attacker-influenced value (e.g. a `path` embedding raw `\r` bytes coming from a crafted remote URL, or a `wwwauth[]` value copied from a malicious/compromised HTTP git remote's `WWW-Authenticate` response) reaches `formatCredential` un-rejected, an extra attacker-chosen `key=value` line can be smuggled into the credential record handed to Git Credential Manager. Depending on which key is smuggled (`url=`, `host=`, `protocol=`) this can redirect GCM's subsequent credential lookup/storage to an attacker-chosen host, or corrupt/poison what gets stored/erased in the user's OS-level credential store for a different, legitimate host — a credential-store poisoning / potential token misdirection primitive, matching the "credential/token exfiltration" and "silent corruption" impact classes.

### Likelihood Explanation
Exploitation requires the attacker to control a git remote/proxy/HTTP response that Desktop fetches from (fully within the described threat model), and for the attacker's payload to contain a raw `\r` without `\n` in a field that survives to `formatCredential` unmodified. The external-GCM path is opt-in (`useExternalCredentialHelper()`), which narrows real-world exposure, and reaching this specific gap requires the underlying transport (Git's own libcurl/http layer for `wwwauth[]`, or Git's URL parsing for `host`/`path`) to actually let a bare `\r` through — Git upstream has hardened URL parsing against embedded control characters in recent versions, which may already block this for the `host`/`path` vectors. Overall likelihood is Low–Medium: the code-level guard is unambiguously incomplete, but a fully attacker-controlled reachable path to inject a bare-CR value has not been proven in this analysis beyond the `wwwauth[]` vector.

### Recommendation
Extend `formatCredential`'s guard in `app/src/lib/git/credential.ts` to reject (or strip) any value containing `\r` in addition to `\n`/`\0`, matching the actual delimiter behavior of the downstream consumer (GCM) rather than only Desktop's own `\r?\n`-aware parser. Consider also validating/normalizing `wwwauth[]` and other pass-through fields for control characters before they are ever stored in the `Credential` map, rather than relying solely on the serialization boundary.

### Proof of Concept
1. Configure Desktop to use the external credential helper (Git Credential Manager) via **Use Git Credential Manager**.
2. Point a remote at an attacker-controlled HTTP(S) server that, on the initial unauthenticated request, responds with a `401` and a `WWW-Authenticate` header value containing a bare `\r` such as: `Basic realm="x"\rurl=https://attacker.example/\r`.
3. When Git forwards this as `wwwauth[]=Basic realm="x"\rurl=https://attacker.example/\r` to Desktop's credential-helper trampoline, `parseCredential` stores it as a single value (no `\n` present, so it is not split).
4. `formatCredential` re-emits it as `wwwauth[]=Basic realm="x"\rurl=https://attacker.example/\r\n` — passing the `\n`/`\0` check — and pipes it to `git credential fill -c credential.helper=manager`.
5. If GCM's stdin reader treats the embedded `\r` as a line terminator, it parses two records: `wwwauth[]=Basic realm="x"` and `url=https://attacker.example/`, the latter smuggled in and capable of steering GCM's credential lookup/store operation to `attacker.example`.

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}

export const formatCredential = (credential: Map<string, string>) => {
  const lines = []
  for (const [k, v] of credential) {
    if (v.includes('\n') || v.includes('\0')) {
      throw new Error(`forbidden characters in credential value: ${k}`)
    }
    lines.push(`${k.replace(/\[\d+\]$/, '[]')}=${v}\n`)
  }

  return lines.join('')
}
