### Title
Unchecked satoshi arithmetic bypasses insufficient-funds validation and signs invalid Bitcoin transactions - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` computes input totals, payment totals, fees, and affordability checks using unchecked `u64` arithmetic. In release builds, the sums and additions can wrap, allowing a request with outputs exceeding the available inputs to pass the `NotEnoughFunds` check and proceed into Taproot FROST signing. [1](#0-0) 

### Finding Description
`input_sat` and `payment_sat` are calculated with `.sum::<u64>()`, while `payment_sat + needed_fee` and `payment_sat + fee_with_change` use unchecked addition. [1](#0-0) 

If `payments` contains amounts whose total exceeds `u64::MAX`, `payment_sat` wraps to a small value. The subsequent affordability comparison can therefore succeed even though the encoded transaction contains outputs totaling more than the supplied inputs. [2](#0-1) 

The affected values are supplied through `payments` and through `ReceivedOutput`, whose public `read` implementation accepts the serialized `TxOut` value and outpoint directly. [3](#0-2) 

After the bypassed validation, `multisig` checks only that each supplied prevout script matches the offset threshold key, and `TransactionSignMachine::sign` signs each input using `Prevouts::All`. [4](#0-3) [5](#0-4) 

### Impact Explanation
A caller or counterparty able to influence payment instructions or serialized `ReceivedOutput` data can cause the threshold wallet to sign a transaction that the wallet’s own policy promised to reject for insufficient funds. The resulting transaction has cryptographically valid signatures for an economically invalid spend, so it is not spendable on Bitcoin consensus rules. [6](#0-5) [7](#0-6) 

This is strongest where untrusted payment or output metadata reaches `SignableTransaction::new`; it creates a concrete signing of a transaction outside the wallet’s validated funds invariant rather than merely rejecting malformed input. [8](#0-7) 

### Likelihood Explanation
The bug requires an attacker-controlled input boundary that supplies crafted payment amounts or serialized `ReceivedOutput` values. Those interfaces are public parsing/signing APIs, and two ordinary `u64` values are enough to trigger arithmetic wraparound in a release build. [3](#0-2) [9](#0-8) 

Actual Bitcoin funds cannot naturally contain more than the monetary supply, but deserialization does not enforce `MAX_MONEY` or UTXO existence, so crafted `ReceivedOutput` bytes are not limited to values that can occur on-chain. [3](#0-2) 

### Recommendation
Use checked arithmetic for every monetary total and comparison in `SignableTransaction::new` and `fee`:

- `try_fold` or `checked_add` for `input_sat` and `payment_sat`
- `checked_mul` for `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change`
- `checked_add` for `payment_sat + needed_fee` and `payment_sat + fee_with_change`
- `checked_sub` for the final fee calculation
- reject `TxOut` values above Bitcoin’s maximum money range when reading or constructing spendable outputs

Any overflow should produce `TransactionError::NotEnoughFunds` or a dedicated overflow error rather than reaching signing. [10](#0-9) 

### Proof of Concept
The following release-build scenario demonstrates the validation bypass:

```rust
// networks/bitcoin/src/wallet/send.rs

let input = received_output_with_value_and_matching_script(1_000_000);
let payments = [
  (attacker_script.clone(), u64::MAX),
  (attacker_script.clone(), 2),
];

// In release mode:
// payment_sat = u64::MAX + 2 = 1
// payment_sat + needed_fee remains much smaller than input_sat.
let signable = SignableTransaction::new(
  vec![input],
  &payments,
  None,
  None,
  10,
).expect("overflowed payment total incorrectly passed validation");

let machine = signable
  .multisig(&threshold_keys)
  .expect("prevout scripts match the threshold key");

let (machine, our_preprocess) = machine.preprocess(&mut rng);
let (machine, our_share) = machine.sign(other_preprocesses, &[]).unwrap();

// This transaction is signed even though its output amounts exceed the
// supplied input amount by approximately u64::MAX satoshis.
assert_eq!(
  signable.transaction().output.iter().map(|o| o.value.to_sat()).sum::<u64>(),
  1
);
```

The important behavior occurs before `sum::<u64>()` in the assertion: construction already emits two `TxOut`s with `u64::MAX` and `2`, while the wrapped `payment_sat` used for validation is only `1`. [2](#0-1)
