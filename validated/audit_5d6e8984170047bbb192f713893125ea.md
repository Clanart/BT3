## Analysis

This is a solid analog. The Vether bug's core pattern — an unprivileged, one-click action that adds an attacker-influenced value to a global "trust/exclude" list with no verification that the value corresponds to what the user actually intended — has a direct match in Desktop's "safe directory" trust flow.

### Title
Unverified `git rev-parse` dubious-ownership path is trusted verbatim, letting a malicious repo's `.git` gitlink redirect the "Trust Repository" action to an arbitrary attacker-chosen path - (File: `app/src/lib/git/rev-parse.ts`, `app/src/ui/add-repository/add-existing-repository.tsx`, `app/src/lib/git/config.ts`)

### Summary
`getRepositoryType()` determines an "unsafe" repository by regex-parsing Git's own stderr message and returns whatever path Git printed as `{ kind: 'unsafe', path }` [1](#0-0)  . The UI then feeds this path, completely unverified, straight into `addSafeDirectory()`, which appends it to the global `safe.directory` git config [2](#0-1)  . Because a repository's `.git` entry can be a "gitlink" file whose `gitdir:` target is resolved with an unrestricted relative/absolute path (`Path.resolve(Path.dirname(gitPath), gitDirMatch[1])`, no containment check) [3](#0-2)  , a malicious repository can make the path Git reports as "the repository with dubious ownership" be an arbitrary location on disk that has nothing to do with the folder the user actually opened.

### Finding Description
Desktop's own UI already anticipates that the reported unsafe path and the folder the user is opening can diverge — `buildRepositoryUnsafeError()` explicitly branches on `repositoryUnsafePath !== convertedPath` and only then shows the resolved repository path in the warning text [4](#0-3)  . Despite this, when the user clicks "add an exception for this directory," the handler trusts `repositoryUnsafePath` unconditionally:

```ts
private onTrustDirectory = async () => {
  this.setState({ isTrustingRepository: true })
  const { repositoryUnsafePath, path } = this.state
  if (repositoryUnsafePath) {
    await addSafeDirectory(repositoryUnsafePath)
  }
  ...
}
``` [5](#0-4) 

The same pattern exists for repositories that go missing/relocate, in `MissingRepository.onTrustDirectory` [6](#0-5) .

`repositoryUnsafePath` originates purely from Git's stderr, produced when Desktop runs `git rev-parse --is-bare-repository --show-cdup --git-dir` inside the user-selected `path` [7](#0-6) . Git resolves `--git-dir` following any `.git` gitlink file it finds, and a `.git` file's `gitdir:` value is attacker-controlled content checked into the repository (this is normal for submodules/worktrees, as seen in the fixtures `worktree = ../../../foo/submodule` and `gitdir: ../../.git/modules/foo/submodule`) [8](#0-7) [9](#0-8) . Nothing in Desktop's `git-info.ts` gitlink resolution restricts the target to stay within the repository [10](#0-9) .

So a crafted repository can contain a `.git`-style pointer file (or a submodule/worktree entry) whose `gitdir:` points at a directory that is owned by a different user (e.g., another account's home directory, a shared/network path, or any location the attacker can predict), triggering Git's dubious-ownership error for *that* redirected path instead of the folder the victim opened. The victim sees Desktop's generic "Trust Repository" prompt, clicks it believing they are trusting the repo they intended to add, and Desktop silently writes the attacker-chosen path into the machine-wide `safe.directory` git config via `addGlobalConfigValueIfMissing('safe.directory', path)` [11](#0-10) . This exactly mirrors the Vether flaw: an unrestricted "add to trusted/excluded list" primitive that anyone (here, any repository author) can steer via an argument they fully control, with no check tying the added value back to a properly reviewed target.

### Impact Explanation
`safe.directory` is a global, machine-wide allowlist that disables Git's ownership-mismatch protection, which Desktop's own copy states exists because "Adding untrusted repositories may automatically execute files in the repository" [12](#0-11) . Tricking a user into trusting a path they never reviewed — potentially a shared directory, another user's profile folder on a multi-user machine, or a path an attacker can later populate/control — extends Git's auto-execution trust boundary (hooks, filters, config) to that location for every future Git operation performed there by Desktop or the Git CLI, without the user ever consciously reviewing or approving that specific directory.

### Likelihood Explanation
Requires only that the victim clone/open an attacker-authored repository (a normal, expected Desktop workflow) and click through the existing "Trust Repository" warning — a single click most users treat as routine when opening repos with submodules/worktrees. No local access, malware, or leaked credentials are needed; the attacker only needs to control repository content (a `.git`/gitlink file) and predict or control a path on the victim's system that is owned by a different user (realistic on shared machines, CI runners, or via known well-known paths).

### Recommendation
Before calling `addSafeDirectory`, verify that the "unsafe" path reported by Git is the same as (or a legitimate ancestor/gitdir of) the path the user explicitly selected/reviewed, and refuse to auto-trust redirected paths originating from repository-controlled `.git` gitlink indirection; alternatively, resolve and display the *actual* target path to the user with an explicit confirmation step distinct from the generic "Trust Repository" action, and restrict/validate `.git` gitlink targets (`app/git-info.ts`) to remain within expected boundaries.

### Proof of Concept
1. Attacker creates a repository whose working tree contains a `.git` file (not directory) with content `gitdir: /some/shared/path/owned/by/another/user` (or a relative traversal reaching such a path), mimicking the submodule/worktree gitlink format Desktop already parses in `app/git-info.ts`.
2. Victim clones/opens this repository in GitHub Desktop via `AddExistingRepository`/clone flow, which calls `getRepositoryType(path)` [7](#0-6) .
3. Git resolves `--git-dir` to the attacker-specified path; since that path is owned by a different user, Git emits `fatal: detected dubious ownership in repository at '<attacker path>'`, which Desktop parses into `{ kind: 'unsafe', path: '<attacker path>' }`.
4. The UI shows the generic "add an exception for this directory" prompt; the victim clicks it.
5. `onTrustDirectory` calls `addSafeDirectory('<attacker path>')`, permanently adding the attacker-chosen path to the global `safe.directory` list — a directory the victim never intentionally reviewed or opened.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}

function resolveGitDirectories(gitPath: string): IGitDirectories {
  // eslint-disable-next-line no-sync
  const gitPathStat = Fs.statSync(gitPath)

  if (gitPathStat.isDirectory()) {
    return { gitDir: gitPath, commonGitDir: gitPath }
  }

  // eslint-disable-next-line no-sync
  const gitFileContents = Fs.readFileSync(gitPath, 'utf8')
  const gitDirMatch = /^gitdir:\s*(.+)\s*$/m.exec(gitFileContents)

  if (gitDirMatch === null) {
    throw new Error(
      `Invalid .git file contents in ${gitPath}: ${gitFileContents}`
    )
  }

  const gitDir = Path.resolve(Path.dirname(gitPath), gitDirMatch[1])
  const commonDirPath = Path.join(gitDir, 'commondir')
