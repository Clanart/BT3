### Title
Untrusted `ReceivedOutput` bytes can claim an arbitrary outpoint and value - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` deserializes the spend offset, `TxOut`, and `OutPoint` as three independent attacker-controlled fields without validating that the outpoint identifies a real transaction containing that output. An unprivileged party can therefore submit bytes representing a large payment to a valid Serai-controlled Taproot script while naming a nonexistent or unrelated outpoint.

### Finding Description
`ReceivedOutput` is documented as “a spendable output” and stores the scalar `offset`, the output’s `TxOut`, and its claimed `OutPoint`. [1](#0-0)  Its deserializer sequentially accepts a scalar, a consensus-encoded `TxOut`, and a consensus-encoded `OutPoint`, then returns all three without consistency or provenance checks. [2](#0-1) 

The analogous extraction error is that the claimed spend location is taken from attacker-controlled bytes rather than derived from the transaction being scanned. Legitimate scanner-created values bind the outpoint to the transaction ID and enumerated output index. [3](#0-2)  Deserialized values bypass that binding.

The forged object is accepted into transaction construction: `SignableTransaction::new` trusts `input.outpoint` when building the Bitcoin input and `input.output.value` when calculating available funds. [4](#0-3)  `multisig` only checks that the supplied `TxOut` script corresponds to the offset-adjusted group key; it does not establish that the referenced prevout exists or contains that `TxOut`. [5](#0-4) 

### Impact Explanation
A caller that accepts serialized `ReceivedOutput` values from an untrusted source can be shown funds that do not exist. The fabricated object can report an arbitrary Bitcoin amount and script while pointing to an outpoint that is nonexistent, already spent, or associated with a different output.

If used for spending, this can cause Serai to construct and threshold-sign a transaction spending an invalid prevout. That transaction is unspendable by consensus and will be rejected when broadcast, while the signer already processed the claimed funds.

### Likelihood Explanation
The attack only requires the ability to supply bytes to `ReceivedOutput::read`. No private keys, validator compromise, malformed curve encodings, or blockchain mutation are required. The Taproot script must correspond to `group_key + offset * G` for later signing, but this is publicly computable once the group key is known.

### Recommendation
Do not expose `ReceivedOutput::read` as producing a trusted spendable output. Either:

- make deserialization crate-private and obtain `ReceivedOutput` exclusively from `Scanner::scan_transaction`/`scan_block`;
- rename/document the deserializer as untrusted data requiring chain validation; or
- add an explicit validation API that fetches the referenced transaction and verifies that `outpoint.vout` exists and its `TxOut` equals the serialized output.

Consumers should not use the embedded value, script, or outpoint before that provenance check.

### Proof of Concept
For a scanner/group Taproot script `serai_script`:

```rust
use bitcoin_serai::{
  bitcoin::{
    consensus::encode::serialize,
    Amount, OutPoint, TxOut, Txid,
    hashes::Hash,
  },
  wallet::ReceivedOutput,
};
use k256::Scalar;

// Choose a valid Serai P2TR script and claim it used offset zero.
let mut serialized = Scalar::ZERO.to_bytes().to_vec();

// Claim an arbitrary amount was paid to the valid script.
let claimed_output = TxOut {
  value: Amount::from_sat(1_000_000_000),
  script_pubkey: serai_script,
};
serialized.extend(serialize(&claimed_output));

// Name an unrelated/nonexistent location instead of deriving it from a real
// transaction output index.
let fake_outpoint = OutPoint {
  txid: Txid::all_zeros(),
  vout: 0,
};
serialized.extend(serialize(&fake_outpoint));

// This returns a "spendable" ReceivedOutput despite no such output existing.
let forged = ReceivedOutput::read(&mut serialized.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000_000);
assert_eq!(forged.outpoint(), &fake_outpoint);
```

The object reports one billion satoshis at `fake_outpoint`. Passing it to `SignableTransaction::new` uses that fake location as a transaction input and the fabricated value as available funds.
