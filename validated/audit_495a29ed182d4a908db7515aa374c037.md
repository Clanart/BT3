### Title
Unbounded-length numeric string parsing in legacy JSON precompile `ExtractAsUint256` causes CPU-DoS on trace RPCs - ([File: precompiles/json/legacy/{v552,v555,v562,v603,v605,v606,v610,v614,v620,v640}/json.go])

### Summary
Several legacy versions of the `JSON` precompile's `ExtractAsUint256` method decode an arbitrary-length numeric string extracted from user-controlled call data with `big.Int.SetString(strValue, 10)` without any length cap, unlike the current and `v66`/`v67` implementations which cap `strValue` at 100 characters before conversion.

### Finding Description
The `JSON` precompile is reachable at a fixed address from any EVM contract call. Its `extractAsUint256` method takes a JSON blob and a key, extracts the string value for that key, and converts it to a `big.Int` via `new(big.Int).SetString(strValue, 10)`. In the current implementation and in `v66`/`v67`, the extracted string is bounded to 100 characters: [2](#0-1) [5](#0-4) 

However, ten legacy versions (`v552`, `v555`, `v562`, `v603`, `v605`, `v606`, `v610`, `v614`, `v620`, `v640`) removed or never had this guard, calling `SetString` directly on `strValue` of unbounded length: [6](#0-5) 

`big.Int.SetString` for base-10 decimal input is `O(n²)` in the number of digits (this is the same class of unbounded-length parsing issue as CVE-2016-7416, where ICU's locale/message parser lacked a length restriction on attacker-controlled input). The size of the input JSON blob (`bz`) is only bounded by EVM call-data gas costs, so an attacker can supply tens of KB of digit characters for a modest amount of gas.

These legacy precompile implementations are not dead code: `x/evm/keeper.Keeper.CustomPrecompiles` selects between the latest and historical/legacy precompile implementations based on `ctx.IsTracing()`: [7](#0-6) 
and `GetCustomPrecompilesVersions` picks the specific legacy version that was active at the traced block's height: [8](#0-7) 

This means any historical transaction that called `extractAsUint256` with a large digit string during one of the affected upgrade windows can be re-executed via public tracing RPC methods (`debug_traceTransaction`, `debug_traceBlockByNumber`, `debug_traceCall`), forcing the node to re-run the unbounded `SetString` parse every time that trace is requested.

### Impact Explanation
Because `debug_trace*` endpoints are part of the public EVM JSON-RPC surface and can be invoked repeatedly and freely by any client, an attacker who once (during an affected upgrade window) submitted a cheap transaction invoking `extractAsUint256` with a very large digit string can cause every subsequent trace request against that transaction/block to consume disproportionate CPU on the serving node, degrading RPC availability and potentially delaying block/trace processing on nodes that serve public tracing.

### Likelihood Explanation
The precompile is a fixed, well-known EVM address reachable by any contract call; the missing bound applies to ten historical upgrade versions, several of which were live for meaningful periods and reachable by any transaction sender at the time. Exploitation requires the attacker to have (or be able to get) one qualifying transaction mined and then repeatedly request tracing on it, both of which are unprivileged, public actions.

### Recommendation
Backport the `len(strValue) > 100` (or an equivalent bound) check into all affected legacy `ExtractAsUint256` implementations (`v552`, `v555`, `v562`, `v603`, `v605`, `v606`, `v610`, `v614`, `v620`, `v640`), or add a length guard in the shared tracing dispatch path (`CustomPrecompiles`/`GetCustomPrecompilesVersions`) before invoking any historical precompile version with attacker-controlled string input.

### Proof of Concept
1. Deploy or use an existing contract that calls the `JSON` precompile's `extractAsUint256(bytes, string)` with a JSON payload `{"k":"<N-digit string>"}` where `N` is tens of thousands of characters, during a block height where one of the affected legacy versions (e.g. `v552`) is active per `GetCustomPrecompilesVersions`.
2. Mine the transaction (bounded only by gas for the call-data size).
3. Call `debug_traceTransaction` (or `debug_traceBlockByNumber`) against that transaction's hash via the public JSON-RPC endpoint.
4. Observe that the node spends disproportionately high CPU time inside `big.Int.SetString` while re-executing the legacy precompile's `ExtractAsUint256`, compared to a call using the same-length input against the current (length-capped) implementation.

func (k *Keeper) CustomPrecompiles(ctx sdk.Context) map[common.Address]vm.PrecompiledContract {
	if !ctx.IsTracing() {
		return k.latestCustomPrecompiles
	}
	versions := k.GetCustomPrecompilesVersions(ctx)
	cp := make(map[common.Address]vm.PrecompiledContract, len(k.customPrecompiles))
	for addr, versioned := range k.customPrecompiles {
		cp[addr] = versioned[versions[addr]]
	}
	return cp
}

func (k *Keeper) GetCustomPrecompilesVersions(ctx sdk.Context) map[common.Address]string {
	height := ctx.BlockHeight()
	cp := make(map[common.Address]string, len(k.customPrecompiles))
	for addr, versioned := range k.customPrecompiles {
		mostRecentUpgradeHeight := int64(0)
		noForkHistory := true
		for upgrade := range versioned {
			upgradeHeight := k.upgradeKeeper.GetDoneHeight(ctx, upgrade)
			if upgradeHeight != 0 {
				noForkHistory = false
			}
			if height < upgradeHeight {
				// requested height hasn't seen this upgrade version yet.
				continue
			}
			if upgradeHeight > mostRecentUpgradeHeight {
				mostRecentUpgradeHeight = upgradeHeight
				cp[addr] = upgrade
			}
		}
		if noForkHistory {
			cp[addr] = k.latestUpgrade
		}
	}
	return cp
}
