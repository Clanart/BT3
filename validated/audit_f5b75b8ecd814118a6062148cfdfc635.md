### Title
Silent Git remote host rewrite from unvalidated GitHub API `clone_url` - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` silently rewrites a repository's local Git remote URL using the `clone_url` field returned by the GitHub API, but the guard that decides whether to apply the update only checks that the URL *protocol* (http vs. ssh-style) is unchanged — it never verifies that the *hostname* of the new URL matches the hostname of the existing remote or of the previously-known GitHub repository.

### Finding Description
`updateRemoteUrl` compares `gitStore.defaultRemote.url` to `apiRepo.clone_url` and decides whether to overwrite the local remote: [3](#0-2) 

The three conditions gating the rewrite are:
1. `protocolsMatch` — only compares `URL.parse(url).protocol` for equality (e.g. `https:` === `https:`), not the host.
2. `remoteUrlUnchanged` — checks that the *current* remote still equals the *previously stored* `gitHubRepository.cloneURL` via `urlMatchesRemote`, which itself only compares hostname/owner/name of the two URLs being compared to each other, not to any trusted allowlist: [4](#0-3) 
3. `!urlsMatch` — the incoming `apiRepo.clone_url` differs from the current remote.

None of these three checks constrain the new `clone_url`'s hostname to match the original host the user cloned from. If the GitHub API response object (`apiRepo.clone_url`) that Desktop fetches for the repository is attacker-influenced — e.g. a malicious or compromised GitHub Enterprise Server endpoint, or a man‑in‑the‑middle on an Enterprise account's API traffic — Desktop will overwrite the user's `origin` remote to point at an arbitrary host of the same protocol scheme, with no user confirmation dialog, as long as the user has not manually edited the remote away from what Desktop last recorded.

This mirrors the DeFi report's broken-invariant pattern: a value that should require a consistency check against a trusted reference (SAT-002's tolerance bounds) is instead validated only against itself (old vs. new), letting an attacker-controlled input pass unchecked and produce state corruption — here, the corrupted value is the Git remote URL that determines where the user's next `git push`/`git fetch` goes.

### Impact Explanation
If exploited, an attacker-controlled GitHub API endpoint (realistic for GitHub Enterprise deployments where the API endpoint itself may be attacker-controlled/spoofed, or for accounts pointed at a malicious proxy) can cause Desktop to silently repoint a victim's `origin` remote to an attacker's server. Subsequent pushes would send commits/credentials-bearing traffic (via HTTPS credential helper or SSH) to the attacker's host instead of the legitimate one, and subsequent fetches/pulls would pull attacker-supplied history into the user's working repository — a silent corruption of what the user pushes to/pulls from, without any explicit action or confirmation.

### Likelihood Explanation
This requires the attacker to control the API object Desktop uses to refresh repository metadata (an explicitly in-scope actor per the task's valid-impact list: "attacker controls...a GitHub API object"). It does not require local access, admin rights, or leaked credentials — only that Desktop query a hostile or compromised API endpoint (most plausible for GitHub Enterprise accounts) and that the user had not manually edited their remote away from Desktop's last-known clone URL. I could not confirm the exact frequency/trigger of the calling code path in `app-store.ts` that feeds `updateRemoteUrl` its `apiRepo` argument, so likelihood should be validated further with that context.

### Recommendation
In `updateRemoteUrl`, add a hostname equality check between the existing remote/GitHub-repository endpoint and the incoming `apiRepo.clone_url` before allowing an automatic rewrite (i.e., only allow updates that keep the same host, changing at most owner/name), and/or prompt the user for confirmation whenever the target host changes.

### Proof of Concept
1. User has a repository whose `origin` remote and stored `GitHubRepository.cloneURL` both point to `https://ghe.legit-corp.com/org/repo.git`.
2. The GitHub Enterprise API endpoint used for repository metadata is compromised/spoofed (e.g., DNS hijack, malicious proxy, or a rogue "GitHub Enterprise" account added by the user under attacker influence).
3. The API response for the repository returns `clone_url: "https://ghe.attacker.com/org/repo.git"` (same protocol scheme, different host).
4. `updateRemoteUrl` evaluates `protocolsMatch = true`, `remoteUrlUnchanged = true` (user hasn't touched the remote), `urlsMatch = false` (different host) → calls `gitStore.setRemoteURL('origin', 'https://ghe.attacker.com/org/repo.git')` with no user prompt. [5](#0-4) 
5. The user's next push/fetch silently targets the attacker's host.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
