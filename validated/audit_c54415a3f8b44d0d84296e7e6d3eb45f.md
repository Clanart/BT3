### Title
Untrusted `ReceivedOutput::read` bytes auto-install an unvalidated scalar offset, bypassing the unspendable-script-path invariant and crediting outputs spendable by an attacker script path - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Lite XL bug class — silently treating attacker-supplied embedded data as trusted configuration/executable logic without confirmation — maps onto `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`. It deserializes an arbitrary secp256k1 scalar `offset` plus an arbitrary `TxOut`/`OutPoint` from untrusted bytes and returns a `ReceivedOutput` that downstream code (`SignableTransaction::new`, `multisig`) automatically trusts as group-owned spendable funds. Unlike `Scanner::register_offset`/`scan_transaction`, this path never verifies the offset was securely generated, so the TapTweak "unspendable script path" invariant is lost.

### Finding Description
`Scanner::register_offset` (mod.rs:168-196) documents that "Arbitrary offsets may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script (not by the signature of the key)" and therefore requires offsets be securely generated. `Scanner::scan_transaction` only emits `ReceivedOutput`s whose offset came from that registration, preserving the invariant that `offset = TapTweakHash(x(key))` yields an unspendable BIP-341 script path.

`ReceivedOutput::read` (mod.rs:122-134) bypasses this entirely: it accepts any canonical scalar via `Secp256k1::read_F` and any consensus-decoded `TxOut`/`OutPoint`, with no check that the offset corresponds to a registered, securely-derived tweak. The only downstream guard is in `SignableTransaction::multisig` (send.rs:273-285), which checks `p2tr_script_buf(offset.group_key())? == prevouts[i].script_pubkey`. But `p2tr_script_buf` (mod.rs:80-86) uses `TweakedPublicKey::dangerous_assume_tweaked`, which assumes — without verification — that the internal key already carries the unspendable-taproot tweak. An attacker controlling the serialized bytes trivially satisfies this check by setting `script_pubkey = P2TR(key + offset*G)` for their chosen `offset`, including an `offset` for which they know a valid script-path spend.

The bytes are then "executed" automatically: `SignableTransaction::new` collects `input.offset` (send.rs:176), `multisig` re-keys every participant's view via `keys.clone().offset(self.offsets[i])` (send.rs:276-281), and `TransactionSignMachine::sign` produces BIP-340 signature shares committing to `Prevouts::All` — all without any confirmation that the offset ever passed through `register_offset`.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., a serialized output record transmitted to or stored by a signer) obtains a `ReceivedOutput` the wallet stack treats as spendable group funds. Two concrete consequences:

1. **Funds reported received that are not spendable / drainable.** An output recorded with an attacker-chosen offset whose tweaked key has a real script path is credited to the group, yet is spendable on-chain by the attacker's script-path witness — the group's key-path signature is unnecessary. The wallet reports and may attempt to spend funds that are not actually under sole threshold control.
2. **Signing under an unvetted re-keyed key.** `multisig` builds an `AlgorithmMachine` for `key + offset*G` and `sign` emits shares over `taproot_key_spend_signature_hash` with `Prevouts::All` committing to the attacker-supplied prevout values. The group signs a key-spend for a key whose script path was never bound by TapTweak — i.e., the group attests to outputs whose security assumptions (unspendable script path) do not hold.

This mirrors Lite XL: untrusted embedded content is automatically adopted and acted upon with no confirmation, converting a data-parsing routine into a trust-boundary violation.

### Likelihood Explanation
Reachable whenever a signer/processor ingests serialized `ReceivedOutput`s from a non-scanner source (network buffer, DB, coordinator message). The attacker needs only to construct canonical scalar + `TxOut` + `OutPoint` bytes — no keys, no collusion. Impact requires the fabricated output to pass the `p2tr_script_buf == script_pubkey` check, which the attacker satisfies by construction. Severity is Medium-High: it does not directly extract secret key material, but it credits unsafely-keyed outputs and elicits threshold signatures under a re-keyed key lacking the unspendable-script-path guarantee.

### Recommendation
- Bind `ReceivedOutput` to provenance: either make `read` verify the offset is the BIP-341 `TapTweakHash(x(internal_key))` of the group key (or a registered offset), or restrict deserialization to `Scanner`-produced values.
- In `SignableTransaction::multisig`, additionally verify the tweaked key's script-path commitment: recompute `TapTweakHash` over the internal key and confirm the Merkle root corresponds to the intended (unspendable or registered) tree rather than relying on `dangerous_assume_tweaked`.
- Reject `offset` values in `ReceivedOutput::read` that were not previously registered via `register_offset`, e.g. by deserializing an index into the scanner's offset table instead of a raw scalar.

    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;

      let mut buf_r = BufReader::with_capacity(0, r);
