### Title
Silent, unconfirmed rewrite of a repo's git remote URL based on owner/name repo re-registration ("repo-jacking") - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Beanstalk's bug let an attacker mutate an external, trusted-looking value (deltaB) between two points in a single flow so the victim's legitimate action silently produced a corrupted result (a penalty) instead of the expected one. GitHub Desktop has a structurally identical flow: `repositoryWithRefreshedGitHubRepository` re-resolves a locally tracked repository purely by `owner/name` via `matchGitHubRepository`, fetches the "current" API object for that owner/name, and then feeds that untrusted API object into `updateRemoteUrl`, which will silently overwrite the user's `origin` remote to whatever `clone_url` the API returned — with no user confirmation — as long as a narrow set of guard conditions happen to line up.

### Finding Description
`matchGitHubRepository` resolves a repository identity strictly by parsing the current remote URL into `{hostname, owner, name}` [1](#0-0) , not by any stable GitHub repository ID. This match result is then used in `repositoryWithRefreshedGitHubRepository` to call `api.fetchRepository(owner, name)` [2](#0-1) , which is a live lookup against `repos/{owner}/{name}` on the GitHub API [3](#0-2) .

If the whatever repository originally lived at `owner/name` is deleted, renamed, or transferred away (a routine, attacker-triggerable event: anyone can register a now-vacant `owner/name` slot, or a compromised/malicious collaborator can rename a repo), the API now returns a **different repository object that is entirely attacker-controlled**, but with the identical `owner/name` pair Desktop is still keyed on.

That attacker-controlled `apiRepo` (a "GitHub API object" per the in-scope threat model) is passed straight into `updateRemoteUrl` [4](#0-3) . There:
- `remoteUrlUnchanged` checks that the *previously stored* `gitHubRepository.cloneURL` still matches the current git remote — true, because the user hasn't touched anything.
- `urlsMatch` checks the *new* `apiRepo.clone_url` against the current remote — false, because it now points at the attacker's repo.
- `protocolsMatch` only checks that both URLs use the same `http`/`https` scheme. [5](#0-4) 

When `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is true, Desktop calls `gitStore.setRemoteURL(...)` and **silently rewrites the local `origin` remote to the attacker's clone URL** [6](#0-5) . This refresh path runs in the background (e.g. on account-change refresh via `refreshSelectedRepositoryAfterAccountChange`) with no dialog, confirmation, or diff shown to the user [7](#0-6) .

The comment at the top of the function even flags the authors' own uncertainty about when the guard conditions are actually reachable ("I'm not sure when these early exit conditions would be met") — indicating this path was not hardened against a hostile API object, only against ordinary drift (e.g. GitHub-initiated repo renames that Desktop is meant to auto-follow).

### Impact Explanation
Once `origin` is silently repointed:
- Every subsequent `git push` from the user (via `performPush`, which trusts `state.remote`/`remote.url` without re-validating provenance [8](#0-7) ) sends the user's commits/code to the attacker's repository instead of the legitimate one — silent corruption/exfiltration of what the user pushes.
- Every subsequent `fetch`/`pull` retrieves attacker-controlled history and merges it into the user's working tree, a supply-chain injection vector.
- Because `envForRemoteOperation`/credential resolution keys off the *account* matched to the endpoint hostname (still `github.com`), the user's existing GitHub credentials will be used to authenticate to the attacker's repository over the "legitimate" host, without any new prompt — this is a strict violation of "silent corruption of what the user commits or pushes," which is explicitly in scope.

### Likelihood Explanation
This does not require local/physical access, admin rights, leaked credentials, or unnatural user steps. The precondition is entirely at GitHub's public layer: a repository owner/name pair the user cloned previously must later become associated (via deletion+re-registration, transfer, or rename-then-reuse) with a repository the attacker controls — a well-known, unprivileged "repo-jacking"/"dependency confusion by URL" pattern that is routinely observed on GitHub for abandoned packages/orgs. Desktop's periodic/background repository refresh (`repositoryWithRefreshedGitHubRepository`) triggers this automatically without any user action, so exploitation is passive from the user's perspective once the attacker has claimed the name.

### Recommendation
- Do not silently call `setRemoteURL` from a background refresh. At minimum, key repository identity on the GitHub repository's stable numeric `id` (already stored, see `IDatabaseGitHubRepository.id`/`GitHubRepository`) rather than solely `owner/name`, and treat an `id` mismatch between the previously known repository and the freshly fetched one as a hard signal that the remote should not be auto-updated.
- When a remote-URL auto-update is otherwise justified (e.g., GitHub-side rename of the same repository, verifiable by `id` equality), still surface it to the user as a confirmable banner/dialog rather than mutating `origin` unattended.

### Proof of Concept
1. User clones `https://github.com/victim-org/some-repo` and pushes/pulls normally; Desktop stores the associated `GitHubRepository` (with `cloneURL` = the legitimate URL) and the local git remote `origin` pointing at it.
2. `victim-org/some-repo` is deleted or transferred/renamed (e.g., org disbanded, or the owner renames it), freeing the `victim-org/some-repo` name.
3. Attacker (no privileges needed) creates a new public repository under the exact same, now-available `owner/name` pair, with any `clone_url`.
4. Desktop's background refresh path (`refreshSelectedRepositoryAfterAccountChange` → `repositoryWithRefreshedGitHubRepository`) runs (e.g., on sign-in/out, periodic refresh, or app relaunch), calling `api.fetchRepository('victim-org', 'some-repo')`, which now returns the attacker's repository object.
5. `updateRemoteUrl` sees `remoteUrlUnchanged = true` (nothing local changed), `urlsMatch = false` (new clone_url differs), `protocolsMatch = true` (both https), and calls `gitStore.setRemoteURL('origin', attackerCloneUrl)` with no prompt.
6. The next time the user pushes from Desktop, their commits are silently sent to the attacker's repository using the victim's stored GitHub credentials for that host.

Note: I could not execute this end-to-end in a live GitHub environment from static analysis alone (I could not confirm from code alone whether any additional runtime guard elsewhere short-circuits `repositoryWithRefreshedGitHubRepository` before `updateRemoteUrl` is reached in all app states), so this should be validated by a background Devin agent by running a local integration/unit test against `updateRemoteUrl` and `repositoryWithRefreshedGitHubRepository` with a mocked `apiRepo` representing a different repository at the same `owner/name`.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  public async fetchRepository(
    owner: string,
    name: string
  ): Promise<IAPIFullRepository | null> {
    try {
      const response = await this.ghRequest('GET', `repos/${owner}/${name}`)
      if (response.status === HttpStatusCode.NotFound) {
        log.warn(`fetchRepository: '${owner}/${name}' returned a 404`)
        return null
      }
      return await parsedResponse<IAPIFullRepository>(response)
    } catch (e) {
      log.warn(`fetchRepository: an error occurred for '${owner}/${name}'`, e)
      return null
    }
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
