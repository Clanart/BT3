### Title
Fee/weight calculation ignores the OP_RETURN output it just added, producing an underpriced and potentially non-standard transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds `tx_outs` in two stages: first the payment outputs, then an optional `OP_RETURN` data output. The subsequent weight/vbyte calculation — which determines `needed_fee`, the `NotEnoughFunds` check, the minimum-relay-fee check, and the `TooLargeTransaction` check — is performed against the *first-stage* `payments` slice only, not the actual output set. This mirrors the reported bug class exactly: a post-hoc protection/limit check (fee adequacy, standardness) is computed over the wrong quantity (the pre-`data` outputs instead of the final transaction shape), so it can pass when it should fail.

### Finding Description
In `SignableTransaction::new`:

1. `tx_outs` is populated with all payment outputs, then, if `data` is `Some`, an `OP_RETURN` output (up to 80 bytes of data plus script overhead) is pushed onto `tx_outs` at `send.rs:194-202`.
2. The weight/vbytes are then computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at `send.rs:204` — `payments` does not include the OP_RETURN output, and `calculate_weight_vbytes` builds its mock `Transaction` solely from `payments` and `change` (`send.rs:85-99`). The same omission occurs in the change path at `send.rs:225-226`.
3. Consequently:
   - `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is computed for a transaction ~90+ weight units smaller than the real one. The `TooLowFee` minimum-relay check at `send.rs:211` also uses the underestimated `vbytes`, so a transaction whose *actual* fee rate is below `DEFAULT_MIN_RELAY_TX_FEE` can be accepted.
   - The change-value computation `input_sat - payment_sat - fee_with_change` (`send.rs:228`) under-funds the fee by the same delta, so the resulting signed transaction pays less than the requested `fee_per_vbyte` — the exact analog of "slippage protection accepts the trade even though the user suffered more loss than expected."
   - The `MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` uses `weight` that excludes the data output, so a tx that is actually over the standardness limit can pass the check and be returned as `Ok(...)`.

The fix is to feed the actual `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, i.e., use the output of the first stage in the second-stage check — precisely the remediation in the external report.

### Impact Explanation
When `data` is specified, the produced transaction underpays the fee relative to the caller-specified `fee_per_vbyte` and can fall under the node's minimum relay fee, producing a signed transaction that will not propagate — freezing the associated inputs/plan until reconstructed. It can also produce a transaction exceeding `MAX_STANDARD_TX_WEIGHT` while reporting success. Fee/change/dust math for `bitcoin-serai` is explicitly in scope; the affected quantity (`needed_fee`) is the value the processor relies on via `SignableTransaction::needed_fee`.

### Likelihood Explanation
Triggering requires `data: Some(_)` to be passed to `SignableTransaction::new`. In-tree, the processor passes `None` (`processor/src/networks/bitcoin.rs:450`), so this is reachable only by integrators of the public `bitcoin_serai::wallet` API that attach OP_RETURN data — a caller-controlled public input to a public constructor. The miscalculation is deterministic whenever data is present; likelihood of misuse is moderate, impact is liveness/under-fee rather than direct theft, meriting Medium.

### Recommendation
Compute weight/vbytes over the real output list. Either build the mock transaction from `tx_outs` (plus a hypothetical change output) instead of `payments`, or pass the serialized OP_RETURN size into `calculate_weight_vbytes` and add it to both `weight` and `vbytes` before computing `needed_fee`, the min-relay check, and the change amount. Apply the same fix to the `fee_with_change` branch.

### Proof of Concept
```rust
// networks/bitcoin context: any ReceivedOutput `input`, even parity key
let payments = vec![(p2tr_script_buf(key).unwrap(), 1000)];
let data = vec![0u8; 80]; // max-size OP_RETURN, ~91 extra bytes of tx weight
let tx = SignableTransaction::new(vec![input], &payments, None, Some(data), 1).unwrap();

// tx.tx contains the OP_RETURN output, but needed_fee was computed from
// calculate_weight_vbytes(1, &payments, None) — a tx with only the payment output.
let actual_vbytes = tx.transaction().vsize() as u64;       // includes OP_RETURN
let charged_fee = tx.fee();                                 // == needed_fee
assert!(charged_fee < actual_vbytes * 1);                   // real feerate < requested
// If actual_vbytes pushes past 100 kvB, the tx is non-standard despite the
// TooLargeTransaction check having passed on the truncated weight.
```
Root cause: `send.rs:204` and `send.rs:226` call `calculate_weight_vbytes` with `payments` — the stage-one output set — after `tx_outs` was already extended with the OP_RETURN output at `send.rs:194-202`. [1](#0-0) [2](#0-1) [3](#0-2)
