Based on my research, I found a concrete SSRF analog in the DataLayer mirror/sync subsystem.

### Title
Unauthenticated Server-Side Request Forgery via forged DataLayer mirror coins - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet user can create a "mirror" coin for an **arbitrary** DataLayer `store_id` (launcher_id) that they do not own, embedding attacker-chosen URLs in the coin's memos. Any node that subscribes to that store will later parse the mirror coin, add the attacker URL to its list of trusted sync servers, and issue an outbound HTTP GET to that exact URL with no destination validation — a classic SSRF, functionally analogous to the Appwrite `/v1/avatars/favicon` SSRF where a user-supplied URL is fetched unchecked by the server.

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a mirror coin by simply spending a standard coin and attaching a memo `[launcher_id, *urls]` — there is no on-chain or wallet-side check that the spender actually owns or controls `launcher_id`: [1](#0-0) 

The mirror puzzle itself is a trivial `P2_PARENT.curry(1)` puzzle with no launcher/store binding logic: [2](#0-1) 

Because the memo (containing `launcher_id` and URLs) is attacker-controlled plaintext with no cryptographic or puzzle-level link to the actual DataLayer singleton for that `launcher_id`, any unprivileged spend-bundle submitter can mint a mirror coin claiming to be a server for *any* victim store, e.g. `dl_new_mirror`/`add_mirror` RPCs which just forward to this puzzle: [3](#0-2) [4](#0-3) 

Once this forged mirror coin confirms on chain, any DataLayer node that is subscribed to (or later subscribes to) that `store_id` will treat its URL as a legitimate sync server. `fetch_and_validate()` shuffles and iterates `servers_info` (populated from mirrors) and calls `insert_from_delta_file()` → `download_file()` → `http_download()`: [5](#0-4) [6](#0-5) 

`http_download()` performs an unrestricted `aiohttp` GET against `server_info.url + "/" + filename` with no scheme/host allow-list, no check against private/link-local ranges (e.g. `169.254.169.254` cloud metadata, `127.0.0.1`, internal RPC ports), and reads response headers/body into the requesting node's process: [6](#0-5) 

This is the SSRF root cause: a URL chosen by an unprivileged, unauthenticated (from the victim's perspective) chain participant is dereferenced by the victim node's own network stack.

### Impact Explanation
An attacker can:
- Force victim DataLayer nodes to make outbound requests to internal/private network addresses or cloud metadata endpoints reachable from the node's host, potentially exfiltrating data via response size/timing side channels or triggering unintended actions on internal HTTP services that treat any GET as significant (webhook-style admin panels, internal debug endpoints, etc.).
- Cause repeated connections to arbitrary hosts controlled by the attacker at will, on a schedule (`manage_data_interval`), enabling probing/scanning of the victim's internal network topology (port/service discovery via response codes/timeouts) and potential trigger of internal side effects — impacting any Data Layer client node that has ever subscribed to the targeted store.
- Because ownership of the mirrored `launcher_id` is not verified, the victim's own store (or any store) can be targeted without any interaction from that store's legitimate owner.

This maps to the "Data Layer roots and proofs" and "Data Layer client" reachable-actor category explicitly listed as in-scope, and constitutes concrete unauthorized network-reachable behavior triggered by a cheap on-chain spend from an untrusted party.

### Likelihood Explanation
High likelihood: creating a mirror coin only requires a standard coin spend (`dl_new_mirror`/`add_mirror`) with no special privilege, no ownership proof of the target store, and minimal cost (a small mojo amount + fee). Any node that later subscribes to that `store_id` (a normal, expected DataLayer client action) will automatically pick up and dereference the malicious URL during its periodic sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`), requiring no additional victim interaction beyond normal subscription.

### Recommendation
- Validate mirror URLs before treating them as trusted sync sources: enforce an allow-list of schemes (http/https only), and reject requests to private/link-local/loopback/multicast/metadata IP ranges (RFC1918, `169.254.0.0/16`, `127.0.0.0/8`, etc.) unless explicitly configured by the local operator.
- Consider requiring that mirror-coin creation be provably tied to ownership of the target `launcher_id`/store (e.g., signed by or spent alongside the DataLayer singleton) rather than an arbitrary memo, so third parties cannot advertise mirrors for stores they don't control.
- Apply DNS resolution + connection-time IP checks (not just string/scheme checks) in `http_download()`/`get_downloader()` to prevent DNS-rebinding bypasses of any host allow-list.
- Rate-limit and sandbox outbound DataLayer HTTP fetches (e.g., via a dedicated network namespace/proxy) so SSRF cannot reach node-local RPC/admin ports.

### Proof of Concept
1. Attacker runs `chia data add_mirror --id <victim_store_id> --url http://169.254.169.254/latest/meta-data/ --amount 1 --fee 1` (or calls the `dl_new_mirror`/`add_mirror` RPC directly) using their own funded wallet — `victim_store_id` is any DataLayer launcher_id the attacker does not own. [4](#0-3) 
2. The resulting mirror coin confirms on chain with memo `[victim_store_id, "http://169.254.169.254/latest/meta-data/"]`, produced via `create_mirror_puzzle()`/`create_new_mirror()` with no ownership check. [1](#0-0) 
3. Any node (including the legitimate owner of `victim_store_id`, or any peer) that has an active subscription to `victim_store_id` runs its periodic `fetch_and_validate()` cycle, retrieves the forged `ServerInfo(url="http://169.254.169.254/latest/meta-data/")`, and calls `http_download()`, causing the victim's process to issue a live GET to the attacker-chosen internal/cloud-metadata address. def create_mirror_puzzle() -> Program:
```python
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
