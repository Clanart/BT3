## Missing module/app identity binding in `onAccept` privileged governance handlers - (File: evm/src/core/HostManager.sol / evm/src/apps/BandwidthManager.sol)

### Summary
Both `HostManager.onAccept()` and `BandwidthManager.onAccept()` authorize incoming cross-chain governance actions (host-param updates, revenue withdrawals, bandwidth tier pricing, treasury withdrawals) by checking only that `msg.sender == host` and that `request.source` equals the Hyperbridge chain id. Neither function checks `request.from` — the specific sending module/pallet identity on the source chain — before executing high-risk state changes. [1](#0-0) [2](#0-1) 

### Finding Description
The ISMP request-authentication model in this repo is supposed to bind three things: the calling host contract (`onlyHost`), the source chain (`request.source`), and the specific sending module (`request.from`). `IntentGatewayV2.authenticate()` demonstrates the intended pattern — it explicitly checks `request.from` against a known module instance before trusting the payload: [3](#0-2) 

`HostManager.onAccept()` and `BandwidthManager.onAccept()`, however, skip the `request.from` check entirely:

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
    PostRequest calldata request = incoming.request;
    // Only the Hyperbridge parachain can send requests to this module.
    if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
    OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
    if (action == OnAcceptActions.Withdraw) {
        ...
        IHostManager(_params.host).withdraw(withdrawParams);
    } else if (action == OnAcceptActions.SetHostParam) {
        ...
        IHostManager(_params.host).updateHostParams(hostParams);
    }
}
``` [1](#0-0) 

The same pattern repeats in `BandwidthManager.onAccept()`, which executes `SetTiers`/`Withdraw` actions after checking only `request.source`: [2](#0-1) 

This mirrors the Olympus M-4 bug class exactly: the code enumerates and gates a set of "known" high-risk operations (module upgrade risk levels, policy dependency risk levels) but leaves other equally dangerous operations (kernel migration) unchecked because a *category* of authorization (chain-level source) is treated as sufficient when a finer-grained one (specific sending module identity) is actually required. Here, the binding of chain-id (`source`) is enforced, but the binding of module/app identity (`from`) — which the codebase's own pattern in `IntentGatewayV2.authenticate()` shows is the correct control — is omitted for the two contracts that carry the highest-privilege actions: full host-parameter replacement (`updateHostParams`, which sets `hostManager`, `handler`, `consensusClient`, `admin`) and direct token/native withdrawals.

### Impact Explanation
If any component on the Hyperbridge parachain runtime other than the intended governance pallet (`pallet-ismp-host-executive` / `pallet-bandwidth`) can dispatch an ISMP POST request whose `to` field targets `HostManager` or `BandwidthManager`, it can fully take over host governance: replace `hostManager`, `handler`, or `consensusClient` with attacker-controlled addresses (bricking or hijacking the bridge), or directly drain the `Withdraw` path to any beneficiary/amount. This is a direct violation of the "Cross-chain admin or host-management effects must not be reachable through ... wrong module bindings ... " bounty pivot, and can result in unauthorized execution / fund loss at the highest privilege level in the protocol.

### Likelihood Explanation
Exploitability depends on whether any code path in the Hyperbridge parachain runtime allows dispatching an ISMP POST request with a `to` field equal to `HostManager`/`BandwidthManager` from a module other than the intended one (spoofed `from`), without the same scrutiny given to those pallets' own restricted calls. Because `EvmHost` only checks `restrict(_hostParams.hostManager)` at the *contract* dispatch layer, the security model already relies on `onAccept` re-validating the *module* that produced the request; here that re-validation is missing, so the safety of the whole flow silently depends on assumptions never enforced in code. This is a genuine, reviewable code defect independent of any specific relayer/pallet compromise — the check that should exist (`request.from` binding) simply does not exist, the same class of gap identified as Medium severity in the seed report.

### Recommendation
Add an explicit `request.from` check to `HostManager.onAccept()` and `BandwidthManager.onAccept()`, mirroring `IntentGatewayV2.authenticate()`: store the expected governance module id (e.g. the `pallet-ismp-host-executive` / `pallet-bandwidth` `PalletId`, as already referenced by `PALLET_BANDWIDTH_MODULE_ID`) and require `request.from == expectedModuleId` before dispatching any privileged action, in addition to the existing `source` and `onlyHost` checks.

### Proof of Concept
1. `HostManager` and `BandwidthManager` both only assert `request.source == hyperbridge`; they never compare `request.from` to a known pallet identity, unlike `IntentGatewayV2.authenticate()`.
2. `BandwidthManager` even defines `PALLET_BANDWIDTH_MODULE_ID` as the expected sender constant [4](#0-3)  but never actually compares `request.from` against it in `onAccept`.
3. Any component capable of getting an ISMP POST request routed with `to = address(HostManager)` (or `BandwidthManager`) and `source = hyperbridge` — regardless of which pallet/account authored it — will have its `body` decoded and acted on as governance, executing `updateHostParams` (full host takeover) or `withdraw`/`Withdraw` (fund drain) with no verification that the request actually originated from the intended governance pallet.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
