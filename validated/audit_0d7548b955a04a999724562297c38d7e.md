## Analysis

The Fairside bug's broken invariant is: **a global threshold/config value changes, but per-entity cached state derived from the old threshold is not invalidated, so a security-relevant gating decision (quorum) is computed from a mix of new config + stale cached flags.**

The closest analog in GitHub Desktop is the `cachedRepoRulesets` map in the app store, which backs the repo-rules commit-gating logic.

### Title
Stale, never-invalidated `cachedRepoRulesets` entries let Desktop enforce outdated (weaker) branch/push rules after a ruleset is tightened server-side - ([File: app/src/lib/stores/app-store.ts])

### Summary
`refreshBranchProtectionState` fetches rulesets by id and stores them in `this.cachedRepoRulesets`, but only fetches a ruleset if its id is **not already** in the cache, never re-fetching or invalidating an existing entry: [1](#0-0) 
`_updateCachedRepoRulesets` unconditionally overwrites by id when new fetches happen, but nothing ever proactively refreshes or expires an id that's already cached: [2](#0-1) 

### Finding Description
`parseRepoRules` looks up each rule's `ruleset_id` in the (potentially stale) `rulesets` map and derives `enforced` (`true` vs `'bypass'`) from `ruleset.current_user_can_bypass`: [3](#0-2) 
This directly parallels the `governanceThreshold` bug: the ruleset's `current_user_can_bypass` (an org/repo-admin-controlled "threshold") can be tightened on GitHub.com (e.g., changed from `always` to `never`, or a `RequiredSignatures`/`PullRequest` rule added to an existing ruleset id) without the app ever refetching that id once it's in `cachedRepoRulesets`. The resulting `RepoRulesInfo` (`signedCommitsRequired`, `basicCommitWarning`, `pullRequestRequired`, `creationRestricted`) directly gates whether commits/amends are allowed client-side: [4](#0-3) 
and drives the warning UI that tells the user whether a rule is a hard block or bypassable: [5](#0-4) 

### Impact Explanation
An attacker who controls the GitHub-side ruleset configuration for a repo the victim has cloned (e.g., a malicious/compromised org admin, or an attacker who briefly loosens then tightens a ruleset id) can cause Desktop to keep treating an already-tightened rule as `'bypass'`/looser than it actually is for the remainder of the session, since the ruleset id is never re-fetched once cached. This misleads the user's local commit workflow (`canCommit`/`canAmend`) into believing an action is permitted or bypassable when it is not, and vice versa. Because enforcement is ultimately re-checked by GitHub's server on push, this cannot cause a bypass of the actual protection, but it can cause the client UI to present an incorrect gating decision, confusing the user about whether their commit/branch action will succeed, similar in *kind* (stale derived state driving a security-relevant decision) but weaker in *effect* (no direct fund/commit corruption) than the original finding.

### Likelihood Explanation
Requires a ruleset change to be made mid-session while Desktop already has that ruleset id cached (which happens on first commit-message render, branch checkout, or push) and for the user not to restart Desktop, since the cache is process-lifetime and never expires. This is a plausible but narrow window, and the description explicitly frames this as advisory-only since GitHub enforces server-side.

### Recommendation
Invalidate or time-bound entries in `cachedRepoRulesets` (e.g., re-fetch periodically or when the associated branch protection refresh runs) instead of caching by id indefinitely for the lifetime of the app session.

### Proof of Concept
Not verifiable purely from static code — reproducing requires: (1) cloning a repo with a ruleset R (bypass=`always`) applied to branch `main`; (2) opening Desktop and triggering `refreshBranchProtectionState` so ruleset R is cached; (3) an admin edits ruleset R server-side to bypass=`never` (same ruleset id); (4) without restarting Desktop, attempt a commit to `main` — Desktop's UI still shows the rule as bypassable per the stale cached entry, rather than blocking. I was not able to execute this against a live GitHub API/Desktop instance to confirm behavior end-to-end; this assessment is based on static code reading of the cache logic only.

**Caveat**: This is a weaker analog than the original finding — the original report's impact was a genuine on-chain accounting corruption (fund/vote miscounting) with no downstream re-validation, whereas here GitHub's server always re-validates rules on push, so the worst outcome is a misleading local UI state rather than an actual security bypass or repository corruption. If a stricter reading of "Valid Impact" (requiring code execution, file write/read outside repo, credential exfiltration, or silent commit/push corruption) is applied, this finding does **not** clearly qualify, since no path was found where the stale cache alone lets an attacker cause silent corruption of what's actually committed/pushed or bypass server-enforced protections.

export async function parseRepoRules(
  rules: ReadonlyArray<IAPIRepoRule>,
  rulesets: ReadonlyMap<number, IAPIRepoRuleset>,
  repository: Repository
): Promise<RepoRulesInfo> {
  const info = new RepoRulesInfo()
  let gpgSignEnabled: boolean | undefined = undefined

  for (const rule of rules) {
    // if a ruleset is null/undefined, then act as if the rule doesn't exist because
    // we don't know what will happen when they push
    const ruleset = rulesets.get(rule.ruleset_id)
    if (ruleset == null) {
      continue
    }

    // a rule may be configured multiple times, and the strictest value always applies.
    // since the rule will not exist in the API response if it's not enforced, we know
    // we're always assigning either 'bypass' or true below. therefore, we only need
    // to check if the existing value is true, otherwise it can always be overridden.
    const enforced =
      ruleset.current_user_can_bypass === 'always' ? 'bypass' : true

    switch (rule.type) {
      case APIRepoRuleType.Update:
      case APIRepoRuleType.RequiredDeployments:
      case APIRepoRuleType.RequiredStatusChecks:
        info.basicCommitWarning =
          info.basicCommitWarning !== true ? enforced : true
        break

      case APIRepoRuleType.Creation:
        info.creationRestricted =
          info.creationRestricted !== true ? enforced : true
        break

      case APIRepoRuleType.RequiredSignatures:
        // check if the user has commit signing configured. if they do, the rule
        // passes and doesn't need to be warned about.
        gpgSignEnabled ??=
          (await getBooleanConfigValue(repository, 'commit.gpgsign')) ?? false

        if (gpgSignEnabled !== true) {
          info.signedCommitsRequired =
            info.signedCommitsRequired !== true ? enforced : true
        }
        break

      repoRulesInfo.signedCommitsRequired === true ||
      repoRulesInfo.pullRequestRequired === true ||
