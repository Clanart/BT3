## Finding

### Title
Gasless swap admission only checks `minAmountOut ≥ amountRepay`, not real market slippage, enabling sandwich attacks on `swapForGas` transactions - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
Kaia's gasless module lets an unprivileged sender submit a fee-delegation-like `swapForGas` transaction (KIP-247 `GaslessSwapRouter`) that swaps an ERC-20 token for KAIA on an external AMM to pay for its own gas. The only on-chain-relevant slippage validation performed before admitting the transaction is that `minAmountOut >= amountRepay`, i.e. the swap output only has to cover the gas the node advances. There is no requirement that `minAmountOut` reasonably reflect the current market price of `amountIn`, so a sender (or a naively-built wallet/front-end constructing the tx) can submit a `swapForGas` call whose `minAmountOut` sits only marginally above `amountRepay` while `amountIn` is worth far more. This is functionally identical to the reported bug class: slippage protection can be effectively zero, letting a searcher sandwich the swap and extract nearly all of the value between `amountIn`'s fair value and `amountRepay`.

### Finding Description
`checkBalanceForSwap` in [1](#0-0)  enforces:
```
// tx.minAmountOut >= tx.amountRepay
```
as the sole numeric bound relating `minAmountOut` to anything meaningful; the only other value check is that `amountIn` is sufficient to obtain `minAmountOut` at current price via `routerContract.GetAmountIn` (an optional, config-gated check), shown in [2](#0-1) . Neither check verifies that `minAmountOut` is close to the actual expected output for `amountIn` — it only verifies `minAmountOut` is internally consistent with itself and `amountRepay`. The `SwapArgs.MinAmountOut` value is entirely sender-supplied and decoded verbatim from calldata in [3](#0-2) .

Because `amountRepay` is only the estimated gas cost (three fixed-size legs: approve gas + swap gas + lending overhead, as constructed in the test helper at [4](#0-3) ), it can be a small fraction of the swap's `amountIn` value. A sender (or a compromised/negligent front-end building this transaction on the user's behalf) can set `minAmountOut = amountRepay + ε`. This transaction is a valid, publicly broadcastable transaction that any block proposer will accept into the pool (the check only rejects the tx if `minAmountOut < amountRepay`, per the test assertion in [5](#0-4) ), so it propagates through the public mempool where any MEV searcher can observe and sandwich it — exactly the risk pattern described in the external report: a swap with effectively no meaningful slippage floor is executed on an AMM, permitting front-running/back-running to capture almost the entire trade value beyond the minimal `amountRepay` floor.

### Impact Explanation
An attacker (an ordinary, unprivileged mempool observer / MEV searcher) can sandwich a `swapForGas` transaction whose `minAmountOut` was set just above `amountRepay`, extracting the difference between the token's fair value and the bare minimum needed to satisfy the gasless-lending repayment check. The victim (the gasless transaction's sender) suffers direct, unauthorized value loss — their ERC-20 tokens are swapped for far less KAIA than the market rate, with the surplus captured by the sandwiching searcher. This is a concrete unauthorized value movement from an ordinary end user to a third party, reachable purely by submitting a single public transaction.

### Likelihood Explanation
This requires no validator or node collusion: any wallet/front-end integration that (a) doesn't independently add its own generous slippage margin, or (b) is itself malicious/negligent, can produce such a transaction, and any public searcher monitoring the mempool for `swapForGas` calls can react to it. The gasless module's mempool-level check (`checkBalanceForSwap`) explicitly treats `minAmountOut >= amountRepay` as sufficient, so it neither warns nor blocks such transactions.

### Recommendation
Enforce a real slippage bound in `checkBalanceForSwap` (or in the on-chain `GaslessSwapRouter`) that ties `minAmountOut` to the router's live quote for `amountIn` (e.g., `minAmountOut >= router.getAmountOut(amountIn, token) * (1 - maxSlippageBps)`), not merely to `amountRepay`. This mirrors the referenced remediation pattern of deriving a market-based minimum output rather than accepting an arbitrary sender-supplied floor.

### Proof of Concept
1. Sender crafts a `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` transaction where `amountIn` corresponds to a token amount worth, e.g., 100x `amountRepay`, but sets `minAmountOut = amountRepay + 1`.
2. `checkBalanceForSwap` ( [6](#0-5) ) accepts the tx into the pool since `minAmountOut >= amountRepay`.
3. A searcher observes the pending tx, front-runs it by buying the output token on the same AMM pool to push the price up, lets the victim's swap execute near `minAmountOut`, then back-runs by selling, capturing the price difference — the victim's swap still succeeds on-chain (since `minAmountOut` is trivially low) but receives far less KAIA than fair value. 	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}
