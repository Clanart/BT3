`SignableTransaction::new` computes the change residual and the minimum-fee check from a weight that omits the OP_RETURN data output, so the funded change is over-credited and the resulting transaction can be unbroadcastable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a residual/change amount computed against the wrong quantity (WETH balance when the deposit was consumed as ETH), yielding a refund of 0 and stranded funds. The same bug class exists in Serai's Bitcoin wallet: `SignableTransaction::new` adds an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` to the transaction, but computes the transaction weight/vbytes — and therefore `needed_fee`, the dust/change decision, and the change output's value — from `payments` and `change` only, omitting the data output entirely. The "residual" (change) is therefore computed against a fee that does not reflect the actual signed transaction, mirroring the "balance measured in the wrong token" accounting error.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` when `data` is present, but the fee math only ever calls `calculate_weight_vbytes(tx_ins.len(), payments, change)`:

```rust

  tx_outs.push(TxOut {
    value: Amount::ZERO,

  })
}

  Err(TransactionError::TooLowFee)?;
}

Because the real transaction is larger than the one measured, the actual implied fee rate `fee() / real_vsize` is lower than `fee_per_vbyte` requested, and `fee()` can fall below `DEFAULT_MIN_RELAY_TX_FEE * real_vsize / 1000` even though the `TooLowFee` check passed against the understated `vbytes`. ### Impact Explanation
- The change output is over-credited by the uncounted OP_RETURN weight; the transaction's true fee is `fee_with_change`, which is less than `fee_per_vbyte * actual_vsize`. This is the direct analog of refunding the residual measured in the wrong unit.
- In the worst case (low `fee_per_vbyte`, large `data`), the signed transaction is below the Bitcoin Core minimum relay fee. Nodes reject it, so the threshold-signed transaction spending all selected `inputs` cannot be broadcast — the inputs' funds are effectively locked behind an invalid transaction until the wallet re-signs with corrected fee math, i.e. loss of availability of the funds and wasted signing rounds.
- Conversely, with no change output, the construction is self-correcting but the declared `needed_fee()` reported to callers is wrong, breaking any accounting that relies on it.

### Likelihood Explanation
`data` is a public, caller-controlled parameter of `SignableTransaction::new` (any integrator embedding arbitrary data, e.g. an `InInstruction`, reaches this path), and change is the common case, so the miscalculation is exercised on ordinary usage whenever both are present. Exploitation/reachability does not require any privileged position — only a transaction built with an OP_RETURN payload plus change.

### Recommendation
Include the OP_RETURN output in the transaction used for weight estimation (build `tx_outs` first, including the data output, and pass it to `calculate_weight_vbytes` instead of reconstructing outputs from `payments`). Additionally, after finalizing `tx_outs`, recompute the true vsize and re-check `DEFAULT_MIN_RELAY_TX_FEE`, and report `needed_fee` based on the final transaction.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
```
