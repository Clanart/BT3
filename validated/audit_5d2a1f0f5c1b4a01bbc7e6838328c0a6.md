### Title
Copilot AI merge-conflict resolutions are applied to disk using a stale write-time check instead of the same invariant enforced at validation-time - ([File: app/src/lib/stores/app-store.ts])

### Summary
The external report's bug class is: an invariant check is computed and enforced over one representation of "what will happen" (Seaport's `totalExecutions` array), while the code that actually performs the effect can diverge from that representation (self-transfers that never appear in the array). GitHub Desktop's Copilot-assisted merge-conflict-resolution feature has a structurally similar gap: the set of file paths the model is allowed to touch is validated once, at generation time, against a snapshot of conflicted files, but the code that actually writes to disk and stages the result re-uses that already-validated list at a later point in time without re-deriving/re-checking the invariant against the *current* state.

### Finding Description
`validateResolutionPaths` in `app/src/lib/copilot-conflict-resolution.ts:473-521` is the security-relevant invariant: it throws unless the LLM's returned resolution paths are exactly the `expectedFiles` set (no unexpected paths, no duplicates, no missing files, correct hunk counts) [1](#0-0) . This check runs inside `CopilotStore.resolveChunk` immediately after parsing the model's response [2](#0-1) .

The validated result (`copilotResolutions`) is then stored in `multiCommitOperationState` and is not applied to disk until the user later clicks "Continue Merge" in the result dialog, which calls `_applyCopilotConflictResolutions` [3](#0-2) . That function re-derives the absolute path with `resolveWithin` (a good path-traversal guard) but the *only* re-check against current repository state is:

```
const onDiskFile = state.changesState.workingDirectory.files.find(
  f => f.path === resolution.path
)
if (
  onDiskFile !== undefined &&
  isConflictedFileStatus(onDiskFile.status) &&
  !hasUnresolvedConflicts(onDiskFile.status)
) {
  continue
}
``` [4](#0-3) 

This guard only skips a write when `onDiskFile` **exists** and is a resolved conflict. It does **not** verify that `resolution.path` is still part of the active conflict set at all. If `onDiskFile` is `undefined` — because the working directory changed between the time the resolution was generated/validated and the time the user confirms it (e.g., the conflict set shrank, the operation state was reused, or the file simply isn't reported by `git status` at that moment) — the code falls straight through to:

```
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
``` [5](#0-4) 

and then stages it with `git add -- <path>` [6](#0-5) .

This is the corrupted invariant: `validateResolutionPaths` guarantees "the model may only touch files that were genuinely conflicted **at prompt-build time**," but `_applyCopilotConflictResolutions` executes writes based on that already-consumed guarantee without re-confirming the file is still (or ever independently) an active conflict at **apply time**. Exactly like the Seaport bug — where the invariant check operated on a list that didn't reflect the actual on-chain state because self-transfers were excluded from it — here the write path trusts a list that was correct for a state that no longer necessarily holds.

### Impact Explanation
Since the file content that gets written is attacker-influenceable (the model resolves conflicts by reading conflict-marker content taken directly from the cloned/fetched repository, and prompt-injection payloads embedded in a malicious branch's conflicting hunks/commit messages/PR descriptions are a known attack surface for LLM-driven tools), a path returned by the model that survives `validateResolutionPaths` at generation time but is no longer tracked as a conflict at apply time would be written to disk and silently `git add`-ed with no further review, UI confirmation, or diff shown to the user for that specific file. This matches the "silent corruption of what the user commits or pushes" impact category: a file outside what the user believes they are resolving/committing gets modified and staged without their awareness.

### Likelihood Explanation
This is a narrower and lower-confidence analog than the original Seaport finding. I confirmed the structural gap in the write-time re-check with direct code evidence, but I could not fully trace, within the available index, every state transition under which `multiCommitOperationState.copilotResolutions` could become stale relative to `workingDirectory.files` while still being accepted by the "Continue Merge" button (e.g., whether the abort/retry/re-run flows always regenerate and re-validate `copilotResolutions`, or whether a merge/rebase re-scan could shrink the conflict set while a previously computed resolution list persists in state). That timing window is the crux of exploitability and remains unverified. Given the requirement in the Copilot SDK session (`availableTools: []`, `onPermissionRequest: reject`) and the fact that `validateResolutionPaths` is otherwise strict, this is a plausible but not confirmed-exploitable gap.

### Recommendation
Re-validate `resolution.path` against the *current* conflict state (or discard/re-fetch conflict context) immediately before writing in `_applyCopilotConflictResolutions`, rather than relying solely on the one-time `validateResolutionPaths` check performed at generation time. Specifically, only allow a write when `onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status)`, and treat `onDiskFile === undefined` as a reason to skip (with a warning), symmetric to how "already externally resolved" is handled.

### Proof of Concept
Not independently verified end-to-end; the concrete reachable code gap is:
1. Start a merge/rebase with conflicts in files `A` and `B`; invoke "Resolve with Copilot." `validateResolutionPaths` accepts a resolution set for `{A, B}` because they matched `expectedFiles` at that time [7](#0-6) .
2. Before clicking "Continue Merge," cause the working-directory conflict list to no longer include `A` (e.g., the multi-commit operation state is retained across an abort/retry cycle, or another async status refresh changes `workingDirectory.files`).
3. Click "Continue Merge." `_applyCopilotConflictResolutions` iterates `copilotResolutions`, finds `onDiskFile === undefined` for `A`, does not skip, and writes/stages `resolution.resolvedContent` for `A` anyway [8](#0-7) .

The write and staging code paths were directly verified; the specific state-transition sequence to reach step 2 was not exhaustively confirmed against the full state-management code for multi-commit operations.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
