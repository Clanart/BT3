### Title
Unbounded recursive puzzle-layer matching in wallet outer-puzzle drivers causes stack-overflow crash on attacker-crafted offers/spends - ([File: chia/wallet/outer_puzzles.py])

### Summary
`match_puzzle()` and the various outer-puzzle driver `match()`/`get_inner_puzzle()`/`get_inner_solution()`/`construct()`/`solve()` implementations (`CATOuterPuzzle`, `OwnershipOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `CROuterPuzzle`) recurse into each successive inner puzzle layer with no depth limit, driven entirely by attacker-controlled puzzle structure. A malicious offer file or coin spend containing a puzzle reveal with an arbitrarily deep chain of recognized outer-puzzle layers (e.g., CAT-inside-CAT-inside-CAT…, or nested ownership layers) drives unbounded Python recursion, causing a stack overflow/`RecursionError` that crashes the processing wallet — the same bug class as the reported Suricata SWF stack overflow (unbounded recursive decompression of attacker-supplied nested/compressed data with no depth cap).

### Finding Description
`match_puzzle()` in [1](#0-0)  iterates driver `match()` implementations. Each driver, on a match, recursively calls back into `self._match(...)` (which is `match_puzzle` itself) on the puzzle's inner layer to build the nested `also` chain, e.g. in `CATOuterPuzzle.match`: [2](#0-1) 

and similarly in `OwnershipOuterPuzzle.match`/`get_inner_puzzle`/`get_inner_solution`/`solve`, which recurse through `self._match`, `self._get_inner_puzzle`, `self._get_inner_solution`, `self._solve`/`self._construct` for every "also" layer: [3](#0-2) 

None of these recursive paths enforce a maximum nesting depth. The recursion depth is fully determined by how many recognizable outer-puzzle layers (CAT/ownership/singleton/metadata/CR) an attacker curries into a single puzzle reveal. Because CLVM puzzle construction/currying has no such depth restriction and the mempool/consensus layer does not bound puzzle "layering" depth (only CLVM cost, which a deeply nested but cheaply-executing puzzle does not necessarily exhaust), an attacker can build a puzzle reveal with thousands of nested recognized layers.

This puzzle reveal reaches wallet code entirely through untrusted, attacker-supplied data in normal flows:
- An offer counterparty crafts an `Offer` whose `_bundle.coin_spends` include such a puzzle; when a wallet user's client calls `Offer.__post_init__` (invoked whenever an `Offer` object is constructed/parsed from an offer file) it calls `compute_spend_hints_and_additions`, and downstream offer methods such as `Offer._get_offered_coins()` call `match_puzzle(parent_puzzle)` directly on each `CoinSpend.puzzle_reveal` from the untrusted bundle: [4](#0-3) 

- `Offer.from_spend_bundle()` also calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` on every coin spend of an externally supplied bundle: [5](#0-4) 

Because Python's default recursion limit (~1000 frames) is far lower than the trivially achievable CLVM currying depth an attacker can construct, this is a real, remotely-triggerable stack exhaustion — not merely a resource/performance issue — that terminates the wallet process (or a Python thread within it) with an unhandled `RecursionError`, halting further transaction processing.

### Impact Explanation
This maps to the "spend-triggered transaction-processing halt" category explicitly accepted by the validation rules. A wallet user opening/parsing an untrusted offer file, or any code path that runs `match_puzzle`/`Offer.from_spend_bundle` on an attacker-supplied `SpendBundle`, can be crashed via an unhandled `RecursionError`, denying service to that wallet and any queued operations. This is comparable in severity to the Suricata CVE: unauthenticated crash of the processing engine via crafted attacker-controlled recursive input, no direct fund theft but a functional denial of service against a wallet component participating in offers/trades.

### Likelihood Explanation
Likelihood is high for any wallet user who evaluates offers received from untrusted counterparties, which is the normal, expected usage pattern of the offer/trade system (`chia wallet take_offer`, GUI offer preview, `Offer.from_spend_bundle`/`Offer.__post_init__`). No signature, fee, or special privilege is required to craft such a puzzle reveal — only the ability to curry a puzzle with many nested recognized outer layers, which is standard CLVM puzzle construction available to any user.

### Recommendation
Add an explicit recursion/nesting depth limit (e.g., a bounded counter threaded through `match_puzzle`, `construct_puzzle`, `get_inner_puzzle`, `get_inner_solution`, and each outer-puzzle driver's recursive calls) and reject/return `None` once the limit is exceeded, mirroring the fix pattern in the referenced Suricata patch (bound recursive descent by a hard depth cap independent of stack size). Alternatively, convert the outer-puzzle matching/traversal to an explicit iterative loop instead of language-level recursion so that attacker-controlled nesting cannot exhaust the call stack. Also consider validating/limiting puzzle "also"-layer depth when accepting `Offer` objects and coin spends from untrusted sources (offer files, taken offers) before ever calling into `match_puzzle`.

### Proof of Concept
Conceptual PoC (not run, but structurally supported by the code above):
1. Build an inner puzzle `P0` (e.g., `1` or any valid puzzle).
2. Repeatedly wrap it N times (N ≈ 5,000–100,000, well within CLVM's ability to curry/construct) using `construct_cat_puzzle`/`CAT_MOD` currying (or `puzzle_for_ownership_layer`) so that the puzzle reveal contains N nested recognizable outer-puzzle layers: `Pn = CAT(tail, CAT(tail, CAT(tail, ... P0)))`.
3. Create a `CoinSpend` with `puzzle_reveal = Pn` and any accompanying solution, and place it into a `WalletSpendBundle`/`Offer` object (e.g. serialize as an `.offer` file, or hand-construct via `Offer.from_spend_bundle`).
4. Have a victim wallet parse this offer/spend bundle, triggering `Offer.__post_init__` → `Offer._get_offered_coins()`/`Offer.from_spend_bundle()` → `match_puzzle()` → `CATOuterPuzzle.match()` → `self._match(...)` recursively N times.
5. Once N exceeds Python's recursion limit, the call stack overflows and the wallet process crashes with an unhandled `RecursionError`, halting the wallet's transaction processing.
