### Title
Scanner misclassifies externally-sent payments to internal offset scripts as internal `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner` maps registered offset scripts to `Scalar` offsets in a `scripts: HashMap<ScriptBuf, Scalar>` and reports any transaction output paying to a registered script as a `ReceivedOutput` carrying that offset, with no check of provenance. An unprivileged third party can send a payment directly to a script reserved for an internal purpose (branch, change, forwarded output), and the scanner will classify the output under that internal offset, identical to an output the protocol itself produced — the same class of "attacker-controlled value interpreted in a trusted category" flaw as CVE-2024-10963's hostname confusion in `pam_access`.

### Finding Description
`Scanner::register_offset` inserts `p2tr_script_buf(key + G*offset)` into `self.scripts` keyed only by `ScriptBuf` [1](#0-0) . `Scanner::scan_transaction` then performs a pure `self.scripts.get(&output.script_pubkey)` lookup and emits a `ReceivedOutput` whose `offset` field is claimed to be "the scalar offset to obtain the key usable to spend this output" [2](#0-1) . `ReceivedOutput` carries no marker distinguishing an output the protocol itself created (e.g., its own change or a forwarded output it produced) from an output an arbitrary third party created by paying to the same well-known, publicly derivable address [3](#0-2) . There is no mechanism — script structure, amount check, or origin metadata — to distinguish provenance; classification is by destination alone.

### Impact Explanation
Consumers of `Scanner`/`ReceivedOutput` use the offset to determine the *kind* of output received (external deposit vs. internal branch/change/forwarded output). A third party who sends funds to the address reserved for an internal purpose causes the scanner to report an externally-originated payment as an internally-typed output. Downstream, that output is eligible for the same handling (aggregation, scheduling, presumed-protocol origin) as genuine internal outputs, corrupting accounting and enabling an attacker to inject outputs into internal-only flows. This is an integrity violation reachable by any party able to broadcast a Bitcoin transaction, requiring no key material or protocol participation.

### Likelihood Explanation
All registered scripts are deterministic P2TR addresses derived from the group key and known offsets, so any observer can compute and pay to them. Sending a transaction to such an address costs only the transaction amount plus fees. The scanner performs no provenance check by design, so the misclassification occurs deterministically whenever such a payment confirms.

### Recommendation
Distinguish provenance for offset-derived scripts: either reserve offset scripts exclusively for outputs the protocol itself produced and reconcile them against expected internal transactions (TXID/outpoint allowlists built when the protocol constructs the transaction), or tag `ReceivedOutput` with whether the script corresponds to the zero-offset external deposit path vs. an internal offset so callers can reject externally-created payments to internal addresses. Document that `scripts` membership only proves destination, not origin.

### Proof of Concept
1. The protocol registers an internal offset via `Scanner::register_offset`, producing script `S = p2tr_script_buf(group_key + G*offset)`.
2. An unprivileged attacker derives `S` from the public group key and broadcasts a transaction `tx` with an output paying ≥ dust to `S`.
3. `scan_block`/`scan_transaction` returns `ReceivedOutput { offset, output, outpoint }` indistinguishable from a protocol-created internal output [4](#0-3) .
4. The output is processed under the internal output type, despite originating entirely outside the protocol.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
