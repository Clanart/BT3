### Title
Silent auto-rewrite of the `origin` remote URL from untrusted GitHub API data allows repository-hijack redirection of fetch/push - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop periodically refreshes the cached metadata for a repository, it calls `updateRemoteUrl()`, which silently rewrites the local `origin` remote to whatever `clone_url` the GitHub API now reports for that `owner/name` pair, with no user confirmation. Because the only safeguards are "protocol still matches" and "the remote hasn't been manually edited since we last cached it," an attacker who controls the GitHub-side repository object addressed by the previously-matched `owner/name` (e.g., via repo-name squatting after a rename/deletion, or a compromised/malicious org repo) can cause Desktop to silently redirect the user's local git remote to attacker infrastructure, corrupting where the user's future fetches/pushes go.

### Finding Description
`repositoryWithRefreshedGitHubRepository` re-resolves the GitHub repository for a locally tracked repo by calling `api.fetchRepository(owner, name)` and, if the repository already has a cached `gitHubRepository`, invokes `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

`updateRemoteUrl` performs the actual rewrite: [2](#0-1) 

The only checks performed before rewriting are:
1. The URL protocol (http vs ssh) is unchanged.
2. The *currently configured* local remote URL still matches the previously cached `gitHubRepository.cloneURL` (i.e., the user hasn't manually customized the remote since the last refresh).

If those two conditions hold and the newly fetched `apiRepo.clone_url` differs from what's configured, Desktop calls `gitStore.setRemoteURL(...)`, which runs `git remote set-url` directly against the working copy with **no user prompt**: [3](#0-2) [4](#0-3) 

Critically, this differs from how Desktop treats *upstream* remote changes for forks, where the equivalent situation explicitly shows a confirmation dialog (`UpstreamAlreadyExists`) before touching the remote: [5](#0-4) 

No such gate exists for the primary `origin` remote update path. The repository match itself is keyed purely on `owner`/`name` strings parsed from the current remote URL, not on any GitHub-side repository ID: [6](#0-5) 

and the API lookup is a simple `GET repos/{owner}/{name}` call whose response is trusted as-is: [7](#0-6) 

So the broken invariant is: **"the local `origin` remote URL should only change via explicit user action,"** but in practice it is silently mutated based on an unauthenticated identity assumption (same `owner/name` string ⇒ same repository) rather than a stable repository identifier, and with no user notification comparable to the `UpstreamAlreadyExists` flow used elsewhere.

### Impact Explanation
If GitHub reports a new `clone_url` for the `owner/name` the user's repo was last matched against — which happens naturally when a repository is renamed, transferred, deleted-and-recreated, or when the same `owner/name` slot is later reused by a different party — Desktop will automatically point the user's `origin` remote at that new URL without any confirmation. Because the check only verifies that the *user* hasn't manually edited the remote, and not that the repository is still "the same" repository, an attacker who can cause `fetchRepository(owner, name)` to return a URL under their control (e.g. by taking over a vacated `owner/name`, or an org repo being intentionally repointed) achieves a silent redirection of the victim's git operations:
- Future `git fetch`/`git pull` performed by Desktop retrieve objects from attacker-controlled infrastructure, enabling injection of malicious commits/files into the user's working tree.
- Future `git push` sends the user's local commits — potentially private source code — to the attacker's server, which is a form of code/data exfiltration.

This matches the class of "silent corruption of what the user commits or pushes" and "attacker controls a GitHub API object" described in the report's valid-impact criteria.

### Likelihood Explanation
The precondition (protocol unchanged + local remote URL still equal to the previously cached `cloneURL`) is the common case, since most users never hand-edit their `origin` remote. The refresh path runs automatically as part of Desktop's routine repository/background refresh cycle (`repositoryWithRefreshedGitHubRepository`), requiring no user interaction beyond having the repository open in Desktop with network access. The attacker-side requirement — causing the GitHub API to report a different `clone_url` for the same `owner/name` — is realistic in real-world scenarios such as repository-name squatting after a legitimate rename/deletion, or malicious changes made by an org/repo owner that a fork or clone still references by name. No local access, admin rights, or prior malware is needed.

### Recommendation
- Before silently rewriting `origin`, verify repository identity using a stable identifier (e.g., GitHub repository `id`) rather than trusting `owner/name` continuity alone; if the underlying repository ID has changed, treat it as a different repository and do not auto-migrate the remote.
- Surface a confirmation dialog to the user before changing the `origin` URL, mirroring the existing `UpstreamAlreadyExists` pattern used for upstream remotes, instead of calling `gitStore.setRemoteURL` unconditionally inside `updateRemoteUrl`.
- Log/emit a visible notification when an automatic remote URL change occurs so users can detect unexpected redirection.

### Proof of Concept
1. User clones `https://github.com/acme/widget.git` in Desktop; Desktop caches `gitHubRepository.cloneURL = https://github.com/acme/widget.git` and configures `origin` to the same URL.
2. The `acme/widget` repository is deleted or transferred away, and an attacker creates a new repository at the same `owner/name` slot (`acme/widget`) with `clone_url` pointing to an attacker-controlled git host reachable over HTTPS (satisfying the protocol-match check).
3. On the next periodic refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('acme', 'widget')`, which returns the attacker's `clone_url` [1](#0-0) .
4. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (local remote still equals cached `cloneURL`) and `protocolsMatch === true`, so it calls `gitStore.setRemoteURL(...)` with the attacker's URL, with no prompt shown to the user [8](#0-7) .
5. The next `git fetch`/`git push` performed through Desktop silently talks to the attacker's server.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
