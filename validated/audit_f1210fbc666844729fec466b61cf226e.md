### Title
Cross-chain order settlement permanently strands user-escrowed collateral if the solver's fixed beneficiary address becomes unable to receive the payout - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s cross-chain fill path splits settlement into two independent legs, on two different chains, joined only by an immutable `WithdrawalRequest.beneficiary` fixed at fill time. If that beneficiary address (the solver's `msg.sender`) becomes unable to receive the escrowed input token by the time the settlement message lands on the source chain — because the token is a blocklist-capable ERC-20 (USDC/USDT-style) or the solver used a contract address that cannot receive native value — the source-chain `_withdraw` call reverts every time it is attempted, and the destination-chain fill record permanently blocks the only alternate recovery path (source-side cancellation). The user's original escrowed collateral is then locked in the gateway contract forever, exactly the invariant break identified in the referenced report: a receiver chosen without any liveness/deliverability guarantee, whose transfer failure freezes funds that were already irrevocably committed in an earlier step.

### Finding Description
When a solver fills a cross-chain order on the destination chain, `_fillCrossChain` immediately marks the order filled locally (`_filled[commitment] = msg.sender`) and dispatches a `RedeemEscrow` request back to the source chain whose `WithdrawalRequest.beneficiary` is hard-coded to `msg.sender` (the filling solver's address) — see [2](#0-1) . This beneficiary can never be changed after dispatch; it travels unauthenticated-by-liveness through Hyperbridge to the source chain.

On the source chain, `onAccept` authenticates only that the message came from the registered destination gateway instance, then calls `_withdraw`, which unconditionally attempts `IERC20(token).safeTransfer(beneficiary, amount)` (or a native `.call`) — see [3](#0-2) . If that transfer reverts (blocklisted address on a USDC/USDT-style token, a paused token, or a non-payable contract for a native-token order), the entire `onAccept` transaction reverts. Because Solidity reverts are atomic, `_filled[commitment]` on the source chain is never set, and the escrow decrement (`_orders[commitment][token] -= amount`) never persists — meaning every future relayer resubmission of the same message will hit the exact same revert, forever.

The only alternative recovery path, cancellation from the source chain (`_cancelFromSource`), dispatches a Hyperbridge GET request to read the destination chain's `_filled[commitment]` slot; `onGetResponse` reverts with `Filled()` whenever that slot is non-empty — see [5](#0-4) . Since the destination chain already recorded `msg.sender` (the solver) as the filler the moment the fill transaction succeeded, this slot is permanently non-empty, so cancellation is permanently blocked too.

The result: the user's original escrowed input tokens (`order.inputs`) have no code path left that can ever release them. Unlike the same-chain fill path, where the transfer to `beneficiary` and the escrow release happen atomically in one transaction (so a failing transfer simply reverts the whole fill with no state change), the cross-chain path splits the same operation across two chains and a message-passing layer, so the destination-side "fill happened" fact becomes permanently true and irreversible before the source-side payout is ever validated to be deliverable.

### Impact Explanation
This is a direct "fund loss/lock" impact under the bounty's live categories. The user's escrowed collateral (which can be arbitrarily large, unrelated to the solver's own output delivery) becomes permanently unrecoverable, with no governance, admin, or manual override in the contract to redirect the stuck `WithdrawalRequest.beneficiary` or force a settlement to an alternate address. This matches the structure of the referenced report precisely: a receiver address is fixed at an early, irrevocable step, and its later inability to receive funds locks value that a different party (here, the order's original placer) already committed.

### Likelihood Explanation
No malicious relayer, prover, governance actor, or leaked key is required. Any solver whose address is later blocklisted by the token issuer between the destination-chain fill (step 1) and the source-chain settlement delivery (step 2, which is delayed by Hyperbridge's mandatory challenge/finality period) will trigger this permanently. It can also be deliberately triggered by an unprivileged solver who fills an order using a smart-contract address with no `receive()`/payable fallback when the order's inputs include the native token, guaranteeing the source-side `.call{value: amount}("")` in `_withdraw` reverts every time, permanently freezing that order's escrow with no recovery — a low-cost, single-transaction griefing vector against any order's escrowed collateral.

### Recommendation
Decouple escrow release from a single hard-coded beneficiary picked at fill time. Options: (1) use a pull-based claim pattern where the solver (or a re-specified beneficiary, signed for separately) withdraws credited amounts from a per-address balance rather than a push `transfer`/`call` embedded in the cross-chain message; (2) if a push transfer to the recorded beneficiary fails, fall back to crediting an internal claimable balance for that beneficiary instead of reverting the whole `onAccept`, so the settlement still finalizes and the escrow decrements; (3) add an expiry-based reclaim path so that if settlement cannot be completed within a bounded window, the original order placer can recover the input escrow directly, independent of the destination chain's `_filled` state.

### Proof of Concept
1. Order creator places a cross-chain order on chain A (source) escrowing `1,000 USDC` as `order.inputs`, targeting chain B (destination) for `900 DAI` output.
2. An attacker/solver deploys a minimal contract on chain B with no `receive()`/payable `fallback()` (or simply uses an address they know is about to be added to `USDC`'s blocklist on chain A).
3. The attacker calls `fillOrder`/`_fillCrossChain` from that contract address on chain B, honestly delivering the required `900 DAI` to `order.output.beneficiary` (satisfying all destination-side checks) — see `_fillCrossChain` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171`. This sets `_filled[commitment] = <attacker contract>` on chain B and dispatches a `RedeemEscrow` message with `beneficiary = <attacker contract>` back to chain A.
4. After the Hyperbridge challenge period, a relayer delivers the message to chain A's `onAccept`, which calls `_withdraw`. Because `<attacker contract>` cannot receive native value (or is blocklisted for the ERC-20 case), `IERC20(token).safeTransfer`/the native `.call` reverts, reverting the entire `onAccept` transaction — see `IntentsBase._withdraw` at `evm/src/apps/intentsv2/IntentsBase.sol:390-410`.
5. Every subsequent relayer resubmission of the identical message reverts identically; `_filled` on chain A is never set and the `1,000 USDC` escrow is never decremented.
6. The order creator attempts `_cancelFromSource` on chain A; the resulting GET response finds chain B's `_filled[commitment]` slot non-empty and reverts with `Filled()` in `onGetResponse` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:319-324`), permanently blocking the refund path.
7. The `1,000 USDC` remains locked in the `IntentGatewayV2` contract on chain A indefinitely, with no on-chain mechanism to release it.
