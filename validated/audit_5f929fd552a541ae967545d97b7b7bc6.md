### Title
OP_RETURN transaction data bypasses size and fee bounds - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` adds an OP_RETURN output to `tx_outs`, but both fee and maximum-weight calculations call `calculate_weight_vbytes` with only the payment outputs and optional change. [1](#0-0) [2](#0-1)  The size-estimation helper itself has no data-output parameter and constructs outputs solely from `payments` and `change`, so every OP_RETURN byte is omitted from the transaction's calculated weight and virtual size. [3](#0-2) 

### Finding Description
The OP_RETURN output is appended before `vbytes` and `needed_fee` are calculated, yet the calculation only models `payments`, excluding the already-added `tx_outs` entry. [4](#0-3)  When change is enabled, the change amount is calculated using another estimate that also omits the OP_RETURN output, leaving `needed_fee` equal to the fee for a smaller transaction than the one ultimately signed. [2](#0-1)  The final `MAX_STANDARD_TX_WEIGHT` check likewise tests the underestimated `weight`, not the transaction containing the OP_RETURN output. [5](#0-4) 

This is the same bug class as the virtio-net issue: a bounded object contains an additional component, but the size check uses the payload length without that component's encoded overhead.

### Impact Explanation
A transaction that requests exactly the minimum relay rate can pass the minimum-fee check while paying less than that rate once the omitted OP_RETURN output is serialized. [6](#0-5)  Similarly, a transaction whose modeled weight is within `MAX_STANDARD_TX_WEIGHT` can exceed that bound by the serialized size of the OP_RETURN output after signing. [7](#0-6) 

The result is a medium-severity transaction validity failure: participants can produce a fully signed transaction that normal Bitcoin relay policy rejects as underpriced or oversized, even though `SignableTransaction::new` reported that it satisfied the requested fee and standardness constraints. [8](#0-7) 

### Likelihood Explanation
The `data` field is a caller-controlled transaction payload and may contain up to 80 bytes before `TooMuchData` is returned. [9](#0-8)  An unprivileged requester who can cause an OP_RETURN transaction to be signed can supply 80 bytes and choose payments whose modeled weight or fee rate is near a policy boundary. No malicious validator, key compromise, or invalid curve input is required.

### Recommendation
Calculate weight and virtual size from the exact final output set, including the OP_RETURN output and any change output. [10](#0-9)  This can be done by changing `calculate_weight_vbytes` to accept the complete `tx_outs` list, or by constructing a candidate `Transaction` for both the no-change and change cases before deriving `needed_fee`. [3](#0-2)  The final `MAX_STANDARD_TX_WEIGHT` check should also use the complete transaction rather than the modeled subset. [11](#0-10) 

### Proof of Concept
```rust
use bitcoin::{Amount, TxOut};
use bitcoin::script::{PushBytesBuf, ScriptBuf};

// Select inputs so there is enough value for change.
let inputs = vec![received_output_with_sufficient_value];
let payments = vec![];
let change = Some(branch_or_change_script);
let data = Some(vec![0u8; 80]);

// At 1 sat/vbyte, the current minimum-fee check compares a fee equal
// to the estimated vbytes against that same estimated vbytes.
let stx = SignableTransaction::new(inputs, &payments, change, data, 1).unwrap();

// Simulate the 64-byte Taproot witness added to every input by signing.
let mut signed_tx = stx.transaction().clone();
for input in &mut signed_tx.input {
    input.witness.push([0u8; 64]);
}

let actual_vbytes = u64::from(signed_tx.vsize());
let paid_fee = stx.fee();

// needed_fee was calculated without the OP_RETURN output.
assert_eq!(paid_fee, stx.needed_fee());
assert!(actual_vbytes > stx.needed_fee());
assert!(paid_fee < actual_vbytes); // Actual feerate is below 1 sat/vbyte.
```

The boundary variant is equally direct: choose inputs and payment script sizes so the modeled weight is within the last serialized OP_RETURN-output size below `MAX_STANDARD_TX_WEIGHT`; the current check succeeds, while adding the requested 80-byte OP_RETURN output makes the signed transaction exceed the limit.     // Expand this a full transaction in order to use the bitcoin library's weight function

      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()

        // The script pub key is not of a fixed size and does have to be used here

          script_pubkey: payment.0.clone(),

      // the value is fixed size (so any value could be used here)
