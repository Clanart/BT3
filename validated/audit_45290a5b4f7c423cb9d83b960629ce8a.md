### Title
Irrevocable `SolverSelection` authorizations allow stale, advantageous-to-solver order execution - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The Intent Gateway's solver-selection flow lets a user authorize exactly one solver to fill an order by signing an EIP‑712 `SelectSolver(bytes32 commitment, address solver)` message with a disposable session key [1](#0-0) . This signed authorization carries no nonce, sequence number, or independent expiry — its only bound is the order's own `deadline` [2](#0-1) . Once handed to a solver as part of the bid protocol, the authorization is a durable bearer credential: the solver can hold it and call `fillOrder` at any block up to `order.deadline`, exactly mirroring the reported RFQ bug where a signed order lacking a revocation path becomes a "free option" that can be exercised whenever conditions swing in the holder's favor.

### Finding Description
The documented auction flow explicitly describes signing a `SolverSelection` message once a "best bid" is picked, then handing that signature to the solver to embed in its `UserOperation` [3](#0-2) . On-chain, `_select` recovers the session key from this signature and stages `keccak256(abi.encode(solver, sessionKey))` in transient storage purely to bind `select()` and `fillOrder()` atomically within one transaction [4](#0-3) . Crucially, the signed message itself (`abi.encode(SELECT_SOLVER_TYPEHASH, commitment, solver)`) has no expiry or single-use nonce field, so it remains cryptographically valid for the full lifetime of the order — from the moment it is signed until `order.deadline` or an explicit `cancelOrder()` call.

`fillOrder` re-validates the caller against this static authorization every time it is invoked [5](#0-4) , with only two states an order can be in: unfilled/uncancelled (authorization still exercisable) or filled/cancelled (`_filled[commitment] != address(0)`, reverts with `Filled()`) [6](#0-5) . There is no third state that lets the user revoke a specific solver's authorization while keeping the order open for a different solver — the only revocation mechanism is `cancelOrder()`, which kills the *entire* order (and, for cross-chain orders, requires either waiting past the deadline or sending a cross-chain `RefundEscrow` message) [7](#0-6) .

This produces the exact "irrevocable order" primitive from the RFQ report: a solver who has obtained a valid `SolverSelection` signature can simply defer calling `fillOrder`, holding the option to fill at the fixed, already-agreed output amounts (`order.output.assets`) for as long as the deadline window allows, regardless of subsequent price movement in the underlying tokens. Because `fillOrder` only requires outputs `>= order.output.assets` amounts [8](#0-7) , the solver is free to wait for the moment the required output basket is cheapest for them to provide (or the escrowed input is most valuable to receive) before finally submitting the transaction, extracting value from the user without the user having any way to invalidate that specific authorization short of nuking the whole order and forfeiting the auction to date. The `priceOracle` / `recordSpread` call that runs after a fill only records analytics after the fact — it does not gate or bound how stale a fill against a given authorization can be [9](#0-8) .

### Impact Explanation
This falls under the "logic attacks" category in the bounty's impact gate: a fully authorized, legitimate protocol actor (the selected solver) can exploit the absence of a targeted revocation/expiry mechanism on a signed authorization to time execution to their advantage at the user's expense — a value-extraction bug in production order-settlement logic, not a front-running or peer/relayer misbehavior scenario. The user's escrowed input tokens are exposed to this "free option" for the full window up to `order.deadline`, and the only recourse (full `cancelOrder`) is a blunt instrument that discards the entire auction rather than surgically un-authorizing a stale bid.

### Likelihood Explanation
Any solver that receives a `SolverSelection` signature as part of normal auction participation has everything needed to exploit this — no privileged access, malicious relayer, or race condition against the mempool is required. The solver only needs to choose *when*, within the existing deadline, to submit `fillOrder`; this is a deliberate economic decision available to every solver on every solver-selection-enabled order, making the likelihood high wherever `solverSelection` is enabled and deadlines are non-trivial.

### Recommendation
Add a nonce or short validity window (e.g., `validAfter`/`validUntil` fields, or a monotonic per-order selection sequence number) to the `SelectSolver` EIP-712 struct, and let the user's session key sign a fresh, uniquely-scoped authorization for the currently intended solver that automatically invalidates any prior authorization for the same commitment (e.g., by storing the latest authorized `(solver, sequence)` pair on-chain rather than accepting any historically valid signature). This allows the user to revoke a specific solver's stale authorization without cancelling the whole order.

### Proof of Concept
1. User places an order with `solverSelection` enabled and a `deadline` far in the future [10](#0-9) .
2. Solver A bids; user reviews the bid and signs `SelectSolver(commitment, solverA)` with the order's session key, handing this signature to Solver A as part of its `UserOperation` [3](#0-2) .
3. Solver A does not submit `fillOrder` immediately. Token prices move such that providing `order.output.assets` becomes cheap relative to the escrowed input the solver will receive.
4. At this later, favorable moment, Solver A submits its untouched `UserOperation`; `fillOrder` re-checks the still-valid transient selection hash from `_select` and succeeds [11](#0-10) .
5. The user had no way to invalidate Solver A's specific authorization in the interim (e.g., after seeing a better bid from Solver B) without calling `cancelOrder()` and forfeiting the whole order and its escrow lock-up/relayer fees.

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
}

### Bid selection
The user reviews all bids and picks the best one. To authorize the winning solver, the user signs an EIP-712 `SolverSelection` message with the session key:
```solidity
struct SolverSelection {
    bytes32 commitment,   // order commitment hash
    address solver       // authorized solver address
}
```
The session signature is appended to the solver's `UserOperation` as `abi.encodePacked(commitment, solverSignature, sessionSignature)` and submitted to an ERC-4337 bundler. The solver pays all gas costs for on-chain execution.
