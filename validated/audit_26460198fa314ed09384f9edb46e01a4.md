## Title
Interaction-before-effect in `withdraw()` combined with missing reentrancy guards allows double-release of escrowed order funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The Tron port of `IntentGatewayV2` diverges from the audited EVM implementation's escrow-release pattern. In the canonical EVM contract, `_withdraw()` (in `IntentsBase.sol`) reads the escrowed balance, verifies it, and **updates storage before performing the external token transfer**, and the caller-facing entrypoints `placeOrder`/`fillOrder` are wrapped in `nonReentrant`. The Tron variant's `withdraw()` performs the **external transfer first and decrements `_orders` afterward**, and none of `placeOrder`/`cancelOrder` carry a reentrancy guard. This is the same class of bug as the H01 report: a value/ordering inconsistency was correctly handled in one code path but is broken in the sibling implementation that is supposed to behave identically.

## Finding Description
`withdraw()` in the Tron gateway: [1](#0-0) 

only checks `_orders[body.commitment][token] == 0` (not `< amount`) and then performs the raw `token.call(...)`/native `.call{value:amount}` transfer **before** `_orders[body.commitment][token] -= amount`. Compare this to the main EVM contract's `_withdraw()`: [2](#0-1) 

which decrements `_orders[body.commitment][token] = escrowed - amount;` before executing the transfer, and whose public entrypoints are `nonReentrant`: [3](#0-2) [4](#0-3) [5](#0-4) 

`placeOrder` on Tron accepts **any** ERC-20 as an input token with no allowlist, so an attacker fully controls the token contract that will later be `.call()`-ed inside `withdraw()`: [6](#0-5) 

`cancelOrder`'s same-chain path is reachable by the order owner without any reentrancy lock and itself calls `withdraw()`: [7](#0-6) 

Because the escrow decrement for token `i` only happens *after* its transfer completes, a malicious token's `transfer()` callback can re-enter `cancelOrder()`/`withdraw()` for the same commitment while later tokens in `body.tokens` (or the fee entry) still show their full, un-decremented escrow balance, letting the reentrant call redeem escrow that the outer call has not yet accounted for.

## Impact Explanation
This breaks the "moves exactly once" invariant for escrowed order funds: an attacker who places an order using a malicious, attacker-authored ERC-20 as one of the input tokens can trigger the settlement/refund path (`onAccept`→`withdraw`, `onGetResponse`→`withdraw`, or same-chain `cancelOrder`→`withdraw`) and, through the token's transfer hook, re-enter before the corresponding storage decrement lands—causing duplicate release of escrowed tokens for other legitimate assets in the same order, or of the accumulated transaction fee, to the attacker-controlled beneficiary. This matches the bounty's "stealing or loss of funds" / "replay/double-claim/double-settlement" impact classes.

## Likelihood Explanation
Reachability is fully permissionless: any user can call `placeOrder` with an arbitrary ERC-20 they author as `order.inputs[i].token`, and can call `cancelOrder` themselves as `order.user` — no relayer, prover, or admin compromise is required. The main constraint (and source of uncertainty) is that the outer settlement call (`onAccept`/`onGetResponse`) is `onlyHost`-gated, so the attacker's exploitation window is limited to reentering through `cancelOrder`/`placeOrder`, and whether a profitable, non-reverting double-spend sequence can be fully constructed end-to-end (e.g., against the `TRANSACTION_FEES` slot or a second, distinct order sharing timing) needs dynamic verification I could not complete with static reading alone. What is concretely provable from the code is the interaction-before-effect ordering and the total absence of `nonReentrant` protection on `placeOrder`/`cancelOrder` in this file, which is a regression relative to the hardened EVM sibling contract.

## Recommendation
Mirror the EVM implementation exactly in the Tron port:
1. In `withdraw()`, read and validate `escrowed = _orders[body.commitment][token]` (revert if `amount > escrowed`), decrement `_orders[body.commitment][token] -= amount` **before** issuing the external transfer for each token, following checks-effects-interactions.
2. Add a reentrancy guard (`nonReentrant` or an equivalent transient-storage lock) to `placeOrder` and `cancelOrder`.
3. Apply the same fix to the fee redemption block (decrement before transfer).

## Proof of Concept
Conceptual sequence (requires dynamic testing against the actual Tron contract to confirm a non-reverting profitable path):
1. Attacker deploys `EvilToken` with a `transfer()` override that, when called from the gateway, re-enters `cancelOrder()` for the same order commitment.
2. Attacker calls `placeOrder` with `order.inputs = [EvilToken: X, USDC: Y]`, escrowing both.
3. Attacker (as `order.user`) triggers `cancelOrder()` (same-chain path) which calls `withdraw(body, true)`.
4. `withdraw()`'s loop transfers `EvilToken` first (index 0); `EvilToken.transfer()` re-enters `cancelOrder()`/`withdraw()` for the same commitment before `_orders[commitment][EvilToken]` is decremented.
5. In the reentrant call, `_orders[commitment][USDC]` is still full (outer loop hasn't reached it), so USDC is transferred out and decremented to zero in the nested call.
6. Control returns to the outer loop, which then attempts to transfer/decrement USDC again — outcome (revert vs. underflow handling) determines whether funds are actually retained; this final step needs to be verified in a Foundry/Tron test harness to confirm net fund extraction survives transaction finalization.
