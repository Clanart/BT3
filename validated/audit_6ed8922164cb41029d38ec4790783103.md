## Finding

The bug-class in the report is "trust a low-level primitive without validating it, and it silently breaks/misbehaves when an assumption doesn't hold" (`transfer()`'s fixed-gas assumption). The closest real Desktop analog is a missing-validation issue: **URLs that originate from attacker-controlled GitHub API objects (Check Run `details_url`) are passed straight to `shell.openExternal` with no protocol allow-list**, even though the app has an equivalent guard elsewhere (the sandboxed markdown link interceptor) that it fails to apply consistently.

### Title
Check-run `details_url` from the GitHub Checks API is opened via `shell.openExternal` without scheme validation - (File: `app/src/main-process/main.ts`)

### Summary
`CICheckRunPopover.onViewCheckDetails` takes `checkRun.htmlUrl` — a value that comes directly from the GitHub Checks API (`details_url` on a check run) — and forwards it unchanged to `dispatcher.openInBrowser(url)`, which calls `shell.openExternal(url)` over IPC. The main-process IPC handler for `open-external` does not validate or restrict the URL scheme at all before invoking Electron's `shell.openExternal`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`details_url` on a GitHub check run is set by whatever GitHub App/CI system reports the check (e.g. a third-party Action, a fork's workflow, or any integration with `checks:write`). It is attacker-influenceable text supplied through the GitHub API, not a value GitHub Desktop itself generates or sanitizes. `onViewCheckDetails` uses it verbatim:

```ts
const url = checkRun.htmlUrl ?? `${this.props.repository.htmlURL}/pull/${this.props.prNumber}`
this.props.dispatcher.openInBrowser(url)
``` [4](#0-3) 

`dispatcher.openInBrowser` → `appStore._openInBrowser` calls `shell.openExternal(url)` directly, with no scheme check: [2](#0-1) 

That call is proxied to the main process via `open-external`, whose handler only *logs* when the URL happens to be `http(s)`, but performs no allow-list or rejection of other schemes before calling Electron's `shell.openExternal`: [3](#0-2) 

Contrast this with the one place in the codebase that *does* get this right — the sandboxed markdown link interceptor, which explicitly requires the href to be `http`/`https` before invoking the click callback:
```ts
if (/^https?:/.test(a.protocol)) {
  this.props.onMarkdownLinkClicked?.(a.href)
}
``` [5](#0-4) 

The check-run details flow bypasses this guard entirely: it is not markdown, so it never goes through `sandboxed-markdown.tsx`'s protocol check, yet ends up at the exact same `shell.openExternal` sink. This is the "existing guard doesn't stop the path" gap: Desktop has already implemented a scheme allow-list pattern in one code path, but the `open-external` IPC handler itself — the common choke point for *all* callers, including check-run URLs, CI notification URLs, PR body links, etc. — does not enforce it, so any caller that forgets to pre-validate (as this one does) reaches an unguarded `shell.openExternal`.

### Impact Explanation
`shell.openExternal` with an uncontrolled scheme can invoke arbitrary registered URI-scheme handlers on the user's OS (e.g. custom protocol handlers registered by other installed software, or platform-specific handlers that Electron/Chromium has historically had issues sandboxing). Because the value here originates from a GitHub Checks API object that a CI integration/App (potentially attached to a fork or third-party workflow) fully controls, an attacker who can get a check run associated with a PR the victim views in Desktop controls the string that is handed to the OS shell-open primitive with no scheme restriction. Depending on installed applications/handlers on the victim's machine, this can range from information disclosure (triggering an outbound request to an attacker server via an unexpected protocol) up to code execution through a vulnerable third-party protocol handler.

### Likelihood Explanation
This requires the victim to be viewing PR checks in Desktop for a repository/PR whose check run was reported with an attacker-crafted `details_url`. Any CI system or GitHub App with permission to post check runs (e.g. on a public repo, third-party integrations added by a maintainer, or a fork's own Actions workflow reporting a status back) can set this field freely — no elevated privileges, no local access, and no unusual user action beyond opening the check-run popover and clicking "view details," which is normal Desktop usage. It does not need social engineering beyond the attacker's own CI integration.

### Recommendation
Enforce the scheme allow-list at the single choke point (`open-external` IPC handler in `app/src/main-process/main.ts`), rejecting/no-oping any URL whose scheme is not `http:`/`https:`, instead of only logging for those schemes. This mirrors the guard already present in `sandboxed-markdown.tsx`'s `setupLinkInterceptor`, and ensures every caller of `shell.openExternal` — including check-run `details_url`, workflow-step URLs, and any future caller — is protected even if it forgets to pre-validate.

### Proof of Concept
1. As a maintainer of a CI integration/GitHub App (or an Actions workflow in a repository/fork), report a check run for a commit/PR with `details_url` set to a non-http(s) URI (e.g. a custom-protocol handler string or a `file:`-style path) instead of a normal `https://` link.
2. In GitHub Desktop, the victim opens the pull request's CI Checks popover and clicks the check run to "View check details."
3. `onViewCheckDetails` passes `checkRun.htmlUrl` straight to `dispatcher.openInBrowser` → `shell.openExternal`, and the main-process `open-external` handler forwards it to Electron's `shell.openExternal` without validating the scheme, causing the OS to resolve/execute whatever handler is registered for that URI scheme.   private onViewCheckDetails = (checkRun: IRefCheck): void => {

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
