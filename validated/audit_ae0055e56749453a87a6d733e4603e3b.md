### Title
Ungoverned `kip71.gastarget` vote of 0 causes a division-by-zero panic in `NextMagmaBlockBaseFee`, halting block production/validation network-wide - (File: params/kip71_config.go)

### Summary
`Kip71GasTarget` governance votes are accepted with no format or consistency validation. A vote setting `gasTarget = 0` is accepted by `checkConsistency`, gets merged into the effective `ParamSet`, and is later used as a divisor in `NextMagmaBlockBaseFee`. When `gasTarget == 0` and any gas is used in a block, the `big.Int.Div` call panics with a division-by-zero error, which is invoked from `validateHeader` on all nodes verifying subsequent blocks, effectively halting the chain.

### Finding Description
`Kip71GasTarget`'s `Param` definition uses `noopFormatChecker`, meaning any `uint64` value including `0` is accepted as a valid canonical value: [1](#0-0) .

When a header vote for `gov.Kip71GasTarget` is verified in `checkConsistency`, it falls into the generic case that performs no additional cross-parameter validation (unlike `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which are explicitly checked against each other): [2](#0-1) .

Once ratified, this value becomes part of the effective `ParamSet.GasTarget` used across the node (via `GetParamSet`) and is fed into `KIP71Config.NextMagmaBlockBaseFee`:
- `baseFeeDenominator` has an explicit zero-guard (falls back to 64) ( [6](#0-5) ), but `gasTarget` has no equivalent guard: [7](#0-6) .
- If `gasTarget == 0`, then for any `parentGasUsed > 0`, execution enters the `parentGasUsed > gasTarget` branch and computes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))`, dividing by zero, which panics in Go's `math/big` package: [8](#0-7) .
- Even if `parentGasUsed == 0` for one block, any subsequent block with nonzero gas usage will hit the panic.

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked from `BlockValidator.validateHeader`, which runs for every incoming header on every node once Magma is active: [5](#0-4) . It is also called during block assembly (`chain_makers.go`, `work/worker.go`) and in the tx pool for gas price updates ( [9](#0-8) ), meaning the panic is reachable from multiple independent code paths across all full nodes and validators, not just a single component.

### Impact Explanation
A single ratified governance vote setting `kip71.gastarget` to `0` causes an unrecovered panic (division by zero) in core block-validation and block-assembly logic on every node that processes a subsequent block with nonzero gas usage. This is a chain-halting, network-wide denial-of-service: honest nodes crash or become unable to advance the chain, since header validation, block building, and tx-pool base-fee updates all hit the same unguarded division. This is far more severe than the referenced report's "incorrect liquidation" impact, but the root cause class is identical: an unvalidated numeric governance parameter is accepted without a safety/consistency check before being used in downstream computation, exactly analogous to `updateReserveParam` not validating `_initialMortgageRate` against `_liquidationMortgageRate`.

### Likelihood Explanation
Governance votes are cast via the standard `governance_vote` mechanism used for regular parameter tuning; `Kip71GasTarget` is documented as a normal mutable governance parameter ( [10](#0-9) ). Nothing in the voting, canonicalization, or consistency-check pipeline rejects `0` (or any other pathological value) for this parameter, so the only barrier is operational care by whoever proposes/ratifies the vote — there is no protocol-level safety net, unlike the analogous `LowerBoundBaseFee`/`UpperBoundBaseFee` pair which the code already protects against similar misconfiguration.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) rejecting `0`, and/or add a runtime guard in `NextMagmaBlockBaseFee` treating `gasTarget == 0` the same way `baseFeeDenominator == 0` is handled (fallback to a safe default instead of dividing by zero). Additionally, consider a `checkConsistency` cross-check ensuring `gasTarget` is within a sane range relative to `MaxBlockGasUsedForBaseFee`.

### Proof of Concept
1. A vote is ratified changing `gov.Kip71GasTarget` to `uint64(0)` (accepted because `FormatChecker` is a no-op and `checkConsistency` performs no validation for this parameter).
2. Once active, at the next block where `parentGasUsed > 0` (virtually guaranteed on a live chain), `NextMagmaBlockBaseFee` executes:
   ```go
   gasTarget := kc.GasTarget // 0
   parentGasUsed := min(parentHeaderGasUsed, upperGasLimit) // > 0
   // parentGasUsed > gasTarget branch taken
   gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // = parentGasUsed
   x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
   y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // Div by zero -> panic
   ```
3. This function is called both when building the next block header (`chain_makers.go`, `work/worker.go`) and when every node verifies the incoming header (`block_validator.go`), so the panic occurs network-wide, halting block production/verification.
