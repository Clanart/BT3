### Title
Consensus-liquidity `CLStakingAmount` is derived from a raw `balanceOf`/native balance, letting anyone inflate a validator's staking-reward weight via direct token donation - (File: kaiax/staking/impl/getter.go)

### Summary
The Prague-era reward split (`kaiax/reward`) weights each validator's share of minting rewards partly by `CLStakingAmount`, a value obtained from the `CLRegistry`/`MultiCallDPStakingInfo` system-contract query. The only concrete implementation available in the codebase — the test mock `WrappedKaiaMock.balanceOf()` — simply returns `account.balance`, and the corresponding staking-info test fixtures set the CL pool's `CLStakingAmount` directly equal to the CL pool contract address's raw native balance. [1](#0-0) [2](#0-1) 

### Finding Description
`CLStakingInfo.CLStakingAmount` is read from the CL registry/pool and consumed unmodified to weight staking rewards in `assignStakingRewards` and `assignStakingRewardsFlex`, exactly mirroring the pattern in the Notional bug where an underlying-token `balanceOf()`-derived exchange rate is trusted without accounting for donated (unminted) tokens. [3](#0-2) [4](#0-3) 

If (as the mock implies) the production `CLStakingAmount` is sourced from a plain `balanceOf`/native-balance read on the CL pool address rather than from internally tracked share accounting, then any unprivileged account can send KAIA/wKAIA directly to a CL pool address in a single transaction to inflate that pool's reported staking amount without acquiring any shares or going through the legitimate consensus-liquidity deposit flow — the same "donate to the balance-tracked contract to inflate the derived value" root cause as the M-4 report.

### Impact Explanation
If exploitable, this would let an attacker (or a colluding validator) unilaterally increase a specific node's `CLStakingAmount`, which is used in `assignStakingRewardsFlex`/`assignStakingRewards` to proportionally split the staker reward budget across validators. [5](#0-4) 
This redirects minting rewards away from other honest validators/stakers toward the manipulated node — a concrete reward-redirection/value-movement outcome, matching the Sherlock report's "unauthorized value movement via balance donation" bug class.

### Likelihood Explanation
Likelihood is **uncertain and cannot be confirmed from this repository**: the actual on-chain `CLRegistry` and `WrappedKaia` contract source code (the real, non-mock implementations used on Kaia mainnet) is not present in the indexed codebase — only Go bindings for `MultiCallContract` and Solidity **test mocks** are available. The mock's `balanceOf() = account.balance` and the getter test's alloc-equals-CLStakingAmount fixture are the only evidence suggesting this balance-donation pattern; it is possible the real system contract uses proper share/deposit accounting (e.g., an ERC-4626-style vault) that is immune to this class of donation attack, in which case this finding would not apply.

### Recommendation
Since the real `CLRegistry`/`WrappedKaia`/CL-pool contract implementation could not be located in this repository, a Devin session with full repository/system-contract access should verify:
1. Whether `CLStakingAmount` (as surfaced via `multiCallDPStakingInfo`) is computed from a raw `balanceOf()`/native-balance read on the CL pool address, or from internally tracked, share-based accounting.
2. If it is balance-based, add donation-resistant accounting (e.g., track deposited principal separately from the pool's raw token balance, or use share-price rounding protections) before allowing `CLStakingAmount` to influence `assignStakingRewards`/`assignStakingRewardsFlex`.

### Proof of Concept
Cannot be constructed with confidence from the available code, because the real CL pool contract is not present in this repository — only the test mock (`WrappedKaiaMock.balanceOf() = account.balance`) hints at this pattern. If confirmed, the PoC would be: attacker sends a plain native-KAIA transfer to a target CL pool address in a single transaction (no special privilege required), then observes the next `kaia_getStakingInfo`/reward distribution call inflate that CL pool's `CLStakingAmount` and its associated validator's `stakersAlloc` share in `assignStakingRewardsFlex`. [6](#0-5) 

**Caveat:** Given the uncertainty about the real (non-mock) system contract implementation, this should be treated as a hypothesis requiring verification against the actual deployed `CLRegistry`/CL-pool bytecode rather than a confirmed vulnerability.

// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

	// Distribute the budget to the CNs based on the excess stakes.
	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(budget)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		if excessInt[cn.RewardAddr] <= 0 {
			continue
		}
		excess := new(big.Int).SetUint64(excessInt[cn.RewardAddr])

		// The KAIA unit will cancel out:
		// reward (kei) = excess (KAIA) * budget (kei) / totalExcess (KAIA)
		reward := new(big.Int).Div(new(big.Int).Mul(excess, budget), totalExcess)
		if reward.Sign() <= 0 {
			continue
		}

		// If Prague and CL is configured for this CN, split the reward between CN and CL.
		if isPrague && cn.CLStakingInfo != nil {
			cnAmount, clAmount := cn.Split(reward)
			alloc[cn.RewardAddr] = cnAmount
			alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
		} else {
			alloc[cn.RewardAddr] = reward
		}
		remaining.Sub(remaining, reward)
	}
	return alloc, remaining
}
