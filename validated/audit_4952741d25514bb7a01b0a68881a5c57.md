## Finding

The core broken invariant in the C4 report is: a **per-scope release amount computed from an aggregated/cumulative ledger, rather than the caller's actual allocation**, lets a caller drain more than their rightful share by controlling the order/timing of claims. The same pattern exists in Hyperbridge's Intent Gateway same-chain fill path.

### Title
Same-chain partial-fill escrow release uses a per-token aggregate bucket instead of a per-leg allocation, letting a solver drain another leg's escrow — (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_orders` is keyed only by `(commitment, token address)`, not by output-leg index: [1](#0-0) . When an order's `inputs` array contains the same token address at more than one index (a legitimate configuration — e.g. one input token funding two different output legs), the escrow for *all* those legs is combined into a single bucket. In `_fillSameChain`, once any single leg `i` reaches `amountFilled == totalRequired`, the code releases the **entire remaining balance of that token bucket**, not just leg `i`'s proportional share: [2](#0-1) 

### Finding Description
`escrowedAmount = _orders[commitment][token]` reads the whole aggregate balance for that token, which may include escrow that was placed to fund a *different*, not-yet-filled output leg `j` sharing the same input token. A solver who completes leg `i` first (fully, in a single call or via successive partial fills) collects `_orders[commitment][token_i]`, which equals the sum of whatever remains for every leg keyed to that same token — including leg `j`'s untouched allocation. This mirrors the reported bug's root cause: a limit/allocation derived from an aggregate counter (`userAllocation.bought` in the original report; `_orders[commitment][token]` here) rather than from the caller's actual current-leg entitlement.

Existing guards do not stop this:
- `_partialFills[commitment][outputToken]` tracks fill progress **per output token**, correctly gating how much of leg `i`'s *output* can be filled — but it has no relationship to how the *input* escrow bucket is shared across legs.
- `_withdraw`'s only check is `if (escrowed == 0) revert UnknownOrder()` [3](#0-2)  — it does not verify that the amount being released was actually escrowed *for this leg*, only that the token bucket is non-zero.
- Nothing in `_fillSameChain` computes leg `i`'s true share of the combined bucket before taking "all remaining" on that leg's completion.

### Impact Explanation
This falls under "logic attack / wrong beneficiary or amount / fund loss": a solver (unprivileged, using only the public `fillOrder` entrypoint) can, through fill ordering alone, capture escrow intended to pay out for a different order leg. Depending on which leg finishes first, this either (a) over-pays the first filler relative to work done, taking funds that should have released to a later filler completing leg `j`, or (b) leaves leg `j` under-collateralized so its rightful fill later reverts (`UnknownOrder`) once the shared bucket is drained, permanently locking the user's counterpart obligation and breaking the order's intended settlement.

### Likelihood Explanation
Any user (or an attacker crafting an order via `placeOrder` and then acting as their own colluding "solver", or simply exploiting orders placed by others with legitimately duplicated input tokens) can trigger this by controlling which leg is completed first among legs sharing an input token address, with no special privileges, no malicious relayer, and no reliance on proof forgery. This is a straightforward selection of call order on public functions.

### Recommendation
Track escrow per `(commitment, inputIndex)` (or per `(commitment, outputToken)` since that's already the fill-progress key) instead of aggregating purely by token address, or compute the leg's proportional share from `order.inputs[i].amount` scaled by `totalRequired`/`amountFilled` rather than reading the whole shared bucket on final-fill completion.

### Proof of Concept
1. User places a same-chain order with `inputs = [ {token: DAI, amount: 600}, {token: DAI, amount: 400} ]` and `outputs = [ {tokenA, 100}, {tokenB, 50} ]`. `_orders[commitment][DAI] = 1000` (aggregated).
2. Solver calls `fillOrder` providing only `outputs[0] = 100` (tokenA), fully satisfying leg 0 (`amountFilled == totalRequired` for leg 0).
3. In the loop at leg 0, `escrowedAmount = _orders[commitment][DAI]` = **1000** (the full combined bucket), not the 600 that was actually earmarked for leg 0. The solver receives 1000 DAI for filling only the 100-tokenA leg.
4. When another solver later attempts to fill leg 1 (tokenB), `_orders[commitment][DAI]` is now 0, and `_withdraw` reverts with `UnknownOrder`, permanently blocking leg 1's settlement and leaving the user's second output unfulfillable. [4](#0-3) [5](#0-4)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
