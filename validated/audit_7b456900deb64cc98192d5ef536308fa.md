### Title
Governance-settable `kip71.gastarget = 0` causes divide-by-zero panic in `NextMagmaBlockBaseFee` - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` when computing the next block's base fee, but unlike `BaseFeeDenominator` (which is explicitly checked to be nonzero), the `GasTarget` governance parameter has no such check, allowing it to be set to `0` and causing an unhandled `big.Int` division panic — directly analogous to the `drm_mode_vrefresh()` divide-by-zero class of bug (guarding one divisor but not all reachable zero-divisor paths).

### Finding Description
In `params/kip71_config.go`, `NextMagmaBlockBaseFee` computes: [1](#0-0) 
```
gasTarget := kc.GasTarget
upperGasLimit := kc.MaxBlockGasUsedForBaseFee
```
When `parentGasUsed != gasTarget`, the function unconditionally divides by `gasTarget`: [2](#0-1) [3](#0-2) 

The code explicitly guards against `BaseFeeDenominator == 0` by falling back to `64`: [4](#0-3) 
but performs **no equivalent guard for `GasTarget`**. If `GasTarget == 0` and `parentGasUsed != 0` (the `parentGasUsed > gasTarget` branch, since `parentGasUsed == gasTarget` only holds when both are 0), `x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by zero, which panics in `math/big`.

This value is a governable chain parameter (`Kip71GasTarget`) whose format checker performs no validation at all: [5](#0-4) 
Compare this to `Kip71BaseFeeDenominator`, which explicitly rejects zero: [6](#0-5) 
No such `v != 0` check exists for `Kip71GasTarget`, so a governance vote/parameter update can set it to `0` and it will pass validation.

`NextMagmaBlockBaseFee` is invoked on every block for baseFee calculation/verification (consensus-critical path) via `VerifyMagmaHeader`, and also from the RPC-facing fee-history oracle: [7](#0-6) [8](#0-7) 

### Impact Explanation
A panic in `NextMagmaBlockBaseFee` during block header verification or base fee computation would crash consensus/RPC-serving nodes (denial of service on block processing and fee estimation), and because it's on the block-verification path for every node computing the next base fee, it can produce a chain-wide halt/crash rather than a single-node issue, satisfying the "state divergence / DoS via invalid parameter acceptance" impact class.

### Likelihood Explanation
Exploitation requires the governance mechanism to actually accept `GasTarget = 0` as a valid parameter change (i.e., no other higher-level guard exists beyond the `FormatChecker` shown). This requires governance-level access (vote/proposal), which is a higher bar than an arbitrary unprivileged transaction, so likelihood is moderate rather than trivially reachable by any public RPC caller — the report's "Medium" severity classification for the analogous DRM bug is consistent given the mitigating factor that a governance action is needed to set the malicious parameter.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0` (analogous to `Kip71BaseFeeDenominator`), and/or add a defensive `gasTarget == 0` fallback inside `NextMagmaBlockBaseFee` similar to the existing `BaseFeeDenominator == 0` fallback, before performing the division at params/kip71_config.go lines 100-102 and 118-121.

### Proof of Concept
1. Governance sets `kip71.gastarget = 0` (passes `noopFormatChecker` validation, at `kaiax/gov/param.go:324-334`).
2. A block is produced where `parentHeaderGasUsed > 0` (any nonzero gas usage), so `parentGasUsed != gasTarget` and the `parentGasUsed > gasTarget` branch executes at `params/kip71_config.go:92-109`.
3. `gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)` computes fine, but `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` at line 102 divides by the zero-valued `gasTarget`, panicking (`big.Int` division by zero panics in Go's `math/big`), crashing the node's block-processing/fee-history goroutine.

Note: I was unable to fully verify whether there exists an additional, higher-level governance-vote sanity check outside `kaiax/gov/param.go` that might reject `GasTarget = 0` before it reaches `ChainConfig`; the index search found no such check, but a Devin session with full repo access should confirm no other validation layer exists (e.g., in vote-casting or `AddressBook`/governance-contract validation) before treating this as fully exploitable.
