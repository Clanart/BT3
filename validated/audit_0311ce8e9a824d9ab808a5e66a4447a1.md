## Title
Missing state-manager lock on `pw_absorb_rewards` for `PlotNFT2Wallet` allows concurrent reward-claim races to double-select unspent pool reward coins - (File: chia/wallet/wallet_rpc_api.py)

### Summary
The reported CEI/re-entrancy bug pattern (accounting mutated *after* the external transfer/callback, allowing repeated withdrawal before the mutation lands) maps to a concrete "check happens, external state-changing call happens, but the guard/lock that prevents an overlapping second call is missing" flaw in the pool/plotnft claim path. `WalletRpcApi.pw_absorb_rewards` explicitly wraps the `PoolWallet` claim in `wallet_state_manager.lock`, but the `PlotNFT2Wallet` branch does not take that lock before calling `claim_rewards()`.

### Finding Description
`pw_absorb_rewards` in `chia/wallet/wallet_rpc_api.py` dispatches on wallet type: [1](#0-0) 

For `PoolWallet` the whole claim (`wallet.claim_pool_rewards(...)`) is executed under `self.service.wallet_state_manager.lock`. For `PlotNFT2Wallet`, `wallet.claim_rewards(...)` is invoked with **no lock at all**.

`PlotNFT2Wallet.claim_rewards` reads the currently-unspent reward set via `plotnft2_store.get_pool_rewards(plotnft_id=...)`, builds a `CoinSpend` list consuming those reward coins plus the singleton coin, and only later (asynchronously, on chain confirmation / sync) does `mark_pool_reward_as_spent` get called to remove them from the "unspent" set: [2](#0-1) [3](#0-2) [4](#0-3) 

`get_pool_rewards` filters on `spent_height IS NULL`, and `spent_height` is only updated by `mark_pool_reward_as_spent`, which fires from wallet-sync processing of confirmed/observed on-chain spends - not synchronously when the spend bundle is built or pushed. Unlike `PoolWallet.claim_pool_rewards`, which explicitly checks `have_unconfirmed_transaction()` before proceeding: [5](#0-4) 

`PlotNFT2Wallet.claim_rewards` has no equivalent guard, and because the RPC handler for this wallet type doesn't take `wallet_state_manager.lock`, two concurrent `pw_absorb_rewards` RPC calls (or an auto-claim path racing with a manual RPC call) can both read the same "unspent" reward-coin set from `plotnft2_store` before either spend is confirmed, both construct singleton-consuming `CoinSpend`s off the same singleton lineage tip, and both get pushed. This is structurally the same class of bug as the reported issue: the accounting/guard that should serialize "read unspent state -> build transfer -> commit accounting" is absent on this path, whereas the analogous, correctly-guarded code path (`PoolWallet`) demonstrates what the missing protection looks like.

### Impact Explanation
Concurrent unlocked claims would each try to spend the same reward coins and the same singleton coin. On-chain, only one of the two conflicting spend bundles can be accepted (the singleton and reward coins are single-use UTXOs), so outright double-spend/fund duplication is not possible at the consensus layer. However, this still produces wallet-facing incorrect state: transaction records / coin-selection bookkeeping can diverge from what actually lands on chain, unconfirmed transactions can conflict with each other and get evicted, and repeated auto-claim vs. manual-claim races can leave the local wallet DB out of sync with confirmed history (mis-tracked `spent_height`, spurious pending removals, or a stuck singleton lineage view) until the next successful sync/resolution. This is a data-integrity/availability issue for the wallet process rather than a fund-theft primitive, since Chia's coin-set model prevents the "drain the pool via reentrant transfer" outcome described in the Solidity original.

### Likelihood Explanation
Requires two overlapping calls into the same wallet's `pw_absorb_rewards` for a `PlotNFT2Wallet` (e.g. manual RPC call racing with the auto-claim job, or a caller issuing rapid duplicate RPC requests). This is reachable by any local RPC caller with wallet access and is plausible under load or scripted callers, but not attacker-controlled from an unprivileged remote peer.

### Recommendation
Wrap the `PlotNFT2Wallet` branch of `pw_absorb_rewards` in `self.service.wallet_state_manager.lock`, matching the `PoolWallet` branch, and/or add an unconfirmed-transaction/in-flight-claim guard inside `PlotNFT2Wallet.claim_rewards` (analogous to `PoolWallet.have_unconfirmed_transaction()`) so that a second concurrent claim cannot select reward coins that are already part of an unconfirmed, in-flight claim spend.

### Proof of Concept
Not independently verified against a running node; based on static code reading:
1. Call `pw_absorb_rewards` for a `PlotNFT2Wallet` wallet id twice concurrently (or trigger `auto_claim_coins`/manual claim race).
2. Both calls call `plotnft2_store.get_pool_rewards(...)` before either spend is confirmed and `mark_pool_reward_as_spent` runs, so both see the same unspent reward set.
3. Both build and push conflicting `CoinSpend`s consuming the same singleton/reward coins; only one is later confirmed, while local transaction/coin-record bookkeeping for the losing attempt can be left inconsistent. [1](#0-0) [4](#0-3)
