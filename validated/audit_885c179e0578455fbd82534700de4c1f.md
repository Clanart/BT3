### Title
Overpaid native `msg.value` sent to `dispatch()`/`fundRequest()` is permanently donated to `EvmHost` instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the direct Hyperbridge analog of the Cally `buyOption()` finding: a payable entry point accepts `msg.value` greater than what is actually required, and the surplus is not returned to the payer but is instead captured by a different party — here the `EvmHost` contract itself rather than the caller who overpaid.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all follow the same pattern when `msg.value > 0`: [1](#0-0) 

```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```

`swapETHForExactTokens` only consumes the amount of ETH required to buy exactly `post.fee` (or `get.fee` / `amount`) of the fee token; any unspent ETH is refunded by the Uniswap V2 router to `msg.sender` of that call. But the `msg.sender` seen by the router is `EvmHost` itself, because `EvmHost` is the contract that directly calls `swapETHForExactTokens{value: msg.value}(...)`. The caller who originally sent the excess `msg.value` to `dispatch()`/`fundRequest()` is never reimbursed — the router's refund lands in `EvmHost`'s own balance instead. [2](#0-1) [3](#0-2) 

This is not a defensive edge case: overpaying is easy to trigger because fee estimation is done off-chain/client-side (per the docs' "Estimating Fees" guidance) and any slippage, gas-price change, or conservative buffer in the client's fee estimate results in `msg.value > required swap input`. One concrete caller that exhibits this is `WrappedHyperFungibleTokenUpgradeable.send()`, which forwards its entire leftover `msgValue` (not a computed fee amount) straight into `dispatch{value: msgValue}`: [4](#0-3) 

Neither `dispatch()` nor `fundRequest()` computes the exact native amount needed before forwarding `msg.value`, and neither validates `msg.value == requiredAmount` (the fix pattern recommended in the referenced Cally report). The excess is simply absorbed by the Uniswap swap call and re-captured by `EvmHost`, with no mechanism shown in this code path to return it to the `payer`.

### Impact Explanation
Every caller who overestimates the native-token amount required for a POST/GET dispatch or a `fundRequest()` top-up permanently loses the difference — it becomes stranded ETH held by `EvmHost` rather than the fee token owed to the relayer or a refund to the payer. This is a direct fund-loss bug for legitimate users (unprivileged, no relayer/prover/admin assumption needed), matching the "stealing or loss of funds" and "wrong beneficiary or amount" impact categories in the bounty scope. Because `dispatch()` is a widely used public entry point (used by every `HyperApp`, the intents gateway, wrapped-token bridge, and LayerZero endpoint adapter), the blast radius spans the whole EVM-side messaging surface.

### Likelihood Explanation
High. Overpayment is the normal, expected client behavior described in the docs themselves ("Estimating Fees" section recommends estimating client-side, which is inherently approximate), and there is no on-chain guard forcing `msg.value` to equal the exact swap input. No malicious relayer, prover, or admin is required — any regular user or integrating contract calling `dispatch()`/`fundRequest()` with a slightly generous `msg.value` triggers the loss.

### Recommendation
Compute the excess native input explicitly after the swap and refund it to `_msgSender()` (or `post.payer`/`get.payer` where applicable), mirroring the pattern already used correctly elsewhere in the codebase (e.g., `ExtrinsicIntents._fillCrossChain`'s explicit `msgValue -= ...` and refund-to-solver logic, and `IntentGatewayV2`'s tested "refunds excess native token" behavior). Concretely, in `EvmHost.dispatch()` and `fundRequest()`, capture `amounts[0]` returned by `swapETHForExactTokens` and transfer `msg.value - amounts[0]` back to `_msgSender()` instead of letting the router's refund settle into `EvmHost`'s own balance.

### Proof of Concept
1. User calls `MyApp.sendMessageWithNative{value: 1 ether}(...)` which forwards to `IDispatcher(host()).dispatch{value: 1 ether}(post)` where `post.fee` only requires the ETH-equivalent of 0.1 ether.
2. Inside `EvmHost.dispatch()`, `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), ...)` executes, spending only ~0.1 ether of ETH to acquire exactly `post.fee` fee tokens.
3. The Uniswap V2 router refunds the remaining ~0.9 ether to `msg.sender`, which at this call site is `EvmHost`'s own address (the contract that invoked the router), not the original user or `MyApp`.
4. The user's request is dispatched correctly, but their 0.9 ether excess is now sitting in `EvmHost`'s native balance with no code path shown that returns it to them — the exact "excess is captured by the wrong party" pattern the referenced report warns about.
