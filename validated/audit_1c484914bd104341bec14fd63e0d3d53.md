## Analysis

The seed report's core invariant break: **the contract's internal accounting ledger for a token amount is fixed at deposit time, decoupled from the token's actual transferable/held balance, and later payouts blindly trust the stale ledger value drawn from a shared balance pool.** In Cally this caused permanently locked rewards; in Hyperbridge's `IntentGatewayV2` the same class of bug appears in the fee-escrow path, but with a stronger consequence — the shared `feeToken` custody pool can go insolvent relative to its own ledger, causing loss/lock of other orders' redemptions.

### Title
Fee escrow ledger uses requested amount instead of measured received amount, unlike the input-token path, causing shared `feeToken` custody insolvency - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`placeOrder()` deliberately measures the *actual* tokens received for `order.inputs` via balance-before/after diffing specifically to be safe against fee-on-transfer/deflationary/rebasing-style ERC20s. The transaction-fee escrow path does not apply this same protection: it stores the *requested* `order.fees` value directly into the shared `_orders[commitment][TRANSACTION_FEES]` ledger, regardless of what the contract actually received from `safeTransferFrom`.

### Finding Description
In `placeOrder()`, input tokens are protected against transfer-amount discrepancies: [1](#0-0) 
(measuring `IERC20(token).balanceOf(address(this)) - balBefore` and writing that measured value into `order.inputs[i].amount` before it is credited to escrow).

But the fee escrow, a few lines later in the same function, skips this check entirely: [2](#0-1) 

`_orders[commitment][TRANSACTION_FEES] = order.fees;` records the *requested* amount, not what `safeTransferFrom` actually delivered. The `feeToken` is a single contract-wide ERC20 whose balance is shared across every pending order's escrowed fees and inputs — it is not a per-order isolated custody. If that token ever exhibits any transfer-amount reduction (transfer fee, deflationary burn, or a downward rebase between deposit and withdrawal), the ledger sum across all orders can permanently exceed the contract's actual token balance.

On finalize, `_withdraw()` pays out the full ledger value unconditionally: [3](#0-2) 

Because `feeToken()` balance is shared, whichever order's beneficiary calls `withdraw`/`onAccept`/`onGetResponse` first drains real tokens that the ledger says belong (in aggregate) to multiple orders. Any later order's `_withdraw` for its own `TRANSACTION_FEES` value will then revert with insufficient balance — an ordinary, unprivileged user's cross-chain settlement or refund becomes permanently stuck, exactly mirroring the "rewards accrue... and remain locked forever" impact from the seed report, except here it manifests as fund loss/lock via ledger/balance divergence rather than balance growth.

### Impact Explanation
This breaks the required invariant that "bridged assets, order escrow, refunds, paymaster balances, relayer rewards... must move exactly once and only to the rightful beneficiary and amount." A shortfall in the shared `feeToken` pool relative to the sum of `_orders[..][TRANSACTION_FEES]` entries means legitimate order fillers/cancellers cannot redeem their escrowed transaction fees — funds get stuck in the contract while other orders' beneficiaries have already consumed the actual balance meant to cover them. This is triggered purely by normal `placeOrder`/`fillOrder`/`cancelOrder` flows and requires no malicious relayer, prover, or governance action — only a `feeToken` (set once via governance param, not attacker-controlled at call time) that has any transfer-amount deviation.

### Likelihood Explanation
Low-to-moderate: it depends on the deployed `feeToken` having fee-on-transfer, deflationary, or rebasing-down behavior. The protocol's own code shows the authors are already aware of and defend against exactly this token behavior for `order.inputs`, which indicates it's a recognized threat model for this contract family — but the same protection was not applied consistently to the `TRANSACTION_FEES` accounting path, leaving an inconsistency that is directly exploitable by ordinary usage the moment such a `feeToken` is configured.

### Recommendation
Mirror the input-token pattern for the fee deposit: measure `IERC20(feeToken).balanceOf(address(this))` before and after the `safeTransferFrom`, and store the measured delta into `_orders[commitment][TRANSACTION_FEES]` instead of the raw `order.fees` value, so the ledger can never promise more than what was actually received.

### Proof of Concept
1. Governance/host configures a `feeToken` with a transfer fee or deflationary burn (e.g., 1% fee-on-transfer).
2. User A calls `placeOrder` with `order.fees = 100`; actual tokens received by the gateway are only 99 due to the token's transfer fee, but `_orders[commitmentA][TRANSACTION_FEES] = 100` is recorded (the full requested amount).
3. User B similarly places an order with `order.fees = 100`, again only 99 actually received, ledger records 100.
4. Contract's real `feeToken` balance backing fees is 198, but the ledger promises 200 total.
5. Order A finalizes first (`fillOrder`/`cancelOrder` completes and `_withdraw` runs with `finalize = true`): `safeTransfer(beneficiaryA, 100)` succeeds, consuming 100 of the real 198.
6. Order B finalizes: `_orders[commitmentB][TRANSACTION_FEES]` still reads 100, but only 98 tokens remain in the contract — `safeTransfer(beneficiaryB, 100)` reverts, permanently blocking user B's otherwise-legitimate settlement/refund until additional funds are donated to the contract.
