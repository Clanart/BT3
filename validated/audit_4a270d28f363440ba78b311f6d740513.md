## Finding

`app/src/lib/git/clone.ts` explicitly disables Git's built-in protection against the CVE-2022-39253 submodule file-protocol attack when performing recursive clones, allowing an attacker-controlled repository to trigger arbitrary local file reads on clone. [1](#0-0) 

### Title
Disabling `GIT_CLONE_PROTECTION_ACTIVE` on recursive clone reintroduces the CVE-2022-39253 submodule file-protocol arbitrary file read - (File: app/src/lib/git/clone.ts)

### Summary
Git introduced `GIT_CLONE_PROTECTION_ACTIVE` as the runtime guard for the CVE-2022-39253 fix, which blocks a malicious `.gitmodules` file from using the local `file://` transport (combined with symlinks) to read files outside the intended clone destination during a `git clone --recursive`. Desktop's `clone()` function passes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the git process environment for every recursive clone, which disables this protection unconditionally.

### Finding Description
The `clone()` function builds its execution environment for `git clone --recursive` and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`: [1](#0-0) 

This directly mirrors the broken-invariant pattern in the seed report — a downstream value (here, the safety of the recursive submodule fetch) is trusted/accepted without the guard that upstream (Git itself) provides by default, because Desktop actively turns that guard off. Just as `LRTDepositPool.depositAsset` accepted an oracle-derived mint amount with no bound, Desktop's clone path accepts a repository-controlled `.gitmodules`/submodule URL set with no bound on protocol, because the exact mitigation git ships to stop `file://` submodule abuse is disabled.

The existing `isClonePathSensitive` check in the same file only guards against the *destination path* being a sensitive location (home dir, `.ssh`, `.gnupg`, etc.); it does nothing to prevent a submodule inside the cloned repository from using a `file://` URL (or path-based local transport) to read arbitrary files elsewhere on disk during the recursive submodule clone that git performs as part of `--recursive`. [2](#0-1) 

Separately, `app/src/lib/git/submodule.ts` shows the app is well aware of this exact protection and conditionally re-enables it (`protocol.file.allow=always`) only when explicitly requested via `allowFileProtocol`, with the parameter defaulting to `false` at the checkout call sites: [3](#0-2) [4](#0-3) 

This confirms the team understands the file-protocol submodule risk and normally keeps it opt-in for post-clone submodule updates — but the initial `clone --recursive` path in `clone.ts` bypasses this by disabling the protection outright at the environment level rather than leaving Git's default (protected) behavior in place.

### Impact Explanation
An attacker who controls a public/shared repository (a normal, unprivileged capability — anyone can author a repo a victim might clone) can add a `.gitmodules` entry with a submodule URL using the `file://` transport pointing at a local path, exploiting the classic CVE-2022-39253 technique (a submodule directory replaced with a symlink to a sensitive path outside the checkout, e.g. into the user's home directory or other files on disk) to have Git copy/read arbitrary files during the recursive clone. Because `GIT_CLONE_PROTECTION_ACTIVE=false` is forced by Desktop, Git's own opt-out defense never engages, so file content that should not be reachable can be pulled into the cloned working tree — an out-of-repo file read triggered purely by cloning an attacker-authored repository.

### Likelihood Explanation
Likelihood is high for any user who clones a malicious or compromised repository through Desktop's normal "Clone repository" flow, since `--recursive` is always passed and no additional user action beyond a standard clone is required. No local/physical access, admin rights, or pre-existing malware is needed — the attacker only needs the victim to clone their repository, which is the exact ordinary Desktop workflow.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or set it to `true`/leave it unset) so Git's default CVE-2022-39253 mitigation stays active during `git clone --recursive`. If Desktop needs to allow `file://` submodules for legitimate local development flows, gate it the same way `submodule.ts`/`checkout.ts` already do — via an explicit, narrowly-scoped `allowFileProtocol` flag rather than disabling the protection for every clone.

### Proof of Concept
1. Attacker creates and publishes a repository containing a `.gitmodules` file referencing a submodule with `url = file:///` combined with a symlinked submodule directory technique consistent with the public CVE-2022-39253 PoC (submodule path replaced by a symlink pointing outside the repository, e.g., to a directory containing sensitive files).
2. Victim uses GitHub Desktop's "Clone a repository from the Internet" feature to clone the attacker's repository.
3. Desktop invokes `clone()` in `app/src/lib/git/clone.ts`, which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'` in the environment. [5](#0-4) 
4. Because Git's file-protocol submodule protection is disabled, the recursive submodule clone follows the `file://` transport/symlink to copy file contents from outside the intended clone directory into the victim's working tree, where they become readable/visible to the attacker's repository content or subsequent operations — reproducing the CVE-2022-39253 arbitrary file read.

Note: I was not able to fully trace every call site that might independently pass `allowFileProtocol=true` for checkout/pull-time submodule updates within the remaining tool budget; the finding above is scoped specifically to the `clone()` recursive-clone path, which is unambiguously and unconditionally affected.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
