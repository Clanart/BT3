### Title
Out-of-range Participant index causes index-out-of-bounds panic during DKG blame evaluation (Denial of Service) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept arbitrary `sender`/`recipient` `Participant` values and index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` without bounds checks. `Participant::new` only rejects `0`, so any index greater than `n` (or not in the DKG set) produces a `HashMap` index panic — a reachable crash of the process evaluating a blame claim, analogous to CVE-2022-21412's unauthorized hang/crash DoS.

### Finding Description
In `Decryption::decrypt_with_proof`, the ECDH key is looked up with `self.enc_keys[&decryptor]`, which panics if `decryptor` was never registered. In `BlameMachine::blame_internal`, the sender's commitments are fetched via `self.commitments[&sender]`, which panics for any sender not in the DKG's participant set:

- `crypto/dkg/pedpop/src/encryption.rs:388` — `&[self.enc_keys[&decryptor], *proof.key]`
- `crypto/dkg/pedpop/src/lib.rs:599` — `&self.commitments[&sender]`

`Participant` is defined as a non-zero `u16` (`crypto/dkg/src/lib.rs:29-35`); `Participant::new(0)` returns `None`, but values `> n` are valid `Participant`s. `AdditionalBlameMachine::new` only populates `commitments` and `enc_keys` for `1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`), and its doc-comment explicitly acknowledges this: "Usage of invalid commitments ... may cause everything from inaccurate blame to panics" (`crypto/dkg/pedpop/src/lib.rs:647-648`) — but the `blame()` entry point itself takes unchecked `sender`/`recipient` arguments that an accuser controls.

### Impact Explanation
Blame evaluation is meant to run when a participant accuses another of sending an invalid share; in a coordinator/processor deployment it can also be run by a third party (`AdditionalBlameMachine::new` requires no private key material — just the public commitments messages). Any party who can submit a blame request with a forged `sender`/`recipient` index outside `1..=n` — or simply a legitimate accusation naming a non-existent participant — causes a panic. If the host does not isolate the call, this is a complete crash of the node handling blame arbitration, matching the CVE's availability impact (unauthorized ability to cause a hang or repeatable crash). Note: blame requires a valid `EncryptedMessage`/proof path only to reach `decrypt_with_proof`; the `self.enc_keys[&decryptor]` panic occurs after the PoP signature check on `msg`, so the attacker must supply a `msg` whose PoP verifies under a `from` participant — which a real DKG participant can do. Alternatively, `blame_internal` reaches `self.commitments[&sender]` only if decryption succeeded, so the practical trigger is `decrypt_with_proof` with a valid `proof` but an out-of-range `decryptor`, which panics before verifying the proof.

### Likelihood Explanation
Reachable by any party able to invoke blame evaluation with attacker-chosen participant indexes. `Participant` has no upper bound at construction, no range check exists in `register`/`decrypt_with_proof`/`blame_internal`, and the indexing uses `HashMap`'s panicking `Index` impl. However, the practical exposure depends on the integrator routing blame requests into these APIs — Serai's own coordinator handles DKG blame via tributary transactions where participant indexes are serialized and would hit this path. Panics on arbitrary `unwrap()`/`assert!` patterns elsewhere (e.g., `Decryption::register`'s assert on duplicate registration, `crypto/dkg/pedpop/src/encryption.rs:356-358`) show the crate treats fault detection as caller responsibility, but index-panics on attacker-supplied `Participant` values are not documented as a MUST.

### Recommendation
Replace panicking `HashMap` indexers with `get` + error returns: in `decrypt_with_proof`, return `DecryptionError::InvalidProof` (or a new `UnknownParticipant` variant) when `enc_keys.get(&decryptor)` is `None`; in `blame_internal`, check `commitments.contains_key(&sender)` and return a defined outcome instead of panicking. Additionally, validate `sender <= n` and `recipient <= n` at the top of `BlameMachine::blame` / `AdditionalBlameMachine::blame`.

### Proof of Concept
```rust
// AdditionalBlameMachine over a DKG with n = 3 participants
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs)?;

// Attacker (or buggy accuser) names a non-existent recipient.
// Participant::new only rejects 0; 999 is accepted.
let attacker_chosen = Participant::new(999).unwrap();

// blame -> blame_internal -> decrypt_with_proof:
//   proof is Some(...) => reaches `self.enc_keys[&decryptor]` (encryption.rs:388)
//   or msg with valid PoP + sender out of range => `self.commitments[&sender]` (lib.rs:599)
machine.blame(attacker_chosen, attacker_chosen, msg, Some(proof));
// => thread panic: "key not found" / index out of bounds — process crash
```

This relies only on public inputs: the `sender`/`recipient` arguments and the `EncryptedMessage`/`EncryptionKeyProof` bytes fed to `blame`.
