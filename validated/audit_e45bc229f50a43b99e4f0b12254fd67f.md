### Title
Symlink-based arbitrary file deletion via `_discardChanges` untracked-file path handling - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore._discardChanges` builds filesystem paths for "discard" (trash or permanent delete) operations by joining the repository root with `file.path` values that come straight from `git status` parsing, with no containment check. Other recently-hardened code paths in this same codebase (Copilot conflict resolution) explicitly wrap equivalent repository-relative paths with `resolveWithin()` to defend against symlink/traversal escapes, but the discard-changes path was never given the same treatment.

### Finding Description
`_discardChanges` in `app/src/lib/stores/git-store.ts` iterates over the files the user asked to discard and, for `Untracked` files, resolves the on-disk path with plain `Path` operations before deleting it: [1](#0-0) 

Specifically:
- `this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))`
- `await rm(Path.join(this.repository.path, file.path))` (fallback when trash fails, or when the user has opted to always discard permanently)

`file.path` originates from `git status --porcelain=2 -z` output as parsed in `app/src/lib/status-parser.ts` / `app/src/lib/git/status.ts`, i.e. it reflects whatever is physically present in the working tree of a cloned/checked-out repository — including symlinked directories. Neither `Path.resolve` nor `Path.join` dereferences or validates symlink components; the containment check is only performed later, at the OS syscall level, which *does* follow symlinks.

This is the same class of bug the codebase has already fixed elsewhere: `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` and the Copilot resolution writer in `app/src/lib/stores/app-store.ts` explicitly call `resolveWithin(repository.path, path)` — which uses `realpath` to detect symlink escapes — before touching the filesystem: [2](#0-1) [3](#0-2) 

`_discardChanges` has no equivalent guard.

### Impact Explanation
A malicious repository can contain a committed symlink (e.g. `evil-link -> /Users/victim/Library/Application Support/GitHub Desktop/...` or any sensitive path), which Git will check out as-is (a symlink is a normal file type as far as `checkout`/`clone` is concerned). If the symlink target directory subsequently gains a file — e.g. the attacker pre-populates the pointed-to directory, or simply points the symlink at an already-existing sensitive file/directory the victim has on disk — the *symlink itself* or paths traversing through it can show up as `Untracked` in `git status`. When the user selects "Discard changes" on that entry, `moveItemToTrash`/`rm` operate on `Path.resolve(repository.path, file.path)`, and because the OS resolves the symlink component at syscall time, the operation is actually performed on the attacker-chosen target outside the repository — resulting in deletion (or trash-move) of an arbitrary file on the victim's filesystem, chosen entirely by the contents of the cloned repository. This is a "file write/delete outside the repo" primitive triggered purely by cloning a repository and using a normal UI action (Discard Changes), matching the accepted impact category.

### Likelihood Explanation
The trigger requires only: (1) the victim clones/opens a repository containing a symlink, and (2) the victim discards changes on the resulting untracked entry — a completely ordinary Desktop workflow, not an "unnatural" user step. No admin rights, local access, or leaked credentials are needed; the attacker only needs the victim to open a crafted repository, which is squarely in-scope per the task's allowed attacker model ("attacker controls a cloned/fetched repository"). The `rm(Path.join(...))` fallback path is reached whenever trash-move fails or the user has previously chosen "always discard permanently," both realistic conditions (e.g., trash unavailable/sandboxed, or default confirmation dialog behavior).

### Recommendation
Apply the same `resolveWithin(repository.path, file.path)` containment check (already used in `copilot-conflict-context.ts` and `app-store.ts`) before calling `shell.moveItemToTrash` or `rm` in `GitStore._discardChanges`, rejecting/skipping any file whose resolved real path escapes the repository root. Additionally consider detecting symlinked entries in the untracked-file set (e.g. via `lstat`) and refusing to discard them silently rather than following them.

### Proof of Concept
1. Attacker publishes a repository containing a tracked symlink `payload -> /home/victim/.ssh` (or a Windows junction equivalent) and commits it.
2. Victim clones the repository in GitHub Desktop.
3. Attacker (or a subsequent commit/checkout) causes a file to appear underneath the symlink target such that `git status --porcelain=2 -z` reports `payload/somefile` (or the symlink `payload` itself) as `Untracked`, surfaced in the Changes list.
4. Victim selects the entry and clicks "Discard Changes." `GitStore._discardChanges` computes `Path.resolve(repository.path, 'payload/somefile')`, which the OS resolves through the `payload` symlink to `/home/victim/.ssh/somefile`, and either trashes or `rm`s it — deleting a file entirely outside the cloned repository, driven solely by repository content.
