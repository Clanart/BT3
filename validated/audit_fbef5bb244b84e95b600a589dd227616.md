Found a genuine local analog. The Tron `IntentGatewayV2` contract lacks the parameter-validation guard that the mainline EVM `IntentGatewayV2`/`IntentsBase` enforces before accepting cross-chain governance parameter updates.

### Title
Missing `Params` validation in Tron `IntentGatewayV2.onAccept(UpdateParams)` allows host/dispatcher misconfiguration and permanent bricking or fund misdirection - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
On the mainline EVM `IntentGatewayV2`, every path that writes `_params` — both local `initialize()` and the cross-chain governance `UpdateParams` handler — is routed through `IntentsBase._validateParams`, which rejects a zero/non-contract `host`, zero/non-contract `dispatcher`, `surplusShareBps > 10_000`, `protocolFeeBps >= 10_000`, and a non-contract `priceOracle` [1](#0-0) , applied in `_updateParams` [2](#0-1)  and in `initialize` [3](#0-2) .

The Tron variant of the same contract has no such validation function at all. Its local `setParams` directly assigns `_admin`-supplied params with no checks [4](#0-3) , and its cross-chain governance handler for `RequestKind.UpdateParams` decodes the `ParamsUpdate` and overwrites `_params` unconditionally: `_params = update.params;` with no bounds or non-zero checks on `host`, `dispatcher`, `surplusShareBps`, or `protocolFeeBps` [5](#0-4) .

### Finding Description
This is a direct structural analog to the reported bug class: a config value (here, `Params.host`, `.dispatcher`, `surplusShareBps`, `protocolFeeBps`) is written into permanent contract state with no invariant checks, exactly like the unchecked `lp_wallet`/`sol_deposited` in the original report. The corrupted values are `_params.host`, `_params.dispatcher`, `_params.surplusShareBps`, `_params.protocolFeeBps` in the Tron `IntentGatewayV2`.

Concretely:
- `_params.surplusShareBps` gates the split of solver surplus between beneficiary and protocol in `_fillCrossChain`: `protocolShare = (dust * _params.surplusShareBps) / 10_000` [6](#0-5) . Mainline caps this at `10_000` (100%) via `_validateParams`; the Tron path has no such cap, so a value above `10_000` would let `protocolShare` exceed `dust`, and downstream token transfers (`safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` and the separate `protocolShare` transfer) would attempt to move more than the solver ever intended to pay, causing over-debiting of the solver or reverting the fill entirely (locking every subsequent fill for that order).
- `_params.protocolFeeBps` is applied unchecked against user input escrow amounts in `placeOrder`: `protocolFee = (originalAmount * protocolFeeBps) / 10_000` [7](#0-6) . Mainline requires `protocolFeeBps < 10_000`; without that cap on Tron, a value `>= 10_000` makes `reducedAmount = originalAmount - protocolFee` underflow-adjacent or leave zero/negative funds escrowed for the user's declared order — silently breaking the fee-accounting invariant and potentially letting escrowed amounts diverge from what the user intended, since `reducedAmount` (not `originalAmount`) becomes both the commitment input and the escrow credit.
- `_params.host`/`_params.dispatcher` being writable to zero or an EOA (no `code.length` check as mainline performs) can permanently brick the gateway: `host()` returns `_params.host`, and `onlyHost` (from `HyperApp`) gates every incoming settlement (`RedeemEscrow`, `RefundEscrow`) and future governance message. If `_params.host` is set to a non-existent/wrong address, `onlyHost` will never match any live host and all escrowed funds under existing orders become permanently unwithdrawable — the same "cannot call withdraw"/fund-lock outcome flagged in the original report.

Why existing guards don't stop this: the only gate on the `UpdateParams` path is a source check (`keccak256(incoming.request.source) == hyperbridge`) confirming the message came from Hyperbridge governance [8](#0-7) . That authenticates *who* sent the update but performs no validation of *what* was sent. There is no analog to `_validateParams` anywhere in the Tron file.

### Impact Explanation
This produces the same class of harm as the seed report: loss/lock of escrowed user funds and inconsistent accounting caused purely by the absence of a bounds/zero-address check on a governance-writable configuration struct, reachable without any malicious relayer/prover/admin assumption beyond the ordinary (trusted) Hyperbridge governance message flow that mainline itself treats as needing validation. Once `_params.host` is corrupted, escrow held by the contract for outstanding orders becomes permanently unreachable since `withdraw()` can only be invoked through `onAccept`, gated by `onlyHost` against the now-wrong host address.

### Likelihood Explanation
Governance parameter updates for the Tron deployment are an expected, routine, in-scope operational flow (mirrored exactly by the mainline EVM contract, which found it important enough to validate on both `initialize` and `onAccept(UpdateParams)`). Any operational mistake in constructing the ABI-encoded `Params` for the Tron chain — e.g. omitting a field, copy-paste from a different chain's config, or an off-by-one in fee-bps units — silently corrupts live state with no revert, unlike the mainline path which would revert with `InvalidInput()` at the exact same governance step.

### Recommendation
Port `IntentsBase._validateParams` (host non-zero/has code, dispatcher non-zero/has code, `surplusShareBps <= 10_000`, `protocolFeeBps < 10_000`, `priceOracle` zero-or-has-code) into the Tron `IntentGatewayV2`, and call it from both `setParams` and the `onAccept` `UpdateParams` branch before assigning `_params`, exactly as done in the mainline contract's `initialize`/`_updateParams`.

### Proof of Concept
1. Deploy Tron `IntentGatewayV2` and place an order that escrows tokens (`placeOrder`) — funds now sit in `_orders[commitment][token]`.
2. As Hyperbridge governance, dispatch a `RequestKind.UpdateParams` message whose `ParamsUpdate.params.host` is set to an address with no code (or unrelated address) — no local check exists to reject this, unlike mainline's `_validateParams` which would revert with `InvalidInput()` on `p.host.code.length == 0`.
3. `onAccept` executes: `_params = update.params;` unconditionally [9](#0-8) .
4. `host()` now returns the corrupted address; all subsequent `onAccept` calls for `RedeemEscrow`/`RefundEscrow` fail `onlyHost`, and the previously escrowed tokens for the earlier order can never be withdrawn — a permanent fund lock caused solely by the missing input validation, matching the seed report's outcome where an unchecked address write blocks legitimate withdrawal of protocol-entitled or user-entitled funds.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }
