### Title
Silently ignored `SendCoinsAndWei` failure in EVM `EndBlock` fee-surplus sweep permanently strands per-transaction coinbase funds - (File: `x/evm/keeper/abci.go`)

### Summary
`x/evm/keeper/abci.go`'s `EndBlock` sweeps every EVM transaction's ephemeral per-tx coinbase balance (usei + wei) to the real coinbase/fee-collector account via `k.BankKeeper().SendCoinsAndWei(...)`. If that call returns an error, the code only logs it and continues, exactly mirroring the reported bug class: a value-transfer call whose failure is silently swallowed instead of being validated/handled, leaving funds detached from any account that is normally swept or reachable again.

### Finding Description
In `EndBlock`, for every `deferredInfo` in `evmTxDeferredInfoList`, the keeper computes the per-transaction ephemeral coinbase address via `state.GetCoinbaseAddress(idx)` [1](#0-0) , and then attempts to move its `usei`/`wei` balance to the block's real coinbase (fee collector) address:

```go
if err := k.BankKeeper().SendCoinsAndWei(ctx, coinbaseAddress, coinbase, balance, weiBalance); err != nil {
    logger.Error("failed to send usei surplus to coinbase account", "from", coinbaseAddress, "err", err)
}
``` [2](#0-1) 

The error is only logged; execution proceeds unchanged, exactly the "message not sent, dropped silently, and no error is surfaced" pattern from the report. The same pattern repeats twice more, immediately below, for sweeping the ante-handler surplus into the EVM module account via `AddCoins`/`AddWei`:

```go
if err := k.BankKeeper().AddCoins(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), sdk.NewCoins(sdk.NewCoin(k.GetBaseDenom(ctx), surplusUsei)), true); err != nil {
    logger.Error("failed to send usei surplus to EVM module account", "surplus", surplusUsei)
}
...
if err := k.BankKeeper().AddWei(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), surplusWei); err != nil {
    logger.Error("failed to send wei surplus to EVM module account", "surplus", surplusWei)
}
``` [3](#0-2) 

The per-tx coinbase address (`state.GetCoinbaseAddress(idx)`) is documented as ephemeral — "Its account state and balance will be deleted before the block commits" [4](#0-3)  — and the AGENTS.md doc for the module states "each transaction gets a deterministic coinbase address for collecting fee surplus, which is swept to the fee collector at end-of-block" [5](#0-4) . If the sweep in `SendCoinsAndWei` fails for any reason (e.g. `BlockedAddr` on the recipient, an invariant/locked-coins edge case in `SubWei`/`AddWei`, or any other error surfaced from `BaseSendKeeper.SendCoinsAndWei`) [6](#0-5) , the balance is left sitting at the per-tx ephemeral coinbase address instead of being swept, exactly the class described by the report: "the message is not sent... funds can be lost, or the system state can become out of sync between contracts."

### Impact Explanation
Every EVM transaction executed on the chain deterministically derives its own per-tx coinbase address and expects its gas-fee surplus to be swept there each block. If the sweep silently fails, the usei/wei balance becomes stranded at that ephemeral, non-swept address rather than reaching the fee collector — a real, permanent loss of protocol fee revenue with no error surfaced to any downstream consumer (no panic, no failed block, no visible on-chain signal beyond a log line). Because this runs unconditionally in `EndBlock` for every block that processed at least one EVM transaction, a single tolerable-but-erroring condition (e.g., transient invariant/locked-coin mismatch or a blocked recipient scenario) can cause repeated, chain-wide fee loss without validators or operators being alerted through normal transaction/error-code paths.

### Likelihood Explanation
This path executes on literally every block containing EVM transactions, so the reachable-surface is essentially guaranteed. What determines exploitability is whether `SendCoinsAndWei`/`AddCoins`/`AddWei` can realistically fail under adversary-influenced conditions (e.g., a transaction that manipulates the sender's locked coins, or attempts to overflow/underflow the wei sub-balance ledger) — the code path was clearly anticipated to be fallible (an `if err != nil` check exists), yet the failure mode chosen is "log and drop" rather than "retry, refund, or halt," matching the report's core criticism precisely.

### Recommendation
Do not silently swallow the error from the surplus-sweep calls in `EndBlock`. At minimum, retry or fall back to a safe recipient (e.g., re-credit the ante surplus / re-attempt against the module account), emit a chain event so it is auditable, and add an invariant/metric that alerts when this path errors so operators can detect stranded funds. Following the report's long-term recommendation, add tests that specifically trigger a `SendCoinsAndWei` failure in this sweep (e.g., a blocked or locked-coins scenario) to verify funds are not lost.

### Proof of Concept
1. Craft or trigger a scenario where the per-tx ephemeral `coinbaseAddress` for some `deferredInfo.TxIndex` has `LockedCoins` or another bank invariant condition that causes `BankKeeper().SendCoinsAndWei` to return a non-nil error at `x/evm/keeper/abci.go:130` (e.g., through interaction with `LockedCoins` accounting or a blocked-address collision on the derived ephemeral address).
2. Observe that `EndBlock` only calls `logger.Error(...)` and continues; the ExecTxResult/receipt for that transaction is unaffected and no revert occurs.
3. Query the bank balance of `state.GetCoinbaseAddress(idx)` after block commit and confirm the usei/wei surplus remains there rather than at the fee collector, and that no subsequent block logic ever revisits or re-sweeps that specific historical ephemeral address (each `idx` is only swept once, in the block it was produced), confirming the funds are permanently stranded.

func (k BaseSendKeeper) SendCoinsAndWei(ctx sdk.Context, from sdk.AccAddress, to sdk.AccAddress, amt sdk.Int, wei sdk.Int) error {
	if err := k.SubWei(ctx, from, wei); err != nil {
		return err
	}
	if err := k.AddWei(ctx, to, wei); err != nil {
		return err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeWeiTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, to.String()),
			sdk.NewAttribute(types.AttributeKeySender, from.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, wei.String()),
		),
	})
	if amt.GT(sdk.ZeroInt()) {
		return k.SendCoinsWithoutAccCreation(ctx, from, to, sdk.NewCoins(sdk.NewCoin(sdk.MustGetBaseDenom(), amt)))
	}
	return nil
}
