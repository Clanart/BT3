### Title
`ManualCompound.compound()` sweeps the contract's entire current token balance to any caller instead of only the amount they earned - (File: `rewards/ManualCompound.sol`)

### Summary
This is a valid analog of the reported bug class. The external report's root cause is that a component's execution logic doesn't restrict itself to funds it legitimately owns, letting a caller access balances/components it has no claim to. In `ManualCompound.compound()`, the same pattern occurs: reward tokens are swept from the contract using `IERC20(token).balanceOf(address(this))` rather than an amount tied to what the caller actually earned in that transaction, and the token addresses checked are entirely caller-supplied with no verification that they correspond to the `_lps` the caller claimed from.

### Finding Description
`compound()` first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0)  which routes the claimed reward tokens into the `ManualCompound` contract. It then does two sweeps:

1. Non-compoundable rewards: for every token address in the caller-supplied `_rewards[i][j]` array, if that token is not in `compoundableRewards`, the **entire current balance** of that token held by the contract is sent to `msg.sender`: [2](#0-1) 

2. Compoundable rewards: for every registered reward token, the **entire current balance** is again pulled from `balanceOf(address(this))` and routed to converter/locker/helper/caller: [3](#0-2) 

Neither loop tracks a before/after balance diff scoped to the current call, and the `_rewards[i][j]` addresses are never cross-checked against what `_lps[i]` actually holds as reward tokens for that pool, or against what was actually harvested for `msg.sender` in this call (unlike, e.g., `WombatStaking._toMasterWomAndSendReward`, which correctly uses before/after diffs — see `wombat/WombatStaking.sol:671-696`). This means any residual/dust balance of a token sitting in the contract (from rounding, a partially processed prior `compound()` call, or a direct transfer) can be claimed in full by the next arbitrary caller simply by naming that token address in `_rewards`, with no requirement that the caller's own claim generated that balance. This mirrors the report's core issue: a shared component (token balances held by a shared contract) is reachable without restricting access to the actor's own funds.

### Impact Explanation
Any unprivileged wallet can call `compound()` with a crafted `_rewards` array to drain non-compoundable token balances, or trigger `receivedBalance`-based conversion/locking of registered reward tokens, that were not earned by them but happen to be resting in the `ManualCompound` contract. This is a direct theft of yield belonging to other users/the protocol, satisfying the "theft or permanent freezing of unclaimed yield" impact bar.

### Likelihood Explanation
Likelihood depends on the contract regularly holding a non-zero balance of some token between calls (e.g., due to rounding remainders, dust from `safeApprove`/`safeTransfer` operations, or reward tokens that were fetched via `multiclaimOnBehalf` for one caller but not fully routed out in the same transaction for a legitimately unrelated `_rewards[i][j]` entry). Any user calling `compound()` with an empty or minimal `_lps` and their own crafted `_rewards` entry naming a token with a stray balance can immediately claim it — no special timing or admin action required, making this reachable purely from an ordinary wallet's transaction.

### Recommendation
Track exact amounts received per call (before/after balance diffs scoped to the specific `_lps`/reward tokens claimed for `msg.sender` in that transaction) rather than sweeping `balanceOf(address(this))`. Additionally, validate that `_rewards[i][j]` tokens are consistent with the actual reward tokens configured for `_lps[i]`, so a caller cannot name arbitrary token addresses to sweep unrelated balances.

### Proof of Concept
1. Assume `ManualCompound` accumulates a small non-zero balance of token `X` (not in `compoundableRewards`) from normal operation (rounding dust, or a user's prior `compound()` call that under-swept due to a reentrancy-safe partial transfer, or a direct/accidental transfer to the contract).
2. An attacker calls `compound(_lps, _rewards, ...)` where `_lps` is an array of pools they hold (even trivial/zero-value positions) and `_rewards[0] = [X]`.
3. Inside `compound()`, since `compoundableRewards[X]` is `false`, the loop executes `IERC20(X).balanceOf(address(this))` and transfers the **full** balance of `X` to the attacker: [4](#0-3) , regardless of whether the attacker's own claim generated any of that `X` balance.

**Uncertainty note:** I could not fully verify from the indexed context whether `_claimBaseRewarder`/`multiclaimOnBehalf` in `rewards/MasterMagpie.sol` ever leaves reward tokens unswept in a way that guarantees non-zero dust balances in normal operation (i.e., how reliably the precondition in step 1 is triggered). Confirming the exact frequency/certainty of residual balances would require reviewing `_claimBaseRewarder` and `BaseRewardPool` claim logic in full, which was not completely available in the indexed context — a Devin session with full repo access could trace this precisely.
