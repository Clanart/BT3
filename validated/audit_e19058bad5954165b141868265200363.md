### Title
PedPoP releases ECDH blame key before the message's proof-of-possession is verified, letting an attacker decrypt a victim's share message - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
The DKG encrypts each participant-to-participant secret share with ChaCha20 under an ECDH key `enc_key_recipient * msg.key`, where `msg.key` is a per-message ephemeral public key supplied inside the attacker-controlled `EncryptedMessage`. A Schnorr proof-of-possession (`pop`) exists specifically to stop an attacker from copying a victim's `msg.key` into their own message, because doing so would cause the blame procedure to reveal the victim's ECDH shared key. However, `Encryption::decrypt` applies the keystream and returns the blame `EncryptionKeyProof` (containing the shared key `enc_key * msg.key` plus a DLEq proof) immediately, while the `pop` signature is only *queued* into a `BatchVerifier` that runs later. In `KeyMachine::calculate_share`, a non-canonical decrypted share triggers an early `Err` return carrying `blame: Some(...)` *before* `batch.verify_with_vartime_blame()` is ever invoked — so the PoP is never checked, and the shared key is published anyway. ### Finding Description
`Encryption::decrypt` (encryption.rs:469-501) does three things: (1) queues `msg.pop` for batch verification, (2) computes `key = ecdh(&self.enc_key, msg.key)` and decrypts the message in place, (3) returns `(msg, EncryptionKeyProof { key, dleq })`. No synchronous PoP check occurs; verification is deferred to the caller's batch.

In `KeyMachine::calculate_share` (lib.rs:476-482), each share is decrypted and immediately parsed with `C::F::from_repr`. If parsing fails, the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` at once. The `batch.verify_with_vartime_blame()` call at line 493 is only reached if *all* shares parse — so for the faulting share, the queued PoP statement is never verified. The blame proof is then propagated outward: `processor/src/key_gen.rs:419-425` serializes it into `ProcessorMessage::InvalidShare`, and `CoordinatorMessage::VerifyBlame` (key_gen.rs:504-549) feeds it to `AdditionalBlameMachine::blame` → `decrypt_with_proof`, which treats the revealed `key` as valid for decrypting the message.

The comment on `EncryptedMessage` (encryption.rs:84-88) describes exactly this attack — Eve reuses Alice's key `X`, triggers blame, and Bob's reveal of `bX` decrypts Alice's message — and states the `pop` exists to prevent it. The mitigation is correct in design but defective in ordering: because decryption and blame-key generation precede the deferred PoP verification, any path that aborts before `batch.verify_*` releases the ECDH key for a message whose `key` field the sender never proved ownership of.

### Impact Explanation
An unprivileged protocol participant (anyone able to send an `EncryptedMessage` to a victim participant `i`) can force disclosure of `enc_key_i * X` for *any* point `X` they choose, including `X` copied from a third party's `EncryptedMessage` observed on the wire or obtained from blame transcripts. Concretely: Eve copies `msg.key = aG` from Alice's encrypted share message to Bob, attaches arbitrary ciphertext plus a garbage `pop` (never verified), and sends it to Bob. Bob's `calculate_share` fails `from_repr` with high probability (a random 32-byte string is a non-canonical Ed25519/Ristretto scalar in the overwhelming majority of cases) and emits a blame proof containing `b*aG` — exactly the ChaCha20 shared key protecting Alice's share to Bob. Anyone who sees the published blame (the protocol requires broadcasting it so all participants can adjudicate via `AdditionalBlameMachine`) can derive the cipher via `cipher(context, b*aG)` and decrypt Alice's ciphertext, recovering the secret share Alice sent to Bob. Repeating across senders recovers every share constituting Bob's secret key share — full threshold key share recovery, breaking confidentiality of the DKG even though the channel was only assumed authenticated, not private. This matches the advisory's class: unauthenticated attacker reaches a library API with attacker-controlled input and obtains unauthorized access to secret data.

### Likelihood Explanation
Exploitation requires only sending one malformed `EncryptedMessage` to a victim during DKG round 2 — no collusion, no threshold compromise, no special position. The attacker does not need to know any secret; `msg.key` is attacker-chosen and the PoP is bypassed rather than forged. The only requirement is that the victim publishes the blame proof, which is the protocol-mandated behavior on `InvalidShare` errors (the processor serializes and broadcasts it). The probability the early `from_repr` error triggers is near 1 per attempt for arbitrary ciphertext (canonical scalars occupy roughly `l/2^256 ≈ 1/16` of the space), and even if a share accidentally parses, a second attempt with different ciphertext retries. Deterministic, cheap, single-message attack.

### Recommendation
Verify `msg.pop` synchronously inside `Encryption::decrypt` *before* performing the ECDH/decryption and before constructing the `EncryptionKeyProof`, returning a distinct error (e.g., `InvalidSignature`) that carries `blame: None` — mirroring how `decrypt_with_proof` already checks `msg.pop.verify(...)` first at encryption.rs:374-379. Alternatively, keep batching for performance but suppress the `EncryptionKeyProof` (emit `None` blame) whenever the function returns early before `batch.verify_*` has confirmed the queued PoP statement. Also consider rejecting the identity point for `msg.key`/`enc_key` via `Curve::read_G`-style checks so a degenerate ECDH cannot produce a publicly known shared key.

### Proof of Concept
1. Run an n=5, t=3 PedPoP `KeyGenMachine` session over `Ristretto` with `CONTEXT`. Participants 1..5 complete `generate_coefficients` and `generate_secret_shares`, producing per-recipient `EncryptedMessage<C, SecretShare<C::F>>` values.
2. Attacker (participant 4) copies `msg.key` and `msg.msg` handling as follows: take Alice's (participant 1) share message to Bob (participant 2); extract `key_A = msg.key` (`aG`) and ciphertext `ct_A`.
3. Attacker constructs `EncryptedMessage { key: key_A, pop: <garbage or self-signed SchnorrSignature>, msg: <arbitrary 32 bytes> }` and sends it to Bob as the attacker's share. Note `pop` need not verify under `key_A` — it is only queued in `BatchId::Decryption(4)`.
4. Bob runs `calculate_share`. `self.encryption.decrypt(...)` computes `ecdh(enc_key_bob, key_A) = b·aG` (the same shared key protecting Alice's real share to Bob), decrypts the garbage to bytes that fail `C::F::from_repr` (~15/16 chance, retry otherwise), and returns `InvalidShare { participant: 4, blame: Some(EncryptionKeyProof { key: b·aG, dleq }) }` — before `batch.verify_with_vartime_blame()` ever checks the attacker's `pop`.
5. The blame is broadcast per `processor/src/key_gen.rs:419-425`. Attacker computes `cipher(context, b·aG)` and applies the keystream to `ct_A` from step 2, recovering Alice's secret share to Bob.
6. Repeat against each sender's message to Bob (all use Bob's `enc_key`), recovering all shares summing to Bob's secret key share — key share recovery by a single malicious participant.

Concrete check (test-only scaffolding exists): `invalidate_pop` (encryption.rs:192-194) already mutates `pop.s` to an invalid signature; pairing that with a copied `key` and non-canonical ciphertext produces the early `InvalidShare { blame: Some(..) }` path with a guaranteed-invalid PoP, demonstrating the PoP is never evaluated before the ECDH key is released.
