### Title
Cached FROST preprocess reused across distinct signing evaluations because the cache key omits the participant set and message — nonce reuse enables secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Linea report's bug class is a mapping keyed by an identifier missing a discriminating dimension (token address without chain ID), so the same key resolves to inconsistent state across two evaluations and a second evaluation completes against the wrong state. `SigningProtocol::preprocess_internal` exhibits the same shape: the deterministic FROST nonce seed is cached in `CachedPreprocesses` keyed only by `self.context` — for `DkgConfirmer` just `(b"DkgConfirmer", attempt)` — while the actual signing inputs (`participants`, and the `msg` derived from `key_pair`/`removed`) are *not* part of the key. Every call to `share_internal` (reached by both `DkgConfirmer::share` and `DkgConfirmer::complete`) rebuilds an `AlgorithmSignMachine` from that same seed via `AlgorithmSignMachine::from_cache`, producing identical nonces, and then calls `sign` with whatever `preprocesses` map and `msg` were supplied to *that* call.

### Finding Description
`preprocess_internal` stores/loads a `CachedPreprocess` under `CachedPreprocesses::set(self.txn, &self.context, ...)` / `::get(self.txn, &self.context)` where the context is only `(&'static [u8; 12], u32)` (`(b"DkgConfirmer", self.attempt)`). The `keys`/`participants` and the message are inputs to `share_internal`, not to the cache key. `from_cache` → `seeded_preprocess` feeds the seed into `ChaCha20Rng` to derive `nonces` deterministically, so all calls under one context share `d, e`. `share` and `complete` are two separate public entry points that each call `share_internal` with independently supplied `preprocesses`/`key_pair`. If the effective signing tuple differs between the two evaluations — different counterparty preprocess sets (which change the binding factors `rho` and the signing set) or a different `key_pair`/`removed` (changing `msg` via `set_keys_message`) — the same nonce pair is committed to two different challenges `c1 ≠ c2`. Two shares `s_i = d + rho·e + λ_i·c_i·secret_share` with identical `d + rho·e` and different challenges yield the secret share by `(s1 − s2) / (λ·(c1 − c2))`. The file's own safety argument concedes this is only prevented because BFT is assumed to deliver identical inputs to both evaluations: "In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again."

### Impact Explanation
Recovery of a validator's MuSig secret share under the validator-set key. Since these are the validators' root-of-trust keys used to confirm DKG results on Substrate (`set_keys_message`), a recovered share undermines the threshold assumption for validator-set signing; combined with threshold-many compromised or reconstructed shares this enables forging validator confirmations. This is a secret-leakage / unintended-signature impact, not merely a logic anomaly.

### Likelihood Explanation
The leak requires `share_internal` to be invoked twice under the same `(b"DkgConfirmer", attempt)` context with inputs that differ in any component affecting the share equation — the counterparty `preprocesses` map (supplied per-call and attacker-influenced by validators' tributary messages) or `key_pair`. `share` and `complete` are structurally two independent evaluations over independently supplied maps, so the only guard is the BFT ordering assumption rather than anything enforced in this code or bound into the cache key. Any inconsistency between the two evaluations — e.g., a validator supplying different preprocess bytes in the share round versus the complete round, or a logical flaw letting messages be rewritten — converts directly into nonce reuse. Likelihood is bounded by the integrity of the tributary ordering layer, making it conditional but nonzero, since no local check (e.g., the acknowledged TODO of verifying on-chain commitments match the cached preprocess) prevents re-signing under divergent inputs.

### Recommendation
Bind the cached preprocess to the full evaluation inputs, not just the context: include a hash of the participant set and the message (or `key_pair` + `removed` set) in the `CachedPreprocesses` key, and refuse to `sign` a second time under the same context with different inputs. Alternatively, persist the decided `(participants, msg)` alongside the seed on first use and assert equality on every subsequent `share_internal` call, so any inconsistent second evaluation aborts instead of reusing the nonce. Implement the noted TODO of checking published commitments against the cached preprocess before emitting shares.

### Proof of Concept
1. A `DkgConfirmer` is created for `attempt = a`; `share(preprocesses_A, key_pair)` is invoked. `share_internal` → `preprocess_internal` caches seed `S` under key `(b"DkgConfirmer", a)` and signs with nonces `(d, e)` derived from `ChaCha20Rng::from_seed(S)` against preprocess set A, emitting share `s1 = d + rho_A·e + λ·c1·x`.
2. `complete(preprocesses_B, key_pair, shares)` is invoked where `preprocesses_B` differs from `preprocesses_A` (a validator submits altered preprocess bytes in the later round). `share_internal` reloads `S` from `CachedPreprocesses` — the key `(b"DkgConfirmer", a)` does not cover the preprocesses — rebuilds identical `(d, e)` via `from_cache`, and `sign` computes a different binding factor/challenge `c2`, emitting/using share `s2 = d + rho_B·e + λ·c2·x`.
3. Anyone observing `s1` and `s2` (broadcast shares) recovers `x = (s1 − s2)·(λ·(c1 − c2))^{-1}`, i.e., the validator's secret share, since the nonce contribution `d + rho·e` is identical in both equations.
