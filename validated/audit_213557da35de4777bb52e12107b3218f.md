### Title
Partial-commit line selection is index-based and not revalidated against a freshly-fetched diff, allowing a changed working tree to silently corrupt what gets committed - (File: app/src/lib/git/apply.ts, app/src/lib/stores/updates/changes-state.ts)

### Summary
`DiffSelection` (the "poke"-equivalent recomputation surface here) tracks which lines a user wants to commit purely by absolute line index into a diff, with no binding to the diff's content or shape. Two places in the codebase reuse or re-derive this index-based selection against a diff that is *not guaranteed to be the same diff the user reviewed*: `updateChangedFiles` blindly carries an old selection onto a newly-fetched file/diff object keyed only by file id, and `applyPatchToIndex` re-fetches the working-directory diff from disk at commit time and re-applies the (possibly stale) selection's `isSelected(absoluteIndex)` against it. If the underlying file content shifts between the time the user made a partial selection and the time the commit patch is generated, the index-based selection silently maps onto different lines than what the user saw and approved.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `withRangeSelection` operate purely on numeric line indices with no notion of the diff content they were computed against: [1](#0-0) 

When the working directory state is refreshed, `updateChangedFiles` merges the new status into state by matching files by `id` (path) and reusing the *previous* selection object verbatim, without checking whether the diff shape (hunks/line offsets) for that file has changed: [2](#0-1) 

At commit time, `_commitIncludedChanges` takes the currently cached `workingDirectory.files` (with their cached `DiffSelection`) straight from `repositoryStateCache` and passes them to `createCommit`: [3](#0-2) 

`createCommit`/`applyPatchToIndex` then re-fetches the diff fresh from disk (`getWorkingDirectoryDiff`) — i.e., a *new* diff, potentially with different line offsets than the one the user actually reviewed — and builds the patch by testing `file.selection.isSelected(absoluteIndex)` against this new diff's line indices: [4](#0-3) [5](#0-4) 

There is no guard comparing the diff that produced the `DiffSelection` (e.g. via `withSelectableLines`) to the diff being patched. `isSelectable`/`selectableLines` only filters which indices *can* be toggled from the UI; it is never used at apply time to confirm the diff hasn't drifted: [6](#0-5) 

### Impact Explanation
This breaks the invariant that "the lines a user visually selected in the diff view are the lines that end up committed." If the tracked file's content on disk changes between diff display and commit — e.g. via an editor auto-save/format-on-save, a background process, or content rewritten by tooling shipped in a cloned/fetched repository (build scripts, generated files, filters) — a previously "safe" line-range selection can silently map onto entirely different, attacker-influenced lines in the new diff. The result is that GitHub Desktop can create and push a commit whose contents do not match what the user reviewed and approved, matching the "silent corruption of what the user commits or pushes" impact class named in the report's valid-impact list.

### Likelihood Explanation
The window between diff computation (shown to the user, used to build `DiffSelection`) and commit-time diff re-fetch is real and unbounded in normal Desktop usage (users can leave a partial selection pending indefinitely while other tools/processes touch the working tree, and Desktop's own background refresh cycle (`_refreshRepository` → `refreshChangesSection`) re-runs status/diff independently of the pending selection). No content hash, diff revision counter, or hunk-shape check exists anywhere in `DiffSelection`, `updateChangedFiles`, or `applyPatchToIndex` to detect drift, so the class of bug is reachable through the normal commit code path, not a hypothetical. That said, triggering a *malicious* line-offset shift specifically requires some external actor/process to rewrite the tracked file's content at the right moment, which is a meaningfully narrower condition than the fully unauthenticated, single-call trigger in the original `poke()` report — this weakens confidence versus a directly-reachable, no-precondition exploit.

### Recommendation
Bind `DiffSelection` to the diff it was computed from (e.g., a content hash or diff revision id of the hunks) and re-fetch/re-validate the diff shape immediately before building the commit patch, rejecting or re-prompting the user if the working-directory diff has changed shape since the selection was made, rather than blindly reusing indices from a stale diff. `updateChangedFiles` should likewise discard or renormalize a file's `selection` whenever the new diff's line/hunk structure diverges from the one that originally produced it, instead of always carrying it forward keyed only by path.

### Proof of Concept
1. Open a repository in GitHub Desktop with a tracked file `foo.txt` containing several lines; modify it so the Changes view shows a multi-hunk diff.
2. Partially select only specific lines (e.g., lines 10-12) via the side-by-side diff UI, building a `DiffSelection` whose diverging indices are 10-12 against the *current* diff shape (`side-by-side-diff.tsx` `onEndSelection` → `withLineSelection`) — see [7](#0-6) .
3. Before clicking "Commit", have another process (editor auto-format, background script, or a tool bundled in the project) rewrite `foo.txt`, shifting line numbers so that indices 10-12 in the *new* diff correspond to different content than what was originally selected.
4. Click "Commit". `_commitIncludedChanges` uses the cached `WorkingDirectoryFileChange` (with the old `DiffSelection`) [3](#0-2) ; `applyPatchToIndex` re-fetches the diff from disk and applies `selection.isSelected(absoluteIndex)` against the new hunks [8](#0-7) .
5. Inspect the resulting commit: it contains the lines at indices 10-12 of the *new* diff, not the content the user actually reviewed and intended to select — demonstrating silent corruption of the committed content.

Note: I was not able to fully trace every background-refresh trigger (e.g., exact timing of `repositoryIndicatorUpdater`/focus-based refresh races) within the indexed portion of the codebase, so the precise minimal timing window for exploitation is not fully confirmed from local code alone; a Devin session with full repo/file access would be needed to verify the exact race conditions and any existing mitigations not captured by the index.
