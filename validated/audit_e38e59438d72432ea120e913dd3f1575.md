### Title
Unrestricted self-place/self-fill on `IntentGatewayV3` lets an attacker double-claim reward points for the same order - ([File: sdk/packages/indexer/src/services/intentGatewayV3.service.ts])

### Summary
The external report describes a Nested Finance bug where a user could copy their own portfolio and receive royalty shares from themselves, repeating this to farm rewards indefinitely because no check prevented the "copier" and "original creator" from being the same address. The same broken invariant — no check that reward-earning roles are distinct actors — exists in Hyperbridge's intent reward-points pipeline: the same wallet can be both `order.user` (placer) and `filler` (solver) on the same `OrderV3`, and the indexer independently credits `ORDER_PLACED_POINTS` to the user and `ORDER_FILLED_POINTS` to the filler for that single order, with no self-dealing guard.

### Finding Description
`IntentGatewayV3Service.getOrCreateOrder` awards `ORDER_PLACED_POINTS` to `order.user` when an order is placed: [1](#0-0) 

`IntentGatewayV3Service.updateOrderStatus` separately awards `ORDER_FILLED_POINTS` to `filler` when the same order transitions to `FILLED`: [2](#0-1) 

Both code paths call `PointsService.awardPoints`, which unconditionally adds `points` to the `RewardPoints` balance keyed by `(address, chain, earnerType)` — it performs no check that `address` (filler) differs from the order's `user`, and no check that the same wallet isn't earning both roles on the same commitment: [3](#0-2) 

Nothing in `IntrinsicIntents._fillSameChain` (the on-chain fill path that emits the `OrderFilled`/`filler` data the indexer consumes) restricts `msg.sender` (the filler) from being the same address as `order.user`: [4](#0-3) [5](#0-4) 

This is structurally identical to the seed bug: a single actor holds two "roles" in the reward accounting (creator/copier there, user/filler here), and the system pays out to both roles without checking they are distinct, letting the actor collect a reward stream from acting against themselves.

### Impact Explanation
An attacker can place a same-chain order with `order.user = A` and immediately fill it themselves with `msg.sender = A` (self-fill, escrow released back to `A`, net cost is only the protocol dust/fee and gas). The indexer will:
1. Credit `A` with `ORDER_PLACED_POINTS` = floor(orderValueUSD) as `USER`.
2. Credit `A` with `ORDER_FILLED_POINTS` = floor(orderValueUSD) as `FILLER` for the same commitment.

Repeating this loop (place → self-fill → place → self-fill…) lets `A` accumulate `RewardPoints` at roughly `2×orderValueUSD` per cycle with no real bridging activity and near-zero net capital outlay (funds return to the same wallet each time). Since `RewardPoints` is the accounting ledger that (per the schema's `PointsActivityType`/`ProtocolParticipantType` design) underlies protocol reward/airdrop distribution, this is a duplicate/self-claim of reward value analogous to the Nested royalty-farming bug — it drains the fixed reward pool disproportionately to a single self-dealing actor rather than genuine users/fillers, which is the "reward claims" impact category called out in the bounty scope.

### Likelihood Explanation
High. The attack requires no privileged role, no relayer/prover collusion, and no malformed proof — only two ordinary `IntentGatewayV3` calls (`placeOrder` + `fillOrder`) from a single EOA, which is exactly the same-chain self-fill path already exercised in the repo's own reentrancy tests. It is trivially automatable and repeatable at will, bounded only by gas cost and whatever dust/protocol fee is charged on each order.

### Recommendation
- In `IntentGatewayV3Service.updateOrderStatus` (and the on-chain `_fillSameChain`/`_fillCrossChain` fill path if reward accrual is ever moved on-chain), reject or zero out `ORDER_FILLED_POINTS` when `filler == orderPlaced.user` (compare normalized 20-byte addresses).
- Likewise guard the `REFERRER` bonus path so `user.referrer` cannot resolve to `order.user` or `filler` themselves.
- Consider tracking `(orderId, role)` claim state so points for a given commitment can only be awarded once per distinct role-holder, and add off-chain monitoring that flags high-frequency same-address user/filler pairs for review.

### Proof of Concept
1. Attacker wallet `A` calls `IntentGatewayV2/V3.placeOrder(order)` on the same chain with `order.user = A`, escrowing input tokens.
   - Indexer handler fires `getOrCreateOrder`, crediting `A` `ORDER_PLACED_POINTS = floor(inputUSD)`: [1](#0-0) 
2. Attacker wallet `A` calls `fillOrder(order, options)` themselves (`msg.sender = A`), which is permitted since `_fillSameChain` never checks `msg.sender != order.user`: [4](#0-3) 
3. `_fillSameChain` releases the escrowed input back to `A` (as filler) and pays the order output to `A` (as beneficiary), netting only dust/fee cost.
4. Indexer's `updateOrderStatus` sees `status = FILLED, filler = A` and credits `A` `ORDER_FILLED_POINTS = floor(inputUSD)` again, for the same commitment: [2](#0-1) 
5. Repeat steps 1–4 indefinitely to accumulate `RewardPoints` under both `USER` and `FILLER` `earnerType` buckets for the same wallet, with `PointsService.awardPoints` performing no cross-role or self-claim check: [6](#0-5) 

Note: I could not fully verify from the indexed code whether the `referrer` field on `OrderPlaced` events is authenticated on-chain or freely supplied by the placing wallet (which would let `A` also self-claim the `REFERRER` bonus, tripling the payout per cycle) — `evm/src/apps/intentsv2/**` contains no `referrer` handling, and the indexer decodes `referrer` at `sdk/packages/indexer/src/handlers/events/intentGatewayV3/orderPlacedV3.event.handler.ts`, which I did not have iteration budget left to inspect in full. This should be checked directly in a Devin session to confirm whether the referrer path adds a third self-claim vector.
