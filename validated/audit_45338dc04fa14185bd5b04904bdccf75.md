### Title
`BlameMachine::blame` / `blame_internal` accepts `sender == recipient` (and `proof = None`), letting any party fabricate a blame verdict against an arbitrary honest participant — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The ERC777 bug class is a missing "actor must not equal target" check (`require(operator != msg.sender)`). The PedPoP DKG's blame path has the same shape: `BlameMachine::blame` and `AdditionalBlameMachine::blame` take `sender` and `recipient` as untrusted `Participant` arguments and never reject `sender == recipient`, and `decrypt_with_proof` treats a missing `proof` as evidence against the `recipient`. Since the PoP on an `EncryptedMessage` is just a Schnorr signature over an attacker-chosen ephemeral key with `from` bound into the challenge transcript, an unprivileged third party can construct a syntactically valid message naming any victim as `sender`, call `blame(victim, victim, msg, None)` (or `blame(sender, victim, msg, None)`), and get a verdict labeling the honest victim as the faulty party. `AdditionalBlameMachine::blame` is explicitly usable by callers who were not even DKG participants.

### Finding Description
`blame_internal` in `crypto/dkg/pedpop/src/lib.rs` performs no validation of the `sender`/`recipient` relationship before adjudicating:

- `BlameMachine::blame` and `AdditionalBlameMachine::blame` pass caller-supplied `sender` and `recipient` straight into `blame_internal` (crypto/dkg/pedpop/src/lib.rs:623-632, 674-682).
- `blame_internal` first calls `Decryption::decrypt_with_proof(sender, recipient, msg, proof)` (crypto/dkg/pedpop/src/lib.rs:582).
- In `decrypt_with_proof`, the only checks are `msg.pop.verify(...)` with `pop_challenge(context, R, msg.key, from, ciphertext)` and, if `proof` is `Some`, a DLEq verify; `proof == None` unconditionally yields `DecryptionError::InvalidProof` (crypto/dkg/pedpop/src/encryption.rs:374-396).
- Back in `blame_internal`, `InvalidProof` maps to `return recipient`, i.e., the recipient is declared faulty (crypto/dkg/pedpop/src/lib.rs:586-588).
- `pop_challenge` binds `sender` (a two-byte `Participant` index) into the transcript but the signature key `msg.key` is chosen by whoever constructed the message, so anyone can forge a `from`-bound PoP for an arbitrary `Participant` (crypto/dkg/pedpop/src/encryption.rs:302-324).
- `AdditionalBlameMachine::new` builds the blame machine for any observer given only the public commitment messages, so this is reachable by an unprivileged party, not just DKG members (crypto/dkg/pedpop/src/lib.rs:649-662).

Unlike `validate_map` (which does enforce `*included == ours` must not appear in the peer map, crypto/dkg/pedpop/src/lib.rs:69-74), the blame path has no equivalent `sender != recipient` rejection, mirroring the ERC777 omission of `operator != msg.sender`.

### Impact Explanation
Any party — including a non-participant observer using `AdditionalBlameMachine` — can obtain a verdict that blames an arbitrary honest participant for a DKG failure with no valid evidence. This enables targeted framing (an honest validator marked faulty in every adjudication) and forced aborts of the DKG, since `blame` exists to "prevent completion of the machine, forcing an abort of the protocol". It is a forged adjudication result produced purely from attacker-controlled inputs.

### Likelihood Explanation
Fully deterministic and cheap: the attacker only needs the public commitment messages (to build `AdditionalBlameMachine`), plus one forged `EncryptedMessage` whose `pop` is a Schnorr signature they create over their own ephemeral key. No collusion, no secret material, and no race is required. Impact is bounded to blame/abort (no key material is leaked), so severity is Medium rather than High.

### Recommendation
In `blame_internal` (or in `Decryption::decrypt_with_proof`), reject `sender == recipient` before any adjudication, and treat `proof == None` as an invalid accusation rather than evidence against the `recipient` — a blame claim of "invalid signature" should only convict the `sender` after the PoP check fails, never the `recipient` for declining to reveal a key. Additionally, verify `sender` and `recipient` are registered participants (`enc_keys.contains_key`) instead of relying on `HashMap` indexing.

### Proof of Concept
```rust
// Attacker (not necessarily a DKG member) has all Commitments messages.
let mut machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

// Pick a victim participant index to frame.
let victim = Participant::new(5).unwrap();

// Forge an EncryptedMessage whose PoP binds `from = victim` into the challenge.
// `key`/`nonce` are attacker-known scalars, so the Schnorr PoP verifies.
let key = Zeroizing::new(C::random_nonzero_F(rng));
let pub_key = C::generator() * key.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(rng));
let pub_nonce = C::generator() * nonce.deref();
let ciphertext: SecretShare<C::F> = /* arbitrary bytes */ ;
let pop = SchnorrSignature::<C>::sign(
  &key,
  nonce,
  pop_challenge::<C>(context, pub_nonce, pub_key, victim, ciphertext.as_ref()),
);
let forged = EncryptedMessage { key: pub_key, pop, msg: Zeroizing::new(ciphertext) };

// sender == recipient == victim, proof == None:
// decrypt_with_proof -> Err(InvalidProof) -> blame_internal returns `victim` as faulty.
let blamed = machine.blame(victim, victim, forged, None);
assert_eq!(blamed, victim); // honest participant framed with zero evidence
```

Relevant code: `blame_internal` returns `recipient` on `DecryptionError::InvalidProof` (crypto/dkg/pedpop/src/lib.rs:582-588) and `decrypt_with_proof` returns `InvalidProof` whenever `proof` is `None` (crypto/dkg/pedpop/src/encryption.rs:394-396), with no `sender != recipient` guard anywhere on the path.
