## Signature replay across `accumulate` and `withdraw_fees` due to identical signed payload and shared nonce counter

### Title
Relayer beneficiary signatures are interchangeable between `accumulate` and `withdraw` due to identical hash construction and a shared nonce counter - (File: `modules/pallets/relayer/src/accumulate.rs`, `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The pallet-relayer fee flow has two independent, permissionless extrinsics that each accept a relayer-produced signature over a `(nonce, state_machine, beneficiary)` triple: `accumulate`'s optional `beneficiary_details` field, and `withdraw`'s `WithdrawalInputData`. Both derive their nonce from the exact same storage map `Nonce<T>` keyed by `(address, state_machine)`, and both hash the exact same SCALE-encoded tuple shape. Neither payload includes a domain tag identifying which extrinsic it authorizes, so a signature the relayer produced for one flow is a valid signature for the other.

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
``` [4](#0-3) 

Both hash `(u64, StateMachine, Vec<u8>).encode()` — SCALE encoding of these tuples is byte-for-byte identical to `beneficiary_message`'s `(u64, StateMachine, &[u8]).encode()` for the same values. Both `Nonce<T>` reads/writes use the same map keyed by `(relayer_address, state_machine)`, and both extrinsics increment that same counter on success: [5](#0-4) [6](#0-5) 

This means no cryptographic separation exists between "authorize a beneficiary redirect during fee accumulation" (low-stakes: only rewrites the `Fees` bookkeeping entry that a relayer address owns) and "authorize a withdrawal" (high-stakes: dispatches a real cross-chain `WithdrawalRequest`/`WithdrawalParams` message that a destination host manager executes to actually transfer funds and zero the `Fees` balance, per `withdraw`'s body): [7](#0-6) 

Both extrinsics are unsigned/permissionless (`RuntimeOrigin::none()`, spam-gated only via `validate_unsigned`), matching the existing test pattern: [8](#0-7) 

### Impact Explanation
An unprivileged party who observes a relayer's signed `(nonce, state_machine, beneficiary)` payload on-chain (e.g., captured from an `accumulate` call the relayer submitted to redirect fee bookkeeping to a beneficiary) can resubmit that exact signature into `withdraw` before the relayer does, as long as the nonce for `(relayer_address, state_machine)` still matches. Because the hash and nonce source are identical between the two functions, `withdraw`'s verification (`eth_address != address` / sr25519/ed25519 checks) will accept it, forcing the pallet to dispatch a real fund-disbursing ISMP request to the destination host manager and zero the relayer's `Fees` balance — an action the relayer never separately authorized, triggered by anyone who merely replays a signature meant for a different, lower-stakes extrinsic. This is a direct analog of the H-01 bug class: the signed hash lacks a binding to the specific execution context (function/purpose), so the signature is fungible across code paths it was never intended to authorize, leading to unauthorized execution of the fund-transfer path and consumption/invalidation of the relayer's intended nonce.

### Likelihood Explanation
High: both signed payloads and the shared nonce value are publicly readable from on-chain extrinsic data (chain history/mempool), the attacker needs no privileged role, no relayer key compromise, and no additional oracle — just resubmitting captured bytes into the sibling extrinsic before the legitimate call consumes the nonce, exactly mirroring the original report's "replay previous signatures" primitive.

### Recommendation
Include a domain separator (e.g., a distinct byte/string identifying `"accumulate-beneficiary"` vs `"withdraw"`) inside both `message()` and `beneficiary_message()` so a signature produced for one extrinsic cannot be replayed into the other. Consider also using separate nonce counters per purpose, or fold the extrinsic name/call-index into the signed hash the way EIP-712 domain separators bind signatures to a specific contract and action.

### Proof of Concept
1. Relayer `R` delivers a request and later calls `accumulate` with `beneficiary_details = Some((B, sig))`, where `sig` is `R`'s signature over `beneficiary_message(nonce_N, state_machine, B)` (`Nonce[R, state_machine] == N` at that time).
2. This call succeeds, incrementing `Nonce[R, state_machine]` to `N+1` per `accumulate.rs:128-132`.
3. Before `R` calls `withdraw` at nonce `N+1`, an attacker who observed `sig` from step 1 on-chain cannot immediately reuse it (nonce already advanced) — but if the attacker front-runs step 2, i.e. submits `withdraw` with the *same* `sig`, `dest_chain = state_machine`, `beneficiary = Some(B)` while the nonce is still `N`, `withdraw`'s `message(N, state_machine, B)` recomputes to the identical hash as `beneficiary_message(N, state_machine, B)`, passing signature verification (`withdrawal.rs:88-115`).
4. `withdraw` executes: it reads `Fees[state_machine, R]`, dispatches a real `WithdrawalRequest`/`WithdrawalParams` payout to beneficiary `B` on the destination chain, zeroes `Fees[state_machine, R]`, and increments `Nonce[R, state_machine]` — none of which `R` authorized as a withdrawal action; `R` only signed intending the lighter-weight `accumulate` beneficiary bookkeeping update. The relayer's subsequent legitimate `accumulate` call at nonce `N` now fails (nonce already consumed), and real funds have already moved via the unintended path. [9](#0-8) [10](#0-9)

					Err(Error::<T>::InvalidPublicKey)?
				}
			},
			Signature::Sr25519 { .. } => {
				// Verify signature with public key provided in signature enum

					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},

				// Verify signature with public key provided in signature enum
