### Title
Missing Timestamp/Deadline Validation in App Proxy Signature Verification Allows Indefinite Replay of Signed Requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` only checks that the HMAC `signature` query parameter matches the other query parameters; it never validates that the `timestamp` parameter is recent or within any acceptable window. Because the signature computation is a pure, deterministic function of the query string (excluding `signature`) plus the shared secret, any previously valid, intercepted app-proxy request remains permanently valid and can be replayed by an unrelated/anonymous attacker at any point in the future — directly analogous to the reported "missing deadline" bug class, where a stale signed action executes long after it was originally authorized.

### Finding Description
The verification logic is: [1](#0-0) 

`verify_proxy_request` calls `query_string_valid?`, which extracts the `signature` parameter, recomputes an HMAC-SHA256 over the remaining sorted query parameters (including `timestamp`), and compares it via `secure_compare`. The `timestamp` field is treated as opaque signed data, not as a freshness/expiry check — there is no comparison against `Time.now` and no rejection of old timestamps. This means:
- The signature check only proves the request parameters (including `shop`, `path_prefix`, `timestamp`, and any app-specific query args) were signed by Shopify's shared secret at some point in the past.
- It proves nothing about *when* that happened, so a request captured once (e.g., via browser history, logs, a shared/public link, a misconfigured proxy/cache, or network capture on the storefront side) remains a valid, replayable credential forever.

This mirrors the `convert()`/`buyPortalEnergy()`/`sellPortalEnergy()` issue in the external report: a validly-signed action can sit "pending" (in this case, simply saved by an attacker) and be executed at an attacker-chosen later time, when application state has changed, producing outcomes the original request author never intended.

### Impact Explanation
Any app that relies on `ShopifyApp::AppProxyVerification` to authorize app-proxy actions (e.g., adding a review, submitting a form, triggering a purchase-adjacent action, or any state-changing endpoint reachable via the storefront proxy) is vulnerable to indefinite replay by an anonymous attacker who obtains one previously valid signed URL/query string. Depending on the endpoint's business logic, this can cause duplicate/unauthorized state changes (e.g., duplicate reviews, retriggered discounts, stale form resubmission) executed with the app's trust that the request is a fresh, legitimate storefront-originated action. This is a concrete forged/accepted signed-request replay under the CSRF/HMAC-verification category.

### Likelihood Explanation
Exploitation requires only that an attacker obtain one previously-issued, validly signed app-proxy query string (no secret leakage, no privileged access needed — capture via shared links, browser/proxy logs, referer headers, or passive network observation of the customer's storefront request is sufficient). The verification code as written provides no defense against replay once such a string is obtained, making this trivially exploitable whenever the underlying action is not idempotent or has time-sensitive business meaning.

### Recommendation
Add a timestamp freshness check to `query_string_valid?` in `lib/shopify_app/controller_concerns/app_proxy_verification.rb`: parse the `timestamp` parameter and reject the request if `Time.now.to_i - timestamp.to_i` exceeds a small tolerance window (e.g., a few minutes), in addition to the existing HMAC comparison. This closes the replay window analogous to adding a `deadline` parameter/check in the referenced report.

### Proof of Concept
1. A legitimate customer triggers a state-changing action through the app's storefront app-proxy endpoint (e.g., `GET /apps/my-app/submit?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid_hmac>`).
2. An attacker captures this full URL (via shared link, logs, network capture, etc.) — no access to `ShopifyApp.configuration.secret` is needed.
3. At any later time (hours, days, or longer), the attacker resends the exact same request to the app.
4. `query_string_valid?` in [2](#0-1)  recomputes the same HMAC over the same (unchanged) parameters and returns `true`, so `verify_proxy_request` allows the request through, causing the underlying controller action to re-execute exactly as before, regardless of how much time has passed since the original signing.

```ruby
    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
