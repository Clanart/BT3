### Title
Nested/recursive precompile calls corrupt EVM StateDB balances via shared-`ctx` event-range double-processing in `BalanceHandler` - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` translate Cosmos SDK bank events into EVM `StateDB.AddBalance`/`SubBalance` calls by slicing `ctx.EventManager().Events()` from a recorded `prevEventsLen` index to the current length. Every precompile invocation gets a *new* `BalanceHandler` instance and a *new* event-length checkpoint, but all nested/recursive precompile calls within the same top-level EVM transaction share the underlying `sdk.Context`'s single, ever-growing `EventManager`. When a precompile call itself triggers another EVM call that re-enters a balance-affecting precompile (directly, as with the bank-precompile-invoking pattern used by `werc20`/`ics20`, or via a contract that calls back into a precompile mid-execution, e.g. `FlashLoan.sol`, `StakingReverter.sol`, `DebugPrecompileCaller.sol`), the outer call's `AfterBalanceChange` executes only after the inner call has already applied its own `AfterBalanceChange` on the *same* event log range. Because the outer handler's `prevEventsLen` was captured *before* the nested call ran, its post-processing slice `events[bh.prevEventsLen:]` **still includes the events already consumed and applied to the StateDB by the inner call**, causing `AddBalance`/`SubBalance` to be re-applied for the same bank Coin movement.

### Finding Description
- `precompiles/common/precompile.go` `runNativeAction()` creates a fresh `BalanceHandler` per precompile `Run`, calls `BeforeBalanceChange(ctx)` (recording `len(ctx.EventManager().Events())`), executes the precompile action, then calls `AfterBalanceChange(ctx, stateDB)`. [1](#0-0) 
- `BalanceHandler.AfterBalanceChange` re-derives the balance delta purely from `banktypes.EventTypeCoinSpent` / `EventTypeCoinReceived` (and precisebank fractional events) found in `events[bh.prevEventsLen:]` and applies them directly to the EVM `StateDB`. [2](#0-1) 
- The `sdk.Context`'s `EventManager` is not reset or scoped per nested precompile call — it is the same object threaded through `ctx` for the whole call stack, so events emitted by an inner/nested precompile invocation remain visible (and get reprocessed) when the outer invocation's `AfterBalanceChange` runs afterward, since the outer handler's `prevEventsLen` is a snapshot taken *before* the nested call executed.
- This exact recursion pattern (precompile → EVM call → precompile) is demonstrated by the repository's own regression test, whose docstring states: "demonstrates the balance handler bug by triggering recursive calls that share the same BalanceHandler instance... leads to balance desync between native bank keeper and EVM stateDB." [3](#0-2) 
- The test drives this via `debug` precompile's `Call0`, which calls back into the EVM via `p.evmKeeper.CallEVMWithData` (a nested EVM message execution while already inside a precompile call), recursing several times and asserting a specific (already-buggy) event count of `10` `debug_precompile` events for what should be fewer distinct emissions given the recursion depth used. [4](#0-3) [5](#0-4) 
- Any real (non-debug) precompile with `BalanceHandlerFactory` set — e.g. the `bank`, `erc20`, `werc20`, or `ics20` precompiles — that can be reached from a nested/recursive EVM call within the same top-level transaction is exposed to the same event-range double-counting, because the mechanism (`RunNativeAction` → `BeforeBalanceChange`/`AfterBalanceChange`) is shared code used by all stateful precompiles. [6](#0-5) 

This is the closest native analog to the ERC777 `tokensReceived` reentrancy in the Arcadia report: instead of a hostile token hook reentering a lending pool mid-flash-action to manipulate collateral accounting, a hostile contract reenters the precompile-call pipeline mid-execution (via nested EVM calls triggered from within a precompile, or by calling back into a precompile from a contract invoked by that precompile) to make the shared, mutable event-window bookkeeping in `BalanceHandler` desynchronize the EVM `StateDB` balance from the actual bank-keeper balance.

### Impact Explanation
If the resulting double-application of bank events to the EVM `StateDB` inflates a caller/attacker-controlled address's EVM balance beyond what was actually moved by the bank keeper, this is an unauthorized duplication/creation of spendable EVM-visible value: the attacker's on-chain EVM balance (readable/spendable by `eth_getBalance`, native `CALL` value transfers, and any DeFi contract relying on `StateDB` balances) would exceed their true bank balance, i.e., a native-balance vs. EVM-balance accounting divergence analogous to unauthorized minting. This falls under the allowed Critical impact category of "irreversible accounting corruption of spendable user value across native balances, EVM balances... or precompile-mediated assets."

### Likelihood Explanation
The trigger requires only an unprivileged user deploying/calling an ordinary contract that performs a nested precompile invocation while already inside a `BalanceHandler`-enabled precompile call within a single EVM transaction — no privileged role, relayer, or validator is needed. The repository's own test suite already reproduces the anomalous event/duplication behavior using an ordinary user transaction and a simple attacker-deployed contract, confirming the mechanism is reachable through the standard transaction/EVM execution path. However, I was not able to fully trace, within the available tool budget, whether the specific test's observed anomaly (`10` debug events, `15` total events) actually corresponds to a confirmed StateDB balance over-crediting in a bank-affecting precompile (the debug precompile itself does not move bank balances, it only emits ad-hoc events) — the test as written only exercises the event-counting side effect, not a concrete balance-duplication proof-of-concept on a value-bearing precompile such as `bank`, `erc20`, `werc20`, or `ics20`. Confirming actual fund duplication would require constructing a PoC where a nested precompile call inside another balance-affecting precompile call (e.g., an ICS20 transfer callback re-entering the ERC20/bank precompile, or a contract using `werc20.deposit()` that reenters `bank`/`erc20` mid-call) triggers `AfterBalanceChange` twice over an overlapping event window.

### Recommendation
- Scope `BalanceHandler`'s event tracking per-call using an isolated/nested `EventManager` (e.g., `ctx.WithEventManager(sdk.NewEventManager())`) for each precompile invocation rather than relying on the shared, monotonically growing context event log combined with a captured start index.
- Alternatively, make nested precompile calls consume/drain the event slice they process (e.g., truncate or mark processed events) so an outer handler cannot see events already applied to the `StateDB` by an inner handler.
- Add a reentrancy guard/depth counter specifically for balance-affecting precompiles (similar to the existing `MaxPrecompileCalls` limit) to detect and reject balance-handler nesting rather than silently double-applying deltas.
- Extend the existing `balance_handler_test.go` regression test (and add new ones for `bank`, `erc20`, `werc20`, `ics20`) to assert exact EVM `StateDB` balance vs. bank-keeper balance equality after nested/recursive precompile calls, not just event counts.

### Proof of Concept
Not independently constructed/verified within the available investigation budget. The existing repository test `TestRecursivePrecompileCallsWithDebugPrecompile` in `evmd/tests/integration/balance_handler/balance_handler_test.go` (lines 43-106) already demonstrates the underlying mechanism (shared event log + per-call `prevEventsLen` checkpoint across a nested precompile→EVM→precompile recursion) and is explicitly documented by its authors as demonstrating "the balance handler bug." A concrete fund-duplication PoC would extend this pattern to a value-bearing precompile (e.g., a contract that, from within a `werc20.deposit()` or `ics20.transfer()` call, triggers a nested call back into `bank`/`erc20` precompiles) and assert the EVM `StateDB` balance exceeds the actual bank-keeper balance afterward — this exact extension was not completed due to tool-call/iteration limits.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
