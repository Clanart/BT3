### Title
Wrong argument passed to `deposit_constant` in `host_deposit_constant` causes permanent `prove_bridge_circuit` failure and operator collateral slashing - (File: bridge-circuit-host/src/structs.rs)

---

### Summary

`host_deposit_constant` in `bridge-circuit-host/src/structs.rs` passes `deposit_value_bytes` (the deposit amount as a 32-byte big-endian integer) as the 4th argument to `deposit_constant`, while the actual zkVM circuit in `circuits-lib/src/bridge_circuit/mod.rs` passes `*move_txid` (the move-transaction ID extracted from the verified storage proof). Because both are `[u8; 32]` the code compiles, but the two values are semantically unrelated, so the `DepositConstant` computed on the host is always different from the one committed inside the circuit. The explicit journal-hash equality check in `prove_bridge_circuit` therefore always returns `Err("Journal hash mismatch")`, making it impossible for an operator to ever produce a valid bridge-circuit Groth16 proof.

---

### Finding Description

**Circuit side** (`circuits-lib/src/bridge_circuit/mod.rs`, lines 183–229):

```rust

    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,

```

**Host side** (`bridge-circuit-host/src/structs.rs`, lines 488–515):

```rust

    serde_json::from_str(&input.sp.storage_proof_deposit_txid)...;

let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,

The `deposit_constant` function's own documentation names the 4th parameter `move_txid: [u8; 32]` and hashes it into the `DepositConstant` output:

```rust

    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],   // ← named move_txid
    ...
``` [1](#0-0) [2](#0-1) [3](#0-2) 

The `deposit_constant` is then fed into `journal_hash`, which is what the circuit commits to the zkVM journal:

```rust
let journal_hash = journal_hash(
    payout_tx_blockhash, latest_blockhash,
    challenge_sending_watchtowers,
    deposit_constant,   // ← wrong on host, correct in circuit
);
guest.commit(journal_hash.as_bytes());
``` [4](#0-3) 

`prove_bridge_circuit` then explicitly checks that the host-recomputed journal hash equals the one the circuit actually committed:

```rust
if *journal_hash.as_bytes() != succinct_receipt_journal {
    return Err(eyre!("Journal hash mismatch"));
}
``` [5](#0-4) 

Because `deposit_value_bytes` ≠ `move_txid` for any real deposit, this check always fires and `prove_bridge_circuit` always returns an error before producing the Groth16 proof. [6](#0-5) 

---

### Impact Explanation

`prove_bridge_circuit` is the operator's sole mechanism for generating the Groth16 proof required to complete the BitVM2 assertion flow. When it always fails:

1. **Operator cannot assert**: The operator can never produce a valid `BridgeCircuitBitvmInputs` + Groth16 proof to submit on-chain.
2. **Collateral slashing**: Any challenger who sends the Challenge transaction can wait out the assertion window. Because the operator cannot respond with a valid proof, the challenger can execute the Disprove transaction and burn the operator's collateral UTXO.
3. **Reimbursement permanently blocked**: The operator who fronted the user's withdrawal (payout) can never recover the bridged BTC from the vault, resulting in a direct, permanent loss of operator funds.

The `deposit_constant` is also returned inside `BridgeCircuitBitvmInputs.deposit_constant` and used in the on-chain Groth16 public-input verification; even if the journal-hash guard were removed, the wrong constant would cause on-chain verification to reject the proof. [7](#0-6) [8](#0-7) 

---

### Likelihood Explanation

- The bug is on the critical path executed every time an operator attempts to prove a challenged withdrawal.
- No special attacker capability is required: any party can send the Challenge transaction to force the operator into the assertion flow.
- The mismatch is deterministic — `deposit_value_bytes` (a small integer like `0x0000…01E8480`) will never equal a 32-byte transaction ID.
- The verifier's own `deposit_constant` call in `core/src/verifier.rs` correctly passes `move_txid`, confirming the circuit's expectation and the host's deviation. [9](#0-8) 

---

### Recommendation

In `host_deposit_constant` (`bridge-circuit-host/src/structs.rs`), replace `deposit_value_bytes` with the move-transaction ID extracted from the deposit storage proof, mirroring exactly what `verify_storage_proofs` returns inside the circuit:

```rust
// Correct: extract move_txid from the storage proof value field
// (the storage slot stores the move txid, not the deposit amount)
let move_txid: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();
// ↑ rename variable and ensure the slot being read is the move-txid slot,
//   OR deserialize the txid bytes directly from the proof value.

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    move_txid,   // ← must match what verify_storage_proofs returns
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

Additionally, add a unit test that runs `host_deposit_constant` and the circuit's `deposit_constant` call on the same `BridgeCircuitInput` fixture and asserts they produce identical `DepositConstant` values.

### Proof of Concept

1. Operator fronts a withdrawal and sends the Kickoff transaction.
2. A challenger sends the Challenge transaction.
3. Operator calls `prove_bridge_circuit(params, elf)`.
4. Inside `prove_bridge_circuit`:
   - The zkVM executes `bridge_circuit`, computing `deposit_constant` with `*move_txid` and committing `journal_hash_circuit`.
   - `SuccinctBridgeCircuitPublicInputs::new` calls `host_deposit_constant`, which computes `deposit_constant` with `deposit_value_bytes`, yielding `journal_hash_host ≠ journal_hash_circuit`.
   - Line 239: `*journal_hash_host.as_bytes() != succinct_receipt_journal` → `Err("Journal hash mismatch")`.
5. Operator has no valid proof to submit; the assertion window expires.
6. Challenger calls Disprove, burning the operator's collateral UTXO. [10](#0-9) [11](#0-10) [12](#0-11)

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}
