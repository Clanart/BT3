### Title
Deterministic `CachedPreprocess` reuse across `share()`/`complete()` calls reuses FROST nonces, enabling secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` seeds the FROST `AlgorithmSignMachine` from a seed cached in the database, keyed only by `context` (`(b"DkgConfirmer", attempt)`). Every call under the same context rebuilds the identical nonce/commitment set via `AlgorithmMachine::seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`). `share_internal` calls `preprocess_internal` every time it is invoked, and `DkgConfirmer::complete` calls `share_internal` again — i.e., `SignMachine::sign` is executed multiple times with the **same nonces** but with attacker-influenced `preprocesses` maps and potentially different messages.

The analog to CVE-2021-46923 is structural: the kernel took a reference while building `mount_kattr` and leaked it on an early-return failure path because the cleanup (`finish_mount_kattr`) was skipped. Here, a sensitive one-time resource (the cached preprocess seed, which `crypto/frost/src/sign.rs:85-87` and `spec/cryptography/FROST.md:51-55` state MUST be used only once because reuse enables private key share recovery) is "acquired" and then left in `CachedPreprocesses` on both the success and failure paths — there is no deletion/rotation of the seed after `sign` consumes it, so it is reused for every subsequent `share`/`complete` invocation under the same context.

### Finding Description

In `coordinator/src/tributary/signing_protocol.rs:123-147`, `preprocess_internal` writes the seed to `CachedPreprocesses` once and then reconstructs the sign machine from that same seed on every call:

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(...).preprocess(&mut OsRng);
  ... CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

`from_cache` → `seeded_preprocess` (`crypto/frost/src/sign.rs:127-132`) runs `Commitments::new` on `ChaCha20Rng::from_seed(*seed.0)`, producing identical nonces and identical own-commitments each time.

`share_internal` (lines 150-181) rebuilds this machine and calls `machine.sign(preprocesses, msg)`, where `preprocesses` is parsed from externally supplied bytes (`read_preprocess`, untrusted input) and `msg` is `set_keys_message(...)` derived from the caller-supplied `key_pair`. Two distinct paths reach `sign` with the same nonces:

1. `DkgConfirmer::share` (line 304) → `share_internal` → `sign` (first use).
2. `DkgConfirmer::complete` (line 312-327) → `share_internal` → `sign` again (second use of the same nonce), then `complete_internal`.

Because the `preprocesses` map and `key_pair` are supplied per-call, the signing set and bound message fed to `sign` on the second call can differ from the first (different `included` set changes the per-participant binding factors `rho` and the challenge; a different `key_pair` changes `msg` directly). Each `sign` emits a share `z = d + e·ρ + λ·secret_share·c`. Two shares with the same nonce but different challenge `c` (or different ρ/included set) yield two linear equations, recovering the signer's secret share — exactly the failure the `CachedPreprocess` "MUST only be used once" contract warns about.

Additionally, on the failure path (`read_preprocess` error → `Err(participant)` early return at line 166), the cached seed is not burned: the caller can retry with a different `preprocesses` map and obtain another share under the same nonce — mirroring the CVE's failure-path reference leak.

### Impact Explanation

Recovery of a validator's MuSig/FROST secret share for the tributary `set_keys` confirmation signature. With enough recovered shares (or combined with a threshold of colluding/compromised signers' shares), the DKG confirmation key can be forged — attacker-controlled `set_keys` signatures attest to validator-set keys the honest validators never agreed to. Even a single leaked share degrades the security threshold. Severity: High.

### Likelihood Explanation

The share/complete invocations are driven by coordinator message handling (`DkgConfirmer::share`/`complete` called from `coordinator/src/tributary/handle.rs` with externally supplied `preprocesses` and `key_pair`). An unprivileged participant can submit a malformed preprocess to force the `Err` early-return and then trigger a retry under the same `attempt` context, or simply observe the share from `share()` and the implicit second signing inside `complete()` with a differing participant map. Any divergence between the two `sign` inputs — different preprocess set, different `removed` list, different `key_pair` — produces the two equations needed. The code itself acknowledges the danger in comments (`sign.rs:85-87`, `218-219`; `FROST.md:51-53`) yet persists and reuses the seed unconditionally.

### Recommendation

After a `sign` consumes the cached preprocess — on both success and failure — delete `CachedPreprocesses` for that context (or key the cache by the full signing-set/message commitment so a differing input cannot reuse the nonce). `complete` should not re-run `share_internal` from the persisted seed; the `AlgorithmSignatureMachine`/share produced by the first `sign` should be carried forward instead of regenerating it.

### Proof of Concept

1. Validator V's coordinator handles a `share` request for attempt `a`: `preprocess_internal` loads seed `s` from `CachedPreprocesses[(b"DkgConfirmer", a)]`, regenerates nonces `(d, e)`, and emits share `z₁` over preprocess set `P₁` and `key_pair` `K₁` → challenge `c₁`.
2. An attacker causes a retry/`complete` for the same attempt with a different preprocess set `P₂` (e.g., omits one participant or changes a commitment). `share_internal` regenerates the same `(d, e)` from `s`; `sign` computes `c₂ ≠ c₁` (different binding factors/message) and emits `z₂`.
3. From `z₁ = n + λ·x·c₁` and `z₂ = n + λ·x·c₂` (same effective nonce combination `n`, same Lagrange coefficient `λ` for V's fixed participant index), solve `x = (z₁ − z₂) / (λ·(c₁ − c₂))` — V's secret share.
