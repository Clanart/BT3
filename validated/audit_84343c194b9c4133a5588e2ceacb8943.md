### Title
Unbound InInstruction data lets a co-signer hijack another party's Serai deposit in a multi-party (coinjoin) transaction - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Like the dnsmasq bug — where extra, unauthenticated metadata in a packet (RFC 7871 client-subnet) bypasses the source check — Serai's Bitcoin processor treats a transaction-level "Serai data" field and a heuristically-chosen `input[0]` as authoritative metadata for every Serai-bound output, without binding either to the party that actually funded the deposit. In any transaction with more than one input contributor (e.g., a coinjoin/JoinMarket/PayJoin-style transaction), an unprivileged co-signer can inject an InInstruction and/or control which input sits at index 0, causing a victim's deposit to Serai's external address to be attributed to — and its embedded instruction executed in favor of — the attacker.

### Finding Description
`Bitcoin::extract_serai_data` scans **all** outputs for any OP_RETURN push and, failing that, **all** inputs' witnesses for the `SHA256 <hash> EQUALVERIFY` pattern, returning a single `data` blob for the entire transaction (processor/src/networks/bitcoin.rs:493-524). `get_outputs` then:

1. Collects every scanned output paying Serai (`scanner.scan_transaction`), classifying `External`, `Branch`, `Change`, `Forwarded` purely by script (lines 686-700).
2. Computes a single `presumed_origin` from `tx.input[0]`'s spent output script (lines 707-729) — i.e., whichever input the transaction builder happened to place first.
3. Copies that one `data` blob onto **every** `External`-kind output and stamps `presumed_origin` on all outputs (lines 730-736).

Neither the extracted data nor the origin is cryptographically bound to the output or to the entity that created the Serai-bound output. A transaction is attacker-influenced public input: any party contributing an input or output to a jointly-built transaction controls witness contents, OP_RETURNs, and (with the coordinator's typical input ordering, or by being the coordinator) input order.

### Impact Explanation
- **Instruction injection onto a victim's deposit:** A victim participating in a coinjoin pays Serai's external deposit address as one output of the joint transaction. The attacker (another participant, or the coordinator) adds an OP_RETURN (or a witness matching `segwit_data_pattern`) encoding an InInstruction — e.g., a `transfer`/refund Shorthand naming an attacker-controlled Serai address (`insecure_pair_from_name("alice").public()` in tests shows the shape). `get_outputs` attaches that instruction to the victim's `External` output, so the deposited funds are credited/routed per the attacker's instruction rather than the victim's intent.
- **Origin spoofing:** `presumed_origin` comes solely from `input[0]`. In a multi-party transaction it need not belong to the depositor at all, so refunds and provenance reporting are directed to an address the depositor does not control.
- This is exactly the reported bug class: untrusted packet metadata (witness/OP_RETURN/input order) is trusted as authoritative context for an authenticated-looking object (the scanned output) without any check that the metadata's source is the output's funder.

Reachability: an unprivileged party only needs to get a joint transaction mined — public inputs (a Bitcoin transaction they send), matching the allowed analog surface.

### Likelihood Explanation
Coinjoin, PayJoin, and multiparty-funded transactions are routine on Bitcoin. A coordinator or any participant whose wallet software lets them add outputs/witness data can execute this with no cooperation from the victim beyond the victim including a Serai-bound output in the same transaction. The defect is deterministic — no probabilistic or collusion assumptions are needed; `data` is unconditionally cloned onto every `External` output (line 733) and `presumed_origin` is unconditionally `input[0]` (line 715).

### Recommendation
- Bind `data` to a specific output/index (e.g., only accept an OP_RETURN in the same output position convention, or require per-output commitment) instead of applying one transaction-wide blob to all `External` outputs.
- Reject or flag transactions with multiple independently-funded inputs when deriving `presumed_origin`; treat origin as `None` when it cannot be uniquely attributed, rather than trusting `tx.input[0]`.
- Consider requiring the InInstruction to commit to the depositor's funding outpoint so instructions cannot be transplanted across outputs/parties.

### Proof of Concept
1. Victim V and attacker A build a joint transaction T (standard coinjoin flow). T has inputs `[I_A (attacker's), I_V]` placed so A's input is `input[0]`, and outputs including `O_serai` paying Serai's external address (funded by V) plus an OP_RETURN output containing `InInstruction` bytes naming A's Serai address.
2. `Bitcoin::get_outputs` scans T: `scanner.scan_transaction` returns `O_serai` as kind `External` (lines 692-699). `extract_serai_data` returns A's OP_RETURN blob (lines 496-505). The loop at lines 731-735 sets `O_serai.data = A's instruction` and `presumed_origin = Address::new(script of I_A's spent output)` — the attacker's address.
3. The processor executes A's instruction against V's deposit and records A's address as origin, diverting the credit/refund to the attacker. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

Caveat: I could not fully trace downstream consumers of `Output.data`/`presumed_origin` (multisig scheduler / substrate in-instructions pallet) within the iteration budget, so the exact economic consequence (direct theft vs. misattributed credit/refund) depends on how those layers consume the spoofed fields. The root-cause flaw — unbound per-transaction metadata applied to all scanned outputs — is fully verified in the cited code.

  fn extract_serai_data(tx: &Transaction) -> Vec<u8> {
    // check outputs
    let mut data = (|| {
      for output in &tx.output {
        if output.script_pubkey.is_op_return() {
          match output.script_pubkey.instructions_minimal().last() {
            Some(Ok(Instruction::PushBytes(data))) => return data.as_bytes().to_vec(),
            _ => continue,
          }
        }
      }
      vec![]
    })();

    // check inputs
    if data.is_empty() {
      for input in &tx.input {
        let witness = input.witness.to_vec();
        // expected witness at least has to have 2 items, msg and the redeem script.
        if witness.len() >= 2 {
          let redeem_script = ScriptBuf::from_bytes(witness.last().unwrap().clone());
          if Self::segwit_data_pattern(&redeem_script) == Some(true) {
            data.clone_from(&witness[witness.len() - 2]); // len() - 1 is the redeem_script
            break;
          }
        }
      }
    }

    data.truncate(MAX_DATA_LEN.try_into().unwrap());
    data
  }

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
