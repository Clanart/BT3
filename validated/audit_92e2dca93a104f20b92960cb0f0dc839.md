### Title
Zero-slippage WOM→mWOM conversion in ArbWomUp3 lock mode exposes users to sandwich-attack fund loss - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.incentiveDeposit` with `_mode == 2` internally invokes `SmartWomConvert.convert()` with a hardcoded `_minRec` of `0`, disabling the slippage protection that `SmartWomConvert` otherwise exposes to external callers. This is the same bug class as the reported liquidation issue: a swap executed with `amountOutMinimum`/`_minRec` set to zero, making it vulnerable to market manipulation (sandwiching) and resulting in the depositing user receiving less mWOM than they should, permanently.

### Finding Description
`ArbWomUp3._deposit` handles the WOM deposit/lock flow triggered by the external, unprivileged-callable `incentiveDeposit` function: [1](#0-0) 

For `_mode == 2`, half of the user's deposited WOM is routed through `SmartWomConvert.convert()`, but the `_minRec` argument is hardcoded to `0`: [2](#0-1) 

Inside `SmartWomConvert._convertFor`, the buyback portion is swapped through the Wombat router with a hardcoded `0` minimum output on the swap call itself, and the only protection is a post-hoc check against the caller-supplied `_minRec`: [3](#0-2) 

Because `ArbWomUp3` passes `_minRec = 0` into `convert()`, this end check (`convertAmount + amountRec < _minRec`) can never revert, meaning the swap has zero effective slippage protection. Any user calling `incentiveDeposit(..., _mode = 2)` has part of their WOM swapped at whatever price an attacker can force via a sandwich attack (front-run to move the WOM/mWOM pool price, execute the victim's zero-min swap, back-run to restore the price and capture the difference). The user is not given any way to specify a real minimum, unlike direct calls to `SmartWomConvert.convert()`/`convertFor()` which do accept a caller-supplied `_minRec`.

### Impact Explanation
This directly causes concrete loss of user funds: the amount of mWOM ultimately locked into `mWomSV` on behalf of the user (and thus the reward tier and locked balance credited to that user) can be manipulated to be significantly lower than the fair-market amount, with the difference captured by an attacker via sandwiching the Wombat pool swap. This is an unrecoverable, permanent loss of value for an ordinary user, matching the reported bug's impact of "receiving significantly less than expected."

### Likelihood Explanation
Likelihood is Medium: `incentiveDeposit` with `_mode == 2` is a normal user-facing entry point requiring no special privileges, and Wombat pool swaps (single-sided stableswap style pools) are financially feasible to manipulate for a sufficiently large deposit, similar to the reasoning behind the original medium-severity finding.

### Recommendation
Do not hardcode `_minRec = 0` when internally invoking `SmartWomConvert.convert()`/`convertFor()` from `ArbWomUp3._deposit`. Instead, either let the caller of `incentiveDeposit` supply an explicit minimum output for the conversion leg (validated against a quote, e.g. via `SmartWomConvert.estimateTotalConversion`), or compute an on-chain minimum from `IWombatRouter.getAmountOut` before calling `convert`, and propagate that non-zero minimum through to the swap.

### Proof of Concept
1. User calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, false, 2)` to deposit WOM in lock mode.
2. Internally `_deposit` calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` — note the third argument (`_minRec`) is `0`.
3. Attacker observes the pending transaction in the mempool, front-runs it by swapping WOM→mWOM on the Wombat `womMWomPool` to skew the price unfavorably for the buyback leg.
4. The victim's transaction executes `SmartWomConvert._convertFor`, whose `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` call accepts any non-zero output because `_minRec` passed down is `0`, so the post-swap check `convertAmount + amountRec < _minRec` never reverts.
5. Attacker back-runs to restore the pool price, pocketing the difference; the victim's `mWomSV` lock is funded with fewer mWOM tokens than the pre-manipulation market price would have provided.
