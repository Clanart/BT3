## Title
Persistent unrevoked ERC20 allowance to attacker-specified contract on deterministic IBC isolated address enables theft of future funds - (File: x/ibc/callbacks/keeper/keeper.go)

### Summary
`IBCReceivePacketCallback` grants an ERC20 `approve()` allowance from a deterministic "isolated address" to an attacker/memo-specified `contractAddress` for the exact transferred amount, in order to let that contract pull tokens via `transferFrom`. This approval is never reset to zero after the callback executes, and the isolated address is derived deterministically from `(destChannel, sender)` and therefore reused across every future packet from the same sender on the same channel. Any unspent portion of the allowance — or an allowance from a callback the attacker/receiving contract chooses not to fully consume — remains permanently valid, letting the previously-specified contract silently drain any tokens of that denomination later delivered to the same isolated address, even via ordinary (non-callback) transfers.

### Finding Description
In `IBCReceivePacketCallback`: [1](#0-0) 
the isolated address is generated purely as a deterministic function of channel ID and sender string: [2](#0-1) 
so the exact same address is reused for every packet the same counterparty sender relays through the same channel (confirmed by tests reusing `GenerateIsolatedAddress(path.EndpointA.ChannelID, sender)` across multiple packets/sequences).

The keeper then approves the callback target contract (fully attacker/memo-controlled, taken directly from packet metadata) for the packet's transfer amount from that isolated address: [3](#0-2) 
and invokes arbitrary calldata on that contract, expecting it to pull the full amount via `transferFrom`: [4](#0-3) 

The only post-condition enforced is that the isolated address's *balance* is zero afterward — the *allowance* itself is never inspected or revoked: [5](#0-4) 

The underlying precompile `Approve`/allowance semantics only delete an allowance when explicitly re-approved to zero or fully spent via `transferFrom`; a partially-used or unused allowance simply persists in the `x/erc20` allowance store: [6](#0-5) 

Because the isolated address is reusable, any scenario where the granted allowance is not fully consumed by the callback contract (e.g., the contract transfers the balance out through some other bank/precompile path instead of `transferFrom`, reverts partway leaving a prior successful sub-call's allowance state uncommitted-but-not-cleared in a related flow, or the callback contract is intentionally malicious and simply holds the allowance without draining it during this call) leaves a live, uncapped-in-time allowance for that contract. The isolated address itself is a completely ordinary account address — nothing prevents anyone (including the original attacker) from later sending a plain, non-callback IBC transfer or even a same-chain ERC20 transfer of the same denom directly to that address. The stale allowance then lets the previously-authorized contract call `transferFrom` and drain those unrelated, later-arriving funds without any new authorization step from the actual value owner.

### Impact Explanation
This breaks the asset-representation/ERC20-allowance invariant: an allowance granted transiently for one specific IBC packet's value becomes a permanent backdoor for unauthorized extraction of value credited to the same account in the future, satisfying the Critical impact bar of "unauthorized extraction of user funds ... token-pair-backed balances." The isolated address is not scoped per-packet; it is scoped per `(channel, sender)`, so the blast radius spans every future transfer for that sender/channel/denom combination, not just the single packet that created the approval.

### Likelihood Explanation
Triggering requires no privileged access: any unprivileged IBC relayer/user can submit an ICS-20 transfer with a `dest_callback` memo naming a contract they control, causing an allowance to be created on the deterministic isolated address for that contract. The same unprivileged actor (or anyone aware of the deterministic address derivation, which is public) can subsequently send ordinary tokens to that address. The only defense in the existing code is the post-callback zero-balance check for the *triggering* packet, which does not protect against allowances left over from that packet or against completely separate, later transfers.

### Recommendation
After the callback executes (regardless of success/consumption), explicitly revoke the allowance granted to `contractAddress` (approve amount 0 / call `DeleteAllowance`) rather than relying solely on the balance-zero check. Consider also scoping isolated addresses per-packet (e.g., include the sequence number in `GenerateIsolatedAddress`) so no allowance or balance state can ever be reused across packets.

### Proof of Concept
1. Attacker relays IBC packet P1 to `evmChainA` with `dest_callback.address = AttackerContract`, denom `D`, amount `100`, destined to `isolatedAddr = GenerateIsolatedAddress(channel, attackerSender)`.
2. `IBCReceivePacketCallback` calls `approve(AttackerContract, 100)` from `isolatedAddr`, then invokes `AttackerContract`'s calldata. `AttackerContract` transfers the 100 tokens out via a path that does not fully consume the ERC20 allowance record (e.g. it calls `transferFrom` for a smaller sub-amount while moving the remainder out via the bank/precompile `transfer` from `isolatedAddr`, if reachable, or simply lets a partial `transferFrom` leave residual allowance) — balance check still passes since final balance is 0, but the `Allowance(isolatedAddr, AttackerContract)` entry remains non-zero in the erc20 allowance store.
3. Later, any user (Victim) sends a normal ICS-20 transfer of denom `D` directly to `isolatedAddr` (a valid, ordinary address with no special protection against being an IBC transfer receiver) as a plain transfer (no callback memo).
4. `AttackerContract` calls `transferFrom(isolatedAddr, AttackerContract, remainingAllowance)` on the ERC20 precompile/token, draining Victim's funds without any new authorization.
