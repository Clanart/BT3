### Title
Capacity check in `collateral-add` computes `current-notional`/`current-debt-usd` from stale, un-accrued position data instead of the accrued values, letting a health/capacity verdict be based on outdated debt/collateral - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
This is the same bug class as the reported Carapace issue: a verdict-relevant value is refreshed into a local variable but the code that makes the actual accept/reject decision reads the stale cached value instead of the freshly-updated one, letting an attacker exploit the window where "checked" state and "actual" state diverge.

### Finding Description
In `collateral-add`, when a user adds a new collateral asset while already having debt, the code explicitly computes accrued debt and collateral (`u-debt`, `u-coll`) "required for price resolution": [1](#0-0) 
but the very next step, `get-notional-evaluation`, is invoked with the original, un-accrued `position` object rather than `u-debt`/`u-coll`: [2](#0-1) 
`current-debt-usd` and `current-coll-usd`, and consequently `current-capacity`, are therefore derived from debt/collateral amounts that have not had interest accrued to the current block, while `future-capacity` is compared against this stale `current-capacity` in the critical check: [3](#0-2) 
Interest accrual only increases scaled debt over time, so `current-debt-usd` computed from stale debt will be lower than the true, currently-accrued debt, and `current-coll-usd`/`current-capacity` computed from un-accrued (rehypothecated) collateral will also be understated if that collateral's liquidity index has grown. Because the check only enforces `future-capacity >= current-capacity` (both computed relative to the same stale baseline), it is comparing against the wrong baseline — the actual, accrued capacity headroom for the user may already be tighter or the debt higher than what is reflected in `current-notional`.

### Impact Explanation
Because the capacity check is gating whether a user is allowed to move into a new egroup mask while carrying debt, using stale (lower) debt and stale collateral values means the check can pass in situations where the true, accrued position would fail it. This can let a user add a new (possibly higher-LTV) collateral asset and shift egroup mask when their real debt/capacity is already unfavorable, weakening the protocol's LTV/egroup safety guarantees and enabling positions to enter states that under-collateralize debt relative to the intended risk parameters — this lands on the temporary/permanent freezing-of-funds / protocol-insolvency category since under-collateralized positions increase bad debt risk for lenders/vault depositors.

### Likelihood Explanation
This triggers on the ordinary `collateral-add` path any time a user with existing debt adds a new collateral asset type (changing their mask) after enough time/blocks have passed for interest to accrue meaningfully; no privileged access or oracle manipulation is required, only a naturally-occurring window between debt accrual and the moment `collateral-add` is called — comparable in mechanism (checking a value before it's refreshed within the same call) to the ProtectionPoolHelper analog.

### Recommendation
Use the accrued `u-debt`/`u-coll` values (or an accrued `position`) when building `current-assets`/`current-notional`, i.e., pass the accrued collateral/debt lists into `get-notional-evaluation` instead of the raw `position`, so `current-debt-usd`/`current-coll-usd`/`current-capacity` reflect actual, up-to-date obligations before comparing against `future-capacity`.

### Proof of Concept
1. User has debt and rehypothecated collateral; time passes so that debt accrues (and/or collateral liquidity index grows) but the position record isn't yet updated.
2. User calls `collateral-add` with a new collateral asset id, changing their mask (`is-new-collateral` true).
3. `u-debt`/`u-coll` are computed via `accrue-user-debts`/`accrue-user-collateral` but discarded; `get-notional-evaluation` uses the original un-accrued `position`, producing an understated `current-debt-usd`/overstated or understated `current-capacity` relative to true state.
4. `future-capacity >= current-capacity` check passes based on this stale baseline, allowing the mask/egroup change even though the truly accrued position would not satisfy the intended capacity invariant.
