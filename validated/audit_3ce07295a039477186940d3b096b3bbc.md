### Title
Cached FROST preprocess deterministically re-signed across `share()` and `complete()` enabling nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The original bug class is a lifecycle/accounting mismatch: an asset is "burned" on one ledger (shares consumed) while the backing value remains counted on the other (TVL), letting the same value be claimed twice. The exact analog exists in `SigningProtocol`: a preprocess (nonce seed) is "spent" when a signature share is produced, yet the cached seed is never invalidated — the same deterministic nonces are re-derived and re-signed on every subsequent call for the same context. `DkgConfirmer::share()` and `DkgConfirmer::complete()` both invoke `share_internal`, and `complete()` unconditionally re-signs via `share_internal` again, producing a second signature share under the same nonces for whatever `key_pair`/preprocess set is presented at that later time.

### Finding Description
`preprocess_internal` derives all FROST nonces deterministically from a cached 32-byte seed stored in `CachedPreprocesses`, keyed solely by `context` (for `DkgConfirmer`, `(b"DkgConfirmer", attempt)`). After generating the seed once, every call to `preprocess_internal` reloads the same seed and calls `AlgorithmSignMachine::from_cache`, which regenerates identical nonces via `ChaCha20Rng::from_seed` → `Commitments::new` (`crypto/frost/src/sign.rs:127-144`). The cache entry is never deleted or marked consumed after `sign()` runs.

`DkgConfirmer::share(preprocesses, key_pair)` computes a signature share over `msg = set_keys_message(set, removed, key_pair)`. Separately, `DkgConfirmer::complete(preprocesses, key_pair, shares)` calls `share_internal` **again** (line 322) — re-signing with the identical nonces `d, e` — before aggregating. If the `key_pair` (and hence `msg`, which feeds `Hram` → challenge `c`) or the preprocess set (which feeds `rho` via `BindingFactor::calculate_binding_factors`) visible at `complete` time differs from what was used at `share` time, two distinct shares `s1 = d + ρ1·e + c1·λ·x` and `s2 = d + ρ2·e + c2·λ·x` are published.

If the signing set is identical but `msg` differs (different `key_pair` proposed for the same attempt, or re-execution observing an updated key pair), `ρ` and `R` are identical, so `s1 − s2 = λ·x·(c1 − c2)` directly yields the signer's interpolated secret `λ·x` — i.e., the validator's MuSig secret share for the DKG-confirmation signature.

### Impact Explanation
Recovery of a validator's MuSig secret share breaks the DKG-confirmation signing protocol. The leaked share undermines the unforgeability of the `set_keys` confirmation signature that is the root of trust for onboarding a new threshold key set on Substrate (`set_keys_message` signs the `KeyPair` to be registered). Combined with the share's public reuse across re-executions, this is a key-share-recovery class bug — the exact consequence the code comments repeatedly warn about ("Reusing preprocesses would enable a third-party to recover your private key share", `crypto/frost/src/sign.rs:85`, `spec/cryptography/FROST.md:51-55`).

### Likelihood Explanation
The design intends safety via "context-bound under a BFT protocol" — the header comment (lines 25-54) argues nonce reuse requires operating on distinct finalized messages, and reasons a rebuild re-decides nonces. However:

- The safety argument covers *preprocess* decisions, not the fact that `sign()` itself is executed twice per context: once inside `share()` and again inside `complete()`. `complete()` does not reuse the machine from `share()` — it rebuilds it from the cached seed and re-signs (line 321-324).
- The `key_pair` passed to `share()` vs. `complete()` is supplied per call site, not bound into the context. Any divergence (e.g., `complete` evaluated against a different confirmed `KeyPair` than the one shares were collected for) yields two shares over two messages with identical nonces.
- Additionally, `share()` itself carries no "already signed" guard: repeated invocations of `share()` with attacker-influenced `preprocesses` maps each emit a fresh share over the same nonces, each with a distinct `ρ` — providing the extra equations needed to solve `d, e, x` even when `msg` is constant.

The triggering condition does not require breaking BFT finality — only that the data presented to `share()` and `complete()` differ, which is reachable through ordinary protocol timing (shares collected against one key proposal, completion run against another, or repeated share calls with different signer subsets).

### Recommendation
Consume the cached preprocess on first use: after `share_internal` successfully produces a share, delete or tombstone `CachedPreprocesses[context]` (or record the signed `(preprocesses_digest, msg_digest)` and refuse to sign for any other value under that context). At minimum, `complete()` must verify the machine it reconstructs signs the identical `msg` and identical preprocess set that `share()` already signed — i.e., persist the `msg`/`key_pair` and participant set used at first signature-share generation and assert equality on re-execution, rather than re-signing whatever is currently presented. This mirrors the report's Option B: keep the "supply" (nonce usage) and "TVL" (cached backing seed) consistent across the whole lifecycle instead of letting a spent nonce remain spendable.

### Proof of Concept
Conceptual reproduction within `coordinator/src/tributary/signing_protocol.rs`:

1. Attempt `a` begins; `DkgConfirmer::new(key, spec, txn, a)` is created.
2. `preprocess()` stores seed `S` under `CachedPreprocesses[(b"DkgConfirmer", a)]`; commitments `(D, E)` are published.
3. `share(preprocesses_P, key_pair_K1)` executes `share_internal` → `from_cache(S)` → identical nonces `d, e`; emits `s1 = d + ρ·e + c1·λ·x` where `c1 = Hram(R, A, set_keys_message(.., K1))`.
4. Later, `complete(preprocesses_P, key_pair_K2, shares)` is invoked with `K2 ≠ K1` (a different `KeyPair` visible for the same attempt). It calls `share_internal` again → `from_cache(S)` → same `d, e`, same `ρ`, same `R`; emits `s2 = d + ρ·e + c2·λ·x` with `c2` derived from `set_keys_message(.., K2)`.
5. Both shares are public. Compute `x' = (s1 − s2)·(c1 − c2)⁻¹`, recovering the signer's effective secret `λ·x` — equivalently, recover `e`/`x` jointly given a third reuse from a repeated `share()` call with a different participant set.
6. With `x` recovered, compute arbitrary signature shares for the victim under any future message in this MuSig context.

Caveat noted for completeness: the concrete trigger relies on `share()`/`complete()` being invoked with divergent `key_pair`/preprocess data for the same `attempt` context, which is gated by the tributary handlers in `coordinator/src/tributary/handle.rs` (not fully traceable within index limits). The code-level precondition — deterministic nonce re-derivation on every `share_internal`/`complete` call with no consumption guard — is confirmed by `CachedPreprocesses` never being cleared (`signing_protocol.rs:123-145`) and `complete()` re-executing `share_internal` unconditionally (`signing_protocol.rs:321-324`).
