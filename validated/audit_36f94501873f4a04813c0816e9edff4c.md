### Title
Rounding-based share-price manipulation in `PublicDelegation` staking vault (`convertToShares`/`convertToAssets`) enabling first-depositor / donation attacks against KAIA public delegation stakers - ([File: contracts/bindings/publicdelegation/PublicDelegation.go])

### Summary
`PublicDelegation` is an ERC-4626-style vault: a public transaction sender calls `stake()`/`stakeFor()` to deposit native KAIA and receive shares computed via `convertToShares`, and later redeems via `redeem()`/`previewRedeem()`/`convertToAssets()` [1](#0-0) [2](#0-1) [3](#0-2) . This share/asset conversion pattern is structurally identical to the AToken `mint`/`burn` share-accounting flow described in the report, which is the classic "first depositor / share-price inflation" attack surface (as in Compound, Uniswap V2 LP tokens, and various ERC-4626 vaults) when `totalSupply == 0` or is driven to near-zero and an attacker "donates" underlying assets directly to the vault to inflate the assets-per-share ratio before a victim's deposit rounds down to zero shares.

### Finding Description
The Go bindings expose `stake()` (payable), `stakeFor(recipient)` (payable), `convertToShares(assets)`, `convertToAssets(shares)`, `previewDeposit(assets)`, `previewRedeem(shares)`, `previewWithdraw(assets)`, `totalSupply()`, and `totalAssets()` [4](#0-3) . A `Staked(user, assets, shares)` event confirms the deposit path computes `shares` from `assets` via the vault's share-price formula (`shares = assets * totalSupply / totalAssets`, or equivalent) [5](#0-4) . This is the same "AToken"-style mint/burn-by-shares mechanism flagged in the external report, and it is reachable directly by any unprivileged, unpermissioned transaction sender: `PublicDelegation` is a public delegation/staking pool meant to let ordinary KAIA holders (not just validators) stake through it, per the kaiax staking module's staking/reward documentation which references `PublicDelegation` as a proxy for delegated staking amounts [6](#0-5) .

If (a) the vault can reach a state where `totalSupply()` is zero or extremely small relative to `totalAssets()` (e.g., right after deployment/initialization, or after all shares are redeemed), and (b) an attacker can transfer/donate native KAIA directly to the contract (the contract has a `receive() payable` per the ABI, and it also accumulates staking rewards from validator/reward distribution as `totalAssets`) without minting shares, then the attacker can:
1. Be the first (or sole remaining) staker, depositing a minimal amount (e.g., 1 wei) to obtain 1 share.
2. Donate a large amount of KAIA directly to the contract (increasing `totalAssets` without increasing `totalSupply`), inflating `convertToAssets(1 share)`.
3. Wait for a victim to call `stake()`/`stakeFor()`; the victim's deposit gets rounded down via `convertToShares` (integer division) to 0 or very few shares, effectively donating their deposit to the attacker's 1 share.
4. The attacker then calls `redeem()` and captures the victim's principal.

This exact bug class (rounding + attacker-controlled totalAssets/totalSupply ratio via a first-deposit or donation) is the one named in the external report as the "AToken Price Inflation" vulnerability, which the target project (Aave v2 fork) remediated by adding a `LendingPoolPeriphery` contract that atomically initializes and seeds the pool. I could not verify, within the indexed contents (only Go bindings are available, not the underlying Solidity source), whether `PublicDelegation`'s `initialize()` function performs an equivalent atomic first-deposit seeding, or whether `stake()`/`convertToShares()` include a minimum-shares check (e.g., `require(shares != 0)`) or a virtual-shares/virtual-assets offset (the OpenZeppelin ERC-4626 "decimals offset" mitigation) to prevent this rounding attack.

### Impact Explanation
If unmitigated, this allows a malicious first staker of a `PublicDelegation` pool (deployable/initializable by a GC operator's staking flow, but stakeable by anyone) to steal principal from subsequent honest stakers, and would constitute unauthorized value movement/theft of staked KAIA — a High/Critical severity issue matching the BVSS profile in the reference report (`I:H`, integrity impact high, no confidentiality/availability impact).

### Likelihood Explanation
Likelihood depends entirely on facts not visible in the indexed bindings: whether `initialize()`/constructor seeds an initial nonzero `totalSupply`/`totalAssets` atomically, whether `stake()` enforces a nonzero minimum-shares-minted check, and whether the contract has any restriction preventing plain KAIA transfers (`receive()`) from directly inflating `totalAssets()` without minting shares. Without visibility into the actual Solidity implementation (only ABI/bytecode bindings are indexed), likelihood cannot be confirmed as exploitable in the deployed contract — it is a plausible reachable analog based on the bug class, but not proven root cause.

### Recommendation
Verify in the actual `PublicDelegation.sol` source (not included in the indexed bindings) whether:
1. `initialize()` performs an atomic first-stake (e.g., minting a nonzero minimum number of shares to a burn address, mirroring the `LendingPoolPeriphery` fix referenced in the report), and
2. `stake()`/`convertToShares()` reject zero-share mints, and
3. Whether the contract accepts direct KAIA transfers via `receive()` that bypass share minting (which would allow attackers to inflate `totalAssets` independent of `totalSupply`).
If any of these protections are missing, add: a minimum-liquidity lock on first stake, a `require(shares > 0)` check in `stake()`/`stakeFor()`, and/or an ERC-4626 decimals-offset (virtual shares/assets) mitigation.

### Proof of Concept
Not constructible from the indexed bindings alone since the actual share-price formula, `initialize()` logic, and `receive()` behavior of `PublicDelegation.sol` are not present in the codebase index (only compiled ABI/bytecode Go bindings are available). A concrete PoC would require the Solidity source or bytecode disassembly to confirm the exact rounding behavior of `convertToShares`/`convertToAssets` and whether a first-deposit seed exists.
