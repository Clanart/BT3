### Title
Schnorr aggregate signature verification bypass — weights do not bind to nonces/keys, enabling trivial forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives each signature's random weight `z` from a digest that commits **only to the challenges**, not to the nonce points `Rs`, the public keys, or the messages. An attacker who supplies the aggregate signature bytes (`SchnorrAggregate::read` → untrusted `Rs` and `s`) can compute every weight in advance and then choose `R_0` (and `s`) so the multiexp trivially sums to identity — a forged aggregate signature over keys the attacker does not control.

### Finding Description
Verification computes, at `crypto/schnorr/src/aggregate.rs:132-145`:

- a `DigestTranscript` seeded with the caller's `dst`, domain-separated with `"signatures"`, into which **only the challenges** are appended (`append_message(b"challenge", ...)`);
- for each `(key_i, challenge_i)`, a weight `z_i = weight(&mut digest)`;
- pairs `(z_i, R_i)` and `(z_i * challenge_i, key_i)`, plus `(-s, generator)`, checked to sum to identity via `multiexp_vartime`.

The verifier equation is:

```
Σ_i z_i·R_i + Σ_i z_i·c_i·A_i − s·G = 0
```

Because the transcript never absorbs `Rs`, the keys, or the messages, all `z_i` are computable from the public `keys_and_challenges` input alone, *before* the attacker selects any `R_i` or `s`. The attacker can therefore solve the equation algebraically: pick arbitrary `R_1..R_{n-1}` and any `s`, then set

```
R_0 = −( Σ_{i>0} z_i·R_i + Σ_i z_i·c_i·A_i − s·G ) / z_0
```

yielding sum = identity and `verify` returning `true` without knowledge of any discrete logarithm. This is precisely the half-aggregation security requirement from eprint 2021/350 — weights must be unpredictable *given* the adversary's chosen commitments (typically `z_1 = 1` and the remaining weights derived from a hash binding all `R`s, keys, and challenges). The first weight is also not fixed to `ONE`, compounding the issue, though the missing binding to `Rs` is the root cause.

Note `weight()` (`crypto/schnorr/src/aggregate.rs:22-65`) is a deterministic function of the digest state; the digest state depends only on `dst` and the challenge sequence, all public inputs.

### Impact Explanation
Any caller accepting a `SchnorrAggregate` as authentication of `n` Schnorr signatures — e.g. half-aggregated FROST/Schnorr signatures over bridge messages or transactions — will accept a forged aggregate produced by an unprivileged remote party with only public keys and challenges. This is a complete signature-verification bypass (the analog of the CVE's "security feature bypass" class: the protective check exists but is defeatable with public inputs). Concrete impact: forged acceptance of `n` purported signatures for messages/keys the attacker does not control.

### Likelihood Explanation
Reachable entirely through public inputs: the attacker submits serialized bytes consumed by `SchnorrAggregate::read` and then `verify(dst, keys_and_challenges)` — no internal state, no leaked secrets, no malicious-validator assumption needed (the *verifier* is honest; only the submitted proof is adversarial). Forgery requires only group arithmetic on known values; success is deterministic whenever `z_0 ≠ 0` (overwhelming probability).

### Recommendation
Bind the weight derivation to the full statement being verified. Before drawing weights, additionally append to the digest each `R_i` (and ideally each public key): e.g., `digest.append_message(b"nonce", R_i.to_bytes())` and `digest.append_message(b"key", key_i.to_bytes())` inside the loop at `aggregate.rs:134`. Alternatively fix `z_0 = F::ONE` and derive `z_i` for `i > 0` from a transcript that has absorbed all nonces, keys, and challenges, matching the paper's construction.

### Proof of Concept
```rust
// Attacker-only computation; no private keys required.
// keys_and_challenges: &[(A_i, c_i)] — public verifier input.
// Reproduce the verifier's digest:
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, c) in keys_and_challenges { digest.append_message(b"challenge", c.to_repr()); }

// Precompute all weights (public computation).
let zs: Vec<C::F> = (0..n).map(|_| weight(&mut digest)).collect();

// Choose s = 0 (so -s*G = identity) and arbitrary R_1..R_{n-1} (e.g., identity).
// Solve for R_0:
let mut acc = -zs[0] * (keys_and_challenges[0].0 * keys_and_challenges[0].1);
for i in 1..n {
    acc += zs[i] * Rs[i] + (zs[i] * keys_and_challenges[i].1) * keys_and_challenges[i].0;
}
Rs[0] = -(acc * zs[0].invert().unwrap());

// SchnorrAggregate { Rs, s: 0 }.verify(dst, keys_and_challenges) == true
```

The forged `Rs`/`s` are serialized with `write`/`serialize` and delivered as untrusted bytes to `SchnorrAggregate::read`, then accepted by `verify` at `crypto/schnorr/src/aggregate.rs:127-146`.
