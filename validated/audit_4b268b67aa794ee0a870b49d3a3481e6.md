## Title
Alpenglow validator/leader vote rewards can be lost when the reward certificate for a slot is delayed by more than one epoch, because `EpochInflationAccountState` only retains `current`/`prev` epoch inflation budgets — (File: `runtime/src/block_component_processor/vote_reward/epoch_inflation_account_state.rs`, `runtime/src/block_component_processor/vote_reward.rs`)

### Summary
The reported Olas bug is a "value reserved/derived at the start of a period, but the period's actual settlement crosses a boundary where the enforcement mechanism only understands the current/adjacent period" class of bug: `effectiveBond` is computed once per epoch and later consumed by `OLAS.mint()`, which enforces a *yearly* inflation cap; if the epoch straddles a year boundary, part of the reserved amount cannot be minted and the shortfall is silently dropped (mint returns without reverting). The structural analog I looked for in Agave is a value computed once per epoch (an inflation/reward "budget") that is looked up later by an epoch index, where the lookup structure has a *bounded window* of history and the consuming side can legitimately be more than that window behind.

### Finding Description
For Alpenglow, per-epoch inflation budgets are computed and persisted in an off-curve account by `EpochInflationAccountState`: [1](#0-0) 

Only two epochs of state are ever kept — `current` and `prev` — and `new_epoch_update_account` simply demotes `current` to `prev` and computes a brand-new `current` every epoch boundary: [2](#0-1) 

Vote/leader rewards for a given slot are looked up by the *epoch of the reward slot* (`reward_epoch`), not the current bank epoch, because reward certificates are processed with a fixed delay (`NUM_SLOTS_FOR_REWARD`) after the slot they reward: [3](#0-2) 

If `reward_epoch` is neither the account's `current.epoch` nor `prev.epoch`, `get_epoch_state` returns `None`: [4](#0-3) 

and the caller turns that into a hard error, `RewardStateError::NoEpochValidatorStake`: [5](#0-4) [6](#0-5) 

The invariant the code implicitly relies on is: "a slot's reward certificate is always processed while the reward slot's epoch is still `current` or `prev`", i.e., processing can lag the earned slot by at most about one epoch. This invariant is enforced only by the *typical* value of `NUM_SLOTS_FOR_REWARD` (a small, fixed delay) relative to normal epoch length — it is not actually guarded anywhere in the state machine itself. Nothing prevents:
- a reward slot near the very end of an epoch combined with a delay that pushes crediting past the *next* epoch boundary as well (two boundaries crossed instead of one), or
- catch-up/replay scenarios where a node processes a backlog of reward certificates for a slot whose epoch is now more than one epoch stale relative to the bank it is replaying into (e.g., after falling behind, or during warmup/short first epochs where `EpochSchedule` produces very short early epochs), or
- an epoch schedule with unusually short epochs (as already exercised by the existing warmup test in the same file, `new_epoch_update_account_uses_current_epoch_rewards`, which explicitly creates epochs of different lengths) combined with the fixed `NUM_SLOTS_FOR_REWARD` delay.

In any such case `reward_epoch` becomes older than `prev.epoch`, `get_epoch_state` returns `None`, and the previously-computed/reserved reward budget for that epoch becomes permanently unrecoverable — the vote/leader reward for that slot cannot be credited at all (this is the direct analog of Olas's "bond created spanning a year boundary can never be fully minted because the OLAS inflation cap only understands the current year"). The two-epoch history window plays exactly the role of OLAS's yearly `mint()` cap: a budget value computed for a specific past period is unreachable once execution has moved far enough past that period, and the value is not carried forward or reconstructed — it is simply gone.

### Impact Explanation
Unlike the OLAS bug (silent `return` with no error), this Agave analog manifests as a hard error (`RewardStateError::NoEpochValidatorStake` / debug_assert failure) at reward-processing time rather than a silently-dropped mint. That makes the practical impact either:
- **Lost/unpayable validator and leader inflation rewards** for the affected slot's reward certificate (funds are never credited to the intended vote accounts — same class of harm as the Olas issue: bond depositors/agent owners never receiving payout), or
- If this error path is not gracefully tolerated by the block-processing pipeline (the code comments show it is only `debug_assert`-checked, meaning it's assumed impossible rather than defensively handled), it could propagate into `Result::Err` in a place that halts processing of that bank/slot for that validator — a correctness/liveness issue on the Alpenglow reward path rather than pure fund loss.

This satisfies the requested valid-impact categories (fund loss for validators, or false execution/halt of reward processing) if the underlying assumption about maximum crediting delay vs. epoch length can be violated in practice.

### Likelihood Explanation
This is **conditional and not confirmed to be reachable with default mainnet parameters** — I could not locate the concrete value of `NUM_SLOTS_FOR_REWARD` or the `EpochSchedule` minimum-slots-per-epoch constant within the indexed portion of the codebase (the relevant epoch-schedule crate content and the constant definition in `votor-messages/src/reward_certificate.rs` were not returned by the tools available to me), so I cannot mathematically prove that `NUM_SLOTS_FOR_REWARD` can exceed one epoch's length under production configuration. What is concretely established from local code is:
1. The state machine only ever stores two epochs of inflation budget (`current`/`prev`) — this is a hard, code-verified fact.
2. The lookup path used for reward crediting explicitly assumes reward-slot epoch is within that two-epoch window and treats violation as an unrecoverable/`debug_assert`-guarded error condition.
3. The codebase's own tests deliberately exercise unequal/short epoch lengths (warmup schedules) around this exact code path, showing the authors are aware that epoch-length variability interacts with this budget-lookup mechanism.

Because I could not fully confirm the numeric relationship between `NUM_SLOTS_FOR_REWARD` and minimum epoch length, and because the index does not contain the full `votor-messages`/`bls-sigverify` constant definitions, I state this with reduced confidence and flag it explicitly as requiring further investigation (e.g., in a full Devin session with file-system access) to confirm whether short/warmup epochs or fork/catch-up replay can practically push `reward_epoch` more than one epoch behind `current`.

### Recommendation
- Verify whether `EpochSchedule` warmup or any configurable minimum epoch length can produce an epoch shorter than `NUM_SLOTS_FOR_REWARD`'s crediting delay; if so, either lengthen the stored history in `EpochInflationAccountState` (store N epochs instead of 2) or bound `NUM_SLOTS_FOR_REWARD` to a fraction of the minimum allowed epoch length.
- Replace the `debug_assert!(epoch_inflation_account_state.is_some())` with an explicit, release-mode-checked error path plus telemetry, so that if this situation does occur, it degrades gracefully (e.g., the specific reward slot's credit is deferred/retried or explicitly logged as burned) instead of relying on an assumption that is not enforced.
- Add a fuzz/property test that randomizes epoch length together with `NUM_SLOTS_FOR_REWARD` to assert `reward_epoch` is always within the retained two-epoch window.

### Proof of Concept
No executable PoC was constructed; this analysis is based on static code inspection of the two-epoch-window design in `epoch_inflation_account_state.rs` and the corresponding lookup/error path in `vote_reward.rs`. A full PoC would require:
1. Locating the `NUM_SLOTS_FOR_REWARD` constant definition and default `EpochSchedule` minimum slots-per-epoch (not available in the indexed subset returned to me).
2. Constructing a `GenesisConfig` with an epoch schedule shorter than that delay (similar to the existing `new_epoch_update_account_uses_current_epoch_rewards` test's warmup schedule), driving the bank forward across at least two epoch boundaries while a reward certificate for an old slot is still in flight, and observing `RewardState::try_new` return `RewardStateError::NoEpochValidatorStake`.

Given the confirmed uncertainty about numeric feasibility, I present this as a plausible, code-supported analog rather than a fully proven exploit; a Devin session with full repository/file-system access would be needed to pull the exact constants and confirm reachability.

    /// Returns the [`EpochState`] corresponding to the given `epoch`.
    pub(super) fn get_epoch_state(self, epoch: Epoch) -> Option<EpochInflationState> {
        if self.current.epoch == epoch {
            return Some(self.current);
        }
        if let Some(prev) = self.prev
            && prev.epoch == epoch
        {
            return Some(prev);
        }
        None
    }
