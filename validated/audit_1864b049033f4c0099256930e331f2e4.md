### Title
Order-Based (Not Identity-Based) Hunk Matching in Copilot Conflict Resolution Allows Silent Corruption of Merged File Content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted merge-conflict resolution validates that the model returned the *correct number* of hunks for a file, but never validates that each returned hunk corresponds to the *same conflict block* it was generated for. The hunk-to-conflict-block mapping is done purely by array position ("matched by order, not by line number"), exactly the same class of flaw as the Pear report: a value that should be tied to a validated identity (the specific conflict block) is instead taken from a positional index that an untrusted, attacker-influenced input can shuffle.

### Finding Description
When the user resolves conflicts with Copilot, `resolveChunk` sends the conflicted files (built from the working directory, which includes content from the attacker-controlled branch/PR being merged) to the model, then:
1. Parses the model's JSON response into `IRawFileResolution[]` in `parseCopilotConflictResolution`, where each file entry contains a `hunks` array.
2. Validates only that the count of returned paths/hunks matches expectations in `validateResolutionPaths`: [1](#0-0) 
3. Reassembles the resolved file by walking the on-disk conflict markers in order and splicing in `hunkResolutions[hunkIndex]` for the `hunkIndex`-th marker block encountered — purely positional, with no check that the spliced-in content was actually generated for *that* block: [2](#0-1) [3](#0-2) 

There is no anchor (e.g. a hash or excerpt of the original ours/theirs content) tying a returned hunk resolution to the specific conflict block it was meant to resolve. `reassembleResolutions` then writes this content straight into the file the user is about to commit: [4](#0-3) 

Finally, `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` directly to disk and stages it for commit without further verification against the original conflict content: [5](#0-4) 

This mirrors the Pear bug precisely: the code trusts a *positional* element (last path element / n-th hunk) as if it were a *validated identity* (the correct collateral token / the correct conflict block), and the only guard in place (a length/count check) does not catch a reordering that preserves length. In the GMX case a mismatched identity caused funds/fees to lock; here it causes the wrong resolved code to be spliced into the wrong location of a file the user is about to commit and push — a "silent corruption of what the user commits" event with no error, warning, or revert to alert the user.

### Impact Explanation
If the model's response lists a file's hunks out of the order they physically appear in the conflicted file (same count, different assignment), `reassembleResolvedFile` will insert hunk resolutions into the wrong conflict blocks. Since the count check passes, no `CopilotValidationError` is thrown, no warning is surfaced, and the file is written and `git add`-ed as if correctly resolved. This falls squarely under the accepted impact category "silent corruption of what the user commits or pushes" — the user can unknowingly commit and push code where two conflict resolutions have effectively been swapped between two hunks of the same file (e.g., swapping a security check hunk with an unrelated logging hunk), with no explicit malicious/incorrect diff shown to raise suspicion beyond normal review.

### Likelihood Explanation
The attacker needs only to control the content of one side of a merge (a branch/PR the victim merges, or a repository the victim clones/fetches) — squarely within scope of "attacker controls a cloned/fetched repository." Files with multiple hunks in a single conflicted region are common in real-world merges, and prompt-injection-style content embedded in the conflicting code/comments (attacker-controlled, since it's part of the repository being merged) could induce the LLM to emit its hunks array in an order that doesn't match the physical order of markers in the file, especially for larger multi-hunk files that get processed in the batched/chunked path (`SinglePromptFileLimit` chunking in `resolveConflicts`). No local access, credentials, or social engineering beyond a routine "merge branch"/"resolve with Copilot" action is required.

### Recommendation
Tie each hunk resolution to the conflict block it was generated for using a content-derived identity (e.g., include a hash or verbatim excerpt of each hunk's original "ours"/"theirs" text in the request/response schema and verify it against the actual on-disk block before splicing) rather than relying solely on array order and count. Reject/repair a resolution whose anchor doesn't match the corresponding on-disk conflict block instead of silently accepting a same-length but reordered `hunks` array.

### Proof of Concept
1. Craft a branch/PR with a file containing two adjacent conflict blocks, A and B, where the "correct" resolution content differs meaningfully between them (e.g., block A should keep a validation check, block B should keep unrelated formatting).
2. Embed content in the file (visible to the LLM as part of the conflict context) that induces the model to return `hunks: [resolutionForB, resolutionForA]` (i.e., swapped order) while keeping the count equal to `expectedHunkCounts` per `validateResolutionPaths`.
3. Because `reassembleResolvedFile` only tracks a running `hunkIndex` and blindly assigns `hunkResolutions[hunkIndex]` to the next marker block encountered [6](#0-5) , block A receives the resolution meant for block B and vice versa.
4. `validateResolutionPaths` passes (path present, hunk count matches) [1](#0-0) , so no error is raised, and `_applyCopilotConflictResolutions` writes and stages the swapped content as though it were correct [5](#0-4) .

 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved

 * resolved sections.

 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
