## Title
Attacker-crafted postdispatch `Call.value` can permanently strand solver-delivered funds in an external contract, bypassing `CallDispatcher`'s dust-sweep — (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` lets an order creator attach arbitrary `Call[]` calldata (`order.output.call`, a.k.a. "postdispatch") that is executed by the shared `CallDispatcher` contract after a solver delivers the order's output funds to the dispatcher. `CallDispatcher.dispatch()` blindly forwards each `Call.value` to an attacker-chosen `to` address with attacker-chosen `data`, with no validation that the target call actually consumes that value. The post-execution "sweep" in `IntentsBase._execute()` only recovers funds still sitting on the `CallDispatcher`'s own balance for the order's *declared* output tokens — it cannot recover value the attacker's calldata forwarded into an external router-like contract that doesn't fully consume/refund it. This is a local analog of the Arkis `CommandSafeExecutor` finding: an untrusted, user-supplied `value` is executed against an arbitrary target without validating that the call legitimately uses that value, letting funds be stranded in a third-party contract for later extraction.

### Finding Description
When a same-chain order has postdispatch calldata, the beneficiary can be set to the `CallDispatcher` address, so the solver's output payment lands on the dispatcher (see `testPostdispatchTokenSweep` pattern in `evm/tests/foundry/IntentGatewayV2Test.sol`). `IntentsBase._execute()` then runs: [1](#0-0) 

which calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`. The dispatcher itself has no notion of what the calldata is supposed to do — it simply executes: [2](#0-1) 

`call.value` is entirely attacker-controlled (it comes from the `Order.output.call` field, which is set by the order *creator* at placement time, i.e. by an unprivileged user). If the crafted call sends the solver-delivered native ETH (or ERC-20, via a `transfer`-ignoring path) to an external protocol contract using a function selector that does not fully consume or refund that value (the same Uniswap-router quirk exploited in the Arkis report — a call whose calldata doesn't touch `msg.value`, or an exact-input/partial-consumption path that leaves residue on the target contract's balance), that value is now stuck in the *target* contract, not the `CallDispatcher`.

The only recovery mechanism is the sweep loop that runs immediately after `dispatch()`: [3](#0-2) 

This sweep only checks `dispatcher.balance` (for native) or `IERC20(token).balanceOf(dispatcher)` (for declared output tokens) — i.e., only funds still resident on the `CallDispatcher` itself. It has no visibility into balances the dispatcher's own calldata pushed out to arbitrary third-party contracts. Just like the Arkis `CommandSafeExecutor.execute()` (which uses the untrusted `Command.value` without validating it against what the compliance rules actually authorize), `CallDispatcher.dispatch()` executes the untrusted `Call.value`/`Call.data` pair with no invariant tying the forwarded value to what the target call is expected to consume.

### Impact Explanation
This lets an unprivileged order creator design an order whose postdispatch calldata routes the *solver's* delivered payment into a vulnerable external contract (e.g., any AMM router with the "leftover funds are free for anyone" property) in a way that the funds never return to the `CallDispatcher`/gateway. Because the sweep loop reports zero residual dust, the loss is invisible on-chain to the protocol's own accounting, while the solver has already fulfilled the order and is credited the escrowed input on the source chain via the normal `RedeemEscrow`/`withdraw()` flow. Net effect: the solver's output payment is siphoned off to a contract from which only whoever can exploit that contract's own quirk (which could be the malicious order creator via a separate, out-of-protocol transaction) can extract it — a direct loss of solver funds through unauthorized execution enabled by Hyperbridge's own dispatcher.

### Likelihood Explanation
Any user can call `placeOrder()` and set arbitrary `output.call`/`output.beneficiary` — no privileged role, relayer, or governance action is required. The only precondition is that some integrated/whitelisted external contract exhibits the "stray value is spendable by anyone" property (a known, common pattern in AMM router designs, exactly as called out in the source report). Because `CallDispatcher` is a shared, generic executor with no allow-list on `to` or validation on `value` vs. `data`, this is reachable by construction whenever postdispatch composability is used with any DEX/router integration.

### Recommendation
- In `CallDispatcher.dispatch()`, require that `Call.value` be consumed exactly by verifying pre/post native balance deltas on the dispatcher and target, or restrict `Call.value` to zero for non-allow-listed targets.
- In `IntentsBase._execute()`, don't rely solely on sweeping the dispatcher's own balance for declared output tokens; either disallow forwarding `value` to calls whose selector is not verified to require/refund it, or maintain a strict allow-list of downstream targets (e.g., only vetted router contracts with a known no-stray-value invariant) for postdispatch/predispatch calldata.
- Consider requiring postdispatch/predispatch calls to be simulated/validated so that all native/ERC-20 value that leaves the `CallDispatcher` is provably returned or delivered to a known beneficiary before the transaction is accepted.

### Proof of Concept
1. Order creator (attacker) places a same-chain order:
   - `output.beneficiary = CallDispatcher address`
   - `output.assets = [{token: address(0), amount: X}]` (native ETH output)
   - `output.call = abi.encode([Call({to: vulnerableRouter, value: X, data: <selector for a token-to-token swap function that never touches msg.value>})])`
2. A solver fills the order via `fillOrder`, sending `X` wei of native ETH to the beneficiary (the `CallDispatcher`), per the fill logic in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (`beneficiary.call{value: beneficiaryTotal}("")`) / same-chain analog in `IntentGatewayV2.sol`.
3. `_execute()` invokes `CallDispatcher.dispatch(order.output.call)`, which forwards `X` wei to `vulnerableRouter` via `to.call{value: call.value}(call.data)` — but the called function ignores `msg.value`, so the ETH sits on `vulnerableRouter`'s balance, not returned to the dispatcher.
4. The sweep loop in `_execute()` checks `dispatcher.balance`, finds `0`, and emits no `DustCollected` — the solver's `X` wei is unrecoverable through the gateway.
5. The attacker (or anyone aware of `vulnerableRouter`'s stray-balance quirk) issues a separate, out-of-protocol transaction against `vulnerableRouter` to claim the stranded `X` wei, completing the theft of the solver's filled payment.
