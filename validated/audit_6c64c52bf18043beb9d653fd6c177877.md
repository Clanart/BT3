I found a concrete analog of the underlying bug class: a uniqueness/"already claimed" check that only validates one side of a bidirectional mapping, allowing the same identifier (here, an EVM address) to be claimed/bound multiple times by different owners, silently overwriting the reverse pointer.

### Title
Address association only checks the `seiAddr → evmAddr` direction, allowing one EVM address to be re-associated to multiple Sei addresses - ([File: precompiles/addr/addr.go])

### Summary
Similar to the Footium finding — where `redeemed[seasonId][clubId][generationId]` checked uniqueness on a narrower key than the identifier actually being claimed (`generationId`), letting the same player ID be minted more than once — the Sei `addr` precompile's `associateAddresses`/`associate` functions check only that the `seiAddr` side of the association is unclaimed, never that the `evmAddr` side is unclaimed. Since the reverse mapping (`EVMAddressToSeiAddressKeyPrefix`) is unconditionally overwritten, a second, unrelated Sei address can bind itself to an `evmAddr` that is already associated with a different Sei address, and the `SetAddressMapping` write silently reassigns the EVM-address side to the new owner while the original owner's forward mapping stays intact but "orphaned" from the reverse lookup.

### Finding Description
`AssociateAddresses` (invoked from the `addr` precompile's `Associate`/`AssociatePubKey` methods, and mirrored across all legacy versions) performs exactly one existence check before writing the association: [1](#0-0) 

```go
func (p PrecompileExecutor) associateAddresses(...) {
    // Check that address is not already associated
    _, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
    if found {
        return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
    }
    associationHelper := helpers.NewAssociationHelper(...)
    err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
    ...
}
```

This only queries `GetEVMAddress(ctx, seiAddr)` — i.e., "is *this Sei address* already bound to *some* EVM address?" It never calls `GetSeiAddress(ctx, evmAddr)` to check "is *this EVM address* already bound to *some other* Sei address?" The identifier actually being claimed (`evmAddr`, derived and verified from a signature over `customMessage`/pubkey in the `associate` path) is not the key that's checked for prior use — exactly the same "wrong scope" mismatch as the Footium report, where the check (`redeemed[seasonId][clubId][generationId]`) didn't match the identifier space of what needed to be unique (`generationId` globally).

`SetAddressMapping`, called from `AssociateAddresses`, then unconditionally overwrites both directions of the mapping: [2](#0-1) 

```go
func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
    store := ctx.KVStore(k.storeKey)
    store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
    store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
    ...
}
```

Because only the `seiAddr`-side existence is checked, a second caller who can produce a valid signature/pubkey recovering to the same `evmAddr` (or otherwise supply that `evmAddr` value together with a fresh, previously-unassociated `seiAddr`) can call associate again and have `EVMAddressToSeiAddressKey(evmAddr)` overwritten to point at the new Sei address, while the original Sei address's forward mapping (`SeiAddressToEVMAddressKey`) is left pointing at `evmAddr` — a stale, inconsistent forward mapping. This is a duplicate "claim" of the same `evmAddr` identifier, analogous to a duplicate mint of the same player ID because the wrong dimension was checked for prior use.

### Impact Explanation
`GetSeiAddress`/`GetSeiAddressOrDefault` (the reverse lookup) governs receiving funds sent to the EVM-address-derived account and is relied upon by `CanAddressReceive`: [3](#0-2) 

If the reverse pointer for `evmAddr` can be redirected to a new Sei address after the fact, funds and control associated with the EVM address (via the `getSeiAddr`/`getEvmAddr` precompile queries, pointer/erc20 bridging, and any code paths keyed off the EVM→Sei reverse mapping) can be redirected away from the original claimant, which is a fund-loss / unauthorized-control class issue.

### Likelihood Explanation
Requires a second address holder to be able to supply the *same* `evmAddr` with a fresh signature/pubkey in a new `associate` call, or (for the `AssociatePubKey` path) that the evmAddr derivation only ties to the pubkey and not to prior mapping state. Verifying whether this is actually exploitable end-to-end (whether the signature-recovery step in `associate` can be replayed with a different resulting `seiAddr`, or whether `AssociatePubKey` permits an attacker-chosen `evmAddr` value paired with a distinct `seiAddr`) requires deeper review of `helpers.GetAddresses` and the `AssociatePubKey` argument derivation, which I was not able to fully trace within the available index. I flag this as the strongest reachable analog found, but recommend a Devin session review of the full `associate`/`associatePublicKey` code paths (including all legacy versions) to confirm exploitability before treating this as fully proven.

### Recommendation
Symmetrically check both directions before writing the association — reject if either `GetEVMAddress(ctx, seiAddr)` **or** `GetSeiAddress(ctx, evmAddr)` already returns a mapping, mirroring the Footium fix of moving the uniqueness check to the correct/complete key scope (in this case, checking uniqueness on the `evmAddr` identifier as well as the `seiAddr` identifier) before calling `SetAddressMapping`.

		return nil, 0, err

}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}
