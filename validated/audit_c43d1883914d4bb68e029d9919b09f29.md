## Analysis

The report's bug class is a **guard/normalization step present in one commit path but silently missing in a structurally similar sibling path**, letting attacker-influenced state leak into a result the user never explicitly approved. In `blackvul/desktop--010` there is a direct analog in the two Git commit helpers used by Desktop's commit machinery.

`createCommit` (used for ordinary commits from the Changes pane) always calls `unstageAll(repository)` before staging exactly the files the user selected, guaranteeing the commit reflects only what the user reviewed: [1](#0-0) 

`createMergeCommit`, used to finish a conflicted merge, explicitly documents that it **does not** do this: [2](#0-1) 

The only staging it performs is for the manual conflict resolutions and the `conflictedFiles` subset that Desktop's Merge Conflicts UI knows about: [3](#0-2) 

The function's own comment acknowledges the implicit assumption underpinning this: *"any uncommitted changes in the index that were in place before the merge was started will not be included, unless the user stages them manually via CLI."* That assumption depends entirely on the index only containing what git's own merge machinery staged for the visible conflict — it is not re-verified before committing.

### Title
Merge commit path skips index normalization, letting attacker-controlled merge drivers smuggle unreviewed staged content into commits - (File: `app/src/lib/git/commit.ts`)

### Summary
`createMergeCommit` intentionally omits the `unstageAll` step that `createCommit` performs, so whatever is present in the git index at the moment the user clicks "commit merge" is committed verbatim — not just the conflicted files rendered in Desktop's Merge Conflicts dialog.

### Finding Description
When a user merges a branch/repository they don't fully control (a fork, PR branch, or any cloned/fetched ref), git's merge process can stage content via `.gitattributes`-declared custom merge drivers or clean/smudge filters that run as part of `git merge`. Desktop's `_finishConflictedMerge` only ever stages the files it explicitly enumerates as `Conflicted` in `workingDirectory` plus `manualResolutions`: [4](#0-3) 
It never calls `unstageAll` or otherwise re-derives what should be committed from the reviewed diff, unlike the sibling function `createCommit`: [5](#0-4) 
Because a malicious repository can define a merge driver (via `.gitattributes` + `.gitconfig`/repo-local `merge.<driver>.driver`) that runs arbitrary staging side effects during `git merge`, or because any other index state left over from git's automatic non-conflicting merge staging is trusted, `createMergeCommit` will fold that content into the resulting commit without it ever being surfaced in the conflict-resolution UI the user approves.

### Impact Explanation
This allows silent corruption of what the user commits and, transitively, what gets pushed to a remote (including the user's own upstream/fork) — matching the "silent corruption of what the user commits or pushes" impact class. Because merge drivers execute as part of normal `git merge` invocations that Desktop already shells out to, an attacker who only controls the content of a repository the victim merges from can influence the final commit tree without any additional local privilege.

### Likelihood Explanation
Reaching this path requires only that the victim merge a branch from an attacker-influenced source (fork PR, malicious remote) using Desktop's UI, hit a conflict, and complete the merge via `_finishConflictedMerge`. No admin rights, local access, or pre-existing malware are needed — the trigger is a routine "merge branch, resolve conflicts, commit" workflow that Desktop actively encourages.

### Recommendation
Normalize the index in `createMergeCommit` the same way `createCommit` does: explicitly diff the current index against the intended commit set (conflicted files + manual resolutions + git-auto-staged non-conflicting merge changes that are already reflected in the reviewed working directory state) and reject/unstage anything else before running `git commit`, rather than trusting the ambient index state.

### Proof of Concept
1. Attacker publishes a repository/branch containing a `.gitattributes` entry assigning a custom `merge=` driver to some path, and a repo-local git config (or a driver installed via a crafted `.gitmodules`/hook that the victim's environment would run) that, when invoked during merge resolution, additionally runs `git add` on an unrelated file with attacker-chosen content.
2. Victim, using Desktop, fetches and merges this branch into their own branch, hits a real (separate) conflict, and resolves it in Desktop's Merge Conflicts dialog.
3. Victim clicks "Commit merge", triggering `_finishConflictedMerge` → `createMergeCommit`.
4. Because `createMergeCommit` never resets/validates the index (`app/src/lib/git/commit.ts:82-101`), the attacker-staged unrelated file is committed alongside the legitimately resolved conflict, even though it was never shown in the Merge Conflicts dialog's `conflictedFiles` list.

```typescript
/**
 * Creates a commit to finish an in-progress merge
 * assumes that all conflicts have already been resolved
 * *Warning:* Does _not_ clear staged files before it commits!
 *
 * @param repository repository to execute merge in
 * @param files files to commit
 */
export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }

  const otherFiles = files.filter(f => !manualResolutions.has(f.path))

  await stageFiles(repository, otherFiles)
```

```typescript
  public async _finishConflictedMerge(
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    manualResolutions: Map<string, ManualConflictResolution>
  ): Promise<string | undefined> {
    /**
     *  The assumption made here is that all other files that were part of this merge
     *  have already been staged by git automatically (or manually by the user via CLI).
     *  When the user executes a merge and there are conflicts,
     *  git stages all files that are part of the merge that _don't_ have conflicts
     *  This means that we only need to stage the conflicted files
     *  (whether they are manual or markered) to get all changes related to
     *  this merge staged. This also means that any uncommitted changes in the index
     *  that were in place before the merge was started will _not_ be included, unless
     *  the user stages them manually via CLI.
     *
     *  Its also worth noting this method only used in the Merge Conflicts dialog flow, not committing a conflicted merge via the "Changes" pane.
     *
     *  *TLDR we only stage conflicts here because git will have already staged the rest of the changes related to this merge.*
     */
    const conflictedFiles = workingDirectory.files.filter(f => {
      return f.status.kind === AppFileStatusKind.Conflicted
    })
    const gitStore = this.gitStoreCache.get(repository)
    return await gitStore.performFailableOperation(() =>
      createMergeCommit(repository, conflictedFiles, manualResolutions)
    )
  }
```
