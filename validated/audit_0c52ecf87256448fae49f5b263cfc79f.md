### Title
`ThresholdKeys::read` / `ThresholdKeys::new` accept identity verification shares, producing a group key whose signatures can never verify - ([File: crypto/dkg/src/lib.rs])

### Summary
The audit report's bug class is "constructor stores an unchecked `address(0)` value, making the object permanently unusable (deposits/withdrawals/removal all revert)". The Serai analog is the identity group element (the cryptographic equivalent of `address(0)`): `ThresholdKeys::read` deserializes verification shares with `<C as Ciphersuite>::read_G`, which only enforces canonical encodings and does **not** reject the identity point (`crypto/ciphersuite/src/lib.rs:91-100`). `ThresholdKeys::new` then stores those shares and computes `group_key` as their interpolated sum without any identity check (`crypto/dkg/src/lib.rs:349-391`). The result is a `ThresholdKeys` value that is accepted as valid but whose `group_key()` is inconsistent with any real secret-sharing — exactly the "stuck plugin" shape.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-631) reads `t`, `n`, `i`, the interpolation variant, the `secret_share`, and `n` verification shares via `C::read_G` at lines 620-623. This is the `Ciphersuite::read_G` implementation (crypto/ciphersuite/src/lib.rs:91-100), which validates canonical encoding only. The identity-rejecting reader `Curve::read_G` (crypto/frost/src/curve/mod.rs:123-131, which errors on `res.is_identity()`) exists specifically because identity is a dangerous value, but `ThresholdKeys::read` does not use it (it is generic over `Ciphersuite`, not `Curve`).

`ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) validates only the count of `verification_shares` (line 355) and that participant indexes are `<= n` (line 361), then computes `group_key` as `sum(verification_shares[i] * interpolation_factor(i))` over `1..=t` (lines 376-378). An identity entry contributes nothing, so the resulting `group_key` equals the interpolation of the *other* shares — it is not the discrete log of any share set consistent with the stored shares, and it does not equal `generator * recover_key(...)`.

The mismatch propagates into signing: `ThresholdKeys::view` (crypto/dkg/src/lib.rs:463-533) interpolates `secret_share` and the per-participant `verification_shares` used by FROST share verification. With an identity verification share, either (a) that participant's secret share is genuinely `0` — which `ThresholdKeys::new` also accepts without check — in which case the holder knows nothing of a real share and the group key is still wrong relative to everyone else's honest shares; or (b) the share is nonzero, in which case every signature share from that participant fails share-verification, and any signing set including the corrupted index cannot complete.

### Impact Explanation
This maps to "funds reported received that are not spendable". A `ThresholdKeys` deserialized from untrusted bytes (the explicitly in-scope `ThresholdKeys::read` path — e.g., processor-side `GeneratedKeysDb::read_keys` at `processor/src/key_gen.rs:50-63` reads consecutive `ThresholdKeys::read` blobs) containing an identity verification share yields a `group_key()` that does not correspond to the held secret shares. Any funds/output addressed to `group_key()` cannot be signed for: the FROST shares produced verify against the corrupted verification shares and the produced Schnorr signature verifies against `R + c*group_key`, but `group_key` is not `G * recovered_secret`, so `SchnorrSignature::verify` (`crypto/schnorr/src/lib.rs:108-110`) fails for every signature the honest participants produce. This is the exact analog of the plugin being permanently non-functional because an unchecked zero value was baked in at construction.

### Likelihood Explanation
Reachability requires untrusted bytes flowing into `ThresholdKeys::read`, which is within the stated scope. The check is cheap and already performed elsewhere (`Curve::read_G` rejects identity; `Participant::new` rejects zero; `ThresholdParams::new` rejects zero `t`/`n`; `scale` returns `None` on a zero scalar at `crypto/dkg/src/lib.rs:400-407`), so its absence in `ThresholdKeys::new`/`read` is a genuine gap rather than a design decision. Impact is loss of availability of the affected key set rather than key theft, fitting Medium.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), reject identity verification shares before computing `group_key`, mirroring `Curve::read_G`'s identity check:

```rust
for share in verification_shares.values() {
  if bool::from(share.is_identity()) {
    Err(DkgError::/* new variant */ ...)?;
  }
}
```

Additionally consider rejecting a zero `secret_share` and an identity computed `group_key`, and/or having `ThresholdKeys::read` use the stricter `Curve::read_G` where `C: Curve` is available, so the identity encoding cannot be introduced via deserialization.

### Proof of Concept
```rust
// Deserialize ThresholdKeys where one verification share is the identity encoding.
let mut serialized = vec![];
serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
serialized.extend(C::ID);
serialized.extend(2u16.to_le_bytes());          // t = 2
serialized.extend(3u16.to_le_bytes());          // n = 3
serialized.extend(1u16.to_le_bytes());          // i = 1
serialized.push(1);                             // Interpolation::Lagrange
serialized.extend(secret_share.to_repr().as_ref());
for l in 1 ..= 3u16 {
  let share = if l == 2 { C::G::identity() } else { C::generator() * share_l };
  serialized.extend(share.to_bytes().as_ref());
}
// Succeeds: read_G only checks canonical encoding, new() never checks identity.
let keys = ThresholdKeys::<C>::read(&mut serialized.as_ref()).unwrap();
// keys.group_key() is the interpolation of only shares 1 and 3;
// no set of shares consistent with these verification shares exists,
// so all FROST sessions over this key produce signatures that fail
// SchnorrSignature::verify against keys.group_key().
```
