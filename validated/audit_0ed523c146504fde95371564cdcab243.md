## Analog Found

### Title
Stale DID recovery/backup-ID approvals survive ownership transfer, allowing prior recovery parties to reclaim a "sold" DID - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
The external report's bug class is: a constructor grants a third party ongoing rights to move funds, and that grant is never revoked when the asset/strategy is migrated to a new owner. The Chia analog is `DIDWallet.transfer_did()`, which changes the DID's p2 (ownership) puzzle hash to a new owner but unconditionally carries forward the *existing* `backup_ids` (recovery/social-recovery DID list) and `num_of_backup_ids_needed` threshold into the new owner's inner puzzle, with no parameter to strip them during the transfer itself.

### Finding Description
`transfer_did()` builds the new inner puzzle hash for the receiving party like this: [1](#0-0) 

`backup_ids` and `backup_required` are read straight from `self.did_info` (the pre-transfer state) and passed into `get_inner_puzhash_by_p2()` for the *new owner's* puzzle. `reset_recovery_list()` only special-cases hash preservation when `num_of_backup_ids_needed == 0`; it does not clear an active recovery set: [2](#0-1) 

The DID's recovery mechanism (`num_of_backup_ids_needed` out of `backup_ids`) is a social-recovery backdoor: if that threshold of listed recovery DIDs cooperates, they can re-assign the DID's owning p2 puzzle *without the current owner's key*. Because `transfer_did()` does not remove or let the caller clear this list as part of the ownership change, whichever DIDs the seller previously designated as recovery parties (which may be entirely controlled by the seller, e.g., other wallets they own) remain valid after the sale/transfer. The CLI surfaces a `reset_recovery` flag suggesting this can be controlled, but the underlying wallet method `transfer_did()` has no parameter to actually drop `backup_ids`, so the recovery set persists regardless of intent at the call site that ultimately reaches this method.

This is directly analogous to the report: a set of addresses/parties was authorized (approved) to act on the asset in a prior configuration; when the asset transitions to a new owner, that authorization is not revoked, so the old, no-longer-trusted party retains an ability to unilaterally move/reclaim the asset.

### Impact Explanation
If a DID (and anything bound to it — e.g., NFTs owned/controlled by that DID, CATs approved via a VC tied to it, or DataLayer store ownership) is sold or transferred through an offer or direct transfer without also independently zeroing the recovery list, the seller (via their retained recovery DIDs) can later execute a DID recovery spend and redirect the DID's p2 puzzle back to themselves or a puzzle of their choosing — reclaiming ownership from the legitimate buyer without ever holding the buyer's key. This is unauthorized/forged reclamation of coin ownership, i.e., concrete unauthorized coin movement.

### Likelihood Explanation
This requires: (1) the transferred DID had a non-zero recovery threshold configured by the seller, and (2) the seller retains control of enough of the listed recovery DIDs to meet the threshold — both fully within the seller's control before initiating a sale, making this trivially exploitable by a malicious seller against any buyer who doesn't separately audit and manually neutralize the DID's recovery configuration post-purchase.

### Recommendation
`transfer_did()` (and any RPC/CLI paths that call it, e.g. `did_transfer_did`) should provide and, by default, exercise a real mechanism to clear `backup_ids`/`num_of_backup_ids_needed` for the new owner's inner puzzle unless the new owner explicitly opts to keep the previous recovery configuration. `reset_recovery_list()` should support fully zeroing an active (non-empty, non-zero-threshold) recovery configuration on transfer, not just preserving an already-nil hash, and this should be wired through to `transfer_did()` as a real parameter rather than left to out-of-band caller conventions.

### Proof of Concept
1. Seller creates a DID with `backup_ids = [seller_did_2]`, `num_of_backup_ids_needed = 1` (self-controlled recovery).
2. Seller sells/transfers the DID to Buyer via `transfer_did()` (through an offer or direct RPC/CLI transfer), moving the p2 puzzle to Buyer's key.
3. Because `transfer_did()` forwards `self.did_info.backup_ids` unchanged, the new DID inner puzzle still lists `seller_did_2` as a valid recovery party with threshold 1.
4. Seller later performs a DID recovery spend using `seller_did_2`'s signature, reassigning the DID's p2 puzzle back to an address the seller controls — reclaiming the DID (and anything gated on DID ownership) from Buyer without Buyer's cooperation or key.

**Caveat**: I was not able to fully trace whether `with_recovery_info=False` at the RPC/CLI layer (`DIDTransferDID`, `DidTransferDidCMD`) performs additional clearing of `backup_ids` before or outside of `DIDWallet.transfer_did()` in code paths I did not inspect (e.g., inside `wallet_rpc_api.py`'s `did_transfer_did` handler). If such clearing exists there, the effective risk may be limited to the default/naive call path. This should be verified directly in the repository before treating this as fully confirmed.

        if self.did_info.current_inner is None:

        _, og_recovery_list_hash, _, _, _ = uncurried_args
