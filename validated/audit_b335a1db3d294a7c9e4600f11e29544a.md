## Finding: Reentrancy in Tron `IntentGatewayV2.withdraw()` — external call before escrow-state update, with no reentrancy guard anywhere in the contract

### Title
Reentrant escrow drain via CEI violation in `withdraw()` and missing `nonReentrant` guards — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` reintroduces exactly the bug class the external report describes: an external, attacker-influenceable transfer happens **before** the corresponding internal escrow accounting is updated, and the contract has **no reentrancy guard** on any public entrypoint. The canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against precisely this: it imports `ReentrancyGuardTransient`, applies `nonReentrant` to `cancelOrder`/`fillOrder`, and its `_withdraw()` (in `IntentsBase.sol`) decrements escrow **before** making the external transfer — a fix that is directly documented and regression-tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. The Tron file does not carry either mitigation forward.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` (called from `onAccept()` for `RedeemEscrow`/`RefundEscrow`, and from `onGetResponse()`) does: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");     // <-- external call FIRST
            ...
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); // <-- external call FIRST
            ...
        }
        _orders[body.commitment][token] -= amount;                  // <-- state update AFTER
        ...
    }
```

Compare this to the already-fixed canonical EVM path in `IntentsBase.sol`, which decrements escrow **before** transferring: [2](#0-1) 

The regression test suite explicitly documents that this exact ordering (external call before the effect) was the pre-fix vulnerability class for the canonical contract: [3](#0-2) 

Two compounding facts make this a real regression rather than a benign ordering choice:
1. **`token` is attacker-controlled.** `order.inputs[i].token` is a user-supplied address at `placeOrder()` time, so an order creator can register an arbitrary malicious contract as the escrowed "token." When `withdraw()` fires, `token.call(...)` hands execution control to that attacker-authored contract before `_orders[commitment][token]` is decremented.
2. **No reentrancy guard exists anywhere in the file.** Unlike the canonical `evm/src/apps/IntentGatewayV2.sol`, which imports `ReentrancyGuardTransient` and marks `fillOrder`/`cancelOrder` `nonReentrant`, the Tron file has zero occurrences of `nonReentrant`/`ReentrancyGuard`, confirmed by direct search of the file. `placeOrder`, `fillOrder`, and `cancelOrder` are all freely reenterable public/external functions with no lock.

### Impact Explanation
This directly matches the bounty's "false state acceptance / unauthorized execution / stealing or loss of funds" categories for bridge custody: escrow accounting (`_orders[commitment][token]`) is read and mutated around an untrusted external call with no reentrancy protection anywhere in the module, on live bridge custody state. Since the attacker fully controls the callee (`order.inputs[i].token`) and the beneficiary of `withdraw()` is the attacker (as solver in `RedeemEscrow`, or as `order.user` in `RefundEscrow`), the attacker's contract executes with full call-stack access to every other public function of `IntentGatewayV2` (`placeOrder`, `fillOrder`, `cancelOrder`) precisely at the point where the current order's escrow balance for that token has not yet been zeroed out and no lock prevents concurrent, cross-cutting state mutation on the same contract during that window. This is the same "ether transfer before internal accounting update, no reentrancy guard" primitive the external report flags for `contractAdventure`, applied here to actual bridged/escrowed asset custody.

### Likelihood Explanation
High, in the sense that reachability requires no privileged actor: `placeOrder` lets any user choose the escrowed token contract, and `fillOrder`/`onAccept`/`onGetResponse` are the normal, permissionless lifecycle of every order — no relayer collusion, admin key, or governance action is needed to reach the vulnerable code path. The one caveat is that `withdraw()` itself is only invoked from `onAccept`/`onGetResponse`, both gated by `onlyHost`, so the attacker must go through a legitimate (self-authored) order fill/settlement cycle to trigger it — this is a normal, permissionless user action, not a privileged one.

### Recommendation
1. Add `ReentrancyGuardTransient` (or `ReentrancyGuard`) to `evm/tron/contracts/apps/IntentGatewayV2.sol` and apply `nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder`, matching `evm/src/apps/IntentGatewayV2.sol`.
2. In `withdraw()`, decrement `_orders[body.commitment][token]` **before** performing the native/ERC-20 transfer, mirroring the fixed `_withdraw()` in `evm/src/apps/intentsv2/IntentsBase.sol`.
3. Port the `IntrinsicIntentsReentrancyTest.sol` regression suite to the Tron contract build to lock in the fix.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20-like contract whose `transfer()` calls back into `IntentGatewayV2` (e.g. `placeOrder()` or `cancelOrder()` on an unrelated/self-controlled order) before returning `true`.
2. Attacker calls `placeOrder()` on the source chain with `order.inputs[0].token = EvilToken`, escrowing a large `amount`.
3. Attacker (as their own solver) calls `fillOrder()` on the destination chain, triggering the cross-chain `RedeemEscrow` dispatch back to source.
4. When the host delivers the message and calls `onAccept -> withdraw()`, the loop reaches `EvilToken.call(transfer(...))`; `_orders[commitment][EvilToken]` is still non-zero at this point.
5. `EvilToken.transfer()` reenters an unguarded public function (`placeOrder`/`cancelOrder`) on `IntentGatewayV2`, executing with the stale, not-yet-decremented escrow state and no lock preventing it — demonstrating the CEI violation is live and unguarded, unlike the canonical EVM contract which both reorders the effect and blocks reentry with `nonReentrant`.

Note: I was not able to fully trace every downstream effect of the reentrant call (e.g., interaction with `SweepDust`/dust accounting or price-oracle recording) within the available search depth; the core, directly-verifiable defect is the CEI-violating ordering plus total absence of a reentrancy guard in this file, both confirmed by direct comparison against the canonical, test-hardened contract.
