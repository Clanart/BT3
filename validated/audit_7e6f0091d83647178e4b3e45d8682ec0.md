Confirmed the deterministic structure of `create_move_to_vault_txhandler` (`core/src/builder/transaction/mod.rs:306-344`): input is `deposit_outpoint` with fixed `DEFAULT_SEQUENCE`, script-path spend index 0, outputs are the fixed `bridge_amount` to the fixed N-of-N/security-council taproot address and a fixed 0-sat anchor. All non-witness fields of the eventual real movetx are fully deterministic and publicly derivable from `deposit_outpoint` alone (verifier keys, security council config, and protocol paramset are public). This confirms an attacker can pre-compute the exact `compute_txid()` (which excludes witness data per BIP141) of the legitimate movetx and craft a colliding transaction with an empty witness.

### Title
Empty-witness `movetx` submitted to `send_move_to_vault_tx` permanently poisons the tx-sender queue for the real move-to-vault transaction of the same deposit - ([File: core/src/rpc/aggregator.rs])

### Summary
`Aggregator::send_move_to_vault_tx` validates only input/output counts, output values, and output script pubkeys of the attacker-supplied `raw_tx`, never checking that input 0 carries a valid (or any) witness, nor that it actually matches the deposit's real signed transaction. Because Bitcoin's `compute_txid()` excludes witness data, an attacker can submit a syntactically-conforming movetx with an empty witness whose txid is identical to the eventual valid, N-of-N-signed movetx for the same `deposit_outpoint`; `insert_try_to_send`'s txid-based deduplication then permanently blocks the real, validly-witnessed movetx from ever being stored/sent for that outpoint.

### Finding Description
Binding claimed broken: `try_to_send_id_for(real_movetx.txid()) == try_to_send_id_for(malicious_empty_witness_movetx.txid())`, i.e. the DB row keyed by txid that the tx-sender will actually broadcast for a given deposit should equal the row created from the properly-signed movetx, not from any earlier attacker-submitted transaction with the same non-witness fields.

Code path:
1. `create_move_to_vault_txhandler` (`core/src/builder/transaction/mod.rs:306-344`) builds the movetx deterministically from only `deposit_outpoint`, the (public) N-of-N/security-council scripts, and paramset constants (`bridge_amount`, `DEFAULT_SEQUENCE`, 0-sat anchor). None of the non-witness fields depend on any secret.
2. `SpentTxIn::to_txin` (`core/src/builder/transaction/input.rs:256-263`) defaults the witness to `Witness::default()` when unset, but this is irrelevant here — the attacker doesn't need Clementine to construct this; they build the raw bytes themselves.
3. `Aggregator::send_move_to_vault_tx` (`core/src/rpc/aggregator.rs:1973-2101`) deserializes the caller-supplied `raw_tx` directly and checks only `input.len()==1`, `output.len()==2`, output values (`bridge_amount`, `0`), and output script pubkeys. It never checks `movetx.input[0].previous_output == deposit_outpoint` from the request, nor that `movetx.input[0].witness` is non-empty/valid.
4. It calls `self.tx_sender.insert_try_to_send(...)` (`crates/clementine-tx-sender/src/client.rs:59-101`), which computes `txid = signed_tx.compute_txid()` — a hash that (per BIP141/rust-bitcoin) excludes witness data — and short-circuits via `check_if_tx_exists_on_txsender` (`crates/clementine-tx-sender/src/db/tx_sender.rs:223-240`, keyed only on `txid`). If a row for that txid already exists, `insert_try_to_send` returns the existing `try_to_send_id` immediately, **without** calling `save_tx` again.
5. `save_tx` (`crates/clementine-tx-sender/src/db/tx_sender.rs:242-274`) itself uses `ON CONFLICT (txid) DO UPDATE SET txid = EXCLUDED.txid` — a no-op update that never overwrites `raw_tx`, so even a race into `save_tx` wouldn't fix a pre-existing bad row.

Exploit flow: once a legitimate depositor's funding transaction to the deposit address is visible (mempool or confirmed), its `deposit_outpoint` is public. The attacker constructs a transaction with that same `previous_output`, `DEFAULT_SEQUENCE`, version, locktime, and the two fixed outputs (bridge address + amount, 0-sat anchor), but an empty witness on input 0, and calls `send_move_to_vault_tx` with `raw_tx` = that transaction and `deposit_outpoint` = the same outpoint. All of `send_move_to_vault_tx`'s checks pass (they never look at witness or cross-check `previous_output`). `insert_try_to_send` computes the same txid the real movetx will eventually have and inserts a DB row storing the empty-witness `raw_tx`. When the aggregator later legitimately finishes `new_deposit`/`deposit_finalize` and calls `send_move_to_vault_tx` with the real, properly N-of-N-signed movetx (same txid, valid witness), `check_if_tx_exists_on_txsender` finds the existing row and `insert_try_to_send` returns early — the correct, spendable raw transaction is **never persisted**. The tx-sender loop (`crates/clementine-tx-sender/src/lib.rs`, `try_to_send_unconfirmed_txs`) will keep reading and re-broadcasting the stored empty-witness transaction via `send_raw_transaction`, which Bitcoin Core will reject every time (mandatory-script-verify-flag-failed), so the deposit's UTXO is never actually moved into the vault through the automated path, for as long as the poisoned DB row exists.

Existing guards fail because: (a) `send_move_to_vault_tx` performs no witness validation and no cross-check between the request's `deposit_outpoint` and the actual `movetx.input[0].previous_output`; (b) `insert_try_to_send`'s deduplication is keyed solely on legacy `txid`, which is witness-independent by design (BIP141), so a malformed and a valid transaction spending the same input collide on the same key; (c) `save_tx`'s `ON CONFLICT` clause is a no-op for `raw_tx`, providing no self-healing path.

### Impact Explanation
For the targeted deposit, the automated move-to-vault flow becomes permanently stuck: the tx-sender will forever attempt (and fail) to broadcast an invalid, empty-witness transaction under the same txid the real movetx would use, and the correctly-signed movetx can never be (re-)inserted into the send queue through `send_move_to_vault_tx` because of the txid collision. The deposited BTC UTXO cannot be moved into the vault via the automated path — matching the "move-to-vault UTXO permanently frozen" Critical category. The attack is repeatable against any deposit whose outpoint becomes known before the aggregator's own `send_move_to_vault_tx` call completes, i.e. it can be launched against every future depositor, at negligible cost (no fee spent, since the malicious transaction is invalid and never actually broadcasts/confirms).

### Likelihood Explanation
The attacker needs no privileges beyond calling the aggregator's public `SendMoveToVaultTx` gRPC method and observing a deposit outpoint (visible the moment the depositor's funding transaction reaches the mempool). The entire non-witness structure of the movetx is deterministic and publicly computable from `deposit_outpoint` plus public protocol parameters, so no guessing is required. The only race is beating the legitimate `new_deposit` → `send_move_to_vault_tx` sequence, which — given deposit finality wait times (multiple confirmations) before `new_deposit` is even called — gives the attacker ample time. This is trivially repeatable per deposit and requires no BTC expenditure by the attacker.

### Recommendation
In `send_move_to_vault_tx`, verify that `movetx.input[0].previous_output == deposit_outpoint` from the request, and reject (or independently reconstruct and compare against) the deterministic movetx it should be. Additionally, `insert_try_to_send`/`save_tx` should not silently keep stale/invalid raw tx bytes under a txid; consider validating witness non-emptiness before insertion, or updating `raw_tx` on conflict when the incoming transaction is more complete (e.g., has a non-empty witness) than the stored one, and/or independently constructing the movetx server-side rather than trusting caller-supplied raw bytes for a chain-critical transaction.
