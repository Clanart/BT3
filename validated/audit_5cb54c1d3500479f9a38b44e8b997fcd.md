## Analysis

The external report's bug class — using `transfer`/`transferFrom` (or a raw low-level call selector) instead of `SafeERC20.safeTransfer`/`safeTransferFrom`, so token transfers that return `false` on failure (without reverting) go undetected — has a direct local analog in the Tron variant of the Intent Gateway.

### Title
Unchecked ERC20 return value in escrow settlement lets silent transfer failures finalize orders and permanently lock user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.withdraw()` function releases escrowed tokens using a raw low-level `.call` with the `IERC20.transfer` selector, checking only that the call itself did not revert (`success`), never decoding/validating the returned boolean payload. The sibling mainline EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly uses `SafeERC20.safeTransfer`/`safeTransferFrom` for the equivalent operation, showing the Tron path is the outlier.

### Finding Description
In `withdraw()`, escrow release and refund logic does: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```

`success` is `true` as long as the target contract call does not revert. A token whose `transfer` implementation returns `false` on failure (rather than reverting) — a real, non-uncommon ERC20 behavior explicitly called out in the original report — makes this check pass even though no tokens were actually moved. Immediately after, `_orders[body.commitment][token] -= amount` decrements the escrow accounting and `_filled[body.commitment] = beneficiary` is set, permanently marking the order as settled.

The same unchecked pattern recurs in the fee redemption path and in the `SweepDust` handler within `onAccept`: [2](#0-1) [3](#0-2) 

By contrast, the mainline `IntentsBase.sol` correctly uses `SafeERC20`: [4](#0-3) 

### Impact Explanation
Once `withdraw()` completes with a failed-but-"successful" transfer, `_filled[commitment]` is set and escrow balances are decremented as if the beneficiary was paid. There is no retry path in this function for a partially/fully non-delivering token — the order is finalized, so:
- The beneficiary (user or filler) never receives the tokens they are owed — direct loss of user/solver funds.
- The tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to recover them, since the escrow ledger has already been zeroed and the commitment marked filled/refunded.

This is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests (i.e., normal cross-chain settlement of every order that used a non-strictly-compliant ERC20 as an input token) and from `onGetResponse` for cross-chain cancellations, so it sits on the core custody/settlement path rather than an edge case.

### Likelihood Explanation
No malicious relayer, prover, or admin is required — this triggers purely from using any ERC20 input token that returns `false` on failed transfer instead of reverting (a documented, real-world token behavior class, as acknowledged in the original external report itself). Any order routed through this Tron gateway with such a token, combined with a transfer-blocking condition on the token side (e.g., blacklist, pause, insufficient allowance edge case reintroduced by non-standard tokens), reaches this code deterministically through the normal settlement flow.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()`, the fee-redemption block, and `SweepDust` handling with `SafeERC20.safeTransfer`/`safeTransferFrom`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol` and elsewhere in this same Tron file (`safeTransferFrom` is already used for inbound escrow in `placeOrder`). This ensures any transfer that returns `false` reverts the whole settlement transaction rather than silently finalizing it.

### Proof of Concept
1. Create an order whose input token is an ERC20 that returns `false` (rather than reverting) when a transfer condition isn't met (e.g., a token with a pausable/blacklist feature not raising on failure), and escrow it via `placeOrder`.
2. Trigger a `RefundEscrow`/`RedeemEscrow` `onAccept` call (via ISMP) or `onGetResponse` cancellation path targeting this order's commitment while the token transfer condition causes `transfer` to return `false` for the beneficiary address.
3. Observe `withdraw()`: `token.call(...)` returns `success = true` (call didn't revert) with return data encoding `false`; the `if (!success)` check passes, `_orders[...] -= amount` executes, `_filled[commitment]` is set.
4. The beneficiary's balance is unchanged (transfer failed) but the order is now finalized and the escrow accounting shows zero — funds are irrecoverably stuck in the contract.
