### Title
Missing timestamp freshness check in `AppProxyVerification#query_string_valid?` allows indefinite replay of captured app-proxy requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification` validates the HMAC `signature` Shopify attaches to App Proxy requests, but it never checks the accompanying `timestamp` query parameter for freshness. Any request whose signature was once valid remains valid forever, so a captured (e.g. leaked via browser history, referrer headers, shared/forwarded links, proxy/access logs) app-proxy URL can be replayed by an unrelated, unprivileged party at any point in the future. This mirrors the `ChainlinkOracle.getPrice()` defect in the reference report: the value is cryptographically "signed"/attested, but nothing enforces that the attestation is still recent, so stale/replayed data is trusted indefinitely.

### Finding Description
`verify_proxy_request` only calls `query_string_valid?`, which recomputes the HMAC over all query params (including `timestamp`) and compares it to the `signature` param: [1](#0-0) 

The `timestamp` value is part of the signed payload (so it cannot be tampered with independently), but the code never reads or validates it — there is no check that `Time.now.to_i - timestamp.to_i` falls within an acceptable window (Shopify's own app proxy documentation recommends rejecting requests whose `timestamp` is stale, analogous to Chainlink's "heartbeat"/`updatedAt` freshness recommendation cited in the report). As a result, a signature that was valid at generation time remains valid and accepted by `verify_proxy_request` for the lifetime of the app, since the same signature/query-string combination will always recompute to the same HMAC.

This is the direct structural analog of the `ChainlinkOracle` bug: a trusted, cryptographically-verifiable value (`answer` / `signature`) is accepted without checking a companion freshness field (`updatedAt` / `timestamp`) that Shopify explicitly provides for that purpose.

### Impact Explanation
An attacker who obtains a single previously-valid app-proxy request URL — through browser history, shared links, server/proxy access logs, Referer headers on the merchant's storefront, or network capture — can replay it against the app's app-proxy endpoint at any later time and have it accepted as an authentic, current Shopify-signed request. Any state-changing or data-returning app-proxy action bound to that URL executes exactly as if it were a fresh, legitimate request from that shop, even though the shop/customer context may no longer be valid. This is a forged/replayed request being accepted by the verification layer, which the rules classify as an acceptable "accepted forged signed request" finding.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one previously valid signed app-proxy URL, which is a realistic but non-trivial precondition (log access, browser history, leaked links, etc.). The verification code itself provides no time-bounded protection whatsoever — there is no expiry logic to defeat, so once a URL is captured, replay is trivial and works indefinitely. This differentiates it from a typical nonce-based CSRF/session flow that would auto-expire.

### Recommendation
Enforce a freshness window on the `timestamp` parameter in `query_string_valid?`/`verify_proxy_request`, e.g.:
```ruby
def verify_proxy_request
  head(:forbidden) unless query_string_valid?(request.query_string) && timestamp_fresh?
end

def timestamp_fresh?
  ts = Rack::Utils.parse_query(request.query_string)["timestamp"].to_i
  (Time.now.to_i - ts).abs <= ShopifyApp.configuration.app_proxy_timestamp_tolerance # e.g. 60 seconds
end
```
This mirrors the Sentiment Team's fix of checking `block.timestamp - updatedAt < validPeriod` before trusting the value.

### Proof of Concept
1. Legitimate request to the app proxy path is issued by Shopify with `...&timestamp=1466106083&signature=<valid_hmac>`.
2. Attacker captures this full URL (e.g., from access logs, shared chat link, or browser history) at some point after the original request.
3. At any later time, the attacker replays the exact same URL to the app's app-proxy endpoint.
4. `query_string_valid?` in [2](#0-1)  recomputes the same HMAC over the same query string and it matches `signature`, so `verify_proxy_request` allows the request through with no timestamp/staleness check, executing the associated controller action as if it were a fresh, authentic Shopify app-proxy call.

```ruby
    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
