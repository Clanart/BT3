### Title
`ThresholdKeys` deserialization accepts an arbitrary participant index with no binding to the secret share, enabling identity spoofing / misattributed blame - (File: crypto/dkg/src/lib.rs)

### Summary
The bug class of CVE-2025-55370 — accessing/acting under an identity obtained purely by modifying an ID value, with no access-control check binding the ID to the caller — maps onto `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg/src/lib.rs`. The serialized format carries a self-declared `Participant` index `i` and a self-declared `secret_share`, yet neither `read` nor `new` verifies that `C::generator() * secret_share == verification_shares[i]`. The claimed participant ID is therefore fully attacker-controlled.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, `i` (the participant index), the interpolation method, a secret share, and the verification-share map, then calls `ThresholdKeys::new` (lines 574–632). `ThresholdKeys::new` only checks that the map has `n` entries, that no participant exceeds `n`, and that the interpolation is applicable (lines 355–374) — it computes the group key from `verification_shares[1..=t]` but never checks that the supplied `secret_share` corresponds to `verification_shares[i]`. The participant index `i` stored in `params` is whatever byte string the attacker supplied. When `view(included)` is later called (lines 463–533), all validity checks (`DuplicatedParticipant`, `NotParticipating`, `InvalidParticipant`) operate on this attacker-chosen `i`, and the interpolated `secret_share` is used to produce signature shares which FROST's `complete` will verify against `verification_shares[i]` and attribute failures to `params().i()`.

### Impact Explanation
An attacker who can feed crafted bytes to `ThresholdKeys::read` (an explicitly in-scope untrusted-input path) can instantiate keys claiming any victim's participant index `i` with a garbage secret share. During signing, the produced shares fail verification against the real `verification_shares[i]`, causing `FrostError::InvalidShare(i)` to blame the victim participant (see `verify_share` in `crypto/frost/src/algorithm.rs` and blame propagation in `complete_internal`). This lets an unprivileged party get an honest participant blamed — and in deployments where blame drives removal, removed from the validator set — without ever possessing their key share. It is an integrity violation of the accountability layer caused purely by "modifying the ID value", matching the CVE's incorrect-access-control shape.

### Likelihood Explanation
Reachability requires the deployment to deserialize `ThresholdKeys` from bytes an attacker can influence; the format is self-describing (curve ID, params, index, share) so any path loading keys from shared/untrusted storage or messages is exposed. Exploitation is trivial (flip the `i` field, randomize the share) and needs no cryptographic break, but it only yields blame misattribution rather than key recovery or signature forgery — the signature verification itself remains sound — so impact is bounded to framing honest participants and degrading liveness.

### Recommendation
In `ThresholdKeys::new` (or at the end of `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` under the identity interpolation context and reject mismatched input. This cryptographically binds the claimed participant index to the supplied share, closing the spoofing vector.

### Proof of Concept
```rust
// Attacker-craft serialized ThresholdKeys claiming victim index i = 2
let mut serialized = vec![];
serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
serialized.extend(C::ID);
serialized.extend(t.to_le_bytes());
serialized.extend(n.to_le_bytes());
serialized.extend(2u16.to_le_bytes()); // victim's Participant index
serialized.push(1);                    // Lagrange
serialized.extend(C::F::random(&mut OsRng).to_repr().as_ref()); // garbage share
for share in &victim_verification_shares { // public data
  serialized.extend(share.to_bytes().as_ref());
}
// Accepted without complaint — no binding of share to index
let forged = ThresholdKeys::<C>::read::<&[u8]>(&mut serialized.as_ref()).unwrap();
assert_eq!(forged.params().i(), Participant::new(2).unwrap());
// forged.view(included) now signs garbage attributed to participant 2,
// yielding FrostError::InvalidShare(Participant(2)) against the honest party.
```

Caveat: I verified the missing share↔index binding in `crypto/dkg/src/lib.rs`, but could not trace every downstream consumer (e.g., `processor`) within the iteration budget; exploitability depends on `ThresholdKeys::read` ever being fed non-self-generated bytes. If keys are only ever loaded from locally generated storage, this degrades to a hardening gap rather than a reachable vulnerability.
