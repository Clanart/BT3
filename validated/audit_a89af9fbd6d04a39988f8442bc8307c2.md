### Title
Deposit Index Tracking Reads from Wrong Table, Causing Deposit Skipping and Index-Space Collision — (`File: core/src/database/verifier.rs`)

---

### Summary

`get_last_deposit_idx` queries `MAX(idx) FROM withdrawals`, but the `withdrawals` table stores **both** Citrea deposit records (keyed by the Citrea deposit index) and Citrea withdrawal records (keyed by the independent Citrea withdrawal index) in the same `idx` primary-key column. Because the two index spaces are independent counters on the Citrea bridge contract, the function returns a value inflated by withdrawal indices, causing the verifier to permanently skip deposits whose indices fall below the highest withdrawal index. A secondary collision corrupts the deposit-to-withdrawal association for any index value shared by both counters.

---

### Finding Description

The `withdrawals` table schema uses a single `idx INT PRIMARY KEY` column: [1](#0-0) 

Two completely independent Citrea index spaces are written into this one column:

1. **Deposit path** — `upsert_move_to_vault_txid_from_citrea_deposit` inserts a row with `idx = citrea_deposit_index`: [2](#0-1) 

2. **Withdrawal path** — `update_withdrawal_utxo_from_citrea_withdrawal` updates a row with `idx = citrea_withdrawal_index`: [3](#0-2) 

The function that is supposed to return the last **deposit** index instead queries `MAX(idx)` across the entire `withdrawals` table, which includes rows created by both paths: [4](#0-3) 

This value is then passed directly to `collect_deposit_move_txids` as the resume cursor: [5](#0-4) 

`collect_deposit_move_txids` starts fetching from `last_deposit_idx + 1`: [6](#0-5) 

---

### Impact Explanation

**Impact 1 — Permanent deposit skipping (Critical):**
The Citrea `depositTxIds` array and `withdrawalUTXOs` array are independent on-chain counters. If N withdrawals have been processed but only M < N deposits exist, `get_last_deposit_idx` returns N (the max withdrawal index), and the verifier starts fetching deposits from index N+1. All deposits with indices M+1 through N are permanently skipped — the bridge never records their `move_to_vault_txid`, so the operator never initiates a kickoff for them and the deposited BTC is permanently locked in the vault with no reimbursement path.

**Impact 2 — Index-space collision corrupts deposit-withdrawal association (High):**
If deposit index K and withdrawal index K both exist, they share the same row. The deposit write sets `move_to_vault_txid = TX_deposit_K`; the withdrawal write then sets `withdrawal_utxo_txid = UTXO_withdrawal_K` on the same row. The payout flow (`get_payout_txs_for_withdrawal_utxos`, `get_payout_info_from_move_txid`) then associates withdrawal K's UTXO with deposit K's move-txid, which are unrelated events. This can cause the operator to initiate a kickoff for the wrong deposit or the watchtower to challenge the wrong kickoff, breaking the reimbursement invariant. [7](#0-6) 

---

### Likelihood Explanation

This triggers under normal bridge operation with no adversarial action required. The Citrea deposit and withdrawal counters diverge as soon as the number of withdrawals differs from the number of deposits, which is the expected steady-state. The bug is deterministic and reproducible on any deployment where `count(withdrawals) ≠ count(deposits)`.

---

### Recommendation

1. **Separate the index spaces.** Add a dedicated `deposits` tracking table (or a separate `deposit_idx` column) so that deposit indices and withdrawal indices are never stored in the same primary-key column.

2. **Fix `get_last_deposit_idx`.** It must query only rows that were created by the deposit path. The simplest correct fix is to query a separate table or filter by a discriminator column (e.g., `WHERE move_to_vault_txid IS NOT NULL AND withdrawal_utxo_txid IS NULL`), but the cleanest fix is a separate table.

3. **Add a uniqueness constraint** that prevents a withdrawal-index write from overwriting a deposit-index row and vice versa.

---

### Proof of Concept

1. Bridge starts. No deposits or withdrawals yet.
2. User A makes deposit → Citrea deposit index 0. Verifier inserts `(idx=0, move_to_vault_txid=TX_A)`.
3. User B makes withdrawal → Citrea withdrawal index 0. Verifier calls `update_withdrawal_utxo_from_citrea_withdrawal(idx=0, utxo=UTXO_B)`. This updates the **same row** (idx=0), setting `withdrawal_utxo_txid=UTXO_B` on deposit A's row. Withdrawal B is now incorrectly linked to deposit A's `move_to_vault_txid`.
4. User C makes withdrawal → Citrea withdrawal index 1. Verifier inserts/updates `(idx=1, ...)`.
5. User D makes deposit → Citrea deposit index 1. `get_last_deposit_idx` returns `MAX(idx) FROM withdrawals = 1`. The verifier calls `collect_deposit_move_txids(last_deposit_idx=1, ...)`, which starts from index 2. Deposit D (index 1) is **permanently skipped**.
6. All subsequent deposits with index ≤ current max withdrawal index are silently skipped. User D's BTC is permanently locked with no reimbursement. [4](#0-3) [8](#0-7) [9](#0-8) [1](#0-0)

        &self,
        tx: Option<DatabaseTransaction<'_>>,
    ) -> Result<Option<u32>, BridgeError> {
        let query = sqlx::query_as::<_, (i32,)>("SELECT COALESCE(MAX(idx), -1) FROM withdrawals");
        let result = execute_query_with_tx!(self.connection, tx, query, fetch_one)?;
        if result.0 == -1 {
            Ok(None)
        } else {
            Ok(Some(result.0 as u32))
        }
