### Title
Missing identity (zero) check on verification shares / group key in `ThresholdKeys::read`/`new` allows a key blob encoding the zero group key, making deposited funds spendable by anyone - (File: crypto/dkg/src/lib.rs)

### Summary
The "no 0 address check" bug class maps onto Serai as a missing identity-point check for the FROST group key. `ThresholdKeys::read` deserializes each verification share with `<C as Ciphersuite>::read_G`, which enforces canonical encoding but does **not** reject the identity point (unlike `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131`, which explicitly rejects identity). `ThresholdKeys::new` then computes the group key as the interpolated sum of the first `t` verification shares with no check that the result is non-identity.

### Finding Description
- `ThresholdKeys::read` reads `n` verification shares via `<C as Ciphersuite>::read_G(reader)?` (crypto/dkg/src/lib.rs:620-623). `Ciphersuite::read_G` only checks canonicality (crypto/ciphersuite/src/lib.rs:91-100), so identity shares are accepted.
- `ThresholdKeys::new` computes `group_key = Σ verification_shares[i] * interpolation_factor(i)` for `i ∈ 1..=t` and stores it without any `is_identity` check (crypto/dkg/src/lib.rs:376-390). An attacker-controlled serialized blob can set all verification shares to identity, yielding `group_key == identity` (the "zero address" of the group).
- `ThresholdKeys::offset` then sets `group_key = identity * scalar + G * offset = G * offset` (crypto/dkg/src/lib.rs:414-417, 445-447), i.e., a key whose discrete log is a publicly known/attacker-chosen offset scalar.

### Impact Explanation
A `ThresholdKeys` blob encoding the identity group key produces a multisig address whose effective private key is just the offset scalar — public knowledge. Any funds deposited to the corresponding Bitcoin address (via `p2tr_script_buf`/`Scanner` on networks/bitcoin) or signed under this key are spendable by anyone, a direct loss-of-funds analog of sending funds to the 0 address. Individual share verification also degenerates: `verify_share` checks `share * G == R + c * verification_share`, and with identity verification shares the expected share is deterministic and attacker-controlled.

### Likelihood Explanation
Reachable wherever untrusted or restored bytes are fed to `ThresholdKeys::read` — the explicit threat model for this API per its `Read` interface. The attack requires no threshold collusion and no honest-participant misbehavior; it only requires that a crafted serialized key blob is accepted, which the code permits since `read` → `new` performs no zero/identity validation on the reconstructed group key.

### Recommendation
- In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), reject if the computed `group_key` is identity, and reject identity verification shares.
- Alternatively/additionally, use the identity-rejecting `Curve::read_G` semantics for verification shares in `ThresholdKeys::read` (crypto/dkg/src/lib.rs:622), consistent with FROST's point parsing.

### Proof of Concept
```rust
// Craft a serialized ThresholdKeys where all verification shares are identity.
// ThresholdKeys::read accepts them (Ciphersuite::read_G doesn't reject identity),
// so group_key = sum(identity * lambda_i) = identity.
// After keys.offset(k), group_key() == G * k: anyone knowing k can spend/sign.
let mut buf = vec![];
buf.extend((Secp256k1::ID.len() as u32).to_le_bytes());
buf.extend(Secp256k1::ID);
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(1);                    // Interpolation::Lagrange
buf.extend(Secp256k1::F::ZERO.to_repr());            // secret_share = 0
buf.extend(<Secp256k1::G as Group>::identity().to_bytes()); // identity verif share
let keys = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // "zero address" accepted
let tweaked = keys.offset(Secp256k1::F::ONE); // group_key == generator: key = 1
```
