### Title
Unvalidated `sender`/`recipient` indexes in blame evaluation panic via unchecked `HashMap` indexing - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Mattermost advisory (CVE-2023-5967) is a missing-validation panic: a request field (User-Agent) is used without checking it exists, crashing the plugin. The Serai analog is in PedPoP's blame evaluation: `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` directly, without validating that the claimed `sender`/`recipient` are members of the participant set (`1..=n`). An unprivileged party who submits a blame request naming a nonexistent participant causes an out-of-bounds `HashMap` index panic, crashing the evaluating node.

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys and commitments only for participants `1..=n` (crypto/dkg/pedpop/src/lib.rs:656-660). `blame(sender, recipient, msg, proof)` then forwards to `blame_internal` → `Decryption::decrypt_with_proof`, which does `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388). `Participant` is any nonzero `u16` (crypto/dkg/src/lib.rs:29-35), so `Participant(999)` is a perfectly valid value that is simply absent from the map — indexing panics (`HashMap` `Index` impl unwraps).

The only gate before the panic is `msg.pop.verify(...)` (encryption.rs:374-379), and the PoP challenge binds `from` = the attacker-chosen `sender` (encryption.rs:302-323). The attacker fully controls the `EncryptedMessage` bytes — they pick `key = k*G` for a known `k`, compute `pop_challenge(context, pub_nonce, key, attacker_chosen_sender, msg)`, and produce a valid `SchnorrSignature`. Passing `proof = Some(<any bytes that parse as EncryptionKeyProof>)` then reaches `self.enc_keys[&decryptor]` with a bogus `decryptor` before the DLEq is even checked.

Even when a *legitimate* decryption key is used (the accuser is a real participant who knows their own `enc_key` and builds a valid `EncryptionKeyProof` for a crafted `msg`), setting `sender = Participant(n+1)` gets past signature verification and decryption, then panics at `self.commitments[&sender]` in `blame_internal` (crypto/dkg/pedpop/src/lib.rs:599) when evaluating the share-verification statements. `AdditionalBlameMachine::new`'s own docstring admits invalid input "may cause everything from inaccurate blame to panics" (lib.rs:646-648), but neither `blame` nor `blame_internal` validates `sender`/`recipient` against the registered set.

### Impact Explanation
Any node evaluating blame — including third-party observers via `AdditionalBlameMachine` and participants via `BlameMachine::blame` — crashes on a single crafted blame request. In a coordinator/processor deployment this is a remotely triggerable panic aborting DKG fault handling, denying completion of the key-generation/slashing flow — the same availability impact class as the Mattermost panic (CWE-754, CVSS A:L, Medium).

### Likelihood Explanation
Reachable by any unprivileged party who can submit a blame accusation: the only requirements are bytes that parse as `EncryptedMessage` (easy — `EncryptedMessage::read` accepts any canonical point/signature/scalar bytes, encryption.rs:170-177), a self-signed PoP bound to an arbitrary `sender` index (trivially produced by the attacker), and a `recipient`/`sender` index outside `1..=n`. No collusion, no leaked keys, no broken BFT assumption needed.

### Recommendation
In `blame_internal`/`decrypt_with_proof`, validate `sender` and `recipient`/`decryptor` are present in `commitments`/`enc_keys` before indexing — return `sender` (faulty accusation encoding) or an explicit error otherwise. Replace `map[&key]` indexing with `map.get(&key).ok_or(...)` / a checked lookup in both `Decryption::decrypt_with_proof` (encryption.rs:388) and `BlameMachine::blame_internal` (lib.rs:599), and document that `blame` must not panic on arbitrary participant indexes.

### Proof of Concept
```rust
// params: ThresholdParams::new(t, n, i); n = e.g. 150
// Attacker builds a blame request as accuser:
let ghost = Participant::new(n + 1).unwrap();      // valid Participant, not in the DKG
let k = Zeroizing::new(<C as Ciphersuite>::random_nonzero_F(rng));
let key = C::generator() * k.deref();
let nonce_s = Zeroizing::new(C::random_nonzero_F(rng));
let R = C::generator() * nonce_s.deref();
let msg_bytes: SecretShare<C::F> = SecretShare::read(&mut &[0u8; 32][..], params).unwrap();
// pop binds attacker-chosen `from` (= a real registered sender, or even `ghost`)
let c = pop_challenge::<C>(context, R, key, some_sender, msg_bytes.as_ref());
let pop = SchnorrSignature::sign(&k, nonce_s, c);
let msg = EncryptedMessage { key, pop, msg: Zeroizing::new(msg_bytes) };
let proof = Some(EncryptionKeyProof::read(&mut valid_64_bytes.as_slice()).unwrap());

// Victim runs blame evaluation (e.g., AdditionalBlameMachine built from the
// round-1 commitments) — panics inside decrypt_with_proof:
machine.blame(some_sender, ghost, msg, proof);
// thread panics: `enc_keys[&ghost]` -> HashMap index out of bounds
```
Likewise `machine.blame(ghost, real_recipient, msg_with_pop_bound_to_ghost, Some(valid_key_proof))` panics at `self.commitments[&ghost]` in `blame_internal` once decryption succeeds.
