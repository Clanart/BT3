### Title
Payout tx's OP_RETURN operator attribution is not covered by the withdrawal signature, allowing malleation of which operator is credited/blamed for a fronted withdrawal - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` spends the user's withdrawal UTXO with a `SIGHASH_SINGLE|ANYONECANPAY` Schnorr signature that only binds input 0 to output 0 (the user's payout). The `operator_xonly_pk` written into the OP_RETURN output — the sole piece of data the protocol later uses to decide *which operator fronted the withdrawal* — is not covered by that signature at all. Any party that observes the signature (e.g., in the mempool before confirmation, or via RBF) can rebroadcast a variant of the payout transaction with the same signed output 0 but a different OP_RETURN operator pubkey (or an invalid one), before the real operator's broadcast confirms.

### Finding Description
`create_payout_txhandler` builds the payout transaction as: [1](#0-0) 

The witness is a single key-spend signature (`user_sig`) over input 0. The caller (`Operator::withdraw` / verifier's optimistic payout path) enforces `SinglePlusAnyoneCanPay` sighash type when validating the user's signature: [2](#0-1) 

By BIP-341/342 semantics, `SIGHASH_SINGLE | ANYONECANPAY` binds *only* input 0 to output 0. It does **not** commit to any other input or output — including the anchor output and, critically, the OP_RETURN output carrying the operator's x-only pubkey. That means the OP_RETURN content is unauthenticated plaintext that whoever constructs/broadcasts the final transaction can set to anything, without invalidating the signature.

The chain later trusts this OP_RETURN blindly to decide "who fronted this withdrawal": the block-syncer scans the transaction that spends the registered withdrawal UTXO and extracts the operator pubkey purely from the OP_RETURN bytes, with no cryptographic binding to who actually funded/broadcast the transaction: [3](#0-2) 

This value is persisted as `payout_payer_operator_xonly_pk` and drives two critical downstream flows:
1. `PayoutCheckerTask` looks up the *first unhandled payout* keyed by an operator's own xonly pubkey and automatically starts the reimbursement/kickoff process for it: [4](#0-3) [5](#0-4) 

2. `is_kickoff_malicious` compares the operator that actually sends a kickoff against the `payout_payer_operator_xonly_pk` recorded from the OP_RETURN, and treats *any mismatch or missing pubkey as malicious*: [6](#0-5) 

Because the OP_RETURN is unauthenticated, an attacker who sees the signed, not-yet-confirmed payout transaction in the mempool (public information, requiring no privileged role, key, or certificate) can construct and get mined a variant transaction that:
- reuses the exact same signed input/output 0 (so the signature check still passes), and
- carries a different operator's x-only pubkey (or a malformed/absent OP_RETURN) in place of the genuine payer's.

Effects:
- If the attacker substitutes a *different, uninvolved* operator's pubkey: that operator's `PayoutCheckerTask` (`get_first_unhandled_payout_by_operator_xonly_pk`) will pick up a payout it never funded and drive it through `handle_finalized_payout`/kickoff/reimbursement, letting an operator claim reimbursement for a withdrawal it did not pay for — "an operator reimbursed for a payout it never funded."
- If the attacker instead strips/corrupts the OP_RETURN so `operator_xonly_pk` parses to `None`: the genuine operator that actually fronted the withdrawal is never matched by `get_first_unhandled_payout_by_operator_xonly_pk` (query filters on `payout_payer_operator_xonly_pk = $1`), so it can never be routed into the reimbursement flow through the normal task; and if it nevertheless sends a kickoff, `is_kickoff_malicious` treats "no operator xonly pk found in payout tx OP_RETURN" as malicious — leading to the honest operator being challenged and having its round/collateral burned for a withdrawal it legitimately paid.

### Impact Explanation
This breaks the core custody-attribution binding the whole reimbursement protocol relies on: *the operator recorded as "payer" for a withdrawal UTXO must equal the operator that actually fronted the payment*. Once broken:
- A malicious actor can misattribute reimbursement rights to an uninvolved operator (or to no operator), causing an operator to be reimbursed for BTC it never paid out — a direct custody/economic loss for the bridge.
- Alternatively an honest operator that genuinely fronted a withdrawal can be permanently denied reimbursement and/or have its kickoff flagged malicious (collateral burn), which matches the Critical impact categories "an operator reimbursed for a payout it never funded," "an honest operator permanently unable to be reimbursed," and "an honest operator's collateral burned."

### Likelihood Explanation
The attack requires no privileged role, no key compromise, and no deployment-configuration deviation: it only requires observing a broadcast-but-unconfirmed payout transaction (public mempool data) and re-broadcasting a variant with a different OP_RETURN before/instead of the original confirms (feasible via fee bumping / first-seen races, or simply by whichever transaction miners include). The requirement to construct a competing transaction using only the publicly visible signature and UTXO is a standard SIGHASH_SINGLE|ANYONECANPAY malleability technique and does not require breaking any cryptography.

### Recommendation
Bind the operator attribution cryptographically to the same signature that authorizes spending the withdrawal UTXO, rather than relying on an unsigned OP_RETURN push. Concretely, either:
- Have the user's payout authorization committed with a sighash mode that also covers the OP_RETURN output (e.g. `SIGHASH_ALL` restricted to a fixed transaction template, or `SIGHASH_SINGLE` applied to an output index that structurally includes the OP_RETURN data), or
- Require the operator to musig2/co-sign (or otherwise cryptographically commit to) the operator-pubkey-bearing output so it cannot be swapped without invalidating the transaction, or
- Attribute payer identity from something intrinsically bound to the operator (e.g., the change/anchor output's script pubkey being an operator-controlled key, verified against known operator keys) instead of from unauthenticated OP_RETURN data.

### Proof of Concept
1. Operator A calls `withdraw`, causing `create_payout_txhandler` to build and sign (via the user's pre-supplied `SinglePlusAnyoneCanPay` `user_sig`) a payout transaction `tx1` with `OP_RETURN = operator_A_xonly_pk`, and broadcasts it. [7](#0-6) 
2. Before `tx1` confirms, an attacker observes it in the mempool (public data) and constructs `tx2` reusing the same input 0 witness (valid because the signature only commits to input 0/output 0) but with an OP_RETURN containing operator B's xonly pubkey (or invalid data), and gets `tx2` mined instead (e.g. by paying a higher fee).
3. The verifier's block syncer processes the block, calls `update_finalized_payouts`, and records `payout_payer_operator_xonly_pk = operator_B` (or `NULL`) for this withdrawal index, based purely on `tx2`'s OP_RETURN: [8](#0-7) 
4. Operator B's `PayoutCheckerTask` subsequently detects the "unhandled payout" attributed to it and autonomously drives the kickoff/reimbursement flow, claiming reimbursement it never funded: [5](#0-4)  — while operator A, who actually paid the user, is left with no matching `payout_payer_operator_xonly_pk` entry and, if it proceeds with its own kickoff, is flagged malicious by `is_kickoff_malicious`: [9](#0-8)

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
