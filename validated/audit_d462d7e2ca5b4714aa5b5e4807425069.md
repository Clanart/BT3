## Analog Found: Phantom Escrow Credit in `IntentGatewayV2.placeOrder` (Tron Deployment)

### Title
Tron `IntentGatewayV2.placeOrder` credits escrow from `safeTransferFrom` return value alone, without verifying actual token receipt — enabling fake-collateral orders that drain solver funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core broken invariant is: *a contract trusts an ERC20 `transferFrom`-family call's "success" signal to conclude that value actually moved, and then records accounting state (a tier/escrow balance) based on that unverified signal.* The report explicitly notes that switching to `safeTransferFrom` alone does **not** fix this — an actual balance-delta check is required, because `safeTransferFrom` only requires the call to not revert and (if it returns data) decode to `true`; it never inspects `balanceOf`.

The Tron-chain deployment of Hyperbridge's Intent Gateway, `evm/tron/contracts/apps/IntentGatewayV2.sol`, reproduces exactly this residual gap. In `placeOrder`, escrow accounting is credited from the caller-declared/fee-reduced order amount immediately after calling `safeTransferFrom`, with no balance-before/after check:

```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:444-462
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    address token = address(uint160(uint256(order.inputs[i].token)));
    if (token == address(0)) {
        if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
        msgValue -= order.inputs[i].amount;
    } else {
        IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
    }

    // Store reduced amount (after protocol fees) in escrow
    _orders[commitment][token] += reducedInputs[i].amount;
    ...
``` [1](#0-0) 

The canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`) protects against exactly this by snapshotting the gateway's real token balance before and after the transfer and crediting only the *actual received delta*:

```solidity
// evm/src/apps/IntentGatewayV2.sol:288-292
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [2](#0-1) 

The Tron variant omits this balance verification entirely, both in the non-predispatch path (line 453/457) and the predispatch-to-dispatcher path where it still records `reducedInputs[i].amount` into `_orders` without confirming the dispatcher's swept balance matches what was declared.

### Finding Description
`order.inputs[].token` is fully attacker-controlled — any user placing an order chooses the ERC20 contract used as the input asset. A malicious order-placer can deploy a custom ERC20 whose `transferFrom` returns `true` (satisfying `SafeERC20.safeTransferFrom`'s success check) while moving zero or near-zero real balance to the gateway. Because `placeOrder` on Tron credits `_orders[commitment][token] += reducedInputs[i].amount` unconditionally after the call succeeds, the escrow ledger now shows a fully-collateralized order commitment even though the gateway holds none of the declared input token.

This is the direct analog of the DAO Pool bug: `createTier` accepted a `totalTokenProvided` value into pool accounting based purely on a low-level call's return, without checking that the contract's balance actually increased — here, `_orders[commitment][token]` is credited purely from `safeTransferFrom`'s pass/fail signal.

### Impact Explanation
The `OrderPlaced` event and on-chain `_orders` state make the fake order appear fully backed. A solver observing the order commits real value by:
1. Delivering genuine output tokens to the beneficiary during `fillOrder`, and
2. Relying on the settlement/withdrawal path (`_withdraw`/`withdraw`) to later release the "escrowed" input tokens to them as compensation.

Because the recorded escrow for the malicious token never corresponds to real custody, the solver either receives a worthless transfer (if the malicious token also fakes its own `transfer`/`balanceOf`, which the attacker fully controls) or the withdrawal reverts, leaving the solver's already-delivered output assets unrecovered. This is a direct loss-of-funds / wrong-beneficiary-value vector for solvers acting on gateway-reported escrow state, matching the bounty's "false state acceptance" and "loss of funds" categories — reachable by any unprivileged order-placer with no relayer, prover, or admin compromise required.

### Likelihood Explanation
High: placing an order is a fully public, unprivileged entrypoint (`placeOrder`), and choosing a custom malicious ERC20 as an input token requires no special permission or capital beyond deploying a trivial contract. The only requirement is that a solver chooses to fill the order — solvers routinely fill orders based on on-chain escrow state exactly because that state is expected to reflect real custody, which is the whole premise of the Intent Gateway design.

### Recommendation
Mirror the canonical EVM contract's pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`: snapshot `IERC20(token).balanceOf(address(this))` (or the dispatcher's balance for the predispatch path) before calling `safeTransferFrom`, and credit `_orders[commitment][token]` only with the post-transfer balance delta, not the caller-declared `reducedInputs[i].amount`. Apply the same before/after balance check to the predispatch sweep-back loop (lines 410–440) so dust/shortfall is measured against real balances rather than assumed transfer success.

### Proof of Concept
1. Attacker deploys `FakeToken`, an ERC20 whose `transferFrom(from, to, amount)` always returns `true` without adjusting any balances (or transfers a negligible amount).
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FakeToken, amount: 1_000_000e18}` and a legitimate `order.output` (e.g., requesting USDC).
3. `placeOrder` executes `IERC20(FakeToken).safeTransferFrom(attacker, address(this), 1_000_000e18)` — call succeeds per `FakeToken`'s logic — then executes `_orders[commitment][FakeToken] += reducedInputs[0].amount` (≈1,000,000e18 minus protocol fee), despite the gateway's real `FakeToken` balance never increasing.
4. A solver observes the `OrderPlaced` event/`_orders` state showing full collateralization, calls `fillOrder`, and delivers real USDC to the beneficiary.
5. On settlement, `withdraw`/`_withdraw` attempts to release the "escrowed" `FakeToken` amount to the solver; the transfer is either worthless (if `FakeToken.transfer` is also spoofed) or reverts due to insufficient real balance — in either case the solver's genuine USDC outlay is not honored by real collateral.
