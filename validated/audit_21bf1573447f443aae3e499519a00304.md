### Title
Forged `ReceivedOutput` causes signing of transactions spending nonexistent UTXOs - ([File: networks/bitcoin/src/wallet/mod.rs](crypto/../networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an untrusted `(offset, TxOut, OutPoint)` tuple without proving that the outpoint contains the supplied output or belongs to the wallet. [1](#0-0) 

### Finding Description
`ReceivedOutput::read` deserializes the scalar offset, claimed `TxOut`, and claimed `OutPoint` as three independent, attacker-controlled fields. [1](#0-0)  `SignableTransaction::new` then trusts the embedded `TxOut` as the input value and embeds the embedded `OutPoint` in the transaction input. [2](#0-1)  Before creating the signing machines, `SignableTransaction::multisig` only checks that the offset-derived key produces the same `script_pubkey` as the claimed output; it does not authenticate that `outpoint` resolves to that output or that the output exists. [3](#0-2)  The resulting signature hash commits to the forged prevout data through `Prevouts::All`. [4](#0-3) 

### Impact Explanation
An unprivileged party that can supply serialized `ReceivedOutput` bytes can make the wallet treat an unavailable or mismatched outpoint as spendable balance. [1](#0-0)  The wallet can then construct and threshold-sign a transaction whose declared prevout value does not match the actual blockchain UTXO, producing a transaction that cannot be validly spent. [4](#0-3)  This satisfies the impact of funds being reported as received even though they are not spendable. [2](#0-1) 

### Likelihood Explanation
The attack requires only control over bytes passed to `ReceivedOutput::read`, such as forged wallet state, cached scan data, or another untrusted source feeding that API. [1](#0-0)  No validator compromise, malformed signature share, or knowledge of the private key is required because `multisig` checks only key/script agreement, not UTXO authenticity. [5](#0-4) 

### Recommendation
Do not treat deserialized `ReceivedOutput` values as authenticated scan results. [1](#0-0)  Before `SignableTransaction::new`, verify every `outpoint` against a trusted Bitcoin UTXO source and confirm that the retrieved `TxOut` exactly matches the supplied output. [2](#0-1)  Prefer making `ReceivedOutput` construction private to `Scanner`, or introduce an authenticated/untrusted representation so arbitrary bytes cannot be promoted directly into spendable inputs. [6](#0-5) 

### Proof of Concept
```rust
// The wallet's normal, already-Taproot-tweaked key.
let wallet_key = wallet_keys.group_key();
let wallet_script = p2tr_script_buf(wallet_key).unwrap();

// Attacker-controlled bytes accepted by ReceivedOutput::read:
//   offset = 0
//   output = high-value TxOut paying wallet_script
//   outpoint = arbitrary/nonexistent or lower-value UTXO
let forged = ReceivedOutput::read(&mut forged_bytes).unwrap();

// The forged output is accepted because its script matches the key/offset.
let signable = SignableTransaction::new(
  vec![forged],
  &[(payment_script, payment_amount)],
  None,
  None,
  fee_per_vbyte,
).unwrap();

// This check passes even though the outpoint does not contain the claimed TxOut.
let machine = signable.multisig(&wallet_keys).unwrap();
```

`SignableTransaction::multisig` checks only that `p2tr_script_buf(keys.offset(offset).group_key())` equals the claimed prevout script, so a forged tuple using the wallet script and a fabricated `OutPoint` reaches signing. [5](#0-4)  The completed workflow embeds signatures into the transaction inputs even though the claimed funding output is not the actual referenced UTXO. [7](#0-6)

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;

      outpoint =
