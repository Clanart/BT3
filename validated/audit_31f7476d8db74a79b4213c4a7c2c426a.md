Direct evidence found: GitHub Desktop explicitly **disables** the exact Git security control designed to stop this class of attack. [1](#0-0) 

## Title
Cloning untrusted repositories disables Git's CVE-2022-39253 embedded-repository protection, allowing a crafted `.git`/submodule symlink to make Desktop persist and later read/write a `gitDir` outside the repository - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every `git clone --recursive` Desktop performs: [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is Git's own escape hatch for the fix to CVE-2022-39253, which normally makes `git clone --recurse-submodules` refuse to embed a submodule (or follow a `.git` gitlink) whose resolved location escapes the top-level worktree (e.g. via a symlinked submodule path or a crafted `gitdir:` pointer). By forcing this variable to `false`, Desktop re-enables exactly the class of attack the question describes: a malicious repository can contain a submodule/`.git` construct whose real git directory resolves outside the cloned tree, and Git itself will now happily create/follow it during Desktop's clone instead of refusing.

### Finding Description
1. A user clones a malicious repository through Desktop's `_clone`/`CloningRepositoriesStore.clone` → `clone()` path [3](#0-2) .
2. `clone()` runs `git ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false`, disabling Git's own out-of-tree embedded-repository guard [4](#0-3) .
3. With that guard off, Git will resolve/create a gitlink (`.git` file with `gitdir: ...`) or submodule admin directory that points outside the clone root when the repository's submodules/`.gitmodules`/tree entries are crafted to do so.
4. When Desktop subsequently inspects the repository, `getRepositoryType()` shells out to `git rev-parse --is-bare-repository --show-cdup --git-dir` and trusts whatever absolute `gitDir` Git reports, resolving it with `resolve(path, gitDir)` [5](#0-4) .
5. That value is persisted verbatim into the `RepositoriesDatabase` via `updateRepositoryGitDir`, with no validation that it is contained within the repository path [6](#0-5) .
6. `Repository.resolvedGitDir` then returns this untrusted, potentially out-of-tree path for all subsequent Git-metadata file reads/writes Desktop performs directly (bypassing `git` itself), e.g. `MERGE_HEAD`/`SQUASH_MSG` and rebase state files [7](#0-6) [8](#0-7) [9](#0-8) .

Note: a bare top-level `.git` file with a malicious `gitdir:` cannot itself be smuggled through `git clone` because Git refuses to check out a tracked blob named `.git` regardless of this setting (a separate, unrelated protection). The exploitable path is specifically through `--recursive` submodule cloning, which is precisely what `GIT_CLONE_PROTECTION_ACTIVE=false` reopens.

### Impact Explanation
An attacker who controls a repository's content (submodule layout / `.gitmodules`) can, when a victim clones it in Desktop, cause Git to place git-administrative data (and via subsequent operations, hook execution or object writes) at a location Desktop itself is subsequently made to trust as `gitDir`/`resolvedGitDir`. Desktop's own file reads/writes against `resolvedGitDir` (merge/rebase/squash state files) then target that attacker-influenced path, which can be outside the intended working tree - matching the "file write or read outside the repo" impact class.

### Likelihood Explanation
High for any user who clones an untrusted/malicious public repository through Desktop's clone flow, since the protection is disabled unconditionally for every clone (`clone.ts` line 83), not just local clones, and there is no repository-trust prompt gating this behavior before the flag is applied.

### Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`, or scope it only to cases where it's provably required, restoring Git's default CVE-2022-39253 protections.
- In `getRepositoryType()`/`updateRepositoryGitDir`, validate that the resolved `gitDir` is contained within the repository's top-level working directory (or a known-safe location such as `.git/worktrees/...`) before persisting or using it, rejecting/flagging repositories where it is not.

### Proof of Concept
1. Build a malicious repository with a submodule entry in `.gitmodules` whose working-tree path is a symlink (or otherwise crafted to resolve) to a location outside the top-level repo.
2. Clone it in GitHub Desktop (which runs `git -c ... clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false`).
3. Observe that Git, with the protection disabled, creates/embeds the submodule's git directory at the out-of-tree location instead of refusing as it would with default settings.
4. Trigger `getRepositoryType()` (e.g. via repository refresh) and inspect the `gitDir` persisted by `repositoriesStore.updateRepositoryGitDir` in the `RepositoriesDatabase`, confirming it points outside the repository root.
5. Trigger a merge/rebase status check (`isMergeHeadSet`, `getRebaseInternalState`) and confirm the file reads/writes occur via `repository.resolvedGitDir` against the out-of-tree path.

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
