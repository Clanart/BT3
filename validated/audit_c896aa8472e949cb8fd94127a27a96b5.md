Recursive clone disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safety check, allowing a malicious repository to execute arbitrary hooks/code on clone - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` in `app/src/lib/git/clone.ts` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` when invoking `git clone --recursive` for every repository the user clones through Desktop. `GIT_CLONE_PROTECTION_ACTIVE` is the Git-upstream safety switch introduced to mitigate the class of vulnerabilities where a crafted repository (with a submodule or nested `.git` path that collides with `.git` on case-insensitive or Unicode-normalizing filesystems, or via symlinks) tricks `git clone --recursive` into writing into the parent repository's `.git` directory - e.g. planting a hook that then executes during the same clone/checkout sequence. Desktop force-disables this check on every clone, reintroducing that class of attack for any user who clones or adds a malicious remote through the app, on the default (case-insensitive) filesystems most desktop users run (Windows and macOS).

Note that the rest of `clone.ts` shows careful, defense-in-depth hardening against other clone-time attacks — `isClonePathSensitive()` blocks destination paths that point at `~/.ssh`, `~/.gnupg`, `~/.config`, `~/.gitconfig`, etc. [4](#0-3)  and `sanitizeCloneName()` (in `app/src/lib/remote-parsing.ts`) prevents traversal via a crafted repository name so the clone destination can't escape the intended base directory. This makes the explicit, unconditional disabling of `GIT_CLONE_PROTECTION_ACTIVE` for the `--recursive` clone stand out as an intentional relaxation of an upstream Git safety mechanism rather than an oversight — but nothing in the file documents *why* it is necessary, and no compensating check (e.g. rejecting submodule paths that collide with `.git` case-insensitively, or refusing symlinked submodule gitdirs) exists elsewhere in this code path to replace the protection that was turned off.

This is the same broken-invariant pattern as the Sablier report: a single combined operation (`_cancel`'s dual transfer; here, `clone --recursive`'s "fetch objects + write worktree + init/checkout submodules" sequence) is executed without separating out the step an attacker can corrupt from the step the victim depends on. In Sablier, the recipient (attacker-controlled address) could make the shared transfer step fail and thereby block the sender's legitimate withdrawal. Here, the attacker (a hostile remote/repository author) controls the exact content processed inside that same combined operation — including submodule paths/names, symlinks, and nested `.git` layout — and Desktop has explicitly told Git not to apply the guard that exists specifically to stop that content from writing into (or executing from) the outer repository's control directory during the clone.

### Impact Explanation
If the Git binary bundled via `dugite` includes the `GIT_CLONE_PROTECTION_ACTIVE` guard (added upstream specifically to close the class of "malicious submodule/`.git` collision" clone vulnerabilities), disabling it here means:
- An attacker who gets a victim to clone or add-and-clone their repository through GitHub Desktop's UI (a normal, expected user action — cloning a repo is core functionality, not "unnatural user steps") can craft a repository whose submodule structure exploits case-insensitivity/Unicode-normalization or symlinks so that Git writes attacker-controlled content into the *outer* repository's `.git` directory (e.g. hooks) during the same `--recursive` clone.
- Because hooks execution is already wired up through Desktop's own hook-interception machinery (`app/src/lib/hooks/*`, `withHooksEnv`, `getRepoHooks`), any hook planted this way can subsequently run with the user's privileges the next time Desktop performs a covered Git operation (commit, checkout, merge, push, etc.), i.e. arbitrary code execution as the desktop user — a "silent corruption" primitive well beyond just corrupting what is committed.
- This exactly matches the accepted impact bar: attacker controls a cloned/fetched repository, and the result is code execution / file write outside the intended repo structure.

### Likelihood Explanation
The trigger requires nothing more than the victim cloning (or adding as a remote and letting Desktop auto-init submodules for) an attacker-supplied repository URL — the single most common Desktop workflow — with no local access, no admin rights, no pre-existing malware, and no unnatural steps. The only uncertainty is whether the specific `dugite`/Git version bundled with this build actually implements the `GIT_CLONE_PROTECTION_ACTIVE` check server-side (this could not be verified from the available `package.json`/`clone-test.ts` contents in this pass); if it does, disabling it is a direct reintroduction of a fixed CVE-class bug. This should be confirmed by checking the bundled Git/dugite version, but the code unambiguously and unconditionally opts out of the protection for every recursive clone regardless of source trust, which is a real, exploitable regression regardless of exact CVE numbering.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE` unconditionally. If there is a specific benign scenario (e.g. cloning a trusted local template repo) that needs the check bypassed, gate the bypass behind that specific, narrow case instead of applying it to every `git clone --recursive` invocation triggered by an arbitrary user-supplied URL. At minimum, keep the protection enabled for all remote (non-local, non-verified) clone sources, and add regression tests analogous to the existing `clone-path-safety-test.ts`/`sanitizeCloneName` tests that assert a malicious submodule/`.git`-colliding repository fails the clone rather than silently completing with hooks planted in `.git/hooks`.

### Proof of Concept
1. On a case-insensitive filesystem (default macOS/Windows), craft a repository `evil.git` containing a submodule whose configured path/name is chosen so that, combined with Git's submodule gitdir linking, it aliases the outer repository's `.git` directory (the historical CVE-2024-32002-style layout: a submodule path that case-insensitively or via Unicode normalization resolves to `.git`, or a symlink placed as a tracked entry pointing back at `.git`).
2. Populate the submodule's checked-out content with an executable file named after a hook Desktop intercepts (e.g. `post-checkout`, `pre-commit` — see `knownHooks` in `app/src/lib/hooks/get-repo-hooks.ts`).
3. Have the victim clone `evil.git` via GitHub Desktop's "Clone repository" flow. Desktop runs `git -c init.defaultBranch=... clone --recursive -- evil.git <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set [2](#0-1) , so the upstream check that would normally abort the clone or refuse to write the colliding path is skipped.
4. On the next Desktop-driven Git operation in that repository that Desktop intercepts hooks for (commit, checkout, etc., per `createCommit` in `app/src/lib/git/commit.ts`), the planted hook executes with the victim's privileges.

*Caveat:* Full exploitation depends on the exact `dugite`/Git version bundled by this build actually enforcing `GIT_CLONE_PROTECTION_ACTIVE`; this could not be confirmed from the indexed files (only two matches in `package.json` for `"dugite"` were found, and their content was not retrievable in this pass). The unconditional disabling of a named, security-purpose environment variable for every recursive clone of an arbitrary URL is nonetheless a concrete, reachable weakening of clone-time defenses that should be verified and fixed regardless.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
