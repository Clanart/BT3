## Title
Native-token overpayment is silently trapped in `EvmHost` because `dispatch()`/`fundRequest()` never refund unspent ETH after the exact-output Uniswap swap - ([File: evm/src/core/EvmHost.sol])

### Summary
The external report's core invariant break is: an AMM interaction that moves user funds provides no protection/accounting for the difference between what the user is charged and what they should be charged, letting value leak away silently. In Hyperbridge's `EvmHost.sol`, the native-token fee-payment path performs the same class of unguarded value flow: `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` call `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` but discard the returned `amounts` array and never refund the caller for the difference between `msg.value` and the ETH actually consumed by the swap.

### Finding Description
`IUniswapV2Router02.swapETHForExactTokens` is an exact-output swap: it consumes only as much ETH as needed to produce the requested `fee`/`get.fee`/`amount` of fee tokens, and refunds the unused portion of `msg.value` to whoever called the router — which is `EvmHost` itself, not the original transaction sender. [1](#0-0) [2](#0-1) [3](#0-2) 

In all three functions the return value of `swapETHForExactTokens` (an `amounts` array whose `amounts[0]` is the ETH actually spent) is discarded, and there is no subsequent step that computes `msg.value - amounts[0]` and forwards it back to `_msgSender()`. Contrast this with the correct pattern used elsewhere in the same codebase, `IntentGatewayV2._placeOrder`, which explicitly captures the swap result and refunds the leftover native token to the caller: [4](#0-3) 

Because `EvmHost.dispatch()`/`fundRequest()` are public, unauthenticated, `payable` entrypoints callable by any user who wants to send a cross-chain message or top up a request's relayer fee, any ETH sent above the exact amount required by the swap (which is unpredictable in advance since it depends on live pool price, especially under a sandwich/backrun that moves the WETH↔feeToken price up between quote and execution) becomes permanently stuck in the `EvmHost` contract balance instead of being returned to the payer. There is no accounting structure (`FeeMetadata`, event, or storage) that tracks this residual ETH as belonging to any user, so it is not recoverable by the original sender through any normal path.

### Impact Explanation
This is a direct "loss of user funds" primitive matching the bounty's accepted impact list: any user (or automated relayer/SDK client, since the SDK's own fee-quoting logic in `docs/content/developers/evm/messaging/post-requests.mdx` and `tokenGateway.ts` explicitly documents users "will perform a swap under the hood using the local uniswap router" via `msg.value`) who overestimates the ETH needed to cover `post.fee`/`get.fee`/`amount` — which is normal/expected since exact costs depend on the live AMM price at execution time and cannot be perfectly predicted at submission time — has the excess silently absorbed by the `EvmHost` contract with no refund and no recovery mechanism. Repeated across every `dispatch()`/`fundRequest()` call from any user paying in native token, this is a systemic, unbounded fund-loss bug in the primary fee-payment code path of the bridge's core host contract.

### Likelihood Explanation
High. `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` are the standard, documented way for any application/user to pay Hyperbridge fees in native token (per the docs snippet: "let the Host handle the Uniswap swap"). No malicious relayer, prover, or governance action is required — an ordinary user simply needs to send `msg.value` that isn't exactly equal to the router's required input (which is the common case, since the caller typically supplies a buffer above the on-chain quote to avoid reverting from price movement between quote and execution).

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2._placeOrder`.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: X}(DispatchPost{..., fee: F, ...})` where `X` is deliberately or naturally larger than the ETH cost to acquire `F` fee tokens at current pool price (e.g. `X` includes a slippage buffer, which any front-end/SDK would reasonably add given price can move between quote and tx confirmation).
2. `swapETHForExactTokens{value: X}(F, path, address(this), block.timestamp)` executes: it pulls only `amounts[0] < X` ETH from `msg.value` into the swap and refunds `X - amounts[0]` ETH to the caller, which is `EvmHost`, landing in the host contract's own balance.
3. `EvmHost.dispatch()` does not read `amounts[0]`, computes no refund, and simply continues to build/emit the `PostRequest`.
4. The user's transaction succeeds, `PostRequestEvent` is emitted with `fee: F`, but the user never receives back the `X - amounts[0]` ETH they overpaid — it remains stuck in `EvmHost`'s balance with no accounting entry crediting it to them, matching the exact repro pattern of `IntentGatewayV2._placeOrder` at [5](#0-4)  which the `EvmHost` functions are missing.
