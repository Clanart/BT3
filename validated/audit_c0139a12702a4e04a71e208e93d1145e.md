## Analysis [1](#0-0) 

The `CLZ` opcode (EIP-7939, activated at the Osaka fork) is registered without a `computationCost` field, leaving it at the Go zero-value (`0`):

```go
func enable7939(jt *JumpTable) {
	jt[CLZ] = &operation{
		execute:     opCLZ,
		constantGas: GasFastStep,
		minStack:    minStack(1, 1),
		maxStack:    maxStack(1, 1),
	}
}
```

The `computationCost` for `CLZ` is only ever assigned in `enablePermissionlessComputationCostModification`, which is applied exclusively to the `PermissionlessInstructionSet` (a fork strictly later than Osaka), not to `OsakaInstructionSet` itself: [2](#0-1) [3](#0-2) 

This is exactly the type of gap the CosmWasm/wasmvm advisory describes: an opcode/operation that a malicious contract can invoke cheaply (in gas) but whose real execution cost is not counted against the metering mechanism designed to bound wall-clock execution time (`ComputationCostLimit`), letting an attacker's transaction run far more operations per unit of gas than the limit intends, slowing block production.

### Root cause detail
Kaia's interpreter enforces a real-time execution bound via `opcodeComputationCostSum` vs `Config.ComputationCostLimit` (100ms/150ms per tx) on every opcode dispatch: [4](#0-3) 

Since `CLZ.computationCost == 0` on any chain running the Osaka fork (but not yet Permissionless), every `CLZ` execution adds `0` to `opcodeComputationCostSum`. Because `CLZ`'s gas cost is `GasFastStep` (very cheap, 5 gas per go-ethereum convention), a contract can execute an enormous number of `CLZ` instructions within a normal transaction gas limit while never approaching the `ComputationCostLimit` that is supposed to cap execution time — defeating the very purpose of the mechanism introduced to prevent exactly this "slow down block production" attack class.

### Reachability
This is reachable by any unprivileged party: deploy a contract with a tight loop of `PUSH/CLZ/JUMP` (or similar cheap-gas, uncosted opcodes) and send a normal `SmartContractExecution`/`SmartContractDeploy` transaction. `Execute` on `TxInternalDataSmartContractExecution` funnels straight into `vm.Call` → `run` → `EVMInterpreter.Run`, hitting the flawed accounting path directly: [5](#0-4) 

### Caveat
This bug is only live once a chain has activated the Osaka fork (`IsOsaka` but not yet `IsPermissionless`). I could not determine from the indexed files whether Osaka is currently activated on any production Kaia network (mainnet/testnet) — that would need to be checked against the live chain config/governance parameters, which is outside what the index can confirm.

### Title
Missing computationCost for CLZ opcode (EIP-7939) allows bypass of the OpcodeComputationCostLimit block-production time-guard - (File: blockchain/vm/eips.go)

### Summary
The `CLZ` opcode introduced by EIP-7939 at the Osaka fork is registered via `enable7939` without setting the `computationCost` field, leaving it at `0`. The `computationCost` value for `CLZ` is only assigned by `enablePermissionlessComputationCostModification`, applied solely to `PermissionlessInstructionSet`, a fork strictly after Osaka. As a result, any chain running with the Osaka fork active (prior to reaching Permissionless) treats every `CLZ` execution as contributing zero real-time cost, even though it is charged only cheap `GasFastStep` gas.

### Finding Description
Kaia bounds the real wall-clock execution time of a transaction's EVM execution using `opcodeComputationCostSum`, incremented per-opcode by `operation.computationCost` and checked against `Config.ComputationCostLimit` (100ms pre-Cancun / 150ms Cancun+) in the interpreter's main loop: [6](#0-5) 

For every other opcode in the jump table, a nonzero `computationCost` calibrated to its approximate real execution time is set (see `params/computation_cost_params.go`). `CLZ` is the exception: [1](#0-0) [7](#0-6) 

Since `newOsakaInstructionSet` only calls `enable7939` (no cost assignment), and the cost-fix `enablePermissionlessComputationCostModification` is applied only in `newPermissionlessInstructionSet` (a strictly later fork), the Osaka-era jump table ships `CLZ` with `computationCost = 0`. A contract composed mostly of `CLZ` instructions (interleaved with cheap stack/jump ops) can execute an arbitrarily large number of iterations for a given gas budget without ever tripping `ErrOpcodeComputationCostLimitReached`, defeating the safety mechanism that exists specifically to bound per-tx execution time and thereby protect block production throughput.

### Impact Explanation
This directly maps to the reported bug class: "malicious smart contract can slow down block production." Kaia's `ComputationCostLimit` mechanism (analogous to wasmvm's gas metering for real CPU time) exists precisely to prevent a contract from consuming disproportionate wall-clock time relative to its gas cost, which would otherwise let an attacker craft transactions/blocks that take excessively long to execute, delaying block production and degrading network-wide liveness. The `CLZ` gap allows exactly this bypass at low cost (paid gas ≈ trivial per-op).

### Likelihood Explanation
Exploitation requires only deploying an ordinary contract and sending a normal transaction/bundle — no special privileges, node access, or governance action needed, matching an unprivileged transaction sender scenario. The likelihood is gated only by whether/when the Osaka fork (and not yet Permissionless) is active on a given Kaia network; if so, exploitation is straightforward and repeatable by anyone.

### Recommendation
Set `jt[CLZ].computationCost = params.ClzComputationCost` directly inside `enable7939` (at Osaka activation) instead of deferring it to `enablePermissionlessComputationCostModification`, so the cost is present for every fork starting at Osaka, not only from Permissionless onward. Audit other `enableXXXX` functions introducing new opcodes to ensure `computationCost` is always populated at the opcode's activation point rather than a later fork.

### Proof of Concept
1. On a Kaia network with the Osaka fork active (and Permissionless not yet active), deploy a contract whose bytecode is a tight loop dominated by `PUSH1/CLZ/DUP/JUMPI` such that most gas is spent on `CLZ` (constant gas `GasFastStep`, `computationCost = 0`).
2. Send a `SmartContractExecution` transaction with a large gas limit invoking this loop; `TxInternalDataSmartContractExecution.Execute` calls `vm.Call` → `EVMInterpreter.Run`.
3. Because each `CLZ` contributes `0` to `in.evm.opcodeComputationCostSum`, the check `in.evm.opcodeComputationCostSum > in.evm.Config.ComputationCostLimit` at [8](#0-7)  never fires for this loop, regardless of how many `CLZ` iterations execute, up to the full gas limit of the transaction/block — unlike any other opcode-heavy loop, which would be capped by `ComputationCostLimit` well before exhausting gas.
4. Submitting many such transactions in a block lets the attacker consume the full per-block gas limit while incurring real execution/wall-clock time uncontrolled by the `ComputationCostLimit` safety valve, achieving the "slow down block production" effect the guard was designed to prevent.
