Based on my investigation, I found a legitimate local analog to the certificate-chain early-exit bug: `read_proof_check_for_parachain` in `modules/ismp/state-machines/substrate/src/lib.rs:316-358` silently `continue`s past a key when the trie lookup returns `TrieError::IncompleteDatabase`, instead of treating it as a hard failure.

### Title
Incomplete-trie proof causes silent skip of parachain header verification instead of rejection - (File: `modules/ismp/state-machines/substrate/src/lib.rs`)

### Summary
`read_proof_check_for_parachain` walks a trie built from prover-supplied nodes and, for each requested key, either records `Some(value)`, records `None` (genuine absence), or — on `TrieError::IncompleteDatabase` — silently `continue`s, omitting the key from the result map entirely [1](#0-0) . This mirrors the report's core flaw: a verification loop has more than one way to "exit" a per-item check, and one of those paths (an attacker-craftable condition — here, an incomplete/malformed proof node set) skips the check entirely rather than failing closed.

### Finding Description
The function is a copy of `sp_state_machine::read_proof_check`, adapted to tolerate incomplete databases [2](#0-1) . Compare this to the sibling function `read_proof_check` a few lines above, which has no such tolerance and returns a hard error for any trie read failure [3](#0-2) . The parachain variant instead does:
```rust
Err(e) =>
    if let TrieError::IncompleteDatabase(_) = *e {
        continue;
    } else {
        return Err(...);
    },
```
A prover can supply a storage proof that is deliberately missing the node needed to resolve one specific key while including enough nodes to satisfy the root check for the remainder of the requested keys. For that key, the trie lookup errors with `IncompleteDatabase` and the loop simply moves on — the key never appears in `result`, neither as `Some` nor `None`.

Whether this becomes exploitable depends entirely on how callers of this function treat a key absent from the returned `BTreeMap` versus a key present with `None`. If any downstream membership/receipt check does `result.get(&key).cloned().flatten()` (as `outbound_request.rs` and `accumulate.rs` do for other proof types) and treats "not found in map" the same as "no value" without independently re-checking `result.len() == keys.len()`, an attacker gets to choose whether a specific state-trie fact (e.g., a request commitment or a request receipt) is silently treated as absent, bypassing a membership check the same way the root CRL check was bypassed in the original report — by exploiting an inconsistency between two different "end of verification" paths in the same loop.

I was not able to fully trace every call site of `read_proof_check_for_parachain` within the available indexed context to confirm a caller that fails to re-check the map length before consuming a `None`/missing value; the two call sites are in `modules/ismp/clients/parachain/client/src/consensus.rs`, whose contents I could not fully inspect due to index size limits. This is a genuine gap in verification, not a confirmed end-to-end exploit chain.

### Impact Explanation
If a caller relies on `BTreeMap::get(...).flatten()` without also asserting `result.len() == keys.len()`, this allows false non-membership or false state acceptance for a chosen key inside an otherwise-valid batch proof — directly matching the bounty's "false proof/state acceptance" and "unauthorized execution" categories, since request/response/receipt checks gate fund movement and message dispatch.

### Likelihood Explanation
Medium-low confidence: the vulnerable *pattern* (inconsistent loop-exit semantics under an attacker-influenced condition) is confirmed in code, but I could not fully verify a consuming code path that fails to check the returned map's completeness, due to index truncation. The sibling `read_proof_check` function, and every other `verify_state_proof`/`verify_membership` implementation I reviewed (EVM, Tendermint, Pharos), enforces `values.len() != keys_len` as a hard error immediately after collecting proof results — suggesting the codebase is otherwise disciplined about this exact class of bug, which lowers confidence that `read_proof_check_for_parachain`'s callers are unguarded.

### Recommendation
- Make `read_proof_check_for_parachain` fail closed: return an error for `IncompleteDatabase` just like `read_proof_check` does, rather than silently omitting the key.
- At minimum, have every caller of `read_proof_check_for_parachain` assert `result.len() == keys.len()` before using the map, matching the pattern already used in `EvmStateMachine`, `TendermintEvmStateMachine`, `PharosStateMachine`, and `SubstrateEvmStateMachine`'s `verify_state_proof`/`verify_membership` implementations [4](#0-3) .
- Add a negative test supplying a storage proof with an intentionally missing node for one key in a multi-key batch, asserting the whole verification call fails rather than silently dropping that key.

### Proof of Concept
Conceptual (not independently executed, due to inability to inspect full caller context in `modules/ismp/clients/parachain/client/src/consensus.rs`):
1. Construct a parachain header/consensus state update whose storage proof correctly proves N-1 keys but omits the trie node needed to resolve the Nth key.
2. Call the code path that invokes `read_proof_check_for_parachain` with all N keys.
3. Observe the function returns `Ok(result)` with only N-1 entries instead of erroring.
4. If the caller consumes `result.get(&missing_key)` without checking `result.len() == keys.len()`, the missing key is treated as `None`/absent, letting an attacker choose which fact in the batch is silently unproven. [1](#0-0)

pub fn read_proof_check<H, I>(
	root: &H::Out,
	proof: StorageProof,
	keys: I,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error>
where
	H: hash_db::Hasher,
	H::Out: Debug,
	I: IntoIterator,
	I::Item: AsRef<[u8]>,
{
	let db = proof.into_memory_db();

	if !db.contains(root, EMPTY_PREFIX) {
		Err(Error::Custom("Invalid Proof".into()))?
	}

	let trie = TrieDBBuilder::<LayoutV0<H>>::new(&db, root).build();
	let mut result = BTreeMap::new();

	for key in keys.into_iter() {
		let value = trie
			.get(key.as_ref())
			.map_err(|e| Error::Custom(format!("Error reading from trie: {e:?}")))?
			.and_then(|val| Decode::decode(&mut &val[..]).ok());
		result.insert(key.as_ref().to_vec(), value);
	}

	Ok(result)
}

pub fn read_proof_check_for_parachain<H, I>(
	root: &H::Out,
	proof: StorageProof,
	keys: I,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error>
where
	H: hash_db::Hasher,
	H::Out: Debug,
	I: IntoIterator,
	I::Item: AsRef<[u8]>,
{
	let db = proof.into_memory_db();

	if !db.contains(root, EMPTY_PREFIX) {
		Err(Error::Custom("Invalid Proof".into()))?
	}

	let trie = TrieDBBuilder::<LayoutV0<H>>::new(&db, root).build();
	let mut result = BTreeMap::new();

	for key in keys {
		let raw_key = key.as_ref();

		match trie.get(raw_key) {
			Ok(Some(val)) => {
				let decoded = Decode::decode(&mut &val[..])
					.map_err(|e| Error::Custom(format!("Decode error: {e:?}")))?;
				result.insert(raw_key.to_vec(), Some(decoded));
			},
			Ok(None) => {
				result.insert(raw_key.to_vec(), None);
			},
			Err(e) =>
				if let TrieError::IncompleteDatabase(_) = *e {
					continue;
				} else {
					return Err(Error::Custom(format!("Trie fetch error: {e:?}",)));
				},
		}
	}

	Ok(result)
}
