Shared `Scanner` script pool lets unprivileged senders inject outputs into reserved internal flows, mixing token flows across purposes - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a "shared contract" bug class: multiple logical owners/flows funnel through one contract so token flows cannot be separated, funds get co-mingled, and an unrelated party can pollute the shared pool. In `bitcoin-serai`, the exact analog exists in `Scanner`: all output kinds (external deposits, branch outputs, change, forwarded outputs) share a single `HashMap<ScriptBuf, Scalar>` keyed only by `script_pubkey`, so `scan_transaction` cannot distinguish who created an output or which flow it belongs to beyond the script. Because the reserved offsets are publicly derivable constants (`Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")`), any unprivileged party can craft a transaction paying to the Branch/Change/Forwarded script of a known multisig key, and the scanner will classify their external payment as an internal-flow output.

### Finding Description
`Scanner::new` seeds `self.scripts` with the zero-offset P2TR script and `register_offset` inserts additional `script_pubkey -> offset` entries into the same map (`networks/bitcoin/src/wallet/mod.rs` lines 163–196). `scan_transaction` then reports any output whose `script_pubkey` is in the map as a `ReceivedOutput` carrying only the offset — no other distinguishing data (lines 199–214). The processor builds one scanner per group key where offsets `0`, `hash_to_F(KEY_DST, b"branch")`, `hash_to_F(KEY_DST, b"change")`, `hash_to_F(KEY_DST, b"forward")` map to `OutputType::External/Branch/Change/Forwarded` (`processor/src/networks/bitcoin.rs` lines 308–346), and `get_outputs` assigns `kind` purely from the matched offset and gives every matched output in a tx the same `presumed_origin` (derived from `tx.input[0]`) and `data` (lines 686–737). Since `hash_to_F` and `p2tr_script_buf` are public and deterministic, an attacker who knows the group key (publicly visible on-chain once used) can compute the Branch/Change/Forwarded addresses and send to them, producing outputs indistinguishable from the protocol's own internal-flow outputs.

### Impact Explanation
Outputs intended exclusively for protocol-internal flows (branch key rotation, change, forwarded funds) can be fabricated by an arbitrary third party and will be reported by `get_outputs`/`scan_transaction` with `OutputType::Branch`, `Change`, or `Forwarded`. This mixes attacker-originated token flow into buckets downstream logic assumes are protocol-generated, corrupting per-flow attribution (`presumed_origin` is shared across all outputs in the tx regardless of kind). Depending on scheduler/rotation handling (outside the in-scope crate), internal-flow outputs created by an outsider can perturb accounting, trigger spurious branch/rotation handling, or be aggregated as if they were change — exactly the co-mingling and misattribution consequences described in the report. Severity is bounded because the injected funds remain spendable only by the multisig (no direct theft), so this is a Medium integrity/attribution issue.

### Likelihood Explanation
Any Bitcoin user can send to any computable script_pubkey. The reserved offset scripts are deterministically derived from public constants and the public group key, so no privileged position is needed — a single standard P2TR payment to a Branch/Change/Forwarded address suffices to inject a misclassified output.

### Recommendation
Per the report's "separate contracts per safe" guidance, separate flows structurally rather than by convention: bind internal-flow outputs to their creating transaction (e.g., only accept Branch/Change outputs produced by transactions the protocol itself signed/spent inputs for — verifiable via `tx.input` prevouts being scanner-owned), or use per-purpose keys/offsets that are not publicly derivable, so an external payment cannot alias an internal flow. At minimum, `get_outputs` should not blanket-apply `presumed_origin`/`data` to all matched outputs in a tx and should sanity-check that internal-kind outputs appear only in transactions spending known internal inputs.

### Proof of Concept
1. Observe a Serai Bitcoin multisig key `K` (any prior deposit reveals it).
2. Locally compute `branch = K + G·hash_to_F(b"Serai Bitcoin Output Offset", b"branch")` and `p2tr_script_buf(branch)` — identical computation to `processor/src/networks/bitcoin.rs` `scanner()`.
3. Broadcast any transaction paying ≥ `DUST` (10,000 sat) to that script.
4. `Bitcoin::get_outputs` → `scanner.scan_transaction(tx)` returns the output; `kinds[offset]` resolves it to `OutputType::Branch`, `presumed_origin` is set to the attacker's input, and the output is emitted as a scanned protocol output indistinguishable from a genuine key-rotation branch output.

Note: severity and downstream exploitability depend on how `processor`'s scheduler/scanner consume `OutputType` (out of the audited scope); the in-scope defect is the unauthenticated, publicly derivable aliasing of internal-flow scripts in the shared `Scanner` map.
