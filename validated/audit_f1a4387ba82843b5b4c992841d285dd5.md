### Title
Disabled overfill clamp lets a manipulated venue price drain the Simplex filler's funds on intent fills - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The external report's core invariant is: a configured cap (`maxMembers`) exists in the data model, is documented as the enforcement boundary, but no code path actually clamps behavior to it — the check is decorative. The equivalent local pattern is the `fx.ts` overfill-protection ceiling: `maxOverfillBps` is documented and configured as a hard cap on how far the filler's computed output can exceed the user-requested amount, but the clamp that enforces it has been explicitly disabled, leaving the pricing engine to trust an unbounded, venue-derived rate.

### Finding Description
`fx.ts` computes a `policyMaxOutput` for each leg of an order and is supposed to bound it with `overfillCeiling = output.amount * (1 + maxOverfillBps) / 10000` before committing to fill it: [1](#0-0) 

The comment explicitly documents the regression: *"Overfill detection is warn-only: the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds (1 + maxOverfillBps) × user-requested — including venue-priced legs (e.g. Uniswap V4)."* Instead of clamping, `policyMaxOutput` is assigned directly from the unclamped `rawPolicyMaxOutput`, and any breach of the ceiling only produces a `logger.warn`: [2](#0-1) 

This value then flows straight into how much the filler actually pays out (`walletContribution`, `credited`, `finalOutputAmount`), with the only remaining check being whether the filler *has enough balance* to pay it — not whether the amount is fair: [3](#0-2) 

Per the docs, this overfill ceiling exists precisely to bound "per-leg loss if the filler's internal pricing is wrong (bug, stale cache, manipulated venue)," and for pairs with no configured price policy the leg is priced from a live Uniswap V4 venue quote: [4](#0-3) 

Because Uniswap V4 pool prices are attacker-observable and attacker-influenceable on-chain (e.g., via a flash-loan swap immediately before an intent is filled), and because the clamp that was designed to bound exactly this "manipulated venue" scenario is disabled, an unprivileged actor can distort the venue price so `rawPolicyMaxOutput` balloons far past the fair value, and the filler will pay the full unclamped (and unfair) amount rather than being capped at `(1 + maxOverfillBps) × output.amount`.

### Impact Explanation
This directly causes loss of solver/filler funds during intent settlement: the filler pays out more of the exotic/output token than the order economically justifies, with no on-chain or off-chain enforcement stopping it beyond a log line. Because the filler's wallet and vault-sourced liquidity (`fundingVenues`, ERC-4626 vault withdrawals) are drawn on to cover the inflated `policyMaxOutput`, a single manipulated fill can drain meaningfully more value than the legitimate order size, and the loss is realized irreversibly once `fillOrder` executes on-chain.

### Likelihood Explanation
The precondition is only a price-manipulable venue (Uniswap V4) feeding an unconfigured/reference-priced pair — no relayer, prover, or governance compromise is required. Any actor able to submit or trigger fills against a pair without a `bidPricePolicy`/`askPricePolicy` (venue-priced) can move the pool price around the fill and let the disabled clamp pass the inflated amount straight through, matching the "logic attack" / fund-loss criteria of the impact gate. The comment in the code confirms this is a known, intentional removal of a previously-existing safety bound rather than a latent theoretical gap.

### Recommendation
Re-enable the overfill clamp so `policyMaxOutput` is hard-bounded by `overfillCeiling` for every leg (not just warned about), especially for venue-priced (Uniswap V4) legs where price manipulation is most feasible. If a genuine business need exists to exceed the ceiling in exceptional cases, gate that override behind an explicit, audited operator decision rather than a silent default, and keep `maxConsecutiveClamps`-style circuit breakers wired to the actual clamped path so systemic mispricing still halts the strategy.

### Proof of Concept
1. Configure (or use an existing) `TradingPair` with no `bidPricePolicy`/`askPricePolicy`, so pricing falls through to the Uniswap V4 venue quote path referenced in `resolveLegRates`.
2. Before an order targeting that pair is filled, execute a large swap against the underlying Uniswap V4 pool to skew the observable price sharply in the attacker's favor (a flash loan makes capital cost negligible).
3. Submit/allow the intent order to be processed by the Simplex filler; `computeLegPolicyOutput` derives `rawPolicyMaxOutput` from the manipulated rate.
4. Observe that `overfillCeiling` is computed and compared (`rawPolicyMaxOutput > overfillCeiling`) but only logged — `policyMaxOutput = rawPolicyMaxOutput` is used unclamped for `walletContribution`/`credited`/`finalOutputAmount`, so the filler pays the manipulated, unclamped amount: [5](#0-4) 
5. Revert the pool price after the fill executes — the filler has already transferred the inflated output amount, realizing a loss with no on-chain recourse.

### Overfill Protection

Bounds per-leg loss if the filler's internal pricing is wrong (bug, stale cache, manipulated venue). For every order, the filler clamps its computed output to at most `(1 + maxOverfillBps) × user-requested amount` — this ceiling applies to every strategy. After `maxConsecutiveClamps` consecutive orders where the clamp activated, the **HyperFX** strategy halts itself — a pattern that strongly suggests a systemic pricing error — and requires an operator restart. HyperFX additionally rejects any order where the total output USD value ≥ total input USD value.

Defaults are sensible (`maxOverfillBps = 500` ≈ 5% ceiling, `maxConsecutiveClamps = 3`). Override under `[simplex.overfillProtection]`:
