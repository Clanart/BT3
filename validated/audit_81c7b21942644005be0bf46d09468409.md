### Title
CW20ERC20Pointer.approve() is subject to the classic ERC20 approve front-running/allowance-race condition, enabling unauthorized double-spend of pool/token allowance - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
The `CW20ERC20Pointer` contract, which is deployed to expose an ERC20-compatible interface for arbitrary CW20 tokens on Sei's EVM, implements `approve()` by reading the *current* on-chain allowance and issuing a CW20 `increase_allowance`/`decrease_allowance` message for the delta needed to reach the caller-specified target value. The net effect is functionally identical to a standard ERC20 `approve()` that unconditionally overwrites the allowance to the requested amount, and it is therefore exposed to the same well-known approve/allowance front-running race condition described in the referenced report: a spender can front-run an owner's allowance-reducing (or re-approving) transaction to consume the old allowance and still receive the full newly-approved amount, resulting in the spender controlling more tokens than the owner ever intended to expose at any one time.

### Finding Description
`approve()` in `CW20ERC20Pointer.sol` is: [1](#0-0) 

```
function approve(address spender, uint256 amount) public override returns (bool) {
    ...
    uint256 currentAllowance = allowance(msg.sender, spender);
    if (currentAllowance > amount) {
        ... decrease_allowance by (currentAllowance - amount)
    } else if (currentAllowance < amount) {
        ... increase_allowance by (amount - currentAllowance)
    }
    return true;
}
```

Whatever the state of the on-chain allowance is at the moment this transaction executes, the function computes a delta so that after execution `allowance(owner, spender) == amount` — i.e., it deterministically sets the allowance to the caller-supplied target, exactly like a standard ERC20 `approve()` overwrite. This reproduces the classic scenario from the report:

1. Owner has approved spender for `X`.
2. Owner decides to change the approval and submits `approve(spender, Y)`.
3. The malicious spender sees this pending transaction and front-runs it with `transferFrom(owner, ..., X)`, consuming the full existing allowance and transferring `X` worth of the underlying CW20 tokens to itself before the owner's transaction lands.
4. The owner's `approve(spender, Y)` transaction now executes when `currentAllowance == 0`, so the pointer issues `increase_allowance` by `Y`, setting the allowance to `Y`.
5. The spender has already extracted `X` (via the front-run) and now also controls a fresh allowance of `Y` — for a total of `X + Y`, exceeding what the owner intended to allow in total.

This is reachable by any unprivileged EVM transaction sender/CosmWasm token holder who deploys or uses a CW20↔ERC20 pointer, since pointer deployment and use is a permissionless production path (`deployErc20PointerForCw20` / `registerPointerForERC20` flows exist in the test suite, confirming pointer contracts are user-facing). [2](#0-1) 

### Impact Explanation
A malicious approved spender can extract more value than the owner ever intended to have outstanding at once, resulting in unauthorized transfer of CW20 token balances via the pointer's `transferFrom` path — a concrete loss of user funds for anyone who re-approves (including reducing/revoking) an untrusted spender on a CW20 ERC20 pointer contract, which is the standard/generally-recommended mitigation pattern users are told to follow when a spender becomes suspicious.

### Likelihood Explanation
Exploitation requires the attacker (the approved spender) to observe the pending `approve` transaction in the mempool and front-run it with a `transferFrom` call before it lands — a realistic and low-cost condition on any chain with public mempools, and the classic reason this bug class is normally called out during audits of `approve`-based allowance systems.

### Recommendation
Do not implement `approve()` as a delta-based overwrite of the full target amount. Instead, expose explicit `increaseAllowance(spender, addedValue)` and `decreaseAllowance(spender, subtractedValue)` functions (as OpenZeppelin recommends) that operate relative to the current allowance, and document/encourage their use instead of `approve()` for adjusting an existing non-zero allowance, or require the allowance to be set to zero before it can be changed to a new non-zero value.

### Proof of Concept
1. Owner calls `pointer.approve(spender, X)` — allowance becomes `X`.
2. Owner decides to reduce trust in spender and submits `pointer.approve(spender, Y)` with `Y < X` (or `Y = 0`) to protect remaining funds.
3. Spender monitors mempool, and before the owner's transaction is mined, submits `pointer.transferFrom(owner, spender, X)`, which succeeds since the allowance is still `X`; CW20 tokens worth `X` move to spender.
4. Owner's `approve(spender, Y)` executes afterward; `currentAllowance` is now `0`, so the code issues `increase_allowance` for `Y`, leaving spender with an active allowance of `Y`.
5. Net result: spender has captured `X` (already transferred) and can additionally spend up to `Y` in the future — total exposure `X + Y`, more than the owner intended when submitting the reducing/re-approval transaction.

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
