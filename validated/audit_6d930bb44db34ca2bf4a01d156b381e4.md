### Title
`SignableTransaction::new()` panics or produces a consensus-invalid transaction when `payment_sat + needed_fee` overflows u64, instead of rejecting with `NotEnoughFunds` - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Kirstentat/serai--016))

### Summary
The audit hint is an unchecked `base - discount` subtraction that reverts on underflow when it should clamp/error gracefully. The Serai analog is the unchecked `payment_sat + needed_fee` sum inside the fund-sufficiency check in `SignableTransaction::new`. The payment amounts are `u64` values derived from externally ordered payments (burn events initiated by unprivileged users). When `payment_sat + needed_fee` exceeds `u64::MAX`, the code either panics (overflow-checks on) or wraps (overflow-checks off), never returning the intended `TransactionError::NotEnoughFunds`.

### Finding Description
`SignableTransaction::new` computes `payment_sat` as an unchecked `sum::<u64>()` over the caller-supplied payment amounts (`send.rs:187`) and then performs the solvency check with a plain `u64` addition:

```rust
// networks/bitcoin/src/wallet/send.rs
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();        // L187
let mut needed_fee = fee_per_vbyte * vbytes;                                     // L206
if input_sat < (payment_sat + needed_fee) {                                      // L215
  Err(TransactionError::NotEnoughFunds { ... })?;
}
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) { ... } // L228
```

Each `payment.1` is only checked against `DUST` (L165-169); there is no upper bound. The same unchecked `payment_sat + fee_with_change` is used inside `checked_sub` at L228. If `payment_sat + fee_with_change` wraps, `checked_sub` succeeds and a change output is emitted, producing a transaction whose outputs vastly exceed its inputs.

Consequences:
- Overflow-checks enabled: the `+` panics, aborting plan construction — the same "reverts when it should work" shape as the Buffer finding (a DoS on the signing pipeline rather than a clean `NotEnoughFunds` error).
- Overflow-checks disabled: the sum wraps to a small value, `input_sat < wrapped` is false so `NotEnoughFunds` is bypassed, and the change branch computes `input_sat - wrapped_value`, appending a near-`input_sat` change output. The resulting `SignableTransaction` is passed to `TransactionSignMachine::sign`, which commits the validators' FROST signatures via `taproot_key_spend_signature_hash` over `Prevouts::All` (send.rs:373-391) — i.e. the threshold group signs a transaction that is consensus-invalid (outputs exceed inputs) and can never confirm, while `fee()` (send.rs:138-141) additionally underflows/panics when inspected since `sum(outputs) > sum(inputs)`.

### Impact Explanation
A single unprivileged burn of an amount near `u64::MAX` (the coin denomination is `u64` and `DUST` is the only lower bound enforced; no upper bound exists on `payment.1`) can either crash the processor's transaction-construction path — stalling all payouts for that validator set — or cause the threshold group to produce a fully-signed, consensus-invalid Bitcoin transaction. In the latter case the funds are committed to a plan whose only possible completion is unbroadcastable, leaving inputs locked until out-of-band remediation. This is reachable purely through public input data (the payment amount), matching the report's "admin-parameter combination reverts a legitimate operation" bug class mapped to Serai's external-payment flow.

### Likelihood Explanation
Likelihood depends on whether the deployed denomination allows a payment value large enough that `payment_sat + needed_fee` exceeds `u64::MAX` (~1.8e19). For coins with high decimal precision (the code uses `u64` base units), a single attacker-controlled burn of a very large nominal amount is sufficient — no collusion, no malicious validator, and no special state is required. Medium: requires an extreme-but-permitted payment amount and the consequence is DoS / stuck funds rather than direct theft.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:

```rust
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: u64::MAX, fee: needed_fee })?;
let total = payment_sat.checked_add(needed_fee)
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: payment_sat, fee: needed_fee })?;
if input_sat < total { Err(TransactionError::NotEnoughFunds { ... })?; }
// and the same for `payment_sat + fee_with_change` before checked_sub
```

`fee()` should likewise use `checked_sub` and surface an error instead of panicking.
