### Title
Distribution precompile `rewards()` reports a hardcoded 18-decimal precision for every reward denom regardless of the denom's actual decimals - ([File: precompiles/distribution/distribution.go])

### Summary
The `rewards()` view method of the distribution precompile (address `0x1007`) builds its `Coin` response objects with a hardcoded `Decimals: big.NewInt(sdk.Precision)` (i.e. `18`) for every reward coin, regardless of what denom the reward actually is in. This mirrors the reported wagmi-leverage bug class of applying one fixed decimal-precision constant to "each token type without actually checking how many decimal points the token has."

### Finding Description
`getResponseOutput` in the distribution precompile constructs the `Coin` entries returned by `rewards()` by copying `coin.Denom` and `coin.Amount` directly from the Cosmos SDK `QueryDelegationTotalRewardsResponse`, but sets every coin's `Decimals` field to the constant `sdk.Precision`, which is statically defined as `18` in `sei-cosmos/types/decimal.go`: [1](#0-0) [2](#0-1) 

This same pattern is duplicated verbatim across every legacy precompile version directory (`v65`, `v66`, `v67`, `v580`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`), confirming it is not a one-off typo but the consistently shipped behavior of this precompile: [3](#0-2) 

`sdk.Precision = 18` is the internal fixed-point precision used by the SDK's `Dec` type for *ratio/rate* math (e.g. commission rates, exchange rates) — it has no relationship to the actual base-denomination decimal exponent of the reward coin's denom (e.g. `usei` has 6 decimals, IBC-vouchers and tokenfactory denoms can have arbitrary decimal metadata, as seen elsewhere in the codebase where the native-pointer precompile explicitly reads the real exponent from `bankKeeper.GetDenomMetaData`): [4](#0-3) 

The distribution precompile never looks up denom metadata for the reward coins and instead blindly stamps `18` onto every entry, exactly analogous to the wagmi issue where `COLLATERAL_BALANCE_PRECISION = 1e18` was applied to every token type without checking its actual decimals.

### Impact Explanation
`rewards()` is a public view function reachable by any EVM caller (including other smart contracts) through the distribution precompile at `0x0000000000000000000000000000000000001007`. If a downstream consuming contract (e.g. a yield aggregator, dashboard, or auto-compounder built on top of this precompile) trusts the returned `Decimals` field to convert the raw `Amount` into a human/token-normalized value, it will systematically misinterpret amounts for any reward denom whose actual decimals differ from 18 (which is the common case — `usei` uses 6 decimals). This can lead to gross over- or under-estimation of reward value by many orders of magnitude in any contract logic that performs `amount / 10**decimals` using this field, potentially causing fund-management decisions (e.g. swap sizing, liquidation thresholds, minting pegged wrapped rewards) to be wrong by up to 10^12x for a 6-decimal denom being read as 18-decimal.

### Likelihood Explanation
Likelihood is high for exposure (every call to `rewards()` returns this incorrect metadata; no special conditions or privileges are needed — any address can call this view function), but the finalized impact severity depends entirely on whether any consuming contract actually trusts and uses the `Decimals` field for financial calculations rather than treating it as informational. This function only returns *data* — it does not itself move funds — so the concrete "fund loss" impact is conditional on client contracts.

### Recommendation
Populate `Coin.Decimals` from the actual denom metadata (via `bankKeeper.GetDenomMetaData`, following the same pattern already used in the native ERC20 pointer precompile) instead of hardcoding `sdk.Precision`. If metadata is unavailable, either omit the field, document that it is a display placeholder rather than an authoritative decimals field, or default in a way that doesn't imply "18 decimals, safe to scale."

### Proof of Concept
1. Register a tokenfactory or native denom with 6 (or other non-18) decimal metadata, e.g. `usei`.
2. Have a validator distribute rewards in this denom to a delegator.
3. Call the distribution precompile's `rewards(delegatorAddress)` view function from any EVM account or contract: [5](#0-4) 
4. Observe the returned `Coin.Decimals` is `18` for the `usei`-denominated reward, even though `usei` actually uses 6 decimal places on-chain.
5. Any downstream contract that computes `humanAmount = amount / 10**decimals` using this precompile's output will compute a value that is `10^12` times smaller than the true reward, corrupting any financial logic built on top of it.

func getResponseOutput(response *distrtypes.QueryDelegationTotalRewardsResponse) Rewards {
	rewards := make([]Reward, 0, len(response.Rewards))
	for _, rewardInfo := range response.Rewards {
		coins := make([]Coin, 0, len(rewardInfo.Reward))
		for _, coin := range rewardInfo.Reward {
			coins = append(coins, Coin{
				Amount:   coin.Amount.BigInt(),
				Denom:    coin.Denom,
				Decimals: big.NewInt(sdk.Precision),
			})
		}
		rewards = append(rewards, Reward{
			ValidatorAddress: rewardInfo.ValidatorAddress,
			Coins:            coins,
		})
	}

	totalCoins := make([]Coin, 0, len(response.Total))
	for _, coin := range response.Total {
		totalCoins = append(totalCoins, Coin{
			Amount:   coin.Amount.BigInt(),
			Denom:    coin.Denom,
			Decimals: big.NewInt(sdk.Precision),
		})
	}

	return Rewards{
		Rewards: rewards,
		Total:   totalCoins,
	}
}
