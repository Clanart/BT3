### Title
Untrusted `ReceivedOutput` bytes let internal value accounting diverge from the actual UTXO, producing signatures over fictitious prevout amounts - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an `(offset, TxOut, OutPoint)` triple from untrusted bytes with no consistency or authenticity check. Downstream, `SignableTransaction::new` treats `input.output.value` as ground truth for balance/fee/change accounting, and `TransactionSignMachine::sign` commits to the claimed `TxOut`s verbatim via `Prevouts::All`. This mirrors the M-07 class: an internally tracked amount that is never reconciled with the actual on-chain object it claims to represent. [1](#0-0) 

### Finding Description
`ReceivedOutput::read` reads `offset` via `Secp256k1::read_F`, then consensus-decodes a `TxOut` and an `OutPoint` from the same byte stream, returning them as a coherent unit. [1](#0-0)  None of the three fields are validated against each other or against the chain:

- The `TxOut`'s `script_pubkey` is only later checked in `SignableTransaction::multisig`, where `p2tr_script_buf(offset.group_key())` is compared to `prevouts[i].script_pubkey`. [2](#0-1) 
- The `TxOut`'s `value` and the `OutPoint` are never verified at all. The `OutPoint` need not reference a real UTXO, and the claimed `value` need not match the value locked in the real outpoint.

`SignableTransaction::new` then computes `input_sat` — the protocol's internal accounting of available funds — by summing these attacker-supplied `output.value` fields, and uses it for the `NotEnoughFunds` solvency check and for sizing the change output (`input_sat - payment_sat - fee_with_change`). [3](#0-2) [4](#0-3) 

Finally, `sign` hashes every claimed prevout into the BIP-341 sighash via `Prevouts::All(&self.tx.prevouts)`, so the threshold signature commits to the fabricated amounts. [5](#0-4) 

This is exactly the M-07 shape: an internal ledger (`prevouts`/`input_sat`) updated from a self-reported figure and never re-queried against the real object — analogous to `staked_amounts` being incremented without calling `get_real_total_stakes`.

### Impact Explanation
The divergence produces a signed transaction the network will reject in two distinct ways:

1. **Inflated claimed value**: `input_sat` passes the `NotEnoughFunds` check and may produce a change output funded by value that does not exist. The sighash commits to the inflated prevout amount, so the resulting Schnorr signature is invalid under BIP-341 verification — the funds accounting reports solvency and change that are not real.
2. **Nonexistent or mismatched outpoint**: the transaction spends a UTXO that does not exist, so it is unspendable regardless of signature validity.

In both cases outputs are reported as received/spendable by the Serai-side accounting (the `ReceivedOutput` was accepted, planned, and signed) while they are not actually spendable on chain — the "funds reported received that are not spendable" impact class, and a signing round is consumed producing a transaction of an unintended (invalid) form.

### Likelihood Explanation
Reachable by an unprivileged party able to feed bytes to `ReceivedOutput::read` (explicitly in scope). No collusion, malicious validator, or leaked key is required — only a crafted serialization where `output.value`/`outpoint` do not correspond to a real UTXO. `multisig()` only narrows the attack by enforcing `script_pubkey` consistency; an attacker can satisfy that by copying the real script for the registered offset while arbitrarily choosing `value` and `outpoint`.

### Recommendation
Treat `ReceivedOutput` as a claim, not a fact:

- Re-verify each `ReceivedOutput` against the chain (or at minimum against the scanner that produced it) before it enters `SignableTransaction::new` — the analog of calling `pool_router::get_real_total_stakes` after compounding.
- Extend the `multisig()` consistency check beyond `script_pubkey`: confirm `outpoint` resolves to a live UTXO whose `value` and `script_pubkey` equal the stored `output`, e.g. via an `rpc.rs`/`get_output`-style lookup, or bind `outpoint` + `value` + `offset` together at read time with an authenticated encoding so `ReceivedOutput::read` cannot splice fields from different outputs.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read:
//   offset: a registered offset `o` (even tweaked key)
//   TxOut:  { value: 1_000_000_000, script_pubkey: p2tr_script_buf(key + G*o) }  // real script, fake value
//   OutPoint: an outpoint that does not exist, or a real low-value UTXO to that script
let ro = ReceivedOutput::read(&mut &attacker_bytes[..])?;

// Internal accounting credits 1 BTC regardless of the real UTXO:
let stx = SignableTransaction::new(
  vec![ro],
  &[(payment_script, 500_000_000)],
  Some(change_script),
  None,
  fee_per_vbyte,
)?; // passes NotEnoughFunds; change sized from phantom balance

// The FROST round signs Prevouts::All(&[claimed TxOut]); the signature commits to the
// fabricated 1 BTC amount, so the completed transaction is invalid/unsSpendable —
// internal accounting diverged from chain state exactly as in M-07.
```

Residual uncertainty: the accept/reject boundary here depends on whether downstream consumers treat deserialized `ReceivedOutput`s as trusted scanner output; the code path itself performs no validation, so within the stated input model the desync is reachable.
