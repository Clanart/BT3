Based on my investigation, I found a real analog: `addRemote()` in `app/src/lib/git/remote.ts` is invoked with a GitHub API–controlled URL without the "end of options" (`--`) protection that the sibling `clone()` function in `app/src/lib/git/clone.ts` deliberately applies. This is a missing-guard-on-a-trusted-adjacent-path issue, structurally the same class of bug as the `VaultStrat` report (an operation that should be constrained the same way as its sibling operation is left unguarded, letting attacker-controlled data corrupt internal state).

### Title
Argument injection into `git remote add` via attacker-controlled Pull Request `clone_url` - (File: app/src/lib/git/remote.ts)

### Summary
`addRemote()` builds the git command line as `['remote', 'add', name, url]` and passes it directly to `git()` with no `--` end-of-options marker, unlike `clone()` in the same directory which explicitly does `args.push('--', url, path)` for this exact reason. The `url` value that reaches `addRemote()` when checking out a pull request comes straight from the GitHub API response (`pullRequest.head.repo.clone_url`), i.e., a value fully controlled by whoever owns the fork the PR was opened from.

Compare with `clone()` in `app/src/lib/git/clone.ts`, which treats the exact same kind of value (a remote URL) as untrusted and defensively terminates option parsing before passing it to git: [2](#0-1) 

The attacker-controlled value flows into `addRemote()` through `_findPullRequestBranch`, called from `_checkoutPullRequest`, using `headCloneUrl` taken straight from the GitHub Pull Request API object: [3](#0-2) [4](#0-3) 

This `headCloneUrl`/`headRepoOwner` pair originates from `pullRequest.head.repo.clone_url` and `pullRequest.head.repo.owner.login` — fields of a `IAPIPullRequest` fetched from the GitHub API for a fork the attacker controls (they own the forked repo the PR was created from). No validation is performed that `clone_url` looks like a well-formed `https://`/`ssh://`/`git@` URL before it is placed as the final CLI argument to `git remote add`.

Because git's `remote add` subcommand recognizes option flags such as `--mirror=fetch` / `--mirror=push` / `-f` / `--tags`, and git's own argument parser permutes options regardless of position, a `clone_url` value that begins with `-` is not guaranteed to be treated as an opaque positional URL. This is the identical class of vulnerability that `clone()` was hardened against with an explicit `--` separator; `addRemote()` was not given the same treatment, so it is the exact unguarded sibling.

### Impact Explanation
An attacker who creates a public fork and opens a pull request against a victim's tracked repository controls the `clone_url` field returned by GitHub's API for that PR's `head.repo`. If GitHub Desktop's PR-checkout flow is invoked (e.g., by the victim clicking "Checkout this PR" or the "Open in Desktop" deep link for a PR), Desktop calls `addRemote()` with the attacker's `clone_url` unsanitized. A crafted value such as `--mirror=fetch` can alter how the newly-added remote is configured, causing subsequent fetches against that "fork" remote to silently rewrite the victim's local refs/remote-tracking state in ways the user did not intend — matching the explicitly valid impact category "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Medium. Exploitation requires only that a victim check out a pull request originating from an attacker-controlled fork (a normal, expected, unprompted Desktop workflow — no unnatural user steps, no local/admin access, and no credential leakage needed). The severity is bounded by which `remote add` options are actually reachable via a single positional argument (only options with inline `=` values, like `--mirror=fetch`, are viable since `name`/`url` are each a single argv element), so full arbitrary command execution is not established from local evidence, but option/argument injection into the remote's configuration is directly supported by the code path.

### Recommendation
Apply the same defense used in `clone()` to `addRemote()` (and any other git subcommand builder that appends a raw, externally-sourced URL): insert `--` immediately before the URL/positional arguments, e.g. `['remote', 'add', '--', name, url]`, and/or reject `clone_url`/`ssh_url` values from the GitHub API that do not parse as valid URLs (mirroring `parseRemote()`/`remote-parsing.ts` validation) before they reach `git()`.

### Proof of Concept
1. Attacker forks the victim's GitHub repository and opens a pull request from the fork.
2. Attacker's fork's `clone_url`, as returned by the GitHub API for that PR's `head.repo`, is set/manipulated (e.g., via a GitHub Enterprise instance the attacker controls, or by any path that lets the reported clone URL diverge from a normal `https://…`/`git@…` value) to `--mirror=fetch`.
3. Victim opens the PR in Desktop (`app/src/ui/dispatcher/dispatcher.ts` `openPullRequestFromUrl` / `checkoutPullRequest`), which calls `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)`.
4. `addRemote()` executes `git remote add github-desktop-<owner> --mirror=fetch` with no `--` separator, letting git interpret the attacker-supplied value as an option rather than a URL, silently altering the remote's fetch/mirror behavior instead of failing safely as `clone()` would.
