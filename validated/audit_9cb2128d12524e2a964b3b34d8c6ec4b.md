### Title
Integer overflow in payment/fee summation defeats the `NotEnoughFunds` check and causes the multisig to sign an invalid transaction — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` sums attacker-influenced `u64` payment amounts and computes `fee_per_vbyte * vbytes` and `payment_sat + needed_fee` using unchecked `*`, `+`, and `.sum()` arithmetic. The bug class mirrors CVE-2023-52389: a numeric quantity derived from untrusted input overflows and wraps, and the wrapped value is then used in a bounds/fund-sufficiency check, defeating it. When `payment_sat` (or `payment_sat + needed_fee`) wraps past `u64::MAX`, the guard `input_sat < (payment_sat + needed_fee)` spuriously passes, and the construction proceeds to emit `TxOut`s whose declared values exceed the total value of the inputs. The FROST `TransactionMachine` then signs sighashes for that malformed transaction, producing a threshold signature for a message that should have been rejected.

### Finding Description
In `SignableTransaction::new`:

```rust
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();        // line 187
...
let mut needed_fee = fee_per_vbyte * vbytes;                                    // line 206
...
if input_sat < (payment_sat + needed_fee) {                                     // line 215
  Err(TransactionError::NotEnoughFunds { .. })?;
}
```

- `payment_sat` is a `u64` sum over an arbitrary-length `payments` slice. Two entries of `~1.8e19` sats each overflow the sum back to a small number. `Amount::from_sat` does not enforce Bitcoin's 21M `MAX_MONEY` bound, so oversized `TxOut` values are constructed without error (line 190).
- `fee_per_vbyte * vbytes` (line 206) and `fee_per_vbyte * vbytes_with_change` (line 227) can also overflow for a large `fee_per_vbyte`, causing `needed_fee` to wrap to ~0 and bypass both the `TooLowFee` and `NotEnoughFunds` checks.
- The change computation does use `checked_sub` (line 228), but it subtracts the *already-wrapped* `payment_sat + fee_with_change`, so it returns `Some(large_value)` and pushes a change `TxOut` worth far more than the inputs actually contain (line 230).

The resulting `SignableTransaction` flows into `multisig` → `TransactionMachine` → `TransactionSignMachine::sign`, which calls `cache.taproot_key_spend_signature_hash` and has every participant produce a FROST share over the sighash of the malformed transaction (lines 373–397). There is no later re-validation that output totals are sane before signing.

### Impact Explanation
The threshold validators produce a valid BIP-340 signature committing to a transaction that (a) should have been rejected by `NotEnoughFunds`/`TooLowFee`, and (b) cannot be accepted by the Bitcoin network because its outputs exceed its inputs / money supply rules. This is concrete signing of an unintended message: the signing set's preprocesses and nonces are consumed on a malformed plan, and the emitted signature attests to a transaction the policy checks were meant to forbid. In debug builds the same overflow panics, aborting the signing attempt; in release builds it silently wraps and signs.

### Likelihood Explanation
Reachability requires the `payments` slice (or `fee_per_vbyte`) reaching `SignableTransaction::new` to carry values whose sum exceeds `u64::MAX`. These values originate in plan/out-instruction data committed to by the coordinator rather than from validated on-chain BTC amounts — the function itself only enforces a per-payment dust floor (`*amount < DUST`, line 166) and never bounds the count or the aggregate, so nothing upstream in this crate prevents an adversarial plan from containing a handful of astronomically large payment entries. No threshold collusion or key compromise is required; a single crafted plan reaching the signing path suffices.

### Recommendation
Use checked/saturating arithmetic throughout `SignableTransaction::new`:

- `payment_sat`: accumulate with `checked_add`, erroring via a new `TransactionError` variant on overflow.
- `needed_fee` / `fee_with_change`: use `fee_per_vbyte.checked_mul(vbytes)` and error on overflow.
- The `NotEnoughFunds` comparison: use `payment_sat.checked_add(needed_fee)` before comparing to `input_sat`.
- Additionally bound each payment to `bitcoin::Amount::MAX_MONEY` sats and cap `payments.len()`.
