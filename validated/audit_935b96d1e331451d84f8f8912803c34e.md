### Title
Missing sanity check on `kip71.gastarget` governance parameter causes division-by-zero panic in Magma base fee calculation - ([File: params/kip71_config.go])

### Summary
The `Kip71GasTarget` governance parameter (`kip71.gastarget`) is validated only with a `noopFormatChecker`, meaning any `uint64` value including `0` can be accepted through the governance mechanism. This value is later used unguarded as a divisor in `NextMagmaBlockBaseFee()`, which computes the block's base fee under KIP-71/Magma rules. If `GasTarget` is set to `0`, the function performs a `big.Int` division by zero, which panics in Go, crashing any node that processes/verifies a block header at that point — this exactly mirrors the reported CORGI bug class of "missing sanity check on a value used as a divisor, leading to division-by-zero."

### Finding Description
`Kip71GasTarget` is registered with no bound/nonzero enforcement: [1](#0-0) 

Compare this to `Kip71BaseFeeDenominator`, which is also declared with `noopFormatChecker`, but the *consuming* code in `NextMagmaBlockBaseFee()` explicitly guards against a zero value by falling back to `64`: [2](#0-1) 

However, `GasTarget` receives no equivalent protection. It is used directly as a `big.Int` divisor in both the "gas used above target" and "gas used below target" branches: [3](#0-2) [4](#0-3) 

If `kip71.gastarget` is `0`:
- `parentGasUsed == gasTarget` is only true when `parentGasUsed == 0`; for any block with `gasUsed > 0`, the code enters the `parentGasUsed > gasTarget` branch.
- `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by a zero-valued `*big.Int`, which panics (`math/big` package panics on division by zero) rather than returning an error.

This function is invoked from block validation/production paths (`blockchain/block_validator.go`, `work/worker.go`, `blockchain/chain_makers.go`, `blockchain/tx_pool.go`, and gas price estimation in `node/cn/gasprice`), so a zero `GasTarget` would panic every node computing or verifying the base fee for the next block — an unrecoverable consensus-halting condition rather than a graceful rejection.

The governance parameter is set/changed through header-vote or contract-vote governance mechanisms (`kaiax/gov`), which is one of the explicitly in-scope reachable paths (governance parameters). Unlike `RewardRatio`/`RewardKip82Ratio`, which have hand-rolled validation enforcing sums equal 100 and non-negativity ( [5](#0-4) ), and unlike `BaseFeeDenominator`, which has a defensive zero-fallback in the consumer, `GasTarget` has neither producer-side validation nor consumer-side protection.

### Impact Explanation
A single governance vote setting `kip71.gastarget = 0` causes every full/validator node computing `NextMagmaBlockBaseFee` for the next block (during block assembly, block validation, or `eth_feeHistory`/gas price estimation) to panic. This is a chain-halting, denial-of-service condition affecting the entire network's block production and validation pipeline, not merely a single transaction — a severe, systemic impact analogous to (and worse than) the referenced CORGI division-by-zero bug, since it can stop the chain rather than just revert a single transfer.

### Likelihood Explanation
The parameter is only settable through the governance module (governing node / contract governance), so exploitation requires governance-level access rather than an arbitrary unprivileged transaction. This restricts likelihood compared to a fully permissionless bug, but it remains a valid "governance parameters" reachable path per scope, and the lack of any format check (compared to siblings like `IstanbulCommitteeSize` which enforces `v > 0`, see [6](#0-5) ) shows this is an overlooked, easily triggered oversight rather than a defense-in-depth gap.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71BaseFeeDenominator`) requiring the value to be strictly greater than zero, consistent with `IstanbulCommitteeSize`'s pattern:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v > 0
    },
    ...
}
```
Additionally, as defense-in-depth, `NextMagmaBlockBaseFee()` in `params/kip71_config.go` should guard against a zero `GasTarget` the same way it already guards `BaseFeeDenominator`, to avoid a panic even if an invalid value slips through via chain-config or legacy data.

### Proof of Concept
1. Governance sets `kip71.gastarget = 0` (via header-vote governance, reachable pre-Kore, or contract governance post-Kore).
2. At the next block after activation, any node calls `KIP71Config.NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)` with `parentGasUsed > 0`.
3. Execution reaches:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // gasTarget=0 → parentGasUsed
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // Div by big.Int(0) → panic
```
4. The node panics ("division by zero" from `math/big`), consistent with the reported bug class in `params/kip71_config.go:100-102` and `params/kip71_config.go:120-121`. [7](#0-6) [8](#0-7)
