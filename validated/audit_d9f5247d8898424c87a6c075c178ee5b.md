### Title
Unicode Bidirectional Override Characters in Branch/Issue Names Are Spliced Verbatim into Commit Message Text, Corrupting Visual vs. Actual Content - (File: app/src/ui/autocompletion/autocompleting-text-input.tsx)

### Summary
`insertCompletion` in `AutocompletingTextInput` takes the raw string returned by an autocompletion provider's `getCompletionText` and concatenates it directly into the textarea/input's `.value` with no sanitization of Unicode control characters such as `U+202E` (RIGHT-TO-LEFT OVERRIDE), `U+202D`, or other bidi/format characters.

### Finding Description
`insertCompletion` builds the new field value by string concatenation of untrusted text: [1](#0-0) 

The inserted text originates from `autocompletionState.provider.getCompletionText(item)`. For the branch provider, this is the raw git branch name with no filtering: [2](#0-1) 

For the issues provider it's built from the issue number only (`#${item.number}`), so that path is not exploitable this way, but the branch name path is: [3](#0-2) 

Git branch names are attacker-controllable in a cloned/fetched repository (an attacker who controls a remote can create branches with arbitrary Unicode names, since git branch refs accept most Unicode characters, including bidi control characters, as long as they aren't null bytes or a few reserved ASCII characters). When a user types `feature/` or similar in the commit summary/description box and the autocomplete list offers such a branch, selecting it (`onRowMouseDown` → `insertCompletion`, or Tab/Enter → `insertCompletion`) writes the branch name — including any embedded `U+202E`/`U+202D`/`U+2066`-`U+2069` bidi override characters — verbatim into `element.value`, which then becomes the actual commit summary/description content via `onValueChanged`.

I searched for any existing sanitization of bidi/invisible characters applied to this input path (`sanitize-ref-name.ts`, `ref-name-text-box.tsx`, `sanitized-repository-name.ts`) and none of them are wired into `AutocompletingTextInput.insertCompletion` or `BranchAutocompletionProvider.getCompletionText`; those sanitizers exist for different flows (creating/renaming refs, repository path/name fields), not for text inserted into the commit message via autocompletion. The codebase does show some existing awareness of bidi-related rendering issues in `diff-contents-warning.tsx`, but that mitigation is scoped to diff rendering, not to the commit message autocomplete-insertion path.

### Impact Explanation
If exploited, the actual byte content committed (e.g., `git commit -m`) would contain literal bidi override control characters that most terminals/UIs render right-to-left, while GitHub Desktop's own textarea would visually reorder/hide characters — the classic "Trojan Source"-style visual spoofing. This falls under "silent corruption of what the user commits or pushes," an explicitly listed valid impact category, because the user could be tricked into publishing a commit message whose visible text differs from its actual stored bytes (e.g., hiding or reordering words), without the user intending it or the app warning them.

### Likelihood Explanation
Exploitation requires: (1) an attacker-controlled repository/remote containing a branch (or any other autocompletion source using raw untrusted text as `getCompletionText`) with an RLO/bidi character embedded in its name, and (2) the victim opening the commit box, typing a prefix that matches, and selecting that suggestion via mouse click or Tab/Enter. This is a plausible but non-trivial "natural" user flow — it doesn't require unusual steps beyond typing a partial branch name and picking from the autocomplete popup, which is a very ordinary Desktop workflow. Since GitHub itself and other tools generally do not block bidi characters in ref names, an attacker can realistically craft such a branch name in a shared/forked repository ahead of a victim cloning/fetching it.

### Recommendation
Sanitize/strip (or visually flag) Unicode bidirectional control characters (`U+202A`–`U+202E`, `U+2066`–`U+2069`, and other format characters) from text returned by `getCompletionText` implementations (at minimum `BranchAutocompletionProvider`) before it is spliced into `newText` in `insertCompletion`, or perform the stripping centrally in `insertCompletion` itself before assigning `element.value`. Additionally, consider warning the user (similar to the existing bidi-related warning already present for diffs) when inserted autocomplete text contains such control characters.

### Proof of Concept
1. Create a repository with a branch named `feature-\u202Etxt.exe\u202C` (embedding U+202E RLO / U+202C PDF), and have the victim fetch/clone it so `allBranches` includes this name.
2. In GitHub Desktop, open the commit summary box and type a prefix that matches (e.g., `feature-`).
3. Select the malicious branch entry from the autocomplete popup (mouse click or Tab/Enter), triggering `insertCompletion`.
4. Compare `element.value` (actual string, e.g. via `element.value.length` / char codes) against what is visually rendered in the textarea — the rendered text will appear reordered (e.g., appearing as `feature-exe.txt`) while the actual value/commit message bytes contain the original character sequence with the RLO override, demonstrating the visual-vs-actual mismatch that would be published in the commit.

```typescript
  private insertCompletion(
    item: AutocompleteItemType,
    source: 'mouseclick' | 'keyboard'
  ) {
    const element = this.element!
    const autocompletionState = this.state.autocompletionState!
    const originalText = element.value
    const range = autocompletionState.range
    const autoCompleteText =
      autocompletionState.provider.getCompletionText(item)

    const textWithAutoCompleteText =
      originalText.substr(0, range.start - 1) +
      autoCompleteText +
      (this.props.completionSuffix ?? ' ')

    const newText =
      textWithAutoCompleteText +
      originalText.substring(range.start + range.length)

    element.value = newText
```
