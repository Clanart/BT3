### Title
Stop-hook activates indefinite prompt-injection loop from a pre-seeded state file without checking `active: true` - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
`stop-hook.sh` treats the mere existence of `.claude/ralph-loop.local.md` as proof that a Ralph loop is active and never verifies the `active: true` field that `setup-ralph-loop.sh` writes when `/ralph-loop` is actually invoked. Any repository content (e.g., a file committed to a repo, or a malicious PR merged into it) that contains a pre-crafted `.claude/ralph-loop.local.md` will cause every `Stop` event in the victim's session to be intercepted and answered with attacker-controlled prompt text, with no `/ralph-loop` command ever run by the victim.

### Finding Description
The hook's only activation gate is a file-existence test: [1](#0-0) 
It then parses `iteration`, `max_iterations`, and `completion_promise` from frontmatter via simple `grep`/`sed`, but at no point does it read or validate an `active` field: [2](#0-1) 
By contrast, the legitimate creation path in `setup-ralph-loop.sh` (invoked only by the `/ralph-loop` slash command) writes `active: true` into the frontmatter as documented intent, but nothing in `stop-hook.sh` ever consumes that field: [3](#0-2) 
Since the plugin registers `stop-hook.sh` unconditionally for every `Stop` event (once the ralph-wiggum plugin is enabled) with no separate opt-in check, any checked-in `.claude/ralph-loop.local.md` — supplied via cloning a crafted repo, checking out a malicious branch/PR, or an attacker landing the file in a shared repository — is sufficient to trigger the loop: [4](#0-3) 
Once triggered, the hook validates only that `iteration`/`max_iterations` are numeric and extracts the markdown body as `PROMPT_TEXT`, then returns `{"decision":"block","reason":$prompt,...}`, feeding that attacker-controlled body straight back into the model on every attempted Stop: [5](#0-4) 
If `max_iterations` is `0` (the default used by `setup-ralph-loop.sh` when unset) and no `completion_promise` matches, the loop runs indefinitely, as the script itself documents ("Ralph runs infinitely by default!").

### Impact Explanation
This is a consent/scoping bypass: the plugin's design intent is that Ralph loops are only "active" after an explicit `/ralph-loop` invocation (which writes `active: true` and prints prominent warnings to the user), but the enforcement code never checks that flag. An attacker who can place a file into a repository the victim clones/checks out — a normal, unprivileged content-supply path (malicious PR content, a poisoned branch, a shared workspace) — can force the victim's every Stop attempt to be blocked and their next-turn input to be silently replaced with attacker-chosen prompt text (`PROMPT_TEXT`/`reason`), indefinitely if `max_iterations` is 0 or absent. This matches denial-of-exit and prompt-injection impact classes: unauthorized control-flow interception of the session and injection of attacker text into the model's context without the user ever running the enabling command.

### Likelihood Explanation
Highly feasible: the only precondition is that the victim has the ralph-wiggum plugin enabled (a normal state for users of this plugin) and clones/checks out repository content containing the crafted `.claude/ralph-loop.local.md`. No `active` field, signature, session-binding, or provenance check exists to distinguish an attacker-planted file from one created by the legitimate `/ralph-loop` command, so exploitation is deterministic and repeatable on every `Stop` event until removed.

### Recommendation
In `stop-hook.sh`, after parsing the frontmatter, explicitly require and validate an `active: true` field (or equivalent session-bound token minted only by `setup-ralph-loop.sh`, e.g., tied to the current session ID) before treating the file as an active loop; treat missing/false `active` the same as a missing file (`exit 0`, optionally warning that a stale/foreign state file was ignored). Additionally consider scoping the state file to the session (e.g., embedding and verifying `session_id` from `HOOK_INPUT` against the file) so a checked-in file from version control cannot be reused across arbitrary sessions.
