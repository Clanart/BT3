### Title
Deposit rounding-down of `convert-to-shares-preview` can mint zero vault shares while assets are still transferred in - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The Zest v2 vault contracts (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) compute the number of zToken shares to mint on deposit using a floor-rounding division, exactly analogous to `WUSDA::_usdaToWUSDA`. Unlike the `redeem` path, the `deposit` path has no explicit "output not zero" guard, so a depositor whose share price has appreciated enough (via accrued interest) can transfer underlying assets into the vault and receive `0` shares in return, permanently losing the deposited funds to the vault's existing shareholders.

### Finding Description
Shares minted on deposit are computed by `convert-to-shares-preview`, which performs a floor division `mul-div-down amount ts ta` (shares = amount * totalSupply / totalAssets): [1](#0-0) 

`deposit` calls this preview function and only checks the result against a caller-supplied `min-out` slippage bound - it does not assert that `inkind` (shares minted) is non-zero: [2](#0-1) 

By contrast, `redeem` explicitly guards against a zero output with `ERR-OUTPUT-ZERO`: [3](#0-2) 

This is the same shape of bug reported in `WUSDA::_usdaToWUSDA` for H-03: floor rounding in the mint-side conversion function is unguarded, while the withdraw/redeem side has a check. As documented, vault shares are priced via the liquidity index and appreciate over time (`1 zUSDC = 1.10 USDC` after interest accrues, etc.): [4](#0-3) 

As `total-assets-preview` (numerator of the share price) grows relative to `total-supply-preview` due to accrued interest, `ta` grows relative to `ts`. For any deposit `amount` small enough that `amount * ts / ta` truncates to `0`, the depositor's call to `deposit` succeeds: `receive-underlying` pulls in their tokens and increases `assets`, but `ft-mint? zft inkind recipient` mints `0` shares, since `min-out` defaults to `0` for naive callers, satisfying `(>= inkind min-out)`.

### Impact Explanation
The depositor's underlying tokens are absorbed into the vault's `assets` balance (increasing the value backing existing zToken holders) while they receive zero shares - a direct, non-recoverable loss of the depositor's principal for the vault's benefit. This is a direct theft of user funds at rest (silently redistributed to existing shareholders), matching the Critical impact class. This is worse the longer a vault has accrued interest (i.e., the higher the vault's share price / liquidity index), making legacy vaults with meaningful yield more susceptible to dust-sized or unlucky-sized deposits rounding to zero shares.

### Likelihood Explanation
Likelihood is moderate: it requires the vault's assets-to-supply ratio to have grown enough, and the deposited `amount` to be small relative to that ratio, for `amount * ts / ta` to truncate to zero. Unlike the WUSDA PoC (which used a flash loan to instantly inflate `_totalUsdaSupply`), the Zest vaults mint shares proportionally on every deposit, so an attacker cannot trivially manufacture the ratio in a single transaction to force a victim's rounding to zero the same way; however, natural interest accrual over time, or a UI/integration that submits `min-out = 0`, is sufficient to trigger loss for the depositor without any attacker action. It is a real but narrower-likelihood variant of the reported bug class (rounding-direction defect, no floor-zero revert on the minting path).

### Recommendation
Add an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check in the `deposit` function of all vault contracts (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), mirroring the existing check already present in `redeem`. Consider also rounding `convert-to-shares-preview` up (`mul-div-up`) or otherwise ensuring depositors are never charged for share-price precision loss.

### Proof of Concept
1. Vault has been live long enough that `total-assets-preview` / `total-supply-preview` (the effective share price) has grown substantially due to accrued interest, per the liquidity-index mechanism described in `docs/vaults.md`.
2. A user calls `deposit` with a small `amount` and `min-out = 0` (default/naive integration).
3. `convert-to-shares-preview` computes `inkind = (amount * ts) / ta`, which truncates to `0` because `amount` is small relative to `ta/ts`. [1](#0-0) 
4. `deposit` passes all its assertions (`amount > 0`, `inkind >= min-out` since `0 >= 0`), transfers the user's underlying tokens into the vault via `receive-underlying`, and mints `0` shares via `ft-mint? zft inkind recipient`. [5](#0-4) 
5. The depositor's tokens are now part of `assets` (benefiting all existing zToken holders), but the depositor holds zero shares and cannot redeem anything - a total loss of their deposit.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))

## Share Pricing Mechanism

### How Ztokens Accrue Value

Vault shares (ztokens) increase in value relative to underlying assets through the **liquidity index**:

```
Initial State:
- 1 zUSDC = 1 USDC (index = 1.0)

After Interest Accrual:
- 1 zUSDC = 1.10 USDC (index = 1.10)
- 10% interest earned

Later:
- 1 zUSDC = 1.25 USDC (index = 1.25)
- 25% cumulative interest
```

### Deposit Flow
1. User deposits 100 USDC
2. Vault calculates shares: `shares = amount / price`
3. If current price is 1.10 USDC per share
4. User receives ~90.9 zUSDC
5. Value remains 100 USDC equivalent
