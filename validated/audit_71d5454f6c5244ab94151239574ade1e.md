### Title
Hookify `PreToolUse`/`Stop` hook rule engine fails open on any evaluation error, allowing dangerous tool calls to bypass configured deny rules with no other enforcement layer - ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
The external report describes an English auction whose reserve price ("the total outstanding debt") is a best-effort target with no enforcement anywhere else in the protocol — if bidding fails to reach it, the liquidator still wins the collateral by default. The `hookify` plugin's `PreToolUse` (and `Stop`) hooks implement an analogous best-effort-only security control: user-defined `block` rules are the only mechanism preventing dangerous `Bash`/`Edit`/`Write` operations, but there is no backstop that enforces "deny" as the default when the mechanism itself fails. On any exception during rule loading or matching, the hook unconditionally allows the tool call.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` reads the tool call, loads user rules via `load_rules()`, and evaluates them with `RuleEngine.evaluate_rules()` [1](#0-0) . Any exception raised anywhere in that path (rule loading, frontmatter parsing, condition matching, regex compilation) is caught by a blanket `except Exception` that only emits a `systemMessage`, and the `finally` block unconditionally calls `sys.exit(0)` — the exit code Claude Code interprets as "hook approved" [2](#0-1) . There is no fallback to `deny` or `ask`.

`RuleEngine._check_condition` calls `self._regex_match(pattern, field_value)` for the `regex_match` operator with no local exception handling visible around the compilation step [3](#0-2) , and `compile_regex()` calls `re.compile(pattern, re.IGNORECASE)` directly [4](#0-3) . A malformed regex pattern (e.g., unbalanced parentheses/brackets) raises `re.error`, which propagates up through `evaluate_rules` uncaught by any of the specific `(IOError, OSError, PermissionError)`/`(ValueError, KeyError, AttributeError, TypeError)` handlers in `config_loader.py` (those only guard file loading, not rule matching) [5](#0-4) , and lands in `pretooluse.py`'s catch-all, which allows the operation rather than denying it.

This mirrors the auction bug's root cause exactly: a best-effort protective mechanism (auction bids reaching the reserve price / hookify's deny rules matching) has no independently enforced floor. When the mechanism doesn't function as intended (no bids reach reserve / rule evaluation throws), the "loser" outcome (liquidator gets collateral for free / dangerous command proceeds unblocked) happens silently by default.

### Impact Explanation
Any project relying on `hookify` deny rules (e.g., "block `rm -rf /`", "block writes to `.env`", "block `sudo`") loses that protection entirely and silently whenever the specific rule file that would have matched contains any input that trips an uncaught exception in the matching path (most notably an invalid regex pattern). The tool call proceeds exactly as if no rule existed, with only a `systemMessage` noting a "Hookify error" — easy to miss in a busy transcript, and it does not surface as a permission prompt or denial. Since `hookify` is explicitly marketed as a security-relevant hook (`PreToolUse` gating of `Bash`/`Edit`/`Write`), fail-open behavior on error defeats the safety purpose of the plugin for the affected rule and effectively for the whole tool call, because `evaluate_rules` returns "no matches, allow" as soon as an exception aborts processing (other rules in the same batch are also skipped, since the exception aborts the whole `for rule in rules` loop in `evaluate_rules`).

### Likelihood Explanation
Moderate. This does not require attacker-controlled rule files under normal use — rule files are project-owner-authored — but errors of this class are easy to trigger unintentionally (a user writing a regex-based rule with a typo, e.g., missing a closing parenthesis) or via an untrusted content injection scenario where a rule file is generated/edited by the agent itself under indirect prompt injection from repository content (e.g., a malicious README instructing Claude to "add a safety rule" with a subtly broken pattern). Because failure is silent (fail-open, exit 0) rather than loud (fail-closed with a prompt), the exposure window persists until a user notices the missing enforcement.

### Recommendation
Change the fail-open default to fail-closed (or at least fail-to-`ask`) for `PreToolUse` hooks that exist specifically to enforce `block` rules: on any unhandled exception during rule loading/matching, emit `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "ask"}}` rather than exiting 0 with only a system message. Additionally, wrap `_regex_match`/`compile_regex` in a narrow `try/except re.error` that treats a malformed pattern as "rule cannot be evaluated safely" and escalates to `ask`/`deny` for that specific rule instead of allowing the exception to abort evaluation of the whole rule set.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```
---
name: block-dangerous-rm
enabled: true
event: bash
action: block
conditions:
  - field: command, operator: regex_match, pattern: "rm -rf ("
---
Blocked dangerous rm command.
```
(Note the pattern `rm -rf (` is an unbalanced/invalid regex.)

2. Trigger a `Bash` tool call with `command: "rm -rf (/important/data)"` — this pattern is exactly what the rule intends to block.

3. `pretooluse.py` invokes `RuleEngine.evaluate_rules` → `_check_condition` → `_regex_match("rm -rf (", ...)` → `compile_regex` → `re.compile` raises `re.error: missing ), unterminated subpattern`.

4. This exception is uncaught within `rule_engine.py`/`config_loader.py`, propagates to `pretooluse.py`'s outer `except Exception`, which prints a `systemMessage` and then `sys.exit(0)` in the `finally` block [2](#0-1) .

5. Claude Code treats exit code 0 with no `permissionDecision: deny` as approval, and the destructive `rm -rf` command executes despite an explicit, matching deny rule.

Note: I could not view the remaining body of `_regex_match` beyond line 220 of `rule_engine.py` before the tool budget ran out, so I cannot 100% rule out a local try/except specifically around the `re.compile`/`match` call inside that function; however, no such guard is visible in the code I reviewed (`compile_regex` itself has none), and the broader architecture (specific exception handling only around file I/O in `config_loader.py`, generic catch-all only at the top-level hook script) strongly supports that regex compilation errors are unhandled until they reach the fail-open top-level handler.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
