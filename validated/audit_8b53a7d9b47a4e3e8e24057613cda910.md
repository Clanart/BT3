### Title
Missing `chain_id` in EIP-712 Domain Separator Enables Cross-Network Replay of Withdrawal Authorization Signatures - (File: `core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to authenticate aggregator withdrawal authorization signatures is defined without a `chain_id` field. This allows a valid signature produced for one Citrea EVM network (e.g., testnet, chain_id=5655) to be replayed verbatim on any other Citrea EVM network (e.g., mainnet) where the same Clementine bridge is deployed, bypassing the aggregator authentication gate and causing operators to execute unauthorized BTC payout transactions.

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is declared as a static constant in `core/src/rpc/ecdsa_verification_sig.rs`:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 standard's domain separator is specifically designed to include a `chain_id` field to prevent cross-chain replay. Here, neither `chain_id` nor `verifying_contract` is present. The domain hash is therefore identical across every EVM network.

This domain is used in `recover_address_from_ecdsa_signature` to reconstruct the signing hash for both `OptimisticPayoutMessage` (used in the verifier's `sign_optimistic_payout`) and `OperatorWithdrawalMessage` (used in the operator's `withdraw` RPC):

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [2](#0-1) 

The recovered address is then compared against `aggregator_verification_address` from config:

```rust
if address_from_sig != address_in_config {
    return Err(BridgeError::InvalidECDSAVerificationSignature);
}
``` [3](#0-2) [4](#0-3) 

The `citrea_chain_id` is present in `BridgeConfig` and is used to configure the EVM wallet signer, but it is never incorporated into `CLEMENTINE_EIP712_DOMAIN`: [5](#0-4) [6](#0-5) 

### Impact Explanation

When `aggregator_verification_address` is configured (the production guard for withdrawal authorization), an attacker who obtains a legitimately signed `OperatorWithdrawalMessage` or `OptimisticPayoutMessage` from one Citrea network can submit it to operators/verifiers on a different Citrea network. Because the domain hash is network-agnostic, `recover_address_from_prehash` returns the same address on both networks, and the check passes.

Concretely: if the aggregator signs a withdrawal authorization for deposit #N on Citrea testnet, that exact signature is accepted on Citrea mainnet for deposit #N (which may reference a different, larger BTC UTXO). The operator then constructs and broadcasts a payout transaction on mainnet, spending bridge-controlled BTC without a valid mainnet authorization. This constitutes unauthorized loss of bridged BTC from the operator's perspective and breaks the bridge safety invariant.

### Likelihood Explanation

The precondition is that `aggregator_verification_address` is set in config (it is optional, but it is the intended production security control as documented in `BridgeConfig`). The attacker needs access to a legitimately signed message from one network — obtainable by participating in a withdrawal on testnet. The replay requires no privileged access and no code modification; it is a straightforward cross-network signature submission to the operator/verifier gRPC endpoint. [7](#0-6) 

### Recommendation

Include `chain_id` (and optionally `verifying_contract`) in `CLEMENTINE_EIP712_DOMAIN`. The `citrea_chain_id` from `BridgeConfig` must be incorporated at domain construction time rather than using a static constant. Since the domain must be network-specific, `CLEMENTINE_EIP712_DOMAIN` should be constructed dynamically from the runtime config:

```rust
// Instead of a static:
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Then pass `config.citrea_chain_id as u64` wherever `CLEMENTINE_EIP712_DOMAIN` is currently referenced.

### Proof of Concept

1. Deploy Clementine on Citrea testnet (chain_id=5655) and Citrea mainnet (chain_id=X, different value).
2. On testnet, initiate a withdrawal for deposit #0 with output amount A. The aggregator signs an `OperatorWithdrawalMessage` over `(withdrawal_id=0, input_sig, input_outpoint, output_script, A)` using `CLEMENTINE_EIP712_DOMAIN` (no chain_id). Call this `sig_testnet`.
3. On mainnet, deposit #0 also exists (same sequential ID) with a larger BTC UTXO.
4. Submit to the mainnet operator's `Withdraw` RPC: `WithdrawParamsWithSig { withdrawal: params_for_mainnet_deposit_0, verification_signature: sig_testnet }`.
5. The operator calls `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` with `CLEMENTINE_EIP712_DOMAIN` (identical on both networks). The recovered address matches `aggregator_verification_address`. The check passes.
6. The operator executes the payout transaction on mainnet, spending mainnet BTC without a valid mainnet authorization. [8](#0-7) [9](#0-8) [10](#0-9)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
