## Analysis

The Redstone report's core broken invariant: **a value that was authenticated/rejected/expired can be resubmitted and re-accepted because the acceptance guard only checks weak ordering (`>` on a window) instead of remembering that this exact value/height was already dealt with.**

The closest local analog is in Hyperbridge's EVM `HandlerV2`/`EvmHost` state-machine-commitment veto flow, where a fisherman-deleted (fraudulent) state commitment can be **re-inserted at the same height** because the "latest height" bookkeeping is reset to a low sentinel value instead of permanently recording that height as invalid.

### Title
Vetoed/fraudulent state machine commitments can be re-accepted at the same height after a fisherman deletes them - (File: evm/src/core/HandlerV2.sol, evm/src/core/EvmHost.sol)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` resets `_latestStateMachineHeight` to the sentinel value `1` when the vetoed height was the current latest height [1](#0-0) . `HandlerV2.handleConsensus` then only refuses to store an intermediate commitment when `latestHeight != 0 && intermediate.height > latestHeight` is false [2](#0-1) . After a veto, `latestHeight` becomes `1`, so any subsequently delivered intermediate for the **same, previously-vetoed height** (as long as it's `> 1`) satisfies this check and is written back into `_stateCommitments`, silently undoing the fisherman's fraud-proof action.

### Finding Description
The intended lifecycle is: consensus proof verified → intermediate state (child/counterparty state-machine commitment) stored → if later proven fraudulent, a fisherman calls `deleteStateMachineCommitment` to purge it [3](#0-2) . `deleteStateMachineCommitmentInternal` deletes the commitment and its update-time entry, and "resets" `_latestStateMachineHeight` only if the deleted height was the currently recorded latest height — but it resets it to `1`, not to a value that blocks resubmission of that very height:
```
if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
    _latestStateMachineHeight[height.stateMachineId] = 1;
``` [4](#0-3) 

`storeStateMachineCommitment` itself performs an **unconditional overwrite** of both the commitment and `_latestStateMachineHeight`, with no check that the new height is actually greater than what is already stored, and no memory of previously-deleted/fraudulent heights:
```
_stateCommitments[height.stateMachineId][height.height] = commitment;
_stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
_latestStateMachineHeight[height.stateMachineId] = height.height;
``` [5](#0-4) 

The only gate against reinsertion lives in `HandlerV2.handleConsensus`:
```
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ...
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
``` [2](#0-1) 

Because the veto path drops `latestHeight` down to `1` instead of remembering "height H was invalidated," any later consensus/intermediate-state proof for the same height `H` (`H > 1`) passes `intermediate.height > latestHeight` and is written straight back into `_stateCommitments`, exactly reproducing the state that governance/fishermen just proved fraudulent and removed. There is no per-height "vetoed" marker, and the height-monotonicity check is the only defense — which this reset defeats.

This mirrors the Redstone flaw precisely: acceptance is gated purely by "is this within an acceptable range/ordering" rather than "has this exact value already been rejected," so a value that was explicitly invalidated can flow back into the trusted state.

### Impact Explanation
A resurrected fraudulent `StateCommitment` (state root + timestamp) is exactly the artifact used downstream by `HandlerV2.handlePostRequests`, `handleGetResponses`, and the timeout handlers to authorize dispatch of cross-chain requests/responses via Merkle Mountain Range and non-membership proofs anchored to `stateMachineCommitment(height)` [6](#0-5) . If a vetoed (attacker-controlled/incorrect) state root is re-accepted at the same height, an attacker can forge inclusion proofs against that resurrected root to get arbitrary `PostRequest`/`GetResponse` payloads accepted as authentic cross-chain messages — i.e., false state acceptance leading to unauthorized execution or fund movement through the ISMP request/response pipeline.

### Likelihood Explanation
No privileged, malicious-relayer, or malicious-prover assumption is required beyond what already exists in the normal proof-submission flow: any permissionless caller of `handleConsensus` (this function has no access restriction beyond `notFrozen`) can resubmit a proof/intermediate that reconstructs the same height once the fisherman veto has reset the sentinel. The precondition is simply that a fraud veto has previously occurred for the latest height of a given state machine — an expected, not exceptional, event in the protocol's threat model (fishermen exist specifically because provers can misbehave).

### Recommendation
Track invalidated/vetoed heights explicitly (e.g., a `mapping(bytes32 stateMachineId => mapping(uint256 height => bool vetoed))`) and permanently reject `storeStateMachineCommitment` calls for any height marked vetoed, instead of relying solely on resetting `_latestStateMachineHeight` to a low sentinel. Additionally, `storeStateMachineCommitment`/`handleConsensus` should refuse to overwrite an existing (or previously vetoed) height rather than allowing unconditional overwrite once the height-ordering check passes.

### Proof of Concept
1. Consensus proof P1 is submitted via `handleConsensus`, producing intermediate `IntermediateState{stateMachineId: X, height: H, commitment: C1}`; `latestStateMachineHeight(X)` becomes `H` [7](#0-6) .
2. `C1` is later proven fraudulent; a fisherman calls `deleteStateMachineCommitment({stateMachineId:X, height:H}, fisherman)`. Since `H == latestStateMachineHeight(X)`, `_latestStateMachineHeight[X]` is reset to `1` [1](#0-0) .
3. Anyone resubmits (or re-derives) an intermediate for the same height `H` with commitment `C2` (which can again be attacker-influenced, since the underlying consensus proof for that historical relay/finality point is still cryptographically "valid" and not itself re-checked for freshness beyond the height-ordering test).
4. In `handleConsensus`, `latestHeight = 1`, so `latestHeight != 0 && H > 1` is `true`; `storeStateMachineCommitment` is called, writing `C2` (or replaying `C1`) back into `_stateCommitments[X][H]`, overwriting the post-veto empty slot [2](#0-1) .
5. Downstream `handlePostRequests`/`handleGetResponses` now trust `stateMachineCommitment(X, H)` again, allowing proofs anchored to the resurrected/forged root to be accepted [8](#0-7) .

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }
