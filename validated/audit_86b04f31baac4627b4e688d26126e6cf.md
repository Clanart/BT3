## Finding: Duplicate crediting of transferred value when native-ERC20 conversion fails after ICS-20 receipt succeeds

### Title
IBC receive callback returns an error acknowledgement after already committing the underlying coin transfer, causing double-crediting of value across chains - (File: `x/erc20/ibc_middleware.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`IBCMiddleware.OnRecvPacket` first runs the standard ICS-20 receive logic (which mints/un-escrows the transferred coin to the recipient) and, only if that succeeds, calls `erc20 Keeper.OnRecvPacket` to auto-convert the coin into its native ERC20 representation. If this second step fails (e.g. `MintingEnabled` or `ConvertCoinNativeERC20` errors), the middleware returns an **error acknowledgement** to the counterparty chain, even though the ICS-20 transfer itself already completed and credited the bank coin balance of the recipient in the same execution context. Because IBC core commits state written during `OnRecvPacket` regardless of whether the final acknowledgement is success or error (the *acknowledgement* only tells the counterparty whether to refund the sender - it does not roll back state already written by the callback), the source chain will refund/un-escrow the sender's original funds while the destination chain has already permanently credited the same value to the receiver. This is the same class of bug as the Renzo report: a secondary “deposit/convert” step failing incorrectly signals failure of the whole operation even though the primary funds-moving step already succeeded and was committed.

### Finding Description
`IBCMiddleware.OnRecvPacket` [1](#0-0)  executes:
1. `im.Module.OnRecvPacket(...)` — the standard ICS-20 transfer receive logic, which mints or un-escrows the coin into the recipient's bank balance and returns a success acknowledgement.
2. If that ack is a success, `im.keeper.OnRecvPacket(ctx, packet, ack)` is called to convert the just-credited coin into its native ERC20 representation.

Inside `Keeper.OnRecvPacket`, for the "native ERC20 token" case, if `MintingEnabled` fails or `ConvertCoinNativeERC20` fails, the function returns `channeltypes.NewErrorAcknowledgement(err)` [2](#0-1) , even though step 1 already wrote the coin balance to the recipient using the *same* `sdk.Context` (no `CacheContext()`/`writeFn()` isolation is used around this composite flow).

The test suite exercises exactly this path: setting `BankKeeper.SetSendEnabled(denom, false)` causes the conversion step to fail and the middleware to return an error acknowledgement [3](#0-2) . An error acknowledgement returned from `OnRecvPacket` causes the *source* chain, upon processing the acknowledgement, to refund/un-escrow the originally sent tokens back to the sender (that is the entire purpose of ICS-20 error acknowledgements). However, on the destination chain, the underlying ICS-20 mint/un-escrow performed in step 1 is not rolled back, because IBC-go's core packet-receiving handler commits any state written during the (possibly multi-layer) `OnRecvPacket` middleware chain once a non-nil acknowledgement — success or error — is produced; the acknowledgement is a signal to the counterparty, not a Go-level transaction abort.

### Impact Explanation
This results in the transferred value existing twice: once as a bank coin credited to the recipient on the destination chain (from the already-committed ICS-20 receive), and once again refunded to the sender on the source chain after the source chain processes the error acknowledgement. This is unauthorized duplication of spendable user value across an IBC escrow/transfer boundary, matching the Critical "duplication/unauthorized minting" impact category in scope.

### Likelihood Explanation
The trigger condition — the conversion step failing after the base ICS-20 receive succeeds — is reachable by unprivileged actors/ordinary chain configuration changes, not just malicious validators: e.g. `SendEnabled=false` toggled for a denom (as demonstrated directly in the repo's own test), a token pair being disabled between packet send and receipt, or `ConvertCoinNativeERC20` failing because the corresponding ERC20 contract reverts (paused/blocklisted/self-destructed but not yet cleaned up). Any relayer delivering a packet under these ordinary conditions triggers the divergence; no privileged access is required to cause the mismatch itself once such a condition exists.

### Recommendation
Wrap the composite receive+convert flow in a single `ctx.CacheContext()`/`writeFn()` pair keyed off the *final* acknowledgement, mirroring the pattern already used in `x/ibc/callbacks/keeper/keeper.go` for destination callbacks [4](#0-3) . Only call `writeFn()` (persisting both the coin credit and the ERC20 conversion) when the overall result is success; if the conversion fails, discard the cached ICS-20 mint/un-escrow effects as well, or leave the coin as a bank coin balance to the receiver *and* return the passthrough success ack (consistent with the doc-comment intent: "If conversion fails, then the user will receive the bank token instead" [5](#0-4) ) instead of an error acknowledgement that also triggers a refund on the source chain.

### Proof of Concept
1. Register a native ERC20 token pair on the destination (EVM) chain.
2. From the source chain, initiate an ICS-20 transfer of that token's IBC voucher back to the EVM chain (round trip) or use the direct receive path shown in the test.
3. Before the relayer delivers the packet, disable send for the destination denom: `BankKeeper.SetSendEnabled(ctx, denom, false)` (this can also occur due to governance-driven denom restrictions or a paused/blocklisted ERC20 contract implementing `MintingEnabled`/`transfer` checks).
4. Relay the packet: `im.Module.OnRecvPacket` succeeds and credits the recipient's bank balance [3](#0-2) ; `Keeper.OnRecvPacket`'s `ConvertCoinNativeERC20` call fails and an error acknowledgement is returned.
5. The relayer submits this error acknowledgement to the source chain, causing the source chain to refund/un-escrow the sender's original tokens.
6. Result: the recipient holds the credited bank coin on the destination chain (already committed, never rolled back) AND the sender has been refunded on the source chain — the same value now exists on both chains.

```go
func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
```
