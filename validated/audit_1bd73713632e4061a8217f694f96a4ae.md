### Title
Cached FROST nonce seed is reused across signing attempts under the same context, enabling secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a `CachedPreprocess` (the ChaCha20 seed that deterministically generates the FROST nonces `d` and `e`) keyed only by `self.context`, writes it once, and never deletes or rotates it. Every subsequent `share_internal`/`complete` call under the same context rebuilds `AlgorithmSignMachine::from_cache` with the identical seed, producing identical nonces. If `share()` is invoked more than once with different peer-preprocess maps — e.g., a first call that errors on an invalid preprocess followed by a retry — the same `(d, e)` pair is combined with different binding factors `rho`, which is textbook FROST nonce reuse and yields the signer's MuSig secret share.

### Finding Description
In `preprocess_internal`, the seed is generated only when `CachedPreprocesses::get` returns `None`; afterwards the stored seed is loaded and decrypted for every call. `seeded_preprocess` in `crypto/frost/src/sign.rs` derives both nonces and commitments deterministically from that seed via `ChaCha20Rng::from_seed`. There is no consumption/deletion of the cached entry — the FROST docs (`spec/cryptography/FROST.md`) state a preprocess MUST be used only once, yet here one seed backs `preprocess()`, `share()`, and `complete()` for the whole context `(b"DkgConfirmer", attempt)`.

A signature share is `s_i = d + e·rho_i + lambda_i·secret·c`. For two calls with different `preprocesses` maps, `rho_i` differs (it binds the participant to the commitment list/message via `hash_msg`), while `d`, `e`, `secret`, and `c` are unchanged. From `s1 - s2 = e·(rho1 - rho2)`, an attacker recovers `e`, then `d`, then `secret = (s1 - d - e·rho1)/(lambda1·c)` — the private key share.

Reachability: `DkgConfirmer::share` returns `Err(participant)` on `FrostError::InvalidPreprocess` without consuming the cache; the calling coordinator code can subsequently evaluate a different preprocess map for the same attempt, and `complete()` re-derives the same machine. Any path where two distinct valid preprocess maps are signed under one `(context)` reuses the nonces.

### Impact Explanation
Recovery of a validator's MuSig secret share. Combined with threshold-many compromised shares this collapses the multisig; even individually it defeats per-participant blame and enables forging that validator's participation. Severity: High/Critical per the accept criteria (key share recovery via attacker-influenced preprocess messages).

### Likelihood Explanation
Requires the coordinator to run the share step twice for one context — feasible when a first preprocess set contains an invalid preprocess from a malicious validator (error path does not burn the seed) and a corrected/different set is processed, or across the separate `share`/`complete` invocations if the preprocess map is re-evaluated. The deterministic reuse is unconditional in the code.

### Recommendation
Delete or rotate `CachedPreprocesses` once a `share` has been produced for a context (single-use semantics), or mix a per-session value (e.g., hash of the preprocess map / session ID) into the seed derivation so nonces differ per signing set.

### Proof of Concept
1. In an attempt, deliver a preprocess map `P1` containing one malformed preprocess so `share()` errors; the seed remains cached.
2. Deliver a second, valid map `P2 ≠ P1`. `share()` succeeds and emits share `s2` with nonces derived from the same seed.
3. Because the commitments in the victim's broadcast preprocess are identical in both calls, `d`, `e` are identical while `rho` differs; given shares from two executions (`s1` from any successful `P1'` set, `s2`), compute `e = (s1 - s2)/(rho1 - rho2)` and recover the secret share as above.

Caveat: I could not fully trace `coordinator/src/tributary/handle.rs` to confirm the exact retry/multi-invocation path for `DkgConfirmer::share`; the deterministic nonce reuse itself is unconditional in `preprocess_internal`, but exploitation requires a second share generation under the same context.
