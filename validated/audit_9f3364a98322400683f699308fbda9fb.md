### Title
Native tokens attached as `msg.value` to WERC20 `transfer`/`transferFrom`/`approve` calls are permanently locked because the ERC20 "cannot receive funds" guard is bypassed - (File: `precompiles/werc20/werc20.go`)

### Summary
The base ERC20 precompile explicitly rejects any call carrying `msg.value` because it has no mechanism to return or account for received native coins: [1](#0-0) 
The WERC20 precompile wraps the ERC20 precompile to add `deposit`/`withdraw`, but its own `Execute` dispatcher only forwards to `Deposit` for the fallback/receive/`deposit` selectors; every other selector (`transfer`, `transferFrom`, `approve`, view methods, etc.) falls into the `default` branch which calls `p.HandleMethod` **directly**, skipping `erc20.Precompile.Execute`'s value check entirely: [2](#0-1) 

### Finding Description
This is the direct Cosmos EVM analog of the C4 Infinity finding: a function family that legitimately accepts native value in one code path (here, `deposit()`/fallback/receive) and an ERC20-style path in another (`transfer`, `transferFrom`, `approve`), where the ERC20 path fails to reject unexpected `msg.value`.

In standard EVM `CALL` semantics, any `value` attached to a call to a contract address (precompile or not) is transferred from the caller's balance to the callee's balance in the state DB **before** the callee code (or precompiled contract logic) executes. For Cosmos EVM's native-coin-backed precompiles, this callee balance is the module/token-pair account associated with the WERC20 precompile address, which is kept synchronized with the bank module per the design described in the WERC20 README ("EVM and Cosmos SDK balances remain synchronized", "No Lock-up: Native tokens are never locked in the precompile").

The `Deposit` handler explicitly undoes this transfer by reading `contract.Value()` and sending the equivalent bank coins back to the caller: [3](#0-2) 

However, if a caller invokes `transfer(to, amount)` (or `transferFrom`/`approve`) on the WERC20 precompile while attaching `value` in the same call (e.g. `token.transfer{value: 1 ether}(to, amount)`), the value is still transferred into the precompile's backing account by the EVM's value-transfer step, but `Execute`'s `default` branch routes straight to `p.HandleMethod` — the exact same method used by the base ERC20 precompile — without ever calling the value-rejecting check found in `erc20.Precompile.Execute()` (`precompiles/erc20/erc20.go` lines 148-156). No refund, revert, or accounting adjustment occurs for that value in this code path; only `Deposit` performs the refund logic.

### Impact Explanation
Any native token amount attached via `msg.value` to a `transfer`, `transferFrom`, `approve`, or other non-deposit/withdraw ERC20 selector on the WERC20 precompile is transferred into the module account backing the precompile and is never returned to the sender, nor is it reflected in any user-facing balance. This is a permanent, irrecoverable freezing/loss of user funds (native coins) triggerable by an ordinary EOA or contract with no privileged access — matching the "Critical permanent freezing/locking of user funds" impact category. The base ERC20 precompile was intentionally hardened against exactly this scenario ("ERC20 precompiles cannot receive funds... this check is a safety measure"), but the WERC20 subclass's custom `Execute` override drops that protection for all non-deposit selectors.

### Likelihood Explanation
Likelihood is comparable to the original finding: it requires user/integrator error (attaching `value` to a call that is not `deposit`), which is plausible because WERC20 is explicitly designed to be usable as a drop-in ERC20/WETH-style token by third-party DeFi contracts that may not distinguish "deposit-style" calls from "ERC20-style" calls, and because `deposit()` legitimately accepts value, callers/composing contracts could mistakenly attach value to `transfer`/`transferFrom` in the same interaction pattern used for WETH-like tokens.

### Recommendation
In `precompiles/werc20/werc20.go`'s `Execute`, add the same guard used in the base ERC20 precompile for any method that is not `deposit`/fallback/receive: reject the call (or explicitly refund `contract.Value()`) when `contract.Value().Sign() == 1` for the `WithdrawMethod` and `default` branches, mirroring the C4 recommendation of requiring `msg.value == 0` for code paths that do not process native value.

### Proof of Concept
1. Deploy/obtain the WERC20 precompile instance for the native token's token pair (`precompiles/werc20`).
2. From an EOA/contract with a native token balance, call `transfer(to, amount)` on the precompile ABI while attaching `value: X` (X > 0) to the EVM call.
3. Observe: EVM value-transfer semantics move `X` from the caller into the precompile's backing account balance before `Execute` runs.
4. `Execute` dispatches to the `default` branch (since method name is `transfer`), calling `p.HandleMethod` directly (`precompiles/werc20/werc20.go` lines 118-120) — bypassing the `ErrCannotReceiveFunds` check present in `precompiles/erc20/erc20.go` lines 148-156.
5. The `transfer` executes normally (moving `amount` of the ERC20/bank-represented token), but `X` remains credited to the precompile's account indefinitely, with no code path to reclaim it (only `Deposit`, at `precompiles/werc20/tx.go` lines 28-57, refunds `contract.Value()`, and it is never invoked in this flow).

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch {
	case method.Type == abi.Fallback,
		method.Type == abi.Receive,
		method.Name == DepositMethod:
		bz, err = p.Deposit(ctx, contract, stateDB)
	case method.Name == WithdrawMethod:
		bz, err = p.Withdraw(ctx, contract, stateDB, args)
	default:
		// ERC20 transactions and queries
		bz, err = p.HandleMethod(ctx, contract, stateDB, method, args)
	}

	return bz, err
}

func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}
