### Title
Cached FROST preprocess is never invalidated and is reused on retry, enabling nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates the FROST nonces from a cached seed stored in `CachedPreprocesses`, keyed only by `self.context`. The cache is written once (if absent) and is never deleted after a signing attempt. Every call to `share_internal` for the same context reuses the identical nonce seed, so any retry of `machine.sign` — for example, after a malicious participant submits an invalid preprocess and the round is re-run within the same attempt — produces a signature share over the same secret nonces. Two shares sharing a nonce but differing in signing set/message reveal the validator's secret key share algebraically.

### Finding Description
The kernel bug class is "a faulted/missed invalidation leaves stale state that is consumed as if fresh" (the skipped cache-line flush). The Serai analog lives here:

In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148):

- The nonce seed is fetched with `CachedPreprocesses::get(self.txn, &self.context)` (line 123); if absent, a machine is created, `machine.cache()` is XOR-encrypted and stored via `CachedPreprocesses::set` (line 134).
- The cached seed is then decrypted and passed to `AlgorithmSignMachine::from_cache` → `seeded_preprocess(cache)` (crypto/frost/src/sign.rs:268-274), which derives the actual signing nonces deterministically from that seed.

Critically:

- Nothing ever removes or rotates the entry in `CachedPreprocesses`. The `SignMachine::cache` documentation itself warns the cached preprocess "MUST only be used once. Reuse of it enables recovery of your private key share" (crypto/frost/src/sign.rs:211-219) and that after `from_cache` "the preprocess must be deleted so it's never reused" — this deletion never happens in `preprocess_internal`.
- `share_internal` (lines 150-180) calls `preprocess_internal` again and then `machine.sign(preprocesses, msg)`. If `sign` fails with `FrostError::InvalidPreprocess`/`InvalidShare` — which any other participant can trigger by supplying malformed preprocess bytes through `read_preprocess`/`Commitments::read` — the handler returns `Err(participant)` but the cached seed remains in the DB. A subsequent call to `share_internal` for the same context (same attempt) reconstructs the machine with the *same* nonces and signs again, potentially with a different `included` set (different binding factors ρ and different Lagrange coefficients λ).

The FROST share has the form `s = (d + e·ρ) + c·λ·x` where `d + e·ρ` is derived from the cached seed and `x` is the secret share. With the same nonces, the same message/context, and two different signing sets (`λ₁ ≠ λ₂`, possibly different ρ), an observer holding both broadcast shares solves for `x`:

`s₁ − s₂ = c·(λ₁ − λ₂)·x` ⇒ `x = (s₁ − s₂) / (c·(λ₁ − λ₂))`

Both shares are broadcast publicly per the FROST protocol, so any participant (or anyone observing the tributary data) recovers the validator's secret share. Collecting `t` such compromised shares — or compromising one validator while the protocol runs across attempts — degrades the threshold key.

### Impact Explanation
Recovery of a validator's FROST secret share. Repeating this against `t` validators (or combining with shares already exposed by other means) reconstructs the group private key, enabling forgery of arbitrary threshold signatures — i.e., signing unintended messages/transactions. Severity: High. A single reuse only exposes one share, but the shares are broadcast and the attack is repeatable per attempt, and the leaked share is permanent.

### Likelihood Explanation
- Reachable by an unprivileged participant: `read_preprocess`/`Commitments::read` parse attacker-controlled bytes; submitting an invalid preprocess deterministically causes `FrostError::InvalidPreprocess` (crypto/frost/src/sign.rs:348-358, coordinator/src/tributary/signing_protocol.rs:165-177), which aborts the round *after* the cached seed was stored but without consuming/erasing it.
- A retry within the same attempt/context — the natural protocol response to a blamed participant (drop them and re-run with the remaining set) — deterministically reuses the nonces. No RNG failure, no collusion, and no leaked key material is required; the "freshness" the signer relies on is silently stale, exactly mirroring the skipped-invalidation bug class.
- Likelihood is bounded by whether the coordinator/validators re-drive `share_internal` for an identical context after an error; the code issues no guard against it and the cache persists indefinitely.

### Recommendation
- Delete the `CachedPreprocesses` entry (or rotate the seed) immediately after it is consumed in `preprocess_internal`/`share_internal`, honoring the `from_cache` contract in crypto/frost/src/sign.rs:216-224.
- As defense-in-depth, make `seeded_preprocess` mix in the message/signing-set commitment (e.g., the `preprocesses` transcript challenge) so nonces are bound to the exact session and cannot repeat across retries — noting this deviates from strict IETF nonce derivation and should be documented.
- On `FrostError::InvalidPreprocess`/`InvalidShare`, treat the cached preprocess as burned: never sign again with the same seed.

### Proof of Concept
1. Setup: tributary signing protocol running `SigningProtocol` with a fixed `context` C for attempt `a`; `CachedPreprocesses` empty.
2. Attacker (Participant `l`) sends a syntactically valid blob that deserializes but whose addendum/commitments fail `process_addendum` or `Commitments` validation → `share_internal` returns `FrostError::InvalidPreprocess(l)`. `CachedPreprocesses` entry for C now exists (set during this call).
3. The protocol re-runs `share_internal` for the same context C with a corrected participant set `included₂` (attacker excluded or replaced). `preprocess_internal` hits `CachedPreprocesses::get` → same seed → `seeded_preprocess` → identical nonces `d, e`.
4. Honest validator broadcasts share `s₂` over `included₂`. Had the first call succeeded (or a prior partial execution produced `s₁` over `included₁`), or by forcing two sign invocations with distinct sets in the same context, the attacker obtains two shares `s₁, s₂` with identical nonce component and different `λ`/ρ.
5. Compute `x = (s₁ − s₂)·(c·(λ₁ − λ₂))⁻¹` (ρ terms are publicly recomputable via `hash_binding_factor`, `c` via the public challenge). The validator's secret share is recovered; verify by checking `C::generator()·λ·x == verification_share(i)` via `view.verification_share(i)` (crypto/dkg/src/lib.rs:680-682).

Key uncertainty: whether the coordinator issues a second `share_internal` under an identical `context` after an `InvalidPreprocess` error (vs. always bumping `attempt`). The cache key is only `self.context.encode()`, so any code path that re-enters with the same context — retry, duplicate delivery, or reshare within an attempt — triggers the reuse; no code path deletes the entry, so the precondition is purely a scheduling decision external to this module.
