### Title
Deep-link driven PR checkout trusts attacker-supplied repo/PR parameters, silently adding an attacker remote and checking out fork content into an existing local repository - (File: app/src/ui/dispatcher/dispatcher.ts)

### Summary
The original bug lets an attacker redirect the outcome of an operation that should be scoped to a resource the caller legitimately controls (`gtId`) by supplying attacker-chosen parameters instead of verifying ownership. The closest analog in GitHub Desktop is the `open-repository-from-url` deep-link handler: the `pr` and `url` values in the custom-protocol URL are fully attacker-controlled, and Desktop uses them to fetch a pull request and then automatically add a new git remote and check out that PR's fork branch into the user's existing local repository — without verifying that the link's target actually corresponds to something the user trusted, and without any confirmation prompt.

### Finding Description
`parseAppURL` accepts any `openrepo` deep link and extracts `url`, `branch`, `pr`, and `filepath` straight from the URL query string with only superficial format validation (numeric `pr`, ref-name characters for `branch`) [1](#0-0) . This action is dispatched to `Dispatcher.openRepositoryFromUrl`, which for a `pr` parameter calls `openPullRequestFromUrl(url, pr)` [2](#0-1) .

`openPullRequestFromUrl` fetches the PR data using the attacker-supplied `url`/`pr` pair, locates (or clones) the matching local repository, and then unconditionally calls `_checkoutPullRequest` using `pullRequest.head.repo.clone_url` — a value that comes from the PR's *head* repository, i.e. the fork that opened the PR, which is fully attacker-controlled since anyone can open a PR against a public repository from their own fork: [3](#0-2) 

`_checkoutPullRequest`/`_findPullRequestBranch` then, with no confirmation to the user, adds a brand-new git remote pointing at that attacker fork URL to the user's existing repository, fetches from it, and creates/checks out a local branch tracking it: [4](#0-3) [5](#0-4) 

Nothing in this path verifies that the deep link actually originated from a page the user was legitimately viewing (e.g., a real "Open in Desktop" button rendered for that exact PR) — `url` and `pr` are taken at face value from whatever process invoked the `x-github-client://`/`github-mac://`/`github-windows://` protocol handler (email client, browser, any local app). Since PR numbers are attacker-choosable (the attacker just opens a PR against the target repo from their own fork) and the target `url` can be any public repository the victim might already have cloned, the "recipient" of the operation — i.e., which remote/branch content gets pulled into the user's working directory — is effectively attacker-selected, mirroring the original report's core flaw: the function trusts a caller-supplied destination without validating that it corresponds to something the invoking party actually owns/controls in a trusted way.

### Impact Explanation
Clicking such a link causes GitHub Desktop to:
- Silently add a new remote (`github-desktop-<owner>`) pointing at attacker infrastructure into an already-existing, trusted local repository [6](#0-5) .
- Fetch and check out attacker-authored branch content into the user's working directory [7](#0-6) .

If the user is unaware their working tree switched (e.g., is mid-workflow, builds/runs code, or commits on top of the checked-out branch), this silently corrupts what they may subsequently commit or push, and persists an untrusted remote in the repo's git config for future fetch/push operations — matching the "silent corruption of what the user commits or pushes" and "attacker-controlled GitHub API object / deep link" impact categories.

### Likelihood Explanation
Requires the victim to click a crafted deep link (an explicitly in-scope attacker capability per this assessment's rules). No local access, admin rights, or pre-existing malware is needed; the attacker only needs to open a real pull request (a low-privilege, self-service GitHub action) against a public repository the victim is likely to have cloned, then distribute a `github-mac://openRepo/...?pr=<N>` link. The existing input validation in `parseAppURL` (numeric `pr`, ref-name sanity check on `branch`) does not address this because the issue is not malformed input but trusting attacker-chosen `url`/`pr` values as if they came from a verified, trusted source.

### Recommendation
- Before adding a remote/fetching/checking out a PR triggered via an external deep link, present an explicit confirmation dialog naming the fork's clone URL and PR author, distinct from the flow used when a PR is selected from within Desktop's own vetted PR list.
- Consider requiring that `open-repository-from-url` actions only affect repositories the local app already associates via a signed/verified GitHub API context, rather than trusting the raw `url`/`pr` values from the protocol URL directly for the checkout step.
- Rate-limit or gate automatic remote-adding based on deep links, and clearly surface newly added `github-desktop-*` remotes to the user.

### Proof of Concept
1. Attacker forks a popular public repository the victim likely already has cloned in Desktop (e.g. `https://github.com/desktop/desktop`) and opens a pull request (PR #N) from the fork containing arbitrary content.
2. Attacker sends the victim a link: `x-github-client://openrepo/https://github.com/desktop/desktop?pr=N`.
3. Victim clicks the link. `handleAppURL` → `parseAppURL` recognizes it as `open-repository-from-url` with `pr=N` [1](#0-0) .
4. `Dispatcher.dispatchURLAction` → `openRepositoryFromUrl` → `openPullRequestFromUrl` fetches PR #N and passes `pullRequest.head.repo.clone_url` (attacker's fork) to `_checkoutPullRequest` [3](#0-2) .
5. `_findPullRequestBranch` adds the attacker's fork as a new remote, fetches it, and checks out `pr/N` into the victim's existing local `desktop/desktop` repository without any confirmation prompt [8](#0-7) .

**Uncertainty note:** I could not fully verify, from the indexed portions of the codebase, whether a confirmation dialog for PR checkouts triggered specifically via `open-repository-from-url` exists elsewhere in the UI layer that isn't captured in the indexed snippets (e.g., a popup shown before `_checkoutPullRequest` executes). Given index size limits, some file contents may not be available; a full review of `app/src/ui/dispatcher/dispatcher.ts` and any related popup/confirmation components in a live Devin session is recommended to confirm no such gate exists before treating this as fully confirmed.

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }

  public async _checkoutPullRequest(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<void> {
    const prBranch = await this._findPullRequestBranch(
      repository,
      prNumber,
      headRepoOwner,
      headCloneUrl,
      headRefName
    )
    if (prBranch !== undefined) {
      await this._checkoutBranch(repository, prBranch)
      this.statsStore.increment('prBranchCheckouts')
    }
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
