### Title
MessageSet extension parsing skips the type-tag check that the sibling non-MessageSet extension path enforces - (File: `src/google/protobuf/extension_set_inl.h`)

### Summary
The generic extension parsing path (`ExtensionSet::ParseField` → `FindExtensionInfoFromFieldNumber`) validates that the wire type on the wire matches the schema-declared type of the extension before dispatching to a type-specific handler. The sibling `MessageSet` item parsing path (`ExtensionSet::ParseMessageSetItemTmpl` / `WireFormat::MessageSetParser::ParseElement`) looks up the extension by `type_id` alone and then unconditionally treats it as `WireFormatLite::TYPE_MESSAGE`, without checking `extension.type == WireFormatLite::TYPE_MESSAGE`, mirroring the audited pattern of "fewer checks in sibling functions than in the primary one."

### Finding Description
For normal (non-MessageSet) extensions, `ExtensionSet::FindExtensionInfoFromFieldNumber` computes the schema's `expected_wire_type` from `extension->type` and requires the wire's actual wire type to match (or be packable) before returning success: [1](#0-0) 

This means `ExtensionSet::ParseField` / `ParseFieldWithExtensionInfo` can only ever dispatch to a handler whose wire-type expectation matches what's on the wire, and `info.message_info.class_data` is only used from the `TYPE_MESSAGE`/`TYPE_GROUP` case branches, which are only reached when `info.type` is actually `TYPE_MESSAGE`/`TYPE_GROUP`: [2](#0-1) 

The sibling function, `ExtensionSet::ParseMessageSetItemTmpl`, handles the `MessageSet` wire format (`repeated group Item { required uint32 type_id = 2; required bytes message = 3; }`). It looks up the extension via `FindExtension(2, type_id, extendee, ctx, &extension, &was_packed_on_wire)` — hardcoding wire type `2` (`WIRETYPE_LENGTH_DELIMITED`) rather than checking the extension's declared field type — and then, if found, **unconditionally** treats it as a message and calls `AddMessage`/`MutableMessageByClassData` using `extension.message_info.class_data`, without ever checking `extension.type == WireFormatLite::TYPE_MESSAGE`: [3](#0-2) 

This is structurally identical to the audited bug: `pairTransferERC20From()` performs a `variant`-matching check that its siblings `pairTransferNFTFrom()`/`pairTransferERC1155From()` omit, letting those siblings act on the wrong pair type. Here, `ExtensionSet::ParseField` performs a type/wire-type consistency check that its sibling `ParseMessageSetItemTmpl` omits, letting the MessageSet path treat an extension of unknown/unverified declared type as `TYPE_MESSAGE` and reinterpret `extension.message_info.class_data`/`extension.descriptor` as message metadata.

The equivalent C++ non-templated `WireFormat::MessageSetParser::ParseElement` path (used for full/reflection-based `Message`) has the same shape — it looks up `field` by `type_id` via `pool->FindExtensionByNumber` and only defends against `field->message_type() == nullptr` (i.e., checks the field is a message-*type* field), which is a real but different/partial check than the templated `MessageLite` path, showing inconsistency between implementations too: [4](#0-3) 

### Impact Explanation
Whether this is exploitable hinges entirely on whether the descriptor/schema validation layer (trusted per the threat model) *guarantees* that every extension registered against a message with `message_set_wire_format = true` is always type `TYPE_MESSAGE`. If that invariant is enforced at `.proto` compile time / descriptor-pool build time for *all* extensions that can be found via `FindExtension` for a MessageSet-typed extendee, then `extension.type` can never be anything but `TYPE_MESSAGE` when this code path is reached, and the missing runtime check is unreachable by an attacker sending only wire bytes — it would be dead code protecting against corrupt/malicious schemas, which are out of scope. I was not able to fully confirm from the retrieved code whether this invariant is enforced universally across all extension-registration paths (dynamic extension registries built at runtime, cross-file extension registration, or `DescriptorPool` construction from untrusted `FileDescriptorProto` — which is explicitly out of scope per the rules) versus only for statically compiled/generated extensions. Given the tool's read-only access and the exclusion of "hostile schema" scenarios, I cannot produce a concrete, schema-trusted, wire-bytes-only proof of a type confusion via this specific missing check.

### Likelihood Explanation
Low-to-unknown under the stated threat model (ordinary client sending bounded binary protobuf to a public parse API, with trusted schemas/registries). If schema/extension-registration validity guarantees `extension.type == TYPE_MESSAGE` for every extension reachable via `FindExtension` on a MessageSet extendee, this asymmetry is not attacker-triggerable with a fixed, valid schema — it is a defense-in-depth check present in one code path (the general extension parser) and absent in a structurally similar sibling path, but never actually exercised differently for a given valid deployment.

### Recommendation
For defense-in-depth and consistency with the general extension-parsing path, add an explicit check in `ExtensionSet::ParseMessageSetItemTmpl` (and the reflection-based `WireFormat::MessageSetParser::ParseElement`) that `extension.type == WireFormatLite::TYPE_MESSAGE` (and not repeated, since MessageSet items are singular) before dereferencing `extension.message_info.class_data`/`extension.descriptor` as message metadata, mirroring the check already performed by `FindExtensionInfoFromFieldNumber` for the general path. If such an extension is found but is not a message type, treat it the same as "not found" (route the raw bytes to unknown fields) rather than assuming message semantics.

### Proof of Concept
I was unable to construct a concrete, schema-trusted, bounded-wire-bytes proof of concept that demonstrates observable type confusion, because doing so would require either (a) a schema in which an extension is legitimately registered against a `message_set_wire_format` extendee but is not of `TYPE_MESSAGE` — which appears to be prevented by descriptor validation for statically compiled schemas (out of scope to attack per the rules excluding hostile schemas) — or (b) manipulating the extension registry at runtime, which is excluded as internal API misuse. No local reproduction was run; this finding should be treated as an asymmetric-validation code-quality/defense-in-depth issue rather than a proven exploitable vulnerability, pending confirmation from the Protobuf security team on whether all `FindExtension`-reachable extensions for MessageSet extendees are guaranteed by construction to be `TYPE_MESSAGE`.
