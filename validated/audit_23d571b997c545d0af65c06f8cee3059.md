### Title
Cached FROST preprocess is never consumed/invalidated, enabling deterministic nonce reuse and key-share recovery on protocol retry — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The vm2 escape is a bug-class where a spec-conforming mechanism (Proxy) unexpectedly instantiates a privileged host object. The Serai analog is `SigningProtocol::preprocess_internal`: a spec-conforming cache lookup unexpectedly re-instantiates a *live signing machine* (`AlgorithmSignMachine::from_cache`) from a persistent seed every time it runs. The cached seed is written once and never cleared after `sign()` consumes it, so any retry of `share_internal` under the same context deterministically regenerates the same FROST nonces and produces a second signature share — the classic nonce-reuse path to key-share recovery, reachable by an unprivileged co-signer supplying preprocesses.

### Finding Description
`preprocess_internal` generates a `CachedPreprocess` seed the first time a `context` is seen and stores it XOR-encrypted in `CachedPreprocesses` (`signing_protocol.rs:123-135`). On every subsequent call — including the call inside `share_internal` (`signing_protocol.rs:156`) — it decrypts the same seed and rebuilds the signing machine via `AlgorithmSignMachine::from_cache` (`signing_protocol.rs:144-145`). Inside `seeded_preprocess`, that seed deterministically instantiates `ChaCha20Rng`, from which the FROST nonces are derived (`crypto/frost/src/sign.rs:127-132`). There is no code path that deletes or rotates `CachedPreprocesses` after `machine.sign(preprocesses, msg)` succeeds or fails (`signing_protocol.rs:170`). The FROST docs in-tree acknowledge that reusing a preprocess "will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`) and that each new attempt must obtain a fresh seed (`spec/cryptography/FROST.md:57-60`), yet the persistence layer guarantees the same seed is returned for the same context forever.

### Impact Explanation
A signature share is `s = d + (ρ·e) + λ·c·x_i` where `d, e` are the seed-derived nonces. If `share_internal` is invoked twice for the same context — e.g., a first attempt aborts after shares are broadcast (an invalid/missing share from a peer triggers `FrostError` and the attempt is retried), or the processor reboots between rounds and re-runs the share step for the same `(session, id, attempt)` context — the same `d, e` are used with a different binding factor set / challenge `c`. Any party holding both shares recovers `x_i` via `(s₁ − s₂) / (λ(c₁ − c₂))`. Recovery of one participant's share reduces the effective threshold; combined with `t−1` colluding-free public inputs this directly enables forging signatures under the group key.

### Likelihood Explanation
The vulnerability requires the same signing context to reach the share phase twice, which occurs on fault-triggered retries and reboot-resume paths the code explicitly handles (`handle` in `processor/src/batch_signer.rs:226-233` re-reads persisted machines after reboot). Because the seed persists in `CachedPreprocesses` and is keyed only by `context`, any re-execution deterministically reuses nonces — no attacker influence over randomness is needed; a malicious participant only needs to force an abort (e.g., submit an invalid share/preprocess, `signing_protocol.rs:170-178`) and participate in the retry. I was unable to confirm whether `context` encodes the attempt counter; if it does not, retries under the same `(session, id)` definitively reuse nonces. If `context` already includes `attempt`, the residual risk is confined to same-attempt re-execution paths, which the reboot-resume code suggests exist.

### Recommendation
Consume the cached preprocess on use: delete `CachedPreprocesses[context]` (or write a tombstone) inside `preprocess_internal` after building the machine, so a retry regenerates a fresh seed via `AlgorithmMachine::preprocess(&mut OsRng)`. Alternatively, derive the seed as `H(secret ‖ context ‖ attempt ‖ retry_counter)` where `retry_counter` is monotonically incremented per `share_internal` call, guaranteeing nonce freshness without relying on deletion ordering.

    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
