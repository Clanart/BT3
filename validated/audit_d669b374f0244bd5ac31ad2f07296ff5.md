## Root Cause

`Kip71GasTarget` uses `noopFormatChecker` (no validation) while its sibling `Kip71BaseFeeDenominator` explicitly rejects zero: [1](#0-0) 

```go
Kip71BaseFeeDenominator: {
    ...
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
},
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: noopFormatChecker,
    ...
},
```

This means a governance vote (or contract-based governance) setting `kip71.gastarget` to `0` is accepted without error. `KIP71Config.GasTarget` is then used unguarded as a divisor in `NextMagmaBlockBaseFee`, unlike `BaseFeeDenominator`, which has an explicit `== 0` fallback: [2](#0-1) 

```go
var baseFeeDenominator *big.Int
if kc.BaseFeeDenominator == 0 {
    baseFeeDenominator = new(big.Int).SetUint64(64)   // guarded
} else {
    baseFeeDenominator = new(big.Int).SetUint64(kc.BaseFeeDenominator)
}
gasTarget := kc.GasTarget          // NOT guarded against zero
...
if parentGasUsed == gasTarget {
    return makeEvenByFloor(parentBaseFee)
} else if parentGasUsed > gasTarget {
    ...
    y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // divide by GasTarget
    ...
} else {
    ...
    y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // divide by GasTarget
    ...
}
```

If `GasTarget == 0` and any block has `parentGasUsed > 0` (virtually every real block), the code hits `x.Div(x, big.NewInt(0))`, which is a `big.Int` division-by-zero panic — the same bug class as GoPro's `GPMF_ScaledData()` unguarded division in CVE-2020-16161.

`NextMagmaBlockBaseFee` is invoked from `VerifyMagmaHeader`, called during header validation for every block after the Magma/KIP-71 fork: [3](#0-2) 

## Reachability

Governance parameters are explicitly in scope per the rules. `Kip71GasTarget` is a votable governance parameter (see `kaiax/gov/headergov` vote handling and `kaiax/gov/param.go` `Params` map), and its `FormatChecker` is the only server-side gate before the value is written into `ChainConfig`/`KIP71Config` and used by every node computing/verifying the next block's base fee. Because `BaseFeeDenominator` was deliberately hardened against a zero value but `GasTarget` was not, this is a real, asymmetric validation gap rather than a hypothetical.

### Title
Missing zero-check on KIP-71 `GasTarget` governance parameter causes division-by-zero panic in base fee calculation - (File: params/kip71_config.go)

### Summary
The `kip71.gastarget` governance parameter is accepted with `noopFormatChecker` (no validation), allowing it to be set to `0`. `KIP71Config.NextMagmaBlockBaseFee` (called by `VerifyMagmaHeader` on every block after Magma fork) divides by `GasTarget` without a zero-guard, unlike the adjacent `BaseFeeDenominator` field which is explicitly protected. A `GasTarget` of `0` causes a `big.Int` division-by-zero panic on the very next block that uses any gas.

### Finding Description
`Params[Kip71GasTarget]` in [4](#0-3)  uses `FormatChecker: noopFormatChecker`, so any `uint64` value including `0` is accepted as a valid vote/parameter value. This value flows into `ChainConfig.Governance.KIP71.GasTarget` and is consumed unguarded by `NextMagmaBlockBaseFee` in [5](#0-4) , where it is used as a `big.Int` divisor (`x.Div(x, new(big.Int).SetUint64(gasTarget))`) in both the "gas used above target" and "gas used below target" branches. There is no analogous zero-fallback as exists for `BaseFeeDenominator`.

### Impact Explanation
Every node computing or verifying block headers after the Magma/KIP-71 fork calls `VerifyMagmaHeader` → `NextMagmaBlockBaseFee`. Once `GasTarget=0` is committed via governance, the very next block containing any gas usage (`parentGasUsed != 0`, i.e., virtually every block) triggers `parentGasUsed > gasTarget`, entering the division-by-zero branch and panicking. This crashes block production and header verification network-wide — a full chain halt, not merely a single node's DoS — since all honest nodes execute the identical deterministic code path.

### Likelihood Explanation
Governance parameter changes to `kip71.gastarget` go through the standard header-vote or contract-governance mechanism already exercised in this codebase (see `kaiax/gov/headergov` vote tests). Because the `FormatChecker` for this specific parameter performs no validation, the value `0` passes silently through canonicalization and format checking, and would only be discovered when the resulting base-fee calculation actually executes on-chain.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`, `Kip71LowerBoundBaseFee`, `Kip71UpperBoundBaseFee`, which also currently use `noopFormatChecker`) that rejects `0`, mirroring the `v != 0` check already used for `Kip71BaseFeeDenominator`. Additionally, add a defensive zero-guard directly in `NextMagmaBlockBaseFee` around the `gasTarget` divisor, consistent with the existing `BaseFeeDenominator == 0` fallback, to prevent a panic even if an invalid value reaches this function via any other path (e.g., stale chain config, genesis misconfiguration).

### Proof of Concept
1. Submit a governance vote (or contract-governance parameter update) setting `kip71.gastarget = 0`. It passes `Params[Kip71GasTarget].FormatChecker` (`noopFormatChecker` always returns `true`) and is applied to `ChainConfig.Governance.KIP71.GasTarget`.
2. On the next block after the Magma fork with any nonzero gas usage, `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` is invoked with `kc.GasTarget = 0`.
3. Since `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit) > 0 = gasTarget`, execution enters the `parentGasUsed > gasTarget` branch and calls `x.Div(x, new(big.Int).SetUint64(0))`, which panics with "division by zero" in Go's `math/big`.
4. This panic occurs in `VerifyMagmaHeader`, called during header validation on every node — halting block validation/production chain-wide.
