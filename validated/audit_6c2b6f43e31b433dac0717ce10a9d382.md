### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes megabyte-scale allocation from a ~12-byte input, enabling memory/allocator-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
The bug class from CVE-2024-0115 — uncontrolled resource consumption reachable by an unprivileged party feeding untrusted bytes into a long-running process — maps onto `ThresholdKeys::<C>::read` in `crypto/dkg`. The deserializer trusts the attacker-supplied `n` field and immediately performs `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector before validating `n` against `t`/`i` or against the actual bytes present. A handful of input bytes therefore forces a ~2 MiB allocation per call; repeated calls on a network-facing deserialization path consume memory bandwidth and heap without bound.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s from the reader with no sanity check (validation via `ThresholdParams::new` happens only at the very end of the function). When the next tag byte is `0` (`Interpolation::Constant`), it executes `Vec::with_capacity(usize::from(n))` where `n` is fully attacker-controlled up to 65,535:

```rust
// crypto/dkg/src/lib.rs:604-616
let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  _ => Err(io::Error::other("invalid interpolation method"))?,
};
``` [1](#0-0) 

The total input required to trigger the allocation is `4 + C::ID.len() + 6 + 1` bytes (≈ 12 bytes for a typical `ID`): the curve-ID check is satisfiable with publicly known constants, and `Participant::new(i)` only rejects `i == 0`. With `n = 0xFFFF`, `Vec::with_capacity` reserves `65,535 × size_of::<C::F>()` — roughly 2 MiB for a 32-byte scalar — before the first `read_F` fails on a truncated stream. The error is returned, but the allocation already happened, and nothing limits how many times a remote peer can repeat this on a connection that feeds arbitrary bytes to `ThresholdKeys::read`. This mirrors CVE-2024-0115's shape: parsing of attacker-controlled length fields drives resource consumption disproportionate to input size.

### Impact Explanation
Any service that deserializes `ThresholdKeys` from untrusted input (key-import endpoints, message payloads) lets an unauthenticated peer spend ~12 bytes of bandwidth to force a ~2 MiB heap allocation plus the subsequent drop/zeroing work per call — an amplification factor in the hundreds of thousands. A sustained stream of such messages causes allocator pressure, memory exhaustion, and denial of service of the signing/validator process, matching the CVE's impact (DoS, availability loss) without requiring any valid keys, signatures, or threshold participation.

### Likelihood Explanation
Reachability is direct: `read_F`/`ThresholdKeys::read` are explicitly in the enumerated untrusted-byte entry points, and the vulnerable `with_capacity` executes before any cryptographic or structural validation of `n`. The only constraint is `i != 0`, which is trivially satisfied. Exploitation requires only the ability to deliver a byte stream to the deserializer — no participation in DKG, no authentication, no malformed crypto. Severity is Medium: memory consumption is bounded per call (~2 MiB) and the vector is freed on error, so the impact is sustained-amplification DoS rather than a single-shot OOM.

### Recommendation
Validate `n` (and `t`) before allocating: enforce `1 <= t <= n <= MAX_PARTICIPANTS` immediately after reading the header, and avoid `with_capacity(n)` — either push into an empty `Vec` or cap the pre-allocation with a small constant. The same ordering check should be applied to the `verification_shares` loop (`for l in (1 ..= n)` at line 621), which currently loops `n` times performing `read_G` for attacker-chosen `n`.

### Proof of Concept
```rust
// Pseudo-PoC against crypto/dkg ThresholdKeys::<C>::read
let mut bytes = Vec::new();
bytes.extend(&(C::ID.len() as u32).to_le_bytes()); // id_len
bytes.extend(C::ID);                              // correct public curve ID
bytes.extend(&u16::MAX.to_le_bytes());            // t
bytes.extend(&u16::MAX.to_le_bytes());            // n = 65535
bytes.extend(&1u16.to_le_bytes());                // i (valid, non-zero)
bytes.push(0);                                    // Interpolation::Constant
// No further bytes: with_capacity(65535) has already run when read_F fails
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
// Each ~12-byte invocation allocates ~2 MiB (65535 * 32-byte scalar capacity)
```
