## Analysis

The report's core broken invariant: **checking only that a call did not revert, rather than verifying the actual ERC20 boolean return value, causes silent transfer failures.** In Wild Credit's `TransferHelper`, the bug caused the opposite problem (an unwanted revert on non-standard tokens), but the underlying flaw — not properly interpreting an ERC20 token's return value — has a mirror-image, more dangerous variant that appears live in Hyperbridge's Tron deployment of `IntentGatewayV2`.

The canonical EVM `IntentsBase._withdraw` correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and validates the ERC20 return value: [1](#0-0) 

But the Tron-specific fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, reimplements this logic with a raw low-level `.call()` that only checks the boolean `success` returned by the call itself — never decoding or validating the actual ABI-encoded return value of `transfer()`: [2](#0-1) 

The same unchecked pattern recurs in the `SweepDust` handler and the tx-fee redemption path: [3](#0-2) [4](#0-3) 

### Title
Unchecked ERC20 return value in Tron `IntentGatewayV2.withdraw()` permanently finalizes escrow release/refund even when the token transfer silently fails - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` moves escrowed input tokens to a beneficiary using `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only reverts if the raw `.call()` itself reverted (`!success`). It never decodes/validates the boolean payload that ERC20 `transfer()` is supposed to return. Any TRC20/ERC20 token that returns `false` on failure instead of reverting — the standard-compliant legacy pattern still used by numerous tokens deployed on Tron/EVM chains — will make `success == true` at the call site while zero tokens actually moved.

### Finding Description
`withdraw()` is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests, which are the terminal step of intent settlement after a cross-chain fill or cancellation is authenticated via ISMP proof. Before performing the transfer it unconditionally marks the order finalized (`_filled[body.commitment] = beneficiary`) and, after the (unchecked) transfer, decrements the escrow ledger (`_orders[body.commitment][token] -= amount`). Both of these state mutations execute regardless of whether the token actually delivered funds, because the guard `if (!success) revert TransferFailed();` only detects reverts, not a `false` boolean return.

This diverges from the shared base contract `IntentsBase._withdraw`, which correctly relies on `SafeERC20.safeTransfer` to validate the return value. The Tron fork's reimplementation dropped that safety net while reusing the exact bytes of raw `.call()` + `abi.encodeWithSelector` construction that WildCredit's `TransferHelper` used — just with the return-value check removed instead of it being present-but-decoding-incorrectly.

### Impact Explanation
Because `_filled` and `_orders` are updated as if the transfer succeeded, a beneficiary interacting with a non-compliant (false-returning) token loses their escrowed funds permanently: the commitment is marked filled/refunded so it can never be retried, and the escrow accounting shows the balance as already paid out, even though the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path pointing back to them. This is a direct loss-of-funds / false-state-acceptance condition reachable by any unprivileged solver or user who settles an order denominated in such a token — no malicious relayer, prover, or admin is required.

### Likelihood Explanation
The path is reached through the standard, unprivileged `RedeemEscrow`/`RefundEscrow` flow that every solver or refunding user goes through after a normal cross-chain fill or timeout/cancellation. It requires no privileged role and is triggered purely by the destination/output token's implementation returning `false` on failure — a well-known ERC20 non-compliance pattern (the same class the original report targeted for USDT-style tokens), which is plausible for arbitrary tokens listed in an intents marketplace.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()`, the `SweepDust` branch of `onAccept`, and the tx-fee redemption block with OpenZeppelin's `SafeERC20.safeTransfer`, matching the implementation already used in `IntentsBase._withdraw`. This decodes and enforces the boolean return value (or absence of one) correctly and reverts the whole transaction — including the `_filled`/`_orders` state updates — if the underlying transfer did not actually succeed.

### Proof of Concept
1. Deploy or use an ERC20/TRC20 token whose `transfer()` returns `false` on failure rather than reverting (e.g., a token that returns `false` when the recipient is blacklisted, or when balance bookkeeping fails for some edge case) as an order's input token.
2. A user places an order via `placeOrder`, escrowing this token in `IntentGatewayV2`; `_orders[commitment][token]` is credited.
3. A solver fills the order cross-chain; Hyperbridge later delivers a `RedeemEscrow` request that is authenticated and passed to `withdraw()`.
4. Craft/trigger the condition under which the token's `transfer()` returns `false` for this specific payout (e.g., the beneficiary is on the token's internal blacklist, or the contract enforces a policy check that fails silently).
5. `token.call(...)` returns `success = true` (no revert) with return data encoding `false`; the code does not inspect this data, so `TransferFailed` is never raised.
6. `_orders[body.commitment][token] -= amount` executes, zeroing the escrow record, and `_filled[body.commitment]` is set — the order is now permanently finalized.
7. No tokens were actually delivered to the beneficiary; they remain trapped in the `IntentGatewayV2` contract with no state pointing to them, resulting in permanent loss of the escrowed funds.
