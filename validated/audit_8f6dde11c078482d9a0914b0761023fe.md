### Title
Panic on unregistered participant index in PedPoP blame/decryption path enables remote crash DoS - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` performs a `HashMap` index (`self.enc_keys[&decryptor]`) without checking that the participant index was registered. A blame accusation naming an out-of-range recipient (any nonzero `u16` `Participant` not in `1..=n`) causes a panic — the Rust analog of the CVE-2004-0079 null-dereference crash: an attacker-controlled handshake/protocol value reaches a code path that dereferences a non-existent object and aborts the process.

### Finding Description
In `Decryption::decrypt_with_proof`, the ECDH public key for the alleged decryptor is looked up by unchecked indexing:

- `crypto/dkg/pedpop/src/encryption.rs:388`: `&[self.enc_keys[&decryptor], *proof.key]` panics (`HashMap` index) if `decryptor` never registered an encryption key.

The same pattern exists in `Encryption::encrypt` at `crypto/dkg/pedpop/src/encryption.rs:466` (`self.decryption.enc_keys[&participant]`) and in `BlameMachine::blame_internal` at `crypto/dkg/pedpop/src/lib.rs:599` (`self.commitments[&sender]`).

The public entry points `BlameMachine::blame` (`crypto/dkg/pedpop/src/lib.rs:623`) and `AdditionalBlameMachine::blame` (`crypto/dkg/pedpop/src/lib.rs:674`) accept `sender` and `recipient` as arbitrary `Participant` values derived from an accusation message supplied by another DKG party. `blame_internal` calls `decrypt_with_proof(sender, recipient, msg, proof)` with `decryptor = recipient` before any range check on `recipient` against `params.n()`. A `Participant` can be any nonzero `u16` (`Participant::new` only rejects zero, per `crypto/dkg/src/lib.rs`), so `recipient = n+1` is constructible and is never present in `enc_keys`, which is only populated for `1..=n` during `verify_r1`/`AdditionalBlameMachine::new`. Result: `index` panic on a missing key — an abort of the node/validator process handling the blame message, triggered purely by bytes/indexes an unprivileged counterparty controls.

### Impact Explanation
Any participant in a PedPoP DKG (or anyone able to submit a blame statement evaluated by `AdditionalBlameMachine`, which is explicitly usable by non-members) can crash the process evaluating the accusation by choosing an out-of-range `sender`/`recipient`. Since DKG validators are consensus-critical, a panic aborts key generation and can halt the multisig/protocol — a remote denial of service analogous to the OpenSSL crash, with the panic reached before the message's cryptographic validity is even checked.

### Likelihood Explanation
Triggering requires only sending/relaying a blame accusation whose `recipient` (or `sender`) field encodes a participant index outside `1..=n`, together with an `EncryptedMessage` whose PoP signature verifies for `from = sender`... Note: `decrypt_with_proof` first verifies `msg.pop` with `from = sender`; however the panic on `self.enc_keys[&decryptor]` occurs at line 388 only after a valid PoP — an attacker who controls any registered participant's encryption key can craft a valid `EncryptedMessage` (self-encrypted) satisfying the PoP, then name an unregistered `recipient`. A malicious DKG participant (normal threat model for blame evaluation) therefore reaches the panic deterministically.

### Recommendation
Replace `HashMap` indexing with fallible lookups that return a blame/invalid-participant error: use `self.enc_keys.get(&decryptor)` and `self.commitments.get(&sender)`/`get(&l)` in `decrypt_with_proof`, `blame_internal`, `encrypt`, and `calculate_share`, and validate `sender`/`recipient` against `params.all_participant_indexes()` in `blame`/`blame_internal` before use.

    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty

      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
