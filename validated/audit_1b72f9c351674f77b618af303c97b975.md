### Title
Tron `IntentGatewayV2.withdraw()`/`SweepDust` use raw `token.call(transfer.selector)` and only check call success, not the ERC20 boolean return value — silent transfer failures still finalize escrow release - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
This is the local Hyperbridge analog of the C4 "safeTransfer is not implemented correctly" bug class. The external report's core broken invariant is: *a function named/labelled as performing a "safe" transfer omits the check that actually validates the transfer outcome, so state is finalized as if the transfer succeeded even when it didn't reach the intended party.* In Hyperbridge's Tron variant of `IntentGatewayV2`, the escrow-release path (`withdraw()`) and the governance dust-sweep path both replace OpenZeppelin's `SafeERC20.safeTransfer` (used everywhere else in the codebase, e.g. `IntentsBase.sol` and the main EVM `IntentGatewayV2.sol`) with a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only inspect the outer `success` boolean of the call itself, never decoding/validating the ERC20 contract's returned `bool` value.

### Finding Description
`SafeERC20.safeTransfer`/`safeTransferFrom` (used consistently in `evm/src/apps/intentsv2/IntentsBase.sol` [1](#0-0)  and `evm/src/apps/IntentGatewayV2.sol`) is safe precisely because it both (a) requires the external call to not revert, and (b) if return data is present, decodes and requires it to be `true` — this is required because many ERC20 tokens (older/non-compliant implementations) return `false` on failure instead of reverting.

The Tron port of the same protocol drops this second check. In `withdraw()`: [2](#0-1) 
the escrowed-token transfer is performed via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the low-level call itself reverted — it does not reflect whether the token contract's `transfer()` returned `true` or `false`. For any ERC20 token that signals failure by returning `false` (rather than reverting), this call succeeds at the EVM level while the actual token balance of `beneficiary` never changes. Despite this, the very next lines commit state as if the transfer succeeded:
```solidity
_orders[body.commitment][token] -= amount;
```
and, at the top of the same function, `_filled[body.commitment] = beneficiary;` is set unconditionally [3](#0-2) . The escrow accounting is decremented and the order is marked filled/finalized before or regardless of any real verification that the tokens landed with the beneficiary.

The same unchecked-return-value pattern also appears in the governance-triggered `SweepDust` handler inside `onAccept`: [4](#0-3) 
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
```
followed by `emit DustSwept(...)` regardless of the token's actual boolean return value.

This is a direct structural analog to the ParaSpace bug: a "safe"-sounding transfer/withdrawal routine that is missing the guard that would actually detect an unsuccessful transfer, letting the contract commit irreversible state (escrow decrement, `_filled` marking, `EscrowReleased`/`EscrowRefunded` events) as though funds were correctly delivered.

### Impact Explanation
If any escrowed input token used by the Tron `IntentGatewayV2` deployment is a non-standard ERC20 that returns `false` instead of reverting on transfer failure (a well-documented real-world token behavior class), the beneficiary receives nothing while:
- `_orders[commitment][token]` is permanently decremented (escrow accounting believes funds were paid out),
- `_filled[commitment]` is set, permanently blocking any retry/withdrawal/refund path for that order,
- `EscrowReleased`/`EscrowRefunded` fires, signalling success to off-chain systems/relayers.

The result is a genuine, unrecoverable loss of the user's or solver's escrowed funds — the tokens remain stuck in the gateway contract with no code path left to claim them, since the order is already marked as settled. This falls squarely under "stealing or loss of funds" for the Intent Gateway's bridge custody/escrow logic, reachable by any unprivileged party whose order or fill happens to use such a token — no malicious relayer, prover, or admin is required; the trigger condition is purely the choice of token used in the order.

### Likelihood Explanation
This requires a token whose `transfer()` can return `false` without reverting to be used as an order's input/output/fee token. This is a real-world token category (some proxy/legacy tokens), not merely theoretical, but it does depend on the deployer/solver's choice of supported tokens on the Tron deployment; the main EVM contracts already defend against this via `SafeERC20`, showing that the protocol itself considers this a real threat model it otherwise guards against everywhere except this Tron variant. The likelihood is therefore moderate: it requires a specific token property but no privileged actor or off-chain compromise.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`, `SweepDust` handling, and any other outbound transfer path in that file) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, consistent with the main EVM `IntentGatewayV2.sol` and `IntentsBase.sol` implementations, so that both call-success and boolean-return-value are validated before escrow state is finalized.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with an ERC20 token whose `transfer()` implementation returns `false` (instead of reverting) under some failure condition (e.g., paused state, blacklist, insufficient internal allowance edge case) while otherwise passing normal integration checks used at order placement.
2. A user places an order with this token as an input, escrowing funds via `placeOrder` (standard path uses `safeTransferFrom`, so escrow can be funded normally in the token's non-failure state).
3. Trigger a condition that later causes `transfer()` to return `false` for the beneficiary address during `withdraw()` (e.g., beneficiary becomes blacklisted, or contract enters a state where transfer silently no-ops and returns false).
4. Call the path that invokes `withdraw()` (`onAccept` for `RedeemEscrow`/`RefundEscrow`, or `onGetResponse` for cancellation) — `token.call(...)` returns `success = true` (the call itself doesn't revert) even though the token's internal `bool` return is `false` and no balance moved.
5. Observe: `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, `EscrowReleased`/`EscrowRefunded` is emitted — yet `beneficiary`'s token balance is unchanged. The escrowed tokens remain stuck in the gateway with no further code path to claim them, since the order is already finalized.
