### Title
ReferralStorage.updateTotalFactor is not called from VLMGP.cancelUnlock/unlock/forceUnLock, permanently desynchronizing `userInfos[account].factor` from `totalBoostFactor` - (File: rewards/ReferralStorage.sol)

### Finding Description
`updateTotalFactor()` recomputes a user's referral boost factor as `sqrt(getUserTotalLocked(account))` and updates the shared `totalBoostFactor` accordingly: [1](#0-0) 

It is invoked from `VLMGP._lock` (via `lock`/`lockFor`) and from `VLMGP.startUnlock`: [2](#0-1) 

but it is **not** called from `unlock()`, `cancelUnlock()`, or `forceUnLock()`: [3](#0-2) 

Tracing the actual effect on `getUserTotalLocked` (which excludes amounts currently in a cooldown slot, `_amountInMasterMagpie - getUserAmountInCoolDown`): [4](#0-3) 

- `unlock()` and `forceUnLock()` only finalize a slot that was already moved into cooldown by a prior `startUnlock()` call — at that time `getUserTotalLocked` was already reduced and `updateTotalFactor` was already invoked, so no further real balance change occurs at `unlock`/`forceUnLock` time. These two omissions do not introduce a real accounting drift.
- `cancelUnlock()`, however, does introduce a genuine drift: it removes an amount from `totalAmountInCoolDown` and zeroes `slot.amountInCoolDown`, which **increases** the user's real `getUserTotalLocked` (the funds return to being counted as locked) — but it never calls `updateTotalFactor`. The user's stored `factor` (and thus `totalBoostFactor`) stays frozen at the lower, cooldown-reduced value even though the real locked balance is restored to the higher pre-cooldown amount.

Because `totalBoostFactor` is a shared global denominator used by every referrer in `_calBoosted`: [5](#0-4) 

an artificially low `totalBoostFactor` (caused by repeated lock → startUnlock(partial) → cancelUnlock cycles by any unprivileged user, since `lockFor`/`startUnlock`/`cancelUnlock` are all permissionless) inflates `basic + boosted` percentages for all active referrers in `trigger()`: [6](#0-5) 

There is no cap ensuring `refererPercentage + refereePercentage <= DENOMINATOR`, so a persistently understated `totalBoostFactor` can push aggregate referral payouts above the intended share of `_amount`, paid out of the `MGP` balance held by `ReferralStorage` and released via `claimReward()`: [7](#0-6) 

This over-allocation is funded from the shared MGP balance and therefore comes at the expense of other referrers/referees who claim later — i.e., theft/misallocation of unclaimed yield.

### Impact Explanation
An unprivileged attacker (any address, since `lockFor`, `startUnlock`, and `cancelUnlock` require no special role) can permanently desynchronize the shared `totalBoostFactor` denominator downward relative to the true sum of participants' real locked-balance-derived factors, by repeatedly: locking MGP, partially `startUnlock`-ing (correctly reduces `factor`/`totalBoostFactor`), then `cancelUnlock`-ing (restores real locked balance but never restores `factor`/`totalBoostFactor`). This causes `_calBoosted` to over-report boosted percentages for referrers system-wide, inflating `refererAmount`/`refereeAmount` credited in `trigger()` beyond the intended share of `_amount`, ultimately allowing more real MGP to be drained via `claimReward()` than the reward pool logic intends — matching Immunefi "High - Theft of unclaimed yield."

### Likelihood Explanation
The precondition is minimal: the attacker only needs `myCode != bytes32(0)` (register a referral code via `registerCode`), then lock MGP via `lock`/`lockFor`, call `startUnlock` for part of the position, and then `cancelUnlock` that same slot — all permissionless entrypoints, repeatable indefinitely at low gas cost (no capital loss, since MGP is never actually withdrawn during the cycle). This is fully attacker-controlled and requires no admin/oracle assistance and no specific `sharePercent` value (sharePercent only shifts the split between referrer/referee, not whether the exploit is triggerable).

### Recommendation
Call `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` inside `cancelUnlock()` (and, defensively, inside `unlock()` and `forceUnLock()` as well, to remove any implicit reliance on `startUnlock` having been called beforehand) in `VLMGP.sol`, so that every state-changing path that affects `getUserTotalLocked` refreshes the referral boost factor and the shared `totalBoostFactor` denominator. Additionally, add an explicit cap in `ReferralStorage.trigger()` ensuring `refererPercentage + refereePercentage <= DENOMINATOR` as defense in depth.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, mock `MasterMagpie`/`MGP` token; wire `referralStorage` into `VLMGP` and `vlMGP`/`masterMagpie` into `ReferralStorage`.
2. Attacker calls `registerCode(code)` on `ReferralStorage`, then a second account uses that code via `useCode` so `trigger()` has a non-zero path.
3. Attacker calls `lock(A)` on `VLMGP` — assert `userInfos[attacker].factor == sqrt(A)` and `totalBoostFactor == sqrt(A)`.
4. Attacker calls `startUnlock(A)` (full amount) — assert `updateTotalFactor` fired, `userInfos[attacker].factor == 0`, `totalBoostFactor == 0`.
5. Attacker calls `cancelUnlock(slotIndex)` — assert `getUserTotalLocked(attacker) == A` again (real balance restored) but `userInfos[attacker].factor` and `totalBoostFactor` remain `0` (stale/desynced), violating the invariant `userInfos[account].factor == sqrt(getUserTotalLocked(account))`.
6. Repeat steps 4-5 across multiple accounts/cycles to drive `totalBoostFactor` toward 0 while multiple accounts hold nonzero real locked balances; call `masterMagpie`-triggered `trigger()` and show `refererPercentage + refereePercentage` computed in `_calBoosted`-driven math exceeds `DENOMINATOR`, and that cumulative `rewardAmount` credited across referrers exceeds the `_amount` passed into `trigger()`, then show `claimReward()` transfers real MGP reflecting this over-allocation, exceeding what the reward pool should have paid.
