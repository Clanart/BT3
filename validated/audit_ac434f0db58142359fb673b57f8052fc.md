### Title
Missing protocol allow-list in `open-external` IPC handler allows arbitrary scheme execution via `shell.openExternal` - (File: `app/src/main-process/main.ts`)

### Summary
`viewOnGitHub()` passes `getGitHubHtmlUrl(repository)` — which is ultimately sourced from the GitHub API's `html_url` field — to `dispatcher.openInBrowser()`, which flows through `AppStore._openInBrowser` → `shell.openExternal` (renderer proxy) → the `open-external` IPC channel → `ipcMain.handle('open-external', ...)` in the main process. That main-process handler does **not** enforce an http/https allow-list; it only logs when the URL starts with `http://`/`https://` and then unconditionally calls `shell.openExternal(path)` regardless of scheme.

### Finding Description
1. `viewOnGitHub` in `app/src/ui/app.tsx` computes `url = getGitHubHtmlUrl(repository)` and calls `dispatcher.openInBrowser(url)` with no scheme validation. [1](#0-0) 
2. `getGitHubHtmlUrl` returns `GitHubRepository.htmlURL` directly, with no format/protocol validation. [2](#0-1) 
3. `htmlURL` is populated straight from the GitHub API response's `html_url` field when a repository is upserted into the local DB, with no scheme check. [3](#0-2) 
4. `AppStore._openInBrowser` forwards the raw URL to `shell.openExternal`. [4](#0-3) 
5. The renderer's `shell.openExternal` is a thin IPC proxy (`invokeProxy('open-external', 1)`) with no client-side validation. [5](#0-4) 
6. Critically, the main-process handler that actually performs the privileged `shell.openExternal` call does not gate on scheme at all — the http/https check only controls a `log.info` call, and `shell.openExternal(path)` executes unconditionally for any input: [6](#0-5) 

So for the specific scenario in the question — an attacker-influenced (e.g. malicious/MITM'd GitHub Enterprise) API response setting `html_url` to `file:///etc/passwd` or a custom URI scheme — the value would indeed reach `shell.openExternal` unmodified, because there is no enforcement point anywhere in this call chain, not even the one that superficially looks like an allow-list in `main.ts`.

### Impact Explanation
`shell.openExternal` with a `file://` URL opens the local file with the OS default handler (e.g., could open an executable, or via crafted extension trigger a "protocol/handler" invocation chain in some environments), and a custom URI scheme (e.g., `ms-officecmd:`, `outlook:`, or others registered on the victim's OS) could invoke third-party protocol handlers with attacker-influenced input, which has historically led to code execution in several disclosed Electron-app/OS protocol-handler chained vulnerabilities. This matches the "corruption of the http/https-only invariant" concern, and the sink is reachable with attacker-controlled data (a GitHub API repository object) without any local access, admin rights, or unnatural user steps beyond clicking the normal "View on GitHub" menu/button.

### Likelihood Explanation
Reaching this sink requires the GitHub API response (or GitHub Enterprise Server response, which a user might configure to point to an attacker-controlled/MITM'd host) for a repository to return a non-`http(s)` value in `html_url`. This is plausible for a malicious GHE server the user has been socially engineered into adding as an account endpoint, or a MITM position against an HTTP-only or misconfigured GHE deployment. It's not exploitable from a fully honest, TLS-pinned github.com session, so likelihood is bounded by the attacker's ability to control the API response content for a repository the user has added to Desktop.

### Recommendation
Add real scheme validation in the `open-external` IPC handler in `app/src/main-process/main.ts` — reject (return `false` without calling `shell.openExternal`) for any URL that does not start with `http://` or `https://`, rather than only logging. This centralizes protection at the trust boundary (the main process) regardless of which renderer code path constructs the URL, closing this and any similar call sites (`viewOnGitHub`, `openIssueCreationPage`, `_openCreatePullRequestInBrowser`, `onViewBranchOnGitHub`, `LinkButton`, markdown link handlers, etc.) that all funnel through this single IPC channel.

2. This value is persisted via `_upsertGitHubRepository` into `GitHubRepository.htmlURL`. [7](#0-6)

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)

    }
