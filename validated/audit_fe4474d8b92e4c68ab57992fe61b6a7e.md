### Title
Stale cached FROST preprocess reused across validator sets — deterministic nonce reuse enables private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
CVE-2019-13233 is a race/use-after-free where state is consumed after the object it refers to has effectively been replaced. The analog in Serai is the `CachedPreprocesses` table: `SigningProtocol::preprocess_internal` derives a one-time-use FROST preprocess seed from a DB entry keyed only by `context`, which for `DkgConfirmer` is `(b"DkgConfirmer", attempt)` — notably omitting the tributary `genesis`/validator-set identity. The entry is never deleted and `from_cache` deterministically regenerates the same nonces. When a new DKG begins for a subsequent validator set, `attempt` restarts at the same small values, so `("DkgConfirmer", 0)` resolves to the *stale* seed generated for a previous set — a use-after-(logically)-consumed preprocess.

### Finding Description
`preprocess_internal` stores a seeded-RNG cache entry under `self.context` and reuses it whenever the key exists (`coordinator/src/tributary/signing_protocol.rs:123-145`). For the DKG confirmation signer, the context is exactly `(b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:275`). The `create_db!` declaration `CachedPreprocesses: (context: &impl Encode) -> [u8; 32]` (`signing_protocol.rs:88`) contains no `genesis` or set component, unlike neighboring tables (`DataDb`, `ConfirmationNonces`, `DkgKeyPair`) which are all keyed by genesis. Since `AttemptDb` is keyed per `(genesis, topic)`, a new validator set's DKG restarts at `attempt = 0`, producing an identical `context` while the MuSig keys (`musig(musig_context(self.spec.set().into()), ...)`) and the signed message (`set_keys_message(self.spec.set(), ...)`) differ.

`AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`) feeds the cached 32-byte seed into `ChaCha20Rng`, so identical seed ⇒ identical nonce scalars `d, e` and identical commitments. `share_internal`/`share`/`complete` all route through `preprocess_internal` (`signing_protocol.rs:150-181, 288-327`), so each confirmation signs `set_keys_message` for a *different* key pair/set with the same FROST nonces. The file's own safety argument (`signing_protocol.rs:25-48`) relies solely on messages being fixed under BFT *within* an attempt; it never considers the same context string recurring across sets.

### Impact Explanation
FROST signature shares have the form `z_i = d_i + (e_i · b_i · ρ_i) + λ_i · s_i · c` where `d_i, e_i` are the secret nonces and `s_i` is the long-lived private key share. The preprocesses (hence every participant's binding factors `ρ_i`) and the shares are published on the public tributary. With the nonces pinned to a reused seed, each new set's confirmation adds one more linear equation over the same unknowns (`d_i`, `e_i`, and `s_i`/`λ_i·s_i` for that set's key). After enough confirmations reusing `("DkgConfirmer", k)` contexts, the system is overdetermined and the validator's private key share — the root-of-trust key used to authorize `set_keys` on Substrate — is recoverable by any observer. This matches the documented consequence of preprocess reuse: "Reuse will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`).

### Likelihood Explanation
Exploitation requires no malicious validator, collusion, or BFT failure: it triggers on the ordinary protocol event of a second validator-set DKG (set rotation/removal), since `attempt` resets while `CachedPreprocesses` persists across the shared coordinator DB. Recovery requires multiple reused-context signatures to pin down all unknowns; a single reuse may only leak partial nonce information, so severity is bounded by how often contexts collide (once per attempt index per set). The shares and preprocesses needed are public tributary data, so an unprivileged observer can perform the recovery offline.

### Recommendation
Include the validator-set identity in the cache context, e.g. `let context = (b"DkgConfirmer", self.spec.genesis(), self.attempt)` (and key `CachedPreprocesses` by `(genesis, context)`), matching the scoping used by `DataDb`/`ConfirmationNonces`. Additionally, after `share_internal` successfully signs for a context, delete or tombstone the `CachedPreprocesses` entry so a logically consumed preprocess can never be reloaded, and have `from_cache`/consumers assert the entry was removed.

### Proof of Concept
```rust
// Pseudocode over coordinator DB state
// Set A (genesis_A): DKG attempt 0 completes
let confirmer_a = DkgConfirmer::new(key, spec_a, txn, 0).unwrap();
confirmer_a.share(preprocesses_a, &key_pair_a); // writes CachedPreprocesses[("DkgConfirmer", 0)]
// ... time passes, set rotation ...
// Set B (genesis_B): DKG attempt 0 completes
let confirmer_b = DkgConfirmer::new(key, spec_b, txn, 0).unwrap();
// context == ("DkgConfirmer", 0) again -> CachedPreprocesses::get returns the
// stale seed; line 123's `is_none()` check fails, so NO new seed is generated.
confirmer_b.share(preprocesses_b, &key_pair_b); // same d_i, e_i; different msg
// Observer collects share_a, share_b (+ preprocesses_a/b for rho_i) from the
// public tributary and solves the linear system for key share s_i.
```

Uncertainty: this assumes the coordinator's `serai_db` instance (and thus `CachedPreprocesses`) is shared across tributary specs/sets rather than per-set; the table declarations and `txn` threading are consistent with a shared DB, but I could not fully verify DB instantiation. If each set receives a fresh database, the collision — and the finding — does not hold.
