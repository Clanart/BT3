The external report's class — value committed by a caller that is not accounted for against the declared amount, so the leftover is diverted — maps onto `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`, where the OP_RETURN `data` output is pushed into `tx_outs` but is never included in the weight/vbytes calculation used to derive `needed_fee`, so the created transaction commits more bytes than the fee it pays for.

### Title
OP_RETURN data output excluded from weight/fee calculation causes underpaid fee and unbroadcastable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying `data` to the transaction's outputs, but both calls to `calculate_weight_vbytes` build the weight-estimation transaction solely from `payments` (plus optional `change`). The OP_RETURN output's bytes are therefore never counted, so `needed_fee = fee_per_vbyte * vbytes` undercharges. The transaction ends up paying a lower effective fee rate than requested — potentially below `DEFAULT_MIN_RELAY_TX_FEE` — making it unrelayable while still being constructed and signed.

### Finding Description
At `send.rs:194-202` the OP_RETURN output is pushed onto `tx_outs` before the weight calculation. At `send.rs:204` and `send.rs:225-226`, `calculate_weight_vbytes` is called with `payments` and `change` only; internally (`send.rs:85-99`) it builds a `Transaction` whose `output` vector contains only payment outputs plus an optional change output — the OP_RETURN output is absent. With up to 80 bytes of data (`send.rs:171`), the missing output contributes roughly 90 vbytes (8-byte value, script length, `OP_RETURN` + push of up to 80 bytes) that are never priced.

Two consequences follow:

1. `needed_fee` (`send.rs:206`, and `fee_with_change` at `send.rs:227`) is computed against an understated vsize, so the actual paid fee rate `(inputs - outputs) / actual_vsize` is lower than `fee_per_vbyte`.
2. The minimum-relay-fee guard at `send.rs:211` also uses the understated `vbytes`, so it cannot catch the shortfall: a transaction that is actually below the minimum relay rate passes the check.

When `change` is specified, the change output at `send.rs:228-233` absorbs the difference (change is oversized relative to intent), so the deficit manifests purely as an underpaid fee. `SignableTransaction::fee()` (`send.rs:138-141`) will report an actual fee equal to `needed_fee`, but the real vsize is larger than the `vbytes` used, so the realized fee rate is lower than `fee_per_vbyte`. For a `fee_per_vbyte` near the protocol minimum (~1 sat/vbyte), the realized rate drops below `DEFAULT_MIN_RELAY_TX_FEE` and the signed transaction is rejected by Bitcoin relay — the inputs' funds are committed to a plan that cannot confirm.

This mirrors the report's root cause: a caller supplies a parameter (`data`) whose cost is committed to the artifact but never charged against the amount/fees declared, with the unaccounted value silently redirected (here, from the intended fee into change, or producing a non-standard transaction).

### Impact Explanation
Any use of `SignableTransaction::new` with `data` (OP_RETURN payloads carry Serai `InInstruction` metadata) produces a transaction whose fee rate is strictly below the caller-specified `fee_per_vbyte`. At moderate fee rates this silently degrades confirmation priority; at low rates it produces a transaction the network refuses to relay, locking the selected inputs in a plan that can never complete — funds effectively frozen until abandoned, exactly the "value committed but not correctly accounted" failure mode of the reference bug.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some` — it requires no adversarial control beyond passing a data payload to the public constructor, and is reachable by any integrator invoking the in-scope `networks/bitcoin/src/wallet` send API with an OP_RETURN. The miscalculation is structural (the estimation transaction simply never includes the output), not probabilistic.

### Recommendation
Include the OP_RETURN output in the weight estimation: build the estimation `Transaction`'s `output` vector from `tx_outs` (or pass `data` into `calculate_weight_vbytes` and push the OP_RETURN output there), so `vbytes`/`vbytes_with_change` reflect the final transaction. Additionally, consider asserting `self.fee()` meets the intended rate for the real `tx.vsize()` after construction.
