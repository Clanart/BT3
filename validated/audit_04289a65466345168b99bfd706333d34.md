## Title
`git clone --recursive` explicitly disables Git's submodule-hook clone protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling remote-code-execution via malicious `.gitmodules`/embedded-`.git` payloads — (File: `app/src/lib/git/clone.ts`)

### Summary
Every clone performed by Desktop runs `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` hard-coded to `'false'`. [1](#0-0) 
`GIT_CLONE_PROTECTION_ACTIVE` is the upstream Git kill-switch introduced (Git 2.45.1 / CVE-2024-32002 fix family) to stop a clone/recursive-submodule-checkout from executing hooks placed by a hostile repository (e.g. a submodule whose worktree contains a symlinked or case-confused `.git` that clobbers the hooks directory of the superproject, or a `.gitmodules` file that points a submodule to a path/URL crafted to run code during checkout). Git ships with this protection **on by default**; Desktop explicitly forces it off for every single clone, including clones of arbitrary, attacker-controlled remote URLs typed or clicked by the user (deep links / "Clone repository" dialog / `openrepo` URL actions in `app/src/lib/parse-app-url.ts`).

### Finding Description
The broken invariant, translated from the ERC777/`depositCap` report, is: *a guard that is supposed to prevent an attacker-influenced side effect from happening is bypassed because the calling code deliberately disables it before invoking the vulnerable primitive.* In the original report, `depositCap` is checked but the reentrant callback (attacker-controlled) runs before the check's effects are finalized. Here, the analogous "guard" is Git's own `GIT_CLONE_PROTECTION_ACTIVE` check, and Desktop does not merely fail to add a missing guard — it actively flips the guard off for a code path that:
- always runs `--recursive` (`args.push(... 'clone', '--recursive' ...)`), so any submodules present in an attacker-controlled repository are cloned and checked out automatically without further user confirmation, and
- receives its remote URL from data that the attacker controls, since `clone()` is invoked for URLs coming from `open-repository-from-url` deep-link actions parsed in `app/src/lib/parse-app-url.ts` as well as from the normal clone-URL dialog. [2](#0-1) 

Because the protection is disabled, the class of attacks it was created to close (submodule/embedded-repo content causing hook or config-driven code execution as a *side effect of cloning*) is not mitigated by anything else in this call path: there is no separate check in `clone()` for hostile `.gitmodules` entries, no sandboxing of the recursive submodule checkout, and no confirmation prompt before the recursive clone proceeds. The only other check present, `isClonePathSensitive`, only validates the *destination path* on the local filesystem and has nothing to do with content coming from the remote repository itself. [3](#0-2) 

This mirrors the reentrancy bug class at the "broken invariant" level: a security check that exists specifically to stop an attacker-supplied object (submodule/repo content) from causing unauthorized effects (code execution during checkout) is turned off right at the point where the attacker-supplied object is processed (`clone --recursive`), which is exactly the "existing guards do not stop the path" requirement — because the app has explicitly removed the guard rather than merely omitted a check.

### Impact Explanation
If exploitable, this allows an attacker who controls a repository URL that the victim clones (via the Clone dialog, a shared URL, or a `x-github-client://openrepo/...` deep link) to have code executed as a side effect of the clone/recursive-submodule-checkout — this is remote code execution triggered purely by an unprivileged, attacker-controlled repository/URL, matching the "attacker controls a cloned/fetched repository" and "code execution" categories from the valid-impact list.

### Likelihood Explanation
Likelihood is high for triggering conditions (any user cloning an untrusted URL) but the actual exploitability depends on details this index cannot confirm: whether the bundled `dugite`/Git version still contains a code path that `GIT_CLONE_PROTECTION_ACTIVE=false` meaningfully re-enables (i.e., whether the underlying CVE-class bug was otherwise fixed upstream regardless of this flag), and whether other layers (e.g. Git's `protocol.allow`, symlink protections on the OS, or `core.hooksPath` template guards) still block the specific hook-execution primitive. I could not find any comment, test, or changelog entry in this repository explaining *why* the flag is force-disabled, which is itself notable — it suggests this may be an unintentional/leftover override (possibly meant only for CI or a specific edge case) rather than a deliberate, reviewed security decision.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally. Only disable Git's clone protection (if it must be disabled at all) for provably trusted/local operations, and otherwise leave Git's default (enabled) protection in place for all `clone --recursive` calls that process attacker-supplied URLs/content. If the override exists to work around a specific compatibility issue, scope it narrowly and document the justification, and add a regression test asserting the flag is not disabled for user-initiated/deep-link clones.

### Proof of Concept
Not independently reproduced in this environment (no terminal/Git binary access here). Based on static code review:
1. A victim clicks/enters a malicious repository URL (e.g., via `x-github-client://openrepo/<attacker-url>` handled by `parseAppURL`/`dispatchURLAction`, or via the normal Clone-repository UI).
2. Desktop calls `clone(url, path, options, progressCallback)`.
3. `clone()` builds the environment with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and always passes `--recursive`. [1](#0-0) 
4. Git performs the clone and recursively checks out submodules defined in the attacker's `.gitmodules`/tree with Git's built-in clone-protection check disabled, which is the exact scenario that upstream protection flag exists to prevent.

I could not confirm end-to-end exploitability against the specific `dugite`/Git version vendored in this repo (that would require running `git --version` and testing an actual malicious submodule payload, which is outside the scope of static code search). This should be verified with a live Devin session that can build and run the app against a crafted malicious repository.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
