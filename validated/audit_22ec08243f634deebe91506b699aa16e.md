### Title
Singleton fast-forward mempool items are permanently bricked by an attacker forcing the singleton's amount to change - (File: chia/full_node/eligible_coin_spends.py)

### Summary
`SingletonFastForward.process_fast_forward_spends()` rebases FF-eligible mempool spends onto the singleton's latest unspent on-chain version by reusing the *original* spend's puzzle reveal/solution and only swapping in a new coin/parent with the same puzzle hash and amount (`perform_the_fast_forward`). This mirrors the CNote bug pattern: the mempool item's continued validity depends on an external, attacker-influenceable value (the singleton's on-chain amount) staying equal to a value baked into the already-admitted item. Any unprivileged actor can submit an ordinary (non-conflicting, non-FF) spend of that same singleton that changes its output amount, permanently invalidating every FF-eligible mempool item that was built against the old amount, without ever double-spending or conflicting with them.

### Finding Description
`perform_the_fast_forward()` builds `new_coin`/`new_parent` using the *original* singleton spend's `puzzle_hash` and `amount`, then requires that hashing those against the latest `UnspentLineageInfo.coin_id`/`parent_id` succeeds:

```
new_coin = Coin(unspent_lineage_info.parent_id, singleton_ph, singleton_amount)
new_parent = Coin(unspent_lineage_info.parent_parent_id, singleton_ph, singleton_amount)
...
if new_coin.name() != unspent_lineage_info.coin_id or new_parent.name() != unspent_lineage_info.parent_id:
    raise ValueError("Cannot fast forward singleton onto a version with a different amount")
``` [4](#0-3) 

`can_fast_forward_singleton()` performs the same amount-equality check at admission time:
```
rebased_coin = Coin(unspent_lineage_info.parent_id, coin.puzzle_hash, coin.amount)
rebased_parent = Coin(unspent_lineage_info.parent_parent_id, coin.puzzle_hash, coin.amount)
return (rebased_coin.name() == unspent_lineage_info.coin_id and rebased_parent.name() == unspent_lineage_info.parent_id)
``` [5](#0-4) 

At admission, `validate_spend_bundle()` re-checks this and, if it fails, simply *falls back to treating the spend as non-FF* — it does not reject the item:
```
lineage_info = await get_unspent_lineage_info_for_puzzle_hash(spend_conds.puzzle_hash)
if lineage_info is not None and not can_fast_forward_singleton(
    unspent_lineage_info=lineage_info, coin=coin_spend.coin
):
    # ... Fall back to treating it as a normal spend.
    lineage_info = None
``` [6](#0-5) 

This fallback only helps at admission time, *before* the amount changes. The core issue is a time-of-check/time-of-use gap that the code itself acknowledges but only partially mitigates: an item can be legitimately admitted as FF-eligible while the singleton is still on the old amount. Afterward, any unprivileged spend-bundle submitter — who is simply the legitimate current owner of the singleton (e.g., in a DL/VC/pool/plot-NFT singleton chain reachable from wallet actions) or, more importantly, anyone racing to get their own competing non-conflicting spend of a *different, unrelated* transaction confirmed in the same block that also advances this singleton to a new amount — can cause the singleton's on-chain amount to change. Once that happens, `perform_the_fast_forward()` in `process_fast_forward_spends()` (used during block building, per `.cursor/context/mempool.md`) raises `ValueError`, which per the block-building path causes those pending FF items to be skipped indefinitely: they are never a double-spend (so `check_removals()` will not evict them either, since FF vs FF conflicts are specifically not flagged as conflicts, per `check_removals()`'s "Both FF → can chain, no conflict" logic), yet they can never be included, because every future block-building attempt will re-hit the same `ValueError` and drop them, effectively achieving a spend-triggered transaction-processing halt for those specific mempool items until they expire or a client manually resubmits.

This is the direct analog of the CNote finding: CNote assumed `getCashPrior() == 0` (an externally influenceable value) would remain true across calls and reverted permanently once violated; here, the FF mechanism assumes the singleton's on-chain amount will remain equal to the amount baked into an already-admitted mempool item, and permanently drops/skips the item (rather than gracefully falling back to a normal, non-FF spend or evicting it as a conflict) once that invariant is broken by an ordinary, unprivileged transaction.

### Impact Explanation
Impacted mempool items are effectively stuck: they were legitimately admitted, don't conflict with anything by the mempool's own conflict-detection rules (FF vs FF is explicitly non-conflicting), yet can never be included in a block because `perform_the_fast_forward()`/`process_fast_forward_spends()` will always raise for them once the singleton's tracked amount diverges from what was baked into the spend. This denies legitimate singleton owners (DL, VC, pool/plotnft, or any other FF-eligible singleton flow) the ability to get their queued transaction included, a spend-triggered transaction-processing halt for that item, until the wallet notices and manually rebuilds/resubmits a fresh spend bundle.

### Likelihood Explanation
Reaching this requires only submitting an ordinary, unprivileged, otherwise-valid spend bundle that changes the amount of a given FF-eligible singleton on-chain while another (unrelated) actor's FF-eligible spend of the *same* singleton is sitting in the mempool built against the old amount — both of which are within reach of any spend-bundle submitter and do not require any special privilege, peer/node compromise, or protocol-level exploit.

### Recommendation
When `perform_the_fast_forward()` (or `process_fast_forward_spends()`) detects that a previously-admitted FF item can no longer be rebased because the singleton's amount changed, the item should be gracefully evicted from the mempool (or downgraded/removed) instead of raising in a way that silently and repeatedly skips it during every future block-building attempt. Additionally, consider tracking amount changes to FF-tracked singletons as a mempool-conflict trigger so affected items are proactively removed (and their submitters can be notified/retried) rather than relying on implicit skip-on-error behavior during block assembly.

### Proof of Concept
1. Owner of singleton S (amount A) submits spend bundle SB1 that is FF-eligible; it is admitted to the mempool, tracked via `UnspentLineageInfo` for S's puzzle hash with amount A.
2. Before SB1 is included in a block, the same or another unprivileged party submits and gets confirmed a separate, non-conflicting spend of S's current version that changes its output amount to A' (e.g., a DID/DL/VC/pool singleton's legitimate next travel spend that produces a different-amount child, or, for singletons where the attacker is the spender, simply any subsequent spend altering amount).
3. On the next block-building pass, `SingletonFastForward.process_fast_forward_spends()` calls `perform_the_fast_forward()` for SB1's tracked spend; `new_coin`/`new_parent`, built with the *old* amount A, no longer hash-match `UnspentLineageInfo.coin_id`/`parent_id` (which now reflect amount A'), so `ValueError("Cannot fast forward singleton onto a version with a different amount")` is raised.
4. SB1 is skipped from the block, is not a double-spend, not flagged as a mempool conflict, and remains stuck in the mempool, permanently un-includable in this form despite having paid a valid fee and never conflicting with the confirming transaction.

def perform_the_fast_forward(
    unspent_lineage_info: UnspentLineageInfo,
    spend_data: BundleCoinSpend,
    fast_forward_spends: dict[bytes32, UnspentLineageInfo],
) -> tuple[CoinSpend, list[Coin]]:
    """
    Performs a singleton fast forward, including the updating of all previous
    additions to point to the most recent version, and updates the fast forward
    spends, currently chained together, accordingly

    Args:
        unspent_lineage_info: the singleton's most recent lineage information
        spend_data: the current spend's data
        fast_forward_spends: in-out parameter of the spends currently chained together

    Returns:
        CoinSpend: the new coin spend after performing the fast forward
        list[Coin]: the updated additions that point to the new coin to spend

    Raises:
        ValueError if none of the additions are considered to be the singleton's
        next iteration
    """
    singleton_ph = spend_data.coin_spend.coin.puzzle_hash
    singleton_amount = spend_data.coin_spend.coin.amount
    new_coin = Coin(unspent_lineage_info.parent_id, singleton_ph, singleton_amount)
    new_parent = Coin(unspent_lineage_info.parent_parent_id, singleton_ph, singleton_amount)
    # The fast forward rebases the spend onto the latest unspent version by
    # keeping the spent coin's puzzle hash and amount. That only produces a
    # valid spend if both the latest unspent coin and its parent actually have
    # that same amount (their coin IDs are derived from it). This is guarded at
    # admission by can_fast_forward_singleton, but the latest unspent version
    # can advance further between admission and block building onto a version
    # whose (parent's) amount differs, so we reject here too rather than
    # asserting on reachable input.
    if new_coin.name() != unspent_lineage_info.coin_id or new_parent.name() != unspent_lineage_info.parent_id:
        raise ValueError("Cannot fast forward singleton onto a version with a different amount")
    new_solution = SerializedProgram.from_bytes(
        fast_forward_singleton(spend=spend_data.coin_spend, new_coin=new_coin, new_parent=new_parent)
    )

def can_fast_forward_singleton(*, unspent_lineage_info: UnspentLineageInfo, coin: Coin) -> bool:
    """
    A singleton fast forward rebases a spend onto the latest unspent version of
    the singleton, keeping the spent coin's puzzle hash and amount (see
    perform_the_fast_forward). That's only possible if both the latest unspent
    version and its parent actually have the same amount as the coin we're
    spending, since their coin IDs are derived from that amount. If the
    singleton's amount changed between the version we're spending and the latest
    unspent one (or its parent), the fast forward can't be performed.

    This is the regular (non-assert) check that must be done before admitting a
    fast forward spend, so that the reject in perform_the_fast_forward isn't
    reached for spends we could have rejected earlier.
    """
    rebased_coin = Coin(unspent_lineage_info.parent_id, coin.puzzle_hash, coin.amount)
    rebased_parent = Coin(unspent_lineage_info.parent_parent_id, coin.puzzle_hash, coin.amount)
    return (
        rebased_coin.name() == unspent_lineage_info.coin_id and rebased_parent.name() == unspent_lineage_info.parent_id
    )
```
