### Title
Missing payout-value binding in `bridge_circuit` allows a reused withdrawal signature to authorize a zero-payout, fee-only transaction that still qualifies for full Reimburse - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` only checks that the input at `payout_input_index` spends `(user_wd_outpoint, vout)` and that an OP_RETURN carrying a valid `operator_xonlypk` exists somewhere in the payout transaction's outputs; it never checks that any output actually delivers value to the withdrawer. Because the withdrawal input is signed with `SinglePlusAnyoneCanPay`, which only binds the output at the *same index* as the signed input, an operator who controls the final transaction layout can place the OP_RETURN at that index instead of the user payout output, reusing the withdrawer's existing signature to produce a transaction that pays nothing to any wallet while still satisfying every check in `bridge_circuit`.

### Finding Description
Binding claimed: `sum(value delivered to non-miner outputs of accepted payout tx) == withdrawal amount owed`.

Trace of `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs): [1](#0-0) 
only asserts the previous-output txid/vout of `input[payout_input_index]` equals the storage-proof-derived withdrawal outpoint/vout, and [2](#0-1) 
only asserts that some OP_RETURN output anywhere in the transaction carries a valid `operator_xonlypk`. There is no check anywhere in `bridge_circuit`, `verify_storage_proofs` (`circuits-lib/src/bridge_circuit/storage_proof.rs`), or `deposit_constant`/`journal_hash` that a specific output value or script pays out to the withdrawer, and `verify_storage_proofs` itself never reads/commits an amount at all — only `wd_outpoint`, `vout`, and `move_txid` are returned. [3](#0-2) 

The intended binding is instead delegated entirely to the Bitcoin signature: the withdrawer signs the payout input with `SinglePlusAnyoneCanPay` [4](#0-3) 
which, per BIP-341/consensus semantics of `SIGHASH_SINGLE`, only commits the *output at the same index as the signed input*. The operator constructs the transaction with the payout output first and the OP_RETURN last: [5](#0-4) 
but nothing in the protocol or in `bridge_circuit` enforces that this ordering (payout output at the signed input's index) is preserved. An operator (or a colluding withdrawer/operator pair) can reorder the outputs so the OP_RETURN sits at the same index as the withdrawal input and omit the real payout output entirely. The withdrawer's original `SinglePlusAnyoneCanPay` signature remains valid for this restructured transaction because it only binds output index == input index, which is now the OP_RETURN (value 0, script = operator pubkey push). The remaining input value (and any operator-added funding) can be routed entirely to miner fees. `bridge_circuit` will still: match `input[payout_input_index].previous_output` to the stored withdrawal outpoint/vout, find a syntactically valid OP_RETURN with the correct `operator_xonlypk`, pass SPV/LCP/storage checks (none of which reference amount), and commit a valid `journal_hash`.

Once this proof/commitment exists, the reimbursement path pays the operator the full deposit amount unconditionally, independent of what the payout transaction actually delivered: [6](#0-5) 
There is no verifier-side check (`Verifier::is_kickoff_malicious`, disprove machinery) described in the codebase that re-derives "did the withdrawer actually get paid" from the payout transaction; the entire disprove path relies on `bridge_circuit`'s output being correct, and `bridge_circuit` does not encode a payout-amount/output check.

### Impact Explanation
An operator can front a peg-out with zero real payout (all value to fees or to the operator's own change), obtain a valid `bridge_circuit` proof, and later collect the full move-to-vault amount via `Reimburse`, matching the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." This is repeatable for every deposit/withdrawal handled by any dishonest or colluding operator, since the missing check is structural (in the circuit logic itself, not per-deposit configuration), and blast radius extends to all operators and all deposits using the standard payout flow.

### Likelihood Explanation
Preconditions: the attacker/colluding party must control (or collude with) the operator that fronts the payout, since it is the operator's node that assembles and broadcasts the final Bitcoin transaction (via `fund_raw_transaction`/`sign_raw_transaction_with_wallet` in `core/src/operator.rs`). A withdrawer alone cannot force this reordering because they do not control transaction assembly; however, a dishonest operator holding a validly obtained withdrawal signature can always restructure the transaction before broadcast, since bitcoind will happily sign/relay a transaction where only the sighash-covered bytes are fixed and everything else (output ordering, extra outputs, extra inputs) is free under `ANYONECANPAY`. No mainnet or live Citrea state is needed to demonstrate this at the circuit level — a `cargo test` constructing such a payout transaction and its SPV/storage proof stubs is sufficient to show `bridge_circuit` still succeeds.

### Recommendation
In `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs), explicitly verify that the output at the index corresponding to `payout_input_index` under the withdrawer's committed sighash scheme is the actual payout output (correct script pubkey/value bound to the withdrawal), or otherwise commit the payout output's value/script into the storage proof and cross-check it against the payout transaction, rather than relying solely on off-chain Bitcoin signature semantics that permit output reordering under `ANYONECANPAY`.
