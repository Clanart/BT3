## Answer

The premise is directionally correct, but the exact PoC needs a correction: a bare `.gitattributes` filter driver alone cannot invoke an arbitrary command unless that filter is already registered in the victim's `git config` (filters are configured via `filter.<name>.clean`/`filter.<name>.smudge`, which live in `.git/config`/global config — not in the versioned `.gitattributes` file, so an attacker-controlled repo cannot introduce a brand-new filter command by itself). The realistic exploitation path is Git LFS's repo-tracked `.lfsconfig` file, which *can* set `[lfs] url = ssh://attacker-host/...` and is honored automatically by the pre-existing, commonly-installed LFS `clean`/`smudge` filter — no local pre-configuration of a custom filter is required beyond having Git LFS installed (extremely common). That LFS process then shells out to `ssh` to negotiate the LFS SSH endpoint.

The core architectural finding holds regardless of which filter mechanism is used to reach `ssh`:

### Title
Trampoline SSH-host-authenticity prompt is applied indiscriminately to any subprocess spawned during a git operation (including LFS/filter drivers), and `AddSSHHost` never discloses the triggering context - (File: `app/src/ui/ssh/add-ssh-host.tsx`)

### Summary
GitHub Desktop wraps **every** `git` invocation — not just explicit clone/fetch/push — with `withTrampolineEnv`, which unconditionally sets `SSH_ASKPASS`, `DISPLAY`, and (in some configurations) `GIT_SSH_COMMAND` in the child process environment. [1](#0-0)  These environment variables are inherited by any subprocess `git` spawns, including filter/clean/smudge drivers (e.g., Git LFS), which is explicitly called out in the code comments as intentional: "we want commands invoked by filters (i.e. Git LFS) to be able to pick up our configuration." [2](#0-1)  Because `DISPLAY` is forced non-empty, any `ssh` invocation made by such a filter (e.g., Git LFS talking to a repo-declared `ssh://` LFS endpoint from `.lfsconfig`) that encounters an unknown host key will use `SSH_ASKPASS` rather than a TTY prompt, routing straight into `createAskpassTrampolineHandler` → `handleSSHHostAuthenticity`. [3](#0-2) [4](#0-3) 

That handler, if the host isn't `github.com`, unconditionally opens the `AddSSHHost` dialog via `trampolineUIHelper.promptAddingSSHHost`. [5](#0-4)  The dialog component and its backing `PopupType.AddSSHHost` payload only carry `host`, `ip`, `keyType`, and `fingerprint` — there is no field describing which git operation (checkout, fetch, LFS smudge, etc.) triggered the prompt. [6](#0-5) [7](#0-6)  The rendered dialog text is generic ("The authenticity of host '...' can't be established... Are you sure you want to continue connecting?") with no indication that the connection was initiated indirectly by repository content rather than a direct clone/fetch/push against the repo's configured remote. [8](#0-7) 

### Impact Explanation
A user who opens/checks out an attacker-supplied repository can be presented with an SSH host-key trust prompt for an arbitrary attacker-controlled host with no indication that it originates from repo-defined filter machinery rather than the trusted remote they intended to interact with. If accepted, the host key is pinned exactly (`EXACT_VALUE`) into `known_hosts`, and network traffic (potentially including SSH auth attempts) is directed at the attacker endpoint — all triggered merely by checking out/fetching content, not by any deliberate remote operation the user chose.

### Likelihood Explanation
This requires only that the victim has Git LFS installed (very common) and clones/fetches a repository containing a malicious `.lfsconfig` pointing at an `ssh://` endpoint under attacker control, plus LFS-tracked content that triggers the smudge/clean path. No explicit `.gitattributes → arbitrary shell command` path exists without a pre-existing local filter definition, so the exact PoC framing in the question ("a `.gitattributes` filter driver calling `ssh`") is not directly reachable purely from repo content; the LFS `.lfsconfig` vector is the realistic equivalent.

### Recommendation
- Propagate the originating operation/context (e.g., "clone", "fetch", "LFS smudge for path X") through the trampoline token metadata into `handleSSHHostAuthenticity` and surface it in `AddSSHHost` so users can distinguish a direct remote connection from an indirect one triggered by repository-declared tooling. [4](#0-3) 
- Consider treating SSH host-authenticity prompts arising from filter-driver subprocesses (LFS `.lfsconfig`-declared hosts, custom filters) with heightened scrutiny or a distinct, more explicit warning, since these hosts are effectively attacker-chosen via repository content.

### Proof of Concept
1. Create a repository with an `.lfsconfig` file setting `[lfs] url = ssh://attacker-controlled-host/repo.git`.
2. Add an LFS-tracked file (`.gitattributes` with `filter=lfs`) and commit a pointer file.
3. Have the victim clone/fetch the repo in GitHub Desktop with Git LFS installed; the LFS smudge/clean filter shells out to `ssh` against `attacker-controlled-host`, which is not in `known_hosts`.
4. Because `SSH_ASKPASS`/`DISPLAY` are globally set by `withTrampolineEnv` for all git subprocesses, the resulting host-authenticity prompt is routed to Desktop's `AddSSHHost` dialog, which shows only host/IP/fingerprint with no mention that the prompt was triggered by an LFS filter rather than the actual git remote.

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })

async function handleSSHHostAuthenticity(
  operationGUID: string,
  prompt: string
): Promise<'yes' | 'no' | undefined> {
  const info = parseAddSSHHostPrompt(prompt)

  if (info === null) {
    return undefined
  }

  // We'll accept github.com as valid host automatically. GitHub's public key
  // fingerprint can be obtained from
  // https://docs.github.com/en/github/authenticating-to-github/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints
  if (
    info.host === 'github.com' &&
    info.keyType === 'RSA' &&
    info.fingerprint === 'SHA256:nThbg6kXUpJWGl7E1IGOCspRomTxdCARLviKw6E5SY8'
  ) {
    return 'yes'
  }

  if (getIsBackgroundTaskEnvironment(operationGUID)) {
    log.debug(
      'handleSSHHostAuthenticity: background task environment, skipping prompt'
    )
    return undefined
  }

  const addHost = await trampolineUIHelper.promptAddingSSHHost(
    info.host,
    info.ip,
    info.keyType,
    info.fingerprint
  )
  return addHost ? 'yes' : 'no'
}

export const createAskpassTrampolineHandler: (
  accountsStore: AccountsStore
) => TrampolineCommandHandler =
  (accountsStore: AccountsStore) => async command => {
    if (command.parameters.length !== 1) {
      return undefined
    }

    const firstParameter = command.parameters[0]

    if (firstParameter.startsWith('The authenticity of host ')) {
      return handleSSHHostAuthenticity(command.trampolineToken, firstParameter)
    }

    if (firstParameter.startsWith('Enter passphrase for key ')) {
      return handleSSHKeyPassphrase(command.trampolineToken, firstParameter)
    }

    if (firstParameter.endsWith("'s password: ")) {
      return handleSSHUserPassword(command.trampolineToken, firstParameter)
    }

    return undefined
  }
