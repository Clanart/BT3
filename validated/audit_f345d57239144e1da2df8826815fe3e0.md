Confirmed: `multiclaimSpec` and `multiclaimFor` are ordinary-wallet-reachable entry points that let any user call `_multiClaim()` with a non-empty `_rewardTokens` array per pool, which routes into `BaseRewardPool.getRewards()` — a function whose body is entirely empty.

### Title
Base rewarder's `getRewards()` is a stub that never pays out selected bonus rewards, permanently freezing users' base-reward-pool token earnings claimed via `multiclaimSpec`/`multiclaimFor` - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool.getReward(_account, _receiver)` correctly computes and transfers all accrued reward tokens to a user. However, the sibling function `getRewards(_account, _receiver, _rewardTokens)`, which is meant to let a user claim a specific subset of reward tokens, has an empty function body and performs no computation, no state update, and no token transfer. [1](#0-0) 

### Finding Description
`MasterMagpie._claimBaseRewarder()` dispatches to the rewarder based on whether the caller supplied specific reward tokens: if `_rewardTokens.length > 0` it calls `rewarder.getRewards(...)`, otherwise it calls `rewarder.getReward(...)`. [2](#0-1) 

Any ordinary wallet can trigger the broken path directly through `multiclaimSpec()` or `multiclaimFor()`, both of which accept an arbitrary `address[][] _rewardTokens` argument per staking pool and forward it unmodified into `_multiClaim()` → `_claimBaseRewarder()` → `getRewards()`. [3](#0-2) [4](#0-3) 

Because `BaseRewardPool.getRewards()` is empty, when a user calls this path the transaction succeeds silently: no `RewardPaid` event is emitted, no `IERC20.safeTransfer` occurs, and no reward-tracking state (`userRewards`, `userRewardPerTokenPaid`) is updated (the `updateReward` modifier used on `getReward` is absent from `getRewards`). This mirrors the root cause pattern in the reference report: a profit/reward amount is correctly tracked and accrued at the protocol level, but the code path responsible for actually paying it out to depositors is missing. [5](#0-4) 

### Impact Explanation
Reward tokens that a user attempts to claim through `multiclaimSpec`/`multiclaimFor` for any pool using the (non-V2) `BaseRewardPool` rewarder are never transferred to the user in that call, even though the pool has legitimately queued and accrued those rewards via `queueNewRewards`/`donateRewards`. Since `IBaseRewardPool` is used generically across pools by `MasterMagpie`, any deployment wiring a plain `BaseRewardPool` (as opposed to `BaseRewardPoolV2`, `vlMGPBaseRewarder`, or `mWOMSVBaseRewarder`, all of which implement `getRewards` correctly) as a pool's rewarder is affected: unprivileged users lose the ability to claim specific reward tokens through this documented, user-facing entry point, and no revert alerts them to the failure. [6](#0-5) 

### Likelihood Explanation
This is triggered purely by an unprivileged wallet calling a standard, documented public function (`multiclaimSpec` or `multiclaimFor`) with a non-empty reward token list — no special preconditions, roles, or external protocol state are required.

### Recommendation
Implement `getRewards()` in `BaseRewardPool.sol` analogous to `BaseRewardPoolV2.getRewards()`: apply `updateReward(_account)`, iterate over the supplied `_rewardTokens`, zero out `userRewards[token][_account]`, and `safeTransfer` the reward to `_receiver`, emitting `RewardPaid` for each. [7](#0-6) 

### Proof of Concept
1. A pool in `MasterMagpie` is configured with a `BaseRewardPool` (not `BaseRewardPoolV2`) rewarder that has multiple registered reward tokens with non-zero accrued balances for a user, established via `queueNewRewards`. [8](#0-7) 
2. The user calls `MasterMagpie.multiclaimSpec([stakingToken], [[rewardTokenA]])` (or `multiclaimFor`) specifying a subset of reward tokens for that pool. [9](#0-8) 
3. This routes to `BaseRewardPool.getRewards(user, receiver, [rewardTokenA])`, whose body is empty — the transaction returns successfully but `rewardTokenA` is never transferred and internal reward-tracking mappings are untouched. [5](#0-4) 
4. The user receives zero tokens for that claim call despite having a legitimately accrued balance, with no on-chain revert or event indicating failure.

        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
