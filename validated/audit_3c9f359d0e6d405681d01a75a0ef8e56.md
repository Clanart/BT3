Found a real analog: `updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts` reuses a file's previously-computed `DiffSelection` bitmap by absolute diff-line index whenever the file id still exists on disk, without re-validating that the index positions still refer to the same lines in the newly-fetched diff.

### Title
Stale line-index reuse in `updateChangedFiles` can silently commit unselected/wrong lines after external file changes - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`DiffSelection` tracks partial-commit state purely as a `Set<number>` of "diverging" absolute line indices into a specific diff's hunk layout [1](#0-0) . These indices only have meaning relative to the exact hunk structure (`unifiedDiffStart`/`unifiedDiffEnd`) of the diff that was displayed when the user made the selection [2](#0-1) . `updateChangedFiles` carries this same `DiffSelection` object forward onto the new `WorkingDirectoryFileChange` for a file whenever the file `id` is still present, via `file.withSelection(existingFile.selection)` [3](#0-2) , but it never checks whether the underlying diff (hunk boundaries, `unifiedDiffStart`, number of hunks) has changed in the meantime.

### Finding Description
Like the Cork Protocol bug — where a raw Ct/Ds quantity was used as an RA amount without applying the exchange-rate conversion between the two units — Desktop's selection bitmap is an index defined in the coordinate space of one diff (call it "unit A": absolute line positions in diff v1) and is reused as-is against a different diff (call it "unit B": absolute line positions in diff v2) without any remapping/"exchange rate" applied between the two.

Concretely:
1. The user opens a file with unstaged changes and selects specific lines/hunks for a partial commit; this produces a `DiffSelection` whose `divergingLines` set is keyed to `diff.hunks[i].unifiedDiffStart` values computed by `DiffParser.parseHunk` for the diff shown at that moment [4](#0-3) .
2. Before the user commits, the file on disk changes again (e.g. another process modifies the file, a build step regenerates it, a merge/checkout touches it, or Desktop just re-reads status after a background git operation) so a new diff is fetched with a different hunk count/sizes/positions.
3. `updateChangedFiles` matches the file purely by `file.id` (based on path/status, not diff content) and reattaches the *old* `existingFile.selection` object onto the file representing the *new* diff [3](#0-2) . There is no call to `withSelectableLines` with the new diff's line set to invalidate stale indices, and no diff-identity/hash check.
4. `patch-formatter.ts`'s `formatPatch` then consults `file.selection.isSelected(absoluteIndex)` using the *new* diff's `hunk.unifiedDiffStart + lineIndex` [5](#0-4) . Because the index set was computed against the old hunk layout, the same numeric indices now point at semantically different lines (different additions/deletions, possibly in a different hunk entirely).

This is exactly the "unit mismatch without conversion" bug class from the report: an index/quantity valid in one accounting context (old diff layout) is consumed directly in a different context (new diff layout) with no reconciliation step, and downstream code (`formatPatch` → `applyPatchToIndex` → `git apply --cached`) treats it as authoritative.

`withSelectableLines` exists specifically to prune indices that are no longer selectable [6](#0-5) , which shows the developers are aware selection sets can go stale — but this reconciliation is not invoked from `updateChangedFiles` when a fresh diff is fetched for an already-known file id; only file `id` membership is checked [7](#0-6) .

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes." A partial-commit selection made by the user against one version of a diff can be silently re-applied to a different diff, causing the generated patch (`formatPatch`) to stage/commit lines the user never selected, or omit lines the user did select — without any error or warning, since `formatPatch` and `applyPatchToIndex` operate purely on indices with no cross-check against diff content identity [8](#0-7) , [9](#0-8) . In the worst case this can commit unintended secrets/content or drop intended fixes, and the corrupted commit is what gets pushed.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the diff for a file with an existing partial selection to change shape (hunk count/positions) between the time selection was made and the time of commit, driven by an external file modification, a background status refresh, or another git operation racing with the UI — none of which require local/admin access or malware, only ordinary use of the app while something else touches the working tree (a common scenario for build tools, formatters, linters-on-save, or a second git client).

### Recommendation
Invalidate/remap `DiffSelection` whenever the diff backing a file changes shape. When merging state in `updateChangedFiles`, compare the new diff's hunk signature (e.g. hash of hunk headers/`unifiedDiffStart`s) against what the existing selection was built from; if it differs, drop back to `DiffSelectionType.None` (or re-run `withSelectableLines` against the new diff's selectable-line set and clear indices with no longer-valid meaning) instead of blindly forwarding `existingFile.selection`.

### Proof of Concept
Conceptual reproduction (would need to be verified in a running Desktop instance since this is a race/refresh-timing bug, not unit-testable purely from static code):
1. Modify a tracked file to produce diff v1 with hunks A and B.
2. In Desktop, partially select only some added lines inside hunk B (setting `divergingLines` to indices computed against v1's `unifiedDiffStart` for hunk B).
3. Before clicking Commit, externally modify the file again (e.g. `echo extra >> file` then revert part of it, or have a formatter reflow the file) so that a background status/diff refresh produces diff v2 with different hunk boundaries (e.g. hunk B now starts at a different `unifiedDiffStart`, or the two hunks merge into one).
4. Observe that `updateChangedFiles` reattaches the old selection to the file representing diff v2 [3](#0-2) .
5. Click Commit; `formatPatch` builds the patch using the stale indices against v2's lines [5](#0-4) , producing a patch whose selected content differs from what the user actually intended to select, which is silently applied via `applyPatchToIndex`/`git apply --cached`.

  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })
