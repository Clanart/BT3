## Analysis: Intent Gateway GET‑cancellation timeout is not bound to the actual response state

The CSX report's core broken invariant is: **a party can force a "nothing happened" resolution path via a stale/permissionless check window, even though the counterparty-side event has already occurred, and thereby collect both sides of a value transfer.** The closest verified analog in this repo is in the Hyperbridge ISMP handler's GET-request timeout path combined with `IntentGatewayV2`'s source-side order cancellation, which uses a GET query with `timeout: 0` to check destination fill status.

### Title
Intent Gateway source-cancellation GET request can be force-timed-out with a stale non-membership proof, allowing refund of escrow after the order was already filled - (File: `evm/src/core/HandlerV2.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2._cancelFromSource` (renamed `ExtrinsicIntents._cancelFromSource` in the newer app) dispatches a Hyperbridge `DispatchGet` with `timeout: 0` to ask the destination chain whether an order's `_filled[commitment]` slot is populated [1](#0-0) . The intended flow is: the honest relayer proves the destination slot is empty via `onGetResponse`, and only then is escrow refunded (a non-empty slot causes a revert) [2](#0-1) . However, `HandlerV2.handleGetRequestTimeouts` provides an entirely separate path to the same app callback (`onGetTimeout`) that is not synchronized with the actual response-delivery state.

### Finding Description
`handleGetRequestTimeouts` accepts *any* previously-stored state commitment height chosen by the caller (`message.height`), with no requirement that it be the latest known height for the destination/coprocessor state machine [3](#0-2) . It verifies:
1. That `request.timeout() > state.timestamp` is false (i.e., "timed out" as of that height's timestamp).
2. A **non-membership** proof that no response receipt exists in a remote child-trie at that historical height for the request commitment.

Because `_cancelFromSource` sets `timeout: 0` on the `DispatchGet` [4](#0-3) , the condition `request.timeout() > state.timestamp` (i.e. `0 > state.timestamp`) is false for essentially any non-zero timestamp — meaning the request is considered "timed out" as soon as *any* state commitment for the coprocessor exists, including one recorded immediately after dispatch, long before the destination chain has actually been queried or a genuine fill/no-fill response has propagated.

Separately, `handleGetResponses` (the path that legitimately proves fill status) only checks a **local** mapping, `host.responseReceipts(...)`, for duplicate delivery [5](#0-4) , and `EvmHost.dispatchTimeOut` for GET requests deletes `_requestCommitments[commitment]` and unconditionally invokes `onGetTimeout` on the app, with no cross-check against `_responseReceipts` at all [6](#0-5) . The two resolution paths (`onGetResponse` vs `onGetTimeout`) for the *same* GET request are therefore decoupled: nothing prevents the timeout path from being driven to completion using an early/stale height proof while the order has, in reality, already been filled on the destination chain (with `RedeemEscrow` already dispatched back toward the solver).

This exactly mirrors the CSX bug class: the "24 hour window" in CSX let the buyer bypass the seller's completed action (trade acceptance) via an independent, time-gated escape hatch (`buyerCancel`) that didn't check whether settlement (`keeperNodeConfirmsTrade`) was already in flight/complete. Here, the "escape hatch" is `handleGetRequestTimeouts`, which is not required to reflect the *current* fill status of the order and is trivially satisfiable due to `timeout: 0`.

### Impact Explanation
If the Intent Gateway's `onGetTimeout` handler treats a timeout as equivalent to "order unfilled" and issues a refund (mirroring the refund-on-timeout pattern used elsewhere in the codebase, e.g. `HyperFungibleTokenUpgradeable.onPostRequestTimeout` re-minting burned tokens [7](#0-6) ), then `order.user` can obtain the input escrow refund on the source chain *after* a solver has already filled the order and been paid on the destination chain. This is a direct fund-loss / double-settlement outcome: the solver delivers output tokens and the beneficiary/user recovers the same value again from escrow — funds move to the wrong party twice, from a single order.

### Likelihood Explanation
The only actor required is `order.user` themselves, who is explicitly authorized to call `_cancelFromSource` (`if (order.user != ... ) revert Unauthorized()` [8](#0-7) ). No malicious relayer, prover, or admin is needed — an ordinary user can pick an early, honestly-obtained state commitment height and submit the timeout proof themselves (or via any relayer, since `handleGetRequestTimeouts` is permissionless). This requires no front-running of another party's transaction; it exploits the handler's failure to bind the "timed-out" determination to the true, current fill state.

### Recommendation
- Do not allow `handleGetRequestTimeouts` to be satisfied with an arbitrary/non-latest historical height; require the proof height to reflect state at or after the point a response could have legitimately been recorded, and/or require monotonic height ordering per commitment.
- Avoid `timeout: 0` for order-verification GET requests in `_cancelFromSource`, or otherwise ensure `onGetTimeout` cannot be triggered before genuine response delivery has had an opportunity to occur.
- In `EvmHost.dispatchTimeOut(GetRequestTimeout ...)`, cross-check `_responseReceipts[commitment]` and refuse to dispatch a timeout if a response has already been (or is being) delivered — mirroring the Substrate implementation's explicit check ("Reject the timeout if a response has already been received for this request") [9](#0-8) , which the EVM `HandlerV2`/`EvmHost` path lacks.
- In the Intent Gateway's `onGetTimeout`, re-verify order state (e.g., re-check `_filled` via a fresh query or require a minimum height/finality gap) before refunding escrow.

### Proof of Concept
1. `order.user` places a cross-chain order and it is filled by a solver on the destination chain (destination `_filled[commitment]` set, `RedeemEscrow` dispatched toward the solver).
2. Before (or racing) the honest relayer's `handleGetResponses` delivery of the real fill-status response, `order.user` calls `cancelOrder` → `_cancelFromSource`, dispatching a `DispatchGet` with `timeout: 0` [4](#0-3) .
3. `order.user` (or any relayer they control) immediately submits `HandlerV2.handleGetRequestTimeouts` using a proof against an early, already-finalized coprocessor state height where no response receipt for the commitment yet exists — trivially true since it precedes the real proof-delivery pipeline [3](#0-2) .
4. The `0 > state.timestamp` timeout check passes immediately due to `timeout: 0`, the non-membership proof against the chosen stale height verifies, and `EvmHost.dispatchTimeOut` deletes the request commitment and invokes `onGetTimeout` on the Intent Gateway [6](#0-5) , unaware that the order was, in fact, filled.
5. If `onGetTimeout` refunds escrow (as the analogous timeout-refund pattern elsewhere in the codebase does), `order.user` now holds both the destination-chain output (from the real fill) and the source-chain input refund — a double payout at the solver's/protocol's expense.

Note: I was not able to directly view the body of `onGetTimeout` in `ExtrinsicIntents.sol`/`IntentGatewayV2.sol` within the indexed content to confirm its exact refund logic; this assessment is based on the verified handler-level decoupling (`HandlerV2.sol`, `EvmHost.sol`) and the documented refund-on-timeout convention used elsewhere in the codebase. Confirming the exact `onGetTimeout` body would require opening the full contract source, which may not be fully covered by the current index — a Devin session with full repository access can confirm this final link.

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
