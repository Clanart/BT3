## Title
Tron `IntentGatewayV2.placeOrder` accepts duplicate input/output tokens, allowing an order's escrow to be under-collateralized and a solver to over-claim from a single escrow bucket — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The main EVM `IntentGatewayV2.sol` explicitly guards `placeOrder` against duplicate input tokens and duplicate output tokens, with regression tests calling out the exact failure mode ("same-chain partial fills over-release repeated input escrow" / "prematurely finalize repeated output legs"). The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements `placeOrder` without either check, reproducing the "duplicate whitelist entry causes value to be double/incorrectly counted" bug class from the external report inside a fund-custody path instead of a governance-admin path.

## Finding Description
In the canonical contract, `placeOrder` runs two independent duplicate guards before escrowing anything:
1. A transient-storage loop rejecting duplicate `order.output.assets[i].token` entries. [1](#0-0) 
2. An explicit check in the escrow-crediting loop rejecting duplicate `order.inputs[i].token` entries via `_orders[commitment][token] != 0`. [2](#0-1) 

The Tron variant's `placeOrder` has neither guard. Its escrow-crediting loop uses `+=` instead of an existence check: [3](#0-2) 
and the predispatch-path escrow crediting loop also uses `+=` unconditionally: [4](#0-3) 
There is no equivalent of the main contract's transient-storage output-duplicate check anywhere in the Tron `placeOrder` function (confirmed by inspecting the full function body from its start through the escrow/fee logic).

This is structurally the same invariant violation as the ClearingHouse `whitelistAmm` bug: a list/array that should contain only distinct entries (AMMs there, token legs here) is accepted without a uniqueness check, and a downstream accounting routine that iterates and sums per-entry values (there: `getTotalNotionalPositionAndUnrealizedPnl`; here: the per-token `_orders[commitment][token]` escrow-crediting loop and the fill-side per-leg release logic) silently aggregates or fragments value across the duplicate entries instead of treating them as one.

## Impact Explanation
The main-chain regression tests document what duplicate input/output tokens actually cause when unguarded: "same-chain partial fills over-release repeated input escrow" (duplicate inputs) and "same-chain partial fills prematurely finalize repeated output legs" (duplicate outputs). Applied to the Tron deployment:
- A user (or an attacker crafting an order on behalf of a victim's escrow flow) can place an order with the same input token listed twice; the escrow bucket accumulates via `+=`, but downstream partial-fill/refund logic that indexes by (commitment, token) can be driven into releasing or refunding more than was actually escrowed for that leg, or finalizing one leg based on state intended for another.
- Duplicate output tokens are not rejected, so the same per-token output leg can be double-processed by fill/partial-fill accounting that assumes one leg per token, again risking over-release of escrowed funds to a solver or beneficiary, or a solver being able to mark an order filled without delivering the full aggregate output.

This falls squarely under the bounty's "stealing or loss of funds" and "transaction manipulation / logic attacks" categories: escrowed user funds in `IntentGatewayV2` (bridge custody / intent settlement) can be released incorrectly to an unintended amount or party purely by an unprivileged user crafting an `Order` struct with repeated token legs — no relayer, prover, or admin compromise is required.

## Likelihood Explanation
`placeOrder` is a fully public, unprivileged entrypoint that takes an arbitrary `Order` struct directly from `msg.sender`; nothing prevents the caller from listing the same token address twice in `inputs` or `output.assets`. The main-chain code needed two explicit, purpose-built regression tests to close this exact gap, which confirms the underlying escrow/fill accounting genuinely misbehaves on duplicates when unguarded — and the Tron fork simply never received that fix.

## Recommendation
Port the same two guards from `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`:
1. Add the transient-storage (or equivalent Tron-compatible) duplicate-output-token check before escrowing.
2. Replace the unconditional `_orders[commitment][token] += reducedInputs[i].amount;` accumulation with the main contract's `if (_orders[commitment][token] != 0) revert InvalidInput();` guard in both the predispatch and non-predispatch escrow loops.
3. Add regression tests mirroring `testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateInputTokens_WithProtocolFee`, and `testRevert_PlaceOrder_DuplicateOutputTokens` for the Tron contract.

## Proof of Concept
1. On the Tron deployment, call `placeOrder` with `order.inputs = [ {token: USDC, amount: 1200e6}, {token: USDC, amount: 1000e6} ]` and any valid `output.assets` — this is accepted (no revert), whereas the identical call against the main `IntentGatewayV2.sol` reverts with `InvalidInput` (see `testRevert_PlaceOrder_DuplicateInputTokens`, [5](#0-4) ).
2. Similarly, call `placeOrder` with `order.output.assets = [ {token: DAI, amount: 400e18}, {token: DAI, amount: 600e18} ]` — accepted on Tron, whereas the main contract reverts (see `testRevert_PlaceOrder_DuplicateOutputTokens`, [6](#0-5) ).
3. Because the underlying per-token escrow/fill bookkeeping (`_orders[commitment][token]`, partial-fill tracking) was never designed to handle repeated legs — as evidenced by the main contract needing dedicated guards to prevent "over-release" and "premature finalization" — accepting these duplicate-leg orders on Tron reproduces the same escrow-accounting corruption those guards were written to prevent.
