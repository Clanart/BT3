### Title
Distribution precompile's `rewards()` view method skips the non-payable check, allowing sent value to be silently stranded - (File: `precompiles/distribution/distribution.go`)

### Summary
The external report flags `AtomWallet.execute()` for a payable/non-payable mismatch: a function meant to carry ETH value lacks `payable`, so calls with `msg.value > 0` unexpectedly revert, breaking the intended value-forwarding flow. The reachable analog in sei-chain is the inverse but same bug class (payable/non-payable handling bug on a value-carrying EVM entrypoint): the Sei distribution precompile's `rewards()` query method is documented as the one phase-2 view **without** the standard `pcommon.ValidateNonPayable` guard that every sibling precompile method enforces, meaning a value-bearing call to it succeeds instead of reverting and the attached value is not processed or refunded.

### Finding Description
Every other Sei precompile method (bank `send`, addr `getSeiAddr`, pointer `AddNative`, distribution's other query/action methods, staking queries, etc.) calls `pcommon.ValidateNonPayable(value)` at the top of the handler to reject any call carrying `msg.value > 0` for functions that are not designed to accept native value: [1](#0-0) [2](#0-1) [3](#0-2) 

The integration test suite explicitly calls out that the distribution precompile's `rewards()` view breaks this pattern — it has no non-payable check, so a value-bearing call to it would succeed rather than revert, and the sent value would be stranded: [4](#0-3) 

This is precisely analogous to the reported bug class: a mismatch between a Solidity/EVM-reachable function's payability semantics and its actual value-handling logic. In the `AtomWallet` report, the mismatch causes reverts (denial of an intended value transfer); in the sei-chain distribution precompile, the mismatch causes acceptance of value with no downstream accounting, so the caller's attached usei/wei value is neither used to pay for rewards processing, refunded, nor credited anywhere — it is effectively lost from the caller's perspective once the precompile call succeeds and the EVM commits the value transfer into the precompile's account address without any state update crediting it back.

### Impact Explanation
Any unprivileged EVM transaction sender or public-RPC client can call the distribution precompile's `rewards()` method with a non-zero `value` field. Because the non-payable guard other methods rely on is absent here, the call does not revert as it does for every other query/view method on this and other precompiles. The value is transferred to the precompile's associated account as part of standard EVM value-transfer semantics but is never routed back to the caller (unlike stateful/payable precompile methods such as `staking.delegate` or `wasmd.execute`, which explicitly call `pcommon.HandlePaymentUsei` to account for and refund/consume the value). This results in a concrete, permanent loss of funds for any caller who mistakenly (or is tricked into, e.g. via a wallet/dApp bug) attaching value to a `rewards()` call.

### Likelihood Explanation
Likelihood is moderate: this requires a caller to attach non-zero `value` to what is normally understood as a read-only/view call, which is not typical client behavior, but is trivially reachable by any transaction sender, and is exactly the sort of value/payable inconsistency that dApp integrations or misconfigured relayers could hit (similar to how the AtomWallet report's issue arises from a mismatch a caller could easily trigger without malicious intent).

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used by all sibling distribution precompile methods (e.g. `WithdrawValidatorCommission`, `SetWithdrawAddress`, `DelegationRewards` queries) to the `rewards()` handler in `precompiles/distribution/distribution.go`, so that any call carrying non-zero value reverts consistently instead of succeeding and stranding the funds.

### Proof of Concept
1. Call the distribution precompile at its fixed address (`0x0000000000000000000000000000000000001007`) with function selector for `rewards(...)` and a non-zero `value` field via `eth_call`/a signed transaction, analogous to the existing test harness pattern used in `distribution.spec.ts` (`rawSei('eth_call', [{ ..., value: '0x1' }, 'latest'])` as used against other methods in the same file for other precompiles): [5](#0-4) 
2. Observe that, unlike every other guarded method (which reverts with "sending funds to a non-payable function"), the `rewards()` call succeeds while the attached value is not refunded/accounted for anywhere, per the explicit quirk documented in the test file header comment.
