### Title
Secret-dependent table indexing in `multiexp` leaks DKG secret shares via a cache/timing side channel - (File: crypto/multiexp/src/straus.rs)

### Summary

`crypto/multiexp`'s "constant-time" Straus and Pippenger implementations index precomputed tables and bucket arrays directly with chunks of the scalar being multiplied. `BatchVerifier::verify()` (which `verify_with_vartime_blame` runs first on every call) routes through `multiexp`, and PedPoP's `KeyMachine::calculate_share` queues statements containing the secret scalar `share` received from each DKG participant (`share_verification_statements::<C>(..., share)`). A local unprivileged observer — the same attacker model as CVE-2018-6260 (AV:L, perf counters/cache) — can recover scalar bits from the memory-access pattern and reconstruct secret shares.

### Finding Description

- `straus` indexes `tables[s][usize::from(groupings[s][b])]` where `groupings` are windows of the secret scalar (crypto/multiexp/src/straus.rs:42-44). The precomputed per-point table lookup address is a pure function of secret bits, so a cache-line / perf-counter observer learns each window value.
- `pippenger` does the same via `buckets[usize::from(bits[p][n])] += pairs[p].1` (crypto/multiexp/src/pippenger.rs:24-27), again indexed by secret scalar bits.
- `multiexp` selects Straus/Pippenger automatically (crypto/multiexp/src/lib.rs:183-189) and is used by `BatchVerifier::verify` (crypto/multiexp/src/batch.rs:93-94), which is unconditionally invoked by `verify_with_vartime_blame` (crypto/multiexp/src/batch.rs:127-133).
- `KeyMachine::calculate_share` queues `share_verification_statements` built from the decrypted secret `share` scalar and then calls `batch.verify_with_vartime_blame()` (crypto/dkg/pedpop/src/lib.rs:487-499). Pedersen share verification statements include `-share · G` (i.e., the secret share as a scalar against a point), so `share`'s bits drive the secret-indexed lookups in `straus`/`pippenger`.
- The zeroizing wrappers (`flat` returns `Zeroizing<Vec<...>>`, batch.rs:15-19) show the authors knew these buffers hold private values, yet the algorithms performing the multiplication are not actually constant-time with respect to memory access.

### Impact Explanation

A local attacker on the same host (or co-located VM/SMT sibling) that can observe cache-line accesses or hardware performance counters while a node runs `calculate_share` recovers the scalar windows of each received Pedersen share. With enough observations across the n−1 statements, the victim's accumulated secret share — and hence their FROST key share — is recoverable, satisfying the key-share-recovery impact bar. This mirrors CVE-2018-6260: a non-cryptographic side channel exposing data processed by a shared computation unit.

### Likelihood Explanation

Local-only requirement caps severity at Medium (matching the reference CVE's 5.5). Exploitation needs co-residency and noise-heavy reconstruction of 256-bit scalars through windowed lookups, but no interaction with the victim beyond triggering an ordinary, legitimate DKG round — the leakage path executes on the happy path every time `calculate_share` runs.

### Recommendation

Make the non-vartime `straus`/`pippenger` truly constant-time: replace `tables[s][idx]`/`buckets[idx]` with constant-time conditional selection over the whole table/bucket row (e.g., `subtle::ConditionallySelectable`), or for single-scalar cases use the fixed-base constant-time multiplication provided by the underlying curve implementation. Reserve indexed lookups for `*_vartime` variants, and audit that `BatchVerifier::verify`/`verify_with_vartime_blame` are only ever fed statements whose scalars may be secret when a CT path is used.

### Proof of Concept

1. Stand up a PedPoP `SecretShareMachine`/`KeyMachine` session on `Ristretto`; drive `KeyMachine::calculate_share` with valid shares so `batch.verify()` executes `multiexp` over statements containing the secret `share` scalar.
2. On a co-located process, record cache-line hits (Flush+Reload or perf counters) on the `tables`/`buckets` allocations during `straus`/`pippenger`.
3. Recover each window nibble from the observed index sequence; reconstruct `share` and confirm `share·G` equals the recipient's verification share / matches the Pedersen commitment evaluation — demonstrating recovery of a secret the protocol never transmits in the clear.

Note: I could not fully read `share_verification_statements`'s definition within the available iterations; the claim that it embeds `share` as a scalar is inferred from its call sites (`calculate_share` line 490 and `blame_internal` line 597) passing `Zeroizing::new(share)` as the scalar argument, consistent with the standard `s·G − Σ x^j·C_j = 0` verification equation.
