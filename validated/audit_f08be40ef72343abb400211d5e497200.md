### Title
Identity public key forges PedPoP encrypted-message proof of possession - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`EncryptedMessage::read` accepts the canonical encoding of the identity point for both the per-message encryption key and the Schnorr proof nonce, without rejecting either value. [1](#0-0)  Verification only checks `sG == R + cK`, so the tuple `K = 0`, `R = 0`, and `s = 0` satisfies the equation for every challenge. [2](#0-1) 

### Finding Description
An untrusted `EncryptedMessage` is parsed by `EncryptedMessage::read`, which calls the generic `Ciphersuite::read_G` implementation for `key` and `pop.R`. [3](#0-2)  `Ciphersuite::read_G` enforces canonical point encodings, but does not reject the identity point. [4](#0-3) 

The proof-of-possession challenge binds the claimed nonce, claimed key, sender, and ciphertext. [5](#0-4)  However, `SchnorrSignature::batch_statements` checks only that `R + cK - sG` is identity. [6](#0-5)  With `K = R = 0` and `s = 0`, this becomes `0 + c0 - 0G = 0`, so the message passes the PoP check without knowledge of a discrete logarithm. [7](#0-6) 

The same malformed message also forces the ECDH result to identity because decryption calculates `public * private`. [8](#0-7)  That identity shared secret is public and independent of the recipient's private key, while a static ChaCha20 IV is used. [9](#0-8) 

### Impact Explanation
A DKG participant can send a malformed encrypted share whose proof-of-possession validates despite the sender not knowing a private key corresponding to the claimed encryption key. This is a forged proof reachable through bytes supplied to `EncryptedMessage::read` and accepted by the subsequent `batch_verify` call. [10](#0-9) 

The forged proof also causes the recipient to use a publicly computable cipher key, because both ECDH and the ChaCha20 IV become known to the sender. [11](#0-10)  The share itself is still checked against the sender's commitments during `KeyMachine::calculate_share`, so the malformed PoP does not by itself make an arbitrary share valid. [12](#0-11) 

### Likelihood Explanation
The malicious input is short, deterministic, and does not require solving a discrete logarithm or obtaining a secret. `Participant` indexes and message maps are validated separately, but those checks do not reject an identity `msg.key`. [13](#0-12)  The attack requires the ability to submit an authenticated share message as an assigned DKG participant, and it produces a forged PoP rather than an arbitrary valid DKG share. [14](#0-13) 

### Recommendation
Reject the identity point for `EncryptedMessage.key`, `SchnorrSignature.R`, and any Schnorr public key used as a proof target when the protocol requires a non-identity public key. [3](#0-2)  FROST already has a stricter `Curve::read_G` helper that rejects identity after canonical point decoding, but PedPoP calls `Ciphersuite::read_G` instead. [15](#0-14)  Add a PedPoP-specific non-identity check around the `key` and `pop.R` fields, or make `SchnorrSignature::read` provide an identity-rejecting variant for proof-of-possession uses. [16](#0-15) 

### Proof of Concept
For a ciphersuite whose canonical identity encoding is all-zero bytes, construct an `EncryptedMessage` with:

```text
msg.key  = identity-point encoding
pop.R    = identity-point encoding
pop.s    = scalar-zero encoding
msg.msg  = scalar-representation bytes XOR ChaCha20(cipher(context, identity))
```

`EncryptedMessage::read` accepts all three identity/zero encodings because it only requires a valid point encoding and canonical scalar. [3](#0-2)  During share processing, `Encryption::decrypt` queues `pop.batch_verify` using `msg.key` as the public key and `pop_challenge(context, R, key, from, ciphertext)` as the challenge. [17](#0-16)  For every resulting challenge `c`, the verification statement is `0 + c0 - 0G = 0`, so the forged PoP passes batch verification. [2](#0-1)  The ciphertext is deterministically decryptable by the attacker because the ECDH output is identity and the cipher derives a ChaCha20 key from that public point with a fixed IV. [18](#0-17)

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }

      }
