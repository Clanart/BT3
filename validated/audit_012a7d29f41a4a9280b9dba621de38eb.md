Based on the investigation, the "missing field validation" bug class in the report — an untrusted data structure used in a critical operation without validation, where existing guards elsewhere in the codebase are inconsistently applied — has a real analog in GitHub Desktop's git-checkout argument construction.

### Title
Missing `--` argument-separator before untrusted branch name allows git argument injection during checkout - (File: app/src/lib/git/checkout.ts)

### Summary
`git clone` in Desktop correctly places the `--` end-of-options marker *before* passing an attacker-influenced value (the clone URL) as a positional argument, preventing git from mis-parsing it as a flag. `git checkout`, however, does not apply the same guard to the branch name, even though branch names can originate from an untrusted remote (e.g. a forked repository used in the "checkout PR" flow, or any fetched remote branch).

### Finding Description
In `app/src/lib/git/clone.ts`, the untrusted `url` value is protected: [1](#0-0) 
`args.push('--', url, path)` — the `--` precedes `url`, so git cannot interpret a malicious value such as `--upload-pack=...` as an option.

By contrast, `app/src/lib/git/checkout.ts` builds its argument list with the ref name coming *before* the `--` marker, not after: [2](#0-1) 
`getBranchCheckoutArgs` returns `[branch.name, ...(['-b', branch.nameWithoutRemote] if remote), '--']`, and `checkoutBranch` assembles `['checkout', ...baseArgs, branch.name, ('-b', name)?, '--']`: [3](#0-2) 

`branch.name` is not validated against git's `check-ref-format` disallow-list before being used here. Desktop's own sanitizer only strips a leading `-`/`+` for *user-typed* names in text boxes: [4](#0-3) 
but this sanitizer is never applied to `Branch` objects built from refs discovered on a remote (via `git for-each-ref`/`git branch -r` parsing) — those are trusted implicitly, unlike the report's `NotarizedTransaction` fields that were assumed valid without being checked at every use site.

This is reachable from an attacker-controlled repository: `_findPullRequestBranch` in `app-store.ts` fetches from a fork's remote and can create/track a branch whose name matches the fork's ref exactly: [5](#0-4) 
and the "Open in Desktop" deep-link flow (`x-github-client://openRepo/...?branch=...`) also drives a `checkoutBranch` call after fetching from a user-supplied URL: [6](#0-5) 

### Impact Explanation
If a malicious fork/remote publishes a ref whose short name is itself a recognized `git checkout` flag (git's ref-name rules — mirrored by Desktop's own `invalidCharacterRegex` — do not forbid a leading `-`), that ref name would be parsed by git as an option instead of a revision when Desktop runs the composed `git checkout <branch.name> ... --` command. Depending on the specific flag accepted in this position, this can silently change the checkout result (corrupting what the user believes they are checking out) — the same class of "silent corruption of what the user commits" called out as in-scope, and is a lower-severity but concrete instance of unvalidated data reaching a privileged git invocation.

### Likelihood Explanation
Moderate-to-low. It requires the attacker to control a remote/fork that Desktop fetches from and get the victim to check out a specifically-crafted branch (via PR checkout or "Open in Desktop" deep link), and requires git to accept the crafted string as a meaningful flag in that exact argument position. I was not able to fully enumerate which specific `git checkout` flags are exploitable for code execution versus just behavioral corruption within my remaining research budget — this reduces confidence in the maximum achievable impact (full RCE vs. checkout-behavior corruption) but the argument-injection primitive itself is clearly demonstrated by comparing `clone.ts`'s correct `--` placement against `checkout.ts`'s incorrect placement.

### Recommendation
Apply the same discipline used in `clone.ts`: place `--` immediately before `branch.name` (and any other ref-derived positional argument) in `getBranchCheckoutArgs`, so git can never interpret a ref name as an option, regardless of its origin.

### Proof of Concept
1. Create/control a remote repository containing a branch whose short name begins with `-` (git does not reject this on push/fetch).
2. Have the victim either checkout a PR from this fork (`_findPullRequestBranch` → `_checkoutBranch`) or open a "github-mac://openRepo/<url>?branch=<crafted-name>" deep link that survives `testForInvalidChars` (which only blocks control chars, `~^:?*[\|"<>`, `..`, leading `.`, `.lock` suffix — not a leading `-`).
3. Observe that `checkoutBranch` executes `git checkout <crafted-name> [-b <name>] --` with the crafted name positioned before the `--` separator, allowing it to be parsed as a git option rather than a ref name.

*Note: full confirmation of a specific exploitable `git checkout` flag chain to arbitrary code execution was not completed due to research constraints; this should be verified in a live Devin session before being treated as fully proven.*

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
