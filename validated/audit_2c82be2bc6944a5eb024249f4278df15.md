### Title
Unauthenticated payout OP_RETURN allows crediting an arbitrary operator for a payout it never funded - (File: core/src/verifier.rs, core/src/operator.rs)

### Summary
The withdrawing user's `SinglePlusAnyoneCanPay` signature on the payout transaction only commits to input 0 and output 0 (the user's payment), leaving the OP_RETURN output (which encodes the "payer" operator's x-only pubkey) completely unauthenticated. An attacker who controls the withdrawal UTXO can reuse their own valid signature to build and broadcast a competing payout transaction with an arbitrary victim operator's x-only pubkey in the OP_RETURN, poisoning the `withdrawals.payout_payer_operator_xonly_pk` DB column that both `Operator::send_asserts` and `Verifier::is_kickoff_malicious` trust without re-derivation.

### Finding Description
The broken binding is: `withdrawals.payout_payer_operator_xonly_pk == "the operator that actually funded output_txout of the on-chain payout_tx"`. In practice this equality is never re-verified at assert time; both consumers only compare the DB value against `kickoff_data.operator_xonly_pk`.

`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with output0 = user payment, output1 = anchor, output2 = OP_RETURN(operator_xonly_pk). The user only signs with `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) , and `calculate_pubkey_spend_sighash`/`calculate_sighash_txin` for that sighash type commit only to the signer's own prevout and, per BIP-341, only to the single output at the same index as the input (output 0) [2](#0-1) . The OP_RETURN output (index 2) and any extra funding inputs (added via `fund_raw_transaction`, `add_inputs: true`) are outside the signed message.

Because the withdrawal UTXO's script pubkey/private key is user-chosen (the attacker per the threat model chooses the withdrawal UTXO bytes and the signature/sighash flag), the attacker can independently reconstruct a transaction spending the same withdrawal UTXO with the identical committed input0/output0, but with an attacker-chosen OP_RETURN naming any victim operator, funding fees from their own wallet, and broadcast it directly to Bitcoin without ever calling any operator's `withdraw` RPC.

`Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) blindly derives `operator_xonly_pk` from whichever transaction is recorded as the spender of the withdrawal UTXO (`get_payout_txs_for_withdrawal_utxos`, `core/src/database/verifier.rs:170-196`, joining purely on `withdrawal_utxo_txid`/`vout` in `bitcoin_syncer_spent_utxos`) and writes it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) with no check that this operator ever called `withdraw` or funded anything.

Later, `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) filters `get_first_unhandled_payout_by_operator_xonly_pk` by the victim operator's own key, finds the poisoned row, and automatically drives `handle_finalized_payout` → kickoff → `send_asserts`. In `send_asserts` (`core/src/operator.rs:1227-1341`), the only guard is:
```
if payout_op_xonly_pk != kickoff_data.operator_xonly_pk { return Err(...) }
``` [3](#0-2) 
Since both sides now equal the victim operator's own pubkey (attacker-chosen), this check passes trivially — the payout transaction's OP_RETURN is never re-parsed from `payout_tx` (which is fetched at line 1312 but only used for the LCP/block position, not for re-deriving the payer). `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) performs the exact same DB-trusting comparison and thus also fails to flag the kickoff as malicious.

### Impact Explanation
An honest operator, running normal automation, can be tricked by an unrelated third party into believing it fronted a withdrawal it never paid. Its own `PayoutCheckerTask` and `send_asserts` will proceed through kickoff, N-of-N-backed asserts, and eventually the `Reimburse` transaction, releasing bridge-held funds to that operator's collateral for a payout that was never funded by it. This falls squarely under the Critical category "an operator reimbursed for a payout it never funded." The attack requires no privileged role — only control over one withdrawal UTXO's key and the ability to broadcast a Bitcoin transaction — and is repeatable per withdrawal/operator, and the false attribution can target any operator's registered x-only pubkey (a public value).

### Likelihood Explanation
Preconditions: attacker performs a normal Citrea `withdraw` call registering a withdrawal UTXO they control, signs with `SinglePlusAnyoneCanPay` as required by protocol, then — instead of/racing an operator's legitimate payout — crafts and broadcasts their own transaction reusing the same signed input/output0 with an arbitrary OP_RETURN and self-funded fee inputs. This only costs the attacker Bitcoin transaction fees (and possibly the withdrawal amount itself, which returns to the attacker's own address since output0 is the user's own payment) plus normal deposit/withdraw flow costs. No special timing beyond normal mempool/fee-rate competition is needed to win the race to be the canonical spender of the UTXO.

### Recommendation
At `send_asserts` (and `is_kickoff_malicious`), re-fetch the confirmed `payout_tx` from Bitcoin (already available via `get_full_block_from_hash`/`payout_block.txdata`) and re-derive `payout_op_xonly_pk` directly from its OP_RETURN using the same `get_first_op_return_output`/`parse_op_return_data` logic, instead of trusting the previously written DB column. Additionally, consider committing the operator identity inside the sighash-covered output (e.g., embedding it in output0 or requiring `SIGHASH_ALL`/covering all outputs) so a third party cannot rewrite the OP_RETURN without invalidating the user's signature.

    //    call Operator::send_asserts for victim_operator; assert it proceeds past the
