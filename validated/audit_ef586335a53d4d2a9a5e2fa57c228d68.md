### Title
Unchecked ERC20 `transfer`/`transferFrom` return value in ERC20→CW20 pointer contract allows fake CW20 accounting for non-standard ERC20 tokens - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The CW20 pointer contract that wraps an arbitrary ERC20 token (deployed via `MsgRegisterPointer` for `PointerType_ERC20`) issues a `DelegateCallEvm` to the underlying ERC20's `transfer`/`transferFrom` functions but never checks the boolean return value of that ERC20 call, only that the delegatecall itself did not revert. Any ERC20 that returns `false` on failure instead of reverting (a common, standards-compliant pattern for many real tokens) will cause the CW20 wrapper to record success and emit success attributes even though no token movement occurred on the underlying ERC20.

### Finding Description
`transfer` and `transfer_from` in `example/cosmwasm/cw20/src/contract.rs` build an `EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload }` targeting the pointed-to ERC20 contract's `transfer`/`transferFrom` selector, and return `Ok(res)` unconditionally once the message is constructed: [1](#0-0) [2](#0-1) 

The `DelegateCallEvm` custom message is routed to `HandleInternalEVMDelegateCall` → `CallEVM`, which only surfaces an error if the EVM call reverts (`res.Err`); it does not decode or validate the ABI-encoded return data of the target call: [3](#0-2) 

This means the CosmWasm message succeeds as long as the target ERC20's `transfer`/`transferFrom` function executes without reverting — regardless of whether it returns `true` or `false`. Many real-world ERC20 tokens (e.g., tokens with blocklists, pausable transfers, or non-reverting failure semantics) return `false` on failed transfers rather than reverting. This exactly matches the root cause in the referenced Cooler.sol report: an unchecked `transferFrom`/`transfer` return value lets a caller "succeed" a transfer that never actually happened.

Contrast this with the sibling `NativeSeiTokensERC20.sol` pointer contract, which does check the bank-precompile transfer boolean and reverts if it is `false`: [4](#0-3) 
The ERC20-wrapping CW20 pointer contract has no equivalent check.

The `RegisterPointer` handler instantiates exactly this CW20 wasm code for the `PointerType_ERC20` pointer type, making this reachable for any ERC20 token address a user chooses to register: [5](#0-4) 

### Impact Explanation
If a user registers a pointer for a malicious or non-standard ERC20 (one that can be made to return `false` on transfer without reverting, e.g., via a blocklist, allowance quirk, or paused state), calling `transfer`/`transfer_from` on the CW20 pointer will emit a "success" response and CosmWasm-level events/attributes indicating a completed transfer, while the underlying ERC20 balances are unchanged. Any downstream CosmWasm contract or integrator that trusts the CW20 pointer's execution success (e.g., a lending/escrow contract accepting "repayment" via this CW20, or a DEX/vault crediting a deposit) can be tricked into believing funds moved when they did not, resulting in direct fund loss for counterparties who rely on the reported CW20 transfer outcome. This matches the "unauthorized transfer via precompile or pointer" / fund-loss impact class.

### Likelihood Explanation
Reachable by any transaction sender: registering a pointer for an attacker-chosen or already-malicious ERC20 token is permissionless via `MsgRegisterPointer`, and calling the resulting CW20 pointer's `transfer`/`transfer_from` is a normal, permissionless CosmWasm execute message. No validator, governance, or privileged access is required — only a single crafted or pre-existing non-standard ERC20 token and a CosmWasm consumer that trusts the pointer's reported success.

### Recommendation
Decode the ABI-encoded boolean return value from the ERC20 `transfer`/`transferFrom` call (available via `res.ReturnData` from `CallEVM`, surfaced through the `DelegateCallEvm` response) in `example/cosmwasm/cw20/src/contract.rs`, and return `ContractError` if the value is `false`, mirroring the pattern used in `contracts/src/NativeSeiTokensERC20.sol`'s `require(success, ...)` check.

### Proof of Concept
1. Deploy a "fake-fail" ERC20 whose `transfer`/`transferFrom` returns `false` when the caller/recipient is on an internal blocklist, without reverting (standards-compliant behavior, e.g., similar to STASIS EURO).
2. Call `MsgRegisterPointer` with `PointerType_ERC20` for this token; the chain instantiates a CW20 pointer via `msg_server.go`'s `RegisterPointer`.
3. Add the intended victim/recipient (or the caller itself, depending on token blocklist semantics) to the fake token's blocklist so `transfer`/`transferFrom` returns `false`.
4. Call `transfer` or `transfer_from` on the CW20 pointer contract; `execute_transfer`/`transfer_from` build and dispatch the `DelegateCallEvm` message which internally calls the ERC20's `transfer` and gets back `false` without reverting.
5. `CallEVM` sees no VM error (`res.Err == nil`) and returns success; the CosmWasm `Response` is `Ok`, so any observer or dependent contract sees a successful "transfer" event even though the underlying ERC20 balance never moved.

func (k *Keeper) CallEVM(ctx sdk.Context, from common.Address, to *common.Address, val *sdk.Int, data []byte) (retdata []byte, reterr error) {
	if ctx.IsEVM() && !ctx.EVMEntryViaWasmdPrecompile() {
		return nil, errors.New("sei does not support EVM->CW->EVM call pattern")
	}
	if to == nil && len(data) > params.MaxInitCodeSize {
		return nil, fmt.Errorf("%w: code size %v, limit %v", core.ErrMaxInitCodeSizeExceeded, len(data), params.MaxInitCodeSize)
	}
	if to != nil && to.Cmp(common.HexToAddress(solo.SoloAddress)) == 0 {
		return nil, errors.New("cannot call Solo precompile via CosmWasm")
	}
	value := utils.Big0
	if val != nil {
		if val.IsNegative() {
			return nil, sdkerrors.ErrInvalidCoins
		}
		value = val.BigInt()
	}
	// This call was not part of an existing StateTransition, so it should trigger one
	executionCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx)).WithEVMEntryViaWasmdPrecompile(false)
	stateDB := state.NewDBImpl(executionCtx, k, false)
	gp := k.GetGasPool()
	evmMsg := &core.Message{
		Nonce:     stateDB.GetNonce(from), // replay attack is prevented by the AccountSequence number set on the CW transaction that triggered this call
		GasLimit:  k.getEvmGasLimitFromCtx(ctx),
		GasPrice:  utils.Big0, // fees are already paid on the CW transaction
		GasFeeCap: utils.Big0,
		GasTipCap: utils.Big0,
		To:        to,
		Value:     value,
		Data:      data,
		From:      from,
	}
	// should not increment nonce since this isn't a transaction
	res, err := k.applyEVMMessage(ctx, evmMsg, stateDB, gp, false)
	if err != nil {
		return nil, err
	}
	k.consumeEvmGas(ctx, res.UsedGas)
	if res.Err != nil {
		return nil, res.Err
	}
