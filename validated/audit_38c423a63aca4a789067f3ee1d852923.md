Based on the investigation, the closest structural analog to the reported bug ("a state-machine step that trusts an external condition and then commits an irreversible action without validating it belongs to the expected scope") is the Copilot AI-assisted merge-conflict resolution write path in GitHub Desktop.

### Title
Copilot conflict-resolution write path stages AI-supplied file paths without verifying they belong to the actual conflict set - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes file content returned by the Copilot SDK directly to disk and `git add`s it, using only an in-repo path-traversal guard (`resolveWithin`). It does not independently verify, at the point of writing, that the returned `resolution.path` corresponds to a file that is actually part of the current merge/rebase/cherry-pick conflict set.

### Finding Description
`_applyCopilotConflictResolutions` iterates over `copilotResolutions`, which originates from the parsed Copilot SDK response (`parseCopilotConflictResolution` / `reassembleResolutions` in `app/src/lib/copilot-conflict-resolution.ts`), and is model-controlled JSON containing `path` and `resolvedContent` fields [1](#0-0) .

For each resolution, the code resolves the path with `resolveWithin(repository.path, resolution.path)`, which only ensures the resolved absolute path stays inside the repository directory tree, then checks whether an entry with that path exists in the current `workingDirectory.files` and is already resolved (to avoid clobbering the user's manual edits) — but if no matching working-directory entry exists at all, this check is skipped entirely and the code proceeds straight to `writeFile` and staging: [2](#0-1) 

There is no check here against the original conflicted-file set that was captured when the merge/rebase/cherry-pick conflict state was built (`conflictState`); the only membership check is against `state.changesState.workingDirectory.files`, and it's used solely to detect "already resolved externally," not to gate whether the path is legitimate. `normalizeLLMPath` further shows the file paths are explicitly treated as free-form, model-normalizable strings (backslashes, `./`, double slashes) rather than validated against a known set [3](#0-2) .

The conflict-resolution prompt context is built from repository content — commits, PR descriptions, file diffs — that is attacker-influenced when the attacker controls one side of the merge (a malicious branch/PR/fork being merged or rebased by the victim), per `formatConflictContextForPrompt` in `copilot-conflict-context.ts`. A prompt-injection payload embedded in that content could cause the model to emit an additional "resolution" entry for a file that is not actually conflicted (e.g. a build script, CI config, or hook file elsewhere in the repo), with attacker-chosen content.

### Impact Explanation
If the model can be induced (via prompt injection embedded in commit messages, file contents, or PR metadata used as resolution context) to return a `resolutions[].path` for a file outside the actual conflict set, `_applyCopilotConflictResolutions` will write that attacker-influenced content to disk and immediately `git add` it — corrupting what the user is about to commit/push without an explicit conflict-marker prompt for that file. This falls under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Medium-to-Low. It requires: (1) the victim to have opted into Copilot conflict resolution during an active merge/rebase/cherry-pick against attacker-influenced content, and (2) a successful prompt injection against the underlying model to add an out-of-scope path to the JSON response. The result dialog does show per-file resolutions before the user clicks "Continue Merge," so a vigilant user reviewing the diff list could notice an unexpected file — this is a partial mitigating factor I could not fully verify (I did not confirm whether the result dialog enumerates literally every entry in `copilotResolutions` or filters by known conflicted paths for display, e.g. in `copilot-conflicts-changes.tsx`).

### Recommendation
In `_applyCopilotConflictResolutions`, before writing/staging, explicitly reject any `resolution.path` that is not a member of the conflict state's known conflicted-file paths (`conflictState`/`step.conflictState`), independent of `resolveWithin` and independent of the `onDiskFile` "already resolved" check. Treat any resolution path outside that allow-list as a validation failure and surface it (e.g., as a skipped file) rather than silently writing it.

### Proof of Concept
Not independently verified end-to-end (would require confirming a working prompt-injection payload against the live Copilot model, which is outside static code review). The code-level gap enabling it is directly evidenced: `_applyCopilotConflictResolutions` performs `resolveWithin` (repo-boundary check only) and an "already resolved" check gated on the path already existing in `workingDirectory.files`, but has no check requiring `resolution.path` to be a member of the original conflict set before calling `writeFile` + `git add`. /**
 * Normalize a file path returned by the LLM. The model may return
 * Windows-style backslashes (`src\\file.ts`), a leading `./`, or redundant
 * separators — all of which would cause validation to reject an otherwise
 * correct resolution.

function normalizeLLMPath(raw: string): string {
  return raw
    .trim()
    .replace(/\\/g, '/')
    .replace(/^\.\//, '')
    .replace(/\/\/+/g, '/')
