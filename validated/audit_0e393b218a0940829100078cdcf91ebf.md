Based on the report's bug class — an untrusted/incidental signal from any third party unconditionally forcing a "disqualification" (session/eligibility invalidation) on a legitimate actor, with no way for the victim to prevent it — the closest analog in `shopify_app` is `login_again_if_different_user_or_shop` (used as a `before_action` in `EnsureHasSession` for the legacy, non-token-exchange auth strategy), which unconditionally clears a victim's valid session whenever the untrusted `shop` query parameter in the request doesn't match the current session's shop.

### Title
Forced session invalidation via unauthenticated `shop` parameter mismatch (link-based griefing) - (File: `lib/shopify_app/controller_concerns/login_protection.rb`)

### Summary
`EnsureHasSession` registers `login_again_if_different_user_or_shop` as a `before_action` for apps using the legacy (non-token-exchange) auth strategy. This method destroys a merchant's valid, authenticated session purely because the request's `shop` query parameter differs from the shop bound to the current session — with no verification that the mismatch reflects genuine merchant intent.

### Finding Description
`login_again_if_different_user_or_shop` calls `session_shop_conflicts_with_params`, which compares `current_shopify_session.shop` to the raw `params[:shop]` value and, on any mismatch, unconditionally clears the session cookie and redirects to login: [1](#0-0) [2](#0-1) 

This is wired up unconditionally for every authenticated action under the legacy strategy: [3](#0-2) 

Just like the RewardsEngine hook flips `eligible = false` on any inflow after `checkpointStart` regardless of whether the inflow represents a genuine "new entry" (vs. dust transfer or reward mint), this code flips the session to "invalid" on any `shop` param mismatch regardless of whether that mismatch represents genuine merchant intent (e.g. actually switching shops) versus an incidental/crafted value in a link the merchant is tricked into clicking. The parameter is fully attacker-controlled and the destructive action (`clear_shopify_session`) fires on a simple `GET`, which is not covered by Rails' standard CSRF token protection.

### Impact Explanation
An attacker can craft a link to the app (e.g. `https://victim-app.example.com/some_authenticated_path?shop=attacker-shop.myshopify.com`) and send it to a logged-in merchant. If the merchant clicks it while embedded/browsing the app, their valid session cookie is deleted and they are force-logged-out and redirected to the login/OAuth flow — a denial-of-service / griefing vector directly analogous to the "any inflow disqualifies for the epoch" bug: an unrelated party's crafted request destroys a victim's otherwise-valid state (session) with no way for the victim to prevent it once the request lands.

### Likelihood Explanation
This is reachable by any anonymous third party who can get a merchant to click a link or load a page containing this app's URL with an attacker-chosen `shop` parameter — no privileges or existing app access required. It is a `before_action`, so it applies to essentially all authenticated non-embedded/legacy-flow requests.

### Recommendation
Only clear/invalidate the session when the mismatch is derived from a verified source (e.g. a signed/verified request such as a completed OAuth callback or a verified session token), not from the raw, unauthenticated `shop` query parameter. Consider ignoring `shop` param mismatches for GET navigations that aren't part of an explicit re-authentication flow, or require the mismatch to be corroborated by another authenticated signal before destroying the session.

### Proof of Concept
1. Merchant has an active session for `victim-shop.myshopify.com` in a legacy (non-token-exchange) `EnsureHasSession`-protected app.
2. Attacker sends the merchant a link: `https://app.example.com/orders?shop=attacker-shop.myshopify.com`.
3. Merchant clicks the link; `login_again_if_different_user_or_shop` runs as a `before_action`, `session_shop_conflicts_with_params` returns `true` since `params[:shop] != current_shopify_session.shop`.
4. `clear_shopify_session` deletes the encrypted session cookie and the merchant is redirected to login, losing their session with no direct way to prevent it: [1](#0-0)

      return unless session_id_conflicts_with_params || session_shop_conflicts_with_params

      clear_shopify_session
