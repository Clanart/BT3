### Title
`ReceivedOutput::read` deserializes an unverified offset/output pair, bypassing the mandatory script↔offset binding the `Scanner` enforces — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to CVE-2019-12428 (a crafted request bypassing a mandatory authorization restriction), `ReceivedOutput::read` accepts attacker-controlled bytes that skip the only check which makes a received output spendable: that `output.script_pubkey` equals the Taproot output of `key + offset·G`. The `Scanner` enforces this binding by construction (it only yields outputs whose `script_pubkey` was looked up in `self.scripts`); the deserialization path enforces nothing at all.

### Finding Description
`Scanner::new`/`register_offset` populate `scripts: HashMap<ScriptBuf, Scalar>` mapping each valid P2TR script to the scalar offset needed to spend it. `scan_transaction` only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` hits, so every honestly-produced `ReceivedOutput` pairs `offset` with a script that is actually `p2tr(key + offset·G)`:

- `networks/bitcoin/src/wallet/mod.rs:205` — `if let Some(offset) = self.scripts.get(&output.script_pubkey)`

`ReceivedOutput::read` (lines 122–134) instead reads `offset` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns the tuple with no consistency check:

- `networks/bitcoin/src/wallet/mod.rs:122-133` — `offset`, `output`, and `outpoint` are accepted independently; `output.script_pubkey` is never compared against `p2tr_script_buf(key + offset·G)`.

The mandatory "authorization" — proof that the holder of the threshold key can actually spend this output — is silently bypassed by a crafted byte stream.

### Impact Explanation
Any untrusted party able to feed bytes into `ReceivedOutput::read` (e.g., a peer relaying claimed deposits, or data recovered from an untrusted store) can cause the consumer to record funds as received that are not spendable: the declared `offset` does not correspond to `output.script_pubkey`, so `key.offset(offset)` cannot produce a signature for that UTXO. Downstream accounting that credits the output's `value()` would over-credit the attacker, and any spend attempt built on the pairing fails — a loss-of-funds-availability / false-credit condition.

### Likelihood Explanation
Exploitation requires the integrator to trust serialized `ReceivedOutput`s from a non-`Scanner` source. `read`/`write`/`serialize` exist precisely for moving outputs between components, so a hostile peer or corrupted DB row is a realistic byte source. It does not require key material, collusion, or malformed curve encodings — only a mismatched `offset`/`script_pubkey` pair.

### Recommendation
Make `ReceivedOutput` unforgeable from raw bytes: either (a) store the base `ProjectivePoint` and recompute `p2tr_script_buf(key + offset·G)` inside `read`, rejecting inputs where it differs from `output.script_pubkey`, or (b) include the expected `ScriptBuf` (or the base key) as a parameter to `read` so the binding is verified at deserialization time, matching the invariant `scan_transaction` maintains.
