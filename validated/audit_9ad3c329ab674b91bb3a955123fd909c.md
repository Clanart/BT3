## Analysis

The reported bug class is a Node.js file-server following a symlink to escape its declared root directory. Github Desktop's own codebase shows the maintainers are aware of this exact risk class — `resolveWithin()` in `app/src/lib/path.ts` was built specifically to reject symlink-based escapes (see the explicit test `'fails for paths that use a symlink to traverse outside of the root'` in `app/test/unit/path-test.ts`), and it is applied in a few call sites such as `app/src/lib/copilot-conflict-context.ts` and `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`. However, this guard is **not** applied to the working-directory file readers used for diff/image rendering, which instead do a raw `Path.join(repository.path, file.path)` followed by `fs.readFile`/`stat`, both of which follow symlinks by default. ### Title
Symlink path traversal via tracked symlink entries when rendering working-directory image/text diffs - (File: app/src/lib/git/diff.ts)

### Summary
Github Desktop lets `file.path` values that originate from `git status` (i.e. from the contents of a cloned/checked-out repository) flow directly into `Path.join(repository.path, file.path)` and then into `fs.readFile`/`readPartialFile` in several diff-rendering code paths, without the `resolveWithin` containment check that other parts of the codebase already use for the same class of risk.

### Finding Description
Git tracks symbolic links as regular tree entries (mode `120000`). When a user clones or fetches a malicious repository containing a symlink — e.g. a file named `logo.png` whose blob content is a relative/absolute path pointing outside the working directory (such as `../../../../.ssh/id_rsa` or an absolute path) — that symlink is checked out as-is into the working tree. `git status` reports it as a normal new/modified file, and Desktop's `WorkingDirectoryFileChange.path` will simply be `"logo.png"`.

When the user opens the Changes view or diff for that path, Desktop calls:
- `getWorkingDirectoryImage(repository, file)` in `app/src/lib/git/diff.ts:926-937`, which does `readFile(Path.join(repository.path, file.path))`, or
- `getNewFileContent` in `app/src/ui/diff/syntax-highlighting/index.ts:89-94`, which calls `readPartialFile(Path.join(repository.path, file.path), ...)`, or
- `getResolutionDiff` in `app/src/lib/git/diff.ts:459-463` for conflict-resolution previews.

None of these use `resolveWithin` (defined in `app/src/lib/path.ts:36-72`), which is the function the project itself introduced specifically to defeat symlink-based escapes by comparing `realpath()` of the resolved target against `realpath()` of the root. Because `fs.readFile`/`fs.stat` transparently dereference symlinks, the read is not confined to the repository root — it follows the symlink to whatever the attacker specified, and the file's bytes are base64-encoded and rendered as an `<img>` (for images) or displayed/tokenized as diff text (for the syntax highlighter), directly in Desktop's UI.

This is functionally identical to the reported `public` npm module bug: a path is joined against a "root" without verifying that the *resolved* (symlink-dereferenced) path still lives under that root.

### Impact Explanation
An attacker who controls a repository the victim clones or fetches (a fully unprivileged, remote-controlled input per the program's valid-impact criteria) can plant a symlink pointing at any file the victim's OS user can read — SSH keys, cloud credential files, browser profiles, etc. Simply having the victim view that entry's diff (an ordinary, expected user action when reviewing changes) causes Desktop to read the target file's contents and render them in the app, disclosing file contents that reside outside the cloned repository. This satisfies the "read outside the repo" valid-impact category without requiring local/physical access, admin rights, or prior compromise.

### Likelihood Explanation
Likelihood is realistic: creating a symlink entry in a git repository is trivial (`ln -s`, `git add`, commit), and no special server-side support is required — the payload travels via a normal `git clone`/`fetch`. The only user action needed is opening the Changes/diff view for the affected path, which is core, everyday Desktop usage, not an "unnatural" step. The vulnerability is also inconsistent with the app's own established mitigation (`resolveWithin`), showing the guard was omitted rather than intentionally scoped out.

### Recommendation
Route every working-directory file path derived from `file.path` (or `getOldPathOrDefault(file)`) through `resolveWithin(repository.path, file.path)` (or `resolveWithinPosix`/`Win32` as appropriate) before calling `fs.readFile`, `readPartialFile`, or `fs.stat`, mirroring the pattern already used in `app/src/lib/copilot-conflict-context.ts` and `openRepositoryFromUrl`. If resolution fails or returns `null`, treat the file as unreadable/skip it (e.g. render as binary/"file could not be read") rather than dereferencing the symlink. Apply the same fix to `app/src/ui/diff/syntax-highlighting/index.ts`'s `getNewFileContent`, `getResolutionDiff` in `app/src/lib/git/diff.ts`, and `getLargeFilePaths` in `app/src/lib/large-files.ts`, which have the identical unguarded `Path.join(repository.path, file.path)` pattern.

### Proof of Concept
1. Attacker creates a repository containing a symlink entry:
   ```
   ln -s /home/victim/.ssh/id_rsa secret.png
   git add secret.png && git commit -m "add image"
   git push
   ```
2. Victim clones or fetches/checks out this branch in Desktop.
3. Victim opens the Changes tab and clicks on `secret.png` (recognized as an image by extension).
4. Desktop's diff view calls `getWorkingDirectoryImage(repository, file)` → `readFile(Path.join(repository.path, 'secret.png'))` in `app/src/lib/git/diff.ts:930`. Node's `fs.readFile` follows the symlink and returns the bytes of `/home/victim/.ssh/id_rsa`.
5. Those bytes are base64-encoded and rendered as an image (or garbled image render, but the raw bytes are already loaded into the renderer process/UI state and can be exposed via further UI/export features), demonstrating the file was read from outside the repository boundary.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
