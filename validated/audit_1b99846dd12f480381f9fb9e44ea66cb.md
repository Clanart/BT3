## Finding: Persistent `safe.directory` Trust Is Never Revoked on Repository Removal [1](#0-0) 

### Title
Stale `safe.directory` trust entries are never revoked when a repository is removed, permanently bypassing Git's unsafe-ownership check for that path - (File: `app/src/lib/git/config.ts`, `app/src/lib/stores/repositories-store.ts`)

### Summary
When Desktop encounters a repository path owned by a different local user, `getRepositoryType` classifies it as `'unsafe'` [2](#0-1) , and the UI offers a "Trust Repository" action that calls `addSafeDirectory(path)`, which permanently appends the path to the user's **global** `safe.directory` git config [1](#0-0) . This trust decision is never revoked. When a user later removes that repository from Desktop, `RepositoriesStore.removeRepository` only deletes the database row and clears pending push tags — it never calls any routine to strip the corresponding `safe.directory` entry: [3](#0-2) . A codebase-wide search confirms no `removeSafeDirectory`/unset routine exists anywhere in the app.

### Finding Description
The bug-class from the report is: a validation flag is flipped to "trusted"/"valid" but is never flipped back to "untrusted"/"invalid" on the corresponding teardown event, so a downstream "skip" check that relies on that flag silently stops protecting anything at that identity (in Riz, `_isValidAddressProvider`; here, git's `safe.directory` allow-list).

In Desktop:
- Trust is granted per-path via `addSafeDirectory` from `MissingRepository` [4](#0-3)  and `AddExistingRepository` [5](#0-4) .
- That trust lives forever in the user's global `~/.gitconfig`, keyed only by filesystem path, with no linkage to a specific repository identity (no commit SHA pin, no repo id, nothing).
- The "shutdown" analog — removing the repository from Desktop via `_removeRepository` → `repositoriesStore.removeRepository` — performs no cleanup of that config entry [6](#0-5) [3](#0-2) .
- The "skip" check downstream is inside `getRepositoryType`: git's own ownership check consults `safe.directory` before raising "dubious ownership", and once the path is listed it will never again report `'fatal: detected dubious ownership'` for that path, so `getRepositoryType` can never return `{ kind: 'unsafe' }` for it again [7](#0-6) .

Because the trust decision is bound only to a path string and never expires or is revoked, any future filesystem object placed at that exact path — after the original repository is removed from Desktop, deleted, ejected (USB/network share), or the directory is otherwise repurposed by a different, less-trusted local identity — inherits full trust with no additional prompt. Desktop will treat it as `'regular'`, run `git` commands in it, and read/use its local `.git/config`, hooks-adjacent settings, and working tree as if the user had freshly vetted it, since the entire point of the unsafe-ownership check that Desktop deliberately surfaced (see changelog entries for 2.9.14/2.9.15/3.0.5 adding this exact protection) is silently defeated for that path forever.

### Impact Explanation
This directly corrupts the security invariant Desktop introduced the unsafe-directory warning to protect: "only run git in / trust directories whose ownership the user has explicitly vetted, right now." Once bypassed, a directory reused by another local identity can carry attacker-controlled `.git` config (`core.hooksPath`, `core.fsmonitor`, filters, etc.) or working-tree content, and Desktop will operate on it as fully trusted without ever re-prompting, since the underlying git ownership check that would normally catch a changed owner is permanently suppressed by the stale `safe.directory` entry. This can lead to arbitrary command execution in the context of the Desktop/git process (via hook or config-driven execution) for a path the user no longer even has registered in Desktop.

### Likelihood Explanation
Moderate. This requires a path being reused across ownership changes (shared drives, mounted volumes, temp directories, build/CI machines, or a removed repo's directory being recreated by another local account) — the exact scenario the original unsafe-directory feature (changelog 2.9.14, 2.9.15, 3.0.5) was built to defend against. Desktop's own UI actively steers users toward clicking "Trust Repository" to unblock themselves, and nothing in the product surface ever tells the user that trust is permanent and independent of the Desktop repository list, making silent persistence likely to be triggered by normal usage patterns rather than requiring an unusual workflow.

### Recommendation
- When `RepositoriesStore.removeRepository` (and/or repository-move/relocate flows) deletes a repository, also remove the matching `safe.directory` entry via `git config --global --unset safe.directory <path>` if no other tracked Desktop repository still references that path.
- Consider scoping trust decisions more tightly (e.g., re-validate ownership/identity at each session start rather than persisting indefinitely), and surface an explicit "Manage trusted directories" setting so users can audit and revoke stale trust.

### Proof of Concept
1. On a machine with multiple local users (or using a removable/mounted path), Alice adds an existing repository at `/shared/repo` in Desktop; Desktop detects `getRepositoryType` returns `{ kind: 'unsafe' }` and Alice clicks "Trust repository", invoking `addSafeDirectory('/shared/repo')` [4](#0-3) , permanently adding the path to her global `safe.directory` list.
2. Alice removes the repository from Desktop (`Remove Repository`), which only deletes the DB row [3](#0-2)  and leaves the `safe.directory` entry intact.
3. Mallory, a different local user (or a process able to write to `/shared/repo`, e.g. after Alice deletes the directory and it gets recreated), places a malicious git repository — with a crafted `.git/config` (e.g., `core.fsmonitor`, hooks, or filters referencing an attacker script) — at the exact same path `/shared/repo`.
4. Alice re-adds `/shared/repo` in Desktop (or Desktop rediscovers it via recent-repositories). `getRepositoryType` runs `git rev-parse` in that path; because `/shared/repo` is still listed in `safe.directory`, git never emits the "dubious ownership" error, so the function returns `{ kind: 'regular' }` instead of `{ kind: 'unsafe' }` [8](#0-7) , and Desktop proceeds to run git commands / load config against Mallory's attacker-controlled repository without any warning or re-prompt.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```

```typescript
export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
```

```typescript
  public async _removeRepository(
    repository: Repository | CloningRepository,
    moveToTrash: boolean
  ): Promise<void> {
    try {
      if (moveToTrash) {
        try {
          await shell.moveItemToTrash(repository.path)
        } catch (error) {
          log.error('Failed moving repository to trash', error)

          this.emitError(
            new Error(
              `Failed to move the repository directory to ${TrashNameLabel}.\n\nA common reason for this is that the directory or one of its files is open in another program.`
            )
          )
          return
        }
      }

      if (repository instanceof CloningRepository) {
        this._removeCloningRepository(repository)
      } else {
        await this.repositoriesStore.removeRepository(repository)
      }
    } catch (err) {
      this.emitError(err)
      return
    }

    const allRepositories = await this.repositoriesStore.getAll()
    if (allRepositories.length === 0) {
      this._closeFoldout(FoldoutType.Repository)
    } else {
      this._showFoldout({ type: FoldoutType.Repository })
    }
  }
```
