## Analysis: `BandwidthManager.onAccept` — Missing Source-Module Check

Confirmed vulnerability: `onAccept` in `evm/src/apps/BandwidthManager.sol` only authenticates the **source chain** of the inbound message, not the **source module**.

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    PostRequest calldata request = incoming.request;

    if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

    OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
    ...
``` [1](#0-0) 

The `PostRequest` struct carries both a `source` (chain identifier) and a `from` (source module identifier) field, as seen in the test harness's construction of a governance request:

```solidity
request: PostRequest({
    source: h.hyperbridge(),
    dest: h.host(),
    nonce: 0,
    from: bytes("hyperbridge-governance"),
    to: PALLET_TO,
    ...
``` [2](#0-1) 

`onAccept` never inspects `request.from`, despite the contract declaring `PALLET_BANDWIDTH_MODULE_ID = bytes("BWMARKET")` specifically to identify the trusted source module on the pallet side:

```solidity
/// Must equal `pallet-bandwidth`'s `PalletId`. The pallet enforces
/// this on inbound messages, so changing it on either side breaks
/// the round-trip.
bytes public constant PALLET_BANDWIDTH_MODULE_ID = bytes("BWMARKET");
``` [3](#0-2) 

`PALLET_BANDWIDTH_MODULE_ID` is only ever used as the `to` field when *dispatching outbound* purchase messages in `purchase()` [4](#0-3) ; it is never compared against `request.from` on the inbound path. This means any module on the Hyperbridge chain (`request.source == hyperbridge`) — not just `pallet-bandwidth` — can send a `SetTiers` or `Withdraw` message and have it executed by `onAccept`, because the only enforced invariant is chain identity, not module identity.

The test suite's own comment acknowledges only chain-level defense is being tested: *"Defence-in-depth: even if the local host delivered it, only hyperbridge-source messages may govern the manager"* [5](#0-4)  — there is no corresponding test asserting rejection of a message from the correct chain but a wrong module (`from != PALLET_BANDWIDTH_MODULE_ID`), confirming the check simply doesn't exist in the contract.

### Title
Missing source-module authentication in `BandwidthManager.onAccept` allows any Hyperbridge-chain module to issue governance/withdrawal actions - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`onAccept` authenticates only `request.source` (the origin chain, must equal `IDispatcher(_host).hyperbridge()`) but never validates `request.from` against `PALLET_BANDWIDTH_MODULE_ID`. Any ISMP module deployed on the Hyperbridge parachain can therefore craft a `SetTiers` or `Withdraw` payload and have `HandlerV2.handlePostRequests` deliver it to `BandwidthManager.onAccept`, which will execute it as if it originated from `pallet-bandwidth`.

### Finding Description
`onAccept` decodes `request.body[0]` into an `OnAcceptActions` discriminant and executes privileged logic (`SetTiers` tier-price mutation, or `Withdraw` asset transfer) after checking only:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
``` [6](#0-5) 
This verifies the message came from the correct **chain** (the Hyperbridge parachain) but not from the correct **module** on that chain. The contract defines `PALLET_BANDWIDTH_MODULE_ID` explicitly as the pallet identity that should gate inbound trust, with a comment stating the pallet enforces module identity on its side [3](#0-2) , but the EVM-side contract never performs the symmetric check (`request.from.equals(PALLET_BANDWIDTH_MODULE_ID)`). Since any deployed ISMP module (pallet) on the Hyperbridge state machine can dispatch a `PostRequest` targeting `to = PALLET_BANDWIDTH_MODULE_ID`/`BandwidthManager`'s address, and the router/host only ensures the request is correctly proven and routed to the destination `to` module — not that the *source* module matches an app-specific allowlist — an attacker who controls or compromises (or merely operates) a different, unprivileged pallet on the Hyperbridge chain could forge the `from` field and drive `onAccept` to mutate `tierPrice` mappings or transfer arbitrary ERC20/native balances out of `BandwidthManager` to an attacker-chosen `beneficiary`.

### Impact Explanation
This breaks the core invariant stated in the target question: *cross-chain bandwidth actions must authenticate both source chain and source module before changing credit or withdrawing assets*. An unauthenticated source module reaching `Withdraw` results in direct, unauthorized transfer of all ERC20/native funds held by `BandwidthManager` to an attacker-controlled beneficiary — theft of funds. Reaching `SetTiers` allows arbitrary manipulation of pricing used in the public `purchase()` flow, enabling economic manipulation (e.g., setting tier price to 0, or manipulating price such that `PriceNotRepresentable` misbehaves) — logic/governance manipulation. Both align with "Critical: unauthenticated cross-chain governance or host-management execution".

### Likelihood Explanation
Exploitability depends on whether an attacker can get *any* message with `source == hyperbridge` and `to == <address of BandwidthManager as registered on hyperbridge>` (or however routing binds destination) delivered with a forged/uncontrolled `from`, i.e., whether the broader ISMP router/pallet-side or host-side machinery independently constrains which modules may address `BandwidthManager`. That router-level binding (module dispatch model on the Substrate side, `pallet-ismp`/`ismp-rs` routing) was not fully inspected in this pass — I could not confirm from the EVM-side code alone whether the Substrate router restricts which pallet ids can send `PostRequest`s to a given destination `to`/app on EVM, or whether that binding is exclusively left to the destination app (as is standard practice in this codebase per other apps). If routing is enforced purely by destination-side app logic (as the missing check here suggests it is expected to be, given the pallet-side comment "the pallet enforces this on inbound messages" implying the EVM side should symmetrically enforce it), then any pallet capable of dispatching an ISMP `PostRequest` to `BandwidthManager`'s app id can exploit this with no privileged access needed.

### Recommendation
Add an explicit check comparing `request.from` to `PALLET_BANDWIDTH_MODULE_ID` in `onAccept`, symmetric to the existing `request.source` check:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
if (!request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```
Add a regression test (analogous to `testOnAcceptRejectsNonHyperbridgeSource`) that sets `inc.request.from` to an arbitrary non-`BWMARKET` value while keeping `source` valid, and asserts `UnauthorizedAction` is reverted with no state mutation.

### Proof of Concept
Using the existing test harness's `_governanceRequestFor` helper as a base: construct an `IncomingPostRequest` with `request.source == host.hyperbridge()` (valid chain) but `request.from = bytes("some-other-pallet")` instead of `bytes("BWMARKET")`, body encoding a `Withdraw` action draining the fee token to an attacker address, then call `manager.onAccept(req)` via `vm.prank(address(host))`. With the current code this succeeds and transfers funds; per [7](#0-6)  there is no line rejecting on `request.from`, so the transfer/tier-mutation goes through despite the wrong source module — this is exactly the "success" that a correct implementation should reject.

**Caveat**: I was not able to fully trace the Substrate-side ISMP router / `pallet-bandwidth` dispatch logic in this pass to confirm whether module-source binding is enforced anywhere else in the stack (e.g., at the router or pallet level preventing other pallets from addressing `BandwidthManager`). If such enforcement exists upstream and is airtight, this finding would be defense-in-depth only rather than exploitable end-to-end; a full assessment would require reviewing `modules/pallets/bandwidth/src/lib.rs` and the core ISMP router (`modules/ismp/core/src/router.rs`) dispatch-side module binding, which is recommended before finalizing severity.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
```
