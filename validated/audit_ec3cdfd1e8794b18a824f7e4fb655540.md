I found a genuine analog of the reported bug class. The root cause in the smart-contract report is a "check looks correct but omits a boundary/exactness validation" — the same pattern exists in GitHub Desktop's directory-containment guard.

### Title
Path-containment check `_resolveWithin()` uses a naive string prefix comparison, allowing symlink/sibling-directory escape from the repository root - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` / `resolveWithinPosix()` / `resolveWithinWin32()` are the app's central guard used everywhere a repository-relative, potentially attacker-influenced path must be proven to stay inside the repository working directory before it is read, written, or handed to the OS shell. The underlying `_resolveWithin()` implementation validates containment with `realResolved.startsWith(realRoot)`, a raw string-prefix test with no path-separator boundary check.

<cite repo="Annirich/desktop--001" path="app/src/lib/path.ts" start="64="71" /> [1](#0-0) 

Just as `computeRootFromWitness()` accepted a witness that matched a *different* leaf/index than the one being challenged because it never verified the terminal index, `_resolveWithin()` accepts any resolved path whose string representation happens to share a prefix with the root — not just paths that are actually nested underneath it.

### Finding Description
The vulnerable logic:

```ts
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

`String.prototype.startsWith` has no concept of path segment boundaries. If the repository lives at `/Users/victim/Documents/GitHub/app` and a sibling directory `/Users/victim/Documents/GitHub/app-secrets` exists (an entirely ordinary situation — users routinely clone multiple, similarly prefixed repos side by side, e.g. `app` / `app2`, `foo` / `foo-private`), then `realpath()` resolving a symlink (or `..`-based traversal) that lands in `app-secrets` produces a string that `startsWith('/Users/victim/Documents/GitHub/app')` even though it is a completely different, sibling directory — outside the intended root.

The function is documented as resolving "one or more path sequences into an absolute path underneath **or at** the given root path" and guarantees the result "resides at, or underneath this path" [2](#0-1)  — that guarantee is false for this class of input.

This guard is relied upon by security-sensitive, attacker-reachable code paths:
- Reading and writing Copilot-AI merge-conflict-resolution content, where the checked path (`resolution.path`) originates from git status entries of the working tree: `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` after `resolveWithin(repository.path, resolution.path)`. [3](#0-2) 
- Reading conflicted file contents to build AI context: `readFile(absolutePath, 'utf8')` after `resolveWithin(workingDirectory, file.path)`. [4](#0-3) 
- Revealing a file from a deep-link (`x-github-client://openRepo/...?filepath=`) in the OS file manager: `shell.showItemInFolder(resolved)` after `resolveWithin(repository.path, filepath)`. [5](#0-4) 

In all three, `file.path` / `resolution.path` / `filepath` are paths that either come from the working tree of a repository the attacker can influence (a malicious clone/fetch introducing a tracked symlink) or from a link the user clicks. A tracked symlink such as `evil -> ../app-secrets/id_rsa` inside a repository named `app` would cause `realpath()` to resolve outside the repository into `app-secrets`, yet `_resolveWithin()`'s `startsWith` check would wrongly treat it as contained, because the guard never verifies that the character immediately following the shared prefix is a path separator (or that the strings are equal).

The existing unit tests only cover the ".." and symlink-to-completely-unrelated-directory cases, and never exercise the "sibling directory sharing a prefix" case, which is exactly the boundary condition the check is missing. [6](#0-5) 

### Impact Explanation
An attacker who controls the contents of a repository that the victim fetches/clones/checks out (e.g. via a malicious fork, PR branch, or fetched remote) can plant a tracked symlink whose target — once resolved — lands in a sibling directory sharing a name prefix with the repository directory. Depending on which call site is triggered:
- **Arbitrary file read outside the repo**, exfiltrated into the Copilot conflict-resolution AI context.
- **Arbitrary file write/corruption outside the repo**, if the resolved symlink target is used as the destination for `writeFile()` of AI-resolved conflict content.
- **Unintended file reveal via shell** from a clicked deep link.

This matches the report's underlying primitive: a validation function that is supposed to bind an operation to one specific, intended target but can be tricked into accepting a different one due to insufficient exactness in the check.

### Likelihood Explanation
Exploitation requires two conditions that are individually common but need to coincide: (1) the victim has (or can be made to have) a sibling directory whose name is a superstring of the repository's directory name at the same parent path, and (2) the attacker can get a tracked symlink into the victim's working tree (via clone/fetch/checkout/merge of attacker content) or get the victim to click a crafted deep link. Multi-repo development directories (e.g., `GitHub/app`, `GitHub/app-old`, `GitHub/app2`) are a realistic, everyday layout, making condition (1) plausible without any special user action; the guard's job is precisely to be safe regardless of what else exists on disk, and it currently is not.

### Recommendation
Fix `_resolveWithin()` in `app/src/lib/path.ts` to require an exact match or a match followed by a path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests for the sibling-directory-prefix case (e.g. root `.../app` vs. resolved `.../app-secrets/...`) for both POSIX and Windows separator variants.

### Proof of Concept
1. Victim has repositories cloned side-by-side: `/Users/victim/Documents/GitHub/app` (the target repo) and `/Users/victim/Documents/GitHub/app-secrets` (any other directory/repo containing sensitive files, e.g. `id_rsa`).
2. Attacker crafts a branch/PR for `app` that adds a tracked symlink `leak -> ../app-secrets/id_rsa` and creates a merge conflict on that path (or simply gets the victim to fetch/checkout it).
3. Victim opens the repository in Desktop, hits a merge conflict, and uses the Copilot AI-assisted conflict resolution flow, or otherwise triggers a code path that resolves `leak` via `resolveWithin('/Users/victim/Documents/GitHub/app', 'leak')`.
4. `realpath()` resolves `leak` to `/Users/victim/Documents/GitHub/app-secrets/id_rsa`. `_resolveWithin()` computes `realRoot = '/Users/victim/Documents/GitHub/app'` and checks `'/Users/victim/Documents/GitHub/app-secrets/id_rsa'.startsWith('/Users/victim/Documents/GitHub/app')`, which evaluates to `true`.
5. The guard returns the resolved path as "safe," and the caller proceeds to read (or write) content at a location entirely outside the `app` repository.
