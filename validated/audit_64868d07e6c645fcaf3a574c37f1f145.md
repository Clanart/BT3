Unauthenticated NFT "minter DID" attribution allows forging provenance/creator identity for any NFT - (File: chia/wallet/wallet_state_manager.py)

### Summary
`WalletStateManager.get_minter_did()` derives the "minter DID" shown to users and RPC clients for any NFT by reading the `-10` change-owner condition out of the eve-coin's own solution, or, if that is empty, by walking up to the parent coin and assuming it is a DID coin. Neither path cryptographically ties the reported minter DID to an actual authorized spend of that DID. This is directly acknowledged elsewhere in the same codebase: "eve coin DID can be set to whatever ... WARNING: wallets should always ignore DID value for eve coins as they can be set to any DID without approval" (`chia/wallet/nft_wallet/nft_wallet.py`). `get_minter_did` violates that warning by trusting the eve-coin-supplied DID value as ground truth and persisting/displaying it as `minter_did`.

### Finding Description
When an NFT eve coin (the very first singleton spend after the launcher) is created, the CLVM ownership layer does not require any DID-side authorization for setting the *initial* owner/minter value — this is explicitly documented in `nft_wallet.py`'s `generate_new_nft()`: [1](#0-0) 

which is precisely why the legitimate minting flow keeps the eve owner-DID field empty (`b""`) and only sets the real DID afterward via `get_did_approval_info()`, which requires an actual announcement from the DID wallet: [2](#0-1) 

However, `get_minter_did()` — used to populate the `minter_did` field returned to wallet RPC callers/UI for every NFT — reads whatever DID value an *arbitrary* eve-coin spend claims via the `-10` condition, with no verification that the named DID coin ever spent to authorize it: [3](#0-2) 

Because the ownership-layer puzzle's `-10` mode does not require asserting a puzzle announcement from the claimed DID on an eve spend (only material `puzhash`/change-owner conditions are enforced; see `nft_puzzle_utils.get_new_owner_did()`, which simply parses the condition without any authorization check): [4](#0-3) 

an attacker who mints their own NFT (their own coins, their own fee) can set the `-10` condition on the eve spend to any victim's DID `launcher_id`, and `get_minter_did` will report that victim's DID as the NFT's minter/creator with no cryptographic proof the victim ever approved it. If the `-10` field is left empty (the "correct"/warned-about default), `get_minter_did` falls back to inspecting the launcher's *parent* coin and, if that parent coin happens to curry as a DID puzzle, attributes minting to that DID (`chia/wallet/wallet_state_manager.py:1098-1111`) — again with no verifying announcement, singleton lineage check, or signature tying that DID's private key holder to this specific NFT mint.

This is the closest available analog to CVE-2017-18906: in the Mattermost bug, an external identity claim (an OAuth-provided email) was trusted to bind to/take over an internal account identity without verifying the claimant actually controlled that identity. Here, an externally-supplied identity claim (a DID launcher ID embedded in an unauthenticated coin spend) is trusted by wallet code to bind NFT provenance/creator attribution to a DID identity without verifying the DID owner authorized the association.

### Impact Explanation
This allows impersonation of a DID's creator identity: any user can forge the `minter_did` attribution on their own newly minted NFT to point at any real, existing DID (e.g. a well-known collection, artist, or verified-creator DID) they do not control. Because `minter_did`/`owner_did` is surfaced through wallet RPCs (`nft_get_nfts`, `get_nft_info`) and used by clients/marketplaces to establish "verified by DID X" provenance, this enables spoofed provenance that can deceive counterparties in an offer/trade (fraudulent attribution to increase perceived value or trick a buyer into thinking an NFT is part of a DID-verified collection), which is a form of forged asset identity within the Impact taxonomy (offer settlement/impersonation risk), even though it does not directly move funds. It does not grant control over the victim DID's coins, and does not by itself cause direct fund loss, mempool/consensus divergence, or double-spend — the impact is confined to identity/provenance forgery consumed by wallet clients and marketplaces that trust `minter_did`/`owner_did` fields without independently re-verifying DID authorization on eve spends.

### Likelihood Explanation
Trivial to trigger: an attacker only needs standard-wallet spend capability (mint fee coins) and knowledge of a target DID's public launcher ID (publicly visible on-chain). No special privileges, races, or peer cooperation are required — a single locally-crafted mint transaction (spend bundle) submitted through the normal NFT minting RPC path is sufficient, and the resulting "minter_did" misattribution is then reported by any full/wallet node processing that spend via `get_minter_did`/`manual_nft_search`.

### Recommendation
Do not trust the `-10` owner-DID field on eve (first) NFT spends as proof of DID authorization when computing `minter_did`. `get_minter_did()` and the parent-coin fallback path should require and verify an actual DID coin spend that creates a puzzle/coin announcement referencing the specific NFT launcher id (mirroring the verification already performed by `get_did_approval_info()` for post-mint DID assignment), and should reject/mark as "unverified" any DID attribution that cannot be tied to a real DID-authorized announcement. At minimum, expose a separate, clearly-labeled "unverified/claimed" attribution distinct from `minter_did` so wallet/marketplace consumers cannot conflate the two, consistent with the existing internal warning in `nft_wallet.py` about never trusting eve-coin DID values without approval.

### Proof of Concept
1. Note a target's DID launcher_id `victim_did` (public, e.g. from an on-chain DID coin they own).
2. Using an attacker-controlled wallet with any XCH balance, mint a new NFT via the standard mint RPC/flow (`NFTWallet.generate_new_nft`), but instead of leaving the eve-coin owner-DID empty as the legitimate flow does, construct/patch the eve-coin's `-10` condition argument to be `victim_did` (bypassing the wallet's normal safety of keeping it `b""`) — this only requires crafting the coin spend's solution program directly, since the CLVM ownership layer places no DID-authorization requirement on this field on an eve spend.
3. Push the resulting spend bundle; it succeeds because CLVM only checks conditions the ownership layer defines (create-coin/owner update), not any assertion tied to `victim_did`'s own DID coin.
4. Any wallet calling `WalletStateManager.get_minter_did()` (directly, or via `manual_nft_search`, `nft_get_nfts`, `get_nft_info`) on this new NFT will report `minter_did == victim_did`, attributing the mint to the victim DID despite the victim never approving or signing anything. def get_new_owner_did(unft: UncurriedNFT, solution: Program) -> Literal[b""] | bytes32 | None:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(solution))
    new_did_id: Literal[b""] | bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.first().as_int() == -10:
            # this is the change owner magic condition
            atom = condition.at("rf").as_atom()
            if atom == b"":
                new_did_id = b""
            else:
                new_did_id = bytes32(atom)
    return new_did_id
