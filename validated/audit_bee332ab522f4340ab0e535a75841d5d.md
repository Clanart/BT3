### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw()`/`SweepDust` causes silent escrow loss on Tron - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) deliberately avoids OpenZeppelin's `SafeERC20.safeTransfer` for its escrow-release paths and instead uses a raw low-level `.call` with the `IERC20.transfer` selector, checking only that the call itself did not revert (`success`), never decoding the returned boolean. This is the exact bug class described in the external report: tokens whose `transfer()` returns `false` on failure instead of reverting will be treated as a successful payout, while the internal escrow accounting is already decremented, permanently stranding the funds in the contract.

### Finding Description
In `withdraw()`, which is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse` for cancellations, the escrowed tokens are released like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the low-level call reverted, not whether the ERC20 `transfer` actually moved value. Per EIP-20, a compliant token may legally return `false` on failure (insufficient balance, blacklist, paused state, etc.) rather than reverting; in that case `success == true` even though `beneficiary` received nothing, and the code proceeds to decrement `_orders[body.commitment][token] -= amount` as if the payout succeeded. The identical pattern is repeated for the transaction-fee release [2](#0-1)  and in the `SweepDust` handler [3](#0-2) .

The contract even imports and aliases `SafeERC20` (`using SafeERC20 for IERC20;`) [4](#0-3)  and uses `safeTransferFrom`/`safeTransfer` correctly for inbound escrow and fee collection, but the outbound payout paths (`withdraw`, `SweepDust`) were written with the unchecked raw `.call` pattern instead — this is the same root cause the M-7 report describes for the AutoRoller contract: `transfer()` calls whose return value is never checked, versus other locations in the same codebase that correctly use `safeTransfer`. This directly contrasts with the mainline EVM `IntentsBase._withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`, which correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` [5](#0-4) .

### Impact Explanation
Once `_orders[body.commitment][token]` is decremented, the withdraw is considered finalized (`_filled[body.commitment] = beneficiary` is also set), and there is no other code path to retry or reclaim that escrow entry. If the escrowed input token is one that returns `false` on a failed `transfer` (rather than reverting) — e.g. due to a solver/beneficiary address being blacklisted by the token, the token being paused, or any other soft-failure condition — the beneficiary never receives the tokens, and the tokens remain permanently locked/lost inside the `IntentGatewayV2` contract with no accounting path back to any user. This is a direct fund-loss condition on escrowed order inputs and accumulated transaction fees, matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
This requires only that the escrowed input token (chosen by the order's `user` at order placement) be one of the well-known non-reverting ERC20/TRC20 implementations, or a token that can enter a state where `transfer` returns `false` instead of reverting (blacklist/pause functionality is common on Tron-native TRC20 tokens, e.g. USDT). No malicious relayer, prover, or governance actor is needed — the withdrawal path is reached through the normal cross-chain settlement/cancellation flow (`onAccept`/`onGetResponse`), which any legitimate order lifecycle triggers once a token in that class is used as an order input.

### Recommendation
Replace the raw `.call(...)` + `success`-only check in `withdraw()` (both the token loop and the fee release) and in the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the rest of the contract and with the non-Tron `IntentGatewayV2`/`IntentsBase` implementations. If `safeTransfer` is unusable for a specific Tron TRC20 quirk, at minimum decode and check the boolean return value (`success && (returndata.length == 0 || abi.decode(returndata, (bool)))`) before mutating `_orders`.

### Proof of Concept
1. Deploy a TRC20/ERC20-like token whose `transfer()` returns `false` instead of reverting when it cannot fulfill the transfer (e.g., recipient is on the token's internal blacklist, or contract is paused).
2. Place a cross-chain order on `IntentGatewayV2` using this token as an input; escrow it normally via `placeOrder`.
3. Have a solver fill the order on the destination chain and dispatch the `RedeemEscrow` message back to the Tron source chain, or trigger a `RefundEscrow`/cancellation flow.
4. Ensure the `beneficiary`/solver address is blacklisted (or the token is paused) at the moment `onAccept`/`onGetResponse` calls `withdraw()`.
5. Observe: `token.call(...transfer...)` returns `success = true` (no revert) with an ABI-encoded `false` in `returndata`, which is never checked; `_orders[body.commitment][token] -= amount` proceeds, `EscrowReleased`/`EscrowRefunded` is emitted, and the beneficiary's on-chain token balance is unchanged — the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no state left indicating an outstanding claim.
