### Title
Sibling-directory prefix collision in `resolveWithin` allows a malicious "Open in Desktop" deep link to reveal files outside the cloned repository - (File: `app/src/lib/path.ts`)

### Summary
The `_resolveWithin` helper, which is the sole guard used to keep a user-supplied `filepath` from a `x-github-client://openRepo/...?filepath=...` deep link inside the target repository, verifies containment with a bare `realResolved.startsWith(realRoot)` check with no trailing path-separator boundary. This is the same class of bug as the AlgebraPool report: a value that is *assumed* to always satisfy an invariant (there, "balance diff is always positive"; here, "a resolved path that starts with the root string is always inside the root directory") is used unguarded downstream, and the assumption is false at the boundary.

### Finding Description
`app/src/ui/dispatcher/dispatcher.ts` handles the `open-repository-from-url` deep-link action. After cloning/opening the attacker-referenced repository, it takes the `filepath` query parameter straight from the URL (parsed in `app/src/lib/parse-app-url.ts`, which does *not* validate `filepath` for `..` segments — only `branch` goes through `testForInvalidChars`) and passes it to `resolveWithin`: [1](#0-0) 

`resolveWithin` (`_resolveWithin`) normalizes and joins the segments, resolves an absolute path, `realpath`s both the root and the resolved path, and then checks containment with: [2](#0-1) 

`String.prototype.startsWith` performs a raw substring comparison with no separator check. If the repository's real path is `.../foo` and, on the victim's machine, a sibling directory such as `.../foo-secret` or `.../foobar` exists, then a resolved path of `.../foo-secret/creds.txt` will satisfy `realResolved.startsWith(realRoot)` even though it is *not* inside the repository root at all — it only shares a string prefix. The check that is supposed to be the single enforcement point for "stay inside the repo" is bypassed for any target whose parent-relative path traversal (`../`) lands on a sibling directory that happens to share a name prefix with the cloned repo.

This differs from a normal `..`-traversal bug (which `resolve`+`realpath` already defeats for arbitrary escapes) in that the flaw is specifically the *missing separator boundary* in the final containment check — exactly analogous to the AlgebraPool bug, where the code trusted an invariant (`amountRequired` diff is always ≥ 0 / here, "starts with root ⇒ inside root") that fails at an edge condition the author didn't account for.

### Impact Explanation
A successful exploit lets a remote, unprivileged actor who controls only a link (an `x-github-client://openRepo/...` URL a victim clicks, e.g. from a malicious "Open in Desktop" button on a web page or a crafted GitHub PR page) cause GitHub Desktop to resolve and act on (`shell.showItemInFolder`, revealing/opening) a file located outside the intended repository boundary, provided a same-prefix sibling directory exists — which is common in real developer setups (e.g. `~/src/project` and `~/src/project-old`, `~/src/project.bak`, monorepo variants, or organization-standard clone layouts where multiple repos share a base name). This fits the report's "file read outside the repo" impact class: the guard whose entire purpose is to stop exactly this is defeated by a boundary condition, not by disabling or skipping the check.

### Likelihood Explanation
Exploitability is gated on the existence of a sibling directory with a matching prefix next to the victim's clone of the targeted repository, which the attacker cannot control directly and can only guess/target opportunistically (e.g., targeting well-known repos cloned into predictable, prefix-colliding folder layouts, or combining this with the attacker's own `openRepo`/clone URL so the "root" and "sibling" are both attacker-influenced through the clone step). This makes it lower likelihood than a universal traversal bug, but it remains a genuine, unprompted, single-click deep-link path with no local access, admin rights, or prior compromise required — consistent with the required threat model (attacker controls only the link the user clicks).

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require a path-separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This closes the prefix-collision gap while preserving the existing intent of the function, and should be applied uniformly since `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are shared by other callers (`app-store.ts`, `copilot-conflict-context.ts`) that rely on the same invariant.

### Proof of Concept
1. Victim has cloned a repository to `/Users/victim/src/proj` and separately has an unrelated sensitive folder at `/Users/victim/src/proj-secrets/token.txt`.
2. Attacker crafts a deep link:
   `x-github-client://openRepo/https://github.com/victim/proj?filepath=..%2Fproj-secrets%2Ftoken.txt`
3. `parseAppURL` (`app/src/lib/parse-app-url.ts:98-124`) accepts this since `filepath` is not validated against traversal.
4. `dispatcher.openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1940-1973`) confirms `filepath` is not absolute, then calls `resolveWithin(repository.path, filepath)`.
5. Inside `_resolveWithin` (`app/src/lib/path.ts:36-72`), `resolve()` produces `/Users/victim/src/proj-secrets/token.txt`; `realResolved.startsWith(realRoot)` (`realRoot = /Users/victim/src/proj`) evaluates `true` due to the missing separator, so the function returns the out-of-repo path instead of `null`.
6. `shell.showItemInFolder(resolved)` is invoked on the attacker-chosen out-of-repository file, confirming the boundary bypass.
