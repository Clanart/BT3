### Title
Stale line-index selection allows silently committing unreviewed content after the diff changes underneath a pending partial commit - (File: `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop tracks partial-commit line selections by absolute diff-line index rather than by the underlying content of the line. When the working-directory diff for the currently selected file is reloaded (`updateChangesWorkingDirectoryDiff`), the code only clears a selected index if that index no longer exists or has degraded into a context line — it does not verify that the content at a still-valid index is still the content the user actually selected. This is the same class of bug as the reported `MarinateV2.migrateToken` issue: a derived accounting/state value (`totalTokenRewardsPerStake` there, the line-selection state here) is not recomputed/invalidated when the underlying data it depends on changes, so a stale value is used downstream and produces an incorrect result (loss of funds there; committing unintended/unreviewed diff content here).

### Finding Description
`updateChangesWorkingDirectoryDiff` reloads the diff for the single selected file whenever the working directory changes (e.g. status refresh, file watcher tick, background operation): [1](#0-0) 

The comment in the code explicitly acknowledges the gap:
> "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines such that any previously selected line which now no longer exists or has been turned into a context line isn't still selected."

In other words, `withSelectableLines` only drops indices that are no longer includeable; it never re-validates that a still-includeable index at the same `hunk.unifiedDiffStart + lineIndex` position still refers to the same line content the user reviewed and checked. If the file's hunks shift (lines added/removed elsewhere, or the file is rewritten in a way that keeps a comparable hunk shape), the same absolute index can end up pointing at completely different `Add`/`Delete` line text.

That stale, index-based selection state is exactly what is later consumed to build the commit patch: [2](#0-1) 

`formatPatch` calls `file.selection.isSelected(absoluteIndex)` against the *new* diff's lines using indices chosen against the *old* diff. This patch is then applied straight to the index with `git apply --cached`: [3](#0-2) 

There is no re-diff/re-confirmation step between the moment the user checks specific lines in the UI and the moment `_commitIncludedChanges` builds the commit from `file.selection`: [4](#0-3) 

This mirrors the audit report's root cause precisely: a dependent/derived value (`totalTokenRewardsPerStake` / line-selection-to-content mapping) is not recalculated when the thing it depends on (staked balances / diff hunks) changes, so a stale value silently drives a downstream, security-relevant operation (reward payout / commit content).

### Impact Explanation
If the working directory content for the file under review changes (via an external process, an editor autosave, a build/format-on-save tool, an LFS smudge filter running after a background fetch/pull, or any other tool that rewrites the file while Desktop's diff is open with a partial selection), the user can end up committing and pushing lines they never saw or explicitly approved, while lines they did approve may be silently dropped. Because this is the core "what did the user actually agree to commit" contract of git client software, a mismatch here is a silent corruption of what the user commits — the value class explicitly called out as in-scope ("silent corruption of what the user commits or pushes"). This can leak content the user did not intend to share (e.g. accidentally including secrets/at that stayed unselected) or push code the user never reviewed.

### Likelihood Explanation
This requires a timing window: the file whose diff is being partially staged must change on disk after Desktop has computed/rendered the diff and the user has made line selections, but before the commit is created. Desktop's own status refresh / file-watcher driven re-diff (`updateChangesWorkingDirectoryDiff`) runs automatically and frequently, so the window is not contrived, but an external actor needs a way to modify that specific file during that window (e.g. a git filter/smudge process associated with LFS-tracked content in an attacker-supplied repository, or another background tool). This is a plausible but not trivially exploitable scenario, and the code comment itself flags it as a known, accepted limitation rather than an already-fixed edge case — moderate likelihood.

### Recommendation
When reloading the diff for a selected file, don't just recycle the previous `DiffSelection` bitset against new indices. Either:
- Invalidate ("select none"/warn) any partial selection whenever the diff hash/content of a hunk changes rather than only when a line index disappears or turns into context, or
- Re-anchor selections to line content (hash of line text + position) instead of raw absolute index, so a content mismatch clears the selection instead of silently carrying it forward, or
- Re-diff and re-validate immediately before `_commitIncludedChanges` builds the patch, refusing to commit if the diff used to build the patch differs from the diff currently backing the file's selection.

### Proof of Concept
1. In a repository, modify `foo.txt` so it has multiple independent hunks; open it in Desktop's Changes view.
2. Partially select specific "+" lines in one hunk (uncheck others).
3. Before committing, cause `foo.txt` to be rewritten on disk (e.g., have an external process such as an LFS smudge filter, formatter-on-save, or another git operation append/remove lines earlier in the file) such that hunk boundaries shift but the previously selected absolute line indices remain within an `Add`/`Delete` line of the new diff.
4. Desktop's status watcher triggers `updateChangesWorkingDirectoryDiff`, which reloads the diff and calls `withSelectableLines` — because the indices are still "includeable," the old selection bitset survives unchanged (`app/src/lib/stores/app-store.ts:3478-3497`).
5. Click Commit. `formatPatch` (`app/src/lib/patch-formatter.ts:129-170`) builds the patch using the stale selection against the new diff, and `applyPatchToIndex`/`git apply --cached` (`app/src/lib/git/apply.ts:52-83`) stages content the user never reviewed under the lines they thought they had selected.   file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // never appear for new files.

        hunkBuf += `${line.text}\n`

        newCount++
