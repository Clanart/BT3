### Title
Unauthenticated `address` field in `handle_get_requests` lets any unprivileged caller redirect relayer reputation payouts to itself - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`pallet-state-coprocessor::handle_get_requests` mints `ReputationAsset` (a real, transferable fungible asset shared with `pallet-messaging-incentives`) to whatever account is named in the caller-supplied `address: Vec<u8>` field of `GetRequestsWithProof`, with no cryptographic binding between that address and the entity that actually delivered the proof. The call is dispatched as an **unsigned** extrinsic (`ensure_none`), so any unprivileged party who can assemble a valid state/consensus proof for an already-dispatched `GetRequest` can submit it first and claim the reward for an address of their choosing — including their own — while the party that actually did the relaying work gets nothing. This mirrors the M-22 pattern: a value that determines a payout/charge (`address`, analogous to the attacker-inflatable dictionary) is trusted at face value with no completeness/ownership check tying it back to genuine, proportional work.

### Finding Description
`GetRequestsWithProof` carries a free-form `address: Vec<u8>` field described only as "Address that should be credited with fees": [1](#0-0) 

`handle_get_requests` verifies the source-chain membership proof and the destination-chain state proof for the requests, then unconditionally mints reputation to that `address`: [2](#0-1) [3](#0-2) 

Note the comment at line 166: `address` is converted directly into an `AccountId` and credited — there is no signature check, no relationship asserted between `address` and the transaction submitter, and no relationship to whichever party actually retrieved/attested the state proof data.

Contrast this with the sibling reward path in `pallet-messaging-incentives`, which recovers the reward recipient from a cryptographic signature embedded in the message rather than trusting a bare field: [4](#0-3) 

The entry point that carries the attacker-controlled `address` is dispatched with `ensure_none`, i.e. it is an unsigned transaction accepted from anyone whose payload passes `validate_unsigned` (which only re-runs proof verification, not any identity check): [5](#0-4) [6](#0-5) 

Because the requests being proven are public data already committed on the source chain (any `GetRequest` an app dispatched), and the state values being proven are public storage on the destination chain, an unprivileged observer needs no special relayer key or role to construct a valid `GetRequestsWithProof` — they only need to win the race to submit it with `address` set to their own account.

### Impact Explanation
`ReputationAsset::mint_into` mints real fungible tokens (`Assets` pallet asset) directly to the named account: [7](#0-6) 

Since minted amount scales with `total_bytes` (the abi-encoded size of the proven `GetResponse`s), an attacker can systematically front-run genuine relayers on high-value Get-response deliveries, submitting the same publicly-derivable proof first with themselves as `address`, capturing the reputation reward that was meant to compensate whoever actually did the relaying work. This is a direct "wrong beneficiary" fund-diversion: value moves to an unentitled party rather than the rightful relayer, with no on-chain check preventing it. It does not require a compromised relayer, prover, or admin — any party capable of reading public request/response data and assembling a proof can do this.

### Likelihood Explanation
High. `handle_unsigned` is explicitly an unsigned, mempool-gossiped call (`propagate: true` in `validate_unsigned`), meaning any node can observe a pending or minable `GetRequestsWithProof` and resubmit it with a modified `address`, or independently construct their own proof for any request they see committed on a source chain. The only gating conditions are proof validity and non-duplication of the underlying `GetResponse` (via `response_receipt`) — neither of which restricts who may claim the reward field.

### Recommendation
Bind the reward recipient to a verifiable identity rather than a bare `address: Vec<u8>` field, mirroring `pallet-messaging-incentives::relayer_for`: require an sr25519 (or equivalent) signature over the message contents and recover the account from that signature, or otherwise cryptographically tie `address` to the actual submitter of the unsigned extrinsic (e.g., via a signed payload/nonce scheme) before minting `ReputationAsset`.

### Proof of Concept
1. App `A` on a source chain dispatches a `GetRequest` for some public storage key on a destination chain; the request commitment lands on-chain and is publicly observable.
2. A relayer `R` begins assembling `source` (membership) and `response` (state) proofs to submit `GetRequestsWithProof { requests, source, response, address: R }` via `handle_unsigned`.
3. Attacker `M`, who is not running any relaying infrastructure and has no privileged role, observes the same public commitments and independently (or by copying `R`'s broadcast unsigned transaction and only mutating the `address` field) constructs/obtains an equally valid `GetRequestsWithProof` with `address: M`.
4. `M` submits first (or gets included first by the block author). `Pallet::handle_get_requests` verifies the proofs successfully (they are valid, since they attest real public state) and mints `ReputationAsset` to `M` per `impls.rs:166-176`.
5. `R`'s subsequent submission for the same requests fails the `response_receipt` duplicate check (`impls.rs:94-102`), so `R` receives nothing despite having done identical or greater relaying work.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
