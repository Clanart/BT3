Based on the codebase investigation, the report's hint about undocumented `getCumulativeReward`/`totalWithdrawnReward`-style accounting maps to a concrete, exploitable bug in the actual reward-forfeiture accounting of `mWOMSVBaseRewarder`, reachable by any ordinary staker who calls `getReward`/`getRewards`.

### Title
Broken expire-forfeit calculation in `mWOMSVBaseRewarder` permanently prevents redistribution of forfeited yield to other lockers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder` implements a "forfeit" mechanism intended to claw back part of a user's earned reward and redistribute it to other stakers via `_queueNewRewardsWithoutTransfer` (emitting `ForfeitRewardAdded`). However, the internal helper that computes the forfeit amount, `_calExpireForfeit`, is a no-op: it always returns `0`, so no forfeiture is ever applied and the intended redistribution to the remaining honest lock holders never happens.

### Finding Description
`_calExpireForfeit` in `mWOMSVBaseRewarder.sol` is implemented as: [1](#0-0) 

```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
```
`rewardableAmount` is set equal to `_amount` itself, so `forfeitAmount = _amount - rewardableAmount` is always `0`; the `_account` parameter is never used to look up any actual forfeit percentage. This is called from `_sendReward` on every `getReward`/`getRewards` claim: [2](#0-1) .

For comparison, the sibling contract `vlMGPBaseRewarder` implements the equivalent function correctly by querying the actual lock contract for a rewardable percentage: [3](#0-2) 

```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
```
The `mWOMSVBaseRewarder` version never calls `mWOMSV`/`ILocker` to fetch any equivalent forfeit percentage, despite having the reference to `mWOMSV` (`ILocker public mWOMSV;`) available at [4](#0-3) . The infrastructure for forfeiture (the `ForfeitRewardAdded` event, `_queueNewRewardsWithoutTransfer`, and the subtraction logic in `_sendReward`) is present but functionally dead, meaning the contract was clearly designed to forfeit and redistribute part of the reward for users who don't meet some condition (e.g., early exit / cooldown), but this never actually triggers.

### Impact Explanation
Because forfeiture never fires, 100% of the accrued `mWOMSVBaseRewarder` reward flows to the claimant regardless of the account-specific condition the forfeit was meant to check, and the portion that should have been redirected into `rewardInfo.rewardPerTokenStored` for redistribution to the remaining `mWOMSV` holders (via `_queueNewRewardsWithoutTransfer`) is never created. This permanently deprives the legitimate remaining lockers of yield they were entitled to receive under the intended accounting model, which falls under theft/permanent freezing of unclaimed yield for other unprivileged users of the pool.

### Likelihood Explanation
This triggers on every single call path through `getReward`/`getRewards` for any account and reward token registered on `mWOMSVBaseRewarder` — there is no special precondition, admin action, or attacker skill required. It is a deterministic, always-on logic error rather than a rare edge case.

### Recommendation
Implement `_calExpireForfeit` in `mWOMSVBaseRewarder` to actually compute a rewardable percentage from the `mWOMSV` locker state (analogous to `vlMGPBaseRewarder`'s use of `vlMGP.getRewardablePercentWAD(_account)`), instead of unconditionally setting `rewardableAmount = _amount`.

### Proof of Concept
1. Deploy/observe `mWOMSVBaseRewarder` with rewards queued via `queueNewRewards`.
2. Any account with a positive `earned(_account, _rewardToken)` calls `getReward` (through `MasterMagpie`).
3. Inside `_sendReward`, `_calExpireForfeit(_account, userRewards[_rewardToken][_account])` is invoked; trace shows `rewardableAmount` is assigned `_amount` on line 386, making the line 387 check always false and `forfeitAmount` on line 390 always `0`.
4. `toSend` therefore always equals the full `userRewards[...]` balance, and `_queueNewRewardsWithoutTransfer` on line 374-375 is never called with a non-zero amount, so no forfeited yield is ever redistributed to other `mWOMSV` holders, regardless of the account's actual lock/cooldown status.
