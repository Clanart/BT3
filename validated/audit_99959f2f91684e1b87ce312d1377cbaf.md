Based on the investigation, the strongest analog to the reported "USDC pause/blacklist stuck funds" bug class exists in sei-chain's `x/bank` `AllowList`/`BlockedAddr` mechanism combined with `MsgMultiSend`, and it turns out the codebase has specific defensive handling for the staking/distribution EndBlock paths but the `MsgMultiSend` atomic-revert behavior is directly analogous and reachable by any transaction sender.

### Title
Atomic revert of `MsgMultiSend` on a single blocked/non-allow-listed output address lets an attacker grief batched payouts - ([File: sei-cosmos/x/bank/keeper/msg_server.go])

### Summary
`x/bank`'s `MsgMultiSend` handler validates every input against `IsInDenomAllowList` and every output against `BlockedAddr`/`IsInDenomAllowList` before calling `InputOutputCoins`, and if **any single** output address is blocked or not on the token-factory denom's allow list, the **entire** multi-send transaction is rejected, exactly mirroring the reported USDC-pause/blacklist bug class where one bad recipient blocks a whole batched settlement.

### Finding Description
`msgServer.MultiSend` loops over every input and output and returns an error immediately if a single output address fails `BlockedAddr` or `IsInDenomAllowList`, before any transfer occurs: [1](#0-0) 

The `IsInDenomAllowList` check applies specifically to `factory/...` tokenfactory denoms, so any tokenfactory denom creator can set a restrictive allow list, and any subsequent `MsgMultiSend` payout involving even one non-approved recipient among many will fail atomically: [2](#0-1) 

This is architecturally the same failure mode as the audited `CrabNetting.sol` bug: a batch operation (there, `netAtPrice()`/`withdrawAuction()`; here, `MsgMultiSend`) must succeed for *every* recipient in the batch, and a single non-compliant/blocked recipient causes the whole batch to revert, with no mechanism to skip or exclude just that recipient.

Separately, the codebase shows it is aware of this bug class for the *EndBlock* unbonding/reward-withdraw paths and has already hardened them defensively — `staking`'s `CompleteUnbonding`/`EndBlocker` and `distribution`'s `SetWithdrawAddr`/`AfterValidatorRemoved` explicitly check `CanSendTo`/`BlockedAddr` up front and skip or fall back rather than reverting the whole block: [3](#0-2) [4](#0-3) 

That EndBlock hardening does **not** extend to the transaction-level `MsgMultiSend` path, which remains fully atomic and user-reachable.

### Impact Explanation
Any account holding a token-factory denom with a configured `AllowList` (or a bank-blocked recipient in a batch) can be griefed: a legitimate multi-recipient payout (e.g., payroll, airdrop, auction settlement) that includes even one non-compliant address will always fail, blocking the sender from paying the other, valid recipients in that same message. Since Cosmos SDK/Sei transactions are atomic per-message, the sender must manually identify and exclude the bad address and resubmit, which is not always possible for automated on-chain batch-payout contracts (CosmWasm contracts constructing `BankMsg::Send`/`MsgMultiSend` in a loop) that assume all outputs will succeed. This matches the reported "Medium" pattern of impaired core functionality/denial-of-service on batched fund movement, though it does not by itself cause fund loss or permanent freezing (senders retain full control of their own funds and can retry after excluding the bad address).

### Likelihood Explanation
Reaching this requires only: (1) creating a tokenfactory denom and setting a restrictive `DenomAllowList` (a normal, permissionless tokenfactory admin action), and (2) any account (the admin or a third party who received such tokens) submitting a `MsgMultiSend` that includes a disallowed recipient among its outputs. Both actions are available to any unprivileged tokenfactory denom creator/public transaction sender, making this a straightforward, no-privilege interaction.

### Recommendation
Consider either (a) validating all output addresses against `BlockedAddr`/`IsInDenomAllowList` at message construction/CLI time so senders can filter bad recipients before submission (already partially done via wallets), or (b) exposing a non-atomic multi-send variant that lets the sender opt into "best-effort" delivery, skipping restricted outputs and returning the remainder, similar to the defensive fallback logic already implemented in `x/staking`/`x/distribution` for EndBlock paths. At minimum, document that `MsgMultiSend` is fully atomic with respect to allow-list/blocklist checks so downstream contract authors (e.g., CosmWasm batch-payout contracts) design around it.

### Proof of Concept
1. Create a tokenfactory denom `factory/<admin>/comp` and set a `DenomAllowList` containing only a subset of intended recipients via `SetDenomAllowList` (exercised by `TestMultiSendAllowList` in the test suite): [5](#0-4) 
2. Fund the sender with the denom and submit `MsgMultiSend` with `Outputs` containing both an allow-listed and a non-allow-listed address.
3. Observe the entire `MsgMultiSend` fails with `"<addr> is not allowed to receive funds"`, and none of the outputs — including the compliant ones — receive funds, as demonstrated by `TestSendReceiverNotInAllowList`: [6](#0-5)

func (k msgServer) MultiSend(goCtx context.Context, msg *types.MsgMultiSend) (*types.MsgMultiSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	denomToAllowListCache := make(map[string]AllowedAddresses)
	// NOTE: totalIn == totalOut should already have been checked
	for _, in := range msg.Inputs {
		if err := k.IsSendEnabledCoins(ctx, in.Coins...); err != nil {
			return nil, err
		}
		accAddr := sdk.MustAccAddressFromBech32(in.Address)
		if !k.IsInDenomAllowList(ctx, accAddr, in.Coins, denomToAllowListCache) {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", accAddr)
		}
	}

	for _, out := range msg.Outputs {
		accAddr := sdk.MustAccAddressFromBech32(out.Address)

		if k.BlockedAddr(accAddr) || !k.IsInDenomAllowList(ctx, accAddr, out.Coins, denomToAllowListCache) {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", out.Address)
		}
	}

	err := k.InputOutputCoins(ctx, msg.Inputs, msg.Outputs)
	if err != nil {
		return nil, err
	}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (k Keeper) canReceiveWithdrawAddr(ctx sdk.Context, withdrawAddr sdk.AccAddress) bool {
	// BlockedAddr mirrors the gate SendCoinsFromModuleToAccount actually enforces:
	// beyond the module-account blocklist it also rejects dynamically-derived
	// addresses such as the EVM coinbase addresses (an "evm_coinbase"-prefixed
	// address), which CanSendTo does not catch. Consulting it here keeps this
	// predicate in lockstep with the send, so AfterValidatorRemoved never concludes
	// an address is receivable and then panics on the resulting bank error.
	return !k.blockedAddrs[withdrawAddr.String()] &&
		!k.bankKeeper.BlockedAddr(withdrawAddr) &&
		k.bankKeeper.CanSendTo(ctx, withdrawAddr)
}
