### Title
Untrusted `.claude/hookify.*.local.md` rule files committed to a repo are auto-loaded and silently activated on `UserPromptSubmit` without user approval - (File: `plugins/hookify/hooks/userpromptsubmit.py`)

### Summary
`load_rules()` in `plugins/hookify/core/config_loader.py` discovers rule files purely by filesystem glob (`os.path.join('.claude', 'hookify.*.local.md')`) with no provenance, ownership, or git-tracked/untracked check, and no user-approval gate. If an attacker commits a `.claude/hookify.<name>.local.md` file into a repository (violating the documented convention that these files "should be git-ignored"), the file is auto-discovered and its rule is enforced the moment the victim's Claude Code session (with the hookify plugin already enabled) submits its first prompt in that checkout.

### Finding Description
`userpromptsubmit.main()` reads stdin JSON and calls `load_rules(event='prompt')` [1](#0-0) . `load_rules()` globs `.claude/hookify.*.local.md` relative to the current working directory with no distinction between files the user authored/approved and files that arrived as ordinary repository content: [2](#0-1) . Any matching file is parsed by `load_rule_file()`/`extract_frontmatter()` and turned into a `Rule` object with attacker-controlled `enabled`, `event`, `pattern`, `action`, and `message` fields — no schema/allowlist restricts these, and `action` accepts arbitrary `warn`/`block` values [3](#0-2) . `RuleEngine.evaluate_rules()` then matches the rule's regex against the submitted prompt/tool input and, if it matches, injects the attacker's `message` text into the hook's `systemMessage` output shown during prompt handling [4](#0-3) . There is no step anywhere in this path — `userpromptsubmit.py`, `load_rules`, `load_rule_file`, or `RuleEngine` — that checks whether the rule file is git-tracked, was authored by the user, or has been explicitly approved; the plugin's own documentation only *recommends* gitignoring these files as a convention, it is not enforced [5](#0-4) .

### Impact Explanation
The practical impact for the `UserPromptSubmit` event is limited to arbitrary attacker-controlled text being injected as a `systemMessage` on every prompt (or every prompt matching a regex the attacker chooses, e.g. `.*` for every prompt), enabling persistent prompt-injection/social-engineering content or a UX-level denial-of-nuisance against the victim without their consent — this is achieved purely through markdown/YAML content, not code execution. Note that in `RuleEngine.evaluate_rules()`, `action: block` only produces a real blocking `hookSpecificOutput` (`permissionDecision: deny`) for `PreToolUse`/`PostToolUse`/`Stop` events; for `UserPromptSubmit` it falls into the generic `else` branch and only returns a `systemMessage`, so it does not actually block prompt submission [6](#0-5) . This confirms the exploitable behavior is confined to unauthorized message injection into the session, not command execution, file mutation, or full prompt blocking. This is a real, but scoped, trust-boundary violation: repository content becomes automatically-effective "hook policy" without any explicit user review/approval step distinct from the (already-consented) installation of the hookify plugin itself.

### Likelihood Explanation
Preconditions: the victim must have the hookify plugin already installed/enabled in Claude Code (a prerequisite the attacker cannot control), and must clone/open a repository containing the attacker's committed `.claude/hookify.<name>.local.md` file, then submit any prompt. Given those preconditions, the exploit is fully deterministic and repeatable — the glob-based, unauthenticated auto-load logic in `load_rules()` guarantees discovery and activation on the very first `UserPromptSubmit` event, with no retry or timing dependency.

### Recommendation
Add an explicit trust/approval gate before rule files are loaded from a workspace: e.g., only load rule files that are not part of the tracked git tree (or conversely, warn/refuse to load ones that are tracked and unreviewed), require a one-time interactive confirmation (similar to Claude Code's project-trust prompts) the first time a new `.claude/hookify.*.local.md` file is seen in a given project, and persist that approval (e.g., by hash) so future edits to an approved file require re-approval. At minimum, `load_rules()`/`load_rule_file()` should refuse silently-appearing new rule files that are part of freshly cloned/checked-out repository content until the user has reviewed them via `/hookify:list` or `/hookify:configure`.

### Proof of Concept
1. Create a fixture git repo with `.claude/hookify.evil.local.md` containing:
   ```
   ---
   name: evil
   enabled: true
   event: prompt
   action: warn
   pattern: .*
   ---
   ATTACKER CONTROLLED MESSAGE
   ```
   and commit it (simulating an attacker's PR/clone).
2. `cd` into the fixture repo, set `CLAUDE_PLUGIN_ROOT` to the hookify plugin path, and invoke `python3 plugins/hookify/hooks/userpromptsubmit.py` with `{"hook_event_name": "UserPromptSubmit", "prompt": "hello"}` piped to stdin.
3. Assert the JSON printed to stdout contains `"systemMessage"` equal to `"**[evil]**\nATTACKER CONTROLLED MESSAGE"`, proving the rule from the committed file was loaded and enforced without any explicit approval step from the user, `load_rules()` returning it purely via `glob.glob` discovery [7](#0-6) .
