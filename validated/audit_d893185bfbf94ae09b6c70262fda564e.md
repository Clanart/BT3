### Title
Cached deterministic FROST preprocess reused across multiple `share`/`complete` calls under one context enables remote recovery of the validator MuSig secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a single 32-byte `CachedPreprocess` seed in the DB keyed only by `context = (b"DkgConfirmer", attempt)` and never invalidates or rotates it. Every call to `share_internal` — reachable via `DkgConfirmer::share` and again inside `DkgConfirmer::complete` — rebuilds the sign machine via `AlgorithmSignMachine::from_cache`, which deterministically re-derives the same FROST nonces `(d, e)` through `seeded_preprocess` (`ChaCha20Rng::from_seed`). The nonces are therefore fixed for the entire attempt, while the per-participant binding factors `rho_i` and the challenge `c` are fully determined by attacker-supplied `preprocesses` (parsed via `read_preprocess`) and the `key_pair` message. Each `share` call publishes a fresh linear equation in the fixed unknowns `{d, e, secret_share}`; collecting three distinct shares lets an unprivileged submitter solve for the coordinator's MuSig secret share — the same hot-key-compromise outcome as the reference incident.

### Finding Description
- `preprocess_internal` writes the encrypted seed once (`CachedPreprocesses::set`) and thereafter always loads it (`CachedPreprocesses::get ... unwrap`), decrypting and calling `from_cache` (`coordinator/src/tributary/signing_protocol.rs:123-145`). There is no "already signed" flag, no deletion after `sign`, and no check that a subsequent call uses the same preprocess set or message — the file's own header flags the missing guard: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (`signing_protocol.rs:50-54`).
- `from_cache` calls `seeded_preprocess`, which derives both nonces from `ChaCha20Rng::from_seed(*seed.0)` via `Commitments::new` → `Curve::random_nonce` (`crypto/frost/src/sign.rs:121-144`, `crypto/frost/src/nonce.rs:58-61`). Same seed ⇒ identical `(d, e)` every time.
- `share_internal` sorts attacker-controlled `serialized_preprocesses` keys, deserializes each via `read_preprocess`, and calls `machine.sign(preprocesses, msg)` (`signing_protocol.rs:150-180`). In `sign`, the binding factor `rho_i = hash_binding_factor(...)` is computed over the *other* participants' commitments and the message — both attacker-influenced — while the local share has the form `s_i = d + e·rho_i + λ_i·secret·c` (`crypto/frost/src/sign.rs:283-318` and the FROST share formula in `spec/cryptography/FROST.md`).
- `complete` re-invokes `share_internal` (`signing_protocol.rs:321-324`), so completion itself is a second deterministic signing; and `share` can be invoked repeatedly per attempt since nothing records that a share was already published.

Each invocation emits one equation `s_j = d + e·rho_ij + λ·x·c_j` where `rho_ij` varies with the supplied commitment set and `c_j` varies with the `key_pair` message. The unknowns `{d, e, x}` (x = secret share) are constant across the attempt. Three published shares with pairwise-distinct `(rho_ij, c_j)` yield a 3×3 linear system over the scalar field that recovers `x` directly — no discrete log, no collusion, no BFT violation required beyond causing the coordinator to process multiple confirmation sign requests for the same attempt (e.g., a `share` followed by a `complete`, or repeated share transactions carrying different preprocess sets/key_pairs).

### Impact Explanation
Critical. Recovery of `x` yields the validator's MuSig secret share for the set — the coordinator's root-of-trust signing key share. Combined with the publicly computable Lagrange/interpolation structure (`ThresholdKeys::new`/`view`), possession of threshold-many recoverable shares (or this share plus known offsets) enables forgery of set-key confirmations, i.e., an attacker can sign `set_keys_message` for an attacker-chosen `KeyPair`, confirming a malicious DKG key and thereby controlling the network keys that custody funds — the direct analog of a hot-wallet key drain. Per `CachedPreprocess` docs, reuse "will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`, `209-213`).

### Likelihood Explanation
Medium–High. Triggering requires only that `share`/`complete` be invoked more than once under a single `(DkgConfirmer, attempt)` context with differing `preprocesses` maps or `key_pair` — inputs parsed from untrusted bytes via `read_preprocess`/`read_share`. The design relies entirely on BFT message ordering plus the explicitly-acknowledged missing on-chain commitment check; any logical path that feeds a distinct preprocess set or message into `share_internal` (duplicate confirmation transactions, `share` then `complete` with different shares/preprocesses, or a rebuild that re-executes with different finalized data while the DB-cached seed persists) produces nonce reuse. The persistence of the seed in the DB means restarts do not re-randomize nonces, contradicting the header's assumption that "upon any complete rebuild, we'd re-decide nonces."

### Recommendation
- Record the exact preprocess commitments and message hash alongside the cached seed; on any subsequent `share`/`complete` under the same context, reject unless both match byte-for-byte (implementing the noted TODO).
- Delete or mark-consumed the `CachedPreprocesses` entry after the first successful `sign`, and never call `share_internal` twice for one logical signature (have `complete` reuse the machine/share produced by `share` rather than re-signing).
- Prefer fresh `OsRng`-seeded preprocesses per signing instance over DB-persisted deterministic seeds; if caching is retained for re-execution, bind the cache key to the full signing context including the canonical preprocess set and message digest.

### Proof of Concept
1. Within a single DKG attempt, cause the coordinator to execute `DkgConfirmer::share(preprocesses_A, key_pair)` — obtaining share `s_1 = d + e·rho_1 + λ·x·c_1` broadcast as the `[u8; 32]` share.
2. Cause a second invocation with a different participant commitment set (`preprocesses_B`, altering `rho_2`) or a different `key_pair` (altering `c_2`) — e.g., via `complete(preprocesses_B, key_pair', shares)`, which internally re-signs (`signing_protocol.rs:321-324`). Obtain `s_2`.
3. Repeat once more for `s_3`. Since the seed is DB-persisted under `("DkgConfirmer", attempt)`, `d` and `e` are identical across all three; `rho_j` and `c_j` are recomputable offline from the published preprocesses and `set_keys_message`.
4. Solve `⎡1 ρ₁ λc₁⎤·⎡d e x⎤ᵀ = ⎡s₁ s₂ s₃⎤ᵀ` over the Ristretto scalar field → recover `x`, the validator's MuSig secret share, without any discrete-log computation.

Note: end-to-end reachability of step 2 depends on the tributary transaction handlers in `coordinator/src/tributary/handle.rs` permitting multiple `share`/`complete` invocations per attempt with attacker-distinct inputs; the cryptographic weakness itself — unconditional deterministic nonce reuse with no same-input guard — is fully present in `signing_protocol.rs` and `crypto/frost/src/sign.rs`.
