### Title
Untrusted `ReceivedOutput` bytes can falsely claim another transaction output as spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without verifying that they describe an output actually received and spendable by the wallet. This allows an unprivileged party to serialize a reference to someone else's UTXO—or a wallet UTXO with an incorrect value—and have it represented as a `ReceivedOutput`, analogous to claiming a victim's pending withdrawal through a publicly enumerable request ID.

### Finding Description
`ReceivedOutput` represents “a spendable output” and consists of an offset, an output, and an outpoint. [1](#0-0) 

Its deserializer independently reads all three attacker-controlled fields and immediately returns a `ReceivedOutput`. It does not verify that `offset` derives `output.script_pubkey`, that `outpoint` exists, or that `output` matches the output referenced by `outpoint`. [2](#0-1) 

This bypasses the provenance check performed by `Scanner::scan_transaction`, which only constructs `ReceivedOutput` for transaction outputs whose script was previously registered to an offset and binds the result to the real transaction ID and output index. [3](#0-2) 

`SignableTransaction::new` subsequently trusts the claimed `TxOut.value` as available input value and uses the claimed `OutPoint` as the transaction input. [4](#0-3) 

Although `SignableTransaction::multisig` checks that the supplied offset derives the claimed `script_pubkey`, it does not check that the referenced on-chain output has the claimed value or that the `TxOut` equals the actual prevout. [5](#0-4) 

### Impact Explanation
An attacker can cause funds to be reported as received or spendable when they are not. For example, serialized bytes can name a victim's UTXO and associate it with an arbitrary `TxOut` value and offset. Any inventory or accounting layer accepting `ReceivedOutput::read` as proof of receipt can credit the wallet for value the wallet does not control.

If the attacker uses a valid wallet-controlled script and known offset but inflates the serialized `TxOut.value`, `SignableTransaction::new` counts the inflated amount as input value. The resulting spend is based on a false prevout and cannot be validly confirmed by Bitcoin, even though the wallet may have already recorded the output as received.

### Likelihood Explanation
The input required is only serialized transaction data passed to `ReceivedOutput::read`; Bitcoin outpoints, output scripts, and output amounts are public. The attacker does not need a validator role, private key material, or control over a consensus peer.

Successful exploitation depends on an application accepting serialized `ReceivedOutput` values as an authoritative record of scanned outputs rather than treating them as unverified data. The type's API presents the decoded object as “a spendable output,” making that trust boundary plausible.

### Recommendation
Do not expose `ReceivedOutput::read` as an authoritative reconstruction of spendable wallet state.

At minimum:

1. Validate that `offset` derives `output.script_pubkey` for the wallet's base key before returning a `ReceivedOutput`.
2. Treat deserialized `ReceivedOutput` values as unverified until their `OutPoint` and full `TxOut` are checked against confirmed chain data.
3. Prefer serializing scanner state or returning an explicit unverified type rather than allowing arbitrary bytes to construct a nominal “spendable output.”
4. Before accounting or signing, compare the supplied `TxOut` byte-for-byte with the confirmed prevout obtained from the blockchain.

### Proof of Concept
Conceptually, an attacker serializes:

```text
offset   = arbitrary scalar encoding
txout    = TxOut {
             value: victim_or_inflated_value,
             script_pubkey: selected_script
           }
outpoint = victim_txid || victim_vout
```

Feeding these bytes to `ReceivedOutput::read` succeeds because the function only parses the fields and returns `Ok(ReceivedOutput { offset, output, outpoint })`. [2](#0-1) 

The resulting object reports `victim_or_inflated_value` through `ReceivedOutput::value()` and names the victim's UTXO through `ReceivedOutput::outpoint()`. `SignableTransaction::new` then uses those claims as spendable input balance and transaction input data. [4](#0-3) 

For a foreign script, the later `multisig` check prevents signing because the forged offset does not derive the script. For a wallet script with a known offset but an altered `TxOut.value`, the local signing setup can proceed while committing to a false prevout amount, producing a transaction Bitcoin will reject. In either case, an unprivileged party can make nonexistent or non-spendable value appear as a wallet-received output.

  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
