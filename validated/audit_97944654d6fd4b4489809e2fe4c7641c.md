### Title
FROST `CachedPreprocess` persisted under a coarse `context` key is reused to sign distinct messages, enabling private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`preprocess_internal` stores a deterministic FROST preprocess seed in the `CachedPreprocesses` DB keyed only by `self.context` — `(b"DkgConfirmer", attempt)` — and never deletes or re-binds it. `share_internal` and `complete` both call `preprocess_internal` again, reloading the *same* seed via `AlgorithmSignMachine::from_cache`, which deterministically regenerates the identical nonce pair (`seeded_preprocess` → `ChaCha20Rng::from_seed` → `Commitments::new`). The message signed, however, is `set_keys_message(set, removed, key_pair)` — it varies with the externally supplied `key_pair`. A persisted approval/seed bound to the coarse attempt "carrier" instead of the actual invoked target (the concrete message/signing set) means two distinct messages can be signed with identical nonces, which per the in-repo documentation enables third-party recovery of the signer's secret share.

### Finding Description
- `CachedPreprocesses` is keyed `context -> [u8; 32]` and stores an XOR-obfuscated ChaCha20 seed.
- In `preprocess_internal` (lines 123–145), if the key exists it is *read* and reused; it is never `del`eted after use, despite `SignMachine::from_cache`'s contract in `crypto/frost/src/sign.rs:216-220` stating "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share."
- `share_internal` (line 156) calls `preprocess_internal` unconditionally, so the same seed is expanded into the same `nonces`/`commitments` every call.
- `complete` (lines 312–327) calls `share_internal` a second time, so even a single confirmation flow rebuilds the machine twice from the same seed; `DkgConfirmer::share`/`complete` accept caller-supplied `key_pair`, so the bound message differs while the nonce does not.
- `seeded_preprocess` (crypto/frost/src/sign.rs:121-144) derives `nonces` purely from the seed and `original_secret_share` — no message or participant-set binding — so nonce reuse across different `msg` values is guaranteed whenever the same `(context)` entry is hit.

The FROST spec file confirms the hazard: "Reusing preprocesses would enable a third-party to recover your private key share" (spec/cryptography/FROST.md:51-53).

### Impact Explanation
Two FROST signature shares produced with the same nonces over different messages (or different binding-factor sets) allow linear recovery of the signer's secret share: with `z = d + e·ρ·λ·s` style shares, two shares with identical `d`,`e` but different `ρ`,`λ`,`msg` yield the share `s` directly. Recovery of a validator's MuSig/Schnorrkel secret share undermines the threshold security of set-key confirmations — an attacker who collects two such shares (broadcast over the tributary) can compute the victim's share and, combined with other shares, forge confirmations/signatures. Severity: High (key share recovery, reachable through normal protocol messages).

### Likelihood Explanation
Likelihood hinges on whether the coordinator ever signs two different `set_keys_message` payloads under one `attempt` context. `key_pair` is attacker/peer-supplied data reaching `share`/`complete` via tributary transactions, and the code explicitly supports multiple `share` calls plus a `complete` call per attempt (`preprocess`, `share`, `complete` are separate pub(crate) entry points sharing the same DB context). The crash/restart path makes reuse likely: if the process restarts between `preprocess` and `share`, the persisted seed is reloaded — that is the cache's purpose — but nothing distinguishes "first use" from "already consumed", and there is no `delete` call anywhere (`CachedPreprocesses` appears only 4 times, all in this file). Any second distinct message under the same `attempt` deterministically reuses nonces. I could not fully verify the call-site multiplicity in `handle.rs` (search limited), but the absence of deletion and the seed's lack of message binding are proven in the shown code.

### Recommendation
Delete the `CachedPreprocesses` entry when it is consumed for signing (or atomically rotate it), and bind the cache key — or the derived seed — to the actual signing target (e.g., hash of `set_keys_message` / the exact `key_pair` and participant set), not merely `(b"DkgConfirmer", attempt)`. Alternatively, include the message and signing set in `seeded_preprocess`'s transcript before nonce generation so reuse of a seed under a different target yields different nonces.

### Proof of Concept
```rust
// Same attempt context, two different key_pair claims:
let mut confirmer = DkgConfirmer::new(&key, &spec, &mut txn, attempt).unwrap();

// First signing: msg1 = set_keys_message(set, removed, kp1)
let share1 = confirmer.share(preprocesses.clone(), &key_pair_1).unwrap();
// share_internal -> preprocess_internal reloads the SAME CachedPreprocesses seed
// -> identical nonces (d, e) and identical commitments.

// Second signing: msg2 = set_keys_message(set, removed, kp2), msg2 != msg1
let share2 = confirmer.share(preprocesses.clone(), &key_pair_2).unwrap();

// share1 and share2 were produced with the same nonce scalars but different
// binding factors/messages -> solve the linear system for the secret share s.
// Per spec/cryptography/FROST.md and sign.rs docs, this recovers the
// validator's private key share.
```
