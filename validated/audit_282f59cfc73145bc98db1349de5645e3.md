## Finding

### Title
Offer summary shown to users before accepting a trade omits full spend/condition details, preventing verification of what is actually being signed - ([File: chia/wallet/trading/offer.py])

### Summary
Chia's offer-acceptance flow mirrors the reported wallet UI flaw: a user is asked to approve a transaction based on a partial summary, while the full set of conditions and coin spends that will actually be signed and broadcast is not shown or validated against that summary.

### Finding Description
When a user runs `take_offer`, the CLI/RPC layer prints only a coarse summary — offered/requested amounts, fees, and asset driver info — and asks the user to confirm before pushing the resulting spend bundle: [1](#0-0) [2](#0-1) 

This summary is produced by `Offer.summary()`, which is explicitly documented as being "mostly for the UI": [3](#0-2) 

The underlying amounts come from `get_offered_coins()`/`_get_offered_coins()`, which the code itself documents as heuristic and incomplete: "This method does not get every coin that is being offered, only the `settlement_payment` children. It's also a little heuristic, but it should get most things": [4](#0-3) 

A separate helper, `get_pending_amounts()`, is annotated with the same caveat — "This method is also imperfect for sufficiently complex spends" — and is not even used in the summary shown at confirmation time: [5](#0-4) 

The RPC equivalent (`get_offer_summary`) exposes the same limited fields (`offered`, `requested`, `fees`, `infos`, `additions`, `removals`) without exposing the full puzzle reveals, solutions, or complete condition list for every coin spend in the bundle: [6](#0-5) [7](#0-6) 

This is directly analogous to the reported issue: the wallet interface displays only the coarse "amount"/"recipient" equivalent (offered/requested amounts) while omitting the equivalent of `data`/full conditions (arbitrary coin spends, announcements, and non-settlement conditions bundled into the same aggregated `WalletSpendBundle`). A user (or automated tooling built on `get_offer_summary`) approving a trade cannot fully verify from the displayed summary what coins are actually being moved or what conditions are being satisfied when the offer is completed via `to_valid_spend()`.

### Impact Explanation
Because the confirmation step (`cli_confirm("Would you like to take this offer? (y/n): ")`) is gated only on this partial, heuristic summary rather than a full accounting of every coin spend and condition in the bundle, a maliciously crafted offer file can contain coin spends/conditions that fall outside what `_get_offered_coins()` identifies as "offered," and thus never surface in the amounts a user reviews before accepting. This creates the same class of risk described in the report: financial approval decisions made without visibility into the complete transaction mechanics, undermining the ability of a wallet user to detect an offer that does something other than what the summary implies.

### Likelihood Explanation
Any user manually reviewing an offer file via the wallet CLI or a GUI built on `get_offer_summary` is affected, since the incompleteness is inherent to how the summary is derived (documented heuristic, not a corner-case bug), and applies to every offer accepted via the standard `take_offer` flow.

### Recommendation
Extend the offer summary (both `Offer.summary()` and the `get_offer_summary` RPC response) to enumerate all coin spends and conditions in the underlying bundle rather than only the heuristically-identified settlement-payment coins, and require the CLI/GUI confirmation step to be based on this complete accounting — matching the report's short-term recommendation to display all mechanically-relevant fields, and its long-term recommendation to add validation/warnings for spends or conditions that fall outside the expected offered/requested amounts.

### Proof of Concept
Not applicable in this ask-only context; conceptually, a proof-of-concept would construct an `Offer` whose `_bundle` includes an extra `CoinSpend` (or extra conditions on an existing spend) that does not create a child through `OFFER_MOD`, and show that `Offer.summary()` / `get_offer_summary` do not reflect these extra spends/conditions in the displayed `offered`/`requested` amounts, while `to_valid_spend()` still includes them in the final pushed transaction.

    def _get_offered_coins(self) -> dict[bytes32 | None, list[Coin]]:
        offered_coins: dict[bytes32 | None, list[Coin]] = {}

        cost_left = INFINITE_COST
        for parent_spend in self._bundle.coin_spends:
            coins_for_this_spend: list[Coin] = []

            parent_puzzle: UnknownPuzzle = UnknownPuzzle(known_program=parent_spend.puzzle_reveal)
            parent_solution = Program.from_serialized(parent_spend.solution)
            additions: list[Coin] = self._additions[parent_spend.coin]

            puzzle_driver = match_puzzle(parent_puzzle)
            if puzzle_driver is not None:
                asset_id = create_asset_id(puzzle_driver)
                inner_puzzle: Program | None = get_inner_puzzle(puzzle_driver, parent_puzzle, parent_solution)
                inner_solution: Program | None = get_inner_solution(puzzle_driver, parent_solution)
                assert inner_puzzle is not None and inner_solution is not None

                # We're going to look at the conditions created by the inner puzzle
                puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
                assert cost_left >= puzzle_cost
                cost_left -= puzzle_cost
                expected_num_matches: int = 0
                offered_amounts: list[int] = []
                for condition in conditions.as_iter():
                    if condition.first() == 51 and condition.rest().first() == OFFER_MOD_HASH:
                        expected_num_matches += 1
                        offered_amounts.append(condition.rest().rest().first().as_int())

                # Start by filtering additions that match the amount
                matching_spend_additions = [a for a in additions if a.amount in offered_amounts]

                if len(matching_spend_additions) == expected_num_matches:
                    coins_for_this_spend.extend(matching_spend_additions)
                # We didn't quite get there so now lets narrow it down by puzzle hash
                else:
                    # If we narrowed down too much, we can't trust the amounts so start over with all additions
                    if len(matching_spend_additions) < expected_num_matches:
                        matching_spend_additions = additions
                    matching_spend_additions = [
                        a
                        for a in matching_spend_additions
                        if a.puzzle_hash == construct_puzzle(puzzle_driver, OFFER_MOD).get_tree_hash()
                    ]
                    if len(matching_spend_additions) == expected_num_matches:
                        coins_for_this_spend.extend(matching_spend_additions)
                    else:
                        raise ValueError("Could not properly guess offered coins from parent spend")
            else:
                # It's much easier if the asset is bare XCH
                asset_id = None
                coins_for_this_spend.extend([a for a in additions if a.puzzle_hash == OFFER_MOD_HASH])

            # We only care about unspent coins
            coins_for_this_spend = [c for c in coins_for_this_spend if c not in self._bundle.removals()]

            if coins_for_this_spend != []:
                offered_coins.setdefault(asset_id, [])
                offered_coins[asset_id].extend(coins_for_this_spend)
        return offered_coins

    def summary(self) -> tuple[dict[str, str], dict[str, str], dict[str, PuzzleInfo], ConditionValidTimes]:
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        def keys_and_amounts_to_strings(dic: dict[bytes32 | None, int]) -> dict[str, str]:
            new_dic: dict[str, str] = {}
            for key, val in dic.items():
                if key is None:
                    new_dic["xch"] = str(val)
                else:
                    new_dic[key.hex()] = str(val)
            return new_dic

        driver_dict: dict[str, PuzzleInfo] = {}
        for key, value in self.driver_dict.items():
            driver_dict[key.hex()] = value

        return (
            keys_and_amounts_to_strings(offered_amounts),
            keys_and_amounts_to_strings(requested_amounts),
            driver_dict,
            self.absolute_valid_times_ban_relatives(),
        )

    # Also mostly for the UI, returns a dictionary of assets and how much of them is pended for this offer
    # This method is also imperfect for sufficiently complex spends
    def get_pending_amounts(self) -> dict[str, int]:
        all_additions: list[Coin] = self.additions()
        all_removals: list[Coin] = self.removals()
        non_ephemeral_removals: list[Coin] = list(filter(lambda c: c not in all_additions, all_removals))

        pending_dict: dict[str, int] = {}
        # First we add up the amounts of all coins that share an ancestor with the offered coins (i.e. a primary coin)
        for asset_id, coins in self.get_offered_coins().items():
            name = "xch" if asset_id is None else asset_id.hex()
            pending_dict[name] = 0
            for coin in coins:
                root_removal: Coin = self.get_root_removal(coin)

                for addition in filter(lambda c: c.parent_coin_info == root_removal.name(), all_additions):
                    pending_dict[name] += addition.amount

        # Then we gather anything else as unknown
        sum_of_additions_so_far: int = sum(pending_dict.values())
        unknown: int = sum(c.amount for c in non_ephemeral_removals) - sum_of_additions_so_far
        if unknown > 0:
            pending_dict["unknown"] = unknown

        return pending_dict

    async def get_offer_summary(self, request: GetOfferSummary) -> GetOfferSummaryResponse:
        dl_summary = None
        if not request.advanced:
            dl_summary = await self.service.wallet_state_manager.trade_manager.get_dl_offer_summary(

            response = GetOfferSummaryResponse(
                summary=OfferSummary(
                    offered=offered,
                    requested=requested,
                    fees=uint64(request.parsed_offer.fees()),
                    infos=infos,
                    additions=[c.name() for c in request.parsed_offer.additions()],
                    removals=[c.name() for c in request.parsed_offer.removals()],
                    valid_times=valid_times.only_absolutes(),
                ),
