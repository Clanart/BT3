### Title
BridgeTransferKLAY fallback lacks EOA check, causing possible unrecoverable loss of KLAY when a contract sends value directly to the bridge - (File: contracts/service_chain/bridge/BridgeTransferKLAY.sol)

### Summary
`BridgeTransferKLAY`'s fallback function (the Kaia service-chain bridge's equivalent of `L2ToL1MessagePasser#receive()`) forwards a cross-chain value-transfer request using `msg.sender` as the destination address, with no check that `msg.sender` is an EOA. Just as in the Optimism report, a contract that sends ETH/KLAY directly to the bridge contract (instead of calling `requestKLAYTransfer` with an explicit `_to`) will have the withdrawn value routed to its own address on the counterpart chain, which is a different deployment context where that same address may not be controlled by anyone, resulting in an unrecoverable loss of funds.

which calls `_requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0))`: [2](#0-1) 

This mirrors the pattern flagged in the external report: any address (EOA or contract) that transfers value directly to the bridge contract implicitly requests that the funds be delivered to `msg.sender`'s own address on the counterpart chain — there is no `onlyEOA`-style guard as recommended in the report, nor any other check that `msg.sender` is capable of receiving/controlling funds at that same address on the destination chain.

Unlike a plain EOA (whose private key controls the same address on both chains), a smart contract address is meaningful only in the context of the chain it was deployed on. A contract's address on the child/service chain has no guaranteed relationship to control over that same address on the parent chain (and vice versa) — it may be unowned, owned by an unrelated party, or a contract without any withdrawal logic. When the operator later processes the request via `handleKLAYTransfer`, it performs a raw `_to.call.value(_value)("")` to that address: [3](#0-2) 

If the target on the counterpart chain is not a contract the original sender controls (or has no payable fallback), the value transfer either reverts (blocking that nonce and any nonces sequenced after it, since nonces are handled in order via `lowerHandleNonce`) or succeeds while delivering funds to an address the original depositor cannot access — a direct value-loss analog to the reported issue.

### Impact Explanation
A contract that mistakenly (or due to a wallet/aggregator/proxy sending a plain value transfer) sends KLAY straight to the bridge contract's fallback has its funds routed to its own address on the counterpart chain. Since a contract's address is not portable/controllable across the two independently-deployed chains the way an EOA's private key is, this can permanently strand the transferred KLAY, matching the "loss of funds" impact class described in the original report. Additionally, because the bridge processes requests in strict nonce order (`lowerHandleNonce`/`requestNonce`), a request whose `handleKLAYTransfer` call reverts because the destination cannot accept the raw call can stall processing of that value-transfer queue.

### Likelihood Explanation
This is trivially reachable by any unprivileged transaction sender or contract via a single plain value-transfer transaction to the bridge address — no privileged role, governance action, or malicious peer/validator behavior is required. Contract wallets, aggregators, or any other automated contract-based caller that is unaware it must call `requestKLAYTransfer(to, value, extraData)` explicitly would trigger this path.

### Recommendation
Add an EOA-only guard (as recommended in the original report) to the bridge's fallback function, e.g.:
```solidity
modifier onlyEOA() {
    require(!Address.isContract(msg.sender), "BridgeTransferKLAY: sender must be EOA");
    _;
}

function () external payable onlyEOA {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
```
This prevents contracts from unintentionally requesting a value transfer to their own (non-portable) address, forcing them to use `requestKLAYTransfer(_to, _value, _extraData)` and explicitly specify a valid, controlled destination address.

### Proof of Concept
1. Deploy any smart contract `C` on the source chain (child or parent chain, whichever hosts the `BridgeTransferKLAY` bridge).
2. From `C`, execute a plain value transfer (e.g., `address(bridge).call{value: amount}("")` or `.transfer(amount)`) to the bridge contract address — this triggers the fallback at [1](#0-0) , which calls `_requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0))`, embedding `C`'s own address as the destination `_to` in the `RequestValueTransfer` event.
3. The bridge operator observes the event and calls `handleKLAYTransfer` on the counterpart chain, sending the value via low-level `call` to the address of `C` on that other chain (see [4](#0-3) ).
4. If no contract controlled by the same operator/owner exists at that address on the counterpart chain (or if the contract has no compatible payable fallback), the funds are either stuck unreachable (if delivered to an uncontrolled address) or the `handleKLAYTransfer` call reverts, blocking further nonce processing.

        internal
        unlockedKLAY

            TokenType.KLAY,
            msg.sender,

            requestNonce,
            fee,
            _extraData
