Now I have sufficient evidence to write up the finding. The critical asymmetry is between the Tron `IntentGatewayV2.onAccept`/`withdraw` path (no try/catch protection at the app level) versus the core `EvmHost.dispatchIncoming` path which self-heals on failure by deleting the receipt for retry. On the Tron gateway, `onAccept` is called directly and unconditionally by the host without an outer catch, so any revert inside `withdraw()` propagates and permanently blocks settlement for that commitment.

### Title
Permanent loss/lock of escrowed funds via unrecoverable push-transfer revert in `IntentGatewayV2.withdraw()` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` on the Tron variant of the Intent Gateway pushes native ETH/TRX and ERC20/TRC20 tokens directly to `beneficiary` inside the same atomic call that also finalizes order state (`_filled[body.commitment] = beneficiary` and `_orders[...] -= amount`). If the beneficiary address cannot receive the asset (a contract without a payable fallback, or a token contract that blacklists/rejects the beneficiary, e.g. a USDT/USDC-style blacklist), the low-level `call`/`transfer` fails and the function unconditionally `revert`s (`InsufficientNativeToken` / `TransferFailed`). Because this same function is invoked directly from `onAccept()` and `onGetResponse()` — both called unconditionally by the host with no surrounding try/catch — the revert propagates all the way up, rolling back the escrow debit and the `_filled` finalization together with the transfer. This mirrors exactly the external report's root cause: a push-payment inside a state-finalizing callback that can be permanently bricked by an unreceivable recipient.

### Finding Description
`withdraw()` is the single settlement path for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund on cancellation) on the Tron `IntentGatewayV2`: [1](#0-0) 

It is called directly and unconditionally from `onAccept()`: [2](#0-1) 

and from `onGetResponse()`: [3](#0-2) 

Unlike the core EVM host's incoming-message dispatch, which wraps the app callback in a low-level `call` and deletes the request/response receipt on failure so the message can be retried later: [4](#0-3) [5](#0-4) 

there is no equivalent self-healing at the application layer for the Tron gateway's `withdraw()`: the failing native/token transfer inside `withdraw()` uses `revert` on failure rather than deferring or pulling. Even where the outer host *does* retry-delete on failure (as on the mainline EVM host path), retrying is useless here because the beneficiary condition that caused the revert (non-payable contract, or a blacklisted/rejecting token receiver) is deterministic and does not change — every retry attempt fails identically, and the escrowed `_orders[commitment][token]` balance, plus any accumulated `TRANSACTION_FEES`, remain locked in the gateway forever with no pull-based recovery path.

The beneficiary is attacker-influenceable in the exact way the original report describes: `order.user` is stamped from `msg.sender` at order-placement time, so any account (including a deliberately non-payable/rejecting contract) can place an order, guaranteeing that its own `RefundEscrow`/cancellation-triggered `withdraw()` will always revert once the transfer is attempted, permanently locking the escrowed assets and, critically, also blocking the `_filled[body.commitment]` finalization write and `_orders[...] -=` debit in the same atomic call — an availability/asset-loss primitive matching "loss of funds" and "false state acceptance can never finalize" bug class from the report.

### Impact Explanation
This qualifies as loss of funds: escrowed input tokens (and any accrued protocol/relayer fee amounts stored under `TRANSACTION_FEES`) become permanently unrecoverable once a beneficiary address is chosen (or becomes, e.g. via blacklist) unable to receive the pushed asset. There is no fallback pull-withdrawal mechanism, and no way to redirect or retry with a different beneficiary — `withdraw()` hardcodes `beneficiary` from the message body and always reverts identically. This directly parallels the cited Vodka report: a push-transfer embedded in a state-finalizing callback (`afterDepositCancellation` there, `onAccept`/`onGetResponse` → `withdraw()` here) that can never complete once the recipient is unreceivable, causing the underlying accounting/escrow release to never settle.

### Likelihood Explanation
Likelihood is straightforward for the self-griefing/self-lock variant: any unprivileged user can place an order whose `order.user` (their own account, since it's stamped from `msg.sender`) is a contract with no receive/fallback, guaranteeing their own refund path always reverts and their escrow is stuck. The severity bar is met because the loss is concrete and irreversible (no admin recovery path exists in `withdraw()`), and the trigger requires no privileged actor, relayer collusion, or malformed proof — only a standard order placement followed by the standard cancellation/refund flow that any user is expected to be able to use.

### Recommendation
Convert the push-transfer in `withdraw()` to a pull-based pattern: on transfer failure, credit an internal `pendingWithdrawals[beneficiary][token]` balance instead of reverting, still finalize `_filled`/escrow debit/`TRANSACTION_FEES` cleanup, and expose a separate `claim()` function the beneficiary (or anyone, sending to the same beneficiary) can call later once the receiving condition is resolved. Alternatively wrap the native/token transfer in a try/catch (or check `success` without reverting) and emit a `TransferFailed`/`WithdrawalPending` event while still completing the state finalization, so a stuck beneficiary cannot block finalization of `_filled` and escrow accounting for its own order.

### Proof of Concept
1. Attacker deploys `RevertingBeneficiary`, a contract with no `receive()`/payable `fallback()`.
2. Attacker (as `RevertingBeneficiary` or any account they control) calls `placeOrder()` with native-ETH inputs; `order.user` is stamped to `msg.sender = RevertingBeneficiary` at placement time.
3. Attacker (or anyone after deadline) calls `cancelOrder()` from the destination chain, which dispatches a `RefundEscrow` message back to source chain (`order.user` set as beneficiary).
4. When the message arrives, `onAccept()` calls `withdraw(body, isRefund=true)`.
5. Inside `withdraw()`, `(bool sent,) = beneficiary.call{value: amount}("")` fails because `RevertingBeneficiary` has no payable fallback; `if (!sent) revert InsufficientNativeToken();` fires.
6. The entire `onAccept()` call reverts; `_filled[commitment]` is never set and `_orders[commitment][token]` is never debited. Every subsequent relay attempt of the same message hits the identical revert. The escrowed native tokens are permanently locked in the gateway with no pull-based recovery mechanism.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
