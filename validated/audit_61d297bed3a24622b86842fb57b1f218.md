### Title
Missing zero-check on the `governance.kip71.gastarget` parameter causes a `big.Int` division-by-zero panic in `NextMagmaBlockBaseFee`, crashing all nodes during header verification - ([File: params/kip71_config.go])

### Summary
The KIP-71 dynamic base-fee formula divides by the governance-controlled `GasTarget` value without ever checking that it is non-zero. Unlike the sibling parameter `Kip71BaseFeeDenominator`, whose `FormatChecker` explicitly rejects `0`, the `Kip71GasTarget` parameter uses `noopFormatChecker`, which accepts any `uint64` value including `0`. If `GasTarget` is set to `0` via a governance vote, every node that subsequently calls `NextMagmaBlockBaseFee` to compute or verify a block's base fee will panic with a `division by zero`, because `big.Int.Div` panics on a zero divisor. This is directly analogous to the libtiff `tiffcrop` divide-by-zero DoS: a value that should be validated as non-zero is allowed through unchecked and later used as a divisor in gas/fee accounting.

### Finding Description
`Kip71GasTarget`'s parameter definition in `kaiax/gov/param.go` uses `noopFormatChecker`, which performs no validation: [1](#0-0) 

Compare this to `Kip71BaseFeeDenominator`, which explicitly guards against zero: [2](#0-1) 

The unguarded `GasTarget` flows into `KIP71Config.NextMagmaBlockBaseFee`, which is used both to compute the next block's base fee and to verify a proposed header's base fee (`VerifyMagmaHeader`): [3](#0-2) 

Inside `NextMagmaBlockBaseFee`, `gasTarget := kc.GasTarget` is used directly as a `big.Int` divisor with no zero check, unlike `BaseFeeDenominator` which is defensively defaulted to `64` when zero: [4](#0-3) 

If `parentGasUsed > gasTarget` (true for essentially any nonzero gas usage when `gasTarget == 0`) and `parentBaseFee != upperBoundBaseFee`, execution reaches:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // = parentGasUsed
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 -> panic: division by zero
```
The symmetric decreasing-base-fee branch has the identical unguarded division. `big.Int.Div` in Go panics on a zero divisor (unlike Solidity's revert semantics), so this is an unrecoverable runtime panic in a core, consensus-path function.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked from:
- `blockchain/block_validator.go` (header verification path, called by every full/verifying node for every incoming block after Magma),
- the block-building/worker path (`work/worker.go`) when a proposer assembles the next block,
- the gas-price oracle (`node/cn/gasprice/feehistory.go`, `gasprice.go`) for RPC fee estimation.

Once `governance.kip71.gastarget` is set to `0` via a governance vote (a legitimate governance parameter update path explicitly listed as in-scope), every node in the network that validates or produces the next block will panic and crash. Because this is deterministic and hit by *all* honest nodes simultaneously (not just a malicious one), it results in a full network-wide denial of service rather than a localized fault — matching the "acceptance of an invalid transaction or block" / consensus-halting impact bar for this analog class. This qualifies as Medium/High severity: it does not move funds directly, but it halts block production/validation network-wide, which is a critical availability failure reachable through the in-scope "governance parameters" surface.

### Likelihood Explanation
The likelihood depends on a governance vote actually setting `GasTarget=0`, which requires the governing node(s)/council to submit such a vote. This is a plausible operational or malicious-insider scenario (fat-fingered governance parameter, or a compromised/malicious governing node), and there is no code-level safeguard preventing it — the format checker silently accepts `0`, in clear contrast to the deliberate zero-guard on the neighboring `BaseFeeDenominator` parameter, indicating this is an oversight rather than an intentional design choice. Because `NextMagmaBlockBaseFee` is unconditionally reached on the very next block after the parameter takes effect (whenever gas used differs from `gasTarget`), the crash is deterministic and immediate once the bad parameter is active — no attacker crafting or race condition needed.

### Recommendation
Add a zero-check to the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go`, analogous to `Kip71BaseFeeDenominator`, rejecting `GasTarget == 0` at vote-canonicalization time. As defense-in-depth, `NextMagmaBlockBaseFee` in `params/kip71_config.go` should also guard against `gasTarget == 0` (e.g., falling back to a safe default, mirroring the existing `BaseFeeDenominator == 0` fallback), so that even a value that somehow bypasses parameter validation cannot cause a panic in the core base-fee calculation.

### Proof of Concept
1. Governance votes to set `governance.kip71.gastarget = 0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, which always returns `true`).
2. Once the vote takes effect at block `N`, any block `N+1` (or later) with `header.GasUsed != 0` triggers `NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)` with `gasTarget == 0`.
3. Since `parentGasUsed > gasTarget` (0) is true, and `parentBaseFee != upperBoundBaseFee` (typical case), the code executes:
   ```go
   gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - 0)
   x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
   y := x.Div(x, new(big.Int).SetUint64(0)) // panics: division by zero
   ```
4. This panic occurs inside header verification (`blockchain/block_validator.go`) on every node processing the block, and inside block assembly (`work/worker.go`) for the proposer — crashing the process and halting the chain network-wide.

*Note: I was unable to execute this scenario in an actual Go runtime within this session to directly confirm the panic message/stack trace, so this is derived from static code-path analysis of `big.Int.Div` semantics (documented to panic on division by zero) combined with the confirmed absence of a zero-guard for `GasTarget`, in contrast with the explicit guard present for `BaseFeeDenominator`.*

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
