### Title
Stale line-index diff selections silently re-applied to a freshly re-fetched diff during partial commits, corrupting committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-commit ("stage selected lines") feature stores the user's line selection as pure line-index bookkeeping (`DiffSelection`), independent of any specific diff content or hash [3](#0-2) . When the user commits, `applyPatchToIndex` re-fetches a brand-new diff from disk at staging time and blindly applies the stored selection's line indices to that new diff via `formatPatch` [4](#0-3) [5](#0-4) . If the tracked file's content on disk changes between the moment the user reviewed the diff/made line selections in the UI and the moment `createCommit`/`stageFiles` actually run, the line-index selection no longer corresponds to the same hunks/lines, so `git apply --cached` stages and commits different content than what the user saw and approved — silently.

### Finding Description
The `DiffSelection` class is explicitly documented as having "no notion of how many lines exist or what it is that is being selected" [6](#0-5) ; it only tracks a `Set<number>` of diverging absolute line indices relative to whatever diff was in view when the selection was built.

The commit path is:
1. `_commitIncludedChanges` reads `state.changesState.workingDirectory.files` — the files with their current `.selection` objects — and passes them straight to `createCommit` [7](#0-6) .
2. `createCommit` calls `stageFiles`, which for any file with a `Partial` selection calls `applyPatchToIndex` [8](#0-7) .
3. `applyPatchToIndex` does **not** reuse the diff that was displayed to the user in the Changes view. Instead it calls `getWorkingDirectoryDiff(repository, file)` again, right before staging [9](#0-8) .
4. `formatPatch(file, diff)` then walks the hunks of this newly fetched diff and, for every non-context line, calls `file.selection.isSelected(absoluteIndex)` to decide inclusion [5](#0-4) .

There is no verification anywhere in this path that the newly fetched diff has the same hunk layout/line count as the diff the selection was originally computed against. If the file's on-disk content changed in the interim (added/removed lines shifting hunk offsets, or entirely different content), the same absolute indices now point at different lines. `formatPatch` will happily produce a syntactically valid patch that stages/commits a different subset of changes than the user selected — potentially including lines the user explicitly excluded, or excluding ones they included — and `git apply --cached`/`git commit` succeed without error.

This is the direct structural analog of the Karak finding: a per-user "share"/selection value (`DiffSelection`, computed against a stale total/diff state) is combined with a freshly recomputed underlying value (`totalAssets` / the new diff) without re-validating that the relationship between the two still holds, silently producing an incorrect result.

### Impact Explanation
This allows silent corruption of what the user commits — one of the explicitly in-scope impacts. A user reviewing a partial diff and deliberately excluding certain lines (e.g., a debug print, secret, or unfinished code) could end up committing and pushing content they never approved, or vice versa lose intended changes, with no error or warning from the app. Because GitHub Desktop shows no post-hoc diff of what was actually committed by default, this can go unnoticed until pushed to a shared/public remote.

### Likelihood Explanation
The window between diff display and commit staging is not negligible: GitHub Desktop's Changes view polls/refreshes diffs on a timer/`Tailer`-driven basis and file-system watcher events [10](#0-9) , and users commonly leave the Changes tab open while other tools (linters/formatters/build watchers, editor auto-save, or repository-provided scripts run by the user) touch the same file. Any process — including one shipped inside a cloned/fetched malicious repository (e.g. an npm `postinstall`/watch script, editor tooling config, or a git hook run by a prior Desktop operation) — that rewrites a tracked file shortly before the user clicks "Commit" can trigger the mismatch without any unusual user action beyond normal editing/committing.

### Recommendation
`applyPatchToIndex`/`stageFiles` should not silently re-fetch a diff and reuse a stale line-index `DiffSelection` against it. Instead, either (a) capture and reuse the exact diff object the user selected lines against and pass it through `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`, refusing to commit if the working tree changed since; or (b) have `applyPatchToIndex` compare the newly fetched diff to the one the selection was derived from (e.g., via a content hash or hunk-shape check) and abort/re-prompt the user if they differ, rather than proceeding to build and apply a patch from mismatched indices.

### Proof of Concept
1. Modify a tracked file with two independent hunks (A and B).
2. In the Changes view, select only hunk A for commit (leave hunk B unselected), producing a `Partial` `DiffSelection` whose diverging line indices are relative to the *currently displayed* diff.
3. Before pressing Commit, have an external process (simulating a repo-shipped watcher/build script) modify the file such that lines are inserted/removed before hunk A, shifting the line numbering of the file's diff (e.g., add 3 new lines at the top) — Desktop does not force a diff/selection re-validation before commit.
4. Click Commit. `applyPatchToIndex` calls `getWorkingDirectoryDiff` again, obtaining a diff with shifted hunk boundaries, then applies the old `DiffSelection`'s absolute indices via `formatPatch` [11](#0-10) [5](#0-4) .
5. Inspect the resulting commit with `git show`: it stages/commits a different set of lines than what was visually selected in the UI (e.g., parts of hunk B are included, or parts of hunk A are dropped), with no error reported to the user.
