### Title
Panic on unregistered participant index in PedPoP blame path causes node crash (DoS) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG's blame-resolution code indexes its encryption-key map with an attacker-supplied `Participant` index without validating it is within `1..=n`. A malformed accusation naming an out-of-range `accused`/`recipient` causes a HashMap-index panic, crashing the evaluating node — an unprivileged, remote, repeatable denial of service analogous to CVE-2019-2689 (crafted input → crash of the server component).

### Finding Description
`Decryption::decrypt_with_proof` at `crypto/dkg/pedpop/src/encryption.rs` performs `self.enc_keys[&decryptor]` inside the `Some(proof)` branch:

```rust
// crypto/dkg/pedpop/src/encryption.rs:383-389
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // panics if decryptor not in map
  )
```

`enc_keys` only ever contains indexes `1..=n`, populated by `Decryption::register` (called per participant in `AdditionalBlameMachine::new` at `crypto/dkg/pedpop/src/lib.rs:656-660` and in `SecretShareMachine::verify_r1` at `crypto/dkg/pedpop/src/lib.rs:313-315`). Neither `BlameMachine::blame` (`lib.rs:623-632`) nor `AdditionalBlameMachine::blame` (`lib.rs:674-682`) bounds-check the `sender`/`recipient` arguments, which are raw `Participant` values; `Participant::new` only rejects zero (`crypto/dkg/src/lib.rs:29-35`). A second panic site exists in the same function path: `self.commitments[&sender]` in `blame_internal` (`lib.rs:599`).

Reachability: an accuser submits an `InvalidDkgShare`/`VerifyBlame` message where `accuser`/`accused` are parsed with `Participant::new(u16)` and no `<= n` check (`coordinator/src/tributary/transaction.rs:346-353`). The processor forwards these directly: `AdditionalBlameMachine::new(...).unwrap().blame(accuser, accused, substrate_share, substrate_blame)` (`processor/src/key_gen.rs:543-549`). To reach the indexing line, the attacker must provide (a) an `EncryptedMessage` whose `pop` Schnorr signature verifies — constructible by anyone since they choose the ephemeral key themselves — and (b) `proof: Some(_)` — any parseable `EncryptionKeyProof` (`key` point + `DLEqProof`), which needs no validity since the panic occurs while building the verify arguments, before `dleq.verify` runs.

### Impact Explanation
Every processor evaluating the blame transaction panics on the `enc_keys[&decryptor]` HashMap index because `decryptor = accused` (e.g., `Participant(65535)`) was never registered. This is a complete, repeatable crash of the evaluating node from a single unauthenticated-content message, matching the CVE's availability-only impact (CVSS A:H). It also aborts the slash/blame adjudication flow.

### Likelihood Explanation
Requires only the ability to submit a blame transaction/message naming an invalid participant index plus a self-generated valid PoP and any well-formed `EncryptionKeyProof` bytes. No collusion, no key material, no special privileges — low complexity. Caveat: I confirmed the message parsing (`transaction.rs`) and the processor call site (`key_gen.rs`) perform no bound check on `accused`/`accuser`; if an intermediate consensus layer filters out-of-range participants, reachability would be reduced to the in-scope API misuse itself.

### Recommendation
In `Decryption::decrypt_with_proof` (and `BlameMachine::blame`/`AdditionalBlameMachine::blame` / `blame_internal`), validate `decryptor` and `sender` against `enc_keys`/`commitments` membership before indexing — e.g., `enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` and `commitments.get(&sender)` returning the accusing party as faulty on `None`. Additionally, callers should reject `accuser`/`accused` values `> params.n()` before invoking the blame machine.

### Proof of Concept
1. Node completes PedPoP round 1 with `n` participants; `Decryption.enc_keys` = `{1..=n}`.
2. Attacker broadcasts a `VerifyBlame`-triggering message with `accuser = Participant::new(1)`, `accused = Participant::new(n + 1)` (or any `u16 > n`, nonzero).
3. `share` = an `EncryptedMessage` where `key = k·G`, `pop = SchnorrSignature::sign(&k, r, pop_challenge(ctx, r·G, k·G, accuser, msg_bytes))` — passes the `msg.pop.verify` check.
4. `blame` = serialized `EncryptionKeyProof { key: <any point>, dleq: <any parseable DLEqProof> }` → `Some(_)`.
5. `decrypt_with_proof` evaluates `self.enc_keys[&Participant(n+1)]` → `index out of bounds`/HashMap panic → node crashes before any DLEq verification or blame determination.
