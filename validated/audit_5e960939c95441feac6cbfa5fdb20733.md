### Title
Attacker-forged OP_RETURN in a self-broadcast payout transaction lets any registered operator be falsely credited as payer, enabling an uncollateralized reimbursement claim - (File: core/src/verifier.rs, core/src/operator.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
`update_finalized_payouts` attributes a payout's `payer_xonly_pk` solely by parsing the OP_RETURN output of whatever Bitcoin transaction is found spending the registered `withdrawal_utxo`, with no cryptographic binding between that OP_RETURN data and who actually funded/signed the transaction. Because the user's withdrawal signature uses `SinglePlusAnyoneCanPay`, it commits only to input 0 and output 0 — it leaves every other input and output (including the OP_RETURN) completely unconstrained, so an unprivileged attacker who owns the withdrawal UTXO can self-fund and broadcast the whole payout transaction, stamping any registered Operator X's xonly public key into the OP_RETURN. `Operator::validate_payer_is_operator` later trusts this DB-recorded key at face value, letting Operator X's automation (or manual `GetReimbursementTxs` call) proceed through the Round/Kickoff/Reimburse chain and collect `bridge_amount`, even though Operator X never called `withdraw` or spent a satoshi.

### Finding Description
The claimed binding is:
`payout_payer_operator_xonly_pk` (as read by `validate_payer_is_operator`) == xonly_pk of the entity whose Bitcoin funds paid output 0 of the payout tx.

Trace:
1. A user (attacker) registers a withdrawal on Citrea (`withdraw` on the Citrea Bridge contract) with their own `withdrawal_utxo`, an `output_script_pubkey`/`output_amount` paying themselves, and a `SinglePlusAnyoneCanPay` Schnorr signature over input 0 they generate themselves. This gets synced into the DB via `update_citrea_deposit_and_withdrawals` and stored per `withdrawal_utxo` (`core/src/verifier.rs:2204-2262`).
2. `create_payout_txhandler` shows the canonical structure: input 0 (the withdrawal UTXO, key-spend), output 0 (user payout, the only output committed by the `SinglePlusAnyoneCanPay` signature), output 1 (anchor), output 2 (OP_RETURN with `operator_xonly_pk`) [1](#0-0) . `calculate_pubkey_spend_sighash` confirms that for `SinglePlusAnyoneCanPay`/`AllPlusAnyoneCanPay`/`NonePlusAnyoneCanPay` only `Prevouts::One(txin_index, ...)` is used, i.e. the signature covers only this one input, and BIP341 SIGHASH_SINGLE only commits to the output at the same index (index 0) [2](#0-1) . The anchor output, the OP_RETURN output, and any extra funding inputs are therefore *not* covered by the user's signature at all.
3. Because of this, the attacker (who controls the withdrawal UTXO and signature) can independently assemble and broadcast a final transaction that: keeps input 0 + output 0 exactly as signed, adds their own extra input(s) to pay fees (`AnyoneCanPay` explicitly allows this), and adds an OP_RETURN output containing any 32 bytes they like — e.g. Operator X's `xonly_pk` — without going through any operator's `withdraw`/`InternalWithdraw` RPC at all (bypassing `Operator::is_profitable` and any operator-side checks in `core/src/operator.rs:539-627`).
4. Once mined and finalized, `Verifier::update_finalized_payouts` locates the payout purely by matching `bitcoin_syncer_spent_utxos` against the registered `withdrawal_utxo_txid`/`vout` (`get_payout_txs_for_withdrawal_utxos`, `core/src/database/verifier.rs:168-196`), with no check on who funded the extra inputs. It then blindly parses the first OP_RETURN output and, if it decodes to a valid `XOnlyPublicKey`, records it as `payout_payer_operator_xonly_pk` [3](#0-2) .
5. `Operator::validate_payer_is_operator` reads this DB value and compares it only to `self.signer.xonly_public_key`; if it matches (which it will, since the attacker chose Operator X's key), it proceeds to return the payout blockhash/kickoff txid and lets `get_reimbursement_txs` build the Round → Kickoff → Reimburse chain for Operator X [4](#0-3) [5](#0-4) .
6. `Verifier::is_kickoff_malicious`, the only other check that touches this data, merely verifies that the OP_RETURN's `operator_xonly_pk` equals `kickoff_data.operator_xonly_pk` (trivially true, since Operator X's own kickoff naturally uses its own key) and that the committed blockhash matches — neither check verifies who actually funded the payout transaction [6](#0-5) .

No existing guard (`SECP.verify_schnorr` on the withdrawal signature, `is_profitable`, `is_kickoff_malicious`, SPV/light-client verification) checks that the OP_RETURN pubkey corresponds to the entity that supplied the extra funding inputs of the payout transaction — because `SinglePlusAnyoneCanPay` was never designed to bind that.

### Impact Explanation
BTC from the deposit's move-to-vault UTXO (equal to `bridge_amount`) is ultimately released via the Reimburse transaction to Operator X's reimbursement address, even though Operator X never fronted the corresponding withdrawal payout — a direct instance of "an operator reimbursed for a payout it never funded" (Critical). The attack is repeatable per deposit/withdrawal and can target any operator registered in the deposit's operator set, since the attacker chooses which operator's xonly_pk to stamp into the OP_RETURN. It requires no privileged role, key, or collateral — only that the attacker can create a deposit/withdrawal and broadcast a Bitcoin transaction, which is within the unprivileged attacker's granted capabilities.

### Likelihood Explanation
Preconditions are minimal and fully within the attacker's described capabilities: perform a normal deposit, call Citrea's `withdraw` with a self-controlled UTXO/signature, and self-fund/broadcast the final payout transaction directly instead of going through any operator's RPC. Cost is just the deposit amount (recoverable to self at output 0) plus Bitcoin transaction fees for the extra funding input. No collusion with the targeted operator is required for the misattribution to occur; if the targeted operator's automation is running (`PayoutCheckerTask`/`get_first_unhandled_payout_by_operator_xonly_pk`), it will proceed automatically since it isn't itself malicious — it just trusts the corrupted DB attribution.

### Recommendation
Do not derive `payout_payer_operator_xonly_pk` solely from an unauthenticated OP_RETURN parse of the on-chain payout transaction. Either (a) require the operator's own signature/commitment (e.g., an operator-signed acknowledgment stored at withdrawal-request time via the `withdraw`/`InternalWithdraw` RPC path, tied cryptographically to the specific payout txid) before attributing payer identity, or (b) extend the payout transaction's committed sighash (e.g., require `All` or a covering commitment over the OP_RETURN output, or use a script path that ties the OP_RETURN to the operator's key via a signature check) so a third party cannot inject an arbitrary operator's identity into an uncommitted output. In all cases, `validate_payer_is_operator`/`update_finalized_payouts` should require proof that the claimed operator authored/funded the transaction, not just that its pubkey byte-string happens to appear in an OP_RETURN nobody signed over.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
