### Title
Missing amount binding between payout output value and reimbursed/bridge amount in `bridge_circuit` - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` (the zk-proof that gates the BitVM2 disprove path and thus the operator's `reimburse_tx`) never reads or constrains the value of any output in `payout_spv.transaction`. It only checks that the payout tx's input `previous_output` (txid+vout) matches the withdrawal UTXO recorded via `verify_storage_proofs`, and that an OP_RETURN encodes the operator's pubkey. Since `create_reimburse_txhandler` always pays the operator the fixed `bridge_amount` from the `MoveToVault` UTXO regardless of what the operator actually paid the withdrawer, and no code path — not `bridge_circuit`, not the disprove scripts it backs — checks `payout output value == bridge_amount`, an operator can front an arbitrarily small amount to a withdrawal UTXO and still be fully reimbursed the entire `bridge_amount`, with the shortfall being economically unprovable/undisprovable.

### Finding Description
The claimed binding — `sum(payout_spv.transaction.output[i].value for scripts paying withdrawer) == bridge_amount` (or the amount actually owed for that withdrawal) — is never computed or asserted anywhere in `bridge_circuit`.

Walking the function body in `circuits-lib/src/bridge_circuit/mod.rs`:
- `verify_storage_proofs` returns only `(user_wd_outpoint, vout, move_txid)` — no amount. [2](#0-1) 
- The circuit then asserts the payout tx's input txid/vout equal this outpoint. [3](#0-2) 
- It reads the first OP_RETURN output only to extract `operator_xonlypk`, and computes `deposit_constant`/`journal_hash` from `move_txid`, watchtower pubkeys, operator pubkey, round/kickoff txids and `genesis_state_hash` — never from any output value. [4](#0-3) 

At no point does the function index into `input.payout_spv.transaction.output[..]` to read `.value`. The storage proof itself (`UTXOS_STORAGE_INDEX`) only stores the withdrawal outpoint's `(txid, vout)`, not an amount, in the Bridge contract. [5](#0-4) 

Meanwhile, the reimbursement side (`create_reimburse_txhandler`) unconditionally pays the operator the full value held in the `MoveToVault` UTXO (i.e., `bridge_amount`), sourced only from the move transaction, not from the payout transaction's actual output value: [1](#0-0) 

The only amount discipline that exists is `Operator::is_profitable` — a purely self-interested, off-chain, unenforced check the operator applies to *itself* when voluntarily constructing a payout via the RPC `withdraw`/`internal_withdraw` path: [6](#0-5)  This is not a protocol invariant; nothing forces an operator (or a operator that colludes with, or is, the withdrawal registrant) to pay any particular fraction of `bridge_amount`. Since `is_profitable` treats a smaller `output_txout.value` as *more* profitable for the operator, a rational operator is incentivized to pay the minimum amount the withdrawer will sign for while still collecting the full `bridge_amount` reimbursement.

Because `bridge_circuit`'s journal (which is what the Disprove/Groth16 verification on-chain checks) contains no output-value data, the BitVM2 `BridgeDisproveScript`/`ClementineDisproveScript` path (documented in `docs/bridge-circuit.md`) has no way to ever flag or punish an under-funded payout — the amount is simply outside the set of facts the circuit commits to or proves.

### Impact Explanation
This directly matches the Critical category "an operator reimbursed for a payout it never funded": the operator (or an operator colluding with the withdrawal-registering party) can front a payout of arbitrarily small value to the exact UTXO/script recorded for a withdrawal, and still receive the full `bridge_amount` reimbursement from the `MoveToVault`/round/collateral chain via `create_reimburse_txhandler`, since neither `bridge_circuit` nor the disprove scripts it feeds ever check or commit the payout output's value. This is systemic — it applies to every withdrawal serviced through the kickoff/reimburse path, for every operator, not a one-off edge case, and the loss is drawn from the protocol's locked bridge value rather than the operator's own funds.

### Likelihood Explanation
No special privilege beyond the operator role (which is inherently semi-trusted and is precisely the actor the disprove/BitVM2 machinery exists to keep honest) is required to trigger this. It requires only a withdrawal registration with a signature/output that authorizes an amount below `bridge_amount` (the withdrawer, who may be a sybil/colluding party of the operator, controls that signature and amount), and one operator-driven `withdraw` call plus the normal kickoff/reimburse flow. No mainnet or live Citrea infrastructure is needed to demonstrate the missing binding — it can be shown purely from the absence of value reads/asserts in `bridge_circuit` and from `is_profitable`'s incentive structure.

### Recommendation
Extend the storage-proof/UTXO commitment (or add a dedicated Bridge-contract storage slot) to record the expected withdrawal amount, and have `verify_storage_proofs` return it. In `bridge_circuit`, sum the values of `payout_spv.transaction.output[..]` that pay the recorded withdrawer script/outpoint and assert that sum equals the recorded/expected withdrawal amount (or at minimum equals `bridge_amount` minus the fixed protocol fee) before computing `deposit_constant`/`journal_hash`, so that an under-funded payout produces a provably-invalid journal and can be caught by `ClementineDisproveScript`/`BridgeDisproveScript`.

    /// Checks if the withdrawal amount is within the acceptable range.
    fn is_profitable(
        input_amount: Amount,
        withdrawal_amount: Amount,
        bridge_amount_sats: Amount,
        operator_withdrawal_fee_sats: Amount,
    ) -> bool {
        // Use checked_sub to safely handle potential underflow
        let withdrawal_diff = match withdrawal_amount
            .to_sat()
            .checked_sub(input_amount.to_sat())
        {
            Some(diff) => Amount::from_sat(diff),
            None => {
                // input amount is greater than withdrawal amount, so it's profitable but doesn't make sense
                tracing::warn!(
                    "Some user gave more amount than the withdrawal amount as input for withdrawal"
                );
                return true;
            }
        };

        if withdrawal_diff > bridge_amount_sats {
            return false;
        }

        // Calculate net profit after the withdrawal using checked_sub to prevent panic
        let net_profit = match bridge_amount_sats.checked_sub(withdrawal_diff) {
            Some(profit) => profit,
            None => return false, // If underflow occurs, it's not profitable
        };

        // Net profit must be bigger than withdrawal fee.
        // net profit doesn't take into account the fees, but operator_withdrawal_fee_sats should
        net_profit >= operator_withdrawal_fee_sats
    }
