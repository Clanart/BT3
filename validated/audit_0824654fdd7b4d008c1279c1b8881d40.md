### Title
Trusting an unsafe repository directory permanently whitelists that path in global Git config with no way to revoke it - (File: `app/src/lib/git/config.ts`)

### Summary
GitHub Desktop lets a user "Trust" a repository directory that Git considers unsafe (owned by a different user). Trusting calls `addSafeDirectory()`, which appends the path to the global, cross-repository `safe.directory` Git config list. There is no corresponding function or UI control anywhere in the codebase to remove a path from this list once added, so the exemption is permanent for that filesystem path, for every repository (existing or future) located there.

### Finding Description
`addSafeDirectory` writes the chosen path into the user's global `~/.gitconfig` `safe.directory` multi-value list via `addGlobalConfigValueIfMissing('safe.directory', path)`: [1](#0-0) 

This is invoked from two UI entry points when Desktop detects an "unsafe" repository (owned by a different user than the current process) — the "Add Existing Repository" dialog and the "Missing Repository" recovery view — both exposing a "Trust Repository" action that calls `addSafeDirectory`: [2](#0-1) [3](#0-2) 

The dialog copy explicitly warns that "Adding untrusted repositories may automatically execute files in the repository," confirming that trusting the directory removes Git's ownership-safety guard that normally prevents automatic execution of repository-controlled config/hooks: [4](#0-3) 

A repository-wide search confirms there is no `removeSafeDirectory`, "untrust", or equivalent revocation function/UI anywhere in the codebase — the only matches for `safe.directory` are the three call sites above plus tests, and `_removeRepository` (removing a repo from Desktop's list) does not touch this global git config at all. Once a path is trusted it remains in `safe.directory` indefinitely, surviving repository removal from Desktop, uninstall/reinstall of the repository at that path, or reuse of that same path by a completely different (and possibly attacker-supplied) repository/user.

This mirrors the BathHouse `strategist` bug-class exactly: a privileged grant (`approveStrategist` ↔ `addSafeDirectory`) with no corresponding revoke, meaning a decision made about one specific repository content bleeds into trust of *any future content* that occupies the same path.

### Impact Explanation
Because the trust is keyed only by filesystem path (not by repository identity/commit/remote), any attacker who can get content placed at a previously-trusted path — e.g. a shared workstation, a re-imaged/re-cloned directory, a network share, a CI/build directory, or a path a user previously trusted and later deleted and let an attacker repopulate — inherits Desktop's/Git's bypass of the unsafe-ownership check with zero additional user interaction or warning. Since the warning text itself states this class of directory "may automatically execute files in the repository" (Git hooks, `core.fsmonitor`, filters, etc., which Git normally refuses to honor for unsafe-owned directories), a stale, unrevocable trust entry converts what should be a one-time, reviewed exception into a standing local code-execution primitive for whoever next controls that path.

### Likelihood Explanation
The precondition (an attacker gaining control of a directory a user once trusted) requires either a shared/multi-user machine, a reused temp/build directory, or a user re-cloning attacker content into the same path — this is a plausible, low-effort scenario in CI runners, shared dev boxes, or when users recreate project folders after cleanup. No admin rights or pre-existing malware are required; the only "credential" needed is filesystem path reuse, which is common in build pipelines and shared environments. The complete absence of any revoke UI or API in the codebase (confirmed via full-repo search) means this is not a partially-mitigated edge case but a structural gap.

### Recommendation
Add a `removeSafeDirectory(path)` function mirroring `addSafeDirectory` (using `git config --global --unset` or rewriting the multi-valued key) and expose it in Desktop's UI — e.g., a "Remove trust" action when a repository is removed from Desktop (`_removeRepository`), plus a dedicated settings panel listing all currently trusted directories with per-entry revoke controls. Additionally, consider re-validating trust decisions against something more specific than a bare path (e.g., prompting again if the directory's ownership or `.git` identity changes) rather than trusting indefinitely by path alone.

### Proof of Concept
1. User opens Desktop and adds an existing repository at `C:\Shared\proj` (or any path on a multi-user/shared mount) that Git flags as unsafe (different owner). Desktop shows the "appears to be owned by another user" warning and offers **Trust Repository**. [5](#0-4) 
2. User clicks "Trust Repository" → `onTrustDirectory` → `addSafeDirectory('C:\Shared\proj')` writes `safe.directory=C:\Shared\proj` to the global `.gitconfig`. [2](#0-1) [6](#0-5) 
3. User later removes the repository from Desktop, deletes the folder, or the shared environment is repurposed. The `safe.directory` entry is never cleaned up (no such call exists anywhere in the codebase, confirmed by search across `app/src`).
4. An attacker (another user on the shared machine, or a subsequent process reusing that path/mount) places a malicious Git repository at `C:\Shared\proj`, including crafted hooks/config that rely on the "not unsafe" bypass.
5. When Desktop (or the user's Git) next operates on `C:\Shared\proj`, Git honors `safe.directory` and treats the attacker's repository as trusted, skipping the ownership-mismatch protection the "unsafe" check was designed to enforce — with no record or means for the original user to have revoked the earlier trust grant.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
