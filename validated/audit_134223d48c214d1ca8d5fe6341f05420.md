### Title
Global EVM coin denom/decimal cache (`evmCoinInfo`) is permanently frozen by `sync.Once` and never resynced after `x/vm` `MsgUpdateParams` changes `EvmDenom`, causing systemic balance-scaling corruption across bank, EVM, and precisebank accounting - (File: x/vm/module.go, x/vm/types/denom_config.go)

### Summary
This is the same bug class as the FrankenDAO `monsterMultiplier` issue: a governance-updatable parameter (`monsterMultiplier` / here, `x/vm` `Params.EvmDenom` and its associated decimals) is cached into a separate value at one point in time, and a critical accounting path keeps using the **stale cached copy** instead of re-reading the authoritative, governance-updated source.

### Finding Description
The EVM module maintains a package-level global `evmCoinInfo` (`x/vm/types/denom_config.go:30`) that stores the EVM coin's `Denom`, `ExtendedDenom`, `DisplayDenom`, and `Decimals`. All decimal-scaling logic throughout the codebase reads from this cached global via `GetEVMCoinDecimals()`, `GetEVMCoinDenom()`, `GetEVMCoinExtendedDenom()` [1](#0-0) , rather than from the live `x/vm` `Params` in the KV store.

This global is set exactly once, guarded by a `sync.Once` (`am.initializer`), inside `PreBlock`: [2](#0-1) 

and during `InitGenesis`: [3](#0-2) 

`SetGlobalConfigVariables` calls `configurator.WithEVMCoinInfo(coinInfo).Configure()`, which internally calls `setEVMCoinInfo`, but that function explicitly **panics/errors if `evmCoinInfo != nil`** — it is designed to run only once per process lifetime: [4](#0-3) 

However, `x/vm`'s `UpdateParams` governance message only calls `k.SetParams(ctx, req.Params)` — it never calls `k.InitEvmCoinInfo` or re-invokes `SetGlobalConfigVariables`: [5](#0-4) 

Because `EvmDenom` is a mutable field of `Params` (validated and settable via `SetParams`) and can reference denom metadata with different decimal exponents, governance can legitimately change `params.EvmDenom` (and therefore expected decimals, via `LoadEvmCoinInfo`/`InitEvmCoinInfo` semantics) — but the already-`sync.Once`-locked global `evmCoinInfo` will never reflect this change for the lifetime of the running node process.

Every critical scaling/accounting path depends on this stale global, not on live params:
- `x/vm/types/scaling.go` — `ConvertAmountTo18DecimalsLegacy`, `ConvertAmountTo18DecimalsBigInt`, `ConvertAmountTo18Decimals256Int`, `ConvertBigIntFrom18DecimalsToLegacyDec`, `ConvertEvmCoinDenomToExtendedDenom` all call `GetEVMCoinDecimals()`/`GetEVMCoinDenom()` [6](#0-5) 
- `x/vm/wrappers/bank.go` — `MintAmountToAccount`, `BurnAmountFromAccount`, `GetBalance`, `SpendableCoin`, `SendCoinsFromAccountToModule/ModuleToAccount` all use `types.GetEVMCoinDenom()`/`GetEVMCoinExtendedDenom()` to decide what denom/scaling to apply [7](#0-6) 
- `x/precisebank` uses `evmtypes.GetEVMCoinDecimals().ConversionFactor()` as its `ConversionFactor()` for fractional-balance/reserve accounting [8](#0-7) 
- `x/vm/wrappers/feemarket.go` uses `types.ConvertAmountTo18DecimalsLegacy` for base-fee scaling [9](#0-8) 

If governance changes `params.EvmDenom` to point at a coin with a different registered decimal exponent (e.g., moving from a 6-decimal denom to an 18-decimal denom, or vice versa) — a state transition that `SetParams`/`Params.Validate()` does not prevent — the `x/bank` module will operate against the **new** denom metadata (its own store of `DenomMetadata`), while every EVM-facing accounting function keeps using the **old, cached** `ConversionFactor()`. The mismatch is a fixed power-of-ten scaling error (e.g., 10^12) applied inconsistently between the "true" bank-side integer amount and the EVM/precisebank-side extended-decimal amount.

### Impact Explanation
This directly violates the required 1:1 accounting invariant between native coins and EVM/precisebank balances. Depending on the direction of the mismatch:
- Balances, mint/burn amounts, and transfers computed via `BankWrapper`/`FeeMarketWrapper`/precisebank would be scaled by the wrong factor, allowing effectively unbounded amplification (mint far more EVM-visible balance than the underlying bank coin backs it) or deflation (destroy/lock value on conversion) — i.e., unauthorized minting/duplication of spendable value or permanent freezing/loss of user funds, matching the required Critical impact categories (unauthorized minting or irreversible accounting corruption of spendable value across native/EVM/precisebank balances).
- Because `x/precisebank`'s reserve-to-fractional accounting assumes `ConversionFactor()` is authoritative and consistent with the bank module's real decimals, a mismatch breaks the reserve invariant that backs all fractional balances, which can be leveraged to mint/extract value disproportionate to actual reserves.

### Likelihood Explanation
Triggering this requires a governance-approved `MsgUpdateParams` for `x/vm` that changes `EvmDenom` to a denom with different decimals during the life of a running validator process (no restart in between) — this is a privileged, governance-gated action, similar to the original Sherlock finding requiring an admin's `setMonsterMultiplier()` call. Given the "Allowed Impact Gate" excludes governance-only assumptions, this materially weakens the case as a purely "unprivileged user" trigger; it is fundamentally a governance-driven parameter-desync bug, not an attacker-controlled unprivileged exploit path. I could not find any additional unprivileged trigger (e.g., an RPC/precompile call) that forces re-derivation of `evmCoinInfo` mid-process, nor could I fully verify from the indexed code whether `Params.Validate()` (in `x/vm/types/params.go`, not fully retrieved) restricts `EvmDenom` from being changed to an existing-but-differently-decimaled denom, or whether such a change is even a realistic operational scenario for a live chain (chains are documented as generally choosing a fixed decimal count at genesis, per the migration doc referencing "your chain is an 18-decimal chain").

### Recommendation
Do not rely on a process-lifetime `sync.Once`-guarded package global for values that are mutable through governance. Either:
1. Make `UpdateParams` for `x/vm` reject changes to `EvmDenom`/decimals entirely (treat decimals as immutable chain configuration, documented and enforced), or
2. If denom/decimals changes must be supported, have `UpdateParams` call `k.InitEvmCoinInfo`/re-run `SetGlobalConfigVariables` (removing the one-shot guard) synchronously within the same state transition, and audit all `GetEVMCoinDecimals()`/`GetEVMCoinDenom()` call sites (`x/vm/types/scaling.go`, `x/vm/wrappers/*.go`, `x/precisebank/types/fractional_balance.go`) to ensure they always read live, ctx-scoped params rather than a global cache.

### Proof of Concept
Not independently reproducible from the indexed code alone — I could not confirm from available files whether `Params.Validate()` in `x/vm/types/params.go` blocks changing `EvmDenom` to a denom with a different registered decimal exponent (the file's decimal-validation logic wasn't part of the retrieved content), which is required to fully demonstrate exploitability. A concrete PoC would require: (1) confirming `SetParams`/`Validate()` allows an `EvmDenom` change to a denom whose `x/bank` `DenomMetadata` has different decimals than the currently cached `evmCoinInfo.Decimals`, (2) submitting/passing a `MsgUpdateParams` governance proposal for `x/vm` with the new `EvmDenom`, and (3) demonstrating that subsequent `BankWrapper`/precisebank operations still scale amounts using the old conversion factor, producing a balance mismatch against the bank module's `DenomMetadata`-implied conversion.

// setEVMCoinInfo allows to define denom and decimals of the coin used in the EVM.
func setEVMCoinInfo(eci EvmCoinInfo) error {
	if evmCoinInfo != nil {
		return errors.New("EVM coin info already set")
	}

	if Decimals(eci.Decimals) == EighteenDecimals {
		if eci.Denom != eci.ExtendedDenom {
			return errors.New("EVM coin denom and extended denom must be the same for 18 decimals")
		}
	}

	evmCoinInfo = new(EvmCoinInfo)

	if err := setEVMCoinDenom(eci.Denom); err != nil {
		return err
	}
	if err := setEVMCoinExtendedDenom(eci.ExtendedDenom); err != nil {
		return err
	}
	if err := setDisplayDenom(eci.DisplayDenom); err != nil {
		return err
	}
	return setEVMCoinDecimals(Decimals(eci.Decimals))
}

// UpdateParams implements the gRPC MsgServer interface. When an UpdateParams
// proposal passes, it updates the module parameters. The update can only be
// performed if the requested authority is the Cosmos SDK governance module
// account.
func (k *Keeper) UpdateParams(goCtx context.Context, req *types.MsgUpdateParams) (*types.MsgUpdateParamsResponse, error) {
	if k.authority.String() != req.Authority {
		return nil, errorsmod.Wrapf(govtypes.ErrInvalidSigner, "invalid authority, expected %s, got %s", k.authority.String(), req.Authority)
	}

	ctx := sdk.UnwrapSDKContext(goCtx)
	if err := k.SetParams(ctx, req.Params); err != nil {
		return nil, err
	}

	return &types.MsgUpdateParamsResponse{}, nil
}

// ConvertAmountTo18DecimalsLegacy convert the given amount into a 18 decimals
// representation.
func ConvertAmountTo18DecimalsLegacy(amt sdkmath.LegacyDec) sdkmath.LegacyDec {
	evmCoinDecimal := GetEVMCoinDecimals()

	return amt.MulInt(evmCoinDecimal.ConversionFactor())
}

// ConvertAmountTo18DecimalsBigInt convert the given amount into a 18 decimals
// representation.
func ConvertAmountTo18DecimalsBigInt(amt *big.Int) *big.Int {
	evmCoinDecimal := GetEVMCoinDecimals()

	return new(big.Int).Mul(amt, evmCoinDecimal.ConversionFactor().BigInt())
}

// ConvertAmountTo18Decimals256Int convert the given amount into a 18 decimals
// representation.
func ConvertAmountTo18Decimals256Int(amt *uint256.Int) *uint256.Int {
	evmCoinDecimal := GetEVMCoinDecimals()

	return new(uint256.Int).Mul(amt, uint256.NewInt(evmCoinDecimal.ConversionFactor().Uint64()))
}

// ConvertBigIntFrom18DecimalsToLegacyDec converts the given amount into a LegacyDec
// with the corresponding decimals of the EVM denom.
func ConvertBigIntFrom18DecimalsToLegacyDec(amt *big.Int) sdkmath.LegacyDec {
	evmCoinDecimal := GetEVMCoinDecimals()
	decAmt := sdkmath.LegacyNewDecFromBigInt(amt)
	return decAmt.QuoInt(evmCoinDecimal.ConversionFactor())
}

// ConvertEvmCoinDenomToExtendedDenom converts the coin's Denom to the extended denom.
// Return an error if the coin denom is not the EVM.
func ConvertEvmCoinDenomToExtendedDenom(coin sdk.Coin) (sdk.Coin, error) {
	if coin.Denom != GetEVMCoinDenom() {
		return sdk.Coin{}, fmt.Errorf("expected coin denom %s, received %s", GetEVMCoinDenom(), coin.Denom)
	}

	return sdk.Coin{Denom: GetEVMCoinExtendedDenom(), Amount: coin.Amount}, nil
}

// MintAmountToAccount converts the given amount into the evm coin scaling
// the amount to the original decimals, then mints that amount to the provided account.
func (w BankWrapper) MintAmountToAccount(ctx context.Context, recipientAddr sdk.AccAddress, amt *big.Int) error {
	coin := sdk.Coin{Denom: types.GetEVMCoinDenom(), Amount: sdkmath.NewIntFromBigInt(amt)}

	convertedCoin, err := types.ConvertEvmCoinDenomToExtendedDenom(coin)
	if err != nil {
		return errors.Wrap(err, "failed to mint coin to account in bank wrapper")
	}

	coinsToMint := sdk.Coins{convertedCoin}
	if err := w.MintCoins(ctx, types.ModuleName, coinsToMint); err != nil {
		return errors.Wrap(err, "failed to mint coins to account in bank wrapper")
	}

	return w.BankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, recipientAddr, coinsToMint)
}

// BurnAmountFromAccount converts the given amount into the evm coin scaling
// the amount to the original decimals, then burns that quantity from the provided account.
func (w BankWrapper) BurnAmountFromAccount(ctx context.Context, account sdk.AccAddress, amt *big.Int) error {
	coin := sdk.Coin{Denom: types.GetEVMCoinDenom(), Amount: sdkmath.NewIntFromBigInt(amt)}

	convertedCoin, err := types.ConvertEvmCoinDenomToExtendedDenom(coin)
	if err != nil {
		return errors.Wrap(err, "failed to burn coins from account in bank wrapper")
	}

	coinsToBurn := sdk.Coins{convertedCoin}

	if err := w.BankKeeper.SendCoinsFromAccountToModule(ctx, account, types.ModuleName, coinsToBurn); err != nil {
		return errors.Wrap(err, "failed to burn coins from account in bank wrapper")
	}
	return w.BurnCoins(ctx, types.ModuleName, coinsToBurn)
}
