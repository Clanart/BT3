### Title
OP_RETURN data output is omitted from the fee/weight calculation, so the signed transaction pays a lower fee rate than requested - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts an optional `data` blob that is appended as an OP_RETURN output to `tx_outs` before the weight is measured, yet `calculate_weight_vbytes` is only ever called with `payments` — never with the data output included. The resulting `needed_fee` is therefore computed on a smaller virtual size than the transaction that is actually built and signed, mirroring the reported bug class of "expected vs actual fee mismatch": the parameter used at fee-calculation time (the tx without the data output) differs from the parameter at execution time (the tx with the data output).

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` at lines 194-202. Immediately after, the weight/vbytes are computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), which constructs a template transaction whose `output` list contains only `payments` (lines 85-99) — it never sees the data output. The same omission occurs in the change branch: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at lines 225-226 also excludes the OP_RETURN output.

Consequences inside the same function:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is underestimated by `fee_per_vbyte * (vbytes of the OP_RETURN output)`. With the maximum allowed 80 bytes of data (checked at lines 171-173), the OP_RETURN output adds roughly 90+ bytes (8-byte amount, script with OP_RETURN + push opcodes + up to 80 bytes of data), i.e. ~90 vbytes of unpaid-for weight.
2. The `TooLowFee` check at line 211 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the underestimated `vbytes`, so a transaction can pass the minimum-relay-fee gate while its *actual* feerate (`fee / real_vsize`) falls below the relay minimum.
3. The dust/change logic at lines 228-233 computes `value = input_sat - payment_sat - fee_with_change` where `fee_with_change` is also underestimated, so the change output is credited more sats than the intended fee schedule dictates and the effective feerate drops further.
4. `SignableTransaction::fee()` (lines 138-141) reports the real `sum(inputs) - sum(outputs)`, which silently diverges from `needed_fee()` whenever `data` is `Some`, even though the test at `networks/bitcoin/tests/wallet.rs:269` asserts they are equal (`needed_fee == tx.vsize() * FEE`) — that assertion only holds because the test never passes `data`.

This is reachable by any caller of the public `SignableTransaction::new` API that supplies a `data` payload (a public, untrusted input), including downstream processor paths that attach metadata to transactions.

### Impact Explanation
The signed transaction is larger than what the fee covered. With `fee_per_vbyte` near the relay minimum, the actual feerate drops below 1 sat/vB and the transaction is rejected by standard relay policy, stalling the spend; at higher requested feerates the transaction still underpays relative to the caller's intent, degrading confirmation priority and inflating `fee()` over the advertised `needed_fee()`. Since the fee shortfall is absorbed either by a reduced change output or silently by `sum(inputs) - sum(outputs)`, callers that rely on `needed_fee()` for accounting (as `prepare_send`/amortization logic does in the processor) will misaccount the true cost.

### Likelihood Explanation
Deterministic whenever `data: Some(_)` is supplied — the miscalculation happens on every construction, no adversary timing required. Severity is bounded because the fee is still paid from inputs (no theft), and the tx remains consensus-valid, but the min-relay-violation case makes the output transaction non-broadcastable, which can wedge a signing plan whose eventuality expects that txid.

### Recommendation
Build the weight-estimation template from the actual `tx_outs` (including the OP_RETURN output), or pass `data` into `calculate_weight_vbytes` and push the same `TxOut` there. Concretely, move the OP_RETURN push before line 204 and change `calculate_weight_vbytes` to accept `&[TxOut]` so the estimated output set is identical to the committed one, in both the no-change and with-change calls.

### Proof of Concept
```rust
// networks/bitcoin context: one confirmed ReceivedOutput, FEE sat/vB
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
  vec![output],
  &[(p2tr_script_buf(key).unwrap(), 1000)],
  None,
  Some(data),
  FEE,
).unwrap();

// needed_fee was computed on a template WITHOUT the 80-byte OP_RETURN output
assert!(tx.needed_fee() < u64::try_from(tx.transaction().vsize()).unwrap() * FEE);
// The real fee rate is therefore below the requested FEE; with FEE = 1 sat/vB
// the actual feerate < DEFAULT_MIN_RELAY_TX_FEE and the TX is unrelayable,
// despite passing the TooLowFee check inside SignableTransaction::new.
```
