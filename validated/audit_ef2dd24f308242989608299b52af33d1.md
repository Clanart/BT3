### Title
Arbitrum Orbit consensus client accepts unconfirmed/challengeable rollup nodes as final state - (File: modules/ismp/clients/ismp-arbitrum/src/lib.rs)

### Summary
`ArbitrumConsensusClient::verify_consensus` (Orbit branch, `modules/ismp/clients/ismp-arbitrum/src/lib.rs` lines 133-175) delegates all validation of an `ArbitrumPayloadProof` to `verify_arbitrum_payload` in `modules/ismp/clients/arbitrum/src/lib.rs`. That function only proves that a `state_hash` value exists at the storage slot for `_nodes[node_number].stateHash` in the classic Nitro `RollupCore` contract and matches the recomputed hash from the supplied `GlobalState`/`MachineStatus`/`inbox_max_count`. It never checks the node's `deadlineBlock`, `confirmData`/confirmation status, or whether a rival/challenging node exists.

### Finding Description
In the classic (non-BoLD) Nitro rollup protocol, a `Node` is written into the `_nodes` mapping as soon as a staker calls `stakeOnNewNode` / creates the assertion — well before the challenge period (`deadlineBlock`) elapses and before `confirmNode` is called. The `stateHash` field is populated at node-creation time, not at confirmation time. Therefore, proving inclusion of `stateHash` in `_nodes[node_number]` via a storage proof, as `verify_arbitrum_payload` does at [1](#0-0) , only proves that *some* proposer submitted this assertion — not that it survived the challenge window or was confirmed.

Contrast this with the sibling `verify_arbitrum_bold` function, which explicitly reads the parent assertion's `AssertionNode.secondChildBlock` and rejects the proof if it is non-zero, i.e., if the branch is contested: [2](#0-1) . No equivalent check (challenge state, `deadlineBlock`, or confirmation) exists for the Orbit path.

The `ismp-arbitrum` client wrapper simply forwards the verifier's result directly into the trusted `state_machine_map`/`StateCommitmentHeight`, treating it as finalized state: [3](#0-2) .

The project's own documentation for Arbitrum Orbit states finality is reached only "If no challenge arises within a specific timeframe" — i.e., after the challenge deadline: [4](#0-3) . The implementation does not enforce this documented invariant.

### Impact Explanation
If a still-challengeable (or outright invalid, currently-disputed) node's `state_hash` is accepted, `StateCommitmentHeight` for that height is inserted into the host's trusted state machine map as final Arbitrum L2 state. Any ISMP request/response/timeout message, or downstream settlement (e.g., cross-chain order fulfillment) that relies on a state/storage proof against that state root would be accepted, even though the real Nitro rollup could later invalidate that assertion via the challenge game. This corrupts the state commitment Hyperbridge treats as canonical and can enable settlement against state that never becomes canonical on L1.

### Likelihood Explanation
Exploitation requires that a permissioned Arbitrum proposer/validator (per the classic protocol's staking model) have submitted an assertion that has not yet passed its confirmation deadline or is being challenged. The submission of the ISMP consensus proof itself is unprivileged — anyone can relay a valid storage proof for any node present in `_nodes`, regardless of confirmation state, since `verify_consensus`/`verify_arbitrum_payload` do not gate on relayer identity or require the node to be confirmed. Given the docs explicitly promise "no challenge within a specific timeframe" as the finality condition, and the code never checks this, the missing check is a genuine, reachable protocol gap in the Orbit path.

### Recommendation
Add an explicit confirmation/challenge check to `verify_arbitrum_payload` analogous to `verify_arbitrum_bold`'s challenge check: e.g., prove and check the node's `deadlineBlock` against the L1 block referenced by `root`/the proof height (rejecting if `l1_block_number < deadlineBlock`), and/or prove the node has been confirmed (e.g., via the `_latestConfirmed` node number, or a `confirmData`/`NodeConfirmed` state check) before accepting its `state_hash` as final.

### Proof of Concept
1. On a classic-Orbit Arbitrum chain configured with `ismp-arbitrum`, a permissioned staker calls `stakeOnNewNode` to create node `N` with a given `stateHash`, but does not wait for `deadlineBlock` to pass (no `confirmNode` call), and/or a challenger later disputes it.
2. Any unprivileged relayer fetches the current storage proof for `_nodes[N].stateHash` from the still-unconfirmed L1 state and constructs `ArbitrumPayloadProof { node_number: N, storage_proof, contract_proof, global_state, machine_status, inbox_max_count, arbitrum_header }` matching the emitted `NodeCreated` event.
3. Submit `ArbitrumUpdate { l1_height, proof: ArbitrumConsensusProof::ArbitrumOrbit(proof) }` as an ISMP consensus message.
4. `verify_arbitrum_payload` succeeds because the `stateHash` slot proof matches, with no check for `deadlineBlock`/confirmation/challenge status; `verify_consensus` inserts the corresponding `StateCommitmentHeight` into `state_machine_map`, making the unconfirmed/challengeable state trusted by the host.

Arbitrum orbit finalizes L2 state commitments when a trusted proposer submits the L2's `state_hash` to the RollupCore  contract on the L1.
These submissions occur at designated intervals. Anyone acting as a challenger can dispute an invalid submissions.
If no challenge arises within a specific timeframe, the submitted `state_hash` is considered final. This approach leverages a permissioned proposer and challenger.
