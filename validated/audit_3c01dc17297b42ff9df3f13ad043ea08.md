### Title
Direct-transfer donation of a staking token inflates `_calLpSupply` denominator and permanently dilutes `accMGPPerShare`, freezing yield owed to legitimate stakers - (File: rewards/MasterMagpie.sol)

### Summary
`_calLpSupply()` uses `IERC20(_stakingToken).balanceOf(address(this))` as the reward-accrual denominator for every pool other than `vlmgp`/`mWomSV`. Because this balance can be inflated by anyone simply transferring the staking token directly to `MasterMagpie` (no `deposit()` call, no `UserInfo.amount` credit), any subsequent `updatePool()` call — including one triggered inside the permissionless `multiclaim`/`multiclaimSpec`/`multiclaimFor` functions — permanently bakes an under-stated `accMGPPerShare` increment into pool state, causing MGP emitted for that interval to be irretrievably under-distributed to the actual stakers.

### Finding Description
`_calLpSupply()` returns raw token balance for standard pools: [1](#0-0) 

This value is used directly as the divisor when accruing rewards in `updatePool()`: [2](#0-1) 

`mgpReward` is computed purely from elapsed time, `mgpPerSec`, and `allocPoint`/`totalAllocPoint` — it is independent of `lpSupply`. It is then divided by `lpSupply` to get the per-share increment added to `pool.accMGPPerShare`. Any user's claimable/pending MGP is `user.amount * accMGPPerShare / 1e12 - user.rewardDebt` (see `_calNewMGP`): [3](#0-2) 

If an attacker (or anyone) sends the staking token directly to `MasterMagpie` via `IERC20.transfer` (bypassing `deposit()`), `_calLpSupply()` immediately reflects the inflated balance while no `UserInfo.amount` is credited to any account for that donated amount. The next time `updatePool()` runs — which happens unconditionally inside `_multiClaim` for every staking token passed in, callable permissionlessly through `multiclaim(address[] _stakingTokens)`: [4](#0-3) [5](#0-4) 

— the elapsed-time-based `mgpReward` is divided by the artificially inflated `lpSupply`, producing a smaller `accMGPPerShare` increment than the true staked supply would warrant. `pool.lastRewardTimestamp` is then advanced to `block.timestamp`, permanently closing that accrual window. Because the sum of all `UserInfo.amount` for the pool never included the donated balance, and the increment to `accMGPPerShare` is written once and not retroactively correctable, the portion of `mgpReward` "assigned" to the phantom (uncredited) donated balance is unrecoverable by any staker — it is neither claimable by the donor (who has no `UserInfo.amount`) nor by legitimate stakers (whose `accMGPPerShare` credit was diluted). This is a genuine unprivileged EOA action requiring only holding/buying the staking token and calling a plain `IERC20.transfer`, no special role.

The described precondition (contract just unpaused, `lastRewardTimestamp` far behind `block.timestamp`) maximizes the loss window since `multiplier = block.timestamp - pool.lastRewardTimestamp` in `updatePool` is large, so a single donation right before the first `updatePool()` call dilutes a large batch of accrued MGP reward at once. `nonReentrant`, `whenNotPaused`, and existing reward-index bookkeeping do not prevent this because they only guard against reentrancy/pausing, not against unaccounted token transfers inflating `balanceOf`.

### Impact Explanation
The gap between the MGP that the emission schedule intends to distribute (based on `mgpPerSec * allocPoint * elapsed time / totalAllocPoint`) and what is actually made claimable via `accMGPPerShare * UserInfo.amount` is permanently lost for that pool's legitimate stakers once `lastRewardTimestamp` advances — this matches "High - Permanent freezing of unclaimed yield." The magnitude scales with the ratio of donated tokens to genuinely staked tokens and with the elapsed time since the last `updatePool()`, so it is maximized immediately after `unpause()` when `lastRewardTimestamp` is stale.

### Likelihood Explanation
This requires no privileged role — only ownership of some units of the target staking token (which for a Magpie receipt/LP token is typically obtainable cheaply or even flash-loanable if the token supports it) and a plain `transfer()` to `MasterMagpie`, followed by any permissionless action that calls `updatePool()` (e.g., `multiclaim`, `deposit`, `withdraw`, or `massUpdatePools`). It is fully repeatable across every non-`vlmgp`/`mWomSV` pool and does not depend on any admin misconfiguration — it is a structural consequence of using raw `balanceOf` as `_calLpSupply()`'s denominator, so likelihood is high whenever there is a meaningful gap between `block.timestamp` and `pool.lastRewardTimestamp` (e.g., right after unpausing, or any pool with infrequent interaction).

### Recommendation
Track staked supply explicitly (e.g., maintain a `poolInfo.totalStaked` incremented/decremented only in `_deposit`/`_withdraw`, or sum `UserInfo.amount` for the pool) and use that value — not `IERC20(_stakingToken).balanceOf(address(this))` — as the denominator in `updatePool()`/`_calMGPReward()`. This removes any dependency on raw token balance and makes the reward-per-share calculation immune to donation-based dilution.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `MGP`, a mock ERC20 staking token, register the pool via `add()`, fund `MasterMagpie` with MGP for reward payout, set `mgpPerSec` and `startTimestamp`.
2. User A deposits `1000` staking tokens via `deposit()`.
3. Pause and then `unpause()` the contract; advance `block.timestamp` far forward (e.g., +30 days) without calling `updatePool()` so `lastRewardTimestamp` is stale.
4. **Run 1 (baseline):** Immediately call `multiclaim([stakingToken])` from User A. Record `accMGPPerShare`, `userInfo[stakingToken][A].amount`, and A's claimed MGP.
5. **Run 2 (attack):** Reset to the same state as step 3. Have an unprivileged attacker EOA call `stakingToken.transfer(masterMagpie, 9000)` (a raw ERC20 transfer, not `deposit()`), inflating `IERC20(stakingToken).balanceOf(masterMagpie)` to `10000` while `userInfo[stakingToken][attacker].amount` stays `0`. Then call `multiclaim([stakingToken])` from User A.
6. Assert: in Run 2, `pool.accMGPPerShare` increment and A's claimed MGP are ~10x smaller than in Run 1, even though the same MGP emission interval and `mgpPerSec`/`allocPoint` applied — demonstrating that `sum(UserInfo.amount)` (`1000`) diverges from `_calLpSupply()` (`10000`), and the shortfall in distributed MGP is unrecoverable since `pool.lastRewardTimestamp` has already advanced past the interval.
7. Assert that the attacker cannot claim any of the diluted-away reward (since they have no `UserInfo.amount`), confirming the MGP is permanently frozen/unclaimed rather than merely redirected.

```text
    function updatePool(address _stakingToken) public whenNotPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        if (block.timestamp <= pool.lastRewardTimestamp || totalAllocPoint == 0) {
            return;
        }
        uint256 lpSupply = _calLpSupply(_stakingToken);
        if (lpSupply == 0) {
            pool.lastRewardTimestamp = block.timestamp;
            return;
        }        
        uint256 multiplier = block.timestamp - pool.lastRewardTimestamp;
        uint256 mgpReward = (multiplier * mgpPerSec * pool.allocPoint) / totalAllocPoint;
        
        pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
        pool.lastRewardTimestamp = block.timestamp;

        emit UpdatePool(
            _stakingToken,
            pool.lastRewardTimestamp,
            lpSupply,
            pool.accMGPPerShare
        );
    }    
```
