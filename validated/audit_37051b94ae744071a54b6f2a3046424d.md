### Title
Zero-value and dust outputs received via the Scanner are accepted as transaction inputs, letting any sender force the multisig to burn fees signing for worthless inputs - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is "a zero/rounded-to-zero amount is passed unconditionally into an operation that cannot handle zero, causing a permanent failure (DOS)". The analog in Serai's in-scope code is the inverse direction of the same mistake: `SignableTransaction::new` never checks that *inputs* are worth anything. Any output whose `script_pubkey` matches a Serai P2TR key — including a `0`-sat or dust-valued output that any unprivileged party can create in a Bitcoin transaction — is registered by the scanner as a `ReceivedOutput` and is unconditionally accepted as an input, where it adds ~57 vbytes of weight, consumes a full FROST signing round (preprocess + signature share per input in `SignableTransaction::multisig`/`TransactionMachine::preprocess`), and contributes nothing to the payment.

### Finding Description
`SignableTransaction::new` enforces a dust floor on *payments* (`*amount < DUST` → `TransactionError::DustPayment`, send.rs:165-169) and bounds change to `value >= DUST` (send.rs:228-233), but applies no value floor whatsoever to inputs. It simply sums them and serializes every `ReceivedOutput` into a `TxIn` (send.rs:175-185). Each input then gets its own `AlgorithmMachine` (a full Schnorr/FROST signing instance) in `multisig` (send.rs:273-285) and its own preprocess in `TransactionMachine::preprocess` (send.rs:306-315).

The scanner registers any transaction output whose `script_pubkey` equals the (possibly offset) P2TR key, matching on `script_pubkey` alone — the tests show `scan_transaction` returning `ReceivedOutput`s purely by address match (tests/wallet.rs:249-257). Since the P2TR address is public, any third party can craft a transaction containing a `0`-sat or sub-dust output to the multisig address. Such outputs are consensus-valid (Bitcoin only requires non-negative values; 0-value outputs are non-standard to *relay* but a miner or any confirmed path can include them, and dust outputs in the 1-545 sat range relay fine).

A `ReceivedOutput` of value `v < ~57*fee_rate` sats can never pay for its own input weight. When the scheduler aggregates inputs (`MAX_INPUTS: usize = 520`), each poisoned input:
- consumes signing bandwidth (a nonce commitment, binding-factor computation, and signature share per input per input),
- increases `needed_fee`/`weight` while contributing zero or dust value, and
- at the extreme, a 0-value output is pure fee-burn that the wallet will happily spend a signature on — the exact "zero amount fed to an operation that shouldn't see zero" shape of the original finding.

If enough worthless outputs are registered, transaction construction can also be pushed toward `NotEnoughFunds`/`TooLargeTransaction`, stalling legitimate payments.

### Impact Explanation
Economic DOS: an unprivileged attacker spends dust (or gets 0-value outputs mined) to the Serai multisig address, and the protocol thereafter burns real fees and threshold-signing rounds on inputs that can never recoup their cost. Funds are also *reported received* by the scanner that are economically unspendable. Unlike the Allo case this doesn't revert, but the trust model is the same: an unprivileged party's public input (a Bitcoin transaction they send) forces the honest set into a loss-making operation with no filter.

### Likelihood Explanation
Medium: the attack is cheap and permissionless — the multisig's P2TR `script_pubkey` is public and anyone can send to it. The cost is bounded by needing the outputs confirmed, and mitigation is possible by ignoring dust inputs at the scheduler level (out of scope here), which keeps it out of the High range.

### Recommendation
Apply the same `DUST` floor to inputs that is already applied to payments and change in `SignableTransaction::new`: reject or skip `ReceivedOutput`s whose `output.value` is below `DUST` (send.rs:175-185), and/or have the `Scanner` decline to register outputs below a spendability threshold so they never become `ReceivedOutput`s.

### Proof of Concept
1. Obtain the multisig's P2TR address (`p2tr_script_buf(group_key)`).
2. Broadcast a transaction paying `546` sats (or a 0-value output via a cooperative miner) to that address.
3. `Scanner::scan_transaction` registers it as a `ReceivedOutput` (no value check; matching is by `script_pubkey` only, per tests/wallet.rs:249-257).
4. `SignableTransaction::new(vec![poisoned_output, ...], &payments, ...)` accepts it as an input — only payments and change are dust-checked (send.rs:165-169, 228-233) — and `multisig`/`preprocess` spawn a full Schnorr signing instance for it (send.rs:273-315), adding ~57 vbytes of fee while contributing ~0 sats. Repeat to fill up to `MAX_INPUTS = 520` slots.

Caveat: the `Scanner` source file itself was not located in the index (`networks/bitcoin/src/wallet/scanner.rs` not found), so the claim that scanning applies no value floor is inferred from the wallet tests and the "matches script_pubkey only" design rather than read directly; the input-side absence of any dust check in `send.rs` is confirmed by the code shown above.
