### Title
Re-association after a delegation/commission accrues under a direct-cast address permanently diverts the user's staking rewards to the community pool - ([File: sei-cosmos/x/distribution/keeper/hooks.go])

### Summary
The Velocimeter report shows that burning/re-pointing an identity token (`veNFT` merge) before its accrued rewards are claimed causes those rewards to become permanently unclaimable, because the reward-claim path is gated on `msg.sender` being the (now-burned) owner. Sei-chain has a structurally identical bug class in its EVM↔Sei dual-address model: staking/distribution state (delegations, validator self-bond, accrued commission/rewards) is keyed off a Sei `AccAddress`, but an EVM address can be "re-pointed" from its direct-cast Sei address to a different, "true" pubkey-derived Sei address via `associatePubKey`. When that happens, the old direct-cast address becomes permanently unreceivable, and any staking rewards/commission that would have been paid to it are diverted away from the user rather than delivered to them - a fund-loss outcome analogous to losing rewards on `merge`.

### Finding Description
Every EVM address has two possible Sei-side identities: a deterministic **direct-cast** address (`sdk.AccAddress(evmAddr[:])`) used before any explicit association, and a **true** pubkey-derived Sei address established once the user calls `associate`/`associatePubKey` (or signs any tx) [1](#0-0) .

A user can accumulate staking state (self-delegation as a validator operator, delegator rewards, accumulated commission) under the direct-cast address before ever associating. If they later associate that EVM address with a *different* true Sei address, `SetAddressMapping` simply overwrites the mapping [2](#0-1) , and `CanAddressReceive`/`CanSendTo` subsequently reports the old direct-cast address as **unable to receive funds**, since the associated address is no longer itself: [3](#0-2) 

Distribution's `AfterValidatorRemoved`/reward-withdraw path force-pays outstanding commission/rewards to the delegator's withdraw address, which defaults back to the delegator's own address. `GetDelegatorWithdrawAddr` explicitly falls back to the (now-unreceivable) delegator address whenever the configured withdraw address is not receivable: [4](#0-3) 

Because the operator/delegator address itself is the direct-cast, unreceivable address after re-association, the force-withdraw in `AfterValidatorRemoved` cannot actually pay the user. The code deliberately avoids panicking (which would halt the chain) by instead routing the funds to the community pool: [5](#0-4) 

This is confirmed as an intentional, known trade-off in the codebase's own comments describing the root cause: re-association "orphan[s] any staking/distribution state created under the direct-cast identity" [6](#0-5)  and [7](#0-6) . Mitigations exist only for two narrow cases: (1) the EIP-7702 `SetCode` authority is pre-associated to its true address before a delegation can be installed [8](#0-7) , and (2) the staking precompile's `delegate`/`delegateFor` refuse to let an *unassociated* caller delegate at all, specifically because "there is no good way to merge delegations if it becomes associated" [9](#0-8) . Neither mitigation covers the case where staking state (e.g., a self-delegated validator, or a delegation made directly via a Cosmos-signed `MsgDelegate` before any EVM interaction) already exists under the direct-cast address and the user only associates afterward — this path remains reachable by any public RPC/transaction submitter who controls the underlying key material.

### Impact Explanation
Analogous to the `veNFT` merge issue where burning the position token permanently forfeits at least one week of rewards, here the user's own action of associating their EVM address (a completely ordinary, publicly reachable operation) permanently forfeits any commission/rewards that were pending under the pre-association direct-cast identity. The code's own fix confirms the funds are not returned to the user but are diverted to the community pool — a genuine, permanent loss of the affected delegator's/operator's funds, even though the protocol avoids a chain halt.

### Likelihood Explanation
Reachable by any ordinary user/public RPC client: create a validator or delegation under a direct-cast address (e.g. via a Cosmos-signed tx before ever touching the EVM), let commission/rewards accrue, then submit a normal `associatePubKey`/`Associate` transaction — an action many users will naturally perform to unlock full EVM address capabilities. No privileged access or malicious peer/validator behavior is required.

### Recommendation
Before or during `AssociateAddresses`, migrate outstanding distribution state (pending rewards, `ValidatorAccumulatedCommission`, delegator withdraw address entries) from the direct-cast address to the newly associated true Sei address, mirroring the balance migration already done in `MigrateBalance` [10](#0-9) . At minimum, force-withdraw any pending rewards/commission to the direct-cast address's *current* balance (which is still migrated) before flipping the mapping, so the community-pool fallback in `AfterValidatorRemoved` is never triggered for a still-recoverable balance.

### Proof of Concept
1. Using a normal Cosmos key, sign a `MsgCreateValidator` (or `MsgDelegate`) with `DelegatorAddress` set to `sdk.AccAddress(evmAddr[:])` — the direct-cast address of some EVM address the same key controls — before ever sending an EVM transaction or calling `associate`.
2. Let commission/rewards accrue for that validator/delegation over several blocks.
3. Submit an ordinary `associatePubKey`/`Associate` EVM transaction that maps `evmAddr` to a different, pubkey-derived Sei address (this is normal behavior per `AssociateAddresses` in `utils/helpers/associate.go`).
4. `CanAddressReceive`/`CanSendTo` now report the original direct-cast address as unreceivable [3](#0-2) .
5. Trigger `AfterValidatorRemoved` (e.g. by having the validator unbond/removed) or any reward withdrawal targeting that address; the accrued commission/rewards are routed to the community pool instead of the user, as demonstrated by `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator` [11](#0-10) .

## Dual Address Model

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func (k Keeper) GetDelegatorWithdrawAddr(ctx sdk.Context, delAddr sdk.AccAddress) sdk.AccAddress {
	store := ctx.KVStore(k.storeKey)
	b := store.Get(types.GetDelegatorWithdrawAddrKey(delAddr))

		return delAddr
	}

		return delAddr
	}
	return withdrawAddr
}

// TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator covers the
// case where the validator operator address itself cannot receive funds — its EVM
// address was re-associated (e.g. via associatePubKey) away from the direct-cast Sei
// address it was created under. The withdraw-address fallback in GetDelegatorWithdrawAddr
// resolves back to that same unreceivable operator address, so the commission
// force-withdraw fails. AfterValidatorRemoved runs during EndBlock, so it must not panic:
// the commission is routed to the community pool instead, which conserves value because
// the coins already back the distribution module account.
func TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	// The validator operator is the direct-cast Sei address of an EVM address.
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	castAddr := sdk.AccAddress(evmAddr[:])
	valAddr := sdk.ValAddress(castAddr)
	valAccAddr := sdk.AccAddress(valAddr) // == castAddr

	require.True(t, app.BankKeeper.CanSendTo(ctx, castAddr))

	// Re-associate the EVM address to a different true Sei address, mirroring
	// associatePubKey after a validator was created under the direct-cast address.
	associatedAddr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))[0]
	app.EvmKeeper.SetAddressMapping(ctx, associatedAddr, evmAddr)

	// The operator/delegator address can no longer receive funds, and the
	// withdraw-address fallback resolves back to that same unreceivable address.
	require.False(t, app.BankKeeper.CanSendTo(ctx, castAddr))
	require.Equal(t, valAccAddr.String(), app.DistrKeeper.GetDelegatorWithdrawAddr(ctx, valAccAddr).String())

	commission := sdk.DecCoins{sdk.NewDecCoin("usei", sdk.NewInt(10))}
	coins := sdk.NewCoins(sdk.NewCoin("usei", sdk.NewInt(10)))
	distrAcc := app.DistrKeeper.GetDistributionAccount(ctx)
	require.NoError(t, apptesting.FundModuleAccount(app.BankKeeper, ctx, distrAcc.GetName(), coins))
	app.AccountKeeper.SetModuleAccount(ctx, distrAcc)

	app.DistrKeeper.SetValidatorOutstandingRewards(ctx, valAddr, types.ValidatorOutstandingRewards{Rewards: commission})
	app.DistrKeeper.SetValidatorAccumulatedCommission(ctx, valAddr, types.ValidatorAccumulatedCommission{Commission: commission})

	communityBefore := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	moduleBalanceBefore := app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei")

	require.NotPanics(t, func() {
		app.DistrKeeper.Hooks().AfterValidatorRemoved(ctx, sdk.ConsAddress{}, valAddr)
	})

	// The commission could not be paid out, so it stays in the distribution module
	// account and is accounted to the community pool. No value leaves the module and
	// the unreceivable operator address receives nothing.
	communityAfter := app.DistrKeeper.GetFeePool(ctx).CommunityPool.AmountOf("usei")
	require.Equal(t, communityBefore.Add(sdk.NewDec(10)), communityAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, castAddr, "usei").IsZero())
	require.Equal(t, moduleBalanceBefore, app.BankKeeper.GetBalance(ctx, distrAcc.GetAddress(), "usei"))

// AssociateAuthorizationAuthorities pre-associates every EIP-7702 SetCode authorization
// authority in the transaction with its true (pubkey-derived) Sei address before EVM
// execution installs delegation code for it. Authorities are distinct accounts from the tx
// sender, so the sender association performed by the caller does not cover them. Without
// this, SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey
// call can remap, orphaning any staking/distribution state created under the direct-cast
// identity (which can then halt the chain via the distribution validator-removal hook).

// paths associate authorities identically. It is best-effort: only authorities whose
// authorization the EVM will actually apply are pre-associated — helpers.AuthorityToPreAssociate
// enforces the same chain-id/nonce/account-code checks go-ethereum uses, which also prevents
// replaying a publicly-visible authorization a user signed for another chain to force-associate
// them. Each association runs in its own cache context and is only committed on success, so an
// already-associated, skipped, or failing authority affects only itself and never rejects the
// transaction (matching go-ethereum, which would still accept it). Non-SetCode transactions

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
