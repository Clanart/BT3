### Title
Address-association precompile accepts any EIP-191–signed message with no purpose binding, enabling replay of unrelated signatures to force irreversible EVM↔Sei association and balance migration — ([File: precompiles/addr/addr.go])

### Summary
Analogous to the nuts-node JWT confusion (a signature produced for one purpose — a Verifiable Presentation — accepted by a verifier that only checks "is this a validly-signed artifact from a known key" instead of "was this artifact specifically created/typed for this action"), the `addr` precompile's `associate` function accepts *any* EIP-191 `(v, r, s, message)` tuple and treats a successful `ecrecover` as sufficient proof of intent to permanently bind an EVM address to a Sei address. There is no canonical-message check, no domain separator, no nonce, and no "purpose" tag embedded in what is hashed and verified.

### Finding Description
`PrecompileExecutor.associate` takes attacker-supplied `v, r, s` and an attacker-supplied `customMessage` string, hashes the message with `crypto.Keccak256Hash([]byte(customMessage))`, and recovers a pubkey/address pair purely from that hash and signature: [1](#0-0) 

Nothing in this path validates that `customMessage` is the documented association template ("Please sign this message to link your EVM and Sei addresses…"), nor does it bind the signature to a `typ`/purpose discriminator, nonce, chain ID, or contract address. Any message the victim ever signed with `personal_sign`/EIP-191 for a *completely unrelated* purpose (dApp login, off-chain order, another protocol's message) is structurally indistinguishable from an "I want to associate my address" message once hashed and passed to `helpers.GetAddresses`: [2](#0-1) 

The recovered pubkey then drives `associateAddresses`, which — because it is unauthenticated as to *intent* — permanently writes the address mapping and immediately migrates all balances from the "cast" pseudo-account (`sdk.AccAddress(evmAddr[:])`) to the real Sei account, and mutates account state (sets pubkey, creates `BaseAccount`) without further consent: [3](#0-2) [4](#0-3) 

This is the same root-cause class as CVE-2026-41164: the verifier (`sigverify`/`GetAddresses`/`AssociateAddresses`) performs only a generic "is the signature cryptographically valid for a key I can derive" check, and completely omits any type/purpose binding that would distinguish "signed intentionally for address-association" from "signed for something else." Contrast this with the chain's own EIP-7702 authorization handling, which explicitly guards against a structurally similar replay by checking the authorization's `ChainID` before pre-associating, showing the team is aware of this exact bug class elsewhere in the code but has not applied the same discipline to the `addr` precompile's free-form `customMessage`: [5](#0-4) 

### Impact Explanation
Because the check is purely "does ecrecover succeed," anyone who has ever observed a victim's `(message, v, r, s)` signed for an unrelated purpose (e.g., harvested from another dApp's login flow, an off-chain marketplace signature, or any personal_sign artifact) can submit it to `associate()` on the victim's behalf. This forces an **irreversible** state change on the victim's account:
- Permanently binds the victim's EVM address to their Sei address (idempotent going forward — the "already associated" guard means the victim can never redo this under their own chosen timing/message).
- Immediately triggers `MigrateBalance`, moving all spendable `usei`/wei balances that had accrued at the implicit "cast" address into the associated Sei account and deleting the cast `BaseAccount`.
- Sets the account pubkey and account metadata as a side effect of a signature the victim never intended to use for this purpose.

This is a forced, attacker-triggered, irreversible mutation of on-chain account state and fund location performed without the victim's actual consent to that specific action — the analog of the "type confusion → active:true" outcome in the original report, where a signed artifact meant for one purpose is silently accepted to grant a materially different capability.

### Likelihood Explanation
Requires the attacker to have obtained *some* message the victim signed with the same EVM key via `personal_sign`/EIP-191 for any purpose (common in web3 UX — logins, off-chain approvals, etc.), which is realistic since victims routinely sign many messages besides the association template. No special privileges are needed; this is reachable by any public RPC client submitting an EVM transaction to the precompile at `0x0000000000000000000000000000000000001004`.

### Recommendation
Bind the `associate` signature to its specific purpose:
- Require `customMessage` to match a canonical, versioned template that embeds a domain separator (e.g., contract address `0x1004`, chain ID, and a fixed "ASSOCIATE" type tag), rejecting any message that doesn't match this exact structure — mirroring how the fixed `typ: "at+jwt"` check was added to `IntrospectAccessToken`.
- Alternatively, require an EIP-712 typed-data signature with a struct/type hash unique to association, so signatures produced for other typed-data domains cannot be replayed here.
- Add a nonce or one-time challenge issued by the chain/precompile so a given signed message cannot be replayed if it wasn't freshly generated for this specific call.

### Proof of Concept
1. Victim signs any unrelated message `M` with `personal_sign` for some other dApp (e.g., "Login to ExampleApp at 2026-09-17T12:00:00Z"), producing `(v, r, s)`.
2. Attacker (who obtained `M, v, r, s` through the unrelated dApp's own infra, a phishing log, or any public source) calls `addr.associate(v-27, r, s, M)` on Sei's EVM RPC.
3. `helpers.GetAddresses` recovers the victim's pubkey from `keccak256(M)` and `(v,r,s)` since these are exactly the standard ecrecover inputs — no check ties `M` to "association intent."
4. `associateAddresses`/`AssociateAddresses` executes, permanently binding the victim's EVM↔Sei addresses and migrating any balance held at the implicit cast address, without the victim ever intending or executing this specific `associate` action.

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

// RecoverAddressesFromTx recovers the sender's EVM address, Sei address, and public key
// from a signed PROTECTED Ethereum transaction using the provided signer.
// This is the core recovery function used by both the EVM ante handler and Giga executor.
//
// IMPORTANT: This function calls AdjustV internally, which is only correct for protected
// (EIP-155) transactions. For unprotected legacy transactions (blocktest only), use
// GetAddresses directly with the raw V value.
//
// The caller must provide the appropriate signer for the context. Use evmante.SignerMap[version](chainID)
// where version is determined by evmante.GetVersion(ctx, ethCfg) to ensure consistent behavior
// with the EVM ante handler.
func RecoverAddressesFromTx(ethTx *ethtypes.Transaction, signer ethtypes.Signer, chainID *big.Int) (common.Address, sdk.AccAddress, cryptotypes.PubKey, error) {
	txHash := signer.Hash(ethTx)
	V, R, S := ethTx.RawSignatureValues()
	adjustedV := AdjustV(V, ethTx.Type(), chainID)
	return GetAddresses(adjustedV, R, S, txHash)
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// TestPreprocessSkipsForeignChainSetCodeAuthority verifies that an EIP-7702 authorization
// signed for a DIFFERENT chain is not pre-associated. The authorization sig-hash uses the
// auth's own ChainID, so recovery succeeds, but the EVM would skip a wrong-chain auth at
// execution — so pre-associating it would let anyone replay a victim's public cross-chain
// authorization to force-associate them.
func TestPreprocessSkipsForeignChainSetCodeAuthority(t *testing.T) {
	k := &testkeeper.EVMTestApp.EvmKeeper
	ctx := testkeeper.EVMTestApp.GetContextForDeliverTx(nil)
	handler := ante.NewEVMPreprocessDecorator(k, k.AccountKeeper())
	chainID := k.ChainID(ctx)
	foreignChainID := new(big.Int).Add(chainID, big.NewInt(1)) // guaranteed != local chain

	sponsorKey, err := crypto.GenerateKey()
	require.NoError(t, err)
	victimKey, err := crypto.GenerateKey()
	require.NoError(t, err)
	victimEVM := crypto.PubkeyToAddress(victimKey.PublicKey)
	_, victimTrueSei, _, err := helpers.GetAddressesFromPubkeyBytes(crypto.FromECDSAPub(&victimKey.PublicKey))
	require.NoError(t, err)

	// Victim's authorization is signed for a foreign chain (e.g. Ethereum mainnet).
	auth, err := ethtypes.SignSetCode(victimKey, ethtypes.SetCodeAuthorization{
		ChainID: *uint256.MustFromBig(foreignChainID),
		Address: common.HexToAddress("0x000000000000000000000000000000000000c0de"),
		Nonce:   0,
	})
	require.NoError(t, err)
	// Sanity: recovery still resolves the victim (the sig-hash uses the auth's own ChainID).
	recoveredEVM, _, _, rerr := helpers.RecoverAddressesFromAuthorization(auth)
	require.NoError(t, rerr)
	require.Equal(t, victimEVM, recoveredEVM)
