## Analog Found

### Title
Position-indexed partial-commit line selection is not content-validated against a freshly refetched diff, allowing silent inclusion of unintended/attacker-influenced lines in a commit - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
The Sherlock finding's broken invariant is: an accounting function trusts a *stale* quantity (`amountDue` = original principal) instead of re-deriving the *current* remaining value, and nothing revalidates that the stale value still matches reality before it's used to mutate global state (`totalPrincipalTokensRepaid`). The GitHub Desktop analog is architecturally identical in kind, applied to "what gets committed": Desktop tracks a user's partial-staging selection as a set of **positional line indices** (`absoluteIndex`) computed against one snapshot of a file's diff, then re-fetches a **new** diff of the same file at the moment of staging and blindly re-applies those same positional indices to decide which lines to include in the patch — without verifying that line *content* at that index is unchanged.

### Finding Description
`formatPatch` selects lines purely by `absoluteIndex = hunk.unifiedDiffStart + lineIndex`, checking `file.selection.isSelected(absoluteIndex)`: [1](#0-0) 

That `file.selection` object (a `DiffSelection`) is populated by the UI against the diff that was rendered for the user in the Changes view. But when the user actually commits, `stageFiles` invokes `applyPatchToIndex` for every partially-selected file, and `applyPatchToIndex` **re-fetches a brand-new diff from git** right before building the patch: [2](#0-1) 

There is no guarantee this freshly-fetched diff (`diff` at line 60) is identical to the diff the user actually looked at when they checked/unchecked lines — `stageFiles`/`applyPatchToIndex` is invoked after `unstageAll(repository)` resets the index, and asynchronously after the UI-side diff render: [3](#0-2) [4](#0-3) 

The application is aware that diffs can go stale relative to a held selection — there's an explicit reconciliation step, `updateChangesWorkingDirectoryDiff`, that runs when the working directory diff is reloaded: [5](#0-4) 

Critically, that reconciliation only strips selection state for indices that are **no longer includeable** (turned into context lines or removed entirely). It does **not** detect the case where a line at the same `absoluteIndex` still exists and is still an addable/removable line, but its **content has changed** (e.g. because the hunk boundaries shifted, an unrelated edit above it changed indices, or the working tree content was rewritten between the two diff snapshots). The selection identity is purely "is this numeric index still a line" — never "is this the same semantic change the user reviewed and approved." This is the same class of bug as the Sherlock report: reusing a previously-computed scalar/identifier as if it still represents current state, with no invariant check tying it back to the live data before it is consumed to produce an on-disk/committed artifact.

### Impact Explanation
This corrupts **what the user actually commits and later pushes** without any error, warning, or diff mismatch surfaced to the user — one of the explicitly valid impact classes ("silent corruption of what the user commits or pushes"). A user who reviews a diff, selects only benign lines for a partial commit, and then commits while the working tree diff has shifted (e.g. due to an external editor autosave/format-on-save tool bundled with a cloned/fetched repository, a build/lint task the repo instructs contributors to run, or any tool that rewrites the file between the rendered diff and the staging-time diff) can end up silently staging and committing **different lines than what they saw and approved**, including lines they explicitly deselected. Because staging uses `git apply --cached` against the freshly-fetched diff with stale indices, the mismatch is not detected — `git apply` will happily apply against whatever hunk exists at that position in the new diff.

### Likelihood Explanation
The window is real but narrow: it requires the working-tree file to change (in a way that shifts hunk/line positions while retaining includeable line types at the same index) between the diff render the user is looking at and the moment `stageFiles`/`applyPatchToIndex` executes for the commit. Desktop's own file watcher normally triggers `updateChangesWorkingDirectoryDiff` on such changes, but that reconciliation (as shown above) is coarse — it prunes only lines that literally vanished from being includeable, not lines whose content changed while remaining includeable at the same index. A cloned/fetched repository that ships tooling which reformats/rewrites files as part of a normal contributor workflow (format-on-save, pre-commit formatters run outside Desktop, lint-staged, etc.) is a realistic and not-unnatural trigger, since Desktop explicitly supports "open in external editor" while reviewing a diff.

### Recommendation
Tie selection identity to diff *content*, not raw positional index: when `updateChangesWorkingDirectoryDiff` (or any refetch preceding `applyPatchToIndex`) detects a new diff, re-validate that each selected line at `absoluteIndex` still has the same `type`/`text` as when the selection was made, not merely that it is still includeable. If content differs, drop the selection for that line (mirroring the existing "no longer exists" pruning) and require re-review, and/or have `applyPatchToIndex`/`stageFiles` compare the diff used for the patch against the diff snapshot the current `DiffSelection.selectableLines` was derived from, refusing to stage if they diverge.

### Proof of Concept
1. Open a modified file with several hunks in Desktop's Changes view; the app fetches diff D1 and the user selects only specific benign lines via `DiffSelection` (indices computed against D1), per `formatPatch`'s `absoluteIndex` logic.
2. Before clicking "Commit", an external tool tied to the repo (e.g., a formatter invoked by "Open in external editor", or a save-hook from the repo's tooling) rewrites the file such that line counts/positions shift but the reconciliation in `updateChangesWorkingDirectoryDiff` still finds the previously-selected indices "includeable" (e.g., an insertion above the hunk shifts everything down by N lines while keeping the same line *types* at those indices).
3. The user clicks "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches a **new** diff D2 via `getWorkingDirectoryDiff` (`app/src/lib/git/apply.ts:60`) and calls `formatPatch(file, D2)` using the stale `file.selection` computed against D1.
4. `formatPatch` includes whatever lines sit at the stale `absoluteIndex` positions in D2 — which are no longer the lines the user reviewed/approved — and `git apply --cached` stages them silently, producing a commit whose content differs from what the user intended and saw on screen.
