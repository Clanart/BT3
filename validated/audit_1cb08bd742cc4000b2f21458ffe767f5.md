## Analysis

The reported bug class is a **time-of-check/time-of-use (TOCTOU) staleness bug**: a value is captured/decided at one point in time, an asynchronous operation runs, and then the stale value is applied without re-validating it against the current state — with no economically/structurally sound guard covering all the ways the underlying state can drift in between.

The closest analog in this codebase is in GitHub Desktop's Copilot-powered merge-conflict resolution flow.

### Title
Stale snapshot of conflicted file content can be silently spliced back to disk when applying Copilot conflict resolutions - (`app/src/lib/stores/app-store.ts`)

### Summary
`buildConflictContext` snapshots each conflicted file's on-disk content (`rawContent`) once, before the Copilot request is sent. The AI request/response round-trip is asynchronous and can take well over a minute (the code tracks `copilotConflictResolutionOver120sCount`). The model's per-hunk resolutions are later spliced back into that stale `rawContent` snapshot — by ordinal hunk position, not by content matching — and, when the user confirms, `_applyCopilotConflictResolutions` writes the resulting reassembled string straight to disk. The only staleness guard checks whether the file has *already been fully resolved* externally; it does not check whether the conflicted content has *changed* (e.g. different/added/reordered conflict markers) while still remaining conflicted.

### Finding Description
1. `buildConflictContext` reads each conflicted file and stores its full content as `rawContent`, then extracts ordered conflict hunks: [1](#0-0) 

2. The model only returns lightweight per-hunk resolutions, which are later spliced back into that captured `rawContent`, matched **by order, not by line number or content**: [2](#0-1) [3](#0-2) 

3. This round trip is explicitly asynchronous and can take minutes; the app even buckets and records how long it takes: [4](#0-3) 

4. When the user clicks "Continue Merge," `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` (built from the stale `rawContent` snapshot) directly to disk. The only re-validation it performs is checking whether the file is *fully resolved* (no more conflict markers at all) — if so, it skips to avoid clobbering the user's own edits: [5](#0-4) 

There is no check that the file's *current* conflicted content (which still has markers, so the "already resolved" guard doesn't fire) still matches the `rawContent` that was fed to the model. If the underlying conflict state changes between generation and apply — for example the user aborts and restarts the operation with `useCopilotConflictResolution` state retained across ConfirmAbort transitions, another operation modifies the working tree, or the merge/rebase is redone against updated remote content fetched in the interim — the ordinal-position splice from `reassembleResolvedFile` will graft resolutions computed for the *old* hunk set onto the *new* file content, producing content that does not correspond to either side's actual latest markers.

### Impact Explanation
The corrupted result is written to disk and immediately staged (`git add`): [6](#0-5) 

This is a silent corruption of what the user is about to commit/push, without the user necessarily re-reviewing content that no longer matches the diff they approved in the result dialog, since the splice happens by hunk order rather than verifying the base content is unchanged.

### Likelihood Explanation
The window is real (round-trips explicitly tracked past 120 seconds) and the multi-commit-operation state machine allows navigating away (e.g., to `ConfirmAbort`) and back while a resolution result is pending, per the code's own comments: [7](#0-6) 
However, triggering an actual content mismatch generally requires the user (or an external process) to alter the conflicted working directory while the AI request is in flight — a narrower condition than a purely remote-attacker-controlled path, so likelihood is moderate rather than high.

### Recommendation
Store a hash/fingerprint of `rawContent` alongside each `IFileResolution`, and at apply time re-read the current on-disk content and compare against that fingerprint (in addition to the existing "already resolved" check) before splicing. If content has drifted, treat the file as stale and require re-resolution or fall back to manual resolution for that file instead of writing a mismatched splice.

### Proof of Concept
Not independently reproduced against a running build — this is a static-analysis-based finding derived from the code paths cited above (`buildConflictContext` snapshot → async model round-trip → ordinal splice in `reassembleResolvedFile`/`reassembleResolutions` → write in `_applyCopilotConflictResolutions` with only an "already fully resolved" guard).

---

**Caveat:** This finding involves the working directory being mutated by the same local user (or a concurrent Desktop-driven git operation) during the AI round-trip, rather than a single unambiguous "attacker fully external to the local session" primitive as crisply as the FeeCollector's keeper economics. If you need a strictly network/attacker-controlled-content analog with no dependency on local timing, I did not find one with equally strong file/function support in the areas searched (push/remote handling, account token refresh, avatar token caching, repo rules parsing) — those all had explicit staleness guards already in place.

 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved

 * resolved sections.

 *

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
