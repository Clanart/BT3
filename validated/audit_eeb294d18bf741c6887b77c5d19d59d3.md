### Title
Auction bid submission API can hang RPC threads forever via unbounded blocking channel send in `BidPool.AddBid` - (File: kaiax/auction/impl/bid_pool.go)

### Summary
The `auction_submitBid` RPC endpoint (documented as a callable API for any auction bidder/searcher) synchronously calls `BidPool.AddBid`, which performs an unconditional, unbuffered-style blocking send (`bp.newBidCh <- bid`) with no `select`/`default`/timeout guard. If the consumer goroutine (`handleNewBid`) stalls — which happens whenever `event.Feed.Send` blocks on a slow or non-draining subscriber — the bounded channel (`bidChSize = 2048`) fills up and every subsequent `AddBid` call (and therefore every `auction_submitBid` RPC call) blocks indefinitely. This lets an unprivileged bidder-driven code path exhaust RPC-handling goroutines and permanently stall auction bid processing, a resource-release/handling failure analogous to CWE-404.

### Finding Description
`BidPool.AddBid` is the function invoked directly by the RPC-exposed `AuctionAPI.SubmitBid`: [1](#0-0) 

`AddBid` ends with an unconditional channel send that has no bound-check, `select default`, or timeout: [2](#0-1) 

The consumer of `newBidCh` is `handleNewBid`, which forwards every bid to `bp.newBidFeed.Send(bid)`: [3](#0-2) 

`event.Feed.Send` (standard go-ethereum-style feed semantics used throughout this codebase) blocks until *all* current subscribers have received the value or been dropped/unsubscribed. `SubscribeNewBid` allows any caller to register a sink without any requirement that the sink is drained promptly: [4](#0-3) 

If a subscriber's receiving channel is not actively drained (e.g., a subscriber goroutine dies, panics, or the receiver end is momentarily busy), `newBidFeed.Send` blocks, which blocks `handleNewBid`'s consumption of `newBidCh`. Because `newBidCh` has a fixed capacity of `bidChSize = 2048`: [5](#0-4) 

once 2048 in-flight bids have been queued without being drained, every subsequent call to `AddBid` — and therefore every `auction_submitBid` RPC call from any auction bidder — blocks forever on `bp.newBidCh <- bid`, holding the calling RPC goroutine hostage.

Notably, the P2P ingress path (`HandleBid`) already recognizes this exact hazard and protects itself with a non-blocking `select`/`default` drop-if-full pattern, with an explicit code comment and dedicated regression test proving the intent: [6](#0-5) [7](#0-6) 

The direct-RPC path via `AddBid`/`newBidCh`, however, was never given the same treatment — it lacks the bounded/non-blocking guard that the P2P path has, meaning the resource protection that was correctly designed for one ingress point is missing for the other.

### Impact Explanation
Any external caller of the documented `auction_submitBid` API (an "auction bidder" per the module's own README, which shows a bare curl example with no special authorization) can eventually cause `newBidCh` to saturate (2048 buffered bids, easily reachable by an automated bidder or if the feed subscriber momentarily stalls), after which every future `auction_submitBid` call — from that bidder or any other legitimate bidder — blocks the calling RPC goroutine indefinitely. This is a Denial of Service against the auction subsystem: RPC worker exhaustion prevents legitimate bidders from having their bids accepted, and the accumulated blocked goroutines are never released (the defining trait of CWE-404, Improper Resource Shutdown or Release) unless the node is restarted.

### Likelihood Explanation
`auction_submitBid` is explicitly published as an externally callable JSON-RPC API for searchers/bidders (see README curl example and `web3ext.go` binding), requiring only a validly signed bid (no special privilege). Filling a 2048-slot channel is trivial for an automated bidder submitting sequential valid bids faster than the (single, potentially blocked) `handleNewBid`/feed-consumer can drain them, especially since nothing guarantees a `SubscribeNewBid` consumer stays alive and actively draining. No consensus, staking, or governance privilege is required to trigger it.

### Recommendation
Change `bp.newBidCh <- bid` in `AddBid` to a non-blocking send with a `select`/`default` (mirroring `HandleBid`'s pattern) or a bounded timeout, and drop/queue-reject the bid with an error returned to the RPC caller instead of blocking the calling goroutine. Additionally, consider making `newBidFeed.Send` non-blocking or bounding the number of concurrent subscribers/consumption latency so a stalled subscriber cannot back-pressure the entire bid ingestion pipeline.

### Proof of Concept
1. Start a Kaia CN node with the auction module enabled and `auction_submitBid` reachable via RPC.
2. Subscribe to `SubscribeNewBid`/`newBidFeed` with a consumer that never reads from its channel (or simply do not create a fast draining reader — the module itself does not guarantee prompt draining internally).
3. As an unprivileged bidder, submit `bidChSize` (2048) valid, distinct bids in rapid succession via `auction_submitBid`. Each call to `AddBid` succeeds and pushes into `newBidCh` up to capacity because `handleNewBid`→`newBidFeed.Send` is stalled behind the non-draining subscriber.
4. Submit one more `auction_submitBid` call: the RPC goroutine now blocks forever inside `bp.newBidCh <- bid` in `AddBid`, since the channel is full and never drained.
5. Repeat step 4 concurrently from multiple callers: every call hangs, exhausting RPC worker capacity and blocking the auction pipeline for all legitimate bidders, with no way to recover short of a node restart.

func (api *AuctionAPI) SubmitBid(ctx context.Context, bidInput BidInput) RPCOutput {
	numBidRequestCounter.Inc(1)
	if api.a.IsDisabled() {
		return makeRPCOutput(EMPTY_HASH, auction.ErrAuctionDisabled)
	}

	//  1. directly send target transaction
	targetTx, errTxDecode := toTx(bidInput.TargetTxRaw)
	if errTxDecode != nil {
		return makeRPCOutput(EMPTY_HASH, errTxDecode)
	}
	if targetTx.Hash() != bidInput.TargetTxHash {
		return makeRPCOutput(EMPTY_HASH, auction.ErrInvalidTargetTxHash)
	}
	errTargetTxSend := api.a.Backend.SendTx(ctx, targetTx)
	// ignore known transaction related errors against target tx validation
	if errTargetTxSend != nil && !(strings.HasPrefix(errTargetTxSend.Error(), "known transaction:") || errors.Is(errTargetTxSend, gasless_impl.ErrUnableToAddKnownBundleTx)) {
		return makeRPCOutput(EMPTY_HASH, errTargetTxSend)
	}

	// 2. add bid
	bid := ToBid(bidInput)
	bidHash, errValidateBid := api.a.bidPool.AddBid(bid)
	return makeRPCOutput(bidHash, errValidateBid)
}

// AddBid adds a bid to the bid pool.
// Required mutex is locked in each function.
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) HandleBid(peerID string, bid *auction.Bid) {
	if atomic.LoadUint32(&bp.running) == 0 || bid == nil {
		return
	}

	// Check rate limit for this peer
	if !bp.checkRateLimit(peerID) {
		logger.Trace("Rate limit exceeded for peer", "peerID", peerID)
		return
	}

	select {
	case bp.bidMsgCh <- bid:
	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}

func (bp *BidPool) handleNewBid() {
	defer bp.wg.Done()

	for {
		select {
		case bid, ok := <-bp.newBidCh:
			if !ok {
				return
			}
			bp.newBidFeed.Send(bid)
		}
	}
}
