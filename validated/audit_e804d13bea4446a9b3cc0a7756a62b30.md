### Title
`ReceivedOutput::read` deserializes `offset` and `script_pubkey` independently, breaking the scan-time invariant that binds them — recovered key is attacker-controlled - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The DNS-TOCTOU class is "validate X, then act on an independently re-resolved Y with no binding between them". In Serai the same shape exists in the Bitcoin wallet: the invariant "this `offset` corresponds to this output's `script_pubkey`" is established only once, inside `Scanner::scan_transaction`, and is then serialized away. `ReceivedOutput::read` accepts the `offset` scalar and the `TxOut` as two independent, untrusted fields and never re-verifies that `p2tr_script_buf(key + offset·G) == output.script_pubkey`. Downstream, `Output::key()` recomputes the owning group key as `scriptkey − offset·G`, so a forged `ReceivedOutput` silently resolves to a different key than the one the script actually pays to — a validate-time/act-time mismatch with no pinning, exactly as in the advisory.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>`, mapping each registered tweaked-key script to the offset that produced it. When scanning, `scan_transaction` looks up `output.script_pubkey` in that map and attaches the *map's* offset, so the pair `(offset, script_pubkey)` is guaranteed consistent at scan time (`networks/bitcoin/src/wallet/mod.rs:199-214`).

`ReceivedOutput::serialize`/`write` emit `offset` and the output as raw fields (`mod.rs:137-141`), and `read` (`mod.rs:122-133`) performs only `Secp256k1::read_F` for the offset and `TxOut::consensus_decode` for the output — canonical scalar parsing, but no check that the offset actually derives the script's key. The round-trip is even asserted in tests (`networks/bitcoin/tests/wallet.rs:252`), confirming serialized `ReceivedOutput`s are a real interchange format, not an internal-only structure.

The consumer then re-derives the owning key from both halves independently: `OutputTrait::key()` parses the x-only key out of `script_pubkey` and subtracts `GENERATOR * output.offset()` (`processor/src/networks/bitcoin.rs:112-122`). With a scan-produced output this returns the true group key; with attacker-crafted bytes, the offset is arbitrary and `key()` returns `scriptkey − o'·G` — an arbitrary point entirely under the attacker's control. Like the DNS case, the "resolution" performed at use time (key recovery) operates on untrusted input rather than the value that was validated.

### Impact Explanation
Any component that ingests a serialized `ReceivedOutput`/`Output` (untrusted bytes explicitly within scope) and relies on `key()`, the offset, or the script for attribution or signing can be made to associate an output with the wrong key or wrong offset. Concretely: an offset inconsistent with the script_pubkey produces funds that are reported as received under a key the validator set does not hold, or that are spent using `offset` applied to the real group key while the actual script key is different — i.e., funds reported received that are not spendable by the reported key, or spendable by a different key than attributed. This is the spendability/attribution analog of the SSRF bypass: the security invariant checked at discovery time is not enforced at consumption time.

### Likelihood Explanation
Reachability requires attacker-influenced serialized `ReceivedOutput` bytes reaching `ReceivedOutput::read` / `Output::read`, e.g., outputs relayed between processors or recovered from stored/forwarded data rather than produced by a local `Scanner`. The primitive itself is fully attacker-controlled (`offset` and `TxOut` are arbitrary fields), and no defence exists in the read path — canonicality of the scalar is checked, consistency is not. Severity is Medium: the flaw is deterministic once reachable, but its concrete impact depends on how the consumer uses `key()`/`offset()`, which I could not fully trace within the iteration budget.

### Recommendation
Either (a) pin the validated pair like the advisory's suggested fix — recompute `p2tr_script_buf(key + offset·G)` at read/use time and reject mismatches, or (b) store the group `key` inside `ReceivedOutput` and verify `key + offset·G` is even-Y and matches `script_pubkey` in `ReceivedOutput::read`. At minimum, `Output::key()` should assert consistency instead of silently returning `scriptkey − offset·G` for unverified input.

### Proof of Concept
```rust
// Construct a ReceivedOutput whose offset does not derive its script_pubkey.
// Take a legitimately scanned output (offset o, script for key + o*G).
let mut legit = scanner.scan_transaction(&tx).pop().unwrap();

// Craft a malicious one: keep the script, swap in an arbitrary offset.
let evil_offset = Scalar::random(&mut OsRng); // != legit.offset()
let mut buf = vec![];
buf.extend(evil_offset.to_bytes());           // attacker-chosen offset
buf.extend(bitcoin::consensus::serialize(legit.output()));
buf.extend(bitcoin::consensus::serialize(legit.outpoint()));

// Parsing succeeds: only canonicality of the scalar is checked.
let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();

// Output::key() now returns scriptkey - evil_offset*G, a wrong,
// attacker-influenced group key; the output is attributed to a key
// that cannot spend it (or vice versa).
//   key() = script_pubkey_key - forged.offset()*G
//        != real group key
```
