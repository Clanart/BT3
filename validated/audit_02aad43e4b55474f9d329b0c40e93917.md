Based on the codebase, I found a legitimate analog to the H-01 pattern: an invariant ("the line index a user selected still refers to the same logical content") that is assumed to hold but is never actually verified, allowing attacker-influenced content to be silently included in a commit.

### Title
Stale, content-blind line-index selection state lets a changed working-tree diff cause silent corruption of partial commits - (File: `app/src/lib/patch-formatter.ts`, `app/src/models/diff/diff-selection.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
Just as `RWIPStaking` always minted stRWIP 1:1 without checking the real, current backing ratio, GitHub Desktop's partial-commit "stage this line" feature tracks selection purely by **numeric line index**, with no notion of what content that index actually represents. `DiffSelection` explicitly documents this: "it has no notion of how many lines exist or what it is that is being selected." [1](#0-0)  When the working-directory diff is recomputed (e.g. after a fetch/merge/checkout touches the same file) the app only prunes indices that are no longer selectable — it never re-verifies that the content at a retained index is the same content the user actually reviewed and selected.

### Finding Description
`updateChangesWorkingDirectoryDiff` reloads the diff and explicitly acknowledges — but does not fix — this gap:

> "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." [2](#0-1) 

This recomputes only *which indices are selectable*, not whether the semantic content at a still-selectable index has changed.

At actual commit time, `applyPatchToIndex` fetches a **fresh** diff independent from whatever diff the UI last rendered to the user: [3](#0-2) 

That fresh diff is fed into `formatPatch`, which walks the new hunks and blindly asks the old `file.selection` object, keyed only by absolute line index, whether each index `isSelected`: [4](#0-3) 

`DiffSelection.isSelected`/`isSelectable` never compare line text — they only consult `divergingLines`/`selectableLines` sets of bare integers: [5](#0-4) 

So the invariant the code silently relies on is: *"index N in the diff currently shown to the user == index N in the diff used to build the patch."* Nothing enforces that. If the working tree changes between when the user picks lines to stage and when `createCommit`/`applyPatchToIndex` runs (e.g. the same file is also touched by a `pull`/`merge` bringing in attacker-controlled content from a remote, or Desktop's periodic file-watcher-driven `updateChangesWorkingDirectoryDiff` reloads the diff while a partial selection is pending), a previously "safe" selected index can now point at attacker-introduced lines. Those lines get silently included in the patch applied to the index and end up in the commit — with no re-confirmation from the user and no diff-content check anywhere in the pipeline. `formatPatchToDiscardChanges` has the identical, unguarded pattern for the discard-lines flow. [6](#0-5) 

### Impact Explanation
This allows a remote/repo-supplied change (fetched or merged content, i.e. attacker-controlled repository state) to be committed and potentially pushed under the victim's identity without the victim ever seeing or approving that content — "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories. Because commits are cryptographically signed/attributed to the user and pushed upstream, this can be used to smuggle malicious code changes into a project via a legitimate contributor's commit, bypassing code review expectations that "what I selected in the diff viewer is what got committed."

### Likelihood Explanation
Medium: it requires a specific race — the working copy of the exact file with a pending partial selection must be modified (via merge/pull/checkout of attacker-influenced content) in the narrow window between the user's line selection and the commit action — but Desktop's status/diff refresh is driven by a file watcher and runs continuously in the background while the Changes view is open, so this window is realistically reachable without any unusual user steps, local access, or prior compromise.

### Recommendation
`formatPatch`/`formatPatchToDiscardChanges` should not trust bare line indices across diff reloads. Either (a) bind selection state to a content hash/fingerprint of each hunk/line so a changed hunk invalidates its selection rather than merely being marked "still selectable," or (b) recompute selection against the diff that is fetched immediately before `applyPatchToIndex`/`createCommit` runs and hard-fail (or force reconfirmation) if that diff differs from the one the selection was derived against, mirroring how the ERC-4626 fix moved from a blind fixed ratio to validating against the actual current state.

### Proof of Concept
1. Modify `file.md` locally and open it in Desktop's Changes view; deselect an unwanted hunk and select only a "safe" hunk for a partial commit (`DiffSelectionType.Partial`, selection built against diff D1).
2. Before clicking "Commit," trigger a working-tree change to the same file at the same line offsets (e.g. `git merge`/`git pull` bringing in remote changes, or an external tool/editor rewriting the file) so the new diff D2 has different content at the same absolute indices that were previously selected.
3. Click "Commit." `applyPatchToIndex` calls `getWorkingDirectoryDiff` and gets D2, but `formatPatch` still consults the old `DiffSelection` object (built from D1) via bare integer indices — `hunk.lines.forEach(... file.selection.isSelected(absoluteIndex))` in `app/src/lib/patch-formatter.ts` lines 143-161.
4. The resulting commit silently contains the attacker/merge-introduced content at those indices instead of (or in addition to) what the user visually selected in D1, with no warning shown.
