Confirmed: `ShopifyApp::AppProxyVerification#query_string_valid?` at [1](#0-0)  only verifies the HMAC signature matches the query parameters — it never checks that the `timestamp` param (which Shopify includes precisely to let apps detect stale/replayed requests) is recent. This is the same bug class as the Aave report: data whose integrity is verified but whose *freshness* is never checked, so an old but validly-signed artifact is accepted indefinitely.

### Title
App Proxy signature verification never checks request `timestamp` for staleness, permitting indefinite replay of captured signed requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` recomputes the HMAC signature over all query parameters (including `timestamp`) and compares it to the `signature` parameter, but it never validates that `timestamp` is within an acceptable window of the current time. Because the signature is a deterministic function of fixed parameter values and the shared secret, any request that was ever validly signed by Shopify's app-proxy infrastructure remains permanently valid and can be replayed by anyone who has observed it (e.g., via browser history, referrer leakage, logs, proxies, or a shared/forwarded link), even months or years later.

### Finding Description
When a storefront hits an app's App Proxy URL, Shopify appends a `signature` query parameter computed via HMAC-SHA256 over the sorted set of query parameters (including a `timestamp`), using the app's shared secret. `ShopifyApp::AppProxyVerification` is the library mixin apps are told to include on App Proxy controllers to validate these requests: [2](#0-1) 

The `verify_proxy_request` before_action calls `query_string_valid?`, which:
1. Parses the query string.
2. Extracts and removes `signature`.
3. Recomputes the HMAC over the remaining params and compares it to the extracted signature.

At no point is the `timestamp` parameter (which is present in every app-proxy request, as shown in the test fixtures) compared against `Time.now` to reject requests older than some threshold. Compare this to the AaveOracle bug class: the oracle contract verifies a `latestAnswer()` value came from a legitimate Pyth price feed but never checks `publishTime`/staleness, so it can accept arbitrarily old data as "current." Here, `AppProxyVerification` verifies a request's HMAC was legitimately produced by Shopify but never checks the accompanying `timestamp`, so it can accept arbitrarily old requests as "current."

The engine documentation confirms this is the officially recommended (and only) verification mechanism, with no mention of a staleness check: [3](#0-2) 

The generated `AppProxyController` template relies solely on this mixin: [4](#0-3) 

### Impact Explanation
Because signature validity never expires, any captured legitimate app-proxy request (leaked via logs, browser history/cache, HTTP referrer headers, shared screenshots/links, proxy/CDN logs, or network capture) can be replayed by an anonymous/unrelated party at any point in the future and will still pass verification with a `200`/success response rather than being rejected. If the app-proxy endpoint performs any state-changing or shop-context-sensitive action (not just read-only rendering, which is what the stock generator does, but which app developers are explicitly encouraged to extend per `docs/shopify_app/engine.md`), this becomes a genuine replay-based state-change/CSRF-equivalent vector against a specific shop's storefront-triggered actions, since the shop domain itself is embedded and authenticated by the (never-expiring) signature.

### Likelihood Explanation
Exploitation requires an attacker to first obtain one previously issued, legitimately signed app-proxy query string (this is inherent to the report's request-forgery framing: "accepted forged/replayed signed request"). App proxy URLs are storefront-facing and routinely appear in browser history, HTTP Referer headers sent to third-party resources loaded on the storefront page, and various logging middlewares, making capture plausible over time. Once captured, replay requires no further secrets or session and works indefinitely, which is a materially different and more severe risk profile than a normal signed request with a short validity window.

### Recommendation
Add a staleness check in `query_string_valid?`/`verify_proxy_request`: parse `timestamp` from the query hash and reject the request (return `false`/`head(:forbidden)`) if `Time.now.to_i - timestamp.to_i` exceeds a small threshold (e.g., a few minutes), mirroring the fix suggested in the reference report (checking `publishTime`/timestamp freshness in addition to signature integrity).

### Proof of Concept
1. A merchant's storefront loads a page that triggers a request to the app's App Proxy endpoint, e.g. `GET /apps/my-app?shop=some-shop.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-hmac>`.
2. This URL (with its valid, never-expiring signature) is captured by an unrelated party (e.g., via a shared browser history entry, a referrer leak to a third-party analytics/ad script embedded on the storefront, or a proxy/CDN access log).
3. At any later time — verified here using the existing test fixture values from `test/shopify_app/controller_concerns/app_proxy_verification_test.rb` lines 61-72, which use `timestamp=1466106083` (an epoch timestamp from 2016) and its correspondingly valid signature — replay the exact same query string against the live app-proxy endpoint.
4. `query_string_valid?` recomputes the same HMAC over the same parameters and it matches, so `verify_proxy_request` allows the request through and the controller action executes, despite the request being years old: [5](#0-4)

# frozen_string_literal: true

module ShopifyApp
  module AppProxyVerification
    extend ActiveSupport::Concern
    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_proxy_request
    end

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
  end
end

## Verify HTTP requests sent via an app proxy

See [`ShopifyApp::AppProxyVerification`](/lib/shopify_app/controller_concerns/app_proxy_verification.rb).

The engine provides a mixin for verifying incoming HTTP requests sent via an App Proxy. Any controller that `include`s `ShopifyApp::AppProxyVerification` will verify that each request has a valid `signature` query parameter that is calculated using the other query parameters and the app's shared secret.

### Recommended usage of `ShopifyApp::AppProxyVerification`

The App Proxy Controller Generator automatically adds the mixin to the generated app_proxy_controller.rb
Additional controllers for resources within the App_Proxy namespace, will need to include the mixin like so:

```ruby
# app/controllers/app_proxy/reviews_controller.rb
class ReviewsController < ApplicationController
  include ShopifyApp::AppProxyVerification
  # ...
end
```
