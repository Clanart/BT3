### Title
`getEndpointKind` trusts attacker-controlled `WWW-Authenticate: realm="GitHub"` response to classify a remote as GitHub, causing Desktop to solicit a real GitHub OAuth token and hand it to the attacker's host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The credential-helper trampoline decides whether a Git remote should be treated as a GitHub/GHE endpoint (and thus prompt for GitHub OAuth sign-in) partly by inspecting the `WWW-Authenticate` header value that the *remote server* returned to Git, which Git forwards verbatim to the credential helper as `wwwauth[]` entries. If that header contains `realm="GitHub"`, Desktop unconditionally classifies the host as `'enterprise'` — even though the request went to an attacker-controlled URL — and will subsequently mint/reuse a real GitHub credential for that host.

### Finding Description
In `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:137-179`), the classification logic is: [1](#0-0) 

This `wwwauth[...]` value is not attested by GitHub in any cryptographic sense — it's simply an HTTP response header echoed by whatever server is on the other end of the git remote/proxy connection, and Git itself hands it to the credential helper without validation: [2](#0-1) 

`getCredential` uses the result of `getEndpointKind` to decide whether to trigger the GitHub sign-in popup for a *previously-unauthenticated* endpoint: [3](#0-2) 

Because `endpointKind !== 'generic'` is now true purely from the spoofed header, and there is no stored account yet for `apiEndpoint` (an attacker's arbitrary host will never match a real stored GitHub account), the code calls `ui.promptForGitHubSignIn(endpoint)`, which is wired straight into the real OAuth flow via `dispatcher.beginDotComSignIn`/`beginEnterpriseSignIn`: [4](#0-3) 

Once the user completes the (legitimate) GitHub OAuth handshake, `credWithAccount` attaches the resulting `login`/`token` to the credential map, which is then formatted and handed back to Git as the Basic-Auth credential for the connection: [5](#0-4) [6](#0-5) 

Git will then send that credential (a real GitHub OAuth token) over HTTPS Basic auth to the original request URL — which is the attacker-controlled remote/proxy, not github.com. This is the exact bug-class analog to the smart-contract report: a value that should only be trusted when it truly originates from the privileged party (GitHub) is instead derived from an untrusted party's self-reported claim (`realm="GitHub"` in a response the attacker fully controls), and the downstream authorization/credential-issuance logic accepts it without an independent, authoritative check equivalent to `isGitHubHost()` (a DNS/HTTPS-based check that is only used as a *last-resort* fallback, after the spoofable header check already returns early).

The existing guards do not stop this path because:
- `isDotCom(endpoint)` / `isGHE(endpoint)` only match known GitHub domains, and the attacker's host won't match — but the code doesn't stop there; it falls through to the attacker-controlled header parsing before ever consulting `isGitHubHost(endpoint)`, which performs a real network-based determination.
- The `wwwauth[...]` branch returns immediately (`return 'enterprise'`) without any corroborating check, so it fully short-circuits the more trustworthy `isGitHubHost` fallback at line 178.

### Impact Explanation
An attacker who controls a git remote/proxy (e.g. a malicious HTTP git server the user is cloning/fetching from, or a MITM/compromised proxy in the request path) can respond to Git's authentication probe with `WWW-Authenticate: Basic realm="GitHub"`. This causes GitHub Desktop to launch its real GitHub/GHE OAuth sign-in dialog for that remote, and — since the resulting Account's token is merged into the credential returned to Git for that same connection — the user's freshly minted, valid GitHub OAuth token gets sent via HTTPS Basic Auth to the attacker's server. This matches the "unauthorized OAuth" / "credential and token exfiltration" impact class: full account tokens can be exfiltrated to a party the user never intended to authenticate to, without any local access or pre-existing malware required — only a normal `git clone`/`fetch` against an attacker-controlled remote.

### Likelihood Explanation
The trigger requires nothing beyond a user adding/cloning from an attacker-controlled or compromised HTTP(S) git remote (including any MITM'd proxy on the network path) — a scenario explicitly listed as an accepted attacker-control surface in this exercise. No social engineering beyond "the user has this remote configured," no elevated privileges, and no separate leaked secret are needed. The only precondition is that the user does not already have a stored account matching that host (the common case for a first-time/never-before-seen malicious remote), which is exactly when the vulnerable code path executes.

### Recommendation
Do not classify a host as GitHub/GHE ("enterprise") based solely on the `WWW-Authenticate` realm string reported by the remote itself. Either:
- Remove the `wwwauth[...]` fast-path entirely and always fall back to the authoritative `isGitHubHost(endpoint)` network/TLS-based check, or
- Use the `wwwauth` value only as a *negative*/generic-host signal (as already done for GitLab/Gitea/Bitbucket), never as a positive trigger that causes Desktop to solicit and forward a genuine GitHub credential to that host, and always corroborate a positive "GitHub" claim with `isGitHubHost()` before prompting sign-in or reusing account tokens for that endpoint.

### Proof of Concept
1. Stand up a plain HTTP(S) git server (e.g. any `git http-backend` instance) at `https://evil.example.com/repo.git` that, on receiving Git's credential probe request, returns `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone/add `https://evil.example.com/repo.git` (no prior account stored for `evil.example.com`).
3. When Desktop's credential-helper trampoline runs `getCredential`, `getEndpointKind` reads the forwarded `wwwauth[]=Basic realm="GitHub"` value at `trampoline-credential-helper.ts:157-165` and returns `'enterprise'` without contacting `evil.example.com` or github.com for verification.
4. `getCredential` sees no stored account for `evil.example.com` and calls `ui.promptForGitHubSignIn(endpoint)` (`trampoline-credential-helper.ts:109-125`, `trampoline-ui-helper.ts:80-104`), which is wired to the real GitHub OAuth device/browser flow.
5. The user, believing they are authenticating a legitimate "Enterprise"-style prompt, completes GitHub OAuth sign-in.
6. `credWithAccount` merges the resulting real GitHub `login`/`token` into the credential map returned to Git, which sends it as HTTP Basic Auth to `evil.example.com` — exfiltrating the token to the attacker.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

import { exec as git } from 'dugite'

export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
