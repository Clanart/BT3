### Title
Zero-amount input tokens escrowed via the `placeOrder` predispatch path permanently brick `withdraw()` for the whole order - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` has two code paths for escrowing `order.inputs`: the plain-transfer path explicitly rejects a zero-amount input, but the predispatch (call-dispatcher) path does not. An order creator can therefore include a zero-amount input token in an order routed through the predispatch branch. That token is recorded in `_orders[commitment][token]` with value `0`. When a solver later tries to redeem the escrow via `withdraw()`, the function iterates every token in the order and reverts with `UnknownOrder` as soon as it hits a token whose `_orders[commitment][token]` is `0`. Because `withdraw()` is atomic across the whole token list, this single zero-amount entry permanently blocks redemption of *all* escrowed assets for that order.

### Finding Description
In the non-predispatch escrow branch, a zero amount is explicitly rejected: [1](#0-0) 

But in the predispatch branch, no such check exists before the escrow bookkeeping line: [2](#0-1) 

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus the protocol fee: [3](#0-2) 

If `order.inputs[i].amount == 0`, `reducedInputs[i].amount` is also `0`, and `_orders[commitment][token] += 0` leaves the mapping entry at its default value of `0`, while the token address is nonetheless part of the order's committed input set (used to build `commitment` via `keccak256(abi.encode(order))`).

The only guard at the top of `placeOrder` is on the array length, not per-element amounts: [4](#0-3) 

Later, `withdraw()` walks every token supplied in `body.tokens` (which mirrors the order's committed inputs) and treats a zero-valued `_orders` entry as proof the order/token pair is unknown, reverting the entire call: [5](#0-4) 

Since `withdraw()` has no per-token try/catch or removal-and-continue logic, and `_orders[commitment][token]` can never be topped up outside `placeOrder`'s escrow bookkeeping, once a zero-valued token entry exists for a commitment, `withdraw()` for that commitment reverts unconditionally, forever, for both the `RedeemEscrow` (fill payout) and `RefundEscrow` (cancellation) flows — this is the same class of bug as H-4: a value that can only ever be read as `0 == false-negative "unknown"` gets permanently baked into a settlement path with no recovery mechanism.

### Impact Explanation
This is a permanent loss/lock of funds in the bridge's intent-settlement mechanism: any legitimate, correctly-funded input tokens included in the same order as the crafted zero-amount input become permanently unredeemable, for both the solver (on a successful fill) and the original user (on a refund/cancellation). It matches the required impact categories directly: "stealing or loss of funds" and "transaction manipulation / logic attack" against a production contract entry point (`placeOrder`), reachable without any relayer, prover, or admin privilege — any ordinary user can craft such an order.

### Likelihood Explanation
High feasibility: `placeOrder` is a fully public, unprivileged entry point, and choosing the predispatch branch (`order.predispatch.call.length > 0 && order.predispatch.assets.length > 0`) together with an `order.inputs[i].amount == 0` entry is entirely within an ordinary caller's control — there is no on-chain validation preventing it. No race condition, no relayer collusion, and no proof forgery is needed; the attacker only needs to submit a single crafted transaction.

### Recommendation
Add the same `if (order.inputs[i].amount == 0) revert InvalidInput();` check to the predispatch escrow loop (mirroring the non-predispatch branch), and/or change `withdraw()`'s unknown-order check to not conflate "amount is legitimately zero" with "order/token pair was never escrowed" (e.g., track presence with a separate boolean/set rather than relying on `amount == 0`), and skip zero-value ERC20 transfers instead of reverting the whole withdrawal.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.predispatch.call.length > 0` and `order.predispatch.assets.length > 0` (satisfying the predispatch branch), and `order.inputs` containing two entries: token A with a nonzero amount and token B with `amount = 0`.
2. `_orders[commitment][tokenA] = reducedAmountA` (nonzero), `_orders[commitment][tokenB] = 0` (line 435).
3. A solver fills the order on the destination chain and later a `RedeemEscrow` proof-driven call reaches `withdraw(body, false)` on the source chain, with `body.tokens` including both `tokenA` and `tokenB` (mirroring the committed order).
4. The loop in `withdraw()` reaches `tokenB`, evaluates `_orders[commitment][tokenB] == 0`, and reverts with `UnknownOrder()` (line 691), rolling back the entire transaction including the transfer of `tokenA` that would otherwise have succeeded.
5. Every subsequent attempt to call `withdraw()` for this `commitment` reverts identically — the escrowed `tokenA` funds are permanently locked in the contract, and the solver who legitimately filled the order is never paid.
