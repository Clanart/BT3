## Analog Confirmed

### Title
Unsanitized GitHub profile name injected into `Co-Authored-By` trailer allows attacker-controlled data in a signed commit - (File: `app/src/ui/lib/author-input/author-input.tsx`, `app/src/ui/changes/commit-message.tsx`, `app/src/lib/git/interpret-trailers.ts`)

### Summary
This mirrors the ConseilJS report's core defect: an attacker-controlled string that is documented/expected to be a constrained token (a smart-contract entrypoint / here, a person's display name) is embedded verbatim into a structured, machine-parsed field without length/character validation, letting the attacker smuggle additional structured content into data the user will sign/commit.

### Finding Description
When a user adds a co-author via `@mention` autocomplete, `authorFromUserHit` builds a `KnownAuthor` directly from the GitHub API's `name` field with no sanitization: [1](#0-0) 

That `name` (fully attacker-controlled — any GitHub user can set an arbitrary display name, including newlines/control characters, via the API or profile settings; the local API model `apiUser.name` is fetched as-is) flows into `getCoAuthorTrailers`, which builds a trailer value by naive string interpolation: [2](#0-1) 

This raw string is then passed to `git interpret-trailers --trailer token=value` as a single argv value: [3](#0-2) 

Crucially, there is a name-validation function, `gitAuthorNameIsValid`, that rejects git "crud" characters — but it is only used in `preferences.tsx` and `repository-settings.tsx` for the local `user.name` config field, never for co-author names sourced from the GitHub API or the autocompletion path: [4](#0-3) 

Because `--trailer` values containing embedded newlines are still git-legal argv content, a name like `Foo\n\nSigned-off-by: Attacker <a@evil.com>` (or a blank line followed by attacker text) can cause `git interpret-trailers` to fold the malicious text into the finished commit message body as if it were separate, legitimately-formatted lines/trailers once merged into the message via `formatCommitMessage`: [5](#0-4) 

The user only sees the co-author "chip" UI in `AuthorInput`, not the raw underlying string that is spliced into the commit message the user is about to author/sign — exactly analogous to the wallet user only seeing "Invoke tab" text while extra operations get appended to the signed payload.

### Impact Explanation
A malicious GitHub user (or GHES account) who is added as a co-author (a routine, low-friction action — the victim just needs to `@mention` them in a commit) can inject additional trailer-like lines or content into the commit message that GitHub Desktop then commits and (typically) pushes on the user's behalf. This can be used to forge/spoof additional attribution trailers (e.g., fake `Signed-off-by`, additional bogus `Co-Authored-By` entries, or repo-rule-bypassing text) inside a commit that the victim believes only contains the co-author they intended, silently corrupting what the user commits — one of the explicitly valid impact categories (silent corruption of what the user commits or pushes), driven entirely by attacker-controlled data (a GitHub API object: the user's profile name) with no local/physical access or social engineering required beyond a normal @mention.

### Likelihood Explanation
Likelihood is moderate-to-high: setting an arbitrary display name (including special characters) is a normal, unprivileged GitHub account action, and co-authoring via `@mention` autocomplete is a core, frequently-used Desktop feature. The only precondition is that the victim mentions the attacker as a co-author, which the attacker can encourage through normal collaboration (e.g., pairing, contribution guidelines suggesting co-authorship). No existing validation stops this path — `gitAuthorNameIsValid` exists in the codebase but is not wired into the co-author/API-derived name path at all.

### Recommendation
- **Short term:** Apply `gitAuthorNameIsValid` (or an equivalent check rejecting newlines/control characters and other "crud" characters) to `IMentionableUser.name`/`apiUser.name` before it is used to construct `KnownAuthor.name` in `authorFromUserHit` (`app/src/ui/lib/author-input/author-input.tsx`), and again defensively in `getCoAuthorTrailers` (`app/src/ui/changes/commit-message.tsx`) before building the trailer value.
- **Long term:** Treat all data retrieved from the GitHub API (names, logins, emails) as untrusted input everywhere it is later serialized into git plumbing commands or commit content; centralize sanitization for identity fields (name/email) in one place rather than relying on ad hoc validation used only for local `user.name` settings.

### Proof of Concept
This is a data-flow / logic finding based on static code review; it was not executed against a live GitHub account. Conceptually:
1. Attacker sets their GitHub display name to a value containing embedded newlines and fake trailer syntax, e.g. `Foo\n\nSigned-off-by: Attacker <a@evil.com>` (allowed since the API model imposes no additional constraint captured in this codebase — `apiUser.name` is used as-is in `github-user-store.ts`).
2. Victim, in GitHub Desktop, `@mentions` the attacker as a co-author on a commit.
3. `authorFromUserHit` stores the raw multi-line name as `KnownAuthor.name`.
4. On commit, `getCoAuthorTrailers` produces `{ token: 'Co-Authored-By', value: 'Foo\n\nSigned-off-by: Attacker <a@evil.com> <victim-email>' }`.
5. `formatCommitMessage` → `mergeTrailers` passes this as a single `--trailer` argv value to `git interpret-trailers`; depending on git's line-folding/unfolding behavior, the embedded `\n\n` and trailer-like text can end up rendered as extra lines/trailers in the final commit message that the victim commits and pushes, without ever having typed or reviewed that content themselves. [6](#0-5)

```typescript
export async function mergeTrailers(
  repository: Repository,
  commitMessage: string,
  trailers: ReadonlyArray<ITrailer>,
  unfold: boolean = false
) {
  const args = ['interpret-trailers']

  // See https://github.com/git/git/blob/ebf3c04b262aa/Documentation/git-interpret-trailers.txt#L129-L132
  args.push('--no-divider')

  if (unfold) {
    args.push('--unfold')
  }

  for (const trailer of trailers) {
    args.push('--trailer', `${trailer.token}=${trailer.value}`)
  }

  const result = await git(args, repository.path, 'mergeTrailers', {
    stdin: commitMessage,
  })

  return result.stdout
}
```

```typescript
// Git forbids names consisting entirely of these characters
// (what Git calls crud) but as long as there's at least one
// valid character in the name it'll strip the crud and be happy.
// See https://github.com/git/git/blob/e629a7d28a405e/ident.c#L191-L203
const crudCharactersRe = /^[\x00-\x20.,:;<>"\\']+$/

/**
 * Returns a value indicating whether the given `name` is a valid
 * Git author name that can be used for the `user.name` Git config
 * setting without producing an error about disallowed characters
 * at commit time.
 *
 * This logic is intended to be an exact copy of that of Git's own
 * logic, see https://github.com/git/git/blob/e629a7d28a/ident.c#L401
 *
 * Note that this method considers an empty string to be a valid
 * author name.
 */
export function gitAuthorNameIsValid(name: string): boolean {
  return !crudCharactersRe.test(name)
}
```

```typescript
export async function formatCommitMessage(
  repository: Repository,
  context: ICommitContext
) {
  const { summary, description, trailers } = context

  // Git always trim whitespace at the end of commit messages
  // so we concatenate the summary with the description, ensuring
  // that they're separated by two newlines. If we don't have a
  // description or if it consists solely of whitespace that'll
  // all get trimmed away and replaced with a single newline (since
  // all commit messages needs to end with a newline for git
  // interpret-trailers to work)
  const message = `${summary}\n\n${description || ''}\n`.replace(/\s+$/, '\n')

  return trailers !== undefined && trailers.length > 0
    ? mergeTrailers(repository, message, trailers)
    : message
}
```
