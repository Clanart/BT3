## Analysis

The report’s bug class is a **classifier confusion**: a mode-selection function decides the wrong destination for a sensitive value (assets) because its matching logic is too permissive, and that misclassification is reachable purely by controlling data the function is asked to classify (the token address).

Searching desktop--024 for an analogous "cheap heuristic decides where a sensitive value goes" pattern led to the GitHub-host classifier used to gate Desktop's credential/OAuth flow.

### Title
Overbroad substring heuristic in `isGitHubHost()` lets an attacker-controlled remote be classified as a trusted GitHub Enterprise server, triggering credential/OAuth exfiltration - (File: `app/src/lib/api.ts`)

### Summary
`isGitHubHost()` uses the regex `/(^|\.)(github)\./` against a remote's hostname to decide whether it is a genuine GitHub/GHE server, and returns `true` immediately, before ever making a network request to verify. [1](#0-0)  This classification feeds directly into `getEndpointKind()` in the Git credential-helper trampoline, which — when it decides a host is `'enterprise'` — causes Desktop to pop the trusted "Sign in to GitHub Enterprise" flow, pointed at the attacker's endpoint, instead of falling back to the generic/basic-auth prompt. [2](#0-1) 

### Finding Description
When Git needs credentials for any remote host, Desktop's credential-helper trampoline handler (`getCredential`/`getEndpointKind`) classifies the endpoint. It first checks dotcom/GHE/gist patterns and any cached account, then a `WWW-Authenticate` realm hint, and only as a last resort calls `isGitHubHost(endpoint)`: [3](#0-2) 

```
// All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
// assume that this is not a GitHub host.
if (credentialUrl.protocol !== 'https:') {
  return 'generic'
}
return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```

`isGitHubHost()` short-circuits on a hostname substring match before doing any verification request:

```
// github.example.com,
if (/(^|\.)(github)\./.test(hostname)) {
  return true
}
``` [4](#0-3) 

Any hostname containing `github.` as a label boundary — e.g. `github.attacker.io` or `sub.github.evil.com`, domains fully controlled by an attacker who registers `attacker.io`/`evil.com` — satisfies this regex over HTTPS and is classified `'enterprise'`, exactly as if it were a real GitHub Enterprise Server. This mirrors the original bug: a coarse condition (`withdrawMode` / hostname substring) picks the "trusted" branch for data the attacker fully controls (the token address / the remote hostname), causing the wrong (here: privileged) code path to run.

Once classified `'enterprise'` with no matching cached account, `getCredential()` calls the GitHub sign-in prompt rather than the generic-auth prompt: [5](#0-4) 

```
if (endpointKind !== 'generic' && !accounts.some(a => a.endpoint === apiEndpoint)) {
  ...
  const account = await ui.promptForGitHubSignIn(endpoint)
```

`promptForGitHubSignIn` then wires the sign-in UI directly to the attacker-supplied `endpoint`/`origin`, with no additional allowlist check: [6](#0-5) 

```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
```

The remote/endpoint URL used here comes straight from the Git credential request for whatever remote (or submodule remote) the user fetched/cloned — content fully controlled by the repository the user opened, matching the required attacker primitive ("a git remote/proxy response").

### Impact Explanation
The user is shown Desktop's normal "Sign in to GitHub Enterprise" dialog (a UI the user is trained to trust because Desktop itself decided the remote "is" an enterprise GitHub host), but the sign-in/OAuth exchange targets the attacker's server. Depending on the auth mode negotiated (basic auth vs. OAuth device/browser flow), this can result in the user's GitHub Enterprise username/password or a valid OAuth/PAT-equivalent token being sent to the attacker-controlled endpoint — i.e., credential/token exfiltration and unauthorized "account binding" of the attacker's endpoint as a trusted account inside Desktop, matching the explicitly valid impact categories (credential/token exfiltration, unauthorized OAuth/account binding). It does not require local/physical access, admin rights, prior malware, or unnatural steps — only that the user open/clone/fetch a repository whose remote (or a submodule remote) uses such a hostname.

### Likelihood Explanation
Triggering this requires no user click on a crafted link — simply adding/fetching from a remote (or a submodule pointing to one) whose hostname contains `github.` as a label, served over HTTPS, and returning a 401/requiring auth on some `git` operation (fetch, clone, push, LFS, submodule update). Registering such a domain (`github.<attacker-domain>` or `<sub>.github.<attacker-domain>`) is trivial and cheap for an attacker who owns any domain. The only obstacles are the earlier checks in `getEndpointKind` (cached account match, `WWW-Authenticate` realm, dotcom/GHE exact-hostname match) — none of which block an attacker who simply doesn't set those headers and uses a fresh hostname, so likelihood is meaningfully high for a socially-engineered but still fully "remote-controlled data" attack path.

### Recommendation
Do not use a bare substring/heuristic match to grant a remote host the trusted `'enterprise'`/`'GitHub'` classification that unlocks the GitHub sign-in UI. Either:
- Require the confirmatory network check (the `x-github-request-id` / `/meta` probe already implemented later in `isGitHubHost`) to run for *all* candidate hosts before returning `true`, removing the early-return substring branches, or
- Gate the "enterprise" sign-in prompt behind explicit user confirmation showing the literal hostname before any credentials/OAuth flow is initiated, so users aren't silently funneled into what looks like Desktop's own trusted GitHub Enterprise sign-in for an arbitrary attacker domain.

### Proof of Concept
1. Attacker registers `attacker.io` and creates a repository server at `https://github.attacker.io/evil/repo.git` requiring HTTP auth (401 with no `WWW-Authenticate: realm="GitHub"` header).
2. Victim clones or fetches this repository in GitHub Desktop (e.g., via `Clone repository` → “URL”, or it's added as a submodule of an otherwise innocuous repo the victim opens).
3. Git invokes the Desktop credential-helper trampoline for `https://github.attacker.io/...`. `getEndpointKind()` fails the dotcom/GHE/gist/account/`WWW-Authenticate` checks, sees `https:` protocol, and calls `isGitHubHost('https://github.attacker.io/...')`. [7](#0-6) 
4. `isGitHubHost` matches `/(^|\.)(github)\./` against `github.attacker.io` and returns `true` without any request to the attacker's server. [4](#0-3) 
5. `getCredential()` sees `endpointKind === 'enterprise'` and no existing account for that endpoint, so it calls `ui.promptForGitHubSignIn('https://github.attacker.io/...')`, which starts the Enterprise sign-in flow pointed at the attacker's origin. [6](#0-5) 
6. Victim, believing this is Desktop's legitimate GitHub Enterprise sign-in (because Desktop itself labeled the host as GitHub Enterprise), completes sign-in — sending credentials/OAuth tokens to the attacker's server.

Note: I was not able to inspect the full implementation of `isKnownThirdPartyHost()` or `getEnterpriseAPIURL()` (referenced in `app/src/lib/api.ts` but their bodies weren't returned by search), so I cannot rule out that they add extra denylisting beyond common third-party hosts (bitbucket/gitlab); however, neither would block an arbitrary attacker-registered domain containing the `github.` label, since such a domain cannot be enumerated in advance. If further verification is needed, a full read of `app/src/lib/api.ts` (isKnownThirdPartyHost, getEnterpriseAPIURL) would be advisable.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
```

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
