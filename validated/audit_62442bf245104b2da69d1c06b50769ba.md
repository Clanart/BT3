### Title
Malformed Bitcoin transaction preprocess vectors trigger an uncontrolled panic - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`TransactionSignMachine::sign` trusts every supplied per-participant preprocess vector to contain one entry per transaction input, then indexes those vectors without checking their lengths. A participant can submit an empty or short `Vec<Preprocess<Secp256k1, ()>>` for a multi-input transaction and panic the signing process.

### Finding Description
`TransactionSignMachine::sign` accepts a `HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>>` as its `commitments` argument. It iterates `0 .. self.sigs.len()` and extracts `commitments[c]` from every participant's vector without first validating that every vector has `self.sigs.len()` elements. [1](#0-0) 

For a transaction with at least one input, a vector of length zero causes an immediate index-out-of-bounds panic on `commitments[0]`; more generally, any vector shorter than the number of inputs panics when the missing input index is reached. [1](#0-0) 

The direct `sign` API is an explicitly supported untrusted-input path, while the helper deserializer reads one preprocess for each local signing machine and therefore cannot itself produce a short vector. [2](#0-1) 

### Impact Explanation
An unprivileged signing participant can abort Bitcoin transaction signing by sending a malformed preprocess vector rather than a valid sequence of per-input preprocesses. The panic prevents transaction completion and can terminate or repeatedly stall the caller's signing task depending on panic handling. [1](#0-0) 

### Likelihood Explanation
The attacker only needs control of one `Participant` entry in the `commitments` map and a signing session for a transaction with at least one input. No valid preprocess, secret share, signature, Bitcoin output, or special transaction contents are required. [3](#0-2) 

### Recommendation
Before constructing the per-input commitment maps, validate that every supplied preprocess vector has exactly `self.sigs.len()` elements and that the map contains the intended participants. Return a `FrostError`, such as `InvalidParticipantQuantity` or `InvalidPreprocess`, instead of indexing unchecked. [3](#0-2) 

### Proof of Concept
```rust
use std::collections::HashMap;
use frost::{Participant, sign::{Preprocess, SignMachine}};
use frost::curve::Secp256k1;

fn trigger(sign_machine: TransactionSignMachine) {
    let attacker = Participant::new(2).unwrap();

    // The transaction has at least one input, so c = 0 is reached.
    let mut preprocesses: HashMap<
        Participant,
        Vec<Preprocess<Secp256k1, ()>>,
    > = HashMap::new();
    preprocesses.insert(attacker, Vec::new());

    // Panics at commitments[0] while building the per-input maps.
    let _ = sign_machine.sign(preprocesses, b"");
}
```

The panic occurs because `TransactionSignMachine::sign` requires an empty message and then indexes `commitments[c]` for every input index without checking the vector's length. [3](#0-2)

  fn read_preprocess<R: Read>(&self, reader: &mut R) -> io::Result<Self::Preprocess> {
    self.sigs.iter().map(|sig| sig.read_preprocess(reader)).collect()

  fn sign(
    mut self,
    commitments: HashMap<Participant, Self::Preprocess>,
    msg: &[u8],
  ) -> Result<(TransactionSignatureMachine, Self::SignatureShare), FrostError> {
    if !msg.is_empty() {
      panic!("message was passed to the TransactionSignMachine when it generates its own");
    }

    let commitments = (0 .. self.sigs.len())
      .map(|c| {
        commitments
          .iter()
          .map(|(l, commitments)| (*l, commitments[c].clone()))
          .collect::<HashMap<_, _>>()
      })
