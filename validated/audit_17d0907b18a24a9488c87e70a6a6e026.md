## Analysis

The referenced report describes a pattern where a multi-step, stateful operation (`vestFor`) can be pushed into an unrecoverable failure state by a griefer occupying a precondition ("already a vester") that the legitimate caller needed to satisfy — causing the transaction to revert *after* the precondition was already consumed by someone else. The Cosmos EVM analog is not simply "reverting a call" — it is much worse: the equivalent precondition check happens **after** an earlier, already-committed state change has taken effect, so overriding the outcome to "failure" does not actually undo that earlier change. This produces value duplication instead of a mere denial. [1](#0-0) [2](#0-1) 

### Title
Erc20 IBC middleware `OnRecvPacket` can convert an already-successful ICS20 transfer into a duplicated (double-minted) balance by returning an error acknowledgement after the coin transfer has already been committed - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`erc20.IBCMiddleware.OnRecvPacket` first executes the underlying ICS20 transfer (`im.Module.OnRecvPacket`), which unlocks/mints the transferred coin into the recipient's bank balance and returns a success acknowledgement. Only *afterward* does it call `k.keeper.OnRecvPacket`, which attempts to auto-register a token pair (Case 1) or auto-convert the received coin into its ERC20 representation (Case 2). If that secondary step fails — e.g. because the deterministic token-pair key is already occupied, or because ERC20 minting reverts — the middleware overrides the already-successful acknowledgement with `channeltypes.NewErrorAcknowledgement(err)`. There is no rollback of the bank-balance change performed in step one; only the ack byte string that is relayed back to the source chain changes. [3](#0-2) 

### Finding Description
`OnRecvPacket` runs in two independent phases without a shared atomic rollback boundary:

1. `im.Module.OnRecvPacket` — the standard ICS20 transfer logic — validates and credits the recipient's bank balance with the voucher/received coin. This state mutation is applied against the live `ctx`, not a throwaway cache context, so it survives regardless of what happens next.
2. `im.keeper.OnRecvPacket(ctx, packet, ack)` then inspects the coin and, depending on the token-pair state, either:
   - **Case 1** (`!found && ibc/` prefix): calls `RegisterERC20Extension` → `CreateNewTokenPair`, which fails with `ErrTokenPairAlreadyExists` if an account with a code hash already sits at the deterministic ERC-20 address for that denom, or if the denom/ERC20 map key is already registered.
   - **Case 2** (`found && pair.IsNativeERC20()`): calls `MintingEnabled` and `ConvertCoinNativeERC20`, which fail if the externally-owned ERC20 contract (registered permissionlessly via `MsgRegisterERC20`) reverts on mint (e.g., paused, blacklisted, self-destructed, or otherwise adversarially implemented token). [4](#0-3) [5](#0-4) [6](#0-5) 

In both cases, on failure the function returns `channeltypes.NewErrorAcknowledgement(err)` — overriding the previously-successful ack from step 1. The chain relays this error acknowledgement back to the source chain. On the source chain, an error acknowledgement triggers a refund of the originally escrowed/burned coins (standard ICS20 semantics: error ack ⇒ unescrow or re-mint on the sending side). Meanwhile, on the destination (this) chain, the bank balance credited in step 1 was never reverted, since no cache/snapshot context wraps the two phases together.

Net effect: the same transferred value now exists both as a refunded/unescrowed balance on the source chain **and** as a live bank balance on the destination chain — a duplication of spendable value across chains, mediated entirely by this middleware's post-hoc ack override.

The `MsgRegisterERC20` message is permissionless by default parameter and lets any unprivileged account register an arbitrary ERC20 contract as a "native ERC20" token pair (`OWNER_EXTERNAL`), which is exactly the Case-2 precondition an attacker needs to control: [7](#0-6) 

An attacker who owns such a registered ERC20 contract can make its `mint`/`transfer` function revert on demand (e.g., pause it, or blacklist the intended recipient just before the relayer submits the `RecvPacket` message), deterministically forcing `ConvertCoinNativeERC20` to fail on every incoming transfer of that denom while the underlying bank credit has already landed.

### Impact Explanation
This breaks the fundamental 1:1 accounting invariant between native/bank balances and IBC escrow/backing value that the erc20+ICS20 integration is supposed to preserve. Any unprivileged party who registers (or already owns) the ERC20 side of a token pair can repeatedly trigger silent duplication of transferred value across two chains — each relayed IBC transfer of that denom can be doubled: once refunded on the sender chain (because of the forced error ack) and once retained as a live bank balance on the receiving chain. This is unauthorized duplication of spendable user value via IBC escrow accounting corruption, matching the Critical impact bucket in the scope (duplication/resurrection of spendable value across native balances, IBC escrows, and precompile/ERC20-mediated assets).

### Likelihood Explanation
The trigger requires no privileged role: registering a native ERC20 token pair is permissionless (default `PermissionlessRegistration=true`, or a governance-enabled feature), and controlling when the owned ERC20 contract reverts minting (pausable/blacklist patterns are common, or simply self-destructing the contract once registered) is entirely within the attacker's control. The only external dependency is timing the mint failure to coincide with a real relayed transfer of that denom, which the attacker can induce by making their own transfer or waiting for any other user's transfer using the compromised token pair.

### Recommendation
Wrap the entire `OnRecvPacket` sequence (both the base ICS20 transfer effects and the erc20 auto-conversion/registration attempt) in a single cached/branched context (similar to the pattern already used in `x/ibc/callbacks/keeper/keeper.go` with `ctx.CacheContext()`/`writeFn()`), so that returning an error acknowledgement always fully reverts any bank-balance mutation performed earlier in the same packet-processing call. Alternatively, make the auto-conversion step best-effort and never let its failure override an already-successful acknowledgement — leave the recipient with the bank-denominated coin (as is already documented behavior for `OnAcknowledgementPacket`/`OnTimeoutPacket` failures) instead of retroactively failing the packet.

### Proof of Concept
1. Attacker deploys a pausable/blacklistable ERC20 contract and calls `MsgRegisterERC20` (permissionless) to register it as the native ERC20 side of denom `D` — `k.registerERC20` succeeds since nothing yet occupies `D`.
2. Attacker (or victim) initiates a normal ICS20 transfer of denom `D` from chain B to this chain.
3. On `OnRecvPacket`, the underlying ICS20 module (`im.Module.OnRecvPacket`) credits the recipient's bank account with `D` and returns success.
4. Before/at this point, attacker pauses or blacklists the ERC20 contract so `MintingEnabled`/`ConvertCoinNativeERC20` reverts.
5. `k.keeper.OnRecvPacket` hits Case 2, `ConvertCoinNativeERC20` fails, and the middleware returns `channeltypes.NewErrorAcknowledgement(err)` overriding the prior success.
6. The relayer relays this error ack back to chain B, which refunds/unescrows the sender's original coins.
7. Result: the recipient on this chain retains the bank-credited `D` balance from step 3 (never rolled back) while chain B has also restored the sender's original balance — the value now exists twice.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

// RegisterERC20Extension creates and adds an ERC20 precompile interface for an IBC Coin.
//
// It derives the ERC-20 address from the token denomination and registers the
// EVM extension as an active dynamic precompile.
//
// CONTRACT: This must ONLY be called if there is no existing token pair for the given denom.
func (k Keeper) RegisterERC20Extension(ctx sdk.Context, denom string) (*types.TokenPair, error) {
	pair, err := k.CreateNewTokenPair(ctx, denom)
	if err != nil {
		return nil, err
	}

	// Add to existing EVM extensions
	if err := k.EnableDynamicPrecompile(ctx, pair.GetERC20Contract()); err != nil {
		return nil, err
	}

	return &pair, err
}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

		ctx.EventManager().EmitEvent(
			sdk.NewEvent(
				types.EventTypeRegisterERC20,
				sdk.NewAttribute(types.AttributeKeyCosmosCoin, pair.Denom),
				sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
			),
		)
	}

	return &types.MsgRegisterERC20Response{}, nil
}
