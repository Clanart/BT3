## Analysis

The reduced invariant from the LiFi bug: **a low-level `.call()` to an address with no deployed code returns `success = true` even though nothing executed** — code that treats that `success` flag as proof of a completed side effect will finalize state and move funds it shouldn't.

`EvmHost.sol` contains exactly this pattern, and — critically — the fix is applied inconsistently across four structurally identical functions.

`dispatchIncoming(PostRequest, ...)` correctly guards against this: [1](#0-0) 

But the three sibling entrypoints that dispatch the *other* ISMP callback types omit the same `extcodesize` guard before trusting `.call(...)`'s `success` flag to finalize protocol state and move funds: [2](#0-1) [3](#0-2) [4](#0-3) 

### Title
Missing contract-existence check in `EvmHost.dispatchIncoming(GetResponse)`/`dispatchTimeOut` lets a spurious low-level-call success permanently finalize receipts and pay relayer fees without the app callback ever running - (File: `evm/src/core/EvmHost.sol`)

### Summary
`dispatchIncoming(PostRequest, address)` explicitly checks `extcodesize(destination) == 0` before performing the low-level `.call` to `IApp.onAccept`, and early-returns without writing the replay-protection receipt if the destination has no code [5](#0-4) . The other three ISMP delivery functions — `dispatchIncoming(GetResponse, address)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` — perform the identical low-level `.call` pattern but never check `extcodesize` on the target first [6](#0-5) [7](#0-6) [8](#0-7) .

Per the Solidity call semantics cited in the original report, `.call(...)` against an address with no code returns `(success: true, data: "")` without executing anything. All three unguarded functions treat that `success == true` as proof the app's `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` callback ran, and irreversibly commit protocol state on that basis:
- `dispatchIncoming(GetResponse)` has already written `_responseReceipts[commitment]` *before* the call, and on spurious success it proceeds to pay the relayer's fee out of `feeToken()` and emits `GetRequestHandled` [9](#0-8) .
- `dispatchTimeOut(GetRequestTimeout, ...)` deletes `_requestCommitments[commitment]` *before* the call (removing the ability to retry), and on spurious success refunds the fee to `meta.sender` and emits `GetRequestTimeoutHandled` [10](#0-9) .
- `dispatchTimeOut(PostRequestTimeout, ...)` follows the identical delete-then-call-then-refund pattern [11](#0-10) .

### Finding Description
The corrupted values are `_responseReceipts[commitment]` and `_requestCommitments[commitment]`: they are finalized as "handled" based solely on a low-level call's boolean return, which is not a reliable signal that the destination module's code actually ran. The `if (!success) { restore state; return; }` fallback that all four functions implement to allow a retry on genuine revert is defeated whenever the target has no bytecode, because `success` is unconditionally `true` in that case — the retry path is never taken, and the state is committed as though delivery succeeded.

This is the exact defect class from the external report: funds/state are moved (relayer fee payout, receipt/commitment finalization) on the assumption that a call executed real logic, when in fact a no-code target silently "succeeded" doing nothing. `IsmpModule`/`IApp` callback contracts on Hyperbridge are expected to perform request-specific bookkeeping in `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` (e.g. releasing escrow, per `IntentsBase._withdraw` [12](#0-11) ); if that code path is a target address with no bytecode at delivery time, the corresponding refund/settlement logic never executes, yet the protocol marks the request/response as permanently and non-retriably resolved.

### Impact Explanation
Any request/response/timeout whose destination module (`response.request.from`, `timeout.request.from`) has no deployed code at delivery time (e.g., predates a CREATE2 deployment, was `selfdestruct`'d, or is simply misconfigured) will be marked as successfully delivered and have its associated relayer fee paid out, while the actual application-level effect (refund/settlement logic inside the callback) never runs. Because the receipt/commitment is deleted or written *before* the call and only restored on `success == false`, there is no retry path once this happens — the loss is permanent. This directly matches the bounty's "false state acceptance" and "stealing or loss of funds" categories: value can be paid to a relayer for a "delivery" that never happened, and users relying on the callback to unlock or refund escrowed assets can have that logic permanently skipped.

### Likelihood Explanation
No malicious relayer, prover, or admin is required — the relayer only needs to submit a legitimate proof for a request whose destination `from`/`to` address happens to have no code at the time of processing on this specific chain. This is an ordinary, non-adversarial condition reachable through normal chain state evolution (e.g., a module contract self-destructing, or timing/ordering differences vs. what `PostRequest` intentionally guards for). The inconsistency between the four sibling functions (one guarded, three unguarded) strongly indicates this is an unintentional omission rather than an accepted risk, since the developers clearly identified and mitigated the exact same class of bug for `dispatchIncoming(PostRequest)`.

### Recommendation
Apply the same `extcodesize` check used in `dispatchIncoming(PostRequest, address)` to `dispatchIncoming(GetResponse, address)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` before performing the low-level `.call`, and treat a zero-code target the same way as a call failure (restore/skip state, do not pay the relayer, allow retry) rather than as success.

### Proof of Concept
1. App `A` on the destination chain dispatches a `GET` request through `EvmHost.dispatch`, recorded with `from = address(A)`.
2. Before the response (or a timeout) is delivered, `A` executes `SELFDESTRUCT` (or, for a POST timeout, the originating module address for `timeout.request.from` otherwise ends up with no bytecode by delivery time), so `extcodesize(address(A)) == 0`.
3. A relayer submits a valid state/membership proof for the `GetResponse` (or the timeout proof), and the handler calls `EvmHost.dispatchIncoming(GetResponse, relayer)` / `dispatchTimeOut(...)`.
4. Inside `EvmHost.sol`, `_bytesToAddress(response.request.from).call(...)` targets the no-code address and returns `success = true` with empty data, even though `onGetResponse`/`onGetTimeout` never ran [13](#0-12) .
5. Because `success == true`, the function does not restore `_responseReceipts`/`_requestCommitments`, and proceeds to transfer the relayer fee via `IERC20(feeToken()).safeTransfer(...)` and emit the "Handled" event, permanently recording the request as resolved [14](#0-13) .
6. Any escrow release, refund, or settlement logic that was supposed to run inside `A`'s callback (analogous to `IntentsBase._withdraw`) never executes and can never be retried, resulting in funds/state permanently stuck while the relayer is paid for a delivery that had no effect.

    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
