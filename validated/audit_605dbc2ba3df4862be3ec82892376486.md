### Title
Attacker-controlled "theirs" content can spoof conflict-marker syntax to desync `extractConflictHunks()`/`reassembleResolvedFile()`, silently corrupting the AI-assisted merge/rebase resolution written to disk - ([File: app/src/lib/copilot-conflict-context.ts], [File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
This is the closest structural analog to the reported bug: two independent counters/parsers that are supposed to stay in lock-step (`self.startIdx` vs `self.length` in the Solidity report) can silently desynchronize once an attacker-influenced value grows/shifts past what the code assumes. In Desktop's Copilot-based merge-conflict resolver, the "context builder" (`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts:179-279`) and the "reassembler" that writes the final file (`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts:549-599`) each independently re-scan the *same* raw file for `<<<<<<<`/`=======`/`>>>>>>>` marker lines using naive line-oriented regexes, with no shared/authoritative index and no verification that the reassembled result actually matches what was analyzed.

### Finding Description
Both parsers rely on regexes anchored only at column 0 with exactly 7 marker characters: [1](#0-0) 

`extractConflictHunks` collects `theirsContent` by scanning forward until it finds a line matching `theirsMarker` (`/^>{7}(?:\s|$)/`): [2](#0-1) 

Crucially, while collecting `oursLines`/`theirsLines` the loop never re-checks for a *nested* `oursMarker`/`theirsMarker`-looking line other than the specific terminator it's waiting for — it simply stops at the *first* line that matches the closing-marker regex, regardless of whether that line is a real git-inserted marker or just file content that happens to look like one.

Separately, `reassembleResolvedFile` — the function that actually splices the model's `resolvedContent` into the file that gets written to disk and eventually committed — performs its own independent scan of the raw file to find `hasSeparator`/`closingIndex`: [3](#0-2) 

Because the "theirs" side of a real git conflict is fully attacker-controlled content (it comes from a remote branch, PR, or fetched ref the user merges/rebases/cherry-picks), an attacker can commit a file whose content contains a line that is *exactly* 7 `>` characters followed by whitespace or end-of-line (e.g. `>>>>>>> spoof`) at column 0, embedded inside what will become the "theirs" hunk of a genuine conflict. When Desktop's own git conflict markers wrap that content, both `extractConflictHunks` and `reassembleResolvedFile` will treat the attacker's spoofed line as the real closing marker, truncating the theirs section before the actual git-inserted `>>>>>>> <ref>` marker. The genuine marker line and everything the parser "gives up on" afterward is then handled as ordinary file content — i.e. copied through verbatim by `reassembleResolvedFile`'s outer loop (`resultLines.push(lines[i]); i++`) — while `hunkIndex` has already advanced.

This produces exactly the same class of failure as the Solidity report: two loop/index bookkeeping mechanisms (`extractConflictHunks`'s hunk count sent to the model vs. `reassembleResolvedFile`'s independent re-scan at write time) that are supposed to agree on hunk boundaries can desync once attacker-influenced content satisfies the marker regex in an unexpected position, causing hunk resolutions to be spliced against the wrong boundaries and leaving literal git conflict-marker text and misplaced code silently mixed into the file that `reassembleResolutions()` returns and that the app subsequently writes and lets the user commit/push. [4](#0-3) 

### Impact Explanation
The corrupted output is exactly the kind of file content the user is expected to trust as "conflict resolved" and then commit/push. Silent corruption here means: (a) leftover raw conflict-marker syntax and truncated/duplicated code end up in the final committed source, (b) code from the wrong side of the conflict can be attributed to the wrong branch (intent misattribution), and (c) because Desktop's whole selling point for this feature is "AI resolved this conflict, review and commit," a user reviewing the diff may not notice a subtly displaced hunk boundary buried inside a large file, especially when many files are batched (`SinglePromptFileLimit`/`MaxConcurrentChunks` in `app/src/lib/copilot-conflict-resolution.ts:182-185`). This matches the requested impact category of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires no local access, no admin rights, and no prior compromise — only that the victim merges/rebases/cherry-picks a branch, PR, or fetched ref containing an attacker-crafted file. The trigger condition (a column-0 line of exactly 7 `>` or `<` characters followed by whitespace/EOL) is a narrow but entirely realistic string an attacker can embed in source, documentation, fixtures, or generated content, and requires no unnatural user interaction beyond the normal "resolve conflicts with Copilot" flow that Desktop actively promotes. I was not able to fully trace the exact write-to-disk call site downstream of `reassembleResolutions()` (only `copilot-store.ts`'s imports were visible before the exploration limit was reached), so I cannot confirm with certainty whether any additional guard (e.g., a final "no conflict markers remain" re-check before commit) exists between reassembly and disk write — this is the one point of uncertainty in this analysis.

### Recommendation
- Use a single, shared parser/index for both context extraction and reassembly instead of two independently re-implemented marker scanners, so hunk boundaries can never disagree between the two passes.
- When scanning for a closing/separator marker, validate that it is the *matching* marker for the specific hunk being parsed (e.g., track marker provenance/position rather than just regex-matching arbitrary lines), or re-verify after reassembly that the output contains zero residual conflict-marker-looking lines before allowing the file to be treated as resolved.
- Add a post-reassembly integrity check (e.g., re-run `extractConflictHunks` on the final content and assert zero hunks remain) before surfacing the file as "resolved" to the user, so any hunk-count mismatch fails closed instead of silently committing corrupted content.

### Proof of Concept
1. Attacker creates a branch/PR whose modified version of `file.ts` contains, among normal code, a standalone line consisting of exactly `>>>>>>> spoof` at column 0.
2. Victim merges/rebases this branch, producing a real git conflict where that line lands inside the "theirs" section, e.g.:
   ```
   <<<<<<< HEAD
   our code
   =======
   some code
   >>>>>>> spoof
   more attacker code that should stay in "theirs"
   >>>>>>> feature-branch
   trailing file content
   ```
3. `extractConflictHunks` and `reassembleResolvedFile` both stop theirs-content collection at the attacker's `>>>>>>> spoof` line instead of the real `>>>>>>> feature-branch` marker inserted by git.
4. The model only sees/resolves the truncated hunk; `reassembleResolvedFile` splices the model's resolution at the wrong boundary and copies the real trailing marker line and subsequent content through verbatim as ordinary text.
5. The file returned by `reassembleResolutions()` (and ultimately written/committed) still contains a stray `>>>>>>> feature-branch` marker line and misplaced code, without the tool or user necessarily flagging the file as unresolved. [5](#0-4)

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
