### Title
Missing Slippage Protection in `WombatPoolHelperV2.depositFor()` Allows Sandwich Attacks on Deposits - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor()` is a public, unrestricted function that any wallet can call to deposit stable tokens into a Wombat pool on behalf of a beneficiary. Unlike the sibling `deposit()` function, it hardcodes the `_minimumLiquidity` slippage parameter to `0` when forwarding the call down to `WombatStaking.deposit()` and ultimately `IWombatPool.deposit()`, completely removing the caller's ability to protect against unfavorable pool pricing.

### Finding Description
`deposit()` correctly forwards a caller-supplied `_minimumLiquidity` value: [1](#0-0) 

But `depositFor()`, which is callable by any unprivileged wallet with no access-control modifier, hardcodes this same parameter to `0`: [2](#0-1) 

This `0` propagates through `_deposit()` into `WombatStaking.deposit()`: [3](#0-2) 

and finally into the underlying Wombat AMM pool's `deposit()` call, whose `minimumLiquidity` parameter is the documented slippage-protection mechanism (the minimum LP/asset liquidity the depositor accepts): [4](#0-3) [5](#0-4) 

Because `minimumLiquidity` is forced to `0`, the deposit will succeed no matter how little liquidity is actually minted for the deposited amount — the transaction can never revert due to unfavorable pricing. The identical hardcoded-zero pattern also exists in `AnkrBNBPoolHelper.sol`, which shares the same `_deposit` structure (though `AnkrBNBPoolHelper` does not itself expose a public `depositFor`, its `deposit()`/`depositNative()` do accept caller-supplied minimums, so the primary affected path is `WombatPoolHelperV2.depositFor`): [6](#0-5) 

This directly mirrors the reported bug class: a user-facing deposit function lacking a usable slippage-protection parameter, exposing depositors to NAV/price changes between transaction submission and execution — except here the protection exists in the contract's own API but is deliberately zeroed out for one specific unprivileged entry point.

### Impact Explanation
An attacker (or generalized MEV searcher) can front-run/sandwich any call to `depositFor()`: swap against the target Wombat pool to skew its internal asset ratio immediately before the victim's `depositFor` transaction executes, causing the pool to mint significantly fewer LP/receipt tokens for the same deposited stablecoin amount than the victim expected, then reverse the swap after. Because `_minimumLiquidity` is hardcoded to `0`, the deposit transaction cannot revert to protect the depositor, resulting in a direct, concrete loss of user funds (value) at the moment of deposit. This satisfies the "direct theft of user funds" impact bar, since the deposited principal converts into a token amount worth measurably less than fair value, extractable by the attacker via the sandwich.

### Likelihood Explanation
`depositFor()` has no access-control modifier, so any unprivileged wallet can call it directly (e.g., as part of any front-end flow that deposits "for" a user, or a user simply calling it on their own behalf). Sandwiching an on-chain AMM deposit that has zero slippage protection is a standard, low-cost, highly reliable MEV strategy requiring only capital and pool-manipulation gas, making exploitation straightforward and repeatable for any deposit routed through this function.

### Recommendation
Do not hardcode `_minimumLiquidity` to `0` in `depositFor()`. Add a `_minimumLiquidity` parameter to `depositFor()` (and any other internal call sites following this pattern, e.g. `AnkrBNBPoolHelper`'s internal helpers if reused this way) and forward the caller-supplied value through to `WombatStaking.deposit()` / `IWombatPool.deposit()`, consistent with the existing `deposit()` function.

### Proof of Concept
1. Attacker observes a pending `depositFor(amount, victim)` transaction (or simply calls it themselves) targeting `WombatPoolHelperV2`.
2. Attacker front-runs with a large swap into the underlying Wombat pool's `depositToken`/`lpToken` asset to skew the pool's cash/liability ratio, worsening the deposit exchange rate.
3. The victim's `depositFor()` executes, calling `WombatStaking.deposit()` → `IWombatPool.deposit(token, amount, 0, address(this), block.timestamp, false)` — since `minimumLiquidity = 0`, the deposit succeeds despite minting far fewer LP tokens than a fair-price deposit would.
4. Attacker back-runs with the reverse swap, restoring the pool and pocketing the difference, while the victim (`_for` address) is left staked with LP/receipt tokens worth less than the stablecoins they deposited. [2](#0-1) [7](#0-6)
