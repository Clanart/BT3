### Title
Hookify plugin's rule loader resolves security rules relative to the current working directory instead of `$CLAUDE_PROJECT_DIR`, silently disabling all guardrail hooks when cwd diverges from the project root - (File: `plugins/hookify/core/config_loader.py`)

### Summary
The `hookify` plugin implements user-configured `PreToolUse`/`PostToolUse`/`Stop`/`UserPromptSubmit` guardrails (e.g. blocking `rm -rf`, warning on dangerous edits) by reading rule files from `.claude/hookify.*.local.md` [1](#0-0) . The loader builds this path with `os.path.join('.claude', ...)`, which resolves relative to the process's *current working directory* rather than the fixed project root exposed via `$CLAUDE_PLUGIN_ROOT`/`$CLAUDE_PROJECT_DIR` convention used elsewhere in the same plugin ecosystem [2](#0-1) . This mirrors the root cause of the reported Midas bug: an incorrect assumption baked in at "initialization" time (here, at every hook invocation) about which object/location holds the authoritative source, so the intended enforcement mechanism silently stops doing anything useful instead of loudly failing.

### Finding Description
Every hookify hook entry point (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) calls `load_rules(event=...)`, which in turn does:
```
pattern = os.path.join('.claude', 'hookify.*.local.md')
files = glob.glob(pattern)
``` [3](#0-2) 

`glob.glob` with a relative pattern resolves against `os.getcwd()` at the time the script runs — not against the Claude Code project/session root. Claude Code's own hook documentation shows that hook scripts are expected to anchor security-relevant lookups to `$CLAUDE_PROJECT_DIR`, precisely because the working directory is not guaranteed to stay fixed (subagents/worktrees can run with a different `cwd`, and Bash tool invocations, `/cd`, or worktree-isolated sessions can change it mid-session) [4](#0-3) [2](#0-1) . `hookify` does not use this variable at all for locating its rule files, unlike the pattern documented for “Configuration-based activation” hooks.

Every hook entry point additionally swallows all exceptions and unconditionally exits `0`, explicitly choosing to "allow the operation" on any error [5](#0-4) . Combined with the cwd-relative glob, this produces a silent fail-open: if the hook subprocess's cwd is anything other than the exact directory containing `.claude/`, `glob.glob` returns an empty list (no exception), `load_rules` returns `[]`, `evaluate_rules([], ...)` returns `{}` (no match) [6](#0-5) , and the tool call is allowed with no warning that the guardrail never ran.

### Impact Explanation
Any user who has configured `hookify` rules to block/warn on dangerous operations (destructive `rm -rf`, writes to credential paths, etc. — the exact use cases documented for the plugin [7](#0-6) ) gets no enforcement whenever the tool executes with a working directory that differs from the directory hookify's own process happened to start in. This is a genuine "hook bypass" in the sense scoped by this review: the safety mechanism the user explicitly installed is defeated, and — unlike the M-1 Solidity bug, which fails loudly (revert/DoS) — this failure mode is silent, which is strictly worse from a security-monitoring standpoint because there is no indication to the user that their configured guardrail rule never fired.

### Likelihood Explanation
Likelihood is moderate: it requires a hookify rule to be configured, plus a tool invocation whose effective working directory differs from the directory Claude Code launched the hook subprocess in (e.g., worktree-isolated sessions, subagents with a `cwd:` override, or an interactive `cd` before a chained Bash command). These are all normal, unprivileged usage patterns already documented in this repository's changelog as scenarios Claude Code explicitly has to handle for cwd correctness elsewhere (worktree isolation, subagent `cwd:` overrides) [8](#0-7) , so hitting this condition does not require any special privilege or attacker control — just normal multi-directory or multi-agent usage.

### Recommendation
Anchor the rule-file glob to `$CLAUDE_PROJECT_DIR` (falling back to cwd only if unset), matching the convention already documented for other hook scripts in this repo, e.g.:
```python
project_dir = os.environ.get('CLAUDE_PROJECT_DIR', os.getcwd())
pattern = os.path.join(project_dir, '.claude', 'hookify.*.local.md')
```
Additionally, consider distinguishing "no rules configured" from "rules directory not found / lookup failed" so a misconfiguration surfaces to the user instead of silently behaving like there are no rules.

### Proof of Concept
1. Configure a blocking rule, e.g. `.claude/hookify.no-rm-rf.local.md` with `event: bash`, `action: block`, pattern `rm\s+-rf`, in project root `/repo`.
2. Start a Claude Code session whose current tool-execution working directory differs from `/repo` (e.g., a worktree-isolated background session created under a different checkout, or any hook invocation where `PLUGIN_ROOT`/cwd is not `/repo`).
3. Ask Claude to run `rm -rf some_dir` via the Bash tool.
4. `pretooluse.py` invokes `load_rules(event='bash')`, which globs `('.claude', 'hookify.*.local.md')` relative to the subprocess cwd — not `/repo` — finds no files, returns `[]`.
5. `evaluate_rules([], ...)` returns `{}`; hookify prints `{}` and exits 0; the PreToolUse hook approves the command with no warning, even though a matching `block` rule exists in the project.
