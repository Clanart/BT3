Based on my investigation, I found a genuine "incorrectly-resolved name" bug in sei-chain's pointer registry: the reverse-registry key derivation truncates bech32 address strings instead of the raw 20-byte address, creating collision potential analogous to GitLab's ambiguous git-reference resolution.

### Title
Truncated bech32-string-to-address key derivation causes reverse pointer-registry collisions - (File: `x/evm/keeper/pointer.go`)

### Summary
When registering a CW→ERC pointer (CW20/CW721/CW1155 wrapper pointing back to an existing ERC20/721/1155 contract), the reverse-registry key is derived by calling `common.BytesToAddress([]byte(addr))` on the *bech32 string* of the CW pointer contract, rather than on its raw 20-byte account address. `common.BytesToAddress` silently truncates any input longer than 20 bytes down to its last 20 bytes. Since a bech32 sei address string is far longer than 20 bytes, this produces a key derived only from the tail characters of the string, which is a materially weaker/incorrectly-resolved "name" than the real address.

Because CosmWasm contract addresses on sei-wasmd are derived deterministically (either sequential `BuildContractAddress(codeID, instanceID)` or attacker-controlled `Instantiate2` with an arbitrary salt), an attacker fully controls or can grind the byte contents of a to-be-created contract's address: [6](#0-5) [7](#0-6) 

Bech32-encoding the 20-byte address into a `sei1...` string and then truncating that string's *last 20 raw characters* means the resolved reverse-registry key is a function of only a slice of the human-readable string, not the actual 20-byte address. Two distinct CW contract addresses can be crafted (via salt-grinding with `Instantiate2`) so that their bech32 string representations share the same trailing 20 ASCII characters, causing their `PointerReverseRegistryKey` entries to collide.

### Impact Explanation
This is directly analogous to the GitLab bug class: the name used to resolve/validate an entity (the pointer's identity in the reverse registry) is not the true canonical identifier, so two different objects can resolve to the same key. Concretely:
- An attacker can grind a CW20/CW721/CW1155 pointer-contract address whose bech32 suffix collides with an already-registered pointer, causing `cwAddressIsPointer` to falsely report "true"/"false" for the wrong address, corrupting the "no pointer-to-pointer" invariant that the whole pointer system relies on to keep the ERC↔CW mapping 1:1 and non-recursive.
- Because `Set*ERC*Pointer` writes unconditionally overwrite whatever was previously stored at the (colliding) reverse key, a second pointer registration under a colliding address silently clobbers the first pointer's reverse entry, which is later read by `GetERC20Pointee`/`GetERC721Pointee`/`GetERC1155Pointee`/`GetNativePointee` (used by public gRPC queries and EVM/CW bridging logic) to resolve "which ERC contract does this CW contract point to." [8](#0-7) 

A wrong/clobbered reverse mapping means downstream logic (and any RPC/query consumer or EVM precompile relying on `GetAnyPointerInfo`/`GetXPointee`) can be given an incorrect ERC/CW pointee address, i.e., what is displayed/queried as "the pointer target" no longer matches what pointer system semantics guarantee, potentially enabling misdirected pointer-based token operations (unauthorized transfer surface via wrong pointer resolution) between a legitimate and an attacker-planted pointer.

### Likelihood Explanation
Exploitability requires: (1) the ability to deploy a CosmWasm contract with an attacker-chosen salt via `Instantiate2` (available to any wasm user), and (2) grinding enough candidate salts offline to find a bech32-string collision in the last 20 raw bytes against a target's pointer address — a non-trivial but bounded (birthday-bound) brute-force computation, not requiring any privileged access. This raises it above a purely theoretical issue, though I could not find a runtime check in the reviewed code that closes this off, and I did not find direct proof-of-concept exploit code in the indexed files confirming end-to-end fund transfer — this should be validated further with an actual collision-grinding proof.

### Recommendation
Change all `PointerReverseRegistryKey` derivations for the CW→ERC pointer directions to use the raw 20-byte `sdk.AccAddress` (e.g., `sdk.AccAddress(addr).Bytes()` after `sdk.AccAddressFromBech32`) instead of `common.BytesToAddress([]byte(addr))` on the bech32 string, in `SetCW20ERC20PointerWithVersion`, `SetCW721ERC721PointerWithVersion`, `SetCW1155ERC1155PointerWithVersion`, `cwAddressIsPointer`, `DeleteCW20ERC20Pointer`, `DeleteCW721ERC721Pointer`, and `DeleteCW1155ERC1155Pointer` in `x/evm/keeper/pointer.go`.

### Proof of Concept
Not independently reproduced in this analysis — the mechanism (bech32-string truncation via `common.BytesToAddress`) is confirmed by direct code inspection, but I did not have the ability to grind an actual colliding `Instantiate2` salt or execute an end-to-end fund-loss transaction in this environment. A Devin session with repo access and a local sei-chain devnet would be needed to grind a real collision and demonstrate the resulting reverse-pointer clobbering/misresolution.

// BuildContractAddress builds an sdk account address for a contract.
func BuildContractAddress(codeID, instanceID uint64) sdk.AccAddress {
	contractID := make([]byte, 16)
	binary.BigEndian.PutUint64(contractID[:8], codeID)
	binary.BigEndian.PutUint64(contractID[8:], instanceID)
	return address.Module(types.ModuleName, contractID)[:types.ContractAddrLen]
}
