### Title
Git option/argument injection via unvalidated PR `head.repo.clone_url` passed to `git remote add` - (File: `app/src/lib/git/remote.ts`)

### Summary
GitHub Desktop's "Open PR from Desktop" deep-link flow adds a git remote whose URL comes directly from the GitHub API's pull-request payload (`head.repo.clone_url`), which is attacker-controlled (any fork's owner controls this value). That URL is passed straight into the `git remote add` argv without the `--` end-of-options separator that the project's own `clone()` implementation uses for the exact same class of untrusted input, allowing the string to be interpreted as a git option rather than a URL.

### Finding Description
`addRemote`/`setRemoteURL` build the git command with the untrusted URL as a bare trailing argument and no `--` guard: [1](#0-0) [2](#0-1) 

Contrast this with `clone()`, in the same codebase, which explicitly uses `--` to stop option parsing before the very same kind of externally supplied URL: [3](#0-2) 

The attacker-reachable path is: a user clicks an `x-github-client://openRepo/...&pr=<n>` deep link (or the equivalent "Open PR from Desktop" browser button), which is parsed here: [4](#0-3) [5](#0-4) 

This calls `_checkoutPullRequest`/`_findPullRequestBranch`, which fetches the PR object from the API and, if no existing remote matches, adds a new remote using the **unvalidated** `headCloneUrl` field taken from that API object: [6](#0-5) [7](#0-6) 

Nowhere along this path is `headCloneUrl`/`clone_url` checked against `parseRemote`'s protocol allowlist (`https`, `ssh`, `git@...`) before being handed to `addRemote`; that validation (in `app/src/lib/remote-parsing.ts`) is only used in the manual "Clone repository" UI flow, not in the PR-remote-creation path. Because a pull request's head repository is whatever fork the attacker controls, the attacker fully controls the string that becomes `clone_url`, including making it start with `-` (e.g. `--mirror=fetch`, `-f`, `-t<ref>`, `--upload-pack=...` depending on the underlying git version's option parser), which `git remote add <name> <value>` will interpret as an option rather than a literal URL.

### Impact Explanation
This falls squarely in scope: the attacker is an unprivileged actor (a fork owner opening a PR) and the trigger is a link/deep-link the victim clicks. Depending on which git-recognized option string is smuggled through the unguarded positional argument, outcomes include:
- `-f` forces `git remote add` to immediately fetch from an attacker-chosen host as a side effect of adding a "PR remote," which is not the developer's expectation.
- `--mirror=fetch` reconfigures the remote's refspec so that a subsequent fetch mirrors *all* refs from the attacker's server into the local repository, silently overwriting local branches the user later commits to/pushes from — matching the "silent corruption of what the user commits or pushes" impact category.
- Malformed/garbage option strings can also be used to break the remote configuration or write unexpected values into `.git/config`.

### Likelihood Explanation
The flow requires no local access, no pre-existing malware, and no leaked credentials — only that the victim click a "View pull request in GitHub Desktop"-style deep link for a PR from an attacker-controlled fork. The lack of a `--` separator here is a genuine asymmetry versus `clone.ts`'s handling of the same untrusted-input class, suggesting the omission in `remote.ts` was not deliberate. I was not able to execute git directly to confirm the exact exploitable option surface for `git remote add`/`git remote set-url` in the git version(s) Desktop bundles (via `dugite`), so the precise severity (config corruption vs. an option that triggers network egress) should be verified experimentally rather than assumed.

### Recommendation
Add `--` before the URL argument in `addRemote` and `setRemoteURL` (mirroring `clone.ts`), and/or validate any URL sourced from the GitHub API (`clone_url`, `head.repo.clone_url`, etc.) against the same `parseRemote` protocol allowlist used by the manual clone flow before it is ever passed to a git subprocess.

### Proof of Concept
1. Attacker forks a public repository and opens a pull request from a fork whose repository's `clone_url` (as returned by the GitHub API) is a crafted string such as `--mirror=fetch` (this typically requires control of how the fork is registered/renamed via the GitHub API/UI rather than the PR itself, since `clone_url` is normally derived from the repo's canonical URL — this step needs further verification against real GitHub API behavior).
2. Attacker sends the victim a deep link: `x-github-client://openRepo/https://github.com/<owner>/<repo>?pr=<n>`.
3. Victim (who has the target repository already open in Desktop or lets Desktop clone it) clicks the link; `parseAppURL` classifies it as `open-repository-from-url` with `pr` set, triggering `openPullRequestFromUrl` → `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)`.
4. Because `addRemote` issues `git(['remote', 'add', name, url])` without a `--` separator, if `url` begins with `-`, git parses it as an option instead of a URL, producing behavior outside the developer's expectations (unexpected fetch, refspec reconfiguration, or config corruption) the next time the fork remote is used.

**Uncertainty:** I could not verify from static code review alone (a) whether GitHub's API ever actually returns a `clone_url` value that can be made to start with `-` for a real fork, or (b) which specific `git remote add`/`set-url` option strings are exploitable for a given bundled git version. This would need to be confirmed with a live Desktop build and a controlled malicious fork/API response before treating this as a fully confirmed RCE/corruption primitive rather than a plausible argument-injection gap.
