### Title
Silent, unconfirmed rewrite of a repository's Git remote URL from GitHub API data - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The report's underlying invariant is: a trusted-but-not-fully-trusted party can change security‑relevant configuration for downstream users, and the client applies that change immediately with no confirmation and no time window for the user to notice or opt out. In GitHub Desktop, the analogous mutable, security‑relevant value is the local Git `origin` remote URL — the destination that all future `push`/`fetch`/`pull` operations, and any stored credentials, are resolved against. `updateRemoteUrl` silently calls `git remote set-url` whenever the GitHub API reports a different `clone_url` for the matched repository, with no dialog, confirmation, or delay.

### Finding Description
`updateRemoteUrl` compares the locally configured remote URL against `apiRepo.clone_url` returned by the GitHub API and, if it decides the local remote is "unchanged" from what was last cached, it rewrites the remote in place: [1](#0-0) 

This function is invoked from `repositoryWithRefreshedGitHubRepository`, a background refresh routine that runs automatically — not only in response to a deliberate user action: [2](#0-1) 

That refresh path is triggered, among other places, every time a repository is selected (`_selectRepositoryRefreshTasks` → `this.repositoryWithRefreshedGitHubRepository(repository)`), when accounts change (`refreshSelectedRepositoryAfterAccountChange`), and when repositories are (re-)added (`_addRepositories`): [3](#0-2) [4](#0-3) 

The actual mutation is performed via `git remote set-url`: [5](#0-4) 

There is no UI confirmation step comparable to the one that exists for a manual remote URL edit in Repository Settings (`onSubmit` in `repository-settings.tsx`, which is an explicit, user-initiated action the user can review before saving): [6](#0-5) 

The broken invariant: for user-initiated remote-URL edits, the user reviews and submits the change (`repository-settings.tsx`). For the automatic API-driven path, the exact same security‑relevant value is rewritten with the same trust level as if the user typed it — but silently, on a background timer/selection event, and the only guard (`remoteUrlUnchanged`/`protocolsMatch`/`!urlsMatch`) is a heuristic that decides *whether* to apply the change, not *whether the user should be asked*.

### Impact Explanation
Once the remote is rewritten, all subsequent `push`, `pull`, and `fetch` operations for that repository target the new URL without the user ever seeing or approving it, matching the "silent corruption of what the user commits or pushes" impact category. Because the update happens transparently as part of a routine background refresh (`repositoryWithRefreshedGitHubRepository`), a user who has cloned/collaborates on a repository controlled by another party (the repository owner/admin — the "manager" analog from the report) will have their local push/fetch destination changed automatically the moment that party changes the repository's `clone_url` (e.g., via a rename or transfer), with no notification, confirmation dialog, or grace period in which the user could notice and object, unlike the deliberate, reviewable flow in Repository Settings.

### Likelihood Explanation
The heuristic guard (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) requires that the user's local remote still matches the previously cached `clone_url` and only fires when the API-reported `clone_url` differs — conditions that are trivially satisfied by an ordinary repository rename/transfer, something entirely within the control of a repository owner/admin. The refresh path runs unconditionally on repository selection and on repository add, so the window in which an owner-triggered rename propagates to collaborators' local remotes is effectively "next time Desktop refreshes that repo," which happens very often during normal use.

### Recommendation
Treat an automatically detected `clone_url` change the same way the report recommends for `SetToken` module changes: introduce a confirmation step (or at minimum a non-blocking, dismissible notice) before silently rewriting the remote URL, and/or add a short delay/opt-out window so the user can review the new destination before it becomes the operative push/fetch target — mirroring the deliberate, reviewable flow already used for manual edits in `repository-settings.tsx`.

### Proof of Concept
1. User A clones a repository and it is tracked by Desktop with `gitHubRepository.cloneURL` cached (e.g. `https://github.com/org/repo`).
2. The repository owner (org admin) renames the repository (e.g. to `https://github.com/org/repo-renamed`) — a routine, unprivileged-from-Desktop's-perspective server-side action available to any repo admin.
3. On User A's next repository selection or app focus, `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` runs, calls `api.fetchRepository(owner, name)`, and `apiRepo.clone_url` now differs from the local remote.
4. `updateRemoteUrl` finds `protocolsMatch && remoteUrlUnchanged && !urlsMatch` true and calls `gitStore.setRemoteURL(...)`, which runs `git remote set-url origin https://github.com/org/repo-renamed` — with zero UI indication to User A that their push/fetch target just changed. [7](#0-6)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
