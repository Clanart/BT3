## Analysis

`BaseRewardPool.donateRewards` is permissionless and forwards directly to `_provisionReward`, gated only by `isRewardToken[_rewardToken]` [1](#0-0) . `_provisionReward` branches purely on `this.totalStaked()` at call time: if it's zero, the incoming reward is parked in `rewardInfo.queuedRewards`; otherwise the *entire* queued backlog plus the new amount is folded into `rewardPerTokenStored` divided by the current `totalStaked()` [2](#0-1) .

`totalStaked()` is just `IERC20(stakingToken).balanceOf(operator)` [3](#0-2)  — i.e., whatever is currently staked in `MasterMagpie`. `MasterMagpie.deposit`/`withdraw` have no cooldown or vesting; a user can deposit and withdraw in the same transaction [4](#0-3) [5](#0-4) . Reward accrual (`earned`) only checkpoints via `userRewardPerTokenPaid`, which is only updated on `_updateFor` (deposit/withdraw/getReward) [6](#0-5) [7](#0-6)  — there is no time-weighting of when the stake was held while `queuedRewards` accumulated.

So while `totalStaked()==0` (e.g., pool bootstrap, or after all stakers exit), any `queueNewRewards`/`donateRewards` calls simply accumulate in `queuedRewards` indefinitely. Because `donateRewards` is permissionless and takes no `msg.sender` restriction, an attacker can:
1. Watch for/produce a state where `totalStaked()==0` while `queuedRewards` has built up for a reward token.
2. Deposit a stake (even relatively small) into `MasterMagpie`.
3. Immediately call `donateRewards(1, _rewardToken)` in the same transaction — this flushes the entire `queuedRewards` backlog into `rewardPerTokenStored`, divided only by the attacker's own freshly-deposited stake (since they're the only staker), giving the attacker 100% of the accumulated backlog.
4. Withdraw immediately afterward, claiming the reward.

This is a real, reachable exploit path: `donateRewards` has no owner/manager/poolManager gating [1](#0-0) , and nothing prevents an attacker from timing the flush against a stake set they just assembled. The economic effect is that legitimately-owed backlog rewards (from `queueNewRewards` calls made by the real reward manager while the pool had zero stakers) are diverted entirely to whichever party happens to be staked (even momentarily) at the instant someone calls `donateRewards`, rather than to genuine long-term/future stakers of that pool.

The "low-decimal staking token" detail from the prompt affects the magnitude of `(_amountReward * 10**stakingDecimals()) / totalStaked()` precision but is not the root cause — the root cause is the lack of any time-vesting/streaming of `queuedRewards` and the fact that release timing is fully attacker-controlled via a permissionless function.

### Title
Permissionless `donateRewards` allows flash-stake sniping of accumulated `queuedRewards` - (File: rewards/BaseRewardPool.sol)

### Summary
`donateRewards` is callable by anyone and flushes `rewards[token].queuedRewards` (accumulated while `totalStaked()==0`) into `rewardPerTokenStored`, divided by whatever `totalStaked()` is at that exact block. An attacker can deposit a stake and call `donateRewards` in the same transaction to capture the entire backlog before withdrawing.

### Finding Description
`_provisionReward` only queues rewards while `totalStaked()==0`; the moment `totalStaked()!=0`, it dumps `queuedRewards + _amountReward` into `rewardPerTokenStored` proportional to current stake [8](#0-7) . Since `donateRewards` has no access control beyond `isRewardToken` [1](#0-0) , and `MasterMagpie.deposit`/`withdraw` allow atomic same-transaction stake/unstake with no lockup [4](#0-3) , an attacker fully controls the stake distribution present at the exact moment the backlog is released.

### Impact Explanation
Reward tokens that accumulated in `queuedRewards` while the pool had zero stakers (i.e., real yield deposited via `queueNewRewards` by the reward manager) are diverted in full to an attacker's transient stake rather than to genuine stakers, constituting theft of unclaimed yield.

### Likelihood Explanation
Requires a window where `totalStaked()==0` while a reward manager has queued rewards for that pool (pool bootstrap or full-exit scenarios), and capital to briefly hold a stake for one transaction. This is realistic during new-pool launches or between full user exits and re-entries, and is fully repeatable.

### Recommendation
Add time-weighted release/streaming of `queuedRewards` (e.g., Convex-style capped `newRewardRatio` per distribution) instead of dumping the full backlog instantly against whatever `totalStaked()` happens to be, and/or restrict `donateRewards`/backlog-release timing to occur only through `updatePool`-style periodic accrual rather than an attacker-triggered instantaneous call.

### Proof of Concept
Foundry test plan:
1. Deploy `BaseRewardPool` with a reward token, `totalStaked()==0`.
2. Manager calls `queueNewRewards(1000e18, rewardToken)` — verify it lands in `rewards[token].queuedRewards`.
3. Attacker (from a helper contract) in one transaction: `MasterMagpie.deposit(stakingToken, 1)` then `BaseRewardPool.donateRewards(1, rewardToken)` then `MasterMagpie.withdraw(stakingToken, 1)`, calling `getReward` after.
4. Assert attacker receives ~1000e18 reward tokens despite staking only 1 wei for one transaction, while legitimate later stakers receive nothing from that backlog.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
