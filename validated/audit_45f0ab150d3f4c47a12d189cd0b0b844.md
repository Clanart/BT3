### Title
Unvalidated `sender`/`recipient` participant indexes in PedPoP blame evaluation panic (crash) on out-of-range indexes - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2015-8722 is a missing-validation bug where attacker-controlled input reaches a dereference of an invalid frame pointer, crashing the application. The Serai analog is in PedPoP's blame machinery: `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender` and `recipient` `Participant` values from an accusation without checking they are within `1 ..= n`, and then index `self.commitments[&sender]` (lib.rs ~line 599) and `self.encryption`'s `enc_keys[&decryptor]` (encryption.rs ~line 388). `HashMap`'s `Index` impl panics on a missing key, so a blame request naming any `Participant > n` aborts the calling process.

### Finding Description
`blame_internal` at crypto/dkg/pedpop/src/lib.rs:575-609 computes `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)` after decryption. Before that, `Decryption::decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:366-397) evaluates `self.enc_keys[&decryptor]` when an `EncryptionKeyProof` is supplied. Both are unchecked map indexings. `AdditionalBlameMachine::new` (lib.rs:649-662) populates `commitments` and `enc_keys` only for `1 ..= n`, so any `sender` or `recipient`/`decryptor` index `> n` (or any participant whose commitment was never registered) causes a panic via `HashMap::index`. `Participant` is merely a non-zero `u16`; nothing in `blame` bounds it against `n`.

### Impact Explanation
An unprivileged participant (or anyone able to submit a blame/accusation to a node evaluating PedPoP blame, e.g., via the `VerifyBlame` path that passes `accuser`/`accused` into `AdditionalBlameMachine::blame`) can specify an `accused`/`sender` index such as `Participant(n + 1)`. The honest node dereferences `commitments[&sender]` / `enc_keys[&decryptor]` on a key that does not exist and panics, crashing the validator/processor — a remotely-triggered denial of service, matching the CVE's crash-on-crafted-input class. Note `decrypt_with_proof` can panic even before the signature check's early return? The `pop.verify` runs first and returns `InvalidSignature` for a bogus `sender` — however the panic path via `enc_keys[&decryptor]` only requires `proof: Some(...)` and a valid `pop` under the claimed `from`; an attacker cannot forge `pop` for an arbitrary `sender`. The more direct path is `self.commitments[&sender]` in `blame_internal` reached only after `decrypt_with_proof` returns `Ok`, which requires a genuinely well-formed share — so attacker reachability for `sender` out-of-range is limited. The `recipient`/`decryptor` index, however, is attacker-claimed: `enc_keys[&decryptor]` is indexed before the proof verifies, so an accuser who supplies a valid-looking accusation naming itself as a `recipient > n`... also panics only if `decryptor` was never registered, but the accuser must pass the `pop` signature check bound to `from` — `from`/`sender` is used in `pop_challenge`, not `recipient`. So a valid accusation message from real `sender` with attacker-chosen `recipient > n` reaches `enc_keys[&decryptor]` panic directly.

### Likelihood Explanation
Medium: it requires a participant to submit (or relay) a blame request with a crafted `recipient`/`accuser` index out of range, which is public-input-controlled and unchecked by the library (`blame` has no bounds check on either index). Exploitation crashes the evaluating node rather than producing wrong blame output.

### Recommendation
In `BlameMachine::blame_internal` / `AdditionalBlameMachine::blame`, validate `sender` and `recipient` against `1 ..= n` (or use `HashMap::get` and return a defined error/`PedPoPError`) before indexing `self.commitments` and `self.enc_keys`.

### Proof of Concept
```rust
// crypto/dkg/pedpop context: n = 5, DKG completed or AdditionalBlameMachine built
let machine = AdditionalBlameMachine::<C>::new(context, 5, commitment_msgs).unwrap();
let bogus_recipient = Participant::new(6).unwrap(); // > n
// attacker supplies a real sender's encrypted share + an EncryptionKeyProof
machine.blame(sender, bogus_recipient, msg, Some(proof));
// -> decrypt_with_proof evaluates self.enc_keys[&bogus_recipient]
// -> HashMap Index panic: "no entry found for key" -> process abort
```
Confidence caveat: exact reachability depends on the coordinator/processor relaying `accuser`/`accused` fields unvalidated into `blame` (the `VerifyBlame` handler passes them through). The unchecked indexing itself is confirmed at crypto/dkg/pedpop/src/lib.rs:599 and crypto/dkg/pedpop/src/encryption.rs:388.
