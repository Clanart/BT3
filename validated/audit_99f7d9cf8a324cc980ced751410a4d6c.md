Based on my investigation, the closest local analog to the WatchPug `arbitraryCall()` bug is found in `CallDispatcher.sol`, which is used as a shared execution sandbox by `IntentGatewayV2`/`IntentsBase` for composable order fulfillment.

### Title
Unrestricted, callerless `CallDispatcher.dispatch()` lets anyone drain residual/dust token balances left by other users' orders - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public function with **no caller restriction and no check on the `to` target**, executing arbitrary calldata using the dispatcher's own token balance and native ETH. `IntentGatewayV2`/`IntentsBase` use this single, shared `CallDispatcher` instance (`_params.dispatcher`) as a transient holding contract during `placeOrder` (predispatch) and order fulfillment (`_execute`), transferring user/solver tokens into it before invoking arbitrary solver-supplied calldata (`order.predispatch.call` / `order.output.call`) and then sweeping back only the tokens explicitly listed in `order.inputs`/`order.output.assets`.

### Finding Description [1](#0-0) 

`dispatch()` has zero access control — any external account can call it directly, bypassing `IntentGatewayV2` entirely, and force the dispatcher to execute arbitrary `Call{to, value, data}` entries using whatever ETH/ERC-20 balance currently sits in the `CallDispatcher` contract.

The dispatcher is used as a shared execution sandbox in the intents flow: [2](#0-1) [3](#0-2) 

In both `placeOrder`'s predispatch phase and `_execute`'s output-fulfillment phase, tokens are pushed into the dispatcher, arbitrary solver/user-supplied calldata is executed via `ICallDispatcher(dispatcher).dispatch(...)`, and only tokens matching the order's declared `inputs`/`output.assets` list are swept back out. The code comment itself acknowledges the gap: "any residual token balances left on the dispatcher are swept back... and accounted for as protocol dust" — meaning dust/residual balances are an expected occurrence, not an edge case that's fully eliminated.

Because the dispatcher is a single persistent contract shared across all orders and all chains it's deployed on, any balance that is not captured by the narrow sweep logic (e.g., extra tokens obtained by a DEX/lending call routed through arbitrary calldata, fee-on-transfer remnants, or partial execution failures) remains sitting in the `CallDispatcher`'s balance indefinitely. Since `dispatch()` has no caller restriction, **any unrelated third party** can then call `CallDispatcher.dispatch()` directly with a `Call` that transfers that stranded ERC-20/ETH balance to themselves — this is functionally identical to the Locke `arbitraryCall()` primitive: an unrestricted arbitrary-call surface that doesn't validate whether the target/asset in play still belongs to (or is escrowed for) another party.

### Impact Explanation
Any dust, rounding remainder, fee-on-transfer shortfall, or unaccounted asset acquired through arbitrary order calldata that is not swept in the same transaction becomes permanently and unconditionally stealable by any address, since `CallDispatcher.dispatch()` enforces no ownership, no caller allowlist, and no check that `to`/`data` doesn't move funds belonging to another party's pending or completed order. This is a direct "loss of funds to non-rightful beneficiary" scenario matching the bounty's fund-custody impact class.

### Likelihood Explanation
The attack requires no privileged role, no relayer/prover compromise, and no front-running — it is a plain unprivileged call to a public function (`CallDispatcher.dispatch()`) whenever the shared dispatcher happens to hold an uncaptured balance. Given fee-on-transfer tokens, DEX slippage, or any output-call flow that acquires assets outside the declared `output.assets` set, non-zero balances are a realistic and recurring occurrence rather than a purely theoretical edge case.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the authorized `IntentGatewayV2`/`IntentsBase` contract(s) (e.g., an `onlyAuthorizedCaller` modifier set at construction), and additionally enforce that the sweep logic in `_execute`/`placeOrder` fully drains the dispatcher's balance for every token touched by the arbitrary calldata (not just tokens declared in `order.inputs`/`order.output.assets`), so no exploitable residual balance can ever persist between transactions.

### Proof of Concept
1. A solver fills an order whose `order.output.call` routes through a DEX/lending call that, due to slippage or an extra reward token, leaves an ERC-20 balance in the shared `CallDispatcher` that is not part of `order.output.assets` (so it's never included in `sweepCalls`). [4](#0-3) 
2. That token balance now sits in `CallDispatcher`, unclaimed, awaiting the next `IntentGatewayV2` interaction to eventually sweep it — but nothing enforces that happens promptly, and no code path revokes third-party access in the meantime.
3. Any attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: strandedToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly. [5](#0-4) 
4. Since `dispatch()` performs no caller check, the call succeeds and the stranded balance — which rightfully belonged to the order's escrow/dust-collection flow — is transferred to the attacker instead of the gateway/beneficiary.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
