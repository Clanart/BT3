### Title
Sole re-locker can sweep 100% of queued mWOMSVBaseRewarder rewards via permissionless `donateRewards(0, ...)` right after `totalStaked()` hits zero - (`rewards/mWOMSVBaseRewarder.sol`)

### Summary
When `totalStaked()` (total supply of `mWomSV`) drops to zero, any reward provisioned through `_provisionReward`/`_queueNewRewardsWithoutTransfer` is parked in `rewardInfo.queuedRewards` instead of being distributed. An unprivileged attacker who becomes the sole `mWomSV` locker right after that zero-supply window can call the permissionless `donateRewards(0, _rewardToken)` to trigger `_provisionReward`, which flushes the entire `queuedRewards` balance into `rewardPerTokenStored` divided by `totalStaked()`, at that moment equal to the attacker's own dust stake. The attacker then claims the whole pot via `getReward`.

### Finding Description
`_provisionReward` and `_queueNewRewardsWithoutTransfer` share the same branch: [1](#0-0) 

If `totalStaked() == 0` the incoming reward amount is simply added to `rewardInfo.queuedRewards` and `rewardPerTokenStored` is left untouched. It is only converted into `rewardPerTokenStored` on the *next* call to `_provisionReward`/`_queueNewRewardsWithoutTransfer`, and that conversion divides the whole accumulated `queuedRewards` (plus any new amount) by whatever `totalStaked()` is at that instant: [2](#0-1) 

`donateRewards` is a fully permissionless, unprivileged entry point that calls `_provisionReward` for any already-registered reward token, with no restriction on the amount (including `0`): [3](#0-2) 

Exploit flow:
1. `mWomSV` (`stakingToken`) organically reaches `totalSupply() == 0` (all lockers finish unlocking) — this is normal, non-privileged churn, not misconfiguration. `totalStaked()` reads directly from `mWOMSV.totalSupply()`: [4](#0-3) .
2. At some point while `totalStaked() == 0`, a manager (e.g. `WombatStaking`/`rewardManager`) sends normal periodic bonus rewards via `queueNewRewards`, which lands entirely in `rewardInfo.queuedRewards` per the branch above. This is routine protocol operation, not an admin exploit.
3. The attacker observes `totalStaked() == 0` and `queuedRewards > 0`, then calls `mWomSV.lock(1)` (or `lockFor`), becoming the sole locker with `totalStaked() == 1`.
4. The attacker immediately calls `donateRewards(0, _rewardToken)` on `mWOMSVBaseRewarder`. This invokes `_provisionReward(0, _rewardToken)` with `totalStaked() == 1`, hitting the `else` branch: `_amountReward (0) += queuedRewards; rewardInfo.rewardPerTokenStored += _amountReward * 1e18 / 1`. The entire queued pot is now credited at a rate that makes the attacker's 1-wei stake worth 100% of it.
5. The attacker calls `MasterMagpie`'s claim path which invokes `getReward(_account, _receiver)` (`onlyMasterMagpie`), which pays out the full queued amount via `_sendReward`.

Since `_calExpireForfeit` always returns `forfeitAmount == 0` (`rewardableAmount = _amount` unconditionally, so `_amount - rewardableAmount == 0`), no clawback/forfeit mechanism reduces the payout — the attacker receives the full swept amount with no penalty: [5](#0-4) 

No modifier (`onlyManager`, `nonReentrant`, pause) prevents this: `donateRewards` has no access control on caller, and `lock`/`lockFor` on `mWomSV` are open to any address: [6](#0-5) 

### Impact Explanation
This is theft of unclaimed/queued yield belonging to other, prior or future, `mWomSV` lockers. An attacker with negligible capital (1 wei of `mWOM`/`mWomSV`) can capture the entirety of a reward pool's queued balance the moment `totalStaked()` transiently reaches zero, concentrating funds meant to be shared pro-rata among all stakers into a single depositor. This matches the "theft or permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
- Requires `totalStaked()` (i.e., `mWomSV.totalSupply()`) to hit zero — plausible for a low-TVL or newly-launched pool, or transiently between locker exits and re-entries; no admin action needed.
- Requires `queuedRewards > 0` at that moment, which accrues naturally from routine `queueNewRewards` calls by the reward manager (WombatStaking distributing bonus tokens) while total stake is zero.
- The attacker's actions (`lock(1)`, `donateRewards(0, token)`, claim) are all permissionless, cheap, and repeatable each time the zero-total-staked window recurs.
- Capital needed: trivial (dust amount of `mWOM`).

### Recommendation
Do not allow `rewardPerTokenStored` to be updated by an arbitrary, uninvolved caller with `totalStaked()` reduced to a dust value right after a zero-supply window. Options:
- Snapshot/track a minimum bonding period or minimum stake threshold before a locker can receive a share of previously-queued rewards (e.g., pro-rate queued rewards based on time-weighted stake rather than instantaneous `totalStaked()`).
- Restrict `donateRewards` (and any code path that can trigger `_provisionReward`/queued-rewards flush) to be non-front-runnable by requiring the flush to be time-averaged or only triggerable by governance/manager with rate limits.
- Alternatively, when `totalStaked()` was previously zero and just became non-zero, delay conversion of `queuedRewards` into `rewardPerTokenStored` until a cool-down/vesting period has elapsed, or distribute queued rewards streaming over time instead of instantaneously to whoever is first to stake.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, mock `masterMagpie`, and a mock reward manager; register a reward token in the rewarder.
2. Simulate normal operation: multiple users `lock()` mWOM, then all `startUnlock`/complete cooldown and fully exit so `mWomSV.totalSupply() == 0` (`totalStaked() == 0`).
3. As the reward manager, call `queueNewRewards(X, rewardToken)` while `totalStaked() == 0`; assert `rewards[rewardToken].queuedRewards == X` and `rewardPerTokenStored` unchanged.
4. As attacker (fresh unprivileged EOA), call `mWomSV.lock(1)`; assert `totalStaked() == 1`.
5. As attacker, call `mWOMSVBaseRewarder.donateRewards(0, rewardToken)`; assert `rewards[rewardToken].rewardPerTokenStored` jumps to reflect the full `X` divided by `1`, and `queuedRewards` resets to `0`.
6. Trigger `getReward(attacker, attacker)` through the mock `masterMagpie`; assert the attacker's reward token balance increases by the full `X`, while no other locker (who contributed to accruing `X`) receives anything.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
