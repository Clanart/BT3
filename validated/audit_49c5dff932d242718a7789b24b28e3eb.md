Based on my research, the strongest local analog to the reported "fee accounting ordering" bug class is in the relayer fee-withdrawal flow in `pallet-ismp-relayer`, where the accrued fee balance is read and used to build a cross-chain payout instruction, but the code I was able to retrieve does not show the balance being zeroed atomically with that read before the outbound dispatch.

### Title
Relayer fee balance read before zeroing enables repeated/duplicate withdrawal dispatches - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
The external report's core defect is: a balance/accounting value is snapshotted or used to authorize an action *before* the corresponding debit is applied, so the same balance can be consumed more than once (or the two operations get out of sync and cause faulty accounting). The direct Hyperbridge analog is `pallet_ismp_relayer::withdrawal::Pallet::withdraw`, which reads the relayer's accrued fee balance and immediately dispatches an ISMP POST instructing a destination `HostManager` to disburse `available_amount`, using the pre-dispatch balance as the payout amount.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  performs the following sequence:
1. Verifies the signature over `(nonce, dest_chain, beneficiary)`.
2. Reads `available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone())`.
3. Checks `available_amount >= min_withdrawal_amount`.
4. Increments the per-relayer `Nonce`.
5. Builds and dispatches (in the code shown, lines [2](#0-1) ) a cross-chain `WithdrawParams`/`WithdrawalRequest` message carrying `available_amount` to the destination chain's `HostManager`, which will unconditionally transfer that amount to the beneficiary once delivered (see `EvmHost.withdraw` at [3](#0-2)  and the substrate `HyperbridgeWithdrawalModule::on_accept` at [4](#0-3) , both of which pay out unconditionally based solely on the amount encoded in the incoming message).

The module-level doc comment explicitly states the intended invariant: "The `Fees` entry is zeroed so the same balance cannot be withdrawn twice" ( [5](#0-4) ). However, in the portion of `withdraw()` I was able to inspect (through line 160), there is no `Fees::<T>::insert(...)` / `mutate` call that zeroes or decrements the `Fees` storage entry prior to, or atomically with, building the dispatch payload — only `Nonce` is mutated. The `Nonce` bump does not protect against duplicate payout because the relayer holds the private key and can simply produce a *new* signature over the incremented nonce and call `withdraw` again immediately; each call independently re-reads the same (still-unzeroed) `available_amount` from `Fees` and would dispatch another full-value payout request to the destination `HostManager`.

This mirrors the external report's root cause exactly: an amount is derived from a balance record that is consumed (used to authorize a transfer) before/without being decremented in the same atomic step, so a party who controls the trigger (here, the relayer, an unprivileged-with-respect-to-this-invariant caller who legitimately owns the fee balance but should only be able to claim it once) can obtain the value multiple times.

### Impact Explanation
If the `Fees` balance is not zeroed synchronously with the withdrawal dispatch, a relayer can trigger multiple independent ISMP `WithdrawRelayerFees`/`WithdrawParams` dispatches for the same accrued balance before any of them lands (dispatch is only queued here; settlement happens asynchronously on the destination chain, per the docs at [6](#0-5) ). Each delivered message causes an unconditional payout on the destination `HostManager`/`EvmHost.withdraw` or the substrate `HyperbridgeWithdrawalModule`, resulting in double- or multi-claiming of the same relayer revenue — direct loss of protocol/bridge funds, matching the bounty's "double-claim/double-settlement" and "stealing or loss of funds" categories.

### Likelihood Explanation
This requires only an unprivileged relayer account with a legitimately-accrued (even small) fee balance — no malicious peer, prover, or governance actor is needed, satisfying the "public entrypoint, unprivileged attacker" requirement. However, I was not able to view the full body of `withdraw()` past line 160 within the available tool budget, so I cannot rule out that the zeroing occurs later in the function (e.g., immediately after the `match` block that builds `(to, body)`) or that some other mutex/lock prevents concurrent execution. This is the key uncertainty: **the finding is contingent on confirming that no `Fees::<T>::insert(dest_chain, address, 0.into())` (or equivalent decrement) executes before or atomically with the dispatch call.** If such a reset exists later in the same function body (making the whole read-decrement-dispatch sequence atomic within one extrinsic), the vulnerability does not exist as described and would need to be re-scoped to a narrower race (e.g., re-entrancy via the dispatcher callback, if any).

### Recommendation
- Zero (or decrement by `available_amount`) the `Fees::<T>` storage entry for `(dest_chain, address)` immediately after reading `available_amount` and before performing any external dispatch, within the same atomic extrinsic execution.
- Consider using `Fees::<T>::mutate` with a `take`-style pattern (read-and-reset in one storage access) rather than a separate `get` followed by later mutation, to eliminate any window where the same balance could be read twice.
- Add a regression test that calls `withdraw` twice in immediate succession (with two validly-signed, nonce-incremented payloads) for the same `dest_chain` and asserts the second call fails with `NotEnoughBalance` because `Fees` was already reset by the first call.

### Proof of Concept
1. Relayer accrues fee balance `X` for `dest_chain = D` via the normal accumulation flow (`pallet_ismp_relayer::accumulate`).
2. Relayer signs `WithdrawalInputData { dest_chain: D, beneficiary: B, nonce: n }` and calls `withdraw`. This reads `Fees::<T>::get(D, addr) == X`, passes the minimum-balance check, bumps `Nonce` to `n+1`, and dispatches an ISMP POST to `D`'s `HostManager` requesting payout of `X` to `B`.
3. Before the first dispatch is delivered/settled on `D` (an asynchronous, potentially multi-block process per [6](#0-5) ), the relayer signs a second `WithdrawalInputData { dest_chain: D, beneficiary: B, nonce: n+1 }` and calls `withdraw` again. If `Fees` was not reset by step 2, this again reads `Fees::<T>::get(D, addr) == X`, passes the check, and dispatches a second POST requesting another payout of `X`.
4. Both messages are eventually delivered to `D`'s `HostManager`/`EvmHost.withdraw`, each of which unconditionally transfers `X` to `B` ( [3](#0-2) ), resulting in `2X` paid out for a single accrued balance of `X`.

**Uncertainty note:** Steps 2–4 assume the `Fees` reset does not occur elsewhere in `withdraw()` beyond what I could retrieve (lines 63–160 of `modules/pallets/relayer/src/withdrawal.rs`). This should be verified against the complete function body before treating this as a confirmed, exploitable finding.

```text
## Withdrawing Fees

Tesseract maintains a local sqlite database where it keeps track of successfully delivered messages. The withdrawal process happens in two phases, the first phase is the fee accumulation on hyperbridge, then withdrawal on any of the connected chains.
In the fee accumulation phase, tesseract submits state proofs of messages all delivered to hyperbridge. If the proof verification is successful, the total amount of unclaimed fees for the relayer address is updated onchain. Next, the relayer can submit a withdrawal transaction to hyperbridge. This initiates potentially multiple ISMP requests to any chain where it has unclaimed fees, that instructs the Hyperbridge contract to credit the relayer their owed funds. This request will not timeout, allowing it to be submitted to the destination chain at any time.

### Accumulating fees

Fee accumulation runs automatically in the background. Every successful
outbound submit produces delivery receipts that flow into a per-chain
accumulation task; each task submits proofs of delivery to Hyperbridge
and increments the relayer's unclaimed-fee balance on-chain. Receipts
are persisted to the local database first so a crash between submit
and accumulation doesn't lose the reward.

> The legacy standalone `tesseract --accumulate-fees` subcommand no
> longer exists in the consolidated relayer — accumulation is part of
> the long-running process.

### Initiating withdrawals

To initiate a withdrawal from hyperbridge, a relayer needs to submit a transaction to hyperbridge which triggers the withdrawal request. This extrinsic is unsigned and will not require any native tokens for execution fees. Once the extrinsic is executed, hyperbridge dispatches a POST request that when executed on its destination, will provide the relayer with the fees they've accrued. The relayer account must have sufficient funds to deliver this request to its destination chain.
```
