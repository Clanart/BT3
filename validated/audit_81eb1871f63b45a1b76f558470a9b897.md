### Title
Tokenfactory denom creator can self-declare arbitrary `decimals` used verbatim by the native ERC20 pointer, causing amount-scale corruption for any EVM contract composing with the pointer - ([File: precompiles/pointer/pointer.go])

### Summary
Any tokenfactory denom admin can call `MsgSetDenomMetadata` to set an arbitrary `DenomUnits[].Exponent` for their own denom (bank/tokenfactory only validates internal consistency of the metadata, not truthfulness of the decimals value). When anyone subsequently calls the pointer precompile's `addNativePointer`, the resulting ERC20 pointer contract's `decimals()` is taken directly from that self-declared, unvalidated exponent and hard-baked into the pointer's constructor — with no adjustment or reconciliation against the token's real value or actual on-chain unit granularity (which is always integer usei-equivalent amounts with no fractional smaller unit). This is the same bug class as the reported `_replenishPaymentBalance` issue: a value/decimal assumption is fixed at pointer-creation time and never re-derived or checked against the true unit scale of the underlying asset, so any downstream contract that composes with the ERC20 pointer (AMMs, lending markets, price-oracle-based valuators, wallets) will misinterpret transferred `amount` values by the wrong power-of-ten scale.

### Finding Description
`AddNative` in the pointer precompile fetches `bankKeeper.GetDenomMetaData` for a token, then blindly walks `metadata.DenomUnits` and takes the maximum `Exponent` as `decimals`, using it as-is to construct the ERC20 pointer: [1](#0-0) 

The metadata is set via `x/tokenfactory` `MsgSetDenomMetadata`, whose only checks are: the sender is the token's tokenfactory admin, and `msg.Metadata.Validate()` (a generic Cosmos SDK bank-metadata sanity check for well-formedness), plus that the denom belongs to a tokenfactory-created denom: [2](#0-1) 

Nothing checks that the declared `Exponent` corresponds to how the denom is actually handled in the bank ledger. Tokenfactory-created denoms (like all bank denoms other than usei) are integer-only, single-unit balances in `x/bank` — there is no sub-usei-equivalent fractional unit backing them, unlike `usei` which genuinely has a defined wei sub-unit handled specially via `SplitUseiWeiAmount`/`UseiToSweiMultiplier`: [3](#0-2) 

The native-token ERC20 pointer's `send`/transfer path passes the raw `amount` argument straight through to `bank.MsgSend` with no rescaling: [4](#0-3) 

So the pointer's on-chain transfer semantics are always "1 raw unit = 1 bank unit", while its advertised `decimals()` (and thus its ERC20-interface-implied value-per-unit) can be set to anything the tokenfactory admin wants (e.g., 18 instead of the true 0/6), independent of the real token's granularity. This exactly mirrors the reported bug's root cause: a payment/value parameter (there, "pack cost"; here, "decimals/value scale") is fixed based on an assumption about the token that is never validated or dynamically reconciled, and any change in the underlying token's real characteristics silently breaks downstream value calculations.

### Impact Explanation
Any EVM contract that composes with a native-token ERC20 pointer and relies on `decimals()` to convert `balanceOf`/transfer `amount` into a human/USD value (AMM pools computing price ratios, lending protocols computing collateral value via `amount * price / 10**decimals`, as seen in the codebase's own `LendingFixture.sol`/`DeterministicPriceOracle` patterns), will compute values off by up to 10^18, since the tokenfactory admin fully controls the declared `decimals` independent of the real value of the token. This can enable fund-loss exploits: e.g., a malicious tokenfactory admin creates a denom, declares 18 decimals (making 1 raw-unit transfer look like 10^-18 of a "full" token to naive integrators, or the reverse — declaring 0 decimals for a token meant to look like a large-value integer token) to manipulate any protocol that prices the pointer token by its advertised decimals, extracting value from counterparties. This satisfies "unauthorized transfer via precompile or pointer" / "fund loss" in the validation criteria.

### Likelihood Explanation
Reachable by any unprivileged tokenfactory denom creator/admin and any EVM contract deployer/user who registers or interacts with a native pointer — no governance or validator collusion required. `CreateDenom` and `SetDenomMetadata` are open, permissionless (create) / self-administered (set-metadata) message types, and `addNativePointer` on the pointer precompile is callable by anyone once metadata exists.

### Recommendation
Do not let denom creators/admins freely choose an ERC20 `decimals` value that is disconnected from how the bank module actually accounts the token. Either (a) hardcode `decimals = 0` for all native/tokenfactory pointer tokens (matching how bank amounts are always integral, exactly as the bank precompile itself already documents/does for `decimals()`), or (b) validate that the declared exponent is consistent with genuine, chain-enforced sub-unit conversion logic (analogous to the usei/wei split) before it can be used to construct a pointer, and disallow re-declaring metadata after a pointer has already been created for that denom.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/<attacker>/foo`.
2. Attacker calls `MsgSetDenomMetadata` declaring `DenomUnits` with `Exponent: 18` for `foo` (a value with no real backing/verification), passing `Validate()` and admin checks in `x/tokenfactory/keeper/msg_server.go`.
3. Anyone calls pointer precompile `addNativePointer("factory/<attacker>/foo")`; `AddNative` reads the declared exponent 18 and constructs an ERC20 pointer contract advertising `decimals() == 18`.
4. A DeFi contract (AMM/lending market) that composes with the pointer computes value as `amount / 10**decimals` assuming an 18-decimal ERC20 semantics, while the underlying bank ledger moves the token 1:1 per raw unit with no fractional component — creating a 10^18 mispricing that the attacker can exploit for fund extraction, exactly analogous to the reported "cost of packs not adjusting to new token" issue.

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
