### Title
Stale line-index diff selection can silently commit unintended file content when the working file changes between selection and commit - (File: app/src/lib/patch-formatter.ts)

### Summary
GitHub Desktop lets users select individual lines/hunks of a modified file for a partial commit. That selection (`DiffSelection`) is stored purely as a set of **absolute line indices**, not tied to the actual line content or a hash of the diff it was computed from. If the working-directory file is modified on disk (e.g., by another process, a build tool, an editor autosave, or a malicious pre-checkout/post-checkout hook triggered by an attacker-controlled repository) between the time the user visually selects lines and the time the commit is executed, Desktop reuses the old line-index selection against a **freshly regenerated diff**, both when merging repository status (`updateChangedFiles`) and when building the actual git patch (`applyPatchToIndex`/`formatPatch`). This mirrors the FraxSwap bug class: internal bookkeeping (the line-index selection) is not re-validated against the real, current state (the on-disk file/diff), so the operation (committing) proceeds using stale accounting and can silently include/exclude the wrong lines.

### Finding Description
- `DiffSelection` selection state is attached to a `WorkingDirectoryFileChange` and is defined purely by numeric line positions in the diff, with no linkage to line content or diff hash.
- On every repository status refresh, `updateChangedFiles` takes the *existing* selection object and blindly re-applies it (`file.withSelection(existingFile.selection)`) onto the newly parsed file from git status, with no check that the new diff's hunk layout matches the old one [1](#0-0) .
- When the user commits, `_commitIncludedChanges` uses whatever selection is currently on the `WorkingDirectoryFileChange` objects in `repositoryStateCache` [4](#0-3) , which then flows into `stageFiles` → `applyPatchToIndex`.
- `applyPatchToIndex` re-fetches the working directory diff at commit time (`getWorkingDirectoryDiff`) — this is a *different* diff object than the one that was originally rendered to the user when they made their line selection — and hands it to `formatPatch` together with the (unchanged) `file.selection` [2](#0-1) .
- `formatPatch` walks the new diff's hunks and simply asks `file.selection.isSelected(absoluteIndex)` for each line by numeric index, with an explicit warning in its own doc comment that this method assumes the "file" and "selection" are still self-consistent [5](#0-4) .
- There is no guard comparing the diff hunks used to build the original selection against the diff hunks used to build the final patch. If the file has changed (lines inserted/removed above the selected range, or the selected lines themselves changed), the same absolute indices now point at different, unrelated lines — yet the code proceeds to build a patch and apply it to the index without error.
- The corrupted value is the effective content committed to the repository: it can differ from what is displayed/intended in the UI, and depending on which lines shift, `git apply` might either succeed silently (producing a commit with unintended content) or fail unpredictably.

### Impact Explanation
This allows a "silent corruption of what the user commits" — one of the explicitly valid impact categories. In a realistic attacker-controlled scenario (e.g., a malicious `post-checkout`/`post-merge` hook in a cloned repository, or another tool watching/mutating files in the working directory while the user reviews a diff and stages partial changes), the file content on disk can be altered between when the user picks lines to include and when Desktop actually builds the patch. Because Desktop's selection model is purely index-based and never invalidated against a "hunk fingerprint" or content check, the final commit can include lines the user never intended to commit (potential secret/credential leakage) or exclude lines the user meant to include, all without any warning to the user.

### Likelihood Explanation
Requires the attacker to be able to modify tracked files in the working directory between the user's diff review/selection and the click of "Commit" — for example via a git hook shipped in a cloned/fetched malicious repository, or a background process the attacker convinces the user to run against the repo. This satisfies the report's threat model ("attacker controls a cloned/fetched repository ... git remote/proxy response") without requiring local/physical access, admin rights, or pre-existing host compromise. The timing window is realistic since Desktop's diff review UI is asynchronous and there's no re-diff/consistency check gating the final `git apply` step.

### Recommendation
- Before applying `formatPatch`/`applyPatchToIndex`, re-fetch the diff and verify it matches (e.g., via a content hash or hunk fingerprint) the diff that was current when the user made the line selection; if it differs, invalidate the selection and force the user to re-review before committing.
- In `updateChangedFiles`, avoid blindly carrying over `existingFile.selection` across status refreshes when the underlying diff/hunks have structurally changed — clear or remap the selection instead.
- Consider storing selections keyed by line content/context (or diff hash) rather than pure numeric indices, so stale selections are detected rather than silently reused.

### Proof of Concept
1. Modify a tracked text file with several distinct sections, open Desktop, and in the "Changes" diff view select only lines from the second hunk for a partial commit (leaving the first hunk unselected).
2. Before clicking "Commit", have an external process (e.g., a `post-checkout`/file-watcher script, or simply another editor process race) rewrite the file such that lines are inserted/removed above the previously-selected hunk (changing absolute line numbering) while keeping the file still "modified" relative to HEAD.
3. Click "Commit". Trace through: `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex`, which calls `getWorkingDirectoryDiff` again [6](#0-5)  — a diff object that no longer matches what generated the original selection indices — then `formatPatch` builds the patch using the stale index-based selection [7](#0-6) .
4. Inspect the resulting commit: the actual staged/committed lines correspond to a different section of the file than what the user visually selected in the UI, demonstrating silent commit-content corruption.

Note: I was not able to execute this scenario in a live Desktop instance (no filesystem/terminal access in this environment) — the finding is based on static code-path analysis of `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, and `app/src/lib/stores/updates/changes-state.ts`. A background Devin session with repo access would be needed to build and run a concrete reproduction to confirm the exact `git apply` behavior (silent success vs. hunk-context failure) for various shift patterns.
