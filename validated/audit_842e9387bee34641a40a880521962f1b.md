### Title
Sub-dust deposits are credited as spendable received outputs, locking funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report concerns a bridge crediting received amounts after scaling them down to zero, locking funds on the source chain. The closest reachable analog in Serai is the `Scanner`: `Scanner::scan_transaction` treats *every* transaction output paying to a registered script as a `ReceivedOutput`, regardless of value. An unprivileged party can send a sub-dust (1–545 sat) P2TR output to a Serai deposit key; the scanner reports it as received value, but `SignableTransaction::new` / Bitcoin relay policy make such an output uneconomical or impossible to spend — the "received" funds are effectively locked, and any attempt to spend them costs more in fees than they are worth.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199–214) matches only on `output.script_pubkey`:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

There is no lower bound on `output.value`. A 1-sat P2TR output is consensus-valid (non-standard for relay, but standard enough to be mined, and anyone can pay a miner directly). Once scanned, `ReceivedOutput` flows into `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150–256), which *rejects* payments below `DUST = 546` (send.rs:165–169) and requires `input_sat >= payment_sat + needed_fee` with a minimum relay fee check (send.rs:211–221). A dust-valued input can therefore:

- only ever be consumed as fee/change fodder, at a marginal cost of ~68 vbytes of weight for ≤546 sats of value — frequently a net loss;
- never fund a payment on its own, since any payment it could pay for is rejected as `DustPayment`.

This mirrors the report exactly: the receiving side accepts denominations the spending side refuses to move, creating permanently/uneconomically locked "received" balance. Unlike the fixed Teleporter code (destination registration so the source knows the minimum denomination), the Serai scanner has no denomination awareness at all — no minimum-value gate exists between `scan_transaction` and crediting.

### Impact Explanation
Anyone can dust the bridge/deposit keys at trivial cost (a few hundred sats plus a fee). Each dust output is reported by `scan_block`/`scan_transaction` as a received output backed by a valid scalar offset. If downstream accounting credits these as deposits, attackers can inflate perceived received amounts or force the wallet to either (a) leave outputs unspendable forever (accounting imbalance, exactly the report's consequence) or (b) burn fee value spending them. At scale (many dust outputs) this degrades the wallet's usable balance versus its reported balance.

### Likelihood Explanation
Fully unprivileged and cheap: the attacker only needs the well-known deposit script (derived from the public group key via `Scanner::new`/`register_offset`) and a standard Bitcoin transaction. No validator collusion, no key material, no malformed encoding required — the attack uses only "Bitcoin transactions they send," which is explicitly in scope.

### Recommendation
Reject or quarantine outputs below `DUST` in `Scanner::scan_transaction` (e.g., `if output.value.to_sat() < DUST { continue }`), or surface value so callers can exclude uneconomical outputs before crediting them, mirroring the fix direction of the upstream report (making the receiving side aware of the minimum spendable denomination before recognizing the transfer).

### Proof of Concept
1. Derive the deposit script for the wallet key: `p2tr_script_buf(key)` (wallet/mod.rs:80–86).
2. Broadcast a transaction containing `TxOut { value: Amount::from_sat(1), script_pubkey: deposit_script }`.
3. `Scanner::scan_transaction(&tx)` returns a `ReceivedOutput` with `value() == 1` (wallet/mod.rs:199–214, 116–118).
4. Pass the output to `SignableTransaction::new`: the only way to move its value is as fee; any payment ≤545 sats errors with `TransactionError::DustPayment` (send.rs:165–169). The 1-sat "received" fund is permanently locked — identical in effect to tokens scaled to zero on the destination chain in the original report.
