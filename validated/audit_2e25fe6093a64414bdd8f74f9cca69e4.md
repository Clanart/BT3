### Title
Unvalidated participant indices in PedPoP blame handling cause panic and abort of the DKG - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The Carapace report describes a public function (`expireProtection`) that performs an unauthenticated state transition with caller-supplied indexes, letting any party abort valid positions and DoS the system. The analog in Serai is `BlameMachine::blame` / `blame_internal` in PedPoP: a `pub` API that takes fully caller-controlled `sender`/`recipient` `Participant` values and indexes `HashMap`s with them, panicking instead of erroring when the index is not a protocol participant. Any party able to feed a blame accusation into the machine can crash the honest node's DKG finalization.

### Finding Description
`BlameMachine::blame` is `pub` and forwards `sender` and `recipient` verbatim into `blame_internal` [1](#0-0) . `blame_internal` then does two unguarded map lookups with attacker-controlled keys:

- `self.commitments[&sender]` when verifying the revealed share [2](#0-1) 
- `self.enc_keys[&decryptor]` inside `Decryption::decrypt_with_proof` when verifying the `EncryptionKeyProof`'s DLEq [3](#0-2) 

`HashMap`'s `Index` impl panics on a missing key. Neither `sender` nor `recipient` is validated against `params.all_participant_indexes()` (contrast `calculate_share`, which calls `validate_map` before indexing `self.commitments[&l]` [4](#0-3) ). `Participant` values exceeding `n` or `Participant::new(0)`-style edge indices therefore unwind with a panic rather than returning `PedPoPError`.

Like the original bug — where any caller could expire arbitrary protections because the function lacked access control and index validation — here any caller who can invoke `blame` (the API is public; its only documented precondition is that the message be "authenticated" to some sender, which does not constrain `recipient` and does not require `sender` ∈ [1, n]) can force a panic, aborting the participant's DKG.

### Impact Explanation
A panic in `blame` crashes the task handling PedPoP blame resolution. In deployments where this runs in-process (coordinator/processor), this is a reachable abort of the DKG confirmation phase: the node cannot distinguish a crafted out-of-range blame from a legitimate accusation and dies before producing `ThresholdKeys`. The result is a liveness failure of key generation / share resolution — the same "arbitrary caller forces premature/invalid state transition → DoS" shape as the original report.

### Likelihood Explanation
Requires an unprivileged party to reach the `blame` call site with a message carrying an authenticated-enough `sender` field. `blame_internal` checks the PoP and ECDH proof only *after* (or while) indexing the maps; `self.commitments[&sender]` is evaluated inside `share_verification_statements` only after the decrypt path, but `self.enc_keys[&decryptor]` is reached whenever `proof: Some(_)` is supplied with a bogus `recipient`. A single malformed accusation suffices; no threshold, collusion, or secret knowledge is needed.

### Recommendation
Validate `sender` and `recipient` against `ThresholdParams::all_participant_indexes()` at the top of `blame`/`blame_internal` (and inside `decrypt_with_proof`), returning a dedicated `PedPoPError` variant instead of indexing. Replace `map[&key]` indexing with `map.get(&key).ok_or(...)`, matching the validation pattern already used in `calculate_share`. Also replace the `assert!` on re-registration in `Decryption::register` [5](#0-4)  with an error return, since duplicate `EncryptionKeyMessage`s are similarly attacker-influenced input.

### Proof of Concept
```rust
// After an honest PedPoP run yields `blame_machine: BlameMachine<C>`,
// an attacker-controlled accusation (e.g., relayed to a coordinator/validator
// performing blame resolution) passes an out-of-set recipient:
let msg: EncryptedMessage<C, SecretShare<C::F>> = /* any well-formed message */;
let bogus_recipient = Participant::new(u16::MAX).unwrap(); // never registered
let proof = Some(EncryptionKeyProof::<C>::read(&mut proof_bytes).unwrap());

// panic: `self.enc_keys[&decryptor]` -> HashMap index on absent key
let _ = blame_machine.blame(sender, bogus_recipient, msg, proof);
```
The DLEq `verify` at `decrypt_with_proof` dereferences `self.enc_keys[&decryptor]` before any range check [6](#0-5) , and `blame_internal` similarly dereferences `self.commitments[&sender]` for an out-of-set `sender` [7](#0-6) . Either path panics, aborting the caller's DKG — an unauthenticated, unvalidated-index-triggered denial of service mirroring the original `expireProtection` finding.

Caveat: severity depends on deployment — if the integrator only ever calls `blame` with `Participant` values already filtered against the participant set (treating it as a documented precondition not fully spelled out in the doc comment), this degrades to a misuse footgun rather than a directly reachable panic. Within the library itself, the input validation is absent.
