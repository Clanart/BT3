### Title
Attacker-controlled serialized `ThresholdKeys` set the group key from the first `t` verification shares with no consistency check against the holder's secret share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts fully attacker-controlled bytes and passes them to `ThresholdKeys::new`, which derives the group key by interpolating only the first `t` entries of the supplied `verification_shares` map and never verifies that `C::generator() * secret_share == verification_shares[params.i()]` nor that the shares lie on a common polynomial. Like the vault's first depositor fixing a manipulated share price for all subsequent depositors, whoever supplies the serialized keys fixes the group key (and the effective secret) for every subsequent `view`/`sign`/`recover` operation. The holder's real DKG secret is never consulted.

### Finding Description
`ThresholdKeys::new` computes the group key as the interpolation of `verification_shares[1] ..= verification_shares[t]` (`crypto/dkg/src/lib.rs` L376-378) and stores the caller-supplied `secret_share` without any binding between the two. `ThresholdKeys::read` (L574-631) reads `t`, `n`, `i`, an interpolation mode, the secret share scalar, and all `n` verification shares straight from the reader and calls `ThresholdKeys::new` — the only validations are count/index checks (L355-365) and `t == n` for `Constant` interpolation.

An attacker who can feed bytes to `ThresholdKeys::read` therefore supplies:
- `secret_share = s'` (a scalar the attacker picks),
- `verification_shares = { s'·G, y_2·G, ..., y_n·G }` chosen so the interpolation over `1..=t` equals a target key `K·G` whose discrete log the attacker knows.

`new` accepts this and returns `ThresholdKeys` whose `group_key()` is `K·G` and whose `secret_share` is `s'`. Every later operation uses these attacker-set "base rates": `view(included)` interpolates `s'` against the forged shares (L494-521) and produces per-participant verification shares that are self-consistent with the forgery, so FROST `verify_share` checks in `complete()` pass for every signer.

### Impact Explanation
The victim is enrolled as signer `i` in a threshold set whose group key `K·G` is entirely known to the attacker. When the victim signs a message, their share `λ_i·s' + nonce` verifies cleanly against `verification_shares[i] = s'·G`, and the aggregated signature verifies under `K·G`. The attacker supplies the other `t-1` shares (they know every `y_j`), producing a valid threshold signature on any message with the victim cryptographically attributed as a participant — despite the victim's genuine secret share playing no role. This is concrete production of a valid signature under a key the victim never agreed to, derived purely from untrusted bytes passed to `ThresholdKeys::read`. Any funds, rotation decisions, or protocol messages gated on that multisig's signature can be authored by the attacker with the victim's apparent consent.

### Likelihood Explanation
`ThresholdKeys::read`/`serialize` exist precisely for persisting and transporting key material; any path where serialized keys are restored from an untrusted or corrupted source (backups, replication, handover between nodes) is exposed. The attack needs no cooperation from other honest participants — all `n` verification shares come from the same byte stream. Requirements: an attacker-controlled or tampered serialization reaches a signer. Medium likelihood, Medium-High impact.

### Recommendation
In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[params.i()]` and reject otherwise. Additionally, when reconstructing via `read`, verify the map's internal consistency — e.g., check that interpolating a second disjoint `t`-subset (or all `n` shares) yields the same `group_key`, or attach/verify a proof/committed digest of the verification-share set produced at DKG time so that deserialized shares can't be silently substituted. `recover_key` already performs a post-hoc `C::generator() * res == group_key` check (`crypto/dkg/recovery/src/lib.rs` L80-82); the same sanity must be enforced at construction/deserialization.

### Proof of Concept
1. Attacker picks scalar `k` and sets target group key `Y = k·G`. For a `t`-of-`n` victim at index `i`, attacker picks a degree-`t-1` polynomial `f` with `f(0) = k`, sets `s' = f(i)`, `Y_j = f(j)·G` for `j = 1..=n`.
2. Attacker serializes via `ThresholdKeys::write` layout (or crafts bytes): `C::ID`, `t`, `n`, `i`, `Interpolation::Lagrange` (tag `1`), `s'`, then `Y_1 ..= Y_n`.
3. Victim deserializes with `ThresholdKeys::<C>::read`. `new` computes `group_key = Σ_{j=1..=t} Y_j·λ_j(1..=t) = f(0)·G = k·G` — accepted with no error.
4. Attacker runs a FROST session with the victim and `t-1` keys of their own (`s_j = f(j)`). The victim's `view()` yields secret share `λ_i·s'`; each share passes `verify_share` since `s'·G = Y_i`.
5. `complete()` outputs a valid Schnorr signature `(R, s)` under group key `k·G` naming the victim's `Participant` index — a signature the victim produced for a key controlled entirely by the attacker.
