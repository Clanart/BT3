### Title
PedPoP accepts identity ephemeral encryption keys, publicly exposing victim secret shares - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`EncryptedMessage` accepts the group identity as its per-message encryption key, and the attached Schnorr proof-of-possession can also use an identity nonce/signature. This makes the ECDH shared point the identity, causing the ChaCha20 cipher key to be derived from a publicly known value. A malicious DKG participant can therefore send a syntactically valid encrypted share whose plaintext is recoverable by anyone, leaking the recipient’s threshold secret share.

### Finding Description
`EncryptedMessage` contains an ephemeral public `key`, a Schnorr `pop`, and the encrypted message. During decryption, Serai queues `msg.pop` for verification against `msg.key`, computes `ecdh = msg.key * enc_key`, and derives the stream cipher from the resulting shared point. Because `msg.key` is read using `C::read_G`, the identity point is not rejected. A signature with `R = identity` and `s = 0` satisfies `R + cA - sG = 0` when `A = identity`, so a malicious sender can make the proof-of-possession valid for an identity ephemeral key.

The relevant path is:

- `EncryptedMessage::decrypt` verifies the PoP, computes `ecdh(self.enc_key, msg.key)`, and decrypts the share.
- `ecdh` is simply `public * private`, so `key = identity` makes the shared point public and fixed at identity.
- `cipher` derives a ChaCha20 key from that identity encoding and a fixed IV.
- `calculate_share` accepts the decrypted scalar if it matches the sender’s Pedersen commitments.

Since the encryption key is identity, every observer can derive the same ChaCha20 keystream and recover the secret-share bytes from the broadcast ciphertext.

### Impact Explanation
An unprivileged DKG participant can transmit an `EncryptedMessage` addressed to any victim using `key = identity`. The victim accepts and validates the share normally, while any observer can decrypt the ciphertext and obtain the victim’s secret share. If enough victim shares are exposed in this way, the threshold private key can be reconstructed and signatures can be forged under the resulting `ThresholdKeys`.

This is not prevented by the per-message PoP, because `C::read_G` accepts identity points and the Schnorr verifier’s equation permits `(R, s, A) = (0, 0, 0)`.

### Likelihood Explanation
The attack requires only control of the bytes for one outbound `EncryptedMessage` and valid Pedersen commitments/share. It requires no malformed encoding, invalid scalar, threshold collusion, leaked private key, or broken consensus. The sender can generate a normally valid secret share and then encrypt it under the identity ephemeral key, so the victim’s `calculate_share` path accepts it.

### Recommendation
Reject identity points wherever they represent public keys or ephemeral encryption keys. In particular, PedPoP should deserialize points with a variant equivalent to FROST’s `Curve::read_G`, which rejects identity, rather than the base `Ciphersuite::read_G`. This should apply to:

- `EncryptedMessage.key`
- encryption-key registration messages
- Pedersen commitment points where identity is not a legitimate coefficient commitment
- Schnorr signature nonces/public keys used for PoP verification

Additionally, explicitly reject `R = identity`, `s = 0` signatures for proof-of-possession purposes, and add a test that an encrypted share using the identity ephemeral key fails `read`/`calculate_share`.

### Proof of Concept
Conceptually, a malicious sender constructs:

```text
msg.key = identity
msg.pop = SchnorrSignature { R: identity, s: 0 }
msg.msg = share_bytes XOR ChaCha20(context || identity_bytes, fixed_iv)
```

`msg.pop` passes because:

```text
sG = 0
R + cA = 0 + c*0 = 0
```

The ECDH result is:

```text
victim_enc_key * identity = identity
```

Therefore, the ChaCha20 keystream is publicly derivable and `msg.msg` reveals the victim’s secret-share ciphertext plaintext to anyone who sees the message.
