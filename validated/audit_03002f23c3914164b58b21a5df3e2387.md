### Title
Fee/weight calculation omits the OP_RETURN data output, underestimating vbytes and fees — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts an optional `data` payload and pushes an `OP_RETURN` output onto `tx_outs` before computing the transaction weight. However, both calls to `calculate_weight_vbytes` are passed `payments` — not `tx_outs` — so the OP_RETURN output is excluded from the weight/vbyte estimate. Analogous to the reported boundary miscalculation in `calculate_pre_fee_amount`, a fee formula silently produces a wrong result for an entire class of inputs (any transaction carrying `data`), rather than the true amount.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is added to `tx_outs` (lines 194–202), yet the weight used for `needed_fee` is computed as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, and the change path again uses `payments` at line 226. Inside `calculate_weight_vbytes`, the dummy transaction's outputs are built solely from `payments` (lines 85–93), so the OP_RETURN output — up to 80 bytes of payload plus ~9+ bytes of output overhead — is never counted. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed against a vbytes value that is too small.
- The minimum-relay-fee check at line 211 compares against the underestimated `vbytes`, so it can pass even though the real serialized transaction's fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the underestimated `weight`, so a transaction that is actually non-standardly large can be accepted.
- The change computation `input_sat - (payment_sat + fee_with_change)` (line 228) grants the change output more funds than the real fee schedule warrants, meaning `fee()` (lines 138–141, defined as `sum(inputs) - sum(outputs)`) ends up below the intended `fee_per_vbyte` rate once the real (larger) transaction is serialized.

### Impact Explanation
The signed transaction pays a lower effective fee rate than requested via `fee_per_vbyte`. With the maximum 80-byte payload, the discrepancy is roughly 89–90+ weight units (~22–23 vbytes, or more depending on script length encoding) — enough to push a borderline transaction below the minimum relay feerate, producing a signed transaction that nodes will not relay, or to produce a transaction exceeding standard weight that is unrelayable. Since `make_signable_transaction`/`prepare_send` treat a constructed `SignableTransaction` as valid and immediately signable, this is a reachable incorrect-fee-calculation result rather than a rejected input.

### Likelihood Explanation
Any caller of `SignableTransaction::new` that supplies `data` triggers the miscalculation deterministically; no attacker cooperation is required. It only matters when the fee/weight margin is thin (fee rate near the relay minimum, or weight near the standard limit), so the practical severity is Medium: transactions are created that do not meet their stated fee rate, rather than loss of funds.

### Recommendation
Pass the final `tx_outs` (or an equivalent output list including the OP_RETURN output) into `calculate_weight_vbytes` — e.g., refactor it to accept `&[TxOut]` — at both the no-change and with-change call sites, so `weight`, `vbytes`, `needed_fee`, the minimum-fee check, the change amount, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)`. The resulting `needed_fee` equals `fee_per_vbyte * vbytes(without OP_RETURN)`, while `transaction()` includes the ~92-byte OP_RETURN output; the real serialized transaction therefore pays `fee_per_vbyte` over fewer vbytes than it occupies, so its actual feerate is strictly below `fee_per_vbyte` — verified by comparing `fee()` against `fee_per_vbyte * get_virtual_tx_size(tx.weight())` on the produced transaction.
