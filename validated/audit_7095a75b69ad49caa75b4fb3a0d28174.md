### Title
Silent, unconfirmed remote-URL redirection via trusted GitHub API `clone_url` field can repoint `origin` to an attacker-controlled repository - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop automatically rewrites a repository's `origin` remote URL to match whatever `clone_url` the GitHub API returns for the matched repository, with no user prompt or confirmation. This happens as part of routine, frequent background operations (repository refresh, fetch/pull/push) via `repositoryWithRefreshedGitHubRepository`, which calls `updateRemoteUrl`. [1](#0-0) [2](#0-1) 

### Finding Description
`updateRemoteUrl` decides whether to silently call `git remote set-url` by checking three conditions: (1) the URL scheme (`http`/`https` vs other) of the old and new URL match, (2) the currently configured `origin` URL still matches the repo's *previously cached* `cloneURL`, and (3) the new URL differs from the current one: [3](#0-2) 

None of these checks validate that the *destination* is actually the same GitHub repository the user originally added — they only check that the user hasn't manually diverged the remote from what Desktop last recorded. The trust boundary is entirely the API response body (`apiRepo.clone_url`), which is compared with `urlMatchesRemote`, a pure string/hostname/owner/name comparer that has no notion of repository identity (e.g. no comparison against a stable, unspoofable ID such as the repo's numeric `id`): [4](#0-3) 

This automatic remote-update logic is invoked on essentially every repository selection/refresh and every fetch/pull/push through `repositoryWithRefreshedGitHubRepository`/`withRefreshedGitHubRepository`, which are called from `_pull`, `_selectRepositoryRefreshTasks`, and other network-triggering paths: [5](#0-4) [6](#0-5) 

By contrast, when Desktop detects that a *fork's upstream* remote doesn't point where expected, it shows an explicit confirmation dialog (`UpstreamAlreadyExists`) asking the user to accept or ignore the change: [7](#0-6) 

No equivalent confirmation exists for the `origin` remote change performed by `updateRemoteUrl` — it is applied unconditionally via `gitStore.setRemoteURL`: [8](#0-7) [9](#0-8) 

If an attacker can influence the `clone_url` value returned for the matched repository (e.g. a compromised/malicious GitHub Enterprise Server that a victim has already added an account for, a MITM/rogue proxy on the API request path, or a scenario where the repository is renamed/transferred so the API now legitimately reports a different `clone_url` under attacker control), Desktop will silently reconfigure the user's local `origin` to point at that URL as long as the protocol class matches and the user hasn't manually edited the remote in the meantime. All subsequent pushes/fetches then go to the attacker-controlled destination without any indication to the user beyond the remote URL text in settings, which most users never inspect. This matches "silent corruption of what the user commits or pushes" and a git-remote/API-controlled attacker primitive.

### Impact Explanation
Silent redirection of `origin` causes the user's future commits/pushes to be sent to a repository the user did not knowingly configure, potentially exfiltrating proprietary source code, and any subsequent fetch/pull would pull attacker-supplied history/content into the user's working tree with no explicit consent. Because Desktop does not verify repository identity beyond hostname/owner/name string matching, an attacker who can influence the API's `clone_url` (through a compromised enterprise endpoint or an actual, permitted rename/transfer they control) can redirect the trust that Desktop implicitly grants to "the GitHub API told me this is the URL," bypassing the one explicit confirmation UX (`UpstreamAlreadyExists`) that exists for a very similar scenario (upstream mismatch).

### Likelihood Explanation
The mechanism triggers automatically on ordinary, frequent operations (background fetch, repository selection, pull), requiring no unusual user action, so once the API response is under attacker influence, exploitation is passive from the user's perspective. However, the primary limiting factor is how realistically an attacker can control the `clone_url` field of an *already-matched* repository object returned by a trusted `API.fromAccount(account)` call — this generally requires either a compromised/malicious GHE server the victim already trusts, a network position that can tamper with authenticated API responses, or a legitimate repository rename/transfer under attacker control. This is a plausible but not universal attacker position, which is why likelihood is assessed as moderate rather than high; I was unable to fully verify within available context whether additional integrity checks (e.g., TLS pinning, response signing) exist elsewhere in the API client stack that further reduce this likelihood.

### Recommendation
Require explicit user confirmation before rewriting the `origin` remote URL in `updateRemoteUrl`, mirroring the existing `UpstreamAlreadyExists` dialog UX. Additionally, strengthen the identity check beyond `urlMatchesRemote`'s hostname/owner/name string comparison by validating against a stable repository identifier (e.g., the API repository's numeric `id`, cached from the original association) before treating a `clone_url` change as a legitimate rename rather than a redirection.

### Proof of Concept
Conceptual sequence (I could not execute this against a live Desktop instance — this is derived purely from the code paths cited above):
1. User adds a GitHub Enterprise (or GitHub.com-via-MITM-proxy) account and clones/opens a repository whose `origin` matches the stored `gitHubRepository.cloneURL`.
2. The attacker controls or intercepts the `repos/{owner}/{name}` API response used by `repositoryWithRefreshedGitHubRepository` (`api.fetchRepository`), and returns a `clone_url` pointing at an attacker-controlled repository with the same URL scheme (e.g. `https://github.example.com/attacker/evil-repo.git`). [10](#0-9) 
3. On the next background refresh/fetch/pull (which happens automatically), `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (user hasn't touched the remote), and `urlsMatch === false`, so it calls `gitStore.setRemoteURL('origin', updatedRemoteUrl)` without prompting the user. [8](#0-7) 
4. The user's next `git push` (via Desktop's push UI) now sends commits to the attacker's repository at the rewritten `origin` URL.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
