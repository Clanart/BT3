### Title
Path containment check in `resolveWithin` uses unanchored `startsWith`, allowing sibling-directory escape from repository root - (File: `app/src/lib/path.ts`)

### Summary
The reported Solidity bug is a boundary-comparison flaw: a `>=`/`<=` check was used where a strict `>`/`<` was required, silently widening/narrowing the accepted range and breaking the "must stay within bounds" invariant. The Desktop analog is the same class of bug applied to filesystem path containment: `_resolveWithin` in `app/src/lib/path.ts` decides whether a resolved path is "underneath the root" using a bare string-prefix comparison instead of a boundary-aware comparison, which incorrectly treats sibling paths sharing a prefix as being inside the root.

### Finding Description
`_resolveWithin` computes `realRoot` and `realResolved` via `realpath`, then decides containment with: [1](#0-0) 

`realResolved.startsWith(realRoot)` is a pure string-prefix test with no separator boundary check. If `realRoot` is e.g. `/Users/victim/repo` and an attacker-influenced segment resolves to `/Users/victim/repo-evil/secrets`, `startsWith('/Users/victim/repo')` is `true` even though `repo-evil` is a completely different, sibling directory — not "at or underneath" the root. This is structurally the same defect as the Ajna report: the code implements a boundary/containment check but the actual comparison operator/primitive used (`startsWith` on raw strings) accepts values just outside the intended boundary, exactly like `>=` accepting values at the excluded edge.

This function is reachable with attacker-influenced input via the deep-link handler `openRepositoryFromUrl`, which takes a `filepath` parameter straight from a `x-github-client://` URL a user can be lured into clicking: [2](#0-1) 

The only other guard is `isAbsolute(filepath)`, which rejects absolute paths but does nothing to stop a relative traversal segment like `../repo-sibling/secret.txt` that legitimately resolves outside `repository.path` while still passing the flawed `startsWith` prefix check if the sibling directory name happens to start with the repository directory's name (a realistic scenario since GitHub Desktop commonly clones repositories into directories such as `~/Documents/GitHub/<repo>` alongside other repos with prefix-overlapping names, or into directories the attacker can predict/create, e.g. `repo` vs `repo-secrets`).

`resolveWithin` is also used from `app-store.ts` and `copilot-conflict-context.ts`, meaning any consumer relying on the "guaranteed to reside at or underneath root" contract documented in the function's JSDoc is protected by a check that does not actually enforce that contract.

### Impact Explanation
A successful bypass lets an attacker-crafted deep link or PR/API-driven filepath value cause Desktop to treat a path outside the intended repository root as safe. In the concrete `openRepositoryFromUrl` sink this results in `shell.showItemInFolder(resolved)` being called on a path outside the repository, revealing/opening files outside the repo boundary that the user did not intend to expose — a "read outside the repo" primitive triggered purely by clicking an attacker-controlled link, matching the accepted impact category (deep-link-triggered access outside the intended sandboxed boundary).

### Likelihood Explanation
Likelihood depends on the attacker being able to get a victim to click a `x-github-client://openLocalRepo?...&filepath=...` link and on a suitably-named sibling directory existing next to the target repository (either naturally, e.g. `repo` and `repo.wiki`/`repo-old` clones common in GitHub workflows, or by having previously convinced the victim to clone an attacker-named repo into the same parent folder). This is a real but conditional path; it requires no local access, admin rights, or pre-existing malware — only a link click and a directory naming coincidence/setup, which is within the accepted attacker model (link/deep-link click).

### Recommendation
Fix the containment check to be boundary-aware instead of a raw prefix comparison, mirroring the fix pattern in the source report (replace the loose comparison with a strict one that actually respects the boundary):

```ts
// app/src/lib/path.ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```

Use the appropriate `sep` for the `options` variant (`Path.win32.sep` / `Path.posix.sep`) so `resolveWithinWin32`/`resolveWithinPosix` are fixed consistently.

### Proof of Concept
1. Suppose the victim has cloned two repositories side by side: `/Users/victim/Documents/GitHub/project` and `/Users/victim/Documents/GitHub/project-secrets` (the latter containing sensitive files).
2. Attacker sends the victim a link: `x-github-client://openLocalRepo?url=<project-repo-url>&filepath=..%2Fproject-secrets%2Fapi-keys.txt`.
3. Desktop's protocol handler routes this to `openRepositoryFromUrl` with `repository.path = /Users/victim/Documents/GitHub/project` and `filepath = ../project-secrets/api-keys.txt` (relative, so it passes the `isAbsolute` check at `app/src/ui/dispatcher/dispatcher.ts:1958-1961`).
4. `resolveWithin(repository.path, filepath)` resolves to `/Users/victim/Documents/GitHub/project-secrets/api-keys.txt`; `realResolved.startsWith(realRoot)` at `app/src/lib/path.ts:71` evaluates `true` because `project-secrets...` starts with the string `project` — the flawed boundary check passes.
5. `shell.showItemInFolder(resolved)` at `app/src/ui/dispatcher/dispatcher.ts:1966` opens/reveals the file from the sibling `project-secrets` directory, outside the intended repository boundary, from a single link click.
