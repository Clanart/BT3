## Title
Stale diff snapshot allows `applyPatchToIndex()` to commit/discard the wrong lines when a partial-selection's line indices no longer match the file's current hunks - (File: `app/src/lib/git/apply.ts`)

## Summary
The reported bug is a "stale reference used against a value that has since moved" pattern: `expiredOiUsd` is recorded against one collateral price and later applied without being rescaled to the current price, corrupting the trade's open-interest accounting. The same *broken-invariant class* exists in GitHub Desktop's partial-commit ("stage some lines") pipeline: a user's line `DiffSelection` (a set of absolute line indices) is computed against one diff snapshot of a file, but `applyPatchToIndex()` re-fetches a brand-new diff of the working directory at staging time and blindly re-applies the old index-based selection to it, with no check that the two diffs still agree on hunk boundaries/line counts.

## Finding Description
When the user partially stages/commits a file, the UI computes a `DiffSelection` bitmap keyed by `absoluteIndex` (`hunk.unifiedDiffStart + lineIndex`) against the diff that was rendered at selection time. [1](#0-0) 

That `WorkingDirectoryFileChange` (path + status + `selection`) is later handed to `stageFiles()` → `applyPatchToIndex()`. Crucially, `applyPatchToIndex()` does **not** reuse the diff the selection was built from — it calls `getWorkingDirectoryDiff(repository, file)` again, fetching a fresh `git diff` of the current on-disk content: [2](#0-1) 

It then feeds this fresh diff straight into `formatPatch(file, diff)`, which walks the *new* diff's hunks and lines and tests `file.selection.isSelected(absoluteIndex)` using the *old* index scheme: [3](#0-2) 

There is no verification that the newly fetched diff's hunk layout (start offsets, line counts, line ordering) matches the diff the selection indices were derived from. If the working tree changes between "user makes a partial selection" and "commit staging executes" — e.g., a background auto-formatter/build tool touches the file, a git hook runs, another process (or another Desktop-driven git operation) modifies it, or simply enough wall-clock time passes for the file to be edited externally — the hunk boundaries shift. The old `absoluteIndex` values then point at semantically different lines in the new diff. `isSelected()` has no bounds/identity check tying it to a specific diff generation; it purely operates on a `Map`/range structure of indices, so it will silently return `true`/`false` for indices that now correspond to unrelated content. The existing "refresh" logic (`updateChangesWorkingDirectoryDiff` in `app-store.ts`) only reconciles selection *for the UI's currently-loaded diff and displayed file*, clearing selected lines that no longer exist as `isIncludeableLine()`; it does **not** run as a guard immediately before `applyPatchToIndex()`/`stageFiles()` executes, so a race between the last UI refresh and the actual `git apply --cached` invocation is not covered. [4](#0-3) 

The same broken pattern is duplicated in `discardChangesFromSelection()`, which accepts an externally supplied `diff`/`selection` pair and applies them via `git apply` without any cross-check either. [5](#0-4) 

This is the direct analog of the report's core flaw: a value (`expiredOiUsd` / here, the selection's index space) captured at time T0 is reused unscaled/unvalidated against a different reference frame at time T1 (`currentCollateralPriceUsd` / here, the freshly fetched diff), with no reconciliation step guarding the boundary.

## Impact Explanation
If exploited (attacker controls a cloned/fetched repository, e.g. via a build script, pre-commit/post-checkout hook, or any tracked tool that rewrites a file the user is actively staging), the corrupted `DiffSelection` can cause Desktop to silently commit lines the user never selected (data/secrets leaking into the commit) or omit lines the user did select (partial data loss/incomplete fix committed) — this matches the "silent corruption of what the user commits or pushes" impact category explicitly called out as valid. Severity is Medium: the attacker needs the ability to modify tracked working-tree content on a timing window controlled by normal Desktop workflows (hooks/build tools triggered by `git status`/`git diff` calls Desktop itself makes), not local/physical/admin access.

## Likelihood Explanation
Likelihood is Medium: Desktop repeatedly calls `git diff`/`git status` while the user is actively looking at the Changes view (each keystroke/selection can trigger `updateChangesWorkingDirectoryDiff`), and any repository-provided hook (`post-checkout`, filters, smudge/clean, file watchers invoked by build tooling) that rewrites tracked files during this window can shift hunk boundaries between the moment the user finalizes a partial selection and the moment "Commit" is pressed and `applyPatchToIndex` executes. No unusual user action beyond normal partial-staging (a documented, common Desktop feature) is required.

## Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, verify that the diff used to build `file.selection` is still valid against the newly fetched diff (e.g., compare a hash of the pre-image content, or hunk headers/line counts) and, if it has changed, refuse to stage and force the UI to refresh the diff and re-derive the selection — mirroring the reconciliation `updateChangesWorkingDirectoryDiff` already does for `selectableLines`, but applied synchronously in the commit/stage path rather than only in the passive UI-refresh path.

## Proof of Concept
1. In a tracked repository open in Desktop, edit `foo.md` and select only lines 10–12 via the partial-staging UI; this bakes `absoluteIndex` values 10–12 into `file.selection` against the diff currently shown.
2. Before pressing "Commit", have an external process (e.g., a `pre-commit`/file-watcher script, or simply another editor) insert 5 new lines near the top of `foo.md`, shifting all subsequent hunk offsets down by 5 — Desktop has not re-rendered the diff yet.
3. Press "Commit". `stageFiles()` → `applyPatchToIndex()` calls `getWorkingDirectoryDiff()` fresh, obtaining a diff with shifted hunk `unifiedDiffStart` offsets: [6](#0-5) 
4. `formatPatch()` reuses the old `file.selection` bitmap against the new hunks' `absoluteIndex`, so the "selected" lines 10–12 in the *new* diff correspond to different, unintended content (the 5 newly inserted lines plus adjacent original lines shift into the selected range): [7](#0-6) 
5. The resulting commit silently contains different content than what the user visually selected, with no warning or error surfaced to the user.
