### Title
Authorization grants remain usable exactly at their expiration timestamp due to strict `Before` comparison - ([File: sei-cosmos/x/authz/keeper/keeper.go])

### Summary
`Keeper.GetCleanAuthorization` in the authz module treats a grant as still valid when the current block time exactly equals the grant's `Expiration`, because it uses the strict comparison `grant.Expiration.Before(ctx.BlockHeader().Time)` instead of an inclusive check. This is the same boundary-condition class of bug as the reported `QVBaseStrategy._checkOnlyAfterAllocation` issue (`block.timestamp < allocationEndTime` vs `<=`): a strict `<`/`Before` check at a state-transition deadline lets a caller act exactly on the boundary instant when the grant should already be considered expired.

### Finding Description
`GetCleanAuthorization` is the gate used by `Keeper.DispatchActions` (the handler for `MsgExec`) to decide whether a grantee may execute a message on behalf of a granter: [1](#0-0) 

```go
func (k Keeper) GetCleanAuthorization(ctx sdk.Context, grantee sdk.AccAddress, granter sdk.AccAddress, msgType string) (cap authz.Authorization, expiration time.Time) {
	grant, found := k.getGrant(ctx, grantStoreKey(grantee, granter, msgType))
	if !found {
		return nil, time.Time{}
	}
	if grant.Expiration.Before(ctx.BlockHeader().Time) {
		_ = k.DeleteGrant(ctx, grantee, granter, msgType)
		return nil, time.Time{}
	}
	return grant.GetAuthorization(), grant.Expiration
}
```

`time.Time.Before` returns `false` when the two timestamps are equal, so when `ctx.BlockHeader().Time == grant.Expiration`, the grant is *not* deleted and is returned as a live authorization. This is invoked from `DispatchActions`: [2](#0-1) 

which is reachable by any grantee submitting a plain `MsgExec` (or via any of the EVM precompiles that wrap authz grants/executes, e.g. the distribution precompile's `withdrawDelegationRewardsWithAuthorization`/`withdrawValidatorCommissionWithAuthorization`, which call `pcommon.ExecuteAuthorization` → `msgServer.Exec` → `DispatchActions`): [3](#0-2) [4](#0-3) 

The same off-by-boundary pattern (`Expiration.Before(...)`) also appears in the authz simulation code, confirming the intended semantics are ambiguous project-wide: [5](#0-4) 

### Impact Explanation
Any account that granted a time-limited authorization (bank `SendAuthorization`, distribution `MsgWithdrawDelegatorReward`/`MsgWithdrawValidatorCommission`, staking, etc.) expects that authorization to stop working at its `Expiration` instant. Because of the strict `Before` comparison, a grantee whose transaction lands in a block whose timestamp exactly equals `Expiration` can still successfully dispatch the authorized message — e.g. execute an unauthorized token transfer via `SendAuthorization`, or withdraw delegation rewards/commission on the granter's behalf — one instant after the granter reasonably believed the permission had expired. This is a genuine unauthorized-transfer-via-authorization boundary defect, reachable from any unprivileged transaction (a plain `MsgExec`, or an EVM call into the distribution/staking precompiles that route through `ExecuteAuthorization`).

### Likelihood Explanation
Exploitation requires the grantee to time a `MsgExec` (or an authorization-consuming precompile call) for a block whose timestamp is exactly equal to the recorded `Expiration` second. Because Sei block times are seconds-granular and somewhat predictable near a known expiration, a motivated grantee can attempt this in the same block/second the grant is due to expire; it is a narrow one-block/one-second window rather than an open-ended bypass, but it is deterministically reachable by any grantee holding a soon-to-expire grant, with no special privilege required.

### Recommendation
Change the expiry check in `GetCleanAuthorization` (and the equivalent check in `x/authz/simulation/operations.go`) from a strict comparison to an inclusive one, e.g.:

```go
if !grant.Expiration.After(ctx.BlockHeader().Time) {
    _ = k.DeleteGrant(ctx, grantee, granter, msgType)
    return nil, time.Time{}
}
```

so that a grant is treated as expired as soon as `block time >= Expiration`, matching the intended "grant is valid only strictly before its expiration" semantics.

### Proof of Concept
1. Granter calls `MsgGrant`/`grantWithdrawAuthorization` with `expiration = T`.
2. Grantee waits until a block is produced with `ctx.BlockHeader().Time == T` (exact match).
3. Grantee submits `MsgExec` (or calls the distribution precompile's `withdrawDelegationRewardsWithAuthorization`) in that block.
4. `GetCleanAuthorization` computes `grant.Expiration.Before(ctx.BlockHeader().Time)` → `false` (equal times are not "before"), so the grant is returned as valid and `DispatchActions` executes the authorized message, even though the authorization was meant to have expired at `T`.

// ExecuteAuthorization routes a concrete message through the native authz
// server, preserving its message-type scope and normal grant consumption.
func ExecuteAuthorization(ctx sdk.Context, msgServer utils.AuthzMsgServer, grantee sdk.AccAddress, msg sdk.Msg) (*authztypes.MsgExecResponse, error) {
	if err := msg.ValidateBasic(); err != nil {
		return nil, err
	}
	exec := authztypes.NewMsgExec(grantee, []sdk.Msg{msg})
	if err := exec.ValidateBasic(); err != nil {
		return nil, err
	}
	return msgServer.Exec(sdk.WrapSDKContext(ctx), &exec)
}
