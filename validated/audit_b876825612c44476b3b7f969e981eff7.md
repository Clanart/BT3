### Title
Forged `ReceivedOutput` deserialization credits arbitrary/nonexistent UTXOs, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes the three fields that fully define a wallet credit — the spend `offset`, the claimed `TxOut` (script + value), and the `OutPoint` — with no binding between them and no check that the output pays to `key + offset·G`. This mirrors the CORS bug class (trusting cross-origin input without validating its provenance): bytes from an untrusted channel are accepted as a "received output" even though only `Scanner::scan_transaction` can legitimately produce one bound to an on-chain transaction.

### Finding Description
`ReceivedOutput` has entirely private fields; its only public constructors are `Scanner::scan_transaction` / `scan_block` (which bind `outpoint` to `tx.compute_txid()` and `offset` to a registered script) and `ReceivedOutput::read`, which accepts any bytes: [1](#0-0)  The read path performs zero consistency checks — it does not verify that `output.script_pubkey == p2tr_script_buf(key + offset·G)`, nor that the outpoint exists, is unspent, or is mature.

Downstream, `SignableTransaction::new` trusts `input.output.value` for all balance, fee, and change math: [2](#0-1)  and builds `Prevouts::All` from the attacker-supplied `TxOut`s for the Taproot sighash: [3](#0-2)  The only integrity check, in `multisig`, merely confirms `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — which a forger trivially satisfies by computing the matching script for their chosen offset, while the `outpoint` itself remains unconstrained and can point to a nonexistent or already-spent output: [4](#0-3) 

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., a peer relaying scanner results, or any service persisting/receiving `ReceivedOutput` blobs) can fabricate credits: an output paying the correct `key + offset·G` script but anchored to a fabricated `OutPoint`. The wallet then reports funds as received and constructs/signs a spend transaction that is permanently unconfirmable — the referenced UTXO doesn't exist, or the `Prevouts::All` commitment disagrees with on-chain prevout values, producing signatures Bitcoin rejects. This is funds reported received that are not spendable. Severity: Medium — it corrupts balance/UTXO state and can wedge the signing pipeline (every signing attempt produces an invalid transaction), but cannot directly steal funds since the forged input can't be validly spent.

### Likelihood Explanation
`ReceivedOutput::serialize`/`read` exist precisely to move outputs across a trust boundary; any deployment receiving them over an unauthenticated channel is exposed. The attacker needs no key material — only the wallet's public key and knowledge of an offset (or brute-force a valid `(offset, script)` pair via `p2tr_script_buf(key + offset·G)`). Crafting the bytes is trivial: `offset || TxOut || OutPoint`.

### Recommendation
Bind `ReceivedOutput` to its origin: either make `read` crate-private/unchecked-explicit (e.g., `read_unchecked` with a documented MUST), or better, have `read` take the `Scanner`/public key and reject any `(offset, output)` where `output.script_pubkey != p2tr_script_buf(key + offset·G)`. Additionally verify the outpoint resolves to a confirmed, unspent output before the value is counted toward `input_sat`.

### Proof of Concept
1. Attacker learns wallet group key `K` and picks arbitrary scalar `o` such that `p2tr_script_buf(K + o·G)` returns `Some(script)` (increment `o` as `register_offset` does).
2. Attacker constructs `TxOut { value: 1_000_000_000, script_pubkey: script }` and `OutPoint::new(<any txid>, 0)`.
3. Serialize `o.to_bytes() || serialize(TxOut) || serialize(OutPoint)` and deliver to a component calling `ReceivedOutput::read`.
4. `SignableTransaction::new(vec![forged], …)` succeeds, reports ~10 BTC of inputs, and `multisig` accepts since `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` holds. The threshold signs a transaction whose input references a nonexistent UTXO — funds were reported received yet can never be spent.
