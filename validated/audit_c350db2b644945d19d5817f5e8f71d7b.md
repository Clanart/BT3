## Finding

### Title
Missing zero-amount input validation in `placeOrder`'s predispatch escrow path allows malformed orders that mis-credit escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core invariant is: **a cross-chain settlement/order function must reject non-existent/zero-value parameters (amount, recipient, token) before committing state**, because the Solidity reference implementation enforced these checks while a sibling implementation (Cairo) omitted them, causing wasted resources and broken invariants. The same class of divergence exists in this repository between the Tron `IntentGatewayV2.placeOrder` implementation and its sibling EVM mainline implementation.

### Finding Description
`IntentGatewayV2.placeOrder` escrows a user's input tokens and computes an order `commitment` from them. There are two code paths depending on whether the order carries `predispatch` calldata:

- **Non-predispatch path** (`evm/tron/contracts/apps/IntentGatewayV2.sol`, lines 444-463) explicitly enforces `if (order.inputs[i].amount == 0) revert InvalidInput();` at line 446 before escrowing.
- **Predispatch path** (same file, lines 383-443) has no equivalent check. `requiredAmount` (`order.inputs[i].amount`) is only used in a `balance < requiredAmount` comparison (lines 419, 423), which trivially passes when `requiredAmount == 0`, and the escrow is credited via `_orders[commitment][token] += reducedInputs[i].amount;` (line 435) with no floor check. [1](#0-0) [2](#0-1) 

By contrast, the sibling mainline EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) enforces `amount == 0` checks in **both** the predispatch branch (line 233: `if (order.inputs[i].amount == 0) revert InvalidInput();`) and the non-predispatch branch (line 283), and additionally rejects duplicate escrow entries per token via `if (_orders[commitment][token] != 0) revert InvalidInput();` before assignment (line 337), whereas the Tron version always accumulates with `+=` (lines 435, 457) without ever rejecting a repeated/zero-valued entry. [3](#0-2) [4](#0-3) 

This is a direct analog of the reported bug class: one implementation of the same public entrypoint (`placeOrder`, callable by any unprivileged user) enforces the invariant "escrow can only be created with a valid non-zero input amount," while another implementation of the identical function omits it on one of its two code branches.

### Impact Explanation
An order creator can place an order via the predispatch path with `order.inputs[i].amount == 0` for one or more input legs. That leg is included in `order.inputs` (and therefore in `order.output` matching solver obligations) but contributes `0` to `_orders[commitment][token]`. When a solver later fills the order (`fillOrder`), the solver must still deliver the full output amount specified by `order.output.assets[i]` for a fully-filled order, while the "escrowed input" returned to them for that leg is `0` — a mismatch between the value a solver is expected to receive and what the order creator actually escrowed, which can result in solver fund loss/economic manipulation of the fill, and in a broken invariant matching the reported class ("wastes resources… recipients not receiving expected value").

### Likelihood Explanation
The path is reachable by any unprivileged external caller through the public `placeOrder(Order memory order, bytes32 graffiti)` entrypoint by simply supplying `order.predispatch.call.length > 0` and an `order.inputs[i].amount == 0` entry — no relayer, prover, admin, or malicious peer is required, satisfying the "public-entrypoint, unprivileged attacker" requirement.

### Recommendation
Add the same `if (order.inputs[i].amount == 0) revert InvalidInput();` check to the predispatch escrow-crediting loop (around line 412-440) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring the check already present in the non-predispatch branch and in the mainline EVM implementation. Additionally, align the escrow-credit logic to explicitly reject (rather than silently accumulate via `+=`) duplicate input-token entries, matching `evm/src/apps/IntentGatewayV2.sol`'s `if (_orders[commitment][token] != 0) revert InvalidInput();` guard.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` on the Tron-deployed gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) with:
   - `order.predispatch.call.length > 0` and `order.predispatch.assets.length > 0` (any trivial no-op call satisfying the dispatcher).
   - `order.inputs` containing one entry with `amount = 0` for some token, alongside other legitimate legs.
   - `order.output.assets` specifying the corresponding non-zero output amount the solver must deliver for that leg.
2. `placeOrder` executes the predispatch branch (lines 383-443); the `amount == 0` leg passes the `balance < requiredAmount` check trivially and is credited into `_orders[commitment][token]` as `0` (line 435).
3. A solver later calls `fillOrder`, delivers the full output amount for that leg per `order.output.assets[i].amount`, but on settlement receives `escrowedInputs[i].amount == 0` for the corresponding input — a mismatch not caught by any guard in either `fillOrder` or `placeOrder`.
