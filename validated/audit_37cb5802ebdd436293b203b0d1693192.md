### Title
JSON key-spelling ambiguity bypasses ProtoJSON duplicate-field detection, causing silent field-value confusion - ([File: python/google/protobuf/internal/json_format_test.py])

### Summary
CVE-2024-38473 fails because two different encodings of the same logical request target (a mangled vs. canonical URL) are treated as distinct by mod_proxy's front-end check but resolved to the same backend resource, letting an attacker smuggle a request past an authorization check that assumed one canonical form. The transferable invariant is: *when a parser's "reject ambiguous/duplicate input" safety check compares raw encoded tokens instead of the canonical entity they resolve to, an attacker can present two different encodings of the same target and defeat the uniqueness check.* Protobuf's own ProtoJSON parser exhibits the same failure mode: its "reject duplicate keys" defense is keyed on the literal JSON string, not on the resolved `FieldDescriptor`, so `int32Value` (camelCase) and `int32_value` (snake_case) — two different encodings of the same field — bypass the duplicate check entirely and silently produce last-write-wins semantics instead of the intended parse failure.

### Finding Description
ProtoJSON is documented and tested to reject duplicate JSON keys as a hard parse error, e.g. `testDuplicateField` expects `'{"int32Value": 1,\n"int32Value":2}'` to fail with `'Failed to load JSON: duplicate key int32Value.'` [1](#0-0) . This check is implemented purely on the *raw JSON key string*, not on which proto field the key resolves to.

Because `json_format.Parse` also accepts the original proto field name (`snake_case`) in addition to the canonical `camelCase` JSON name (a compatibility feature), an attacker who supplies **both spellings of the same field** in one JSON object defeats the "duplicate key" guard even though both keys unambiguously resolve to the identical `FieldDescriptor`. This is explicitly acknowledged in the test suite as a known oversight:

```
def testDuplicateFieldAlternateNames(self):
  # Note: this behavior is non-spec and an oversight bug in the
  # implementation, but would be a breaking change to fix. The duplicate field
  # checker intends reject inputs with duplicate key names, but it only
  # catches keys that are exact matches and not alternate spellings that
  # correspond to the same field.
  parsed_message = json_format_proto3_pb2.TestMessage()
  json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
  self.assertEqual(parsed_message.int32_value, 2)
``` [2](#0-1) 

The same alternate-spelling collision reaches map fields as well, with the second spelling's map silently replacing the first's contents rather than being rejected or merged deterministically: [3](#0-2) 

The root cause is architectural, not merely a Python quirk: the descriptor layer itself acknowledges that proto field names and their default/custom JSON names can collide via multiple distinct encodings, and only *enforces* uniqueness among distinct **schema-declared** names — it has no mechanism to prevent a single incoming payload from supplying both the field's `name` and its `json_name` simultaneously and having the duplicate-detector miss it, because the detector never canonicalizes the incoming key to the resolved field before checking for repeats. The C++ ProtoJSON parser (`src/google/protobuf/json/internal/parser.cc`) uses a `SeenState`/`RecordAsSeen` mechanism keyed off the *resolved* field is closer to correct, but the legacy/Python/Ruby paths and the "alternate name" compatibility feature reproduce the classic encoding-ambiguity flaw: the safety check and the resolution step disagree about what counts as "the same target." This mirrors mod_proxy's flaw where the URL-normalization component and the backend routing component disagreed about which encoded string represented "the same resource," letting one encoding slip past a check keyed to the other.

### Impact Explanation
Impact is bounded and does not reach RCE, memory corruption, or protobuf's own authentication mechanisms (protobuf has none) — consistent with the report's own caveat that this class of finding rarely transfers 1:1. The concrete, provable impact within Protobuf's surface is: an attacker who controls a bounded ProtoJSON payload consumed by a trusted application via the public `google.protobuf.json_format.Parse` / `MessageToJson` round-trip can cause the parser to silently accept a payload that the application's security model assumes would be rejected as "ambiguous/duplicate," and can control *which* of two conflicting values for a security-relevant field (e.g., an authorization flag, quota, or role field) wins, with no diagnostic emitted to the application. Any consuming application that relies on "duplicate-key rejection == unambiguous input" as an integrity invariant (a documented, tested protobuf guarantee) has that invariant silently violated for one specific, attacker-reachable class of inputs (paired camelCase/snake_case spellings of the same field, or `json_name`-vs-default-name pairs). This is analogous in kind (encoding disagreement defeating a validation check) to the Apache issue, but the concrete blast radius is limited to field-value confusion inside a single message rather than a network-wide authentication bypass.

### Likelihood Explanation
High likelihood of reachability: `json_format.Parse` is a fully public, documented API; both camelCase and original-name spellings are accepted by design for backward compatibility, and the test file confirms this is a known, currently-unfixed, backward-compatibility-locked behavior ("would be a breaking change to fix"). No special schema, privileged access, or malformed wire bytes are required — a completely ordinary, spec-conformant-looking JSON payload with two keys triggers it.

### Recommendation
Canonicalize the incoming JSON key to its resolved `FieldDescriptor` (or `json_name`/`name` pair) *before* performing duplicate-key detection, so that any two spellings that resolve to the same field are treated as duplicates and rejected (or deterministically merged), matching the behavior already used by the C++ `SeenState` seen-field tracking in `src/google/protobuf/json/internal/parser.cc`. Since this is a "fix would change behavior" issue that protobuf maintainers have declined to change for backward-compatibility reasons, applications that rely on the duplicate-key guard as a security boundary should be explicitly warned in documentation that alternate-name spellings are not covered by the guard.

### Proof of Concept
Using the existing, already-passing test as the reproduction (bounded ProtoJSON payload, trusted schema, public API):
```python
parsed_message = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
assert parsed_message.int32_value == 2  # no error raised, despite the "duplicate key" rule
```
This exact assertion is present and passing in the checkout's test suite [2](#0-1) , confirming the bypass is live and not merely theoretical in this codebase revision.
