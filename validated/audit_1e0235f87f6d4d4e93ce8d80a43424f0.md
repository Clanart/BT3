## Title
Rounding-to-zero in partial-fill escrow release lets order creators keep both the solver's payment and the full escrow - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes the escrow released to a solver on a partial fill with integer division that truncates to zero whenever `order.inputs[i].amount * fillAmount < totalRequired`. When this happens, the solver's real output-token payment to the beneficiary still executes and `_partialFills` progress is recorded, but zero input tokens are released from escrow. Because `_cancelSameChain` reads the live `_orders` balance directly and is unguarded by fill history, the order creator can later cancel and reclaim the entire un-decremented escrow — capturing the solver's payment for free. This is the same broken invariant as the external report: a division that rounds a per-unit value down to zero lets a value-transferring operation execute without the corresponding compensating balance change.

### Finding Description
In `_fillSameChain`: [1](#0-0) 

For any partial fill (`amountFilled != totalRequired`), `escrowedAmount` is computed as `(order.inputs[i].amount * fillAmount) / totalRequired`, rounding down. Whenever `order.inputs[i].amount * fillAmount < totalRequired`, this evaluates to `0`.

The solver still pays the beneficiary the full `fillAmount` (plus any surplus share) in the earlier transfer block: [2](#0-1) 

`escrowedInputs[i]` is then set to `0` and passed to `_withdraw`, which explicitly skips any zero-amount token without touching `_orders`: [3](#0-2) 

So the escrow balance for that commitment/token is left completely untouched even though the solver just paid the beneficiary. The order is not finalized (`isFullyFilled` is false), so `_filled[commitment]` is deleted: [4](#0-3) 

The order creator (`order.user`) can now cancel at any time. `_cancelSameChain` never checks `_partialFills` or prior fill activity — it only reads the current `_orders[commitment][token]` balance, which is unchanged: [5](#0-4) 

The repository's own tests acknowledge rounding dust exists and fix the *locked-dust* case by giving the full remaining balance to whichever fill happens to complete the order (`amountFilled == totalRequired` branch reads `_orders[commitment][...]` directly): [6](#0-5) 

That fix only addresses dust getting stuck permanently; it does not address the case where a *non-final* partial fill's share rounds all the way down to zero, letting a real payment happen with zero offsetting escrow release, while the creator still holds — and can reclaim — 100% of the escrow.

### Impact Explanation
Any order creator can size `order.inputs[i].amount` to be small relative to `order.output.assets[i].amount` (e.g., a low-decimal or low-unit-count input token traded against a higher-precision output token). Any solver who performs a partial fill smaller than `totalRequired / order.inputs[i].amount` pays real output tokens to the beneficiary but receives zero escrowed input tokens for that fill. The creator (or a colluding beneficiary) keeps the solver's payment, and since `_orders` was never decremented, the creator can subsequently call `_cancelSameChain` to reclaim the *entire* original escrow. This is a direct loss of funds for the solver and an unauthorized/free value capture by the order creator — no malicious relayer, prover, or governance actor is required, only a public call to `fillOrder`/`cancelOrder` on an intentionally crafted order.

### Likelihood Explanation
The trigger condition (`order.inputs[i].amount * fillAmount < totalRequired`) is fully controlled by the order creator via the ratio of input to output amounts, and partial fills are an explicitly supported, encouraged code path (the contract has dedicated logic and tests for partial fills). No privileged role, race condition, or off-chain component is needed — a solver only needs to submit a partial fill sized below the rounding threshold, which can happen either through a deliberately crafted order (attacker-controlled) or accidental sizing by an unaware solver.

### Recommendation
Round the proportional escrow release up (or otherwise guarantee `escrowedAmount > 0` whenever `fillAmount > 0`), mirroring the standard ERC4626 `mulDivUp` mitigation used for the analogous PirexERC4626 bug. Alternatively, require `escrowedAmount >= 1` for any non-zero `fillAmount`, and/or reject fills whose computed `escrowedAmount` would round to zero, so solver payments are always matched with a proportional (or minimum-1) escrow release. Additionally, consider having `_cancelSameChain` account for outstanding solver payments already made against `_partialFills`, not just the raw `_orders` balance.

### Proof of Concept
1. Attacker creates an `Order` with `order.inputs[0].amount = 1` (e.g., 1 raw unit of a token, arbitrarily small relative to its typical order size) and `order.output.assets[0].amount = totalRequired = 1_000_000` (e.g., 1 USDC at 6 decimals). Beneficiary is set to the attacker or a colluding address. Escrow of `1` unit of the input token is locked via `placeOrder`.
2. A solver calls `fillOrder` with `options.outputs[0].amount = 999_999` (a legitimate, almost-full partial fill, one unit short of completing the order).
   - `fillAmount = 999_999`, `escrowedAmount = (1 * 999_999) / 1_000_000 = 0` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:120`).
   - The solver's `999_999` output tokens are transferred to the beneficiary (`IntrinsicIntents.sol:107`).
   - `_withdraw` is called with `amount = 0` for the input token and skips decrementing `_orders` (`IntentsBase.sol:397-398`).
   - `isFullyFilled = false`, so `_filled[commitment]` is deleted (`IntrinsicIntents.sol:140`), and `_orders[commitment][inputToken]` still equals the full original escrow (`1` unit).
3. Attacker (as `order.user`) calls `cancelOrder` → `_cancelSameChain`, which reads `_orders[commitment][inputToken] == 1` (untouched) and refunds the full original escrow back to the attacker (`IntrinsicIntents.sol:174-186`).
4. Net result: the solver paid `999_999` output-token units to the beneficiary and received `0` input tokens; the attacker recovered the full escrow via cancellation. The solver's payment is pure loss captured by the attacker/beneficiary.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
