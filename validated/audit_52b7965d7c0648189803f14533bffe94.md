### Title
Malicious FROST participant can crash the signer by forcing the nonce sum `R` to the point at infinity, hitting the `x()` panic in `Hram::hram` - (File: networks/bitcoin/src/crypto.rs)

### Summary
CVE-2015-4646 is a denial-of-service (application crash) via crafted input to a parser. The Serai analog is a remote, unauthenticated-validator-reachable panic in the BIP-340 Schnorr `Hram` used by the Bitcoin FROST algorithm: a malicious signing participant supplies nonce commitments crafted so that the aggregate nonce `R` is the point at infinity, causing `x(R)` to panic mid-`sign()` and crash the processor.

### Finding Description
`Hram::hram` calls `x(&R)`, which does `encoded.x().expect("point at infinity")` and panics when `R` is infinity (`networks/bitcoin/src/crypto.rs:13-16`, `:59-72`). The same panic exists in `x_only` (`crypto.rs:21-23`). The doc comment claims this has "a negligible probability for a well-reasoned caller, even with malicious participants present" (`crypto.rs:78-83`), which is incorrect.

In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283-318`), each participant's preprocess commitments are read via `read_preprocess` → `Commitments::read` (`sign.rs:276-281`). `Commitments::read` deserializes arbitrary group elements and does not enforce that the summed binding-factor-weighted nonce `R = Σ (D_i + ρ_i·E_i)` is non-identity. Because preprocesses are broadcast to all participants before `sign` is invoked (see `processor/src/batch_signer.rs:241-271`, `processor/src/cosigner.rs:155-185`, `processor/src/slash_report_signer.rs:149-178`), an attacker sees every other participant's commitments and can choose their own commitments `D_j, E_j` so the aggregate `R` cancels to the identity point. When `sign_share` later evaluates `Hram::hram(R, A, m)`, `x(R)` panics — the panic propagates out of `machine.sign(...)` as an abort/`unreachable` class failure rather than the handled `FrostError` variants (`batch_signer.rs:274-288`).

### Impact Explanation
An unprivileged participant in a Bitcoin signing set (any validator who can submit a SubstratePreprocess message they cause to be signed) can crash every honest processor node executing `sign()` for that batch. This halts Bitcoin multisig signing — withdrawals and output spends stall — matching the CVE class (remote crash via crafted input). It requires no key material, no collusion, and works against all honest signers simultaneously.

### Likelihood Explanation
The attacker only needs to be a member of the signing set (a validator position), observe the other preprocesses (delivered publicly), and solve `D_j + ρ_j·E_j = -(Σ_{i≠j}(D_i + ρ_i·E_i))` — trivially satisfiable, e.g. `E_j = G` and `D_j` chosen to cancel. The malformed preprocess deserializes cleanly since identity/degenerate points are not rejected at `Commitments::read`, so the attack reaches `hram` on every `sign()` attempt, and retries keep crashing.

### Recommendation
Reject the point at infinity (and non-canonical encodings) in `Commitments::read` in `crypto/frost/src/sign.rs`, and in `AlgorithmSignMachine::sign` verify the computed aggregate nonce `R` is non-identity before invoking `sign_share`, returning `FrostError::InvalidPreprocess(participant)` instead of panicking. Additionally, make `x()`/`x_only()` in `networks/bitcoin/src/crypto.rs` return `io::Result`/`Option` rather than `expect`, so degenerate points cannot abort the process even if other checks are missed.

### Proof of Concept
1. Attacker (Participant `j`) joins a Bitcoin signing attempt and receives serialized preprocesses for all other participants via `CoordinatorMessage::SubstratePreprocesses`.
2. Attacker computes `ρ_i` for each `i` (the binding factors are deterministic over the public commitment set and message) and selects `E_j = G`, `D_j = -(Σ_{i≠j}(D_i + ρ_i·E_i) + ρ_j·G)`, a valid Secp256k1 point encoding.
3. Attacker serializes `D_j || E_j` as their preprocess and submits it.
4. In every honest node's `machines[m].sign(preprocesses, msg)`, the nonce sum `R` equals infinity; `Hram::hram` calls `x(R)` → `expect("point at infinity")` panics → processor crashes instead of emitting `InvalidParticipant`.

Confidence note: the panic site and the reachability of attacker-controlled commitments into `hram` are confirmed from `crypto.rs:13-16`, `:59-72` and `sign.rs:276-318`; I could not fully verify within the iteration limit whether `Commitments::read` or the nonce-sum aggregation rejects identity elsewhere — if it does, the panic is unreachable and this finding would not hold.
