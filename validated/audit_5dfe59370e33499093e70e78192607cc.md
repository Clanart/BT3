### Title
`InternalSendTx` reachable without caller authentication when the `Noop` interceptor is active - broadcasts an attacker-supplied raw transaction ([File: core/src/rpc/aggregator.rs])

### Summary
`ClementineAggregator::internal_send_tx` performs no caller-identity check of its own; it deserializes the raw transaction from `SendTxRequest` and unconditionally queues it via `tx_sender.insert_try_to_send`, relying entirely on an external gRPC interceptor to enforce the "self only" binding implied by the `Internal` prefix. When the deployment's interceptor is `Interceptors::Noop` (as selected by `client_verification=false` in the aggregator config), that binding is never checked, so any caller reaching the aggregator's gRPC port can invoke this method.

### Finding Description
The intended binding is: `caller reaching InternalSendTx == aggregator itself (self-loopback only)`, enforced by `only_aggregator_and_self`/`is_internal` in `core/src/rpc/interceptors.rs`, which is wired into the aggregator's tonic server in `create_grpc_server` (`core/src/servers.rs`) based on the `client_verification` config flag (`core/src/config/mod.rs`, `core/src/config/env.rs`).

The handler itself, `ClementineAggregator::internal_send_tx` (`core/src/rpc/aggregator.rs:1270-1312`), contains no independent authorization logic: [1](#0-0) 
It takes `request.into_inner()`, converts `raw_tx` into a `bitcoin::Transaction`, and calls `self.tx_sender.insert_try_to_send(...)` unconditionally, then commits — no signature check, no origin check, no reference to any known presigned txhandler is performed inside the RPC method.

When `client_verification=false`, the server is configured with `Interceptors::Noop`, so the `is_internal()`/`only_aggregator_and_self` gate in `core/src/rpc/interceptors.rs` never runs for this call, meaning the transport-level enforcement of "self only" access is bypassed for every RPC on that server, including `InternalSendTx`.

### Impact Explanation
If exploited, an unprivileged network caller can get the aggregator's `tx_sender` to accept and attempt to broadcast an arbitrary transaction of the attacker's choosing. However, `send_raw_transaction`/the Bitcoin network's own consensus and script-verification rules still require any transaction spending a bridge-controlled UTXO (move-to-vault, kickoff, round, challenge, disprove, payout, etc.) to carry a valid N-of-N Schnorr signature, which the attacker cannot forge without a compromised key (out of scope per the rules). Therefore this endpoint cannot itself be used to move bridge BTC, forge a reimbursement, or produce N-of-N signatures for an unauthorized spend — those require signature forgery, which is unaffected by this gap. The concrete, demonstrable impact is limited to the aggregator's Bitcoin RPC being usable as an unauthenticated broadcast/relay endpoint and its `tx_sender` queue accepting attacker-controlled rows — matching the "unauthenticated state-changing or broadcasting call" High-severity bucket by definition, but with no shown path to the Critical categories (no fund movement, no false reimbursement, no forged N-of-N signature).

### Likelihood Explanation
Exploitability is entirely conditioned on the deployment running with `client_verification=false` (selecting `Interceptors::Noop`), which is a configuration option present in `core/src/config/mod.rs`/`env.rs` and used in test/dev config files (`core/src/test/data/bridge_config.toml`, `scripts/docker/configs/testnet4/bridge_config.toml`). Whether any production deployment runs with this flag disabled is not established from the code alone — this determines whether the finding is reachable in practice. No Bitcoin cost is required beyond normal broadcast/relay fees since the attacker's own transaction still has to be independently valid to be accepted by the network.

### Recommendation
Enforce the "self only" restriction for `InternalSendTx` (and other `Internal*` RPCs) inside the handler itself — e.g., verify a shared secret/mTLS peer identity or explicit loopback-source check independent of the configurable interceptor — rather than relying solely on `client_verification`/`Interceptors::Noop` selection at server construction time, so that disabling the interceptor cannot silently strip authorization from internal-only RPCs.

### Proof of Concept
```
cargo test -p clementine-core --features automation -- internal_send_tx_noop_interceptor
```
Test outline:
1. Start an aggregator instance with `client_verification=false` (forcing `Interceptors::Noop`) against regtest bitcoind, per the existing e2e harness pattern in `core/src/test/deposit_and_withdraw_e2e.rs`.
2. From a client context that is not the aggregator (i.e., no internal-loopback credential), call `aggregator.internal_send_tx(SendTxRequest { raw_tx: Some(RawSignedTx{raw_tx: serialize(&attacker_tx)}), fee_type: FeeType::Cpfp as i32 })`, where `attacker_tx` spends only attacker-owned UTXOs (not derived from any known txhandler).
3. Assert the call returns `Ok(Empty{})` (no `Status::permission_denied`/`unauthenticated`).
4. Assert via `bitcoind.get_raw_transaction` / mempool inspection that the transaction was submitted by the aggregator's `tx_sender`, confirming broadcast occurred without any caller check — asserting the "caller reaching InternalSendTx" side of the equality no longer equals "aggregator itself" while the transaction is still relayed.
