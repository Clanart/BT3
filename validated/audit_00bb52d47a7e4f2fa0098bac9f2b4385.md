### Title
Withdrawals can be permanently blocked if a reward token blacklists a staker's address - (File: rewards/MasterMagpie.sol, rewards/BaseRewardPool.sol)

### Summary
`MasterMagpie._harvestAndUnstake()` unconditionally forces a reward "push" transfer to the withdrawing user before allowing their principal to be unstaked. Because the reward-claim call reverts the entire transaction on failure, and there is no way to withdraw principal without triggering this claim, a user whose address is blacklisted by any reward token added to a pool's `BaseRewardPool` can never withdraw their staked LP/receipt tokens again.

### Finding Description
`_harvestAndUnstake()` calls `_harvestBaseRewarder(_stakingToken, _account)` before adjusting the user's staked `amount`/`available` balance: [1](#0-0) 

`_harvestBaseRewarder` ultimately calls into `BaseRewardPool.getReward(_account, _receiver)`, which loops over all registered reward tokens and performs a `safeTransfer` directly to the account for each nonzero pending reward: [2](#0-1) 

The equivalent push-transfer pattern also exists in `BaseRewardPoolV2._sendReward`, used by `getReward`/`getRewards`: [3](#0-2) [4](#0-3) 

Reward tokens for a `BaseRewardPool` can be arbitrary ERC20s registered via `queueNewRewards`/`donateRewards` by anyone with manager rights or, in `BaseRewardPoolV2`, via permissionless `donateRewards`. If any such reward token implements an address blacklist (e.g. a USDC-like token) and the staker's own address later becomes blacklisted (or the token otherwise reverts on transfer to that specific address, e.g. via a malicious/incompatible callback), the `safeTransfer` in `getReward` reverts. Because `getReward`/`_sendReward` do not use try/catch and there is no pull-based claim path that bypasses this transfer before unstaking, the revert propagates all the way up through `_harvestAndUnstake` → `withdrawFor`/`_multiClaim`, and the user's principal (their staked LP/receipt tokens) becomes permanently unwithdrawable — this is the exact "push over pull" bug class described in the reference report, but here the blocked party is an ordinary unprivileged depositor rather than a manager.

### Impact Explanation
Any staker whose address is denied by a reward token (blacklist, malicious callback token, or a token that simply reverts for that specific recipient) permanently loses access to their own staked principal, since every withdrawal path forces a reward harvest/push first. This is a direct, permanent freezing of user funds with no admin or pull-based recovery mechanism in the reviewed code.

### Likelihood Explanation
Reward tokens are added over time as new incentive campaigns are created for a pool; the protocol does not control which addresses interact with the pool nor which external token deny-lists might later apply to a staker. While triggering a self-blacklist purely to grief oneself is not rational, an attacker (or an unrelated third party such as a token issuer) blacklisting a victim's address, or a manager/anyone permissionlessly donating a non-standard/reverting-on-recipient token as a reward via `donateRewards`, is sufficient to lock that victim out of ever withdrawing, satisfying the required permanent-freeze bar.

### Recommendation
Adopt a pull-over-push accounting model for reward payouts, mirroring the report's suggestion for the analogous manager-fee case: track earned-but-unclaimed rewards per user/token in storage without transferring, and let each user claim their rewards independently via a separate function. Ensure `withdraw`/`unstake` paths never depend on the success of an ERC20 transfer to an unrelated (and potentially deny-listed) recipient. At minimum, wrap the reward `safeTransfer` calls in `getReward`/`_sendReward` in a way that failures only skip that specific token's payout (e.g., swallow failure and leave the reward accrued/claimable later) rather than reverting the entire unstake transaction.

### Proof of Concept
1. A pool's `BaseRewardPool` has reward token `R` added via `queueNewRewards`/`donateRewards`.
2. Alice stakes into the pool through `MasterMagpie`, accruing pending `R` rewards.
3. `R`'s issuer blacklists Alice's address (or `R` is a token engineered to revert transfers to a specific address).
4. Alice calls `withdraw()`/`unstake()` on `MasterMagpie`, which invokes `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPool.getReward(Alice, Alice)`.
5. The `safeTransfer(Alice, reward)` for token `R` reverts, causing the entire withdrawal transaction to revert.
6. Alice's staked LP/receipt tokens remain locked in `MasterMagpie` indefinitely, with no available function to withdraw principal without first successfully transferring the blocked reward token. [1](#0-0) [2](#0-1)

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }

    /// @notice Calculates and sends reward to user. Only callable by masterMagpie
    /// @param _account Address account
    function getReward(address _account, address _receiver)
        override
        public
        onlyMasterMagpie
        updateReward(_account)
        returns (bool)
    {
        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

        return true;
    }
