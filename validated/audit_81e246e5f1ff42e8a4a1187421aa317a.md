Based on my investigation, GitHub Desktop's recently-added Git hooks execution feature is a legitimate analog to the "UberOwner has too much power" pattern: a single, global, all-or-nothing trust decision (enable hooks) grants any repository content the power to execute arbitrary code on ordinary user actions, with no per-repository vetting.

### Title
Git hooks execution grants any cloned/opened repository unconditional code-execution power with no per-repository trust gate - (File: `app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/hooks-proxy.ts`)

### Summary
Once a user has the hooks environment feature enabled (default in beta/dev channels via `enableHooksByDefault`/`enableBetaFeatures`, optionally enabled by any user in Preferences on stable), GitHub Desktop will automatically discover and execute any executable file matching a known Git hook name found at whatever `core.hooksPath` resolves to for the *currently open repository* — with no per-repository confirmation, diffing, or trust prompt. Because `core.hooksPath` is commonly pointed at a repository-tracked directory by widely used tooling conventions (Husky, lefthook, pre-commit frameworks), an attacker who controls a cloned/fetched repository can get their scripts silently executed the moment the victim performs a routine action (commit, pull, merge, push, checkout). This mirrors the "UberOwner" concern: a single global switch confers total, ongoing power over local code execution to whatever repository the user happens to have open, without any narrower, per-repository consent mechanism, review, or time-delay/confirmation step.

### Finding Description
The hook interception pipeline works as follows:

1. `git()` in `app/src/lib/git/core.ts` calls `withHooksEnv()` whenever a git operation (commit, pull, push, merge, etc.) sets `interceptHooks`. [1](#0-0) 

2. `withHooksEnv()` gates purely on a global boolean (`getHooksEnvEnabled()`), not on any per-repository trust state, and then enumerates hooks for the *current* repository path: [2](#0-1) 

3. `getRepoHooks()` resolves the hooks directory by reading the repository's own `core.hooksPath` config (falling back to `.git/hooks`), lists files there, and yields any file whose name matches a fixed list of known hook names and which is executable (on Windows, the executable check is skipped entirely — "we have to assume that any valid hook name is executable"): [3](#0-2) 

4. Discovered hooks are then proxied and, when triggered by Git, actually spawned as real child processes with the user's full shell environment via `hooks-proxy.ts`: [4](#0-3) 

There is no verification step anywhere in this chain that checks:
- Whether the hook script content has changed since the last time it ran (no hash/diff comparison).
- Whether the user has ever been shown or asked to approve *this specific repository's* hooks.
- Whether `core.hooksPath` itself was set by a source under attacker control (e.g. a tracked setup script executed by the user as part of a documented project "install" step, a common convention for Husky/lefthook/pre-commit, which set `core.hooksPath` to a versioned, repository-tracked directory).

The only control is `getHooksEnvEnabled()`, a single global on/off toggle: [5](#0-4) 
and `enableHooksByDefault` currently equals `enableBetaFeatures()`, i.e. hooks execution is **on by default** for beta/canary channel users, and can be turned on by any stable-channel user in Preferences with no further per-repository consent required afterward: [6](#0-5) 

Once enabled, this power extends uniformly to every repository the user opens or clones for the lifetime of that setting — exactly the "too much power concentrated in one place, with no time delay, no scoping, no multisig-equivalent" pattern flagged in the source report. Compare this to Git's own upstream mitigation for a related class of bug (CVE‑2022‑24765), where Git added `safe.directory` to require explicit per-directory trust before certain repository-controlled configuration takes effect — GitHub Desktop's hook feature has no equivalent per-repository trust registry.

### Impact Explanation
An attacker who can get a victim to clone or fetch a repository (public GitHub repo, PR branch, fork) can achieve local, arbitrary code execution as the victim user, on the victim's machine, the next time the victim performs a completely ordinary action like `git commit`, `git pull`, `git merge`, or `git push` in that repository within Desktop — no unusual action required beyond normal repository usage, since committing/pulling are core, expected Desktop workflows. This can lead to credential theft (SSH keys, GitHub tokens, other repos on disk), further supply-chain compromise, or full host compromise, satisfying the "unprivileged Desktop issue where attacker controls a cloned/fetched repository ... and the result is code execution" impact category.

### Likelihood Explanation
Likelihood is elevated for beta/canary channel users because the feature is enabled by default. For stable users, likelihood depends on the user having opted in via Preferences, which is a legitimate and increasingly common opt-in for developers wanting local hook automation (e.g. commit linting), and the underlying repository convention it targets (setting `core.hooksPath` to a tracked directory via a documented install step) is a mainstream, widely-adopted pattern (Husky et al.), meaning the attack surface is real and not contrived. The lack of any per-repository confirmation means a single opt-in decision silently applies to all future repositories, including ones the user has not vetted.

### Recommendation
- Introduce a per-repository trust prompt (similar in spirit to VS Code's "Workspace Trust") the first time Desktop is about to execute a discovered hook for a given repository, showing the hook name and its script content/hash, and requiring explicit user approval before execution.
- Track approved hook content by hash per repository, and re-prompt if the hook script content changes between runs (protecting against a benign hook being swapped for a malicious one after initial approval, e.g. via a subsequent `pull`).
- Consider not treating `core.hooksPath` values that resolve inside the tracked working directory as automatically safe, since that value/directory content can originate from the remote repository itself.
- Surface a persistent, visible indicator in the UI when hooks are enabled for the currently open repository, rather than relying solely on a global, easy-to-forget Preferences toggle.

### Proof of Concept
1. Attacker creates a public repository containing a tracked directory, e.g. `.githooks/pre-commit`, containing a malicious executable script (with the executable bit set, or matching a known hook name on Windows where the executable bit is not checked).
2. Attacker documents (or automates via an npm `prepare`/`postinstall` script that many developers run without close scrutiny) a setup step that runs `git config core.hooksPath .githooks`.
3. Victim, using GitHub Desktop with the Hooks feature enabled (default on beta/canary, or previously opted-in on stable), clones the repository and performs the documented setup step (or the repository's tooling sets this during a normal `npm install`).
4. Victim performs an ordinary action in Desktop, e.g. commits a file. `withHooksEnv()` in `app/src/lib/hooks/with-hooks-env.ts` detects the `pre-commit` hook via `getRepoHooks()` in `app/src/lib/hooks/get-repo-hooks.ts`, and `hooks-proxy.ts` spawns it with the victim's shell environment — no dialog, no warning, no confirmation is shown before the attacker's script runs with the victim's OS-user privileges.

```typescript
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```

```typescript
export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
```
