### Title
`ReceivedOutput::read` accepts an arbitrary scalar offset not bound to the output's `script_pubkey`, producing unspendable "received" outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The XStream advisory is an unmarshalling flaw: attacker-controlled bytes are decoded into an object whose fields are then trusted to drive a security-sensitive action, without validating the object's internal consistency. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` (lines 120–134). It deserializes a `Scalar` offset, a `TxOut`, and an `OutPoint` from untrusted bytes, but never verifies that `offset` actually derives the Taproot key committed inside `output.script_pubkey`. The resulting `ReceivedOutput` is indistinguishable from a legitimately scanned one.

### Finding Description
`Scanner::scan_transaction` (lines 199–214) is the only honest constructor of `ReceivedOutput`: it looks up `output.script_pubkey` in `self.scripts`, a map from script → offset built by `Scanner::new`/`register_offset`, so by construction `p2tr_script_buf(key + G*offset) == script_pubkey`. That invariant is what makes the output spendable — when the output is later spent, the signer offsets its key share by `output.offset()` so the FROST group signature verifies against the x-only key embedded in the script.

`ReceivedOutput::read` reconstructs the struct from raw bytes with no such check:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Any `offset` will deserialize as long as it is a canonical scalar. There is no field storing the base key either, so the inconsistency is unrecoverable at read time — the object simply asserts "this output is spendable by key + offset·G" with no proof of it.

### Impact Explanation
Untrusted bytes fed to `ReceivedOutput::read` (explicitly in scope) yield a struct that downstream code treats as a spendable input: `offset()` is applied to the threshold key to form the signing view for that input. Two failure modes:

- Wrong `offset` for a script we do control → the aggregated FROST signature is produced for the wrong tweaked key, so the fully-signed transaction is invalid; the funds are reported received but are not spendable by that path.
- A `TxOut`/`OutPoint` naming a real UTXO paying a *different* (e.g., attacker's or third party's) Taproot key, paired with any offset → the scheduler counts attacker-chosen value as received balance and builds/signs a transaction spending an input the multisig can never validly spend. At best the transaction is rejected after burning the signing attempt; at worst fee/change accounting in `SignableTransaction::new` is driven by phantom input value.

This is a "funds reported received that are not spendable" impact reachable purely through crafted serialized bytes — the analog of the advisory's "type confusion at deserialization enables an unintended privileged action".

### Likelihood Explanation
Medium. Exploitation requires an attacker to get crafted bytes into a `ReceivedOutput::read` call (e.g., a stored/relayed output record rather than a scanner-produced one). It requires no key material, no threshold collusion, and no malformed curve encodings — `read_F`, `consensus_decode` all succeed on the crafted input. Mitigating factor: if all `ReceivedOutput`s in a deployment only ever originate from `Scanner::scan_transaction` and are never deserialized from attacker-influenced storage, the path is unreachable; the rules, however, designate `ReceivedOutput::read` as an untrusted-bytes entry point.

### Recommendation
Bind the offset to the script at deserialization time. `ReceivedOutput::read` cannot do this alone since the base key isn't serialized; options:

- Include the base `ProjectivePoint` (or the registered script) in the serialized form and assert `p2tr_script_buf(key + G*offset) == output.script_pubkey` in `read`, or
- Relegate `read` to a private constructor and expose a `ReceivedOutput::read_and_verify(reader, key)`/`Scanner::read_output` that re-derives the script from `(key, offset)` and rejects on mismatch, mirroring how `scan_transaction` guarantees the invariant.

Additionally, `ScriptBuf` identity should be checked rather than trusting that any P2TR script corresponds to `key + offset·G` (a script with a real script-path commitment would be spendable without the signature entirely).

### Proof of Concept
```rust
// networks/bitcoin crate context
let key = ProjectivePoint::GENERATOR * Scalar::random(&mut OsRng);
let scanner = Scanner::new(key).unwrap();
let good_script = p2tr_script_buf(key).unwrap();

// Attacker crafts bytes: a real TxOut paying OUR script, but with a wrong offset
let evil = ReceivedOutput {
  offset: Scalar::random(&mut OsRng),   // any offset != the registered one
  output: TxOut { value: Amount::from_sat(50_000), script_pubkey: good_script },
  outpoint: OutPoint::new(Txid::all_zeros(), 0),
};
let bytes = evil.serialize();

// Deserialization succeeds with no consistency check
let decoded = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// decoded.offset() will now be applied to the threshold key during signing,
// producing a signature for `key + evil_offset*G` — which is NOT the x-only key
// committed in `good_script`. The output is counted as received balance yet the
// signed spend is invalid / the funds are unspendable via this path.
```

A symmetric variant sets `script_pubkey` to an attacker-controlled P2TR key (or a P2TR output with a meaningful script path); `read` still succeeds and the phantom value flows into `SignableTransaction::new`'s input accounting.
