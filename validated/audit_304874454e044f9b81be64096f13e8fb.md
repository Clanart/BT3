## Finding Confirmed

The code confirms the vulnerability. In `on_accept`, the token transfer/mint to the beneficiary happens **before** the optional-calldata signature verification: [1](#0-0) 

Then signature verification runs afterward, and any of the `Ed25519`/`Sr25519`/`Ecdsa` branches can return `HftError::SignatureVerificationFailed` (or `EcdsaRecoveryFailed`, `CallFiltered`, `RuntimeCallDecodeError`, `CallDispatchError`) which propagates `Err` out of `on_accept`: [2](#0-1) 

Critically, the project's own documentation confirms that when `IsmpModule::on_accept` returns an error, **the receipt is not persisted, allowing the request to be replayed**, and explicitly places the burden on the module to guard all invariants *before* mutating state: [3](#0-2) 

This is exactly the anti-pattern present here: state (fund transfer/mint) is mutated at lines 93-117 *before* the invariant check (signature validity) at lines 124-173, violating the documented safety contract of the ISMP module interface.

### Title
Fund minting occurs before signature verification in `on_accept`, enabling replay-driven duplicate credit - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` mints/transfers the bridged amount to the beneficiary before validating the optional Ed25519/Sr25519/Ecdsa signature attached to calldata. If the signature is invalid, `on_accept` returns `Err(HftError::SignatureVerificationFailed)` *after* the funds have already moved. Per the ISMP request-handling contract, an `Err` from `on_accept` means the request receipt is never persisted, so the same `PostRequest` remains eligible for reprocessing by relayers until its timeout expires.

### Finding Description
The handler order is: authenticate source contract → decode message → mint/transfer funds to beneficiary (lines 93-117) → decode and dispatch optional calldata, which includes signature verification (lines 119-203). Any unprivileged actor who controls the message's `data` field (attacker-controlled cross-chain calldata) can submit a message with a non-empty `data.signature` that is syntactically well-formed but cryptographically invalid. The mint/transfer at lines 93-117 will succeed and commit before the code reaches the signature check, and the subsequent failure at lines 138-171 aborts `on_accept` with `Err`. Because `pallet-ismp`'s request handler only persists a request receipt for requests whose module `on_accept` returned `Ok` (as documented at `docs/content/protocol/ismp/requests.mdx:109-113`), the request is not marked processed and remains available to be resubmitted by a relayer with the exact same (still-invalid) signature and proof, re-triggering the mint/transfer again on each resubmission, until the request's `timeout_timestamp` is reached.

### Impact Explanation
Each replay of the same unconfirmed request re-executes the fund movement (mint/transfer) to the beneficiary while never successfully completing (and thus never being consumed). This breaks settlement atomicity between custody movement and full message success, allowing duplicate crediting of funds to the beneficiary purely from resubmitting the same proof/message, without any new source-chain lock. If the source chain eventually also processes a timeout for the same request (since the destination never records a receipt) and issues a refund/re-mint on the source side, the result is a duplicate fund credit / double refund across the two chains for a single locked amount — a direct loss/duplication of bridged assets.

### Likelihood Explanation
High. The attacker only needs unprivileged conditions already assumed to be in scope: a registered asset/contract mapping, non-empty `calldata` with an attached signature field, and a bogus/invalid signature. No privileged operator or malicious relayer collusion is required — the relayer's role is simply to submit the proof, which can be resubmitted by anyone as long as the request has not timed out and no receipt exists. The vulnerable ordering (mutate-then-validate) is directly visible in the source and contradicts the framework's own documented invariant requirement.

### Recommendation
Reorder `on_accept` so that all validation that can fail — decoding the calldata, decoding/verifying the `MultiSignature`, decoding and filtering the `RuntimeCall` — is performed **before** any custody-affecting mutation (the `NativeCurrency::transfer` / `Assets::transfer` / `Assets::mint_into` calls). Alternatively, wrap the entire `on_accept` body in a `frame_support::storage::with_transaction` block that reverts all pallet-level storage changes when any step after the mint returns an error, so a failed calldata execution cannot leave the mint/transfer committed while receipt persistence is skipped upstream.

### Proof of Concept
1. Register an asset and its `ContractToAsset` mapping and `Precisions` config for a source `(source, from)` pair as normal.
2. Craft an EVM/Substrate `PostRequest` whose ABI-encoded `Message` has a valid `to`/`amount`, and a non-empty `data` field decoding to `SubstrateCalldata` with `signature = Some(bogus_bytes)` that decodes successfully as a `MultiSignature` variant (e.g., `Ed25519`) but fails `sp_io::crypto::ed25519_verify`.
3. Submit this request through the standard ISMP request-handling path (`handlers::request::handle` → module `on_accept`).
4. Observe: the `NativeCurrency::transfer`/`Assets::mint_into` call at `module.rs:95-116` succeeds and the beneficiary balance increases (and a `Transfer`/`Mint` event is emitted) — but `on_accept` ultimately returns `Err(HftError::SignatureVerificationFailed)` at `module.rs:138-140`.
5. Confirm no request receipt was persisted for this request's commitment (per the documented behavior at `docs/content/protocol/ismp/requests.mdx:111-113`).
6. Resubmit the identical `PostRequest`/proof before `timeout_timestamp`; the beneficiary balance increases again, demonstrating duplicate crediting from a single source-chain lock.
