### Title
`AppKey` truncation lets an attacker collide with and drain/evict another app's paid bandwidth allowance - (File: modules/pallets/bandwidth/src/types.rs, modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth` keys every prepaid bandwidth ledger by `AppKey = BoundedVec<u8, ConstU32<32>>`, built with `AppKey::truncate_from(...)`, which silently drops any bytes beyond the first 32 instead of rejecting or hashing the input. The purchase message's `app` field is an attacker-controlled, unbounded `bytes` value (`PurchaseMessage::app: Vec<u8>`) decoded from arbitrary ABI calldata on any registered `BandwidthManager` chain, and the pallet also lets any payer choose an arbitrary `msg.chain` to credit (the documented "sponsorship" feature). This is the same fixed-capacity/overflow-collapse pattern as the external report — a value that should stay isolated to its own bucket instead silently overflows/collapses into a different one because the boundary is enforced by truncation rather than a hard rejection or a collision-free encoding.

### Finding Description
`AppKey` is defined as a 32-byte-bounded vector: [3](#0-2)  and every credit/consume path builds it with `truncate_from`, which keeps only the first 32 bytes of whatever byte string it is given: [4](#0-3) [5](#0-4) 

The purchase message body is decoded from raw ABI `bytes` with no length check on `app` (only `tier`, `months`, `chain` are validated): [1](#0-0) 

Because `app` can be any length greater than 32 bytes, an attacker who controls a `BandwidthManager.purchase()` call (any unprivileged EVM caller, since `purchase()` is a public entrypoint and the docs confirm the credit `chain`/`app` in the message body is independent of the caller and of `request.source`) can construct an `app` byte string whose first 32 bytes are identical to a victim's real (shorter, ≤32-byte) `AppKey`, e.g. by right-padding the victim's genuine 20-byte EVM address with 12 extra chosen bytes to reach length 32 and beyond, or crafting a longer string whose prefix collides with the victim's key. `Allowance::<T>::mutate(app_chain, app_key, ...)` then indexes the *same* storage row as the real victim app, because `AppKey` equality is on the truncated 32-byte value, not on the original untruncated bytes or their length. [6](#0-5) 

This collision is exploitable in either direction:
- **Griefing/loss of funds**: the attacker force-pushes new subscriptions into the victim's `(chain, app)` FIFO queue via cheap repeated purchases, evicting the victim's legitimately paid, unconsumed subscription once the 1024-entry cap is hit — the lost bytes are only logged (`SubscriptionEvicted`), never refunded. [7](#0-6) 
- **Unauthorized consumption / bandwidth theft**: because the gate's `try_consume` also builds its key with the same lossy truncation from the inbound request's `from` field, an attacker who can get a message accepted with a crafted `from` colliding on the same 32-byte prefix drains a victim's paid byte allowance for their own unrelated dispatches. [8](#0-7) 

The pallet's own documentation and code comments explicitly design the sponsorship model so that *any* payer can name *any* `(chain, app)` pair to credit and thereby write into that row — this is precisely the mechanism that gives an attacker free choice over the identifier that collides via truncation. [9](#0-8) 

### Impact Explanation
This directly matches the bounty's accepted "loss of funds" / "unauthorized execution" classes: a paid, unconsumed bandwidth subscription (real economic value, since tiers cost real fee-token payments) can be evicted or drained by an unrelated third party without ever compromising a relayer, prover, or admin key — the entire path runs through the public `purchase()` entrypoint and the pallet's own `on_accept`/gate logic. No malicious peer, governance actor, or leaked key is required; a normal attacker on a registered source chain suffices.

### Likelihood Explanation
The precondition (crafting an `app` byte string longer than 32 bytes whose prefix matches a target's key) is fully attacker-controlled and cheap to construct — it only requires knowing the victim's public 20-byte (or shorter) app identifier. The cost of the griefing variant scales with the tier price times number of pushes needed to reach the 1024 cap and evict the target entry, which can be nontrivial for very active queues but trivial for freshly credited, thinly populated ones (fewer purchases needed to evict the sole entry). The consumption-theft variant additionally depends on how permissively the ISMP router passes the raw `from` bytes into `try_consume`, which was not fully traceable in the available index; this part of the analysis carries some uncertainty since the router call-site wiring the request `from` field into `BandwidthGate::try_consume` was not directly inspected in full.

### Recommendation
- Reject purchase/consume calls where `app.len() > 32` instead of silently truncating via `AppKey::truncate_from`; use `AppKey::try_from` and bubble up an explicit error (e.g. `AppKeyTooLong`).
- Alternatively, key the storage by a fixed-size hash (e.g. `keccak256(app)`) rather than a truncated raw prefix, so no variable-length input can collide with a shorter, legitimately-registered key.
- Add a regression test asserting that two distinct `app` byte strings that share a 32-byte prefix never map to the same `AppKey`/storage row.

### Proof of Concept
1. Victim owns EVM app address `V` (20 bytes) and has a healthy, paid `TierFour` subscription credited to `(EVM-8453, V)` via a legitimate `BandwidthManager.purchase()` call.
2. Attacker calls `BandwidthManager.purchase()` on any registered source chain with `BandwidthPurchaseMsg.app = V || <12 arbitrary bytes>` (33 bytes total, first 20 bytes equal to `V`) and `chain = "EVM-8453"`, paying only the minimal `TierOne` price.
3. `pallet-bandwidth::on_accept` decodes this into `PurchaseMessage { app: V||junk, .. }` (no length check in `abi.rs`), then calls `AppKey::truncate_from(msg.app)`, producing the *same* 32-byte (or shorter, if `V` is 20 bytes, the collision is on the full 20-byte value since truncation only drops the tail past index 32 — for exact collision the attacker instead appends within the 32-byte window, e.g. crafts `app` as any string of length > 32 whose first 32 bytes equal the victim's registered key padded to 32) key as the victim's real row.
4. `push_subscription` appends the attacker's cheap subscription into the victim's FIFO list at `Allowance::<T>::mutate((EVM-8453, V_key), ...)`.
5. Attacker repeats the minimal purchase up to `MAX_SUBSCRIPTIONS` (1024) times targeting the same collided key, each time evicting the oldest entry in the FIFO list until the victim's genuine `TierFour` subscription is evicted and its `remaining_bytes` permanently lost (only surfaced via `SubscriptionEvicted`, with no refund path).

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
