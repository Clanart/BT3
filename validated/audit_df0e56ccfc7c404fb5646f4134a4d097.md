### Title
Silent, unconfirmed rewrite of a repository's git remote origin URL based on attacker-influenced GitHub API `clone_url` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically calls `gitStore.setRemoteURL()` to rewrite the local `origin` remote whenever the GitHub API's `clone_url` for the associated repository differs from the last-known cached value, without any user confirmation or explicit re-verification at the moment of use (push/fetch). This mirrors the `PartyGovernance` bug: a security-relevant parameter (`passThresholdBps` there, the trusted destination remote URL here) is not "locked in" per-operation but is instead re-derived from a mutable, externally-influenced source (`apiRepo.clone_url` returned by the GitHub API) and silently applied to state that controls where a user's commits are pushed/fetched from.

### Finding Description
`updateRemoteUrl` compares the repository's current git remote URL to the "old" cloneURL cached on the local `GitHubRepository` model, and to the "new" `clone_url` field on a freshly-fetched `IAPIRepository`: [1](#0-0) 

If the protocol is unchanged and the current remote still matches the previously cached `gitHubRepository.cloneURL` (i.e., the user hasn't manually customized the remote), but the API's `clone_url` no longer matches, the code calls `gitStore.setRemoteURL(...)` and silently rewrites `origin` to the new URL — with no user prompt, diff view, or confirmation dialog: [2](#0-1) 

The unit tests confirm this exact "auto-follow" behavior whenever the GitHub API reports a changed `clone_url` for a repo the user has cloned: [3](#0-2) 

The trust anchor here is the `clone_url`/`ssh_url` field of an `IAPIRepository` object returned by a GitHub API call — a value that is not scoped or pinned to the specific repository the user originally cloned, but is re-fetched on every repository metadata refresh via `GitHubRepository`, whose `cloneURL` field is itself just a cached copy of a prior API response: [4](#0-3) 

Because `IAPIRepository.clone_url` is attacker-influenceable in realistic scenarios (repository transfer/rename to a different owner, a compromised/malicious GHES endpoint, or any API response that legitimately or illegitimately changes what `clone_url` a given repo ID reports), the "cached" trust decision (`remoteUrlUnchanged` check against the *old* cloneURL) is not equivalent to verifying the *current* operation's target. There is no re-confirmation at push/fetch time — the remote is mutated ahead of time, silently, as a side effect of a background metadata refresh.

### Impact Explanation
This directly matches "silent corruption of what the user commits or pushes": the user believes they are pushing to `origin` pointing at repository X, but the origin URL can be silently rewritten to point at a different URL sourced from an API response, without the user's knowledge or consent. Subsequent `git push`/`git fetch` operations (`app/src/lib/git/push.ts`, `app/src/lib/git/fetch.ts`) will operate against whatever URL was silently written to `.git/config`, potentially sending code/credentials-bearing traffic (via `envForRemoteOperation`) to an unintended destination, or causing the user's work to be silently pushed to the wrong repository.

### Likelihood Explanation
The precondition ("current remote matches the previously cached cloneURL" i.e. user hasn't manually edited the remote) is the common case for the vast majority of GitHub Desktop users who never touch remote configuration by hand. The trigger is simply a change in what the GitHub API reports as `clone_url` for the repository's ID/owner/name combination — something that occurs naturally on repository rename/transfer, but which is not authenticated as "the same trusted target" beyond a bare URL structural comparison (`urlMatchesRemote`/protocol match), and is not something the user is asked to approve.

### Recommendation
Do not silently rewrite `origin` based on a background API refresh. At minimum:
- Require explicit user confirmation (a dialog, similar to other destructive/trust-changing actions in the app) before changing the remote URL in response to an API-reported change.
- Bind the trust decision to a stable, non-spoofable repository identity (e.g., the GitHub repository's numeric `id`) rather than only comparing URL strings, and audit that the `id` hasn't changed in a way indicating a different underlying repository.
- Avoid updating remotes as a side effect of routine metadata refresh; instead surface the mismatch to the user in the repository settings UI so they can decide whether to accept the change.

### Proof of Concept
1. User clones `https://github.com/victim/repo.git`; `GitHubRepository.cloneURL` is cached as this same URL and the local git remote `origin` is set identically.
2. The repository is later renamed/transferred on GitHub (or the app talks to a compromised/rogue endpoint) such that a subsequent `fetchRepository`/refresh call returns an `IAPIRepository` with `clone_url: https://github.com/attacker/repo.git` for the same repository ID.
3. On the next repository metadata refresh, `updateRemoteUrl` sees: protocols match, `remoteUrlUnchanged` is true (local remote still equals the old cached cloneURL), and `urlsMatch` is false — so it calls `gitStore.setRemoteURL('origin', 'https://github.com/attacker/repo.git')` with no user prompt, per [5](#0-4) .
4. The user's next `git push`/`git fetch` now targets the attacker-controlled URL, as validated by the existing test suite reproducing this exact flow: [3](#0-2) .

Note: I could not fully trace the exact call sites in `app-store.ts` that invoke `updateRemoteUrl` (grep found 3 matches but content wasn't retrieved before the tool budget ran out), so the precise refresh trigger frequency/context (e.g., whether it runs automatically on every app foreground/repository selection, or only after certain explicit user actions) is not fully confirmed from the index and would need direct inspection of `app-store.ts` to pin down exact triggering conditions.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

    const { gitHubRepository, gitStore } = await createRepository(
      t,
      apiRepository
    )

    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }
