### Title
ThresholdKeys deserialization accepts identity verification shares, yielding an identity group key for which signatures are universally forgeable - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is a missing zero-value check on a security-critical parameter (`owner = address(0)`), permanently destroying the object's security. The Serai analog lives in `ThresholdKeys::new` / `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`): neither the per-participant verification shares nor the computed `group_key` are checked for the identity (zero) point. Because `ThresholdKeys::read` decodes shares with `<C as Ciphersuite>::read_G` rather than the FROST `Curve::read_G` wrapper that explicitly rejects identity (`crypto/frost/src/curve/mod.rs`), an untrusted byte string can instantiate keys whose group key is the identity point.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs`, `ThresholdKeys::read` at ~lines 574-632) reads `n` verification shares with `<C as Ciphersuite>::read_G(reader)` and passes them into `ThresholdKeys::new`. `ThresholdKeys::new` (~lines 349-391) validates only:

- `verification_shares.len() == n`,
- participant indexes `<= n`,
- `Constant` interpolation only when `t == n`.

It then computes `group_key = Σ verification_shares[i] * interpolation_factor(i, 1..=t)` and stores it without any identity/zero check. In contrast, FROST's `Curve::read_G` (`crypto/frost/src/curve/mod.rs` lines 123-131) exists specifically to reject identity points on incoming points — a check the DKG deserialization path never applies.

An attacker who feeds crafted bytes to `ThresholdKeys::read` can set every verification share to the identity. The interpolated `group_key` is then the identity point, yet `ThresholdKeys::new` returns `Ok` and produces a fully "valid" `ThresholdKeys` object.

### Impact Explanation
A group key equal to the identity point is the cryptographic equivalent of `owner = address(0)`: any signature check of the form `s·G == R + c·A` with `A = 0` collapses to `s·G == R`. Anyone can forge a valid signature for that group key by choosing an arbitrary scalar `s` and setting `R = s·G`. Concretely:

- Funds controlled by a Bitcoin/Schnorr output keyed to this group key are spendable by anyone (or the key is unspendable garbage, equivalent to the locked-owner impact of the original report).
- Individual share verification in `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs` lines 474-489) verifies `verify_share` statements against `view.verification_share(l)`; an identity verification share makes `c·Y = 0`, so share verification is trivially satisfiable.
- The code itself acknowledges malformed deserialized keys are possible: `crypto/frost/src/sign.rs` lines 491-494 note "The only known way to cause this... is to deserialize a semantically invalid FrostKeys" — but nothing prevents deserialization from producing the worse outcome of a forgeable identity group key.

### Likelihood Explanation
Reachability requires an untrusted party to supply `ThresholdKeys` bytes to a deserialization entry point (`ThresholdKeys::read`), which is an explicitly in-scope untrusted-input surface. The crafted encoding is trivial: a valid `C::ID`, consistent `t`/`n`/`i`, an `Interpolation::Lagrange` tag, an arbitrary secret share, and `n` identity point encodings. All length/count checks in `ThresholdKeys::new` pass since identity points are valid `C::G` values under `Ciphersuite::read_G` (the identity rejection lives only in `Curve::read_G`, which this path never calls). No malicious quorum, validator, or peer collusion is required — only acceptance of attacker-controlled serialized keys.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), reject identity verification shares and an identity computed `group_key`:

```rust
for share in verification_shares.values() {
  if bool::from(share.is_identity()) {
    Err(DkgError::InvalidParticipant /* or a new ZeroShare error */)?;
  }
}
// after computing group_key:
if bool::from(group_key.is_identity()) {
  Err(...)?;
}
```

Additionally, consider routing point deserialization for key material through an identity-rejecting reader (as `Curve::read_G` does) so the invariant is enforced at the parsing boundary rather than relying on each constructor.

### Proof of Concept
```rust
// Given a Ciphersuite C, build a byte stream for ThresholdKeys::read:
//   u32 LE len(C::ID) || C::ID ||
//   u16 LE t || u16 LE n || u16 LE i (1 <= i <= n) ||
//   0x01 (Interpolation::Lagrange) ||
//   F: arbitrary secret share ||
//   n x G: identity point encoding (e.g., 32 zero bytes for Ristretto/ed25519)
let keys = ThresholdKeys::<C>::read(&mut crafted_bytes.as_slice()).unwrap();
// keys.group_key() == C::G::identity()
assert!(bool::from(keys.group_key().is_identity()));

// Forgery against the identity group key (Schnorr-style s*G == R + c*A, A = 0):
let s = C::F::random(&mut OsRng);
let R = C::generator() * s;
// c * identity == identity, so (R, s) verifies for any message/challenge c.
```

This mirrors the original finding exactly: a missing zero/identity check on a critical authority parameter (owner / group key) accepted through a public initialization/deserialization path, after which the object is permanently broken — here, universally forgeable rather than merely locked.
