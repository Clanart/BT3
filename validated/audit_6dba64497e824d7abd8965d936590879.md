### Title
Forked-remote pruning can race with an in-flight `_fetchRefspec` fetch, deleting the remote mid-fetch - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/stores/git-store.ts`)

### Summary
The Solidity bug is: `removeConnectedChain` deletes shared state (`connectedChains[schainHash]`) without checking for pending/in-flight messages against that chain, so an operation that is mid-flight loses its destination and the associated transfer is stuck or lost. The closest Desktop analog is `GitStore.pruneForkedRemotes` / `removeRemote`, which deletes a fork remote based on GitHub-API-supplied PR state while `AppStore._fetchRefspec` may simultaneously be fetching from that exact remote, and `_fetchRefspec` was deliberately built to bypass Desktop's own concurrency guard.

### Finding Description
`AppStore._fetchRefspec` explicitly does **not** go through `withPushPullFetch`, the mutex Desktop uses everywhere else to serialize push/pull/fetch operations: [1](#0-0) 

The comment on the method itself acknowledges the tradeoff: "As this action is required to complete when viewing a Pull Request from a fork, it does not opt-in to checks that prevent multiple concurrent network actions. This might require some rework in the future to chain these actions."

Concurrently, `GitStore.pruneForkedRemotes` computes remotes to delete purely from GitHub API data (open PR list) and local branches, and deletes them with no coordination with any fetch/push in flight: [2](#0-1) 

The remotes-to-prune decision itself is driven entirely by attacker-influenceable GitHub state — whether a PR is open and what `cloneURL` its head repository reports: [3](#0-2) 

`removeRemote` runs `git remote remove <name>` unconditionally, regardless of any concurrent git process using that remote: [4](#0-3) 

The pull request list (`this.pullRequestCoordinator.getAllPullRequests`) is refreshed independently of, and asynchronously to, the moment a user opens a PR-from-fork checkout, which is what triggers `_fetchRefspec` for the fork remote. Because `_fetchRefspec` was intentionally exempted from `isPushPullFetchInProgress` locking, there is no invariant preventing `pruneForkedRemotes` from running (e.g., triggered by a repo owner closing the PR at the exact moment the fetch starts) and calling `git remote remove <fork-remote>` while `git fetch <fork-remote> <refspec>` is executing against the same remote name.

### Impact Explanation
If the remote entry disappears mid-fetch, the in-flight `git fetch` targeting that remote name can fail unpredictably or race against the app re-adding a differently-scoped remote under the same generated name (`ForkedRemotePrefix`-prefixed) for a subsequent PR. Because the remote name→URL mapping is what Desktop trusts to resolve which upstream a fetched ref came from, corruption of that mapping during a race window can result in the app associating fetched refs/commits with the wrong fork, or dropping the fetch outcome silently — matching the "silent corruption of what the user commits/checks out" impact class, driven entirely by attacker-controlled GitHub API state (PR open/closed, fork clone URL), with no local access required.

### Likelihood Explanation
This requires a narrow timing window: a user must open a PR-from-fork checkout (triggering `_fetchRefspec`) while, concurrently, the PR list refresh determines the same PR is now closed and triggers pruning of the associated fork remote. An attacker who controls the target repository (e.g., a malicious/compromised maintainer or bot) can close/reopen PRs to increase the probability of hitting this window, but exploitation is opportunistic and probabilistic rather than deterministic, similar to the original finding's "medium severity, no easy fix at this layer" characterization.

### Recommendation
Route `_fetchRefspec` through the same mutex used by `withPushPullFetch` (or a per-remote lock keyed by remote name) so that fetches and remote-pruning cannot interleave for the same remote. Alternatively, have `pruneForkedRemotes` check/set an in-flight marker per remote name before calling `removeRemote`, and defer/skip pruning of any remote currently in use, mirroring the report's suggested mitigation of "pausing" removal until pending operations complete.

### Proof of Concept
1. User A opens Desktop and views a pull request from a fork; Desktop calls `_fetchRefspec(repository, refspec)` which fetches directly from the fork remote (`github-desktop-<fork>`), bypassing the `isPushPullFetchInProgress` guard (`app/src/lib/stores/app-store.ts:5875-5885`).
2. Concurrently, the repository owner (attacker-controlled GitHub state) closes that same PR right as the fetch starts.
3. Desktop's periodic `pullRequestCoordinator.getAllPullRequests` refresh completes and calls into `GitStore.pruneForkedRemotes`, which now considers the PR closed and calls `removeRemote(repository, 'github-desktop-<fork>')` (`app/src/lib/stores/git-store.ts:1743-1752`, `app/src/lib/git/remote.ts:39-54`) while the fetch from step 1 is still running against that same remote name.
4. The in-flight `git fetch` either errors out unpredictably or, if the app later re-adds a remote under the same generated name for a different fork, subsequent operations can resolve refs against the wrong upstream — no code path in `_fetchRefspec` or `pruneForkedRemotes` guards against this interleaving.

```typescript
export function findForkedRemotesToPrune(
  remotes: readonly IRemote[],
  openPRs: ReadonlyArray<PullRequest>,
  allBranches: readonly Branch[]
) {
  const prRemoteUrls = new Set(
    openPRs.map(pr => pr.head.gitHubRepository.cloneURL)
  )
  const branchRemotes = new Set(
    allBranches.map(branch => branch.upstreamRemoteName)
  )

  return remotes.filter(
    r =>
      r.name.startsWith(ForkedRemotePrefix) &&
      !prRemoteUrls.has(r.url) &&
      !branchRemotes.has(r.name)
  )
}
```

```typescript
/** Removes an existing remote, or silently errors if it doesn't exist */
export async function removeRemote(
  repository: Repository,
  name: string
): Promise<void> {
  const options = {
    successExitCodes: new Set([0, 2, 128]),
  }

  await git(
    ['remote', 'remove', name],
    repository.path,
    'removeRemote',
    options
  )
}
```
