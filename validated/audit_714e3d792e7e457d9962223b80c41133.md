## Title
Unauthenticated `DuplicateShred.from` field lets a single attacker identity bypass the per-node buffer cap in `DuplicateShredHandler`, causing unbounded memory growth - (File: `gossip/src/duplicate_shred_handler.rs`)

## Summary
The Hats Protocol bug allowed an attacker to defeat a per-parent child-count cap by inserting *phantom* (unvalidated, non-existent) intermediate identifiers into a hierarchy, because the enforcement code trusted the structure of the ID rather than verifying each level actually existed. The Agave analog is structurally the same: `DuplicateShredHandler::handle_shred_data` enforces a "per-identity" resource cap (`MAX_NUM_ENTRIES_PER_PUBKEY`) keyed on a field (`DuplicateShred.from`) that is taken directly from attacker-supplied, unauthenticated wire data instead of the actual cryptographic signer of the gossip message. This lets one real network identity fabricate unlimited "phantom" identities and escape the intended per-identity bound.

## Finding Description
`DuplicateShred` is a gossip `CrdsData` payload used to reassemble a two-shred duplicate-slot proof from chunks: [1](#0-0) 

Its `from: Pubkey` field is meant to identify which node produced the proof, but `Sanitize` never checks it against the actual signer of the enclosing `CrdsValue` - it only validates wallclock/chunk-index bounds and calls `self.from.sanitize()`, a no-op structural check: [2](#0-1) 

On the honest send path, `push_duplicate_shred` always sets `from: self_pubkey` (the sender's own key) and self-limits itself to `MAX_DUPLICATE_SHREDS` recycled slots: [3](#0-2) 

But that limiting logic is purely client-side courtesy in the *sending* helper - nothing forces an attacker crafting raw gossip payloads to route through `push_duplicate_shred`, or to set `from` to their real pubkey.

On the receiving side, `DuplicateShredHandler` buffers incoming chunks keyed by `(Slot, Pubkey)`, where `Pubkey` is `chunk.from` — the unverified field: [4](#0-3) 

The intended safety valve is a per-pubkey cap (`MAX_NUM_ENTRIES_PER_PUBKEY = 128`) and a total capacity (`BUFFER_CAPACITY = 512 * 128`), enforced only lazily once the buffer has grown to *twice* that capacity: [5](#0-4) [6](#0-5) 

Because the per-pubkey key is attacker-controlled forged data rather than the real gossip signer, one real network identity can populate the buffer with arbitrarily many distinct `(slot, fake_pubkey)` entries, each holding up to `MAX_NUM_CHUNKS = 3` `DuplicateShred` chunks (each chunk's `Vec<u8>` payload sized up to the max gossip packet payload). The per-identity cap of 128 entries is meaningless because the "identity" is fabricated per message at zero cost, exactly mirroring how Hats' per-admin child-count cap was meaningless once phantom (unvalidated) intermediate hat IDs could be inserted into the admin path.

## Impact Explanation
This is a remotely triggerable resource-exhaustion primitive reachable by any unprivileged gossip participant (no elevated stake, leader status, or trust required) — it falls under the valid "non-RPC remote exhaustion/crash" category. An attacker can drive `buffer` to `BUFFER_CAPACITY * 2` (131,072) entries using only forged `from` values before the amortized pruning logic even executes, consuming memory proportional to `entries * MAX_NUM_CHUNKS * max_chunk_size`. Because the eventual eviction is stake-weighted (`staked_nodes.get(&pubkey)`), and the forged pubkeys are guaranteed to have zero stake, the pruning cost itself (a full-buffer scan and `select_nth_unstable_by_key` sort) is also driven up on every overflow cycle, adding CPU cost to the memory pressure. This can degrade or crash a validator's gossip-processing path without needing sustained bandwidth from many distinct physical peers or real stake — one identity is sufficient to mint unlimited logical "identities" for the purposes of this specific cap.

## Likelihood Explanation
High. No cryptographic or protocol barrier prevents an attacker from setting `DuplicateShred.from` to any value independent of the actual signer; `Sanitize` explicitly does not perform this check. Only a single valid, already-established gossip identity (which is cheap/easy to obtain) is required to originate the crafted `CrdsData::DuplicateShred` messages; the cap this bug bypasses (`MAX_NUM_ENTRIES_PER_PUBKEY`) is the only defense against buffer bloat from a single identity, and it is fully circumvented.

## Recommendation
Do not trust `DuplicateShred.from` as the per-identity accounting key in `DuplicateShredHandler`. Instead:
- Bind the buffer/accounting key to the actual signer/pubkey of the enclosing `CrdsValue` (the value that is cryptographically verified by gossip ingestion), not to a field embedded inside the payload.
- Alternatively, add an explicit check that `chunk.from` equals the CRDS value's own pubkey before accepting the chunk, rejecting otherwise (mirroring the "each level must correspond to something real" fix - `isValidHatId` - applied in the Hats Protocol remediation).
- Consider capping total buffer growth strictly (not lazily at 2x capacity) and account memory by real, verified sender identity.

## Proof of Concept
Conceptually (mirrors the Hats "phantom admin path" trick, substituting "phantom pubkey" for "phantom hat level"):
1. Attacker holds one real, valid gossip keypair/identity.
2. Attacker crafts `N` (N ≫ 131,072) `CrdsData::DuplicateShred` payloads, each with:
   - a distinct/random 32-byte value in the `from` field (not their real pubkey),
   - `num_chunks = 3`, `chunk_index = 0`, and a maximal `chunk` payload,
   - a unique `slot` or unique gossip `index` so each message is treated as new by the delivery pipeline (bypassing crds-table dedup on the honest `push_duplicate_shred` codepath, since the attacker is not required to use that helper).
3. Attacker signs and sends these as ordinary gossip Push/PullResponse messages using their single real identity.
4. `DuplicateShredHandler::handle` → `handle_shred_data` inserts each into `buffer` keyed by `(slot, chunk.from)`: [7](#0-6) 
5. Because `chunk.from` differs on every message, `MAX_NUM_ENTRIES_PER_PUBKEY` never triggers (each "pubkey" only has 1 entry), and the buffer grows unbounded until the lazy `maybe_prune_buffer` threshold (`BUFFER_CAPACITY * 2`) is reached, at which point the victim must perform an O(n) scan/sort over attacker-controlled, zero-stake entries.

Note: I was not able to fully trace the upstream gossip ingestion path (`duplicate_shred_listener.rs` / `crds_gossip.rs` inbound processing) within this session to confirm whether an additional layer enforces stricter per-sender rate limiting before `handle()` is invoked; this should be verified in a full Devin session with repository access before treating this as fully confirmed, since such a layer (if present and strict enough) could reduce the practical severity of this finding.

    fn handle_shred_data(&mut self, chunk: DuplicateShred) -> Result<(), Error> {
        if !self.should_consume_slot(chunk.slot) {
            return Ok(());
        }
        let slot = chunk.slot;
        let num_chunks = chunk.num_chunks();
        let chunk_index = chunk.chunk_index();
        if usize::from(num_chunks) > MAX_NUM_CHUNKS || chunk_index >= num_chunks {
            return Err(Error::InvalidChunkIndex {
                chunk_index,
                num_chunks,
            });
        }
        let entry = self.buffer.entry((chunk.slot, chunk.from)).or_default();
        *entry
            .get_mut(usize::from(chunk_index))
            .ok_or(Error::InvalidChunkIndex {
                chunk_index,
                num_chunks,
            })? = Some(chunk);

    fn maybe_prune_buffer(&mut self) {
        // The buffer is allowed to grow to twice the intended capacity, at
        // which point the extraneous entries are removed in linear time,
        // resulting an amortized O(1) performance.
        if self.buffer.len() < BUFFER_CAPACITY.saturating_mul(2) {
            return;
        }
        self.consumed.retain(|&slot, _| slot > self.last_root);
        // Filter out obsolete slots and limit number of entries per pubkey.
        {
            let mut counts = HashMap::<Pubkey, usize>::new();
            self.buffer.retain(|(slot, pubkey), _| {
                *slot > self.last_root
                    && should_consume_slot(*slot, &self.blockstore, &mut self.consumed)
                    && {
                        let count = counts.entry(*pubkey).or_default();
                        *count = count.saturating_add(1);
                        *count <= MAX_NUM_ENTRIES_PER_PUBKEY
                    }
            });
        }
        if self.buffer.len() <= BUFFER_CAPACITY {
            return;
        }
        // Lookup stake for each entry.
        let staked_nodes = self.epoch_specs.current_epoch_staked_nodes();
        let mut buffer: Vec<_> = self
            .buffer
            .drain()
            .map(|entry @ ((_, pubkey), _)| {
                let stake = staked_nodes.get(&pubkey).copied().unwrap_or_default();
                (stake, entry)
            })
            .collect();
        // Drop entries with lowest stake and rebuffer remaining ones.
        buffer.select_nth_unstable_by_key(BUFFER_CAPACITY, |&(stake, _)| Reverse(stake));
        self.buffer.extend(
            buffer
                .into_iter()
                .take(BUFFER_CAPACITY)
                .map(|(_, entry)| entry),
        );
    }
