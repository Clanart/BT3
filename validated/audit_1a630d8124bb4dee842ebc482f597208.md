## Analysis Summary

The external report's core defect is a **decimal-precision mismatch that silently corrupts value calculations across a token boundary** (hardcoded 18-decimal assumption vs. actual token decimals). The Hyperbridge analog is the decimal-scaling arithmetic in the `hyper-fungible-token` pallet's cross-chain amount conversion, where — unlike the ERC-20 metadata cosmetic bug — a corrupted decimal difference directly changes the **real token amount minted/escrowed across the bridge**, i.e., fund custody, not just display.

### Title
Silent decimal-underflow clamp in `convert_to_erc20`/`convert_to_balance` can mint inflated cross-chain amounts - (`modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_erc20` and `convert_to_balance` compute the scaling exponent with `saturating_sub`, which silently clamps to `0` instead of reverting whenever `erc_decimals < local_decimals`. When that happens, an amount that should be divided down before being embedded in the cross-chain `Message` is instead forwarded unscaled, so the destination side credits far more value than was actually escrowed/burned on the source chain.

### Finding Description
`convert_to_erc20` scales a local balance up to the destination ERC-20 precision: [1](#0-0) 

and the inverse `convert_to_balance` scales an incoming ERC-20 `U256` down to local precision: [2](#0-1) 

Both use `erc_decimals.saturating_sub(local_decimals)` (or the reverse) as the power-of-ten exponent. `saturating_sub` returns `0` whenever the subtrahend exceeds the minuend, rather than erroring. This means:
- In `send()`, `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` is dispatched as the cross-chain `Message.amount`: [3](#0-2) 

If the configured `Precisions` entry for a given `(asset, destination)` pair ever has `erc_decimals < local decimals` (native `T::Decimals` or the local asset's `fungibles::metadata::Inspect::decimals`), the intended down-scaling (`amount / 10^(local_decimals - erc_decimals)`) never happens — the exponent silently becomes `0` and the raw, unscaled local amount is sent as-is as the destination ERC-20 amount.

The pallet even defines an error variant for exactly this precondition, `ErcDecimalsBelowLocal`: [4](#0-3) 

but no invocation of this check is present in the `send` extrinsic reviewed — the arithmetic helper itself never enforces or reports the violated precondition; it just quietly clamps. Documented intent confirms the assumption that erc_decimals conversions "scale down from ERC20 precision," i.e., that `erc_decimals >= local_decimals` is assumed to always hold, not defensively verified at the point of use: [5](#0-4) 

### Impact Explanation
If any asset is registered (via governance's `register_token`/`update_token`, or simply misconfigured) with EVM-side decimals lower than the local asset's decimals for a given destination chain, every unprivileged user calling the public `send` extrinsic with that asset receives a destination-side `Message.amount` that is `10^(local_decimals - erc_decimals)` times larger than what was actually escrowed or burned locally. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint or release that inflated amount to the recipient, directly stealing value from the pallet's escrow or minting unbacked tokens — a false-state/unauthorized-mint condition reachable through a normal, unprivileged cross-chain transfer, not through a compromised relayer or prover.

### Likelihood Explanation
Exploitability depends entirely on whether any registered `(asset, chain)` pair in `Precisions` has `erc_decimals < local_decimals`. This is plausible in practice: many Substrate assets use non-18 decimals (e.g., DOT=10, native currencies commonly 10–12) while paired EVM tokens can use 6 (USDC-style) or other lower precisions. Nothing in the code path examined prevents such a registration from being accepted, and the conversion helper itself provides no runtime guard — it was clearly anticipated (`ErcDecimalsBelowLocal` exists) but not wired into the actual arithmetic or into the `send` flow shown.

### Recommendation
Replace `saturating_sub` with a checked subtraction in both `convert_to_erc20` and `convert_to_balance`, returning/propagating `Error::<T>::ErcDecimalsBelowLocal` (or the destination-side analog) whenever `erc_decimals < local_decimals` instead of silently clamping the exponent to zero. Additionally enforce this invariant at `register_token`/`update_token` time so no such configuration can ever be persisted.

### Proof of Concept
1. Governance (or a misconfiguration) registers asset `X` with local `decimals = 12` and, for destination chain `D`, `Precisions[X][D] = 6` (a plausible EVM USDC-style pairing) — the code has no check preventing this combination.
2. An unprivileged user calls `send(SendParams { asset_id: X, destination: D, amount: 1_000_000, .. })`, escrowing/burning `1_000_000` local units (`0.000001` token at 12 decimals).
3. `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(12) = 0`, so `convert_to_erc20` returns `1_000_000 * 10^0 = 1_000_000` unscaled instead of the correct `1_000_000 / 10^6 = 1`.
4. The destination contract receives `Message.amount = 1_000_000` at its native 6-decimal precision — i.e., `1.0` full token — a `10^6`-times inflation of the value actually escrowed, minted/released to the attacker-controlled recipient on `D`. [6](#0-5) [7](#0-6)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
