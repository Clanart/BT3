Based on the README documentation confirming that per the callbacks design, "If an ICS-20 packet is directed towards EVM callbacks, and is formatted incorrectly, then EVM callbacks returns an error and the recv packet application state changes are reverted and an error acknowledgement is returned" [1](#0-0) , an error returned from `IBCReceivePacketCallback` causes the *entire* `OnRecvPacket` state to revert and an error acknowledgement to be sent back to the source chain, which will trigger a refund there. This changes the impact profile of the balance-equality check significantly.

### Title
Donation-griefing of isolated-address balance check permanently blocks IBC callback receipt and can force a refund of already-delivered funds - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`IBCReceivePacketCallback` enforces that the deterministic, sender-derived isolated address holds **exactly zero** tokens after the destination callback executes, mirroring the flawed `balanceOfSelf() == args.amount` pattern from the external report: it checks an absolute post-state balance instead of a delta relative to what the callback itself should have moved.

### Finding Description
`IBCReceivePacketCallback` computes a deterministic `isolatedAddr` from `GenerateIsolatedAddress(destChannel, sender)` [2](#0-1)  — a value fully predictable by anyone off-chain (channel IDs are public, and `sender` is an attacker-chosen string on the source chain). After running the user-supplied `dest_callback` contract call and writing its effects to state via `writeFn()`, the keeper asserts the isolated address's ERC-20 balance is exactly zero: [3](#0-2) 

This is an *absolute* balance check, not a "delta" check comparing before/after values, so it cannot distinguish tokens legitimately delivered by the current packet from tokens an attacker pre-funded ("donated") directly to that address via a normal ERC-20 `transfer()` on the destination chain before the packet ever arrives. Because `isolatedAddr` is fully predictable from public channel/sender values, an attacker can:
1. Compute the isolated address for `(destChannel, sender)` in advance.
2. Send even 1 wei of the token-pair ERC20 to that address on the EVM side.
3. Cause every future `IBCReceivePacketCallback` for that `(channel, sender)` pair to fail the zero-balance check, regardless of whether the callback contract behaved correctly.

Per the module's own documented execution flow, a callback error here causes "the recv packet application state changes are reverted and an error acknowledgement is returned" [1](#0-0) . An error acknowledgement propagates back to the source chain and triggers the standard ICS-20 refund path there, unlocking/re-minting the sender's original coins on the source chain.

### Impact Explanation
This does not clearly rise to the Critical bar defined for this scope. The `writeFn()` commit happens on the same `ctx` used for the recv packet processing, and per the documented middleware contract, an error at this stage reverts the *entire* recv-packet state transition (approve, callback execution, and any transfers effected during the destination callback), not just this check — implying the token minting for the ICS-20 receive itself is also rolled back before the error acknowledgement is returned. If that documented invariant fully holds, the result is a pure denial-of-service against any callback-based receiver for a specific `(channel, sender)` pair (Medium/DoS, matching the External Report's own severity), not a duplication of value, because both sides of the packet end up consistent (refunded on source, nothing credited on destination).

I could not fully verify, from the available code and index, whether the revert genuinely covers the ICS-20 mint that happens upstream in `transfertypes.Module.OnRecvPacket` (prior to invoking `ContractKeeper.IBCReceivePacketCallback`) within the same atomic `ctx`, versus already being committed at an outer layer before this callback runs. If the upstream mint/unlock to the isolated address is *not* rolled back by this specific error path (i.e., it was already committed in a parent, non-cached context before the callback keeper is invoked), then a griefer could force a scenario where the destination chain retains delivered value while the source chain independently refunds the sender — a double-spend. Confirming this ordering requires inspecting the vendored `ibc-go` `callbacks` middleware's `ProcessCallback`/`OnRecvPacket` implementation and the exact context (cached vs. base) used for the ICS-20 token transfer itself, which is outside what I could locate in the indexed contents of this repository.

### Likelihood Explanation
High. Computing the isolated address only requires knowing the public destination channel ID and choosing an arbitrary sender string on the source chain; no privileged access, relayer collusion, or race condition is needed. A single low-value donation transaction permanently poisons that specific `(channel, sender)` route for any future dest-callback packet.

### Recommendation
Replace the absolute zero-balance check with a delta-based check: snapshot the isolated address's ERC-20 balance immediately before invoking the callback contract, and after the callback assert that the balance decreased by exactly the amount that was approved/transferred in for this packet (i.e., verify the callback moved *its own* newly-received tokens, ignoring any pre-existing balance). Additionally, confirm (and if necessary restructure) that any upstream ICS-20 mint/unlock into the isolated address occurs in the same reverted scope as this callback check, so that a forced callback failure cannot leave the destination chain crediting funds while the source chain also refunds the sender.

### Proof of Concept
1. Attacker determines the destination channel ID `C` (public) they intend to grief and chooses a `sender` string `S`.
2. Attacker computes `isolatedAddr = GenerateIsolatedAddress(C, S)` off-chain using the same algorithm as `x/ibc/callbacks/types/keys.go`.
3. Attacker sends 1 wei of the relevant token-pair ERC20 directly to `isolatedAddr` on the destination EVM chain via a normal `transfer()` call.
4. Any legitimate IBC transfer from `sender = S` over channel `C` carrying a `dest_callback` memo now fails the `receiverTokenBalance.Cmp(big.NewInt(0)) != 0` check in `IBCReceivePacketCallback` at [4](#0-3) , permanently causing an error acknowledgement for that route until the residual balance is manually cleared (which the isolated address cannot do, since it has no private key).
