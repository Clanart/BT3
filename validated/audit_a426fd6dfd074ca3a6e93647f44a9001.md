### Title
Out-of-range participant index in DKG blame path causes panic (HashMap index on missing key) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The libfpx CVE is a NULL-pointer dereference reachable via a crafted file — i.e., attacker-controlled bytes drive the code into a dereference of missing state and crash the process. The Rust analog in Serai is a panic on a missing `HashMap` key: `BlameMachine::blame_internal` (and the standalone `AdditionalBlameMachine::blame`) index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with participant indexes that are never validated against the DKG's `n`. A blame/accusation message naming a `sender` or `recipient` index that was never registered crashes the node instead of returning an error.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender: Participant` and `recipient: Participant` directly from the caller and pass them to `blame_internal`. Inside `blame_internal`:

- `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)` at `crypto/dkg/pedpop/src/lib.rs:597-601` indexes `self.commitments` by `sender`. `self.commitments` only contains entries for participants `1 ..= n` (populated in `verify_r1`/`AdditionalBlameMachine::new` over `all_participant_indexes()` / `1 ..= n`). Any `sender` with `u16::from(sender) > n` hits a `HashMap` index panic.
- Earlier, `decrypt_with_proof` at `crypto/dkg/pedpop/src/encryption.rs:388` evaluates `self.enc_keys[&decryptor]`, which panics identically if `recipient` (`decryptor`) is a `Participant` outside the registered set.

The upstream validation gap exists because `Participant::new` only rejects `0` (`crypto/dkg/src/lib.rs:29-35`); it imposes no upper bound. The on-wire format confirms this: `Transaction::InvalidDkgShare` in `coordinator/src/tributary/transaction.rs:346-353` parses `accuser` and `faulty` with `Participant::new(...)` and accepts any non-zero `u16`, with no `<= n` check before these values flow into blame resolution. The code itself acknowledges this hazard — the `AdditionalBlameMachine::new` doc comment states "Usage of invalid commitments ... may cause everything from inaccurate blame to panics" (`crypto/dkg/pedpop/src/lib.rs:646-648`) — but the panic is reachable through the public `blame` API with attacker-influenced indexes, not just through invalid construction.

### Impact Explanation
An unprivileged participant (or any party able to submit/relay an accusation naming an out-of-range `Participant`) can crash every node that evaluates the blame claim. Because blame evaluation is part of DKG fault handling, a single crafted accusation with `sender` or `recipient` in `(n, u16::MAX]` turns a recoverable `PedPoPError` path into a process abort, denying service during exactly the window where the protocol must adjudicate faults. This mirrors the CVE's impact: remote, unauthenticated-input-triggered denial of service via a missing-state dereference.

### Likelihood Explanation
Reachability requires only that attacker-influenced `Participant` values reach `blame`/`blame_internal`. The serialization layer explicitly accepts arbitrary non-zero `u16` participant indexes from wire bytes (`Participant::new` checks only `i == 0`), and `EncryptedMessage::read`/`EncryptionKeyProof::read`/`Commitments::read` all happily parse the accompanying message bodies. No cryptographic validity is needed to reach the indexing panic — in the `proof.is_some()` path the panic at `enc_keys[&decryptor]` occurs after PoP verification of `msg`, but the `self.commitments[&sender]` index in `blame_internal` is reached for any well-formed message once a valid share scalar parses, and the `enc_keys[&decryptor]` panic is reachable whenever the accusation carries a `Some(proof)` with a valid DLEq (which the accuser can generate for their own keys). Caveat: the exact call-site wiring in the coordinator isn't fully visible in the indexed code; if an upper-layer bounds-check on `n` exists before calling `blame`, reachability narrows accordingly.

### Recommendation
Replace the panicking `HashMap` indexes with checked lookups that return `PedPoPError`:

- In `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:596-601`): use `self.commitments.get(&sender)` and return `PedPoPError::MissingParticipant(sender)` (or treat out-of-range `sender` as faulty-by-omission → return `sender`) instead of `self.commitments[&sender]`.
- In `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:388`): use `self.enc_keys.get(&decryptor)` and map `None` to `DecryptionError::InvalidProof`.
- Additionally validate `sender`/`recipient` against `1 ..= n` at the entry points (`BlameMachine::blame`, `AdditionalBlameMachine::blame`) and at the transaction layer when parsing `InvalidDkgShare`.

### Proof of Concept
```rust
// Any participant index > n that is non-zero parses successfully
let evil = Participant::new(u16::from(n) + 1).unwrap(); // accepted: only 0 is rejected

// Constructed via AdditionalBlameMachine::new(context, n, msgs) over senders 1..=n,
// or via BlameMachine obtained from KeyMachine::calculate_share.
// Then, any accusation naming `evil` as the sender:
let faulty = machine.blame(
  evil,            // sender: not in self.commitments (only 1..=n registered)
  honest,          // recipient
  msg,             // any EncryptedMessage read via EncryptedMessage::read
  proof,           // Option<EncryptionKeyProof>
);
// Panics inside blame_internal at `&self.commitments[&sender]`
// (pedpop/src/lib.rs ~line 599) — index into HashMap with absent key.
// Symmetrically, `recipient = evil` panics at `self.enc_keys[&decryptor]`
// (pedpop/src/encryption.rs:388) when `proof` is Some.
```

Both panics are index-on-absent-key, the direct Rust analog of the CVE's NULL-pointer dereference: attacker-supplied bytes steer the code to dereference state that was never populated, aborting the process rather than returning a `PedPoPError`.
