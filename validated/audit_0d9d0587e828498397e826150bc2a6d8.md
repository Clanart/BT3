### Title
Race condition in `Transaction.ValidateSender`/`ValidateFeePayer` causes fee-payer/sender field confusion when a shared `*Transaction` pointer is validated concurrently - ([File: blockchain/types/transaction.go])

### Summary
`blockchain/types/transaction.go`'s `ValidateSender` and `ValidateFeePayer` mutate the shared, pointer-referenced fields `tx.validatedSender` and `tx.validatedFeePayer` on the same `*types.Transaction` object under a mutex, but the *decision logic* embedded in the critical section depends on a "not-yet-set" sentinel value (the zero address) and on the transient state left by a concurrently-running call. This is structurally the same bug class as CVE-2017-17712: a flag/derived value (`hdrincl`) that is set-then-consulted without atomicity across the whole operation, so a racing second caller can observe and act on a half-initialized value.

### Finding Description
`ValidateSender` seeds both `validatedSender` and `validatedFeePayer` to the sender address on first touch: [1](#0-0) 

`ValidateFeePayer` later only overwrites `validatedFeePayer` if it still equals `validatedSender` (i.e., "hasn't been corrected yet"): [2](#0-1) 

Both are invoked together from `AsMessageWithAccountKeyPicker`, which is a normal per-transaction validation entry point used across the node (tx pool add/promote, state prefetcher, miner/worker block building, tracers, `eth_call`/`estimateGas`-style APIs): [3](#0-2) [4](#0-3) 

Because `*types.Transaction` is a heap-allocated object shared by pointer across the tx pool, the state prefetcher, block builder (`work/worker.go`), and RPC/tracer code paths, it is plausible for two independent code paths to call `AsMessageWithAccountKeyPicker` (and therefore `ValidateSender`/`ValidateFeePayer`) on the *same* transaction object concurrently — e.g., the tx pool validating/promoting the pending transaction while the prefetcher or another validation pass concurrently re-validates it before block inclusion. The developers were aware this can go wrong: there is an existing regression test explicitly built to catch it: [5](#0-4) 

The race window: `ValidateSender` sets `validatedFeePayer = validatedSender` (both equal to the tx sender) as a placeholder value. Any reader of `tx.ValidatedFeePayer()` that runs in the window before `ValidateFeePayer` corrects it — including a second concurrent validation/execution path — can observe the sender address as the fee payer instead of the real fee payer. Since `Execute()` builds its `AccountRef` directly from these mutable fields: [6](#0-5) 
a consumer of the placeholder (uncorrected) state would execute/charge fees against the wrong account (sender instead of the designated fee payer, or vice versa depending on interleaving), i.e., the transaction is applied with an incorrect fee-payer attribution.

### Impact Explanation
If two validation/execution contexts operate on the same `*Transaction` pointer concurrently (tx pool validation vs. a concurrent prefetch/second validation/mempool re-check), a fee-delegated transaction can transiently expose `ValidatedFeePayer() == ValidatedSender()` to a reader instead of the real fee payer. Any code path that consumes this transient/incorrect value to apply state (charge gas, execute the message) would misattribute the fee payment — an unprivileged fee-delegation counterparty (the designated fee payer or the sender) could end up paying (or evading) fees they should not, a form of fee-delegation abuse/incorrect value movement. Because this affects consensus-relevant execution results (which account is debited), it could also cause state divergence between nodes if the race is hit non-deterministically during block validation.

### Likelihood Explanation
Exploitation requires triggering genuine concurrent validation of the same transaction pointer, which is a narrow, timing-dependent race rather than a directly attacker-controlled trigger — hence the kernel CVE's own rating is "AC:H" (race condition, non-trivial to win reliably). The Kaia codebase already has a dedicated regression test (`TestRaceAsMessageWithAccountPickerForFeePayer`) demonstrating the race reproduces with high iteration counts (10,000 iterations with `-race`), confirming the race is real and repeatably observable under load, though I could not fully verify (given available search results) a concrete unlocked production caller pair that runs on the exact same shared `*Transaction` pointer concurrently in a live node without triggering it only under test-harness conditions. This uncertainty should be resolved by a deeper trace of `TxPool` pointer-sharing with `statePrefetcher`/`worker` during ordinary block-building/tx-pool operation.

### Recommendation
- Make `ValidateSender` + `ValidateFeePayer` set the final `validatedSender`/`validatedFeePayer`/`validatedGas` atomically as a single locked operation instead of two independently-locked mutations with an interleaved crypto-recovery step in between.
- Avoid using "sender == feePayer" as an implicit "not yet validated" sentinel; introduce an explicit `validated bool` flag (protected by `tx.mu`) so partially-validated state is never observably indistinguishable from validated state.
- Audit and eliminate any production code path (tx pool, prefetcher, worker, tracer, gasless module) that can call `AsMessageWithAccountKeyPicker`/`ValidateSender`/`ValidateFeePayer` concurrently on the same `*types.Transaction` pointer; if concurrency is required for performance, validate on a private copy of the transaction and only publish results once fully validated.

### Proof of Concept
The repository's own test demonstrates the race deterministically under `-race`: [7](#0-6) 
Running two goroutines calling `tx.AsMessageWithAccountKeyPicker(signer, stateDB, 0)` concurrently on the same fee-delegated `tx` (`genFeeDelegatedChainDataAnchoring`) repeatedly yields `msg.ValidatedFeePayer() != feePayer.GetAddr()`, i.e., the observed fee payer is the sender instead of the real fee payer, confirming the field-confusion race described above.

```go
func (tx *Transaction) AsMessageWithAccountKeyPicker(s Signer, picker AccountKeyPicker, currentBlockNumber uint64) (*Transaction, error) {
	intrinsicGas, err := tx.IntrinsicGas(currentBlockNumber)
	if err != nil {
		return nil, err
	}

	gasFrom, err := tx.ValidateSender(s, picker, currentBlockNumber)
	if err != nil {
		return nil, ErrSender(err)
	}

	tx.mu.Lock()
	tx.checkNonce = true
	tx.mu.Unlock()

	gasFeePayer := uint64(0)
	if tx.IsFeeDelegatedTransaction() {
		gasFeePayer, err = tx.ValidateFeePayer(s, picker, currentBlockNumber)
		if err != nil {
			return nil, ErrFeePayer(err)
		}
	}

	sigValidationGas := gasFrom + gasFeePayer
	intrinsicGas = intrinsicGas + sigValidationGas

	tx.mu.Lock()
	tx.validatedGas = &ValidatedGas{IntrinsicGas: intrinsicGas, SigValidateGas: sigValidationGas}
	tx.mu.Unlock()

	return tx, err
```

```go
// TestRaceAsMessageWithAccountPickerForFeePayer tests calling AsMessageWithAccountPicker of a fee delegated transaction
// where a fee payer may be inserted wrongly due to concurrent issue.
func TestRaceAsMessageWithAccountPickerForFeePayer(t *testing.T) {
	log.EnableLogForTest(log.LvlCrit, log.LvlTrace)

	// Configure and generate a sample block chain
	var (
		gendb = database.NewMemoryDBManager()

		// create a sender and a feepayer
		from, _     = createAnonymousAccount("a5c9a50938a089618167c9d67dbebc0deaffc3c76ddc6b40c2777ae594389999")
		feePayer, _ = createAnonymousAccount("ed580f5bd71a2ee4dae5cb43e331b7d0318596e561e6add7844271ed94156b20")

		funds = new(big.Int).Mul(big.NewInt(1e16), big.NewInt(params.KAIA))
		gspec = &blockchain.Genesis{
			Config: params.TestChainConfig,
			Alloc: blockchain.GenesisAlloc{
				from.GetAddr():     {Balance: funds},
				feePayer.GetAddr(): {Balance: funds},
			},
		}
		genesis = gspec.MustCommit(gendb)
		signer  = types.LatestSignerForChainID(gspec.Config.ChainID)
	)

	iterNum := 10000
	errCh := make(chan error, 2*iterNum)

	for i := 0; i < iterNum; i++ {
		tx, _ := genFeeDelegatedChainDataAnchoring(t, signer, from, nil, feePayer, big.NewInt(1234))
		for i := 0; i < 2; i++ {
			go func() {
					stateDB, err := state.New(genesis.Root(), state.NewDatabase(gendb), nil, nil)
				if err != nil {
					panic(err)
				}

				msg, err := tx.AsMessageWithAccountKeyPicker(signer, stateDB, 0)
				if err != nil {
					panic(err)
				}

				if msg.ValidatedFeePayer() != feePayer.GetAddr() {
					errCh <- fmt.Errorf("expected: %v, actual: %v", feePayer.GetAddr().String(), msg.ValidatedFeePayer().String())
				} else {
					errCh <- nil
				}
			}()
		}
	}

	for i := 0; i < 2*iterNum; i++ {
		if err := <-errCh; err != nil {
			t.Fatal(err)
		}
	}
```
