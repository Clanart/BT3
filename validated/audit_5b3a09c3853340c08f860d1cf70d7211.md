### Title
Spoofed `WWW-Authenticate` header from a malicious git remote/proxy tricks Desktop into starting an Enterprise OAuth/sign-in flow against the attacker's server - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The credential-helper trampoline classifies an HTTPS remote as a trusted "enterprise" GitHub host based on an unauthenticated `WWW-Authenticate` header value that is fully controlled by the remote server itself, then hands that attacker-controlled endpoint straight to the interactive GitHub Enterprise sign-in flow, which will exchange the user's credentials/OAuth tokens with that same attacker-controlled origin.

### Finding Description
`getEndpointKind` first checks the endpoint against known-good hostnames (`isDotCom`, `isGHE`). If those fail, it falls back to inspecting `wwwauth[...]` credential fields — values captured verbatim from the HTTP response of the remote git server — and if any contains `realm="GitHub"` it immediately classifies the endpoint as `'enterprise'`, skipping the network-verified check (`isGitHubHost`) used in the final fallback branch: [1](#0-0) [2](#0-1) 

This classification feeds `getCredential`: for an endpoint with no stored account and `endpointKind !== 'generic'`, Desktop calls `ui.promptForGitHubSignIn(endpoint)` with the raw, attacker-supplied endpoint URL: [3](#0-2) 

`promptForGitHubSignIn` then trusts the `hostname`/`origin` derived from that same attacker URL: since it isn't `github.com`, it calls `dispatcher.beginEnterpriseSignIn` and `dispatcher.setSignInEndpoint(origin)`, launching the "Sign in to GitHub Enterprise" popup pointed at the attacker's own domain: [4](#0-3) 

The broken invariant: an endpoint is only supposed to be treated as a trusted GitHub/Enterprise host after either matching a known GitHub domain or being verified live via `isGitHubHost(endpoint)`. The `wwwauth[...]` "happy path" bypasses that verification entirely and instead trusts a header value the remote server chose to send, which any HTTPS git server (or a MITM/malicious proxy sitting on the path of a legitimate remote) fully controls.

### Impact Explanation
A malicious or compromised git remote (or a network proxy intercepting an HTTPS git fetch/push) can respond to an unauthenticated request with `WWW-Authenticate: realm="GitHub"`. This causes Desktop to present its native GitHub Enterprise sign-in UI with the sign-in endpoint set to the attacker's origin. If the user completes that sign-in (entering a PAT, or completing an OAuth/device flow), the resulting credential exchange targets the attacker's server, not a legitimate GitHub Enterprise instance — leading to credential/token exfiltration and an unauthorized account-binding, since Desktop will subsequently treat that attacker origin as a configured "enterprise" account.

### Likelihood Explanation
The trigger requires only that the user perform a routine, expected action — fetching, pulling, or pushing to a repository whose remote points at (or is proxied through) an attacker-controlled HTTPS endpoint. No local access, admin rights, or pre-existing malware is needed; the attacker only needs to control the HTTP response of the git server the user's remote points to, which matches the "attacker controls ... a git remote/proxy response" primitive.

### Recommendation
Remove or harden the `wwwauth[...]`-header heuristic in `getEndpointKind` so that a `realm="GitHub"` claim from an unauthenticated response is never sufficient on its own to classify a host as `'enterprise'`. At minimum, corroborate the header claim with the same `isGitHubHost` verification used in the final fallback before triggering `promptForGitHubSignIn`, and clearly surface the actual target hostname to the user in the sign-in dialog so a mismatched/unexpected enterprise domain is visible before any credential exchange occurs.

### Proof of Concept
1. Stand up an HTTPS server at `https://evil.example.com` that responds to unauthenticated Git smart-HTTP requests with `401` and header `WWW-Authenticate: realm="GitHub"`.
2. In GitHub Desktop, add/clone a repository whose remote `origin` is `https://evil.example.com/whatever.git` (or point an existing remote's traffic through a proxy that injects this header).
3. Perform a fetch/push; the embedded git process forwards the captured `wwwauth[...]` value to the trampoline credential helper.
4. `getEndpointKind` returns `'enterprise'` for `evil.example.com` purely from the spoofed header [1](#0-0) .
5. Since no account exists for that endpoint, Desktop calls `promptForGitHubSignIn('https://evil.example.com')`, which opens the Enterprise sign-in dialog bound to `origin = https://evil.example.com` [5](#0-4) .
6. Any credentials/tokens the user enters in that dialog are sent to the attacker's server.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
