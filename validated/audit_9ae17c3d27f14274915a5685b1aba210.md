### Title
Unvalidated submodule `fullPath` allows path-traversal outside the repository when opening a submodule from a diff - ([File: app/src/lib/git/diff.ts])

### Summary
`buildSubmoduleDiff()` derives the `fullPath` shown/opened for a submodule diff with a plain `Path.join(repository.path, path)` instead of the app's own traversal-safe helper `resolveWithin()`, which is used consistently elsewhere in the codebase (e.g. `dispatcher.ts`'s `openRepositoryFromUrl`, `copilot-conflict-context.ts`) specifically to stop a crafted repository path segment from escaping the repository root.

### Finding Description
When Desktop renders a submodule change, `buildSubmoduleDiff` computes: [1](#0-0) 

`path` comes directly from the `FileChange` produced by parsing `git status`/`git diff` output for the gitlink entry (`file.path`), and is joined onto the repository root with `Path.join` — which normalizes but does **not** constrain `..` segments to stay inside `repository.path`. This is the same broken invariant as the zkVM report: a value that should be constrained to a safe domain (here, "resolved path must stay under the repo root") is instead only nominally processed (path-join/normalize) without the actual bounding check.

Compare this to the pattern used everywhere else Desktop opens a derived, repo-relative path from potentially attacker-influenced data — it explicitly calls `resolveWithin()`, which normalizes, rejects null bytes, and verifies via `realpath` that the resolved path is still contained in the root before it is used: [2](#0-1) [3](#0-2) [4](#0-3) 

The resulting `fullPath` on the `ISubmoduleDiff` is exactly the value the UI hands to `dispatcher.openOrAddRepository`, which opens/adds it as an ordinary Desktop repository: [5](#0-4) [6](#0-5) 

The `IDiff.fullPath` field is documented and typed as an unconditional string with no traversal guarantee: [7](#0-6) 

### Impact Explanation
If a malicious/cloned repository can cause a gitlink entry path reported by git status/diff to resolve (after `Path.join`) outside the working directory, Desktop would compute a `fullPath` pointing anywhere on disk and offer "Open this submodule on GitHub Desktop," which calls `openOrAddRepository(fullPath)` — adding an attacker-chosen directory as a tracked Desktop repository and potentially exposing/opening files/directories outside the intended repo, and re-pointing subsequent git operations (fetch/clone/checkout of "the submodule") at that external path. This is consistent with the "read/write outside the repo" impact class named in the task.

### Likelihood Explanation
Uncertain/likely low in current git versions. Git tree/gitlink entries and `.gitmodules` submodule paths are, as of the CVE-2018-17456 hardening, checked by the `git` binary itself to reject `..`/absolute-path components before Desktop ever sees them via `git status`/`git diff`/`git submodule status`. I could not find in this codebase (nor confirm/deny with certainty) any additional Desktop-side sanitization of `file.path` before it reaches `buildSubmoduleDiff`, so I cannot fully verify whether a crafted repository can still smuggle a traversal path through to `Path.join` on the git/Node versions Desktop bundles. This uncertainty means the practical exploitability depends on git-core protections that are outside this repository's code and that I was not able to inspect or rule out within the available tool budget.

### Recommendation
Regardless of whether git-core currently blocks the traversal, `buildSubmoduleDiff` should not rely on that external invariant holding forever. It should validate the derived path the same way the rest of the codebase already does for repo-relative values: replace `Path.join(repository.path, path)` with `resolveWithin(repository.path, path)`, and treat a `null` result (traversal, symlink escape, or null byte) as "diff cannot be resolved," matching the guard pattern already implemented in `app/src/lib/copilot-conflict-context.ts` and `app/src/ui/dispatcher/dispatcher.ts`.

### Proof of Concept
Could not be concretely demonstrated from the local code alone: constructing a submodule/gitlink path containing `../` segments that survives `git status --porcelain`/`git diff --path-with-raw` output would require confirming that no upstream git validation rejects such tree entries first — a check outside this repository that I was unable to verify in the time available. The concrete, verifiable local-code weakness is the structural one cited above: `buildSubmoduleDiff` is the only path-deriving function in the codebase that skips the `resolveWithin` guard used by all comparable "open a repo-relative path" call sites.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
