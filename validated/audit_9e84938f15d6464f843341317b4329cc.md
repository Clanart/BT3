## Analysis

The external report's core invariant: **when a function accepts `msg.value` for a fee and only needs a portion of it, unused native token must be returned to the payer — otherwise funds are locked in the contract.**

Hyperbridge's own codebase demonstrates the correct pattern in `IntentGatewayV2.sol`, where fee-swap functions explicitly track leftover `msgValue` and refund it to `msg.sender` after the Uniswap swap: [1](#0-0) 

However, `EvmHost.sol`'s three fee-paying entrypoints — `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` — do the swap but never track or refund any leftover native token: [2](#0-1) [3](#0-2) [4](#0-3) 

### Title
Missing refund of overpaid native token in `EvmHost.dispatch`/`fundRequest` fee swaps - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` forward the entire `msg.value` to `IUniswapV2Router02.swapETHForExactTokens(post.fee, ...)`, but the router only consumes the ETH necessary to produce `post.fee`/`amount` of `feeToken`. Uniswap's `swapETHForExactTokens` refunds any unused ETH to its immediate caller — which is `EvmHost` itself, not the original user — because `EvmHost` is the one invoking the router with `{value: msg.value}`. Unlike `IntentGatewayV2`/`ExtrinsicIntents`, which explicitly compute `msgValue -= amounts[0]` and send the remainder back to the caller, `EvmHost` never captures the router's refund or forwards it back to `_msgSender()`.

### Finding Description
`IUniswapV2Router02.WETH()`-based `swapETHForExactTokens` guarantees exact-output token delivery and only spends `amounts[0]` of the supplied ETH; any excess is refunded via `_refundETH()` to `msg.sender` of the *swap call*. Because `EvmHost.dispatch`/`fundRequest` call the router directly (not via a low-level forwarding pattern that preserves the original sender), the refund lands in `EvmHost`'s own balance: [2](#0-1) 

There is no code path in `EvmHost.sol` that returns this stray ETH to the depositor, nor a subsequent user-callable "claim excess" function tied to the specific dispatch call. Every caller who slightly overestimates the native-token cost of the fee-token swap (a documented risk explicitly warned about in the wrapped-token integration, e.g., "the remainder of `msg.value` after wrapping is forwarded as native payment for dispatch fees" in `WrappedHyperFungibleTokenUpgradeable.send`) permanently loses that excess to the `EvmHost` contract balance, since `EvmHost` has no owner/admin sweep or user-refund mechanism for this specific value, unlike the deliberate fix already present in `ExtrinsicIntents._fillFromDestination`/`IntentGatewayV2.placeOrder` (`msgValue -= amounts[0]` then explicit `.call{value: msgValue}` refund).

### Impact Explanation
Any user or integrating contract (including `WrappedHyperFungibleTokenUpgradeable.send`, which forwards `msgValue` after wrapping) that supplies more native token than the swap consumes for `dispatch`/`fundRequest` permanently loses the difference — it becomes stuck in `EvmHost`, with no public accessor to reclaim it. This is a direct, deterministic loss of user funds on every native-fee dispatch that isn't perfectly estimated, matching the "loss of funds" bounty category.

### Likelihood Explanation
High: native-token fee payment is a documented, actively-used payment path (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`), and callers cannot know the exact ETH/feeToken exchange rate at the moment of the swap, so overpayment (a safety margin) is the expected normal usage pattern, not an edge case. No malicious actor, relayer, or privileged role is required — any ordinary end user triggers the loss.

### Recommendation
Mirror the pattern already used in `ExtrinsicIntents`/`IntentGatewayV2`: capture the `amounts` array returned by `swapETHForExactTokens`, compute the unspent ETH (`msg.value - amounts[0]`), and refund it to `_msgSender()` (or `post.payer`/`get`'s originating caller) via a low-level `.call{value: ...}` with success check, in all three functions: `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`.

### Proof of Concept
1. Configure `EvmHost` with a live `uniswapV2` router and `feeToken`.
2. Call `dispatch(DispatchPost{... fee: 1e18 ...})` with `msg.value` deliberately set higher than the ETH needed to buy `1e18` feeToken (e.g., 2x the expected amount, as a safety margin against slippage/price movement).
3. Observe that `swapETHForExactTokens` only consumes the exact ETH needed and refunds the rest to `address(this)` (`EvmHost`), increasing `EvmHost`'s native balance.
4. Confirm there is no subsequent transfer or event returning this excess to the caller — check the caller's ETH balance before/after: it decreases by the full `msg.value`, not just the amount actually spent on the swap.
5. Compare against `IntentGatewayV2Test.testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, which asserts the opposite (correct) behavior in a sibling contract, confirming `EvmHost` diverges from the codebase's own established remediation pattern. [5](#0-4)

    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
