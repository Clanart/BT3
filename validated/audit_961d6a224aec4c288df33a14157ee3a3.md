## Analysis

The Sherlock SUI report's core pattern is: **an unexpected/edge-case input is not validated, gets persisted into on-chain state, and permanently blocks all future processing with no recovery path** (a stuck monotonic nonce). Mapping this bug class to Zest's pricing path, the closest analog is the **per-feed monotonic timestamp gate** in `price-resolve`, specifically the flawed `oracle-timestamp-fresh` helper.

### Title
Flawed staleness/monotonicity check in `oracle-timestamp-fresh` can permanently freeze all price resolution for an asset - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` computes `delta` as `u0` whenever the oracle-reported timestamp `ts` is greater than `stacks-block-time`, instead of rejecting or bounding such a future timestamp. This lets a future-dated `ts` be accepted as maximally "fresh" and written into the persistent `last-update` map. Because `price-resolve` also enforces a strict monotonic check (`>= ts prev`) against that same stored value, any subsequent legitimate price update whose real timestamp has not yet caught up to the erroneously stored future value will fail `ERR-ORACLE-INVARIANT` on every call, with no mechanism to reset or recover the stored `last-update` entry.

The bug: `delta` is forced to `u0` (i.e., "perfectly fresh") whenever `ts > stacks-block-time`, rather than treating a future timestamp as suspicious/invalid. Because Stacks block timestamps can legitimately lag real-world/off-chain clock time (the source of Pyth's `publish-time`), a normal, non-malicious price update can have `ts` ahead of `stacks-block-time`. When this happens, `price-resolve` writes this future `ts` into `last-update` for that `{type, ident}` feed key (`map-set last-update key timestamp`, line 392). From that point forward, `oracle-timestamp-fresh`'s second conjunct `(>= ts prev)` — the monotonic per-feed timestamp guard — will reject **every** subsequent legitimate price update whose real timestamp has not yet caught up to the erroneously-stored future value, causing `ERR-ORACLE-INVARIANT` to fire on every call to `price-resolve`/`price-multi-resolve` for that feed.

This directly parallels the SUI report's root cause: an edge-case/out-of-order input is accepted without adequate validation, gets persisted as durable on-chain state, and then permanently blocks all further processing through the same code path — with no built-in recovery (no way to reset `last-update`, no owner/DAO function shown to clear it).

### Impact Explanation
Every operation that depends on pricing for the affected asset — `borrow`, `repay`, `collateral-add`/`collateral-remove` health checks, and liquidation (`get-assets`, `is-healthy-with-mask`, `get-asset-value`) — calls into `price-resolve` for that asset's oracle feed. Once the feed's `last-update` checkpoint is poisoned with a future timestamp, all of these operations revert for that asset until real time/block time catches up, i.e. **temporary freezing of funds** (borrowing, repaying, withdrawing collateral, and liquidating positions collateralized/debited in that asset become impossible) — matching the in-scope "temporary freezing of funds" impact class. If the skew is large (e.g., due to a bad actor deliberately triggering resolution during a window of clock drift, or a burst of block-time lag), the freeze duration can be significant, and there is no operator-facing function to reset the stored checkpoint early.

### Likelihood Explanation
No special privilege is required — any user calling any price-consuming market function (`borrow`, `repay`, `liquidate`, etc.) triggers `price-resolve`. The trigger condition (`ts > stacks-block-time`) can occur through ordinary clock/timestamp skew between Pyth's off-chain publish time and the Stacks chain's block time, without needing malicious or externally corrupted oracle data — the flaw is in this contract's own handling of that skew, not in third-party data correctness.

### Recommendation
In `oracle-timestamp-fresh`, reject (or clamp) timestamps that are ahead of `stacks-block-time` instead of treating them as automatically fresh, e.g. only accept `ts <= stacks-block-time + <bounded tolerance>`; and/or before persisting a new `last-update` value, validate it is not implausibly far in the future relative to on-chain time. Consider also adding a DAO-gated recovery path to reset a poisoned `last-update` checkpoint per feed.

### Proof of Concept
1. Pyth publishes a price with `publish-time = T`, where `T` is marginally ahead of the current `stacks-block-time` (a routine clock-skew scenario given Stacks block cadence).
2. Any user calls `borrow`/`repay`/etc. for the asset using that feed, invoking `price-resolve` → `oracle-timestamp-fresh(T, prev, max-staleness)`. Since `T > stacks-block-time`, `delta = u0`, so the freshness check trivially passes, and since `T >= prev` also passes, the call succeeds and `last-update` is set to `T`.
3. Real-world/Pyth time and `stacks-block-time` continue to advance, but until block time (or the next real publish-time) exceeds `T`, every new call to `price-resolve` for that feed has `ts < T = prev`, so `(>= ts prev)` fails, and `ERR-ORACLE-INVARIANT` is returned on every subsequent borrow/repay/liquidation call for that asset. (define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
