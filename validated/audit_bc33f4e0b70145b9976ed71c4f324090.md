### Title
`redirect_to_bounce_page` fails to strip `id_token` from the redirect Location header due to Symbol/String key mismatch in `.except(:id_token)` - ([File: lib/shopify_app/controller_concerns/token_exchange.rb])

### Summary
`redirect_to_bounce_page` attempts to remove the sensitive `id_token` query parameter before echoing the rest of the query string into a `redirect_to(..., allow_other_host: true)` call, but it calls `.except(:id_token)` (a Symbol) against `request.query_parameters`, which is a plain `Hash` with **String** keys. Because Ruby `Hash#except` does an exact key match, the `"id_token"` string key is never removed, so the JWT/id_token value is reflected verbatim into both the `bounce_url` and the outer `patch_shopify_id_token_url` redirect target.

### Finding Description
In `redirect_to_bounce_page`: [1](#0-0) 

`request.query_parameters` is populated from Rack's parsed `GET` hash (`ActionDispatch::Http::Parameters#query_parameters`), which yields a regular `Hash` keyed by Strings, not a `HashWithIndifferentAccess`. Calling `.except(:id_token)` with a Symbol therefore never matches the String key `"id_token"` that Rack put in the hash, so the exclusion is a no-op — the token is retained in `patch_shopify_id_token_params`. This value is then:
1. Interpolated into `bounce_url` via `.to_query`.
2. Stored under `patch_shopify_id_token_params["shopify-reload"] = bounce_url`, embedding the token a second time.
3. Interpolated again into the outer redirect target passed to `redirect_to(..., allow_other_host: true)`.

The call path is reached from `respond_to_invalid_shopify_id_token`, which is invoked whenever `activate_shopify_session`, `authenticated_shopify_domain`, or `current_shopify_domain` raise `MissingJwtTokenError`/`InvalidJwtTokenError` and the request has no `Authorization` header and is embedded: [2](#0-1) 

This is a normal, unauthenticated-reachable flow — App Bridge legitimately sends expired/invalid id_tokens as query params during session-token refresh, and an attacker can also trigger it directly by hitting any protected embedded route with `?id_token=<value>&embedded=1`. No `Authorization` header, shop verification, or HMAC check gates this path; `reject_mismatched_requested_shopify_domain` and shop sanitization occur only for successfully-parsed tokens, not for this error branch.

None of the existing checks (id token verification, `sanitize_shop_domain`, session id derivation, `secure_compare`) prevent this — the bug is purely in the parameter-filtering logic, independent of the casing/duplicate-key scenario suggested in the question. Even the simplest case `?id_token=SECRET` fails to be stripped.

### Impact Explanation
The id_token value is reflected into the `Location` response header of a redirect (`allow_other_host: true` permits redirecting to a different scheme/host than the request), and is duplicated inside the `shopify-reload` parameter as well. This exposes the token to browser history, any `Referer` headers sent by subsequent same-page navigation/App Bridge fetches to third parties, and to access logs on the redirect target host. This matches the Shopify HackerOne "Sensitive data exposure via URL / secret leaked in redirect/Location header" impact class described in the audit's scoped impact.

### Likelihood Explanation
Highly feasible and repeatable: any embedded request lacking an `Authorization` header whose `id_token`/session raises `MissingJwtTokenError` or `InvalidJwtTokenError` (e.g., expired, malformed, or simply omitted-but-present-as-blank id_token) will trigger `redirect_to_bounce_page` and reflect the token unconditionally — no casing trick or duplicate-key trick is even required because the exclusion never works at all.

### Recommendation
Use indifferent-access-safe exclusion, e.g. `request.query_parameters.symbolize_keys.except(:id_token)` or `.except("id_token")` (matching the actual key type), and add a regression test asserting `response.location` never contains the token value for `id_token`, `Id_Token`, `ID_TOKEN`, or duplicate/array-form variants.

### Proof of Concept
```ruby
test "#redirect_to_bounce_page never leaks id_token in Location header" do
  with_application_test_routes do
    secret_token = "super-secret-jwt-value"
    get :index, params: { id_token: secret_token, embedded: "1" }

    assert_response :redirect
    refute_includes response.location, secret_token,
      "id_token leaked into redirect Location header due to Hash key type mismatch in .except(:id_token)"
  end
end
```
Expected (current) result: the assertion fails — `response.location` contains `id_token=super-secret-jwt-value` (and again inside the `shopify-reload` parameter), confirming the leak.

    def respond_to_invalid_shopify_id_token(error)
      ShopifyApp::Logger.debug("Responding to invalid Shopify ID token: #{error.message}")
      return if performed?

      if request.headers["HTTP_AUTHORIZATION"].blank?
        if embedded?
          redirect_to_bounce_page
        else
          redirect_to_embed_app_in_admin
        end
      else
        ShopifyApp::Logger.debug("Responding to invalid Shopify ID token with unauthorized response")
        response.set_header("X-Shopify-Retry-Invalid-Session-Request", 1)
        unauthorized_response = { message: :unauthorized }
        render(json: { errors: [unauthorized_response] }, status: :unauthorized)
      end
    end

    def redirect_to_bounce_page
      ShopifyApp::Logger.debug("Redirecting to bounce page for patching Shopify ID token")
      patch_shopify_id_token_url =
        "#{ShopifyAPI::Context.host}#{ShopifyApp.configuration.root_url}/patch_shopify_id_token"
      patch_shopify_id_token_params = request.query_parameters.except(:id_token)

      bounce_url = "#{request.path}?#{patch_shopify_id_token_params.to_query}"

      # App Bridge will trigger a fetch to the URL in shopify-reload, with a new session token in headers
      patch_shopify_id_token_params["shopify-reload"] = bounce_url

      redirect_to(
        "#{patch_shopify_id_token_url}?#{patch_shopify_id_token_params.to_query}",
        allow_other_host: true,
      )
    end
