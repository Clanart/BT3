### Title
Incomplete allowlist in `isApplicationBundle` fails to detect non-`.app` executable bundle types (`.prefPane`, `.saver`, `.qlgenerator`, `.plugin`), allowing `UNSAFE_openDirectory` to launch attacker-supplied bundles - (File: `app/src/lib/is-application-bundle.ts`)

### Summary
`isApplicationBundle` is the sole safety gate that decides whether `showFolderContents` calls the dangerous `UNSAFE_openDirectory` (which invokes `shell.openPath`, i.e., LaunchServices `open`) or the safe `_showItemInFolder` (Finder reveal) when a user clicks "Show folder contents" on a directory inside a repository. [1](#0-0)  The gate works by shelling out to `mdls` and checking whether the resulting Uniform Type Identifier (UTI) content-type/tree string contains one of exactly three hardcoded identifiers. [2](#0-1) 

### Finding Description
macOS treats many directory bundle types as "openable and capable of loading/executing code," not just `.app` bundles. `isApplicationBundle` only checks for `com.apple.application-bundle`, `com.apple.application`, and `public.executable` anywhere in the `mdls` output. [2](#0-1) 

Bundle types such as `.prefPane` (`com.apple.systempreference.prefpane`), `.saver` (screen saver bundles), `.qlgenerator` (Quick Look generators), and generic `.plugin`/`.bundle` types descend from `com.apple.plugin`/`com.apple.bundle` in Apple's UTI hierarchy rather than from `com.apple.application` or `public.executable`. Because these types are loaded/executed by a host process (System Preferences, Quick Look, Finder) rather than being a directly launchable `com.apple.application`, their `kMDItemContentTypeTree` output would not necessarily contain any of the three hardcoded strings, so `probableBundleIdentifiers.some(...)` would evaluate to `false` for them. [3](#0-2) 

The check is a closed, hand-maintained allowlist rather than a structural test (e.g., checking whether the path is a bundle at all via `com.apple.bundle`, or using `LSCopyKindStringForURL`/an "is this a package that opens something" test). This breaks the function's own stated invariant — its doc comment claims it determines whether a path is "actually an application bundle or otherwise executable" [4](#0-3)  — for any bundle type not in the three-item list.

### Impact Explanation
If `isApplicationBundle` returns `false` for a `.prefPane`, `.saver`, `.qlgenerator`, or similar executable-plugin directory committed into a repository, `showFolderContents` proceeds to call `UNSAFE_openDirectory(path)`, whose own documentation explicitly warns it "should never be used to open user-provided or derived paths" because "no verification is performed to ensure that the provided path isn't actually an executable." [5](#0-4)  This would invoke `shell.openPath`, handing the attacker-controlled bundle to LaunchServices, which for these bundle types has historically resulted in the bundle's code being loaded into a trusted host process (e.g., System Preferences loading a malicious `.prefPane`/`.saver`), i.e., code execution triggered purely by the victim clicking "Show folder contents" on a cloned/fetched repository directory.

### Likelihood Explanation
Exploitation requires: (1) macOS (the check is a no-op on other platforms per the early return), (2) the attacker committing a directory with the right bundle extension/Info.plist so the OS assigns it one of these UTIs, and (3) the victim using the "Show folder contents" context-menu action on that specific directory rather than opening the repository generally. This is a plausible but not automatic user interaction — it requires the victim to right-click that particular folder — so likelihood is moderate rather than high, and would need to be confirmed empirically with `mdls` against a real `.prefPane`/`.saver`/`.qlgenerator` bundle on macOS, which I cannot execute from this environment.

### Recommendation
Replace the closed allowlist with a broader/structural test, e.g., treat any path whose `kMDItemContentTypeTree` contains `com.apple.bundle` (or is a package per `NSWorkspace`/`LSCopyKindStringForURL`) as unsafe to open directly, rather than enumerating specific descendant identifiers. Alternatively, invert the logic to a strict allowlist of known-safe, non-executable directory types instead of a blocklist of known-dangerous ones, since the set of "openable and code-loading" bundle types on macOS is broader than `.app`.

### Proof of Concept
On macOS, create a directory bundle with a `.prefPane` (or `.saver`/`.qlgenerator`) extension and appropriate `Info.plist`/`CFBundlePackageType`, commit it into a test repository, clone it in GitHub Desktop, right-click the folder in the Changes/repository view and choose "Show folder contents". Compare the actual `mdls -name kMDItemContentType -name kMDItemContentTypeTree` output for that bundle against the three strings checked in [2](#0-1)  — if none match, `isApplicationBundle` returns `false` and `UNSAFE_openDirectory` is invoked on the bundle per [6](#0-5) .

  }

  // Expected output for an application bundle:
  // $ mdls -name kMDItemContentType -name kMDItemContentTypeTree /Applications/GitHub\ Desktop.app
  // kMDItemContentType     = "com.apple.application-bundle"
  // kMDItemContentTypeTree = (
  //     "com.apple.application-bundle",
  //     "com.apple.application",
  //     "public.executable",
  //     "com.apple.localizable-name-bundle",
  //     "com.apple.bundle",
  //     "public.directory",
  //     "public.item",
  //     "com.apple.package"
  // )
  const { stdout } = await execFile('mdls', [
    ...['-name', 'kMDItemContentType'],
    ...['-name', 'kMDItemContentTypeTree'],
    path,
  ])

  const probableBundleIdentifiers = [
    'com.apple.application-bundle',
    'com.apple.application',
    'public.executable',
  ]

  return probableBundleIdentifiers.some(id => stdout.includes(`"${id}"`))
