### Title
`smartConvert`'s zero-slippage-tolerance check reverts `_sendRewards`, blocking `deposit`/`depositLP`/`withdraw` - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._sendRewards` unconditionally routes the WOM protocol-fee slice through `SmartWomConvert.smartConvert` whenever a fee is flagged `isMWOM` and `smartWomConverter` is set, with no try/catch. `smartConvert` forwards `_minRec = _amountIn` to `_convertFor`, requiring the WOM→mWom buyback+deposit to return at least 100% of the input with zero slippage tolerance. Because the buyback leg swaps through the public, permissionlessly-tradeable `womMWomPool`, an attacker can skew that pool so the actual swap executes worse than the cheap 1e18-unit price probe used to decide whether to buy back, causing `MinRecNotMatch()` to revert and, since `_sendRewards` sits unconditionally on the path of `deposit`, `depositLP`, `withdraw`, and `harvest`, blocking all of these operations for the affected pool.

### Finding Description
`withdraw` calls `_toMasterWomAndSendReward(_lpToken, _liquidity, false)` before doing the actual pool withdrawal: [1](#0-0) 

`_toMasterWomAndSendReward` computes `womRewards` from the harvest triggered by the master-wombat interaction and unconditionally calls `_sendRewards(_lpToken, wom, poolInfo.rewarder, womRewards)`: [2](#0-1) 

Inside `_sendRewards`, for any active fee flagged `isMWOM` on the `wom` token, if `smartWomConverter != address(0)` the fee slice is routed through `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` with no error handling: [3](#0-2) 

`smartConvert` first probes `currentRatio()` — the output of swapping a fixed `1e18` of mWom for wom through `womMWomPool` — to decide whether/how much of `_amountIn` to route through a buyback swap versus a straight `mWom.deposit()`. It then calls `_convertFor(_amountIn, convertRatio, _amountIn, msg.sender, 0)`, passing `_minRec` equal to the *full* `_amountIn`: [4](#0-3) 

In `_convertFor`, the buyback swap executes with `amountOutMin = 0` (no per-swap slippage protection), and only the aggregate result is checked against `_minRec`: [5](#0-4) 

Because `currentRatio()` samples a tiny fixed-size (1e18) trade while the real buyback trades `amountToSwap` (potentially up to `maxSwapAmount()`, sized off pool cash/liability imbalance), the two legs can see materially different execution prices on the same AMM curve. An attacker can perform an ordinary swap against the public `womMWomPool` (buy mWom / sell wom, or vice versa) to move the pool into a state where the cheap price probe still indicates "buy back mWom" (`mWomToWom < buybackThreshold`) but the larger, actually-executed swap yields `amountRec < amountToSwap`, driving `convertAmount + amountRec` below `_minRec = _amountIn`. This reverts with `MinRecNotMatch()`, which propagates all the way up through `_sendRewards` → `_toMasterWomAndSendReward` → `withdraw` (and equally `deposit`, `depositLP`, `harvest`), reverting the entire user transaction. No modifier (`nonReentrant`, `whenNotPaused`, `_onlyPoolHelper`) intercepts this failure path — the revert happens deep in an unrelated fee-routing side effect that principal-affecting functions cannot skip.

### Impact Explanation
As long as the affected pool has accrued any WOM reward (`womRewards > 0`) that flows through the `isMWOM` fee bucket, every `withdraw`/`deposit`/`depositLP`/`harvest` call for that pool can be forced to revert by an attacker who keeps `womMWomPool`'s exchange rate skewed at the moment of the call. This blocks user principal withdrawals and deposits — matching Immunefi's "Temporary freezing of funds" class — for as long as the attacker is willing/able to keep re-skewing the pool ahead of legitimate transactions (front-running), which is economically feasible against a shallow WOM/mWom pool.

### Likelihood Explanation
Requires: (a) `smartWomConverter` configured and an active `isMWOM` fee (owner-configured, not attacker-controlled, but plausible default protocol configuration since the feature exists for this purpose), (b) the pool having accrued nonzero WOM rewards to convert on the call path, and (c) attacker capital sufficient to move `womMWomPool`'s price/imbalance and front-run victim transactions. No privileged role is needed — the attacker only needs to trade on the public AMM and front-run calls to `withdraw`/`deposit`. This is repeatable per block as long as the attacker is willing to pay the swap/arbitrage cost each time.

### Recommendation
Remove the hard zero-slippage requirement in `smartConvert` (do not set `_minRec = _amountIn`); instead compute an acceptable minimum with real slippage tolerance (e.g., via `estimateTotalConversion` with a configurable tolerance), or make the buyback best-effort (fall back to a plain `mWom.deposit()` for the shortfall instead of reverting). Additionally, wrap the `smartConvert` call in `_sendRewards` with a try/catch so that a converter-side failure degrades gracefully (e.g., falls back to `IMWom(mWom).deposit(feeAmount)`) instead of reverting the entire deposit/withdraw transaction.

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatStaking`, register a pool with `depositToken`/`lpAddress`, set an active fee with `isMWOM = true`, and set `smartWomConverter` to a deployed `SmartWomConvert` pointed at a test `womMWomPool` (mock Wombat AMM) with a low `buybackThreshold`.
2. Seed the pool with pending WOM rewards (via a `MasterWombatMock` that emits WOM on `deposit`/`withdraw`).
3. Baseline run: call `withdraw(lpToken, liquidity, minAmount, sender)` with `womMWomPool` in a balanced state — confirm it succeeds and assert `IERC20(poolInfo.depositToken).balanceOf(address(this)) - beforeWithdraw` matches `_liquidity` burned from the receipt token.
4. Attack run: before calling `withdraw` again, have an attacker EOA execute a swap against `womMWomPool` sized so that `currentRatio()` (1e18 probe) still passes `mWomToWom < buybackThreshold` but the larger `amountToSwap` computed from `maxSwapAmount()` executes at worse effective price.
5. Call `withdraw` again with identical parameters and assert the transaction reverts with `MinRecNotMatch()`, demonstrating the principal withdrawal is blocked purely due to fee-conversion side effects, with no change to the core withdrawal logic itself.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
