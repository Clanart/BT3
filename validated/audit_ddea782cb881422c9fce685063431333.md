### Title
Same-chain `cancelOrder` refunds the pre-fee amount while escrow holds the post-fee amount, causing an underflow revert that permanently locks user funds — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder` escrows the **fee-reduced** input amount (`originalAmount − protocolFee`) per token, but the same-chain branch of `cancelOrder` builds the refund `WithdrawalRequest` from the **raw, pre-fee** `order.inputs` amounts. `withdraw()` only guards against a *zero* escrow balance, not an *insufficient* one, so subtracting the larger pre-fee amount from the smaller escrowed balance underflows and reverts under Solidity 0.8 checked arithmetic — permanently locking the user's escrowed tokens whenever `protocolFeeBps > 0`. This is the exact bug class from the external report: a per-item amount that is systematically larger than what is actually held, driving a subtraction into underflow and bricking the only refund/withdrawal path.

### Finding Description
At `placeOrder`, when `protocolFeeBps > 0`, the contract computes `reducedInputs[i].amount = originalAmount - protocolFee` and stores **only that reduced amount** as escrow: [1](#0-0) [2](#0-1) 

When the user calls `cancelOrder` for a same-chain, still-unfilled order, the refund body is built from `order.inputs` directly — the **original, pre-fee** amounts, not `reducedInputs` and not the actual `_orders[commitment][token]` balance: [3](#0-2) 

`withdraw()` then only checks that the escrow is non-zero, not that it covers the requested amount, before subtracting: [4](#0-3) 

Since `_orders[commitment][token] == originalAmount - protocolFee < originalAmount`, the line `_orders[body.commitment][token] -= amount;` underflows and reverts (Solidity ≥0.8 checked arithmetic) whenever `amount` (the pre-fee `order.inputs[i].amount`) is used. `cancelOrder` is the sole recovery path for an order that has not yet been filled, so every cancellation of a fee-bearing order permanently locks the escrowed tokens in the contract — nobody, including the user, can ever retrieve them (the order can't be re-cancelled with a different amount, and it can't be filled either since a solver would need to match the original, un-reduced `order.output`/`order.inputs`, not the reduced escrow).

This mirrors the sibling, corrected implementation on the main EVM path, which reads the actual escrowed balance rather than the order's raw amount: [5](#0-4) 

### Impact Explanation
This is a direct, unprivileged, public-entrypoint loss/lock of user funds — the exact impact class in the bounty scope ("stealing or loss of funds", "logic attacks"). Any user who places a same-chain order while `_destinationProtocolFees[...]` or `_params.protocolFeeBps` is non-zero and later cancels before a solver fills it will have their entire escrowed principal permanently stuck in the `IntentGatewayV2` (Tron) contract — the transaction reverts every time `cancelOrder` (or any code path reusing this construction) is invoked, so there is no way to drain the correct, reduced amount instead.

### Likelihood Explanation
High whenever the deployment has a non-zero protocol fee configured (the normal revenue-generating configuration for the protocol) and any order is left unfilled and cancelled — a routine, expected user action requiring no privileged role, malicious peer, relayer, or governance action. The condition triggers deterministically from ordinary contract state (fee > 0) and does not depend on race conditions or external actors.

### Recommendation
In the same-chain branch of `cancelOrder`, build the refund `WithdrawalRequest` from the actual escrowed balances (`_orders[commitment][token]`) exactly as `IntrinsicIntents._cancelSameChain` does, rather than from `order.inputs`. Additionally, harden `withdraw()` to check `escrowed >= amount` (not just `!= 0`) before subtracting, and revert with a clear error rather than relying on the arithmetic underflow, to prevent any future recurrence of this rounding/mismatch class of bug.

### Proof of Concept
1. Governance sets a non-zero `protocolFeeBps` (or a destination-specific fee) via `UpdateParams`.
2. User calls `placeOrder` with `inputs[0].amount = 1000`. With `protocolFeeBps = 100 (1%)`, `protocolFee = 10`, so `_orders[commitment][token] = 990` is escrowed (line 356-358, 456-458), while `order.inputs[0].amount` remains `1000` in the order struct used for the commitment/event.
3. Before any solver fills it, the user calls `cancelOrder(order, options)` on the same chain.
4. `cancelOrder`'s same-chain branch constructs `WithdrawalRequest{ tokens: order.inputs, ... }` with `amount = 1000` (line 527-528).
5. `withdraw()` reads `_orders[commitment][token] == 990` (non-zero, so it passes the `== 0` guard) and executes `_orders[commitment][token] -= 1000`, i.e., `990 - 1000`, which underflows and reverts under Solidity 0.8 checked arithmetic.
6. The transaction always reverts; the user has no other path to reclaim the escrowed 990 tokens, which are permanently locked in the contract.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
