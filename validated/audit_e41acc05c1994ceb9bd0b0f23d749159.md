## Analog Found: `send()` bank precompile — same "usei" denom is not TokenFactory-prefixed, but `sendNative` bypasses the allow-list/BlockedAddr checks that the standard `MsgSend` path enforces

### Title
Bank precompile `sendNative` bypasses `BlockedAddr`/tokenfactory `AllowList` enforcement applied to the standard bank `Send` path - ([File: precompiles/bank/bank.go])

### Summary
ChainSwap's root cause was a code path that could move funds/increase balances to addresses that were never validated against the intended whitelist, because a "convenience"/automated code path skipped the authorization check that the primary path enforced. The `x/bank` module in sei-chain implements exactly this kind of authorization gate for TokenFactory denoms — `MsgSend`/`MsgMultiSend` explicitly check `BlockedAddr` and `IsInDenomAllowList` before moving coins [1](#0-0) . However, the EVM `bank` precompile's `sendNative` transaction handler moves `usei`/`wei` balances directly via `p.bankKeeper.SendCoinsAndWei(...)` without ever calling `BlockedAddr` or `IsInDenomAllowList` [2](#0-1) .

### Finding Description
The Cosmos-side `bank` module enforces two authorization gates before any coin transfer completes through `MsgSend`: `BlockedAddr` (module/reserved account protection) and `IsInDenomAllowList` (TokenFactory per-denom allow-list) [3](#0-2) . The `send()` method of the bank precompile (used for ERC20-pointer-backed TokenFactory denoms) correctly routes through the same `bankMsgServer.Send` path and thus inherits these checks [4](#0-3) .

In contrast, `sendNative` (used to move the chain's native `usei`/wei balance from an EVM caller to any Sei address) calls `p.bankKeeper.SendCoinsAndWei` directly, bypassing `bankMsgServer.Send` entirely, and therefore never checks `BlockedAddr` or the TokenFactory `AllowList` [5](#0-4) . This same pattern is repeated identically across every legacy precompile version (v552 through v67) [6](#0-5) .

### Impact Explanation
For the native `usei` denom specifically this is low-impact because `usei` is not a TokenFactory denom (`IsInDenomAllowList` explicitly skips non-`factory/` prefixed denoms [7](#0-6) ), so the allow-list gap has no practical effect there. The only enforcement that would matter for `usei` transfers is `BlockedAddr`, which blocks module accounts/reserved addresses (e.g. the `evm_coinbase` withdraw-address protection built for the distribution module) from *receiving* funds via the normal `Send` path [8](#0-7) . Since `sendNative` skips `BlockedAddr`, it is possible to send `usei`/wei to blocked/module addresses through the EVM precompile that `MsgSend` would reject, which could deposit funds into an address the protocol intended to be unreachable/reserved (e.g., the reserved coinbase-withdraw address), inconsistent with the invariant the Cosmos-side path enforces.

### Likelihood Explanation
Any unprivileged EVM caller that is Sei-address-associated can call the `sendNative` method on the bank precompile with an arbitrary recipient bech32 address and a non-zero `msg.value`. No special privilege, precompile access control, or governance action is required — this is directly reachable from a single transaction.

### Recommendation
Route `sendNative`'s balance movement through the same authorization checks the Cosmos-side `Send`/`MultiSend` path enforces — at minimum call `k.BlockedAddr(receiverSeiAddr)` before `SendCoinsAndWei`, and ideally also apply `IsInDenomAllowList` semantics if usei/wei transfers are ever extended to allow-listed denoms, so behavior is consistent across the EVM and Cosmos entry points.

### Proof of Concept
1. As any EVM account associated with a Sei address and holding `usei`, call `bank.sendNative(receiver)` on precompile address `0x0000000000000000000000000000000000001001` with `value` set to the desired wei amount, where `receiver` is a bech32 address for which `BlockedAddr` would return true (e.g. a module account address or the reserved `evm_coinbase`-prefixed withdraw address) [9](#0-8) .
2. Observe the transfer succeeds via `SendCoinsAndWei`, whereas the equivalent Cosmos `MsgSend` to the same recipient would be rejected with `"... is not allowed to receive funds"` [10](#0-9) .

**Uncertainty note:** I could not fully confirm from the index which specific addresses (beyond the documented `evm_coinbase` reserved prefix) are registered in `BlockedAddr` at genesis/runtime, nor whether any downstream consumer of a blocked-address balance could actually cause fund loss or a chain halt (the distribution tests suggest a halt risk if such an address later receives funds and is force-withdrawn from) [11](#0-10) . A full assessment of severity requires checking the complete `BlockedAddr` module-account list and whether `sendNative` is the only such bypass path (`SendCoinsAndWei` callers elsewhere were not exhaustively enumerated). I recommend starting a Devin session with full repository access to confirm the blocked-address set and trace all callers of `SendCoinsAndWei`/`SendCoinsWithoutAccCreation` to rule out or confirm concrete fund-loss/halt scenarios.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	err = k.SendCoins(ctx, from, to, msg.Amount)
	if err != nil {
		return nil, err
	}

func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func TestSetWithdrawAddrRejectsCoinbaseAddress(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	params := app.DistrKeeper.GetParams(ctx)
	params.WithdrawAddrEnabled = true
	app.DistrKeeper.SetParams(ctx, params)

	addr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))
	coinbaseAddr := coinbaseWithdrawAddr()

	// CanSendTo alone would let this address through; BlockedAddr is what catches it.
	require.True(t, app.BankKeeper.CanSendTo(ctx, coinbaseAddr))
	require.True(t, app.BankKeeper.BlockedAddr(coinbaseAddr))

	require.Error(t, app.DistrKeeper.SetWithdrawAddr(ctx, addr[0], coinbaseAddr))
}
