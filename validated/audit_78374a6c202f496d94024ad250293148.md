### Title
Webhook shop attribution relies on an unauthenticated `X-Shopify-Shop-Domain` header that is not covered by the HMAC signature - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the shop identity for a webhook purely from the `X-Shopify-Shop-Domain` request header, while `hmac_valid?` only authenticates the raw POST body [1](#0-0) . Because the signature never covers the header, the header value is not cryptographically bound to the verified payload, mirroring the Astaria `flashAction` finding where the callback recipient has no verified way to know who/what actually initiated the call.

### Finding Description
`WebhookVerification#verify_request` computes `hmac_valid?(request.raw_post)` and only checks the body against the app secret [2](#0-1) . The companion `shop_domain` helper simply reads `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` [3](#0-2) , with no cryptographic linkage back to the HMAC-verified body. This is the officially documented pattern for custom webhook controllers built on this gem:
```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end
end
``` [4](#0-3) 

Just as Astaria's `onFlashAction` callback gave the recipient no verified way to authenticate who triggered the call (forcing integrators to build their own ad-hoc flags), `WebhookVerification` gives the "recipient" (the app's job/controller code) an unauthenticated `shop_domain` value alongside an HMAC that only proves the body came from someone who knows the shared app secret - not that the body is actually associated with the shop named in the header. Any downstream job that uses `shop_domain` to select which shop's data to mutate (as shown in the generator templates, e.g. `AppUninstalledJob` deleting `Shop.find_by(shopify_domain: shop_domain)` [5](#0-4) ) is trusting a value that is not part of the signed material.

### Impact Explanation
If a party in possession of a validly-HMAC-signed body/signature pair (the app secret is shared across all shops installing the same app, so a valid signature only proves knowledge of the shared secret, not the identity of a specific shop) replays that body with a forged `X-Shopify-Shop-Domain` header for a different (victim) shop, `hmac_valid?` still returns true because the header is not part of the signed data. Any consumer that keys its side effects off `shop_domain` (uninstall handling, redact jobs, data updates keyed by shop) would then act on the attacker-chosen shop rather than the shop that actually owns the payload - a cross-shop attribution/authentication bypass in the webhook trust boundary.

### Likelihood Explanation
Exploitation requires an attacker to first obtain a legitimately HMAC-signed webhook body (e.g., from webhooks generated by their own installed instance of the app, or any leaked/observable webhook delivery), then replay it to the endpoint with a modified shop-domain header. This is harder to arrange than a purely unauthenticated request, since normal webhook deliveries flow directly from Shopify to the app server without merchant visibility. This mirrors the original Astaria finding's own acknowledged-but-medium severity: the design gap is real, but reliably obtaining a signable/replayable pair reduces likelihood compared to a fully unauthenticated bypass. This limitation could not be more precisely bounded without also inspecting the shopify_api gem's `ShopifyAPI::Webhooks::Registry`/`Request` internals, which are outside this repo's index.

### Recommendation
Bind the shop identity to the signed content: either include the shop domain in the HMAC computation (sign `headers + body`, or a canonical string incorporating the shop domain) before calling `hmac_valid?`, or cross-validate the `shop_domain` header against shop-specific webhook secrets/session records before trusting it in downstream jobs. At minimum, document that `shop_domain` from `WebhookVerification` is not authenticated by the HMAC and must not be used for security-sensitive shop selection without additional verification (e.g., confirming the shop has an active installed session before acting).

### Proof of Concept
1. Register `CustomWebhooksController` as documented, including `ShopifyApp::WebhookVerification`, and use `shop_domain` to route a job (`SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`) [4](#0-3) .
2. Capture a legitimately signed webhook body + `X-Shopify-Hmac-Sha256` value (e.g., from a webhook delivered for the attacker's own shop, or via any means of observing a valid pair).
3. Replay a POST to the webhook endpoint with the same body/HMAC but a different `X-Shopify-Shop-Domain` header value pointing at a victim shop.
4. `verify_request` in `WebhookVerification` calls `hmac_valid?(request.raw_post)`, which validates successfully since only the body (not headers) is signed [2](#0-1) .
5. `shop_domain` returns the attacker-forged victim domain [3](#0-2) , and the downstream job (e.g., an uninstall/redact job pattern shown in the generators) acts on the victim shop's record using attacker-controlled attribution.
