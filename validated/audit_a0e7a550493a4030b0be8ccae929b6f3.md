### Title
ERC20-to-CW20 pointer contract does not verify the underlying ERC20's `transfer`/`transferFrom` boolean return value before reporting success - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The CW20 pointer contract that wraps an arbitrary EVM ERC20 token (`example/cosmwasm/cw20/src/contract.rs`, used by `x/evm`'s ERC20→CW20 pointer registration flow) issues a `transfer`/`transferFrom` call to the underlying ERC20 via `EvmMsg::DelegateCallEvm` and unconditionally reports success (attributes, `Cw20ReceiveMsg` hook) without checking the boolean return value of the delegated ERC20 call.

### Finding Description
`transfer()` and `transfer_from()` in `example/cosmwasm/cw20/src/contract.rs` build a `DelegateCallEvm` message targeting the wrapped ERC20's `transfer`/`transferFrom` selector and simply `add_message` it, without any `Reply` handling to check the actual boolean return data of the ERC20 call: [1](#0-0) [2](#0-1) 

`execute_send`/`execute_send_from` compound this: after calling `transfer`/`transfer_from`, they unconditionally append a `Cw20ReceiveMsg` notification to the recipient contract, telling it that `amount` was received — regardless of whether the underlying ERC20 delegatecall actually moved funds: [3](#0-2) [4](#0-3) 

This is analogous to the reported Cooler bug: an ERC20 that returns `false` on failure instead of reverting (e.g. a token with insufficient-balance/insufficient-allowance checks that silently return `false`) will make the `DelegateCallEvm` succeed at the EVM call layer (no revert ⇒ `success=true` in the Go handler `CallEVM`), so the CosmWasm message itself never errors. The pointer contract has no mechanism to inspect the ABI-decoded boolean return value of `transfer`/`transferFrom`, so it always treats the delegatecall as a successful transfer.

The EVM-side delegatecall is executed via `MsgInternalEVMDelegateCall`, handled in `x/evm/keeper/evm.go`'s `HandleInternalEVMDelegateCall`, which only returns an error if `CallEVM` itself reverts — it does not decode/verify the ERC20 return payload: [5](#0-4) 

Contrast this with the forward-direction pointer, `contracts/src/CW20ERC20Pointer.sol` (CW20→ERC20), which does have a `require(success, ...)` guard around the wasmd `execute` delegatecall — but that guard only checks that the *Cosmos execute message* didn't error, not that a wrapped ERC20's `transfer` returned `true`; conceptually the same root cause exists on that side too if the underlying CW20/ERC20 could return an ok response while silently not moving funds: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any CosmWasm contract that integrates with these ERC20-backed CW20 pointer tokens (via `Send`/`SendFrom` hooks, escrow, DEX, vault, or lending logic) and trusts a successful `TransferFrom`/`Send` execution as proof that funds moved can be tricked: an attacker deploys a malicious ERC20 (or points to an already-deployed non-standard token) whose `transfer`/`transferFrom` return `false` on failure instead of reverting. The attacker then calls `Send`/`SendFrom` on the CW20 pointer claiming to pay the victim contract; the delegatecall to the malicious ERC20 "succeeds" (no revert), the pointer contract fires the `Cw20ReceiveMsg` hook to the victim claiming the transfer of `amount`, and the victim contract releases collateral/goods/credit believing payment was received — while no value actually moved. This is a direct funds-loss vector for any contract trusting these hooks, matching the "Medium — lender can steal collateral" class from the source report.

### Likelihood Explanation
Reachable entirely by a permissionless actor: deploying a custom ERC20 with non-reverting failure semantics is a normal, unprivileged EVM contract deployment, and registering/using an ERC20→CW20 pointer for it is a standard, permissionless pointer-registration and `MsgExecuteContract`/EVM-tx flow. No validator, governance, or privileged operation is required. The only precondition is that some other contract chooses to trust the pointer's CW20 `Send`/`TransferFrom` semantics without independently verifying balance deltas — a reasonably common integration pattern for CW20-compatible vault/lending/DEX contracts.

### Recommendation
- After issuing the `DelegateCallEvm` for `transfer`/`transferFrom`/`approve`, decode the ABI return data of the ERC20 call (via a `Reply` submessage or a synchronous decode path) and explicitly assert it decodes to `true`; treat a `false` return the same as a revert (fail the CosmWasm execution).
- Only emit `Cw20ReceiveMsg`/attributes claiming a successful transfer after confirming the underlying transfer boolean is `true`.
- Consider using `SubMsg` with `ReplyOn::Success` plus explicit decode-and-check logic instead of `add_message`, so failures (including "silent" `false` returns) properly abort the whole CW20 execute.

### Proof of Concept
1. Attacker deploys a custom ERC20 contract `EvilToken` whose `transfer(address,uint256)` and `transferFrom(address,address,uint256)` return `false` (instead of reverting) whenever the sender's balance is insufficient.
2. Attacker registers an ERC20→CW20 pointer for `EvilToken` (permissionless pointer registration), obtaining CW20 contract `PointerCW20`.
3. Attacker (who holds `0` `EvilToken` balance) calls `PointerCW20::Send { contract: Victim, amount: 1000000, msg: <payload> }`.
4. Internally, `transfer()` in `example/cosmwasm/cw20/src/contract.rs` issues `EvmMsg::DelegateCallEvm` to `EvilToken.transfer(Victim, 1000000)`, which returns `false` without reverting — no CosmWasm error is raised.
5. `execute_send` unconditionally appends the `Cw20ReceiveMsg` to `Victim`, informing it that `1000000` tokens were received from Attacker.
6. `Victim` (e.g., a lending/escrow contract) trusts the receive hook, releases collateral/assets to Attacker, while `EvilToken`'s balances never changed — attacker obtains value without paying.

Note: I could not fully verify from the index whether the `example/cosmwasm/cw20` contract is byte-for-byte identical to the on-chain code deployed by `register-evm-pointer` for arbitrary ERC20 tokens (the wiring is only inferable from `wasmbinding/`, `x/evm/client/wasm/encoder.go`, and matching `EvmMsg::DelegateCallEvm` usage), so confirming the exact production wasm bytecode used for `WASM.POINTER_CW20`/`deployErc20PointerForCw20` would benefit from a full repository checkout in a Devin session.

    _env: Env,
    info: MessageInfo,

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;

        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

func (k *Keeper) HandleInternalEVMDelegateCall(ctx sdk.Context, req *types.MsgInternalEVMDelegateCall) (*sdk.Result, error) {
	var to *common.Address
	if req.To != "" {
		addr := common.HexToAddress(req.To)
		to = &addr
	} else {
		return nil, errors.New("cannot use a CosmWasm contract to delegate-create an EVM contract")
	}
	addr, _, exists := k.GetAnyPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(req.FromContract))))
	if !exists || common.BytesToAddress(addr).Cmp(*to) != 0 {
		return nil, errors.New("only pointer contract can make delegatecalls")
	}
	zeroInt := sdk.ZeroInt()
	senderAddr, err := sdk.AccAddressFromBech32(req.Sender)
	if err != nil {
		return nil, err
	}
	// delegatecall caller must be associated; otherwise any state change on EVM contract will be lost
	// after they asssociate.
	senderEvmAddr, found := k.GetEVMAddress(ctx, senderAddr)
	if !found {
		err := types.NewAssociationMissingErr(req.Sender)
		evmKeeperMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "evm_handle_internal_evm_delegate_call"), attribute.String("type", err.AddressType())))
		return nil, err
	}
	ret, err := k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)
	if err != nil {
		return nil, err
	}
	return &sdk.Result{Data: ret}, nil
}

    function transfer(address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");

        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));

        string memory req = _curlyBrace(_formatPayload("transfer_from", _curlyBrace(_join(_join(sender, recipient, ","), amt, ","))));

        return true;

    function _execute(bytes memory req) internal returns (bytes memory) {
        (bool success, bytes memory ret) = WASMD_PRECOMPILE_ADDRESS.delegatecall(
            abi.encodeWithSignature(
                "execute(string,bytes,bytes)",
                Cw20Address,
                bytes(req),
                bytes("[]")
            )
        );
        require(success, "CosmWasm execute failed");
        return ret;
    }
