### Title
Deferred validation of ephemeral string reads allows garbage/unvalidated data to reach message fields before the length mismatch is detected - ([File: upb/wire/internal/eps_copy_input_stream.h])

### Summary
The external report describes a pattern where `_validateTokenInput()` has two data-intake paths: one (`router.pairTransferERC20From`) verifies the actual amount received against the requested amount immediately, and the other (`safeTransferFrom`) trusts the nominal transfer amount without checking what was actually received, deferring any discrepancy to be silently absorbed into contract state. The Protobuf analog is `upb_EpsCopyInputStream_ReadStringEphemeral()`, which by design skips validating that the requested `size` is actually within the current buffer/stream limit at the time of the read, and explicitly documents that the resulting `upb_StringView` may contain "garbage bytes from the patch buffer" that only gets caught later via `upb_EpsCopyInputStream_IsDone()` — an out-of-band, deferred check, exactly mirroring the "unchecked transfer now, maybe caught later" defect class in the report.

### Finding Description
`upb_EpsCopyInputStream_ReadStringEphemeral()` reads a length-delimited value for `size` bytes and returns a `upb_StringView` pointing directly at `ptr`, but only bounds-checks against `e->end + kUpb_EpsCopyInputStream_SlopBytes` (the slop-padded buffer boundary), not against the actual wire-format limit for the current sub-message/field: [1](#0-0) 

The header-level documentation for this function is explicit about the consequence: "this function does not check that `size` is within the current limit or even the end of the stream... they may contain garbage data that does not correspond to anything in the input. This error will be detected later, when calling `upb_EpsCopyInputStream_IsDone()`... but it may result in nonsense bytes ending up in the output." [2](#0-1) 

This is structurally the same invariant violation as the Sudoswap bug: the "amount actually available/received" (bytes truly present within the field's limit) is not verified at the point the value is consumed and handed off to the caller; instead, an untrusted/garbage value is optimistically accepted and validation is deferred to a later, decoupled check (`IsDone()`), similar to how `_validateTokenInput()`'s direct `safeTransferFrom()` path accepts the nominal `inputAmount` without confirming the recipient's balance actually increased by that amount, deferring any correctness guarantee to trust in the ERC20 implementation.

By contrast, `upb_EpsCopyInputStream_ReadStringAlwaysAlias()` (the "checked" counterpart in the same file) performs the size-vs-limit check immediately and fails fast, matching the router-based path in the report that validates immediately via `balanceOf` diffing: [3](#0-2) 

### Impact Explanation
Within `upb`'s architecture, `ReadStringEphemeral` is intentionally a low-level, opt-in primitive for callers who can tolerate deferred validation (e.g., because they will call `IsDone()` before trusting the result), not a general-purpose parsing entry point exposed directly to untrusted wire input without a subsequent gate. I was not able to fully trace, within the remaining tool budget, every call site in `upb/wire/decode.c` to confirm whether any production decode path consumes the ephemeral view (e.g., copies it into a message field, map key, or forwards it to application code) *before* the corresponding `IsDone()` check executes for that record. If such a path exists, garbage/uninitialized bytes from the patch buffer could be observed by application code prior to the parse ultimately being rejected — an integrity/information-disclosure concern analogous to, but distinct from, the token-count mismatch in the report (there, the impact is contract-state corruption from trusting an unchecked transfer amount; here, it would be use of unvalidated buffer contents prior to error detection).

Given the documentation frames this explicitly as a known, deliberate deferred-check design (not a silently-introduced bug), and given I could not confirm a reachable path where consumer code observes the garbage bytes before `IsDone()` fires and rejects the parse, this does not clearly rise to the same "silently accepted, unrecoverable state corruption" severity described in the LSSVM report. It should be treated as a **Low-to-Medium** severity design note rather than a confirmed exploitable vulnerability.

### Likelihood Explanation
Likelihood is **low**. `ReadStringEphemeral` is a specialized/internal primitive (in `upb/wire/internal/...` and `upb/wire/eps_copy_input_stream.h`'s public but clearly-labeled-risky API), not the default path used by the standard generated-code fast/table-driven parsers for strings/bytes (those use `ReadStringAlwaysAlias`/`_upb_Decoder_ReadString`, both of which validate immediately, as seen in `upb/wire/decode_fast/field_string.c`). Exploitation would require a caller within the trusted `upb` codebase (not attacker-controlled) to use the ephemeral variant and then act on the returned view before calling `IsDone()`, which the API contract explicitly warns against.

### Recommendation
- Audit all call sites of `upb_EpsCopyInputStream_ReadStringEphemeral()` in `upb/wire/decode.c` to confirm none expose the ephemeral (potentially garbage) `upb_StringView` to application-visible state (message fields, hashmap keys, output buffers) prior to the enclosing `upb_EpsCopyInputStream_IsDone()` check for that read.
- Consider renaming/annotating the function more forcefully (e.g., `_Unsafe` suffix) or adding an assertion-gated invariant that the caller must not persist/leak the returned view outside the current record boundary until validated.
- No change is recommended for `ReadStringAlwaysAlias`, which already validates eagerly and is the correct analog of the "checked" transfer path in the report.

### Proof of Concept
Not established. I could not, within the available tool budget, construct or confirm a concrete crafted-input trace demonstrating that a caller in `upb/wire/decode.c` uses `ReadStringEphemeral`'s result before the deferred `IsDone()` check runs. This would require reading the full body of `upb/wire/decode.c` around each of its `ReadStringEphemeral`/`IsDone` call sites, which was not completed before the iteration limit. This finding should be treated as a documented design risk requiring further verification rather than a proven exploitable vulnerability with a reproduced trace.

UPB_INLINE const char* upb_EpsCopyInputStream_ReadStringAlwaysAlias(
    struct upb_EpsCopyInputStream* e, const char* ptr, size_t size,
    upb_StringView* sv) {
  UPB_ASSERT(size <= PTRDIFF_MAX);
  // The `size` must be within the input buffer. If `ptr` is in the input
  // buffer, then using the slop bytes is fine (because they are real bytes from
  // the tail of the input buffer). If `ptr` is in the patch buffer, then slop
  // bytes represent bytes that do not actually exist in the original input
  // buffer, so we must fail if the size extends into the slop bytes.
  const char* limit =
      e->end + (e->input_delta == 0) * kUpb_EpsCopyInputStream_SlopBytes;
  if ((ptrdiff_t)size > limit - ptr) {
    // For the moment, we consider this an error.  In a multi-buffer world,
    // it could be that the requested string extends into the next buffer, which
    // is not an error and should be recoverable.
    return UPB_PRIVATE(upb_EpsCopyInputStream_ReturnError)(e);
  }
  const char* input = UPB_PRIVATE(upb_EpsCopyInputStream_GetInputPtr)(e, ptr);
  *sv = upb_StringView_FromDataAndSize(input, size);
  return ptr + size;
}
