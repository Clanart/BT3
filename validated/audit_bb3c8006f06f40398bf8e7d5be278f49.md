### Title
Repeated claiming during an active vlMGP unlock forfeit lets a user reclaim their own penalty, undermining the early-unlock forfeit mechanism - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder` applies a forfeit to a user's accrued reward based on that user's own unlock status (`vlMGP.getRewardablePercentWAD`), but the forfeited amount is re-injected into the pool's global `rewardPerTokenStored` accumulator, which the forfeiting user continues to participate in as long as they still hold vlMGP balance. This mirrors the reported bug class: a claim-time deduction that is redistributed to all participants, including the very account that was penalized, enabling that account to recapture part of its own forfeited reward through repeated claims.

### Finding Description
`_sendReward` computes a `forfeitAmount` from the user's own `userRewards` balance via `_calExpireForfeit`, which is driven by `vlMGP.getRewardablePercentWAD(_account)` — a value tied to how much of the user's vlMGP is still locked vs. in cooldown/expired. [1](#0-0) 

The forfeited amount is not burned or set aside for other users only — it is pushed back into the shared accumulator via `_queueNewRewardsWithoutTransfer`, which increases `rewardPerTokenStored` proportionally to `totalStaked()` (i.e., `vlMGP` total supply): [2](#0-1) 

Because `totalStaked()` is the entire vlMGP supply and `balanceOf(_account)` is the caller's own locked/cooldown weight, the caller is itself one of the beneficiaries of this re-accumulation: [3](#0-2) 

The forfeit percentage is derived purely from `_account`'s own lock/cooldown state each time it is (re)computed: [4](#0-3) 

Flow across repeated calls to `getReward`:
1. Call 1: `_updateFor` syncs `userRewards[account]` to current earned amount and sets `userRewardPerTokenPaid[account] = R0`. `_sendReward` forfeits `f0` of it, pays out the rest, and calls `_queueNewRewardsWithoutTransfer(f0, ...)`, which raises `rewardPerTokenStored` to `R1 = R0 + f0*10**dec/totalStaked()`.
2. In a subsequent call (next block/tx), `_updateFor` recomputes `earned` using the now-stale `userRewardPerTokenPaid = R0` vs the new `rewardPerToken() = R1`, crediting the account with `balanceOf(account) * (R1-R0)/10**dec` — i.e., the account's proportional share of the very forfeit it just triggered.
3. Calling `getReward` again pays out `(1 - forfeitRate)` of that reclaimed share, and forfeits the rest, which is again re-injected into the pool (partially benefiting the same account again on the next call).

This is a geometric process: each round returns a shrinking amount back to the same account, driven purely by that account's own share of `totalStaked()`. The larger the caller's proportion of the vlMGP supply, the larger the fraction of its own "penalty" it can reclaim across repeated claims, defeating the purpose of the forfeit (which is meant to be a real penalty transferred to *other* honest lockers, not partially refunded to the offending account).

### Impact Explanation
The early-unlock/cooldown forfeit in `vlMGPBaseRewarder` is a specific anti-abuse penalty tied to an individual account's lock status (unlike a uniform protocol-wide "compounding" deduction). By repeatedly calling `getReward`, an unprivileged wallet with a non-trivial share of the vlMGP supply can recapture part of the reward it was supposed to forfeit, which comes at the direct expense of the pool's other honest lockers, who were expecting the full forfeited amount to be redistributed away from the penalized account. This constitutes unclaimed-yield/permanent-loss redirection for other users and undermines the protocol's intended tokenomics/penalty design for `vlMGP` reward claims — an in-scope "VLMGP lock slots and forfeits" surface.

### Likelihood Explanation
Reachable by any ordinary vlMGP holder who is in an "unlock cooldown" or otherwise has `getRewardablePercentWAD < 100%` and has pending rewards in a `vlMGPBaseRewarder` pool — no privileged role or admin action required. The only precondition affecting severity is the account's proportional share of `totalStaked()` (total vlMGP supply): the more vlMGP the account holds, the more of its own forfeit it can reclaim, but even smaller holders extract more than the intended zero.

### Recommendation
Do not use the account's own forfeited amount to inflate the same pool's shared `rewardPerTokenStored` that this account also participates in. Instead, either exclude the forfeiting account from the specific re-accumulation event (e.g., snapshot `totalStaked() - balanceOf(account)` as the distribution base, or track/settle the account's `userRewardPerTokenPaid` past the newly injected forfeit before crediting it), or route forfeited rewards to a separate, non-self-referential distribution mechanism (e.g., protocol treasury or a snapshot-based distribution excluding the current claimer).

### Proof of Concept
Given `vlMGPBaseRewarder._sendReward`/`_queueNewRewardsWithoutTransfer`: [1](#0-0) [2](#0-1) 

1. Alice locks a majority share of the total vlMGP supply and later has some vlMGP in cooldown/expired such that `vlMGP.getRewardablePercentWAD(alice) < 100%`.
2. Rewards accrue for Alice's `userRewards[token][alice]`.
3. Alice calls `getReward` (via `masterMagpie`): a forfeit `f0` is computed from her own status and re-added to `rewardPerTokenStored` (shared across all `vlMGP` holders, including herself).
4. In a following transaction, Alice calls `getReward` again: `_updateFor` credits her with `balanceOf(alice)/totalStaked() * f0`, a portion of the "penalty" she was just charged, since `balanceOf(alice)` is a large fraction of `totalStaked()`.
5. Repeating this process lets Alice recapture a geometrically-decreasing but material fraction of the reward that should have been permanently forfeited to other lockers.

Note: I was not able to fully trace the exact `MasterMagpie` harvesting entry points that call `vlMGPBaseRewarder.getReward` (e.g., whether a `multiclaim`/`harvest` batch function exists that could compress this into fewer transactions) due to running out of search iterations; this does not affect the root-cause finding in `vlMGPBaseRewarder.sol`, but a full exploit-transaction script would need that context, which a Devin session with full repository access could confirm.

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }

    function _sendReward(address _rewardToken, address _account, address _receiver) internal {
        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
            
        if (toSend > 0) {
            IERC20(_rewardToken).safeTransfer(_receiver, toSend);
            emit RewardPaid(_account, _receiver, toSend, _rewardToken);
        }

        if(forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
