### Title
Unprotected/front-runnable initializer in upgradeable contracts (MasterMagpie, VLMGP, mWomSV, WomUp, ReferralStorage) allows any wallet to seize ownership - (File: rewards/MasterMagpie.sol, VLMGP.sol, wombat/mWomSV.sol, wombat/WomUp.sol, rewards/ReferralStorage.sol)

### Summary
`MasterMagpie`, `VLMGP`, `mWomSV`, `WomUp`, and `ReferralStorage` are OpenZeppelin `Initializable` upgradeable contracts whose `__*_init(...)` functions are `public` and guarded only by the standard `initializer` modifier, which merely prevents *re*-initialization — it does not restrict *who* may call the function first. Each of these functions calls `__Ownable_init()`, which sets `msg.sender` as the contract owner, and also wires in critical protocol addresses (MGP token, masterMagpie address, vlMGP, treasury/reward-related state). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
These contracts are deployed as implementation contracts behind upgradeable proxies (see `TransparentUpgradeableproxy` wrapper) and initialized in a separate transaction from deployment (the proxy constructor's `_data` parameter can be left empty, matching the exact deployment pattern flagged in the referenced report). Because the `initializer` modifier only enforces "can be called once," any unprivileged wallet monitoring the mempool/deployment transactions can front-run the legitimate deployer's initialization call and invoke `__MasterMagpie_init`, `__VLMGP_init`, `__mWOMSV_init_`, `__womup_init`, or `__ReferralStorage_init` directly with attacker-controlled parameters. [6](#0-5) [7](#0-6) 

Since `__Ownable_init()` sets the caller as `owner()`, the attacker becomes the contract's owner — gaining control over `_onlyPoolManager`-gated functions (pool management, allocation points) in `MasterMagpie`, and owner-only configuration in `VLMGP`/`mWomSV`/`WomUp`/`ReferralStorage`, such as `masterMagpie`, `MGP`, `vlMGP`, `penaltyDestination`, `coolDownInSecs`, and `startTime`. Because `PoolManagers[owner()] = true` is set in `MasterMagpie`'s initializer, the attacker also gains pool-manager privileges directly upon front-running. [8](#0-7) 

### Impact Explanation
If exploited, the attacker becomes the permanent owner (and pool manager) of the emission/staking core (`MasterMagpie`) or of the lock/vault contracts (`VLMGP`, `mWomSV`), or controls reward routing addresses in `WomUp`/`ReferralStorage`. This is not a benign misconfiguration — it directly enables the attacker to redirect emissions, set malicious `masterMagpie`/`penaltyDestination`/`rewardToken` addresses, or otherwise seize control of unclaimed yield and locked-token accounting for all subsequent users, since these are the exact contracts users deposit MGP/mWOM/LP tokens into. This can result in permanent loss/freezing of user funds and protocol insolvency, matching the required impact bar.

### Likelihood Explanation
Exploitation requires only watching a public/known deployment sequence and sending a single transaction with a higher gas price to front-run the legitimate initialization call — this needs no special privileges, and is a well-documented, cheap, and repeatable class of attack (as evidenced by the very report this analog is derived from) against every one of the initializer functions cited above.

### Recommendation
- Restrict who may call the `__*_init` functions, e.g., require `msg.sender == deployer` recorded in the proxy admin/factory, or perform the deployment+initialization atomically by passing the encoded initializer call as the `_data` parameter to the `TransparentUpgradeableProxy` constructor rather than leaving it empty and calling it in a separate transaction.
- After any deployment, verify on-chain that `owner()` and critical addresses (`mgp`, `masterMagpie`, `vlMGP`, `penaltyDestination`, etc.) match the intended values before allowing user interaction (e.g., before unpausing or funding the contract).

### Proof of Concept
1. Deployer deploys the `TransparentUpgradeableproxy` pointing at the `MasterMagpie` (or `VLMGP`/`mWomSV`/`WomUp`/`ReferralStorage`) implementation with empty `_data`. [9](#0-8) 
2. An attacker monitoring the mempool/deployment sequence sends a transaction calling `__MasterMagpie_init(attackerMgp, ..., ...)` on the proxy address before the deployer's own initialization transaction lands.
3. `initializer` modifier only blocks a second call — it does not check `msg.sender` — so the call succeeds, `__Ownable_init()` sets the attacker as `owner()`, and `PoolManagers[owner()] = true` grants the attacker pool-manager rights. [10](#0-9) 
4. The deployer's later initialization transaction reverts (already initialized), and the protocol's core emission/staking contract is now owned and configured by the attacker, requiring a redeploy or resulting in loss of funds/control if unnoticed.
