### Title
Unbounded array index in git raw/numstat diff parser causes unhandled crash on attacker-controlled fork/PR diffs - (File: `app/src/lib/git/log.ts`)

### Summary
The bug-class of the go-f3 advisory is: an unchecked integer derived from untrusted input is used to index/validate data, and no overflow/bounds check exists before it is used, leading to a crash of the consuming process. The closest verified analog in this codebase is `parseRawLogWithNumstat` in `app/src/lib/git/log.ts`, which indexes into the `files` array using a running counter (`numStatCount`) that is never bounds-checked against `files.length` before being dereferenced.

### Finding Description
`parseRawLogWithNumstat` walks the NUL-separated output of `git diff/log --raw --numstat -z` and builds a `files` array from the `--raw` section, then walks the `--numstat` section and, for each numstat line, looks at the file previously pushed at `files[numStatCount]` to decide whether the entry is a rename/copy (which consumes two extra lines for old/new path): [1](#0-0) 

Every other value extracted from this untrusted git output in the same function is defensively unwrapped with `forceUnwrap(...)`, which throws a clear, descriptive error if a capture is missing (see the `srcMode`/`dstMode`/`status`/`oldPath`/`path` reads): [2](#0-1) 

but the `files[numStatCount]` access at line 326 has no such guard. If `numStatCount` ever reaches or exceeds `files.length` (i.e., the number of `--numstat` entries emitted by git exceeds the number of `--raw` entries collected into `files`), the expression `files[numStatCount].status` dereferences `.status` on `undefined`, producing an unhandled `TypeError` instead of the graceful `forceUnwrap` error used everywhere else in this same function. This is the same broken-invariant pattern as the go-f3 issue: a value computed from attacker-influenced (repository/diff) content is trusted to stay within a valid range, and the one code path handling that value skips the validation applied everywhere else nearby.

This parser is directly reachable with attacker-influenced input:
- `getChangedFiles` runs `git log -m --raw --numstat -z` for a single commit and feeds the output straight into `parseRawLogWithNumstat` [3](#0-2) .
- `getCommitRangeChangedFiles` and `getBranchMergeBaseChangedFiles` do the same for `git diff --raw --numstat -z` across a commit range / merge-base, feeding output from `-C -M` rename/copy detection [4](#0-3) [5](#0-4) .
- `getStashedFiles` also reuses this parser for `git stash show --raw --numstat -z` [6](#0-5) .

All of these are exercised on commits/diffs that originate from remote branches, forked pull requests being previewed, or fetched history — content an attacker fully controls (file paths, rename/copy layout, mode changes, merge structure), not something the local user authored. The project's own changelog documents a prior real-world occurrence of exactly this class of bug: `"[Fixed] Fix "Invalid numstat line" error when trying to preview a pull request - #17267"` [7](#0-6) , confirming that crafted/unusual diff content from external repositories has previously desynchronized the raw/numstat pairing in this exact code path. The `files[numStatCount]` guard was never brought up to the same defensive standard as the rest of the function when that fix landed.

### Impact Explanation
A successful trigger produces an unhandled `TypeError` inside Desktop's git-operations layer (main process), while the process is fetching/parsing changed-file data for a commit, PR preview, stash entry, or branch comparison sourced from an untrusted repository. Depending on where the promise rejection propagates, this can manifest as: the "Diverged from — Changes" / "Files Changed" view failing to render, the app entering a broken/frozen state for that repository, or (if unhandled at a higher level) crashing the operation pipeline — a silent-corruption/denial style impact on the specific feature (PR preview / commit view) rather than remote code execution. This maps to the "silent corruption of what the user commits or pushes" / crash category named in the report's valid-impact list, since a partially-consumed `files` array or an aborted changeset computation could also produce an incomplete/misleading changed-files list if the exception is swallowed upstream.

### Likelihood Explanation
Reaching this code only requires an attacker to control the git history/diff of a repository or fork that a legitimate Desktop user opens, fetches, or previews as a PR — no elevated privileges, no local access, and no unusual user action beyond normal review-a-PR workflows that Desktop explicitly supports. The changelog entry for issue #17267 is direct evidence that real, unmodified fork content has already desynchronized raw/numstat parsing here once; the missing bounds check at line 326 means a similar (or intentionally crafted) diff shape can still produce an unguarded `undefined.status` dereference today.

### Recommendation
Add the same defensive check used elsewhere in the function before dereferencing `files[numStatCount]`, e.g.:
```ts
const file = files[numStatCount]
if (file === undefined) {
  throw new Error('Invalid log output (numstat/raw entry count mismatch)')
}
if (isCopyOrRename(file.status)) {
  i += 2
}
```
or use `forceUnwrap('Invalid numstat line (no matching raw entry)', files.at(numStatCount))` to match the error-handling style of the rest of `parseRawLogWithNumstat`, ensuring callers get a catchable, descriptive `Error` instead of a raw `TypeError` from `undefined`. Additionally, wrap calls to `parseRawLogWithNumstat` (`getChangedFiles`, `getCommitRangeChangedFiles`, `getBranchMergeBaseChangedFiles`, `getStashedFiles`) so a parse failure on one commit/PR degrades gracefully (e.g., empty changeset) rather than propagating an unhandled exception.

### Proof of Concept
Conceptual repro (exact git invocation that reproduces a raw/numstat mismatch was not reproducible without running git locally, so this is derived from static analysis, not a captured crash trace):
1. Attacker creates/maintains a public fork with a commit history containing an unusual diff shape (e.g., combining renames, mode-only changes, and submodule updates in a merge commit) such that `git diff/log --raw --numstat -z -M -C` emits more `--numstat` entries than `--raw` entries for the parser to have pushed into `files` — this is the same class of malformed pairing that previously caused issue #17267 ("Invalid numstat line" when previewing a PR).
2. Victim uses Desktop to preview this PR / fetch this fork, triggering `getBranchMergeBaseChangedFiles` or `getCommitRangeChangedFiles` [8](#0-7) .
3. `parseRawLogWithNumstat` processes the numstat section; once `numStatCount` reaches the end of `files`, `files[numStatCount]` is `undefined` and `.status` throws `TypeError: Cannot read properties of undefined (reading 'status')` [9](#0-8) , an unhandled exception distinct from the graceful `forceUnwrap` errors used on every other field in this function.

export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)

  // NOTE: order here matters - doing -M before -C means copies aren't detected

    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}

export async function getCommitRangeChangedFiles(
  repository: Repository,
  shas: ReadonlyArray<string>,
  useNullTreeSHA: boolean = false
): Promise<IChangesetData> {
  if (shas.length === 0) {
    throw new Error('No commits to diff...')
  }

  const oldestCommitRef = useNullTreeSHA ? NullTreeSHA : `${shas[0]}^`
  const latestCommitRef = shas.at(-1) ?? '' // can't be undefined since shas.length > 0
  const baseArgs = [
    'diff',
    oldestCommitRef,
    latestCommitRef,
    '-C',
    '-M',
    '-z',
    '--raw',
    '--numstat',
    '--',
  ]

  const { stdout, gitError } = await git(
    baseArgs,
    repository.path,
    'getCommitRangeChangedFiles',
    {
      expectedErrors: new Set([GitError.BadRevision]),
    }
  )

  // This should only happen if the oldest commit does not have a parent (ex:
  // initial commit of a branch) and therefore `SHA^` is not a valid reference.
  // In which case, we will retry with the null tree sha.
  if (gitError === GitError.BadRevision && useNullTreeSHA === false) {
    const useNullTreeSHA = true
    return getCommitRangeChangedFiles(repository, shas, useNullTreeSHA)
  }

  return parseRawLogWithNumstat(stdout, latestCommitRef, oldestCommitRef)
