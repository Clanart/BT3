### Title
`ReceivedOutput::read` accepts an arbitrary scalar `offset` never bound to the output's `script_pubkey`, reporting unspendable outputs as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The zkSync finding is a "validated-but-never-bound" bug: `initialize()` checked `_l1LegecyBridge != 0` but never assigned it, so `l1LegacyBridge` remained `address(0)` and `finalizeDeposit()` rejected every legitimate message from the still-active legacy bridge. The invariant the check was meant to establish was never persisted into the state the authorization path consults.

The same class exists in `networks/bitcoin/src/wallet/mod.rs`: `ReceivedOutput` pairs a scalar `offset` with a `TxOut`, and the only thing that makes an output spendable is that `key + G·offset` actually produces `output.script_pubkey`. `Scanner::scan_transaction` establishes this binding at scan time via `self.scripts.get(&output.script_pubkey)` (lines 205–211), but `ReceivedOutput::read` (lines 122–134) deserializes `offset`, `output`, and `outpoint` from untrusted bytes with no such consistency check — and nothing downstream re-validates it before the output is treated as a received, spendable coin.

### Finding Description
```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;      // arbitrary scalar, only canonicality-checked
    output = TxOut::consensus_decode(&mut buf_r)?;   // arbitrary script_pubkey
    outpoint = Outpoint::consensus_decode(&mut buf_r)?;
    Ok(ReceivedOutput { offset, output, outpoint })  // binding never verified or enforced
}
```

In the scanner path, `offset` is only meaningful because it was inserted by `register_offset`, which guarantees `p2tr_script_buf(key + G·offset) == script` (lines 184–195). `read` skips that guarantee entirely: `read_F` only checks canonical scalar encoding, and `consensus_decode` only checks syntactic validity. The struct fields are private, so the invariant "offset derives the script_pubkey under the scanner key" exists nowhere in the type — exactly like `l1LegacyBridge` being checked but never written into the storage slot `finalizeDeposit` reads.

### Impact Explanation
An attacker who can feed serialized `ReceivedOutput` bytes to a wallet (e.g., a malicious or compromised peer/coordinator supplying the output list) causes the wallet to record an output whose `offset` does not correspond to its `script_pubkey`. When the wallet later builds a spend via `send`, it tweaks `ThresholdKeys` by this `offset` (`keys.offset(offset)`); the resulting tweaked group key will not match the taproot internal key committed in `script_pubkey`, so the produced Schnorr signature cannot satisfy the output. The funds are reported received but are cryptographically unspendable — one of the accepted impact classes — and can additionally poison fee/change selection since `ReceivedOutput::value()` is trusted for coin selection.

### Likelihood Explanation
Requires an untrusted party to supply `ReceivedOutput` bytes to a deserializing wallet component, which the scope rules explicitly treat as reachable (`ReceivedOutput::read` is a listed untrusted-bytes sink). The malformed input requires no secret knowledge — any scalar plus any syntactically valid `TxOut`/`OutPoint` passes. Impact is a funds-accounting/spendability denial rather than key recovery, matching Medium severity of the source finding.

### Recommendation
Bind the offset to the output it claims to spend. Since `ReceivedOutput` does not carry the scanner key, either (a) have `read`/`scan` re-derive `p2tr_script_buf(key + G·offset)` against the loaded `Scanner`'s key and reject mismatches before the output enters the spendable set, or (b) make `ReceivedOutput::read` private to `Scanner` and expose a `Scanner::read_outputs(key, bytes)` constructor that performs the same `self.scripts.contains(&output.script_pubkey)` check as `scan_transaction`. This mirrors the upstream fix: persist/verify the value the later authorization path depends on, not merely validate its shape.

### Proof of Concept
```rust
// Given a Scanner with key K and any attacker-chosen scalar o' and TxOut
// whose script_pubkey is NOT p2tr(K + G*o'):
let mut bytes = Vec::new();
bytes.extend(o'.to_bytes());            // arbitrary canonical scalar
bytes.extend(serialize(&victim_txout)); // e.g., an output to a key the wallet doesn't control
bytes.extend(serialize(&fake_outpoint));
let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap(); // accepted
// Wallet treats `ro` as owned funds of value ro.value();
// send() calls keys.offset(o') -> tweaked group key != taproot internal key
// in victim_txout.script_pubkey -> signature invalid -> output unspendable,
// while balance accounting counted it as received.
```

Caveat: I could not inspect `networks/bitcoin/src/wallet/send.rs` (feature-gated) to confirm the spend path consumes `offset` without re-derivation; the finding assumes `send` trusts `ReceivedOutput.offset` for key tweaking, which is consistent with the field's documented purpose (lines 91–92, "the scalar offset to obtain the key usable to spend this output") and with `tweak_keys`/`offset` semantics in `crypto/dkg/src/lib.rs:414`.
