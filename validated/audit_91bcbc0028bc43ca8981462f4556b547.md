Based on the code I found, the Tron variant of `IntentGatewayV2` diverges from the canonical EVM implementation in exactly the way the zBanc report warns about: a governance/admin-settable numeric parameter used directly in fee arithmetic has no bounds check, unlike its sibling contract which explicitly validates it.

### Title
Unbounded `protocolFeeBps` / `surplusShareBps` in Tron `IntentGatewayV2.setParams` allows fee-calculation corruption and fund loss - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The canonical `IntentGatewayV2` (EVM) validates all governance-settable `Params` fields via `_validateParams`, explicitly rejecting `surplusShareBps > 10_000` and `protocolFeeBps >= 10_000` before they are applied [1](#0-0) , and the same bound is enforced per-destination in `_updateParams` [2](#0-1) . The Tron port of `IntentGatewayV2`, however, exposes a `setParams` function that stores the caller-supplied `Params` struct with **no validation at all**:

```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    _admin = address(0);
    _params = p;
}
``` [3](#0-2) 

This is precisely the pattern the zBanc report flags: a percentage-denominated field (`protocolFeeBps`, "10000 = 100%") that is later used directly as a fee multiplier without checking it lies within `[0, 10_000)`.

### Finding Description
`protocolFeeBps` is documented as basis points where 10,000 = 100% [4](#0-3) , and it is consumed in `placeOrder` to compute the protocol fee deducted from escrowed order inputs:

```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
``` [5](#0-4) 

If `protocolFeeBps >= 10_000`, `protocolFee` exceeds `originalAmount`, and `originalAmount - protocolFee` underflows, causing `placeOrder` to revert (functional bricking of order placement, matching the zBanc "functionality not working correctly" impact) — or, for values just at/above 10,000, silently over-deducts user input tokens beyond their escrowed amount, corrupting the amount recorded in `_orders[commitment][token]` versus what was actually collected. Because `_orders` tracks the *reduced* amount while actual token transfers (`safeTransferFrom`) still move the *original*, unreduced amount from the user in the non-predispatch path [6](#0-5) , an out-of-range fee value breaks the accounting invariant between what is escrowed on-chain (`_orders`) and what was actually pulled from the user, since `_orders` is what governs subsequent withdrawal/refund/redeem-escrow amounts.

Unlike the EVM `IntentsBase._validateParams`, the Tron `setParams` has no equivalent guard for `_params.protocolFeeBps` or `_params.surplusShareBps`, and no equivalent validation exists in the cross-chain `UpdateParams` path either based on the code inspected.

### Impact Explanation
This falls within the bounty's accepted class ("logic attacks", "transaction manipulation", "false ... state acceptance" of parameters) because it lets a misconfigured or malicious value for `protocolFeeBps` cause either (a) denial of the `placeOrder` entrypoint via underflow revert, or (b) escrow accounting to diverge from the true token amount transferred, both of which are direct fund-safety concerns for an unprivileged user who places an order once the parameter is misconfigured. The divergence between actual token custody and the `_orders` ledger is the class of bug ("wrong beneficiary or amount", "fund loss/lock") explicitly called out in the impact gate.

### Likelihood Explanation
Triggering requires the Tron `_admin` (or later, the governance `UpdateParams` message path) to set an out-of-range `protocolFeeBps`/`surplusShareBps` — this is a one-time misconfiguration during setup/lifecycle akin to the original zBanc scenario where "these values are usually set in the beginning of the lifecycle... misconfiguration may stay unnoticed until" the affected code path is exercised. Once set, every subsequent unprivileged call to `placeOrder` is affected without needing any additional attacker capability, matching the original report's framing exactly.

### Recommendation
Port the exact same guard used in `evm/src/apps/intentsv2/IntentsBase.sol::_validateParams` to the Tron `IntentGatewayV2.setParams` (and any `UpdateParams` handling path in the Tron contract), rejecting `p.protocolFeeBps >= 10_000` and `p.surplusShareBps > 10_000` before committing `_params = p`, and apply the same `feeBps >= 10_000` check to any per-destination fee override.

### Proof of Concept
1. Admin (or the entity controlling `_admin` before renouncement) calls `setParams` on the Tron `IntentGatewayV2` with `protocolFeeBps = 10_000` (100%) or higher — no revert occurs since there is no validation [7](#0-6) .
2. Any user calls `placeOrder` with a non-zero-fee order; `_destinationProtocolFees` is 0 so `_params.protocolFeeBps` (10,000+) is used [8](#0-7) .
3. `protocolFee = originalAmount * 10_000 / 10_000 = originalAmount` exactly at the boundary (or exceeds `originalAmount` above it), causing `reducedAmount = originalAmount - protocolFee` to be `0` or to underflow and revert — either bricking order placement or recording `0`/corrupted escrowed amount in `_orders[commitment][token]` while the full `order.inputs[i].amount` was already pulled via `safeTransferFrom` [9](#0-8) , desynchronizing custody from the escrow ledger used for later withdrawal/refund.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();

        if (p.surplusShareBps > 10_000) revert InvalidInput();
