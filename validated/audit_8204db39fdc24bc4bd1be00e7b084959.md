### Title
Frozen-message immutability guard implemented only as `UPB_ASSERT`, silently disabled in release builds - (File: `upb/wire/decode.c`, `upb/json/decode.c`, `upb/message/message.c`)

### Summary
The Astaria report describes a pattern where a security-relevant state flag (`isShutdown`) is fetched by the code but never actually checked in a conditional to gate a mutating action, so the guard exists in name only and the mutating flow proceeds regardless of state. The strongest structural analog in this Protobuf checkout is the `upb` "frozen message" invariant: `upb_Message_IsFrozen()` is the documented mechanism by which a host application can mark a message immutable, but every call site in the wire decoder, the JSON decoder, and the low-level mutation helpers enforces this invariant exclusively via `UPB_ASSERT(!upb_Message_IsFrozen(msg))` rather than a real runtime `if`/return-error check.

### Finding Description
`upb_Decode` (the binary wire-format entry point used transitively by Python/Ruby/PHP/Java-via-upb bindings) begins with: [1](#0-0) 
The only protection against parsing into an already-frozen message is `UPB_ASSERT(!upb_Message_IsFrozen(msg));` — an assertion, not a branch that aborts the operation and returns an error status.

The same pattern repeats throughout the JSON/ProtoJSON decoder, which is a supported public parse API (`upb_JsonDecodeDetectingNonconformance` / `upb_JsonDecode`): every recursive helper (`jsondec_object`, `jsondec_field`, `jsondec_array`, `jsondec_map`, `jsondec_any`, `jsondec_wrapper`, `jsondec_wellknown*`, etc.) opens with `UPB_ASSERT(!upb_Message_IsFrozen(msg))` before mutating the target message, again purely a debug-time assertion: [2](#0-1) [3](#0-2) 

The low-level mutators that both decoders call into (`_upb_Message_AddUnknown`, `_upb_Message_AddUnknownSlowPath`, `upb_Message_Mutable`, `_upb_Message_TryAddUnknownAliasAllowMerge`) rely on the identical assert-only pattern: [4](#0-3) [5](#0-4) 

`UPB_ASSERT` in upb is defined to compile to a no-op when `NDEBUG` is set (standard for release/production builds, including the wheels/gems typically shipped to consumers). This means that in a production build, if a host application obtains a frozen `upb_Message` (e.g., a cached/shared, previously validated, or otherwise trusted-immutable message, exposed via the `Message.Freeze()`/`freeze` bindings in Ruby, or the `MESSAGE_FROZEN` state in Python) and then routes attacker-controlled bytes into `upb_Decode`, `upb_DecodeLengthPrefixed`, or the JSON decoder against that same message pointer, the "should not be mutable" invariant is not actually enforced at runtime — parsing proceeds and silently corrupts/overwrites fields of the object the application believed was immutable. This directly parallels the original bug's failure mode: the flag that should gate the mutating flow (`isShutdown` / `IsFrozen`) is present and computed, but not used as a real, always-active runtime check in the reachable production code path — only in an assertion that vanishes outside of debug/ASan builds.

### Impact Explanation
If a consuming application freezes a message and relies on that invariant for correctness or security decisions (e.g., treating a frozen message as an already-validated/immutable record, sharing it across threads/tenants, or reusing it as a cache key), an attacker who can route additional attacker-controlled binary or ProtoJSON bytes into a parse call against that same message object in a release build can silently mutate fields that the application assumes are fixed. This is a data-integrity violation analogous to the smart-contract report's core failure ("commit to lien" succeeding despite the vault being shut down) — an invariant intended to block a state-changing operation is bypassed because the enforcing check is not actually active in the code path attacker input reaches.

### Likelihood Explanation
Reachability depends entirely on whether a specific consuming application (a) exposes a public parse API, (b) freezes messages as part of its trust model, and (c) later re-parses attacker data into an already-frozen message instance rather than a fresh one. Because `IsFrozen`/freezing is an opt-in feature used by higher-level bindings (Ruby/Python `Message.freeze`), and typical decode call sites (`FromString`, `MergeFromString`) construct/target a fresh, non-frozen message in normal application flow, this requires an application pattern where a frozen message is deliberately reused as a decode target — which is somewhat unusual but not implausible (e.g., defensive-copy-avoidance patterns, object pooling). I was not able to fully verify, within the remaining investigation budget, whether the higher-level language bindings (`python/message.c`, `ruby/ext/google/protobuf_c/message.c`) add an additional real (non-assert) `IsFrozen` check at their own public parse entry points that would prevent this from being reachable in practice — that would need to be confirmed by inspecting those files' `IsFrozen` call sites directly, which I could not complete before running out of tool iterations.

### Recommendation
Convert the `UPB_ASSERT(!upb_Message_IsFrozen(msg))` guards in `upb_Decode`, `upb_DecodeWithTrace`, `upb_JsonDecoder_Decode`/`upb_JsonDecodeDetectingNonconformance`, and the internal mutators (`_upb_Message_AddUnknown*`, `upb_Message_Mutable`) into real runtime checks that return an explicit error/decode-status (e.g., a new `kUpb_DecodeStatus_Frozen` / `kUpb_JsonDecodeResult_Error`) instead of relying on assertions that are stripped in `NDEBUG`/release builds. Additionally, audit each language binding's public `ParseFromString`/`MergeFrom`/`FromString` entry points to confirm they perform an explicit frozen check before invoking the native decoder, independent of the upb-internal asserts.

### Proof of Concept
I was unable to complete a runnable local reproduction within the remaining tool budget. The reasoning above is based on static code inspection showing that every `IsFrozen` gate along the `upb_Decode` / JSON-decode / message-mutation call chain is implemented as `UPB_ASSERT` rather than a runtime-enforced branch: [6](#0-5) [7](#0-6) 
A minimal conceptual repro (pseudocode, C, release/NDEBUG build) would be:
```c
upb_Message* msg = upb_Message_New(mt, arena);
/* ... application populates and validates msg, then freezes it ... */
upb_Message_Freeze(msg, mt);  /* application now treats msg as immutable */

/* attacker-controlled bytes reach a decode call targeting the same frozen msg */
upb_Decode(attacker_buf, attacker_len, msg, mt, NULL, 0, arena);
/* In a release (NDEBUG) build, the UPB_ASSERT(!upb_Message_IsFrozen(msg))
   is compiled out, so decode proceeds and mutates fields of `msg`
   despite it being frozen. */
```
This was not executed against the actual build system in this session; confirming the exact reachability (whether any binding's public API can be coerced into calling `upb_Decode`/JSON-decode against a message it has already frozen) would require follow-up verification with a Devin session that can build and run the repository's test harnesses.
