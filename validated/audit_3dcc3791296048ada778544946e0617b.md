### Title
Excess native ETH sent to `EvmHost::dispatch` is refunded to the Host contract instead of the original payer, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report describes a class of bug where a value meant to be excess/refundable to the caller (`minOutput`) is consumed by an internal swap/settlement step whose own refund logic sends the leftover to the wrong party, permanently locking it. The same broken invariant exists in Hyperbridge's `EvmHost::dispatch`, which forwards the entire `msg.value` into a Uniswap V2 exact-output swap. Any ETH left over from that swap is refunded by the Uniswap router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original caller who supplied the `msg.value`. The excess therefore accumulates in the host contract's native balance and is never returned to the payer.

### Finding Description
`EvmHost::dispatch` handles native-token fee payment for POST requests: [1](#0-0) 

When `msg.value > 0`, the entire value is forwarded to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. The standard UniswapV2Router implementation of `swapETHForExactTokens` only consumes the amount needed to buy `post.fee` units of the fee token, and refunds `msg.value - amountIn` to `msg.sender` — but the `msg.sender` observed by the router is `EvmHost` itself, since `EvmHost` is the direct caller of the swap. The refunded dust ETH therefore lands in `EvmHost`'s own balance rather than being returned to whichever account/contract originally supplied the `msg.value` to `dispatch()`.

This is structurally identical to the reported `LSSVMRouter` bug: an outer caller supplies value expecting any unused portion back, an internal swap/settlement step computes and issues a refund, but the refund is bound to the wrong address (the intermediary contract) rather than the true payer, so the excess is permanently unrecoverable by that payer.

Every `HyperApp`/integrator that dispatches a POST request with native value (e.g. `evm/src/apps/intentsv2/ExtrinsicIntents.sol` forwards `options.nativeDispatchFee` to `IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request)` at [2](#0-1) ) relies on an off-chain/on-chain price estimate to size that value. Any overestimation — due to normal AMM price movement between quoting and execution, slippage buffers, or a caller intentionally sending slightly more to be safe — results in the excess being swallowed by `EvmHost` rather than refunded to the calling app, which in turn cannot return it to its own end-user.

### Impact Explanation
This causes an unprivileged, no-special-access loss of funds: any account (application contract or EOA) that calls `dispatch()` with native ETH will lose any amount beyond what the exact-output swap consumes, with no code path returning it. Because `dispatch()` is the primary payable entrypoint used by every HyperApp across the protocol for POST requests paid in native token, this is a broadly reachable, wallet-draining accounting bug rather than a theoretical edge case — it fires on ordinary price movement, not just attacker-crafted input.

### Likelihood Explanation
Likelihood is high: it triggers under completely normal operating conditions any time the actual on-chain swap price differs even slightly from the value the caller supplied (which is unavoidable given AMM price movement between fee estimation and transaction execution), and it requires no malicious actor, relayer, or governance action — only a standard call to `dispatch()` with `msg.value` slightly larger than what the exact-out swap needs.

### Recommendation
After the `swapETHForExactTokens` call in `EvmHost::dispatch`, compute the actual ETH spent (e.g., via the returned `amounts[0]` from the swap or a balance-delta snapshot) and refund `msg.value - amountSpent` to `_msgSender()` (the original caller of `dispatch`), mirroring the pattern already used correctly elsewhere in the codebase (e.g., `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol` and `UniV4UniswapV2Wrapper.sol`, both of which snapshot balance and explicitly refund unspent ETH back to `msg.sender`).

### Proof of Concept
1. A `HyperApp` (e.g., `ExtrinsicIntents::_fillCrossChain`) computes `options.nativeDispatchFee` slightly higher than the exact price needed to buy `post.fee` fee-tokens (a realistic scenario given AMM price drift), then calls `IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request)`.
2. Inside `EvmHost::dispatch` (`evm/src/core/EvmHost.sol:921-932`), the full `msg.value` is forwarded to `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`.
3. The Uniswap V2 router only spends `amounts[0] <= msg.value` and refunds `msg.value - amounts[0]` to `msg.sender`, which resolves to `EvmHost`'s own address (since `EvmHost` is the caller of the router).
4. `EvmHost.dispatch()` returns without ever moving that refunded dust ETH back to `_msgSender()` (the calling `HyperApp`/user).
5. Result: the excess ETH permanently accumulates in `EvmHost`'s balance; the original payer has no path to reclaim it — directly analogous to the locked `minOutput` funds in the `LSSVMRouter` report.
