Wrong Price Attached to `stSTXbtc`/`zstSTXbtc` Asset in Health/LTV Calculation - (File: `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
`get-asset-price` in `v0-1-data.clar`, the function that backs `get-user-position` (collateral/debt USD valuation, LTV, and health-factor/`is-liquidatable` computation), fetches the **STX** Pyth price for the BTC-denominated assets `stSTXbtc` and `zstSTXbtc` instead of the **BTC** price, mirroring the report's "price attached to the wrong asset" bug class.

### Finding Description
In `get-asset-price`, every other branch correctly maps an asset id to its corresponding Pyth feed constant (`PYTH-STX` for STX, `PYTH-BTC` for sBTC, etc.). For `stSTXbtc` and `zstSTXbtc`, the comment states "BTC price (liquid staked STX with BTC yield)" and "stSTXbtc price x liquidity index," but the code calls `get-pyth-price PYTH-STX` in both branches instead of `PYTH-BTC`: [1](#0-0) 

This same defect is duplicated in the local-testing mirror `protocol-data.clar`: [2](#0-1) 

`get-asset-price` feeds directly into `sum-collateral-usd`/`sum-debt-usd`, which compute `total-collateral-usd`/`total-debt-usd`, `current-ltv`, and `health-factor`/`is-liquidatable` returned by the read-only `get-user-position` function: [3](#0-2) 

Because BTC price is orders of magnitude higher than STX price, any position holding `stSTXbtc`/`zstSTXbtc` as collateral will have its collateral USD value drastically understated by this function, making `current-ltv` appear far higher (and `health-factor` far lower) than the true value, i.e., the position looks close to or past liquidation when it is not.

### Impact Explanation
I was unable to confirm within the available iterations whether the actual on-chain enforcement path (`v0-4-market.clar`'s `price-resolve`/`resolve-price-feed`/`resolve-callcode`, which is driven by a registered `{type, ident, callcode}` oracle tuple per asset rather than this hardcoded `get-asset-price` switch) shares the same mis-mapping for `stSTXbtc`/`zstSTXbtc`. If external liquidation keepers or monitoring tooling rely on `get-user-position`'s `is-liquidatable`/`health-factor` output to select or time liquidations, the understated collateral value could cause a position to be flagged for liquidation that is not actually undercollateralized under the true BTC price — a wrong health verdict. This would map to temporary freezing of funds (liquidator seizes/repays against a position that shouldn't be eligible) if that verdict is acted upon without independent re-verification against the market contract's own price feed.

### Likelihood Explanation
Any user supplying `stSTXbtc` or `zstSTXbtc` collateral and any consumer of `get-user-position` for liquidation/health decisions triggers the bug; no special conditions or attacker action are required beyond normal position usage. The bug is deterministic and always fires for these two asset ids.

### Recommendation
Change the `stSTXbtc` and `zstSTXbtc` branches in `get-asset-price` (both `mainnet/contracts/utility/v0-1-data.clar` and `local-testing/contracts/utility/protocol-data.clar`) to call `get-pyth-price PYTH-BTC` instead of `PYTH-STX`, consistent with the inline comments and the analogous `sBTC`/`zsBTC` branches. Separately, confirm whether `v0-4-market.clar`'s registered oracle `ident` for `stSTXbtc`/`zstSTXbtc` assets is correctly wired to the BTC feed, since that is the contract that actually enforces liquidation/borrow decisions.

### Proof of Concept
1. A user deposits `stSTXbtc` as collateral.
2. Call `get-user-position` for that account.
3. Observe `total-collateral-usd` computed via `sum-collateral-usd` → `get-asset-price(stSTXbtc)` → `get-pyth-price(PYTH-STX)` instead of `PYTH-BTC`, understating collateral value by the STX/BTC price ratio.
4. `current-ltv` is inflated and `is-liquidatable` may incorrectly report `true` for a healthy, BTC-collateralized position. [4](#0-3)
