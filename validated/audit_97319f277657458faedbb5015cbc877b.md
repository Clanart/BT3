### Title
Desktop disables Git's clone-time repository/hook safety check (`GIT_CLONE_PROTECTION_ACTIVE=false`), enabling hook execution from a malicious cloned repository - (File: app/src/lib/git/clone.ts)

### Summary
The `RoyaltyModule` report's underlying pattern is: the application trusts a value/behavior fully controlled by an untrusted, attacker-supplied source (an external policy contract) instead of enforcing its own protective invariant, letting the attacker override a safety mechanism designed to protect the victim. In GitHub Desktop, the `clone()` function explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone, which turns off Git's own built-in protection that guards against symlink/hook-planting attacks from a malicious repository being cloned, similar in spirit to disabling a safety check that Git itself added specifically to stop attacker-controlled repository content from executing code on the victim's machine.

### Finding Description
`clone()` in `app/src/lib/git/clone.ts` builds the environment for the `git clone` invocation: [1](#0-0) 

```
  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }
  ...
  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to prevent cloning a maliciously crafted repository (e.g., one containing symlinks or crafted `.git`/hooks paths, especially on case-insensitive filesystems) from being able to write into the local `.git/hooks` directory or otherwise escape the working tree during checkout — the exact class of bug fixed upstream by Git's clone-protection work (related to symlinked/hook-planting attacks in cloned repositories). By force-setting this to `'false'` for every single clone performed by Desktop, the application unconditionally disables that safety net for content that is, by definition, fully attacker-controlled (a remote repository the user is choosing to clone).

This directly matches the report's bug class: the value that determines whether a protective bound is enforced (`GIT_CLONE_PROTECTION_ACTIVE`) is set to permit the unsafe behavior, and the content that exploits it (the cloned repository's tree/hooks) is entirely supplied by an external, potentially malicious party — analogous to the External Royalty Policy contract dictating an unvalidated value that a critical operation (transfer / here, hook execution) trusts.

`app/src/lib/git/clone.ts` does add other protections — a path-traversal-guarding `isClonePathSensitive()` check and `sanitizeCloneName()` in `remote-parsing.ts` — but neither of these substitute for Git's own clone-content protection; they only guard the destination path derivation, not the content or hooks of the cloned repository itself: [2](#0-1) [3](#0-2) 

Clones are also performed with `--recursive`, meaning any submodules referenced by the malicious repository are fetched and initialized automatically as part of the same operation, widening the attack surface that the disabled protection would otherwise cover: [4](#0-3) 

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` disables the upstream Git safeguard against hook-planting/symlink attacks during clone, an attacker who controls a repository (the exact threat model named in the Valid Impact section — "attacker controls a cloned/fetched repository") could craft a repository that, when cloned via Desktop, plants or overwrites files under `.git/hooks` (or similar sensitive locations) through symlink tricks, resulting in arbitrary command execution on the victim's machine the next time a hook fires (e.g., on `post-checkout`, which Desktop and Git also invoke as part of routine operations). This is unprompted-by-the-user code execution triggered purely by cloning a repository, which is a normal, expected user action.

### Likelihood Explanation
I was unable to verify from the available code index the exact semantics Git upstream attaches to `GIT_CLONE_PROTECTION_ACTIVE` (I could not access Git's own source in this environment to confirm the precise CVE/behavior it guards), and I found no comment or test in the Desktop codebase explaining *why* this variable is forced to `'false'`. This is a meaningful gap: it's possible this is intentional and compensates for something else Desktop enforces elsewhere (e.g., it always runs its own `--recursive` submodule handling and separately gates `protocol.file.allow` per operation), which would reduce or eliminate the practical risk. Given the ambiguity, likelihood should be treated as uncertain rather than confirmed exploitable.

### Recommendation
Investigate why `GIT_CLONE_PROTECTION_ACTIVE` is explicitly forced to `'false'` in `app/src/lib/git/clone.ts` — check the commit history/PR that introduced this line — and confirm whether disabling it removes an active Git security control. If there's no strong compensating control, remove the override (or set it to `'true'`/leave it unset) so Git's own clone-time protection remains active for arbitrary, attacker-supplied repositories.

### Proof of Concept
I could not construct or verify a concrete PoC without access to Git's internal documentation/source for `GIT_CLONE_PROTECTION_ACTIVE` in this sandboxed environment. A complete PoC would require: (1) confirming the exact Git version bundled with Desktop and whether that version's clone protection is affected by this env var, and (2) crafting a repository with a symlinked path (e.g., a symlinked `.git` alias directory on a case-insensitive filesystem) that would normally be rejected by Git during `clone` but succeeds when `GIT_CLONE_PROTECTION_ACTIVE=false` is set, then observing hook execution after checkout completes.

**Caveat:** Given the lack of an inline explanation in the code and my inability to confirm upstream Git's exact behavior for this variable from the indexed codebase, this finding should be verified against Git's actual source/release notes for the bundled Git version before treating it as a confirmed vulnerability. I flag this explicitly per the instruction to state uncertainty rather than assert unconfirmed claims as fact.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
