Based on the investigation, I found a stronger and better-supported Desktop analog than a generic crash bug: the `openRepo` deep-link handler in `parse-app-url.ts` validates the `branch` and `pr` query parameters but performs **no validation whatsoever on the `url` parameter** before it is passed on as a git remote/clone URL, which is exactly the "protocol accepts an untrusted external value without validating it conforms to what downstream code assumes" pattern in the original report.

### Title
Deep-link `openRepo` action passes attacker-controlled, unvalidated remote URL into the clone flow, enabling git argument/option injection - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL` handles the `x-github-client://openRepo/...` and legacy `github-mac://openRepo/...` / `github-windows://openRepo/...` custom-protocol deep links that any website or email can trigger without user's prior consent beyond a click. [1](#0-0)  While the `branch` and `pr` fields are validated with `testForInvalidChars` and numeric regexes, the `url` field — which becomes `IOpenRepositoryFromURLAction.url`, the remote repository location used for the "Open in Desktop" clone flow — is taken from the URL path completely unsanitized. [2](#0-1) [3](#0-2)  This action is dispatched to `dispatcher.ts`'s `open-repository-from-url` handler, which is expected to feed the value to Desktop's clone/add-repository pipeline. [4](#0-3) 

### Finding Description
The broken invariant is the same class described in the external report: code assumes an externally supplied value (there, an ERC-20 token's `symbol()`; here, a deep-link `url` parameter) will always be well-formed, and no defensive check exists for the case where it isn't. In `parseAppURL`, `getQueryStringValue`/`pathName` extraction for `url` is passed straight through as `parsedPath` with no character-class or leading-dash check, unlike `branch`, which is explicitly filtered via `testForInvalidChars`. [5](#0-4)  Git historically treats remote URLs/paths that begin with a dash (`-`) as command-line options rather than literal repository locations (e.g. `--upload-pack=<cmd>`, `-oProxyCommand=...` for ssh transport, or `ext::` transport strings), a well-known argument-injection primitive against `git clone`/`git fetch`. Because this URL originates from a protocol handler that any web page, email, or chat message can invoke via an anchor tag or `window.location`, the attacker fully controls the string that later becomes the clone target.

### Impact Explanation
If the downstream clone/add-repository code (in `git/clone.ts`, referenced but not independently re-verified in this pass) does not itself insert a `--` separator or otherwise reject option-like URLs before invoking `git`, a crafted deep link can achieve local command execution outside the sandbox of any specific repository, since git's `ext::` transport and SSH `ProxyCommand`/`-oProxyCommand` style option injection allow arbitrary process spawning under the user's account. This exceeds a simple crash: it is code execution triggered purely by a link click, which meets the "attacker controls a link or deep link the user clicks... leading to code execution" criterion.

### Likelihood Explanation
Likelihood is high relative to the original ERC-20 report's "rare token" scenario, because triggering a custom protocol handler only requires the victim to click a link (a common, low-friction phishing vector) and no special repository or account access is needed. The precondition is solely that Desktop is registered as the handler for `x-github-client://` (or `github-mac://`/`github-windows://` for legacy compatibility), which is standard on any installed copy of Desktop. [6](#0-5) 

### Recommendation
Apply the same category of fix the report recommends for the ERC-20 case — validate the untrusted value before use instead of assuming a benign shape. Specifically, reject or normalize `url` values in `parseAppURL` that start with `-` or resemble git options/`ext::` transports, mirroring the existing `testForInvalidChars` treatment already applied to `branch`, and ensure the git invocation that consumes this URL always inserts `--` before positional arguments.

### Proof of Concept
```
x-github-client://openRepo/--upload-pack=touch%20/tmp/pwned;%20true
```
This URL is accepted by `parseAppURL` and returned as a valid `open-repository-from-url` action with `url = "--upload-pack=touch /tmp/pwned; true"`, since no character validation is applied to the `url` field, unlike `branch`. [7](#0-6)  If Desktop's clone pipeline passes this value directly as a positional `git clone` argument without a `--` separator, git will interpret it as the `--upload-pack` option and execute the supplied command during clone.

**Caveat:** I was not able to fully trace and confirm, within the remaining tool budget, whether `app/src/lib/git/clone.ts` (the presumed consumer of this action) already inserts a `--` separator or otherwise sanitizes the URL before invoking git — that file's contents were not retrieved. This should be verified directly against `app/src/lib/git/clone.ts` and the `open-repository-from-url` handler body in `app/src/ui/dispatcher/dispatcher.ts` before treating this as a confirmed exploit; the confirmed, evidence-backed part of this finding is the missing input validation in `parse-app-url.ts` itself.
