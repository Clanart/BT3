Audit Report

## Title
Stake-delegation cache accumulator (`delegated_stakes`) can panic or corrupt on mid-epoch feature-gate flip because `Stakes::upsert_stake_delegation` recomputes the "old" effective stake with the *current* math flag instead of the flag in effect when the stake was originally cached - (File: runtime/src/stakes.rs)

## Summary
`Stakes::upsert_stake_delegation` recomputes both the "old" and "new" effective stake for a delegation via `delegation_effective_stake()`, which branches between legacy `Delegation::stake()` and `Delegation::stake_v2()` based on the externally-supplied `use_fixed_point_stake_math` flag and `new_rate_activation_epoch`. Because these parameters are threaded in per-call from `Bank`'s current feature set rather than pinned to the delegation record at insertion time, a feature-gate activation occurring between two updates to the same stake pubkey within a single epoch causes the "old" stake to be recomputed under a different formula than the one used to add it, producing either a panic in `sub_delegated_stake`'s `expect()` or a silently corrupted `delegated_stakes`/`vote_accounts` cache.

## Finding Description
`Stakes::upsert_stake_delegation` at `runtime/src/stakes.rs` (L620-658) computes `stake` for the incoming `StakeAccount` via `delegation_effective_stake(delegation, self.epoch, &self.stake_history, new_rate_activation_epoch, use_fixed_point_stake_math)`. When the stake pubkey already exists in `self.stake_delegations`, the code recomputes `old_stake` for the *previously stored* `StakeAccount`'s `Delegation` using the *same call's* `new_rate_activation_epoch`/`use_fixed_point_stake_math` parameters, not the parameters that were in effect when that old value was originally inserted. `delegation_effective_stake` in `runtime/src/stake_delegation.rs` (L9-23) dispatches to either `Delegation::stake()` (legacy floating-point math) or `Delegation::stake_v2()` (fixed-point math) based on the boolean flag — the two are expected to diverge by design (that is the reason the feature and the dual code path exist). `sub_delegated_stake` at (L562-576) then subtracts `old_stake` from the accumulator with `.expect("subtraction value exceeds delegated stake")`, which will panic if the recomputed value disagrees with what was actually added previously, or otherwise leave a residual/incorrect balance if it under-subtracts.

`check_and_store` (L87-164) shows that `new_rate_activation_epoch` and `use_fixed_point_stake_math` are passed in per invocation from `Bank`, i.e., derived from `bank.feature_set` at call time — not stored per-delegation. Feature activation in Agave occurs at the specific slot where sufficient stake-weighted votes accumulate, which is not constrained to epoch boundaries; therefore two banks that are still within the same epoch (`self.epoch` unchanged) can legitimately have different active feature sets, and thus different `use_fixed_point_stake_math` values, across two `check_and_store` calls for the same stake pubkey. The intra-epoch incremental path in `upsert_stake_delegation` has no self-correcting mechanism analogous to the full-epoch recomputation performed by `calculate_activated_stake`/`activate_epoch` at epoch boundaries, so this drift is not healed until the next epoch.

## Impact Explanation
Because feature-set activation is a deterministic, consensus-driven event, every validator processing the same block/slot sequence on the same fork observes the identical flag flip and therefore hits the identical panic or identical accumulator corruption. A panic in `sub_delegated_stake`'s `expect()` during block replay/production would deterministically halt all validators processing that transaction, constituting a network-wide consensus halt in the `runtime`/`accounts` stake-caching path. A non-panicking mismatch (under- or over-subtraction) corrupts `delegated_stakes`/`vote_accounts` stake totals for the affected voter for the remainder of the epoch, which are read by leader-schedule-adjacent and reward-point calculations, causing false accounting.

## Likelihood Explanation
No malicious actor or privileged control is required — an unprivileged user submitting an ordinary stake-account-modifying transaction (delegate, merge, split, deactivate) on the same stake pubkey during the exact slot window when a stake-math-related feature activates mid-epoch triggers the divergence. Feature activations are consensus events that are infrequent but not tied to epoch boundaries, making this a genuine, if narrow, timing window rather than an always-reachable bug. The bug is a structural invariant gap: the epoch-boundary path fully recomputes `delegated_stakes` from scratch specifically to avoid this class of drift, while the intra-epoch incremental `upsert_stake_delegation` path assumes—without enforcement—that recomputing the "old" value under new parameters reproduces the value that was actually cached under the old parameters.

## Recommendation
Do not recompute the "old" effective stake in `upsert_stake_delegation` using the current call's `new_rate_activation_epoch`/`use_fixed_point_stake_math`. Instead, cache the effective stake value alongside each `StakeAccount` entry in `stake_delegations` at insertion time, and use that stored value (not a fresh recomputation) when removing/replacing the entry in `sub_delegated_stake`/`vote_accounts.sub_stake`, so that add and subtract are always symmetric irrespective of feature-gate transitions occurring between the two calls.

## Proof of Concept
1. Bank B1 (epoch E, slot N), `use_fixed_point_stake_math = false`: stake account S delegates to voter V; `upsert_stake_delegation` computes `stake1 = delegation.stake(...)` and adds it via `add_delegated_stake`/`vote_accounts.add_stake` (runtime/src/stakes.rs L636-639).
2. Between slot N and N+1 on the same fork, the feature governing `use_fixed_point_stake_math` activates (a slot-level, not epoch-level, event).
3. Bank B2 (still epoch E, slot N+1), `use_fixed_point_stake_math = true`: a legitimate transaction modifies stake account S again; `check_and_store` invokes `upsert_stake_delegation` with the new flag value (runtime/src/stakes.rs L146-153).
4. `old_stake = delegation.stake_v2(...)` is computed for the same underlying old `Delegation`/epoch/history that produced `stake1` under legacy `stake()`; if `stake_v2` and `stake` disagree for this delegation (expected, since that is the feature's purpose), `old_stake != stake1`.
5. `sub_delegated_stake(&V, old_stake)` (runtime/src/stakes.rs L562-576) either panics via `.expect("subtraction value exceeds delegated stake")` if `old_stake > delegated_stakes[V]`, or silently leaves an incorrect residual if `old_stake < stake1`, corrupting the cached total for voter V for the rest of epoch E. A unit test reproducing this can construct a `Stakes` instance, call `upsert_stake_delegation` once with `use_fixed_point_stake_math=false`, then call it again for the same pubkey with `use_fixed_point_stake_math=true` and a `Delegation`/`StakeHistory` combination chosen such that `stake()` and `stake_v2()` diverge, asserting the panic or the resulting `delegated_stakes` mismatch.
