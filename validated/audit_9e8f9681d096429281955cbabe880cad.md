### Title
Unvalidated `offset`/`script_pubkey` binding in `ReceivedOutput::read` lets attacker-supplied outputs be reported as received yet be unspendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The MariaDB SST bug is an interpolation-without-validation flaw: parameters supplied by an untrusted joiner are used verbatim by the donor. The closest reachable analog in Serai's in-scope code is `ReceivedOutput::read`, which deserializes an attacker-controlled `(offset, TxOut, outpoint)` triple and never checks that `output.script_pubkey` actually equals the P2TR script derived from `key + offset * G`. Because the honest production path (`Scanner::scan_transaction`) always pairs a script with the offset that generated it, the invariant "offset ↔ script_pubkey" is implicit and is silently violated for any `ReceivedOutput` obtained from untrusted bytes.

### Finding Description
`Scanner::register_offset` inserts `p2tr_script_buf(self.key + GENERATOR * offset)` keyed by `ScriptBuf`, so a scanned output's `script_pubkey` is mathematically bound to the returned `offset` [1](#0-0) . `scan_transaction` therefore produces consistent `(offset, output)` pairs [2](#0-1) .

`ReceivedOutput::read`, however, accepts the three fields independently: it reads a scalar via `Secp256k1::read_F`, then a `TxOut` and `OutPoint` via consensus decoding, with no access to the scanner key and no consistency check between `offset` and `output.script_pubkey` [3](#0-2) . The struct has no back-reference to the key it belongs to [4](#0-3) .

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (a listed in-scope sink) supplies a real, confirmed `TxOut`/`outpoint` paying to a P2TR script the wallet does not control, paired with an arbitrary `offset`. When the wallet later spends this `ReceivedOutput`, the spend path re-keys the threshold signature by `offset` (the same mechanism `tweak_keys`/`register_offset` establish), producing a signature under `key + offset*G` that does not match the output's script_pubkey. The result is funds reported as received that are not spendable: the wallet counts the value via `ReceivedOutput::value()` while the input can never satisfy the script's key-path spend. For an attacker-chosen `offset`, the offset may also introduce a spendable script path under an attacker-known tweaked key (the hazard the `register_offset` docs warn about), letting the attacker claim the funds outright.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary (relayed scan results, message-queue delivery, DB entries populated from external data). It requires only delivering crafted bytes to `read`; no threshold collusion, no malicious validator, no key compromise. Impact is bounded to mis-accounted/unspendable (or attacker-claimable) outputs rather than secret-key recovery, so it rates Medium rather than High.

### Recommendation
Bind the offset to the key inside `ReceivedOutput` or at its deserialization boundary: either store the scanner key (or a derived key commitment) on `ReceivedOutput` and verify `output.script_pubkey == p2tr_script_buf(key + offset*G)` in `read`, or require callers to re-validate each received output against a `Scanner`'s registered scripts before treating it as spendable. Alternatively, recompute the script from `(key, offset)` at spend time rather than trusting the serialized `TxOut`.

### Proof of Concept
1. Run `Scanner::new(victim_key)` and `register_offset(o)` to learn the legitimate script set.
2. Craft bytes: `offset = o` followed by a consensus-encoded `TxOut` whose `script_pubkey` is `ScriptBuf::new_p2tr_tweaked` of an attacker-controlled x-only key, plus any valid confirmed `OutPoint`.
3. Feed to `ReceivedOutput::read` — it succeeds, and `value()` is counted as received.
4. At spend time, the wallet signs as `key + o*G`; the sighash-valid signature does not correspond to the attacker-controlled output key, so the input fails script validation — the funds were reported received but are unspendable (or spendable only by the attacker).

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
