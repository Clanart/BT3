## Title
Reentrancy in Tron `IntentGatewayV2.withdraw` allows draining escrowed native-token funds beyond the escrowed amount - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements escrow release in `withdraw()` with a checks-effects-interactions violation: for native-token (`token == address(0)`) legs it performs the low-level value `.call` to the beneficiary **before** decrementing `_orders[commitment][token]`. This is the Tron-native analog of the EIP-721 report's core defect — a state-mutating public/external code path that fails to enforce its accounting invariant before exposing state/funds, letting an attacker exploit the temporarily stale value.

### Finding Description
`withdraw()` is reached from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` incoming ISMP messages) and from `onGetResponse()`, and ultimately releases escrow that was deposited during `placeOrder`: [1](#0-0) 

The per-token loop reads `_orders[body.commitment][token]`, checks it is non-zero, then for the native-asset branch performs `beneficiary.call{value: amount}("")` **before** the line `_orders[body.commitment][token] -= amount;` executes. If `beneficiary` is a contract (the `beneficiary` field is attacker-controlled — it comes straight from `body.beneficiary`, which is decoded from the cross-chain `WithdrawalRequest` and, for `RefundEscrow`/`RedeemEscrow`, equals `order.user` or the filler set by the order creator), the callback can re-enter `withdraw` (via a second `onAccept`/`onGetResponse` call authenticated the same way, or via any other reentrant path in the contract) while `_orders[commitment][token]` still holds its pre-decrement value, and drain the same escrow slot multiple times before the balance is ever zeroed.

Compare this to the mainline EVM implementation of the same logic, `_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`, which correctly decrements storage before the external call: [2](#0-1) 

The Tron contract diverges from this safe pattern and reintroduces the classic reorder bug. This is structurally the same class of issue as the report's `tokenURI` — a public-facing function that fails to enforce its core invariant (existence/ownership check, here "sufficient un-spent escrow") at the moment external state becomes observable/exploitable, instead performing the unsafe action first.

### Impact Explanation
This directly enables **theft of escrowed bridge funds** — a beneficiary contract can re-enter `withdraw` before its escrow balance is decremented and receive the native-asset payout multiple times for a single fill/refund/redeem, draining the gateway's native-token reserves beyond what was ever escrowed for that order. This matches the bounty's core categories: stealing/loss of funds, transaction manipulation, and effectively a double-settlement of the same escrow entry.

### Likelihood Explanation
The withdraw path is reachable by any unprivileged actor who can get named as `beneficiary` on a legitimate order (i.e., any user placing and then filling/cancelling their own order with a `beneficiary` they control that is a smart-contract wallet). No malicious relayer, prover, or admin is required — the attacker only needs to control the destination contract address used as `beneficiary`/`order.user`, which is entirely within a normal user's control when placing or cancelling their own order. The relevant guard functions (`onAccept`, `onGetResponse`) authenticate the *message* (via `onlyHost`/`authenticate`) but do nothing to prevent reentrancy into `withdraw` itself, and `withdraw` has no `nonReentrant` modifier.

### Recommendation
Apply checks-effects-interactions consistently in the Tron `withdraw()`: decrement `_orders[body.commitment][token]` (and delete the transaction-fee entry) **before** performing any native-token `.call` or ERC20 `transfer`/`call`, mirroring the ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, add a reentrancy guard (e.g., `nonReentrant`) to `onAccept` and `onGetResponse`, or to `withdraw` itself, as defense in depth.

### Proof of Concept
1. User places an order on the Tron `IntentGatewayV2` with `output.beneficiary` (or, for a same-chain cancel, `order.user`) set to a malicious contract `Attacker` that implements a fallback/`receive()` function.
2. The order reaches a state where `withdraw()` is invoked with `isRefund = true` (e.g., via `RefundEscrow` incoming message or `onGetResponse`) for a native-asset (`address(0)`) input, with escrow balance `X` recorded in `_orders[commitment][address(0)]`.
3. Inside `withdraw()`, execution reaches: [3](#0-2) 
4. `beneficiary.call{value: amount}("")` transfers `amount` to `Attacker` and triggers `Attacker.receive()` **before** `_orders[body.commitment][token] -= amount` executes.
5. `Attacker.receive()` re-enters through the same authenticated entry point (e.g., triggers another `onAccept`/`onGetResponse` call for the same commitment, or any other function that reads/writes `_orders[commitment][address(0)]`), and since `_orders[commitment][address(0)]` is still `X` (not yet decremented), the `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` check passes again and another `amount` is paid out.
6. Repeating this re-entrant call drains native-token reserves for that commitment beyond the single escrowed amount `X`, before the first call's decrement ever lands.
