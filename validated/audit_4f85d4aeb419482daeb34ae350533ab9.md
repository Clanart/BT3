This confirms the mechanism: `validate_state_machine` calls `host.consensus_client_id(proof_height.id.consensus_state_id)` and then `consensus_client.state_machine(proof_height.id.state_id)`, which for the GRANDPA client requires the state machine to still be present in `SupportedStateMachines` (removed by `remove_state_machines`). Any pending request/response/timeout that must be proven at a height on a state machine removed from that whitelist can never be verified again, exactly mirroring the original "elevation group removed from reserve → stale obligation" pattern.

### Title
Removing a state machine from the GRANDPA consensus-client whitelist permanently strands funds and messages for already-dispatched requests - ([File: modules/ismp/clients/grandpa/src/lib.rs], [File: modules/ismp/core/src/handlers.rs])

### Summary
`ismp-grandpa`'s `remove_state_machines` deletes an entry from `SupportedStateMachines` [1](#0-0) , which the consensus client consults both to accept new consensus proofs and to resolve `state_machine()` lookups used by `validate_state_machine` for every request/response/timeout proof [2](#0-1) . Any request that was dispatched to (or received from) that state machine *before* removal, but whose completion (response, or timeout) requires a state commitment at a height not yet finalized at removal time, becomes permanently unprovable: no new consensus proof can update `SupportedStateMachines`-less client, so no new `state_machine_commitment` height is ever produced for it, and neither a membership proof (response) nor a non-membership proof (timeout) can ever be submitted at the required height. This exactly mirrors the reported pattern: a value (elevation group / state-machine reference) stored on an already-created object becomes orphaned when the admin shrinks the corresponding whitelist, permanently freezing the object.

### Finding Description
The GRANDPA consensus client stores per-state-machine slot durations in `SupportedStateMachines` [3](#0-2) . `verify_consensus` for standalone chains fetches this value and errors with `SlotDurationNotSet` if it is missing [4](#0-3) , and for relay/para headers it silently filters out any para id no longer present in the map [5](#0-4) . In both cases, once `remove_state_machines` is called for a given `StateMachine`, the client can never again produce a `StateCommitmentHeight` for that chain.

Every request, response, and timeout message handler calls `validate_state_machine`, which resolves the `ConsensusClient` for the proof's `consensus_state_id` and then calls `consensus_client.state_machine(proof_height.id.state_id)` [2](#0-1) . For requests/responses this determines whether `state_machine_commitment(proof.height)` can even be looked up; if the height was never (and can now never be) committed, `host.state_machine_commitment` fails, and processing of the pending request/response can never succeed. The corresponding timeout path (`modules/ismp/core/src/handlers/timeout.rs`) needs the *same* kind of future non-membership proof at a state height that will now never be produced, so the request can also never be timed out to trigger the fee refund path in `on_request_timeout`.

Unlike the lending example, this is not merely a "management call breaks it" curiosity: relayer fees and dispatched request/response fee metadata (see `fund_message` / `FeeMetadata` in `modules/pallets/ismp/src/lib.rs`) remain escrowed in the pallet/host with no code path to reclaim them once the destination/source state machine is de-whitelisted mid-flight, because the only reclaim paths (successful delivery or proven timeout) both require a state commitment the whitelist removal makes permanently unattainable.

### Impact Explanation
Users who dispatched a request (paying relayer fees, escrowing tokens for bridged transfers, etc.) to a state machine that the `RootOrigin` later removes from the GRANDPA whitelist lose access to both the successful-delivery and the timeout-refund paths for that specific in-flight message. This is a direct loss/permanent lock of escrowed relayer fees and any bridged value tied to that request/response, matching the bounty's "loss of funds" impact category, and is a straightforward operational consequence of a supported administrative action rather than requiring any malicious or compromised party.

### Likelihood Explanation
`remove_state_machines` is a normal, documented maintenance operation ("They can always be re-added") [6](#0-5) , intended for legitimate reasons (deprecating a solochain, rotating identifiers, etc.), so this can be triggered without any adversarial intent — any state machine that has in-flight requests at removal time is affected. The likelihood of triggering the bug is high whenever routine whitelist maintenance coincides with in-flight cross-chain messages, which is an expected steady-state condition on a live bridge.

### Recommendation
Mirror the referenced fix pattern: instead of deleting whitelist entries outright, retain the slot duration (or a "disabled" flag) for state machines that still have unresolved (non-finalized/non-timed-out) requests, responses, or pending consensus updates. `remove_state_machines` should only fully purge an entry once it is confirmed there are no requests/responses/receipts referencing that state machine that are still awaiting a proof at a height beyond the last-known committed height, or it should keep accepting consensus updates for previously-whitelisted-but-now-"disabled" chains solely to allow existing in-flight messages to be finalized or timed out, while blocking new outbound dispatches to them.

### Proof of Concept
1. Chain `A` (a solochain using GRANDPA) is whitelisted via `add_state_machines` and has an active consensus client with state commitments up to height `H`.
2. A user dispatches a `PostRequest` to/through chain `A`, paying a relayer fee that is escrowed via `fund_message`/`FeeMetadata`. The request's timeout is set for a future timestamp corresponding to a height `> H`.
3. Before the relayer can either deliver a response or the timeout window is proven, `RootOrigin` calls `remove_state_machines([A])` [1](#0-0)  — a routine, permitted administrative action (e.g., migrating chain A to a new consensus client id).
4. No further consensus proofs for `A` can be accepted (`SlotDurationNotSet`/filtered out in `consensus.rs`), so no new `StateCommitmentHeight` beyond `H` is ever produced for `A`.
5. The relayer cannot submit a response (no membership proof at a future height exists) nor a timeout (no non-membership proof at a future height beyond `H` exists), so `validate_state_machine` can never succeed for this pending message.
6. The escrowed relayer fee/bridged value tied to that request is now permanently unrecoverable — neither the success path nor the timeout-refund path can ever execute for it.
