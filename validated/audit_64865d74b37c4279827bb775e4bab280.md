### Title
Copilot conflict-resolution validation skips hunk-count/context checks for `action`-based resolutions, letting model output silently discard real merge conflict content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's AI-assisted conflict resolution (`resolveChunk` in `app/src/lib/stores/copilot-store.ts`) sends per-file conflict data (including hunks, commit messages, and PR titles/descriptions gathered from the repository/remote) to a Copilot model and trusts its structured JSON response back. `validateResolutionPaths` in `app/src/lib/copilot-conflict-resolution.ts` is supposed to guarantee the model's response matches the real conflict shape (same paths, same hunk counts) before the resolution is applied, but it unconditionally skips the hunk-count check whenever the model tags a resolution with an `action` field: [1](#0-0) 

`reassembleResolutions` mirrors this gap: for any raw resolution carrying `action`, it passes it straight through as a `deleteConflictAction` without ever checking whether the corresponding `IFileConflictContext` entry actually represents a delete-vs-modify conflict (there is no check like `ctx?.deleteConflict !== undefined`): [2](#0-1) 

This is structurally the same flaw as the reported bug: two related fields (`genesisCircSupply`/`collateral` vs. `msg.value` in the Solidity report; here, "this is a text conflict with N real hunks" vs. "this file is a delete-vs-modify conflict resolved by keep/delete") are supposed to be checked jointly, but the validator only checks one branch and silently accepts the other without cross-referencing it against the ground truth (`expectedFiles`).

### Finding Description
The system prompt explicitly tells the model to use "recent commit messages and/or PR title/description for intent" when deciding conflict resolutions, including whether to emit an `action: "keep"|"delete"` for delete-vs-modify conflicts: [3](#0-2) [4](#0-3) 

This commit-message/PR content originates from a repository or fork that is not necessarily trusted — a contributor who opens a PR, or a branch fetched from any remote, fully controls their own commit messages and PR descriptions. Because the model is steered by this attacker-influenceable text, it can be induced (via prompt-injection-style commit messages) to emit `action: "delete"` or `action: "keep"` for a file that is **not** actually a delete-vs-modify conflict — i.e., a normal text conflict with real, independent hunks from both branches.

When this happens:
1. `validateResolutionPaths` sees `resolution.action !== undefined` and `continue`s, never checking that `resolution.hunks.length` (0) matches the real `expectedHunkCounts` for that file (which would be > 0 for a genuine multi-hunk text conflict). [1](#0-0) 
2. `reassembleResolutions` never reassembles the real per-hunk content for that file at all — it just returns `resolvedContent: ''` with a `deleteConflictAction`, discarding the actual merged content it should have produced by splicing hunks into `ctx.rawContent`. [5](#0-4) 
3. This `IFileResolution` is applied downstream as a `ManualConflictResolution` (keep-ours/keep-theirs equivalent), silently dropping whichever side's changes weren't chosen — including hunks the user would have wanted merged — without ever going through `reassembleResolvedFile`'s line-by-line preservation logic. References to how `deleteConflictAction` is consumed downstream exist in `app/src/lib/stores/app-store.ts` and `app/src/ui/dispatcher/dispatcher.ts`, though the exact write/commit path was not fully traced in this session.

The root cause: neither validation function checks that an `action`-tagged resolution actually corresponds to an `expectedFiles` entry that has a `deleteConflict` context (`IFileConflictContext.deleteConflict`, defined in `app/src/lib/copilot-conflict-context.ts`). The two facts — "the model says this is a delete-vs-modify file" and "this file is actually flagged as a delete-vs-modify conflict by Desktop's own git status parsing" — are never cross-checked, exactly mirroring the missing sum/consistency check in the original report.

### Impact Explanation
If exploited, the outcome is silent corruption of what the user commits: a genuine multi-way text merge conflict can be resolved by simply keeping one side and dropping the other's hunks entirely, with no error surfaced (the validator explicitly treats this as a valid, non-retryable path). The user would see a conflict "resolved" by Copilot and, absent manual diff review, could commit/push a file that silently lost a real code change from one branch — a direct integrity violation of "what the user commits or pushes" driven by content controlled by whoever authored the conflicting branch/PR.

### Likelihood Explanation
Requires: (a) the user has AI conflict resolution enabled and invokes it on a conflict where at least one side originates from an untrusted branch/fork/PR, and (b) the model can be steered by commit-message/PR-description content to emit an `action` field for a non-delete-vs-modify file. Model steering via commit-message content is a realistic prompt-injection vector but not deterministic — it depends on model compliance. This keeps likelihood moderate rather than trivial, but the missing invariant check itself is a certain, always-present gap in the validator, not a corner case.

### Recommendation
In `validateResolutionPaths`, before skipping the hunk-count check for `action`-based resolutions, require that the corresponding `expectedFiles` entry actually has a `deleteConflict` context:
```ts
if (resolution.action !== undefined) {
  const expected = expectedFiles.find(f => f.path === resolution.path)
  if (expected?.deleteConflict === undefined) {
    throw new CopilotValidationError(
      `Copilot returned a delete/keep action for "${resolution.path}" but it is not a delete-vs-modify conflict`
    )
  }
  continue
}
```
Apply the same cross-check in `reassembleResolutions` before accepting `raw.action`, so a resolution can only bypass hunk reassembly when Desktop's own git status determined the file genuinely has a delete-vs-modify conflict.

### Proof of Concept
Conceptual PoC (extends the existing test suite pattern in `app/test/unit/copilot-conflict-resolution-test.ts`):
```ts
// A real text conflict with 2 hunks from independent branch changes
const resolutions = [{
  path: 'shared-file.ts',
  hunks: [],
  reasoning: 'Deletion looks intentional based on commit message',
  action: 'delete' as const,   // model was steered by attacker-authored commit message
}]

const expectedFiles = [{
  path: 'shared-file.ts',
  hunks: [ /* 2 real hunks with independent changes from both branches */ ],
  // NOTE: no `deleteConflict` field — this is NOT actually a delete-vs-modify conflict
}]

// Current behavior: does NOT throw, silently accepts the action and skips hunk validation
assert.doesNotThrow(() => validateResolutionPaths(resolutions, expectedFiles))

// reassembleResolutions then discards both sides' real hunk content entirely
const result = reassembleResolutions(resolutions, expectedFiles)
assert.equal(result[0].resolvedContent, '')          // real merged content is lost
assert.equal(result[0].deleteConflictAction, 'delete') // applied as a delete, not a merge
``` [1](#0-0) [5](#0-4)
