## Title
Missing zero-value check on `order.output.assets[i].amount` in `IntentGatewayV2.placeOrder` permanently locks escrowed input tokens on same-chain fills — (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`placeOrder` validates that every escrowed *input* amount is non-zero [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) , but never validates that the corresponding `order.output.assets[i].amount` (the amount required from the solver for that same leg) is non-zero. This is the same bug class as the external report: a zero-valued parameter that is used to initialize/drive downstream accounting without a guard.

### Finding Description
In `_fillSameChain`, each leg's `totalRequired` comes straight from `order.output.assets[i].amount` with no lower bound: [5](#0-4) 

If `totalRequired == 0`, then `remaining` is `0`, and the loop takes the `continue` branch **before** `escrowedInputs[i]` is ever assigned [6](#0-5) , leaving that slot at its Solidity-default `TokenInfo({token: bytes32(0), amount: 0})` instead of the actual escrowed input token/amount for that leg. Because the zero-required leg's `solverAmount` requirement is vacuously satisfied, `isFullyFilled` is not set to `false` for it, so the order can still be marked fully filled and permanently sealed via `_filled[commitment] = msg.sender` [7](#0-6) [8](#0-7) .

The resulting `WithdrawalRequest.tokens` array then contains a bogus `{token: address(0), amount: 0}` entry instead of the real (non-zero-amount) input token for that leg. The withdrawal/escrow-release routine gates release strictly on the corresponding `_orders[commitment][token]` bookkeeping map being non-zero (confirmed in the equivalent tron implementation of the shared withdraw logic) [9](#0-8) . Since the real escrowed token for that leg is never looked up or transferred, its balance in `_orders[commitment][realToken]` is never decremented and the tokens are never sent to the solver, the user, or anywhere else — they become permanently stranded in the contract, and because `_filled[commitment]` is now set, the order can no longer be filled again nor cancelled through `_cancelSameChain`, which requires `_filled[commitment] == address(0)`.

### Impact Explanation
This is a direct, permanent loss-of-funds bug: real, previously-escrowed ERC-20/native tokens (validated as non-zero at deposit time) become unrecoverable through the normal order lifecycle once a paired output leg has amount `0`. It requires no malicious relayer, prover, or governance actor — only an ordinary `placeOrder` call (unprivileged, permissionless) followed by an ordinary `fillOrder` call by any solver. This matches the bounty's "loss of funds" and "logic attacks" categories.

### Likelihood Explanation
`placeOrder` is fully permissionless and takes an arbitrary `Order` struct; nothing besides the (non-zero) input-amount checks constrains `order.output.assets[i].amount`. A user (or a UI/SDK bug, or a multi-leg order builder that zeroes one leg intentionally to represent an "optional" output) can trivially construct such an order. Any subsequent solver interaction that reaches full-fill status for the other legs will trigger the permanent lock for the zero-output leg's paired input — this does not require solver malice, and can be triggered accidentally.

### Recommendation
Add a zero-amount check for `order.output.assets[i].amount` in `placeOrder` (mirroring the existing `order.inputs[i].amount == 0` guard), or reject orders with any output leg amount of `0` explicitly, and additionally, in `_fillSameChain`, avoid relying on default-initialized `escrowedInputs[i]`/`outputFills[i]` entries when a leg is skipped — always populate them with the leg's actual input token so escrow bookkeeping stays consistent even if a zero-required leg is later allowed.

### Proof of Concept
1. User calls `placeOrder` with two legs:
   - Leg 0: `inputs[0] = {tokenA, 1}` (minimal, e.g. 1 wei), `output.assets[0] = {tokenB, 1}` (trivial requirement).
   - Leg 1: `inputs[1] = {USDC, 1000e6}` (real value, passes the non-zero input check), `output.assets[1] = {tokenC, 0}` (no check blocks this).
2. `placeOrder` escrows `1000e6` USDC into `_orders[commitment][USDC]`.
3. A solver calls `fillOrder` supplying `solverOutputs[0]=1`, `solverOutputs[1]=0` (or any amount — leg 1's `remaining` is already `0`).
4. In `_fillSameChain`, leg 1 hits `remaining == 0` and `continue`s without ever writing `escrowedInputs[1]`; `isFullyFilled` stays `true`.
5. `_withdraw` is called with `escrowedInputs[1] = {address(0), 0}`, so the actual `1000e6` USDC entry in `_orders[commitment][USDC]` is never referenced, never transferred, and never zeroed.
6. `_filled[commitment]` is set to the solver, order is now permanently "filled" — `_cancelSameChain` cannot run — and the `1000e6` USDC remains stuck in the `IntentGatewayV2` contract indefinitely.

Note: I was not able to open the full `IntentsBase.sol::_withdraw` implementation in this session (only the functionally-equivalent tron variant), so exact revert/no-op behavior for the bogus zero entry in the mainline EVM contract should be confirmed directly against that file before remediation.
