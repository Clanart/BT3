### Title
Missing zero-address validation on cross-chain `beneficiary` in `IntentGatewayV2.withdraw()` permanently burns escrowed order funds and collides with the "unfilled" sentinel - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirrored in `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` derives the payout address directly from a cross-chain-delivered `WithdrawalRequest.beneficiary` field with no `require(beneficiary != address(0))` guard, then sends escrowed tokens/ETH to it with a raw `.call`. [1](#0-0)  This is the same bug class as the InstaRegistry `setAddress` report: a missing zero-address check on a fund/role-moving parameter that other parts of this same codebase explicitly guard against (`EvmHost.updateHostParamsInternal`, `SimplexPaymaster._setParams`, `HyperFungibleTokenImpl` constructor). [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`withdraw()` computes `beneficiary = address(uint160(uint256(body.beneficiary)))` and immediately marks `_filled[body.commitment] = beneficiary` before transferring funds — with no check that `beneficiary != address(0)`: [1](#0-0) 

Critically, `address(0)` is the same sentinel value the contract uses elsewhere to mean "not yet filled": [5](#0-4) 

If `body.beneficiary` ever decodes to `bytes32(0)` — whether from a missing/blank input in a client encoding a `WithdrawalRequest`, or from an order whose `output.beneficiary` was never set — two things happen simultaneously:
1. Escrowed input tokens and transaction fees are sent to `address(0)` via a low-level `.call`, which succeeds silently and burns the funds permanently. [6](#0-5) 
2. `_filled[commitment]` is set to `address(0)`, which is indistinguishable from the "never filled" default value used by the `Filled()` guard in `cancelOrder`. [7](#0-6) 

The second effect means an order that has already been redeemed/refunded with a zero beneficiary can pass the `Filled()` check again and re-enter `cancelOrder`'s branches, dispatching a duplicate `RefundEscrow`/storage-query message. Downstream, the per-token `_orders[commitment][token] == 0` guard in `withdraw()` prevents an actual second token payout [8](#0-7) , so the confirmed, unambiguous impact is limited to permanent fund loss (burn to `address(0)`) rather than a proven double-payout to an attacker-controlled address.

### Impact Explanation
Confirmed impact: permanent, irrecoverable loss of escrowed order funds (input tokens, native ETH, and transaction fees) whenever a `WithdrawalRequest.beneficiary` resolves to zero, with no revert to catch it. This matches the "loss of funds" category in the bounty's impact gate. The additional `_filled`/sentinel collision is a real state-integrity defect but, based on the code I reviewed, is bounded by the separate `_orders[...] == 0` check, so I cannot confirm it independently produces a double-payout to a third party.

### Likelihood Explanation
I could not fully confirm the attacker-reachability of a *victim-funds* loss scenario because I ran out of tool calls before reading the `fill()`/`SelectOptions` solver-selection code in `evm/src/apps/IntentGatewayV2.sol`, which determines whether `output.beneficiary` (and thus the eventual `WithdrawalRequest.beneficiary` on redemption) is attacker-influenceable for someone else's order, or is fixed at order-placement time by the order owner. Without that, I can state with confidence only the self-referential/owner-triggered case (an order's own beneficiary field is left as zero when placed or when a `RedeemEscrow`/`RefundEscrow` message is constructed), which is a direct structural analog of the original report but does not clearly meet the "unprivileged attacker steals another party's funds" bar required by the impact gate.

### Recommendation
Add an explicit `require(beneficiary != address(0))` (and equivalently reject `body.beneficiary == bytes32(0)`) at the top of `withdraw()` before any state is mutated or funds transferred, and consider using a dedicated boolean/flag for the "filled" state instead of overloading `address(0)` as both "beneficiary" and "unfilled" sentinel in `_filled`.

### Proof of Concept
Not fully constructible from the code reviewed. The confirmed reachable PoC is: submit an `onAccept`/`onGetResponse` flow where the ABI-encoded `WithdrawalRequest.beneficiary` is `bytes32(0)` (e.g., via a malformed or default-initialized order/message on the counterpart chain that never set the beneficiary field) — `withdraw()` will send the escrowed tokens/ETH to `address(0)` with no revert [1](#0-0) , and will set `_filled[commitment] = address(0)`, which collides with the unfilled sentinel checked in `cancelOrder` [5](#0-4) . Confirming whether this beneficiary value can be forced by an unprivileged third party against another user's order requires reading the solver `fill()` function, which I was unable to review within the available tool budget — a Devin session with full repo access should verify this before treating the finding as exploit-confirmed.
