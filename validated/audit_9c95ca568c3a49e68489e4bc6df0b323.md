### Title
Silent GitHub-repository identity takeover via `[ownerID+name]` upsert key leads to automatic remote-URL repointing - ([File: app/src/lib/stores/repositories-store.ts])

### Summary

### Finding Description
`RepositoriesStore._upsertGitHubRepository` looks up the cached `GitHubRepository` record purely by the composite key `[ownerID+name]` [1](#0-0) , and when a match is found it **reuses the existing row's database `id`** while overwriting `cloneURL`, `htmlURL`, `private`, and `permissions` with whatever the latest API response says [2](#0-1) . This is structurally identical to the `sbt_soul_transfer` bug: a value is looked up and replaced by composite key without verifying that the *identity* behind that key is still the same underlying object — only the (owner, name) pair is checked, not any stable repository ID from the API (GitHub's numeric repo `id`).

On GitHub, a repository name becomes available for reuse once the original repository is deleted or renamed away, and a different (or attacker-controlled) party can create a new repository with the same owner login and same name. Because `putOwner`/`getOwnerKey` key off `endpoint+login` [3](#0-2)  — not off the numeric owner/repo IDs from the API — the next refresh of that account's repos or PRs will match the *same* local `GitHubRepository` row and silently overwrite its `cloneURL`/`htmlURL`/`permissions` in place, exactly like the SBT bug overwrote the recipient's existing balance entry because it kept `issuer_id`/`class_id` as the identity key instead of a truly unique token identity.

That corrupted `cloneURL` then propagates into `updateRemoteUrl`, which is invoked from the app's PR/repository refresh path [4](#0-3) . If the previously recorded `gitHubRepository.cloneURL` still matches the user's actual git remote (i.e., the user hasn't manually changed it) and the URL protocol is unchanged, Desktop will call `gitStore.setRemoteURL` and **automatically rewrite the user's `origin` remote to the new (attacker's) clone URL** [5](#0-4) .

### Impact Explanation
This is silent corruption of what the user pushes: after the repointing, a subsequent `git push` from GitHub Desktop will push the user's commits to a repository the user never intended (the attacker's repurposed repo at the same owner/name), potentially leaking private source code, or (if the attacker's repo is public) making private code public. Because the whole process happens through a normal repository refresh/PR-check background call, there is no explicit user action or warning beyond an automatic remote URL change.

### Likelihood Explanation
This requires a name-squatting/"repo-jacking" precondition (deletion/rename of the original repo by its owner followed by re-creation under the same login+name by an attacker) and requires that the victim hasn't already changed their remote manually. Given that GitHub allows deleted repos' names to be reused, and Desktop performs this key lookup purely on `[ownerID+name]` without ever cross-checking GitHub's immutable numeric repository ID, this is realistically triggerable without any local access, admin rights, or social engineering beyond the attacker registering a repo name — matching the "attacker controls a GitHub API object" impact category.

### Recommendation
Key the `gitHubRepositories` table (and the `upsertGitHubRepositoryFromMatch`/`_upsertGitHubRepository` lookups) on GitHub's immutable numeric repository ID rather than (or in addition to) `[ownerID+name]`, and treat a mismatch between the previously stored numeric ID and the one returned by the API as a *new* repository rather than an in-place update of the existing row/clone URL. `updateRemoteUrl` should additionally refuse to auto-rewrite the remote if the underlying repository ID has changed, even if the name and owner match.

### Proof of Concept
1. Victim clones `github.com/owner/repo-a` (numeric id `111`) in GitHub Desktop; the app stores a `gitHubRepositories` row keyed by `[ownerID(owner), "repo-a"]` with `cloneURL = https://github.com/owner/repo-a.git`.
2. `owner` deletes `repo-a` (or renames it away) and later re-creates a new repository named `repo-a` under the same account, this time as a malicious mirror, or an attacker gains control of that login and does so (repo-jacking).
3. On the next background repository/PR refresh, `_upsertGitHubRepository` finds the existing local DB row via `[ownerID+name]`, reuses its `id`, and overwrites `cloneURL`/`htmlURL`/`permissions`/`private` with the new repository's data [6](#0-5) .
4. The dispatcher's periodic remote-url check calls `updateRemoteUrl(gitStore, gitHubRepository, updatedApiRepository)` [7](#0-6) ; since the victim's remote URL still equals the *old* cached `cloneURL`, `remoteUrlUnchanged` is true and the function calls `gitStore.setRemoteURL(...)`, repointing `origin` to the new repository [8](#0-7) .
5. The victim's next push goes to the attacker's repository.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```
