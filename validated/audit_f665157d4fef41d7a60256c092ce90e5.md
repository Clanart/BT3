### Title
Malformed blame recipient crashes PedPoP blame verification - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`AdditionalBlameMachine::blame` accepts attacker-controlled `sender` and `recipient` participant IDs without checking they are within the DKG’s `1..=n` participant range. When the supplied `EncryptedMessage` has a valid per-message proof of possession, `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` before validating the supplied `EncryptionKeyProof`. A recipient ID such as `n + 1` is absent from `enc_keys`, causing a panic and denial of service.

### Finding Description
`AdditionalBlameMachine::new` populates `Decryption::enc_keys` only for participants `1..=n`. [1](#0-0)  `Participant::new` only rejects zero, so values greater than `n` are representable. [2](#0-1) 

Neither `AdditionalBlameMachine::blame` nor `blame_internal` validates `recipient` against `n` before calling `decrypt_with_proof`. [3](#0-2)  Inside `decrypt_with_proof`, the message PoP is checked first; an unprivileged sender can generate a valid PoP because the challenge commits only to the supplied sender ID, message key, nonce, and ciphertext. [4](#0-3)  If any `proof` is present, evaluating the DLEq verifier arguments immediately indexes `self.enc_keys[&decryptor]`; a missing recipient therefore panics before the proof itself can be rejected. [5](#0-4) 

The encrypted message fields are attacker-controlled serialized bytes: a group element, Schnorr PoP, and fixed-size encrypted payload. [6](#0-5) 

### Impact Explanation
A participant or other party able to submit a blame accusation can crash the node evaluating it. Because the panic occurs while processing a public `VerifyBlame`/blame path rather than returning `InvalidProof`, this is a remotely triggerable denial of service analogous to the reported invalid-dereference crash class.

### Likelihood Explanation
The attacker does not need a threshold coalition, private share, valid decryption key, or valid DLEq proof. They only need to trigger blame evaluation with:

- a syntactically valid `EncryptedMessage`;
- a valid Schnorr PoP for its declared ephemeral key;
- any syntactically valid `EncryptionKeyProof` encoding;
- a nonzero `recipient` outside `1..=n`.

The PoP is easy to satisfy because the attacker chooses the ephemeral key and knows its discrete logarithm. The missing-map-entry panic is deterministic once that PoP passes.

### Recommendation
Validate both `sender` and `recipient` in `blame`/`blame_internal` before dereferencing protocol maps. For example:

```rust
if (u16::from(sender) > self.commitments.len() as u16) ||
  (u16::from(recipient) > self.commitments.len() as u16)
{
  return Participant::new(1).unwrap(); // or return an explicit error
}
```

Prefer changing `blame`/`blame_internal` to return a structured error rather than a `Participant` where neither party can be blamed, and use `HashMap::get` instead of indexing for untrusted participant IDs.

### Proof of Concept
For a PedPoP instance over `Ristretto` with `n` participants:

1. Select `sender = Participant(1)` and `recipient = Participant(n + 1)`.
2. Choose a nonzero ephemeral scalar `k`, encode `K = kG` as `msg.key`.
3. Choose a nonzero nonce `r`, encode `R = rG`, and calculate the same challenge used by `pop_challenge`:
   - transcript domain: `DKG Encryption Key Proof of Possession v0.2`;
   - fields: `context`, domain separator `proof_of_possession`, `nonce`, `key`, `sender`, and encrypted `message`.
4. Set `s = r + challenge * k`, producing a valid `SchnorrSignature { R, s }`.
5. Serialize `EncryptedMessage` as:

```text
K encoding || R encoding || s encoding || fixed-size SecretShare ciphertext
```

6. Append or provide any syntactically valid `EncryptionKeyProof` encoding:

```text
proof.key encoding || DLEq c encoding || DLEq s encoding
```

7. Invoke `AdditionalBlameMachine::blame(sender, recipient, msg, Some(proof))`.

The PoP check succeeds, `proof` is `Some`, and evaluating `self.enc_keys[&decryptor]` for `decryptor = n + 1` panics because the map contains only participants `1..=n`. [1](#0-0) [5](#0-4)

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
