### Title
Webhook HMAC signature lacks domain separation for shop identity, enabling cross-shop webhook replay - (File: `lib/shopify_app/controller_concerns/payload_verification.rb`)

### Summary
The webhook signature verification in `shopify_app` binds only the raw request body to a globally shared app secret. The shop identity (`X-Shopify-Shop-Domain` header) that background jobs use to select which merchant's access token/session to act on is never included in the signed digest. This mirrors the reported bug class: a signed payload lacking a domain separator (chain ID / contract identity in the original report; shop identity here) allows a valid signature to be replayed in a different context than the signer intended.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes the digest solely from `data` (i.e. `request.raw_post`): [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` calls this with `request.raw_post`, and separately exposes `shop_domain` read directly from the `X-Shopify-Shop-Domain` header — a value that is completely outside the HMAC-signed data: [2](#0-1) 

The generated webhook job templates (and any custom controller built on top of `WebhookVerification`) take that unauthenticated `shop_domain` value and use it to look up a `Shop` record and open an authenticated Shopify session/access token for that shop, then process the (attacker-repeatable) webhook body against it: [3](#0-2) 

Because the app's HMAC secret (`ShopifyApp.configuration.secret`/`old_secret`) is a single value shared across every shop that installs the app, and the digest never folds in shop domain, a webhook body that was validly signed and delivered for Shop A can be resubmitted to the same endpoint with the `X-Shopify-Shop-Domain` header changed to Shop B. `hmac_valid?` still succeeds (the body/secret pair is unchanged), so `WebhookVerification#verify_request` accepts the request, and the downstream job executes with Shop B's session/access token using Shop A's webhook body content — a cross-shop replay enabled purely by the missing domain separator, exactly analogous to the reported cross-chain replay caused by an under-scoped digest.

### Impact Explanation
An app installer/merchant (an "unrelated merchant" with respect to any other install of the same app) who legitimately receives properly signed webhooks for their own shop can capture one and replay it against the shared webhook endpoint while spoofing a different shop's `X-Shopify-Shop-Domain` header. Since job lookups (`Shop.find_by(shopify_domain: shop_domain)`) and session activation use only that header, the attacker can cause the app to process forged/replayed webhook content as if it originated from and belongs to another merchant's shop, using that other shop's own access token — a cross-shop data-integrity and privilege-boundary violation.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must already possess a validly-signed webhook body (obtainable by installing the app themselves and receiving real Shopify webhooks, or observing traffic), and must know or guess a target shop domain, but no secret material or authentication token is required to perform the replay itself — only body+header manipulation against a public endpoint.

### Recommendation
Bind the intended shop identity into the verified signature material, or otherwise authenticate the `shop_domain` used for job dispatch (e.g., only trust the shop that Shopify's HMAC-covered payload actually contains, or require that the shop looked up via `shop_domain` matches metadata inside the signed body/topic verified by the underlying `ShopifyAPI::Webhooks::Registry`). At minimum, do not let an externally-supplied, unsigned header alone determine which shop's session is activated when processing webhook content.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled) and capture a legitimately delivered webhook: raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed over `B` using the app-wide shared secret).
2. POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), and `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a different, unrelated shop).
3. `hmac_valid?(request.raw_post)` in `lib/shopify_app/controller_concerns/payload_verification.rb` still validates because it only checks `B` against the shared secret; `shop_domain` is unchecked.
4. The queued job (e.g. `lib/generators/shopify_app/add_webhook/templates/webhook_job.rb.tt`) loads Shop B by the spoofed domain and runs `shop.with_shopify_session` using Shop B's access token to process attacker-supplied body `B`.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

```ruby
# frozen_string_literal: true

module ShopifyApp
  module WebhookVerification
    extend ActiveSupport::Concern
    include ShopifyApp::PayloadVerification

    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_request
    end

    private

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end
  end
end
```
