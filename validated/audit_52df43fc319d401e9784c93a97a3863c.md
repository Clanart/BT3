### Title
Untrusted `ReceivedOutput` bytes pair an arbitrary offset with an arbitrary output, and the strict equality check in `SignableTransaction::multisig` silently aborts or strands funds — (File: networks/bitcoin/src/wallet/mod.rs, networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a strict equality/inequality check between a value fixed at payload-update time and a value observed at processing time, causing unexpected reverts when the underlying value drifts between the two steps. Serai's Bitcoin wallet has the same structural bug: `ReceivedOutput` commits an `offset` (fixed at scan/registration time) together with a `TxOut`/`OutPoint` (observed at spend time), and `ReceivedOutput::read` deserializes all three fields independently from untrusted bytes with no consistency check between them. Later, `SignableTransaction::multisig` applies the strict check `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`, and any mismatch silently returns `None`. Additionally, the sighash commits to `Prevouts::All`, i.e., the deserialized `TxOut` values — if the serialized value does not match the true on-chain prevout, the produced transaction is consensus-invalid.

### Finding Description
`ReceivedOutput::read` reads `offset` via `Secp256k1::read_F`, then independently `consensus_decode`s a `TxOut` and an `OutPoint`, and returns them bundled with no validation that `key + offset*G` actually corresponds to `output.script_pubkey` (networks/bitcoin/src/wallet/mod.rs:122-134). Internally-created `ReceivedOutput`s are consistent because `scan_transaction` only produces them by looking up `output.script_pubkey` in the registered scripts map (mod.rs:205-211), but nothing in `read` enforces that invariant for bytes fed in from an untrusted source — and `ReceivedOutput::read` is a public entry point for untrusted bytes.

At spend time, `SignableTransaction::multisig` derives `offset.group_key()` and strictly compares its P2TR script against `self.prevouts[i].script_pubkey`, returning `None` on any mismatch (send.rs:275-279). If the check passes but the deserialized `output.value` differs from the real on-chain prevout, `TransactionSignMachine::sign` commits to the wrong amounts via `Prevouts::All(&self.tx.prevouts)` (send.rs:375-386); the resulting signatures verify locally under FROST but the broadcast transaction is rejected by Bitcoin consensus because Taproot sighash commits to actual prevout amounts.

This mirrors the report: a strict equality between a value bound at one stage (offset chosen at registration; `kinds`/`scripts` maps in `Scanner::register_offset`, mod.rs:180-196) and a value supplied at a later stage (the `TxOut` bytes) with no slippage/validation, so any drift aborts or invalidates the spend rather than being handled.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ReceivedOutput::read` (e.g., wherever serialized outputs are exchanged between components) can either:

1. Cause `multisig()` to return `None`, silently aborting the signing of a transaction spending a legitimately received output — a denial of service on withdrawals for funds the scanner reported as received.
2. Supply a real output script with a falsified `value`, producing a fully-signed transaction that commits to incorrect prevout amounts via `Prevouts::All`, which is permanently unbroadcastable — funds reported received are not spendable. Since the transaction consumes the inputs set, retries built from the same corrupted `ReceivedOutput` fail identically.

This satisfies the "funds reported received that are not spendable" / unexpected-revert acceptance criteria.

### Likelihood Explanation
Reachable wherever `ReceivedOutput` is round-tripped through serialization across trust boundaries (it implements `read`/`write`/`serialize` specifically for transport). No secret material, validator collusion, or privileged access is required — only the ability to supply bytes to `ReceivedOutput::read`. Severity: Medium — it requires an untrusted-bytes path to the output store, and the outcome is a DoS/stranded-funds condition rather than key compromise.

### Recommendation
Make the staged values self-validating at read time, eliminating the implicit assumption that scan-time and spend-time values agree:

- In `ReceivedOutput::read`, after decoding, recompute `p2tr_script_buf(group_key + offset*G)`-equivalent or store the group key context needed to verify `offset` against `output.script_pubkey`, rejecting inconsistent triples. If the key isn't available at read time, add a `verify(key) -> bool`/`validate` method on `ReceivedOutput` that callers must invoke after deserialization before constructing a `SignableTransaction`.
- Replace the silent `None` return in `SignableTransaction::multisig` (send.rs:273-285) with an explicit error distinguishing "wrong keys" from "corrupted/attacker-controlled `ReceivedOutput`," so the failure surfaces instead of aborting.
- Cross-check `output.value` against the outpoint's actual prevout (via RPC or a committed value) before signing, since `Prevouts::All` bakes the deserialized value into the sighash.

### Proof of Concept
```rust
// A legitimately scanned output
let real: ReceivedOutput = scanner.scan_transaction(&tx).remove(0);

// Attacker crafts bytes: same outpoint, same script_pubkey, but a different offset
// (e.g., Scalar::ONE instead of the registered Scalar::ZERO), or an inflated value.
let mut buf = Vec::new();
Scalar::ONE.write(&mut buf).unwrap();          // wrong offset
buf.extend(serialize(&TxOut {
  value: Amount::from_sat(real.value() + 1),   // inflated value
  script_pubkey: real.output().script_pubkey.clone(),
}));
buf.extend(serialize(real.outpoint()));

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted unconditionally

let stx = SignableTransaction::new(vec![forged], &payments, change, None, FEE).unwrap();
// Case A (wrong offset): stx.multisig(&keys) returns None — signing silently aborts.
// Case B (inflated value, matching offset): sign() succeeds, but the signed TX commits to
// Prevouts::All containing the fake amount and is rejected by the Bitcoin network —
// the received funds cannot actually be moved.
```
