### Title
`ThresholdKeys::read` deserializes attacker-chosen verification shares and secret share without any consistency check, yielding a threshold key whose group key the attacker fully controls - ([File: crypto/dkg/src/lib.rs])

### Summary
The report's bug class is deserialization of attacker-controlled bytes producing objects the type system never validated (unsafe YAML type instantiation → RCE). The Serai analog is `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574`), which reconstructs a `ThresholdKeys` — the object used by every `SignMachine` to produce threshold signatures — from a byte stream, without checking that the deserialized `secret_share` is consistent with the deserialized `verification_shares`, and without rejecting identity verification shares.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an `Interpolation` method (including `Constant(Vec<F>)` whose `n` coefficients come straight from the wire), `secret_share` via `C::read_F`, and `n` verification shares via `<C as Ciphersuite>::read_G`, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:625`).

`Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91`) only enforces canonical encodings — it does **not** reject the identity point (that stricter check lives only in `Curve::read_G`, `crypto/frost/src/curve/mod.rs:125`, and `ThresholdKeys` is generic over `Ciphersuite`, not `Curve`).

`ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349`) validates only:
- `verification_shares.len() == n` and participant indexes `<= n` (`crypto/dkg/src/lib.rs:355-365`),
- `Constant` interpolation requires `t == n` (`crypto/dkg/src/lib.rs:367-374`).

It then computes `group_key` as the interpolation of `verification_shares[1 ..= t]` (`crypto/dkg/src/lib.rs:376-378`) and stores everything verbatim. Nowhere is it checked that `C::generator() * secret_share == verification_shares[i]`, that the shares form a consistent polynomial evaluation, or that `group_key`/`verification_shares` are non-identity. The deserialized object is a fully-formed `ThresholdKeys` usable by `view()`, `group_key()`, `original_secret_share()`, and every FROST signing machine (`AlgorithmMachine::new(algorithm, keys)`).

Concretely, the attacker supplies `Interpolation::Constant([c_1, ..., c_t])` (or Lagrange shares) such that `sum_i verification_shares[i] * factor_i` equals a point whose discrete log the attacker knows — e.g. all-`identity` verification shares give `group_key = identity` (discrete log `0`), or `verification_shares[i] = a_i * G` with chosen `a_i` gives a group key with known discrete log. The attacker also sets `secret_share` to any scalar; `ThresholdKeys::new` accepts it because `interpolation_factor` for `Constant` simply indexes `c[i-1]` (`crypto/dkg/src/lib.rs:228`) and no share/verification consistency equation is ever evaluated.

### Impact Explanation
Whatever consumes the deserialized keys treats `group_key()` as the multisig's public key. If `group_key` is identity or a known-DL point:
- **Key "recovery" is trivial**: the group secret is known to the attacker (`0`, or `sum a_i * factor_i`), so the attacker can unilaterally produce valid threshold signatures for that key — a forged signature without any honest participation. For funds addressed to `group_key` (e.g. a Bitcoin `ReceivedOutput` scanned under this key), the attacker can spend them immediately — funds reported received under this key are effectively the attacker's.
- **Inconsistent `secret_share` vs. `verification_shares[i]`** means `view()` produces a `ThresholdView` whose `secret_share` does not correspond to the advertised verification share, so shares signed by this machine are wrong for the advertised group key — corrupting every signing session the keys participate in.

This is the direct analog of the DotCi bug: attacker-controlled bytes are deserialized into a struct that is then *used as authoritative* — the type instantiated from the wire dictates the effective key.

### Likelihood Explanation
Any path that loads `ThresholdKeys` from bytes influenced by an unprivileged party (restoring keys from supplied/relayed material, or a node fed a crafted serialized key blob) reaches this code. `ThresholdKeys::read` is a public API performing only length and canonicality checks; the malicious input is a fixed-size canonical encoding, so no external validation can distinguish it. The rules of this audit explicitly enumerate `ThresholdKeys::read` as a public-input-reachable entry point.

### Recommendation
In `ThresholdKeys::new` (the shared constructor used by `read`), enforce:
1. `verification_shares[i] == C::generator() * secret_share` for `params.i()`,
2. non-identity `group_key` and non-identity verification shares (use `Curve::read_G`-style identity rejection or an explicit `is_identity` check),
3. for `Constant` interpolation, that the constant interpolation of the verification shares at every index `1..=n` is consistent — or at minimum that `group_key` derived from `1..=t` is non-identity.

### Proof of Concept
```rust
// Crafted byte stream for ThresholdKeys::<C>::read with t = n = 2, i = 1
let mut bytes = vec![];
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(2u16.to_le_bytes());        // t
bytes.extend(2u16.to_le_bytes());        // n
bytes.extend(1u16.to_le_bytes());        // i
bytes.push(0);                           // Interpolation::Constant
for _ in 0 .. 2 {
    bytes.extend(C::F::ONE.to_repr().as_ref());  // c_i = 1
}
bytes.extend(C::F::ONE.to_repr().as_ref());      // secret_share = 1 (inconsistent w/ shares below)
for _ in 0 .. 2 {
    bytes.extend(C::G::identity().to_bytes().as_ref()); // verification_shares = identity
}

let keys = ThresholdKeys::<C>::read(&mut bytes.as_slice()).unwrap();
// group_key = identity * 1 + identity * 1 = identity → discrete log 0, attacker signs unilaterally
assert!(bool::from(keys.group_key().is_identity()));
// Yet keys.original_secret_share() = 1 while verification_shares[1] = identity ≠ G*1 —
// no consistency check was ever performed.
```
