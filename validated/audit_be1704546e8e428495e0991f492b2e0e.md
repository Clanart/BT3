## Analysis Summary

The Royco/RecipeKernel bug is fundamentally a **stale-identity-reuse** flaw: an identifier (`targetMarketID`) that was legitimately bound to one piece of state can, after some other event, become silently re-bound to unrelated, attacker-controlled content, and the code that trusts the identifier never re-verifies that the binding is still the one that was originally committed to.

Searching the current Protobuf checkout for structurally equivalent patterns — a mutable "current type/identity" variable that should be re-established per logical unit of work but instead survives across unit boundaries — surfaces a concrete match in the Lite-runtime **MessageSet** array-decoder.

### Title
Stale extension-identity leak across `MessageSet` items in the Lite array decoder allows attacker-controlled bytes to silently overwrite an unrelated extension field - (File: `java/core/src/main/java/com/google/protobuf/MessageSetSchema.java`)

### Summary
`MessageSetSchema.mergeFrom(T, byte[], int, int, ArrayDecoders.Registers)` — the fast, array-based decoder used by the Lite runtime to parse `message_set_wire_format` messages — declares the `extension` variable *outside* the per-item parsing loop [1](#0-0) . Because it is never reset to `null` at the start of each new `MESSAGE_SET_ITEM_TAG` group [2](#0-1) , a `typeId → extension` binding resolved in one item persists into the next item. If the next item contains a `message` field before (or without) its own `typeId` field, the stale extension identity from the *previous* item is reused to decode the *new*, attacker-controlled bytes, and the result is written into that stale extension's field [3](#0-2) .

### Finding Description
The wire format for `MessageSet` is a sequence of `Item` groups, each of which is expected to carry its own `typeId`/`message` pair:
```
message MessageSet {
  repeated group Item = 1 {
    required uint32 typeId = 2;
    required bytes message = 3;
  }
}
```
The canonical, correctness-verified implementation (`CodedInputStreamReader`-based path) re-declares `Object extension = null;` fresh for *every* item, inside `parseMessageSetItemOrUnknownField` [4](#0-3) . This guarantees that a `message` tag encountered before any `typeId` tag in a given item is treated as unresolved (`rawBytes`), never silently attributed to a type declared in a prior item.

The array-decoder fast path breaks this invariant. `extension` is declared once at the top of `mergeFrom(...)` [5](#0-4)  and is shared across:
- ordinary (non-group) extension fields of the containing message [6](#0-5) , and
- every subsequent `MESSAGE_SET_ITEM_TAG` group in the same buffer [7](#0-6) .

Only `typeId` and `rawBytes` are reset per item (`typeId = 0; ByteString rawBytes = null;` at lines 168–169); `extension` is not. Consequently:

1. Item 1 sends `typeId = N` where `N` resolves to a real registered extension `E`; a `message` tag follows and is decoded/stored into `E`'s field. `extension` now points to `E`.
2. Item 2 begins. If its **first** field is a `message` tag (i.e. `typeId` is omitted or comes after), the check `if (extension != null)` at line 191 is still true — using the *stale* `E` left over from item 1 — so item 2's attacker-supplied bytes are decoded as if they were `E`, and `extensions.setField(extension.descriptor, ...)` overwrites `E`'s value [3](#0-2) .

No identity/consistency check (equivalent to the recommended "hash check" in the original report) exists to confirm that item 2 actually declared type `N` before letting its payload bind to `E`.

### Impact Explanation
This lets an ordinary client craft a single, bounded `MessageSet`-formatted payload where a later, nominally "typeless" item silently rebinds and overwrites a previously-declared extension field with fully attacker-chosen content, without that item ever presenting the corresponding `typeId`. Any application logic that trusts "an extension slot is only set when its `typeId` is explicitly present in that item" (a reasonable reading of the MessageSet wire-format contract, and the actual behavior of the canonical/reflection-based parser) can be bypassed: the same buffer parses differently — and less safely — depending on which of the two `MessageSetSchema` code paths (array-fast-path vs. reflective) handles it, and the fast path allows a value to be attributed to a well-known extension field via content the higher-level code may not have intended to be interpreted as that type at all. This is a parser-differential integrity violation reachable purely through the public `parseFrom(byte[])`/`mergeFrom` APIs on a trusted, ordinary `message_set_wire_format` schema.

### Likelihood Explanation
Reachable by any client sending a single bounded, well-formed binary payload to `MessageLite.parseFrom(byte[])`/`mergeFrom` for a Lite-runtime message using `option message_set_wire_format = true`, which is a standard, documented, non-exotic protobuf feature (still used by legacy/Android generated code) — no hostile schema, no privileged access, and no huge allocation is required.

### Recommendation
Scope the `extension` (and ideally `typeId`) local variable to the per-item inner loop in `MessageSetSchema.mergeFrom(T, byte[], int, int, ArrayDecoders.Registers)`, mirroring `parseMessageSetItemOrUnknownField`'s per-item `Object extension = null;` initialization [4](#0-3) , so that no item can inherit a type binding established while processing a previous item or field.

### Proof of Concept
Conceptually (not run, per constraints):
1. Define a proto2 message `M` with `option message_set_wire_format = true;` and register one extension `Ext` (field number `N`, message type `T`) via `ExtensionRegistryLite`.
2. Build raw bytes for `M` containing two `Item` groups:
   - Item 1: `typeId = N`, `message = <valid encoding of T instance A>`.
   - Item 2: `message = <valid encoding of T instance B>` **only** — no `typeId` field at all in this item.
3. Call `M.parseFrom(bytes, registry)` using the standard byte-array `parseFrom` entry point (which drives the `ArrayDecoders`/`MessageSetSchema.mergeFrom(byte[]...)` path shown above).
4. Observe that `getExtension(Ext)` returns instance `B`, not `A` — i.e., item 2's payload, which never declared `typeId = N`, silently overwrote the `Ext` field because `extension` from item 1 leaked into item 2's decoding at [3](#0-2) . Re-parsing the identical bytes through the reflective/`CodedInputStreamReader` path (`parseMessageSetItemOrUnknownField`) instead treats item 2's message as unresolved raw bytes (`typeId == 0`) and stores it as an unknown field, confirming the divergence and the missing per-item reset.
