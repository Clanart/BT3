### Title
Missing cross-vote consistency check between `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` allows the governing node to ratify an inverted KIP-71 fee bound within a single epoch - (File: `kaiax/gov/headergov/impl/header.go`)

### Summary
`checkConsistency()` in the header-governance module validates a `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` vote only against the **currently effective** `ParamSet`, not against other votes cast (and pending ratification) in the same epoch. Because both bounds can be voted on independently within the same epoch and are ratified together at the epoch boundary, a governing node can produce a final, ratified `header.Governance` record where `LowerBoundBaseFee > UpperBoundBaseFee`. This is the same class of bug as the reported "lack of sanity checks on record update": each individual update passes its local check, but the resulting composite record is never cross-validated, corrupting the KIP-71 base-fee state used by every subsequent block.

### Finding Description
`checkConsistency` handles the two KIP-71 bound votes like this: [1](#0-0) 

Each check compares the *new* voted value only to the *old, currently effective* `ParamSet` (via `h.GetParamSet(blockNum)`), never to any other vote submitted within the same not-yet-ratified epoch. Governance votes accumulate over an epoch and are ratified together at the epoch boundary: [2](#0-1) 

Sequence that breaks the invariant `Lower <= Upper`:
1. Current effective state: `Lower = 25e9`, `Upper = 750e9`.
2. Governing node votes `Kip71UpperBoundBaseFee = 30e9` early in the epoch. Check: `30e9 < Lower(25e9)`? No → passes.
3. Later in the same epoch, governing node votes `Kip71LowerBoundBaseFee = 100e9`. Check: `100e9 > Upper(750e9)` (still the old, pre-ratification value)? No → passes.
4. At epoch end, both votes are ratified together into `header.Governance`, and from the next epoch the effective params become `Lower = 100e9`, `Upper = 30e9` — an inverted, invalid bound that was never checked against itself.

`VerifyGov` only checks that the ratified JSON matches the votes collected for the epoch; it performs no cross-parameter consistency check either: [3](#0-2) 

The corrupted param pair then feeds directly into the KIP-71 fee-adjustment algorithm used for every block's base fee: [4](#0-3) 

With `Upper < Lower`, the `parentBaseFee >= upperBoundBaseFee` branch clamps essentially all future base fees down to the (now too-low) `upperBoundBaseFee`, permanently bypassing the intended `lowerBoundBaseFee` floor until another governance vote intervenes — mirroring the original report's "only the admin can fix" impact, since correcting the state again requires further votes from the same privileged governing node.

### Impact Explanation
Kaia's transaction base fee (KIP-71/Magma) directly determines the minimum fee burned and paid on every transaction network-wide. An inverted bound silently breaks the fee-floor invariant for all blocks until epoch-based correction, effectively suppressing the network's designed minimum fee floor. This is a protocol-level (not contract-level) analog of the reported bug: an authorized but narrowly-scoped update (a single governance vote) escapes the intended invariant because sibling records/parameters are validated independently rather than jointly, corrupting a value (`NextMagmaBlockBaseFee`) that affects fee/burn accounting for every transaction on the chain.

### Likelihood Explanation
Requires control of the governing node under `single` governance mode (the same governance-mode class of actor the rules permit to analyze, analogous to the oracle's privileged `ORACLE_MODIFIER_ROLE`). No hash collisions, races, or multi-party collusion are needed — two ordinary `governance_vote` RPC calls within one epoch suffice, and both individually pass all existing checks.

### Recommendation
When validating a `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee` vote in `checkConsistency`, resolve the *pending* value of the counterpart parameter for the same epoch (i.e., the latest not-yet-ratified vote for that name in the current epoch, if any) rather than only the last-ratified `ParamSet`, and reject the vote if the resulting pair would violate `Lower <= Upper`. Additionally, `VerifyGov` should perform a final cross-check on the fully assembled `header.Governance` payload before acceptance, rejecting any epoch ratification that leaves `LowerBoundBaseFee > UpperBoundBaseFee`.

### Proof of Concept
1. Deploy/enable `single` governance mode with a configured `governance.governingnode`.
2. At the start of an epoch, call `governance_vote("kip71.upperboundbasefee", 30000000000)` — passes because `30e9` is not less than the current lower bound.
3. Later in the same epoch, call `governance_vote("kip71.lowerboundbasefee", 100000000000)` — passes because `100e9` is not greater than the current (old) upper bound.
4. At the epoch boundary both votes ratify into `header.Governance`.
5. From the next epoch, `GetParamSet` returns `LowerBoundBaseFee=100e9, UpperBoundBaseFee=30e9`; `NextMagmaBlockBaseFee` (in `params/kip71_config.go`) now clamps every block's base fee to `30e9`, permanently ignoring the intended `100e9` floor until further governance action.

```go
// (1) governance must be empty in non-epoch block,
// (2) if there are no votes in the previous epoch, governance must be empty,

// (4) the json must not contain unknown fields,
// (5) the parsed json must exactly match the map derived locally from the previous epoch's votes.
func (h *headerGovModule) VerifyGov(header *types.Header) error {
	// (1)
	if header.Number.Uint64()%h.epoch != 0 {
		if len(header.Governance) > 0 {
			logger.Error("governance is not allowed in non-epoch block", "num", header.Number.Uint64())
			return ErrGovInNonEpochBlock
		} else {
			return nil
		}
	}

	// (2), (3)
	expected := h.getExpectedGovernance(header.Number.Uint64())
	if len(header.Governance) == 0 {
		if len(expected.Items()) != 0 {
			return ErrGovVerification
		}

		return nil
	}

	// (4)
	var gb headergov.GovBytes = header.Governance
	actual, err := gb.ToGovData()
	if err != nil {
		logger.Error("DeserializeHeaderGov error", "num", header.Number.Uint64(), "governance", gb, "err", err)
		return err
	}

	// (5)
	if !reflect.DeepEqual(expected, actual) {
		logger.Error("Governance mismatch", "expected", expected, "actual", actual)
		return ErrGovVerification
	}

	return nil
```

```markdown
A vote is initiated by a governing member of the GC casting a vote.
The vote is cast by the `governance_vote` API, which is inscribed in the block header `header.Vote` when the node that received the API call becomes the proposer.
The voter casts a vote as a tuple `(parameter name, new value)`.
The vote is collected for the entire epoch.

At every epoch block (i.e., `k*epoch` blocks), the node that becomes the proposer will check if the vote has been ratified.
If the vote is ratified, the node will announce the ratification in the block header `header.Governance`.
In other words, `header.Governance` can contain data only at epoch blocks.
If there are no votes in an epoch, the next starting block of the epoch will have an empty `header.Governance`.
It contains a JSON object of `{name: value}` for each ratified parameter.

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.

Parameter change ratified at `k*epoch` block takes effect starting from `(k+1)*epoch` block.
```
