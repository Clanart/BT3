### Title
Rebase/cherry-pick "no tracked changes" auto-skip silently drops a commit's content without user confirmation - (File: app/src/lib/git/rebase.ts, app/src/lib/git/cherry-pick.ts)

### Summary
The external report's bug class is: a state-transition guard silently accepts a degenerate input (amount = 0) and the surrounding UX has no path to surface or correct that decision to the user, corrupting the expected outcome. The Desktop analog is in `continueRebase` and `continueCherryPick`: when a conflict resolution leaves the index with zero tracked changes, Desktop automatically decides the commit is a "no-op" and silently runs `git rebase --skip` / commits an empty commit, without ever asking the user to confirm that a commit's content is being dropped from the resulting history.

### Finding Description
When Desktop resolves rebase or cherry-pick conflicts, it stages the manually-resolved files and then checks whether anything ended up staged: [1](#0-0) 

If `trackedFilesAfter.length === 0`, the code assumes "the current commit is a no-op and the changes it contains are already available in the base branch" and runs `git rebase --skip` — logged only via `log.warn`, never surfaced to the user: [2](#0-1) 

The same pattern exists for cherry-pick, where an empty commit is created instead: [3](#0-2) 

The documentation itself confirms this is the designed control-flow, treating "no changes in the index" as equivalent to "this commit is already incorporated": [4](#0-3) 

This assumption is not always true. If a user rebases or cherry-picks their branch onto a base branch that an attacker controls (a malicious fork, a PR branch, or any fetched/cloned remote), the attacker can craft the base branch so it already contains content identical to what the victim's commit would introduce (or arrange the conflict markers/manual-resolution outcome to net to an empty diff). When the victim resolves the conflict (via "ours"/"theirs" or manual edits) and continues, Desktop's own heuristic — not `git`'s native behavior — decides unilaterally that the commit is a no-op and skips it, with only a developer-facing `log.warn`. Unlike the plain git CLI, where `git rebase --continue` on an empty index errors out and forces the user to explicitly type `git rebase --skip` (an intentional, visible confirmation step), Desktop's automation removes that confirmation gate entirely.

This mirrors the reported bug class precisely: a guard/check (`_decreaseRequestIsPending`/`_undelegateRequestIsPending`) that treats a zero-ish value as "nothing to do" and silently forecloses the expected user-visible path (cancel), leaving the actual state divergent from what the user believes happened. Here, the "zero-ish value" is an empty staged diff, and the silently-skipped outcome is a dropped commit — a corruption of what ends up in the resulting rebased/cherry-picked history.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A commit the user believed was rebased/cherry-picked onto the target branch can be silently dropped from the resulting history with no dialog, confirmation, or banner distinguishing it from a normal successful rebase/cherry-pick — the operation reports success (`RebaseResult.CompletedWithoutError` / `CherryPickResult.CompletedWithoutError`) even though a commit's changes never landed. If the dropped commit contained a security fix, license file, or other meaningful change, the victim could unknowingly force-push a branch that is missing that change, believing the operation succeeded cleanly.

### Likelihood Explanation
Requires only that the victim rebase or cherry-pick onto a repository/branch the attacker influences (a common Desktop workflow: pulling in/rebasing onto a fork or PR branch), and that a merge conflict occurs whose resolution nets to an empty diff — attacker-controllable by crafting base-branch content that duplicates the victim commit's changes. No admin rights, local access, or prior compromise needed; it only needs a git remote/PR the user interacts with normally.

### Recommendation
Do not silently auto-skip on empty diff. Surface an explicit, user-visible confirmation (a dialog similar to the existing conflict/abort dialogs) stating "This commit appears to introduce no changes and will be skipped/omitted from the result — continue?" before invoking `git rebase --skip` or creating an empty cherry-pick commit, and record the skipped commit's SHA/summary in the operation result so it can be shown in the completion banner instead of only `log.warn`.

### Proof of Concept
1. Attacker sets up a public fork/branch `feature` that already contains a duplicate of a change the victim intends to bring over (e.g., an identical single-line edit to `file.txt`) alongside other unrelated diffs designed to cause a conflict.
2. Victim clones/fetches the attacker's branch (normal, unprivileged interaction with a git remote) and rebases their own branch (containing commit `C` with that same `file.txt` edit plus other important logic) onto `feature` in Desktop.
3. Git reports a conflict on `file.txt`. The victim resolves it (accepting the offered/likely resolution).
4. After staging, `status.workingDirectory.files` filtered to tracked files is empty for commit `C` specifically because the attacker's branch already carried the identical hunk — see `app/src/lib/git/rebase.ts:516-529`.
5. Desktop silently executes `git rebase --skip` and reports `RebaseResult.CompletedWithoutError`; commit `C`'s intended changes (beyond the duplicated hunk) never enter the rebased history, and the victim sees a normal "rebase completed" outcome with no indication a commit was omitted.

export async function abortRebase(repository: Repository) {
  await git(['rebase', '--abort'], repository.path, 'abortRebase')
}

function parseRebaseResult(result: IGitStringResult): RebaseResult {
  if (result.exitCode === 0) {
    if (result.stdout.trim().match(/^Current branch [^ ]+ is up to date.$/i)) {
      return RebaseResult.AlreadyUpToDate
    }

    return RebaseResult.CompletedWithoutError
  }

  if (result.gitError === GitError.RebaseConflicts) {
    return RebaseResult.ConflictsEncountered
  }

  if (result.gitError === GitError.UnresolvedConflicts) {
    return RebaseResult.OutstandingFilesNotStaged
  }

  throw new Error(`Unhandled result found: '${JSON.stringify(result)}'`)
}
