### Title
Symlinked repository files bypass path-containment check when opened via "Open in External Editor"/"Open with Default Program"/"Reveal in File Manager" - (File: app/src/ui/lib/open-file.ts, app/src/lib/app-shell.ts, app/src/lib/editors/launch.ts)

### Summary
GitHub Desktop has a dedicated, tested path-containment primitive, `resolveWithin()` ( [1](#0-0) ), that resolves symlinks and rejects any path whose real location escapes the repository root. It is correctly applied in exactly two places: the `x-github-client://openRepo` deep-link file handler ( [2](#0-1) ) and the Copilot conflict-context file reader ( [3](#0-2) ). Every other UI action that opens a repository-relative path on disk — "Open with Default Program", "Open in External Editor", and "Reveal in File Manager" for files shown in the Changes list, commit history, PR file list, and conflict resolution UI — builds the path with a plain `Path.join(repository.path, file.path)` and passes it straight to `shell.openExternal`, `shell.showItemInFolder`, or a spawned external editor process, with no symlink/containment check at all.

### Finding Description
`resolveWithin()` exists specifically to defeat symlink-based directory-escape attacks; its own test suite proves the attack it defends against: "fails for paths that use a symlink to traverse outside of the root" ( [4](#0-3) ).

However, the file-open action handlers that surface repository content to the user never call it:
- `openFile()` calls `shell.openExternal('file://'+fullPath)` directly on an unresolved path ( [5](#0-4) ).
- `revealInFileManager()` builds `Path.join(repository.path, path)` and calls `shell.showItemInFolder` with no resolution ( [6](#0-5) ).
- `launchExternalEditor`/`launchCustomExternalEditor` spawn the configured editor binary with the raw `fullPath` as an argument ( [7](#0-6) ).
- All call sites that build these `fullPath` values from a `WorkingDirectoryFileChange`/`CommittedFileChange`'s `.path` (attacker-controlled, since it comes straight from git tree/index entries in a cloned repo) use plain `Path.join`, e.g. `app/src/ui/changes/sidebar.tsx:282-285`, `app/src/ui/app.tsx:3429-3437`, `app/src/ui/changes/filter-changes-list.tsx:628-655`, `app/src/ui/history/selected-commits.tsx:384-419`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx:86-198`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx:212-234`, `app/src/ui/lib/conflicts/unmerged-file.tsx:396-419`.

Git supports tracked symlink blobs (mode `120000`). A malicious repository can commit a tracked symlink entry, e.g. `evil-looking-file.txt -> ../../../.ssh/id_ed25519` (or an absolute path). On checkout (default behavior on macOS/Linux, and on Windows with symlink support enabled), git materializes this as a real filesystem symlink inside the working tree. This file then shows up as a normal entry in the Changes list, commit history file list, or PR file list. If the user right-clicks and chooses "Open in External Editor" or "Open with Default Program", or double-clicks the row, Desktop resolves `fullPath = Path.join(repo.path, 'evil-looking-file.txt')` — which is still nominally "inside" the repo per a naive string check — and hands that path straight to the OS/editor, which follows the symlink and opens whatever the attacker pointed it at. `resolveWithin` exists precisely to catch this case (by comparing `realpath()` of the resolved path against `realpath()` of the root) but is never invoked on this path.

### Impact Explanation
Following the symlink causes the OS shell or the user's configured external editor to open and display the contents of an arbitrary file the OS user can read (SSH private keys, cloud credential files, browser cookie stores, etc.) inside the editor/viewer UI, i.e. file read outside the repository directory, triggered purely by normal post-clone user interaction with content the attacker fully controls. Depending on editor/file-manager behavior this can also enable further compromise (e.g., an editor that auto-executes tasks/extensions on open, or a `.desktop`/`.lnk`-style artifact resolved through the symlink on some platforms).

### Likelihood Explanation
The attacker only needs the victim to clone/fetch a repository and take one ordinary action already presented as a first-class feature in the UI ("Open in External Editor", "Open with Default Program", or double-click a changed/committed file) — no admin rights, no local access, and no unnatural steps are required. The existing `resolveWithin` guard, its dedicated symlink test, and its use in the deep-link handler show the Desktop team is aware of this exact attack class for one entry point but did not extend it to the (more commonly used) file-open menu actions.

### Recommendation
Route every `fullPath`/`Path.join(repository.path, file.path)` construction that feeds `openFile`, `revealInFileManager`, `launchExternalEditor`, and `launchCustomExternalEditor` through `resolveWithin(repository.path, file.path)` first, refusing to open/reveal/launch when it returns `null`, mirroring the pattern already used in `dispatcher.ts`'s `openRepositoryFromUrl` and `copilot-conflict-context.ts`.

### Proof of Concept
1. Create a repository containing a tracked symlink: `ln -s ~/.ssh/id_ed25519 payload.txt && git add payload.txt && git commit -m x` (on a platform where git creates real symlinks, e.g. macOS/Linux).
2. Have the victim clone this repository in GitHub Desktop.
3. In the Changes list (if `payload.txt` is later modified) or in the commit's file list, right-click `payload.txt` → "Open in External Editor" (or double-click the row).
4. Desktop calls `Path.join(repository.path, 'payload.txt')` ( [8](#0-7)  / [9](#0-8) ) and passes it to `launchExternalEditor` ( [10](#0-9) ), which spawns the editor on that path; the OS/editor follows the symlink and displays the victim's `~/.ssh/id_ed25519` contents — no `resolveWithin` check ever runs, unlike the `openRepositoryFromUrl` handler for the same class of path.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
