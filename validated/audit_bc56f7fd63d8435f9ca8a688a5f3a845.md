### Title
SSRF via attacker-controlled DataLayer mirror URLs consumed by a subscriber's `fetch_and_validate`/`http_download` path - (File: `chia/data_layer/data_layer.py`, `chia/data_layer/download_data.py`)

### Summary
Any wallet user can publish an on-chain DataLayer "mirror" coin whose memo contains arbitrary, attacker-chosen URL strings via `DataLayerWallet.create_new_mirror()` [1](#0-0) . Any other node that subscribes to that store will ingest these URLs as trusted "servers" for that store and will have its DataLayer service issue outbound HTTP requests to them with no scheme, host, or address-range restriction — the same bug class as the reported dify SSRF (an unauthenticated/low-privilege actor supplies a `url` value that is later fetched server-side).

### Finding Description
1. Any wallet owner can create a mirror coin for any launcher/store id, encoding one or more free-form URL strings into the coin memo, via `create_new_mirror()`: [1](#0-0) 
This requires nothing more than a normal signed spend bundle from the attacker's own wallet — no special privilege, and the URL field is never validated (no scheme allow-list, no private/loopback/link-local address blocklist).

2. When any other node observes this mirror coin get added on-chain, `DataLayerWallet.coin_added()` decodes the URLs directly from the spend and persists them as a `Mirror` record tied to the store id, without validating the URL: [2](#0-1) 

3. The DataLayer service periodically pulls these wallet-reported mirror URLs into its local subscription "available servers" list for the store: `DataLayer.update_subscriptions_from_wallet()` simply extracts `mirror.urls` with no validation and feeds them into `DataStore.update_subscriptions_from_wallet()`: [3](#0-2) 

4. `fetch_and_validate()` then shuffles these `servers_info` and issues an HTTP request to whichever URL it picks: [4](#0-3) 

5. The actual network call is `http_download()`, which does a plain `aiohttp.ClientSession().get(server_info.url + "/" + filename, ...)` with no scheme restriction and no check against internal/loopback/link-local/metadata addresses: [5](#0-4) 

6. When a plugin downloader is configured, the same untrusted mirror URL is also forwarded server-side as a JSON field (`"url": server_info.url`) to the downloader plugin's `/download` endpoint: [6](#0-5) 

Nowhere in this chain is the mirror URL checked against a scheme allow-list or against private/loopback/link-local/cloud-metadata address ranges — the DataLayer module's own documentation explicitly flags mirror/plugin URLs as an external trust boundary that must not be treated as trusted, and this network-issuing path does not enforce that: "Plugin and mirror URLs are external trust inputs." [7](#0-6) 

### Impact Explanation
Any Chia user running a DataLayer service that subscribes to (or is auto-subscribed as an owner mirror for) a store controlled by an attacker can be forced to make outbound HTTP GET/POST requests to attacker-chosen hosts — e.g. internal LAN addresses, `localhost` (potentially hitting the node's own unauthenticated-by-network-policy or otherwise reachable local services/ports), or cloud metadata endpoints (`http://169.254.169.254/...`). Since the fetched content is then fed into `insert_into_data_store_from_file()` for parsing, this also creates a path for feeding attacker-influenced/probed responses back into further processing, in addition to the pure request-forgery impact (port/service scanning, hitting internal admin endpoints, credential/metadata exfiltration via response timing/side channels).

### Likelihood Explanation
Likelihood is Medium: exploitation requires the victim to be running the DataLayer service and to subscribe to (or otherwise be a mirror-tracking peer of) a store that the attacker controls — a normal, expected DataLayer usage pattern (subscribing to shared/public data stores is a core supported feature). No signature bypass or privileged access is needed; the attacker only needs to spend their own coins to create a mirror coin with a malicious URL, which is a standard, unprivileged wallet action reachable by any spend-bundle submitter.

### Recommendation
Validate mirror/server URLs before they are used for outbound requests: enforce an allow-listed scheme (e.g., `https://`/`http://` only, no `file://`, `s3://` outside the dedicated plugin flow, etc.), and resolve/reject hosts that resolve to private, loopback, link-local, or other non-routable/metadata address ranges (equivalent to SSRF protections) both in `http_download()`/`download_file()` in `chia/data_layer/download_data.py` and in `DataLayer.update_subscriptions_from_wallet()`/`fetch_and_validate()` in `chia/data_layer/data_layer.py`, and optionally allow operators to configure a strict URL allow-list for their DataLayer mirrors.

### Proof of Concept
1. Attacker creates a DataLayer store and calls the wallet RPC `dl_new_mirror` (or CLI `chia data add_mirror`) with `urls=["http://169.254.169.254/latest/meta-data/"]` or `urls=["http://127.0.0.1:8562/some/internal/rpc"]`, per `DLNewMirror`/`add_mirror` request paths: [8](#0-7) [9](#0-8) 
2. Victim node subscribes to the attacker's store id (`subscribe` RPC), a normal, unprivileged DataLayer client action.
3. Victim's `periodically_manage_data()` loop calls `update_subscription()` → `update_subscriptions_from_wallet()`, ingesting the attacker's malicious mirror URL as an available server.
4. On the next sync cycle needing generations, `fetch_and_validate()` selects that server and calls `http_download()`, causing the victim's DataLayer process to issue an HTTP GET to the attacker-chosen internal/metadata URL, confirming SSRF.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
