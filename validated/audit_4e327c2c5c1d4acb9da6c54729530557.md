### Title
Integer overflow in transaction funding check permits signing consensus-invalid Bitcoin transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` calculates `input_sat`, `payment_sat`, and `payment_sat + needed_fee` using unchecked `u64` arithmetic. A caller-controlled payment amount near `u64::MAX` causes the funding comparison to wrap, allowing a transaction whose declared outputs vastly exceed its represented inputs to pass validation and be passed to the FROST transaction-signing machine. [1](#0-0) 

### Finding Description
`SignableTransaction::new` only rejects individual payments below `DUST`; it does not reject payments exceeding Bitcoin's maximum money supply and does not use checked arithmetic when summing payments. [2](#0-1) 

The insufficient-funds check is:

```rust
if input_sat < (payment_sat + needed_fee) {
```

Both `payment_sat` and `payment_sat + needed_fee` can wrap when integer overflow checks are disabled. For example, a single payment of `u64::MAX` makes `payment_sat + needed_fee` equal `needed_fee - 1`, so any ordinary nonzero input amount passes the check. [3](#0-2) 

The parsed `ReceivedOutput` path also accepts a consensus-encoded `TxOut` amount and outpoint without validating that the amount represents a plausibly spendable Bitcoin output. [4](#0-3) 

Once constructed, `SignableTransaction::multisig` creates per-input Schnorr signing machines, and `TransactionSignMachine::sign` commits each input and all prevouts through BIP-341 key-spend sighashes. [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who can influence the payment list or otherwise cause this constructor to be invoked with crafted transaction data can cause the threshold wallet to produce valid signatures over a transaction with outputs greater than its represented inputs. The resulting transaction should be consensus-invalid, limiting direct fund theft, but the wallet still signs an unintended and malformed transaction after its funding policy check was bypassed. [7](#0-6) 

### Likelihood Explanation
The attack requires the attacker to influence `payments` or the surrounding transaction plan and an integer-overflow-enabled build. No cryptographic weakness, malformed curve point, or malformed signature is needed; one payment amount of `u64::MAX` is sufficient to wrap the funding comparison. [8](#0-7) 

### Recommendation
Use checked arithmetic for all monetary accounting in `SignableTransaction::new` and reject overflow:

```rust
let input_sat = inputs
    .iter()
    .try_fold(0u64, |acc, input| acc.checked_add(input.output.value.to_sat()))
    .ok_or(TransactionError::AmountOverflow)?;

let payment_sat = payments
    .iter()
    .try_fold(0u64, |acc, payment| acc.checked_add(payment.1))
    .ok_or(TransactionError::AmountOverflow)?;

let required = payment_sat
    .checked_add(needed_fee)
    .ok_or(TransactionError::AmountOverflow)?;
```

The same checked arithmetic should be applied to `fee_per_vbyte * vbytes` and `payment_sat + fee_with_change`, and payment/output amounts should be checked against Bitcoin's `MAX_MONEY` bound before transaction construction. [9](#0-8) 

### Proof of Concept
Conceptual reproducer, assuming integer overflow checks are disabled:

```rust
let real_input = ReceivedOutput {
    // An outpoint and P2TR output controlled by the multisig.
    offset: Scalar::ZERO,
    output: TxOut {
        value: Amount::from_sat(100_000),
        script_pubkey: multisig_script.clone(),
    },
    outpoint,
};

// This is the public/attacker-influenced transaction data to sign.
let payments = [(attacker_script, u64::MAX)];

let signable = SignableTransaction::new(
    vec![real_input],
    &payments,
    None,
    None,
    100,
).expect("funding check wrapped and accepted u64::MAX payment");

// `signable` contains an output for u64::MAX despite only 100_000 sats
// of represented input value. Calling `multisig(keys)` and completing the
// FROST signing protocol produces signatures over this malformed transaction.
```

The bypass occurs because `payment_sat` is `u64::MAX`, so `payment_sat + needed_fee` wraps to a small value before the comparison against `input_sat`. [10](#0-9)
