### Title
Webhook shop-identity spoofing via HMAC that signs only the request body, not the `X-Shopify-Shop-Domain` header - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` (and the underlying `PayloadVerification#hmac_valid?`) authenticates a webhook solely by HMAC-signing `request.raw_post`. The shop identity used by every generated job (`AppUninstalledJob`, `ShopRedactJob`, generic `WebhookJob`, etc.) is taken from the separate, **unsigned** `X-Shopify-Shop-Domain` header. Because the header is outside the signed data, a party that can obtain one validly-signed webhook body/HMAC pair (e.g., for a shop they themselves installed the app on) can replay that exact body+HMAC while substituting an arbitrary shop domain in the header, and the app will process it as if it belonged to a different shop.

### Finding Description
`ShopifyApp::WebhookVerification` is the module the gem documents and generates for verifying inbound Shopify webhooks: [1](#0-0) 

`verify_request` only calls `hmac_valid?(request.raw_post)`; it never touches or authenticates `shop_domain`: [2](#0-1) 

`shop_domain` is defined right in the same concern as a simple, unauthenticated header read: [3](#0-2) 

This is precisely the same bug class described in the report: a value (`newInstance` in the SGX report; here, `shop_domain`) that determines a security-relevant identity is **not included in the signed hash**, so it can be freely set by whoever sends the HTTP request, even though the accompanying signature is valid.

Every generator-produced job dispatches on that unauthenticated value and uses it to select the tenant/shop record to operate on: [4](#0-3) [5](#0-4) [6](#0-5) 

And the gem's own custom-controller documentation reinforces this exact usage pattern (`shop_domain: shop_domain` passed straight from the header into job processing): [7](#0-6) 

The built-in `ShopifyApp::WebhooksController` follows the identical flow, verifying HMAC via the `WebhookVerification` concern and then handing off `headers` (including the shop-domain header) to `ShopifyAPI::Webhooks::Registry.process`, which derives `shop:` from those headers for dispatch to `handle(topic:, shop:, body:, ...)`: [8](#0-7) 

Test fixtures confirm the shop domain is delivered purely as a header, independent of the signed body: [9](#0-8) 

### Impact Explanation
Because the app's webhook secret is shared across all shops that install the app (a single app-level `client_secret`), any merchant who installs the app on their own shop can legitimately trigger webhook deliveries whose body+HMAC pair is valid under that shared secret. If that request (or its body/HMAC pair) is then replayed with the `X-Shopify-Shop-Domain` header altered to point at a different, victim shop that also has the app installed, `hmac_valid?` still returns true (it never inspects the header), and the downstream job will look up and act on the **victim's** `Shop` record using data that actually originated from the attacker's own shop/webhook body. Depending on the specific webhook/job wired up by the app developer (following the gem's own generated templates), this enables:
- Cross-shop data corruption/injection (e.g., writing attacker-controlled webhook payload content against a victim shop's record).
- Triggering privacy-sensitive jobs (`shop_redact`, `customers_redact`, `app_uninstalled`) against the wrong shop, causing unauthorized destruction of a victim shop's app data/session (`shop.destroy` in the generated `AppUninstalledJob`/`ShopRedactJob`).
- Any custom "shop_domain"-scoped business logic being executed under an attacker-chosen shop identity.

This satisfies the "cross-shop access with an accepted forged signed request" criterion: the signature is valid (correctly derived from real Shopify traffic for the attacker's own shop), but the security-critical shop identifier riding alongside it is not covered by that signature and is fully attacker-controlled.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that:
1. Allows self-serve installation by arbitrary merchants (the norm for public Shopify apps), giving an attacker legitimate access to generate valid signed webhook bodies for their own shop.
2. Uses the gem's own recommended/generated job templates or documented custom-controller pattern, all of which key shop lookup purely off the unauthenticated header value.

No secret leakage, insider access, or dependency bug is required — only normal use of the app as an installing merchant plus the ability to send/replay an HTTP request with a modified header, which is fully within an "unrelated merchant" threat model.

### Recommendation
- Include the shop identity in the data that is HMAC-verified, e.g., verify against `X-Shopify-Shop-Domain` + body (or derive/validate the shop strictly from the signed webhook payload's own `shop_domain`/`myshopify_domain` field rather than the header) so the header cannot be forged independently of the signature.
- Alternatively/additionally, cross-check that the header-derived shop domain matches a value embedded in the signed body itself before using it to scope any database or destructive operation, and update the generator templates (`webhook_job.rb.tt`, `app_uninstalled_job.rb.tt`, privacy job templates) and the documented `WebhookVerification` usage pattern accordingly.
- Document explicitly that `shop_domain`/`X-Shopify-Shop-Domain` is **not** authenticated by `hmac_valid?` so app developers relying on `ShopifyApp::WebhookVerification` are aware they must not trust it as tenant-scoping input without further validation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes to a webhook topic the app handles (e.g., `shop/update` or any topic wired to a job following the generated template pattern).
2. Shopify delivers a legitimate webhook: `POST /webhooks/...` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared secret) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact request (e.g., via a local proxy they control, since it is their own traffic) and replays it to the same endpoint, changing only the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged.
4. `ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(B)`, which succeeds because `H` is still a valid HMAC of unmodified body `B` — the header is never part of the check (`app/controllers/shopify_app/webhooks_controller.rb`, `lib/shopify_app/controller_concerns/webhook_verification.rb`, `lib/shopify_app/controller_concerns/payload_verification.rb`).
5. The job (e.g., `AppUninstalledJob`, `ShopRedactJob`, or a generated `webhook_job.rb.tt`) is invoked with `shop_domain: "victim-shop.myshopify.com"` and performs its lookup/action (`Shop.find_by(shopify_domain: shop_domain)` then e.g. `shop.destroy`) against the victim shop, using attacker-supplied/attacker-shop-originated webhook content, despite Shopify never having sent this webhook for the victim shop.

Note: I could not verify from this repo alone what shop value `ShopifyAPI::Webhooks::Request#shop` derives internally (that class lives in the `shopify_api` gem dependency, not in this repo); the analysis above relies on the header (`X-Shopify-Shop-Domain`) being the source of shop identity as shown by the test fixtures and the gem's own documented custom-controller pattern, which is unambiguously unauthenticated in this repo's code.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```markdown
If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```

The module skips the `verify_authenticity_token` before_action and adds an action to verify that the webhook came from Shopify. You can now add a post route to your application, pointing to the controller and action to accept the webhook data from Shopify.
