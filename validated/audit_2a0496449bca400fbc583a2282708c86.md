### Title
Attacker-controlled `.gitattributes` can defeat Desktop's binary-diff classification, causing silent corruption during partial commits - (File: `app/src/lib/git/diff.ts`, `app/src/lib/diff-parser.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The Sherlock report's broken invariant is: *a weak, spoofable heuristic is used to classify an attacker-influenced object's type, and the wrong classification is then fed into logic that assumes the wrong shape, corrupting behavior without any additional validation.* The closest verified analog in this codebase is Desktop's binary/text classification for diffs, which is derived entirely from parsing `git diff` output and `.gitattributes`-driven detection — both of which live inside a cloned/fetched repository and are therefore attacker controlled. Desktop then uses this classification, unguarded by any independent content check, to decide whether to run its line-oriented partial-commit patch reconstruction (`formatPatch`) against file bytes.

### Finding Description
`DiffParser.parseDiffHeader()` determines whether a diff is binary solely by scanning for the literal marker line `Binary files ... differ` in the textual `git diff` output: [1](#0-0) 

This `isBinary` flag then dictates whether Desktop treats the file as `DiffType.Binary` (opaque, "download to view" only) or `DiffType.Text` (renderable and eligible for line-level selection): [2](#0-1) 

Whether git emits the `Binary files ... differ` marker at all is not a pure content-sniffing decision — it is overridable per-path via `.gitattributes` (`text`/`-text`/`binary` attributes, custom `diff=` drivers). Desktop's separate binary-detection helper for merge/status purposes, `getFilesUsingBinaryMergeDriver`, explicitly relies on `git check-attr ... merge` output, i.e. on attributes read from the repository content itself: [3](#0-2) 

Once a diff is classified as `DiffType.Text`, `applyPatchToIndex` only guards against the enum values `Binary`, `Submodule`, `Image`, and `Unrenderable` — there is no independent re-check of the actual byte content: [4](#0-3) 

The patch is then built by `formatPatch`, which operates purely on line-split text (`hunk.lines`, string concatenation with `\n`), assuming the file decomposes cleanly into text lines: [5](#0-4) 

Because the underlying diff content originates from a `git diff` invocation whose binary/text behavior a hostile repository (via `.gitattributes` committed in the cloned/fetched tree) can force to "text", a file that is actually binary can be walked through the entire text-diff/partial-commit pipeline with no independent validation that the content is safe to reconstruct line-by-line.

### Impact Explanation
If an attacker crafts a repository containing a `.gitattributes` entry that forces a binary-content file to be treated as text (e.g. `path/to/file -diff` reversed, or a custom `diff` filter that alters output), a victim who clones/fetches that repo and performs a **partial commit** (selecting only some hunks/lines in the Changes view) will have `formatPatch` reconstruct a patch from Desktop's line-based model of that content and apply it via `git apply --cached`. Any string/encoding assumptions baked into the diff parser and patch formatter (line splitting on `\n`, UTF-8 string handling, `\ No newline at end of file` markers) can silently diverge from the true byte content of the file, so the bytes that end up staged/committed differ from what the user believed they selected — i.e., "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories.

### Likelihood Explanation
Exploitation only requires the victim to clone or fetch an attacker-authored repository (a normal, unprivileged workflow) and make any partial/line-level commit on a file whose type classification was manipulated via `.gitattributes` — no local access, no admin rights, and no unnatural user steps are needed. The attacker does not need to compromise the user's machine; they only need to control repository content, matching the same attacker model as the original Convex "stash token" bug (attacker controls the object being classified, not the classifying code).

### Recommendation
Do not rely solely on the `git diff` textual "Binary files ... differ" marker (which is influenced by repository-controlled `.gitattributes`) to gate the partial-commit code path. Independently sniff the actual file bytes (e.g., NUL-byte/entropy check on the real working-directory content) before allowing `formatPatch`/`applyPatchToIndex` to perform line-based reconstruction, and refuse partial-commit patch application whenever this independent check disagrees with git's reported classification, surfacing an explicit error to the user instead of silently applying a possibly-corrupting patch.

### Proof of Concept
Not independently executable from the index alone (would require running Desktop end-to-end against a crafted clone), but the code path is fully traceable:
1. Attacker publishes a repo with a binary file (e.g., embedding NUL bytes) and a `.gitattributes` rule forcing git to treat it as text for diffing.
2. Victim clones the repo in Desktop and modifies the file, producing a non-`Binary files differ` diff, so `DiffParser.parseDiffHeader` returns `{ isBinary: false }` [1](#0-0) , and `convertDiff` returns `DiffType.Text` [6](#0-5) .
3. Victim selects only a subset of lines/hunks to commit in the Changes UI.
4. `applyPatchToIndex` passes the `DiffType.Text` check unmodified [4](#0-3)  and `formatPatch` reconstructs a patch from the line-oriented diff model [5](#0-4) , which is applied via `git apply --cached`, without any confirmation that the reconstruction faithfully represents the true binary content.

**Uncertainty:** I could not fully verify from the index alone whether git's own `apply --cached` step would itself reject a malformed/inconsistent binary-as-text patch in all cases (this depends on the exact byte content and git version behavior), nor did I find a Desktop-side re-validation step after `git apply` succeeds. Confirming the precise corrupted-byte-count and whether `git apply` errors out in specific crafted inputs would require running the full pipeline end-to-end, which is outside what static code inspection can determine.

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
```
