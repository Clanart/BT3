## Analysis

The external report's root cause pattern is: a function performs a multi-step operation that includes an unconditional external call (harvest → withdraw from `market`), and when that external call fails, the code does not account for partial state already mutated before the call, causing funds to be lost/frozen. The Cosmos EVM analog is in the `x/erc20` module's IBC refund path.

### Title
Refund/timeout ERC20 re-conversion silently swallows EVM transfer failure after coins are already escrowed, permanently freezing user refunds - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
When an IBC transfer of a coin backed by a "native ERC20" token pair fails (error acknowledgement) or times out, `x/erc20` refunds the sender in Cosmos Coin form and then attempts to re-wrap those coins back into the native ERC20 representation via `ConvertCoinNativeERC20`. That function first escrows the sender's coins into the `erc20` module account, then calls the ERC20 contract's `transfer` via the EVM to release the equivalent ERC20 tokens, and only afterwards burns the escrowed coins. If the EVM `transfer` call fails for any reason (paused/blacklisted/self-destructed ERC20 contract, insufficient module-escrowed ERC20 balance, non-standard return data, etc.), the caller `ConvertCoinToERC20FromPacket` deliberately swallows the error and returns `nil`, causing the whole IBC callback (and therefore the enclosing `MsgTimeout`/`MsgAcknowledgement` transaction) to be treated as successful and committed. The already-escrowed coins are never burned nor returned to the sender, leaving them permanently stuck in the module account.

### Finding Description
The vulnerable flow: [1](#0-0) 

Step-by-step:
1. `x/erc20/ibc_middleware.go`'s `OnAcknowledgementPacket`/`OnTimeoutPacket` first invoke the underlying transfer app, which refunds the sender's coins on this chain [2](#0-1) , then call `im.keeper.OnAcknowledgementPacket`/`OnTimeoutPacket`, which delegate to `ConvertCoinToERC20FromPacket`.
2. For `pair.IsNativeERC20()`, `ConvertCoinNativeERC20` is invoked: it escrows the sender's just-refunded coins to the `erc20` module account with `SendCoinsFromAccountToModule` **before** attempting the EVM transfer: [3](#0-2) 
3. If the EVM `transfer` call errors, the function returns immediately — the coins remain escrowed and are never burned: [4](#0-3) 
4. The caller catches this error but swallows it and returns `nil` (treating it as a recoverable, non-fatal condition where "the user receives the corresponding bank token instead"): [5](#0-4) 

The comment's claim that "the user receives the corresponding bank token instead" is false: by the time the error is caught, the bank token has already been moved out of the user's account into the `erc20` module account by step 2, and the failure path never reverses that transfer or credits the user in any form. Because the error is swallowed (`return nil`), the enclosing SDK message (`MsgTimeout`/`MsgAcknowledgement`) is not aborted, so normal atomic-message-rollback protection does not apply — the partial escrow permanently commits.

### Impact Explanation
This directly matches the "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... escrowed assets ... token-pair-backed balances" impact category. Any user whose IBC transfer of a native-ERC20-backed coin times out or receives an error acknowledgement can have their refund permanently trapped in the `erc20` module account with no burn, no ERC20 credit, and no recovery path, whenever the underlying ERC20 contract's `transfer` call fails for any reason (pause, blacklist, insufficient module-escrowed balance due to prior conversions, or a non-standard/self-destructed ERC20 implementation). This is a deterministic, unprivileged-triggerable loss of user funds baked into ordinary IBC refund/timeout handling.

### Likelihood Explanation
Triggering this does not require any privileged action on the Cosmos EVM chain itself — only that an IBC transfer for a native-ERC20 token pair ends in a timeout or error acknowledgement (a routine occurrence in cross-chain messaging, e.g. relayer delay, receiving-chain rejection, or an external ERC20 admin pausing/blacklisting, exactly mirroring the "market paused" trigger in the source report) while the underlying registered ERC20 contract cannot fulfill the `transfer` call. Given IBC timeouts/failed acks are a normal part of production operation, and native-ERC20 token pairs are an explicit supported feature (`pair.IsNativeERC20()`), this is readily reachable in normal usage.

### Recommendation
`ConvertCoinNativeERC20` should not perform the destructive escrow step until it is certain the EVM `transfer` will succeed, or it should wrap all three steps (escrow, EVM transfer, burn) in a `ctx.CacheContext()` that is only committed on full success — mirroring the pattern already used elsewhere in the codebase (e.g. `x/ibc/callbacks/keeper/keeper.go`'s `cachedCtx, writeFn := ctx.CacheContext()`). Additionally, `ConvertCoinToERC20FromPacket` must not swallow the error as an unconditional `return nil`; if it intends "user keeps the bank token," it must first fully unwind the escrow performed in `ConvertCoinNativeERC20` before returning success.

### Proof of Concept
1. Register a native ERC20 token pair for an `ERC20Pausable`-style contract (e.g. `contracts/solidity/ERC20MinterBurnerDecimals.sol`, which exposes `pause()`/`unpause()` gated by `PAUSER_ROLE`) [6](#0-5) .
2. A user converts some ERC20 tokens into the Cosmos coin form and sends them out via IBC transfer (escrowing the ERC20 tokens in the `erc20` module account, per `convertERC20IntoCoinsForNativeToken`) [7](#0-6) .
3. Before the packet is acknowledged/times out, the ERC20 contract owner calls `pause()`.
4. The IBC packet times out (or the counterparty returns an error ack). `OnTimeoutPacket`/`OnAcknowledgementPacket` refund the sender in Coin form, then attempt `ConvertCoinNativeERC20`, which escrows the coins to the `erc20` module account and then calls `transfer` on the paused ERC20 contract — reverting.
5. `ConvertCoinToERC20FromPacket` swallows this error and returns `nil`; the `MsgTimeout`/`MsgAcknowledgement` transaction succeeds and commits.
6. Verify: the sender's bank balance for that denom is zero, the `erc20` module account holds the escrowed coins, and the sender's ERC20 balance is unchanged — funds are permanently stuck with no burn and no user credit.

// ConvertCoinToERC20FromPacket converts the IBC coin to ERC20 after refunding the sender
// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}
	}

	return nil

// OnTimeoutPacket implements the IBCModule interface.
// It refunds the token transferred and then automatically converts the
// Cosmos Coin to their ERC20 token representation.
func (im IBCMiddleware) OnTimeoutPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) error {
	var data transfertypes.FungibleTokenPacketData
	if err := transfertypes.ModuleCdc.UnmarshalJSON(packet.GetData(), &data); err != nil {
		return errorsmod.Wrapf(errortypes.ErrUnknownRequest, "cannot unmarshal ICS-20 transfer packet data: %s", err.Error())
	}

	if err := im.Module.OnTimeoutPacket(ctx, channelVersion, packet, relayer); err != nil {
		return err
	}

	return im.keeper.OnTimeoutPacket(ctx, packet, data)
