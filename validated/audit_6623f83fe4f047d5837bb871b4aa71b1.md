### Title
Cached FROST preprocess is reused for every `share`/`complete` call under the same context, enabling nonce reuse and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The GitLab bug class (a second authentication/verification factor bypassed through an alternate path) maps onto Serai's FROST signing protocol: the one-time-use guarantee for preprocesses/nonces is bypassed because the coordinator deterministically regenerates the identical nonce pair from a database-cached seed on every call, and never invalidates the cache after use.

### Finding Description
`SigningProtocol::preprocess_internal` stores the FROST preprocess as a 32-byte ChaCha20 seed in `CachedPreprocesses`, keyed by `context` (e.g., `(b"DkgConfirmer", attempt)`). If an entry exists, no new seed is generated; `AlgorithmSignMachine::from_cache` re-derives the exact same nonces via `seeded_preprocess` (`crypto/frost/src/sign.rs`). Both the signing path (`share_internal`, line 156: `self.preprocess_internal(participants).0`) and `complete` (line 321-324, which calls `share_internal` again to rebuild the machine) reload the same seed. The FROST spec and Serai's own docs state a cached preprocess MUST be used only once, and that the preprocess "must be deleted" after `from_cache` (`crypto/frost/src/sign.rs:217-219`, `spec/cryptography/FROST.md:51-55`). No code deletes or rotates `CachedPreprocesses` after `sign` completes — every `share`/`complete` invocation for the same `attempt` reuses identical nonces `(d, e)`.

A FROST share has the form `s_i = d + ρ_i·e + λ·x·c_i`, where `ρ_i` is the binding factor derived from the message hash and the submitted preprocess set (`sign.rs:362-395`), `c_i` the challenge, and `x` the secret share. Since `d` and `e` are fixed by the cached seed, an attacker who collects shares produced under the same context but different preprocess sets/messages obtains linear equations in the three unknowns `d`, `e`, `λx`. Three distinct shares under the same cached preprocess suffice to solve for the validator's secret share `x`.

### Impact Explanation
Recovery of a validator's FROST secret share for the MuSig-aggregated tributary signing key. Combined with the threshold structure, repeated compromise degrades the security of all signatures produced by the set; a recovered share lets an attacker forge that participant's contribution to any future `set_keys` confirmation signed under the same attempt context, or combine shares toward full key recovery across compromised validators.

### Likelihood Explanation
The same cached seed is reused whenever `share` or `complete` is invoked again for the same `(b"DkgConfirmer", attempt)` context. `share` is driven by externally supplied `preprocesses` and `key_pair` values; `ρ` varies with the preprocess set and message, so each distinct invocation yields a distinct linear equation rather than an identical share. Whether the surrounding protocol permits multiple share/complete rounds per attempt with differing inputs was not fully verifiable within the indexed `handle.rs` call sites, but the cache design itself violates the documented single-use invariant unconditionally — even a retry after `FrostError::InvalidShare` reuses the nonces.

### Recommendation
Delete (or overwrite) the `CachedPreprocesses` entry the first time `share_internal`/`sign` runs for a context, and make subsequent calls for that context regenerate a fresh seed — or explicitly refuse to sign twice under one context. At minimum, track a "spent" flag alongside the cached seed so `from_cache` cannot reconstruct identical nonces.

### Proof of Concept
1. A validator node processes `share(preprocesses_A, key_pair)` for `attempt = k`, producing share `s_1 = d + ρ_1·e + λ·x·c_1` with nonces derived from the cached seed.
2. A second invocation `share(preprocesses_B, key_pair)` (different peer preprocess set, or different `key_pair` altering `set_keys_message`) calls `preprocess_internal`, hits `CachedPreprocesses::get` for the same context, and re-derives identical `(d, e)`, producing `s_2 = d + ρ_2·e + λ·x·c_2`.
3. A third distinct invocation yields `s_3`. With `ρ_i`, `c_i`, `λ` all publicly computable from the broadcast preprocesses and `group_key`, solve the 3×3 linear system for `d`, `e`, and `λ·x`, hence `x` (λ is known since the participant index is public).
4. The recovered `x` is the validator's secret share of the set's MuSig/FROST key — secret leakage obtainable purely from publicly broadcast shares.

The same pattern applies wherever `SigningProtocol` contexts repeat; only per-context uniqueness of the cached seed prevents it, and nothing enforces single-use.
