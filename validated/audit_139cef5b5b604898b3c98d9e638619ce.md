## Analysis

The external report is about an asset-level admin control (SPL freeze authority) that isn't validated by the protocol, letting a third party permanently freeze a pool's escrow and strand user funds. The Cosmos EVM analog is the `x/erc20` **native ERC20 token pair** IBC refund path, where an externally-owned, pausable/blacklistable ERC20 contract can cause a silent, permanent loss of a user's IBC-refunded coins.

### Title
Silent error-swallowing in IBC timeout/ack ERC20 reconversion permanently strands user coins in the erc20 module account when a native ERC20 token is pausable/blacklistable - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
When an IBC transfer of a "native ERC20" token pair coin times out or receives an error acknowledgement, `x/erc20`'s IBC middleware automatically tries to re-convert the refunded Cosmos coin back into its ERC20 representation via `ConvertCoinNativeERC20`. That function first escrows (debits) the coin from the sender into the module account and only afterwards calls the ERC20 contract to `transfer` (unescrow) tokens to the sender. If that second EVM call fails — which is entirely possible for `TokenPair`s with `Owner = OWNER_EXTERNAL` whose contract implements pause/blacklist logic (a pattern the module explicitly ships and tests, e.g. `ERC20MinterBurnerDecimals.sol`'s `pause()`/`PAUSER_ROLE`) — the caller `ConvertCoinToERC20FromPacket` swallows the error, emits an event, and returns `nil` (success), instead of propagating the failure.

### Finding Description
- `x/erc20/ibc_middleware.go` `OnAcknowledgementPacket`/`OnTimeoutPacket` first invoke the underlying ICS20 transfer app (`im.Module...`), which refunds the sender's coins from the IBC escrow account back to the sender's own bank balance [1](#0-0) .
- They then call `im.keeper.OnAcknowledgementPacket`/`OnTimeoutPacket` on the **same, non-cached** `ctx`, which calls `ConvertCoinToERC20FromPacket` [2](#0-1) .
- `ConvertCoinToERC20FromPacket` calls `ConvertCoinNativeERC20`, and on error, **swallows it**: it emits a telemetry counter/event and `return nil` instead of returning the error [3](#0-2) .
- `ConvertCoinNativeERC20` first debits the sender's just-refunded bank coin into the `erc20` module account (`SendCoinsFromAccountToModule`), and only then attempts to unescrow ERC20 tokens to the sender via `CallEVM(..., "transfer", ...)` [4](#0-3) . If the EVM call reverts or returns `false` (e.g., contract paused or sender/module blacklisted), the function returns an error at this point — but the preceding `SendCoinsFromAccountToModule` state mutation is not rolled back, because there is no `CacheContext`/`Write()` isolation around this call chain.
- Native ERC20 `TokenPair`s can legitimately be owned externally (`Owner = OWNER_EXTERNAL`) per the `erc20.proto` definition [5](#0-4) , and the module's own reference contract demonstrates a pausable ERC20 pattern with an externally-controlled `PAUSER_ROLE` that can halt all transfers at will [6](#0-5) .

### Impact Explanation
Any ordinary IBC transfer of a native-ERC20-backed coin that times out or is acknowledged with an error while the underlying ERC20 contract is paused (or the sender/module address is blacklisted) results in: the sender's refunded coin is debited into the `erc20` module account, no ERC20 tokens are unescrowed to the sender, and the surrounding function reports success. The sender ends up with neither the bank coin nor the ERC20 token — a permanent, unrecoverable loss of user funds triggered by completely ordinary IBC packet-lifecycle processing (timeout/ack), not requiring any malicious validator, relayer, or privileged action. This matches the in-scope Critical impact of permanent freezing/loss of token-pair-backed user balances.

### Likelihood Explanation
Likelihood is realistic: any externally-owned native ERC20 contract with a pause/blacklist capability — a pattern the codebase itself ships and documents (`OWNER_EXTERNAL`, `ERC20MinterBurnerDecimals.sol`'s pauser role) — combined with a normal IBC timeout or error-acknowledgement (which can occur simply due to relayer downtime or receiving-chain rejection, both routine, unprivileged occurrences) is sufficient to trigger the fund loss. No attacker collusion with chain validators is required.

### Recommendation
- In `ConvertCoinToERC20FromPacket` (`x/erc20/keeper/ibc_callbacks.go`), never swallow errors from `ConvertCoinNativeERC20`, or ensure the escrow debit and the unescrow transfer are executed atomically (e.g., via `ctx.CacheContext()` and only `Write()` on full success, or reorder operations to unescrow first and only escrow/burn after confirming the EVM transfer succeeded).
- Alternatively, perform the ERC20 `transfer` call before debiting the sender's bank balance so failures cannot mutate state, and propagate genuine failures back to the sender rather than silently discarding them.

### Proof of Concept
1. Governance (or the pipeline that auto-registers native ERC20 extensions) registers a native ERC20 `TokenPair` for a contract that is `OWNER_EXTERNAL` and implements a `pause()`/blacklist function controlled by its own (non-chain) owner, e.g. deployed from `ERC20MinterBurnerDecimals.sol`.
2. A user converts some ERC20 tokens to the native coin (`ConvertERC20`) and initiates an ICS20 IBC transfer of that coin to another chain.
3. Before the packet is acknowledged, the external contract owner calls `pause()` on the ERC20 contract.
4. The IBC transfer times out (or the receiving chain returns an error acknowledgement).
5. `OnTimeoutPacket`/`OnAcknowledgementPacket` refunds the coin to the sender via the base ICS20 module, then `ConvertCoinToERC20FromPacket` debits that coin into the `erc20` module account and attempts to `transfer` ERC20 tokens back to the sender; the EVM call reverts because the contract is paused.
6. The error is swallowed, the function returns `nil`, and the packet callback commits successfully — the user's coin balance is now permanently zero, with no ERC20 tokens received and no coin refunded.

func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}
