### Title
Recursive precompile calls corrupt the shared `BalanceHandler` checkpoint, desyncing EVM `StateDB` balances from native `x/bank` state - (File: precompiles/common/balance_handler.go)

### Summary
This is the Cosmos EVM analog of the Flayer `ProtectedListings` checkpoint bug: an accounting mechanism relies on a single mutable "checkpoint" value (`prevEventsLen`) to bound the window of state it must reconcile, but that checkpoint can be silently overwritten by a nested/recursive operation before the outer operation finishes using it — producing incorrect derived accounting. Here the checkpoint is not an interest-rate checkpoint but the event-log offset used by the EVM `BalanceHandler` to translate native `x/bank` `coin_spent`/`coin_received` events into `StateDB.AddBalance`/`SubBalance` calls.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())` before a precompile executes, and `AfterBalanceChange` later replays only the events emitted after that index to update the EVM `StateDB` balances: [1](#0-0) [2](#0-1) 

Several stateful precompiles (`distribution`, `erc20`, `gov`, `ics20`, `slashing`) obtain this handler via a `GetBalanceHandler()` accessor rather than creating a fresh instance scoped to each individual `Run()` invocation, meaning the same `*BalanceHandler` (and therefore the same `prevEventsLen` field) can be shared across nested/recursive precompile calls that occur within one EVM call frame (e.g. a contract calling a precompile, which itself triggers another EVM call back into a precompile). When an inner call invokes `BeforeBalanceChange` again, it overwrites `prevEventsLen` with the inner call's starting offset. When the inner call's `AfterBalanceChange` fires, the checkpoint has already advanced past the outer call's own bank events, so events get replayed against the wrong window — either double-applied to `StateDB` or skipped entirely.

This exact defect is described and reproduced in-repo: [3](#0-2) 

The debug precompile used to reproduce it shows the same `Run()` pattern (`BeforeBalanceChange` / `Execute` / `AfterBalanceChange`) used by production precompiles, confirming the checkpoint-then-execute-then-reconcile flow is the shared root cause across all `GetBalanceHandler()`-based precompiles: [4](#0-3) 

By contrast, the `RunNativeAction` path in the common `Precompile` base struct constructs a brand-new `BalanceHandler` per call via `BalanceHandlerFactory.NewBalanceHandler()`, which is the safe pattern: [5](#0-4) 

The precompiles referencing `GetBalanceHandler()` instead of the factory-per-call pattern are the vulnerable surface: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
`BalanceHandler.AfterBalanceChange` directly drives `StateDB.AddBalance`/`SubBalance`: [11](#0-10) 

If the checkpoint is corrupted by re-entrant/nested precompile calls, the EVM-visible balance of an account can diverge from the true `x/bank` balance within the same transaction — e.g., an account's `StateDB` balance failing to reflect a native transfer the precompile performed (funds "disappear" from EVM view while still resident in `x/bank`, or vice versa where `StateDB` credits an amount that was never actually moved in `x/bank`). Because `StateDB` balance is what all subsequent EVM instructions (transfers, `CALL` with value, `balanceOf` reads by other contracts in the same tx) act upon, this can allow duplication of spendable value from the EVM's perspective, or an account being able to spend value not backed by real `x/bank` funds once the state is written back to `x/bank` via `s.cacheCtx.MultiStore().Write()`. This matches the "Critical unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances or EVM balances" impact class.

### Likelihood Explanation
Triggering this requires only an unprivileged user to deploy/call a contract that makes a precompile call which itself, directly or indirectly, results in a second (nested) precompile invocation within the same EVM message call (e.g., a contract calling `gov`/`distribution`/`ics20` precompile from a callback, or a precompile's own execution triggering a reentrant EVM call, as demonstrated by the debug-precompile PoC). No validator/relayer/governance privilege is needed — it is reachable via ordinary transaction/contract flow, satisfying the "unprivileged trigger" requirement.

### Recommendation
Ensure every precompile that mutates native balances constructs a `BalanceHandler` scoped strictly to its own `Run()` invocation (mirroring the `RunNativeAction`/`BalanceHandlerFactory.NewBalanceHandler()` pattern) rather than sharing one instance (or one `prevEventsLen` field) across nested/recursive precompile calls. Alternatively, maintain a stack of checkpoints (push on `BeforeBalanceChange`, pop on `AfterBalanceChange`) so nested calls cannot clobber an outer call's event-window offset, and add an invariant check post-transaction comparing aggregate `x/bank` balance deltas against aggregate `StateDB` balance deltas for all touched accounts.

### Proof of Concept
The repository already contains a reproducing integration test that deploys a caller contract invoking the debug precompile recursively and asserts on the resulting event/balance-update count, explicitly documented as demonstrating the "balance desync between native bank keeper and EVM stateDB": [12](#0-11) 

Note: I was not able to fully inspect the internal bodies of `distribution.go`, `erc20.go`, `gov.go`, `ics20.go`, and `slashing.go` (only their `GetBalanceHandler` reference lines were confirmed via grep) to verify whether each has already been patched to allocate a handler per call; a Devin session with full repository access is recommended to confirm current mitigation status of each production precompile before treating this as unpatched.

func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}
