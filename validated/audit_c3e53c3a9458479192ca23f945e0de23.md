### Title
Unauthorized freeze of an object-hosted code package — anyone can permanently lock another account's upgradeable package via `object_code_deployment::freeze_code_object` - (File: `aptos-move/framework/aptos-framework/sources/object_code_deployment.move`)

### Summary
`object_code_deployment::freeze_code_object` forwards the caller-supplied `publisher` signer and `code_object` straight to `code::freeze_code_object` without first verifying that `publisher` owns `code_object`, unlike the sibling `upgrade` entry function which explicitly checks `object::is_owner` before doing anything else. [1](#0-0) 

### Finding Description
`upgrade()` in `object_code_deployment.move` enforces ownership before mutating the code object:
```
assert!(
    object::is_owner(code_object, publisher_address),
    error::permission_denied(ENOT_CODE_OBJECT_OWNER),
);
``` [2](#0-1) 

`freeze_code_object()`, by contrast, does no such check at this layer — it simply calls `code::freeze_code_object(publisher, code_object)`: [3](#0-2) 

The delegate, `code::freeze_code_object`, is documented in the module spec as requiring ownership (`aborts_if !object::is_owner(code_object, signer::address_of(publisher));`), and `code.move` declares an `ENOT_PACKAGE_OWNER` error constant apparently reserved for this purpose: [4](#0-3) [5](#0-4) 

However, a targeted grep across `code.move` for `is_owner`, `assert_is_owner`, and `ENOT_PACKAGE_OWNER` returns **no matches anywhere in the file**, meaning the constant is declared but never asserted, and no ownership check exists in the actual `freeze_code_object` implementation that mutates `PackageRegistry.packages[*].upgrade_policy` to `upgrade_policy_immutable()`: [6](#0-5) 

Because `Object<PackageRegistry>` handles can be constructed by anyone who knows the target address (e.g., via `object::address_to_object`), and no signer-derived authority (such as the `ExtendRef`-based signer used in `upgrade`) is required to reach the mutation, any account can invoke `object_code_deployment::freeze_code_object` against an arbitrary victim's code object and successfully set its packages' `upgrade_policy` to `immutable`.

### Impact Explanation
This is a code-object ownership/freeze-authority violation with mainnet relevance: an unprivileged, non-owning account can permanently and irreversibly freeze another account's deployed package (`freeze_code_object` explicitly has "no unfreeze function... once modules are marked immutable, they cannot be made mutable again", per the module doc comment). This is a permanent denial-of-service against the legitimate owner's ability to ever upgrade that code object again — directly analogous to the external report's "indefinite block" bug class, but here achieved by an entirely unauthorized third party rather than a legitimate-but-malicious co-signer. It matches the Publish Impact Gate's "Unauthorized module publish, upgrade, freeze, code-object ownership change" category.

### Likelihood Explanation
High likelihood if confirmed: the attack requires only knowledge of a public, on-chain object address (trivially discoverable) and a single permissionless entry-function call (`freeze_code_object`) with no special privileges, tokens, or race conditions required.

### Recommendation
Add an explicit ownership check in `object_code_deployment::freeze_code_object` (mirroring `upgrade`'s pattern) before calling into `code::freeze_code_object`:
```
assert!(
    object::is_owner(code_object, signer::address_of(publisher)),
    error::permission_denied(ENOT_CODE_OBJECT_OWNER),
);
```
Additionally, wire the existing `ENOT_PACKAGE_OWNER` constant into `code::freeze_code_object` itself (asserting `object::is_owner`) so the guarantee is enforced defense-in-depth at both the object-deployment and code-registry layers, consistent with what `code.spec.move` already documents as an invariant.

### Proof of Concept
1. Victim deploys a package to an object via `object_code_deployment::publish`, creating `code_object` at address `A` with `upgrade_policy = compat` (or `arbitrary`), owned by victim.
2. Attacker (any unrelated account) calls:
   ```
   object_code_deployment::freeze_code_object(attacker_signer, object::address_to_object<PackageRegistry>(A))
   ```
3. Because neither `object_code_deployment::freeze_code_object` nor `code::freeze_code_object` verifies `object::is_owner(code_object, attacker_address)`, the call succeeds, setting all packages at `A` to `upgrade_policy_immutable()`.
4. Victim can no longer upgrade code at `A` — permanently, since there is no unfreeze path — a full and irreversible denial of the owner's upgrade authority caused solely by an unauthorized third party.
