### Title
`aptos move verify-package` never compares on-chain bytecode, only self-declared source metadata - (File: aptos-move/cli/src/stored_package.rs)

### Summary
The CLI's package-verification flow, documented as "Downloads a package and verifies the bytecode... verifies the bytecode matches a local compilation of the Move code," does not actually fetch or compare the deployed bytecode. It only checks a `PackageMetadata` struct whose fields (source text, manifest, `source_digest`) are attacker-supplied at publish time and are never cross-validated on-chain against the compiled module bytes.

### Finding Description
On-chain, `code::publish_package` (`aptos-move/framework/aptos-framework/sources/code.move:159-231`) accepts a `PackageMetadata` argument containing `source_digest`, `manifest`, and per-module `source`/`source_map` fields that are pure, unverified byte blobs (see `code.move:27-65`). The native publish path (`native_request_publish` in `aptos-move/framework/natives/src/code.rs:264-360` and `validate_publish_request` in `aptos-move/aptos-vm/src/aptos_vm.rs:1804-1865`) verifies module *names*, *dependencies*, bytecode compatibility/compat-policy, natives, resource groups and events — but never checks that `PackageMetadata.source`/`source_digest`/`manifest` are consistent with the actual bytecode bundle. This is by design: the metadata is documentation, not consensus-checked input.

The CLI's `verify-package` command is supposed to be the tool that closes this gap for end users, by recompiling locally and diffing against the deployed artifact. However:
- `VerifyPackage::execute` calls `CachedPackageRegistry::create(client, self.account, false)` with `with_bytecode = false` (`commands.rs:2121`), so `stored_package.rs`'s `bytecode: BTreeMap<String, Vec<u8>>` is left empty (`stored_package.rs:52-66`).
- `package.verify(&compiled_metadata)?` (`commands.rs:2137`) only calls `CachedPackageMetadata::verify`, which compares `PackageMetadata` struct fields directly — `name`, `deps`, `modules` (name/source/source_map/extension), `manifest`, `upgrade_policy`, `extension`, `source_digest` (`stored_package.rs:193-241`). None of these branches ever call `get_bytecode` or fetch `get_account_module` to diff actual bytecode bytes.

Because `source_digest` is computed purely from the locally declared source files (`third_party/move/tools/move-package/src/resolution/digest.rs:12-52`) and is submitted as-is inside `PackageMetadata` at publish time, an attacker can publish a package where the embedded `source`/`manifest`/`source_digest` fields describe innocuous Move code while the actual bytecode bundle performs different, malicious logic. A user (or auditor) running `aptos move verify-package` against the malicious account, using source obtained out-of-band (e.g., a GitHub repo matching the fabricated `source`/`manifest`), will get "Successfully verified source of package" even though the executing bytecode does not correspond to that source at all.

### Impact Explanation
This breaks the exact "verified bytes vs. committed module bytes" invariant called out by the impact gate: `verify-package` is the primary Aptos-native tool users rely on to confirm that an on-chain package matches its publicly reviewed source. A false "verified" result lets a malicious or compromised package operator publish arbitrary bytecode (subject only to the bytecode/type verifier and compatibility rules — not to any content match) while presenting a benign, git-auditable source tree that the CLI will happily "verify" as matching. This directly enables silent code substitution/backdoors in production contracts that downstream integrators, auditors, or governance reviewers believe they have checked.

### Likelihood Explanation
High. Exploitation requires no special privilege beyond being the ordinary package publisher/upgrader (already the owner of the account or code object) and does not need to defeat the Move bytecode verifier, dependency checks, or the compatibility checker — the mismatch happens in the CLI's local verification against the `PackageMetadata`, not in consensus. Any user who runs `aptos move verify-package` as their sole verification step (which the tool's own documentation implies is sufficient) can be misled with a single crafted publish/upgrade transaction; `with_bytecode` is hardcoded to `false` in `VerifyPackage::execute`, so this is not a rare misconfiguration but the tool's default and only behavior.

### Recommendation
- Change `VerifyPackage::execute` to call `CachedPackageRegistry::create(client, self.account, true)` so bytecode is fetched, and add a bytecode-comparison step: recompile the local package (already done via `BuiltPackage::build_to`), extract its compiled module bytes, and diff them byte-for-byte (or by hash) against `CachedPackageRegistry::get_bytecode` for every module in the package before reporting success.
- Update `CachedPackageMetadata::verify` to require and check this bytecode equality in addition to the existing metadata-field comparisons, and fail loudly (rather than silently omitting the check) if bytecode could not be retrieved.
- Consider also documenting/asserting that `source_digest`/`source`/`manifest` are informational only and are not checked on-chain, so integrators do not conflate a successful publish with a source/bytecode-consistency guarantee.

### Proof of Concept
1. Attacker builds and publishes a package via `code::publish_package_txn` (or `object_code_deployment::publish`) where the `PackageMetadata.modules[i].source` (gzipped) and `manifest` describe a benign module (e.g., a simple counter) and `source_digest` is computed to match that fabricated source, but the actual `code: vector<vector<u8>>` bytecode bundle implements different, malicious logic (e.g., a hidden drain function). Nothing in `validate_publish_request` (`aptos_vm.rs:1804-1865`) or `code::publish_package` (`code.move:159-231`) checks source/bytecode correspondence, so the transaction succeeds.
2. Attacker publishes the fabricated benign source as a public repository matching the embedded manifest/source metadata.
3. A user/auditor runs `aptos move verify-package --account <attacker_addr>` against a local checkout of that public repository.
4. `VerifyPackage::execute` (`commands.rs:2104-2140`) builds the local package, retrieves `CachedPackageRegistry` with `with_bytecode=false`, and calls `package.verify(&compiled_metadata)`, which only diffs `PackageMetadata` struct fields — all of which match because they were crafted to match. The tool prints `"Successfully verified source of package"` despite the deployed bytecode being entirely different from the reviewed source. [4](#0-3) [5](#0-4) [6](#0-5)

    /// Publishes a package at the given signer's address. The caller must provide package metadata describing the

    public fun publish_package(owner: &signer, pack: PackageMetadata, code: vector<vector<u8>>) acquires PackageRegistry {
        // Disallow incompatible upgrade mode. Governance can decide later if this should be reconsidered.
        assert!(
            pack.upgrade_policy.policy > upgrade_policy_arbitrary().policy,
            error::invalid_argument(EINCOMPATIBLE_POLICY_DISABLED),
        );

        let addr = signer::address_of(owner);
        if (!exists<PackageRegistry>(addr)) {
            move_to(owner, PackageRegistry { packages: vector::empty() })
        };

        // Checks for valid dependencies to other packages
        let allowed_deps = check_dependencies(addr, &pack);

        // Check package against conflicts
        // To avoid prover compiler error on spec
        // the package need to be an immutable variable
        let module_names = get_module_names(&pack);

        // Record, per module in this package, the object's transitive root owner at (re)publish, so
        // lazy self-init can detect a later transfer of the object or an ancestor since that module
        // was published (see `init::internal_maybe_initialize`). Objects only; feature-gated.
        if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
            let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
            module_names.for_each_ref(|name| {
                init::record_deploy_owner(addr, *name.bytes(), owner);
            });
        };
        let package_immutable = &borrow_global<PackageRegistry>(addr).packages;
        let len = package_immutable.length();
        let index = len;
        let upgrade_number = 0;
        package_immutable.enumerate_ref(|i, old| {
            let old: &PackageMetadata = old;
            if (old.name == pack.name) {
                upgrade_number = old.upgrade_number + 1;
                check_upgradability(old, &pack, &module_names);
                index = i;
            } else {
                check_coexistence(old, &module_names)
            };
        });

        // Assign the upgrade counter.
        pack.upgrade_number = upgrade_number;

        let packages = &mut borrow_global_mut<PackageRegistry>(addr).packages;
        // Update registry
        let policy = pack.upgrade_policy;
        if (index < len) {
            pack.modules.for_each_ref(|m| {
                let m: &ModuleMetadata = m;
                init::reset_initialized(addr, *m.name.bytes());
            });
            *packages.borrow_mut(index) = pack
        } else {
            packages.push_back(pack)
        };

        event::emit(PublishPackage {
            code_address: addr,
            is_upgrade: upgrade_number > 0
        });

        // Request publish
        if (features::code_dependency_check_enabled())
            request_publish_with_allowed_deps(addr, module_names, allowed_deps, code, policy.policy)
        else
        // The new `request_publish_with_allowed_deps` has not yet rolled out, so call downwards
        // compatible code.
            request_publish(addr, module_names, code, policy.policy)
    }
