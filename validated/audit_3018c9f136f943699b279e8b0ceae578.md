### Title
Unchecked ERC20 `approve()` return-value unpacking in ICS-20 destination callback permanently locks transferred funds for non-standard token pairs - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` sets up an allowance for the destination callback contract by calling `approve` on the token pair's ERC20 contract and then unconditionally unpacks the return data as a `bool` with `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)`. Unlike the sibling logic in `x/erc20/keeper/msg_server.go` (`convertERC20IntoCoinsForNativeToken`, `ConvertCoinNativeERC20`), which explicitly checks `len(res.Ret) == 0` before attempting to unpack (falling back to event-log validation for tokens that don't return a bool, e.g. USDT-style tokens), the callback keeper skips this guard. This is the exact bug class from the external report (unsafe handling of ERC20 calls that don't return a bool), reachable here through the permissionless native-ERC20 token pair registration and the ICS-20 `dest_callback` flow.

### Finding Description
`IBCReceivePacketCallback` in [1](#0-0)  performs:
1. `CallEVM(..., "approve", contractAddr, amountInt.BigInt())` on `tokenPair.GetERC20Contract()`.
2. Immediately calls `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` with no check on `len(res.Ret)`.

If the target is a *native ERC20* token pair (permissionlessly registrable via `RegisterERC20`, see `x/erc20/keeper/msg_server.go:326-362`) whose `approve()` function does not return a `bool` (a very common non-standard ERC20 pattern, the same class as USDT cited in the original report), `res.Ret` will be empty. `abi.UnpackIntoInterface` on an empty byte slice for a method expecting a `bool` output returns an unpack error, causing the function to bail out via `ErrAllowanceFailed` before `writeFn()` is ever called.

Contrast this with the codebase's own established mitigation pattern in [2](#0-1)  where `len(res.Ret) == 0` is explicitly handled by validating the `Transfer` event log instead of blindly unpacking. That defensive pattern is missing in the callback keeper's `approve` handling.

Because the underlying ICS-20 token transfer to the isolated receiver address (`receiverHex`) is committed by the transfer app *before* the callback middleware invokes `IBCReceivePacketCallback` (i.e., it is not part of the `cachedCtx` this function rolls back), a failure inside the callback (such as this spurious `approve` unpack error) does not reverse the token receipt. The tokens remain credited to the `isolatedAddr`, which per the function's own security comment is only usable by successfully executing the callback that pulls funds out via `transferFrom`: [3](#0-2) 

Since the callback contract can never be invoked (the function returns before reaching `CallEVMWithData` for the calldata), and the isolated address has no other way to move the tokens, the funds become permanently unrecoverable.

### Impact Explanation
This causes permanent, irreversible loss/freezing of user funds transferred over IBC to any chain-registered native ERC20 token pair whose `approve` does not return a `bool`, whenever the sender attaches ICS-20 `dest_callback` memo data (a normal, unprivileged, user-controlled feature). This matches the in-scope Critical impact: "permanent freezing, locking, theft, or unauthorized extraction of user funds ... or token-pair-backed balances," triggerable by an ordinary unprivileged user through the standard ICS-20 transfer + callback flow.

### Likelihood Explanation
Native ERC20 token pairs can be registered permissionlessly when `PermissionlessRegistration` is enabled (`x/erc20/keeper/msg_server.go` `RegisterERC20`), and non-standard `approve()` implementations that omit the boolean return value are common in real-world tokens (as acknowledged by the very report this analysis is seeded from). Any user who sends an ICS-20 transfer with a `dest_callback` memo targeting such a token pair reliably triggers the failure path — no privileged access or race condition is required.

### Recommendation
Mirror the defensive pattern already used in `x/erc20/keeper/msg_server.go`: check `len(res.Ret) == 0` before calling `UnpackIntoInterface` for the `approve` call in `IBCReceivePacketCallback`, and fall back to validating the emitted `Approval` event (or otherwise tolerate a missing return value) instead of treating it as a hard failure that leaves the isolated receiver's tokens stranded.

### Proof of Concept
1. Enable permissionless native ERC20 registration (or use governance) to register a token pair for a contract whose `approve(address,uint256)` performs the approval but returns no data (a `void`/non-standard ERC20 implementation).
2. As any unprivileged IBC user, send an ICS-20 transfer to the chain running this code, targeting that token's denom, with a `memo` containing a valid `dest_callback` (isolated receiver address, valid contract with code, valid calldata).
3. On `OnRecvPacket`, the transfer completes and credits `isolatedAddr` with the tokens; then `IBCReceivePacketCallback` executes `approve`, which succeeds on-chain but returns no data.
4. `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` errors on the empty `res.Ret`, so the function returns `ErrAllowanceFailed` before invoking the callback contract or writing `cachedCtx`.
5. The previously credited tokens remain at `isolatedAddr` permanently, since the only intended withdrawal path (the callback contract's `transferFrom`) can never execute.
