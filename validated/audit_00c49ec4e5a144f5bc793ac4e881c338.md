## Finding

### Title
Unauthenticated OP_RETURN in `payout_tx` lets an attacker redirect reimbursement attribution to an arbitrary operator via RBF replacement - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` signs input 0 with the withdrawer's `SinglePlusAnyoneCanPay` signature, which under BIP-341 only commits to input 0's own prevout/sequence and to output 0 (the user payout). Outputs 1 (anchor) and 2 (OP_RETURN carrying `operator_xonly_pk`) are never covered by the sighash, and the tx uses `DEFAULT_SEQUENCE = Sequence::ENABLE_RBF_NO_LOCKTIME`, so anyone who observes the broadcast tx in the mempool can reuse the witness in an RBF-replacing transaction that keeps output 0 identical but swaps the OP_RETURN operator pubkey to any value they choose.

### Finding Description
The broken binding is:
`withdrawals.payout_payer_operator_xonly_pk` (set by `Verifier::update_finalized_payouts`, `core/src/verifier.rs:2283-2352`, from the OP_RETURN of whichever transaction is recorded as spending `withdrawal_utxo`) == the operator whose own wallet funded and broadcast that winning transaction.

Trace:
- `create_payout_txhandler` builds output 0 (user payout), output 1 (anchor), output 2 (`op_return_txout` with `operator_xonly_pk`), and signs only input 0 via `set_p2tr_key_spend_witness` [1](#0-0) .
- The operator's `withdraw` flow verifies the user signature against `calculate_sighash_txin(0, in_signature.sighash_type)` only, then funds/broadcasts with `fund_raw_transaction` (no `replaceable` override, i.e., tx keeps its own `ENABLE_RBF_NO_LOCKTIME` sequence) [2](#0-1) .
- `calculate_pubkey_spend_sighash` uses `Prevouts::One(txin_index, ...)` for `SinglePlusAnyoneCanPay`, confirming the sighash covers only input 0's own prevout data [3](#0-2) . Under BIP-341 `SIGHASH_SINGLE` only commits to the output at the same index as the signed input (output 0); outputs 1 and 2 are unauthenticated.
- `DEFAULT_SEQUENCE` is `Sequence::ENABLE_RBF_NO_LOCKTIME` [4](#0-3) , so the broadcast payout tx is RBF-replaceable.
- Attribution is later derived purely from on-chain data: `get_payout_txs_for_withdrawal_utxos` joins on `bitcoin_syncer_spent_utxos` by the withdrawal outpoint (txid+vout) in the canonical block, returning whichever `spending_txid` actually confirmed [5](#0-4) . `update_finalized_payouts` then parses the OP_RETURN of that confirmed transaction and trusts its embedded xonly pubkey as the funding operator with no signature check [6](#0-5) .

Exploit flow: attacker watches the mempool for a broadcast `payout_tx`, copies its input-0 witness (still valid because the sighash preimage is unaffected by other outputs/inputs), builds a replacement transaction with the same input 0 and identical output 0, but attacker-chosen output 2 (OP_RETURN) and their own fee-paying input(s)/higher fee (permitted by `AnyoneCanPay`), and RBF-broadcasts it. If it confirms, `payout_payer_operator_xonly_pk` in the DB is set to the attacker's chosen pubkey rather than the real funding wallet's operator key. `Verifier::is_kickoff_malicious` and the `payout_checker` task (`get_first_unhandled_payout_by_operator_xonly_pk`) then key subsequent kickoff/reimbursement logic off this falsified attribution [7](#0-6) [8](#0-7) , so an uninvolved operator matching the forged pubkey can be automatically driven into claiming a kickoff/reimbursement for a payout they never funded, while the true funding wallet's original (RBF'd-out) transaction never confirms and gets no credit.

No existing guard checks this: `SECP.verify_schnorr` only checks input 0's sighash, `is_kickoff_malicious` only compares against the (already falsified) DB record, and there is no DB uniqueness/authentication constraint tying `payout_payer_operator_xonly_pk` to the actual spender of extra inputs.

### Impact Explanation
Real bridge value is at stake: the operator credited via the forged OP_RETURN can be driven (via its own automated `payout_checker`) to spend real reimbursement transactions (kickoff → reimburse) for a withdrawal it never fronted, i.e., "an operator reimbursed for a payout it never funded." Alternatively, if the attacker uses a non-operator or mismatched pubkey, no operator's kickoff will ever match the recorded attribution, permanently freezing that deposit's move-to-vault UTXO and permanently preventing the honest (actual) funder from ever being reimbursed. This is repeatable per withdrawal/deposit for any attacker willing to front the withdrawal amount themselves (since output 0 must remain fully funded in any competing transaction).

### Likelihood Explanation
Requires the attacker to observe the operator's broadcast payout tx in the mempool (trivial, public) and to itself supply enough BTC to fully fund output 0 (the user payout amount) in the replacement transaction, plus a higher fee to win RBF before confirmation. This is costly (attacker must pay the whole withdrawal amount) but is a straightforward, mechanically guaranteed protocol violation, not probabilistic — no majority hashrate, no key compromise, and no privileged role is needed, only fee-paying capability and public mempool visibility, matching the stated unprivileged-attacker capabilities.

### Recommendation
Bind the OP_RETURN operator attribution to the same signature that authorizes the withdrawal, e.g., have the withdrawer's/aggregator's signature cover the OP_RETURN output (use `SIGHASH_ALL` or otherwise commit output 2's contents into the signed message), or require the payout tx's non-malleable/committed operator identity to be established by a mechanism the withdrawer or protocol actually authenticates (e.g., verify the confirmed transaction's OP_RETURN operator pubkey against the operator that funded/broadcast it through an authenticated channel, not by trusting arbitrary on-chain OP_RETURN bytes).

### Proof of Concept
`cargo test` plan:
1. Set up a regtest environment with an operator (`operator_xonly_pk_A`) and register a second operator (`operator_xonly_pk_B`) for the same deposit.
2. Call `Operator::withdraw` (or the `Withdraw` gRPC) for operator A to build and broadcast `payout_tx` via `create_payout_txhandler`; capture its input-0 witness from the mempool.
3. Construct a replacement transaction: same input 0 (outpoint/sequence), identical output 0, an attacker-funded extra input to cover output 0's value plus higher fee, and OP_RETURN output rewritten with `operator_xonly_pk_B.serialize()`; reuse the captured witness for input 0.
4. Broadcast the replacement and mine it, ensuring `A`'s original tx is evicted (RBF) and never confirms.
5. Run `Verifier::update_finalized_payouts` and assert `db.get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` returns `operator_xonly_pk_B`, not `operator_xonly_pk_A` — proving attribution is arbitrarily attacker-controlled and decoupled from who actually funded the payout.
