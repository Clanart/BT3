### Title
SQL Injection via Unvalidated `start`/`end` Parameters in `get_transactions_between` LIMIT Clause - (File: chia/wallet/wallet_transaction_store.py)

### Summary
`WalletTransactionStore.get_transactions_between()` builds its SQL query by directly f-string-interpolating the `start` and `end` parameters into a `LIMIT {start}, {limit}` clause instead of using parameterized placeholders, mirroring the exact root cause of the Propel2 advisory (missing integer casting of a `limit()`/offset value before string-formatting it into SQL).

### Finding Description
The method signature declares `start` and `end` with no type annotation and no runtime cast: [1](#0-0) 

Every other value that is attacker/caller influenced in this query (`wallet_id`, `confirmed`) is passed through a parameterized `?` placeholder, but `start` and the derived `limit = end - start` are concatenated directly into the SQL string: [2](#0-1) 

Because Python performs no implicit type/format validation, if `start` or `end` is anything other than a plain `int` (e.g., a string arriving from a JSON-RPC request body such as `{"start": "0; DROP TABLE transaction_record;--", "end": 1}`), the value is spliced verbatim into the SQL text executed by `aiosqlite`/`sqlite3`. This is architecturally identical to the Propel2 bug: `limit()`/offset values must be cast to `int` before being embedded in raw SQL, and this code path skips that cast entirely, unlike sibling methods in the same class that use `?` for every numeric value (e.g., `confirmed=?` pattern is not even used here — `confirmed` is cast with `int(confirmed)` before formatting, but `start`/`end` are not cast at all).

This function is reachable from the wallet RPC surface (`get_transactions` endpoint in `chia/wallet/wallet_rpc_api.py`, confirmed to call `get_transactions_between`), which is invoked by any local RPC caller with a wallet-RPC session — an actor explicitly in scope per this engagement's rules ("local RPC caller").

### Impact Explanation
An RPC caller who can invoke `get_transactions` (or any other caller of `get_transactions_between`) with non-integer `start`/`end` values can inject arbitrary SQL into the `LIMIT` clause of the wallet database. Because SQLite (used by `aiosqlite`) executes multiple statements per call by default in many execution paths, this can allow: destructive actions against the wallet DB (dropping/altering `transaction_record` or other tables), corruption of wallet state (transaction history, spend records), or, depending on driver behavior, extraction of arbitrary wallet DB content. Given wallet state integrity is directly tied to fund tracking and spend bundle history, this is a high-impact vector once triggered.

### Likelihood Explanation
The likelihood depends on whether the RPC layer (`wallet_rpc_api.py`) coerces `start`/`end` to `int` before calling `get_transactions_between`. I was not able to confirm the exact call site code for `get_transactions` in `wallet_rpc_api.py` within the available search budget — the grep confirmed the call exists but I could not verify whether a `int(request["start"])`-style cast is applied at the RPC boundary. If the RPC handler does cast these values to `int`, the practical exploitability is null for that specific caller, but the store-level function remains unsafe for any other/future caller that does not perform this cast, and the pattern itself (raw f-string LIMIT interpolation without casting) is a real defect matching the reported bug class.

### Recommendation
- In `WalletTransactionStore.get_transactions_between`, cast `start` and `end` to `int` immediately upon entry (e.g., `start = int(start)`, `end = int(end)`), or change the query to use `LIMIT ? OFFSET ?` / `LIMIT ?, ?` with `start`/`limit` passed as bound parameters instead of f-string interpolation, consistent with `TradeStore.get_trades_between` in `chia/wallet/trading/trade_store.py`, which does use `LIMIT ? OFFSET ?` with bound parameters.
- Audit `wallet_rpc_api.py`'s `get_transactions` handler to confirm/enforce that `start`/`end` values are validated as integers before being passed down.
- Add negative/malformed-input tests (non-integer `start`/`end`) to `chia/_tests/wallet/test_transaction_store.py` to lock in the fix.
