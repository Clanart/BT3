## Title
Protocol fee can be avoided entirely by splitting orders below the rounding threshold - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` computes the protocol fee with the exact "subtract-after-floor-division" pattern flagged in the external Yieldy report: `protocolFee = (amount * protocolFeeBps) / 10_000` followed by `reducedAmount = amount - protocolFee`. When `amount * protocolFeeBps < 10_000`, `protocolFee` truncates to `0`, so the fee is skipped entirely for that order. There is no minimum order size — the only check is `amount == 0` — so a user can split an arbitrarily large swap into many sub-threshold orders and pay zero protocol fee on the whole volume.

### Finding Description
In `placeOrder`, Phase 2 computes the fee and reduced escrow amount as: [1](#0-0) 

```
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```

This is precisely the rounding pattern the Yieldy `instantUnstake` finding warned against: fee = floor(amount × rateBps / 10,000), applied via subtraction, rather than rounding the fee up. For any `originalAmount` such that `originalAmount * protocolFeeBps < 10_000`, `protocolFee` floors to `0` and `reducedAmount == originalAmount` — the full input escrows with no fee deducted, and no `DustCollected` event fires (the code only emits it `if (protocolFee > 0)`).

The only guard on input size is a non-zero check: [2](#0-1) 

There is no per-order minimum amount, and nothing throttles the number of orders one caller can place. At the documented production rate of 5 bps, any input strictly less than `10_000/5 = 2000` units (in the token's smallest denomination) pays zero protocol fee — for a 6-decimal stablecoin like USDC that's any amount `< 0.002 USDC`; even at the 30/100/1000 bps values exercised in the test suite (`PROTOCOL_FEE_BPS`, `testProtocolFeeWith1Percent`, `testProtocolFeeWith10Percent`) the threshold scales but never disappears, and per-destination fee overrides (`_destinationProtocolFees`) are independently vulnerable to the same floor.

An attacker with any total volume `V` and fee rate `f` bps can split `V` into `N = ceil(V * f / 9999)`-plus sub-threshold orders, each individually paying zero fee, and complete each via a same-chain self-fill (attacker acts as both `order.user` and the solver in `fillOrder`, which has no restriction preventing solver == user). The full `V` is swapped with the protocol collecting nothing, systematically draining protocol fee revenue that every other user pays.

### Impact Explanation
This is a logic/economic-invariant break in the live fee-collection path of `IntentGatewayV2`, the production intents/order-settlement contract. It lets an unprivileged attacker unilaterally bypass a fee the protocol depends on for revenue, for unbounded total volume, purely through account-level looping — no relayer, prover, or governance compromise required. It matches the bounty's "logic attacks" and fund-loss (protocol revenue loss) category.

### Likelihood Explanation
High. The only requirements are: (1) a `protocolFeeBps` configured at a realistic production value (5–1000 bps per the docs/tests), and (2) willingness to submit many small `placeOrder`/`fillOrder` transactions — cheap on L2s and for low-decimal or high-value tokens where the rounding threshold in "smallest unit" terms corresponds to non-trivial real value. No special privileges, timing, or race conditions are needed.

### Recommendation
Round the fee up instead of the remainder down, mirroring the Uniswap V2 style fix suggested in the original report:
```solidity
uint256 reducedAmount = (originalAmount * (10_000 - protocolFeeBps) + 9_999) / 10_000;
uint256 protocolFee = originalAmount - reducedAmount;
```
This guarantees `protocolFee` is never truncated to zero unless `protocolFeeBps == 0`, eliminating the sub-threshold fee-avoidance path regardless of how small an individual order is split into.

### Proof of Concept
1. Governance sets `protocolFeeBps = 5` (documented production value) via `ParamsUpdate`.
2. Attacker calls `placeOrder` with `order.inputs[0].amount = 1999` (any token where `1999 * 5 / 10000 == 0`).
   - `protocolFee = (1999 * 5) / 10_000 = 0`
   - `reducedAmount = 1999 - 0 = 1999` — full amount escrowed, no fee taken, no `DustCollected` emitted.
3. Attacker (or a colluding/self-controlled solver address) immediately calls `fillOrder` on the same order, completing the swap and releasing escrow — same-chain fill has no `solver != user` restriction.
4. Attacker repeats steps 2–3 in a loop (or batches many such `placeOrder`/`fillOrder` pairs in one transaction) until the desired total volume `V` is swapped, each individual leg contributing `0` to protocol fee revenue, versus the expected `V * 5 / 10_000` if done as a single large order. [3](#0-2) 
The existing test `testProtocolFeeWith1Percent` confirms the fee formula's exact arithmetic (`expectedProtocolFee = (inputAmount * 100) / 10000`), demonstrating the same floor-division-then-subtract logic is used and tested only at amounts safely above the rounding threshold — no test exercises the sub-threshold, fee-avoidance case.
