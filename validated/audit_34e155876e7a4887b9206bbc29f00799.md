### Title
`pallet-ismp-relayer::withdraw` zeroes accrued fees before the destination-chain payout is confirmed, permanently burning relayer fees on transfer failure - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`Pallet::withdraw` reads the relayer's accrued `Fees::<T>` balance, dispatches a one-way (`timeout: 0`) ISMP POST instructing the destination chain's `HostManager`/`EvmHost.withdraw` (or, for Substrate destinations, `HyperbridgeWithdrawalModule::on_accept`) to pay out `available_amount`, and then immediately zeroes the `Fees` entry and bumps the nonce — all before there is any confirmation that the destination-side transfer actually succeeded. This is the same broken invariant as the reported `DebtManager.manualAllocation` bug: the caller commits to local accounting as if the requested amount will be applied exactly as instructed downstream, without accounting for a downstream constraint (here, the destination host's actual token balance) that can make the real effect diverge from the request.

### Finding Description
`Pallet::withdraw` in [1](#0-0)  reads `available_amount = Fees::<T>::get(...)` and only checks it against a minimum threshold — it never checks whether the destination chain actually holds `available_amount` of the fee token. It then dispatches a `DispatchPost` with `timeout: 0` (no timeout/refund path) to the destination's `host_manager`/`HYPERBRIDGE_MODULE_ID`: [2](#0-1) 

Immediately after dispatching, and irrespective of whether the destination-side request ever executes successfully, the pallet zeroes the ledger and emits the withdrawal event: [3](#0-2) 

On the EVM side, the actual payout is `EvmHost.withdraw`, restricted to `_hostParams.hostManager`, which performs a plain `safeTransfer`/native `call`: [4](#0-3) 

If `IERC20(params.token).safeTransfer` reverts (insufficient balance in the host contract — e.g., the fee token pool was drawn down by other relayers withdrawing concurrently, by protocol/governance withdrawals such as `BandwidthManager`'s `dispatch_withdraw` competing for the same or a related pool, or simply because accrued `Fees` on the Substrate ledger were never guaranteed to be backed 1:1 by the destination chain's live balance at withdrawal time), the incoming POST request fails execution on the destination chain. Because `timeout: 0` means there is no timeout window and thus no `on_timeout` refund/credit-back path in the relayer pallet, the failure produces no compensating state change on the source (Hyperbridge) side. The `Fees` entry was already zeroed and the nonce already incremented before the dispatch ever resolved — the relayer's earned fee is now unrecoverable: it cannot be re-withdrawn (the ledger reads zero) and it was never paid out.

This exactly mirrors the reported class of bug: the withdrawal accounting function assumes the exact requested amount will be honored by the downstream execution (`EvmHost.withdraw`), but the downstream call is exposed to a constraint outside the caller's visibility (destination fee-token balance) that can make it diverge from — or outright fail on — the requested value, and the caller's local state has already been mutated as if success were guaranteed.

### Impact Explanation
This causes irrecoverable loss of legitimately earned relayer fees, a "loss of funds" outcome under the bounty's accepted impact categories. Unlike the DebtManager case (which merely reverts and can be retried), here the failure mode is worse: the source-chain ledger commits to "paid" (`Fees` zeroed, nonce incremented, `Withdraw` event emitted) atomically with dispatch, before the destination-side transfer is known to succeed, and there is no timeout/refund mechanism (`timeout: 0`) to restore the balance if it doesn't. Any relayer whose withdrawal races against a moment of insufficient destination-host balance loses that portion of their fee permanently, with no on-chain recourse.

### Likelihood Explanation
The path is reachable by any relayer calling the public `withdraw` extrinsic with a valid signature over their own accrued fees — no malicious peer, relayer, prover, or governance actor is required. The precondition (destination host's fee-token balance being momentarily less than the sum of all relayers' currently-accrued, unwithdrawn `Fees` for that chain) is plausible in normal operation: fee-token balance on `EvmHost` is a shared pool drawn by every relayer's fee accumulation and drained by every relayer's withdrawal and by cross-chain governance withdrawals; nothing in `Pallet::withdraw` checks or reserves against actual destination liquidity before committing to the payout on the source ledger.

### Recommendation
Do not zero `Fees::<T>` (or increment the nonce in a way that forecloses retry) until the destination-side execution is confirmed. Options:
- Use a non-zero `timeout` and implement an `on_timeout`/failure callback that re-credits `Fees::<T>` for the relayer if the destination-chain request is not executed or reverts.
- Alternatively, have the destination-side handler report the *actual* transferred amount back via a response, and only debit the source ledger by that confirmed amount, analogous to using `update_debt`'s actual return value instead of assuming the requested delta was applied.
- At minimum, bound `available_amount` server-side against a periodically-synced view of the destination host's live balance so withdrawals that would fail are rejected before the ledger is mutated.

### Proof of Concept
1. Two relayers, A and B, each accrue fees for withdrawals to the same destination `EVM-X`, such that `Fees[A] + Fees[B]` exceeds `EvmHost`'s current fee-token balance on `EVM-X` (plausible since the host balance also gets drained by unrelated withdrawals/governance actions).
2. Relayer A calls `Pallet::withdraw` first; `EvmHost.withdraw` succeeds, draining most of the balance.
3. Relayer B calls `Pallet::withdraw` for `Fees[B]`; `Fees::<T>::insert(..., U256::zero())` executes and `Nonce` is incremented in the same call as dispatched in [5](#0-4) , before the cross-chain message is even delivered.
4. When relayer B's `WithdrawalParams` POST is finally delivered and executed via `EvmHost.withdraw` [4](#0-3) , the `safeTransfer` reverts because the host's balance is now insufficient.
5. The ISMP message execution fails at the destination; because `timeout: 0` was used, there is no timeout callback to restore `Fees[B]` on the Hyperbridge chain. `Fees::<T>::get(EVM-X, B)` now reads zero, and B's fee is permanently lost with no path to reclaim it.

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();

            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
