## Analysis

The Sherlock report's core broken invariant is: **the protocol uses a token's *nominal* transferred amount as its *true* value, without accounting for a fee the token itself deducts on transfer/exchange**, letting the accounting side over-credit value that was never actually received.

Hyperbridge's `IntentGatewayV2` contains the exact same broken invariant on the **output** side of order fulfillment, even though it explicitly guards against it on the **input** side.

### The protected path (input tokens, `placeOrder`)
`IntentGatewayV2.sol` correctly measures actual received amount via balance-diff for fee-on-transfer *input* tokens: [1](#0-0) 

### The unprotected path (output tokens, fill functions)
Both same-chain and cross-chain fill logic instead trust the **nominal** amount passed by the solver and never verify what the beneficiary actually received: [2](#0-1) [3](#0-2) 

For a fee-on-transfer (deflationary) output token, `safeTransferFrom(msg.sender, beneficiary, totalRequired)` delivers less than `totalRequired` to the beneficiary, yet:
- `outputFills[i].amount` is recorded as the full nominal `totalRequired` [4](#0-3) 
- For cross-chain orders, the contract immediately dispatches `RedeemEscrow` releasing the **full** escrowed input to the solver on the source chain based on this nominal fill [5](#0-4) 
- For same-chain partial fills, `_partialFills[commitment][outputToken]` is incremented by the nominal `fillAmount`, so the order can be marked fully filled and 100% of the proportional escrow released, even though the beneficiary was under-paid every single fill [6](#0-5) 

No `IERC20.balanceOf(beneficiary)` check exists anywhere in either fill path to confirm actual delivery, unlike the input-side protection.

### Title
Fee-on-transfer output tokens let a solver under-deliver value while claiming full escrow — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The IntentGateway measures *actual received* amounts for fee-on-transfer **input** tokens at `placeOrder` time via balance-diffing, but never applies the same check to **output** tokens at fill time. A solver filling an order whose `output.assets[i].token` is a fee-on-transfer/deflationary ERC-20 delivers less than `totalRequired` to the beneficiary, yet the contract records the fill as fully satisfying the nominal amount and releases the entire corresponding escrow (cross-chain, via `RedeemEscrow`) or entire proportional escrow (same-chain, via `_partialFills`) to the solver.

### Finding Description
`_fillCrossChain` and `_fillSameChain` both compute `beneficiaryTotal`/`fillAmount` from the order's nominal required amount and the solver-declared `solverAmount`, then call `IERC20.safeTransferFrom(msg.sender, beneficiary, amount)` without verifying the beneficiary's balance delta. If the output token deducts a transfer fee (a legitimate, user-selectable ERC-20 category, not requiring any malicious actor), the beneficiary receives `amount − fee`, strictly less than `order.output.assets[i].amount`. Despite this shortfall:
- `outputFills[i]` and `escrowedInputs[i]` are computed from the nominal amount, not the delivered amount.
- The cross-chain path immediately emits `RedeemEscrow`, transferring the *full* escrowed input value to the solver on the source chain.
- The same-chain path marks `_partialFills[...]` as fully satisfied with the nominal amount, releasing full escrow and, if `amountFilled == totalRequired`, executing postdispatch calldata as though the order were completely and correctly filled.

The invariant "escrow released == value actually delivered" — the same invariant Vault_Synths.sol violated for collateral valuation — is broken here for output settlement.

### Impact Explanation
This is a direct, unprivileged fund-extraction path: a solver can systematically under-deliver the promised output value to beneficiaries (loss of funds for order-placing users) while capturing 100% of the escrowed input on the source chain — a value mismatch/false state acceptance in the ledger (`_orders`, `_partialFills`, `_filled`) that never reconciles with real token balances. No relayer, prover, or admin compromise is required.

### Likelihood Explanation
Any order (same-chain or cross-chain) whose `output.assets[i].token` is a fee-on-transfer ERC-20 is systematically affected on every fill — this is not a race condition or edge case but a deterministic shortfall reproducible by any solver on any qualifying order, with no additional privilege needed.

### Recommendation
Mirror the input-side protection: measure the beneficiary's actual balance delta (`balanceOf(beneficiary)` before/after `safeTransferFrom`) when settling output tokens in both `_fillSameChain` and `_fillCrossChain`, and use that measured amount — not the nominal `totalRequired`/`solverAmount` — for `outputFills`, `_partialFills` accounting, and the `WithdrawalRequest` amounts dispatched via `RedeemEscrow`. Alternatively, restrict output tokens to a vetted non-fee-on-transfer allowlist.

### Proof of Concept
1. User places a cross-chain order with `output.assets[0].token` = a deflationary ERC-20 charging a 5% transfer fee, `amount = 100e18`.
2. Solver calls `fillOrder` with `options.outputs[0].amount = 100e18` and executes `safeTransferFrom(solver, beneficiary, 100e18)`.
3. Beneficiary's actual balance increases by only `95e18` due to the token's fee, but `outputFills[0].amount` is recorded as `100e18` [7](#0-6) .
4. Contract dispatches `RedeemEscrow` for the order's full escrowed input value [8](#0-7) .
5. On the source chain, `onAccept` releases 100% of the escrowed input to the solver, even though the beneficiary only received 95% of the promised output value — the solver profits the 5% gap at the user's expense every time this is repeated.
