Based on the evidence gathered, I found a genuine local analog to the reported "overshadowing" bug class.

### Title
Vote Account Commission-Collector State Corruption on Implicit V3→V4 Conversion - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
`update_commission_collector` (SIMD-0232) lets the authorized withdrawer redirect either the `InflationRewards` or `BlockRevenue` commission collector of a vote account to a new address [1](#0-0) . When the underlying vote account is still serialized in the legacy `V3` layout (which has no collector fields at all), the call path implicitly upgrades it to `V4` before writing the requested field. That implicit upgrade silently populates the *other*, untouched collector field with a hardcoded default (`node_pubkey` for `BlockRevenue`, or the vote account's own key for `InflationRewards`) instead of preserving whatever value it might have needed to be, exactly mirroring the reported bug class: a single-purpose "set one field" operation ends up resetting a second, unrelated state variable to a value the caller never specified or intended.

### Finding Description
`update_commission_collector` retrieves the vote state via `get_vote_state_handler_checked`, verifies the authorized withdrawer signed, resolves/validates the new collector key through `NewCommissionCollector::validate_and_resolve_key`, and then calls `vote_state.set_inflation_rewards_collector(...)` or `vote_state.set_block_revenue_collector(...)` before serializing the state back with `set_vote_account_state` [2](#0-1) .

The test explicitly documents and asserts the resulting corruption:

```
// V3 -> V4 auto-conversion side-effect: updating one collector against a
// V3-serialized account causes the "other" collector to be written as
// its V4 default (inflation_rewards_collector = vote_pubkey,
// block_revenue_collector = node_pubkey), per try_convert_to_vote_state_v4.
``` [3](#0-2) 

The test then calls `update_commission_collector` only for `CommissionKind::InflationRewards` on a `V3`-encoded account and asserts that the *BlockRevenue* collector — a field the caller never touched — is silently overwritten to the V3-era `node_pubkey`, not preserved or left as configured:

```
// The *other* field was reset to its V4-conversion default
// (block_revenue_collector = node_pubkey from the V3 source).
assert_eq!(
    get_commission_collector(&borrowed_vote_account, CommissionKind::BlockRevenue),
    v3_node_pubkey,
);
``` [4](#0-3) 

This is functionally identical to the original report's root cause: a function meant to update one specific value (`_tokenAddress` in `withDrawFunds`, or here the requested `CommissionKind` collector) instead resets a second, distinct state variable as a side effect of the underlying storage/conversion mechanism, because the code does not isolate the write to only the intended field.

### Impact Explanation
If a vote account operator has previously configured a `BlockRevenue` collector (e.g., pointing rewards to a treasury/multisig) and later performs a routine `UpdateCommissionCollector` call for `InflationRewards` while the account still happens to be in the legacy V3 on-chain encoding, the `BlockRevenue` collector is silently reset to `node_pubkey` — an address the operator did not choose for that purpose. Future block-revenue commission distributions would then be redirected to the validator identity account instead of the intended collector, i.e., a fund-misdirection bug caused by state overshadowing rather than an explicit request. Because vote accounts can hold substantial delegated stake and collect real commission payouts, this can amount to unintended fund loss/misdirection for the account operator or delegators expecting funds at the configured collector.

### Likelihood Explanation
This triggers automatically, without any special crafted input, whenever `update_commission_collector` is invoked against a vote account still encoded as `VoteStateVersions::V3` — which is the default/legacy encoding for any vote account that has not yet been upgraded to `V4` via another state-mutating instruction. Any validator operator adopting the new SIMD-0232 collector feature on an existing (V3) vote account, without first/simultaneously setting both collectors, will hit this path.

### Recommendation
When implicitly converting a `V3` vote account to `V4` inside the collector-update path, explicitly preserve or intentionally initialize the untouched collector field to a documented, caller-visible default (or require both collectors be set together during the V3→V4 transition) rather than silently deriving it from stale V3 fields (`node_pubkey`). At minimum, follow the same pattern recommended in the original report: use a temporary/staged value for the "other" collector and only commit it if it was explicitly intended, so a call that updates one collector can never overwrite the other.

### Proof of Concept
The existing test `test_update_commission_collector` in `programs/vote/src/vote_state/mod.rs` already reproduces and asserts this exact behavior [5](#0-4) :
1. Construct a `VoteStateV3` account with a known `node_pubkey`.
2. Call `update_commission_collector(..., CommissionKind::InflationRewards, ...)` only.
3. Observe that `BlockRevenue` collector is now `v3_node_pubkey` even though it was never referenced in the instruction.

Note: I could not fully inspect `try_convert_to_vote_state_v4` inside `programs/vote/src/vote_state/handler.rs` before running out of tool iterations, so the exact conversion logic that produces this default is confirmed only indirectly through the test's comments and assertions, not by reading the conversion function itself.

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
