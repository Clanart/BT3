## Analog Found

The Kinetiq bug is a classic **stale-snapshot-used-at-execution-time** flaw: a value (`hypeAmount`) is locked in against one state of the world (the exchange rate at *queue* time) and is blindly reused at a later execution point (*confirm* time) without revalidating it against the current state, even though the code has *already* fetched fresh state by then.

GitHub Desktop has the exact same class of bug in its **partial-commit line-selection** pipeline.

### Title
Stale line-index diff selection is reused against a freshly re-fetched diff when staging partial commits, silently committing/excluding the wrong content - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
When a user makes a partial-file commit (selecting individual added/removed lines in the diff viewer), Desktop stores the selection as a set of **abstract line indices** (`DiffSelection`), not as content-addressed line identities. The application self-admittedly only partially revalidates this selection when the diff changes, and the low-level staging code (`applyPatchToIndex`) independently **re-fetches the diff a second time** right before generating the patch, and reuses the old index-based selection against that brand-new diff without any content equivalence check. If the tracked file's content changes between when the user reviewed/selected lines and when the commit is actually staged, Desktop will silently apply the user's line selection to the *wrong* lines of the new content.

### Finding Description
The selection object only tracks line positions: [1](#0-0) 

When the diff is reloaded (e.g. a background status refresh while the file is open), the app itself documents that it cannot fully validate whether previously selected lines still mean the same thing — it only prunes indices that are now out of bounds or turned into context lines, but does not verify the *content* at that index is unchanged: [2](#0-1) 

Then, at actual commit time, `createCommit` clears the index and calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex`: [3](#0-2) [4](#0-3) 

`applyPatchToIndex` re-fetches yet another fresh diff from disk (a third snapshot, independent of whatever the UI last reconciled) and immediately hands it to `formatPatch` together with the old `file.selection`: [5](#0-4) 

`formatPatch` walks the *new* diff's hunks and decides what to include purely by comparing `absoluteIndex` against `file.selection.isSelected(absoluteIndex)` — a pure index lookup with no content correlation to the diff that was on-screen when the user made their choice: [6](#0-5) 

### Impact Explanation
This directly maps to the Kinetiq root cause: a decision (which HYPE amount to release / which lines to commit) is locked in against one snapshot, then executed later against a changed underlying state using the old, now-misaligned reference. In Desktop's case the corrupted value is **the actual byte content committed to the repository**: lines the user explicitly excluded from the commit (e.g. a hardcoded secret, a debug print, a security check they weren't ready to ship) can be silently included, or lines they intended to commit can be silently dropped — with the app showing no warning, since the reconciliation logic (`app-store.ts:3480-3492`) only removes indices, it never blocks the commit or informs the user the underlying content changed. This is a silent corruption of what the user commits (and subsequently pushes), which is explicitly a listed valid impact.

### Likelihood Explanation
This requires no admin rights, no local pre-existing malware, and no leaked credentials. It is triggered by the ordinary developer workflow of having an editor/build tool/formatter (commonly bundled and recommended by the repository itself, e.g. via `package.json` scripts, `.vscode/settings.json` format-on-save, a file watcher, or a linter with autofix) modify the tracked file on disk *while the file is open for partial staging in Desktop* — a very natural sequence (edit → look at diff → tweak selection → commit) that Desktop's own background status polling and the two independent diff re-fetches (`app-store.ts` reconciliation and `apply.ts`'s own fetch) make easy to race, since there are at least two separate points where a stale diff can be paired with the old selection.

### Recommendation
- Bind `DiffSelection` to a content fingerprint of the diff it was created against (e.g. hash of hunk headers + line text), not just line-position indices.
- Have `applyPatchToIndex` reuse the same diff object the UI/selection was validated against instead of independently re-fetching a new diff immediately before patch generation, or re-validate that the freshly fetched diff is identical to the one the selection was built from before calling `formatPatch`.
- If the diff has changed since the selection was made, surface this to the user (e.g. force a re-review of the diff) instead of silently degrading to "just drop indices that no longer exist."

### Proof of Concept
1. In a repo opened with GitHub Desktop, modify `file.md` so it has two hunks; stage none of it, open the diff, and select only specific added lines in hunk 2 for a partial commit (leave the commit dialog open, don't click Commit yet).
2. While the diff is displayed, have an external process (e.g. `npm run format` triggered by a watch task, or simply edit the file in another editor and save) rewrite the file such that the hunk boundaries / line offsets shift but the overall number of added/context lines per hunk stays superficially similar (so no lines get pruned by the `selectableLines` reconciliation in `app-store.ts:3478-3492`).
3. Click "Commit" in Desktop. `createCommit` → `stageFiles` → `applyPatchToIndex` (`apply.ts:60`) fetches the diff fresh from disk (the modified version) and calls `formatPatch(file, diff)` using the original, stale `file.selection`.
4. Inspect the resulting commit: it contains lines from the *new* file content selected at the *old* line indices, which do not correspond to what the user actually reviewed/selected in the UI — a silent corruption of the committed content.
