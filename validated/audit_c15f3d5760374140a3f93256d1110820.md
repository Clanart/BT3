### Title
Untrusted `ReceivedOutput` bytes supply the offset and `TxOut` used for spending-key derivation and sighash prevout commitment, allowing funds to be reported received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes three attacker-chosen fields — `offset` (a scalar), `output` (a `TxOut` including `script_pubkey` and `value`), and `outpoint` — and returns them as a "spendable output" without checking that `offset` is the scalar that actually maps the wallet's base key to `output.script_pubkey`, nor that `outpoint`/`value` correspond to any real UTXO. `SignableTransaction::new` then consumes these untrusted fields to compute input totals, fee accounting, and the BIP-341 `Prevouts::All` commitment. This mirrors the bug class: a client-controlled value is trusted where the protocol should derive it (the Host header standing in for `base_url`; here a supplied offset/`TxOut` standing in for scanner-derived values).

### Finding Description
`ReceivedOutput::read` performs no internal consistency check between `offset` and `output.script_pubkey` [1](#0-0) . When produced by `Scanner::scan_transaction`, the pair is guaranteed consistent because the script was looked up in `self.scripts` (offset → script mapping built by `register_offset`) [2](#0-1) . That guarantee is lost once bytes arrive from an untrusted channel.

`SignableTransaction::new` uses `input.offset` to build `offsets` and `input.output` (with its attacker-chosen `value`) to build `prevouts` and `input_sat` [3](#0-2) . The `NotEnoughFunds` check and all fee/change math operate on the *claimed* value, not the on-chain value [4](#0-3) .

The only downstream guard is `SignableTransaction::multisig`, which returns `None` if `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey` [5](#0-4) . This catches script/offset mismatches but only by aborting — it does not prevent construction of a `SignableTransaction`, and it provides no check that `output.value` or `outpoint` match a real UTXO. During signing, `taproot_key_spend_signature_hash` commits to the attacker-supplied `prevouts` (including the forged amount), so any discrepancy between the claimed `TxOut` and the actual spent output yields a transaction whose signatures are invalid on-chain [6](#0-5) .

### Impact Explanation
An unprivileged party feeding crafted bytes to `ReceivedOutput::read` can produce a `ReceivedOutput` that:

- claims an arbitrary `value` for any outpoint, inflating `input_sat` so `SignableTransaction::new` reports sufficient funds and builds payments/change accordingly; the resulting transaction's BIP-341 signatures commit to the forged amounts and are invalid when the real prevout differs, so the funds are effectively "received" by the wallet's accounting but the signed spend is unspendable/rejected; or
- pairs a real-looking `outpoint`/`TxOut` with a wrong `offset`, causing `multisig()` to return `None` mid-flow after `SignableTransaction::new` already accepted the inputs — a failed/aborted signing round (each FROST attempt burns preprocesses and coordinator time).

This satisfies "funds reported received that are not spendable": the deserializer presents a self-proclaimed spendable output, and the spend path either fails late or produces an invalid transaction.

### Likelihood Explanation
Reachable by any party who can get untrusted bytes into `ReceivedOutput::read` — e.g., serialized outputs relayed between components or persisted state influenced by an attacker. The attacker controls all three fields, so no cryptographic work is needed. Impact is bounded by the late `multisig()` consistency check and by consensus invalidity (no theft of funds directly), which keeps this at Medium rather than High — consistent with the source advisory's Medium rating.

### Recommendation
Make `ReceivedOutput` self-validating:

1. In `ReceivedOutput::read` (or a new `read_for_key(key)` constructor), recompute `p2tr_script_buf(key + G*offset)` and reject inputs whose `script_pubkey` does not match, moving the consistency check from `multisig()` to deserialization.
2. Document that `value`/`outpoint` authenticity cannot be verified offline and must be confirmed against a trusted chain view before funds are counted; alternatively, verify `outpoint`/`value` against the referenced transaction when available.

let mut buf = Vec::new();
buf.extend(Scalar::ONE.to_bytes());                 // offset chosen by attacker

    value: Amount::from_sat(1_000_000_000),          // 10 BTC "received"
    script_pubkey: p2tr_script_buf(victim_even_key).unwrap(),
}));
buf.extend(serialize(&OutPoint::default()));

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000_000);           // accepted unconditionally

// Wallet accepts it as input and does all fee/change math on the forged amount
let tx = SignableTransaction::new(
    vec![forged],
    &[(payment_script, 900_000_000)],
    None, None, 10,
).unwrap();                                          // succeeds — no chain check

// Spending either aborts (offset/script mismatch -> multisig() -> None)
// or produces signatures over Prevouts::All committing to the forged 10 BTC
// prevout, which no real UTXO satisfies -> invalid transaction.

      outpoint =

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
