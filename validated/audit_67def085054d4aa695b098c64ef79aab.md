### Title
Repeated `safeApprove()` without zero-reset in `WombatStaking` deposit/withdraw/stake paths can permanently DoS deposits and withdrawals - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking` uses OpenZeppelin's `safeApprove()` to grant the underlying Wombat pool and `masterWombat` contracts allowance to pull tokens on every `deposit()`, `withdraw()`, and internal staking call, without first resetting the allowance to zero. `safeApprove()` reverts whenever it is called with a non-zero value while a non-zero allowance already exists, so any residual (unconsumed) allowance left over from a prior call will permanently brick the affected function for every user routed through the corresponding pool.

### Finding Description
`WombatStaking.deposit()` approves `poolInfo.depositTarget` for the deposit amount and then calls the target pool's `deposit()`: [1](#0-0) 

`WombatStaking.withdraw()` does the same for the LP token: [2](#0-1) 

`_stakeToWombatMaster()`, called from every deposit path via `_toMasterWomAndSendReward`, approves `masterWombat` for the LP amount on every single deposit: [3](#0-2) 

`convertWOM()` similarly approves `veWom` for the WOM amount on every call: [4](#0-3) 

In every one of these cases, `IERC20.safeApprove(spender, amount)` is invoked with a non-zero `amount` while the previous allowance to that same spender is not guaranteed to be exactly zero. OpenZeppelin's `safeApprove()` enforces `(value == 0) || (allowance == 0)` and reverts otherwise ("SafeERC20: approve from non-zero to non-zero allowance"). If the external pool, `masterWombat`, or `veWom` contract does not fully consume the approved allowance in a given call (e.g., it pulls less than the approved amount due to internal fee/haircut logic, rounding, or only partially executes the transfer), a non-zero residual allowance remains. The very next `deposit()`, `withdraw()`, or `convertWOM()` call for that pool/spender will then revert inside `safeApprove()`, since it is called again with a non-zero amount against a non-zero existing allowance.

This is functionally identical to the referenced Curve/xETH AMO finding: the contract repeatedly calls `safeApprove()` with a non-zero value assuming the entire allowance is always consumed by the counterparty, which is not a safe assumption to hardcode into the approval flow itself.

### Impact Explanation
`deposit()` and `withdraw()` in `WombatStaking` are the core paths reached by ordinary users through `WombatPoolHelperV2.deposit`/`depositFor`/`withdraw`, which are unprivileged, permissionless entry points. If a residual allowance causes `safeApprove()` to revert, both deposits and withdrawals for that pool become permanently unusable until the allowance is manually reset by an admin (there is no user-facing or automatic recovery). Since `withdraw()` is also blocked, user funds already staked in the affected pool become **permanently frozen** — users cannot exit their position through the protocol. This satisfies the "permanent freezing of funds" bar.

### Likelihood Explanation
This requires a specific precondition (the depositTarget/masterWombat/veWom pulling less than the full approved amount at least once), so it is not guaranteed to occur on every call, but it is a structural flaw reachable purely through normal, unprivileged user interaction (deposit/withdraw), with no admin or attacker action required beyond ordinary usage patterns already anticipated by the referenced bug class. Given the pattern is repeated at four separate call sites across the contract, the probability that at least one code path eventually triggers a non-full allowance consumption over the contract's lifetime is non-trivial.

### Recommendation
Replace `safeApprove()` calls with a pattern that first resets the allowance to zero before setting a new non-zero value, or use `forceApprove()` (OZ v4.9+) / `safeIncreaseAllowance()` / plain `approve()`, e.g.:
```solidity
IERC20(depositToken).safeApprove(poolInfo.depositTarget, 0);
IERC20(depositToken).safeApprove(poolInfo.depositTarget, _amount);
```
Apply this fix to all four affected call sites: `deposit()` (line 254), `withdraw()` (line 303), `_stakeToWombatMaster()` (line 711), and `convertWOM()` (line 343), and audit any other `safeApprove()` usages in the codebase (e.g., `SmartWomConvert.sol`, `mWOM.sol`, `ManualCompound.sol`) for the same pattern.

### Proof of Concept
1. A user deposits into a Wombat pool via `WombatPoolHelperV2.deposit()` → `WombatStaking.deposit()`, which calls `IERC20(depositToken).safeApprove(poolInfo.depositTarget, _amount)` followed by `IWombatPool(poolInfo.depositTarget).deposit(...)`. [5](#0-4) 
2. Assume the pool's `deposit()` implementation, due to internal fee/haircut accounting, pulls a token amount slightly less than the full approved `_amount` (a normal AMM behavior, not requiring malicious external behavior), leaving `allowance(WombatStaking, depositTarget) > 0`.
3. Any subsequent user calls `deposit()` (or `withdraw()`, which shares the same `depositTarget` approval target) for the same pool with `_amount > 0`.
4. `safeApprove(poolInfo.depositTarget, _amount)` is invoked again with a non-zero value while a non-zero allowance still exists, and reverts with "SafeERC20: approve from non-zero to non-zero allowance", per OpenZeppelin's implementation referenced in the external report.
5. All further deposits and withdrawals to that pool through `WombatStaking` are permanently blocked, freezing already-staked user funds.
