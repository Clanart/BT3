Based on my investigation, I found a genuine analog in Protobuf's pure-Python ProtoJSON parser. Confirmed source, at `python/google/protobuf/json_format.py`, `_ConvertFieldValuePair` and `_DuplicateChecker`.

### Title
ProtoJSON pure-Python parser's "duplicate field" dispatch check is bypassable via alternate key spellings, allowing an unflagged double-write to the same field - (File: `python/google/protobuf/json_format.py`)

### Summary
The external report's failed invariant is: a dispatch table assumes each identifier (function selector) maps 1:1 to exactly one target, and the code that guards against duplicate/ambiguous identifiers doesn't account for two *different* raw identifiers resolving to the *same* target. In `protobuf`'s pure-Python ProtoJSON parser, the analogous dispatch table is `fields_by_json_name`/`fields_by_name`, which is used to resolve a JSON object key to a `FieldDescriptor`. Two syntactically different JSON keys (the field's `json_name`, e.g. `"int32Value"`, and its original proto `name`, e.g. `"int32_value"`) are both valid selectors for the very same field. The "no duplicate field" guard tracks only the raw JSON key string in the `names` list, not the resolved field, so it fails to catch the case where an attacker supplies both spellings of the same key.

### Finding Description
`json_format.Parse()` first runs the raw JSON text through `_DuplicateChecker` [1](#0-0) , which only rejects *exact* duplicate string keys (e.g. two `"int32Value"` keys). It does not - and cannot, since it runs before descriptor resolution - detect that `"int32Value"` and `"int32_value"` are two different selectors for the same field.

Later, `_ConvertFieldValuePair` resolves each JSON key to a field via `fields_by_json_name` (falling back to `fields_by_name`) [2](#0-1) , and only then checks for a duplicate by testing whether the *raw key string* `name` is already in the `names` list [3](#0-2) . Because the "already seen" check keys off the untranslated JSON string rather than the resolved `field` object (e.g. `field.number` or `field` identity), sending both the canonical name and the camelCase `json_name` for the same field silently bypasses the duplicate-field guard, and the second occurrence simply overwrites the first (last-value-wins) with no error.

This is confirmed by the project's own regression test, which documents the exact bypass and labels it an implementation oversight bug: [4](#0-3) 

By contrast, the C++/upb ProtoJSON parser closes this gap correctly: it tracks "seen" state using the *resolved* field's identity/number rather than the raw key string, so alternate spellings of the same field number are properly caught as duplicates: [5](#0-4) 

### Impact Explanation
The impact is narrow but real: any application built on the pure-Python `protobuf` runtime that relies on `json_format.Parse`'s documented "duplicate key" rejection as an input-validation/anti-ambiguity control (e.g., to reject JSON payloads where a field is set more than once, which some systems use to detect malformed/adversarial input, replay of conflicting values, or signature-covered-field tampering) can be silently bypassed by an attacker who supplies the same logical field twice using two different valid spellings (`json_name` vs. proto `name`). The final parsed value is deterministic ("last one wins," matching allowed ProtoJSON semantics per the conformance suite [6](#0-5) ), so there is no memory-safety or type-confusion impact - the risk is a false sense of security in an input-validation control that is documented to catch duplicate keys but does not catch alternate-spelling duplicates.

### Likelihood Explanation
High likelihood of triggering: the payload is a completely ordinary, well-formed, bounded JSON document sent through the standard public `json_format.Parse`/`ParseDict` API with no privileged access, unusual schema, or malformed bytes required. Any message with at least one field is affected, since `json_name` and `name` are always both valid selectors unless a custom `json_name` happens to coincide. This is not a build-time/schema-trust issue like the original report's diamond-facet registration; it is purely a runtime parsing behavior over attacker-supplied bytes, matching the required threat model.

### Recommendation
In `_ConvertFieldValuePair` (`python/google/protobuf/json_format.py`), track "already seen" state by the resolved `field` (e.g., `field.full_name` or `field.number`) instead of, or in addition to, the raw JSON key string `name`, mirroring the resolved-identity approach already used by the C++/upb `RecordAsSeen` (`SeenState`) logic in `parser_traits.h`. This closes the gap without needing to change wire-level duplicate-key detection.

### Proof of Concept
Using the pure-Python implementation of `protobuf` (verified against the project's own test at `python/google/protobuf/internal/json_format_test.py:1197-1206`):
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as pb

msg = pb.TestMessage()
# Same field ("int32_value") targeted via two different JSON key spellings.
json_format.Parse('{"int32Value": 1, "int32_value": 2}', msg)
# No ParseError is raised even though this is logically a duplicate field,
# whereas '{"int32Value": 1, "int32Value": 2}' correctly raises
# ParseError("Failed to load JSON: duplicate key int32Value.")
assert msg.int32_value == 2  # second (differently-spelled) key silently won
```

def _DuplicateChecker(js):
  result = {}
  for name, value in js:
    if name in result:
      raise ParseError('Failed to load JSON: duplicate key {0}.'.format(name))
    result[name] = value
  return result

  // Marks a field as having been "seen". This will return a SeenState
  // indicating whether it is first seen, duplicate field seen, or oneof
  // conflict seen.
  static SeenState RecordAsSeen(Field f, Msg& msg) {
    if (f->real_containing_oneof() != nullptr) {
      int oneof_index = f->real_containing_oneof()->index();
      bool oneof_inserted =
          msg.parsed_oneofs_indices_.insert(oneof_index).second;
      if (!oneof_inserted) {
        // Oneof takes precedent over Field in the case of "this is in a oneof
        // and the field is set"
        return SeenState::kOneofAlreadySeen;
      }
    }

    bool field_inserted = msg.parsed_fields_.insert(f->number()).second;
    if (!field_inserted) {
      return SeenState::kFieldAlreadySeen;
    }

    return SeenState::kFirstSeen;
  }
