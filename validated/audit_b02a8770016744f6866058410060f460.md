## Analysis

Tracing `branch: string` back through the call chain: `merge()` is called from `GitStore.merge()` with `branch.name` [1](#0-0) , where `branch` is a `Branch` object selected in the merge-choose-branch dialog and ultimately backed by `for-each-ref` parsing of local **and remote-tracking** refs [2](#0-1) . Remote-tracking branch names originate from an attacker-controlled remote's advertised refs.

Critically, when a user checks out a remote branch, Desktop creates a **local branch** using the raw, attacker-chosen name with the remote prefix stripped: [3](#0-2) 
That command is itself protected with a trailing `--` sentinel to stop `branch.nameWithoutRemote` from being parsed as a flag by `git checkout`. However, this only protects the checkout invocation — it does **not** prevent a local branch from literally being named `--strategy=...`, `-Xtheirs`, `-F/etc/passwd`, etc., since `git branch`/`checkout -b` does not restrict ref names starting with `-`.

Later, if that same local branch (or an equivalent remote-tracking ref name) is passed to `merge()`, the constructed argv has no `--` separator: [4](#0-3) 
Unlike `checkout.ts`'s deliberate use of `--` [3](#0-2) , `merge.ts` appends `branch` as the last, un-terminated argument, so `git merge` argv-parses a hyphen-prefixed branch name as an option rather than a ref.

One correction to the submitted proof idea: `--upload-pack=<cmd>` is not a recognized `git merge` option (that flag belongs to `fetch`/`clone`/`pull`), so it would not be accepted by `merge`. The realistic exploitable options are ones `git merge` does parse, e.g. `-s/--strategy=<name>`, `-X<option>`, `--squash`, `--no-verify`, `--cleanup=<mode>`, or `-F/--file=<path>` (reads a local file's contents into the generated merge commit message). None of `git merge`'s own flags directly achieve arbitrary command execution.

### Title
Argument injection via unsanitized branch name in `merge()` — missing `--` separator ([File: app/src/lib/git/merge.ts])

### Summary
`merge()` builds its `git merge` argv as `['merge', ...flags, branch]` without a `--` end-of-options marker [4](#0-3) . A branch name beginning with `-` (originating from an attacker-controlled remote's ref name, and capable of surviving into a local branch name via `checkoutBranch`'s `-b branch.nameWithoutRemote` [3](#0-2) ) is parsed by `git merge` as an option instead of a literal ref.

### Finding Description
`checkout.ts` explicitly appends a trailing `--` in `getBranchCheckoutArgs` to stop `git checkout` from misinterpreting a hyphen-prefixed branch name as a flag [3](#0-2) , showing this exact class of injection is a known concern in this codebase. `merge.ts`, however, has no equivalent protection — `branch` is pushed as the final positional argument with nothing to terminate option parsing [4](#0-3) .

### Impact Explanation
If a malicious remote advertises (or the user's checkout process materializes locally, per `nameWithoutRemote`) a branch literally named e.g. `-s=ours`, `-Xtheirs`, or `--file=<path>`, invoking `merge()` on it causes `git merge` to interpret that string as a flag rather than a ref name. This can silently change the merge strategy/outcome (e.g., forcing `ours`/`theirs` resolution so the "merge" silently discards or overrides the user's intended content — corruption of what the user subsequently commits/pushes), or, via `-F/--file=<path>`, cause a local file's contents to be embedded into the generated merge commit message, which could later be pushed to the attacker's remote and thereby exfiltrate local file contents. The submitted proof idea's specific claim about `--upload-pack=<cmd>` does not apply, since that is not a recognized `git merge` option.

### Likelihood Explanation
Exploitability depends on git accepting a ref name that begins with `-` from a remote's ref advertisement or via `checkout -b <name>` creating a local branch with that literal name, and then on the user selecting that branch as a merge source in the UI. I was not able to verify from the code/tools available whether `check-ref-format` or Desktop's own ref-name handling rejects hyphen-leading ref names anywhere upstream of `merge()`; this would need to be confirmed experimentally (as the proof idea suggests) to establish full end-to-end reachability.

### Recommendation
Add a `--` separator before `branch` in `merge.ts`'s constructed args, mirroring the pattern already used in `checkout.ts`:
```ts
args.push('--', branch)
```

### Proof of Concept
As described in the submitted proof idea: create/fetch a branch whose name is a recognized `git merge` flag (e.g. `-Xtheirs`, `--file=<path>`, or `-s=ours`), then invoke GitHub Desktop's merge UI/`GitStore.merge()` against it, and observe via terminal output capture that `git merge` parses the branch name as an option rather than failing with "not something we can merge" — this can be compared against the equivalent, protected `checkout` code path which correctly rejects/handles such names due to its trailing `--`.
