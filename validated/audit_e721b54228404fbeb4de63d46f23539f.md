## Title
Copilot conflict-resolution accepts LLM output containing partial conflict markers, allowing attacker-influenced context (commit messages / PR text from the merged branch) to silently corrupt committed file content - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
The Sherlock report is a class of bug where a security-relevant loop/condition has an incomplete check that lets one specific "invalid" element slip through unvalidated (missing check on the final owner). The closest analog in GitHub Desktop is in the Copilot conflict-resolution pipeline, where the guard that rejects unsafe/malformed model output for a resolved hunk uses an incomplete (`AND` instead of `OR`) condition, letting a resolution containing a stray/partial conflict marker pass validation and get spliced verbatim into the file that is written to disk and `git add`-ed.

### Finding Description
`parseCopilotConflictResolution` validates each hunk's `resolvedContent` with: [1](#0-0) 

```js
const rc = hunkObj.resolvedContent
if (/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)) {
  throw new CopilotValidationError(
    `... hunk ${j} of file "${path}" still contains conflict markers`
  )
}
```

This only rejects content when it contains **both** an ours-marker line (`<<<<<<< `) **and** a separator line (`=======`). A resolution string containing only one of the two (e.g. a lone `>>>>>>> theirs` or `=======` line, or a `<<<<<<<` with no matching separator) passes validation untouched. Since the model's `resolvedContent` is later spliced verbatim into the original file by `reassembleResolvedFile`: [2](#0-1) 

and that reassembled content is written directly to disk and staged without further sanitization: [3](#0-2) 

there is no defense-in-depth check on the final reassembled file before it's written and `git add`-ed. The `reassembleResolvedFile` function's own marker detector (`reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`) only looks for well-formed triples to decide what to treat as a "real" conflict block; a single stray marker line coming from the model's `resolvedContent` is just ordinary text pushed to `resultLines` with no re-validation.

The model's output is influenced by attacker-controlled input: commit messages, PR titles/descriptions and file diff content ("ours"/"theirs"/context) from the branch being merged/rebased/cherry-picked are fed into the prompt as part of `IConflictResolutionContext`/`IFileConflictContext`. A malicious remote branch or PR (crafted by an untrusted collaborator) can therefore attempt prompt injection to make the model emit `resolvedContent` with partial/malformed markers or embedded instructions that the AND-based filter does not catch, since the filter is not a complete conflict-marker scanner — it is only designed to catch the common "model echoed the whole conflict block back" failure mode, not adversarially crafted single-marker strings.

### Impact Explanation
Because the app writes `resolution.resolvedContent` straight to the file at `absolutePath` and then runs `git add` on it, incomplete validation lets content bypass the intended "no conflict markers" invariant and be silently committed/staged as the user's resolved code. This is a silent corruption of what the user commits — the exact impact category in scope — without any prompt, warning, or additional confirmation beyond the normal "Continue Merge" click, since the user is shown the AI's resolution in the result dialog but the validation gap is invisible to them (it doesn't manifest as an obvious visible diff issue like a full duplicated marker block would).

### Likelihood Explanation
This requires only that the user use the "Resolve with Copilot" feature while merging/rebasing/cherry-picking a branch or PR that contains attacker-supplied commit messages, PR title/description, or attacker-crafted diff content — a normal, unprompted workflow for anyone reviewing external contributions. No local access, admin rights, or pre-existing malware is needed; the attacker only needs to get their branch/PR into the merge context. The likelihood of a successful prompt injection producing exactly this bypass depends on model behavior, which is a real but not fully deterministic condition — flagged as the main uncertainty.

### Recommendation
Change the guard to an `OR` (reject if either marker type is present) or, better, run the same well-formed-conflict-block detector used in `reassembleResolvedFile` against `resolvedContent` to reject any line matching `<<<<<<<`, `=======`, or `>>>>>>>` markers, e.g.:

```diff
- if (/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)) {
+ if (/^<{7}(?:\s|$)/m.test(rc) || /^={7}$/m.test(rc) || /^>{7}(?:\s|$)/m.test(rc)) {
    throw new CopilotValidationError(
      `... hunk ${j} of file "${path}" still contains conflict markers`
    )
  }
```
Additionally, add a final sanity re-scan of the fully reassembled file content in `reassembleResolutions`/before the `writeFile` call in `_applyCopilotConflictResolutions` as defense-in-depth, since that is the last point before the content is persisted to disk and staged.

### Proof of Concept
1. Craft or influence a merge source (a PR/branch containing commit messages / diff text designed for prompt injection) so that when Copilot resolves a conflict hunk, its JSON response for one hunk is:
   ```json
   { "resolvedContent": "some legit-looking code\n>>>>>>> malicious-marker\n" }
   ```
   This contains a `>{7}` line but no `<{7}\s` line, so `/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)` evaluates to `false && false` → validation passes.
2. `parseCopilotConflictResolution` accepts the hunk into `validated`.
3. `reassembleResolvedFile` splices this resolved content verbatim into the file at the corresponding conflict site (lines 584-590), producing a file whose content includes the stray marker line as ordinary code.
4. `_applyCopilotConflictResolutions` writes this content to `absolutePath` via `writeFile` and runs `git add` on it (lines 7258-7267), silently committing the corrupted/marker-polluted content when the user clicks "Continue Merge".

Note: I could not fully trace the exact prompt-construction code that assembles commit/PR text into the LLM's input (search for it hit only supporting files, not the prompt-builder itself), so the precise mechanics of how attacker text reaches the model are inferred from `ConflictResolutionSystemPrompt`'s stated inputs ("recent commit messages and/or PR title/description") rather than directly observed in a single function; a Devin session with full repo access would be needed to confirm that data path exactly.
