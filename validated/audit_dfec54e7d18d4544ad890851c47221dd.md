### Title
Silent auto-rewrite of git remote URL from untrusted GitHub API `clone_url` bypasses user confirmation - (`File: app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Biconomy report describes a case where an attacker-controlled sequence of transactions manipulates pool state that the protocol trusts implicitly (front/back deposits around a victim's tx), causing the protocol to silently reward the attacker twice because the guard logic reasons only about *local* state consistency, not about *who* is driving the state change. The GitHub Desktop analog is `updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts`, which silently rewrites a repository's local git `origin` remote URL based solely on the GitHub API's `clone_url` field, using only same-class "consistency" checks (protocol match, "remote hasn't been manually changed") rather than any explicit user confirmation.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts` every time Desktop refreshes GitHub metadata for a repo: [1](#0-0) 

The function itself performs three checks and then unconditionally calls `gitStore.setRemoteURL`, with no popup, prompt, or any other form of user consent: [2](#0-1) [3](#0-2) 

The guard logic (`protocolsMatch`, `remoteUrlUnchanged`) is analogous to the LiquidityPool's `getRewardAmount` invariant: it only verifies that the *locally observed* state is internally consistent (i.e., "the current remote still equals what we last cached from the API, and the protocol scheme hasn't changed"), but it never verifies *why* the API's `clone_url` changed or that the change is something the user actually intended. Just like the LiquidityPool trusted its own before/after liquidity snapshot without a trust boundary on who produced the intervening deposit, this code trusts the GitHub API response's `clone_url` field without any user-facing confirmation step — contrasting with the explicit, user-initiated flow for changing a remote manually via `RepositorySettings`, which requires the user to type a new URL and click Save: [4](#0-3) 

Because `fetchRepository(owner, name)` simply re-queries `repos/{owner}/{name}` on every refresh, any condition that causes that endpoint to return a different `clone_url` for the same cached owner/name (e.g., a repository rename/transfer, or a "repo-jacking"-style takeover where an attacker reclaims a vacated `owner/name` slot after the original owner deletes/renames their account, or a compromised collaborator who renames the repo) will cause Desktop to automatically retarget the user's `origin` remote to the new URL — with zero notification. All subsequent `git push`/`git fetch`/`git pull` operations initiated by the user will silently transact with the new (potentially attacker-controlled) endpoint.

### Impact Explanation
If a repository is renamed/transferred (legitimately, by an admin, or through an attacker acquiring the previously-used `owner/name`), Desktop will silently swap the user's push/fetch target on their next refresh without any confirmation dialog. This falls squarely into "silent corruption of what the user commits or pushes": the user believes they are pushing to their known repository, but the local remote has been reprogrammed to point elsewhere. Depending on git credential helper configuration, this could also lead to credential/token exfiltration to the new endpoint on the next authenticated fetch/push.

### Likelihood Explanation
This code path runs automatically as part of routine background/foreground repository refreshes (`repositoryWithRefreshedGitHubRepository` is called broadly throughout `app-store.ts`), not on any unusual user action — it requires no special local access, no malware, and no credential leak; it only requires the GitHub-side `owner/name → clone_url` mapping to change while the local cached `gitHubRepository.cloneURL` still matches the existing local remote (the common case for any repo the user hasn't manually re-pointed). The existing "protocolsMatch"/"remoteUrlUnchanged" guards do not stop this because they check for *consistency*, not *authorization* or *user intent* — they were designed to avoid clobbering a manually-configured remote, not to prevent trusting an unconfirmed API-driven redirect.

### Recommendation
- Do not auto-rewrite the local git remote based on API data alone. Surface a confirmation dialog (similar to the manual "Repository Settings" flow) informing the user that the associated GitHub repository's URL has changed and asking them to confirm before `setRemoteURL` is invoked.
- If auto-update must remain for legitimate rename scenarios, pin the decision to a stronger identity signal (e.g., GitHub's stable repository `id`, not `owner/name`-derived `clone_url`) to distinguish a genuine rename from a name being reclaimed by a different repository/account.
- Log/audit and notify the user whenever the remote is changed non-interactively.

### Proof of Concept
1. User has Desktop tracking `origin` = `https://github.com/acme/widget.git`, associated in Desktop's local DB with `gitHubRepository.cloneURL = https://github.com/acme/widget.git`.
2. The `acme/widget` repository is later transferred/renamed such that the GitHub API's `repos/acme/widget` (or the owner/name pair Desktop still queries via `matchGitHubRepository`) now resolves to a different, e.g. attacker-controlled, repository whose `clone_url` is `https://github.com/acme/widget-evil.git` (achievable e.g. through a repo-jacking scenario, or an org rename by a compromised collaborator).
3. On the next automatic/background refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('acme','widget')`, gets the new `clone_url`, and calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.
4. Inside `updateRemoteUrl`: `protocolsMatch` is true (both https), `remoteUrlUnchanged` is true (cached cloneURL still equals current remote — user never touched it), `urlsMatch` is false (URL differs) → `gitStore.setRemoteURL('origin', 'https://github.com/acme/widget-evil.git')` executes silently.
5. The user's next `git push`/`fetch` from Desktop's UI silently targets the new remote with no warning shown at any point in the flow. [5](#0-4)

```typescript
import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
