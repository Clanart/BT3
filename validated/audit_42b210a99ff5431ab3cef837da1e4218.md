## Title
Silent, unvalidated rewrite of a repository's git remote URL from untrusted GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

## Summary
`updateRemoteUrl` automatically rewrites a tracked repository's `origin` remote to whatever `clone_url` the GitHub API returns for the matched repository, guarded only by a same-protocol check and a check that the remote hasn't been "manually changed" from the last-known clone URL. It never validates that the new URL still points to the same host/owner/name relationship that the user originally trusted, so a changed API response can silently redirect all future `git push`/`fetch` traffic (and the trampoline credential lookups keyed on that URL) to a different destination without any user confirmation.

## Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` periodically re-resolves the GitHub repository behind a local clone and, if a match is found, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

`updateRemoteUrl` then decides whether to overwrite the local `origin` remote: [2](#0-1) 

The only guards are:
- `protocolsMatch` — compares only the URL *scheme* (`https` vs `ssh`), not the host.
- `remoteUrlUnchanged` — checks the *current* remote still matches the *previously stored* `gitHubRepository.cloneURL` via `urlMatchesRemote`, which itself only compares `hostname`/`owner`/`name` between the **old** cached value and the **current** remote — it says nothing about the **new** `apiRepo.clone_url`.
- `!urlsMatch` — simply detects that the new URL differs from the current one.

Once these pass, `gitStore.setRemoteURL(...)` is called unconditionally with the new `clone_url`, regardless of whether it points to an entirely different host, owner, or repository: [3](#0-2) [4](#0-3) 

`apiRepo` originates from `api.fetchRepository(owner, name)`, i.e., data returned by the GitHub API/GHES endpoint for the repository the user has cloned: [5](#0-4) 

This value is attacker-influenceable in the report's sense of "a GitHub API object": a malicious/compromised GHE server, a MITM'd API response, or a legitimate repo owner who renames/transfers the repository can cause `clone_url` to point anywhere (as long as the protocol matches), and Desktop will silently rewrite the user's `origin` remote to that new destination on the next background refresh with no prompt, diff, or confirmation dialog.

## Impact Explanation
This directly matches "silent corruption of what the user commits or pushes." Once `origin` is rewritten:
- Subsequent `git push` operations silently go to the attacker-chosen remote instead of the repository the user believes they're contributing to.
- Because trampoline credential lookup (`findGitHubTrampolineAccount`) resolves credentials by matching the *account's* endpoint origin against the *remote* URL's origin, a same-host-but-different-repo redirect still authenticates seamlessly and can leak legitimate push credentials/commits to a repository outside the user's control, all without any user-visible warning. The only user-facing evidence is the (rarely inspected) Repository Settings remote-URL field.

## Likelihood Explanation
This runs automatically as part of routine background GitHub repository refresh (`repositoryWithRefreshedGitHubRepository`) for every tracked GitHub repository — no user action beyond having the app open is required. The precondition is that the tracked repository's `clone_url` as returned by the API changes to a different owner/name/host while the local remote still matches the previously cached value — achievable by a malicious repo owner (rename/transfer trick) or a compromised/MITM'd GHE(S) API response, both of which are within the stated valid attacker model ("a GitHub API object", "a git remote/proxy response").

## Recommendation
Before silently rewriting the remote, additionally verify that the new `clone_url` still resolves to the same expected identity anchor (e.g., the GitHub repository's stable database ID/`dbID`, not just owner/name strings), and/or surface an explicit, dismissible confirmation to the user before changing `origin`, rather than applying the change unconditionally once protocol/staleness checks pass.

## Proof of Concept
1. Victim clones a public repository and Desktop associates it with a `GitHubRepository` record (endpoint + `cloneURL`).
2. The repository owner (or an attacker who compromises the GHE(S) server / performs a response MITM) causes the GitHub API's `fetchRepository(owner, name)` response for that repository to return a different `clone_url` (e.g., a repo transfer/rename to an attacker-controlled destination) while keeping the same protocol scheme.
3. On the next background refresh, `app-store.ts`'s `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (still matches old cached `cloneURL`), and `urlsMatch === false` (new URL differs) — so it calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` with no user prompt.
4. The victim's next `git push` silently goes to the new remote instead of the intended repository, as confirmed by the existing unit test demonstrating the automatic rewrite: [6](#0-5) .

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```

```typescript
  public async setRemoteURL(name: string, url: string): Promise<boolean> {
    const wasSuccessful =
      (await this.performFailableOperation(() =>
        setRemoteURL(this.repository, name, url)
      )) === true
    await this.loadRemotes()

    this.emitUpdate()
    return wasSuccessful
```

```typescript
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
```
