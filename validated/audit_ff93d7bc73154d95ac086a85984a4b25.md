### Title
Missing zero-address validation in `lockFor` permanently freezes user funds - ([File: VLMGP.sol])

### Summary
`VLMGP.lockFor` and the analogous `mWomSV.lockFor` accept an arbitrary `_for` address without validating it is non-zero. Any ordinary wallet can call these unprivileged, user-facing functions and lock MGP/mWom "for" `address(0)`, permanently freezing those tokens with no possible recovery path. This is the same bug class as the reported `UmamiPriceFeed` issue (missing zero-address check leading to a locked/broken state), but here it is reachable by any unprivileged caller rather than only `onlyGov`.

### Finding Description
`lockFor` takes user-supplied tokens from `msg.sender` and credits the lock to an arbitrary `_for` address with no validation: [1](#0-0) 
The identical pattern exists in `mWomSV.sol`: [2](#0-1) 

The locked balance is tracked via `MasterMagpie.stakingInfo(address(this), _for)`, i.e. the deposit accounting lives in `MasterMagpie` keyed by the `_for` address: [3](#0-2) 

Unlocking is only ever initiated by `msg.sender` (`startUnlock` uses `msg.sender` throughout, with no `_for` parameter or delegate mechanism): [4](#0-3) 

Since `address(0)` cannot sign transactions, any MGP (or mWom) locked with `_for = address(0)` becomes permanently unreachable — no code path allows a third party to call `startUnlock`/`forceUnlock` on behalf of the zero address to retrieve it. This mirrors the report's root cause exactly: an unchecked address parameter that, if zero, locks funds in the contract with no way out — except here the entry point is the public `lockFor`/`ILocker.lockFor` function rather than a `onlyGov` setter: [5](#0-4) 

### Impact Explanation
Funds locked for `address(0)` are permanently and irrecoverably frozen, satisfying the "permanent freezing of funds" impact bar. Both `VLMGP` (vote-locked MGP) and `mWomSV` share this flaw, so the impact applies to both the MGP and Wom locking systems that underpin `MasterMagpie` reward accounting.

### Likelihood Explanation
`lockFor` is a completely public, unprivileged function requiring only that the caller hold and approve the underlying token; passing `address(0)` as `_for` is a trivial and plausible user/integration mistake (e.g., a misconfigured frontend, bot, or integrating contract that fails to populate the recipient field), with no on-chain guard preventing it.

### Recommendation
Add a zero-address check to `lockFor` in both `VLMGP.sol` and `mWomSV.sol`:
```solidity
function lockFor(uint256 _amount, address _for) override external whenNotPaused nonReentrant {
    if (_for == address(0)) revert InvalidAddress();
    _lock(msg.sender, _for, _amount);
    emit NewLock(_for, block.timestamp, _amount);
}
```
`VLMGP.sol` already defines an `InvalidAddress()` error that is unused for this purpose and can be reused here.

### Proof of Concept
1. User A approves `VLMGP` to spend MGP.
2. User A calls `lockFor(amount, address(0))`. [6](#0-5) 
3. `_lock(msg.sender, address(0), amount)` records the locked balance under `address(0)` in `MasterMagpie`'s staking info for the `vlMGP` pool.
4. No account can ever call `startUnlock` as `address(0)` (transactions cannot originate from the zero address), so the locked MGP is permanently unrecoverable.
