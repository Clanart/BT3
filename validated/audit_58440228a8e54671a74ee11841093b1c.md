### Title
`ReceivedOutput::read` trusts an embedded spend-offset and never checks it actually unlocks the claimed `TxOut` — attacker-supplied bytes can report outputs as received/spendable under the wrong key - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The Discourse bug is a crafted container whose embedded path metadata writes attacker data to an unintended location. The Serai analog is `ReceivedOutput::read`, which deserializes a `(offset, TxOut, OutPoint)` triple where the `offset` — the scalar that determines which derived key is supposed to spend the output — is taken verbatim from untrusted bytes and is never checked against `output.script_pubkey`. A crafted blob can therefore "write" an arbitrary offset onto an arbitrary outpoint, the deserialization analogue of writing a file to an attacker-chosen path.

### Finding Description
`ReceivedOutput` couples three fields that are only consistent if `output.script_pubkey == P2TR(group_key + offset * G)` (the script the `Scanner` registers under that offset). `Scanner::scan_transaction` enforces this invariant by construction: the offset is looked up from `self.scripts` keyed by the actual `script_pubkey` on chain [1](#0-0) . `ReceivedOutput::read` performs no equivalent check — it reads a canonical scalar via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns them as a coherent spendable output [2](#0-1) .

```rust
// networks/bitcoin/src/wallet/mod.rs
let offset = Secp256k1::read_F(r)?;           // attacker-chosen
output = TxOut::consensus_decode(&mut buf_r)?; // attacker-chosen script_pubkey
outpoint = OutPoint::consensus_decode(&mut buf_r)?; // attacker-chosen location
Ok(ReceivedOutput { offset, output, outpoint }) // no consistency check
```

`register_offset`'s own documentation acknowledges that offsets select which key spends the output and that arbitrary offsets can introduce script paths spendable without the key [3](#0-2) . Nothing downstream re-validates the pairing: consumers use `offset()` to re-key `ThresholdKeys` for signing and `outpoint()`/`output()` as the spend input [4](#0-3) .

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` can:

- Claim an outpoint paying to an unrelated script as "received" by the wallet (any `TxOut` + any offset). The wallet reports funds received that are not spendable — the exact accepted impact class.
- Pair a legitimately-received outpoint with the wrong offset (e.g., an offset registered for a different deposit script, or an unregistered one). Signing then proceeds under `key + offset'` while the UTXO is locked to `key + offset`, producing signatures that cannot spend it — funds effectively burned or the spend silently failing.
- Combine both: point at a victim's UTXO with an offset whose derived key is unrelated, causing the coordinator to build/sign transactions around inputs it does not control.

### Likelihood Explanation
Requires an attacker to control bytes passed to `ReceivedOutput::read` — e.g., received-output blobs relayed between components or persisted and re-read. This is a Medium analog: it needs a deserialization surface carrying untrusted data, and the result is incorrect accounting/spend failure rather than direct theft, since an invalid offset yields unspendable signatures rather than a forged spend of real funds. Severity Medium.

### Recommendation
Either make `ReceivedOutput` unforgeable-by-construction (only construct it inside `Scanner`, and store only `(offset, outpoint)` with the `TxOut` re-derived from chain data), or add a `verify`/`rekey`-time consistency check: recompute `p2tr_script_buf(scanner_key + GENERATOR * offset)` and require equality with `output.script_pubkey` before treating the output as spendable. At minimum, have `read` take the scanner's key and reject mismatched pairs.

### Proof of Concept
```rust
// Given a Scanner-derived serialized ReceivedOutput for a real deposit,
// or fresh attacker bytes entirely:
let mut buf = vec![];
buf.extend(Scalar::ZERO.to_bytes());                    // offset = base key
// TxOut paying to an arbitrary script_pubkey the attacker does NOT control
// (e.g., someone else's P2TR output, or an OP_RETURN):
buf.extend(serialize(&TxOut { value: Amount::from_sat(100_000),
                              script_pubkey: foreign_script }));
buf.extend(serialize(&OutPoint::new(victim_txid, 0)));

let ro = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted
// ro.value() == 100_000 is now "received", yet key + offset*G does not
// match foreign_script: unspendable / wrongly-attributed funds.
```
No check in `read` (lines 122–134) or in `offset()`/`output()`/`outpoint()` accessors ties the three fields together; the only place the invariant holds is the `Scanner::scan_transaction` construction path.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
