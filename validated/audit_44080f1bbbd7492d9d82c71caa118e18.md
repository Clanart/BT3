## Analysis

The Sherlock finding is about a function that silently trusts an *aggregated* value derived from attacker-influenceable inputs (multiple Uniswap pools) without validating the individual components, letting a single low-quality/malicious input corrupt the trusted result. The closest structural analog I could confirm in this Desktop fork is not an "averaging" bug, but the same failure pattern of **disabling a safety guard that exists specifically to stop untrusted/attacker-controlled repository content from corrupting host state** — here, Git's own anti-symlink clone protection is explicitly turned off by Desktop for every clone.

### Title
Desktop disables Git's clone symlink/hardlink protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) during recursive clones - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and always passes `--recursive` when invoking `git clone`. `GIT_CLONE_PROTECTION_ACTIVE` is the runtime switch Git itself introduced to prevent a malicious repository (including its submodules, cloned locally as part of `--recursive`) from using symlinks/hardlinks in its tree to make Git copy or hardlink files from outside the intended destination directory into the newly created working copy. Desktop disables this protection on every single clone it performs. [1](#0-0) 

### Finding Description
When a user clones a repository (or a nested submodule is cloned locally, which happens implicitly with `--recursive`), Git checks whether any part of the source tree resolves through a symlink to a path outside the repository, and — when the protection is active — refuses to hardlink/copy the pointed-to content. This protection is controlled by `GIT_CLONE_PROTECTION_ACTIVE`. Desktop's `clone()` function builds the environment for every clone with this flag forced to `'false'`: [2](#0-1) 

and always adds `--recursive` to the git args: [3](#0-2) 

Because the protection is off, an attacker-controlled repository (the exact threat actor allowed by the task: "attacker controls a cloned/fetched repository") can craft a tree/submodule structure containing a symlink that resolves outside the clone destination. With the guard disabled, the recursive clone can copy or hardlink content from that out-of-repo location into the user's new working directory, corrupting what actually lands on disk under the user's control.

The same disabled guard is combined with submodule handling elsewhere in the app — `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` conditionally re-enables `protocol.file.allow=always` for local submodule URLs, and `checkoutBranch`/`checkoutCommit` in `app/src/lib/git/checkout.ts` thread an `allowFileProtocol` flag through to it — showing the app is aware that local/file-protocol submodule operations are a trust boundary, yet the top-level `clone()` path has no equivalent conditional; the anti-symlink protection is turned off unconditionally rather than only for cases explicitly reviewed as safe. [4](#0-3) [5](#0-4) 

### Impact Explanation
If exploitable as intended by upstream Git's protection, this lets a malicious repository cause local host files (outside the intended clone directory) to be copied/hardlinked into the freshly cloned working tree. Since Desktop then presents that working tree to the user as ordinary "new files" in the repo, the user could unknowingly `git add`/commit/push them — silently exfiltrating local file contents (potentially credentials, SSH keys, or other sensitive files reachable via a crafted symlink target) to a remote the attacker controls. This matches the accepted impact categories: "silent corruption of what the user commits or pushes" and potential "credential/token exfiltration."

### Likelihood Explanation
Likelihood depends entirely on whether this Git build/version still exercises the `GIT_CLONE_PROTECTION_ACTIVE` check for the clone paths Desktop uses (the flag exists as Git's fix for a real, previously reported local-clone symlink issue). The attacker precondition is minimal and matches the allowed threat model — the user only needs to clone a repository the attacker controls, no local access, no admin rights, and no unnatural extra steps beyond the normal "clone this repo" action.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` unconditionally in `clone()`. Only disable the protection (if at all) for narrowly-scoped, already-trusted local operations (mirroring the existing `allowFileProtocol` pattern already used in `submodule.ts`/`checkout.ts`), and otherwise let Git's built-in guard run for all clones of user-supplied/remote URLs.

### Proof of Concept
Full exploitation requires constructing a Git tree whose recursive submodule reference resolves through a symlink to a path outside the destination — I could not fully verify against a live Desktop build in this environment. What is confirmed directly from source is the unconditional disabling of the guard for every clone call: [1](#0-0) 

**Caveat:** I could not trace all downstream callers of `checkoutBranch`/`checkoutCommit` in `app-store.ts` to confirm whether `allowFileProtocol` is ever passed as `true` in production flows (tool budget exhausted before that check completed), so I cannot state with certainty whether the submodule-specific file-protocol gate is ever actually opened outside of tests. The `clone.ts` finding above, however, is independent of that and is directly verifiable in the source shown.
