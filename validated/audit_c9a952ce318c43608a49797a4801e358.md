### Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL based on attacker-influenced GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The report's core pattern is: a value that is *checked* at one point (the fee percentage) is silently changed by a party the victim trusts (market/protocol owner) before it is *used* in a sensitive operation (`lenderAcceptBid`), with no explicit re-confirmation from the victim. The Desktop analog is `updateRemoteUrl()`, which automatically rewrites the local `origin` remote's URL to whatever `clone_url` the GitHub API currently reports for the repository, with no user prompt, whenever the previously-recorded remote still matches the repository's last-known API clone URL.

### Finding Description
`updateRemoteUrl` compares the repository's current git remote against the GitHub API's `clone_url` for that `GitHubRepository`, and if the current remote still matches the *previously known* clone URL but the *live* API value has since changed (and the URL scheme/protocol is unchanged), it calls `gitStore.setRemoteURL` to silently rewrite the remote: [1](#0-0) 

The matching logic (`urlMatchesRemote` in `repository-matching.ts`) only checks hostname/owner/name derived from regex parsing — it does not require any user interaction or confirmation before the swap: [2](#0-1) 

This mirrors exactly the "front-run" broken invariant in the Sherlock report: an entity that controls externally-reported state (there: `MarketRegistry`/`ProtocolFee` values used inside `lenderAcceptBid`; here: the `clone_url` field of the `IAPIRepository`/`IAPIFullRepository` object returned by the GitHub API) can change that state, and the client silently trusts and consumes the new value in a follow-on git operation (`push`/`pull`/`fetch`) without the user re-confirming the destination they thought they were pushing to or pulling from. A malicious or compromised repository/organization owner can rename or transfer a repository (which changes `clone_url` in the API response) to redirect a collaborator's local `origin` to a different location, and Desktop will silently rewrite the remote and then push/fetch against it on the next sync — corrupting where the user's commits go, or what content is merged into their working tree, without any confirmation dialog.

### Impact Explanation
If exploited, this leads to "silent corruption of what the user commits or pushes" (explicitly listed as valid impact): the user's `origin` can be redirected without their knowledge, so subsequent `git push` sends code to an unintended/attacker-influenced destination, and subsequent `git pull`/`fetch` can bring in content from a different repository that gets merged into the user's branch. This is analogous to the lender losing funds because a value they implicitly trusted was changed underneath them by the counterparty.

### Likelihood Explanation
The precondition (repository owner renames/transfers the repo, changing the reported `clone_url` while the user's local remote still matches the old API value) is a normal, unprivileged action available to any repository/org owner or maintainer with rename/transfer rights — no local access, no malware, and no credential leakage are required, satisfying the "unprivileged attacker controls a GitHub API object" criterion. The test suite confirms this exact automatic-rewrite behavior is implemented and expected: [3](#0-2) . I was not able to confirm from the index the exact call site and refresh cadence inside `app-store.ts` (grep only returned match counts, not surrounding code), so how frequently/automatically this runs per session is uncertain and should be verified directly in the repository.

### Recommendation
Require explicit user confirmation (a dialog similar to the existing repository-settings remote URL change flow) before silently rewriting `origin` based on API-reported `clone_url` changes, rather than performing the swap unconditionally in `updateRemoteUrl`. At minimum, surface a non-blocking but visible notification identifying the old vs. new remote URL so the user can consciously accept or reject the redirection before the next push/fetch/pull uses it.

### Proof of Concept
1. User A clones `https://github.com/org/repo` in Desktop; `GitHubRepository.cloneURL` and the git `origin` remote both equal that URL.
2. A malicious/compromised owner of `org/repo` renames or transfers the repository, so the GitHub API now reports a different `clone_url` (e.g., pointing to a different owner/name that the attacker controls or that no longer belongs to the trusted org).
3. On Desktop's next background refresh of the GitHub repository metadata, `updateRemoteUrl` sees `remoteUrlUnchanged === true` (local remote still equals the old API value) and `urlsMatch === false` (new API value differs), and protocol matches, so it calls `gitStore.setRemoteURL(...)` and silently repoints `origin` — confirmed by the existing test `"updates the repository's remote url when the github url changes"`: [3](#0-2) .
4. User A, unaware of the change, performs a normal push/pull; the operation now targets the attacker-influenced destination with no confirmation prompt.

  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

    const { gitHubRepository, gitStore } = await createRepository(
      t,
      apiRepository
    )
    assert(gitStore.currentRemote !== null)

    const originalUrl = gitStore.currentRemote.url
    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }
    await updateRemoteUrl(gitStore, gitHubRepository, updatedApiRepository)
    assert.notEqual(originalUrl, updatedUrl)
    assert.equal(gitStore.currentRemote.url, updatedUrl)
  })
