Based on my investigation, chia-blockchain's coin management model does not have an analog to this vulnerability.

The root cause in `TrufVesting.sol` is that `claimable()` computes a claim amount from a stateless time-based formula (`initialRelease`) without subtracting `userVesting.claimed`, so it can be called repeatedly during the cliff window to drain funds — an off-chain/on-chain **accounting bug** in a contract where balances are tracked by mutable ledger state (`userVesting.claimed`) rather than by consuming discrete tokens.

Chia's coin-set model is fundamentally different: every value transfer (clawback claim, CR-CAT pending-approval claim, pool-reward absorb) is expressed as spending a specific, uniquely-identified `Coin`. Once a coin is spent, it is permanently removed from the coin set and cannot be spent again — there is no analogous "claimable() recomputes a fixed amount from a stale time-based formula against a mutable claimed-counter" pattern:

- Clawback: the merkle/`P2_1_OF_N` coin is claimed via `create_merkle_solution`/`generate_clawback_spend_bundle`, consuming the actual coin; a second claim attempt on the same coin fails because it's already spent, as validated by test `chia/_tests/wallet/test_wallet.py` (`test_wallet_clawback_errors`, "no transaction for attempting to claim a coin already claimed"). [1](#0-0) 
- CR-CAT pending-approval claims (`claim_pending_approval_balance`) select specific unspent `CoinType.CRCAT_PENDING` coin records and spend them via `CRCAT.spend_many`, again consuming actual coins rather than computing a claimable amount from a time formula. [2](#0-1) 
- Pool reward claiming (`claim_pool_rewards`) iterates over actual unspent farming-reward coins and absorbs each exactly once via `create_absorb_spend`.
