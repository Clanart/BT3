### Title
Self-delegated PoX locking (`delegate-stack-stx`/`delegate-stack-increase`/`delegate-stack-extend`) bypasses the `Staking` post-condition check - (File: pox-locking/src/pox_4.rs, pox-locking/src/pox_3.rs)

### Summary
The `Staking` post-condition type exists specifically to let a signer guard against unexpected STX-locking caused by a transaction they authorize. The Rust-side PoX contract-call handlers only record a locking event into the Clarity `AssetMap`'s `stacking_map` (via `global_context.log_stacking(...)`) when the Clarity function name is the *direct* variant (`stack-stx`, `stack-increase`, `stack-extend`), and explicitly skip this recording for the *delegate* variants (`delegate-stack-stx`, `delegate-stack-increase`, `delegate-stack-extend`) — even though nothing prevents the "stacker" named in a delegate call from being the tx-sender themselves (self-delegation). This mirrors the "high-risk action not counted as high-risk" bug class from the reference report: a subset of the operations that move/lock an asset (here, delegate-flavored locking calls) is carved out of the very enumeration used to decide whether an action is covered by an asset-movement check.

### Finding Description
`check_transaction_postconditions` in `crates/stacks-transactions/src/lib.rs` enforces `Staking` post-conditions purely from `asset_map.get_stacking()` / `asset_map.get_all_stacking()`: [1](#0-0) 
and, in Deny/Originator modes, requires every principal recorded in `get_all_stacking()` to be covered by a `Staking` post-condition: [2](#0-1) 

The only way an amount enters `stacking_map` is through `AssetMap::add_stacking`, invoked indirectly via `GlobalContext::log_stacking`. In the PoX-4 handler, this call is gated by an exact function-name match: [3](#0-2) [4](#0-3) [5](#0-4) 

Note that only `"stack-stx"`, `"stack-extend"`, and `"stack-increase"` trigger `log_stacking`; the sibling `"delegate-stack-stx"`, `"delegate-stack-extend"`, `"delegate-stack-increase"` branches route into the exact same lock-application code (`pox_lock_v4`, `pox_lock_extend_v4`, `pox_lock_increase_v4`) but never call `log_stacking`, per the dispatcher: [6](#0-5) 
The PoX-3 handler has the identical asymmetry (only records for direct variants, not delegate variants) as seen in its lock-up handler: [7](#0-6) 

Nothing in the Clarity `pox-4.clar`/`pox-3.clar` `delegate-stack-stx`/`delegate-stack-increase` definitions requires that the delegated-to principal differ from the `stacker` principal — a principal can call `delegate-stx` naming themselves as `delegated-to`, then call `delegate-stack-stx`/`delegate-stack-increase`/`delegate-stack-extend` naming themselves as `stacker`. In that case the tx-sender's own STX is locked by the same code path that direct staking uses, but because the Rust dispatcher keys `log_stacking` strictly off the Clarity function name rather than off whether `stacker == sender`, the lock is never recorded in `asset_map.stacking_map`.

### Impact Explanation
The `Staking` post-condition and Deny-mode "all staked amounts must be covered" invariant exist to guarantee that a locking action affecting the signer's own account is always visible to the account's own post-conditions. `check_transaction_postconditions` treats coverage as "principal is present in `stacking_map`", so if `stacking_map` never receives an entry for a given lock, the enforcement loop at lines 393-407 silently has nothing to check — the transaction is accepted as if no staking occurred, even though the sender's STX was in fact locked. This is functionally equivalent to the "asset moving past its post-conditions" class: a `Staking` post-condition placed by the signer to bound/forbid a lock on their own account does not fire for this specific call shape, and a Deny-mode transaction that should abort due to uncovered staking will instead succeed.

### Likelihood Explanation
Requires the attacker/signer to route their own stacking lock through the delegate entry points by first self-delegating (`delegate-stx` naming themselves) — a state entirely under their own control, requiring no cooperation from anyone else and no privileged role. The exact clarity-level checks in `delegate-stx`/`delegate-stack-stx` that might forbid `delegated-to == tx-sender` or `stacker == tx-sender` could not be fully confirmed within the available search budget; this is the main source of uncertainty for exploitability.

### Recommendation
Make the `log_stacking` call unconditional on the resulting `stacker` principal rather than the Clarity function name — i.e., always record the lock/extension/increase against whichever principal actually had funds locked (`stacker`), regardless of whether the call was the direct or delegate-flavored PoX function. This restores the equality that "every principal whose STX gets locked by this transaction appears in the asset map," matching the intent of the `Staking` post-condition feature.

### Proof of Concept
1. Signer `A` calls `pox-4.delegate-stx` naming `delegated-to = A` (self-delegation), establishing delegation state for their own principal.
2. `A` submits a transaction in `TransactionPostConditionMode::Deny` with no `Staking` post-condition (or with a `Staking(NotSent)`-style condition intended to forbid locking), calling `pox-4.delegate-stack-stx(stacker: A, amount-ustx: N, ...)`.
3. `pox_locking::pox_4::handle_contract_call` dispatches to `handle_stack_lockup_pox_v4` with `function_name == "delegate-stack-stx"`; `pox_lock_v4` locks `N` uSTX for `A`, but the `if function_name == "stack-stx"` guard at `pox-locking/src/pox_4.rs:211` prevents `global_context.log_stacking(&stacker, locked_amount)` from being called.
4. `check_transaction_postconditions` never observes an entry for `A` in `asset_map.get_all_stacking()`, so the Deny-mode "uncovered staking" check at `crates/stacks-transactions/src/lib.rs:393-407` cannot trigger, and the transaction is accepted despite the intended post-condition protection.

Note: full end-to-end confirmation that `delegate-stx`/`delegate-stack-stx` permit `stacker == tx-sender` (self-delegation) in `pox-4.clar` was not completed due to tool-call limits; this should be verified directly against `stackslib/src/chainstate/stacks/boot/pox-4.clar` before treating this as fully proven.
