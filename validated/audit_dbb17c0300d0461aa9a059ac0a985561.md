### Title
Empty DLEq relation verifies successfully with attacker-supplied proof - ([File: crypto/dleq/src/lib.rs](crypto/dleq/src/lib.rs))

### Summary
`DLEqProof::verify` only checks that `generators.len() == points.len()` and then iterates over the paired slices. When both slices are empty, no generator, nonce, or point is added to the transcript, yet the verifier still derives a challenge and accepts any proof whose public `c` equals it. An attacker can generate or serialize such a proof without knowing any discrete logarithm.

### Finding Description
`DLEqProof::verify` validates only equality of the two input lengths, leaving zero as an accepted length. The verification loop then runs zero times, so `self.s` is never checked against any group equation and no claimed point is bound into the challenge. Verification succeeds whenever `self.c` equals the challenge derived from the merely domain-separated transcript. `DLEqProof::read` accepts arbitrary canonical `c` and `s`, and `DLEqProof::prove` also accepts an empty `generators` slice, making construction of the accepted proof straightforward. The existing tests explicitly exercise `i = 0`, confirming this behavior is reachable rather than hypothetical.

### Impact Explanation
A caller that accepts DLEq proofs over a dynamically supplied or accidentally empty generator set can be made to accept a proof for a statement containing no points. This is a forged verification result relative to the API’s documented purpose of proving that specified points share a discrete logarithm across generators. The attacker needs no secret key, no valid relation, and no valid nonce.

### Likelihood Explanation
The attack requires reaching `DLEqProof::verify` with an empty generator/point pair, which can occur when the relation list is attacker-controlled, decoded from untrusted input, filtered before verification, or constructed incorrectly. Because neither `prove` nor `verify` rejects empty input, and untrusted `DLEqProof` bytes deserialize without a lower-bound check, exploitation requires only canonical scalar encodings.

### Recommendation
Reject empty relations in both `DLEqProof::prove` and `DLEqProof::verify`. For a discrete-log equality proof, require at least two generators, or at minimum enforce `generators.len() == points.len() && !generators.is_empty()` if single-generator Schnorr-style use is intentionally supported. Consider similarly requiring at least one discrete logarithm in `MultiDLEqProof::prove` and `MultiDLEqProof::verify`.

### Proof of Concept
The following pattern produces a proof that verifies while proving no equality relation:

```rust
use rand_core::OsRng;
use zeroize::Zeroizing;
use ff::Field;
use k256::{Scalar, ProjectivePoint};
use transcript::RecommendedTranscript;
use dleq::DLEqProof;

let secret = Zeroizing::new(Scalar::random(&mut OsRng));

// No generators and therefore no claimed points.
let generators: &[ProjectivePoint] = &[];
let points: &[ProjectivePoint] = &[];

let proof = DLEqProof::prove(
    &mut OsRng,
    &mut RecommendedTranscript::new(b"attacker context"),
    generators,
    &secret,
);

// Accepted even though no scalar multiplication, point, or nonce was checked.
proof
    .verify(
        &mut RecommendedTranscript::new(b"attacker context"),
        generators,
        points,
    )
    .unwrap();
```

The root cause is that `verify` checks only equal lengths before an empty `zip` loop and final challenge comparison, while deserialization accepts arbitrary `c` and `s` scalars. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  /// Verify the specified points share a discrete logarithm across the specified generators.
  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[G],
    points: &[G],
  ) -> Result<(), DLEqError> {
    if generators.len() != points.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"dleq");
    for (generator, point) in generators.iter().zip(points) {
      Self::verify_statement(transcript, *generator, *point, self.c, self.s);
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }

    Ok(())
  }
