### Title
PedPoP decrypts attacker-controlled ciphertext and emits ECDH-revealing blame before the proof-of-possession is verified - (crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
The SurrealDB bug class is "an attacker-supplied expression is evaluated against protected data before the authorization check that would reject it." In Serai's PedPoP DKG, the exact same ordering inversion exists: `Encryption::decrypt` performs the ECDH key agreement and ChaCha20 decryption of a received `EncryptedMessage` immediately, while the per-message proof-of-possession (`msg.pop`) — the only check that authorizes the message's encryption key — is merely queued into a `BatchVerifier` and not verified until later. Worse, `KeyMachine::calculate_share` can early-return an `InvalidShare` error carrying the blame proof (which contains the raw ECDH shared key) *before* `batch.verify_with_vartime_blame()` ever runs, so a message whose PoP would fail still forces disclosure of the ECDH key.

### Finding Description
`Encryption::decrypt` queues `msg.pop.batch_verify(...)` and then, without any verification having occurred, computes `ecdh::<C>(&self.enc_key, msg.key)` and applies the keystream to the ciphertext, returning an `EncryptionKeyProof` whose `key` field is the raw ECDH shared point `b * msg.key`. [1](#0-0) 

In `KeyMachine::calculate_share`, the loop calls `decrypt`, then attempts `C::F::from_repr(share_bytes.0)`. If the decrypted bytes are a non-canonical scalar, it returns `PedPoPError::InvalidShare { blame: Some(blame) }` via `?` on line 482 — before `batch.verify_with_vartime_blame()` on line 493 ever verifies the queued PoP. [2](#0-1) 

The PoP exists precisely to prevent this: the comment on `EncryptedMessage` explains that without it, Eve can reuse Alice's per-message encryption key X, induce Bob to publish a blame proof revealing `bX` (Bob's ECDH with X), and thereby decrypt Alice's real message to Bob. [3](#0-2)  Because the blame path escapes before the batch check, that protection is void: the "permission check" (PoP verification) runs after the side effect (ECDH decryption + blame-key disclosure) — the same ordering flaw as the advisory.

### Impact Explanation
A DKG participant Eve observes the authenticated channel, copies Alice's per-message encryption key `X` from Alice's `EncryptedMessage` to Bob, and sends Bob her own `EncryptedMessage { key: X, pop: <invalid>, msg: <ciphertext that decrypts under the bX cipher to non-canonical scalar bytes> }`. Eve fully controls the ChaCha20 plaintext, so making `from_repr` fail is trivial. `calculate_share` returns `InvalidShare` with `blame.key = bX` before the PoP is checked; the processor serializes and broadcasts this blame (`ProcessorMessage::InvalidShare`, processor/src/key_gen.rs:419-425). Anyone holding the blame can derive the cipher for context and `bX` and decrypt Alice's genuine secret share to Bob, leaking a secret share of an honest dealer's polynomial — confidential protocol data exposed before authorization, matching the CWE-863 "incorrect authorization ordering" class. Severity is bounded because a single leaked share-of-share does not alone reach the threshold, and blame verification later attributes fault to Eve via `decrypt_with_proof`'s PoP check — but the ECDH key is already public. [4](#0-3) 

### Likelihood Explanation
Requires only a DKG participant sending a malformed `EncryptedMessage` — public inputs to `EncryptedMessage::read`/`calculate_share`. No collusion or network control needed; the plaintext condition (non-canonical scalar) is fully attacker-chosen.

### Recommendation
Verify `msg.pop` synchronously inside `Encryption::decrypt` (as `decrypt_with_proof` already does at encryption.rs:374-379) before computing `ecdh` and before returning any `EncryptionKeyProof`; alternatively, in `calculate_share`, run the batch verification for the `BatchId::Decryption` statements before deserializing the share and before attaching blame. Never release `proof.key` for a message whose PoP has not been verified.

### Proof of Concept
1. Bob runs `KeyMachine::calculate_share` with shares from all participants.
2. Eve submits `EncryptedMessage::read`-parseable bytes with `key = X` (copied from Alice's message to Bob), an arbitrary invalid `pop`, and `msg` = ChaCha20 ciphertext chosen so that after `cipher(context, bX).apply_keystream` the bytes are `>= q` (e.g., `0xFF…FF`).
3. `decrypt` queues the (failing) PoP into `batch`, computes `key = ecdh(b, X)`, decrypts, returns `EncryptionKeyProof { key: bX, dleq }`.
4. `from_repr` fails → early `Err(InvalidShare { blame: Some(proof) })` at lib.rs:480-482; `batch.verify_with_vartime_blame()` at line 493 is never reached, so the invalid PoP is never detected.
5. The blame `bX` is broadcast; Eve/any observer reconstructs `cipher(context, bX)` and decrypts Alice's real ciphertext, recovering Alice's secret share to Bob.
