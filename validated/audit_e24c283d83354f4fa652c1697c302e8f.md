### Title
Deterministic cached FROST preprocess is reused across `share` and `complete`, enabling nonce reuse and MuSig secret share recovery for the same DKG-confirmation attempt - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class in ALPINE-CVE-2024-28960 is mishandling of shared/reused cryptographic state (the PSA Crypto API operating incorrectly on shared memory). Serai's analog is the coordinator's `SigningProtocol`, which persists a FROST `CachedPreprocess` (the ChaCha20 seed that deterministically regenerates the signing nonces) in the DB keyed only by `(b"DkgConfirmer", attempt)`, and reloads that same seed every time a share or completion is computed. Because `seeded_preprocess` derives the nonces purely from this seed plus `original_secret_share()`, any two `sign()` invocations under the same context that differ in either the participant set or the message produce two signature shares over identical nonces, which is a textbook private-key-share recovery.

### Finding Description
`preprocess_internal` stores the preprocess seed in `CachedPreprocesses`, encrypted under `Blake2s256("Cached Preprocess Encryption Key" || context || key)`, but it is **never consumed or deleted**: every call re-reads the same row and calls `AlgorithmSignMachine::from_cache`, regenerating identical `nonces` (`crypto/frost/src/sign.rs:121-144`, where `ChaCha20Rng::from_seed(*seed.0)` feeds `Commitments::new` keyed by `params.keys.original_secret_share()` — our key, independent of the participant set).

Two paths then invoke `share_internal` (which calls `preprocess_internal` and then `machine.sign(preprocesses, msg)`):

1. `DkgConfirmer::share` (line 304) — publishes a share for `set_keys_message(set, removed, key_pair)` over the preprocess set supplied.
2. `DkgConfirmer::complete` (line 312) — **re-executes** `share_internal` with a caller-supplied `preprocesses`/`key_pair` pair to rebuild the signature machine.

If the `preprocesses` map handed to `complete` differs from the one used at `share` time — which can occur without any Byzantine fault, e.g., a different valid supermajority subset of `t`-of-`n` MuSig signers providing shares, or a different `key_pair`/`removed` set under the same `attempt` — the same nonce `(d, e)` is combined with different binding factors `rho` and/or a different challenge `c`, yielding two shares `z = d + (e·rho) + (c·lambda·s_i)` and `z' = d + (e·rho') + (c'·lambda·s_i)` that form a solvable linear system recovering the secret share `s_i` — here, the validator's own MuSig/Ristretto key (`self.key`), i.e., the root-of-trust validator key, not merely an ephemeral DKG share.

The file's own header (lines 25-55) documents this exact hazard ("it is explicitly unsafe to reuse nonces across signing sessions") and defends it only via BFT ordering plus a still-open `TODO` to check that on-chain commitments match presumed preprocesses — the same note admits Processor-side preprocesses need the same review. The persisted cache additionally means a process restart mid-attempt reloads identical nonces, while the header's safety argument ("upon any complete rebuild, we'd re-decide nonces") is wrong whenever the DB (which holds `CachedPreprocesses`) survives the rebuild.

### Impact Explanation
Recovery of the validator's secret key from two published signature shares. The key being leaked is the coordinator-side validator signing key used for `set_keys` DKG confirmation on Substrate — compromise of it lets an attacker forge that validator's participation in subsequent DKG confirmations / validator-set messages. Severity: High (key share recovery via published shares under a deterministic nonce).

### Likelihood Explanation
Likelihood hinges on the coordinator ever calling `sign` twice for one `attempt` with differing `preprocesses`, `key_pair`, or `removed`. `complete` unconditionally re-invokes `share_internal` with caller-provided preprocesses rather than reusing the exact set used at `share` time, so any path delivering a different signer subset to `complete` (a different supermajority completing the threshold, an out-of-order/replayed delivery, or a restart between `share` and `complete`) produces the collision with no malicious action required. I was unable to fully trace the `handle.rs` call sites within the available iterations to confirm a concrete external trigger, so likelihood is Medium pending that verification; the cryptographic root cause (nonce determinism + non-consumed cache + double sign execution) is confirmed in code.

### Recommendation
- Key `CachedPreprocesses` by a binding of `(context, participant set hash, msg hash)` rather than `context` alone, and have `preprocess_internal`/`sign` assert equality of the bound values, so any divergence fails instead of signing with reused nonces.
- In `DkgConfirmer::complete`, persist the `AlgorithmSignatureMachine` (or the exact preprocess map + share) produced during `share` rather than re-executing `share_internal` with newly supplied preprocesses.
- On loading a cached preprocess for `sign`, atomically delete/flag the `CachedPreprocesses` row so a restart cannot re-derive the same nonces; regenerate on the next `preprocess` if no share was ever published for it.
- Implement the acknowledged TODO: verify on-chain preprocess commitments match the presumed cached preprocess before publishing any share.

### Proof of Concept
1. `DkgConfirmer::share(preprocesses_A, key_pair)` is invoked for `attempt = k`. `preprocess_internal` loads cached seed `S` (context `(b"DkgConfirmer", k)`), producing nonces `(d, e)` and share `z_A = d + e·rho_A + c_A·λ·s_i`, which is published.
2. `DkgConfirmer::complete(preprocesses_B, key_pair, shares)` is later invoked with `preprocesses_B ≠ preprocesses_A` (a different valid signing subset for the same attempt — different `included` ⇒ different `rho_i` per `Curve::hash_binding_factor`). `share_internal` reloads the same seed `S` (the row was never deleted), regenerates `(d, e)`, and emits `z_B = d + e·rho_B + c_B·λ·s_i`.
3. With `z_A`, `z_B`, `rho_A`, `rho_B`, `c_A`, `c_B`, and `λ` all public/computable, solve the 2×2 linear system for `(d + e·…)` terms to recover `s_i` = the validator's secret key.
