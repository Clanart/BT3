### Title
Contract governance path can set `kip71.lowerboundbasefee` > `kip71.upperboundbasefee`, bypassing the consistency check enforced for header-based votes - (File: kaiax/gov/contractgov/impl/getter.go, kaiax/gov/paramset.go, params/kip71_config.go)

### Summary
`ParamSet.Set()` and `PartialParamSet.Add()` only perform type/format checks per individual parameter (via each param's own `FormatChecker`, which is `noopFormatChecker` for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`), with no cross-field validation that `LowerBoundBaseFee <= UpperBoundBaseFee`. That cross-check exists only in `headerGovModule.checkConsistency()`, which is exercised solely on the header-vote path (`VerifyGov`/`VerifyVote`). The contract-governance path (KIP-81, `GovParam` contract) that feeds `contractGovModule.GetParamSet()` never calls `checkConsistency`, so a `kip71.lowerboundbasefee` value larger than the current `kip71.upperboundbasefee` (or vice versa) can be committed to state via `GovParam.setParam`/`setParamIn` and later be read back as the effective governance parameter set.

### Finding Description
The governance module aggregates parameters from header governance and contract governance: [1](#0-0) 

For header-based votes, `checkConsistency()` explicitly cross-validates the KIP-71 bounds before a vote is accepted: [2](#0-1) 

However, for contract governance, `contractGovModule.GetParamSet()` builds the parameter set purely by calling `ret.Set(k, v)` for every name/value pair returned from the `GovParam` contract's `getAllParamsAt`, with no equivalent consistency check: [3](#0-2) [4](#0-3) 

`ParamSet.Set()` performs only a type assertion for each parameter name in isolation — it never compares `LowerBoundBaseFee` against `UpperBoundBaseFee`: [5](#0-4) 

`PartialParamSet.Add()`, used when parsing contract call results, only runs the per-parameter `Canonicalizer`/`FormatChecker`, and both KIP-71 bound parameters use `noopFormatChecker` (always returns true), so no bound is enforced there either: [6](#0-5) [7](#0-6) 

Since `GovParam.setParam`/`setParamIn` (KIP-81 contract governance) lets the GC set `lowerboundbasefee` and `upperboundbasefee` as two independent calls with independent activation blocks, a GC member can set `lowerboundbasefee` to a value greater than the currently effective `upperboundbasefee` (or set them in an order/activation-block combination that produces `lower > upper`) without any node rejecting it, because the only guard (`checkConsistency`) is bypassed on this path.

Once `LowerBoundBaseFee > UpperBoundBaseFee` reaches `ParamSet.ToKip71Config()` and is fed into `KIP71Config.NextMagmaBlockBaseFee()`, the base-fee algorithm's invariants break: [8](#0-7) 
The function clamps `parentBaseFee` first to `upperBoundBaseFee` then to `lowerBoundBaseFee` — with `lowerBoundBaseFee > upperBoundBaseFee`, the resulting `baseFee` value used in `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` becomes inconsistent between the lower and upper clamps, producing either a base fee that no longer respects normal ordering, or a base fee that can make legitimate transactions unable to satisfy `GasFeeCap >= BaseFee` in `preCheck()`: [9](#0-8) 
and in the tx pool's `ErrFeeCapBelowBaseFee`/`ErrGasPriceBelowBaseFee` checks: [10](#0-9) 

### Impact Explanation
This is analogous to the Sense `Divider.issue()` bug: a critical protocol invariant (`ISSUANCE_FEE_CAP` check in the original report; here, `LowerBoundBaseFee <= UpperBoundBaseFee`) is enforced on one entry point (Adapter's owner-controlled fee update / header-vote path here) but omitted on another equally reachable entry point (constructor in Sense; contract-governance `GovParam.setParam` here). The result can be that the base-fee computation and, consequently, the entire transaction-pool/state-transition gas-price acceptance logic diverges from the intended KIP-71 semantics, potentially rejecting all normal transactions (chain-wide DoS on tx acceptance) or admitting transactions at incorrect fee levels network-wide — a chain-wide availability/consensus-parameter integrity issue reachable purely through the governance-parameter contract, which the scope explicitly allows as an analog category.

### Likelihood Explanation
Exploitation requires the actor able to call `GovParam.setParam`/`setParamIn` (the contract owner / GC-authorized account under KIP-81), not an arbitrary unprivileged sender. This is a lower likelihood than a fully public entry point, but it is squarely within the "governance parameters" analog category explicitly permitted by the task rules, and the root cause (missing cross-field validation on one path while present on another) mirrors the reported bug class precisely. The bug is a straightforward "guard exists on path A, missing on path B" gap, not a resource-only or purely theoretical issue — it is directly reachable by a governance transaction and directly reachable by chain block-production/verification logic afterward.

### Recommendation
Enforce the `LowerBoundBaseFee <= UpperBoundBaseFee` (and any other necessary KIP-71 cross-field constraints) inside `ParamSet.Set()`/`SetFromMap()` (or immediately after merging in `contractGovModule.GetParamSet()`), so that the same consistency invariant currently checked only in `headerGovModule.checkConsistency()` is uniformly applied regardless of whether the parameter originates from header voting or from the `GovParam` contract. Alternatively, add a `ParamSet`-level `Validate()` method invoked by every producer of a `ParamSet` (header, contract, and merged) before it is returned to callers such as `ToKip71Config()`.

### Proof of Concept
1. Deploy `GovParam` contract and register it via header vote `gov.GovernanceGovParamContract` (post-Kore fork), as done in `tests/gov_contract_test.go`. [11](#0-10) 
2. As the GovParam owner, call `setParamIn("kip71.upperboundbasefee", true, <small value>, activation)` to lower the effective upper bound.
3. In a later block (after the above activates), call `setParamIn("kip71.lowerboundbasefee", true, <value greater than the now-active upper bound>, activation)`.
4. Both calls succeed because `ParamSet.Set`/`PartialParamSet.Add` never compare the two fields against each other (unlike `checkConsistency` for header votes), and `contractGovModule.GetParamSet()` never invokes `checkConsistency`.
5. Once both changes are active at the same block, `GetParamSet(num).ToKip71Config()` returns a `KIP71Config` with `LowerBoundBaseFee > UpperBoundBaseFee`, which is then passed into `NextMagmaBlockBaseFee`, producing an inconsistent/invalid `expectedBaseFee` for subsequent blocks and potentially causing `VerifyMagmaHeader` failures or malformed base-fee enforcement in `preCheck`/tx pool validation network-wide.

func (c *contractGovModule) GetParamSet(blockNum uint64) gov.ParamSet {
	m, err := c.contractGetAllParamsAt(blockNum)
	if err != nil {
		return *gov.GetDefaultGovernanceParamSet()
	}

	ret := *gov.GetDefaultGovernanceParamSet()
	for k, v := range m {
		err = ret.Set(k, v)
		if err != nil {
			return *gov.GetDefaultGovernanceParamSet()
		}
	}

	return ret
}

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]

		return ErrInvalidParamName
	}

	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
