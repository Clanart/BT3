### Title
Excess native-token overpayment in `EvmHost.dispatch()` / `fundRequest()` is silently trapped in the contract instead of being returned to the payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native ETH and route it through `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` to buy an exact amount of `feeToken()`. This mirrors the exact bug class from the seed report: a swap-integration call whose parameters and refund path are not adapted to the actual caller/context, causing value to be misdirected.

### Finding Description
In all three entry points the swap is invoked with `msg.sender` (from the router's perspective) being `EvmHost` itself, because `EvmHost` is the contract calling the router, not the end user: [1](#0-0) [2](#0-1) 

`UniswapV2Router02.swapETHForExactTokens` only pulls the exact input amount needed to obtain `fee`/`amount` output tokens; if `msg.value` supplied by the user exceeds that requirement, the router refunds the difference to its own `msg.sender` — which here is `EvmHost`, not the original caller (`_msgSender()`/user) who sent the ETH into `dispatch`/`fundRequest`. There is no logic in `EvmHost.sol` that forwards this refunded ETH back to the user, tracks it as a per-user balance, or exposes any withdrawal path for stray native ETH held by the contract. Once the refund lands in `EvmHost`, it becomes indistinguishable protocol-owned ETH with no accounting entry tying it back to the overpaying user.

This is the direct analog of the seed report's root cause: a swap-integration call is invoked with parameters/recipients that don't match the caller's actual context (there, wrong pool fee/router per chain; here, wrong refund recipient), and the surrounding code has no correction or accounting for the resulting mismatch.

### Impact Explanation
Any user who calls `dispatch()` or `fundRequest()` with `msg.value` even slightly greater than what's needed to purchase the exact `fee`/`amount` of `feeToken` permanently loses the excess ETH — it is swept into `EvmHost` with no recovery mechanism visible in the reviewed contract. Since users must estimate the required ETH input off-chain against a router quote that can move between quote-time and execution-time (due to normal AMM price movement or MEV), some overpayment margin is a realistic, common occurrence, not an edge case. This is a direct, unauthorized loss of user funds matching the bounty's "stealing or loss of funds" category, triggered purely by normal use of a public entrypoint — no malicious relayer, prover, or admin is required.

### Likelihood Explanation
High. Any caller supplying `msg.value` computed with a safety margin above the router's live quote (standard practice to avoid revert on slippage) will trigger this path on every call. No special conditions, front-running, or privileged actors are needed — this is a plain unprivileged user interaction with `dispatch()`/`fundRequest()`.

### Recommendation
Capture the actual ETH consumed by the swap (e.g., compare `address(this).balance` before/after, or use `swapExactETHForTokens`/read `amounts[0]` returned by `swapETHForExactTokens`) and refund any unused `msg.value` to `_msgSender()` (or `post.payer`) at the end of `dispatch()`/`fundRequest()`, rather than letting the router refund to `address(this)` with no forwarding logic.

### Proof of Concept
1. User calls `dispatch(DispatchPost{ fee: F, ... })` with `msg.value = V > required_input_for(F)` (e.g., padding for slippage protection).
2. `EvmHost` calls `swapETHForExactTokens{value: V}(F, [WETH, feeToken], address(this), deadline)` — see [1](#0-0) .
3. Router pulls only the ETH needed for `F` feeToken and refunds `V - required_input_for(F)` to its caller, `EvmHost`.
4. `EvmHost` has no code path in `dispatch()`/`fundRequest()` (verified end-to-end through line 1051) that forwards this refund to the user; the request is committed and the function returns with the excess ETH now held by the contract with no per-user accounting.
5. The user has permanently lost `V - required_input_for(F)` ETH with no way to reclaim it through any function reviewed in `EvmHost.sol`.

Note: I was not able to fully verify whether `EvmHost` defines a `receive()`/`fallback()` function or any generic native-ETH withdrawal path elsewhere in the contract (index/size limits may have truncated some sections); if such a function exists but has no linkage back to per-depositor accounting, the fund-loss conclusion still holds. A Devin session with full filesystem access would be needed to conclusively rule out an existing sweep/withdraw mechanism for stray ETH.
