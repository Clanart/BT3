### Title
Unbounded recursion during `AccountKeyRoleBased` RLP/JSON decoding permits stack-exhaustion DoS on any node decoding an AccountUpdate transaction - (File: blockchain/types/accountkey/account_key_serializer.go)

### Summary
CVE-2019-9903 is a stack-consumption bug caused by unbounded recursive object marking (`PDFDoc::markObject` → `Dict::find`) triggered by a crafted, deeply-nested structure passed to a public-facing binary. The analogous pattern in Kaia is the recursive decoding of `AccountKeyRoleBased`, which can contain arbitrarily nested `AccountKeyRoleBased` values during RLP/JSON decoding, before any depth or composite-type restriction is applied.

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes a key type tag and then recursively decodes the concrete `AccountKey` value: [1](#0-0) 

When the tag is `AccountKeyTypeRoleBased`, the concrete value is an `AccountKeyRoleBased`, i.e. a slice of `AccountKey`, each element itself decoded through the same `AccountKeySerializer` machinery. Nothing in this decode path enforces that nested role keys cannot themselves be `AccountKeyRoleBased`. The "no nested composite type" rule is only enforced *after* full decoding has already completed, inside `CheckInstallable`/`CheckUpdatable`/`checkAccountKeyZeroValues`: [2](#0-1) [3](#0-2) 

Because these guards run only after the transaction/account key has been decoded, an attacker only needs to submit a raw RLP-encoded `TxTypeAccountUpdate` transaction whose `AccountKey` field is a chain of nested `AccountKeyRoleBased{AccountKeyRoleBased{AccountKeyRoleBased{...}}}` values. Decoding this structure (via `tx.DecodeRLP`/`AccountKeySerializer.DecodeRLP` or the JSON variant `AccountKeySerializer.UnmarshalJSON`) recurses once per nesting level with no depth limit, matching the root cause class of CVE-2019-9903 (recursive marking with no recursion bound, leading to stack exhaustion on crafted input reachable through a public entry point). The RLP package's own documentation acknowledges the absence of any general recursion/size safeguard: [4](#0-3) 

### Impact Explanation
Any unprivileged transaction sender can submit (or broadcast/RPC-submit) an `AccountUpdate` transaction with a deeply nested `AccountKeyRoleBased` payload. Because decoding happens before the composite-type check and before full transaction validation/gas metering, every node that receives and attempts to decode this transaction (via `TxPool.AddRemote`, block processing, or `eth_sendRawTransaction`) will recurse proportionally to the attacker-chosen nesting depth. In Go, unbounded recursion that exceeds the runtime-managed goroutine stack results in an unrecoverable `fatal error: stack overflow`, which terminates the entire process — not just the offending goroutine — causing a denial of service against the consensus/RPC node that processed the transaction.

### Likelihood Explanation
Likelihood is limited primarily by transaction size limits enforced by the network/tx pool (e.g., max transaction size), which bounds how many nesting levels can be packed into a single transaction. Each `AccountKeyRoleBased` nesting level requires only a small number of bytes (a key-type tag plus a short RLP list header), so a large number of nesting levels can plausibly be packed within typical transaction size limits, though the exact number of levels needed to trigger a stack overflow given Go's dynamically-growing goroutine stacks was not independently verified in this review (this is a known unresolved point of uncertainty).

### Recommendation
Enforce a maximum recursion/nesting depth check inside `AccountKeySerializer.DecodeRLP` and `AccountKeySerializer.UnmarshalJSON` (or in `AccountKeyRoleBased`'s decode path) *before* recursing into nested keys, rejecting any `AccountKeyRoleBased` value that contains another `AccountKeyRoleBased` at decode time rather than only after decoding completes. This mirrors the existing `IsCompositeType`/`ErrNestedCompositeType` semantics but applies the check eagerly during decode instead of post-decode.

### Proof of Concept
Conceptually:
1. Construct an `AccountKeyRoleBased` value `K0 = AccountKeyRoleBased{AccountKeyPublic}`.
2. Iteratively wrap: `K_{i+1} = AccountKeyRoleBased{K_i}` for N iterations, RLP-encoding each level so the final blob is a single nested `AccountKeySerializer`-encoded value with N levels.
3. Build a `TxTypeAccountUpdate` transaction whose `TxValueKeyAccountKey` is `K_N`, sign it (validity of signature is irrelevant since decoding happens before signature verification/composite check).
4. Submit the raw transaction bytes via `eth_sendRawTransaction`/`txpool.AddRemote`, or include it in gossip; observe `rlp.Decode`/`AccountKeySerializer.DecodeRLP` recurse N times through `NewAccountKey` → `s.Decode(serializer.key)`, exhausting stack before `checkAccountKeyZeroValues`/`CheckInstallable` (which reject nested composite types) ever execute.

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
