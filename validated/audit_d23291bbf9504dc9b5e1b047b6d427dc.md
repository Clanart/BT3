## Verdict: Valid, but with an important caveat about the actual attack surface

The core mechanism described is real, but the vulnerability is not a shell/argument-injection issue (git is invoked via `spawn(args, path, ...)` with an argv array, never a shell string, so no metacharacter escaping is needed there). It is a **commit-message trailer injection**: an unsanitized, attacker-influenced string is embedded as a single `--trailer` value, and if that string contains an embedded literal newline, `git interpret-trailers` will emit that newline verbatim in the trailer block of the resulting commit message. If the injected second line itself looks like `Token: value`, any trailer-consuming tool (including Desktop's own `parseTrailers`/`git log --format=%(trailers)` and GitHub's web UI) will parse it as a second, independent, seemingly legitimate trailer that the user never typed.

### Finding Description

`getCoAuthorTrailers` builds a raw `Name <email>` string with no validation: [1](#0-0) 

This flows unmodified into `ICommitContext.trailers`, then into `formatCommitMessage` → `mergeTrailers`: [2](#0-1) 

`mergeTrailers` pushes `--trailer`, `` `${trailer.token}=${trailer.value}` `` as a single argv element with no escaping of embedded newlines: [3](#0-2) 

Because `git()` ultimately calls `spawn(args, path, ...)` (dugite), the string is passed as one argv element via `execve`, so classic shell injection is not possible — but a literal `\n` byte inside that argv string is preserved by git and written verbatim into the trailer block of the formatted commit message.

The `email` (and `name`) fields that feed `a.email`/`a.name` originate from `IMentionableUser`, populated from the GitHub API's mentionables response (`IAPIMentionableUser.email`/`.name`) with no format/character validation performed anywhere in the pipeline: [4](#0-3) [5](#0-4) 

Neither `GitHubUserDatabase`, `matchMentionableUsers`, `UserAutocompletionProvider`, nor `AuthorInput.authorFromUserHit` perform any sanitization of the name/email strings before they're used to build the trailer value: [6](#0-5) 

### Impact Explanation

If a mentionable user's `email` (or, more plausibly, their less-validated `name`) contains an embedded newline followed by attacker-chosen `Token: value` text, selecting that user as a co-author silently injects an extra, spoofed trailer into the committed message — a form of "silent corruption of what the user commits," which is within the valid-impact scope. This could be used to spoof `Signed-off-by`, `Reviewed-by`, or other trailers that downstream tooling (CI, GitHub UI, repo rules) trusts.

### Likelihood Explanation

Likelihood is low-to-moderate and the caveat matters:
- On GitHub.com, the `email` field returned by the mentionables API is the user's *verified/attributable* email, and GitHub server-side email validation would reject a raw newline or a bare `>` in a deliverable address, making this specific vector hard to exploit against dotcom without a compromised/malicious server.
- The `name` field, however, is a free-text profile "real name" with much looser validation on GitHub, and is a more plausible vector for embedding special characters (this needs to be confirmed against current GitHub name-field validation, which is outside this codebase).
- This is reachable per the stated scope's "attacker controls ... a GitHub API object" criterion (e.g., malicious/compromised GitHub Enterprise Server, or any future looser validation on dotcom), and it also requires the victim to add the attacker's account as a co-author — a normal, expected collaboration action, not an "unnatural" step.

### Recommendation

Sanitize (or reject) trailer tokens/values before passing them to `git interpret-trailers`: strip or reject embedded `\n`/`\r` characters (and validate `token` doesn't contain `=`/whitespace) in `getCoAuthorTrailers` (`app/src/ui/changes/commit-message.tsx`) and/or centrally in `mergeTrailers` (`app/src/lib/git/interpret-trailers.ts`) before constructing the `--trailer` argument, regardless of where the co-author name/email originated.

### Proof of Concept

1. Mock/intercept the mentionables API response (or point the client at a malicious GitHub Enterprise-like endpoint) so `getMentionableUsersMatching` returns a user with `name: "Evil"` and `email: "x>\nEvil-Trailer: pwned <e@e.com"` (or embed the newline in `name` if email validation blocks it).
2. Add this user as a co-author via the commit message co-author input and create a commit.
3. Inspect the resulting commit message: it contains an extra `Evil-Trailer: pwned <e@e.com>` line in the trailer block that the user never typed, which `git log --format=%(trailers)` and other trailer-aware consumers will parse as a legitimate trailer.

export async function formatCommitMessage(
  repository: Repository,
  context: ICommitContext
) {
  const { summary, description, trailers } = context

  // Git always trim whitespace at the end of commit messages
  // so we concatenate the summary with the description, ensuring
  // that they're separated by two newlines. If we don't have a
  // description or if it consists solely of whitespace that'll
  // all get trimmed away and replaced with a single newline (since
  // all commit messages needs to end with a newline for git
  // interpret-trailers to work)
  const message = `${summary}\n\n${description || ''}\n`.replace(/\s+$/, '\n')

  return trailers !== undefined && trailers.length > 0
    ? mergeTrailers(repository, message, trailers)
    : message

export async function mergeTrailers(
  repository: Repository,
  commitMessage: string,
  trailers: ReadonlyArray<ITrailer>,
  unfold: boolean = false
) {
  const args = ['interpret-trailers']

  // See https://github.com/git/git/blob/ebf3c04b262aa/Documentation/git-interpret-trailers.txt#L129-L132
  args.push('--no-divider')

  if (unfold) {
    args.push('--unfold')
  }

  for (const trailer of trailers) {
    args.push('--trailer', `${trailer.token}=${trailer.value}`)
  }

  const result = await git(args, repository.path, 'mergeTrailers', {
    stdin: commitMessage,
  })

  return result.stdout
}
