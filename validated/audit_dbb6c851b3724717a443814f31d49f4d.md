### Title
Operator crediting for a payout is decided solely by an unauthenticated OP_RETURN, which the user's `SinglePlusAnyoneCanPay` signature never commits to - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_kickoff_malicious` and `PayoutCheckerTask::run_once` trust `payout_payer_operator_xonly_pk`, a value parsed purely from the confirmed payout transaction's OP_RETURN output by `update_finalized_payouts`. Because the withdrawal input is signed by the user with `TapSighashType::SinglePlusAnyoneCanPay`, that signature commits only to the withdrawal input and the output at the same index (output 0); it commits to neither the OP_RETURN output nor any additional funding inputs, so any party holding the signature can build and fund their own version of the payout transaction that credits an arbitrary, uninvolved registered operator.

### Finding Description
The binding assumed by the protocol is:
`payout_payer_operator_xonly_pk` (stored in `withdrawals.payout_payer_operator_xonly_pk`) == the operator whose BTC actually funded output[0] of the confirmed payout transaction.

Tracing the code shows this binding is never enforced:

1. `update_finalized_payouts` (`core/src/verifier.rs:2283-2354`) scans the confirmed payout tx for any output, parses the OP_RETURN naively via `parse_op_return_data`, and stores whatever xonly-pk is embedded there as the payer, with no check that this key relates to who actually paid: [1](#0-0) 
2. `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) later only compares this stored `operator_xonly_pk` to `kickoff_data.operator_xonly_pk`; if they're equal it is not malicious: [2](#0-1) 
3. `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) is driven purely by `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` — an operator's own automation will automatically claim any withdrawal credited to it in the DB, with no verification that it actually broadcast the funding: [3](#0-2) 

The root cause is in how the payout tx is constructed and signed. `create_payout_txhandler` builds outputs `[user_payout, anchor, OP_RETURN(operator_pk)]`, and only the withdrawal input is signed with the user's key-spend signature: [4](#0-3) . The operator's `withdraw` handler verifies this signature with `SECP.verify_schnorr` using `sighash_type = SinglePlusAnyoneCanPay`: [5](#0-4) . Under BIP-341, `SinglePlusAnyoneCanPay` only commits to the single signed input and the output at the same index (output 0); `calculate_pubkey_spend_sighash` uses `Prevouts::One` and passes the sighash type straight to `taproot_key_spend_signature_hash`, confirming no other outputs or inputs are covered: [6](#0-5) . Consequently, the OP_RETURN (naming the operator who is to be reimbursed) and any additional funding inputs are completely unsigned by the user and freely malleable by anyone who has the user's signature (e.g., by observing it once it is broadcast to operators via the aggregator's public, unauthenticated `withdraw` gRPC, or seeing it in the mempool).

Exploit flow:
- User signs a `SinglePlusAnyoneCanPay` withdrawal input for withdrawal idx N; this is sent to operators (or observed in the public mempool once operator A funds and broadcasts it).
- Attacker builds a new payout transaction reusing the identical input+signature and output[0], adds their own funding input(s) (paid with attacker's own BTC), and sets the OP_RETURN to an unrelated, registered operator B's xonly-pk.
- Attacker gets this transaction confirmed (it spends the same unique withdrawal UTXO, so only one version can ever confirm).
- `update_finalized_payouts` records B as `payout_payer_operator_xonly_pk` for idx N.
- Operator B's own `PayoutCheckerTask` automatically calls `handle_finalized_payout`/sends a kickoff for withdrawal N, and `is_kickoff_malicious` finds `operator_xonly_pk == kickoff_data.operator_xonly_pk`, so B is reimbursed from collateral for a payout it never actually funded.
- Operator A, having possibly funded a competing broadcast that lost the race, can never be credited for withdrawal N again (`withdrawals` row for idx N is now bound to B and eventually marked handled).

No existing guard closes this gap: `Verifier::is_deposit_valid`, `SPV::verify`, `verify_storage_proofs`, and the presigned transaction graph all operate on a different axis (deposit validity, withdrawal UTXO existence, and the amount/sighash of the user's own leg) and never bind the OP_RETURN operator identity to the transaction's actual funding source.

### Impact Explanation
This directly matches the Critical category "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed": operator B's collateral-backed reimbursement flow is triggered without B spending any BTC, while operator A's real, uninvolved funding effort is optionally lost/unclaimable since the withdrawal's OP_RETURN attribution and DB state are now fixed to B. The attack is repeatable across every withdrawal and against any registered operator, since the mechanism depends only on generic sighash semantics, not on any deposit- or operator-specific secret.

### Likelihood Explanation
The attacker only needs to observe/obtain one `SinglePlusAnyoneCanPay`-signed withdrawal input (broadcast publicly to potentially many operators via the aggregator's `withdraw` RPC, or visible once any operator funds/broadcasts the payout tx) and enough BTC to fund and out-race the transaction (fees + output[0] amount is unaffected since output[0] is fixed by the signature; the attacker's own funding input(s) and fee are attacker-controlled). No special privileges, collateral, or key shares are required — matching the stated unprivileged attacker model — making this practical to execute against a live operator race.

### Recommendation
Bind the OP_RETURN operator identity cryptographically to the actual payer. Options: require the operator to sign an additional taproot input/anchor (with their own key) that is committed by the withdrawal's own signature scope, or move to `SighashType::All` for the operator-controlled outputs so the OP_RETURN and funding inputs are covered by a signature verifiably tied to the crediting operator, or independently verify (e.g., by tracing back the funding inputs and checking they belong to the OP_RETURN-named operator's known wallet/collateral) before trusting `payout_payer_operator_xonly_pk` in `update_finalized_payouts`.

### Proof of Concept
`cargo test` plan (new test in a non-excluded location, e.g. a verifier/operator integration test):
1. Set up two registered operators A and B with distinct xonly-pks and collateral, and one deposit/withdrawal idx N with a user-signed `SinglePlusAnyoneCanPay` withdrawal input.
2. Construct payout_tx_A: `create_payout_txhandler(input_utxo, output_txout, A_xonly_pk, user_sig, ...)`, fund with A's wallet inputs, but do not broadcast/confirm it.
3. Construct payout_tx_B: same `input_utxo`, same `output_txout` (output[0] identical bytes), same `user_sig`, but `operator_xonly_pk = B_xonly_pk`, funded instead with a fresh, attacker-controlled wallet input.
4. Assert both transactions pass `SECP.verify_schnorr` for the same `user_sig`/sighash (proving output[1..] and additional inputs aren't covered).
5. Broadcast and confirm only payout_tx_B; run the verifier's block-sync path so `update_finalized_payouts` executes.
6. Assert `db.get_payout_info_from_move_txid(...)` returns `Some(B_xonly_pk)` for withdrawal N, and that B's BTC balance decreased by the payout amount+fees while A's balance is unaffected (A funded nothing, since A never actually confirmed anything) — demonstrating the credited xonly_pk (B) does not need to equal, and in this scenario never equals, the operator whose collateral-backed BTC is expected to fund it, when compared against a legitimate scenario where A is the intended payer.
7. Additionally run `Verifier::is_kickoff_malicious` with `kickoff_data.operator_xonly_pk = B_xonly_pk` and assert it returns `Ok(false)` (not malicious), proving B's kickoff/reimbursement would proceed despite B never having funded the payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
