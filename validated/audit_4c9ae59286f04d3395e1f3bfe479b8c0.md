### Title
Unauthenticated senders can force registration of unspendable dust outputs — `Scanner::scan_transaction` accepts any value with no dust threshold or recourse (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Compound report — where anyone can force execution of a queued transaction the protocol cannot cancel — `Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` accepts every output whose `script_pubkey` matches a registered P2TR script, regardless of `value`. Any unprivileged party can send a dust-valued output (below the ~546 sat P2TR dust relay limit) to Serai's deposit or offset addresses, causing the processor to report funds as received that can never be economically spent. There is no filter, minimum, or way to reject/discard the output once seen.

### Finding Description
`scan_transaction` looks up only `output.script_pubkey` in `self.scripts` and pushes a `ReceivedOutput` with whatever `TxOut` the attacker supplied (mod.rs:205-211). `ReceivedOutput::value()` simply returns `output.value.to_sat()` (mod.rs:116-118), and the processor's `get_outputs` (`processor/src/networks/bitcoin.rs:686-700`) turns every scanned output into a credited `Output`/`ExternalBalance` with no value check.

Meanwhile, `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` correctly refuses to *create* dust payments (`TransactionError::DustPayment`), but dust checks on inputs do not exist: a `ReceivedOutput` worth less than the fee needed to spend it (each Taproot key-path input adds ~57.5 vB; at nontrivial feerates a <few-hundred-sat output is net-negative) will either produce `NotEnoughFunds` errors when combined or silently reduce the spendable balance when bundled. The offset-registered addresses (Branch/Change/Forwarded, `processor/src/networks/bitcoin.rs:333-344`) are publicly derivable via `Secp256k1::hash_to_F(KEY_DST, ...)`, so an attacker can target them without any prior interaction.

### Impact Explanation
Funds reported received that are not spendable: the protocol credits/mints against BTC deposits that cost more to move than they are worth, or that `SignableTransaction` cannot include without dragging other inputs below the fee floor. In a bridge context this is a direct accounting hole — Serai-side minted coins backed by economically unspendable inputs. Repeated dust deposits to registered offset scripts accumulate permanently unclaimable `ReceivedOutput`s, and since scanning is purely passive there is no equivalent of a "cancel": once on-chain, the output is irrevocably registered as received.

### Likelihood Explanation
Fully reachable by any unprivileged party with public inputs — a standard Bitcoin transaction paying a dust amount to the well-known P2TR script. No validator collusion, leaked keys, or malformed encodings are required; the only requirement is that the feerate make the deposited value below its spend cost, which the attacker fully controls by choosing a tiny `value`.

### Recommendation
In `scan_transaction` (or in the processor's `get_outputs`), reject outputs whose `value.to_sat()` is below the P2TR dust threshold *plus* the marginal fee weight of an additional input (i.e., require `value > input_vbytes * current_fee_rate`). Document that outputs below this floor are deliberately ignored, and consider having `SignableTransaction::new` refuse inputs whose value is less than their marginal fee contribution to prevent unspendable inputs from ever entering a transaction.

### Proof of Concept
1. Compute Serai's group key address via `p2tr_script_buf(key)` (or a registered offset script, e.g. `key + G * hash_to_F(KEY_DST, "forward")`).
2. Broadcast a Bitcoin transaction creating a `TxOut { value: 100 sats, script_pubkey: <that script> }`.
3. `scanner.scan_transaction(&tx)` returns a `ReceivedOutput` with `value() == 100`.
4. `get_outputs` wraps it into a credited `Output`; a subsequent `SignableTransaction::new(vec![that_output], ...)` either fails with `NotEnoughFunds` (the 100-sat input cannot cover its own ~57 vB × fee share) or forces other inputs to subsidize it, proving the reported deposit is not independently spendable.
