I found a concrete lock-discipline bug analogous to the ALSA UAF: `PreAddTx` in the gasless module mutates the shared `knownTxs` map while holding only a read lock (`RLock`), whereas every other mutator of the same map (`IsReady`, `PreReset`, `PostReset`) takes the exclusive write lock (`Lock`). This mirrors the ALSA root cause precisely — one code path in the lifecycle of a shared, concurrently-accessed object is missing the exclusive lock that all other paths use, allowing concurrent writes/reads to race on the underlying data structure.

### Title
Gasless `PreAddTx` mutates `knownTxs` under only a read lock, racing with writer paths - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.PreAddTx` (invoked from `TxPool.add`/`addTx` on every submitted transaction) takes `g.knownTxsMu.RLock()` and then calls `g.knownTxs.add(tx, TxStatusQueue)`, which performs unsynchronized map writes on the shared `knownTxs` map (`map[common.Hash]*knownTx`) — a plain Go map with no internal locking. Every other function that touches the same map (`IsReady`, `PreReset`, `PostReset`) correctly takes the exclusive `Lock()`. Because `RLock()` permits multiple concurrent holders, two or more inbound transactions processed concurrently through `PreAddTx` can execute `knownTxs.add` at the same time, and a `PreAddTx` reader can also run concurrently with a writer holding `Lock()` in `IsReady`/`PreReset`/`PostReset` since Go's `sync.RWMutex` does not itself protect the map — the RLock only serializes against other `Lock()` holders, not against other `RLock()` holders performing the same unguarded write.

### Finding Description
`PreAddTx` is called for every transaction (local or remote) entering the pool via `TxPool.add` (`blockchain/tx_pool.go` module hooks), and multiple transactions can be added concurrently (e.g., via `AddRemotes`/`checkAndAddTxs`, or via the `AuctionAPI.SubmitBid` path that calls `SendTx` concurrently with normal RPC submissions, as demonstrated by `tests/race_test.go`'s `TestRaceBetweenTxpoolAddAndCommitNewWork`, which shows the codebase's own awareness that concurrent tx admission requires locking). Since `PreAddTx` only acquires `RLock()`, two concurrent transaction submissions that each become `PreAddTx` calls can concurrently execute `g.knownTxs.add(...)`, both mutating the same underlying Go map without exclusion. In Go, concurrent unsynchronized map writes are undefined behavior detected by the runtime as `fatal error: concurrent map writes`, immediately crashing the node process. This is the direct structural analog of the ALSA bug: a mutating operation on a shared, reference-counted/tracked object omits the lock that every sibling operation in the same lifecycle correctly takes, "quick workaround" being to simply promote `RLock()` to `Lock()` in `PreAddTx`, exactly as the kernel patch adds `register_mutex` to `snd_timer_user_params()`.

### Impact Explanation
An unprivileged transaction sender or gasless swap participant reaching this path from a normal RPC-submitted transaction can trigger a crash of the node (full node/CN) that has the gasless module enabled, simply by submitting concurrent gasless-eligible (approve/swap) transactions or interleaving them with block-processing resets (`PreReset`/`PostReset`) and promotions (`IsReady`), which run on the same shared map from different goroutines (tx pool `loop()`, RPC handler goroutines, miner goroutine). This is a state-divergence/availability defect reachable purely from public RPC transaction submission — no privileged or validator access required — and can crash node processes handling gasless transactions, which is a form of denial of service to honest nodes and can cause state divergence between nodes that crash versus nodes that don't hit the race window.

### Likelihood Explanation
Triggering requires only submitting two or more approve/swap-typed transactions (or bundle-eligible transactions) close together in time so their `PreAddTx` calls overlap, or racing tx submission with the pool's periodic `reset`/`promoteExecutables` cycle — both are externally triggerable by any RPC caller with no special permissions, and Go's race detector / runtime map-write panic guarantees that concurrent unsynchronized writes are readily observable under load (the project's own `tests/race_test.go` demonstrates this exact class of concurrency bug is realistically triggerable in this codebase's tx-pool machinery).

### Recommendation
Change `PreAddTx` in `kaiax/gasless/impl/tx_pool.go` to acquire `g.knownTxsMu.Lock()` (not `RLock()`) before calling `g.knownTxs.add`, matching the locking discipline used in `IsReady`, `PreReset`, and `PostReset`.

### Proof of Concept
1. Enable the gasless module with a whitelisted token/router.
2. From two separate RPC connections (or goroutines), concurrently submit two distinct gasless approve/swap transactions (`IsBundleTx(tx) == true`) directly to the node's public transaction-submission RPC so that both invoke `TxPool.add` → `GaslessModule.PreAddTx` at overlapping times.
3. Because `PreAddTx` only takes `RLock()`, both goroutines can enter `g.knownTxs.add(tx, TxStatusQueue)` concurrently and mutate the same `map[common.Hash]*knownTx` without mutual exclusion, which the Go runtime detects as a concurrent map write and crashes the process with `fatal error: concurrent map writes`, or (if it doesn't crash first) leaves `knownTxs` in a corrupted/inconsistent state read by `IsReady`/`PreReset` under the promoted `Lock()`, causing metric/promotion state divergence between nodes. func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

type knownTxs map[common.Hash]*knownTx

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
