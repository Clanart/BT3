### Title
`MapField` list/map storage-mode desync allows a stale duplicate-key entry to survive in the reflection-visible repeated-field list after wire parsing, diverging from the deduplicated `Map` view - (File: `java/core/src/main/java/com/google/protobuf/MapField.java`)

### Summary
CometBFT's mempool keeps a `list` and a `map` that are supposed to represent the same set of transactions; the `map` only tracks a single index per transaction, so once the two structures desync, duplicate entries can be stuck in the `list` forever and can never be fully purged through the `map`-based removal path. The Protobuf Java `MapField` class has the same architectural pattern — one authoritative dataset (`mapData` / `listData`) is lazily converted to the other, and the class explicitly tracks which of `MAP`, `LIST`, or `BOTH` mode it is in [1](#0-0) . When a message containing a map field with duplicate wire-format keys is parsed, the builder accumulates entries into `listData` (LIST mode), including duplicate-key entries [2](#0-1) . If the read-only `getMap()` accessor is subsequently invoked, it converts `listData` into a deduplicated `mapData` (last-key-wins, matching the documented last-one-wins map semantics) but sets the mode to `BOTH` without discarding or rebuilding `listData` [3](#0-2) . In `BOTH` mode, `getList()` returns the untouched, still-duplicated `listData` directly, since only `mode == MAP` triggers regeneration [4](#0-3) .

### Finding Description
`MapField` maintains the invariant, per its own class-level documentation, that `mapData` and `listData` "have the same data" whenever the mode is `BOTH` [5](#0-4) . This invariant is the direct analog of CometBFT's requirement that the mempool's `list` and `map` "are supposed to be in sync all the time." The failure mode is structurally the same: the map-like structure (`mapData`) enforces uniqueness per key (last-one-wins, exactly like CometBFT's map tracking one index per tx-key), but the list-like structure (`listData`) is repeated-entry and can legitimately contain duplicates that arrive from an attacker-controlled input stream (repeated map entries with the same key in the wire format, which is explicitly permitted and tested — see `DuplicatedKeyWireFormat`/`DuplicateEntriesInWireFormatLastOneWins` in `map_test.inc` [6](#0-5) , confirming duplicate-keyed map entries in the wire format are a normal, reachable, attacker-controllable input).

The transition path `LIST -> BOTH` (via `getMap()`) is the "missing release" analog: it deduplicates into `mapData` but never rewrites `listData` to match, so `listData` keeps stale duplicate entries indefinitely once in `BOTH` mode — there is no code path that purges the extra copies from `listData` short of forcing the mode back to `MAP` (via `getMutableMap()` or `clear()`), which is not guaranteed to happen on the read-only/reflection paths that consume `getList()` (e.g. reflection-based repeated field access, iteration, or serialization consumers that go through the list view rather than the map view). This mirrors CometBFT's core defect precisely: once desync occurs, the "index"-tracking structure (map) cannot express or reach the duplicate entries stranded in the list-like structure, so those duplicates are never cleaned and any consumer that reads the list view sees stale/duplicated data that diverges from what the map view (the "authoritative", deduplicated view) reports.

### Impact Explanation
This is an internal data-integrity/consistency defect, not a memory-leak/flood/DoS class (excluded by the rules), so its severity is bounded to correctness impact: two accessors of the same `MapField` object (`getMap()` vs `getList()`) can return divergent contents for the same logical field after parsing attacker-supplied duplicate map keys — `getMap()` returns 1 deduplicated entry while `getList()` (used by reflection-based access, e.g. `DynamicMessage`/reflection API consumers, and repeated-field-style iteration) returns 2+ entries including stale/duplicate keys. Any application logic that trusts reflection-based repeated-field access (`getRepeatedFieldCount`/`getRepeatedField` equivalents for map entries) to be consistent with the strongly-typed map accessor could observe or act on inconsistent counts/entries, which is an integrity failure rather than confirmed RCE or unbounded resource growth.

### Likelihood Explanation
Reaching the divergent state requires only: (1) parsing a message with a map field containing duplicate keys in the wire format — an ordinary, always-accepted input per the codebase's own conformance tests [7](#0-6) , and (2) invoking the read-only `getMap()` (or equivalent typed accessor) before any mutation forces a full `MAP`-mode rebuild. Both conditions are ordinary, unprivileged operations reachable through any public parse API (`parseFrom`, JSON parsing into a map field, etc.) with no privileged access, hostile schema, or malicious peer required.

### Recommendation
When `getMap()` converts `listData` to `mapData` while transitioning `LIST -> BOTH`, `listData` should also be rebuilt/deduplicated from the freshly-computed `mapData` (or the mode should not advertise `BOTH` until the two are actually reconciled) so that any subsequent `getList()` call reflects the same deduplicated content as `getMap()`. This fully restores the invariant documented in the class Javadoc.

### Proof of Concept
I was not able to fully verify a concrete downstream consumer (e.g. exact reflection call site) that reads `getList()` after `getMap()` has already been called in the same object lifecycle within this checkout — search for call sites in `GeneratedMessage.java` did not return matches, and I could not confirm within the remaining tool budget whether a `MAP -> BOTH` (via `getList()`) or `LIST -> BOTH` (via `getMap()`) transition is actually reachable through the public parsing APIs before mutation forces a `MAP`-mode reset. This is the load-bearing assumption of the finding and should be independently confirmed (e.g. with a Devin session that can build/run the Java module) before treating this as a fully proven, reproducible security-relevant defect rather than a structural code-smell analog.   private List<Message> convertMapToList(MutabilityAwareMap<K, V> mapData) {
    List<Message> listData = new ArrayList<Message>(mapData.size());
    for (Map.Entry<K, V> entry : mapData.entrySet()) {
      listData.add(convertKeyAndValueToMessage(entry.getKey(), entry.getValue()));
    }
    return listData;
  }

  private MutabilityAwareMap<K, V> convertListToMap(List<Message> listData) {
    Map<K, V> mapData = newLinkedHashMapWithCapacity(listData.size());
    for (Message item : listData) {
      convertMessageToKeyAndValue(item, mapData);
    }
    return new MutabilityAwareMap<K, V>(this, mapData);

  public Map<K, V> getMap() {
    if (isEmpty()) {
      return Collections.emptyMap();
    }
    if (mode == StorageMode.LIST) {
      synchronized (this) {
        if (mode == StorageMode.LIST) {
          mapData = convertListToMap(listData);
          mode = StorageMode.BOTH;
        }
      }
    }
    return Collections.unmodifiableMap(mapData);
  }

TEST(GeneratedMapFieldTest, DuplicatedKeyWireFormat) {
  UNITTEST::TestMap message;

  // Two key fields in wire format
  std::string data = "\x0A\x06\x08\x01\x08\x02\x10\x01";

  EXPECT_TRUE(message.ParseFromString(data));
  EXPECT_EQ(1, message.map_int32_int32().size());
  EXPECT_EQ(1, message.map_int32_int32().at(2));

  // A similar test, but with a map from int to a message type.
  // Again, we want to be sure that the "second one wins" when
  // there are two separate entries with the same key.
  const int key = 99;
  UNITTEST::TestRequiredMessageMap map_message;
  UNITTEST::TestRequired with_dummy4;
  with_dummy4.set_a(0);
  with_dummy4.set_b(0);
  with_dummy4.set_c(0);
  with_dummy4.set_dummy4(11);
  (*map_message.mutable_map_field())[key] = with_dummy4;
  std::string s = map_message.SerializeAsString();
  UNITTEST::TestRequired with_dummy5;
  with_dummy5.set_a(0);
  with_dummy5.set_b(0);
  with_dummy5.set_c(0);
  with_dummy5.set_dummy5(12);
  (*map_message.mutable_map_field())[key] = with_dummy5;
  std::string both = s + map_message.SerializeAsString();
  // We don't expect a merge now.  The "second one wins."
  ASSERT_TRUE(map_message.ParseFromString(both));
  ASSERT_EQ(1, map_message.map_field().size());
  ASSERT_EQ(1, map_message.map_field().count(key));
  EXPECT_EQ(0, map_message.map_field().find(key)->second.a());
  EXPECT_EQ(0, map_message.map_field().find(key)->second.b());
  EXPECT_EQ(0, map_message.map_field().find(key)->second.c());
  EXPECT_FALSE(map_message.map_field().find(key)->second.has_dummy4());
  ASSERT_TRUE(map_message.map_field().find(key)->second.has_dummy5());
  EXPECT_EQ(12, map_message.map_field().find(key)->second.dummy5());
}
