### Title
Unrecoverable panic in PedPoP blame verification — untrusted `decryptor` index causes `HashMap` indexing panic instead of a graceful `DecryptionError` - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2025-27465 describes a path that should handle an exception gracefully but instead treats it as fatal because the recovery metadata was wrong. The direct analog in Serai is `Decryption::decrypt_with_proof` in the PedPoP DKG encryption module: when verifying a blame (decryption key) proof, it indexes `self.enc_keys[&decryptor]` with `HashMap`'s `Index` impl, which **panics** if `decryptor` was never registered, rather than returning the `DecryptionError::InvalidProof` error the function's own signature promises. A "should be handled gracefully" condition (unknown/unregistered participant in a blame proof) is instead fatal.

### Finding Description
`Decryption::decrypt_with_proof` verifies an `EncryptionKeyProof` DLEq against `[C::generator(), msg.key]` and `[self.enc_keys[&decryptor], *proof.key]` (encryption.rs:381-392). `enc_keys` is populated only in `Decryption::register` (encryption.rs:356-361), which itself uses an `assert!` that panics on re-registration. There is no `get`/missing-key check before the indexing:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-390
if let Some(proof) = proof {
  proof.dleq.verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],   // panics if decryptor not registered
  ).map_err(|_| DecryptionError::InvalidProof)?;
```

`EncryptedMessage::read` / `EncryptionKeyProof::read` / `EncryptionKeyMessage::read` (encryption.rs:171-177, 267-269, 57-59) deserialize all of the attacker-supplied bytes (`key`, `pop`, `msg`, `dleq`), and `from`/`decryptor` are `Participant` values supplied alongside the blame. The blame path exists specifically to adjudicate accusations by potentially-malicious parties — i.e., the caller is by design handling untrusted accusations — yet a `decryptor` participant index that maps to no registered encryption key aborts the thread instead of producing `InvalidProof`.

The same unguarded indexing exists in `Encryption::encrypt` (`self.decryption.enc_keys[&participant]`, encryption.rs:466), but `generate_secret_shares` iterates `all_participant_indexes()` after `verify_r1` registered every included participant, so it is internally consistent. `decrypt_with_proof` has no such invariant: it is invoked in the blame phase with indices derived from the accusation, which a malicious accuser controls.

### Impact Explanation
A malicious DKG participant (or an accuser relaying a crafted accusation in the blame round) can crash the PedPoP evaluation/blame logic at a verifying party by supplying a blame/encrypted-message tuple referencing a `decryptor` participant with no registered `enc_key`. The panic propagates out of the library boundary (Serai documents an expectation not to panic — see `frost/src/curve/mod.rs:88`). If used under `panic = "abort"` or inside the coordinator's task, this terminates the key generation process, denying availability to honest participants. This mirrors the CVE impact (CVSS A:L): an exception that should yield a clean `InvalidProof` verdict instead becomes a fatal crash.

### Likelihood Explanation
Reachability requires an attacker able to send PedPoP/blame messages — precisely the "untrusted bytes fed to `EncryptedMessage::read` / blame proof" surface the threat model includes. The attacker does not need a valid share or proof; they only need the verification path to look up an unregistered `decryptor` before the DLEq check returns. The indexing is evaluated as an argument to `dleq.verify`, so it executes unconditionally whenever `proof.is_some()`, regardless of whether the PoP or DLEq would pass. Cost to trigger: one malformed accusation. Uncertainty: whether the upstream caller (coordinator) sanitizes `decryptor` against the included-participant set before calling; the library itself performs no validation, and `Decryption`/`decrypt_with_proof` is the crate's own blame-verification API (`into_decryption` at encryption.rs:503).

### Recommendation
Replace `self.enc_keys[&decryptor]` with a checked lookup:

```rust
let Some(enc_key) = self.enc_keys.get(&decryptor) else {
  Err(DecryptionError::InvalidProof)?
};
&[*enc_key, *proof.key]
```

Apply the same treatment to `Encryption::encrypt`'s `enc_keys[&participant]`, and downgrade the `assert!` in `Decryption::register` to a returned error so duplicate registrations are handled gracefully rather than aborting.

### Proof of Concept
```rust
// After a normal DKG, a party holds a Decryption<C> whose enc_keys
// contains only participants who registered EncryptionKeyMessages.
// A malicious accuser submits a blame referencing a decryptor that
// never registered (e.g. an index not in the included set, or a
// participant whose registration was rejected):

let msg: EncryptedMessage<C, SecretShare<C::F>> =
  EncryptedMessage::read(&mut attacker_bytes, params)?;   // attacker-controlled
let proof: EncryptionKeyProof<C> =
  EncryptionKeyProof::read(&mut attacker_proof_bytes)?;   // attacker-controlled

// `attacker_decryptor` is a valid Participant with NO entry in enc_keys.
decryption.decrypt_with_proof(from, attacker_decryptor, msg, Some(proof));
// => thread panics at encryption.rs:388 (`enc_keys[&decryptor]`),
//    instead of returning Err(DecryptionError::InvalidProof)
```

The panic occurs before the DLEq proof is even evaluated — the mere construction of the `verify` arguments dereferences a missing map entry — so no valid cryptography from the attacker is required.

**Caveat:** `Decryption` and `decrypt_with_proof` are `pub(crate)`; exploitability depends on callers (e.g., the coordinator's blame handling, outside the crypto scope) passing accusation-derived `decryptor` values without pre-validation. If callers already restrict `decryptor` to registered participants, the reachable impact is limited to the same panic class via `register`'s `assert!`, which is weaker. The library-level defect — fatal panic where the `Result` signature promises graceful failure — is nonetheless concrete in the in-scope code.
