### Title
MessageSet duplicate `type_id`/payload entries are resolved with different "which value wins" semantics across Protobuf language runtimes - ([File: src/google/protobuf/wire_format_lite.h])

### Summary
The KernelSU report's root cause is a **consumer/verifier disagreement about which entry to honor when a binary blob contains multiple entries tagged with the same ID** (first-match vs. last-match), letting an attacker choose bytes that two different logic paths interpret differently. The nearest real, provable analog in this Protobuf checkout is the handling of duplicate `type_id`/`message` pairs inside a `MessageSet` group (`kMessageSetItemStartTag` ... `kMessageSetItemEndTag`). Different Protobuf runtimes implement different "first wins / no merge" vs. "re-resolve and re-parse every occurrence" policies for the same wire bytes.

### Finding Description
`MessageSet` wire format is:
```
message MessageSet {
  repeated group Item = 1 {
    required uint32 typeId = 2;
    required bytes message = 3;
  }
}
```
`typeId` is attacker-controlled and is used to look up which extension descriptor/schema should be used to interpret the following `message` bytes — structurally identical to the KernelSU report's `0x7109871a`-tagged "ID -> payload" scan inside an attacker-supplied signing block.

- **C++ (`wire_format_lite.h:1619-1699`, `ParseMessageSetItemImpl`)**, and the equivalent full-runtime template in **`extension_set_inl.h:193-272` (`ParseMessageSetItemTmpl`)** and reflection path **`wire_format.cc:614-709` (`WireFormat::MessageSetParser::ParseElement`)** all gate on an explicit state machine (`kNoTag` / `kHasType` / `kHasPayload` / `kDone`). Once `state == kHasType`, a second `typeId` tag is silently dropped (no `else` branch matches it), and once `state == kDone`, a second `message` payload is parsed only far enough to skip it. This is documented by the conformance suite comments themselves: [1](#0-0) 
which state: "`[type_id, value, value] -> first value honored, no merge`" and "`[type_id, value, type_id (different)] -> first type_id and value honored`".

- **Python (`decoder.py:900-928`, `MessageSetItemDecoder.DecodeItem`)** independently enforces the same "first occurrence wins" rule by explicit sentinel checks (`if type_id == -1: ...`, `if message_start == -1: ...`): [2](#0-1) 

- **upb (`upb/wire/decode.c:665-720`, `upb_Decoder_DecodeMessageSetItem`)** explicitly comments `// Ignore dup.` on both the type-id and message tags via a `state_mask` bitmask: [3](#0-2) 

- **Java (`MessageSetSchema.java:136-219`, the `mergeMessageSetFrom` loop)** has **no such "already seen" gate**. Every time `MESSAGE_SET_TYPE_ID` is read, `typeId`/`extension` are unconditionally reassigned, and every time `MESSAGE_SET_MESSAGE` is read *while `extension != null`*, it is unconditionally re-parsed and merged into the extension map via `extensions.setField(extension.descriptor, registers.object1)`: [4](#0-3) 

This means that for a sequence like `[typeId=A, message=M1, message=M2]` (both messages sent while `typeId` is still resolved to extension `A`), the C++/Python/upb runtimes will only interpret `M1` (first payload honored, `M2` skipped/ignored — "no merge"), while the Java runtime will call `extensionSchema.parseLengthPrefixedMessageSetItem`/`decodeMessageField` a second time for `M2`, whose result is written into the extension map for `A` again — and because submessage `setField` in the java array-decoder path performs field-merge semantics for message-typed fields (`decodeMessageField` merges into the existing builder rather than clearing it first), the final decoded value for extension `A` can differ between Java and the other runtimes: Java may end up with `M1` merged with `M2`, whereas C++/Python/upb only ever see `M1`.

### Impact Explanation
This reproduces the exact invariant violated in the KernelSU report — **two trusted consumers of the identical byte stream disagree on which duplicate-ID entry (or resulting merged value) is authoritative** — mapped onto Protobuf's own wire format rather than APK signing blocks. In a consuming application that uses `MessageSet`-style polymorphic extensions for anything security-relevant (e.g., an authorization/claims extension keyed by `type_id`), a cross-language deployment (e.g., a Java-based gateway/validator plus a C++/Python/Go(upb) backend, or vice versa) could be made to decode the same bytes into different application-level extension values. That is a decoding differential/type-confusion class bug, not a crash, and its blast radius is limited strictly to applications that (a) use the legacy, largely-deprecated `message_set_wire_format` proto2 feature, and (b) mix Java with a non-Java Protobuf runtime on the same untrusted bytes. Given the narrowness of `MessageSet` usage in modern schemas, this is a real but low-likelihood-of-exploitation issue — consistent with "Medium," similar to the original report's severity, rather than Critical/High.

### Likelihood Explanation
Likelihood is limited by:
- `MessageSet` (the `message_set_wire_format` option) is a legacy proto2-only feature; most application/consuming schemas today do not use it.
- The differential only manifests when duplicate `type_id`/`message` pairs targeting the *same* extension are deliberately crafted by an attacker who also knows which runtime(s) are consuming the bytes.
- It requires a mixed-runtime deployment (Java vs. C++/Python/upb) verifying/consuming the same bytes for it to produce divergent application behavior; a single-runtime deployment is internally consistent.

This satisfies the report's exposure assumption (an ordinary client sending bounded, well-formed-looking Protobuf binary through a public parse API) but the practical reach is narrower than the original KernelSU scenario (Android package installation, which is universal).

### Recommendation
- Harden `MessageSetSchema.mergeMessageSetFrom` (Java) to match the "first typeId / first payload wins, no merge" state machine used by C++ (`extension_set_inl.h`, `wire_format_lite.h`), Python (`decoder.py`), and upb (`decode.c`): once a `type_id`/`message` pair has been resolved and consumed for a given `MessageSet` item slot, subsequent duplicate tags for the same slot must be skipped rather than re-parsed/re-merged.
- Add/extend `conformance/binary_json_conformance_suite.cc` `RunMessageSetTests` cases specifically exercising duplicate `(type_id, message)` pairs that resolve to the *same* extension type across all languages (the current cases at [5](#0-4)  only assert the C++ behavior conceptually; there is no evidence the Java conformance runner enforces "no merge").
- Document the required "first occurrence wins, no merge" semantics explicitly as a MUST in the wire-format spec for `MessageSet`, and cross-check all language implementations against it in CI.

### Proof of Concept
Construct a `MessageSet`-wire-format group with a duplicated payload for the same `type_id`, targeting a message-typed extension with a field that reveals whether merge occurred (e.g., a `repeated` sub-field, so that "merge" produces 2 elements and "first wins" produces 1):

```
group(1,                                   // MessageSet Item group
  field(2, VARINT, varint(<typeId_A>)) +   // typeId = A (first occurrence)
  len(3, <serialized ExtA{ repeated_field: [1] }>) +   // message #1
  len(3, <serialized ExtA{ repeated_field: [2] }>)     // message #2 (duplicate payload, same extension)
)
```
- Parsing this with the C++ full runtime (`ExtensionSet::ParseMessageSetItemTmpl`, `extension_set_inl.h:193-272`) or Python (`MessageSetItemDecoder`, `decoder.py:862-961`) or upb (`upb_Decoder_DecodeMessageSetItem`, `decode.c:665-720`) is expected to yield `ExtA.repeated_field == [1]` only (second payload ignored — "no merge", per the documented conformance behavior at `conformance/binary_json_conformance_suite.cc:533-550`).
- Parsing the identical bytes with the Java runtime (`MessageSetSchema.mergeMessageSetFrom`, `MessageSetSchema.java:136-219`) is expected to invoke `decodeMessageField`/`extensions.setField` twice for the same `extension.descriptor`, and — because message-typed field decoding merges into the pre-existing builder rather than resetting it — is expected to yield `ExtA.repeated_field == [1, 2]`.

Note: I was not able to fully trace the exact merge-vs-overwrite semantics of `ArrayDecoders.decodeMessageField`/`extensions.setField` for message-typed extension fields inside this session (ran out of tool iterations before reading `ExtensionSchema.java`'s full source), so the Java-side "merge" outcome above is inferred from `MessageSetSchema.java:136-219`'s lack of an "already parsed" guard plus general Protobuf message-merge semantics, not from a directly-executed test. A background engineer should write and run the above conformance-style test (comparing Java vs. C++/Python/upb decode results byte-for-byte) to confirm the differential before filing/fixing.
