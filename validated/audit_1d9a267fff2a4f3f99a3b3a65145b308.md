### Title
Fee-to-mWOM conversion in `WombatStaking._sendRewards`/`SmartWomConvert.smartConvert` performs an unprotected swap that can be sandwiched, stealing protocol reward yield - (File: `wombat/WombatStaking.sol`, `wombat/SmartWomConvert.sol`)

### Summary
`WombatStaking.harvest()` is a permissionless, unprivileged-wallet-callable function that triggers `_sendRewards`, which — when a WOM fee is configured to be converted to mWOM — calls `SmartWomConvert.smartConvert()`. That function reads the live spot price of the WOM/mWOM Wombat pool and, based on it, executes a real swap through `IWombatRouter.swapExactTokensForTokens` with a hardcoded `0` minimum-output, i.e. no slippage protection on the individual swap leg. This mirrors the SpotHedgeBaseMaker bug class: a protocol contract trades against a live AMM pool as part of normal, permissionless operation without adequate execution-price protection, letting an attacker manipulate the pool immediately before/after the protocol's trade to extract value.

### Finding Description
`WombatStaking.harvest()` has no access control beyond requiring the pool to be active: [1](#0-0) 

It calls `_toMasterWomAndSendReward` → `_sendRewards`, which, for WOM fees configured with `isMWOM = true`, converts the WOM fee into mWOM via the configured `smartWomConverter`: [2](#0-1) 

`SmartWomConvert.smartConvert` computes a live `currentRatio()` by querying `IWombatRouter.getAmountOut` on the WOM/mWOM pool, and decides how much of the input to swap ("buyback") through the pool versus mint 1:1: [3](#0-2) 

The actual swap executed inside `_convertFor` passes `0` as the minimum amount out to the router, relying only on a coarse aggregate check afterward: [4](#0-3) 

Because `currentRatio()` and `maxSwapAmount()` are read from the live, on-chain Wombat WOM/mWOM pool state at execution time, and the actual swap leg has zero slippage protection, an attacker can:
1. Trade against the WOM/mWOM Wombat pool to move `currentRatio()`/pool reserves into a favorable state (classic front-run of a pending or self-triggered `harvest()` call).
2. Call (or bundle) `WombatStaking.harvest()` — callable by any wallet — causing the protocol's WOM reward fee to be swapped through the now-skewed pool with no floor on the amount of mWOM received.
3. Reverse their initial trade, capturing the value that should have accrued as mWOM sent to the reward pool (`IBaseRewardPool(feeInfo.to).queueNewRewards`).

This is the same root cause pattern as the SpotHedgeBaseMaker sandwich issue: a contract executes a swap against a manipulable AMM price as part of normal unprivileged operation, without adequate per-trade slippage bounds, enabling a sandwich that shifts value from the protocol/stakers to the attacker. Unlike the report's Uniswap price-band mitigation, there is no price-band or oracle sanity check at all here — the only protection is the aggregate `_minRec` check equal to the raw input amount, which does not prevent the attacker from capturing the spread from a manipulated buyback swap while still passing that low bar.

### Impact Explanation
The mWOM obtained from this conversion is queued as reward yield for mWOM/vlMGP/pool stakers via `IBaseRewardPool.queueNewRewards`. A sandwich attack against the internal, slippage-unprotected swap reduces the amount of mWOM reward yield the protocol receives for a given WOM fee input, permanently diverting that yield to the attacker. This falls under theft of unclaimed protocol/staker yield.

### Likelihood Explanation
`harvest()` is unprivileged and callable by anyone at any time (subject only to the pool being active), and the WOM/mWOM Wombat pool is a public AMM that any wallet can trade against in the same transaction/bundle. No admin, oracle, or governance action is required — only capital to move the pool's price and Wombat pool liquidity being thin enough for the manipulation to be profitable relative to gas/slippage costs, analogous to the liquidity/fee-tier constraints discussed in the source report.

### Recommendation
- Require a caller-supplied, properly-bounded minimum output for the internal buyback swap in `SmartWomConvert._convertFor` instead of hardcoding `0`.
- Compare the router's realized swap price against the pool's own quoted/theoretical price (or an external reference) with a bounded deviation before accepting the swap result.
- Consider restricting `harvest()`/fee-conversion triggering to a trusted keeper, or add a minimum-time/TWAP-based price check for `currentRatio()` to reduce single-block manipulability.

### Proof of Concept
Conceptual PoC (mirrors the referenced SpotHedgeBaseMaker sandwich):
1. Attacker observes `WombatStaking` has accumulated WOM fees destined for mWOM conversion (or triggers accrual via any deposit/withdraw/harvest activity).
2. Attacker trades a large amount against the WOM/mWOM Wombat pool to skew `currentRatio()` favorably for the pending buyback swap.
3. Attacker (or anyone) calls `WombatStaking.harvest(_lpToken)`, which routes through `_sendRewards` → `SmartWomConvert.smartConvert` → `_convertFor`, executing `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` at the manipulated price. [5](#0-4) 
4. Attacker reverses their initial pool trade in the same transaction/bundle, capturing the value difference at the expense of the mWOM amount that would have been queued to `IBaseRewardPool` for stakers.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
