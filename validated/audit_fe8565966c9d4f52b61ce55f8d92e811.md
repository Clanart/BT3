### Title
`SignableTransaction::new` omits the OP_RETURN output from the fee/weight calculation, producing transactions that underpay the fee and cannot be relayed — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
The bug class from the external report is a value computation whose rounding/units cause the amount of funds actually moved to diverge from what was intended — in the worst case making funds unretrievable. In `bitcoin-serai`, `SignableTransaction::new` appends a `data` OP_RETURN output to `tx_outs` (the real transaction) but never includes it in the template passed to `calculate_weight_vbytes`, so `vbytes` and `vbytes_with_change` are both computed on a transaction missing an up-to-80-byte output. The fee `fee_per_vbyte * vbytes` is therefore calculated for a smaller transaction than the one actually signed and broadcast.

### Finding Description
`calculate_weight_vbytes` builds a template `Transaction` whose outputs are derived only from `payments` plus an optional change output: [1](#0-0) 

But the caller pushes the OP_RETURN output into `tx_outs` before measuring, without feeding it into the measurement: [2](#0-1) [3](#0-2) 

Both calls at lines 204 and 225–226 pass `payments` only; the `data` output (up to ~90 bytes including the script and value fields, allowed up to 80 bytes of payload per the check at line 171) is absent from the template. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is computed for a tx ~90+ vbytes smaller than the signed tx.
- The minimum-relay-fee check at line 211 is evaluated against this deflated `vbytes`, so it does not catch the underpayment.
- When change exists, the change amount is computed as `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is likewise too small — so the change output is over-credited and the *actual* fee paid (`sum(inputs) - sum(outputs)`, per `fee()` at lines 137–141) is exactly `fee_per_vbyte * vbytes_underestimated`, an effective fee rate strictly below `fee_per_vbyte`, and potentially below the 1 sat/vbyte minimum relay rate.

### Impact Explanation
A threshold signing session (`TransactionMachine`/`TransactionSignMachine::sign`, lines 355–398) will produce a fully signed transaction whose real fee rate is lower than intended and can fall below `DEFAULT_MIN_RELAY_TX_FEE`. Such a transaction is rejected by Bitcoin nodes on broadcast — the threshold's UTXOs remain unspent, and the planned payments are never made, i.e., the inability-to-retrieve-funds outcome of the reported class. Even when still relayable, every transaction with `data` pays a lower effective fee rate than the caller specified and requested via `needed_fee()`, which callers use to account for operating costs. Note `processor/src/networks/bitcoin.rs::make_signable_transaction` currently passes `data: None`, so the vulnerable path is reachable by any other consumer of the `bitcoin-serai` wallet API that uses the public `data` parameter.

### Likelihood Explanation
Deterministic whenever `SignableTransaction::new` is called with `Some(data)` and a low `fee_per_vbyte` (e.g., 1 sat/vbyte): the ~90-byte omission directly drops the paid fee below the relay minimum for the actual signed transaction. At higher fee rates the tx still relays but systematically underpays relative to the requested rate.

### Recommendation
Include the OP_RETURN output in the template transaction inside `calculate_weight_vbytes` (pass `data`/`tx_outs` rather than `payments`), and recompute the minimum-fee check against the final, complete output set — including re-verifying the fee after the change output decision, since adding change with the true size also shifts `needed_fee`.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), 1)` with sufficient `inputs`.
2. The template tx at line 204 measures only `payments` (+ optional change), omitting the ~90-byte OP_RETURN output.
3. `needed_fee = 1 * vbytes_template`; the signed `Transaction` (lines 245–251) additionally contains the OP_RETURN output, so `fee() / actual_vsize < 1` sat/vbyte.
4. Broadcasting the signed tx fails minimum-fee relay policy, leaving the threshold's funds unspendable via this transaction despite a valid signature.
