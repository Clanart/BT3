### Title
Deserialization of `ReceivedOutput`/`ThresholdKeys` trusts attacker-controlled internal fields, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The mass-assignment pattern in the AdonisJS report — untrusted input populating fields that the code treats as internally consistent — maps onto Serai's byte-deserialization readers. `ReceivedOutput::read` accepts a serialized `offset`, `output` (TxOut), and `outpoint` and constructs internal wallet state without ever checking that `offset` actually derives `output.script_pubkey` from the scanner's key. The result is that crafted bytes are "assigned" into wallet state exactly like the `$isPersisted`/`$attributes` hijack: the fields pass through wholesale and later logic assumes they are consistent.

### Finding Description
`Scanner::scan_transaction` is the only legitimate constructor for `ReceivedOutput` and guarantees the invariant `p2tr_script_buf(key + offset*G) == output.script_pubkey` by construction (`networks/bitcoin/src/wallet/mod.rs:199-214`). `ReceivedOutput::read` (`mod.rs:122-134`) reconstructs the same struct from raw bytes with zero validation of that invariant:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)?;
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
Ok(ReceivedOutput { offset, output, outpoint })
```

Any consumer that ingests serialized `ReceivedOutput`s (e.g., `processor/src/networks/bitcoin.rs:145-166` `Output::read`, which wraps `ReceivedOutput::read` plus attacker-influenced `kind`/`presumed_origin`/`data`) treats the record as a spendable input. `SignableTransaction::new`/`TransactionMachine` then sign each input with a key derived as `group_key + offset`, assuming the invariant holds. A forged record whose `script_pubkey` pays an attacker key while claiming some `offset` produces inputs the multisig can never actually sign for — the threshold signature is computed for key `K + offset·G` while the UTXO requires `x·G` chosen by the attacker.

The same unchecked-field pattern exists in `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`): `t`, `n`, `i`, `interpolation`, `secret_share`, and `verification_shares` are all read from the byte stream, and `ThresholdKeys::new` validates only structural constraints (counts, index bounds, `t == n` for `Constant`). It never checks `generator * secret_share == verification_shares[i]`. The codebase itself acknowledges the consequence at `crypto/frost/src/sign.rs:491-494`: "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys" — i.e., signing can complete with all shares "valid" under the attacker-chosen verification shares while the produced aggregate signature is invalid, or vice versa.

### Impact Explanation
An attacker who can supply bytes to `ReceivedOutput::read`/`Output::read` (the prompt's in-scope untrusted-bytes surface) can fabricate a deposit: an `Output` claiming kind `External`, an arbitrary `offset`, and a `script_pubkey` paying the attacker is recorded as funds received by the multisig. The bridge credits the deposit, but the UTXO is not spendable by the validator set — "funds reported received that are not spendable," a direct loss for the depositor/protocol accounting. For `ThresholdKeys::read`, forged keys cause the FROST aggregator to emit invalid signatures or to mis-attribute blame during share verification, corrupting the signing session.

### Likelihood Explanation
Likelihood depends on where serialized outputs/keys cross a trust boundary. In `processor`, `Output::read` is used to deserialize persisted/relayed output records; if any of those bytes are attacker-influenced (e.g., coordinator-supplied data, imported state, or a compromised-but-untrusted store — explicitly *not* excluded since the rules only exclude malicious-RPC and DB-arbitrary-read assumptions for secrets, not integrity of non-secret records), the exploit is deterministic. Severity is Medium-High: it does not leak key material, but it breaks the credit/spendability invariant the bridge relies on.

### Recommendation
In `ReceivedOutput::read`, re-derive the expected script: reject unless the caller's expected key satisfies `p2tr_script_buf(expected_key + offset*G) == output.script_pubkey` (pass the base `ProjectivePoint` into `read`, as `Commitments::read` already takes `params`). Alternatively, store only the `outpoint` and re-scan the chain. For `ThresholdKeys::read`, add `assert`-level validation `C::generator() * secret_share == verification_shares[&params.i()]` inside `ThresholdKeys::new`, closing the documented "semantically invalid FrostKeys" hole.

### Proof of Concept
```rust
// networks/bitcoin: forge a ReceivedOutput credited to the multisig
// that actually pays an attacker key
let attacker_scalar = Scalar::random(&mut OsRng);
let attacker_script = p2tr_script_buf(ProjectivePoint::GENERATOR * attacker_scalar).unwrap();

let mut buf = vec![];
// arbitrary offset the victim "should" use
buf.extend(Scalar::ZERO.to_bytes());
// TxOut paying the attacker
TxOut { value: Amount::from_sat(100_000), script_pubkey: attacker_script }
  .consensus_encode(&mut buf).unwrap();
// a real-looking outpoint
OutPoint::new(real_txid, 0).consensus_encode(&mut buf).unwrap();

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// `forged` is accepted; SignableTransaction will sign for group_key + ZERO·G,
// which cannot spend attacker_script -> funds credited but unspendable.
```
