Audit Report

## Title
Global (non-per-IP) DoS of QUIC connection-tracker capacity via slow-handshake burst — (File: `streamer/src/nonblocking/quic.rs`)

## Summary
An unprivileged, unstaked attacker can send bursts of QUIC connection Initial packets and deliberately stall the handshake to occupy `ClientConnectionTracker` slots for the full 2-second `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, then repeat immediately. Because both the overall and per-IP rate limiters are only ever consulted (peeked) before slot admission and only debited on successful handshake completion, incomplete/stalled attempts never get throttled by either limiter, allowing the attacker to occupy a large share of the shared, global `max_concurrent_connections` handshake headroom.

## Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs`), before a `ClientConnectionTracker` slot is granted, two checks occur: the global bucket check `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0)  and the per-IP check `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) . Both are non-mutating "peek" operations. Token consumption only happens later, inside `setup_connection`, and only on the success branch after the handshake completes, via `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` [3](#0-2) . `ConnectionRateLimiter::is_allowed` explicitly returns `true` for any IP with no existing record [4](#0-3) , and a record is only created via `register_connection`, reached only on success [5](#0-4) .

The only actual gate on concurrent in-flight handshakes is `ClientConnectionTracker::new`, which compares a single global `stats.open_connections` counter against `max_concurrent_connections`, with no per-IP partitioning [6](#0-5) . Once granted, the slot is held for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds) via `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` before `outstanding_incoming_connection_attempts` is decremented and (via `Drop`) the tracker slot released [7](#0-6) . `max_concurrent_connections` is deliberately sized with only 25% headroom above the steady-state stake-based cap to accommodate in-flight handshakes: `self.config.max_staked_connections * 5 / 4` [8](#0-7) . Since this headroom is a single global counter rather than partitioned per-IP, a burst of stalled connections from one source can consume it entirely, and the in-code comment describing the intended mitigation policy ("protect against connection attempt bursts with a global rate-limiter... rate-limit abusive peers by (control-asserted) ip") does not match the actual enforcement point, since both limiters are checked before, but consumed only after, handshake completion [9](#0-8) .

## Impact Explanation
This is a resource-exhaustion/availability degradation at the QUIC connection-admission layer of the TPU path, which falls under "non-RPC remote exhaustion/degradation" in scope. A single unprivileged, unstaked attacker can occupy a meaningful fraction of the shared `max_concurrent_connections` pool indefinitely by cycling stalled handshakes every ~2 seconds, degrading the server's ability to admit genuinely new connections (staked or unstaked) during the attack window. It is bounded in severity: it is not a crash, and once a connection is established, existing per-peer caps and stream throttling (`max_connections_per_peer`, `ConnectionTable` partitioning) still apply; it also does not cause fund loss, false execution, or consensus impact by itself.

## Likelihood Explanation
Likelihood is moderate-to-high: the attacker needs no stake, authentication, or special network position — only the ability to send valid-looking QUIC Initial packets and then withhold subsequent handshake packets. No IP spoofing is required (a normal client stalling after the Initial flight suffices). Because rate limiters are peek-only pre-admission and only debited on success, stalled attempts are never throttled by either limiter, making the attack fully repeatable at whatever rate the attacker can generate new `Incoming` streams from possibly a small number of source addresses (only bounded by whatever OS/network-level connection limits exist per source, not by the application's rate limiters).

## Recommendation
- Reserve/consume tokens (or otherwise account for in-flight attempts) from the per-IP and/or overall rate limiters at admission time (before or at `ClientConnectionTracker::new`), rather than only on handshake success, so stalled attempts are throttled identically to completed ones.
- Add a per-IP cap on concurrent outstanding (`ClientConnectionTracker`-held) connection attempts, independent from the existing per-IP completed-connection rate limiter, preventing a single source from monopolizing the shared handshake headroom.
- Consider reducing `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or making it adaptive under load.

## Proof of Concept
Using the existing test scaffolding pattern (`test_client_connection_tracker`, `test_quic_server_multiple_connections_on_single_client_endpoint` in `streamer/src/nonblocking/quic.rs`) [10](#0-9) : spin up `setup_quic_server`, then repeatedly open QUIC client endpoints that send only the Initial packet (never letting `connecting.await` resolve), in bursts sized close to `qos.max_concurrent_connections()`, while concurrently attempting a legitimate `endpoint.connect(...).await`. Measure `stats.refused_connections_too_many_open_connections` and the increased latency/failure rate of the legitimate connection while the attacker's stalled attempts occupy slots for the ~2s `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window, confirming `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain at 0 for the attacker's stalled attempts.

    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
