Confirmed: `_selectRepositoryRefreshTasks` in `app-store.ts` calls `repositoryWithRefreshedGitHubRepository` on every repository selection, silently invoking `updateRemoteUrl` with the freshly fetched `apiRepo` from the GitHub API — with no user prompt or confirmation.

### Title
Silent, unconfirmed repointing of the `origin` remote URL from an untrusted GitHub API response - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
This is a Desktop analog of the Float Capital "admin/treasury change should be confirmed" finding: a security-relevant, high-impact value (the git remote URL that determines where the user's next `git fetch`/`git pull`/`git push` goes) is overwritten automatically based on data returned by a remote party (the GitHub/GHES API), with no `pendingRemote`-style confirmation step and no user-visible prompt, analogous to the missing `pendingAdmin`/`pendingTreasury` two-step pattern recommended in the report.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  compares the current `origin` remote against `apiRepo.clone_url` returned from the GitHub API and, if the remote hasn't been "manually changed" and the URL scheme (`http`/`https`/etc.) matches, calls `gitStore.setRemoteURL(...)` to rewrite the remote — silently, with no user confirmation dialog. The protocol check only compares `URL.parse(...).protocol` (e.g. `https:` vs `https:`), it never validates that the new host/owner/repo is a legitimate successor of the old one (e.g. same host, same repo id, or an actual rename/transfer event).

This function is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts`, which fetches the repository from the API via `api.fetchRepository(owner, name)` and immediately calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [2](#0-1) . This refresh path runs automatically and non-interactively every time a repository is selected in the sidebar, via `_selectRepositoryRefreshTasks`: [3](#0-2) .

The actual git remote mutation happens in `git-store.ts`'s `setRemoteURL`, which just shells out to `git remote set-url` and reloads remotes — there is no confirmation callback or dialog anywhere in this chain: [4](#0-3) .

### Impact Explanation
Because this happens on ordinary repository selection (not a rare admin action), any response from `repos/{owner}/{name}` that changes `clone_url` while keeping the same URL scheme will cause Desktop to silently retarget `origin` to a different host/repo — for example a GitHub Enterprise Server instance that is compromised or MITM'd (self-signed cert scenarios are common for GHES), or any other path where the API response can be influenced. Once retargeted, the user's next background/foreground fetch pulls from, and next push sends code (and implicitly authenticates) to, the attacker-controlled remote, which can result in credential/token exfiltration via the git transport (HTTP Basic/Bearer or SSH), or silent redirection of what the user believes they are pushing to/pulling from. This matches the report's "wrong address locks out funds/methods" pattern — here the "funds" are the user's push/pull operations and credentials, and the "wrong address" is the rewritten remote.

### Likelihood Explanation
The refresh path fires unconditionally and non-interactively on every repository selection (`_selectRepositoryRefreshTasks`), and the guard logic (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) only prevents overwriting a *manually customized* remote — it does not validate that the new URL is a legitimate/expected successor (same host or same underlying repository identity beyond string matching), so a spoofed or attacker-influenced `apiRepo.clone_url` from a non-dotcom endpoint would satisfy the check as long as the URL scheme matches.

### Recommendation
Require explicit user confirmation before automatically changing the `origin` remote URL in response to an API-detected change (mirroring the report's `pendingAdmin`/`pendingTreasury` two-step pattern): surface a dialog showing the old and new URLs and only call `setRemoteURL` after the user accepts, or at minimum restrict automatic updates to same-host renames verified via a stable repository identifier (e.g. the numeric GitHub repo `id`) rather than trusting `clone_url` string comparison and protocol-only matching.

### Proof of Concept
1. User has a repository cloned from a GitHub Enterprise Server endpoint added as an account in Desktop, with `origin` pointing to `https://ghes.example.com/org/repo.git`.
2. The GHES instance (or a MITM position against it) is compromised/spoofed such that `GET repos/org/repo` returns `clone_url: "https://attacker.example.com/org/repo.git"` — same `https:` scheme, so `protocolsMatch` is true; the remote hasn't been manually altered so `remoteUrlUnchanged` is true; and the URLs differ so `!urlsMatch` is true.
3. User simply clicks on the repository in the Desktop sidebar, triggering `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`.
4. Desktop silently runs `git remote set-url origin https://attacker.example.com/org/repo.git` with no prompt shown to the user, as seen in `updateRemoteUrl` at [5](#0-4) .
5. Subsequent background fetch (`startBackgroundFetching`) and any user-initiated pull/push now interact with `attacker.example.com`, exposing credentials supplied via the git credential flow and/or corrupting what the user believes they are syncing with.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  /** Changes the URL for the remote that matches the given name  */
  public async setRemoteURL(name: string, url: string): Promise<boolean> {
    const wasSuccessful =
      (await this.performFailableOperation(() =>
        setRemoteURL(this.repository, name, url)
      )) === true
    await this.loadRemotes()

    this.emitUpdate()
    return wasSuccessful
  }
