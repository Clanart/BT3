### Title
Deserialized `ThresholdKeys` accept inconsistent verification shares, so `group_key()` (derived only from participants `1..=t`) diverges from the key any other t-subset actually signs under - (File: crypto/dkg/src/lib.rs)

### Summary
The external report (CVE-2020-6117) is an injection-class bug: attacker-controlled bytes reach a sensitive operation without validation. The analog in Serai is `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg`. Untrusted bytes are decoded into `t`, `n`, a `secret_share`, and a map of `verification_shares`, and the group key is computed by Lagrange-interpolating **only** the verification shares of participants `1..=t`. No check verifies that the `verification_shares` lie on a consistent degree-`<t` polynomial, nor that `verification_shares[i]` matches the supplied `secret_share`. A crafted byte string therefore produces `ThresholdKeys` where the reported `group_key()` is unrelated to the public key a different quorum of `t` signers actually produces signatures under.

### Finding Description
`ThresholdKeys::read` deserializes `(t, n, i)`, an interpolation method, a `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` [1](#0-0) . Inside `new`, after only checking the count of shares and that indexes are `<= n`, the group key is computed as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

i.e., the group key is bound exclusively to the shares of participants `1..=t` [2](#0-1) . When `view()` is later called for a signing set `included`, each participant's verification share and the secret share are interpolated over `included`, and FROST `complete` verifies the resulting signature against shares interpolated over `included` — not over `1..=t` [3](#0-2) [4](#0-3) . If the `n` verification shares are not points of one polynomial (trivially achievable by supplying arbitrary points in `ThresholdKeys::read`), every distinct t-subset interpolates a *different* effective group key. The code itself acknowledges this failure mode: `AlgorithmSignatureMachine::complete` notes the only known way for "everyone [to have] a valid share yet the signature was still invalid" is "to deserialize a semantically invalid FrostKeys" [5](#0-4) .

### Impact Explanation
An attacker who can supply the serialized `ThresholdKeys` bytes to a victim (e.g., a key file, backup, or peer-provided key blob fed to `ThresholdKeys::read`) can construct keys where:

- `group_key()` reports key **X** (interpolated from attacker-chosen `verification_shares[1..=t]`), which is what integrators use to derive the wallet/address the group controls.
- A quorum of `t` signers drawn from participants outside `{1..=t}` produces FROST signatures whose shares are individually valid, yet which verify under a *different* key **Y** whose discrete log the attacker can fully control (by choosing the verification shares for that subset as `G * chosen_i`).

Result: the victim believes it operates a threshold wallet under `X`, while signatures produced by a quorum are valid under attacker-chosen `Y`. Depending on how the consumer binds signatures to keys, this either silently produces signatures for an attacker-owned key (any funds/approvals addressed via `group_key()` flow to a key the attacker controls while appearing legitimate) or causes unrecoverable signing failure detected only after funds are committed. This is a concrete integrity failure — an incorrect verifier formula / inconsistent key material accepted from untrusted bytes — not merely a DoS.

### Likelihood Explanation
Reachability requires only that attacker-influenced bytes reach `ThresholdKeys::read`, which is a public deserialization API explicitly in scope for untrusted input. The attack needs no collusion between signers, no malicious validator assumptions, and no leaked secrets: the entire exploit is a malformed serialized structure. Severity is Medium: the impact requires a downstream consumer that trusts `group_key()` from deserialized keys without cross-checking against the actual signing quorum's interpolated key, but within that deployment the consequence (key substitution) is complete.

### Recommendation
In `ThresholdKeys::new`, validate consistency of the key material:

1. Verify `C::generator() * secret_share == verification_shares[&params.i()]`.
2. Verify all `verification_shares` lie on a common degree-`<t` polynomial — e.g., check that for every participant `l`, `verification_shares[l]` equals the interpolation of shares `1..=t` evaluated at `l` (or equivalently that the group key is identical for every t-subset used). A cheaper equivalent: require that `group_key` recomputed via interpolation over a second disjoint t-subset matches.
3. Reject identity/invalid points in verification shares (use a `read_G` that rejects identity, as `Curve::read_G` in FROST already does [6](#0-5) ).

This turns `ThresholdKeys::read` into a validating parser rather than a raw injection point for inconsistent key material.

### Proof of Concept
```rust
// Construct inconsistent verification shares: participants 1..=t encode a
// known key X, participants t+1..=n encode attacker-chosen key Y.
let n = 5u16; let t = 3u16;
let x: Zeroizing<F> = random();            // victim-facing secret
let y: Zeroizing<F> = random();            // attacker-known secret
let mut vs = HashMap::new();
for i in 1..=t { vs.insert(Participant::new(i).unwrap(), G::generator() * x_poly(i)); }
for i in (t+1)..=n { vs.insert(Participant::new(i).unwrap(), G::generator() * y_poly(i)); }
// serialize via write() fields / feed to ThresholdKeys::read:
//   t=3, n=5, i=1, interpolation=Lagrange, secret_share=<anything>, vs as above
let keys = ThresholdKeys::<C>::read(&mut bytes).unwrap(); // accepted
assert_eq!(keys.group_key(), X); // reports X
// A quorum {3,4,5} calling keys.view(...) and running FROST produces a
// signature whose shares are individually valid yet which verifies under
// the key interpolated by {3,4,5} — attacker-controlled Y, not X.
```
