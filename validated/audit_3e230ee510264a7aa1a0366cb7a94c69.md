### Title
`SignableTransaction::new` computes `needed_fee`/vsize before the OP_RETURN output is added, so the signed transaction pays a lower fee rate than requested and can fall below the minimum relay fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
This is the same bug class as `Controller.inCaseStrategyGetStuck` failing to call `updateBalance`: a mutation (appending the `data`/OP_RETURN output, and later the change output) is applied to `tx_outs` after the "recorded" accounting values (`vbytes`, `needed_fee`) were computed, and those recorded values are never refreshed to reflect the actual transaction. The struct then persists the stale `needed_fee` and the real transaction diverges from what was measured, yielding an underpaid fee rate — an untrusted `data` payload (fed via burn instructions / `SignableTransaction::new(_, _, _, Some(data), _)`) directly controls the size of the unaccounted output.

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output onto `tx_outs` at `networks/bitcoin/src/wallet/send.rs:194-202`, then computes weight/vbytes via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, which rebuilds a mock transaction containing only `payments` — the `data` output is never included in the measured transaction. `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum-relay check (lines 211-213) therefore use a vsize understated by the full size of the OP_RETURN output (up to ~90 vbytes for the 80-byte max data). The same omission repeats in the change path at lines 225-227: `fee_with_change` is measured on `payments` plus change, still excluding the `data` output. The stored `needed_fee` (line 254) and the check `input_sat < payment_sat + needed_fee` (line 215) are thus computed against a transaction smaller than the one actually signed in `TransactionSignMachine::sign` (lines 373-397). The reported analog of "field does not track the real balance, so the withdraw amounts are wrong" maps here to "`needed_fee`/`vbytes` do not track the real transaction, so the fee deducted is wrong for the size actually broadcast."

### Impact Explanation
`fee()` (lines 138-141) returns `sum(prevouts) - sum(outputs)`, which equals `needed_fee` — the fee amount is correct, but because the real transaction is larger than measured, the effective fee rate is `needed_fee / actual_vsize < fee_per_vbyte`. With a large `data` payload the discrepancy is meaningful: the signed transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` in edge cases (the min-relay check at lines 211-213 uses the same understated `vbytes`, so a `fee_per_vbyte` that just passes the check can produce a real rate under the relay minimum), causing broadcast rejection, or simply a degraded fee rate that stalls confirmation. For the threshold wallet this means the multisig signs a transaction that will not propagate or confirm as intended — funds appear spent/locked by an output the network won't accept, and each input's `Prevouts::All` commitment re-keying means a new attempt requires re-signing. This is reachable entirely from public inputs: the `data` bytes and `fee_per_vbyte` are attacker-influenced request parameters.

### Likelihood Explanation
Any caller passing `data` (e.g., `OutInstruction` payloads that embed data in Bitcoin transactions) with a `fee_per_vbyte` near the minimum relay bound triggers a transaction whose true fee rate is below the relay floor. Non-edge cases still silently degrade the negotiated fee rate proportional to data size. No malicious validator or leaked key is required — only untrusted bytes reaching `SignableTransaction::new`.

### Recommendation
Include the OP_RETURN output in the fee measurement: pass the populated `tx_outs` (or the data length) into `calculate_weight_vbytes` so `vbytes`, `needed_fee`, the min-relay check, and the change-value computation at lines 204-235 all reflect the final transaction — i.e., "update the recorded balance" after the mutation, matching the upstream fix of calling `updateBalance` after `inCaseStrategyGetStuck`.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs style
let inputs = vec![received_output]; // 1 input
let data = vec![0u8; 80];           // max allowed OP_RETURN payload
let fee_per_vbyte = 1;              // sat/vB, near relay minimum

let tx = SignableTransaction::new(
  inputs, &[], None, Some(data), fee_per_vbyte,
).unwrap();

// needed_fee was computed from a mock tx WITHOUT the OP_RETURN output:
// calculate_weight_vbytes measured `payments` only (send.rs:204), while
// tx_outs already contained the data output (send.rs:194-202).
let actual_vsize = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < actual_vsize * fee_per_vbyte);
// effective rate = needed_fee / actual_vsize < 1 sat/vB
// -> below DEFAULT_MIN_RELAY_TX_FEE; broadcast fails despite the
//    min-relay check at send.rs:211-213 having "passed".
```
