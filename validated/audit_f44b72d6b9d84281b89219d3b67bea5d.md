### Title
Vault `deposit()` mints zero shares for a nonzero underlying contribution when `total-assets` is fully utilized, permanently donating the deposit to existing shareholders - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent files in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
`convert-to-shares-preview()` returns `u0` shares whenever `total-supply-preview()` is nonzero but `total-assets-preview()` is `u0`, yet `deposit()` never checks that the computed `inkind` (shares to mint) is greater than zero before accepting the underlying transfer and minting. This mirrors the GoodDollar bug: a computed "amount to mint" derived from a ratio can silently resolve to zero, and the caller-facing function proceeds to move real value (accepting the deposit, incrementing `assets`) without gating on that zero result.

### Finding Description
`convert-to-shares-preview` explicitly special-cases a zero total-assets denominator by returning `u0`: [1](#0-0) 

`total-assets`/`total-assets-preview` can legitimately be `u0` when the vault is fully utilized (`assets` var is `0` because all liquidity is out on loan) and no unrealized interest has accrued yet (`debt <= borrowed`): [2](#0-1) 

`deposit()` computes `inkind` via this preview function, but only asserts `amount > 0` and `inkind >= min-out` (a caller-supplied slippage bound). It never asserts `inkind > 0`. It then unconditionally accepts the underlying transfer, mints `inkind` shares (possibly zero), and increases `assets` by the full deposited amount: [3](#0-2) 

By contrast, `redeem()` in the same contract explicitly guards against a zero output with `ERR-OUTPUT-ZERO`, proving the pattern is known and intentionally enforced on the withdrawal side but omitted on the deposit side: [4](#0-3) 

The identical `convert-to-shares-preview`/`deposit` structure (missing zero-share check) is duplicated across every vault: [5](#0-4) [6](#0-5) 

**Direction of the error / who profits:** If a depositor calls `deposit()` when `total-assets` has dropped to `0` (vault fully borrowed out) while `total-supply` (outstanding `zft` shares) is nonzero, `inkind` resolves to `0`. As long as the depositor's `min-out` is `0` (the common/naive default for a first-time or automated depositor unaware of the internal utilization state), the `>= inkind min-out` check (`0 >= 0`) passes trivially. The depositor's full `amount` of underlying tokens is pulled in and added to `assets`, but they receive zero `zft` shares — their contribution is irrecoverably donated to the pool. Every existing `zft` holder's share of `total-assets` increases proportionally without them contributing anything, i.e., existing shareholders profit at the depositor's expense.

An attacker can engineer the triggering state (`assets == 0`, `ts > 0`) by borrowing the vault's full `available-assets` immediately before a victim's deposit transaction lands (front-running, or simply timing deposits against a known fully-utilized vault), reproducing the "attacker manipulates a ratio's denominator to zero, victim's subsequent value-adding call silently mints nothing" root cause from the GoodDollar report.

### Impact Explanation
This is a permanent freezing/loss of the victim depositor's funds: the underlying tokens are transferred into the vault (`assets` increases) but no `zft` shares are minted to represent that claim, so the depositor can never redeem the value back. Concurrently, existing shareholders' claim on `total-assets` is inflated without cost, i.e., the deposited amount is effectively transferred to them. This satisfies the in-scope **High** impact class (temporary/permanent freezing of user's principal) and arguably **Critical** insofar as it is a direct, irreversible loss of the depositor's principal that redistributes to other position holders.

### Likelihood Explanation
Likelihood depends on the vault reaching `assets == 0` with `total-supply > 0` — a state reachable through ordinary high-utilization borrowing (100% utilization) that the protocol's caps do not explicitly forbid, combined with a depositor (or an automated integrator) supplying `min-out = 0`. An attacker can proactively force this state via a borrow immediately preceding a targeted victim deposit. This is a realistic, low-cost attack path (borrowing available liquidity is a normal, permissionless operation via the market contract), though it requires either a careless `min-out` on the victim's side or precise timing against a naturally reached fully-utilized state.

### Recommendation
Add an explicit zero-output guard to `deposit()` symmetric with the one already present in `redeem()`, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, in every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`). This prevents accepting a nonzero underlying contribution while minting zero shares regardless of the caller-supplied `min-out`.

### Proof of Concept
1. Vault starts with nonzero `total-supply` (`zft` shares outstanding) and nonzero `assets`.
2. A borrower (attacker or organic activity) calls `system-borrow` via the market for the full `available-assets`, driving `(var-get assets)` to `0` [7](#0-6) 
   immediately after an `accrue()` pass so `debt <= borrowed` (no unrealized interest), making `total-assets-preview()` return `0`.
3. A victim calls `deposit(amount, 0, recipient)` with `min-out = 0`. `convert-to-shares-preview(amount)` evaluates `ts != 0` and `ta == 0`, returning `inkind = u0` [1](#0-0) 
4. `deposit()`'s checks pass (`amount > 0` ✓, `inkind (0) >= min-out (0)` ✓), the underlying transfer succeeds, `ft-mint? zft 0 recipient` mints zero shares, and `assets` increases by the full `amount` [8](#0-7) 
5. The victim holds `0` `zft` tokens and can never redeem back the deposited `amount`; existing shareholders' claim on the vault's assets increases by that same amount at no cost to them.
