### Title
Deep-link `open-repository-from-url` action forwards an unvalidated URL scheme directly into `git clone` - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/git/clone.ts`)

### Summary
The bug-class from the report is "a validation check that exists for one code path is missing/disabled on a sibling code path, letting an attacker skip an intended restriction." In GitHub Desktop, `enterprise-validate-url.ts` shows the app enforces a strict `https:`-only allowlist when a URL is going to be used for a trusted server connection [1](#0-0) . No equivalent scheme check exists on the sibling, attacker-reachable path: `parseAppURL`'s `openrepo` action parses the `url` query/path segment used for the "Open in Desktop" deep link and passes it through untouched, without restricting it to `http(s)`/`ssh` [2](#0-1) . That raw string ultimately reaches `clone()`, which validates only the **destination** path (`isClonePathSensitive`) and not the **source** URL, before splicing it directly into the `git clone` argument vector [3](#0-2) .

### Finding Description
`main.ts` registers Desktop as the handler for `x-github-client://` (and legacy `github-mac://`/`github-windows://`) links and forwards any URL sent by `open-url`/protocol-launcher arguments to `handleAppURL` → `parseAppURL` [4](#0-3) . For the `openrepo` hostname, `parseAppURL` only checks that a PR number is numeric and a branch name has no invalid ref characters — it does not check the scheme of the `url` field at all [2](#0-1) . The resulting `IOpenRepositoryFromURLAction.url` flows into the dispatcher's clone/open logic and, for a URL that isn't already tracked, into `_clone`/`clone()`, which builds `['clone', '--recursive', ..., '--', url, path]` and executes it with no scheme allowlist, only a check on the local destination directory [5](#0-4) .

This mirrors exactly the pattern in the report: a validating guard exists elsewhere in the codebase (`validateURL` restricting to `https:`) but the analogous, attacker-reachable entry point (the clone URL taken from a clickable deep link) has no such guard, so the intended restriction ("only network git protocols may be used to clone") is bypassed by construction, not by disabling a check but by that check simply never having been applied to this path.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openrepo/<url>` link (e.g., embedded on a web page, in a README, or in a chat message — GitHub.com itself renders "Open in Desktop" links from arbitrary repo URLs) can supply a `file://` or bare local path as `<url>`. Desktop will then run `git clone --recursive -- <attacker-supplied-path> <destination>`, letting the deep link direct the app to read from an arbitrary local filesystem location the OS user can already access and materialize it as a new "repository" that Desktop opens and manages (including its `--recursive` submodule expansion, which can pull in further local paths referenced by `.gitmodules` in the source). This is a "corruption of what the app treats as a legitimate remote" and a file-read-outside-the-intended-repo primitive triggered purely by a link click, matching the report's abuse pattern (a validation guard applied in one place but missing on the reachable sibling path).

### Likelihood Explanation
High for triggering (a single click on an attacker-controlled/embedded deep link is a well-established Desktop attack surface, and `possibleProtocols` explicitly registers this scheme for OS-level handling [6](#0-5) ). Medium-to-uncertain for full impact: I could not, within available searches, trace a confirmed downstream exfiltration sink (e.g., automatic push to an attacker remote after the local clone) — the clone-time behavior and lack of source-URL validation are directly confirmed in code, but the strongest "data leaves the machine" chain (rather than "app treats local path as remote") is not conclusively demonstrated in what I retrieved.

### Recommendation
Apply the same protocol allowlist used in `enterprise-validate-url.ts` (or an equivalent restricted to `https:`/`ssh:`/`git:`) to the `url` extracted in `parseAppURL`'s `openrepo` branch before it is returned as a valid `open-repository-from-url` action, rejecting `file:` and bare/relative local paths outright [2](#0-1) . Defense in depth: `clone()` should also reject non-network schemes for its `url` parameter independent of the caller, mirroring the existing destination-path sensitivity check [7](#0-6) .

### Proof of Concept
1. Attacker crafts: `x-github-client://openrepo/file:///Users/victim/some/local/git/repo`
2. Victim (with Desktop installed and registered as the protocol handler) clicks the link from a webpage/README/chat client.
3. `main.ts`'s `open-url` handler invokes `handleAppURL` → `parseAppURL`, which returns `{ name: 'open-repository-from-url', url: 'file:///Users/victim/some/local/git/repo', ... }` with no scheme check [8](#0-7) .
4. Desktop calls `clone()` with that URL as the clone source, running `git clone --recursive -- file:///Users/victim/some/local/git/repo <dest>` [3](#0-2) , materializing the target local path as a Desktop-managed repository without any user-initiated file/folder picker step.

**Caveat:** I was not able to fully confirm, within the tool budget available, whether a subsequent automatic step (e.g., silently configuring a remote or push) turns this into confirmed off-machine exfiltration, versus "merely" tricking the app into opening/copying a local path the user could already access manually. Treat the impact rating as provisional pending that additional trace.

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
