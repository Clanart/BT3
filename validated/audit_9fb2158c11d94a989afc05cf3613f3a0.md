### Title
Offer/OFFER_MOD settlement is not bound to the intended taker, letting a MEV bot or block proposer front-run and steal a taker's arbitrage/settlement profit - (File: chia/wallet/trading/offer.py)

### Summary
The Rubicon report describes a bug class where a "filler" role that is supposed to require off-chain effort to be profitable is actually optional/unauthenticated on-chain (`exclusive == address(0)` bypass in `hasFillingRights`), so a MEVbot or block proposer can copy the pending fill transaction from the mempool, resubmit it as themselves, and steal the filler's profit while the original filler's transaction fails and burns gas. The same structural weakness exists in Chia's offer settlement path: `Offer.to_valid_spend()` builds a completion spend for the maker's `OFFER_MOD` coins using only the publicly-known notarized-payment data (asset id, puzzle hash, amount, nonce), with no cryptographic binding to a specific taker's identity or signature [1](#0-0) .

### Finding Description
When a taker calls `TradeManager.respond_to_offer`, it computes the `arbitrage()` (the leftover/spread amount the taker is entitled to) and builds a completion `WalletSpendBundle` that aggregates the maker's original `OFFER_MOD`-locked coin spends together with the taker's own completion spends [2](#0-1) . `Offer.to_valid_spend()` constructs the actual settlement solution purely from `requested_payments`/`arbitrage()` data and an `arbitrage_ph` supplied at completion time — it does not require any secret known only to the intended taker, nor a maker signature over the taker's identity [3](#0-2) .

Because the maker's `OFFER_MOD` coin spends are re-broadcast as part of the taker's completion transaction, once that transaction is visible in the mempool (or once an offer bech32 file circulates before being taken), any third party can read the maker's `notarized_payments`, `driver_dict`, and coin data and construct their *own* alternative completion spend for the *same* maker coins, directing the "arbitrage" leftover (and, more importantly, the maker's whole offered asset) to their own puzzle hash instead of the original taker's. Since this alternative spend consumes the exact same maker coins, it directly conflicts with the honest taker's transaction in the mempool. Chia's mempool replace-by-fee logic (`can_replace`) allows any conflicting transaction with sufficiently higher `fee_per_cost` and total fee increase to evict the existing one [4](#0-3) . A MEVbot or the block proposer itself (who controls transaction ordering/inclusion) can therefore front-run the honest taker by rebroadcasting a copy of the settlement with a higher fee, taking the maker's assets and the arbitrage profit for itself, while the original taker's transaction is evicted from the mempool (losing the trade and wasting the fee they attached) — mirroring exactly the impact described in the Rubicon report ("original transaction would fail and suffer both order profit and gas loss").

This is structurally analogous to the `ExclusivityOverrideLib.hasFillingRights` bug: just as `exclusive == address(0)` allows *any* address to act as filler once order data leaks to the mempool, Chia's `OFFER_MOD` settlement allows *any* address to act as the completing party once the maker's offer data leaks to the mempool (via the honest taker's own broadcast) or is otherwise observed off-chain (shared offer files, DL/NFT marketplaces, etc.).

### Impact Explanation
An attacker (MEV bot or the block proposer who orders transactions) can capture assets and settlement profit that were rightfully due to the intended offer taker, causing:
- Loss of the intended taker's fee and the settlement asset/arbitrage profit they expected to receive.
- Redirection of the maker's offered coins to an attacker-chosen puzzle hash — a form of offer-settlement theft, explicitly listed as an in-scope impact category.

This rises to Medium/High severity because it is a concrete, unauthorized-recipient redirection of coin value that requires no cooperation from the maker or victim taker beyond broadcasting a normal `take_offer` transaction.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (1) monitoring the mempool for `take_offer` transactions or otherwise obtaining an offer file before/while it is completed, and (2) attaching a higher fee to win RBF, which is straightforward for any bot with mempool visibility, and trivial for a block proposer who can simply reorder/replace transactions within a block they are building. Both conditions are readily achievable on a public, permissionless network, similar to well-known offer-sniping behavior already informally acknowledged in the Chia ecosystem for NFT offers.

### Recommendation
- Bind offer completion cryptographically to a specific taker (e.g., require an assertion/announcement that can only be satisfied by a party holding a taker-specific secret, or require the taker's spend to be co-signed/aggregated with the maker's spend in a way that cannot be replayed by a third party without that secret).
- Where feasible, use puzzle-level restrictions (e.g., a taker-specific puzzle hash commitment baked into the notarized payment) so that a third party cannot redirect the settlement to an arbitrary address purely from public mempool data.
- Consider mempool/network-level mitigations such as encouraging private submission channels for time-sensitive offer completions, or documenting this race condition clearly so wallets can warn users that offer-taking is a race and can be front-run by higher-fee competitors.

### Proof of Concept
1. Maker publishes/creates an `Offer` with `requested_payments` for asset X, offering asset Y [5](#0-4) .
2. Honest taker B calls `respond_to_offer`, which computes `arbitrage()` and builds a completion spend bundle that aggregates the maker's `OFFER_MOD` coin spends with B's own payment spends, directing arbitrage/leftover to B's puzzle hash [6](#0-5) , then broadcasts it to the mempool with fee F.
3. Attacker A observes this transaction in the mempool (or observed the raw offer file earlier), extracts the maker's `OFFER_MOD` coin data and notarized-payment structure, and independently calls `Offer.to_valid_spend()` on the same maker offer using A's own `arbitrage_ph`, producing a conflicting spend of the same maker coins [1](#0-0) .
4. Attacker A broadcasts this alternative completion with a fee F' > F satisfying `can_replace`'s fee-per-cost and minimum-fee-increase rules [7](#0-6) , evicting B's transaction from the mempool.
5. A's transaction confirms, redirecting the maker's offered assets (and any arbitrage) to A instead of B; B's transaction fails/is dropped, losing B the trade and the fee already committed.

Note: I was unable to locate/verify the actual `settlement_payments.clsp` CLVM source in the indexed codebase (only the Python driver `chia/wallet/trading/offer.py` was available), so the exact on-chain enforcement details of `OFFER_MOD` (e.g., whether any additional binding exists inside the CLVM puzzle itself) could not be fully confirmed from the indexed files. If a Devin session with full repo access is started, this should be double-checked against the actual `.clsp`/`.clvm` puzzle source before finalizing severity.

    @staticmethod
    def notarize_payments(
        requested_payments: dict[bytes32 | None, list[CreateCoin]],  # `None` means you are requesting XCH
        coins: list[Coin],
    ) -> dict[bytes32 | None, list[NotarizedPayment]]:
        # This sort should be reproducible in CLVM with `>s`
        sorted_coins: list[Coin] = sorted(coins, key=Coin.name)
        sorted_coin_list: list[list[bytes32 | uint64]] = [coin_as_list(c) for c in sorted_coins]
        nonce: bytes32 = Program.to(sorted_coin_list).get_tree_hash()

        notarized_payments: dict[bytes32 | None, list[NotarizedPayment]] = {}
        for asset_id, payments in requested_payments.items():
            notarized_payments[asset_id] = []
            for p in payments:
                notarized_payments[asset_id].append(NotarizedPayment(p.puzzle_hash, p.amount, p.memos, nonce=nonce))

        return notarized_payments

    def is_valid(self) -> bool:
        return all([value >= 0 for value in self.arbitrage().values()])

    # A "valid" spend means that this bundle can be pushed to the network and will succeed
    # This differs from the `to_spend_bundle` method which deliberately creates an invalid SpendBundle
    def to_valid_spend(self, arbitrage_ph: bytes32 | None = None, solver: Solver = Solver({})) -> WalletSpendBundle:
        if not self.is_valid():
            raise ValueError("Offer is currently incomplete")

        completion_spends: list[CoinSpend] = []
        all_offered_coins: dict[bytes32 | None, list[Coin]] = self.get_offered_coins()
        total_arbitrage_amount: dict[bytes32 | None, int] = self.arbitrage()
        for asset_id, payments in self.requested_payments.items():
            offered_coins: list[Coin] = all_offered_coins[asset_id]

            # Because of CAT supply laws, we must specify a place for the leftovers to go
            arbitrage_amount: int = total_arbitrage_amount[asset_id]
            all_payments: list[NotarizedPayment] = payments.copy()
            if arbitrage_amount > 0:
                assert arbitrage_amount is not None
                assert arbitrage_ph is not None
                all_payments.append(NotarizedPayment(arbitrage_ph, uint64(arbitrage_amount)))

    async def respond_to_offer(
        self,
        offer: Offer,
        peer: WSChiaConnection,
        action_scope: WalletActionScope,
        solver: Solver | None = None,
        fee: uint64 = uint64(0),
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> TradeRecord:
        if solver is None:
            solver = Solver({})
        take_offer_dict: dict[bytes32 | int, int] = {}
        arbitrage: dict[bytes32 | None, int] = offer.arbitrage()

        for asset_id, amount in arbitrage.items():
            if asset_id is None:
                wallet: WalletProtocol | None = self.wallet_state_manager.main_wallet
                assert wallet is not None
                key: bytes32 | int = int(wallet.id())
            else:
                # ATTENTION: new wallets
                wallet = await self.wallet_state_manager.get_wallet_for_asset_id(asset_id)
                if wallet is None and amount < 0:
                    raise ValueError(f"Do not have a wallet for asset ID: {asset_id} to fulfill offer")
                elif wallet is None or wallet.type() in {WalletType.NFT, WalletType.DATA_LAYER}:
                    key = asset_id
                else:
                    key = int(wallet.id())
            take_offer_dict[key] = amount

        # First we validate that all of the coins in this offer exist
        valid: bool = await self.check_offer_validity(offer, peer)
        if not valid:
            raise ValueError("This offer is no longer valid")
        # We need to sandbox the transactions here because we're going to make our own
        async with self.wallet_state_manager.new_action_scope(
            action_scope.config.tx_config, push=False
        ) as inner_action_scope:
            result = await self._create_offer_for_ids(
                take_offer_dict,
                inner_action_scope,
                offer.driver_dict,
                solver,
                fee=fee,
                extra_conditions=extra_conditions,
                taking=True,
            )
            if not result[0] or result[1] is None:
                raise ValueError(result[2])

            _success, take_offer, _error = result

            complete_offer, valid_spend_solver = await self.check_for_final_modifications(
                Offer.aggregate([offer, take_offer]), solver, inner_action_scope
            )

        async with action_scope.use() as interface:
            if interface.side_effects.get_unused_derivation_record_result is not None:
                # This error is of a protection against potential misues of this band-aid solution.
                # We should put more thought into how sub-action scopes are generated and what effects
                # we might want to push. A ticket to this respect can be found [CHIA-2984].
                raise ValueError("Cannot use `respond_to_offer` with existing puzzle hash generation")
            interface.side_effects.get_unused_derivation_record_result = (
                inner_action_scope.side_effects.get_unused_derivation_record_result
            )
        self.log.info("COMPLETE OFFER: %s", complete_offer.to_bech32())
        assert complete_offer.is_valid()
        final_spend_bundle: WalletSpendBundle = complete_offer.to_valid_spend(
            solver=Solver({**valid_spend_solver.info, **solver.info})
        )

def can_replace(conflicting_items: list[MempoolItem], new_item: MempoolItem) -> bool:
    """
    This function implements the mempool replacement rules. Given a Mempool item
    we're attempting to insert into the mempool (new_item) and the set of existing
    mempool items that conflict with it, this function answers the question whether
    the existing items can be replaced by the new one.
    """

    conflicting_fees = 0
    conflicting_cost = 0
    assert_height: uint32 | None = None
    assert_before_height: uint32 | None = None
    assert_before_seconds: uint64 | None = None
    # we don't allow replacing mempool items with new ones that remove
    # eligibility for dedup and fast-forward. Doing so could be abused by
    # denying such spends from operating as intended
    # collect all coins that are eligible for dedup and FF in the existing items
    existing_ff_spends: set[bytes32] = set()
    existing_dedup_spends: set[bytes32] = set()

    for item in conflicting_items:
        conflicting_fees += item.fee
        conflicting_cost += item.cost

        # All coins spent in all conflicting items must also be spent in the new item. (superset rule). This is
        # important because otherwise there exists an attack. A user spends coin A. An attacker replaces the
        # bundle with AB with a higher fee. An attacker then replaces the bundle with just B with a higher
        # fee than AB therefore kicking out A altogether. The better way to solve this would be to keep a cache
        # of booted transactions like A, and retry them after they get removed from mempool due to a conflict.
        for coin_id, bcs in item.bundle_coin_spends.items():
            if coin_id not in new_item.bundle_coin_spends:
                log.debug("Rejecting conflicting tx as it does not spend conflicting coin %s", coin_id)
                return False
            if bcs.supports_fast_forward:
                existing_ff_spends.add(bytes32(coin_id))
            if bcs.eligible_for_dedup:
                existing_dedup_spends.add(bytes32(coin_id))

        assert_height = optional_max(assert_height, item.assert_height)
        assert_before_height = optional_min(assert_before_height, item.assert_before_height)
        assert_before_seconds = optional_min(assert_before_seconds, item.assert_before_seconds)

    # New item must have higher fee per cost
    conflicting_fees_per_cost = conflicting_fees / conflicting_cost
    if new_item.fee_per_cost <= conflicting_fees_per_cost:
        log.debug(
            f"Rejecting conflicting tx due to not increasing fees per cost "
            f"({new_item.fee_per_cost} <= {conflicting_fees_per_cost})"
        )
        return False

    # New item must increase the total fee at least by a certain amount
    fee_increase = new_item.fee - conflicting_fees
    if fee_increase < MEMPOOL_MIN_FEE_INCREASE:
        log.debug(f"Rejecting conflicting tx due to low fee increase ({fee_increase})")
        return False
