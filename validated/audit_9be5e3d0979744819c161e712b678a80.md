Based on my research, I found a structurally strong analog in GitHub Desktop's trampoline/credential-helper subsystem. The broken invariant in the Solidity report is: *an external call made mid-operation can call back into shared state and mutate it before the outer transaction finishes, and the guarded function does not check that this reentry is legitimate*. The Desktop analog is the trampoline credential helper accepting a credential request for **any** host from **any** process that inherits the current operation's environment, without tying the request to the repository/remote actually being operated on.

### Title
Git hooks/filters run during a Desktop-initiated operation can request and receive the signed-in user's GitHub credentials for an arbitrary host via the inherited trampoline credential helper - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Desktop configures every git subprocess it spawns to use `credential.helper=desktop`, `GIT_ASKPASS=''`, and a per-operation `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` via environment variables, explicitly so that filters like Git LFS (child processes of the git command) can "pick up our configuration." [1](#0-0)  The token is validated only for existence/liveness, not for which repository/operation it belongs to. [2](#0-1)  The credential `get` handler resolves credentials purely from the `host`/`url` fields supplied in the incoming request, independent of the repository or remote that the outer Desktop operation is actually acting on. [3](#0-2) 

### Finding Description
When Desktop performs a remote git operation (clone/fetch/pull/checkout), it wraps the git invocation with `withTrampolineEnv`, which issues a fresh trampoline token and injects it plus `GIT_CONFIG_PARAMETERS='credential.helper=' 'credential.helper=desktop'` into the child process environment. [4](#0-3)  Because this is done via environment variables rather than one-off `-c` arguments specifically so "commands invoked by filters ... are able to pick up our configuration," any grandchild process git spawns during that operation — smudge/clean filters declared in a cloned repo's `.gitattributes`, or git hooks — also inherits `DESKTOP_TRAMPOLINE_TOKEN`, `DESKTOP_PORT`, and the `credential.helper=desktop` config. [5](#0-4) 

The trampoline server accepts any command over the local socket as long as `isValidTrampolineToken` returns true for the token in the message — there is no check that the caller is the specific git process the outer operation spawned, nor which repository/remote the token was issued for. [6](#0-5)  The credential helper's `getCredential` function then looks up an account purely by the `host`/`url` in the request (`getCredentialUrl(cred)`), first checking internally stored GitHub accounts. [7](#0-6) [8](#0-7) 

This means a malicious repository can ship a `.gitattributes` filter or a hook (e.g. `post-checkout`) that, while running as a legitimate child of Desktop's own git invocation (and thus holding a valid trampoline token for that in-flight operation), issues its own `git credential fill` request for `host=github.com` — a host unrelated to the actual remote Desktop is talking to. The credential helper cannot distinguish this "reentrant" request from the legitimate one made by the outer git process for the real remote, and returns the user's real GitHub account login/OAuth token via `credWithAccount`. [9](#0-8) 

This is structurally the same class of bug as `mergeTranches()`: an external call made during an in-progress privileged operation (the git subprocess tree) is allowed to re-enter shared, sensitive state (the trampoline/credential-helper session) and extract/mutate something the outer call did not intend to expose, because the guard (`isValidTrampolineToken`) only checks token liveness, not call provenance or the intended target of that specific operation.

### Impact Explanation
If exploitable, this allows exfiltration of the signed-in user's GitHub OAuth token to an attacker who merely gets the user to clone/fetch/checkout a malicious repository (or add it as a submodule) — no other credentials, admin rights, or local access are required. This matches the report's listed valid impact category ("attacker controls a cloned/fetched repository ... credential/token exfiltration").

### Likelihood Explanation
Requires the victim to clone or fetch a repository containing an attacker-crafted `.gitattributes` filter or hook, which is a normal, unprivileged content addition to a repo — no unusual user action beyond opening/cloning the repo is needed. Whether git hooks execute automatically for Desktop-driven clone/fetch/checkout, and whether Desktop's `app/src/lib/hooks/with-hooks-env.ts` / `hooks-proxy.ts` already sandbox or strip this environment for hook execution, could not be fully confirmed from the available index — those files exist and reference `GIT_CONFIG_PARAMETERS`/`credential.helper=desktop`, suggesting hooks are handled through a related but distinct code path that may already mitigate part of this. This uncertainty should be resolved by inspecting `app/src/lib/hooks/with-hooks-env.ts` and `app/src/lib/hooks/hooks-proxy.ts` directly (their contents were not retrievable within the current investigation due to tool/iteration limits), and by testing whether Git LFS/`.gitattributes` filters specifically (which are explicitly called out as intended recipients of this env, per the comment in `trampoline-environment.ts`) can be abused this way.

### Recommendation
Scope each trampoline token's credential responses to the specific host/remote of the operation that requested the token (e.g., pass the expected remote host into `withTrampolineEnv`/`withTrampolineToken` and have `getCredential` reject requests whose `host` doesn't match), rather than trusting any process holding a live token to request credentials for an arbitrary host. Separately, audit `with-hooks-env.ts`/`hooks-proxy.ts` to confirm whether hook-spawned processes already have a restricted environment, and if not, strip `DESKTOP_TRAMPOLINE_TOKEN`/`GIT_CONFIG_PARAMETERS` before invoking user-controlled hooks/filters unless strictly required (e.g., only for LFS-known filters, not for arbitrary hooks).

### Proof of Concept
1. Attacker publishes a repo containing a `.gitattributes` entry with a custom `filter.exfil.smudge` script, or a `post-checkout` hook.
2. Victim, signed in to GitHub Desktop, clones/fetches this repo. Desktop invokes git via `withTrampolineEnv`, injecting a live `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` and `credential.helper=desktop` into the git process's environment. [1](#0-0) 
3. During checkout, git invokes the malicious filter/hook script as a child process, inheriting that environment.
4. The script runs `git credential fill` with `host=github.com` (unrelated to the actual remote), which reaches Desktop's `trampolineServer` and passes `isValidTrampolineToken`. [6](#0-5) 
5. `getCredential`/`getGitHubCredential` looks up the stored GitHub account for `github.com` and returns its login/token to the requesting (attacker) process. [7](#0-6) 
6. The malicious script exfiltrates the returned token over the network.

I was unable to fully confirm within the available tool budget whether Desktop's hook execution path (`with-hooks-env.ts`, `hooks-proxy.ts`) already neutralizes this by stripping the trampoline environment before running user-supplied hooks — that should be verified directly (e.g., via a Devin session with full file access) before treating this as a confirmed, unmitigated finding.

export async function withTrampolineEnv<T>(
  fn: (env: object) => Promise<T>,
  path: string,
  isBackgroundTask = false,
  customEnv?: Record<string, string | undefined>
): Promise<T> {
  const sshEnv = await getSSHEnvironment()

  return withTrampolineToken(async token => {
    isBackgroundTaskEnvironment.set(token, isBackgroundTask)
    trampolineEnvironmentPath.set(token, path)

    const existingGitEnvConfig =
      customEnv?.['GIT_CONFIG_PARAMETERS'] ??
      process.env['GIT_CONFIG_PARAMETERS'] ??
      ''

    const gitEnvConfigPrefix =
      existingGitEnvConfig.length > 0 ? `${existingGitEnvConfig} ` : ''

    // The code below assumes a few things in order to manage SSH key passphrases
    // correctly:
    // 1. `withTrampolineEnv` is only used in the functions `git` (core.ts)
    // 2. Those two functions always thrown an error when something went wrong,
    //    and just return a result when everything went fine.
    //
    // With those two premises in mind, we can safely assume that right after
    // `fn` has been invoked, we can store the SSH key passphrase for this git
    // operation if there was one pending to be stored.
    try {
      return await fn({
        DESKTOP_PORT: await trampolineServer.getPort(),
        DESKTOP_TRAMPOLINE_TOKEN: token,
        GIT_ASKPASS: '',
        // This warrants some explanation. We're configuring the
        // credential helper using environment variables rather than
        // arguments (i.e. -c credential.helper=) because we want commands
        // invoked by filters (i.e. Git LFS) to be able to pick up our
        // configuration. Arguments passed to git commands are not passed
        // down to filters.
        //
        // We're using the undocumented GIT_CONFIG_PARAMETERS environment
        // variable over the documented GIT_CONFIG_{COUNT,KEY,VALUE} due
        // to an apparent bug either in a Windows Python runtime
        // dependency or in a Python project commonly used to manage hooks
        // which isn't able to handle the blank environment variables we
        // need when using GIT_CONFIG_*.
        //
        // See https://github.com/desktop/desktop/issues/18945
        // See https://github.com/git/git/blob/ed155187b429a/config.c#L664
        GIT_CONFIG_PARAMETERS: `${gitEnvConfigPrefix}'credential.helper=' 'credential.helper=desktop'`,

        GIT_USER_AGENT: await GitUserAgent(),
        ...sshEnv,
      })

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
