### Title
Cached FROST preprocess seed is deterministically reused across `share` and `complete`, leaking the signer's secret share when inputs differ - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the FFmpeg `vf_hqdn3d` bug — where a buffer sized once from an initial frame is later written to by a larger frame — Serai's coordinator caches a FROST preprocess *seed* once under a `context` key and re-derives identical signing nonces every time `share_internal` is invoked with that context. A `sign` executed over attacker-influenced preprocesses/message bytes that differ from an earlier invocation reuses the same nonce pair `(d, e)`, enabling algebraic recovery of the secret key share.

### Finding Description
`SigningProtocol::preprocess_internal` derives a one-shot preprocess by storing a `CachedPreprocess` (a 32-byte RNG seed) in `CachedPreprocesses`, keyed solely on `context` (e.g. `(b"DkgConfirmer", attempt)`). On every call it loads the cached seed and calls `AlgorithmSignMachine::from_cache`, which routes to `seeded_preprocess`, re-seeding `ChaCha20Rng` with the same 32 bytes and regenerating the *identical* nonce pair via `Commitments::new::<_>(&mut rng, ...)` and the identical addendum RNG stream. [1](#0-0) [2](#0-1) 

`share_internal` calls `preprocess_internal().0` to build a fresh `AlgorithmSignMachine` each time it runs, then signs a caller-supplied `serialized_preprocesses` map and message. [3](#0-2)  Crucially, `DkgConfirmer::complete` calls `share_internal` *again* (after `share` may already have run), with the same context but with `preprocesses` and `key_pair` that are supplied per-call and can differ between invocations. [4](#0-3) 

The result is two FROST signature shares `z = d + (e · rho_l) + lambda · s · c` produced with *identical* nonces `d, e` but different binding factors `rho` (rho is transcripted over the submitted commitments, which the submitting party controls) and/or a different challenge `c` (transcripted over the message and group key/offset). Two such shares yield a linear system in the three unknowns `d`, `e`, `s` (secret share), directly recoverable. This matches the documented hazard that reuse of a cached preprocess "will enable third-party recovery of your private key share" — but here the reuse is performed *internally* by `share_internal`/`complete` rather than by integrator error. [5](#0-4) [6](#0-5) 

### Impact Explanation
Recovery of a validator's FROST secret share `s` collapses the threshold scheme for that participant: combined with any `t-1` other shares (or used to forge the victim's share in a rogue session), it enables signature forgery / unauthorized signing under the validator set's group key — the "key share recovery / signing of an unintended message" acceptance criterion. In FFmpeg terms: the cache allocates fixed "dimensions" (nonce seed) at first use and is then written against adversarially resized inputs (different preprocess sets / messages) on subsequent passes.

### Likelihood Explanation
High wherever `share` and `complete` (or repeated `share` retries under the same `attempt`) run with different preprocess maps or `key_pair` values. The preprocess bytes are read through `read_preprocess` from validator-supplied serialized data, so a party able to submit different preprocess sets across the two calls — or a coordinator retry path where the set membership changed — triggers distinct `rho`/challenge values. The seed reuse itself is guaranteed by the get-or-set cache logic; no race is needed.

### Recommendation
Bind the cached preprocess to a single use: delete/rotate `CachedPreprocesses` after the first `sign` consumes it, and/or mix a per-consumption nonce derivation (e.g., transcript of the exact preprocess set + msg) into the seed so differing inputs cannot produce identical nonces. At minimum, `complete` must reuse the share computed by `share` rather than re-invoking `share_internal`.

### Proof of Concept
Within `DkgConfirmer`: call `share(preprocesses_A, key_pair_A)` → internally `preprocess_internal` loads seed `S`, signs, emits `z1 = d + e·rho1 + λ·s·c1`. Then call `complete(preprocesses_B, key_pair_B, shares)` → `share_internal` reloads the same `S`, regenerates identical `d, e`, and emits `z2 = d + e·rho2 + λ·s·c2` with `rho2 ≠ rho1` and/or `c2 ≠ c1`. Solving the two-share linear system recovers `d`, `e`, and `λ·s`, hence the secret share `s`.

Caveat: I could not fully trace the coordinator call sites that feed `share`/`complete` to confirm an unprivileged party can inject distinct preprocess sets between them; if upstream code pins both calls to identical inputs, exploitability drops to coordinator-level retry/membership-change scenarios rather than a purely external attacker.

    msg: &[u8],

    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();

      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
