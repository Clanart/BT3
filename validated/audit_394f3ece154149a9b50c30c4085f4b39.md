### Title
Partial-commit staging trusts a stale line-selection index against a freshly re-read working-tree diff, silently corrupting what the user commits - ([File: app/src/lib/git/apply.ts])

### Summary
`applyPatchToIndex()` builds the patch that is `git apply --cached`-ed into the index by combining the user's saved `file.selection` (a set of line indices chosen against the diff the UI rendered) with a *freshly re-fetched* diff obtained by calling `getWorkingDirectoryDiff(repository, file)` at commit time. [1](#0-0) 
If the file on disk changes between the moment the user made their line-level selection in the UI and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs, `file.selection.isSelected(absoluteIndex)` is evaluated against hunk offsets from the *new* diff while the selection bitmap was computed against the *old* one — the same class of bug as the Pendle report: a value (the selection state) is trusted as still valid against a target that has since moved (the SY exchange rate / here, the diff hunks), with no revalidation before the trusted action (redeem / here, `git apply`) is taken.

### Finding Description
The GitHub Desktop partial-commit flow works as follows:
1. The UI renders a diff and lets the user pick individual lines/hunks, storing selections as absolute line indices in `DiffSelection` (`app/src/models/diff/diff-selection.ts`).
2. When the user commits, `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) is invoked with the `WorkingDirectoryFileChange[]` carrying those selections. [2](#0-1) 
3. For any file with a partial selection, `applyPatchToIndex` is called. Crucially, it does **not** reuse the diff the UI already had — it calls `getWorkingDirectoryDiff(repository, file)` again, right before formatting the patch: [3](#0-2) 
4. `formatPatch(file, diff)` (`app/src/lib/patch-formatter.ts:129-232`) walks the *new* diff's hunks and calls `file.selection.isSelected(absoluteIndex)` for each line, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` is computed from the **new** hunk layout. [4](#0-3) 

There is no check anywhere in `applyPatchToIndex`, `stageFiles`, or `createCommit` that the diff used to build the selection is the same diff being used to build the patch (no hash/line-count/mtime comparison). If the working-tree file is modified between selection time and commit time — e.g. by an editor autosave, a background formatter/linter, a file watcher, or (most attacker-relevant) a `smudge`/`clean` filter or a hook triggered by an unrelated git operation on the same repo — the hunk boundaries shift. Because `absoluteIndex` is a flat, hunk-relative position (not tied to a stable line-content anchor), the same numeric index can now point at an entirely different line of an entirely different hunk. `formatPatch` will silently mark unintended lines as "selected" (staged) or drop intended ones, and `git apply --cached` will apply that content into the index without any error, since the patch it receives is syntactically well-formed. The bug is silent: no error surfaces, the user sees a normal commit succeed, but the actual staged content differs from what they reviewed and clicked "commit" on.

This mirrors the Pendle finding precisely: the "priced" value (line selection) is not re-validated against the actual redemption/target (current diff), so the system silently accepts a worse outcome than the user was shown, and none of the existing guards (patch emptiness check at `patch-formatter.ts:224-227`, `assertNever` exhaustiveness checks) detect a mismatch between the *displayed* diff and the *applied* diff — they only guard against internal inconsistency of a single diff, not staleness across two.

### Impact Explanation
This is a silent corruption of what the user commits — one of the explicitly in-scope impact categories. A user could believe they are staging/committing only reviewed, intended lines, while the tool actually stages different content (including lines the user explicitly excluded, e.g. secrets, debug code, or partially-reverted edits), because the index update is driven by a diff computed after the file changed underneath the recorded selection. In adversarial contexts (e.g. a cloned repository with a `.gitattributes` `clean`/`smudge` filter, or a build/watch process the user has running against the same working tree), an attacker who can trigger working-tree mutation between the diff render and the commit action can cause the victim to commit and potentially push content they never selected, without any error or warning from Desktop.

### Likelihood Explanation
The window between diff-render/selection and commit execution is not vanishingly small in a real UI: staging happens through async operations (`getStatusOrThrow`, `refreshChangesSection`, hook callbacks) between selection and the eventual `_commitIncludedChanges` call, and any file watcher, IDE autosave, linter-on-save, or `smudge` filter running in the same working directory can race this window. No additional privileges are required; only the ability to modify a tracked file at an opportune moment (a capability an attacker-controlled filter/hook already gets from a malicious clone). It requires no local/physical access beyond what's already normal Desktop usage, and no admin rights.

### Recommendation
Bind the `DiffSelection` to the specific diff it was computed against (e.g. a content hash or the diff's raw text/hunks) and re-validate at commit time in `applyPatchToIndex`/`stageFiles`: if the freshly fetched diff for a file doesn't match the diff the selection was created from, refuse the partial commit for that file and prompt the user to re-review it, rather than silently reinterpreting stale line indices against new hunk boundaries.

### Proof of Concept
1. Open a modified file in Desktop's Changes view; it renders a diff with hunk A (lines 10-15) and hunk B (lines 40-45).
2. Select only a line inside hunk B for partial commit (deselect hunk A). This selection is stored as an absolute index, e.g. index 42.
3. Before the user finalizes the commit (during the async window between UI selection and `_commitIncludedChanges` execution), a background process (editor autosave / lint-on-save / a filter driven hook) rewrites the file so that hunk A grows, shifting hunk B's `unifiedDiffStart` such that the *new* absolute index 42 now falls inside what used to be hunk A.
4. `applyPatchToIndex` calls `getWorkingDirectoryDiff` and gets this new diff; `formatPatch` evaluates `file.selection.isSelected(42)` against the new hunk layout and stages a hunk-A line the user never selected (and may skip the hunk-B line they actually chose).
5. `git commit` succeeds with no error; `git show <sha>` reveals content the user never explicitly reviewed/selected in the UI at commit time. [1](#0-0) [4](#0-3)

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
