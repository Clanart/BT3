### Title
Strict-Greater-Than Work Invariant Violated in Bridge Circuit: Operator with Equal Work Passes Proof Verification - (File: `circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The `bridge_circuit` function in `circuits-lib/src/bridge_circuit/mod.rs` uses a strict `<` comparison to guard the operator's total-work claim against the maximum watchtower work. The protocol invariant — stated explicitly in both the documentation and the circuit's own comment — requires the operator's work to be **strictly greater than** the watchtower's maximum work. The `<`-only guard allows an operator whose chain has **equal** truncated 128-bit work to pass the circuit, violating the canonical-chain safety invariant and enabling reimbursement for a payout made on a non-canonical fork.

### Finding Description

In `bridge_circuit()`, the operator's HCP total work (lower 128 bits of the 256-bit `ChainState.total_work`) is compared against `max_total_work` returned by `total_work_and_watchtower_flags`:

```rust
// circuits-lib/src/bridge_circuit/mod.rs, lines 151-160
let total_work: TotalWork = input.hcp.chain_state.total_work[16..32]
    .try_into()
    .expect("Cannot fail");

// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

The guard panics only when `total_work < max_total_work`. When `total_work == max_total_work`, execution continues and the proof is accepted.

The protocol documentation is unambiguous:

> "Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers." [2](#0-1) 

The `TotalWork` struct derives `PartialOrd` over `[u8; 16]`, giving lexicographic (big-endian) comparison, which is correct. The values being compared are both the lower 128 bits of the 256-bit work: the operator's from `chain_state.total_work[16..32]` and the watchtower's from `work_conversion` in the work-only circuit, which explicitly truncates to the lower 128 bits:

```rust
// circuits-lib/src/work_only/mod.rs, lines 111-113
fn work_conversion(work: U256) -> [u8; 16] {
    let (_, work): (U128, U128) = work.into();
    work.to_be_bytes()
}
``` [3](#0-2) 

`TotalWork` is defined as:

```rust
#[derive(Debug, Clone, Copy, PartialEq, PartialOrd, Eq, BorshDeserialize, BorshSerialize)]
pub struct TotalWork(pub [u8; 16]);
``` [4](#0-3) 

### Impact Explanation

The bridge circuit is the core proof that an operator uses to justify reimbursement after fronting a withdrawal. If the circuit accepts a proof where the operator's chain work equals the watchtower's chain work, the operator can be reimbursed for a payout made on a fork that is not definitively canonical. Two chains with equal total work are tied under Bitcoin's heaviest-chain rule — neither is provably canonical. The protocol's "strictly greater" requirement exists precisely to exclude this ambiguous case.

Additionally, because both sides compare only the **lower 128 bits** of the 256-bit total work (upper bits are discarded by `work_conversion`), two chains with different full 256-bit work can collide in the truncated 128-bit space, making the equal-work scenario more reachable than it appears. On regtest (where all blocks carry minimum work), every block adds the same `MINIMUM_WORK` increment, making equal-work chains trivially constructible. [5](#0-4) 

If exploited, the operator receives a `Reimburse` transaction payout for a withdrawal that was processed on a non-canonical fork, constituting theft of bridge-controlled BTC collateral.

### Likelihood Explanation

On mainnet and testnet4, two independent chains reaching exactly the same lower-128-bit truncated work by chance is extremely unlikely. However:

1. On **regtest** (used for testing and potentially staging), all blocks add identical minimum work, making equal-work chains trivially constructible.
2. The truncation to 128 bits increases collision probability compared to the full 256-bit work.
3. An operator who controls when they submit their HCP can choose a chain tip whose truncated work matches a watchtower's submitted work, if such a tip exists in the chain history.

### Recommendation

Change the comparison from strict-less-than to less-than-or-equal, so the circuit panics whenever the operator's work does not **strictly exceed** the watchtower's maximum work:

```rust
// Before (incorrect):
if total_work < max_total_work {

// After (correct):
if total_work <= max_total_work {
```

This enforces the documented invariant that the operator must prove a chain with **strictly more** cumulative work than any valid watchtower challenge. [6](#0-5) 

### Proof of Concept

1. A watchtower submits a valid watchtower challenge transaction containing a Groth16 Work-Only Proof (WOP) for a chain with truncated 128-bit total work value `W`.
2. `total_work_and_watchtower_flags` verifies the Groth16 proof and returns `max_total_work = TotalWork(W)`.
3. The operator constructs an HCP for a chain whose `chain_state.total_work[16..32]` also equals `W` (a fork of equal work, or on regtest, any chain of the same block count with minimum-difficulty blocks).
4. The circuit evaluates `total_work < max_total_work` → `W < W` → `false` → no panic.
5. The circuit proceeds through SPV, LCP, and storage proof verification and commits a valid journal hash.
6. The operator uses this accepted proof to claim reimbursement via the `Reimburse` transaction for a payout made on a non-canonical chain, extracting bridge-controlled BTC.
