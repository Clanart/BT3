### Title
Silent origin remote hijack via unvalidated GitHub API `clone_url` - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` automatically rewrites a repository's `origin` remote URL whenever the GitHub API's reported `clone_url` for the associated repository differs from the current remote, without validating that the new URL still points at the same host/owner/repo identity that the user originally trusted. [1](#0-0) 

### Finding Description
The guard logic only checks two things before calling `gitStore.setRemoteURL(...)`:
1. `protocolsMatch` — that the URL *scheme* (`https:` vs the SSH pseudo-URL) hasn't changed. [2](#0-1) 
2. `remoteUrlUnchanged` — that the *current* origin URL still matches the previously cached `gitHubRepository.cloneURL` (i.e., the user hasn't manually repointed origin). [3](#0-2) 

Neither check constrains the **new** `apiRepo.clone_url` to the same hostname/owner as before — it only requires `!urlsMatch` (i.e., that it's different from the current remote), which is the exact condition needed to detect a legitimate rename. `urlMatchesRemote` in `app/src/lib/repository-matching.ts` does compare hostname/owner/name, but it is only used to detect "no change" or "manual override," never to validate that the *replacement* URL is still on a trusted host. [4](#0-3) 

`apiRepo` is the `IAPIRepository`/`IAPIFullRepository` object returned from a `GET` to the account's API endpoint (dotcom or a user-configured GitHub Enterprise Server). If that response is attacker-influenced — e.g., a compromised/malicious GHES instance the user has added as an account, or a network-level tamperer able to forge/modify the JSON response for that endpoint — an arbitrary `clone_url` (any host, any owner) satisfies both guards as long as the scheme string matches (e.g., `https://` → `https://attacker.example/foo/bar.git`) and the origin hasn't been manually edited by the user. `updateRemoteUrl` then calls `gitStore.setRemoteURL`, which shells out to `git remote set-url origin <url>` [5](#0-4) , silently repointing `origin` to the attacker's server with no user confirmation or diff/warning UI.

### Impact Explanation
Once `origin` is silently repointed:
- The next `fetch`/`pull` retrieves refs/objects from the attacker's server (`envForRemoteOperation` derives credential/auth context from the remote URL) [6](#0-5) , letting the attacker serve arbitrary commit history/content that the user then merges into their working tree — silent corruption of what the user believes they're pulling.
- The next `push` sends the user's local commits (potentially private/proprietary code) to the attacker-controlled host instead of the real repository [7](#0-6) , and if the user's git credential helper or Desktop prompts for fresh credentials for the new host, those credentials are typed directly into a prompt destined for the attacker's server — credential exfiltration.
- All of this happens with no interactive confirmation; the origin URL simply changes as a side effect of a background repository refresh.

### Likelihood Explanation
The precondition is that the GitHub API response for the tracked repository be attacker-controlled — plausible for users of self-hosted/compromised GitHub Enterprise Server instances, a MITM'd network path to the API endpoint, or an account whose token/session has been used against a malicious mirror endpoint. This fits the "attacker controls a GitHub API object" category. It requires no local access, no admin rights, and no unnatural user action — it fires automatically as part of Desktop's normal background repository/API refresh cycle. The test suite explicitly confirms and exercises this "auto-update on differing clone_url" behavior [8](#0-7) , showing the code path is real and reachable, not merely theoretical.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the new `clone_url`'s hostname matches an already-trusted endpoint (e.g., the account's configured API endpoint hostname) and, ideally, surface a non-silent confirmation to the user when the remote's host/owner is changing, rather than only gating on protocol-string equality and prior-URL equality.

### Proof of Concept
1. User has a repository tracked with `origin` pointing at `https://ghe.example.com/org/repo.git`, added via a GitHub Enterprise Server account.
2. The GHES instance (compromised, or MITM'd in transit) returns, for the repository details API call, `clone_url: "https://attacker.example.com/org/repo.git"`.
3. On the next background repository refresh, `updateRemoteUrl` is invoked: `protocolsMatch` is `true` (both `https:`), `remoteUrlUnchanged` is `true` (user never manually edited origin), and `urlsMatch` is `false` (different host) — all conditions to trigger the update are satisfied. [9](#0-8) 
4. `git remote set-url origin https://attacker.example.com/org/repo.git` executes silently. [5](#0-4) 
5. User's next `git push` (via Desktop's push UI) sends commits/credentials to `attacker.example.com`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
