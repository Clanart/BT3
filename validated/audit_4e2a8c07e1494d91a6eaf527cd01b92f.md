### Title
OP_RETURN data output is excluded from the transaction weight/vbyte calculation, producing an under-priced fee that can fall below relay minimum - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the referenced issue (missing sanity checks on transaction-construction parameters leading to an unintended, unfavorable signed transaction), `SignableTransaction::new` omits the OP_RETURN output created from `data` when measuring transaction weight. The resulting `needed_fee`/minimum-fee validation is computed against a smaller virtual size than the transaction that is actually built and signed, so the fee/change math the signature commits to does not match the real transaction size.

### Finding Description
In `SignableTransaction::new`, when `data` is `Some`, an OP_RETURN `TxOut` is appended to `tx_outs` (lines 194-202). However, both calls to `calculate_weight_vbytes` pass only `payments` and `change` — the data output is never included: [1](#0-0) [2](#0-1) 

`calculate_weight_vbytes` builds a template `Transaction` from `inputs`, `payments`, and an optional `change` script, then calls `tx.weight()` — so every OP_RETURN byte (up to 80 bytes of data plus script/output overhead, i.e. ~90+ vbytes since output bytes are non-witness) is invisible to both `needed_fee` and `fee_with_change`: [3](#0-2) 

Consequences:

1. The `TooLowFee` check at lines 206-213 compares `fee_per_vbyte * vbytes` (computed without the data output) against the relay minimum times the same wrong `vbytes`. For a minimal `fee_per_vbyte`, the *actual* feerate of the signed transaction is `fee_with_change / (vbytes + ~90)`, which can be below `DEFAULT_MIN_RELAY_TX_FEE` while the check still passes — the threshold check validates against a transaction that is not the one being signed. [4](#0-3) 

2. When `change` is specified, the change amount is `input_sat - payment_sat - fee_with_change` (lines 228-230). Since `fee_with_change` is underestimated, the change output is inflated and the transaction's real feerate is lower than the caller-requested `fee_per_vbyte`. The signers then commit (via the taproot sighash over `Prevouts::All`, lines 373-390) to a transaction whose economics differ from what was specified — exactly the class of "value validated against stale/wrong parameters, unintended outcome signed" from the source report. [5](#0-4) [6](#0-5) 

Note the weight check at line 241 also misses the OP_RETURN output's weight, marginally weakening the `TooLargeTransaction` bound (sub-standardweight edge only, ~360 WU, not independently significant).

### Impact Explanation
- A signed transaction paying a real feerate below the requested `fee_per_vbyte` — and, in the worst case, below the network's minimum relay feerate despite `TooLowFee` passing. Such a transaction will not propagate or confirm, yet `Prevouts::All` signatures were already produced, leaving funds frozen until a replacement is signed.
- `needed_fee()` and `fee()` report inconsistent economics: the caller believes the fee equals `fee_per_vbyte * vsize`, but the actual vsize is larger, so the realized feerate is strictly less than intended and the change output is correspondingly larger.
- In the processor integration (`processor/src/networks/bitcoin.rs:417-472`), `make_signable_transaction` relies on this fee computation to satisfy plans; a systematically under-priced transaction means eventualities may never be fulfilled and the `Err(TransactionError::TooLowFee) => panic!` arm encodes an assumption this bug violates.

### Likelihood Explanation
Reachable whenever `SignableTransaction::new` is called with `data: Some(_)` and `fee_per_vbyte` near the relay minimum — deterministic arithmetic error, not probabilistic. In the wallet library the caller controls `data`, `payments`, and `fee_per_vbyte` directly. Severity is Medium rather than High because funds are not directly stolen; the impact is a mis-priced/unbroadcastable signed transaction and fee-to-change misallocation, requiring a fee bump or re-signing.

### Recommendation
Include the OP_RETURN output in the weight estimation. Pass the already-constructed `tx_outs` (or append a `data` parameter) to `calculate_weight_vbytes` so both the no-change and with-change measurements reflect the final transaction:

```rust
fn calculate_weight_vbytes(
  inputs: usize,
  tx_outs: &[TxOut],        // include OP_RETURN output
  change: Option<&ScriptBuf>,
) -> (u64, u64) { ... }
```

Then the `TooLowFee` check and `fee_with_change` derivation validate the actual signed bytes, matching the invariant that `needed_fee` corresponds to the real vsize.

### Proof of Concept
```rust
// inputs worth 100_000 sats, one 10_000-sat payment, 80-byte OP_RETURN data,
// change script, fee_per_vbyte chosen minimally
let tx = SignableTransaction::new(
  inputs,
  &[(payment_script, 10_000)],
  Some(change_script),
  Some(vec![0u8; 80]),
  FEE,
).unwrap();

// Actual vsize of tx.transaction() exceeds the vbytes used internally by
// ~90+ bytes (output base + OP_RETURN script). Consequently:
assert!(tx.needed_fee() < FEE * real_vsize);
// real feerate = tx.fee() / real_vsize < FEE, and for minimal FEE can be
// < DEFAULT_MIN_RELAY_TX_FEE while TooLowFee was not returned.
```

```rust
  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }

    let weight = tx.weight();
```
