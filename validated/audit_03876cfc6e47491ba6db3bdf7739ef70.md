### Title
Reused deterministic FROST nonces when `share`/`complete` is re-executed under the same `CachedPreprocesses` context — validator Ristretto secret key recoverable - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
Analogous to the Reserve finding — where `furnace.melt()` was bundled inside a "refresh only if not already refreshed" branch so a prior external `refresh()` call skipped a required state update — `SigningProtocol::preprocess_internal` bundles **nonce generation** inside a "generate only if nothing is cached" branch. Once a `CachedPreprocesses` entry exists for a `(b"DkgConfirmer", attempt)` context, every subsequent call to `share`/`complete` re-derives the *identical* FROST nonces `(d, e)` from the same ChaCha20 seed, while the binding factors `rho`, Lagrange coefficients `lambda`, and message `c` are recomputed from whatever preprocess map the caller supplies. An unprivileged tributary participant who can get multiple distinct preprocess sets finalized (or trigger `complete` with a different set than `share` used) obtains multiple signature shares under the same nonce pair — linear equations that recover the validator's MuSig secret key.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmMachine::seeded_preprocess` derives both FROST nonces deterministically: `Commitments::new(&mut ChaCha20Rng::from_seed(*seed.0), ...)`. The resulting `AlgorithmSignMachine` carries `nonces` and `seed`; `from_cache` rebuilds the identical machine from the identical seed (`crypto/frost/src/sign.rs:121-145, 268-274`).

`sign` consumes `self.nonces` via `drain(..)` and computes the share as `d + e*rho_i + lambda_i * s * c` where `rho_i` comes from `BindingFactor::calculate_binding_factors` over a transcript of the **entire preprocess set** plus `hash_msg(msg)` (`crypto/frost/src/sign.rs:362-398`).

In `coordinator/src/tributary/signing_protocol.rs`, the cache key is `context = (b"DkgConfirmer", self.attempt)` — i.e., fixed for the whole DKG-confirmation attempt (`signing_protocol.rs:274-277`). The critical block is `signing_protocol.rs:123-145`:

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
    let (machine, _) = AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
    ... // XOR-encrypt seed, store
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
let (machine, preprocess) = AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

This is the exact shape of the Reserve bug: the "refresh" (`assetRegistry.refresh()` ↔ cached-seed existence check) gates a *distinct, mandatory* state update (`furnace.melt()` ↔ **fresh nonce generation**). Because the check passes on the second call, the nonce-update step is silently skipped and a stale value is used.

The nonces are then re-signed with at least twice per confirmation:

- `DkgConfirmer::share` → `share_internal` → `preprocess_internal` + `sign` (`signing_protocol.rs:288-310`)
- `DkgConfirmer::complete` → `share_internal` **again** → `preprocess_internal` + `sign`, this time with the preprocess map supplied at *completion* time (`signing_protocol.rs:312-327`)

Both maps are built from tributary-finalized (but participant-supplied) preprocess bytes via `threshold_i_map_to_keys_and_musig_i_map` (`signing_protocol.rs:208-250`). The file's own safety argument (lines 29-54) relies **only** on BFT ordering making the received messages identical — it does not argue the preprocess *set* is identical. Nothing prevents the set of preprocesses seen at `share` time from differing from the set at `complete` time (different included participants, or a participant whose bytes were rejected in round one being re-finalized differently, or a coordinator reboot/retry between rounds). Each such variation changes `rho` and `lambda` while `d, e` stay fixed.

### Impact Explanation
Each published/used share is `share_i = d + e·rho_i + lambda_i·s·c_i` with attacker-observable `rho_i` (recomputable — the transcript inputs are public), `lambda_i`, `c_i`, and unknowns `{d, e, s}` (3 scalars). Every additional signing pass under the same `(DkgConfirmer, attempt)` context contributes one independent linear equation. Three passes with distinct preprocess sets/`included` lists suffice to solve for `s` — the validator's Ristretto secret key for the MuSig DKG-confirmation protocol — by plain Gaussian elimination. The shares from `share` are broadcast on the tributary, so the attacker collects equations passively and can also actively induce variations by submitting preprocesses keyed under their own `Participant`.

Compromise of this key lets the attacker forge the validator's contribution to the on-chain DKG-confirmation MuSig — the mechanism that ratifies threshold keys controlling all bridged funds — and defeats the "removed validator" accounting, since `removed_as_of_dkg_attempt` is per-attempt and the same key signs across all variations within that attempt.

### Likelihood Explanation
Medium. Exploitation requires the same coordinator to execute `share_internal` ≥3 times under one attempt with varying preprocess sets — achievable through ordinary re-execution paths the code explicitly supports: `share` failing with `FrostError::InvalidPreprocess(p)`/`InvalidShare(p)` and being retried (`signing_protocol.rs:170-178` maps these to a blamed participant rather than aborting the attempt), `complete` re-running `share_internal` unconditionally, reboots, and preprocess sets that grow as more validators' messages finalize. An unprivileged participant controls their own preprocess bytes and their timing, directly influencing `rho` diversity. The determinism of the reuse is guaranteed by the code path — the only question is input variation, which the file itself flags as unreviewed (`TODO`, lines 53-54).

### Recommendation
Do not reuse a cached preprocess across distinct `sign` invocations. Concretely:

- Bind the cache key to the *full signing instance*, not the attempt: e.g., key `CachedPreprocesses` by `(context, hash(sorted participant set ‖ their preprocess bytes ‖ msg))`, and refuse to sign if a different instance under the same context is requested.
- Better: make `share` single-use — after a successful `sign`, store `Signed(context)` and return the *previously computed share* (or an error) on any re-invocation rather than recomputing with recycled nonces. `complete` should reuse the share computed by `share`, not regenerate it via `share_internal`.
- Independently, implement the file's own TODO: verify the on-chain commitments match the presumed preprocess before publishing shares, which removes the "distinct messages under BFT" assumption the current safety argument leans on.

### Proof of Concept
Sketch against `DkgConfirmer` (a participating validator or any party who can observe published shares and submit preprocesses):

1. Attempt `a` begins; coordinator caches seed under `("DkgConfirmer", a)` and publishes `preprocess` with nonce commitments `(D, E)` fixed for the whole attempt.
2. Round 1: preprocess set `P1 = {p1, p2, …}` finalizes. `share(P1, kp)` emits `s1 = d + e·rho1 + λ1·s·c`. All `rho1, λ1, c` are publicly recomputable from `P1` and `set_keys_message`.
3. Round 2: the attacker submits their own preprocess `p_att'` (distinct bytes → `InvalidPreprocess` retry path, or simply finalized in a later tributary block), giving set `P2 = P1 ∪ {p_att'}` or with the attacker index's bytes changed. `complete(P2, kp, shares)` re-runs `share_internal` → same `(d, e)`, new `rho2, λ2`. If a second `share` is emitted (retry), `s2` is public; even `s1`-vs-`s2` alone with identical `msg` gives `s1 − s2 = e(rho1 − rho2) + s(λ1c − λ2c)` — one equation.
4. Repeat once more (`P3`, e.g., post-reboot re-execution with a third distinct set) → 3 equations in `d, e, s` → solve for `s`, the validator's `Zeroizing<<Ristretto as Ciphersuite>::F>` MuSig key.

Uncertainty note: the exact call multiplicity of `share` vs `complete` per attempt in `coordinator/src/tributary/handle.rs` was not fully traced (tool budget exhausted); the PoC relies on the retry/`complete`-re-executes-`share_internal` paths visible in `signing_protocol.rs` itself, which guarantee at least two nonce-consuming evaluations per confirmation.
