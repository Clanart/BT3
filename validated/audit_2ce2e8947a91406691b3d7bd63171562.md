## Analysis

This maps to a concrete analog in Kaia's on-chain governance for the KIP-71 dynamic fee parameters `kip71.lowerboundbasefee` and `kip71.upperboundbasefee`, which are interdependent exactly like `lotSize`/`tradingLotSize` in the M09 report, and which are updated via separate, non-atomic governance votes.

### Title
Non-atomic governance updates to `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` allow ratification of an inverted fee band (lower > upper) - ([File: kaiax/gov/headergov/impl/header.go])

### Summary
`kip71.lowerboundbasefee` and `kip71.upperboundbasefee` are two dependent governance parameters that must satisfy `lower <= upper` for the KIP-71 (Magma) dynamic base-fee formula to behave correctly. The header-governance module validates each vote against the *currently effective* `ParamSet`, not against other votes pending ratification in the same epoch, so the pair can be updated to a mutually inconsistent, invalid state at the epoch boundary, exactly the class of bug described in the M09 report (`tradingLotSize`/`lotSize` non-atomicity).

### Finding Description
Each vote for `Kip71LowerBoundBaseFee` or `Kip71UpperBoundBaseFee` is checked in `checkConsistency` against `h.GetParamSet(blockNum)`, i.e., the parameter set *currently effective for the epoch*, not the value that will actually be ratified from any other vote already cast earlier in the same epoch: [1](#0-0) 

Because ratified votes only take effect at the *next* epoch boundary (`Parameter change ratified at k*epoch block takes effect starting from (k+1)*epoch block`), both a lower-bound vote and an upper-bound vote cast within the same epoch are checked against the same stale, pre-epoch values: [2](#0-1) 

This allows the following non-atomic sequence within a single epoch (in `single` governance mode, which Mainnet/Kairos use):
1. Governing node casts `Kip71UpperBoundBaseFee = 30e9`. Check: `30e9 >= currentLowerBound(25e9)` → passes (current, not-yet-updated `UpperBoundBaseFee` is irrelevant to this check).
2. Same governing node casts `Kip71LowerBoundBaseFee = 500e9`. Check: `500e9 <= currentUpperBoundBaseFee` — but `currentUpperBoundBaseFee` is still the *old* pre-vote value (e.g., `750e9`), not the pending `30e9` from step 1 — so it also passes.
3. At the epoch boundary, both votes are ratified verbatim (`VerifyGov`/`getExpectedGovernance` only check that the ratified JSON matches the votes cast, with no cross-parameter consistency re-check): [3](#0-2) [4](#0-3) 

The result is a ratified `ParamSet` where `LowerBoundBaseFee (500e9) > UpperBoundBaseFee (30e9)`, an inverted band that was never checked as a pair.

### Impact Explanation
This inverted param set is fed directly into the KIP-71 base-fee calculation used for every block/transaction, via `ToKip71Config()`/`GetParamSet` and `NextMagmaBlockBaseFee`: [5](#0-4) 

With `lowerBound > upperBound`, the clamp logic (`if parentBaseFee >= upperBoundBaseFee { parentBaseFee = upperBoundBaseFee } else if parentBaseFee <= lowerBoundBaseFee { parentBaseFee = lowerBoundBaseFee }`) can force the effective base fee to the (now much lower) `upperBoundBaseFee` even though governance intended a much higher floor (`lowerBoundBaseFee`). This breaks the fee-floor guarantee that KIP-71 is designed to enforce network-wide, letting all subsequent transactions be processed and included at an unintended, abnormally low base fee — a fee-mechanism integrity failure reachable by any transaction sender once the inconsistent state is ratified, since it silently degrades the fee floor for the entire network rather than merely affecting the governing node.

### Likelihood Explanation
Reaching this state requires two governance votes in the same epoch by the entity authorized to vote (the governing node in `single` mode, or GC members in `none` mode) — no additional privilege beyond normal parameter voting rights is needed, and the check bypass is deterministic and always exploitable because it stems from the vote validation always referencing `GetParamSet(blockNum)` (fixed for the whole epoch) rather than tracking pending same-epoch votes.

### Recommendation
Validate `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` together atomically: `checkConsistency` should check each vote against the *pending* value of its counterpart (i.e., the last vote already cast within the current epoch, if any, in addition to the currently effective `ParamSet`), and/or `getExpectedGovernance`/`VerifyGov` should reject ratification of a governance set at the epoch boundary that would leave `LowerBoundBaseFee > UpperBoundBaseFee`.

### Proof of Concept
1. Node A is the `governance.governingnode` in `single` mode.
2. In epoch `k`, at block `b1`, Node A calls `governance_vote("kip71.upperboundbasefee", 30000000000)`. Since `checkConsistency` compares only against the current `LowerBoundBaseFee` (25e9), it passes.
3. At block `b2` (still epoch `k`), Node A calls `governance_vote("kip71.lowerboundbasefee", 500000000000)`. `checkConsistency` compares only against the current (stale) `UpperBoundBaseFee` (750e9), so it also passes.
4. At the epoch-boundary block `(k+1)*epoch`, both votes are ratified into `header.Governance` as `{lowerboundbasefee: 500e9, upperboundbasefee: 30e9}` with no cross-check.
5. From block `(k+1)*epoch + 1` onward, `GetParamSet` returns this inverted pair, and `NextMagmaBlockBaseFee` computes an effective base fee clamped to `30e9` regardless of the intended `500e9` floor, silently and network-wide undermining the configured fee floor.

// VerifyGov checks the following:
// (1) governance must be empty in non-epoch block,
// (2) if there are no votes in the previous epoch, governance must be empty,
// (3) if any vote exists in the previous epoch, governance must not be empty,
// (4) the json must not contain unknown fields,
// (5) the parsed json must exactly match the map derived locally from the previous epoch's votes.
func (h *headerGovModule) VerifyGov(header *types.Header) error {
	// (1)
	if header.Number.Uint64()%h.epoch != 0 {
		if len(header.Governance) > 0 {
			logger.Error("governance is not allowed in non-epoch block", "num", header.Number.Uint64())
			return ErrGovInNonEpochBlock
		} else {
			return nil
		}
	}

	// (2), (3)
	expected := h.getExpectedGovernance(header.Number.Uint64())
	if len(header.Governance) == 0 {
		if len(expected.Items()) != 0 {
			return ErrGovVerification
		}

		return nil
	}

	// (4)
	var gb headergov.GovBytes = header.Governance
	actual, err := gb.ToGovData()
	if err != nil {
		logger.Error("DeserializeHeaderGov error", "num", header.Number.Uint64(), "governance", gb, "err", err)
		return err
	}

	// (5)
	if !reflect.DeepEqual(expected, actual) {
		logger.Error("Governance mismatch", "expected", expected, "actual", actual)
		return ErrGovVerification
	}

	return nil
}

// The blockNum's epoch index must be greater than 0. That is, it must be blockNum >= epoch.
func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.

Parameter change ratified at `k*epoch` block takes effect starting from `(k+1)*epoch` block.
It is worth noting that the effective time of the ratification is `(k+1)*epoch + 1` before Kore.
