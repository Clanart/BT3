### Title
Payment amount overflow permits denial of service or signing invalid Bitcoin transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` calculates `payment_sat` with unchecked `u64` summation and then performs unchecked addition with `needed_fee`. Malformed payment instructions containing amounts whose sum exceeds `u64::MAX` can panic under overflow checks or wrap in release builds, bypassing the insufficient-funds check and producing an invalid transaction.

### Finding Description
All payment outputs are converted into `payment_sat` using `sum::<u64>()` without rejecting non-canonical Bitcoin amounts or using `checked_add`. [1](#0-0)  The subsequent solvency test evaluates `input_sat < (payment_sat + needed_fee)`, which can itself overflow. [2](#0-1)  If the arithmetic wraps in a release build, an input set far smaller than the requested outputs can pass validation, and the resulting `SignableTransaction` retains the attacker-controlled oversized outputs. [3](#0-2)  The transaction machine then signs each input’s Taproot sighash without rechecking output totals. [4](#0-3) 

### Impact Explanation
In builds with overflow checks, arithmetic overflow panics during transaction construction, causing a remote denial of service. In release builds using two’s-complement wrapping, Serai can construct and threshold-sign a Bitcoin transaction whose outputs exceed its inputs and are consensus-invalid. This can cause the signing flow to commit FROST signatures to an unintended, unspendable transaction plan.

### Likelihood Explanation
An unprivileged party that can influence requested payment amounts can supply two or more large `u64` values whose sum overflows. The only prior validation is a per-payment dust check, so values near `u64::MAX` are accepted. [5](#0-4)  Exploitation depends on whether the deployed build enables overflow checks: it produces a panic when enabled and a safety-check bypass when disabled.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`. Specifically, accumulate payments with `try_fold`/`checked_add`, cap each payment to Bitcoin’s maximum money range before creating `Amount`, calculate `payment_sat + needed_fee` with `checked_add`, and reject overflow as `TransactionError::NotEnoughFunds` or a new overflow-specific error. Apply equivalent checked accumulation to `input_sat` and `fee()`.

### Proof of Concept
```rust
use bitcoin::ScriptBuf;
use serai_bitcoin::wallet::{send::SignableTransaction, ReceivedOutput};

fn malicious_plan(input: ReceivedOutput) {
  let payments = [
    (ScriptBuf::new_op_return(&[]), u64::MAX),
    (ScriptBuf::new_op_return(&[]), 1),
  ];

  // With overflow checks: panics while summing or adding the fee.
  // Without overflow checks: payment_sat wraps to 0, the solvency check
  // compares input_sat against roughly `needed_fee`, and succeeds.
  let tx = SignableTransaction::new(
    vec![input],
    &payments,
    None,
    None,
    1,
  ).unwrap();

  // This object can then be converted into TransactionMachine and signed,
  // despite representing outputs greater than the input amount.
  let _ = tx;
}
```

The relevant bypass is that `payment_sat` for `[u64::MAX, 1]` wraps to `0`, after which `payment_sat + needed_fee` remains small enough for even a low-value input to satisfy the check.
