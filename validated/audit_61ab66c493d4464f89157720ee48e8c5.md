### Title
Malformed `ReceivedOutput` triggers unbounded Bitcoin consensus decode allocation - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts untrusted bytes and feeds the remainder directly into `TxOut::consensus_decode` and `OutPoint::consensus_decode` via `BufReader::with_capacity(0, r)`, without imposing any Serai-side length cap. [1](#0-0)  A compact-size length inside the embedded `TxOut` can therefore drive Bitcoin consensus deserialization into allocating/expecting an attacker-declared payload before the outpoint is even reached, matching the malformed-object crash/availability bug class.

### Finding Description
The parser first reads a canonical scalar with `Secp256k1::read_F`, then wraps the same reader in `BufReader::with_capacity(0, r)` and calls `TxOut::consensus_decode` followed by `OutPoint::consensus_decode`. [2](#0-1)  The zero-capacity `BufReader` is not a limiter; it only changes buffering, so consensus decoding still trusts the transaction-output encoding. Because `ReceivedOutput::read` is a public deserialization entry point for received-output data, attacker-controlled bytes can specify a syntactically valid prefix followed by an oversized `TxOut` script/amount encoding and cause excessive allocation or decode failure before bounds are enforced.

### Impact Explanation
An unprivileged party that can cause a node/processor to deserialize a `ReceivedOutput` can force resource exhaustion during parsing, crashing or stalling the decoding path before spendability logic runs. [1](#0-0)  This is an availability failure on untrusted input rather than a signature forgery.

### Likelihood Explanation
The trigger requires only control of serialized bytes passed to `ReceivedOutput::read`; the attacker does not need a valid key, signature, or spendable output. [3](#0-2)  The vulnerable surface is the explicit public `read` API listed for untrusted inputs.

### Recommendation
Do not hand an unbounded `Read` directly to Bitcoin consensus decoding inside `ReceivedOutput::read`. Bound the remaining serialized size before `TxOut::consensus_decode`, decode from a strictly length-limited slice, reject trailing bytes, and enforce a maximum `TxOut`/script size compatible with Bitcoin consensus policy before allocation.

### Proof of Concept
Input layout sent to `ReceivedOutput::read`:
```text
[offset: 32 canonical scalar bytes]
[TxOut: 8-byte value][script_pubkey compactsize claiming huge length]
[truncated or absent script bytes]
[OutPoint bytes never reached]
```
A canonical scalar followed by a `TxOut` whose `script_pubkey` compact-size field declares a very large vector causes `TxOut::consensus_decode` to attempt decoding/allocation for that claimed length, exhausting memory or failing only after attacker-controlled length is consumed. [4](#0-3)

  /// Read a ReceivedOutput from a generic satisfying Read.
  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
