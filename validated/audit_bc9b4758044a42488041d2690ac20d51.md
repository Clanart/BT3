### Title
Stale permissions/fork state reused across different underlying GitHub repositories sharing the same owner+name key - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
`RepositoriesStore._upsertGitHubRepository` looks up an "existing" `GitHubRepository` database row using only the composite key `[ownerID+name]` [2](#0-1) , and the unique Dexie index enforcing this is `&[ownerID+name]` [4](#0-3) . Nothing in this key involves GitHub's immutable numeric repository id — the model comment explicitly says the local `dbID` "is no relation to the API ID" [1](#0-0) . Because a GitHub owner/login can delete a repository and later recreate (or a name can be vacated and reclaimed under org name-squatting rules) a *different* repository under the identical `owner/name`, Desktop's upsert logic will silently treat it as the same row: it reuses the existing `dbID`, and explicitly falls back to the old cached `permissions` and `parentID` when the new API payload doesn't resolve them cleanly [3](#0-2) .

### Finding Description
This mirrors the Vader oracle bug: a security-relevant value (there, the price oracle; here, `permissions`/`parentID`/fork relationship) is bound to an under-specific composite key (`foreignAsset` there, `[ownerID+name]` here) instead of to the actual unique identity of the object (the specific pair, or here the immutable GitHub repository id). When a *new* logical repository is introduced that happens to reuse the same key, its data is silently merged with/derived from the prior entry's cached state rather than being treated as a fresh, independent object.

Concretely:
- `putOwner` resolves an `ownerID` purely from `endpoint+login` [5](#0-4) .
- `_upsertGitHubRepository` then finds "existingRepo" by `[ownerID+name]` only [2](#0-1) .
- The comment block acknowledges the design assumes name+owner is a stable proxy for the repository's identity, and explicitly preserves old `permissions`/`parentID` "until we're certain [they need] to be cleared" [3](#0-2) .
- The resulting `dbID` (local database id) is what all other subsystems key off of: PR store, commit-status cache, branch-protection caches (`branchProtectionSettingsFoundCache`, `protectionEnabledForBranchCache`), and mentionables cache all use this `dbID`/`ownerID+name`-derived identity as if it uniquely and durably identifies one GitHub repository [6](#0-5) .

### Impact Explanation
If a user's local clone is associated with `owner/name` and that name is later deleted/recreated on GitHub as a different repository (e.g. renamed away and then claimed by another actor, or an org repo deleted and re-created), Desktop's periodic refresh (`repositoryWithRefreshedGitHubRepository`) re-fetches by `owner/name` [7](#0-6)  and upserts using the same stale key, potentially carrying forward write permissions, fork/parent linkage, or private/public status that reflect the *old* repository, not the new one occupying that name. This can misinform push-permission checks (`hasWritePermission`) [8](#0-7) , branch-protection warnings, and which upstream a fork's PRs/commit-status/issue data are fetched from — i.e., corrupting the user's understanding of what they are committing to or reviewing.

### Likelihood Explanation
Requires a specific but realistic condition: repository deletion/recreation or org name-squatting under the same owner+name that a Desktop user already has locally cloned/tracked, combined with Desktop's background refresh re-associating by name. It does not require local/physical access, admin rights, or leaked credentials — only a GitHub-side rename/delete/recreate event which is normal, unprivileged GitHub behavior from the perspective of Desktop.

### Recommendation
Bind cached repository state (`permissions`, `parentID`, PR/commit-status/branch-protection caches) to GitHub's immutable numeric repository id rather than (or in addition to) `[ownerID+name]`. When upserting, detect a mismatch between the cached immutable id and the API's `id` field and treat it as an entirely new repository, invalidating all derived caches instead of merging state.

### Proof of Concept
1. Clone `owner/repo-a` (private, no write access) in Desktop; Desktop upserts a `GitHubRepository` row keyed `[ownerID, "repo-a"]` with `permissions: 'read'`.
2. On GitHub, `owner` deletes `repo-a` and creates a brand-new repository also named `repo-a` (different underlying id) to which the local user now has write access, or vice versa.
3. Desktop's background refresh (`repositoryWithRefreshedGitHubRepository`) calls `api.fetchRepository(owner, name)` and `upsertGitHubRepository`, which finds the "existingRepo" via `[ownerID+name]` and, depending on API response fields available at that moment (e.g. a transient failure resolving permissions), can retain the previous `permissions`/`parentID` value from step 1 rather than the new repository's actual state [9](#0-8) , since nothing compares the underlying immutable repository id before reusing the cached row.

  private async putOwner(
    endpoint: string,
    login: string,
    ownerType?: GitHubAccountType
  ): Promise<Owner> {
    const key = getOwnerKey(endpoint, login)
    const existingOwner = await this.db.owners.get({ key })
    let id

    // Since we look up the owner based on a key which is the product of the
    // lowercased endpoint and login we know that we've found our match but it's
    // possible that the case differs (i.e we found `usera` but the actual login
    // is `userA`). In that case we want to update our database to persist the
    // login with the proper case.
    if (
      existingOwner === undefined ||
      existingOwner.login !== login ||
      // This is added so that we update existing owners with an undefined type.
      (ownerType !== undefined && existingOwner.type !== ownerType)
    ) {
      id = existingOwner?.id
      const existingId = id !== undefined ? { id } : {}
      id = await this.db.owners.put({
        ...existingId,
        key,
        endpoint,
        login,
        type: ownerType,
      })
    } else {
      id = forceUnwrap('Missing owner id', existingOwner.id)
    }

    return new Owner(login, endpoint, id, ownerType ?? existingOwner?.type)

    // that it's because it's the parent repository of another repository and we

    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in

    //
    // Since going from having a parent to not having a parent is incredibly

    // with the same name or the parent getting deleted, etc) we assume that the
