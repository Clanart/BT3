### Title
`SignableTransaction` fee/weight estimation omits the OP_RETURN data output, underpaying the real fee rate and bypassing the standardness weight check - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying caller-supplied `data` to the transaction, but `calculate_weight_vbytes` is only ever invoked with `payments` — never with `tx_outs`. The data output is therefore excluded from both the `weight` used for the `MAX_STANDARD_TX_WEIGHT` check and the `vbytes` used to compute `needed_fee`, exactly the GMX pattern where `estimateExecuteWithdrawalGasLimit` omitted a component (swaps) that executes later.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` (lines 194–202), then estimates the transaction size at line 204:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62–127) builds a template `Transaction` whose outputs are derived solely from `payments` plus an optional `change`. The `data` output never appears in the template. The same omission occurs in the change path at lines 225–226. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206/227) is computed over a transaction up to ~93 bytes (~372 weight units) smaller than the one actually signed (`data` is capped at 80 bytes by the `TooMuchData` check, plus OP_RETURN script overhead and the 8-byte value field).
- The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 is evaluated on the understated weight, so a transaction that is actually non-standard can pass validation and be signed.

The real fee paid is `sum(inputs) - sum(outputs)` (`fee()`, lines 138–141), which equals the underestimated `needed_fee`, so the broadcast transaction achieves a strictly lower sat/vbyte rate than `fee_per_vbyte` requested.

### Impact Explanation
Two concrete harms, both reachable purely by supplying `data` bytes that end up inside a threshold-signed transaction:

1. **Underpaid fee**: the signed transaction pays `needed_fee` corresponding to a smaller vsize than reality, so its effective fee rate is below the caller-specified `fee_per_vbyte`. Under fee-market pressure the transaction can stall or fail to relay.
2. **Unbroadcastable signed transaction**: when the payment set is near the weight limit, adding an 80-byte OP_RETURN pushes the real weight past `MAX_STANDARD_TX_WEIGHT` while the check on the underestimated `weight` passes. The FROST threshold signature is then produced over a transaction the network will not accept — the coordination round is consumed for an invalid transaction.

### Likelihood Explanation
The flawed template is deterministic: any non-`None` `data` argument produces an underestimate proportional to the data length. The only mitigating factor is that the current in-repo consumer, `processor/src/networks/bitcoin.rs::make_signable_transaction`, passes `None` for `data` (line 450), so exploitation requires a caller that uses the documented `data` capability of this public wallet API. Within `networks/bitcoin` itself the path is fully implemented and untested for fee/weight correctness (tests only assert `TooMuchData`).

### Recommendation
Perform weight/vbyte estimation over the actual `tx_outs` vector (payments + OP_RETURN + change) rather than re-deriving outputs from `payments`. Concretely, refactor `calculate_weight_vbytes` to accept `&[TxOut]` (or build the final `tx` first and call `tx.weight()` on it), so the OP_RETURN output and any future output kinds are inherently accounted for in both `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept
```rust
// networks/bitcoin: construct with near-maximum data
let data = vec![0u8; 80]; // passes the <= 80 TooMuchData check
let st = SignableTransaction::new(inputs, &payments, None, Some(data), fee_per_vbyte).unwrap();

// The signed/serialized tx contains the OP_RETURN output, but:
let reported = st.needed_fee();              // fee_per_vbyte * vbytes WITHOUT the ~93-byte OP_RETURN
let actual_vsize = st.transaction().vsize(); // includes the OP_RETURN output
assert!(reported < actual_vsize as u64 * fee_per_vbyte); // effective feerate < fee_per_vbyte

// With enough payments, tx.weight() exceeds MAX_STANDARD_TX_WEIGHT while
// the internal `weight` (which omitted the data output) stayed below it,
// so TooLargeTransaction is never returned and an unrelayable TX is signed.
```
