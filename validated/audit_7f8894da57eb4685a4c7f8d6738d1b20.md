### Title
Unauthenticated panic via out-of-set Participant index in PedPoP blame handling - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
CVE-2024-21199 is a remotely-triggerable crash/hang (complete DoS) of a server by a network-reachable party. The analog in Serai is a remotely-triggerable panic in the PedPoP DKG blame path: `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with `Participant` values taken directly from an accusation (`sender`, `recipient`) without checking they belong to the DKG's participant set. An accusation naming a participant index that was never part of the protocol panics the process, aborting the validator/coordinator mid-BlameMachine evaluation.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender: Participant` and `recipient: Participant` plus an attacker-supplied `EncryptedMessage` and optional `EncryptionKeyProof` [1](#0-0) . `Participant` is any nonzero `u16`, while the DKG only has `n` participants, so the accusation can name indexes up to `u16::MAX` that were never registered.

Inside `blame_internal`, the call to `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` eagerly as an argument to `DLEqProof::verify` [2](#0-1) . `enc_keys` is only populated by `register` for participants actually in the protocol [3](#0-2) , so any `recipient` outside `1..=n` panics on the `HashMap` index (`index` panics on missing keys) whenever a `Some(proof)` is supplied.

Independently, after a successful decryption with a canonical share, `blame_internal` evaluates `self.commitments[&sender]` [4](#0-3) , which panics if `sender` is a `Participant` not in the DKG — no validation of `sender`/`recipient` against `params` exists anywhere in the blame path. Neither `blame` nor `blame_internal` returns `Result`, so there is no error path; the only outcome is a panic.

The same unchecked indexing exists on the encrypt side: `self.decryption.enc_keys[&participant]` in `Encryption::encrypt` [5](#0-4) , though that specific call site is guarded upstream by `validate_map`.

### Impact Explanation
A single DKG participant submitting an accusation (or a blame relayed to an `AdditionalBlameMachine`) with a `recipient` index outside the registered set, or a `sender` index outside the commitment set, crashes the evaluating process. In a validator/coordinator deployment this kills the node mid-epoch, halting DKG completion, multisig rotation, and any signing that depends on the resulting `ThresholdKeys` — matching the CVE's complete availability loss. No secret material is required and no signature/threshold assumption is broken; any party that can get an accusation message processed (a normal DKG participant channel message) triggers it.

### Likelihood Explanation
The trigger is a syntactically valid message: `Participant::new(k)` for any `k > n` is a legitimate `Participant`, and the accusing party can produce a `msg` with a valid PoP (`SchnorrSignature::sign` over a key they choose) plus a `Some(EncryptionKeyProof)` so the panic at `self.enc_keys[&decryptor]` is reached. Nothing in `blame`, `blame_internal`, `AdditionalBlameMachine::new`, or `decrypt_with_proof` bounds `sender`/`recipient` to the participant set. Likelihood depends only on whether the deployment routes blame accusations to this API, which is the documented purpose of `BlameMachine`/`AdditionalBlameMachine`.

### Recommendation
Validate `sender` and `recipient` against the known participant set at the top of `blame`/`blame_internal` (e.g., `enc_keys.contains_key` / `commitments.contains_key` checks, returning the accuser or an error), and replace `self.enc_keys[&decryptor]` / `self.commitments[&sender]` indexing with `get()` + graceful handling. Consider returning `Result<Participant, _>` so blame evaluation cannot panic.

```rust
// After DKG completes, hold a `BlameMachine` (or build an
// `AdditionalBlameMachine::new(context, 3, commitment_msgs)`).

// Attacker constructs an accusation naming a recipient that was never registered.
let bogus_recipient = Participant::new(7).unwrap(); // n = 3, so 7 is out-of-set
let sender = Participant::new(1).unwrap();

// Attacker crafts a syntactically valid EncryptedMessage with a valid PoP
// over a key they generated, plus a Some(EncryptionKeyProof) so the
// `enc_keys[&decryptor]` argument is evaluated.
let (msg, proof) = craft_valid_encrypted_message_and_proof(/* attacker key */);

// Inside decrypt_with_proof, the argument `self.enc_keys[&bogus_recipient]`
// is evaluated before DLEqProof::verify runs:
//   crypto/dkg/pedpop/src/encryption.rs:388
// => HashMap index on a missing key => panic!("key not found"), crashing
//    the process instead of returning DecryptionError.
blame_machine.blame(sender, bogus_recipient, msg, Some(proof));

// Variant 2: valid recipient, out-of-set sender with a canonically valid
// share that decrypts successfully => panic at
//   crypto/dkg/pedpop/src/lib.rs:599  `self.commitments[&sender]`
```

Note: I could not inspect the coordinator-side accusation dispatch (outside the in-scope crates) to confirm whether it pre-filters out-of-range participants; within the in-scope PedPoP library itself there is no bounds check on `sender`/`recipient`, and the library documents these APIs as the blame-handling entry points for external accusations.
