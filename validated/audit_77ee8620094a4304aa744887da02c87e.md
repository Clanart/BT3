### Title
`ReceivedOutput::read` accepts untrusted offset/output pairs without verifying the offset actually controls the `script_pubkey`, reporting unspendable outputs as spendable — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the ERC-4626 report — where `maxDeposit()`/`maxMint()`/`maxWithdraw()` return permissive values while the corresponding actions revert — `bitcoin-serai` has a "report vs. action" inconsistency: `ReceivedOutput` is documented and typed as "a spendable output," and `ReceivedOutput::read` reconstructs one directly from untrusted bytes, yet nothing checks that the claimed `offset` actually derives the key controlling the output's `script_pubkey`. The inconsistency is only detected much later (and silently, via `Option`), when `SignableTransaction::multisig` fails, or — worse — is never detected if the output is counted as balance.

### Finding Description
`ReceivedOutput` bundles three independently parsed fields: an `offset` scalar, a `TxOut`, and an `OutPoint` (`wallet/mod.rs:90-97`). Its decoder, `ReceivedOutput::read`, simply deserializes all three fields from the reader and returns the object — there is no consistency check (`wallet/mod.rs:122-134`):

```rust
let offset = Secp256k1::read_F(r)?;
// ... consensus_decode TxOut and OutPoint
Ok(ReceivedOutput { offset, output, outpoint })
```

By contrast, the only honest constructor, `Scanner::scan_transaction`, produces a `ReceivedOutput` where `offset` was looked up in `self.scripts`, a `HashMap<ScriptBuf, Scalar>` that maps each registered P2TR script to the offset that generates it (`wallet/mod.rs:153-156, 205-211`). That invariant — `p2tr_script_buf(key + G*offset) == output.script_pubkey` — is what makes the output actually spendable, and it is exactly what `read` fails to re-establish.

The "actual action" side does check: `SignableTransaction::multisig` recomputes `p2tr_script_buf(offset.group_key())` and compares it against `prevouts[i].script_pubkey`, returning `None` on mismatch (`wallet/send.rs:275-281`). So, like `maxMint()` returning `u256::MAX` while `mint()` reverts, `ReceivedOutput::read` reports a spendable output while the spending path silently refuses it.

### Impact Explanation
- **Funds reported received that are not spendable.** Any component that consumes serialized `ReceivedOutput`s (e.g., outputs relayed between signer processes or reconstructed from storage/RPC) will treat attacker- or corruption-supplied bytes as a valid, spendable UTXO of `output.value` sats. Balance accounting, fee/input selection (`SignableTransaction::new` happily builds a transaction over it at `send.rs:175-221`), and eventuality tracking all proceed under a false premise.
- **Silent, late failure with DoS potential.** The mismatch surfaces only inside `multisig()` as a bare `None` (`send.rs:277-279`), after a full `SignableTransaction` was constructed and `needed_fee`/weight checks passed — indistinguishable from "wrong keys," providing no attribution that a malformed `ReceivedOutput` was the cause. A malicious party feeding crafted serialized outputs can stall signing rounds or poison input selection.
- The value field is fully attacker-controlled (any `TxOut`/outpoint pair is accepted by `consensus_decode`), so reported inflow amounts can be arbitrarily inflated.

### Likelihood Explanation
`ReceivedOutput::read` is an explicitly public deserialization API taking arbitrary `Read` bytes — precisely the untrusted-input surface in scope. Any peer, coordinator, or compromised transport supplying these bytes can inject `offset`/`script_pubkey` mismatches. No cryptographic work is required: choose any valid scalar and any `TxOut`. Exploitation requires that some consumer trusts deserialized `ReceivedOutput`s without re-deriving them via `Scanner`, which is the natural usage of a `read`/`write` API pair. Impact is bounded to misreporting/DoS rather than key leakage or forged signatures, consistent with Medium.

### Recommendation
Bind the offset to the output at deserialization time. Either:
- Store the scanning `key` (or a fingerprint of it) in `ReceivedOutput` and have `read`/`write` carry it, then verify `p2tr_script_buf(key + G*offset) == output.script_pubkey` inside `read`, returning an `io::Error` on mismatch; or
- Provide a `verify(&self, key: &ProjectivePoint) -> bool` on `ReceivedOutput` performing that check, and call it in `SignableTransaction::new` (failing loudly with a dedicated `TransactionError::UnspendableInput`) rather than only inside `multisig()`.

This mirrors the report's fix: make the reporting path (`read`) enforce the same invariant the action path (`multisig`) requires, instead of returning misleading "spendable" values.

### Proof of Concept
```rust
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf, hashes::Hash, Txid};
use k256::Scalar;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction};

// Crafted bytes: offset = 7, but TxOut pays to an unrelated script
let mut buf = vec![];
buf.extend(Scalar::from(7u64).to_bytes());                       // arbitrary offset
let fake_out = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: ScriptBuf::new_op_return(&[] as &bitcoin::script::PushBytes), // not our P2TR
};
buf.extend(bitcoin::consensus::encode::serialize(&fake_out));
buf.extend(bitcoin::consensus::encode::serialize(
    &OutPoint::new(Txid::from_raw_hash(/* any */), 0),
));

// Accepted unconditionally: reported as "a spendable output" worth 100k sats
let output = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(output.value(), 100_000);

// SignableTransaction::new treats it as a real input
let tx = SignableTransaction::new(
    vec![output], &payments, None, None, fee_per_vbyte,
).unwrap();

// The actual spend path silently fails: multisig() returns None because
// p2tr_script_buf(key + G*7) != fake_out.script_pubkey
assert!(tx.multisig(&keys).is_none());
```
