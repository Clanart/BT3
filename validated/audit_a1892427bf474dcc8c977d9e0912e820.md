## Title
Unvalidated PR file paths from GitHub API allow directory-traversal/symlink escape when opening files in "Open with Default Program" / "Reveal in File Manager" - (File: app/src/ui/open-pull-request/pull-request-files-changed.tsx)

### Summary
`onFileContextMenu` in `PullRequestFilesChanged` builds the full filesystem path for a pull-request file with a raw `Path.join(repository.path, file.path)`, where `file.path` comes from `CommittedFileChange` objects populated from GitHub's Pull Request "files changed" API data. [1](#0-0)  Unlike other parts of the codebase that resolve untrusted repo-relative paths through the containment-checking helper `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` (see `app/src/lib/path.ts`, used from `dispatcher.ts`, `app-store.ts`, `copilot-conflict-context.ts`), this code path never validates that the resolved path stays inside `repository.path`. [2](#0-1) 

### Finding Description
`_resolveWithin` in `app/src/lib/path.ts` exists specifically to prevent a repo-relative path from escaping the repository root — it normalizes the input, joins/resolves it against the root, and then compares real (symlink-resolved) paths with `realpath` before declaring the result safe. [3](#0-2)  This is the sanctioned pattern for handling repo-relative, attacker-influenced paths elsewhere in the app.

`onFileContextMenu`, however, computes `fullPath` with plain `Path.join`, which collapses `..` segments and does not resolve symlinks or verify containment:
```
const fullPath = Path.join(repository.path, file.path)
``` [4](#0-3) 

The only downstream gate is `pathExists(fullPath)`, which merely checks that *something* exists at that (already-joined, unvalidated) location — it provides no containment guarantee and in fact will happily return `true` for a path that has escaped the repository via a symlinked intermediate directory. [5](#0-4)  If `fileExistsOnDisk` is true, the menu offers "Open with Default Program" (`this.onOpenFile(file.path)` → `onOpenFile` re-does the same unchecked `Path.join` and calls `openFile`), "Reveal in File Manager" (`revealInFileManager(repository, file.path)`, which independently does `Path.join(repository.path, path)` with no check either), and "Open in \<editor\>" (`dispatcher.openInExternalEditor(fullPath)`). [6](#0-5) [7](#0-6) 

`file.path` is a `CommittedFileChange.path` that is populated from GitHub's pull-request "files changed" API response — attacker-controlled content whenever the PR author (or the PR's underlying commit tree) is untrusted. A PR whose diff includes a path component that resolves through a symlink present in the repository's working directory (e.g., a symlink committed to the base branch pointing outside the repo, combined with a file path segment crafted to traverse through it) can cause `fullPath` to point to a file outside `repository.path`.

### Impact Explanation
If exploited, opening the PR's Files Changed tab and using the context menu's "Open with Default Program", "Open in \<editor\>", or "Reveal in File Manager" actions can read/open/reveal a file outside the intended repository scope, disclosing local user data (files reachable via the symlink target) to an action triggered from untrusted PR content. This matches the "Attacker-controlled repository content... makes Desktop read... files outside the selected repository scope" impact class described in the question.

### Likelihood Explanation
Requires the victim to open a specific PR's Files Changed tab and right-click a file to invoke "Open with Default Program"/"Reveal in File Manager"/"Open in editor" — a normal, expected user interaction for reviewing PRs, not an unusual or "unnatural" step. The attacker only needs control over PR content (a commit introducing a symlink plus a file path that traverses through it), which is within the scope of "repository content" defined as attacker-controlled input in this review.

### Recommendation
Route `file.path` through the existing `resolveWithin` (or platform-specific variant) helper before constructing `fullPath` in `onFileContextMenu`/`onOpenFile`, and apply the same containment check inside `revealInFileManager` in `app/src/lib/app-shell.ts`, mirroring how `dispatcher.ts` and `app-store.ts` already validate repo-relative paths from untrusted sources. If `resolveWithin` returns `null`, disable/hide the corresponding menu items instead of falling back to the raw joined path.

### Proof of Concept
1. Prepare a repository where the base branch contains a symlink (e.g., `evil -> /Users/victim/Documents`) committed to the tree.
2. Open a pull request whose diff introduces/touches a file path that traverses through that symlink (e.g., `evil/secrets.txt`), as reported by GitHub's PR "files changed" API (`CommittedFileChange.path`).
3. In Desktop, open the PR's "Files changed" tab; select the file, right-click to trigger `onFileContextMenu`.
4. `fullPath = Path.join(repository.path, "evil/secrets.txt")` resolves on disk through the symlink to `/Users/victim/Documents/secrets.txt`, `pathExists` returns true, and choosing "Open with Default Program"/"Reveal in File Manager" opens/reveals the file outside the repository, with no `resolveWithin`-style check ever rejecting it.

Note: I was unable to fully trace the exact upstream fetch/normalization step that populates `CommittedFileChange.path` from the raw GitHub API pull-request-files response in the time available (searches for `getPullRequestFilesChanged`/`changePullRequestFileSelection` only located call sites in `dispatcher.ts`/`app-store.ts`, not the API-parsing code itself), so I could not rule out an additional normalization step there; however, no containment check equivalent to `resolveWithin` was found anywhere in this specific rendering/context-menu code path, which is the direct sink in question.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
