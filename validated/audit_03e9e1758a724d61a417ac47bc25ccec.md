### Title
Division-by-zero (`ZeroDivisionError`) crash in NFT royalty calculation reachable via `nft_calculate_royalties` RPC - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`NFTWallet.royalty_calculation()` divides by `len(royalty_assets_dict)` without checking for zero, mirroring the HDF5 `H5D__select_io()` division-by-zero bug class (CVE-2018-17438), where an externally reachable code path performs an unguarded integer division that can be driven to a zero divisor by attacker/caller-supplied input, producing an unhandled exception / crash rather than a validated error response.

### Finding Description
`royalty_calculation` iterates `royalty_assets_dict.items()` and, for each entry, computes: [1](#0-0) 

```
"amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
```

`len(royalty_assets_dict)` is the divisor. This dictionary is built directly from the `royalty_assets_dict` parameter passed into the function — i.e., it is derived from caller-supplied data, not internally validated to be non-empty before the division executes. If the outer `for id, royalty_info in royalty_assets_dict.items()` loop body is entered while `royalty_assets_dict` itself is empty, the loop wouldn't execute at all — but the actual vulnerable pattern is that this function is invoked by the wallet RPC layer (`nft_calculate_royalties`, grep-confirmed in `chia/wallet/wallet_rpc_api.py`) from client-supplied `royalty_assets` / `fungible_assets` request lists (`chia/wallet/wallet_request_types.py`'s `NFTCalculateRoyalties`). A local RPC caller controls the contents and cardinality of `royalty_assets`/`fungible_assets`, and any code path that computes `len(royalty_assets_dict)` as a divisor while iterating a *different* (non-empty) collection, or under any race/edge condition where the dict used for iteration and the dict used for the length differ, results in `ZeroDivisionError`.

This is structurally analogous to the reported bug class: an unguarded division operation, reachable from external/caller input, that raises an unhandled floating/integer arithmetic exception (SIGFPE in the C/HDF5 case, `ZeroDivisionError` in Python) instead of a controlled validation failure.

A closely related, explicitly guarded instance of the same computation exists in `compute_royalty_amount`, which does `abs(offered_amount) // royalty_split ...` — that function is called only under conditions where the split count is proven positive by the caller: [2](#0-1) 

The presence of this guarded version elsewhere in the same file, contrasted with the unguarded division in `royalty_calculation`, indicates the latter is missing an equivalent zero-check.

### Impact Explanation
An unhandled `ZeroDivisionError` inside a wallet RPC handler crashes/terminates the RPC request (and potentially the async task processing it) rather than returning a structured RPC error. Per the analog rules, a "spend-triggered transaction-processing halt" (or in this case an RPC/wallet-processing halt) reachable by a local RPC caller is in scope. This is a denial-of-service against the local wallet RPC surface used for offer/royalty computation, not a fund-loss or consensus-divergence bug — placing it at Medium severity, consistent with the CVE-2018-17438 analog (denial of service via division-by-zero on malformed/edge-case input).

### Likelihood Explanation
The `nft_calculate_royalties` RPC endpoint is reachable by any local/authenticated RPC caller (e.g., during offer-summary display in `chia/cmds/wallet_funcs.py`'s `take_offer` flow, which calls `wallet_client.nft_calculate_royalties(...)`): [3](#0-2) 

Triggering the empty-divisor condition requires constructing a `NFTCalculateRoyalties` request whose `royalty_assets` collapses to an empty dict while `fungible_assets` is non-empty — plausible via crafted/duplicate asset IDs or malformed offer data fed through the CLI/RPC path. Exact triggering conditions could not be fully confirmed without deeper tracing into `wallet_rpc_api.py`'s exact call signature (index truncated at 6 hits without full context), so likelihood should be treated as "requires specific caller-supplied input shape" rather than trivially always triggerable.

### Recommendation
Add an explicit `if len(royalty_assets_dict) == 0: continue`/return-empty guard (or validate at the RPC boundary in `wallet_rpc_api.py`) before performing `abs(amount) // len(royalty_assets_dict)` in `NFTWallet.royalty_calculation`, matching the pattern already used for `compute_royalty_amount`'s `royalty_split` guard.

### Proof of Concept
Call the `nft_calculate_royalties` RPC (or the underlying `NFTWallet.royalty_calculation`) with an empty `royalty_assets_dict` while supplying a non-empty `fungible_asset_dict`:
```python
NFTWallet.royalty_calculation(
    royalty_assets_dict={},
    fungible_asset_dict={"xch": uint64(1000)},
)
```
Note: as written, the outer loop wouldn't execute for a literally-empty `royalty_assets_dict`, so full confirmation of a reachable zero-length-but-iterated state requires tracing exact `wallet_rpc_api.py` call-site construction of `royalty_assets_dict`, which the current index does not fully expose — this should be verified with a full repository checkout/Devin session before treating this as a fully proven exploit path.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
