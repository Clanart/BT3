### Title
Tokens delivered via ICS-20 destination-callback can be permanently frozen at an unrecoverable isolated address when the receiving contract fails to forward the full balance - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`ContractKeeper.IBCReceivePacketCallback` in `x/ibc/callbacks/keeper/keeper.go` mints/unescrows ICS-20 tokens to a deterministic, key-less "isolated address" *before* invoking the destination contract, then approves and calls the contract to pull the funds. This mirrors the Aegis pattern of moving value into a contract as part of a multi-step flow and only afterward validating whether the flow can complete. If the invoked contract does not withdraw the entire balance (bug, revert on partial transfer, fee/rounding behavior, malicious/careless contract, or gas exhaustion), the code deliberately returns an error, but the underlying token transfer to the isolated address happened on the real (uncached) `ctx` prior to the callback and is not undone by that error. Because the isolated address has no private key (`x/ibc/callbacks/types/keys.go`, `GenerateIsolatedAddress`), any remaining balance is permanently unreachable, exactly the scenario the module's own README documents as a "Limitation."

### Finding Description
`IBCReceivePacketCallback` (x/ibc/callbacks/keeper/keeper.go:104-242):

1. Verifies the packet's receiver equals the isolated address derived from `(destChannel, sender)` (lines 145-155) — the ICS-20 transfer's `OnRecvPacket` has *already* minted/unescrowed the ERC20-backed coin to this isolated address as part of core IBC packet processing, executed on the real context, not a cached one.
2. Sets an ERC-20 `approve` for the target contract on a `cachedCtx` (lines 185-212).
3. Calls the target contract with attacker/user-supplied calldata via `CallEVMWithData` on the same `cachedCtx` (lines 214-218).
4. Only after `writeFn()` commits the cached context (line 227) does it check `receiverTokenBalance` on the *isolated address* and return an error if it is non-zero (lines 229-239), explicitly to "prevent funds from getting stuck in the isolated address."

The problem: the token mint/unescrow to the isolated address (step 0, performed by the ICS-20 transfer app's `OnRecvPacket`) occurs *before* this callback runs and outside of `cachedCtx`. Per ibc-go's ADR-8 callback middleware design, a contract-keeper callback failure does not roll back the underlying application's already-applied state changes — only the callback's own effects (wrapped separately) are affected. Therefore, when the balance check at line 236 fails and an error is returned:
- The already-received tokens remain sitting at the isolated address (unreachable, since `GenerateIsolatedAddress` produces a key-less account — confirmed in the module's own README, "Limitations" section: "If tokens are deposited back into the isolated address, they are unreachable").
- The returned error typically results in an error acknowledgement being communicated for source-chain bookkeeping purposes, which can cause the sender-side chain to treat the transfer as failed/refund the sender, while the destination-side value is not correspondingly burned/reverted — leaving the destination-chain isolated address holding an un-recoverable balance.

The `receiverTokenBalance != 0` guard, intended as a safety check, cannot actually prevent the freeze once the mint has already landed in the isolated account; it can only surface the condition after the fact via an error, by which point the funds are already stuck.

### Impact Explanation
This satisfies the "Critical permanent freezing, locking… of user funds… or token-pair-backed balances" impact class. Any ERC20-backed IBC coin routed through the destination-callback path becomes permanently locked whenever the destination contract (which can be specified by any sender via packet memo, and may be buggy, malicious, under-gassed, or simply designed around fee-on-transfer/rounding assumptions that don't zero out the balance) fails to fully drain the isolated address's balance. Since the isolated address is provably key-less (`address.Module(...)`), there is no admin or user recovery path once tokens land there. This can be triggered by an ordinary, unprivileged relayed ICS-20 packet — no validator/relayer collusion or governance action required.

### Likelihood Explanation
Likelihood is high: any user can construct an ICS-20 transfer with a `dest_callback` memo pointing at a contract they do not fully control the correctness of (or that has non-atomic multi-step forwarding logic), and any rounding/fee/reentrancy/gas-limit edge case in that contract results in a non-zero residual balance at the isolated address. The check at keeper.go:236 confirms the developers were aware residual balances are dangerous, but the mitigation (returning an error after the mint already landed) does not actually reverse the underlying transfer.

### Recommendation
Ensure the entire receive-plus-callback flow (including the underlying ICS-20 mint/unescrow to the isolated address) is executed within a single cached context that is only committed if the post-callback balance check passes; if the contract fails to drain the isolated address, propagate an ack that both (a) prevents the SDK from committing the mint to the isolated address, or (b) automatically refunds/reroutes the residual balance to the original packet `Receiver`/`Sender` instead of leaving it parked in a key-less account. At minimum, add an explicit sweep/rescue mechanism so any residual balance left in an isolated address can be moved by the legitimate packet sender.

### Proof of Concept
Conceptual (not executed, given tool-call limits):
1. Sender A on chain B sends an ICS-20 transfer to chain A with `memo` containing a `dest_callback` pointing to a contract `C` that implements `IERC20(token).transferFrom(msg.sender, address(this), amount - 1)` (i.e., leaves 1 wei/unit behind) — this could be an honest bug (rounding) or intentional griefing by any third party who deploys such a contract and convinces users/relayers to reference it.
2. `OnRecvPacket` executes normally, minting/unescrowing the full amount to the isolated address (real ctx, committed).
3. `IBCReceivePacketCallback` approves `C` for the full amount and calls it; `C` only pulls `amount-1`.
4. `receiverTokenBalance` at line 234-236 is non-zero (`1`), so the function returns `types.ErrEVMCall` "receiver has 1 unrecoverable tokens after callback."
5. The leftover `1` unit (and, depending on ibc-go's exact ack-override semantics for this version, potentially the full amount if the callback fails earlier, e.g. `approve` revert at line 192-195, before any tokens are pulled) remains at the isolated address with no corresponding private key — permanently frozen, matching the module's documented "Limitations." func (k ContractKeeper) IBCReceivePacketCallback(
	ctx sdk.Context,
	packet ibcexported.PacketI,
	ack ibcexported.Acknowledgement,
	contractAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.DestinationCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	// receiver := sdk.MustAccAddressFromBech32(data.Receiver)
	receiver, err := sdk.AccAddressFromBech32(data.Receiver)
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"acc addr from bech32 conversion failed for receiver address: %s", data.Receiver)
	}
	receiverHex, err := utils.HexAddressFromBech32String(receiver.String())
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"hex address conversion failed for receiver address: %s", receiver)
	}

	// Generate secure isolated address from sender.
	isolatedAddr := types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)
	isolatedAddrHex := common.BytesToAddress(isolatedAddr.Bytes())

	acc := k.authKeeper.NewAccountWithAddress(ctx, receiver)
	k.authKeeper.SetAccount(ctx, acc)

	// Ensure receiver address is equal to the isolated address.
	if receiverHex.Cmp(isolatedAddrHex) != 0 {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress, "expected %s, got %s", isolatedAddrHex.String(), receiverHex.String())
	}

	contractAddr := common.HexToAddress(contractAddress)

	// Check if the contract address contains code.
	// This check is required because if there is no code, the call will still pass on the EVM side,
	// but it will ignore the calldata and funds may get stuck.
	if !k.evmKeeper.IsContract(ctx, contractAddr) {
		return errorsmod.Wrapf(types.ErrContractHasNoCode, "provided contract address is not a contract: %s", contractAddr)
	}

```markdown
## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
```
