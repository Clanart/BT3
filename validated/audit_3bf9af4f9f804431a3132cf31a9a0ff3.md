## Title
Explicit disabling of Git's clone-time symlink/submodule protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) can let a malicious cloned repository write files outside the destination folder - (File: `app/src/lib/git/clone.ts`)

### Summary
The upstream report's broken invariant is: a hostile, attacker-controlled asset (the NFT contract) is allowed to interact with a critical state-transition function (`stopRent`) without the protocol validating that the asset will behave safely, and the code path assumes the external call cannot fail in a way that corrupts protocol invariants. The reNFT team's own fix was to add a whitelist so untrusted assets can't reach the vulnerable code path.

The GitHub Desktop analog with the same "attacker-controlled external input reaches a critical filesystem operation whose safety was assumed rather than enforced" shape is in `clone()`: Desktop explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` when invoking `git clone --recursive`, which disables Git's own built-in defenses (added in Git 2.45.1/2.45.2 as part of the CVE-2024-32002 fixes) against symlinked `.git` directories and malicious submodules during clone. Since the clone target is attacker-controlled content (the repository being cloned), this is precisely the "attacker controls a cloned/fetched repository" primitive called out in the task's valid-impact list.

### Finding Description
`clone()` in [1](#0-0)  builds the environment for the `git clone --recursive` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to let embedders/scripts explicitly opt out of the hardening that was added to `git clone --recursive` to stop a malicious repository's submodule structure (e.g., a submodule whose worktree/`.git` is a symlink, or nested submodule paths designed to escape the destination directory) from writing hook files or other content outside the intended clone directory. By forcing this variable to `'false'`, Desktop is telling the bundled Git binary to skip that protection for every clone, regardless of where the repository comes from.

This directly parallels the reNFT bug's structure: a critical operation (`stopRent` / here, `git clone --recursive`) is executed against attacker-supplied content (a rentable NFT / here, a cloned repository's submodule tree) while a safety mechanism that exists specifically to prevent that content from corrupting state has been bypassed — in reNFT's case there was no whitelist yet; in Desktop's case the built-in Git safeguard has been actively turned off rather than merely absent.

### Impact Explanation
If a user clones or adds-as-submodule a maliciously crafted repository through Desktop's clone flow (`_clone` → `clone()`), the disabled protection could allow the initial recursive submodule checkout to place files or symlinked directories outside of the intended clone destination, which is exactly the "file write outside the repo" impact category called out as valid for this scan. Because `checkoutBranch`/`checkoutCommit` also invoke `updateSubmodulesAfterOperation` with a similar recursive `submodule update --init --recursive` [2](#0-1) , the same class of attacker-controlled submodule content is processed again on every checkout after clone, not just once.

### Likelihood Explanation
The condition is unprivileged and fully attacker-controlled from the victim's perspective: any public or shared repository the user is enticed to clone (a common, natural workflow in Desktop — no unnatural steps required) can embed a crafted `.gitmodules`/submodule layout. The only mitigating factor is that Git's own upstream protection has already patched the specific known symlink/embedded-`.git` vectors this variable guards against in modern Git releases bundled with recent Desktop versions, so real-world exploitability depends on which class of the CVE-2024-32002 family of issues remains reachable once the opt-out is forced — the finding cannot be reduced to a fully working end-to-end PoC without testing against the exact bundled Git version, which is not verifiable from the indexed code alone.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. If the flag was added to work around a specific compatibility problem, scope the opt-out narrowly (e.g., only for known-safe/local clones) rather than applying it unconditionally to every `clone()` call, and add regression tests using a submodule-based malicious-symlink fixture (similar to the existing `test-submodule-checkouts` / `submodule-basic-setup` fixtures) to confirm the protection remains active for remote clones.
