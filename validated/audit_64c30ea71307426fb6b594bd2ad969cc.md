## Title
Unbounded EIP-7702 authorization-list loop performs expensive ECDSA recovery before intrinsic-gas/fee validation in EVM ante handling - (File: x/evm/ante/preprocess.go)

### Summary
`EVMPreprocessDecorator.AnteHandle` iterates over every entry in a `SetCodeTx`'s attacker-controlled `AuthList` (via `associateAuthorizationAuthorities` / `ethTx.SetCodeAuthorizations()`) and performs ECDSA signature recovery plus association bookkeeping for each entry, under an **infinite gas meter**, before the transaction's intrinsic gas is checked. This mirrors the reported bug class (unbounded loop over a caller-supplied array causing excessive/uncapped work) but is more severe here because the loop runs with no gas metering and before the fee/intrinsic-gas checks that would otherwise reject an underpriced transaction.

### Finding Description
In the EVM ante pipeline, `EVMPreprocessDecorator` runs first and installs an infinite gas meter: [1](#0-0) 

It then calls `p.associateAuthorizationAuthorities(ctx, msg, associateHelper)`, which loops over every authorization in the transaction's `SetCodeAuthorizations()`, performing an ECDSA-based pubkey recovery check (`helpers.AuthorityToPreAssociate`) and a cache-context association write for each entry: [2](#0-1) 

Only *after* this decorator runs does `BasicDecorator.AnteHandle` compute intrinsic gas (which does account for authorization-list cost via `core.IntrinsicGas(..., etx.SetCodeAuthorizations(), ...)`) and reject the transaction if `etx.Gas() < intrGas`: [3](#0-2) 

And fee/balance charging (`EVMFeeCheckDecorator`) happens even later in the chain: [4](#0-3) 

So the order of operations is: **(1) unpack tx → (2) loop over the entire attacker-controlled AuthList doing ECDSA recovery for each entry, with no gas accounting → (3) check intrinsic gas (which is what should have rejected an AuthList that's too large for the declared gas) → (4) charge fees.** A transaction with a large `AuthList` but a `Gas` field set just below what `core.IntrinsicGas` would require will still pay for and force step (2)'s full CPU cost on every node that runs ante handling (both `CheckTx` mempool admission and `DeliverTx`) before being rejected for insufficient gas — meaning the expensive work happens for free, repeatedly, for every peer that receives the tx via gossip and re-validates it in `CheckTx`.

This is functionally the same bug class as the reported `useCollateral()` DOS: an unbounded loop over a caller-controlled array (`OfferArg[]` there, `AuthList` here) that can be sized to exhaust resources — except here the loop runs under an *infinite* gas meter and prior to the exact gas check that is supposed to bound it.

### Impact Explanation
An attacker can craft a `SetCodeTx` with a very large `AuthList` (bounded only by tx-size/mempool limits, not by any explicit cap on authorization count) and a `Gas` value deliberately set below the true intrinsic-gas requirement. Every validator/full node that receives this transaction (via `CheckTx` in the mempool, and again in `DeliverTx` if it makes it into a block, plus any re-broadcast/re-check cycles) will perform full ECDSA authority-recovery work for every authorization entry before the transaction is ultimately rejected for insufficient gas — at effectively zero cost to the attacker (no fee is charged since fee-check happens after intrinsic-gas rejection). Submitted repeatedly/concurrently across the network, this can consume disproportionate validator CPU time relative to attacker cost, degrading mempool throughput and potentially delaying block production.

### Likelihood Explanation
Reachable directly by any unprivileged transaction sender submitting a normal RPC-broadcast EVM transaction (`SetCodeTx`/EIP-7702) — no special privileges, precompile access, or governance action required. The only precondition is constructing a `SetCodeTx` with many authorization tuples and an intentionally-low gas limit, which is straightforward with standard tooling (go-ethereum tx construction libraries support `AuthList`).

### Recommendation
Move a cheap, size-only bound check on `len(etx.SetCodeAuthorizations())` (or equivalently a rough intrinsic-gas/gas-limit sanity check) into `EVMStatelessChecks`/`EVMPreprocessDecorator` *before* `associateAuthorizationAuthorities` runs, so that transactions whose declared `Gas` cannot possibly cover the authorization list are rejected prior to doing any per-authorization ECDSA work. Alternatively, reorder the ante chain so intrinsic-gas validation (`BasicDecorator`) runs strictly before `EVMPreprocessDecorator`'s authority pre-association loop, and/or bound the loop by a hard maximum authorization count independent of the gas check.

### Proof of Concept
1. Construct an EIP-7702 `SetCodeTx` with a large `AuthList` (e.g. several thousand `SetCodeAuthorization` entries), each a syntactically valid (or even garbage/self-consistent) authorization tuple.
2. Set `Gas` on the transaction to a value just below the true intrinsic gas cost that `core.IntrinsicGas` would compute for that many authorizations (this is normally used to reject the tx cheaply).
3. Sign and broadcast the transaction to a node's public RPC.
4. Observe that `EvmCheckTxAnte` → `EVMPreprocessDecorator.AnteHandle` → `associateAuthorizationAuthorities` iterates and ECDSA-validates every authorization in `AuthList` (via `helpers.AuthorityToPreAssociate`) under an infinite gas meter, *before* `BasicDecorator` computes intrinsic gas and rejects the tx with `core.ErrIntrinsicGas`. Repeating this broadcast across many peers/re-checks demonstrates the disproportionate CPU cost imposed on the network relative to the attacker's cost (an ultimately-rejected, fee-free transaction).

*(Note: I could not fully verify the exact per-authorization cost of `helpers.AuthorityToPreAssociate` — the file `utils/helpers/address.go` could not be retrieved in this session due to a tool/path issue, so the precise crypto operations performed per loop iteration are inferred from the call site's documented purpose (pubkey-derived authority association) and the surrounding comments in `preprocess.go`, not directly confirmed by reading its implementation.)*

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
