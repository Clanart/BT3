[1](#0-0) ### Title
Forged `ReceivedOutput` deserialization can fabricate unspendable wallet funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Severity: Medium. `ReceivedOutput::read` constructs an object representing a spendable wallet output from an attacker-controlled scalar offset, `TxOut`, and `OutPoint`, without validating the script-to-offset binding or confirming that the referenced output exists. [2](#0-1) 

### Finding Description
`Scanner::new` establishes the legitimate ownership invariant by registering the wallet’s base P2TR script with a zero offset. [3](#0-2)  `Scanner::register_offset` similarly computes the P2TR script for `key + offset * G` before storing that script-to-offset mapping. [4](#0-3) 

The normal scan path only constructs a `ReceivedOutput` after a transaction output’s `script_pubkey` matches a registered script, and it derives the `OutPoint` from the actual transaction ID and output index. [5](#0-4)  `ReceivedOutput::read` bypasses all of those provenance checks by directly accepting the offset, transaction output, and outpoint from serialized bytes. [1](#0-0) 

This is a deserialization object-injection analog: attacker-controlled bytes instantiate a fixed internal object while bypassing the invariant enforced by its normal constructor. [1](#0-0) 

### Impact Explanation
A forged `ReceivedOutput` is indistinguishable from one produced by `Scanner::scan_transaction`, and its public accessors expose the attacker-selected offset, output, outpoint, and amount to downstream wallet logic. [6](#0-5) 

An attacker can therefore cause an application to report funds as received even though no such UTXO exists, or the output’s script is not controlled by the wallet’s key and offset. [1](#0-0)  The concrete consequence is funds reported received that are not spendable. [7](#0-6) 

### Likelihood Explanation
The issue is reachable wherever serialized `ReceivedOutput` values are loaded from peer input, imported wallet data, or mutable storage that an unprivileged party can influence. [2](#0-1)  The format has no keyed authentication or wallet/scanner context, so constructing a syntactically valid forged value only requires a canonical scalar and consensus-valid Bitcoin encodings. [1](#0-0) 

### Recommendation
Do not deserialize `ReceivedOutput` into trusted wallet state without revalidation. Change `ReceivedOutput::read` to accept the relevant `Scanner` or wallet key and require `scripts.get(&output.script_pubkey) == Some(offset)`, then verify that the claimed outpoint exists on-chain and has sufficient maturity before crediting it. [8](#0-7)  Alternatively, authenticate locally serialized scan results with a keyed MAC and treat unauthenticated inputs as untrusted claims rather than received outputs. [9](#0-8) 

### Proof of Concept
The following creates a `ReceivedOutput` containing the wallet’s base P2TR script and the expected zero offset, but a nonexistent null outpoint. `p2tr_script_buf` produces the script form registered by `Scanner::new`, while `ReceivedOutput::read` never checks whether the transaction or outpoint exists. [10](#0-9) [1](#0-0) 

```rust
use bitcoin::{
  consensus::encode::serialize,
  Amount, OutPoint, TxOut,
};
use k256::{ProjectivePoint, Scalar};

let wallet_key = ProjectivePoint::GENERATOR;
let script_pubkey = p2tr_script_buf(wallet_key).unwrap();

let mut bytes = Scalar::ZERO.to_bytes().to_vec();
let fake_output = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey,
};
let fake_outpoint = OutPoint::null();

bytes.extend(serialize(&fake_output));
bytes.extend(serialize(&fake_outpoint));

let mut cursor = &bytes[..];
let forged = ReceivedOutput::read(&mut cursor).unwrap();

assert_eq!(forged.value(), 1_000_000);
assert_eq!(forged.offset(), Scalar::ZERO);
assert_eq!(forged.outpoint(), &fake_outpoint);
```
