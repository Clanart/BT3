## #Vulnerability found for this question — SSRF analog in Chia DataLayer mirror URL fetching

### Title
Attacker-Controlled Mirror URLs Enable Server-Side Request Forgery in DataLayer Sync — (File: `chia/data_layer/download_data.py`, `chia/data_layer/data_layer.py`)

### Summary
Chia's DataLayer feature lets any wallet publish an on-chain "mirror" coin containing arbitrary URL strings tied to *any* existing store (launcher) id, not just stores the publisher owns. Any node that subscribes to that store id automatically fetches those URLs over HTTP with no scheme/host/IP restriction, creating a classic SSRF primitive analogous to CVE-2018-18867 (unvalidated URL parameter reaching a server-side HTTP fetch).

### Finding Description
`DLNewMirror` creates a coin paid to `create_mirror_puzzle()` whose memo simply encodes `[launcher_id, *urls]` — there is no on-chain or wallet-side check that the caller owns `launcher_id`: [1](#0-0) 

The RPC/service layer forwards this directly, only rejecting an empty URL list: [2](#0-1) [3](#0-2) 

Any node subscribed to that `store_id` periodically reads mirror URLs from the wallet and folds them into subscription server info with no validation of scheme, hostname, or IP range: [4](#0-3) 

During `fetch_and_validate()`, these attacker-supplied URLs are used directly as fetch targets: [5](#0-4) 

and are handed to `http_download()`, which performs a raw `aiohttp` GET against `server_info.url + "/" + filename` with no allow-list, no blocking of loopback/link-local/private ranges, and no restriction to a known-good scheme: [6](#0-5) 

Tests confirm mirror URLs and subscription server URLs are accepted verbatim, including loopback addresses, with no filtering logic present anywhere in this path: [7](#0-6) [8](#0-7) 

The project's own internal documentation flags mirror/plugin URLs as an external trust boundary that is only supposed to be mitigated by validating *downloaded content* against the wallet-advertised root — it explicitly does not claim URL-destination validation exists: [9](#0-8) [10](#0-9) 

### Impact Explanation
An unprivileged wallet user (any spend-bundle submitter with minimal funds) can create a `DLNewMirror` transaction referencing a `launcher_id` they do not own, embedding an arbitrary URL (e.g., a cloud metadata endpoint `http://169.254.169.254/...`, an internal-only admin/RPC service, or a local loopback service) as the mirror server. Once confirmed on chain, every other DataLayer node that subscribes to that store id — which requires no permission from the store owner — will periodically issue outbound HTTP GET requests to that URL as part of normal sync (`fetch_and_validate` → `http_download`). This turns victim nodes into an SSRF proxy: it can be used to probe/attack internal network services reachable from the node, exfiltrate data reachable via HTTP responses (limited by response validation only after the fact), or as a vector for internal network reconnaissance/DoS against internal infrastructure. This satisfies the "concrete unsigned/unauthorized action reachable from a single spend bundle" bar because publishing the malicious mirror requires only a standard signed transaction from an attacker's own wallet, and the resulting SSRF fires on any node that later subscribes.

### Likelihood Explanation
Likelihood is high for any deployment using DataLayer with subscriptions/mirrors enabled (a supported production feature, e.g., for CAT/NFT metadata roots or general off-chain data anchored on-chain). No coordination with the store owner or victim is required; the attacker only needs a wallet and a small mirror amount/fee. The victim's DataLayer service performs the fetch autonomously via its periodic `periodically_manage_data()` loop.

### Recommendation
- Validate mirror/subscription URLs before use in `chia/data_layer/data_layer.py::update_subscriptions_from_wallet` and `download_data.py::http_download`: restrict scheme to `http`/`https`, resolve and reject loopback/link-local/private/multicast/metadata-service IP ranges (unless explicitly configured for trusted local testing), and consider an allow-list/opt-in setting for mirror URL fetching.
- Consider requiring store-owner authorization (e.g., signature over the mirror payload) before mirror URLs for a `launcher_id` are honored, since currently anyone can attach mirrors to any store id.
- Apply the same URL-destination validation to `get_downloader()`'s plugin POST calls, which also send attacker-influenced `url` values to plugin services.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror` (`DLNewMirror(launcher_id=<victim_store_id>, amount=1, urls=["http://169.254.169.254/latest/meta-data/"], fee=...)`) referencing a `launcher_id` it does not own — accepted because no ownership check exists (`chia/data_layer/data_layer_wallet.py:687-703`).
2. Transaction confirms on chain, creating a `Mirror` coin visible via `dl_get_mirrors`.
3. Any node with an active `DataLayer` service that is subscribed to `<victim_store_id>` runs `update_subscriptions_from_wallet` on its next `manage_data_interval` tick, pulling the malicious URL into its subscription server list (`chia/data_layer/data_layer.py:979-985`).
4. `fetch_and_validate()` selects that server and calls `insert_from_delta_file` → `download_file` → `http_download`, causing the victim node process to issue an outbound HTTP GET to the attacker-chosen internal URL (`chia/data_layer/download_data.py:298-324`), with the request originating from the victim's network position.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
