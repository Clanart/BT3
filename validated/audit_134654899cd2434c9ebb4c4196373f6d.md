### Title
Cached FROST preprocess reused across DKG sessions/attempts enables Schnorr nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`DkgConfirmer` caches a FROST preprocess seed in `CachedPreprocesses` keyed only by `("DkgConfirmer", attempt)`. Because the cache key omits the session/genesis/validator-set, any second DKG confirmation that reuses the same `attempt` number (e.g., a later session's `attempt = 0`, or a rebuilt/overwritten `DkgKeyPair` under the same attempt) regenerates identical FROST nonces and produces a second Schnorrkel signature share over them. Two shares with the same nonce but different binding factors/messages recover the validator's MuSig secret — the same class as CVE-2025-6015 (a value that must be single-use is accepted more than once).

### Finding Description
`SigningProtocol::preprocess_internal` stores a 32-byte `CachedPreprocess` seed in the DB under `self.context`, loading it back whenever it already exists:

- `create_db!` declares `CachedPreprocesses: (context: &impl Encode) -> [u8; 32]` (`coordinator/src/tributary/signing_protocol.rs:86-90`).
- The `DkgConfirmer` context is only `(b"DkgConfirmer", self.attempt)` — no session, genesis, network, or participant set (`signing_protocol.rs:252`, `signing_protocol.rs:274-277`).
- If `CachedPreprocesses::get` returns a value, it is reused verbatim via `AlgorithmSignMachine::from_cache` (`signing_protocol.rs:123-145`).
- `from_cache` calls `seeded_preprocess`, which derives nonces deterministically from the seed plus `keys.original_secret_share()` (`crypto/frost/src/sign.rs:121-144`, `sign.rs:268-274`). The validator's `original_secret_share` is its persistent root key scalar, unchanged across sessions, so a reused seed yields byte-identical FROST nonces (identical published preprocess commitments).
- `share_internal` then calls `machine.sign(preprocesses, msg)` where `msg = set_keys_message(set, removed, key_pair)` (`signing_protocol.rs:296-301`), which differs across sessions/attempts.

`generated_key_pair` writes `DkgKeyPair::set(...)` unconditionally — unlike `save_first_preprocess`, which asserts equality on re-write (`coordinator/src/db.rs:83-95`) — and then calls `share()`, producing a share under the cached nonce (`coordinator/src/tributary/handle.rs:47-60`). `Transaction::DkgConfirmed` later calls `confirmer.complete(...)`, which internally invokes `share_internal` a second time under the same context (`handle.rs:533-535`, `signing_protocol.rs:321-326`). The file's own header acknowledges that safety rests entirely on the message and received preprocesses never differing under a fixed nonce (`signing_protocol.rs:25-48`), and explicitly notes the "check the commitments ... are in fact its commitments on-chain" guard is still a TODO (`signing_protocol.rs:50-54`).

### Impact Explanation
FROST signature shares are linear in the nonce scalars: `s = d + e·rho + lambda·secret·c`. Two shares produced with identical `(d, e)` but different `rho`/`c` (different `removed`, `key_pair`, or participant set) yield two linear equations that solve for the validator's MuSig secret share. Both the published preprocess (64 bytes) and the confirmation shares/final signature are public on the tributary and on Substrate via `publish_set_keys` (`handle.rs:551-559`), so any observer can perform the extraction. Recovery of this key lets the attacker forge the validator's contribution to future DKG-confirmation MuSigs — the root-of-trust signature used to install threshold keys on-chain — effectively breaking the "one-time token" guarantee exactly as in the Vault TOTP-reuse advisory.

### Likelihood Explanation
Reuse requires `share_internal`/`sign` to run more than once under the same `("DkgConfirmer", attempt)` context with a differing message or preprocess set. Concretely: (a) a coordinator participating in a second validator-set session whose DKG confirmation recycles attempt number 0 in the same DB (the cache key has no session/genesis component); (b) `DkgKeyPair` being overwritten by a second `generated_key_pair` report before `DkgConfirmed` completes, since neither `DkgKeyPair::set` nor the share path enforces first-write-wins (`handle.rs:54-55`). The code itself flags the missing commitment-equality check as TODO. Triggering requires at least participation in/observation of repeated DKG confirmations rather than any privileged access, but depends on a second distinct signing context materializing under the same attempt index, keeping this out of the trivially-exploitable category.

### Recommendation
Bind the cache context to the full signing session: include the tributary genesis/`spec.set().session`, the `removed` set, and the `KeyPair` in `context`, e.g. `(b"DkgConfirmer", genesis, attempt, key_pair_hash)`. Additionally, mirror `save_first_preprocess`'s pattern for `DkgKeyPair` — assert equality rather than overwrite on a second report — and after a share is produced under a context, record that fact and refuse to call `sign` again under the same seed. The pending TODO of verifying the on-chain preprocess matches the presumed cached preprocess before publishing shares should also be implemented.

### Proof of Concept
Conceptual, based on the cited code paths:

1. Validator `V` participates in DKG confirmation attempt `0` of session `s0`. `preprocess_internal` stores seed `x` under key `encode(("DkgConfirmer", 0))` and `share()` emits `s_1 = d + e·rho_1 + lambda·k·c_1` for `msg_1 = set_keys_message(set_0, removed_0, kp_0)`.
2. A subsequent session `s1` (validator rotation, new tributary genesis) runs DKG confirmation attempt `0` again. `CachedPreprocesses::get` returns `x`; `seeded_preprocess` regenerates identical `(d, e)` because the nonce derivation only mixes `x` and `V`'s unchanged secret share (`crypto/frost/src/sign.rs:127-133`). The published preprocess commitments are byte-identical to step 1's — publicly observable.
3. `share()`/`complete()` emits `s_2 = d + e·rho_2 + lambda'·k·c_2` for `msg_2 = set_keys_message(set_1, removed_1, kp_1)`. Since `set_1`/`removed_1`/`kp_1` differ, `rho_2 ≠ rho_1` and `c_2 ≠ c_1` (`crypto/frost/src/sign.rs:362-371` shows `rho` binds `group_key`, `message`, and the preprocess transcript).
4. From `(s_1, rho_1, c_1, lambda)` and `(s_2, rho_2, c_2, lambda')` — all computable from public preprocesses, the public group key, and the published signature — solve for `d`, then `e`, then `k` (V's MuSig secret share) via standard two-equation Schnorr nonce-reuse algebra.

Uncertainty: whether a coordinator DB in fact persists `CachedPreprocesses` across session/genesis boundaries, and whether `generated_key_pair` can be driven twice with distinct `key_pair`s for one attempt without a divergent DKG — I was unable to trace the DB scoping and the `GeneratedKeyPair` call sites within the available iterations; if the DB is per-session, vector (a) narrows to vector (b).
