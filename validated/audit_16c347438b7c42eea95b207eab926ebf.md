### Title
Payout attribution to an operator is derived from unauthenticated OP_RETURN data instead of who actually funded the payout - ([File: core/src/verifier.rs], [File: core/src/builder/transaction/operator_reimburse.rs], [File: core/src/operator.rs])

### Summary
The reimbursement-eligibility check `validate_payer_is_operator()` binds "who gets credited/reimbursed for a payout" to an `operator_xonly_pk` value that is read from an unsigned OP_RETURN output of the on-chain payout transaction, rather than from any authenticated proof that the named operator actually funded that payout. This is the same class of bug as the reported analog: an identity check that is supposed to verify "the caller/payer is who it claims to be" is satisfied by a value that can be freely set by anyone, breaking the binding `operator credited == operator who funded the payout`.

### Finding Description
`create_payout_txhandler` builds the payout transaction with a `SinglePlusAnyoneCanPay`-signed input (the user's withdrawal signature covers only input 0 / output 0) and appends an OP_RETURN output carrying the `operator_xonly_pk` of whichever party constructs/broadcasts the transaction: [1](#0-0) 

Because the sighash type is `SIGHASH_SINGLE | ANYONECANPAY`, the user's signature only commits to output index 0 (their own payout) and to input 0; it does not cover the fee-funding inputs added later, nor the OP_RETURN output that identifies the payer-operator: [2](#0-1) 

When Citrea/Bitcoin sync processes a finalized payout, `update_finalized_payouts` extracts `operator_xonly_pk` purely by parsing the OP_RETURN bytes of the on-chain payout transaction with no signature or authorization check tying that value to the party that actually funded the transaction's additional inputs: [3](#0-2) [4](#0-3) 

This unauthenticated value is then persisted as the "payer" and later trusted by `validate_payer_is_operator`, which only compares it against the local operator's own key to decide whether the payout was "made by me" and therefore whether the reimbursement/kickoff flow should proceed: [5](#0-4) 

The equality the protocol relies on is:
`payer_xonly_pk (read from unsigned OP_RETURN data) == the xonly_pk of the party that actually funded the payout's additional inputs`

but nothing enforces this equality — the OP_RETURN output is not covered by the only signature present on the transaction (the user's `ANYONECANPAY|SINGLE` signature covers input/output index 0 only). Any party who observes the user's signed input (e.g., from the mempool, or by intercepting the operator's broadcast before confirmation) can reconstruct a payout transaction with the same signed input/output but attach their own fee-paying inputs and write an arbitrary `operator_xonly_pk` — including that of a different, unrelated operator — into the OP_RETURN, then broadcast it first.

### Impact Explanation
If this transaction confirms, `update_finalized_payouts` will record the named (but not actually paying) operator as the payer of that withdrawal in the database. Two outcomes follow the analog pattern of "operator credited versus the party that paid":
- An operator who never funded the payout becomes eligible to be reimbursed for it via `validate_payer_is_operator` returning success for their own key, i.e. an operator is reimbursed for a payout it never funded (Critical impact per the rules).
- Conversely, the operator who actually funded the payout (paid the fees) will not be recorded as payer and will be permanently unable to claim their legitimate reimbursement for that deposit, since `validate_payer_is_operator` requires an exact match to `self.signer.xonly_public_key` and there is no recovery path once a different key is committed on-chain — an honest operator permanently unable to be reimbursed.

### Likelihood Explanation
Exploitation requires observing a signed-but-unconfirmed payout transaction (broadcast/relayed on the Bitcoin P2P network or visible in the mempool) and rebroadcasting a variant with attacker-chosen fee inputs and OP_RETURN content before the original confirms — a standard transaction-malleability/front-running technique requiring no special role, key, or privileged access, only the ability to observe mempool transactions and broadcast a competing one, which any unprivileged network participant can do.

### Recommendation
Bind the payer identity to something the payout transaction's signature actually authenticates, e.g.:
- Include the operator's xonly public key inside the sighash committed by a signature the operator (not just the withdrawing user) must produce for that specific payout, or
- Change the sighash flags used for the payout input so it commits to all outputs (e.g., use `SIGHASH_ALL` or restructure so the OP_RETURN/reimbursement identity output is covered), preventing a third party from altering the OP_RETURN payer field without invalidating the existing signature, or
- Require an additional operator signature over the full transaction (including the OP_RETURN) before treating the OP_RETURN-declared `operator_xonly_pk` as authoritative for reimbursement bookkeeping.

### Proof of Concept
1. Operator A constructs and broadcasts a payout transaction: input 0 = user's withdrawal UTXO with `SIGHASH_SINGLE|ANYONECANPAY` signature, output 0 = user's payout, output 2 = OP_RETURN containing Operator A's xonly pubkey; Operator A funds the remaining inputs/fees via `fund_raw_transaction` (`core/src/operator.rs` lines 620-674).
2. Before Operator A's transaction confirms, an attacker (or Operator B) observes it in the mempool, extracts input 0 (with the valid, reusable `ANYONECANPAY|SINGLE` signature) and output 0, and constructs a new transaction with the same input 0/output 0 but with attacker/Operator-B-funded fee inputs and an OP_RETURN output containing Operator B's xonly pubkey.
3. Attacker broadcasts and gets this transaction confirmed first.
4. `update_finalized_payouts` (`core/src/verifier.rs` lines 2313-2350) parses the OP_RETURN and records Operator B as the payer for this withdrawal in the DB, even though Operator A funded it and Operator B contributed nothing (or the attacker contributed the fee funding and named an arbitrary operator).
5. Operator B's `validate_payer_is_operator` (`core/src/operator.rs` lines 1686-1729) now succeeds, allowing Operator B to proceed through the kickoff/reimbursement flow for a payout it never funded, while Operator A — the true payer — can never pass this check for that deposit.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };
