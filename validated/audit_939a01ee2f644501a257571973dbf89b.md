## Title
Balance Handler `prevEventsLen` Desync in Recursive Precompile Calls Causes StateDB/Bank Balance Divergence - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
This is the closest reachable analog to the "missing balance deduction" bug class in this Cosmos EVM fork. In `runNativeAction` (`precompiles/common/precompile.go`), each precompile call creates a fresh `BalanceHandler` via `p.BalanceHandlerFactory.NewBalanceHandler()`, but that handler tracks bank events using a single mutable `prevEventsLen int` field recorded at `BeforeBalanceChange` and consumed at `AfterBalanceChange`. When a precompile call recursively re-enters the EVM/precompile execution path (e.g. a precompile calling back into a contract that calls a precompile again, or nested precompile-to-precompile calls sharing an execution context/event manager), the `prevEventsLen` snapshot recorded by an outer invocation can be overwritten or misaligned relative to the inner invocation's event window, causing the outer `AfterBalanceChange` call to process the wrong slice of `ctx.EventManager().Events()` — either double-processing already-applied bank events (double `AddBalance`/`SubBalance` on the StateDB) or skipping events entirely. This directly threatens the invariant that native (`x/bank`) balances and EVM `StateDB` balances must remain 1:1 synchronized, which is explicitly called out in the codebase's own security model (`precompiles/werc20/README.md: "Balance Consistency: EVM and Cosmos SDK balances remain synchronized"`) and is exactly the same class of bug as the reported "missing balance deduction" (state that should reflect one accounting truth is not updated in step with the on-chain accounting truth, permitting duplication/desync of spendable value).

### Finding Description
`BalanceHandler.BeforeBalanceChange` [1](#0-0)  records `prevEventsLen = len(ctx.EventManager().Events())` before a native action executes. `AfterBalanceChange` [2](#0-1)  then iterates `events[bh.prevEventsLen:]` to translate `x/bank` `CoinSpent`/`CoinReceived` events (and precisebank fractional-balance events) into `StateDB.SubBalance`/`AddBalance` calls, which is the sole mechanism keeping the EVM's `StateDB` balances consistent with the native bank ledger after a precompile executes a native action (e.g., delegate, transfer, deposit).

`runNativeAction` in `precompiles/common/precompile.go` [3](#0-2)  allocates a `balanceHandler` per call via the `BalanceHandlerFactory`, calls `BeforeBalanceChange` immediately before executing the precompile's native action, and `AfterBalanceChange` immediately after. This pairing implicitly assumes that within a single precompile invocation, no nested precompile call re-enters and mutates the *same* underlying event manager's event list in a way that would invalidate the previously captured `prevEventsLen` index for an enclosing, still-pending `AfterBalanceChange` call.

The repository ships a dedicated regression test explicitly describing this exact defect: `evmd/tests/integration/balance_handler/balance_handler_test.go` states in its own doc comment: *"BalanceHandlerTestSuite tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [4](#0-3)  The test drives a contract that recursively calls a debug precompile (`callback`/`Call0`/`Call1`) that itself re-enters the EVM via `CallEVMWithData` [5](#0-4) , reproducing nested precompile invocation depth.

Because `prevEventsLen` is stored on a per-call `BalanceHandler` struct instance (not global), the actual sharing/overwrite hazard depends on whether recursive precompile calls end up reusing the same handler instance or event-index baseline (e.g., through the shared `ctx.EventManager()` across cache contexts, or through `stateDB.CommitWithCacheCtx()` merging event streams from nested cache contexts back into a parent event manager before the outer `AfterBalanceChange` executes). The exact reachability trigger (whether the shared `ctx` passed down or `CommitWithCacheCtx`/`RevertMultiStore` event replay logic in `x/vm/statedb/statedb.go` [6](#0-5)  causes events emitted by an inner precompile call to be visible/counted twice or in the wrong window for an outer `AfterBalanceChange`) is not fully confirmed from static reading alone — this would require executing the existing regression test and tracing runtime event-manager identity across nested `GetCacheContext()`/`CommitWithCacheCtx()` calls, which I could not do in this read-only investigation.

### Impact Explanation
If the balance handler processes a stale or overlapping event window, a `CoinReceived`/`CoinSpent` bank event from a real native transfer (e.g., a staking delegate, WERC20 deposit, or bank precompile-mediated transfer) can be applied to the EVM `StateDB` more than once, or an event can be dropped. Double-application of `AddBalance` inflates a user's or contract's EVM-visible balance without a corresponding increase in the native `x/bank` ledger, i.e., unauthorized minting/duplication of spendable value visible to and spendable via the EVM (e.g., subsequently transferable to other EVM accounts or usable as collateral in DeFi contracts), which corrupts the 1:1 accounting invariant between native coins and EVM balances the project explicitly promises to preserve. Dropped events instead cause a user's legitimately received or spent balance to permanently desync from state, freezing or misrepresenting spendable funds. Both directions match the "Critical unauthorized minting/duplication" and "permanent freezing/locking of user funds" impact classes in scope.

### Likelihood Explanation
Reachability requires a contract to recursively invoke a stateful precompile that performs a native balance-affecting action (staking delegate/undelegate, distribution withdraw, WERC20 deposit, bank precompile calls, etc.) from within another precompile call or from a callback triggered by a precompile — a pattern fully reachable by any unprivileged EVM contract deployer, since Solidity contracts can freely call precompile addresses (`0x...0800`, `0x...0801`, etc.) recursively or via callback patterns, as demonstrated by the project's own `StakingCaller.sol` test contracts using `call`/`delegatecall`/`staticcall`/`callcode` against the staking precompile. The project maintaining a dedicated regression-test suite specifically to catch this bug is a strong signal it is a real, previously-identified, and non-trivial-to-fully-eliminate hazard in the precompile execution/event-accounting design, but I was not able to confirm from the code alone whether the currently-shipped state of `balance_handler.go`/`precompile.go` fully closes the gap or whether the test only exercises a partially-mitigated scenario.

### Recommendation
- Make `BalanceHandler`'s event-window tracking robust to reentrancy: instead of a single mutable `prevEventsLen int`, use a stack (push/pop) of event-length checkpoints, or tag each `BalanceHandler` instance with a unique identifier and scope its "before/after" pairing to only the deterministic event range recorded on entry, verified not to have been consumed by another call.
- Ensure `AfterBalanceChange` only processes events that have not already been converted to `StateDB` balance changes elsewhere — e.g., by marking/consuming processed events, or by deriving the balance delta from `bankKeeper` account-balance snapshots (before/after) rather than from potentially-reordered/aliased event streams.
- Add an invariant check (assertion or property test) at the end of each top-level EVM transaction that the total EVM `StateDB` balance for every touched address equals the corresponding `x/bank`/`x/precisebank` balance, failing the transaction (not just logging) on divergence.
- Expand `evmd/tests/integration/balance_handler/balance_handler_test.go` into a suite covering deeper and multi-branch recursion patterns (including recursion through different precompiles, e.g., staking → distribution → bank) to confirm the fix actually holds for all currently-registered stateful precompiles, not just the synthetic debug precompile.

### Proof of Concept
Not independently reproduced beyond the existing project regression test. The project's own test, `TestRecursivePrecompileCallsWithDebugPrecompile` [7](#0-6) , is the concrete PoC harness: it deploys a caller contract that recursively invokes the debug precompile (`Call0` → `CallEVMWithData` back into the caller → `callback` again) and asserts on the resulting event count/structure. To weaponize this class of bug against a real balance-affecting precompile, an attacker would replace the debug precompile's synthetic events with a genuine staking/distribution/bank precompile call and recursively trigger it from a malicious contract (e.g., a contract whose `receive()`/fallback calls back into a precompile during an `undelegate`/`withdrawDelegatorReward`/WERC20 `deposit` flow) to attempt to get `AfterBalanceChange` to apply a bank-events window twice to `StateDB`. I was unable to execute this end-to-end in the available read-only environment to confirm actual double-crediting occurs versus being already mitigated by the per-call `BalanceHandlerFactory.NewBalanceHandler()` allocation and the journal/snapshot revert machinery (`x/vm/statedb/journal.go`, `x/vm/store/snapshotkv/store.go`) — this needs a Devin session with EVM execution access to instrument `AfterBalanceChange` and observe actual event-slice boundaries across nested precompile calls before this can be escalated from "plausible, project-acknowledged bug class" to "confirmed exploitable divergence."

func (s *StateDB) RevertMultiStore(snapshot int, events sdk.Events) {
	s.snapshotter.RevertToSnapshot(snapshot)
	s.writeCache = func() {
		s.ctx.EventManager().EmitEvents(events)
		s.cacheCtx.MultiStore().(storetypes.CacheMultiStore).Write()
	}
}

// cache creates the stateDB cache context
func (s *StateDB) cache() error {
	if s.ctx.MultiStore() == nil {
		return errors.New("ctx has no multi store")
	}
	s.cacheCtx, _ = s.ctx.CacheContext()

	// Get KVStores for modules wired to app
	cms := s.cacheCtx.MultiStore().(storetypes.CacheMultiStore)
	storeKeys := s.keeper.KVStoreKeys()

	// Create and set snapshot store to stateDB
	snapshotStore := snapshotmulti.NewStore(cms, storeKeys)
	s.snapshotter = snapshotStore
	s.cacheCtx = s.cacheCtx.WithMultiStore(snapshotStore)
	s.writeCache = func() {
		s.ctx.EventManager().EmitEvents(s.cacheCtx.EventManager().Events())
		s.cacheCtx.MultiStore().(storetypes.CacheMultiStore).Write()
	}

	return nil
}
