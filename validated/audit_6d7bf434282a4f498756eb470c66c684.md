## Finding: Valid — Symlinked repo entries can redirect "Open in External Editor" outside the repository

### Summary
The path passed to `launchExternalEditor` is built by lexically joining the repository root with a git-reported relative path (`Path.join(repository.path, path)`), without ever resolving symlinks or verifying the result stays inside the repository. Git tracks symlinks as first-class blobs (mode `120000`) whose target text is fully attacker-controlled at checkout time, so a malicious repo can ship a tracked symlink (e.g. `notes` → `/Users/victim` or `../../../../`) that a user later selects via the Changes/History context menu's "Open in External Editor" action.

### Finding Description
`launchExternalEditor` receives `fullPath` and hands it straight to `spawn`/`open`: [1](#0-0) [2](#0-1) 

Every caller that builds `fullPath` for this feature does so with a plain, lexical `Path.join(repository.path, file.path)`: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`Path.join` is purely string manipulation — it does not consult the filesystem and does not know that an intermediate path component is a symlink. `_openInExternalEditor` in `app-store.ts` then forwards this string unchanged to `launchExternalEditor`: [7](#0-6) 

Notably, this codebase already has a dedicated helper, `resolveWithin` (in `app/src/lib/path.ts`), whose explicit purpose is to reject a joined path if its `realpath()` (i.e., symlink-resolved) form escapes the root directory: [8](#0-7) 

That helper is used elsewhere in the code (`dispatcher.ts`, `copilot-conflict-context.ts`) to defend against exactly this class of symlink/traversal escape, but it is never applied to the external-editor path. Because Git allows committing symlinks (mode `120000`) with attacker-chosen target strings, a cloned malicious repository can contain a tracked or untracked symlinked directory/file whose real target lies outside the repository working tree. The path string reported by git status/log for files nested under that symlink (e.g. `evil-link/config.json`) still lexically looks like it's "inside" the repo, so no existing check rejects it — but when the OS actually opens `repoPath/evil-link/config.json`, it transparently follows the symlink component and resolves to the attacker-chosen out-of-repo target.

### Impact Explanation
If the user right-clicks such a file/folder entry (in Changes, History, PR file list, or merge-conflict dialogs) and selects "Open in External Editor," the spawned editor process actually opens/edits a file outside the intended repository, potentially:
- reading sensitive host files the attacker predicted the target path of, or
- causing the user to unknowingly save edits to an arbitrary host file (e.g. overwriting `~/.ssh/authorized_keys`, shell rc files, or other config that leads to further code execution) if the user edits and saves in the external editor.

This matches the "file write or read outside the repo" impact category permitted by the program scope.

### Likelihood Explanation
Requires: (1) the victim clones/fetches an attacker-controlled repository containing a symlink entry pointing outside the repo, and (2) the victim explicitly right-clicks a nested file and chooses "Open in External Editor." This is a normal, expected user action (not an "unnatural" step) and doesn't require admin/local access — it fits within the allowed attacker model of "repository content" being attacker-controlled. Likelihood is moderate: it depends on the user interacting with the specific crafted entry, but no additional social engineering beyond normal repo browsing is needed.

### Recommendation
Before invoking `launchExternalEditor`/`launchCustomExternalEditor` (and similarly `openFile`/`revealInFileManager` if not already covered), validate `fullPath` with the existing `resolveWithin(repository.path, path)` helper (which already performs the `realpath` symlink-escape check) and refuse to launch if it returns `null`, mirroring how it's already used in `dispatcher.ts`/`copilot-conflict-context.ts`.

### Proof of Concept
1. Create a repository containing a symlinked directory tracked in git, e.g. `git symlink-add evil -> /Users/victim` (mode `120000` blob with target `/Users/victim`), and inside conceptually a nested "changed"/untracked file path like `evil/.ssh/config` reported by `git status`.
2. Victim clones this repository with GitHub Desktop; checkout creates a real OS-level symlink `evil -> /Users/victim` in the working tree.
3. In the Changes list, the entry `evil/.ssh/config` appears; user right-clicks → "Open in External Editor."
4. `onOpenItemInExternalEditor` → `Path.join(repository.path, "evil/.ssh/config")` produces `…/repo/evil/.ssh/config`, which is passed unmodified into `dispatcher.openInExternalEditor` → `_openInExternalEditor` → `launchExternalEditor` → `spawn(editorPath, [fullPath])`.
5. Because `evil` is a symlink to `/Users/victim`, the OS/editor resolves the path to `/Users/victim/.ssh/config`, opening/editing a file entirely outside the repository, confirming the escape.
