### Title
Validator staking weight is derived from the raw native-token balance of CN staking contracts, enabling a donation attack that inflates reward share and proposer-selection weight - (File: kaiax/staking/impl/getter.go)

### Summary
The `kaiax/staking` module computes each validator's `StakingAmounts` directly from the KAIA balance of its registered staking contract address, rather than from an internally tracked "staked/deposited" accounting variable. This mirrors the Tokemak `DestinationVault.balanceOfUnderlying()` bug class: anyone can inflate the accounted value simply by transferring native tokens directly to the target address, without going through any deposit/staking function.

### Finding Description
`kaiax/staking/README.md` explicitly documents that `StakingInfo summarizes the current AddressBook contract state, and all the staking contracts registered in the AddressBook, and their native token balances.` [1](#0-0) 

The getter reads staking amounts through the `MultiCallContract` and stores the raw amounts (converted from wei to KAIA) as `StakingAmounts` with no subtraction of any locked/tracked component: [2](#0-1) [3](#0-2) 

This is confirmed by the unit test, which sets `Balance` in `GenesisAlloc` for the staking contract addresses and expects that exact figure (divided by `KAIA`) to appear as `StakingAmounts`: [4](#0-3) 

`StakingContracts` (i.e., the CN staking contract addresses) are public information retrievable from the `AddressBook`, so any unprivileged sender can construct a plain value-transfer transaction to one of these addresses to unilaterally raise its `.balance`, with no interaction with the staking contract's own deposit/withdraw logic (e.g. `CnStakingV4`'s tracked `staking()`/`unstaking()` accessors are bypassed entirely by a direct transfer) [5](#0-4) .

The resulting `StakingAmounts` feed directly into the reward module's proportional distribution logic, where a validator's "excess" over `MinimumStake` determines its share of staking rewards: [6](#0-5) [7](#0-6) 

The same `StakingAmounts`/consolidated staking figures also feed the Gini coefficient computation used by the weighted-random proposer policy (`consolidatedNodes`, `cachedGini` fields in `StakingInfo`), i.e. block-proposer selection probability: [8](#0-7) 

### Impact Explanation
Because `StakingAmounts` is a spot balance read rather than a deposit-tracked value, a single unprivileged transaction sender can:
- Send KAIA directly to any CN's registered staking contract address to inflate that validator's `StakingAmounts` beyond its true, intentionally staked amount.
- This artificially increases the "excess" stake used in `assignStakingRewards`, redirecting a larger proportional share of the minted staking reward to that validator's `RewardAddr` at the expense of honest validators whose accounted stake did not change - a direct reward redirection/fund misallocation.
- It also skews the Gini coefficient and, transitively, the weighted-random proposer-selection probabilities, biasing block-proposer opportunities (and thus proposer rewards/fees) toward the inflated validator.
- Any account, including a malicious validator operator or a third party colluding with one, can perform this without any privileged access, and the donated balance is never "spent" by the protocol (it simply increases `address.balance`), making the attack essentially free except for the donated principal, which remains in the attacker's/target's control.

This satisfies the "reward redirection" and "unauthorized value movement" criteria: honest nodes computing `StakingInfo` from state will all agree on the inflated figure (no state divergence), but the reward allocation itself is provably distorted relative to the intended stake-weighted design.

### Likelihood Explanation
Likelihood is High: `StakingContracts` addresses are public (readable via `AddressBook`/`AddressBookV2`), a plain value-transfer transaction is trivially available to any account on the network, and the manipulation requires no special permissions, contract interaction ABI knowledge, or timing beyond sending a transaction before the block whose `StakingInfo` snapshot is captured (`SourceBlockNum` rules in `kaiax/staking/impl/getter.go`).

### Recommendation
Do not use the raw native-token balance of the staking contract as the authoritative "staked amount" for reward and proposer-weight computations. Instead:
- Have the staking contract (e.g., `CnStakingV4`) expose and have the `MultiCallContract`/`kaiax/staking` module consume the internally tracked `staking()` value (i.e., an explicit ledger of deposits made via the contract's staking functions) instead of `address.balance`, so that donated/unsolicited transfers cannot affect the accounted staking amount used for reward distribution and Gini/proposer-weight computation.
- If backward compatibility requires reading balances, add validation/reconciliation against the tracked `staking()`/`unstaking()` figures so that any balance in excess of the tracked stake is excluded from reward-weight calculations.

### Proof of Concept
1. Identify a validator's `StakingContract` address via the `AddressBook`/`AddressBookV2` (`kaiax/staking/impl/getter.go`'s `parseCallResult`/`parsePermissionlessCallResult`).
2. From any unprivileged account, send a plain native KAIA transfer transaction to that `StakingContract` address (no interaction with the contract's staking API required).
3. At the next `StakingInfo` snapshot block (per `SourceBlockNum` rule), `kaiax/staking.GetStakingInfo` will report an inflated `StakingAmounts[i]` for that validator, exactly equal to `address.balance / 1e18` as demonstrated in `TestGetStakingInfo_Uncached` [9](#0-8) .
4. On the next reward distribution, `kaiax/reward/impl/getter.go`'s `assignStakingRewards` computes that validator's staking-reward share proportional to the inflated `cn.StakingAmount`, redirecting more of the minted staking reward to it than its genuinely staked capital warrants.

Note: the concrete Solidity source of the production `MultiCallContract` (as opposed to its test mocks `MultiCallContractMock.sol`/`MultiCallContractMockPermissionless.sol`) was not found in the indexed codebase, so the exact on-chain read expression (`address.balance` vs. a wrapped accessor) could not be directly inspected; the conclusion above is based on the module's documented behavior (`kaiax/staking/README.md`) and the test fixtures that tie `StakingAmounts` 1:1 to `GenesisAlloc.Balance`, both of which strongly indicate balance-based accounting.

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
