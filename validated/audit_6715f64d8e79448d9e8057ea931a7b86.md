## Finding

### Title
Unchecked ERC20 transfer return value in `IntentGatewayV2.withdraw()` causes silent fund loss on redeem/refund - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report flags `AaveV3YieldManager.withdraw` for using `IERC20.transfer` (interface-typed call) that forces Solidity to decode a boolean return value USDT doesn't provide, causing a revert. The Hyperbridge Tron `IntentGatewayV2` contract took the "fix" in the wrong direction for its escrow-settlement path: instead of adopting `SafeERC20`, it replaced typed `.transfer()` calls with raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call itself didn't revert (`success`), never checking/decoding the returned boolean. This reintroduces the exact class of bug the report warns against, but in the opposite direction: it accepts token transfers that return `false` (fail) as if they succeeded, silently losing escrowed user funds.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the internal settlement routine invoked from `onAccept` for both `RedeemEscrow` and `RefundEscrow` request kinds, and from the `SweepDust` handler: [1](#0-0) 

For every escrowed ERC20/TRC20 token, the payout is done via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

A raw `.call()` only reports `success = false` if the callee reverted or the call otherwise failed at the EVM level. Many ERC20/TRC20 tokens (a well-known non-standard-compliance class the original report is specifically about) return `false` from `transfer()` on failure instead of reverting — e.g. insufficient balance, blacklisting, paused state, or fee-on-transfer edge cases. In that case, `success` is `true` (the call executed and returned normally) even though the token was never actually moved to `beneficiary`. The code does not decode/check the returned `bool`, so this failure is invisible.

Crucially, `_filled[body.commitment] = beneficiary;` is set unconditionally at the top of `withdraw()`, and `_orders[body.commitment][token] -= amount;` is unconditionally decremented right after the unchecked transfer: [1](#0-0) 

Both the fill-marking and the escrow-accounting are updated as if the payout succeeded, regardless of whether tokens actually reached `beneficiary`. This same unchecked pattern is repeated for the transaction-fee payout and for `SweepDust`: [3](#0-2) [4](#0-3) 

By contrast, the canonical EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) and the deposit-side paths in this Tron file consistently use `SafeERC20.safeTransferFrom`/`safeTransfer`, which correctly validates non-standard return-value semantics: [5](#0-4) 

Only the settlement/payout leg of the Tron gateway (`withdraw` and `SweepDust`) was changed to raw `.call()` without validating the returned boolean.

### Impact Explanation
This breaks the core intent-settlement invariant that escrowed funds move exactly once and only to the rightful beneficiary. If any input/output token used in an order returns `false` on transfer failure:
- The escrow accounting (`_orders[commitment][token]`) is wiped out and the order is marked filled/refunded (`_filled[commitment]`) even though the beneficiary received nothing.
- The tokens remain permanently stuck in the `IntentGatewayV2` contract with no recorded claim on them (the escrow entry that would authorize a retry has already been deleted), and the beneficiary has no way to reclaim their funds.
- This is a genuine, unauthorized loss of user funds and a false "settlement accepted" state — the on-chain state asserts the order was filled/refunded when it was not.

### Likelihood Explanation
This path executes on every `RedeemEscrow`/`RefundEscrow` cross-chain settlement and every `SweepDust` operation for ERC20/TRC20 tokens on the Tron deployment. It requires no malicious relayer, prover, or admin — it is triggered by ordinary protocol operation whenever a listed token's `transfer` implementation returns `false` instead of reverting on failure, a documented and common pattern (the exact class the underlying report calls out for USDT-style tokens).

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (e.g. `evm/src/apps/IntentGatewayV2.sol`, `EvmHost.sol`). This ensures both revert-on-failure tokens and false-returning tokens are handled correctly, and escrow/fill-state updates should only occur after a provably successful transfer.

### Proof of Concept
1. An order includes as input/output a TRC20/ERC20 token whose `transfer` implementation returns `false` on failure (e.g., insufficient contract balance due to a rounding/dust edge case, a paused or blacklisted transfer, or any non-reverting-failure token).
2. A relayer/user triggers settlement via `onAccept` with `RequestKind.RedeemEscrow` (or `RefundEscrow`), invoking `withdraw(body, ...)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting, so `success == true`, even though the token contract internally returned `false` and moved no tokens.
4. `_filled[commitment]` is set and `_orders[commitment][token] -= amount` is executed, permanently closing out the escrow entry.
5. `beneficiary` receives zero tokens; the escrowed principal remains locked in the `IntentGatewayV2` contract with no on-chain record entitling anyone to reclaim it.
