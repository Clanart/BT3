## Analysis

The vulnerability described is valid. The core issue: `on_accept` performs state-mutating balance transfers/mints (lines 93–117) *before* validating and dispatching the optional calldata (lines 119–203), and a failure in the calldata path returns `Err` — but that `Err` does **not** unwind the mint/transfer that already executed.

### Why this isn't atomically rolled back

Looking at the ISMP request handler that invokes `on_accept`: [1](#0-0) 

The handler processes each request in a `.map()` closure and collects **individual** `Result`s into `result: Vec<_>`, then returns `Ok(MessageResult::Request { events: result, weight: total_weights })` for the *whole batch* regardless of whether some/all individual `on_accept` calls returned `Err`. Only on a per-request `Err`, the framework deletes that request's receipt so it can be retried: [2](#0-1) 

Because the overall `handle()` call — and thus the enclosing dispatchable/extrinsic that invokes it — returns `Ok(...)`, standard FRAME behavior does **not** trigger a storage rollback for that extrinsic. FRAME only auto-reverts all storage writes made during a dispatchable's execution when the dispatchable itself returns `Err`; here the top-level result is `Ok`, so any storage mutations performed inside a failing `on_accept` (the beneficiary mint/transfer) remain committed. This exact pitfall is explicitly called out in the protocol's own documentation: [3](#0-2) 

> "if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying its internal state to prevent partial state changes that could result in critical vulnerabilities."

### The concrete flaw in `pallet-hyper-fungible-token`

`on_accept` violates that documented invariant directly: [4](#0-3) 

executes the mint/transfer to `beneficiary` unconditionally, and only afterward attempts to decode and dispatch the optional `SubstrateCalldata`: [5](#0-4) 

If `SubstrateCalldata::decode` fails, the runtime call is filtered by `BaseCallFilter`, or `runtime_call.dispatch(...)` fails, `on_accept` returns `Err(...)`. Per the handler above:
1. The mint/transfer already committed to storage stays committed (no rollback occurs at the batch/extrinsic level).
2. The request receipt for that message is deleted, clearing the duplicate-request guard used in `request.rs` (`host.request_receipt(&req).is_some()` check).
3. A relayer can resubmit the identical `PostRequest`/proof in a subsequent `RequestMessage`, causing `on_accept` to execute again from scratch — minting/transferring to the same beneficiary a second time — repeatable indefinitely as long as the calldata portion keeps failing (or even succeeds later, still after multiple credits already landed).

This produces duplicate settlement / free credit of bridged funds, matching the "duplicate-claim/double-settlement" and "wrongful asset movement" impact categories in scope.

### Title
Non-atomic on_accept allows duplicate minting/transfer via replay after calldata-dispatch failure - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` credits the beneficiary before validating/dispatching optional calldata. A calldata failure causes `on_accept` to return `Err`, which only deletes the request receipt (allowing replay) but does not revert the already-applied mint/transfer, since the ISMP request handler returns `Ok` for the overall batch regardless of per-request failures.

### Finding Description
See analysis above: mint/transfer occurs at [4](#0-3)  before calldata validation/dispatch at [5](#0-4) . The batch handler in `modules/ismp/core/src/handlers/request.rs` only deletes the receipt on error rather than rolling back all module state, and the top-level `handle()` returns `Ok` for the batch even when individual `on_accept` invocations error [6](#0-5) .

### Impact Explanation
An unprivileged sender can craft a cross-chain `Message` with a valid transfer/mint amount and a `data` field whose `SubstrateCalldata`/`runtime_call` is deliberately invalid, filtered, or dispatch-failing. Each time the message (with a fresh/valid proof — or the same request replayed since its receipt was deleted) is processed, the beneficiary is credited again, while the extrinsic overall succeeds and never reverts the credit. This is a direct fund-duplication / free-credit bug.

### Likelihood Explanation
High for an attacker controlling the source-chain message content (e.g., an EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract call) — no privileged relayer or infrastructure compromise is needed, only submission of a message whose optional calldata is intentionally malformed/filtered.

### Recommendation
Reorder `on_accept` to fully validate and prepare (but not execute) the calldata path — decode `SubstrateCalldata`, verify signature, decode `RuntimeCall`, and check `BaseCallFilter` — before performing any mint/transfer. Only after all validation succeeds should the balance-changing operations and the `runtime_call.dispatch(...)` be executed, so that any error path in `on_accept` returns before mutating balances.

### Proof of Concept
Not directly executable in this review (no test harness run), but the code path is deterministic:
1. Construct `Message { to: <victim/attacker beneficiary>, amount: <valid>, data: <SubstrateCalldata with valid signature but a runtime_call filtered by BaseCallFilter or one that fails dispatch> }`.
2. Call `on_accept` — the mint/transfer at lines 93–117 executes and commits; the `Err(HftError::CallFiltered)` or `Err(HftError::CallDispatchError(..))` is returned at line 195/200.
3. Because the enclosing `handle()` batch call in `modules/ismp/core/src/handlers/request.rs` returns `Ok` overall and only deletes the request receipt on a per-request `Err`, the mint/transfer persists and the message becomes eligible for replay, allowing the same credit to be minted again on resubmission.
