## Finding: Griefing eviction of a victim's paid bandwidth subscription via unrestricted `purchase()` targeting

### Title
Unrestricted, attacker-chosen `(app_chain, app)` targeting in `BandwidthManager.purchase()` lets anyone evict a victim's prepaid bandwidth allowance via FIFO cap eviction - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
The external report's core broken invariant is: an unprivileged actor can flood a FIFO-bounded queue with cheap, self-serving entries to force eviction/blocking of legitimate, already-paid-for entries belonging to other users, at a cost the attacker considers acceptable relative to the damage caused. The same primitive exists in `pallet-bandwidth`'s subscription ledger.

### Finding Description
`BandwidthManager.sol::purchase()` lets **any caller** specify an arbitrary `app` (recipient) and `chain` (credit chain) in the dispatched `BandwidthPurchaseMsg`, completely independent of `msg.sender`: [1](#0-0) 

This is by design ("Sponsorship" — a payer on one chain can credit an app on another chain), but it also means nothing ties the purchase to a relationship with the target app. On the pallet side, `on_accept` keys the FIFO purely off attacker-controlled fields from the message body (`msg.chain`, `msg.app`), not `request.source`: [2](#0-1) 

Every purchase — regardless of who targets whom — appends to the same bounded `SubscriptionList` (`BoundedVec`, cap `MAX_SUBSCRIPTIONS = 1024`) for that `(app_chain, app)` key: [3](#0-2) 

`push_subscription` evicts the **oldest** entry once the list is full, unconditionally, regardless of the evicted entry's remaining value: [4](#0-3) 

An attacker can call `purchase()` (or a small helper contract calling it in a loop / across many txs) 1024 times with the cheapest configured tier and `months = 1`, always targeting the same victim's `(app_chain, app)` key. Each call is legitimate, unprivileged, and requires no relayer, prover, or admin collusion — it is a plain user-facing entrypoint. Once 1024 cheap subscriptions are queued, any further purchase (including the victim's own legitimate, larger prepurchase, or subsequent top-ups) evicts the oldest entry in the queue — which, once the attacker has fully repopulated the queue with fresh purchases, is guaranteed to include real, unexpired, high-value subscriptions the victim already paid for and has not consumed. `SubscriptionEvicted` is emitted, but this is only an audit trail — there is no refund path for `lost_bytes`.

Existing guards do not stop this:
- `BandwidthManager::purchase()` has no allowlist/ownership check tying `app` to `msg.sender`.
- `pallet-bandwidth::on_accept` has no rate limit, minimum stake, or per-target quota — it only checks that `request.from` matches the registered manager and that the tier is configured.
- The FIFO cap-and-evict logic in `push_subscription` treats every purchase identically regardless of who is being credited or targeted.

This is the direct analog of the EigenLayer report: an unbounded, cheap, unprivileged action (`requestWithdraw` / `purchase`) fills a FIFO queue bound to a shared resource, forcing eviction of legitimate entries that other users already paid for, without any per-target rate limiting.

### Impact Explanation
The victim's already-paid bandwidth (real ERC-20 fee-token value transferred to `BandwidthManager` and burned toward a specific tier/duration) is destroyed with no possibility of recovery once evicted — this is a direct loss of funds for the victim app, achievable by any unprivileged third party through ordinary contract calls. Depending on tier pricing, the attacker's cost to fill 1024 slots (minimum tier price × 1024) may be substantially lower than the value of the subscriptions they destroy, especially against apps that bought high-value, long-duration tiers (e.g., the $1000/8MB tier) which can be evicted by cheap $50/1-month purchases at essentially fixed cost regardless of the victim's subscription size.

### Likelihood Explanation
The attack requires only calling a public, unauthenticated function (`purchase()`) with attacker-chosen `app`/`chain` parameters and paying the (governance-set, potentially low) tier price — no relayer, prover, governance, or leaked-key assumption is needed. The docs themselves acknowledge the FIFO/cap-and-evict design ("pushing onto a full list evicts the oldest entry") is reachable via repeat-buy behavior and only assume it is impractical "at the default of one purchase per cycle" — an assumption that does not hold against a motivated attacker willing to pay tier price 1024 times.

### Recommendation
Bind purchases to a relationship between payer and target (e.g., require `app` to equal `msg.sender`, or maintain a separate allowance/sponsor-approval list per target app), and/or scope the FIFO cap and eviction fairness per payer rather than per `(chain, app)` so an unrelated payer cannot force eviction of another payer's unconsumed subscriptions. Alternatively, evict only expired/lowest-value entries first, or refund `lost_bytes` pro-rata to the original payer when forcibly evicted before expiry.

### Proof of Concept
1. Attacker deploys/uses an EOA with enough fee-token balance for `1024 * tierPrice[cheapestTier]`.
2. Attacker calls `BandwidthManager.purchase(app = <victimAppBytes>, tier = cheapestTier, months = 1, chain = <victimAppChain>)` 1024 times (loop or scripted), each dispatching a `BandwidthPurchaseMsg` to `pallet-bandwidth`.
3. Each message is accepted by `on_accept` (no ownership check on `msg.app`/`msg.chain`), appending to `Allowance[(victimAppChain, victimApp)]` per `push_subscription`, per [2](#0-1) .
4. Once the list is at the 1024 cap, any subsequent purchase — including a legitimate, high-value purchase later made for the victim — causes `push_subscription` to evict the oldest entry (`list.remove(0)`), per [5](#0-4) ; repeating attacker purchases will progressively evict every legitimate subscription the victim previously bought that is still in the queue, emitting `SubscriptionEvicted` for each with no refund mechanism.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
