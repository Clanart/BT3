### Title
Scanner only matches exact P2TR script_pubkey equality, with no recovery path for outputs sent to the multisig key under any other encoding — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report concerns a vault that can receive an asset class (ERC721) it has no function to recover. The Serai analog lives in `bitcoin-serai`'s wallet scanning and spending pipeline: `Scanner::scan_transaction` recognizes a deposit solely by exact `script_pubkey` equality against a fixed set of registered P2TR scripts, and `SignableTransaction`/`TransactionMachine` can only spend `ReceivedOutput`s via BIP-340 key-path Schnorr signatures. Any unprivileged sender can pay the multisig's key material under a different output encoding — a script-path-tweaked P2TR output committing to the same internal key, a P2WPKH/P2SH-wrapped encoding of the same key hash, or a P2TR address derived from the odd-parity form of the group key — and the output is both invisible to the scanner and unspendable by the only signing path that exists. There is no recovery or sweep mechanism, so such funds are permanently locked and uncredited.

### Finding Description
`Scanner` stores a `HashMap<ScriptBuf, Scalar>` and detects outputs purely by `self.scripts.get(&output.script_pubkey)` [1](#0-0) . The only scripts ever registered are `p2tr_script_buf(key)` (a tweak-assumed P2TR script built with `dangerous_assume_tweaked`, i.e., no merkle root) and a handful of `register_offset` variants [2](#0-1) [3](#0-2) . The processor constructs the scanner with exactly four offsets (`External`, `Branch`, `Change`, `Forwarded`) and looks up `kinds[offset_repr]`, indexing blindly [4](#0-3) [5](#0-4) .

On the spending side, `SignableTransaction::multisig` verifies the prevout's `script_pubkey` equals `p2tr_script_buf(offset.group_key())` and produces only key-path `taproot_key_spend_signature_hash` signatures [6](#0-5) [7](#0-6) . Every valid Bitcoin output type that can encumber the same key material — a P2TR output `Q = P + H(P||root)G` with a real script tree over internal key `P`, a P2WPKH/`OP_EQUAL` script over the same key hash, or the odd-parity x-only encoding — falls outside both the scan set and the signature capability. `Scanner::new` additionally returns `None` for odd keys, so even the canonical-path scanner cannot be instantiated for the alternate parity encoding [8](#0-7) .

There is no function anywhere in `bitcoin-serai` analogous to an ERC721 `transferToVault` — no script-path spend, no ECDSA path, no sweep of unregistered scripts.

### Impact Explanation
Any external Bitcoin user can send BTC to an output that commits to the multisig's key but is neither detected by `get_outputs` nor spendable by `TransactionMachine`. Two consequences:

- **Permanently locked funds.** A sender paying `Q = group_key + H(group_key || root)G` with an arbitrary merkle root creates an output whose key-path spend requires a tweak scalar the multisig does not know, and whose script path is controlled by the sender. The funds are unrecoverable by anyone else and are never credited.
- **Unspendable-but-related deposits.** Even where the underlying secret could theoretically spend an alternate encoding (e.g., a legacy script keyed to the same group key), no code path exists to construct or sign such a spend — the `ReceivedOutput` → `SignableTransaction` pipeline only ever emits key-path Taproot witnesses.

In a custody/bridge context where depositors expect refunds or crediting of anything sent to the vault key, this is a Medium-severity permanent loss vector for assets that reach the key outside the four recognized scripts.

### Likelihood Explanation
The trigger requires only that an unprivileged Bitcoin sender craft a non-standard output — entirely within their power and costing only their own funds. It does not require validator misbehavior, collusion, or malformed infrastructure. Whether it is "accidental" (a user paying the vault's x-only key via an incompatible wallet encoding) or deliberate (griefing by locking funds against the key), the outcome — funds at the multisig's key that are neither credited nor recoverable — is identical and is guaranteed by the exact-match `HashMap` lookup plus the absence of any alternate spend path.

### Recommendation
Document explicitly which output encodings are recognized, and add one of: (a) a recovery/sweep path in `SignableTransaction` capable of spending outputs committed to the group key under alternate scripts (e.g., a script-path leaf `key OP_CHECKSIG`, which would also reclaim tree-tweaked deposits), or (b) a coordinator-facing API to register additional script templates in `Scanner::scripts` with their required offsets/tweaks, so `get_outputs`/`kinds` never silently drops a deposit committed to the vault key. At minimum, reject or alert on-chain monitoring for outputs paying `Q` derivable from the group key.

### Proof of Concept
An external sender computes `P = group_key` (public, even-parity after `tweak_keys`), picks an arbitrary leaf script/merkle root `r`, and pays to `P2TR(P + H(P||r)·G)` or to a P2WPKH script over `P`. The transaction confirms. `get_outputs` iterates `block.txdata[1..]`, calls `scanner.scan_transaction`, and `self.scripts.get(&output.script_pubkey)` returns `None` — the output is never emitted. Even if it were manually added to a `SignableTransaction` as a `ReceivedOutput`, `multisig()` would return `None` at the `p2tr_script_buf(offset.group_key())? != prevout.script_pubkey` check, and no other signing path exists. The BTC is permanently unspendable and uncredited.

  /// Register an offset to scan for.
  ///
  /// Due to Bitcoin's requirement that points are even, not every offset may be used.
  /// If an offset isn't usable, it will be incremented until it is. If this offset is already
  /// present, None is returned. Else, Some(offset) will be, with the used offset.
  ///
  /// This means offsets are surjective, not bijective, and the order offsets are registered in
  /// may determine the validity of future offsets.
  ///
  /// The offsets registered must be securely generated. Arbitrary offsets may introduce a script
  /// path into the output, allowing the output to be spent by satisfaction of an arbitrary script
  /// (not by the signature of the key).
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),

    OutputType::Change,

  );
