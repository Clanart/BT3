### Title
Panic on identity aggregate nonce in BIP-340 `hram` aborts honest signers via crafted FROST preprocesses - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
The CVE class is a crafted-input parser bug that yields denial of service (and, in C, information disclosure). In Serai's memory-safe code the reachable analog is a hard panic on attacker-supplied bytes rather than an OOB read. The concrete instance is in the Bitcoin Schnorr algorithm: `Hram::hram` calls `x()`/`x_only()`, which `expect` on a non-infinity point, while the FROST pipeline places no identity check on the summed nonce commitments `R` derived from peer-supplied preprocesses.

### Finding Description
`Hram::hram` hashes `x(R)`, `x(A)`, and `m`, where `x()` is defined as `(*encoded.x().expect("point at infinity"))` — a documented panic on the identity point (crypto.rs:13–15, 59–72). `R` is the sum of each included participant's nonce commitments, which come from `Preprocess`/`Commitments` structures deserialized by `read_preprocess` from bytes supplied by other signers (`TransactionSignMachine::sign`, `networks/bitcoin/src/wallet/send.rs:355–398`, and `AlgorithmSignatureMachine`/`AlgorithmSignMachine` in `crypto/frost/src/sign.rs`). A grep of `crypto/frost/src/sign.rs` shows no `is_identity` check anywhere in the sign/commitment path, and `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs`) decodes points without rejecting the identity encoding. A malicious participant in a Bitcoin threshold signing session can therefore choose nonce commitments that sum to the point at infinity (e.g., negating the honest participants' summed commitments), causing `x()` to panic inside `sign_share` on every honest `TransactionSignMachine::sign` call — crashing the processor task instead of returning a `FrostError`.

### Impact Explanation
An unprivileged participant whose only capability is submitting a preprocess (untrusted bytes reaching `read_preprocess`, then `sign`) can deterministically abort honest signers' signing path via an unhandled panic. This halts threshold signing for that session (and kills the executing task), a reachable denial of service analogous to the CVE's DoS primitive. The information-disclosure half of the CVE does not port — Rust prevents adjacent-memory reads — so severity is capped at Medium rather than High.

### Likelihood Explanation
Requires a participant already admitted into a signing set for a Bitcoin multisig (an untrusted party in the threat model, since preprocessing messages are peer-supplied). The exploit is deterministic and costless: one crafted preprocess whose commitments force `sum(nonces) = ∞`. Caveat: I did not fully verify whether `modular-frost`'s `Commitments`/`BindingFactor` path in `crypto/frost` rejects an identity aggregate earlier in `sign` before `sign_share` invokes `hram` — `sign.rs` contains no identity checks, but a rejection inside the `Algorithm` internals (e.g., in `IetfSchnorr::sign_share` before `Hram::hram` is called) would reduce reachability to a misparse error instead of a panic. The panic itself is confirmed by the explicit `expect("point at infinity")` and doc comments.

### Recommendation
Reject the point at infinity at deserialization and aggregation time: check `R.is_identity()` (and each nonce commitment) before calling `hram`, returning `FrostError::InvalidPreprocess(l)` for the offending participant instead of panicking; alternatively make `x()`/`x_only()` return `Option`/`Result` and propagate.

### Proof of Concept
1. Victim constructs a Bitcoin `SignableTransaction` and `TransactionSignMachine` via `SignableTransaction::multisig` + `preprocess`.
2. Attacker (a `Participant` in `included`) submits a `Preprocess` whose `Commitments.nonces` are chosen as `-(Σ honest commitments)`, delivered as raw bytes into `read_preprocess`.
3. Victim calls `TransactionSignMachine::sign(commitments, b"")` → `Schnorr::sign_share` → `Hram::hram(R = ∞, A, m)` → `x()` hits `expect("point at infinity")` (`networks/bitcoin/src/crypto.rs:15`) → panic aborts the signing task instead of producing `FrostError::InvalidPreprocess(attacker)`.
