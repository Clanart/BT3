### Title
Governance-settable `kip71.gastarget = 0` causes division-by-zero panic in `NextMagmaBlockBaseFee` (KIP-71 pricing) - ([File: params/kip71_config.go])

### Summary
`KIP71Config.GasTarget` is a governance-controlled parameter with no non-zero validation (`noopFormatChecker`), unlike its sibling parameter `BaseFeeDenominator`, which is explicitly protected against zero. When `GasTarget == 0`, `NextMagmaBlockBaseFee()` divides by `gasTarget` in `math/big` arithmetic, which panics on division by zero for any block with `parentGasUsed > 0`. This mirrors the reported bug class: an unchecked divisor/interpolation input (curve values in the original finding vs. `GasTarget` here) that is fully attacker/governance-controllable and used unguarded in a hot financial-calculation path, causing a denial-of-service.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee (KIP-71 dynamic pricing): [1](#0-0) 

```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
baseFeeDelta := math.BigMax(x.Div(y, baseFeeDenominator), common.Big1)
```
and the symmetric decreasing-usage branch: [2](#0-1) 

Both branches divide by `gasTarget` with no guard. Go's `big.Int.Div` panics with "division by zero" when the divisor is zero.

The developers were clearly aware of this exact hazard for the sibling parameter `BaseFeeDenominator`, adding both a strict format checker and a defensive runtime fallback: [3](#0-2) [4](#0-3) 

But the equivalent protection is missing for `GasTarget`, which uses `noopFormatChecker`: [5](#0-4) 

This is directly analogous to the Merit Circle finding: `getMultiplier()` in `TimeLockPool.sol` divided by `curve[n+1] - curve[n]` with no check that the divisor was non-zero, because `setCurvePoint()`/`setCurve()` lacked validation. Here, `Kip71GasTarget`'s setter (`param.go`) lacks the same class of validation that its sibling parameter (`BaseFeeDenominator`) explicitly has, and the consuming function (`NextMagmaBlockBaseFee`) divides unconditionally by the unguarded value.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked both to compute the header's expected base fee during block preparation/verification (`VerifyMagmaHeader`) and to build new blocks. If governance sets `kip71.gastarget = 0` (a legitimate governance parameter update path within the KIP-71 pricing category), then the very next block whose parent used any nonzero gas (virtually every block, since `parentGasUsed == gasTarget(0)` is the only safe path) will trigger a division-by-zero panic in every node that processes that block header — both when validating the incoming block and when a validator attempts to build the next block. This produces a chain-wide crash/halt across all conforming nodes simultaneously, which is a critical denial-of-service to the KIP-71 pricing and block-assembly pipeline, consistent with the "possible DOS due to unchecked divisor" bug class in the source report.

### Likelihood Explanation
Setting `GasTarget` requires a governance parameter update, which is an in-scope category explicitly called out ("governance parameters," "KIP-71 pricing"). No additional validation exists anywhere in the vote/format-checking pipeline (`Kip71GasTarget`'s `FormatChecker` is a no-op) to reject a zero value, whereas the neighboring `BaseFeeDenominator` parameter has exactly this protection, indicating this is a genuine oversight rather than an intentionally permitted value. Once set, the panic condition triggers deterministically on the very next block with nonzero gas usage — an operationally trivial trigger with no special timing or race condition required.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (mirroring `Kip71BaseFeeDenominator`) rejecting `0`, e.g. `return ok && v != 0`. Additionally, add a defensive runtime fallback in `NextMagmaBlockBaseFee` analogous to the existing `BaseFeeDenominator == 0` guard, so that a `GasTarget` of zero cannot cause a division-by-zero panic even if it slips through parameter validation.

### Proof of Concept
1. Governance submits and finalizes a vote setting `kip71.gastarget = 0` (no format check rejects this, per `kaiax/gov/param.go` `Kip71GasTarget` entry using `noopFormatChecker`).
2. On the next block after the parameter activates, assume `parentHeaderGasUsed > 0` (true for essentially any active chain).
3. In `NextMagmaBlockBaseFee`, `gasTarget = 0`; since `parentGasUsed != gasTarget` and `parentGasUsed > gasTarget` is true, execution reaches:
   `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`.
4. `big.Int.Div` panics with "division by zero", crashing the node during header verification/finalization — reproducible on every full node and validator processing that block, causing a full chain halt.
