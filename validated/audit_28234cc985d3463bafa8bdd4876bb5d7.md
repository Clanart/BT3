Based on my investigation, I found a concrete, code-supported analog worth reporting. I could not fully verify end-to-end exploitability against every git-internal protection (e.g. whether Git's tree-object format blocks `..` components — it does, but it does **not** block symlinks), so I flag that caveat explicitly in the write-up below.

### Title
Untrusted repository symlinks allow file-open operations to escape the repository root - (File: `app/src/lib/app-shell.ts`, `app/src/ui/app.tsx`)

### Summary
GitHub Desktop already has a hardened, symlink-aware path-containment helper, `resolveWithin` [1](#0-0) , which is used specifically when handling attacker-influenced input — the `filepath` query parameter of the `x-github-client://openRepo` deep link [2](#0-1) . That code path explicitly calls `realpath()` on both the root and the resolved target and rejects the result unless it is still contained, precisely to defeat symlink-based escapes.

However, several other code paths that build a full file path from repository-relative, attacker-influenced strings (file paths coming from a cloned/checked-out commit or PR diff) skip this hardening and use plain `Path.join()` instead:
- `revealInFileManager()` [3](#0-2) 
- `onOpenInExternalEditor()` in the main app component [4](#0-3) 
- Commit/PR file context menus that build `fullPath` the same way and pass it to `openInExternalEditor`, `revealInFileManager`, or "Open with default program" [5](#0-4) [6](#0-5) 

### Finding Description
`Path.join(repository.path, path)` normalizes `..` segments syntactically but performs no filesystem-level containment check. It does not resolve symlinks. Git's tree-object format itself forbids a path *component* literally named `..`, but it does **not** forbid a tracked file or directory from being a **symlink** whose target points outside the repository (e.g. a tracked entry `evil` with `symlink -> /` or `symlink -> ../../../..`). When a user clones or checks out a commit/branch/PR containing such an entry, and Desktop lists a file whose relative path traverses through that symlinked component (e.g. `evil/passwd`), `Path.join(repository.path, 'evil/passwd')` produces a path string that lexically looks contained under the repo root, but which the OS will actually resolve outside of it because of the symlink.

This is the same broken invariant as the Sherlock report: a downstream action (voting / opening a file) is performed without validating a precondition (having votes / staying inside the repo) that a sibling code path *does* validate. Here, `openRepositoryFromUrl` validates containment with `resolveWithin` [7](#0-6) , while `revealInFileManager`, `onOpenInExternalEditor`, and the commit/PR file context-menu handlers do not.

### Impact Explanation
An attacker who controls a repository the user clones, or a fork whose PR/commit the victim views inside Desktop, can plant a symlink pointing at a sensitive location outside the repo (home directory, SSH keys directory, etc.), then rely on ordinary UI affordances (Changes list, History view, PR "Files changed" view) — "Reveal in Finder/Explorer", "Open in <editor>" — to have Desktop hand a path outside the repository to `shell.showItemInFolder`, the external editor, or (via "Open with default program", gated only by `isSafeExtension`, not by containment) the OS default handler. Depending on target and OS handler, this can expose/reveal or execute content outside the intended repository sandbox — matching the “file write or read outside the repo” / code-execution class explicitly listed as valid impact.

### Likelihood Explanation
Requires no special privileges beyond convincing/getting the user to clone or open a PR/branch from an attacker-controlled repository — a normal Desktop workflow. It does require a user interaction (opening a context menu and clicking "Reveal"/"Open in editor"), which is a legitimate part of Desktop's own UI, not an "unnatural" step. The scenario is somewhat mitigated by requiring the victim to specifically act on the malicious file entry, and by the fact that this is unverified against additional runtime protections Desktop may apply during checkout of symlinks (e.g. `core.symlinks` handling on Windows), which I was not able to confirm from the indexed code.

### Recommendation
Route all repository-relative paths that originate from tracked/checked-out content (commit diffs, PR file lists, working directory changes) through the same `resolveWithin`/`resolveWithinPosix` containment check used by `openRepositoryFromUrl` before calling `shell.showItemInFolder`, `openInExternalEditor`, or `shell.openPath`, rejecting (and logging) any path whose real, symlink-resolved location falls outside `repository.path`.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink `payload -> /Users/victim/.ssh` (or another sensitive path) plus a file at `payload/somefile`.
2. Victim clones the repository, or opens the attacker's fork/PR/branch containing that commit inside Desktop.
3. Victim opens the Changes list, History view, or the PR "Files changed" view and right-clicks the entry shown for the tracked path under `payload/`, selecting "Reveal in Finder/Explorer" or "Open in <editor>".
4. `revealInFileManager`/`onOpenInExternalEditor` build the path via `Path.join(repository.path, 'payload/somefile')` [3](#0-2)  with no `resolveWithin` check, so the OS resolves the symlink and the file manager/editor is launched against `~/.ssh/somefile`, outside the repository — unlike the `openRepositoryFromUrl` flow, which would reject the equivalent traversal via `resolveWithin` [2](#0-1) .

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
