### Title
`get-asset-price` prices stSTXbtc/zstSTXbtc collateral and debt using the STX feed instead of the BTC feed - ([File: mainnet/contracts/utility/v0-1-data.clar])

### Summary
### Finding Description
The read-only position/health reporting path resolves the price of the `stSTXbtc` and `zstSTXbtc` assets by calling the STX Pyth feed (`PYTH-STX`) while the surrounding comments and variable names claim it is fetching the BTC price: [1](#0-0) 

```
;; stSTXbtc - BTC price (liquid staked STX with BTC yield)
(if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-STX))
;; zstSTXbtc - stSTXbtc price x liquidity index
(if (is-eq aid zstSTXbtc)
    (let ((btc-price (default-to u0 (get-pyth-price PYTH-STX)))
          (lindex (get-vault-liquidity-index stSTXbtc)))
      (mul-div-down btc-price lindex INDEX-PRECISION))
```

The identical bug is duplicated verbatim in the sibling `protocol-data.clar` helper: [2](#0-1) 

Both `get-asset-price` implementations are consumed by `sum-collateral-usd`/`sum-debt-usd`, which in turn feed `get-user-position`'s `total-collateral-usd`, `total-debt-usd`, `current-ltv`, `health-factor`, and `is-liquidatable` fields: [3](#0-2) 

Because `PYTH-STX` and `PYTH-BTC` are distinct constants with wildly different USD values, the code silently attaches the STX/USD price to the stSTXbtc-denominated collateral/debt instead of the BTC/USD price: [4](#0-3) 

### Impact Explanation
Direction of the error: any position holding `stSTXbtc`/`zstSTXbtc` as collateral or debt has its USD notional computed with the (much lower) STX price instead of the (much higher) BTC price, understating that leg's USD value by orders of magnitude.
- If held as collateral: `total-collateral-usd` and `health-factor` are understated, and `is-liquidatable` can be incorrectly reported `true` for a genuinely healthy position — this benefits whoever monitors/acts on this endpoint to trigger unwarranted liquidations (attacker/liquidator profits at the healthy user's expense), analogous to the referenced report's "unfairly penalizes a solvent party due to a miscalculated value."
- If held as debt: `total-debt-usd` and health metrics are understated, letting an actually-unhealthy borrower's position be reported healthy — delaying liquidation and risking bad debt / protocol insolvency, which benefits the borrower at the protocol's/lenders' expense.

This lands on the in-scope impact class of temporary freezing of funds (delayed/blocked liquidation of at-risk debt, or forced/unjustified liquidation of solvent collateral) depending on which side of the position holds the mispriced asset.

### Likelihood Explanation
The bug requires no attacker action beyond holding or borrowing the `stSTXbtc`/`zstSTXbtc` asset, which is a normal, currently-supported vault asset per `mainnet/contracts/vault/v0-vault-ststxbtc.clar` and the `v0-init.clar` proposal registering it. Since this exact wrong-feed code is duplicated in two separate contracts (`v0-1-data.clar` and `protocol-data.clar`), it is not an isolated typo but a systemic copy-paste defect. Likelihood of the defect being live in a deployed helper is high; likelihood of exploitation depends on whether external liquidator bots or the front-end health/liquidation flow rely on this `get-user-position`/`is-liquidatable` output as their source of truth, which I could not fully confirm from the indexed code (the on-chain enforcement path in `market.clar`'s `borrow`/`liquidate` functions appears to resolve prices via the `.assets` registry's per-asset oracle configuration rather than this hardcoded helper, so the blast radius may be limited to whichever consumer trusts this read-only reporting contract).

### Recommendation
In `mainnet/contracts/utility/v0-1-data.clar` (and the duplicate in `local-testing/contracts/utility/protocol-data.clar`), change both occurrences of `(get-pyth-price PYTH-STX)` under the `stSTXbtc` and `zstSTXbtc` branches to `(get-pyth-price PYTH-BTC)`, matching the surrounding comments and intended asset semantics. Add a regression test asserting that `get-asset-price` for `stSTXbtc`/`zstSTXbtc` tracks the BTC feed and diverges from the STX feed.

### Proof of Concept
1. Register/hold `stSTXbtc` (or `zstSTXbtc`) collateral or debt for an account.
2. Call the read-only `get-user-position` (or `sum-collateral-usd`/`sum-debt-usd` internally) and observe that the USD valuation of the `stSTXbtc`/`zstSTXbtc` leg is computed from `PYTH-STX`'s price rather than `PYTH-BTC`'s price — verifiable directly from the code at `mainnet/contracts/utility/v0-1-data.clar:588-594`, where the `btc-price` binding literally calls `get-pyth-price PYTH-STX`.
3. Given STX/USD ≪ BTC/USD in practice, the reported collateral/debt USD value, `health-factor`, and `is-liquidatable` flag for any account holding this asset will be grossly wrong in the direction described above.

**Note:** I was unable to fully confirm from the indexed files whether `market.clar`'s on-chain `borrow`/`liquidate` enforcement path (which resolves prices via the `.assets` registry's per-asset `oracle` field rather than this hardcoded helper) is also affected, or whether this defect is confined to the `v0-1-data.clar`/`protocol-data.clar` read-only reporting utilities. If a full-repository check is needed to trace all consumers of `get-user-position`/`is-liquidatable`, a Devin session with full file access would be required to verify this conclusively.
