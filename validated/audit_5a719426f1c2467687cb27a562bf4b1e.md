### Title
Partial-Commit Line Selection Applied to a Freshly-Fetched Diff Without Re-Validating Hunk Positions Against the Selection That Produced It — Silent Corruption of Committed Content - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets a user select individual diff lines to include in a commit (`DiffSelection`, stored as a positional bitmask of absolute line indices). When the commit is actually staged, `applyPatchToIndex` re-fetches the diff from disk **at commit time**, then reuses the user's positional selection (computed against whatever diff was on screen when they clicked lines) to build the patch. There is no check that the freshly fetched diff has the same hunk layout/line positions as the diff the selection was made against. If the file's on-disk content changes between the time the diff was displayed/selected and the time the commit is executed, the selection bitmask is silently re-applied to different line positions, causing the wrong lines to be staged and committed — without any warning to the user. This mirrors the Oval bug class: two reads of related state ("the diff shown" and "the diff used to build the patch") that are supposed to be consistent, but aren't guaranteed to be, producing divergent/incorrect output for what should be one atomic operation.

### Finding Description
`applyPatchToIndex` fetches a brand-new diff and immediately combines it with the file's existing `selection` object: [1](#0-0) 

That selection is a positional bitmask over "absolute diff line index," originally computed by the UI against a diff that was displayed to the user at some earlier point (see `selectableLines`/`unifiedDiffStart` indexing used throughout the diff view): [2](#0-1) 

`formatPatch` then walks the **new** diff's hunks and lines and asks `file.selection.isSelected(absoluteIndex)` for each line, using the new diff's line positions: [3](#0-2) 

Nowhere in this path is there a check that the diff fetched inside `applyPatchToIndex` is structurally identical (same hunk boundaries/line counts) to the diff the selection was computed against. Compounding this, the working-directory diff cache explicitly reuses a previously fetched diff across status refreshes purely by matching the file's `id` (its path-derived key), with no verification that the underlying file content is unchanged: [4](#0-3) 

So the invariant the app implicitly relies on — "the positional selection the user made corresponds to the diff that will be turned into a patch" — can be broken by anything that mutates the working tree file between diff-display and commit-execution (e.g., a background process spawned from the repository such as an npm `postinstall`/build script, an editor auto-format-on-save extension, or a `post-checkout`/`post-merge` hook triggered by repository content). The commit flow does not re-diff-and-re-validate the selection against the new diff before formatting the patch; it just re-fetches a diff and blindly re-applies the old positional bitmask.

### Impact Explanation
This falls under "silent corruption of what the user commits" from the valid-impact list. If hunk boundaries shift (e.g., lines added/removed elsewhere in the same file) between the time the user reviewed/selected lines and the time Desktop builds the actual patch, the resulting commit can:
- Include lines the user never reviewed or approved (attacker-controlled content silently committed), or
- Exclude lines the user intended to include, or
- Produce a patch that partially corresponds to neither the reviewed diff nor the current file state.

Because this happens without any error or warning, the user has no signal that what was committed differs from what they approved in the UI.

### Likelihood Explanation
Exploitation requires a way to change file content on disk in the (short) window between the UI's diff computation and `applyPatchToIndex`'s diff computation. This is plausible via content that ships with a cloned/fetched attacker-controlled repository (build scripts, hooks, file watchers commonly present in JS/TS projects) rather than requiring local/physical access or pre-existing malware — matching the allowed attacker model ("attacker controls a cloned/fetched repository"). That said, I was not able to fully trace every caller of `applyPatchToIndex` (e.g., exact timing between `_selectWorkingDirectoryFiles`/diff caching and the commit dispatcher call) within the available search budget, so the precise race window size and whether any other layer (e.g., `git status` recheck before commit) partially mitigates this could not be fully confirmed from the indexed code alone.

### Recommendation
Before generating the patch, re-validate that the diff used for the patch (`getWorkingDirectoryDiff` result inside `applyPatchToIndex`) structurally matches the diff the current `file.selection` was computed against (e.g., by storing a content hash or the diff's hunk signature alongside the selection, similar to `entryIsEligibleForRefresh`-style staleness checks used elsewhere) and abort/re-prompt the user if it doesn't match, rather than silently reusing stale positional selection state against new diff content.

### Proof of Concept
Conceptual reproduction (not independently executed due to lack of terminal/filesystem access in this environment):
1. Clone/open a repository containing a script that appends/removes lines to a tracked file shortly after checkout (e.g., via an npm `postinstall` hook or a background watcher process bundled in the repo).
2. Modify the file, view its diff in GitHub Desktop, and select only specific lines/hunks for a partial commit.
3. Trigger the repository's background script to mutate the same file (adding/removing lines above the selected hunk) right before clicking "Commit".
4. Observe that `applyPatchToIndex` re-fetches the diff and applies the old positional selection (`app/src/lib/git/apply.ts` line 60, `app/src/lib/patch-formatter.ts` lines 143-157) to the new hunk layout, producing a commit whose actual staged content differs from what was shown/approved in the UI.
