### Title
CAT wallet accepts a `puzzle_decorator_override` for Clawback but never applies it, causing clawback-decorated CAT sends to skip the decorator while the RPC layer allows requesting it - (File: chia/wallet/cat_wallet/cat_wallet.py)

### Summary
The `CreateSignedTransaction` RPC / `create_signed_transaction` endpoint in `chia/wallet/wallet_rpc_api.py` explicitly permits `Wallet`, `CATWallet`, `CRCATWallet`, and `RCATWallet` and forwards a caller-supplied `puzzle_decorator_override` (Clawback settings) to `wallet.generate_signed_transaction(...)`. [1](#0-0)  However, only the base `Wallet` (standard XCH wallet) implementation of `_generate_unsigned_transaction` actually consults `decorator_manager.decorate_target_puzzle_hash(...)` / `decorator_manager.solve(...)` to wrap the output puzzle hash in the Clawback `p2_1_of_n` merkle puzzle and attach the `REMARK` metadata condition. [2](#0-1) [3](#0-2)  `CATWallet.generate_signed_transaction` / `generate_unsigned_spendbundle`, by contrast, builds `CreateCoin` payments directly from the caller-provided `puzzle_hashes` and never reads `kwargs["puzzle_decorator_override"]` or calls into `self.wallet_state_manager.decorator_manager` at all. [4](#0-3) 

### Finding Description
This is the analog of the OpenQ bug: an entity path (RPC request, `CreateSignedTransaction.puzzle_decorator` field, which is explicitly documented as "only Clawback is supported") [5](#0-4)  is exposed for CAT wallets, but the downstream CAT spend-generation code silently drops the decorator instead of applying it or rejecting the request. On the flip side, once a coin *is* correctly clawback-wrapped (i.e., created via the standard `Wallet`), the claim/claw-back path in `ClawbackManager.spend_clawback_coins` is hard-coded to only ever look up `CoinType.CLAWBACK` records filtered by `wallet_type=WalletType.STANDARD_WALLET`, and always constructs the recipient/sender inner puzzle via `self.xch_wallet.puzzle_for_pk(...)` (the plain p2_delegated puzzle). [6](#0-5) [7](#0-6)  There is no code path in `ClawbackManager` or `CATWallet`/`NFTWallet` that knows how to identify or spend a Clawback-wrapped CAT or NFT coin: `WalletStateManager.determine_coin_type` calls `match_clawback_puzzle` on the *outer* puzzle only, and immediately routes to `self.clawback_manager.identify(...)`, which always stores the record under `WalletType.STANDARD_WALLET`/`self.xch_wallet` regardless of what asset is actually wrapped. [8](#0-7) [9](#0-8) 

This mirrors the OpenQ finding structurally: the system offers/accepts a generic wrapping mechanism (Clawback puzzle decorator; OpenQ's NFT deposit) for an asset class it has no corresponding claim logic for (CAT/NFT clawback claims; OpenQ's `_claimOngoingBounty` NFT claims), so value that legitimately enters through one path (a Clawback-wrapped CAT/NFT coin, however it is created — e.g., manually crafted spend bundle, or third-party wallet software implementing the general Clawback puzzle spec) has no supported code path to be claimed via this wallet's `spend_clawback_coins`.

### Impact Explanation
If a CAT or NFT coin is ever wrapped by the generic `p2_1_of_n` Clawback puzzle (the puzzle mechanism itself is asset-agnostic — it only wraps an inner puzzle hash and enforces a timelock via merkle proof, as seen in `create_merkle_puzzle`/`create_merkle_solution`) [10](#0-9) , this wallet's automatic/manual claim and claw-back machinery (`auto_claim_coins`, `spend_clawback_coins`, the `spend_clawback_coins` RPC) cannot correctly recognize or reconstruct the inner CAT/NFT layer solution needed to release it — it unconditionally uses the plain XCH inner puzzle and filters strictly by `WalletType.STANDARD_WALLET`. [11](#0-10)  This would either fail silently (funds appear un-claimable through this wallet) or, if such a coin's record were coerced into the `CoinType.CLAWBACK`/`STANDARD_WALLET` path, produce an invalid spend attempting to treat a CAT/NFT-wrapped coin as bare XCH. Separately, the dead/no-op `puzzle_decorator_override` handling in `CATWallet.generate_signed_transaction` means a wallet user who requests Clawback protection for a CAT send via `cat_spend`/`create_signed_transaction` silently does not get it, sending CATs as a normal unprotected transfer while believing it is clawback-protected — a functional/trust gap rather than a direct fund-loss primitive by itself.

### Likelihood Explanation
Direct exploitation purely through this wallet's own CAT/NFT sending UI is unlikely today because `CATWallet.generate_signed_transaction` never actually curries a Clawback wrapper onto a CAT coin (it silently ignores the override), so the wallet itself won't normally create a CAT/NFT coin wrapped by the Clawback puzzle. However, the underlying `p2_1_of_n` Clawback puzzle is a fully generic wrapper independent of the wrapped asset type, and any external tool, interoperable wallet implementation, or crafted spend bundle following the same Clawback puzzle spec could create a CR/CAT/NFT coin under this puzzle and send it to a chia-blockchain wallet user, who would then have no reliable claim path via `spend_clawback_coins`/auto-claim. I was not able to fully verify from the indexed code whether any additional guard exists elsewhere (e.g., in `NFTWallet` or `CRCATWallet`) that explicitly rejects or specially handles Clawback-wrapped non-XCH coins during sync, so likelihood should be treated as uncertain pending closer manual review of `determine_coin_type` and coin-type identification order across all wallet types.

### Recommendation
Either (1) make `CATWallet`/`CRCATWallet`/`RCATWallet`/`NFTWallet` generate_signed_transaction implementations consult `puzzle_decorator_override`/`wallet_state_manager.decorator_manager` and correctly curry the Clawback (or any) decorator into their asset-specific inner puzzle and reconstruct it symmetrically on claim, or (2) explicitly reject/ignore-with-error any `puzzle_decorator` requests routed to non-standard wallets in `create_signed_transaction`, and (3) extend `ClawbackManager.identify`/`spend_clawback_coins` (or add a parallel per-asset-type clawback manager) to detect the wrapped asset type from the coin's parent spend and reconstruct the correct inner puzzle/solution (CAT layer, singleton/NFT layer, etc.) instead of unconditionally assuming `WalletType.STANDARD_WALLET` and `self.xch_wallet.puzzle_for_pk`.

### Proof of Concept
A concrete PoC would require constructing a spend bundle that creates a coin whose puzzle is `create_merkle_puzzle(timelock, sender_ph, recipient_ph)` wrapping a CAT or singleton/NFT outer puzzle (rather than a bare `p2_delegated_puzzle_or_hidden_puzzle` puzzle hash) and submitting it to a synced full node, then observing that `WalletStateManager.determine_coin_type` → `ClawbackManager.identify` records it as `WalletType.STANDARD_WALLET`/`CoinType.CLAWBACK`, and that calling `spend_clawback_coins` on it produces an invalid/incorrect spend (since `generate_clawback_spend_bundle` is given `self.xch_wallet.puzzle_for_pk(...)` as the inner puzzle instead of the actual CAT/NFT inner puzzle). I could not execute this against a live simulator within this investigation; this should be validated with a `chia/_tests/wallet/clawback` style simulator test analogous to `test_clawback_lifecycle.py`, substituting a CAT/singleton-wrapped coin for the plain XCH coin used there. [12](#0-11)

```python
def create_merkle_puzzle(timelock: uint64, sender_ph: bytes32, recipient_ph: bytes32) -> Program:
    merkle_tree = create_clawback_merkle_tree(timelock, sender_ph, recipient_ph)
    puzzle: Program = P2_1_OF_N.curry(merkle_tree.calculate_root())
    return puzzle


def create_merkle_solution(
    timelock: uint64,
    sender_ph: bytes32,
    recipient_ph: bytes32,
    inner_puzzle: Program,
    inner_solution: Program,
) -> Program:
    """
    Recreates the full merkle tree of a p2_1_of_n clawback coin. It uses the timelock and each party's
    puzhash to create the tree.
    The provided inner puzzle must hash to match either the sender or recipient puzhash
    If it's the sender, then create the clawback solution. If it's the recipient then create the claim
    solution.
    Returns a program which is the solution to a p2_1_of_n clawback.
    """
    merkle_tree = create_clawback_merkle_tree(timelock, sender_ph, recipient_ph)
    inner_puzzle_hash = inner_puzzle.get_tree_hash()
    if inner_puzzle_hash == sender_ph:
        cb_inner_puz = create_p2_puzzle_hash_puzzle(sender_ph)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_p2_puzzle_hash_solution(inner_puzzle, inner_solution)
    elif inner_puzzle_hash == recipient_ph:
        condition = [80, timelock]
        cb_inner_puz = create_augmented_cond_puzzle(condition, inner_puzzle)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_augmented_cond_solution(inner_solution)
    else:
        raise ValueError("Invalid Clawback inner puzzle.")
    solution: Program = Program.to([merkle_proof, cb_inner_puz, cb_inner_solution])
    return solution
```
