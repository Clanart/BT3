### Title
Deterministic FROST nonce reuse via never-invalidated `CachedPreprocesses` seed leaks the validator's private key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives FROST nonces from a single 32-byte seed stored in the `CachedPreprocesses` DB table, keyed only by `context = (b"DkgConfirmer", attempt)`. The seed is written once and **never deleted or rotated** — every subsequent `share`/`complete` call under the same attempt deterministically regenerates the identical nonce pair `(d, e)` via `ChaCha20Rng::from_seed`. The FROST library's own contract states that after `from_cache`, "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share." If the coordinator signs two or more distinct `set_keys_message`s (different `key_pair`) under one DKG attempt, the published `confirmation_share`s form a linear system that recovers the signer's secret — which here is the validator's actual MuSig private key.

### Finding Description
- `preprocess_internal` checks `CachedPreprocesses::get(...)`; if absent it creates a machine, caches `machine.cache()` (the RNG seed), and on **every** later call reloads that seed and calls `AlgorithmSignMachine::from_cache`, which runs `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)` → identical `nonces` and `commitments`. [1](#0-0) [2](#0-1) 
- No code path ever calls `CachedPreprocesses` deletion; `create_db!` provides only get/set, and the seed persists for the life of the attempt context. [3](#0-2) 
- `share_internal` → `machine.sign(preprocesses, msg)` produces `share = d + rho·e + λ·x·c`, where `rho` is the binding factor derived from `msg`/`preprocesses` transcript and `c` the signature challenge. Reusing `(d, e)` across distinct `(rho_j, c_j)` yields linear equations in the three unknowns `(d, e, x)`. [4](#0-3) 
- The signed message is `set_keys_message(set, removed, key_pair)` — it varies with `key_pair`. [5](#0-4) 
- `generated_key_pair` unconditionally overwrites `DkgKeyPair`/`KeyToDkgAttempt` and invokes `DkgConfirmer::share` — there is no guard preventing a second invocation for the same `attempt` with a different `key_pair` (e.g., processor re-reporting a generated pair, retry/fork in key generation, or `complete` running after `DkgKeyPair` was overwritten between share collection and confirmation). [6](#0-5) [7](#0-6) 
- Each share is broadcast publicly on the tributary as `Transaction::DkgConfirmed { confirmation_share }`, so any observer (unprivileged party) collects them. [8](#0-7) 
- The threshold keys are built as `musig(..., self.key, ...)` — a MuSig wrapper over the validator's own private key — so recovering `x` recovers the validator key itself, not an ephemeral DKG share. [9](#0-8) 

### Impact Explanation
Full recovery of a validator's Ristretto private key from publicly broadcast `DkgConfirmed` shares. With that key an attacker can sign arbitrary tributary transactions as the victim (slash votes, removal votes, signing-protocol data) and impersonate them in consensus-adjacent message flows. This matches the documented consequence in `SignMachine::from_cache`: "Any reuse will presumably cause the signer to leak their secret share." [10](#0-9) 

### Likelihood Explanation
The nonce seed persists indefinitely under `(b"DkgConfirmer", attempt)` and all sign operations deterministically reuse it. The primary path (`share` once + `complete` once with identical inputs) produces identical shares and is safe, but the code tolerates repeated `generated_key_pair` calls per attempt — `DkgKeyPair::set` overwrites without checking — so any second, distinct `key_pair` report (processor retry after restart, duplicate key-gen result, blame-driven regeneration within an attempt) produces a cryptographically distinct share under reused nonces. Three such shares fully determine `x`; two shares already eliminate the nonce and reduce the key to a relation. The missing "delete on use" step is exactly the class of bug in the reference advisory: the resource (nonce seed / keyslot) is retained past the point where completion is signaled instead of being released.

### Recommendation
Delete the cached seed before returning the signing machine — i.e., treat `from_cache` as consuming the seed: remove the `CachedPreprocesses` entry in `share_internal` (or have `preprocess_internal` clear it once the preprocess has been consumed for signing), and additionally guard `generated_key_pair` against being called more than once per `attempt` (reject if `DkgKeyPair` is already set with a different value). This mirrors the upstream fix's approach of releasing the resource before reporting completion rather than weakening the reuse check. [11](#0-10) 

### Proof of Concept
Conceptual, based on `crypto/frost/src/sign.rs` share equation:

1. During DKG attempt `k`, the coordinator calls `preprocess_internal` → seed `s` stored under context `("DkgConfirmer", k)`; `d, e` derived via `ChaCha20Rng::from_seed(s)`; preprocess `(D = dG, E = eG)` published via `dkg_confirmation_nonces`. [12](#0-11) 
2. `generated_key_pair(txn, key, spec, key_pair_A, k)` emits share `s_A = d + ρ_A·e + λ·x·c_A` (broadcast later in `DkgConfirmed`).
3. `generated_key_pair` is invoked again for the same `attempt` with `key_pair_B ≠ key_pair_A` (unguarded overwrite at `DkgKeyPair::set`). The cached seed regenerates identical `d, e`; new message yields `ρ_B, c_B`; share `s_B` published.
4. A third distinct signing (`key_pair_C`, or `complete` executing after `DkgKeyPair` changed) gives `s_C`.
5. Observer solves the 3×3 linear system over the Ristretto scalar field:
   `s_j = d + ρ_j·e + (λ·c_j)·x` for unknowns `(d, e, x)` → recovers `x`, the validator's private key (single-signer MuSig share equals the key). Verify with `x·G == validator_pubkey`.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
