### Title
Hardcoded Pyth Storage Contract Address in Market Prevents Upgrades, Permanently Freezing Price-Dependent Operations - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` hardcodes the fully-qualified Pyth storage contract address (`'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4`) for both writing new price updates and reading current prices, instead of resolving the active storage contract dynamically through the Pyth governance indirection layer. If the Pyth bridge's storage contract is ever upgraded (a supported, expected event, as evidenced by the versioned naming `v1`→`v4` and the dedicated governance mechanism for it), the market's hardcoded calls stop working, and price freshness checks eventually cause all Pyth-priced asset operations to permanently revert.

### Finding Description
`call-pyth` reads prices directly from a hardcoded address: [1](#0-0) 

`write-feed` also hardcodes the storage contract address as a parameter passed into `pyth-oracle-v4.verify-and-update-price-feeds`: [2](#0-1) 

Pyth's own governance contract, `pyth-governance-v3`, is explicitly designed to support upgrading the active storage/decoder/oracle contracts via `update-pyth-storage-contract`, `update-pyth-decoder-contract`, and `update-pyth-oracle-contract`, tracked in a mutable `current-execution-plan`: [3](#0-2) [4](#0-3) 

When `pyth-oracle-v4.verify-and-update-price-feeds` is invoked, it enforces that the `pyth-storage-contract` argument matches the governance's current expected plan via `check-execution-flow`: [5](#0-4) [6](#0-5) 

If governance updates the storage contract to a new version (e.g. `pyth-storage-v5`), Zest's `write-feed` will keep passing the old hardcoded `pyth-storage-v4` address, which no longer matches the governance's `current-execution-plan`, causing `check-execution-flow`/`check-storage-contract` to fail and `verify-and-update-price-feeds` to revert — price updates for STX, sBTC, and USDC feeds would permanently fail. Simultaneously, `call-pyth` reads directly from the now-frozen `pyth-storage-v4` address, which no longer receives new price writes from anyone, so its stored price/timestamp become permanently stale.

Once stale, the market's own staleness gate rejects the value: [7](#0-6) 

`oracle-timestamp-fresh` compares `stacks-block-time` against the frozen `publish-time` and will always exceed `max-staleness`, so `price-resolve` returns `ERR-ORACLE-INVARIANT` for every operation requiring that price.

### Impact Explanation
Any user position collateralized in or borrowing STX, sBTC, or USDC (all Pyth-priced) becomes unable to have its health factor computed once the freshness check fails. This blocks borrow, withdraw, repay, and liquidation flows that depend on `price-resolve`/`price-multi-resolve` for these assets, since they all revert with `ERR-ORACLE-INVARIANT`. This is a temporary freezing of user funds (High impact) — positions and collateral become inaccessible until the market contract is redeployed/upgraded via a new DAO proposal pointing at the correct storage address, and if the market cannot atomically catch up (e.g. liquidations also block), unhealthy positions cannot be liquidated either, elevating protocol risk during the freeze window.

### Likelihood Explanation
This requires no attacker action or compromise — it is triggered purely by Pyth's own bridge infrastructure being upgraded through its supported governance path (`update-pyth-storage-contract`/`update-pyth-decoder-contract`/`update-pyth-oracle-contract`), which the versioned contract naming (`v1` → `v4`) shows has already happened multiple times historically. Any future such upgrade on the Pyth side will silently desynchronize Zest's hardcoded address from the live indirection layer.

### Recommendation
Do not hardcode the Pyth storage/oracle contract principal in `v0-4-market.clar`. Either (a) read the currently active `pyth-storage-contract`/`pyth-decoder-contract`/`wormhole-core-contract` from `pyth-governance-v3.get-current-execution-plan` at call time and pass those into `write-feed`/`call-pyth`, or (b) make the addresses upgradeable market-side data-vars settable only through a DAO proposal, so they can be kept in sync whenever Pyth's execution plan changes.

### Proof of Concept
1. Pyth governance calls `update-pyth-storage-contract` on `pyth-governance-v3`, updating `current-execution-plan.pyth-storage-contract` from `pyth-storage-v4` to `pyth-storage-v5`.
2. Zest's `write-feed` in `v0-4-market.clar` still calls `pyth-oracle-v4.verify-and-update-price-feeds` with the hardcoded `pyth-storage-contract: 'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4`.
3. Inside `verify-and-update-price-feeds`, `pyth-governance-v3.check-execution-flow` compares the passed plan against the updated `current-execution-plan` and fails, so the write reverts with `ERR-PRICE-FEED-UPDATE-FAILED`.
4. `call-pyth` continues reading from the now-frozen `pyth-storage-v4`, whose last stored `publish-time` stops advancing.
5. Once `stacks-block-time - publish-time > max-staleness`, `oracle-timestamp-fresh` returns `false` in `price-resolve`, and every borrow/withdraw/liquidate call touching STX/sBTC/USDC reverts with `ERR-ORACLE-INVARIANT`, freezing those positions until the market contract is redeployed with the corrected address.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-public (verify-and-update-price-feeds 
		(price-feed-bytes (buff 8192))
		(execution-plan {
			pyth-storage-contract: <pyth-storage-trait>,
			pyth-decoder-contract: <pyth-decoder-trait>,
			wormhole-core-contract: <wormhole-core-trait>
		}))
	(begin
		;; Check execution flow
		(try! (contract-call? .pyth-governance-v3 check-execution-flow contract-caller (some execution-plan)))
		;; Perform contract-call
		(let ((pyth-decoder-contract (get pyth-decoder-contract execution-plan))
				(wormhole-core-contract (get wormhole-core-contract execution-plan))
				(pyth-storage-contract (get pyth-storage-contract execution-plan))
				(decoded-prices (try! (contract-call? pyth-decoder-contract decode-and-verify-price-feeds price-feed-bytes wormhole-core-contract)))
				(updated-prices (try! (contract-call? pyth-storage-contract write decoded-prices)))
				(fee-info (contract-call? .pyth-governance-v3 get-fee-info))
				(fee-amount (* (len updated-prices) (* (get mantissa fee-info) (pow u10 (get exponent fee-info))))))
			;; Charge fee
			(if (> fee-amount u0) (unwrap! (stx-transfer? fee-amount tx-sender (get address fee-info)) ERR_BALANCE_INSUFFICIENT) true)
			(ok updated-prices))))
