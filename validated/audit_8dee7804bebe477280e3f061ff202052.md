### Title
Fee calculation omits the `OP_RETURN` data output's weight, so `fee_per_vbyte` is never charged on it — ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes` where `vbytes` is derived from `calculate_weight_vbytes(tx_ins.len(), payments, ...)`. The weight model is built from `payments` only, yet the caller-supplied `data` `OP_RETURN` output (up to 80 bytes) is pushed into `tx_outs` *before* the weight calculation and is never included in the fee. This is the same bug class as the report: a fixed buffer is added to the transaction after the per-unit fee ("multiplier") is computed, so the premium never applies to that portion of the actual cost.

### Finding Description
In `SignableTransaction::new`:

1. The `data` output is appended to `tx_outs` at lines 194-202.
2. `calculate_weight_vbytes` is then invoked with `payments` — not `tx_outs` — at line 204 (`Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`) and again at line 226 for the change case.
3. Therefore the `OP_RETURN` output (up to ~83 vbytes: ~10-byte output overhead + 82-byte script push) contributes zero vbytes to the fee estimate, even though it increases the real transaction's weight and is included in the final `Transaction` stored in `SignableTransaction` (lines 245-255).
4. The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same under-estimated `vbytes`, so a transaction constructed at exactly the minimum relay rate will actually be *below* the minimum relay feerate once the `OP_RETURN` output is serialized.

Concretely: `fee()` (lines 138-141) returns `sum(inputs) - sum(outputs)`, which equals `needed_fee`. The effective feerate is `needed_fee / actual_vsize`, strictly less than `fee_per_vbyte`, and possibly below `DEFAULT_MIN_RELAY_TX_FEE`.

### Impact Explanation
An 80-byte `data` payload adds roughly 80-83 vbytes unpaid. At `fee_per_vbyte` near the minimum relay rate, the broadcast transaction is rejected by peer nodes (`min relay fee not met`) or sits unconfirmable. The corresponding UTXOs are committed to a specific sighash/transaction (the signed `Prevouts::All` commitment and the `SignableTransaction`'s `txid` used as the `Eventuality` in `processor/src/networks/bitcoin.rs` line 830), so funds earmarked for that plan cannot be spent until a new transaction is negotiated and re-signed — i.e., outputs reported as payable become unspendable in practice, and the protocol silently subsidizes data payloads at the intended feerate's expense. Since `data` is a caller-supplied argument to a public wallet API, an unprivileged party who can cause data-bearing transactions to be created pays a strictly lower effective feerate than intended.

### Likelihood Explanation
Any invocation of `SignableTransaction::new` with `data: Some(..)` triggers it deterministically — no race or adversarial sequencing required. The underpayment scales with data length up to the 80-byte cap checked at line 171. It becomes consensus-relevant (relay rejection) whenever `fee_per_vbyte` is at or near `DEFAULT_MIN_RELAY_TX_FEE`, which is precisely the regime the `TooLowFee` guard is meant to protect.

### Recommendation
Pass the complete output set (including the `OP_RETURN` output) into the weight model. `calculate_weight_vbytes` takes `payments: &[(ScriptBuf, u64)]`; either push `(op_return_script, 0)` into a cloned payments vector before calling it, or refactor to take `&[TxOut]` built from `tx_outs`. Apply the same fix to both call sites (lines 204 and 226) so the change-output path is also computed over the full output list. Then `needed_fee` covers the actual serialized weight and the `TooLowFee` check is meaningful.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// data output added to tx_outs (line ~194):
tx_outs.push(TxOut {
  value: Amount::ZERO,
  script_pubkey: ScriptBuf::new_op_return(/* up to 80 bytes */),
});

// but the fee model only sees `payments` (line ~204):
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```
Test sketch: construct `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` with `fee_per_vbyte = 1` sat/vbyte (min relay). Then compare `tx.fee()` against `tx.vsize()` of the signed transaction: `fee / vsize < 1` sat/vbyte, so `send_raw_transaction` fails `min relay fee not met`, while `SignableTransaction::new` returned `Ok` instead of `TooLowFee`.
