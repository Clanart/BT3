### Title
`create_payout_txhandler` OP_RETURN operator pubkey is unsigned under `SinglePlusAnyoneCanPay`, allowing payout attribution hijack - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The payout transaction's user signature uses `TapSighashType::SinglePlusAnyoneCanPay`, which commits only to input 0 (via ANYONECANPAY) and output 0 (via SIGHASH_SINGLE). The OP_RETURN output (output 2) carrying `operator_xonly_pk` is completely unsigned, so anyone who observes the broadcast signature can rebuild an alternate payout transaction with the same input/output 0 but an arbitrary OP_RETURN payload, and if that variant is the one that ends up confirmed, `Verifier::update_finalized_payouts` records the attacker-chosen pubkey as the payer for that withdrawal.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk` (for withdrawal `idx`) == the operator whose collateral/kickoff funded the fronted payout output.

Trace:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds the payout tx with input 0 = withdrawal UTXO (`SpendPath::KeySpend`), output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(operator_xonly_pk.serialize())`. Only `set_p2tr_key_spend_witness(&user_sig, 0)` is applied to input 0; there is no additional commitment to output 2.
- `Operator::withdraw` (`core/src/operator.rs:630-637`) verifies `in_signature` with `sighash_type` supplied by the caller (enforced to be `SinglePlusAnyoneCanPay` in `core/src/rpc/parser/operator.rs:161-187`). `calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-233`) shows that for `SinglePlusAnyoneCanPay`/`AllPlusAnyoneCanPay`/`NonePlusAnyoneCanPay`, only `Prevouts::One(txin_index, ...)` is used, and BIP-341's `SIGHASH_SINGLE` semantics (also implemented identically in the circuit's sighash computation, `circuits-lib/src/bridge_circuit/mod.rs:801-810`) commit only to the output at the *same index* as the signed input (index 0). Outputs 1 and 2 (anchor, OP_RETURN) are never hashed into the signed message.
- Consequently, the operator's broadcast payout tx's witness for input 0 is valid for *any* transaction that reuses the identical input 0, output 0, and sighash flags — regardless of what appears in outputs 1/2, and regardless of what other (ANYONECANPAY, so uncommitted) inputs are added for fees.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) determines the payer purely from whichever transaction the chain records as spending the withdrawal outpoint: `Database::get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) joins `withdrawals` to `bitcoin_syncer_spent_utxos` on `(txid, vout)` of the withdrawal UTXO and returns `bsu.spending_txid` — i.e., whatever transaction actually confirmed as the spender, with no reference to which specific transaction the operator originally broadcast. It then parses that on-chain tx's first OP_RETURN output and stores its 32 bytes as `operator_xonly_pk` if it decodes as a valid `XOnlyPublicKey` (lines 2312-2342), else `NULL`.
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) later requires `operator_xonly_pk == kickoff_data.operator_xonly_pk` (line 1887) or marks the kickoff malicious, which drives `Verifier::handle_kickoff` to queue a `Challenge` tx (`core/src/verifier.rs:1966-2026`), burning the honest fronting operator's collateral.

Root cause: the OP_RETURN attribution output is placed outside the coverage of the only signature that authorizes spending the withdrawal UTXO, so it is fully attacker-malleable as long as the attacker can get their re-built variant of the transaction confirmed instead of (or as) the one the honest operator broadcast. No other guard (`is_kickoff_malicious`, `handle_finalized_payout`, `get_payout_txs_for_withdrawal_utxos`, DB uniqueness) re-derives or re-checks the expected OP_RETURN payload against the operator that actually funded/broadcast the payout; they all trust whatever ends up on-chain for that outpoint.

Exploit flow: attacker observes the honest operator's payout tx in the mempool (public), extracts the witness signature for input 0 (a public/relayed value), constructs a new transaction with the same input 0 (same outpoint + identical witness signature) and identical output 0, but supplies its own fee-paying input(s) (uncommitted due to ANYONECANPAY) and replaces output 2's OP_RETURN with a 32-byte value that parses as a valid but arbitrary/unregistered `XOnlyPublicKey`. The attacker races/fee-bumps this transaction so it (rather than the operator's original) is the one that gets mined for that outpoint.

### Impact Explanation
If successful, `update_finalized_payouts` stores an operator xonly pk that matches no real operator's `kickoff_data.operator_xonly_pk` (or a valid-but-wrong operator's key) for that withdrawal. When the honest fronting operator later sends its kickoff, `is_kickoff_malicious` will find `operator_xonly_pk != kickoff_data.operator_xonly_pk` and return `true`, causing verifiers to queue a `Challenge` transaction against the honest operator's kickoff. This matches the Critical category "an honest operator's collateral burned." The attack is per-withdrawal and repeatable against any fronted payout the attacker can race, independent of which operator fronts it, so the blast radius spans all deposits/withdrawals and all operators.

### Likelihood Explanation
Preconditions: an operator must have broadcast (but not yet be finalized/deep-confirmed) a fronting payout tx for withdrawal `i`; the attacker only needs to observe the Bitcoin mempool (public data) and be able to broadcast a competing/replacing transaction with sufficient fee to win the race for confirmation — no verifier/operator/aggregator role, key share, or collateral is required, matching the "unprivileged attacker" threat model. Cost is bounded by fees needed to outbid/replace the operator's transaction (and dust/fee inputs of their own). This is feasible on any Bitcoin-like network without needing hashrate majority, matching a plain sighash-malleability/mempool-racing exploit; it does not require reorgs. Confirmation depends on standard mempool/RBF/miner selection rules rather than any code guarantee in this repo, so it is a genuine, reachable weakness, though its success is probabilistic (dependent on the attacker's fee-bidding ability against the honest operator, and whether nodes/miners treat the competing spend as conflicting/first-seen or accept a higher-fee replacement).

### Recommendation
Bind the OP_RETURN (and the anchor output) to the input-0 signature by switching the payout signature's sighash type to a variant that commits to all outputs (e.g., `TapSighashType::AllPlusAnyoneCanPay` or `Default`) instead of `SinglePlusAnyoneCanPay`, or move `operator_xonly_pk` attribution out of an unsigned/malleable on-chain field entirely (e.g., derive/verify it against the actual reimbursement path/kickoff rather than trusting an arbitrary OP_RETURN byte string parsed from whichever tx happens to spend the UTXO).

### Proof of Concept
`cargo test` plan (regtest, no mainnet/live Citrea):
1. Set up a deposit + withdrawal as in existing e2e helpers (`core/src/test/common/clementine_utils.rs`, `generate_withdrawal_transaction_and_signature`).
2. Have the honest operator call `withdraw`, producing `payout_tx_honest` signed with `SinglePlusAnyoneCanPay` for input 0, with `operator_xonly_pk == honest_operator_xonly_pk` in output 2.
3. Before `payout_tx_honest` confirms, build `payout_tx_attacker`: same input 0 (same outpoint, same witness signature copied from `payout_tx_honest`), identical output 0, an attacker-funded extra input for fees, and output 2 replaced with an arbitrary but valid `XOnlyPublicKey` not equal to any registered operator's key.
4. Broadcast/mine `payout_tx_attacker` instead of `payout_tx_honest` (e.g., mine it directly via regtest RPC before submitting the honest tx to a block).
5. Run the verifier's finalized-block sync so `update_finalized_payouts` processes the block containing `payout_tx_attacker`.
6. Assert: `db.get_payout_info_from_move_txid(...).0 != Some(honest_operator_xonly_pk)` (binding broken).
7. Proceed with the honest operator's kickoff (`kickoff_data.operator_xonly_pk == honest_operator_xonly_pk`) and call `Verifier::is_kickoff_malicious(...)`; assert it returns `true`, proving the honest operator is flagged malicious solely due to the mutated OP_RETURN.
