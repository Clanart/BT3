## Analysis

I found a legitimate analog to the flow-limit DoS pattern in claude-code's `security-guidance` plugin, specifically in the commit-review security hook.

### Title
Rate-limit exhaustion allows silent bypass of the LLM-based commit/push security review - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin runs a `PostToolUse` hook that sends every `git commit` (and pushed commit ranges) to an LLM for a security scan (secrets, vulnerabilities) before allowing work to continue silently. To bound LLM spend, both the commit-review and push-sweep paths are gated by a shared rolling-window rate limiter, `atomic_check_rate_limit()`, capped at `MAX_COMMIT_REVIEWS_PER_HOUR` (default 20) per rolling hour [1](#0-0) . This is directly analogous to the Axelar TokenManager's flow limit, which caps token movement per 6-hour epoch to protect against abuse [2](#0-1) .

### Finding Description
`handle_commit_review_posttooluse` calls `atomic_check_rate_limit(session_id, "CommitReview", MAX_COMMIT_REVIEWS_PER_HOUR, COMMIT_REVIEW_RATE_WINDOW_S)` right before invoking `analyze_code_security`; if the budget is exhausted it simply logs a debug message, records telemetry, and exits `0` — i.e., the commit proceeds with **no review at all** and no warning surfaced to the user [3](#0-2) . The same fail-open pattern exists in `handle_push_sweep_posttooluse` under the "PushSweep" key [4](#0-3) . Because the quota is consumed by any qualifying commit — cheap, trivial commits included — an unprivileged local user (or an agent driven by a prompt-injected instruction) can burn through the hourly budget with throwaway commits, then land a genuinely malicious or secret-leaking commit as the next one, which will skip the LLM review entirely.

### Impact Explanation
This defeats the intended safety net: the security-guidance plugin exists specifically to catch secrets and vulnerabilities introduced via `git commit`/`git push` before they land, but the rate limiter can be trivially exhausted to disable that protection for the remainder of the rolling window, with the bypass being completely silent (no error, no warning, only an internal debug log/telemetry entry). This mirrors the Axelar finding's core problem: a rate-limiting mechanism intended to protect the system can be weaponized by the very party it's meant to constrain, degrading availability/reliability of the protection for the rest of the window.

### Likelihood Explanation
Likelihood is moderate-to-high in adversarial contexts: an attacker who can influence agent behavior (e.g., via a prompt-injected task, a malicious skill, or a compromised dependency instructing many small commits) can cheaply spend the 20-per-hour budget, since the "spend" only requires committing reviewable source-file changes — no special privilege beyond running `git commit`/`git push` locally. The window is also shared per-session, so any legitimate-looking burst of commits (e.g., an aggressive auto-commit workflow) could accidentally or deliberately create the same blind spot.

### Recommendation
- Do not fail-open to "no review" when the rate limit is hit; instead, fail loud (surface a visible warning to the user/transcript that review was skipped due to rate limiting) so the gap in coverage is not silent.
- Consider a lightweight fallback (e.g., pattern-based secret/vuln heuristic scan) when the LLM-based rate limit is exhausted, rather than skipping review entirely.
- Consider weighting the rate limit by diff size/risk rather than a flat per-commit budget, so an attacker can't cheaply exhaust the quota with trivial commits before landing the actual malicious change.

### Proof of Concept
1. In a repo with the security-guidance plugin's commit-review hook enabled and `MAX_COMMIT_REVIEWS_PER_HOUR` at its default (20), have the agent (or a script) perform 20 trivial commits with reviewable source-file changes within the same rolling hour — this satisfies `atomic_check_rate_limit` up to the cap at `plugins/security-guidance/hooks/security_reminder_hook.py:271-304`.
2. On the 21st commit within the same hour, introduce the actual malicious payload (e.g., a hardcoded secret or an injected backdoor).
3. `handle_commit_review_posttooluse` reaches `atomic_check_rate_limit(..., "CommitReview", ...)`, gets `_allowed=False`, logs `"Commit review: hourly rate limit reached, skipping"`, emits metrics, and calls `sys.exit(0)` without ever invoking `analyze_code_security` — the malicious commit is never scanned and no warning is shown to the user [5](#0-4) .

```python
def atomic_check_rate_limit(session_id, key, max_per_window, window_s):
    """Rolling-window rate limit: allow at most `max_per_window` calls per
    `window_s` seconds, per (session_id, key).

    Returns (allowed: bool, count_in_window: int). count_in_window is the
    post-decision count (i.e., includes this call if allowed) so callers can
    emit it directly as a telemetry gauge.

    Replaces session-lifetime `atomic_check_counter` for commit-review and
    push-sweep. Telemetry showed a small but persistent share of sessions hit
    the lifetime cap, and those were multi-day persistent sessions that then
    lost coverage for many subsequent commits — not burst abusers. A rolling
    hour keeps the same cost ceiling for any 1h window while letting long
    sessions regain coverage.

    State key: rate_limits: {"<key>": [ts, ts, ...]}. Timestamps are pruned
    on every call so the list is bounded by max_per_window; no migration
    needed from the old `counters` dict — different key.
    """
    import time as _time
    now = _time.time()
    cutoff = now - window_s

    def _check(state):
        buckets = state.setdefault("rate_limits", {})
        ts_list = buckets.get(key, [])
        # Prune; tolerate non-numeric junk from a corrupted state file.
        ts_list = [t for t in ts_list if isinstance(t, (int, float)) and t > cutoff]
        if len(ts_list) >= max_per_window:
            buckets[key] = ts_list
            return False, len(ts_list)
        ts_list.append(now)
        buckets[key] = ts_list
        return True, len(ts_list)
```
