## Title
Stale-diff race in partial-commit staging allows silent corruption of what gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
The reported Sudoswap issue is a **time-of-check/time-of-use (TOCTOU)** flaw: the state a user reasoned about when initiating an action (the promised price) is not the state actually used when the action executes, and the pool owner can swap it out in between. GitHub Desktop has an analogous TOCTOU gap in its **partial-commit (line/hunk selection) pipeline**: the diff a user reviews and selects lines from is not the diff that is actually turned into a patch and applied to the index at commit time — the two are computed from the working-directory file content at two different points in time, and the line-selection bitmap computed against the first is blindly re-applied to the second.

### Finding Description
When a user stages part of a file for commit (selecting individual lines/hunks in the Changes view), Desktop:

1. Computes a diff via `getWorkingDirectoryDiff()` while rendering the UI and records the user's selection as **absolute line indices** into that diff's hunks (`updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts`, lines 3404-3465).
2. On commit, `stageFiles()` (`app/src/lib/git/update-index.ts:109-169`) calls `applyPatchToIndex()` for every partially-selected file.
3. `applyPatchToIndex()` **re-fetches the working directory diff from disk again**, independent of the diff the user actually looked at: [1](#0-0) 

```
const applyArgs: string[] = [
  'apply',
  '--cached',
  '--unidiff-zero',
  '--whitespace=nowarn',
  '-',
]

const diff = await getWorkingDirectoryDiff(repository, file)
```

4. `formatPatch(file, diff)` (`app/src/lib/patch-formatter.ts:129-232`) then walks this **freshly re-read** diff's hunks and decides which lines to include purely by index, using `file.selection.isSelected(absoluteIndex)`: [2](#0-1) 

There is no check that the newly fetched diff's hunk structure/content matches the diff the selection indices were computed against. If the tracked file's on-disk content changes between the moment the user reviews/selects lines in the UI and the moment `stageFiles`/`applyPatchToIndex` runs (e.g. a build tool, linter/formatter, LFS smudge, or any other process that rewrites the file — commonly run automatically by dev tooling shipped in a cloned/fetched repository, such as a `postinstall`-installed hook or a watch-mode formatter), the hunk offsets and content shift. The stale index-based selection is then applied to the *new* content, so `git apply --cached` stages **different lines than the ones the user actually selected and reviewed** — with no warning, diff mismatch detection, or re-confirmation step.

### Impact Explanation
This breaks the fundamental invariant that "what the user visually selected to commit is what actually gets committed." A shifted/rewritten file causes Desktop to silently stage attacker- or tool-influenced content the user never reviewed or approved, which then gets committed and potentially pushed under the user's identity — i.e., silent corruption of what the user commits, matching the report's "Valid Impact" category (unprivileged repo-controlled content leading to corruption of committed/pushed content).

### Likelihood Explanation
Medium: it requires a real, if narrow, timing window between diff-render/selection and the staging step, and something (script, tool, or hook installed by the repository's own build/dev tooling) modifying the file in that window. This is more plausible than it first appears because many JS/TS repositories run auto-formatters, linters, or file watchers (`prettier --write`, `eslint --fix`, webpack/ts watch, husky+lint-staged installed via `postinstall`) as normal parts of the cloned project's tooling — all of which are attacker-controllable when the repository itself is attacker-authored. No existing guard (line-ending diffing, diff caching, or index reset in `stageFiles`) detects or prevents the mismatch; `getWorkingDirectoryDiff` is invoked twice with no consistency check between the two invocations.

### Recommendation
Detect and reject stale selections instead of blindly reapplying them:
- Have `applyPatchToIndex`/`stageFiles` receive (or independently verify) the exact diff/hunk content the selection was computed against (e.g. a hash of the diff text or hunk boundaries), and refuse to stage (surfacing an error/refresh prompt) if the on-disk diff no longer matches what was reviewed.
- Alternatively, always re-render the diff and require the user to re-confirm selection immediately before staging rather than reusing a selection bitmap computed against a possibly stale diff.

### Proof of Concept
1. Open a text file with multiple hunks of changes in Desktop's Changes view; select only a subset of lines in hunk #1 for commit (leave other hunks/lines unselected).
2. Before clicking "Commit", have another process (a save-on-format extension, `prettier --write`, or any script) rewrite the file so line offsets shift (e.g., reflow/reformat, or insert lines above the hunks) while keeping the file's status as "modified."
3. Click "Commit" immediately. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-reads the diff at this point, and `formatPatch` (`app/src/lib/patch-formatter.ts:143`) applies the original absolute-index selection to the new hunk layout.
4. Inspect the resulting commit: the staged/committed content does not correspond to the lines the user visually selected — different or additional lines end up in the commit, without any dialog or warning.
