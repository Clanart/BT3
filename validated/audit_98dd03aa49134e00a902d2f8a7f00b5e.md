## Title
Integer overflow in withdrawal-index storage-key derivation could let an operator prove a false withdrawal claim - (File: circuits-lib/src/bridge_circuit/storage_proof.rs)

### Summary
`verify_storage_proofs` derives the Ethereum storage slots that bind a Bitcoin withdrawal outpoint/vout to a specific Citrea withdrawal index by computing `storage_address + U256::from(storage_proof.index * 2)` and `storage_address + U256::from(storage_proof.index * 2 + 1)`, where `storage_proof.index` is a plain `u32` multiplied and added using native (non-checked) arithmetic before being widened to `U256`. [1](#0-0) 

### Finding Description
`StorageProof.index` is a `u32` field carried inside the Borsh-serialized `BridgeCircuitInput`/`StorageProof` struct that is supplied to the bridge circuit (guest) as untrusted prover input. [2](#0-1) 

The multiplication `storage_proof.index * 2` and `storage_proof.index * 2 + 1` are performed in `u32` arithmetic *before* the `U256::from(...)` conversion. In a release build (`overflow-checks` disabled, the Rust default for `--release`), `u32` multiplication wraps silently instead of panicking. If a value near `u32::MAX` is chosen (e.g. `index = 0x8000_0001`), `index * 2` wraps around to a small value, causing the derived storage key to collide with the key that would normally be produced for a *different*, smaller withdrawal index. [3](#0-2) 

Because the subsequent `storage_verify` calls only check that the supplied Merkle-Patricia proof is valid for whatever key was derived (and that the key matches what was computed), an attacker who controls `storage_proof.index` could substitute the storage key for their intended withdrawal with the key/value of an unrelated, already-existing withdrawal slot, as long as they can present a valid proof for that colliding slot. This breaks the intended equality: `deposit_id (as committed via storage_proof.index) == the withdrawal outpoint/vout actually verified in the circuit`, undermining the storage-proof binding between "the withdrawal actually paid" and "the withdrawal the circuit certifies".

I was not able to fully verify, within the scope of this repository and time available, (a) whether `storage_proof.index` is independently cross-checked elsewhere against the `deposit_id`/`payout_input_index` before or after this function runs in a way that would neutralize the collision, or (b) whether the workspace's Cargo profile enables `overflow-checks = true` for release builds (which would turn the overflow into a panic/DoS instead of silent wraparound and would remove the soundness concern). I searched for `overflow-checks` in `Cargo.toml` files and did not find an explicit override, meaning the Rust/Cargo default (checked only in `debug`, wrapping in `release`) likely applies, but I could not confirm the exact release build configuration used for the zkVM guest binaries.

### Impact Explanation
If exploitable, this could allow a malicious operator (who controls the `BridgeCircuitInput` fed into the bridge circuit for proof generation) to have the circuit accept a storage proof whose derived key does not actually correspond to the withdrawal the circuit is meant to certify, potentially causing the circuit to certify a `move_txid`/vout pairing that does not match the intended withdrawal. This maps to the Critical impact category "a false circuit claim proved" from the custody-binding rules, since the deposit_constant/journal produced by the bridge circuit is used downstream to validate reimbursement and disprove-related payouts.

### Likelihood Explanation
Likelihood is uncertain and likely low-to-moderate in practice: exploitation requires (1) the overflow to actually manifest as silent wraparound in the compiled circuit binary (dependent on build profile, unconfirmed here), and (2) the attacker to find or construct a colliding, pre-existing valid storage-proof entry at the wrapped index that is favorable to them, which constrains the practical exploitability considerably. Without confirming the release build's overflow-check setting and without a way to fully trace whether `index` is independently bound to `deposit_id` elsewhere, this should be treated as a plausible but not fully confirmed finding.

### Recommendation
Replace the native `u32` multiplication/addition with checked or widened arithmetic performed directly in `U256`, e.g. compute `U256::from(storage_proof.index) * U256::from(2) + U256::from(1)`, or use `checked_mul`/`checked_add` on the `u32` and reject (panic) on `None`, ensuring no silent wraparound is possible regardless of build profile. Additionally, explicitly set `overflow-checks = true` for the release profile of the circuit crates to make any residual overflow fail loudly rather than wrap.
