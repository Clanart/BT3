### Title

Unsolicited outputs to the forwarding address are discarded from scheduler accounting - ([File: processor/src/multisigs/mod.rs](processor/src/multisigs/mod.rs))

### Summary

Serai’s Bitcoin processor recognizes outputs to the deterministic forwarding address, but only reconciles them against previously recorded forwarding instructions. An unprivileged sender can create a valid Bitcoin transaction paying that address; the output is marked as scanned, classified as `Forwarded`, and then removed before reaching the UTXO scheduler, leaving the funds spendable by the multisig but absent from its tracked inputs. This mirrors the accounting flaw where externally supplied assets do not update the separately maintained pool balance.

### Finding Description

Bitcoin derives a deterministic `Forwarded` output offset and address from the multisig group key, so any observer who knows the group key can calculate and pay that address. [1](#0-0) [2](#0-1) 

`Bitcoin::get_outputs` reconstructs the scanner, matches the transaction output’s `script_pubkey`, maps its offset to `OutputType::Forwarded`, and returns the output to the multisig scanner. [3](#0-2) [4](#0-3) 

The multisig layer only uses a `Forwarded` output to recover a previously stored instruction from `ForwardedOutputDb`; if no matching amount exists, no instruction is produced. [5](#0-4)  It then unconditionally removes every non-`External` output before those outputs are handed to the normal received-output flow. [6](#0-5) 

The UTXO scheduler’s spendable inventory is its `utxos` vector, populated only through `add_outputs`; outputs removed earlier cannot later be selected as transaction inputs. [7](#0-6) [8](#0-7) 

The scanner records output IDs as seen and panics if the same output is scanned again, so a dropped forwarded output is not naturally rediscovered on a later pass. [9](#0-8) 

### Impact Explanation

Bitcoin sent to the forwarding address is controlled by the multisig key but never enters the scheduler’s spendable UTXO set. Consequently, there is no protocol path to credit a direct reimbursement, refund, or insurance contribution sent to that deterministic address, nor to use it to cover later operating-cost or payment shortfalls. The funds are consumed by the scanner’s duplicate-output bookkeeping while remaining unavailable to transaction planning.

This is not merely an unclassified deposit: the output is detected, classified, removed from instruction processing, and prevented from being processed again by the `seen` check. Manual intervention or a code/database migration would be required to reintroduce the UTXO into the scheduler.

### Likelihood Explanation

The trigger only requires an unprivileged Bitcoin transaction paying the publicly derivable forwarding address. No validator cooperation, malformed curve input, leaked key, malicious RPC result, or protocol-private information is needed. The main mitigating factor is that the sender must deliberately pay the internal forwarding address rather than the normal external deposit address; nevertheless, refunds, reimbursements, migration transfers, and user mistakes can realistically target a known multisig-derived address.

### Recommendation

Do not silently discard unrecognized `Forwarded` outputs. Either:

- Add them to the scheduler’s UTXO inventory while omitting them from external-deposit instruction processing, or
- Emit an explicit unassigned-forwarded-output event and provide an authorized recovery/sweep path that inserts the verified `ReceivedOutput` into the scheduler.

In either design, the `seen` marker must not permanently suppress an output before it has been durably admitted into spendable accounting.

### Proof of Concept

1. Obtain the active Bitcoin multisig group key.
2. Build the deterministic forwarding address via `Bitcoin::forward_address`, which internally uses the `Forwarded` offset. [2](#0-1) 
3. Broadcast a normal Bitcoin transaction with an output paying that address and an amount above `Bitcoin::DUST`.
4. When the block is scanned, `Scanner::scan_transaction` finds the matching `script_pubkey` and creates a `ReceivedOutput`. [4](#0-3) 
5. `Bitcoin::get_outputs` maps that output to `OutputType::Forwarded`. [10](#0-9) 
6. Because no `ForwardedOutputDb` entry exists for that exact amount, no instruction is restored. [5](#0-4) 
7. The output is removed by `outputs.retain(|output| output.kind() == OutputType::External)`, never reaching `Scheduler::add_outputs` or its `utxos` inventory. [6](#0-5) [8](#0-7) 
8. The output ID is nevertheless inserted into `ram_outputs`/`seen`, preventing ordinary rescanning from recovering it. [9](#0-8)

  fn add_outputs(
    &mut self,
    mut utxos: Vec<N::Output>,
    key_for_any_change: <N::Curve as Ciphersuite>::G,
  ) -> Vec<Plan<N>> {
    log::info!("adding {} outputs", utxos.len());

    let mut txs = vec![];

    for utxo in utxos.drain(..) {
      if utxo.kind() == OutputType::Branch {
        let amount = utxo.balance().amount.0;
        if let Some(plans) = self.plans.get_mut(&amount) {
          // Execute the first set of payments possible with an output of this amount
          let payments = plans.pop_front().unwrap();
          // They won't be equal if we dropped payments due to being dust
          assert!(amount >= payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>());

          // If we've grabbed the last plan for this output amount, remove it from the map
          if plans.is_empty() {
            self.plans.remove(&amount);
          }

          // Create a TX for these payments
          txs.push(self.execute(vec![utxo], payments, key_for_any_change));
          continue;
        }
      }

      self.utxos.push(utxo);
    }
