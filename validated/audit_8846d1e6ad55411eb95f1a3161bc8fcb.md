Confirmed the same pattern exists identically across `BaseRewardPool.sol`, `BaseRewardPoolV2.sol`, and `mWOMSVBaseRewarder.sol`: `donateRewards` is a permissionless, unprivileged-wallet-callable function that feeds a caller-supplied `_amountReward` value straight into `_provisionReward`, which never verifies the actual tokens received via a balance diff before updating `rewardInfo.rewardPerTokenStored`/`historicalRewards`.

### Title
Unvalidated `donateRewards`/`_provisionReward` accounting enables deflationary/fee-on-transfer reward-token insolvency - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.donateRewards` (mirrored in `BaseRewardPoolV2.sol` and `mWOMSVBaseRewarder.sol`) is a public, unprivileged function that lets anyone top up an already-registered reward token. It forwards the caller-specified `_amountReward` to `_provisionReward`, which performs `safeTransferFrom(msg.sender, address(this), _amountReward)` and then updates `rewardPerTokenStored` using that same nominal `_amountReward`, rather than the amount actually received (no before/after `balanceOf` check).

### Finding Description [1](#0-0) 

`_provisionReward` trusts `_amountReward` as truth for both the transfer and the reward-per-share bookkeeping:
- It calls `safeTransferFrom(msg.sender, address(this), _amountReward)`.
- It then adds the full `_amountReward` to `historicalRewards` and folds it into `rewardPerTokenStored` (scaled by `stakingDecimals()`/`totalStaked()`).

If the registered reward token has any transfer-fee, rebasing, or deflationary mechanic (the exact bug class from the referenced Balancer STA report — the contract does not validate the amount actually received against the nominal accounting value), the pool will receive strictly less than `_amountReward`, yet `rewardPerTokenStored` is inflated as if the full amount arrived. Because `donateRewards` only checks `isRewardToken[_rewardToken]` (no owner/manager check), any ordinary wallet can trigger this path for any token that has already been registered as a reward via `queueNewRewards` — including bribe-sourced reward tokens surfaced through `WombatBribeManager`/`WombatStaking.vote`, whose token set originates from third-party bribers and is not guaranteed to be fee-free. [4](#0-3) 

### Impact Explanation
Once `rewardPerTokenStored` is inflated beyond the pool's real token balance, `getReward`/`getRewards` will attempt to `safeTransfer` amounts the contract does not hold once enough legitimate stakers try to claim, causing later claimants' `getReward` calls to revert (they cannot withdraw earned rewards) or forcing a permanent shortfall split across all reward claimants of that token — a permanent freezing/loss of a portion of user-earned, unclaimed yield, which is within the accepted impact classes (permanent freezing of unclaimed yield).

### Likelihood Explanation
Likelihood depends on a deflationary/fee-on-transfer/rebasing token being registered as a reward token at some point (e.g., via bribe harvesting flows where reward tokens are determined by the external Wombat bribe contracts rather than Magpie governance). Given `donateRewards` requires no permission beyond the token already being registered, any wallet can pull the trigger the moment such a token exists, with no additional privilege needed.

### Recommendation
In `_provisionReward` (all three rewarder variants), measure the actual tokens received via a `balanceOf` diff around the `safeTransferFrom` call and use that measured amount for `historicalRewards`/`rewardPerTokenStored`/`queuedRewards` updates instead of the caller-supplied `_amountReward`, consistent with the pattern already used elsewhere in the codebase (e.g., `WombatStaking.deposit`'s `beforeBalance`/`afterBalance` check). [5](#0-4) 

### Proof of Concept
1. A reward token `T` with a transfer fee (e.g., 5% burned/redirected on each transfer) becomes a registered reward token for a `BaseRewardPool` (via a manager `queueNewRewards` call, or via bribe harvesting flow where `T` is an external bribe reward token).
2. Attacker (or any user) approves the pool for `_amountReward = 1000 T` and calls `donateRewards(1000e18, T)`.
3. `_provisionReward` calls `safeTransferFrom(attacker, pool, 1000e18)`; due to the 5% fee, the pool actually receives only `950e18 T`.
4. `rewardPerTokenStored` is nonetheless incremented based on the full `1000e18`, over-crediting all current stakers' claimable balances of `T` by `50e18` in aggregate.
5. As stakers call `getReward`, the pool's actual `T` balance is exhausted before all entitled amounts are paid, causing later `getReward` calls involving `T` to revert (`ERC20: transfer amount exceeds balance`) — those stakers' earned `T` rewards become permanently unclaimable.

        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );

        rewardInfo.historicalRewards =

                rewardInfo.queuedRewards = 0;

                (_amountReward * 10**stakingDecimals()) /
