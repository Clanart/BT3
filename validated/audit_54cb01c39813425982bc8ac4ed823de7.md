### Title
Change output created below the network dust floor becomes unspendable/unscanned - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` enforces two different "minimum output" floors depending on which output path is taken — mirroring M-18, where the dust floor was enforced on one branch but a conditional alternative (`loansCount >= 10` → average-based minimum) let a below-floor value through. Here, payments are rejected below `DUST` (546 sat) and change is only emitted if `>= DUST` (546 sat), but the processor's dust floor — the value below which received outputs are never even scanned — is `Network::DUST = 10_000` sat. A change output in the `[546, 10_000)` range is created on-chain yet can never be recognized or respent.

### Finding Description
In `SignableTransaction::new`, payments below the wallet `DUST` constant (546) are rejected (`send.rs:165-169`), and the change output is pushed only when the leftover satisfies `value >= DUST` (`send.rs:228-233`). That check is the only minimum enforced on the change path.

The processor, however, defines its own floor: `Bitcoin::DUST = 10_000` (`processor/src/networks/bitcoin.rs:638`), justified in the doc comment as an order-of-magnitude margin over spendability cost. This floor is what the multisig scanner applies to incoming outputs — anything below `N::DUST` is silently skipped (`processor/src/multisigs/scanner.rs:564`), and `prepare_send` explicitly assumes on-chain change below `Self::DUST` will not exist, folding `theoretical_change_amount` into `operating_costs` in that case (`processor/src/networks/mod.rs:579-591`).

So when `input_sat - payment_sat - fee_with_change` lands in `[546, 10_000)`, the transaction is built and signed with a change output the accounting layer believes was dropped: the change is real, owned by a registered offset key, but below the scan threshold, so it is never credited back to the multisig's usable UTXO set while simultaneously being counted as lost in `operating_costs`.

### Impact Explanation
Funds are stranded. The change output exists and is spendable in principle (the key is derivable), but the scanner's dust filter guarantees it will never be added to `self.utxos`, so the multisig can never sign for it through normal operation. The protocol's own invariant — every emitted output is above the value it costs to recognize and respend — is violated, and the value is additionally double-counted as an operating cost. This is exactly the M-18 shape: a minimum-value guard enforced with the wrong/weaker floor on one code path, producing below-floor outputs the rest of the system assumes cannot exist.

### Likelihood Explanation
Requires no adversary — it triggers whenever change naturally falls into the `[546, 10_000)` window, i.e., whenever `input_sat - payment_sat - fee_with_change ∈ [546, 9999]`. Given `fee_with_change` is determined by chain fee rates and payment amounts come from arbitrary user withdrawals, this window is routinely hit during ordinary operation. Reachable purely through public inputs (payments the processor is instructed to make).

### Recommendation
Make the wallet layer's change floor the network's floor, not the relay-rule floor. Either:
- Pass the required minimum into `SignableTransaction::new` (e.g., `min_output: u64`) and use it for both the payment check and the `value >= min_output` change check at `send.rs:229`, with `make_signable_transaction` passing `Self::DUST`; or
- In `make_signable_transaction`, treat a produced change output `< Self::DUST` as absent (drop it / recompute) so the accounting in `prepare_send` at `mod.rs:589` matches reality.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// inputs: one ReceivedOutput worth payment + fee_with_change + 5_000
let payments = [(script, 20_000u64)];
let change = p2tr_script_buf(change_key).unwrap();
// Suppose input_sat - 20_000 - fee_with_change == 5_000
let tx = SignableTransaction::new(vec![input], &payments, Some(change), None, fee).unwrap();
// tx.output contains a change output of 5_000 sat: >= DUST (546), so it is emitted
assert_eq!(tx.tx.output.last().unwrap().value.to_sat(), 5_000);
```
At the processor layer (`processor/src/networks/mod.rs:589`), `on_chain_expected_change = 5_000 < Self::DUST = 10_000`, so `operating_costs += theoretical_change_amount` — the output is assumed nonexistent. Then in `processor/src/multisigs/scanner.rs:564`, `5_000 >= N::DUST` fails, so the change output is never pushed to `outputs`, never enters `self.utxos`, and its value is permanently unspendable by the multisig despite being owned by its own change key.
