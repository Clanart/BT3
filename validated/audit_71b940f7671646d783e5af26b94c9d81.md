## Title
Missing proof-length binding lets a malicious repair peer forge a `FecSetRoot` block-id-repair response by substituting an internal double-Merkle node for a leaf — (File: `core/src/repair/serve_repair.rs`)

## Summary

## Finding Description

The external report's broken invariant is: *a Merkle tree's leaf-hash domain and its internal-node-hash domain must be cryptographically distinguishable, otherwise an internal node can be replayed as a leaf with a truncated proof.* Agave's shred/double-Merkle tree implementation already defends against this in general by using distinct domain prefixes for leaves vs. nodes (`MERKLE_HASH_PREFIX_LEAF` / `MERKLE_HASH_PREFIX_NODE`) [1](#0-0) , and the "double Merkle tree" that aggregates per-FEC-set roots explicitly binds `fec_set_count` into the trailing parent-info leaf specifically to stop an odd/even leaf-count duplication attack, with an accompanying regression test proving that mitigation works [2](#0-1) [3](#0-2) .

However, that binding/length check is only enforced for the `ParentAndFecSetCount` response, where `verify_response` explicitly computes the expected proof size from `fec_set_count` and rejects any mismatch: [4](#0-3) 

For the sibling `FecSetRoot` response type, the same function only checks that the proof is *non-empty* — it never checks that the proof length matches the expected tree depth for that leaf: [5](#0-4) 

Crucially, every FEC-set root fed into the double-Merkle tree as a "leaf" is itself produced by the exact same `join_nodes` function (same `MERKLE_HASH_PREFIX_NODE` prefix, same truncated 20-byte format) used to combine internal nodes of that same double-Merkle tree [6](#0-5) . The double-Merkle "leaves" are never re-hashed with a leaf-specific prefix before being inserted into `MerkleTree::try_new_with_len`; they are pushed in verbatim [7](#0-6) . Consequently, an *internal* node of the double-Merkle tree (e.g., the combination of two adjacent FEC-set roots) has the identical byte format as a *leaf* (a single FEC-set root), and `get_merkle_root`'s fold loop has no notion of "expected depth" — it simply keeps hashing until the running index reaches 0: [8](#0-7) 

## Impact Explanation

Because `verify_response` for `FecSetRoot` (i) accepts any non-empty proof length and (ii) the leaf/node domains for the double-Merkle tree collapse to the same hash construction, a malicious repair-response peer can:
1. Observe the real (public) block data for a slot, from which it can derive the real internal double-Merkle node that combines FEC-set-root at index *i* and index *i+1* (call it `N`).
2. Respond to a legitimate `BlockIdRepairType::FecSetRoot` request for index *i* with `fec_set_root = N` and a proof that is **one entry shorter** than the correct proof (omitting the sibling FEC-set root at index *i+1*, since `N` already encodes that combination).
3. `verify_merkle_proof` folds this truncated proof up to the real, correct `block_id`, so `verify_response` returns `true` even though `fec_set_root` is *not* the actual Merkle root of FEC set *i*'s shreds.

The requester then trusts `N` as the FEC-set root and issues `ShredRepairType::ShredForBlockId` requests using it, per the flow in `process_block_id_repair_response` [9](#0-8) . Every subsequent per-shred Merkle proof verification against this poisoned root will fail, since `N` is not the real per-shred tree root for that FEC set. This causes false acceptance of corrupted repair metadata (the exact "false execution/rooting/acceptance" class), wasting the round trip and stalling repair of that FEC set/block for the victim node — a low-cost, single-packet, non-RPC remote degradation of that node's ability to catch up on the affected slot.

## Likelihood Explanation

The attack requires only a single crafted UDP repair-response packet from any peer that legitimately receives a `FecSetRoot` request (which any repair-serving node can be selected to answer, per the decentralized/untrusted repair source model that the Merkle-proof verification exists to protect against). No brute-force hash collision search is needed — the attacker reuses a real, publicly-derivable internal hash value from the shreds already broadcast for that slot. The `debug_assert_eq!` on `fec_set_index` alignment is compiled out in release builds and provides no runtime protection anyway [10](#0-9) .

## Recommendation
In the `FecSetRoot` verification branch, compute the expected proof length the same way `ParentAndFecSetCount` does — either by requiring the caller to have already learned `fec_set_count` (e.g., cache it from the prior `ParentAndFecSetCount` exchange keyed by `block_id`) and enforce `fec_set_proof.len() == get_proof_size(fec_set_count + 1) * SIZE_OF_MERKLE_PROOF_ENTRY`, or add a leaf-domain prefix distinct from `MERKLE_HASH_PREFIX_NODE` when hashing FEC-set roots into the double-Merkle tree so an internal node can never validate as a leaf regardless of proof length.

## Proof of Concept
1. Let a slot have `fec_set_count = 4` (5 double-Merkle leaves: `L0..L3` = FEC-set roots, plus `PInfo`).
2. Real tree: `N01 = join(L0, L1)`, `N23 = join(L2, L3)`, `M = join(N01, N23)`, `P' = join(PInfo, PInfo)`, `root = join(M, P')` — all values are publicly derivable from the broadcast shreds for the slot.
3. Victim sends `BlockIdRepairType::FecSetRoot { fec_set_index: 0, block_id: root }` to a malicious peer.
4. Malicious peer replies with `FecSetRoot { fec_set_root: N01, fec_set_proof: [N23, P'] }` (2 entries instead of the correct 3-entry proof `[L1, N23, P']`).
5. `verify_response` -> `verify_merkle_proof(N01, 0, [N23, P'], root)`: fold gives `join(N01, N23) = M`, then `join(M, P') = root`; index reaches 0 -> `Ok(())` -> verified `true`, even though `N01 ≠` the real FEC-set-0 root [5](#0-4) [8](#0-7) .
6. The victim now issues shred repair requests believing `N01` is the FEC-set-0 root; all real shred proofs will fail against it, stalling repair for that FEC set.

```rust
// Recovers root of the merkle tree from a leaf node
// at the given index and the respective proof.
pub fn get_merkle_root<'a, I>(index: usize, node: Hash, proof: I) -> Result<Hash, Error>
where
    I: IntoIterator<Item = &'a MerkleProofEntry>,
{
    let (index, root) = proof
        .into_iter()
        .fold((index, node), |(index, node), other| {
            let parent = if index % 2 == 0 {
                join_nodes(node, other)
            } else {
                join_nodes(other, node)
            };
            (index >> 1, parent)
        });
    (index == 0)
        .then_some(root)
        .ok_or(Error::InvalidMerkleProof)
}
```
