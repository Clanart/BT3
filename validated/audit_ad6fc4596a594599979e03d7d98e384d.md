## Title
Unvalidated pull-request `head.ref` from the GitHub API is used to construct git remote/branch operations - (File: `app/src/lib/stores/app-store.ts`)

## Summary
The external report's core defect is that on-chain oracle responses (attacker/environment-controlled data) are consumed by protocol logic without validating that the value is sane or fresh before it drives further state changes. The closest verified analog in GitHub Desktop is the "Open Pull Request from Desktop" / PR-checkout flow, where the `head` object of a `pull_request` API response — which describes a **fork the PR author controls** — is passed straight into git remote and branch-creation calls without validating the ref name's shape.

## Finding Description
When a user opens a PR link (deep link `x-github-client://openrepo/...&pr=NNN`) or clicks "Checkout" on a PR from a fork, Desktop fetches the PR object from the GitHub API and forwards `pullRequest.head.repo.clone_url` and `pullRequest.head.ref` unchanged into `_checkoutPullRequest`/`_findPullRequestBranch`: [1](#0-0) 

```
await this.appStore._checkoutPullRequest(
  repository,
  pullRequest.number,
  pullRequest.head.repo.owner.login,
  pullRequest.head.repo.clone_url,
  pullRequest.head.ref
)
```

`_findPullRequestBranch` then concatenates the attacker-supplied `headRefName` into a remote ref string and hands it to `_createBranch`, which shells out to `git`: [2](#0-1) 

`head.ref` is the name of a branch in a **fork the attacker owns**, so its value is entirely attacker-controlled (it's not validated to be a "safe" git ref beyond whatever the GitHub API itself accepts). Nowhere in this path — `doesRepositoryMatchUrl`, `_findPullRequestBranch`, or `_createBranch` — is `headRefName` checked against a known-safe pattern (e.g., rejecting names beginning with `-` which git can interpret as command-line options for `git branch`/`git checkout`, or containing `..`/control characters) before being interpolated into `remoteRef` and passed to git plumbing.

This is structurally the same defect class as the oracle report: an externally-sourced value (there: an oracle price feed; here: a GitHub API object describing an attacker-owned fork) is trusted and threaded directly into a sensitive downstream operation without a validation gate.

## Impact Explanation
If a crafted branch name in an attacker's fork can be interpreted as a git command-line flag rather than a ref name when interpolated into the `git branch`/`git checkout` invocation used by `_createBranch`, this could enable argument injection against the local git invocation on the victim's machine, potentially altering how the branch is created/checked out (e.g., abusing flags such as `--upload-pack`/`-t`/`--track` depending on which git subcommand ultimately consumes `remoteRef`). This directly matches the "Valid Impact" criteria: the attacker controls a GitHub API object (their own fork/PR), and the target victim only has to click a PR/deep link — no local access, malware, or leaked credentials required.

## Likelihood Explanation
Likelihood is moderate rather than confirmed high: I was not able to inspect the internals of `_createBranch`/the exact git subcommand and argument ordering (i.e., whether a `--` separator is used before the start-point argument) within the available index, so I cannot confirm whether option injection actually succeeds against the current git plumbing wrapper. What is confirmed is that `headRefName` is untrusted, unsanitized, and reaches a shell-out to git without any format validation — the same "missing validation on external input before it's trusted" pattern the report flags, unlike the sibling code path (`openRepositoryFromUrl`'s `filepath` handling) which *does* validate via `resolveWithin`/`isAbsolute` before use: [3](#0-2) 

The absence of an equivalent guard for `head.ref` specifically indicates a validation gap on this path.

## Recommendation
- Validate `pullRequest.head.ref` against git's `check-ref-format` rules (or a conservative allow-list) before it is used to build `remoteRef`, `pr/${prNumber}` branch names, or any git command arguments.
- Ensure `_createBranch` (and any other call sites that accept a ref/start-point derived from API data) always pass user/API-controlled ref arguments after a literal `--` separator to git, preventing them from being interpreted as options.
- Apply the same treatment to `headCloneUrl`/`headRepoOwner` before use in `addRemote`.

## Proof of Concept
Because I could not confirm the exact argument layout used inside `_createBranch`'s underlying git invocation from the available index, I can outline the attack precondition but not a fully verified exploit string:
1. Attacker forks the target repository and creates a branch whose name is crafted to resemble a git command-line flag (e.g., starting with `-`).
2. Attacker opens a pull request from that branch and shares the PR link (or an `x-github-client://openrepo/...?pr=N` deep link) with the victim.
3. Victim opens the link/clicks "Checkout" in Desktop, triggering `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` → `_createBranch`, which threads the crafted `head.ref` value into a git invocation.

**Caveat:** I was unable to locate and inspect the body of `_createBranch`/the specific git command construction within the indexed code, so I cannot confirm whether an existing `--` separator or ref-format check already neutralizes this path. If a Devin session with full repository access confirms `_createBranch` passes the ref/start-point without a preceding `--`, this should be treated as a confirmed argument-injection bug; if it already guards against this (as several other paths in this codebase clearly do, e.g. `resolveWithin`, `sanitizeCloneName`, `isClonePathSensitive`), then the residual risk is limited to logic errors (checking out the wrong branch) rather than injection.
