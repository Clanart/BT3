### Title
OP_RETURN data output omitted from fee and weight calculation, underpaying the fee rate and bypassing the standardness weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

Analogous to the Cooler report (collateral computed without a required term, so the resulting position is economically under-reserved), `SignableTransaction::new` computes the transaction's vbytes — and hence the fee — from a `Transaction` template that includes only the payments and the optional change output. The OP_RETURN output carrying `data` (up to 80 bytes) is pushed into the real transaction's outputs at send.rs:194-202, yet is never passed to `calculate_weight_vbytes`. The resulting `needed_fee` is therefore `fee_per_vbyte` times a vsize that is ~10–90 vbytes smaller than the actual signed transaction.

### Finding Description

`calculate_weight_vbytes` reconstructs a template `Transaction` whose `output` vector contains only `payments` plus an optional `change` output:

- send.rs:85-99 — template outputs built from `payments` and `change` only
- send.rs:204 — `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` called *after* the OP_RETURN output is appended to `tx_outs` (send.rs:194-202), but the data output is not part of the template
- send.rs:225-226 — same omission for the with-change fee (`fee_with_change = fee_per_vbyte * vbytes_with_change`)
- send.rs:241 — `weight > MAX_STANDARD_TX_WEIGHT` check uses the same under-estimated `weight`

The actual transaction is then built with `tx_outs` which does contain the data output (send.rs:246-251). Every satoshi the change calculation reserves is `input_sat - payment_sat - fee_with_change`, so the fee paid is exactly `fee_with_change`, spread over a transaction that is actually larger — meaning the true feerate is strictly below the `fee_per_vbyte` the caller specified, and below what `needed_fee()` reports.

The same omission affects the `TooLowFee` guard at send.rs:211, which compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the too-small `vbytes`. A caller requesting exactly the minimum relay feerate with a large `data` payload produces a transaction whose *actual* feerate is below the minimum relay fee and which Bitcoin nodes will reject. It also affects the `TooLargeTransaction` standardness check, which can be passed while the real transaction exceeds `MAX_STANDARD_TX_WEIGHT` (each byte of OP_RETURN data adds ~1 vbyte / 4 WU unaccounted).

This is reachable purely through public inputs: `data` is an untrusted caller-supplied `Option<Vec<u8>>` parameter to `SignableTransaction::new`, and in the processor flow it is the serialized Serai `InInstruction`/metadata attached to transactions.

### Impact Explanation

The fee actually paid is `fee_per_vbyte` applied to a vsize missing the data output, so:

- Transactions specifying `data` always pay a lower feerate than requested — mispriced security accounting identical in shape to collateral being computed without the interest term.
- When `fee_per_vbyte` is at or near `DEFAULT_MIN_RELAY_TX_FEE`, the real feerate falls below the relay minimum and the transaction is rejected by the network — a threshold-signing round produces a signature over a transaction that can never confirm, burning the input selection and forcing re-planning.
- The max-standard-weight check is computed on a template missing up to ~80 bytes, so a boundary transaction with data can exceed `MAX_STANDARD_TX_WEIGHT` while passing `TooLargeTransaction`, again yielding an unbroadcastable signed transaction.

### Likelihood Explanation

Any caller of `SignableTransaction::new` that passes `Some(data)` triggers the underestimation unconditionally — no attacker precondition needed. The effect scales with `fee_per_vbyte` and the data length. The hard-failure modes (below min-relay, over max weight) require boundary fee rates / sizes, so the deterministic outcome is fee underpayment rather than guaranteed non-propagation — consistent with a Medium/High severity rather than critical.

### Recommendation

Include the OP_RETURN output in the weight/vbyte template. The cleanest fix is to build the template in `calculate_weight_vbytes` from the *actual* `tx_outs` (payments + data + change) rather than from `payments` alone — e.g., pass `&tx_outs` and the change script, or add a `data_len`/`Option<&ScriptBuf>` parameter so the data output's `TxOut` is included in the template before calling `tx.weight()`. The `TooLowFee` check at send.rs:211 and the `MAX_STANDARD_TX_WEIGHT` check at send.rs:241 then automatically operate on the correct size.

### Proof of Concept

```rust
// networks/bitcoin: construct a SignableTransaction with data and compare
// the reported fee rate to the real one.

let data = vec![0u8; 80]; // max allowed
let tx = SignableTransaction::new(
  vec![output],                       // a single ReceivedOutput
  &[(p2tr_script_buf(key).unwrap(), 1000)],
  Some(change_script),                // change so leftover is reserved exactly
  Some(data),
  fee_per_vbyte,
).unwrap();

let signed = sign(&keys, &tx); // real transaction, contains the OP_RETURN output
let actual_vsize = signed.vsize() as u64;

// needed_fee was computed WITHOUT the ~90 vbytes of the OP_RETURN output
assert!(tx.needed_fee() < actual_vsize * fee_per_vbyte);
// => effective feerate = needed_fee / actual_vsize < fee_per_vbyte
```

With `fee_per_vbyte` set so `needed_fee` exactly equals `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (passing the send.rs:211 check), the signed transaction's real feerate is `(DEFAULT_MIN_RELAY_TX_FEE * vbytes/1000) / (vsize + ~90)` — below the relay minimum — and `sendrawtransaction` rejects it.
