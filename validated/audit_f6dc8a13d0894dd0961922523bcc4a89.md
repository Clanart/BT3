### Title
Panic in `BlameMachine::blame_internal` via out-of-range `Participant` index allows remote denial of service - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame_internal` indexes `self.commitments[&sender]` with a `Participant` supplied by the caller. `Participant` is only validated as non-zero (`Participant::new` rejects solely `0`), while `commitments` is a `HashMap` populated strictly for participants `1..=n`. Passing a `sender` (or `recipient` via share verification) with index `> n` causes a `HashMap` index panic, crashing the calling process. This is reachable with public, untrusted inputs: blame accusations are submitted over the network naming arbitrary participant indexes.

### Finding Description
- `Participant::new` only rejects zero: `crypto/dkg/src/lib.rs:29-35` — any value `1..=65535` is a "valid" `Participant`.
- `BlameMachine`/`AdditionalBlameMachine` build `commitments` keyed only by `1..=n`: `AdditionalBlameMachine::new` inserts `Participant::new(i)` for `i in 1..=n` (`crypto/dkg/pedpop/src/lib.rs:656-660`), and `KeyMachine::calculate_share` inserts only `all_participant_indexes()` (`crypto/dkg/pedpop/src/lib.rs:313-336`).
- `blame_internal` then performs `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) inside `share_verification_statements::<C>(recipient, &self.commitments[&sender], ...)`, and `blame`/`AdditionalBlameMachine::blame` (`crypto/dkg/pedpop/src/lib.rs:623-631`, `674-682`) accept `sender`/`recipient` directly with no bound check against `n`.
- Neither `blame` nor `blame_internal` validates that `sender <= n` or `recipient <= n`. `self.commitments[&sender]` panics on a missing key (std `HashMap` indexing), and a `recipient` within range but `sender > n` (or vice versa) still hits the same panic path.

The downstream caller in Serai (processor `AdditionalBlameMachine::blame` invoked with `accuser`/`accused` parsed from a blame transaction, where `Participant` is deserialized with only the non-zero check) demonstrates this is reachable from unauthenticated network data, not just a local API misuse.

### Impact Explanation
A single crafted blame message naming a participant index greater than `n` (e.g., `u16::MAX`) panics the DKG blame-evaluation code, crashing the processor/coordinator task evaluating it. This is an unprivileged remote denial of service: the attacker needs only to cause an `InvalidDkgShare`-style accusation (or any `blame` invocation) referencing an out-of-range `Participant` to be processed. No valid key share, signature, or threshold cooperation is required — the panic occurs on a `HashMap` index before any cryptographic verification of the accused/accuser relationship.

### Likelihood Explanation
Blame messages are handled via a dedicated path whose entire purpose is evaluating accusations submitted by other parties. The `Participant` fields are attacker-controlled `u16`s; nothing in `Participant::new`, `AdditionalBlameMachine::new`, or `blame` constrains them to `<= n`. The DKG libraries document that callers must authenticate messages, but index-bounds validation is internal responsibility — the library itself panics rather than returning an error. Any deployment that processes blame for a DKG it observes (including `AdditionalBlameMachine`, explicitly designed for non-participants evaluating blame) is exposed.

### Recommendation
In `blame_internal` (and before use in `AdditionalBlameMachine::blame`/`BlameMachine::blame`), validate `sender` and `recipient` against the key set: return an error or a deterministic verdict when `u16::from(sender) > n` or `u16::from(recipient) > n`, e.g. treat the accuser/malformed accusation as faulty, or use `self.commitments.get(&sender)` and handle `None`. Similarly, `KeyMachine::calculate_share`'s `self.commitments[&l]` is currently protected by `validate_map`, but switching to `.get()` with explicit error handling would harden the code against future changes to the validation logic.

```rust
// After a completed PedPoP DKG producing a BlameMachine for params (t, n),
// or via AdditionalBlameMachine::new(context, n, commitment_msgs):
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker-controlled accusation naming a participant beyond n.
let evil_sender = Participant::new(u16::from(n) + 1).unwrap(); // valid non-zero Participant
let recipient   = Participant::new(1).unwrap();

// Any EncryptedMessage/EncryptionKeyProof values; the panic occurs before they matter.
machine.blame(evil_sender, recipient, msg, proof);

// (crypto/dkg/pedpop/src/lib.rs:599) -> process abort
```

The same panic is reachable through `BlameMachine::blame` (line 623) after `calculate_share` succeeds, since `blame_internal` performs no bounds check on `sender`/`recipient` before indexing `self.commitments`.
