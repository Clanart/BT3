### Title
Unbounded future oracle timestamp poisons the monotonic `last-update` check, permanently freezing price resolution - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` clamps the staleness delta to `u0` whenever the feed's reported timestamp `ts` exceeds `stacks-block-time`, with no upper bound on how far in the future `ts` is allowed to be. Any such timestamp is accepted as "fresh" and then persisted as the new `last-update` watermark for that `{type, ident}` feed. Because the monotonicity check requires all subsequent updates to satisfy `ts >= prev`, a single anomalously-far-future timestamp permanently (or for an extended period) blocks every later, correctly-timed price update for that feed from passing `oracle-timestamp-fresh`, causing `price-resolve` to revert with `ERR-ORACLE-INVARIANT` on every call that touches that asset's price.

The `if (> ts stacks-block-time) u0 ...` branch is meant to avoid an unsigned-subtraction underflow when the feed timestamp is slightly ahead of the local block clock (a plausible situation given Pyth's `publish-time` is a real-world Unix time that can outpace `stacks-block-time`, and DIA timestamps are converted from ms to s independently). However, this branch has no upper bound: no matter how large `ts` is relative to `stacks-block-time` (10, 1000, or 10^9 seconds in the future), `delta` is forced to `u0`, which trivially satisfies `(<= delta max-staleness)`. The price is accepted, and because `timestamp > last-update-time` triggers `(map-set last-update key timestamp)`, this arbitrarily-large `ts` becomes the new floor (`prev`) for the per-feed `last-update` map: [3](#0-2) 

On every subsequent call, the monotonicity clause `(>= ts prev)` in `oracle-timestamp-fresh` now compares the *next legitimate* (correct, near-real-time) `ts` against this inflated `prev`. Since legitimate timestamps will be far smaller than the poisoned `prev` until real-world time catches up, every future `price-resolve` call for that feed fails the `asserts!` and reverts with `ERR-ORACLE-INVARIANT`, regardless of how fresh and correct the new price actually is. This is a genuine logic defect in Zest's own freshness/monotonicity gate — it is not caused by bad data content or feed-price accuracy, but by the missing upper bound in `oracle-timestamp-fresh` and the unconditional persistence of any accepted future timestamp into the monotonic watermark.

### Impact Explanation
`price-resolve` (via `find-and-resolve-asset-value` / `get-asset-value` / `price-multi-resolve`) underlies every price-dependent operation in the market: `is-healthy` checks for borrowing, withdrawing collateral, and liquidation all call into this path. Once the `last-update` watermark for a feed is poisoned with a far-future timestamp, all operations requiring a fresh price for that asset revert, freezing borrowing, withdrawal, and liquidation for that asset until the real timestamp progression exceeds the poisoned value (which, for even a moderately large future skew, could take a long time). This is a temporary freezing of funds/functionality for users holding or borrowing that asset, and — critically — it also blocks liquidations, which can create additional risk if a position becomes unhealthy while price checks are disabled.

### Likelihood Explanation
This does not require a malicious DAO update or oracle data-content manipulation. It only requires the oracle to report a `publish-time`/timestamp that exceeds `stacks-block-time` by a large margin at least once — plausible from routine clock skew being amplified by an upstream bug in Pyth's relay/decoder pipeline, a misbehaving DIA timestamp read, or a temporary Stacks block-time lag/jump. Once that single anomalous value is written, the freeze is automatic and requires no further attacker action.

### Recommendation
Bound how far into the future a reported timestamp may be before it is treated as "fresh" (e.g., reject or clamp `ts` if `ts - stacks-block-time` exceeds a small tolerance, rather than forcing `delta` to `u0` unconditionally). Do not persist a timestamp into `last-update` that exceeds `stacks-block-time` beyond that tolerance, so a single anomalous reading cannot poison the monotonic watermark for the feed.

### Proof of Concept
1. Pyth (or DIA) reports, for feed `ident`, a `publish-time`/timestamp `ts0` that is far ahead of the current `stacks-block-time` (e.g., due to clock skew or an upstream decoding bug propagating a corrupted timestamp field) — call `price-resolve` for that asset.
2. `oracle-timestamp-fresh` computes `delta = u0` (since `ts0 > stacks-block-time`), passing the staleness check trivially; `(>= ts0 prev)` also passes since `prev` was previously smaller. `price-resolve` succeeds and stores `last-update[{type, ident}] = ts0`. [4](#0-3) 
3. On the next legitimate update, the feed reports a correct, near-real-time timestamp `ts1` where `stacks-block-time < ts1 < ts0`. Now `oracle-timestamp-fresh(ts1, ts0, max-staleness)` evaluates `(>= ts1 ts0)` as `false`, so the `and` fails.
4. `price-resolve` hits `(asserts! ... ERR-ORACLE-INVARIANT)` and reverts for every subsequent call, blocking borrow/withdraw/liquidate operations that need this asset's price, until real time advances past `ts0`.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
