### Title
Attacker-controlled participant count `n` in `ThresholdKeys::read` drives unbounded allocation and expensive point decoding — (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to GHSA-qpgv-g792-wh6x / CVE-2021-29932 (`parse_duration` letting an attacker-controlled numeric field — a huge exponent — dictate CPU/memory expenditure), `ThresholdKeys::read` in `crypto/dkg` lets a single attacker-controlled `u16` field (`n`) dictate both an allocation (`Vec::with_capacity(n)`) and a loop performing `n` field-element reads plus `n` elliptic-curve point decompressions (`read_G`), and, for `Interpolation::Constant`, `n` additional `read_F` calls, before any semantic validation of `n` occurs [1](#0-0) .

### Finding Description
`ThresholdKeys::read` parses the multisig parameters `t`, `n`, and `i` directly from the byte stream [2](#0-1) . It then immediately uses the raw `n` to:

1. `Vec::with_capacity(usize::from(n))` and loop `0 .. n` calling `C::read_F` when the interpolation tag is `0` (Constant) [3](#0-2) ,
2. Loop `1 ..= n` calling `C::read_G` for every claimed verification share [4](#0-3) ,
3. Only afterwards call `ThresholdParams::new(t, n, i)` / `ThresholdKeys::new`, which validate `n` [5](#0-4) .

`n` can be `65535`, so a short serialized blob causes ~65k expensive `read_G` decompressions (each involving field inversions / `sqrt_ratio_i`-style work) plus allocations. The same pattern exists transitively: `ThresholdKeys::new` computes `group_key` by iterating `1 ..= t` with a quadratic `interpolation_factor` evaluation per index over `&t` (`c[usize::from(u16::from(i) - 1)]` / Lagrange loop over `included`) [6](#0-5) [7](#0-6) . Lagrange interpolation is O(n²) field operations, so `n = 65535` implies ~4 billion field multiplications in `ThresholdKeys::new` — a severe CPU amplification from ~2 MB of input.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as an in-scope untrusted sink) can cause disproportionate CPU and memory consumption — a denial of service against any node/service that deserializes externally supplied threshold key material. With `n = 65535` and the Lagrange path, `ThresholdKeys::new`'s O(n²) interpolation makes the cost grow quadratically, mirroring the parse_duration "large exponent" amplification. This is a CWE-400 uncontrolled resource consumption analog.

### Likelihood Explanation
Reachability depends on `ThresholdKeys::read` being applied to untrusted input (e.g., key material supplied during reshare/recovery flows or peer-provided blobs). The read path runs before the `t > n`/`n` sanity checks in `ThresholdParams::new`, so no valid keyset is required — only a crafted prefix. Resource cost is bounded by `u16`, so impact is Medium rather than High: ~65k point decodes plus O(n²) field arithmetic per crafted input.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new` *before* allocating or looping on `n`, and cap `n` at the protocol's real maximum participant count. Reorder `read` to: parse params → construct/validate `ThresholdParams` → then read interpolation coefficients and verification shares bounded by the validated `n`.

### Proof of Concept
```rust
// Serialize a malicious ThresholdKeys blob for curve C:
//   C::ID len + ID || t=1u16 || n=0xFFFFu16 || i=1u16 || interp=1 (Lagrange)
//   || secret_share F || n * read_G bodies
let mut blob = vec![];
blob.extend((C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes());        // t
blob.extend(u16::MAX.to_le_bytes());    // n = 65535
blob.extend(1u16.to_le_bytes());        // i
blob.push(1);                           // Interpolation::Lagrange
blob.extend(C::F::ONE.to_repr());       // secret share
// 65535 valid encodings of the generator
for _ in 1 ..= u16::MAX {
    blob.extend(C::generator().to_bytes());
}
// ThresholdKeys::<C>::read(&mut &blob[..])
// -> ~65k read_G decompressions, then ThresholdKeys::new performs
//    O(n^2) Lagrange interpolation_factor work => CPU exhaustion.
```

```rust
    match self {

      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut denom = F::ONE;

        // (which we have an if case to avoid)
```
