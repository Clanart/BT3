### Title
Cached FROST preprocess survives participant removal, reusing identical nonces to sign a mutated `set_keys_message` — validator secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Grafana advisory's bug class is a capability that remains usable after the authorization for it was revoked. The Serai analog lives in the tributary confirmation signer: `SigningProtocol::preprocess_internal` caches a FROST preprocess seed under a context of only `(b"DkgConfirmer", attempt)` (coordinator/src/tributary/signing_protocol.rs:88,123-145) and deterministically re-derives the same nonces on every later call, while the signed message `set_keys_message(set, removed, key_pair)` embeds `removed`, the set of validators removed mid-attempt (signing_protocol.rs:296-301). A participant removal (`RemoveParticipantDueToDkg` / fatal slash, coordinator/src/tributary/handle.rs:258-283) changes `removed` *without* changing the context, so the node's next `share`/`complete` call signs a different message under the same nonce pair — classic FROST nonce reuse yielding the validator's MuSig secret share. Additionally, `preprocess_internal` builds the MuSig key over `spec.validators()` — the *unfiltered* validator list — so a removed validator's key remains inside the signing key and their shares remain valid after revocation (signing_protocol.rs:280,293; musig() at lines 118-120).

### Finding Description
Two interlocking defects in `DkgConfirmer`/`SigningProtocol`:

1. **Stale membership in the signing key.** `DkgConfirmer::preprocess_internal` and `share_internal` collect participants from `self.spec.validators()` (all validators, ignoring `self.removed`), then construct `ThresholdKeys` via `musig(musig_context(...), key, participants)` (signing_protocol.rs:118-121, 280-281, 293). The `removed` list is only applied when *mapping threshold indexes* in `threshold_i_map_to_keys_and_musig_i_map` (lines 214-249) and when forming the message. A validator fatally slashed / removed mid-attempt is thus still a constituent of the MuSig key: their preprocess and share continue to be accepted and their key share still contributes to the aggregate — the revoked capability keeps working, mirroring GHSA-wfhv-mj62-f5xh.

2. **Deterministic nonce reuse across a message that mutates on removal.** `preprocess_internal` stores a `CachedPreprocess` seed keyed only by `(b"DkgConfirmer", attempt)` (lines 88, 123-135) and every subsequent call — `share_internal` calls `preprocess_internal` again at line 156, and `complete` calls `share_internal` at line 322 — rebuilds the machine via `AlgorithmSignMachine::from_cache` → `seeded_preprocess`, which seeds `ChaCha20Rng` with the stored seed (crypto/frost/src/sign.rs:121-144, 268-274). The nonces `d, e` are therefore identical on every invocation for the attempt. The message signed is `set_keys_message(&set, &removed, key_pair)` (lines 296-301): if `removed` changes between two sign invocations — which is precisely what `RemoveParticipantDueToDkg` and `fatal_slash` do mid-attempt (handle.rs:258-283, 229) — or if `share` is retried with a different `key_pair`/preprocess set, two signature shares are emitted under the same `(d, e)` with different binding factors/challenges. Per FROST (`spec/cryptography/FROST.md`:51-62), reusing a preprocess enables third-party recovery of the private key share; here the reuse is forced by the cache rather than being caller misuse.

### Impact Explanation
Any party observing two `Share` publications from the same validator under the same `attempt` context but different `removed`/`key_pair` obtains two equations `s₁ = d + e·ρ₁ + λ·x·c₁`, `s₂ = d + e·ρ₂ + λ·x·c₂` in the two unknowns `d` and `λ·x`, recovering the validator's MuSig secret key share (the code itself notes recovery "will enable recovering the private key", line 104). The tributary confirmation signatures authenticate `set_keys` on-chain (substrate/validator-sets/pallet/src/lib.rs:1138-1142), so compromise of a threshold of shares forges validator-set key confirmations. Independently, removed (fatally slashed) validators retain signing capability inside the MuSig key, defeating the removal mechanism the confirmation is supposed to attest.

### Likelihood Explanation
Requires only that a removal lands mid-attempt while the node still produces `share`/`complete` for that attempt — an ordinary, race-free sequence since `removed_as_of_dkg_attempt` is evaluated at `DkgConfirmer::new` and the cache persists in `CachedPreprocesses`. The second signature is produced by honest code paths (share retry, `complete` re-signing at line 322), not adversarial timing. Recovery is passive observation of public share data.

### Recommendation
- Build the MuSig `participants` list from the *post-removal* set (`spec.i(removed, ...)`-filtered keys) in `preprocess_internal`/`share_internal`, so removal actually revokes signing capability.
- Include `removed` (and the key set) in the `CachedPreprocesses` context, or delete the cached seed when `removed` changes / after `share` succeeds, so nonces can never be replayed against a mutated message.
- In `crypto/frost`, consider making `from_cache`/`sign` consume-and-invalidate or requiring the caller to prove one-shot use, since the current design makes silent reuse the default for any re-entry.

### Proof of Concept
1. Attempt `a` of the tributary DKG begins; node calls `DkgConfirmer::new` with `removed = []`, publishes `preprocess()`. Seed `S` stored under `(b"DkgConfirmer", a)`; nonces `(d,e)` fixed by `S`.
2. `share(preprocesses, key_pair)` signs `m₁ = set_keys_message(set, [], key_pair)` → share `s₁` broadcast.
3. Validator `V` is fatally slashed (`handle.rs` `RemoveParticipantDueToDkg`), so `removed_as_of_dkg_attempt` now returns `[V]`.
4. The node's `complete` (or a re-instantiated `DkgConfirmer::share`) reloads `S`, regenerates identical `(d,e)`, and signs `m₂ = set_keys_message(set, [V], key_pair)` → share `s₂` with the same nonce commitments but a different challenge.
5. Observer solves the two-share linear system for `λ·x` and `d`, recovering the validator's secret share; `t` such recoveries forge the confirmation signature. The removed `V` likewise remains in `musig(...participants)`, so `V`'s own share is still accepted post-removal.

Caveat: the reachable path spans `coordinator/` code, which is outside the strictly enumerated in-scope crates; the nonce-derivation root cause (`seeded_preprocess`, `from_cache`) is in the in-scope `crypto/frost/src/sign.rs`. The analogous removed-but-still-signing behavior in the in-scope `crypto/frost` sign path itself (`sign.rs:283-313` accepts any `included ⊆ 1..=n` with no notion of revocation) is a documented-MUST misuse case and was therefore not used as the finding.
