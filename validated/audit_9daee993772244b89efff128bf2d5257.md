## Analysis

The external report's core invariant is: **a storage-layout change during an upgrade silently repurposes slots that other code paths still address by a fixed, hardcoded position, causing that other code to misinterpret unrelated state.**

I found a direct, code-supported analog in the `IntentGatewayV2` cross-chain cancellation logic.

### Key evidence
- `_filled` is a `mapping(bytes32 => address)` declared at storage slot 2, and the codebase hardcodes this fact as a constant used purely for **off-chain-constructed, cross-chain storage-proof key derivation** — not for any in-contract read: [1](#0-0) [2](#0-1) 

- This constant is used to build the ISMP `GET` request key that determines whether an order was filled on the destination chain, driving a **refund decision on the source chain**: [3](#0-2) 

- The gateway supports a governance-driven, cross-chain `UpgradeContract` action that swaps the ERC-1967 implementation behind the proxy. The only checks applied are that the request source is the Hyperbridge coprocessor and that the new implementation has code — there is **no validation that the new implementation preserves the storage layout**: [4](#0-3) 

- A dedicated regression test exists precisely because this is a known, fragile invariant, not an enforced one: [5](#0-4) 

### The break

`FILLED_SLOT_BIG_ENDIAN_BYTES` is a compile-time constant baked into the deployed bytecode of *every* `IntentGatewayV2` instance across all chains. It is never re-derived or asserted against the live implementation. If a legitimate protocol upgrade (via the `UpgradeContract` cross-chain governance path) ships a new implementation that adds or reorders a state variable ahead of `_filled` — exactly the kind of change the external report warns about — `_filled` moves to a different slot (e.g., slot 3), but `_calculateCommitmentSlotHash` on every gateway that has *not* independently patched this constant keeps pointing at slot 2.

Concretely, for **source-initiated cancellation**:
1. Destination gateway is upgraded to `V2'` which shifts `_filled` off slot 2.
2. A solver fills an order; `_filled[commitment]` is written correctly to the new slot, but old slot 2 is now occupied by different (empty/zero) data (or is simply unused after the shift).
3. The user calls `cancelOrder()` from the source chain (source gateway may or may not be upgraded — cross-chain proofs read the *destination* gateway's storage using the source gateway's still-stale constant).
4. Hyperbridge relays a storage read of slot 2 on the destination gateway — which reads zero/empty, because the actual fill status now lives at the new slot.
5. `onGetResponse` interprets the empty slot as "order not filled" and refunds the escrow to the user on the source chain, **even though the solver already delivered the output tokens to the beneficiary on the destination chain**.

This is a double-payment / fund-loss condition (solver pays out + escrow refunded), matching the bounty's "loss of funds" / "logic attack" impact class, and it does not require a malicious relayer, prover, or governance actor — only a legitimate, protocol-sanctioned upgrade that changes storage layout, which the `UpgradeContract` path permits with no layout-compatibility check.

### Title
Hardcoded `_filled` storage slot constant is invalidated by the ungated `UpgradeContract` path, enabling stale-slot cancel proofs and double payout - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase.sol` hardcodes `FILLED_SLOT_BIG_ENDIAN_BYTES = 0x…02`, assuming `_filled` permanently occupies storage slot 2, and uses this constant to build the cross-chain storage-proof key consumed by `_cancelFromSource` / `onGetResponse`. The `UpgradeContract` governance action (`RequestKind.UpgradeContract`, handled in `ExtrinsicIntents.sol`) swaps the ERC-1967 implementation with no storage-layout compatibility check — only source authentication and code-existence are verified. A layout-changing upgrade silently breaks the hardcoded slot assumption used elsewhere.

### Finding Description
`_calculateCommitmentSlotHash` derives the ISMP GET-request key purely from the compile-time constant `FILLED_SLOT_BIG_ENDIAN_BYTES`, independent of the actual, live storage layout of the target contract [6](#0-5) . This key is used by `_cancelFromSource` to build a `DispatchGet` request whose result gates a refund on the source chain [7](#0-6) . The `UpgradeContract` cross-chain governance action allows arbitrary implementation swaps subject only to authentication (must originate from Hyperbridge) and bytecode presence, never storage layout equivalence [4](#0-3) . Nothing on-chain enforces that `_filled` remains at slot 2 after such an upgrade — only a Foundry test asserts it as a convention [5](#0-4) .

### Impact Explanation
If a future implementation reorders storage (adding fields ahead of `_filled`, similar to the reported `LiquidityWindow` V1→V2 case), any `IntentGatewayV2` deployment that still references the stale `FILLED_SLOT_BIG_ENDIAN_BYTES` constant will read the wrong slot when proving fill status for cross-chain cancellation. An empty/zero read at the stale slot for an order that was actually filled causes the source chain to refund escrow to the user in addition to the solver already having been paid on the destination chain — a direct, unauthorized loss of protocol/solver funds.

### Likelihood Explanation
This does not require a malicious operator: it is triggered by a normal protocol upgrade cycle through the already-supported `UpgradeContract` governance flow, which performs no storage-compatibility validation. The only safeguard today is developer discipline plus a unit test (`testFilledMappingStaysAtSlotTwo`), not an on-chain or protocol-level guarantee, so the risk materializes on the very first upgrade that changes layout without every deployed gateway being resynced.

### Recommendation
Remove the compile-time slot constant dependency: derive `_filled`'s storage slot dynamically (e.g., via `keccak256`-based EIP-1967-style fixed slot allocation, or an on-chain getter that the relayer/SDK queries instead of hardcoding), or add an explicit storage-layout compatibility check/version tag validated during `UpgradeContract` processing before the swap is allowed to complete.

### Proof of Concept
Conceptual (build on existing tests):
1. Start from `testOnAcceptUpgradeContractPreservesState`, which already demonstrates the `UpgradeContract` path swapping implementations while preserving raw storage [8](#0-7) .
2. Deploy a new implementation identical to `IntentGatewayV2` but with one extra `address` state variable declared before `_filled`, shifting it to slot 3.
3. Perform the `UpgradeContract` onAccept flow on the destination gateway.
4. Fill an order post-upgrade (`_filled` now correctly set at slot 3).
5. On the source chain (still running the pre-upgrade `FILLED_SLOT_BIG_ENDIAN_BYTES = 2` constant), trigger `_cancelFromSource` and simulate the GET response reading slot 2 of the destination gateway (now unused/zero).
6. Observe `onGetResponse` treats the order as unfilled and refunds escrow, while the solver already received the destination-side payout — demonstrating the double-payment condition.

Note: I could not fully trace the exact `onAccept`/`UpgradeContract` dispatch implementation body in `ExtrinsicIntents.sol` within the available iterations (only the enum discriminant and test-observed behavior were confirmed); a full session should verify there is no additional storage-layout guard added elsewhere in that file before finalizing severity.
