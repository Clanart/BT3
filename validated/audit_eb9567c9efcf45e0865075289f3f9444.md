### Title
Silent redirect of a tracked repository's git remote to an attacker-controlled repo via unpinned owner/name matching - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
Desktop associates a local repository with a `GitHubRepository` by matching the current git remote's `owner/name` string against the GitHub API, not by any immutable GitHub repository ID. When Desktop periodically "refreshes" this association, it will silently rewrite the local `origin` remote URL to whatever `clone_url` the GitHub API returns for that `owner/name` pair, with no verification that the returned repository is the *same* repository the user originally added.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` re-derives the GitHub identity of a tracked local repository purely from the current remote URL: [1](#0-0) 

`matchGitHubRepository` in `app/src/lib/repository-matching.ts` extracts `owner`/`name` from the remote URL string and looks up an account by hostname only — it never checks a stored GitHub repository ID: [2](#0-1) 

The `owner`/`name` pair is then used to call `api.fetchRepository(owner, name)`, i.e. `GET repos/{owner}/{name}`. Whatever object the GitHub API returns for that path is trusted as "the same repository." The result is fed into `updateRemoteUrl`: [3](#0-2) 

The guard logic only checks: (1) the URL protocol hasn't changed, and (2) the *current* local remote still matches the previously cached `gitHubRepository.cloneURL`. It never verifies repository identity (e.g. GitHub's numeric repo `id`) before calling `gitStore.setRemoteURL(...)`, which directly executes `git remote set-url` on disk: [4](#0-3) 

This is the exact bug class from the report: a value that should stay in lock-step with a cached invariant (`gitHubRepository.cloneURL` ↔ actual remote) is instead updated from a mutable, externally-supplied source (the GitHub API response) without validating that the underlying entity is unchanged. Just as `USDE_GAS_COMPENSATION` changes retroactively corrupted every trove's derived debt without reconciling the invariant, here a changed `owner/name → repo` binding on GitHub's side (via the well-documented "repo-jacking" pattern — a repository or account is renamed/deleted, freeing the `owner/name` slug, and re-claimed by an attacker) silently corrupts the local git remote that Desktop trusts for all subsequent fetch/push operations. No user confirmation, diff, or identity check is shown.

### Impact Explanation
Once the app-store's periodic refresh (`repositoryWithRefreshedGitHubRepository`, called from many flows including `_publishRepository` and normal repository refresh) observes an `owner/name` that now resolves to an attacker-controlled repository, `updateRemoteUrl` rewrites `origin` to the attacker's `clone_url` with no prompt. Every subsequent `git fetch`/`pull` performed by Desktop will pull attacker-supplied history/content into the user's working copy (silent corruption of what the user later builds/commits on top of), and every subsequent `git push` will silently exfiltrate the user's commits/code to the attacker's repository instead of the intended destination — matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires only that the GitHub-side `owner/name` binding the user's remote points at gets reassigned to a different repository (classic repo-jacking: deleted/renamed account or repo, then re-registered by an attacker) — no local access, no malware, and no unusual user action; it happens automatically the next time Desktop refreshes the repository's GitHub association in the background. The likelihood is moderated by the fact that it depends on an external, opportunistic condition (slug becoming available) rather than being attacker-triggerable on demand against an arbitrary target.

### Recommendation
Before trusting `apiRepo` in `updateRemoteUrl`/`repositoryWithRefreshedGitHubRepository`, verify repository identity continuity using GitHub's immutable numeric repository `id` (already stored on `GitHubRepository`) rather than relying solely on `owner/name` string matching and URL comparison. If the `id` differs from the previously stored `GitHubRepository.dbID`/GitHub `id`, treat it as a different repository: do not auto-update the remote URL, and instead surface an explicit warning/prompt to the user before ever calling `git remote set-url`.

### Proof of Concept
1. User clones and tracks `https://github.com/alice/project` in Desktop; Desktop stores `gitHubRepository.cloneURL = https://github.com/alice/project` and matches it against the local `origin` remote.
2. Alice deletes her GitHub account or renames the repository, freeing the `alice/project` slug.
3. Attacker registers the `alice` username (or creates a same-named repo under an account reachable via the same slug) and creates a new repository `alice/project` with `clone_url = https://github.com/alice/project` (same string) but a different backing repository/content.
4. On its next background refresh, Desktop calls `matchGitHubRepository` → `api.fetchRepository('alice','project')`, gets the attacker's repo object, and passes it to `updateRemoteUrl`.
5. Because the cached `gitHubRepository.cloneURL` still textually matches the local remote and the protocol is unchanged, `remoteUrlUnchanged && !urlsMatch` short-circuits correctly to no-op only if the URL string is literally identical — but for any repo the attacker registers under a **different but redirect-eligible** owner/name history (e.g. project was renamed by Alice to `alice/project-old`, then attacker claims the freed `alice/project` and Desktop's next refresh, still querying by the stale local remote `alice/project`, receives the attacker's `clone_url`), `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', <attacker clone_url>)`, rewriting `.git/config` without any prompt. Subsequent `git fetch`/`push` from Desktop now silently targets the attacker's repository. [5](#0-4)

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
