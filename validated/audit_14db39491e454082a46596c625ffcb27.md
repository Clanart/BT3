## Analysis

The external report's core invariant: **swap output tokens sent to `address(this)` with no corresponding withdrawal/sweep mechanism become permanently trapped**. I searched Hyperbridge for public entrypoints that route native-token payments through a Uniswap swap where the destination is the contract itself, then checked whether leftover/excess value is properly returned to the caller.

`IntentGatewayV2.placeOrder()` performs the same `swapETHForExactTokens{value: msgValue}(...)` pattern for solver fees, but it explicitly captures the `amounts[0]` spent and refunds the remainder to `msg.sender` [1](#0-0) . `EvmHost.sol`'s core `dispatch()`/`fundRequest()` functions use the identical Uniswap V2 pattern but **do not** capture the swap output or refund the leftover native value at all.

### Title
Unrefunded Excess Native Token Permanently Stuck in `EvmHost` During Fee-Token Swap in `dispatch()`/`fundRequest()` - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all accept `msg.value` and swap it for an exact amount of `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. Unlike `IntentGatewayV2.placeOrder()`, which captures the swap's actual ETH spent (`amounts[0]`) and refunds `msgValue - amounts[0]` to the caller, `EvmHost` discards the return value and performs no refund logic.

### Finding Description
`swapETHForExactTokens` on Uniswap V2 refunds any unused ETH to `msg.sender` of that call — which, from the router's perspective, is `EvmHost` itself (since `EvmHost` is the contract invoking the router with `{value: msg.value}`), not the original end user who called `dispatch()`. [2](#0-1) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
```

No amount is captured from the swap, and there is no code path afterward that forwards leftover ETH back to `_msgSender()`. The same pattern (no refund) also exists in `dispatch(DispatchGet)` [3](#0-2)  and `fundRequest()` [4](#0-3) . Any ETH sent in excess of what the swap actually needs to produce `post.fee`/`get.fee`/`amount` worth of fee tokens is silently absorbed into `EvmHost`'s native balance with no sweep, withdrawal, or accounting mechanism exposed anywhere in the reviewed contract.

The project's own documentation acknowledges this exact risk class for the native-token dispatch path, noting it is subject to "Slippage (Yes - Uniswap swap)" and "Approximate (subject to slippage)" fee calculation [5](#0-4)  — meaning users are expected to send an approximate/rounded-up ETH amount, virtually guaranteeing leftover value on most calls, none of which is ever returned.

### Impact Explanation
Every unprivileged caller of `dispatch()`/`fundRequest()` who pays with native token instead of `feeToken` loses any ETH sent beyond the exact amount consumed by the internal swap. This is a direct, unconditional loss of user funds on a widely-used, public entrypoint of the core ISMP host contract, matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
High. This triggers on ordinary, expected usage — any caller who doesn't send the exact wei amount required for the swap (which is effectively unknowable in advance due to AMM slippage) loses the difference. No malicious relayer, prover, governance actor, or front-running is required; a single honest transaction with mildly generous `msg.value` suffices.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder()` [6](#0-5) . Alternatively, add an owner/permissionless sweep function limited to excess native balance beyond tracked accounting.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` requires only `0.4 ether` worth of ETH to acquire via the Uniswap V2 pool at current price.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes: it computes the required input (e.g., `0.4 ether`), performs the swap, and the router refunds the remaining `0.6 ether` to its `msg.sender`, which is `EvmHost`.
3. `EvmHost.dispatch()` never reads the swap's return value nor forwards any ETH back to the caller.
4. The `0.6 ether` becomes part of `EvmHost`'s native balance with no function anywhere to withdraw or account for it — permanently stuck, exactly as in the reported `DaosLive.finalize()` issue.
