### Title
Stale cached `decimals`/`name`/`symbol` in native ERC20 pointer contract after tokenfactory admin updates denom metadata - ([File: x/evm/precompiles/pointer/pointer.go], [File: contracts/src/NativeSeiTokensERC20.sol])

### Summary
A tokenfactory denom admin can create an ERC20 pointer for their own denom (via the `AddNativePointer` precompile method), and then later change that denom's `decimals`/`name`/`symbol` with `MsgSetDenomMetadata`. The already-deployed `NativeSeiTokensERC20` pointer contract caches `name`, `symbol`, and `decimals` as immutable constructor-set state variables, so it keeps returning the old values to any EVM contract that queries it, until someone explicitly re-invokes the pointer precompile to redeploy/upsert the pointer.

### Finding Description
The `NativeSeiTokensERC20.sol` pointer contract stores `nname`, `ssymbol`, and `ddecimals` as plain state variables set once in the constructor and returned directly by `name()`, `symbol()`, and `decimals()`: [1](#0-0) 

These values originate from the bank denom metadata fetched at pointer-creation time in `AddNative`, which is only called once when a user submits the `AddNativePointer` precompile transaction: [2](#0-1) 

A tokenfactory denom's admin (which, for a self-created denom, is the creating account — an ordinary, unprivileged sender) can later call `MsgSetDenomMetadata` to change `Name`, `Symbol`, or the `DenomUnits`/exponents (effectively changing "decimals") for that denom, as long as they are the recorded authority for the denom: [3](#0-2) 

This writes directly into the bank module's denom metadata store via `bankKeeper.SetDenomMetaData`, with no notification to, or synchronization with, any already-deployed ERC20 native pointer contract. The pointer contract's `decimals()`/`name()`/`symbol()` continue to return the stale values baked in at construction, since re-deriving them requires an explicit new pointer-registration call (`AddNativePointer` again, which upserts by redeploying constructor bytecode via `UpsertERCNativePointer`): [4](#0-3) [5](#0-4) 

This is the analog of the reported bug class: an ERC20-facing contract (the yToken/vault analog here is the Sei ERC20 native pointer) allows the underlying asset's metadata to be updated after third-party contracts have already cached/relied on `name`/`symbol`/`decimals`, and there is no on-chain mechanism forcing consumers to refresh those values.

### Impact Explanation
`decimals()` in particular is not purely cosmetic: EVM DeFi contracts (DEX routers, lending markets, vaults) commonly read `decimals()` once at integration/initialization time and use it to compute exchange rates, pricing, or normalization factors for the pointer token. If the tokenfactory admin later changes the denom's exponent/decimals via `MsgSetDenomMetadata`, any contract that cached the pointer's old `decimals()` value will apply the wrong scaling factor to the same underlying `usei`/wei balances returned by `BankPrecompile.balance`, leading to gross miscalculation of value (fund loss, mispriced swaps/collateral) for any protocol built atop that pointer. Because tokenfactory denom creation and metadata-setting are fully permissionless/self-service actions for the denom's own admin, this can be triggered by a single unprivileged account, and the effect (stale, incorrect state used in downstream financial computations) can result in concrete fund loss in third-party contracts integrating the pointer.

### Likelihood Explanation
Likelihood is dependent on: (1) a denom admin choosing to register an ERC20 pointer for their denom, (2) later altering that denom's metadata, and (3) a third-party contract having already cached/relied on the old `decimals`/`name`/`symbol`. All three steps are directly reachable by ordinary users/self-service tokenfactory admins with no special privilege — no governance, no validator collusion, no malicious peer involvement required — matching the "unprivileged... tokenfactory denom creator" reachable category. The likelihood of an integrator being affected depends on ecosystem usage patterns of the pointer (external), which is not verifiable purely from the repo, but the vulnerable code path itself is concretely and trivially reachable on-chain.

### Recommendation
- Either make `NativeSeiTokensERC20.decimals()/name()/symbol()` dynamically re-query the bank module (like `CW20ERC20Pointer.decimals()` already does for CW20) instead of caching, or
- Disallow decimals changes to a denom's metadata in `SetDenomMetadata` once a pointer has been registered for that denom, or
- Emit clear on-chain events/documentation warning integrators that pointer ERC20 metadata is not immutable and can change if the underlying denom's metadata is subsequently updated (mirroring the "short term" and "long term" recommendations from the referenced audit finding), and consider automatically triggering `UpsertERCNativePointer` as part of the `SetDenomMetadata` message handler so pointer bytecode stays in sync.

### Proof of Concept
1. Account A creates a tokenfactory denom `factory/A/foo` with `MsgCreateDenom`, then sets initial metadata with `decimals: 6` via `MsgSetDenomMetadata` (`x/tokenfactory/keeper/msg_server.go:188-217`).
2. Account A (or anyone) calls the `pointer` precompile's `addNativePointer("factory/A/foo")`, which deploys `NativeSeiTokensERC20` with `ddecimals = 6` baked into the constructor (`precompiles/pointer/pointer.go:93-126`, `contracts/src/NativeSeiTokensERC20.sol:17-23`).
3. A third-party EVM lending/DEX contract integrates the pointer address, calling `decimals()` once and caching `6` for pricing/normalization.
4. Account A later calls `MsgSetDenomMetadata` again for `factory/A/foo`, changing the top denom unit's exponent to `18` — this succeeds because A remains the recorded admin (`x/tokenfactory/keeper/msg_server.go:197-206`).
5. The pointer contract's `decimals()` still returns `6` (stale cached value; `contracts/src/NativeSeiTokensERC20.sol:37-39`), while the "real" intended decimals is now `18`. Any external contract relying on the initial cached `6` will now miscompute deposit/withdraw amounts against the pointer's `balanceOf`/`totalSupply` (which are always correctly scaled per the bank module's raw integer amount), causing a 10^12 magnitude mismatch in value accounting for that integrator.

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}

func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
	if err != nil {
		return
	}
	ctx.GasMeter().ConsumeGas(k.GetCosmosGasLimitFromEVMGas(ctx, suppliedGas-remainingGas), "ERC pointer deployment")
	if err = setter(liveCtx(), pointee, contractAddr); err != nil {
		return
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypePointerRegistered, sdk.NewAttribute(types.AttributeKeyPointerType, typ),
		sdk.NewAttribute(types.AttributeKeyPointerAddress, contractAddr.Hex()), sdk.NewAttribute(types.AttributeKeyPointee, pointee)))
	return
}
