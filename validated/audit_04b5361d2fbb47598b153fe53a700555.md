### Title
`ThresholdKeys::read` trusts an attacker-controlled `n` to pre-allocate a vector before any data is read - (File: crypto/dkg/src/lib.rs)

### Summary
The Avahi bug class is "documented limits ignored / unbounded resource consumption driven by unprivileged input → memory/FD exhaustion DoS". The direct Serai analog lives in `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: an attacker-controlled 2-byte `n` field drives `Vec::with_capacity(usize::from(n))` and two loops of `n` element reads, allocating memory proportional to the declared count rather than to bytes actually present. ~14 bytes of input can force a ~2 MB allocation (n = 0xFFFF × ~32-byte scalar); repeated invocations exhaust daemon memory with no data needing to back the claim.

### Finding Description
`ThresholdKeys::read` parses `(t, n, i)` as raw `u16`s straight from the wire at `crypto/dkg/src/lib.rs:591-602`. For `Interpolation::Constant` (tag `0`) it immediately executes `Vec::with_capacity(usize::from(n))` at `crypto/dkg/src/lib.rs:607-613`, committing `n * size_of::<C::F>()` bytes of heap regardless of whether any scalar bytes follow. Only afterward does the loop `for _ in 0 .. n { res.push(C::read_F(reader)?) }` attempt the reads, and the verification-share loop `for l in (1 ..= n)` issues another `n` `read_G` calls at `crypto/dkg/src/lib.rs:620-623`. Semantic validation (`ThresholdParams::new` checking `t <= n`, `i <= n`) only runs at the very end in `ThresholdKeys::new` at `crypto/dkg/src/lib.rs:625-631`, after the allocation and read work has already been performed. There is no cap on `n` tied to message size — the exact same defect as `client_new` unconditionally appending past `CLIENTS_MAX`.

The same pattern exists in `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`), which loops `u32::from_le_bytes(len)` times pushing `read_G` results, though that variant's cost scales with bytes actually delivered, making it weaker.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (an explicitly in-scope ingestion point) can request a ~65,535-element capacity vector with a 2-byte field — a >100,000× amplification between bytes sent and heap committed per call. Issued repeatedly, this causes memory exhaustion / OOM of the deserializing process (processor/coordinator-level DoS), matching the Avahi "exhaust daemon memory" impact. The subsequent read failures return `io::Error` but do not undo the already-committed allocation pressure and allocator churn.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a code path that deserializes `ThresholdKeys` from untrusted input, which in Serai's deployment is primarily local storage rather than a public socket — however the rules count untrusted bytes fed to `ThresholdKeys::read` as reachable, and the function is a public API with no documented precondition of trusted input. Per-request amplification is real but capped at ~u16::MAX elements (~2 MB per call), keeping this in Medium range rather than higher.

### Recommendation
Do not size allocations from untrusted length fields. Replace `Vec::with_capacity(usize::from(n))` with incremental `push` into `Vec::new()`, or enforce a sane bound (`n <= MAX_PARTICIPANTS`, e.g. the protocol's real participant ceiling) immediately after reading `n` and before any allocation or loop. Validate `t <= n` and `i <= n` up front (before the interpolation branch) rather than deferring all semantic checks to `ThresholdKeys::new`.

### Proof of Concept
```rust
// Feeding ~len(C::ID) + 11 bytes forces a ~2MB allocation
// (65535 * size_of::<C::F>) before any scalar is read.
let mut bytes = vec![];
bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
bytes.extend(C::ID);
bytes.extend(1u16.to_le_bytes());      // t = 1
bytes.extend(u16::MAX.to_le_bytes());  // n = 65535 -> with_capacity(65535)
bytes.extend(1u16.to_le_bytes());      // i = 1
bytes.push(0u8);                       // Interpolation::Constant
// Stream ends here. Vec::with_capacity already committed ~2MB;
// the first C::read_F then fails on EOF.
let res = ThresholdKeys::<C>::read(&mut bytes.as_slice());
assert!(res.is_err()); // but allocation already occurred
```
Repeating this parse in a loop against an attacker-controlled byte source exhausts process memory at a rate disproportionate to input size.
