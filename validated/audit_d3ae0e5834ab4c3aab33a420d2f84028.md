### Title
`extract_frontmatter()` uses naive `content.split('---', 2)` allowing a `pattern` value containing a literal `---` to truncate YAML frontmatter and silently downgrade `action: block` to the default `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter()` in `plugins/hookify/core/config_loader.py` splits the rule file on the literal string `---` using `content.split('---', 2)`. If the YAML frontmatter contains a field value (e.g., `pattern: a---b`) with an embedded `---` substring that appears before the real closing delimiter, that embedded substring is consumed as the second split point, truncating the parsed frontmatter and pushing all subsequent lines - including `action: block`/`enabled: true` - into the unparsed "message" body. `Rule.from_dict()` then applies its default `action = frontmatter.get('action', 'warn')`, silently converting an intended block rule into a warn rule.

### Finding Description
`extract_frontmatter()` performs:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
``` [1](#0-0) 

`str.split(sep, 2)` splits at the first two literal occurrences of `---`, left-to-right, regardless of YAML semantics (line boundaries). If a rule file is:
```
---
name: block-x
pattern: a---b
action: block
---

message body
```
the string contains three `---` occurrences in this order: the opening delimiter, the one embedded inside the `pattern` value, and the real closing delimiter. `split('---', 2)` treats the first two occurrences (opening delimiter + embedded `---` inside `pattern`) as the split points, so:
- `parts[1]` (parsed as frontmatter) = `"\nname: block-x\npattern: a"` - `pattern` value is also truncated, and `action: block` never appears in this segment.
- `parts[2]` (treated as free-text message) = `"b\naction: block\n---\n\nmessage body"` - the real `action: block` line is now inside the message body text, not parsed as YAML.

Because `action` is absent from the parsed `frontmatter` dict, `Rule.from_dict()` falls back to its default:
```python
action=frontmatter.get('action', 'warn'),
``` [2](#0-1) 

In `RuleEngine.evaluate_rules()`, rules are routed to `blocking_rules` only if `rule.action == 'block'`; otherwise they go to `warning_rules`, which never yields `permissionDecision: "deny"`: [3](#0-2) 

No validation, allowlist, or parser guard exists in this code path to detect that the frontmatter was truncated early or that a delimiter-like substring appeared inside a field value; `load_rule_file()` only checks that `frontmatter` is non-empty before proceeding, which it still is (it just has fewer keys than intended). [4](#0-3) 

### Impact Explanation
This breaks the "deny means deny" enforcement guarantee documented in the plugin: a rule file that visually and textually specifies `action: block` (e.g., blocking `rm -rf`, `dd`, credential exfiltration commands, etc., as shown in `plugins/hookify/README.md`) silently behaves as a non-blocking warning due to the parser bug, allowing the guarded dangerous operation to execute (`PreToolUse`/`PostToolUse` never receives `permissionDecision: "deny"`, and `Stop` events never receive `decision: "block"`). Any team or reviewer relying on committed `.claude/hookify.*.local.md` policy files as an enforcement/guardrail mechanism would have a false sense of security, since a crafted rule (or an accidentally malformed one) containing an embedded `---` in a `pattern`/condition value neutralizes enforcement without any error being surfaced to the operator at runtime.

### Likelihood Explanation
The only precondition is that a `.claude/hookify.*.local.md` rule file (checked into or landed in the repository, e.g., via a merged PR) contains a `pattern:` (or similar) value with a literal `---` substring positioned before the intended closing frontmatter delimiter. This requires no special privilege beyond the ability to add/modify a file in the repository - the same capability needed to introduce any other file-based misconfiguration - and the trigger condition (an embedded `---`) is trivial to construct and easy to disguise as an innocuous regex pattern (e.g., a date range or a name separator). The bug is deterministic and 100% repeatable given the crafted input.

### Recommendation
Rewrite `extract_frontmatter()` to find frontmatter delimiters by scanning whole lines equal to `---` (as most YAML frontmatter parsers do), rather than doing a raw string split on the `---` substring, e.g., split `content` into lines and find the first line that is exactly `---` (index 0) and the next line that is exactly `---` afterward, treating everything between as frontmatter and everything after as the message. This prevents any field value containing `---` from being mistaken for a delimiter.

### Proof of Concept
```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-x
event: bash
pattern: a---b
action: block
---

Blocked!
"""

frontmatter, message = extract_frontmatter(content)

# Bug: 'action' (and possibly other post-delimiter fields) missing from frontmatter
assert 'action' not in frontmatter, "action leaked into frontmatter unexpectedly"

rule = Rule.from_dict(frontmatter, message)
assert rule.action == 'warn'  # should have been 'block'

from plugins.hookify.core.rule_engine import RuleEngine
engine = RuleEngine()
rule.conditions = [__import__('plugins.hookify.core.config_loader', fromlist=['Condition']).Condition(
    field='command', operator='regex_match', pattern='rm -rf')]
result = engine.evaluate_rules([rule], {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"}
})
assert result.get("hookSpecificOutput", {}).get("permissionDecision") != "deny"
```
Expected: both assertions pass, demonstrating that a rule file explicitly declaring `action: block` is parsed with a missing `action` key and evaluated by `RuleEngine.evaluate_rules()` as a warning (never `permissionDecision: "deny"`), confirming the silent block→warn downgrade.
