### Title
Operator falsely attributed as payout payer via unsigned OP_RETURN in payout transaction, leading to unauthorized reimbursement claim - (File: core/src/verifier.rs, core/src/task/payout_checker.rs)

### Summary
The `payout_payer_operator_xonly_pk` recorded for a withdrawal is derived purely from the OP_RETURN output of the on-chain payout transaction, parsed by `update_finalized_payouts` without any cryptographic binding to the actual operator that funded the payout. Because the user's withdrawal signature is verified with a sighash flag that (per the code's own comment) is expected to be `SIGHASH_SINGLE|ANYONECANPAY`, the OP_RETURN output sits outside the signed commitment, allowing a withdrawer to reuse their own presigned input to construct a payout-shaped transaction naming an arbitrary, non-consenting operator as the fronting party.

### Finding Description
The broken binding is: `payout_payer_operator_xonly_pk` stored for withdrawal `i` (used to trigger `PayoutCheckerTask`/`handle_finalized_payout` for that operator) should equal the operator that actually expended its own funds to pay output[0] of the payout transaction for withdrawal `i`.

- `Operator::withdraw` (`core/src/operator.rs:560-637`) builds the payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which embeds `operator_xonly_pk` (the calling operator's own key) into an **unsigned** OP_RETURN output (index 2), while the input is spent via a single Schnorr signature verified against the user's key with `in_signature.sighash_type` — expected but not code-enforced to be `SIGHASH_SINGLE|ANYONECANPAY` (see the error message at `core/src/operator.rs:637`).
- Under `SIGHASH_SINGLE|ANYONECANPAY`, only input 0 and output 0 (the user payout output) are committed to by the signature; outputs 1 (anchor) and 2 (OP_RETURN operator pubkey) are **not covered**.
- The withdrawer, who is the one who originally produced `in_signature` when calling `withdraw()`/`safeWithdraw()` on Citrea, therefore already possesses a valid signature that can be reused in a self-constructed transaction with an arbitrary OP_RETURN payload naming any 32-byte value as "operator_xonly_pk", per `get_first_op_return_output`/`parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:608-617`, `686-692`).
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) trusts this OP_RETURN unconditionally and writes it into the DB via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`).
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) picks up the withdrawal keyed solely by `get_first_unhandled_payout_by_operator_xonly_pk(operator_xonly_pk)` and calls `operator.handle_finalized_payout(...)` (`core/src/operator.rs:839-916`) for whichever operator's key happens to be named — with no check that this operator's wallet/UTXO actually funded output[0].
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that `payout_payer_operator_xonly_pk` (same forged value) equals `kickoff_data.operator_xonly_pk`, which trivially matches because the named operator's own node performs the kickoff using its own key — this guard is self-consistent with the forged data and does not catch the forgery.
- The bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs:206-229`) similarly derives `operator_xonlypk` from the same unauthenticated OP_RETURN for `deposit_constant`, so a later dispute/disprove circuit will also treat the forged attribution as ground truth.

None of the existing guards (`is_kickoff_malicious`, SPV verification, storage-proof verification) check that the named operator's own capital was spent in the payout transaction; they only check self-consistency between the OP_RETURN value and the kickoff signer, which the attacker fully controls by choosing the OP_RETURN content.

### Impact Explanation
This allows the deposit's move-to-vault BTC (matching a specific withdrawal) to be released via kickoff/reimbursement to an operator that never fronted anything, falling under the Critical category "an operator reimbursed for a payout it never funded." The withdrawer already receives their withdrawal amount from their own self-spent UTXO (output 0, which is signature-committed and cannot be altered), so this does not require any operator cooperation — it can be repeated for any withdrawal where the withdrawer chooses to self-front, against any target operator's public key (which is publicly known), draining bridge reserves to arbitrary/unwilling operators and disrupting the protocol's collateral accounting. It also forces the named operator to spend a kickoff connector and open a challenge window they never intended, exposing them to griefing (loss of round bandwidth / added liveness assumptions) even before any BTC moves.

### Likelihood Explanation
Precondition: the attacker only needs to be the registered withdrawer for a Citrea withdrawal index (a normal, unprivileged action) and self-front by spending the registered `withdrawal_utxo` themselves. The claim rests on the withdrawal signature using `SIGHASH_SINGLE|ANYONECANPAY` — which the code's own error message says is expected ("Ensure the signature uses SinglePlusAnyoneCanPay sighash type"), but I could not fully confirm from the retrieved code whether the sighash type is a hard-enforced constant or merely conventional/documented (the actual construction/enforcement point, e.g. in `core/src/rpc/parser/operator.rs`, was not retrievable within the available search budget). If sighash type is indeed enforced to be `SIGHASH_SINGLE|ANYONECANPAY` (as the codebase's naming and documentation strongly suggest), the attack is essentially free (only Bitcoin fees) and fully repeatable across withdrawals/operators. If some other enforcement elsewhere pins the entire transaction (e.g., `SIGHASH_ALL`) or validates the OP_RETURN independently, the vulnerability would be moot.

### Recommendation
Bind the OP_RETURN operator-attestation output to the user's signature (e.g., require `SIGHASH_ALL` or `SIGHASH_ALL|ANYONECANPAY` covering all outputs, or otherwise commit to the OP_RETURN content within the sighash message), so a withdrawer cannot rewrite the operator attribution post hoc. Additionally, require operator-specific proof of funding (e.g., an operator signature over the payout tx, or verifying that the payout output was actually funded/paid by the claimed operator's UTXO/wallet, not merely by an arbitrary OP_RETURN value) before crediting `payout_payer_operator_xonly_pk`.
