### Title
Unbounded recursive decoding of nested `AccountKeyRoleBased` account keys allows unauthenticated stack-overflow DoS - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
Kaia's `AccountKeyRoleBased` type recursively decodes its own serialized form via both JSON (`UnmarshalJSON`) and RLP (`DecodeRLP`), by re-invoking the generic `AccountKeySerializer` decoder for each inner element. Because `AccountKeyType` allows a `RoleBased` key type as one of the possible inner key types, and the "nested composite type is not allowed" rule is enforced only *after* decoding completes (`CheckInstallable`/`CheckUpdatable`), an attacker can submit an arbitrarily deeply nested `RoleBased(RoleBased(RoleBased(...)))` account key. Each nesting level adds another recursive Go call, and with no depth limit during decode, sufficiently deep nesting can exhaust the goroutine stack and crash the whole node — this is a fatal runtime stack overflow, not a recoverable `panic`, so the `recover()` guard in the RPC callback dispatcher cannot save the process.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` and `AccountKeyRoleBased.UnmarshalJSON` iterate over the encoded inner keys and recursively call `AccountKeySerializer`'s decode functions, which in turn call `NewAccountKey` for the declared inner `AccountKeyType` and decode into it: [1](#0-0) 

`AccountKeySerializer.DecodeRLP`/`UnmarshalJSON` construct a new `AccountKey` of whatever type is declared (including `AccountKeyTypeRoleBased` again) and decode into it: [2](#0-1) 

`NewAccountKey` has no restriction preventing `AccountKeyTypeRoleBased` from being instantiated as a nested element type at decode time: [3](#0-2) 

The only place nested composite keys are rejected is `CheckInstallable`/`CheckUpdatable`, which run *after* the full (already recursively decoded) structure is built: [4](#0-3) 

This means the recursion depth during decode is bounded only by how much encoded data the attacker supplies, not by any explicit nesting-depth check. A single crafted `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction (or a direct call to the public `kaia_decodeAccountKey`/`kaia_encodeAccountKey` RPC methods) with deeply nested `RoleBased` keys triggers this unbounded recursion: [5](#0-4) 

Transaction decoding for `TxInternalDataAccountUpdate`/`TxInternalDataFeeDelegatedAccountUpdate` invokes the same recursive `AccountKeySerializer`/RLP decode path before any nested-type validation occurs: [6](#0-5) [7](#0-6) 

RPC method calls are wrapped in a `recover()`, but a genuine Go stack-overflow is a fatal, unrecoverable runtime error (`runtime: goroutine stack exceeds ... limit`), so this guard cannot prevent a full process crash: [8](#0-7) 

### Impact Explanation
Any unauthenticated network caller (RPC client or transaction sender) can crash a Kaia node process by submitting a crafted, deeply nested `RoleBased` account key — either as raw transaction bytes to the public transaction-submission RPC, or directly to `kaia_decodeAccountKey`/`kaia_encodeAccountKey`. Because a real stack overflow terminates the Go runtime rather than being caught as a panic, the entire node (RPC service, block production/validation participation) goes down, producing a denial of service. If widely exploited against many nodes simultaneously (e.g., broadcast as a pending transaction across the p2p network before rejection), this could impact network availability broadly, matching the CVSS High/DoS characteristic of the original Rancher bug class.

### Likelihood Explanation
The attack requires only crafting a sufficiently deep nested `RoleBased` account key structure and submitting it either via RLP-encoded transaction bytes (e.g., `eth_sendRawTransaction`) or via the public `kaia_decodeAccountKey`/`kaia_encodeAccountKey` API — no authentication, special privileges, staking, or prior state is needed. The complexity is bounded by the maximum transaction/call payload size, but Go's default goroutine stack limit (typically far smaller than the max transaction size allows for encoding thousands of nesting levels) makes triggering the overflow practically feasible with moderately sized payloads.

### Recommendation
Enforce a maximum nesting depth for `AccountKeyRoleBased` decoding at the point of decode (both `DecodeRLP` and `UnmarshalJSON`), rejecting any inner key whose declared type is `AccountKeyTypeRoleBased` immediately instead of allowing recursive decode-then-check. This mirrors the disallowed "composite type" rule but must be applied *during* decoding, not only after the whole structure is materialized, e.g. by having `AccountKeySerializer`'s decode paths reject `AccountKeyTypeRoleBased` as an invalid nested key type outright (since nested `RoleBased` keys are never valid per `IsCompositeType`/`ErrNestedCompositeType`).

### Proof of Concept
1. Construct a JSON/RLP-encoded `AccountKeySerializer` payload where `keyType == AccountKeyTypeRoleBased` and its `key` field is itself a `RoleBased` serializer, nested recursively N times (N large enough, e.g. tens of thousands of levels, within the max tx/RPC payload size).
2. Submit this as the `Key` field of an `AccountUpdate` transaction via the public raw-transaction submission RPC, or call `kaia_decodeAccountKey`/`kaia_encodeAccountKey` directly with the crafted bytes/JSON.
3. Decoding recurses through `AccountKeyRoleBased.DecodeRLP`/`UnmarshalJSON` → `AccountKeySerializer.DecodeRLP`/`UnmarshalJSON` → `NewAccountKey(AccountKeyTypeRoleBased)` N times before any `CheckInstallable`/`ErrNestedCompositeType` check runs, exhausting the goroutine stack and causing a fatal, unrecoverable crash of the node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (s *KaiaAPI) EncodeAccountKey(accKey accountkey.AccountKeyJSON) (hexutil.Bytes, error) {
	if accKey.KeyType == nil {
		return nil, errors.New("key type is not specified")
	}
	key, err := accountkey.NewAccountKey(*accKey.KeyType)
	if err != nil {
		return nil, err
	}
	if err := json.Unmarshal(accKey.Key, key); err != nil {
		return nil, err
	}
	// Invalidate zero values of threshold and weight to prevent users' mistake
	// JSON unmarshalling sets zero for those values if they are not exist on JSON input
	if err := checkAccountKeyZeroValues(key, false); err != nil {
		return nil, err
	}
	accKeySerializer := accountkey.NewAccountKeySerializerWithAccountKey(key)
	encodedKey, err := rlp.EncodeToBytes(accKeySerializer)
	if err != nil {
		return nil, errors.New("the key probably contains an invalid public key: " + err.Error())
	}
	return (hexutil.Bytes)(encodedKey), nil
}
