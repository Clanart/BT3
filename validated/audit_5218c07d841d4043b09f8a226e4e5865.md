## Title
`getResolutionDiff()` / manual conflict resolution treats git's `ours`/`theirs` stages as literal even though a rebase swaps their meaning, risking silent commit of the wrong side - (File: `app/src/lib/git/diff.ts`)

### Summary
`getResolutionDiff()` documents that `stage: 'ours' | 'theirs'` maps directly to git's merge-index stages 2 and 3, and explicitly warns that **during a rebase git swaps these** — the upstream branch becomes `ours` and the commit being replayed becomes `theirs` — and that "the caller is responsible for mapping user-facing labels to the correct git side." [1](#0-0)  This is structurally the same class of bug as the Yieldy `_storeRebase()` report: a function is called with a value (`'ours'`/`'theirs'`) that looks correct by name but represents the wrong side of the operation relative to what the caller/UI intends, because the responsibility for re-mapping was pushed onto the caller instead of being enforced by the API.

### Finding Description
`ManualConflictResolution.ours`/`theirs` strings are passed straight through to `git checkout --ours`/`--theirs` [2](#0-1)  and to `getResolutionDiff()`'s stage lookup (`:2`/`:3`) [3](#0-2) . The UI layer (`copilot-conflicts-changes.tsx`, `copilot-conflicts-dialog.tsx`) builds its "Use current file from `<branch>`" / "Use incoming file from `<branch>`" labels via `getOursTheirsLabels()` [4](#0-3)  using `ourBranch`/`theirBranch` values threaded through the conflict state, and then feeds the user's choice straight to `getResolutionDiff(..., { stage: choice }, ...)` [5](#0-4) . Nowhere in these code paths is there a rebase-specific remap step that swaps `'ours'` and `'theirs'` before calling `getResolutionDiff` or `checkoutConflictedFile`/`stageManualConflictResolution` [6](#0-5)  — the comment in `diff.ts` places that burden entirely on "the caller," but no caller in the codebase appears to perform this remapping for the rebase flow.

Since GitHub Desktop's rebase conflicts originate directly from replaying an attacker-influenced upstream commit's content against the target branch (an attacker who controls a branch/PR that the user rebases onto, or a commit the user cherry-picks/rebases, fully controls the conflicting content on one side), a caller-label mismatch here means the label the user clicks (e.g. "Use current file from main") can silently resolve to the git stage that actually contains the attacker's incoming content rather than the user's own branch content, or vice versa.

### Impact Explanation
This directly matches the "silent corruption of what the user commits or pushes" impact category. If the `ours`/`theirs` labels are not correctly swapped for the rebase case, the user believes they are keeping their own code (per the UI label) but the file staged via `checkoutConflictedFile`/committed via the rebase actually contains the other side's content — controlled by whoever authored the branch/commit being rebased onto or replayed. This can silently reintroduce reverted vulnerable code, drop security fixes, or splice attacker content into a commit that gets pushed, without any error or warning to the user.

### Likelihood Explanation
This requires: (1) the user performs a rebase (or cherry-pick, which also swaps semantics relative to "current branch" framing) against an attacker-controlled branch/commit, and (2) the conflict UI's `ourBranch`/`theirBranch` → git-stage mapping is not correctly inverted for that flow. Given the explicit warning comment in the source acknowledging this exact class of mistake is easy to make and dependent entirely on caller discipline, and given that the remap logic was not found in any of the calling code paths inspected (`copilot-conflicts-changes.tsx`, `copilot-conflicts-dialog.tsx`, `copilot-resolution-helpers.ts`, `dispatcher.ts` rebase methods), likelihood is credible but **not fully confirmed** — I could not exhaustively trace every code path (e.g. `base-rebase.tsx`, `unmerged-file.tsx`) to determine with certainty whether a remap exists elsewhere that neutralizes the risk. This should be treated as a likely-but-unverified finding requiring manual confirmation.

### Recommendation
Move the rebase-vs-merge `ours`/`theirs` swap into `getResolutionDiff()`, `checkoutConflictedFile()`, and `stageManualConflictResolution()` themselves (e.g. by passing an explicit `operationKind: 'merge' | 'rebase' | 'cherry-pick'` parameter) rather than relying on comments instructing every caller to remember to invert the mapping. Add a regression test that simulates a rebase conflict and asserts that choosing "keep my current branch's version" in the UI actually resolves to the target branch's content, not the replayed commit's content.

### Proof of Concept
Not independently reproduced — this is a code-path analysis based on the documented caller-responsibility comment at `app/src/lib/git/diff.ts:428-434` and the absence of a discoverable rebase-specific remap in the Copilot conflict-resolution UI call sites. A concrete PoC would require: creating a repo, starting `git rebase` where the target commit's incoming change and current commit's change conflict, opening the Desktop conflict-resolution dialog during that rebase, selecting "Use current file from `<branch>`", and verifying via `git show :2:<path>` / `:3:<path>` whether the staged/committed content matches the label the user actually clicked.

```typescript
/**
 * Returns the ours/theirs dropdown labels for a conflicted file, handling
 * both delete-vs-modify and regular text conflicts.
 */
export function getOursTheirsLabels(
  status: ConflictedFileStatus | undefined,
  ourBranch?: string,
  theirBranch?: string
): { readonly oursLabel: string; readonly theirsLabel: string } {
  if (status !== undefined && isDeleteConflictFile(status)) {
    return getDeleteConflictLabels(status, ourBranch, theirBranch)
  }

  const oursLabel = ourBranch
    ? `Use current file from ${ourBranch}`
    : 'Use current file'
  const theirsLabel = theirBranch
    ? `Use incoming file from ${theirBranch}`
    : 'Use incoming file'
  return { oursLabel, theirsLabel }
}
```

```typescript
export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
```
