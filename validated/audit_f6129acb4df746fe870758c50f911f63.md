### Title
`ThresholdKeys::read` accepts attacker-crafted secret share / verification shares without consistency proof, allowing a fully attacker-known group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, a `secret_share`, and `n` verification shares from untrusted bytes, then calls `ThresholdKeys::new`. Neither function verifies that `secret_share` is consistent with `verification_shares[i]` (i.e. `G * secret_share == verification_shares[i]`), nor that the verification shares form a coherent polynomial. `ThresholdKeys::new` derives `group_key` purely as the interpolation of the *attacker-supplied* `verification_shares[1..=t]` [1](#0-0) . The bug-class analog to unrestricted file upload: a blob the code treats as trusted structured key material is accepted with no proof of internal consistency, so the consumer can be made to operate on keys whose group key is entirely attacker-controlled.

### Finding Description
`ThresholdKeys::read` reads `C::ID`, `t`, `n`, `i`, the interpolation variant, one scalar `secret_share`, and `n` group elements, then constructs `ThresholdKeys` [2](#0-1) . `ThresholdKeys::new` only checks: count of verification shares equals `n`, participant indices `<= n`, and that `Constant` interpolation implies `t == n` [3](#0-2) . It then computes `group_key = Σ verification_shares[j] * interpolation_factor(j, [1..=t])` and stores everything unconditionally [4](#0-3) .

Two distinct violations result:

1. **No share/commitment consistency.** The node's own `secret_share` is never checked against `verification_shares[i]`. During signing, `view()` interpolates `secret_share` and expects shares to verify against `verification_shares` [5](#0-4) . With mismatched material the node either produces invalid signature shares, or — if the attacker supplies a *self-consistent but fully known* set (choose `s`, set `verification_shares[j] = G * s_j` for shares of a known polynomial) — operates under a group key whose discrete logarithm the attacker knows.

2. **Arbitrary group key.** Because `group_key` is derived only from the supplied verification shares over participants `1..=t`, the deserializer can embed *any* target group key. Combined with (1), a key blob claiming to be the validator set's threshold key can actually encode a key the attacker can spend from unilaterally.

Contrast with legitimate construction paths (`key_gen`, PedPoP `calculate_share`, `musig`, `GeneratorPromotion::complete`), all of which derive verification shares from proven contributions — e.g. PedPoP computes verification shares from verified commitments [6](#0-5) . The deserializer skips the entire verification pipeline.

### Impact Explanation
If an unprivileged party can cause a validator/processor to load a `ThresholdKeys` blob they supplied (backup restore, key-import path, or any untrusted input routed to `ThresholdKeys::read`), they can install a group key whose aggregate secret they fully know. Any Bitcoin/funds sent to the resulting `group_key()` (e.g., via `p2tr_script_buf`/scanner registration on that key) are spendable by the attacker alone — the threshold provides no security. Alternatively, an inconsistent blob yields a node that emits shares failing verification, causing incorrect signing/blame behavior. This satisfies the "incorrect verifier/accepted material" and "key material misuse" acceptance criteria rather than mere DoS when the attacker-chosen shares are self-consistent.

### Likelihood Explanation
Requires an attacker to get bytes into a `ThresholdKeys::read` call. The serialized format is a raw, unauthenticated, self-describing blob (curve ID + params + scalars + points) [7](#0-6) , so any ingestion point that doesn't authenticate origin is exposed. Consistency checking costs one scalar multiplication (`G * secret_share == verification_shares[i]`) plus optionally verifying `group_key` recomputation — clearly an omitted check rather than a design constraint. Rated Medium–High: exploitation needs a reachable untrusted ingestion path, but requires no threshold collusion or key leakage once reached.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Consider additionally committing the group key or requiring callers to supply the expected `group_key` so a deserialized blob cannot silently redefine the validator's identity. Document that `read` alone does not establish that the shares form a valid `t`-of-`n` polynomial.

### Proof of Concept
```rust
// Attacker chooses an arbitrary secret polynomial they know.
let s1 = C::F::random(rng); // share for participant 1
// ... generate t self-consistent shares s_1..s_n of a known polynomial
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes());
blob.extend(n.to_le_bytes());
blob.extend(1u16.to_le_bytes()); // i = 1
blob.push(1);                    // Interpolation::Lagrange
blob.extend(s1.to_repr().as_ref());
for j in 1..=n {
    blob.extend((C::generator() * s_j).to_bytes().as_ref());
}
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();
// keys.group_key() is now a key whose discrete log the attacker knows,
// yet it is accepted as a valid threshold key set.
assert_eq!(keys.group_key(), C::generator() * known_group_secret);
```
