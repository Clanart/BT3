### Title
Cached FROST preprocess seed reused across multiple `sign()` calls enables private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::share_internal` rebuilds a deterministic `AlgorithmSignMachine` from a seed stored in `CachedPreprocesses` on every invocation, and `DkgConfirmer` calls it twice for one signing session: once in `share()` and again inside `complete()`. Because the same ChaCha20 seed regenerates the same FROST nonces, any divergence in the preprocess set or message between the two calls produces two signature shares under one nonce — directly enabling algebraic recovery of the signer's secret key share, the classic "use-after-consumption" analog of use-after-free for a two-round Schnorr threshold signing protocol. [1](#0-0) 

### Finding Description
`preprocess_internal` writes the cached seed once (`if CachedPreprocesses::get(...).is_none()`) and then unconditionally reloads and reuses it; the entry is never deleted or rotated after a `sign()`. [2](#0-1) 

`from_cache` → `seeded_preprocess` feeds that seed into `ChaCha20Rng::from_seed`, regenerating identical `nonces` and `commitments` every time. [3](#0-2) 

`DkgConfirmer::share` produces and broadcasts a signature share via `share_internal`. `DkgConfirmer::complete` then calls `share_internal` **again** — a second `machine.sign(preprocesses, msg)` under the same nonce — before completing the signature. [4](#0-3) 

A Schnorr-style FROST share is `s_i = nonce_i + λ_i · c · share_i`. Two shares with the same `nonce_i` but different `c` (different signing set → different binding factors `rho` → different challenge, or different `key_pair` → different `msg`) yield a linear system that recovers `nonce_i`, and hence the private share — exactly the failure the FROST spec warns about. [5](#0-4) 

The file's own safety argument concedes the flaw: nonce reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" — which is precisely what `share()` + `complete()` do. Safety is asserted only via BFT message finality; nothing in this code enforces that the second `sign()` sees byte-identical inputs. [6](#0-5) 

### Impact Explanation
If the `preprocesses` map or `key_pair` passed to `complete()` differs in any way from what `share()` signed (a different signer subset, an additional late-arriving preprocess, or a different key pair), the coordinator publishes two valid shares under one nonce. Any observer of both shares can solve for the secret key share of that validator, compromising its MuSig/FROST root-of-trust key. This is concrete key-share recovery, the highest-impact outcome in scope.

### Likelihood Explanation
The nonce reuse is unconditional — `share_internal` is invoked at least twice per confirmation. Whether the second call diverges depends on upstream callers in `coordinator/src/tributary/handle.rs` passing identical preprocess sets to `share` and `complete` (I could not fully verify the caller behavior within the available iterations). If the inputs ever differ — reachable via messages an unprivileged participant causes to be gossiped/finalized, or a benign difference in which preprocesses were collected at each stage — the leak triggers. The defense is purely an ordering assumption, not a cryptographic check; the acknowledged TODO to verify on-chain commitments match presumed nonces is unimplemented. [7](#0-6) 

### Recommendation
- Derive distinct nonces per `sign()` call (e.g., include a monotonically increasing counter or the digest of `preprocesses || msg` in the cached-seed context) so a second call cannot regenerate identical nonces.
- Alternatively, hash `share()`'s exact `(preprocesses, msg)` at first use and have `complete()` abort — rather than re-sign — if the inputs differ.
- Implement the noted check that published nonce commitments match the commitments derived from the cached seed before publishing any share.

### Proof of Concept
1. A validator executes `DkgConfirmer::share(preprocesses_A, key_pair)` → publishes share `s1` under nonce `k` (seed from `CachedPreprocesses[(b"DkgConfirmer", attempt)]`).
2. `DkgConfirmer::complete(preprocesses_B, key_pair', shares)` is invoked with any differing set/message → `share_internal` regenerates nonce `k` and publishes share `s2` under a different challenge `c'`.
3. Attacker computes `k = (s1 - s2) / (λ·c - λ'·c')` and recovers the secret share from `s = k + λ·c·x`.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
