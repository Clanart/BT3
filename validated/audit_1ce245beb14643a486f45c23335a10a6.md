## Title
Shell-metacharacter injection via repository path when launching Cygwin - (File: `app/src/lib/shells/win32.ts`)

## Summary
`Win32.launch()` builds the Cygwin launch command by interpolating the untrusted repository working-directory `path` inside a **single-quoted** `sh -lc` argument, and the directory name that becomes part of `path` is only sanitized against path-traversal/separator characters — not against shell metacharacters such as `'`. A single quote in the repository's local folder name breaks out of the `-lc '...'` quoting and lets the rest of the string be interpreted as separate shell commands.

## Finding Description
`launch()` handles `Shell.Cygwin` like this: [1](#0-0) 

```
case Shell.Cygwin:
  const cygwinPath = `"${foundShell.path}"`
  return spawn(
    cygwinPath,
    [`/bin/sh -lc 'cd "$(cygpath "${path}")"; exec bash'`],
    { shell: true, cwd: path }
  )
```

`path` here is `repository.path`, the local clone directory, propagated unmodified from `App._openShell` → `AppStore._openShell` → `launchShell` → `Win32.launch`. [2](#0-1) [3](#0-2) 

The clone directory name is derived from the attacker-supplied clone URL (or `x-github-client://openRepo` deep link) via `sanitizeCloneName`, which only splits on `/`, `\`, `:` and rejects `..`/`.` traversal segments — it does **not** strip or reject other shell-significant characters such as `'`, `` ` ``, `$`, or `;`: [4](#0-3) 

This sanitized (but not shell-escaped) name is joined into the clone path in `updateUrl`/`onChooseWithOpenDialog` in the Clone dialog and becomes the eventual `repository.path`: [5](#0-4) 

Because the `path` value is embedded inside a single-quoted `-lc` string, a folder name containing `'` terminates that quoting early. Everything after the injected `'` is executed as literal shell syntax by `/bin/sh -lc`, allowing arbitrary command injection (e.g. appending `'; touch pwned; '`), which mintty/Cygwin will execute when the shell session starts.

## Impact Explanation
If reachable, this results in arbitrary command execution in the user's Cygwin/mintty environment merely from choosing "Open in <shell>" on an attacker-influenced repository — a plausible, low-friction user action. That satisfies the "code execution from attacker-controlled repository content/URL" impact class in scope.

## Likelihood Explanation
Exploitation requires several conditions that reduce likelihood substantially:
1. The victim must have Cygwin installed and have selected it as their configured/default shell in GitHub Desktop (Cygwin is not the default; `Default = Shell.Cmd`). [6](#0-5) 
2. A single quote must survive into the actual repository name/local folder. GitHub-hosted repository names do not permit `'`, so this path realistically only applies to generic/self-hosted git URLs typed or deep-linked by the user, whose `name` capture group is unconstrained by character class: [7](#0-6) 
3. The user must explicitly invoke "Open in Shell" for that specific repository.

I could not fully verify within the available context whether `resolveCloneInfo()`/`API` calls (for GitHub-recognized repos) further constrain or re-derive the `name` from the API's `name` field (which GitHub restricts to a safe character set) versus using the raw regex-parsed `name` from the user-typed/deep-linked URL for the "generic" clone tab. The generic/URL clone path (`CloneRepositoryTab.Generic`, used by `openOrCloneRepository` for deep links) appears to rely on the unrestricted regex capture, which is the more concrete attack surface.

## Recommendation
- Do not interpolate `path` into a hand-built shell command string at all; instead pass the working directory via `spawn`'s `cwd` option (already set) and drop the `cd "$(cygpath ...)"` step, or resolve `cygpath` synchronously in Node and pass the safe, escaped path as a separate `-lc` argument component.
- If the `cd`-via-cygpath approach must be kept, properly escape `path` for POSIX single-quoted contexts (replace `'` with `'\''`) before interpolation, consistently with how other shell-launch code paths should also be validated (Git Bash's `--cd="${path}"` argument has the same class of risk if `path` contains `"`).
- Additionally, harden `sanitizeCloneName` (or add a follow-up validation step before it is used to build a filesystem path that will later be shell-quoted) to reject characters that are meaningful to shells (`'`, `` ` ``, `$`, `;`, `|`, `&`, newlines) in addition to path separators, since this value flows into shell-launch code on multiple platforms.

## Proof of Concept
1. Attacker crafts a generic git clone URL such as:
   `https://evil.example.com/owner/name'; touch ~/pwned #.git`
   (or a `github-mac://openRepo/...` / `x-github-client://openRepo/...` deep link that resolves to a name containing `'`), and gets the victim to open it via the Clone dialog / deep link.
2. `parseRepositoryIdentifier` → `sanitizeCloneName` returns the name largely intact except for stripped trailing `.git` and `/`/`\`/`:` splitting; the embedded `'` is preserved.
3. The repository is cloned into a directory such as
   `C:\Users\victim\Documents\GitHub\name'; touch ~/pwned #`.
4. Victim (having Cygwin configured as their preferred shell) selects the repository and clicks "Open in Shell".
5. `Win32.launch()` builds:
   `/bin/sh -lc 'cd "$(cygpath "C:\...\name'; touch ~/pwned #")"; exec bash'`
   — the single quote in the path closes the `-lc` argument early, and `; touch ~/pwned #` (or any injected payload) is executed by `/bin/sh` as a separate command when Cygwin/mintty starts.

I was not able to execute this against a live build to confirm mintty's exact argv-splitting behavior with `shell: true` on Windows; this should be validated by a Devin agent with a Windows + Cygwin test environment before treating this as fully confirmed, but the source-level quoting flaw is clearly present as shown above.

export async function launchShell(
  shell: AnyFoundShell,
  path: string,
  onError: (error: Error) => void
): Promise<void> {
  // We have to manually cast the wider `Shell` type into the platform-specific
  // type. This is less than ideal, but maybe the best we can do without
  // platform-specific build targets.
  const exists = await pathExists(shell.path)
  if (!exists) {
    const label = __DARWIN__ ? 'Settings' : 'Options'
    throw new ShellError(
      `Could not find executable for '${shell.shell}' at path '${shell.path}'.  Please open ${label} and select an available shell.`
    )
  }

  let cp: ChildProcess | null = null

  if (__DARWIN__) {
    cp = Darwin.launch(shell as FoundShell<Darwin.Shell>, path)
  } else if (__WIN32__) {
    cp = Win32.launch(shell as FoundShell<Win32.Shell>, path)
  } else if (__LINUX__) {
    cp = Linux.launch(shell as FoundShell<Linux.Shell>, path)
  }

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
