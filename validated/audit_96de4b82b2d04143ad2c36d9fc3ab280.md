### Title
Arbitrary file write outside the repository tree via a symlinked `.gitignore`, preserving the target's permission bits (including the executable bit) — (`app/src/lib/git/gitignore.ts`)

### Summary
`saveGitIgnore` and `readGitIgnoreAtRoot` operate on `Path.join(repository.path, '.gitignore')` without ever checking whether that path is a symbolic link. Because Node's `fs.readFile`/`fs.promises.writeFile` do not use `O_NOFOLLOW` by default, a `.gitignore` that is checked out as a symlink pointing outside the repository will be transparently followed on both read and write, letting a malicious repository redirect Desktop's file I/O to an arbitrary path on the user's filesystem.

### Finding Description
`readGitIgnoreAtRoot` reads `ignorePath` with plain `FS.readFile` [1](#0-0) , and `saveGitIgnore` writes it back with `writeFile(ignorePath, fileContents)`, no flags or mode supplied [2](#0-1) . Neither function `lstat`s the path first, so if git checked out `.gitignore` as a symlink (git tracks and restores symlinks verbatim, without validating their target), both the read and the write transparently follow that link to whatever it points to, even outside the working tree.

Regarding the specific question about permission bits: on POSIX, the `mode` argument passed to `open()` (and therefore to `fs.writeFile`, which defaults to flag `'w'` i.e. `O_WRONLY|O_CREAT|O_TRUNC`) is only applied by the kernel when a *new* inode is created. When the target of the symlink already exists, `O_TRUNC` only truncates and rewrites its contents — the existing `st_mode` (owner/group/other bits, including the executable bit) is left untouched. So yes: if `.gitignore` is a symlink to a pre-existing file that has the executable bit set, `saveGitIgnore`'s overwrite will preserve that executable bit while replacing the file's byte content.

The content that ends up written is not, however, fully attacker-controlled shell code in the simple "edit and Save" flow: it is whatever text sits in the Repository Settings → Ignored Files textbox, which itself was populated by `readGitIgnoreAtRoot` following the same symlink (i.e., largely the target file's own original content, reformatted only for CRLF handling by `formatGitIgnoreContents`), plus any edits the user makes [3](#0-2) [4](#0-3) . That write only occurs after the user actively edits the ignore text and clicks Save (`ignoreTextHasChanged`) [5](#0-4) .

A more directly reachable path is the "Ignore file" context-menu action, which calls `appendIgnoreFile` → `appendIgnoreRule` → `saveGitIgnore` [6](#0-5) [7](#0-6) . Here Desktop reads the (symlink-followed) current contents, appends a new pattern line derived from the path of the file the user chose to ignore (only `[ ] ! * # ?` are escaped — other shell metacharacters in a filename are not) [8](#0-7) , and writes the result back through the symlink, again preserving the target's permission bits.

### Impact Explanation
The primitive that is reliably demonstrable is: **file write outside the repository tree**, corrupting an arbitrary file the running user account can write to, while leaving that file's existing permission bits (including `+x`) intact. This matches the bounty's "file write... outside the repo" impact category on its own.

Escalating this to guaranteed remote code execution ("a later unrelated Desktop or shell action executes it") is not established by the code alone — it requires (a) the attacker knowing or guessing an absolute path to an existing executable/script the victim will later invoke (e.g. a shell rc file at a predictable `$HOME` path), and (b) the injected content (mostly a preserved copy of the original file plus a filename-derived line) to happen to be valid/malicious script syntax. That chain is plausible in specific circumstances (e.g., targeting a shell startup file with a crafted filename containing shell metacharacters via the "Ignore file" action) but is speculative and environment-dependent, not a direct, code-guaranteed consequence.

### Likelihood Explanation
Requires a natural user action — either editing/saving the Ignored Files tab in Repository Settings, or using the "Ignore file" context-menu action on a tracked file — after cloning an attacker-controlled repository whose `.gitignore` is a symlink. Both are ordinary, expected workflows a user might perform on an untrusted clone, so this does not require unnatural or contrived steps, though it is not automatic on clone/fetch alone.

### Recommendation
Before reading or writing the ignore file, `lstat` the resolved `.gitignore` path and refuse to proceed (or refuse to follow the link) if it is a symlink, or open it with `O_NOFOLLOW`/verify via `fs.realpath` that the resolved path stays within `repository.path`. Apply the same treatment anywhere else in the codebase that reads/writes well-known repo-root files (e.g. `.gitattributes`, git config) by path join without an `lstat`/containment check.

### Proof of Concept
1. Create a repository containing a tracked symlink `.gitignore -> /home/<victim>/.bashrc` (or any other file the victim's Desktop process can write) and commit it.
2. Have the victim clone this repository with GitHub Desktop.
3. Open Repository Settings → Ignored Files (this calls `readGitIgnoreAtRoot`, which follows the symlink and shows the target's content in the textbox), make a trivial edit, and click Save (or alternatively, use "Ignore file" from the Changes list context menu on any tracked file).
4. Inspect the target file (`/home/<victim>/.bashrc`): its content has been overwritten/appended by `saveGitIgnore`'s `writeFile(ignorePath, fileContents)` call, while `stat` shows its original mode bits (including any pre-existing execute bit) unchanged, confirming that `writeFile` truncates in place rather than recreating the inode.

export async function readGitIgnoreAtRoot(
  repository: Repository
): Promise<string | null> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  return new Promise<string | null>((resolve, reject) => {
    FS.readFile(ignorePath, 'utf8', (err, data) => {
      if (err) {
        if (err.code === 'ENOENT') {
          resolve(null)
        } else {
          reject(err)
        }
      } else {
        resolve(data)
      }
    })
  })
}

export async function saveGitIgnore(
  repository: Repository,
  text: string
): Promise<void> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  if (text === '') {
    return new Promise<void>((resolve, reject) => {
      FS.unlink(ignorePath, err => {
        if (err) {
          reject(err)
        } else {
          resolve()
        }
      })
    })
  }

  const fileContents = await formatGitIgnoreContents(text, repository)
  await writeFile(ignorePath, fileContents)
}
```

/** Add the given pattern or patterns to the root gitignore file */
export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}
```

export async function appendIgnoreFile(
  repository: Repository,
  filePath: string | string[]
): Promise<void> {
  if (filePath instanceof Array) {
    const escapedFilePaths = filePath.map(path =>
      escapeGitSpecialCharacters(path)
    )

    return appendIgnoreRule(repository, escapedFilePaths)
  }

  const escapedFilePath = escapeGitSpecialCharacters(filePath)
  return appendIgnoreRule(repository, escapedFilePath)
}

/** Escapes a string from special characters used in a gitignore file */
export function escapeGitSpecialCharacters(pattern: string): string {
  const specialCharacters = /[\[\]!\*\#\?]/g

  return pattern.replaceAll(specialCharacters, match => {
    return '\\' + match
  })
}
