**Investigation summary:** I searched the Aptos-native publish/upgrade/ownership analogs to the ERC-4337 bug class (a self-call/context switch causing a caller-identity check to compare against the wrong address):

- `aptos_framework::code::publish_package` performs its owner/upgrade checks directly against `signer::address_of(owner)` with no intermediate self-call or context switch that could substitute the wrong address. [1](#0-0) 
- `aptos_framework::code::freeze_code_object` checks `object::is_owner(code_object, signer::address_of(publisher))` directly against the actual transaction signer, with no delegated/self-call path that could desynchronize the checked identity. [2](#0-1) 
- `aptos_experimental::large_packages` threads the same `owner: &signer` through `stage_code_chunk_internal` → `publish_to_account`/`publish_to_object`/`upgrade_object_code` without any external self-call substitution that would change the effective caller. [3](#0-2) 
- `aptos_framework::object_code_deployment` documents that upgrade/freeze require asserting the `code_object` is owned by `publisher` before an `ExtendRef`-derived signer is generated for the object itself; this is an intentional and separate signer (the object's own address), not a substitute for the caller-identity check — conceptually different from the Sequence bug's `msg.sender` corruption. I was not able to retrieve the full function bodies of `publish`/`upgrade`/`freeze_code_object` in this file due to index truncation, so I could not independently verify the exact ordering/implementation of that ownership assertion beyond what the module doc-comments and the linked `code.move`/tests describe. [4](#0-3) 

None of the located code paths reproduce the ERC-4337 bug-class invariant (an unprivileged self-call/context change silently altering the identity used in a caller/ownership check) with a provable, unprivileged root cause and exact corrupted value. Given the required strict evidence bar (exact corrupted field + local proof), I'm not reporting a finding for the `object_code_deployment.move` gap — the visible parts of the codebase (doc comments, `code.move`, tests) are consistent with correct ownership checks, and I could not obtain contradicting evidence from the indexed content.

/// This module allows users to deploy, upgrade and freeze modules deployed to objects on-chain.
/// This enables users to deploy modules to an object with a unique address each time they are published.
/// This modules provides an alternative method to publish code on-chain, where code is deployed to objects rather than accounts.
/// This is encouraged as it abstracts the necessary resources needed for deploying modules,
/// along with the required authorization to upgrade and freeze modules.
///
/// The functionalities of this module are as follows.
///
/// Publishing modules flow:
/// 1. Create a new object with the address derived from the publisher address and the object seed.
/// 2. Publish the module passed in the function via `metadata_serialized` and `code` to the newly created object.
/// 3. Emits 'Publish' event with the address of the newly created object.
/// 4. Create a `ManagingRefs` which stores the extend ref of the newly created object.
/// Note: This is needed to upgrade the code as the signer must be generated to upgrade the existing code in an object.
///
/// Upgrading modules flow:
/// 1. Assert the `code_object` passed in the function is owned by the `publisher`.
/// 2. Assert the `code_object` passed in the function exists in global storage.
/// 2. Retrieve the `ExtendRef` from the `code_object` and generate the signer from this.
/// 3. Upgrade the module with the `metadata_serialized` and `code` passed in the function.
/// 4. Emits 'Upgrade' event with the address of the object with the upgraded code.
/// Note: If the modules were deployed as immutable when calling `publish`, the upgrade will fail.
///
/// Freezing modules flow:
/// 1. Assert the `code_object` passed in the function exists in global storage.
/// 2. Assert the `code_object` passed in the function is owned by the `publisher`.
/// 3. Mark all the modules in the `code_object` as immutable.
/// 4. Emits 'Freeze' event with the address of the object with the frozen code.
/// Note: There is no unfreeze function as this gives no benefit if the user can freeze/unfreeze modules at will.
///       Once modules are marked as immutable, they cannot be made mutable again.
