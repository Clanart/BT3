### Title
Missing zero-address check on pool `target_puzzle_hash` allows farming rewards to be irrecoverably burned - ([File: chia/pools/pool_wallet.py])

### Summary
`PoolWallet._verify_pool_state()` only checks that `state.target_puzzle_hash` is not `None`, but never checks that it isn't the null/zero puzzle hash (`bytes32.zeros`). This mirrors the reported bug class: a constructor/state validator that fails to reject the "null address" sentinel value, allowing an object (here, a pool wallet / plot-NFT singleton) to be created in a state that can never function correctly — in this case, sending farmed rewards to an unspendable destination.

### Finding Description
`PoolWallet._verify_pool_state()` is the single validation gate used both when a user proposes a new target pool state locally and when the wallet parses a `PoolState` observed on-chain in a launcher or travel spend: [1](#0-0) 

```
@classmethod
def _verify_pool_state(cls, state: PoolState) -> str | None:
    if state.target_puzzle_hash is None:
        return "Invalid puzzle_hash"
    ...
```

This is invoked by `_verify_initial_target_state()` when creating a new pool wallet, which raises only if `_verify_pool_state` returns a non-empty error string: [2](#0-1) 

The check `state.target_puzzle_hash is None` only rejects the Python `None` sentinel. It does **not** reject `bytes32.zeros` (32 zero bytes) — the "null address" equivalent for a puzzle hash. Since `target_puzzle_hash` is a `bytes32` field (not `Optional[bytes32]` at the type level in practice, since `None` is guarded against but the all-zero value is a perfectly valid `bytes32` and passes every subsequent check), a `PoolState` with `target_puzzle_hash = bytes32.zeros` sails through validation for both `SELF_POOLING` and `FARMING_TO_POOL`/`LEAVING_POOL` states (`_verify_self_pooled` / `_verify_pooling_state` only check `pool_url` and `relative_lock_height`, never the puzzle hash).

`target_puzzle_hash` is used directly as the final payout destination for the pool singleton's inner puzzle (`pool_state_to_inner_puzzle()`, `create_pooling_inner_puzzle()`, `create_waiting_room_inner_puzzle()`), meaning any coin absorbed by this singleton in self-pooling mode, or claimed via a waiting-room exit, would be sent to a `CREATE_COIN` with puzzle hash `0x00...00`. Puzzle hash zero has no known preimage/spending path (it does not correspond to any standard puzzle a wallet can construct a solution for), so a coin created at that puzzle hash is permanently unspendable — value is effectively burned.

This is the direct analog of the reported issue: `MerchantSubscription`'s constructor accepted `merchant == 0x0`, silently creating a contract instance that could never be activated/used. Here, `_verify_pool_state` accepts `target_puzzle_hash == 0x00...00`, silently creating a pool wallet whose future rewards can never be spent.

### Impact Explanation
If a user (via CLI/RPC `create_new_pool_wallet` or a pool response) is passed or otherwise ends up with a zero `target_puzzle_hash` (e.g., a buggy pool client, malicious pool leave/travel payload the wallet parses from on-chain `PoolState`, or a UI bug that fails to fill in a puzzle hash), the wallet will not reject it. All farming/pool rewards subsequently absorbed to that target are burned with no recovery path — a concrete case of unrecoverable value loss triggered by ordinary wallet-driven or pool-driven state transitions, not by a malicious peer exploiting cryptography. This satisfies the "unauthorized/irrecoverable coin movement" criterion (funds sent to a destination nobody can spend from), reachable through a normal plotnft/pool state transition.

### Likelihood Explanation
Medium. The bug requires a zero `target_puzzle_hash` to be supplied either locally (RPC call with an unset/zero puzzle hash) or observed in a `PoolState` parsed from a pool's `target_puzzle_hash` field embedded in an on-chain travel/launcher solution (`solution_to_pool_state()`), which the wallet accepts without any additional consensus-level check beyond `_verify_pool_state`. A malicious or buggy pool server could set `target_puzzle_hash` to zero when instructing the wallet to leave to `SELF_POOLING`, and the wallet would faithfully build and broadcast a spend that burns future rewards — this doesn't require breaking any cryptographic assumption, only supplying a value that the validation function fails to reject.

### Recommendation
In `PoolWallet._verify_pool_state()` (and/or `_verify_self_pooled`/`_verify_pooling_state`), explicitly reject `state.target_puzzle_hash == bytes32.zeros` (and any other well-known non-spendable puzzle hashes if applicable) in addition to the existing `is None` check, before accepting a `PoolState` as either a local target state or a parsed on-chain state. Apply the same "fail fast" principle used elsewhere in the codebase for puzzle-hash validation.

### Proof of Concept
1. Call the pool wallet RPC to create a new pool wallet (or drive a `PoolState` transition) with `target_puzzle_hash = bytes32.zeros` (all-zero 32 bytes), leaving all other fields valid (e.g., valid `relative_lock_height`, `pool_url` for `FARMING_TO_POOL`, or empty `pool_url` for `SELF_POOLING`).
2. Observe that `PoolWallet._verify_pool_state()` returns `None` (no error) because the only check on `target_puzzle_hash` is `is None`, which is false for `bytes32.zeros`.
3. Proceed with `_verify_initial_target_state`, which does not raise, allowing the pool wallet/launcher spend to be created with this target.
4. Once the singleton later self-pools or leaves to this state and absorbs a farming reward, `pool_state_to_inner_puzzle()` builds the waiting-room/member inner puzzle using this zero puzzle hash as the final `CREATE_COIN` destination; the reward coin created at puzzle hash `0x00...00` cannot be spent by any known puzzle reveal, permanently burning the reward.

```python
    @classmethod
    def _verify_pool_state(cls, state: PoolState) -> str | None:
        if state.target_puzzle_hash is None:
            return "Invalid puzzle_hash"

        if state.version > POOL_PROTOCOL_VERSION:
            return (
                f"Detected pool protocol version {state.version}, which is "
                f"newer than this wallet's version ({POOL_PROTOCOL_VERSION}). Please upgrade "
                f"to use this pooling wallet"
            )

        if state.state == PoolSingletonState.SELF_POOLING.value:
            return cls._verify_self_pooled(state)
        elif state.state in {PoolSingletonState.FARMING_TO_POOL.value, PoolSingletonState.LEAVING_POOL.value}:
            return cls._verify_pooling_state(state)
        else:
            return "Internal Error"
```
