## Finding [1](#0-0) 

The `clone` function explicitly disables Git's native clone-protection mechanism while invoking `git clone --recursive` on an attacker-supplied URL.

### Title
Recursive clone explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard, enabling submodule-hook RCE from an attacker-controlled repository - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` builds the environment for every `git clone` invocation with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` hard-coded, and always passes `--recursive` regardless of the URL's trustworthiness. [2](#0-1) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is the guard Git itself introduced (as part of the fix line for CVE-2024-32002/CVE-2024-32004-class submodule attacks) to detect a malicious repository whose `.gitmodules`/submodule structure attempts to write executable content into the superproject's real `.git/hooks` directory during a `--recursive` clone (e.g. via a submodule path that collides with `.git` on case-insensitive or path-normalizing filesystems, or via symlink tricks during submodule checkout). When that protection is active, Git aborts the clone/checkout instead of writing attacker-controlled files into the hooks directory.

Desktop's `clone()` unconditionally forces this variable to `'false'` for every clone, while simultaneously always requesting `--recursive` submodule cloning: [3](#0-2) 

This is analogous to the auction's broken invariant: a guard (`whenNotPaused` in the original report, `GIT_CLONE_PROTECTION_ACTIVE` here) exists specifically to reject an unsafe operation, but the code path that should be protected by it explicitly opts out of the guard, letting attacker-controlled input (a malicious repo, analogous to the front-run bid) complete an operation that the guard was designed to block.

Making it worse, Desktop's own hook-interception feature (`withHooksEnv`) is enabled by default and automatically executes any hooks found in the repository's `hooks` path on subsequent git operations (`push`, `pull`, `commit`, `merge`, `rebase`), without additional confirmation: [4](#0-3) [5](#0-4) 

So if Git's clone protection is bypassed and a malicious hook file lands under `.git/hooks` during the recursive clone, that hook can subsequently be picked up and run by Desktop's own hook-runner on the very next `commit`/`push`/`pull`, without any indication to the user that anything unusual happened.

### Impact Explanation
An attacker who controls a repository URL that a victim clones with GitHub Desktop (e.g. via a link, "Open in Desktop" deep link, or a forked/renamed repo) can achieve arbitrary code execution on the victim's machine, because the one safeguard Git added specifically to stop this submodule/hooks-path attack class is disabled by Desktop itself. This satisfies the "attacker controls a cloned/fetched repository ... resulting in code execution" criterion directly.

### Likelihood Explanation
Every clone performed by Desktop goes through this same `clone()` function with the guard force-disabled and `--recursive` always on, so there is no user action beyond "clone/open this repository in Desktop" required to hit the vulnerable path. No local access, admin rights, or pre-existing malware is needed — only an attacker-hosted Git repository/URL.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or set it to `'true'`/leave it unset so Git's default protection applies) so that Git's own submodule/hooks-path safety checks remain active during `--recursive` clones. If the override exists to work around some benign edge case, that case should be identified precisely and handled narrowly rather than disabling the protection globally for every clone of arbitrary, untrusted URLs.

### Proof of Concept
1. Attacker publishes a malicious Git repository containing a submodule configuration crafted to exploit the case-insensitive/path-collision class of clone attacks (the same class `GIT_CLONE_PROTECTION_ACTIVE` was introduced to stop), placing an executable hook (e.g. `post-checkout`) into what becomes the victim's real `.git/hooks` directory once the recursive clone completes.
2. Victim clones the repository through GitHub Desktop (via UI, "Open in Desktop" link, or `x-github-client://` deep link).
3. `clone()` invokes `git -c init.defaultBranch=... clone --recursive ... -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'`, so Git's built-in protection does not abort the clone. [6](#0-5) 
4. The malicious hook file is written into the victim's `.git/hooks`. On the next git operation performed by Desktop, either Git itself invokes the hook natively, or Desktop's own `withHooksEnv`/`getRepoHooks` mechanism discovers and executes it via the hooks proxy, running attacker-supplied code with the victim's privileges. [7](#0-6)

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
