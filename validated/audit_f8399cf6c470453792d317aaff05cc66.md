### Title
Tokenfactory `SetDenomMetadata` and native ERC20 pointer creation allow arbitrary `Name`/`Symbol` spoofing of existing tokens for social engineering - (File: `x/tokenfactory/keeper/msg_server.go`)

### Summary
Any account can create a tokenfactory denom under its own namespace (`factory/{creator}/{subdenom}`) and then set that denom's bank `Metadata.Name`/`Metadata.Symbol` to arbitrary strings — including the exact `Name`/`Symbol` of a well-known token such as `SEI`, `USDC`, or `ATOM` — with no uniqueness or collision check against existing metadata. That attacker-controlled metadata is then used verbatim as the constructor `name`/`symbol` for the auto-deployed ERC20 pointer contract, producing an ERC20 token on the EVM side that is indistinguishable by name/symbol from the legitimate asset. This mirrors the GitLab issue class of "ambiguous naming used to social engineer users," but on-chain it enables direct phishing of wallets/DEX front-ends into treating a malicious token as the real one, leading to fund loss when users approve/transfer against the spoofed pointer contract.

### Finding Description
`CreateDenom` only rejects a subdenom that collides with an existing *denom string*, never with existing display metadata: [1](#0-0) 

`SetDenomMetadata` lets the denom's admin (the original creator, a fully permissionless action) replace the bank `Metadata` for their own denom with any `Name`/`Symbol`, and the only checks are structural (`Validate()`, `Base` denom ownership, sender is admin) — there is no check that `Name`/`Symbol` collide with another well-known token's metadata: [2](#0-1) 

The keeper test explicitly demonstrates this is accepted: an arbitrary factory denom's metadata is set with `Name: "SEI", Symbol: "SEI"` and the call succeeds: [3](#0-2) 

This spoofed metadata then flows directly into the EVM pointer precompile's `AddNative` path, which reads `metadata.Name`/`metadata.Symbol` from bank keeper and uses them unmodified as ERC20 constructor arguments when deploying/upserting the pointer contract: [4](#0-3) 

Because `name()`/`symbol()` are exactly what wallets, block explorers, and DEX UIs use to identify a token to end users, an attacker can create `factory/{attacker}/fake`, set its metadata to impersonate a legitimate asset (e.g. `SEI`, `USDC`), call `addNativePointer` to deploy a same-named/symboled ERC20 pointer, and then distribute/list that pointer address so that unsuspecting users approve spend or send funds to it believing it is the genuine token.

### Impact Explanation
This is a direct on-chain analog of "ambiguous naming to social-engineer users": victims interacting with a wallet or DEX that displays only `name()`/`symbol()` cannot distinguish the spoofed ERC20 pointer from the legitimate token. Approvals or transfers made against the attacker's pointer contract/tokenfactory denom, believing it to be the real asset, result in unauthorized transfer/loss of the victim's funds — satisfying the "unauthorized transfer via precompile or pointer" impact criterion. Because pointer deployment is a normal permissionless EVM transaction path, this is reachable by any unprivileged contract deployer/tokenfactory user.

### Likelihood Explanation
High likelihood: `CreateDenom` and `SetDenomMetadata` are fully permissionless (any account can create a denom and become its own admin), require no whitelist and no collision check on `Name`/`Symbol`, and `addNativePointer` in the pointer precompile is a standard public EVM call available to any caller.

### Recommendation
Add a metadata-collision check in `SetDenomMetadata`/`CreateDenom` (and/or in the pointer precompile's `AddNative`) that rejects `Name`/`Symbol` values matching those already registered for another denom's `DenomMetaData`, or otherwise namespaces/prefixes tokenfactory-derived `Name`/`Symbol` fields (similar to how the denom itself is namespaced with `factory/{creator}/...`) so that pointer-contract display fields cannot be trivially spoofed to match an existing legitimate asset.

### Proof of Concept
1. Attacker submits `MsgCreateDenom{subdenom: "fake"}` → creates `factory/{attacker}/fake`, attacker becomes admin (`x/tokenfactory/keeper/createdenom.go`).
2. Attacker submits `MsgSetDenomMetadata` with `Metadata{Base: "factory/{attacker}/fake", Name: "SEI", Symbol: "SEI", ...}` → succeeds because no uniqueness check exists against other tokens' metadata (`x/tokenfactory/keeper/msg_server.go` `SetDenomMetadata`).
3. Attacker calls the pointer precompile's `addNativePointer("factory/{attacker}/fake")` → an ERC20 pointer contract is deployed whose `name()`/`symbol()` both return `"SEI"` (`precompiles/pointer/pointer.go` `AddNative`).
4. Attacker publishes/lists this pointer contract address as "SEI". Victims interacting through wallets/DEX UIs that trust `name()`/`symbol()` approve or send funds against this contract, believing it is the genuine SEI token, resulting in fund loss.

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
