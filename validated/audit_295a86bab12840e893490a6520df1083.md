Based on my research, I found a strong analog in Agave's Alpenglow vote-account/VAT (Validator Admission Ticket) mechanism: the same "minimum vote-account balance" invariant is computed inconsistently across two code paths — one includes `pending_delegator_rewards`, the other does not — mirroring the Lybra `collateralRatio` inconsistency (one formula accounts for accrued fees/shares, the other omits them).

### Title
Inconsistent minimum-vote-account-balance calculation lets VAT burn drain lamports reserved for `pending_delegator_rewards` - (File: `runtime/src/bank.rs`)

### Summary
`programs/vote/src/vote_state/mod.rs::withdraw()` enforces that a vote account's lamport balance can never drop below `rent_exempt_minimum + pending_delegator_rewards` [1](#0-0) . However, the epoch-boundary VAT burn in `runtime/src/bank.rs::maybe_burn_vat_from_staked_accounts()` subtracts `vat_to_burn_per_epoch` directly from every top-2000 vote account's lamports using only the pre-filtering done by `clone_and_filter_for_vat`/`minimum_vote_account_balance_for_vat`, neither of which factors in `pending_delegator_rewards` [2](#0-1) [3](#0-2) .

### Finding Description
`vote_state::withdraw()` treats `pending_delegator_rewards` as lamports that must remain in the account, reserved for distribution to delegators via SIMD-0123 block rewards:
```
// SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
// is lamports - pending_delegator_rewards - rent_exempt_minimum.
let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
let min_balance = min_rent_exempt_balance.checked_add(pending_delegator_rewards)...
``` [1](#0-0) 

This is the "correct" formula — the invariant is `balance >= rent_exempt_minimum + pending_delegator_rewards`.

But `Bank::minimum_vote_account_balance_for_vat()`, which gates which vote accounts are considered eligible/filtered for VAT admission and burn, only computes:
```
let vote_account_rent_exempt_minimum = ...minimum_balance(VoteStateV4::size_of());
if alpenglow { vote_account_rent_exempt_minimum + self.vat_to_burn_per_epoch() } else { ... }
``` [3](#0-2) 

This formula omits `pending_delegator_rewards` entirely. `maybe_burn_vat_from_staked_accounts()` then unconditionally subtracts the VAT amount from every filtered account's lamports:
```
account.set_lamports(
    account.lamports().checked_sub(vat_to_burn_per_epoch)
        .expect("Vote accounts should have already been filtered to contain enough balance for the VAT"),
);
``` [4](#0-3) 

The `.expect()` only guards against underflow relative to `rent_exempt_minimum + vat_to_burn_per_epoch` (per the filtering comment), not against dropping below `rent_exempt_minimum + pending_delegator_rewards`, so it does not panic in the scenario described — it silently succeeds while violating the true reserve invariant. Just like the Lybra report where `rigidRedemption()` used a weaker `collateralRatio` formula (`borrowed[provider]` only) than `liquidation()` (`getBorrowedOf()`, including fees/shares), Agave here uses a weaker balance-sufficiency formula (`rent_exempt + VAT`) in the burn path than the one the withdraw path enforces (`rent_exempt + pending_delegator_rewards`).

### Impact Explanation
If a vote account accumulates `pending_delegator_rewards` (credited each slot per SIMD-0123, awaiting distribution to delegators as block rewards) close to its rent-exempt minimum, the VAT burn can push the account's lamport balance below `rent_exempt_minimum + pending_delegator_rewards` without tripping any check. Later, when `calculate_block_reward()`/reward distribution attempts to pay out `pending_delegator_rewards` to stake accounts based on the value read from vote state [5](#0-4) , the vote account may lack sufficient lamports to back the promised distribution, or the account could fall below its rent-exempt threshold — a false-acceptance of an invalid state that should have been rejected consistently with the `withdraw()` invariant. This falls under "false execution/acceptance" of protocol invariants in the runtime/accounts space.

### Likelihood Explanation
This does not require a malicious actor: `maybe_burn_vat_from_staked_accounts` runs automatically every epoch boundary for all top-2000 vote accounts under Alpenglow [6](#0-5) , and `pending_delegator_rewards` naturally accrues over time via ordinary validator voting. Any validator whose vote account balance is only marginally above `rent_exempt + VAT` (which is exactly the threshold enforced by the filter) is at risk once `pending_delegator_rewards` grows, since the filter never checks that second reserve.

### Recommendation
Make `minimum_vote_account_balance_for_vat()` (and the VAT filtering it feeds) consistent with `vote_state::withdraw()`'s invariant by including the vote account's current `pending_delegator_rewards` in the required minimum balance before allowing a VAT burn, or by clamping/skipping the burn (and re-filtering) for any account where `lamports - vat_to_burn_per_epoch < rent_exempt_minimum + pending_delegator_rewards`.

### Proof of Concept
1. Under Alpenglow, get a validator's vote account balance to `rent_exempt_minimum + vat_to_burn_per_epoch + ε` for a small `ε`.
2. Allow `pending_delegator_rewards` to accumulate (via normal voting/credits) to a value `> ε`.
3. At the next epoch boundary, `maybe_burn_vat_from_staked_accounts` passes the `.expect()` (balance still ≥ `rent_exempt + VAT`) and burns `vat_to_burn_per_epoch`, leaving `balance = rent_exempt_minimum + ε - vat_to_burn_per_epoch + vat_to_burn_per_epoch = rent_exempt_minimum + ε < rent_exempt_minimum + pending_delegator_rewards` (since `pending_delegator_rewards > ε`).
4. The account is now in a state that `withdraw()` itself would reject as insufficient (`remaining_balance < min_balance`), yet it was reached via the burn path with no equivalent check [4](#0-3) [1](#0-0) .

Note: I was unable to fully trace, within the available index, the exact downstream mechanism that debits `pending_delegator_rewards` lamports out of the vote account during block-reward distribution (I found where the reward amount is computed in `calculate_block_reward` but not the precise `checked_sub_lamports` call against the vote account itself). This limits full certainty about the concrete on-chain failure mode (panic vs. silent under-payment); confirming that would require a Devin session with full repository/test access to trace `distribute_reward_commissions`/`build_updated_stake_reward` and related vote-program CPI paths end-to-end.

            .rent
