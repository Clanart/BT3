### Title
Unvalidated `Participant` indexes in PedPoP blame evaluation panic on out-of-range accuser/sender — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with a `Participant` value that is never bounds-checked against `1 ..= n`. `Participant` is any non-zero `u16` (`crypto/dkg/src/lib.rs:29-35`), so an accuser/sender index of e.g. `n + 1` (or any unregistered index) causes a `HashMap` index panic — a reachable crash (DoS) analog of the CVE-2025-50091 "repeatable crash of the server" class. The same pattern exists for `self.commitments[&l]` in `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:490`) when reached through paths where the commitments map keys differ from the shares map keys, and for `original_verification_share`/`verification_share` on `ThresholdView` (`crypto/dkg/src/lib.rs:672-682`), which document "will panic if the participant index is invalid".

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Decryption::decrypt_with_proof` verifies the accuser's `EncryptionKeyProof` DLEq against `self.enc_keys[&decryptor]`:

- `enc_keys` is populated by `Decryption::register`, which is only ever called for `1 ..= n` (e.g. `AdditionalBlameMachine::new` at `crypto/dkg/pedpop/src/lib.rs:656-660` registers exactly `Participant::new(i)` for `i in 1 ..= n`).
- `AdditionalBlameMachine::blame(sender, recipient, msg, proof)` forwards both attacker-influenced `Participant` arguments into `blame_internal` → `decrypt_with_proof` with no `participant <= n` validation anywhere in the path (`crypto/dkg/pedpop/src/lib.rs:674-682`).
- `decrypt_with_proof` performs `self.enc_keys[&decryptor]` (`encryption.rs:388`); `HashMap`'s `Index` impl panics on a missing key.

A `Participant` with value `> n` is constructible from untrusted input (`Participant::new` only rejects `0`), and the accuser index in a blame claim is attacker-chosen message data.

### Impact Explanation
Evaluating a blame statement where the accusing `recipient` (or claimed `decryptor`) carries any index not in `1 ..= n` — trivially produced by an unprivileged party who controls the accused/accuser fields of a blame submission — panics the evaluation routine. Any caller (validator, coordinator, arbitration service) that runs blame verification on attacker-supplied blame claims crashes, matching the "frequently repeatable crash / complete DOS" impact of the reference CVE.

### Likelihood Explanation
Reachability requires only that the host feeds attacker-controlled `Participant` values into `BlameMachine::blame`/`AdditionalBlameMachine::blame` — the entire purpose of the blame API is to adjudicate claims from parties already suspected of misbehavior, so hostile inputs are the expected input. No secrets, valid shares, or proof forgeries are needed; a single out-of-range index suffices. Likelihood is bounded only by whether the integrator pre-validates indexes itself, which the API neither requires nor documents.

### Recommendation
Validate `sender` and `recipient`/`decryptor` against `self.enc_keys`/`commitments` key sets (or `params.n()`) before indexing in `blame_internal`/`decrypt_with_proof`, returning a `DecryptionError`/blame result for an unknown party instead of panicking. Prefer `enc_keys.get(&decryptor)` with an error on `None`.

### Proof of Concept
```rust
// Construct a valid AdditionalBlameMachine for n = 3 with honest commitment
// messages, then submit a blame claim whose accuser index is out of range:
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();
// Participant::new(200) succeeds: only 0 is rejected. 200 > n = 3.
let malicious_accuser = Participant::new(200).unwrap();
// Panics at crypto/dkg/pedpop/src/encryption.rs:388 on self.enc_keys[&decryptor]
machine.blame(sender, malicious_accuser, msg, Some(proof));
```
`msg`/`proof` can be any well-formed `EncryptedMessage`/`EncryptionKeyProof` — `decrypt_with_proof` reaches `self.enc_keys[&decryptor]` after the (passable or skippable) PoP/DLEq checks, so no valid cryptography is required to trigger the panic.

Caveat: I could not fully trace `blame_internal` (it was not in the retrieved snippets), so the exact line at which the `sender` index is dereferenced is inferred from the `commitments[&l]`/`enc_keys[&decryptor]` indexing patterns shown; the `decrypt_with_proof` panic on `decryptor` is confirmed at `encryption.rs:388`.
