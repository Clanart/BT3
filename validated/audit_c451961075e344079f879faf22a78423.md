### Title
Unguarded division by `total_stake_lamports` in Alpenglow block-reward calculation can panic block processing - (File: `runtime/src/block_component_processor/vote_reward.rs`)

### Summary
The Panoptic report is a class of bug where a margin/collateral formula divides by a value (`distanceFromStrike * expValue`) that can become zero for a specific, reachable input combination (`width==1`, `tickSpacing==1`, `atTick==strike`), with no explicit guard, causing a hard revert that blocks a consensus-critical action (`dispatchFrom`/liquidation). The closest Agave analog is `calculate_reward` in `runtime/src/block_component_processor/vote_reward.rs`, which computes a validator's Alpenglow block reward using a raw `u128` division by `denominator = slots_per_epoch * total_stake_lamports` with no zero-check and an `unwrap()` on the result [1](#0-0) . Unlike sibling reward-math in the same codebase (`runtime/src/inflation_rewards/points.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`), which explicitly filter/guard against a zero stake denominator before dividing [2](#0-1) [3](#0-2) , `calculate_reward` has no such guard.

### Finding Description
`calculate_reward` computes:
```
numerator = max_possible_validator_reward * validator_stake_lamports
denominator = slots_per_epoch * total_stake_lamports
reward_lamports = (numerator / denominator).try_into().unwrap()
``` [4](#0-3) 

If `total_stake_lamports` is `0` for the relevant validator/epoch bucket at the call site, the `numerator / denominator` division panics (integer division by zero in Rust), which — if reached during bank/block reward processing rather than in a client-only helper — would crash the validator process during a consensus-path routine. This mirrors the Panoptic bug's structure exactly: a raw division whose denominator is built from a runtime-derived value (`total_active_stake` in Panoptic vs. `total_stake_lamports` here) that is not defensively checked at the point of division, even though sibling code paths in the same module/repo area (`calculate_block_reward` in `calculation.rs`, `calculate_alpenglow_points` in `points.rs`) explicitly test for and short-circuit a zero-stake denominator before dividing.

### Impact Explanation
Unverified/uncertain: I was not able to fully trace, within the available tool budget, all call sites of `calculate_reward` to confirm whether `total_stake_lamports` can actually reach `0` given upstream invariants (e.g., whether it always represents total active epoch stake, which is normally guaranteed non-zero by genesis/staking invariants, or whether it can represent a narrower, potentially-zero subset such as a specific validator's delegated stake bucket during a specific reward-distribution edge case). If reachable with a zero value, this would panic the validator during reward/block processing — a consensus-path routine — which could cause a validator crash or, if triggered identically for all validators processing the same block, a broader halt.

### Likelihood Explanation
Low-to-uncertain confidence. The surrounding code in the same file (`RewardStateError` variants like `NoEpochValidatorStake`, `MissingRewardSlotValidator`) suggests there are validation layers upstream that may already reject/handle missing or zero-stake states before `calculate_reward` is invoked, which would prevent this path from being reachable in practice [5](#0-4) . I could not confirm within the remaining budget whether these guards fully preclude a zero `total_stake_lamports` at the `calculate_reward` call site.

### Recommendation
Add an explicit zero-check (mirroring the pattern used in `calculate_alpenglow_points` and `calculate_block_reward`) before performing the division in `calculate_reward`, returning `(0, 0)` or propagating an error if `total_stake_lamports == 0`, rather than relying on `unwrap()` after a raw `/` operation.

### Proof of Concept
Not constructed — a concrete PoC would require confirming (via the full call graph of `calculate_reward`, which was not completed within the tool budget) a code path where `total_stake_lamports` is `0` at the call site. This is flagged as the strongest structural analog found, but **should be treated as a lead requiring further verification** (specifically tracing all callers of `calculate_reward` and the origin of its `total_stake_lamports` argument) rather than a confirmed exploit.

    // The code below is equivalent but changes the order of operations to maintain precision

    // epoch to exceed u64::MAX.

    let leader_reward_lamports = reward_lamports - validator_reward_lamports;
