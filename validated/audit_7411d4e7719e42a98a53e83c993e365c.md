### Title
Balance-based sweep in `compound()` lets stakeless callers steal residual reward tokens - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` is a public, unrestricted function that forwards the caller's `_lps`/`_rewards` selection to `IMasterMagpie.multiclaimOnBehalf`, then unconditionally runs two sweep loops driven by `IERC20(token).balanceOf(address(this))` rather than the amount actually claimed in that transaction. Since the caller can pass staking tokens they hold no position in (which contribute zero to the claim) and the sweep is a balance snapshot, any leftover reward-token balance sitting on the contract from an unrelated prior interaction is paid out entirely to the calling attacker.

### Finding Description
`compound()` performs: [1](#0-0) 
`multiclaimOnBehalf` is called with the attacker-supplied `_lps`/`_rewards`, and internally `_multiClaim` computes `claimableMgp`/base-rewarder amounts from the `_user`'s (`msg.sender`, i.e., the attacker's) own `UserInfo.amount`/`available` for each staking token: [2](#0-1) . If the attacker passes staking tokens where they have no stake (or an empty `_lps` array), this leg legitimately produces zero reward, but the call does not revert — it simply does nothing.

Execution then falls through to the two sweep loops, which are gated only on `!compoundableRewards[token]` (first loop, non-configured tokens) or unconditionally (second loop, for every configured `rewards[i].tokenAddress`) and use `IERC20(_tokenAddress).balanceOf(address(this))` as the amount to distribute: [3](#0-2) . Neither loop measures a before/after delta scoped to the current `multiclaimOnBehalf` call; they simply forward whatever the contract currently holds. Consequently, if a residual balance of a configured reward token exists on the contract (e.g., left over from a previous compound where a convertor/helper/locker call did not consume 100% due to rounding, a prior claim that reached the contract but wasn't fully forwarded, or a direct token transfer), the very next caller — with zero stake and zero genuine claim — receives that entire residual balance via `safeTransfer`/`convertFor`/`lockFor`/`depositFor` to their own address.

There is no modifier restricting who may call `compound()` (no `onlyOwner`, `onlyCompounder`, etc.), so this is reachable by any unprivileged EOA or contract.

### Impact Explanation
This breaks the invariant that a distribution must be gated on value the caller generated in the same call. It results in direct theft of another user's/protocol's residual reward tokens — funds that rightfully belong to prior compounders/stakers — matching "Critical - Direct theft of user funds."

### Likelihood Explanation
The only precondition is that some non-zero token balance of a configured `rewards[i].tokenAddress` exists on the `ManualCompound` contract at the time of the attacker's call (a plausible and recurring state given rounding in `convertFor`/`lockFor`/`depositFor`, or any token dust/donation). No capital or special privileges are required — the attacker can call `compound()` with empty or irrelevant `_lps`/`_rewards` arrays at any time, and can repeat the attack every time dust reappears.

### Recommendation
Scope the sweep to the value produced by the current call instead of the contract's absolute balance: snapshot `IERC20(token).balanceOf(address(this))` before calling `multiclaimOnBehalf`, and only distribute the delta (`balanceAfter - balanceBefore`) to `msg.sender`; alternatively, have `multiclaimOnBehalf`/`_claimBaseRewarder` return the actually-claimed amounts per token and use those directly instead of `balanceOf`. Any genuinely leftover dust should be swept by a privileged role (owner/rewardManager) rather than being claimable by arbitrary callers.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie` and `ManualCompound`, register `ManualCompound` as an approved compounder in `MasterMagpie`, and add a reward token (e.g., `WOM`) via `addReward` with no convertor/locker/helper so it falls to `safeTransfer`.
2. Simulate residual balance: directly transfer (or via a legitimate compound call that leaves dust) some `WOM` tokens to the `ManualCompound` contract address, so `IERC20(WOM).balanceOf(ManualCompound) > 0` while `compoundableRewards[WOM] == true`.
3. From an attacker address with zero stake in any pool (`user.amount == 0` for all `_lps`), call `compound(emptyOrArbitraryLps, matchingEmptyRewards, 0, 0, false)`.
4. Assert: `multiclaimOnBehalf` contributed 0 (no `Harvest` events for attacker), yet `IERC20(WOM).balanceOf(attacker)` increased by the full residual amount and `IERC20(WOM).balanceOf(ManualCompound)` dropped to 0 — proving theft of funds not generated by the attacker's own call.
