## Finding



### Title
Unbounded/unvalidated `order.deadline` in `placeOrder` can immediately strand escrowed funds - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` escrows a user's `inputs` and stamps `order.nonce`/`order.user`/`order.source`, but never validates `order.deadline` against the current block number or against any minimum/maximum window, unlike the reported `createAuction` timestamp issue.

### Finding Description
`placeOrder` performs input-array checks (non-empty inputs, no duplicate output tokens, non-zero amounts) but has no check on `order.deadline` before escrowing tokens. [1](#0-0) 
The only place `deadline` is later enforced is in `fillOrder`, which reverts if `order.deadline < _blockNumber()`. [2](#0-1) 
Because `placeOrder` never rejects a `deadline` that is already at/behind the current block (or arbitrarily far in the future), a user (or a malicious frontend/wallet bug) can escrow inputs into an order that is *unfillable from the moment it is placed* — exactly the `endTimestamp == startTimestamp` / no-minimum-duration class described in the external report. For cross-chain orders, recovering these funds is not immediate: it requires either the destination-chain owner-only-then-anyone `cancelOrder` flow, or the source-chain path where `CancelOptions.height` must be a destination block **after** `order.deadline` before a relayer can supply the non-membership proof and trigger the refund. [3](#0-2) 
No guard mirrors the `createAuction` recommendation (min/max duration, deadline must be some bounded distance from placement time).

### Impact Explanation
Funds are not stolen or redirected to a wrong beneficiary — refunds ultimately return to the original user — but escrow can be placed into an order that is dead on arrival, delaying recovery of funds behind the (relayer-fee-costed, proof-gated) cross-chain cancellation path rather than an immediate refund. This matches the "stuck value" concern in the source report, though the ultimate beneficiary is preserved, which limits severity relative to the reported issue.

### Likelihood Explanation
Low — this requires user/integrator error (e.g., a malformed or already-expired `deadline` computed off-chain) rather than an attacker exploiting another party's funds, consistent with the "Low" likelihood rating in the original report.

### Recommendation
Add explicit bounds checks in `placeOrder`: require `order.deadline > currentBlockOrTimestamp + MIN_DURATION` and `order.deadline <= currentBlockOrTimestamp + MAX_DURATION`, mirroring the min/max duration recommendation from the source report.

### Proof of Concept
1. Call `placeOrder` with `order.deadline` set to the current block number (or a past value); the call succeeds and inputs are escrowed (no revert path exists for this).
2. Any subsequent `fillOrder` call reverts immediately with `Expired()` since `order.deadline < _blockNumber()`.
3. The user's funds now depend on the cancellation path (`cancelOrder`, cross-chain proof/relayer flow) to be recovered rather than being refundable as part of normal escrow entry, illustrating the missing-validation analog to the `createAuction` timestamp issue. [2](#0-1)

```text
There are two modes for cross-chain cancellation:

**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.

![Cancel from Source Chain](/intent-gateway-cancel-source.svg)

**Cancel from destination chain**: Before the deadline, only the order owner can call `cancelOrder()` on the destination chain. After the deadline, anyone can cancel. The function marks the order as cancelled locally (`_filled[commitment] = user`) to prevent future fills, then dispatches a cross-chain `RefundEscrow` message back to the source chain. When the source chain receives this message via `onAccept()`, it calls `withdraw()` to refund the escrowed tokens to the user and emits `EscrowRefunded(commitment)`.

![Cancel from Destination Chain](/intent-gateway-cancel-dest.svg)
```
