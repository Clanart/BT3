### Title
`InvalidDkgShare` blame lookup reads the share in the wrong direction, fetching the accuser's share to the accused instead of the accused's share to the accuser - (File: coordinator/src/tributary/handle.rs)

### Summary
Analogous to CVE-2017-5936 (nova-lxd applying security-group rules to the wrong veth name), the Tributary coordinator applies its DKG blame/verification control to the wrong keyed object: when handling `Transaction::InvalidDkgShare`, it looks up `DkgShare` under `(accuser, faulty)` — the share the accuser *sent to* the accused — rather than `(faulty, accuser)` — the share the accused sent to the accuser that is actually being blamed.

### Finding Description
When a `DkgShares` transaction is processed, each share is stored keyed by `(from, to)`, where `from` is a Participant index owned by the *signer* of the `DkgShares` transaction (the dealer), and `to` is the recipient participant: [1](#0-0) 

The blame path then retrieves the disputed share as: [2](#0-1) 

`DkgShare::get(self.txn, genesis, accuser.into(), faulty.into())` (line 486) uses the accuser's index as `from` and the accused (`faulty`) index as `to`. The share being blamed is the one *faulty sent to accuser*, stored under `(faulty, accuser)`. Because every participant deals shares to every other participant, the key `(accuser, faulty)` almost always exists too, so the lookup silently succeeds while returning the wrong ciphertext/plaintext for blame verification.

### Impact Explanation
The coordinator forwards the fetched share to the processors to verify the blame claim. Since it fetches a share the *accuser* dealt (which the accuser controls and knows is valid/invalid for a different recipient), the security control is applied to the wrong object:

- A genuinely faulty dealer can evade blame: the verified share is not the one they sent, so a malformed share cannot be proven faulty against them, defeating the DKG blame mechanism that guards key generation.
- Conversely, an accuser could craft their own outgoing share to make the fetched `(accuser, faulty)` share appear invalid under blame verification, causing an honest dealer (`faulty`) to be slashed/removed based on data the dealer never sent.

Either way the integrity of the DKG participant-removal/slashing path — a consensus-level security restriction — is undermined by misidentifying which stored object the rule applies to.

### Likelihood Explanation
Reachable by any participating validator: publishing a `DkgShares` transaction and later an `InvalidDkgShare` accusation are normal protocol transactions signed by participants. Both `accuser` and `faulty` are passed range checks (`range.contains(&accuser)` ensures the accuser claims an index in their own signer range; `range.contains(&faulty)` only rejects self-accusation), so the misdirected lookup is exercised on the normal path whenever anyone files a blame claim. No collusion or invalid curve input is required; the only precondition is that the accuser also dealt a share to the accused, which always holds in a completed DKG round.

### Recommendation
Swap the key components in the blame lookup so the share the accused sent to the accuser is fetched:

```rust
let Some(share) = DkgShare::get(self.txn, genesis, faulty.into(), accuser.into()) else { ... };
```

in `coordinator/src/tributary/handle.rs` (the `Transaction::InvalidDkgShare` arm, ~line 486). Additionally, add a regression test in `coordinator/src/tests/tributary/dkg.rs` asserting that a blame claim verifies against the share the accused actually dealt to the accuser.

### Proof of Concept
1. In a Tributary DKG round, participant `F` (dealer indexes owned by signer F) publishes `DkgShares`; the coordinator stores `DkgShare[(F, A)] = share_F_to_A` and `DkgShare[(A, F)] = share_A_to_F`.
2. Participant `A` publishes `InvalidDkgShare { accuser: A, faulty: F, ... }`.
3. `handle_application_tx` executes `DkgShare::get(genesis, A, F)` and retrieves `share_A_to_F` — the share A dealt — instead of `share_F_to_A` (handle.rs:486, versus the write at handle.rs:361 which keys by `(sender, recipient)`).
4. The blame verification is run against the wrong share: if F dealt A a malformed share, verification of A's own well-formed share clears F; if A crafts `share_A_to_F` to fail the blame equation, honest F is slashed.

*Caveat: the exact field order of the `DkgShare` DB key in `coordinator/src/tributary/db.rs` was not directly inspected in this pass; the conclusion relies on the write site `DkgShare::set(genesis, from=sender_index, to=recipient_index)` at handle.rs:347-361, which unambiguously establishes the key direction as (dealer, recipient).*
