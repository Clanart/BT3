## Analysis

The report's core invariant — "ERC20 transfers must be verified for actual success, not just call-non-revert" — has a direct, exploitable analog in the Tron variant of the Intent Gateway.

### Title
Escrow release/refund silently accepts failed ERC20 transfers via unchecked low-level `.call`, allowing an order to be marked filled/refunded while funds never leave the contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw` (and the `SweepDust` branch of `onAccept`) on Tron release escrowed tokens using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the outer `success` boolean (i.e., that the call did not revert). They never decode/verify the ERC20 return value. This is precisely the pattern the external report flags: non-reverting-on-failure ("bad") ERC20 tokens can return `false` from `transfer` while the call itself succeeds, so `success` is `true` even though no tokens moved.

In `withdraw`, escrow accounting is unconditionally decremented and the order is marked filled/refunded regardless of whether the token transfer actually succeeded: [2](#0-1) 

The same unchecked pattern appears for fee redemption and dust sweeping in the same file: [3](#0-2) [4](#0-3) 

Note that the same file already imports and uses `SafeERC20` correctly for the deposit path (`safeTransferFrom`), so the escrow-out path is an inconsistent, unsafe deviation: [5](#0-4) 

Contrast this with the canonical (non-Tron) EVM implementation, which correctly uses `safeTransfer` for the same operation: [6](#0-5) 

### Impact Explanation
`order.inputs[i].token` is an arbitrary ERC20 address chosen by the unprivileged order creator (`order.user`) at `placeOrder` time — the protocol imposes no allow-list. An attacker can create an order whose input token is malicious: it returns `true` from `transferFrom` (satisfying the `safeTransferFrom` deposit check) but returns `false` (without reverting) specifically from `transfer` calls originating from `withdraw`/`onAccept`. A legitimate solver who fills the order on the destination chain (delivering real value there) subsequently triggers `RedeemEscrow` on the source chain via Hyperbridge. `withdraw` then calls the malicious token's `transfer`, gets `success = true` but an internal `false` return that is never checked, decrements `_orders[...]` to zero, sets `_filled[commitment] = beneficiary`, and emits `EscrowReleased` — all while the tokens never leave the `IntentGatewayV2` contract. The solver has provided real cross-chain value and receives nothing, the order is irreversibly marked settled (`_filled` already set blocks any retry), and the escrowed tokens are permanently stuck in the contract. This is a direct loss-of-funds / false-settlement-acceptance outcome triggered purely by an unprivileged user's token choice — no relayer, prover, or admin compromise required.

### Likelihood Explanation
Likelihood is moderate-to-high: it only requires an attacker to deploy one custom ERC20 contract and place a normal-looking cross-chain intent order using it as the input token. No privileged role, malicious relayer, or protocol misconfiguration is needed — the vulnerability is purely in how `withdraw`/`onAccept` validate `transfer` outcomes.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, the fee-redemption block, and the `SweepDust` branch of `onAccept`) with `SafeERC20.safeTransfer`, consistent with the deposit path in the same file and with `IntentsBase.sol` in the main EVM contracts. `safeTransfer` correctly reverts when a token call succeeds but returns `false`, or when a non-standard token returns no data at all, preventing escrow state from being finalized without an actual transfer.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transferFrom` behaves normally (returns `true`) but whose `transfer` function returns `false` (no revert) when called by the `IntentGatewayV2` contract address as `msg.sender`.
2. Attacker calls `placeOrder` with `order.inputs[0].token = EvilToken`, depositing escrow via `safeTransferFrom` (succeeds normally).
3. A solver fills the order on the destination chain, delivering the promised output asset to the attacker.
4. The solver (or relayer on solver's behalf) triggers the `RedeemEscrow` flow; Hyperbridge delivers the `PostRequest` to `IntentGatewayV2.onAccept` on the source chain, which calls `withdraw(body, false)`.
5. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting (`success == true`), but `EvilToken.transfer` internally returns `false` and performs no balance change.
6. `_orders[commitment][token] -= amount` proceeds, `_filled[commitment] = beneficiary` is set, and `EscrowReleased` is emitted — the order is permanently marked settled, but the solver's beneficiary balance never increases, and the escrowed `EvilToken` remains stuck in `IntentGatewayV2`, unrecoverable through the normal flow.
