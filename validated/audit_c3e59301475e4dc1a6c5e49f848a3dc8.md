### Title
Partial-commit line selection is applied against a re-fetched diff without re-validating line content, allowing silent inclusion of unreviewed content in a commit - ([File: app/src/lib/git/apply.ts], [File: app/src/lib/patch-formatter.ts], [File: app/src/lib/stores/app-store.ts])

### Summary
When a user makes a partial (line-level) commit, GitHub Desktop records the selection as a set of numeric line indices (`DiffSelection`) computed against the diff that was rendered in the UI at selection time. At commit/stage time, `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a **fresh** diff via `getWorkingDirectoryDiff(repository, file)` and then reuses the old numeric `file.selection` indices against that new diff in `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`), via `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and `file.selection.isSelected(absoluteIndex)`. There is no verification that the line at a given index still contains the same content the user actually saw and selected. `app/src/lib/stores/app-store.ts:3480-3484` explicitly documents this weakness for the "selected diff refresh" path but does not close it for the staging/commit path.

### Finding Description
The broken invariant is: *"a numeric line-selection index computed from diff snapshot D1 is safe to reapply against diff snapshot D2."* Between the moment the user reviews a diff and selects specific lines in the Changes view, and the moment `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681`) actually stages and commits the file, an unbounded amount of time can pass and the working tree content can change (background processes, another git client, editors with auto-save/format-on-save, `.gitattributes`-driven filters, file watchers, etc., some of which are configurable from within an untrusted cloned repository, e.g., editor workspace settings or build tooling that a cloned repo can trigger). `applyPatchToIndex` does not use the diff object the user actually interacted with; it independently re-runs `getWorkingDirectoryDiff` (`app/src/lib/git/apply.ts:60`) and blindly indexes into whatever hunks that call returns. If the new diff's hunk boundaries/line ordering shift relative to the old one (e.g., an attacker-influenced pre-existing background process appends/removes lines earlier in the file, or an automatic formatter reflows the file), the same absolute index that used to correspond to "line X the user intentionally selected" can now correspond to a different, unreviewed line. `formatPatch` will happily build a patch selecting that different content because it only checks `file.selection.isSelected(absoluteIndex)` — a pure integer comparison with no content/hash validation (`app/src/lib/patch-formatter.ts:157`).

The only partial mitigation in the codebase, `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts:3478-3493`, re-derives `selectableLines` from a freshly loaded diff and prunes previously-selected indices that are no longer "includeable," but it explicitly does **not** validate that a still-includeable index still refers to the same line content — the comment says as much. This mitigation also only runs when the diff panel happens to reload while the file is the active selection; it is not invoked as a guard immediately before `applyPatchToIndex` builds and applies the patch during commit.

### Impact Explanation
This matches the "silent corruption of what the user commits or pushes" impact category. A user could intend to stage lines A–B of a file but end up committing different lines (e.g., lines that were never reviewed, or lines belonging to a different logical hunk) without any error or warning, because `git apply --cached` will succeed as long as the generated patch is internally consistent — it has no way to know the hunk no longer matches user intent. In a worst case, this could be leveraged to smuggle attacker-influenced content (e.g., from a build step or tool that a cloned/malicious repository triggers to touch the working tree) into a commit that the developer believes only contains their reviewed lines, which is then pushed upstream.

### Likelihood Explanation
This requires the working tree content to actually change between selection and staging, and for that change to alter line offsets in a way that maps the old indices onto different content — a timing-dependent condition, not deterministically triggerable by a remote/passive attacker alone. It does not require local/physical access or admin rights, and the existing partial mitigation in `updateChangesWorkingDirectoryDiff` shows the Desktop team is aware such staleness happens in practice, but that mitigation does not fully close the gap for the commit path.

### Recommendation
Before calling `applyPatchToIndex`/`formatPatch` for a partial selection, re-fetch the diff immediately prior to staging and verify that the previously selected line indices still correspond to lines with matching content (not just still "includeable") in the newly fetched diff; if they don't match, abort the stage/commit for that file and surface an error to the user rather than silently applying a mismatched patch.

### Proof of Concept
1. Open a repository in Desktop, modify a tracked file, and open the Changes diff for it.
2. Select only a subset of lines for partial commit (e.g., lines 10–12) and leave the commit dialog open without immediately committing.
3. While the commit is pending, have an external process running in the working tree modify the file above the selected region (e.g., a background formatter/build tool, or `.gitattributes` filter execution triggered by another git invocation) so that the line offsets shift but the file still parses as a valid diff.
4. Click "Commit" — `stageFiles`/`applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a new diff and `formatPatch` (`app/src/lib/patch-formatter.ts:157`) reapplies the old indices 10–12 against it, staging and committing whatever content now occupies those offsets instead of the originally reviewed lines, with no warning to the user.
