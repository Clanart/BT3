## Title
`open-external` IPC handler passes any renderer-supplied string to `shell.openExternal` without validating scheme - (File: `app/src/main-process/main.ts`)

### Summary
The report's broken invariant is that a security-relevant sink (which token can be redeemed) accepts an unchecked, attacker-influenceable value. The closest Desktop analog is the `open-external` IPC handler, which hands whatever string it receives straight to Electron's `shell.openExternal()` with no allow-list on the URI scheme, and the renderer-side `LinkButton` component that calls it, also without a protocol check.

### Finding Description
`ipcMain.handle('open-external', ...)` only inspects the string to decide whether to *log* it as "opening in browser" when it starts with `http://`/`https://`; it performs no validation before invoking `shell.openExternal(path)`: [1](#0-0) 

`LinkButton`, the primary UI primitive used to open "external" links throughout the app (About dialog, PR comments/reviews, secret-scanning bypass links, submodule info, tutorial panel, etc.), forwards its `uri` prop to `shell.openExternal(uri)` on click with no scheme check at all: [2](#0-1) 

By contrast, the sandboxed markdown renderer (used for READMEs/commit messages/PR bodies) *does* enforce `/^https?:/.test(a.protocol)` before invoking its link-click callback: [3](#0-2) 

This shows the project is aware that link-click handlers need scheme validation in at least one path, but the same discipline was not applied uniformly to the `open-external` IPC entry point or to `LinkButton` itself — mirroring the Zap `redeem()` bug where the mitigation ("check the token/parameter before acting on it") was applied inconsistently.

### Impact Explanation
`shell.openExternal` on Windows/macOS/Linux can hand off arbitrary URI schemes to the OS shell (custom protocol handlers, `file:`, or other registered handlers), which historically has been abused in Electron apps to reach code execution or unwanted local application launches via crafted protocol payloads. Any code path that lets attacker-influenced content (GitHub API objects rendered via `LinkButton`, e.g. `IAPIComment.html_url`/`html_url` fields, secret-scanning `bypassURL`, or other server-controlled strings surfaced in the UI) reach `LinkButton`/`open-external` without a scheme allow-list inherits this risk.

### Likelihood Explanation
Exploitability depends on finding a call site where the `uri` fed into `LinkButton`/`openExternal` is not a hard-coded Desktop constant but originates from an external, less-trusted source (a GHES/GHAE server response, or repository-derived data) that isn't first restricted to `https:`. I was not able to fully confirm such an untrusted, non-hardcoded call site in the code I could inspect — most `LinkButton` usages I found use hardcoded first-party URLs or GitHub API `html_url` fields, which GitHub itself normally formats as canonical `https://` URLs. The submodule-info link in `submodule-diff.tsx` reconstructs the URI as `https://${hostname}/${owner}/${name}`, which forces the scheme and is not exploitable via protocol injection (only the host/path portion is attacker-influenced). Given the index size limits on this ask-only session, I could not exhaustively enumerate every `LinkButton uri=...` call site in the codebase to find one fed directly by untrusted, unsanitized repository or third-party data reaching an unrestricted scheme.

### Recommendation
- Add a centralized scheme allow-list (`https:`, and `mailto:` if needed) in the `open-external` IPC handler in `app/src/main-process/main.ts`, rejecting or warning on any other scheme before calling `shell.openExternal`.
- Apply the same protocol check used in `sandboxed-markdown.tsx` (`/^https?:/`) inside `LinkButton.onClick` so every consumer of the component gets the protection automatically rather than depending on each caller to pre-validate its `uri`.
- Audit all `LinkButton uri={...}` call sites for any that plumb a repository-derived or third-party-service-derived string ithout enforcing `https:` first.

### Proof of Concept
Not independently verified end-to-end within the available index (no confirmed untrusted-data call site reaching an unrestricted scheme was located). The concrete, verifiable gap is structural: `ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts:581-597` and `LinkButton.onClick` in `app/src/ui/lib/link-button.tsx:76-92` both invoke `shell.openExternal` with zero scheme validation, unlike the equivalent link-click path in `app/src/ui/lib/sandboxed-markdown.tsx:288-305`, which does enforce `https?:`. A full PoC would require identifying (or introducing, e.g. via a future feature) a call site where `uri`/`path` is populated from repository or third-party content without a prior `https:` restriction.

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })

        const a = ev.target.closest('a')

        }
      }
