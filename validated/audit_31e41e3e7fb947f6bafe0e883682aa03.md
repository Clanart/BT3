### Title
Malformed `---` delimiter in hookify rule pattern silently truncates YAML frontmatter, causing `action: block` to be dropped and defaulted to `warn` - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` uses a naive `content.split('---', 2)` to separate frontmatter from the message body, with no awareness of YAML document-boundary semantics. If a rule's `pattern` (or any value) written after the `action` line does not itself contain `---`, this is not exploitable; but if the frontmatter section legitimately contains a literal `---` sequence anywhere before the `action:` key is reached in file order, or if `action: block` is placed after a value/pattern containing `---`, the split truncates the frontmatter early, dropping `action: block` from the parsed dict and causing `Rule.from_dict` to fall back to its default of `warn` at [1](#0-0) .

### Finding Description
`extract_frontmatter` naively splits on the literal three-character sequence `---` using `parts = content.split('---', 2)`, taking `parts[1]` as the entire frontmatter text [2](#0-1) . This is not a real YAML parser and does not respect quoting: any `---` occurring inside a value on a line *before* the `action:` key (in file order) will be treated as the closing frontmatter delimiter, silently truncating the frontmatter dict and pushing all subsequent lines — including `action: block` — into the `message` body text, which is never parsed for the `action` key.

`Rule.from_dict` then reads `frontmatter.get('action', 'warn')`, defaulting to `'warn'` when the key is absent [3](#0-2) . `RuleEngine.evaluate_rules` treats any rule whose `action != 'block'` as a non-blocking warning rule, which only sets a `systemMessage` and allows the tool call to proceed, rather than emitting `permissionDecision: deny` [4](#0-3) [5](#0-4) .

Reachability: `/hookify` generates rule files from example patterns provided either by the user or, notably, by an LLM-driven `conversation-analyzer` agent that extracts "regex or literal pattern" text directly from conversation/user content [6](#0-5) , and the generated file template places `pattern: {regex pattern}` on the line *before* `action: {warn|block}` [7](#0-6) . If attacker-influenced conversation/repo content causes a pattern value containing a literal `---` sequence (e.g. a regex like `rm -rf ---` or any dangerous-command example text embedded with `---`) to be written unescaped into the `pattern:` line, the resulting file's `action: block` line ends up in the "message" portion and is dropped from the parsed frontmatter, downgrading a would-be blocking rule to warn-only — while the on-disk `.md` file still visibly shows `action: block`, meaning the parsed `Rule` object silently diverges from the visible file, exactly matching the described invariant violation.

There is no quoting/escaping enforcement of pattern values in the file template, no schema validation performed on the produced rule file, and `extract_frontmatter` provides no fallback detection for an incorrectly-terminated frontmatter block (e.g. it does not verify that `parts[1]` looks like structurally complete YAML or count `---` occurrences at line starts only, which is the standard YAML/Markdown frontmatter convention of requiring `---` to be alone on its own line).

### Impact Explanation
This breaks the stated security invariant "a deny rule must never be parsed into a non-blocking configuration." A rule author (or an automated `/hookify` flow acting on attacker-influenced conversation content) who believes they created a `block` rule for a dangerous command actually gets a rule that only warns and allows the dangerous tool invocation (e.g., `rm -rf`) to execute, matching the "Security-control bypass that silently disables or routes around blocking" impact category — the block silently becomes a no-op enforcement-wise while superficially appearing intact in the file.

### Likelihood Explanation
Exploitability depends on getting a `---` sequence into a frontmatter value positioned before the `action:` key in a generated/edited `.claude/hookify.*.local.md` file. This is plausible because: (1) the `/hookify` command's own template places `pattern:` before `action:` [8](#0-7) ; (2) pattern content can originate from conversation-analyzer-extracted text or direct user/repo-provided examples, neither of which is sanitized for `---`; (3) no unit test or validation step in `load_rule_file`/`extract_frontmatter` checks for this truncation — it silently succeeds with a plausible-looking (but incomplete) dict rather than raising an error. However, it requires the specific coincidence of a `---`-containing pattern combined with `action` appearing after it, so it is not guaranteed on every rule but is a real, reproducible parser defect, not merely theoretical.

### Recommendation
Replace the ad hoc `split('---', 2)` parser with a proper frontmatter boundary rule: only treat a line that is *exactly* `---` (stripped, on its own line) as a delimiter, and use a real YAML parser (e.g. `yaml.safe_load`) for the frontmatter block instead of the current hand-rolled line-based state machine. Additionally, add a post-parse validation in `load_rule_file` that rejects/logs rules where the raw file text contains an `action: block` (or similar) string that does not appear in the parsed `frontmatter` dict, as a defense-in-depth consistency check between visible file content and parsed `Rule`.

### Proof of Concept
Unit test for `plugins/hookify/core/config_loader.py`:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

malformed = """---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm -rf --- do not run
action: block
---

Dangerous rm command blocked!
"""

fm, msg = extract_frontmatter(malformed)
rule = Rule.from_dict(fm, msg)

# Expected (if parser were correct): rule.action == 'block'
# Actual observed: 'action' key is dropped from `fm` because the
# literal '---' inside the pattern value prematurely closes the
# frontmatter block; Rule.from_dict falls back to default 'warn'.
assert rule.action == 'warn'  # demonstrates the downgrade bug
```
Integration test: place the malformed file at `.claude/hookify.block-dangerous-rm.local.md`, invoke the Bash pre-tool-use hook with `tool_input.command = "rm -rf /"`, and assert `RuleEngine.evaluate_rules` returns a `systemMessage`-only response (warn) instead of `hookSpecificOutput.permissionDecision == "deny"` (block), confirming the dangerous command is not actually blocked despite the file visibly containing `action: block`.
