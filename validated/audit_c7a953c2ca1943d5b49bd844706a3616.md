## Analog Found: Duplicate-Token Escrow/Partial-Fill Collision in the `intentsv2` Module Family

### Title
Same-chain intent settlement allows escrow over-release via duplicate input/output tokens — analog present in `evm/src/apps/intentsv2/` without the duplicate-token guard that protects the monolithic gateway - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The PYT report's root cause is a cached/shared value that gets **overwritten instead of accumulated** when two logically distinct operations collapse onto the same storage key (`from == to`). Hyperbridge's intent-settlement code has the exact same class of bug: escrow accounting keys off `token address` and off `outputToken`, and both `_orders[commitment][token]` (escrow credit) and `_partialFills[commitment][outputToken]` (fill progress) are **overwritten/shared** rather than isolated per order leg. If an order contains two legs referencing the same token, the two legs collide on one storage slot exactly like `PerpetualYieldToken`'s `balanceOf[to]` collided on self-transfer.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol`, `placeOrder` credits escrow with a direct overwrite: [1](#0-0) 

and this is exploitable if the input array contains the same token twice: the user's tokens are pulled twice via `safeTransferFrom` (Phase 1), but the escrow record is written non-additively, so the second write clobbers the first, exactly like `balanceOf[to] = toBalance + amount` clobbering the zeroed `balanceOf[msg.sender]` in the PYT bug. The same collision exists on the output side via the shared `_partialFills[commitment][outputToken]` bucket used in `_fillSameChain`: [2](#0-1) 

Two output legs pointing at the *same* `outputToken` share one `_partialFills[commitment][outputToken]` progress counter and one `alreadyFilled`/`remaining` computation, while the escrow release per leg is still calculated **per input index `i`** (`order.inputs[i].amount * fillAmount / totalRequired`) rather than per token — this is the "attacker structures self-referential operations to make cached/shared state overwrite itself" primitive, applied to intent settlement instead of token transfer.

The monolithic `evm/src/apps/IntentGatewayV2.sol` was already patched for this exact defect: `placeOrder` now explicitly rejects duplicate output tokens via transient-storage dedup and duplicate input tokens via a `_orders[commitment][token] != 0` check before crediting: [3](#0-2) [1](#0-0) 

The regression tests confirm this was a real, previously-exploitable bug in the exact same escrow/partial-fill mechanism: [4](#0-3) [5](#0-4) 

However, the modular `intentsv2` implementation (`IntentsBase.sol`, `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`) — which defines its own `_orders`, `_partialFills`, and `_fillSameChain`/`_withdraw` logic identical in structure to the vulnerable pre-patch code — contains **no duplicate-token rejection anywhere in the directory**: neither a `function placeOrder` definition nor any "reject duplicate" guard exists under `evm/src/apps/intentsv2/`. The escrow map declaration and shared-bucket declarations mirror the vulnerable pattern verbatim: [6](#0-5) 

### Impact Explanation
If the `intentsv2` module's order-placement entry point (composed from `IntentsBase`) does not carry forward the duplicate-input/duplicate-output guard, an order containing two legs on the same token would let escrow accounting be clobbered on placement or let `_fillSameChain`'s shared `_partialFills` bucket miscompute `fillAmount`/`remaining` across the duplicated legs. Either path can cause escrowed user funds to be released beyond what was legitimately owed, or leave user-paid funds unaccounted in escrow — a direct "loss or theft of funds" / "transaction manipulation" outcome in bridge custody, matching the bounty's fund-safety criteria.

### Likelihood Explanation
This requires no privileged actor: any user calling `placeOrder` (or whatever `intentsv2` exposes as its order-placement entrypoint) with a duplicate-token order, and any solver calling the corresponding fill function, can trigger the collision — the same "self-transfer" pattern from the original report, fully within an unprivileged, single-transaction attacker primitive.

### Recommendation
Port the exact fix already applied to `evm/src/apps/IntentGatewayV2.sol` — the duplicate-output-token transient-storage check and the duplicate-input-token `_orders[commitment][token] != 0` guard — into the `intentsv2` module's order-placement path (`IntentsBase.sol`/whatever contract implements `placeOrder` on top of it), and add the same regression tests (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateOutputTokens`) against the `intentsv2` contract set.

### Proof of Concept
1. Construct an `Order` with `inputs = [ {token: USDC, amount: A}, {token: USDC, amount: B} ]` (same token twice) and place it via the `intentsv2` gateway's order-placement entrypoint.
2. Because Phase-1 token pulls (`safeTransferFrom`) run per array index, the user is charged `A + B` USDC.
3. Because escrow crediting in the shared base logic writes `_orders[commitment][token] = amount` per index without an existing-value check (unlike the patched `IntentGatewayV2.sol`), the second write for USDC overwrites the first, leaving only `B` (or `A`, depending on fee-reduction order) recorded as escrow — the surplus becomes unaccounted, and/or a symmetric structure on the output side lets `_fillSameChain`'s shared `_partialFills[commitment][outputToken]` bucket be manipulated across the duplicated legs to over-release escrow relative to what was actually delivered to the beneficiary, mirroring the `testRevert_PlaceOrder_DuplicateOutputTokens`/`testRevert_PlaceOrder_DuplicateInputTokens` regressions already proven exploitable against the monolithic gateway before its fix.

**Caveat:** I could not locate the exact contract file that implements the public `placeOrder`/fill entrypoints on top of `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` (it is not under `evm/src/apps/intentsv2/`), so I could not directly confirm at the call-site level whether that composing contract independently re-adds the duplicate-token guard. The vulnerable underlying pattern (`_orders` overwrite-on-credit and shared `_partialFills` bucket) is confirmed present in the `intentsv2` base/mixin files, and no guard code exists anywhere in that directory — a Devin session with repo access should locate the concrete composing contract and verify/patch its `placeOrder` implementation.
