### Title
Reward-per-share snapshotting in `BaseRewardPoolV2._provisionReward` lets an attacker sandwich `queueNewRewards`/`donateRewards` to steal freshly injected rewards - (File: rewards/BaseRewardPoolV2.sol)

### Summary
`BaseRewardPoolV2` distributes reward tokens to `MasterMagpie` stakers using a global `rewardPerTokenStored` accumulator that is bumped by `_provisionReward()` in proportion to `totalStaked()` at the exact moment a reward is injected. Because a staker's share of any newly injected reward depends only on their balance at that instant and not on how long they have actually been staked, an attacker can deposit into the pool immediately before a reward injection (`queueNewRewards` by a manager, or the permissionless `donateRewards`) and withdraw immediately after collecting their disproportionate share, exactly the "sandwich the rate/reward update" pattern described in the external report for `VectorETH`.

### Finding Description
`_provisionReward` computes the new `rewardPerTokenStored` using the instantaneous `totalStaked()`: [1](#0-0) 

`totalStaked()` reads the live staking-token balance held by `MasterMagpie` at call time: [2](#0-1) 

A user's earned amount for any reward token is `_userShare * (rewardPerToken - userRewardPerTokenPaid) / 10**decimals + userRewards`, i.e., it is a pro-rata split of whatever reward was queued while the user's balance was recorded, with no notion of deposit duration: [3](#0-2) 

Deposits and withdrawals into `MasterMagpie` are immediate and have no lock-up, cooldown, or vesting for the "available" (unlocked) staking-token pools — `_deposit`/`_withdraw` simply harvest, adjust `user.amount`/`user.available`, and move the underlying tokens: [4](#0-3) 

Because `rewardPerTokenStored` is bumped a single time, atomically, based on whoever is staked at that moment, an attacker who front-runs a large `queueNewRewards` (called periodically by a reward manager, e.g., a `PoolHelper` harvest) or the permissionless `donateRewards` call can:
1. Deposit a large amount of the staking token into `MasterMagpie` for that pool right before the reward-queuing transaction.
2. Let the reward-queuing transaction execute, which credits `rewardPerTokenStored` proportional to the attacker's now-dominant share of `totalStaked()`.
3. Immediately claim rewards (`getReward`/`multiclaim`) and withdraw the deposited principal.

This mirrors the reported `VectorETH` bug class: the reward/rate math is a single point-in-time proportional split rather than being weighted by the time each depositor actually contributed to earning the reward, letting a large, brief deposit siphon rewards meant for long-term stakers.

`donateRewards` in particular has no access control beyond the reward token being registered, making the attack fully triggerable from an ordinary wallet without waiting for a manager's `queueNewRewards` call: [5](#0-4) 

### Impact Explanation
This is a direct theft of yield/rewards belonging to genuine long-term stakers of any `MasterMagpie`-registered pool that uses `BaseRewardPoolV2` (which is the primary reward pool implementation used across the LP/MGP/mWOM staking pools). An attacker can capture a disproportionate share of every reward injection by flash-depositing right before it and withdrawing right after, diluting/stealing rewards from all other depositors in that pool. This satisfies the "theft or permanent freezing of unclaimed yield" impact category — the diverted reward tokens are permanently lost to the legitimate long-term stakers.

### Likelihood Explanation
Likelihood is high: reward injections (`queueNewRewards`) happen routinely (harvest cycles via pool helpers), are visible in the mempool, and deposits/withdrawals into `MasterMagpie` for these pools are unrestricted for any wallet holding the staking token, with no lock period on the "available" balance. `donateRewards` is fully permissionless and can even be self-triggered by the attacker to time the sandwich precisely, removing the need to front-run a third-party transaction at all — the attacker can simply deposit, call `donateRewards` themselves (funding the pool from their own resources is not required since they only need `isRewardToken[_rewardToken]` to be true and can donate any small amount to force a snapshot after depositing, but the larger and more damaging case is front-running a large manager-initiated `queueNewRewards`).

### Recommendation
Rework reward accrual so that a user's entitlement to newly queued rewards is weighted by the time-integral of their stake (e.g., a checkpoint/streaming model such as accruing rewards over a `periodFinish` window as seen in `WomUp.sol`'s `rewardRate`/`lastUpdateTime` design) rather than crediting the full reward against the instantaneous `totalStaked()`. At minimum, add a deposit cooldown (time-lock before a fresh deposit's balance counts toward `totalStaked()`/`balanceOf()` for reward purposes) or stream rewards linearly over time instead of crediting them atomically at `_provisionReward()`.

### Proof of Concept
1. Attacker monitors mempool / anticipated harvest schedule for a `BaseRewardPoolV2` instance backing a `MasterMagpie` pool with a small existing `totalStaked()`.
2. Attacker calls `MasterMagpie._deposit`-driven entrypoint (e.g., `depositFor`/pool-helper deposit) to stake a very large amount of the pool's staking token, becoming the majority of `totalStaked()`.
3. A manager's `queueNewRewards(amountReward, rewardToken)` (or the attacker's own `donateRewards`) executes, calling `_provisionReward`, which increases `rewardPerTokenStored` by `(amountReward * 10**decimals) / totalStaked()` — with the attacker now owning most of `totalStaked()`.
4. Attacker calls `getReward`/`multiclaim` to harvest their pro-rata share of `rewardPerTokenStored`, then immediately withdraws their principal via the corresponding withdraw path, having held the position for a negligible amount of time yet capturing most of the newly injected reward. [6](#0-5)

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

    function _earned(address _account, address _rewardToken, uint256 _userShare) internal view returns (uint256) {
        return ((_userShare *
                (rewardPerToken(_rewardToken) -
                    userRewardPerTokenPaid[_rewardToken][_account])) /
                10**stakingTokenDecimals) + userRewards[_rewardToken][_account];
    }
```
