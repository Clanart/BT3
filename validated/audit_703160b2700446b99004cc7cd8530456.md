### Title
JIT-deposit reward sniping via lump-sum `_provisionReward` tied to instantaneous `totalStaked()` - ([File: rewards/BaseRewardPool.sol])

### Summary
`_provisionReward` (invoked by `queueNewRewards`) distributes an entire reward donation instantly by dividing it by the *current* `totalStaked()`, with no time-weighting, streaming rate, or vesting. Because `depositLP`/`withdraw` have no lock-up or minimum staking duration, an attacker can front-run a manager's `queueNewRewards` transaction with `depositLP`, receive a pro-rata share of the injected reward for zero staking time, then `withdraw` in the same block, diluting the rewards that should accrue to honest long-term stakers.

### Finding Description
`_provisionReward` computes:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
``` [1](#0-0) 
This happens atomically inside `queueNewRewards`, using whatever `totalStaked()` (i.e., `IERC20(stakingToken).balanceOf(operator)`) is at that instant. [2](#0-1) 

An attacker who front-runs the manager's `queueNewRewards` transaction (gets their transaction ordered first in the same block, which is achievable via normal gas-price bidding since `queueNewRewards` is a plain visible mempool transaction) can:
1. Call `WombatPoolHelper.depositLP(_lpAmount)`, which calls `_stake` → `MasterMagpie.depositFor`, increasing `totalStaked()` and setting the attacker's `userRewardPerTokenPaid` to the pre-injection `rewardPerTokenStored` value. [3](#0-2) [4](#0-3) 
2. Let the manager's `queueNewRewards` land, which now spreads the injected reward over a `totalStaked()` that includes the attacker's freshly-deposited principal, crediting the attacker (and diluting existing stakers) via the updated `rewardPerTokenStored`. [5](#0-4) 
3. Immediately call `WombatPoolHelper.withdraw(_liquidity, 0)`, which triggers `_harvestAndUnstake` → `getReward`, paying out `earned()` computed from the now-inflated `rewardPerTokenStored` minus the attacker's low `userRewardPerTokenPaid`, then returns the principal. [6](#0-5) [7](#0-6) 

There is no mechanism preventing this: no time-weighted/streamed reward-rate accounting (unlike a typical `StakingRewards.rewardRate`/`periodFinish` model), no minimum staking duration, no same-block deposit/withdraw restriction, and no snapshotting of "eligible" balances prior to a reward injection. `nonReentrant`/`whenNotPaused` modifiers on `WombatStaking.depositLP`/`withdraw` only guard against reentrancy and pausing — they do not stop distinct transactions (front-run deposit, manager tx, withdraw) from executing in the same block. [8](#0-7) [9](#0-8) 

### Impact Explanation
This is a direct theft of unclaimed yield from existing/long-term stakers: a JIT depositor with zero economic exposure time captures a proportional slice of every reward donation, permanently reducing the `rewardPerTokenStored` accrual that would otherwise flow to legitimate stakers who bore price/duration risk. This matches the Immunefi impact class "theft of unclaimed yield." It is not principal theft (the attacker cannot withdraw more principal than deposited), and it does not freeze funds; the loss is limited to the reward slice diverted per attack, but it is repeatable against every `queueNewRewards`/`donateRewards` call and scales with the attacker's deposit size relative to `totalStaked()`.

### Likelihood Explanation
Feasibility is high: `queueNewRewards` is called by whitelisted managers as routine reward funding and is visible in the public mempool before inclusion; an attacker only needs sufficient capital to briefly hold a large LP position and pay a higher gas price (or use a private relay) to land `depositLP` in the same block, before the manager's transaction, then `withdraw` right after. No privileged role is needed — only `depositLP`, `withdraw`, and normal token approvals, all public/external functions. The attack is fully repeatable for every reward funding event and is capital-efficient because principal is only at risk for one block/transaction bundle (subject to withdrawal/slippage parameters and any external Wombat pool withdrawal fees, which are out of scope here).

### Recommendation
Replace the lump-sum, instant-injection reward model with a time-weighted/streamed distribution (e.g., Synthetix-style `rewardRate` over a fixed `rewardsDuration`, updated via `lastUpdateTime`/`periodFinish`), so `rewardPerToken()` accrues continuously rather than jumping the entire donated amount onto whatever `totalStaked()` happens to be at the exact block of injection. Alternatively/additionally, introduce a minimum staking duration or checkpoint-based eligibility (e.g., only balances staked before `block.number - N` or before the reward-injection transaction are eligible for that specific reward tranche) to prevent same-block or near-instant deposit-then-withdraw reward capture.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (or `BaseRewardPoolV2`), `WombatStaking`, `WombatPoolHelper`, mock LP token, mock reward token; register a manager for the reward pool.
2. Set up two honest stakers, Alice and Bob, each depositing LP via `depositLP` at `block N`, and let several blocks pass with no reward events, confirming `earned()` for both is 0 (no rewards yet).
3. In a single test block (use `hre.network.provider.send("evm_setAutomine", [false])` or manually build a multi-tx block), simulate the front-run:
   a. Attacker (Mallory) calls `depositLP(largeAmount)`.
   b. Manager calls `queueNewRewards(rewardAmount, rewardToken)`.
   c. Mallory calls `withdraw(largeAmount, 0)` immediately in the same block.
   Mine the block so all three txs land in the same block, with Mallory's deposit ordered before `queueNewRewards`.
4. Assert: `earned(Mallory, rewardToken)` (captured right before her withdraw executes, or via emitted `RewardPaid` event) is > 0 despite Mallory having staked for zero blocks/time.
5. Assert conservation violation: compute `sum(earned(Alice) + earned(Bob) + rewardPaidToMallory)` and show that Alice's and Bob's `earned()` per unit staked is strictly lower than it would have been had Mallory not front-run the deposit (i.e., rerun the same scenario without Mallory's deposit/withdraw and compare `rewardPerTokenStored` deltas), demonstrating dilution/yield theft directly attributable to the JIT deposit-withdraw sandwich around `queueNewRewards`.
