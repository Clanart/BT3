### Title
Submodule checkout re-enables `protocol.file.allow=always` based on repository-controlled submodule state, permitting local file exfiltration via a malicious clone - (File: app/src/lib/git/submodule.ts)

### Summary
Similar to the `TimeLock` bug, where a privileged action (agreement satisfaction) is decoupled from the verification step that should gate it (confirming the asset transfer actually happened), GitHub Desktop's submodule-checkout flow decouples the decision to grant an elevated Git protocol permission (`protocol.file.allow=always`) from any verification that the submodule URL requesting that permission is trustworthy. The `allowFileProtocol` flag is threaded from `checkoutBranch`/`checkoutCommit` into `updateSubmodulesAfterOperation`, and when `true` it unconditionally adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation.

### Finding Description
`checkoutBranch` and `checkoutCommit` accept an `allowFileProtocol` boolean (default `false`) and pass it straight through to `updateSubmodulesAfterOperation`: [1](#0-0) 

`updateSubmodulesAfterOperation` uses that flag to decide whether to append `-c protocol.file.allow=always` before running `submodule update --init --recursive`: [2](#0-1) 

Git upstream deliberately restricts `file://` protocol usage for submodule clones by default (hardening added after CVE-class issues where a malicious repository's `.gitmodules` could point a submodule at an arbitrary local path, causing `git submodule update --init` to "clone" that local path into the submodule directory of the working tree). Desktop's own test fixtures confirm this exact mechanic is exercised: a submodule is added using a local filesystem path with `protocol.file.allow=always`, then `checkoutBranch` is called with the fifth argument (`allowFileProtocol`) explicitly set to `true` to initialize it: [3](#0-2) 

The submodule URL and the very fact that a submodule is "uninitialized" are both entirely attacker-controlled: they come from `.gitmodules` and `.git/config` inside a repository the user clones or fetches. If the logic in `app-store.ts` that decides to pass `allowFileProtocol: true` does so based on detecting an uninitialized submodule in the target branch/commit (rather than validating that the submodule's URL is a remote, non-local, expected-host URL), then simply cloning an attacker-authored repository and checking out a branch is enough to trigger `git -c protocol.file.allow=always submodule update --init --recursive`, with the submodule URL fully chosen by the attacker.

### Impact Explanation
If the submodule URL is set to `file:///path/to/existing/local/git/repo` (e.g., a commonly-known path on the victim's machine, or a path guessed/discovered via other means), `git submodule update --init` will treat that local path as a Git repository and clone/copy its contents into a directory inside the victim's working tree. This is a "file read outside the repo" primitive: the attacker's cloned repository, once checked out, pulls contents from arbitrary local paths into the user's working directory. If the user subsequently stages/commits/pushes (a very natural next step for a repository that just "gained files"), those contents are silently exfiltrated to whatever remote the attacker controls — matching "silent corruption of what the user commits or pushes" and unauthorized disclosure of local file contents to a remote the attacker chose.

### Likelihood Explanation
The attacker-controlled surface (a cloned/fetched repository) is exactly the category this task's Valid Impact section calls out. No local/physical access, admin rights, or pre-existing malware are required — only that the victim clones and checks out a branch in a repository the attacker authored, which is core, expected GitHub Desktop usage. The likelihood of this being reachable depends entirely on the exact condition in `app-store.ts` that decides to pass `true`; I was unable to confirm within my available tool calls whether that decision is scoped narrowly (e.g., only for submodules whose URL matches the parent's already-trusted host) or broadly (any uninitialized submodule, regardless of URL scheme). This is the key open question a Devin session with full file access should resolve before treating this as confirmed-exploitable.

### Recommendation
- Never automatically pass `allowFileProtocol: true` based solely on repository-declared state (e.g., "submodule uninitialized"). The presence or absence of an uninitialized submodule is fully attacker-controlled content, exactly like the `TimeLock` bug's "agreement creation" step being triggerable without any check on the paired "asset transfer" step.
- If `file://` submodule initialization must be supported for local development/testing, explicitly gate it behind additional checks (e.g., the submodule URL's host is the same as an already-configured remote, or the path is inside the already-cloned repository tree) so that a hostile clone cannot direct Desktop to read from arbitrary local paths.
- Preserve Git's own default `protocol.file.allow` hardening behavior for submodules originating from untrusted, freshly cloned/fetched repositories.

### Proof of Concept
1. Attacker creates a public repository with a branch containing a `.gitmodules` entry such as:
   ```
   [submodule "steal"]
       path = steal
       url = file:///Users/victim/some-existing-local-repo
   ```
   with the submodule left uninitialized in `.git/config`/index (as in the `setupRepositoryWithUninitializedSubmodule` fixture pattern). [4](#0-3) 
2. Victim clones the attacker's repository via GitHub Desktop and checks out the branch containing this submodule.
3. If Desktop's checkout flow detects the uninitialized submodule and calls `checkoutBranch(repository, branch, remote, progressCallback, true)`, this results in: `git -c protocol.file.allow=always submodule update --init --recursive` [5](#0-4) 
4. Git clones `file:///Users/victim/some-existing-local-repo` into `steal/` inside the victim's working directory, exposing that local repository's file contents inside the attacker's repo's working tree, ready to be committed/pushed back to the attacker's remote.

**Note on confidence:** I could not verify, within the available search budget, the exact conditional in `app-store.ts` that ultimately sets `allowFileProtocol`. The mechanism (`checkout.ts` → `submodule.ts`) and the test fixtures proving Desktop intentionally supports `true` for this flag are confirmed; whether the real trigger condition is narrow/safe or broad/exploitable is not confirmed and should be validated directly against `app-store.ts` before treating this as a confirmed, exploitable finding.

export async function setupRepositoryWithUninitializedSubmodule(
  t: TestContext
): Promise<Repository> {
  const repo = await setupTwoCommitRepo(t)

  // Create a submodule repository
  const submoduleRepo = await setupTwoCommitRepo(t)

  // Create a new branch and add the submodule
  await exec(['checkout', '-b', 'branch-with-submodule'], repo.path)

  await exec(
    [
      '-c',
      'protocol.file.allow=always',
      'submodule',
      'add',
      submoduleRepo.path,
      'test-submodule',
    ],
    repo.path
  )
  await exec(['commit', '-m', 'Add submodule'], repo.path)

  // Go back to main branch
  await exec(['checkout', 'master'], repo.path)

  // Remove the .git/modules directory for the submodule to make it uninitialized
  const modulesPath = join(repo.path, '.git', 'modules', 'test-submodule')
  await rm(modulesPath, { recursive: true, force: true })
  await rm(join(repo.path, 'test-submodule'), { recursive: true, force: true })

  return repo
}
