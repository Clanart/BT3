The strongest analog to the reported Elasticsearch CWE-789 pattern ("a small, specially crafted request causes an excessively large memory allocation that exhausts memory and kills the process") in this codebase is the Full Node RPC `get_blocks` endpoint, which builds an unbounded height list directly from attacker-supplied `start`/`end` integers with no upper-bound check.

### Title
Unbounded Memory Allocation via `start`/`end` Range in Full Node RPC `get_blocks` - (File: chia/full_node/full_node_rpc_api.py)

### Summary
The `/get_blocks` RPC endpoint parses `start` and `end` from the request body and builds a `block_range` list by iterating `range(start, end)` with no upper bound, before ever touching the database. A single small JSON RPC request with a very large `end` value forces the full node to allocate a list containing up to `end - start` `uint32` objects, which can be billions of entries from a tiny request payload.

### Finding Description
In `get_blocks`, `start` and `end` are taken directly from the request dict and converted to `int`, then used to populate `block_range`: [1](#0-0) 

There is no validation that `end - start` is bounded by any constant analogous to `MAX_BLOCK_COUNT_PER_REQUESTS`, which is enforced on the equivalent peer-to-peer protocol message `request_header_blocks`: [2](#0-1) 

The sibling RPC endpoint `get_block_records` at least bounds its loop by the chain's actual `peak_height` inside the loop body before appending to the result list: [3](#0-2) 

`get_blocks` has no such check — the list comprehension runs to completion for the full requested range regardless of the actual chain height, so `block_range` can be built to an attacker-chosen size before `get_full_blocks_at()` is even called.

### Impact Explanation
Any RPC caller who can reach the full node RPC surface (a "semi-trusted" local RPC caller per the trust boundary map) can submit a single small JSON body such as `{"start": 0, "end": 4294967295}` to `/get_blocks`. This forces the full node process to allocate a Python list of hundreds of millions to billions of `uint32` objects purely from list construction, which can exhaust process memory and crash or severely degrade the full node — a spend-triggered/RPC-triggered transaction-processing halt via resource exhaustion, matching CWE-789 (Memory Allocation with Excessive Size Value) / CAPEC-130 (Excessive Allocation) described in the report.

### Likelihood Explanation
The endpoint requires only a valid RPC client certificate (semi-trusted, not privileged/admin-only), and the crafted request is tiny (two integers) yet the resulting allocation is proportional to the difference between them, with no server-side clamp. This mirrors the "one small, specially crafted...request" reachability described in the source advisory.

### Recommendation
Clamp `end - start` to a bounded constant (e.g., reuse `MAX_BLOCK_COUNT_PER_REQUESTS` as done for the P2P `request_header_blocks` path) before constructing `block_range`, and/or validate against the current peak height the way `get_block_records` does, rejecting or truncating requests that exceed the limit.

### Proof of Concept
1. Connect to the full node RPC (`/get_blocks`) with a valid local RPC client certificate.
2. Send: `{"start": 0, "end": 4294967295, "exclude_header_hash": true}`.
3. Observe the full node attempting to allocate a list of ~4.3 billion `uint32` entries in `block_range` inside `get_blocks` before the DB query is issued, causing high memory pressure / OOM on the full node process.
