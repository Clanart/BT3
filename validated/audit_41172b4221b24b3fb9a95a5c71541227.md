### Title
Webhook HMAC verification does not bind the trusted `shop_domain` header to the signed payload, enabling cross-shop webhook replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` (the module the gem instructs developers to include in custom webhook controllers) authenticates only the raw request body via HMAC, while the shop identity used downstream (`shop_domain`) is read straight from the unauthenticated `X-Shopify-Shop-Domain` header. This is the same root-cause pattern as the reported issue: a signed/verified blob (the webhook body) is not cryptographically bound to the context it is later assumed to belong to (the originating shop). An attacker who can obtain any one genuine (body, HMAC) pair can replay it while substituting the domain header, causing the app to process the payload as if it came from a different, victim shop.

### Finding Description
`hmac_valid?` computes the HMAC over `request.raw_post` only: [1](#0-0) 

`WebhookVerification#verify_request` gates the action solely on this body HMAC, and separately exposes `shop_domain` by directly trusting the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header with no cryptographic tie to the HMAC-verified body: [2](#0-1) 

The gem's own documentation instructs developers building custom webhook handlers to rely on exactly this `shop_domain` value to route/scope webhook processing: [3](#0-2) 

And the generator-provided job templates use this untrusted `shop_domain` to resolve an ActiveRecord `Shop` and open a Shopify session/data context for it: [4](#0-3) [5](#0-4) 

Because the HMAC covers only the raw body and not the shop domain (or topic) header, the "ciphertext" (HMAC-authenticated payload) is not bound to the context it is trusted to represent — precisely the failure mode described in the report (encrypted/authenticated data not bound to its associated identity), just applied to HMAC-authenticated webhooks instead of AES-GCM ciphertexts.

### Impact Explanation
If an attacker controls or has visibility into any legitimate webhook delivery for one shop (e.g., their own store where they have installed the app and can observe real webhook traffic, or a captured request from logs/proxies), they can replay that exact body+HMAC to the same endpoint while changing only the `X-Shopify-Shop-Domain` header to a victim shop's domain. Because `hmac_valid?` never inspects the header, verification still passes, and the custom controller/job will process the payload under the wrong shop's `Shop` record and Shopify session — a cross-shop data/context confusion. Depending on the webhook topic and the app's job logic (e.g. uninstall, redact, cart/order handling), this can cause data to be applied to, deleted from, or acted upon for the wrong merchant's shop.

### Likelihood Explanation
Exploitation does not require the attacker to know `ShopifyApp.configuration.secret`; they only need one legitimately-signed webhook body (trivially obtainable by installing the app on any shop, including their own) to replay against another shop's domain. This applies to any app that follows the documented pattern of using `ShopifyApp::WebhookVerification` directly in a custom controller, which is explicitly recommended in the gem's own docs.

### Recommendation
Bind the shop identity (and topic) to the authenticated payload rather than trusting the header independently:
- Compute/verify the HMAC over a canonical string that includes the shop domain and topic (or otherwise validate that the header-provided domain matches an authenticated claim), or
- Prefer parsing shop/topic exclusively through `ShopifyAPI::Webhooks::Request`/`Registry.process` (as the default `WebhooksController` does) instead of the unauthenticated header helper, and deprecate/guard `shop_domain` in `WebhookVerification` so it cannot be used without accompanying authenticated context.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook delivery (raw body `B` and header `X-Shopify-Hmac-Sha256: H`), where `H = HMAC-SHA256(secret, B)`.
2. Replay the request to the app's custom webhook endpoint (implemented per docs using `ShopifyApp::WebhookVerification`) with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `hmac_valid?(B)` succeeds (HMAC only covers `B`), `verify_request` passes, and the controller/job calls `Shop.find_by(shopify_domain: "victim.myshopify.com")`, processing the attacker's webhook payload under the victim shop's session/context.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end

```markdown
If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```

The module skips the `verify_authenticity_token` before_action and adds an action to verify that the webhook came from Shopify. You can now add a post route to your application, pointing to the controller and action to accept the webhook data from Shopify.
