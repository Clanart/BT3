### Title
Legacy `pattern` field-inference in `Rule.from_dict` silently disables `event: file` block rules against the `Write` tool - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` auto-derives the condition `field` for legacy `pattern:` rules from the `event` value alone (`event: file` → `field: new_text`), without regard to which specific tool (`Write`, `Edit`, `MultiEdit`) triggers the hook. `RuleEngine._extract_field` resolves `new_text` to `tool_input['new_string']`, which does not exist for the `Write` tool (Write uses `content`). As a result, any legacy-style `pattern:` rule with `event: file` and `action: block` never matches `Write` operations, silently evading the block, while an equivalent rule written with explicit `conditions: [{field: content, ...}]` correctly blocks `Write`.

### Finding Description
`Rule.from_dict` at [1](#0-0)  converts a legacy `pattern` frontmatter field into a single `Condition` whose `field` is inferred purely from `event`: `bash`→`command`, `file`→`new_text`, else→`content`. This inference ignores that `event: file` is dispatched to three distinct tools (`Write`, `Edit`, `MultiEdit`), each with a different `tool_input` schema, as seen in the hook entrypoints filtering `tool_name in ['Edit', 'Write', 'MultiEdit']` for `event = 'file'` (e.g. [2](#0-1) ).

When `RuleEngine._extract_field` resolves the generated `new_text` field for tool_name `Write`, it falls into the `Write`/`Edit` branch and returns `tool_input.get('new_string', '')`, at [3](#0-2) . The `Write` tool's actual payload uses the key `content`, not `new_string`, so this lookup always returns an empty string for `Write` calls — never the actual file content. `_check_condition` then evaluates the regex/contains/etc. operator against `''` instead of the real content, at [4](#0-3) , so a legacy pattern rule practically never matches a `Write` call unless the pattern also matches an empty string.

By contrast, if the same intended check is authored with the "advanced" explicit `conditions` form (`field: content`, documented in [5](#0-4) ), `_extract_field`'s `content` branch correctly returns `tool_input.get('content') or tool_input.get('new_string', '')`, at [6](#0-5) , and the rule matches `Write` operations as intended.

This is a genuine legacy-vs-explicit semantic divergence: identical intended policy ("block if file content matches X") is enforced for `Edit`/`MultiEdit` but silently not enforced for `Write` when expressed via the legacy `pattern:` shorthand that the plugin's own documentation and `/hookify` skill recommend for "simple single-condition rules" ( [7](#0-6) ). Any content written entirely via `Write` (e.g., a brand-new file containing a hardcoded secret, forbidden command, or malicious payload) bypasses a `block` rule that the repository/session owner believes is protecting all file-write operations, whether that rule was hand-authored, repo-shipped, or generated by `/hookify`.

### Impact Explanation
A block rule intended to stop dangerous or policy-violating file content (e.g., "block hardcoded API keys in TypeScript files", "block writes of malicious code") is silently ineffective whenever the agent uses `Write` rather than `Edit`/`MultiEdit` to create/overwrite the file, because the legacy pattern's auto-derived `field=new_text` never resolves to real content for `Write`. This breaks the invariant that legacy and explicit rule forms enforce identical security semantics, and lets a false sense of protection persist (the rule shows as `enabled` and appears to function for edits) while the actual enforcement gap allows unauthorized file content to be written unblocked — a workspace/policy-enforcement bypass with real, reproducible security impact across any session/repo that relies on the documented legacy `pattern` shorthand for `event: file` block rules.

### Likelihood Explanation
No special privilege is required beyond the ability to trigger a `Write` tool call (any normal file-creation/edit flow) against a repository that has a `hookify.*.local.md` block rule authored in the legacy `pattern:` shorthand for `event: file` — the format explicitly documented and recommended by the plugin's own skill file for "simple single-condition rules." This is deterministic and 100% repeatable: every `Write` call against such a rule bypasses the block, every `Edit`/`MultiEdit` call against the same rule is correctly blocked.

### Recommendation
In `Rule.from_dict`, when converting the legacy `pattern` field for `event: file`, do not hardcode a single `field=new_text`; either (a) generate multiple `Condition`s (e.g. an OR-combined check across `content` and `new_text`), or (b) fix `RuleEngine._extract_field` so `new_text` resolves to `tool_input.get('content') or tool_input.get('new_string', '')` for the `Write` tool_name specifically (mirroring the `content` branch), guaranteeing legacy and explicit forms produce identical match results for the same tool. Add a regression test that runs a legacy-pattern block rule against `Write`, `Edit`, and `MultiEdit` events with matching content and asserts a "deny"/block decision in all three cases.

### Proof of Concept
Unit test plan (extends existing `rule_engine.py`/`config_loader.py` self-test patterns):
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter = {
    "name": "block-secret-write",
    "enabled": True,
    "event": "file",
    "action": "block",
    "pattern": "SECRET_KEY",
}
rule = Rule.from_dict(frontmatter, "blocked")
engine = RuleEngine()

write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "config.py", "content": "SECRET_KEY = 'abc123'"},
}
edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "config.py", "new_string": "SECRET_KEY = 'abc123'", "old_string": ""},
}

result_write = engine.evaluate_rules([rule], write_input)
result_edit = engine.evaluate_rules([rule], edit_input)

# Expected (current buggy behavior): result_write == {} (NOT blocked)
# Expected (correct behavior, invariant): result_write should equal result_edit's
# blocking shape (permissionDecision == "deny"), matching Edit's blocked result.
assert result_edit.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
assert result_write.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", \
    "Legacy pattern rule fails to block Write operations - evasion confirmed"
```
This demonstrates that the identical secret content is blocked via `Edit` but passes unblocked via `Write`, confirming the legacy/explicit semantic divergence and block-rule evasion.

### Advanced Format (Multiple Conditions)

For complex rules with multiple conditions:

```markdown
---
name: warn-env-file-edits
enabled: true
event: file
conditions:
  - field: file_path
    operator: regex_match
    pattern: \.env$
  - field: new_text
    operator: contains
    pattern: API_KEY
---

You're adding an API key to a .env file. Ensure this file is in .gitignore!
```

**Condition fields:**
- `field`: Which field to check
  - For bash: `command`
  - For file: `file_path`, `new_text`, `old_text`, `content`
- `operator`: How to match
  - `regex_match`: Regex pattern matching
```
