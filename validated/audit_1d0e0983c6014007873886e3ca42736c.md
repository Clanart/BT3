### Title
Permissionless On-Chain Mirror Coins Let Any Spend-Bundle Submitter Force DataLayer Nodes to Issue SSRF-Style HTTP Requests to Attacker-Chosen URLs - (File: `chia/wallet/db_wallet/db_wallet_puzzles.py`, `chia/data_layer/download_data.py`)

### Summary
The CVE-2021-1627 report describes an SSRF vulnerability where an unprivileged actor causes a trusted server component to issue outbound requests to attacker-controlled destinations. Chia's DataLayer "mirror" mechanism has an analogous bug class: mirror coins that advertise download URLs for a given store are permissionless and are not bound to store ownership, so any spend-bundle submitter can register arbitrary URLs for someone else's store, and other nodes' DataLayer services will automatically issue HTTP GET requests to those URLs.

### Finding Description
A DataLayer mirror is simply a coin created with the generic `P2_PARENT` puzzle curried with `1`, i.e. `MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()` [1](#0-0) . The store id ("launcher_id") and URL list that a mirror advertises are taken purely from the `CREATE_COIN` condition's memo field, with no cryptographic or puzzle-level binding to the actual DataLayer singleton/store owner: `get_mirror_info()` just reads `memos[0]` as the launcher_id and the rest as URLs from whichever coin creation matches `MIRROR_PUZZLE_HASH` [2](#0-1) . Because `P2_PARENT.curry(1)` is a generic "anyone can spend, provided by parent" puzzle rather than a puzzle authenticated against the DataLayer singleton, any wallet user submitting a spend bundle can create such a coin with any `launcher_id` memo (including one they do not own) and any attacker-chosen URL strings.

Other nodes that subscribe to that store id read all mirrors for it via `get_mirrors()`/`update_subscriptions_from_wallet()` [3](#0-2)  and store them as `ServerInfo` entries. The periodic `fetch_and_validate()` loop then iterates these server URLs and calls `insert_from_delta_file()` for each, which calls `download_file()` [4](#0-3) [5](#0-4) . When no plugin downloader is configured, `http_download()` performs an unauthenticated `aiohttp` GET request directly against the attacker-supplied URL concatenated with a filename derived from the store id/root hash: `session.get(server_info.url + "/" + filename, ...)` [6](#0-5) . There is no allow-list, no restriction against private/internal/link-local addresses (e.g. `169.254.169.254`, `127.0.0.1`, internal service ports), and no verification that the URL belongs to a server actually authorized by the store owner — the trust boundary documented in the repo's own design notes explicitly says "Plugin and mirror URLs are external trust inputs" [7](#0-6) , but no enforcement mechanism exists to stop an arbitrary third party from injecting mirrors for a store they don't own.

The `test_server_http_ban` test confirms the download path is driven purely by `ServerInfo(url=..., ...)` records with no origin validation [8](#0-7) .

### Impact Explanation
Any user able to submit a spend bundle (no special privilege required) can force every DataLayer node subscribed to (or auto-subscribed to, since owned stores are pseudo-subscribed) a targeted store id to make outbound HTTP requests to attacker-controlled hosts on a schedule (`manage_data_interval`, default 60s, per `chia/util/initial-config.yaml`). This is a classic SSRF primitive against the DataLayer service process: it can be used to probe/attack internal network services reachable from the DataLayer host, hit cloud metadata endpoints, perform request smuggling against internal HTTP services, or serve as a covert exfiltration/DoS channel (repeated requests, large response consumption up to `max_delta_file_size`). Because the requests are periodic and automatic (not user-interactive), this is a persistent, repeatable SSRF against any node participating in DataLayer for a targeted store, without requiring the victim to take any explicit action beyond having previously subscribed to (or created) that store.

### Likelihood Explanation
Likelihood is high for any DataLayer-participating node: creating the malicious mirror coin only requires a standard spend bundle spending some coin to `MIRROR_PUZZLE_HASH` with an arbitrary memo — no CAT, no singleton control, and no `dl_new_mirror` RPC ownership check is enforced at the puzzle level (the memo-based launcher_id binding is purely convention, not cryptographic authorization). Any node that subscribes to that store id (which can itself be discovered from chain data or DataLayer's own store registries) will pick up the malicious mirror automatically during its normal sync loop.

### Recommendation
- Cryptographically bind mirror-coin creation to the DataLayer singleton owner (e.g., require the mirror creation to be co-signed by or announced from the current singleton coin) rather than relying solely on unauthenticated memo data.
- Validate and restrict mirror/downloader URLs before use: block loopback, link-local, private, and metadata-service IP ranges, enforce scheme allow-lists, and consider requiring operator opt-in/allow-listing of mirror hosts before automatic fetch.
- Add configurable SSRF protections (e.g., DNS-rebinding-safe resolution, egress restrictions) around `http_download()` in `chia/data_layer/download_data.py`.

### Proof of Concept
1. Attacker crafts and broadcasts a standard spend bundle that spends any owned coin and creates a new coin with puzzle hash `MIRROR_PUZZLE_HASH` (`create_mirror_puzzle()` from `chia/wallet/db_wallet/db_wallet_puzzles.py`), with `CREATE_COIN` memos `[victim_store_id, "http://169.254.169.254/", ...]` where `victim_store_id` is the launcher id of a DataLayer store the attacker does not own.
2. Once confirmed on chain, any node's `wallet_rpc.dl_get_mirrors()` for `victim_store_id` returns this malicious URL (`chia/data_layer/data_layer.py:975-985`).
3. Any node subscribed to (or owning) `victim_store_id` runs its periodic `fetch_and_validate()` loop, selects the malicious `ServerInfo`, and calls `http_download()` which issues an unauthenticated `aiohttp.ClientSession().get("http://169.254.169.254/" + filename, ...)` request from the DataLayer service host (`chia/data_layer/download_data.py:298-319`).

Note: I was not able to fully trace the exact RPC handler code path for `dl_new_mirror` in `chia/wallet/wallet_rpc_api.py`/`chia/data_layer/data_layer_wallet.py` (e.g., whether it independently checks singleton ownership before broadcasting the spend), since the index truncated those specific handler bodies. If a background agent needs to confirm whether any additional ownership check exists at that RPC layer (as opposed to at the puzzle/consensus layer, which is what determines what an attacker can actually put on-chain), a full read of `chia/data_layer/data_layer_wallet.py`'s mirror-creation method and `chia/wallet/wallet_rpc_api.py`'s `create_new_dl`/mirror RPC handlers would be needed — a Devin session with full file access could verify this.

```python
def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

```python
async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
```
