### Title
Unauthenticated duplicate/missing-participant indexing panics in PedPoP encryption-key handling - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP encryption layer uses `assert!` and unchecked `HashMap` indexing (`enc_keys[&participant]`, `enc_keys[&decryptor]`) on state driven by messages received from other participants. A DKG participant who sends a second `EncryptionKeyMessage`, or who triggers a blame/decryption path naming a participant who never registered an encryption key, causes an unconditional panic — a remotely-triggerable crash (availability loss) analogous to CVE-2026-22009's "easily exploitable, low-privileged, network-reachable hang/crash" class.

### Finding Description
Three panic sites in `crypto/dkg/pedpop/src/encryption.rs` are reachable with attacker-controlled protocol inputs:

1. `Decryption::register` asserts the participant hasn't already registered: `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")`. An `EncryptionKeyMessage` is deserialized from peer bytes via `EncryptionKeyMessage::read` (`read_G` + inner message read, no deduplication) and passed to `register`. A participant who sends two registration messages in a session triggers the assert, panicking the honest node's DKG task. [1](#0-0) 
2. `Encryption::encrypt` indexes `self.decryption.enc_keys[&participant]`. If `encrypt` is invoked for a participant whose registration message was never received (or was rejected), the `HashMap` index panics. [2](#0-1) 
3. `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` when handling a blame/accusation flow with an attacker-supplied `decryptor` index. Naming a participant who never registered an encryption key panics. [3](#0-2) 

These are `panic!`-equivalent paths in production code reachable from `EncryptedMessage`/`EncryptionKeyMessage` bytes supplied by another party — not internal invariant violations gated behind `debug_assert`.

### Impact Explanation
A single crafted or replayed DKG message crashes the receiving node's key-generation/signing process. For a threshold network, repeatedly forcing nodes to abort during the DKG or blame-resolution phase prevents key generation from completing — a complete denial of service of the signing service matching the advisory's "hang or frequently repeatable crash (complete DOS)". No key material is leaked, but availability of the protocol is fully compromised per instance of the malicious message.

### Likelihood Explanation
The attacker needs only to be a DKG participant able to send messages to an honest party — a low-privilege, network-reachable position. Triggering requires sending a duplicate `EncryptionKeyMessage` (case 1) or an accusation referencing an unregistered `decryptor` (case 3); both are single-message, deterministic triggers with no computational work — directly mirroring CVE-2026-22009's `AC:L/PR:L` profile.

### Recommendation
Replace the `assert!` in `Decryption::register` with an error return (`Result<M, PedPoPError>`) so duplicate registrations are reported as a faulty-participant condition rather than panicking — consistent with the documented "presumed malicious" policy in `Commitments`. In `encrypt` and `decrypt_with_proof`, use `enc_keys.get(&participant)`/`get(&decryptor)` and return `Err`/`DecryptionError::InvalidProof` on `None` instead of indexing.

### Proof of Concept
Conceptual (crate-internal API): during `PedPoP` key generation, a malicious participant `j` serializes two distinct valid `EncryptionKeyMessage`s and broadcasts both. Each honest node calls `Encryption::register(j, msg1)` then `Encryption::register(j, msg2)`; the second call reaches `Decryption::register`, where `self.enc_keys.contains_key(&j)` is true and the `assert!` at `crypto/dkg/pedpop/src/encryption.rs:356` panics, aborting the node's DKG session on every honest node that processed both messages.
