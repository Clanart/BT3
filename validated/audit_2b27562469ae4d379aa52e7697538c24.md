### Title
Webhook HMAC verification does not bind the `X-Shopify-Shop-Domain` header, enabling cross-shop webhook replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only the raw request body against the HMAC header, while the `shop_domain` value used to route webhook data to per-shop background jobs is read from a completely unauthenticated header. Because the shop identity is never part of the signed material, a party who can obtain one validly-signed webhook body (e.g., by triggering a webhook from their own installed shop) can replay that body to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header and have the payload processed and attributed to a different shop.

### Finding Description
`PayloadVerification#hmac_valid?` computes the digest solely over `data` (the raw POST body): [1](#0-0) 

`WebhookVerification#verify_request` calls this with `request.raw_post`, and separately exposes `shop_domain` read directly from the `X-Shopify-Shop-Domain` header, with no cross-check against the signed body: [2](#0-1) 

The documented (and generator-produced) usage pattern explicitly forwards this unauthenticated header value, together with the body, into a background job that acts on behalf of that shop: [3](#0-2) [4](#0-3) 

This mirrors the report's root cause exactly: the signed artifact (HMAC digest) omits the identifying/binding context (the shop the payload is claimed to belong to), so the same valid signature is accepted regardless of which shop identity is asserted alongside it. Just as the analog contract's signature omitted `address(this)` letting a signature be replayed across contracts, here the HMAC omits the shop domain letting a signed body be replayed across shop identities.

### Impact Explanation
An attacker who owns/controls a shop that has the app installed can trigger legitimate webhook deliveries with attacker-chosen resource content (Shopify signs the body with the app's shared client secret, which is the same across all shops using the app). By capturing such a request and resending it to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header, the attacker can make the app process and persist/act on forged data as if it originated from a victim shop — a cross-shop data-integrity / spoofing issue reachable by any unrelated, unprivileged merchant who can install the app.

### Likelihood Explanation
Medium: it requires the attacker to (a) install the app on a shop they control, (b) be able to intercept/replay their own valid webhook HTTP requests (straightforward, since they control network egress from their own test environment or can simply construct requests once they've recorded one valid `(body, hmac)` pair), and (c) target this only affects apps that use the documented custom `WebhookVerification` pattern (or the generator template) and key business logic on the unauthenticated `shop_domain` header.

### Recommendation
Bind the intended shop identity into the verified material rather than trusting the header independently: derive/validate the shop domain from data that is itself covered by the HMAC (e.g., include shop domain in the signed payload) or, at minimum, cross-verify that the `X-Shopify-Shop-Domain` header shop actually installed the app and matches a known, previously stored session id, rejecting mismatches before dispatching jobs — analogous to including the binding context in the signed hash to prevent replay across contexts.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., `carts/update`) causing Shopify to send a POST to the app's webhook endpoint with `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared secret, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(raw_post, hmac_header)`.
4. Attacker (or any actor who can reach the endpoint) resends the same `raw_post` and `hmac_header`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `hmac_valid?(request.raw_post)` succeeds (body/HMAC pair is unchanged and valid), `verify_request` passes, and `shop_domain` in `WebhookVerification` resolves to `victim.myshopify.com`, so the app queues/executes the job as though the (attacker-controlled) payload came from the victim shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end
  end

```markdown
If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```

module Webhooks
  class <%= @controller_class_name %> < ApplicationController
    include ShopifyApp::WebhookVerification

    def receive
      webhook_request = ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
      <%= @job_class_name %>.perform_later(shop_domain: webhook_request.shop, webhook: webhook_request.parsed_body)
      head(:no_content)
    end
  end
end
