### Title
Unvalidated `sender`/`recipient` participant indexes in PedPoP blame handling panic on missing HashMap keys, crashing the process - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame_internal` (and the `AdditionalBlameMachine::blame` / `Decryption::decrypt_with_proof` wrappers around it) indexes `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with participant indexes supplied by the accusing party's message, without checking they were registered DKG participants. A blame request naming an out-of-set `Participant` causes a HashMap-index panic — a remotely triggerable crash (the analog of CVE-2021-35638's remotely caused server DOS).

### Finding Description
`AdditionalBlameMachine::new` only populates `commitments` and `encryption.enc_keys` for participants `1..=n` [1](#0-0) . Later, `blame_internal` performs `self.enc_keys[&decryptor]` inside `decrypt_with_proof` [2](#0-1)  and `self.commitments[&sender]` during share verification [3](#0-2) . `std::collections::HashMap`'s `Index` impl panics on a missing key.

The inputs `sender` (`accused`) and `recipient` (`accuser`) arrive from an untrusted blame message: in `processor/src/key_gen.rs` `VerifyBlame` handling, `accuser`/`accused` are taken straight from the coordinator message and passed to `AdditionalBlameMachine::blame` with no bounds/membership check [4](#0-3) . `Participant::new` only rejects zero, so any value `> n` is "valid" yet absent from both maps.

Note the normal DKG path is safe: `calculate_share` runs `validate_map` before indexing `self.commitments[&l]` [5](#0-4) . Only the blame path skips membership validation.

### Impact Explanation
A single crafted `VerifyBlame` message with `accuser` or `accused` set to any participant index not in `1..=n` (e.g. `n+1`, or a non-participant observer) panics the processor thread evaluating blame. In the deployed binaries, panics in tasks abort the process (see the panic-hook pattern used across serai services), giving an unprivileged party a reliable, repeatable crash — complete denial of service of the key-gen/blame evaluation, matching the CVE's "hang or frequently repeatable crash" impact class.

### Likelihood Explanation
Reachability requires only that a party can submit a blame evaluation request — blame requests are an intended unprivileged message flow (any participant may accuse). No valid share, no threshold cooperation, and no key material is needed; the panic occurs before any cryptographic check on `sender`/`recipient`.

### Recommendation
In `blame_internal` / `decrypt_with_proof`, replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `.get()` and return a defined fault/identity result (e.g. blame the accuser, or a dedicated `NotParticipant` error) when the index isn't registered. Also validate `accuser`/`accused ∈ 1..=n` at the `VerifyBlame` entry point in `processor/src/key_gen.rs`.

### Proof of Concept
```rust
// n = 3 DKG; commitments/enc_keys only contain Participants 1..=3
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();
// attacker-controlled indices: recipient = Participant(4) (never registered)
let bogus_recipient = Participant::new(4).unwrap();
// decrypt_with_proof hits self.enc_keys[&4] -> HashMap Index panic -> process abort
machine.blame(Participant::new(1).unwrap(), bogus_recipient, msg, Some(proof));
```
Equivalently, `sender = Participant::new(4)` reaches `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` after the DLEq check, or earlier via `blame` → `blame_internal` indexing.
