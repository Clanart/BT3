Based on available code, the strongest analog isn't a literal "refund" theft but a structurally similar bug: a **shared pool that unprivileged depositors fund, whose accounting is never decremented after being spent**, letting the value be paid out again and again beyond what was actually deposited/entitled. This lives in the new SIMD-0123 "delegator rewards" feature.

### Title
`pending_delegator_rewards` is never decremented after being distributed, causing block-reward re-distribution/inflation from a single deposit - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`VoteInstruction::DepositDelegatorRewards` lets **any unprivileged signer** transfer lamports into a vote account and increments `VoteStateV4::pending_delegator_rewards` accordingly [1](#0-0) . Every epoch, `calculate_block_reward` derives each delegator's share of `pending_delegator_rewards` proportional to stake and credits it to stake accounts [2](#0-1) , and `build_updated_stake_reward` adds that `block_reward` directly to the stake account's lamports [3](#0-2) . Across the whole codebase, `add_pending_delegator_rewards` is the only mutator of that field — there is no corresponding decrement/consume function anywhere [4](#0-3) , and the vote account's own lamport balance is never debited for the block reward it is supposedly funding.

### Finding Description
The broken invariant: `pending_delegator_rewards` is meant to represent a *finite, one-time* pool deposited by a depositor to be paid out to delegators, similar to how a Sablier "sender" deposit is meant to be earmarked. Instead:

- `deposit_delegator_rewards` is fully permissionless for the `source` role (any signer with lamports can call it) — analogous to Sablier's "anyone can deposit" model [5](#0-4) .
- `calculate_block_reward` reads `pending_delegator_rewards` and computes `stake/total_active_stake * pending_delegator_rewards` **every epoch** with no state showing it was already spent [6](#0-5) .
- The resulting `block_reward` is credited straight into the stake account (`account.checked_add_lamports(partitioned_stake_reward.block_reward)`), but nothing subtracts it from the vote account's real balance, and `distribute_epoch_rewards_in_partition` only adds `stake_reward_lamports_minted` (the *inflation* component) to `capitalization` — the block-reward component is excluded from capitalization tracking [7](#0-6) .
- The `withdraw` instruction explicitly reserves `pending_delegator_rewards` from being pulled out by the withdraw authority, which shows the intent was for this value to represent an as-yet-undistributed, spendable-once pool [8](#0-7) . But because nothing ever decrements it after the reward is paid, the "already spent" state is never recorded.

The net effect: a single deposit of `X` lamports causes stake accounts delegated to that vote account to receive a proportional share of `X` **every subsequent epoch, indefinitely**, without the deposit ever being consumed and without the corresponding lamports being subtracted anywhere or reflected in `capitalization`. This is the same bug class as the Sablier report — a value meant to bound how much can be paid out of a shared, third-party-funded pool is not tracked/decremented against actual disbursement, letting value be extracted repeatedly beyond what was ever deposited.

### Impact Explanation
This causes silent, unbounded lamport creation (protocol-level fund duplication) tied to `capitalization` becoming inconsistent with real total lamports in existence, and stakers of a vote account with even a tiny (e.g., 1 lamport) `DepositDelegatorRewards` call receiving that reward re-materialized every epoch forever. This is a "false execution" / fund-creation bug in the runtime reward-distribution path, not a privileged/gossip/plugin issue, and directly affects consensus-critical state (bank capitalization, stake account balances) computed identically by every validator.

### Likelihood Explanation
The path requires the newer feature flags `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` (SIMD-0123/0185/0232/0291) to all be active [9](#0-8) , so it is gated behind features that may not yet be enabled on mainnet. Given the index-size limits on this search, I was not able to rule out a decrement step existing elsewhere in the reward-distribution pipeline (e.g., a later commit stage not captured by the search); this should be verified against the full source before treating it as confirmed.

### Recommendation
Decrement `pending_delegator_rewards` by the amount actually distributed each epoch (or zero it once fully paid out), and ensure the block-reward lamports credited to stake accounts are either (a) debited from the vote account's real balance, or (b) counted in `capitalization` consistently, so a single deposit cannot be paid out more than once.

### Proof of Concept
1. Enable `block_revenue_sharing`/`custom_commission_collector`/`commission_rate_in_basis_points`; create a `VoteStateV4` vote account with an active stake delegation.
2. Any unprivileged account calls `VoteInstruction::DepositDelegatorRewards { deposit: X }`, transferring `X` lamports into the vote account and setting `pending_delegator_rewards = X` [10](#0-9) .
3. At epoch N, `calculate_block_reward` computes `stake/total_active_stake * X` and credits it to the delegated stake account.
4. At epoch N+1 (and every epoch after), with the same stake still delegated, `pending_delegator_rewards` is still `X` (no decrement exists in `handler.rs`), so the same reward is computed and credited again — repeating indefinitely from the original single deposit. [11](#0-10)

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
