### Title
Unbounded u32 signature count in `SchnorrAggregate::read` enables denial of service via forced mass point deserialization - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the Hubble `processWithdrawals` DoS (a queue-processing routine forced to burn unbounded resources on attacker-chosen input), `SchnorrAggregate::read` lets an untrusted 4-byte length field dictate up to ~4.3 billion iterations of elliptic-curve point deserialization. There is no upper bound, no way to skip the oversized entry, and no early termination other than the reader running dry — so any path that deserializes an attacker-supplied `SchnorrAggregate` can be stalled indefinitely.

### Finding Description
`SchnorrAggregate::read` reads a little-endian `u32` length prefix and then pushes `C::read_G(reader)` that many times into a `Vec`, with no cap on the count:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    #[allow(non_snake_case)]
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }
    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

`C::read_G` is a full point decompression/canonicality check (field inversion/square root plus torsion/identity handling, depending on the curve implementation in `crypto/dalek-ff-group`, `crypto/ed448`, etc.) — a comparatively expensive operation per element. The structure mirrors the Hubble bug exactly:

- **Same shape as `processWithdrawals`**: a single ordered list is processed in one loop; one malicious entry (here, the length field itself) forces the callee to expend more resources than the caller can afford, and the loop cannot be advanced past or trimmed — the only escape is erroring out, which aborts the whole aggregate.
- **No size sanity bound**: compare with the rest of the codebase where length prefixes are capped before use — `Transaction::read` rejects `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` and `SlashReport` caps `len` at `MAX_KEY_SHARES_PER_SET - 1` (coordinator/src/tributary/transaction.rs:286, 431), and `networks/ethereum/src/machine.rs:51-60` explicitly reads claimed data in 1 KB chunks with a comment acknowledging exactly this DoS class. `SchnorrAggregate::read` has no equivalent guard.
- **Memory exhaustion secondary effect**: each successful `read_G` pushes a `C::G` (often 100+ bytes of heap/inline data after decompression for non-dalek curves) into `Rs`. A long stream legitimately containing ~4 billion short encodings also grows `Rs` until OOM; since `verify` later does `Vec::with_capacity(2 * len + 1)` and `multiexp_vartime` over all pairs, a large-but-valid aggregate also forces a quadratic-scale multiexponential workload.

The reachable paths permitted by the scope rules include untrusted bytes fed to `SchnorrSignature::read`-family APIs and `verify` APIs; `SchnorrAggregate` is the aggregate counterpart of `SchnorrSignature` in the same crate and is precisely the type deserialized before aggregate `verify`.

### Impact Explanation
Any consumer that calls `SchnorrAggregate::read` (or `SchnorrAggregate::serialize`-compatible framing) on bytes influenced by an untrusted party can be made to loop up to 4,294,967,295 times through `C::read_G`. Each iteration is a full point deserialization, so even when the underlying byte stream eventually ends, CPU time scales linearly with attacker-chosen length and the in-memory `Rs` vector can exhaust RAM. Like the Hubble withdrawal queue, the failure is not recoverable per-entry: there is no index-based skip or eviction — the single oversized declaration poisons the entire read, and a reader backed by a streaming/network `Read` implementation will block until the declared count is satisfied or the peer stops sending.

### Likelihood Explanation
Reaching the bug requires only that a caller deserialize a `SchnorrAggregate` from attacker-influenced bytes and that the byte stream supply enough data to keep the loop running (or simply block, for a streaming reader). No cryptographic validity, collusion, validator status, or leaked secrets are needed — the attack is a pure resource-exhaustion primitive with cost to the attacker proportional to bytes sent and cost to the victim proportional to a decompression per element, plus unbounded heap growth in `Rs`.

### Recommendation
- Reject any `len` exceeding a protocol-appropriate maximum before iterating (e.g., the maximum number of signatures that can legitimately be aggregated, analogous to the `MAX_KEY_SHARES_PER_SET` check in `Transaction::read`).
- Alternatively, pre-validate that the remaining input is at least `len * size_of::<C::G::Repr>()` bytes (so a huge declared count with a short buffer fails immediately), and/or stream-verify without buffering all `Rs` first.
- Apply the same chunked-read pattern used by `Call::read` in networks/ethereum/src/machine.rs for any length-prefixed untrusted data.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;
// Any in-scope ciphersuite, e.g. dalek-ff-group Ed25519 or ed448
use dalek_ff_group::Ed25519;

fn main() {
    // Attacker-controlled input: declared length = u32::MAX, followed by a
    // repeating stream of canonical encodings (or an infinite/slow network reader).
    let mut buf = Vec::new();
    buf.extend_from_slice(&u32::MAX.to_le_bytes());
    // Append many valid-ish point encodings (e.g., generator repr repeated).
    let gen = <Ed25519 as Ciphersuite>::generator().to_bytes();
    for _ in 0 .. 1_000_000 {
        buf.extend_from_slice(gen.as_ref());
    }

    let start = std::time::Instant::now();
    let mut cursor = Cursor::new(&buf);
    // Runs 4 billion loop bound; only stops when reader yields EOF.
    let _ = SchnorrAggregate::<Ed25519>::read(&mut cursor);
    println!("elapsed: {:?}", start.elapsed());
}
```

With `len = u32::MAX`, each iteration performs a full `Ed25519::read_G` decompression; against a streaming `Read` that never EOFs, the loop (and the victim's verification pipeline) stalls indefinitely, and `Rs` grows without bound — the same permanent-DoS profile as the Hubble `processWithdrawals` queue.
