## Root cause confirmed

`WalletStateManager.interested_coin_cache: dict[bytes32, list[int]]` [1](#0-0)  is populated by `add_interested_coin_ids()` and `add_interested_puzzle_hashes()`, both of which insert unconditionally with **no size cap and no eviction** — every new key just grows the dict forever: [2](#0-1) 

This is reachable from attacker-influenced coin data (not merely local wallet actions): `ClawbackManager.identify()` calls `add_interested_coin_ids([coin_state.coin.name()])` for **every clawback merkle coin sent to the wallet** the moment it's recognized as a recipient — before any spam-amount filtering is applied, unlike the ordinary incoming-coin path which is gated by `xch_spam_amount`/`spam_filter_after_n_txs`: [3](#0-2) 

Clawback coin names are derived from the sender's own coin data (parent id, puzzle hash, amount) via a merkle/clawback puzzle, meaning any counterparty who knows the victim's puzzle hash can spend trivial-amount clawback coins to the victim repeatedly, each producing a distinct `coin_state.coin.name()` — a fresh key inserted into `interested_coin_cache` with no bound, exactly analogous to the Spring Data `PersistentPropertyPathFactory.propertyPaths` pattern: attacker chooses the cache key (indirectly, via coin construction), and the cache never evicts.

### Title
Unbounded `interested_coin_cache` growth via attacker-controlled clawback coins - (File: `chia/wallet/wallet_state_manager.py`)

### Summary
`WalletStateManager.interested_coin_cache` is a plain, unbounded `dict[bytes32, list[int]]` that is populated by `add_interested_coin_ids()`/`add_interested_puzzle_hashes()` with no LRU/TTL/size bound. `ClawbackManager.identify()` inserts a new entry for every clawback coin sent to the wallet as recipient, bypassing the dust/spam filtering (`xch_spam_amount`) applied to ordinary incoming coins. A counterparty who knows the victim's puzzle hash can spend an unbounded number of dust-value clawback coins to it, each creating a new permanent cache entry and growing the victim wallet's memory without bound.

### Finding Description
`interested_coin_cache` (declared at `chia/wallet/wallet_state_manager.py:160-161`) is a class-level dict with no cap, contrasted with other attacker-influenced counters in the same file that *are* explicitly capped (`did_auto_add_limit`, `nft_auto_add_limit` — see the comment at `chia/wallet/nft_wallet/nft_wallet.py:362-370` acknowledging exactly this attack pattern for DID-scoped NFT wallets). `add_interested_coin_ids()` (`wallet_state_manager.py:2145-2158`) unconditionally does `self.interested_coin_cache[coin_id] = list(set(wallet_ids))` for any new `coin_id`, with no eviction logic anywhere in the class.

`ClawbackManager.identify()` (`chia/wallet/clawback_manager.py:85-92`) calls this unconditionally the first time a clawback merkle coin state is seen where the wallet is the recipient — this is driven by coin states arriving from chain (i.e., from any coin actually created by a spend bundle), not gated by dust filtering. Ordinary standard-puzzle incoming coins are filtered by `xch_spam_amount`/`spam_filter_after_n_txs`, but clawback coin identification has no equivalent guard before the cache insert.

### Impact Explanation
An attacker who knows a victim's receive puzzle hash (a normal, expected precondition for sending them any coin) can create spend bundles that send an arbitrary number of tiny-value clawback coins to that puzzle hash. Each distinct coin (attacker fully controls parent coin id / amount / timing, hence the resulting `coin.name()`) causes a permanent, unbounded insertion into `interested_coin_cache` in the victim wallet process. Over time this can exhaust wallet memory, causing the wallet daemon to OOM or become unresponsive — a spend-bundle/coin-triggered denial-of-service against the recipient's wallet node (CWE-400, matching the analog report's classification).

### Likelihood Explanation
Moderate-high. The attacker needs no special privilege — only the victim's puzzle hash (already required to send any coin) and mempool fees to submit spend bundles creating dust clawback coins. There is no per-sender/per-coin rate limit or size cap on `interested_coin_cache`, and clawback coin recognition is not subject to the `xch_spam_amount` dust filter that protects the normal incoming-coin path.

### Recommendation
Bound `interested_coin_cache` (e.g., wrap it in the repo's existing `LRUCache`/`LRUKeyedListCache` utility, matching how `PeerRequestCache`, `future_eos_cache`, etc. are already hardened) or apply the same `xch_spam_amount`-style dust/count threshold to clawback-coin recognition in `ClawbackManager.identify()` before calling `add_interested_coin_ids`. Persisting the coin id list is already handled via `WalletInterestedStore`; the in-memory cache should be treated purely as an LRU accelerator, not an unbounded ledger of every externally-triggered coin id ever seen.

### Proof of Concept
1. Victim wallet publishes/derives a puzzle hash `PH`.
2. Attacker (no shared key with victim) repeatedly constructs standard spend bundles that create new clawback merkle coins with `recipient_puzzle_hash = PH` and dust `amount` (e.g., 1 mojo), each from a fresh parent coin so every resulting `coin.name()` is unique, and submits them to the mempool/chain.
3. As the victim's wallet syncs each new clawback coin, `ClawbackManager.identify()` recognizes the wallet as recipient and calls `add_interested_coin_ids([coin_state.coin.name()])`, inserting a new permanent entry into `WalletStateManager.interested_coin_cache`.
4. Repeating this at scale (bounded only by attacker's fee budget for creating dust coins) grows `interested_coin_cache` without bound in the victim's wallet process, exhausting memory over time.

**Confidence note:** I could not fully trace whether any block-height/coin-creation-rate limits elsewhere in the sync pipeline (e.g., subscription limits or `max_coin_state_update_items`) throttle the *rate* at which new clawback coin states reach `ClawbackManager.identify()` per sync batch; this would affect only the speed of the attack, not its unbounded nature, but I was not able to verify this with full certainty given tool-call limits.
