### Title
`ThresholdKeys` deserialization never checks the secret share is consistent with the verification shares — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to the JOJO finding (a documented "these two values must match" invariant that is never enforced), `ThresholdKeys::new` / `ThresholdKeys::read` enforce structural checks — the number of verification shares equals `n`, participant indexes are in range, `t <= n`, and `Interpolation::Constant` implies `t == n` — but never verify that the deserialized `secret_share` actually corresponds to `verification_shares[i]` (i.e., `generator * secret_share == verification_shares[params.i()]`). The codebase itself acknowledges this gap: `AlgorithmSignatureMachine::complete` comments that "the only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" [1](#0-0) .

### Finding Description
`ThresholdKeys::new` checks the verification-share count and participant range, then derives `group_key` by interpolating `verification_shares[1..=t]` [2](#0-1) . `secret_share` is stored verbatim with no consistency check against `verification_shares[params.i()]` [3](#0-2) . `ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation variant, `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new`, inheriting the same omission [4](#0-3) . Because `group_key` is computed only from participants `1..=t`, a crafted blob can claim an arbitrary group key while arming participant `i` with an unrelated secret share.

### Impact Explanation
A `ThresholdKeys` deserialized from attacker-influenced bytes (or produced by a faulty/corrupt pipeline) lets the holder run the full FROST `sign` path: `view()` interpolates the bogus share [5](#0-4) , the participant emits a `SignatureShare` that fails `verify_share`, and `complete` blames that participant via `FrostError::InvalidShare` [6](#0-5) . In a validator set this produces a false-positive "faulty participant" attribution against the victim (ejection/slashing risk and aborted signing sessions) rather than a clean key-load failure. Additionally, `recover_key` only fails late, at the `generator * res == group_key` check, after summing inconsistent views [7](#0-6) .

### Likelihood Explanation
The secret share and the verification-share map are transported as one serialized blob, so any party able to influence stored/loaded key material can induce the inconsistency; no threshold cooperation is needed. The failure is deterministic once such bytes are read — every signing attempt produces an invalid share attributable to the victim. Exploitation requires reaching a `ThresholdKeys::read` path rather than pure network messages, so Medium is appropriate rather than High.

### Recommendation
In `ThresholdKeys::new` (or in `ThresholdKeys::read` immediately after construction), check `C::generator() * secret_share == verification_shares[&params.i()]` and reject with a new `DkgError` variant when it does not hold. This turns semantically invalid key material into an immediate, correctly-attributed deserialization error instead of a downstream `InvalidShare` blame event.

### Proof of Concept
1. Craft a serialized `ThresholdKeys` blob: valid `C::ID`, `t`, `n`, `i`, `Interpolation::Lagrange`, a random `secret_share`, and `n` random (or honestly generated but mismatched) verification-share points.
2. `ThresholdKeys::<C>::read` succeeds because only count/range checks exist [8](#0-7) .
3. Build an `AlgorithmMachine`/`AlgorithmSignMachine` with these keys, complete `sign`, and broadcast the share.
4. `SignatureMachine::complete` fails full-signature verification, then per-share verification blames participant `i` (the victim) with `FrostError::InvalidShare`, or hits the `InternalError("everyone had a valid share yet the signature was still invalid")` path acknowledged in the comment [9](#0-8) .
5. `recover_key` on such keys returns `RecoveryError::Failure` only after interpolation, confirming the keys were semantically invalid yet accepted [10](#0-9) .
