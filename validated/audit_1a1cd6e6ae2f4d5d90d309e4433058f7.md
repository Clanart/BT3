### Title
`shop_login` builds login redirect from unvalidated raw `params[:shop]`/`params[:host]` instead of the sanitized shop domain - ([File: app/controllers/concerns/shopify_app/shop_access_scopes_verification.rb])

### Summary
`scopes_mismatch?` correctly gates on the sanitized shop domain via `current_shopify_domain` (which calls `ShopifyApp::Utils.sanitize_shop_domain`), but the subsequent `shop_login` redirect uses the raw, unsanitized `params[:shop]` and `params[:host]` directly. This creates a mismatch where the scope check is bound to a verified/canonical shop while the resulting redirect target is attacker-controlled.

### Finding Description
In `login_on_scope_changes`, when `scopes_mismatch?` is true and `embedded_param?` is false, the code calls `redirect_to(shop_login)`. `shop_login` is defined as: [1](#0-0) 
which passes `params[:shop]` and `params[:host]` verbatim (not the sanitized value returned by `current_shopify_domain`) into `ShopifyApp::Utils.shop_login_url`. That helper only special-cases a blank `shop` (falling back to the configured login URL); otherwise it URL-encodes and embeds whatever string was supplied without validating it is a real/trusted myshopify domain: [2](#0-1) 

Meanwhile the actual scope-mismatch decision is based on `current_shopify_domain`, which does run the input through `sanitize_shop_domain` and its trusted-domain/punycode/case-normalization logic: [3](#0-2) [4](#0-3) 

So the check that triggers the redirect is bound to a validated shop, but the redirect target itself is not re-derived from that same sanitized value — it echoes back the raw `params[:shop]`/`params[:host]` that the attacker supplied in the GET request. Since `shop_login_url` builds an absolute URL from `ShopifyApp.configuration.login_url` with query params for `shop`/`host`/`return_to`, and doesn't validate that `shop` is a legitimate `*.myshopify.com` domain, an attacker can supply a value in `params[:shop]` that differs from what actually satisfies `sanitize_shop_domain` (e.g., a value that normalizes to a trusted domain for the scope check via case-folding/whitespace, but is echoed raw into the redirect) or simply supply an arbitrary string, and have that value appended into the login redirect URL that the browser is redirected to. Because `login_url` is app-configured and the params are merely appended as a query string (not used to build the host of a redirect target), the exploitable surface here is limited to open-redirect-adjacent parameter smuggling into `return_to`/`shop`/`host` on the app's own login endpoint, not redirecting to an arbitrary third-party host — the redirect always lands on `ShopifyApp.configuration.login_url`, which is same-app/first-party.

I could not verify (index limits / not reached) how `ShopifyApp.configuration.login_url`'s controller consumes `shop`/`host`/`return_to` downstream (e.g., whether the login controller re-sanitizes `shop` before using it to construct an OAuth authorize URL). That downstream consumer is the actual location where an unsanitized `shop`/`host` value could translate into a genuine open redirect or cross-shop token issuance; without seeing that controller I cannot confirm a full end-to-end exploit chain from this file alone.

### Impact Explanation
As isolated to this file, the impact is limited to parameter inconsistency between the scope-mismatch check (sanitized) and the login redirect (raw) — this alone does not demonstrate a complete open-redirect or cross-shop reauthorization primitive, because the redirect host itself (`ShopifyApp.configuration.login_url`) is fixed and app-controlled, not attacker-controlled. Confirming the claimed "open redirect / cross-shop reauthorization" impact requires tracing how the login route consumes the unsanitized `shop`/`host`/`return_to` params, which is outside this file's scope.

### Likelihood Explanation
Reaching `login_on_scope_changes` only requires an unprivileged GET request with a `shop` param that triggers `update_access_scopes?` to return true, which is plausible for any embedding attempt with mismatched scopes. However, without confirmation of unsafe consumption of `shop`/`host` downstream, likelihood of a concretely exploitable open redirect from this code path alone is not established.

### Recommendation
Use the sanitized shop domain (`current_shopify_domain`) rather than raw `params[:shop]` when constructing `shop_login`'s URL, and validate/allowlist `params[:host]` (e.g., base64-decode and check it decodes to a trusted `*.myshopify.com` admin host) before embedding it in any redirect.

### Proof of Concept
Not fully reproducible from this file in isolation — a complete PoC requires the login-route controller behind `ShopifyApp.configuration.login_url` to confirm whether it treats the `shop`/`host` query params as trusted without re-sanitizing, which could not be verified within available context.

```ruby
      def sanitize_shop_domain(shop_domain)
        uri = uri_from_shop_domain(shop_domain)
        return if uri.nil? || uri.host.nil?

        trusted_domains.each do |trusted_domain|
          no_shop_name_in_subdomain = uri.host == trusted_domain
          from_trusted_domain = trusted_domain == uri.domain

          return myshopify_domain_from_unified_admin(uri) if unified_admin?(uri) && from_trusted_domain
          return nil if no_shop_name_in_subdomain || uri.host&.empty?
          return uri.host if from_trusted_domain
        end
        nil
      end
```

```ruby
        return ShopifyApp.configuration.login_url unless shop

          shop: shop,
          host: host,
```
