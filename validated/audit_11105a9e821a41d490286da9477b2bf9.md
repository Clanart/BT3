### Title
Unbounded `order.inputs`/`order.output.assets` array lets an order creator permanently gas-lock escrow release in `IntentGatewayV2` / `IntentsBase` - ([File: evm/src/apps/IntentGatewayV2.sol], [File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`placeOrder()` only rejects an empty `inputs` array (`order.inputs.length == 0`); it never caps the number of input or output tokens an order can carry. [1](#0-0) 
`fillOrder()` only requires `order.inputs.length == order.output.assets.length == options.outputs.length` — a symmetry check, not a size bound. [2](#0-1) 
Escrow release (`_withdraw`/`withdraw`) then loops once per token doing an external transfer call per iteration, exactly the unbounded `for` pattern flagged in the Frax report (`removeValidator`/`removeMinter`), except here the corrupted value gates release of real escrowed funds rather than a registry entry. [3](#0-2) [4](#0-3) 

### Finding Description
An order creator fully controls `order.inputs` and `order.output.assets` at `placeOrder()` time, with no maximum length enforced anywhere in the validated fields. [5](#0-4) 
A cross-chain fill dispatches a `WithdrawalRequest` back to the source chain whose `tokens` field is `order.inputs` verbatim (the same pattern used for cancellation, seen at `_cancelFromSource`): [6](#0-5) 

On the source chain, the incoming `RedeemEscrow`/`RefundEscrow` message is routed to `withdraw()`/`_withdraw()`, which iterates over the *entire* `tokens` array and performs a real external call (native transfer or `safeTransfer`) per entry before the escrow can be considered released: [7](#0-6) [8](#0-7) 

Because the number of iterations equals the attacker-chosen `order.inputs.length`, an order can be crafted with hundreds of tiny/duplicate input tokens. When the module callback (`onAccept`) is invoked from the ISMP request-handling path, its gas cost scales linearly with that array; once it exceeds what fits in a single block's gas limit, the callback can never complete successfully, no matter how much gas the relayer supplies (the ceiling is the block gas limit, not caller-supplied gas). This is the exact broken invariant from the Frax report — an attacker-sized array turning a critical state-mutating loop into a call that can never fit in an executable transaction.

### Impact Explanation
Unlike the Frax case (an admin-called validator/minter registry that simply becomes hard to prune), this loop sits directly on the fund-release path for cross-chain intent settlement:
- A solver who legitimately fills the destination side of the order (handing over their own assets to `order.output.beneficiary`) can never redeem the source-chain escrow if the paired `RedeemEscrow` callback perpetually exceeds the block gas limit — a direct loss of the solver's already-delivered assets with no compensating escrow release.
- Symmetrically, a user who wants their own oversized order cancelled/refunded (`RefundEscrow`) can permanently strand their own escrow, but more importantly this same array-inflation primitive is reachable by *any* unprivileged order creator against *any* solver who chooses to fill their order — the victim is not the attacker.
- This qualifies as "loss of funds" / "unauthorized transaction or execution" under the bounty gate: it is a public-entrypoint (`placeOrder`/`fillOrder`), no malicious relayer, prover, or admin required — only a specially crafted `Order`.

### Likelihood Explanation
Likelihood is moderate-to-high: constructing an order with many low-value input/output tokens is a normal user action requiring no special privilege, just enough tokens (or duplicate token approvals with zero-checked but non-zero amounts) to populate a large array; `placeOrder` performs standard ERC-20 transfers per input so the attacker pays gas at creation time but that cost is amortized once, while the redemption-side gas cost is paid by whichever solver/relayer attempts settlement, on a chain whose block gas limit is fixed and cannot be worked around by supplying more gas.

### Recommendation
- Enforce a `MAX_INPUTS`/`MAX_OUTPUTS` cap in `placeOrder()` (and mirror it in `fillOrder()`'s array-length check) sized to a gas budget that provably fits well under the target chain's block gas limit, analogous to the bandwidth pallet's `MAX_SUBSCRIPTIONS` bound already used elsewhere in this codebase.
- Alternatively/additionally, make `_withdraw`/`withdraw` resilient to partial failure (e.g., process a bounded slice per call and allow repeated calls to drain the remainder) rather than requiring the full array to succeed atomically in one callback.

### Proof of Concept
1. Attacker calls `placeOrder` with an `Order` whose `inputs` and `output.assets` each contain N (e.g., 300+) distinct low-value ERC-20 tokens, satisfying only the `inputs.length != 0` check. [5](#0-4) 
2. A solver, attracted by the order's advertised output, calls `fillOrder` on the destination chain; the array-length symmetry check passes since inputs and outputs match in length. [9](#0-8) 
3. The fill dispatches a `RedeemEscrow` `WithdrawalRequest` back to the source chain carrying the full N-length `tokens` array (same construction pattern as `_cancelFromSource`). [6](#0-5) 
4. When the message is delivered, `onAccept`/`withdraw()` on the source chain must loop N times doing external token transfers; for large enough N this exceeds the block gas limit and the callback can never succeed. [3](#0-2) 
- Note: I was not able to fully trace the exact revert/retry semantics of the EVM host's `onAccept` dispatch (whether a failed module callback reverts the whole relayer transaction or is caught and marked retriable) within the available indexed content of `evm/src/core/EvmHost.sol`; a Devin session with full repo access should confirm this control-flow detail to finalize the exact failure mode (permanent revert vs. infinite retry) before filing.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                IERC20(token).safeTransfer(beneficiary, amount);

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
