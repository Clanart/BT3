Path-containment check `_resolveWithin` uses a bare string-prefix comparison, allowing symlink/traversal escape into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
The report's underlying pattern is: a safety invariant is checked using an inequality/containment test that is not tight enough at the boundary, so a value that should fail the check slips through and is used downstream as if it were validated. In GitHub Desktop, `_resolveWithin` (the central helper used to guarantee that a file path stays inside a repository root before it is read, opened, or exposed) implements its containment check with `realResolved.startsWith(realRoot)` and returns the pre-verification `resolved` path if that string comparison passes. [1](#0-0) 

### Finding Description
`resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` are documented as guaranteeing that "the resolved path is guaranteed to reside at, or underneath" the given root path. The implementation: [2](#0-1) 

computes `realRoot = realpath(normalizedRoot)` and `realResolved = realpath(resolved)` (this correctly follows symlinks for the *check*), but the containment test is a raw string `startsWith`, with no path-separator boundary. `"/Users/victim/Documents/GitHub/repo-secrets".startsWith("/Users/victim/Documents/GitHub/repo")` is `true`, even though `repo-secrets` is a sibling directory, not a subdirectory, of `repo`. This is exactly the class of bug in the report: the check is performed against a boundary condition (`<`, `startsWith`) that doesn't account for the exact edge where the invariant actually needs to hold (a directory separator, or `p_spot < 1` with the fee term included).

Contrast this with `isClonePathSensitive` in `app/src/lib/git/clone.ts`, which does the containment check correctly by explicitly appending the separator: `clonePath.startsWith(sensitive + Path.sep)`. `_resolveWithin` lacks this `+ Path.sep` (or equality) guard, so its "invariant" (`resolved path is at or underneath root`) is not actually enforced at the boundary.

The existing unit tests in `app/test/unit/path-test.ts` only exercise same-directory traversal and symlink-to-parent cases; they never test a sibling directory whose name is a superstring of the root directory's basename, so this gap is untested and unnoticed. [3](#0-2) 

`resolveWithin` is relied upon as the authoritative safety gate in at least two real, attacker-reachable code paths:

1. `openRepositoryFromUrl` in the dispatcher, which handles a deep-link (`x-github-client://openRepo?filepath=...`) that a malicious web page/link can trigger, uses `resolveWithin(repository.path, filepath)` before calling `shell.showItemInFolder(resolved)`. [4](#0-3) 

2. `buildConflictContext` in `copilot-conflict-context.ts`, which resolves conflicted file paths coming from a fetched/merged repository (attacker-controlled content, since conflict file paths and on-disk symlinks are derived from a repo the user cloned/fetched/merged), and then reads the file's contents to send to Copilot for AI-assisted conflict resolution. [5](#0-4) 

### Impact Explanation
If a victim has (or later creates) a sibling directory whose name is a superstring of the repository directory's basename (a very common real-world layout, e.g. `~/Documents/GitHub/project` and `~/Documents/GitHub/project-secrets`, `repo` and `repo2`, `app` and `app-legacy`), an attacker who controls the contents of a cloned/fetched/merged repository (e.g. via a crafted `.gitattributes`-driven merge, a symlink checked into a branch that participates in a merge conflict, or a crafted deep-link `filepath` parameter) can make `_resolveWithin` treat a path in that sibling directory as "inside the repo":
- Via the deep-link path (`openRepositoryFromUrl`), this can be used to make Desktop reveal/open an arbitrary file outside the repo in the file manager (information disclosure of file existence/location, and depending on OS file-manager behavior, further exposure).
- Via `buildConflictContext`, this can cause file contents from outside the repository (e.g. from a sibling directory containing credentials, notes, or other unrelated project files) to be read and sent to the Copilot backend as "conflict content" — an unprivileged, attacker-crafted merge conflict causing exfiltration of file content outside the intended repo directory to a third-party (Copilot) service.

This matches the required impact bar: attacker controls a cloned/fetched/merged repository or a link the user interacts with, and the result is file read outside the repo / exfiltration of file content, with no local/physical access, no admin rights, and no pre-existing malware needed.

### Likelihood Explanation
Exploitation requires two things to align: (1) the victim's filesystem happens to have (or the attacker can cause to exist, e.g. via a previous clone naming pattern) a sibling directory whose name is a prefix-extension of the repository's own directory name, and (2) the attacker can get a symlink or crafted relative path checked out/merged into the repository that, once resolved, lands in that sibling directory. Both conditions are plausible but not guaranteed for every victim — this raises the bar from "always exploitable" to "environment-dependent." Still, it is squarely in scope as a broken invariant with no additional privileges or user missteps required beyond normal usage (opening a deep link, or Desktop auto-invoking AI conflict resolution over merge conflicts from a fetched branch).

### Recommendation
Fix the boundary check in `_resolveWithin` to require an exact match or a path-separator-bounded prefix, mirroring the correct pattern already used in `isClonePathSensitive`:

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the appropriate `options.sep`/join module for the POSIX/Win32 variants). Add a regression test asserting that a sibling directory whose name extends the root's basename (e.g. root `/tmp/foo`, target `/tmp/foobar/secret.txt`) is correctly rejected by `resolveWithin`.

### Proof of Concept
1. Suppose the victim has cloned two repositories side by side: `~/Documents/GitHub/app` (the target, non-sensitive-looking repo) and `~/Documents/GitHub/app-secrets` (containing sensitive notes/tokens, unrelated to `app`).
2. Attacker crafts a branch that, when merged into `app`, produces a merge conflict on a file whose repository-relative path is a relative traversal that `Path.resolve` normalizes to point at `../app-secrets/token.txt` relative to `app`'s working directory — or, more robustly, checks in a symlink `evil -> ../app-secrets/token.txt` and causes a merge conflict involving `evil`.
3. Victim, using GitHub Desktop, fetches/merges the attacker's branch, hits a conflict, and Desktop's Copilot conflict-resolution flow calls `buildConflictContext`, which calls `resolveWithin(workingDirectory /* .../app */, 'evil')`.
4. `realpath` resolves `evil` to `/Users/victim/Documents/GitHub/app-secrets/token.txt`; `realRoot` is `/Users/victim/Documents/GitHub/app`. The check `realResolved.startsWith(realRoot)` returns `true` (string prefix match) even though the file is in a sibling directory, so `resolveWithin` returns the path as valid.
5. `buildConflictContext` proceeds to `stat`/`readFile` the file outside the intended repo and includes its contents in the payload sent to the Copilot conflict-resolution context, exfiltrating data from outside the repository the user believed was in scope.

(Note: I could not execute this against a live build to confirm end-to-end behavior of the Copilot pipeline beyond the code shown, since I only have read access to the indexed source; the vulnerable boundary check itself, however, is directly verifiable from `app/src/lib/path.ts` lines 64-71 and is not covered by the existing `path-test.ts` suite.)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
