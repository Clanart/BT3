## Title
Unauthenticated OP_RETURN operator attribution in `payout_tx` lets any funder frame an arbitrary operator as the fronting party - ([File: core/src/builder/transaction/operator_reimburse.rs])

## Summary
`create_payout_txhandler` builds the payout transaction with the user's withdrawal UTXO signed under `SinglePlusAnyoneCanPay` (SIGHASH_SINGLE|ANYONECANPAY), covering only input 0 and output 0 (the user's payout output). The OP_RETURN output that records which operator "fronted" the withdrawal (`operator_xonly_pk`) sits at output index 2 and is completely outside the signed message. Any party able to complete and broadcast the transaction (add funding inputs under ANYONECANPAY, sign them with their own key) can therefore write an arbitrary xonly public key into that OP_RETURN, i.e., attribute the payout to any operator regardless of who actually supplied the BTC.

## Finding Description
`create_payout_txhandler` at `core/src/builder/transaction/operator_reimburse.rs:407-436` constructs:
- input 0: the withdrawal UTXO, signed by the user with `SinglePlusAnyoneCanPay`
- output 0: user payout output (covered by SIGHASH_SINGLE)
- output 1: anchor
- output 2: OP_RETURN containing `operator_xonly_pk.serialize()` [1](#0-0) 

`calculate_pubkey_spend_sighash`/`calculate_script_spend_sighash` in `core/src/builder/transaction/txhandler.rs` show that for `SinglePlusAnyoneCanPay`, `Prevouts::One(txin_index, ...)` is used and the sighash only commits to the single input and the output at the same index — outputs 1 and 2 are never bound by the user's signature. [2](#0-1) 

The operator's own `withdraw()` flow only inserts its *own* `self.signer.xonly_public_key` into that OP_RETURN when it fronts a withdrawal via `fund_raw_transaction`, and the transaction is then broadcast via RBF. [3](#0-2) 

However, on the verification/attribution side, `update_finalized_payouts` in `core/src/verifier.rs` extracts `operator_xonly_pk` purely from the OP_RETURN of whatever payout transaction actually lands on-chain and confirms — with **no check that the funding inputs of that transaction were actually contributed/signed by that operator**: [4](#0-3) 

This attribution is later relied upon in `is_kickoff_malicious`, which only compares the OP_RETURN-derived `operator_xonly_pk` against the kickoff sender's own key and the committed blockhash — it never verifies that the credited operator actually paid the withdrawal: [5](#0-4) 

and in `validate_payer_is_operator`, which simply trusts the DB-recorded `payer_xonly_pk` (populated straight from the OP_RETURN data) to decide whether "this operator" is entitled to pursue reimbursement for a given deposit: [6](#0-5) 

**Binding broken:** the protocol needs `operator credited (OP_RETURN pubkey) == party that actually paid (funder/signer of the completing inputs)`. Because the OP_RETURN output is outside the SIGHASH_SINGLE|ANYONECANPAY commitment and no additional signature or input-ownership check ties it to the actual funder, any party that can complete the withdrawal transaction (funding it with their own BTC, since ANYONECANPAY lets anyone add inputs/outputs beyond index 0) can insert a victim operator's xonly public key into that OP_RETURN. The system will then treat that arbitrary operator as the party owed reimbursement, purely from unauthenticated on-chain data.

## Impact Explanation
This is the same bug class as the DeXe report's core lesson: a value-moving action is not gated by matching who actually supplied the value to who is credited/rewarded for it. Here, once the forged payout confirms:
- The DB (`withdrawals.payout_payer_operator_xonly_pk`, `is_payout_handled` via `mark_payout_handled`/`update_payout_txs_and_payer_operator_xonly_pk`) marks a chosen operator as the payer for that deposit even though that operator contributed zero BTC.
- The framed/benefiting operator's own reimbursement logic (`get_reimbursement_txs`/`get_next_txs_to_send`, gated by `validate_payer_is_operator`) is driven entirely by this DB state, not by the operator's own memory of having funded a payout, so it can proceed to kick off and eventually reimburse from the round-tx collateral for a payout it never fronted.
- Simultaneously, the genuine withdrawal UTXO is now spent by the attacker's transaction, permanently preventing the intended operator (or the correct payer) from ever fronting or being properly credited for that withdrawal.

This matches the specified Critical impact: "an operator reimbursed for a payout it never funded."

## Likelihood Explanation
The likelihood depends on how the attacker obtains the user's `SinglePlusAnyoneCanPay` withdrawal signature, which is stated to be "given to operators off-chain." If that signature/parameters transit through any unauthenticated aggregator/operator RPC path (e.g., `Withdraw`/`OptimisticPayout` request plumbing) reachable by unprivileged callers, or if the withdrawal signature becomes visible once any operator attempts to fund it (mempool visibility of a rebroadcastable ANYONECANPAY input), an attacker can splice in a replacement transaction crediting a different operator before the legitimate payout confirms. I was not able to fully trace, within the available index, whether the withdrawal signature/parameters are exposed to fully unauthenticated callers or are strictly limited to actor-to-actor gRPC channels; this materially affects whether this is exploitable by a totally unprivileged network attacker versus one with at least some access to the withdrawal parameters (e.g., mempool visibility of a first, legitimate payout attempt broadcasting the ANYONECANPAY-signed input, followed by a replacement transaction with a different OP_RETURN and additional funder inputs).

## Recommendation
Bind the OP_RETURN operator attribution to the same commitment that authorizes fund movement:
- Have the credited operator co-sign a commitment (or have the aggregator/verifiers check) that the OP_RETURN `operator_xonly_pk` matches an operator who actually authorized/contributed the completing inputs of the payout transaction, e.g., by requiring the operator to sign over the whole transaction (including OP_RETURN) rather than only relying on `SinglePlusAnyoneCanPay` from the user, or by having verifiers independently validate that the additional funding inputs in the confirmed payout tx are provably controlled by the OP_RETURN-named operator (e.g., checking that the extra inputs' scriptPubkeys/spend paths resolve to that operator's known wallet/collateral key) before recording `payout_payer_operator_xonly_pk`.
- As defense in depth, require the withdrawal's `SinglePlusAnyoneCanPay` signature/parameters to be scoped and single-use (bound to a specific operator/session) so it cannot be reused/rebroadcast by a third party with a substituted OP_RETURN.

## Proof of Concept
Conceptual (Bitcoin-transaction-level) PoC, mirroring the report's "simultaneously funded via two paths → misattribution" pattern:
1. Obtain (via any leaked/observed channel) the user's withdrawal `input_signature` for outpoint `in_outpoint` with `SinglePlusAnyoneCanPay`, `output_script_pubkey`, `output_amount` (as consumed by `parse_withdrawal_sig_params` in `core/src/rpc/parser/operator.rs:161-203`).
2. Build a transaction with:
   - input 0 = `in_outpoint` with the intercepted signature/witness
   - additional inputs funded and signed by the attacker's own wallet to cover `output_amount`
   - output 0 = the user's payout output (must match exactly what the signature commits to)
   - output 1 = anchor
   - output 2 = OP_RETURN containing an arbitrary victim operator's `xonly_pk` (per `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`)
3. Broadcast before the legitimate operator's own payout transaction confirms.
4. Once confirmed, `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) records the victim operator's xonly key as `payer_xonly_pk` for that withdrawal, purely from the OP_RETURN, with no verification that the victim operator supplied any of the funding inputs.
5. The victim operator's automation (`get_reimbursement_txs` → `validate_payer_is_operator`, `core/src/operator.rs:1686-1729, 2087-2150`) subsequently treats itself as the legitimate payer and pursues kickoff/reimbursement from round collateral for a payout it never funded.

I could not execute this end-to-end in the current environment (no test harness run), so this PoC is derived directly from reading the transaction-construction and payout-attribution code paths cited above rather than an executed exploit.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
