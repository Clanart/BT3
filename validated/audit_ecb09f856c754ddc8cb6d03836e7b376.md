### Title
Aggregate Schnorr signatures can be forged by cancelling a victim signature with a controlled key - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives aggregation weights only from the supplied per-signature challenges. It does not bind each weight to the corresponding public key or nonce. An attacker who controls at least one public key in the verified batch can choose its nonce and the aggregate scalar so a statement involving an honest victim’s key cancels, producing an aggregate accepted without any valid signature for the victim’s message. [1](#0-0) 

### Finding Description
The verifier computes `z_i` solely from the transcript of challenges at `crypto/schnorr/src/aggregate.rs:132-140`. [2](#0-1)  It then verifies `sum_i(z_i * R_i + z_i * c_i * A_i) - s * G == identity`. [3](#0-2) 

Because `R_i`, `s`, and at least one controlled key pair `(x_a, A_a = x_a G)` can be attacker-selected, the attacker can include a victim statement `(A_v, c_v, R_v)` and cancel it through the controlled component. The aggregation weights are predictable before submission because they depend only on the ordered challenges, not on the nonce or public key being weighted. [4](#0-3) 

The individual Schnorr verifier uses the correct per-signature relation `R + cA - sG = 0`; this issue is specific to the aggregate verifier’s insufficiently bound coefficients and freely supplied aggregate `s`. [5](#0-4) 

### Impact Explanation
Any caller that accepts `SchnorrAggregate` for signatures over attacker-influenced messages or public keys may accept a forged aggregate containing a victim public key/challenge that never signed the associated message. The result is an accepted aggregate signature even though the victim component was not individually valid. [1](#0-0) 

### Likelihood Explanation
The attacker needs one controlled key in the same aggregate and must know the victim key, victim challenge, victim nonce point, and ordering used to derive weights. Those are public verification inputs in normal aggregate-signature operation. No discrete logarithm, secret key, malformed encoding, validator compromise, or protocol misbehavior beyond submitting the forged aggregate is required. [6](#0-5) 

### Recommendation
Derive each aggregation weight from the complete statement being weighted, including the signature index, public key, nonce point, and challenge/message binding, rather than only the challenge stream. Alternatively, verify each `(R_i, s_i)` signature independently or use an aggregation protocol whose coefficients commit to all aggregate components. [7](#0-6) 

### Proof of Concept
Let the aggregate contain two entries:

- Victim: public key `A_v`, challenge `c_v`, supplied nonce `R_v`.
- Attacker: private scalar `x_a`, public key `A_a = x_a G`, challenge `c_a`.

Let `z_v` and `z_a` be the weights generated by `verify`. The attacker chooses fresh scalar `r_a` and sets:

```text
R_a = -(z_v / z_a) * (R_v + c_v * A_v) + r_a * G
s   = z_a * (r_a + c_a * x_a)
```

The verifier then computes:

```text
z_v R_v + z_v c_v A_v + z_a R_a + z_a c_a A_a - sG

= z_v(R_v + c_v A_v)
  - z_v(R_v + c_v A_v)
  + z_a r_a G
  + z_a c_a x_a G
  - z_a(r_a + c_a x_a)G

= identity
```

Therefore `multiexp_vartime(&pairs).is_identity()` returns true even though the victim component does not represent a valid Schnorr signature under `A_v`. [3](#0-2)

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }

  /// Return the series of pairs whose products sum to zero for a valid signature.
  /// This is intended to be used with a multiexp.
  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }
