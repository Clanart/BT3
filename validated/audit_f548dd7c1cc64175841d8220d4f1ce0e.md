Based on my investigation, I found the `_cancelSameChain` function in `IntrinsicIntents.sol` has a genuine bookkeeping omission analogous to the `CreateValidator`/`Delegate` pattern: a specific-purpose function skips accounting that the general-purpose function performs.

### Title
`_cancelSameChain` omits `TRANSACTION_FEES` bookkeeping present in `_withdraw`, but relies on `_withdraw` unconditionally sweeping it — full-fill/cancel race causes double payout or fee loss - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol], [File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_cancelSameChain` (evm/src/apps/intentsv2/IntrinsicIntents.sol:161-187) collects only the remaining `order.inputs` escrow balances and calls `_withdraw(body, true, true)`, without itself checking or reasoning about `_orders[commitment][TRANSACTION_FEES]`. The `order.fees` bookkeeping is entirely delegated to `_withdraw` in `IntentsBase.sol:391-425`, which unconditionally sweeps and zeroes `TRANSACTION_FEES` whenever `finalize == true`.

### Finding Description
`_withdraw`'s fee-sweep block runs whenever `finalize` is true, independent of whether the caller was a real full-fill (`fillOrder`) or a same-chain cancellation (`_cancelSameChain`) [1](#0-0) . Both `fillOrder`'s full-fill path and `_cancelSameChain` invoke `_withdraw` with `finalize = true` [2](#0-1) [3](#0-2) . `_cancelSameChain` computes `remainingTokens` strictly from live `_orders[commitment][token]` input balances and never touches or checks `TRANSACTION_FEES`, unlike `placeOrder`, which is the only place that writes `_orders[commitment][TRANSACTION_FEES] = order.fees` [4](#0-3) .

Because a partial fill can happen (`isFullyFilled = false` path in `IntrinsicIntents.sol` at fillOrder, which deletes `_filled[commitment]` and does *not* finalize, leaving the order fillable/cancellable again) [5](#0-4) , and the order's `TRANSACTION_FEES` entry is left untouched after a partial (non-finalizing) fill, the order's `user` can call `cancelOrder` → `_cancelSameChain` on the *unfilled remainder*. `_cancelSameChain`'s only precondition is `hasEscrow` on the *input token* balances (not fees) [6](#0-5) ; it then calls `_withdraw(..., finalize=true)`, which sweeps whatever remains in `_orders[commitment][TRANSACTION_FEES]` to `order.user` as a side effect. If a partial fill already occurred and a subsequent solver relies on `order.fees` still being available at the time of their fill to be paid (the fee is documented as being paid "at fill time" for the *filler*, and refunded to `order.user` on cancellation) — the cancel path can race and drain the `TRANSACTION_FEES` slot to `order.user` before a legitimate solver's remaining partial fill claims it, or vice versa, whichever transaction lands first zeroes the slot for the other.

The root issue mirrors the report's pattern precisely: the specialized entry point (`_cancelSameChain`, analogous to `CreateValidator`) does not perform its own explicit accounting check/decision on the shared ledger entry (`TRANSACTION_FEES`, analogous to the liquid-staking cap), instead silently inheriting whatever the shared helper (`_withdraw`, analogous to `Delegate`'s bookkeeping) does unconditionally when `finalize=true`. There is no invariant enforced that ties `TRANSACTION_FEES` finalization strictly to "no partial fill has claimed a share of this fee." Because partial fills and full-fill/cancel are both driven by unprivileged solver/user calls with no ordering guarantee, whichever transaction finalizes first captures the entire fee balance.

### Impact Explanation
This directly implicates "wrong beneficiary or amount" and "moves exactly once" bandwidth/escrow invariants called out in the Hyperbridge Impact Gate: the `order.fees` amount can be paid to the wrong party (the cancelling user instead of the solver who performed the partial fill, or paid twice if both `_withdraw` calls race on stale reads) depending on transaction ordering, with no relayer/admin/prover compromise required — only two ordinary unprivileged actors (the order's own user calling cancel, and a solver calling fillOrder) racing on the same order.

### Likelihood Explanation
This requires a same-chain order with `order.fees > 0` that has received at least one partial fill (not a full fill) and then a cancellation racing against another partial/full fill in the same block window — a plausible and unprivileged sequence of ordinary calls (`fillOrder` partial + `cancelOrder`) rather than any adversarial infrastructure compromise. However, I was not able to conclusively verify from the fetched code whether `_orders[commitment][TRANSACTION_FEES] == 0` is otherwise guarded against in `fillOrder`'s partial branch (my search did not surface the exact preceding lines validating this), so I cannot rule out an additional check elsewhere in `IntrinsicIntents.sol` that may already gate this race. This uncertainty should be resolved by a full read of `IntrinsicIntents.sol`'s `fillOrder` function before treating this as conclusively exploitable.

### Recommendation
Make `_cancelSameChain` (and any other caller of `_withdraw` with `finalize=true`) explicitly account for `TRANSACTION_FEES` the way `placeOrder`/`_withdraw` do elsewhere: either require that no partial fill has occurred before allowing the fee sweep on cancel, or split "fee entitlement" (owed to whichever party completes/cancels the order first) from "escrow return" (owed to the user) with an explicit, order-state-checked invariant rather than relying on shared, unconditional bookkeeping in `_withdraw`.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
