### Title
Gasless swap deadline is validated against the current head block's timestamp at tx-pool admission time, not the actual timestamp of the block that executes the swap - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The Sherlock finding describes a time-window check (`isInCreationWindow`) that is validated against an inconsistent time reference rather than the actual moment the option is exercised. Kaia's KIP-247 gasless-swap module has the same class of bug: `checkBalanceForSwap` enforces `SwapArgs.Deadline` by comparing it to `g.Chain.CurrentBlock().Time()` — the timestamp of the current head block at the moment the transaction is validated/promoted in the tx pool — rather than the timestamp of the block that will actually execute the transaction.

### Finding Description
`checkBalanceForSwap` performs the deadline check as: [1](#0-0) 

This function is the module's `GetCheckBalance` override, which is the *only* place `Deadline` is validated for gasless swaps: [2](#0-1) 

It is invoked from two places in the generic tx pool:
1. At initial admission (`validateTx`), using `pool.currentState`/head-relative context: [3](#0-2) 
2. During `Filter()`, used when re-checking the queue on each `reset()`/`promoteExecutables` cycle: [4](#0-3) 

Both call sites resolve "now" as `g.Chain.CurrentBlock().Time()`, i.e. the currently-imported head block, not the timestamp of the block the swap transaction will eventually be included in and executed against. A swap transaction can be admitted (and promoted to `pending`) while `Deadline >= CurrentBlock().Time()`, then sit in the pending pool across several block intervals (block generation interval, congestion, proposer scheduling) before it is actually picked up by a block builder. There is no re-validation of the deadline immediately before block assembly/execution — `Filter`/`checkBalanceForSwap` is only re-run when the pool performs a `reset()` for a *new* head, and even then the comparison is against that new head's `Time()`, which lags the timestamp of the *next* block that will actually contain the transaction (`parent.Time + BlockGenerationInterval`, per `validateHeader`): [5](#0-4) 

This mirrors exactly the class of bug in the report: the "window" (deadline) is checked against a proxy time reference (owner-configured start/end in the forex case; head-block time here) instead of the time at which the action is actually finalized (`block.timestamp + 24h` in the forex case; the executing block's timestamp here).

### Impact Explanation
Because the on-chain enforcement of the deadline exists only as an off-chain heuristic in the tx-pool module (the pool's own test asserts the message comes from `checkBalanceForSwap`'s Go-level error, not a Solidity revert): [6](#0-5) 
a swap transaction whose `Deadline` is only marginally in the future relative to `CurrentBlock().Time()` can be admitted and then executed one or more blocks later, once actual block time has advanced past `Deadline`. Since gasless swaps are always preceded by a `LendTxGenerator`-produced lend transaction that transfers KAIA from the block proposer to the sender before the swap tx runs, the proposer's gas-lending exposure and the exchange-rate assumptions embedded in `MinAmountOut`/`AmountRepay` (computed at submission time) can become stale by the time of actual on-chain execution — potentially allowing settlement under conditions the sender/deadline was meant to prevent, without any on-chain deadline safeguard rejecting it. This is a fee-delegation/gasless settlement integrity issue (reward/repayment mis-settlement), matching the "gasless or auction settlement theft" category.

### Likelihood Explanation
Any unprivileged gasless-swap sender can trigger this by submitting a swap with a `Deadline` set close to the current head's timestamp; ordinary network/pool latency (multiple block intervals under load, or a `reset()` computed against a stale head) is sufficient to create the window mismatch — no special privileges are required to reach this path via a normal `SwapForGas`-style transaction submitted through public RPC.

### Recommendation
Re-validate `Deadline` against the timestamp of the block actually being built (e.g., the pending block's expected timestamp) immediately before including the swap tx in a bundle (in `GetLendTxGenerator`/bundle assembly), not only at tx-pool admission/`Filter` time relative to the current head. Alternatively, enforce the deadline on-chain inside the `GaslessSwapRouter`/`swapForGas` execution itself so an invalid-by-deadline swap always reverts atomically regardless of pool-level staleness, and ensure the lend transaction is not settled ahead of that on-chain check.

### Proof of Concept
1. Submit a `GaslessSwapTx` with `Deadline = CurrentBlock().Time() + 1` (or any value just above head time). `checkBalanceForSwap` passes the deadline check at admission time (`deadline.Cmp(CurrentBlock().Time()) < 0` is false): [1](#0-0) 
2. The transaction is promoted to `pending` (module `IsReady` only checks nonce sequencing, not the deadline): [7](#0-6) 
3. Due to network conditions the tx is not included immediately; several `BlockGenerationInterval`-spaced blocks pass, advancing the actual block time well beyond `Deadline`, while the tx pool's `Filter` (run against whatever head is current at the time of `reset()`) may still not detect the staleness before block-building selects the tx for the next block.
4. The bundle (`LendTxGenerator` + swap) executes in a block whose timestamp exceeds `Deadline`, with no on-chain check rejecting it (confirmed by the deadline-rejection test asserting a Go-level error string, not a Solidity revert reason).

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}
