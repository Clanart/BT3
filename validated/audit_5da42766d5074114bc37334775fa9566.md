### Title
Lack of Slippage Control in `PublicDelegation::redeem` and `PublicDelegation::withdraw` Can Cause Value Loss for Public Stakers - (File: contracts/bindings/publicdelegation/PublicDelegation.go, generated from PublicDelegation.sol)

### Summary
`PublicDelegation` is an ERC4626-style vault contract that lets public stakers deposit KAIA and receive shares, and later redeem shares for assets or withdraw a specific amount of assets. Like the `AuraVault::deposit`/`mint` bug in the external report, `PublicDelegation`'s `redeem` and `withdraw` entry points take only an amount (shares or assets) and a recipient, with no caller-specified bound on the counter-value, exposing stakers to slippage from exchange-rate changes.

### Finding Description
`PublicDelegation` implements the same conversion-based accounting pattern as `AuraVault`: it exposes `convertToAssets(uint256 _shares)`, `convertToShares(uint256 _assets)`, `previewDeposit`, `previewRedeem`, `previewWithdraw`, `maxWithdraw`, and `maxRedeem` [1](#0-0) [2](#0-1) .

Its user-facing mutating functions `redeem(address _recipient, uint256 _shares)` and `withdraw(address _recipient, uint256 _assets)` accept only the shares-to-burn or assets-to-receive amount and a recipient — there is no parameter allowing the caller to bound the resulting asset amount (for `redeem`) or the shares that will be burned (for `withdraw`): [3](#0-2) [4](#0-3) 

Because the internal conversion rate between shares and assets (`convertToAssets`/`convertToShares`) reflects the vault's dynamic state (accrued staking rewards, commission changes, or other stakers' concurrent `stake`/`redeem`/`withdraw` calls), the exact rate at execution time can differ from what the caller observed when constructing the transaction. Since neither `redeem` nor `withdraw` allow specifying a minimum-assets-out or maximum-shares-in bound, a staker's transaction cannot revert on unfavorable execution — it will silently settle at whatever rate is in effect when it lands.

### Impact Explanation
An unprivileged staker submitting a `redeem` transaction can receive fewer assets than expected if the exchange rate shifts (e.g. due to another pending transaction executing first within the same block, or a state update to `commissionTo`/rewards). Conversely, a staker calling `withdraw` for a fixed asset amount can have more shares burned than intended. This is a direct instance of unauthorized value loss for the staker analogous to the AuraVault finding, reachable purely through a single submitted transaction from any public delegation staker — no privileged role or node compromise is required.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the exchange rate to move between transaction submission and inclusion, which can happen naturally (reward accrual, other users' stake/withdraw activity) or be induced by front-running/back-running the staker's transaction in the public mempool. Given `PublicDelegation` is a public, permissionless staking entry point (reachable by any staker/public-RPC caller), this condition is realistically triggerable, though the per-transaction loss magnitude depends on how much the rate moves.

### Recommendation
Add slippage-control parameters to the public mutating entry points, mirroring the EIP-4626 guidance cited in the report:
- `redeem(address recipient, uint256 shares, uint256 minAssetsOut)` — revert if `convertToAssets(shares) < minAssetsOut`.
- `withdraw(address recipient, uint256 assets, uint256 maxSharesIn)` — revert if `convertToShares(assets) > maxSharesIn`.
- Similarly review the `stake`/deposit-style entry point to accept a `minSharesOut` parameter.

### Proof of Concept
1. Alice observes `previewRedeem(1000 shares)` off-chain and expects to receive ~1000 KAIA-equivalent assets, then submits `redeem(alice, 1000)`.
2. Before Alice's transaction is included, another transaction (e.g., a large `withdraw`/`redelegate` from another staker, or a commission update) shifts the vault's asset/share ratio unfavorably.
3. Alice's `redeem` call executes and burns her 1000 shares for fewer assets than she expected, with no revert path available since `redeem` has no `minAssetsOut` bound [5](#0-4) .
4. The analogous scenario applies to `withdraw`, where Bob requesting a fixed `_assets` amount can have more shares burned than anticipated [6](#0-5) .
