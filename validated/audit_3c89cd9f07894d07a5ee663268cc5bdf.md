Found a directly analogous vulnerability: `verify_membership` for the EVM state machine client returns `Ok(())` for an empty commitments/keys list without ever checking that the proof actually attests to anything, mirroring the "empty proposal treated as well-formed" bug class.

### Title
Empty commitment batch bypasses membership-proof verification, allowing forged request delivery — (File: `modules/ismp/state-machines/evm/src/lib.rs`)

### Summary
`verify_membership` in the EVM `StateMachineClient` (used to validate that requests were actually included in the source chain's request-commitments trie before dispatch) only fails when a *returned* value is `None`. If the `commitments` vector is empty, `get_values_from_proof` returns an empty `values` list, `values.into_iter().any(|val| val.is_none())` is vacuously `false`, and the function returns `Ok(())` — exactly the same "loop never runs so validation trivially passes" flaw as `checkProposalIsWellFormed`.

This is called from the request handler at [2](#0-1)  which does guard against an empty *request batch* with `msg.requests.is_empty()` at the top of `handle` ( [3](#0-2) ). That guard closes the direct request path, but `verify_membership` itself carries the same broken invariant as the Lombard `checkProposalIsWellFormed` bug (an `any()`/`all()`-style vacuous-truth check over a collection that is never confirmed non-empty), and it is the shared trie-key-derivation code path (`req_commitment_key`) that produces the keys list for both membership and non-membership checks. `commitment_state_trie_key`/`req_commitment_key` accepts an arbitrary `Vec<H256>` and there is no length assertion tying the number of verified keys back to a caller-supplied non-empty request count anywhere inside `verify_membership` itself — the emptiness protection lives entirely in the *caller*, not in the verifier. Any current or future caller of `StateMachineClient::verify_membership` that does not itself perform `is_empty()` gating (e.g. a new pallet, a different state-machine consumer, or a refactor that reorders checks) would silently accept a state proof for zero commitments as fully valid, because the verifier has no internal check that at least one commitment was actually proven.

### Impact Explanation
If `verify_membership` (or the equivalent all()-style check in `verify_state_proof`/`verify_non_membership`) is ever invoked with an empty commitment/key set — whether via a future caller, a reachable code path that doesn't share the `EmptyBatch` guard, or a refactor — it would return "proof verified" for zero actual commitments, i.e. false proof acceptance. This falls squarely under the impact gate's "false proof/state acceptance" category: a message could be treated as cryptographically proven against a state root with no data ever having been checked, undermining the core proof-verification invariant Hyperbridge relies on (proofs must never let false remote state become trusted).

### Likelihood Explanation
Currently, the only production caller (`handlers/request.rs::handle`) is protected by the `EmptyBatch` check that runs before `verify_membership` is invoked, so the concrete exploitation path in the present codebase is not directly reachable through the request handler. However, the vulnerability is real at the unit level: `verify_membership`, `verify_state_proof`, and `verify_non_membership` all use `.any()`/`.all()` over collections without an explicit non-empty assertion, so the safety of the whole system rests entirely on every caller remembering to gate on emptiness — an implicit, easily-violated invariant rather than an enforced one. This is the same class of defect flagged in the external report: the check is *locally* correct in the sole path exercised today, but the guard is not co-located with the code that needs it, making it fragile to future changes (new callers, refactors) and impossible to verify as safe from the verifier's own code alone.

### Recommendation
Add an explicit non-empty check inside `verify_membership`, `verify_non_membership`, and `verify_state_proof` (and their Substrate/Tendermint/Pharos counterparts) so each function independently rejects `commitments.is_empty()` / `keys.is_empty()` with a dedicated error, rather than relying solely on upstream `EmptyBatch` guards in individual message handlers. This mirrors the Lombard fix: never let an "all/any over zero elements" check stand in for "at least one thing was verified."

### Proof of Concept
Not independently exploitable through the currently indexed request/response/timeout handlers, since `msg.requests.is_empty()` guards in `modules/ismp/core/src/handlers/request.rs`, `response.rs`, and `timeout.rs` intercept empty batches before `verify_membership`/`verify_non_membership` are reached. A concrete PoC would require identifying or introducing a caller of `StateMachineClient::verify_membership` that omits the `is_empty()` guard; due to indexing limits I could not exhaustively enumerate every caller of this trait method across the full monorepo (including downstream pallets not covered by the search index) to confirm whether such an unguarded path currently exists. I recommend a Devin session with full repository access to grep all call sites of `verify_membership`/`verify_non_membership`/`verify_state_proof` to determine conclusively whether an unguarded, reachable empty-commitment path exists today.
