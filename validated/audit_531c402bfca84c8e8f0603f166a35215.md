### Title
Malformed PedPoP blame accusation can panic on unregistered recipient - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`AdditionalBlameMachine::blame` and `BlameMachine::blame` accept arbitrary `sender` and `recipient` participant IDs. When a syntactically valid `EncryptionKeyProof` is supplied, `decrypt_with_proof` dereferences `self.enc_keys[&decryptor]` before checking that `decryptor` belongs to the DKG set, causing a panic for any nonzero participant ID greater than `n`. [1](#0-0) 

### Finding Description
`AdditionalBlameMachine::new` registers encryption keys only for participants `1 ..= n`. [2](#0-1) 

The subsequent blame path accepts attacker-controlled `sender` and `recipient` values without range checks. After verifying the encrypted message’s PoP, it evaluates `self.enc_keys[&decryptor]` while building the DLEq verification statement. A recipient such as `Participant::new(n + 1)` is valid as a `Participant` but absent from `enc_keys`, so the indexing operation panics before the proof is verified. [3](#0-2) 

`Participant::new` only rejects zero and does not enforce the DKG’s participant bound. [4](#0-3) 

### Impact Explanation
An unprivileged party able to submit a PedPoP blame accusation can crash the process evaluating blame by naming an out-of-range recipient and attaching any canonically encoded `EncryptionKeyProof`. The proof does not need to be valid because the missing-key dereference occurs before `DLEqProof::verify` executes. This provides a remote denial of service against a participant or arbitrator handling blame proofs. [5](#0-4) 

### Likelihood Explanation
The malicious message itself must pass the PoP check, but the attacker can generate a fresh ephemeral key and valid Schnorr signature for it. `EncryptedMessage::read` and `EncryptionKeyProof::read` provide deserialization paths for the required public inputs. [6](#0-5) [7](#0-6) 

### Recommendation
Validate that both `sender` and `recipient` are registered participants before calling `blame_internal`, or replace unchecked `HashMap` indexing with `get` and return deterministic `InvalidProof`/`MissingParticipant` errors. Apply the same validation in `Decryption::decrypt_with_proof` before dereferencing `enc_keys`.

### Proof of Concept
```rust
let invalid_recipient = Participant::new(n + 1).unwrap();

let machine =
  AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// `msg` is an EncryptedMessage whose PoP verifies for `sender`.
// `proof` only needs to deserialize successfully; it is indexed before verification.
machine.blame(sender, invalid_recipient, msg, Some(proof));
```

The panic occurs while constructing the DLEq points at `self.enc_keys[&decryptor]`, before the supplied proof can be rejected. [1](#0-0)

  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;
