Based on my research, I found a solid, locally-provable analog in the Intent Gateway's same-chain settlement code.

### Title
Full-balance escrow read on leg completion lets one solver drain escrow reserved for another unfilled leg - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain()` computes the escrow amount to release for a completed output leg by reading the *entire* remaining `_orders[commitment][token]` balance instead of the amount proportionally reserved for that specific leg — the exact same class of bug as the reported `stopVesting()` issue, where `returnAmount` included funds (`vest.claimed`) that belonged to someone else's already-settled portion instead of computing the caller's true entitlement.

### Finding Description
`_orders[commitment][token]` is a mapping keyed only by **token address**, not by output-leg index: [1](#0-0) 

An `Order` can legitimately contain multiple `(input[i], output[i])` legs that share the same input token (e.g., two output legs, each escrowing 500 USDC, targeting different output assets — a normal way to split a trade across DAI and WETH legs).

In `_fillSameChain`, when a leg finishes (`amountFilled == totalRequired`), the code does **not** compute the proportional share still owed for that leg. Instead it reads the raw remaining balance for the shared token key: [2](#0-1) 

If leg 0 (USDC→DAI) completes first, `escrowedAmount = _orders[commitment][USDC]` reads the **combined** balance backing both leg 0 and leg 1 (since both legs' USDC deposits landed in the same per-token slot at placement). That entire amount is placed into `escrowedInputs[0]` and released to the filling solver via `_withdraw`, which zeroes the shared slot: [3](#0-2) 

When the second solver later completes leg 1 (USDC→WETH), the code again reads `_orders[commitment][USDC]` — now zero — and the withdrawal reverts inside `_withdraw` (`if (escrowed == 0) revert UnknownOrder();`). Because the WETH transfer to the beneficiary and the escrow release both happen in the same call before this revert, the entire fill reverts, but leg 1's escrow is already gone (taken by solver 1), permanently locking leg 1 out of ever being fillable.

This mirrors the reported pattern precisely: the code should compute "amount reserved for *this* leg" (analogous to `amountVested = balanceOf - claimed`), but instead reads a raw aggregate balance that includes value belonging to a different, still-open claim (analogous to including `vest.claimed` in `returnAmount`).

### Impact Explanation
The first solver to complete a leg is paid the full shared-token escrow amount, not just their proportional share — an unauthorized amount transfer of funds belonging to a separate, unfilled leg. The order's remaining leg then becomes permanently unfillable (the user's escrow for that leg is unrecoverable — cancellation, if attempted, will read the same zeroed slot and refund nothing for that portion either). This is a direct loss-of-funds / wrong-amount bug reachable by any solver calling the public `fillOrder` entrypoint on an order that happens to use a repeated input token across legs — no malicious relayer, prover, or admin involved.

### Likelihood Explanation
Requires an order with two or more `(input, output)` legs sharing the same input token address, which is a realistic and unrestricted configuration — nothing in `placeOrder` or `fillOrder` rejects duplicate input tokens across legs. Any ordinary sequential partial fill of such an order by different solvers (or even the same solver filling legs one at a time) triggers the bug deterministically; no race condition, front-run, or privileged actor is needed.

### Recommendation
Track escrow per `(commitment, legIndex)` rather than per `(commitment, token)`, or compute the amount to release on full-leg completion as the leg's proportional remainder (`totalRequired - alreadyReleasedForThisLeg`) rather than the raw `_orders[commitment][token]` balance, mirroring the audit's fix of deriving the true entitlement instead of reading an aggregate that can include other claimants' funds.

### Proof of Concept
1. User places a same-chain order with two output legs, both `input[i].token = USDC`, `input[0].amount = input[1].amount = 500 USDC`; outputs are DAI (leg 0) and WETH (leg 1). At placement, `_orders[commitment][USDC] = 1000`.
2. Solver A fully fills leg 0 by delivering the required DAI. In `_fillSameChain`, `amountFilled == totalRequired` for leg 0, so `escrowedAmount = _orders[commitment][USDC] = 1000` (not 500). `_withdraw` transfers all 1000 USDC to Solver A and sets `_orders[commitment][USDC] = 0`.
3. Solver B attempts to fill leg 1 by delivering the required WETH. The output transfer executes, but when `_withdraw` tries to release `input[1].token = USDC`, `_orders[commitment][USDC]` is now `0`, triggering `revert UnknownOrder()`, reverting the whole transaction.
4. Leg 1 can never be completed: the user's 500 USDC meant to pay for it was already paid out to Solver A in step 2, and no future fill of leg 1 can succeed.
