### Title
Bank precompile `sendNative` bypasses the `x/bank` `BlockedAddr` blocklist enforced by `MsgSend`/`MsgMultiSend` - ([File: precompiles/bank/bank.go])

### Summary
The `fickling` bug is a classic "incomplete blocklist" bypass: a security-critical denylist (`UnsafeImports`) is enforced for some dangerous primitives but not for a functionally-equivalent one (`runpy`), so callers who rely on the blocklist as a safety gate are silently bypassed. Sei-chain has the same structural pattern in `x/bank`: the blocklist of addresses forbidden from receiving funds (`BlockedAddr`, backed by `blockedAddrs` map and dynamic checks such as the `evm_coinbase` prefix) is enforced at the Cosmos message-handling layer (`MsgSend`/`MsgMultiSend`), but the EVM bank precompile's `sendNative` entry point calls the lower-level keeper primitive `SendCoinsAndWei` directly, skipping that enforcement.

### Finding Description
`x/bank`'s `BaseKeeper`/`BaseSendKeeper` accepts a `blockedAddrs` map specifically to prevent funds from reaching module accounts and other reserved addresses outside the expected rules of the state machine [1](#0-0) . The blocklist doc explicitly says: "If these addresses receive funds outside the expected rules of the state machine, invariants are likely to be broken and could result in a halted network" [2](#0-1) . This includes dynamically-derived addresses such as the reserved `evm_coinbase`-prefixed addresses, as confirmed by `CoinbaseAddressPrefix` and its use in `BlockedAddr` [3](#0-2)  and by the distribution keeper's own defensive comments describing this exact class of address ("beyond the module-account blocklist it also rejects dynamically-derived addresses such as the EVM coinbase addresses") [4](#0-3) .

The enforcement point for ordinary Cosmos transactions is `MsgMultiSend`, which explicitly checks `k.BlockedAddr(accAddr)` on every output address before calling the underlying send primitive [5](#0-4) . The keeper primitives themselves (`SendCoins`, `sendCoinsWithoutAccCreation`) contain no `BlockedAddr` check — that check lives only at the message-server layer [6](#0-5) .

The EVM bank precompile's `sendNative` function, reachable by any EVM contract sending native value to the precompile address, calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly — it does not go through `bankMsgServer` and therefore never invokes `BlockedAddr` [7](#0-6) . By contrast, the sibling `send` method in the same precompile constructs a `banktypes.MsgSend` and dispatches it through `p.bankMsgServer.Send`, which *does* enforce the blocklist [8](#0-7) . This asymmetry — one reachable transfer primitive is gated, a functionally equivalent one is not — mirrors the `runpy` vs `os.system`/`eval` asymmetry in the fickling advisory (the blocklist covers `os.system`/`eval`/`exec` but is missing an equivalent RCE primitive `runpy.run_path`, while a separate control catches only one path).

This pattern is repeated identically across every version of the bank precompile shipped in `precompiles/bank/legacy/*` (`v600`, `v603`, `v605`, `v606`, `v610`, `v630`, `v65`, `v66`), all of which call `SendCoinsAndWei` directly from `sendNative` [9](#0-8) .

### Impact Explanation
An unprivileged EVM contract or EOA can call the bank precompile's `sendNative(receiverAddr)` with `value` set to a reserved/blocklisted Sei address (e.g., a module account or an `evm_coinbase`-derived address) as the `receiverSeiAddr` and have funds credited there, bypassing the invariant-preserving check that normal `MsgSend`/`MsgMultiSend` transactions are subject to. Per the bank module's own documentation, funds landing on these addresses outside expected state-machine rules can break invariants and halt the chain, i.e. this can lead to permanent freezing of funds in an address the invariant system does not expect to receive them, or corruption of module-account accounting that later manifests as a panic/halt (the distribution keeper explicitly guards against a coinbase-prefixed address reaching it precisely to avoid an `AfterValidatorRemoved` panic during `EndBlock`).

### Likelihood Explanation
Trivially reachable: the bank precompile is a standard EVM precompile at a fixed address callable from any transaction/contract without any special privilege, and `sendNative` is a normal payable entry point (`BankPrecompileContract`) exercised in existing tests [10](#0-9) . No governance, validator, or operator action is required — a single crafted EVM transaction suffices.

### Recommendation
Add a `BlockedAddr`/`CanSendTo` check on `receiverSeiAddr` inside `sendNative` (and its legacy precompile versions) before calling `SendCoinsAndWei`, mirroring the check `MsgMultiSend`/`MsgSend` perform, so that the blocklist is enforced consistently regardless of entry point (EVM precompile vs. Cosmos message).

### Proof of Concept
1. Deploy or use an existing EVM contract (or EOA) associated with a Sei address that holds `usei`.
2. Call the bank precompile at `0x0000000000000000000000000000000000001001`'s `sendNative(string)` function with `value` set to some amount and the target `receiverAddr` set to the bech32 string of a blocklisted address (e.g., an `evm_coinbase`-prefixed address or a module account address returned by `BlacklistedAccAddrs`) [11](#0-10) .
3. Observe that `sendNative` succeeds because it calls `p.bankKeeper.SendCoinsAndWei` directly without any `BlockedAddr` check [12](#0-11) , whereas attempting the equivalent transfer via a normal `MsgSend`/`MsgMultiSend` or via the precompile's `send` function (ERC20-pointer path) is rejected by `BlockedAddr` in `msgServer.MultiSend`/`Send` [5](#0-4) .

func (k BaseSendKeeper) SendCoins(ctx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amt sdk.Coins) error {
	if err := k.SendCoinsWithoutAccCreation(ctx, fromAddr, toAddr, amt); err != nil {
		return err
	}

	// Create account if recipient does not exist.
	//
	// NOTE: This should ultimately be removed in favor a more flexible approach
	// such as delegated fee messages.
	accExists := k.ak.HasAccount(ctx, toAddr)
	if !accExists {
		defer func() {
			recordNewAccounts(ctx.Context(), 1)
		}()
		k.ak.SetAccount(ctx, k.ak.NewAccountWithAddress(ctx, toAddr))
	}

	return nil
}

// recordNewAccounts dual-emits the legacy new-account counter and its OTel
// counterpart (bank_new_account). Runs from consensus-critical send paths, so
// a telemetry fault here must not panic into the caller.
func recordNewAccounts(ctx context.Context, count int64) {
	if count <= 0 {
		return
	}
	defer func() {
		if e := recover(); e != nil {
			fmt.Fprintf(os.Stderr, "telemetry panic: %v\n%s", e, debug.Stack())
		}
	}()
	// TODO(PLT-353): remove once bank_new_account verified
	telemetry.IncrCounter(float32(count), "new", "account")
	bankMetrics.newAccount.Add(ctx, count)
}

func (k BaseSendKeeper) SendCoinsWithoutAccCreation(ctx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amt sdk.Coins) error {
	return k.sendCoinsWithoutAccCreation(ctx, fromAddr, toAddr, amt, true)
}

func (k BaseSendKeeper) sendCoinsWithoutAccCreation(ctx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amt sdk.Coins, checkNeg bool) error {
	err := k.SubUnlockedCoins(ctx, fromAddr, amt, checkNeg)
	if err != nil {
		return err
	}

	err = k.AddCoins(ctx, toAddr, amt, checkNeg)
	if err != nil {
		return err
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, toAddr.String()),
			sdk.NewAttribute(types.AttributeKeySender, fromAddr.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, amt.String()),
		),
		sdk.NewEvent(
			sdk.EventTypeMessage,
			sdk.NewAttribute(types.AttributeKeySender, fromAddr.String()),
		),
	})

	return nil
}

func (k Keeper) canReceiveWithdrawAddr(ctx sdk.Context, withdrawAddr sdk.AccAddress) bool {
	// BlockedAddr mirrors the gate SendCoinsFromModuleToAccount actually enforces:
	// beyond the module-account blocklist it also rejects dynamically-derived
	// addresses such as the EVM coinbase addresses (an "evm_coinbase"-prefixed
	// address), which CanSendTo does not catch. Consulting it here keeps this
	// predicate in lockstep with the send, so AfterValidatorRemoved never concludes
	// an address is receivable and then panics on the resulting bank error.
	return !k.blockedAddrs[withdrawAddr.String()] &&
		!k.bankKeeper.BlockedAddr(withdrawAddr) &&
		k.bankKeeper.CanSendTo(ctx, withdrawAddr)
}

func (p PrecompileExecutor) sendNative(ctx sdk.Context, method *abi.Method, args []interface{}, caller common.Address, callingContract common.Address, value *big.Int, readOnly bool, hooks *tracing.Hooks, evm *vm.EVM) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call sendNative from staticcall")
	}
	if ctx.EVMPrecompileCalledFromDelegateCall() {
		return nil, 0, errors.New("cannot delegatecall sendNative")
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	if value == nil || value.Sign() == 0 {
		return nil, 0, errors.New("set `value` field to non-zero to send")
	}

	senderSeiAddr, ok := p.evmKeeper.GetSeiAddress(ctx, caller)
	if !ok {
		return nil, 0, errors.New("invalid addr")
	}

	receiverAddr, ok := (args[0]).(string)
	if !ok || receiverAddr == "" {
		return nil, 0, errors.New("invalid addr")
	}

	receiverSeiAddr, err := sdk.AccAddressFromBech32(receiverAddr)
	if err != nil {
		return nil, 0, err
	}

	usei, wei, err := pcommon.HandlePaymentUseiWei(ctx, p.evmKeeper.GetSeiAddressOrDefault(ctx, p.address), senderSeiAddr, value, p.bankKeeper, p.evmKeeper, hooks, evm.GetDepth())
	if err != nil {
		return nil, 0, err
	}

	if err := p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei); err != nil {
		return nil, 0, err
	}
	accExists := p.accountKeeper.HasAccount(ctx, receiverSeiAddr)
