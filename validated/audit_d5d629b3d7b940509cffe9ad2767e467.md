### Title
`ThresholdKeys::read` deserializes an inconsistent secret share / verification share set without binding checks, enabling attacker-supplied key material under a self-controlled group key — (File: crypto/dkg/src/lib.rs)

### Summary
The Samson analog class is "attacker-controlled bytes flow into a deserializer which instantiates security-relevant objects without validating semantic consistency." In Serai, `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574`) reads `t`, `n`, `i`, the interpolation variant, the `secret_share` scalar, and the full `verification_shares` map straight from the byte stream, then hands them to `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349`). `ThresholdKeys::new` validates only:
- `verification_shares.len() == n`
- each participant index `<= n`
- `Constant` interpolation implies `t == n`

It never checks that `C::generator() * secret_share == verification_shares[i]`, and never checks the shares are non-identity. The `group_key` is then derived purely from the first `t` verification shares (`crypto/dkg/src/lib.rs:376-378`), completely independent of the deserialized secret share.

### Finding Description
`read_F`/`read_G` enforce canonical encodings, so the individual elements are well-formed — but the *relationship* between them is entirely attacker-controlled. An unprivileged party who can feed bytes to `ThresholdKeys::read` can craft:

- `secret_share = s'` (any scalar)
- `verification_shares = { 1..=n -> identity }` (identity is a canonical, valid `GroupEncoding`)

`ThresholdKeys::new` accepts this. `group_key` becomes the identity point, i.e., a threshold key whose discrete log is `0` and fully known to the attacker. Alternatively, the attacker supplies shares inconsistent with `secret_share`, producing keys that sign under a group key unrelated to the share holder's actual contribution — the deserialized object simply does not satisfy the invariant `view().secret_share * G` being consistent with `view().verification_shares[i]` (compare `crypto/dkg/src/lib.rs:494-521`, where `view()` interpolates `secret_share` and `verification_shares` independently).

### Impact Explanation
If the resulting `ThresholdKeys` is used by a `SignMachine`/`AlgorithmMachine`, the holder signs messages whose aggregate signature verifies under `group_key() = scalar * group_key_core + G * offset`. With attacker-chosen verification shares equal to identity, the group key is attacker-controlled (private key `0` plus any offset), so signatures can be produced — or forged — for a key the application believes is a genuine threshold output. More generally, deserialized keys where `secret_share` does not match `verification_shares[i]` break the core DKG invariant, enabling signing of unintended messages under an incorrect group key or silent production of unusable shares — a concrete failure of the deserialized-object invariant, exactly analogous to trusting a deserialized `RoleConfigFile`.

### Likelihood Explanation
Exploitability hinges on the integrator feeding externally influenced bytes to `ThresholdKeys::read` (e.g., restored/migrated key material, coordinator-supplied key blobs). The crate exposes `serialize`/`read` as a public round-trip API with an embedded curve-ID check suggesting it is intended to guard against confused inputs — but it does not guard against self-inconsistent inputs of the *correct* type. No cryptographic primitive is bypassed; the gap is purely the missing consistency check at deserialization.

### Recommendation
In `ThresholdKeys::new` (and therefore in `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]`, reject identity verification shares, and for `Constant` interpolation additionally verify the coefficients reproduce the verification shares. This binds the deserialized components together, mirroring the fix of validating deserialized objects before use.
