## Finding

### Title
Missing slippage protection in `WombatPoolHelperV2.depositFor` due to hardcoded zero minimum liquidity - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2.depositFor` is an externally callable, unprivileged function that lets any user deposit stable tokens into the underlying Wombat pool on behalf of an address, but it hardcodes the `_minimumLiquidity` slippage parameter to `0` when forwarding to `WombatStaking.deposit`, unlike the sibling `deposit()` function which lets the caller supply a real minimum.

### Finding Description
`depositFor` pulls `depositToken` from `msg.sender`, approves it, and calls the internal `_deposit` helper with a hardcoded `0` for `_minimumLiquidity`: [1](#0-0) 

This flows into `WombatStaking.deposit`, which forwards `_minimumLiquidity` straight to the Wombat pool's `deposit` call as `minimumLiquidity`: [2](#0-1) 

The underlying `IWombatPool.deposit` interface explicitly supports a `minimumLiquidity` parameter meant to protect the depositor from adverse price movement / pool imbalance at deposit time: [3](#0-2) 

By contrast, the normal `deposit(uint256 _amount, uint256 _minimumLiquidity)` entry point correctly forwards a caller-supplied minimum: [4](#0-3) 

This is the same bug class as the referenced report (H-2): an operation that moves value into/out of an AMM-style pool without any slippage floor, exposing the depositor to sandwich attacks or unfavorable pool-imbalance pricing at execution time, entirely bypassable by any ordinary wallet calling `depositFor`.

### Impact Explanation
Because `_minimumLiquidity` is forced to `0`, any depositor using `depositFor` (or anyone front-running/sandwiching a `depositFor` transaction) can cause the depositor to receive an arbitrarily small amount of LP/receipt tokens for the stable tokens supplied, with the pool's imbalance-based haircut or an MEV sandwich extracting the difference. This is a direct loss of principal for the depositing wallet — a concrete theft-of-funds vector reachable by any unprivileged user, matching the accepted impact criteria.

### Likelihood Explanation
Likelihood is high: `depositFor` is a public, unprivileged, unconditional entry point with no owner/role gating, and the hardcoded `0` guarantees the missing protection is always in effect for every call to this function, not just an edge case.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`) and forward the caller-supplied value instead of hardcoding `0`, so depositors can enforce their own slippage tolerance:
```solidity
function depositFor(uint256 _amount, uint256 _minimumLiquidity, address _for) external {
    IERC20(depositToken).safeTransferFrom(msg.sender, address(this), _amount);
    IERC20(depositToken).safeApprove(wombatStaking, _amount);
    _deposit(_amount, _minimumLiquidity, _for, address(this));
}
```

### Proof of Concept
1. Attacker monitors mempool for a `WombatPoolHelperV2.depositFor(amount, for)` call.
2. Attacker front-runs with a large swap/deposit that skews the Wombat pool's asset-liability ratio, reducing the LP-per-token issuance rate.
3. Victim's `depositFor` executes with `_minimumLiquidity = 0`, so it cannot revert regardless of the unfavorable rate, and the victim receives fewer receipt/LP tokens than expected.
4. Attacker reverses their position (back-run), profiting from the spread while the `depositFor` caller/`_for` beneficiary permanently receives fewer staking-token shares than the fair-value deposit would have produced.
