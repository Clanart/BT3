## Analysis

**Core broken invariant from the seed report:** the withdrawal function pulls/moves value based on a partial completion, but finalizes overall accounting (state that gates further scaling by users) only after doing so, causing accounting to diverge from what actually moved — enabling a duplicate/incorrect settlement.

**Local analog found:** `IntrinsicIntents._fillSameChain()` performs the *external token transfer* to the (attacker-controlled) `beneficiary` **inside** the per-leg loop, before the function has fully computed whether the whole order `isFullyFilled` and before it calls `_execute()`/finalizes `_filled[commitment]`. When an order has a native-ETH output leg (`token == address(0)`), the transfer is a raw low-level `.call` to `beneficiary` — an address fully controlled by the order creator — which unconditionally triggers the beneficiary's `receive()`/fallback before the loop, the `isFullyFilled` determination, and the final `_execute()`/`_filled` write have completed.

### Title
Reentrancy through native-ETH output leg in `_fillSameChain` causes duplicate `_execute()` calldata execution and overwritten order-filler record - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` updates the per-leg `_partialFills` mapping before performing the external ETH transfer to `beneficiary` for that leg [1](#0-0) , but the escrow release (`_orders` decrement, via `_withdraw`), the `isFullyFilled` decision, and the `_execute()`/`_filled` finalization only happen **after the entire loop over all output legs completes** [2](#0-1) . Because the ETH transfer is a raw `.call` to an attacker-controlled `beneficiary`, a reentrant call into `fillOrder`/`_fillSameChain` for the *same commitment* can complete the remaining legs and finalize the order (calling `_execute()` and setting `_filled[commitment]`) while the outer call is still mid-flight. When the outer call resumes and finishes its own (now stale) view of the loop, it independently concludes `isFullyFilled == true` again and re-invokes `_execute(order, outputsLen)` and re-emits `OrderFilled`, overwriting `_filled[commitment]` a second time.

### Finding Description
In `_fillSameChain`:
1. For each output leg `i`, `_partialFills[commitment][outputToken]` is updated (CEI-style) **before** the token transfer [1](#0-0) .
2. For native output assets (`token == address(0)`), the transfer to `beneficiary` is a raw external call: `(bool sent,) = beneficiary.call{value: beneficiaryTotal}("");` [3](#0-2) . `beneficiary` is `order.output.beneficiary`, fully attacker-controlled since it is chosen when the order is placed.
3. The decision variable `isFullyFilled`, the escrow release via `_withdraw`, and the call to `_execute()` (which dispatches arbitrary `order.output.call` calldata) and the write to `_filled[commitment]` all occur **after the full loop finishes**, not per-leg [2](#0-1) .
4. `fillOrder`/`_fillSameChain` has no reentrancy guard visible in this file, and the only per-order guard (`_filled[commitment]`) is read once at the top of the call and only written at the very end, so a reentrant call started mid-loop reads a stale `_filled` value and can independently finalize the same order.

An attacker who is both the order creator (choosing a malicious `beneficiary` contract with a `receive()` hook) and the filler/solver can call `fillOrder` on a multi-leg order where one leg is native ETH. When that leg's ETH is sent, the `receive()` hook reenters `fillOrder` for the same order/commitment. The reentrant call processes the remaining not-yet-filled legs, sees the whole order as fully filled (since the currently-interrupted leg's `_partialFills` entry was already bumped by the outer call before the external call), and finalizes the order: it calls `_execute()` (running the attached arbitrary output calldata) and marks `_filled[commitment]`. Control then returns to the outer call, which finishes its own loop, still concludes `isFullyFilled == true` (its own tracking variable never learns that the other legs were already finalized by the nested call), and therefore calls `_execute()` again and re-marks `_filled[commitment]`, duplicating the settlement.

### Impact Explanation
This is a duplicate/double-settlement of an intent order: `_execute()` — which dispatches attacker/user-supplied `order.output.call` calldata through the `CallDispatcher` — runs twice for a single order, and `OrderFilled` is emitted twice with `_filled[commitment]` overwritten. This matches the bounty's "logic attacks / replay / double-claim / double-settlement" category and can be leveraged to duplicate side effects the attached calldata performs (e.g., double execution of a downstream DeFi call funded by protocol/dispatcher-held assets), or to corrupt the authoritative `_filled` record of who "won" the order — all reachable from an unprivileged, single public entrypoint with no relayer, prover, or admin involved.

### Likelihood Explanation
Requires only: (1) an order with a native ETH output leg alongside at least one more not-yet-filled leg, and (2) the attacker acting as both order creator (controls `beneficiary`) and filler (calls `fillOrder`), both of which are permissionless roles available to any user. No malicious relayer, prover, governance, or leaked key is needed — this is a pure reentrancy path through a standard `.call{value:}` to a user-supplied address, a well-known but exploitable pattern given the finalization logic is deferred to the end of the loop rather than executed atomically per state transition.

### Recommendation
- Add a reentrancy guard (`nonReentrant`) around `fillOrder`/`_fillSameChain`.
- Re-check `_filled[commitment] == address(0)` immediately before writing it inside `_fillSameChain` (not just at the outer entrypoint), and make the finalize/`_execute()` path strictly single-entry (e.g., use the current `_filled` value being non-zero as an atomic finalize guard, checked-and-set in one step).
- Prefer pull-payment or `nonReentrant` + checks-effects-interactions ordering for native ETH legs, deferring all external `.call` transfers until after all accounting (`_partialFills`, `isFullyFilled`, `_orders` decrement, `_filled` write) is finalized.

### Proof of Concept
1. Attacker deploys `EvilBeneficiary` with a `receive()` that calls back into `IntentGatewayV2.fillOrder()` for the same `order`/`commitment`, supplying fill amounts for the remaining legs.
2. Attacker (as user) places an order with two output legs: leg 0 = native ETH to `EvilBeneficiary`, leg 1 = ERC-20 token, with `order.output.call` set to some arbitrary calldata to be executed once on full fill.
3. Attacker (as solver) calls `fillOrder` supplying full amounts for both legs.
4. During the loop, leg 0's ETH transfer to `EvilBeneficiary` triggers `receive()`, which reenters `fillOrder` and completes leg 1 (already the only remaining leg), causing the reentrant call to see `isFullyFilled == true`, call `_execute()` once, and set `_filled[commitment]`.
5. Execution returns to the outer call, which finishes its own loop over legs (its local `isFullyFilled` remains `true` because leg 1 now reads `remaining == 0`), and it independently calls `_execute()` again and re-writes `_filled[commitment]`, duplicating the arbitrary calldata execution and the `OrderFilled` event.
