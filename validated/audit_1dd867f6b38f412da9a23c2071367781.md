### Title
Attacker-controlled `ReceivedOutput` bytes let `Output::balance()` credit arbitrary satoshi amounts, enabling withdrawals against non-existent funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes the `TxOut` (including its `value` field) and the `OutPoint` verbatim from an untrusted byte stream, with no check that the outpoint exists on-chain or that the declared value matches the real UTXO. Downstream, `Output::balance()` in `processor/src/networks/bitcoin.rs` reports this embedded value directly as the received balance. An unprivileged party who can feed crafted bytes to `ReceivedOutput::read`/`Output::read` therefore causes an arbitrary balance to be credited — the same "incorrect balance update" class as the Aark incident — which can then be spent/withdrawn up to the honest pool's real funds.

### Finding Description
- `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) reads `offset` via `Secp256k1::read_F`, then `TxOut::consensus_decode` and `OutPoint::consensus_decode`. The `TxOut` carries an attacker-chosen `value` and `script_pubkey`; the `OutPoint` carries an attacker-chosen `txid`/`vout`. No validation binds either to the chain.
- `Output::read` (`processor/src/networks/bitcoin.rs:145-166`) wraps this: it reads `OutputType`, `presumed_origin`, then calls `ReceivedOutput::read(reader)` and attaches attacker-controlled `data`.
- `Output::balance()` (`processor/src/networks/bitcoin.rs:128-130`) returns `ExternalBalance { coin: Bitcoin, amount: Amount(self.output.value()) }` — i.e., the unverified deserialized value — and `Output::id()`/`tx_id()` derive from the attacker-chosen `outpoint`.
- The processor's output store (`processor/src/multisigs/scanner.rs:148-159`) persists outputs by looping `N::Output::read(&mut bytes)` over stored bytes, so any path that admits untrusted bytes into `Output::read`/`ReceivedOutput::read` yields a credited balance of arbitrary size.
- `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:175`) sums `input.output.value` into `input_sat` and only checks the *script pubkey* (via `multisig`/`p2tr_script_buf` at `send.rs:277`), never the value against the real UTXO. If the forged value under-reports, the sighash commitment (`Prevouts::All`, `send.rs:375`) diverges from the chain and the resulting signature is invalid — the output is reported received but unspendable. If it over-reports on a *real* outpoint the attacker controls, the balance credited exceeds the funds actually locked.

### Impact Explanation
The balance accounting treats deserialized, unverified bytes as ground truth. Two concrete outcomes:
1. A fabricated `ReceivedOutput` credits a large balance backed by a worthless/nonexistent UTXO; the victim system's ledger believes funds were received and can be induced to pay out against them (mirroring Aark's inflated user balance being converted/withdrawn for ~1.5M USDC + 159 ETH).
2. A mismatched value on a real outpoint produces a transaction whose BIP-341 signature is permanently invalid, burning the honest inputs' spendability for that attempted spend.

### Likelihood Explanation
The vulnerability requires an untrusted-bytes-to-`read` path, which the in-scope rules explicitly admit (`ReceivedOutput::read`, `Output::read`, and the DB deserialization loop in `save_outputs`/`outputs`). `consensus_decode` accepts any valid serialization, so crafting the bytes is trivial — no validator status, collusion, or key material is needed. Exploitation converts directly to theft wherever credited balances authorize releases.

### Recommendation
- Re-verify every `ReceivedOutput` against the chain (or a trusted scanner result) before crediting `balance()`: confirm the `OutPoint` exists, its `script_pubkey` matches the expected P2TR key for the declared `offset`, and its `value` equals the on-chain amount.
- In `SignableTransaction::new`/`multisig`, cross-check `prevouts[i].value` against the confirmed UTXO value rather than trusting the embedded `TxOut`.
- Fail `Output::read`/`ReceivedOutput::read` (or mark outputs pending) until an on-chain confirmation pass has validated the deserialized claims.

### Proof of Concept
```rust
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf, hashes::Hash, Txid};
use bitcoin_serai::{bitcoin, wallet::ReceivedOutput};
use frost::curve::Secp256k1;
use k256::elliptic_curve::ff::PrimeField;

// Attacker crafts bytes claiming a 21 BTC deposit to a registered-offset script
let mut bytes = vec![];
bytes.extend(Secp256k1::read_F // offset chosen so p2tr_script_buf(key + G*offset) == our script
  // ... supply offset scalar bytes ...
);
let fake = TxOut {
  value: Amount::from_sat(2_100_000_000),   // 21 BTC, no such UTXO
  script_pubkey: /* victim P2TR script for that offset */ ScriptBuf::new(),
};
// consensus-encode fake TxOut + arbitrary OutPoint, append to `bytes`
let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 2_100_000_000); // balance() now reports 21 BTC
```
`balance()` in `processor/src/networks/bitcoin.rs:128-130` then reports the forged amount as a genuine received balance; `SignableTransaction` either builds an unspendable transaction (wrong prevout value → invalid BIP-341 sighash) or enables payout of real pool funds against phantom inputs.
