## Analog Found

### Title
Missing reentrancy protection in `BridgeTransferERC20`/ERC721 request-and-handle flow allows request-nonce duplication and double value-transfer via callback/hook tokens - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
The Kaia service-chain bridge contract `BridgeTransferKLAY` explicitly wraps its KLAY transfer paths with a `nonReentrant` modifier because it performs a raw external call (`_to.call.value(_value)("")`) mid-function, before mutating `requestNonce`/`lowerHandleNonce`. `BridgeTransferERC20` performs the structurally identical pattern — external token calls (`safeTransfer`, `mint`, `burn`) sandwiched between event emission and the `requestNonce++`/nonce bookkeeping — but never inherits `ReentrancyGuard` nor applies `nonReentrant`, leaving it exposed to the exact same class of bug described in the H-01 report (external callback fires before internal accounting state is finalized).

### Finding Description
In `_requestERC20Transfer`, the sequence is: [1](#0-0) 

1. `_payERC20FeeAndRefundChange` performs `IERC20(_token).safeTransfer(feeReceiver, fee)` and/or `safeTransfer(from, feeRefund)` — both external calls into the token contract.
2. If `modeMintBurn`, `ERC20Burnable(_tokenAddress).burn(_value)` is called — another external call into the token.
3. Only *after* both of these external calls does the contract `emit RequestValueTransfer(...)` using the *current* (not-yet-incremented) `requestNonce`, and finally execute `requestNonce++`.

Because none of `_requestERC20Transfer`, `requestERC20Transfer`, `onERC20Received`, or `handleERC20Transfer` carry a `nonReentrant` guard, any registered token whose `transfer`/`burn`/`mint` implementation invokes a callback into `msg.sender` (ERC777 `tokensToSend`/`tokensReceived` hooks, or any custom hookable/rebasing ERC20) can re-enter the bridge's public `requestERC20Transfer`/`onERC20Received` entry points from within step 1 or 2, before `requestNonce` has been incremented.

This is the same root-cause pattern as the external report: an attacker-controlled token callback fires in the middle of a multi-step state-mutation sequence (fee payment/burn → event/nonce commit), letting the attacker observe and exploit the intermediate, not-yet-finalized state (the stale `requestNonce`) to make the bridge emit multiple `RequestValueTransfer` events referencing the same nonce for the same request, or interleave requests so that the off-chain relayer/operator (`node/sc/bridge_manager.go` `handleRequestValueTransferEvent`) processes duplicate/inconsistent bridging events keyed by nonce.

By contrast, the developers already recognized and mitigated this exact risk for the native-KLAY path: [2](#0-1) 
where both `handleKLAYTransfer` and `_requestKLAYTransfer` are `nonReentrant`, precisely because the low-level `.call.value()` can hand control to an attacker contract before nonce bookkeeping completes — the same hazard exists whenever the "token" being transferred can execute arbitrary code during transfer, which is true for ERC20 too (ERC777, fee-on-transfer, callback-enabled, or otherwise non-standard tokens), yet the ERC20/ERC721 bridge paths were left unprotected.

### Impact Explanation
Reentrancy through a hookable token in `_requestERC20Transfer`/`onERC20Received` can:
- Cause the same `requestNonce` to be emitted in more than one `RequestValueTransfer` event for different underlying calls, corrupting the request/nonce invariant the counterpart-chain operator relies on to mint/unlock value 1:1 with locked/burned value (`node/sc/bridge_manager.go` `handleRequestValueTransferEvent` at [3](#0-2) ), which can lead to double-minting/unlocking on the counterpart chain relative to what was actually locked/burned on the source chain — i.e., unauthorized value movement / bridge supply inflation.
- In mint-burn mode, allow the burn accounting and fee accounting to be interleaved across reentrant calls, letting a single deposit of tokens be counted as backing for more than one cross-chain transfer request.

### Likelihood Explanation
Any unprivileged caller who can get a registered bridge token deployed/whitelisted with a transfer/mint/burn hook (ERC777-style tokens, or any custom ERC20 with hooks) can trigger this from a single transaction calling `requestERC20Transfer`/`onERC20Received` — no validator, operator, or bridge-owner privilege is required to trigger the reentrancy itself, only ordinary registration of a token by the bridge operator (a normal, expected bridge operation, not an attacker-controlled privileged action).

### Recommendation
Add the same `ReentrancyGuard`/`nonReentrant` protection already used in `BridgeTransferKLAY` to `BridgeTransferERC20` (and `BridgeTransferERC721`), guarding `_requestERC20Transfer`, `requestERC20Transfer`, `onERC20Received`, and `handleERC20Transfer`. Additionally, follow checks-effects-interactions ordering: increment `requestNonce` and finalize all internal bookkeeping/state (`_updateHandleNonce`, nonce increments) before making any external token calls (`safeTransfer`, `mint`, `burn`).

### Proof of Concept
1. Bridge operator registers an ERC777-compatible (or any hook-enabled) token via `registerToken` and it becomes usable through `onlyRegisteredToken`.
2. Attacker deploys a contract implementing the ERC777 `tokensToSend`/`tokensReceived` hook (analogous to `AttackImp` in the report) that, upon being notified of the `safeTransfer`/`burn` call made from within `_requestERC20Transfer`/`_payERC20FeeAndRefundChange`, re-enters `requestERC20Transfer` (or `onERC20Received`) on the bridge.
3. Because `requestNonce` has not yet been incremented on the outer call, the reentrant inner call emits `RequestValueTransfer` with the same nonce value as the (not-yet-completed) outer call, then increments `requestNonce` itself; when the outer call resumes, it emits its own `RequestValueTransfer` with the (now stale) nonce and increments again — producing duplicate/skewed nonce bookkeeping that the operator's `handleRequestValueTransferEvent` logic consumes as if they were sequential distinct requests, opening the door to duplicate handling/minting on the counterpart chain for what was effectively a single locked/burned amount on the source chain.
