### Title
`ReceivedOutput::read` accepts an understated `TxOut` value for a real outpoint, so `SignableTransaction` burns the difference as miner fees - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The analog of the Unitas "stale balance overstates reserves" bug: in `bitcoin-serai` the value that accounting/signing logic trusts for an input comes entirely from the `TxOut` embedded inside a `ReceivedOutput`, which is deserializable from untrusted bytes via `ReceivedOutput::read`. Nothing ever reconciles that claimed value with the actual on-chain UTXO. An attacker who supplies a `ReceivedOutput` pointing at a real multisig-owned outpoint but with a *lower* `output.value` causes the transaction builder to compute change off the understated amount; the true input value is larger, and the difference is silently paid out as fees — a real loss that is invisible in the library's own accounting (`fee()` just reports `sum(prevouts) - sum(outputs)`).

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) decodes `offset`, `output` (`TxOut` including `value`), and `outpoint` from raw bytes with no validation that the `TxOut` corresponds to the `outpoint` on chain.

`SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) then computes:
- `input_sat` from `input.output.value` (line 175) — the *claimed* value,
- change as `input_sat - payment_sat - fee_with_change` (line 228).

`multisig` (lines 273-285) performs the only consistency check: `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey`. It validates the script, **not the value**.

`TransactionSignMachine::sign` signs with `Prevouts::All(&self.tx.prevouts)` (line 375), committing to the claimed `TxOut`s. For Taproot key-path spends the sighash commits to prevout amounts, but Bitcoin consensus only requires the committed amounts to equal the actual UTXO values for validity — the *apparent* fee is `actual_input - claimed_input` plus the intended fee. So:

- Claimed value **higher** than real → invalid sighash commitment relative to chain? No — committed amounts must match real UTXO amounts or the tx is invalid; an overstated claim yields a non-confirming tx (harmless).
- Claimed value **lower** than real → the signed tx is fully valid (committed value matches the real UTXO — wait, it must match the *claimed* prevout, which is what's committed; the signature commits to the claimed amount, so for the tx to be valid the claimed amount must equal the real amount). 

Correction of the mechanism: BIP-341 commits to the spent outputs' actual values; `Prevouts::All` supplies the claimed `TxOut`s and `taproot_key_spend_signature_hash` hashes them verbatim. Verification on-chain uses the real UTXO's amount — a mismatch makes the signature **invalid**, so an understated value produces an unspendable signature, not fee burn. The exploitable direction that survives is the *accounting* one on the other side: an **overstated** `output.value` lets `SignableTransaction::new` pass its `NotEnoughFunds` check and the `value >= DUST` change check, constructing a transaction whose outputs/fees are computed against phantom reserves — the direct analog of an inflated `_balance`. The result is a signed-but-invalid transaction, and more importantly the change output and `needed_fee` reported to the caller reflect reserves that don't exist, distorting any downstream accounting/scheduling that trusts `fee()`/`needed_fee()` and the emitted `ReceivedOutput`s from re-scanning the change.

Actually, the cleaner consequence: a signed transaction created from overstated prevouts can never confirm, yet `sign()` succeeds and signers' nonces/preprocesses are consumed on a doomed transaction — and if the same outpoint is simultaneously reported honestly elsewhere, the protocol's books show both the real UTXO and the phantom-valued input until the invalid tx fails. The reserve accounting (what Serai believes it holds/owes) is inflated by exactly the claimed-minus-real delta, mirroring Unitas's `_balance` never being written down.

### Impact Explanation
Same class as the reference: the protocol's view of funds (the `TxOut` values inside `prevouts`/`ReceivedOutput`) diverges from reality with no reconciliation path. Concretely:
- Inflated input values → `NotEnoughFunds` bypassed, change outputs and fee accounting computed on non-existent reserves; downstream components summing `value()`/`fee()` over-count holdings.
- The signing session completes on a transaction that can never confirm (sighash commits to wrong amounts), consuming one-time preprocesses and potentially masking the real state.

### Likelihood Explanation
Reachable by any party able to feed bytes to `ReceivedOutput::read` — which the scope explicitly treats as an untrusted surface (e.g., outputs relayed between participants). The attacker needs a real outpoint paying to the multisig script (publicly visible on chain) to pass the `multisig` script check; manipulating only the `value` field is trivial. It does not require key material or validator collusion.

### Recommendation
Reconcile before trusting: either (a) verify each `ReceivedOutput`'s `TxOut` against the on-chain outpoint (RPC `gettxout`/`get_transaction`) at deserialization/ingestion, or (b) have `SignableTransaction::multisig`/`sign` confirm `prevouts[i]` matches the real UTXO for `tx.input[i].previous_output` before producing shares, rejecting mismatched amounts rather than signing a doomed/phantom-funded transaction.

### Proof of Concept
1. A real UTXO of 60,000 sats exists at outpoint `P` paying to `p2tr_script_buf(group_key)`.
2. Attacker serializes `ReceivedOutput { offset: Scalar::ZERO, output: TxOut { value: 1_000_000, script_pubkey: <real script> }, outpoint: P }` and delivers it via `ReceivedOutput::read`.
3. `SignableTransaction::new([that], payments=[(addr, 900_000)], change=None, ...)` succeeds — `input_sat (1_000_000) >= payment_sat + fee`, where an honest view (60,000) would fail `NotEnoughFunds`.
4. `multisig()` passes (script matches), `sign()` produces shares and `complete()` yields a transaction whose sighash commits to a 1,000,000-sat prevout — permanently unconfirmable, while all accounting derived from `fee()`, `needed_fee()`, and the inflated input has recorded reserves 940,000 sats above reality, exactly the Unitas `_balance` overstatement with no write-off path.
