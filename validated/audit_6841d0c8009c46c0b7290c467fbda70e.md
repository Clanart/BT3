### Title
Permissionless `donateRewards` Enables Reward Sandwiching/Theft From Genuine Stakers - (File: `rewards/BaseRewardPoolV2.sol`, `rewards/BaseRewardPool.sol`, `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`BaseRewardPoolV2`, `BaseRewardPool`, and `mWOMSVBaseRewarder` all expose an unrestricted, non-access-controlled `donateRewards()` function that immediately mixes new rewards into `rewardPerTokenStored`, distributed pro-rata to whoever is currently staked. Because staking/unstaking through `MasterMagpie` has no lockup or cooldown, any wallet can front-run a `donateRewards()` (or a manager's `queueNewRewards()`) call by staking a large position immediately before the call and withdrawing immediately after, capturing a disproportionate share of the reward and diluting genuine long-term stakers — the same "reward disbursement front-running" bug class described in the external report.

### Finding Description
`donateRewards()` is `external` with no `onlyManager`/`onlyOwner` modifier, allowing any wallet to call it directly: [1](#0-0) 

It funnels straight into `_provisionReward()`, which updates `rewardPerTokenStored` based on `totalStaked()` at the time of the call: [2](#0-1) 

The same unrestricted pattern exists in `BaseRewardPool.sol`: [3](#0-2) [4](#0-3) 

and in `mWOMSVBaseRewarder.sol`: [5](#0-4) [6](#0-5) 

Since `rewardPerTokenStored` is updated atomically at the moment rewards are injected and divided by `totalStaked()` at that instant, whoever holds the largest share of `totalStaked()` in that block captures the largest share of the newly injected reward — exactly the mechanism described in the external report for `addRewardsForAccessory`. An attacker (or the same actor calling `donateRewards` themselves) can:
1. Stake a large amount into the pool via `MasterMagpie` right before calling/triggering `donateRewards()` (no lock/cooldown gates deposits or withdrawals).
2. Call `donateRewards()`, which immediately credits `rewardPerTokenStored` proportional to the attacker's inflated share of `totalStaked()`.
3. Immediately withdraw the staked principal, retaining the harvested reward share while genuine long-term stakers receive a diluted portion of the reward that was meant for them.

This is functionally identical to the report's "equip immediately before, unequip immediately after" attack against `Rewards.addRewardsForAccessory()`, but here the reward-adding function itself is unauthenticated (`donateRewards`), making the attack even easier since the attacker does not need to race someone else's transaction — they can self-trigger the reward injection at the moment they hold maximum stake share.

### Impact Explanation
This results in theft of yield from legitimate, longer-term stakers: reward tokens intended to be distributed pro-rata over the staking period are instead captured disproportionately by an attacker who only holds a stake for the single block/transaction surrounding the `donateRewards()` call. Because `donateRewards` accepts arbitrary reward tokens already registered (`isRewardToken`), and pools such as `WombatStaking`-linked rewarders forward WOM/bribe rewards through `queueNewRewards`/`donateRewards`, the amounts at stake can be non-trivial across the protocol's reward flows.

### Likelihood Explanation
Likelihood is high: `donateRewards()` has zero access control, requires no special conditions, and depositing/withdrawing via `MasterMagpie` appears to have no cooldown or lock period gating this attack. Any wallet holding the reward token can execute the attack unilaterally, without needing to race another user's transaction, using flash-loanable or self-owned capital to temporarily inflate `totalStaked()` share.

### Recommendation
- Restrict `donateRewards()` to trusted managers (`onlyManager`) or otherwise rate-limit/require a minimum reward-injection interval, consistent with `queueNewRewards()`.
- Consider streaming reward distribution over time (e.g., a `periodFinish`/`rewardRate` linear vesting model as in Synthetix-style `StakingRewards`) rather than crediting `rewardPerTokenStored` atomically, so instantaneous stake share cannot capture disproportionate rewards.
- Introduce a minimum staking duration or withdrawal cooldown in `MasterMagpie` to prevent same-block stake/unstake sandwiching around reward injections.

### Proof of Concept
1. Attacker observes (or self-triggers) a call to `BaseRewardPoolV2.donateRewards(amount, rewardToken)`.
2. Attacker calls `MasterMagpie.deposit(...)` staking a large amount of `stakingToken` just before the `donateRewards` transaction (or bundles it in the same transaction if `donateRewards` is unauthenticated and self-callable).
3. `donateRewards()` executes, calling `_provisionReward()`, which increases `rewardPerTokenStored` by `(_amountReward * 10**stakingTokenDecimals) / totalStaked()` — with the attacker's large deposit inflating `totalStaked()` in their favor for that instant. [7](#0-6) 
4. Attacker immediately calls `MasterMagpie.withdraw(...)` to unstake, retaining their claim on `userRewards` accrued from the disproportionate `rewardPerTokenStored` bump, while pre-existing long-term stakers receive a diluted share of the same reward injection.

```text
    /// @notice Sends new rewards to be distributed to the users staking. Only possible to donate already registered token
    /// @param _amountReward Amount of reward token to be distributed
    /// @param _rewardToken Address reward token
    function donateRewards(uint256 _amountReward, address _rewardToken) external {
        if (!isRewardToken[_rewardToken])
            revert MustBeRewardToken();

        _provisionReward(_amountReward, _rewardToken);
    }
```

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
