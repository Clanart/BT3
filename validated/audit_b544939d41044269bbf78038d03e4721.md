### Title
Unbounded backward pointer scan in `jsondec_any` can read out-of-bounds before the JSON input buffer - (File: upb/json/decode.c)

### Summary
The upb JSON parser's `google.protobuf.Any` decoding logic (`jsondec_any`) contains a backward-scanning loop that decrements a pointer looking for a `,` character with **no lower-bound check**, unlike the analogous and correctly-guarded scan in `jsondec_typeurl` a few lines above it in the same file. This is the same bug class as CVE-2020-35380 (GJSON): a parser that walks a buffer boundary without validating the walk stays inside the buffer, causing an out-of-bounds read/panic on crafted input.

### Finding Description
`jsondec_typeurl` correctly bounds its backward scan: [1](#0-0) 

But `jsondec_any`, when the `@type` key appears after other fields in the JSON object (so `pre_type_data` was recorded from an earlier field), performs an **unchecked** backward scan for the previous field separator: [2](#0-1) 

```
pre_type_end = start;
while (*pre_type_end != ',') pre_type_end--;
```

There is no `pre_type_end > <buffer start>` condition (contrast with `jsondec_typeurl`'s `while (ptr > type_url.data && *--ptr != '/')`). The loop assumes that whenever `pre_type_data` is non-null (i.e., some field preceded `@type`), a literal `,` character is guaranteed to exist between that earlier field and the `@type` key, purely from JSON grammar. This invariant is what an attacker-controlled JSON payload attacks: any path that lets the scan begin walking backward without a `,` appearing before it exits the buffer causes `pre_type_end` to decrement past `d->ptr`'s buffer start (the caller-supplied `buf`), performing out-of-bounds byte reads (`*pre_type_end`) indefinitely until a `,` byte happens to occur in adjacent (attacker-uncontrolled) heap/stack memory, or the process crashes via a guard page / ASan trap.

This directly parallels the GJSON flaw: GJSON's "improper bounds checking" let crafted JSON structure drive an index past the allocated buffer, causing an out-of-bounds panic; here, a crafted JSON `Any` object drives a raw pointer decrement past the start of the parse buffer, with no corresponding check.

### Impact Explanation
- **Reachability**: `jsondec_any` is reached by any ordinary caller of `upb_JsonDecode` (and by extension `google::protobuf::json_internal`/ProtoJSON parsing paths that route through upb for messages containing a `google.protobuf.Any` field) when parsing attacker-supplied JSON that maps into an `Any`-typed field.
- **Effect**: Out-of-bounds memory read via unbounded pointer decrement. In the best case this reads adjacent heap/stack bytes until a stray `,` byte is found (information leak into control flow, though not attacker-observable directly); in the worst case (buffer at/near a page boundary, or under ASan/hardened allocators) it triggers a segmentation fault / crash — a denial-of-service, matching the class and severity discussed in the GJSON advisory (CWE-400/CWE-125 boundary).
- **No memory corruption/RCE** is claimed — this is a read-only pointer walk, so the impact is a crash/DoS or, at most, a bounded information disclosure of adjacent memory content used only for a comparison, not returned to the caller.

### Likelihood Explanation
Determining a concrete confirmed trigger requires proving there's a reachable state where `pre_type_data` is set (an earlier field exists before `@type`) yet the raw byte stream, scanning backward from the `@type` key's opening quote, contains **no** literal `,` before the start of the buffer. Under strict, well-formed JSON object grammar, a `,` must exist between any two sibling members, so under a *fully valid* JSON payload this scan is expected to terminate correctly, since `jsondec_skipval` (used to skip prior field values) is expected to consume matched brackets/quotes correctly, leaving genuine separator commas intact. I could not, within the available tool budget, confirm or rule out an edge case (e.g., interaction with `jsondec_skipval`'s handling of numbers/malformed literals, or the special "scan ahead for `@type`" restart logic that seeks backward across a value it already partially consumed) that would let this scan run off the start of the buffer. This is a **structural missing-bounds-check** identical in shape to the GJSON root cause and to the already-fixed neighboring `jsondec_typeurl` function, but full proof-of-concept confirmation (a byte-exact minimal JSON payload demonstrating the underflow) was not completed.

### Recommendation
Add the same defensive bound used in `jsondec_typeurl` to the backward scan in `jsondec_any`:
```c
if (pre_type_data) {
  pre_type_end = start;
  while (pre_type_end > pre_type_data && *pre_type_end != ',') pre_type_end--;
  if (*pre_type_end != ',') {
    jsondec_err(d, "Malformed Any object: could not find field separator");
  }
}
```
This mirrors the existing pattern at `upb/json/decode.c:1428` (`while (ptr > type_url.data && *--ptr != '/')`) and ensures the scan cannot walk before `pre_type_data` (the start of the earliest recorded field), let alone before the input buffer.

### Proof of Concept
Not confirmed. I was unable to construct or verify, within the tool budget available, a concrete JSON payload that forces the backward scan in `jsondec_any` (`upb/json/decode.c:1467`) to walk past the start of the input buffer — this would require either a bug in `jsondec_skipval`'s bracket/quote matching that swallows the true separator comma, or some other lenient-parsing path that admits a field boundary with no literal `,` present. The finding is reported as a structural missing-bounds-check analog to CVE-2020-35380 based on direct code comparison with the adjacent, correctly-bounded `jsondec_typeurl` scan, but a minimal reproducible crash input was not produced or executed.
