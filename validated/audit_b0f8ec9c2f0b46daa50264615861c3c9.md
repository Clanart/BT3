### Title
Uncapped per-conflict-chunk prompt size lets a crafted merge conflict stall/blow up Copilot conflict resolution - (File: app/src/lib/stores/copilot-store.ts)

### Summary
`CopilotStore.resolveConflicts` batches conflicted files into chunks bounded only by file **count** (`SinglePromptFileLimit`, `MaxConcurrentChunks`), never by the **size** of the conflict content each file contributes. A repository that produces a merge/rebase conflict with a small number of files but enormous conflict hunks (large binary-adjacent text blobs, generated files, minified bundles, deeply repeated content, etc.) will still be classified as "one file" for chunking purposes, so up to `SinglePromptFileLimit` (15–20) such files are packed into a single prompt, and up to `MaxConcurrentChunks` (5) such prompts run concurrently — with no gate on the aggregate content size handed to the LLM session.

### Finding Description
`resolveConflicts` (`app/src/lib/stores/copilot-store.ts:1231-1366`) filters out files with a `skippedReason` (e.g., "too large", from `copilot-conflict-context.ts`) but that per-file skip check does not translate into a cap on the *combined* size of a chunk. The `createDependencyAwareChunks` function (`app/src/lib/copilot-conflict-resolution.ts:908-1002`) only bin-packs by number of files against `targetSize` (15 or 20) — files that dependency-group together (shared imports/exports, detected via `extractSymbols`) are kept in the same chunk regardless of their combined byte size [1](#0-0) . Each chunk is serialized with `formatConflictContextForPrompt` and sent as one prompt via `resolveChunk`, with up to `MaxConcurrentChunks` running in parallel [2](#0-1) .

This is structurally identical to the reported bug class: the report's mempool admission caps concurrency by *transaction count* while NU6.3 let a transaction carry double the expensive proof work, defeating the intended bound. Here, Desktop's concurrency/batch gate is expressed in *file count* while a single conflicted file (attacker-controlled content merged from a fetched branch/PR) can carry an arbitrarily large amount of conflict-hunk text, defeating the intended bound on prompt size and LLM invocation cost/latency per unit of "count."

### Impact Explanation
Because a merge/rebase/cherry-pick conflict is populated from content the user is merging in (which can originate from an untrusted remote branch, fork, or pull request that the user fetched and attempted to merge — no unusual user action beyond a normal merge), an attacker who controls that branch's content can shape conflict hunks to be extremely large while remaining under file-count thresholds. Consequences:
- Excess memory/CPU building and holding oversized prompt strings in the renderer process (`formatConflictContextForPrompt`).
- Disproportionate, unbounded Copilot/LLM token consumption and possible cost impact charged against the user's Copilot subscription/quota, since nothing gates aggregate content size per chunk before dispatch.
- Multiple such oversized chunks running concurrently (`MaxConcurrentChunks = 5`) multiplies the effect, potentially stalling the conflict-resolution UI/progress reporting for the user for extended periods, and increasing exposure of large amounts of source content to the model session per request.

This does not achieve code execution or credential exfiltration by itself, so it does not reach the "High" severity of the report, but it matches the same CWE-405/CWE-770 asymmetric-cost pattern where a count-based cap fails to bound aggregate cost.

### Likelihood Explanation
Reasonably likely for any user who merges/rebases against a hostile or compromised fork/branch and then opts into the Copilot AI conflict-resolution feature (an increasingly promoted first-class flow in the "Resolve conflicts" UI). No special privileges, admin rights, or unnatural steps are required beyond normal merge-conflict resolution with the AI assist enabled.

### Recommendation
Add a per-chunk (and ideally per-file) content-size/token budget check in `createDependencyAwareChunks` / `resolveConflicts`, splitting or skipping files (surfaced via `ICopilotSkippedFile`, similar to the existing "too large" skip path) once the aggregate prompt size for a chunk exceeds a defined cost budget, independent of file count.

### Proof of Concept
1. Set up a repository and create two branches that will conflict on a small number of files (e.g., 3–5 files) but make each conflicting file huge (e.g., megabytes of unique per-line content on both "ours" and "theirs" sides so the conflict hunk can't be trivially deduplicated).
2. Fetch and attempt to merge the hostile branch, producing a merge conflict.
3. Trigger "Resolve conflicts with Copilot." Because file count (3–5) is well under `SinglePromptFileLimit`, all files go into a single chunk with no aggregate size check, and `formatConflictContextForPrompt` builds one very large prompt that is dispatched without a size gate.
4. Observe elevated memory/CPU in the renderer while building/holding the prompt, high latency/cost of the LLM call, and — if multiple large conflicts are queued or the batch path is hit with many such heavy chunks — up to 5 such heavy prompts running concurrently via `MaxConcurrentChunks`, degrading responsiveness of the conflict-resolution flow.
