### Title
Discard Changes uses unsanitized git-status paths for file deletion/trash, bypassing the app's own `resolveWithin` containment guard - (File: `app/src/lib/stores/git-store.ts`)

### Summary
GitHub Desktop already recognizes that file paths derived from git-controlled data (status entries, conflict resolutions, deep-link file paths) must be validated to stay inside the repository before being used in filesystem operations, and implements `resolveWithin()` for exactly that purpose. [1](#0-0) 
That guard is used in `copilot-conflict-context.ts` and in `dispatcher.ts`'s `openRepositoryFromUrl`/copilot-resolution write path. [2](#0-1) [3](#0-2) 
However, `GitStore.discardChanges` — the handler behind the standard "Discard Changes" UI action — builds the on-disk path directly from `file.path` (and `file.status.oldPath`) using plain `Path.resolve`/`Path.join`, with no `resolveWithin` check, before either moving the file to trash or permanently `rm`-ing it. [4](#0-3) 

### Finding Description
`file.path` originates from `parsePorcelainStatus`, which captures the trailing bytes of a `git status --porcelain=2 -z` line verbatim into `IStatusEntry.path`/`oldPath` — the parser comment explicitly states "filenames containing special characters are not specially formatted; no quoting or backslash-escaping is performed." [5](#0-4) 
That raw string is carried through `mapStatus`/`convertToAppStatus`/`buildStatusMap` into the `WorkingDirectoryFileChange` objects shown in the Changes list with no path normalization or containment check. [6](#0-5) 

`discardChanges` then does:
```
await this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))
...
await rm(Path.join(this.repository.path, file.path))
```
for untracked files, and separately queues `file.status.oldPath` for checkout/reset when the entry is a rename/copy. [7](#0-6) 

Because `Path.resolve`/`Path.join` do not confine the result to `repository.path` the way `resolveWithin` does (which additionally resolves symlinks via `realpath` and rejects results that escape the root), any path component such as `..` that survives as a literal path segment in a status entry would cause the trash/`rm` target to be computed outside the repository. This is precisely the containment guarantee the app itself already implements and applies elsewhere (`resolveWithin`'s tests specifically cover `..` traversal and symlink escape), but the guard is absent on this particular, destructive code path. [8](#0-7) 

### Impact Explanation
If reachable, this allows a crafted/fetched repository to cause GitHub Desktop to delete or send-to-trash a file outside the working directory when the user performs the ordinary "Discard Changes" action — a normal, expected user interaction, not an unusual step. `rm()` on Untracked entries is a permanent, non-trash deletion, so a successful escape would be a silent, irreversible file deletion outside the repo, matching the class of "silent corruption of what the user commits/discards" and "file write/read (here, delete) outside the repo" called out as valid impact.

### Likelihood Explanation
Likelihood hinges on whether an attacker-controlled clone/fetch can actually cause `git status --porcelain=2 -z` to emit a path containing traversal (`..`) or a foreign-platform separator as a literal path segment for a tracked/renamed/untracked entry. Modern git itself blocks `..`/`.git`-like path components in tree/index entries during checkout (fsck/`protectNTFS`-style protections), which constrains this on tracked/renamed paths. The most plausible surviving vector is the **untracked-file** case, where the "path" is whatever exists in the actual working tree the app is scanning — including the results of a submodule checkout, a symlinked working directory entry, or a filename crafted to be valid on the host filesystem but interpreted by `Path.resolve`/`Path.join` in a way that traverses upward (e.g., a component equal to `..` that git/OS permitted to be created as an untracked file, or interaction with symlinked directories inside the working tree, which `resolveWithin`'s own tests demonstrate is realizable). I could not fully verify a concrete end-to-end reproduction (i.e., confirm git will let such a status entry exist) using the available index/tools, so likelihood should be treated as **medium, not confirmed** — the code-level gap (missing `resolveWithin`) is definite, but the exact attacker-crafted-repository trigger needs live testing against real git behavior (index/tree, submodules, symlinked working-tree components) which is outside what static code search can confirm.

### Recommendation
In `GitStore.discardChanges`, replace the raw `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)` calls with `resolveWithin(this.repository.path, file.path)` (and likewise for `file.status.oldPath` when queuing checkout/reset targets), skipping/erroring the entry (and logging) if `resolveWithin` returns `null`, exactly as already done in `copilot-conflict-context.ts` and the copilot-resolution write path in `app-store.ts`. [9](#0-8) 

### Proof of Concept
Not independently reproducible from static code alone — I could not confirm, using the tools available, an exact sequence in which `git status --porcelain=2 -z` reports a working-directory entry whose `path` literally contains a `..` traversal segment for a real git checkout. Suggested validation for a Devin session with terminal access:
1. Create a repository with a working-tree directory that is itself a symlink pointing outside the repo root (or contains one), then create/modify an untracked file inside it so it surfaces via `git status --porcelain=2 -z` with a path like `symlinked-dir/../../outside-file`.
2. Fetch/clone this repository into Desktop, select the file in the Changes list, and invoke "Discard Changes."
3. Observe whether `Path.resolve(repository.path, file.path)` in `discardChanges` resolves to a location outside `repository.path`, and whether the target file (trash or `rm`) is actually outside the repo, compared to running the same path through `resolveWithin`, which is expected to return `null` and block the operation.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
