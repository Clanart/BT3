### Title
Rounding of `feeAmount` to zero in `WombatStaking._sendRewards` permanently DoSes `deposit`/`withdraw`/`harvest` via `SmartWomConvert.smartConvert` revert - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._sendRewards` unconditionally forwards a percentage-based fee slice of harvested WOM to `SmartWomConvert.smartConvert()` without checking that the computed `feeAmount` is non-zero. `smartConvert` reverts with `MustNoBeZero()` whenever its input is `0`. Because harvested WOM rewards are frequently small (dust harvests, low-TVL pools, or an admin-set `feeInfo.value` that is small relative to typical harvest sizes — all within normal, allowed bounds), integer division `(originalRewardAmount * feeInfo.value) / DENOMINATOR` can floor to `0` even though `originalRewardAmount > 0`. This causes the whole `_sendRewards` call — and therefore the enclosing `deposit`, `withdraw`, and `harvest` calls on `WombatStaking` — to revert every time it is invoked for that pool, permanently freezing user deposits/withdrawals for that asset. This mirrors the reported bug class: a value derived from a BPS split can be too small for a downstream function's minimum/non-zero check, causing an unconditional revert and DoS.

### Finding Description
`WombatStaking.deposit()` and `WombatStaking.withdraw()` both call `_toMasterWomAndSendReward`, which calls `_sendRewards` to distribute freshly harvested WOM to configured fee recipients before continuing: [1](#0-0) [2](#0-1) [3](#0-2) 

Inside `_sendRewards`, for every active fee entry, the code computes `feeAmount` via a BPS calculation and unconditionally calls `smartConvert` when the fee is marked `isMWOM` and a converter is set — with **no check that `feeAmount > 0`**: [4](#0-3) 

`SmartWomConvert.smartConvert` explicitly reverts on a zero amount: [5](#0-4) 

Because `feeAmount = (originalRewardAmount * feeInfo.value) / DENOMINATOR` uses integer division with `DENOMINATOR = 10_000`, any harvested WOM amount smaller than `10_000 / feeInfo.value` produces `feeAmount == 0` while `originalRewardAmount != 0`. `feeInfo.value` is admin-configured via `addFee`/`setFee`, both of which only enforce `_value < DENOMINATOR` — a normal, allowed configuration, not a malicious one: [6](#0-5) 

Once triggered, `smartConvert(0, 0)` reverts, bubbling up through `_sendRewards` → `_toMasterWomAndSendReward` → `deposit`/`withdraw`/`harvest`, meaning any unprivileged user's ordinary deposit or withdrawal call on that pool reverts unconditionally as long as the harvested-reward-to-fee-BPS ratio stays below the rounding threshold (e.g., low-volume pools, small pending WOM emissions between harvests, or thin liquidity periods).

### Impact Explanation
This is a direct, permanent freeze of core LP custody functions in `WombatStaking` — `deposit` and `withdraw` both trigger the vulnerable code path before completing their principal-moving logic, so a triggering condition blocks not only yield distribution but also users' ability to withdraw their principal from the affected pool. This matches the "permanent freezing of funds" impact category.

### Likelihood Explanation
The trigger condition depends only on ordinary protocol operation (small/harvested WOM amounts relative to a normally-configured, in-bounds `feeInfo.value`) — no malicious actor or privileged misuse is required, matching the accepted root-cause pattern from the referenced report ("owner misconfiguration within allowed boundaries leads to DoS"). Low-TVL pools, newly registered pools, or pools with infrequent harvest intervals are especially likely to hit `feeAmount == 0`, and once hit, every subsequent `deposit`/`withdraw`/`harvest` call reverts until an admin intervenes (e.g., disables the fee or the converter), which is outside of what a normal user can influence within the transaction itself.

### Recommendation
Guard the `smartConvert` call in `_sendRewards` with a `feeAmount > 0` check (mirroring the existing `if (_amount == 0) return;` pattern already used at the top of the function), and route the entire fee amount without conversion (or skip conversion and simply forward WOM) when the computed `feeAmount` rounds to zero, so a dust fee never blocks the whole reward-processing/deposit/withdraw flow.

### Proof of Concept
1. Admin registers a pool and calls `addFee(_value, converterOrRewarder, isMWOM=true, isAddress=false)` with a modest, in-bounds fee value (e.g. 50 = 0.5%) and sets `smartWomConverter` via `setSmartConvert`. [7](#0-6) [8](#0-7) 
2. A user calls `deposit()` (or the pool is harvested) at a time when pending WOM rewards for that pool are small, e.g. `originalRewardAmount = 100` wei WOM: `feeAmount = (100 * 50) / 10_000 = 0` (rounds down). [9](#0-8) 
3. `_sendRewards` still calls `IConverter(smartWomConverter).smartConvert(0, 0)` since there is no `feeAmount > 0` guard. [10](#0-9) 
4. `smartConvert` reverts with `MustNoBeZero()` because `_amountIn == 0`. [11](#0-10) 
5. The revert propagates up through `_toMasterWomAndSendReward` into `deposit`/`withdraw`, causing the user's transaction (including principal withdrawal) to fail every time this condition recurs, until an admin changes the fee configuration or disables the converter.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
