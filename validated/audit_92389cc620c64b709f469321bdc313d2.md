### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` causes stack exhaustion before nesting-depth validation - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLp` recursively decodes account-key sub-elements without any depth limit. The safeguard that rejects a role-based key nested inside another role-based key (`ErrNestedCompositeType`) is only enforced *after* decoding completes, in `CheckInstallable`/`CheckUpdatable`. A crafted `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate` (or `WithRatio` variant) whose `AccountKey` field contains deeply, self-similarly nested `AccountKeyRoleBased` blobs forces the RLP decoder to recurse to a depth bounded only by the maximum transaction size, not by any explicit recursion-depth check — analogous to the FreeImage `TIFFReadDirectory` bug where the parser kept recursing/looping without a depth guard, exhausting the call stack.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes an arbitrary number of sub-key blobs and, for each one, invokes `AccountKeySerializer.DecodeRLP`, which in turn instantiates the concrete key type (via `NewAccountKey`) and calls its `DecodeRLP` again: [1](#0-0) [2](#0-1) 

If the decoded sub-key type is again `AccountKeyTypeRoleBased`, this chain re-enters `AccountKeyRoleBased.DecodeRLP`, recursing without any depth counter or limit. The only defense against nested role-based keys, `IsCompositeType()`/`CheckInstallable`/`CheckUpdatable`, is invoked *after* the entire structure has already been fully decoded and only rejects the tx once decoding returns successfully: [3](#0-2) 

This decode path is reached for any incoming `AccountUpdate`-family transaction the moment it is RLP-decoded — during `TxInternalDataAccountUpdate.DecodeRLP` and analogous fee-delegated variants — which happens on `txpool.AddRemote` (i.e., `eth_sendRawTransaction`/`kaia_sendRawTransaction` public RPC) before pool admission checks, and again during block/state processing. Each nesting level in the crafted blob only costs a few bytes of RLP overhead (a type byte plus a short list header), so within the transaction size budget (`txSlotSize = 32*1024` bytes, several slots allowed) an attacker can encode many thousands of nesting levels: [4](#0-3) 

Each level of recursion consumes real Go call-stack frames across `DecodeRLP` → `NewAccountKey` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`, with no cap, which is the direct analog of the FreeImage `TIFFReadDirectory` issue: the parser "always continues" without bounding recursion/looping depth, leading to stack exhaustion.

### Impact Explanation
An unprivileged transaction sender (or any public-RPC caller submitting a raw transaction) can crash any node that decodes the transaction — whether via `txpool.AddRemote` at RPC ingestion or during block validation/state transition — by submitting a single crafted `AccountUpdate`-type transaction with deeply self-nested `AccountKeyRoleBased` data. This is a denial-of-service against transaction pool admission and block processing, matching the CVE's "always returns/loops without bound → stack exhaustion" bug class, mapped onto Kaia's `AccountKey` decoding path.

### Likelihood Explanation
The attack requires only constructing and RLP-encoding a nested `AccountKeyRoleBased` structure and submitting it as the `Key` field of any `AccountUpdate` transaction type via a public RPC endpoint — no special privileges, valid signatures matching an existing account's update key are still required to pass earlier steps of decoding (decoding happens on the raw bytes regardless of signature validity), and the transaction size limits (`txSlotSize`, `MaxTxDataSize`) are generous enough to encode very deep nesting cheaply.

### Recommendation
Add an explicit recursion-depth (or nesting-level) limit inside `AccountKeyRoleBased.DecodeRLP` (and/or `AccountKeySerializer.DecodeRLP`), rejecting decode immediately once nesting exceeds 1 level (role-based keys are only ever allowed to contain non-composite sub-keys), rather than deferring the nested-composite check to `CheckInstallable`/`CheckUpdatable` after the full structure has already been decoded.

### Proof of Concept
Conceptually: build a byte string `b0` = RLP-encoded `AccountKeySerializer{keyType: RoleBased, key: <minimal AccountKeyPublic>}`. Then repeatedly construct `bN = RLP-encode(AccountKeySerializer{keyType: RoleBased, key: AccountKeyRoleBased{ decode-target = bN-1 as one raw sub-key element }})`, chaining thousands of levels within the ~32KB+ transaction data budget. Embed the final blob as the `Key` field of a `TxTypeAccountUpdate` transaction and submit it via `eth_sendRawTransaction`/`txpool.AddRemote`; `TxInternalDataAccountUpdate.DecodeRLP` → `AccountCommon.DecodeRLP`/key decode path will recurse through `AccountKeyRoleBased.DecodeRLP` to the crafted depth before any `ErrNestedCompositeType` check can run, exhausting the goroutine stack.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
