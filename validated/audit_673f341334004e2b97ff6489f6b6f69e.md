## Verdict

### Title
Unauthenticated Caller Can Trigger `restart_background_tasks` on All Operators and Verifiers via Aggregator `GetEntityStatuses` — (`core/src/rpc/aggregator.rs`, `core/src/servers.rs`)

### Summary
When the aggregator gRPC server runs with `client_verification=false` (the documented design for the aggregator), any network-reachable caller — with no client certificate — can call `GetEntityStatuses(restart_tasks=true)`. The aggregator then fans out `RestartBackgroundTasks` RPCs to every registered operator and verifier using its own privileged client certificate, which the operator/verifier interceptors accept. This allows an unauthenticated attacker to repeatedly disrupt all bridge automation tasks (PayoutChecker, StateManager, TxSender, BitcoinSyncer) on every entity.

### Finding Description
The `create_grpc_server` function gates both the mTLS client-cert requirement and the `OnlyAggregatorAndSelf` interceptor behind the single `client_verification` flag. When this flag is `false` on the aggregator (the documented and code-warned-about expected state), the interceptor degrades to `Noop`, and no client certificate is required at the TLS layer. The `GetEntityStatuses` RPC handler performs no additional authorization check before honoring `restart_tasks=true`. The aggregator then uses its own privileged client certificate to call `RestartBackgroundTasks` on all operators and verifiers, which those entities accept because the call originates from the aggregator cert.

### Impact Explanation
An attacker who can reach the aggregator's TCP port can repeatedly call `GetEntityStatuses(restart_tasks=true)` in a tight loop. Each call restarts all background tasks on every operator and verifier. Tasks that are mid-execution (e.g., a challenge response being assembled, a payout tx being sent, a watchtower challenge being timed) are aborted and restarted. If the attacker sustains this during a timelock-sensitive window (e.g., `OPERATOR_CHALLENGE_TIMEOUT_TIMELOCK`, `WATCHTOWER_CHALLENGE_TIMEOUT_TIMELOCK`), the relevant task may never complete before the timelock expires, causing the operator to lose collateral or a challenge to go unanswered — a material fund impact.

### Likelihood Explanation
The aggregator is the externally-facing entry point for the bridge backend. The docs explicitly state it does not enforce client certificates. Any attacker with network access to the aggregator port can exploit this with a single gRPC call. No key material, privileged position, or prior knowledge beyond the port number is required.

### Recommendation
Add an explicit authorization check in `AggregatorServer::get_entity_statuses` that gates `restart_tasks=true` behind a verified caller identity (e.g., require a specific metadata token, restrict to localhost/Unix socket, or introduce a separate privileged endpoint). Alternatively, separate the aggregator's public-facing surface (no client cert) from its privileged management surface (requires client cert or is Unix-socket-only), so that `GetEntityStatuses(restart_tasks=true)` is only reachable from the management surface.

### Proof of Concept
1. Start an aggregator with `client_verification=false` and at least one operator/verifier endpoint configured.
2. Connect to the aggregator's TCP port with a plain TLS client (no client certificate).
3. Call `/clementine.ClementineAggregator/GetEntityStatuses` with `restart_tasks: true`.
4. Observe that the aggregator fans out `RestartBackgroundTasks` to all operators and verifiers (visible in logs: `"Restarting background tasks rpc called"`).
5. Repeat in a loop during a timelock-sensitive operation to demonstrate liveness failure.
