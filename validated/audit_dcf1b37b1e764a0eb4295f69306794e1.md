### Title
Crafted `ThresholdKeys` deserialization yields attacker-controlled group key with no share consistency check - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts untrusted bytes and reconstructs a threshold keypair, but neither `read` nor `ThresholdKeys::new` verifies that the deserialized `secret_share` corresponds to `verification_shares[i]`, nor that the verification shares collectively produce a group key consistent with the provided share. Analogous to CVE-2022-34113 (crafted plugin bytes accepted without validation → attacker-controlled execution), crafted serialized key bytes are accepted without validation → attacker-controlled threshold key.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, an interpolation method, an arbitrary `secret_share`, and `n` arbitrary verification-share points, then calls `ThresholdKeys::new`. [1](#0-0)  `ThresholdKeys::new` only checks the count of verification shares and that participant indexes do not exceed `n`; it then derives `group_key` by interpolating the first `t` verification shares. [2](#0-1)  No check binds `secret_share` to `verification_shares[i]` (`secret_share * G == verification_shares[i]` is never evaluated), so a crafted blob can declare any `secret_share` alongside verification shares whose discrete logs the attacker knows, producing `ThresholdKeys` whose `group_key()` is a key the attacker alone controls. The FROST vectors importer demonstrates this byte format is trivially constructible by an external party. [3](#0-2) 

### Impact Explanation
If attacker-influenced bytes reach `ThresholdKeys::read` (the format is self-describing and reachable wherever serialized keys are exchanged or restored), the resulting `ThresholdKeys` reports a `group_key` the attacker can sign for unilaterally — the attacker chooses `secret_share`/verification shares they know the discrete logs of — enabling theft of funds sent to that group key and forged threshold signatures. Alternatively, an inconsistent `secret_share` yields a group that can never produce valid signatures, permanently locking funds — "funds reported received that are not spendable."

### Likelihood Explanation
Reachability depends on a caller feeding externally supplied bytes to `ThresholdKeys::read`; the API performs no authentication of origin (only the `C::ID` tag, which is public). [4](#0-3)  Within the threat model of untrusted bytes reaching `read` APIs, the construction requires no other party's cooperation and succeeds deterministically, making it Medium-High likelihood where the deserialization surface is exposed.

### Recommendation
In `ThresholdKeys::new` (or `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Consider additionally requiring `t >= 1` semantics that prevent `group_key` from being formed entirely from a minimal attacker-controlled subset, and document that `ThresholdKeys::read` must only consume authenticated storage.

### Proof of Concept
1. Attacker picks `x` known, sets `verification_shares = {1: G*x}`, `t = n = i = 1`, `secret_share = x`, `Interpolation::Lagrange`.
2. Serialize per the format in `ThresholdKeys::write` / the manual construction in `crypto/frost/src/tests/vectors.rs:119-129`.
3. `ThresholdKeys::<C>::read` succeeds; `group_key() == G*x`, whose discrete log `x` is known only to the attacker. Any deposit or signing authority associated with `group_key()` is under sole attacker control, despite the blob being untrusted input.
