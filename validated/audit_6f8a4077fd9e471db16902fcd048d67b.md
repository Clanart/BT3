### Title
Cached FROST preprocess seed is never consumed — re-entry into `share_internal`/`complete` reuses identical nonces, enabling secret-share recovery - (File: crypto/frost/src/sign.rs)

### Summary
The analog to "calling `curl_easy_pause()` inside the socket callback touches a freed/invalidated struct" is a **one-time resource silently reused on re-entry**: in Serai, `AlgorithmMachine::seeded_preprocess` derives all FROST nonces deterministically from `CachedPreprocess` seed bytes (`ChaCha20Rng::from_seed`), and `from_cache` reconstructs the same nonce set every time the same seed is reloaded. `SigningProtocol::preprocess_internal` stores the seed under `CachedPreprocesses` keyed only by `context` and **never deletes or rotates it** — every `preprocess`, `share`, and `complete` call for the same context re-derives the exact same nonces, i.e., the consumed preprocess is "freed" semantically but still dereferenced.

### Finding Description
- `crypto/frost/src/sign.rs:121-144` — `seeded_preprocess` builds `ChaCha20Rng` from `seed.0` and calls `Commitments::new(rng, original_secret_share, nonces)`; the same seed always yields the same nonce pair and the same `Preprocess` commitments.
- `crypto/frost/src/sign.rs:264-274` — `cache()`/`from_cache` round-trip the seed; `from_cache` calls `seeded_preprocess` again, regenerating identical nonces.
- `coordinator/src/tributary/signing_protocol.rs:123-145` — `preprocess_internal` writes `CachedPreprocesses::set(txn, &context, &cache)` only `if ... is_none()`, then re-reads and decrypts the same entry on every invocation. Nothing marks the entry consumed after `sign()`.
- `coordinator/src/tributary/signing_protocol.rs:150-181` — `share_internal` calls `preprocess_internal` fresh each time, so two share computations under one context reuse the nonce.
- `coordinator/src/tributary/signing_protocol.rs:288-327` — `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal`, i.e., the seed is dereferenced at least twice per confirmation flow. The context is only `(b"DkgConfirmer", attempt)` (line 275) — it does not bind `key_pair`, `removed`, or the preprocess set.
- The binding factor `rho` and challenge depend on the *set of preprocesses* and `msg` (`crypto/frost/src/sign.rs:283-313`), which are derived from validator-supplied bytes read via `read_preprocess` — attacker-influenceable public inputs committed on-chain.

### Impact Explanation
A Schnorr share is `s = d + b·e·ρ + λ·share·c` where `d, e` are the reused nonces. If two `share_internal` executions under the same `context` ever observe *different* inputs — a different `preprocesses` map (different validator preprocess set between a reboot/retry or between `share` and `complete`), a different `removed` set from `removed_as_of_dkg_attempt`, or a different `key_pair` in `set_keys_message` — then `ρ`/`c` differ while the nonce is identical. Two shares `s₁, s₂` give two linear equations; an observer with the published preprocesses and shares solves for `λ·share`, recovering the validator's MuSig threshold key share, then forges `DkgConfirmer`/tributary signatures. This is the ROS-style parallel-session nonce reuse: the "freed" preprocess is used again because the callback-equivalent (`share_internal`) re-loads rather than invalidates it.

### Likelihood Explanation
Reaching it requires the local coordinator to compute shares twice for the same `attempt` with non-identical preprocess sets/messages — e.g., a crash/reboot between `share` and `complete`, or `removed`/preprocess-set drift between the two on-chain reads. The inputs (`preprocesses` HashMap, `key_pair`) are entirely supplied by external validators and on-chain data, satisfying the unprivileged-party reachability criterion. The window is narrower than always-exploitable (inputs must differ while context is identical), which keeps this at High rather than Critical.

### Recommendation
Rotate or delete the `CachedPreprocesses` entry the first time it is consumed for signing: in `SigningProtocol::preprocess_internal`, after `from_cache`, overwrite the DB slot with a fresh seed (or delete it) so any subsequent `preprocess`/`share`/`complete` for the same context generates new nonces or fails loudly. Alternatively, bind `context` to a hash of the preprocess set and message so a differing input deterministically yields a different seed — though explicit consumption is safer since it also forbids same-input replays from consuming nonce budget. `crypto/frost` could additionally expose a consuming variant of `from_cache` that makes silent reuse impossible by construction.

### Proof of Concept
1. `DkgConfirmer::share(preprocesses_A, key_pair)` → `share_internal` → `preprocess_internal` loads seed `S`, nonces `(d,e)`, emits share `s₁` over `msg(key_pair)` with binding `ρ₁`.
2. After a reboot (or via `complete`), `share_internal` runs again under the identical `context = ("DkgConfirmer", attempt)`; `CachedPreprocesses::get` returns the same `S` — the entry at `signing_protocol.rs:137` was never cleared. `seeded_preprocess` regenerates the identical `(d,e)` (`sign.rs:127-132`).
3. If the `preprocesses` map now contains any different entry (a validator posted an additional/different preprocess, or `removed_as_of_dkg_attempt` changed), `included`/`ρ` differ → share `s₂ = d + be·ρ₂ + λ·share·c₂`.
4. From the two broadcast 32-byte shares and the public preprocesses, compute `be = (s₁−s₂−λ·share·(c₁−c₂))/(ρ₁−ρ₂)` — solving jointly recovers `λ·share` (the MuSig secret share contribution) since all other terms are public or linear. Knowledge of `λ·share` for the local signer enables forging its contributions to tributary `DkgConfirmer` signatures.

Caveat: the precise on-chain call sequence that produces two differing-input `share_internal` invocations for one `attempt` (in `coordinator/src/tributary/handle.rs`) could not be fully confirmed within the available iterations; the nonce-reuse mechanism itself is fully evidenced in `crypto/frost/src/sign.rs` and `coordinator/src/tributary/signing_protocol.rs`.
