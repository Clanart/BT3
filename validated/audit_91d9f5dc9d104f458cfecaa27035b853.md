### Title
Vesting schedule is unenforced — full `totalAmount` becomes claimable instantly at `startVestingTime` - (File: rewards/ArbitrumMWomAirdrop.sol)

### Summary
`_getClaimable` sets `vested = totalAmount` unconditionally, making the `vestingPeriodCount`/`intervals` state variables entirely unused dead code. Any address with a valid merkle proof can call `claim()` once `block.timestamp >= startVestingTime` and receive their entire allocation in a single transaction, with no linear/interval vesting enforced at all.

### Finding Description
`claim()` at [1](#0-0)  only requires `block.timestamp >= startVestingTime` and a valid merkle proof, then calls `_getClaimable`. Inside `_getClaimable`: [2](#0-1) 
`vested` is hardcoded to `totalAmount` regardless of `startVestingTime`, `vestingPeriodCount`, or `intervals`, so the `if (vested > totalAmount)` branch is unreachable dead code and the function always returns `totalAmount - claimed`. The state variables `vestingPeriodCount` and `intervals` are declared at [3](#0-2)  but are never written to (no setter exists) or read anywhere else in the contract, confirming the interval-based vesting schedule was never actually wired into the claim logic.

Regarding the "double count" part of the question: this is **not** exploitable. `claimedAmount[msg.sender]` is correctly incremented after every claim [4](#0-3) , and `_getClaimable` returns `0` once `claimed >= totalAmount` [5](#0-4) , which combined with `require(claimable > 0, ...)` and the `nonReentrant` modifier prevents any user from receiving more than their `totalAmount` across multiple `claim()` calls (with any combination of `isStake`/`isLock`). So calling `claim` twice does not double the payout — a second call after full claim will always revert.

### Impact Explanation
The real, exploitable issue is that the entire `totalAmount` is released the instant `startVestingTime` is reached instead of unlocking gradually over `vestingPeriodCount` intervals as the state layout implies. This is a premature release of unclaimed yield: any eligible claimant (not a privileged actor, just a merkle-tree recipient) can immediately withdraw, stake, or lock funds that were intended to vest over time, defeating the protocol's distribution schedule and potentially forcing `reward` token outflows far earlier than budgeted/expected by the protocol/treasury.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: any address in the merkle tree needs only to wait for `startVestingTime` and call `claim` with a valid proof — no special capital, front-running, or privileged role required. It affects every claimant, not just an attacker, but any such claimant benefits from full immediate release rather than the intended vesting.

### Recommendation
Implement the actual vesting math in `_getClaimable`: compute `vested` based on elapsed time since `startVestingTime` divided by `intervals`, capped by `vestingPeriodCount`, e.g. `vested = totalAmount * min(elapsedIntervals, vestingPeriodCount) / vestingPeriodCount`, and only return `vested - claimed`. Add setters (or constructor params, already partially present) to ensure `vestingPeriodCount` and `intervals` are configured and actually used before deployment.

### Proof of Concept
Foundry test:
1. Deploy `ArbitrumMWomAirdrop` with `startVestingTime = block.timestamp + 1 days`, and (hypothetically) intended `vestingPeriodCount = 10`, `intervals = 30 days` (note: no constructor/setter path currently sets these, underscoring they're dead).
2. Warp to `startVestingTime`.
3. Call `claim(totalAmount, proof, false, false)` for a valid leaf.
4. Assert `reward.balanceOf(claimant) == totalAmount` immediately, i.e., 100% of the allocation released with 0 of 10 vesting periods elapsed — demonstrating the vesting schedule is not enforced.

    function _getClaimable(address account, uint256 totalAmount) internal view returns (uint256) {
        uint256 claimed = getClaimed(account);
        if (claimed >= totalAmount) {
            return 0;
        }

        uint256 vested = totalAmount;
        if (vested > totalAmount) {
            return totalAmount - claimed;
        }

        return vested - claimed;
    }
