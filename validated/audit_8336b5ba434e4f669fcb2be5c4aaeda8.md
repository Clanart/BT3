### Title
Out-of-range blamed participant crashes blame verification - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`AdditionalBlameMachine::blame` accepts an attacker-controlled `sender: Participant` without checking that it belongs to the DKG’s `1 ..= n` participant set. After the encrypted share and optional ECDH proof verify, the implementation indexes `self.commitments[&sender]`. Because `AdditionalBlameMachine::new` only inserts commitments for participants `1 ..= n`, a syntactically nonzero participant such as `n + 1` causes an out-of-bounds `HashMap` indexing panic.

This is analogous to CVE-2017-3733’s inconsistent negotiated-state crash: blame adjudication proceeds with a participant identity outside the negotiated DKG set, then dereferences protocol state as if that identity had been established.

### Finding Description
`AdditionalBlameMachine::new(context, n, commitment_msgs)` builds `commitments` only for `Participant` values `1 ..= n` and stores them in `BlameMachine.commitments`.

`AdditionalBlameMachine::blame(sender, recipient, msg, proof)` delegates to `BlameMachine::blame_internal`. `blame_internal` first calls `decrypt_with_proof(sender, recipient, msg, proof)` and deserializes the decrypted bytes as a scalar. Once those checks succeed, it evaluates the share against `self.commitments[&sender]`.

There is no preceding check that `u16::from(sender) <= n`. Since `Participant::new` only rejects zero, any nonzero participant—including `n + 1`—can be supplied. The `HashMap` index then panics before blame can be returned.

### Impact Explanation
An unauthenticated or minimally privileged caller capable of submitting a blame adjudication request can crash the verifier/task processing the request. The attacker must provide an `EncryptedMessage` and proof that pass `decrypt_with_proof` and a canonically encoded scalar, but can do so for a fabricated participant identity because the proof is generated by the attacker and bound to that attacker-selected `sender` identifier.

The impact is denial of service of blame verification, potentially preventing the protocol from resolving a legitimate accusation and aborting or stalling the surrounding DKG/error-handling path.

### Likelihood Explanation
The panic is deterministic once the crafted `sender` exceeds `n`. It does not require control of an existing participant, private key material, or a threshold coalition. Feasibility depends on the integrator exposing `AdditionalBlameMachine::blame` inputs derived from untrusted blame messages without independently constraining `sender` to the DKG membership set; the API itself does not enforce that invariant.

### Recommendation
Validate both `sender` and `recipient` against the stored participant set before calling `decrypt_with_proof`, and return a defined error or blame result rather than indexing the map:

```rust
if !self.commitments.contains_key(&sender) {
  return sender; // or a dedicated InvalidParticipant error
}
if !self.commitments.contains_key(&recipient) {
  return recipient; // or a dedicated InvalidParticipant error
}
```

Prefer changing `blame`/`blame_internal` to return `Result<Participant, PedPoPError>` so malformed or out-of-set blame claims cannot panic. `AdditionalBlameMachine` should also reject `n == 0` in `new`.

### Proof of Concept
```rust
// Conceptual PoC using the pedpop API.

let n = 3;
let context = [0x42; 32];

// commitment_msgs contains authenticated commitments only for participants 1..=3.
let machine = AdditionalBlameMachine::<Ristretto>::new(
  context,
  n,
  commitment_msgs,
).unwrap();

// Choose a nonzero participant outside the negotiated DKG set.
let fake_sender = Participant::new(n + 1).unwrap();
let recipient = Participant::new(1).unwrap();

// Construct an EncryptedMessage containing a canonical scalar and an
// EncryptionKeyProof valid under `fake_sender`. The attacker can generate
// the ephemeral ECDH key/proof because `fake_sender` is merely an input
// identifier; no existing commitment for that participant is required.
let msg: EncryptedMessage<Ristretto, SecretShare<ristretto_scalar>> =
  attacker_encrypted_scalar_for(fake_sender, recipient);
let proof: Option<EncryptionKeyProof<Ristretto>> =
  Some(attacker_ecdh_proof_for(fake_sender, recipient, &msg));

// decrypt_with_proof succeeds, then `self.commitments[&fake_sender]` panics.
let _ = machine.blame(fake_sender, recipient, msg, proof);
```
