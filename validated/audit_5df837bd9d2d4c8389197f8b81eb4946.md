## Finding [1](#0-0) 

### Title
Diff-expansion index shift corrupts line-selection mapping used to build commit/discard patches - ([File: app/src/ui/diff/text-diff-expansion.ts])

### Summary
`expandTextDiffHunk`/`expandWholeTextDiff` rewrite a text diff's hunks and shift every hunk's `unifiedDiffStart`/`unifiedDiffEnd` (the "index/unit" used to address individual diff lines) whenever a hunk is expanded or merged with its neighbor, but the function never touches or remaps the user's existing per-line `DiffSelection` state, which was built against the *old* absolute line indices. `formatPatch` and `formatPatchToDiscardChanges` later re-derive `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and query that stale selection object to decide what to include in the patch that is actually applied to the index/working tree. This is structurally identical to the Merit Circle bug: an array (`curve` / `hunks`) is resized, but a derived offset value (`unit` / `unifiedDiffStart`) used elsewhere to interpret that array is not recalculated for the object that depends on it (the selection bitmap), producing silently wrong results.

### Finding Description
- `expandTextDiffHunk` computes `numberOfNewDiffLines` and re-bases every subsequent hunk's `unifiedDiffStart`/`unifiedDiffEnd` by that offset: [2](#0-1)  and [3](#0-2) .
- When a hunk is merged with its adjacent one (`mergeDiffHunks`), lines are dropped/reordered and the offset is adjusted again: [4](#0-3) .
- The function's signature and return value only carry the new `ITextDiff` (`text`, `hunks`, `maxLineNumber`, `hasHiddenBidiChars`) — no selection object is passed in or returned, so there is no mechanism to shift the caller's existing selection to match the new indices: [5](#0-4) .
- The consumer of this shifted indexing is `formatPatch`, which is what actually builds the unified diff applied to the git index when partially staging/committing: it computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` and looks up `file.selection.isSelected(absoluteIndex)` to decide whether an added/deleted line is included: [6](#0-5) .
- `formatPatchToDiscardChanges`, used for discarding a partial selection of lines, does the exact same absolute-index lookup: [7](#0-6) .

Because `unifiedDiffStart` for hunks after the expanded one is only ever incremented by `numberOfNewDiffLines` and never realigned with whatever selection bitmap the UI is holding, any selection state computed prior to a diff expansion becomes misaligned with the new absolute indices once expansion/merging occurs. There is no bounds/consistency check anywhere in `text-diff-expansion.ts` or `patch-formatter.ts` that detects or rejects a selection object whose indices predate the current hunk layout — the same missing-invariant class as the Solidity report, where `curve.length` changed but `unit` was not recalculated and nothing detected the mismatch before `getMultiplier()` used it.

### Impact Explanation
If the mapping between selection indices and hunk content silently desyncs, `formatPatch`/`formatPatchToDiscardChanges` will attribute selection state (include/exclude) computed for one set of lines to a different set of lines after expansion. Because these functions generate the actual patch applied with `git apply` to stage or discard changes, this can cause the user to commit content they did not intend to select (or fail to commit content they did select), which is a silent corruption of what the user commits — the exact impact class called out as valid in the task (attacker controls the content of a fetched/cloned repository and can shape the file so that hunk boundaries/merges shift in the direction that maximizes selection misalignment).

### Likelihood Explanation
Triggering hunk expansion/merging is a normal, low-friction user action (clicking "Expand" on a diff hunk in the "Changes" view), and an attacker who controls the diffed file's content can control the number/spacing of hunks and thus whether/when merges happen during expansion, making the misalignment reproducible. However, I was unable to fully verify — due to index/tool limits — whether the calling component (`side-by-side-diff.tsx`, `changes-list`, etc.) resets or discards the user's line selection whenever the diff is re-expanded, which would mitigate this. I could not locate explicit selection-remapping or selection-reset logic tied to `expandTextDiffHunk`/`expandWholeTextDiff` calls in the portions of `side-by-side-diff.tsx` I was able to inspect, but a full audit of the selection lifecycle (`DiffSelection`, `onIncludeChanged`, and where `file.selection` is reset on diff changes) would be needed to confirm there is no mitigating reset step.

### Recommendation
- When `expandTextDiffHunk`/`expandWholeTextDiff` shift hunk indices, either remap the caller's `DiffSelection` bitmap to the new absolute indices in lockstep, or force a full reset of the selection to a safe default (e.g., "none selected") whenever the diff's hunk layout changes due to expansion/merging.
- Add an invariant check in `formatPatch`/`formatPatchToDiscardChanges` (or in the diff/selection state itself) that verifies the selection's addressable range matches the current diff's total line count before building a patch, refusing to silently proceed on mismatch.

### Proof of Concept
1. Open a large modified file in GitHub Desktop's diff view where the diff has multiple hunks with a small gap between them (smaller than `DefaultDiffExpansionStep`, i.e. 20 lines) — a repository author (attacker, since the content of the file is fully controlled by whoever authored the commits being diffed) can shape the file to guarantee this hunk spacing.
2. Select/deselect specific added or deleted lines for partial staging within the second hunk.
3. Click "Expand" on the first hunk in a direction that causes it to merge with the second hunk (`shouldMergeWithAdjacent` becomes true in `expandTextDiffHunk`, see [8](#0-7) ). This changes `unifiedDiffStart`/`unifiedDiffEnd` for the merged hunk and all following hunks per [9](#0-8) .
4. Stage/commit the partial selection: `formatPatch` recomputes `absoluteIndex` against the new hunk layout and looks up the pre-expansion selection bitmap [6](#0-5) , which — absent any remap/reset step that I could not confirm exists — resolves against indices that no longer correspond to the lines the user actually selected, causing the wrong lines to be included in (or excluded from) the resulting commit.
