## Analog Found [1](#0-0) 

### Title
Unchecked ERC20 boolean return value in escrow withdrawal lets a non-reverting failed transfer still finalize and zero out escrow accounting - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed tokens using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the call itself did not revert, not the ERC20 `transfer` boolean return value. Any token whose `transfer` returns `false` instead of reverting on failure (e.g. blacklist/whitelist-gated tokens, or any non-conforming ERC20) causes escrow accounting and order-completion state to be finalized as if the transfer succeeded, even though no tokens moved.

### Finding Description
`withdraw()` is the internal handler invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` message kinds, and from `onGetResponse()` for cross-chain cancellation settlement: [2](#0-1) [3](#0-2) 

Inside `withdraw()`, for each escrowed token it does: [4](#0-3) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the external call reverted, not whether the token's `transfer()` actually returned `true`. Standard ERC20 tokens are permitted to signal failure by returning `false` without reverting (this is exactly the class of token the original Gearbox report cites — tokens gated by an off-chain whitelist/blacklist, e.g. USDC/USDT-style behavior). In that case `success == true`, the escrow balance `_orders[body.commitment][token]` is decremented, `_filled[body.commitment]` is set to the beneficiary at function entry, and `EscrowReleased`/`EscrowRefunded` is emitted — all while the tokens never left the contract.

Notably, the contract even declares `using SafeERC20 for IERC20;` and could call `.safeTransfer(...)`, which reverts on a `false` return, but this specific path deliberately bypasses that safe wrapper (as also seen identically in the `SweepDust` branch just above it): [5](#0-4) 

This is the same broken invariant as the Gearbox report: the internal accounting update is not gated on the *actual* success of the token movement, only on the absence of a revert.

### Impact Explanation
Once `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set, the order is considered fully settled by the contract's state machine — there is no other code path to retry or recover that specific token amount for that commitment. If the beneficiary address is blacklisted by the escrowed token (or the token otherwise silently returns `false`), the tokens remain permanently locked in the `IntentGatewayV2` contract while the protocol's bookkeeping shows the order as filled/refunded with zero remaining escrow. This is a direct loss/lock of bridged user funds reachable through the normal `RedeemEscrow`/`RefundEscrow`/GET-response cancellation flows — no malicious relayer, prover, or admin action is required.

### Likelihood Explanation
Reaching this requires only that the output/input token used in an intent order is one that returns `false` on failed transfers instead of reverting (a common and well-documented ERC20 quirk, not an exotic assumption — this is precisely the token class the source report is about). An attacker or unlucky solver could construct/select an order whose beneficiary or filler address becomes blacklisted by such a token before settlement, or target chains where such tokens are commonly used as intent assets, silently trapping the escrow.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handling with `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used via `using SafeERC20 for IERC20`), so any `false` return value reverts the transaction instead of allowing escrow accounting to finalize on a no-op transfer.

### Proof of Concept
1. Create/fill an order whose escrowed token is an ERC20 that returns `false` (rather than reverting) when `transfer()` is denied for the recipient (e.g., a blacklist-style token, matching the case described in the source report).
2. Have the destination-side `RefundEscrow`/`RedeemEscrow` message (or the `onGetResponse` cancellation path) resolve to a beneficiary that the token denies.
3. `withdraw()` executes: `token.call(...)` returns `(true, encodedFalse)`; `success` is `true` so no revert occurs.
4. `_orders[body.commitment][token] -= amount` runs, `_filled[body.commitment]` is set, and `EscrowReleased`/`EscrowRefunded` fires — while the beneficiary received nothing and the tokens sit unspendable in the contract with no remaining accounting entry to trigger a re-send.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
