## Finding: Division-by-zero panic in `EVMMempoolIterator.extractCosmosEffectiveTip`

The external report's bug class is "unbounded/zero-value parameter used as a divisor causing revert/DoS." Searching the Cosmos EVM mempool code for the same anti-pattern (a value taken from user-controlled input used directly as a divisor without a zero-check) surfaces `extractCosmosEffectiveTip` in the EVM/Cosmos unified mempool iterator. [1](#0-0) 

### Finding Description
`extractCosmosEffectiveTip` computes the effective gas price of a pending Cosmos-native transaction as `fee_amount / gas_limit`:

```go
gasPrice, overflow := uint256.FromBig(bondDenomFeeAmount.Quo(math.NewIntFromUint64(feeTx.GetGas())).BigInt())
``` [2](#0-1) 

`feeTx.GetGas()` is the transaction's declared gas limit, taken directly from the (attacker-supplied) `AuthInfo.Fee.GasLimit` field of the signed transaction. `cosmossdk.io/math.Int.Quo` wraps `big.Int.Quo`, which **panics** when the divisor is zero (Go's `math/big` semantics: `ErrDivideByZero`). If `GetGas()` returns `0`, this line panics.

Tracing the admission path for Cosmos-native transactions in `newCosmosAnteHandler`: [3](#0-2) 

None of the chained decorators reject a zero gas limit for a plain Cosmos transaction:
- `ante.NewValidateBasicDecorator()` — the standard Cosmos SDK `Tx.ValidateBasic()` does not require `Fee.GasLimit > 0`.
- `cosmosante.NewMinGasPriceDecorator` — short-circuits entirely when `MinGasPrice` is zero (the default), before ever looking at `gas`: [4](#0-3) 
- `ante.NewDeductFeeDecorator` — only validates that the coins provided cover the computed fee; with `GasLimit = 0` and `Fee = 0` coins this is trivially satisfied.
- `evmante.NewGasWantedDecorator` (`CheckGasWanted`) — only checks `gasWanted > blockGasLimit`; `gasWanted == 0` passes this check trivially and even skips the `AddTransientGasWanted` call path logic that would otherwise touch gas accounting: [5](#0-4) 

So a Cosmos-native transaction (e.g., `MsgSend`) with `GasLimit = 0` and zero/no fee can pass the full ante chain and be admitted into the Cosmos-side mempool. Once such a transaction is present, every subsequent call to `EVMMempoolIterator.Tx()` / `Next()` (invoked during `PrepareProposal`/block building on every validator) calls `getNextCosmosTx()` → `extractCosmosEffectiveTip()`, which panics on `Quo` by zero.

### Impact Explanation
Because block proposal/iteration logic runs identically on every validator node processing the same mempool content, an unprivileged user broadcasting a single zero-gas transaction can trigger a deterministic panic in the mempool iterator used during block production. If this panic is not recovered up the call stack before it reaches consensus-critical block-building code, it results in a **chain-wide halt** — every honest validator attempting to build/verify a block containing (or considering) this transaction crashes or fails deterministically. This matches the in-scope "Critical chain halt ... triggered through ordinary transaction ... flow" impact class, analogous to how `NarwhalPool`'s unchecked `rewardsDuration` divisor caused a hard failure of core contract logic once a boundary value was supplied.

### Likelihood Explanation
The trigger is a single, ordinary, unprivileged transaction — a standard bank-send (or any `sdk.FeeTx`) with `GasLimit` set to `0`. No special privileges, governance action, or malicious validator/relayer collusion is required. The only uncertainty is whether the panic is caught by a `recover()` somewhere between `Tx()/Next()` and the ABCI `PrepareProposal`/`ProcessProposal` boundary (I could not locate such a recover wrapper around the mempool iterator invocation in the code retrieved) — if a recover exists at that layer, the impact would degrade to an isolated proposal failure/liveness stall for the affected proposer rather than a full determinism/AppHash issue. **I was not able to fully confirm the presence/absence of a top-level recover around block-proposal mempool iteration within the indexed code**, so this should be verified in a live/`session` environment before treating it as fully confirmed Critical.

### Recommendation
In `extractCosmosEffectiveTip` (and any other location where `feeTx.GetGas()` or similarly attacker-controlled divisors are used), add an explicit zero-check before dividing, e.g.:
```go
gas := feeTx.GetGas()
if gas == 0 {
    return nil // or uint256.NewInt(0)
}
gasPrice, overflow := uint256.FromBig(bondDenomFeeAmount.Quo(math.NewIntFromUint64(gas)).BigInt())
```
Additionally, consider enforcing `GasLimit > 0` as part of ante-handler validation for all Cosmos-native transactions, consistent with the EVM-side `gas.IsZero()` check already present in `FeeChecker`: [6](#0-5) 

### Proof of Concept
1. Construct and sign a standard Cosmos SDK transaction (e.g. `MsgSend`) with `Fee.GasLimit = 0` and `Fee.Amount = []` (or a denom not equal to bond denom, to bypass `MinGasPriceDecorator`'s `validFees` check trivially since `MinGasPrice` defaults to zero and short-circuits regardless).
2. Broadcast it via `CheckTx`; trace through `newCosmosAnteHandler` decorators — confirm none reject `GasLimit = 0`.
3. Once accepted into the Cosmos mempool, on the next block-building cycle the node calls into `EVMMempoolIterator.Tx()`/`Next()`, which invokes `getNextCosmosTx()` → `extractCosmosEffectiveTip(tx)`.
4. `bondDenomFeeAmount.Quo(math.NewIntFromUint64(0))` panics with `division by zero`, crashing (or, if a recover exists, corrupting) the block-proposal routine on every validator that has this tx in its mempool.

**Note:** I could not fully verify from the indexed files whether a `recover()` wraps mempool iteration during `PrepareProposal`, which affects whether this manifests as a full chain halt versus a per-node liveness issue. If more certainty is needed, a Devin session with full repository/runtime access should trace the ABCI `PrepareProposal` call chain end-to-end and reproduce this with a live testnet.

// extractCosmosEffectiveTip extracts the effective gas tip from a Cosmos transaction
// This aligns with EVM transaction prioritization by calculating: gas_price - base_fee
func (i *EVMMempoolIterator) extractCosmosEffectiveTip(tx sdk.Tx) *uint256.Int {
	feeTx, ok := tx.(sdk.FeeTx)
	if !ok {
		i.logger.Debug("Cosmos transaction doesn't implement FeeTx interface")
		return nil // Transaction doesn't implement FeeTx interface
	}

	bondDenomFeeAmount := math.ZeroInt()
	fees := feeTx.GetFee()
	for _, coin := range fees {
		if coin.Denom == i.bondDenom {
			i.logger.Debug("found fee in bond denomination", "denom", coin.Denom, "amount", coin.Amount.String())
			bondDenomFeeAmount = coin.Amount
		}
	}

	// Calculate gas price: fee_amount / gas_limit
	gasPrice, overflow := uint256.FromBig(bondDenomFeeAmount.Quo(math.NewIntFromUint64(feeTx.GetGas())).BigInt())
	if overflow {
		i.logger.Debug("overflowed on gas price calculation")
		return nil
	}
```

func CheckGasWanted(ctx sdk.Context, feeMarketKeeper anteinterfaces.FeeMarketKeeper, tx sdk.Tx, isLondon bool, feemarketParams *feemarkettypes.Params) error {
	if !isLondon {
		return nil
	}

	feeTx, ok := tx.(sdk.FeeTx)
	if !ok {
		return nil
	}

	gasWanted := feeTx.GetGas()

	// return error if the tx gas is greater than the block limit (max gas)
	blockGasLimit := types.BlockGasLimit(ctx)
	if gasWanted > blockGasLimit {
		return errorsmod.Wrapf(
			errortypes.ErrOutOfGas,
			"tx gas (%d) exceeds block gas limit (%d)",
			gasWanted,
			blockGasLimit,
		)
	}
