### Title
Unbounded future oracle timestamp permanently poisons the per-feed monotonic freshness gate, freezing price resolution - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s `oracle-timestamp-fresh` function is meant to do what `BackingManager.tradeEnd` does in the Reserve report: gate a future action using a stored timestamp so nothing "stale" or "already processed" happens again. Here the gate is the per-feed `last-update` map, which is supposed to only move forward when a genuinely newer, valid price arrives. Because the freshness check clamps any timestamp greater than the current block time to a zero staleness delta, a future-dated `publish-time` is accepted unconditionally and is then written into `last-update` as the new floor. Just like `tradeEnd` being set too far into the future blocked the next Dutch auction for up to a week, an inflated `last-update` value blocks every subsequent (correct, real-time) price update for that feed until real chain time catches up to the erroneous stored value - freezing borrow/repay/liquidation flows that depend on that asset's price.

### Finding Description
`oracle-timestamp-fresh` and `price-resolve` implement the freshness/monotonicity gate: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

`delta` is defined as `0` whenever the oracle-reported `publish-time` (`ts`) is greater than the current `stacks-block-time`. That branch makes the `<= delta max-staleness` staleness check trivially true for *any* future timestamp, no matter how far ahead it is — there is no upper bound on how far into the future `ts` may be. `price-resolve` then unconditionally advances the ratchet: [2](#0-1) 

```clarity
(define-private (price-resolve ...)
  ...
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```

Once a `timestamp` value ahead of the true chain time is accepted and written to `last-update`, every future call for the same `{type, ident}` feed key must satisfy `(>= ts prev)` where `prev` is now this inflated value. Any subsequent genuinely correct `publish-time` (which, by definition, tracks real wall-clock/chain time and therefore will be *less* than the erroneous stored value) fails the monotonicity check and the whole call reverts with `ERR-ORACLE-INVARIANT`. There is no admin/DAO function found in `mainnet/contracts/market/v0-4-market.clar` that clears or resets entries in the `last-update` map, so the feed remains gated until real time simply catches up to the bad stored timestamp.

This is structurally identical to the Reserve `tradeEnd` bug: a state value meant to prevent double-processing/out-of-order events is set from an externally supplied value without an upper bound, and once inflated it blocks all subsequent legitimate operations for an extended, sometimes very long, period — the exact "monotonic per-feed timestamp" failure mode called out as in-scope.

### Impact Explanation
Every sensitive action that needs a price for the affected asset — `borrow`, `withdraw`, `repay`-triggered health checks, and liquidation — routes through `price-resolve`/`price-multi-resolve`. If the ratchet for one feed becomes poisoned, all of those operations revert with `ERR-ORACLE-INVARIANT` for that asset until the stored future timestamp is naturally surpassed by real time. Depending on how far ahead the accepted timestamp is, this can freeze user funds (inability to withdraw, repay, or be liquidated normally) for the asset in question — a temporary freezing-of-funds impact, matching the Reserve report's own conclusion (confirmed Medium/mitigated) about `tradeEnd` blocking Dutch auctions for up to a week.

### Likelihood Explanation
The trigger condition (`ts > stacks-block-time`) requires only clock skew or an out-of-order/ahead-of-time `publish-time` from the upstream feed relative to the Stacks chain clock — not a compromise of the DAO, oracle governance, or a malicious price value. The check as written treats "future" timestamps as automatically fresh instead of rejecting them, which is a logic defect local to `oracle-timestamp-fresh`/`price-resolve` in this contract, independent of whether the upstream price itself is correct.

### Recommendation
Reject timestamps that are ahead of `stacks-block-time` (or bound the allowed forward skew to a small explicit tolerance) instead of clamping `delta` to `0`:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)          ;; reject future timestamps outright (or allow a small explicit tolerance)
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
Additionally, provide a DAO-gated recovery path to reset a poisoned `last-update` entry for a given `{type, ident}` key so operators are not solely dependent on waiting out an erroneous future timestamp.

### Proof of Concept
1. A price update for feed `{type: TYPE-PYTH, ident: STX_FEED}` arrives with `publish-time = T + N` where `N` is large and `T` is the current `stacks-block-time`.
2. `oracle-timestamp-fresh` computes `delta = 0` (because `ts > stacks-block-time`), so `(<= delta max-staleness)` passes trivially, and `(>= ts prev)` passes since `ts` is the largest seen value.
3. `price-resolve` accepts the price and executes `(map-set last-update key (T + N))`.
4. On the next legitimate call, the real oracle timestamp `ts' ≈ current stacks-block-time < T + N`, so `(>= ts' prev)` fails, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT`.
5. Any `borrow`, `withdraw`, `repay`, or liquidation call requiring this asset's price now reverts until real chain time exceeds `T + N`, freezing the corresponding funds/positions for that duration.
