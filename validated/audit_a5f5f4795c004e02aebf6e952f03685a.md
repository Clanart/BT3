### Title
Payout tx's SIGHASH_SINGLE|ANYONECANPAY witness lets a third party malleate the OP_RETURN operator-pubkey output via RBF, permanently blocking the honest operator's reimbursement - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the `Payout` tx with a single key-spend input signed by the user with `TapSighashType::SinglePlusAnyoneCanPay`, and this signature is verified and reused byte-for-byte by `Operator::withdraw`. Because BIP341 `SIGHASH_SINGLE|ANYONECANPAY` only commits to the input being spent and the output at the same index (vout 0), the anchor (vout 1) and OP_RETURN (vout 2, carrying the operator's xonly pubkey) are unauthenticated and can be freely replaced by anyone who observes the unconfirmed tx, then RBF'd to confirmation with a different fee split.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk` (recorded by `Verifier::update_finalized_payouts`) **should equal** the xonly pubkey of the operator whose funds actually paid `output_txout` at vout 0 of the confirmed payout tx, i.e. `payout_payer_operator_xonly_pk == kickoff_data.operator_xonly_pk` for the operator that fronted the withdrawal.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds outputs `[user_payout, anchor, OP_RETURN(operator_xonly_pk)]` and signs input 0 with `SpendPath::KeySpend` using the user-supplied `taproot::Signature` (`in_signature`), whose `sighash_type` is `SinglePlusAnyoneCanPay` (enforced only by the error message in `Operator::withdraw`, `core/src/operator.rs:630-637`, not by any consensus-level restriction on which sighash flag is accepted).
- `TxHandler::calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-233`) computes the sighash for `SinglePlusAnyoneCanPay` using `Prevouts::One(txin_index, ..)`. Per BIP341, `SIGHASH_SINGLE` only hashes the single output at the same index as the signed input (vout 0), and `ANYONECANPAY` only commits to the one input being spent — the anchor (vout 1) and OP_RETURN (vout 2) bytes are **not** part of the signed message.
- `TransactionType::Payout` is queued with `FeePayingType::RBF` (`core/src/tx_sender_queue.rs:92-104`), so the honest operator's own tx sender explicitly signals opt-in RBF (BIP125) for this tx type — anyone observing it in the mempool can broadcast a conflicting tx spending the same `input_utxo.outpoint`, keep vout 0 (`output_txout`) and the copied witness identical (since the signature remains valid for that exact vout 0 and input), but rewrite vout 2's OP_RETURN payload (or vout 1's anchor amount, to raise the fee) and get it accepted as an RBF replacement, since BIP125 rule 2 (no new unconfirmed inputs) and rule 3/4 (higher absolute fee and feerate) are satisfiable purely by shrinking the anchor output.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) does not track which specific txid the operator submitted; it queries `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`), which joins on `bitcoin_syncer_spent_utxos` keyed only by `withdrawal_utxo_txid`/`vout` — i.e., **whichever transaction actually spends the withdrawal UTXO on chain** is treated as canonical, regardless of whether it's the operator's original broadcast or the attacker's malleated replacement. It then extracts the operator pubkey via `get_first_op_return_output` + `parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:608-617, 686-692`) from that confirmed tx and stores it via `update_payout_txs_and_payer_operator_xonly_pk`.
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) later compares `kickoff_data.operator_xonly_pk` (submitted by the honest operator A in its kickoff) against the DB-recorded `operator_xonly_pk_opt`. If the attacker replaced the OP_RETURN with a different/garbage pubkey, this comparison fails (or is `None`), and `is_kickoff_malicious` returns `true` even though operator A genuinely funded output 0.
- No existing guard closes this gap: `Operator::is_profitable` and `SECP.verify_schnorr` only check output 0's value/signature validity, not the immutability of vouts 1–2; there is no database uniqueness/txid-pinning constraint tying a withdrawal index to the specific payout txid the operator broadcast before confirmation.

### Impact Explanation
An unprivileged party can, for any withdrawal an operator fronts, cause the confirmed payout tx's OP_RETURN to no longer match the fronting operator's pubkey. This makes `is_kickoff_malicious` return `true` for the honest operator's subsequent kickoff, which (per `Verifier::handle_kickoff`, `core/src/verifier.rs:1966-2027`) triggers a `Challenge` tx against that operator, and can lead to `Disprove`, burning the operator's collateral for a legitimate reimbursement it is entitled to. This is repeatable per withdrawal/operator since it only requires observing a broadcast, unconfirmed `Payout` tx (which is queued via RBF specifically to allow fee-bumping and thus signals replaceability) — matching the Critical category "an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned."

### Likelihood Explanation
Preconditions are minimal and match the attacker capability model: the attacker only needs to (1) watch the Bitcoin mempool for a `Payout` tx (public), (2) copy the exact input, keyspend witness, and vout-0 output bytes (no cryptographic capability required since these are untouched by the sighash), (3) rewrite vout 2 (and optionally shrink vout 1) to increase the fee, and (4) broadcast it as an RBF replacement with sufficient fee/feerate per BIP125. This requires no signing key, no verifier/operator role, and only the cost of the marginal fee bump needed to win the RBF race — cheap relative to the collateral burned. It's deployable against any operator's payout on any withdrawal and directly enabled by Clementine's own choice to send `Payout` via `FeePayingType::RBF`.

### Recommendation
Do not derive the operator-payer binding from mutable, unauthenticated outputs of the confirmed payout transaction. Either (a) have the user's signature cover all outputs (e.g. sign with `SIGHASH_ALL` or `SIGHASH_ALL|ANYONECANPAY` instead of `SIGHASH_SINGLE|ANYONECANPAY`) so the OP_RETURN and anchor cannot be altered without invalidating the signature, or (b) have the operator additionally commit to the exact payout txid/OP_RETURN payload off-chain (e.g., recorded before broadcast and matched by txid rather than solely by "whichever tx spent the withdrawal UTXO"), or (c) bind the operator's payer identity to something the user's signature actually authenticates (e.g., include the operator pubkey in the signed output/script rather than an unsigned OP_RETURN).

### Proof of Concept
`cargo test` plan (in a Devin-executable, non-mainnet, non-live-Citrea regtest environment):
1. Set up regtest via existing test scaffolding (`create_test_config_with_thread_name`, `create_regtest_rpc`, `MockCitreaClient`) as in `core/src/test/deposit_and_withdraw_e2e.rs`.
2. Run a single deposit and register a withdrawal (`run_single_deposit`, `insert_withdrawal_utxo`), generate the user signature with `generate_withdrawal_transaction_and_signature` (`SinglePlusAnyoneCanPay`).
3. Call `Operator::withdraw` for operator A; capture the resulting `Transaction` before it confirms (do not mine it yet).
4. Construct a "malicious" replacement transaction: same `TxIn` (same outpoint, same witness bytes copied verbatim), same vout 0 `TxOut`, but a different vout 2 OP_RETURN payload (either a different `XOnlyPublicKey::serialize()` or garbage bytes) and a reduced-value anchor output at vout 1 to raise the fee above operator A's original tx (satisfying BIP125 rules).
5. Broadcast the replacement via `rpc.send_raw_transaction`, assert it displaces A's original tx in the mempool (`test_mempool_accept`/`getrawmempool`), then mine it into a block.
6. Run the verifier's block-finalization path (`handle_finalized_block` → `update_finalized_payouts`) against this block.
7. Assert `db.get_payout_info_from_move_txid` returns `operator_xonly_pk_opt` that is either `None` or not equal to operator A's xonly pk.
8. Drive operator A's kickoff to the point where `Verifier::is_kickoff_malicious` (or `handle_kickoff`) is invoked with `kickoff_data.operator_xonly_pk == A`; assert it returns `true`, i.e., a `Challenge` tx is queued against operator A despite A's UTXO having genuinely funded vout 0 of the confirmed payout.
