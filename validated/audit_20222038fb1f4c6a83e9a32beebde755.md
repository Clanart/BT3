### Title
FROST nonce reuse via re-signing from a persistent `CachedPreprocess` leaks the MuSig validator key share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores the FROST preprocess seed (`CachedPreprocess`) in the DB keyed only by `context` and never deletes or rotates it. Every call to `share_internal` regenerates a fresh `AlgorithmSignMachine` from the *same* seed, reproducing identical nonces (`seeded_preprocess` uses `ChaCha20Rng::from_seed(*seed.0)`). `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal`, and `share` can be invoked multiple times per attempt. This is the direct analog of the use-after-free bug class: a signing "session object" (the nonce material) is reused after its logical lifetime ended, because the cached state is resurrected instead of consumed.

### Finding Description
- `preprocess_internal` only generates a new preprocess when `CachedPreprocesses::get(txn, &self.context)` is `None`; afterwards the same entry is decrypted and reused for every subsequent call (`signing_protocol.rs:123-145`). The cache entry is never removed after `sign` succeeds.
- `DkgConfirmer::share` calls `share_internal` which calls `preprocess_internal` then `machine.sign(preprocesses, msg)` (`signing_protocol.rs:150-180`, `288-310`). `DkgConfirmer::complete` calls `share_internal` *again* to rebuild the machine (`signing_protocol.rs:312-327`), performing a second `sign` with identical nonces.
- In FROST, the signature share is `s = d + e·rho + λ·x·c` where `d + e·rho` is the nonce and `c` the challenge. The binding factors `rho` and challenge are derived from the message (`C::hash_msg(msg)` into `rho_transcript`, `sign.rs:362-379`) and from the peer preprocess set (`commitments.transcript(...)`, `sign.rs:348-356`), both of which are attacker-influenced: `preprocesses` are raw bytes supplied by other validators via `read_preprocess`, and `msg` varies with `key_pair`/`removed`. Two `share()` invocations with different preprocess sets or different `key_pair`s therefore produce `s1 = k + c1·x'` and `s2 = k + c2·x'` with identical `k` but different `c`, yielding `x' = (s1 - s2)/(c1 - c2)` — the secret share.
- The file's own header acknowledges this hazard: nonce reuse across distinct received messages is unsafe, and a `TODO` at line 53 notes processor preprocess handling still needs review. The safety argument (lines 34-48) relies on BFT guaranteeing identical messages — but it does not protect against `share`/`complete` both signing, nor against multiple `share()` calls with different `preprocesses`/`key_pair` inputs.

### Impact Explanation
Two published signature shares computed under the same nonce with distinct challenges allow any holder (a peer validator who receives the broadcast shares) to algebraically recover the coordinator's MuSig secret share — i.e., the validator's root-of-trust key used to confirm DKG results on Substrate. This is full key share recovery, the most severe outcome in scope. Even the re-sign inside `complete` is dangerous if the coordinator's share publication path differs between the `share` and `complete` flows.

### Likelihood Explanation
Reachable by an unprivileged peer: the `preprocesses` argument to `share` originates from other validators' preprocess messages (untrusted bytes parsed via `read_preprocess`). A peer that causes the coordinator to evaluate `share` under two distinct valid preprocess sets — or a `share` plus a later `complete` where the message changed (e.g., a different `key_pair` or `removed` set for the same `attempt` context) — obtains two shares under identical nonces. Since the `CachedPreprocess` is keyed only by `(b"DkgConfirmer", attempt)`, all sign operations within an attempt deterministically reuse the nonce.

### Recommendation
Treat `CachedPreprocess` as single-use: delete the `CachedPreprocesses` entry before calling `machine.sign(...)`, failing closed if the entry is absent (or caching the produced `AlgorithmSignMachine`/share for reuse instead of re-signing). `complete` should reuse the share produced by `share` rather than re-running `share_internal`. Alternatively, track a "spent" flag per context so a second `sign` under the same seed is rejected.

### Proof of Concept
Conceptual: with `context = (b"DkgConfirmer", attempt)` fixed,
1. `share(preprocesses_A, key_pair)` → `sign` with nonces `k`, produces `s1 = k + c_A·x'` (msg `m_A`, binding factors from set A).
2. `share(preprocesses_B, key_pair)` with a distinct valid peer preprocess set → `sign` with the same `k`, produces `s2 = k + c_B·x'`.
3. `x' = (s1 - s2)·(c_A - c_B)^-1` recovers the lagrange-scaled secret share; dividing by the public Lagrange coefficient recovers the raw share. The same holds for `share` followed by `complete` whenever the message differs between the two invocations.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
