### Title
Future-dated oracle timestamp bypasses staleness gate and permanently freezes price feed via monotonic ratchet - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` in `market.clar` treats any oracle timestamp greater than `stacks-block-time` as automatically "fresh" (`delta = u0`), with no upper bound on how far in the future it may be. Combined with the monotonic per-feed ratchet (`last-update` map, updated whenever a new timestamp is greater than the stored one), a single forward-dated price update permanently blocks all subsequent legitimate price resolutions for that asset, freezing borrow/repay/liquidation flows that depend on it.

### Finding Description
`oracle-timestamp-fresh` computes staleness only in the backward direction: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

If `ts > stacks-block-time` (a future-dated publish time), `delta` is forced to `u0`, which always satisfies `<= max-staleness` regardless of how far in the future `ts` is. This is the exact same bug class as the referenced report's missing bound check on a caller-supplied timestamp (`_startTimestamp` never validated against `block.timestamp`): here the bound check on the oracle-supplied `timestamp` is only enforced in one direction, leaving the "future" direction completely unchecked.

This future timestamp is then accepted by `price-resolve` and persisted as the new high-water mark for that feed: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let (...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Once a forward-dated `timestamp` is stored in `last-update`, every subsequent genuine price update carries the real, smaller `ts`. The monotonic check `(>= ts prev)` then fails permanently (until real wall-clock time catches up to the injected future value, which can be arbitrarily far away), so `oracle-timestamp-fresh` returns `false` and `price-resolve` reverts with `ERR-ORACLE-INVARIANT` for every future call on that feed. There is no recovery path in `market.clar` to reset or override `last-update` for a feed.

This is directly analogous to the report's root cause: a timestamp field accepted by the contract with a check that is only one-directional (only rejecting "too old", never rejecting "too far ahead"), which then gets locked into contract state with no way to unwind it, permanently disabling functionality that depends on it. This maps to the explicitly allowed "monotonic per-feed timestamp" analog class in scope for this scan.

### Impact Explanation
Any asset whose price feed becomes stuck in this state can no longer have its price resolved: `price-resolve` reverts with `ERR-ORACLE-INVARIANT`, and every downstream operation that needs that asset's price (borrow, repay, withdraw collateral, and — critically — liquidation health checks) reverts as well. This is a temporary (potentially very long, depending on the size of the injected future timestamp) freezing of user funds/positions denominated in or collateralized by that asset, which lands in the in-scope "temporary freezing of funds" impact class. Because health checks for the asset become unresolvable, liquidations of unhealthy positions collateralized in the affected asset can also be blocked, compounding protocol risk.

### Likelihood Explanation
Triggering requires only one price update from Pyth or DIA to carry a `publish-time`/`timestamp` value ahead of the local `stacks-block-time` — this can occur from normal clock skew between the oracle network and the Stacks chain, from DIA's millisecond-to-second conversion rounding, or from a malicious/compromised relay pushing an inflated timestamp once. The Zest code itself never bounds `ts` against a reasonable future window, so the trigger condition does not require any control over collateral, egroup, or DAO configuration — it is purely a gap in `oracle-timestamp-fresh`'s own validation logic, keeping it in scope per the "bug in THIS code" carve-out even though the triggering timestamp originates from an external oracle call.

### Recommendation
Bound `ts` on both sides in `oracle-timestamp-fresh`, e.g. reject timestamps that exceed `stacks-block-time` by more than a small tolerance (clock-skew allowance) instead of clamping `delta` to `u0`:

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((future-tolerance u30)) ;; seconds
    (and
      (<= ts (+ stacks-block-time future-tolerance))
      (<= (if (> ts stacks-block-time) u0 (- stacks-block-time ts)) max-staleness)
      (>= ts prev))))
```
Additionally, provide a DAO-governed recovery/reset function for `last-update` per feed so an accidentally or maliciously inflated timestamp can be corrected without permanently bricking the feed.

### Proof of Concept
1. Pyth (or DIA) reports a price for asset `X` with `publish-time` (timestamp) `T_future`, where `T_future >> stacks-block-time` (e.g., due to relay bug, clock skew, or a compromised feed briefly emitting a bad timestamp).
2. `price-resolve` calls `oracle-timestamp-fresh(T_future, prev, max-staleness)`; since `T_future > stacks-block-time`, `delta = u0 <= max-staleness`, and `T_future >= prev`, so the check passes.
3. `map-set last-update key T_future` stores the inflated timestamp as the feed's high-water mark.
4. On the next real block, the oracle reports a legitimate price with real timestamp `T_real < T_future`.
5. `oracle-timestamp-fresh(T_real, T_future, max-staleness)` now fails the `(>= ts prev)` monotonic check, so `price-resolve` returns `ERR-ORACLE-INVARIANT`.
6. All operations needing asset `X`'s price (borrow, repay, liquidation health checks) revert until real time advances past `T_future`, freezing any position depending on that asset.
