### Title
Fee/weight estimation omits the OP_RETURN data output, producing transactions that underpay the minimum relay fee and fail to broadcast - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an arbitrary `data` payload which is appended as an OP_RETURN output, but the weight/vbyte calculation used to derive `needed_fee` is computed only over `payments`, excluding the OP_RETURN output. The resulting transaction is larger than estimated, so the effective fee rate falls below the caller-specified `fee_per_vbyte` and can fall below the Bitcoin minimum relay fee even though the `TooLowFee` check passed, yielding a transaction that cannot be relayed/confirmed — the same failure class as the hardcoded gas limit bug (an underestimate of the resources a transaction actually consumes).

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` before computing the fee:

- The data output is added at `send.rs:194-202`.
- Weight/vbytes are computed at `send.rs:204` via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — note `payments`, not `tx_outs`, is passed.
- `calculate_weight_vbytes` (`send.rs:62-127`) builds the estimation transaction solely from `payments` plus an optional `change` output; it never sees the OP_RETURN output.
- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) and the minimum-relay check at `send.rs:211` therefore use a vbyte count that omits up to ~90 bytes of OP_RETURN output.
- The change path repeats the same call at `send.rs:225-226`, so `fee_with_change` is also understated.

Since `fee()` is defined as `sum(inputs) - sum(outputs)` (`send.rs:138-141`), when no change output is created the leftover is paid as fee and the *absolute* fee is fine, but the *rate* may be below what the caller requested. More critically, when change exists, the change amount is computed as `input_sat - payment_sat - fee_with_change` where `fee_with_change` is based on the understated vbytes — the signed transaction's true fee rate is `(input - outputs) / actual_vsize`, which is lower than `fee_per_vbyte` and, for a ~90-byte OP_RETURN on a small transaction, can drop below `DEFAULT_MIN_RELAY_TX_FEE` (1000 sat/kvB) even though the check at `send.rs:211` passed against the understated `vbytes`.

### Impact Explanation
An unprivileged caller supplying `data` (the documented API purpose of the `data` parameter) can produce a signed transaction whose real fee rate is below the network's minimum relay fee. The transaction is then rejected by Bitcoin nodes / never propagates — a failed transaction, directly analogous to transactions failing due to underestimated gas. Where change is present, the underestimate also silently burns less-than-intended fee while returning change computed against the wrong fee target; combined with the dust check at `send.rs:229` this can also alter whether a change output is created at all. Severity: Medium (transaction fails to relay; no direct theft, but funds become temporarily locked in a non-propagating signed transaction and the behavior is silently incorrect).

### Likelihood Explanation
Deterministic whenever `data` is provided and the resulting true fee rate falls below the relay minimum or below `fee_per_vbyte`. The OP_RETURN output adds roughly `9 + data_len` bytes; with data near the 80-byte cap, that is ~90 vbytes omitted from the denominator on a transaction whose total size may only be a few hundred vbytes — easily enough to push a 1 sat/vB fee below relay minimum for a minimally-funded transaction.

### Recommendation
Include the OP_RETURN output in the estimation transaction inside `calculate_weight_vbytes` — e.g. pass the fully-built `tx_outs` (or `data: Option<&[u8]>`) to the function so weight is computed over the actual output set, in both the no-change (`send.rs:204`) and change (`send.rs:225`) calls. Alternatively, construct the candidate `Transaction` once and compute `tx.weight()` on it directly rather than maintaining a parallel estimation structure that can diverge from the real transaction.

### Proof of Concept
```rust
// Conceptual: networks/bitcoin wallet test
let inputs = vec![output]; // funded ReceivedOutput
let payments = vec![(p2tr_script_buf(key).unwrap(), 1000)];
let data = vec![0u8; 80]; // max allowed

let tx = SignableTransaction::new(inputs, &payments, None, Some(data.clone()), 1).unwrap();
// needed_fee was computed WITHOUT the ~90-byte OP_RETURN output
let needed = tx.needed_fee();
// Actual signed tx includes the OP_RETURN output:
//   actual_vsize = estimated_vsize + ~90
//   actual feerate = needed / actual_vsize < 1 sat/vB
// => falls under DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB) despite the
//    TooLowFee check at send.rs:211 having passed; send_raw_transaction is
//    rejected by the mempool.
```
Root cause: `send.rs:204` and `send.rs:225` pass `payments` to `calculate_weight_vbytes` while the OP_RETURN output added at `send.rs:194-202` is excluded from the weight estimate.
