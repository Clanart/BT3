### Title
Unauthenticated OP_RETURN operator-attribution in payout transactions lets an outsider redirect bridge reimbursement to an arbitrary operator - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The user's withdrawal authorization signature only commits to the payout input and its matching output (`SinglePlusAnyoneCanPay`), never to the `OP_RETURN` output that names which operator "fronted" the withdrawal. Verifiers blindly trust whatever xonly-pubkey appears in that unsigned `OP_RETURN` byte string to decide which operator is credited with having funded the payout and is therefore allowed to kick off the reimbursement flow. Anyone who can construct a valid alternative payout transaction (paying the same required user output, as forced by the sighash) can insert any operator's pubkey they like into the `OP_RETURN`, hijacking that operator's reimbursement/kickoff machinery for a payout they never authorized or funded — the same "commitment doesn't bind the privileged party" class of bug as the auction crowdfund report, where any third party could out-bid on the party's behalf because the contract never verified *who* was allowed to act.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user's payout, an anchor, and an `OP_RETURN` containing the caller-supplied `operator_xonly_pk`: [1](#0-0) 

The only thing that authorizes spending the withdrawal UTXO is the user's Schnorr signature, and the protocol explicitly requires this signature to use `SinglePlusAnyoneCanPay`: [2](#0-1) 

`SIGHASH_SINGLE | ANYONECANPAY` only commits to input index 0 and the output at the *same* index (the user's payout output) — it says nothing about output 1 (anchor) or output 2 (`OP_RETURN`/operator identity), and `ANYONECANPAY` explicitly allows adding/replacing other inputs and outputs freely: [3](#0-2) [4](#0-3) 

Once any valid payout transaction spending the withdrawal UTXO is visible (e.g. broadcast to the mempool by an honest operator, or reconstructed from a leaked/observed signature), anyone can build a competing transaction with the identical required output for the user (satisfying the `SIGHASH_SINGLE` commitment) but with a *different* `OP_RETURN` payload naming a different — or arbitrary — operator xonly-pubkey, and get it confirmed instead (via RBF/fee bump) since none of that data is signed.

Verifiers then take whatever `OP_RETURN` value ends up on-chain at face value with no additional authentication check: [5](#0-4) 

This value is persisted as `payout_payer_operator_xonly_pk` and is the sole key used by an operator's automation to decide "this payout is mine to reimburse": [6](#0-5) 

The `PayoutCheckerTask` picks up any such "unhandled payout" attributed to the operator's own key and automatically drives the kickoff → reimbursement flow for it, without any confirmation that the named operator actually broadcast or funded that specific transaction: [7](#0-6) [8](#0-7) 

**Binding broken:** *the operator credited (and whose kickoff/reimbursement slot is consumed, and who is eligible to receive the vault's `reimburse_tx` payout) must equal the party that actually fronted the withdrawal.* Because the `OP_RETURN` operator-identity field is not covered by the withdrawal-authorizing signature, an unprivileged party — who need not hold any operator key or role — can break this equality by fabricating the on-chain attribution.

### Impact Explanation
This directly matches the Critical impact category "an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed." An attacker who funds a competing payout transaction (still paying the withdrawing user correctly, so no funds are stolen from the user) can name an arbitrary registered operator's pubkey in the `OP_RETURN`. That operator's automation will then autonomously consume one of its kickoff connectors for the round and attempt to claim `reimburse_tx` from the vault for money it never actually spent — either enabling an uninvolved operator to be paid from the vault for a payout someone else funded (a genuine bridge value leak, since the true funder receives nothing back), or, if the attacker instead names a non-existent/unintended operator key, permanently orphaning that withdrawal's reimbursement path and consuming/burning that operator's per-round kickoff/collateral slot on a payout it never chose to service.

### Likelihood Explanation
The precondition is only that a valid payout transaction (or its user signature) becomes observable before it confirms — an ordinary consequence of the fact that Bitcoin transactions are visible in the mempool before confirmation, and that the withdrawal UTXO's presigned authorization uses `ANYONECANPAY`, which is explicitly designed to allow third parties to add inputs/outputs. No verifier, operator, watchtower, or key compromise is required by the attacker; they only need enough capital to front the withdrawal amount themselves and the ability to broadcast/RBF a transaction, exactly analogous to the referenced report's "bid from your own wallet, then let it be overridden" pattern.

### Recommendation
Require the withdrawal-authorizing signature (or an aggregator/verifier co-signature) to commit to the operator identity that will be credited, e.g. by using `SIGHASH_ALL` (or `AllPlusAnyoneCanPay`) so the `OP_RETURN` output is covered, or by having the N-of-N/aggregator additionally sign a binding between the withdrawal id and the specific operator's kickoff instance before any reimbursement is honored, rather than trusting an unsigned on-chain `OP_RETURN` byte string as the sole attribution mechanism.

### Proof of Concept
1. Operator A calls `Withdraw`/`InternalWithdraw`, producing and broadcasting `payout_tx` (input: withdrawal UTXO signed `SinglePlusAnyoneCanPay`; outputs: user payout, anchor, `OP_RETURN(A_xonly_pk)`) as in `core/src/operator.rs` `withdraw()`.
2. Before `payout_tx` confirms, an attacker observes it in the mempool, extracts the reusable `SinglePlusAnyoneCanPay` signature over input 0/output 0, and builds `payout_tx'` with the same required user output (satisfying the signature) but funds it from their own wallet and substitutes `OP_RETURN(B_xonly_pk)` for a different registered operator B (or any arbitrary key), then broadcasts it with a higher fee (RBF) so it confirms instead of A's.
3. `update_finalized_payouts` in `core/src/verifier.rs` reads `B_xonly_pk` from the confirmed tx's `OP_RETURN` and records `payout_payer_operator_xonly_pk = B`.
4. Operator B's `PayoutCheckerTask` (`core/src/task/payout_checker.rs`) finds this "unhandled payout" attributed to itself and automatically drives `handle_finalized_payout` → kickoff → `reimburse_tx`, claiming vault funds for a payout it never funded or authorized, while the attacker who actually paid the user receives nothing back from the bridge.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
