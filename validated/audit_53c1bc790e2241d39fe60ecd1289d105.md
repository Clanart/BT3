### Title
Unbounded length-prefixed parsing loop in `SchnorrAggregate::read` enables denial of service (parser hang / unbounded work) - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs` reads an attacker-controlled 32-bit length prefix and then loops `u32::from_le_bytes(len)` times performing `C::read_G(reader)` — a point deserialization — with no upper bound and no chunked/streaming mitigation. This is the direct analog of CVE-2019-20860: a crafted input document declaring a huge element count causes the parser to perform up to ~4.3 billion point-decoding iterations (or block indefinitely on a streaming reader), hanging the application.

### Finding Description
The bug class is "crafted input causes application hang." In Serai's code the same shape exists in `SchnorrAggregate::read`:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    #[allow(non_snake_case)]
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

- The count field is a full `u32`, so an attacker can declare up to 4,294,967,295 elements with just 4 bytes.
- `C::read_G` performs a full canonical-encoding check and group-element deserialization per element (e.g., a decompression/torsion-free check for Ristretto/Secp256k1/ed448), so each iteration is non-trivial CPU work — not a cheap byte copy.
- There is no bound, no size limit, and no incremental/chunked read. Notably, Serai's own codebase recognizes this exact pattern as a vulnerability elsewhere: `networks/ethereum/src/machine.rs:51-60` reads `data_len` in 1 KB chunks explicitly commenting "A valid DoS would be to claim a 4 GB data is present for only 4 bytes." That mitigation was not applied here.
- When `reader` is a blocking/streaming source (network peer feeding bytes), the loop blocks waiting for each 32-byte encoding, so a peer that dribbles bytes keeps the parsing task occupied indefinitely — a literal application hang matching the CVE.

The parsed aggregate is then consumed by `SchnorrAggregate::verify` (`aggregate.rs:127-146`), which builds `2 * len + 1` multiexp pairs — a second unbounded allocation/computation driven by the same attacker-controlled count.

### Impact Explanation
An unprivileged party who can supply aggregate-signature bytes to any caller of `SchnorrAggregate::read` (the function is a public untrusted-bytes parsing API in the in-scope `crypto/schnorr` crate, in the same class as the enumerated `SchnorrSignature::read`/`Commitments::read` entry points) can:

- Cause the parsing loop to execute up to ~4.3 billion point deserializations, or hold the reader open indefinitely by streaming bytes slowly — an application hang/CPU-exhaustion DoS with zero authentication and a 4-byte trigger prefix.
- Force allocation of a `Vec` holding up to ~4.3 billion group elements (hundreds of GB) if enough data is supplied, plus a `2n+1`-element multiexp pair vector in `verify`.

This is a Medium-severity availability impact consistent with the reference advisory (CVSS 5.5, availability-only).

### Likelihood Explanation
Likelihood depends on whether an integrator exposes `SchnorrAggregate::read` over a byte stream reachable by untrusted parties — the type is used for validator-set batch signing verification in the codebase's consensus layer, which is exactly an unauthenticated-bytes context. Within the audited crates the defect is unconditional: the function imposes no limit, and the codebase's own comment in `networks/ethereum/src/machine.rs` acknowledges unbounded declared-length reads as a valid DoS. Exploitation requires no key material, no collusion, and no malformed cryptographic values — only a large length prefix.

### Recommendation
Apply the same mitigation pattern used in `Call::read`:

- Cap the declared `len` against a protocol-defined maximum (the number of signatures that can ever legitimately be aggregated is bounded by the validator/participant set size, i.e., `u16::MAX` at most), and reject larger values before looping.
- Alternatively/ additionally, read elements lazily or bound the loop by the remaining bytes actually available, and avoid growing `Rs` beyond a sane limit.
- In `SchnorrAggregate::verify`, independently sanity-check `keys_and_challenges.len()` before building the `2n+1` multiexp pair vector.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ristretto;
use schnorr::aggregate::SchnorrAggregate;

// 4 bytes declaring u32::MAX aggregate members, followed by nothing else.
let mut malicious = Vec::new();
malicious.extend_from_slice(&u32::MAX.to_le_bytes());

// Over a blocking/streaming reader this loop never makes progress past the
// available bytes and the task hangs; even over a Cursor the caller performs
// per-iteration work until read failure, and a peer trickling 32-byte
// encodings keeps the loop alive for up to ~4.3 billion iterations.
let mut cursor = Cursor::new(malicious);
let _ = SchnorrAggregate::<Ristretto>::read(&mut cursor);
```

The absence of any bound (compare `aggregate.rs:78-85` with the chunked-read guard in `networks/ethereum/src/machine.rs:51-60`) is the root cause; a length prefix of `0xffffffff` is sufficient to declare ~4.3 billion point decodings.
