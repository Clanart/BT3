## Analysis Summary

The seed report's core pattern is: **a state-changing operation mutates an "epoch/height" pointer, but instead of correctly reflecting reality, it snaps to an arbitrary value — creating a gap that lets subsequent (even honest-looking) submissions be mis-accepted as "new," or blocking legitimate progress.**

The closest verifiable local analog is in `EvmHost.sol`'s commitment-veto path, where the height-progression pointer is reset to a hardcoded `1` instead of the actual prior height — unlike the Substrate side, which correctly restores the true previous height.

### Title
EvmHost veto resets `_latestStateMachineHeight` to a hardcoded `1` instead of the true previous height, breaking the height-monotonicity guard that gates new consensus state acceptance - (File: `evm/src/core/EvmHost.sol`)

### Summary
`deleteStateMachineCommitmentInternal` on `EvmHost` resets the latest-height pointer for a state machine to the constant `1` whenever the vetoed height was the recorded latest, rather than restoring it to the true previous valid height. The equivalent Substrate path (`pallet_ismp::host::IsmpHost::delete_state_commitment`) does this correctly by looking up `PreviousStateMachineHeight`. This divergence mirrors the seed report's "epoch changes and the contract uses stale/mismatched pointer state" bug class.

### Finding Description
On the Substrate side, vetoing the latest commitment restores the pointer to the recorded previous height: [1](#0-0) 

On the EVM side, the same operation instead hardcodes the pointer to `1`: [2](#0-1) 

That pointer (`_latestStateMachineHeight`) is exactly the value `HandlerV2.handleConsensus` uses as the sole monotonicity guard for accepting new intermediate state commitments from a verified consensus proof: [3](#0-2) 

The Rust-side `update_client` handler enforces the analogous invariant ("Only allow heights greater than latest height") against `previous_latest_height`: [4](#0-3) 

After a legitimate veto of the current latest height on an EVM destination (fisherman-driven, a normal and expected operational event — see `veto_state_commitment` / `deleteStateMachineCommitment`, restricted to the handler and invoked through the cross-chain fisherman flow), `_latestStateMachineHeight[id]` becomes `1` instead of the real prior height (which may be arbitrarily large). Any subsequent, cryptographically valid consensus proof whose intermediate state height is merely `> 1` — including heights far below the chain's actual previous finalized height — now satisfies `intermediate.height > latestHeight` and is accepted via `storeStateMachineCommitment`, which unconditionally overwrites `_latestStateMachineHeight` with that (possibly stale/low) height: [5](#0-4) 

This collapses the height-progression invariant the protocol relies on to keep the "latest trusted height" pointer meaningful, for the entire window between the veto and the next fresh consensus update.

### Impact Explanation
This breaks the "consensus proofs, state proofs, challenge periods, and state commitments must never let false remote state become trusted" invariant: the monotonic-height guard that is supposed to prevent stale/superseded state from being re-registered as the tracked latest state is defeated by the veto's own bookkeeping bug. Even though `handlePostRequests`/`handleGetResponses` verify against the specific `request.proof.height` rather than the pointer directly, the pointer is the only guard preventing arbitrary lower-height commitments from being (re-)written and having their update-timestamp reset to `block.timestamp`, corrupting challenge-period timing bookkeeping for those heights, and misrepresenting the chain's sync progress to consumers of `latestStateMachineHeight()`.

### Likelihood Explanation
Triggering requires only a legitimate (and expected) fisherman veto of the current latest EVM state-machine height — a normal, permissionless-consequence event in the protocol's fraud-response design, not a compromised/malicious actor. Once triggered, exploitation of the weakened guard only requires a normal, unprivileged relayer to submit a valid consensus proof, which is a fully public, permissionless action.

### Recommendation
Mirror the Substrate implementation: track and restore the true previous height (e.g., via a `_previousStateMachineHeight` mapping analogous to `PreviousStateMachineHeight`) in `deleteStateMachineCommitmentInternal` instead of hardcoding `1`.

### Proof of Concept
1. A fisherman vetoes the current latest height `H` for state machine `S` on `EvmHost` via `deleteStateMachineCommitment` → `_latestStateMachineHeight[S]` becomes `1` (see `evm/src/core/EvmHost.sol:719-721`) instead of the true prior height `H_prev` (which could be `H-100`, `H-1000`, etc.).
2. Any relayer submits a valid consensus proof (via `HandlerV2.handleConsensus`) whose verified intermediate state includes a height `h` such that `H_prev < h` is false but `1 < h` is true (i.e., `h` is stale relative to the real chain but passes the corrupted guard).
3. `EvmHost.storeStateMachineCommitment` accepts and stores this stale height as if new, overwriting `_latestStateMachineHeight[S]` and resetting that height's `_stateCommitmentsUpdateTime` to the current block timestamp — corrupting both the tracked "latest" pointer and challenge-period timing for that height. [6](#0-5)

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
