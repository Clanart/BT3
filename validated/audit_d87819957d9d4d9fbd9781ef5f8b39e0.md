### Title
Missing non-zero validation on `kip71.gastarget` governance parameter allows a division-by-zero panic in Magma base-fee calculation - (File: `params/kip71_config.go`)

### Summary
The KIP-71 dynamic base-fee formula divides by the governance-controlled `GasTarget` parameter whenever the block's gas usage differs from target. Unlike the sibling parameter `Kip71BaseFeeDenominator`, which explicitly requires a non-zero value in its `FormatChecker`, `Kip71GasTarget` uses `noopFormatChecker`, so it can be set to `0` through a normal governance vote/contract-governance update. This is the same bug class as the external report: a critical divisor variable that feeds a pricing formula can be driven to zero because its setter lacks a "never zero" / immutability guard, letting a privileged-but-not-fully-trusted actor break the pricing mechanism — except here the consequence is a division-by-zero panic in every node's block-processing path rather than a DoS to a single auction.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget := kc.GasTarget` as a divisor: [1](#0-0) 

When `parentGasUsed > gasTarget` (true for `gasTarget == 0` and any nonzero gas usage), the code does `x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e. divide by zero, which panics in Go's `math/big`. The same division occurs in the decreasing branch: [2](#0-1) 

`GasTarget` is a mutable governance parameter (`kip71.gastarget`), and its format checker is a no-op that accepts any `uint64` including `0`, in contrast to `Kip71BaseFeeDenominator` which explicitly rejects zero: [3](#0-2) 

During vote/consistency verification, `Kip71GasTarget` falls into the bucket of parameters that pass with "no more checks" beyond the format checker: [4](#0-3) 

`NextMagmaBlockBaseFee` (via `VerifyMagmaHeader`) is invoked on every block once the Magma hard fork is active, so once `GasTarget=0` is committed into the effective `ParamSet`, all subsequent header verification/base-fee computation on every node hits the division-by-zero panic.

### Impact Explanation
This is a critical availability/consensus issue: a division-by-zero panic in a code path executed for every block (`VerifyMagmaHeader`/`NextMagmaBlockBaseFee`) would crash the Go process on all nodes that compute or verify the base fee, effectively halting the chain — far more severe than the original report's auction price manipulation, since it converts a governance mis-configuration (or malicious governing-node vote/contract-governance update) into a total network outage rather than just financial manipulation.

### Likelihood Explanation
Reachability requires only a single governance parameter update to `kip71.gastarget=0`, which is allowed by the current validation logic (no non-zero check, no immutability guard). In `governance.governancemode = "single"` (the documented Mainnet configuration), a single governing node can push this value; under contract governance (Kore+), whoever controls the `GovParamContract`/admin role for that parameter could set it directly. No code review or per-value bound is enforced beyond the trivial `FormatChecker`, unlike the parallel `BaseFeeDenominator` field which already got a `!= 0` guard — indicating the omission for `GasTarget` is an oversight rather than an intentional design choice.

### Recommendation
Add a non-zero `FormatChecker` to `Kip71GasTarget` (mirroring `Kip71BaseFeeDenominator`'s check), e.g. `func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }`, and additionally add a defensive guard inside `NextMagmaBlockBaseFee` (similar to the existing `if kc.BaseFeeDenominator == 0 { ... }` fallback) so that `gasTarget == 0` can never reach the `Div` calls even if an invalid value slips through some other governance path (e.g., stale ChainConfig defaults or contract governance bypassing the header-vote FormatChecker).

### Proof of Concept
1. As the governing node (single mode) or via `GovParamContract` (Kore+), submit a governance vote/update setting `kip71.gastarget = 0`.
2. Once this value becomes effective in the `ParamSet` for a block after the Magma fork, any block whose gas usage differs from `0` causes `NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))`.
3. `math/big.Int.Div` panics on division by zero, crashing the node process during block verification/production — reproducible deterministically by any node processing that block, since `VerifyMagmaHeader` is called unconditionally for Magma-enabled blocks.
