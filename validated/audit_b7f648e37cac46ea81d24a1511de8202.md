### Title
Balance-based (non delta-tracked) reward sweep in `ManualCompound.compound()` allows stealing tokens left in the contract - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` mirrors the reported `PayrollManager.executePayroll()` bug class: it determines the amount of tokens to move out of the contract by reading the contract's **current cumulative `balanceOf(address(this))`** instead of tracking a delta tied to the caller's own claim. Because this "before/after" accounting is not scoped to what the caller actually claimed in that same transaction, any balance of a registered reward token that is sitting in the contract — whether from dust left by a previous compound, a partial conversion, or a direct/erroneous transfer — is swept out to whichever unrelated wallet happens to call `compound()` next.

### Finding Description
`compound()` first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, which routes the caller's earned rewards for the pools/tokens in `_lps`/`_rewards` into the `ManualCompound` contract (`_receiver == address(this)`, since `ManualCompound` is `msg.sender` w.r.t. `MasterMagpie`). [1](#0-0) 

The final distribution loop, however, iterates over the entire globally-registered `rewards` array — **not** the specific tokens the caller just claimed — and for each one uses the contract's live balance as the amount to move:
```solidity
for (uint256 i; i< rewardTokensLength; i++) {
    ...
    uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));
    if (receivedBalance > 0) {
        ... // convert / lock / deposit / transfer receivedBalance to msg.sender
    }
}
``` [2](#0-1) 

This is the same anti-pattern as the reported bug: there is no snapshot of the balance *before* the caller's own claim was pulled in, and no check that the swept amount corresponds to what `_account` (the caller) actually earned. Any tokens already sitting in the contract for a registered reward token — from a prior partial compound, rounding dust in `SmartWomConvert`/locker calls, or a stray transfer — get attributed entirely to whoever calls `compound()` next, since the loop runs unconditionally over `rewards.length` regardless of `_lps`/`_rewards` content (an attacker can call `compound()` with irrelevant or empty `_lps` and still trigger the sweep of whatever balance is present).

This mirrors the external report precisely: "The after-balance check ... is a workaround ... tokens that are previously stored in the contract are used and can be stolen. This is also unwanted, although normally there shouldn't be tokens left in the contract" — `ManualCompound` has the identical property that funds legitimately belonging to a different user (or in transit) can be diverted to an arbitrary caller purely because accounting is balance-based rather than claim-delta-based.

### Impact Explanation
Reward tokens (e.g. WOM, MGP, or other bonus tokens registered in `rewards[]`) that end up temporarily resident in `ManualCompound` — due to dust from conversion/locking calls not consuming the full approved amount, or any other reward flow that doesn't perfectly zero out the balance in the same call — can be swept and stolen by any unprivileged wallet simply by invoking `compound()`. This is a direct theft of other users'/protocol's yield tokens.

### Likelihood Explanation
Likelihood depends on residual balances actually accumulating in the contract (e.g. from `IConverter`/`ILocker` calls not consuming 100% of the approved `receivedBalance`, or races among users' claims through the shared `rewards[]` list). Under normal, atomic single-call operation, most balance is swept in the same transaction as it's claimed, but any deviation (dust, partial consumption, or an errant transfer to the contract) exposes the exact steal vector the report describes, and any wallet can trigger it opportunistically at low cost (just calling `compound()`).

### Recommendation
Do not use `balanceOf(address(this))` as the transfer amount for a shared/global contract. Instead:
- Track a strict delta: snapshot `balanceOf` immediately before `multiclaimOnBehalf` for each token in `rewards[]`, and only move `after - before` per call, scoped to `_account`'s claim.
- Or, restrict the final distribution loop to only the reward tokens that were actually included in `_rewards` for this call (rather than iterating the full global `rewards[]` list), so a caller cannot receive tokens they never claimed.

### Proof of Concept
1. Reward token `X` is registered in `ManualCompound.rewards`.
2. Due to `SmartWomConvert`/`ILocker`/`ISimpleHelper` not consuming exactly 100% of `receivedBalance` in a prior `compound()` call (or via a stray/mistaken direct ERC20 transfer to `ManualCompound`), a nonzero balance of `X` is left sitting in the contract.
3. An unrelated wallet calls `compound(emptyOrUnrelatedLps, emptyOrUnrelatedRewards, ...)`.
4. `multiclaimOnBehalf` claims nothing relevant to `X`, but the final loop at [2](#0-1)  still reads `IERC20(X).balanceOf(address(this))` and sends/locks/converts the entire leftover balance to `msg.sender`, even though that caller never earned it.
