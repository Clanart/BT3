### Title
`compound()` sweeps the entire contract balance of any caller-named token instead of only the caller's claimed share - (File: rewards/ManualCompound.sol)

### Summary
In `compound(address[] _lps, address[][] _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp)`, the "return non-compoundable reward" loop reads `IERC20(_rewards[i][j]).balanceOf(address(this))` and transfers the *entire* balance to `msg.sender` for every token address the caller supplies, gated only by `!compoundableRewards[_rewards[i][j]]`. Because the transferred amount is derived from ambient contract balance rather than the amount actually claimed for `msg.sender` in that specific call, any residual balance of a non-compoundable token left on the contract (dust, a prior partial/failed sweep, or leftover balance from a token that was previously removed via `removeReward`) can be swept in full by an unrelated, unprivileged caller.

### Finding Description
```solidity
for(uint256 i; i < _lps.length; i++) {
    uint256 rewardLength = _rewards[i].length;
    if (rewardLength > 0) {
        for (uint j; j < rewardLength; j++) {
            if (!compoundableRewards[_rewards[i][j]]) {
                uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                if (rewardBalance > 0)
                    IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
            }
        }
    }
}
``` [1](#0-0) 

The only check performed is `!compoundableRewards[_rewards[i][j]]`, which is a global boolean per token address, not a per-caller accounting record — it does not verify that the balance currently held equals only what `msg.sender` just had claimed on their behalf via `multiclaimOnBehalf` in this same transaction. [2](#0-1)  `_lps` and `_rewards` (and thus the exact token addresses swept) are entirely attacker-supplied `calldata` with no restriction on the caller. [3](#0-2) 

Because a fixed pool address (this contract) holds cumulative balances rather than per-user ledgered amounts, any residue of a non-compoundable token address left behind from a prior transaction (e.g., partial/failed transfer, dust from a token that was later `removeReward`'d and is now marked non-compoundable while still holding un-swept balance, or an accidental/incidental transfer to the contract) becomes claimable in full by the next caller who simply names that token address in `_rewards`, even though they never earned any of it. This breaks the invariant that the caller's payout must be reconciled to their own claimed share rather than to the contract's total ambient balance of an arbitrary token.

### Impact Explanation
If residual non-compoundable-token balance accumulates on the contract (per the stated precondition), any unprivileged caller can extract that entire balance for themselves by simply including the token address in `_rewards`, regardless of whether it is a legitimate reward for the `_lps` they pass. This is a direct diversion of funds that rightfully belong to other users (whoever's dust/residue it was), matching a fund-theft impact class, since the extracted tokens are not limited to what `msg.sender` actually claimed.

### Likelihood Explanation
Exploitability is conditioned entirely on the stated precondition — a residual balance of a non-compoundable token already sitting on the contract from a prior compound/administrative action (e.g., `removeReward` demoting a token to non-compoundable while balance remains, or a partial/failed transfer in a previous call). Given that precondition, exploitation requires no capital, no special role, and is trivially repeatable: any EOA can call `compound()` naming the residual token in `_rewards`. The attack does not require reentrancy or flash loans — it only requires the ability to name arbitrary addresses in `_rewards`, which the function unconditionally allows.

### Recommendation
Do not use `balanceOf(address(this))` as the basis for the non-compoundable sweep amount. Instead, have `multiclaimOnBehalf` return (or have `ManualCompound` measure via before/after balance deltas scoped strictly to the tokens/amounts claimed in that call) the exact amount claimed for `msg.sender`, and transfer only that delta. Alternatively, track and forward the return value of `multiclaimOnBehalf` per reward token rather than reading global balance.

### Proof of Concept
Hardhat test plan:
1. Deploy `ManualCompound` with a mock `MasterMagpie` and one non-compoundable ERC20 token `T` (i.e., `compoundableRewards[T] == false`, not present in `rewards` array).
2. Simulate the "residue" precondition: directly mint/transfer `1000 T` to the `ManualCompound` contract to represent a previous compound's un-swept residue (or drive it via a prior `compound()` call whose mocked `multiclaimOnBehalf` leaves dust).
3. From an unrelated attacker EOA with no stake/claim in any `_lps`, call `compound([lpX], [[T]], 0, 0, false)` where the mock `multiclaimOnBehalf` claims `0` new `T` for the attacker.
4. Assert: attacker's `T` balance increases by `1000` and `ManualCompound`'s `T` balance goes to `0`, despite the attacker having claimed nothing themselves — demonstrating `IERC20(T).balanceOf(address(this))` diverges from the attacker's actual claimed share and is fully drained to an unrelated caller.
