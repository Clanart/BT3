Confirmed: `Kip71GasTarget` uses `FormatChecker: noopFormatChecker` [1](#0-0)  — unlike `Kip71BaseFeeDenominator`, which explicitly rejects zero (`v != 0`) [2](#0-1) , there is no check preventing `kip71.gastarget` from being set to `0` via governance vote.

### Title
Governance-settable `kip71.gastarget = 0` causes division-by-zero panic in `NextMagmaBlockBaseFee`, crashing/diverging nodes on every block after any non-empty block - (File: `params/kip71_config.go`)

### Summary
The KIP-71 base fee formula divides by `GasTarget` in two branches without ever validating that it is non-zero, while the governance parameter registry that would normally reject invalid values explicitly omits this check for `Kip71GasTarget`. This mirrors the reported "Funding.deposit() doesn't work if there is no discount set" bug class: a governance/config-controlled divisor/threshold that, when left at its zero-valued edge case, is used unconditionally in an arithmetic operation without a guard, breaking every subsequent transaction/block that depends on it.

### Finding Description
`NextMagmaBlockBaseFee` computes the delta needed to adjust the base fee using `gasTarget` as a divisor in both the "gas used above target" and "gas used below target" branches: [3](#0-2) [4](#0-3) 

The only zero-protected divisor in this function is `BaseFeeDenominator`, which has an explicit fallback of `64` when zero: [5](#0-4) 

No equivalent guard exists for `gasTarget`. The function only short-circuits when `parentGasUsed == gasTarget` (both zero) or when the bound has already been hit; any other case where `gasTarget == 0` and `parentGasUsed > 0` falls into the `parentGasUsed > gasTarget` branch and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e., a `big.Int` division by zero, which panics.

Critically, the governance registry entry for this parameter uses `noopFormatChecker`, i.e., no validation at all is performed on submitted `kip71.gastarget` votes: [1](#0-0) 

Contrast this with the sibling parameter `Kip71BaseFeeDenominator`, whose `FormatChecker` explicitly rejects zero: [2](#0-1) 

This asymmetry indicates the missing check was an oversight rather than an intentional design decision — exactly analogous to the `Funding.getAmountOut()` bug where a `discount > 0` guard was intentionally added for one branch but the caller's zero-fallback semantics were never validated against the actual downstream usage.

### Impact Explanation
`GasTarget` is a governance parameter which the governing node (or council under a general-vote framework) can change through the standard governance-vote mechanism (`kaiax/gov`), consumed as an unsigned integer directly into `ParamSet.GasTarget` and passed to `NextMagmaBlockBaseFee` on every block header validation and construction after Magma. If a vote sets `kip71.gastarget` to `0` and passes, then on the very next block that contains any gas usage above zero, every node computing/verifying the header's `BaseFee` (both block proposers via `NextMagmaBlockBaseFee` used to construct headers, and validators via `VerifyMagmaHeader`) will panic on a division by zero. Because this function is on the critical path of header assembly and header verification, this results in a chain-wide crash/halt — an availability-critical consensus failure reachable purely through a governance parameter update, not a peer/validator-privileged malicious action.

### Likelihood Explanation
The parameter is governance-settable through the standard, permissionless-friendly `governance.vote`/general-vote flow, and no validation anywhere in the governance parameter pipeline (`kaiax/gov/param.go`) prevents a zero value from being canonicalized and accepted. Any block author or vote proposer who can get a `kip71.gastarget=0` vote passed (or a malformed/misconfigured genesis/governance value) triggers the panic deterministically on the first subsequent non-empty block — no timing, race conditions, or additional preconditions are required beyond gas usage being nonzero, which is true of virtually every real block.

### Recommendation
Add a `FormatChecker` to `Kip71GasTarget` (mirroring `Kip71BaseFeeDenominator`) that rejects `0`, e.g. `func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }`. Additionally, as defense in depth, `NextMagmaBlockBaseFee` should apply the same zero-fallback pattern used for `baseFeeDenominator` to `gasTarget` (e.g., treat `0` as an invalid/default value) so that a bad `ChainConfig`/genesis value cannot crash the node even if the governance-layer check is bypassed.

### Proof of Concept
1. Submit and pass a governance vote (or configure genesis) setting `kip71.gastarget = 0` — this is accepted because `Kip71GasTarget.FormatChecker` is `noopFormatChecker` [1](#0-0) .
2. Once the parameter becomes effective at the next epoch/param-set boundary, produce or receive any block with `GasUsed > 0`.
3. In `NextMagmaBlockBaseFee`, `parentGasUsed (>0) > gasTarget (0)` is true, so the code executes:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // parentGasUsed
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 -> panic: division by zero
``` [3](#0-2) 
4. Every node executing this code path (proposers building headers and validators calling `VerifyMagmaHeader`) panics, halting block production/validation network-wide.
