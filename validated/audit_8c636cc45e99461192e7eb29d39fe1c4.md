### Title
`Scanner::scan_block` accepts immature coinbase outputs as spendable received funds - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The external report describes an inconsistent-validation bug class: one path validates a destination/input while a second path stores and later uses the same kind of value without revalidating it. The analog in Serai lives in the Bitcoin wallet scanner. `Scanner::scan_transaction` performs no coinbase/maturity check, and `Scanner::scan_block` unconditionally iterates `block.txdata` — including `txdata[0]`, the coinbase transaction — so a coinbase output paying to a registered script is returned as an ordinary `ReceivedOutput`. That output is reported as received funds even though it is unspendable for 100 blocks. There is no flag on `ReceivedOutput` distinguishing coinbase outputs, so downstream consumers that build a `SignableTransaction` from scanned outputs have no way to revalidate maturity — the check was simply never performed on the block-scan path.

### Finding Description
`scan_transaction` matches outputs purely on `script_pubkey` membership in `self.scripts` (`networks/bitcoin/src/wallet/mod.rs:205-211`) and `scan_block` feeds it every transaction in the block, including the coinbase (`networks/bitcoin/src/wallet/mod.rs:221-227`). A grep of `networks/bitcoin/src` shows no `is_coinbase`/maturity handling anywhere in the crate — the only mitigation is a doc comment on `scan_block` saying a "post-processing pass is needed" if outputs must be immediately spendable. A `ReceivedOutput` carries only `offset`, `output`, and `outpoint` (`networks/bitcoin/src/wallet/mod.rs:90-97`), so once produced, the coinbase provenance is erased and no later stage can detect it.

### Impact Explanation
A miner (an unprivileged party producing public Bitcoin transaction data) can include an output paying to Serai's registered script in a coinbase transaction. `scan_block` reports it as received, and any consumer that treats scanned outputs as spendable inputs will construct a transaction spending an immature coinbase output, which the network rejects as a consensus violation. This is "funds reported received that are not spendable" — balance inflation plus a poisoning vector against automated aggregation/spend pipelines, which can stall or repeatedly build invalid transactions. Severity Medium: integrity/availability impact on fund tracking, no key or signature compromise.

### Likelihood Explanation
Triggering requires mining a block (or a miner colluding), which limits frequency, but requires no Serai credentials and only public transaction data — exactly the reachable-input class specified. Whether downstream code actually spends immature outputs depends on integrator behavior, but the library provides no in-band signal to prevent it.

### Recommendation
In `scan_block`, skip `block.txdata[0]` when it `is_coinbase()`, or record coinbase provenance on `ReceivedOutput` (e.g., a `coinbase: bool` field) and require maturity (100 confirmations) before the output is returned/spendable. At minimum, `scan_transaction` itself should ignore outputs of coinbase transactions when called via block scanning.

### Proof of Concept
1. Create `Scanner::new(key)` for an even key, yielding the canonical P2TR script (`networks/bitcoin/src/wallet/mod.rs:162-166`).
2. A miner constructs a block whose coinbase transaction includes an output with that `script_pubkey`.
3. Call `scanner.scan_block(&block)` — it iterates all of `block.txdata` and returns a `ReceivedOutput` for the coinbase output (`networks/bitcoin/src/wallet/mod.rs:221-227`).
4. Pass that `ReceivedOutput` to `SignableTransaction::new` and produce a signed spend; the transaction is consensus-invalid because the coinbase input is immature, yet Serai has recorded the funds as received.

Uncertainty: whether in-scope callers auto-spend scanner outputs without a maturity check could not be fully confirmed, but the scanner API itself produces the unmarked immature `ReceivedOutput`, which is the root-cause gap.
