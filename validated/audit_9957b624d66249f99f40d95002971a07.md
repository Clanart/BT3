### Title
BIP-340 Schnorr algorithm never normalizes group-key parity, producing signatures that fail Bitcoin consensus verification for odd-Y keys - (File: networks/bitcoin/src/crypto.rs)

### Summary
Analogous to CVE-2026-28432 (signature verification not actually enforcing what the surrounding protocol requires), `frost_crypto::Schnorr` in `networks/bitcoin/src/crypto.rs` implements BIP-340 challenge/parity handling only for the nonce `R`, never for the public key `A`. BIP-340 defines the public key as the even-Y lift `lift_x(x(A))`, so when the FROST group key `A` has odd Y, the effective secret key is `-x`, not `x`. The code signs with `params.secret_share()` (= `x`) unmodified, and emits a signature the internal check accepts but Bitcoin rejects.

### Finding Description
`Hram::hram` hashes only `x(R) || x(A) || m` and conditionally negates the challenge when `R` is odd (`networks/bitcoin/src/crypto.rs:59-73`). `sign_share` delegates to `FrostSchnorr::sign_share`, which computes `s = r + c·x` using the raw `params.secret_share()` (`crypto/frost/src/algorithm.rs:201-211`). `verify` checks `sG = R + c·A` against the raw `group_key` and then negates `s` iff `R` is odd (`networks/bitcoin/src/crypto.rs:139-150`).

Case `A` odd, `R` odd: `c' = -c`, `s = r - cx`; emitted `s' = -s = -r + cx`, so `s'G = -R + cA`. A BIP-340 verifier checks `s'G = R_even + c·lift_x(A) = -R + c·(-A) = -R - cA`. Equality requires `cA = -cA`, i.e. `c = 0` — probability negligible. The emitted signature is invalid on-chain even though `verify` returned `Some`. The same holds for `R` even: emitted `sG = R + cA` vs required `R + c(-A)`. No code path negates the secret share or asserts even-Y on `A`; the only `needs_negation` call sites operate on `R`.

### Impact Explanation
For any FROST key whose group key has odd Y (~50% of honestly generated keys), every produced "BIP-340" signature fails Bitcoin's signature check. Taproot outputs controlled by such a threshold key cannot be spent — the signing session completes successfully, `AlgorithmSignatureMachine::complete` returns a signature via the internal `verify` at `crypto/frost/src/sign.rs:465`, yet consensus rejects it. This is a verification-formula defect: the internal `sig.verify(group_key, c)` validates against `A` rather than `lift_x(x(A))`, so the algorithm certifies signatures that do not satisfy the scheme they claim to implement.

### Likelihood Explanation
Deterministic for odd-Y group keys; no adversary is required. Reachability caveat: if every caller externally constrained group keys to even-Y (e.g., via a parity-forcing key offset at key-gen time), the defect is latent rather than live — no such normalization is visible in the FROST signing path or this file, and `sign_share`/`verify` take `params`/`group_key` verbatim.

### Recommendation
Normalize the group key inside the BIP-340 `Algorithm`: in `sign_share` (and `verify_share`), conditionally negate the effective secret/verification share when `needs_negation(&params.group_key())` / `needs_negation(&group_key)` is set — equivalent to signing with `x' = -x` when `A` is odd, matching `lift_x`. Alternatively reject/normalize odd-Y group keys at `ThresholdKeys` registration for the Bitcoin network so this invariant is enforced once.

### Proof of Concept
1. Complete PedPoP DKG yielding `ThresholdKeys<Secp256k1>` with `group_key()` odd-Y (retry until odd, ~2 trials).
2. Run `algorithm_machines`/`sign` with `bitcoin::crypto::Schnorr::new()` over any sighash `m`.
3. `verify` returns `Some([u8; 64])`; parse as a BIP-340 signature `(x(R_emit), s')` where `R_emit` is even.
4. `bitcoin::secp256k1::schnorr::verify` (or libsecp256k1 `secp256k1_schnorrsig_verify`) against `XOnlyPublicKey::from_slice(x(A))` fails: required equation is `s'G = R_emit + c·lift_x(A)` with `lift_x(A) = -A`, while the signature satisfies `s'G = R_emit + c·A`.
