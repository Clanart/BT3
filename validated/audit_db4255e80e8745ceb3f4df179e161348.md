### Title
Stale index-based line selection lets working-directory changes between diff review and commit silently swap which content is staged - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-commit feature stores which lines a user wants to commit as a `DiffSelection` bitmap over **absolute line indices** of a diff snapshot, not as content-bound references. When staging happens, `applyPatchToIndex` re-fetches a **fresh** diff from disk and reapplies the **old** index-based selection to it via `formatPatch`. If the working-directory file changes between the moment the user reviews/selects lines and the moment `_commitIncludedChanges` actually stages the file, and the change preserves line/hunk counts (e.g. an auto-formatter, linter, build watcher, or a git filter modifies content in place), the same numeric indices in the new diff point to different logical content. The result: the user commits content they never saw or reviewed, without any error, warning, or bundle failure — a direct analog of the reported "front-run to change initialized ticks" bug, where index-based bookkeeping and actual state diverge silently.

### Finding Description
The commit pipeline is:
1. UI review/selection: the user toggles lines in the Changes view; the resulting `DiffSelection` divergence set is keyed purely by `unifiedDiffStart + lineIndex` positions of the diff loaded at review time [2](#0-1) .
2. Commit: `_commitIncludedChanges` takes whatever `file.selection` is currently attached to the `WorkingDirectoryFileChange` objects in state and passes them straight to `createCommit` without re-validating that the selection still matches current disk content [3](#0-2) .
3. Staging: `stageFiles` → `applyPatchToIndex` calls `getWorkingDirectoryDiff` **again**, fetching a brand-new diff straight from the filesystem at staging time, and immediately builds the patch from it: `formatPatch(file, diff)` [4](#0-3) .
4. `formatPatch` decides what to keep purely by `file.selection.isSelected(absoluteIndex)` against the **new** diff's line positions [5](#0-4) .

The only staleness guard that exists, `updateChangesWorkingDirectoryDiff`, is invoked on *selection-change* events for UI rendering purposes and merely strips indices that are no longer "includeable" lines — it does not verify that an index which is still valid still refers to the *same content* it did when selected: "Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines" [6](#0-5) . This guard is not invoked again immediately before `_commitIncludedChanges` builds the patch, and even if it were, it only removes stale indices — it never detects that an index now maps to *different* text while remaining nominally "selectable" (e.g., a hunk changed size elsewhere, keeping the total line count/positions of an untouched-looking hunk aligned).

This exactly mirrors the reported Uniswap-analog bug: a numeric/positional "slot" (tick index vs. diff line index) is filled by a snapshot taken at one point in time, then reused against a live, mutable data structure that can be altered (front-run) between snapshot and use, without breaking the count-based sanity checks that would otherwise cause the operation to abort.

### Impact Explanation
This causes **silent corruption of what the user commits**: content that was never shown to, or approved by, the user in the diff view ends up in the git history, potentially including unreviewed/malicious lines from a build tool, formatter, or filter that runs as part of a normal cloned-repository workflow (e.g. `npm run watch`, `prettier --watch`, a pre-existing lint-on-save daemon documented in the project's README). Because `git apply --cached` only fails on structural mismatches (line counts/context), not on "this content differs from what the UI displayed," the bundle/commit proceeds without any error dialog, matching the report's "does not revert" property.

### Likelihood Explanation
The user has to leave the partial-selection review open (or return to it) while a legitimate, repo-provided process is actively rewriting a tracked file with the same line/hunk layout, then click Commit before Desktop reloads the diff. This is a realistic occurrence in real dev workflows (watch-mode builds, format-on-save, generated files) inside a repository the user just cloned, especially for larger diffs where users select some lines and take time to write a commit message before hitting "Commit". It requires no admin rights, no local malware, and no unnatural steps — only that a legitimately-run process from the cloned repo modifies the file while Desktop's stale selection is still in memory.

### Recommendation
Bind `DiffSelection` (or at least a per-commit snapshot of it) to line **content**, not just position — e.g., re-diff and re-validate immediately before `applyPatchToIndex`/`formatPatch` are invoked in `_commitIncludedChanges`, comparing the diff used for staging against the diff the user actually saw (by hash or by line text), and abort/re-prompt the user if they differ, rather than silently reapplying stale positional selection to new content.

### Proof of Concept
1. Clone a repo containing a file `foo.txt` with 10 lines, and a documented dev command that a watch-mode tool runs which rewrites lines 5-6 in place without changing total line count (e.g., a code generator or formatter run via `npm run watch`).
2. In Desktop, open the Changes view for `foo.txt`, and select only lines 1-4 for commit (leaving 5-10 unselected), based on the diff currently displayed.
3. Before committing, let the watch tool fire and rewrite the *unselected* lines 5-6 with different content while keeping line positions identical; do not touch lines 1-4.
4. Without reopening/refreshing the diff panel, click "Commit". `applyPatchToIndex` fetches the new diff and `formatPatch` reapplies the old index bitmap (`1-4 selected`) to it — this appears to work as intended since content the user chose to select is unaffected.
5. Now instead have the watch tool rewrite line 3 (a *selected* line) and shift/replace an unselected trailing block by the exact same number of lines, keeping the hunk header counts identical to what `updateChangesWorkingDirectoryDiff`'s `selectableLines` recomputation would still accept — the committed content for line 3 will be whatever is on disk at staging time, not what the user saw and selected, and no error is raised.
