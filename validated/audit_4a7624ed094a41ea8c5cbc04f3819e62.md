### Title
Reachable panic (DoS) via unhandled `HashMap` index on `enc_keys` in PedPoP blame/decrypt path - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP `Decryption` box stores per-participant encryption public keys in a `HashMap<Participant, C::G>`. Both `decrypt_with_proof` and `encrypt` index this map with `[]` (`self.enc_keys[&decryptor]` / `self.decryption.enc_keys[&participant]`), which panics if the participant index is absent. A blame/decryption request referencing a participant whose `EncryptionKeyMessage` was never registered crashes the process instead of returning an error — the Rust analog of the NULL-pointer-dereference DoS in CVE-2017-17554: attacker-influenced input reaching a dereference of a missing object.

### Finding Description
`Decryption::register` only inserts into `enc_keys` when a participant's `EncryptionKeyMessage` is processed, and `register` itself asserts on re-registration but performs no existence guarantee for participants who withhold or fail to deliver their key message. [1](#0-0) 

Later, `decrypt_with_proof` verifies the accuser's PoP signature (`msg.pop.verify`, line 374) — which any participant can satisfy since it is a public-key Schnorr PoP over `msg.key` — and then unconditionally dereferences `self.enc_keys[&decryptor]` when checking the `EncryptionKeyProof` DLEq: [2](#0-1) 

`HashMap`'s `Index` impl panics on a missing key. The same pattern exists in `Encryption::encrypt`, which indexes `self.decryption.enc_keys[&participant]` for the intended recipient: [3](#0-2) 

All other read paths in the crate (`EncryptedMessage::read`, `EncryptionKeyProof::read`, `Commitments::read`) return `io::Error` on malformed input — but this lookup is not input-validated, so an absent participant entry produces `panic!` instead of `Err`.

### Impact Explanation
An unprivileged DKG participant (or an accuser in the blame protocol, whose identity `decryptor` is derived from protocol messages) can crash a node/process executing the PedPoP protocol if the referenced participant never had a registered encryption key — e.g., a participant whose `EncryptionKeyMessage` was withheld, dropped, or processed under a different index. This is a denial of service against the key-generation/signing stack reachable purely from protocol messages and attacker-influenced `Participant` values, matching the CVE's "crash on crafted input" class.

### Likelihood Explanation
Triggering requires reaching `decrypt_with_proof` (or `encrypt`) with a `decryptor`/`participant` index not present in `enc_keys`. Whether this state is reachable depends on the caller in `crypto/dkg/pedpop/src/lib.rs` guaranteeing all `n` participants registered before the encrypt/blame phases — if any flow permits blaming or encrypting for a non-registered index, a single message suffices. Medium likelihood: it requires a partially completed DKG or a blame against an unregistered participant, but needs no secrets or collusion beyond a faulty/malicious participant withholding their key-registration message.

### Recommendation
Replace `self.enc_keys[&decryptor]` and `self.decryption.enc_keys[&participant]` with `.get(&...).ok_or(...)` / `.ok_or(DecryptionError::InvalidProof)`-style lookups, returning a typed error for missing participants rather than panicking.

### Proof of Concept
```rust
// crypto/dkg/pedpop context
let mut dec = Decryption::<Ed25519>::new(context);
// Participant 2 never registers an EncryptionKeyMessage.

// Attacker (participant 1) crafts an EncryptedMessage with a key they know,
// so the PoP check at encryption.rs:374 passes:
let msg: EncryptedMessage<Ed25519, SecretShare> = encrypt(&mut rng, context, p1, attacker_pub, share);

// A blame proof is then evaluated naming decryptor = participant 2:
let proof = EncryptionKeyProof { key: ecdh_key, dleq: valid_dleq };
// PANIC: index into HashMap misses `participant 2`
let _ = dec.decrypt_with_proof(p1, Participant::new(2).unwrap(), msg, Some(proof));
```
The panic occurs at `self.enc_keys[&decryptor]` (encryption.rs:388) after the attacker-satisfiable PoP verification, crashing the caller rather than returning `DecryptionError`.
