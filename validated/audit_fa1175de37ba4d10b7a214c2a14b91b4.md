## Title
Governance-settable `Kip71GasTarget=0` causes division-by-zero panic in KIP-71 base fee calculation, crashing all nodes - (File: `params/kip71_config.go`)

### Summary
The `KIP71Config.NextMagmaBlockBaseFee` function computes the next block's base fee by dividing by `gasTarget`, a value fully controlled by the `reward.gastarget`/`kip71.gastarget` governance parameter. Unlike the sibling parameter `BaseFeeDenominator`, which is explicitly guarded against a zero value both at the format-validation layer and at the point of use, `GasTarget` has no such protection anywhere in the code path. A governance vote setting `Kip71GasTarget` to `0` will pass all validation and, once activated, cause a division-by-zero panic in every node (proposers and verifiers alike) that computes the next block's base fee — a full chain halt rather than a localized DoS.

### Finding Description
`NextMagmaBlockBaseFee` uses `gasTarget := kc.GasTarget` directly as a divisor when the parent block's gas usage differs from the target: [1](#0-0) 

Specifically, in both the "used more than target" and "used less than target" branches:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
```
If `gasTarget == 0`, `big.Int.Div` panics with "division by zero". Note that the code explicitly guards against `BaseFeeDenominator == 0` a few lines above ("To avoid panic, set the fluctuation range small"), but performs no analogous guard for `GasTarget`.

The governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, unlike `Kip71BaseFeeDenominator` which explicitly rejects zero: [2](#0-1) 

The header-vote consistency checker (`checkConsistency`) also performs no extra validation for `Kip71GasTarget`, grouping it with parameters that pass as long as they satisfy the generic format checks: [3](#0-2) 

Test coverage confirms `uint64(0)` is never rejected for `Kip71GasTarget` (only wrong-typed/negative values are in the bad-vote list), whereas malformed values for other KIP-71 parameters are tested more thoroughly: [4](#0-3) 

This is directly analogous to the MerkleResistor `coinsPerSecond` bug: a governance-influenced divisor derived from external input can reach zero and is used unguarded as a divisor in a periodic (per-block, here) computation, causing a hard failure of core functionality. The Kaia impact is materially worse because `NextMagmaBlockBaseFee` / `VerifyMagmaHeader` is invoked by every node (both block-building and header-verification paths) at every block once Magma is active, so a panic here is not merely "withdrawal blocked" but a full network-wide crash/halt.

### Impact Explanation
Once a `Kip71GasTarget = 0` vote is cast and takes effect (governance votes are counted every epoch and become active as `ParamSet` values used by `GetParamSet`/`ToKip71Config`), the very next block whose gas usage is not exactly zero will trigger `NextMagmaBlockBaseFee` to divide by zero. This function is called by:
- Block proposers when building the next block's base fee.
- All nodes when verifying that block's header via `VerifyMagmaHeader`.
- RPC-facing code such as fee-history estimation (`node/cn/gasprice/feehistory.go`).

A panic in this path on all nodes simultaneously is a critical, chain-halting bug: it is a genuine state-divergence/liveness failure of the entire network, not merely of one vault or user's withdrawal, exceeding the severity of the original MerkleResistor finding.

### Likelihood Explanation
Reaching this bug only requires a governance vote (one of the explicitly permitted analog categories in scope) setting `Kip71GasTarget` to `0`. There is no validation anywhere in the vote pipeline (`NewVoteData`/`VerifyVote`/`checkConsistency`) or in the parameter definitions (`kaiax/gov/param.go`) that rejects a zero value, in contrast to the deliberate zero-guard applied to the sibling `BaseFeeDenominator` parameter. Governance parameter changes are explicitly in scope per the prompt's allowed analog categories.

### Recommendation
Add an explicit `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (mirroring the `Kip71BaseFeeDenominator` checker), and additionally add a defensive zero-check inside `NextMagmaBlockBaseFee` (fallback to a safe default, similar to the existing `BaseFeeDenominator == 0` guard) so that even a value that somehow bypasses governance-layer validation cannot crash the node.

### Proof of Concept
1. A governance-participating validator casts a vote `Kip71GasTarget = uint64(0)` via `headergov.NewVoteData`. This passes `NewVoteData`/`VerifyVote` because `noopFormatChecker` accepts any `uint64`, including `0` (see `kaiax/gov/headergov/vote_test.go` bad-vote list, which never tests `uint64(0)` for this parameter).
2. The vote is included and finalized at an epoch block, updating the active `ParamSet.GasTarget` to `0`, which flows into `ToKip71Config()`.
3. On the next block after activation, assuming any nonzero gas usage, `parentGasUsed > gasTarget` (or `< gasTarget` in the low-usage branch) is true since `gasTarget == 0`, hitting:
   ```go
   y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 → panic
   ```
   in `params/kip71_config.go`, lines 100-102 (and 118-121 for the decreasing branch).
4. Every node calling `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` for that block panics, halting block production and verification network-wide.
