### Title
`OP_RETURN` data is omitted from Bitcoin fee calculations, producing underpriced transactions - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts caller-provided `data` and adds it as an `OP_RETURN` output, but calculates transaction weight and fees using only `payments` and the optional change output. The resulting signed transaction is larger than the size used to calculate its fee, so its effective fee rate is lower than requested.

### Finding Description
The `data` argument is public transaction data supplied to `SignableTransaction::new`. [1](#0-0)  The constructor adds it to `tx_outs` as an `OP_RETURN` output before calculating fees. [2](#0-1)  However, `calculate_weight_vbytes` only reconstructs payment outputs and an optional change output; it has no parameter for the already-created `OP_RETURN` output. [3](#0-2) [4](#0-3) 

Both the no-change estimate and the change-enabled estimate therefore omit the `OP_RETURN` output's serialized size. [5](#0-4) [6](#0-5)  When change is used, the excess bytes increase the final transaction's vsize while `needed_fee` remains the under-calculated value. The transaction is then signed with this mismatched fee policy. [7](#0-6) 

### Impact Explanation
An unprivileged party that can cause transaction data to be signed can force a Bitcoin withdrawal or data transaction to be signed with less fee than its true size requires. With a change output, the under-calculated fee is transferred to change, leaving the actual fee equal to the incorrectly small estimate while the transaction contains up to 80 additional bytes plus `OP_RETURN` output overhead.

For low fee rates, the signed transaction can fall below Bitcoin's minimum relay fee despite passing the constructor's minimum-fee check, because that check also uses the underestimated vsize. [8](#0-7)  This can leave the transaction unrelayable or stalled and require fee-bumping or reconstruction before the funds can move.

### Likelihood Explanation
The issue is deterministic whenever `data` is supplied. It becomes directly impactful whenever a change output is produced, since the change amount is calculated using the underestimated `fee_with_change`. [9](#0-8)  The attacker only needs to supply data accepted by the public `data: Option<Vec<u8>>` parameter and does not need control over keys or peers.

### Recommendation
Include the serialized `OP_RETURN` output in the transaction used for fee estimation. A clean approach is to change `calculate_weight_vbytes` to accept the complete initial `tx_outs`, or an explicit optional `data: &[u8]`, and use that representation for both the no-change and with-change calculations. Alternatively, calculate weight after constructing the final output set rather than reconstructing a separate output set from `payments`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs

// One spendable input, at least one payment, a change script, and maximum
// caller-controlled OP_RETURN data.
let tx = SignableTransaction::new(
    vec![received_output],
    &[(payment_script, DUST)],
    Some(change_script),
    Some(vec![0; 80]),
    1, // sat/vbyte
)
.unwrap();

let actual_vbytes = tx.transaction().weight().to_wu().div_ceil(4);

// fee() == needed_fee() when the change output is created, but both were
// calculated without the OP_RETURN output.
assert_eq!(tx.fee(), tx.needed_fee());
assert!(tx.fee() < actual_vbytes);
```

The assertion follows because `calculate_weight_vbytes` was invoked with `payments` rather than `tx_outs`, omitting the `OP_RETURN` output already pushed at lines 193-202. [2](#0-1)
