## Analysis

The original bug describes a **rate-change/accrual-settlement gap**: an emission rate is changed in place without first "closing out" the reward index for the elapsed period under the old rate, so a stale/mixed rate gets applied across a rate-change boundary.

The direct structural analog in this repo lives in `pallet-consensus-incentives`, which pays relayers `(latest_height − baseline) × cost_per_block` for the *entire unpaid span* of a state machine's consensus advancement, using whatever `cost_per_block` happens to be in storage at the moment the reward is computed — not the rate(s) that were actually in effect while each of those blocks were produced.

### The mechanism

`update_cost_per_block` simply overwrites the map value with no settlement step: [1](#0-0) 

`calculate_reward` computes the reward for the *whole* unpaid span (`latest_height - baseline`, where `baseline` is the `LastRewardedHeight` watermark) multiplied by whatever `block_cost` is passed in — i.e., the value read from `StateMachinesCostPerBlock` at the time `process_message`/`on_executed` runs: [2](#0-1) 

`process_message` reads the current rate and pays the full span in one shot, then moves the watermark forward — there's no per-height rate bucketing and no "flush the outstanding span at the old rate before changing it" step, unlike the reported `market_two` bug where `increase_share_indexes` must run before the emission rate changes: [3](#0-2) 

### Why this is exploitable by an unprivileged actor

The watermark (`LastRewardedHeight`) only advances when a relayer actually submits a consensus message that triggers `on_executed`. A relayer fully controls *when* they submit an already-available, valid consensus proof — nothing forces them to submit continuously. So a relayer can:

1. Withhold submission of valid consensus proofs while the state machine's remote height keeps advancing (this is a normal, permissionless choice by the relayer — no compromised keys, no colluding admin, no malicious peer needed).
2. Wait for a routine, legitimate governance rate change (`update_cost_per_block`) to raise `cost_per_block` for that `state_machine_id`.
3. Immediately after the rate increases, submit the accumulated proof covering the entire backlog span from the old `LastRewardedHeight` watermark to the new `latest_height`.
4. `calculate_reward` pays `(latest_height − baseline) × NEW_cost_per_block` for the *entire* backlog — including all the blocks that accrued while the *old*, lower rate was in force — draining the treasury for the delta between old and new rate times the backlog size.

The reverse (rate cut) causes the opposite: honest relayers who withheld/failed to submit before a decrease get underpaid for work done under the old, higher rate — a fund-loss scenario for the relayer instead of the treasury, but still a corrupted-value bug from the same root cause.

Existing guards don't stop this: the `LastRewardedHeight` watermark only prevents *double* payment for the same span (replay), it does nothing to bind a sub-span of blocks to the rate that was active when those blocks were produced. There's no per-rate-epoch accounting comparable to `increase_share_indexes` in the reported bug.

### Title
Consensus-incentive rewards apply the current `cost_per_block` retroactively across the entire unpaid block span, letting a relayer arbitrage a rate change to drain the treasury - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::calculate_reward` pays a relayer for the whole `latest_height - LastRewardedHeight` span using the single `cost_per_block` value stored *at the moment the reward is computed*. Because relayers choose when to submit consensus messages, this lets a relayer bank an unpaid backlog through a governance rate change and collect the *entire* backlog at the post-change rate, instead of the rate(s) that were actually in effect for each portion of the span.

### Finding Description
`update_cost_per_block` mutates `StateMachinesCostPerBlock` in place with no accrual/settlement step: [4](#0-3) . `calculate_reward` then multiplies the full unpaid height span by whatever rate is currently stored: [5](#0-4) . The watermark `LastRewardedHeight` only advances on delivery, so an attacker relayer that simply delays delivering an already-valid consensus proof accumulates a large unpaid span priced entirely at whichever rate happens to be active when they finally deliver it: [3](#0-2) .

### Impact Explanation
This is a direct treasury fund-loss/theft vector: `T::Currency::transfer` pays from `TreasuryAccount` to the relayer for the miscalculated amount [6](#0-5) . A relayer can multiply their payout by the ratio of new-to-old rate over an arbitrarily large backlog, with no cap on `blocks` in `calculate_reward`.

### Likelihood Explanation
Requires only permissionless timing control by any relayer holding valid consensus proofs and a (routine, expected) governance rate update — no admin collusion, no compromised keys, no malicious peer/prover. Rate updates to `StateMachinesCostPerBlock` are a normal operational action, and the exploit window opens automatically whenever one occurs while a backlog exists.

### Recommendation
Before applying a new `cost_per_block`, settle/flush any outstanding unpaid span at the old rate (mint/transfer or checkpoint it), mirroring `increase_share_indexes` from the referenced fix — e.g., have `update_cost_per_block` force-settle all pending rewards for that `state_machine_id` at the *current* rate (advancing `LastRewardedHeight` to `latest_height` and paying out) before writing the new rate, so no span is ever priced at a rate that wasn't in effect while it accrued.

### Proof of Concept
1. Relayer observes `state_machine_id X` has `cost_per_block = 10`, and `LastRewardedHeight = 1000`.
2. Relayer refrains from submitting consensus proofs for X even though the remote chain is advancing (proofs remain valid/deliverable), letting `latest_height` climb to 2000 without triggering `on_executed`.
3. Governance later raises `cost_per_block` to 1000 for X via `update_cost_per_block` (a routine parameter update, unrelated to the attacker).
4. Relayer immediately submits the deferred proof; `on_executed` → `process_message` → `calculate_reward` computes `(2000 - 1000) * 1000 = 1,000,000` instead of the ~`10,000` that should have accrued while the old rate was active, and the treasury pays out the inflated amount [7](#0-6) .

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
