### Title
Unrecovered type-assertion panic in the `pointer` precompile's `AddCW20`/`AddCW721`/`AddCW1155` handlers crashes block processing when pointing at an attacker-controlled CW contract - ([File: precompiles/pointer/pointer.go])

### Summary
The `pointer` precompile's CW→ERC pointer-creation handlers (`AddCW20`, `AddCW721`, `AddCW1155`) unmarshal a JSON query response from an arbitrary, caller-supplied CosmWasm contract into a `map[string]interface{}` and then perform unchecked type assertions (`formattedRes["name"].(string)`, `formattedRes["symbol"].(string)`) on attacker-controlled data. Any EVM caller can invoke `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` against a contract they deploy and control, whose `token_info`/`contract_info` query response returns a non-string (or missing) `name`/`symbol` field, causing a Go panic inside precompile execution.

### Finding Description
`AddCW20`, `AddCW721`, and `AddCW1155` in `precompiles/pointer/pointer.go` (and all `precompiles/pointer/legacy/*` versions) call `p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, ...)` against a CW contract address supplied directly by the EVM caller (`args[0].(string)`), then do: [1](#0-0) 
```go
formattedRes := map[string]interface{}{}
if err := json.Unmarshal(res, &formattedRes); err != nil {
    return nil, 0, err
}
name := formattedRes["name"].(string)
symbol := formattedRes["symbol"].(string)
```
Since `QuerySmartSafe` returns whatever JSON the target CW contract's `token_info`/`contract_info` query handler produces, an attacker who deploys a malicious CW20/CW721/CW1155 contract can make that query return `{"name": 123}` (or omit `name` entirely, or return `null`), causing `formattedRes["name"]` to be `nil` or a non-string type. The bare type assertion `.(string)` (without the `, ok` form) then panics with `interface conversion: interface {} is nil, not string` (or similar).

This differs from the pattern used everywhere else in this codebase — precompile executors elsewhere explicitly wrap execution in `defer recover()` to convert gas-meter/library panics into `execution reverted` errors: [2](#0-1) 
The generic precompile dispatcher (`precompiles/common/precompiles.go` `Run`), which the `pointer` precompile uses, has no `recover()` at all — it only inspects the returned `err` value: [3](#0-2) 
So a panic raised inside `AddCW20`/`AddCW721`/`AddCW1155` is not caught by the precompile framework and propagates up through the EVM interpreter/state-transition call stack into `ProcessBlock`.

`app.App.ProcessBlock` has a top-level `recover()` that catches this panic and turns the *entire block's* processing into an error: [4](#0-3) 
```go
defer func() {
    if r := recover(); r != nil {
        ...
        err = fmt.Errorf("ProcessBlock panic: %v", r)
        events = nil
        txResults = nil
        endBlockResp = abci.ResponseEndBlock{}
    }
}()
```
This means a single malicious transaction embedded anywhere in a block can cause the whole block's `events`, `txResults`, and `endBlockResp` to be discarded and an error returned from `ProcessBlock`, rather than just failing that one transaction with `execution reverted` as intended by the precompile framework's error-handling contract.

### Impact Explanation
Because the panic is deterministic given the same malicious CW contract and its (attacker-controlled) query response, every validator that processes the block containing the triggering transaction hits the same panic and the same `ProcessBlock` failure. This is a full-block processing failure reachable from a single unprivileged, unprivileged-permission EVM transaction (contract deployer + one caller), analogous in effect to CVE-2019-2585 (an easily-reachable operation causing a repeatable crash/hang of the server process) — here the "server" is block execution, and repeated submission of such transactions can repeatedly disrupt block processing, causing a validator-halt / block-delay condition rather than clean, isolated transaction reversion. This qualifies as validator halt / block delay impact under the stated validation criteria.

### Likelihood Explanation
High likelihood of triggering: any account can deploy a CosmWasm contract with a `token_info`/`contract_info` query handler that returns a JSON object lacking a `name`/`symbol` string field (e.g., returning an integer, `null`, or omitting the key), then call `addCW20Pointer`, `addCW721Pointer`, or `addCW1155Pointer` on the pointer precompile (`0x...100b`) pointing at that contract from a normal EVM transaction. No special privileges, large funds, or race conditions are required — deploying a CW contract and calling the precompile once is sufficient.

### Recommendation
Replace the unchecked type assertions with the safe two-value form and return a normal precompile error (not a panic) when the field is missing or of the wrong type, e.g.:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw contract token_info response missing/invalid name field")
}
symbol, ok := formattedRes["symbol"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw contract token_info response missing/invalid symbol field")
}
```
Apply this fix to `AddCW20`, `AddCW721`, and `AddCW1155` in `precompiles/pointer/pointer.go` and all versioned copies under `precompiles/pointer/legacy/*`. Additionally, consider adding a `defer recover()` guard in the shared `Precompile.Run` dispatcher (`precompiles/common/precompiles.go` and its legacy variants) so that any future unexpected panic inside an executor is downgraded to `execution reverted` for that single transaction instead of aborting the entire block in `ProcessBlock`.

### Proof of Concept
1. Deploy a CosmWasm contract whose `token_info` query handler responds with `{"name": 12345, "symbol": "X", "decimals": 0, "total_supply": "0"}` (a non-string `name`), or omits the `name` field entirely.
2. From any EVM account, call the `pointer` precompile at `0x000000000000000000000000000000000000100b` with `addCW20Pointer(<contract_bech32_address>)`.
3. `AddCW20` in `precompiles/pointer/pointer.go` unmarshals the response and executes `formattedRes["name"].(string)`, which panics because the underlying value is not a string (or is `nil`).
4. The panic is not caught by `precompiles/common/precompiles.go`'s `Run` (no `recover()`), propagates through EVM execution, and is only caught by `app.App.ProcessBlock`'s top-level `recover()`, which discards the entire block's `events`/`txResults`/`endBlockResp` and returns an error, disrupting block processing for all validators that include this transaction.

Note: I was unable to fully trace whether an intermediate layer (e.g., the go-ethereum `vm.EVM.Call`/`Create` precompile dispatch path) independently recovers panics before they reach `ProcessBlock`; the `precompiles/common/precompiles.go` `Run` function itself has no such recovery, and `ProcessBlock`'s recover comment/structure indicates it is designed to catch exactly this class of panic. Confirming the exact intermediate call path would benefit from a live Devin session with full build/test access.
