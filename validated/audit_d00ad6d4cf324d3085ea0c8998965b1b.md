### Title
Path-quoting mismatch between `git diff --check` output and `git status --porcelain=2 -z` output causes conflict marker counts to be silently lost - (File: `app/src/lib/git/diff-check.ts`)

### Summary
`getFilesWithConflictMarkers` derives its map keys from the human-readable, potentially quoted/escaped output of `git diff --check`, while `getMergeConflictDetails`/`getRebaseConflictDetails`/`getWorkingDirectoryConflictDetails` look up those keys using the raw, unescaped path parsed from `git status --porcelain=2 -z`. For paths containing characters that Git quotes in non-`-z` output (e.g. an embedded CR, LF, backslash, or double-quote), the two representations of "the same" path diverge, so the map lookup misses and the conflict marker count silently falls back to `0`.

### Finding Description
`getFilesWithConflictMarkers` runs `git diff --check` and extracts the path with the regex `/^(.+):\d+: leftover conflict marker/gm`: [1](#0-0) 

Git's pathname quoting (`quote_c_style` in Git core) escapes control characters such as CR/LF and wraps the whole path in double quotes with backslash escapes whenever such output is not explicitly produced in the NUL-terminated machine format. `git diff --check`'s textual output is exactly this kind of "human" output, so a path containing an embedded CR would be printed as something like `"file\r.txt":3: leftover conflict marker in line`, and the regex above captures the *quoted, escaped* string `"file\r.txt"` verbatim as the map key.

By contrast, `parsePorcelainStatus` reads `git status --porcelain=2 -z`, splitting on NUL bytes, and the code comment explicitly documents that in this format "filenames containing special characters are not specially formatted; no quoting or backslash-escaping is performed": [2](#0-1) 

The parsed `IStatusEntry.path` therefore contains the *raw, unescaped* bytes, including the literal CR.

These two independently derived strings for the same file (`"file\r.txt"` quoted-escaped vs. raw `file\r.txt`) are never reconciled. `parseConflictedState` uses the raw `path` from status parsing to look up the count from the diff-check-derived map: [3](#0-2) [4](#0-3) 

Both call sites (`BothAdded` and `BothModified`) use `conflictDetails.conflictCountsByPath.get(path) || 0`, so a key mismatch is indistinguishable from "genuinely zero conflict markers" — the fallback silently swallows the error.

The whole chain is reached through the entrypoint `getConflictDetails`, which dispatches to the merge/rebase/working-directory variants, all of which call `getFilesWithConflictMarkers`: [5](#0-4) 

### Impact Explanation
When the mismatch occurs, `conflictMarkerCount` for a genuinely conflicted file is reported as `0` even though the file actually contains unresolved `<<<<<<<`/`=======`/`>>>>>>>` markers. This is a data-integrity issue in the conflicts UI: a file that GitHub Desktop's UI logic treats as "no markers left" may be presented differently than a file with markers remaining (e.g. not flagging it for the user's attention), increasing the risk that the user commits/pushes a file that still contains raw conflict markers, without a clear warning. I was not able to fully trace, within the available context, every downstream UI/commit-gating consumer of `conflictMarkerCount` to confirm whether it is used as a hard gate that blocks committing, or only as a display hint — this matters for how severe the "silent corruption of what the user commits" impact actually is, and should be verified before treating impact as certain to reach the commit path.

### Likelihood Explanation
This requires the attacker (repository content) to introduce a file whose path contains a control character that Git quotes in non-`-z` textual output (CR, LF, backslash, double quote, or non-ASCII bytes depending on `core.quotePath`), and for that file to end up in a merge/rebase/stash conflict. Git tree entries only forbid NUL and `/` in path components, so such filenames are constructible in a crafted repository, and checkout of such names is possible on POSIX filesystems (though not guaranteed on Windows, where CR is often disallowed in filenames, which would limit reproduction on that platform).

### Recommendation
Avoid relying on textual, quotable `git diff --check` output for path-keyed lookups. Either:
- Run `git diff --check` in a mode that disables path quoting (`-c core.quotePath=false`) and still be aware that other escapes (backslash/CR/LF) are applied regardless of `core.quotePath`, or
- Replace the regex-based `git diff --check` parsing with a machine-parseable approach (e.g., iterate over `conflictedFilesInIndex` paths directly and scan blob contents for conflict markers, keyed by the same raw paths obtained from `git status --porcelain=2 -z`) so both count and path come from the same trusted, unescaped source.

### Proof of Concept
1. Create a repository and, via a script (not the Desktop UI, since some OSes disallow typing CR into filenames), create a blob/tree entry for a file named `file\r.txt` (embedded CR) using low-level plumbing (`git hash-object`, `git update-index --cacheinfo`, `git write-tree`).
2. Set up a merge scenario so this path ends up with conflict markers and status `UU`/`AA`.
3. Run `git diff --check` manually and observe the printed line uses a quoted/escaped path (e.g. `"file\r.txt":N: leftover conflict marker in line`).
4. Run `git status --porcelain=2 -z` and observe the raw path bytes (containing the literal CR, unquoted) as documented in `app/src/lib/status-parser.ts`.
5. Confirm that `getFilesWithConflictMarkers`'s map key (from step 3) does not `===` the `path` used in `parseConflictedState` (from step 4), so `conflictDetails.conflictCountsByPath.get(path)` at `app/src/lib/git/status.ts:96`/`112` returns `undefined` and falls back to `0`.

function parseConflictedState(
  entry: UnmergedEntry,
  path: string,
  conflictDetails: ConflictFilesDetails

  switch (entry.action) {
    case UnmergedEntrySummary.BothAdded: {
      const isBinary = conflictDetails.binaryFilePaths.includes(path)
      if (!isBinary) {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
          conflictMarkerCount:
            conflictDetails.conflictCountsByPath.get(path) || 0,
        }

async function getConflictDetails(
  repository: Repository,
  mergeHeadFound: boolean,
  conflictedFilesInIndex: ReadonlyArray<IStatusEntry>,
  rebaseInternalState: RebaseInternalState | null
): Promise<ConflictFilesDetails> {
  try {
    if (mergeHeadFound) {
      return await getMergeConflictDetails(repository, conflictedFilesInIndex)
    }

    if (rebaseInternalState !== null) {
      return await getRebaseConflictDetails(repository, conflictedFilesInIndex)
    }

    // If there's conflicted files in the index but we don't have a merge head
    // or a rebase internal state, then we're likely in a situation where a
    // stash has introduced conflicts
    if (conflictedFilesInIndex.length > 0) {
      return await getWorkingDirectoryConflictDetails(
        repository,
        conflictedFilesInIndex
      )
    }
  } catch (error) {
    log.error(
      'Unexpected error from git operations in getConflictDetails',
      error
    )
  }
  return {
    conflictCountsByPath: new Map<string, number>(),
    binaryFilePaths: new Array<string>(),
  }
}
