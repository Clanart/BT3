### Title
SignableTransaction excludes the OP_RETURN data output from weight/fee calculation, underpaying the declared fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying caller-supplied `data` to `tx_outs`, but computes transaction weight via `calculate_weight_vbytes`, which is only ever passed `payments` — never the OP_RETURN-bearing `tx_outs`. Like the upstream bug (a buffer's accounted size diverging from its actual contents after an element is appended without being re-checked), the appended output is omitted from the size accounting, so `needed_fee` understates the real vsize.

### Finding Description
At `send.rs` lines 193-202, the OP_RETURN output (up to 80 bytes of data, checked at line 171) is pushed onto `tx_outs`. However, both weight computations use only `payments`:

- Line 204: `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`
- Line 226: `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`

Inside `calculate_weight_vbytes` (lines 85-94), the transaction's `output` vector is built exclusively from `payments`, so the OP_RETURN output (~11 bytes overhead + data, i.e. up to ~91 bytes ≈ 23+ vbytes) is never counted. Consequently:

1. `needed_fee` (= `fee_per_vbyte * vbytes`) is computed against a vsize that omits the data output.
2. The change amount at lines 228-233 is `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is equally understated.
3. The `TooLowFee` check at line 211 and `TooLargeTransaction` check at line 241 both run against the understated weight, so an oversized transaction can pass the `MAX_STANDARD_TX_WEIGHT` check.

The result is a signed transaction whose actual fee (`inputs - outputs`) equals the understated value: the transaction pays a lower sat/vbyte rate than `fee_per_vbyte` requested and than `needed_fee()` reports.

### Impact Explanation
An unprivileged party whose instruction/transaction data is relayed into a `SignableTransaction` (the `data: Option<Vec<u8>>` path is explicitly fed by untrusted instruction data the multisig is asked to spend over) can cause the multisig to produce a transaction paying materially less fee than intended — up to ~23+ vbytes × `fee_per_vbyte` sats short. Two consequences:

- The `DEFAULT_MIN_RELAY_TX_FEE` gate is evaluated on the underestimated vsize, so the broadcast transaction can fall below mempool minimum relay fee and never propagate/confirm. Since all inputs use `Sequence::MAX` (line 79/182) and there is no RBF/CPFP path in this wallet, the spent outputs — including the multisig's change — are locked in an unconfirmable transaction: funds committed but not spendable.
- `needed_fee()` lies to callers, and `TooLargeTransaction` admits transactions exceeding `MAX_STANDARD_TX_WEIGHT` once the omitted output is added back, producing non-standard, non-relayable transactions.

This is an incorrect size/fee accounting formula reachable purely via attacker-supplied `data` — analogous to appending to a shared buffer without re-checking capacity.

### Likelihood Explanation
Any spend flow that attaches OP_RETURN data (supported up to 80 bytes, line 171) triggers the miscalculation deterministically — no race, no collusion, no leaked key required. Whether the resulting transaction is non-relayable depends on `fee_per_vbyte` margins, but the fee discrepancy occurs on every data-carrying transaction.

### Recommendation
Pass the final `tx_outs` (or the data length) into `calculate_weight_vbytes` so the OP_RETURN output is included in the weight used for `needed_fee`, `fee_with_change`, the `TooLowFee` floor, and the `MAX_STANDARD_TX_WEIGHT` check. Alternatively compute the data output's serialized size explicitly and add it to the measured weight before deriving fees.
