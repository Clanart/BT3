## Analysis

The seed report's core invariant: **native `msg.value` forwarded into a swap can return unspent ETH to the calling contract, and that contract has no path to return/rescue that native balance** — it becomes permanently stranded.

`EvmHost` on EVM chains has this exact pattern, in three separate payable entry points that accept native token to cover protocol fees by routing through Uniswap V2: [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Excess native-token fee payments to `EvmHost.dispatch()`/`fundRequest()` become permanently stranded with no rescue path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` on `EvmHost` are all `payable` and, when `msg.value > 0`, call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard Uniswap V2 Router's `swapETHForExactTokens` treats the supplied `msg.value` as `amountInMax` and refunds any unused ETH to the immediate caller of the swap — which in this call is `EvmHost` itself (`address(this)` is also set as the token recipient, and the router's internal `msg.sender` for the refund is the Host contract, not the original end-user). Any ETH sent in excess of the exact `fee`/`post.fee`/`amount` therefore lands back inside `EvmHost`'s own balance instead of the user who originally paid it.

### Finding Description
This mirrors the `FeeBuyback` M-3 pattern exactly: a contract accepts `msg.value` as input to an aggregator/router swap, the swap can legitimately return leftover native token to the contract, and the contract's asset-recovery machinery does not cover native token. In `EvmHost`, the only fee-recovery/withdrawal logic that was inspected (e.g. relayer-fee refunds on request/response timeouts) operates exclusively on the ERC-20 `feeToken()` via `safeTransfer` — not on native ETH: [4](#0-3) [5](#0-4) 

Users cannot control the exact ETH amount they must send since it depends on live Uniswap pricing; any over-estimation (a normal, expected client behavior when quoting fees on-chain vs. execution-time slippage) leaves the difference trapped inside `EvmHost` with no corresponding accounting entry and no exposed function to sweep it back out to the payer or to governance.

### Impact Explanation
Every call to `dispatch()` (POST or GET) or `fundRequest()` paid with native token can leak user funds into the Host contract balance with no recovery mechanism, meeting the bounty's "loss of funds" impact class: value is neither returned to the rightful payer nor withdrawable by any authorized party through the paths examined.

### Likelihood Explanation
This triggers under ordinary usage — any caller who sends `msg.value` even marginally above the router's actual required input (which is common, since callers must pre-fund with a safety margin against price movement between quoting and execution) causes leftover ETH to be stranded in `EvmHost`. No malicious peer, relayer, or governance actor is needed; it's a normal unprivileged interaction with `dispatch{value: msg.value}(...)`.

### Recommendation
After the `swapETHForExactTokens` call, check `address(this).balance` (or track pre/post balance) and refund any leftover native token to `_msgSender()`/`post.payer` within the same transaction, mirroring the explicit refund pattern already used in `UniV3UniswapV2Wrapper.swapETHForExactTokens` (which forwards unspent ETH back to `msg.sender`): [6](#0-5) 
Alternatively/additionally, add an admin-gated native-token rescue function to `EvmHost` for any residual balance.

### Proof of Concept
1. User calls `EvmHost.dispatch(post)` with `post.fee = X` and sends `msg.value = X + delta` (a normal safety margin) as ETH.
2. `EvmHost` invokes `IUniswapV2Router02.swapETHForExactTokens{value: X + delta}(X, path, address(this), block.timestamp)`.
3. The router spends only enough ETH to acquire `X` fee tokens and refunds `delta` ETH — to `address(this)` (`EvmHost`), because the Host is the caller in that inner call, not the original user. [7](#0-6) 
4. `delta` ETH now sits in `EvmHost`'s balance permanently; no function in the reviewed contract (fee/timeout refund logic only handles `feeToken()` ERC-20) can move it back out.

**Note on completeness:** I was not able to review the entirety of `EvmHost.sol` (only ~200 lines around the dispatch/timeout functions were retrievable) to definitively confirm the total absence of any native-token sweep/rescue function elsewhere in the contract. If such a function exists elsewhere in the file, it would need to be checked against this exact refund path to confirm it actually recovers this specific stranded balance.
