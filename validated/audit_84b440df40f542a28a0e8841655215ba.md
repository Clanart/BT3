## Title
Withdrawal path checks only `escrowed == 0` instead of `escrowed >= amount`, so a legitimate fill/refund can underflow-revert and permanently strand escrowed funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` — the shared escrow-release routine used by both same-chain fills and cross-chain `RedeemEscrow`/`RefundEscrow` settlement — validates only that the escrow slot is non-zero before subtracting the requested `amount`, instead of validating `escrowed >= amount`. This mirrors the H-19 pattern in the external report: a state mutation/precondition is checked too loosely, so a legitimate settlement flow that arrives with a well-formed but non-matching amount hits an arithmetic revert deep in the call, permanently DoS'ing that settlement path and leaving user/solver funds locked in escrow.

### Finding Description
`_withdraw()` is the single choke point for releasing escrowed input tokens on both the same-chain and cross-chain settlement paths: [1](#0-0) 

The guard `if (escrowed == 0) revert UnknownOrder();` only rejects the case where nothing at all is escrowed for that `(commitment, token)` pair. It does **not** check `escrowed >= amount`. The very next line, `_orders[body.commitment][token] = escrowed - amount;`, is unchecked arithmetic protected only by Solidity 0.8's built-in overflow/underflow revert. If `amount > escrowed`, the whole transaction reverts.

The Tron variant of the same contract has the identical shape: [2](#0-1) 

This is the same broken invariant as the LienToken bug: a precondition check (`lien.last` update / `escrowed == 0`) is a coarse existence check rather than an exact-amount/state check, so a legitimate downstream flow (partial lien payment / partial-amount withdrawal) reverts on the arithmetic that follows, rather than degrading gracefully. For cross-chain settlement (`RedeemEscrow`/`RefundEscrow` messages delivered via `onAccept`), this call runs inside the ISMP message-handling path with `finalize=true`, so a revert here also prevents `_filled[commitment]` from being set and blocks the whole incoming message from being processed — there is no per-token partial-success path, no way to retry with a corrected amount, and no way for the order owner to intervene, since the withdrawal amounts are derived entirely from the message body constructed on the other chain and are not re-validated against the actual remaining escrow before the call.

Because `_orders[commitment][token]` is decremented per-input across potentially multiple fills/partial fills (`IntrinsicIntents._fillSameChain`) before the cross-chain leg or a subsequent cancellation runs, any accounting drift between what the destination chain believes was escrowed and what is actually left in `_orders` (e.g., due to a race between a same-chain partial fill and a cross-chain cancel/refund message referencing stale/full amounts) causes the withdrawal to permanently underflow-revert. Unlike the fee/protocol-share code paths in the same file which use `saturating` patterns or amount clamping (see `IntrinsicIntents._fillSameChain`'s `remaining`/`fillAmount` clamping), `_withdraw` has no clamping or partial-release fallback — it either fully succeeds or reverts the entire batch of tokens for that commitment, exactly the "partial bid reverts the whole liquidation" failure mode from the source report.

### Impact Explanation
A reverting `_withdraw()` call inside the cross-chain `onAccept` handling of `RedeemEscrow`/`RefundEscrow` means Hyperbridge's ISMP message delivery for that commitment cannot complete. The escrowed input tokens for the affected commitment become permanently stuck in the `IntentGatewayV2`/`IntentsBase` contract: the solver who legitimately filled the order on the destination chain, or the user who legitimately cancelled, can never redeem the corresponding escrow, because every retry of the same message hits the same underflow. This is a direct loss/lock of user and solver funds in the intent-settlement flow, matching the bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
Triggering this requires only an unprivileged, ordinary sequencing of otherwise-permitted actions — e.g., a solver partially filling a same-chain leg (which decrements `_orders`) racing with, or preceding, a cross-chain settlement message that was computed against the original (undecremented) escrow amount, or any other legitimate path where the amount encoded in the `WithdrawalRequest` body no longer matches the live `_orders[commitment][token]` balance at execution time. No malicious relayer, prover, or admin action is needed — the message itself is otherwise valid and authenticated; it just carries an amount that has since diverged from the escrow balance due to normal partial-fill/cancel state transitions.

### Recommendation
Replace the existence check with a sufficiency check and clamp/short-circuit rather than reverting the whole withdrawal:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
uint256 release = amount > escrowed ? escrowed : amount;
_orders[body.commitment][token] = escrowed - release;
// transfer `release` instead of `amount`
```
Alternatively, if the amount is expected to always equal the exact escrow, explicitly assert `escrowed == amount` up front with a dedicated error (e.g. `AmountMismatch`) so failures are diagnosable, and add an operational recovery path (e.g., a governance-triggered force-settle) so a divergence can never permanently strand funds the way an unrecoverable revert does.

### Proof of Concept
1. User places a same-chain order escrowing `1000 USDC` against a `1000 DAI` output; `_orders[commitment][USDC] = 1000`.
2. Solver partially fills 400 DAI, which proportionally releases 400 USDC from escrow via `_withdraw` (finalize=false): `_orders[commitment][USDC]` becomes `600`.
3. Before/concurrently, a cross-chain cancellation or an out-of-sync relayer submission causes a `RefundEscrow`/`RedeemEscrow` message to be delivered whose `WithdrawalRequest.tokens[i].amount` for USDC was computed as the original `1000` (e.g., built from order data rather than the live `_orders` balance, or replaying a message built before the partial fill was accounted for).
4. `onAccept` invokes `_withdraw(body, isRefund, finalize=true)`. Inside the loop: `escrowed = _orders[commitment][USDC] = 600`, `amount = 1000`. The `escrowed == 0` check passes (600 ≠ 0), but `_orders[commitment][token] = escrowed - amount` underflows and reverts.
5. The entire ISMP message processing for this commitment reverts; the remaining `600 USDC` is now unredeemable — no valid future message can carry the correct (now-current) `600` amount because the settlement amount is fixed by the message that was already dispatched/committed on the counterparty chain, permanently locking the residual escrow.

Note: I was not able to fully trace, within the available context, the exact code path in `ExtrinsicIntents.sol` that constructs the `WithdrawalRequest` for the cross-chain `RedeemEscrow`/`RefundEscrow` messages (i.e., whether the amount is always sourced fresh from `_orders` at dispatch time or can be a stale/order-derived value), so the precise reachability of the race in step 3 above is inferred from the shared `_withdraw` implementation and the partial-fill decrement logic in `IntrinsicIntents.sol` rather than confirmed end-to-end. A Devin session with full repo access should verify the exact `WithdrawalRequest` construction sites in `ExtrinsicIntents.sol` to confirm whether amounts can diverge from live escrow balances in production flows.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
