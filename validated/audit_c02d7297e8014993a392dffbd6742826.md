### Title
Semantic overload of `AppFileStatusKind.Conflicted` lets already-committed conflict markers be staged and committed without re-verification - (File: `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop uses a single enum member, `AppFileStatusKind.Conflicted`, to represent two very different file states: a file that *still has unresolved conflict markers* and a file that *has already been resolved* (either by removing the markers in an editor or by picking a manual `ours`/`theirs` resolution). This is the same class of bug as the Audius `No` outcome overload: one status value is forced to carry two distinct meanings, and every caller must remember to consult a secondary field (`conflictMarkerCount`, or the presence of a `manualResolution`) to tell them apart.

### Finding Description
The model defines the overloaded status here: [1](#0-0) 

`isConflictedFileStatus`/`isConflictedFile` only check `kind === AppFileStatusKind.Conflicted`, which is true for both a genuinely conflicted file and a resolved-but-not-yet-recognized-as-clean one: [2](#0-1) 

The application is fully aware this is ambiguous — `mapStatus` has to branch on `conflictMarkerCount` to decide whether to *display* "Conflicted" or "Resolved" for the exact same `kind`: [3](#0-2) 

The correct way to disambiguate is `hasUnresolvedConflicts`, which requires checking `conflictMarkerCount` (or a manual resolution) in addition to `kind`: [4](#0-3) 

The UI paths that gate user-facing actions (the "Continue rebase"/"Continue merge" buttons) correctly use this disambiguated helper via `getConflictedFiles`: [5](#0-4) [6](#0-5) 

However, the actual commit-producing code path, `_finishConflictedMerge`, filters files using only the raw, overloaded `kind` check — not `hasUnresolvedConflicts`/`getConflictedFiles` — and then stages every non-manually-resolved file exactly as it sits on disk: [7](#0-6) 

Because `createMergeCommit` explicitly documents that it "assumes that all conflicts have already been resolved" and does **not** re-validate marker state before staging/committing: [8](#0-7) 

...the only thing preventing a file that still has live `<<<<<<<`/`=======`/`>>>>>>>` markers from being staged and committed is the *UI-level* gate (`conflictedFilesCount > 0` disabling the Continue button, computed from a `workingDirectory` snapshot passed down as props). Because the commit path itself re-derives "conflicted" from the overloaded `kind` alone rather than re-checking `conflictMarkerCount`/manual resolution at commit time, any staleness between the last rendered status and the moment `_finishConflictedMerge` runs (e.g., a file that an external process, git hook, or attacker-controlled merge driver re-populates with conflict markers after the UI last read status but before the click handler executes) results in that file being staged and committed with its raw on-disk content — including any lingering conflict markers or attacker-injected content — with no second check server-side (i.e., in the store/git layer) to catch it.

### Impact Explanation
If a merge or rebase brings in attacker-influenced content (e.g., a malicious remote/fork whose merge driver or `.gitattributes` re-triggers conflicted state, or a race with an external editor/tool writing to the file) that recreates the "Conflicted" `kind` after the render-time check but the commit path treats the file as already staged, GitHub Desktop can silently commit and push a file whose content still contains raw conflict markers or unintended text from the "wrong" side. This is a "silent corruption of what the user commits/pushes" scenario: the user believes they resolved conflicts (dialog says "Continue"), but the artifact placed into the commit reflects the file's actual on-disk state at staging time, not the state the UI validated. Because `createMergeCommit` performs no independent verification (no `git diff --check`, no `getFilesWithConflictMarkers` re-scan) before committing, there is no server-side backstop.

### Likelihood Explanation
This requires a timing window between the UI's cached `workingDirectory` state and the moment `_finishConflictedMerge`/`createMergeCommit` executes, or a file whose `kind` remains `Conflicted` for a reason other than unresolved text markers (e.g., binary/manual conflicts where `conflictMarkerCount` doesn't even exist and `isManualConflict` must be relied on). This is a real, code-supported gap (the commit path literally re-derives the "conflicted" set with a weaker check than the UI), but exploiting it to cause user-visible corruption needs a specific race or an interaction with an external tool modifying the working directory during the merge-conflict flow — it is not trivially triggerable by a static "malicious repo" alone. This lowers likelihood relative to a report severity, but the underlying architectural bug (checking `kind` instead of `hasUnresolvedConflicts` at the point where content is actually staged) is objectively present and is a textbook case of the reported semantic-overloading bug class.

### Recommendation
Introduce a distinct discriminator instead of overloading `AppFileStatusKind.Conflicted`, e.g. split into `Conflicted` and `ConflictResolved` kinds (mirroring the suggested `Veto` outcome split in the original report), or, at minimum, make `_finishConflictedMerge`/`createMergeCommit` call `hasUnresolvedConflicts` (the same check the UI uses) immediately before staging each file, refusing to stage/commit any file that still reports unresolved markers, rather than trusting the caller's already-rendered `kind`.

### Proof of Concept
Conceptual reproduction (requires local Desktop instrumentation/debugger to verify the race, since it depends on timing rather than a single deterministic input):
1. Start a merge that produces a text conflict in `file.txt` (kind `Conflicted`, `conflictMarkerCount > 0`).
2. Open the "Resolve conflicts" dialog. Desktop reads working directory status and shows the file as unresolved (`getConflictedFiles` returns it, Continue disabled).
3. Before clicking Continue, have an external process (e.g., a slow merge driver, editor autosave, or malicious `smudge`/merge tool triggered by `.gitattributes` in the merged branch) rewrite `file.txt` back to a state that still has `kind: Conflicted` but where the app's last-known `workingDirectory` prop snapshot is stale relative to disk.
4. If the button is enabled from a stale prior evaluation (or a resolution is chosen for a different file while this file re-enters conflict), clicking "Continue" invokes `_finishConflictedMerge`, which filters purely on `f.status.kind === AppFileStatusKind.Conflicted` and stages the file via `stageFiles`/`git add` as-is, then commits it via `createMergeCommit` with no re-scan for conflict markers — producing a commit containing literal conflict-marker text or attacker content in `file.txt`. export function mapStatus(status: AppFileStatus): string {
  switch (status.kind) {
    case AppFileStatusKind.New:
    case AppFileStatusKind.Untracked:
      return 'New'
    case AppFileStatusKind.Modified:
      return 'Modified'
    case AppFileStatusKind.Deleted:
      return 'Deleted'
    case AppFileStatusKind.Renamed:
      return 'Renamed'
    case AppFileStatusKind.Conflicted:
      if (isConflictWithMarkers(status)) {
        const conflictsCount = status.conflictMarkerCount
        return conflictsCount > 0 ? 'Conflicted' : 'Resolved'
      }

      return 'Conflicted'
    case AppFileStatusKind.Copied:
      return 'Copied'
    default:
      return assertNever(status, `Unknown file status ${status}`)
  }

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

  public async _finishConflictedMerge(
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    manualResolutions: Map<string, ManualConflictResolution>
  ): Promise<string | undefined> {
    /**
     *  The assumption made here is that all other files that were part of this merge
     *  have already been staged by git automatically (or manually by the user via CLI).
     *  When the user executes a merge and there are conflicts,
     *  git stages all files that are part of the merge that _don't_ have conflicts
     *  This means that we only need to stage the conflicted files
     *  (whether they are manual or markered) to get all changes related to
     *  this merge staged. This also means that any uncommitted changes in the index
     *  that were in place before the merge was started will _not_ be included, unless
     *  the user stages them manually via CLI.
     *
     *  Its also worth noting this method only used in the Merge Conflicts dialog flow, not committing a conflicted merge via the "Changes" pane.
     *
     *  *TLDR we only stage conflicts here because git will have already staged the rest of the changes related to this merge.*
     */
    const conflictedFiles = workingDirectory.files.filter(f => {
      return f.status.kind === AppFileStatusKind.Conflicted
    })
    const gitStore = this.gitStoreCache.get(repository)
    return await gitStore.performFailableOperation(() =>
      createMergeCommit(repository, conflictedFiles, manualResolutions)
    )
  }

/**
 * Creates a commit to finish an in-progress merge
 * assumes that all conflicts have already been resolved
 * *Warning:* Does _not_ clear staged files before it commits!
 *
 * @param repository repository to execute merge in
 * @param files files to commit
 */
export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }

  const otherFiles = files.filter(f => !manualResolutions.has(f.path))

  await stageFiles(repository, otherFiles)
