## Title
`_cancelFromDest` in `IntentGatewayV2`/`ExtrinsicIntents` permanently marks `_filled[commitment]` before any escrow is verified to exist, letting an unprivileged caller lock a not-yet-placed order out of ever being filled - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The Tidal report's core defect is: a one-shot, idempotency-style state flag (`coverage.refunded`) is written unconditionally by a public function *before* verifying that the value it is meant to gate (`refundMap[...]`) has actually been allocated, so an attacker can burn the flag on a zero/unallocated case and permanently deny the real, later allocation. The same broken invariant exists in `_cancelFromDest`, which unconditionally sets the one-shot `_filled[commitment]` mapping without ever checking that the order it references was actually escrowed (i.e., without any analog of the `UnknownOrder` check that its sibling function `_cancelFromSource` performs).

### Finding Description
`_cancelFromDest` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:240-267`) is reachable by any address once `order.deadline < block.number`: [1](#0-0) 

Unlike `_cancelFromSource`, which requires proof that escrow exists for the commitment before doing anything (`if (_orders[commitment][token] == 0) revert UnknownOrder();`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol:193-200`), `_cancelFromDest` performs **no such check on the destination chain** — it cannot, because escrow for cross-chain orders lives only on the source chain. It simply writes `_filled[commitment] = order.user` and fires off a `RefundEscrow` request. `order` itself is fully attacker-supplied calldata (there is no on-chain record of "real" orders — commitments are computed ad hoc from whatever struct the caller passes in), and `commitment = keccak256(abi.encode(order))`.

Compare with `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:89-171`), which is the only path a solver can use to actually deliver output tokens to a beneficiary; it starts with `_filled[commitment] = msg.sender;` and is not otherwise guarded against a pre-existing `_filled` entry via any allow-recovery path — once `_filled[commitment]` is non-zero the destination chain treats that commitment as settled for `isOrderFilled`/`isOrderRefunded` purposes (per the SDK docs, `isOrderFilled` and `isOrderRefunded` "can both be true simultaneously").

Because `order.deadline` is a field the caller/attacker fully controls when constructing the calldata struct for `_cancelFromDest`, the "after deadline, anyone can cancel" bypass is satisfied by simply choosing a `deadline` value that is already in the past relative to `block.number`, for *any* commitment the attacker wants to poison — including a commitment matching an order a legitimate user is about to place with that same (already-in-the-past-looking, but originally intended) deadline. There is no `_orders[commitment]`-based check gating this destination-side write, no signature check binding `order.user` to a real off-chain intent, and no verification that the `PostRequest`/escrow ever existed. This mirrors the Tidal bug precisely: a public entrypoint permanently writes a one-shot "settled" flag for a key that has no allocation behind it yet, and that flag can never be undone because there is no unset path once written (the source-chain `_withdraw` — `evm/src/apps/intentsv2/IntentsBase.sol:390-401` — will simply revert with `UnknownOrder()` on the source side since `escrowed == 0` there, but that revert does **not** roll back the destination-side `_filled[commitment]` write that already committed on this chain in the same/earlier transaction).

### Impact Explanation
Once `_filled[commitment]` is set for a commitment that legitimately corresponds to an order a user is about to place, that order can never be filled cross-chain: `_fillCrossChain`/the top-level `fillOrder` entrypoint treats the commitment as settled. If the user does go on to place and escrow the order on the source chain (unaware the destination-side commitment was pre-poisoned), the input tokens land in escrow with no solver able to fill and, since the destination-side `RefundEscrow` message that would normally accompany a legitimate cancel already reverted (or was never delivered against real escrow), the user has no straightforward path to recover funds — this is fund lock and unauthorized settlement-state manipulation of the type explicitly in-scope (loss/lock of funds, transaction manipulation, false state acceptance of "already filled/cancelled").

### Likelihood Explanation
This requires no privileged role, no relayer/prover compromise, and no front-running — it needs only knowledge of the deterministic order fields (source, destination, deadline, inputs/outputs, user, nonce) that a user's off-chain intent tooling would need to publish or that are otherwise predictable/replayable for orders with a fixed deadline. The likelihood is capped by the fact that in-scope EVM Solidity test files (`evm/tests/foundry/IntentGatewayV2Test.sol`) demonstrate exactly this call path (`testRefundEscrowOnSourceChainAfterDestinationCancellation`, `testCancelOrderFromDestinationChainByAnyoneAfterExpiry`) is functional and permissionless once `order.deadline` has elapsed, which is the exact gate the attacker needs to satisfy.

### Recommendation
`_cancelFromDest` should not be allowed to mark `_filled[commitment]` for a commitment that has no corresponding proof of source-chain escrow. Since destination-side code cannot directly read source-chain storage, the write to `_filled[commitment]` should instead only be finalized once the source-chain `withdraw()` path confirms real escrow existed (i.e., invert the ordering the way `_cancelFromSource` already does: verify state before mutating), or `_cancelFromDest` should require a signed authorization/proof binding the caller to a real, previously-registered order rather than accepting an arbitrary attacker-constructed `Order` struct.

### Proof of Concept
1. Attacker crafts an `Order` struct with `deadline` in the past (relative to current `block.number`) matching fields a target user intends to submit later (source/destination chains, inputs/outputs, `user` = target's address).
2. Attacker calls `cancelOrder(order, cancelOptions)` on the destination chain. `order.deadline < block.number` passes the "anyone may cancel" branch in `_cancelFromDest` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:241-243`).
3. `_filled[commitment] = order.user` is set (`ExtrinsicIntents.sol:245`) and a `RefundEscrow` `DispatchPost` fires toward the source chain; on delivery, source-side `_withdraw` reverts with `UnknownOrder()` (`IntentsBase.sol:401`) because no escrow exists yet — but this revert does not undo the destination-chain state already committed.
4. The target user later calls `placeOrder`/escrows the identical order on the source chain.
5. No solver can ever successfully call `fillOrder` for this commitment on the destination chain because `_filled[commitment]` is already non-zero, permanently blocking settlement and stranding the user's escrowed input tokens on the source chain. [2](#0-1) [3](#0-2)

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
