### Title
Unbounded low-level callback calls in `EvmHost` dispatch functions allow permanent griefing/locking of in-flight requests, responses and relayer rewards - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming` (both `PostRequest` and `GetResponse` overloads) and `EvmHost.dispatchTimeOut` (both overloads) invoke the destination/source application's callback via an un-gassed, un-bounded low-level `.call(...)`, discarding the returned bytes with the `(bool success,)` pattern. This is the same broken invariant as the `ProtocolFees` bug in the seed report: a low-level external call whose return data is implicitly decoded into memory by the Solidity ABI-decoding step for the `(bool, bytes memory)` tuple, even though the caller never reads the `bytes` value. Any address can be registered as the `to`/`from` module of an ISMP message (there is no allow-list on destination contracts), so an attacker can deploy a malicious "app" that returns/reverts with an attacker-sized payload to inflate the caller's memory-copy cost. ### Finding Description
In `dispatchIncoming(PostRequest memory request, address relayer)`, `dispatchIncoming(GetResponse memory response, address relayer)`, `dispatchTimeOut(GetRequestTimeout, ...)` and `dispatchTimeOut(PostRequestTimeout, ...)`, the module callback is invoked with the full remaining gas of the enclosing transaction and no cap on the size of return data:

```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
```

Unlike the Uniswap `ProtocolFees` pattern (which at least bounds the call by `controllerGasLimit`), here there is *no* gas stipend at all — the callee can consume essentially all of the transaction's remaining gas, and can additionally return or revert with an arbitrarily large payload. Solidity's generated code for `x.call(data)` always copies the full `returndatasize()` into freshly allocated memory to build the `bytes memory` return value even when the caller discards it via `(bool success,)`. That copy is charged against the **caller's** gas (the relayer executing `HandlerV2.handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts`), and memory-expansion cost is quadratic and cumulative across the whole transaction.

These `dispatch*` functions are invoked in a loop, once per leaf, from the batch handler entry points: [4](#0-3) [5](#0-4) 

so a single attacker-controlled leaf mixed into a batch of otherwise-legitimate leaves inflates the memory-expansion cost for the *entire* transaction, not just the malicious call. Existing guards do not stop this:
- `notFrozen(host)` and the challenge-period/Merkle proof checks in `HandlerV2` only validate that the *messages* are authentic; they do nothing to bound the gas or return-data size of the *destination module's* callback.
- The `if (!success) { delete receipt; return; }` fallback in `EvmHost` only handles an explicit revert from the callback — it does not prevent the return-data copy from happening, and it does not protect the rest of the batch from the accumulated memory cost already paid before/while executing that leaf.
- There is no per-call gas cap (e.g. `{gas: X}`) and no assembly-level bounded copy (e.g. `returndatacopy` limited to 32 bytes) anywhere in these four call sites.

### Impact Explanation
Because `to`/`from` module addresses are attacker-deployable and unrestricted, an attacker can register a malicious module and either (a) receive a legitimate cross-chain message routed to it (e.g. as the destination of a `HyperFungibleToken`/`TokenGateway` transfer, or an intents `IntentGatewayV2` settlement callback) or (b) simply be one leaf among many batched by the relayer. On invocation, the malicious module returns/reverts with a large payload, driving up the memory-expansion cost paid by the relayer for the remainder of the batch. This can push the transaction's actual gas consumption past the relayer's pre-computed gas limit (computed via `estimate_gas`/`debug_traceCall` in `tesseract/messaging/evm/src/provider.rs`), causing the whole batch (including unrelated, legitimate requests/responses/timeouts) to run out of gas and revert. Because delivery, relayer-fee payout (`safeTransfer(relayer, fee)` in `dispatchIncoming`/`dispatchTimeOut`), and receipt bookkeeping only occur on a successful top-level execution, repeated griefing can indefinitely prevent delivery of the batched messages and permanently strand the associated escrowed relayer fees/assets — a fund-lock outcome, not merely wasted gas.

### Likelihood Explanation
Any unprivileged address can deploy a contract implementing `IApp` and be named as the `to`/`from` of a dispatched ISMP message (no allow-list exists in `EvmHost`/`HandlerV2`). Getting that message batched alongside victim messages requires no special relayer collusion — batching is a normal operational behavior of relayers processing pending messages together for gas efficiency. No admin, prover, or relayer compromise is required; the only prerequisite is being the recipient contract of at least one in-flight message, which an attacker fully controls by deploying their own malicious module and dispatching (or being dispatched) a message to it.

### Recommendation
Bound both dimensions of every module callback in `EvmHost`:
1. Forward a fixed, capped gas stipend (`.call{gas: MODULE_CALLBACK_GAS_LIMIT}(...)`) instead of forwarding all remaining gas.
2. Avoid the implicit `(bool, bytes memory)` decoding pattern; perform the call in inline assembly and only copy a small, fixed number of bytes (e.g. 32) from `returndatasize()`, mirroring the fix adopted for `ProtocolFees` in Uniswap v4-core.
3. Consider isolating each leaf's dispatch in a way that a single malicious leaf's gas/memory blow-up cannot affect accounting or delivery of the other leaves in the same batch.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept` such that it does:
```solidity
function onAccept(IncomingPostRequest calldata) external override {
    assembly {
        return(0, 0x100000) // return ~1MB of zeroed memory
    }
}
```
2. Attacker dispatches (or is the destination of) a `PostRequest` whose `to` is `EvilApp`.
3. A relayer batches this leaf together with N legitimate `PostRequest` leaves and calls `HandlerV2.handlePostRequests`.
4. `EvmHost.dispatchIncoming` calls `EvilApp.onAccept`, which returns 1MB of data; the low-level `.call` in `EvmHost` implicitly copies that returndata into the caller's memory even though the destructured value is discarded, consuming disproportionate gas against the relayer's estimated gas budget.
5. With enough return-data size (tunable by the attacker at negligible cost, since the callee only needs `RETURN`/`REVERT` with a large size argument), the enclosing `handlePostRequests` transaction runs out of gas and reverts, failing to deliver all N legitimate requests in that batch and leaving their relayer fees/escrow locked pending re-submission — repeatable indefinitely by re-including the same malicious leaf in future batches.
