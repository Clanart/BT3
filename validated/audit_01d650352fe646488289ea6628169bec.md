### Title
`ReplacementDeposit` accepted with no on-chain check that `old_move_txid`'s output was ever spent (let alone by *any* security council) - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` never inspects the *inputs* of the transaction that funds a `ReplacementDeposit`'s `deposit_outpoint`; it only checks that the outpoint's *output* amount/script and confirmation height are correct. The `old_move_txid` cited in `ReplacementDepositScript` is purely opaque data pushed inside an `OP_FALSE OP_IF ... OP_ENDIF` branch, never validated against `deposit_tx.input[..].previous_output`, so no code path ever confirms a real spend (by nofn or by any security council, current or past) of the cited `old_move_txid` output actually occurred.

### Finding Description
The binding this system is supposed to enforce is:
`ReplacementDeposit.old_move_txid` output was really consumed by an authorized spend (nofn signature OR the security council governing that deposit at the time) == the `deposit_outpoint` transaction that funds the new replacement deposit.

Tracing `Verifier::is_deposit_valid` (`core/src/verifier.rs:541-732`):
1. It checks `deposit_data.security_council == self.config.security_council` (verifier's *current* config) at [1](#0-0) .
2. It computes `expected_scriptpubkey` from `deposit_data.get_deposit_scripts(...)`, which for `DepositType::ReplacementDeposit` builds `ReplacementDepositScript::new(nofn_xonly_pk, replacement_deposit_data.old_move_txid)` plus `Multisig::from_security_council(self.security_council.clone())` (i.e. the *current* council) at [2](#0-1) .
3. It fetches `deposit_tx = self.rpc.get_tx_of_txid(&deposit_txid)` and only checks `deposit_tx.output[vout].value` and `.script_pubkey` against the expected values, plus the confirmation block height, at [3](#0-2) . **At no point does it read `deposit_tx.input` to confirm that this transaction actually spends `old_move_txid`'s UTXO.**

`ReplacementDepositScript::to_script_buf` shows why this matters: the `old_move_txid` is pushed as inert data inside a dead `OP_FALSE OP_IF` branch, not enforced by Bitcoin Script at all: [4](#0-3) . The only Script-enforced spend condition on the new `deposit_outpoint` is `CheckSig(new_nofn_xonly_pk)` OR `Multisig(current_security_council)` — nothing that ties this UTXO's *creation* to a real consumption of the cited old vault.

Consequently, `old_move_txid` is nothing more than an unverified label. An attacker can fund a `deposit_outpoint` UTXO with their own bitcoin (matching only the expected `scriptPubKey`, which is fully computable off-chain) and cite *any* `old_move_txid` — including a genuine, currently-unspent move-to-vault output belonging to a completely different, honest deposit (created under security council A, B, or any config) — and `is_deposit_valid` will accept it as a valid replacement, because the check only cares that the *new* outpoint's own script/amount matches, never that the *old* outpoint was actually spent by anyone.

This is a strictly broader break than "wrong security council was used to spend it": no spend of `old_move_txid` is required at all for the check to pass. The specific scenario in the question (citing a deposit signed under an old security council after rotation) is a subset of this general break — it also passes, but so does citing an entirely unrelated, never-touched deposit.

### Impact Explanation
Once accepted, `deposit_sign`/`create_movetx` will have verifiers co-sign a *new* move-to-vault transaction for this bogus replacement, and downstream flows (e.g. `register_replacement_deposit_to_citrea`) tell Citrea to treat the new move-to-vault txid as the vault backing the withdrawal rights previously associated with `old_move_txid`. The real, cited `old_move_txid` output is never touched by this process — it remains a live, unspent UTXO on Bitcoin that no protocol flow will ever reference again once Citrea's bookkeeping is repointed to the new (attacker-funded) vault. This matches the Critical category "a move-to-vault UTXO permanently frozen": the original depositor's/bridge's BTC becomes unreachable through any future protocol path, while the attacker only had to fund an ordinary looking deposit of `bridge_amount` (which functions economically like an ordinary deposit for them). This is repeatable against every existing move-to-vault UTXO on the network, by any unprivileged actor who can construct a taproot output and get verifiers to sign.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (a) knowledge of any real move_to_vault txid (all such txids are public on Bitcoin), (b) enough BTC to fund one `bridge_amount` deposit into a taproot address they can precompute (`ReplacementDepositScript(new_nofn_xonly_pk, chosen_old_move_txid)` + `Multisig(current_security_council)`), and (c) the ability to submit a `Deposit`/`ReplacementDeposit` gRPC request to the aggregator — all within the unprivileged capability set described. No key compromise, no majority hashrate, no TLS interception is needed. This is highly feasible and repeatable across every deposit currently in the bridge.

### Recommendation
In `Verifier::is_deposit_valid` (and any other place that validates a `ReplacementDeposit`), fetch the actual on-chain transaction that produced `deposit_outpoint` and require that one of its inputs' `previous_output` equals `(old_move_txid, UtxoVout::DepositInMove)`, and that the witness/script-path used to spend it corresponds to a valid nofn or the *security council that governed that specific old deposit* (not merely the current config's council). Persist/verify the old deposit's own security council (e.g., from stored deposit data keyed by `old_move_txid`) rather than trusting only the current `self.config.security_council` equality check.

```rust
// 1. Create deposit D under security_council A (config.security_council = A), run to completion
//    to obtain move_to_vault_txid = old_move_txid (never spend this UTXO).
// 2. Rotate config.security_council = B (simulating a key rotation).
// 3. As an unprivileged actor (no key shares), fund a fresh UTXO whose scriptPubKey equals
//    taproot([ReplacementDepositScript(new_nofn_pk, old_move_txid), Multisig(B)]) using ONLY
//    normal wallet funds (no signature from A, no signature from nofn on old_move_txid).
// 4. Submit this as deposit_outpoint in a ReplacementDeposit and call verifier.deposit_sign /
//    is_deposit_valid.
// 5. Assert: old_move_txid's UTXO is still unspent on chain (rpc.is_utxo_spent(old_move_txid_outpoint) == false)
//    AND is_deposit_valid returns Ok(()) — demonstrating acceptance despite no real spend of
//    old_move_txid ever happening, i.e., the binding
//    "replacement authorized by a real spend of old_move_txid" != "is_deposit_valid Ok(())".
```
