## Analysis

The external report's core defect is: **a reward pool is computed over an aggregate quantity (all funding votes) but the payout is attributed without checking that every unit of that aggregate belongs to the payee** — so the actor collects rewards for contributions it didn't actually make.

The direct Hyperbridge analog lives in `pallet-consensus-incentives`, the pallet that pays relayers in `$BRIDGE` for delivering BEEFY consensus proofs.

### Title
Consensus-incentive reward misattribution lets one relayer claim rewards for the entire batch's state-machine advances - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`FeeHandler::on_executed` for `pallet-consensus-incentives` identifies the relayer to be paid using **only the first message in the batch** (`messages.get(0)`), but then pays a reward for **every distinct `StateMachineId`** whose `StateMachineUpdated` event appears anywhere in the batch's event list. Any account that can get itself positioned as message index 0 of a multi-message batch collects the reward for every other state-machine advance in that batch, even ones it did not sign or deliver.

### Finding Description
In `modules/pallets/ismp/src/impls.rs`, `Pallet::<T>::execute` accepts an arbitrary `Vec<Message>` in a single call and hands the whole batch, plus the flattened `events` produced by processing every message, to `T::FeeHandler::on_executed` once: [1](#0-0) 

`pallet-consensus-incentives`'s implementation of `on_executed` derives the relayer identity **exclusively from `messages.get(0)`**: [2](#0-1) 

It then collapses **all** `StateMachineUpdated` events across the whole batch (which can span many distinct `state_machine_id`s, each potentially produced by a different `Message::Consensus` entry with its own independent signer) into one "highest height per state machine" map, and pays the reward for every entry in that map to the single relayer recovered from message[0]: [3](#0-2) 

`Self::calculate_reward` then computes `(latest_height - baseline) * cost_per_block` per state machine and `process_message` transfers that amount from the treasury and mints matching reputation to the same message[0]-derived account: [4](#0-3) 

Consensus proofs are, by protocol design, public and freely obtainable by anyone (the docs explicitly say so): "these proofs can be generated by anyone, as they are freely provided by its connected chains" — meaning an attacker doesn't need a malicious peer or leaked key, they only need to grab already-public, independently-valid consensus proofs for other state machines and bundle them into their own submission, with their own signed message placed first. [5](#0-4) 

The `signer` field inside `ConsensusMessage` is used **only** for reward attribution here — nothing in `on_executed` validates that the signer of message[0] is actually the party whose proof produced each `StateMachineUpdated` event later in the batch. The comment in the code even acknowledges the batch can contain "multiple `StateMachineUpdated` events for the same `state_machine_id`" and de-duplicates within a state machine, but does nothing to verify that the *single* attributed signer is responsible for updates on *other* state machines in the same batch.

### Impact Explanation
This is a direct fund-diversion / wrong-beneficiary bug against the `TreasuryAccount`:
- An unprivileged account submits a single extrinsic containing multiple `Message::Consensus` entries — its own (validly self-signed, cheap or trivial) consensus message first, followed by any number of other, already-public, independently valid consensus proofs for other state machines.
- `on_executed` pays out the reward for **every** state-machine advance in that batch to the attacker's account (message[0]'s signer), including advances the attacker did not deliver, sign, or otherwise earn.
- This directly drains the `TreasuryAccount` to an account not entitled to the funds and mints matching `ReputationAsset` to that account as well — both a value-theft and a reputation-forgery outcome.

This falls squarely within the bounty's "reward claims" / "unauthorized transaction or execution" / "wrong beneficiary or amount" categories, and requires no malicious peer, relayer collusion, or privileged role — any user able to submit an ISMP message batch can exploit it.

### Likelihood Explanation
High. Batching multiple ISMP messages (including multiple `Message::Consensus` entries) into one extrinsic is a normal, expected code path (`execute(messages: Vec<Message>)`), not an edge case. Consensus proofs are intentionally public by protocol design, so the attacker never needs privileged access to obtain the other proofs it rides along with — it only needs to observe legitimate proofs in flight (e.g., from the relayer's own offchain storage / mempool, which is explicitly open per the docs) and resubmit them bundled with its own message as index 0.

### Recommendation
Attribute rewards per-message, not per-batch-via-message[0]:
- Correlate each `StateMachineUpdated` event with the specific `Message::Consensus` entry (and its own verified signer) that produced it, rather than using a single signer recovered from `messages.get(0)` for the entire event list.
- If multiple consensus messages in a batch come from different signers, each signer should only be credited for the state-machine advances their own proof produced.

### Proof of Concept
1. Attacker observes two independently valid, publicly available `ConsensusMessage`s in flight: one for `StateMachine::A` (any signer, e.g. relayer R1) and one attacker-authored trivial/self-signed message for `StateMachine::B` where the attacker is the genuine relayer of a small height delta.
2. Attacker constructs `messages = [ConsensusMessage_for_B (attacker-signed), ConsensusMessage_for_A (R1-authored proof)]` and submits both together in one `execute` call.
3. `handle_incoming_message` validates each consensus proof independently against its own consensus client rules and succeeds for both, emitting `StateMachineUpdated` for both `A` and `B`.
4. `on_executed` reads `messages.get(0)` (the attacker's own `ConsensusMessage_for_B`), recovers the attacker's `relayer_account`, then iterates `highest_per_state_machine` covering **both** `A` and `B`, and calls `process_message` for each — transferring the treasury's `CostPerBlock`-scaled reward for **both** state machines to the attacker's account, even though R1 actually produced the proof for `A`.
5. Attacker collects rewards (and reputation mint) for consensus updates it never delivered, while `LastRewardedHeight` for `A` is advanced, permanently preventing R1 (or anyone) from ever claiming that reward again for the same height span.

			// check that requests will be successfully dispatched

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}
