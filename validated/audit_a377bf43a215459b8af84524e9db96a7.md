### Title
Unbounded WebSocket Message Size on Fast RPC Path Enables Memory-Exhaustion DoS - (File: networks/rpc/websocket.go)

### Summary
The gorilla/websocket-based JSON-RPC handler explicitly caps incoming message size via `conn.SetReadLimit(...)`, but the parallel `clevergo/websocket` ("fastws")-based handler used by `FastWebsocketHandler` never applies an equivalent read-size limit before reading frames off the wire. This mirrors the KubeEdge advisory's bug class: a stream endpoint reads a full message into memory with no imposed size limit, letting a remote caller exhaust server memory.

### Finding Description
`newWebsocketCodec`, used by `Server.WebsocketHandler` (the gorilla/websocket path), sets an explicit per-connection read limit before serving: [1](#0-0) 

By contrast, `FastWebsocketHandler` upgrades the connection via `github.com/clevergo/websocket` ("fastws") and immediately starts reading JSON-RPC frames with `conn.ReadMessage()` inside the `decoder` closure, with no call analogous to `SetReadLimit` anywhere in the handler: [2](#0-1) 

The only size constraint present, `MaxRequestBodySize: common.MaxRequestContentLength` on the `fasthttp.Server` returned by `NewFastWSServer`, only bounds the initial HTTP upgrade request body — it does not constrain WebSocket frames read after the protocol switch, since those are read directly off the raw connection by `fastws.Conn.ReadMessage()`, independent of the fasthttp request/response cycle: [3](#0-2) 

I could not inspect the vendored `github.com/clevergo/websocket` package internals through the code index to confirm whether it imposes any built-in default frame-size ceiling; this should be verified directly against the vendored/go.sum-pinned source before treating this as conclusively exploitable.

### Impact Explanation
If `FastWebsocketHandler`/`NewFastWSServer` is the active WS-RPC transport (an alternative to the standard gorilla-based `WebsocketHandler`), any public RPC caller who can open a WebSocket connection to the node's ws-rpc endpoint could send an arbitrarily large single WebSocket message. Absent an enforced read limit at the frame level, the server will buffer and read the full message into memory before JSON-decoding it, risking memory exhaustion and denial of service to CloudCore-equivalent node process (EdgeCore/CloudCore analog here is `EdgeNode`/`kaiaServer`'s RPC listener), directly matching CWE-400/CWE-770.

### Likelihood Explanation
Requires the operator to have enabled the fasthttp-based WS-RPC listener (`ws-rpc`/fast websocket path) rather than the default gorilla-based one — analogous to the original advisory's precondition that `cloudStream`/`edgeStream` be explicitly enabled. If enabled, exploitation needs only a single unauthenticated (or minimally authenticated, depending on deployment) WebSocket connection and one oversized frame, making it straightforward once the precondition is met.

### Recommendation
Set an explicit maximum message/frame size on the `fastws.Conn` in `FastWebsocketHandler` mirroring the gorilla path's `conn.SetReadLimit(int64(common.MaxRequestContentLength))`, or reject/close the connection when the read payload exceeds `common.MaxRequestContentLength` before or during decoding, ensuring parity between both WebSocket transport implementations.

### Proof of Concept
1. Start a node with the fasthttp-based WS-RPC server (`NewFastWSServer`) enabled and reachable.
2. Open a WebSocket connection to the ws-rpc endpoint using any client library that does not enforce client-side frame-size limits.
3. Send a single WebSocket text frame far exceeding `common.MaxRequestContentLength` (e.g., hundreds of MB).
4. Observe `conn.ReadMessage()` in the `decoder` closure at `networks/rpc/websocket.go:136` buffering the full frame with no rejection, causing elevated memory usage; repeating this from multiple connections drives the node toward OOM/DoS.

```go
func (srv *Server) FastWebsocketHandler(ctx *fasthttp.RequestCtx) {
	// TODO-Kaia handle websocket protocol
	protocol := ctx.Request.Header.Peek("Sec-WebSocket-Protocol")
	if protocol != nil {
		ctx.Response.Header.Set("Sec-WebSocket-Protocol", string(protocol))
	}

	err := upgrader.Upgrade(ctx, func(conn *fastws.Conn) {
		if atomic.LoadInt32(&srv.wsConnCount) >= MaxWebsocketConnections {
			return
		}
		atomic.AddInt32(&srv.wsConnCount, 1)
		wsConnCounter.Inc(1)
		defer func() {
			atomic.AddInt32(&srv.wsConnCount, -1)
			wsConnCounter.Dec(1)
		}()
		if WebsocketReadDeadline != 0 {
			conn.SetReadDeadline(time.Now().Add(time.Duration(WebsocketReadDeadline) * time.Second))
		}
		if WebsocketWriteDeadline != 0 {
			conn.SetWriteDeadline(time.Now().Add(time.Duration(WebsocketWriteDeadline) * time.Second))
		}
		// Create a custom encode/decode pair to enforce payload size and number encoding
		encoder := func(v interface{}) error {
			msg, err := json.Marshal(v)
			if err != nil {
				return err
			}
			err = conn.WriteMessage(websocket.TextMessage, msg)
			if err != nil {
				return err
			}
			return err
		}
		decoder := func(v interface{}) error {
			_, data, err := conn.ReadMessage()
			if err != nil {
				return err
			}
			dec := json.NewDecoder(bytes.NewReader(data))
			dec.UseNumber()
			return dec.Decode(v)
		}

		reader := bufio.NewReaderSize(bytes.NewReader(ctx.Request.Body()), common.MaxRequestContentLength)
		srv.ServeCodec(NewFuncCodec(&httpReadWriteNopCloser{reader, ctx.Response.BodyWriter()}, encoder, decoder), 0)
	})
```
