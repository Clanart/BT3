### Title
Automatic remote URL rewrite trusts unauthenticated GitHub API `clone_url` field, enabling silent push/fetch redirection - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` automatically rewrites a repository's local `origin` remote URL whenever the cached `GitHubRepository.cloneURL` (the "old" value) no longer matches a freshly-fetched `IAPIRepository.clone_url` (the "new" value) returned by the GitHub API, as long as the current git remote still matches the old cached URL and the protocol is unchanged: [1](#0-0) 

This mirrors the report's broken invariant class: a "new" value (the refreshed API field) is substituted for a "current"/trusted value (the git remote actually configured by the user) in a decision that has real side effects — here, silently mutating the destination of future `git push`/`git fetch` operations.

### Finding Description
The function's guard logic is:
1. `remoteUrlUnchanged` — checks that the *current git remote* still matches the *previously cached* `gitHubRepository.cloneURL` [2](#0-1) 
2. `protocolsMatch` — checks the URL scheme (`https`/`ssh`) of old vs new value hasn't changed [3](#0-2) 
3. `!urlsMatch` — the remote differs from the new `clone_url`

If all three hold, Desktop calls `gitStore.setRemoteURL(...)` with the **new** `apiRepo.clone_url` value, which shells out to `git remote set-url` [4](#0-3) [5](#0-4) .

The critical trust boundary problem: `apiRepo.clone_url` originates from a GitHub API response for the repository object — a field that is attacker-influenced whenever an attacker controls or can manipulate the metadata of a repository the victim has open in Desktop (e.g., a repository the victim forked from an attacker-controlled repo, a malicious collaborator who transfers/renames the repo, or a compromised/malicious GitHub Enterprise Server endpoint returning arbitrary JSON). The code's only defenses are hostname/owner/name equality checks between old and new API-supplied values (`urlMatchesRemote`) and protocol match — none of which validate that the *new* clone_url still points to a location the user actually trusts; it just needs to differ from the currently configured remote while sharing scheme. There is no user confirmation step before the remote is silently rewritten.

Because the rewrite happens transparently as part of routine repository refresh (whenever the app syncs GitHub metadata for a repo), the user's subsequent commits pushed via the default "origin" remote can be silently redirected to whatever URL the API now reports for that repository, without any visible warning dialog akin to the branch-protection or repo-rules warnings shown elsewhere in the app (e.g. `commit-message.tsx`'s `renderBranchProtectionsRepoRulesCommitWarning`) [6](#0-5) .

### Impact Explanation
If exploited, this allows an attacker who can influence the GitHub API's reported `clone_url` for a repository the victim has cloned in Desktop (e.g., by being granted collaborator/owner rights to redirect/rename the repo, or a compromised GHES metadata endpoint) to silently redirect the victim's git remote to an attacker-controlled repository/server. Subsequent pushes performed by the victim (who believes they are pushing to the original trusted repository) would be sent to the attacker's endpoint instead — this is "silent corruption of what the user commits or pushes," one of the explicitly valid impact classes. Depending on the destination host, this could also facilitate credential exfiltration during the push (git credentials/tokens are supplied per `envForRemoteOperation`) since the push now targets an untrusted host.

### Likelihood Explanation
This code path runs automatically as part of normal repository metadata refresh — no unusual user action is required beyond having the repository open and Desktop periodically/manually syncing GitHub repo details. The guard conditions (`remoteUrlUnchanged`, `protocolsMatch`, `!urlsMatch`) are all satisfiable through ordinary API responses and do not require any privileged access on the attacker's part beyond control over what `clone_url` value is served for the repository object. This makes the primitive plausible without local/physical access, admin rights, or social engineering, satisfying the required attacker model (an attacker-controlled GitHub API object).

### Recommendation
Do not silently rewrite the user's configured remote URL based solely on the GitHub API's `clone_url` field. At minimum:
- Prompt the user for explicit confirmation before changing a remote URL derived from API data, similar to existing branch-protection/repo-rule warnings.
- Validate that the new `clone_url` still resolves to the exact same repository identity that was cryptographically/originally associated with the account+dbID pair used when the repository was first added, not merely "protocol matches and hostname/owner/name differ."
- Log/audit remote URL changes so users can detect unexpected redirections.

### Proof of Concept
Conceptual PoC (not executed, derived from code inspection):
1. Victim adds/clones a repository `https://github.com/victim-org/repo` in GitHub Desktop; Desktop caches `GitHubRepository.cloneURL = https://github.com/victim-org/repo`.
2. Attacker (a collaborator/owner with rename or transfer rights, or a malicious GHES admin) changes the GitHub-side repository metadata such that the API now returns `clone_url: https://attacker-host/attacker/repo` for the same `dbID` (e.g. via repo transfer/rename, or a compromised/malicious API/proxy response for GHES users).
3. On the next repository refresh, `updateRemoteUrl` is invoked with the stale cached `gitHubRepository` (old `cloneURL` matching the still-configured local remote) and the new `apiRepo.clone_url` (attacker URL, same protocol `https`).
4. All three guard conditions pass (`protocolsMatch=true`, `remoteUrlUnchanged=true`, `urlsMatch=false`), so `gitStore.setRemoteURL('origin', 'https://attacker-host/attacker/repo')` executes silently [7](#0-6) .
5. The victim's next `git push` (using the unchanged UI, unaware the remote changed) sends commits/credentials to the attacker's host.

Note: I was not able to fully trace, within the indexing limits, the exact call sites and ordering guarantees in `app-store.ts` where `updateRemoteUrl` is invoked (grep found 6 matches but full context wasn't retrievable in this session) — verifying the precise trigger frequency/timing (e.g. whether this runs on every background refresh vs. only user-initiated fetches) would require deeper inspection, ideally via a full Devin session with complete file access.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

}
