### Title
Invalid PedPoP proof-of-possession leaks the recipient's ECDH key before authentication - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`KeyMachine::calculate_share` decrypts every submitted `EncryptedMessage` and creates an `EncryptionKeyProof` containing the recipient's ECDH result before the message's proof-of-possession batch check has been evaluated. When the decrypted bytes are not a canonical scalar, it immediately returns that proof as blame material. A participant can therefore submit a malformed message reusing another message's public encryption key and obtain the ECDH key needed to decrypt the copied ciphertext.

### Finding Description
`Encryption::decrypt` queues `msg.pop` for batch verification, but does not wait for that verification before calculating `ecdh(&self.enc_key, msg.key)`, decrypting the ciphertext, and constructing `EncryptionKeyProof { key, dleq }`. [1](#0-0)  In `KeyMachine::calculate_share`, a non-canonical decrypted share immediately returns `PedPoPError::InvalidShare` with `blame: Some(blame)` before `batch.verify_with_vartime_blame()` runs. [2](#0-1)  The proof contains `proof.key`, the ECDH point, and a DLEq proving it corresponds to `msg.key` and the recipient's registered encryption key. [3](#0-2) 

The code explicitly identifies this as a dangerous disclosure pattern: revealing the ECDH result for an attacker-controlled message can also reveal another ciphertext encrypted under the same per-message key. [4](#0-3)  The intended mitigation is the per-message Schnorr proof-of-possession, but queuing that check is not equivalent to enforcing it before disclosure. [5](#0-4) 

### Impact Explanation
An attacker who observes a victim's encrypted DKG share can copy its `key`, submit a malformed encrypted message using that key, and cause the honest recipient to publish the ECDH point in blame material. [6](#0-5)  With that ECDH point, the attacker can derive the ChaCha20 stream and decrypt the observed ciphertext, recovering another participant's secret share. [7](#0-6) 

This is secret-share/key material disclosure triggered solely by untrusted DKG message bytes supplied to `EncryptedMessage::read` and `calculate_share`. [8](#0-7)  The disclosure is also propagated in processor errors as serializable blame data. [9](#0-8) 

### Likelihood Explanation
The attack only requires a DKG participant capable of observing the victim's encrypted share message and submitting its own malformed share message. The malformed ciphertext merely needs to decrypt to bytes rejected by `C::F::from_repr`; random corrupted bytes provide a high probability of triggering the early return. [10](#0-9)  No valid proof-of-possession for the copied per-message key is needed because the key proof is returned before the queued PoP verification is evaluated. [11](#0-10) 

### Recommendation
Do not create or return an `EncryptionKeyProof` until the message's PoP has been verified successfully. Structurally, PoP verification should precede decryption, or decryption/proof generation should be staged and discarded if any queued authentication fails. `calculate_share` should also not attach a decryption proof on the scalar-decoding error path until all queued PoP statements have passed.

### Proof of Concept
Conceptual protocol-level PoC:

1. Victim `A` sends recipient `B` an `EncryptedMessage` containing `key = K_A`, ciphertext `C_A`, and PoP `P_A`.
2. Attacker `E`, acting as another DKG participant, observes `(K_A, C_A, P_A)` on the authenticated message channel.
3. `E` sends `B` a new `EncryptedMessage` with `key = K_A`, arbitrary corrupted ciphertext `C_E`, and an invalid PoP.
4. `B` calls `calculate_share`; `decrypt` queues the invalid PoP, but still computes `K = ecdh(b, K_A)` and creates a DLEq-backed `EncryptionKeyProof`.
5. Corrupted `C_E` decrypts to non-canonical scalar bytes, causing `calculate_share` to return `InvalidShare { blame: Some(proof) }` before the batch verifier rejects the invalid PoP.
6. `E` obtains `K` from the published blame proof, feeds it to `cipher(context, K)`, and decrypts the originally observed `C_A` to recover `A`'s share for `B`.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
