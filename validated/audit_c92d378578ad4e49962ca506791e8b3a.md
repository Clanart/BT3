## Confirmed important detail

`_applyCopilotConflictResolutions` in `app/src/lib/stores/app-store.ts` writes `resolution.resolvedContent` straight to disk with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and stages it with `git add` [1](#0-0) , with no re-validation that the reassembled content is actually correct or free of conflict markers before it is committed.

### Title
Divergent marker-scanning logic between `extractConflictHunks` and `reassembleResolvedFile` lets attacker-controlled conflicted content silently misplace AI resolutions into unrelated code, corrupting what the user commits - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot conflict-resolution feature parses a conflicted file once with `extractConflictHunks` (in `app/src/lib/copilot-conflict-context.ts`) to build the prompt sent to the model, and later re-parses the *same raw file content* independently with `reassembleResolvedFile` (in `app/src/lib/copilot-conflict-resolution.ts`) to splice the model's per-hunk resolutions back in "matched by order, not by line number." [2](#0-1)  These two scans use similar but not identical state machines, so a file whose "ours" region legitimately contains a line matching the exact 7-character marker pattern (e.g. `>>>>>>> `) — plausible in documentation, test fixtures, or ASCII-art content that an attacker previously got merged into the repository — will be parsed consistently by `extractConflictHunks` but misidentified as a "malformed" block by `reassembleResolvedFile`'s look-ahead loop, which breaks on the **first** `>>>>>>>`-looking line it sees regardless of whether the separator has been found yet [3](#0-2) .

### Finding Description
`extractConflictHunks` walks the file with a stateful parser: while collecting "ours" content it only watches for the base (`|||||||`) or separator (`=======`) markers, never for a theirs marker (`>>>>>>>`), so any line that merely *looks like* a theirs marker inside the ours section is treated as ordinary content [4](#0-3) . This produces the correct hunk count and content that is sent to the model, and is exactly what `validateResolutionPaths` checks the model's hunk count against [5](#0-4) .

`reassembleResolvedFile`, however, re-derives the block boundaries independently and more naively: after finding an opening `<<<<<<<`, it scans forward and breaks out of the loop as soon as it finds **any** line matching the theirs-marker pattern, before it has necessarily seen the separator [6](#0-5) . If `hasSeparator` is still false at that point (because the real `=======` line hasn't appeared yet), the whole block is declared "malformed" and the opening `<<<<<<<` line is copied through verbatim as ordinary content, and the loop resumes one line later — it does **not** skip past the real conflict block. The result: the real `<<<<<<<`, `=======`, `>>>>>>>` markers and both sides' content remain untouched in the final file, `hunkIndex` is never incremented for that block, and every hunk resolution *after* that point in the file gets spliced against the wrong hunk index for the rest of that file's reassembly.

Because `reassembleResolvedFile` trusts pure positional/order matching with no content fingerprinting tying `hunkResolutions[i]` back to the specific original hunk it was generated for, there is nothing to catch this divergence — mirroring the audited bug's core flaw (blind trust that backup/restore state matches the assumed structure, with no integrity check before it is written back).

### Impact Explanation
The result of `_applyCopilotConflictResolutions` is written directly to the working tree and `git add`-ed [1](#0-0) , then committed as part of a merge/rebase/cherry-pick continuation. An attacker who can get such a marker-lookalike line merged into any file in the repository history (a realistic, low-friction PR — e.g. a doc explaining conflict-marker syntax) can cause a **later, unrelated** legitimate conflict-resolution session (using GitHub Desktop's Copilot conflict resolution) to:
- leave literal `<<<<<<<`/`=======`/`>>>>>>>` markers physically committed into source files (build breakage / silent corruption), and/or
- splice the AI's resolution for hunk *N* into the *wrong* conflict block in the file, silently substituting unrelated code into the user's commit without any error or warning shown to the user.

This is a silent corruption of what the user commits, matching the requested impact category, without requiring local/physical access, admin rights, or social engineering beyond a normal PR merge.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the attacker's marker-lookalike content to have been merged into the repo at some point (a normal contribution, not a suspicious one — it doesn't need to be flagged as malicious), and (2) a subsequent, otherwise-unrelated real conflict to occur in a way that positions that lookalike line inside the "ours" region of a hunk before the file is run through the Copilot conflict-resolution flow. Both conditions are plausible for any actively-maintained repository containing documentation/tests about git conflict markers, and the feature is user-opt-in but produces no warning when this divergence occurs, so users have no signal that anything went wrong.

### Recommendation
Make `reassembleResolvedFile` re-use the exact same block-detection state machine as `extractConflictHunks` (ideally by having both derive from one shared parser), rather than maintaining a second, subtly different look-ahead implementation. Additionally, tie each `IHunkResolution` to an integrity check against the original hunk it was generated for (e.g., include or verify a hash of `oursContent`/`theirsContent` per hunk) instead of relying purely on ordinal position, and fail loudly (surface an error to the user) rather than falling back to "copy through as regular content" when a mismatch is detected, so that partially-resolved or marker-laden output is never silently written and committed.

### Proof of Concept
1. Attacker gets a file merged (via a normal, innocuous-looking PR) containing a paragraph/fixture with a line consisting of exactly `>>>>>>> example` at column 0 (e.g., inside a markdown doc about resolving conflicts).
2. Later, a real merge/rebase/cherry-pick produces a genuine conflict in that same file such that the attacker's `>>>>>>> example` line ends up inside the "ours" text of the real conflict block, before the real `=======` separator:
   ```
   <<<<<<< HEAD
   some real ours code
   >>>>>>> example
   more real ours code
   =======
   real theirs code
   >>>>>>> feature
   ```
3. `extractConflictHunks` parses this as one hunk (it doesn't stop on a stray theirs-marker while collecting ours content) and sends it to Copilot, which returns one `resolvedContent` for that single hunk. `validateResolutionPaths` passes (hunk count 1 == 1).
4. `reassembleResolvedFile`'s look-ahead loop hits the fake `>>>>>>> example` line first, sets `closingIndex` there with `hasSeparator` still `false`, and declares the block malformed — leaving the entire real conflict markers and both sides' content in place, uncorrected, and un-consuming the model's resolution (which then gets misapplied to whatever the *next* real hunk in the file happens to be, if any).
5. `_applyCopilotConflictResolutions` writes this corrupted content to disk and stages it, and the user commits it believing Copilot resolved the conflict correctly. [7](#0-6)
