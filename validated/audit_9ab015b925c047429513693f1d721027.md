## Title
Path-containment check in `resolveWithin()` uses unanchored string-prefix comparison, allowing conflict-file paths to escape the repository root and leak sibling-directory file contents to the Copilot cloud API - (File: `app/src/lib/path.ts`)

### Summary
The report's root cause is a comparison performed at the wrong "boundary": a value computed and used in one context, but validated/stored using a different, less-precise representation. In GitHub Desktop, the same class of bug appears in `_resolveWithin()`, the canonical path-containment guard used across the app to prevent path traversal. The final containment check compares two path strings with `String.prototype.startsWith()` without verifying a path-separator boundary, so a resolved path that merely shares the *root's characters as a prefix* — while actually being a sibling directory — is incorrectly accepted as "inside" the root.

### Finding Description
`_resolveWithin()` in [1](#0-0)  resolves the caller-supplied relative path against the root, `realpath()`s both the root and the resolved path (to defeat symlinks), and then validates containment with:

```
return realResolved.startsWith(realRoot) ? resolved : null
```

`startsWith` performs a raw substring comparison, not a directory-boundary comparison. If `realRoot` is e.g. `/Users/name/repo` and an attacker-controlled repository contains a tracked symlink whose real target resolves to `/Users/name/repo-secrets/token.txt` (or any other sibling path that happens to start with the exact same characters as `realRoot`), the check `"/Users/name/repo-secrets/token.txt".startsWith("/Users/name/repo")` evaluates to `true`, even though the resolved file lives entirely outside the repository's directory tree. This is the analog of the Sherlock finding: a boundary/invariant ("resolved path must be inside root") is validated using a comparison that doesn't match the actual invariant needed (must be inside root *as a directory*, not merely prefix-matched as a string).

`resolveWithin()` is the security boundary relied on by:
- `app/src/ui/dispatcher/dispatcher.ts`'s `openRepositoryFromUrl()`, which resolves a `filepath` query parameter from an `x-github-client://openRepo/...` deep link before calling `shell.showItemInFolder()` [2](#0-1) .
- `buildConflictContext()` in `app/src/lib/copilot-conflict-context.ts`, which resolves each conflicted file's repo-relative path against `workingDirectory` before reading its contents from disk with `readFile(absolutePath, 'utf8')` [3](#0-2) .

In the conflict-resolution flow, the resulting file content is parsed into conflict hunks and those hunks (`oursContent`/`theirsContent`/`baseContent`/context lines) are embedded into the prompt sent to the Copilot SDK via `formatConflictContextForPrompt()` [4](#0-3) , which is transmitted off-device through `CopilotStore.resolveConflicts()` [5](#0-4) .

### Impact Explanation
An attacker who controls a repository the victim clones/fetches (a tracked symlink pointing to a sibling directory whose real path happens to share the root's literal prefix, or any layout that satisfies the same-prefix-without-separator condition) can cause Desktop to treat an out-of-repository file as "inside the repo." This is read from disk and, in the conflict-resolution path, its content is sent to an external cloud API (Copilot) as part of an LLM prompt — matching the "credential/token exfiltration" and "file read outside the repo" impact categories, since arbitrary sibling-directory files (which may include unrelated project secrets, config, or other repos checked out under the same parent directory) can be exfiltrated without any additional user action beyond triggering an AI-assisted conflict resolution on a malicious repo. The same flawed primitive also backs the deep-link `filepath` handler, so a crafted `x-github-client://openRepo/...?filepath=...` link combined with a matching repo layout could similarly cause Desktop to reveal/open a file outside the intended repository.

### Likelihood Explanation
Exploitation requires the attacker-controlled repository's containing directory structure to produce a `realpath` that is a literal character-prefix of the victim's repo root without a path separator at the boundary (e.g., `repo` vs `repo-secrets`, `repo2`, `repoBackup`, etc., at the same parent directory level). This is a real but layout-dependent condition — it is not guaranteed for arbitrary clone locations, but it is entirely plausible in common workflows (multiple checkouts/forks/worktrees of similarly named repos side-by-side, e.g. `project` and `project-backup`, `project.bak`, `project2`), and the attacker fully controls the symlink target committed inside the malicious repository. No local/physical access, admin rights, or pre-existing malware is required — only that the victim clones the repo and triggers a path resolution (deep link click or Copilot conflict resolution).

### Recommendation
Replace the prefix comparison with an explicit boundary-aware check, e.g.:
```ts
const rel = path.relative(realRoot, realResolved)
const isInside = rel === '' || (!rel.startsWith('..') && !path.isAbsolute(rel))
return isInside ? resolved : null
```
or equivalently ensure `realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)`.

### Proof of Concept
1. Create two sibling directories: `repo` (the victim's cloned repository) and `repo-secrets` (containing a sensitive file, e.g. `token.txt`).
2. Inside `repo`, add a tracked symlink, e.g. `evil -> ../repo-secrets/token.txt`, and commit it as part of a file involved in a merge conflict (or reference it via the deep-link `filepath` parameter).
3. Call `resolveWithin('/Users/name/repo', 'evil')`. Internally: `resolved` = `/Users/name/repo/evil`, `realRoot` = `realpath('/Users/name/repo')` = `/Users/name/repo`, `realResolved` = `realpath('/Users/name/repo/evil')` = `/Users/name/repo-secrets/token.txt`.
4. `realResolved.startsWith(realRoot)` → `"/Users/name/repo-secrets/token.txt".startsWith("/Users/name/repo")` → `true`, so the function returns `resolved` even though the real target is outside `repo`.
5. In the conflict-resolution flow, `buildConflictContext()` then reads `token.txt`'s contents and, if it contains conflict markers (or is otherwise treated as file content), that content flows into the Copilot prompt and off-device via `CopilotStore.resolveConflicts()`. [6](#0-5)  shows existing tests only cover the `..`-traversal and symlink-escape-then-return cases — none exercise the same-prefix/no-separator sibling-directory scenario, so this gap in the containment check is untested.
