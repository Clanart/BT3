### Title
TOCTOU in `resolveWithin`: containment check validates a `realpath`'d value but returns the un-resolved, symlink-traversable path to callers - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` (and its `posix`/`win32` variants) is Desktop's central guard against path traversal / symlink escape when handling repository-relative paths that originate from git-controlled content (conflicted files, deep-link filepaths, etc.). The function determines safety by calling `realpath()` on the candidate path and checking that the *resolved* real path starts with the *resolved* real root. However, it returns the **original, non-realpath'd** path (`resolved`), not the value it actually validated (`realResolved`). Every caller then performs its own, independent filesystem access (`stat`, `readFile`, `shell.showItemInFolder`) against that unresolved path, which re-walks the filesystem — including any symlinks — from scratch. This is the same "check on one value, act on a value that can drift before use" pattern as the reported precompile bug: the security decision is based on a point-in-time snapshot (`realResolved` at check time) while the operation that actually matters is executed later against a different resolution of the same string.

### Finding Description
```ts
// app/src/lib/path.ts:64-71
const resolved = resolve(normalizedRoot, normalizedRelative)

const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

The function verifies containment using `realResolved` (the fully symlink-resolved path) but hands back `resolved` (the pre-resolution path) as the "safe" value. Callers treat a non-null return as proof that any subsequent access to that path stays inside the repository:

- `app/src/lib/copilot-conflict-context.ts:391-431` calls `resolveWithin(workingDirectory, file.path)`, then separately calls `stat(absolutePath)` and `readFile(absolutePath, 'utf8')` using the returned (unresolved) path, and sends the file's raw content to the Copilot SDK. [2](#0-1) 

- `app/src/ui/dispatcher/dispatcher.ts:1963-1971` calls `resolveWithin(repository.path, filepath)` for a deep-link `filepath` and, if non-null, passes it straight to `shell.showItemInFolder(resolved)`. [3](#0-2) 

Because Node re-walks every path component (including symlinks) on each independent `fs` call, the guarantee `resolveWithin` provides only holds for the exact instant the two `realpath()` calls executed inside it. If any path component between the repository root and the target file can be swapped from a plain directory/file to a symlink pointing outside the repository between the `realpath` check and the later `stat`/`readFile`/`shell.showItemInFolder` call, the containment guarantee is void even though `resolveWithin` reported "safe." The existing unit tests only validate the synchronous, non-racy case (`app/test/unit/path-test.ts:65-100`) and do not exercise the check-then-use gap. [4](#0-3) 

An attacker who fully controls a cloned/fetched repository controls the git objects (including symlink blobs) at every path Desktop will later resolve as a "conflicted file" or deep-link target. Because merge/rebase/cherry-pick conflicts on paths that differ in type between "ours" and "theirs" (regular file vs. symlink) leave the working tree in a state that can change across the sequence of git operations Desktop performs on its own (status refresh, discard, checkout, stash pop, background fetch), there is a realistic window in which the on-disk entry at a given repository-relative path flips between a real file (passes the `realpath` check) and a symlink (used at the later read/open), all without any unnatural extra user action — the user only needs to open the malicious repository and let Desktop resolve a merge conflict, exactly as intended by the report's "same block, multiple transactions" staleness pattern.

### Impact Explanation
If the swap lands in the window between `resolveWithin`'s internal `realpath` check and the caller's subsequent access:
- `buildConflictContext` will `readFile` and transmit the contents of a file outside the repository (e.g., SSH keys, `.netrc`, other project secrets) to the Copilot SDK as part of the "conflict context" payload — credential/token exfiltration.
- `openRepositoryFromUrl`'s deep-link path would cause `shell.showItemInFolder` to reveal/open an out-of-repo path, an unprompted file-system disclosure triggered purely by clicking an `x-github-client://` link, matching the "link/deep link" attacker vector.

This satisfies the valid-impact bar: attacker-controlled cloned repository content leading to read of files outside the repository / credential exfiltration, without requiring local/physical access, admin rights, or pre-existing host compromise (the "race" is driven entirely by Desktop's own sequence of git operations against attacker-supplied repository content, not by a co-resident attacker process).

### Likelihood Explanation
Medium. The vulnerability is real and structurally present (the return value does not match what was validated), but exploitation requires the attacker to arrange for a path-component symlink swap to occur inside the narrow window between the two internal `realpath()` calls and the caller's later `fs` access — a genuine race that depends on git/Desktop's operation timing and is not fully within the attacker's direct control from outside the process. It is comparable in spirit, but not identical in mechanics, to the report's bug (which is a per-block staleness window rather than a microsecond filesystem race), so I flag this as the closest available analog rather than a byte-for-byte equivalent.

### Recommendation
Make `resolveWithin` return the value it actually validated (`realResolved`), or re-verify containment with `realpath` immediately before each sensitive filesystem operation that consumes its result, so the checked value and the used value are always the same object, eliminating the TOCTOU gap. Additionally, consider opening conflicted-file paths with `O_NOFOLLOW`/`lstat` pre-checks where the platform allows it, since git working trees can legitimately contain attacker-supplied symlinks.

### Proof of Concept
1. Attacker publishes a repository with two branches that conflict on path `secrets/link`: on `main` it's a normal text file (`"conflict marker content"`), on `feature` it's a symlink pointing at, e.g., `../../../../.ssh/id_rsa` (relative escape from the repo root).
2. Victim opens the repository in Desktop and starts a merge/rebase between the two branches. Git reports `secrets/link` as conflicted; at the instant `buildConflictContext` runs, the working-tree entry is a regular file (post checkout of the "ours" side), so `resolveWithin(workingDirectory, 'secrets/link')` passes its internal `realpath` check and returns the joined path.
3. Because Desktop's background status refresh / discard-changes / checkout flows continue to run against the same working tree while the conflict-resolution UI is open (git operations that can rewrite the entry back to the "theirs" symlink version, e.g. via "discard changes" on that file or a retried checkout), the entry at `secrets/link` becomes a symlink to `~/.ssh/id_rsa` before `buildConflictContext`'s subsequent `stat`/`readFile` executes.
4. `readFile(absolutePath, 'utf8')` at `app/src/lib/copilot-conflict-context.ts:431` now follows the symlink and reads `~/.ssh/id_rsa`, which is embedded as `rawContent` in the conflict context sent to the Copilot SDK. [5](#0-4) 

(Note: precisely triggering the swap requires the attacker to also induce a Desktop-initiated git operation on `secrets/link` between steps 2 and 4; I could not fully verify from static code alone how deterministically this timing window can be won in the shipped app, since that depends on the interleaving of background refresh timers versus the conflict-resolution UI flow — a background-agent Devin session with the running app would be needed to confirm exploitability end-to-end.)
