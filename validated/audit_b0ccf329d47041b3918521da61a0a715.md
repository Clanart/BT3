### Title
Regex evaluation failures in hookify's `RuleEngine` fail open, allowing blocking rules to be silently bypassed - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._regex_match` catches only `re.error` and returns `False` on failure, treating a broken/failing regex condition as "no match" instead of denying by default. More critically, the hook entry points (e.g. `plugins/hookify/hooks/pretooluse.py`) wrap the entire rule-evaluation call in a catch-all `except Exception` that is explicitly designed to "ALWAYS exit 0 - never block operations due to hook errors," so any exception raised while evaluating a `regex_match` condition (e.g. `RecursionError`/`MemoryError` from pathological backtracking, which is not an `re.error`) results in the Bash command being allowed even if it should have been blocked.

### Finding Description
The call chain is `evaluate_rules` → `_rule_matches` → `_check_condition` → `_regex_match` → `compile_regex` (cached via `lru_cache`), all in [1](#0-0) . Inside `_regex_match`, only `re.error` is caught; on failure it prints a warning and returns `False`, which `_check_condition` treats as "condition not satisfied," causing `_rule_matches` to return `False` for the whole rule (line 122-123) — i.e., a `block` rule silently stops matching instead of defaulting to deny.

More significantly, at the hook-script layer, `plugins/hookify/hooks/pretooluse.py` wraps `engine.evaluate_rules(...)` in a broad `except Exception` block that explicitly documents its fail-open intent: [2](#0-1) . If regex evaluation raises anything other than `re.error` (e.g. `RecursionError` from deep/pathological backtracking depth, or any other runtime exception surfaced through `regex.search(text)`), it is not caught inside `_regex_match`, propagates up through `_check_condition`/`_rule_matches`/`evaluate_rules`, and is caught only by this outer handler, which emits a non-blocking `systemMessage` and unconditionally `sys.exit(0)`s, never emitting `"decision": "block"` or `"permissionDecision": "deny"`. This means an attacker-controlled Bash `command` string crafted to trigger a regex exception (or extreme slowdown) against a rule's pattern can cause a `block` rule to be skipped entirely, and the command proceeds.

Note: classic catastrophic-backtracking (ReDoS) patterns typically cause `regex.search` to hang rather than raise, which would stall the hook process rather than silently return an "allow" decision through the exception path. The exploitable fail-open behavior demonstrated here is triggered by exceptions during matching (malformed pattern caught inside `_regex_match` returning `False`, or other exceptions such as `RecursionError` propagating to the hook script's catch-all), not by a pure infinite-hang scenario, which the codebase has no timeout/fail-closed handling for either.

### Impact Explanation
A `block` rule intended to stop dangerous Bash commands (e.g. `rm -rf`) can be bypassed if the matched text or pattern combination causes a regex-layer exception, because the enforcement point defaults to "allow" on error rather than "deny." This is an approval/enforcement bypass of the hookify policy engine, letting an attacker-influenced command execute despite a configured blocking rule.

### Likelihood Explanation
Exploitability depends on being able to influence the `command` text evaluated against an existing `regex_match` block rule such that regex evaluation throws a non-`re.error` exception (e.g., very deep nested/pathological input triggering `RecursionError`) — the pattern itself does not need to be attacker-controlled since only the input text matched against a legitimate rule pattern is needed. This is feasible for any repository/session where hookify block rules with `regex_match` conditions are in effect and command text is influenced by external/untrusted content flowing into `tool_input.command`. The design intent of "ALWAYS exit 0 - never block operations due to hook errors" makes this a systemic, reproducible fail-open, not a one-off edge case.

### Recommendation
- In `_regex_match`, catch broader failure modes (`re.error`, `RecursionError`, and use a timeout-bounded match, e.g. via a separate process/thread with a hard deadline or the `regex` module's timeout support) and, for `block`-action rules, fail closed (treat evaluation failure as a match) rather than returning `False`.
- In `pretooluse.py`/`posttooluse.py`/`stop.py`/`userpromptsubmit.py`, change the catch-all exception handler so that failures during rule evaluation do not unconditionally allow the operation; at minimum, distinguish rule-loading errors (safe to fail open) from rule-evaluation errors on already-loaded blocking rules (should fail closed or explicitly surface a warning without silently permitting the tool call).
- Add a maximum input length / regex execution timeout guard before calling `regex.search(text)` to bound worst-case backtracking cost.

### Proof of Concept
Unit test plan for `plugins/hookify/core/rule_engine.py`:
1. Construct a `Rule` with `action='block'` and a condition `Condition(field="command", operator="regex_match", pattern=<pattern>)`.
2. Monkeypatch `compile_regex` (or use a real pattern) so that `regex.search(text)` raises `RecursionError` for a crafted `text` (e.g., a string engineered to exceed the regex engine's internal recursion/backtracking limits for a nested-quantifier pattern).
3. Call `engine.evaluate_rules([rule], {"tool_name": "Bash", "tool_input": {"command": text}})` directly — assert it does not crash and returns a deny/block result (expected fail-closed behavior), current code instead lets the exception propagate uncaught out of `evaluate_rules`.
4. Integration test: invoke `plugins/hookify/hooks/pretooluse.py main()` with stdin JSON containing the malicious `command`, and assert the emitted JSON contains `"permissionDecision": "deny"` — current behavior instead prints only `{"systemMessage": "Hookify error: ..."}` and exits 0, i.e., the tool call is allowed to proceed, demonstrating the bypass.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
