### Title
Double reimbursement via withdrawal-UTXO reuse across deposit indices — `get_payout_txs_for_withdrawal_utxos` matches payouts by UTXO bytes only, not by deposit index - ([File: core/src/database/verifier.rs])

### Summary
An unprivileged withdrawer can register the same withdrawal-UTXO bytes on the Citrea Bridge contract for two different deposit indices `i` and `j`. Because Clementine's sync join in `get_payout_txs_for_withdrawal_utxos` matches a Bitcoin payout transaction to a `withdrawals` row purely by `(withdrawal_utxo_txid, withdrawal_utxo_vout)` equality with no per-index uniqueness constraint, the single physical payout that actually fronted withdrawal `i` gets attributed to withdrawal `j` as well. The bridge circuit's `verify_storage_proofs` independently re-derives a valid `WithdrawalOutpointTxid`/`MoveTxid` pair for index `j` from genuine on-chain state, and `bridge_circuit`'s only cross-check (`user_wd_txid == payout tx input outpoint`) is satisfied because it is the same physical outpoint — so a second, fully valid journal/reimbursement claim can be produced for `MoveTxid_j`, distinct from `MoveTxid_i`, for one real Bitcoin payout.

### Finding Description
Broken binding: `MoveTxid` associated with the accepted journal for withdrawal index `i` (`move_txid_i`) should equal the *only* move-to-vault UTXO whose value is spent to reimburse the *single* Bitcoin payout that fronted withdrawal `i`. The exploit produces a second accepted journal with `MoveTxid_j ≠ MoveTxid_i` while `WithdrawalOutpointTxid_j == WithdrawalOutpointTxid_i`, so two vault UTXOs get spent for one payout — breaking custody.

Code path:
1. Attacker (unprivileged) calls `withdraw`/`safeWithdraw` on the Citrea Bridge contract twice, at deposit indices `i` and later `j`, supplying identical withdrawal UTXO bytes (attacker is explicitly permitted to choose these bytes). The Bridge contract stores `withdrawalUTXOs[i] == withdrawalUTXOs[j]`.
2. Citrea sync in this repo pulls these via `collect_withdrawal_utxos` and writes them per-index with `update_withdrawal_utxo_from_citrea_withdrawal` [1](#0-0) , with no check that the UTXO bytes are unique across indices.
3. When the operator's real, single payout transaction (for withdrawal `i`) confirms on Bitcoin, `get_payout_txs_for_withdrawal_utxos` looks up which `withdrawals` rows it satisfies by joining strictly on UTXO bytes: [2](#0-1) 
Because rows `i` and `j` share the same `withdrawal_utxo_txid`/`vout`, this query returns **both** `(i, spending_txid)` and `(j, spending_txid)` for the one physical payout transaction.
4. This result set is used to write `payout_txid`/`payout_tx_blockhash`/`payout_payer_operator_xonly_pk` for both rows via `update_payout_txs_and_payer_operator_xonly_pk`, so deposit `j`'s `withdrawals` row is populated as if it had its own independent fronted payout, though none was ever broadcast for it.
5. `Verifier::is_kickoff_malicious` validates a kickoff for deposit `j` purely against this DB record — checking operator match and WOTS-committed blockhash match — both of which pass because they were populated from the (legitimately fronted) payout for `i`: [3](#0-2) 
6. Independently, `circuits_lib::bridge_circuit::storage_proof::verify_storage_proofs` recomputes `storage_key_utxo`/`storage_key_vout`/`deposit_storage_key` purely as a function of `storage_proof.index` (here `j`) and verifies each against genuine Merkle/JMT proofs of the real contract state: [4](#0-3) . Since `withdrawalUTXOs[j]` genuinely equals `withdrawalUTXOs[i]` on-chain (attacker-caused collision), this call succeeds and returns `WithdrawalOutpointTxid_j == WithdrawalOutpointTxid_i` but `MoveTxid_j = move_to_vault_txid` of deposit `j` (different from `i`).
7. `bridge_circuit` in `mod.rs` only checks that the derived withdrawal outpoint/vout equal the payout transaction's actual spent input — which trivially holds since it's the same physical outpoint: [5](#0-4) . It then folds `move_txid` (from index `j`) together with `round_txid`/`kickoff_round_vout` (which are legitimately deposit-`j`-specific, from the operator's own kickoff for `j`) into `deposit_constant`, and commits a valid `journal_hash`: [6](#0-5) .

No code in the traced path (`verify_storage_proofs`, `bridge_circuit`, `is_kickoff_malicious`, or the DB sync join) enforces that a given withdrawal-UTXO outpoint (or the single real Bitcoin payout that spends it) can be claimed by at most one deposit index/kickoff across the system.

### Impact Explanation
This allows the vault UTXO for deposit `j` to be reimbursed to the operator even though the operator never independently fronted a payout for withdrawal `j` — matching the explicitly listed Critical impact "an operator reimbursed for a payout it never funded" and "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." The blast radius scales with however many deposit indices the attacker can get to collide on the same UTXO bytes (each additional colliding index yields another erroneous reimbursement), and is not limited to a single operator or deposit pair. Deposit `j`'s honest depositor's vault funds are drained without a corresponding real withdrawal ever occurring for them.

### Likelihood Explanation
The only precondition on the attacker side is calling `withdraw`/`safeWithdraw` twice with identical UTXO bytes at different deposit indices — explicitly within the attacker's granted capability set (choosing withdrawal UTXO bytes, calling `withdraw`). No collusion with a malicious operator, verifier, or aggregator is required — the vulnerable join and consistency check are automated node logic in this repo (`get_payout_txs_for_withdrawal_utxos`, `is_kickoff_malicious`) that runs unconditionally during normal Citrea sync and kickoff verification. Cost is limited to Bitcoin transaction fees for the withdrawal registration transactions; no majority hashrate, key compromise, or TLS interception is needed. This is repeatable across deposits/withdrawals as long as the Citrea contract does not itself reject duplicate UTXO registrations (a constraint outside this repo).

### Recommendation
Enforce global uniqueness of the withdrawal UTXO (and/or of the underlying payout Bitcoin transaction) to at most one deposit index/`MoveTxid` in this repo's tracking logic: change `get_payout_txs_for_withdrawal_utxos` (and the schema) to prevent the same `spending_txid` from being attributed to more than one `withdrawals.idx`, and add an explicit check in `is_kickoff_malicious` / the bridge-circuit host param construction that a payout's `(withdrawal_utxo_txid, vout)` has not already been consumed by a different, already-reimbursed deposit index before treating a kickoff as non-malicious.

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }

pub fn verify_storage_proofs(
    storage_proof: &StorageProof,
    state_root: [u8; 32],
) -> (WithdrawalOutpointTxid, u32, MoveTxid) {
    let utxo_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_utxo)
            .expect("Failed to deserialize UTXO storage proof");

    let vout_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_vout)
            .expect("Failed to deserialize vout storage proof");

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_deposit_txid)
            .expect("Failed to deserialize deposit storage proof");

    let storage_address: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(UTXOS_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let storage_key_utxo: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2);

    let storage_key_vout: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2 + 1);

    let storage_address_deposit: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(DEPOSIT_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )

        storage_address_deposit + U256::from(storage_proof.index);

    let deposit_storage_key_bytes = deposit_storage_key.to_be_bytes::<32>();

    if deposit_storage_key_bytes != deposit_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid deposit storage key. left: {:?} right: {:?}",
            deposit_storage_key_bytes,
