### Title
Untrusted DLEq proof scalars cause a panic (DoS) during verification on Ed448 — inversion of identity point's `z` coordinate - (File: crypto/ed448/src/point.rs)

### Summary
The CVE is a crash-only bug class: a single crafted byte in attacker-controlled input reaches a parser path that fatally faults the process (use-after-free in Bison, CVSS A:H only). In Serai, the same class maps onto `DLEqProof::verify` over the Ed448 ciphersuite: an unprivileged party can submit a proof whose scalars make the recomputed nonce `R = sG - cA` the identity point, and serializing that point inside the verifier transcript calls `FieldElement::invert().unwrap()` on a zero `z` coordinate, panicking the verifying process. All `read`/`verify` plumbing carries attacker-controlled bytes into this path unchanged.

### Finding Description
`DLEqProof::verify` recomputes the nonce point as `(generator * s) - (point * c)` and immediately transcripts it via `nonce.to_bytes()` in `verify_statement` (crypto/dleq/src/lib.rs:146-157). A proof read from the wire by `DLEqProof::read` (crypto/dleq/src/lib.rs:191-193) accepts any canonical scalars, including `c = 0, s = 0`. With those values, `R = sG - cA` is the additive identity for every generator/point pair.

For Ed448, `GroupEncoding::to_bytes` performs `self.z.invert().unwrap()` (crypto/ed448/src/point.rs:325-327). The identity point is represented with `z = 0`, `Residue::invert` returns a `CtOption` that is `None` for zero, and `unwrap()` panics. There is no `is_identity` guard before the inversion and no check in the dleq verifier rejecting an identity nonce before `to_bytes` is invoked (compare dalek-ff-group where identity is a valid, serializable point — crypto/dalek-ff-group/src/lib.rs:429-437). The Ed448 decoder in `from_bytes` also never produces identity (it enforces `is_torsion_free` and rejects non-canonical encodings), so identity can only arise internally — exactly at this recomputation — making the panic path invisible to serialization round-trips but reachable in verification.

### Impact Explanation
A crafted DLEq proof (two zero scalars, trivially encoded) deterministically panics any Ed448-based DLEq verification. DLEq proofs are used inside in-scope DKG machinery (PedPoP ECDH/promotion flows) where untrusted participants submit proofs. A panic aborts the protocol run for the honest verifier — availability loss with no preconditions on the attacker beyond submitting bytes to a `verify` API, matching the Medium severity (integrity/confidentiality unaffected) of the CVE analog.

### Likelihood Explanation
Reachable by any unprivileged party that can feed bytes to `DLEqProof::read` + `verify` (or to a PedPoP/promote API that verifies a DLEq) where the instantiated ciphersuite is Ed448. The trigger is a constant, byte-trivial input (`c = s = 0`), requires no valid key share, no collusion, and no timing. Exploitation is deterministic rather than probabilistic; the only dependency is the deployment exposing an Ed448 DLEq verification endpoint on untrusted input.

### Recommendation
In `crypto/ed448/src/point.rs` `to_bytes`, handle the identity case explicitly instead of unwrapping a failed inversion — e.g., branch on `self.is_identity()` (or `self.z.is_zero()`) and return the canonical encoding of the identity point (`1` in `y`, `0` sign bit). Additionally, in `DLEqProof::verify`, reject a recomputed nonce that is the identity (`is_identity() → InvalidProof`) before transcribing it, which also hardens other ciphersuites whose `to_bytes` may not define identity serialization.

### Proof of Concept
```rust
// Against Ed448 as the ciphersuite (crypto/dleq/src/lib.rs::verify path)
// c = 0, s = 0 are canonical scalar encodings:
let mut proof_bytes = vec![];
proof_bytes.extend([0u8; 57]); // c = 0
proof_bytes.extend([0u8; 57]); // s = 0
let proof = DLEqProof::<Ed448Point>::read(&mut proof_bytes.as_slice()).unwrap();

// Any generator/point; verification computes R = s*G - c*A = identity,
// then Self::transcript -> nonce.to_bytes() -> z.invert().unwrap() panics.
proof.verify(&mut transcript, &[generator], &[point]); // thread panics on unwrap of CtOption::None
```

The panic occurs inside `verify_statement` at crypto/dleq/src/lib.rs:156 (`(generator * s) - (point * c)` evaluated to identity), reaching `Point::to_bytes` at crypto/ed448/src/point.rs:326 where `invert()` of `z = 0` returns `None` and `unwrap()` panics. Confidence is high on the panic path for Ed448; I could not fully verify within the index whether upstream callers (PedPoP/promote) wrap verification in `catch_unwind`, but the library-level panic itself is confirmed by the code.
