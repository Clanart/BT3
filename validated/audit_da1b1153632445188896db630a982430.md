### Title
Withdrawal DOS via unconditional reward-token harvesting in `MasterMagpie` - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie._withdraw()` unconditionally harvests all accrued reward tokens from the pool's `BaseRewardPool` before releasing the user's staked principal. Because the reward-token transfer loop performs an unwrapped `IERC20.safeTransfer` for every registered reward token with `reward > 0`, a single broken/blocking reward token (e.g. one that later becomes non-transferable, hits a hard cap, or reverts under some balance/state condition) causes the entire withdraw transaction to revert — permanently freezing the user's staked principal, exactly analogous to the dTRINITY `DStakeToken.withdraw()` DOS where a failure in the "Protocol interaction" leg reverted the whole withdraw flow.

### Finding Description
The unprivileged withdraw path is:

`WombatPoolHelper(V2).withdraw()` → `WombatStaking.withdraw()` (unstakes principal) → and separately `MasterMagpie.withdrawFor()`/`MasterMagpie.withdraw()` → `_withdraw()` → `_harvestAndUnstake()`. [1](#0-0) 

`_harvestAndUnstake()` unconditionally calls `_harvestBaseRewarder(_stakingToken, _account)` before decrementing the user's staked amount and returning the staking token: [2](#0-1) 

The bonus-reward harvesting eventually reaches `BaseRewardPoolV2.getReward()` (invoked with the same `getReward(_account, _receiver)` pattern used elsewhere in the codebase, e.g. `_claimBaseRewarder`): [3](#0-2) 

`getReward()` iterates over *every* registered reward token and unconditionally calls `_sendReward`, which performs a raw `safeTransfer` with no try/catch or skip logic: [4](#0-3) [5](#0-4) 

Reward tokens are appended to `rewardTokens[]` over time via `queueNewRewards`/`donateRewards` (any manager can add new reward tokens throughout the pool's life): [6](#0-5) 

If any single token in this growing array becomes unable to complete a transfer to a particular user's address for any external reason (fee-on-transfer edge case causing balance mismatch, token pause, transfer-amount cap, blacklist, or reentrancy-guard interactions on the token itself) — a condition entirely outside the withdrawing user's control — `_sendReward`'s `safeTransfer` reverts, which bubbles up through `getReward` → `_harvestBaseRewarder` → `_harvestAndUnstake` → `_withdraw`, reverting the **entire** withdraw call. There is no code path that lets a user withdraw principal while skipping a single problematic bonus reward token (unlike `getRewards(_account, _receiver, address[] _rewardTokens)` which allows selecting a subset — but that entrypoint is only reachable via claim functions, not via `withdraw`/`withdrawFor`).

### Impact Explanation
Once any reward token accumulated in a pool's `BaseRewardPool.rewardTokens[]` becomes non-transferable for a user (or for the pool contract itself), that user (or all users, if the block applies pool-wide) can no longer call `withdraw`/`withdrawFor` on `MasterMagpie` for that staking token — their principal deposit becomes permanently locked with no exit path, since `_harvestBaseRewarder` is called unconditionally and unskippably inside every withdraw. This is a permanent freezing-of-funds condition satisfying the "24-hour-plus freeze" / "permanent freezing of funds" bar.

### Likelihood Explanation
Reward tokens are added over the pool's lifetime by any registered reward manager via `queueNewRewards`, and the set of reward tokens only grows — it is never pruned. Any single problematic reward token integration (pausable stablecoins, tokens with transfer caps, blacklist-capable tokens, or any token whose transfer to a specific staker address can revert under some condition) permanently poisons the withdraw path for affected stakers, requiring no privileged or malicious action beyond an already-existing pattern of protocols accepting varied ERC20 reward tokens.

### Recommendation
Wrap the reward-token transfer loop (or the whole `_harvestBaseRewarder` call inside `_withdraw`) in a try/catch so a failing reward-token transfer cannot block principal withdrawal, or decouple reward harvesting from the withdraw path entirely (e.g., mark failed reward sends as "still owed" rather than reverting), similar to patterns that isolate bonus-reward distribution from principal-return logic.

### Proof of Concept
1. A reward manager queues a new bonus reward token `X` into a pool's `BaseRewardPool` via `queueNewRewards` [7](#0-6) .
2. Token `X` later becomes non-transferable to some staker's address (e.g., a blacklist-capable stablecoin blacklists the staker's address, or the token enforces a transfer amount/state constraint that reverts under the exact reward amount computed).
3. That staker calls `MasterMagpie.withdraw(_stakingToken, _amount)`.
4. Execution reaches `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPoolV2.getReward` → `_sendReward` → `IERC20(X).safeTransfer(receiver, reward)`, which reverts.
5. The entire `withdraw` transaction reverts; the staker's principal remains locked in `MasterMagpie` indefinitely with no alternative code path to bypass the broken reward token during withdrawal.
