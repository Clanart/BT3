### Title
Unauthenticated JSON-RPC Server on `0.0.0.0` Allows Remote Attacker to Drain Operator Wallet via CPFP Fee Payer Injection and Corrupt Citrea DA Queue — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

### Summary

`start_jsonrpc_server` exposes `send_tx` and `send_citrea_tx` with no authentication. When `TX_SENDER_JSONRPC_BIND=0.0.0.0`, any network-reachable host can call these methods. An attacker who injects a transaction with `FeePayingType::CPFP` and a P2A anchor output triggers the tx-sender to spend operator Bitcoin wallet funds to create fee-payer UTXOs, draining operator collateral through transaction fees. The attacker can also inject arbitrary Citrea DA payloads, corrupting the bridge's DA submission queue.

### Finding Description

`start_jsonrpc_server` constructs a bare `jsonrpsee` `Server` with no middleware layer: [1](#0-0) 

No token check, no IP allowlist, no mTLS — any TCP client that can reach the bound address is accepted. The config explicitly permits `0.0.0.0`: [2](#0-1) 

The default is `127.0.0.1`, but `0.0.0.0` is a documented, supported value. When set, the full attack surface is:

**Attack path 1 — CPFP operator wallet drain:**

The `send_tx` handler accepts a caller-controlled `fee_paying_type`: [3](#0-2) 

The attacker submits a fully-signed transaction (spending their own UTXOs, or even a zero-value dust transaction) that contains a P2A anchor output (`OP_1 OP_PUSHBYTES_2 0x4e73` — a publicly known, anyone-can-spend script) and sets `fee_paying_type = CPFP`. The tx-sender loop calls `send_cpfp_tx`, which finds no confirmed fee-payer UTXOs and falls through to `create_fee_payer_utxo`: [4](#0-3) 

`fund_raw_transaction` selects inputs from the **operator's Bitcoin Core wallet**, `sign_raw_transaction_with_wallet` signs them with the operator's keys, and `send_raw_transaction` broadcasts the fee-payer transaction — all without any validation that the parent transaction was legitimately submitted by a bridge actor. The attacker repeats this in a loop, each iteration burning operator wallet funds as on-chain transaction fees.

**Attack path 2 — Citrea DA queue corruption:**

`send_citrea_tx` inserts arbitrary `BatchProof`, `BatchProofMethodId`, or `SequencerCommitment` payloads into the DA queue with no caller verification: [5](#0-4) 

The tx-sender loop will attempt to commit and broadcast these payloads to Citrea, wasting gas and potentially displacing or interleaving with legitimate bridge DA submissions.

### Impact Explanation

- **Operator wallet drain**: Each attacker-injected CPFP transaction causes `create_fee_payer_utxo` to call `fund_raw_transaction` + `sign_raw_transaction_with_wallet` + `send_raw_transaction`, spending operator wallet UTXOs as on-chain fees. Repeated calls drain operator collateral held in the Bitcoin Core wallet.
- **Citrea DA corruption**: Arbitrary DA payloads injected by the attacker are submitted to Citrea, corrupting the sequencer commitment and batch proof submission pipeline, breaking bridge liveness.
- **Queue pollution**: The `try_to_send` queue is filled with attacker-controlled entries, interfering with legitimate bridge transaction scheduling.

### Likelihood Explanation

`TX_SENDER_JSONRPC_BIND=0.0.0.0` is an explicitly documented, code-validated configuration option. Any deployment that exposes the tx-sender on a non-loopback interface (e.g., in a containerized or cloud environment where the tx-sender is a separate service) is immediately exploitable by any network peer with no credentials required.

### Recommendation

1. Add an authentication middleware layer to `start_jsonrpc_server` (shared bearer token in `Authorization` header, or mTLS client certificate) before registering any RPC methods.
2. If `0.0.0.0` binding is required for multi-host deployments, enforce that authentication is mandatory when the bind address is not `127.0.0.1`.
3. Consider removing `0.0.0.0` as a supported bind value entirely and requiring a reverse proxy with mTLS for cross-host access.
