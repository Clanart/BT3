Based on the investigation, the closest legitimate analog to the GitLab SSRF report is the `isGitHubHost` heuristic in `app/src/lib/api.ts`, which is invoked from the git-credential trampoline helper (`app/src/lib/trampoline/trampoline-credential-helper.ts`) whenever Desktop needs to decide whether to hand over stored GitHub credentials for a git network operation (fetch/clone/pull/push, including submodule operations) against a given remote host.

### Title
Blind SSRF / internal port-scanning oracle via `isGitHubHost` host-probe triggered by attacker-controlled git remote or submodule URL - (File: `app/src/lib/api.ts`)

### Summary
`isGitHubHost()` performs a live network request (`fetch(..., { method: 'HEAD', redirect: 'error' })`) to a URL derived directly from a git remote/submodule host in order to decide whether GitHub credentials should be attached to git operations for that host <cite repo="Annirich/desktop--001" path="app/src/lib/api.ts" start="2429="/>. This mirrors the reported GitLab bug class exactly: a URL supplied by an untrusted party (here, a `.gitmodules` entry or a remote URL in a cloned repository) causes GitHub Desktop to make an outbound request whose success/failure/latency reveals information about hosts and ports on networks reachable from the user's machine, including internal/private addresses.

### Finding Description
`isGitHubHost(url)` is exported from `app/src/lib/api.ts` and, when the hostname doesn't match `github.com`/known third-party hosts, builds `${endpoint}/meta?ghd=<uuid>` from the **caller-supplied URL's host** and issues a `fetch()` HEAD request with a 2-second timeout, explicitly disabling redirects and suppressing certificate errors for that specific URL: [1](#0-0) 

The endpoint is derived straight from `getEnterpriseAPIURL(url)`, i.e. whatever host is embedded in the remote/submodule URL, with no allow-listing of destination IP ranges (no RFC1918/loopback/link-local exclusion): [2](#0-1) 

This function is consumed by `app/src/lib/trampoline/trampoline-credential-helper.ts`, which is the credential-provisioning path invoked transparently by git during every `fetch`/`clone`/`pull`/`push` (including `git submodule update --init --recursive`, which Desktop runs automatically on checkout/pull, per `app/src/lib/git/submodule.ts`) [3](#0-2) . Because `.gitmodules` URLs and `git remote` URLs are fully attacker-controlled content inside a repository the victim clones or a fork they interact with, this gives a remote party the ability to have GitHub Desktop send network probes to arbitrary hosts/ports on the victim's local or internal network as an ordinary side effect of cloning/fetching/checking out a branch — no unusual user action beyond normal repository interaction is required.

The differing behavior the requester can observe (timeout vs TLS/redirect error vs `x-github-request-id` header present/absent, similar in spirit to the original report's "404" vs "connection refused" oracle) lets an attacker fingerprint internal services reachable from the victim's machine.

### Impact Explanation
This is a **blind SSRF against the user's local/internal network**, initiated automatically by ordinary git operations against attacker-supplied remote/submodule URLs. It allows an attacker to:
- Enumerate open vs closed vs filtered ports/hosts on networks reachable only from the victim's machine (intranet scanning), the same primitive as the cited GitLab report.
- Potentially trigger requests to internal management interfaces or metadata endpoints that respond differently to HEAD requests, depending on what's running in the victim's network.

It does **not**, by itself, appear to leak the user's GitHub OAuth token to the probed host — `isGitHubHost` uses `credentials: 'omit'` — so the most severe scenario (token exfiltration through `trampoline-credential-helper.ts`) could not be fully confirmed with the available code excerpts; this would need to be verified by reading `trampoline-credential-helper.ts` in full, which time did not allow.

### Likelihood Explanation
Medium. The trigger requires only that the victim clone a repository, add/fetch a malicious remote, or check out a branch containing a crafted `.gitmodules` file pointing at an internal or attacker-controlled address — all standard Desktop workflows. The 2-second timeout and certificate-error suppression logic exist specifically to make probing arbitrary hosts tolerable, which increases the reachable attack surface (it's designed to talk to whatever host git points it at).

### Recommendation
- Restrict `isGitHubHost`'s destination resolution to exclude loopback, link-local, and RFC1918 private address ranges before issuing the probe request, or resolve DNS and validate the resulting IP prior to connecting.
- Consider gating this probe so it's only performed for hosts that are already trusted/known (e.g., ones added via explicit "Sign in to Enterprise" flow) rather than any arbitrary remote/submodule URL encountered during git operations.
- Audit `app/src/lib/trampoline/trampoline-credential-helper.ts` to confirm no credential material can ever be attached to a request whose destination host was only "confirmed" via this best-effort `isGitHubHost` heuristic.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` file with a submodule URL pointing at an internal address, e.g. `url = http://127.0.0.1:9200/x` or `http://10.0.0.5/x`, or configures a remote with such a host.
2. Victim clones/fetches/checks out a branch in that repository in GitHub Desktop, which triggers `git submodule update --init --recursive` [4](#0-3) .
3. During the associated credential-resolution step, `isGitHubHost()` is invoked with the submodule/remote host and issues a HEAD request to `http://10.0.0.5/meta?ghd=<uuid>` [5](#0-4) .
4. The attacker (having separately compromised or timed the victim, e.g. via out-of-band signal or repeated commits with different target hosts/ports) can infer from the app's subsequent behavior/errors which internal hosts/ports responded, achieving the same "port is open/closed" oracle described in the original GitLab report.

**Caveat:** I was not able to fully trace the exact control flow inside `trampoline-credential-helper.ts` (only confirmed it imports `isGitHubHost` twice) within the available tool budget, so the extent to which this SSRF could also be leveraged for credential exfiltration to the probed host remains unverified and should be checked directly in that file before treating this as a confirmed high-severity issue.

  // Add a unique identifier to the URL to make sure our certificate error
  // supression only catches this request
  const metaUrl = `${endpoint}/meta?ghd=${crypto.randomUUID()}`

  const ac = new AbortController()
  const timeoutId = setTimeout(() => ac.abort(), 2000)
  suppressCertificateErrorFor(metaUrl)
  try {
    const response = await fetch(metaUrl, {
      headers: { 'user-agent': getUserAgent() },
      signal: ac.signal,
      credentials: 'omit',
      method: 'HEAD',
      redirect: 'error',
    })

    tryUpdateEndpointVersionFromResponse(endpoint, response)

    return response.headers.has('x-github-request-id')
  } catch (e) {
    log.debug(`isGitHubHost: failed with endpoint ${endpoint}`, e)
    return undefined
  } finally {
    clearTimeout(timeoutId)
    clearCertificateErrorSuppressionFor(metaUrl)
  }
}
