### Title
Stale per-file manual conflict resolutions leak across unrelated merge/rebase operations, silently corrupting committed content - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` in `app/src/lib/stores/updates/changes-state.ts` carries a user's previous manual conflict resolutions (`ours`/`theirs` per file path) forward into a brand-new merge or rebase as long as the conflict *kind* matches (`merge`→`merge` or `rebase`→`rebase`), without verifying that the new conflict actually belongs to the same operation. When Desktop detects that the branch/target changed (i.e., the prior operation was aborted and a different one started), it only records a telemetry counter — it never clears the stale `manualResolutions` map.

### Finding Description
`updateConflictState` unconditionally reuses the previous resolution map before even computing the new conflict state: [1](#0-0) 

The new state is produced by `getConflictState`, which simply reattaches whatever `manualResolutions` map it was given to the new merge/rebase conflict object, keyed only by file path: [2](#0-1) 

`updateConflictState` then routes to `performEffectsForMergeStateChange` / `performEffectsForRebaseStateChange` purely based on whether both the previous and new conflict states share the same `kind`: [3](#0-2) 

Both effect functions explicitly detect that the underlying branch/target changed (meaning the earlier operation was aborted and a *different* one started against a different branch), but the only action taken is incrementing a stats counter — the `manualResolutions` map that was already threaded into `newConflictState` is never invalidated: [4](#0-3) [5](#0-4) 

The existing unit tests confirm this behavior is by design for the *continuation* case (same operation, new commit in the sequence, tip changes but resolutions persist) but do not cover — and the implementation does not distinguish — the case where `branchNameChanged` is true and a completely different merge/rebase begins: [6](#0-5) [7](#0-6) 

The corrupted value is the `manualResolutions: Map<string, ManualConflictResolution>` inside `ConflictState`: it should be scoped to a single merge/rebase operation (identified by branch + tip lineage) but is instead scoped only by conflict `kind`. Because `ManualConflictResolution` stores an abstract choice (`ours`/`theirs`) rather than a concrete content hash, replaying it against a different operation applies the choice to whatever content the *new* operation places at that path — which, in a merge, is attacker-controlled if the new incoming branch is attacker-controlled (a malicious PR branch, a crafted remote ref, or a repository the user was tricked into merging via a link/deep-link). Files carried over as already "resolved" from the stale map are staged via `stageManualConflictResolution` without requiring the user to re-review that specific file's diff.

### Impact Explanation
If a user aborts a conflicted merge/rebase against one branch and then merges/rebases against a different (attacker-influenced) branch that happens to conflict on the same file path, Desktop can silently reapply the old `theirs`/`ours` decision to the new, unrelated content at that path. This results in silent corruption of what the user commits — the resulting commit content at that path is decided by a decision the user made for a different operation, potentially incorporating attacker-controlled content into the user's history without a fresh review prompt. This falls squarely into the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Requires a fairly specific user flow: abort/interrupt a merge or rebase, then start a second, different merge/rebase (e.g., against a malicious PR branch or remote ref) that conflicts on the same file path used in the earlier operation. No local/physical access or credentials are needed — the second conflicting branch is the only thing an attacker needs to control (e.g., via a crafted pull request the victim opens/merges through Desktop). This makes the likelihood **Medium**: plausible in normal usage patterns (users frequently abort and restart conflicted operations) but does depend on file-path coincidence and requires unfixed conflicts to remain outstanding across two distinct operations.

### Recommendation
Scope `manualResolutions` to the identity of the operation, not just its `kind`. When `branchNameChanged` (or equivalently, when the rebase's `targetBranch`/`originalBranchTip`/`baseBranchTip` or the merge's `currentBranch` differ from the previous state), clear the `manualResolutions` map before returning the new conflict state in `updateConflictState`, e.g.:

```ts
if (branchNameChanged) {
  return getConflictState(status, new Map())
}
```

applied symmetrically for both the merge and rebase branches inside `updateConflictState`, so resolutions never survive a change of underlying operation.

### Proof of Concept
1. Victim opens Desktop, attempts to merge branch `feature-A` (could be a PR from a collaborator) into `main`. A conflict occurs on `config.json`; the victim manually marks it resolved with `theirs` (accepting `feature-A`'s version) but leaves other files unresolved, then aborts the merge.
2. `updateConflictState` records `manualResolutions = { "config.json": theirs }` tied to the merge conflict state for `feature-A`.
3. Victim later merges a different, attacker-controlled branch `feature-B` (e.g., an externally submitted PR checked out via Desktop's PR flow) into `main`. `feature-B` also conflicts on `config.json`, this time containing attacker-crafted content.
4. Because both `prevConflictState` and `newConflictState` are `kind: 'merge'`, `updateConflictState` carries over `manualResolutions` unchanged (per `changesState.ts:268-275`); `performEffectsForMergeStateChange` detects `branchNameChanged` and bumps `mergeAbortedAfterConflictsCount`, but does not clear the map (`changesState.ts:184-216`).
5. `config.json` is now treated by Desktop as already resolved with `theirs`, silently staging `feature-B`'s attacker-controlled content for that file into the merge commit without prompting the victim to review it again.

Verification of this proof of concept was limited to the store-layer logic; whether the UI unconditionally treats stale `manualResolutions` entries as "resolved" without ever re-surfacing the file for review (rather than re-detecting the conflict as unresolved through some other check) was not independently confirmed due to index coverage limits on the full conflict-list rendering components (e.g., `app/src/ui/multi-commit-operation/dialog/conflicts-dialog.tsx`). Confirming the full end-to-end UI behavior would require a live Desktop session.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}
