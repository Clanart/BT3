### Title
Gasless swap deadline checked only at tx-pool admission time, not re-validated before block inclusion, allowing stale/expired quotes to execute - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The kaiax gasless module validates a user-supplied `deadline` for a `swapForGas` transaction only once, at the moment the transaction is submitted to the transaction pool via `checkBalanceForSwap`. Like the audited protocol's failure to re-check option maturity (`optionsRenewedTimeStamp`) at withdrawal time, Kaia's gasless swap path checks the time-bound condition (`deadline >= currentTimestamp`) against the pool's *admission-time* block, but the swap conditions (exchange rate implied by `MinAmountOut`/`AmountRepay`, and the deadline itself) are not re-verified at the time the transaction is actually promoted and executed in a later block.

### Finding Description
`checkBalanceForSwap` performs the deadline check: [1](#0-0) 

This function is invoked by `GetCheckBalance`, which is called from `TxPool.validateTx` at the time the transaction is added to the pool: [2](#0-1) 

However, `demoteUnexecutables`, which runs on every new head/reset, only performs this "full validation" (which would re-invoke module checks including the deadline) for a bounded number of transactions per pool via `demoteUnexecutablesFullValidationTxLimit`; beyond that limit it falls back to `FilterUnexecutable`, which only checks nonce/balance, not module-specific conditions such as the gasless deadline: [3](#0-2) 

Because the deadline is a value chosen by the swap-tx sender (an untrusted, unprivileged party) and is only checked against the current chain head at admission time, a transaction can sit in the pool (pending or requeued after reorg) across many blocks without deadline re-verification once the per-reset full-validation budget is exhausted. If the transaction is eventually promoted into a block whose timestamp is past `deadline`, nothing in the client stops it from being included and executed by `swapForGas` on-chain (the deadline enforcement, if any, exists only in the off-chain client-side quote check, not in a client-verified consensus rule beyond the coarse tx-pool admission check). This mirrors the audited bug's root cause: a maturity/time-bound condition is checked once but not strictly re-validated at the point where the economically consequential action (settlement / value transfer) actually occurs.

### Impact Explanation
If a stale gasless swap executes after its intended deadline, the `MinAmountOut`/exchange-rate guarantee that the deadline was meant to protect (price staleness protection for the swap-for-gas mechanism) is defeated. Since `swapForGas` moves ERC20 tokens from the user to the router/backend to be swapped for KAIA and repay the fee-delegated relayer, execution against a stale quote can result in the gasless-fee-delegation counterparty (the relayer/protocol) accepting worse terms than intended, or a swap executing under price conditions the deadline was designed to prevent, causing a financial mismatch between the amount repaid and the amount that should have been repaid under fresh conditions — directly analogous to the original report's "borrower pays back less debt than intended" value-movement mismatch.

### Likelihood Explanation
This requires no privileged access: any unprivileged transaction sender can submit an approve+swap gasless bundle with a deadline, and network conditions (congestion, low gas price causing the tx to sit un-promoted, or a chain reorg) can cause the transaction to remain in the pool past the per-reset full-validation budget before being included in a block. This is a plausible, attacker-uncontrolled-but-attacker-triggerable scenario (an attacker can deliberately submit low-priority/low-gas transactions to keep them pending across many resets) rather than a purely theoretical one.

### Recommendation
Re-validate the swap `deadline` (and other economically consequential swap conditions) against the actual block timestamp at the point of block assembly/inclusion (e.g., in `IsReady`/bundle extraction or immediately before applying the transaction in the state transition), not only during initial pool admission or the capped `demoteUnexecutables` full-validation pass. Ensure `FilterUnexecutable` (or an equivalent module hook) also strips transactions whose module-specific time-bound conditions have expired, regardless of the full-validation transaction count limit.

### Proof of Concept
Not independently reproduced; based on static code-path analysis. A candidate PoC path: submit a `swapForGas` transaction with a low gas price and a short `deadline` (e.g., `deadline = currentBlockTime + 5`) into a congested pool (or one exceeding `demoteUnexecutablesFullValidationTxLimit`), causing the pool to skip full re-validation across several block resets, then let the transaction get promoted after `deadline` has elapsed and confirm it's not dropped by the coarse `FilterUnexecutable` nonce/balance check before inclusion.

**Uncertainty note:** I could not locate the `GaslessSwapRouter.sol` Solidity source in this repository (only compiled Go bindings exist under `contracts/bindings/kip247/`), so I could not confirm whether the on-chain contract independently enforces `deadline` in `swapForGas`. If the on-chain contract does enforce the deadline itself, the impact would be reduced to a denial-of-service/wasted-gas issue rather than value-movement abuse, and this may fall outside "Medium/High/Critical" per the exclusion of low/resource-only findings. This should be verified against the actual deployed bytecode/ABI before treating this as fully confirmed.
