### Title
Permissionless referral code registration allows self-referral to drain the MGP referral reward pool - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.registerCode()` and `useCode()` are fully permissionless and unpermissioned, mirroring the Turnstile `register()` pattern in the external report. Any wallet can mint an arbitrary referral code and any other wallet can bind itself as that code's referee. Because the only anti-abuse check is a same-address check (`codeOwners[_code] == msg.sender`), a single actor can trivially operate two addresses — one as "referrer", one as "referee" — and capture both the referrer and referee shares of every claim, redirecting protocol-funded referral incentives to themselves instead of it going to genuine, unrelated referral relationships.

### Finding Description
`registerCode()` lets any address claim any unused `bytes32` code with no restriction: [1](#0-0) 

`useCode()` only blocks the trivial case where the same `msg.sender` uses their own code, but does nothing to prevent a colluding second address (fully controlled by the same actor) from using it: [2](#0-1) 

When `MasterMagpie._multiClaim()` processes a claim, it calls into `ReferralStorage.trigger()` with the referee's full claimed reward amount, and `trigger()` mints/credits *additional* MGP reward to both the referrer and referee based on `(basic + boosted)` percentages of that claim — funds separate from and on top of the reward the user already receives via `_sendMGP`/`_sendVlMGPFor`: [3](#0-2) [4](#0-3) 

Because registration/usage is Sybil-free-for-all (exactly like Turnstile's permissionless `register()`), a single actor with two wallets can register a code with wallet B, bind wallet A to that code via `useCode`, and every time wallet A claims, both the referrer share (credited to B) and the referee share (credited to A) accrue to the same beneficial owner — extracting `(basic + boosted)%` of every claim from the referral pool that is meant to reward genuine third-party referrals. Later `claimReward()` pays this out directly from the contract's MGP balance: [5](#0-4) 

This is the direct analog of the Turnstile issue: permissionless self-registration lets an unprivileged actor redirect value (there, transaction fee refunds; here, referral incentive payouts) that is designed to flow to a distinct, independent party, back to themselves instead — with no mechanism (e.g., KYC/whitelisting, activity thresholds, or code-ownership verification) to prevent self-dealing across two addresses.

### Impact Explanation
The referral reward pool held by `ReferralStorage` (funded by the protocol/treasury to reward genuine referrals) can be systematically drained by any user simply by operating two wallets, with no real referral activity taking place. Every claim by the "referee" wallet siphons `(basic + boosted)%` of the claimed reward into MGP tokens payable to both self-controlled addresses, at the expense of the pool intended to reward real referrers/referees and ultimately the protocol treasury that funds it. This constitutes theft of protocol-allocated yield/incentives.

### Likelihood Explanation
High likelihood: `registerCode` and `useCode` require no permission, no minimum stake, no cooldown, and no verification that referrer and referee are economically distinct parties. Any staker can trivially deploy or use a second EOA to self-refer on every claim.

### Recommendation
Add anti-Sybil protections to the referral system: e.g., require KYC/whitelisting for code issuance, restrict code registration to addresses with a demonstrated independent staking history, cap boosted-tier percentages, or require an explicit relationship attestation. At minimum, detect and block referrer/referee pairs that are likely controlled by the same entity (same funding source, same first-interaction transaction, etc.), or make referral reward funding proportional to net-new capital brought in by the referee rather than a flat percentage of claims.

### Proof of Concept
1. Attacker controls wallets `A` and `B`.
2. `B` calls `ReferralStorage.registerCode(codeX)` — permissionless, succeeds since `codeOwners[codeX] == address(0)`.
3. `A` calls `ReferralStorage.useCode(codeX)` — succeeds since `codeOwners[codeX] != msg.sender` (different address) and `A` has no existing referral.
4. `A` stakes into MasterMagpie and calls `multiclaim`, triggering `_multiClaim` → `ReferralStorage.trigger(A, totalReward)`.
5. `trigger()` credits `refererAmount` to `B.rewardAmount` and `refereeAmount` to `A.rewardAmount`, both controlled by the attacker.
6. Attacker calls `claimReward()` from both `A` and `B`, extracting `(basic + boosted)%` extra MGP from the pool for pure self-dealing, with no genuine referral having occurred. [6](#0-5)
