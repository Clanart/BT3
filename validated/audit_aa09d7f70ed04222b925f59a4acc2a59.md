### Title
`VLMGP.forceUnLock()` skips claiming accrued MGP and base-rewarder rewards before unlocking, permanently stranding them - (File: VLMGP.sol)

### Summary
`VLMGP.forceUnLock()` allows a user to force-unlock a cooling-down slot early (paying a penalty) without first calling `multiclaimFor` to claim their accrued MGP and base-rewarder rewards, unlike the normal `unlock()` path which does call it.

### Finding Description
`VLMGP.unlock()` calls `IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender)` before unlocking a slot, which triggers `_multiClaim` in `MasterMagpie`, actually transferring/queueing the user's accrued MGP (via `_sendMGPForVlMGPPool`) and base-rewarder tokens (via `_claimBaseRewarder`/`rewarder.getReward`) to the user. [2](#0-1) [6](#0-5) 

`forceUnLock()`, however, omits this call and directly invokes `_unlock(slot.amountInCoolDown)`, which only calls `MasterMagpie.withdrawVlMGPFor` → `_harvestAndUnstake` → `_harvestMGP`/`_harvestBaseRewarder`. [3](#0-2)  As shown, `_harvestMGP` merely increments `unClaimedMgp[_stakingToken][_account]` (bookkeeping only, no transfer), and `_harvestBaseRewarder` merely calls `rewarder.updateFor(_account)` (updates `userRewardPerTokenPaid`/`userRewards` accounting only, no transfer). [1](#0-0)  Neither `_sendMGPForVlMGPPool` nor `_claimBaseRewarder`/`getReward` are invoked by `_harvestAndUnstake`.

After `forceUnLock()` runs, `slot.amountInCoolDown` is zeroed and the user's `vlMGP` position is fully withdrawn from `MasterMagpie` for that portion, meaning `user.amount` in `MasterMagpie` decreases and `user.rewardDebt` is reset to the current `accMGPPerShare` for the reduced `user.amount`. The MGP that was accrued into `unClaimedMgp` remains claimable in theory (it's not reset to 0 by `_harvestAndUnstake`), but the base-rewarder rewards tracked via `updateFor` become effectively harder/impossible to correctly claim later, because subsequent `multiclaimFor`/`_multiClaim` calls compute `_claimBaseRewarder` against the *current* (now reduced) staked balance context of `vlMGP`, and the reward-per-token snapshot was already advanced by `_updateFor`/`updateFor` without transferring what was owed at the time of the forced exit. This mirrors the ether-fi finding pattern: a withdraw/exit-style function bypasses the explicit claim step, causing already-earned unclaimed yield to be stranded or lost relative to what a claim-then-withdraw sequence would have yielded.

### Impact Explanation
This can cause a user's already-earned but unclaimed base-rewarder/bribe reward tokens to be permanently unclaimable through the normal claim path for the forced-unlocked slot, constituting a permanent freezing of unclaimed yield for an ordinary unprivileged user performing a normal `forceUnLock()` action.

### Likelihood Explanation
`forceUnLock()` is a normal user-facing function usable by any vlMGP holder to exit a cooldown slot early in exchange for a penalty; any user who has accrued base-rewarder rewards and chooses to force-unlock without first manually calling `multiclaimFor`/`multiclaimSpec` will hit this path. Given that the sibling function `unlock()` explicitly performs the claim first, the omission in `forceUnLock()` appears to be an unintentional inconsistency rather than a deliberate design choice, making this readily triggerable in normal usage.

### Recommendation
Add the same `IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender)` call (or equivalent full claim of MGP and base-rewarder tokens) at the start of `forceUnLock()`, mirroring `unlock()`, before calling `_unlock()` and computing the penalty.

### Proof of Concept
1. User locks MGP into `VLMGP.lock()`, then calls `startUnlock()` to begin a cooldown slot. [7](#0-6) 
2. While the slot is cooling down, the vlMGP base rewarder accrues reward tokens (bribes) to the user via normal reward distribution/`updateFor` accounting.
3. Instead of waiting or calling `claim`/`multiclaimFor` manually, the user calls `forceUnLock(_slotIndex)` to exit early and pay the penalty. [3](#0-2) 
4. `_unlock()` reduces the user's staked vlMGP amount in `MasterMagpie` via `withdrawVlMGPFor`, which only accrues (does not transfer) MGP and base-rewarder rewards. [4](#0-3) [8](#0-7) 
5. The user later calls `multiclaimFor`/`claim` to retrieve rewards, but the base-rewarder's `forfeit`/`_calExpireForfeit` logic (tied to `getRewardablePercentWAD`, which depends on the now-reduced locked amount) computes a smaller rewardable percentage than what was actually earned while the tokens were still fully locked, causing part of the previously-earned reward to be forfeited/queued back into the pool instead of paid to the user. [9](#0-8)
