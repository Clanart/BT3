## Title
Silent history-window truncation causes `--root` misuse in interactive rebase (squash/reorder), rewriting unintended ancestor commits - ([File: app/src/ui/history/commit-list.tsx])

### Summary
The Fuel report fixes an integer/index computation that incorrectly assumed "genesis" (block height 0) when the target was actually beyond the loaded/visible chain state, causing an overflow when the code subtracted from that assumed boundary. The structurally equivalent invariant in GitHub Desktop is the "is this the root commit of the branch" check used to decide whether an interactive rebase must use `--root` instead of a `<sha>` ref, computed in `CommitList.getLastRetainedCommitRef` [1](#0-0) , and consumed by `rebaseInteractive` [2](#0-1) .

### Finding Description
`getLastRetainedCommitRef` decides "is this commit the root of history" purely by comparing the selected commit's index to `this.props.commitSHAs.length - 1`: [1](#0-0) 

`commitSHAs` is not necessarily the full ancestry of the branch — it is the batch of commits the UI currently has loaded (loaded incrementally via `CommitBatchSize` in `app/src/lib/stores/git-store.ts`). If the loaded window happens to end exactly at the commit the user is squashing/reordering — for example because the app has only paged in that many commits, or because of how `reconcileHistory`/batch loading interacts with a remote-controlled ref graph [3](#0-2)  — the code treats that commit as the branch's true root and returns `null` for `lastRetainedCommitRef`.

That `null` is passed to `rebaseInteractive`, which then uses git's `--root` flag instead of a specific ref: [2](#0-1) 

`--root` tells git to rebase the *entire* history of the branch from its actual first commit, not just "everything from the loaded window downward." If the real root is much deeper (more ancestor commits exist that simply weren't loaded into `commitSHAs` yet, e.g. on a large/attacker-crafted history obtained by clone/fetch), this silently expands the scope of the interactive rebase to include commits the user never selected or saw, and `squash.ts`/`reorder.ts` build their todo-list purely from `getCommits(repository, lastRetainedCommitRef === null ? undefined : revRange(...))` [4](#0-3) [5](#0-4)  — when `lastRetainedCommitRef` is `null`, `getCommits` is called with an undefined range, i.e. the whole history from `HEAD`. This is the exact same shape of bug as the Fuel issue: a boundary condition ("am I at the true origin?") computed from a partial/loaded view of state instead of true ground truth, causing the operation to silently extend past the intended boundary.

### Impact Explanation
If the attacker can influence what the victim clones/fetches (a malicious or compromised remote), they can craft a branch whose committed-batch boundary coincides with the commit a victim later selects for squash/reorder in Desktop's UI (a normal, expected user action). The result is that Desktop invokes `git rebase --root`, silently replaying/rewriting far more history than the user intended and requested. This can corrupt what the user believes they are committing (their own local, possibly signed/verified history gets non-consensually rewritten and force-pushed later), which matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires a specific, narrow condition — the client's currently-loaded `commitSHAs` window must end exactly at the commit being operated on while more history genuinely exists upstream — and requires the user to initiate a squash/reorder on that boundary commit. It is not trivially attacker-triggerable without also influencing commit-list pagination timing, which depends on internal batch-loading behavior (`CommitBatchSize` in `git-store.ts`) that I was not able to fully trace before running out of tool calls. I could not confirm the exact default batch size or whether the CommitList component's `commitSHAs` prop is always guaranteed (via some other invariant elsewhere in `git-store.ts` or `app-store.ts`) to represent the complete history rather than a partial page — this is the main open question that determines whether the bug is reachable in practice.

### Recommendation
Do not infer "is root" from `commitSHAs.length`/index equality in the UI layer. Instead, determine root status authoritatively from git itself (e.g., check whether the candidate commit has zero parents, or explicitly verify that `commitSHAs` represents the full loaded history down to the actual root before treating boundary index as root) before returning `null` for `lastRetainedCommitRef`.

### Proof of Concept
Not fully verified — this requires confirming (in `app/src/lib/stores/git-store.ts`) whether/when `commitSHAs` passed into `CommitList` can be a truncated prefix of history rather than the complete ancestry to the root commit. If confirmed, the PoC would be: create a repo with a deep history via a malicious remote, have the victim clone/fetch it such that Desktop only loads N commits into the visible history list, have the victim select and squash the Nth (oldest loaded) commit, and observe that `git rebase --root` is invoked, rewriting commits beyond the N the user intended.

  private getLastRetainedCommitRef(indexes: ReadonlyArray<number>) {
    const maxIndex = Math.max(...indexes)
    const lastIndex = this.props.commitSHAs.length - 1
    /* If the commit is the first commit in the branch, you cannot reference it
    using the sha */
    const lastRetainedCommitRef =
      maxIndex !== lastIndex ? `${this.props.commitSHAs[maxIndex]}^` : null
    return lastRetainedCommitRef
  }

  public async reconcileHistory(mergeBase: string): Promise<void> {
    if (this._history.length === 0) {
      return
    }

    if (this.requestsInFight.has(LoadingHistoryRequestKey)) {
      return
    }

    this.requestsInFight.add(LoadingHistoryRequestKey)

    const range = revRange('HEAD', mergeBase)

    const commits = await this.performFailableOperation(() =>
      getCommits(this.repository, range, CommitBatchSize)
    )
    if (commits == null) {
      return
    }

    const existingHistory = this._history
    const index = existingHistory.findIndex(c => c === mergeBase)

    if (index > -1) {
      log.debug(
        `reconciling history - adding ${
          commits.length
        } commits before merge base ${mergeBase.substring(0, 8)}`
      )

      // rebuild the local history state by combining the commits _before_ the
      // merge base with the current commits on the tip of this current branch
      const remainingHistory = existingHistory.slice(index)
      this._history = [...commits.map(c => c.sha), ...remainingHistory]
    }

    this.storeCommits(commits)
    this.requestsInFight.delete(LoadingHistoryRequestKey)
    this.emitUpdate()
