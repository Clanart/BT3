## Finding

### Title
Git LFS smudge/clean filters inherit Desktop's credential-helper trampoline env, letting a malicious `.lfsconfig` redirect and exfiltrate any stored Git credential to an attacker-chosen host - ([File: app/src/lib/trampoline/trampoline-environment.ts])

### Summary
GitHub Desktop authenticates Git operations by injecting `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and a `GIT_CONFIG_PARAMETERS` value that force-enables `credential.helper=desktop` for *every* process in the Git invocation tree, explicitly including filters such as Git LFS's smudge/clean hooks. The credential-helper trampoline server resolves and returns stored secrets purely based on the "host" field supplied in the incoming `git credential fill` request, with no verification that this host matches the repository's actual remote. Because `.lfsconfig` — a plain tracked file inside any cloned/fetched repository — lets the repository author set `lfs.url` to an arbitrary URL, an attacker-controlled repository can cause the LFS smudge filter (spawned automatically during clone/fetch/checkout) to request credentials for a host of the attacker's choosing, and Desktop's trampoline will hand back the user's previously stored token/password for that host without any additional user interaction.

### Finding Description
`withTrampolineEnv` builds the environment used for every Git subcommand: [1](#0-0) 

The comment on `GIT_CONFIG_PARAMETERS` states plainly that env vars (rather than `-c` args) were chosen specifically so that **filter commands such as Git LFS pick up `credential.helper=desktop`**. This means any filter process git spawns while checking out/fetching a malicious repo inherits `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN`, and has `credential.helper=desktop` forced on for its own `git credential fill/store/erase` calls.

The trampoline server only validates that the token is a *currently valid* trampoline token — it does not restrict which credential requests can be served during that token's lifetime: [2](#0-1) 

When the credential-helper handler processes a `get`, it derives the target host solely from the credential request payload (`getCredentialUrl(cred)`), which for a generic (non-GitHub) host resolves through `findGenericTrampolineAccount`: [3](#0-2) 

`getGenericPassword(endpoint, login)` looks up whatever was previously saved by the user for that hostname via `setGenericCredential`/`saveGenericGitCredentials` — there is no check that `endpoint` corresponds to the remote of the repository whose fetch/clone spawned the trampoline token: [4](#0-3) 

Git LFS supports a repository-tracked `.lfsconfig` file that overrides `lfs.url` for the smudge/clean filters. Since `.lfsconfig` ships as ordinary repository content, an attacker who controls a repository the victim clones or fetches can set `lfs.url` to `https://<host-victim-has-saved-credentials-for>/...`. When Desktop performs a normal fetch/clone/checkout on that repository, Git spawns the LFS smudge filter to materialize LFS pointers; that filter process inherits the trampoline env described above, contacts the attacker-chosen `lfs.url` host, and — needing auth — calls `git credential fill`, which is served by Desktop's `credential.helper=desktop`. The credential helper returns the victim's real stored secret for that host, which the filter then sends as an `Authorization` header in its LFS batch/API request to the attacker-chosen destination — all without any prompt, confirmation, or connection to the actual repo/remote the user thought they were interacting with.

### Impact Explanation
This breaks the invariant that a credential saved for host A is only ever transmitted for operations the user actually initiated against host A. A hostile, otherwise-unrelated repository (which the victim may clone purely out of curiosity, or add as a submodule/dependency) can silently trigger authenticated network requests carrying the victim's real GitHub/GHE/generic Git credential to any host the victim has previously saved a credential for in Desktop — a confused-deputy credential relay/exfiltration primitive requiring no user click beyond a routine fetch/clone/checkout. If the attacker also controls or can observe that target host (e.g., the victim reuses credentials across a self-hosted Git/LFS server the attacker can log requests on), the token itself is exfiltrated; even without that, it lets an attacker use Desktop as a blind SSRF/auth oracle against arbitrary hosts the victim has credentials for.

### Likelihood Explanation
Requires only that the victim clone/fetch/checkout an attacker-supplied repository containing an `.lfsconfig` — normal, unprompted GitHub Desktop usage. No admin rights, local access, or social engineering beyond "user opens/clones a repo" (already an accepted valid-impact trigger). The design intentionally propagates the credential helper into filter subprocesses via environment variables, so the attack surface is by design rather than incidental, and the generic-credential lookup performs no origin/host binding to the operation that created the token.

### Recommendation
- Scope trampoline tokens (and the credential helper's lookups) to the specific remote URL(s) the git operation was invoked against, rejecting `get` requests for hosts that don't match the operation's declared remote(s).
- Do not propagate `credential.helper=desktop` unconditionally to filter subprocesses; instead, restrict/allow-list filter credential requests to the same host as the top-level operation, or require explicit user confirmation the first time a filter requests credentials for a different host.
- Treat `.lfsconfig`-declared `lfs.url` values as untrusted input and warn or prompt before using Desktop-managed credentials against an LFS endpoint that differs from the repository's configured remote.

### Proof of Concept
1. Attacker publishes a public repository containing:
   - `.gitattributes`: `*.bin filter=lfs -text`
   - `.lfsconfig`:
     ```
     [lfs]
       url = "https://victim-has-saved-credential-host.example/lfs-endpoint"
     ```
   - A tracked LFS pointer file `payload.bin`.
2. Victim, who has previously saved generic Git credentials in Desktop for `victim-has-saved-credential-host.example` (e.g., an internal GitLab/Gitea instance), clones or fetches the attacker's repository in GitHub Desktop.
3. Desktop performs the fetch/checkout via `git()`/`withTrampolineEnv`, injecting `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, and `GIT_CONFIG_PARAMETERS='credential.helper=desktop'` [1](#0-0) .
4. Git invokes the LFS smudge filter for `payload.bin`; LFS reads `.lfsconfig`, targets `victim-has-saved-credential-host.example`, and calls `git credential fill`, which routes to Desktop's trampoline server and handler [5](#0-4) .
5. `getGenericCredential`/`findGenericTrampolineAccount` returns the victim's real stored password/token for that host with no check that it matches the actual repo remote [3](#0-2) , which LFS then sends to the attacker-chosen endpoint.

export async function findGenericTrampolineAccount(
  trampolineToken: string,
  remoteUrl: string
) {
  const parsedUrl = new URL(remoteUrl)
  const endpoint = urlWithoutCredentials(remoteUrl)

  const login =
    parsedUrl.username === ''
      ? getGenericUsername(endpoint)
      : parsedUrl.username

  if (!login) {
    return undefined
  }

  const token = await memoizedGetGenericPassword(
    trampolineToken,
    endpoint,
    login
  )

  if (!token) {
    // We have a username but no password, that warrants a warning
    log.warn(`credential: generic password for ${remoteUrl} missing`)
    return undefined
  }

  return { login, endpoint, token }
