## Publish-Path Analog Found



### Title
`freeze_code_object` does not prevent new packages from being added to a "frozen" code object, defeating the immutability guarantee - (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
The bug-class root cause in the Maple report is that a party can present an address whose stored code/commitment is trusted as fixed, then legitimately or covertly cause new code to appear at that same address, defeating a consumer's trust that "this address's code cannot change." The Aptos-native analog is in `aptos_framework::code::freeze_code_object` / `aptos_framework::object_code_deployment`: freezing a code object is documented and expected to make the object's code permanently immutable, but the implementation only marks the *packages that already exist in the registry* as immutable. It does not prevent the object owner from later publishing an entirely new, differently-named package to the very same object address, which bypasses the immutability check entirely.

### Finding Description
`object_code_deployment::freeze_code_object` [1](#0-0)  delegates to `code::freeze_code_object`, which iterates the registry's *existing* packages and sets `upgrade_policy = immutable` on each of them [2](#0-1) .

However, `code::publish_package` (invoked transitively by `object_code_deployment::upgrade`, which still has access to the object's `ExtendRef` via `ManagingRefs` even after freezing [3](#0-2) ) only checks immutability for a package whose `name` matches an existing entry:

```
package_immutable.enumerate_ref(|i, old| {
    let old: &PackageMetadata = old;
    if (old.name == pack.name) {
        upgrade_number = old.upgrade_number + 1;
        check_upgradability(old, &pack, &module_names);   // <- only path that checks immutability
        index = i;
    } else {
        check_coexistence(old, &module_names)              // <- only checks module-name clashes
    };
});
``` [4](#0-3) 

`check_upgradability` is the only function that asserts `old_pack.upgrade_policy.policy < upgrade_policy_immutable().policy` [5](#0-4) . `check_coexistence`, taken when the incoming package has a *new* name, never inspects `old_pack.upgrade_policy` at all — it only rejects overlapping module names [6](#0-5) . Because the new package's name doesn't match `old.name`, it falls into the `index == len` branch and is simply pushed into the registry unconditionally [7](#0-6) .

The module's own documentation states the intended invariant: "Once modules are marked as immutable, they cannot be made mutable again" and "Each `code_object` should only have one package, as one package is deployed per object" [8](#0-7) . Nothing in the code enforces the "one package per object" assumption, and nothing blocks introducing an entirely new package (with a distinct name and fresh, mutable `upgrade_policy`) at an address whose existing packages were frozen.

### Impact Explanation
Any downstream consumer, integrator, or automated trust check (e.g., a DeFi protocol, an indexer, or an auditor) that relies on `freeze_code_object`/`PackageRegistry.packages[*].upgrade_policy == immutable` as a permanent, address-wide guarantee that "no new code can ever land at this address" can be misled: the object owner (holding the `ExtendRef`) can still call `object_code_deployment::upgrade` with a new package name and inject fresh, initially-mutable, and later upgradable code at what is publicly believed to be a permanently immutable address. This is directly analogous to the Solidity finding where a party can reintroduce new/malicious logic at an address whose prior state was trusted as fixed — the address-level "freeze" commitment does not hold. This can corrupt code-ownership/immutability assumptions used for security review sign-off (e.g., "we only need to audit this object once because it's frozen"), enabling delayed publication of malicious modules under the guise of an already-vetted, frozen object address.

### Likelihood Explanation
The action requires no privilege escalation — it is performed by the legitimate object owner who already holds `ManagingRefs`/`ExtendRef` for the object (the same authority that called `freeze_code_object`). No external validation, dependency check, or governance step blocks it; `check_coexistence` unconditionally allows it as long as module names don't collide with existing ones. This makes the bypass trivial and always reachable for any code object that has been "frozen," which is a supported, encouraged, permissionless workflow (object code deployment) with current mainnet relevance.

### Recommendation
In `code::publish_package`, when iterating existing packages in `PackageRegistry`, reject publishing any new package (regardless of name) whenever *any* existing package in that registry has `upgrade_policy == immutable` and the deployment target is a code object that has been explicitly frozen — or, more directly, track an object-level "frozen" flag (e.g., a boolean in `PackageRegistry` or a marker resource written by `freeze_code_object`) and have `publish_package`/`request_publish_with_allowed_deps` abort unconditionally for any target address carrying that flag, regardless of whether the new package's name matches an existing one. This aligns implementation with the documented one-package-per-object, permanently-immutable-after-freeze invariant.

### Proof of Concept
1. Publish package `A` (module `A::m`) to a fresh object via `object_code_deployment::publish`.
2. Call `object_code_deployment::freeze_code_object` on that object — `PackageRegistry.packages[0].upgrade_policy` becomes `immutable`.
3. As the same owner (still holding `ManagingRefs.extend_ref`), call `object_code_deployment::upgrade` again, this time with a *different* package name `B` (module `B::n`), targeting the same `code_object`.
4. `code::publish_package` iterates: `old.name ("A") != pack.name ("B")` → takes the `check_coexistence` branch → no immutability check is performed → package `B` is pushed into the registry and its modules are published, succeeding despite the object having been "frozen."
5. Verify: `PackageRegistry.packages` at the object address now contains 2 entries — the immutable `A` and a brand-new, non-immutable `B` — demonstrating that new code can be introduced after freeze.

    public fun freeze_code_object(publisher: &signer, code_object: Object<PackageRegistry>) acquires PackageRegistry {
        let code_object_addr = code_object.object_address();
        assert!(exists<PackageRegistry>(code_object_addr), error::not_found(ECODE_OBJECT_DOES_NOT_EXIST));
        assert!(
            object::is_owner(code_object, signer::address_of(publisher)),
            error::permission_denied(ENOT_PACKAGE_OWNER)
        );

        let registry = borrow_global_mut<PackageRegistry>(code_object_addr);
        registry.packages.for_each_mut(|pack| {
            let package: &mut PackageMetadata = pack;
            package.upgrade_policy = upgrade_policy_immutable();
        });

        // We unfortunately have to make a copy of each package to avoid borrow checker issues as check_dependencies
        // needs to borrow PackageRegistry from the dependency packages.
        // This would increase the amount of gas used, but this is a rare operation and it's rare to have many packages
        // in a single code object.
        registry.packages.for_each(|pack| {
            check_dependencies(code_object_addr, &pack);
        });
    }

    fun check_upgradability(

        assert!(old_pack.upgrade_policy.policy < upgrade_policy_immutable().policy,

        assert!(can_change_upgrade_policy_to(old_pack.upgrade_policy, new_pack.upgrade_policy),

        let old_modules = get_module_names(old_pack);

        old_modules.for_each_ref(|old_module| {
            assert!(
                vector::contains(new_modules, old_module),
                EMODULE_MISSING
            );
        });
    }

    /// Checks whether a new package with given names can co-exist with old package.
    fun check_coexistence(old_pack: &PackageMetadata, new_modules: &vector<String>) {
        // The modules introduced by each package must not overlap with `names`.
        old_pack.modules.for_each_ref(|old_mod| {
            let old_mod: &ModuleMetadata = old_mod;
            let j = 0;
            while (j < vector::length(new_modules)) {
                let name = vector::borrow(new_modules, j);
                assert!(&old_mod.name != name, error::already_exists(EMODULE_NAME_CLASH));
                j += 1;
            };
        });
    }
