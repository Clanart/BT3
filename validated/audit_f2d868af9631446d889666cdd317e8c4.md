## Analysis

The Guardian/report's core broken invariant: **a completion flag is set optimistically before the side-effect it represents is confirmed to succeed, and the corresponding message is not designed to be resent if it fails on the far side** — so if the message bounces (fails validation on delivery), the local state is permanently wrong and unrecoverable.

The exact local analog exists in `ExtrinsicIntents._cancelFromDest`: [1](#0-0) 

### Title
Optimistic `_filled` finalization before cross-chain RefundEscrow delivery can permanently brick escrowed funds — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` writes `_filled[commitment] = order.user` **before** dispatching the `RefundEscrow` POST request to the source chain. If that message ever fails to be processed by the source-chain gateway's `onAccept` (e.g., its authentication check reverts), the destination-chain order is permanently marked "cancelled/finalized," yet the escrow on the source chain is never actually released — with no compensating retry path, exactly mirroring the multisig `try_execute`/bounce issue where `executed? = true` is set before the receiving contract confirms success.

### Finding Description
`_cancelFromDest` sets the finalize flag first, then builds and dispatches the `RefundEscrow` message: [2](#0-1) 

Delivery on the source chain runs through `onAccept`, which first authenticates the sender against the currently-registered gateway instance: [3](#0-2) [4](#0-3) 

`_instance` is resolved dynamically from the `_instances` mapping, which can be updated at any time via a `NewDeployment` request that is only distinguishable by ordinary governance/operational flow (`_addDeployment`), independent of any in-flight message: [5](#0-4) [6](#0-5) 

If the registered instance for `order.source` changes (e.g., a gateway migration/redeployment) between the time `_cancelFromDest` is called and the time the relayer submits proof for the `RefundEscrow` message, `_authenticate` reverts with `Unauthorized()` on delivery. `EvmHost.dispatchIncoming` treats this as a soft failure and deletes only the *request receipt* on the receiving (source) host so the message "can be retried": [7](#0-6) 

But that receipt deletion has no bearing on the already-committed `_filled[commitment]` state on the *destination* chain — it was set unconditionally in the same transaction that dispatched the message, before any confirmation of delivery. Because `_authenticate` keys off the *current* `_instances` mapping rather than a value pinned at cancel time, the failure is not transient — every retry of the same `RefundEscrow` message will keep failing `_authenticate` post-migration, since the module binding permanently changed. The escrowed tokens (`_orders[commitment][token]`) are never released via `_withdraw`, since that only runs after `_authenticate` succeeds: [8](#0-7) [9](#0-8) 

Critically, there is no fallback path: the alternate cancellation route, `_cancelFromSource`, is now permanently closed too, because its `onGetResponse` checks the destination chain's `_filled` storage slot via proof and reverts if it is non-empty: [10](#0-9) 

This is precisely the reported bug class: a message that "carries" the fund-moving intent is dispatched with a finalize flag already committed, the receiving side can reject it for legitimate reasons (parameter/instance change, exactly analogous to the multisig threshold change in the original report), and there is no bounce-handling or retry-with-corrected-state mechanism — only an unconditional, one-way commit.

### Impact Explanation
The corrupted value is `_filled[commitment]` on the destination chain, set to a non-zero (finalized) value while the corresponding `_orders[commitment][token]` escrow on the source chain is never released. This is a direct loss/permanent lock of user funds — the escrowed input tokens become unwithdrawable through any code path in the contract, matching the bounty's "stealing or loss of funds" / "logic attacks" categories.

### Likelihood Explanation
No malicious peer, relayer, or prover is required — the only precondition is a normal, benign gateway-instance update (`NewDeployment`/re-registration) racing against an in-flight `RefundEscrow` message, which is a foreseeable operational event (chain migrations, gateway redeployments) rather than an attack. This mirrors the original report's own trigger condition (a legitimate multisig parameter change), which the task's method treats as a valid analog trigger, not a "malicious admin" exclusion.

### Recommendation
Do not finalize `_filled` until the cross-chain effect is confirmed successful, or bind `_authenticate` to the gateway instance recorded at cancellation time rather than the live mapping, and/or implement a retry-with-updated-binding mechanism so a bounced `RefundEscrow` can be resubmitted against the corrected instance address without requiring the destination-side state to already be irreversibly finalized. Alternatively, store the pending-refund state separately from the terminal `_filled` flag until `_withdraw` actually executes.

### Proof of Concept
1. User places a cross-chain order with `source = ChainA`, escrowing input tokens on `ChainA`.
2. Governance registers a new `IntentGateway` deployment on `ChainA` for legitimate reasons (contract upgrade requiring redeploy) via `NewDeployment`, updating `_instances[keccak256("ChainA")]` on `ChainB` (the destination) to the new address — but there exists an in-flight cancellation.
3. Before that update, user (or anyone post-deadline) calls `_cancelFromDest` on `ChainB`: `_filled[commitment]` is set to `order.user`, and a `RefundEscrow` POST is dispatched to `ChainA` addressed `to: <old ChainA gateway address>`.
4. The relayer proves this message on `ChainA` after the update took effect; `onAccept` -> `_authenticate` computes `_instance(order.source)` which now differs from `request.from` (the old gateway address embedded in the message body), reverting `Unauthorized()`.
5. `EvmHost.dispatchIncoming` deletes only the `ChainA`-side request receipt for retry; resubmission will always fail the same authentication check since the binding is permanently stale for this message.
6. `_filled[commitment]` on `ChainB` remains finalized forever; `_orders[commitment][token]` on `ChainA` remains escrowed forever; `_cancelFromSource` is now blocked by the `Filled()` check in `onGetResponse`. Funds are permanently locked.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
