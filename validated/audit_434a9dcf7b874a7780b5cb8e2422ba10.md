## Analysis

The GMX bug's broken invariant is: **a piece of state (an "asset" the account is claimed to hold) gets marked as trusted/present based on an assumed outcome, and only a narrow, incomplete check gates whether that assumption is corrected before it flows into a security-relevant action.**

The closest reachable analog in this GitHub Desktop codebase is in the AI-assisted merge/rebase/cherry-pick conflict resolution feature ("Copilot conflict resolution"). Desktop builds an AI prompt using content that is fully controlled by whoever authored the branch/PR being merged (an attacker-controlled GitHub object), and the only safety check performed on the AI's returned file content before it is written to disk and staged for commit is a narrow regex that checks for literal, unmodified conflict-marker syntax — not a structural verification that the returned content is a faithful merge of the two sides.

### Title
Copilot conflict resolution stages AI output built from attacker-controlled PR/commit content with only a conflict-marker regex as a safety check, allowing silent corruption of merge commits - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user merges/rebases/cherry-picks a branch and asks GitHub Desktop's Copilot integration to resolve conflicts, Desktop gathers conflict context — including the incoming side's commit messages and any linked pull-request title/body — from the repository being merged (attacker-controlled if the branch/fork originates from an untrusted contributor) and sends it to the model. The model's JSON response is validated for structural shape and for the literal absence of unmodified `<{7}`/`={7}` conflict-marker text, then the `resolvedContent` is written straight to disk and staged with `git add`, without any diff-level verification that the AI actually just merged the two conflicting hunks rather than inserting or altering unrelated content.
