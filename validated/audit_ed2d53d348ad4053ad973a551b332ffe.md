### Title
Missing `getRewardablePercentWAD()` call in `mWOMSVBaseRewarder._calExpireForfeit()` causes forfeit-on-early-claim to always be zero - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit()` fails to call `mWomSV.getRewardablePercentWAD(_account)` to determine what fraction of a user's pending reward is actually vested/rewardable. Instead it sets `rewardableAmount = _amount` directly, which is functionally the same class of bug as the reported `perp_withdraw.rs` issue: a value that should come from one of two distinct sources (here, a computed vesting percentage vs. the raw amount) is instead hard-set to the "unrestricted" value, making the restrictive check permanently dead code and defeating the protocol's intended penalty mechanism.

### Finding Description
The sibling contract `rewards/vlMGPBaseRewarder.sol` implements `_calExpireForfeit` correctly: [1](#0-0) 

It fetches `vlMGP.getRewardablePercentWAD(_account)` and applies it to `_amount` to determine how much of a user's accrued reward is actually claimable now vs. forfeited (queued back into the pool for other stakers via `_queueNewRewardsWithoutTransfer`).

In `rewards/mWOMSVBaseRewarder.sol`, the analogous function is: [2](#0-1) 

Here `rewardableAmount` is initialized to `_amount` itself (instead of calling `mWOMSV.getRewardablePercentWAD(_account)`, which is a real, implemented function on `mWomSV.sol`): [3](#0-2) 

Because `rewardableAmount == _amount` always, the subsequent `forfeitAmount = _amount - rewardableAmount` is always `0`, and the `if (rewardableAmount > _amount) revert InvalidRewardableAmount();` sanity check can never trigger. This mirrors the reported bug pattern exactly: a check/computation that should differentiate between two distinct states (locked vs. in cool-down / vested vs. not) instead always resolves to the non-restrictive branch, making the intended restriction permanently ineffective.

This dead logic is exercised in `_sendReward`, which computes `forfeitAmount` and forwards any non-zero forfeit back into the reward pool for the benefit of remaining stakers: [4](#0-3) 

### Impact Explanation
The `mWomSV` early-unlock/cool-down forfeit mechanism is designed so that users who claim rewards while their `mWomSV` lock is not fully vested (i.e., in cool-down) forfeit part of their pending reward, which is redistributed pro-rata to all remaining stakers via `_queueNewRewardsWithoutTransfer` (`rewards/mWOMSVBaseRewarder.sol:330-346`). With this bug, `forfeitAmount` is always `0`, so:
- Users who should be penalized for claiming during cool-down instead receive 100% of their accrued reward every time, via the normal, unprivileged `getReward`/`getRewards` claim path (`rewards/mWOMSVBaseRewarder.sol:233-261`).
- The forfeited yield that should be permanently redistributed to other `mWomSV` stakers never materializes, permanently reducing/freezing the yield that honest, fully-locked stakers are entitled to receive.

This is a direct, unprivileged-wallet-reachable loss of unclaimed yield for other stakers in the pool, since every claim silently skips the intended forfeiture and redistribution step.

### Likelihood Explanation
High — this triggers on every single `getReward`/`getRewards` call for any account with `mWomSV` in cool-down; no special conditions, privileged roles, or governance action are required. Any unprivileged user with mWOM locked in `mWomSV` (partially in cool-down) claiming their `mWOMSVBaseRewarder` rewards is affected on every claim.

### Recommendation
Replace the stubbed logic in `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`, computing the rewardable percentage from the actual lock state:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }
    return forfeitAmount;
}
```

### Proof of Concept
1. User A locks mWOM into `mWomSV` and accrues `mWOMSVBaseRewarder` reward token balance over time (`_earned` accrues via `rewardPerToken`).
2. User A calls `mWomSV.startUnlock()` to move part of their stake into cool-down (`wombat/mWomSV.sol:247-277`); per `getRewardablePercentWAD`, this amount should only be partially rewardable until `endTime` fully elapses.
3. Before cool-down ends, MasterMagpie (on behalf of User A, an ordinary unprivileged transaction) calls `getReward`/`getRewards` on `mWOMSVBaseRewarder`, which calls `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`.
4. Because `_calExpireForfeit` sets `rewardableAmount = _amount`, `forfeitAmount` returns `0` regardless of the cool-down state, so User A receives their full pending reward immediately with `toSend == userRewards[...]` and no forfeit is queued back via `_queueNewRewardsWithoutTransfer` (`rewards/mWOMSVBaseRewarder.sol:362-376`).
5. Remaining `mWomSV` stakers permanently lose out on the forfeited yield they should have received, verified by comparing against the correctly implemented `vlMGPBaseRewarder._calExpireForfeit` (`rewards/vlMGPBaseRewarder.sol:386-400`), which does apply `getRewardablePercentWAD`.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
