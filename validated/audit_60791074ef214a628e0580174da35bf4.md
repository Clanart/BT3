### Title
Cross-chain order cancellation refunds against stale `order.inputs` amounts instead of live escrow, causing revert/underflow that permanently locks the unfilled remainder - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The C4 report's broken invariant is: a validation check that is irrelevant to the specific requested operation is applied unconditionally, and its failure reverts the whole transaction — blocking a user's legitimate exit/refund path and leaving funds stuck. The local analog is in the Intent Gateway's shared withdrawal routine, `_withdraw`, in [1](#0-0) , which is invoked by both fill-settlement and cancel/refund flows.

### Finding Description
`_withdraw` decrements escrow using the `amount` field carried in the `WithdrawalRequest.tokens` array against the live escrow mapping `_orders[commitment][token]`: [2](#0-1) 

For a **same-chain** cancel, the caller correctly rebuilds the withdrawal body from the *current* escrow balance per token (`_orders[commitment][token]`), so partial fills are already reflected: [3](#0-2) 

But for **cross-chain** cancellation (both the source-side GET-proof route and the destination-side `RefundEscrow` route), the withdrawal body is built directly from the *original* `order.inputs` amounts, not the live escrowed balance: [4](#0-3) [5](#0-4) 

If escrow for a given input token has already been partially consumed (any mechanism that reduces `_orders[commitment][token]` below `order.inputs[i].amount` prior to cancellation), then when `_withdraw` executes:
- `escrowed = _orders[commitment][token]` may already be `0` for that token, tripping `revert UnknownOrder()` and aborting the whole batch withdrawal — including refund of any *other* input token in the same order that still has funds escrowed, or
- `escrowed - amount` underflows in checked Solidity math and reverts.

Either way, the entire cancellation reverts. This mirrors the AutoRange/AutoExit pattern exactly: a check is applied without regard to whether the specific requested operation (refund of whatever remains) actually needs it, and its failure blocks the user's only exit path.

The consequence differs from the C4 report in one important way that makes it more severe here: in `_cancelFromDest`, the contract **marks the order as settled before dispatching** the cross-chain refund message: [6](#0-5) 
Because `_filled[commitment]` is set synchronously on the destination chain regardless of whether the refund eventually lands on the source chain, `cancelOrder` cannot be called again for this commitment (it would revert with `Filled()`) once this path has been taken. If the corresponding `onAccept` call on the source chain then reverts inside `_withdraw` due to the stale-amount mismatch described above, there is no code path shown in this repo (unlike the explicit "store `meta` and allow resubmission" logic used for POST-request timeouts in `EvmHost.dispatchTimeOut`) that lets the user retry the settlement — the escrowed remainder can become permanently unrecoverable.

### Impact Explanation
This falls under "fund loss/lock" and "duplicate settlement" categories from the impact gate: escrowed user funds tied to a cross-chain order can be rendered permanently unwithdrawable through the ordinary, unprivileged `cancelOrder` entrypoint, with no admin/relayer/prover misbehavior required — the corrupted value is the `amount` field of `WithdrawalRequest.tokens`, which is populated from `order.inputs` (order-time snapshot) rather than the live `_orders[commitment][token]` escrow balance at cancellation time.

### Likelihood Explanation
Requires only that the escrow accounting for at least one input token diverges from `order.inputs[i].amount` before cancellation is attempted — I was not able to fully confirm within the available time whether cross-chain multi-input orders in this codebase support a fill path that partially reduces per-token escrow (analogous to same-chain partial fills), so I present this with that caveat rather than as a fully proven exploit chain. If such a partial-consumption path exists (or arises from any future feature/fee-adjustment touching `_orders[commitment][token]` for a subset of tokens), this bug is trivially and deterministically triggerable by any order owner calling `cancelOrder`.

### Recommendation
Build the `WithdrawalRequest.tokens` array for cross-chain cancel paths (`_cancelFromSource`, `_cancelFromDest`) from the *live* `_orders[commitment][token]` balances (as `_cancelSameChain` already does), rather than from `order.inputs`. Additionally, make `_withdraw` tolerant of tokens with `escrowed == 0` (skip rather than revert) so that a genuinely fully-consumed token in a multi-token order does not block refund of the remaining tokens — mirroring the correct fix recommended in the seed report ("skip rather than fail the whole operation when the specific check is not needed for the requested action").

### Proof of Concept
Not independently executable from indexed content alone — a full PoC requires confirming the exact call path that reduces `_orders[commitment][token]` for a subset of a cross-chain order's input tokens prior to cancellation (e.g., a partial-fill-capable cross-chain fill flow). Conceptually:
1. User places a cross-chain order with two input tokens, A and B, via `placeOrder`.
2. Some mechanism reduces escrow for token A to below `order.inputs[A].amount` (or to zero) while token B remains fully escrowed.
3. User (or anyone, post-deadline) calls `cancelOrder` from the destination chain; `_cancelFromDest` dispatches `RefundEscrow` built from the original `order.inputs`, and sets `_filled[commitment]` immediately.
4. On the source chain, `onAccept` → `_withdraw` reverts on token A (`UnknownOrder` or underflow), reverting the whole refund; token B's still-escrowed funds are not refunded either.
5. Because `_filled[commitment]` was already set in step 3, `cancelOrder` can never be called again for this commitment, and no retry path is shown in the accessible code — the remaining escrow for both tokens is stuck.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
