## Title
Unprivileged `DepositDelegatorRewards` lets any signer permanently block a vote account's withdrawer from closing the account - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote program's `deposit_delegator_rewards` instruction lets *any* account that can sign a lamport transfer — not the vote account's `authorized_withdrawer` — deposit an arbitrary amount into a vote account and unilaterally increase `pending_delegator_rewards` on that vote account's state. [1](#0-0)  The `withdraw` instruction then treats `pending_delegator_rewards` as an untouchable reserve: it refuses to close the account at all while it is nonzero, and it restricts partial withdrawals to `lamports - pending_delegator_rewards - rent_exempt_minimum`. [2](#0-1)  This is the same bug class as the reported `TradingVault.userLastDepositTime`: a third party performs a "deposit" on behalf of an account and thereby forces a lock/restriction on that account's owner without their consent.

### Finding Description
`deposit_delegator_rewards` only requires the *source* (depositor) to be a signer, and only requires the vote account to be deserializable as V4 — it never checks or requires a signature from the vote account's `authorized_withdrawer`: [3](#0-2) 

It then executes a System Program CPI transfer from the depositor into the vote account and calls `add_pending_delegator_rewards`, which unconditionally increments the vote account's `pending_delegator_rewards` field: [4](#0-3) [5](#0-4) 

`pending_delegator_rewards` is enforced as a hard reserve inside `withdraw`, gated only on the withdrawer's signature — not on who created the reserve: [6](#0-5) 

Test code confirms the invariant: with `pending_delegator_rewards > 0` a full close (`Withdraw` for the entire balance) always fails with `InstructionError::InsufficientFunds`, regardless of who controls the account: [7](#0-6) 

The only path that reduces `pending_delegator_rewards` is the epoch block-reward distribution logic in `calculate_block_reward`, and that logic only pays out (and, implicitly, only reduces the pending amount) proportional to `total_active_stake` for that vote account during an Alpenglow reward epoch: [8](#0-7) 
If a vote account has no delegated/active stake (`total_active_stake == 0`), `calculate_block_reward` returns `0`, meaning no portion of `pending_delegator_rewards` is paid out or cleared for that account in that epoch. There is no permissionless "cancel deposit" or "return dust deposit" instruction visible in the vote program that lets the withdrawer purge an attacker-imposed `pending_delegator_rewards` balance outside of this stake-proportional distribution mechanism.

### Impact Explanation
Any unprivileged account (a normal signer with even 1 lamport) can call `DepositDelegatorRewards` against a vote account it does not control, depositing a trivial amount and incrementing `pending_delegator_rewards` by that amount. Once `pending_delegator_rewards > 0`, the account's actual `authorized_withdrawer`:
- Cannot fully close/withdraw the vote account (`InsufficientFunds` unconditionally when `remaining_balance == 0` and `pending_delegator_rewards > 0`).
- Has a reduced maximum withdrawable balance (must always keep `rent_exempt_minimum + pending_delegator_rewards` locked in the account).

For a vote account with zero or negligible delegated stake, this lock is effectively permanent, since the only defined decrement path (epoch block-reward distribution) pays nothing when `total_active_stake == 0`. This mirrors the report's finding exactly: an uninvolved third party imposes a state change on a victim account that restricts the victim's own withdrawal rights, without the victim's consent, causing a denial-of-service / fund-lock condition.

### Likelihood Explanation
The attack requires no privileged keys, no admin/authority role, and no cooperation from the target — only a signer capable of transferring lamports (even 1 lamport) and knowledge of the target vote account's pubkey, which is public. It is a single, permissionless transaction (`DepositDelegatorRewards`) with a public account address as the only precondition, making it trivially and repeatably exploitable against any vote account, particularly newly created or low-stake ones.

### Recommendation
- Require that the `pending_delegator_rewards` reserve be attributable/refundable to the depositor rather than an unconditional lock imposed on the withdrawer, or
- Require the vote account's `authorized_withdrawer` to co-sign/opt in to accept delegator-reward deposits, or
- Add an explicit permissionless mechanism for the withdrawer to reclaim/zero out `pending_delegator_rewards` that was never matched by actual stake-proportional rewards (e.g., refund logic tied to `total_active_stake == 0`), so a depositor cannot permanently encumber an unrelated account's withdrawal rights.

### Proof of Concept
1. Identify any vote account `V` (public pubkey) with `authorized_withdrawer = W`, with little or no delegated stake.
2. As attacker `A` (any funded keypair, no relation to `V`/`W`), submit a `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` instruction with `A` as source/signer and `V` as the vote account.
3. This CPIs a 1-lamport System transfer from `A` to `V` and sets `pending_delegator_rewards = 1` on `V`'s state via `add_pending_delegator_rewards`. [4](#0-3) 
4. `W` (the legitimate withdrawer) attempts `VoteInstruction::Withdraw(full_balance)` to close `V`; this fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0`, as shown by the analogous test `test_withdraw_pending_delegator_rewards`. [7](#0-6) 
5. If `V` has no active delegated stake, no epoch reward distribution will ever reduce `pending_delegator_rewards` back to zero (per `calculate_block_reward`'s `total_active_stake == 0 => 0` branch), leaving `W` permanently unable to fully withdraw/close the account with a single 1-lamport griefing transaction from an unrelated attacker.

            Ok(VoteStateHandler::new_v4(*vote_state_v4))

            Err(InstructionError::InvalidAccountData)
        }

/// Withdraw funds from the vote account
pub fn withdraw<S: std::hash::BuildHasher>(
    instruction_context: &InstructionContext,
    vote_account_index: IndexOfAccount,
    target_version: VoteStateTargetVersion,
    lamports: u64,
    to_account_index: IndexOfAccount,
    signers: &HashSet<Pubkey, S>,
    rent_sysvar: &Rent,
    clock: &Clock,
) -> Result<(), InstructionError> {
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;
    let vote_state = get_vote_state_handler_checked(&vote_account, target_version)?;

    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let remaining_balance = vote_account
        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }
