### Title
Escrow debited after external transfer in `withdraw()` (CEI violation) — Tron IntentGateway diverges from the patched mainline contract - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron-chain deployment of the Intent Gateway contains its own copy of the escrow-release logic in `withdraw()`, and unlike the mainline EVM contract's `IntentsBase._withdraw()` — which was explicitly hardened against reentrancy (see `IntrinsicIntentsReentrancyTest.sol`) — this Tron variant still performs the token/native transfer **before** decrementing the escrow accounting. This is the exact bug class described in the external report: a "double transfer" made possible by failing to follow checks-effects-interactions around an external asset transfer.

### Finding Description
In the mainline contract, escrow is decremented before any external call: [1](#0-0) 

The Tron variant does the opposite — it checks only that escrow is non-zero, performs the external call, and only afterwards subtracts the amount: [2](#0-1) 

Specifically:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    ...
}
_orders[body.commitment][token] -= amount;   // <-- effect applied AFTER the external interaction
```
`_filled[body.commitment]` is set once at the top of `withdraw()` [3](#0-2)  which blocks a second *top-level* call from re-entering the same public entrypoint (`onAccept`/cancel) if that entrypoint re-checks `_filled` on re-entry. But within the loop body itself, the per-token escrow value used by the `if (_orders[...] == 0)` guard is stale at the moment of the external call — the balance hasn't been reduced yet. If the beneficiary is a contract (native-ETH beneficiary, or an ERC-20 with a transfer-hook/callback), its `receive()`/callback can re-enter before its own `_orders[...] -= amount` line executes. This is structurally identical to the audited bidAsset `_bid` bug: a reentrant call sees state that has not yet reflected the in-flight transfer.

This is a real code drift, not a hypothetical: the mainline contract required a dedicated CEI fix and a full reentrancy regression-test suite (`IntrinsicIntentsReentrancyTest.sol`) to close this exact class of bug, and that fix was never carried over into the Tron contract, which still uses the pre-fix ordering.

### Impact Explanation
If exploitable, this allows an attacker acting as `beneficiary` (or `msg.sender` on a fill/cancel path that routes to `withdraw`) to receive the same escrowed input tokens or transaction fees more than once from a single order's escrow before the accounting catches up, i.e., unauthorized double disbursement of bridge-custodied intent escrow — directly matching the bounty's "stealing or loss of funds" / "double-claim/double-settlement" categories.

### Likelihood Explanation
Medium. Exploitability is gated on whether the specific caller of `withdraw()` (`onAccept` for `RedeemEscrow`/`RefundEscrow`, or the local `cancelOrder`) re-validates `_filled[commitment]` on the way back in during reentrancy, and on the destination token supporting a callback (native ETH beneficiary contract always qualifies; ERC-20 needs a hook). Given the raw low-level `token.call(...transfer...)` pattern used throughout this file (rather than `SafeERC20.safeTransfer`), and that native-ETH beneficiaries are fully attacker-controlled contracts, the native-token path is directly reachable without any special token choice. I was not able to fully trace every caller path (`onAccept`, cancel handlers) within the remaining tool budget to confirm whether an outer `_filled` re-check is present on every re-entry route, so likelihood should be treated as unconfirmed-but-plausible pending that trace.

### Recommendation
Port the CEI fix already applied to `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw()` into `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`: decrement `_orders[body.commitment][token]` **before** performing the native call or ERC-20 transfer, mirroring the pattern at `evm/src/apps/intentsv2/IntentsBase.sol:403-409`. Also add a `nonReentrant` guard consistent with the mainline `fillOrder` function, and replace raw `token.call(abi.encodeWithSelector(IERC20.transfer...))` with OpenZeppelin `SafeERC20.safeTransfer` for consistency with the mainline contract.

### Proof of Concept
Conceptual PoC (native-ETH path, requires confirming the exact external caller of `withdraw()` in this file, e.g. `onAccept` handling `RedeemEscrow`/`RefundEscrow`):
1. Attacker places/participates in an order whose beneficiary is set to an attacker-controlled contract, with a native-ETH output escrowed for the order commitment.
2. The settlement path invokes `withdraw(body, isRefund)` with `body.tokens` containing the native-ETH entry.
3. `_orders[commitment][address(0)] == 0` check passes (escrow still fully funded).
4. `beneficiary.call{value: amount}("")` transfers ETH to the attacker contract, invoking its `receive()`.
5. Before line `_orders[body.commitment][token] -= amount;` executes, the attacker's `receive()` re-enters the same settlement path for the same `commitment` (if the calling entrypoint does not re-check `_filled` before invoking `withdraw()` again, or if a duplicate token entry / concurrent code path allows a second pass over the still-undecremented escrow).
6. A second `beneficiary.call{value: amount}("")` fires for the same `amount` before either decrement lands, disbursing escrow twice.

Because I could not exhaustively trace every external caller of `withdraw()` in this Tron contract within the remaining budget, confirming the full end-to-end reentrant call graph (which public function re-enters and whether it re-checks `_filled`) should be the first verification step before remediation.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {

                if (!success) revert TransferFailed();

            }
        }
