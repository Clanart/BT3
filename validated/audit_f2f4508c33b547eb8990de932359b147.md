### Title
Online (per-user) session storage keys sessions solely by global `shopify_user_id`, causing cross-shop session/access-token confusion when a user is staff on multiple installed shops - ([File: lib/shopify_app/session/user_session_storage.rb])

### Summary
### Finding Description
The Arbitrum finding shows that a timer-inheritance check validated only a shared, non-unique identifier (`mutualId`) instead of the precise, one-to-one identifier of the specific entity (`edgeId`/`claimId`), letting an edge from an unrelated ("dishonest") tree inherit state that should have been scoped to one specific edge.

The shopify_app analog is the storage/lookup of **online (per-user) sessions**. `ShopifyApp::UserSessionStorage.store` keys the persisted record purely by the globally-unique `shopify_user_id`, discarding shop context as part of the identity key: [1](#0-0) [2](#0-1) 

`retrieve_by_shopify_user_id` performs the read the same way — by `shopify_user_id` alone, with no shop parameter: [3](#0-2) 

`ShopifyApp::SessionRepository#load_session`, which is invoked on every authenticated request (via `EnsureHasSession`/`TokenExchange`), strips the shop portion out of the composite session id and resolves the session using only the trailing user-id segment: [4](#0-3) 

The generated `User` migration also enforces uniqueness only on `shopify_user_id`, not on `(shopify_domain, shopify_user_id)`: [5](#0-4) 

Consequence: if the same physical Shopify account (same global `shopify_user_id`, e.g. an agency/partner staff member, or a Shopify Plus/organization user) is authorized on two different shops that both have this app installed, the second shop's OAuth/token-exchange `store` call for that user overwrites the single `User` row's `shopify_domain` and `shopify_token` — the row that used to hold Shop A's access token now holds Shop B's `shopify_domain`/`shopify_token`, exactly as an edge inheriting the wrong tree's accumulated timer in the original report (a shared, non-unique key is trusted to stand in for a specific, scoped entity).

### Impact Explanation
When a subsequent request from Shop A's merchant arrives with a valid, cryptographically-verified session token (id_token) for Shop A, `load_session` resolves the stored `User` row purely by `shopify_user_id` and returns whatever `shopify_domain`/`shopify_token` currently occupies that row — which may now be Shop B's. In `ShopifyApp::TokenExchange#activate_shopify_session`, this session is used directly:
- `authenticated_shopify_domain_from_token` returns `current_shopify_session&.shop`, i.e. Shop B's domain, even though the id_token was issued for Shop A.
- `reject_mismatched_requested_shopify_domain` only rejects the request if a `requested_shopify_domain` (an explicit `shop` param) is present and disagrees; for many authenticated XHR/embedded requests that rely purely on the `Authorization: Bearer <id_token>` header (no `shop` query param), this guard is skipped. [6](#0-5) [7](#0-6) 

- `ShopifyAPI::Context.activate_session(current_shopify_session)` then activates Shop B's access token for a request that was actually verified/authenticated for Shop A. Any Admin API calls made under `current_shopify_session` in the controller action will read/write Shop B's data using Shop B's access token, on behalf of a request context believed to be Shop A. This is a cross-shop/cross-user session and access-token confusion (Shop A ends up transparently operating with Shop B's store data/token, or vice versa depending on which OAuth ran most recently).

### Likelihood Explanation
Requires that the same underlying Shopify account (global `shopify_user_id`) be a staff/collaborator user on two different shops that both have the same app installed and configured for online/per-user tokens — a realistic scenario for development partners, agencies, and organizations managing multiple stores, none of which requires any secret leakage or privileged access. Once both shops have completed OAuth/token exchange for that shared user id, the collision is silent and persists until the next OAuth for either shop.

### Recommendation
Scope online-session storage and lookup by the tuple `(shopify_domain, shopify_user_id)` rather than `shopify_user_id` alone: change `find_or_initialize_by`/`find_by`/`destroy_by` in `UserSessionStorage` (and its deprecated `WithScopes` counterpart) to include `shopify_domain`, add a composite unique index on `(shopify_domain, shopify_user_id)` in the generated migration, and require the shop domain to be threaded through `SessionRepository.retrieve_user_session_by_shopify_user_id`/`load_session` so the record retrieved is provably scoped to the shop verified by the id token, not just to the numeric user id. Additionally, `reject_mismatched_requested_shopify_domain` should validate the loaded session's shop against the id-token's verified shop even in the absence of an explicit `shop` query parameter.

### Proof of Concept
1. Configure the app with online tokens (`user_session_repository` using the generated `User`/`UserSessionStorage`).
2. Have the same Shopify staff account (global id `U`) complete OAuth on Shop A → `User` row created: `{shopify_user_id: U, shopify_domain: "shop-a.myshopify.com", shopify_token: "token-A"}`.
3. Have the same account complete OAuth on Shop B (app also installed there) → `UserSessionStorage.store` executes `find_or_initialize_by(shopify_user_id: U)`, which finds the same row and overwrites it to `{shopify_domain: "shop-b.myshopify.com", shopify_token: "token-B"}`.
4. Shop A's merchant now sends an authenticated embedded request with a valid id_token for Shop A but without an explicit `shop` query parameter (common for internal XHR calls under App Bridge).
5. `SessionRepository.load_session` derives the trailing user-id segment and calls `retrieve_user_session_by_shopify_user_id(U)`, returning the row now containing Shop B's domain/token.
6. `TokenExchange#activate_shopify_session` skips the mismatch check (`requested_shopify_domain` is blank) and activates `ShopifyAPI::Context` with Shop B's access token for a request that the merchant believes is scoped to Shop A — confirming cross-shop session/token confusion.
