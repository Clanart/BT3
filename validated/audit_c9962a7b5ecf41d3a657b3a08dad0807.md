## Analog Found: Inconsistent State on Failed Fee Refund in Timeout Handler

### Title
Failed `on_request_timeout` refund via `?` leaves request commitment permanently deleted with fee locked and unrecoverable - ([File: modules/ismp/core/src/handlers/timeout.rs])

### Summary
The `handle` function for `TimeoutMessage` in `modules/ismp/core/src/handlers/timeout.rs` mirrors the exact "inconsistent stack" bug class from the external report: an irreversible state mutation (`delete_request_commitment`) is performed, followed by an `?`-propagated fallible call (`host.on_request_timeout`) whose failure is not rolled back, unlike the sibling failure branch which does perform rollback.

### Finding Description
In both the `TimeoutMessage::Post` and `TimeoutMessage::Get` arms, the handler deletes the request commitment before invoking the module callback and before crediting the refund: [1](#0-0) 

The relevant control flow is:
1. `let meta = host.delete_request_commitment(&request)?;` — irreversibly removes the on-chain commitment (and receipt, for Post).
2. `let res = cb.on_timeout(request.clone())...` — invokes the module callback, captured as `Result`, not `?`-propagated.
3. `if res.is_ok() { host.on_request_timeout(&request, meta)?; } else { host.store_request_commitment(&request, meta)?; ... }`

Only the `else` (module callback failure) branch restores the deleted commitment. The `if res.is_ok()` branch calls `host.on_request_timeout(&request, meta)?` with the `?` operator — if this call fails, the function returns early via `anyhow::Error` without restoring the commitment that was deleted in step 1.

`on_request_timeout` in the pallet-ismp `IsmpHost` implementation performs the actual fee refund transfer: [2](#0-1) 

`T::Currency::transfer(...)` from `RELAYER_FEE_ACCOUNT` to `leaf_meta.fee.payer` can fail (e.g., existential-deposit related failures when crediting a reaped/non-existent payer account with an amount below ED, or other `Currency` trait failure modes). Because this failure occurs *after* the commitment has already been deleted, and because the `?` short-circuits before any cleanup code runs, the escrowed fee held in `RELAYER_FEE_ACCOUNT` becomes permanently stuck: the commitment record needed to retry the timeout no longer exists, so any resubmission of the timeout is rejected with `Error::UnknownRequest` at the "Re-check the commitment right before dispatch" guard just above.

This is a direct analog to the reported issue: use of `?` after an irreversible "begin"-like step (`delete_request_commitment`, analogous to `handler.begin_inter_transaction`) skips the cleanup/rollback that the parallel failure path performs, leaving inconsistent state.

### Impact Explanation
The escrowed relayer fee for the timed-out request becomes permanently locked in `RELAYER_FEE_ACCOUNT` with no code path to retrieve it — the payer cannot be refunded (the failing transfer means they never receive it), and the request cannot be resubmitted for timeout processing (commitment is gone, causing `UnknownRequest`). This is a direct, permanent loss of user funds triggered by an ordinary transfer failure during the success path of timeout settlement, not requiring any malicious relayer, prover, or admin action — any user submitting a legitimately timed-out request that happens to trigger a `Currency::transfer` failure (e.g., their account has been reaped/has zero balance and the refund amount is below existential deposit) suffers permanent fund loss.

### Likelihood Explanation
The trigger condition (payer account no longer existing/below ED at refund time) is plausible in production: users can transfer away or spend down their balance between dispatching a request and its eventual timeout, especially given `Preservation::Expendable` on the *source* side allows `RELAYER_FEE_ACCOUNT` to be drained below ED, but the *destination* (payer) account creation still depends on runtime `ExistentialDeposit` configuration. No privileged actor is required — this is triggerable by ordinary account activity of the requester themselves or simply an insufficiently funded destination account.

### Recommendation
Do not use `?` for `host.on_request_timeout(&request, meta)` inside the success branch. Instead, handle the `Result` explicitly: if it fails, restore the commitment (and receipt/signer for Post) exactly as the `else` branch does, so the timeout can be retried, or otherwise defer/queue the fee for manual recovery instead of silently locking it. Apply the same fix symmetrically to both the `Post` and `Get` arms of `modules/ismp/core/src/handlers/timeout.rs`.

### Proof of Concept
1. Dispatch a `PostRequest`/`GetRequest` with a non-zero relayer fee, escrowed to `RELAYER_FEE_ACCOUNT` as shown in `test_dispatch_fees_and_refunds`: [3](#0-2) 
2. Ensure the request's `payer` account becomes ineligible to receive the refund transfer (e.g., reap the account so its balance is 0 and the refunded fee amount is below the runtime's `ExistentialDeposit`, causing `T::Currency::transfer` in `on_request_timeout` to return an `Err`).
3. Let the request time out and submit a valid `TimeoutMessage`; the handler in `handlers/timeout.rs` reaches `delete_request_commitment` (commitment now gone) and the module callback succeeds (`res.is_ok()`).
4. `host.on_request_timeout(&request, meta)?` fails and the whole `handle` call returns `Err` — but the commitment was already deleted with no rollback.
5. Resubmitting the same timeout message now fails with `Error::UnknownRequest` at the pre-dispatch guard, confirming the fee is permanently unrecoverable in `RELAYER_FEE_ACCOUNT`.

	fn on_request_timeout(&self, _req: &Request, meta: Vec<u8>) -> Result<(), Error> {
		let leaf_meta = RequestMetadata::<T>::decode(&mut &*meta)
			.map_err(|_| Error::Custom("Failed to decode leaf metadata".to_string()))?;
		if leaf_meta.fee.fee > Zero::zero() {
			T::Currency::transfer(
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				&leaf_meta.fee.payer,
				leaf_meta.fee.fee,
				Preservation::Expendable,
			)
			.map_err(|err| Error::Custom(format!("Failed to refund relayer fee: {err:?}")))?;
		}
		Ok(())
	}
