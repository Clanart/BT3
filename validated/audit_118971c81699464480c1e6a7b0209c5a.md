### Title
Untrusted `ReceivedOutput::read` bytes bypass scanner-derived ownership and outpoint validity - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes the private `offset`, `output`, and `outpoint` fields directly, without requiring that the output was produced by `Scanner::scan_transaction` or that the referenced UTXO exists on-chain. [1](#0-0) [2](#0-1) 

### Finding Description
`Scanner::scan_transaction` normally establishes the important invariant that a received output’s `script_pubkey` belongs to the wallet key under a registered offset and that its outpoint names a transaction output actually present in the scanned transaction. [3](#0-2)  `ReceivedOutput::read` bypasses that construction path and trusts all three serialized fields as authoritative. [4](#0-3)  Consequently, attacker-controlled bytes can describe a wallet-looking script and value while naming a nonexistent or unrelated outpoint. [1](#0-0) 

`SignableTransaction::new` subsequently treats each `ReceivedOutput.output` as the previous transaction output, copies `ReceivedOutput.outpoint` into a transaction input, and counts `output.value` as available funds. [5](#0-4) [6](#0-5)  The later `multisig` check only proves that the claimed `script_pubkey` is consistent with the selected key offset; it does not prove that the claimed outpoint is an existing unspent output. [7](#0-6) 

### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` bytes can cause the wallet to report or accept funds that cannot actually be spent. [8](#0-7)  If the forged object uses one of the wallet’s registered scripts, including the base key with `offset = 0`, the offset-to-script consistency check succeeds even when `outpoint` references a nonexistent transaction. [9](#0-8) [10](#0-9)  The resulting transaction can be fully assembled and signed, yet Bitcoin consensus will reject it because its input does not reference a valid UTXO. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
The issue requires an attacker to influence serialized `ReceivedOutput` data consumed by wallet logic, but that is the stated untrusted-byte boundary for this API. [2](#0-1)  No cryptographic break is required because the attacker only has to copy a legitimate wallet `script_pubkey`, choose a nonzero value, and invent an outpoint. [1](#0-0)  The concrete result is an unspendable deposit record or invalid spend attempt rather than direct key disclosure. [5](#0-4) [7](#0-6) 

### Recommendation
Do not expose `ReceivedOutput::read` as a trust-boundary constructor for unauthenticated data. [2](#0-1)  Prefer re-scanning the referenced transaction or UTXO and constructing `ReceivedOutput` only through `Scanner::scan_transaction`, which binds the script and outpoint to observed chain data. [3](#0-2)  If deserialization remains supported, add an authenticated/authenticity-preserving wrapper or a constructor that takes the wallet key and verifies `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`, while still treating the outpoint as unverified until confirmed against the chain. [13](#0-12) [7](#0-6) 

### Proof of Concept
The attacker needs the wallet base key’s normal P2TR script and can then serialize a fake deposit using `offset = 0`:

```rust
// networks/bitcoin/src/wallet/mod.rs shape; field values are encoded as
// ReceivedOutput::write emits them.
let wallet_script = p2tr_script_buf(wallet_base_key).unwrap();

let forged = ReceivedOutput {
    // Cannot be constructed directly outside the module because the fields are private;
    // encode these fields as bytes instead:
    offset: Scalar::ZERO,
    output: TxOut {
        value: Amount::from_sat(100_000),
        script_pubkey: wallet_script,
    },
    outpoint: OutPoint {
        txid: nonexistent_or_unrelated_txid,
        vout: 0,
    },
};

let encoded = forged.serialize();
let decoded = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(decoded.value(), 100_000);
```

`ReceivedOutput::read` accepts this object because it only decodes the scalar, `TxOut`, and `OutPoint`. [4](#0-3)  Passing it to `SignableTransaction::new` records the fake `outpoint` as a spend input and treats the forged value as available input value. [5](#0-4)  Because the forged script legitimately matches the wallet key at offset zero, `SignableTransaction::multisig` accepts the input and creates signing machines for it. [14](#0-13)  Completion writes valid-looking Schnorr witnesses, but the transaction remains consensus-invalid if the claimed outpoint was never created or is already spent. [15](#0-14)
