### Title
Untrusted `ReceivedOutput` can bind an arbitrary outpoint to a forged spendable output - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an independently supplied `offset`, `TxOut`, and `OutPoint` without validating that the referenced UTXO exists or that its actual script/value match the supplied `TxOut`. Downstream transaction construction treats the deserialized output as spendable and can cause threshold signing of an invalid Bitcoin transaction.

### Finding Description
`ReceivedOutput::read` deserializes all three security-critical fields from the same untrusted byte stream and returns the object without checking their relationship: the scalar offset, claimed previous output, and claimed outpoint. [1](#0-0)  `SignableTransaction::new` then copies the claimed outpoint into the transaction input while storing the separately supplied `TxOut` as the committed prevout. [2](#0-1) [3](#0-2) 

When signing is initialized, the implementation checks only that the claimed `script_pubkey` equals the threshold key after applying the supplied offset; it does not check that the outpoint resolves to that exact UTXO. [4](#0-3)  The resulting FROST machines sign Taproot sighashes using `Prevouts::All`, so the forged value and script are incorporated into the signed transaction despite the outpoint potentially referring to a different or nonexistent output. [5](#0-4) 

### Impact Explanation
An unprivileged party who can supply serialized `ReceivedOutput` bytes can cause an output to be represented as spendable when it is not. If that representation reaches the Bitcoin transaction-signing path, the threshold participants can be induced to sign a transaction spending a nonexistent UTXO, or a UTXO whose real script/value differ from those committed through `Prevouts::All`. Bitcoin consensus will reject the transaction, producing reported funds or scheduled spends that are not actually spendable and consuming threshold-signing resources.

### Likelihood Explanation
The only prerequisite is the ability to feed attacker-controlled bytes to the public `ReceivedOutput::read` API and have the result used by `SignableTransaction::new`. No private key, validator privilege, malformed curve encoding, or cooperative signer is required. A crafted input can use a legitimate Serai-controlled Taproot script, so the existing script check still passes while the associated outpoint is invalid.

### Recommendation
Do not expose `ReceivedOutput::read` as a constructor for untrusted input. Prefer obtaining `ReceivedOutput` exclusively from `Scanner::scan_transaction`, which establishes the outpoint, observed `TxOut`, and registered offset from the same confirmed transaction. [6](#0-5)  If deserialization remains necessary, require authenticated storage or validate the outpoint against confirmed chain state before calling `SignableTransaction::new`, ensuring the resolved UTXO’s `TxOut` exactly equals the stored `output`.

### Proof of Concept
Conceptually:

```rust
// Choose any outpoint, including one that does not exist or whose real
// TxOut has a different value/script.
let forged_outpoint = OutPoint { txid: arbitrary_txid, vout: arbitrary_vout };

// Use a script controlled by the Serai threshold key so multisig() accepts it.
let forged_txout = TxOut {
  value: Amount::from_sat(attacker_chosen_value),
  script_pubkey: p2tr_script_buf(threshold_group_key).unwrap(),
};

// Serialize:
//   Secp256k1 offset (for example zero)
//   forged_txout in Bitcoin consensus encoding
//   forged_outpoint in Bitcoin consensus encoding
let received = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();

let signable = SignableTransaction::new(
  vec![received],
  &payments,
  change,
  None,
  fee_per_vbyte,
).unwrap();

// This succeeds because it compares only the supplied script to the
// offset threshold key.
let machine = signable.multisig(&threshold_keys).unwrap();
```

The machine then signs each input with a `Prevouts::All` commitment to the forged `TxOut`. [5](#0-4)  Because the referenced outpoint does not resolve to that UTXO, the completed transaction is invalid even though the deserialized `ReceivedOutput` was treated as spendable.
