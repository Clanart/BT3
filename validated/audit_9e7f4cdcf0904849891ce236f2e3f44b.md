## Finding

### Title
Attacker-controlled `WWW-Authenticate` header from a git remote spoofs credential-helper host classification, triggering a branded GitHub sign-in/OAuth flow for an untrusted host - (`File: app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's credential-helper trampoline determines whether a git remote should be treated as a trusted "GitHub"/"GitHub Enterprise" endpoint (as opposed to a plain, low-trust "generic" git host) partly by inspecting the `WWW-Authenticate` header Git captures from the remote's HTTP 401 response. Any git server the user fetches/clones/pushes from — including an attacker-controlled remote or a MITM proxy sitting on an otherwise unrelated HTTPS endpoint — can set `WWW-Authenticate: Basic realm="GitHub"` and cause Desktop to misclassify that host as `'enterprise'`, exactly like the report's artist manipulating on-chain fee parameters to redirect value that should have gone elsewhere. The classification is trusted without any cryptographic or connectivity verification, and there is no "revert" (fail-safe/generic fallback) path analogous to the recommended fix in the original report.

### Finding Description
In `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:137-179`), once a credential-request's host isn't `github.com`/`api.github.com` or `*.ghe.com`, Desktop falls back to trusting the `wwwauth[]` entries that Git forwarded from the remote's HTTP response: [1](#0-0) 

These `wwwauth[]` values originate entirely from the remote server (or a proxy in the path) and are not authenticated in any way — any HTTPS git host can serve `WWW-Authenticate: Basic realm="GitHub"` on an unauthorized request.

This classification feeds directly into `getCredential` (`app/src/lib/trampoline/trampoline-credential-helper.ts:93-135`), which — for any endpoint classified as non-`'generic'` that has no matching stored account — prompts the user via `ui.promptForGitHubSignIn(endpoint)`: [2](#0-1) 

`promptForGitHubSignIn` (`app/src/lib/trampoline/trampoline-ui-helper.ts:80-104`) then routes non-`github.com` hosts into the full **Enterprise sign-in flow**, using the attacker-controlled host as the sign-in `origin`: [3](#0-2) 

`SignInStore.setEndpoint` (`app/src/lib/stores/sign-in-store.ts:394-459`) only performs syntactic validation (`validateURL`) before advancing to the branded "Sign in to your GitHub Enterprise" step — there is no verification that the target actually is a GitHub/GHE instance: [4](#0-3) 

If the user proceeds with browser-based authentication, `authenticateWithBrowser` opens an OAuth authorization URL built directly from the attacker's `endpoint`: [5](#0-4) 

The existing guards (`isDotCom`, `isGHE` in `app/src/lib/endpoint-capabilities.ts:47-62`) only protect the small set of first-party hostnames; they do nothing for a heuristic that trusts unauthenticated, server-supplied header text for every other host. The best-effort `isGitHubHost` probe (`app/src/lib/api.ts:2429-2491`) — which does make an actual network round-trip to check for GitHub-specific response headers — is bypassed entirely once a `wwwauth[]` realm of `"GitHub"` is present, because the `wwwauth` check short-circuits before that probe runs.

### Impact Explanation
A malicious or compromised git server (or a MITM proxy on any HTTPS git endpoint the user interacts with, including unrelated third-party hosting) can force GitHub Desktop to:
1. Treat that arbitrary host as a legitimate GitHub Enterprise endpoint (`endpointKind === 'enterprise'`), rather than the safer "generic git credentials" path a real third-party host would normally receive.
2. Surface the trusted, GitHub-branded sign-in dialog (`PopupType.SignIn`, "Sign in to your GitHub Enterprise") and initiate a real OAuth-authorization redirect to the attacker's own domain via `shell.openExternal`.
3. Persist a resulting `Account` bound to that attacker-controlled endpoint in the same `AccountsStore` used for legitimate GitHub/Enterprise accounts (unauthorized "account binding"), after which Desktop will auto-attach that account's credentials for future requests to the same host via `findGitHubTrampolineAccount`.

This matches the valid-impact category of "unauthorized OAuth or account binding" originating from an attacker-controlled git remote/proxy response, with no local access, malware, or leaked credentials required.

### Likelihood Explanation
The trigger is a single unauthenticated HTTP response header (`WWW-Authenticate: Basic realm="GitHub"`) returned by any git remote — attacker sets this up trivially by hosting or proxying a git-over-HTTPS endpoint. It fires automatically whenever Desktop's git operations hit that remote and Git needs credentials (clone/fetch/push against a private-looking or protected repo), without any unusual user action beyond adding/using that remote. It does still require the user to click through the resulting sign-in prompt to reach full account binding/OAuth exposure, similar to how the original report required loose slippage tolerance from the user — the mechanism itself, however, executes unconditionally and silently upgrades trust level based purely on attacker-controlled header content.

### Recommendation
Do not trust the `wwwauth[]` realm value alone to classify a host as `'enterprise'`. At minimum:
- Require the existing network-based `isGitHubHost` probe (which checks for authenticated GitHub-specific response headers such as `x-github-request-id`) to succeed before elevating an unknown host to `'enterprise'`, rather than short-circuiting on the header string.
- If the probe is inconclusive or fails, fail safe to the `'generic'` classification (equivalent to "revert" in the referenced report) instead of defaulting to the more trusted GitHub sign-in path.
- Surface the actual hostname prominently in the sign-in dialog so users can visually confirm they are authenticating against the domain they intend to trust.

### Proof of Concept
1. Stand up an HTTPS server (or MITM proxy) at `https://attacker.example` implementing just enough of the git-http-backend protocol to respond to an unauthenticated `git-upload-pack`/`info/refs` request with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add/clone this remote: `git clone https://attacker.example/foo.git`.
3. Git invokes Desktop's credential trampoline; `getEndpointKind` sees the `wwwauth[...]` entry containing `realm="GitHub"` and returns `'enterprise'` (`app/src/lib/trampoline/trampoline-credential-helper.ts:158-160`).
4. Because no account exists for `attacker.example`, `getCredential` calls `ui.promptForGitHubSignIn('https://attacker.example')` (`trampoline-credential-helper.ts:118`), which opens the "Sign in to your GitHub Enterprise" dialog bound to `attacker.example` (`trampoline-ui-helper.ts:90-93`).
5. If the user clicks "Sign in using your browser", `authenticateWithBrowser` opens `getOAuthAuthorizationURL('https://attacker.example', csrfToken)` in the system browser (`sign-in-store.ts:302`), and any resulting `Account` returned through the flow is persisted with `endpoint = https://attacker.example`, bound in Desktop's account store as if it were a legitimate GitHub Enterprise account.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
