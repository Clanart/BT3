### Title
Canceling an unlock without checkpointing rewards lets a vlMGP/mWomSV holder retroactively claim full (non-forfeited) rewards for the entire cooldown period - ([File: VLMGP.sol])

### Summary
`vlMGPBaseRewarder` reduces (forfeits) a portion of a user's earned rewards proportional to how much of their balance was "in cool down" versus fully locked, using a live snapshot of `VLMGP.getRewardablePercentWAD()` taken only at claim time. `VLMGP.cancelUnlock()` (and its `mWomSV.sol` counterpart) allows a user to move cooled-down tokens back to "fully locked" status without first checkpointing/forfeiting the reward accrued while those tokens were still in cool down, unlike `startUnlock()` and `unlock()`, which both call `multiclaimFor` first.

### Finding Description
Rewards accrue continuously based on `balanceOf(_account)`, which is `getUserTotalLocked() + getUserAmountInCoolDown()` [1](#0-0) , i.e., tokens in cool down still accrue reward-per-token at the full rate just like fully-locked tokens (`vlMGPBaseRewarder._earned` uses `balanceOf`) [2](#0-1) . The intended penalty for holding tokens in cool down is only applied later, when rewards are actually claimed, via `_calExpireForfeit`, which multiplies the accumulated earned amount by the *current* `getRewardablePercentWAD(_account)` [3](#0-2) [4](#0-3) .

`getRewardablePercentWAD` computes the forfeitable fraction based on the account's *current* mix of `fullyInLock` vs. `inCoolDown` balances, plus a partial credit if the cool-down slot has already fully matured [5](#0-4) . Crucially, `startUnlock()` and `unlock()` both force a reward checkpoint (`multiclaimFor`) before changing the user's lock/cool-down split, so any forfeiture tied to the "before" state is realized before the split changes [6](#0-5) [7](#0-6) .

`cancelUnlock()`, however, does **not** checkpoint rewards before resetting the cool-down slot back to zero (i.e., before restoring the tokens to "fully locked" status) [8](#0-7) . The identical pattern exists in `mWomSV.sol`'s `cancelUnlock()` [9](#0-8) .

Because forfeiture is computed lazily at claim time using only the *current* rewardable percent (not integrated over the historical cool-down duration), a user can:
1. Call `startUnlock()` to move some/all of their vlMGP balance into cool down (their `rewardablePercentWAD` immediately drops).
2. Continue accruing rewards at the full weighted rate over an arbitrarily long period (since `balanceOf`/`_earned` don't distinguish locked vs. cooling-down amounts).
3. Call `cancelUnlock()` right before claiming, which resets `amountInCoolDown` to 0 without ever calling `_sendReward`/`_calExpireForfeit` for the period that was actually in cool down.
4. Call `getReward()`/`getRewards()`. At this point `getRewardablePercentWAD(_account)` now reports 100% (no cool-down positions left), so `_calExpireForfeit` computes `forfeitAmount = 0`, and the user receives the **entire** accrued reward for the whole period — including the period they were "delinquent" (in cool down) and should have forfeited a proportional share.

This is the same bug class as the Union Finance finding: a discount/penalty mechanism intended to apply for the duration of an "unhealthy"/delinquent state is bypassed because the state is cured (cool down cancelled) before the penalty is ever checkpointed, letting the actor back-claim full rewards for the entire discounted period.

### Impact Explanation
This results in permanent, protocol-wide loss of the forfeited-reward mechanism: forfeited amounts are meant to be redistributed to other honest stakers via `_queueNewRewardsWithoutTransfer` (i.e., `ForfeitRewardAdded`) [10](#0-9) . By using this pattern, any vlMGP or mWomSV holder can systematically avoid ever forfeiting rewards regardless of how much of their balance is nominally in cool down, permanently diverting yield that should have gone to other stakers (theft/permanent freezing of unclaimed yield for honest, non-cooling-down stakers).

### Likelihood Explanation
High — this requires no special privileges, only ordinary user calls (`startUnlock`, `cancelUnlock`, `getReward`) available to every vlMGP/mWomSV holder, and can be repeated indefinitely with no cost beyond gas (cool down slots can be cancelled any time before maturity, per `_checkInCoolDown`) [11](#0-10) .

### Recommendation
Checkpoint (and realize forfeiture for) the account's rewards before resetting `amountInCoolDown` in `cancelUnlock()`, mirroring what `startUnlock()`/`unlock()` already do (i.e., call `IMasterMagpie(masterMagpie).multiclaimFor(...)` — or equivalently force `getReward`/`_sendReward` for the account across all reward pools that reference `vlMGP`/`mWomSV`) before flipping the slot's `amountInCoolDown` to 0. Apply the same fix to `mWomSV.cancelUnlock()`.

### Proof of Concept
1. User locks 100 MGP in `VLMGP`, becomes 100% "rewardable" (`getRewardablePercentWAD` = 1e18).
2. User calls `startUnlock(100e18)` — full balance now in cool down; `getRewardablePercentWAD` immediately drops toward 0 (all balance in an unmatured cool-down slot) [12](#0-11) .
3. Reward tokens are queued via `queueNewRewards` over time; the user's `earned()` accrues at the full `balanceOf` weight since `balanceOf` includes cool-down amount [13](#0-12) .
4. Immediately before the cool-down period ends, the user calls `cancelUnlock(slotIndex)` — this sets `amountInCoolDown = 0` with no reward checkpoint call [8](#0-7) .
5. User calls `getReward()`; `_updateFor` computes `userRewards` using `balanceOf` (now 100 fully locked, no cool down), then `_sendReward` calls `_calExpireForfeit`, which now sees `getRewardablePercentWAD` = 1e18 (100%, since there are no cool-down slots anymore), yielding `forfeitAmount = 0`.
6. The user receives 100% of the rewards accrued during the entire cool-down window, despite the protocol's intended design that cool-down balances should not earn full, unforfeited rewards.

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
```

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
