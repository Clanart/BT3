### Title
Local git remote URL is silently rewritten from an untrusted GitHub API `clone_url` without validating the target host - (`File: app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically executes `git remote set-url` whenever the GitHub API reports a different `clone_url` for a tracked repository. The only checks performed are that the URL scheme (`https`/`ssh`) is unchanged and that the *previous* remote matched the *previously cached* `clone_url` — there is no validation that the new hostname/owner belongs to a trusted endpoint. This mirrors the CoinFabrik `ico` finding: a value that can be mutated from external, attacker-influenceable input is changed without re-validating the invariant that should hold after the change (here: "the remote must still point at the account's trusted GitHub/GHE host").

### Finding Description
`updateRemoteUrl` is invoked with an `IAPIRepository` object (`apiRepo`) obtained from the GitHub API and uses `apiRepo.clone_url` directly to overwrite the local git remote: [1](#0-0) 

It performs three checks before calling the setter: [2](#0-1) 

1. `protocolsMatch` — only compares the URL *scheme* (`https:` vs `ssh:`), not the hostname.
2. `remoteUrlUnchanged` — confirms the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't hand-edited the remote).
3. `!urlsMatch` — the new API-reported URL differs from the current remote.

None of these checks constrain the *hostname* of the new URL to the account's known/trusted endpoint. `urlMatchesRemote`, used elsewhere for comparison, only checks that two URLs' hostname/owner/name are equal to each other — it never checks against an allow-list of trusted hosts: [3](#0-2) 

`parseRemote`/`remote-parsing.ts` will happily parse any hostname out of an `https://` or `git@host:` URL, with no restriction to `github.com` or the configured GitHub Enterprise host: [4](#0-3) 

Once the checks pass, the code calls `gitStore.setRemoteURL`, which shells out to `git remote set-url` with no further confirmation from the user and no re-validation of the resulting state: [5](#0-4) [6](#0-5) [7](#0-6) 

This is directly analogous to the reported bug class: a setter (`setRemoteURL`, via `updateRemoteUrl`) mutates a security-relevant configuration value (the git remote, which determines where fetches/pushes/credential requests go) in response to external input, without validating the post-condition ("the remote's host is still one we trust"). The original report's fix was to add an `isSane`/validity check at the point of mutation; no equivalent host-validation exists here.

### Impact Explanation
If the API object backing `apiRepo` (or the cached `GitHubRepository.cloneURL` baseline) can be influenced by an attacker — e.g., a malicious/compromised GitHub Enterprise server, a spoofed/MITM'd API response, or a scenario where the tracked repository's API metadata is attacker-controlled — Desktop will silently rewrite the user's git remote to point at an attacker-chosen host while preserving only the protocol. Because Desktop does the rewrite silently (no dialog, no diff shown), subsequent `git fetch`/`git push`/credential-helper interactions transparently target the attacker's infrastructure. This can result in:
- Credential/token exfiltration (git asks for credentials against the attacker's host).
- Silent redirection of what the user pushes (their commits could be sent to an attacker-controlled remote instead of the real one).

This fits the "silent corruption of what the user commits or pushes" / "credential exfiltration via attacker-controlled GitHub API object" impact category explicitly called out as valid.

### Likelihood Explanation
Exploitation requires the app to receive a crafted `IAPIRepository`/API response for a repository it already tracks (most plausible via a malicious or compromised GitHub Enterprise endpoint, since Desktop trusts whatever `clone_url` the configured API endpoint returns). It does not require local/physical access, admin rights, or pre-existing malware — the attacker primitive is control over the API object, which is explicitly listed as an accepted attacker capability for this analysis. The rewrite happens automatically as part of normal background repository refresh logic, requiring no unusual user action.

### Recommendation
Before calling `gitStore.setRemoteURL` in `updateRemoteUrl`, validate that the new URL's hostname matches the endpoint associated with the account/`GitHubRepository` (e.g., compare `parseRemote(updatedRemoteUrl).hostname` against `URL.parse(getHTMLURL(account.endpoint)).hostname`), and require explicit user confirmation for any remote rewrite that changes the hostname rather than only the owner/name path segments. This restores the "post-condition validation" that the setter is currently missing, analogous to adding `isPricingSane()`-style checks after mutation in the original report.

### Proof of Concept
1. Track a repository in Desktop that is associated with a GitHub Enterprise (or otherwise attacker-influenceable) API endpoint.
2. Cause the API to return an `IAPIRepository` whose `clone_url` uses the same protocol as the current remote but a different (attacker-controlled) hostname, while `gitHubRepository.cloneURL` (the previously cached baseline) still matches the user's unmodified local remote.
3. `updateRemoteUrl` (app/src/lib/stores/updates/update-remote-url.ts:7-45) computes `protocolsMatch = true`, `remoteUrlUnchanged = true`, `urlsMatch = false`, and calls `gitStore.setRemoteURL(name, updatedRemoteUrl)` with the attacker's host, silently repointing `origin`.
4. The next fetch/push/credential prompt targets the attacker-controlled host.

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
