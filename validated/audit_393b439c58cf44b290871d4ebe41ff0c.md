### Title
Index-space confusion in `threshold_i_map_to_keys_and_musig_i_map` removes the wrong participant's preprocess/share, causing deterministic DKG-confirmation failure and mis-attributed fatal slashes - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The DKG-confirmation MuSig protocol (`DkgConfirmer`) maps tributary `Participant` indexes (threshold-share index space, where each validator owns a range `start..end` of shares) into MuSig `Participant` indexes (validator position in the sorted signer list). `threshold_i_map_to_keys_and_musig_i_map` inserts our own entry into the map keyed by our *threshold* index, builds a new map keyed by *MuSig* index (`position + 1`), and then calls `map.remove(&our_threshold_i)` — removing an entry in the MuSig index space using a threshold index. Whenever any validator owns more than one key share, these two index spaces diverge, so the function either removes an innocent participant's message or leaves our own empty `vec![]` entry in the map.

The two index spaces only coincide when every validator before us holds exactly one share. `spec.i(removed, key)` returns a *range* (`start..end`), and `check_sign_data_len`/`unflatten` explicitly support validators holding multiple shares (handle.rs:232, 62-78), so `our_threshold_i` is a share index while `musig_i` is a validator-position index. For any validator positioned after a multi-share validator (or after skew from removed validators' ranges), `map.remove(&our_threshold_i)` removes a *different* signer's preprocess/share — or nothing at all — while our own empty-byte entry remains.

Downstream, `share_internal` iterates the map and calls `machine.read_preprocess` on our own empty `vec![]` (line 165), which fails, or — if our threshold index happened to collide with another validator's musig index — that validator's message was dropped instead, producing `FrostError::MissingParticipant`/`InvalidPreprocess`/`InvalidShare` with the *wrong* `Participant`. The returned `Participant` is a MuSig index but is passed to `self.spec.reverse_lookup_i(&removed, p)` in handle.rs:539, which interprets it as a threshold index — blaming a different, innocent validator, or panicking on `unwrap()` if out of range. ### Impact Explanation

Analogous to the reported privilege escalation (an unprivileged agent user gaining privileged capabilities): here, a single validator — an unprivileged party relative to the BFT validator set — causes the coordinator to mis-attribute protocol faults, producing a `RemoveParticipantDueToDkg` fatal-slash vote against an *innocent* validator. A fatal slash ejects that validator from the set, shifting relative voting/signature weight toward the attacker and stripping the victim's validator privileges. Additionally, `reverse_lookup_i(...).unwrap()` can panic, halting the coordinator, and the confirmation signing deterministically fails for the affected index — a liveness/integrity failure in `set_keys`. The bug is reached purely through normal, publicly-emitted tributary protocol data (DkgShares/DkgConfirmed transactions), with no privileged access required.

### Likelihood Explanation

The mis-indexing triggers deterministically on any validator set where at least one validator controls more than one key share before our position — a supported configuration (`spec.i` returns share ranges, and signing-data lengths are checked against `signer_i.end - signer_i.start`). However, whether production sets actually assign multiple shares per validator depends on deployment parameters not visible in scope, and the exact mis-blamed participant depends on set composition. Because the failure path (empty preprocess, missing participant, or out-of-range `unwrap`) fires on the ordinary DKG-confirmation flow, it does not require collusion — only a multi-share or removal-skewed set.

### Recommendation

Keep a single index space per map. In `threshold_i_map_to_keys_and_musig_i_map`, record our own *MuSig* index (the position of our key in `sorted`) and remove `Participant::new(our_musig_i)` from the musig-keyed map — or remove our entry while iterating, before re-keying. Separately, propagate blame in the threshold index space back to callers (convert `Participant` musig indexes back to threshold ranges before `reverse_lookup_i`), and avoid `unwrap()` on `reverse_lookup_i` results so a mapping failure degrades to a logged error instead of a coordinator panic.

### Proof of Concept

Setup: 3 validators; validator A holds shares at threshold indexes 1-2 (range 1..3), B at index 3, C at index 4 — i.e., A has two key shares. We are C (`our_threshold_i = 4`).

1. `map.insert(Participant(4), vec![])`; sorted threshold_is = [1,3,4] → musig map keys {1→A, 2→B, 3→C(empty)}.
2. `map.remove(&Participant(4))` removes nothing; `map.remove(...).unwrap()` returns `None` → **panic** at line 247, or if another signer occupies index 4, their data is dropped while C's `vec![]` remains.
3. `share_internal` iterates to musig i=3 (us), calls `read_preprocess(&mut [].as_slice())` → `Err`, returns `Err(Participant(3))`.
4. handle.rs:538 calls `reverse_lookup_i(&removed, Participant(3))` — a musig index interpreted as threshold i — resolving to validator B, not C, and publishes `RemoveParticipantDueToDkg` against honest B → fatal slash of an innocent validator (or `unwrap()` panic → coordinator halt).

This is consistent with the surrounding code's own assumptions: `preprocess_internal` rebuilds the machine from `CachedPreprocesses` per context (b"DkgConfirmer", attempt), so every parse/blame error path is exercised on each `share()`/`complete()` call for the attempt.
