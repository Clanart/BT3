### Title
`internal_withdraw` Bypasses `aggregator_verification_address` ECDSA Gate, Allowing Unauthorized Withdrawal Execution — (`File: core/src/rpc/operator.rs`)

---

### Summary

The `InternalWithdraw` gRPC handler on the Operator server calls the same underlying `operator.withdraw()` function as the public `Withdraw` handler, but completely omits the `aggregator_verification_address` ECDSA signature check that `Withdraw` enforces. When `aggregator_verification_address` is configured — the intended production posture — any caller that can reach `InternalWithdraw` can trigger a payout transaction without the aggregator's mandatory approval, bypassing the explicit authorization gate the protocol designers installed.

---

### Finding Description

`Withdraw` (the externally-facing RPC) contains a deliberate authorization gate:

```rust
// core/src/rpc/operator.rs  lines 209-238
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // ... recover EIP-712 signer from verification_signature ...
    if address_from_sig != address_in_config {
        return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
    }
    // if signature missing → ECDSAVerificationSignatureMissing error
}
```

`InternalWithdraw`, which is registered on the **same TCP port** and calls the **same** `operator.withdraw()` function, contains no such check:

```rust
// core/src/rpc/operator.rs  lines 168-190
async fn internal_withdraw(
    &self,
    request: Request<WithdrawParams>,
) -> Result<Response<RawSignedTx>, Status> {
    let (withdrawal_id, input_signature, input_outpoint,
         output_script_pubkey, output_amount) =
        parser::operator::parse_withdrawal_sig_params(request.into_inner())?;
    // ← no aggregator_verification_address check
    let payout_tx = self.operator.withdraw(
        withdrawal_id, input_signature, input_outpoint,
        output_script_pubkey, output_amount,
    ).await?;
    Ok(Response::new(RawSignedTx::from(&payout_tx)))
}
```

The mTLS interceptor `OnlyAggregatorAndSelf` restricts `Internal*` methods to the operator's own client certificate when `client_verification = true`. However:

1. **`client_verification` is a boolean config flag** that defaults to `false` in the code path that selects `Noop` interceptor. When `false`, the server applies no certificate-based access control at all, making `InternalWithdraw` reachable by any network peer.

2. **Even when `client_verification = true`**, the mTLS gate only enforces *who* can call the method (the operator's own automation). It does not enforce *whether the aggregator has approved the specific withdrawal*. The `aggregator_verification_address` check is a separate, content-level authorization that verifies the aggregator has manually signed off on the exact `(withdrawal_id, input_outpoint, output_amount, output_script_pubkey)` tuple. The operator's own automation calling `InternalWithdraw` bypasses this content-level gate entirely.

The config comment makes the intent explicit:

```
/// Used for both an extra verification of aggregator's identity and to force citrea
/// to check withdrawal params manually during some time after launch.
pub aggregator_verification_address: Option<alloy::primitives::Address>,
```

The proto comment for `InternalWithdraw` acknowledges the missing check:

```
// Note: This is intended for operator's own use, so it doesn't include
// a signature from aggregator.
rpc InternalWithdraw(WithdrawParams) returns (RawSignedTx) {}
```

This is the exact bug class from the external report: a function that performs the same privileged bridge operation as a guarded sibling but omits the guard.

---

### Impact Explanation

`operator.withdraw()` constructs and submits a signed Bitcoin payout transaction that moves BTC out of the bridge vault to the withdrawal recipient. When `aggregator_verification_address` is set, the protocol requires the aggregator to have manually verified the withdrawal before any operator processes it. `InternalWithdraw` removes this requirement.

**Scenario A — `client_verification = false`:** Any network peer that can reach the operator's gRPC port can call `InternalWithdraw` with a valid `(withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount)` tuple (all of which are observable on-chain or derivable from Citrea state) and cause the operator to broadcast a payout transaction without aggregator approval. The operator loses the BTC it fronted and may not be reimbursed if the withdrawal was not legitimately registered.

**Scenario B — `client_verification = true`:** The operator's own automation (background tasks) can call `InternalWithdraw` to process withdrawals that the aggregator has explicitly not yet approved, defeating the "force citrea to check withdrawal params manually" invariant. This is a direct authorization bypass of the content-level gate.

In both cases the corrupted value is the operator's fronted BTC (bridge amount per withdrawal, minus fee), paid out without the required aggregator authorization.

---

### Likelihood Explanation

- `client_verification = false` is a reachable production configuration (the flag exists, the `Noop` path is compiled into the binary, and the `.env.example` sets it to `true` but does not enforce it).
- `aggregator_verification_address` is described as a production security control, not a test-only feature.
- The `InternalWithdraw` endpoint is registered on the same port as all other operator RPCs with no additional network-level isolation.
- An attacker needs only a valid `withdrawal_id` and the corresponding on-chain UTXO data — both publicly observable — to construct a valid call.

---

### Recommendation

Apply the same `aggregator_verification_address` ECDSA check inside `internal_withdraw` that `withdraw` already performs, or remove `InternalWithdraw` from the production gRPC surface entirely and replace it with a process-local call that never crosses a network boundary.

---

### Proof of Concept

**Setup:** Operator configured with `aggregator_verification_address = Some(0xAGGR...)` and `client_verification = false` (or attacker holds the operator's own client cert).

**Steps:**

1. Observe a pending withdrawal on Citrea: `withdrawal_id = 42`, `input_outpoint = <vault UTXO>`, `output_amount = 0.1 BTC`, `output_script_pubkey = <attacker address>`.
2. Construct a valid `input_signature` (Taproot Schnorr sig over the withdrawal UTXO — this is the user's signature already present in the Citrea withdrawal record).
3. Call `InternalWithdraw` directly:
   ```
   grpcurl -plaintext operator:port clementine.ClementineOperator/InternalWithdraw \
     '{"withdrawal_id":42,"input_signature":"...","input_outpoint":{"txid":"...","vout":0},
       "output_script_pubkey":"...","output_amount":10000000}'
   ```
4. The handler at `core/src/rpc/operator.rs:168-190` parses the params and calls `operator.withdraw()` with no `aggregator_verification_address` check.
5. `operator.withdraw()` constructs and broadcasts the payout transaction, paying out BTC without the aggregator's ECDSA approval.

**Root cause line:** `core/src/rpc/operator.rs:178-187` — `operator.withdraw()` is called with no preceding `aggregator_verification_address` guard, while the identical call at lines 241-250 inside `withdraw()` is protected by lines 209-238.
