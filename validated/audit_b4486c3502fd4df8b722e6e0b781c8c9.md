### No vulnerability found for this question.

**Analysis supporting this conclusion:**

The webhook and extension verification paths call `hmac_valid?(data)` in [1](#0-0)  with `data = request.raw_post` — the literal, unmodified raw request body bytes, as shown in `WebhookVerification#verify_request` [2](#0-1)  and `ExtensionVerificationController#verify_request` [3](#0-2) .

There is no reconstruction, sorting, joining, or reformatting of the payload before hashing — unlike `AppProxyVerification#calculated_signature`, which does build a canonical string by sorting and joining query params [4](#0-3) , the webhook/extension HMAC check simply HMACs the raw bytes that Shopify itself signs. Since the "canonical form" here is just the raw body with no transformation, there is no possibility of a canonicalization mismatch to exploit — the premise of the question does not apply to this code path.

Regarding fail-closed behavior: a malformed/wrong-length HMAC header causes `ActiveSupport::SecurityUtils.secure_compare` to return `false`, correctly blocking the request via `head(:unauthorized)`. A missing header (`shopify_hmac` returning `nil`) would cause `secure_compare` to raise an exception when calling `.bytesize` on `nil`, which still prevents the request from being treated as authenticated/processed (it errors out rather than succeeding) — no path exists where a missing/malformed HMAC results in `hmac_valid?` returning `true`.

Regarding "replay" of a previously-captured valid body+HMAC pair: this is not a code defect in this repository. HMAC-based signing is deterministic by design — Shopify's own webhook signing scheme does not embed a nonce/timestamp in the signed canonical form, so a replayed valid pair will always re-validate. This is inherent to the protocol and matches Shopify's own signing behavior, not a bypass introduced by `hmac_valid?`/`shopify_hmac`. It also requires the attacker to already possess a legitimately-signed body+HMAC pair, which does not grant access to anything beyond what was already authorized — it doesn't constitute an authentication bypass, session takeover, or scope escalation as required by the validation rules.

No exploitable authentication bypass, canonicalization mismatch, or fail-open condition exists in `hmac_valid?`/`shopify_hmac` for the webhook or extension verification entrypoints.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
