## Title
Optimistic payout and kickoff-based Reimburse race to spend the same move-to-vault UTXO, leaving the loser permanently unconfirmable - (core/src/rpc/aggregator.rs, core/src/builder/transaction/operator_reimburse.rs)

## Summary
`create_optimistic_payout_txhandler` and `create_reimburse_txhandler` both consume the same `DepositInMove` output of the move-to-vault transaction for a given `deposit_id`, but nothing in the aggregator's `optimistic_payout` path or the verifier's `sign_optimistic_payout` checks whether an operator has already fronted (and is awaiting kickoff-based reimbursement for) that same withdrawal before signing/broadcasting the N-of-N optimistic payout transaction. Because both spending paths are ultimately settled by Bitcoin consensus (only one input-spend can confirm), the loser of the race is left permanently unable to complete its transaction against that UTXO.

## Finding Description
Binding: for a withdrawal index `i`, the number of confirmed spends of `get_move_to_vault_txid_from_citrea_deposit(i)`'s `DepositInMove` output must equal 1, and specifically it must be the reimbursement path the honest operator relied on when it fronted the withdrawal.

- `Aggregator::optimistic_payout` (`core/src/rpc/aggregator.rs:1010-1263`) parses `deposit_id`/`withdrawal_id` from the caller-controlled `WithdrawParams`, checks only that the specific withdrawal UTXO is unspent (`self.rpc.is_utxo_spent(&input_outpoint)`, line 1033) and that `withdrawal_utxo == input_outpoint` (line 1067). It then builds `create_optimistic_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:459-492`), which spends input 0 = the withdrawal UTXO and input 1 = `move_txhandler.get_spendable_output(UtxoVout::DepositInMove)`. Verifiers sign this via `optimistic_payout_sign` → `Verifier::sign_optimistic_payout` (`core/src/verifier.rs:1570-1690`), which repeats the same checks (unspent withdrawal UTXO, script pubkey validity, verification signature) but never queries whether the withdrawal has already been fronted by an operator (no check against `withdrawals.payout_txid` / `is_payout_handled`).
- The kickoff-based `Reimburse` transaction (`core/src/builder/transaction/operator_reimburse.rs:341-385`, `create_reimburse_txhandler`) also spends `move_txhandler.get_spendable_output(UtxoVout::DepositInMove)` as its first input (`NormalSignatureKind::Reimburse1`), using a presigned N-of-N signature collected once during deposit setup — this signature is fixed at deposit time and is not re-validated against "has this UTXO already been spent by an optimistic payout" at broadcast time.
- An unprivileged attacker (who is simply the withdrawer, as permitted by the threat model: they can call Citrea's `withdraw`, choose the withdrawal UTXO bytes, and sign it) can: (1) call Citrea `withdraw` for `deposit_id`, (2) let/have an operator front the payout via `Operator::withdraw` → `create_payout_txhandler` (`core/src/operator.rs:560-675`), which only spends the withdrawal UTXO (not the vault), and (3) in parallel/race, call `Aggregator::optimistic_payout` with the exact same `deposit_id`/withdrawal parameters to get verifiers to co-sign and broadcast a transaction spending the shared `DepositInMove` output before the operator's kickoff+Reimburse chain gets there.
- Neither `Aggregator::optimistic_payout`/`Verifier::sign_optimistic_payout` nor the kickoff/Reimburse flow (`PayoutCheckerTask`, `mark_payout_handled`, `handle_finalized_payout` in `core/src/task/payout_checker.rs:31-113`) consult a single, shared "already paid out"/"already fronted" gate keyed by `deposit_id` before signing or broadcasting; the only true mutual exclusion is Bitcoin's double-spend rule at confirmation time, which arrives after significant off-chain and on-chain work (operator kickoff, timelocks, round-tx state machine) has already been committed by the honest party.

## Impact Explanation
If the optimistic payout tx confirms first, the operator has already fronted funds to the user via its own `Payout` tx (spending the withdrawal UTXO with the operator's own capital) but permanently loses the ability to confirm `Reimburse` against the `DepositInMove` output, because that output is already spent — this matches the Critical category "an honest operator permanently unable to be reimbursed." Conversely, if the kickoff-based `Reimburse` confirms first, the optimistic payout the attacker raced through becomes permanently unconfirmable, though this side only wastes verifier signing effort (no fund loss, since the withdrawer already got paid by the operator through the normal payout). The damaging direction is the first one: repeatable across any deposit/withdrawal id and any operator, since it depends only on winning a race between the operator's kickoff timelock chain and the verifiers' willingness to sign optimistic payout — no verifier or operator compromise is required.

## Likelihood Explanation
The precondition is simply that a withdrawer (which the threat model classifies as an unprivileged attacker) initiates a Citrea withdrawal, gets an operator to front it via `Operator::withdraw`, and then also requests `optimistic_payout` from the aggregator for the same `deposit_id` before the operator's kickoff+Reimburse completes. Because kickoff-based reimbursement requires a multi-step, timelocked chain (round tx → kickoff tx → challenge window → Reimburse tx), while `optimistic_payout` is a single aggregator call that can complete as soon as verifiers respond, the race is realistically winnable by the withdrawer/attacker with no special resources beyond normal transaction fees. This is repeatable per-withdrawal and does not require majority collusion, key compromise, or mainnet-specific conditions — it can be reproduced fully in regtest.

## Recommendation
Introduce a single, atomically-checked "payout committed" state per `deposit_id`/withdrawal index that both the `optimistic_payout` signing path (aggregator + verifier) and the operator's `withdraw`/kickoff flow consult and set before signing or broadcasting any transaction that spends the `DepositInMove` output. Concretely: before verifiers sign an optimistic payout (`Verifier::sign_optimistic_payout`), check the `withdrawals` table for an existing `payout_txid` (operator already fronted) for that `deposit_id` and refuse to sign if present; symmetrically, before an operator accepts `withdraw()`/emits a kickoff for reimbursement, check whether an optimistic payout has already been signed/broadcast/confirmed for that `deposit_id` and refuse. This check must be transactional (DB row lock or unique constraint transition) to avoid a repeat TOCTOU race between the check and the signing/broadcast.

## Proof of Concept
In `core/src/test/regtest` (or an e2e test module such as `deposit_and_withdraw_e2e.rs`):
1. Perform a deposit, obtain `move_txid`, and register a Citrea withdrawal for `deposit_id = i` with a withdrawer-controlled `withdrawal_utxo`/signature.
2. Call `Operator::withdraw` (or the RPC `withdraw`) so the operator fronts the payout (assert the `Payout` tx confirms, spending only the withdrawal UTXO).
3. Concurrently (before the operator's kickoff+Reimburse chain completes), call `Aggregator::optimistic_payout` with the same `deposit_id` and withdrawal parameters, and broadcast the resulting `RawSignedTx`.
4. Assert on the binding: query confirmed spends of `OutPoint { txid: move_txid, vout: UtxoVout::DepositInMove.get_vout() }` — expect exactly 1, and assert it is the optimistic payout txid rather than the operator's `Reimburse` txid.
5. Attempt to drive the operator's normal kickoff/Reimburse flow to completion (`payout_checker` task, `handle_finalized_payout`, `mark_payout_handled`) and assert it now fails/never confirms (`get_handled_payout_kickoff_txid` never returns the expected kickoff, or broadcasting `Reimburse` returns a mempool/consensus rejection due to missing/spent input), demonstrating the operator that fronted the withdrawal is permanently unable to be reimbursed.
