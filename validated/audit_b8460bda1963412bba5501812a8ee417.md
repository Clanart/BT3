### Title
`IntentGatewayV2.withdraw`/`onAccept` (Tron variant) treats a `false`-returning ERC20 `transfer` as success, silently losing escrowed beneficiary funds while marking the order as settled - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The core bug in the external report (H-06) is that a bridge contract's token-transfer handling wrapper incorrectly assumes all ERC20 tokens behave identically w.r.t. return values, causing either false reverts or false success. In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the escrow release path performs raw low-level `.call()`s to `IERC20.transfer` and checks only the boolean `success` returned by the call mechanism itself — never decoding/verifying the `returndata` that ERC20 semantically returns to indicate whether the transfer itself succeeded. [1](#0-0) 

### Finding Description
`withdraw()` is the internal function that releases escrowed order funds to a beneficiary, invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse` for cancellation refunds: [2](#0-1) 

For every non-native token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

`success` here only reflects whether the low-level call did not revert — it says nothing about the ABI-encoded boolean that a compliant `transfer()` is supposed to return. Per the ERC20 standard, a token is allowed to return `false` (rather than reverting) to signal a failed transfer (e.g., due to internal pausing, blacklist checks, insufficient allowance edge cases, or any custom failure logic that opts to return `false` instead of reverting). With this pattern, such a token would make the call succeed (`success == true`) while `returndata` decodes to `false`, i.e., the beneficiary receives nothing.

Despite that, the code proceeds to unconditionally decrement escrow accounting and mark the order filled/refunded:
```solidity
_filled[body.commitment] = beneficiary;
...
_orders[body.commitment][token] -= amount;
...
emit EscrowReleased({commitment: body.commitment});
``` [4](#0-3) 

This is the same root defect class as H-06 (naive ERC20 return-value handling breaking non-standard tokens) but manifests in the opposite direction: instead of a compliant `token.transfer()` call reverting for non-standard tokens without a return value, here a token that legitimately returns `false` on failure is silently accepted as a success. The same unchecked pattern is repeated for the transaction-fee payout and for `SweepDust` in `onAccept`: [5](#0-4) [6](#0-5) 

Notably, the equivalent EVM (non-Tron) `IntentGatewayV2.sol` and other apps in this repo (`ExtrinsicIntents.sol`, `HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, etc.) consistently `using SafeERC20 for IERC20;` and call `safeTransfer`/`safeTransferFrom`, which correctly validate the return data and handle both no-return-value and false-return-value tokens. The Tron fork of `IntentGatewayV2.sol` diverges from this pattern in its `withdraw`/`onAccept` functions, reintroducing the exact unsafe-transfer defect the rest of the codebase was hardened against.

### Impact Explanation
This corrupts the escrow-accounting invariant `_orders[commitment][token]` (the amount of tokens actually custodied for a given order) and the settlement-state invariant `_filled[commitment]` (whether an order's payout has actually reached the beneficiary). If a whitelisted underlying token ever returns `false` on a failed transfer (a legal ERC20 behavior, not requiring a malicious actor), the contract will:
- Mark the cross-chain intent order as filled/refunded (`_filled[commitment] = beneficiary`, `EscrowReleased`/`EscrowRefunded` emitted) even though the beneficiary received nothing.
- Decrement the internal escrow ledger as if funds left the contract, while the tokens remain locked in the contract.
- Permanently strand the beneficiary's funds — the beneficiary cannot re-claim (order already marked filled, escrow already zeroed), and no other authorized code path re-attempts the transfer.

This is a direct "loss of funds to the rightful beneficiary" and "false settlement-state acceptance" impact matching the bounty's core categories, without requiring any relayer, prover, admin, or malicious peer — it only requires a legitimate token used as escrow collateral to return `false` on a transfer failure, which is a standards-compliant ERC20 behavior.

### Likelihood Explanation
Likelihood depends on whether tokens configured for intent settlement can return `false` instead of reverting on failure (e.g., pausable/blacklistable stablecoins, or tokens with balance/allowance edge cases that intentionally return `false`). Given that USDT-class and other non-standard tokens are explicitly cited as in-scope for cross-chain intents (mirroring the original report's concern), and given the contract makes no restriction against such tokens being used as `order.inputs`/`output.assets`, this path is reachable through the normal `fillOrder`/withdrawal flow whenever the escrowed token exhibits this behavior — no privileged actor needed.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of this codebase (`evm/src/apps/IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, `HyperFungibleToken.sol`, etc.). `safeTransfer` correctly reverts if `returndata` is non-empty and decodes to `false`, and also tolerates tokens with no return value, closing both directions of the underlying bug class.

### Proof of Concept
1. Deploy or configure the escrow token used in an intent order to be one that returns `false` (instead of reverting) on a failed `transfer()` call — e.g., a paused/blacklisted stablecoin-style token, or a mock ERC20 that returns `false` when the recipient is blacklisted.
2. Have a user place an order with this token in `order.inputs`/`output.assets`, funding the escrow (`_orders[commitment][token] = amount`).
3. Trigger the fill/refund flow so that `onAccept` (kind `RedeemEscrow`/`RefundEscrow`) or `onGetResponse` calls `withdraw(body, ...)`, where `beneficiary` is (or becomes) an address for which the token's `transfer` returns `false` (e.g., a blacklisted address, or a token contract that returns `false` under some benign condition such as amount `0` guard or pause).
4. Observe: `token.call(...)` succeeds (`success == true`, since the token itself didn't revert), so `withdraw` proceeds to set `_filled[commitment] = beneficiary`, decrement `_orders[commitment][token] -= amount`, and emit `EscrowReleased`/`EscrowRefunded` — while the beneficiary's on-chain token balance is unchanged and the tokens remain stuck in `IntentGatewayV2`.
5. Confirm the beneficiary cannot re-trigger withdrawal: the order commitment is already recorded in `_filled`, and escrow accounting for that token is already zeroed, so funds are permanently unrecoverable through any exposed function.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
