## Analysis

The Linea report's broken invariant is: **a value that is authoritative for display/decision-making (`totalSupply` on L1) can silently diverge from the actual state (post-burn supply) because one code path (L2 burn) bypasses the accounting the other side relies on.**

The closest structural analog in GitHub Desktop is in the diff-computation/partial-commit pipeline: for **renamed files**, the diff the user reviews in the Changes pane is computed against the **index**, not `HEAD`, while for every other file type it is computed against `HEAD`. When a partial (line/hunk) commit is then built from that diff, the resulting patch is applied on top of the (already-diverged) index — so any content already staged in the index but *not* part of `HEAD` is silently folded into the commit without ever appearing in the diff the user approved.

### Title
Renamed-file diffs are computed against the index instead of HEAD, letting already-staged (invisible) content be silently committed - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryDiff` deliberately diffs renamed files against the git index rather than `HEAD`, as acknowledged in the code's own comment. Because `applyPatchToIndex`/`stageFiles` use this same diff to build the partial-commit patch that is applied `--cached` on top of the current index, any bytes that are already staged (index ≠ HEAD) for a renamed file — but that were never shown in the working-directory diff — end up in the final commit without the user ever seeing or approving them.

### Finding Description
`getWorkingDirectoryDiff` branches on file status: [1](#0-0) 
For `Renamed` files it diffs `--` `file.path` with no base ref, which effectively compares working tree to **index**, whereas every other status (`New`/`Untracked` vs `/dev/null`, everything else vs `HEAD`) compares against `HEAD`. The comment explicitly documents the resulting flaw: *"we won't show any changes already staged to the renamed file which differs from our other diffs."*

This same diff is the sole source of truth used to build partial-commit patches: [2](#0-1) 
`applyPatchToIndex` calls `getWorkingDirectoryDiff` again, turns it into a patch via `formatPatch`, and applies that patch `--cached` directly on top of whatever is currently staged: [3](#0-2) 

Because `stageFiles` never resets the index for a renamed file with a partial selection (it only resets/`git add`s files with `DiffSelectionType.All`) before calling `applyPatchToIndex`, whatever is already sitting in the index for that path (staged by a prior conflict resolution, rebase/cherry-pick step, or `git add`) is preserved verbatim and combined with the user's selected hunks: [4](#0-3) 

The net effect: the invariant "what the diff shows == what gets committed" — the same invariant the Linea report is about ("`totalSupply` should reflect real state") — is broken specifically for renamed files with partial-selection commits, exactly like the L2 burn path bypassing the L1 accounting.

### Impact Explanation
This is a "silent corruption of what the user commits" scenario, which is explicitly in-scope. An attacker who controls repository history that a victim clones/fetches/rebases/cherry-picks (e.g., crafting commits designed to produce a rename+conflict during a routine `cherry-pick`/`rebase` operation) can cause the index for a renamed path to hold attacker-chosen bytes that differ from `HEAD`. If the victim reviews the (incomplete) diff in Desktop and does a partial-line commit on that file, the attacker's staged bytes are folded into the resulting commit/push without ever being rendered in the UI for review — the user believes they only committed the lines they saw and selected.

### Likelihood Explanation
This requires: (1) a renamed file, (2) the index for that path differing from `HEAD` prior to the commit (achievable through ordinary multi-commit operations like cherry-pick/rebase/merge conflict resolution that Desktop drives), and (3) the user choosing a partial (not "select all") commit for that specific file. This is a narrower path than a fully generic bug, but it requires no special local access, admin rights, or social engineering beyond the victim performing routine operations (rebase/cherry-pick/merge) against attacker-authored history — squarely in the "attacker controls a cloned/fetched repository" category. Desktop's own code comment acknowledges the discrepancy exists, indicating the divergence is a known, reachable code path rather than a purely theoretical one.

### Recommendation
Make `getWorkingDirectoryDiff` diff renamed files against `HEAD` (consistent with all other statuses) so partial-selection UI always reflects the true delta between what will be committed and what's currently in `HEAD`. If diffing against the index is required for technical reasons (e.g., to avoid recreating a rename), then `applyPatchToIndex`/`stageFiles` should first reconcile the index to `HEAD` for the renamed path (removing any pre-existing staged bytes) before applying the user-approved patch, ensuring the final commit contains exactly the working-tree content the user reviewed and explicitly selected — no more, no less.

### Proof of Concept
1. Attacker crafts a repository/branch history such that a routine `git rebase`/`cherry-pick` performed by Desktop on a victim's clone triggers a rename with a conflict; git leaves the index for the renamed path pre-staged with attacker-chosen bytes that differ from `HEAD` (e.g. malicious code appended) as part of conflict resolution/sequencer state.
2. Victim resolves the conflict/continues the operation; Desktop's Changes pane calls `getWorkingDirectoryDiff` for the renamed file, which diffs working tree against **index** (`app/src/lib/git/diff.ts:379-390`) — the malicious index content is not shown because it isn't a difference between working tree and index.
3. Victim reviews the visible (partial) diff, selects only a few benign hunks, and commits.
4. `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-61`) builds a patch from the same index-relative diff and applies it `--cached` on top of the existing index, which still contains the attacker's invisible bytes.
5. The resulting commit (and subsequent push) silently contains the attacker's content, which was never rendered to or approved by the user in the Desktop UI.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
}
