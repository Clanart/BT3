### Title
Dust-flooding a wallet's puzzle hash can permanently exhaust the 500-coin hard cap in coin selection, bricking normal spends until manual, fee-costly consolidation - (File: `chia/wallet/coin_selection.py`)

### Summary
Any unprivileged actor can send an unbounded number of dust-value coins to a wallet's puzzle hash (a normal, permissionless "deposit" — no different from anyone sending an offer payment, refund, or airdrop). Because `select_coins` enforces a hard `max_num_coins = 500` limit when assembling a spend, an attacker can fragment a victim wallet's balance with more than 500 unspendable-in-aggregate dust coins so that ordinary transaction construction fails with `ValueError`, even though the wallet's total balance is more than sufficient. This mirrors the reported pattern of an adversary permissionlessly creating many small "deposits" that a critical unbounded/limited downstream loop can no longer process, halting normal operation (there, refunds; here, standard spend construction).

### Finding Description
`select_coins` in [1](#0-0)  hard-codes `max_num_coins = 500` for any single transaction. When the wallet's spendable coin set cannot satisfy the requested amount using at most 500 coins (e.g., because it is dominated by attacker-sent dust), the function falls through to the final branch and raises: [2](#0-1) 

This is reachable from the top-level per-wallet spend path used by every standard/CAT transaction: `Wallet.select_coins` and `CATWallet.select_coins` both call `get_spendable_coins_for_wallet` (which returns *all* unspent coins for the wallet, with no upper bound besides an optional `MaxSendQuantityWallet` cap for some wallet types) and then `select_coins`: [3](#0-2) [4](#0-3) 

Since sending coins to any puzzle hash is a fully permissionless on-chain action (identical in spirit to the "permissionless funding" abused in the original report), an attacker can broadcast many transactions creating thousands of tiny-value coins addressed to a victim's reused/announced puzzle hash (e.g., a donation address, an exchange hot wallet address, an offer-settlement address). Once the number of coins needed to reconstruct any requested spend amount exceeds 500, every subsequent `generate_signed_transaction` call for that wallet that needs more coins than the cap will throw, halting the victim's ability to spend until they manually run coin consolidation.

The built-in mitigation, `CombineCoins`/`combine`, itself is capped at 500 coins per combine transaction (`coin_num_limit: uint16 = uint16(500)`): [5](#0-4) 

So recovery requires the victim to pay fees for `ceil(N/500)` separate consolidation transactions (each of which must itself find fee-paying, non-dust coins) before normal spending resumes. An attacker who can send dust faster/cheaper than the victim consolidates can sustain the halt indefinitely for essentially the cost of transaction fees for many dust transactions.

### Impact Explanation
This is a spend-triggered transaction-processing halt: normal spend construction for a wallet can be made to fail (`ValueError`) purely as a result of unprivileged coin deposits from a third party, even though the victim's aggregate balance is more than sufficient to cover the requested spend. This can disrupt automated systems relying on a Chia wallet address (exchanges, bounty/escrow programs, offer-settlement services) exactly as in the referenced report — a party who cannot refuse incoming payments can be denial-of-serviced by a flood of small deposits.

### Likelihood Explanation
Medium-High: creating many small coins requires only standard, unprivileged spend bundles paying normal per-coin creation costs; no special permissions, timing, or protocol weaknesses are needed. Any wallet with a publicly known/reused receiving address (common for services, donation addresses, or offer counterparties) is exposed. The severity is bounded by the cost of the dust transactions and by the existence of the manual `combine` remedy, but the remedy itself is fee-costly and rate-limited to 500 coins per transaction, so a sustained attacker can keep pace with a lower-throughput victim.

### Recommendation
- Enforce upper bounds on the number of unspent coins tracked/considered per wallet/puzzle hash, or proactively auto-consolidate small/dust coins in the background (similar to the existing clawback `auto_claim_coins` batching) rather than only offering a manual `combine` command.
- Consider raising or making configurable the `max_num_coins` cap in `select_coins`, or improving the coin-selection algorithm to better utilize dust when it is the only way to meet an amount, rather than failing outright.
- Provide automatic/opportunistic coin consolidation during regular sync/spend flows so dust accumulation is continuously mitigated instead of requiring manual, fee-paying intervention once the wallet becomes stuck.

### Proof of Concept
1. Attacker learns victim's Chia receive/reuse puzzle hash (common for services, offer addresses, or bounty/donation wallets).
2. Attacker submits many low-fee spend bundles that each create a 1-mojo (or minimal) coin to that puzzle hash, repeating until the number of the victim's unspent coins exceeds 500.
3. Victim's wallet attempts a normal spend (e.g., `generate_signed_transaction`) for an amount that cannot be satisfied by any 500-coin subset of its coin set (because most value is now dust). `select_coins` in [6](#0-5)  exhausts the knapsack/`sum_largest_coins` fallbacks and raises `ValueError("Too many coins are required to make this transaction")`, even though the wallet's total confirmed balance covers the requested amount.
4. Victim must run the `combine` command ( [7](#0-6) ), limited to 500 coins and one target amount per invocation, paying fees each time, to recover spendability — while the attacker can continue sending fresh dust to re-trigger the condition.

```python
    async def select_coins(
        self,
        amount: uint64,
        action_scope: WalletActionScope,
    ) -> set[Coin]:
        """
        Returns a set of coins that can be used for generating a new transaction.
        Note: Must be called under wallet state manager lock
        """
        spendable_amount: uint128 = await self.get_spendable_balance()
        spendable_coins: list[WalletCoinRecord] = list(
            await self.wallet_state_manager.get_spendable_coins_for_wallet(self.id(), in_one_block=True)
        )

        # Try to use coins from the store, if there isn't enough of "unused"
        # coins use change coins that are not confirmed yet
        unconfirmed_removals: dict[bytes32, Coin] = await self.wallet_state_manager.unconfirmed_removals_for_wallet(
            self.id()
        )
        async with action_scope.use() as interface:
            coins = await select_coins(
                spendable_amount,
                action_scope.config.adjust_for_side_effects(interface.side_effects).tx_config.coin_selection_config,
                spendable_coins,
                unconfirmed_removals,
                self.log,
                uint128(amount),
            )
            interface.side_effects.selected_coins.extend([*coins])
        assert sum(c.amount for c in coins) >= amount
        return coins
```

```python
    async def get_spendable_coins_for_wallet(
        self,
        wallet_id: int,
        records: set[WalletCoinRecord] | None = None,
        pending_removals: set[bytes32] | None = None,
        in_one_block: bool = False,
    ) -> set[WalletCoinRecord]:
        wallet = self.wallets[uint32(wallet_id)]
        wallet_type = wallet.type()
        if records is None:
            if wallet_type == WalletType.CRCAT:
                records = await self.coin_store.get_unspent_coins_for_wallet(wallet_id, CoinType.CRCAT)
            else:
                records = await self.coin_store.get_unspent_coins_for_wallet(wallet_id)

        # Coins that are currently part of a transaction
        if pending_removals is None:
            pending_removals = {
                coin.name()
                for coin in await self.unconfirmed_additions_or_removals_for_wallet(
                    wallet_id=uint32(wallet_id), get="removals"
                )
            }

        # Coins that are part of the trade
        offer_locked_coins: dict[bytes32, WalletCoinRecord] = await self.trade_manager.get_locked_coins()

        filtered = set()
        for record in records:
            if record.coin.name() in {*offer_locked_coins.keys(), *pending_removals}:
                continue
            if isinstance(wallet, IsCoinSpendableWallet) and not await wallet.is_coin_spendable(record):
                continue
            filtered.add(record)

        if isinstance(wallet, MaxSendQuantityWallet) and in_one_block:
            filtered_as_list = list(filtered)
            filtered_as_list.sort(reverse=True, key=lambda rec: rec.coin.amount)
            return set(filtered_as_list[0 : min(len(filtered_as_list), wallet.max_send_quantity)])

        return filtered
```

```python
class CombineCoins(TransactionEndpointRequest):
    wallet_id: uint32
    number_of_coins: uint16 = uint16(500)
    largest_first: bool = False
    target_coin_ids: list[bytes32] = field(default_factory=list)
    target_coin_amount: uint64 | None = None
    coin_num_limit: uint16 = uint16(500)

    def __post_init__(self) -> None:
        if self.number_of_coins > self.coin_num_limit:
            raise ValueError(
                f"{self.number_of_coins} coins is greater then the maximum limit of {self.coin_num_limit} coins."
            )
        if self.number_of_coins < 2:
            raise ValueError("You need at least two coins to combine")
        if len(self.target_coin_ids) > self.number_of_coins:
            raise ValueError("More coin IDs specified than desired number of coins to combine")
```
