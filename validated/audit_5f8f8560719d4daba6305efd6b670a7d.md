### Title
Hardcoded `DUST` (546 sats) and `DEFAULT_MIN_RELAY_TX_FEE` policy constants produce transactions that are non-standard/unspendable under raised mempool minimums — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` validates outputs and fees against compile-time Bitcoin Core policy constants: `DUST: u64 = 546` and `bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE` (1000 sat/kvB). These are relay-policy values that Bitcoin Core adjusts dynamically (`mempoolminfee` rises under congestion, and the dust threshold scales with it as 3× min-relay-fee × spend size). A transaction that passes Serai's static checks can still be rejected by every mempool it reaches — or pay out change/payment outputs that are themselves unspendable dust under the prevailing fee regime — permanently stalling or burning funds the multisig already committed to spending.

### Finding Description
In `SignableTransaction::new`, every payment is checked only against the hardcoded `DUST` constant:

```rust
pub const DUST: u64 = 546;
// ...
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
```

The comment above the constant acknowledges it is copied verbatim from a specific Bitcoin Core commit's `policy.cpp`. Similarly, the change-output decision uses `value >= DUST` and the fee floor uses `DEFAULT_MIN_RELAY_TX_FEE`:

```rust
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

Both constants encode relay policy at one point in time. Bitcoin Core raises `mempoolminfee` (and therefore the effective dust limit) whenever the mempool is full; it has reached 10+ sat/vB during fee spikes, pushing the true dust threshold for a P2TR output well above 546 sats and the true minimum relay fee well above 1000 sat/kvB.

Two concrete failure modes result:

1. **Dust-valued change makes the entire transaction non-standard.** At line 229, any leftover `>= 546` is emitted as a change output. If the node's dynamic dust limit is, e.g., 1500 sats, the transaction contains a dust output and is rejected with `dust` — yet `SignableTransaction::new` returned `Ok`, the FROST `TransactionMachine` signs it via `taproot_key_spend_signature_hash` with `Prevouts::All` and `SighashType::Default`, and `TransactionSignatureMachine::complete` produces a signed TX that cannot be broadcast. The plan cannot complete until fees normalize.

2. **Signed transactions below the dynamic mempool minimum.** The `TooLowFee` gate only enforces the static 1000 sat/kvB floor. A caller-specified `fee_per_vbyte` passing this check but below the live `mempoolminfee` produces a fully signed transaction that no node will relay or accept — indistinguishable on-chain from "never sent," while `needed_fee`/`fee()` report it as valid.

### Impact Explanation
Funds are committed to transactions that either (a) cannot enter any mempool under prevailing policy — stalling all payments in the plan until network conditions change, with no override knob since the thresholds are constants — or (b) carry change/payment outputs that are economically unspendable, since spending them costs more in fees than their value. This mirrors the referenced bug class: a hardcoded economic threshold that is correct under average conditions but wrong under volatility, leaving user funds stuck. No protocol rule requires these values to be static; the failure is reachable purely by constructing a `SignableTransaction` with attacker/user-chosen payment amounts and timing broadcast during fee spikes.

### Likelihood Explanation
Reachability is direct: `SignableTransaction::new` is the single gateway for producing spends in `bitcoin-serai`, called with integrator/user-controlled `payments` and `fee_per_vbyte`. The trigger condition — mempool congestion raising `mempoolminfee` above the compile-time floor — is a recurring, well-documented Bitcoin network state (e.g., May 2023 and 2024 fee spikes where min relay fees exceeded 1000–5000 sat/kvB). No malicious validator or broken infrastructure is required; ordinary network congestion suffices.

### Recommendation
Make the dust threshold and minimum relay fee runtime parameters:

- Accept a `min_relay_fee` (or `dust_threshold`) argument to `SignableTransaction::new`, sourced from the connected node's `getmempoolinfo.mempoolminfee` / `estimatesmartfee`, and derive `DUST` dynamically instead of using `pub const DUST: u64 = 546`.
- Alternatively, define `DUST` conservatively relative to a configurable assumed worst-case feerate (as the processor's `Bitcoin::DUST = 10_000` comment already sketches), and treat it as a safety bound rather than a policy mirror.
- Re-check fee adequacy against the live mempool minimum at broadcast time, not just at construction.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Assume node mempoolminfee has risen to 5000 sat/kvB (5 sat/vB),
// making the effective dust limit ~1470 sats for a P2TR output.

let (script, _) = p2tr_script_buf(keys.group_key()).unwrap();
let inputs = vec![received_output_worth(10_000)];

// 1) A payment of 1000 sats passes the hardcoded check (1000 >= 546)...
let payments = vec![(script.clone(), 1000)];

// ...and a fee of 1 sat/vB passes the static TooLowFee floor...
let stx = SignableTransaction::new(inputs, &payments, Some(script), None, 1).unwrap();

// 2) FROST-signing succeeds
let machine = stx.multisig(&keys).unwrap();
// ... preprocess/sign/complete -> signed Transaction

// 3) Broadcast fails on every node:
//    - fee rate 1 sat/vB < mempoolminfee 5 sat/vB -> "min relay fee not met"
//    - even if bumped, the 1000-sat output < dynamic dust limit -> "dust"
// The signed transaction is unbroadcastable; inputs remain locked in the
// multisig until fee conditions change.
```

The bug is that `Ok(...)` is returned for a transaction the network will reject, because validity was judged against `546`-sat and `1000`-sat/kvB compile-time constants rather than live policy.
