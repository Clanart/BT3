### Title
Stale manual conflict resolutions silently survive across unrelated conflict operations, causing incorrect files to be auto-committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateConflictState` unconditionally carries the `manualResolutions` map from the *previous* conflict state into the *new* one before it even determines whether the new conflict belongs to the same Git operation. This mirrors the Fluid DEX bug class: a piece of state that should be reset/cleared when a boundary condition changes (here, the conflict "kind": merge/rebase/cherry-pick) is instead silently carried forward and reapplied, causing later logic to act on stale data it assumes is fresh.

### Finding Description
In `getConflictState`/`updateConflictState` (`app/src/lib/stores/updates/changes-state.ts:121-311`), the manual resolution map is computed up-front: [1](#0-0) 

This happens **before** any check of whether `prevConflictState` and the freshly computed `newConflictState` are even the same *kind* of operation. Only afterward does the function branch on kind: [2](#0-1) 

The comment at the "otherwise" branch explicitly acknowledges a transition between unrelated operations ("we transitioned from a merge conflict to a rebase conflict or vice versa") but does nothing to discard the `manualResolutions` map that was already baked into `newConflictState` at line 275 — it simply returns `newConflictState` as-is, complete with resolutions inherited from the prior, unrelated operation.

`manualResolutions` is keyed only by relative file path (`Map<string, ManualConflictResolution>`), not by operation/commit identity. Downstream, this map drives real file mutations: `_updateManualConflictResolution` writes it into `conflictState.manualResolutions` [3](#0-2) , and it is consumed by `stageManualConflictResolution`, which calls `checkoutConflictedFile` (`git checkout --ours`/`--theirs`) to pick file content at commit time [4](#0-3) , as well as by `createMergeCommit` when building the final commit [5](#0-4) .

So if a user resolves a conflicted path (e.g. `src/config.ts`) with "ours"/"theirs" during one operation (say, a merge that gets aborted or superseded), and a *different, unrelated* operation (a rebase or cherry-pick triggered by a maliciously crafted history) subsequently produces a conflict on a file at the *same path*, the stale resolution choice from the first operation is silently reapplied to the second conflict without the user ever being asked again. The `_getPricesAndExchangePrices`-style guard that should have reset the shared field (`delete _centerPriceShift` / clearing the bit) is analogous to clearing `manualResolutions` on a kind transition — and it's missing here.

### Impact Explanation
This can cause files that still contain genuinely different (attacker-crafted) conflicting content to be silently staged/committed using a resolution the user picked for an entirely different conflict, without any UI prompt. Concretely, a maliciously structured repository/branch history can be built so that the *same file path* conflicts on two different overlapping operations; if Desktop reaches the "otherwise" (kind-mismatch) branch while transitioning between them, whatever "ours"/"theirs" choice existed for that path is reused, resulting in silent corruption of what the user commits/pushes — matching the report's "silent corruption of what the user commits" impact category.

### Likelihood Explanation
Medium-low. It requires a specific sequence: an active conflict of one kind (merge, rebase, or cherry-pick) with a manual resolution already recorded for a path, followed directly (without the conflict state first becoming `null`) by a different kind of conflict re-occurring on the same path. This is a real, reachable code path (the developers explicitly comment on this exact merge↔rebase transition scenario) but it depends on interleaved multi-commit operations rather than a single simple user action, so it is not trivially triggered on every clone/fetch.

### Recommendation
When `prevConflictState` and `newConflictState` are of different kinds (the "otherwise" branch in `updateConflictState`), do not seed `getConflictState` with the old `manualResolutions` map — start fresh (`new Map()`) for the new operation, and only carry resolutions forward when the kind is confirmed unchanged (as already done correctly for the merge-to-merge and rebase-to-rebase branches).

### Proof of Concept
1. Start a merge that conflicts on `file.txt`; manually resolve it via `dispatcher.updateManualConflictResolution(repo, 'file.txt', ManualConflictResolution.ours)`, populating `conflictState.manualResolutions`.
2. Before the app's `conflictState` is reset to `null` (e.g. the merge is superseded by another operation such as a rebase started immediately, which the code's own comment acknowledges as a real transition case), trigger a rebase that produces a *new*, unrelated conflict also touching `file.txt`.
3. `updateConflictState` computes `manualResolutions` from the old (merge) `conflictState` at `changes-state.ts:270-275` and bakes it into the new rebase `ConflictState` returned from the "otherwise" branch (`changes-state.ts:307-310`), without ever re-prompting the user.
4. Completing the rebase (`Continue`) causes `stageManualConflictResolution`/commit creation to check out "ours" for `file.txt` based on the stale resolution, even though the content backing "ours" is now different — silently committing content the user never actually reviewed for this conflict.

Note: I was not able to execute this as a running test within this session (index-only access); the analysis is based on the code paths cited above, and I could not fully confirm every UI trigger sequence that reaches the "otherwise" branch in practice — a Devin session with a full checkout would be needed to write and run an executable repro against `update-conflict-state-test.ts`/the multi-commit-operation UI flow.

```typescript
export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
```
