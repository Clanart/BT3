### Title
Webhook shop-domain header trusted without being covered by HMAC signature, enabling cross-shop webhook forgery via signature reuse - ([File: lib/shopify_app/controller_concerns/payload_verification.rb], [File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` only HMAC-validates the raw request body (`request.raw_post`) against the app's shared secret. The `shop_domain`/`topic` identifying which store a webhook belongs to is read directly from the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` HTTP headers, which are not part of the signed payload. Any actor who legitimately receives one valid `(body, HMAC)` pair for the app (e.g., by installing the app on their own store) can replay that exact body/HMAC to the webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to a victim shop, and the signature check still passes. This is the same bug class as the reported "unvalidated ProposerIndex" issue: a cryptographically valid artifact is accepted, but the identity field associated with it is never cross-checked against who actually produced the signed data.

### Finding Description
`hmac_valid?` computes an HMAC over `data` (the raw body only) and compares it to the `HTTP_X_SHOPIFY_HMAC_SHA256` header: [1](#0-0) 

`WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` as the sole gate before processing, and separately exposes `shop_domain` straight from an unsigned header: [2](#0-1) 

`WebhooksController#receive` builds a `ShopifyAPI::Webhooks::Request` from `request.raw_post` and `request.headers.to_h` and hands it to `ShopifyAPI::Webhooks::Registry.process`, which extracts `topic`/`shop`/`webhook_id` from those same unsigned headers before dispatching to job handlers: [3](#0-2) 

The officially generated webhook job pattern (used for both custom webhooks and the mandatory privacy webhooks) trusts the `shop` value handed to it by the registry and uses it to look up the shop record and activate that shop's session, with no further validation that the `shop` value corresponds to the entity that actually produced the signed body: [4](#0-3) [5](#0-4) 

Because the app's HMAC secret (`ShopifyApp.configuration.secret`) is shared across all shops that install the app (it is not per-shop), an attacker who installs the app on their own store receives a genuine `(body, HMAC)` pair signed by that shared secret. Since headers (`shop`, `topic`) are outside the HMAC's scope, the attacker can resend that exact body/HMAC combination to the webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim's domain. `verify_request` still accepts it (body unchanged ⇒ HMAC valid), and the downstream job then operates on the victim shop's record/session using attacker-supplied webhook content, exactly mirroring the report's pattern where a validly-signed `RandaoReveal` was reused with a spoofed `ProposerIndex` because the index was never cross-checked against the actual signer.

### Impact Explanation
An attacker (any actor able to install the target app on any shop, including their own) can get the app to process attacker-crafted webhook payloads (e.g. `orders/create`, `app/uninstalled`, `shop/redact`, `customers/data_request`) as if they originated from a different, victim shop, because the shop-identifying header is not covered by the signature. Depending on the job logic generated from ShopifyApp's templates, this can trigger cross-shop side effects: incorrect data attributed to another shop, unwarranted uninstall/redact processing for a shop that never sent the event, or execution of business logic under the victim shop's `with_shopify_session` context using forged webhook content.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the app once (to obtain one valid signed webhook body/HMAC pair for the shared app secret) and then replay that raw request to the public, unauthenticated webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secret material needs to be recovered; the HMAC secret is shared across shops and simply doesn't cover the header that determines which shop is impacted.

### Recommendation
Include the shop domain (and topic) as part of the data covered by the HMAC check, or otherwise cryptographically bind the header values to the signed body, so that `verify_request` rejects requests where the claimed `shop_domain`/`topic` cannot be attributed to the same origin that produced the signed body. At minimum, downstream webhook handlers should not treat the `shop`/`shop_domain` value as trusted solely because the accompanying HMAC over the body validated.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook event (e.g., `orders/create`) and capture the raw POST body plus the resulting `X-Shopify-Hmac-Sha256` header sent by Shopify to `POST /webhooks/:type`.
3. Replay the exact same body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyApp::PayloadVerification#hmac_valid?` validates successfully because it only hashes the unchanged body: [6](#0-5) 
5. The registry dispatches to the generated job with `shop: "victim.myshopify.com"`, which looks up and operates on the victim's `Shop` record and session: [7](#0-6)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
