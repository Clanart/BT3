## Title
Instant reward-per-token injection in `BaseRewardPool`/`BaseRewardPoolV2` allows yield stealing via deposit/withdraw sandwiching around `queueNewRewards` - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward()` (and its `BaseRewardPoolV2` equivalent) applies an entire batch of new rewards to `rewardPerTokenStored` in a single atomic step, based on `totalStaked()` at the exact moment `queueNewRewards()`/`donateRewards()` executes, with no time-based vesting. Because `MasterMagpie.deposit()`/`withdraw()` have no lock, cooldown, or fee, an ordinary unprivileged wallet can watch the mempool for the reward-provisioning transaction, front-run it with a large deposit into the target pool, let the reward be credited entirely to the now-inflated `totalStaked`, and immediately back-run with a withdrawal — capturing a disproportionate share of the freshly distributed rewards while contributing zero real staking duration. This mirrors the StUSR "yield stealing" report, where sandwiching a reward-distribution call let an attacker become the primary stakeholder for a single block and harvest rewards meant for long-term stakers.

### Finding Description
`_provisionReward` computes the accumulator update as a lump sum: [1](#0-0) 

This function is invoked by `queueNewRewards` (the routine reward-distribution entrypoint, analogous to `RewardDistributor.distribute()`): [2](#0-1) 

Because the increment to `rewardInfo.rewardPerTokenStored` is `(_amountReward * 10**decimals) / totalStaked()` computed at that instant, whoever holds the largest share of `totalStaked()` at the moment this call lands captures the largest share of the newly injected rewards — regardless of how briefly they've held that stake. `earned()`/`_updateFor()` then credit rewards purely based on the account's current balance and the delta since their last checkpoint: [3](#0-2) [4](#0-3) 

`MasterMagpie.deposit()`/`withdraw()`, which any unprivileged wallet can call freely and instantly (no lock-up, no cooldown, no exit fee), are the entry points an attacker uses to inflate/deflate their stake around the reward injection: [5](#0-4) [6](#0-5) 

The identical pattern exists in `BaseRewardPoolV2._provisionReward`, used by the same `MasterMagpie`: [7](#0-6) 

### Impact Explanation
An unprivileged attacker can:
1. Front-run the reward manager's `queueNewRewards` call by depositing a large amount of the pool's staking token into `MasterMagpie` for that pool (becoming the majority of `totalStaked()`).
2. Let `queueNewRewards`/`_provisionReward` execute, crediting the reward pool's `rewardPerTokenStored` increment almost entirely proportional to the attacker's inflated share.
3. Back-run by calling `withdraw()`/`_harvestAndUnstake()` to claim the harvested bonus reward tokens and pull out their principal, all within the same block or two.

This directly steals unclaimed yield that should have accrued to genuine long-term stakers of that pool, since the entire batch of rewards is applied instantly rather than vested over time. This satisfies the "theft of unclaimed yield" impact bar.

### Likelihood Explanation
Reward distribution via `queueNewRewards` (called by the configured reward `manager`) is a routine, recurring, and predictable operation — its calldata is visible in the public mempool before inclusion. `MasterMagpie` deposits/withdrawals are permissionless and unrestricted (no minimum staking duration, no withdrawal fee, no cooldown), so any wallet with sufficient capital (or a flash-loanable token, if the staking token supports it) can execute the sandwich in the same manner described in the source report. This makes the attack straightforward to automate and repeat against every reward distribution.

### Recommendation
Replace the instantaneous lump-sum reward crediting in `_provisionReward` with a time-weighted/streaming distribution model (e.g., a `rewardRate` and `periodFinish` similar to the Synthetix `StakingRewards` pattern) so that newly queued rewards vest linearly over a fixed duration instead of being credited entirely to whoever holds the largest stake at the instant of injection. Alternatively, introduce a minimum staking duration or checkpoint-based reward accrual so a single-block deposit cannot capture a disproportionate share of freshly queued rewards.

### Proof of Concept
1. Reward manager prepares a transaction calling `BaseRewardPool.queueNewRewards(amountReward, rewardToken)` for pool `P`, visible in the mempool.
2. Attacker front-runs with `MasterMagpie.deposit(P, hugeAmount)`, dramatically increasing `totalStaked()` for `P`.
3. `queueNewRewards` executes; `_provisionReward` computes `rewardPerTokenStored += (amountReward * 10**decimals) / totalStaked()`, where `totalStaked()` now includes the attacker's `hugeAmount`.
4. Attacker back-runs with `MasterMagpie.withdraw(P, hugeAmount)`, which internally calls `_harvestBaseRewarder`/`getReward`, transferring to the attacker a reward amount proportional to `hugeAmount / totalStaked()` — most of the just-queued reward batch — despite having staked for only the duration of one transaction.
5. Genuine long-term stakers of pool `P` receive a diminished share of the reward batch that was intended for them.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

        if (!_isVlMgp)

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();

            user.available = user.available - _amount;
