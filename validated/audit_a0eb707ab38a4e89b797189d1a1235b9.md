### Title
Frozen-message invariant enforced only by `UPB_ASSERT` (no-op in release builds) in core upb mutation primitives - (File: `upb/message/internal/accessors.h`, `upb/reflection/message.c`)

### Summary
The Mochi report's invariant is: a "lock" state should gate whether a function may run, but the function only checks the flag incidentally/incorrectly, allowing the action to run when it shouldn't. The upb analog is the "frozen" message invariant: once a `upb_Message` is frozen, no field/extension mutation should succeed. In the core C library, this is enforced exclusively via `UPB_ASSERT(!upb_Message_IsFrozen(msg))` calls, not a real runtime branch with an error return.

### Finding Description
`upb_Message_SetBaseField`, `upb_Message_SetExtension`, `upb_Message_ClearBaseField` and `upb_Message_ClearByDef` gate mutation on frozen state purely via `UPB_ASSERT`: [1](#0-0) [2](#0-1) 

By contrast, the Python, Ruby, and PHP language bindings implement the same "frozen" invariant with real, always-active runtime checks that raise a language-level exception, not an assert that vanishes in release builds: [3](#0-2) [4](#0-3) 

This asymmetry mirrors the Mochi finding's structure: the "lock" flag (`lockCrv` there, `IsFrozen` here) exists and is checked in some call paths, but the enforcement at the lower-level primitive is either missing or compiled away, so the mutating operation can proceed even though the object's state says it should not.

### Impact Explanation
If a production upb build (release, `NDEBUG` defined — the default/recommended build configuration) reaches one of these core mutation primitives directly — e.g., via a C++/C caller that merges or decodes attacker-supplied bytes into a message object that the application has frozen (for expected immutability, such as a shared default instance, a cached options message, or an application-level "sealed" object) — the assert does not fire, and the write proceeds silently. This would corrupt an invariant the application relies on for correctness (frozen == immutable), rather than causing a crash or memory-safety issue by itself. This is analogous to `withdrawLock()` allowing withdrawals when the treasury believed itself "locked" — a logic-invariant violation, not a memory-corruption bug.

### Likelihood Explanation
Likelihood is uncertain and I could not fully confirm it within available time. `upb/wire/decode.c` also references `upb_Message_IsFrozen` (2 occurrences), which suggests the wire decoder does have some awareness of frozen state, but I was unable to retrieve and inspect those exact lines before running out of iterations, so I cannot confirm whether `upb_Decode`/`upb_DecodeMerge` positively rejects decoding into a frozen message with a real (non-assert) check, or whether it inherits the same assert-only gate as the base accessors. If the decoder itself has a proper runtime check (returning a decode error/status) before touching a frozen message, then the assert-only primitives are only reachable by direct internal/reflection API misuse by trusted application code — which would fall outside the "ordinary client sending bounded protobuf" attacker model and make this not exploitable through the public parse API alone.

### Recommendation
This could not be conclusively established as an externally-triggerable vulnerability within the investigation performed. To resolve the uncertainty, the exact `IsFrozen` check sites in `upb/wire/decode.c` need to be read to confirm whether `upb_Decode`/`upb_DecodeMerge` (the public binary parse entrypoints) validate frozen state with a real (non-assert) runtime check before performing any field write, for both the fast-table and fallback decode paths. If they do not, and instead rely on the caller having already checked frozen state (as the Python/Ruby/PHP bindings do), then core upb parsing into an attacker-reachable, already-frozen `upb_Message*` in a release build would silently succeed, and the fix would be to add an explicit, always-enforced (non-assert) frozen check inside `upb_Decode`/`upb_DecodeMerge` itself, matching the pattern already used in the language bindings.

### Proof of Concept
Not established. A minimal reproduction would require: (1) confirming the build defines `NDEBUG` (assert-off), (2) constructing a trusted-schema message, freezing it via `upb_Message_Freeze`, and (3) calling `upb_Decode`/`upb_DecodeMerge` with attacker-controlled bytes targeting that frozen message directly through the C API (bypassing any language-binding-level frozen check), then asserting the message's field values changed despite being frozen. I was unable to execute or trace this reproduction to completion before running out of tool iterations, so this remains an unconfirmed, plausible analog rather than a proven finding.
