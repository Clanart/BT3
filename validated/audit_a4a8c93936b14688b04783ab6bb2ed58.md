### Title
Unchecked `payment_sat + needed_fee` addition can wrap, bypassing the funds-sufficiency check and producing an unspendable signed transaction - (networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is "subtraction expects `a >= b` but `a` may be smaller" — unchecked arithmetic ordering. In `SignableTransaction::new`, the guard meant to prove `inputs >= payments + fee` is computed as `input_sat < (payment_sat + needed_fee)` where `payment_sat` is an attacker-influenced `u64` sum. The addition can overflow/wrap before the comparison, so the check can pass while `payments + fee` actually exceeds the inputs. The same wrapping addition feeds `checked_sub` for the change output, defeating its protection. The result is a `SignableTransaction` whose output values exceed its inputs — a consensus-invalid transaction the FROST multisig will still sign.

### Finding Description
`SignableTransaction::new` sums caller-supplied payment amounts into `payment_sat` (`send.rs:187`) and then validates sufficiency with:

- `if input_sat < (payment_sat + needed_fee)` at `send.rs:215` — `payment_sat + needed_fee` is a plain `u64` addition that can overflow.
- `input_sat.checked_sub(payment_sat + fee_with_change)` at `send.rs:228` — `checked_sub` protects the subtraction, but its operand `payment_sat + fee_with_change` can itself wrap to a small value, so the subtraction succeeds and yields a `value >= DUST` change output at `send.rs:229-233`.

Only a lower bound (`amount < DUST` at `send.rs:166`) is enforced on each payment; there is no upper bound and no `checked_add`/`checked_sum` on the aggregate. A `payments` list whose amounts sum to near `u64::MAX` (e.g., two payments of `u64::MAX/2 + DUST`) makes `payment_sat + needed_fee` wrap to a small residue, so `NotEnoughFunds` is never raised even though the declared payments vastly exceed `input_sat`. The change branch then computes `input_sat - wrapped_residue`, producing a large change `TxOut` pushed at `send.rs:230`.

The resulting `Transaction` has `sum(outputs) > sum(inputs)`, which is consensus-invalid on the Bitcoin network (negative fee). `TransactionSignMachine::sign` (`send.rs:355-397`) will still run the full FROST ceremony over `taproot_key_spend_signature_hash` and `complete` will return this transaction, and `fee()` (`send.rs:139`) computes `sum(prevouts) - sum(outputs)` which underflows for such a transaction.

### Impact Explanation
A threshold signing round is consumed to produce a transaction that can never be broadcast/confirmed — the signers are induced to sign a malformed, unintended transaction body. Depending on the caller's retry logic this permanently stalls spends of the scanned inputs (the same UTXOs are re-attempted with the same overflowing payment set), a denial of service on the wallet's spend path. In debug builds the overflowing addition also panics. This maps to the accepted impact class of "concrete signing of an unintended message" — the signed bytes encode outputs that were never actually affordable.

### Likelihood Explanation
Reachability requires the payment amounts fed to `SignableTransaction::new` to be attacker-influenced; `payments: &[(ScriptBuf, u64)]` is a public API parameter and in Serai's architecture is populated from externally requested withdrawal data, where amounts are unbounded `u64` values. A request totaling near `u64::MAX` sats is unrealistic in value terms, but the code accepts and acts on it — the flaw is deterministic whenever such input is supplied. Realistically this is a Medium-severity robustness/consensus-validity flaw rather than a direct theft: inputs are not lost (the invalid tx can't spend them), but signatures and spend availability are compromised.

### Recommendation
Use checked arithmetic throughout the funds accounting:

```rust
// networks/bitcoin/src/wallet/send.rs
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: u64::MAX, fee: needed_fee })?;
let required = payment_sat.checked_add(needed_fee)
  .ok_or(TransactionError::NotEnoughFunds { inputs: input_sat, payments: payment_sat, fee: needed_fee })?;
if input_sat < required { /* NotEnoughFunds */ }
```

and similarly `payment_sat.checked_add(fee_with_change).and_then(|r| input_sat.checked_sub(r))` in the change branch. Also make `fee()` use `checked_sub` so an inconsistent transaction cannot silently wrap.

### Proof of Concept
```rust
// Construct a SignableTransaction whose payments overflow the sufficiency check.
let huge = u64::MAX / 2;
let payments = vec![
  (ScriptBuf::new_p2tr_tweaked(TweakedPublicKey::dangerous_assume_tweaked(x)), huge),
  (ScriptBuf::new_p2tr_tweaked(TweakedPublicKey::dangerous_assume_tweaked(x)), huge),
];
// payment_sat wraps mod 2^64; payment_sat + needed_fee wraps below input_sat.
// SignableTransaction::new returns Ok(...) with a tx whose outputs >> inputs.
let tx = SignableTransaction::new(inputs, &payments, Some(change), None, fee_per_vbyte).unwrap();
// tx.fee() underflows; the signed Transaction is consensus-invalid and unbroadcastable.
```

Uncertainty note: I was not able to fully trace which higher-level Serai component populates `payments`, so the unprivileged-reachability claim rests on `payments` being derived from externally supplied withdrawal data; if amounts are clamped by a caller before reaching `SignableTransaction::new`, severity drops accordingly. Other `multiexp`/`frost` subtraction sites were enumerated but not confirmed as underflow-capable within the iteration budget.
