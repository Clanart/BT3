Confirmed: `SignInStore.authenticateWithBrowser()` is the only call site that invokes `AccountsStore.removeAccount()` directly, bypassing `AppStore._removeAccount()` (the only place that also calls `deleteToken()` to revoke the OAuth token server-side). All other call sites (`preferences.tsx` logout, `sign-in.tsx` `ExistingAccountWarning` submit) route through `dispatcher.removeAccount()` → `AppStore._removeAccount()`, which does both steps.

### Title
Re-authenticating over an existing GHE account purges the local keychain entry but never revokes the old OAuth token, leaving a live "ghost" credential - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
`SignInStore.authenticateWithBrowser()` (app/src/lib/stores/sign-in-store.ts:255-283) handles the `ExistingAccountWarning` step of re-signing-in to an Enterprise endpoint that already has a stored account. Before starting the new OAuth flow it calls `this.accountStore.removeAccount(existingAccount)` directly, which deletes the local keytar entry and removes the account from the persisted list, but it never calls `deleteToken()`, the function that sends `DELETE applications/{client_id}/token` to actually revoke the OAuth access token on GitHub's side.

### Finding Description
Compare the two "remove account" code paths:

- The canonical, safe path: `Dispatcher.removeAccount` → `AppStore._removeAccount`, which does both steps: [1](#0-0) 

- The bypass path used specifically during re-authentication over an existing GHE/Enterprise account: [2](#0-1) 

`deleteToken()` is the only mechanism in the codebase that revokes the access token with GitHub's API: [3](#0-2) 

Because `authenticateWithBrowser()` only calls `accountStore.removeAccount()`, the local UI, keychain (`keytar`) entry, and `users` JSON blob are all cleared — the account visibly disappears from Desktop's account list — but the previously-issued OAuth token is never sent to GitHub for revocation. This is structurally analogous to the reported `__abdicate()` bug: an operation that is supposed to fully strip an entity's authority (governor / account) only clears the *local, visible* pointer (`gov = 0` / removed-from-`AccountsStore`) while leaving a still-valid credential (`pendingGov`/`emergency_gov` / the un-revoked OAuth token) that can restore access later.

### Impact Explanation
If the previously stored token for that Enterprise account had already been exfiltrated (e.g. via a compromised extension, disk access, or a prior credential leak), "signing out" through this re-authentication flow gives the user a false sense that the old session/credential is dead. In reality the token remains valid against the GitHub Enterprise instance indefinitely (until it separately expires or is manually revoked from GitHub's web settings), so whoever holds that leaked token retains authenticated API access to the user's account/repos even after the user believes they've cut it off by re-authenticating in Desktop.

### Likelihood Explanation
This triggers on a legitimate, common user action — re-signing into an Enterprise endpoint that Desktop already has an account for (`SignInStep.ExistingAccountWarning` → "Continue" / browser auth) — with no attacker interaction required to hit the code path itself. It is a silent omission (missing `deleteToken()` call) rather than a corner-case race, and it is directly visible by diffing this call site against the otherwise-consistent `_removeAccount` pattern used everywhere else in the codebase.

### Recommendation
In `SignInStore.authenticateWithBrowser()`, replace the direct `this.accountStore.removeAccount(existingAccount)` call with the full removal routine (i.e., also revoke the token via `deleteToken(existingAccount)`, mirroring `AppStore._removeAccount`), or refactor so `SignInStore` invokes `AppStore._removeAccount` (via a passed-in callback/dispatcher) instead of talking to `AccountsStore` directly.

### Proof of Concept
1. Sign in to a GitHub Enterprise instance in Desktop; note the token stored in the OS keychain for that endpoint.
2. From Desktop, start a new Enterprise sign-in for the *same* endpoint (Preferences → Accounts → Sign in, or the sign-in dialog) to trigger `SignInStep.ExistingAccountWarning`.
3. Click "Continue"/submit, which calls `SignInStore.authenticateWithBrowser()`; observe (via logs or a proxy) that only `AccountsStore.removeAccount` runs — no `DELETE applications/{client_id}/token` request is made to the endpoint's API.
4. Complete the new OAuth flow with a different set of credentials.
5. Using the token captured in step 1 (e.g., via `curl -H "Authorization: token <old_token>" https://<endpoint>/user`), confirm the old token still authenticates successfully even though it no longer appears anywhere in Desktop's UI or keychain.

export async function deleteToken(account: Account) {
  try {
    const creds = Buffer.from(`${ClientID}:${ClientSecret}`).toString('base64')
    const response = await request(
      account.endpoint,
      null,
      'DELETE',
      `applications/${ClientID}/token`,
      { access_token: account.token },
      { Authorization: `Basic ${creds}` }
    )

    return response.status === 204
  } catch (e) {
    log.error(`deleteToken: failed with endpoint ${account.endpoint}`, e)
    return false
  }
}
