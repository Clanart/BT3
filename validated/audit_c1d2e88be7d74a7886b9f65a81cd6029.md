### Title
Zero-value reward fee transfers in `_sendRewards` can permanently block LP deposits/withdrawals - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking._sendRewards` distributes harvested reward tokens to fee recipients via `IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend)` without checking that `feeTosend` is non-zero. Since `_sendRewards` is invoked on every deposit, withdraw, and harvest of Wombat LP tokens, a reward token that reverts on zero-value transfers can cause every user action on that pool to permanently revert.

### Finding Description
`_sendRewards` computes a fee amount as a percentage of the harvested reward for each active `feeInfo` entry and, when `feeInfo.isAddress` is true, sends it directly: [1](#0-0) 

`feeTosend` (derived from `feeAmount = originalRewardAmount * feeInfo.value / DENOMINATOR`) can round down to zero when the harvested reward amount is small relative to `DENOMINATOR`, yet the code calls `safeTransfer` unconditionally instead of guarding with `if (feeTosend > 0)` — unlike the sibling zero-guard already present at the top of the function for `_amount`: [2](#0-1) 

`_sendRewards` is reached from `_toMasterWomAndSendReward`, which is called unconditionally inside both `depositLP` and `withdraw` (the LP-custody entry points reachable by any wallet through `WombatPoolHelper`/`WombatPoolHelperV2`): [3](#0-2) 

If any reward token registered for a pool reverts on a zero-value `transfer` (a known non-standard-but-real ERC20 behavior class, exactly the bug class described in the referenced report), then whenever the fee computation rounds to zero for that token, the entire `deposit`/`withdraw`/`harvest`/`vote` transaction for that pool reverts.

### Impact Explanation
`WombatStaking.withdraw` and `depositLP` have no alternate code path — no `emergencyWithdraw` bypassing `_toMasterWomAndSendReward`/`_sendRewards` exists in the contract. If the harvested/fee-token combination hits the zero-transfer-revert condition, LP holders in that pool are permanently unable to withdraw their principal, meeting the freezing-of-funds bar (well beyond 24 hours, indefinitely until an owner reconfigures fees/reward tokens).

### Likelihood Explanation
The trigger condition (fee percentage rounding a small harvested reward amount down to zero) is a normal, frequently-occurring event for pools with low reward accrual per harvest, and does not require any privileged action — it happens automatically as part of ordinary user deposit/withdraw calls once a fee-recipient reward token that reverts on zero transfers is in use.

### Recommendation
Guard the direct fee transfer with a non-zero check, consistent with the pattern already used elsewhere in the function:
```solidity
if (feeTosend > 0) {
    IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
    emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
}
```

### Proof of Concept
1. Register a pool with a reward token whose ERC20 implementation reverts when `transfer`/`transferFrom` is called with amount `0`.
2. Configure an active `feeInfo` with `isAddress = true` and a small `value` such that, for a typical/small harvested reward amount, `feeAmount = amount * value / DENOMINATOR` rounds to `0`.
3. Any user calls `WombatPoolHelper.deposit`/`withdraw` (or `harvest`) for that pool, triggering `_toMasterWomAndSendReward` → `_sendRewards`.
4. `_sendRewards` computes `feeTosend = 0` and calls `IERC20(rewardToken).safeTransfer(feeInfo.to, 0)`, which reverts due to the token's zero-transfer behavior, reverting the user's deposit/withdraw transaction and freezing their LP funds in that pool indefinitely.
