## Title
Stale line-selection indices are trusted against a freshly re-read diff when staging partial commits, allowing a repository-controlled working-copy change to silently smuggle unselected content into a commit - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual diff lines to include in a commit (`DiffSelection`). That selection is captured against a specific `ITextDiff` snapshot's absolute line indices. When the commit is actually staged, `applyPatchToIndex` re-fetches a brand-new diff from disk (`getWorkingDirectoryDiff`) and blindly reuses the old `file.selection.isSelected(absoluteIndex)` values against the new diff's line indices, with no check that the two diffs are the same shape. This is structurally the same class of bug as the EigenPod issue: two independent state trackers (the UI's committed "selection" and the on-disk content used to build the actual patch) are assumed to stay in sync, but nothing enforces or re-validates that invariant at the point of use.

### Finding Description
`formatPatch()` in `app/src/lib/patch-formatter.ts` builds the patch to be applied to the index by iterating over a diff's hunks and, for every added/deleted line, calling `file.selection.isSelected(absoluteIndex)` [1](#0-0) . `applyPatchToIndex()` obtains that diff by calling `getWorkingDirectoryDiff(repository, file)` immediately before formatting and applying the patch [2](#0-1) . This diff is fetched fresh from the current on-disk working tree at staging time - it is **not** the same diff object the user reviewed and clicked lines on in the UI.

The application is aware that diffs can change out from under a selection: when the working directory diff is reloaded during normal refreshes, `app-store.ts` explicitly recomputes `selectableLines` and prunes selections that no longer correspond to real lines [3](#0-2) . However, that reconciliation only happens on the "browse/refresh" path that updates UI state - `applyPatchToIndex` does not go through it. It fetches a diff independently and trusts the possibly-stale `DiffSelection` object's `isSelected(absoluteIndex)` results against the new hunk's `absoluteIndex` values, assuming hunk boundaries and line ordering haven't shifted since the selection was made.

If the working copy content changes between the moment the user's selection was captured and the moment `stageFiles` → `applyPatchToIndex` runs (e.g. because a clean/smudge filter, `.gitattributes`-driven filter process, LFS filter, or any other content-mutating process tied to the cloned repository runs in that window), the hunk layout and absolute line indices in the new diff can differ from the old one. Because `isSelected` is keyed purely by index, not by line content or hash, the same index can now point at a different line. This means lines the user never selected can be silently included in the patch that gets applied to the index (and ultimately committed), or lines the user did select can be silently dropped - a direct case of "silent corruption of what the user commits."

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes," an explicitly in-scope impact. A malicious/compromised repository that ships a git filter (clean/smudge, `textconv`, LFS-style filter defined in `.gitattributes`) can alter file content on checkout/refresh in a way that is invisible in the diff the user reviewed but changes the line layout by the time Desktop stages the commit, causing Desktop to include attacker-influenced content in the user's commit without the user ever seeing or approving it in the diff view. Because commits are typically pushed and trusted by other consumers of the repository, this could propagate malicious content while the local user believes they only committed the lines they explicitly checked.

### Likelihood Explanation
Exploitation requires precise timing: the attacker-controlled filter/process must mutate the file's on-disk content between the diff render used for selection and the internal fetch inside `applyPatchToIndex`, in a way that shifts line/hunk indices without necessarily changing hunk counts drastically (so the empty-patch guard at `patch-formatter.ts:224` isn't tripped). This is plausible via git filters/hooks that run as part of normal Desktop operations on a cloned repository (in scope per the report's "attacker controls a cloned/fetched repository" criterion), but requires the attacker to engineer a specific race window, making it a real but non-trivial-to-hit race condition rather than a deterministic one-shot exploit. I was not able to fully trace every intermediate code path (e.g., exactly how much time elapses between `_performCommit` triggering and `stageFiles` running, or whether Desktop re-diffs immediately before commit in all cases) due to index/tool-call limits, so the precise timing window size is uncertain.

### Recommendation
Before applying `file.selection` against a freshly fetched diff in `applyPatchToIndex`, verify that the newly fetched diff matches the diff the selection was computed against (e.g., by comparing a content hash/hunk signature, or by re-deriving `selectableLines` and rejecting/re-prompting if the previously selected absolute indices no longer resolve to the same line content/type as before). If a mismatch is detected, abort the partial-commit staging and force the user to re-review the diff rather than silently applying a possibly-mismatched selection.

### Proof of Concept
Not independently reproduced in this session (no filesystem/terminal access). Conceptually:
1. Clone a malicious repository containing a `.gitattributes` clean/smudge filter (or similar filter script) on a tracked file.
2. Modify the file in the working directory and let Desktop compute a diff; select a subset of lines for a partial commit (`DiffSelection`).
3. Before Desktop's commit action actually stages the file (`stageFiles` → `applyPatchToIndex`), trigger the filter to rewrite the file content in a way that shifts line positions (e.g., insert/remove leading lines) without the UI re-rendering the diff.
4. Complete the commit; inspect the resulting commit content and observe it differs from what was shown/selected in the UI, because `formatPatch` applied the stale `DiffSelection` indices to the newly fetched diff [1](#0-0) [2](#0-1) .
