### Title
Payout OP_RETURN operator attribution is unauthenticated, allowing the withdrawal UTXO to be consumed with no valid payer, permanently freezing the vault UTXO - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `payout_tx` created by `create_payout_txhandler` commits the user's withdrawal authorization with a `SinglePlusAnyoneCanPay`-style signature that only binds input 0 and output 0 [1](#0-0) . The OP_RETURN output carrying the fronting operator's xonly pubkey (`op_return_txout`) is a separate, unsigned output appended after the anchor output and is not covered by the sighash that the user signs [2](#0-1) . Downstream, the verifier's chain sync (`update_finalized_payouts`) trusts this plaintext OP_RETURN data as the sole source of truth for "who fronted this withdrawal," storing it in the DB and later using it to gate reimbursement and to decide whether a kickoff is malicious [3](#0-2) . Because nothing cryptographically binds the OP_RETURN payload to the party who actually supplied the funding inputs, anyone possessing the user's off-chain-shared payout signature can broadcast a valid payout transaction (fully paying the user from their own BTC) while writing garbage or a non-participant's key into the OP_RETURN. This breaks the "operator credited versus the party that paid" binding and can permanently strand the corresponding `move_to_vault` UTXO.

### Finding Description
The withdrawal flow works as follows:
1. The user pre-signs a `SinglePlusAnyoneCanPay` signature authorizing spend of a small "withdrawal UTXO" into a fixed payout output. This signature is shared off-chain with operators [4](#0-3) .
2. Whoever holds this signature can build `payout_tx`: input 0 is the withdrawal UTXO (signature-verified), output 0 is the user's payout (amount-verified via sighash), output 1 is a CPFP anchor, and output 2 is an OP_RETURN with an arbitrary `operator_xonly_pk` [5](#0-4) .
3. Because `SinglePlusAnyoneCanPay` only commits to input 0 and the single corresponding output (output 0), the OP_RETURN (output index 2) and any additional funding inputs used to cover output 0's value are **not** signed by the user and can be freely chosen by whoever assembles and broadcasts the transaction.
4. When the verifier's block sync observes this tx, it extracts the OP_RETURN, and if it does not parse to a valid xonly pubkey (or is empty), records `operator_xonly_pk = None`, explicitly noting "This can happen if optimistic payout is used, or an operator constructs the payout tx wrong" [3](#0-2) .
5. `is_kickoff_malicious` treats a missing/invalid recorded payer as an automatic malicious signal for any operator attempting a kickoff on that deposit: "No operator xonly pk found in payout tx OP_RETURN, assuming malicious" [6](#0-5) .
6. `sign_optimistic_payout` (the N-of-N fallback path that lets verifiers directly pay the withdrawal recipient without an operator fronting) explicitly refuses to proceed once the withdrawal UTXO is already spent: "if the withdrawal utxo is spent, no reason to sign optimistic payout" [7](#0-6) .

Putting these together: an attacker who obtains the user's off-chain payout signature (shared with every operator that could service the withdrawal) can pay the user in full from their own BTC, but stamp the OP_RETURN with garbage or an unrelated key. The result:
- No operator's `PayoutCheckerTask` will find this payout under its own `operator_xonly_pk` (`get_first_unhandled_payout_by_operator_xonly_pk` keys off the stored payer pubkey) [8](#0-7) , so no legitimate operator will ever attempt `handle_finalized_payout`/kickoff for this deposit.
- Any operator that nonetheless attempted a kickoff for that deposit would be flagged malicious per step 5.
- The optimistic-payout escape hatch is permanently closed because the withdrawal UTXO is already spent (step 6).

Consequently, the `move_to_vault` UTXO for that deposit — funded by the honest depositor's bridge collateral — can no longer be released through any of the protocol's normal paths (`Payout`→`Reimburse` via a legitimate kickoff, or `OptimisticPayout`), even though the user has already been paid by the attacker.

### Impact Explanation
This matches the Critical impact category "a vault UTXO permanently frozen." The deposited collateral in `move_to_vault` (bridge_amount BTC, `UtxoVout::DepositInMove`) becomes unspendable through any operator-driven or verifier-driven path once the withdrawal UTXO is consumed with unattributable payer data, since:
- `create_reimburse_txhandler` requires spending the `DepositInMove` output together with a specific kickoff's reimburse connector tied to a specific operator [9](#0-8) , which requires a valid, attributed payer.
- `create_optimistic_payout_txhandler` also spends `DepositInMove` [10](#0-9)  but is blocked once the withdrawal UTXO is spent (step 6 above).

The only remaining spend path is the security-council multisig branch of the `move_to_vault` output [11](#0-10) , which is explicitly out of scope as a "requires security council" mitigation — it does not change that, from an unprivileged-attacker perspective, the funds are frozen out of the normal bridge protocol.

### Likelihood Explanation
The attack requires only: (1) access to the user's `SinglePlusAnyoneCanPay` payout signature, which by design is distributed off-chain to potentially multiple competing operators (any one of whom, or anyone who intercepts it, e.g. by observing it once any operator submits it to a mempool where the tx is still unconfirmed, can reuse it because it does not commit to the OP_RETURN or extra funding inputs), and (2) sufficient BTC to cover the withdrawal output value. Neither requires an operator role, verifier role, or any privileged key — the OP_RETURN field is plain pushed data, not a signature, so it is trivially forgeable by any party capable of constructing and funding a standard Bitcoin transaction.

### Recommendation
Bind the fronting operator's identity to the transaction the user actually signs — e.g., have the user's signature use a sighash type that commits to all outputs (or at least the OP_RETURN output), or otherwise cryptographically bind the operator's pubkey to the withdrawal request (for example, requiring the operator to sign over the withdrawal parameters, similar to `verification_signature` already used for optimistic payouts) rather than relying on unauthenticated OP_RETURN data for payer attribution during `update_finalized_payouts`.

### Proof of Concept
Conceptual PoC (not run against a live network due to tool limitations):
1. Obtain a valid `WithdrawParams` (`input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) for a pending withdrawal, as would normally be given to a servicing operator [4](#0-3) .
2. Independently construct a transaction mirroring `create_payout_txhandler`'s structure — input 0 = the withdrawal UTXO with the given `user_sig`, output 0 = the given payout amount/script, output 1 = anchor, output 2 = `op_return_txout` with an attacker-chosen 32-byte value that either does not parse as a valid xonly pubkey or is set to a pubkey belonging to an operator with no relationship to this deposit — fund any shortfall with attacker-controlled inputs and broadcast it before any registered operator submits their own `withdraw()` call.
3. Once mined, `update_finalized_payouts` stores `operator_xonly_pk = None` (or an unrelated key) for this withdrawal [3](#0-2) .
4. Verify that `get_first_unhandled_payout_by_operator_xonly_pk` never returns this withdrawal for the deposit's real operator(s), that `sign_optimistic_payout` now errors with "Withdrawal utxo ... is already spent" [7](#0-6) , and that any operator attempting to kick off reimbursement for that deposit is flagged malicious via `is_kickoff_malicious` [6](#0-5) , confirming the `move_to_vault` UTXO is now unreachable by the normal protocol paths.

/// Creates a [`TxHandler`] for the `payout_tx`.
///
/// This transaction is sent by the operator to front a peg-out, after which operator will send a kickoff transaction to get reimbursed.
///
/// # Inputs
/// 1. UTXO: User's withdrawal input (committed in Citrea side, with the signature given to operators off-chain)
///
/// # Outputs
/// 1. User payout output
/// 2. OP_RETURN output (with operators x-only pubkey that fronts the peg-out)
///
/// # Arguments
/// * `input_utxo` - The input UTXO for the payout, committed in Citrea side, with the signature given to operators off-chain.
/// * `output_txout` - The output TxOut for the user payout.
/// * `operator_xonly_pk` - The operator's x-only public key that fronts the peg-out.
/// * `user_sig` - The user's signature for the payout, given to operators off-chain.
/// * `network` - The Bitcoin network.
///
/// # Returns
/// A [`TxHandler`] for the payout transaction, or a [`BridgeError`] if construction fails.
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

                Ok((

pub fn create_move_to_vault_txhandler(
    deposit_data: &mut DepositData,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler<Unsigned>, BridgeError> {
    let nofn_xonly_pk = deposit_data.get_nofn_xonly_pk()?;
    let deposit_outpoint = deposit_data.get_deposit_outpoint();
    let nofn_script = Arc::new(CheckSig::new(nofn_xonly_pk));
    let security_council_script = Arc::new(Multisig::from_security_council(
        deposit_data.security_council.clone(),
    ));

    let deposit_scripts = deposit_data.get_deposit_scripts(paramset)?;

    Ok(TxHandlerBuilder::new(TransactionType::MoveToVault)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            SpendableTxIn::from_scripts(
                deposit_outpoint,
                paramset.bridge_amount,
                deposit_scripts,
                None,
                paramset.network,
            ),
            SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_scripts(
            paramset.bridge_amount,
            vec![nofn_script, security_council_script],
            None,
            paramset.network,
        ))
        // always use 0 sat anchor for move_tx, this will keep the amount in move to vault tx exactly the bridge amount
        .add_output(UnspentTxOut::from_partial(anchor_output(Amount::from_sat(
            0,
        ))))
        .finalize())
