### Title
Malformed generator-promotion proof set can panic `GeneratorPromotion::complete` - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
`GeneratorPromotion::complete` accepts a caller-provided `HashMap<Participant, GeneratorProof<C1>>` and checks only its length and that every supplied participant index is at most `n`. It does not check that the map excludes the local participant or that every expected participant `1..=n` is represented. A crafted map can therefore pass the preliminary checks while omitting an expected participant, causing an indexing `unwrap()` panic.

### Finding Description
The function verifies that `proofs.len() == n - 1` and that every key is `<= n`. [1](#0-0)  However, it then iterates every participant in `1..=n`, skips only the local participant, and unconditionally unwraps `proofs.get(&i)`. [2](#0-1)  Because the earlier checks permit the local participant index to appear in `proofs`, an attacker can replace an expected proof with a proof keyed by the local participant while preserving the expected map length.

For example, with `n = 4` and local participant `i = 1`, the attacker can provide proofs for `{1, 2, 3}`. The map has `n - 1 = 3` entries and all indexes are in range, but participant `4` is missing. The loop reaches `i = 4` and panics at `proofs.get(&i).unwrap()`.

### Impact Explanation
An unprivileged participant who can submit a malformed `GeneratorProof` map to `complete` can trigger a panic and abort the calling protocol/task. This maps the referenced packet-driven denial-of-service class onto Serai’s public proof-completion API. The impact is availability loss in the promotion flow rather than signature forgery or key disclosure.

### Likelihood Explanation
The malformed input requires no secret material and does not need to contain valid proofs. `GeneratorProof::read` merely deserializes a public share and DLEq proof from bytes. [3](#0-2)  The panic occurs before proof verification, so arbitrary syntactically valid `GeneratorProof` values are sufficient.

### Recommendation
Validate the proof map as an exact participant set before indexing it: reject the local participant, duplicates are naturally prevented by `HashMap`, and require every `i != params.i()` in `1..=params.n()` to be present. Replace `proofs.get(&i).unwrap()` with explicit error handling such as `ok_or(PromotionError::MissingParticipant(i))`, adding an appropriate error variant if necessary.

### Proof of Concept
For local params `ThresholdParams { t: 4, n: 4, i: 1 }`, call:

```rust
let proofs: HashMap<Participant, GeneratorProof<C>> = HashMap::from([
  (Participant::new(1).unwrap(), arbitrary_proof.clone()),
  (Participant::new(2).unwrap(), arbitrary_proof.clone()),
  (Participant::new(3).unwrap(), arbitrary_proof),
]);

promotion.complete(&proofs);
```

The preliminary validation accepts this three-entry map, then `complete` panics when it attempts to retrieve the missing proof for participant `4`. [4](#0-3)
