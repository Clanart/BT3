### Title
Non-atomic relayer reward payout lets a partial failure double-pay from the treasury without advancing the reward watermark - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::process_message` pays a relayer reward in two separate, non-atomic side effects — a `Currency::transfer` and a `ReputationAsset::mint_into` — and only advances the `LastRewardedHeight` watermark *after both succeed*. Because the caller (`FeeHandler::on_executed`) swallows the error from `process_message` with `let _ = ...`, a failure in the second step does not roll back the first, and the top-level extrinsic still returns `Ok`. This mirrors the seed bug's core defect: a claim/reward accounting checkpoint (`lastEpochClaimedOperator` there, `LastRewardedHeight` here) is only updated on the "success" path, so a legitimately-executed partial payout is never recorded, allowing the same block-span reward to be recomputed and paid again on a subsequent call.

### Finding Description
In `modules/pallets/consensus-incentives/src/impls.rs`:

```rust
fn process_message(...) -> Result<(), Error<T>> {
    if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
        let reward = Self::calculate_reward(&state_machine_id, block_cost)?;
        if reward.is_zero() { return Ok(()); }

        T::Currency::transfer(
            &T::TreasuryAccount::get().into_account_truncating(),
            &relayer_account,
            reward,
            Preservation::Expendable,
        )
        .map_err(|_| Error::<T>::RewardTransferFailed)?;               // (1) funds move

        Self::deposit_event(Event::<T>::RelayerRewarded { ... });

        T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
            .map_err(|_| Error::<T>::ReputationMintFailed)?;           // (2) can fail independently

        LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
            *watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
        });                                                            // (3) only reached if (2) succeeds
    }
    Ok(())
}

and `on_executed` unconditionally returns `Ok(...)`: [4](#0-3) 

Because the top-level extrinsic (`handle_unsigned` in `pallet-ismp`, which drives `FeeHandler::on_executed`) completes with `Ok`, FRAME's automatic storage-transaction rollback (which only reverts state on a dispatchable's `Err` return) never triggers. The `Currency::transfer` in step (1) is therefore permanently committed even though step (2)/(3) failed — there is no explicit `#[transactional]` boundary scoping just `process_message`. The watermark (`LastRewardedHeight`) stays at its old value, so the *next* honest consensus update for the same `state_machine_id` recomputes `blocks = latest_height - baseline` using the same stale baseline and pays the *same block span again*.

`T::ReputationAsset::mint_into` (a `fungibles::Mutate` implementation, typically `pallet-assets`) can fail for reasons the relayer indirectly controls or can encounter naturally, e.g. `BelowMinimum` when the minted amount is smaller than the asset's existential deposit and the relayer's reputation-asset account does not yet exist. A relayer can engineer this by submitting a consensus update for a very small number of blocks (a tiny `reward`), triggering the reputation mint to fall below the asset's minimum balance, while the `Currency::transfer` for that same tiny reward still succeeds and commits.

### Impact Explanation
This is a treasury loss-of-funds / duplicate-settlement bug matching the bounty class directly: unauthorized/duplicate transfer of value to an unintended extent. An unprivileged relayer can repeatedly trigger the reputation-mint failure path (by keeping rewards below the asset's minimum balance, or via any other transient mint failure condition) so that `LastRewardedHeight` never advances while `Currency::transfer` keeps paying out the same, or overlapping, block-span reward on every subsequent consensus submission. Each iteration drains `T::TreasuryAccount` for a reward that was already paid, without the accounting checkpoint that is supposed to prevent recomputation — the exact same double-claim invariant break as the seed report's `lastEpochClaimedOperator` bug, only here the checkpoint additionally gates funds movement in a non-atomic two-step process instead of a preventing re-claims.

### Likelihood Explanation
The relayer role that calls `handle_unsigned` (which drives `on_executed`) is a normal, permissionless message-submission actor — no admin/governance/relayer-trust assumption beyond "submits a valid consensus proof," which is the intended, expected usage of the pallet. Triggering `mint_into` failure only requires shaping the submitted consensus update so the computed `reward` is small (e.g., submitting updates in tight, small increments) relative to the reputation asset's existential deposit, which is fully within a relayer's control since they choose which height to advance to and how often to submit. No malicious peer, prover, or leaked key is required.

### Recommendation
Make the reward payout atomic with the watermark update:
- Wrap `process_message`'s side effects (`Currency::transfer`, `ReputationAsset::mint_into`, `LastRewardedHeight::mutate`) in an explicit `frame_support::storage::with_transaction` (or `#[transactional]`) block so that any failure in a later step reverts the earlier transfer.
- Alternatively, update `LastRewardedHeight` *before* performing the transfer/mint (compute-then-commit-watermark-then-pay), or perform the watermark update unconditionally as soon as `calculate_reward`'s span is computed, decoupling "reward accounted for" from "asset mint succeeded" (e.g., only propagate the mint failure as a soft warning/event, not a payout blocker).
- In `on_executed`, do not silently discard `process_message`'s `Err` — surface it, and ensure a partial payout cannot occur without the corresponding watermark advance.

### Proof of Concept
1. Configure `StateMachinesCostPerBlock` for a `state_machine_id` with a low `block_cost` such that a single-block reward is smaller than `ReputationAsset`'s existential/minimum balance, and ensure the relayer's reputation-asset account does not pre-exist (fresh relayer key).
2. Relayer submits a consensus message advancing the state machine's `latest_commitment_height` by 1 block over the current `LastRewardedHeight` baseline.
3. In `process_message`: `Currency::transfer` succeeds (treasury pays `reward`), but `T::ReputationAsset::mint_into` fails with `BelowMinimum` since the account has no existing reputation-asset balance and the reward amount is below ED.
4. `process_message` returns `Err(ReputationMintFailed)`; `on_executed` discards it via `let _ = ...` and returns `Ok`. `LastRewardedHeight` is left unchanged; the top-level `handle_unsigned` extrinsic commits successfully, including the `Currency::transfer` already applied.
5. Relayer submits another consensus message advancing to the same (or a further) height. `calculate_reward` recomputes using the same stale `baseline`, yielding the same (or overlapping) reward span, and pays the relayer again from the treasury for blocks already paid for in step 3.
6. Repeat steps 2–5 (keeping each submission's incremental reward below the reputation asset's minimum balance) to accumulate unlimited duplicate payouts from `T::TreasuryAccount`.

This can be reproduced deterministically in the existing testsuite harness (`modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs`), which already sets up the mock host, consensus messages, and reward pathway used by `test_incentivize_relayer` and `reward_covers_only_unpaid_heights_after_rollback` — by additionally configuring a `ReputationAsset` minimum balance and asserting `Balances::balance(&relayer_account)` increases twice for the same `LastRewardedHeight` value.
