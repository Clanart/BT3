### Title
Unauthenticated participant indexes in `BlameMachine::blame` / `AdditionalBlameMachine::blame` cause a panic (denial of service) on attacker-supplied DKG shares - ([File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs])

### Summary
CVE-2018-7870 is a crash-class bug: an unprivileged party feeds malformed input into a parser/lookup path and the program dereferences/indexes an invalid location, causing denial of service. The analog in Serai is `blame_internal` in PedPoP, which indexes `self.commitments[&sender]` and `self.enc_keys[&decryptor]` without first checking that `sender` / `recipient` are members of the DKG set (`1..=n`). An attacker who supplies a blame message and controls the `sender`/`recipient` arguments can force a panic, crashing the caller instead of returning a `PedPoPError`.

### Finding Description
`AdditionalBlameMachine::new` (and `BlameMachine` internally) populate `commitments` and `encryption.enc_keys` only for participants `1..=n`:

- `AdditionalBlameMachine::new` registers exactly `i in 1..=n` [1](#0-0) 
- `Decryption::register` inserts into `enc_keys` only for registered participants [2](#0-1) 

`blame()` accepts `sender` and `recipient` as free `Participant` arguments (any non-zero `u16`), with no bounds check against `n` [3](#0-2) 

`blame_internal` then reaches two unchecked map indexing operations on attacker-influenced keys:

1. `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` when a proof is supplied — panics if `decryptor` is not a registered participant [4](#0-3) 
2. After the message decrypts to a canonically valid scalar, `blame_internal` indexes `self.commitments[&sender]` — panics if `sender` is not a registered participant [5](#0-4) 

The message bytes (`msg: EncryptedMessage<C, SecretShare<C::F>>`) are fully attacker-controlled via `EncryptedMessage::read` [6](#0-5) . The only gate before the panicking lines is the PoP signature check, which the attacker satisfies trivially since they choose `msg.key` and sign it themselves [7](#0-6) . Notably, `Commitments::read` itself does not verify the PoK, and no participant-range validation is performed on `sender`/`recipient` anywhere along the path — unlike `sign()`/`view()` in FROST, which explicitly reject out-of-range and duplicate participants [8](#0-7) .

### Impact Explanation
Any node evaluating a blame accusation (e.g., the `VerifyBlame` flow, which calls `AdditionalBlameMachine::new(...).blame(accuser, accused, ...)` with message-supplied `accuser`/`accused` values) will panic rather than return an error, crashing the processor/verifier handling the accusation. This is a denial-of-service reachable purely from public inputs: a blame claim, an `EncryptedMessage` the attacker serialized, and a `sender`/`recipient` index outside `1..=n` — directly analogous to the CVE's "invalid input causes invalid dereference → crash".

### Likelihood Explanation
Blame evaluation is an unauthenticated-input path: anyone can submit a `VerifyBlame`-style request naming arbitrary participant indexes together with arbitrary ciphertext bytes. Constructing the trigger requires only generating a valid Schnorr PoP over a self-chosen key (public operations) and choosing `sender`/`recipient` > n or a valid-scalar encrypted share. No key material, collusion, or honest-party misbehavior is needed.

### Recommendation
At the top of `blame_internal` (or `BlameMachine::blame`/`AdditionalBlameMachine::blame`), validate `sender` and `recipient` are registered participants (e.g., `self.commitments.contains_key(&sender)` / `self.encryption.enc_keys.contains_key(&decryptor)`) before any map indexing, and return the accusing/accused party or a new `PedPoPError` variant instead of panicking. Replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `get()` + explicit error handling so malformed accusations can never abort the process.

### Proof of Concept
```rust
// Setup: a 3-of-3 PedPoP session completes, yielding commitments for
// participants 1..=3 and an AdditionalBlameMachine (or BlameMachine).
let machine = AdditionalBlameMachine::<Ristretto>::new(context, 3, commitment_msgs).unwrap();

// Attacker crafts an EncryptedMessage with their own ephemeral key and a
// valid PoP (e.g., by calling encrypt() for a scalar-1 SecretShare, or by
// signing pop_challenge themselves), serialized and re-read via
// EncryptedMessage::read -- all public operations.

// Trigger 1: valid `recipient` in 1..=3, `sender` = Participant(0xffff).
// The PoP verifies (attacker signed it), decryption succeeds, the share is a
// canonical scalar, and `self.commitments[&sender]` panics (missing key).
machine.blame(Participant::new(0xffff).unwrap(), Participant::new(1).unwrap(), msg, None);
// -> thread panics at crypto/dkg/pedpop/src/lib.rs (~line 599)

// Trigger 2: `recipient` = Participant(0xffff) with proof = Some(...).
// `self.enc_keys[&decryptor]` panics inside decrypt_with_proof.
machine.blame(Participant::new(1).unwrap(), Participant::new(0xffff).unwrap(), msg, Some(proof));
// -> thread panics at crypto/dkg/pedpop/src/encryption.rs (~line 388)
```

Expected behavior: return the faulty party or a `PedPoPError`. Actual behavior: panic on `HashMap` indexing (`entry not found`), aborting blame evaluation and crashing the host — a remote DoS from unauthenticated input.
