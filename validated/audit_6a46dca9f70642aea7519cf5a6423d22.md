## Finding: Duplicate function names in a module's `FunctionHandle` table cause call-target type confusion in `Module::new`

### Summary
The bytecode verifier's `DuplicationChecker` does not enforce that self-module `FunctionHandle` entries have unique identifier names — it only rejects handles that are byte-for-byte identical (same name **and** same parameter/return signature indices) or `FunctionDefinition`s that point to the same `FunctionHandleIndex`. This lets an attacker craft (or hand-assemble, not source-compile) a `CompiledModule` where two distinct `FunctionHandle`s share the same name but different signatures/bodies, each backed by its own `FunctionDefinition`. When `Module::new` loads this module, it resolves *local* function references by **name**, not by handle index, so both handles collapse onto whichever `FunctionDefinition` was processed last. Any call site statically verified against the *first* handle's signature will, at execution time, actually invoke the *second* function's code — a genuine call-target type confusion, not merely "dead code."

### Finding Description
`DuplicationChecker::check_function_definitions` only checks that the `FunctionHandleIndex` referenced by each `FunctionDefinition` is unique, and that every self-module handle is implemented: [1](#0-0) [2](#0-1) 

The whole-table duplication check for `module.function_handles()` compares full `FunctionHandle` values (module, name, parameters, return, type_parameters); two handles with the same name but different `parameters`/`return_` signature indices are *not* duplicates by this comparison and pass verification.

In the loader, `Module::new` first builds `function_map` keyed by **name** while iterating `function_defs` (positional index): [3](#0-2) 

It then resolves every `function_handle` in the module's handle table — including ones that are *not* directly tied 1:1 to a `FunctionDefinition` position — by looking up `function_map` **by name** to build the `FunctionHandle::Local` reference used for dispatch: [4](#0-3) 

Because `HashMap::insert` silently overwrites on duplicate keys, if two handles share a name, `function_map` only remembers the last-inserted index. Every `Call`/`FunctionHandle::Local` resolution keyed by that name — regardless of which of the two original `FunctionHandleIndex` values the call instruction actually referenced — resolves to the *same* `Arc<Function>` (the last one), even though the call site was statically type-checked against the *other* handle's (different) parameter/return signature. `Module::get_function` (name-based, used by entry-point dispatch) exhibits the identical last-write-wins behavior: [5](#0-4) 

This is stronger than "unreachable first function" — it is a signature/type mismatch between what the bytecode verifier statically validated for a call site and what code actually executes at that call site, because the loader's local dispatch is name-indexed rather than handle-index-indexed.

### Impact Explanation
If reachable, this breaks the Move VM's fundamental safety invariant that a statically verified call site invokes code matching the verified signature. Executing a function body compiled/verified against a different signature than the caller expects (different parameter types/counts, different locals, different acquired resources) can lead to stack/type corruption inside the interpreter, which the Move VM otherwise assumes cannot happen post-verification. Depending on how divergent the two signatures are, this can range from a VM abort to potentially exploitable memory/type confusion within the interpreter's execution of otherwise-"safe" bytecode. This falls squarely in scope as a verifier/loader failure that allows on-chain execution of code the verifier did not actually validate for the call site that triggers it.

### Likelihood Explanation
This requires the attacker to submit hand-crafted bytecode (not simply Move-source-compiled) directly through the permissionless publish path (e.g. `code::publish_package_txn` accepting raw serialized module bytes). The Move source compiler would never emit two `FunctionHandle`s with the same name, but nothing in the deserializer or `DuplicationChecker` forbids it at the bytecode level, so a bytecode-level attacker with no special privileges can construct this input. Likelihood is moderate: it demands bytecode-crafting skill but no privileged access, code ownership, or governance action.

### Recommendation
Add an explicit duplication check in `DuplicationChecker::check_function_definitions` (or `check_function_handles`) that rejects modules where two `FunctionHandle`s pointing to the self module share the same `name` (`IdentifierIndex`), independent of their parameter/return signatures. Separately, harden `Module::new` in `modules.rs` so that `FunctionHandle::Local` resolution for handles tied to `FunctionDefinition`s uses the definition's positional index rather than a name-keyed lookup, removing the silent-overwrite hazard even if a future verifier regression reintroduces duplicate names.

### Proof of Concept
1. Hand-assemble (e.g., via `move-bytecode-source-map`/manual `file_format` construction or `move-asm`) a `CompiledModule` with:
   - Two entries in `function_handles`, both with `module = self_handle_idx` and `name` pointing to the same `IdentifierIndex`, but different `parameters`/`return_` `SignatureIndex` values.
   - Two `FunctionDefinition`s, each referencing one of the two handles, each with its own distinct bytecode body (e.g., one returns `true`, the other aborts).
2. Confirm the module passes `DuplicationChecker::verify_module` (no `DUPLICATE_ELEMENT` on `FunctionDefinition`/`FunctionHandle`, since the two handles differ in signature indices) — see the checks at: [1](#0-0) 
3. Load the module via `Module::new` and observe `function_map` contains only one entry for the shared name, mapping to the second `FunctionDefinition`'s index — verified by inspecting the insert loop: [3](#0-2) 
4. Add a caller (in the same or a dependent module) whose `Call` instruction targets the first `FunctionHandleIndex` (verified against the first signature) and assert at runtime that the interpreter actually executes the second function's body/signature — demonstrating the divergence between statically verified call target and actually-dispatched code.
