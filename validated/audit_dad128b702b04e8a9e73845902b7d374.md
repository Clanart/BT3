## Analysis

The external report's core broken invariant: **funds are credited into a shared, keyed bucket that any unprivileged party can push into, and the bucket's bounded/consumption model can silently destroy a legitimate depositor's already-paid-for value with no recovery path.**

The closest verified local analog is `pallet-bandwidth`'s FIFO subscription ledger. `on_accept` in `modules/pallets/bandwidth/src/lib.rs` accepts a `PurchaseMessage` from *any* registered `BandwidthManager` on *any* source chain, and keys the target bucket by `msg.chain`/`msg.app` taken from the message body — not by the caller's own identity. `push_subscription` (lines 400-437) appends into a `BoundedVec` capped at `MAX_SUBSCRIPTIONS` (1024); once full, it unconditionally evicts (`list.remove(0)`) the oldest live subscription — even if that subscription still has unconsumed `remaining_bytes` — and that value is gone forever (only an event is emitted for "auditability", nothing is refunded or redistributed).

Because purchases are explicitly designed to be **sponsor-able cross-chain** ("a buyer on Ethereum can credit an app on Base"), any address that can call `BandwidthManager.purchase()` on any registered source chain can target an arbitrary victim `(app_chain, app)` pair and push 1024 cheap/small purchases to evict the victim's legitimate, still-unconsumed, higher-value subscription — permanently destroying paid-for bandwidth with no depositor-side control or recovery. This mirrors the reported bug's essence: value stored in a shared bucket is irrecoverably lost due to a structural interaction (no depositors / eviction) that any unprivileged actor can trigger.

### Title
Unbounded permissionless subscription eviction causes irrecoverable loss of prepaid bandwidth - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth::on_accept` credits purchases into a `(app_chain, app)` FIFO list keyed entirely by attacker-controlled message fields, and `push_subscription` evicts the oldest entry once the list hits 1024 entries, discarding any unconsumed `remaining_bytes` permanently.

### Finding Description
`purchase()` on `BandwidthManager.sol` is a public entrypoint on every registered source chain. The resulting ISMP message's body (`PurchaseMessage`) carries `chain` and `app` fields that are decoded and used directly as the storage key (`Allowance::<T>::mutate(&msg.chain, &key, ...)`), independent of `request.source` — this is intentional "sponsorship" so a payer on one chain can credit an app on another (`modules/pallets/bandwidth/src/lib.rs:466-486`). There is no restriction tying `msg.app` to any ownership or consent by the app being credited.

`push_subscription` (lines 400-437) enforces a hard cap of `MAX_SUBSCRIPTIONS` (1024) on the FIFO list. When the cap is hit, it silently removes `list[0]` — the oldest subscription — regardless of how much `remaining_bytes` it still holds, and emits `SubscriptionEvicted` purely for observability. There is no guard preventing an attacker from filling this queue with 1024 cheap tier-one purchases aimed at a victim `(app_chain, app)` pair whose queue already holds a small number of high-value, mostly-unconsumed subscriptions. Because eviction always pops index 0 in FIFO order irrespective of value, an attacker paying the cheapest tier price can force out a victim's large legitimate purchase before it is drained by `BandwidthGate::try_consume`.

This exactly matches the reported invariant break: value legitimately paid into a shared distribution structure is permanently destroyed by an external, unprivileged, low-cost action, with no mechanism (unlike the report's suggested `renotifyRewardAmount`) to recover or redistribute the lost value.

### Impact Explanation
High — an attacker can permanently destroy another app's prepaid bandwidth allocation (a paid-for on-chain resource) by spamming cheap purchases against the victim's `(app_chain, app)` key from any registered source chain. This is a pure loss-of-funds/loss-of-service primitive reachable by any address with the price of 1024 tier-one purchases (which can be arbitrarily cheap since tier price and byte allotment are governance-set and may be small), and the loss is irreversible — there is no admin recovery function for evicted subscriptions.

### Likelihood Explanation
Medium — it requires no privileged role, no relayer/prover assumption, and no race condition beyond simply submitting purchases before the victim's app drains its queue. The economic cost scales with tier price × 1024 and the target chain's gas/dispatch cost, so it's most practical against apps using cheap tiers or against high-value apps an attacker specifically wants to disrupt (competitive griefing), which is a realistic incentive.

### Recommendation
- Restrict `push_subscription`'s eviction target to entries below a minimum "protected" remaining-byte threshold, or require the evicted entry to be fully drained/expired before eviction is allowed.
- Alternatively, gate cross-chain sponsorship (`msg.chain`/`msg.app` not matching `request.source`) behind an allowlist or a minimum purchase value, so low-cost queue-flooding against an arbitrary victim app is not economically trivial.
- Consider evicting based on lowest `remaining_bytes` rather than strict FIFO order, so eviction preferentially removes near-exhausted subscriptions instead of high-value ones.

### Proof of Concept
1. Victim legitimately purchases a large tier (e.g., TierFour, 8MB) for `app_chain = Evm(8453)`, `app = victimApp`, leaving it mostly unconsumed in the FIFO list at index 0.
2. Attacker, from any registered source chain's `BandwidthManager`, calls `purchase()` 1024 times targeting the same `(app_chain=Evm(8453), app=victimApp)` pair with the cheapest configured tier and `months = 1` each time (per `docs/content/developers/evm/bandwidth/overview.mdx` sponsorship model, the payer's source chain need not equal `app_chain`).
3. Each purchase triggers `on_accept` → `push_subscription`; once the list reaches 1024 entries, subsequent purchases evict index 0 — eventually evicting the victim's original large, unconsumed subscription, emitting `SubscriptionEvicted { lost_bytes: <victim's remaining bytes> }`.
4. The victim's paid bandwidth is permanently lost; there is no extrinsic to restore or compensate the evicted subscription. [1](#0-0) [2](#0-1) [3](#0-2)

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {

				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);

				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
