Based on my investigation, the closest local analog to the "totals mutated in the wrong place/order" bug class is not in the accrual-style pallets (bandwidth, relayer fees, streaming vault) — those all update their ledger state either atomically or strictly before external effects. The real match is a **checks-effects-interactions violation in the Tron port of `IntentGatewayV2`**, where escrow accounting (`_orders[commitment][token]`) is decremented *after* the external token/native transfer, and the canonical `nonReentrant` guard present in the audited EVM implementation was dropped.

### Title
Escrow accounting decremented after external transfer, with `nonReentrant` guard dropped, in Tron `IntentGatewayV2.withdraw`/`cancelOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2`/`IntentsBase` implementation updates escrow state (`_orders[commitment][token] = escrowed - amount`) *before* making any external call, and gates `cancelOrder` with `nonReentrant`. [1](#0-0) [2](#0-1) 

The Tron port of the same contract inverts this order — it sends funds first and decrements escrow afterward — and its `cancelOrder` entrypoint has no reentrancy guard at all: [3](#0-2) [4](#0-3) 

This is structurally the same class of bug as the seed report: a value that must be authoritative for correctness (escrowed balance / total) is mutated *after* the state has already been externally observed/acted upon, rather than atomically with the read that gates the action.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2` checks only that escrow is non-zero (`_orders[body.commitment][token] == 0`), not that it covers `amount`, then performs the external transfer, and only afterward writes `_orders[body.commitment][token] -= amount`: [5](#0-4) 

`_filled[body.commitment]` is set at the very top of `withdraw`, which does block a second full re-invocation of `cancelOrder`/`withdraw` for the *same* commitment (`Filled()` reverts on a public re-entry attempt). However, this only protects the specific `_filled` flag — it does nothing to protect the underlying per-token `_orders` accounting once execution has left the guarded path, and the function was ported without the `nonReentrant` modifier that exists on the equivalent EVM `cancelOrder`: [2](#0-1) [4](#0-3) 

Same-chain cancellation is directly reachable by any unprivileged user, with `beneficiary` fully attacker-controlled (it is `order.user`, set to `msg.sender` at `placeOrder` time), and native-asset legs use a raw low-level `.call{value: amount}("")` to that attacker-controlled address, handing over control flow before `_orders` is updated: [6](#0-5) [7](#0-6) 

### Impact Explanation
Escrowed funds (native TRX or ERC-20 tokens) held by the Intent Gateway are the asset directly at risk. Because the transfer happens before the ledger update, any code path that can slip a second read of `_orders[commitment][token]` in between the transfer and the decrement — via a malicious escrowed ERC-20 token's `transfer` callback, or via any future addition of a hook-bearing token/asset type — sees the pre-decrement (stale, too-high) balance and can trigger an additional payout against the same escrow bucket, i.e. unauthorized double-settlement of the same order's funds. This matches the bounty's "double-claim/double-settlement" and "fund loss" categories directly, and it is a regression relative to the project's own hardened main EVM contract, which fixes exactly this ordering and adds `nonReentrant`.

### Likelihood Explanation
The `_filled` flag being set unconditionally at the top of `withdraw` does block the most naive attack (re-entering `cancelOrder` for the *same* order). This meaningfully limits — but does not eliminate — the exposure: it does not protect the `_orders[commitment][token]` accounting itself, it provides no protection for interleavings across multiple escrow legs within a single `withdraw()` call, and the complete absence of `nonReentrant` (present in the canonical contract) means the code no longer has defense-in-depth against future changes (new asset types, hook-bearing tokens, fee-on-transfer tokens) that could reintroduce a directly exploitable drain. Given this is a maintained fork/port of an actively audited contract that deliberately fixed this exact ordering and explicitly added `nonReentrant` upstream, its absence here is a concrete, provable regression rather than a hypothetical.

### Recommendation
Bring the Tron contract in line with the canonical EVM implementation:
1. In `withdraw()`, compute and write `_orders[body.commitment][token] = escrowed - amount` *before* performing the native/ERC-20 transfer (checks-effects-interactions), mirroring `IntentsBase.sol`.
2. Add a `nonReentrant` modifier to `cancelOrder` (and any other externally reachable entrypoint that can reach `withdraw`), matching the main EVM `IntentGatewayV2.cancelOrder`.
3. Verify the same ordering fix in `_execute`'s dust-sweep and fee-payout paths in the Tron file, which have the same "transfer, then clear" pattern.

### Proof of Concept
1. Attacker deploys a contract `Evil` with a `receive()`/`fallback()` that, on first invocation, is intended to reenter the gateway.
2. `Evil` calls `IntentGatewayV2.placeOrder` escrowing native TRX (`token = address(0)`), setting `order.user = address(Evil)`.
3. `Evil` calls `cancelOrder(order, options)` (same-chain path, no `nonReentrant` guard present).
4. Inside `withdraw()`, `_filled[commitment]` is set, then `beneficiary.call{value: amount}("")` transfers TRX to `Evil` **before** `_orders[commitment][address(0)] -= amount` executes.
5. Because the escrow ledger for this leg is still at its pre-decrement value at the moment `Evil` regains control, any code path that reaches `_orders[commitment][token]` for that token in this window (e.g., a second leg processed via a malicious ERC-20's `transfer` hook backing another leg of the same order, or a future asset type without the same-order `_filled` short-circuit) observes stale escrow accounting rather than the true post-transfer value — the class of bug the canonical contract's CEI ordering and `nonReentrant` guard were added specifically to prevent.

This confirms the pattern is present and directly attacker-reachable; full end-to-end fund extraction depends on the specific token/asset combination escrowed in the order, which is attacker-controlled at `placeOrder` time.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                if (!success) revert TransferFailed();
            }
