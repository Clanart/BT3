## Analysis

`check_upgradability` (aptos-move/framework/aptos-framework/sources/code.move, lines 267-281) only verifies that old module names are a subset of the new module set and that the upgrade policy isn't weakened; it does not — and cannot — verify semantic behavior preservation. [1](#0-0) 

The `compat` policy is explicitly documented as a signature/layout compatibility check only: "The check only passes if a new module has (a) the same public functions (b) for existing resources, no layout change." This is a deliberate design boundary, not an oversight — the Move `Compatibility` checker and `InstructionConsistency` operate purely at the structural/type level (function signatures, struct layouts, visibility) and were never intended to enforce behavioral equivalence, which is generally undecidable for arbitrary bytecode. [2](#0-1) 

Critically, `publish_package` is invoked with `owner: &signer`, and `check_upgradability` is only reached when `old.name == pack.name` for a package already registered at that same address — i.e., the party performing the "stub-body" upgrade must already be the account/package owner performing a self-upgrade of their own code.

    fun check_upgradability(
        old_pack: &PackageMetadata, new_pack: &PackageMetadata, new_modules: &vector<String>) {
        assert!(old_pack.upgrade_policy.policy < upgrade_policy_immutable().policy,
            error::invalid_argument(EUPGRADE_IMMUTABLE));
        assert!(can_change_upgrade_policy_to(old_pack.upgrade_policy, new_pack.upgrade_policy),
            error::invalid_argument(EUPGRADE_WEAKER_POLICY));
        let old_modules = get_module_names(old_pack);

        old_modules.for_each_ref(|old_module| {
            assert!(
                vector::contains(new_modules, old_module),
                EMODULE_MISSING
            );
        });
    }
