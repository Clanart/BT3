### Title
Reward-sniping via `donateRewards`/`queueNewRewards` flush of stale `queuedRewards` at near-zero `totalStaked()` - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`_provisionReward` (invoked by both the unpermissioned `donateRewards` and the manager-only `queueNewRewards`) accumulates rewards into `queuedRewards` whenever `totalStaked() == 0`, and dumps the *entire* accumulated `queuedRewards` bucket into `rewardPerTokenStored` proportional to whatever `totalStaked()` happens to be at the moment the bucket is finally flushed. An attacker can stake a dust amount of vlMGP into a `BribeRewardPool` right when `totalStaked()` transitions from 0 to non-zero, then trigger (or wait for) the flush, capturing rewards that accrued while they held no stake at all.

### Finding Description
In `rewards/BaseRewardPoolV2.sol`: [1](#0-0) 

When `totalStaked() == 0`, any call to `_provisionReward` (via `donateRewards`, which is public and unpermissioned aside from requiring `isRewardToken[_rewardToken]`, or via `queueNewRewards`, which is manager-gated) simply adds to `rewardInfo.queuedRewards` without updating `rewardPerTokenStored`: [2](#0-1) [3](#0-2) 

The very next time `_provisionReward` runs while `totalStaked() > 0`, the whole accumulated `queuedRewards` (regardless of how long it accumulated or who deposited it) is added to the new reward and divided by the **current** `totalStaked()`:
```
if (rewardInfo.queuedRewards > 0) {
    _amountReward += rewardInfo.queuedRewards;
    rewardInfo.queuedRewards = 0;
}
rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
```
Since `BribeRewardPool` overrides `totalStaked()` to be the pool's own `totalSupply` (set only via `stakeFor`, called from `WombatBribeManager.vote`), an attacker who is the *only* (or dominant) staker at flush time receives nearly the full `rewardPerTokenStored` credit, even though the queued rewards accrued entirely before their stake existed.

Exploit flow:
1. `BribeRewardPool.totalStaked() == 0` (no votes for that pool yet), and `queuedRewards` has accumulated from prior legitimate donations/queued rewards (either from other users' `donateRewards` calls or the reward manager's periodic `queueNewRewards`).
2. Attacker calls `WombatBribeManager.vote([lp], [1])`, staking 1 wei of vlMGP via `stakeFor`, making `totalStaked() == 1`. `stakeFor` runs `updateRewards` but does not touch `queuedRewards`/`rewardPerTokenStored`, so no flush happens yet.
3. Attacker (or anyone, since `donateRewards` has no access control beyond `isRewardToken`) calls `donateRewards(1, _rewardToken)` (a dust top-up). This triggers `_provisionReward` with `totalStaked() == 1`, flushing the whole `queuedRewards` bucket into `rewardPerTokenStored`, entirely attributed to the 1-wei staker.
4. Attacker calls `claimBribe`/`getRewards`, which reads `earned()` = `balanceOf(attacker) * rewardPerTokenStored / 10**decimals` = the entire flushed reward, since attacker is essentially 100% of `totalStaked()`.

Existing checks (`onlyManager` on `queueNewRewards`, `onlyOperator`/`onlyMasterMagpie` on staking/reward-claim functions) do not prevent this because `donateRewards` is intentionally unpermissioned and the flush logic itself contains no time-weighting or snapshotting to protect against a zero-to-dust transition in `totalStaked()`.

### Impact Explanation
This is theft of unclaimed yield: rewards contributed by prior donors/reward managers during a period when no one had voted for a pool are redirected almost entirely to whoever stakes a trivial amount right before the next `_provisionReward` call, at the expense of legitimate future voters who would otherwise have earned a fair share of that reward pool proportional to their real stake. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
- Requires only holding any positive vlMGP balance (even 1 wei) — no privileged role needed.
- Requires a `BribeRewardPool` with `totalStaked() == 0` and non-zero `queuedRewards`, a state that naturally occurs whenever a bribe/pool has rewards deposited before receiving its first vote, or after all voters withdraw between reward deposits.
- The attacker can force or wait for the triggering `_provisionReward` call themselves via the unpermissioned `donateRewards` function (dust amount), making the attack fully self-contained and repeatable across any bribe pool that fits this pattern.
- Capital required is negligible (dust vlMGP stake + dust donation amount).

### Recommendation
Do not flush `queuedRewards` proportional to instantaneous `totalStaked()` after a zero-stake period. Options:
- Snapshot/timestamp `queuedRewards` and distribute them pro-rata to stakers based on a time-weighted or checkpointed stake, not the stake at the moment of the next `_provisionReward` call.
- Require a minimum bonding/warm-up period after staking before a user's `balanceOf` counts toward `rewardPerToken` distribution of pre-existing `queuedRewards`.
- Alternatively, refuse to flush `queuedRewards` into `rewardPerTokenStored` within the same block/transaction sequence as a stake change, or require `totalStaked()` to exceed a minimum threshold before flushing to prevent dust-stake domination.

### Proof of Concept
Foundry test plan:
1. Deploy `BribeRewardPool` (or via `WombatBribeManager` for a given LP) with `totalStaked() == 0`.
2. Have a non-attacker account call `queueNewRewards`/`donateRewards` several times to build up `queuedRewards = Q` while `totalStaked()` stays 0.
3. Attacker calls `WombatBribeManager.vote([lp], [1])` to stake 1 wei.
4. Attacker calls `donateRewards(1, rewardToken)` to trigger the flush.
5. Assert `BribeRewardPool.rewards(rewardToken).queuedRewards == 0` and `earned(attacker, rewardToken) ≈ Q` (minus dust), i.e., attacker captures nearly all of `Q` despite contributing 0 to its accrual.
6. Compare against a control scenario where a legitimate voter stakes a large amount before rewards are queued — showing their `earned()` share is proportionally correct — to demonstrate the disparity/injustice caused by the timing-dependent flush.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
