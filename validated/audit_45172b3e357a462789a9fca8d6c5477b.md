### Title
Decimal-scaling direction bug in HyperFungibleToken lets a user mint/burn amounts inflated by 10^n on the counterparty chain - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The external report's core broken invariant is: *a numeric value can silently take an equivalent-looking-but-different form across a scalar boundary, and no constraint forces the two forms to agree, so a check that trusts one form is bypassed.* The local analog is in `pallet-hyper-fungible-token`'s ERC20-decimal ↔ local-balance conversion helpers. These helpers compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)` and only ever apply it in one direction (multiply in `convert_to_erc20`, divide in `convert_to_balance`). When `local_decimals > erc_decimals`, `saturating_sub` clamps to `0`, so the required decimal correction (`10^(local_decimals - erc_decimals)`) is silently skipped instead of applied in the opposite direction. The amount that is escrowed/burned on one chain and the amount that is minted/refunded on the other chain then differ by exactly that missing factor, with no additional constraint anywhere in the dispatch path to catch the mismatch.

### Finding Description
`convert_to_erc20` and `convert_to_balance` are the only place amount precision is translated between a local asset's decimals and the ERC20 representation registered for a `(asset_id, destination)` pair: [1](#0-0) 

Both functions assume `erc_decimals >= local_decimals` is always true, because they compute the exponent as `erc_decimals.saturating_sub(local_decimals)`. `saturating_sub` returns `0` whenever `local_decimals > erc_decimals`, which means the exponent becomes `0` (multiplier/divisor `1`) instead of the correct `10^(local_decimals - erc_decimals)` in the opposite direction. There is no validation anywhere that enforces `erc_decimals >= local_decimals` for a registered pair.

This helper is invoked directly in the fund-moving paths with no secondary check:

- `send()` escrows/burns `params.amount` (in local decimals) from the caller, then calls `convert_to_erc20(amount, erc_decimals, decimals)` to build the cross-chain `Message.amount` that will be minted on the destination: [2](#0-1) 

- `on_accept()` (inbound mint) and `on_timeout()` (inbound refund) both call `convert_to_balance(U256::from_big_endian(&message.amount...), erc_decimals, decimals)` and mint/transfer whatever value comes back, with no plausibility check against the amount actually escrowed: [3](#0-2) [4](#0-3) 

`Precisions` (the `erc_decimals` map keyed by `(asset_id, destination)`) is set by governance/`CreateOrigin`, but nothing in the codebase I could locate constrains it to be `>= local_decimals` for every registered destination — the search for a setter/validation turned up only usages, not a bound (this is a point I could not fully verify given tool-call limits; a Devin session with full repo access should confirm the exact extrinsic that writes `Precisions` and check whether it validates decimal ordering).

### Impact Explanation
If any registered `(asset_id, destination)` pair has `local_decimals > erc_decimals` (a realistic configuration — e.g., a locally-native asset with 18 decimals bridged to a remote representation registered with 6 decimals, mirroring common stablecoin conventions), then:
- On `send()`, the full local-decimal-precision amount is forwarded unscaled as if it were already in the smaller erc-decimal precision, causing the destination `onAccept`/local `on_accept` mint to receive `10^(local_decimals - erc_decimals)` times more raw units than the value actually escrowed — an unauthorized inflation of minted value that a user fully controls.
- Symmetrically, `on_accept`/`on_timeout` on the receiving/refund side divide by `1` instead of the correct larger divisor, again mismatching the amount actually locked/burned on the counterparty chain versus the amount released locally.

This is a direct "loss of funds / unauthorized value creation" primitive reachable by any unprivileged, signed caller of the public `send()` extrinsic — no relayer, prover, or governance compromise is required, only a plausible precision-mismatched configuration of the bridge for a given asset/destination pair.

### Likelihood Explanation
Exploitability depends entirely on governance having registered a `(asset_id, destination)` pair where `erc_decimals < local_decimals`. This is plausible because decimals for native/local assets (10, 12, 18) commonly differ from a remote ERC20 mirror's configured decimals, and the code contains no assertion preventing this ordering. Given the helper is unconditionally trusted with no runtime sanity check comparing escrowed vs. minted value, likelihood is Medium-High wherever such a configuration exists, and the actual presence of such a misconfigured pair in production could not be confirmed without further repo access.

### Recommendation
- Fix `convert_to_erc20`/`convert_to_balance` to scale correctly in both directions: compute `let diff = erc_decimals as i16 - local_decimals as i16;` and multiply or divide by `10^|diff|` depending on sign, instead of relying on `saturating_sub` to silently clamp negative differences to zero.
- Add an invariant check (either at `Precisions` registration time or at conversion time) that rejects/flags configurations where decimal handling could lose or gain precision unexpectedly, and add unit tests for the `local_decimals > erc_decimals` case analogous to the existing tests for the `erc_decimals > local_decimals` case in `pallet_hyper_fungible_token.rs`.

### Proof of Concept
1. Governance registers a local asset with `local_decimals = 18` and configures `Precisions::<T>::insert(asset_id, destination, 6)` (erc_decimals = 6) for some EVM destination — a plausible real-world setup.
2. A user calls `HyperFungibleToken::send` with `amount = 1_000_000_000_000_000_000` (1 whole token, 18-decimal units), which is escrowed/burned locally in full (see `send()` at `modules/pallets/hyper-fungible-token/src/lib.rs:257-290`).
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes exponent `6u8.saturating_sub(18) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18` (unscaled) instead of the correct `1e18 / 10^12 = 1_000_000`.
4. The destination `HyperFungibleToken.sol`/mirrored pallet mints `message.amount = 1e18` raw units interpreted at its own 6-decimal precision, i.e. `1e18 / 10^6 = 1e12` whole tokens — a trillion-fold inflation relative to the 1 token actually escrowed. [5](#0-4) [6](#0-5)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
