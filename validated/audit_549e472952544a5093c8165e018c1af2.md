## Analog Found: Nested/Recursive Precompile Calls Cause Duplicate Application of Bank Balance-Change Events to the EVM StateDB

### Title
Nested precompile calls cause double-application of bank `CoinSpent`/`CoinReceived` events to StateDB, duplicating spendable EVM balance — (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The Perennial `closable` bug is fundamentally a class of "cumulative range recomputed incorrectly across nested/overlapping state windows" bug — an outer computation re-scans a range of state that an inner computation already consumed/accounted for, corrupting the final result. The Cosmos EVM analog is in the precompile `BalanceHandler` mechanism: `BeforeBalanceChange`/`AfterBalanceChange` record a starting index into the transaction's cumulative, monotonically-growing `EventManager` event log and slice `events[prevEventsLen:]` to mirror bank balance changes into the EVM `StateDB`. When a precompile call recursively (re-entrantly) triggers another precompile call that also moves funds, the inner call's `AfterBalanceChange` consumes and applies its sub-range of events to `StateDB` immediately, but the outer call's `AfterBalanceChange` — because it computed its start offset *before* the inner call ran — re-scans the same absolute event range on return and re-applies the same `CoinSpent`/`CoinReceived` deltas to `StateDB` a second time.

### Finding Description
Every stateful precompile call goes through `Precompile.runNativeAction` [1](#0-0) , which:
1. Creates a `BalanceHandler` and calls `BeforeBalanceChange(ctx)`, recording `prevEventsLen = len(ctx.EventManager().Events())` [2](#0-1) .
2. Executes the precompile's native `action`, which may itself invoke another precompile (e.g. via `CallEVMWithData` for a nested EVM call, or a Solidity `_beforeTokenTransfer` hook that calls `DISTRIBUTION_CONTRACT.claimRewards` from inside an ICS20 transfer precompile call, as exercised in `ics20_recursive_precompile_calls_test.go`) [3](#0-2) .
3. Calls `AfterBalanceChange(ctx, stateDB)`, which iterates `events[bh.prevEventsLen:]` and applies `stateDB.AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived`/fractional-balance event found in that slice [4](#0-3) .

Because `ctx.EventManager()` is shared across the entire nested call chain (the same cache context is threaded through recursive precompile invocations), the event log is a single, cumulative, ever-growing list. When an inner precompile call runs to completion inside the outer call's `action`, it captures its own `prevEventsLen` (say `N1 >= N0`, where `N0` is the outer's starting offset) and applies `events[N1:N1+k]` to `StateDB` for its own bank moves. Execution then returns to the outer call, which resumes and eventually calls its own `AfterBalanceChange`, re-scanning `events[N0:]` — a range that **still includes** the events at `[N1:N1+k]` already consumed and applied by the inner call. The outer handler has no way of knowing that a nested call already processed part of its range, so it reapplies `AddBalance`/`SubBalance` for the same bank events again.

The test suite explicitly documents this class of bug: `evmd/tests/integration/balance_handler/balance_handler_test.go` states the mechanism is fragile under "recursive precompile calls [that] share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB" [5](#0-4) , and `ics20_recursive_precompile_calls_test.go` separately documents "the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [3](#0-2) . A legacy variant of the debug precompile (`testutil/testdata/debug/debug.go`) still stores a single `BalanceHandler` on the precompile struct itself (`p.GetBalanceHandler()`), a pattern that directly reproduces the shared-instance overwrite described by the tests [6](#0-5) ; even the "fixed" per-call `BalanceHandlerFactory` pattern in production `precompiles/common/precompile.go` does not fix the deeper overlapping-window problem because the underlying `ctx.EventManager()` event log is never partitioned/consumed — only sliced by index — across nested calls.

### Impact Explanation
Any Solidity contract that funnels through a balance-moving precompile (staking delegate/undelegate, distribution reward claim, bank send precompile, ERC-20 precompile transfer, ICS-20 transfer precompile) from within a re-entrant/nested call path (a token hook, a `try/catch` recursive call, or an EVM `CallEVMWithData` inside a precompile's native action) can cause the EVM-visible `StateDB` balance for an account to be credited or debited a second time for the same underlying `x/bank` coin movement. Since `StateDB` balances are what subsequent EVM operations (transfers, precompile calls, ultimately `Commit()` into the persisted EVM/bank state) rely on, this is a duplication of spendable value in the EVM-visible balance relative to the actual backing `x/bank` balance — an unauthorized duplication/accounting-corruption of spendable user value, matching the Critical impact gate ("unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances"). An attacker who controls a contract that recursively triggers fund-moving precompile calls (e.g. an ERC-20 token with a `_beforeTokenTransfer` hook that also claims staking rewards, combined with an outer precompile-driven transfer) can inflate their own EVM balance beyond what is actually backed by bank coins, then use the inflated EVM-side balance to transfer real value out, effectively creating unbacked spendable balance.

### Likelihood Explanation
The trigger is fully within reach of an unprivileged EVM user: deploy an ordinary Solidity contract that combines a token hook or `try/catch` pattern with calls into stateful precompiles (staking, distribution, ERC-20, ICS-20), a pattern the repository's own test suite already constructs and exercises (`ics20_recursive_precompile_calls_test.go`, `balance_handler_test.go`, `StakingReverter.sol`'s `nestedTryCatchDelegations`). No validator, relayer, or privileged key is required — only a contract deployment and a single transaction that recurses through precompiles.

### Recommendation
Do not rely on a monotonically-growing, globally shared `EventManager` sliced by absolute index across nested precompile invocations. Instead, either (a) consume (drain/mark) events as they are processed by an inner `AfterBalanceChange` so an outer handler cannot reprocess them, or (b) track and apply balance deltas via a dedicated, call-scoped ledger of "pending" balance deltas that is properly stacked/popped per call-depth (similar to how `StateDB.Snapshot()`/`RevertToSnapshot()` already stack precompile calls), rather than reasoning about "everything since my start index" against a log other callers may also drain from.

### Proof of Concept
The repository's own integration tests already demonstrate the reachable path (though calibrated only to prove event/counter behavior, not yet to assert on a StateDB/bank balance mismatch for value-moving precompiles):
- `evmd/tests/integration/balance_handler/balance_handler_test.go` deploys `DebugPrecompileCaller.sol`, which recursively re-enters the debug precompile via `evmKeeper.CallEVMWithData` [7](#0-6) , demonstrating that nested precompile calls share the same underlying event log and that `prevEventsLen` bookkeeping is not properly isolated per call depth.
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`'s `"test recursive precompile call with reverts"` case combines an ICS20 transfer precompile call with a contract whose `_beforeTokenTransfer` hook recursively invokes the Distribution precompile (`claimRewards`) in a `try/catch` loop [8](#0-7) , exactly the value-moving nested-precompile scenario needed to reproduce duplicate `AddBalance`/`SubBalance` application to `StateDB`.

To fully confirm double-counting of a value-moving balance (rather than just events), a Devin session with repository/tooling access would need to instrument `BalanceHandler.AfterBalanceChange` (or add an assertion comparing `stateDB` balance to `x/bank` balance after a recursive staking/distribution/ICS20 call) — this exceeds what can be verified via static code reading alone, but the code paths and existing test scaffolding strongly indicate the vulnerability is reachable in production precompiles, not just the debug/test precompile.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
