### Title
Stale line-selection indices are reapplied to a freshly re-fetched diff during partial commits, silently staging the wrong lines - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets users stage a subset of lines from a file (`DiffSelection`) computed against a specific diff snapshot shown in the UI. When the commit is actually created, the staging code does not reuse that reviewed diff — it independently re-fetches the working-directory diff from disk and reapplies the old line-index selection to it. If the file's diff shape (hunk boundaries/line offsets) has changed between the two fetches, the line indices no longer point at the same logical lines, so `git apply --cached` stages content the user never selected, while excluding content they did select — the same "operate on stale state after something has mutated the real state" class of bug as the reported `rebalance` issue, just with the working tree/diff as the "balance" instead of token reserves.

### Finding Description
The commit flow is:
1. `_commitIncludedChanges` (app-store.ts) reads `state.changesState.workingDirectory.files`, filters to files with a selection, and passes them straight to `createCommit`: [1](#0-0) 

2. `stageFiles` routes any file with a partial selection to `applyPatchToIndex`: [2](#0-1) 

3. `applyPatchToIndex` **re-fetches the diff from the current on-disk state** — a brand new `git diff` invocation — rather than using the diff object that was displayed to the user and against which `file.selection` was built: [3](#0-2) 

4. `formatPatch` then walks this newly-fetched diff and decides which lines to include purely by `absoluteIndex = hunk.unifiedDiffStart + lineIndex` compared against `file.selection.isSelected(absoluteIndex)`: [4](#0-3) 

There is a reconciliation step, `updateChangesWorkingDirectoryDiff`, that re-fetches the diff whenever the UI refreshes and remaps the selection to the new diff's selectable lines: [5](#0-4) 

But this reconciliation only runs on UI-triggered refreshes (`_loadStatus`, file selection changes, etc.) — it is not invoked immediately before `applyPatchToIndex` performs its own independent diff fetch at commit time. That means there is a window between "last reconciled selection" and "actual `git apply --cached`" where the on-disk file can change again (e.g. an app filesystem watcher-triggered refresh lands after reconciliation, a background operation like a fetch/checkout of a submodule touches the file, or `core.autocrlf`/a `.gitattributes` `clean` filter defined by the repository normalizes content differently on successive invocations of `git diff`), and the freshly-fetched diff in `applyPatchToIndex` no longer has the same hunk layout that the `DiffSelection` bitmap was built against. Since `formatPatch` blindly indexes into the new diff by absolute line offset, hunks that shifted position will cause unrelated lines to be marked "selected" and staged instead of the ones the user actually checked.

### Impact Explanation
This is exactly the "silently corrupt what the user commits or pushes" impact category: a user believes they are committing only the lines they explicitly checked in the diff viewer, but Desktop can stage and commit different lines than what was reviewed and selected, without any error or warning. Because `git apply --cached --unidiff-zero` succeeds as long as the (now-stale) selection produces a structurally valid patch against the freshly-diffed content, there is no failure signal to the user — the corruption is silent.

### Likelihood Explanation
Triggering the underlying diff-shape change requires content in the repository (or a repository-provided `.gitattributes` filter/attribute) to cause `git diff` output to differ between two closely-timed invocations, or a normal background refresh (file watcher, another git operation) to touch the file in the window between the UI's diff/selection reconciliation and the commit's own re-fetch. This does not require local/physical access or leaked credentials — it is driven by content in a repository the user has cloned and is actively editing, which matches the "attacker controls a cloned/fetched repository" trigger category. Likelihood is Medium: it needs a specific race window and a diff-shape-changing condition, but no unusual user interaction beyond normal partial-line committing.

### Recommendation
`applyPatchToIndex` (and `stageFiles`) should not silently re-fetch and reuse a `DiffSelection` against a different diff snapshot. Either:
- Pass the exact `IDiff` that was reconciled with the selection (from `changesState.selection.diff`) into `stageFiles`/`applyPatchToIndex` instead of re-fetching it from disk, or
- If a fresh diff must be fetched at staging time, re-run the same selectable-line reconciliation (`withSelectableLines`) against it immediately before calling `formatPatch`, and abort/re-prompt the user if the reconciled selection differs materially from what was displayed.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked text file so it has multiple hunks.
2. In the Changes view, partially select a specific line/hunk to commit (leaving other hunks unselected). Desktop computes `DiffSelection` against the diff it fetched for display (`updateChangesWorkingDirectoryDiff`).
3. Before clicking "Commit", have something rewrite the file so that the hunk layout shifts (e.g., a script mimicking a `clean` smudge filter run by another `git` command, or simply appending/removing lines above the selected hunk via an external editor/process) — repository-driven content or attributes can be engineered to make this happen automatically as part of normal git plumbing calls Desktop issues (e.g. `git diff` vs. `git apply --cached` observing different filtered content).
4. Click "Commit". `applyPatchToIndex` fetches a new diff via `getWorkingDirectoryDiff` (app/src/lib/git/apply.ts:60) and `formatPatch` applies the old absolute-line-index selection to it (app/src/lib/patch-formatter.ts:143-171).
5. Inspect the resulting commit: it contains lines from the shifted hunks that the user never checked in the UI, while the actually-selected lines may be dropped — demonstrating silent corruption of committed content, analogous to `rebalance` depositing an incorrect (stale-derived) liquidity amount after the swap changed the real balances.
