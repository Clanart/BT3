### Title
Attacker-triggered spoofing of Serai's internal output types via script_pubkey-only matching lets an unprivileged party inject Branch/Change outputs and manipulate the multisig's reserve accounting - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The incident class is "an unprivileged caller triggers an internal mechanism (token burn) that manipulates the protocol's view of reserves." The Serai analog is `Scanner::scan_transaction`: it attributes received outputs purely by `script_pubkey` match, and every internal offset (Branch, Change, Forwarded) is a deterministic, publicly-computable function of the public group key. Any Bitcoin user can therefore craft a transaction that Serai classifies as its own internal output type, injecting attacker-funded UTXOs into the internal accounting paths reserved for change and branch/rotation flows.

### Finding Description
`Scanner::scan_transaction` scans every transaction output and reports a `ReceivedOutput` whenever `output.script_pubkey` exists in `self.scripts`, with no authentication of who created the output (`networks/bitcoin/src/wallet/mod.rs:199-213`).

The scripts map is populated with:
- the untweaked key (`offset = 0`, `Scanner::new`, `mod.rs:162-166`), and
- offsets registered via `register_offset` (`mod.rs:180-196`).

In the processor, all offset scripts are deterministically derived from the public group key: `Secp256k1::hash_to_F(KEY_DST, b"branch")`, `b"change"`, `b"forward"` (`processor/src/networks/bitcoin.rs:308-346`). `Bitcoin::get_outputs` then maps each matched output back to its `OutputType` solely via the offset (`bitcoin.rs:686-699`) and feeds these outputs into the scheduler/scanner pipeline (`processor/src/multisigs/scanner.rs`).

Like the BCE burn, the vulnerable property is that a permissionless external action (sending an on-chain payment to a computable internal address) flips Serai into an internal-only state transition: outputs intended to originate exclusively from Serai's own transactions (Change of a just-sent plan, Branch outputs used in key rotation/completion flows) can be fabricated by a third party for the cost of the output's value plus fees.

### Impact Explanation
An attacker can send dust or larger amounts to the Branch or Change addresses, which are treated by the pipeline as Serai-internal funds/signals rather than external deposits:

- `data` (the InInstruction) is only attached to `OutputType::External` outputs (`bitcoin.rs:731-735`), so spoofed outputs bypass the external-deposit handling entirely.
- Spoofed Change outputs are injected into the wallet's spendable input set as if they were Serai's own change, distorting the reserve accounting and potentially allowing attacker-funded dust to be consolidated into future plans.
- Spoofed Branch/Forwarded outputs can trigger internal completion/rotation bookkeeping (`ScannerEvent::Completed` path in `processor/src/multisigs/scanner.rs`) without Serai having produced the corresponding plan transaction — the analog of "triggering the burn to manipulate reserves," here "triggering internal classification to manipulate which funds the scheduler believes exist and which plans completed."

Because `register_offset` is surjective and colliding scripts are rejected (`mod.rs:187-188`), the mapping of script → type is stable, so the attacker reliably controls which internal type their injected output is labeled as.

### Likelihood Explanation
- Reachability: fully unprivileged. The group key is public; offsets are `hash_to_F` of fixed strings over public data; anyone can compute `p2tr_script_buf(key + G*offset)` and pay to it.
- Cost: one Bitcoin transaction plus ≥ dust value per spoofed output.
- Attacker benefit depends on downstream handling: misclassified funds either pad Serai's apparent reserves or spoof internal lifecycle signals. At minimum this is accounting corruption reachable at will; depending on how Branch outputs gate plan completion, it can also cause incorrect fund rotation/acknowledgment decisions.
- This is not a "free money for Serai" non-issue: the threat model is manipulation of which outputs the protocol believes are internal vs. external, which is exactly the reserve-manipulation class.

### Recommendation
- Do not attribute output kind purely by script. For Branch/Change/Forwarded outputs, require evidence Serai created them: match the outpoint/txid against plan transactions Serai itself constructed (`SignableTransaction::txid()` is known in advance, `send.rs:258-263`), or require the transaction to spend at least one known Serai input.
- In `Bitcoin::get_outputs`, only emit `OutputType::{Branch,Change,Forwarded}` for transactions recorded as originating from the scheduler; treat any other payment to those scripts as `External` (or ignore entirely), and never attach attacker-controlled classification.
- Document in `Scanner`/`register_offset` that script matching alone cannot distinguish self-sent from attacker-sent outputs.

### Proof of Concept
Conceptual (regtest), mirroring `send_and_get_output` in `networks/bitcoin/tests/wallet.rs`:

```rust
// group key `key` is public; offsets are public constants
let branch_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch");
// adjust like register_offset until the tweaked key is even
let mut o = branch_offset;
while p2tr_script_buf(key + (ProjectivePoint::GENERATOR * o)).is_none() {
  o += Scalar::ONE;
}
let attacker_script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * o)).unwrap();

// attacker broadcasts a tx paying `attacker_script` — no Serai participation
// processor::get_outputs(block, key) returns:
//   Output { kind: OutputType::Branch, output: ReceivedOutput{ offset: o, ... }, data: [] }
// even though Serai never created a branch/rotation transaction.
```

The same construction with `b"change"` yields an injected `OutputType::Change` output. The primitive is guaranteed by `scan_transaction` matching `script_pubkey` only and by offsets being public; the exploit primitive is classification spoofing, which downstream scheduler code consumes as authoritative.
