Based on my investigation, I was unable to confirm a fully exploitable analog with certainty — I ran out of iterations before I could read the actual `git(['checkout', ...])` invocation inside `checkoutLocalBranch`/`_checkoutBranch` in `app/src/ui/dispatcher/dispatcher.ts` and `app/src/lib/stores/app-store.ts` to verify whether a `--` argument separator is used. I can, however, document the concrete broken-invariant I found in the validation layer, which is the strongest lead from this investigation.

### Title
Deep-link branch name validation does not reject leading `-`, permitting git argument-injection payloads to reach checkout - (File: app/src/lib/parse-app-url.ts, app/src/lib/sanitize-ref-name.ts)

### Summary
The `x-github-client://openRepo/...?branch=...` deep-link handler validates the `branch` query parameter with `testForInvalidChars()`, which blocks control characters and `~^:?*[\|""<>`, but does **not** reject a leading `-`. This differs from `sanitizedRefName()` in the same file, which explicitly strips leading `-`/`+` characters (`.replace(/^[-\+]*/g, '')`) when *sanitizing* branch names elsewhere in the app. The deep-link path only *validates* (reject/accept), it never sanitizes, so a branch value such as `--upload-pack=...` or any other leading-dash git-option-shaped string passes validation untouched and is threaded through `dispatcher.openBranchNameFromUrl` → `checkoutLocalBranch`. [1](#0-0) [2](#0-1) 

### Finding Description
This is a link-triggered, attacker-controlled input analogous to the DeFi report's "unvalidated externally-controlled value flows into a sensitive operation." Here:
1. The attacker crafts a link with protocol `x-github-client://openRepo/<url>?branch=<payload>` (a link the victim clicks, matching the valid-impact category "a link or deep link the user clicks").
2. `parseAppURL` extracts `branch` and only checks it against `invalidCharacterRegex`, which does not include `-`. [3](#0-2) 
3. `dispatcher.openBranchNameFromUrl(url, branchName)` opens/clones the repo and calls `this.checkoutLocalBranch(repository, branchName)` with the raw value. [4](#0-3) 

The exact severity depends on whether the eventual `git checkout` invocation passes the branch name after a `--` separator (which would neutralize option injection) — I was not able to verify this in the remaining budget.

### Impact Explanation
If the checkout call site does not use a `--` separator, an attacker could smuggle git options (e.g., `--upload-pack=`, other flags accepted by the specific git subcommand used) via a link click, potentially resulting in unexpected command execution or corrupting the state of the cloned repository. Even absent that, the discrepancy between "validate" and "sanitize" logic for the same class of ref names is a code-smell that should be fixed regardless, since it breaks the invariant enforced everywhere else in the codebase (leading `-`/`+` is explicitly stripped by `sanitizedRefName`).

### Likelihood Explanation
Requires the victim to click a maliciously crafted `x-github-client://` link — no prior compromise, no admin rights. This matches the accepted attack surface ("a link or deep link the user clicks"). The PR-branch path (`^pr\/\d+$`) is unaffected since it's constrained by regex, but the general (non-PR) `branch` parameter path is reachable via `openrepo` action with only `pr == null`.

### Recommendation
Apply the same leading-`-`/`+` stripping (or outright reject leading `-`) in the `openrepo` branch validation path as is done in `sanitizedRefName`, and confirm/enforce that all git invocations that take a branch name positional argument use a `--` separator before the ref name.

### Proof of Concept
```
x-github-client://openRepo/https://github.com/owner/repo?branch=--upload-pack%3D%2Ftmp%2Fpwned.sh
```
`testForInvalidChars('--upload-pack=/tmp/pwned.sh')` returns `false` (no match), so `parseAppURL` accepts it and forwards it unchanged to `openBranchNameFromUrl` → `checkoutLocalBranch`.

**Caveat:** I could not confirm within the available tool budget whether the downstream `git checkout` call uses a `--` separator that would neutralize this; this should be verified in a follow-up session before treating this as a confirmed exploit rather than a validation-layer defect.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
