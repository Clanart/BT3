### Title
Unchecked nil `AccountI` dereference in `EVMAddressDecorator.AnteHandle` can be triggered by any transaction from a signer whose stored account was removed - ([File: x/evm/ante/preprocess.go])

### Summary
`EVMAddressDecorator.AnteHandle`, part of the standard Cosmos-side ante pipeline that runs on every non-EVM (Cosmos) transaction, calls `p.accountKeeper.GetAccount(ctx, signer)` and immediately dereferences the result with `acc.GetPubKey()` without checking for `nil`.

### Finding Description
`AccountKeeper.GetAccount` is explicitly documented and implemented to return `nil` when no account is stored for the address: [1](#0-0) 

`EVMAddressDecorator.AnteHandle` calls this exact fallible accessor and dereferences the return value on the very next line with no nil guard, mirroring the drm_mode_duplicate()/drm_mode_set_name() pattern in the reported CVE (fallible pointer producer → immediate dereference with no check): [2](#0-1) 

The loop is reached for every signer of every Cosmos (non-EVM) transaction whose EVM address is not yet associated: [3](#0-2) 

An account can legitimately have no stored `AccountI` object at the time this decorator runs even though it is a valid `sdk.AccAddress` that can appear as a message signer — for example, a `sdk.AccAddress` derived from an EVM address via direct byte-casting (`sdk.AccAddress(evmAddr[:])`) that has never received funds, been associated, or otherwise triggered account creation via `SetAccount`/`NewAccountWithAddress`. The codebase's own `AssociationHelper.MigrateBalance`/legacy migration logic explicitly removes such cast accounts when they hold no locked coins, i.e. it deliberately puts these addresses back into a no-account state: [4](#0-3) 

Because the associated `EVMAddressDecorator` runs before this cleanup context and the account keeper legitimately returns `nil` for such addresses, `acc.GetPubKey()` at line 318 is a straightforward nil-interface-method-call, which in Go panics with a nil pointer dereference (`runtime error: invalid memory address or nil pointer dereference`), exactly analogous to the CVE's `drm_mode_set_name(mode)` on a NULL `mode`.

This is distinct from the many other `GetAccount` call-sites in the codebase (e.g. `precompiles/auth/auth.go:141`, `utils/helpers/associate.go:44`) which all correctly check `if acc == nil` before use — `EVMAddressDecorator.AnteHandle` is the one path that omits this check.

### Impact Explanation
A nil pointer dereference inside the ante handler causes a Go runtime panic during `AnteHandle`/`CheckTx`/`DeliverTx` processing for the affected transaction. Depending on how far up the call stack the panic is recovered (BaseApp's runTx has a top-level `recover()` that converts panics into an error response for a single transaction), the most likely outcome is that the offending transaction fails deterministically across all validators (denial for that specific account) rather than a chain halt, but because this executes inside `FinalizeBlock`/`DeliverTx` on the state-transition path, any divergence in panic-recovery behavior (e.g. gas metering interactions, or if it escapes a `recover()` boundary) can produce non-determinism or a validator crash, both of which fall in the "block delay/validator halt" impact category described in the rules. At minimum this is a reliable transaction/account-level DoS: any address in this nil-account state can never successfully be a signer of a Cosmos-native tx until its account is (re)created, since every attempt would panic in this ante decorator.

### Likelihood Explanation
The path is reachable by an ordinary Cosmos transaction sender: any `sdk.AccAddress` that is the EVM-cast form of an address (`common.BytesToAddress`/`sdk.AccAddress(evmAddr[:])`) which has never been associated or funded reaches `GetAccount` returning `nil` when it signs a plain Cosmos message. Because address association and cast-account removal are core, actively used flows in Sei's dual-address model (`utils/helpers/associate.go`), the precondition (a valid signer address with no stored account) is a normal state reachable through routine usage of the EVM/Cosmos address bridge, not a contrived edge case.

### Recommendation
Add a nil check immediately after `p.accountKeeper.GetAccount(ctx, signer)` in `EVMAddressDecorator.AnteHandle`, mirroring the pattern already used elsewhere in the codebase (e.g. `if acc == nil { ... continue/skip ... }`), before calling `acc.GetPubKey()`.

### Proof of Concept
1. Construct a Sei address `A = sdk.AccAddress(evmAddr[:])` for an arbitrary EVM address `evmAddr` that has never been associated, funded, or otherwise had `SetAccount` called for it (so `AccountKeeper.GetAccount(ctx, A)` returns `nil`).
2. Submit any ordinary Cosmos SDK transaction (e.g. a `MsgSend`) signed such that `A` is one of `sigTx.GetSigners()`, with `A` not yet associated with an EVM address (`evmKeeper.GetEVMAddress(ctx, A)` returns `found=false`).
3. `EVMAddressDecorator.AnteHandle` reaches the `else` branch, calls `acc := p.accountKeeper.GetAccount(ctx, signer)` which returns `nil`, then executes `acc.GetPubKey()` at line 318, causing a nil pointer dereference panic during ante handling of the transaction.

		return ctx, sdkerrors.Wrap(sdkerrors.ErrTxDecode, "invalid tx type")
	}
