### Title
Deterministic nonce reuse across repeated share computations under the same DkgConfirmer attempt leaks the validator's MuSig/FROST key share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives each signing session's nonces deterministically from a cached 32-byte seed keyed only by `context = (b"DkgConfirmer", attempt)` (`crypto/frost/src/sign.rs:127-141`, `coordinator/src/tributary/signing_protocol.rs:123-145`). `share_internal` rebuilds the sign machine from that same cached seed on every invocation (`signing_protocol.rs:156`). The FROST binding factor `rho` is computed over the received preprocess set, so two calls to `DkgConfirmer::share` within the same attempt that carry different preprocess maps produce two signature shares using identical nonces but different `rho`/challenge — the classic two-signature nonce-reuse equation that yields the secret share directly.

### Finding Description
- `CachedPreprocesses` is a per-context DB entry (`signing_protocol.rs:86-90`). Once set, `preprocess_internal` always re-derives the identical `nonces`/`Commitments` via `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:127-132`) and never deletes or rotates the cache.
- `share_internal` calls `self.preprocess_internal(participants).0` (`signing_protocol.rs:156`), so the same nonce pair is reloaded for every share computation in the attempt.
- In `AlgorithmSignMachine::sign`, the per-participant binding factor depends on the set of preprocesses supplied (`crypto/frost/src/sign.rs:283-318`). The map of serialized preprocesses is attacker-influenced: `DkgConfirmer::share` accepts a `HashMap<Participant, Vec<u8>>` built from other validators' published preprocesses (`signing_protocol.rs:288-309`), and `threshold_i_map_to_keys_and_musig_i_map` re-indexes whatever subset is provided (`signing_protocol.rs:208-250`).
- Nothing in `preprocess_internal`/`share_internal` binds the cache to the preprocess set or records that a share was already issued for this context. If the coordinator processes two finalized messages within the same attempt containing different participant subsets/preprocess bytes for the same `key_pair`, it emits `s1 = d + b·e·rho1 + lambda·share·c1` and `s2 = d + b·e·rho2 + lambda·share·c2` with identical `d, e`. Two linear equations in two unknowns recover the secret share. The file's own header concedes the danger: "it is explicitly unsafe to reuse nonces across signing sessions" and flags an unimplemented commitment-consistency check (`signing_protocol.rs:25-54`, "TODO" at line 51), relying solely on BFT finality to prevent distinct inputs — yet distinct (participant-subset, preprocess-bytes) pairs are legitimately produced by different validator subsets, not only by equivocation.

### Impact Explanation
Recovery of a validator's MuSig secret share. Combined with threshold-many compromised or subsequently recovered shares, this undermines the validator-set root of trust used to confirm DKG results on-chain; a single extracted share also enables blame/forgery attacks against the FROST accountability model and contributes toward full key reconstruction.

### Likelihood Explanation
An unprivileged party (any validator, or any party able to cause different preprocess sets to be finalized within one attempt) supplies distinct preprocess maps — e.g., different signer subsets or mutated-but-valid preprocess bytes. Each distinct map finalized under the same `attempt` context triggers `share()` with reused nonces. No BFT break, collusion, or privileged position is needed — just two different valid preprocess sets in one attempt, which normal subset variation produces. Medium severity fits: high impact but requires the coordinator to process two sets in the same attempt.

### Recommendation
- Key `CachedPreprocesses` by the full session transcript (hash of the sorted preprocess set + message + key_pair), not just `(b"DkgConfirmer", attempt)`, so distinct sessions force distinct seeds.
- Record a `share-issued` flag per context and refuse to sign a second time with different inputs; implement the noted TODO to verify on-chain commitments match the presumed preprocess before publishing shares (`signing_protocol.rs:50-54`).
- Alternatively, include the preprocess-set hash in the ChaCha20 seed derivation so nonce reuse across differing inputs is impossible.

### Proof of Concept
1. In attempt `A`, validator set publishes preprocess map `P1` (subset S1); coordinator's `DkgConfirmer::share(P1, kp)` emits share `s1` under nonces `(d, e)` derived from `CachedPreprocesses[(b"DkgConfirmer", A)]`.
2. A different finalized message in the same attempt carries map `P2` (subset S2 ≠ S1, or identical subset with different preprocess bytes). `share(P2, kp)` reloads the same seed → same `(d, e)`, but `rho` and the challenge differ.
3. From the public commitments `D = d·G`, `E = e·G` (identical in both shares' published preprocess at `signing_protocol.rs:147`) and the two shares, solve `s1 − s2 = lambda·share·(c1 − c2) + b·e·(rho1 − rho2)`; since `b·e` is recoverable from the public nonce combination, the secret share is extracted algebraically.
