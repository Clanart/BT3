### Title

PedPoP reveals a decryption-key blame proof before verifying the message proof-of-possession - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

`KeyMachine::calculate_share` accepts an untrusted `EncryptedMessage` and can return an `EncryptionKeyProof` before the queued proof-of-possession is verified. By copying an honest message’s encryption key and malleating its ciphertext into a non-canonical scalar, a malicious participant causes scalar decoding to fail early, obtaining a proof that also decrypts the honest message. [1](#0-0) [2](#0-1) 

### Finding Description

`EncryptedMessage::read` accepts the attacker-controlled message key, Schnorr proof-of-possession, and encrypted secret-share bytes. [3](#0-2) 

During `calculate_share`, `Encryption::decrypt` queues the proof-of-possession for later batch verification, computes the ECDH point, decrypts the ciphertext, and returns an `EncryptionKeyProof` for that ECDH point. [4](#0-3) 

The caller then attempts to decode the plaintext as a scalar and returns `PedPoPError::InvalidShare { blame: Some(blame) }` immediately on failure. [5](#0-4) 

Because this early return exits the loop, the queued statements are never checked by `batch.verify_with_vartime_blame`, so an invalid proof-of-possession cannot prevent disclosure of the returned ECDH proof. [6](#0-5) 

The proof-of-possession challenge binds the sender and encrypted message, so copying an honest message and mutating its ciphertext invalidates the copied proof. [7](#0-6) 

However, the ECDH point depends only on the copied public message key and victim’s encryption key, and the disclosed proof is sufficient to decrypt any other ciphertext using that same message key. [8](#0-7) [9](#0-8) 

### Impact Explanation

A malicious DKG participant can recover the plaintext `SecretShare<C::F>` from an honest participant’s encrypted share to the victim. These plaintexts are generated as secret polynomial evaluations and are intended to be sent only to their recipient. [10](#0-9) 

The disclosed `EncryptionKeyProof` contains the ECDH point and a DLEq proof binding it to the victim’s registered encryption key and the copied per-message key. [11](#0-10) 

`decrypt_with_proof` demonstrates that this disclosed point is sufficient to derive the ChaCha20 key and decrypt the original message. [9](#0-8) 

This is the exact key-co-option side effect the proof-of-possession was added to prevent: an attacker claims an honest per-message key, induces blame, and obtains a key that reveals the honest participant’s message. [2](#0-1) 

### Likelihood Explanation

The attacker needs only submit one syntactically valid `EncryptedMessage` in their own `calculate_share` input map entry. [12](#0-11) [3](#0-2) 

For encodings whose valid scalar range is much smaller than the encoded byte range, such as Ristretto’s 32-byte scalar encoding, flipping a high bit in the ciphertext predictably turns the decrypted plaintext into a non-canonical scalar while retaining the copied key and invalid proof. [13](#0-12) [14](#0-13) 

No knowledge of the copied message key’s discrete logarithm or the victim’s encryption secret is required because the victim performs ECDH and constructs the revealing proof before detecting the invalid proof-of-possession. [4](#0-3) 

### Recommendation

Do not construct or expose an `EncryptionKeyProof` until the corresponding message proof-of-possession has been verified. [4](#0-3) 

Restructure `calculate_share` so all proof-of-possession statements are batch-verified before scalar decoding can return a blame proof, or synchronously verify each proof-of-possession before ECDH decryption and proof generation. [15](#0-14) 

Add a regression test that copies an honest encrypted share, mutates its ciphertext to decode as a non-canonical scalar, submits it under another participant ID, and asserts that the resulting error contains `blame: None`. [16](#0-15) 

### Proof of Concept

1. During PedPoP, an honest participant sends the victim an `EncryptedMessage<C, SecretShare<C::F>>` containing per-message key `X`, proof `P`, and ciphertext `M`. The encryption uses the ECDH point derived from `X` and the victim’s encryption key. [17](#0-16) 

2. A malicious participant creates `M'` by flipping a high bit in the final scalar byte and submits `(X, P, M')` as their own encrypted share. Mutation of `M` changes the proof-of-possession challenge, so `P` is invalid. [7](#0-6) 

3. The victim’s `Encryption::decrypt` queues that invalid proof, computes the real ECDH point for `X`, decrypts `M'`, and returns an `EncryptionKeyProof` for that ECDH point. [4](#0-3) 

4. For Ristretto, the high-bit flip makes the decrypted `SecretShare` non-canonical, causing `calculate_share` to return `InvalidShare` with `blame: Some(proof)` before the batch verifier checks the invalid proof-of-possession. [5](#0-4) [16](#0-15) 

5. The attacker uses the returned proof’s `key` with `cipher(context, key)` to decrypt the original honest ciphertext `M`, recovering the honest participant’s `SecretShare`. [18](#0-17) [9](#0-8)

  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;

fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {
  Zeroizing::new(public * private.deref())
}

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);

  // Generate a new key for this message, satisfying cipher's requirement of distinct keys per
  // message, and enabling revealing this message without revealing any others
  let key = Zeroizing::new(C::random_nonzero_F(rng));

    key: pub_key,
    pop: SchnorrSignature::sign(
      &key,
      nonce,
      pop_challenge::<C>(context, pub_nonce, pub_key, from, msg.deref().as_ref()),
    ),
    msg,
  }

  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {

  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());

  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
