## Finding

### Title
Relayer-controlled body size lets a self-relaying party mint unbounded `ReputationAsset` supply - (File: `modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
`pallet-messaging-incentives` mints a fungible "reputation" asset to whichever account is recovered as the signer of a delivered ISMP message, in an amount computed as `rate * bytes`, where `bytes` is simply the summed length of the request bodies inside the message (floored at 32 bytes per request) [1](#0-0) . There is no upper bound on body size, no check that the destination module actually accepted/processed the request successfully, and no relation between the minted amount and any real economic value moved by the request. This mirrors the bug-class in the external report ("mint() unrestricted, anyone can mint as much as they want") — here the "restriction" is only a governance-set per-byte *rate*, but the *quantity* minted per call is fully attacker-controlled via the size of the request body they themselves author and relay.

### Finding Description
The mint logic lives in `FeeHandler::on_executed`: [2](#0-1) 

For every processed message, `Self::message_bytes(&mw.message)` sums `max(body.len(), 32)` over all requests in the message with no ceiling [3](#0-2) , and `Self::relayer_for` recovers the beneficiary purely from a signature the submitter attaches to their own message — i.e., the submitting relayer signs their own delivery and names themselves as the payee [4](#0-3) . The pallet then calls `T::ReputationAsset::mint_into(&relayer, amount)` with `amount = rate.saturating_mul(bytes)` and no cap [5](#0-4) .

Because the mint is keyed only to raw byte count and self-attributed signer, an actor who can get *any* well-formed, validly-proven ISMP request delivered to Hyperbridge (e.g., dispatched from a chain/app they control, or any permissionless dispatcher, with an arbitrarily large/junk `body`) and who also relays and signs it themselves, controls both sides of the reward calculation: they choose the body size (hence `bytes`) and they are the signer (hence the payee). There is no requirement that the destination module accept the request, no per-message/per-block cap, and no linkage to a real fee paid or value transferred — only that a message with a valid consensus/state proof was executed by `pallet-ismp`. This lets a relayer manufacture large, low-value/garbage requests purely to inflate their own `bytes` count and self-mint reputation tokens at a rate they don't otherwise control, unbounded except by gas/proof-relay cost.

### Impact Explanation
If `ReputationAsset` carries real transferable value (a governance/BRIDGE-denominated asset, per the pallet's own doc comment "Mints reputation tokens to the relayer that delivered each message, scaled by message size" [6](#0-5) ), this is a logic attack that inflates token supply disproportionate to genuine relay work or value delivered, diluting/stealing value from legitimate reward recipients — matching the bounty's "logic attacks" and "loss of funds" categories. It does not require a malicious relayer/prover in the "compromised infrastructure" sense; any ordinary, unprivileged party who can dispatch and relay a message can exploit this within the existing trust model.

### Likelihood Explanation
Medium-to-high: the only prerequisite is the ability to dispatch a validly-proven ISMP request (a normal, permissionless capability for many source-chain applications) and to relay/sign it. No governance, admin, or leaked-key access is needed — only the standard relayer role that `pallet-messaging-incentives` already assumes exists in the base case. The severity scales directly with the governance-set `MintPerByte` rate; the higher that rate, the more attractive maximizing `bytes` becomes.

### Recommendation
- Cap the per-message/per-request `bytes` counted toward minting (e.g., a maximum reward-eligible body size), independent of the actual dispatched payload size.
- Tie the mint to genuine, successful delivery/acceptance by the destination module rather than mere execution by the ISMP handler.
- Consider basing rewards on a fee actually paid at dispatch time (as the pallet's sibling reward flows do, e.g. `accumulate_fees`) instead of raw attacker-chosen body length, removing the attacker's ability to control both the multiplier and the beneficiary.

### Proof of Concept
1. Attacker controls (or uses) a source-chain application capable of dispatching an ISMP `PostRequest` with an arbitrarily large `body` (e.g., padded with zero bytes) to any destination, including one that will reject/ignore the request.
2. Attacker relays this message to Hyperbridge, attaching a valid signature over the request as the `signer` field, naming their own account.
3. `pallet-ismp` verifies the message's state/consensus proof and executes it, then invokes `FeeHandler::on_executed` on `pallet-messaging-incentives`.
4. `message_bytes` sums the (attacker-inflated) body length; `relayer_for` recovers the attacker's own account from their self-supplied signature.
5. `mint_into` credits `rate * bytes` reputation tokens to the attacker, regardless of whether the destination module accepted the request or any genuine value was transferred.
6. Repeating this with larger bodies/more messages lets the attacker mint an amount of `ReputationAsset` bounded only by gas costs and the per-byte rate, not by any protocol-level cap tied to real relay value.

**Note on verification limits:** I was unable to fully trace `pallet_ismp`'s `FeeHandler::on_executed` call site (`modules/pallets/ismp/src/fee_handler.rs`) within the available tool budget to confirm whether it is invoked even when the destination module's `on_accept`/dispatch reverts, or only after successful application-level processing. This affects the exact cost/ease of the attack (whether junk requests targeting a reverting module still count) but does not change the core issue: the minted amount is derived from an uncapped, attacker-controlled body-length value with a self-attested beneficiary.

	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
