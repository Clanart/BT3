## Title
Bandwidth gate irreversibly debits an app's prepaid byte allowance on every `on_accept` attempt, even when the destination-module lookup fails and the request is replayed — analogous to a "consumed capacity never restored" accounting bug — ([File: parachain/runtimes/gargantua/src/ismp.rs], [File: parachain/runtimes/nexus/src/ismp.rs], [File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`ProxyModule::on_accept` runs the bandwidth gate (`BandwidthGate::try_consume`) and irreversibly decrements the app's `remaining_bytes` **before** it has confirmed that the destination module actually exists. If the module lookup subsequently fails (`Err(anyhow!("Destination module not found"))`), the function returns `Err`, no request receipt is stored, and the ISMP handler explicitly allows the request to be **replayed** — yet the bandwidth already consumed is never restored. The result is a purchased, prepaid resource (bandwidth) that can be drained to zero for a message that never once succeeds, and this drain can be repeated indefinitely via replay by any unprivileged relayer.

### Finding Description
The bandwidth gate documentation and code establish `try_consume` as an atomic check-and-deduct on the app's FIFO subscription list: [1](#0-0) 

In both runtimes wiring `pallet-bandwidth` into the ISMP router, the gate is consulted and its mutation committed **before** the destination `pallet_id` is resolved: [2](#0-1) [3](#0-2) 

If `ModuleId::from_bytes(&request.to)` doesn't match any registered pallet, `on_accept` returns `Err("Destination module not found")` — but by that point `try_consume` has already run, and `Allowance::<T>::mutate` has already drained `remaining_bytes` from the app's live subscriptions (popping fully-drained entries). There is no compensating credit-back path anywhere in `pallet-bandwidth` (no such call exists in `try_consume`, `force_credit`, or elsewhere) for this failure mode.

Crucially, the protocol's own documented invariant for `IsmpModule::on_accept` is that failed modules must leave **no side effects**, precisely so a failed request can be safely retried without double-effect: [4](#0-3) 

And the dispatch handler confirms the mechanics: when `on_accept` errors, the just-stored request receipt is deleted, which is what enables replay: [5](#0-4) 

`ProxyModule::on_accept` violates that invariant: the bandwidth-gate deduction is an irreversible storage mutation that survives the `Err` return, and because no receipt was persisted, the exact same commitment can be resubmitted by any relayer and will re-invoke `try_consume` again, charging the app's subscription a second (and third, and Nth) time for the identical message — each attempt failing the same way at the module lookup.

### Impact Explanation
Bandwidth is a purchased, prepaid asset (paid for in real fee-token value via `BandwidthManager.purchase()`), explicitly named in the bounty scope as a balance that "must move exactly once and only to the rightful beneficiary and amount." Here, an app's paid allowance can be repeatedly and permanently debited for a message that structurally can never succeed (wrong/unregistered `to`), with:
- No refund path in the pallet.
- No cap on how many times the same failed commitment can be replayed and re-charged, since the failure path deliberately avoids persisting a receipt to allow retries.
- The action is triggerable by any unprivileged relayer resubmitting the message batch — the app owner does not need to cooperate or even be aware.

This is a direct loss of purchased protocol capacity (equivalent to loss of funds, since bandwidth was bought with the fee token) with no legitimate value delivered and no way to recover it, matching the bug-class of "capacity decremented but never restored on the corresponding failure/reversal path" from the seed report.

### Likelihood Explanation
Any app that mistypes, misconfigures, or targets a module id not compiled into the current runtime (e.g. during a module deprecation/migration, or simply typo'd `to` bytes) will trigger this on the very first delivery attempt. Once triggered, any relayer (not just malicious ones — even the honest relayer network doing its normal job of resubmitting undelivered messages) will keep re-consuming the app's bandwidth on every retry cycle until the request times out or the subscription is fully drained, whichever comes first. No special privilege, race condition, or malicious relayer collusion is required — normal operational behavior (retry-until-timeout) is sufficient to fully drain a victim app's paid balance.

### Recommendation
Move the bandwidth-gate `try_consume` call to occur only after the destination module has been successfully resolved (and ideally after the module's own `on_accept` succeeds), or make the deduction transactional/rollback-safe with the rest of `on_accept`'s failure path — e.g. wrap the routing logic with `#[transactional]` so any `Err` return reverts the `Allowance` mutation as well, restoring the previous invariant that failed `on_accept` calls have zero persistent side effects.

### Proof of Concept
1. App `A` on source chain `S` buys a bandwidth tier, crediting `Allowance::<T>[S][A]` with `N` bytes (`BandwidthCredited`).
2. `A` dispatches a POST request with `to` set to a module id that is not (or no longer) wired into `ProxyModule::on_accept`'s match arms (e.g. a deprecated/renamed pallet id).
3. Relayer delivers the request to Hyperbridge. `ProxyModule::on_accept` runs:
   - `try_consume(S, A, bytes)` succeeds, deducting `bytes` from `A`'s subscription (`BandwidthConsumed` emitted).
   - `ModuleId::from_bytes(&request.to)` matches no arm → returns `Err("Destination module not found")`.
4. Per `modules/ismp/core/src/handlers/request.rs`, the just-written request receipt is deleted because the callback errored, so the request is not marked as processed.
5. The relayer (or anyone re-submitting the same `RequestMessage`/proof before the request's `timeout_timestamp`) resubmits the identical request. `on_accept` runs again: `try_consume` deducts `bytes` a second time, fails at the same module lookup, receipt deleted again.
6. Repeat until `A`'s entire `N`-byte allowance is exhausted (`GateError::NoAllowance`/`Insufficient` on subsequent legitimate traffic) — `A` has paid for `N` bytes and received zero successful deliveries, with no refund mechanism anywhere in `pallet-bandwidth`.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

					request.from

It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
