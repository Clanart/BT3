### Title
Attacker-controlled `n` in serialized `ThresholdKeys` drives unbounded pre-allocation before any data is validated - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class (CVE-2022-25304: uncontrolled resource consumption because chunk/message counts are not limited before resources are committed) maps onto Serai's deserialization surface. In the in-scope DKG crate, `ThresholdKeys::read` accepts untrusted bytes (explicitly listed as an attack-reachable `read` API) and lets a two-byte attacker-controlled field `n` determine both a `Vec::with_capacity` pre-allocation and the number of field/group elements to read, before any consistency or upper-bound check against a realistic participant set is performed.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the wire as raw `u16`s (crypto/dkg/src/lib.rs:591-602) [1](#0-0) . `n` can therefore be any value up to 65535 supplied by an unprivileged peer feeding bytes into this `read` function. `n` is then used to:

1. Pre-allocate the constant-interpolation coefficient vector with `Vec::with_capacity(usize::from(n))` and read `n` scalars [2](#0-1) .
2. Loop `1 ..= n` performing `C::read_G(reader)?` and inserting into a `HashMap` of verification shares [3](#0-2) .

Only afterwards does `ThresholdParams::new(t, n, i)` run inside `ThresholdKeys::new` [4](#0-3) , so the memory commitment and the parsing work happen before any semantic limit is enforced. There is also no check tying `n` to the actual deployment's validator set size — real sets are far smaller than the u16 ceiling.

This mirrors the advisory pattern: a count field read from the wire drives allocation and consumption without a bound proportional to what is legitimately possible. For comparison, the same codebase demonstrates the correct pattern elsewhere: `Call::read` in the Ethereum crate explicitly notes "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" and reads in bounded chunks (networks/ethereum/src/machine.rs:51-60), and `Transaction::read` bounds `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` before allocating (coordinator/src/tributary/transaction.rs:283-296). `ThresholdKeys::read` has no equivalent guard.

### Impact Explanation
Each call lets an attacker force allocation of `n` scalar slots plus `n` group-element reads and `n` `HashMap` inserts purely from a declared `u16`. With `n = 65535` this is on the order of several MB of committed memory and tens of thousands of elliptic-curve decompression operations per message, and because `read` is a pure `io::Read` consumer there is no per-session or global limit on how many times it can be invoked — exactly the "unlimited chunks per session or in total" shape of the advisory. Sustained garbage input causes CPU burn (curve decompression dominates) and memory growth, degrading or crashing the process handling untrusted key material. This rates Medium rather than High because a single message's amplification is capped by the u16 width and by bytes actually present, not the multi-GB single-message amplification of the original CVE.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization entry point explicitly in scope as reachable from untrusted bytes, e.g., key material received or loaded from peer-supplied data. Triggering it requires only prepending a two-byte `n = 0xFFFF` to an otherwise arbitrary buffer — no valid signature, key, or protocol state is needed, since the allocation and parsing loops run before `ThresholdParams::new` rejects anything. Note: reachability depends on integrators passing peer-controlled streams into this function; I did not verify a specific caller that feeds unbounded network data into it, so the severity assumes the documented in-scope reachability premise.

### Recommendation
In `crypto/dkg/src/lib.rs`'s `ThresholdKeys::read`, validate `t`, `n`, and `i` against a sane bound (e.g., construct `ThresholdParams` or check `n <= MAX_KEY_SHARES_PER_SET` / a hard maximum like `u16::MAX`-independent limit) *before* the `Interpolation::Constant` `with_capacity` and the verification-shares loop. Ideally, defer allocation: collect into `Vec::new()` and let it grow only as bytes are actually read, mirroring the chunked-read fix used in `networks/ethereum/src/machine.rs` `Call::read`. Reject `n` values inconsistent with `t` (`t > n`, `n == 0`, `i > n`) up front.

### Proof of Concept
```rust
use std::io::Cursor;
use dkg::{ThresholdKeys, ThresholdParams, Participant};
use ciphersuite::Ciphersuite;
// Any in-scope ciphersuite, e.g. dalek Ristretto
type C = ciphersuite::ristretto::Ristretto;

fn main() {
  // Build a header: C::ID len + C::ID, then t=1, n=0xFFFF, i=1,
  // interpolation tag 0 (Constant). No scalar/point bytes follow.
  let mut buf = vec![];
  buf.extend(&(C::ID.len() as u32).to_le_bytes());
  buf.extend(C::ID);
  buf.extend(&1u16.to_le_bytes());        // t
  buf.extend(&u16::MAX.to_le_bytes());    // n = 65535, attacker-controlled
  buf.extend(&1u16.to_le_bytes());        // i
  buf.push(0);                            // Interpolation::Constant

  // ThresholdKeys::read will Vec::with_capacity(65535) for scalars
  // and then attempt 65535 read_G calls, before ThresholdParams::new
  // is ever reached. Loop this call in a handler for memory/CPU exhaustion.
  let _ = ThresholdKeys::<C>::read(&mut Cursor::new(&buf));
}
```
The amplification is modest per message (~MB-scale allocation, ~65k curve decompression attempts), but the count is unvalidated and the call is unbounded in repetition, matching the missing-rate/count-limit bug class.
