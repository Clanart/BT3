## Analysis

The report's broken invariant is: **a privileged, state-changing entry point (`_authorizeUpgrade`) has no check on who is allowed to invoke it, so any caller can redirect a trusted operation to an attacker-chosen target.**

Looking for the same invariant break in GitHub Desktop's code — an entry point that takes an attacker-controlled string (from a fetched repo, a link, or an API/URL) and forwards it into a privileged OS-level "open" operation without validating what kind of target it is — the closest analog is the `open-external` IPC handler and the shell wrappers that call it.

`ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts` accepts any string `path` from the renderer and passes it straight to `shell.openExternal(path)`. The only inspection of the string is a lowercase check used purely to decide whether to log it as "opening in browser" — it performs **no allow-listing of URI schemes** before calling `openExternal`: [1](#0-0) 

Renderer-side call sites that ultimately reach this handler take URLs sourced directly from external, attacker-influenceable content:
- `LinkButton` calls `shell.openExternal(uri)` for any `uri` prop passed to it, with no scheme validation. [2](#0-1) 
- The sandboxed markdown renderer (used for READMEs, PR bodies, issue text, etc. — attacker-controlled repository/API content) intercepts clicks and only forwards links whose `protocol` matches `/^https?:/` to `onMarkdownLinkClicked`: [3](#0-2) , and the release-notes dialog wires that straight to `shell.openExternal(url)`: [4](#0-3) 

The `http(s)`-only filter lives in the **UI layer that produces the URL**, not in the shared `shell.openExternal` wrapper or in the `open-external` IPC handler itself: [5](#0-4) . Any other caller of `shell.openExternal` / the `openExternal` proxy — including `LinkButton`, editor-error links, and any future or existing component that builds a URI from repository, PR, issue, or API data without applying the same `^https?:` filter — reaches the main process with zero server-side (main-process) enforcement of the scheme. This mirrors the `_authorizeUpgrade()` bug: the privileged action (main-process `shell.openExternal`, which on Windows/macOS can invoke arbitrary registered URI-scheme handlers) is exposed through an IPC channel that trusts the caller-supplied value completely, relying only on scattered, inconsistent client-side checks rather than a single authoritative check at the privileged boundary.

Given the IPC sender is validated (`isTrustedIPCSender`) but the **URL scheme itself is not validated at the point of privilege** (the main process), and multiple UI call sites (`LinkButton`, `PathText`) don't apply the `https?` filter that `sandboxed-markdown.tsx` does, this satisfies the required attacker model: attacker-controlled content (a PR/issue/README rendered from the GitHub API, or a link a user is enticed to click) can supply the value that finally reaches `shell.openExternal` in the main process.

### Title
Missing scheme allow-listing on `open-external` IPC handler allows arbitrary URI-handler invocation from repository/API content - (File: `app/src/main-process/main.ts`)

### Summary
The `open-external` IPC handler forwards any string it receives from the renderer directly to Electron's `shell.openExternal`, which on Windows and macOS will invoke whatever application/URI-scheme handler is registered for that string (not limited to `http`/`https`). The only scheme filtering that exists (`/^https?:/`) is implemented ad hoc inside `sandboxed-markdown.tsx` and is not enforced by the shared `shell.openExternal` wrapper, the `openExternal` IPC proxy, or the main-process handler. Components such as `LinkButton` and `PathText` call `shell.openExternal` directly with whatever `uri` prop they are given, with no scheme check at all.

### Finding Description
`shell.openExternal` is Desktop's privileged "open link/URI/file" primitive, analogous in trust level to `_authorizeUpgrade()` in the reported contract: a single choke point that should enforce what kind of destination is acceptable before performing the action. Here, that enforcement is missing at the trust boundary (main process) and instead is duplicated inconsistently across UI components:
- `main.ts`'s `open-external` handler performs no scheme check, it only logs when the string happens to start with `http://`/`https://`, and calls `shell.openExternal(path)` regardless.
- `sandboxed-markdown.tsx`'s link interceptor does restrict to `https?:` before invoking the callback that leads to `openExternal`, but this check exists only in that one component.
- `link-button.tsx`'s `LinkButton.onClick` calls `shell.openExternal(uri)` for any `uri` value passed as a prop, with no scheme restriction whatsoever.

Because `uri`/URL values rendered throughout the UI (release notes, PR/issue metadata from the GitHub API, repository content) can originate from attacker-controlled remote data, any code path that builds a `LinkButton`/similar component or otherwise calls `openExternal` from that data — without duplicating the `https?` guard that only exists in `sandboxed-markdown.tsx` — sends an unrestricted string to the main process's `shell.openExternal`.

### Impact Explanation
`shell.openExternal` with a non-`http(s)` string can invoke any URI-scheme handler registered on the OS (e.g., custom protocol handlers registered by other installed applications), or on Windows in older/misconfigured Electron/OS setups can be abused to execute local files or arguments via crafted schemes. This maps directly to the "attacker controls ... a GitHub API object [or] a link ... the user clicks ... result is code execution" clause of the report's valid-impact criteria. The blast radius depends on what URI handlers are registered on the victim's machine, but the missing check is exactly the class of "unprotected privileged operation" the seed report flags.

### Likelihood Explanation
Likelihood is moderate: exploitation requires (a) an attacker-controlled string reaching a component that calls `shell.openExternal` without the `https?` filter (e.g. `LinkButton`, `PathText`) with data sourced from a GitHub API object, repository content, or similar, and (b) the victim clicking the resulting UI element. The `sandboxed-markdown.tsx` component demonstrates the developers are aware such filtering is necessary for exactly this kind of untrusted content, but the guard is not centralized, so any other display path (current or future) that reaches `LinkButton`/`openExternal` with unsanitized data bypasses it entirely.

### Recommendation
Move the `https?`-only scheme allow-list from `sandboxed-markdown.tsx` into the single privileged choke point: enforce it inside `shell.openExternal`'s main-process implementation (the `open-external` IPC handler in `app/src/main-process/main.ts`) or in the shared `app-shell.ts` wrapper, rejecting/logging any non-`http(s)` scheme before calling `electronShell.openExternal`. This follows the same "centralize the authorization/validation check at the privileged entry point" recommendation the client applied for `_authorizeUpgrade()`.

### Proof of Concept
```tsx
// Any component rendering attacker-influenced content, e.g. a PR/issue field from the GitHub API
<LinkButton uri="somecustomscheme://payload">Click here</LinkButton>
```
1. Render `LinkButton` with a `uri` sourced from repository/API content (not filtered by the `https?` check that only exists in `sandboxed-markdown.tsx`).
2. User clicks the link; `LinkButton.onClick` invokes `shell.openExternal(uri)` unconditionally: [6](#0-5) 
3. This resolves through the `openExternal` IPC proxy to the main-process `open-external` handler, which performs no scheme check and calls `shell.openExternal(path)` directly: [1](#0-0) 
4. The OS invokes whatever handler is registered for `somecustomscheme://`, outside Desktop's control.

**Note on confidence**: I could not verify, from the indexed portion of the codebase, whether all current production call sites of `LinkButton`/`PathText` actually pass attacker-controlled (vs. static, hardcoded) URIs — the search only confirmed the components themselves lack scheme validation and that at least one analogous path (`sandboxed-markdown.tsx`) explicitly guards against exactly this risk, implying it is a recognized concern elsewhere in the codebase. A full audit of every call site would require exploring the complete file index, which may exceed this tool's indexing coverage — a Devin session with full repository access would be needed to enumerate every `LinkButton`/`openExternal` call site fed by remote data.
