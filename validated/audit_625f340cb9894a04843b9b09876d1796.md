### Title
Unprotected buyback swap (zero minimum-received) in `ArbWomUp3._deposit` mode 2 lets MEV sandwich attackers steal user WOM during conversion - (File: `wombat/ArbWomUp3.sol`)

### Summary
`ArbWomUp3._deposit` (reached via the unprivileged `incentiveDeposit` entrypoint) hardcodes the minimum-received parameter to `0` when calling `SmartWomConvert.convert` for the "smart convert" half of a user's deposit. Inside `SmartWomConvert._convertFor`, the buyback leg itself also swaps through the Wombat router with a hardcoded `0` minimum output. Combined, there is no effective slippage protection anywhere in this path, unlike the ERC5095 report's scenario where at least a (still insufficient) 1% slippage bound existed. This is a stronger instance of the same "no check that received amount is not less than provided amount" bug class.

### Finding Description
Any wallet can call `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, _mode=2)`, which invokes `_deposit`: [1](#0-0) 

For `_mode == 2`, half of the user's WOM (`toSwap`) is routed to `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` — the third argument (`_minRec`) is hardcoded to `0`. That call reaches `SmartWomConvert._convertFor`: [2](#0-1) 

Here, the buyback portion of the funds is swapped through `IWombatRouter.swapExactTokensForTokens(...)` with the router-level minimum output **also hardcoded to `0`**, and the subsequent overall check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` is a no-op because `_minRec` was passed in as `0` by `ArbWomUp3`. Consequently, the caller receives no protection whatsoever from either the low-level swap or the high-level "received vs. expected" check — the analog of the ERC5095 issue, but without even the partial (1%) slippage bound the original report criticized as insufficient.

### Impact Explanation
A user calling `incentiveDeposit(..., _mode = 2)` has half of their WOM swapped for mWOM through an AMM leg that can be sandwiched to receive an arbitrarily small `amountRec`, since no minimum-output is enforced at either the router call or the aggregate check. This results in a direct, immediate, and permanent loss of a portion of the user's deposited principal to an MEV/sandwich attacker — a concrete theft of user funds reachable by any ordinary wallet using the intended deposit flow, not a privileged or governance action.

### Likelihood Explanation
Likelihood is high: `incentiveDeposit` with `_mode = 2` is a normal, documented user-facing deposit path (locking mode) and requires no special permissions. Any MEV searcher monitoring the mempool can sandwich the `buybackAmount` swap in `SmartWomConvert._convertFor` because both the router-level and converter-level minimum-out checks are effectively disabled (`0`) for this call path.

### Recommendation
Do not hardcode `_minRec` to `0` in `ArbWomUp3._deposit`'s mode-2 branch. Instead, compute an expected output (e.g., via `SmartWomConvert.estimateTotalConversion`) off-chain or on-chain and pass a caller-supplied, validated minimum, and propagate a non-zero minimum-output through to the router swap in `SmartWomConvert._convertFor` rather than hardcoding `0`. At minimum, enforce `obtainedmWomAmount >= convertAmount` type invariant analogous to the `require(returned > a)` fix recommended in the referenced report, so users cannot receive strictly less value than what an unmanipulated swap would return.

### Proof of Concept
1. User calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, false, 2)`.
2. `_deposit` splits `amount` in half; the swap half (`toSwap`) is sent to `SmartWomConvert.convert(toSwap, convertRatio, 0, 0)`.
3. `_convertFor` computes `buybackAmount` and calls `IWombatRouter.swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` — `0` minimum out.
4. An attacker front-runs this transaction, manipulating the WOM/mWOM pool price, then back-runs it to restore price, extracting the difference between fair value and the manipulated `amountRec`.
5. Because `_minRec` passed from `ArbWomUp3` is `0`, the post-swap check `convertAmount + amountRec < _minRec` never reverts, so the user's transaction succeeds despite receiving far less mWOM than expected, and the shortfall is permanently lost to the attacker.
