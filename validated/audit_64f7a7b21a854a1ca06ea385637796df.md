## Analysis

The external report's core broken invariant: **residual native ETH returned by an external swap/call is not tracked and forwarded back to the paying user, so it becomes permanently stuck in the calling contract.**

I found the same broken invariant in `EvmHost.sol`'s fee-payment logic, and unlike `IntentGatewayV2.sol` (which does the correct pattern), `EvmHost` never re-captures or refunds the leftover ETH.

### The good pattern (for contrast)
In `IntentGatewayV2.sol`, when the fee is paid in native token, the code explicitly deducts the amount actually spent by the swap and forwards anything left over to `msg.sender`: [1](#0-0) 

### The broken pattern
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value`, hand the *entire* value to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), ...)`, and never account for what the router returns: [2](#0-1) [3](#0-2) 

Uniswap V2 Router's `swapETHForExactTokens` refunds `msg.value - amounts[0]` to its immediate caller (`msg.sender` of *that* call), which here is `EvmHost` itself (`address(this)`), not the original transaction sender (`_msgSender()`). `EvmHost` has no logic after the swap that measures its own ETH balance delta and forwards the difference to `_msgSender()`. There is no `receive()`-triggered accounting or later refund step in this function.

### Title
Overpaid native-token fee in `EvmHost.dispatch()` is refunded to the Host contract instead of the caller and becomes permanently stuck - (evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap the caller's full `msg.value` for the fee token via `swapETHForExactTokens`, but any unused ETH (`msg.value - amounts[0]`) returned by the router lands on `EvmHost` itself rather than being forwarded to the original caller, permanently trapping the overpayment.

### Finding Description
When a `HyperApp` dispatches a POST or GET request and pays with native token, `EvmHost` executes:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [2](#0-1) 

The router's `swapETHForExactTokens` computes `amounts[0]` needed to buy exactly `post.fee` of the fee token, performs the swap, and refunds `msg.value - amounts[0]` to whoever called it — in this case `EvmHost`, since `EvmHost` itself made the external call. The overpaying user never receives their unused ETH back: `EvmHost` neither measures a balance delta before/after the swap call nor forwards any surplus to `_msgSender()`. The exact same defect exists in the sibling `dispatch(DispatchGet)` function: [3](#0-2) 

This is structurally identical to the H-3 pattern: an external call (Notional's `batchBalanceAndTradeAction` / here, Uniswap's `swapETHForExactTokens`) returns residual native ETH to the calling contract, and the calling contract's downstream logic (`_sendTokensToReceiver` / here, the rest of `dispatch`) never accounts for or forwards that residual back to the rightful owner.

Contrast this with `IntentGatewayV2.sol`, which correctly tracks `msgValue`, deducts what the swap actually consumed (`amounts[0]`), and explicitly refunds the remainder to `msg.sender`: [1](#0-0) 

`EvmHost.dispatch` has no equivalent refund step, so any caller who sends more native token than the exact amount required to purchase `post.fee`/`get.fee` worth of fee token loses the difference — it accumulates as stray ETH inside `EvmHost`, recoverable only through the privileged `withdraw()` governance path (`IHostManager.withdraw`), not by the user who overpaid.

### Impact Explanation
Any unprivileged application or end-user that calls `dispatch(DispatchPost)`/`dispatch(DispatchGet)` with native token and does not send the *exact* wei amount the router will consume (which is generally unknowable in advance without an off-chain quote, since AMM price can move between quote and execution) permanently loses the difference. This is a direct, self-inflicted loss of funds bug reachable by any normal user of the bridge's core dispatch entrypoint — the same functions documented as the standard way to pay Hyperbridge fees in native token.

### Likelihood Explanation
High. Overpayment is the normal/expected case for a fee paid via AMM swap (users must send enough headroom to cover slippage since they cannot predict the exact swap price at execution time), exactly as documented: [4](#0-3) 

Every caller using native-token fee payment through `EvmHost.dispatch` directly (rather than through wrapper apps like `IntentGatewayV2` that implement their own correct refund logic) will systematically lose any overpaid amount, with no attacker action required.

### Recommendation
Snapshot `EvmHost`'s native balance immediately before invoking `swapETHForExactTokens`, and after the swap, compute the delta and forward any residual ETH to `_msgSender()` (or the equivalent `payer`), mirroring the pattern already used correctly in `IntentGatewayV2.sol`:
```solidity
uint256 balanceBefore = address(this).balance - msg.value;
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 refund = address(this).balance - balanceBefore;
if (refund > 0) {
    (bool sent,) = _msgSender().call{value: refund}("");
    require(sent, "refund failed");
}
```
Apply the identical fix to `dispatch(DispatchGet)`.

### Proof of Concept
1. A `HyperApp` (or any EOA through a thin wrapper) calls `EvmHost.dispatch{value: 2 ether}(DispatchPost{... fee: X, ...})` where the swap only actually needs `0.1 ether` to acquire `X` fee tokens.
2. Inside `dispatch`, `swapETHForExactTokens{value: 2 ether}(X, path, address(this), ...)` executes; the router consumes `0.1 ether` and refunds `1.9 ether` back to the caller of the router — which is `EvmHost`, not the original `_msgSender()`.
3. `dispatch` proceeds to build/emit the request and returns; the `1.9 ether` remains in `EvmHost`'s balance forever, with no code path returning it to the original caller.
4. Confirmed by `EvmHost.sol`'s `dispatch` functions containing no post-swap balance check or refund logic, in contrast to `IntentGatewayV2.sol`'s explicit `msgValue -= amounts[0]` / refund pattern at [1](#0-0) .

## Payment Methods

The Hyperbridge protocol ultimately collects its fees in the `feeToken` (usually a stablecoin). But it can also accept native token payments, which are automatically swapped for the `feeToken` using the local AMMs like Uniswap.

|-------|----------------|
| Native token (ETH, BNB, POL, DOT etc.) | Sent with transaction via `msg.value` |
| Fee token (set by IsmpHost) | Requires ERC20 approval before dispatch |
