## Analog Found: Boundary Check Missing Path-Separator in `resolveWithin` Allows Escaping the Repository Root

### Title
`resolveWithin`/`_resolveWithin` uses unbounded `startsWith` prefix check, allowing a crafted deep-link `filepath` to resolve to a sibling path outside the repository root - (File: `app/src/lib/path.ts`)

### Summary
The Solidity report's root cause is a boundary-condition bug in a comparison (`<`/`>` instead of `<=`/`>=`) that mishandles the exact edge value. The closest structural analog in GitHub Desktop is the boundary check in `_resolveWithin`, which validates that a resolved path is contained within a root directory using a bare string `startsWith` comparison without checking for a following path separator: [1](#0-0) 

### Finding Description
`_resolveWithin` is supposed to guarantee that a resolved path lies **at or underneath** `rootPath`. It computes:

```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` does a pure prefix match with no path-separator boundary check. If `realRoot` is `/Users/victim/repo` and an attacker can steer `pathSegments` (e.g. via `..`) so that the resolved real path is a sibling such as `/Users/victim/repo-secrets` or `/Users/victim/repository`, the check `"/Users/victim/repo-secrets".startsWith("/Users/victim/repo")` evaluates to `true`, even though that path is **not** inside `repo` at all. This is the same class of defect as the reported Solidity bug: an edge/boundary comparison (`<` vs `<=`, or here, "prefix" vs "prefix + separator") is not correctly handled, so a value exactly at the boundary is treated incorrectly.

This helper is invoked with attacker-controlled input in `openRepositoryFromUrl`, which is the handler for GitHub Desktop's `x-github-client://openLocalRepo/...?filepath=...` custom-protocol deep link — a link a user can be induced to click: [3](#0-2) 

The code takes explicit care to reject absolute paths (`isAbsolute(filepath)`) and otherwise trusts `resolveWithin` to keep the result confined to `repository.path` before calling `shell.showItemInFolder(resolved)`. Because the confinement check itself has the separator-less boundary flaw, a relative `filepath` value crafted to traverse to a sibling directory that shares the repository directory name as a prefix (e.g. repository at `.../GitHub/project`, target `.../GitHub/project-config/secrets`) can pass the check.

`resolveWithin` is also used elsewhere with untrusted, remote-influenced data: [4](#0-3) [5](#0-4) 
(exact call sites in these two files were not fully inspected due to iteration limits, but both import/use `resolveWithin` per `grep_search` results).

### Impact Explanation
If exploitable end-to-end, this could let an attacker-controlled deep link or repository-derived path cause GitHub Desktop to reveal (via `shell.showItemInFolder`) or, in other call sites that use `resolveWithin` for read/write operations, read or write a file outside the intended repository boundary — matching the "file write or read outside the repo" impact category from the task's valid-impact list.

### Likelihood Explanation
Low/Medium. Exploitation requires: (1) the user clicks a malicious `x-github-client://openLocalRepo/...` deep link (or another vector using `resolveWithin`), and (2) a filesystem layout where a sibling path shares the root directory name as a string prefix (e.g., `repo` and `repo-something`) actually exists on disk — this is opportunistic rather than fully attacker-controlled, since the attacker cannot arbitrarily create directories on the victim's machine. This mirrors the original report's "low likelihood" rating, since it also requires a specific, non-default configuration (`startLeverage == endLeverage`) to be hit.

### Recommendation
Change the boundary check in `_resolveWithin` to require an exact match or a match followed by the platform path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the separator appropriate to the `options` module (`Path.sep`, `Path.posix.sep`, or `Path.win32.sep`) passed in, so `/Users/victim/repo-evil` is no longer treated as being "within" `/Users/victim/repo`.

### Proof of Concept
1. Attacker hosts a page with a link: `x-github-client://openLocalRepo/my-project?filepath=..%2Fmy-project-backup%2Fid_rsa`
2. Victim has a GitHub Desktop repository cloned at `~/Documents/GitHub/my-project` and, coincidentally or via a prior legitimate clone, a sibling directory `~/Documents/GitHub/my-project-backup` containing sensitive files.
3. Victim clicks the link; `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` resolves the repository, then calls `resolveWithin(repository.path, filepath)` with `filepath = "../my-project-backup/id_rsa"`.
4. `_resolveWithin` computes `resolved = "~/Documents/GitHub/my-project-backup/id_rsa"`; `realRoot = "~/Documents/GitHub/my-project"`. Because `resolved.startsWith(realRoot)` is true (string prefix match, no separator check), the function returns the resolved path instead of `null`.
5. `shell.showItemInFolder(resolved)` reveals the out-of-repo file to the user/OS shell, confirming the containment check was bypassed.

Note: I was not able to fully trace every call site (`app-store.ts`, `copilot-conflict-context.ts`) within the available iterations to confirm whether a stronger primitive (arbitrary file write, not just reveal) is reachable through those paths; a Devin session with full file access would be needed to complete that trace.

    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
