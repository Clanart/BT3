Based on the codebase evidence gathered, I found a structurally similar "unguarded edge-case value breaks a downstream operation for certain inputs" pattern — but in Desktop's case it's a missing `--` argument separator combined with an under-restrictive ref-name validator, which lets an attacker-controlled branch name be interpreted as a `git` command-line flag.

### Title
Git branch/ref names starting with `-` can be interpreted as command-line flags due to missing `--` separator - ([File: app/src/lib/git/branch.ts])

### Summary
The `routeFeeRate = 0` bug is really a case of an edge-case value (0) that is technically valid but was never defended against by the code path that consumes it, causing a revert for a subset of inputs. In GitHub Desktop, the analogous invariant is that a branch/ref name is technically valid `git` positional input for many arbitrary strings, including strings starting with `-`, yet the code that shells out to `git` never defends against that edge case with a `--` end-of-options separator, so the argument gets parsed as a flag instead of a literal name for certain (attacker-chosen) inputs.

### Finding Description
`sanitizedRefName`/`testForInvalidChars` in [1](#0-0)  rejects control characters, `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix, and trailing `/` — but it does **not** reject a leading `-`. Nothing else in the ref-name pipeline blocks a leading dash either, as shown by the unit test suite in [2](#0-1) , which only demonstrates that a *leading* `+`/`-` produced by the sanitizer itself is stripped — it never validates *user-supplied* names beginning with `-`.

`createBranch` in `app/src/lib/git/branch.ts` builds the `git branch` argv without a `--` end-of-options marker before the branch name: [3](#0-2) 

If `name` (or `startPoint`) begins with `-`, e.g. `--upload-pack=/tmp/evil.sh` or `--track` or any other `git branch` flag, `git` will parse it as an option rather than a literal ref name, because it appears before any `--` separator in the argument vector.

The deep-link/URL handler `parseAppURL` performs the same insufficient check — it only calls `testForInvalidChars(branch)` (same regex, same gap) before accepting a `branch` querystring value from an `x-github-client://openRepo/...?branch=...` URL: [4](#0-3) 

That value flows through `dispatcher.openBranchNameFromUrl` → `checkoutLocalBranch`, which resolves it against **existing** branches found via `.find()` before calling `checkoutBranch`: [5](#0-4) 

`checkoutBranch`'s argument builder does include a trailing `--` for the base checkout args, but crucially the branch positional appears *before* that `--`: [6](#0-5) 

Because `getBranchCheckoutArgs` returns `[branch.name, ...(remote ? ['-b', nameWithoutRemote] : []), '--']`, any branch whose `.name` (for local branches) starts with `-` is placed before the `--` separator and will be parsed by `git checkout` as an option rather than a ref. A remote-tracking branch name is normally prefixed by the remote name (e.g. `origin/...`), which naturally prevents the leading-dash issue for `checkoutBranch` on remote refs — but `createBranch` has no such prefix protection at all, and is reachable with attacker-supplied strings whenever a new local/tracking branch is created from data that originates in a fetched/cloned remote or a GitHub API pull-request object (e.g., PR head ref names, which are chosen by whoever opened the PR and are not restricted to "normal" git ref conventions beyond what `git` itself enforces, which does allow leading `-` in ref names created via `update-ref`/`push` on a malicious remote).

### Impact Explanation
If an attacker can get Desktop to create or reference a local branch whose name begins with `-` (e.g., via a forked pull request's head branch name, or via a malicious remote that presents such a branch during fetch), a subsequent `git branch <name> ...` or `git checkout <name> ...` invocation can have that name reinterpreted as a git flag. Depending on which flag is smuggled, this can range from silently corrupting the user's repository state (e.g., forcing unexpected `--orphan`, `--track`, `--no-track`, or other branch-creation semantics) up to more dangerous flag injection if any codepath (present or future) constructs `git` argv without the `--` guard and accepts an option like `--upload-pack=<path>` for network-transport-capable subcommands. Within the two call sites found here, the concrete, confirmed corruption is unintended `git branch`/`git checkout` flag execution rather than confirmed arbitrary code execution, since I could not fully trace whether `startPoint`/`name` reach a transport-capable git subcommand (e.g., `fetch`/`clone`) that accepts a dangerous option such as `--upload-pack`.

### Likelihood Explanation
Moderate-to-low confidence exact end-to-end exploitability: I confirmed the missing `--` separator in `createBranch` and the gap in `testForInvalidChars`/`sanitizedRefName`, and confirmed the same gap is used to validate branch names arriving from `x-github-client://` deep links. However, I was not able to fully trace within the available index whether pull-request head ref names (`pullRequest.head.ref`, referenced in `app/src/ui/dispatcher/dispatcher.ts:2039-2045`) or fork-remote branch names actually reach `createBranch` unsanitized — the implementation of `_checkoutPullRequest` in `app-store.ts` was not retrievable in full via the indexed search. This uncertainty should be resolved by a deeper investigation into that function.

### Recommendation
Add a `--` end-of-options separator immediately before any user/remote-derived ref name argument in all `git` invocations that build args positionally (`createBranch`, `getBranchCheckoutArgs`, and any other spot found by auditing `app/src/lib/git/*.ts` for name/ref parameters), and extend `testForInvalidChars`/`sanitizedRefName` in `app/src/lib/sanitize-ref-name.ts` to reject (or sanitize) ref names that begin with `-`, consistent with `git-check-ref-format`'s general recommendation to disallow leading dashes for safety with command-line tooling.

### Proof of Concept
1. On a remote/fork the attacker controls, create a branch literally named `--orphan=malicious` (git itself permits a wide range of ref names via low-level plumbing such as `git update-ref refs/heads/--orphan=malicious <sha>`, bypassing porcelain restrictions).
2. Have a victim fetch/clone that repository in GitHub Desktop, or open a PR whose head ref uses this name and have the victim check out the PR.
3. If the resulting flow calls `createBranch(repository, '--orphan=malicious', startPoint)` (`app/src/lib/git/branch.ts:21-38`) without a `--` separator, `git` receives `branch --orphan=malicious <startPoint>` and interprets `--orphan=malicious` as an option rather than a branch name, corrupting the intended branch-creation operation.
4. Confirm by inspecting the process arguments passed to `dugite`'s `git` wrapper (`git(args, repository.path, 'createBranch')`) for the injected flag being accepted instead of erroring out as an invalid ref name.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

export async function createBranch(
  repository: Repository,
  name: string,
  startPoint: string | null,
  noTrack?: boolean
): Promise<void> {
  const args =
    startPoint !== null ? ['branch', name, startPoint] : ['branch', name]

  // if we're branching directly from a remote branch, we don't want to track it
  // tracking it will make the rest of desktop think we want to push to that
  // remote branch's upstream (which would likely be the upstream of the fork)
  if (noTrack) {
    args.push('--no-track')
  }

  await git(args, repository.path, 'createBranch')
}
