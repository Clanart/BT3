### Title
Per-message PoP does not bind the recipient or recipient encryption key, enabling cross-recipient replay of valid ciphertexts that frames an honest sender for blame - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG encrypts each secret share inside `EncryptedMessage`, which carries a Schnorr proof-of-possession (`pop`) over the per-message key. The PoP challenge (`pop_challenge`) binds the context, nonce, ephemeral key, **sender** index, and ciphertext — but never the intended **recipient** nor the recipient encryption key actually used for the ECDH. Consequently a ciphertext validly signed for sender Alice can be replayed, byte-identical, into any other participant's incoming share set. The PoP still verifies, while the ECDH-derived cipher key differs, so the share decrypts to gibberish and the blame protocol deterministically attributes fault to the honest sender.

### Finding Description
- `pop_challenge` at `crypto/dkg/pedpop/src/encryption.rs:302-324` appends `context`, `nonce`, `key`, `sender`, and `message` — there is no `recipient`/`to` field and no binding to `enc_keys[recipient]`.
- `encrypt` (encryption.rs:135-168) picks a random per-message key and ECDHs it against `self.decryption.enc_keys[&participant]` (encryption.rs:460-467); which recipient key was used exists nowhere in the signed transcript.
- `Encryption::decrypt` (encryption.rs:469-501) verifies the PoP with `from` (the sender index) and decrypts with the *receiver's* registered `enc_key`. A replayed message passes the PoP check and decrypts under the wrong shared secret.
- `KeyMachine::calculate_share` (lib.rs:463-499) then fails `C::F::from_repr` or share verification and emits a blame proof (`EncryptionKeyProof`) containing the ECDH key for *this* recipient.
- `Decryption::decrypt_with_proof` (encryption.rs:366-397) — invoked by `BlameMachine`/`AdditionalBlameMachine::blame` (lib.rs:674-682) and by the coordinator's `VerifyBlame` handler (`processor/src/key_gen.rs:504-549`) — first verifies the still-valid PoP, then DLEq-verifies the accuser's revealed ECDH key against `enc_keys[decryptor]`, decrypts, and finds an invalid share, blaming `sender` (Alice).

The PoP's own comments (encryption.rs:83-90) show the threat model already includes Eve observing and re-submitting Alice's ciphertexts; the missing recipient binding leaves exactly that channel open.

### Impact Explanation
An unprivileged network observer who relays an honest participant's `EncryptedMessage<C, SecretShare>` (intended for Bob) into Carol's share slot causes Carol to produce a valid blame proof that an arbitrator accepts as proving Alice sent Carol an invalid share. Honest Alice is fatally blamed/slashed, and the DKG aborts or completes without her — integrity and liveness impact on the consensus layer, plus unwarranted slashing of an honest validator. This is the Serai analog of CVE-2017-15896: authenticated/encrypted-channel semantics assumed, but replayable unauthenticated-for-this-context application data is accepted and acted upon (blame adjudication) as if bound to the delivery context.

### Likelihood Explanation
Requires an attacker able to copy a transmitted `EncryptedMessage` blob into another recipient's message set — the same network-adversary capability the PoP mechanism was added to defend against. No key knowledge, collusion, or threshold corruption is needed; the replayed object is fully self-authenticating for sender `Alice`. Likelihood is moderate: it needs message-level interception/redirection during round 2 of the DKG, but requires no cryptographic break.

### Recommendation
Extend `pop_challenge` (encryption.rs:302-324) to also append the intended recipient (`to: Participant`) and/or the recipient encryption key (`enc_keys[to]`). `encrypt` must pass the recipient index/key used for the ECDH; `decrypt`, `decrypt_with_proof`, and all blame paths must recompute the challenge with the actual receiver. This makes ciphertexts non-portable across recipients and prevents replayed messages from producing valid blame against honest senders.

### Proof of Concept
1. Participants Alice (2), Bob, Carol (1) run `KeyGenMachine`; all round-1 messages verify.
2. Alice's `generate_secret_shares` emits `m_bob: EncryptedMessage<Ristretto, SecretShare>` destined for Bob, with `pop` over `pop_challenge(ctx, R, m.key, sender=Alice, ct)`.
3. Attacker relays `m_bob` unchanged into Carol's `shares` map under key `Alice` and calls `Carol_machine.calculate_share(rng, shares)`.
4. In `Encryption::decrypt`, `m_bob.pop` batch-verifies (sender field matches Alice; nothing checks the recipient). `ecdh(Carol.enc_key, m.key) ≠ ecdh(Bob.enc_key, m.key)`, so plaintext is gibberish; `from_repr` or share verification fails → `PedPoPError::InvalidShare { participant: Alice, blame: Some(proof) }` where `proof` is a DLEq-valid ECDH key for Carol's `enc_key`.
5. Coordinator `VerifyBlame` → `AdditionalBlameMachine::blame(Alice, Carol, m_bob, proof)` → `decrypt_with_proof`: PoP verifies, DLEq verifies against `enc_keys[Carol]`, decrypted share invalid → returns `Alice` as faulty. Honest Alice is blamed despite having sent a perfectly valid message to Bob.
