### Title
`CodecCommitSig::to_commit_sig` accepts a `BlockIdFlagCommit` vote with no signature - (File: `modules/consensus/tendermint/primitives/src/verifier.rs`)

### Summary
`to_commit_sig()` converts the wire/codec representation of a commit signature into the internal `crate::CommitSig` type used throughout consensus verification. For the `BlockIdFlagCommit` variant — which by the Tendermint/CometBFT spec represents a validator's vote *for* the block and therefore must always be accompanied by a cryptographic signature — the function silently accepts `signature: None` and returns `Ok`, rather than treating this as a malformed/invalid proof.

### Finding Description
The `BlockIdFlagCommit` flag exists specifically to indicate "this validator signed and voted for this block ID." A `BlockIdFlagCommit` entry without a signature is a structurally invalid state that should never occur in a legitimate consensus proof — real CometBFT/tendermint-rs types model the signature field for this variant as non-optional for exactly this reason. In this codebase's `CodecCommitSig`, the field is `Option<Vec<u8>>` [2](#0-1)  and `to_commit_sig()` performs no invariant check requiring `Some` for the `Commit` flag before producing an `Ok(crate::CommitSig::BlockIdFlagCommit { ..., signature: None })`.

### Impact Explanation
Whether this concretely causes false proof/state acceptance depends on how the resulting `crate::CommitSig::BlockIdFlagCommit { signature: None, .. }` is consumed further downstream during voting-power tallying and cryptographic signature verification (in `modules/consensus/tendermint/verifier/src/verifier.rs` and `sp_io_verifier.rs`). I was not able to fully trace that code within the available tool budget, so I cannot confirm with certainty whether the tallying logic:
- correctly treats a missing signature as "verification impossible, so this vote contributes zero voting power" (in which case the defect is contained and only weakens defense-in-depth), or
- has any path that credits voting power for a `BlockIdFlagCommit` entry without independently insisting on a present, cryptographically valid signature (in which case it would directly enable false proof/state acceptance by allowing an attacker to inflate the "signed" validator set with unauthenticated entries).

Regardless of the downstream outcome, the codec layer itself fails to enforce a basic Tendermint structural invariant, which is a defect independent of whatever the tallying code does — it removes a fail-fast guard that should exist at the decode boundary.

### Likelihood Explanation
This is reachable via any submitted consensus proof (unprivileged input), since `CodecConsensusProof`/`CodecCommit`/`CodecCommitSig` are the SCALE-encoded types accepted for proof decoding. No privileged operator is required to trigger the missing check.

### Recommendation
In `CodecCommitSig::to_commit_sig`, explicitly reject a `None` signature for the `BlockIdFlagCommit` variant, e.g.:
```rust
CodecCommitSig::BlockIdFlagCommit { validator_address, timestamp, signature } => {
    let signature = signature
        .as_ref()
        .ok_or_else(|| "BlockIdFlagCommit vote must have a signature".to_string())?;
    ...
}
```
This restores the Tendermint invariant at the decode boundary regardless of what the downstream tallying logic does, ensuring defense-in-depth.
