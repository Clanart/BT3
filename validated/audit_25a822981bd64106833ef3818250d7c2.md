### Title
Scanner `register_offset` surjectivity permanently blocks collateral offsets, leaving funds undetectable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::register_offset` increments an offset until `key + offset·G` is an even point, then refuses registration (`None`) if the resulting `script_pubkey` is already present in `self.scripts`. Because offsets are surjective (distinct requested offsets can resolve to the same registered offset), registering offset `o` whose point is odd consumes `o + 1`. When the owner later tries to register `o + 1` — a logically distinct offset — it collides with the script already claimed by `o` and registration fails forever. Funds sent to `key + (o+1)·G` are never matched by `scan_transaction` and become permanently unclaimable, mirroring the source bug class where removing the last holder of a partition leaves debt unclaimed.

### Finding Description
In `register_offset`, the loop bumps `offset` by one whenever `p2tr_script_buf` returns `None` (odd point): `networks/bitcoin/src/wallet/mod.rs:180-196`. Registration checks `self.scripts.contains_key(&script)` only against the *resolved* offset, not the requested one. The docstring even acknowledges "offsets are surjective, not bijective, and the order offsets are registered in may determine the validity of future offsets" — but no mitigation exists.

The concretely reachable path: an unprivileged party who knows the (public) group key can compute `offset` values (e.g., derived from deposit data such as a TXID hash, the normal HDKD usage) and choose a deposit/offset such that its point is odd and `offset + 1` corresponds to a future legitimate offset. The legitimate offset's registration then fails permanently. `scan_transaction` (`mod.rs:199-214`) only matches `output.script_pubkey` in `self.scripts`, so payments to the blocked offset's script are silently dropped — the wallet reports nothing while funds sit on-chain.

### Impact Explanation
Bitcoin outputs sent to `key + offset·G` for an offset that can never be registered are invisible to the wallet. The key is well-formed and spendable cryptographically, but no `ReceivedOutput` is produced, so `SignableTransaction` never includes them — funds are effectively burned from the protocol's view (unclaimed "debt"), requiring out-of-band recovery.

### Likelihood Explanation
Each offset has ~50% odds of an odd point, so blocking collisions occur naturally with probability ~1/2 per registered pair even without adversarial derivation. An attacker who can influence offset derivation can deliberately construct the collision.

### Recommendation
Track requested-vs-resolved offsets separately (map each script to a set of requested offsets, or store the requested offset on the `ReceivedOutput` after verifying `key + stored_offset·G` produces the script). Alternatively, resolve odd points via negation rather than incrementing, making registration injective, and document that offset registration must be total.

### Proof of Concept
```rust
// Given scanner = Scanner::new(key), find o where (key + o*G) is odd.
// register_offset(o) internally uses o+1 and inserts script(key + (o+1)*G).
scanner.register_offset(o);            // returns Some(o+1)
assert_eq!(scanner.register_offset(o + Scalar::ONE), None); // permanently blocked
// Any tx output paying script(key + (o+1)*G) is now never returned by scan_transaction.
```
