### Title
Cross-transaction deposit-data clobbering in `get_outputs`: an attacker's later transaction overwrites `data`/`presumed_origin` on earlier victims' outputs — ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Analogous to the XToken exploit — where the attacker bought assets at a manipulated external price while the protocol redeemed them at its own internal valuation — Serai's Bitcoin `get_outputs` computes deposit metadata (`InInstruction` data and `presumed_origin`) per transaction but applies it to an accumulator that persists *across* transactions. An attacker who lands a later transaction in the same block causes their transaction's `data` and `presumed_origin` to be stamped onto every previously-scanned output, redirecting the credit of a victim's BTC deposit on Serai.

### Finding Description
In `get_outputs`, the result vector `outputs` is declared *outside* the per-transaction loop:

```rust
let mut outputs = vec![];
// Skip the coinbase transaction which is burdened by maturity
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    ...
    outputs.push(output);
  }

  if outputs.is_empty() {
    continue;
  }

  // populate the outputs with the origin and data
  let presumed_origin = { ... &tx.input[0] ... };
  let data = Self::extract_serai_data(tx);
  for output in &mut outputs {
    if output.kind == OutputType::External {
      output.data.clone_from(&data);
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
``` [1](#0-0) 

Two compounding defects follow:

1. `outputs` accumulates across all transactions in the block, but `data` and `presumed_origin` are recomputed from the *current* `tx` and then written over **all** accumulated outputs. The last matching (or even non-matching, see below) transaction in the block dictates the metadata for every deposit in that block.
2. Once `outputs` is non-empty, `outputs.is_empty()` is never true again, so the populate block runs for **every subsequent transaction** — including transactions that produced no new scanned outputs. Any later transaction `tx` in the block causes `presumed_origin` to be recomputed from `tx.input[0]` (a panic/unwrap on `previous_output.vout` indexing is also reachable via `swap_remove(usize::try_from(input.previous_output.vout).unwrap())` for a crafted vout) and `data` from `Self::extract_serai_data(tx)` to be stamped onto earlier deposits.

The scanned data path (`Output.data`) is what the processor uses to determine where deposited funds are credited on Serai (the `InInstruction`/Shorthand attached via the data-bearing output), and `presumed_origin` is used for refund/origin attribution. Both are attacker-controllable bytes and transaction contents — no validator privilege is required; the attacker simply broadcasts a Bitcoin transaction.

### Impact Explanation
A victim broadcasts a deposit to the Serai external address carrying an `InInstruction` crediting their own Serai account. An attacker watching the mempool (or simply flooding blocks) includes, in the same block and ordered after the victim's transaction, a transaction containing their own InInstruction data (and optionally a dust output to the public external address, though not even that is required due to defect 2). `get_outputs` then overwrites `output.data` on the victim's `External` output with the attacker's instruction. The victim's BTC is credited according to attacker-supplied data — e.g., minted to an attacker-controlled Serai address — while the attacker also forges `presumed_origin`, defeating refund paths. This is a direct theft of deposits, mirroring XToken's mint-cheap-at-one-valuation / redeem-at-another-value inconsistency: the deposit is credited under one transaction's economic context (the attacker's) while the funds came from another (the victim's).

### Likelihood Explanation
Requirements are minimal: the attacker must get a transaction into the same block as a victim deposit (standard mempool sniping / paying a higher fee), and must know the external deposit address or rely on defect 2 (the attacker does not need to send to Serai at all — any transaction triggers re-stamping of prior outputs as long as at least one earlier output was scanned). The offsets for branch/change/forward are deterministic (`Secp256k1::hash_to_F(KEY_DST, ...)`) and the external script is plain P2TR, so all addresses are publicly derivable. No collusion, no validator compromise, and no unusual chain conditions are needed.

### Recommendation
Move the populate block inside the per-transaction scope: accumulate the metadata on only the outputs produced by `scanner.scan_transaction(tx)` (e.g., collect into a per-tx `Vec<Output>` and extend the outer result after stamping), and skip the populate step when the per-tx scan produced no outputs rather than when the global accumulator is empty. Additionally, harden `presumed_origin` extraction against `input.previous_output.vout` being out of bounds for the referenced transaction.

### Proof of Concept
1. Honest user broadcasts `tx_victim`: output paying 0.5 BTC to Serai's external P2TR address plus an InInstruction data output crediting `serai_victim`.
2. Attacker broadcasts `tx_attacker` in the same block, ordered after `tx_victim`: any transaction embedding an InInstruction crediting `serai_attacker` (e.g., the OP_SHA256/EQUALVERIFY data-embedding script used by the protocol), optionally with a dust output to the external address.
3. `get_outputs(block)` iterates: `tx_victim` pushes the victim's `External` output; `tx_attacker` runs the populate block again (outputs non-empty), calling `output.data.clone_from(&data)` with the attacker's extracted data on the victim's output, and `presumed_origin.clone_from(...)` with `tx_attacker.input[0]`'s origin.
4. Serai processes the 0.5 BTC deposit under the attacker's instruction; the victim loses the deposit credit. The same mechanism applies to any number of earlier deposits — one attacker transaction in a block clobbers every earlier deposit's attribution.

  async fn get_outputs(&self, block: &Self::Block, key: ProjectivePoint) -> Vec<Output> {
    let (scanner, _, kinds) = scanner(key);

    let mut outputs = vec![];
    // Skip the coinbase transaction which is burdened by maturity
    for tx in &block.txdata[1 ..] {
      for output in scanner.scan_transaction(tx) {
        let offset_repr = output.offset().to_repr();
        let offset_repr_ref: &[u8] = offset_repr.as_ref();
        let kind = kinds[offset_repr_ref];

        let output = Output { kind, presumed_origin: None, output, data: vec![] };
        assert_eq!(output.tx_id(), tx.id());
        outputs.push(output);
      }

      if outputs.is_empty() {
        continue;
      }

      // populate the outputs with the origin and data
      let presumed_origin = {
        // This may identify the P2WSH output *embedding the InInstruction* as the origin, which
        // would be a bit trickier to spend that a traditional output...
        // There's no risk of the InInstruction going missing as it'd already be on-chain though
        // We *could* parse out the script *without the InInstruction prefix* and declare that the
        // origin
        // TODO
        let spent_output = {
          let input = &tx.input[0];
          let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
          spent_tx.reverse();
          let mut tx;
          while {
            tx = self.rpc.get_transaction(&spent_tx).await;
            tx.is_err()
          } {
            log::error!("couldn't get transaction from bitcoin node: {tx:?}");
            sleep(Duration::from_secs(5)).await;
          }
          tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
        };
        Address::new(spent_output.script_pubkey)
      };
      let data = Self::extract_serai_data(tx);
      for output in &mut outputs {
        if output.kind == OutputType::External {
          output.data.clone_from(&data);
        }
        output.presumed_origin.clone_from(&presumed_origin);
      }
    }

    outputs
  }
