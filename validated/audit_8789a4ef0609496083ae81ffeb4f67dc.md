### Title
DataLayer mirror-coin URLs are unauthenticated attacker-controlled SSRF vectors reachable from any spend bundle - ([File: chia/data_layer/data_layer_wallet.py])

### Summary
DataLayer "mirror" coins use a single, public, non-owner-gated puzzle (`create_mirror_puzzle()` / `MIRROR_PUZZLE_HASH`), and the URLs/launcher-id associated with a mirror are taken verbatim from the `CREATE_COIN` memo of *any* spend that creates a coin with that puzzle hash. Any unprivileged spend-bundle submitter can therefore attach arbitrary URLs (e.g. pointing at internal RPC ports, cloud metadata endpoints, or other internal-network hosts) to any victim's DataLayer store, without owning that store or its singleton. Nodes that later sync that store's mirrors will feed these attacker-chosen URLs straight into outbound HTTP requests (`http_download`, `get_downloader`, plugin `/handle_download`), producing a Server-Side Request Forgery pattern analogous to the FastImage SSRF in the referenced Discourse advisory: unsanitized, attacker-supplied URL data reaches an outbound-request code path with no host/scheme allow-listing.

### Finding Description
- `create_mirror_puzzle()` returns a fixed, curried `P2_PARENT` puzzle with no per-launcher/per-owner customization: [1](#0-0) 
- `get_mirror_info()` extracts the `launcher_id` and mirror `urls` purely from the memo list of a `CREATE_COIN` condition whose puzzle hash matches `MIRROR_PUZZLE_HASH` — there is no check that the coin's creator has any relationship to the DataLayer singleton identified by `launcher_id`: [2](#0-1) 
- `DataLayerWallet.create_new_mirror()` accepts an arbitrary `launcher_id` and `urls` argument and simply creates a coin at `create_mirror_puzzle().get_tree_hash()` with those values in the memo — no ownership validation of `launcher_id`: [3](#0-2) 
- This is exposed directly via wallet RPC `dl_new_mirror`, callable by any wallet holding spendable coins, for any `launcher_id`: [4](#0-3) 
- On the reading side, `DataLayer.update_subscriptions_from_wallet()` pulls all mirrors for a store id via `dl_get_mirrors` and feeds their URLs, unfiltered, into the local subscription table: [5](#0-4) 
- Those subscription URLs are then used by `fetch_and_validate()` to attempt downloads from `server_info.url`, either via a downloader plugin handshake (`/handle_download` POST to a plugin at `downloader.url`) or via `http_download()`/direct HTTP GETs, with no scheme/host restriction visible in this code path: [6](#0-5) [7](#0-6) 
- The project's own internal documentation acknowledges mirror/plugin URLs are untrusted external input, but this only protects the *content* validation (via root-hash verification), not the *destination* of the network request itself: [8](#0-7) 

### Impact Explanation
Any node that runs the DataLayer service and owns or subscribes to a store can be coerced into issuing outbound HTTP requests to attacker-chosen targets (internal RPC endpoints, localhost services, cloud metadata IPs, or other private-network hosts) purely by another party broadcasting a spend that creates a mirror coin referencing that store's `launcher_id`. This is a classic SSRF primitive: it can be used for internal network reconnaissance/port-scanning, hitting local unauthenticated services (e.g., `chia_data_layer` static file server or other localhost RPC), or amplifying requests against arbitrary external hosts under the guise of the victim node — same bug class as the referenced FastImage SSRF (an external URL flows unchecked into a server-side outbound request).

### Likelihood Explanation
Likelihood is high for reachability (creating a coin with a specific puzzle hash and memo requires only a standard signed spend of the attacker's own coins — no special permission, no ownership of the targeted store) but the practical value/severity depends on what internal services are reachable and whether operators run DataLayer with mirrors/subscriptions enabled and, on plugin-enabled deployments, expose more attack surface via `/handle_download`.

### Recommendation
- Require mirror creation to be authenticated to the store owner (or otherwise cryptographically bind mirror provenance) rather than accepting arbitrary `launcher_id` from any coin creator.
- Validate/allow-list mirror and downloader/uploader plugin URLs before use: reject non-http(s) schemes, reject loopback/link-local/private IP ranges (RFC1918, 169.254.0.0/16, etc.), and resolve DNS to re-check target IPs before connecting (to prevent DNS-rebinding SSRF).
- Treat mirror URL lists as untrusted network input requiring the same scrutiny already applied to downloaded file *content*.

### Proof of Concept
1. Attacker (any wallet with a small XCH balance, no relationship to the victim's DataLayer store) calls `dl_new_mirror` with `launcher_id` = victim's known DL store id and `urls` = `["http://169.254.169.254/latest/meta-data/", "http://127.0.0.1:<local-rpc-port>/get_root"]`. This spends only the attacker's own coin to create the mirror coin: [4](#0-3) 
2. The mempool/consensus accepts this normal transaction since `create_mirror_puzzle()` is a public/known puzzle with no ownership constraint tying `launcher_id` to the spender.
3. When the victim's (or any other subscriber's) DataLayer service periodically calls `update_subscriptions_from_wallet()` for that store, it retrieves the attacker's mirror entry via `dl_get_mirrors` and inserts its URLs into local subscriptions: [5](#0-4) 
4. On the next sync cycle, `fetch_and_validate()`/`http_download()` issues an outbound HTTP request to the attacker-chosen URL from the victim node, completing the SSRF: [6](#0-5) 

Note: I was not able to fully inspect `http_download()`'s implementation body (only its call site in `download_file`) within the indexed content, so I cannot confirm with certainty whether it applies any scheme/host restrictions before issuing the request; a Devin session with full repo access would be needed to verify this function body directly.

```python
def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

```python
async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```
