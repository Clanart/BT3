### Title
Cached DKG-confirmation nonces can be reused across distinct signing requests - (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
The DKG confirmer caches a deterministic FROST preprocess seed under only `(b"DkgConfirmer", attempt)`, without binding it to the validator set, removed participants, key pair, participant preprocesses, or final signed message. If the same attempt is used to produce shares for distinct signing inputs, the validator deterministically derives the same nonce pair while the binding factor and challenge differ, allowing observers to recover the validator's private key share.

### Finding Description
`CachedPreprocesses` stores one `[u8; 32]` seed per caller-supplied context, and `DkgConfirmer` defines that context as only the static label and DKG attempt number. [1](#0-0) [2](#0-1) 

On the first request, the coordinator generates and stores a preprocess seed; every later call for the same context loads the same seed and reconstructs the machine through `AlgorithmSignMachine::from_cache`. [3](#0-2) 

`from_cache` calls `seeded_preprocess`, which initializes `ChaCha20Rng` directly from the cached seed and deterministically regenerates the nonce commitments and addendum. [4](#0-3) [5](#0-4) 

A later signing request can nevertheless contain different participant preprocesses and a different `key_pair`, because the remote preprocess map is parsed independently and the signed message is reconstructed from `spec.set()`, `removed`, and the supplied `key_pair`. [6](#0-5) [7](#0-6) 

The regenerated nonce pair is combined with that session's binding factor and then used to calculate the signature share, so identical seeds produce different linear equations when the signing inputs differ. [8](#0-7) 

There is no stored digest or equivalent check proving that the second signing request is identical to the request for which the preprocess was originally created; the cache treats every use with the same attempt number as a renewal of the same session. [3](#0-2) 

### Impact Explanation
Each FROST signature share has the form `s_j = d + rho_j * e + c_j * x_i`, where `d` and `e` are the deterministic nonce scalars and `x_i` is the validator's private share. Once three shares are produced under distinct `rho_j`/`c_j` values from the same cached seed, an observer can solve the resulting linear system for `x_i`.

Recovery of a validator's private key share compromises its ability to safely participate in the MuSig/FROST confirmation protocol and can contribute to unauthorized threshold signing if enough shares are compromised. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The vulnerable condition is reached whenever two share-generation requests reuse the same `(b"DkgConfirmer", attempt)` key but differ in the validator-set context, removals, candidate `key_pair`, or participant preprocesses. Because neither `spec.set()` nor `key_pair` is part of the cache key, competing or repeated DKG-confirmation candidates for the same numeric attempt are not cryptographically distinguished. [10](#0-9) 

An unprivileged observer only needs the public participant preprocesses and published shares; no local database access is required because the nonce-reuse condition is exposed through the resulting signature-share equations. [11](#0-10) 

### Recommendation
Bind the cached preprocess to the complete signing-session identity before reusing it. The context should include at least the validator set or genesis, DKG attempt, removed participants, candidate `key_pair`, and any other immutable values that determine the signed message.

For stronger enforcement, store a hash of the selected participant-preprocess map and final message after the first `sign` call and refuse any later `share` or `complete` call whose values differ. Alternatively, consume the cached preprocess after first use and require a new cache entry for every distinct candidate message. [12](#0-11) 

### Proof of Concept
1. Let a validator create a `DkgConfirmer` for attempt `a` and publish its deterministic preprocess.
2. Cause `share` or `complete` to run for candidate `K1`, producing share `s1`.
3. Cause a second request for the same attempt `a` but a different `key_pair`, removed-participant list, validator-set context, or participant-preprocess map, producing share `s2` from the same cached seed.
4. Repeat once more with a third distinct signing input, producing `s3`.
5. For each share, calculate the validator's public binding factor `rho_j` from the public group key, message, and preprocess transcript, and calculate the public Schnorr challenge `c_j`.
6. Solve:
   ```text
   s1 = d + rho1 * e + c1 * x_i
   s2 = d + rho2 * e + c2 * x_i
   s3 = d + rho3 * e + c3 * x_i
   ```
   for the validator's private share `x_i`.

The same cached seed regenerates the same nonce pair, while the differing preprocesses or messages change the binding factors and challenges that determine the three independent equations. [4](#0-3) [13](#0-12) [8](#0-7)

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
