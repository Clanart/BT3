## Analog Identification

The external report's broken invariant is: **a permission/authorization mapping keyed by a resource identifier (safeHandler) is never invalidated when the resource's ownership changes, so a previous authority silently retains access under the new owner.**

The closest verified analog in this codebase is in the GitHub repository association logic used by GitHub Desktop's push/pull permission gating.

### Title
Stale `GitHubRepository` owner/permission association is never invalidated on repository ownership/rename change, causing Desktop to silently trust outdated write-permission state - (File: `app/src/lib/stores/app-store.ts`)

### Summary
Desktop associates a local clone with a remote GitHub repository by matching the git remote URL's `owner/name` string against known accounts, then persists the resulting `GitHubRepository` record (including its cached `permissions` field) keyed by `[ownerID+name]`. This association is explicitly documented in the code as **never cleared**, and the write-access decision (`hasWritePermission`) defaults to "assume write access" whenever the cached permission value is stale/`null`.

### Finding Description
`matchGitHubRepository` derives the owner/name pair purely from parsing the remote URL string and matching the hostname against a locally known account — it performs no verification that the owner/name still corresponds to the same underlying repository: [1](#0-0) 

The association resolution path explicitly acknowledges that stale associations are never cleared: [2](#0-1) 

The persisted `GitHubRepository` record is looked up/inserted by owner login + repo name (`[ownerID+name]`), and when a fresh API permissions string is unavailable, the store falls back to the **previously cached** permissions value instead of clearing it: [3](#0-2) 

Finally, `hasWritePermission()` treats an unknown/`null` permission as "assume the user can push," and only blocks when the value is explicitly `'read'`: [4](#0-3) 

This mirrors the report's pattern exactly: a permission field (`handlerCan` ~ `GitHubRepository.permissions`) tied to a handler/identifier (safeHandler ~ `owner+name` key) is not cleared when the underlying ownership changes (safe transfer ~ GitHub repository transfer, deletion+recreation under the same `owner/name`, or "repo-jacking" of a renamed owner/org), so the old permission state silently carries over to whatever repository now occupies that identifier.

### Impact Explanation
Because the association is keyed by mutable `owner/name` strings rather than an immutable resource identity, and stale permissions are neither cleared nor re-validated by default, a user's local clone can end up trusting write-permission state that no longer reflects reality (e.g., after the actual GitHub repository behind that `owner/name` has been transferred, or after "repo-jacking" — an attacker recreating a deleted/renamed repository under the same `owner/name` used by the victim's remote). Since `hasWritePermission` defaults to "can push" whenever the permission value is unset/stale, this affects UI/UX gating decisions that rely on that flag (e.g., force-push/protected-branch warnings), risking the user unknowingly pushing to, or otherwise trusting, a repository whose real ownership/permissions have changed — i.e., silent corruption of the trust context for what the user pushes.

### Likelihood Explanation
This requires: (1) a local clone with a remote URL previously associated with a real GitHub repo, and (2) that `owner/name` becoming associated with a different actual repository state (ownership transfer, or deletion+recreation/repo-jacking) — all attacker/environment-controlled conditions that do not require local access, admin rights, or social engineering beyond normal git remote usage. The `// TODO: We currently never clear GitHub repository associations` comment (linking to `desktop/desktop#1144`) in `app-store.ts:4880-4882` confirms this is a known, still-unaddressed gap in the codebase, which raises confidence that the underlying invariant genuinely is not enforced. I was not able to fully trace every UI consumer of `hasWritePermission` within the remaining tool budget (only the definition was confirmed, not every call-site enforcement path), so the exact severity of the downstream UI consequence is not fully verified.

### Recommendation
- Key the `GitHubRepository` association and permissions cache by an immutable identifier (the GitHub API's numeric repository `id`) rather than `owner/name` strings, analogous to the report's recommendation of adding an `_owner` key to `handlerCan`.
- Invalidate/refetch cached `permissions` whenever the matched account/owner or the underlying repository's API `id` no longer matches what was last persisted, instead of falling back to the previous value.
- Change `hasWritePermission`'s default-deny/allow behavior so an unknown or stale permission state does not implicitly grant write trust.

### Proof of Concept
1. Clone `https://github.com/org-A/repo` while it is owned by `org-A`; Desktop persists a `GitHubRepository` row keyed by `[ownerID(org-A)+repo]` with `permissions: 'write'`.
2. `org-A` deletes/renames away from `repo`, and an attacker (or unrelated party) creates a new repository at `org-A/repo` (or the org is renamed and reclaimed) — a well-known "repo-jacking" scenario, requiring no compromise of the victim's machine.
3. The victim's local clone's remote URL still points at `github.com/org-A/repo`, so `matchGitHubRepository` (`app/src/lib/repository-matching.ts:29`) still matches by hostname/owner-name string alone.
4. `repositoryWithRefreshedGitHubRepository` (`app-store.ts:4874`) either bails early (association preserved) or `_upsertGitHubRepository` (`repositories-store.ts:613-630`) reuses the stale `existingRepo?.permissions` value when the fresh call doesn't supply one.
5. `hasWritePermission` (`github-repository.ts:77-84`) continues to report write access based on stale/cached data, so any UI/logic gated on that flag makes decisions against the *new*, attacker-controlled repository using the *old* owner's trust state.

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }
