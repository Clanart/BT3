### Title
ERC20-to-CW20 pointer example contract silently accepts non-standard ERC20 transfer semantics, causing wasm-side accounting to diverge from actual EVM balances - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The reference ERC20→CW20 pointer contract wraps an arbitrary ERC20 token so it can be operated from CosmWasm via `MsgInternalEVMDelegateCall`. Its `transfer`/`transfer_from` handlers build the EVM call payload and unconditionally emit success attributes without validating that the actual token balances changed by the requested `amount`, matching exactly the "Token Integration Checklist" concern that not all ERC20s behave per spec.

### Finding Description
`transfer` and `transfer_from` in `example/cosmwasm/cw20/src/contract.rs` build an `erc20_transfer_payload`/`erc20_transfer_from_payload` and wrap it in `EvmMsg::DelegateCallEvm`, then immediately construct a `Response` with `from`/`to`/`amount` attributes as if the transfer of exactly `amount` succeeded [1](#0-0) , [2](#0-1) . The actual delegatecall is dispatched later by `HandleInternalEVMDelegateCall`, which only checks that the call is delegatecalled by a whitelisted pointer contract and that the caller is EVM-associated; it does not inspect the ERC20 return data or compare pre/post balances, it merely propagates any error from `CallEVM` [3](#0-2) .

Because there's no post-call balance verification, any wrapped ERC20 token that deviates from strict OpenZeppelin-style behavior — e.g., a fee-on-transfer token that debits more than it credits, a rebasing token, or (per the bug-class hint) a token using an extension standard with non-standard `transfer`/`transferFrom` semantics that returns `false` instead of reverting on failure — will cause the CW20 wasm layer to report a successful transfer of the full nominal `amount` even though the EVM-side balance change differs. The CW20 querier (`query_balance`) always reflects the live ERC20 balance via `erc20_balance` [4](#0-3) , so state observed through CW20 queries can diverge from the emitted transfer attributes/events that downstream CW20-consuming contracts (DEXs, escrow, vesting) rely on for accounting.

This is analogous to the ERC20-side `CW20ERC20Pointer.sol`, which likewise treats every `_execute` CosmWasm dispatch as fully successful once `success` is true from the precompile delegatecall, without validating that the wasm-side CW20 balances changed by the expected `amount` [5](#0-4) , so the same class of bug (integrating an asset that doesn't follow the exact expected semantics, and pointer code that assumes 1:1 amount conservation) is reachable from both pointer directions.

### Impact Explanation
A pointer contract (CW20 wrapping an ERC20, or vice versa) that silently trusts nominal transfer amounts rather than measured balance deltas can let downstream integrators (DEX pools, escrow contracts, CW20-based accounting) mis-account balances when wrapping fee-on-transfer/deflationary/rebasing ERC20 tokens. Depending on how a specific downstream CW20-consuming contract uses the reported `amount` (e.g., crediting a pool's internal ledger with the nominal amount while the actual token balance received is less), this can lead to fund loss or accounting corruption for that contract, matching the "unauthorized transfer via precompile or pointer" / "fund loss" impact bar.

### Likelihood Explanation
Reachable by any CW20 pointer user who registers a pointer to an arbitrary ERC20 token via `RegisterPointer`/`registerPointerForERC20` and then transfers through the CW20 interface — no privileged access required. However, the actual severity depends heavily on which non-standard token is chosen and how a specific consuming contract handles the pointer's reported amounts versus real balances; the reference contract itself is example code (`example/cosmwasm/cw20/src/contract.rs`), not a core protocol invariant enforced chain-wide, so likelihood of a concrete, high-impact exploit depends on production pointer/integration usage that this repo snapshot doesn't fully expose.

### Recommendation
Have pointer contracts (both `example/cosmwasm/cw20/src/contract.rs`'s `transfer`/`transfer_from` and `contracts/src/CW20ERC20Pointer.sol`) measure balances before and after the underlying token call and only report/attribute the actually-observed delta, rejecting (reverting) when the delta doesn't match the requested `amount`, rather than trusting nominal `amount`/`success` alone. Publish a Token Integration Checklist (as the underlying report recommends) enumerating required ERC20 semantics (exact-amount transfer, revert-on-failure, no rebasing) that a token must satisfy before a pointer is created for it, and consider validating basic compliance during `RegisterPointer`/`AddCW20`/`AddNative` precompile flows.

### Proof of Concept
Not directly reproducible from static code alone without deploying a concrete non-conforming ERC20 (e.g., a fee-on-transfer token) and a pointer/registration flow. Conceptually:
1. Deploy a fee-on-transfer ERC20 token X (transfer of `amount` actually debits sender `amount` but credits recipient `amount - fee`).
2. Register a `CW20ERC20Pointer`/ERC20→CW20 pointer for X via `RegisterPointer`.
3. Call the CW20 pointer's `transfer { recipient, amount }`; observe the emitted `action=transfer`/`amount` attributes report the full nominal `amount`, while `query_balance` on the recipient shows a lower credited balance (`amount - fee`), demonstrating the accounting mismatch documented in `example/cosmwasm/cw20/src/contract.rs`'s `transfer` function [1](#0-0) .

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(

    _env: Env,
    info: MessageInfo,
    owner: String,

) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

func (k *Keeper) HandleInternalEVMDelegateCall(ctx sdk.Context, req *types.MsgInternalEVMDelegateCall) (*sdk.Result, error) {
	var to *common.Address
	if req.To != "" {
		addr := common.HexToAddress(req.To)
		to = &addr
	} else {
		return nil, errors.New("cannot use a CosmWasm contract to delegate-create an EVM contract")
	}
	addr, _, exists := k.GetAnyPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(req.FromContract))))
	if !exists || common.BytesToAddress(addr).Cmp(*to) != 0 {
		return nil, errors.New("only pointer contract can make delegatecalls")
	}
	zeroInt := sdk.ZeroInt()
	senderAddr, err := sdk.AccAddressFromBech32(req.Sender)
	if err != nil {
		return nil, err
	}
	// delegatecall caller must be associated; otherwise any state change on EVM contract will be lost
	// after they asssociate.
	senderEvmAddr, found := k.GetEVMAddress(ctx, senderAddr)
	if !found {
		err := types.NewAssociationMissingErr(req.Sender)
		evmKeeperMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "evm_handle_internal_evm_delegate_call"), attribute.String("type", err.AddressType())))
		return nil, err
	}
	ret, err := k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)
	if err != nil {
		return nil, err
	}
	return &sdk.Result{Data: ret}, nil
}

    function transfer(address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer", _curlyBrace(_join(recipient, amt, ","))));
        _execute(bytes(req));
        return true;
    }

    function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory sender = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer_from", _curlyBrace(_join(_join(sender, recipient, ","), amt, ","))));
        _execute(bytes(req));
        return true;
    }
