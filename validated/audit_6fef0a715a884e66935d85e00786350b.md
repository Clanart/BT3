### Title
Directory traversal in `revealInFileManager` allows escaping repository root - (File: `app/src/lib/app-shell.ts`)

### Summary
`revealInFileManager` builds the path to reveal with a raw `Path.join(repository.path, path)` and never validates that the result stays inside the repository, unlike other file-path-consuming code paths in the codebase that use `resolveWithin`.

### Finding Description
`revealInFileManager` takes a repository and a `path` argument (documented as "relative path of the file") and does:
```
const fullyQualifiedFilePath = Path.join(repository.path, path)
return shell.showItemInFolder(fullyQualifiedFilePath)
``` [1](#0-0) 

`Path.join`/`Path.normalize` in Node.js collapse `..` segments arithmetically rather than rejecting them, so a `path` value such as `../../.ssh/id_rsa` combined with `repository.path` resolves to a location outside the repository root. This is exactly the scenario the codebase's own `resolveWithin` helper was built to prevent: it normalizes, resolves, and then verifies via `realpath` that the resolved path still starts with the root before returning it (otherwise returning `null`) [2](#0-1) . That helper is used elsewhere in the app (e.g. `app-store.ts`, `dispatcher.ts`, `copilot-conflict-context.ts`) but `revealInFileManager` was not updated to use it [3](#0-2) .

The resulting path is handed to `shell.showItemInFolder`, which is proxied to the Electron main process and ultimately calls Electron's `shell.showItemInFolder` (confirmed via `app/src/ui/main-process-proxy.ts` and `app/src/main-process/main.ts` wiring) — there is no additional boundary check performed at that layer either. Note: the `app/src/main-process/shell.ts` referenced in the question title contains only `UNSAFE_openDirectory`, a separate function explicitly documented as unsafe for user-derived paths and unrelated to `revealInFileManager`; the actual sink for this symbol is `app-shell.ts`'s `shell.showItemInFolder` re-export.

The `path` value passed into `revealInFileManager` originates from UI components handling `WorkingDirectoryFileChange`/status entries (e.g. `unmerged-file.tsx`, `filter-changes-list.tsx`, `selected-commits.tsx`, PR files-changed views) [4](#0-3) . These paths are derived from git status/diff/rename data, or from PR file-changed API data for the "PR files changed" view — both are attacker-influenceable in the threat model given (crafted repository content or API objects).

### Impact Explanation
If a `file.path` value containing traversal segments reaches `revealInFileManager`, the OS file manager would be opened/focused on a file outside the intended repository (e.g. under the user's home directory), and there is no code-execution primitive here — it merely reveals/selects a file in the file explorer, it does not read/exfiltrate file contents to the attacker directly. This is a boundary/scope violation but the actual disclosure requires the local user to observe the revealed file, which is a much weaker impact than the "silent exfiltration to attacker" framing.

### Likelihood Explanation
Likelihood is low in practice: Git itself refuses to record path components equal to `..` in tree/index entries (path components are validated by libgit2/git core when writing trees), so producing a `WorkingDirectoryFileChange`/diff entry whose `path` literally contains `../` segments via a normal clone/fetch is not straightforward. A `resolveWithin`-style call would be a defense-in-depth improvement, but exploitability specifically through crafted git repository content is unproven, and no working end-to-end PoC using real git-derived data was established.

### Recommendation
Route the path through `resolveWithin(repository.path, path)` in `revealInFileManager` and reject (or clamp to the repo root) if the resolved path escapes the root before calling `shell.showItemInFolder`, consistent with `app-store.ts`/`dispatcher.ts` usage patterns.

### Proof of Concept
```ts
// app/src/lib/app-shell.ts
import { revealInFileManager } from './app-shell'
import { Repository } from '../models/repository'

const repo = new Repository('/Users/victim/Projects/repo', -1, null, false)
revealInFileManager(repo, '../../.ssh/id_rsa')
// fullyQualifiedFilePath === '/Users/victim/.ssh/id_rsa' (outside repo.path)
```
This demonstrates the code-level lack of a boundary check; however, producing a genuine git status/diff entry with such a `path` value from attacker-controlled repository content was not verified, so full end-to-end exploitability from a hostile clone/fetch remains unconfirmed.

export function revealInFileManager(repository: Repository, path: string) {

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
