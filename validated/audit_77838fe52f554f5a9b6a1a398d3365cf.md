### Title
Governance can ratify `kip71.gastarget` / `kip71.maxblockgasusedforbasefee` = 0, causing a division-by-zero panic that halts block finalization on every node - ([File: kaiax/gov/headergov/impl/header.go], [File: kaiax/gov/param.go], [File: params/kip71_config.go])

### Summary
The Sherlock report shows an admin-facing setter (`enableSwapFee`) that only rejects values `>= FEE_UNITS` instead of enforcing the documented 20% cap, letting a "restricted" admin set an out-of-policy value that a stricter bound check was supposed to prevent. Kaia has a structurally identical gap: the governance parameters `kip71.gastarget` (`Kip71GasTarget`) and `kip71.maxblockgasusedforbasefee` (`Kip71MaxBlockGasUsedForBaseFee`) use `noopFormatChecker`, which always returns `true`, so **any** `uint64` value — including `0` — is accepted as a valid vote and, once ratified, is fed unchecked into the KIP-71 base-fee formula, where it is used as a divisor.

### Finding Description
Governance parameters are declared with a `Canonicalizer` and a `FormatChecker` in `kaiax/gov/param.go`. For `Kip71GasTarget`, the `FormatChecker` is `noopFormatChecker` (returns `true` unconditionally): [1](#0-0) 

The same pattern applies to `Kip71MaxBlockGasUsedForBaseFee` and `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` (the latter two get partial cross-field checks, but `GasTarget`/`MaxBlockGasUsedForBaseFee` get none): [2](#0-1) 

When a vote is cast via the `governance_vote` API and later included in a block header, `headerGovModule.checkConsistency()` performs cross-field sanity checks only for `GovernanceGoverningNode`, `Kip71LowerBoundBaseFee`, `Kip71UpperBoundBaseFee`, and validator votes. For `Kip71GasTarget`, `Kip71MaxBlockGasUsedForBaseFee`, and several other parameters, the code explicitly states no further checks are performed beyond the (no-op) format check in `NewVoteData()`: [3](#0-2) 

This vote is accepted by `VerifyVote` as long as the voter is the governing node / proposer under `single` governance mode (the trusted-but-restricted role analogous to `onlyConfigMaster` in the original report): [4](#0-3) 

Once ratified at an epoch boundary, the value flows into `KIP71Config.GasTarget` / `MaxBlockGasUsedForBaseFee`, which are used directly as divisors in `NextMagmaBlockBaseFee` without any zero-guard (unlike `BaseFeeDenominator`, which has an explicit fallback to 64 when zero): [5](#0-4) 

If `GasTarget == 0`, then for any block with `parentGasUsed > 0`, the code takes the "gas used above target" branch and computes `x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e., division by zero, which panics in Go's `math/big` package. This function is called on every block by every node computing/verifying the next base fee, so the panic is deterministic and universal — it is not an isolated crash but a chain-wide halt.

### Impact Explanation
This is a state-transition / consensus-halting bug reachable purely through governance parameter voting, matching the "KIP-71 pricing" and "governance parameters" categories explicitly allowed in scope. Because `NextMagmaBlockBaseFee` is invoked by every full node/validator during block preparation and verification, once such a value is ratified at the start of the next epoch, **all nodes** (not just the governing node) crash simultaneously when producing/validating the first block that exercises the divide-by-zero branch. This is a denial-of-service against the entire network with no recovery path other than a coordinated software patch/hard fork, which is High severity impact — analogous in spirit (a missing bound check on an "up-to-X%"-style trusted admin parameter that policy documentation implies should never reach a value that breaks system invariants) to the original swap-fee report, but here the consequence is a full chain halt rather than fee theft.

### Likelihood Explanation
The likelihood depends on the governing node acting maliciously or erroneously (e.g., a governance dashboard bug, human typo, or an actively malicious/compromised governing key), similar to the original report's restricted-admin actor. Unlike `BaseFeeDenominator`, which has a `v != 0` format check and a runtime fallback, `GasTarget` and `MaxBlockGasUsedForBaseFee` have **no protection whatsoever** at either the vote layer or the consensus-application layer, so a single vote transaction with value `0` for `kip71.gastarget` is sufficient once ratified.

### Recommendation
Add explicit `FormatChecker` bounds for `Kip71GasTarget` and `Kip71MaxBlockGasUsedForBaseFee` (e.g., require `v > 0`, and ideally `v <= MaxBlockGasUsedForBaseFee`/some sane upper bound) in `kaiax/gov/param.go`, mirroring the `v != 0` check already used for `Kip71BaseFeeDenominator`. Additionally, add a defensive runtime guard in `NextMagmaBlockBaseFee` (`params/kip71_config.go`) so that `gasTarget == 0` falls back to a safe default instead of dividing by zero, consistent with the existing `baseFeeDenominator == 0` fallback.

### Proof of Concept
1. Governing node (in `single` governance mode) calls `governance_vote("kip71.gastarget", 0)`.
2. `NewVoteData` canonicalizes `0` to `uint64(0)`; `Kip71GasTarget.FormatChecker` (`noopFormatChecker`) returns `true`, so the vote is accepted locally.
3. When this node becomes proposer, `PrepareHeader` writes the vote into `header.Vote`; `VerifyVote` on all other nodes accepts it because `checkConsistency` performs no cross-check for `Kip71GasTarget`.
4. The vote is collected for the epoch and ratified into `header.Governance` at the next epoch boundary, per the header-governance ratification flow described in the module README: [6](#0-5) 
5. Starting from the next epoch, every node's `RewardConfig`/base-fee computation loads `GasTarget = 0` via `GetParamSet` and calls `KIP71Config.NextMagmaBlockBaseFee` on the next block where `parentGasUsed > 0`, hitting the `x.Div(x, new(big.Int).SetUint64(gasTarget))` line with `gasTarget = 0`, causing a `runtime` panic (division by zero) on every node simultaneously — halting block production/verification network-wide.

Note: I was unable to fully verify the exact `Canonicalizer` implementation (`uint64Canonicalizer`) contents since it wasn't retrievable in the final iteration, but the `FormatChecker` for `Kip71GasTarget`/`Kip71MaxBlockGasUsedForBaseFee` being `noopFormatChecker` is directly confirmed in `kaiax/gov/param.go`, and the absence of a consistency check for these two parameters is directly confirmed in `kaiax/gov/headergov/impl/header.go`. For full confirmation of the exact panic behavior under `math/big`, a Devin session with code execution access would be needed to run a concrete regression test against `NextMagmaBlockBaseFee` with `GasTarget = 0`.

func (h *headerGovModule) VerifyVote(header *types.Header) error {
	if len(header.Vote) == 0 {
		return nil
	}

	var (
		vb       headergov.VoteBytes = header.Vote
		blockNum                     = header.Number.Uint64()
	)

	vote, err := vb.ToVoteData()
	if err != nil {
		logger.Error("ToVoteData error", "num", blockNum, "vote", vb, "err", err)
		return err
	}

	if gov.DeprecatedAt(vote.Name(), h.ChainConfig.Rules(header.Number)) {
		logger.Error("Vote is deprecated", "num", blockNum, "name", vote.Name())
		return ErrDeprecatedVote
	}

	council, err := h.ValSet.GetCouncil(blockNum)
	if err != nil {
		return err
	}

	// check if the voter is in council
	if !slices.Contains(council, vote.Voter()) {
		return ErrInvalidKeyValue
	}

	// check if Voter is the block proposer.
	author, err := h.Chain.Sealer().Author(header)
	if err != nil {
		return err
	}
	if author != vote.Voter() {
		return ErrInvalidVoter
	}

	// In single mode, only the governing node can write header.Vote after Permissionless.
	params := h.GetParamSet(blockNum)
	if h.ChainConfig.IsPermissionlessForkEnabled(new(big.Int).SetUint64(blockNum)) &&
		params.GovernanceMode == "single" &&
		vote.Voter() != params.GoverningNode {
		return ErrVotePermissionDenied
	}

	return h.checkConsistency(blockNum, vote)

**File:** kaiax/gov/headergov/README.md (L33-50)
```markdown
A vote is initiated by a governing member of the GC casting a vote.
The vote is cast by the `governance_vote` API, which is inscribed in the block header `header.Vote` when the node that received the API call becomes the proposer.
The voter casts a vote as a tuple `(parameter name, new value)`.
The vote is collected for the entire epoch.

At every epoch block (i.e., `k*epoch` blocks), the node that becomes the proposer will check if the vote has been ratified.
If the vote is ratified, the node will announce the ratification in the block header `header.Governance`.
In other words, `header.Governance` can contain data only at epoch blocks.
If there are no votes in an epoch, the next starting block of the epoch will have an empty `header.Governance`.
It contains a JSON object of `{name: value}` for each ratified parameter.

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.

Parameter change ratified at `k*epoch` block takes effect starting from `(k+1)*epoch` block.
It is worth noting that the effective time of the ratification is `(k+1)*epoch + 1` before Kore.
```
