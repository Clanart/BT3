### Title
OP_RETURN output omitted from Bitcoin transaction weight estimate - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` adds an attacker-controlled `OP_RETURN` output to the transaction that will actually be signed, but both fee and maximum-weight calculations are performed on a transaction containing only `payments` and optional `change`. [1](#0-0) [2](#0-1) 

### Finding Description
`calculate_weight_vbytes` constructs its sizing transaction from `payments` and `change`, with no parameter for the `data` payload or its `OP_RETURN` output. [3](#0-2) [4](#0-3)  After adding up to 80 bytes of caller-controlled data as a real transaction output, `SignableTransaction::new` calls the estimator without representing that output. [5](#0-4) [1](#0-0)  The resulting underestimated `vbytes` value determines `needed_fee`, while the underestimated `weight` determines whether `TooLargeTransaction` is returned. [6](#0-5) [7](#0-6)  The final `SignableTransaction` nevertheless stores the larger transaction containing the omitted output. [8](#0-7) 

For a maximal 80-byte payload, the omitted output is approximately 92 serialized bytes: an 8-byte amount, script-length field, `OP_RETURN`, `PUSHDATA1`, payload-length byte, and payload. [9](#0-8)  Because transaction outputs are base transaction data, this corresponds to approximately 368 WU or 92 vbytes omitted from every fee and weight calculation. [10](#0-9) 

### Impact Explanation
The signing path commits to and returns the actual transaction containing the `OP_RETURN` output, not the smaller transaction used for estimation. [11](#0-10) [12](#0-11)  A caller can therefore obtain a threshold-signed transaction whose fee is below the requested fee rate or whose actual weight exceeds `MAX_STANDARD_TX_WEIGHT` even though construction accepted it. [13](#0-12) [14](#0-13)  Such a transaction can be rejected by standardness policy, leaving the requested spend unconfirmed and the committed transaction unusable despite valid signatures. [8](#0-7) [12](#0-11) 

### Likelihood Explanation
The bug is deterministically reachable whenever `data` is `Some`, and the caller can choose up to 80 bytes without an additional bound beyond `TooMuchData`. [15](#0-14) [5](#0-4)  Triggering the maximum-weight bypass additionally requires payments whose estimated transaction is already close to the standardness limit, while triggering the fee underpayment requires no special sizing beyond nonzero data. [16](#0-15) [14](#0-13) 

### Recommendation
Pass the serialized `OP_RETURN` output—or equivalently the complete `tx_outs` list—into `calculate_weight_vbytes` before calculating `vbytes`, `needed_fee`, or the maximum-weight decision. [17](#0-16) [1](#0-0)  Recalculate both values after deciding whether to include change, and add regression tests asserting that `needed_fee == fee_per_vbyte * actual_vsize` and that any transaction exceeding `MAX_STANDARD_TX_WEIGHT` is rejected. [18](#0-17) 

### Proof of Concept
```rust
// Conceptual reproduction.

let data = Some(vec![0u8; 80]);

// Choose payment scripts/amounts so the transaction built from only
// `payments` is just below MAX_STANDARD_TX_WEIGHT.
let payments = vec![(large_script_pubkey, DUST /* or greater */)];

let tx = SignableTransaction::new(
    inputs,
    &payments,
    change,
    data,
    fee_per_vbyte,
).unwrap();

// The constructor used only `payments` for `vbytes`, while `tx`
// additionally contains the OP_RETURN output.
let actual_vbytes = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() <= fee_per_vbyte * (actual_vbytes - 92));
assert!(tx.transaction().weight().to_wu() >
        bitcoin::policy::MAX_STANDARD_TX_WEIGHT);
```
