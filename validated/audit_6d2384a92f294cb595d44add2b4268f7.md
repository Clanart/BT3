### Title
Governance-settable `kip71.gastarget` can be set to zero, causing a division-by-zero panic in Magma base-fee calculation - ([File: params/kip71_config.go])

### Summary
The `kip71.gastarget` governance parameter is used as a divisor in `KIP71Config.NextMagmaBlockBaseFee`, the function that computes the next block's base fee (Magma/KIP-71 dynamic pricing) and is invoked both when validating incoming headers and when assembling new blocks. Unlike `BaseFeeDenominator`, which has an explicit zero-fallback (`if kc.BaseFeeDenominator == 0 { baseFeeDenominator = 64 }`), `GasTarget` has no such guard, and its governance format checker (`Kip71GasTarget`) is `noopFormatChecker`, which accepts any value including zero. This mirrors the reported bug class: an admin/governance-controlled numeric parameter can be set to zero, which is used unguarded as a divisor/multiplier in a value-critical calculation, causing the function to always fail (panic) once real gas usage occurs.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` in [1](#0-0)  reads `gasTarget := kc.GasTarget` directly from governance without any zero-check, unlike `BaseFeeDenominator` which is defended: [2](#0-1) 

When the parent block's gas used differs from `gasTarget`, the code divides by `gasTarget` in both the increase and decrease branches: [3](#0-2) [4](#0-3) 

If `gasTarget == 0` and `parentGasUsed != 0` (essentially guaranteed in any real block with transactions), `new(big.Int).SetUint64(gasTarget)` is zero and `x.Div(x, 0)` triggers a `division by zero` panic in `math/big`. The only safe path (`parentGasUsed == gasTarget` returning early) requires `parentGasUsed == 0` as well, which cannot be relied upon.

The governance parameter registry confirms `GasTarget` has no format validation preventing zero: [5](#0-4) 

This is set from governance and consumed unguarded in `ParamSet.Set`/`ToMap`, and exposed to `ChainConfig.Governance.KIP71.GasTarget` which flows into `NextMagmaBlockBaseFee` via `blockchain/block_validator.go` (header verification path) and `work/worker.go` (block assembly path), both of which are core state-transition/block-production code reachable on every node.

### Impact Explanation
Once `kip71.gastarget` is voted/set to `0` and takes effect at a subsequent block, every node computing the next base fee for a block with nonzero gas usage — both during header verification (`blockchain/block_validator.go`) and during block assembly (`work/worker.go`) — will panic. This affects the state-transition/gas-fee accounting path used by literally every block, causing the chain to halt or nodes to crash uniformly, which is a state-transition/gas-accounting failure squarely in the "state transition and gas/burn accounting" and "governance parameters" categories called out as in-scope. This is analogous to the original report where `auctionMultiplier = 0` made `newRatio` always revert and permanently broke auction settlement — here, `GasTarget = 0` permanently breaks base-fee computation (and thus block production/validation) network-wide.

### Likelihood Explanation
Setting `kip71.gastarget` requires a governance vote (an authorized/governing-node action), analogous in privilege level to the original report's "factory owner" setting `auctionMultiplier` to zero — i.e., a privileged-but-in-scope actor performing a single misconfiguration/malicious parameter change, not a fully permissionless attack. No other validation in the code path (`Params[Kip71GasTarget].FormatChecker = noopFormatChecker`) prevents this value from being accepted and persisted.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (similar to the checker already used for `Kip71BaseFeeDenominator`, which requires `v != 0`), and/or add a defensive zero-check with a safe fallback in `KIP71Config.NextMagmaBlockBaseFee` (`params/kip71_config.go`) analogous to the existing `BaseFeeDenominator` zero-fallback, to prevent division-by-zero panics regardless of how the value is set.

### Proof of Concept
1. Governance parameter `kip71.gastarget` is voted/set to `0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, see [5](#0-4) ).
2. On the next block after activation, any block with `gasUsed != 0` triggers `KIP71Config.NextMagmaBlockBaseFee` to compute `gasUsedDelta := ... ; y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0` ( [3](#0-2) ), causing a runtime panic (`division by zero`) in `math/big`.
3. This function is called from both header validation (`blockchain/block_validator.go`) and block building (`work/worker.go`), so all nodes attempting to validate or produce the next block panic/crash, halting the chain.
