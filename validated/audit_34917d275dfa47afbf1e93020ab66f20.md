### Title
Quadratic per-input cloning of the full participant preprocess/share map during Bitcoin transaction signing - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`TransactionSignMachine::sign` reconstructs the entire `HashMap<Participant, Preprocess>` once per transaction input, and then clones that whole map a second time when passing it into each per-input `sig.sign(...)`. `TransactionSignatureMachine::complete` repeats the same pattern for signature shares. With `I` inputs and `P` participants, the signing path performs `O(I × P)` `Preprocess`/map clones where only `O(I + P)` copies are needed — the same "clone the whole block-level map per transaction" shape as the Zebra advisory, mapped onto "clone the whole participant map per input."

### Finding Description

In `networks/bitcoin/src/wallet/send.rs`, `TransactionSignMachine::sign` (lines 364–395) does:

```rust
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
```

This builds `I` separate `HashMap`s, each containing `P` cloned `Preprocess<Secp256k1, ()>` values (each `Preprocess` holds a `Commitments` struct with `Vec<NonceCommitments>` of group elements — heap-allocated and non-trivially copied). Then, in the signing loop (lines 382–391), `commitments[i].clone()` clones each of those `I` maps *again* before handing it to `AlgorithmSignMachine::sign`.

The same pattern appears in `TransactionSignatureMachine::complete` (lines 417–425), which builds a fresh `HashMap` over all participants' share vectors for every input:

```rust
let sig = schnorr.complete(
  shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
)?;
```

Each `schnorr.complete` only needs the scalar shares themselves; instead a `P`-entry map is allocated and populated `I` times. Inside `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283-312`), a further `self.params.keys.view(included.clone())` performs `O(t²)` Lagrange interpolation work per input as well, compounding the per-input overhead.

The input count `I` is influenced by external parties: `SignableTransaction::new` (send.rs:150) consumes `ReceivedOutput`s produced by `Scanner::scan_transaction`/`scan_block` (`networks/bitcoin/src/wallet/mod.rs:199-227`), i.e., outputs arbitrary senders create on-chain to the multisig's P2TR script. A sender can fragment a payment into many outputs ≥ `DUST` (10,000 sats in `processor/src/networks/bitcoin.rs:638`), each becoming a distinct input whenever the wallet aggregates. `I` is bounded by `MAX_STANDARD_TX_WEIGHT` (send.rs:241), capping at roughly ~1,700 inputs. `P` is the multisig participant count (bounded by protocol limits, on the order of a hundred+).

### Impact Explanation

Availability only, bounded — matching the referenced bug class. For a worst-case transaction (~1,700 inputs) in a large multisig (~100+ participants), signing performs on the order of 10⁵–10⁶ `Preprocess`/map-entry clones plus `O(I × t²)` scalar interpolation work, stalling every validator executing `attempt_sign`/`sign` for that transaction. There is no consensus divergence, no incorrect signature, and no fund loss; the cost is a processing stall per signing attempt. Because the sign path runs identically on every participant's machine, the stall is replicated across the whole signing set simultaneously, delaying the aggregation/withdrawal transaction. The effect clears when signing completes and requires a new heavily-fragmented funding pattern (plus a transaction that actually selects those inputs) to repeat.

### Likelihood Explanation

Medium-low. Unlike the Zebra case, the attacker here cannot self-fund the trigger for free: every extra input is a real ≥10,000-sat output donated to the multisig (~0.17 BTC for a worst-case transaction), and the stall only occurs if wallet coin-selection actually pulls the attacker's fragmented outputs into a `SignableTransaction`. However, triggering requires no privileged position — any party who learns the multisig's deposit address can send fragmented outputs — and large multisigs routinely sign many-input aggregation transactions even absent an attacker, so the inefficiency also manifests during legitimate operation.

### Recommendation

Restructure `TransactionSignMachine::sign` to avoid per-input whole-map cloning:

- Transpose once: build `Vec<HashMap<Participant, Preprocess>>` via a single pass that `drain`s or borrows the source map (`commitments.iter()` with `iter_mut().map(|(l, v)| (*l, v[c].clone()))` is still `O(I×P)`; better, store each participant's `Vec<Preprocess>` once and hand `sig.sign` a borrowed view, or change `sign` to accept `&HashMap`).
- If `sign` requires ownership, split each participant's `Vec<Preprocess>` into per-input `Preprocess` values by draining the vectors once (`O(I×P)` total moves but with no per-input map reallocation), or refactor `AlgorithmSignMachine::sign` to take `&Commitments` per participant.
- In `complete`, pass each `schnorr.complete` an iterator/slice of `(Participant, SignatureShare)` instead of materializing a fresh `HashMap` per input.
- The change must preserve the participant-keyed binding semantics of `validate_map` (`crypto/frost/src/sign.rs:313`) and produce byte-identical signature shares.

### Proof of Concept

```rust
// networks/bitcoin/src/wallet/send.rs — conceptual amplification harness
// Construct a SignableTransaction with I inputs and observe sign() cost scaling.

#[test]
fn quadratic_sign_scaling() {
  let (keys, key) = keys(); // threshold multisig as in tests/wallet.rs

  // Attacker has funded the multisig address with `I` outputs >= DUST.
  // Each becomes a ReceivedOutput selected as an input.
  let inputs: Vec<ReceivedOutput> = (0 .. 1700)
    .map(|i| fake_received_output(key, i)) // distinct outpoints, value >= 10_000
    .collect();

  let tx = SignableTransaction::new(
    inputs,
    &[(p2tr_script_buf(key).unwrap(), 10_000)],
    Some(p2tr_script_buf(key).unwrap()),
    None,
    FEE,
  ).unwrap();

  let machine = tx.clone().multisig(&keys[&Participant::new(1).unwrap()]).unwrap();
  let (sign_machine, our_preprocesses) = machine.preprocess(&mut OsRng);

  // commitments: P participants each supplying Vec<Preprocess> of length I
  let mut commitments = HashMap::new();
  for p in 2 ..= T { commitments.insert(Participant::new(p).unwrap(), peer_preprocesses[p]); }

  // Inside sign(): `(0 .. sigs.len()).map(|c| commitments.iter().map(...).collect())`
  // performs I * P Preprocess clones + I full-map clones at `commitments[i].clone()`,
  // and complete() rebuilds a P-entry HashMap per input.
  let _ = sign_machine.sign(commitments, &[]);
}
```

Instrumenting `sign` shows allocation work growing as `I × P` (≈1700 × P `Preprocess` clones for the transposition, plus another `I × P` for `commitments[i].clone()`, plus `I` `P`-entry maps rebuilt in `complete`), while the required work is `I` signatures over `P` shares — the identical `O(N)`-map-cloned-`O(N)`-times shape as `remaining_transaction_value` in the Zebra report.
