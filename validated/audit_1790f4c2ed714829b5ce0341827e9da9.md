### Title
Nil-pointer dereference in legacy precompile error handling when `GetDBImpl` returns nil - ([File: precompiles/common/legacy/v605/precompiles.go])

### Summary
Multiple legacy precompile packages (`addr`, `bank`, `distribution`, `gov`, `json`, `oracle`, `pointer`, `pointerview`, `staking`, `wasmd` — versions `v6.0.5`/`v605`, `v6.0.6`/`v606`, `v6.1.0`/`v610`) implement `HandlePrecompileError` by unconditionally dereferencing the result of `state.GetDBImpl(evm.StateDB)`, with no nil check, unlike the fixed pattern used from `v6.1.4`/`v614` onward.

### Finding Description
`HandlePrecompileError` in the v605/v606/v610 legacy precompile packages is: [1](#0-0) 

```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
	if err != nil {
		state.GetDBImpl(evm.StateDB).SetPrecompileError(err)
		metrics.IncrementErrorMetrics(operation, err)
	}
}
```

Every precompile `Run` (see the shared pattern) invokes this in a deferred call whenever `Prepare`/`Execute` return a non-nil error: [2](#0-1) 

`GetDBImpl` only recognizes exactly two StateDB implementations and returns `nil` for anything else: [3](#0-2) 

By contrast, from v6.1.4 onward the same function guards against this: [4](#0-3) 

```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
	if err != nil {
		if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
			sdb.SetPrecompileError(err)
		}
		metrics.IncrementErrorMetrics(operation, err)
	}
}
```

The fact that this nil-check was added later (and consistently kept in every version afterward) is itself evidence that `evm.StateDB` can legitimately be something `GetDBImpl` does not recognize (i.e., neither a raw `*DBImpl` nor a `*state.HookedStateDB` wrapping one) — mirroring the CVE-2023-2166 pattern where a struct field (there, `ml_priv`) is not guaranteed to be initialized on every code path that later dereferences it.

Which precompile version actually executes is height/tracing-dependent, not merely a historical artifact: `Keeper.CustomPrecompiles` selects per-address precompile implementations by upgrade height when the context `IsTracing()`, via `GetCustomPrecompilesVersions`: [5](#0-4) [6](#0-5) 

This means any `eth_call`, `debug_traceCall`, `debug_traceTransaction`, `debug_traceBlock*`, or `eth_getTransactionReceipt`/replay-style RPC request that resolves to a block height before the `v6.1.4` upgrade completed will route precompile calls through the vulnerable `v605`/`v606`/`v610` `HandlePrecompileError`, on a StateDB instance constructed for tracing that may not satisfy `GetDBImpl`'s type assertions.

### Impact Explanation
If `GetDBImpl(evm.StateDB)` returns `nil` on this path, `nil.SetPrecompileError(err)` panics with a nil-pointer dereference. Because this fires inside RPC-triggered tracing/simulation code (not inside consensus `DeliverTx`), the practical impact is a crash of the public JSON-RPC/tracing goroutine handling the request; whether this brings down the whole node process versus just failing the individual RPC call depends on whether the RPC layer recovers panics around this specific call path — I was not able to conclusively verify a recover() wrapping this exact precompile-execution stack within the time available (I found many `recover()` sites in `evmrpc/*.go`, but did not trace whether one specifically wraps `vm.EVM` precompile dispatch during tracing). This uncertainty affects the severity: if unrecovered, this is a crash of a default-configuration RPC node (in scope); if recovered by an outer handler, the practical impact is degraded/failed RPC responses rather than a node crash.

### Likelihood Explanation
Trigger requires (a) a public RPC/tracing request that causes the historical/tracing precompile-version-selection logic to pick `v605`, `v606`, or `v610`, and (b) a precompile call within that trace that errors out (e.g., unknown method selector, bad ABI decode, insufficient funds, disallowed static/delegatecall — many of which are trivially attacker-controlled), and (c) `evm.StateDB` at that point being a wrapper type that `GetDBImpl` does not recognize. Conditions (a) and (b) are straightforward for any external caller to construct (chosen block height + chosen calldata). Condition (c) — confirming which concrete StateDB wrapper type go-ethereum's tracing machinery installs in this codebase, and whether it truly bypasses `GetDBImpl`'s two recognized types — is the part I could not fully verify from the indexed code; the presence and persistence of the nil-guard fix strongly suggests this state is reachable in practice, but I could not find the exact tracing-path constructor that produces such an unrecognized `evm.StateDB` value.

### Recommendation
Backport the nil-guard fix already present in `v614+` to the `v605`, `v606`, and `v610` legacy precompile packages for every affected module (`addr`, `bank`, `distribution`, `gov`, `json`, `oracle`, `pointer`, `pointerview`, `staking`, `wasmd`):
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
	if err != nil {
		if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
			sdb.SetPrecompileError(err)
		}
		metrics.IncrementErrorMetrics(operation, err)
	}
}
```
Additionally, verify (and add if missing) a `recover()` boundary around precompile execution during tracing/simulation RPC paths so that any remaining unrecognized-StateDB nil-dereference in legacy or future precompile code degrades to an RPC error rather than crashing the node process.

### Proof of Concept
Conceptual PoC (not executed, given index limitations on tracing internals):
1. Identify a chain height range prior to the `v6.1.4` (`v614`) upgrade completion but after `v6.0.5`/`v6.0.6`/`v6.1.0` completion, so `GetCustomPrecompilesVersions` resolves a targeted precompile address (e.g. the `pointer` or `bank` precompile) to `v605`, `v606`, or `v610`.
2. Send `debug_traceCall` (or `debug_traceTransaction` for a historical tx) targeting that precompile address with calldata engineered to fail inside `Prepare`/`Execute` (e.g., an unknown 4-byte selector, or malformed ABI-encoded arguments) so `Run`'s deferred `HandlePrecompileError` executes with `err != nil`.
3. If the StateDB used for this tracing context is a wrapper type unrecognized by `GetDBImpl` (neither `*state.DBImpl` nor `*state.HookedStateDB`), `state.GetDBImpl(evm.StateDB)` returns `nil`, and `nil.SetPrecompileError(err)` panics.

I was unable to fully confirm step 3 (the exact tracing-path StateDB wrapper type) within the available tool budget; this should be validated directly against the tracing/backend construction code (e.g. `evmrpc/trace_profile.go`, `evmrpc/tracers.go`) and go-ethereum's tracer/stateOverride wiring before treating this as fully proven.

func (k *Keeper) GetCustomPrecompilesVersions(ctx sdk.Context) map[common.Address]string {
	height := ctx.BlockHeight()
	cp := make(map[common.Address]string, len(k.customPrecompiles))
	for addr, versioned := range k.customPrecompiles {
		mostRecentUpgradeHeight := int64(0)
		noForkHistory := true
		for upgrade := range versioned {
			upgradeHeight := k.upgradeKeeper.GetDoneHeight(ctx, upgrade)
			if upgradeHeight != 0 {
				noForkHistory = false
			}
			if height < upgradeHeight {
				// requested height hasn't seen this upgrade version yet.
				continue
			}
			if upgradeHeight > mostRecentUpgradeHeight {
				mostRecentUpgradeHeight = upgradeHeight
				cp[addr] = upgrade
			}
		}
		if noForkHistory {
			cp[addr] = k.latestUpgrade
		}
	}
	return cp
