### Title
Classic ERC20 `approve()` front-running / allowance race condition in WKAIA - (File: `contracts/testing/system_contracts/WKAIA.sol`)

### Summary
`WKAIA.sol`, the Wrapped-KAIA system contract, implements a bare-bones ERC20-style `approve()`/`transferFrom()` pair with no `increaseAllowance`/`decreaseAllowance` mitigation, unlike the vendored OpenZeppelin `ERC20.sol` used elsewhere in the repo. This reproduces the exact bug class described in the external report: any spender who has been approved for one amount can front-run a subsequent `approve()` call that changes their allowance and drain both the old and new allowances.

### Finding Description
`approve()` in `WKAIA.sol` unconditionally overwrites `allowance[msg.sender][guy]` with the new value and emits `Approval`, with no check that the previous allowance is zero and no atomic increase/decrease primitives: [1](#0-0) 

`transferFrom()` spends the allowance directly against `allowance[src][msg.sender]`, so any pending old allowance is fully spendable up until the moment the new `approve()` transaction is mined: [2](#0-1) 

This is the same root cause flagged in the external report for `SharesManager` / `WLSETH`: an owner who wants to change a spender's allowance (e.g. from `A` to `B`) submits a plain `approve(spender, B)` transaction. A malicious `spender` observing the mempool can front-run it with `transferFrom(owner, spender, A)`, consuming the old allowance, and then—once the owner's transaction lands—immediately call `transferFrom(owner, spender, B)` again, consuming the new allowance as well. The spender ends up transferring `A + B` tokens total instead of the intended `B`.

For contrast, the repo's vendored OpenZeppelin `ERC20.sol` already implements the mitigation (`increaseAllowance` / `decreaseAllowance`) recommended in the external report: [3](#0-2) 

`WKAIA.sol` lacks this mitigation entirely, and being a deployed system contract (Wrapped KAIA), it is directly reachable by any unprivileged transaction sender or public-RPC caller via ordinary `approve`/`transferFrom` calls.

### Impact Explanation
Any user (DEX router, integrator, or individual) who re-approves a spender on `WKAIA` — a common and expected operation for a wrapped-native-token contract used throughout DeFi integrations on Kaia — is exposed to unauthorized extraction of wrapped KAIA beyond the intended allowance. Because `WKAIA` is a widely integrated system contract (used by routers such as Uniswap bindings present in this repo), the blast radius extends to any protocol or user relying on allowance updates against it, resulting in concrete unauthorized value movement of wrapped native tokens.

### Likelihood Explanation
Exploitation requires only mempool visibility and the ability to submit a transaction ahead of the victim's `approve` call — a routine front-running capability on any public network, with no special privileges, validator, or node access required. Any allowance change from a nonzero value to a different nonzero value (rather than always resetting to zero first) triggers the exposure, which is a common real-world pattern.

### Recommendation
Add `increaseAllowance(address spender, uint256 addedValue)` and `decreaseAllowance(address spender, uint256 subtractedValue)` functions to `WKAIA.sol`, mirroring the pattern already present in the vendored `ERC20.sol`, and encourage callers to use these atomic operations instead of `approve()` when adjusting a nonzero allowance. Alternatively, enforce the OpenZeppelin `SafeERC20.safeApprove` invariant of requiring the allowance to be zero before it can be set to a new nonzero value.

### Proof of Concept
1. Owner has approved `Spender` for `A` KAIA-wrapped tokens via `WKAIA.approve(spender, A)`.
2. Owner decides to change the allowance and submits `WKAIA.approve(spender, B)`.
3. `Spender` observes this transaction in the mempool and front-runs it with `WKAIA.transferFrom(owner, spender, A)`, consuming the full old allowance while it is still set to `A`.
4. The owner's `approve(spender, B)` transaction is then mined, resetting `allowance[owner][spender]` to `B`.
5. `Spender` calls `WKAIA.transferFrom(owner, spender, B)` again, consuming the new allowance.
6. `Spender` has extracted `A + B` total tokens although the owner only ever intended to authorize `B`. [4](#0-3)

```text
    function approve(address guy, uint256 wad) public returns (bool) {
        allowance[msg.sender][guy] = wad;
        emit Approval(msg.sender, guy, wad);
        return true;
    }

    function transfer(address dst, uint256 wad) public returns (bool) {
        return transferFrom(msg.sender, dst, wad);
    }

    function transferFrom(address src, address dst, uint256 wad) public returns (bool) {
        require(balanceOf[src] >= wad);

        if (src != msg.sender && allowance[src][msg.sender] != uint256(-1)) {
            require(allowance[src][msg.sender] >= wad);
            allowance[src][msg.sender] -= wad;
        }

        balanceOf[src] -= wad;
        balanceOf[dst] += wad;

        emit Transfer(src, dst, wad);

        return true;
    }
```

```text
    /**
     * @dev Atomically increases the allowance granted to `spender` by the caller.
     *
     * This is an alternative to `approve` that can be used as a mitigation for
     * problems described in `IERC20.approve`.
     *
     * Emits an `Approval` event indicating the updated allowance.
     *
     * Requirements:
     *
     * - `spender` cannot be the zero address.
     */
    function increaseAllowance(address spender, uint256 addedValue) public returns (bool) {
        _approve(msg.sender, spender, _allowances[msg.sender][spender].add(addedValue));
        return true;
    }

    /**
     * @dev Atomically decreases the allowance granted to `spender` by the caller.
     *
     * This is an alternative to `approve` that can be used as a mitigation for
     * problems described in `IERC20.approve`.
     *
     * Emits an `Approval` event indicating the updated allowance.
     *
     * Requirements:
     *
     * - `spender` cannot be the zero address.
     * - `spender` must have allowance for the caller of at least
     * `subtractedValue`.
     */
    function decreaseAllowance(address spender, uint256 subtractedValue) public returns (bool) {
        _approve(msg.sender, spender, _allowances[msg.sender][spender].sub(subtractedValue));
        return true;
    }
```
