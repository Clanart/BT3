### Title
Retained `CachedPreprocess` enables FROST nonce reuse and private share recovery — (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
The kernel bug class is a reference that survives past its intended lifetime: an skb's `secpath` holds a ref on an `xfrm_state` because the secpath is dropped later than the dst, so the stale reference lingers after the object should have been released.

In Serai, the analogous object is the FROST `CachedPreprocess` seed. `from_cache` is documented to require that "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" — yet `SigningProtocol::preprocess_internal` stores the XOR-encrypted seed in `CachedPreprocesses` keyed only by `context` and **never deletes it**. Every subsequent call to `preprocess_internal` / `share_internal` / `complete` under the same context deterministically regenerates the *same* nonces from the retained seed — a lingering reference to a one-time nonce exactly like the lingering secpath ref.

### Finding Description
`preprocess_internal` writes the cache once (`CachedPreprocesses::set`, line 134) and on every later invocation reloads it (`get` at line 137) and rebuilds identical nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:127`). There is no `CachedPreprocesses::del` anywhere in the codebase — the seed outlives the signing session that consumed it.

`share_internal` (line 150) then feeds this fixed nonce into `machine.sign(preprocesses, msg)` where `preprocesses` is built from an attacker-influenced `HashMap<Participant, Vec<u8>>` of peer preprocesses, and `msg` is `set_keys_message(...)` parameterized by a caller-supplied `key_pair` (line 296). Two calls under the same `(b"DkgConfirmer", attempt)` context with different preprocess sets or a different `key_pair` produce two signature shares `s = k + c·x_i` over the same nonce `k` with different challenges — the classic FROST/ROS nonce-reuse equation from which the secret share `x_i` is linearly recovered.

The file's own header acknowledges the danger and rests safety entirely on BFT ordering plus an unimplemented mitigation: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (lines 50–51). The retained-on-disk seed means any path that re-executes `share`/`complete` with distinct inputs — rather than any cryptographic bound — is what stands between correct operation and key-share recovery.

### Impact Explanation
Reuse of a FROST nonce across two distinct `(preprocesses, msg)` tuples lets an observer solve for the signer's secret share. Since this is the coordinator's MuSig validator key (`musig(musig_context(...), self.key, participants)`), recovering it compromises the validator-set root of trust used to confirm DKG results on-chain — full key/share recovery, not merely a forged single signature.

### Likelihood Explanation
The seed is persisted unconditionally and is reusable by construction for crash-recovery/re-execution; the only barrier to reuse is that the caller supplies identical inputs every time. Because the required consistency check is an acknowledged TODO, any code path or future caller that invokes `share`/`complete` twice with differing preprocess maps or `key_pair` values under the same `attempt` deterministically reuses the nonce. Reaching it requires coaxing the coordinator into a second distinct signing call — plausible via re-execution after partial rebuild, which the header itself only partially excludes.

### Recommendation
Delete the `CachedPreprocesses` entry once a signature share has been produced for a context (implement the `del` counterpart), and implement the noted TODO: before publishing a share, verify on-chain that the published preprocess matches the commitments derived from the cached seed, refusing to sign if the incoming preprocess set differs from the one already committed to.

### Proof of Concept
1. Coordinator calls `DkgConfirmer::preprocess()` for `attempt = N`; the seed is stored under `(b"DkgConfirmer", N)` and nonce `k` is fixed.
2. `share(preprocesses_A, key_pair_A)` → `share_internal` reloads the same seed, `sign` emits `s_A = k + c_A·x_i` where `c_A` binds the `preprocesses_A` commitments and `msg_A`.
3. A second call `share(preprocesses_B, key_pair_B)` (or `complete` re-running `share_internal` with a differing map) regenerates the identical `k` but computes `c_B ≠ c_B`, emitting `s_B`.
4. From `(s_A − s_B) = (c_A − c_B)·x_i`, recover `x_i`, the validator's MuSig secret share — identical to the documented consequence of `CachedPreprocess` reuse in `crypto/frost/src/sign.rs:216-219`, made possible because the "must be deleted" contract is never honored.
