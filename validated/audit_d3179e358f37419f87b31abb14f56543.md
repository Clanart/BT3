### Title
Payout attribution relies solely on an unauthenticated, unsigned OP_RETURN, letting anyone frame or falsely credit any operator for a payout they never funded - ([File: core/src/verifier.rs])

### Summary
`create_payout_txhandler` only Schnorr-signs input 0 (the user's withdrawal UTXO) and output 0 (the user's payout) with `SinglePlusAnyoneCanPay`; the OP_RETURN output containing the operator's xonly pubkey and any additional funding inputs are left completely unsigned/unauthenticated. Because the withdrawal UTXO that gets registered in the `withdrawals` table comes purely from a Citrea contract event (attacker-controlled, since anyone can call `withdraw()` on the Citrea Bridge contract with a UTXO and signature they fully control), an unprivileged attacker can construct and broadcast their own fully self-funded payout transaction with an OP_RETURN naming any real operator's public xonly pubkey, and the system will silently attribute that payout to the named operator with no verification that any of the operator's own funds moved.

### Finding Description
The claimed binding: `operator_credited == party_whose_funds_paid_that_payout`.

Trace:
1. `update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2205-2262`) populates the `withdrawals` table's `withdrawal_utxo_txid`/`withdrawal_utxo_vout` purely from `citrea_client.collect_withdrawal_utxos`, i.e. from the Citrea Bridge contract's `withdraw()` event. This event is driven entirely by whatever outpoint an unprivileged caller supplies to the Citrea contract - it is not tied to any operator RPC call. [1](#0-0) 
2. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a payout tx with input 0 = withdrawal UTXO (key-spend, SinglePlusAnyoneCanPay), output 0 = user payout, output 2 = OP_RETURN with `operator_xonly_pk`. Only input 0 and output 0 are covered by the `SIGHASH_SINGLE | ANYONECANPAY` signature; the OP_RETURN output and any additional funding inputs are unsigned by design (that is the whole point of ANYONECANPAY - it lets a funder add inputs/other outputs freely). [2](#0-1) 
3. Whoever controls the private key of the withdrawal UTXO (the attacker, since they chose/signed it when calling `withdraw()` on Citrea) can build this exact transaction themselves, fund it entirely with their own inputs/change (never touching an operator's wallet), and set OP_RETURN to any real operator's `xonly_pk` (public info from `OperatorConfig`), then broadcast it directly to Bitcoin - completely bypassing the operator's own `withdraw()` gRPC handler (`core/src/operator.rs:560-627`) and its `is_profitable` check. [3](#0-2) 
4. `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) detects the spend of the withdrawal UTXO regardless of who broadcast it. [4](#0-3) 
5. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses only the OP_RETURN bytes and writes them as `payout_payer_operator_xonly_pk` with zero verification that the named operator's UTXOs were spent or that the operator authorized the transaction. [5](#0-4) 
6. `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) later only compares `operator_xonly_pk` (read from that DB column) against `kickoff_data.operator_xonly_pk` from the kickoff sender - it never checks that the operator's funds actually paid the payout. [6](#0-5) 
7. Even without any kickoff being sent by the named operator, that operator's own automated `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:31-113`) polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered by its own `signer.xonly_public_key`, finds the attacker's forged entry, and automatically calls `handle_finalized_payout`/sends a kickoff to claim reimbursement for a payout it never made. [7](#0-6) 

Root cause: the protocol treats an unauthenticated OP_RETURN as proof of "who paid," when SIGHASH_SINGLE|ANYONECANPAY explicitly allows any party to add arbitrary unsigned outputs (including the OP_RETURN) and inputs. No code path checks that any UTXO controlled by the named operator (e.g., an input whose scriptPubKey matches the operator's known wallet/collateral) was actually spent in the payout transaction.

### Impact Explanation
This breaks the ATTRIBUTION invariant `operator_credited == party_whose_funds_paid_that_payout` (Critical category: "an operator reimbursed for a payout it never funded" / conversely "an honest operator wrongly framed"). Concretely:
- An attacker can register a real withdrawal on Citrea, self-fund the payout to the user, and frame any operator as the payer. That operator's own automation will subsequently attempt reimbursement (send a kickoff) for a payout it never made, consuming its round/kickoff slot and, if it goes unchallenged (verifiers cannot detect this as malicious because the pubkey check passes), the framed operator becomes eligible for reimbursement from the bridge for funds it never actually fronted - or is forced into an unnecessary kickoff/challenge cycle, wasting its collateral-bound kickoff slots.
- This is repeatable across every withdrawal and every operator, since it only requires public knowledge of an operator's xonly pubkey (from `OperatorConfig`) and control over a self-created withdrawal UTXO, both trivially available to any unprivileged actor.

### Likelihood Explanation
Preconditions are minimal and match the stated attacker model exactly: the attacker needs only to call `withdraw()` on the Citrea Bridge contract with a UTXO/signature they control (explicitly listed as within attacker capability), and knowledge of a target operator's public xonly key. No verifier/operator/aggregator privilege, key compromise, or majority hashrate is required. Attacker cost is only the Bitcoin fees plus the self-funded payout amount (which they can set arbitrarily low subject to Citrea's withdrawal amount, and they control the whole transaction so there is no requirement to overpay). The attack is fully repeatable for every withdrawal cycle and every known operator.

### Recommendation
Do not trust the OP_RETURN alone as proof of payer identity. Require that the payout transaction actually spend a UTXO or otherwise cryptographically commit to the named operator, e.g.:
- Require the payout tx's OP_RETURN commitment to be authenticated (e.g., have the operator sign a message binding withdrawal_id → operator_xonly_pk, verified at `update_finalized_payouts` before writing `payout_payer_operator_xonly_pk`), or
- Change `create_payout_txhandler` to also cover the OP_RETURN output under the signed sighash by using `SIGHASH_ALL|ANYONECANPAY` and only accept the transaction if it was originally submitted through an operator's own `withdraw()` RPC (recording it in the DB pre-broadcast), matching payout_txid against the on-chain result rather than re-deriving payer identity from raw block data, or
- In `is_kickoff_malicious`, additionally verify that at least one transaction input's previous output's scriptPubKey corresponds to the claimed operator's known wallet/round UTXO chain.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
