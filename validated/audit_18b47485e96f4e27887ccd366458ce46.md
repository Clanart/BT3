### Title
Attacker-controlled allocation size in `ThresholdKeys::read` enables memory-consumption DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a `u16` participant count `n` from an untrusted byte stream and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector before validating that the claimed data is actually present. A few input bytes therefore trigger a multi-megabyte allocation, and repeated submissions cause unbounded memory consumption — the same denial-of-service class as CVE-2019-18812 (attacker-triggered memory consumption via a length field).

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), after a fixed-size curve-ID check, the function reads three `u16` values `t`, `n`, `i` directly from the reader. If the next byte selects `Interpolation::Constant`, it executes:

```rust
// crypto/dkg/src/lib.rs:607-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

`n` can be `0xFFFF`, so `Vec::with_capacity(65535)` allocates ~2 MiB (65535 × 32-byte scalar representations, more for wider fields like `ed448`) after the attacker has supplied only ~6 bytes of input. The subsequent per-element `C::read_F` loop will fail immediately on an empty/truncated stream — but the oversized allocation has already been committed by the allocator. The identical pattern repeats at `crypto/dkg/src/lib.rs:620-623` where `n` entries are inserted into a `HashMap` of verification shares (each insert requiring reads, but the loop bound itself is attacker-controlled).

Additionally, `ThresholdParams::new(t, n, i)` is only invoked at `crypto/dkg/src/lib.rs:625-626`, *after* the `n`-bounded allocations, so the parameter validation does not bound `n` before memory is spent.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` — listed as a reachable input surface — can force a ~500,000:1 amplification of bytes-sent to bytes-allocated per call. Repeating the call in a loop (each invocation is independent; no state or authentication is required to reach the allocation) exhausts process memory, causing a denial of service for the signer/coordinator process performing deserialization. This matches the CVE's `A:H` availability-only impact: memory consumption without confidentiality or integrity loss.

### Likelihood Explanation
Any code path that deserializes `ThresholdKeys` from network- or peer-supplied data exposes this. The cost to the attacker is trivial (a ~40-byte message: curve ID + `t`/`n`/`i` + interpolation tag), while each message forces a ~2 MiB transient allocation plus allocator bookkeeping. Since the allocation is committed before the read fails, there is no early-rejection mitigating it; throughput is bounded only by how fast the caller feeds messages to `read`.

### Recommendation
Validate `n` against `ThresholdParams`-style bounds (e.g., maximum set size, and consistency with `t`) before allocating. Replace `Vec::with_capacity(usize::from(n))` with a plain `Vec::new()` and let it grow only as `read_F` actually succeeds — the same chunked/allocation-follows-data approach already used in `networks/ethereum/src/machine.rs:51-60` ("read this in 1 KB chunks to only read data actually present"). At minimum, cap `n` at a protocol-level maximum (e.g., 255, matching `Participant` usage) before any allocation.

### Proof of Concept

```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, Participant};
use dalek_ff_group::Ristretto;

fn attacker_bytes() -> Vec<u8> {
  let mut buf = vec![];
  // Curve ID: length (u32 LE) + ID bytes
  buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
  buf.extend(Ristretto::ID);
  // t = 1, n = 0xFFFF, i = 1
  buf.extend(1u16.to_le_bytes());
  buf.extend(0xFFFFu16.to_le_bytes());
  buf.extend(1u16.to_le_bytes());
  // interpolation = 0 (Constant)
  buf.push(0);
  buf // ~45 bytes total
}

#[test]
fn dos_via_n() {
  // Each call allocates 65535 * size_of::<Scalar>() (~2 MiB) from ~45 bytes of input,
  // then errors. Looping this in a server handler exhausts memory.
  for _ in 0 .. 10_000 {
    let _ = ThresholdKeys::<Ristretto>::read(&mut attacker_bytes().as_slice());
  }
}
```
