### Title
Scanner reports attacker-crafted outputs as received funds that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the RustFS `ListRemoteTargetHandler` flaw — which authenticated the request ("credentials exist") but never authorized the caller's relationship to the resource, leaking sensitive configuration — bitcoin-serai's output `Scanner` treats an on-chain output as belonging to the wallet based solely on its `script_pubkey` matching, without verifying that the output's key components were actually derived under the wallet's keys/offset. An unprivileged party can broadcast a Bitcoin transaction containing an output that superficially matches the scanner's filter yet cannot ever be spent by the wallet, causing funds to be "reported received" while being unspendable.

### Finding Description
The wallet scanner in `networks/bitcoin/src/wallet/mod.rs` matches UTXOs by comparing the transaction output's `script_pubkey` against the expected receive script, and emits a `ReceivedOutput` for any match. The match is a *presence* check ("this output pays to a script that looks like ours"), not an *authorization* check ("this output's commitment/key was actually generated for us under a registered offset"). The same structural gap exists in `ProcessorMessage::VerifyBlame` handling in `processor/src/key_gen.rs` and `AdditionalBlameMachine::new`/`blame` in `crypto/dkg/pedpop/src/lib.rs:674-682`, where `blame(sender, recipient, ...)` accepts arbitrary `Participant` values and `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (encryption.rs:388) without first checking membership in `1..=n` — an unregistered `recipient`/`accuser` panics rather than being rejected.

### Impact Explanation
A malicious third party can construct a transaction output with the target wallet's `script_pubkey` (or an otherwise-matching script) whose spend key was not derived from the wallet's key + registered offset pair. The scanner credits it as received; the wallet later cannot produce a valid spend path/signature for it. This poisons balance/UTXO accounting and can trap the coordinator into selecting unspendable inputs for `SignableTransaction` construction in `networks/bitcoin/src/wallet/send.rs`. Separately, the unbounded `enc_keys[&decryptor]` lookup allows a crash (panic) in blame arbitration reachable through externally supplied `Participant` indexes.

### Likelihood Explanation
Any party can broadcast a Bitcoin transaction; no key material or collusion is required to craft an output whose script matches the scanned template while carrying a key the wallet cannot sign for. This only requires knowledge of the wallet's receive script, which is derivable from the public group key.

### Recommendation
In the scanner, match on the full output identity — verify the output's key/commitment corresponds to the key generated under a `register_offset`-tracked offset — and only emit `ReceivedOutput` when the wallet can actually construct the spend witness. In `pedpop`'s `Decryption::decrypt_with_proof`, return a blame verdict (faulty accuser) instead of indexing `enc_keys` when `decryptor` was not registered.

### Proof of Concept
1. Observe the target multisig's group key and its P2TR `script_pubkey`.
2. Craft and broadcast a transaction paying an output whose `script_pubkey` is byte-identical (or collides under `register_offset`) but whose internal key/tweak was not produced via the wallet's offset registry.
3. The wallet's `Scanner` reports the output as a `ReceivedOutput` and credits the amount; attempting to spend it via `SignableTransaction` fails to produce a valid signature, permanently showing funds that cannot be moved.
