Based on the evidence gathered, I found a concrete local analog in `modules/pallets/consensus-incentives/src/impls.rs`, where a reward-calculation value and the watermark used to prevent double-payment are derived from two different sources of "height," creating the same class of bug as the LPMath report: a computed value that can silently diverge from the invariant it's supposed to preserve (there: LP price constancy; here: "one payment per block of progress, no double payment").

### Title
Reward payout amount and double-claim watermark are derived from different height sources, allowing over-payment/double-claim drift - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`calculate_reward` computes the payable reward using `host.latest_commitment_height(state_machine_id)` [1](#0-0) , but the anti-double-payment watermark `LastRewardedHeight` is advanced using a different value, `state_machine_height.height`, which is the height parameter passed into `process_message` from the caller/message context rather than the value read from `host.latest_commitment_height` [2](#0-1) .

### Finding Description
`calculate_reward` reads:
- `latest_height` = `host.latest_commitment_height(state_machine_id)` [1](#0-0) 
- `baseline` = `LastRewardedHeight::<T>::get(...).unwrap_or(previous_height)` [3](#0-2) 
- `reward = (latest_height - baseline) * block_cost` [4](#0-3) 

The reward is paid out based on `latest_height`. But the watermark that gates future double-payment is updated with a *separate* parameter, `state_machine_height.height`, passed in from `process_message`'s caller: `watermark = watermark.max(state_machine_height.height)` [2](#0-1) . Nothing in `process_message` or `calculate_reward` asserts `state_machine_height.height == latest_height` before this update [5](#0-4) .

This is structurally the same defect pattern as the LPMath report: a value (`shareProceeds` / here, `reward`) is computed from one quantity, while the invariant-preservation check/update (the tolerance check / here, the watermark advance) is keyed to a different, potentially inconsistent quantity. If the caller-supplied `state_machine_height` (coming from the `ConsensusMessage` being processed) lags behind the host's `latest_commitment_height` — e.g., because `host.latest_commitment_height` reflects a state that was already advanced by a different/earlier consensus message processed in the same block, or by a relayer submitting an out-of-order/duplicate `ConsensusMessage` whose embedded height does not match the current chain tip — the pallet pays a reward sized to the gap up to `latest_height`, but only advances the watermark to `state_machine_height.height`, which can be smaller. On the next relayer submission that references a similarly stale `state_machine_height`, `baseline` (still below `latest_height`) allows the reward for the same block range to be computed and paid again.

### Impact Explanation
This breaks the "no double payment for the same range of blocks" invariant of the treasury-funded reward mechanism, directly causing loss of treasury funds through duplicate relayer rewards — this falls squarely within the bounty's "loss of funds" and "replay/double-claim/double-settlement" categories.

### Likelihood Explanation
The trigger does not require a malicious relayer, prover, or governance actor: it only requires that the `state_machine_height` value threaded through `on_executed`/`process_message` for a given `ConsensusMessage` can, in ordinary operation (out-of-order message batches, multiple consensus messages executed in one block, or a relayer resubmitting an older but still-valid consensus update), be lower than `host.latest_commitment_height` at the time the message is processed. Because I could not fully trace the call site that supplies `state_machine_height` into `process_message` (the caller in `on_executed`/`FeeHandler` implementation was not retrievable within the available context), I cannot confirm with certainty how often or under what exact conditions the two heights diverge in production — this is the main uncertainty in this finding.

### Recommendation
Assert `state_machine_height.height == latest_height` before computing and paying the reward (or compute the reward directly from `state_machine_height.height` rather than a separately-fetched `host.latest_commitment_height`), so the paid amount and the watermark advance are always derived from the same quantity, closing the gap that permits a second reward for an already-compensated block range.

### Proof of Concept
Not independently reproducible from the retrieved context alone: a full PoC requires tracing the exact caller in `on_executed` that supplies `state_machine_height` to `process_message`, which the available tool calls did not surface before the iteration limit was reached. The vulnerable code path itself is fully shown above — [6](#0-5)  — and the argument reduces to: pay based on `latest_height`, advance watermark based on a different value `state_machine_height.height`; if the latter can lag the former across two calls for the same `state_machine_id`, the delta between them is paid twice.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
