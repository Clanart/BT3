### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` enables memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in the `dkg` crate trusts an attacker-supplied `n` field to pre-allocate a `Vec` for `Interpolation::Constant` coefficients *before* validating `n` against `ThresholdParams` or confirming the bytes actually exist on the wire. This mirrors the bug class of ALPINE-CVE-2016-6304: a small, attacker-crafted serialized message triggers a disproportionately large memory allocation, enabling memory-consumption denial of service.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574`), the reader consumes the curve ID, then three `u16`s: `t`, `n`, `i` (lines 591–602). `n` is attacker-controlled and is only validated later by `ThresholdParams::new(t, n, i)` at line 626. Before that check, the interpolation tag is read (line 604); if the tag is `0` (`Interpolation::Constant`), the code executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
```

at line 608. `n` is a raw `u16` taken directly from the input stream, so a caller-controlled buffer of roughly a dozen bytes (`C::ID` + `t || n || i` + tag byte `0x00`) forces an immediate allocation of `n * size_of::<C::F>()` — up to ~2 MB for 32-byte fields and ~3.6 MB for ed448's 56-byte field — regardless of whether `n` is consistent with `t`/`i` or whether `n` scalars are actually present. The subsequent `read_F` loop fails on EOF, but the oversized allocation has already occurred; repeated submissions amplify memory consumption ~10⁵× per input byte. Note the contrast with upstream intent elsewhere in the codebase (e.g., `networks/ethereum/src/machine.rs:51-60`), which explicitly chunks length-prefixed reads because "a valid DoS would be to claim a 4 GB data is present for only 4 bytes."

### Impact Explanation
An unprivileged party who can feed serialized bytes to `ThresholdKeys::read` (e.g., key material or share blobs accepted over a channel, or any service deserializing `ThresholdKeys` from unauthenticated input) can force each call to allocate megabytes from a ~15-byte message. Sustained submissions exhaust process memory, aborting signing/verification services — an availability loss consistent with the CVE's memory-consumption DoS, and not merely a timing/CPU issue.

### Likelihood Explanation
The allocation happens on the very first deserialization path, before any validity check (`ThresholdParams::new` runs only after all reads), requires no valid scalars, signatures, or protocol state, and costs the attacker only a handful of bytes per attempt. Exploitability depends on an integrator exposing `ThresholdKeys::read` to untrusted bytes, which is the documented entry point assumed by the security model for these `read` APIs. Bounded by `u16`, the per-call amplification is moderate (~2–3.6 MB), making this a Medium-severity resource-exhaustion vector.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` immediately after reading them, before any allocation; replace `Vec::with_capacity(n)` with incremental `push` (or cap capacity at the already-validated `n`), so allocation grows only as bytes are actually consumed.

### Proof of Concept
```rust
// Conceptual: a ~15-byte buffer that forces a ~2MB allocation in ThresholdKeys::read
// (Ristretto: F::Repr = 32 bytes; n = 0xFFFF)
let mut buf = vec![];
buf.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);            // curve ID passes the check
buf.extend(&1u16.to_le_bytes());      // t = 1
buf.extend(&u16::MAX.to_le_bytes());  // n = 65535 -> Vec::with_capacity(65535) before any read_F
buf.extend(&1u16.to_le_bytes());      // i = 1
buf.push(0);                          // Interpolation::Constant tag
// ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()) allocates ~2MB, then errors on EOF.
// Repeated calls amplify memory usage ~10^5x per input byte.
```
