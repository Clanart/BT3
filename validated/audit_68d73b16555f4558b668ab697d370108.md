### Title
Deposits sent to a multisig address before its activation block are never credited and become unspendable - ([File: processor/src/multisigs/scanner.rs](processor/src/multisigs/scanner.rs), [File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

Analogous to the Rio finding — where an attacker pre-registers a validator so a later ETH "top-up" deposit lands on attacker-chosen withdrawal credentials — Serai's Bitcoin scanner attributes funds purely by `script_pubkey` match against keys it has already activated, with no check of when or why the output was created. Because the group key (and all derived offset addresses) is computable/observable before the key's activation block, an unprivileged party can send BTC to a not-yet-active Serai deposit address. The scanner only matches outputs for keys whose `activation_number <= block_being_scanned` and never rescans earlier blocks, so the pre-activation deposit is silently dropped: the BTC is real, sits at a key Serai controls, yet is never reported as a received output and never enters the scheduler's spendable set.

### Finding Description

`Scanner::scan_transaction` matches an output solely on `output.script_pubkey` membership in `self.scripts` (`networks/bitcoin/src/wallet/mod.rs:205-211`) — there is no notion of provenance or timing. `register_offset` documents that all offsets are deterministic functions of the group key (`networks/bitcoin/src/wallet/mod.rs:180-196`), and the processor derives the Branch/Change/Forwarded offsets from `hash_to_F("Serai Bitcoin Output Offset", ...)` (`processor/src/networks/bitcoin.rs:333-344`), so every scannable address is publicly derivable once the group key is known (e.g., observed from a pending/previous DKG, a prior deposit, or mempool activity).

The processor-side scanner gates scanning on activation height:

```rust

  if activation_number > block_being_scanned {
    continue;
  }
  ...
  for output in network.get_outputs(&block, key).await {
```

(`processor/src/multisigs/scanner.rs:550-567`). `ram_scanned` only advances forward (`processor/src/multisigs/scanner.rs:722`), so any block mined before `activation_number` is never revisited. An attacker who learns the upcoming group key can broadcast a transaction paying to its external (or Branch/Change/Forwarded) address in a block `< activation_number`; the output will never be matched, never emitted in `ScannerEvent::Block`, never saved via `save_outputs`, and never scheduled for spending — despite being an on-chain UTXO controlled by the multisig.

The mirror-image variant also exists for classification: because offsets are public, anyone can send to the `Change`/`Forwarded` offset addresses and have the output classified as `OutputType::Change`/`Forwarded` (`processor/src/networks/bitcoin.rs:686-700`), polluting the output-kind accounting with deposits that did not come through the deposit flow.

### Impact Explanation

Funds are sent to a key Serai controls but are permanently uncredited: they are not reported as received outputs, are absent from the scheduler's input set, and in practice are burned (or require manual intervention) since the wallet machinery will never construct a transaction spending them. This is the direct analog of "funds deposited land on a registration the protocol treats as valid but never reconciles." Severity: Medium — requires knowing a key before activation and only causes loss of the attacker's/relayer's own or griefed deposits, but it is a deterministic crediting failure reachable by any unprivileged party sending a Bitcoin transaction.

### Likelihood Explanation

Any party who can observe or predict a future multisig group key (e.g., a participant in a prior session, or an observer of DKG/coordination messages that reveal the key ahead of `register_key`) can execute this with a single ordinary Bitcoin transaction. No collusion, no malformed encodings, and no validator/node trust assumptions are needed — just public input (a Bitcoin tx) fed to a scanner that matches on script alone.

### Recommendation

- When registering a key, define activation scanning to include a rescan window (or scan from a configurable lower bound) so pre-activation deposits are still discovered, or explicitly document and enforce that addresses must not be published before activation.
- Treat `OutputType::Change`/`Forwarded`-classified outputs that were not created by Serai's own transactions as suspicious: verify in `get_outputs` (`processor/src/networks/bitcoin.rs:686-700`) that `Change`/`Forwarded` outputs originate from a Serai-signed spend before crediting them with that kind.

### Proof of Concept

1. Observe or derive the next session's group key `K` (public value) and compute the external P2TR address `address_from_key(K)` (`processor/src/networks/bitcoin.rs:671-674`, `p2tr_script_buf` in `networks/bitcoin/src/wallet/mod.rs`).
2. Before `Scanner::register_key`/`activation_number` takes effect, broadcast a Bitcoin transaction paying `X` sats to that address; let it confirm in block `b < activation_number`.
3. Once the key activates, the scanner loop at `processor/src/multisigs/scanner.rs:550-567` scans only blocks `>= activation_number`; block `b` is never rescanned (`ram_scanned` monotonic, line 722).
4. Result: the UTXO exists and is controlled by `K`, but no `ScannerEvent::Block` ever includes it, `save_outputs` never records it, and no `SignableTransaction` will ever spend it — funds are received by Serai yet unspendable by its own machinery.
