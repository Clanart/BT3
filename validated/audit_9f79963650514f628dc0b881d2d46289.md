Confirmed: no timestamp/expiry logic exists anywhere in `sign-in-store.ts` — `csrfToken` (state) lives indefinitely in memory until `reset()` is explicitly called by user cancellation or a new sign-in flow being started.### Title
Unbounded OAuth `state` lifetime allows a stale sign-in session to be silently completed by a delayed/attacker-replayed callback - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
The external report's broken invariant is: a signed authorization is created once, but has no deadline, so it can be executed later under different (attacker-favorable) conditions. The Desktop analog is the OAuth sign-in flow: `authenticateWithBrowser()` generates a `csrfToken` and stores it in `oauthState.state` with no expiry, timestamp, or timeout. [1](#0-0)  The only value ever validated by `resolveOAuthRequest()` when the `x-github-client://oauth?code=...&state=...` deep link arrives is state equality — never freshness. [2](#0-1) 

### Finding Description
`parseAppURL()` accepts any `oauth` deep link containing `code` and `state` query parameters with no validation beyond their presence. [3](#0-2)  The main process forwards this to the renderer via `handleAppURL` → `dispatchURLAction` → `_resolveOAuthRequest`. [4](#0-3) [5](#0-4) 

`resolveOAuthRequest()` in `SignInStore` only checks: (1) the store is still in the `Authentication` step, (2) `oauthState` exists, and (3) `oauthState.state === action.state`. [6](#0-5)  There is no timestamp comparison, no expiry window, and no `setTimeout`/TTL anywhere in the file — confirmed by searching the file for `expir`, `TTL`, `Date.now`, `timestamp`, and `setTimeout`, all of which return no matches. The `csrfToken` set at `authenticateWithBrowser()` line 284 remains valid in memory indefinitely until `reset()` is explicitly invoked (e.g., a new sign-in attempt or the popup being dismissed). [7](#0-6) 

This mirrors the reported bug class exactly: a one-time "signed" action (the `state` value bound to a specific authentication attempt) has no deadline, so a callback can be "saved for later" and executed once conditions have changed — e.g., long after the user forgot about it, after account state on the endpoint has changed, or after the corresponding authorization `code` is captured/relayed from a different context (browser history replay, shared/multi-user machine, or a lingering background app instance). Existing guards (state equality, single-instance lock, session-kind check) stop cross-session CSRF but do **not** stop a same-session, delayed completion.

### Impact Explanation
Successful (delayed) completion of `resolveOAuthRequest()` results in `fetchUser(endpoint, token)` and `onAuthCompleted(account)` — i.e., an account gets silently bound/added to the Desktop application without a fresh, time-bounded user confirmation that they still intend to authenticate at that moment. [8](#0-7)  Since the app has no deadline check, any successful late-arriving `oauth` callback with the still-valid `state` is trusted just as if it had happened seconds after being requested. This falls under "unauthorized OAuth or account binding" in the accepted impact category.

### Likelihood Explanation
Likelihood is **low-to-medium**. It requires the sign-in session to remain open in Desktop (the `SignInStep.Authentication` popup left un-dismissed) while the external browser tab/OAuth code from that same flow becomes usable again later — analogous to a low-fee transaction sitting in the mempool. There's no cross-tab/cross-user CSRF bypass since `state` is a `crypto.randomUUID()` value the attacker cannot guess. [9](#0-8)  The realistic trigger is a stale, still-open sign-in dialog plus a delayed/retried OAuth provider callback (e.g., browser tab left open, or a code inadvertently reused/resent), not a remote attacker forging the deep link outright.

### Recommendation
Add an expiry/deadline to `oauthState` (e.g., store a creation timestamp alongside `state` and reject `resolveOAuthRequest()` if the callback arrives after a short window, such as 5–10 minutes), and clear `oauthState` automatically after that deadline elapses instead of leaving it valid indefinitely until manual `reset()`.

### Proof of Concept
1. User clicks "Continue with browser" to sign in; `authenticateWithBrowser()` creates `csrfToken` and opens the OAuth URL, storing `oauthState.state = csrfToken` with no expiry. [1](#0-0) 
2. User does not complete the flow (leaves the browser tab open, gets distracted) — the Authentication dialog in Desktop stays open indefinitely since nothing times it out.
3. Arbitrarily long afterward (hours/days), the OAuth callback `x-github-client://oauth?code=<code>&state=<csrfToken>` is triggered (e.g., the stale browser tab is reloaded/resubmitted, or the code is replayed from browser history/cache). [10](#0-9) 
4. `resolveOAuthRequest()` still finds `this.state.oauthState.state === action.state` true (no expiry check exists) and completes the sign-in, binding whatever account the delayed `code` resolves to. [11](#0-10)

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
