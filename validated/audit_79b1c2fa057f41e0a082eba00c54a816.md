### Title
Stale per-path `manualResolutions` carried across rebase/cherry-pick rounds can silently reapply an earlier ours/theirs choice to an unrelated later conflict on the same path - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
GitHub Desktop's multi-commit-operation conflict handling keeps a single `Map<string, ManualConflictResolution>` (`manualResolutions`) keyed only by file **path**, and this map is explicitly preserved across successive Git status refreshes for the same operation kind. When a rebase/cherry-pick applies multiple commits from a cloned/fetched (attacker-controlled) branch that repeatedly touch the same path, a resolution the user picked for the *first* conflict on that path can still be present in the map when a *second, unrelated* conflict on the same path occurs in a later commit of the same operation, and gets silently re-applied via `stageManualConflictResolution` without the user reviewing the new conflict content.

### Finding Description
`updateConflictState` explicitly threads the previous `manualResolutions` map forward whenever the conflict kind is unchanged (rebase→rebase or merge→merge), with no filtering to drop entries for paths that are no longer part of the *current* conflict round: [1](#0-0) [2](#0-1) 

The resolution map is keyed purely by relative path, not by conflict "round" or commit identity: [3](#0-2) 

When continuing a rebase or cherry-pick, the map is applied unconditionally to any file that currently matches a stored path, regardless of whether that entry was chosen for the *current* conflicted content or a prior, unrelated conflict on the same path from an earlier commit in the same multi-commit sequence: [4](#0-3) [5](#0-4) 

`stageManualConflictResolution` then deterministically checks out either "ours" or "theirs" content for the path and stages it - there is no re-validation that the stored resolution still corresponds to the content currently in conflict: [6](#0-5) 

This is structurally the same bug class as the report: a "pending/carried-forward" tracking value (`$.pendingDecreaseCollateral` in the contract; `manualResolutions[path]` here) that is meant to represent unresolved work from a specific prior request/round, but is not scoped/cleared per-round and gets blindly reused/merged into a later, different request/response - producing a state divergence between what the user believes they decided and what is actually applied.

### Impact Explanation
A malicious or compromised remote repository can be crafted so that a rebase/cherry-pick of its commits produces two (or more) separate conflicts on the exact same file path across different commits in the same operation. If the user resolves the first conflict with "theirs" (to take content from the attacker's branch) and continues, the stored `ours`/`theirs` choice for that path persists in `manualResolutions`. When the second, unrelated conflict on the same path is reached, Desktop can reapply the same resolution automatically instead of surfacing it to the user - silently writing attacker-influenced or otherwise unintended content into the working tree and staging it for the resulting commit. This is a silent corruption of what the user commits and subsequently pushes, without any local/physical access, admin rights, or social engineering beyond the normal "clone/fetch and rebase" workflow.

### Likelihood Explanation
Exploitability requires only that the user rebases or cherry-picks a sequence of commits from an attacker-influenced branch/fork where the same file path is deliberately made to conflict more than once. This is a realistic, low-effort setup for anyone who can push commits to a branch/fork that the victim later fetches and rebases onto (a common collaboration workflow), making the likelihood moderate. The main uncertainty is whether the conflicts-dialog UI additionally filters/represents already-"resolved" paths in a way that would force the user to notice and re-decide before commit ‑ this could not be fully confirmed within the available search budget and would need direct verification against the UI step components that render `ShowConflictsStep`/`unmerged-file.tsx` for round two.

### Recommendation
Scope `manualResolutions` per conflict round rather than globally per path: on every successful `continueRebase`/`continueCherryPick` call, drop or invalidate any manual-resolution entries whose paths are not present in the *newly detected* conflict set, and require the user to explicitly re-choose ours/theirs whenever a path re-enters conflict after having been "resolved" and staged in a prior round of the same multi-commit operation.

### Proof of Concept
1. Attacker maintains/pushes a feature branch with two separate commits, both modifying `shared/config.json`, each producing a conflict against the target branch when rebased.
2. Victim fetches the branch and starts `rebase` (or `cherry-pick`) of both commits onto their target branch via Desktop.
3. First commit conflicts on `shared/config.json`; victim picks "Use theirs" and continues. `manualResolutions` now contains `{ "shared/config.json": theirs }`.
4. `updateConflictState` carries this map forward (kind stays `rebase`) as Desktop refreshes status for the next commit.
5. Second commit also conflicts on `shared/config.json` (different content). `continueRebase`'s path-matching resolution logic re-applies the stored `theirs` resolution and stages attacker content for this second, unrelated conflict without prompting the user to review it.
6. The rebase completes; the victim commits/pushes content for the second conflict that they never actually reviewed or approved.

  const manualResolutions =
    prevConflictState !== null

      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {

  }

export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
