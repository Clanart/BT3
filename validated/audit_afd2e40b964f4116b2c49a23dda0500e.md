## Finding: Valid [1](#0-0) 

### Title
Insufficient sanitization in `sanitizeCloneName` allows attacker-controlled shell metacharacters in the clone folder name, enabling `cmd.exe` command injection when the repository is opened in a Windows shell integration - (File: `app/src/lib/remote-parsing.ts`)

### Summary
`sanitizeCloneName` only guards against **path traversal** (splitting on `/`, `\`, `:`, rejecting `..`/`.`/empty). It performs no filtering of shell metacharacters (`&`, `|`, `^`, `%`, backtick, parentheses) or a leading `-`. Because Windows permits most of these characters in file/folder names, a crafted remote URL can make the sanitized clone-folder name contain `&`/`|`/`^`. That folder path is later passed, unescaped, as part of a string argument to `spawn(..., { shell: true })` in `app/src/lib/shells/win32.ts` for several shell integrations (Git Bash, Cygwin, Alacritty, Hyper, Warp, PowerShell/PowerShellCore, Cmd, WSL, Windows Terminal, Fluent Terminal). On Windows, `cmd.exe` treats `&`, `|`, and `^` as command separators/escapes even when they appear inside a quoted substring, so opening the cloned repository "in shell" from GitHub Desktop executes attacker-chosen commands.

### Finding Description
The clone flow is:
1. `parseRemote`/`parseRepositoryIdentifier` extract the `name` component from the attacker-controlled remote URL using a permissive regex (`[^/]+?`), which can contain almost any character except `/`. [2](#0-1) 
2. `sanitizeCloneName(name)` is applied in `clone-repository.tsx` to compute the local folder name, but it only splits on `/ \ :` and strips a trailing `.git` — it does not reject or escape shell metacharacters or a leading `-`. [3](#0-2) 
3. The resulting folder name is joined via `Path.join` to build the actual on-disk repository path, which is what gets created by `git clone` and later stored as the repository's `path`. [4](#0-3) 
4. When the user opens that repository "in shell" (or in certain custom terminal integrations), `app/src/lib/shells/win32.ts`'s `launch()` builds a command using `spawn(..., { shell: true, cwd: path })`, embedding the repository `path` directly inside a larger, singly-quoted command string, e.g. for Git Bash:
```
spawn(gitBashPath, [`--cd="${path}"`], { shell: true, cwd: path })
``` [5](#0-4) 
The same unsafe pattern (`shell: true` + string-interpolated `path`) is used for `Cygwin`, `Alacritty`, `Hyper`, `Warp`, `PowerShell`, `PowerShellCore`, `Cmd`, `WSL`, `WindowsTerminal`, and `FluentTerminal`. [6](#0-5) 

Because `spawn(..., { shell: true })` on Windows runs the command through `cmd.exe`, and `cmd.exe`'s command-line tokenizer treats `&`, `|`, and `^` as command separators/escape characters even inside a quoted string (unless additionally caret-escaped), a folder name containing these characters breaks out of the intended quoted argument and injects a new command. Windows filesystems permit `&`, `|`, `^`, `%`, backtick, and parentheses in file/directory names (only `< > : " / \ | ? *` are truly forbidden — note `|` itself IS forbidden, but `&`, `^`, `%` are not), so a name like `repo & calc.exe & true` is a legal Windows folder name that `sanitizeCloneName` passes through unchanged.

The regression test suite for `sanitizeCloneName` only covers path-traversal cases (`..`, backslash sequences) and does not test shell-metacharacter or leading-dash inputs, confirming this class of input is not currently rejected. [7](#0-6) 

On macOS/Linux (`darwin.ts`, `linux.ts`), the `launch()` calls generally use `spawn(path, [args])` **without** `shell: true`, so argv entries are passed directly to `execve` and are not subject to shell re-parsing — this specific injection does not reach those platforms via the standard shell-args array. (I was not able to fully verify `custom-integration.ts`'s `spawnCustomIntegration`/`expandTargetPathArgument` implementation within the available context, so whether custom shell/editor integrations on macOS/Linux also use a shell is unconfirmed.)

### Impact Explanation
On Windows, this results in arbitrary command execution as the victim user the moment they choose "Open in <Shell>" for the maliciously-named cloned repository — a normal, expected user action after cloning (not an "unnatural" step). This satisfies the Critical bar: code execution driven purely by attacker-controlled remote URL content, no admin rights or local access required.

### Likelihood Explanation
Requires the victim to clone a repository from an attacker-supplied URL (e.g., via a crafted clone link or `x-github-client://` deep link that pre-fills the Clone dialog) and then use the "Open in Terminal/Shell" feature on that repository — a common, expected workflow. No warning is shown that the folder name is unusual, since the vulnerable characters are valid filesystem characters and don't trigger any existing "unsafe path" checks.

### Recommendation
Harden `sanitizeCloneName` in `app/src/lib/remote-parsing.ts` to allow-list a safe character set for directory names (e.g., alphanumerics, `-`, `_`, `.`, unicode letters) and reject/replace any other characters, in addition to rejecting a leading `-`. Independently, `app/src/lib/shells/win32.ts` should not build shell command strings for `spawn` with `shell: true`; each of the affected branches (`GitBash`, `Cygwin`, `Alacritty`, `Hyper`, `Warp`, `PowerShell`, `PowerShellCore`, `Cmd`, `WSL`, `WindowsTerminal`, `FluentTerminal`) should either invoke the target executable directly with an argv array (no `shell: true`), or properly escape the `path` value for `cmd.exe` (e.g., via `^` escaping of `&|^<>%` in addition to quoting) before interpolating it into the command string.

### Proof of Concept
1. On Windows, use GitHub Desktop's Clone dialog (or a deep link) with URL:
   `https://host/owner/repo & calc.exe & true.git`
2. `parseRemote`/`sanitizeCloneName` yield the folder name `repo & calc.exe & true`, and the repository is cloned into `<baseDir>\repo & calc.exe & true`.
3. Right-click the repository in GitHub Desktop → "Open in Git Bash" (or PowerShell/Cygwin/etc.).
4. `win32.ts`'s `launch()` executes `spawn('"<git-bash.exe>"', ['--cd="<baseDir>\\repo & calc.exe & true"'], { shell: true })`, which `cmd.exe` parses as three chained commands, launching `calc.exe` (replace with any payload) as a side effect of opening the shell.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
```
