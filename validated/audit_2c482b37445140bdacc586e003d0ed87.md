### Title
Reward-provisioning bypass via dust deposit converts deferred `queuedRewards` into an immediate, fully-captured distribution to a 1-wei staker - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward` (and the identical logic in `BaseRewardPoolV2._provisionReward`) only defers a reward into `queuedRewards` when `totalStaked() == 0`; any nonzero `totalStaked()` causes an immediate `rewardPerTokenStored` update divided by that (possibly tiny) `totalStaked()`. Because `totalStaked()` is simply `IERC20(stakingToken).balanceOf(operator)`, an attacker can front-run a predictable `donateRewards`/`queueNewRewards` call with a 1-wei `MasterMagpie.deposit` when the pool otherwise has zero stakers, flipping the pool from "queued/deferred" to "distribute now," and capture essentially the entire reward with `earned()` ≈ full donation.

### Finding Description
`_provisionReward` in [1](#0-0)  computes:
```
if (this.totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    ...
    rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
}
```
`totalStaked()` is derived purely from the staking-token balance held by the operator (`MasterMagpie`): [2](#0-1) . `donateRewards` is a fully public, unprivileged function that anyone can call to trigger `_provisionReward` for an already-registered reward token: [3](#0-2) . `queueNewRewards` is `onlyManager`, but its calls (typically from an automated harvest/manager bot) are visible in the mempool and therefore front-runnable: [4](#0-3) .

`earned()` computes a user's share strictly as `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) / 10**decimals`, so any user's share is proportional to their own balance relative to `totalStaked()` at the moment of the update: [5](#0-4) .

The exploit precondition is that `totalStaked() == 0` (no currently active real staker) at the moment the reward is about to be provisioned. In that state, without attacker action, the reward would simply sit deferred in `queuedRewards` until some future staker exists, and would then be split proportionally among whoever is staked at that future point. By depositing 1 wei of `stakingToken` immediately before the `donateRewards`/`queueNewRewards` transaction lands, the attacker converts `totalStaked()` from `0` to `1`, forcing the `else` branch to execute and dividing the *entire* donated/queued amount (plus any previously accumulated `queuedRewards`) by `1`. The attacker, being the sole staker, then calls `withdraw(1)` with `claim=true` to receive nearly the full reward.

No existing check prevents this: there is no minimum-stake requirement, no virtual/dead shares, no time-lock between deposit and reward accrual, and `updateReward`/`_updateFor` only checkpoints per-account state — it does not protect against a fresh, first-time staker capturing a newly materialized `rewardPerTokenStored` delta in full.

### Impact Explanation
This is a real reward/yield-theft vector: a reward intended to accrue fairly to whichever depositors are present when the pool becomes active is instead siphoned almost entirely by an opportunistic 1-wei staker who exits immediately afterward, at negligible capital cost (1 wei of staking token + gas). This matches the Immunefi impact class "theft of unclaimed yield," since deferred/queued rewards belonging conceptually to the pool are converted and paid out to an attacker who has no meaningful economic stake in the pool.

### Likelihood Explanation
- Preconditions: `totalStaked() == 0` for the target pool at the time of provisioning (new pool, or pool that has been fully emptied by withdrawals) — this is a state that does occur in practice (freshly deployed pools, low-TVL pools, or pools with full turnover).
- Capital needed: negligible (1 wei of the staking/receipt token).
- Feasibility: requires front-running a `donateRewards` (fully public, attacker can even self-trigger by waiting for their own dust deposit to precede any third-party donation) or `queueNewRewards` transaction visible in the mempool; standard MEV/front-running technique, repeatable across any newly-active or thinly-staked pool.
- Note: this specific finding is only realistic when `totalStaked()` is genuinely at or near zero already; it does not let an attacker siphon rewards from pools with substantial existing depositor balances, since the attacker cannot reduce other users' `balanceOf` values and their own dust balance would represent a negligible fraction of a nonzero, non-dust `totalStaked()`.

### Recommendation
- Enforce a minimum non-dust `totalStaked()` threshold (or "dead shares"/virtual balance, à la Uniswap V2/ERC4626 inflation-attack mitigations) before allowing `_provisionReward` to move out of the `queuedRewards` deferred path.
- Alternatively, require `MasterMagpie.deposit` to enforce a protocol-defined minimum deposit amount for first-time depositors of a pool, or lock the reward-per-token update for the first depositor for a minimum time/checkpoint window before it can be withdrawn/claimed.
- Consider requiring `queueNewRewards`/`donateRewards` to snapshot `totalStaked()` prior to accepting deposits within the same block, or add a per-block or timelock guard between `deposit` and `withdraw`/`getReward` for freshly-staked, previously-zero-balance pools.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (or `BaseRewardPoolV2`) with a mock ERC20 staking token and mock ERC20 reward token; register the reward token via constructor/`queueNewRewards`.
2. Ensure `totalStaked() == 0` (no deposits yet).
3. Attacker calls `MasterMagpie.deposit(stakingToken, 1)` (1 wei).
4. Immediately call `BaseRewardPool.donateRewards(1e18, rewardToken)` (simulating a front-run of a legitimate donation/harvest transaction), asserting `totalStaked() == 1`.
5. Assert `rewards[rewardToken].rewardPerTokenStored` jumped to `~1e18 * 10**decimals / 1` (i.e., disproportionate inflation relative to the 1-wei stake).
6. Assert `earned(attacker, rewardToken)` ≈ `1e18` (nearly the entire donation).
7. Attacker calls `MasterMagpie.withdraw(stakingToken, 1, true)` (claim=true) and asserts they receive ~1e18 reward tokens while having contributed only 1 wei of principal, confirming disproportionate capture of the donated reward.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
