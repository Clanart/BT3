### Title
Missing length checks on deserialized preprocess/share vectors cause index-out-of-bounds / remove-on-empty panics during transaction signing - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The external report describes an accounting variable (`creditedNodeETH`) that is not decremented when funds are moved, so a later subtraction (`balance - creditedNodeETH`) underflows and reverts. The analogous defect in Serai's `bitcoin-serai` wallet is a mismatch between the expected count of FROST preprocess/signature-share items (one per transaction input) and the actual length of vectors decoded from untrusted bytes via `read_preprocess` / `read_share`. `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` index and pop these attacker-length-controlled vectors without validating their sizes, converting a benign accounting inconsistency into a panic that aborts threshold transaction signing.

### Finding Description
`SignableTransaction` builds one `AlgorithmMachine` per transaction input (`sigs`), so every participant's preprocess and signature-share contribution is expected to be a `Vec` of exactly `tx.input.len()` elements [1](#0-0) .

However, deserialization accepts a `Vec` of arbitrary length — `read_preprocess` and `read_share` each produce a `Vec` whose element count is entirely determined by the bytes a participant supplies [2](#0-1) , [3](#0-2) .

Two unchecked uses follow:

1. In `sign`, the code reconstructs per-input commitment maps by directly indexing `commitments[c]` for `c in 0 .. self.sigs.len()`. If any participant's `Vec<Preprocess>` is shorter than the input count, this is an out-of-bounds index panic [4](#0-3) .
2. In `complete`, for every input the code calls `shares.remove(0)` on each participant's share vector. A participant that supplies fewer shares than inputs (e.g., an empty `Vec`) causes `Vec::remove(0)` to panic on an empty vector [5](#0-4) .

No `FrostError` is returned; both paths panic, killing the signing session (and potentially the host process/thread executing `complete`), exactly as the original bug's underflow reverts `_startSnapshot()` — the tracked/expected count and the actual vector contents diverge and the inconsistency is discovered via a runtime fault rather than a checked error.

### Impact Explanation
A single participant in a Bitcoin multisig signing session can deterministically abort transaction construction for the whole threshold group at either the sign or complete stage by sending malformed preprocess/share vectors. Since signing machines consume state (`self.sigs.drain(..)`), a panic mid-iteration also destroys the in-progress machines, preventing retry without reconstructing the session. This is a denial of service on spending vault funds — funds remain locked until a new signing session excluding the faulty participant is organized.

### Likelihood Explanation
Reachable with only public/untrusted inputs: any entity able to submit preprocess or share bytes to a `TransactionSignMachine`/`TransactionSignatureMachine` (i.e., a participant in the protocol or an integrator relaying unvalidated participant messages) triggers the panic by truncating the `Vec`. No collusion, invalid curve points, or privileged access is needed — the bytes flow directly through `read_preprocess`/`read_share` into the panicking code. Probability is high whenever a buggy or malicious peer sends a short vector.

### Recommendation
Validate vector lengths against `self.sigs.len()` / `self.tx.input.len()` before use and surface a `FrostError`/`io::Error` instead of panicking:

- In `sign` (send.rs:364-371): check `commitments.len() == self.sigs.len()` per participant before indexing, returning `Err(FrostError::...)` on mismatch.
- In `complete` (send.rs:417-419): check `shares.len() >= self.sigs.len()` (or exact equality) per participant before `remove(0)`, erroring on mismatch.
- Alternatively enforce the length in `read_preprocess`/`read_share` by reading exactly `self.sigs.len()` items.

```rust
// Participant path: a malicious/buggy signer provides a truncated preprocess Vec.
// In TransactionSignMachine::sign (networks/bitcoin/src/wallet/send.rs:364-371):
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone())) // panic: index out of bounds
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
// If attacker-controlled `commitments` Vec has fewer than self.sigs.len() elements,
// `commitments[c]` panics instead of returning FrostError.

// Similarly in TransactionSignatureMachine::complete (send.rs:417-419):
let sig = schnorr.complete(
  shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
)?;
// If a participant's deserialized `Vec<SignatureShare>` is empty, remove(0) panics.
```

Caveat: I verified the panicking sites and deserialization entry points in `send.rs`, but did not exhaustively confirm whether upstream callers in `processor/` pre-validate vector lengths; if they do, exploitability would be gated on that caller.
