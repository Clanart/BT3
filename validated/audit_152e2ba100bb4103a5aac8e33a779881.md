### Title
Unauthorized cross-wallet coin selection in `split_coins` allows spending coins belonging to a different wallet/asset than the one authorized by `wallet_id` - (File: `chia/wallet/fungibility_manager.py`)

### Summary
`FungibilityManager.split_coins` authorizes the caller against a `wallet_id` (via `get_fungible_wallet`) but then fetches the `target_coin_id` from the **global**, unscoped `WalletCoinStore` instead of verifying that the coin actually belongs to the authorized wallet. This is structurally identical to the Craft CMS bug: authorization is validated against one entity (the wallet id), while the object actually operated on (the coin) is fetched by raw ID with no ownership/scope check tying it back to that entity.

### Finding Description
`split_coins` in [1](#0-0)  validates only that `wallet_id` maps to a `Wallet` or `CATWallet` instance. It does not verify anything about `target_coin_id` relative to that wallet.

The coin used for the actual spend is then fetched with an ID-only, wallet-unscoped lookup: [2](#0-1) 

Compare this to the sibling function `combine_coins` in the same file, which explicitly filters coin lookups by `wallet_id=wallet.id()`: [3](#0-2) [4](#0-3) 

`WalletCoinStore.get_coin_record(coin_name)` performs a raw primary-key lookup with no `wallet_id` predicate at all: [5](#0-4) 

whereas `get_coin_records(...)` (used correctly by `combine_coins`) supports an explicit `wallet_id` filter: [6](#0-5) 

The net effect: an RPC caller can invoke `split_coins` with `wallet_id` set to wallet A (e.g., their unrestricted XCH wallet or a CAT wallet they legitimately control) while supplying `target_coin_id` for a coin that is actually tracked under a *different* wallet entry in the same node's wallet database (e.g., a different CAT/asset wallet, a Clawback-type coin, or a coin belonging to another sub-wallet of the same keyring). The amount/ownership checks in `split_coins` (`coin.amount < total_amount`) only look at the raw `Coin` amount, not at which wallet's asset the coin actually represents, and the subsequent `wallet.generate_signed_transaction(...)` call at [7](#0-6)  is invoked using wallet A's spend-construction logic against a coin that was never scoped/validated as belonging to wallet A.

### Impact Explanation
This breaks the same authorization invariant class as the reported CVE: the check is performed on the "container" (wallet_id) while the "target object" (coin) is trusted by raw ID. Concretely, this can:
- Cause the wrong wallet's spend-construction path (standard vs. CAT, or CAT-A vs. CAT-B) to build a spend for a coin it does not actually own/manage, producing incorrect asset-type handling, incorrect lineage/asset-id assumptions, or wallet-state corruption (e.g., staging a `TransactionRecord` and marking/selecting a coin as spent under the wrong wallet's bookkeeping) — this can desynchronize the wallet's local coin-store accounting from on-chain reality across sub-wallets tracked by the same fingerprint (analogous to "coin-set divergence" locally).
- Depending on whether the actual on-chain puzzle hash of the mismatched coin coincidentally matches what the authorized wallet's `generate_signed_transaction` expects to sign for, this is a path toward constructing spends for coins outside the intended wallet scope without the intermediate ownership check that `combine_coins` performs.

I was not able to fully verify, within the available tool budget, whether `CATWallet.generate_signed_transaction`'s internal puzzle/lineage reconstruction ultimately re-derives the puzzle hash strictly from the coin's own on-chain data (which would cause full-node validation to reject a mismatched spend) or partly trusts wallet-level asset-id assumptions that could be satisfied by an attacker-selected coin from a different wallet. This distinction determines whether the bug is "wallet accounting corruption only" (Medium) or can produce an actually accepted spend outside the intended asset/wallet scope (High). Given the missing tool budget to inspect `cat_wallet.py`'s `generate_signed_transaction` body and `unsigned_spend_bundle_for_spendable_cats`, this should be validated before finalizing severity.

### Likelihood Explanation
`split_coins` is reachable by any authenticated wallet RPC caller via `WalletRpcApi.split_coins` → `FungibilityManager.split_coins`, requiring only a `wallet_id` the caller controls and an arbitrary `target_coin_id` string, both attacker-supplied request parameters. No special privilege beyond normal wallet-RPC access is needed, and the missing check is a simple oversight relative to the parallel, correctly-scoped `combine_coins` implementation in the same file.

### Recommendation
In `chia/wallet/fungibility_manager.py`, `split_coins` should look up the target coin scoped by wallet, mirroring `combine_coins`:
- Replace `self.coin_store.get_coin_record(target_coin_id)` with a wallet-scoped query, e.g. `self.coin_store.get_coin_records(wallet_id=wallet.id(), coin_id_filter=HashFilter.include([target_coin_id]))`, and reject the request if the returned record's `wallet_id` does not match `wallet.id()`.
- Add an explicit assertion that `coin_record.wallet_id == wallet.id()` before using the coin in `generate_signed_transaction`.

### Proof of Concept
1. As an authenticated wallet-RPC caller with at least two wallets under the same keyring (e.g., XCH wallet id 1 and CAT wallet id 2, or two distinct CAT wallets id 2 and id 3).
2. Note a coin id, `target_coin_id`, that belongs to wallet id 3 (per `wallet_coin_store` records).
3. Call `split_coins` RPC with `wallet_id=2` (a *different* wallet) and `target_coin_id=<coin owned by wallet 3>`.
4. Observe that `FungibilityManager.split_coins` (chia/wallet/fungibility_manager.py:47-56) fetches and operates on the coin without ever checking that it belongs to wallet 2, unlike `combine_coins`, which filters coin lookups by `wallet_id=wallet.id()` (lines 101-111, 140-156).
5. This demonstrates the missing wallet-ownership check identified above; further validation of on-chain spend acceptance in `CATWallet.generate_signed_transaction` is needed to confirm end-to-end monetary impact.

        """Returns CoinRecord with specified coin id."""
        async with self.db_wrapper.reader_no_transaction() as conn:
            rows = list(await conn.execute_fetchall("SELECT * from coin_record WHERE coin_name=?", (coin_name.hex(),)))

        if len(rows) == 0:
            return None
        return self.coin_record_from_row(rows[0])
