Based on my investigation, I've confirmed a genuine analog vulnerability in GitHub Desktop that mirrors the "reassignment leaves stale state / dual trust" pattern from the bribe issue: a background repository sync silently accepts a new authoritative value from an external, attacker-influenceable source and rewrites a locally-trusted value without user consent, and the guard meant to prevent unwanted overwrites is insufficient because it only checks protocol equality and staleness of the cache — not the target host/identity.

### Title
Silent, unattended rewrite of a repository's git remote URL from GitHub API `clone_url` allows a repo owner/transferer to redirect victims' pushes/fetches to an attacker-controlled remote - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` automatically overwrites the local `origin` remote URL whenever Desktop refreshes a repository's associated `GitHubRepository` from the API and detects that the API's `clone_url` no longer matches the locally configured remote, as long as the local remote still matches what was last cached (`remoteUrlUnchanged`) and the URL protocol is unchanged [1](#0-0) . This refresh path (`repositoryWithRefreshedGitHubRepository`) runs automatically and silently in the background: on periodic background fetch [2](#0-1) , on account-change refresh [3](#0-2) , and via `withRefreshedGitHubRepository` used before push/fetch/other operations [4](#0-3) .

### Finding Description
The broken invariant is analogous to the bribe issue: when the authoritative association between a local trusted state (the git `origin` remote) and an external identity (the GitHub repository record, identified by owner/name -> API `clone_url`) changes, Desktop automatically migrates the local state to the new value instead of requiring a fresh, explicit user decision.

`repositoryWithRefreshedGitHubRepository` calls the GitHub API `fetchRepository(owner, name)` using the endpoint/owner/name previously associated with the repository, then unconditionally calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [5](#0-4) . Inside `updateRemoteUrl`, the only checks performed before rewriting the local remote are:
- the URL scheme (protocol) is unchanged,
- the currently configured remote still equals the *previously cached* `gitHubRepository.cloneURL` (i.e., it hasn't been manually altered since the last sync),
- the new API `clone_url` differs from the current remote. [6](#0-5) 

None of these checks validate that the new `clone_url` still points to the same repository identity/owner the user originally trusted — they only guard against clobbering a URL the user manually edited. Any legitimate GitHub action that changes a repository's canonical `clone_url` for the same owner/name lookup (e.g., the repository owner transferring ownership to a different account, or renaming in a way that the API redirects/returns a different `clone_url`) is silently trusted and pushed into the user's local `.git/config` via `gitStore.setRemoteURL` [7](#0-6) , which shells out to `git remote set-url` [8](#0-7) .

The repository owner is exactly the kind of "attacker who controls a GitHub API object" the task's Valid Impact criteria describe: no local access, no admin rights, and no credential leakage from the victim are required. The attacker only needs to control a GitHub repository that the victim has already cloned (e.g., a public repo the victim contributes to), then transfer/rename it so that the API's `clone_url` for the same lookup key returns an attacker-controlled destination.

### Impact Explanation
Once the origin remote is silently rewritten, all subsequent `git push`/`git fetch`/`git pull` operations initiated through Desktop's UI (which always use `gitStore.defaultRemote`/`currentRemote`) transparently target the new, attacker-chosen URL [9](#0-8) [10](#0-9) . This is "silent corruption of what the user commits or pushes": the user believes they are pushing to the repository they originally added, but their code, history, and potentially credentials-adjacent metadata are sent to a different remote without any dialog, confirmation, or visible diff — the change happens as a side effect of a background indicator refresh or an account switch.

### Likelihood Explanation
The refresh path is exercised extremely often and mostly invisibly: every 15/30/60 minutes via background fetch/indicator updaters [11](#0-10) [12](#0-11) , and whenever the signed-in account changes [3](#0-2) . No user interaction beyond normal usage of an already-added repository is required, and the existing `remoteUrlUnchanged`/protocol checks were designed to avoid clobbering manual edits, not to validate repository identity, so they do not stop this path.

### Recommendation
Before silently rewriting the remote URL, `updateRemoteUrl` (or its caller) should verify that the new `clone_url` still corresponds to the same repository identity the user trusted (e.g., compare the API-reported repository `id`/node id against the previously stored `GitHubRepository`, not just owner/name derived from the local record), and require explicit user confirmation (similar to the existing manual "Repository Settings" remote-URL change flow) whenever the destination host/owner changes as a result of an API-driven update rather than a user-initiated action.

### Proof of Concept
1. Victim clones `https://github.com/attacker/legit-repo` and Desktop stores `GitHubRepository { endpoint, owner: attacker, name: legit-repo, cloneURL: https://github.com/attacker/legit-repo }`, with `origin` remote pointing there.
2. Attacker (owns/administers `legit-repo`) transfers the repository to a different account/organization the attacker controls, or renames it such that the GitHub API's `clone_url` response for that repo id now differs (a routine, self-service, unprivileged GitHub.com operation for a repo the attacker owns).
3. On the victim's next background fetch/indicator refresh/account-switch, Desktop calls `api.fetchRepository(owner, name)` and receives the new `clone_url` [13](#0-12) .
4. Because the victim's local remote still equals the old cached `cloneURL` and the protocol is unchanged, `updateRemoteUrl` calls `gitStore.setRemoteURL(origin, newCloneURL)` with no user prompt [14](#0-13) .
5. The victim's next push/fetch via Desktop's UI silently targets the attacker's new destination.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
