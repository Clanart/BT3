### Title
Path-containment check in `resolveWithin` uses unanchored string prefix match, allowing symlink/sibling-path escape from a cloned repository - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` (and its `resolveWithinPosix`/`resolveWithinWin32` variants) is Desktop's canonical guard against path traversal and symlink escapes when resolving attacker-influenced relative paths against a repository root. Its final containment check compares `realResolved.startsWith(realRoot)` as raw strings, without verifying that the character immediately following `realRoot` is a path separator. This is the same class of bug as the `Rent::default` report: a cheap, wrong stand-in (`String.startsWith`) is substituted for the correct authority check (a proper filesystem-boundary comparison), so the guard can be satisfied by data it was meant to reject.

### Finding Description [1](#0-0) 

```
  const resolved = resolve(normalizedRoot, normalizedRelative)
  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)
  return realResolved.startsWith(realRoot) ? resolved : null
```

`realRoot` and `realResolved` are compared with plain `startsWith`. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo`, then `/Users/victim/Documents/GitHub/myrepo-backup/secret.txt` (or `myrepo.wiki`, `myrepo.bak`, `myrepo2`, etc.) also satisfies `startsWith(realRoot)` even though it is a completely different, sibling filesystem entry outside the intended root. The check should instead verify `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`.

`resolveWithin` exists specifically to stop symlinks committed inside a cloned repository from escaping the working directory: an attacker who controls the contents of a cloned/fetched repository can commit a symlink whose target is an absolute path chosen to exploit this exact string-prefix weakness (a sibling directory/file whose name happens to start with the victim's repo folder name — a very common naming pattern: `.git`-adjacent backups, `-old`, `-bak`, `.wiki`, numbered clones, etc.). Because the symlink resides physically inside the repo, the pre-`realpath` `resolved` path is legitimately "under" root; it is only the post-`realpath` boundary check that is supposed to catch the escape, and that check is the one that is broken.

Two concrete, attacker-reachable call sites consume this guard's result:
- `app/src/ui/dispatcher/dispatcher.ts` `openRepositoryFromUrl` resolves an attacker-supplied `filepath` from a `x-github-client://openRepo/...&filepath=...` deep link against `repository.path` and, if `resolveWithin` returns non-null, calls `shell.showItemInFolder(resolved)`. [2](#0-1) 
- `app/src/lib/copilot-conflict-context.ts` resolves conflicted-file paths against the repository `workingDirectory` and, if within bounds, reads the file's content off disk to build a prompt/context that is sent to the Copilot merge-conflict-resolution feature. [3](#0-2) [4](#0-3) 

Both call sites trust `resolveWithin`'s null-vs-non-null result as the sole containment decision; neither re-validates the resolved path independently.

### Impact Explanation
An attacker who controls a repository's contents (a malicious clone/fetch, or a fork used in an "Open in Desktop"/deep-link flow) can plant a symlink that, combined with the broken boundary check, is treated as "inside the repo" when it actually resolves to a sibling path outside it. Via `copilot-conflict-context.ts` this allows silent exfiltration of file contents outside the repository boundary to the external Copilot API when the user resolves a merge conflict — a credential/data-exfiltration primitive squarely in scope. Via `dispatcher.ts`'s deep-link `filepath` handling it allows a crafted "Open in Desktop"/browser link, combined with a matching repo layout, to reveal filesystem locations outside the cloned repository that the guard was explicitly designed to keep out of reach.

### Likelihood Explanation
Exploitation requires the victim to (a) already have a locally cloned copy of the attacker's (or a forked) repository whose containing folder name is guessable/common, and (b) either resolve a conflict that reads the symlinked file (feeding the Copilot flow) or click a crafted deep link with a `filepath` parameter. This is not trivial to hit reliably in every environment (it depends on a sibling path existing/being guessable), which lowers likelihood relative to a universally reachable bug, but it does not require local/physical access, admin rights, prior malware, or leaked credentials — only an attacker-controlled repository and normal user interaction (opening a link or resolving a conflict), matching the allowed threat model.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to be separator-anchored, e.g.:

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the same `join`/`resolve`/`normalize` option set's separator, or `options === Path.win32 ? '\\' : '/'` depending on the variant used), and add regression tests for sibling-directory-name collisions (e.g., root `.../repo` vs. resolved `.../repo-evil`) to `app/test/unit/path-test.ts`.

### Proof of Concept
1. Victim clones a repository to `/Users/victim/Documents/GitHub/myrepo`.
2. Attacker's malicious branch/fork contains a symlink at `notes` whose target is an absolute path `/Users/victim/Documents/GitHub/myrepo-backup/id_rsa` (or any sibling path sharing the `myrepo` prefix that is likely to exist, e.g. `.wiki`, `-old`, `.bak` conventions).
3. Victim triggers a code path that calls `resolveWithin('/Users/victim/Documents/GitHub/myrepo', 'notes')`:
   - `resolved` = `.../myrepo/notes` (inside root pre-symlink resolution).
   - `realResolved` = `realpath(resolved)` = `/Users/victim/Documents/GitHub/myrepo-backup/id_rsa`.
   - `realRoot` = `/Users/victim/Documents/GitHub/myrepo`.
   - `realResolved.startsWith(realRoot)` evaluates `true` because `"myrepo-backup"` starts with `"myrepo"`, so the function incorrectly returns the resolved path as safe.
4. Depending on call site, this either causes `shell.showItemInFolder` to reveal a location outside the repo (`dispatcher.ts`) or causes the file's contents to be read and forwarded to the Copilot conflict-resolution API (`copilot-conflict-context.ts`), leaking data the user never intended to expose.
