Based on my research, I found a strong analog: the account key decoding path validates against nested `AccountKeyRoleBased` (only one level deep is checked), but this is explicitly guarded — `checkAccountKeyZeroValues` and tx-pool validation reject `ErrNestedCompositeType` at the semantic level, not at the RLP decode level. However, this rejection happens **after** decoding, and the RLP `DecodeRLP` for `AccountKeyRoleBased`/`AccountKeySerializer` is itself mutually recursive with no depth limit before that validation ever runs.

### Title
Unbounded recursion in AccountKey RLP decoding allows pre-validation stack overflow denial of service - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeySerializer.DecodeRLP` [1](#0-0)  and `AccountKeyRoleBased.DecodeRLP` [2](#0-1)  are mutually recursive: a `RoleBased` key decodes a list of sub-keys, each of which is decoded through a fresh `AccountKeySerializer`, which in turn can itself be another `RoleBased` key. There is no recursion-depth check performed during decoding — the "nested RoleBasedKey is not allowed" rule is enforced only afterwards, in `checkAccountKeyZeroValues` (RPC path) [3](#0-2)  or via `ErrNestedCompositeType` in tx-pool/EVM validation, which is reached only *after* the full account key value has already been fully decoded from RLP.

### Finding Description
An attacker can submit an `AccountUpdate`/`AccountCreation`/`FeeDelegatedAccountUpdate*` transaction (via `eth_sendRawTransaction` or equivalent) whose `AccountKey` field is a deeply nested `AccountKeyRoleBased` (a role key containing a role key containing a role key, ...). Because `DecodeRLP` for `AccountKeyRoleBased` calls `rlp.DecodeBytes` recursively for each encapsulated key blob with no depth counter, decoding proceeds through the full call stack (`DecodeRLP -> rlp.DecodeBytes -> AccountKeySerializer.DecodeRLP -> AccountKey.DecodeRLP -> ...`) before any semantic validation (`checkAccountKeyZeroValues`/nested-composite-type check) ever executes. This mirrors the MongoDB BIT-2025-6710 pattern: a structured decoder that recurses into user-controlled nested constructs without a depth limit, causing a stack overflow crash before authorization/validation logic runs.

This differs from the trie/RLP `decodeNode` case (`storage/statedb/node.go`) which is only reachable via P2P snap-sync from another node (explicitly out of scope) — the AccountKey decode path is reachable directly from a submitted transaction's payload, decoded during transaction ingestion (`blockchain/types/account/account_common.go` `DecodeRLP` [4](#0-3)  and via `types.NewTransactionWithMap`/RLP unmarshalling in the tx pool and `EthAPI.DecodeAccountKey`) which any unprivileged sender or public RPC caller can trigger.

### Impact Explanation
A successful stack overflow crashes the node process handling the transaction (mempool ingestion, block validation, or `klay_decodeAccountKey`/`klay_encodeAccountKey` RPC call), causing denial of service. Since account-key decoding occurs during transaction admission (before nonce/balance/signature-role checks complete) and in a public RPC endpoint that takes raw encoded bytes directly from an unauthenticated caller, this is a pre-authentication crash vector, consistent with the "High" severity classification of the reference CVE.

### Likelihood Explanation
Likelihood is High: constructing a deeply nested `AccountKeyRoleBased` RLP blob is trivial and requires no special privileges — just a well-formed transaction (or a call to `klay_decodeAccountKey`) with recursively nested key bytes. The `TestAccountUpdateRoleBasedKeyNested` test [5](#0-4)  confirms that only a single level of nesting is checked and enforced at the semantic layer — but that check runs only after decoding completes, meaning arbitrarily deep nesting bypasses this check entirely at the decode stage and can exhaust the goroutine stack before `ErrNestedCompositeType` is ever returned.

### Recommendation
Add an explicit recursion-depth counter/limit to `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if nesting depth exceeds 1, matching the "no nested RoleBasedKey" invariant), enforced *during* decode rather than only after the value is fully materialized. Additionally consider adding a generic RLP decode-depth guard analogous to Go's `encoding/json` 10,000-level protection.

### Proof of Concept
1. Construct a byte blob `B0 = RLP(AccountKeyNil or AccountKeyPublic)`.
2. Iteratively wrap: `B_{i+1} = RLP(AccountKeySerializer{keyType: RoleBased, key: RLP-list-of([B_i])})`, repeating tens of thousands of times to build a deeply nested `AccountKeyRoleBased`.
3. Embed `B_N` as the `AccountKey` field of an `TxTypeAccountUpdate` (or similar) transaction, sign it validly (only the outer structure needs a valid signature/nonce to reach decode paths, or call `klay_decodeAccountKey(B_N)` directly via public RPC, which requires no signature at all).
4. Submit via `eth_sendRawTransaction` or call `klay_decodeAccountKey` — the recursive `DecodeRLP` calls will consume stack frames proportional to `N`, crashing the node with a stack overflow before any semantic nested-key check is reached.

*Note: I was not able to fully verify the exact goroutine stack limits in this Go runtime configuration, nor definitively trace every RLP field consumer (e.g., whether tx-pool basic sanity checks run before or after full account-key decode in all code paths); the `klay_decodeAccountKey` RPC path (`api/api_kaia.go` lines 166-173) is the most directly and unambiguously reachable trigger, since it performs `rlp.DecodeBytes` on caller-supplied bytes with zero prior validation.*

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
