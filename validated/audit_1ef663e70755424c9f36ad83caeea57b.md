### Title
`SignableTransaction::new` excludes the OP_RETURN `data` output from the transaction weight/vbytes used for the required-fee and `MAX_STANDARD_TX_WEIGHT` checks - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/bsaldua/serai--007/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
The maximum-size accounting in `SignableTransaction::new` is computed over a transaction that does not include the OP_RETURN `data` output that is actually appended to the final transaction. Analogous to the ICHI bug — where `curPosSize` measured only the latest deposit rather than the real position size — Serai measures the weight/fee of only the declared payments while the transaction that is signed carries an additional output. The result is a signed transaction whose real vsize and fee rate differ from what was validated, and which can silently exceed `MAX_STANDARD_TX_WEIGHT` or underpay the minimum relay fee.

### Finding Description
In `SignableTransaction::new`, an optional OP_RETURN output carrying up to 80 bytes of caller-supplied `data` is pushed into `tx_outs` before the weight is computed, yet the weight calculation is invoked on `payments` alone:

```rust
// networks/bitcoin/src/wallet/send.rs

// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
...
if weight > u64::from(bitcoin::policy::MAX_STANDARD_TX_WEIGHT) {
  Err(TransactionError::TooLargeTransaction)?;
}
```

`calculate_weight_vbytes` builds its template transaction strictly from `inputs` and `payments` (plus an optional change output):

```rust
fn calculate_weight_vbytes(
  inputs: usize,
  payments: &[(ScriptBuf, u64)],
  change: Option<&ScriptBuf>,
) -> (u64, u64) {
```

The `data` output is never represented in any of the calls. Consequently:

- `vbytes` and `needed_fee` are under-estimated by the serialized size of the OP_RETURN output (up to ~91 bytes: 8-byte value, script length, `OP_RETURN` + push opcodes + 80 bytes of data).
- The `TooLowFee` check compares a minimum-relay requirement derived from the *smaller* measured vsize against a fee that is correct only for that smaller transaction. The signed transaction, once the OP_RETURN output is appended, pays `needed_fee` over a strictly larger real vsize — i.e., its effective fee rate is lower than `fee_per_vbyte` and can fall below `DEFAULT_MIN_RELAY_TX_FEE`.
- The `weight > MAX_STANDARD_TX_WEIGHT` check is evaluated against a weight missing the data output, so a transaction can pass the check while the final signed `self.tx` exceeds the standardness weight limit.

The change-output branch has the same defect: `fee_with_change` is computed over `payments` + change, still ignoring the already-pushed OP_RETURN output.

`data` is attacker-influenced transaction content (Serai embeds `InInstruction` data into refund/forwarding transactions via this code path), so an external party supplying instruction data causes the multisig to produce a transaction whose committed fee and weight do not match what was validated — and the mismatch is then frozen into the FROST signatures over the sighashes.

### Impact Explanation
A `SignableTransaction` constructed with a `data` payload produces a Bitcoin transaction that pays a fee below the rate required for relay when `fee_per_vbyte` is at/near the minimum relay fee, or that exceeds `MAX_STANDARD_TX_WEIGHT` when the payment set is already near the limit. In either case the fully-signed multisig transaction is non-standard and will be rejected by Bitcoin node mempools. Because the inputs, change amount, and fee are all committed by the threshold signatures, the UTXOs selected for that plan cannot be spent by the produced transaction — the multisig has committed a spend that the network will not accept, forcing a re-plan/re-sign cycle and leaving the involved outputs temporarily unspendable by the protocol. This is the same failure mode as the ICHI finding: an enforcement bound evaluated against an incomplete measurement of the object actually produced.

### Likelihood Explanation
Any external party able to cause Serai to emit a Bitcoin transaction carrying instruction `data` (e.g., via `InInstruction`-bearing flows that reach `SignableTransaction::new`) controls whether the OP_RETURN output exists and its size (up to the 80-byte cap checked separately at `data.len() > 80`). The defect is deterministic whenever `data.is_some()`; whether it bites depends on the resulting fee rate or weight crossing a standardness boundary. When `fee_per_vbyte` equals the minimum relay fee, the shortfall is guaranteed for every transaction carrying data. The worst case — exceeding `MAX_STANDARD_TX_WEIGHT` — additionally requires the underlying payment set to be near the limit, which is less common given input chunking to `MAX_INPUTS`, hence this is rated Medium rather than High.

### Recommendation
Include the OP_RETURN output in the transaction template used by `calculate_weight_vbytes` — e.g., compute weight/vbytes over the final `tx_outs` (payments + data + change) rather than only `payments`, or extend `calculate_weight_vbytes` to accept the data output. The `needed_fee`, `TooLowFee`, and `MAX_STANDARD_TX_WEIGHT` checks must all be evaluated against the exact set of outputs the signed transaction will contain.

### Proof of Concept
```rust
// networks/bitcoin (tests) — demonstrates the accounting gap
use bitcoin::{ScriptBuf, hashes::Hash};

// One confirmed received output controlled by the group key
let inputs = vec![received_output]; // value >= DUST + fee

// Minimal payment set, plus an 80-byte OP_RETURN payload (attacker-instruction data)
let payments = [(p2tr_script_buf(key).unwrap(), 546u64)];
let data = vec![0xAAu8; 80];

// fee_per_vbyte at the minimum relay boundary
let tx = SignableTransaction::new(inputs, &payments, None, Some(data), 1).unwrap();

// needed_fee was computed WITHOUT the OP_RETURN output:
// measured vbytes excluded ~91 bytes, so tx.needed_fee() corresponds to a smaller TX.
let real_vsize = tx.transaction().vsize() as u64;
let implied_rate = tx.needed_fee() / real_vsize; // can be < 1 sat/vbyte → below min relay

// The standardness check also ran on the undercounted weight:
assert!(tx.transaction().weight().to_wu() >= /* check bound applied to smaller tx */);
```
Constructing the same call with a payment set already within ~91 bytes of `MAX_STANDARD_TX_WEIGHT` produces a `SignableTransaction` that passes `TooLargeTransaction` checking yet whose `self.tx` exceeds the standard weight limit — a signed transaction Bitcoin will not relay, exactly mirroring the ICHI report's pattern of a limit enforced against a stale/incomplete size measurement.
