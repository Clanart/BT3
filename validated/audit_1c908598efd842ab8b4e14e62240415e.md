## Title
GitHub token exfiltration via credential-helper trampoline handing out real account tokens to any host requested by an untrusted submodule/hook — (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The external report's broken invariant is: an unauthenticated callback blindly trusts caller-supplied data (an address) to decide whose funds to move, instead of verifying that the caller is the legitimate, expected counterparty. The same class of bug — "trust attacker-supplied context to release a secret, without verifying the request actually originates from the operation the secret was meant for" — exists in Desktop's Git credential trampoline. Desktop configures `credential.helper=desktop` globally for *every* git subprocess spawned during a remote operation via `GIT_CONFIG_PARAMETERS`, and that configuration is inherited by any subcommands git spawns on its own (submodules, filters, hooks). The trampoline's `get` handler then matches the credential request purely by **URL origin** against the user's signed-in accounts and returns the real account token — with no check that the request is actually tied to the URL/remote the user intended to operate on.

### Finding Description
When Desktop performs any remote Git operation it wraps the invocation in `withTrampolineEnv`, which injects: [1](#0-0) 

Crucially it sets `credential.helper=desktop` via `GIT_CONFIG_PARAMETERS`, which (per the surrounding comment) is deliberately used instead of `-c` precisely because it *is* inherited by subprocesses Git spawns internally, such as Git LFS filters and — by the same mechanism — submodule operations.

`clone.ts` always clones `--recursive`, so any submodules referenced by a hostile repository are initialized automatically as part of the same operation and inherit this environment: [2](#0-1) 

When Git needs credentials for *any* URL encountered during that operation (the top-level remote, an LFS endpoint, or a submodule URL), it invokes the configured `credential.helper=desktop`, which routes into `createCredentialHelperTrampolineHandler`: [3](#0-2) 

The `get` command path calls `getCredential`, which first tries `getGitHubCredential`: [4](#0-3) 

`findGitHubTrampolineAccount` decides whether to hand out a signed-in account's real token purely by comparing the **origin** of the requested credential URL to the user's stored account endpoints — it has no notion of which repository, remote, or user-initiated operation the request is "supposed" to belong to: [5](#0-4) 

Because the trampoline server itself only validates that the request carries a currently-active `trampolineToken` (proving it's part of *some* live git operation Desktop started), not that the specific credential URL matches the operation's intended remote: [6](#0-5) 

any URL that Git asks credentials for during that operation — including one contributed entirely by attacker-controlled content such as a `.gitmodules` entry pointing at `https://github.com/...` — will transparently receive the signed-in user's real GitHub credential if the origin matches, exactly as the C-04 callback handed real user tokens to whatever address the (attacker-supplied) `data` decoded to.

This mirrors the original bug's structure precisely: the privileged action (releasing the token) is gated only on "is this a currently valid session/token", not on "does this specific request correspond to the resource the session was created for."

### Impact Explanation
An attacker who controls a cloned/fetched repository (e.g. published on GitHub, or fetched as a fork/PR) can add a submodule whose URL is a same-origin-as-GitHub path requiring authentication (e.g. a private repo URL, or a URL engineered to return `401`/`WWW-Authenticate`). When the victim clones or fetches this repository through Desktop (`--recursive` by default), Desktop's git subprocess will silently invoke the credential helper for that submodule URL, and the helper will hand over the victim's actual GitHub OAuth token bound to that origin — without any prompt, and without verifying the request corresponds to a resource the user actually intended to authenticate against. If the submodule URL is one the attacker controls indirectly (e.g. a URL under a path they can inspect via server logs, or that echoes the `Authorization` header), this results in direct token exfiltration, analogous to "direct loss of funds" in the source report. This is high impact: full account token compromise.

### Likelihood Explanation
Likelihood is high for the "any signed-in account token is released to a same-origin request during a recursive clone/fetch" pattern, since:
- Desktop clones with `--recursive` unconditionally.
- `GIT_CONFIG_PARAMETERS` credential.helper configuration is explicitly designed to be inherited by nested git invocations.
- `findGitHubTrampolineAccount` only checks origin equality, with no binding to the specific remote/operation.

No local access, admin rights, or social engineering beyond the normal act of cloning/fetching a repository (a core, expected Desktop workflow) is required.

### Recommendation
Bind trampoline credential requests to the specific remote/operation they were issued for, not just to a live trampoline token:
- Track the set of remote URLs (and their expected origins) associated with each `trampolineToken`/operation when it is created (e.g., in `withTrampolineEnv`/`envForRemoteOperation`), and reject or explicitly re-confirm credential requests whose origin doesn't match the operation's declared remote(s).
- For submodule/LFS URLs that resolve to a different origin than the top-level remote, require explicit user confirmation before releasing a stored GitHub token, rather than silently matching by origin alone.
- Consider scoping `credential.helper=desktop` so that it does not automatically release first-party GitHub account tokens to arbitrary same-origin URLs discovered inside an untrusted repository's submodule/LFS configuration.

### Proof of Concept
1. Attacker creates and publishes a public repository `evil/repo`.
2. In `evil/repo`, add a `.gitmodules` entry with `url = https://github.com/<attacker-chosen-private-or-401-path>`.
3. Victim (signed into Desktop with a GitHub account) clones `evil/repo` via Desktop, which runs `git clone --recursive ...` per `app/src/lib/git/clone.ts` lines 88-93.
4. During recursive submodule initialization, Git requests credentials for `https://github.com/<attacker-chosen-path>` using the inherited `credential.helper=desktop` config (`app/src/lib/trampoline/trampoline-environment.ts` lines 123-146).
5. `createCredentialHelperTrampolineHandler` → `getGitHubCredential` → `findGitHubTrampolineAccount` matches by origin (`github.com`) only and returns the victim's real account token (`app/src/lib/trampoline/trampoline-credential-helper.ts` lines 50-57; `app/src/lib/trampoline/find-account.ts` lines 20-29), which Git then sends as an `Authorization` header to the attacker-chosen path — exfiltrating the token to the attacker's server logs/endpoint.

export const createCredentialHelperTrampolineHandler: (
  store: AccountsStore
) => TrampolineCommandHandler = (store: Store) => async command => {
  const firstParameter = command.parameters.at(0)
  if (!firstParameter) {
    return undefined
  }

  const { trampolineToken: token } = command
  const input = parseCredential(command.stdin)

  if (__DEV__) {
    debug(
      `${firstParameter}\n${command.stdin
        .replaceAll(/^password=.*$/gm, 'password=***')
        .replaceAll(/^(.*)$/gm, '  $1')
        .trimEnd()}`
    )
  }

  try {
    if (firstParameter === 'get') {
      const cred = await getCredential(input, store, token)
      if (!cred) {
        const endpoint = `${getCredentialUrl(input)}`
        info(`could not find credential for ${endpoint}`)
        setHasRejectedCredentialsForEndpoint(token, endpoint)

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
