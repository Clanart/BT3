### Title
`SignableTransaction`/`TransactionSignMachine` trust the claimed `TxOut` value and `OutPoint` in `ReceivedOutput` — a fabricated input causes the threshold set to sign a transaction spending non-existent funds - (File: networks/bitcoin/src/wallet/mod.rs, networks/bitcoin/src/wallet/send.rs)

### Summary
The DODO bug is a failure to verify that the actual value received (`msg.value`) matches the declared value (`fromTokenAmount`), letting an attacker spend funds that were never supplied. The Serai analog lives in `bitcoin-serai`: `ReceivedOutput::read` deserializes an `offset`, a full `TxOut` (including `value`), and an `OutPoint` from untrusted bytes, and `SignableTransaction::new` uses the *claimed* `output.value` for its payment/fee/change accounting while `TransactionSignMachine::sign` commits those claimed prevouts into the Taproot sighash. Only the `script_pubkey` is ever cross-checked against the supplied offset (`multisig`); the claimed value and the outpoint are never validated against the chain. An untrusted party can therefore hand the signer set a `ReceivedOutput` describing an output that does not exist, or whose value is inflated.

### Finding Description
`ReceivedOutput` is a plain data container whose `read` accepts arbitrary bytes: [1](#0-0) 

`SignableTransaction::new` then performs all funds accounting purely from `input.output.value`: [2](#0-1) [3](#0-2) 

The only consistency check in the signing path is that `p2tr_script_buf(offset.group_key())` equals the prevout's `script_pubkey` — value and outpoint are unchecked: [4](#0-3) 

Finally, `sign` commits `Prevouts::All(&self.tx.prevouts)` — i.e., the *claimed* `TxOut`s — into `taproot_key_spend_signature_hash`: [5](#0-4) 

An attacker who can feed bytes to `ReceivedOutput::read` (or otherwise supply inputs to `SignableTransaction::new`) can register a legitimate offset/script pair they caused to be scanned (e.g., via `Scanner::register_offset`/`scan_transaction` which match on `script_pubkey` alone, [6](#0-5) ) and then rewrite the serialized `ReceivedOutput` to carry an arbitrary `value` or a fabricated `outpoint`. The resulting `SignableTransaction` computes change and fee on phantom sats, and the FROST machines produce a threshold signature for a transaction that is invalid on-chain (the prevout amounts committed in `Prevouts::All` do not match the real UTXO set, or the outpoint does not exist).

### Impact Explanation
Funds are reported/represented as spendable inputs that are not spendable: the protocol can be induced to treat a fabricated UTXO (or an inflated balance) as real input value, produce change outputs and signatures accordingly, and emit a signed transaction that can never confirm. Where the aggregated inputs mix real wallet outputs with the fabricated one, the honest outputs' value is locked into a dead transaction construction and every FROST signing session built on the forged input is wasted; if the claimed value is *deflated* relative to a real output, the `NotEnoughFunds` check or change arithmetic misbehaves in the attacker's favor regarding fee/change sizing. This mirrors the DODO issue's core defect — accounting performed on a declared amount rather than the actual received value.

### Likelihood Explanation
Reachable by any unprivileged party able to supply the untrusted bytes consumed by `ReceivedOutput::read` or to influence the input list given to `SignableTransaction::new` (e.g., a participant proposing inputs, or bytes relayed between validators). Constructing the forgery requires only a `Scalar` offset (arbitrary), a `TxOut`, and an `OutPoint` — all fully attacker-controlled fields with no authentication on `read`. Likelihood is bounded by deployment specifics of how `ReceivedOutput`s are transported, so Medium rather than High.

### Recommendation
Treat `ReceivedOutput` as a claim, not a fact. Before `SignableTransaction::new` (or at `ReceivedOutput` ingestion), verify each input against the node/RPC: that `outpoint` exists, is unspent, is mature (non-coinbase or ≥100 confs), and that the on-chain `TxOut` equals the claimed `value` and `script_pubkey`. At minimum, `multisig`/`sign` should additionally assert the claimed `TxOut` was sourced from `Scanner::scan_transaction` output rather than `ReceivedOutput::read`, or carry a proof of provenance. Do not accept `ReceivedOutput`s deserialized from peers for signing without on-chain confirmation.

### Proof of Concept

let mut bytes = Vec::new();
// offset the attacker previously got registered / matches a scanned script
bytes.extend(real_offset.to_bytes());
// TxOut with an INFLATED value (e.g., 21e14 sats) but the *real* script_pubkey
bytes.extend(serialize(&TxOut {
  value: Amount::from_sat(21_000_000_000_000_00),
  script_pubkey: real_p2tr_script.clone(),
}));
// OutPoint pointing to a non-existent or dust output
bytes.extend(serialize(&OutPoint::new(Txid::from_byte_array([0x41; 32]), 0)));

let forged = ReceivedOutput::read(&mut &bytes[..]).unwrap();
// Passes multisig() because script_pubkey check succeeds:
// p2tr_script_buf(offset.group_key()) == forged.output.script_pubkey
let stx = SignableTransaction::new(
  vec![forged],               // plus real inputs optionally
  &payments, Some(change_script), None, fee_per_vbyte,
).unwrap();

// forged prevout via Prevouts::All -> threshold signature produced for a
// transaction that can never be broadcast (invalid prevout amounts /
// non-existent outpoint). Funds were treated as received yet are unspendable.
