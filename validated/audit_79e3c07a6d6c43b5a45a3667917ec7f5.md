## Confirmed analog: `getEndpointKind` trusts a remote's `WWW-Authenticate` header to trigger a GitHub Enterprise sign-in flow

### Title
Attacker-controlled `WWW-Authenticate` realm triggers phishing-grade GitHub Enterprise sign-in against an arbitrary host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Basin bug is that a downstream component (`GeoEmaAndCumSmaPump`) trusts an invariant ("reserves are never zero") that is never actually enforced by its caller (`Well`), and an attacker can violate that invariant through ordinary, valid transactions, corrupting internal oracle state. The structural pattern to look for in Desktop is: a security-relevant decision made from *untrusted, attacker-suppliable data*, where the code assumes that data reflects a trustworthy fact, with no independent verification. `getEndpointKind` in the trampoline credential helper is exactly this pattern: it derives a trust classification ("this is a GitHub Enterprise host") from an HTTP response header sent by the remote server itself, and that classification then drives whether the user is shown a GitHub Enterprise sign-in prompt bound to the attacker's own hostname.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's `credential.helper=desktop`, which is implemented by `getCredential` in `trampoline-credential-helper.ts`. To classify the endpoint, `getEndpointKind` is called: [1](#0-0) 

The relevant branch:
```
// When Git attempts to authenticate with a host it captures any
// WWW-Authenticate headers and forwards them to the credential helper. We
// use them as a happy-path to determine if the host is a GitHub host without
// having to resort to making a request ourselves.
for (const [k, v] of cred.entries()) {
  if (k.startsWith('wwwauth[')) {
    if (v.includes('realm="GitHub"')) {
      return 'enterprise'
    } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
      return 'generic'
    }
  }
}
``` [2](#0-1) 

The `wwwauth[...]` key/value pairs in the `cred` map originate from the HTTP `WWW-Authenticate` response header sent by whatever server the user's `git` operation (`clone`/`fetch`/`push`/`pull`) is talking to — i.e., the value is fully attacker-controlled if the attacker operates the remote (a malicious "GitHub-like" mirror, a compromised self-hosted git server, or a MITM/corporate proxy sitting in front of an arbitrary URL the user was told to add as a remote). There is no verification that the host is actually GitHub-owned infrastructure (no TLS-certificate pinning, no call to `isGitHubHost()`, no API `/meta` probe as done elsewhere in the codebase for exactly this purpose — see `isGitHubHost` in `app/src/lib/api.ts:2429-2491` which *does* attempt such verification via a real API request, but is only used as a last resort, after the header-based fast path has already short-circuited the classification).

This `endpointKind` value is then used in `getCredential`: [3](#0-2) 
```
const endpointKind = await getEndpointKind(cred, store)
...
if (
  endpointKind !== 'generic' &&
  !accounts.some(a => a.endpoint === apiEndpoint)
) {
  ...
  const account = await ui.promptForGitHubSignIn(endpoint)
  ...
}
```
If the attacker's server declared itself `realm="GitHub"`, `endpointKind` becomes `'enterprise'`, bypassing the generic-credential path, and — because the user (by definition) has no account already registered for this arbitrary `apiEndpoint` — Desktop calls `ui.promptForGitHubSignIn(endpoint)` with `endpoint` set to the attacker's own host.

`promptForGitHubSignIn` then does: [4](#0-3) 
```
const { hostname, origin } = new URL(endpoint)
if (hostname === 'github.com') {
  this.dispatcher.beginDotComSignIn(cb)
} else {
  this.dispatcher.beginEnterpriseSignIn(cb)
  await this.dispatcher.setSignInEndpoint(origin)
}
this.dispatcher.showPopup({
  type: PopupType.SignIn,
  isCredentialHelperSignIn: true,
  credentialHelperUrl: endpoint,
})
```
This launches the full "Sign in to GitHub Enterprise" UI flow, with the sign-in endpoint set to `origin` — the attacker's own domain — and displays a dialog inside GitHub Desktop that visually and behaviorally matches a legitimate Enterprise sign-in. Whatever credentials/OAuth exchange results (basic auth username/password prompt, or an OAuth/device-code request issued against the attacker's `origin`) is negotiated directly with the attacker-controlled server.

### Impact Explanation
This satisfies "unauthorized OAuth or account binding" and "credential/token exfiltration" from an attacker-controlled git remote/proxy response, without any local access, admin rights, or social engineering beyond the user simply performing a normal git operation (clone/fetch/push) against a URL the attacker controls or that is intercepted by a network proxy. The corrupted value is the trust decision `endpointKind` (and by extension the sign-in `origin`/`apiEndpoint` used for the credential exchange), which is derived purely from a header the remote server supplies about itself, i.e. it is exactly analogous to trusting a caller-supplied invariant (non-zero reserve) without independent enforcement.

- If the resulting sign-in flow is basic-auth-style (username/password prompt), the user's credentials go straight to the attacker's server.
- If the flow is an OAuth/device-code exchange scoped to the "enterprise" `origin`, the token issuance dialog and any resulting token get bound to/exchanged with the attacker's endpoint, and any subsequent git operations to that same `apiEndpoint` will use `accounts.some(a => a.endpoint === apiEndpoint)` to auto-supply the account's token — meaning any legitimate token acquired for that endpoint (e.g., if the user had a real token minted through the flow) will subsequently be sent, via the credential helper, to the attacker's HTTPS endpoint on every future operation (`credWithAccount` in `getGitHubCredential`).

### Likelihood Explanation
The trigger is trivial for an attacker who controls the git server, or a network intermediary (corporate/public-Wi-Fi proxy performing a MITM or simply owning a self-hosted git-over-HTTPS endpoint) that a victim is instructed (via README, onboarding doc, or malicious `git clone` link) to add as a remote. No changes to the client, no elevated privileges, and no pre-existing malware are required — it is purely a crafted HTTP response header (`WWW-Authenticate: Basic realm="GitHub"`) returned during Git's normal HTTP authentication negotiation, which git itself forwards verbatim to the configured credential helper.

### Recommendation
Do not classify an endpoint as GitHub/Enterprise based solely on the `WWW-Authenticate` realm string reported by the remote itself. At minimum, require corroboration via an independent check (e.g., the existing `isGitHubHost()` verification in `app/src/lib/api.ts` that performs a real request and checks for the `x-github-request-id` response header) before elevating an endpoint to `'enterprise'` classification and surfacing the GitHub sign-in UI, and clearly disclose the target hostname to the user before starting any credential exchange bound to an unrecognized endpoint.

### Proof of Concept
1. Set up an HTTPS git server (e.g., via `git http-backend` behind a small proxy) that, for any HTTP request, returns `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone or add a remote pointing to `https://attacker.example.com/some/repo.git` and trigger a `fetch`/`push`.
3. Git performs the HTTP auth handshake, receives the `WWW-Authenticate: Basic realm="GitHub"` header, and forwards it (as `wwwauth[0]=...`) to Desktop's `credential.helper=desktop` via the trampoline.
4. `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:157-165`) matches `realm="GitHub"` and returns `'enterprise'`.
5. `getCredential` finds no existing account for `attacker.example.com` and calls `ui.promptForGitHubSignIn('https://attacker.example.com')`.
6. Desktop opens a "Sign in to GitHub Enterprise" dialog bound to `origin = https://attacker.example.com`; any credentials/tokens the user supplies in that flow are negotiated with the attacker's server.

*Note: I was not able to trace the exact OAuth/device-flow implementation invoked by `beginEnterpriseSignIn`/`setSignInEndpoint` within the indexed portion of the codebase (the sign-in store internals), so I cannot confirm with certainty whether the resulting exchange is a raw basic-auth credential capture or a full OAuth device-code negotiation with the attacker's server; both outcomes result in credential/token exposure to an untrusted host, but a Devin session with full repository access would be needed to pin down the exact downstream data captured.*

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

    return 'github.com'
