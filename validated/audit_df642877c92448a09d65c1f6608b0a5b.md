### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read`/`view` enables CPU DoS via untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes attacker-controlled `t`/`n` (each a `u16`, up to 65535) and immediately calls `ThresholdKeys::new`, which computes a Lagrange `interpolation_factor` for each of `t` participants, where each factor itself iterates over all `t` included participants. This yields O(t²) field multiplications (plus `t` field inversions) purely from untrusted bytes. The same quadratic blowup recurs in `ThresholdKeys::view`, which computes `interpolation_factor` for every signer in `included`. This is the Serai analogue of the PocketMine `findResultItem` flattening DoS (CWE-400): a small crafted input triggers disproportionate, super-linear CPU work before any authentication.

### Finding Description
`Participant`, `t`, `n`, `i` are all read directly from the byte stream in `ThresholdKeys::read` [1](#0-0) . `ThresholdKeys::new` then computes the group key by mapping `interpolation_factor` over the set `t = 1..=params.t()` [2](#0-1) . `interpolation_factor` for `Interpolation::Lagrange` runs an inner loop over every entry in `included`, performing a field multiplication per entry and a field inversion at the end [3](#0-2) . With `t = n = 65535` and `Interpolation::Lagrange` (a single `0x01` byte) [4](#0-3) , this is ~4.3×10⁹ field multiplications and ~65k inversions triggered by ~4.2 MB of trivially-constructed input, executed synchronously on the deserialization path.

`ThresholdKeys::view` repeats the pattern: for each of `k` included signers it calls `interpolation_factor(*i, &included)`, which itself is O(k) with an inversion, giving O(k²) multiplications plus `k` inversions per signing-set construction [5](#0-4) .

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as a reachable untrusted-input surface) can force seconds-to-minutes of single-threaded CPU time per message. Repeated submissions against a node/coordinator that deserializes `ThresholdKeys` from network peers or stored blobs produce a practical denial of service — the same externally-observable "server freeze" class as the PocketMine advisory, differing only in degree (quadratic rather than exponential). The check ordering means the full quadratic work is performed inside `ThresholdKeys::new` during `read`, before any caller-level validity assessment.

### Likelihood Explanation
Reachability requires an endpoint that calls `ThresholdKeys::read` on unauthenticated data, which the scan rules designate as in-scope attacker surface. The malicious payload is trivial to construct: correct curve `C::ID`, `t = n = 0xFFFF`, any nonzero `i`, interpolation tag `1`, one scalar, and `n` valid point encodings. No cryptographic validity (correct shares, consistent keys) is needed since `ThresholdKeys::new` performs the interpolation before it can reject anything. Likelihood is bounded by deployment choice — serialization is behind `std`/`borsh` features and `n` is capped at 65535 — so impact is a medium-severity CPU DoS, not a correctness or key-compromise bug.

### Recommendation
- In `Interpolation::interpolation_factor`, compute all denominators for a signing set in one pass and batch-invert them (Montgomery's trick), reducing `view`/`new` to O(k) inversions total; cache per-`included` numerators.
- More directly, bound the cost: validate that `n` does not exceed a protocol-meaningful maximum before constructing `ThresholdKeys` in `read`, and/or defer the `group_key` interpolation in `ThresholdKeys::new` (lazy evaluation) so deserialization alone does not perform O(t²) work.
- Apply an early `t`-vs-`included` consistency check and reject `Lagrange` parameter sets with `n` above the largest legitimately generated DKG size for the deployment.

```rust
// Construct a serialized ThresholdKeys<Secp256k1> forcing quadratic Lagrange work
// inside ThresholdKeys::new, reached purely by `ThresholdKeys::read`.
let mut buf = vec![];
let id = <Secp256k1 as Ciphersuite>::ID;
buf.extend((id.len() as u32).to_le_bytes());
buf.extend(id);
let t: u16 = u16::MAX; // 65535
let n: u16 = u16::MAX;
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(1u16.to_le_bytes()); // i = 1
buf.push(1);                    // Interpolation::Lagrange
buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr()); // secret_share
let g = <Secp256k1 as Ciphersuite>::generator().to_bytes();
for _ in 0 .. n { buf.extend(g.as_ref()); } // n identical verification shares

// ~4.2 MB input -> ~4.3e9 field multiplications + 65535 inversions in
// ThresholdKeys::new's group_key computation (crypto/dkg/src/lib.rs:376-378).
let _ = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice());
```
