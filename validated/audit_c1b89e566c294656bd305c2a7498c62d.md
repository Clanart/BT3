### Title
Webhook shop-domain spoofing via unauthenticated `X-Shopify-Shop-Domain` header (HMAC body-only signing) - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates the HMAC over the raw request body, and the `shop_domain` helper used by webhook consumers reads the shop identity straight from the client-supplied `X-Shopify-Shop-Domain` header, which is never included in the HMAC computation. This mirrors the H-07 pattern (a validly-signed message is accepted in a context — here, "which shop it belongs to" — that was never bound into the signature), letting an attacker who controls one shop replay a genuinely-signed webhook body against the app while relabeling it as belonging to a different shop.

### Finding Description
`hmac_valid?` computes/validates the digest only from `request.raw_post`: [1](#0-0) 

`verify_request` gates the controller solely on this body-only HMAC: [2](#0-1) 

But the shop identity used by consumers of the module is taken directly from an unsigned header: [3](#0-2) 

The generator-provided custom webhook controller pattern documented for apps explicitly relies on this unauthenticated header to route work to a specific shop: [4](#0-3) 

Because the app's client secret used for HMAC signing is shared across *every* shop that has installed the app (it is not per-shop), any merchant who has installed the app receives genuinely Shopify-signed webhook deliveries for their own shop. Since `X-Shopify-Shop-Domain` is not part of the signed payload, that same attacker can capture one of their own valid webhook deliveries and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `hmac_valid?` still returns true (the body and secret are unchanged), so `verify_request` passes, and the downstream job is queued with the attacker-controlled `shop_domain`, exactly analogous to how the SmartAccount contract validated the nonce but not the `batchId`, letting a validly-signed transaction be replayed under a different (unchecked) context identifier.

### Impact Explanation
An unprivileged merchant (any account that can install the target app) can forge webhook events attributed to any other shop using the same app, since the binding between "signed payload" and "which shop it is for" is never checked. Depending on which webhook topics the app subscribes to, this can be used to inject spoofed data-change events, trigger privacy/mandatory webhook jobs (e.g. `shop/redact`, `customers/redact`), or otherwise corrupt/act on another tenant's records — a cross-shop access/action vulnerability.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on their own store (an ordinary, unprivileged action) to obtain a legitimately HMAC-signed webhook payload, then replay it with a modified header to the public webhook endpoint. No secret leakage or privileged access is required beyond normal app installation, making this reasonably likely to be reachable from an unrelated-merchant HTTP request.

### Recommendation
Bind the shop identity into the value that is cryptographically verified rather than trusting the `X-Shopify-Shop-Domain` header in isolation: derive/verify the shop from the signed webhook payload itself (as `ShopifyAPI::Webhooks::Registry.process` does), or additionally verify that the header-provided shop domain corresponds to an existing, currently-installed session before allowing `shop_domain` to be trusted downstream, so a replayed/relabeled payload cannot be attributed to an arbitrary shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a real webhook (e.g. `orders/create`) delivery signed by Shopify using the app's shared client secret.
2. Attacker captures the raw POST body and the valid `X-Shopify-Hmac-Sha256` header from that delivery.
3. Attacker replays the exact same body/HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` validates successfully (body/secret unchanged), `verify_request` allows the request through, and `shop_domain` in `lib/shopify_app/controller_concerns/webhook_verification.rb` returns `victim.myshopify.com`, causing the app to process/queue the webhook job as if it originated from the victim shop.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```ruby
    end
```
