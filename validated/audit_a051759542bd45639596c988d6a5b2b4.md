### Title
Protocol-owned liquidity swaps execute with effectively no slippage protection (`minimum out = 1`) - (File: substrate/emissions/pallet/src/lib.rs)

### Summary
Analogous to the Tokemak finding where `swapRouter.swapForQuote(..., 0)` is called with a zero minimum-out, Serai's `swap_to_staked_sri` (triggered by the externally-originated `InInstruction::SwapToStakedSRI`) swaps half of a user's deposit for SRI and adds liquidity with `minimum out` hardcoded to `1`, explicitly accepting "whatever we get". The SRI minted to the user is priced off the *previous block's* spot price, so any slippage is absorbed by protocol-owned liquidity, making the swap sandwichable / manipulable at the protocol's expense. The same pattern exists in the `DexCall::Liquidity` path in `in-instructions`.

### Finding Description
`Emissions::<T>::swap_to_staked_sri` is invoked from `InInstruction::SwapToStakedSRI` handling in `substrate/in-instructions/pallet/src/lib.rs` (lines 224–227), an instruction any external depositor can cause to be executed by sending coins to Serai. Inside `swap_to_staked_sri` (`substrate/emissions/pallet/src/lib.rs:384-408`):

```rust
// swap half of the liquidity for SRI to form PoL.
let half = balance.amount.0 / 2;
let path = BoundedVec::try_from(vec![balance.coin.into(), Coin::Serai]).unwrap();
let origin = RawOrigin::Signed(POL_ACCOUNT.into());
Dex::<T>::swap_exact_tokens_for_tokens(
  origin.clone().into(),
  path,
  half,
  1, // minimum out, so we accept whatever we get.
  POL_ACCOUNT.into(),
)?;
...
Dex::<T>::add_liquidity(
  origin.clone().into(),
  balance.coin,
  half,
  sri_amount,
  1,
  1,
  POL_ACCOUNT.into(),
)?;
```

The `amount_out_min` passed to the DEX is `1`, and both `coin_min`/`sri_min` on `add_liquidity` are `1` — i.e., zero effective slippage bound, the exact same defect as `swapForQuote(token, amounts[i], _baseAsset, 0)` in the reference report. A symmetric instance exists in `substrate/in-instructions/pallet/src/lib.rs:120-139`, where the user-facing `DexCall::Liquidity` path swaps half the deposit and adds liquidity with minimums of `1` (the code comments admit this: "minimums are set to 1 above to guarantee successful adding liq call").

Critically, the user's SRI payout is not tied to the swap result: `swap_to_staked_sri` computes `value = Dex::<T>::spot_price_for_block(last_block, balance.coin)` and mints `balance.amount * value` SRI to the user (lines 411–419). So the swap executes at the *current* (manipulable) pool price while the protocol compensates the user at the *prior* spot price — the protocol-owned-liquidity account (`POL_ACCOUNT`) deterministically eats any adverse slippage.

### Impact Explanation
An attacker who deposits with a `SwapToStakedSRI` in-instruction (or sandwiches someone else's) can move the `coin:SRI` pool price within the block — e.g., via a large swap or by adding imbalanced liquidity beforehand — so the protocol's `half`-sized swap and subsequent `add_liquidity` execute at a worse rate than the last-block spot price used to mint SRI. The attacker extracts the difference as arbitrage profit, draining value from `POL_ACCOUNT`/the pools. Since the DEX pallet only enforces `amount_out >= amount_out_min` (`ProvidedMinimumNotSufficientForSwap`, `substrate/dex/pallet/src/lib.rs:783-784`) and the bound here is `1`, no check ever fires. Loss of protocol funds = High.

### Likelihood Explanation
- Reachable by any unprivileged external user: `InInstruction::SwapToStakedSRI(address, network)` is processed from inbound external-chain deposits (`in-instructions/pallet/src/lib.rs:224-227`); the only gate is that the target network hasn't reached economic security (line 366–382).
- The attacker fully controls deposit amount and timing; intra-block price manipulation is standard on AMMs, and unlike a normal swap the victim (POL) has a fixed payout oracle (last-block spot price) making extraction deterministic rather than probabilistic.
- The `DexCall::Liquidity` path additionally lets an attacker force other users' liquidity-adds through with `min = 1`.

### Recommendation
- In `swap_to_staked_sri`, compute `amount_out_min` from the same `spot_price_for_block` used for the mint (e.g., `half * spot * (1 - max_slippage_bps)`) instead of `1`, and pass real minimums to `add_liquidity` (e.g., proportional to the spot price), failing the instruction rather than executing at an arbitrary rate.
- In the `DexCall::Liquidity` in-instruction path, take user-supplied minimums in the instruction (as the spec's `Add Liquidity` shorthand already defines a `minimum` field, `spec/integrations/Instructions.md:96-120`) instead of hardcoding `1`.

### Proof of Concept
1. Attacker observes/creates pool `X:SRI` with reserves giving spot price `P`.
2. Before block `n`, attacker executes a large `X -> SRI` swap, depressing `SRI` per `X` (spot at block `n-1` remains `P`).
3. Attacker's (or a victim's) `InInstruction::SwapToStakedSRI` executes in block `n`: `swap_exact_tokens_for_tokens(path=[X,SRI], half, min=1)` fills at the manipulated price; `add_liquidity` likewise fills at min `1`.
4. Pallet mints `balance.amount * P` SRI to the user — priced at stale `P`, not the executed rate — the shortfall is absorbed by `POL_ACCOUNT`.
5. Attacker reverses their position, capturing the difference between `P` and the manipulated execution price. No bound ever reverts because `amount_out_min = 1` always passes the `ensure!(amount_out >= amount_out_min, ...)` check in `substrate/dex/pallet/src/lib.rs:783-784`.
