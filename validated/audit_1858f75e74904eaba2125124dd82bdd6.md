### Title
`clone()` unconditionally disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard, re-enabling recursive-clone symlink RCE on untrusted repositories - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` in `app/src/lib/git/clone.ts` hard-codes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment used for every recursive clone, and always passes `--recursive`. `GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to gate the protections for CVE‑2024‑32002 (malicious repository with crafted submodules/symlinked `.git` directories that can lead to remote code execution during `git clone --recursive`). By actively forcing this protection off for a value the user does not control (an arbitrary clone URL), Desktop performs the same kind of "skip the safety check on the code path that handles untrusted external input" mistake as the Prisma report: `openTrove()` (an entry point that accepts attacker/user-supplied collateral/borrow parameters) omits the health-factor check that the sibling function `adjustTrove()` performs. Here, `clone()` (the entry point that accepts an attacker-controlled remote URL/repository) disables the exact guard that Git's own hardened submodule-checkout code path relies on, while other Desktop git operations (`fetch`, `pull`, `checkoutBranch`/`checkoutCommit` via `updateSubmodulesAfterOperation`) do not set this variable at all and thus retain Git's default (safe) behavior.

### Finding Description
`clone()` builds its execution environment as:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [1](#0-0) 

and always runs `git clone --recursive -- <url> <path>` with that environment [2](#0-1) .

`GIT_CLONE_PROTECTION_ACTIVE` is the variable Git added to control the protections shipped for CVE‑2024‑32002, which hardened `git clone --recursive` against malicious repositories that use crafted submodule paths / case-collision or symlink tricks on a submodule's `.git` directory to get arbitrary hook/config execution during the recursive checkout of the submodule. Setting it to `'false'` deliberately turns those protections off for every clone Desktop performs, regardless of whether the source is a trusted GitHub URL or an arbitrary, attacker-supplied URL (e.g. an add-remote/clone flow driven by a `x-github-client://` deep link or a URL pasted by the user pointing at a hostile server, as handled by `openOrCloneRepository`/`openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`) [3](#0-2) .

By contrast, Desktop's other recursive-submodule-touching code paths (`checkoutBranch`, `checkoutCommit`, `pull`, `fetch`, `updateSubmodulesAfterOperation`) do not set `GIT_CLONE_PROTECTION_ACTIVE` at all [4](#0-3) [5](#0-4) [6](#0-5) , so they retain Git's built-in default protection. `clone()` is the one path that actively strips it — the exact "should also check X" gap the seed report describes, except inverted: instead of omitting a check that a sibling function performs, `clone()` actively disables a check that Git performs by default and that sibling functions leave enabled.

The `updateSubmodulesAfterOperation` function does implement a narrower, unrelated toggle — `allowFileProtocol`, which controls `protocol.file.allow=always` for submodule URLs — and that flag is plumbed through from callers with an explicit default of `false` [7](#0-6) . This shows the codebase is aware that submodule-related git protections are security-sensitive and normally defaults them to the safe value, making the unconditional `'false'` override in `clone()` stand out as an outlier.

### Impact Explanation
If Git's CVE‑2024‑32002 protections would otherwise block a malicious repository's recursive submodule checkout (e.g. because the repository is cloned on a case-insensitive or symlink-capable filesystem and contains a submodule whose path collides with `.git` or whose worktree is redirected via a symlink), Desktop's `clone()` removes that safety net for every single clone operation, including clones of attacker-supplied/unverified URLs. Depending on the Git version bundled with dugite and the host filesystem, this can allow a hostile repository to get Git to execute arbitrary hooks/configuration during the initial recursive clone — i.e., code execution triggered purely by cloning a repository the user does not yet trust, which matches the "attacker controls a cloned/fetched repository ... result is code execution" impact category.

### Likelihood Explanation
`clone()` is invoked on every "Clone repository" action and on every URL-triggered clone (`x-github-client://openRepo` deep links, "Open in Desktop" buttons on arbitrary/forked repos, `git@`/`https://` URLs entered by the user) via `openOrCloneRepository` — no additional local access, admin rights, or unnatural steps are required beyond the user cloning a URL, which is core, expected Desktop functionality. The disabling of the protection is unconditional and silent (no error, no log), so the only mitigating factor is whether the installed Git/dugite version's default protections would have mattered for the given filesystem — but Desktop is actively working against that safety net rather than relying on it, which is the invariant break.

### Recommendation
Remove the hard-coded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or set it to `'true'`/leave it unset) so recursive clones of untrusted repositories benefit from Git's CVE‑2024‑32002 mitigations, consistent with how `fetch`, `pull`, and `checkoutBranch`/`checkoutCommit` do not disable this protection.

### Proof of Concept
1. Confirm the bundled dugite/Git version implements the `GIT_CLONE_PROTECTION_ACTIVE`-gated mitigations for CVE‑2024‑32002.
2. Prepare a malicious remote repository containing a submodule crafted per the public CVE‑2024‑32002 advisory (submodule path colliding with `.git`/symlink redirection to escape the submodule worktree during `--recursive` checkout).
3. In Desktop, trigger a clone of that malicious URL (via the Clone dialog or an `x-github-client://openRepo?url=...` deep link handled by `openOrCloneRepository`) [3](#0-2) .
4. Observe that `clone()` executes `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in its environment [8](#0-7) , bypassing the mitigation and reproducing the CVE‑2024‑32002 primitive during the recursive submodule checkout, whereas the same repository fetched/checked out through `fetch`/`checkoutBranch` (which never set this variable) would be protected by Git's default.

Note: I was not able to execute Git/dugite locally to empirically confirm the exact exploit trigger conditions for the bundled Git version; this PoC path is derived from static analysis of the `GIT_CLONE_PROTECTION_ACTIVE` usage and its documented purpose, and full confirmation would require running the actual clone against a crafted malicious submodule repository in a Devin session with terminal access.

  currentRemote: IRemote | null,

    repository,
