### Title
Cross-chain mint to an unrecoverable zero `AccountId` in `HyperFungibleToken::on_accept` - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The report's core broken invariant is: EVM's "zero address" concept does not translate cleanly to Substrate, and code that blindly derives/accepts an all-zero value as an `AccountId` can silently move funds to an address nobody can control, rather than treating it as "no beneficiary." `HyperFungibleToken::on_accept` derives the on-chain beneficiary directly from attacker/user-supplied bytes in the cross-chain message body without ever rejecting the degenerate all-zero case.

### Finding Description
In `on_accept`, the recipient is taken straight from the ABI-decoded message body and converted into a `T::AccountId` with no validation against a zero/default value: [1](#0-0) 

If `message.to` is 20 zero bytes (the canonical EVM "zero address") or a full 32 zero bytes, `beneficiary_bytes` becomes `[0u8; 32]`, and `beneficiary: T::AccountId` becomes the all-zero `AccountId32`. This value is then used as the transfer/mint target: [2](#0-1) 

The same unguarded pattern also drives the refund path on timeout, deriving the refund beneficiary from `message.from` with identical zero-padding logic and no zero check: [3](#0-2) 

Unlike `pallet-ismp-relayer`, which explicitly added a test to reject an all-zero EVM address recovered from state proofs precisely because "a malicious actor can't claim a reward by writing zeros": [4](#0-3) 

...`hyper-fungible-token` has no equivalent guard. The all-zero `AccountId32` is a perfectly valid, addressable account on any Substrate chain (there is no SS58/consensus-level concept of "the zero address" being invalid, unlike EVM where `address(0)` is a special reject-target in many contracts, e.g. `IntentGatewayV2` explicitly checks `host == address(0)` / `priceOracle == address(0)`): [5](#0-4) 

Because no private key is realistically known for `[0u8;32]`, tokens minted or transferred there via `NativeCurrency::transfer`/`Assets::mint_into` are permanently unrecoverable.

### Impact Explanation
This is a direct, protocol-level "loss of funds" bug matching the Hyperbridge Impact Gate: bridged value dispatched from the source chain is escrowed/burned there and expected to be credited to a beneficiary on the destination chain; if the message's `to` field is the zero value, the destination-side mint/transfer sends the value to an address that is provably unreachable, permanently destroying user funds with no path to recovery — a real bridge custody/settlement failure, not a generic dependency or style issue.

### Likelihood Explanation
The `to` field of the cross-chain `Message` is fully controlled by whoever constructs the message on the source EVM contract side (an ordinary, unprivileged bridge user/dApp), and reaches `on_accept` after only source-contract authentication (`ContractToAsset` lookup) — there is no additional validation of the recipient value itself. No malicious relayer, prover, governance actor, or leaked key is required; a buggy or malicious dApp/integration (or a user's own mistake with unrecoverable consequences) can trigger the loss on every single such transfer, since the check is entirely absent rather than merely misconfigured.

### Recommendation
Add an explicit check in `on_accept` (and mirror it in `on_timeout` for the refund beneficiary) rejecting `beneficiary_bytes == [0u8; 32]` before minting/transferring, returning a dedicated `HftError` (e.g. `ZeroBeneficiary`) instead of silently succeeding. Consider the same audit for any other pallet in the codebase that derives an `AccountId` from raw external bytes without validating against the degenerate all-zero case, consistent with the "use `None`/explicit rejection instead of an implicit zero address" recommendation from the referenced report.

### Proof of Concept
1. Register a source ERC20 contract mapping via `ContractToAsset` as in the existing test harness.
2. Craft a `PostRequest` whose ABI-encoded `Message` body sets `to = bytes20(0)` (or `bytes32(0)`), following the pattern used in `should_receive_asset_with_calldata`: [6](#0-5) 
3. Call `HyperFungibleToken::on_accept(post)`. The call succeeds, and `pallet_balances::Pallet::<Test>::free_balance(AccountId32::new([0u8;32]))` will show the transferred amount permanently held by an address with no recoverable key — demonstrating the fund-loss path with no error and no guard preventing it.
