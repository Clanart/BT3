Based on my investigation, the codebase's core ISMP dispatch path (`EvmHost.dispatchIncoming`, `evm/src/core/EvmHost.sol:794-818`) explicitly documents and fixes the exact M-07 anti-pattern — "instead of reverting the entire batch, early return here" — showing the team is aware that a single failing callback must not block unrelated state. However, the same anti-pattern reappears, unfixed, in the escrow-release loop used to settle intent orders.

### Title
Escrow-release loop reverts the entire withdrawal if any single escrowed token entry is zero, permanently locking all other legitimately escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` (used by both the cross-chain `RedeemEscrow`/`RefundEscrow` settlement path and same-chain fills) iterates over an order's token list and releases escrow to the beneficiary one token at a time. If escrow for *any single* token entry in that list reads as `0`, the function reverts the whole call with `UnknownOrder()` instead of skipping that entry — exactly the `RewardThrottle._sendToDistributor()` defect pattern, where one "inactive" element in a batch aborts processing for every other, otherwise-valid element in the same batch. [1](#0-0) 

The identical pattern is duplicated in the Tron variant's `withdraw()`: [2](#0-1) 

### Finding Description
`_withdraw(body, isRefund, finalize)` loops `for (uint256 i; i < len; i++)` over `body.tokens`, and for each token:
```
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
...transfer...
```
There is no per-token `continue`/skip; a single zero-balance entry aborts the entire settlement transaction. This mirrors `RewardThrottle._sendToDistributor()`, where `IDistributor(distributors[i]).declareReward(share)` reverting for one inactive distributor blocked distribution to every other active distributor in the same call — the fix recommended there (skip/tolerate the failing entry, keep processing the rest) was never applied to this analogous loop.

Both `onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow` messages delivered via `IApp.onAccept`, invoked once by `EvmHost.dispatchIncoming`) and `onGetResponse` (cancel-from-source flow) route to this single, all-or-nothing `_withdraw` call for the order's *entire* token list, not per-token.

### Impact Explanation
If escrow for one of an order's several input tokens can legitimately (or be made to) read `0` while other tokens in the same order still hold non-zero escrow, the settlement call for the whole order — releasing every input token to the solver on a fill, or refunding every input token to the user on cancellation — reverts unconditionally. Because `dispatchIncoming` deletes the request receipt on a failed callback specifically so it can be retried, every retry hits the identical zero-balance token and reverts identically, permanently deadlocking release of the *other*, correctly-escrowed tokens for that order (fund lock). This matches the required impact class of fund loss/lock through a public, unprivileged path (fill/cancel flows are permissionless).

### Likelihood Explanation
I was not able to fully confirm, within the scope of this investigation, the exact external trigger that produces a zero-balance entry for one token while other tokens in the same order retain non-zero escrow (e.g., via duplicate token entries in `order.inputs`, partial same-chain fills combined with a subsequent cross-chain-style consolidated withdraw, or governance/dust-sweep interactions with `_orders`). The vulnerable code path itself — an unconditional revert-on-zero inside a multi-item release loop with no way to omit or retry per-token — is directly confirmed in the source. Whether an unprivileged attacker can force the qualifying zero-escrow precondition needs further verification of `placeOrder`/`fillOrder` accounting in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`, which I did not have remaining budget to fully trace.

### Recommendation
Change `_withdraw`/`withdraw` to skip (not revert on) a zero-escrow token entry — mirroring the `EvmHost.dispatchIncoming` fix already applied elsewhere in this codebase — so that one anomalous or already-drained token entry cannot block release of the order's other, validly-escrowed tokens. At minimum, add an explicit invariant check at order placement/fill time that guarantees `_orders[commitment][token] > 0` for every token address that will later appear in a `WithdrawalRequest`, and de-duplicate token entries defensively.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
