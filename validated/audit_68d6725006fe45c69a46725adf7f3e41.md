Based on my investigation, I found a concrete analog in Hyperbridge's cross-chain revenue withdrawal path: the `EvmHost`/`HostManager` withdrawal mechanism shares a single on-chain token balance between two independent claimants — accrued relayer fees and protocol/governance revenue — with no on-chain accounting split between them, mirroring the `Flip.flip()` bug of checking a shared pool's balance without accounting for other claimants' locked liquidity.

### Title
Shared `feeToken` balance in `EvmHost`/`HostManager.withdraw()` is not partitioned between relayer-owed fees and protocol revenue, allowing governance withdrawals to strand relayer claims - (File: evm/src/core/HostManager.sol)

### Summary
`HostManager.onAccept()` routes every incoming `Withdraw` governance message from Hyperbridge to the exact same `IHostManager(host).withdraw(WithdrawParams)` entrypoint, which pulls from `EvmHost`'s single `feeToken` balance [1](#0-0) . This one balance is the destination for two unrelated claim types: relayer fees accrued off-chain on Hyperbridge's `pallet-ismp-relayer::Fees` ledger [2](#0-1) , and protocol/governance revenue withdrawn via the same `WithdrawParams`/`withdraw()` path documented as "withdraws bridge revenue to the given address" [3](#0-2) . Neither side tracks or checks the other's outstanding claim on the shared balance before transferring funds.

### Finding Description
Relayers accumulate fees by submitting delivery proofs to `pallet-ismp-relayer`, which credits their `Fees[chain][address]` entry on Hyperbridge — this accounting lives entirely off the destination EVM chain [4](#0-3) . The relayer only "cashes out" this balance later by signing a withdrawal that Hyperbridge turns into a `WithdrawParams` POST request dispatched to the destination `HostManager` [5](#0-4) .

Separately, `pallet-ismp-host-executive`/governance can dispatch the identical `Withdraw` action to sweep "bridge revenue" from the same `EvmHost` contract [3](#0-2) . Both code paths converge on the same `withdraw()` call in `EvmHost`, which — per the test suite — is a plain token transfer gated only by the contract's *current* `feeToken.balanceOf(address(this))`, reverting via `SafeERC20` only if that specific transfer's amount exceeds the live balance [6](#0-5) . The earlier successful-withdrawal test confirms the mechanism is a direct balance debit with no other bookkeeping [7](#0-6) .

Because relayer-earned fees are tracked only in Hyperbridge's `Fees` storage map and never reserved/ring-fenced inside the destination `EvmHost` contract itself, a governance-initiated revenue withdrawal has no way to know how much of the current `feeToken` balance is "owed" to relayers who haven't yet triggered their own withdrawal. This is structurally identical to the reported `Flip.flip()` flaw: the check ("does the shared pool have enough for *my* withdrawal") ignores the other claimant's ("other game contracts'"/relayers') outstanding locked claim on the same pool.

### Impact Explanation
If governance withdraws protocol revenue down to (or below) the amount still owed to relayers who accumulated fees but haven't withdrawn yet, subsequent relayer withdrawal requests will revert on `SafeERC20` insufficient-balance, exactly as demonstrated in `test_host_manager_insufficient_balance` [6](#0-5) . Relayers who already delivered messages and had their fees accrued on Hyperbridge (their off-chain ledger entry is zeroed by the relayer pallet as soon as the withdrawal is dispatched) permanently lose the ability to collect the reward — the on-chain ISMP request for their payout fails and their `Fees` entry was already decremented on dispatch. This is a real loss/lock of funds rightfully belonging to relayers, meeting the bounty's "stealing or loss of funds" / "unauthorized ... transaction manipulation" criteria.

### Likelihood Explanation
This requires no malicious relayer, prover, or compromised key — it is a straightforward consequence of two independent, individually-legitimate governance/relayer flows sharing one unpartitioned balance. It will trigger naturally whenever protocol revenue withdrawals are sized against the *total* contract balance instead of `total balance − sum(outstanding relayer fees)`, which is very plausible given there is no such accounting field surfaced anywhere in `EvmHost`/`HostManager` per the available code and tests.

### Recommendation
Track an on-chain (or periodically synced) "reserved for relayers" liability in `EvmHost`, and have `withdraw()` for the `SetHostParam`/protocol-revenue path check `feeToken.balanceOf(address(this)) - reservedForRelayers >= amount` rather than the raw balance. Alternatively, segregate relayer-fee escrow into its own contract/account (mirroring the Substrate side's dedicated `RELAYER_FEE_ACCOUNT`, which pallet-ismp already uses to isolate relayer fees from other funds [8](#0-7) ) so governance withdrawals structurally cannot touch relayer-owed balances.

### Proof of Concept
1. Relayer A delivers a message whose fee entitles it to 500 tokens; it submits proof to `pallet-ismp-relayer`, crediting `Fees[EVM-1][A] = 500` — no funds move on the EVM host yet.
2. Governance dispatches `WithdrawParams{ amount: 1000, token: feeToken, beneficiary: treasury }` for "protocol revenue" through `HostManager.onAccept` → `EvmHost.withdraw()`, draining the entire `feeToken` balance held by the host (as in `test_host_manager_withdraw`, using `SafeERC20` with no reservation check) [7](#0-6) .
3. Relayer A signs and submits a withdrawal for its 500-token entitlement; `pallet-ismp-relayer` zeroes its `Fees` entry and dispatches the corresponding `WithdrawParams` POST to `EvmHost`.
4. `EvmHost.withdraw()` now reverts because the balance is insufficient (as reproduced by `test_host_manager_insufficient_balance`) [6](#0-5) . Relayer A's `Fees` ledger entry was already zeroed on Hyperbridge, so the reward is permanently lost.

Note: I was unable to read the exact body of `EvmHost.withdraw()` itself (grep matched too broadly and I ran out of tool iterations before pulling that specific function), so the precise line range for the balance check inside `EvmHost.sol` is unverified — this is inferred from the interface comment, the `HostManager.onAccept` routing, and the two Rust integration tests that exercise `withdraw()`'s pass/revert behavior. A Devin session with full file access should confirm the exact `withdraw()` implementation in `evm/src/core/EvmHost.sol` before treating this as fully confirmed.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }

## Withdrawing Fees

Tesseract maintains a local sqlite database where it keeps track of successfully delivered messages. The withdrawal process happens in two phases, the first phase is the fee accumulation on hyperbridge, then withdrawal on any of the connected chains.
In the fee accumulation phase, tesseract submits state proofs of messages all delivered to hyperbridge. If the proof verification is successful, the total amount of unclaimed fees for the relayer address is updated onchain. Next, the relayer can submit a withdrawal transaction to hyperbridge. This initiates potentially multiple ISMP requests to any chain where it has unclaimed fees, that instructs the Hyperbridge contract to credit the relayer their owed funds. This request will not timeout, allowing it to be submitted to the destination chain at any time.

### Accumulating fees

Fee accumulation runs automatically in the background. Every successful
outbound submit produces delivery receipts that flow into a per-chain
accumulation task; each task submits proofs of delivery to Hyperbridge
and increments the relayer's unclaimed-fee balance on-chain. Receipts
are persisted to the local database first so a crash between submit
and accumulation doesn't lose the reward.

> The legacy standalone `tesseract --accumulate-fees` subcommand no
> longer exists in the consolidated relayer — accumulation is part of
> the long-running process.

### Initiating withdrawals

To initiate a withdrawal from hyperbridge, a relayer needs to submit a transaction to hyperbridge which triggers the withdrawal request. This extrinsic is unsigned and will not require any native tokens for execution fees. Once the extrinsic is executed, hyperbridge dispatches a POST request that when executed on its destination, will provide the relayer with the fees they've accrued. The relayer account must have sufficient funds to deliver this request to its destination chain.

#[test]
fn test_host_manager_withdraw() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Mint 1000e18 fee tokens to the host
	let amount_to_mint = U256::from(1000u128) * U256::from(10u128.pow(18));
	env.call(env.fee_token, mintCall { to: env.host, amount: amount_to_mint }.abi_encode());
	assert_eq!(host_balance(&mut env), amount_to_mint);

	// Build a withdraw request (body = [0] + abi.encode(WithdrawParams)).
	// Withdraw the fee token (non-zero `token`) — the zero address would be
	// the native-ETH path which this test isn't exercising.
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	// HostManager.onAccept is `restrict(_params.host)` — must call AS the host
	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	env.call_as(host_addr, manager, calldata);

	let withdraw_amount = U256::from(500u128) * U256::from(10u128.pow(18));
	assert_eq!(host_balance(&mut env), amount_to_mint - withdraw_amount);
}

## Hyperbridge-initiated relayer fee withdrawals

Relayers accumulate their earned fees on Hyperbridge. When a relayer initiates a withdrawal, Hyperbridge dispatches a POST request back to the source chain. `pallet-ismp`'s [`RefundingRouter`](https://github.com/polytope-labs/hyperbridge/blob/main/modules/pallets/ismp/src/dispatcher.rs) intercepts requests addressed to the built-in module id `b"HYPR-FEE"`, decodes a `WithdrawRelayerFees` payload, and transfers the owed balance from `RELAYER_FEE_ACCOUNT` to the relayer.

No runtime configuration is required to enable this — it ships with `pallet-ismp`.
