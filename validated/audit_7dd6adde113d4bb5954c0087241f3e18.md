### Title
Unmetered stateless validation before gas-meter installation enables CheckTx/DeliverTx CPU-exhaustion DoS analogous to Keystone "authentication chaining" - (File: app/ante/cosmos_checktx.go)

### Summary
`CosmosCheckTxAnte` (and the equivalent `CosmosDeliverTxAnte`) run `CosmosStatelessChecks` before any gas meter reflecting the transaction's declared gas is installed on the context. The pubkey/auth params lookup even explicitly uses a `NewNoConsumptionInfiniteGasMeter()` so this read is free, and `CosmosStatelessChecks` itself is called without any context/gas meter argument at all, meaning every operation performed inside it (full-tx `ValidateBasic()`, per-message `ValidateBasic()` for every message in the tx, pubkey extraction, and recursive multisig/pubkey validation via `validatePubKey` including elliptic-curve point decoding with `btcec.ParsePubKey`) is executed completely unmetered and for free, prior to `SetGasMeter` being called at [1](#0-0) .

### Finding Description
The relevant control flow is: [2](#0-1) 

`CosmosStatelessChecks` performs, for every message in the transaction, a full `msg.ValidateBasic()` call and, for every provided pubkey, a recursive `validatePubKey` walk (up to `maxNestedPubKeys = 5` levels) that includes `btcec.ParsePubKey` (secp256k1 point-on-curve validation, an expensive elliptic-curve operation): [3](#0-2) [4](#0-3) 

None of this work is gas-metered because `CosmosStatelessChecks` is called with only `tx`, `height`, `consensusParams`, and `authParams` — no `sdk.Context` with a real gas meter is threaded through it, and the one gas-metered lookup on the same line (`accountKeeper.GetParams`) is deliberately wrapped in a `NewNoConsumptionInfiniteGasMeter()` to make it free: [5](#0-4) 

Only after this stateless validation succeeds does `SetGasMeter` install the tx's declared gas limit, after which `CheckPubKeys`/`CheckSignatures` (the actual expensive signature-verification work) run under gas accounting.

This is structurally the same bug class as the OpenStack Keystone V3 "authentication chaining" DoS (CVE-2014-2828): a request can force the server to perform an attacker-controlled amount of expensive per-item validation work (there, repeated auth methods; here, repeated messages and nested multisig pubkeys) before any cost-limiting/authorization gate is applied, allowing CPU exhaustion with a single crafted request.

The number of messages in a tx and the depth/width of multisig pubkey trees are attacker-controlled up to the max tx size and `TxSigLimit`/`maxNestedPubKeys` bounds, but critically **none of that bounded work is charged against the tx's own declared gas before it executes** — it happens unconditionally for every `CheckTx` call (including `ReCheckTx`, which re-runs on every node for every pending mempool tx after each block) and for every `DeliverTx` call, regardless of whether the sender can or will pay for it.

### Impact Explanation
`CheckTx` is invoked by every full node in the network for every transaction gossiped through its mempool, and `ReCheckTx` re-invokes the same unmetered path for every mempool transaction after each block. A single unprivileged RPC client can broadcast crafted transactions maximizing the number of messages (each incurring `ValidateBasic()`) and/or multisig pubkeys (each incurring `btcec.ParsePubKey`) within the max tx-size/`TxSigLimit` bounds, causing that same unmetered CPU cost to be paid by every node's mempool on every gossip hop and on every `ReCheckTx` cycle — without the attacker ever paying gas for it, and without needing the tx to be included in a block. Submitted at scale (many such transactions concurrently), this can degrade validator/full-node CheckTx/ReCheckTx throughput network-wide, potentially delaying block production (RPC nodes and validators share the same mempool/CheckTx code path) beyond acceptable thresholds.

### Likelihood Explanation
Reachable directly and repeatedly by any unprivileged transaction sender / public-RPC client via ordinary `broadcast_tx`/mempool submission — no special privileges, contract deployment, or governance access required. The only preconditions are staying within existing structural limits (`TxSigLimit`, `maxNestedPubKeys`, max tx bytes), all of which are already public constants/params, making a crafted worst-case tx straightforward to construct.

### Recommendation
Thread a properly gas-metered `sdk.Context` (using the tx's own declared/estimated gas, or a fixed pre-metering budget) through `CosmosStatelessChecks` (and the pubkey-validation recursion in `validatePubKey`) so that `ValidateBasic()` calls and cryptographic pubkey validation are charged before/while they execute, not after. Alternatively, cap the number of messages and total pubkey-validation work processed before gas metering is installed, independent of the later `TxSigLimit` check that only bounds `CheckPubKeys`.

### Proof of Concept
1. Craft a transaction near the max tx-size limit containing the maximum number of cheap-to-construct messages (e.g., minimal `MsgSend`s) each of which is valid enough to reach `msg.ValidateBasic()`, and/or set up multisig pubkeys nested to `maxNestedPubKeys` depth using the full `TxSigLimit` budget of secp256k1 keys.
2. Broadcast many such transactions concurrently to a node's RPC endpoint (`broadcast_tx_sync`/`broadcast_tx_async`), or replay-broadcast the same crafted structure across the network so it is gossiped to many peers.
3. Because `CosmosStatelessChecks` runs before `SetGasMeter` in `CosmosCheckTxAnte`/`CosmosDeliverTxAnte`, each node performs the full `ValidateBasic()`/`validatePubKey`/`btcec.ParsePubKey` workload for every copy of the tx it receives (initial CheckTx and every subsequent ReCheckTx) at zero gas cost to the attacker, regardless of whether the tx is ultimately rejected for insufficient fees or invalid signatures.
4. Repeating step 2 at volume is expected to measurably raise CheckTx/ReCheckTx latency and CPU utilization across nodes, since the expensive work happens unconditionally before any fee/gas gate — mirroring the "large number of same authentication method" CPU-consumption pattern from CVE-2014-2828.

Note: I was not able to execute this against a live sei-chain node to directly measure CPU/latency impact magnitude; the analysis above is based on static code-path tracing showing the ordering issue (stateless validation preceding gas-meter installation) is real and unconditional in both `CosmosCheckTxAnte` and `CosmosDeliverTxAnte`.

func validatePubKey(pubKey cryptotypes.PubKey, remainingSigCount *uint64, depth int) (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = sdkerrors.Wrapf(sdkerrors.ErrInvalidPubKey, "invalid public key: %v", r)
		}
	}()

	switch pk := pubKey.(type) {
	case nil:
		return sdkerrors.Wrap(sdkerrors.ErrInvalidPubKey, "missing public key")
	case *kmultisig.LegacyAminoPubKey:
		if pk == nil {
			return sdkerrors.Wrap(sdkerrors.ErrInvalidPubKey, "missing multisig public key")
		}
		if depth >= maxNestedPubKeys {
			return sdkerrors.Wrapf(sdkerrors.ErrInvalidPubKey, "multisig public key nesting exceeds limit %d", maxNestedPubKeys)
		}

		pubKeyCount := len(pk.PubKeys)
		threshold := pk.GetThreshold()
		if threshold == 0 {
			return sdkerrors.Wrap(sdkerrors.ErrInvalidPubKey, "multisig threshold must be positive")
		}
		if threshold > uint(pubKeyCount) {
			return sdkerrors.Wrapf(sdkerrors.ErrInvalidPubKey, "multisig threshold %d exceeds public key count %d", threshold, pubKeyCount)
		}
		if remainingSigCount != nil && *remainingSigCount < uint64(pubKeyCount) { //nolint:gosec // pubKeyCount is bounded by tx size and compared to tx sig limit.
			return sdkerrors.Wrapf(sdkerrors.ErrTooManySignatures, "signatures exceed limit %d", *remainingSigCount)
		}

		for i, packedKey := range pk.PubKeys {
			if packedKey == nil {
				return sdkerrors.Wrapf(sdkerrors.ErrInvalidPubKey, "missing multisig public key at index %d", i)
			}
			child, ok := packedKey.GetCachedValue().(cryptotypes.PubKey)
			if !ok {
				return sdkerrors.Wrapf(sdkerrors.ErrInvalidPubKey, "invalid multisig public key at index %d", i)
			}
			if err := validatePubKey(child, remainingSigCount, depth+1); err != nil {
				return sdkerrors.Wrapf(err, "invalid multisig public key at index %d", i)
			}
		}

		return nil
	case *secp256k1.PubKey:
		if pk == nil {
			return sdkerrors.Wrap(sdkerrors.ErrInvalidPubKey, "missing secp256k1 public key")
		}
		if remainingSigCount != nil {
			if *remainingSigCount == 0 {
				return sdkerrors.Wrap(sdkerrors.ErrTooManySignatures, "signatures exceed limit")
			}
			*remainingSigCount--
		}
		if len(pk.Key) != secp256k1.PubKeySize {
			return sdkerrors.Wrapf(sdkerrors.ErrInvalidPubKey, "invalid secp256k1 public key size %d", len(pk.Key))
		}
		if _, err := btcec.ParsePubKey(pk.Key); err != nil {
			return sdkerrors.Wrap(sdkerrors.ErrInvalidPubKey, "invalid secp256k1 public key")
		}
		return nil
	default:
		if remainingSigCount != nil {
			if *remainingSigCount == 0 {
				return sdkerrors.Wrap(sdkerrors.ErrTooManySignatures, "signatures exceed limit")
			}
			*remainingSigCount--
		}
		if len(pubKey.Address()) == 0 {
			return sdkerrors.Wrapf(sdkerrors.ErrInvalidPubKey, "invalid public key type: %T", pubKey)
		}

		return nil
	}
}
