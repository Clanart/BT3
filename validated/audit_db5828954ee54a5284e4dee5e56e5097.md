### Title
Desktop hardcodes `GIT_CLONE_PROTECTION_ACTIVE=false`, disabling Git's built-in clone protection against malicious submodules (RCE via CVE-2024-32002 class) - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for every recursive clone it performs, regardless of the trustworthiness of the remote being cloned [1](#0-0) . This variable is the kill-switch Git itself introduced to protect users against maliciously crafted repositories containing symlinked/case-collision `.git` directories inside submodules that let a `clone --recursive` write files (including hooks) outside the intended worktree, leading to code execution during or shortly after clone. Desktop's blanket disabling of this protection mirrors the audited report's pattern: a hardcoded, one-size-fits-all assumption (analogous to the fixed 25-hour stale period assumed safe for all Chainlink feeds) is applied uniformly to an operation whose safety actually depends on the specific, attacker-influenced input (the remote/submodule content), silently reintroducing a known-dangerous code path.

### Finding Description
Git added the `GIT_CLONE_PROTECTION_ACTIVE` safety check (and the related `protectNTFS`/`protectHFS`/symlink `.git` detection) after CVE-2024-32002, where a crafted repository with a submodule whose path collides with `.git` (via case-insensitivity or Unicode normalization on affected filesystems) could cause `git clone --recursive` to write a malicious hook (e.g., `post-checkout`) into the actual `.git/hooks` directory of the clone, which git then executes automatically. GitHub Desktop's `clone()` function passes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone [2](#0-1) , and always clones with `--recursive` [3](#0-2) , meaning submodules are unconditionally initialized and checked out as part of a single, protection-disabled operation. The `isClonePathSensitive` guard only defends against the destination path landing in a short list of well-known sensitive directories (`~/.ssh`, `~/.gnupg`, etc.) [4](#0-3) ; it does nothing to validate the content of the repository or its submodules, so it provides no protection against the CVE-2024-32002 class of attack that `GIT_CLONE_PROTECTION_ACTIVE` exists to stop.

This is a direct attacker-controlled-repository scenario as required by the task's valid-impact criteria: a user clones or opens a URL to clone (including via "Clone in Desktop" deep links handled in `dispatcher.ts`'s `openOrCloneRepository`/`openRepositoryFromUrl` path, which ultimately calls this same `clone()`), and the attacker fully controls the repository content, including submodule definitions.

### Impact Explanation
If a maintainer of `clone.ts` disabled this protection because it broke legitimate submodule workflows (a plausible engineering trade-off, similar to assuming "most feeds have a 24h heartbeat"), the practical effect for any repository that actually needs the protection (crafted with a colliding/symlinked submodule) is that Desktop reintroduces the RCE primitive Git upstream fixed. This satisfies "attacker controls a cloned/fetched repository... and the result is code execution" under the given valid-impact rules — likely the most severe listed outcome.

### Likelihood Explanation
Likelihood depends on filesystem case-sensitivity/normalization (historically macOS default HFS+/APFS-case-insensitive and Windows NTFS are affected, Linux ext4 case-sensitive is not), and requires the victim to clone or fetch-and-checkout-submodules from an attacker-supplied URL — a normal, expected Desktop workflow ("Clone repository" or "Open in Desktop" deep links). No special user steps beyond a normal clone are needed, so likelihood is Medium-High on the affected platforms (macOS/Windows), though I could not verify from the index whether some other compensating check (e.g., a newer Git version's default behavior, or additional server-side validation) exists elsewhere in the codebase that might mitigate this on top of what `clone.ts` shows.

### Recommendation
Remove the hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone.ts`, or at minimum gate it: only disable the protection after per-clone/submodule validation confirms no path collisions, and otherwise rely on Git's own default-safe behavior. Add regression tests analogous to `clone-path-safety-test.ts` and `clone-test.ts` that assert `GIT_CLONE_PROTECTION_ACTIVE` is not disabled, and/or a fixture reproducing a CVE-2024-32002-style submodule collision to prove hooks are not written outside the intended `.git/hooks` directory.

### Proof of Concept
1. On a case-insensitive filesystem (default macOS or Windows), an attacker publishes a repository containing a submodule entry in `.gitmodules` whose path is a case/Unicode variant of `.git` (the same technique underlying CVE-2024-32002).
2. Victim uses GitHub Desktop's "Clone repository" (or clicks an `x-github-client://openRepo/...` deep link handled by `dispatcher.ts`'s `openOrCloneRepository`) pointing at the attacker's URL.
3. `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` [5](#0-4) , so Git's built-in guard that would otherwise abort/warn on the colliding submodule path does not trigger.
4. During recursive submodule checkout, the attacker's payload is written into the real `.git/hooks` directory (e.g., as `post-checkout`), and it is executed automatically on the next Git operation Desktop performs against that repository (fetch/checkout/pull all run through the same on-disk hooks directory), achieving code execution in the context of the user running Desktop.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
