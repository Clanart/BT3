### Title
`withdraw()` in the Tron `IntentGatewayV2` reverts on a zero-escrow token entry, permanently locking cross-chain escrow settlement/refund — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary

### Finding Description
The external report's core broken invariant: a loop mutates per-entry state and gates continuation on `entry_value == 0` where the *legitimately expected* value at that point *is* zero (already-drained lender), so the guard incorrectly treats "nothing to do" as an error and reverts the whole batch operation instead of skipping that entry.

The Tron variant of `IntentGatewayV2.withdraw()` reproduces this exact pattern:

```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:682-706
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
        _orders[body.commitment][token] -= amount;
        unchecked { ++i; }
    }
    ...
}
``` [1](#0-0) 

The loop iterates every entry in `body.tokens` and checks `_orders[commitment][token] == 0`, reverting the entire call with `UnknownOrder()` if the *current stored escrow* for that token is already zero — regardless of whether `amount` for that entry is also zero (i.e., nothing was actually meant to be withdrawn for that token in this call). This is functionally identical to the DebtManager bug: an entry whose current state is already at the terminal value (0) causes the whole batched operation to revert instead of being skipped.

Contrast with the corresponding, correctly-guarded EVM implementation, which explicitly skips zero-amount entries before touching the escrow check:
```solidity
// evm/src/apps/intentsv2/IntentsBase.sol:394-401
for (uint256 i; i < len; i++) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) continue;

    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();
    ...
}
``` [2](#0-1) 

The Tron `withdraw()` is missing this `amount == 0 → continue` guard entirely.

This matters because zero-amount / zero-token entries in a `WithdrawalRequest.tokens` array are a normal occurrence in this codebase's partial-fill and multi-input paths — for example, `IntrinsicIntents._fillSameChain` leaves `escrowedInputs[i]` at its Solidity-default `TokenInfo({token: 0, amount: 0})` for any output index it `continue`s past (already-fully-filled output legs), and that array is what gets passed straight into `_withdraw`/`withdraw`: [3](#0-2) [4](#0-3) 

`ExtrinsicIntents` similarly builds `WithdrawalRequest.tokens = order.inputs` on both the `RedeemEscrow`/`RefundEscrow` paths, so any multi-input order where one input token's `_orders[commitment][token]` has already been driven to zero (e.g. a previous partial refund/withdraw touched that specific token, or a duplicate/legacy zero-value token entry is present in `order.inputs`) causes `withdraw()` to hit `token == 0` for that slot and revert `UnknownOrder()` before any of the other, still-escrowed tokens in the same batch are released.

### Impact Explanation
`withdraw()` is the single function that finalizes both settlement (`RedeemEscrow`, solver gets paid) and refunds (`RefundEscrow`, user gets refunded) after a cross-chain ISMP message is delivered via `onAccept`. If it reverts for a legitimately-shaped batch that contains one entry whose escrow is already zero, the *entire* `onAccept` call reverts, meaning:
- A solver who correctly filled the order on the destination chain can never collect the escrowed input tokens on the source chain that are still non-zero — permanent loss/lock of solver funds.
- A user whose order is legitimately refunded via `RefundEscrow` can never recover the remaining escrowed tokens — permanent loss/lock of user funds.

Since ISMP request/response delivery is not designed to be silently retried after a module-level revert of this kind, this is a genuine "loss/lock of funds" impact matching the bounty's fund-safety criteria, reachable by an unprivileged party (any order with a multi-token input array where one token's escrow can reach zero before withdraw is invoked) without needing a malicious relayer, prover, or admin.

### Likelihood Explanation
Reachability requires only a normal cross-chain order lifecycle on the Tron deployment with more than one input token, or a partial-fill/zero-amount token slot reaching the withdrawal path with a pre-drained balance for one token — not an exotic or adversarial precondition. The bug is a straightforward code-level divergence from the hardened EVM `_withdraw` (which already has the fix for exactly this class of issue), so it is a real regression/porting gap rather than a theoretical one.

### Recommendation
Add the same `if (amount == 0) continue;` guard used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, and check `escrowed < amount` (or `escrowed == 0`, matching the EVM version) only after skipping zero-amount entries, to ensure one drained/zero token entry cannot block release of the remaining escrowed tokens in the same withdrawal batch.

### Proof of Concept
1. Place a cross-chain order on Tron `IntentGatewayV2` with two input tokens, A and B.
2. Arrange for token A's escrow to reach `_orders[commitment][A] == 0` prior to the finalizing `withdraw()` call for the order (e.g., via a prior legitimate partial refund/withdraw path that already zeroed out A, or an order whose `inputs` array carries a zero-amount placeholder entry for A while B still holds real escrow).
3. Trigger the cross-chain settlement (`RedeemEscrow`) or refund (`RefundEscrow`) message to `onAccept`, which calls `withdraw(body, isRefund)` with `body.tokens = [A, B]`.
4. The loop hits `_orders[commitment][A] == 0` on the first iteration and reverts with `UnknownOrder()` — token B's non-zero escrow is never released, and the message cannot be reprocessed to release it, permanently locking B's funds in the contract. [1](#0-0)
