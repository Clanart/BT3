## Title
Path Traversal via Tracked Symlinks in "Open in External Editor" / File Context Menu Actions Bypasses `resolveWithin` Guard - (File: `app/src/ui/app.tsx`)

### Summary
GitHub Desktop contains a dedicated helper, `resolveWithin()` in [1](#0-0) , whose explicit purpose is to reject any path (including one reached through a symlink) that resolves outside a given root. It is used to guard the `x-github-client://openRepo` deep-link `filepath` handler [2](#0-1) . Its own test suite specifically proves it blocks symlink-based traversal out of the root [3](#0-2) .

However, several other places in the UI that build a full filesystem path from a repository-relative `file.path` (which comes directly from `git status`/`git diff` output describing the actual working tree, including tracked symlinks) do **not** use `resolveWithin` — they simply do `Path.join(repository.path, path)` and pass the result straight to actions that open/execute/reveal the file:

- `app/src/ui/app.tsx` `onOpenInExternalEditor` [4](#0-3) 
- `app/src/ui/changes/filter-changes-list.tsx` `getCopyPathMenuItem` / `getCopySelectedPathsMenuItem` [5](#0-4) 
- `app/src/ui/open-pull-request/pull-request-files-changed.tsx` `onOpenFile` / `onFileContextMenu` [6](#0-5) [7](#0-6) 

### Finding Description
The path guard `resolveWithin()` explicitly `realpath()`-resolves both the root and the joined candidate path and only allows the result if the real path is still under the real root [8](#0-7) . This is the correct mitigation against exactly the class of bug in the report: a value that looks safe after naive normalization but resolves elsewhere once the filesystem (or, in Apache's case, the decoder) is consulted a second time.

That mitigation, though, is only wired into the `openRepositoryFromUrl` deep-link flow. The much more common "open file" affordances in the Changes list, PR review file list, and "Open in External Editor" context-menu actions build the full path with a bare `Path.join(repository.path, path)` and never call `resolveWithin` or `realpath` on the result:

```ts
// app/src/ui/app.tsx
private onOpenInExternalEditor = (path: string) => {
  const repository = this.state.selectedState?.repository
  if (repository === undefined) return
  const fullPath = Path.join(repository.path, path)   // no resolveWithin check
  this.props.dispatcher.openInExternalEditor(fullPath)
}
```

`path`/`file.path` here originates from `WorkingDirectoryFileChange`/`CommittedFileChange` entries, which are populated from `git status`/`git diff` against the actual working tree of a **cloned or fetched repository the attacker controls**. Because git tracks symlinks as ordinary blobs, an attacker can commit a symlink (e.g. `evil -> ../../../../..` or `evil -> /Users/victim`) as part of the repository. Once checked out, `git status`/`git diff` will report changes for files reachable *through* that symlink using ordinary relative path strings (e.g. `evil/some-file`). `Path.join(repository.path, "evil/some-file")` produces a string that syntactically looks like it's inside the repo, but the filesystem will resolve it through the symlink to a location entirely outside the repository — precisely the traversal `resolveWithin`'s `realpath` check exists to catch, and precisely the scenario the project's own tests validate against [3](#0-2)  — but that check is simply not called on these code paths.

### Impact Explanation
An attacker who gets a victim to clone/fetch a malicious repository (or open a malicious pull request and use "Open in external editor"/"Copy File Path"/double-click in the PR Files Changed view) can cause GitHub Desktop to construct and open/read a path outside the repository via a tracked symlink, without any of the guard rails (`resolveWithin`, `isAbsolute` rejection) applied elsewhere in the codebase for the same class of untrusted-path problem. Depending on which action is used this yields disclosure of file contents outside the repo (Open in External Editor), disclosure of absolute filesystem paths (Copy Path), or unmasking sensitive files (Reveal in File Manager) — matching the "file read outside the repo" impact category. This does not directly grant RCE the way the Apache report did, but it is the direct Desktop analog of "an attacker-controlled path structure defeats the app's directory-confinement check."

### Likelihood Explanation
No unusual user steps are required beyond the normal workflow the app is built for: cloning a repository, viewing its Changes list, or reviewing a pull request and double-clicking/opening a file — actions a user performs routinely on untrusted repositories. The attacker only needs to add a symlink file to the repository, which is a completely ordinary git operation requiring no special privileges.

### Recommendation
Route every code path that turns a repository-relative `file.path` into a filesystem path for opening/revealing/copying (in `app.tsx`'s `onOpenInExternalEditor`, `filter-changes-list.tsx`'s `getCopyPathMenuItem`/`getCopySelectedPathsMenuItem`, and `pull-request-files-changed.tsx`'s `onOpenFile`/`onFileContextMenu`) through the existing `resolveWithin()` helper (already implemented in `app/src/lib/path.ts`) instead of a bare `Path.join`, and refuse to proceed if it returns `null`, mirroring the guard already applied in `dispatcher.ts`'s `openRepositoryFromUrl`.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink `payload -> ../../../../../../Users/victim/.ssh` (or any sensitive/out-of-repo directory) and commits it.
2. Victim clones this repository with GitHub Desktop and checks it out (symlink is materialized on disk).
3. Attacker's follow-up commit/PR adds a file that appears, from git's perspective, as `payload/id_rsa` (i.e., a change to a file through the symlinked path) — or the victim simply browses the file tree of the already-checked-out symlink target which git status will report as ordinary paths.
4. Victim right-clicks the corresponding entry in the Changes list / PR "Files changed" list and selects "Open in External Editor" (or double-clicks it in the PR file list).
5. `Path.join(repository.path, "payload/id_rsa")` resolves through the symlink to `/Users/victim/.ssh/id_rsa`, and `dispatcher.openInExternalEditor` opens that file with no `resolveWithin`/`realpath` check ever applied, unlike the equivalent, already-patched `openRepositoryFromUrl` deep-link flow.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
