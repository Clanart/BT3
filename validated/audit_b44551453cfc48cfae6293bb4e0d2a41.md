### Title
`ReceivedOutput::read` accepts unauthenticated output data without verifying the offset/script/outpoint binding — funds can be reported received that are not spendable — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The reported bug class is accepting and acting on content fetched over an unauthenticated channel (an executable downloaded over plaintext HTTP, substituted by a network attacker). The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134`, which deserializes an `(offset, output, outpoint)` triple from a raw byte stream and trusts it without ever checking that the three fields are mutually consistent — i.e., that `output.script_pubkey` actually equals the P2TR script derived from `key + offset * G`, or that `outpoint` references the claimed `TxOut`. Any `ReceivedOutput` obtained over an untrusted channel (synced, relayed, or stored bytes rather than produced locally by `Scanner::scan_transaction`) can claim the wallet received funds it cannot spend.

### Finding Description
`Scanner::scan_transaction` is the honest producer of `ReceivedOutput`: it only emits an output when `self.scripts.get(&output.script_pubkey)` finds the exact registered script, guaranteeing the `offset` genuinely corresponds to that script_pubkey and the `outpoint` genuinely references that output in the scanned transaction (`networks/bitcoin/src/wallet/mod.rs:199-214`).

`ReceivedOutput::read`, however, performs no such binding. It reads a scalar offset via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and an arbitrary `OutPoint`, and returns them as a trusted `ReceivedOutput`:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no re-derivation of `p2tr_script_buf(key + offset*G)` to compare against `output.script_pubkey`, and (unavoidably but unchecked) no confirmation that `outpoint` resolves to `output`. A caller that hydrates `ReceivedOutput`s from an untrusted source — the exact scenario of the advisory, where bytes arrive over a channel an attacker can modify — will treat a crafted triple as a spendable received output.

### Impact Explanation
An attacker who can supply or alter serialized `ReceivedOutput` bytes (network position, compromised relay/storage — the same attacker model as the HTTP-download advisory) can make the wallet report funds as received that are not spendable:

- `offset` + attacker-chosen `script_pubkey`: the reported `value()` counts toward the balance, but the threshold key cannot sign for it, since the offset does not correspond to the script. `ReceivedOutput` is explicitly documented as "A spendable output" (`mod.rs:88`).
- A fabricated `outpoint` pointing at an output the attacker owns, paired with the wallet's real script_pubkey encoding, inflates the reported balance with funds the wallet never received.

Both lead to accounting acceptance of non-existent/unspendable funds — the "funds reported received that are not spendable" impact class — mirroring how the vulnerable package accepts substituted executables as legitimate.

### Likelihood Explanation
Exploitation requires the attacker to control the byte stream fed to `ReceivedOutput::read` — plausible whenever serialized outputs are transported or persisted over any channel the attacker can modify (the advisory's threat model). It does not require forging signatures, breaking threshold security, or controlling a validator. The read path is in the explicitly enumerated untrusted-input surface (`ReceivedOutput::read`). Impact is limited to incorrect balance/UTXO reporting rather than direct theft, consistent with Medium severity.

### Recommendation
Either (a) bind the fields at deserialization time by requiring the caller's scanning key and re-checking `output.script_pubkey == p2tr_script_buf(key + offset*G)` inside or immediately after `ReceivedOutput::read`, or (b) make `ReceivedOutput` construction non-public so instances can only originate from `Scanner::scan_transaction`/`scan_block`, and document that deserialized outputs must be re-validated against the chain (outpoint → TxOut resolution) before being counted as spendable.

### Proof of Concept
```rust
// Conceptual: attacker-controlled bytes fed to ReceivedOutput::read
let mut bytes = vec![];
// offset = 1 (does NOT correspond to the script_pubkey below)
bytes.extend(Scalar::ONE.to_bytes());
// TxOut paying to an attacker-chosen P2TR script, value = 1_000_000 sats
bytes.extend(&serialize(&TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: attacker_script, // not derivable from wallet key + offset 1
}));
// OutPoint referencing a real transaction output owned by the attacker
bytes.extend(&serialize(&attacker_outpoint));

let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 1_000_000); // reported as received
// ... yet the threshold key cannot produce a signature spending it:
// offset 1 does not yield `attacker_script` under tweak_keys,
// so the "received" funds are unspendable phantom balance.
```

The root cause is that `ReceivedOutput::read` (`mod.rs:122`) treats the serialized triple as self-authenticating, when the only integrity guarantee — the `scripts` HashMap lookup — lives exclusively in `Scanner::scan_transaction` (`mod.rs:205`) and is bypassed entirely by the deserialization path.
