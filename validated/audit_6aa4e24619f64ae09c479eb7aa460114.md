### Title
`ThresholdKeys::read`/`new` accept `t = 1`, letting a single participant unilaterally control the reported `group_key` (a 1-of-n "multisig") - ([File: crypto/dkg/src/lib.rs])

### Summary
Analogous to the HOPR finding — where `NodeStakeFactory` initialized the Safe with `threshold = 1`, letting a single signer unilaterally disable the node-management module while the registry still reported it as registered — Serai's `ThresholdKeys` accepts a threshold of one with no minimum-threshold enforcement. Untrusted bytes fed to `ThresholdKeys::read` (or programmatic use of `ThresholdKeys::new` / `ThresholdParams::new`) can therefore produce a key set whose `group_key()` is spendable by a single participant alone, while still being reported by all accessors (`group_key()`, `params()`, `verification_shares`) as a normal `n`-participant multisig.

### Finding Description
`ThresholdParams::new` only rejects `t == 0` and `t > n`; `t = 1` with any `n` is accepted [1](#0-0) . `ThresholdKeys::new` then derives the group key by interpolating only over participants `1..=t` — i.e., with `t = 1` the group key is simply `verification_shares[1] * interpolation_factor(1, [1]) = verification_shares[1]`, fully controlled by whoever holds secret share 1 [2](#0-1) . `ThresholdKeys::read` reconstructs `t`, `n`, `i`, the interpolation variant, the secret share, and the verification shares entirely from attacker-controlled bytes and passes them to `ThresholdParams::new`/`ThresholdKeys::new` with no floor on `t` [3](#0-2) . At signing time, `view()` only requires `included.len() >= t`, so a single participant satisfies the "quorum" [4](#0-3) , and `AlgorithmSignMachine::sign` accepts `included.len() == 1 == t` [5](#0-4) .

### Impact Explanation
Funds addressed to `group_key()` of a deserialized `t = 1` key set are spendable by one participant alone — the multisig's distributed-authority guarantee is silently void, exactly mirroring how the HOPR Safe remained "registered" while a single signer could strip its functionality. All introspection (`params().n()`, `original_verification_share`, `view().included()`) still presents a coherent `n`-participant structure; nothing in the type distinguishes this state. Any consumer that loads serialized `ThresholdKeys` (the format is fully self-describing: ciphersuite ID, t, n, i, interpolation, shares) inherits the downgraded threshold.

### Likelihood Explanation
`ThresholdKeys::read` is an explicitly in-scope untrusted-byte sink. Crafting the malicious encoding requires only setting the `t` field to `1` in an otherwise-valid serialization — no key material knowledge needed to *construct* the object. Exploitation additionally requires the attacker to control the share of participant 1 (or for the victim to operate on attacker-supplied key material where they also supply share 1), which is realistic wherever serialized key sets cross a trust boundary (e.g., recovery/import paths like `recover_key` consumers or vector-style deserialization as in `crypto/frost/src/tests/vectors.rs`).

### Recommendation
Enforce a protocol-level minimum in `ThresholdParams::new`/`ThresholdKeys::new` (e.g., reject `t < 2`, or require `t` to satisfy the network's `n * 2/3 + 1` policy at construction/deserialization time, not just at use sites). Additionally, `ThresholdKeys::read` should validate the loaded parameters against caller-expected `t`/`n` rather than trusting the byte stream — analogous to the report's suggested Safe `Guard` that re-checks invariants after every state-changing operation.

```rust
serialized.push(1);                             // Interpolation::Lagrange
serialized.extend(attacker_or_victim_share.to_repr().as_ref());
for share in &verification_shares { serialized.extend(share.to_bytes().as_ref()); }

let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut serialized.as_ref()).unwrap();
// group_key() == verification_shares[1] * G — controlled solely by participant 1
// keys.view(vec![Participant::new(1).unwrap()]) succeeds; a single signer produces
// valid FROST signatures under this "n-party" group key.
```
This is reachable purely from untrusted bytes supplied to `ThresholdKeys::read`, with no cooperation from other participants required.
