## Analysis

The external report's core pattern — external token transfer executed **before** the corresponding balance/accounting state is updated, without a reentrancy guard — has a direct structural analog in this repository's Tron fork of the Intent Gateway.

### Title
CEI violation in `IntentGatewayV2.withdraw()` on the Tron fork — no reentrancy guard, escrow accounting decremented after external transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2`/`IntentsBase` contracts were hardened against reentrancy: `_orders[commitment][token]` is decremented **before** the external transfer [1](#0-0) , `cancelOrder`/`fillOrder` carry `nonReentrant` [2](#0-1) , and `_filled[commitment]` is set at the top of the fill path specifically to close the reentrancy window (documented and regression-tested in `IntrinsicIntentsReentrancyTest.sol`) [3](#0-2) . The Tron fork of the same contract does **not** carry these mitigations: its `withdraw()` performs the ETH/ERC-20 transfer with a raw `.call()` and only decrements `_orders[body.commitment][token]` (and deletes the fee entry) **afterward** [4](#0-3) , and none of `placeOrder`, `cancelOrder`, `onAccept`, or `onGetResponse` in this file carry a `nonReentrant` modifier — confirmed by a repo-wide search finding zero occurrences of `nonReentrant`/`ReentrancyGuard` under `evm/tron/**`.

### Finding Description
In `withdraw()`:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        ...
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        ...
    }
    _orders[body.commitment][token] -= amount;   // <-- accounting update AFTER external call
    ...
}
``` [5](#0-4) 

This is the exact CEI-violation shape described in the `CreditorNFT` report: external call to a potentially hook-bearing token/beneficiary, followed by the state write that is supposed to prevent re-use. The escrow-existence guard is also weak — `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only checks non-zero, not sufficiency, so it doesn't protect partial/duplicate spend of the same slot.

The equivalent escrow-crediting path in `placeOrder` has the same ordering problem: `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);` runs, and only afterward is `_orders[commitment][token] += reducedInputs[i].amount;` credited [6](#0-5) . For a multi-input order, a token with a transfer hook fired on an earlier-processed input (already credited) can call back into `cancelOrder` for the same, not-yet-fully-escrowed commitment while later inputs are still uncredited.

The mitigation that exists in the mainline contract (`nonReentrant` + `_filled` set before any transfer, validated by dedicated fuzz/unit tests) was never ported to this Tron variant, so the fork relies solely on the "set `_filled` first" ordering inside `withdraw()` itself with no defense-in-depth guard at the public entry points (`placeOrder`, `cancelOrder`).

### Impact Explanation
If any escrowed input token, the configured fee token, or (via governance) a future asset with transfer hooks/callbacks is used, an attacker-controlled beneficiary/order-user contract can re-enter public functions during the external transfer inside `withdraw()`/`placeOrder()` before the corresponding `_orders[commitment][token]` mutation lands. This falls under "stealing or loss of funds" / "logic attacks" in the bounty scope because it targets escrow custody accounting directly at the Intent Gateway's public entrypoints, without requiring a malicious relayer, prover, or admin — the attacker only needs to control the order's beneficiary contract, which the protocol design already allows (`order.user`/beneficiary is attacker-supplied).

### Likelihood Explanation
Medium: exploitation depends on a registered token exhibiting transfer-time callbacks (ERC-777-style or similar hook token) being paired with the Intent Gateway on Tron, or on native-ETH beneficiary contracts triggering reentrant calls during the ETH leg of `withdraw()`. Standard tokens (plain ERC-20) do not trigger callbacks and are unaffected, which is the same caveat present in the original report. However, the complete absence of `nonReentrant` on this fork (versus the hardened, tested mainline contract) means the fix that was already deemed necessary and shipped elsewhere in this repository was not applied here, leaving the fork strictly weaker than the audited/tested baseline.

### Recommendation
Port the same mitigations already implemented and tested on the mainline `IntentGatewayV2`/`IntentsBase` contracts to the Tron fork:
- Add `nonReentrant` (OpenZeppelin `ReentrancyGuard`) to `placeOrder`, `cancelOrder`, and any `fillOrder`/`select` entrypoints in `evm/tron/contracts/apps/IntentGatewayV2.sol`.
- In `withdraw()`, decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the external `.call()` transfer, matching `IntentsBase._withdraw` in the mainline contract.
- In `placeOrder`, credit `_orders[commitment][token]` before calling `safeTransferFrom`, or otherwise ensure the full input array is credited atomically before any external call can hand control back to `msg.sender`.

### Proof of Concept
1. Attacker places a same-chain order (`placeOrder`) where `order.user` == a malicious contract they control, with two inputs: `inputs[0]` a plain ERC-20 (e.g., USDC) and `inputs[1]` a hook-bearing token (or, on the withdraw side, native ETH as the sole input).
2. Attacker calls `cancelOrder(order, options)` for the same-chain path (`isSameChain == true`), which invokes `withdraw(body, true)` internally [7](#0-6) .
3. Inside `withdraw()`, `_filled[commitment]` is set, then the loop reaches the native-ETH (or hook-token) leg and calls `beneficiary.call{value: amount}("")` before decrementing `_orders[commitment][token]` for that entry [8](#0-7) .
4. The attacker's contract `receive()`/token hook fires during this call. Because `withdraw()` is `internal` and no `nonReentrant` guard exists anywhere in the file, the only thing preventing double-spend is the `_filled[commitment]` check inside `cancelOrder`/`onAccept`/`onGetResponse` for *this same commitment* — there is no protection against reentering `placeOrder` (to manipulate `_nonce`/escrow state for a different, freshly-crafted commitment sharing token balances) or against multi-input orders where some entries are already decremented and others are not, unlike the mainline contract where the analogous class of bug was found, fixed, and regression-tested in `IntrinsicIntentsReentrancyTest.sol`.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
