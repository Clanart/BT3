### Title
lpSupply inflation via direct token donation permanently dilutes staker rewards - (File: rewards/MasterMagpie.sol)

### Summary
`_calLpSupply()` returns the raw `balanceOf(address(this))` of the staking token for every pool except vlMGP and mWomSV, instead of tracking a dedicated "total staked" accumulator credited only through `_deposit`/`_withdraw`. An attacker can transfer staking tokens directly to `MasterMagpie` (bypassing `deposit`), inflating the denominator used in `updatePool` without ever incrementing any `UserInfo.amount`, permanently diluting `accMGPPerShare` growth for all legitimate stakers.

### Finding Description
`updatePool(address _stakingToken)` computes the reward index increment as: [1](#0-0) 

`lpSupply` comes from `_calLpSupply`, which for any pool other than vlMGP/mWomSV simply reads the ERC20 balance held by the contract: [2](#0-1) 

Under normal operation this balance is kept in sync with the sum of `UserInfo.amount` because `_deposit` performs `safeTransferFrom` for exactly `_amount` while crediting `user.amount`/`user.available` by the same `_amount`: [3](#0-2) 

However, nothing prevents an attacker from calling `IERC20(_stakingToken).transfer(masterMagpieAddress, X)` directly — a raw donation that increases `balanceOf(this)` without going through `_deposit` and thus without incrementing any `UserInfo.amount`. The very next `updatePool` call (triggered by any user's deposit/withdraw/claim, or callable by anyone directly since it's `public`) will use this inflated `lpSupply` as the divisor:

```
pool.accMGPPerShare = pool.accMGPPerShare + ((mgpReward * 1e12) / lpSupply);
```

`mgpReward` is fixed by `mgpPerSec * pool.allocPoint / totalAllocPoint * elapsedTime` — independent of how the tokens are distributed among stakers. Dividing this fixed numerator by an artificially inflated denominator permanently reduces the per-share reward accrual rate for every subsequent staker, for as long as the donated balance remains in the contract (which is forever, since no code path removes tokens that were never credited to a `UserInfo` entry). There is no mechanism to "skim" or reconcile the donated balance back out, so the dilution is irreversible for that pool.

Existing guards (`whenNotPaused`, `nonReentrant` on deposit/withdraw, `_onlyPoolHelper` on `depositFor`) do not protect against this because `updatePool` itself has no access control (`public`) and `_calLpSupply` has no way to distinguish donated balance from properly staked balance for generic pools.

### Impact Explanation
Because `mgpReward` (the numerator, tied to `mgpPerSec`) is emitted/funded independently of `lpSupply`, but `accMGPPerShare` accrual is divided by the inflated `lpSupply`, real stakers accrue less `unClaimedMgp` than the MGP amount that was actually allocated for that time interval based on `mgpPerSec`. The gap between what was emitted (per `mgpPerSec`) and what stakers can actually claim (per diluted `accMGPPerShare`) becomes MGP sitting in `MasterMagpie`'s balance that no `UserInfo.amount` can ever claim — a permanent freezing of unclaimed yield, consistent with the "High - Permanent freezing of unclaimed yield" Immunefi classification.

### Likelihood Explanation
The attack requires only the ability to acquire the staking token on the open market (no privileged role, no flash loan even needed) and perform a plain ERC20 `transfer` to the `MasterMagpie` contract address. It is cheap, repeatable per pool, and can be executed at any time (sandwiching a large honest deposit maximizes the dilution window, but is not strictly required — any direct donation immediately and permanently raises the denominator for all future `updatePool` calls on that pool).

### Recommendation
Track staked supply explicitly per pool (e.g., a `pool.totalStaked` field incremented/decremented only inside `_deposit`/`_withdraw`/`_harvestAndUnstake`) and use that value in `_calLpSupply` instead of `IERC20(_stakingToken).balanceOf(address(this))`, so that direct token transfers to the contract cannot affect `accMGPPerShare` accrual.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, register a pool with staking token `LP`, set `mgpPerSec` and `allocPoint`.
2. User A calls `deposit(LP, 100e18)`.
3. Advance time by `T` seconds, call `updatePool(LP)`, record `accMGPPerShare_1`.
4. Reset state (or run a second scenario): before advancing time, an attacker (holding `LP` bought on market, not deposited) directly calls `LP.transfer(masterMagpie, 900e18)` (9x the real staked amount) — no `UserInfo` entry is created/updated for the attacker.
5. Advance the same `T` seconds, call `updatePool(LP)`, record `accMGPPerShare_2`.
6. Assert `accMGPPerShare_2 < accMGPPerShare_1` even though `mgpPerSec`, `allocPoint`, and elapsed time were identical — proving the donation diluted the reward index.
7. Have User A call `multiclaim([LP])` in both scenarios and assert the MGP amount claimed in scenario 2 is materially smaller, while `IERC20(mgp).balanceOf(masterMagpie)` retains the undistributed surplus with no code path to recover it for User A.

        if (_stakingToken == address(vlmgp)) {
            return IERC20(address(vlmgp)).totalSupply();
        }
        if (_stakingToken == address(mWomSV)) {
