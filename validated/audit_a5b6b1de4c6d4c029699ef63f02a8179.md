### Title
`internal_withdraw` RPC bypasses the aggregator-authenticity check enforced by `withdraw`, allowing an unauthenticated caller to trigger operator payout broadcasting - (File: core/src/rpc/operator.rs)

### Summary
The `ClementineOperator` gRPC service exposes two methods that both invoke the identical state-changing/broadcasting function `Operator::withdraw` (which builds, signs, and returns/broadcasts a payout transaction fronting a withdrawal): `withdraw` and `internal_withdraw`. `withdraw` enforces that the request is authenticated by the aggregator/Citrea via an EIP-712 ECDSA `verification_signature` matched against `config.aggregator_verification_address`, but `internal_withdraw` performs no such check before calling the same underlying function.

### Finding Description
`ClementineOperatorServer::withdraw` requires and verifies a `verification_signature` before it will call `self.operator.withdraw(...)`: [1](#0-0) 

In contrast, `internal_withdraw` parses the same `WithdrawParams` and calls `self.operator.withdraw(...)` directly, with no authenticity check at all: [2](#0-1) 

Both handlers funnel into the exact same state-changing function `Operator::withdraw`, which is the operator's mechanism for fronting a withdrawal payout on behalf of a user/Citrea request (analogous to the deposit/callback consistency issue in the referenced report, where one code path enforced an invariant and a parallel path with the same effective privilege did not). The documented purpose of the verification signature module makes clear it exists specifically "for additional verification that the request for optimistic payout and withdrawal is coming from the aggregator, which is the owner of the address in operator/verifiers config": [3](#0-2) 

`internal_withdraw` circumvents this authenticity binding entirely — the equality that should hold is:
`caller of Operator::withdraw == party authenticated via aggregator_verification_address`
but via `internal_withdraw` this becomes:
`caller of Operator::withdraw == any client able to reach the operator's ClementineOperator gRPC service`.

### Impact Explanation
This is a caller reaching a state-changing/broadcasting method (`Operator::withdraw`, which signs and returns a payout transaction fronting BTC for a withdrawal) that is meant to be gated to the party authenticated by the aggregator's verification signature. If `internal_withdraw` is reachable on the same network-exposed service as `withdraw` without equivalent authorization, this matches the "unauthenticated state-changing or broadcasting call" High-impact category: an operator could be induced to front payouts for withdrawal requests that were never legitimately authorized by the aggregator/Citrea light client, independent of whatever on-chain validation `Operator::withdraw` itself performs against Citrea state.

### Likelihood Explanation
Likelihood depends on the operator gRPC service's transport-level authorization (mTLS client-cert policy) allowing any bridge participant (or misconfigured deployment) to reach `internal_withdraw` without being the aggregator. The presence of a completely separate, non-gated RPC method performing the identical privileged action as the gated one is itself a design/implementation inconsistency, independent of transport controls, and is directly analogous to the reported bug class (parallel entry points to the same privileged operation with inconsistent enforcement).

### Recommendation
Either remove `internal_withdraw` as a distinct unauthenticated entry point, or enforce the same `verification_signature`/`aggregator_verification_address` check inside `internal_withdraw` (or better, inside `Operator::withdraw` itself) so that both RPC paths to the shared privileged function are equally authorized, mirroring the recommendation in the reference report to consolidate multiple inconsistent entry points into a single, uniformly-enforced interface.

### Proof of Concept
1. A client with network access to the operator's `ClementineOperator` gRPC service (without possessing the aggregator's verification secret key) calls `InternalWithdraw` with attacker-chosen `WithdrawParams` (`withdrawal_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`).
2. `internal_withdraw` (core/src/rpc/operator.rs:168-190) parses the params and calls `self.operator.withdraw(...)` directly — no `verification_signature` is required or checked, unlike in `withdraw` (core/src/rpc/operator.rs:209-239).
3. The operator proceeds to build and return/broadcast the payout transaction via `Operator::withdraw`, bypassing the aggregator-authenticity gate that the sibling `withdraw` RPC enforces for the identical operation.

Note: I was unable to fully verify, within index limits, whether `Operator::withdraw` (`core/src/operator.rs`) performs independent, sufficient on-chain validation against Citrea withdrawal state that would fully neutralize the missing signature check; confirming that function's internal validation logic would be necessary to establish full exploitability, and I could not retrieve and review that specific function body before this analysis concluded.
