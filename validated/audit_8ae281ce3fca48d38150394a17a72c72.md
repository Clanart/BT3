### Title
DataLayer mirror URLs are unvalidated and cause the local node to make SSRF-style HTTP requests to attacker-chosen (including internal) hosts - (File: `chia/data_layer/data_layer_wallet.py`)

### Summary
Mastodon's FASP flow let an unauthenticated actor register a `base_url` with no host validation, which the server later fetched, enabling SSRF to internal addresses. Chia's DataLayer mirror mechanism has the same shape: any wallet holder can publish arbitrary mirror URLs on-chain for **any** `store_id` (not just their own), and any Data Layer client that subscribes to that store will later make outbound HTTP requests to those unvalidated URLs.

### Finding Description
`DataLayerWallet.create_new_mirror()` creates a standard-wallet spend to the mirror puzzle and embeds `launcher_id` and attacker-chosen `urls` directly into the coin memo, with no check that the caller owns or controls that `launcher_id`/store, and no validation of the URL contents: [1](#0-0) 

The RPC surface (`dl_new_mirror`) exposes this directly, taking only `launcher_id`, `amount`, and free-form `urls`: [2](#0-1) [3](#0-2) 

Once the mirror coin is spent/confirmed, any node tracking that launcher id ingests the mirror via `coin_added()`, which decodes the URLs and stores them without validation: [4](#0-3) 

The DataLayer service `add_mirror()` (reachable via `DataLayerRpcApi.add_mirror`) only rejects an empty URL list — no scheme/host/IP allow-listing: [5](#0-4) [6](#0-5) 

Subscribers pull these attacker-controlled URLs from the wallet and store them as sync servers: [7](#0-6) 

The periodic sync loop (`fetch_and_validate()`/`update_subscription()`) then randomly selects one of these server URLs and performs outbound HTTP GET requests via `http_download()` in `download_data.py`, with no restriction on private/loopback/link-local IP ranges: [8](#0-7) [9](#0-8) 

Existing tests demonstrate that mirror URLs like `http://127.0.0.1/8000` are accepted and stored without complaint, confirming there is no host/IP filtering anywhere in this path: [10](#0-9) 

The project's own internal documentation explicitly flags this as a known trust boundary that is not enforced at the URL level, only at the data-content level (root re-verification), confirming SSRF/URL exposure is a recognized but unmitigated risk: "Plugin and mirror URLs are external trust inputs... file path/name validation must stay strict" — but no mention of host/IP validation for the URLs themselves.


### Impact Explanation
This is directly analogous to the Mastodon FASP SSRF: an unprivileged, unauthenticated (from the target's perspective) actor — any wallet user willing to spend a small fee — can force any subscribing Data Layer node to issue outbound HTTP(S) requests to an internal/local address (e.g., cloud metadata endpoints, internal admin panels, loopback services) chosen by the attacker via mirror coin memos, without needing to own the targeted store. While the attacker cannot see the response body (the wallet log only reports errors/success), the request itself can trigger side effects on unprotected internal services, probe for open ports, or be used to fingerprint internal infrastructure — matching the Medium-severity SSRF classification in the referenced advisory. Because mirrors are published on-chain and consumed by *any* node subscribed to the targeted store, the blast radius includes third-party Data Layer operators who never asked to trust the attacker.

### Likelihood Explanation
Likelihood is high for any Data Layer operator that subscribes to third-party stores (the standard usage pattern for a "client" of someone else's dataset). The attacker only needs standard wallet functionality (`dl_new_mirror`/`add_mirror`) and a small on-chain fee — no special permissions, no admin approval (unlike the FASP flow, which at least required manual admin approval to register a provider; here there is no approval step at all). The victim's periodic `periodically_manage_data()` loop runs automatically and will pick up and fetch from the malicious mirror URL without any manual step from the victim beyond having previously subscribed to the (possibly attacker's own) store.

### Recommendation
- Validate mirror URLs before persisting/publishing and before using them for HTTP downloads: reject or resolve-and-block private/loopback/link-local/multicast IP ranges and non-http(s) schemes, similar to typical SSRF mitigations.
- Consider restricting `create_new_mirror`/`dl_new_mirror` to only allow adding mirrors for stores actually owned/tracked by the caller's wallet where meaningful, or at minimum apply the same host-safety checks used for the DataLayer HTTP client (`aiohttp.ClientSession`) used in `http_download()` and `get_downloader()`/`get_uploaders()` plugin calls.
- Apply the fix at the point of consumption (`fetch_and_validate()`, `http_download()`, `get_downloader()`) as defense-in-depth, since URLs can also arrive from configuration (`downloaders`/`uploaders`) or be added/modified between publication and use.

### Proof of Concept
1. Attacker runs a standard (unprivileged) wallet with a DataLayer wallet enabled and calls `dl_new_mirror` (or CLI `chia data add_mirror`) targeting a `launcher_id` of a store that a victim Data Layer node subscribes to, with `urls=["http://169.254.169.254/latest/meta-data/"]` or `["http://127.0.0.1:6379/"]`, as shown accepted in `chia/_tests/core/data_layer/test_data_rpc.py` (`test_mirrors`) with `http://127.0.0.1/8000`.
2. The mirror coin is confirmed on-chain and picked up by the victim's `DataLayerWallet.coin_added()` for the tracked launcher id.
3. The victim's `DataLayer.update_subscriptions_from_wallet()` pulls this URL into its subscription server list.
4. On the next `periodically_manage_data()` cycle, `fetch_and_validate()` selects this server and issues an HTTP request via `http_download()` to the attacker-chosen internal address, completing the SSRF.

```python
        self,
        request: DLNewMirror,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLNewMirrorResponse:
        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            await dl_wallet.create_new_mirror(
                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,
            )
```

```python
async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```
