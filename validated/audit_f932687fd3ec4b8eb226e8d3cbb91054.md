## Finding

CR-CAT payments can become permanently unclaimable if `authorized_providers` is misconfigured, mirroring the Gitcoin "misconfigured round → assets used to vote may be lost" bug class: an immutable, unchecked configuration value (the voting strategy address there; the CR-CAT authorized-providers list here) is baked into the on-chain object at creation time, is never re-validated, and if wrong causes user funds to become unrecoverable with no revert.

### Title
CR-CAT payments sent to a misconfigured `authorized_providers` list become permanently unclaimable, causing irrecoverable loss of user assets - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
`CRCATWallet.get_or_create_wallet_for_cat` and `CRCAT.launch` accept an `authorized_providers` list (a list of DID launcher IDs) and a `proofs_checker` at CR-CAT creation time and curry them irrevocably into the on-chain puzzle via `construct_cr_layer`. [1](#0-0) [2](#0-1)  Neither method validates that any real, reachable Verified Credential (VC) actually exists (or will ever exist) with a `proof_provider` matching one of the supplied `authorized_providers`.

When a payment for such a CR-CAT is sent to a puzzle hash not already owned by the sender's wallet, `CRCATWallet.generate_signed_transaction` unconditionally wraps the output in `construct_pending_approval_state`, locking the coin behind the credential-restriction layer, again without checking that a satisfying VC exists. [3](#0-2) 

### Finding Description
The credential-restriction inner layer enforces on-chain that only a spend accompanied by a valid VC proof from one of the curried `authorized_providers` can move a CR-CAT coin out of the pending-approval state. This is symmetrical to the Gitcoin report where `votingStrategy` is set once in the constructor with no validation and every subsequent `vote()` call blindly forwards `msg.value` to it.

If `authorized_providers` is misconfigured at creation (wrong DID id, typo, or a DID whose owner never actually issues/possesses a VC with matching proofs), any XCH/CAT value converted into this CR-CAT, and any subsequent payment routed through `construct_pending_approval_state`, can never be claimed. This is confirmed by the wallet's own claim path, which raises when no matching VC exists: [4](#0-3) 

Unlike the Gitcoin report where the payable call simply reverts-then-continues (no-op & no revert on the token transfer), here the spend bundle *does* succeed on-chain (coins are created), but the resulting coin is permanently unspendable by anyone because the CLVM credential-restriction puzzle requires proof from a provider that will never produce a valid VC.

### Impact Explanation
Any wallet user (maker/taker in an offer, or a direct CR-CAT payment sender) who creates or transacts with a CR-CAT whose `authorized_providers` is misconfigured causes value to be irrecoverably locked in a "pending approval" coin that no VC can ever unlock. This is a direct, concrete loss of user funds analogous to the reported issue, reachable purely through normal wallet actions (CR-CAT creation via `get_or_create_wallet_for_cat`/`CRCAT.launch`, or an ordinary payment via `generate_signed_transaction`) with no privileged or malicious-actor requirement.

### Likelihood Explanation
Requires a CR-CAT to be minted/configured with an incorrect `authorized_providers` value (e.g. by a CR-CAT issuer or during an offer/trade flow) — an operator/configuration mistake, not an attack, exactly the scenario flagged as Medium severity in the source report. Given there's no validation anywhere in the mint or payment path that a satisfying VC exists, this misconfiguration is easy to make and hard to detect until funds are already locked.

### Recommendation
Before allowing a CR-CAT to be created (`get_or_create_wallet_for_cat`, `CRCAT.launch`) or before routing a payment into `construct_pending_approval_state`, verify that at least one resolvable VC (or DID capable of issuing one) exists for every entry in `authorized_providers`, and warn/reject if none can be found. Additionally, consider providing an on-chain or wallet-level fallback/timeout path (analogous to a "withdraw" safety valve) for coins stuck in the pending-approval state when no VC can ever satisfy the credential-restriction layer.

### Proof of Concept
1. Create a CR-CAT wallet with `authorized_providers=[<random_or_wrong_did_launcher_id>]` via `CRCATWallet.get_or_create_wallet_for_cat` (no error is raised). [1](#0-0) 
2. Mint/receive value into this CR-CAT (e.g., via `CRCAT.launch` or a normal payment wrapped by `construct_pending_approval_state`). [5](#0-4) 
3. Attempt `claim_pending_approval_balance` — it raises `RuntimeError("No VC exists that can approve spends for CR-CAT wallet ...")` because no VC with a matching provider was ever obtainable, and no on-chain path exists to move the funds otherwise. [4](#0-3)

    @classmethod
    async def get_or_create_wallet_for_cat(
        cls,

        if name is None:

        self.log = logging.getLogger(name)

        for id, w in wallet_state_manager.wallets.items():
            if w.type() == cls.type():
                assert isinstance(w, cls)
                if w.get_asset_id() == limitations_program_hash:
                    self.log.warning("Not creating wallet for already existing CR-CAT wallet")
                    return w

        self.wallet_state_manager = wallet_state_manager

        self.info = CRCATInfo(limitations_program_hash, None, authorized_providers, proofs_checker)
        info_as_string = bytes(self.info).hex()
        self.wallet_info = await wallet_state_manager.user_store.create_wallet(name, WalletType.CRCAT, info_as_string)

        await self.wallet_state_manager.add_new_wallet(self)
        self.tail_hash = self.info.limitations_program_hash
        return self

def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)

                1,

                    [51, new_cr_layer_hash, payment.amount, payment.memos],

                ],
            )
