### Title
OP_RETURN data output escapes weight/fee accounting in `SignableTransaction::new`, producing under-priced transactions that can be non-relayable and unbumpable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to H-01 — where the integration assumed two independent claim paths (`claimVeAsset` for veAsset, `claimRewards` for extra rewards) while a single underlying call drained both, leaving the surplus stranded in `VoterProxy` — `SignableTransaction::new` builds the real output list (`tx_outs`) with three logical components (payments, OP_RETURN data, change) but computes the transaction weight, and therefore the required fee, over only `payments` (+ optional change). The OP_RETURN output (up to 80 bytes of attacker/user-supplied data) is appended to `tx_outs` at lines 194–202 yet is never included in `calculate_weight_vbytes` (lines 204, 225–226). The data-carrying output "escapes" the accounting layer the same way non-veAsset reward tokens escaped the veAsset-only claim path: present in the final artifact, invisible to the component that priced it.

### Finding Description
`SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150–256):

1. Lines 188–191: `tx_outs` is built from `payments`.
2. Lines 194–202: if `data` is `Some`, an OP_RETURN `TxOut` carrying up to 80 bytes is pushed onto `tx_outs`.
3. Line 204: `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` — the synthetic transaction inside `calculate_weight_vbytes` (lines 68–99) is constructed **only** from `payments` and the optional change script. The OP_RETURN output is never modeled, so its weight (~11 bytes overhead + `data.len()` bytes, i.e., up to ~91 vbytes… approximately `(4 * (9 + overhead)) + data_len` weight units, ≈ 24–31 vbytes for 80 bytes of data) is excluded from `vbytes`.
4. Line 206: `needed_fee = fee_per_vbyte * vbytes` is computed on the underestimated size.
5. Lines 211–213: the minimum-relay-fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` also uses the underestimated `vbytes`, so it validates the fee against a smaller transaction than the one actually produced.
6. Lines 224–235: the change path recomputes `fee_with_change` again without the data output, so change is over-credited by the same missing amount, compounding the deficit.

Additionally, `TxIn.sequence = Sequence::MAX` (line 183) disables BIP-125 RBF, so an under-priced signed transaction cannot be fee-bumped in place; recovering requires coordinating a new threshold signature over a conflicting spend.

### Impact Explanation
- The broadcast transaction's effective fee rate is `needed_fee / actual_vbytes`, strictly lower than `fee_per_vbyte`. For a minimal transaction (~160–200 vbytes) plus an 80-byte OP_RETURN (~25–30 vbytes), the realized rate is ~85% of the intended rate.
- If `fee_per_vbyte` was set near the relay minimum (the code only enforces ≥ ~1 sat/vbyte on the *underestimated* size), the actual rate can fall below `DEFAULT_MIN_RELAY_TX_FEE` / node `minrelaytxfee`, causing the signed transaction to be rejected or stuck unconfirmed. The inputs are committed to a transaction the network will not relay, and because `Sequence::MAX` disables RBF, the multisig must produce an entirely new threshold signature on a conflicting transaction to unstick the funds — exactly the "assets stranded in an intermediate stage with no direct recovery" shape of H-01.
- Because `data` originates from user-supplied `InInstruction` payload (bounded only by the 80-byte check at line 171), an unprivileged depositor controls the size of the unaccounted output and can push a borderline-fee transaction under the relay floor.
- The change amount is also overstated by the same unpriced weight (change is computed after subtracting the too-small `fee_with_change`), so the deficit silently lands either in the change output's erosion of feerate or in the paid fee itself.

### Likelihood Explanation
Deterministic arithmetic error triggered whenever `data.is_some()` on any plan the scheduler signs. Severity is bounded by the 80-byte cap (maximum ~30 unpriced vbytes), so it materially matters only when `fee_per_vbyte` is near the relay minimum or when fee estimation must be accurate; it does not by itself lose funds permanently, but it can produce non-relayable, non-bumpable transactions requiring coordinated re-signing. Consistent with Medium.

### Recommendation
Include the OP_RETURN output in the weight calculation: pass the already-built `tx_outs` (or an explicit data length) into `calculate_weight_vbytes` so `vbytes` reflects the final transaction, e.g. construct the synthetic tx from `payments` plus `TxOut { value: ZERO, script_pubkey: <op_return script> }` when `data` is present, in both the no-change and with-change computations at lines 204 and 225–226. Alternatively, mark inputs `Sequence::MAX - 1` (or another `< 0xFFFFFFFE` value) to permit RBF as a recovery path for under-priced transactions.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics, at fee_per_vbyte = 1 sat/vB
// (minimum allowed: needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000)

let data = vec![0xAA; 80]; // max allowed by the `> 80` check at line 171

// Suppose: 1 input (~57 vB) + 1 payment (~43 vB) => vbytes ≈ 110
// needed_fee = 1 * 110 = 110 sats; min-fee check uses vbytes = 110: 110 >= 110 -> passes

// Actual transaction also carries an OP_RETURN output:
//   ~9 bytes fixed overhead + 80 bytes payload => ~+25 vbytes
// actual_vbytes ≈ 135, but actual fee paid is still ~110 sats
// effective rate ≈ 110/135 ≈ 0.81 sat/vB < 1 sat/vB relay minimum
// => transaction is rejected/non-propagating; inputs are committed to a TX
//    that cannot be broadcast, and Sequence::MAX (line 183) disables RBF,
//    so recovery requires a new FROST signing round on a conflicting spend.
```
Concretely: call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)`, then compare `tx.needed_fee()` and the broadcast transaction's real `vsize()` — `fee() / real_vsize < fee_per_vbyte` always holds, and `TransactionError::TooLowFee` never fires because the check in lines 211–213 uses the same underestimated `vbytes`. This mirrors H-01's structure: one code path (fee/weight estimation over `payments`) was assumed to cover every output of the transaction, while an extra component (the OP_RETURN) was added outside that accounting and its cost was stranded.
