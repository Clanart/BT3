### Title
Hand-rolled `extract_frontmatter` parser silently drops `action: block` when attacker-controlled pattern text contains a literal `---` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` splits the rule file on the literal string `---` using `content.split('---', 2)` with no awareness of quoting/escaping inside field values. Because `plugins/hookify/commands/hookify.md` writes the attacker-influenced `pattern` value verbatim and unquoted into the frontmatter block (and explicitly tells the agent "no need to escape" the pattern), a PR/issue-sourced behavior description containing a literal `---` (e.g. a git-diff-style pattern) truncates the frontmatter early, causing the `action: block` line — which is written after `pattern` in the template — to fall into the discarded/message portion of the split and never reach the parsed dict.

### Finding Description
`extract_frontmatter` (plugins/hookify/core/config_loader.py:87-103) does:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
```
This treats the *first two* occurrences of the raw substring `---` anywhere in the file as the frontmatter delimiters, with no support for quoted scalars, escaping, or YAML block scalars (`|`, `>`). `plugins/hookify/commands/hookify.md` instructs Claude to write rule files using the template:
```
---
name: {rule-name}
enabled: true
event: {bash|file|stop|prompt|all}
pattern: {regex pattern}
action: {warn|block}
---
``` [1](#0-0) 
and explicitly tells the agent not to escape the pattern value: "**Regex syntax**: Use Python regex syntax (raw strings, no need to escape in YAML)" [2](#0-1) . Because `pattern` is populated from attacker-influenced conversation/PR/issue content summarized by the `conversation-analyzer` agent (Step 1) [3](#0-2)  and written unquoted by the `Write` tool, an attacker who supplies behavior text containing a literal `---` (for example, wanting a rule to flag diff markers, merge-conflict markers, or Markdown horizontal rules) causes that string to land inside the `pattern:` line before `action:` in the file. When `extract_frontmatter` runs `split('---', 2)`, the injected `---` is consumed as the *second* delimiter, so everything after it — including `action: block` — is shoved into `parts[2]` (the message body) and never parsed into the frontmatter dict. `Rule.from_dict` then falls back to the default `action='warn'` [4](#0-3) , silently downgrading a rule the user intended to `block` into a no-op `warn`. There is no quoting/escaping handling, no re-scan for a closing delimiter that respects quoted values, and no validation after parsing that the expected keys (`action`, `enabled`) were actually recovered — `load_rule_file` only checks that `frontmatter` is non-empty [5](#0-4) , which it still is (it has `name`, `enabled`, `event`, and a partial `pattern`), so no error is raised and the rule loads successfully with the wrong action.

### Impact Explanation
This breaks the "deny means deny" invariant: a rule the user explicitly configured with `action: block` (e.g., to prevent a dangerous `rm -rf` execution or writes to `.env`) is loaded by `load_rules`/`load_rule_file` as `action: warn` instead, because `frontmatter.get('action', 'warn')` returns the default when the key was truncated out of the parsed dict [6](#0-5) . `hooks/pretooluse.py` (or `stop.py`) then enforces the rule as advisory-only rather than blocking, defeating the protection the hookify plugin is supposed to provide.

### Likelihood Explanation
Feasibility depends on the LLM-driven `/hookify` workflow writing an attacker-influenced, unescaped `pattern` value containing a literal `---` before the `action` line in the template order. This is plausible any time a user/PR/issue asks to create a rule matching diff markers, Markdown separators, YAML frontmatter examples, or similar `---`-containing content, especially given the command explicitly discourages escaping. It requires no privilege beyond normal repository/issue/PR content and no direct manipulation of the config file — only influence over the natural-language "behavior description" summarized into the rule pattern.

### Recommendation
Replace the substring-based `split('---', 2)` frontmatter extraction with a proper delimiter scan that only recognizes `---` on its own line (`^---\s*$`) as a boundary, and quote/escape all scalar values written by `hookify.md` (wrap `pattern` in YAML single/double quotes and escape embedded quotes/newlines) before writing the file. Additionally, after parsing, `load_rule_file` should validate that all expected keys for the declared rule are present (e.g., verify `action` matches one of `warn|block` and wasn't silently defaulted) and fail loudly rather than falling back silently, ideally by using a real YAML parser (`yaml.safe_load`) on the delimiter-bounded frontmatter text instead of the hand-rolled parser.

### Proof of Concept
Unit test in `config_loader_test.py`:
```python
def test_embedded_dashes_in_pattern_does_not_drop_action():
    content = (
        "---\n"
        "name: block-diff-markers\n"
        "enabled: true\n"
        "event: bash\n"
        "pattern: detect diff markers like ---\n"
        "+++ trailer\n"
        "action: block\n"
        "---\n\n"
        "Blocked: diff markers detected\n"
    )
    fm, msg = extract_frontmatter(content)
    rule = Rule.from_dict(fm, msg)
    # Expected: action should remain 'block' as the user intended
    assert rule.action == 'block'
```
Running this against the current implementation shows `rule.action == 'warn'` (the default), proving the `action: block` field is silently dropped and the invariant "deny means deny" is violated.
