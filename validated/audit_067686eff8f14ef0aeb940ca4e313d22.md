### Title
`ThresholdKeys::new`/`read` declares a group key without proving the supplied secret share matches its committed verification share — funds become credited yet unspendable - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to MAS performing a sensitive account change without demanding the current password, `ThresholdKeys::new` performs the sensitive act of establishing the canonical `group_key` (the identity under which the Bitcoin scanner derives deposit addresses and under which FROST signs) without ever checking that the supplied `secret_share` actually corresponds to `verification_shares[i]` — i.e., it never verifies "the current password" (`C::generator() * secret_share == verification_shares[i]`). This constructor is reachable directly from untrusted bytes via `ThresholdKeys::read`, which is explicitly a public deserialization path.

### Finding Description
In `ThresholdKeys::new`, the `group_key` is computed purely by interpolating `verification_shares` over participants `1..=t`, while `secret_share` is stored verbatim with no consistency check:

- `group_key` derivation: `crypto/dkg/src/lib.rs:376-378`
- `secret_share` stored unchecked: `crypto/dkg/src/lib.rs:380-387`
- `read` parses attacker bytes and calls `new` without a share-to-commitment check: `crypto/dkg/src/lib.rs:618-631`

Two consequences follow:

1. **Share/commitment mismatch is undetectable.** `g*secret_share == verification_shares[i]` is never asserted. A crafted byte stream sets `verification_shares` to some honest group's committed shares (yielding that group's `group_key`) while `secret_share` is an arbitrary, unrelated scalar.
2. **Only participants `1..=t` determine `group_key`.** `verification_shares[t+1..=n]` contribute nothing to `group_key`, so two encodings that disagree on all shares above index `t` produce identical group keys — the "account state" is mutated without binding to the full supplied credential.

`view()` then interpolates the unchecked `secret_share` (lines 494-498) and produces signature shares that fail `verify_share` against `verification_shares[i]` — the node holds "keys" for a group key it cannot actually sign under.

### Impact Explanation
The processor's Bitcoin `Scanner` watches script pubkeys derived from `group_key()`. If `ThresholdKeys` bytes are attacker-substituted (key material passed between DKG, storage, and reload via `read`), the wallet advertises/vends a deposit address under a group key for which no consistent secret share exists. Outputs are scanned and **reported as received, but the threshold can never produce a valid signature to spend them** — the exact "funds reported received that are not spendable" impact. This is a logic flaw in a public constructor/deserializer, not caller misuse: `new` is the single gate that defines `group_key`, and it omits the one verification that would bind the secret to it — the same omission class as skipping the current-password check before a sensitive change.

### Likelihood Explanation
Reachability requires an unprivileged party to get crafted `ThresholdKeys` bytes consumed (e.g., a tampered serialized key blob reloaded via `read`, or inconsistent verification shares propagated post-DKG). The window is narrower than a purely remote API flaw, hence Medium rather than High; but the check is cheap, the invariant is fundamental, and the failure mode silently burns deposited funds.

### Recommendation
In `ThresholdKeys::new`, assert `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Optionally also verify pairwise consistency that `group_key` equals interpolation over *all* provided shares, or at minimum document and check the 1..=t truncation explicitly.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ThresholdKeys::read:
// honest verification_shares (=> honest group_key), arbitrary secret_share.
let honest_shares: HashMap<Participant, C::G> = /* committed shares for group key K */;
let bogus = Zeroizing::new(C::F::random_nonzero_F(&mut OsRng)); // unrelated to shares[i]

let keys = ThresholdKeys::new(params, Interpolation::Lagrange, bogus, honest_shares).unwrap();
// keys.group_key() == K, scanner derives K's address, deposits credited
// keys.view(...).secret_share() is wrong => every sign_share fails verify_share
assert_eq!(keys.group_key(), K);
assert!(C::generator() * keys.original_secret_share().deref()
        != keys.original_verification_share(params.i())); // unchecked today
```
