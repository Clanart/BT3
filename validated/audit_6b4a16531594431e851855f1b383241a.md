### Title
Wallet trusts unauthenticated offer-embedded `driver_dict` → `asset_id` mapping when auto-creating asset wallets - ([File: chia/wallet/trade_manager.py])

### Summary
When a wallet accepts (or even just fully constructs) a trade `Offer`, it calls `maybe_create_wallets_for_offer`, which iterates the `asset_id` keys returned by `Offer.arbitrage()` and blindly uses the attacker/counterparty-supplied `offer.driver_dict[key]` to create a new asset wallet (CAT/NFT/etc.) for that key, without ever cross-checking that the supplied `PuzzleInfo` in `driver_dict` actually corresponds to the real puzzle reveal of the coins being exchanged for that `asset_id` in the same offer bundle.

### Finding Description
An `Offer` is a `dataclass` carrying three independently-supplied pieces of data: `requested_payments` (keyed by attacker-chosen `asset_id`), the raw `_bundle` (`WalletSpendBundle`), and `driver_dict: dict[bytes32, PuzzleInfo]` which is explicitly commented as "asset_id -> asset driver" [1](#0-0) . `Offer.__post_init__` only validates that every `asset_id` present in `requested_payments` has *some* entry in `driver_dict` — it never validates that the `PuzzleInfo` actually matches any real on-chain puzzle for that identifier [2](#0-1) .

After a trade completes, `TradeManager.respond_to_offer` calls `self.maybe_create_wallets_for_offer(complete_offer)`, which does:
```
for key in offer.arbitrage():
    ...
    exists = await wsm.get_wallet_for_puzzle_info(offer.driver_dict[key])
    if exists is None:
        await wsm.create_wallet_for_puzzle_info(offer.driver_dict[key])
``` [3](#0-2) 

This is directly analogous to the Minder bug: two independently client-supplied identifiers (`asset_id` "name" and `driver_dict` "upstream ID"/definition) are accepted from an untrusted party (the offer file/counterparty) and are trusted to correspond to each other without validating that binding against the ground truth (the actual coin puzzle reveal present in `_bundle`). Elsewhere in the codebase this mismatch is at least partially caught: for coins the *local* wallet is *offering*, `Offer._get_offered_coins()` derives `asset_id` by uncurrying the real `parent_spend.puzzle_reveal` via `match_puzzle`/`create_asset_id`, not from `driver_dict` [4](#0-3) . But `maybe_create_wallets_for_offer` performs no equivalent verification — it trusts `driver_dict[key]` as-is to auto-create/register a persistent wallet keyed to whatever `PuzzleInfo` (e.g., CAT `tail` hash, NFT ownership fields) the counterparty chose to embed in the offer, for an `asset_id` that is also counterparty-controlled.

The maker-side creation path (`_create_offer_for_ids`) does compare a *locally computed* `puzzle_driver` against a caller-supplied `driver_dict[asset_id]` and rejects mismatches unless `check_for_owner_change_in_drivers` allows the specific NFT-DID-ownership-change case [5](#0-4) , but this check only applies to the side you are *offering*/computing yourself — not to `maybe_create_wallets_for_offer`, which runs on an already-completed `Offer` object (including offers received from a remote counterparty) and unconditionally trusts the embedded `driver_dict`.

### Impact Explanation
This is a local wallet state-integrity issue, not a direct value-transfer forgery: on-chain settlement itself is still bound by `Offer.calculate_announcements`/`to_valid_spend`, which construct the actual settlement puzzle hash from `driver_dict` and require it to match real puzzle announcements enforced by consensus [6](#0-5) [7](#0-6) , so a wholesale mismatch would generally cause the completing spend to fail at the puzzle-reveal/announcement level rather than move funds incorrectly. However, `maybe_create_wallets_for_offer` runs independently of that enforcement and can create/register a wallet with an attacker-chosen `PuzzleInfo` (e.g., a forged CAT `tail` or NFT ownership descriptor) under an `asset_id` the attacker also chose, mirroring the Minder finding's core defect: the system reports a registered/tracked entity whose declared identity does not match the underlying resource, silently corrupting future coin classification, balance display, and CAT/NFT identification for that wallet (analogous to "reports as registered but will not remediate future conflicting state" in the original advisory). This is a Medium-severity coin/asset identity confusion issue rather than a fund-theft primitive, since it affects local bookkeeping and can mislead the user about what asset they hold, but does not by itself let an attacker steal already-signed funds.

### Likelihood Explanation
Reachable by any wallet user who accepts an untrusted offer file/counterparty's `Offer` via `respond_to_offer` — a routine wallet action (offer acceptance is explicitly listed as an unprivileged, user-reachable action). No special privileges are required from the counterparty beyond constructing a spend-bundle-backed offer with a crafted `driver_dict`.

### Recommendation
In `maybe_create_wallets_for_offer` (and any other consumer of `offer.driver_dict`), derive/validate the asset identity for each `asset_id` key against the actual puzzle reveal of the corresponding coins in `offer._bundle` (using `match_puzzle`/`create_asset_id`, as already done in `Offer._get_offered_coins`) before calling `create_wallet_for_puzzle_info`, rejecting or flagging any `asset_id`/`driver_dict` entries whose declared `PuzzleInfo` does not match the derived on-chain puzzle.

### Proof of Concept
Conceptual: A counterparty constructs an `Offer` where `requested_payments`/`driver_dict` declare `asset_id = X` with `PuzzleInfo{"type": "CAT", "tail": "<attacker tail>"}` unrelated to any coin actually present/settled in `_bundle` for that role. When the victim wallet calls `respond_to_offer` → `maybe_create_wallets_for_offer(complete_offer)`, it iterates `offer.arbitrage()` and unconditionally calls `wsm.create_wallet_for_puzzle_info(offer.driver_dict[key])` for `key = X`, registering a new CAT wallet under the attacker-chosen tail/identity without ever checking it against the real puzzle reveal in `_bundle`, corrupting the victim wallet's asset bookkeeping [3](#0-2) .
