### Title
CW721->ERC721 pointer's `send_nft` performs an unsafe ERC721 `transferFrom` instead of `safeTransferFrom`, permanently losing wrapped NFTs sent to non-conforming contract recipients - (File: example/cosmwasm/cw721/src/contract.rs)

### Summary
The `ERC721toCW721Pointer` CosmWasm contract (`example/cosmwasm/cw721/src/contract.rs`) exposes the CW721 `send_nft` execute message, which per the CW721 standard is supposed to be the "safe" transfer variant that guarantees the receiving contract can handle the NFT (the CW721 analogue of ERC721's `safeTransferFrom`). However, both `execute_transfer_nft` and `execute_send_nft` delegate the actual on-chain asset movement to the same helper `transfer_nft` [1](#0-0) , which builds its EVM payload via `querier.erc721_transfer_payload(...)` [2](#0-1) . That payload is generated by `HandleERC721TransferPayload`, which ABI-encodes a call to the raw, unsafe `transferFrom` method rather than `safeTransferFrom` [3](#0-2) .

### Finding Description
The reported bug class is: using ERC721 `transferFrom` instead of `safeTransferFrom` causes tokens to be permanently lost when the recipient is a contract that does not implement `onERC721Received`, since `transferFrom` performs no receiver-capability check.

In sei-chain's ERC721<->CW721 pointer flow, `send_nft` is meant to give CosmWasm callers the same safety guarantee: the CW721 spec's "send" variant exists specifically so a caller can be confident the NFT is being delivered to a contract that has explicitly agreed to receive it (mirroring EIP-721's `safeTransferFrom`). But the wrapper's implementation of `execute_send_nft` calls the same `transfer_nft` helper used by the plain, intentionally-unsafe `transfer_nft` message [4](#0-3) . That helper computes the token owner, then requests an EVM `transferFrom` payload and dispatches it as a `DelegateCallEvm` message directly against the real underlying ERC721 contract [5](#0-4) ; the receiver-capability check that `safeTransferFrom` would perform on the real ERC721 asset is never invoked.

The additional `Cw721ReceiveMsg` dispatched by `execute_send_nft` is a *separate* Cosmos-side notification message targeted at the CW721 `recipient` string (a Sei bech32 address) [6](#0-5) . It only protects the flow when the recipient resolves to an actual CosmWasm contract that fails to handle the `Receive` execute message (which reverts the whole tx). It provides no protection at all for the real, underlying ERC721 asset when the corresponding EVM address is a smart contract that can accept arbitrary `transferFrom` calls (i.e., has code, but does not implement `onERC721Received`/EIP-721 receiver semantics expected of a true `safeTransferFrom` recipient) - the DelegateCallEvm transfer already succeeded via unsafe `transferFrom` before/independent of that notification.

### Impact Explanation
Because the real ERC721 token movement always uses unsafe `transferFrom` semantics regardless of whether the CosmWasm caller used `transfer_nft` or the supposedly-safe `send_nft`, an NFT wrapped by the ERC721->CW721 pointer can be transferred by a CosmWasm-side `send_nft` call to an address whose corresponding EVM account is a contract that cannot manage arbitrary ERC721 tokens, permanently locking/losing the underlying real asset with no recovery path, defeating the entire purpose of the "safe" `send_nft` interface. This meets the Medium bar for permanent fund loss/freezing of an ERC721 asset reachable by an ordinary CosmWasm user through a single `send_nft` execute message.

### Likelihood Explanation
Likelihood is Medium: any CosmWasm caller of the ERC721->CW721 pointer using `send_nft` (the standard, "safe" CW721 execute variant) to a Sei address that resolves to a smart-contract EVM account without ERC721 receiver support will trigger this, with no special privileges required — just a normal user transaction.

### Recommendation
Have the underlying EVM payload builder used specifically for `send_nft`/the "safe" path pack a call to the real ERC721 contract's `safeTransferFrom(address,address,uint256)` (or the `bytes data` overload) rather than `transferFrom`, so the real EIP-721 receiver check is actually enforced when a CosmWasm caller requests the safe variant. Keep `transfer_nft` using unsafe `transferFrom` (matching CW721/ERC721 spec parity), but make `send_nft` genuinely safe end-to-end.

### Proof of Concept
1. Deploy an `ERC721toCW721Pointer` wrapping a real ERC721 collection (`deployErc721PointerForCw721`, per `contracts/test/ERC721toCW721PointerTest.js`) [7](#0-6) .
2. Deploy an EVM smart contract `Malicious` with no `onERC721Received` implementation, and obtain/derive its associated Sei address (`recipient`).
3. As the NFT owner, call the CW721 `send_nft` execute message on the pointer contract with `{ contract: recipient_sei_addr, token_id, msg: <arbitrary> }`.
4. `execute_send_nft` → `transfer_nft` → `erc721_transfer_payload` builds an ABI call to `transferFrom(owner, malicious_evm_addr, token_id)` and dispatches it via `DelegateCallEvm` [5](#0-4)  — the transfer succeeds unconditionally because `transferFrom` never checks `onERC721Received`.
5. The real ERC721 token is now owned by `Malicious`, which has no means of transferring it out (no ERC721/CW721 logic implemented), permanently freezing the asset — despite the caller having used the ostensibly "safe" `send_nft` interface.

fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}

func (h *EVMQueryHandler) HandleERC721TransferPayload(ctx sdk.Context, from string, recipient string, tokenId string) ([]byte, error) {
	abi, err := cw721.Cw721MetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	fromEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(from))
	if !found {
		return nil, types.NewAssociationMissingErr(from)
	}
	toEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	t, ok := sdk.NewIntFromString(tokenId)
	if !ok {
		return nil, errors.New("invalid token ID for ERC721, must be a big Int")
	}
	bz, err := abi.Pack("transferFrom", fromEvmAddr, toEvmAddr, t.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
}
