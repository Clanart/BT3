### Title
`ReceivedOutput::read` accepts an unverified offset/script pair, letting untrusted bytes declare a spendable output the group key cannot spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to CVE-2021-40352's IDOR (a client-supplied identifier selects an object without verifying ownership), `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` deserializes a caller-supplied `offset` together with a `TxOut`/`OutPoint` and never verifies the ownership invariant that `Scanner` enforces at construction: that `p2tr_script_buf(scanner_key + G * offset) == output.script_pubkey`. The `offset` is an unchecked "object reference" deciding which derived key is needed to spend the UTXO.

### Finding Description
`Scanner::scan_transaction` only produces a `ReceivedOutput` when the output's `script_pubkey` is present in `self.scripts`, i.e., when the script equals `p2tr_script_buf(key + G*offset)` for a registered offset (`mod.rs:199-214`, `register_offset` at `mod.rs:180-196`). `ReceivedOutput::read` (`mod.rs:122-134`), by contrast, reads `Secp256k1::read_F` for the offset and consensus-decodes the `TxOut`/`OutPoint` with no consistency check. The offset is then consumed downstream as the spend key delta: `Output::key()` computes `script_key - G*offset` (`processor` usage pattern; within the crate, `SignableTransaction` stores per-input `offsets: Vec<Scalar>` in `send.rs:56` and each input's signing machine is instantiated with `keys.offset(offset)`-style re-keying via the `Schnorr` algorithm machines in `TransactionSignMachine`, `send.rs:321-398`).

An attacker who can feed bytes to `ReceivedOutput::read` (the prompt's reachable-input list) can pair a real, confirmed UTXO paying to `K + G*o'` with a mismatched offset `o ≠ o'`, or pair a foreign P2TR output with offset `0`. The wallet then reports the output as received with an offset that does not correspond to the actual locking script.

### Impact Explanation
Two concrete harms follow from the mismatched (offset, script) pair:
- **Funds reported received that are not spendable**: a deposit genuinely paying `K + G*o'` is reported with offset `o`; the signing path re-keys to `K + G*o`, producing a signature invalid for the actual UTXO. The output can never be spent by the multisig despite being counted as received balance.
- **Signature misattribution / wasted signing rounds**: for a foreign UTXO claimed with an arbitrary offset, the group signs a spend bound to the wrong tweaked key; the transaction is invalid once broadcast.

This maps the IDOR class: the serialized `offset` acts as a reference selecting "which of the multisig's keys owns this object," and no authorization/consistency check binds it to the referenced output.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s transit an untrusted boundary (the class of inputs explicitly in scope). Exploitation requires no secrets: the attacker chooses the serialized triple `(offset, TxOut, OutPoint)` freely, and `read_F`/`consensus_decode` accept any canonical values. Severity is bounded because a totally foreign `(script, offset)` pair produces `Output::key() != group_key`, which honest scanner-driven flows would reject — the damaging case is corrupting the offset of an output the attacker caused to exist, which they can always do. Medium severity.

### Recommendation
In `ReceivedOutput::read`, or at the point of use, verify the spendability invariant: reconstruct the expected script from the claimed base key and offset (`p2tr_script_buf(key + G*offset)`) and reject inputs where it does not equal `output.script_pubkey`. Since `ReceivedOutput` does not carry the base key, either add the key to the serialized form or perform the check in a fallible constructor that takes `Scanner`/the base key, e.g. `Scanner::verify_received(output)`.

### Proof of Concept
```rust
// networks/bitcoin context. K = even group key, registered offset o' used for a deposit.
let real_offset = scanner.register_offset(o_prime).unwrap();          // o'
let deposit = TxOut {
  value: Amount::from_sat(50_000),
  script_pubkey: p2tr_script_buf(group_key + G * real_offset).unwrap(),
};
// Attacker-crafted serialization: same UTXO, wrong offset
let mut buf = vec![];
buf.extend((real_offset + Scalar::ONE).to_bytes());                   // wrong offset
buf.extend(serialize(&deposit));
buf.extend(serialize(&OutPoint::new(real_txid, 0)));
let claimed = ReceivedOutput::read(&mut buf.as_slice()).unwrap();     // accepted
// claimed.offset() != the offset that spends `deposit`;
// signing re-keys to group_key + G*(o'+1): invalid spend, funds stuck.
```
Root cause confirmed at `networks/bitcoin/src/wallet/mod.rs:122-134` (no offset↔script binding) versus the invariant guaranteed by `scan_transaction`/`register_offset` at `mod.rs:180-214`.
