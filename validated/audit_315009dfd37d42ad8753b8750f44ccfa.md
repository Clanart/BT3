### Title
Fee and weight are calculated on a transaction that omits the OP_RETURN output, so the produced TX pays a lower fee rate than requested and can pass checks it should fail - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` argument that appends an OP_RETURN output to the transaction (send.rs:194-202). However, the fee/weight estimation helper `calculate_weight_vbytes` is invoked with `payments` — the output list *before* the OP_RETURN output is added — both for the initial fee estimate (send.rs:204) and for the change-including estimate (send.rs:225-226). The transaction that is actually built and signed includes the extra output (send.rs:246-251), so every derived value (`needed_fee`, the `TooLowFee` check, the `NotEnoughFunds` check, the `MAX_STANDARD_TX_WEIGHT` check, and the change amount) is computed against a smaller, idealized transaction than the real one — the same "estimate uses an assumed state while execution uses actual state" class as the dTRINITY leverage mismatch.

### Finding Description
- `calculate_weight_vbytes(inputs, payments, change)` builds a template transaction whose `output` list is constructed solely from `payments` plus an optional change output (send.rs:85-99).
- In `new`, the OP_RETURN output is pushed onto `tx_outs` at lines 194-202, but `calculate_weight_vbytes` is then called with `payments`, not `tx_outs` (line 204), and again at lines 225-226 for the change case.
- Consequences:
  - `needed_fee = fee_per_vbyte * vbytes` (line 206) is under-charged by `fee_per_vbyte * vbytes_of_op_return_output` (up to ~91 vbytes for the allowed 80-byte payload).
  - The minimum-relay check at line 211 uses the underestimated `vbytes`, so a transaction can pass `TooLowFee` while its *actual* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` once the OP_RETURN weight is included — the analog of the dTRINITY check failing on an incorrect expected value.
  - The change-value computation at lines 228-230 subtracts `fee_with_change` (also underestimated), so the change output is slightly overvalued; `fee()` (lines 138-141) still equals `needed_fee`, but the *effective* fee rate of the broadcast transaction is below `fee_per_vbyte`.
  - The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` that excludes the OP_RETURN output, so a TX that actually exceeds standard weight can be produced and signed.

### Impact Explanation
- With a low `fee_per_vbyte` (e.g., 1 sat/vb) and a large `data` payload, the real transaction's fee rate can drop below the 1 sat/vb relay minimum, making the signed transaction unrelayable — funds committed to `prevouts` cannot be moved by this transaction even though construction succeeded. Since signature generation is deterministic over `self.tx`, re-signing reproduces the same invalid/under-fee'd transaction.
- Near the weight boundary, the produced transaction can exceed `MAX_STANDARD_TX_WEIGHT`, again yielding a non-standard, unrelayable spend.
- In the ordinary case the only effect is a fee rate marginally below the caller's requested rate plus an oversized change output — i.e., accounting incorrectness rather than theft, consistent with a Medium-severity miscalculation.

### Likelihood Explanation
- `data` is attacker/user-supplied input to a public constructor in the in-scope `wallet/` code; the miscalculation triggers whenever `data.is_some()` and is deterministic, not probabilistic.
- Within Serai's own processor (`processor/src/networks/bitcoin.rs:446-451`) `data` is hardcoded `None`, so the currently deployed path never exercises it; the bug affects any caller that passes OP_RETURN data, which the API explicitly supports (doc comment line 149, `TooMuchData` limit at lines 171-173).

### Recommendation
Pass the actual output list (including the OP_RETURN output) into `calculate_weight_vbytes`, or add a `data`/extra-output parameter so the template transaction mirrors the final one. E.g., compute weight/fee from `tx_outs` (with change appended before the estimate, or an `extra_outputs: &[TxOut]` argument), and recompute `weight` from the true output set before the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept
Construct via the public API:

```rust
// inputs: any ReceivedOutput(s) with input_sat covering payments + fee
// payments: [(p2tr_script, 10_000)]
// data: Some(vec![0xAA; 80])   // max allowed
// fee_per_vbyte: 1
let st = SignableTransaction::new(inputs, &payments, None, Some(vec![0xAA; 80]), 1).unwrap();
// st.needed_fee() was computed from a TX *without* the OP_RETURN output.
// st.transaction().vsize() > the vbytes used at line 204 by ~91 vbytes.
// Effective fee rate = needed_fee / actual_vsize < 1 sat/vb -> below
// DEFAULT_MIN_RELAY_TX_FEE once actual vsize is counted => unrelayable,
// while the line-211 TooLowFee check still passed.
```

The divergence is directly observable: `st.transaction().vsize() as u64 * fee_per_vbyte > st.needed_fee()` whenever `data.is_some()`.
