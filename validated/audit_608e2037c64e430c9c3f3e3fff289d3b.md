### Title
Ed448 point decoding never performs its torsion check — `is_torsion_free` is a tautology, so non-prime-subgroup (torsion) points are accepted by `read_G` - (crypto/ed448/src/point.rs)

### Summary
`Point::is_torsion_free` in `crypto/ed448/src/point.rs` computes `(*self * (Scalar::ZERO - Scalar::ONE)) + self`, which is `self*(-1) + self` — identically the identity for *every* point. The torsion-free check used by `GroupEncoding::from_bytes` therefore always passes, and `Ed448`'s `Ciphersuite::read_G` / `Curve::read_G` accept points with non-trivial torsion components (Ed448 has cofactor 4), despite the code's explicit intent to reject them and the `PrimeGroup` bound required by `Ciphersuite`. The canonical-re-encode check in `Ciphersuite::read_G` does not catch this, because a torsioned point re-encodes to the same bytes.

### Finding Description
In `crypto/ed448/src/point.rs` (lines ~294-317):

```rust
impl Point {
  fn is_torsion_free(&self) -> Choice {
    ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
  }
}
```

`Scalar::ZERO - Scalar::ONE` is `-1`. `self * (-1) + self` is the group identity unconditionally, so `is_torsion_free()` is `Choice(1)` for all inputs — including the 2- and 4-torsion points on Ed448. `from_bytes` then accepts them:

```rust
CtOption::new(point, not_negative_zero & point.is_torsion_free())
```

All in-scope consumers are affected:

- `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) validates point validity and canonical byte encoding, but relies on `from_bytes` for subgroup membership. For Ed448 it silently accepts torsioned points; `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) additionally rejects only the identity, so a non-identity low-order point (e.g., a point of order 4) passes both layers.
- This reaches `SchnorrSignature::read`, `DLEqProof::read`, `Commitments::read` (PedPoP), `EncryptedMessage::read`, `Commitments::read`/`read_preprocess` (FROST nonce commitments), `ThresholdKeys::read` (verification shares), and `GeneratorProof::read` — every deserialization path fed by untrusted peer bytes for the Ed448 ciphersuite.

The encoding hint in the external report maps directly: this is an improper-input-decoding bug, where bytes that should fail validation are accepted as a canonical, prime-order group element.

### Impact Explanation
Every protocol built on the Ed448 ciphersuite assumes scalars act on the prime-order subgroup (order `l`, cofactor 4). With torsion points admitted:

- **FROST (Ed448):** A malicious participant submits a nonce commitment `E_i = e_i*G + T` with `T` of order 4 in its preprocess (`Commitments::read` via `read_preprocess`, `crypto/frost/src/nonce.rs:34-36`). `BindingFactor::bound` computes `D + rho*E`, which is `D + rho*e*G + (rho mod 4)*T` — an attacker-controlled torsion component enters the aggregate nonce `R`. The resulting signature fails verification, and because honest shares verify correctly while the malicious preprocess was *accepted* at decode time, the attack forces the session into the failure/blame path on demand. The attacker can also tune the torsion across multiple commitment points to cancel, producing a valid signature whose transcript-encoding invariant (all points in the prime subgroup) is violated.
- **PedPoP/DKG:** Commitments and encrypted-message key points (`crypto/dkg/pedpop/src/lib.rs:110-128`, `encryption.rs`) admit torsioned `Am`/ECDH public keys. Share-verification equalities are linear in scalar multiplication, so injected torsion desynchronizes per-recipient verification in ways the caller cannot attribute to a bad encoding — the bytes were "canonical" per `read_G`.
- **Schnorr/DLEq:** `SchnorrSignature::read` and `DLEqProof::read` accept torsioned `R`/proof points, breaking the documented contract that verified statements live in the prime-order group (the doc comment in `crypto/schnorr/src/lib.rs:39-41` explicitly disclaims the cofactor-handling verification formula, relying on strict decoding that Ed448 fails to deliver).

This is an incorrect decoding/verifier-input validation reachable purely from peer-supplied bytes — no collusion, no malicious node, no integrator misuse.

### Likelihood Explanation
Any unprivileged counterparty in an Ed448 DKG/FROST session, or any party whose signature/proof bytes are fed to `SchnorrSignature::read`/`DLEqProof::read`/`Commitments::read`, can include a torsion component by encoding `P + T` (both `P` and the result have canonical encodings). It requires no special position and is deterministic. Full key-extraction forgery is not obtainable from torsion alone (the verification equations are exact over the full curve), which caps the severity at Medium: the guaranteed effects are acceptance of invalid points, controllable session failure, and violation of the prime-subgroup assumption the surrounding verification math is built on.

### Recommendation
Replace the tautological check with a real subgroup-membership test. For Ed448 (order `l`, cofactor 4), `is_torsion_free` should multiply by the prime order: `(*self * Scalar::MODULUS_as_scalar_equiv)` — i.e., test `self * l == identity` (equivalently, multiply by the cofactor and reject the identity component), not `self*(-1) + self`. Concretely, in `crypto/ed448/src/point.rs`:

```rust
fn is_torsion_free(&self) -> Choice {
  (*self * Scalar(MODULUS_residue)).is_identity()  // self * l == 0
}
```

so that `from_bytes` rejects any point with a non-zero component in the 4-torsion subgroup. Add a regression test that `Ed448::read_G` rejects encodings of `P + T` for each generator `T` of the torsion subgroup.

### Proof of Concept
```rust
use minimal_ed448::{Point, Scalar}; // crypto/ed448
use ciphersuite::{group::GroupEncoding, Ciphersuite};
use frost::curve::{Curve, Ed448};

// T: a non-identity point of order 4 on edwards448 (e.g., (x, y) with y^2 = 1 branch),
// or obtained as cofactor-cleared preimage: T = (h/4-torsion generator).
// Any point P on the curve, let P' = P + T where T has order 4.

#[test]
fn torsion_point_accepted() {
  // Construct a torsioned encoding: take a valid encoding of P and add a 4-torsion point.
  // Since is_torsion_free() == self*(-1) + self == identity for ALL points,
  // CtOption::new(point, not_negative_zero & point.is_torsion_free()) always yields Some.
  let torsioned_bytes: [u8; 57] = /* canonical encoding of P + T */;
  let p = Point::from_bytes(&torsioned_bytes.into());
  assert!(bool::from(p.is_some())); // BUG: accepted despite non-trivial torsion

  // Also passes the full read_G stack used by SchnorrSignature::read, Commitments::read, etc.
  assert!(<Ed448 as Ciphersuite>::read_G(&mut torsioned_bytes.as_ref()).is_ok());
  // And Curve::read_G, since the torsioned point is non-identity.
  assert!(<Ed448 as Curve>::read_G(&mut torsioned_bytes.as_ref()).is_ok());
}
```

Root cause is provable without running code: `is_torsion_free` at `crypto/ed448/src/point.rs:295-297` evaluates `(*self * (Scalar::ZERO - Scalar::ONE)) + self` = `-self + self` = `identity` for every `self`, so the `CtOption` guard in `from_bytes` (line ~316) can never reject a torsioned point. Compare with the rejection logic that does work — `not_negative_zero` — and with `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131`, which adds only an identity check on top of the same broken `from_bytes`.
