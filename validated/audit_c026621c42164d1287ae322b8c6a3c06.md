### Title
Source-side IBC callbacks (`onPacketAcknowledgement`/`onPacketTimeout`) are invoked with `msg.sender` set to the packet sender's own address, allowing the sender to directly forge callback invocations - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
This is the closest reachable analog to the `ValkyrieHooklet` bug: a hook function meant to be restricted to a specific privileged caller (the hook-dispatching module) that in practice cannot be authenticated by the receiving contract, because the framework invokes it using an identity (`msg.sender`) that the untrusted party fully controls. In Cosmos EVM's `x/ibc/callbacks` module, `ContractKeeper.IBCOnAcknowledgementPacketCallback` and `ContractKeeper.IBCOnTimeoutPacketCallback` call the contract's `onPacketAcknowledgement`/`onPacketTimeout` entrypoints using the original IBC packet sender's own EVM address as the caller, rather than a distinguishable system/module address.

### Finding Description
The `ICallbacks` interface documents that contracts implementing `onPacketAcknowledgement` and `onPacketTimeout` "must ensure that only the IBC module can invoke these callback methods" [1](#0-0) , mirroring the exact pattern in the external report where a hooklet function is supposed to be restricted to a specific authorized caller.

However, when the keeper actually dispatches these callbacks, it uses the packet sender's own address as the EVM call's caller: [2](#0-1) 

and similarly for the timeout path: [3](#0-2) 

`sender` in both cases is derived directly from `packetSenderAddress`, i.e. the account that originally sent the IBC transfer/packet — an address whose private key is controlled by an ordinary, unprivileged user (unlike the destination-side receive callback, which safely uses a `GenerateIsolatedAddress`-derived address that has no associated private key, per `x/ibc/callbacks/keeper/keeper.go:139-155`). Because `msg.sender` observed by the target contract during a genuine callback invocation is identical to `msg.sender` when that same user directly calls the contract's `onPacketAcknowledgement`/`onPacketTimeout` function via an ordinary EVM transaction, there is no protocol-level way for the implementing contract to distinguish a real IBC callback from a self-forged call — exactly analogous to `ValkyrieHooklet::afterSwap` applying `onlyBunniHub` while being invoked from `BunniHook`, where the wrong entity is used to authorize a privileged code path.

The documented intended use case is explicit: "The cross-chain swaps implementation sends an IBC transfer. If the transfer were to fail, the sender should be able to retrieve their funds ... In order to do either, the contract must receive the acknowledgement and timeout callback" [4](#0-3) . This confirms these callbacks are expected to gate value-affecting logic (refunds/retries) based on packet outcome, yet the framework provides no reliable caller-based authentication for that logic.

### Impact Explanation
Any contract built following the documented pattern (e.g., a cross-chain swap/refund contract that releases or re-sends funds upon `onPacketTimeout`, or advances internal accounting upon `onPacketAcknowledgement`) can have its callback entrypoint invoked directly by the original packet sender with arbitrary/fabricated `channelId`, `portId`, `sequence`, `data`, and `acknowledgement` values, since `msg.sender` cannot differentiate genuine keeper-driven invocation from a spoofed direct call. This can trigger unauthorized release, duplication, or double-refund of contract-held/escrowed value tied to an IBC transfer that never actually failed or was never actually sent, matching the "Critical unauthorized ... duplication ... or irreversible accounting corruption of spendable user value" and "permanent freezing/theft/unauthorized extraction of user funds ... escrowed assets" impact classes.

### Likelihood Explanation
Exploitability depends entirely on the implementing contract's business logic (whether it trusts `msg.sender`/packet fields without additional binding to an actually-completed packet), so this is a framework-level gap rather than a guaranteed bug in every deployed contract. The `CounterWithCallbacks.sol` test/example contract implements `onPacketAcknowledgement`/`onPacketTimeout` with zero caller restriction [5](#0-4) , illustrating that the reference implementation shipped with the framework does not enforce the access control the README says is required, and gives contract authors no supported mechanism to actually enforce it (there's no module/system address exposed for an `onlyCallbacksModule`-style check). I was not able to fully verify `x/vm/keeper/call_evm.go`'s exact `msg.sender`/`tx.origin` semantics for `CallEVM` in this pass, so I cannot 100% confirm there is no other origin-distinguishing signal (e.g., a synthetic "is-internal-call" flag) available to contracts; this should be verified before treating the finding as fully confirmed.

### Recommendation
Use a distinguishable, non-user-controlled caller identity for the source-side callback dispatch (e.g., a dedicated module/precompile address, similar to the isolated-address pattern already used safely in `IBCReceivePacketCallback`), and update `ICallbacks`/README guidance to document a supported mechanism contracts can use to authenticate genuine `x/ibc/callbacks` invocations distinctly from ordinary user calls.

### Proof of Concept
1. User A sends an IBC transfer with a `src_callback` memo pointing to their own deployed contract `C`, which implements `onPacketTimeout` to refund/re-release tokens back to A when a timeout occurs.
2. Before any real timeout occurs (or even if the packet eventually succeeds), User A submits a normal EVM transaction directly to `C.onPacketTimeout(channelId, portId, sequence, data)` with `data` matching the original packet's encoded token/amount fields.
3. Since `msg.sender` observed by `C` equals A's own address in both the genuine-callback path (`x/ibc/callbacks/keeper/keeper.go:409-425`) and this direct call, `C` cannot detect the forgery and executes the refund logic, releasing funds that were never actually timed out — enabling duplicated extraction of value from `C`.

    function onPacketAcknowledgement(
        string memory channelId,
        string memory portId,
        uint64 sequence,
        bytes memory data,
        bytes memory acknowledgement
    ) external override {
        // Emit event when packet is acknowledged
        emit PacketAcknowledged(channelId, portId, sequence, data, acknowledgement);

        counter += 1; // Increment counter on acknowledgement
    }

    /**
     * @dev Implementation of ICallbacks interface
     * Called when a packet times out
     */
    function onPacketTimeout(
        string memory channelId,
        string memory portId,
        uint64 sequence,
        bytes memory data
    ) external override {
        // Emit event when packet times out
        emit PacketTimedOut(channelId, portId, sequence, data);
        counter -= 1; // Decrement counter on timeout
    }
