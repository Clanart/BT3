### Title
Disabled overfill clamp in Simplex FX filler strategy allows a manipulated/stale venue price to drain solver funds via `fillOrder` - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The `HyperFX` filler strategy computes a per-leg output cap (`overfillCeiling = output.amount * (10000n + maxOverfillBps) / 10000n`) intended to bound how much the filler will ever pay out relative to what the user actually requested. The code that would enforce this bound has been removed: the ceiling is only used to emit a warning log, and the filler proceeds to send `rawPolicyMaxOutput` (the unclamped amount) to the beneficiary regardless of how far it exceeds the ceiling.

### Finding Description
In `sdk/packages/simplex/src/strategies/fx.ts` (lines ~591-617), the leg-pricing loop computes `rawPolicyMaxOutput` from `computeLegPolicyOutput`, which for venue-priced pairs (e.g. Uniswap V4, `priceSource: "venue"`) derives its rate from on-chain pool state read at fill time via `venuePriceMemo()`/`resolveLegRates`. The code explicitly states: [1](#0-0) 

`policyMaxOutput` is assigned directly from `rawPolicyMaxOutput` with no `Math.min`/clamp against `overfillCeiling`; only a `logger.warn` fires when the ceiling is exceeded: [2](#0-1) 

This value then flows directly into the amount transferred to the order beneficiary in `fillOrder` on the destination chain, and into the escrow released to the solver on the source chain via the intent gateway's `withdraw()`/`RedeemEscrow` settlement path described in the Intent Gateway docs. There is no independent, protocol-side check on the destination or source chain that a solver's output amount stays within any expected bound relative to the user's requested amount — the intent gateway only requires `solverAmount >= order.output.assets[i].amount` (see `IntrinsicIntents.sol` fill logic), it never rejects an *excessive* fill. The only guard against over-payment (the `maxOverfillBps` ceiling) exists purely client-side in the solver's own strategy code, and that guard has been intentionally disabled ("clamp is DISABLED").

Because the venue price used to compute `rawPolicyMaxOutput` is read live from an AMM pool (Uniswap V4) immediately before filling, an attacker who can move that pool's price momentarily (flash/sandwich manipulation, or exploiting a stale/misreporting oracle path) can inflate `rawPolicyMaxOutput` far above the amount the user actually requested and far above the amount the solver will recoup from the released escrow on settlement. The filler will pay the inflated `beneficiaryTotal` out of its own wallet/vault funds while only receiving the fixed, user-defined `order.inputs[i].amount` in escrow — a direct, exploitable value mismatch between what the solver pays out and what it's compensated with.

### Impact Explanation
This is a fund-loss vector matching the bounty's "logic attacks" and "stealing or loss of funds" categories: an unprivileged party who can influence a venue's spot price (e.g., via a sandwich/flash-manipulation of the priced Uniswap V4 pool right before an order is filled) can cause the filler/solver to transfer far more value to the order beneficiary than the escrowed input compensates, resulting in the filler paying out attacker-controlled excess value that is not recovered from the fixed escrow amount collected via `RedeemEscrow`/`withdraw()`. The docs' own design rationale (`docs/content/developers/evm/intent-gateway/simplex.mdx`, "Overfill Protection" section) confirms this is exactly the attack class the (now-disabled) clamp was built to prevent: "Bounds per-leg loss if the filler's internal pricing is wrong (bug, stale cache, manipulated venue)."

### Likelihood Explanation
The bug is not a hypothetical/config edge case — it is unconditional: the clamp code path was structurally removed and replaced with a warn-only telemetry branch, so every fill using a venue-priced leg is exposed whenever `rawPolicyMaxOutput` exceeds the ceiling, which happens precisely when the venue price is manipulated or stale. No malicious relayer, prover, or governance actor is required — only the ability to move price on the underlying venue pool (a standard, permissionless DeFi action) or otherwise cause the filler's price computation to run stale, both of which are attacker-reachable without any privileged role.

### Recommendation
Re-enable enforcement of `overfillCeiling`: clamp `policyMaxOutput` to `min(rawPolicyMaxOutput, overfillCeiling)` before assembling `fillerOutputs`, restoring the original loss bound, and keep the `maxConsecutiveClamps` halt logic as a secondary circuit breaker for repeated clamp events. If the clamp was disabled intentionally for a documented business reason, the on-chain gateway should independently be hardened to reject overfills above a governance-set bound so the safety property does not depend solely on off-chain solver code.

### Proof of Concept
1. Attacker identifies a `HyperFX` filler configured with a Uniswap V4-priced trading pair (`[vault.uniswapV4]` funding/pricing source, no `bidPricePolicy`/`askPricePolicy`).
2. Attacker submits or waits for an intent-gateway `Order` whose output leg matches that pair.
3. Immediately before/around the filler's `fillOrder` call, attacker manipulates the V4 pool's spot price (e.g., via a large swap) so that `venuePriceMemo()` returns a distorted rate.
4. `resolveLegRates` → `computeLegPolicyOutput` computes `rawPolicyMaxOutput` far above `overfillCeiling = output.amount * 1.05` (default `maxOverfillBps = 500`).
5. Because the clamp is disabled (`policyMaxOutput = rawPolicyMaxOutput`), the filler calls `fillOrder` and pays the inflated amount to `order.output.beneficiary`.
6. On settlement, the filler/solver only receives `order.inputs[i].amount` worth of escrow via `RedeemEscrow`/`withdraw()` — fixed by the original (unmanipulated) order — realizing a net loss equal to the attacker-induced excess payment.

Note: I was unable to fully verify from the index whether `maxConsecutiveClamps` halting logic is also fully inert (the halt code references `overfillCeiling`/clamp state that appears tied to the same disabled path); a Devin session with full file access would be needed to confirm the halt mechanism's current behavior end-to-end.
