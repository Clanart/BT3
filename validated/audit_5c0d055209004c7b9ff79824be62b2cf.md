## Analysis

The Sherlock H-9 issue is a classic **unbounded-loop-over-user-growable-set** DoS: an attacker cheaply inflates an array/set that a *later, unrelated* privileged/critical operation must fully iterate in a single transaction, eventually exceeding the (block) gas limit and permanently bricking that operation.

Searching Cosmos EVM for the same pattern (attacker-growable KV set + later mandatory full iteration in one tx) surfaces `x/erc20`'s allowance deletion path, triggered from `ConvertERC20`.

- [1](#0-0)  — any address can create an `Allowance` entry for `(erc20, owner, spender)` for **any** enabled native-ERC20 token pair, cheaply and unboundedly (any owner × any spender combination is a distinct KV entry).
- [2](#0-1)  — `deleteAllowances` performs an unbounded `KVStorePrefixIterator` scan over *all* allowances keyed by the ERC20 address, collects every key, then deletes them all inside a single call.
- [3](#0-2)  — `ConvertERC20` (an unprivileged, user-callable `Msg`) automatically calls `k.DeleteTokenPair(ctx, pair)` whenever the underlying native ERC20 contract has self-destructed (`!acc.HasCodeHash()`).
- [4](#0-3)  — `DeleteTokenPair` unconditionally calls `k.deleteAllowances(ctx, tokenPair.GetERC20Contract())`.

### Title
Unbounded allowance-store iteration in `DeleteTokenPair`/`deleteAllowances` triggerable via `ConvertERC20` can permanently brick conversion for a native ERC20 token pair - (File: `x/erc20/keeper/allowance.go`)

### Summary
`ConvertERC20` is an unprivileged message that, when the underlying native ERC20 contract has self-destructed, invokes `DeleteTokenPair`, which in turn calls `deleteAllowances`. That function iterates and deletes **every** `Allowance` entry ever created for that ERC20 address, with no bound. Since any account can create ERC20-precompile allowances for arbitrary `(owner, spender)` pairs at near-zero cost via `Approve`, an attacker can inflate this set to a size that makes the mandatory cleanup step in `DeleteTokenPair` exceed the transaction/block gas limit — this exactly mirrors the ProtectionPool `lockCapital`/`_accruePremiumAndExpireProtections` unbounded-loop bug class.

### Finding Description
1. Any user can call the ERC20 precompile `Approve` method for a registered, enabled native-ERC20 token pair from many distinct EOAs/contracts, each creating one `Allowance` KV entry under prefix `erc20.Bytes()` [5](#0-4) .
2. This is cheap and effectively unbounded — the store has no cap on the number of `(owner, spender)` combinations per token.
3. If the attacker also self-destructs (or otherwise removes code from) the underlying native ERC20 contract, any subsequent call to `ConvertERC20` for that denom takes the "selfdestructed" branch and calls `DeleteTokenPair` [3](#0-2) .
4. `DeleteTokenPair` unconditionally calls `deleteAllowances`, which does a full prefix-iterator scan collecting **all** matching keys before deleting them [2](#0-1) .
5. With enough pre-seeded allowances, the gas consumed by this single deletion loop (metered under the normal KV gas config, since this codepath is not zero-gas like the IBC callback path) exceeds the calling transaction's gas limit, causing `ConvertERC20` — and therefore `DeleteTokenPair` — to permanently fail with out-of-gas on every future attempt for that token pair.

### Impact Explanation
Once triggered, no account can successfully call `ConvertERC20` for the affected native-ERC20 token pair, because the mandatory cleanup step always reverts. Any user balances still denominated in that native ERC20's associated bank coin (or vice versa) become permanently unconvertible — this is a **permanent freezing/locking of user funds** for that token pair, matching the "Critical permanent freezing, locking… of user funds" impact class, since there is no other codepath to remove or bypass the stuck token pair/allowance state.

### Likelihood Explanation
The precondition (self-destructing/losing code on the native ERC20 contract) requires the attacker to control or influence a native-ERC20 token pair's underlying contract, which is plausible for `OWNER_EXTERNAL` token pairs (arbitrary externally-deployed ERC20 contracts can be registered). Inflating the allowance count is fully permissionless and low-cost. This makes the attack feasible for any token pair backed by an attacker-controlled or attacker-deployable contract.

### Recommendation
- Bound or paginate the allowance cleanup in `deleteAllowances`, e.g. process it incrementally across multiple blocks/messages instead of a single atomic loop, or cap the number of allowances processed per call.
- Alternatively, avoid a synchronous mass-delete on `DeleteTokenPair`; instead mark the token pair as deleted and lazily/no-op-check stale allowances on read, removing the need for an unbounded loop in a single transaction.
- Consider using a zero-gas-config context for this cleanup (as is done for the IBC callback path) *in combination with* an iteration cap, since zero gas alone does not prevent computational/time-based DoS.

### Proof of Concept
1. Register a native ERC20 token pair for `MaliciousERC20` (an externally deployed, `OWNER_EXTERNAL` contract implementing `SELFDESTRUCT`).
2. From N distinct accounts, call the ERC20 precompile's `approve(spenderX, amount)` against `MaliciousERC20`'s ERC20 address, incrementing N until the resulting `deleteAllowances` prefix-scan/delete would exceed a typical block gas limit (this is purely a function of KV iteration + deletion gas cost, controllable by the attacker's tx count).
3. Self-destruct `MaliciousERC20`'s bytecode.
4. Call `MsgConvertERC20` for this contract's denom; observe that the message enters the `!acc.HasCodeHash()` branch, calls `DeleteTokenPair` → `deleteAllowances`, and runs out of gas before finishing the deletion loop, causing the transaction (and every future attempt) to fail, permanently blocking conversion for that token pair.

*(Note: I was unable to execute this locally to confirm exact gas thresholds/whether the surrounding context uses a zero-gas config in this specific call path; this should be verified in a live/dev environment, as it directly determines the number of allowances needed to trigger the DoS.)*

func (k Keeper) setAllowance(
	ctx sdk.Context,
	erc20 common.Address,
	owner common.Address,
	spender common.Address,
	value *big.Int,
	allowDisabledTokenPair bool,
) error {
	// validate existence of token pair
	tokenPairID := k.GetERC20Map(ctx, erc20)
	tokenPair, found := k.GetTokenPair(ctx, tokenPairID)
	if !found {
		return errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token pair for address '%s' not registered", erc20,
		)
	}
	if !allowDisabledTokenPair && !tokenPair.Enabled {
		return errorsmod.Wrapf(
			types.ErrERC20TokenPairDisabled, "token pair for address '%s' is disabled", erc20,
		)
	}

	// validate addresses
	if (owner == common.Address{}) {
		return errorsmod.Wrapf(errortypes.ErrInvalidAddress, "owner address is empty")
	}
	if (spender == common.Address{}) {
		return errorsmod.Wrapf(errortypes.ErrInvalidAddress, "spender address is empty")
	}

	// validate value
	if value == nil {
		return errorsmod.Wrapf(types.ErrInvalidAllowance, "value is nil")
	}
	if value.Sign() < 0 {
		return errorsmod.Wrapf(types.ErrInvalidAllowance, "value '%s' is less than zero", value)
	}
	if value.BitLen() > 256 {
		return errorsmod.Wrapf(types.ErrInvalidAllowance, "value '%s' is greater than max value of uint256", value)
	}

	// store or delete allowance
	store := prefix.NewStore(ctx.KVStore(k.storeKey), types.KeyPrefixAllowance)
	allowanceKey := types.AllowanceKey(erc20, owner, spender)

	if value.Sign() == 0 {
		store.Delete(allowanceKey)
	} else {
		allowance := types.NewAllowance(erc20, owner, spender, value)
		bz := k.cdc.MustMarshal(&allowance)
		store.Set(allowanceKey, bz)
	}

	return nil
}

func (k Keeper) deleteAllowances(ctx sdk.Context, erc20 common.Address) {
	store := prefix.NewStore(ctx.KVStore(k.storeKey), types.KeyPrefixAllowance)
	iterator := storetypes.KVStorePrefixIterator(store, erc20.Bytes())
	defer iterator.Close()

	var keys [][]byte

	for ; iterator.Valid(); iterator.Next() {
		keys = append(keys, iterator.Key())
	}

	for _, key := range keys {
		store.Delete(key)
	}
