### Title
ReceivedOutput does not bind claimed TxOut metadata to its outpoint - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an offset, `TxOut`, and `OutPoint` as independent untrusted fields, but later transaction construction trusts the claimed `TxOut` as the prevout while spending the claimed outpoint. The signing setup validates only that the `TxOut`’s `script_pubkey` corresponds to the tweaked threshold key; it does not validate that the `TxOut` is the actual output referenced by the `OutPoint`. This is analogous to authenticating an object by one identifier while leaving a second identifier unvalidated.

### Finding Description
`ReceivedOutput::read` deserializes three attacker-controlled components: `offset`, `output`, and `outpoint`, then returns them without consistency checks beyond decoding. [1](#0-0)  `SignableTransaction::new` separately copies the claimed value into `prevouts` and the claimed outpoint into the transaction input. [2](#0-1) [3](#0-2) 

When converting the transaction into a multisig machine, `SignableTransaction::multisig` checks only that `offset.group_key()` produces the claimed prevout’s `script_pubkey`. [4](#0-3)  It does not—and locally cannot—confirm that the outpoint actually resolves to that prevout on-chain. The resulting FROST signature then commits to both the transaction inputs and `Prevouts::All`, meaning the mismatched metadata is incorporated into the signed Taproot sighash. [5](#0-4) 

### Impact Explanation
An unprivileged party who can provide serialized `ReceivedOutput` data can cause signers to authorize a transaction whose input points to one UTXO while its Taproot prevout commitment describes another output. If the claimed `TxOut` carries the scanner-controlled script but an incorrect amount or corresponds to a different output, the completed transaction will fail Bitcoin’s Taproot prevout validation. The signed transaction is therefore unbroadcastable/unspendable, potentially causing funds expected to be spent or accounted for to remain unavailable.

The concrete security consequence is signing of an unintended transaction message and reporting an output as usable when its outpoint metadata is not actually bound to the claimed output. This matches the bug class where object identity is partially validated but a second required tracking field is trusted independently.

### Likelihood Explanation
The issue is reachable whenever untrusted serialized `ReceivedOutput` values are accepted through `ReceivedOutput::read` and then passed to `SignableTransaction::new`. The attacker needs a victim-associated script or another script accepted by the application, plus an arbitrary outpoint/value pairing; they do not need validator privileges or threshold-secret knowledge. Successful exploitation requires a caller to treat deserialized `ReceivedOutput` records as authenticated scanner results rather than unauthenticated claims.

### Recommendation
Bind each `ReceivedOutput` to chain-authenticated data before storing or signing it. At minimum:

- Persist the transaction or a commitment containing the claimed `TxOut` alongside the `OutPoint`.
- During `SignableTransaction::new` or `multisig`, verify each `ReceivedOutput.outpoint` resolves to exactly `ReceivedOutput.output`.
- If full transaction data is unavailable, serialize the observed transaction ID/index under an authenticated scanner event and revalidate it against the Bitcoin node before signing.
- Reject records where `tx.compute_txid()` and `vout` do not produce the claimed `TxOut`.
