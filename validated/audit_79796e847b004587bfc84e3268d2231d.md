## Finding: Division-by-zero panic in consensus-liquidity reward split (`consolidatedNode.Split`)

The Uniswap-style "division by zero as denominator" bug class is reproducible in the reward module's consensus-liquidity (CL) split logic. Unlike the referenced Solidity `revert()` (which only fails a single tx), this is a Go `math/big` division-by-zero, which **panics the node process** during block finalization — a strictly worse DoS.

### Root Cause [1](#0-0) 

`consolidatedNode.Split()` computes `totalAmount = cnAmountBig + clAmountBig` and unconditionally divides `clAmount.Div(clAmount, totalAmount)` whenever `c.CLStakingInfo != nil`, without checking that `totalAmount` is nonzero.

This function is invoked unconditionally (no `minStake`/eligibility gate) in the "proposer split" path: [2](#0-1) [3](#0-2) 

These functions look up the consolidated node matching `config.Rewardbase` (the block proposer's reward address) and, purely on the condition `cn.CLStakingInfo != nil`, call `cn.Split(proposer)`. There is **no check that `cn.StakingAmount` or `cn.CLStakingInfo.CLStakingAmount` is nonzero** at this call site (unlike `assignStakingRewards`/`assignStakingRewardsFlex`, which only call `Split` after gating on `cn.StakingAmount >= minStake`).

### Reachability

A validator can legitimately have `StakingAmount == 0` and still be qualified/proposer-eligible: the valset "understaked" fallback rule states that if no council member meets the minimum stake, no one is demoted: [4](#0-3) 

and the test suite explicitly documents/tests this scenario ("validators can be qualified with zero stakes, if all are understaked"), including that such a zero-stake validator receives a slot in the proposer list: [5](#0-4) 

If that same validator's node has a registered `CLStakingInfo` (via CLRegistry per KIP-226) whose reported `CLStakingAmount` is currently 0 (e.g., fully withdrawn/unbonded CL pool that remains registered), then when it wins proposer selection and `FinalizeState()`/deferred reward distribution runs `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` → `cn.Split(proposer)`, `totalAmount = 0 + 0 = 0`, triggering a `big.Int` division-by-zero panic.

### Impact

Because every full node runs identical deterministic block-finalization/reward-distribution logic, this panic is **not a single node's local failure** — every honest node processing that block crashes identically, halting the entire chain and requiring a coordinated software patch and restart, matching (and exceeding) the severity described in the referenced report.

### Recommendation

In `consolidatedNode.Split()` (`kaiax/staking/staking_info.go`), guard against `totalAmount.Sign() == 0` and return `(amount, big.NewInt(0))` (i.e., treat as CN-only) in that case, mirroring the safe short-circuit already present when `CLStakingInfo == nil`. [1](#0-0)

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
