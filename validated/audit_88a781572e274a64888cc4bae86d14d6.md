Unauthenticated `InternalSendTx` lets any caller make the aggregator's fee-paying wallet broadcast and CPFP-bump an arbitrary transaction - (File: core/src/rpc/aggregator.rs)

### Summary
`ClementineAggregator::internal_send_tx` deserializes an attacker-supplied `raw_tx` and passes it directly to `self.tx_sender.insert_try_to_send` with zero validation against any bridge state (no deposit, UTXO, signature, or ownership check). Whether this call is reachable by an unauthenticated caller depends entirely on `config.client_verification`; by the project's own documented design, "the aggregator does not enforce client certificates but does use TLS for encryption," which in the interceptor implementation means the `Noop` interceptor is installed, and `internal_send_tx` becomes callable by anyone who can reach the aggregator's gRPC port.

### Finding Description
Binding claimed: caller reaching `internal_send_tx` == `self` (only the aggregator's own client certificate). Traced code shows this binding is enforced only conditionally.

- `core/src/servers.rs::create_grpc_server` (lines 106-139) chooses the interceptor based solely on `config.client_verification`:
  - if `true` → `Interceptors::OnlyAggregatorAndSelf { aggregator_cert, our_cert }`
  - if `false` → `Interceptors::Noop`
- `core/src/rpc/interceptors.rs::only_aggregator_and_self` enforces `is_internal` paths (prefixed `Internal`, which includes `InternalSendTx`) require `leaf_cert == our_cert`. `Interceptors::Noop` performs no check at all (`Ok(req)` unconditionally) [1](#0-0) .
- `create_aggregator_grpc_server` uses the same generic `create_grpc_server`, so the aggregator's binding to `self` is contingent on `config.client_verification == true` [2](#0-1) .
- The project's own documentation states explicitly: "The aggregator does not enforce client certificates but does use TLS for encryption" [3](#0-2) , confirming that the aggregator's deployed/intended configuration runs with `client_verification = false`, i.e., `Noop`.
- `internal_send_tx` itself performs no additional authorization or content validation: it decodes `raw_tx`, logs it, and calls `insert_try_to_send` with no metadata, no cancel/activate constraints, and no check that the tx is part of any known presigned transaction graph [4](#0-3) .
- `TxSenderClient::insert_try_to_send` only checks for txid duplication before persisting the tx to the send queue for CPFP/RBF fee bumping — it does not validate provenance of the transaction [5](#0-4) .

Root cause: `InternalSendTx` is guarded by a caller-identity check that is bypassed entirely whenever `client_verification=false`, which is the documented/intended aggregator deployment mode. There is no defense-in-depth check inside `internal_send_tx` itself (e.g., verifying the tx matches a DB-tracked presigned transaction, deposit outpoint, or kickoff), so once past the (optional) TLS-identity gate, any syntactically valid Bitcoin transaction is accepted and queued for the aggregator's automation wallet to fund/broadcast/CPFP-bump.

### Impact Explanation
An attacker who can reach the aggregator's public gRPC port (when it is run per documented configuration with `client_verification=false`) can submit an arbitrary self-funded Bitcoin transaction and have the aggregator's automation wallet add CPFP anchors and pay fees to broadcast it — this is an unauthenticated state-changing/broadcasting call (High severity category per the rules). It does not by itself move BTC out of a move-to-vault UTXO or cause a false reimbursement (the aggregator wallet only pays fees on an already-fully-formed transaction chosen by the attacker; it can't fabricate a valid spend of a bridge UTXO it doesn't control the keys for), so it does not reach the Critical categories (no N-of-N signature forgery, no move-to-vault spend, no reimbursement credited). The primary damage is the aggregator wastes its own funds/fee-bumping capacity/broadcast bandwidth on attacker-chosen transactions, and this is repeatable per attacker request.

### Likelihood Explanation
Feasibility depends entirely on deployment configuration: this is exploitable only if the operator runs the aggregator with `client_verification=false` (Noop interceptor), which the documentation states is the standard behavior for the aggregator ("does not enforce client certificates"). Given this is the documented default posture for the aggregator (as opposed to verifier/operator, which enforce cert checks), the precondition is realistic in real deployments. Attacker cost is minimal — one gRPC call with a self-funded, arbitrary valid Bitcoin transaction; no bridge deposit or withdrawal is required.

### Recommendation
Add an explicit authorization/validation check inside `internal_send_tx` (defense-in-depth, not solely reliant on the TLS interceptor) that verifies the submitted `raw_tx` corresponds to a transaction the aggregator itself already tracks/expects (e.g., matches a known presigned transaction template, deposit outpoint, or kickoff id in the DB) before calling `insert_try_to_send`. Additionally, reconsider making `client_verification=true` mandatory for `Internal*` RPCs on the aggregator regardless of the general aggregator TLS policy, since `Internal*` methods are meant to be self-only per the `is_internal` check semantics already present in `only_aggregator_and_self`.
