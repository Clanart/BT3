Confirmed root cause path: `applyPatchToIndex` in `app/src/lib/git/apply.ts` re-fetches a *fresh* diff (`getWorkingDirectoryDiff`) at commit time and then builds the patch from that fresh diff using `file.selection`, which is a `DiffSelection` object whose "selected" set is keyed purely by **absolute line index** (`hunk.unifiedDiffStart + lineIndex`), computed earlier against a *different, possibly stale* diff shown to the user in the Changes view.

### Title
Stale line-index reuse in partial-commit patch generation causes silent commit-content corruption - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` regenerates the working-directory diff right before staging, then reapplies the user's previously computed `DiffSelection` (an index-based bitset) against that new diff. Because `DiffSelection.isSelected()`/`formatPatch()` trust the numeric line index alone with no content/hunk-identity check, a working-tree mutation between the moment the user made their line-level selection and the moment `stageFiles`/`createCommit` runs can cause entirely different lines to be selected than what the user saw and checked in the UI.

### Finding Description
- The UI computes and stores a `DiffSelection` against a diff snapshot obtained once, in `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3404-3497`). Selection state (`divergingLines`) is a `Set<number>` of absolute indices (`hunk.unifiedDiffStart + lineIndex`) — see `app/src/models/diff/diff-selection.ts:41-283`.
- The comment at `app-store.ts:3480-3485` explicitly acknowledges the invariant is fragile: "The diff might have changed dramatically since last we loaded it... we'll settle on just updating the selectable lines" — i.e., Desktop only prunes indices that no longer exist; it does not re-validate that a still-existing index still refers to the *same content*.
- When the user commits, `_commitIncludedChanges` (`app-store.ts:3681-3714`) passes the stale `WorkingDirectoryFileChange` (with its old `selection`) straight to `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) → `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`).
- Critically, `applyPatchToIndex` line 60 calls `getWorkingDirectoryDiff(repository, file)` **again**, generating a brand-new diff object with its own hunk boundaries/`unifiedDiffStart` values, and then calls `formatPatch(file, diff)` (`app/src/lib/patch-formatter.ts:129-232`), which uses `file.selection.isSelected(absoluteIndex)` against this new diff.
- If the file content on disk changes between the UI-diff snapshot and the apply-time diff (e.g. a `.gitattributes` clean/smudge filter, a build tool, a pre-commit-adjacent background writer, a symlink target swap, or content rewritten by a malicious repo's tooling/hooks that run between refresh and commit), the hunk layout shifts. The old numeric indices now point at semantically different lines (different content, different add/delete type) in the new diff, but `isSelected()` has no way to detect this — it only compares integers.
- This exactly mirrors the report's bug class: a value (`_smNFTBalance`) computed under one state is reused/combined with a quantity computed under an already-updated state, silently producing a wrong result that is accepted without any consistency check.

### Impact Explanation
This can silently corrupt what the user commits and, subsequently, pushes: lines the user explicitly did **not** select could be included in the commit (or vice versa — selected lines silently dropped), without any error or warning, because `formatPatch` only throws if the resulting patch is completely empty (`patch-formatter.ts:224-227`), not if the selection is merely misapplied. This can leak unintended secrets/content into a commit, or produce a commit whose diff doesn't match what the user reviewed and approved in the UI — a direct "silent corruption of what the user commits or pushes" impact per the valid-impact criteria.

### Likelihood Explanation
Requires a window between diff-load and commit during which the tracked file's content changes in a way that shifts hunk boundaries while keeping the file selectable (not fully removed from the changeset). This is plausible in repositories that use git filters/smudge-clean drivers, LFS-like content transformers, or any tooling that rewrites tracked files asynchronously (build watchers, formatters-on-save, generated files) — none of which requires local/physical access beyond normal repository interaction, and the "attacker" here is effectively the repository's own configured tooling (`.gitattributes` filters are repo-controlled and apply automatically). This is a plausible but not fully proven exploit chain from local code alone — I could not find in the indexed code a timing/debounce mechanism that fully closes this window, but I also could not exhaustively verify all UI-side guards (e.g., possible re-fetch-and-diff before commit) since some file contents may not be fully indexed.

### Recommendation
Before calling `formatPatch` in `applyPatchToIndex`, verify the newly-fetched diff is structurally/content-identical to the diff the selection was computed against (e.g., compare a hash of hunk headers/line text, not just line count), and abort/refresh the selection (forcing user re-review) if it has changed, rather than silently reapplying stale indices to new hunk data.

### Proof of Concept
Not independently executed (index-only investigation); the code path establishing the primitive is:
1. `app/src/lib/stores/app-store.ts:3444-3497` — diff loaded once, selection built from its indices.
2. User checks specific lines in the UI (`app/src/ui/diff/side-by-side-diff.tsx:935-961`) — stored via `DiffSelection.withLineSelection`.
3. Underlying tracked file content changes (filter/tool) before commit is triggered.
4. `app/src/lib/git/apply.ts:60` re-fetches diff, `patch-formatter.ts:143-157` walks the **new** hunks using the **old** selection indices.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
