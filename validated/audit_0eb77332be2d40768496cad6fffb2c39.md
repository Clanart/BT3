### Title
Unauthenticated OP_RETURN operator attribution in payout transactions lets an unprivileged party frame an operator into being reimbursed for a payout it never funded - (File: core/src/verifier.rs)

### Summary
The verifier attributes credit for a withdrawal payout solely from an unsigned, unauthenticated `OP_RETURN` output found in the on-chain payout transaction. Because the withdrawal input is signed with `SinglePlusAnyoneCanPay`, any unprivileged party can complete the payout by adding their own funding input and can freely choose which operator's x-only public key to embed in the `OP_RETURN`. This breaks the binding "the operator credited == the party that actually funded the payout."

### Finding Description
`update_finalized_payouts` scans the payout transaction for its first `OP_RETURN` output and parses an x-only public key out of it, storing it as `payout_payer_operator_xonly_pk` with no further authentication: [1](#0-0) 

That value is used directly to decide which operator's automation should treat the withdrawal as "its" unhandled payout: [2](#0-1) 

`PayoutCheckerTask` polls for the first unhandled payout keyed to the local operator's own public key and, if found, unconditionally calls `handle_finalized_payout`, which allocates one of that operator's kickoff connectors and starts the reimbursement flow: [3](#0-2) [4](#0-3) 

The only later consistency check, `is_kickoff_malicious`, merely verifies that the operator who eventually sends the kickoff matches the `OP_RETURN` pubkey recorded for that payout - it does not verify that the credited operator's own funds paid for the withdrawal: [5](#0-4) 

Because the withdrawal input is signed by the withdrawing user with `SinglePlusAnyoneCanPay` (seen in the analogous optimistic-payout signing flow using the same sighash type), any party can combine the user's pre-signed input with additional inputs of their own choosing to complete a valid payout transaction, and can put an arbitrary operator's x-only public key into the `OP_RETURN`: [6](#0-5) 

Since the recorded attribution in the database is taken verbatim from this attacker-controlled `OP_RETURN`, and the targeted operator's own kickoff will match that pubkey (passing the `is_kickoff_malicious` check because the operator itself constructs the matching kickoff), the targeted operator's automation will legitimately proceed through the kickoff/reimburse flow and be paid out of the move-to-vault UTXO for a withdrawal it never funded.

### Impact Explanation
This directly matches the Critical impact category "an operator reimbursed for a payout it never funded." A single unprivileged actor who observes a pending withdrawal request (available once the user broadcasts/signs it) can front the payout using their own BTC while attributing credit to any operator of their choosing. That operator's automated `PayoutCheckerTask` will then consume a scarce, presigned kickoff connector and proceed to claim reimbursement from the shared move-to-vault UTXO for money it never paid, breaking the custody binding between payer and reimbursed party and misallocating vault funds and kickoff-connector inventory. It can also grief an operator's limited kickoff-connector supply and force it into round advances/reimbursement flows it did not intend to enter.

### Likelihood Explanation
Likelihood is high for any unprivileged actor: no verifier, operator, watchtower, or key-compromise role is required. The withdrawal request and its associated signed input are public artifacts of the withdrawal flow (visible via Citrea and the mempool), and constructing an alternate payout tx that reuses the user-signed `SinglePlusAnyoneCanPay` input while substituting an arbitrary `OP_RETURN` operator identity is a straightforward Bitcoin transaction-construction exercise, not requiring any protocol secret.

### Recommendation
Do not rely on the payout transaction's `OP_RETURN` content alone to attribute payout credit. Require and verify a signature (or other cryptographic proof, e.g. the operator's committed funding UTXO/inputs) binding the payout transaction's actual spent inputs to the operator being credited, mirroring the fix pattern the Spearbit report references (detecting all state-changing entry points rather than trusting a single self-declared field). At minimum, `update_finalized_payouts` should reject/ignore attribution unless the claimed operator's own inputs (e.g. from a known operator-controlled address or signed commitment) were used to fund the payout, before writing `payout_payer_operator_xonly_pk` and before `PayoutCheckerTask` acts on it.

### Proof of Concept
1. Observe a user's signed withdrawal request (`input_outpoint`, `input_signature` over `SinglePlusAnyoneCanPay`, `output_script_pubkey`, `output_amount`) submitted through the normal withdraw flow.
2. Construct an alternate Bitcoin transaction that: (a) reuses the user-signed input to produce the required withdrawal output, (b) adds an attacker-funded input to cover the withdrawal amount and fees, and (c) appends an `OP_RETURN` output containing the x-only public key of a target operator `X` (not the attacker).
3. Broadcast and confirm this transaction before operator `X`'s own payout tx.
4. `update_finalized_payouts` records `payout_payer_operator_xonly_pk = X` for this withdrawal [7](#0-6) .
5. Operator `X`'s `PayoutCheckerTask` picks up this "unhandled payout" keyed to its own public key and calls `handle_finalized_payout`, consuming a kickoff connector and proceeding to reimbursement from the move-to-vault UTXO [8](#0-7) , despite `X` never having funded the payout.

    pub async fn handle_finalized_payout<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        deposit_outpoint: OutPoint,
        payout_tx_blockhash: BlockHash,
    ) -> Result<bitcoin::Txid, BridgeError> {
        let (deposit_id, deposit_data) = self
            .db
            .get_deposit_data(Some(dbtx), deposit_outpoint)
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        // get unused kickoff connector
        let (round_idx, kickoff_idx) = self
            .db
            .get_unused_and_signed_kickoff_connector(
                Some(dbtx),
                deposit_id,
                self.signer.xonly_public_key,
            )
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(
            "Operator: Current round index: {}, round idx for kickoff: {}",
            current_round_index,
            round_idx
        );
        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first
            // if current_round_index should only be smaller than round_idx, and should not be smaller by more than 1
            // so sanity check:
            if current_round_index.next_round() != round_idx {
                return Err(eyre::eyre!(
                    "Internal error: Expected the current round ({:?}) to be equal to or 1 less than the round of the first available kickoff for deposit reimbursement ({:?}) for deposit {:?}. If the round is less than the current round, there is an issue with the logic of the fn that gets the first available kickoff. If the round is greater, that means the next round do not have any kickoff connectors available for reimbursement, which should not be possible.",
                    current_round_index, round_idx, deposit_outpoint
                ).into());
            }
            tracing::info!(
                "Operator: Starting next round to be able to get reimbursement for the payout"
            );
            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;
        }
