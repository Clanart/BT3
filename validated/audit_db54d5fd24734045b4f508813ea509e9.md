### Title
Attacker-controlled `n` causes multi-megabyte up-front allocation and unbounded scalar reads in `ThresholdKeys::read` before parameter validation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, and `i` from the input stream and immediately uses the attacker-supplied `n` to drive `Vec::with_capacity(usize::from(n))` and `n` iterations of `C::read_F` / `C::read_G` — all before `ThresholdParams::new(t, n, i)` is invoked to validate the parameters at the end of the function. A tiny crafted header (a 16-byte curve ID, six bytes of `t/n/i`, and one interpolation tag byte) therefore forces an allocation of up to 65 535 field elements (~2–4 MB depending on the curve) and, if the stream continues, up to 65 535 point decodings per call. This is the same bug class as CVE-2022-41723: a small, maliciously crafted input causes resource consumption disproportionate to its size, with no size limit enforced before the work is committed.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), the deserialization order is:

1. Read and verify the curve `C::ID` (fixed-length check).
2. Read `t`, `n`, `i` as raw `u16`s; only `i` is range-checked (via `Participant::new`) — `n` is used raw.
3. Read the interpolation tag. For `Interpolation::Constant`, `Vec::with_capacity(usize::from(n))` is allocated and `n` scalars are read via `C::read_F`.
4. `n` verification shares are read via `C::read_G` into a `HashMap` keyed `1..=n`.
5. Only at the end is `ThresholdParams::new(t, n, i)` called, which is the first place `t <= n`, `n > 0`, and `i <= n` are validated. [1](#0-0) [2](#0-1) 

Because validation happens last, every `n` in `1..=65535` is honored. `Vec::with_capacity` allocates eagerly, so a ~20-byte input yields an immediate ~65 535-element allocation — an amplification of roughly three orders of magnitude for dalek-ff-group scalars and more for wider fields (e.g., ed448 `F`). When the stream actually contains data, each claimed share forces a full scalar/point decode (`read_F`/`read_G` perform canonicality and, for points, decompression/validation), so a modest stream drives tens of thousands of group operations before `ThresholdParams::new` can reject `n` as inconsistent with `t`/`i`.

By contrast, sibling code in the codebase demonstrates awareness of exactly this pattern: `coordinator/src/p2p.rs` bounds `len` against `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating, and `Transaction::read` for `DkgCommitments` rejects `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating. `ThresholdKeys::read` applies no equivalent check.

### Impact Explanation
`ThresholdKeys::read` is listed as an API that may receive untrusted bytes. An unprivileged party that can cause a node to deserialize attacker-controlled `ThresholdKeys` (e.g., during key-share handoff, recovery, or any protocol step feeding peer-supplied bytes to `ThresholdKeys::read`) can, per invocation, force ~2–4 MB of immediate allocation plus up to 65 535 scalar/point decodings. Repeated calls allow sustained memory pressure and CPU burn out of proportion to the bytes sent, degrading or halting the victim's threshold-signing/validator duties — a denial of service achievable with small requests, matching CWE-400.

### Likelihood Explanation
Exploitability requires only that some deployment path feeds external bytes into `ThresholdKeys::read` — the intended use of a `Read`-based deserialization API. No malformed crypto is needed; the bytes are well-formed except for the inflated `n`. The attack is deterministic, cheap for the attacker (a handful of header bytes for the allocation-only variant), and works on any curve implementing `Ciphersuite`.

### Recommendation
Validate before allocating:
- Call `ThresholdParams::new(t, n, i)` (or at minimum check `n <= MAX_N`, `i <= n`, `t <= n`) immediately after reading `t`, `n`, `i`, before any `with_capacity` or per-element reads.
- Replace `Vec::with_capacity(usize::from(n))` with incremental `push` (as used elsewhere, e.g., `Vec::new` + push) so allocation grows only as data is actually consumed.
- Optionally cap `n` at a protocol-level maximum consistent with validator set sizes.

### Proof of Concept
Construct a byte stream for a `ThresholdKeys<Ristretto>::read` call:

```
C::ID (Ristretto ID bytes, length-prefixed as expected)
t = 0x01 0x00            (u16 LE: 1)
n = 0xff 0xff            (u16 LE: 65535)
i = 0x01 0x00            (u16 LE: 1, valid Participant)
interpolation = 0x00     (Interpolation::Constant)
<EOF>
```

On this ~20-byte input:
- `Vec::with_capacity(65535)` allocates ~2 MB (`Scalar` ≈ 32 bytes) at `crypto/dkg/src/lib.rs:608`.
- The first `C::read_F` hits EOF and errors — but the oversized allocation was already performed.
- If the attacker instead supplies ~2 MB of valid scalar encodings followed by ~2 MB of valid point encodings, the function performs 131 070 full field/group decodings plus HashMap insertion of 65 535 entries — all before `ThresholdParams::new` at line 626 gets a chance to reject the parameters. The fix inverts the order so `n` is validated first.

Note: the allocation amplification is bounded by the `u16` width of `n` (~4 MB max per call), so this is a per-invocation memory/CPU amplification DoS rather than unbounded growth; severity is accordingly Medium rather than High, consistent with resource-exhaustion analogs of CVE-2022-41723.
