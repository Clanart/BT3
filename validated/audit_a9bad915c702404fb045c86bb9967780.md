### Title
Unauthenticated `ThresholdKeys::read` input can force oversized heap allocation before parameter validation - (File: `crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::<C>::read` trusts the serialized `n` field and immediately calls `Vec::with_capacity(n)` when deserializing `Interpolation::Constant`, before constructing and validating `ThresholdParams`. A tiny public byte string can therefore force allocation for up to 65,535 scalar elements and trigger an early allocation failure on constrained systems. Because `ThresholdKeys::read` is an exposed untrusted-byte parsing API, this is a reachable resource-exhaustion analog to an unbounded allocation route.

### Finding Description
`ThresholdKeys::read` reads three attacker-controlled `u16` values into `t`, `n`, and `i`, then reads an interpolation selector. When the selector is `0`, it allocates `Vec::with_capacity(usize::from(n))` before attempting to deserialize `n` scalar coefficients. [1](#0-0) 

Only after the interpolation vector, secret share, and all `n` verification shares have been processed does the function call `ThresholdParams::new`, which validates that `t` and `n` are nonzero, `t <= n`, and `i <= n`. [2](#0-1) [3](#0-2) 

`Participant::new` rejects only zero and otherwise permits any nonzero `u16`, while `n` itself is an unconstrained serialized `u16`. [4](#0-3) 

For Ristretto, the expected curve identifier is `b"ristretto"`, so the allocation can be reached with only the curve-ID header, parameter fields, and interpolation selector; no scalar bytes need to follow before the oversized capacity request is made. [5](#0-4) [6](#0-5) 

### Impact Explanation
A 14-byte prefix can request capacity for 65,535 scalar elements—approximately 2 MiB for a typical 32-byte scalar, excluding allocator overhead—before `ThresholdKeys::read` reports `UnexpectedEof` or a parameter error. Repeated or concurrent calls can amplify a small amount of attacker-controlled input into substantial transient heap pressure, and a single call can abort allocation on memory-constrained targets.

This does not corrupt state or forge cryptographic material, but it creates an attacker-controlled allocation size from public serialized input without a protocol-level participant bound. That is an availability issue consistent with the reported class: attacker-controlled requests trigger resource consumption outside an application-enforced cap.

### Likelihood Explanation
Likelihood depends on whether an attacker can invoke key loading or recovery with arbitrary serialized `ThresholdKeys`, but the audit scope explicitly treats bytes supplied to `ThresholdKeys::read` as untrusted input. The function itself requires no key ownership, valid proof, authentication, or well-formed remainder of the message to reach the allocation.

The serialized `n` value is capped by the two-byte encoding at 65,535, so the allocation is not mathematically unbounded per call. It is nevertheless uncapped relative to the actual protocol participant count and is ordered before parameter validation, making this a Medium-severity denial-of-service issue rather than a lower-risk parsing inefficiency.

### Recommendation
Validate `t`, `n`, and `i` immediately after reading them and before selecting or allocating the interpolation representation. In particular:

- Reject `n == 0`, `t == 0`, `t > n`, and `i > n` before `Vec::with_capacity`.
- Enforce a documented protocol maximum for `n`, rather than relying on the `u16` encoding maximum.
- Avoid preallocating from an untrusted count; grow the vector only as valid elements are successfully read, or bound it with a checked capacity.
- Add a regression test that calls `ThresholdKeys::<Ristretto>::read` with a header declaring `n = u16::MAX`, `Interpolation::Constant`, and truncated input, asserting that no `n`-sized allocation occurs before parameter validation.

### Proof of Concept
The following byte stream reaches the allocation path for `ThresholdKeys::<Ristretto>::read` and then ends before any coefficient exists:

```rust
use std::io;
use dkg::ThresholdKeys;
use dalek_ff_group::Ristretto;

#[test]
fn threshold_keys_read_allocates_attacker_controlled_n() {
    let mut input = Vec::new();

    // u32 little-endian curve-ID length and Ristretto's public ID.
    input.extend_from_slice(&9u32.to_le_bytes());
    input.extend_from_slice(b"ristretto");

    // t = 1, n = 65535, i = 1.
    input.extend_from_slice(&1u16.to_le_bytes());
    input.extend_from_slice(&u16::MAX.to_le_bytes());
    input.extend_from_slice(&1u16.to_le_bytes());

    // Interpolation::Constant. ThresholdKeys::read immediately executes
    // Vec::with_capacity(65535), then fails on the missing first scalar.
    input.push(0);

    let result = ThresholdKeys::<Ristretto>::read(&mut input.as_slice());
    assert!(result.is_err());
}
```

The important behavior is not the final error: it is that `Vec::with_capacity(65_535)` executes before `ThresholdParams::new` is called and before even one serialized scalar is available. An allocator-instrumented test can directly observe the approximately 2 MiB capacity request.
