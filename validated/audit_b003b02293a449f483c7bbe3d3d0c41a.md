### Title
Asymmetric decimal-scaling in `convert_to_balance`/`convert_to_erc20` mints/credits wrong amounts when `local_decimals > erc_decimals` - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
The `hyper-fungible-token` pallet converts amounts between the ERC20-side decimal representation and the Substrate-side local balance using `erc_decimals.saturating_sub(local_decimals)` (and the inverse) as the scaling exponent. This is exactly the same bug class as the reported `RAACHousePriceOracle::_processResponse` issue: a fixed/one-directional scaling assumption is applied to a cross-domain numeric value without accounting for the actual relationship between the two precisions, so the stored/dispatched amount ends up off by a power of ten.

### Finding Description
`convert_to_balance` and `convert_to_erc20` are the only functions responsible for translating amounts between the ERC20 (EVM) decimal precision and the local Substrate asset's decimal precision: [1](#0-0) 

Both silently assume `erc_decimals >= local_decimals` (this is documented in the doc-comments — "Divides ... to scale down from ERC20 precision" / "Multiplies ... to scale up to ERC20 precision"). When that assumption doesn't hold — i.e. the registered local asset has **more** decimals than its ERC20 counterpart (e.g. local asset registered with 18 decimals while the corresponding ERC20 token uses 6) — `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the "scaling factor" collapses to `10^0 = 1` and the raw numeric value is passed straight through with no adjustment in either direction.

This is used in two live, unprivileged, user-triggered paths:

1. **Outbound `send()`** (public extrinsic, callable by any signed account): after escrowing/burning the local asset, the pallet computes `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` and puts it directly into the cross-chain `Message.amount` that the destination `HyperFungibleToken.sol`/`HyperFungibleTokenUpgradeable.sol` contracts will mint verbatim via `_mint(beneficiary, message.amount)`: [2](#0-1) [3](#0-2) 

If `erc_decimals` (6, for the ERC20) < `local_decimals` (18, for the local asset), `convert_to_erc20` should **divide** the raw local amount by `10^12` to preserve value, but instead multiplies by `10^0=1`, so `message.amount` is left as the full 18-decimal raw value. The EVM contract then mints that raw number of tokens verbatim (interpreting it as 6-decimal units), inflating the minted supply by a factor of `10^12` relative to what was actually escrowed.

2. **Inbound `on_accept()`** (triggered by any relayed cross-chain message): the same asymmetry runs in reverse via `convert_to_balance`, dividing by `10^0=1` instead of multiplying by `10^12`, drastically **under-crediting** the Substrate-side beneficiary relative to the ERC20 amount that was actually burned/escrowed on the EVM side: [4](#0-3) 

The refund path on timeout (`on_timeout`) uses the identical `convert_to_balance` call and is equally affected: [5](#0-4) 

None of these call sites validate or guard against `erc_decimals < local_decimals`; `saturating_sub` was clearly chosen to avoid an integer-underflow panic, but as a side effect it silently converts "scale down" into "no-op" instead of correctly reversing direction.

### Impact Explanation
This directly matches the required impact categories: **unauthorized minting / fund creation** on the outbound leg (an ordinary `send()` call can cause the destination EVM contract to mint up to `10^(local_decimals - erc_decimals)` times more tokens than were actually escrowed — e.g. a factor of `1e12` for an 18-vs-6 decimal pair), and **fund loss** on the inbound/timeout legs (users receive/get refunded a small fraction of what they are owed, with the difference permanently stuck in the pallet's custodial account / burned with no accounting). Both are core "stealing or loss of funds" and "transaction manipulation" scenarios under the bounty scope, executed purely through the public `send()` extrinsic and the standard ISMP message-acceptance path — no malicious relayer, prover, or governance actor is required beyond the ordinary (non-malicious) act of registering an asset pair whose local decimals exceed its ERC20 decimals.

### Likelihood Explanation
Likelihood depends on whether any live asset-decimal pair is configured with `local_decimals > erc_decimals`. This is a plausible, non-adversarial configuration: pallet-assets tokens or `T::Decimals` native currency can easily be set to 12 or 18 decimals while paired with a common 6-decimal ERC20 stablecoin, and nothing in `Precisions`/`TokenRegistration` setup rejects this combination. Given the code comments explicitly document only the `erc_decimals >= local_decimals` case, this strongly suggests the reverse case was never tested/considered — consistent with an oversight rather than an intentional restriction. I could not confirm from the indexed code whether governance enforces `erc_decimals >= local_decimals` at registration time; if such a check exists elsewhere and is enforced for every registered pair, this reduces to a latent/defense-in-depth issue rather than an immediately triggerable one.

### Recommendation
Replace the one-directional `saturating_sub` scaling with an explicit bidirectional conversion that handles both cases symmetrically and rejects (or explicitly documents/guards) any configuration where the assumption doesn't hold:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add explicit unit tests for the `local_decimals > erc_decimals` case in both `send()` and `on_accept()`/`on_timeout()` paths, and consider validating at asset-registration time that any decimals pair is round-trip-safe (no precision silently dropped to zero).

### Proof of Concept
1. Governance registers a local pallet-assets token `X` with `decimals = 18` and its EVM counterpart ERC20 with `Precisions::<T>::insert(X, dest_chain, 6)` (a normal registration, e.g. mirroring an 18-decimal wrapped asset against a 6-decimal USDC-style ERC20).
2. A user calls `HyperFungibleToken::send(origin, SendParams { asset_id: X, destination: dest_chain, amount: 1_000_000_000_000_000_000 /* 1.0 token, 18dp */, ... })`.
   - `Precisions::get(X, dest_chain) = 6`, `decimals = 18`.
   - `convert_to_erc20(1e18, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, so `erc20_amount = 1e18 * 1 = 1e18`.
3. The dispatched `Message.amount = 1e18` is delivered to `HyperFungibleToken.sol::onAccept`, which calls `_mint(beneficiary, 1e18)` on the destination ERC20 (6-decimal) contract.
4. Instead of receiving the correct `1_000_000` (1.0 token at 6 decimals), the beneficiary is minted `1_000_000_000_000_000_000` raw units — `1,000,000,000,000` (one trillion) tokens, a `10^12`-fold over-mint, while only 1 token's worth was escrowed on the Substrate side.
