### Title
Stale line-indexed diff selection state is silently reapplied against a regenerated diff, allowing unintended working-directory content to be included in a commit - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
The reported UsualSP bug is a broken invariant: a per-user accounting value (`lastRewardPerTokenUsed`) is carried forward and reused against a new baseline (`rewardPerTokenStored`) without being re-synchronized when the underlying state changes, producing an unintended value.

The closest reachable analog in this GitHub Desktop codebase is in the changes/diff subsystem: a file's partial-commit selection is stored as a *pure line-index bitset* (`DiffSelection`), completely decoupled from the actual diff content it was computed against. When the working directory status is refreshed, this stale index-based selection is carried over onto the newly generated file/diff object by identity (file `id`/path) alone, with no verification that the line numbering of the new diff still matches the diff the selection was computed from.

### Finding Description
`DiffSelection` tracks selected/deselected lines purely by absolute line index (`divergingLines: Set<number>`), with no reference to the actual line content: [1](#0-0) [2](#0-1) 

`isSelected(lineIndex)` and `isSelectable(lineIndex)` never validate that a given index still corresponds to the same underlying diff/hunk layout it was recorded against; they trust the index blindly. `withSelectableLines()` only *filters* the diverging-line set against a supplied set of valid indices — it does not detect that the *meaning* of an index shifted: [3](#0-2) 

When a status refresh occurs, `updateChangedFiles` re-associates each file by `id` and reuses its previous selection wholesale on the freshly generated `WorkingDirectoryFileChange`, without recomputing/validating it against the new diff at all (this only happens later, and only for the single currently-selected file): [4](#0-3) 

Even the "correction" path in `updateChangesWorkingDirectoryDiff` only prunes indices from `divergingLines` that are no longer in `selectableLines` — it does not verify that the surviving indices still refer to the same lines of content they did previously: [5](#0-4) 

Finally, when the commit is created, `formatPatch` walks the diff hunks and decides which lines to include purely by asking `file.selection.isSelected(absoluteIndex)` against the *current* diff — with no cross-check that this selection was computed for this exact diff: [6](#0-5) 

If the working tree content is mutated between the time the user reviews/selects lines and the time `createCommit` builds the patch (e.g. an external process, editor autosave, an `.gitattributes` smudge/clean filter, or a script triggered by a `post-checkout`/`post-merge` hook in an attacker-authored repository rewriting a tracked file), the hunk boundaries and absolute line numbers shift. The stale `divergingLines` indices then point at different content than what the user actually inspected and checked/unchecked, so `formatPatch` silently stages/commits lines the user never selected (or drops lines the user did select) — this is precisely "silent corruption of what the user commits," analogous to the reward contract using a stale baseline (`lastRewardPerTokenUsed == 0`) against a moved-forward `rewardPerTokenStored`.

### Impact Explanation
The user's expectation that "only the lines I checked will be committed" is a core trust guarantee of the partial-commit / hunk-selection feature. Silent inclusion of unselected changes (potentially malicious or unreviewed content introduced via a filter/hook defined by a cloned repository) into a commit that later gets pushed can lead to unintentional disclosure or propagation of unreviewed content, and undermines the integrity of code review workflows built on Desktop's line-by-line staging UI.

### Likelihood Explanation
Likelihood is low to medium. It requires the working-directory file content to change (in a way that shifts line numbering) between the time the diff/selection was computed and the time `_commitIncludedChanges`/`createCommit` runs, for a file that is not the currently focused file (so its selection is never revalidated via `updateChangesWorkingDirectoryDiff`). This is plausible with git smudge/clean filters or checkout-time hooks defined in `.gitattributes`/`.git/hooks` inside an attacker-authored/cloned repository, external tools (formatters/linters) running on save, or background file generation — none of which require local admin rights or pre-existing malware, only that the user work with the attacker-supplied repository content.

### Recommendation
Tie `DiffSelection` to a content-derived identity for the diff it was computed against (e.g., a hash of the diff/hunks, or line-content anchors instead of raw indices), and invalidate/re-derive the selection whenever the underlying diff for a file changes — not only for the currently focused file. At minimum, `updateChangedFiles` should compare a diff fingerprint (not just file `id`) before reusing `existingFile.selection`, and `_commitIncludedChanges` should refuse to commit partial selections whose diff fingerprint doesn't match the diff last presented to the user, forcing a refresh/re-review instead of silently applying stale indices.

### Proof of Concept
1. In a working directory, modify `file.txt` with several hunks; open it in Desktop's Changes view and deselect one specific added line (e.g., line 40) while keeping the rest selected. This records `divergingLines = {40}` in `DiffSelection` relative to the diff at that moment.
2. Without re-selecting/re-focusing that file in Desktop (so `updateChangesWorkingDirectoryDiff` never re-validates it), have the file content change externally in a way that shifts line numbers above line 40 (e.g., a `.gitattributes` `clean`/`smudge` filter defined in the repository runs on the next `git status`/`git diff` invocation Desktop performs, or an editor auto-formatter inserts lines earlier in the file).
3. Trigger a background status refresh (e.g. focus change) — `updateChangedFiles` reuses the old `DiffSelection` (`divergingLines = {40}`) onto the new file object unchanged.
4. Commit via `_commitIncludedChanges`; `formatPatch` calls `isSelected(40)` against the new diff, which now names a different line than the one originally deselected — the actually-deselected content gets committed while the originally intended exclusion is lost, silently corrupting the resulting commit.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

  /**
   * Returns a copy of this selection instance with a specified set of
   * selectable lines. By default a DiffSelection instance allows selecting
   * all lines (in fact, it has no notion of how many lines exists or what
   * it is that is being selected).
   *
   * If the selection instance lacks a set of selectable lines it can not
   * supply an accurate value from getSelectionType when the selection of
   * all lines have diverged from the default state (since it doesn't know
   * what all lines mean).
   */
  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }
