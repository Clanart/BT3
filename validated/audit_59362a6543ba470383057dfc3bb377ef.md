### Title
Re-enabling `protocol.file.allow=always` for submodule operations reopens CVE-2022-39253-style local file exposure via a malicious `.gitmodules` - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` boolean and, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. This is the exact git safety knob that upstream Git introduced to fix CVE-2022-39253 (arbitrary local file disclosure via `file://` submodule URLs). Re-enabling it unconditionally for any code path that processes an attacker-supplied repository (a freshly cloned or fetched repo whose `.gitmodules`/tree the attacker fully controls) reopens that class of bug inside Desktop. [1](#0-0) 

### Finding Description
The report's underlying pattern is: a security-relevant computation/config decision (`availableBalance`) is made without checking the identity/trust of the object being acted on (the token address), so an attacker can choose that identity to trigger an unsafe path. The Desktop analog is structurally identical: whether `protocol.file.allow=always` is passed to git is controlled by a caller-supplied `allowFileProtocol` boolean, not by anything that establishes the *provenance* of the submodule URL being processed. `listSubmodules`/`updateSubmodulesAfterOperation` operate on `.gitmodules` content that is fully attacker-controlled once the user has cloned or fetched a malicious repository — the submodule path and URL (including `file://…` URLs pointing anywhere on the local filesystem, e.g. `../../../.ssh` or a Windows drive path) are read straight out of the repo tree. [2](#0-1) 

Git's own `protocol.file.allow=user` default (post CVE-2022-39253 fix) exists specifically to stop a submodule from doing a local `file://` clone of an arbitrary directory, which can hard-link/copy files from outside the intended repository into the working tree (and from there be visible/diffable/committable inside Desktop, satisfying "file read outside repo" / "silent corruption of what the user commits or pushes"). By hard-coding `always` behind a boolean flag, Desktop delegates the security decision to whatever caller sets `allowFileProtocol = true`; if that caller is invoked during clone/checkout/pull flows for a newly obtained, untrusted repository, git's own hardening is bypassed with no boundary check against a known-safe submodule origin.

### Impact Explanation
If `allowFileProtocol` is set to `true` on a code path that runs `submodule update --init --recursive` against a just-cloned or just-fetched attacker-controlled repository, the attacker can craft `.gitmodules` entries with `file://` URLs pointing at sensitive local paths (SSH keys, credential files, other repositories) outside the cloned repo. Git will perform a local clone/checkout of that path into the submodule directory inside the user's working tree, exposing its contents to the user (and to Desktop's diff/commit UI), which can then be inadvertently committed and pushed — an unprivileged, attacker-controlled-repo primitive resulting in file read outside the repo and potential credential/content exfiltration via a normal commit/push.

### Likelihood Explanation
Likelihood depends entirely on whether any call site passes `allowFileProtocol=true` for submodule operations triggered on repositories the user does not already trust (e.g., during/after cloning a new remote repo, or fetching+checking out a branch from an untrusted fork/PR). The flag and the git argument construction that reintroduces the disabled protection are confirmed in code; the codebase index available to this analysis did not let me confirm the exact trust-gating logic in `app/src/lib/git/checkout.ts`, which also references `allowFileProtocol` four times. Without that confirmation, this is a plausible but unverified regression — the risk is real if any of those call sites unconditionally enable the flag for submodules originating from a freshly-cloned/fetched (untrusted) repository.

### Recommendation
- Verify every call site of `updateSubmodulesAfterOperation`/`allowFileProtocol` in `app/src/lib/git/checkout.ts` and ensure `protocol.file.allow=always` is only ever used for submodules whose parent repository is already fully trusted (e.g., re-checkouts within a repo the user explicitly added), never for submodule initialization performed as part of a first clone or a checkout of content just fetched from a remote/PR.
- Prefer leaving Git's default (`protocol.file.allow=user`, or explicitly `deny` for untrusted flows) and only escalate per-submodule after validating the resolved absolute path stays within an allow-listed boundary, mirroring the sanitization approach already used for clone path safety (`sanitizeCloneName` in `app/src/lib/remote-parsing.ts`).

### Proof of Concept
1. Attacker creates a public repository containing a `.gitmodules` file with an entry such as:
   ```
   [submodule "leak"]
     path = leak
     url = file:///C:/Users/victim/.ssh
   ```
2. Victim clones or fetches this repository in GitHub Desktop, then checks out the branch/commit containing this `.gitmodules`.
3. If the resulting submodule-initialization call path passes `allowFileProtocol=true` (i.e. reaches `updateSubmodulesAfterOperation` with that flag set), Desktop runs:
   ```
   git -c protocol.file.allow=always submodule update --init --recursive
   ``` [3](#0-2) 
   which performs a local `file://` clone of `C:\Users\victim\.ssh` into the `leak/` submodule directory inside the working tree, exposing its contents in Desktop's Changes view where the victim could accidentally stage/commit/push them.

**Note on confidence**: The vulnerable configuration line (`protocol.file.allow=always`) and its gating via a boolean parameter are confirmed directly in `app/src/lib/git/submodule.ts`. I was not able to inspect the full logic of `app/src/lib/git/checkout.ts` (where `allowFileProtocol` is also referenced) within this session to confirm whether it is properly restricted to trusted contexts only, so I cannot state with certainty that an exploitable path currently exists end-to-end — this should be verified by reading `app/src/lib/git/checkout.ts` in full before treating this as confirmed-exploitable.

  repository: Repository,
  remote: IRemote | null,

  progressKind: T['kind'],
