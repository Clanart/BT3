## Title
Unvalidated `filepath` parameter from `x-github-client://openRepo` deep link is passed through to app dispatch without traversal/character sanitization - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` in `app/src/lib/parse-app-url.ts` parses attacker-controlled deep-link URLs (`x-github-client://openRepo/...`, and legacy `github-mac://`/`github-windows://`) that are dispatched into the app whenever a user clicks an "Open in Desktop" style link. For the `openrepo` action, the `branch` query parameter is explicitly validated with `testForInvalidChars` before being accepted [1](#0-0) , but the `filepath` query parameter is read with the same `getQueryStringValue` helper and passed straight through into the resulting `IOpenRepositoryFromURLAction` with **no validation at all** [2](#0-1) . This is the structural analog of the audit finding: an externally supplied value ("address"/parameter) that reaches a later privileged operation without being verified, even though a sibling parameter (`branch`) in the very same function demonstrates that validation was considered necessary and technically straightforward.

### Finding Description
The interface contract explicitly documents `filepath` as "the file to open after cloning the repository" [3](#0-2) , meaning this value is expected to later be joined with the cloned repository's working directory and opened (e.g., in an editor). Unlike `branch`, which is checked against `testForInvalidChars` from `sanitize-ref-name.ts` before acceptance [4](#0-3) , `filepath` undergoes no character filtering, no traversal-segment stripping, and no length/format constraint. The action carrying this unsanitized value is routed through `Dispatcher.dispatchURLAction` to `openRepositoryFromUrl(action)` [5](#0-4) .

Elsewhere in the codebase, the project explicitly acknowledges this exact class of risk and has since introduced guards — e.g. `resolveWithin` used to "Guard against path traversal and symlink escapes (cross-platform)" when resolving conflict file paths [6](#0-5) , and `sanitizeCloneName`, which explicitly rejects `..`/traversal segments when deriving a clone directory name from a URL, with accompanying tests for traversal payloads [7](#0-6) [8](#0-7) . No equivalent guard is visible for the `filepath` parameter at its point of origin in `parse-app-url.ts`.

### Impact Explanation
If the value ultimately consumed by `openRepositoryFromUrl` joins `filepath` onto the freshly cloned repository's working directory (as its doc comment implies) without re-validating/resolving it safely (in the manner `resolveWithin` does for conflict files), an attacker who gets a victim to click a crafted `x-github-client://openRepo/<repo-url>?filepath=..%2F..%2F..%2F.ssh%2Fid_rsa` (or similar OS-specific traversal payload) link could cause Desktop to open, in an external editor, a file located outside the cloned repository — i.e., an unprompted file-read primitive triggered purely by a clicked link, matching the "attacker controls...a link or deep link the user clicks" impact category.

### Likelihood Explanation
The attack requires only that the user click an untrusted link; this matches the documented `x-github-client://` and legacy `github-mac://`/`github-windows://` protocol handlers registered by the app [9](#0-8)  and the `open-url`/protocol-launcher handling that feeds arbitrary command-line URLs into `handleAppURL` → `parseAppURL` [10](#0-9) [11](#0-10) . The existing unit tests for `parseAppURL` only assert `filepath` is passed through unchanged and never test rejection of traversal payloads, unlike the `branch` parameter which has explicit invalid-character tests [12](#0-11) .

### Recommendation
Sanitize `filepath` the same way `branch` is sanitized in `parseAppURL` (reject invalid/control characters, reject `..` traversal segments, and reject absolute paths), and additionally re-validate/resolve it at the consumption site (in `openRepositoryFromUrl`/wherever the file is opened) using a `resolveWithin`-style check to ensure the final resolved path stays inside the cloned repository's working directory before invoking any editor-open operation.

### Proof of Concept
1. Register/observe that Desktop is the default handler for `x-github-client://` on the victim's machine.
2. Craft a link: `x-github-client://openRepo/https://github.com/attacker/repo?branch=main&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
3. Victim clicks the link (e.g., embedded in a webpage or issue comment); the OS invokes Desktop via the registered protocol handler, hitting `handleAppURL` → `parseAppURL`.
4. `parseAppURL` accepts the `filepath` value unmodified (no `testForInvalidChars`-style check as applied to `branch`) and returns it inside `IOpenRepositoryFromURLAction`.
5. This action is dispatched to `openRepositoryFromUrl`; if that code joins `filepath` onto the repository directory and opens it without a `resolveWithin`-style containment check, the traversal payload causes a file outside the intended repository to be opened/read.

**Note on confidence:** I was not able to retrieve the full body of `Dispatcher.openRepositoryFromUrl` (the actual consumer of `filepath`) within the available search results, so I cannot confirm with certainty whether that function already performs its own path-containment check before opening the file. The finding above is based on confirmed evidence that `parse-app-url.ts` performs no sanitization of `filepath` despite sanitizing the sibling `branch` parameter, and that the codebase elsewhere treats this exact traversal risk as significant enough to warrant dedicated guards (`resolveWithin`, `sanitizeCloneName`). If `openRepositoryFromUrl` is confirmed to already apply an equivalent guard to `filepath`, this issue would be mitigated at the sink and the residual risk would be limited to defense-in-depth.
