### Title
`WombatStaking` contract can permanently lock stray native BNB sent to its `receive()` function - (wombat/WombatStaking.sol)

### Summary
`WombatStaking` defines a `receive() external payable {}` fallback that accepts arbitrary native BNB from any wallet, but the contract contains no function that allows the received native balance to be withdrawn or swept, other than the fixed accounting inside `vote()`, which only forwards amounts computed from `IWombatBribe` reward data — not the contract's actual native balance.

### Finding Description
`WombatStaking.sol` declares: [1](#0-0) 

This makes the contract able to receive plain BNB transfers from any unprivileged wallet (a simple `call{value: x}("")` to the contract address succeeds). The only place in the contract that moves native value out is inside `vote()`, where BNB bribe rewards are immediately wrapped into WBNB: [2](#0-1) 

That flow only operates on `rewardAmount` values returned by `voter.vote()`/`IWombatBribe`, not on `address(this).balance`. Consequently, if a user (or any external actor) mistakenly sends BNB directly to the `WombatStaking` contract address (e.g., typo'ing an interaction, or a wallet UI that resolves this address for a "deposit"), that BNB is never referenced by any other function. There is no `rescueETH`/`emergencyWithdraw` equivalent for native currency anywhere in the contract — a full read of the contract confirms only ERC20 flows (`deposit`, `depositLP`, `withdraw`, fee/reward routing) exist, none of which touch `address(this).balance`.

This is the same root cause as the referenced Sherlock finding for the nounsDAO `Stream` contract: a contract accepts ETH/BNB via `receive()` but has no corresponding withdrawal path, so any native currency sent to it becomes permanently stuck.

### Impact Explanation
Any BNB accidentally or intentionally sent directly to the `WombatStaking` contract address is permanently frozen with no recovery mechanism, for any wallet, indefinitely (well past the 24-hour threshold). Because `WombatStaking` is a core, actively-used contract in the protocol (referenced/interacted with by pool helpers and users), this is a realistic occurrence, not a purely theoretical one.

### Likelihood Explanation
Likelihood is moderate: it requires a wallet to send BNB directly to the `WombatStaking` contract's address rather than to an intended target. This can happen due to user error, wallet integration issues, or interactions that assume the contract behaves like a payable helper. No privileged role, governance action, or malicious admin is required — an ordinary externally-owned account triggering a plain value transfer to the contract is sufficient to trigger the loss.

### Recommendation
Add an owner-restricted `rescueETH()` (or `emergencyWithdrawNative()`) function to `WombatStaking.sol` analogous to how ERC20 rescue is typically handled, transferring `address(this).balance` out to a designated recipient. Alternatively, remove the unconditional `receive()` function if native BNB is never intentionally expected to be held by the contract outside of the atomic `vote()` flow, or restrict/validate the source of incoming value.

### Proof of Concept
1. Deploy/observe the live `WombatStaking` contract.
2. From any EOA, call `address(wombatStaking).call{value: 1 ether}("")`. This succeeds because of the unconditional `receive()` at [1](#0-0) .
3. Attempt to locate any function that transfers out `address(this).balance` — none exists in the contract; the only native-value-consuming code path is inside `vote()`, which uses `rewardAmount` from bribe accounting, not the contract's raw balance [3](#0-2) .
4. The sent BNB remains locked in the contract permanently, with no `onlyOwner` or any other function capable of retrieving it.
