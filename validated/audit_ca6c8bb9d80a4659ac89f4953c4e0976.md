### Title
Unbounded byte-index read in `is_atom_canonical` on attacker-controlled spend bytes - (File: `chia/full_node/mempool_manager.py`)

### Summary
CVE-2018-14031 describes a heap-based buffer over-read in HDF5's `H5T_copy` caused by insufficient bounds checking while parsing an attacker-supplied structure. The analogous bug class — a length/prefix-driven parser that reads past the caller-supplied buffer without validating remaining length before dereferencing — appears in `is_atom_canonical()` in `chia/full_node/mempool_manager.py`, which walks a CLVM-encoded byte buffer taken directly from an untrusted spend bundle's puzzle reveal / solution.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` [1](#0-0)  decodes a CLVM atom length-prefix by repeatedly indexing `clvm_buffer[offset]` inside a `for i in range(prefix_len)` loop with no check that `offset` stays within `len(clvm_buffer)`. `is_clvm_canonical()` [2](#0-1)  calls `is_atom_canonical` while iterating an attacker-controlled `clvm_buffer` (`bytes(spend.puzzle_reveal)` / `bytes(spend.solution)` from a submitted `SpendBundle`), advancing `offset` by attacker-influenced prefix lengths.

Because Python `bytes` objects raise `IndexError` on out-of-range access rather than allowing a real memory over-read, this is not directly memory-unsafe the way the HDF5 C bug is. However, it reproduces the same *root-cause pattern* — a length-prefixed decoder that trusts an attacker-chosen prefix length/opcode without first checking that enough bytes remain in the buffer before dereferencing. A crafted puzzle reveal or solution with a truncated multi-byte atom-length prefix (e.g., a single `0xFC`-class byte with no following length bytes, at the very end of the buffer) can trigger an uncaught `IndexError` inside this canonical-form check.

### Impact Explanation
`is_clvm_canonical()` is invoked from the mempool add path when validating whether a spend is eligible for `ELIGIBLE_FOR_DEDUP` handling (per `.cursor/context/clvm-execution.md`, "Required for DEDUP-eligible spends") — this is on the path that processes every submitted spend bundle's puzzle_reveal/solution bytes before they are accepted or rejected from the mempool. An uncaught `IndexError` at this call site is not handled by the normal `Err.INVALID_COIN_SOLUTION` failure path exercised by tests such as `test_mempool_requires_canonical_clvm` [3](#0-2) ; if the exception propagates unhandled through spend-bundle processing rather than being converted into a graceful `MempoolInclusionStatus.FAILED`, it constitutes a spend-triggered transaction-processing halt for the mempool manager — a single, unprivileged, unsigned spend-bundle submission could disrupt full-node mempool processing.

### Likelihood Explanation
Likelihood is **uncertain without further verification**. I could not fully confirm (within available tool budget) whether the call path into `is_clvm_canonical`/`is_atom_canonical` from `add_spend_bundle`/`pre_validate_spendbundle` is wrapped in a broad `try/except` that converts any exception (including `IndexError`) into `Err.INVALID_COIN_SOLUTION` or `Err.UNKNOWN`, versus letting it propagate. The visible test `test_mempool_requires_canonical_clvm` only exercises non-canonical *length-encoding* cases (e.g. `c00101`), not a *truncated* prefix that would run off the end of the buffer inside the `for` loop, so a truncation-triggered `IndexError` may not be covered by existing tests. This needs verification directly in the repo before treating it as a confirmed halt-causing bug rather than a benign, caught exception.

### Recommendation
Add explicit remaining-length checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (mirroring the bounds checks already present in `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`, e.g. `if n > len(buf): raise ValueError(...)`), and confirm/ensure that any exception raised while checking CLVM canonicality during spend-bundle admission is caught and converted into a normal `MempoolInclusionStatus.FAILED` / `Err` result rather than propagating and disrupting mempool processing.

### Proof of Concept
Construct a `SpendBundle` whose `coin_spend.solution` (or `puzzle_reveal`) ends with a truncated multi-byte atom length prefix, e.g. a buffer ending in the single byte `0xFC` (which signals a 6-byte length prefix: `(b & 0b11111110) == 0b11111100`) with no following bytes. When `is_atom_canonical` is reached with `offset` pointing at that trailing `0xFC` byte, the `for i in range(prefix_len)` loop attempts `clvm_buffer[offset]` past the end of the buffer, raising `IndexError`. Submit this spend bundle through the normal wallet/RPC spend-bundle submission path and observe whether the mempool manager raises unhandled instead of returning `MempoolInclusionStatus.FAILED` — this last step requires runtime confirmation in the actual repository, which was not completed due to tool-call limits.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
