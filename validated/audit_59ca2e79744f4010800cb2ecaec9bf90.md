### Title
Unsafe `.transfer()` on the `usdt` reward token permanently bricks `incentiveDeposit()` - (File: `wombat/ArbWomUp.sol`)

### Summary
`ArbWomUp.incentiveDeposit()` pays out a reward denominated in a token literally named `usdt` using the raw, unsafe `IERC20(usdt).transfer(...)` call instead of OpenZeppelin's `safeTransfer`. This is the exact bug class from the referenced Sublime finding: if the underlying token does not return a `bool` on `transfer` (as real Tether USDT does not), Solidity's strict ABI decoding of the return value reverts every call, permanently bricking the function.

### Finding Description
`incentiveDeposit()` first pulls the user's WOM via `safeTransferFrom` in `_deposit()`, then attempts to pay the USDT-denominated incentive with a plain `.transfer()` call: [1](#0-0) 

The `usdt` address is set once in the initializer and there is no setter to change it afterward: [2](#0-1) 

`ArbWomUp` exposes no other way to deposit WOM into this contract besides `incentiveDeposit()` — there is no plain `deposit()` function like the one that exists in `mWOM.sol`. If the configured `usdt` address is (or is later found to be) a non-standard ERC20 that omits a return value from `transfer` — such as mainnet Tether USDT, which the report explicitly calls out — the call `IERC20(usdt).transfer(msg.sender, rewardToSend)` will always revert due to Solidity's return-data decoding requirement for the `IERC20` interface. Because the WOM pull (`_deposit`) happens earlier in the same transaction, the revert unwinds the whole call, meaning no user can ever successfully call `incentiveDeposit()` — the sole entry point of this "WOM Up" incentive/airdrop program — for as long as `usdt` points at a non-compliant token, with no owner-controlled way to swap the token address afterward.

### Impact Explanation
This permanently freezes the ability of ordinary users to claim the intended incentive reward tied to depositing WOM through this contract: every `incentiveDeposit()` call reverts unconditionally, so the incentive/reward token allocated to the program (and any user's ability to earn it) is permanently unclaimable via the contract's only external entry point, with no admin remediation path (no setter exists for `usdt`).

### Likelihood Explanation
Any ordinary wallet holding WOM triggers the bug simply by calling `incentiveDeposit()` — no privileged role is required. The likelihood of the underlying token misbehaving is entirely dependent on which token is configured as `usdt`; given the variable and event are explicitly named for USDT (a token confirmed by the referenced finding to omit `transfer` return data), this is a realistic deployment configuration, matching the exact scenario the original report identifies as high-risk for DeFi USDT-integrated flows.

### Recommendation
Replace `IERC20(usdt).transfer(msg.sender, rewardToSend)` with `IERC20(usdt).safeTransfer(msg.sender, rewardToSend)` (the contract already imports and uses `SafeERC20`/`safeTransferFrom` elsewhere), and apply the same fix to the analogous unsafe `.transfer()` calls in `wombat/ArbWomUp.sol` (`transferToAdmin`), `wombat/ArbWomUp2.sol`, and `wombat/ArbWomUp3.sol` (`adminWithdrawReward`).

### Proof of Concept
1. Owner initializes `ArbWomUp` with `usdt` pointing to a token whose `transfer()` function does not return a `bool` (e.g., real Ethereum-style USDT).
2. A user calls `incentiveDeposit(amount)`; `_deposit()` succeeds in pulling WOM via `safeTransferFrom`.
3. Execution reaches `IERC20(usdt).transfer(msg.sender, rewardToSend)`; since no data is returned, Solidity's `IERC20` return-data decoding reverts the call.
4. The entire transaction reverts, and because there is no other deposit entry point and no setter for `usdt`, this failure is permanent and unrecoverable through owner action, freezing the whole incentive program. [1](#0-0)
