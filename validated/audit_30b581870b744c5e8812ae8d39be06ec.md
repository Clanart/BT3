### Title
Hand-rolled frontmatter parser splits on any `---` substring, silently downgrading `action: block` to `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter()` locates the end of the YAML frontmatter block with `content.split('---', 2)`, which matches the literal substring `---` anywhere in the file, not just document-separator lines. If a rule's `pattern:` value contains three consecutive dashes, the split point lands inside that value instead of at the real closing `---`, truncating the frontmatter before later keys (e.g. `action: block`) are parsed. `Rule.from_dict()` then defaults the missing `action` key to `"warn"`, silently converting an intended block rule into a non-blocking warning.

### Finding Description
`extract_frontmatter` in [1](#0-0)  splits the whole file content on the literal string `---` using `content.split('---', 2)`, taking `parts[1]` as the frontmatter text. This does not emulate real YAML document-separator semantics (which require `---` to appear alone on its own line); it matches the substring anywhere, including inside a scalar value such as a regex `pattern`.

Consider a rule file:
```
---
name: block-dangerous-rm
enabled: true
pattern: rm\s+-rf.*---.*
action: block
---
Message body
```
Here `content.split('---', 2)` finds the opening marker as the first delimiter and the `---` embedded inside the `pattern` value as the second delimiter. `parts[1]` (the frontmatter text) becomes only `"\nname: block-dangerous-rm\nenabled: true\npattern: rm\\s+-rf.*"`, and everything after (`.*\naction: block\n---\nMessage body`) is dumped into `message`, which is never re-parsed as YAML.

As a result, `action` is absent from the parsed `frontmatter` dict. `Rule.from_dict()` at [2](#0-1)  falls back to the default `action=frontmatter.get('action', 'warn')`, so the rule silently becomes a `warn`-only rule even though the file visibly declares `action: block`.

This is a real divergence from `yaml.safe_load` semantics: a real YAML parser would treat `---` inside a scalar value as ordinary characters and would never truncate the document there. `load_rule_file()` at [3](#0-2)  has no validation step that cross-checks the parsed dict against the raw file for missing/truncated keys, so no warning is emitted — the rule loads "successfully" with the wrong `action`, and `load_rules()` includes it as an `enabled` rule per [4](#0-3) .

### Impact Explanation
`hookify`'s `PreToolUse`/`PostToolUse` hooks (`plugins/hookify/hooks/pretooluse.py`, `posttooluse.py`) rely on `action: block` to actually stop dangerous operations (per `RuleEngine.evaluate_rules`). A rule file that a maintainer/reviewer visually inspects and believes enforces `action: block` for a dangerous pattern (e.g. `rm -rf`) can be crafted — or unintentionally written — such that the parser downgrades it to `warn`, meaning the dangerous command executes anyway with only a warning message shown. This violates the deny-means-deny expectation of the hookify safety mechanism and allows unreviewed, blocked-in-appearance-only operations to proceed.

### Likelihood Explanation
Exploitation requires only that an attacker control the content of a `.claude/hookify.*.local.md` rule file (e.g. via a malicious plugin, a crafted repository/PR that ships such a rule file, or supply-chain tampering of shared rule files) and place a `pattern` value containing `---` before the `action:` key. No special privileges beyond writing/proposing a rule file are needed, and the resulting behavior (silent `warn` instead of `block`) is deterministic and repeatable.

### Recommendation
Replace the hand-rolled `split('---', 2)` boundary detection with line-based detection of frontmatter delimiters (only treat a line that is exactly `---` after stripping as a delimiter), or use `yaml.safe_load` with a proper `re.split(r'(?m)^---\s*$', content)`-style split. Additionally, after parsing, validate that all documented keys expected to be present in the raw frontmatter block (scanned line-by-line for `key:` at column 0) are actually present in the parsed dict, and fail loudly (reject the rule) rather than silently defaulting `action` to `warn` when parsing is ambiguous.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py` test suite:
```python
def test_pattern_with_triple_dash_does_not_downgrade_block():
    content = (
        "---\n"
        "name: block-dangerous-rm\n"
        "enabled: true\n"
        "pattern: rm\\s+-rf.*---.*\n"
        "action: block\n"
        "---\n"
        "Message body\n"
    )
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    assert rule.action == "block", (
        f"Expected action=block but got {rule.action!r}; "
        "action was silently downgraded due to '---' inside pattern value"
    )
```
Expected current (buggy) result: `rule.action == "warn"` — assertion fails, demonstrating the divergence. A differential fuzz test comparing `extract_frontmatter()` against `yaml.safe_load(content.split('\n---\n')[1])`-equivalent parsing across a corpus of frontmatter strings containing embedded `---` in `pattern`/string fields should show `action` and `enabled` values diverging whenever a value contains the `---` substring.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
