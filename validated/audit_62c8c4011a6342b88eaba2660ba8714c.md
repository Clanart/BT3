### Title
`build_refute_prompt` truncates the diff to a fixed 8000-char window uncorrelated with candidate findings, letting attacker-padded diffs hide flagged vulnerable code from the adversarial refute stage - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_refute_prompt` embeds the full candidate list but only `diff_text[:8000]` of the diff, with no logic to ensure the flagged file/hunk is included in that slice. Because the refute-stage prompt explicitly instructs the model to refute any candidate whose `vulnerableCode` "does NOT appear on any + line in the DIFF block above" (the PRE-EXISTING criterion), an attacker who controls the diff content can push their genuinely dangerous hunk past the first 8000 characters (e.g. by adding large/verbose files or hunks earlier in the diff), causing the review model to lose sight of the real evidence and incorrectly refute the finding.

### Finding Description
`agentic_review` (in `plugins/security-guidance/hooks/llm.py`) computes `diff_text` from all diff files via `_cap_files_for_prompt`, capping per-file/total size to up to 400KB (`DIFF_TOTAL_BYTES`) [1](#0-0) . Before self-refute, candidates are tagged `_diff_anchor: "in_diff"/"off_diff"` using this **full** `diff_text` via `_intersects_diff` [2](#0-1) .

However, `build_refute_prompt` (canonical version in `review_api.py`, duplicated inline in `llm.py`) only shows the model `diff_text[:8000]` — a flat, position-based cutoff with no relation to which file/hunk a candidate cites: [3](#0-2) 

The refute prompt's own instructions tell the model to refute a candidate as PRE-EXISTING if the cited `vulnerableCode` is not found in "the DIFF block above": [4](#0-3) 

Because the visible DIFF block is silently truncated to 8000 characters while the real diff can be up to 400KB, a candidate that IS genuinely in the diff (and was correctly tagged `in_diff` by the earlier, full-text check) can be invisible to the refute-stage model simply because its hunk falls past byte 8000 of the concatenated `diff_text`. The model, following its own explicit instructions, will then refute it as PRE-EXISTING — even though the `_diff_anchor` metadata computed against the untruncated diff says otherwise. This is a deterministic, code-level truncation defect, not merely LLM unreliability: the attacker (the author of the diff being reviewed) directly controls diff ordering/size and can arrange for their dangerous hunk to be pushed out of the 8000-char window (e.g. via large refactors, verbose file content, or many changed files preceding the target file), suppressing review of their own dangerous change.

The identical bug exists in the internal duplicate inside `llm.py`'s `agentic_review`: [5](#0-4) .

### Impact Explanation
This breaks the stated invariant that "prompt assembly must not let untrusted repo content suppress review of dangerous changes." A crafted, attacker-controlled diff can cause a real vulnerability finding from Stage 1 (investigate) to be silently dropped at Stage 2 (self-refute) due to a mechanical truncation bug rather than genuine adjudication, allowing dangerous code changes to bypass the security-guidance review gate. This matches "Logic-level service disruption caused by bypassing a required guard" — the required guard being the two-stage agentic review that is supposed to catch dangerous commits before they land.

### Likelihood Explanation
Any contributor whose diff is processed by the agentic reviewer controls the diff's size, ordering, and content. No special privileges are required. The interaction requires (1) a genuine vulnerability that Stage 1 correctly flags, and (2) enough preceding diff content (attacker-added, e.g. a large but benign refactor/file bundled in the same commit) to push the flagged hunk's text past the 8000-character mark of the concatenated `diff_text`. This is fully within an unprivileged contributor's control and is reproducible deterministically — it does not depend on the LLM "choosing" to follow injected instructions, only on the LLM following its own documented refutation rubric applied to a truncated view.

### Recommendation
Instead of a flat `diff_text[:8000]` slice, `build_refute_prompt` should guarantee that each candidate's cited file/hunk is present in the diff excerpt shown to the refute model — e.g., build the excerpt by prioritizing/including the diff sections for files referenced in `candidates` first (up to the byte budget), or pass the already-computed `_diff_anchor` verdict to the model as authoritative for the PRE-EXISTING check instead of asking it to re-derive presence from a possibly-truncated view. At minimum, log/metric emit when truncation drops content referenced by an `in_diff`-tagged candidate, and treat that condition as fail-open (auto-survive) rather than allowing an unanchored refute.

### Proof of Concept
Unit test against `review_api.build_refute_prompt`:
1. Construct `diff_files` with a large benign file (~9000 bytes of diff) followed by a small file containing an obviously dangerous hunk (e.g. `+ os.system(user_input)`), producing `diff_text` where the dangerous hunk starts after character 8000.
2. Build `candidates = [{"filePath": "danger.py", "category": "Command Injection", "vulnerableCode": "os.system(user_input)", ...}]`.
3. Call `prompt = build_refute_prompt(candidates, diff_text)`.
4. Assert `"os.system(user_input)"` (the exact vulnerableCode string) is present in `prompt` — this assertion FAILS with the current implementation, proving the dangerous line is not "present and correctly anchored" after truncation, which will cause the refute-stage model to apply the PRE-EXISTING refutation criterion incorrectly.
5. As a regression guard, assert that after the fix, `prompt` always contains each candidate's `vulnerableCode`/`filePath` marker regardless of diff size/ordering.
