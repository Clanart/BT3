## Analysis

The external report's core pattern: **the same call site assumes one chain's function/behavior applies to all target chains, and an untested chain silently gets the wrong semantics**, breaking the protocol's runtime logic (not just gas/DoS).

I found the closest local analog in `evm/src/apps/intentsv2/IntentsBase.sol`, in the exact same "Arbitrum block-number quirk" problem space that Hyperbridge's own code and tests explicitly call out.

### Title
Hard-coded Arbitrum chain-id allowlist in `_blockNumber()` causes incorrect deadline enforcement on unlisted Arbitrum Orbit chains - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._blockNumber()` special-cases only three literal chain ids (`ARBITRUM_ONE = 42161`, `ARBITRUM_NOVA = 42170`, `ARBITRUM_SEPOLIA = 421614`) to route through the `ArbSys` precompile instead of `block.number`, because Arbitrum-stack chains return an L1-approximate value from the `block.number` opcode. [1](#0-0) 
Hyperbridge's own consensus tooling, however, treats "Arbitrum Orbit" as a generic rollup-stack category with configurable chain ids and rollup-core addresses, not a fixed enum of three networks. [2](#0-1) [3](#0-2) 

### Finding Description
Any EVM chain built on the Arbitrum Orbit stack (a custom L3, or any future Arbitrum-family deployment whose chain id isn't `42161`/`42170`/`421614`) still has the `ArbSys` precompile at `address(100)` and the same `block.number`-returns-L1-approximate-height quirk. `IntentsBase._blockNumber()` only recognizes the three hard-coded ids:

```solidity
function _blockNumber() internal view returns (uint256) {
    if (block.chainid == ARBITRUM_ONE || block.chainid == ARBITRUM_NOVA || block.chainid == ARBITRUM_SEPOLIA) {
        return IArbSys(ARB_SYS).arbBlockNumber();
    }
    return block.number;
}
``` [4](#0-3) 

`_blockNumber()` is the sole source of truth for order-deadline comparisons in the intent lifecycle: it gates `fillOrder` expiry (per the foundry tests) and gates the caller-authorization branch of `_cancelFromDest`:
```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }
    ...
}
``` [5](#0-4) 

On an unlisted Orbit chain, `_blockNumber()` silently falls through to `block.number`, which on any Arbitrum-stack chain reflects the roughly-L1 height rather than the true L2 height (exactly the same class of divergence the maintainers' own tests exercise for Arbitrum One): [6](#0-5) [7](#0-6) 

That divergence means `order.deadline` (denominated by the front-end/user in that chain's real block height) is compared against a stand-in L1-approximate number that can be off by orders of magnitude in either direction, since Orbit L2 block heights advance far faster than L1. This flips the `order.deadline >= _blockNumber()` authorization branch in `_cancelFromDest` and the `Expired()` check gating `fillOrder`, in either direction:
- Deadline logic reports an order still "live" long after its intended real-world expiry, letting `msg.sender`-restricted early cancellation logic keep enforcing the "only user can cancel" branch well past when it should have opened to anyone — or the reverse, opening early cancellation while the order should still require the user's signature.
- Equivalently for `fillOrder`, a not-yet-expired order can appear `Expired()` (locking user funds until the mismatched height eventually catches up, or never), or an expired order can remain fillable well past its intended deadline — a timing/logic manipulation of settlement, not merely a revert.

### Impact Explanation
This is a false-state-acceptance / timing-manipulation issue in the deadline-authorization guard, not a mere revert: `_cancelFromDest`'s `msg.sender == order.user` authorization gate is silently bypassed or wrongly enforced by any unprivileged filler/solver interacting with `fillOrder`/`cancelOrder` on an affected chain, and escrowed funds tied to `order.deadline` can be prematurely refundable/cancelable by non-owners, or conversely locked past the user's intended deadline. No malicious relayer, prover, or governance actor is required — any ordinary user or filler on the affected deployment triggers the corrupted comparison purely by calling the public `fillOrder`/`cancelOrder` entrypoints.

### Likelihood Explanation
Likelihood is directly tied to whether Hyperbridge (or an integrator) deploys the `IntentGatewayV2`/`IntentsBase` bytecode to any Arbitrum Orbit chain outside the three hard-coded ids. Since the repo's own consensus/relayer tooling (`ArbitrumOrbit` consensus config, generic `rollup_core`/`l1_state_machine` parameters) is explicitly designed to onboard arbitrary Orbit chains, and the intent contracts are deployed deterministically via CREATE2 specifically to be chain-agnostic, this is a realistic deployment path rather than a hypothetical one — it is a genuine gap between the generic Orbit-chain support elsewhere in the codebase and the closed enum in `IntentsBase._blockNumber()`.

### Recommendation
Replace the hard-coded chain-id allowlist with a generic Arbitrum-stack detection, e.g. attempt an `ArbSys.arbBlockNumber()` static call and fall back to `block.number` only if the call fails/reverts (mirroring how `tesseract/messaging/evm/src/gas_oracle.rs`'s `is_orbit_chain`/`is_op_stack` detection is meant to generalize across a chain family rather than enumerate three ids), or maintain the Orbit chain-id list as a governance-updatable parameter rather than an immutable constant baked into deterministic bytecode.

### Proof of Concept
1. Deploy `IntentGatewayV2` (via `IntentsBase`) to a custom Arbitrum Orbit L3 with `block.chainid` not in `{42161, 42170, 421614}` (e.g., a new Orbit chain id `99999`).
2. `placeOrder` with `deadline` denominated in that chain's true L2 height (as reported by `ArbSys.arbBlockNumber()`).
3. Because `_blockNumber()` returns `block.number` (L1-approximate) instead of querying `ArbSys`, `order.deadline` is compared against the wrong numeric scale in both `_cancelFromDest`'s authorization gate and the `fillOrder` expiry check — reproducing the same mismatch the existing tests `testFillOrderExpiredOnArbitrumRevertsUsesArbSys`/`testFillOrderNotExpiredOnArbitrumUsesArbSys` demonstrate for the *listed* Arbitrum chains, but here unguarded.
