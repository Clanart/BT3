## Title
Cross-Context Signature Replay Between `withdraw_fees` and `accumulate_fees` Beneficiary Authorization — (File: modules/pallets/relayer/src/withdrawal.rs, modules/pallets/relayer/src/accumulate.rs)

### Summary
The relayer pallet defines two independent signature schemes that are supposed to authorize two different actions — an immediate full withdrawal of accrued fees (`withdraw_fees`) versus a beneficiary redirection applied during future fee accumulation (`accumulate_fees`) — but both schemes hash the exact same tuple shape with no domain separator, and both consume the same per-`(address, dest_chain)` `Nonce` counter. A signature the relayer produced for one purpose is byte-for-byte valid for the other, and either entrypoint is reachable unsigned (`ensure_none`) by any caller.

### Finding Description
`withdrawal::message` builds the payload a relayer signs to authorize `withdraw_fees`: [1](#0-0) 

`accumulate::beneficiary_message` builds the payload a relayer signs to authorize a beneficiary redirect inside `accumulate_fees`: [2](#0-1) 

Both functions SCALE-encode `(u64 nonce, StateMachine, Vec<u8> beneficiary)` and `keccak256` it — identical bytes for identical inputs. Neither includes a call-selector, purpose tag, or any other domain separator. In addition, both flows read/increment the *same* storage map: [3](#0-2) 

In `withdraw()`, the nonce is read, the message is derived from the caller-supplied `(dest_chain, beneficiary)`, and if the signature checks out the pallet immediately dispatches disbursement of the relayer's *entire currently accumulated* `Fees` balance to `beneficiary`, then increments the nonce and zeroes `Fees`: [4](#0-3) [5](#0-4) 

In `accumulate()`, the `beneficiary_details` signature is verified against `beneficiary_message(nonce, state_machine, beneficiary)` using the same `Nonce` entry, and on success only redirects the specific batch's newly-proven fee amount and advances the same nonce: [6](#0-5) 

Both `accumulate_fees` and `withdraw_fees` are unsigned/unprivileged entrypoints (`ensure_none(origin)?`), executable by anyone who can construct valid inputs: [7](#0-6) 

Because the signed payloads collide, a signature the relayer produced to authorize a narrow, future-scoped accumulate-time beneficiary redirect (`beneficiary_message(nonce, dest_chain, beneficiary)`) is *also* a valid signature for `withdraw_fees` with `dest_chain` and `Some(beneficiary)` at the same nonce — since `message(nonce, dest_chain, Some(beneficiary))` hashes the identical tuple. Any unprivileged party who observes this signature (e.g., relayed off-chain to a delegate for a gasless accumulate flow, or seen in the mempool/a prior block before it is consumed) can submit it directly to `withdraw_fees` first. This immediately drains the relayer's entire *currently escrowed* `Fees[dest_chain][relayer]` balance to `beneficiary`, consumes the shared nonce, and thereby also invalidates the relayer's later, narrower, intended `accumulate_fees` call (nonce mismatch), diverting the flow of funds/timing the relayer did not authorize for that context.

### Impact Explanation
This breaks the stated invariant that "each withdrawal or payee redirection signature must be single-use and bound to the exact destination chain and beneficiary" — it is not bound to the *action/purpose* it authorizes. An unprivileged actor can trigger an unauthorized, premature, full withdrawal of protocol-escrowed relayer fees using a signature the signer only intended for a materially different, narrower on-chain effect (a future fee-redirect versus an immediate full payout of the currently escrowed balance). This is an unauthorized-execution / wrongful-withdrawal condition on user/relayer-escrowed `Fees` balances.

### Likelihood Explanation
Exploitation only requires observing one relayer-produced signature of the `(nonce, dest_chain, beneficiary)` shape (which is either broadcast publicly to enable gasless submission, or visible pre-inclusion in the mempool/tx pool as calldata for an unsigned extrinsic) and racing it into the other entrypoint before the intended call lands. Both entrypoints are permissionless (`ensure_none`), so no privileged access or infrastructure compromise is needed.

### Recommendation
Add explicit domain separation to both signed payloads (e.g., prefix each hash with a distinct static tag/selector such as `b"ISMP-RLYR-WITHDRAW"` vs `b"ISMP-RLYR-ACC-BENEFICIARY"`, or include the pallet call index) so a signature valid for one action can never be replayed as the other. Additionally, consider using separate nonce namespaces (or including a purpose discriminant in the nonce key) for `withdraw_fees` versus the `accumulate_fees` beneficiary redirect, so consuming one does not silently invalidate/interact with the other.

### Proof of Concept
1. Relayer signs `beneficiary_message(nonce=N, dest_chain=S, beneficiary=X)` intending it only to accompany a specific `WithdrawalProof` in `accumulate_fees` (redirecting a small newly-delivered fee amount to `X`).
2. Attacker observes this signature (from mempool, or a leaked delegate flow) before the intended `accumulate_fees` transaction is included.
3. Attacker submits `withdraw_fees(WithdrawalInputData{ signature, dest_chain: S, beneficiary: Some(X) })` — `withdrawal::message(N, S, X)` hashes identically to `beneficiary_message(N, S, X)`, so signature verification in [8](#0-7)  succeeds.
4. `withdraw()` dispatches disbursement of the relayer's entire current `Fees[S][relayer]` balance to `X` and advances `Nonce[relayer][S]` to `N+1`, per [9](#0-8) .
5. The originally intended `accumulate_fees` call now fails signature verification against the advanced nonce, confirming the cross-context replay consumed the authorization meant for a different, narrower action.
