### Title
Protocol fee is levied only on the escrowed `order.inputs`, letting a trade of arbitrary real value dodge the fee by minimizing the fee-bearing side - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
The seed report's broken invariant is: a percentage fee tied to one nominal order field (strike) rather than the field that actually reflects traded value (premium), so a trader can structure the order so the fee-bearing field is trivial while the true value moved is large — silently starving protocol fee revenue. `IntentGatewayV2.placeOrder` reproduces the same broken invariant: the protocol fee is computed *only* from `order.inputs[i].amount` (what the user escrows), while the economically meaningful, solver-supplied side of the trade, `order.output.assets` (what the solver actually delivers to the beneficiary), is never fee-bearing at all.

### Finding Description
In `placeOrder`, the protocol fee is derived exclusively from the input side: [1](#0-0) 

```
if (protocolFeeBps > 0) {
    ...
    uint256 originalAmount = order.inputs[i].amount;
    uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
    uint256 reducedAmount = originalAmount - protocolFee;
    ...
}
```

`order.output.assets` — the tokens the solver must deliver to the beneficiary, and thus the actual value the user receives / the true notional of the intent — carries no fee component whatsoever, as confirmed by the fee table in the docs: [2](#0-1) 

Just as the Putty option fee was tied to `strike` (a value the trader can push near zero for a deep-OTM call while the trade's real economic value sits elsewhere), an IntentGateway user fully controls both `order.inputs` and `order.output.assets` at placement time (`placeOrder(Order memory order, ...)`), and nothing in `placeOrder` requires input value to be proportional to output value: [3](#0-2) 

A user can therefore escrow a dust-valued token (e.g. a cheap/low-decimals token, or a token amount just above zero after the `amount == 0` guard) as `order.inputs`, while demanding a large-value `order.output.assets` from the solver. The `protocolFeeBps` fee is computed only against the trivial input, so the protocol collects a fee that is negligible relative to the true value transferred through the bridge — the entire point of `protocolFeeBps` is defeated for these orders.

The only mitigating control is `IIntentPriceOracle.recordSpread`, invoked after fill: [4](#0-3) 

but this only *records* the input/output spread for analytics after the fact — it does not gate or scale the fee, and `priceOracle` can also be unset (`address(0)`), in which case there is no spread tracking at all.

### Impact Explanation
This directly maps to the seed bug class ("avoid paying system fee"): the protocol fee mechanism can be systematically defeated by any unprivileged user structuring their own orders, degrading the core system's fee capture for trade volume that is, in reality, arbitrarily large (bounded only by what solvers are willing to fill). Because `order.inputs`/`order.output.assets` are both attacker-chosen at `placeOrder` time and the fee formula only reads one side, this is a logic flaw in the fee-gathering design of the intent-settlement path rather than a market-price issue.

### Likelihood Explanation
High: no privileged role, relayer, prover, or governance action is needed. Any user calling `placeOrder` directly controls both `order.inputs` (fee basis) and `order.output.assets` (real value), and solvers who see a profitable spread will fill regardless of how the trade is nominally structured on the input side.

### Recommendation
Compute (or floor) the protocol fee against the greater of the input and output notional values (normalized via the same price oracle used for `recordSpread`), or require `recordSpread`/oracle-based minimum-price validation to be enforced (not just recorded) at fill time, and apply protocolFeeBps to that validated notional rather than solely to `order.inputs`.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `protocolFeeBps = 30` (0.3%), no destination-specific override.
2. User calls `placeOrder` with `order.inputs = [{token: cheapToken, amount: 1}]` (minimal nonzero amount, passes the `amount == 0` check) and `order.output.assets = [{token: expensiveToken, amount: <large value>}]`.
3. `placeOrder` computes `protocolFee = (1 * 30) / 10_000 = 0` (rounds to zero) — see the fee computation block cited above (`evm/src/apps/IntentGatewayV2.sol:314-315`).
4. A solver fills the order via `fillOrder`, delivering the full large-value output to the beneficiary and later redeeming the (near-)full input escrow — with `DustCollected`/protocol fee equal to zero, despite a large real value having moved through the bridge.
5. Repeating this pattern for any order where the user intentionally sets a low-value input side systematically starves the protocol fee, matching the seed report's "zero/near-zero strike avoids fee" pattern exactly.

### Fees

| Fee | When | Who Pays |
|-----|------|----------|
| **Protocol fee** (`protocolFeeBps`) | At order placement | Deducted from user's input tokens |
| **Destination fee** | At order placement (per-destination override) | Deducted from user's input tokens |
| **Surplus share** (`surplusShareBps`) | At fill time, when solver provides more than requested | Split between protocol and beneficiary |
| **Fill fee** (`order.fees`) | At order placement | User (in fee token or native ETH) |
| **Relayer fee** | At fill time (cross-chain) or cancel time | Solver or user |

Protocol fees are retained as "dust" in the gateway and can be swept to a treasury via Hyperbridge governance. When a solver provides more tokens than required, the excess is split according to `surplusShareBps` (100% to protocol if the order has calldata). Surplus only applies on the first fill of each output token pair.
