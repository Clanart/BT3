Based on the investigation, I found a concrete analog to the L2 address sanity check issue.

### Title
TxTypeValueTransfer with zero-address recipient is misclassified as contract creation, causing value to be sent to an unintended derived address instead of failing - ([File: blockchain/types/tx_internal_data_value_transfer.go])

### Summary
Kaia's `TxTypeValueTransfer` (and its fee-delegated/memo variants) accepts an explicit `to = 0x0` recipient, but `GetTo()` silently converts that into a `nil` "to" address. The `nil` "to" sentinel is the same signal the state-transition layer uses to detect **contract creation**, causing a plain value transfer to be executed under contract-creation semantics rather than being rejected, exactly analogous to the report's core theme of unchecked/unsanitized zero-address handling causing unintended fund movement.

### Finding Description
`TxInternalDataValueTransfer.GetTo()` explicitly treats a zero `Recipient` as "no destination": [1](#0-0) 

The exact same pattern is repeated for `TxTypeFeeDelegatedValueTransfer`, `TxTypeValueTransferMemo`, `TxTypeFeeDelegatedValueTransferMemo`, `TxTypeAccountCreation`, etc.: [2](#0-1) [3](#0-2) 

`Transaction.To()` propagates this nil-when-zero behavior to the top-level RPC/consensus-visible API: [4](#0-3) 

In `StateTransition.TransitionDb`, whether a transaction is treated as **contract creation** is determined purely from `msg.To() == nil`: [5](#0-4) 

This flag governs consensus-critical logic paths distinct from ordinary value transfer: init-code size limits, EIP-2929 access-list warm-up target, EIP-7702 delegation-target warming, and floor-data-gas computation are all conditioned on `contractCreation`: [6](#0-5) 

Unlike Ethereum legacy transactions — where `to == nil` is an intentional, protocol-level signal ("deploy a new contract using tx.Data as init code") set via `NewContractCreation`/omitting `to` — Kaia's typed transactions (`TxTypeValueTransfer`, memo variants, fee-delegated variants) **require an explicit `to` field at construction time** (`newTxInternalDataValueTransferWithMap` requires `TxValueKeyTo` to be present): [7](#0-6) 

Nothing in `Validate()` for these types rejects `Recipient == common.Address{}` — it only checks the precompile-address range and EIP-7702 delegation state: [8](#0-7) 

So a user (or fee-delegation counterparty, since these txs support fee delegation) can craft a `TxTypeValueTransfer` with `to = 0x0`. Downstream, `Transaction.To()` and `msg.To()` will report `nil`, which the state-transition layer interprets as a genuine contract-creation transaction. This can cause:
1. Divergent consensus-relevant gas accounting for this transaction relative to what its type (`ValueTransfer`) implies (`contractCreation` toggles init-code-size checks, floor-gas rules, and access-list warm-up target — the warmed/target address differs from the intended `to=0x0`).
2. Trace/RPC and downstream tooling (e.g., `eth_getTransaction`, tracers) classifying and displaying the transaction inconsistently with its actual `TxType` and payload, as seen explicitly handled/worked-around for other special-case types in the tracer test: [9](#0-8) 
3. The value is never actually delivered to address `0x0` as the user intended/specified in the RLP-encoded, signed transaction — it silently changes semantics, which is exactly the class of bug (unchecked zero address on `to` collapsing/aliasing distinct addresses to unintended behavior) called out in the report.

### Impact Explanation
This is a state-transition/consensus-path bug reachable by any unprivileged transaction sender. It causes an on-chain transaction's execution semantics (contract creation vs. plain value transfer) to silently diverge from its declared `TxType` and signed intent whenever `to == 0x0` is chosen, which:
- risks locking/misdirecting value sent by users who set `to=0x0` (deliberately or by mistake, e.g. wallet/tooling bugs, similar to the original bridge/DAI issue where funds got stuck due to zero-address mishandling), and
- creates a discrepancy between what different node implementations, indexers, wallets, or explorers may compute as `to`/contract-creation status for the same transaction, a potential source of state/interpretation divergence.

It does not by itself allow value to be stolen from another account (severity is bounded relative to the original Critical-adjacent StarkNet bug), which is why this is assessed at Medium.

### Likelihood Explanation
Any transaction sender can trivially construct such a transaction (`TxValueKeyTo: common.Address{}`) via `NewTransactionWithMap` since there is no validation rejecting the zero address, and it will pass `Validate()` unless it happens to collide with a precompile address range. This requires no special privileges — a single crafted, self-signed transaction is sufficient to trigger the divergent code path.

### Recommendation
- Reject `Recipient == common.Address{}` in the `Validate()` method of `TxInternalDataValueTransfer`, `TxInternalDataValueTransferMemo`, `TxInternalDataFeeDelegatedValueTransfer*`, and related non-creation typed transactions, returning a clear error (e.g., `ErrInvalidRecipient`) instead of silently mapping to `nil`.
- Alternatively, decouple the "no address" (`GetTo() == nil`) semantic used for contract creation types from Kaia's non-creation typed transactions so `msg.To() == nil` is only ever produced by tx types that are genuinely defined as contract-deployment transactions (`TxTypeSmartContractDeploy` and its variants, and legacy Ethereum contract-creation transactions).

### Proof of Concept
1. Construct a `TxTypeValueTransfer` transaction using `types.NewTransactionWithMap` with `TxValueKeyTo: common.Address{}` (zero address), a non-zero `Amount`, and a valid `From`/nonce/gas — this succeeds because `newTxInternalDataValueTransferWithMap` only requires the key to be present, not non-zero: [7](#0-6) 
2. Sign and submit the transaction; `Validate()` does not reject it: [8](#0-7) 
3. During block processing, `Transaction.To()`/`msg.To()` returns `nil` for this transaction due to `GetTo()`'s zero-address special-casing: [1](#0-0) 
4. `StateTransition.TransitionDb` sets `contractCreation = true` for this transaction purely because `msgTo == nil`, even though the transaction's `TxType` is `TxTypeValueTransfer`: [5](#0-4) 
5. Observe that gas accounting/init-code checks/access-list warm-up now follow the contract-creation path rather than the plain-value-transfer path that the `TxType` and `Execute()` implementation (`vm.Call`) actually perform, demonstrating the semantic mismatch.
