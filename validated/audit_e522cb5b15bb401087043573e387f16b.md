## Title
Same-chain partial-fill escrow release drains shared-token escrow across unrelated order legs — solver receives more escrow than owed - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` computes the escrow amount to release to a solver on a **fully-filled leg** by reading the *entire current balance* of `_orders[commitment][token]` rather than the amount proportional to that specific leg. Because `_orders` is keyed only by `(commitment, tokenAddress)` — not by leg index — an order whose `inputs` array references the same ERC-20 token in more than one leg (matched to different output legs) allows a solver to fully satisfy just one output leg and receive the **combined escrow of all legs sharing that input token**, while leaving the other leg(s) unfilled. This is analogous to the external report's core flaw: a privileged/insider-adjacent code path lets a party withdraw more value than it legitimately provided, moving funds to the wrong amount/beneficiary.

### Finding Description
In `_fillSameChain`: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

When a leg `i` reaches `amountFilled == totalRequired` (i.e., that specific output is fully paid), the code releases **the full current escrow balance for that token address**, not `order.inputs[i].amount`. `_orders` is a `mapping(bytes32 => mapping(address => uint256))` [2](#0-1)  aggregated purely by token address per commitment. If `order.inputs` contains the same token address at two different indices (e.g., `inputs[0].token == inputs[1].token == USDC`, each escrowed at placement and matched 1:1 by index to two different output legs, e.g. DAI and WETH), the escrow for both legs accumulates into the same `_orders[commitment][USDC]` slot.

A solver can call `fillOrder` providing output tokens sufficient to satisfy only leg `i=0` (the DAI leg) while providing zero for leg `i=1` (the WETH leg). Leg 0 hits `amountFilled == totalRequired`, so `escrowedAmount` is read as the **entire** `_orders[commitment][USDC]` balance — including the USDC meant to back the still-unfilled WETH leg. `_withdraw` is then called with `finalize = isFullyFilled` (false, since leg 1 is unfilled), but the escrow *transfer* for each token in `body.tokens` happens unconditionally regardless of `finalize`: [3](#0-2) . This sends the solver the whole USDC escrow for delivering only the DAI-side output, and zeroes out `_orders[commitment][USDC]`. The user's remaining unfilled leg (WETH) can never be filled or refunded correctly afterward: the second solver attempting to fill leg 1 will find `_orders[commitment][USDC] == 0` and hit `revert UnknownOrder()` in `_withdraw`, permanently locking/losing the portion of the user's funds that should have backed the WETH leg — funds that instead ended up with the first solver.

This requires no privileged role, no malicious relayer, prover, or governance actor — any unprivileged solver calling the public `fillOrder`/`_fillSameChain` path with a multi-leg order sharing an input token can trigger it.

### Impact Explanation
This is a direct loss-of-funds / wrong-amount bug in bridge/intent custody logic: a solver receives escrow beyond what it paid for, and the user's remaining order leg becomes irrecoverable (their escrow was already paid out to the wrong party in full). This matches the required impact classes "stealing or loss of funds" and "transaction manipulation / logic attacks," and is a direct code analog of the external report's theme — a party is able to withdraw more value than is properly attributable to it because per-unit accounting is coarser than the actual entitlement being tracked.

### Likelihood Explanation
Exploitability depends on the ability to construct an `Order` whose `inputs` array repeats the same ERC-20 token address across two or more legs mapped 1:1 to distinct output legs. Nothing in the reviewed `IntentsBase`/`IntrinsicIntents` code (within available context) validates that `order.inputs` token addresses are unique per leg, nor that `order.inputs.length == order.output.assets.length` is otherwise constrained beyond the implicit indexing assumption. Users construct and sign their own orders off-chain (or via the SDK) before `placeOrder`, and the fill path is fully public, so an attacker acting as "solver" only needs a user order (which the attacker could also construct/collude on, or find organically) with a duplicated input token across legs to trigger the drain. I was not able to fully verify from the retrieved context whether `placeOrder` or off-chain order construction (SDK) rejects duplicate-token-input orders — this should be confirmed by reading `placeOrder` in `evm/src/apps/IntentGatewayV2.sol` and the SDK order-building code, which I could not retrieve within the remaining tool budget.

### Recommendation
Track escrow per `(commitment, tokenAddress, legIndex)` instead of aggregating solely by `(commitment, tokenAddress)`, or explicitly compute the leg's own proportional share (`order.inputs[i].amount - alreadyReleased[i]`) rather than reading the entire current token balance when a single leg completes. Additionally, either reject `Order`s whose `inputs` array contains duplicate token addresses across legs at `placeOrder` time, or make the "read full balance on full-fill" shortcut safe by tracking per-leg escrow explicitly and only sweeping true rounding dust (a bounded, small residual) rather than the raw storage-mapped balance.

### Proof of Concept
1. User places a same-chain order with:
   - `inputs = [{token: USDC, amount: 1000}, {token: USDC, amount: 1000}]`
   - `output.assets = [{token: DAI, amount: 1000}, {token: WETH, amount: 1}]`
   
   At placement, `_orders[commitment][USDC]` accumulates to `2000`.
2. Solver A calls `fillOrder` (→ `_fillSameChain`) providing `options.outputs = [{token: DAI, amount: 1000}, {token: WETH, amount: 0}]`.
3. In the loop, `i=0` (DAI leg): `alreadyFilled=0`, `fillAmount=1000=totalRequired` → `amountFilled==totalRequired` → `escrowedAmount = _orders[commitment][USDC] = 2000` (not `1000`).
4. `i=1` (WETH leg): `solverAmount=0`, `remaining=1>0` → `isFullyFilled=false`, `continue`.
5. `_withdraw` is invoked with `body.tokens=[{USDC,2000},...]`, `finalize=false`. It unconditionally transfers `2000` USDC to Solver A and sets `_orders[commitment][USDC] = 0`.
6. `_filled[commitment]` is deleted (`isFullyFilled=false`), so the order is technically still "open," but any subsequent solver attempting to fill the WETH leg triggers `_withdraw` → `escrowed = _orders[commitment][USDC] = 0` → `revert UnknownOrder()`. The user's escrow meant to back the WETH leg (1000 USDC) has been paid entirely to Solver A, and the WETH leg can never be completed or its escrow refunded.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
