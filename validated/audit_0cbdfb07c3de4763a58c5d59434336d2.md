### Title
Unauthenticated `InternalSendTx` (and every other RPC) reachable on the Aggregator when `client_verification=false` — ([File: core/src/servers.rs], [File: core/src/rpc/interceptors.rs])

### Summary
`check_mainnet_requirements` only forces `client_verification=true` for the `Verifier` and `Operator` actor types, never for `Aggregator`, so an operator running the aggregator with `client_verification=false` is not flagged as an illegal mainnet configuration. In that state `create_grpc_server` installs `Interceptors::Noop`, which performs no certificate check at all, so the `leaf_cert == our_cert` guard that `is_internal` is meant to enforce for `Internal*` methods (including `InternalSendTx`) is never evaluated for the aggregator.

### Finding Description
The intended binding is: `caller_of(InternalSendTx) == aggregator_self_cert`, enforced by `is_internal(req) && leaf_cert == our_cert` in `only_aggregator_and_self`. [1](#0-0) [2](#0-1) 

This check is only wired up when the server is built with `Interceptors::OnlyAggregatorAndSelf`. `create_grpc_server` picks between `OnlyAggregatorAndSelf` and `Noop` purely based on `config.client_verification`: [3](#0-2) 

`Interceptors::Noop` simply passes every request through unchanged, so `is_internal` is never invoked and no certificate of any kind (aggregator, self, or attacker) is required: [4](#0-3) 

Critically, `create_aggregator_grpc_server` uses the exact same `create_grpc_server` path and, when `client_verification` is false, only logs nothing (it only warns when verification is *enabled*) — it does not refuse to start: [5](#0-4) 

And `check_mainnet_requirements`, the only guard meant to prevent unsafe production configuration, explicitly excludes `Actor::Aggregator` from the "must have client_verification" rule, only enforcing it for `Verifier | Operator`: [6](#0-5) 

So `client_verification=false` on the aggregator is a reachable, non-flagged configuration state. In that state, any unprivileged party with network access to the aggregator's gRPC port can call `InternalSendTx` (or any other `Internal*` method) with no TLS client certificate and no prior authorization, and it will be routed straight into `AggregatorServer`'s handler, which calls `self.tx_sender.insert_try_to_send(...)` to queue a caller-supplied raw transaction for fee-bumping/broadcast (the same pattern used in `send_emergency_stop_tx`, which performs an unconditional `insert_try_to_send` call with no additional authorization check beyond the interceptor layer): [7](#0-6) 

I was not able to view the exact `internal_send_tx` trait-method body in the truncated file (`core/src/rpc/aggregator.rs` is 2691 lines; only lines 1–1000 were retrievable), so I cannot cite its literal implementation, but the authorization gap that the question hinges on — `is_internal`/`leaf_cert == our_cert` never being evaluated — is fully confirmed at the interceptor/server-wiring layer, which is the actual root cause and is independent of exactly what `internal_send_tx` does with the parsed transaction.

### Impact Explanation
This is an unauthenticated state-changing/broadcasting call reaching the aggregator's internal transaction-submission pipeline — this matches the High severity category "an unauthenticated state-changing or broadcasting call" directly. It does not, by itself, demonstrate a path to spending a move-to-vault UTXO, crediting a false reimbursement, or forging an N-of-N signature (the attacker only controls `raw_tx`/`fee_type`, not the aggregator's musig2 session), so it doesn't reach the listed Critical categories on the evidence available. The repeatable, verifiable claim is: with this configuration, every `Internal*` method on the aggregator (not just `InternalSendTx`) loses its authorization check, since `Noop` is a blanket bypass, not one scoped to a single RPC.

### Likelihood Explanation
This requires the deployment to run the aggregator with `client_verification=false`, which is not blocked by `check_mainnet_requirements` for the `Aggregator` actor type (only `Verifier`/`Operator` are checked). All non-mainnet/regtest/testnet default configs in this repo set `client_verification=true`, so exploitability depends entirely on operator misconfiguration of the aggregator specifically — the code does not enforce this by design, and the mainnet safety-net has a gap exactly matching the actor type in question.

### Recommendation
Include `cli::Actor::Aggregator` in the `check_mainnet_requirements` `client_verification` check, and/or make `Interceptors::Noop` unconditionally reject any request whose `grpc-method` starts with `Internal`, so that disabling mTLS never silently removes the self-only guard on internal RPCs.

            raw_tx: attacker_crafted_tx_bytes(),
            fee_type: FeeType::Cpfp as i32,

        .await;

    // BEFORE fix: succeeds because Noop never checks leaf_cert == our_cert.
    assert!(resp.is_ok(), "unauthenticated caller reached InternalSendTx");

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
