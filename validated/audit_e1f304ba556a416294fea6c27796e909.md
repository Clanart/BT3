### Title
Unauthenticated `SendMoveToVaultTx` allows arbitrary caller to force move-to-vault broadcast timing - (File: core/src/rpc/aggregator.rs)

### Summary
`AggregatorServiceImpl::send_move_to_vault_tx` accepts a `raw_tx` and `deposit_outpoint` and, after only structural checks (input/output counts, output amounts, output script-pubkeys), forwards the transaction to `tx_sender` for broadcast, with no check that the caller is the aggregator's own automation path. [1](#0-0) [2](#0-1)  When `config.client_verification == false`, the gRPC server is wired with the `Noop` interceptor instead of `OnlyAggregatorAndSelf`, so any unauthenticated network caller can invoke this endpoint. [3](#0-2) 

### Finding Description
The broken binding is: "the party that decides when the presigned move-to-vault tx is broadcast" == "the aggregator's own controlled automation." In practice this equals "any TCP peer able to reach the aggregator's gRPC port," because authorization is enforced entirely by the transport-level interceptor selected in `create_grpc_server`, and that interceptor becomes `Interceptors::Noop` (a pass-through, `Ok(req)` for every request) whenever `config.client_verification` is `false`. [4](#0-3) [5](#0-4) 

Inside `send_move_to_vault_tx`, the only gates are: (1) automation feature must be compiled in, (2) the tx must deserialize with exactly 1 input / 2 outputs, (3) output[0] must equal `bridge_amount` to the N-of-N+security-council taproot address and output[1] must be a 0-sat anchor output. [6](#0-5)  None of these checks establish caller identity or that the caller is the aggregator's automation loop — they only validate the shape of a transaction that, by construction, could only have been produced by a valid N-of-N presigning ceremony (i.e., it was already legitimately generated earlier by `NewDeposit`). Once these format checks pass, the tx is unconditionally queued via `tx_sender.insert_try_to_send(..., FeePayingType::CPFP, ...)`, causing it to be broadcast. [7](#0-6) 

The gRPC proto documents this method as intended for use "by the clementine-backend service," i.e. an internal, trusted caller, not the public internet. [8](#0-7)  When `client_verification` is disabled, that trust boundary collapses to nothing, and the endpoint is reachable in full by any unprivileged network caller who has obtained (or reconstructed) a valid `raw_tx`/`deposit_outpoint` pair, forcing broadcast at a time of their choosing rather than the aggregator's intended deposit lifecycle.

### Impact Explanation
This matches the "High - an unauthenticated state-changing or broadcasting call" category: an unauthenticated caller can trigger the aggregator to broadcast a bridge transaction (move-to-vault UTXO creation) on their own schedule. [9](#0-8)  It does not itself let the attacker steal funds, redirect the move-to-vault output, or forge signatures — the transaction is a legitimately, fully N-of-N presigned move tx whose destination (bridge script-pubkey) and amount are independently re-validated by the handler. [10](#0-9)  The blast radius is per-deposit (repeatable for any deposit whose presigned move tx the attacker can obtain) but the impact is limited to timing control of an already-authorized action, not value theft or misallocation.

### Likelihood Explanation
This requires the deployment-level precondition `config.client_verification == false`, which is a configuration choice, not a code defect by itself, but the code makes the consequence of that misconfiguration a fully open, high-impact broadcast endpoint rather than a degraded/no-op one. [3](#0-2)  The attacker also needs an already-valid presigned `raw_tx` for a real deposit (obtainable by eavesdropping on `NewDeposit`'s response per the referenced prior finding, or via any other leak of that response). No BTC cost is required to call the RPC itself.

### Recommendation
Do not rely solely on TLS client-certificate interception for authorization of state-mutating/broadcast RPCs; add an explicit application-level authorization check in `send_move_to_vault_tx` (and other automation-triggering endpoints) that is enforced regardless of `client_verification`, or refuse to serve this RPC over `Noop` mode at all. At minimum, document/enforce that `client_verification=false` is only safe for fully isolated/local deployments, and consider gating `SendMoveToVaultTx` behind the same "Internal"-style method check used for `is_internal` in `core/src/rpc/interceptors.rs`.
