## Analysis

The confirmed mechanism: `DiffSelection` is a purely **positional** (line-index-based) data structure with no content binding — `isSelected(lineIndex)` and `divergingLines` are just integers with no association to the actual line text they were selected against. [1](#0-0)  When the working-directory diff is re-rendered after a file changes, the app explicitly acknowledges this danger and *remaps* selectable lines via `withSelectableLines`, but only in the interactive UI-refresh path `updateChangesWorkingDirectoryDiff`. [2](#0-1) 

Critically, the **commit path never goes through that reconciliation step**. `_commitIncludedChanges` takes the file selections directly out of `state.changesState.workingDirectory.files` (whatever was last computed, potentially against a stale diff the user is no longer looking at) and hands them to `createCommit`. [3](#0-2)  `createCommit` → `stageFiles` → `applyPatchToIndex` then calls `getWorkingDirectoryDiff` **again**, fetching a brand-new diff straight from the current on-disk file content, and feeds the old positional `file.selection` into `formatPatch` against these new hunks. [4](#0-3)  `formatPatch` blindly trusts `file.selection.isSelected(absoluteIndex)` against the hunk lines of this freshly-fetched diff, with no verification that the line at that index still corresponds to what the user actually reviewed. [5](#0-4) 

This is the same broken invariant as the SecondSwap `buyFee`/`sellFee` bug: **a value the user "locked in" at decision time (line selection, made against diff version A) is silently re-evaluated against a different, mutated version of the underlying data (diff version B) at execution time (commit), with no guard tying the two together.**

### Title
Stale line-selection indices are silently reapplied to a freshly re-fetched diff at commit time, causing wrong content to be committed — (`app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
Desktop's partial-commit ("stage selected lines") feature stores the user's line selection as raw integer indices (`DiffSelection`), decoupled from the diff content they were chosen against. The only code that revalidates these indices against a changed diff (`updateChangesWorkingDirectoryDiff`'s `withSelectableLines` remap) runs on the interactive UI-refresh path, not on the commit path. When the user actually commits, `applyPatchToIndex` re-fetches the diff from disk fresh and reuses the old, unvalidated selection indices to build the patch, so if the file content shifted between the last diff the user saw and the moment `git commit` executes, the wrong lines can be silently staged and committed.

### Finding Description
`DiffSelection.isSelected(lineIndex)` is purely index-based with no reference to the actual diff line content. [6](#0-5)  The app is aware selections can go stale — see the comment "the diff might have changed dramatically since last we loaded it" — and defensively remaps `selectableLines` whenever the on-screen diff is refreshed. [2](#0-1)  However, `_commitIncludedChanges` reads the working-directory file selections straight from cached repository state without first re-synchronizing them against a fresh diff. [7](#0-6)  Downstream, `createCommit` → `stageFiles` → `applyPatchToIndex` independently calls `getWorkingDirectoryDiff` to get the diff to apply, generating a second, potentially different, hunk/line layout than what backed the user's selection, and then blindly reuses the stale indices. [4](#0-3) 

An attacker who controls a cloned/fetched repository can trigger this window in ways that don't require local/physical access or malware already present: a smudge/clean filter declared in the repository's `.gitattributes` (invoked by the various background `git status`/`git diff` calls Desktop issues while the user is looking at a diff) can non-deterministically rewrite working-tree bytes between renders. Because Desktop performs multiple independent diff computations over time for the same file (UI refresh diff vs. commit-time diff) without pinning file content (e.g., by hashing/blob id) or re-validating selection indices against the diff actually being staged, a content shift introduced this way is silently absorbed into whatever the fresh `applyPatchToIndex` diff produces.

### Impact Explanation
This breaks the fundamental guarantee of the partial-commit feature: what the user visually selected for inclusion is what gets committed. A shifted diff can cause: unreviewed/attacker-influenced lines being silently included in a commit, or a line the user explicitly excluded from a commit (e.g. secrets, unrelated hunks) ending up committed anyway. Because Desktop commits (and often auto-pushes on subsequent flows) with no diff between the "presented" selection and the actually-staged patch, this is a silent corruption of what the user commits — matching the exact class of harm called out as valid impact.

### Likelihood Explanation
Moderate-to-low but plausible. It requires: (1) a partial (line-level, not whole-file) selection state, (2) the working tree file content changing between the last diff render backing that selection and the moment `applyPatchToIndex` recomputes the diff at commit time. Git attribute-driven filters and background refresh timers (`updateChangesWorkingDirectoryDiff` runs on selection change/focus events, independent from the commit trigger) make this window realistic without any local attacker action — only a maliciously crafted repository is needed.

### Recommendation
- Bind `DiffSelection` state to a content fingerprint (e.g., blob SHA or diff hash) of the diff it was computed against, and refuse/re-derive the selection if the underlying file/diff has changed by the time of commit.
- Before calling `createCommit`, re-run the same `withSelectableLines` remap/validation used in `updateChangesWorkingDirectoryDiff` against a diff freshly fetched at commit time, and if selection can't be safely mapped, fail the commit and prompt the user to re-review rather than silently substituting an approximate selection.
- In `applyPatchToIndex`, reuse the exact diff object the UI last displayed (passed down explicitly) instead of independently re-fetching a new one, or verify hunk/line-count parity before trusting old indices.

### Proof of Concept
Conceptual (not fully verifiable without live execution, since this requires timing a working-tree mutation triggered by a filter/hook from a crafted repository against Desktop's background diff refresh cadence):
1. Attacker publishes a repository with a `.gitattributes` entry wiring a `clean`/`smudge` filter for a tracked file that rewrites its content differently depending on invocation count or a timer.
2. Victim clones/opens the repo in Desktop, edits the file, and partially selects a subset of lines in the Changes diff view (`DiffSelection` recorded against diff version A).
3. Before the victim clicks "Commit", a background `git status`/`git diff` triggers the filter again, producing diff version B with shifted hunk boundaries (e.g., an extra blank line inserted upstream in the file).
4. Victim commits. `_commitIncludedChanges` passes the stale (version-A-based) selection indices straight through; `applyPatchToIndex` fetches diff version B and applies those indices to it via `formatPatch`. [4](#0-3)  Because hunk boundaries shifted, the indices now point at different lines than the user selected, and the wrong content is silently included in the commit.

Note: I was not able to fully trace whether Desktop's background diff refresh (`updateChangesWorkingDirectoryDiff`) fires often enough in practice to create this race outside of the explicit remap path, since I did not have execution access to time this against the commit button click; the code-level absence of any selection revalidation on the commit path itself is nonetheless directly confirmed in the cited source.

  /** Returns a value indicating the computed overall state of the selection */
  public getSelectionType(): DiffSelectionType {
    const divergingLines = this.divergingLines
    const selectableLines = this.selectableLines

    // No diverging lines, happy path. Either all lines are selected or none are.
    if (!divergingLines) {
      return this.defaultSelectionType
    }
    if (divergingLines.size === 0) {
      return this.defaultSelectionType
    }

    // If we know which lines are selectable we need to check that
    // all lines are divergent and return the inverse of default selection.
    // To avoid looping through the set that often our happy path is
    // if there's a size mismatch.
    if (selectableLines && selectableLines.size === divergingLines.size) {
      const allSelectableLinesAreDivergent = [...selectableLines].every(i =>
        divergingLines.has(i)
      )

      if (allSelectableLinesAreDivergent) {
        return this.defaultSelectionType === DiffSelectionType.All
          ? DiffSelectionType.None
          : DiffSelectionType.All
      }
    }

    // Note that without any selectable lines we'll report partial selection
    // as long as we have any diverging lines since we have no way of knowing
    // if _all_ lines are divergent or not
    return DiffSelectionType.Partial
  }

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
