### Title
`resolveWithin` boundary check uses bare string `startsWith` instead of a path-separator-aware comparison, allowing symlink escape to sibling directories - (File: app/src/lib/path.ts)

### Summary
`_resolveWithin` is the single containment guard used throughout Desktop to prevent a repository-relative path from escaping the repository root (used for the "Open in Desktop" `filepath` deep-link parameter and for the Copilot merge-conflict file reader). Its final check, `realResolved.startsWith(realRoot)`, is a bare string prefix test with no verification that a path separator (or end-of-string) immediately follows `realRoot`. Any real path whose string form merely begins with the same characters as the root — e.g. a sibling directory `myrepo.wiki` next to `myrepo` — passes the "is inside root" test even though it is a completely different directory tree. This mirrors the Limbo.sol finding: a single unguarded edge case in an invariant check silently defeats the entire protection.

### Finding Description
The containment guard is:
```
app/src/lib/path.ts:66-71
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

`resolve()` alone cannot be escaped by `..` segments, so the guard's real purpose (as its comment states, "Guard against path traversal and symlink escapes") is to catch the case where a symlink *inside* the repository resolves, via `realpath`, to a location outside the repository. That symlink-escape test only calls `realResolved.startsWith(realRoot)` — it never checks that the byte after `realRoot` in `realResolved` is a path separator or that the strings are equal length. Consequently, `realRoot = ".../GitHub/myrepo"` and `realResolved = ".../GitHub/myrepo.wiki/secret.md"` satisfy `startsWith`, even though `myrepo.wiki` is a sibling directory, not a subdirectory of `myrepo`.

This exact function is reused by two independent consumers that both take attacker-influenceable paths:

1. **Open-in-Desktop deep link.** `dispatcher.ts` resolves the `filepath` query parameter of an `x-github-client://openRepo/...` URL against the freshly cloned repository root:
```
app/src/ui/dispatcher/dispatcher.ts:1957-1972
if (filepath !== null) {
  if (isAbsolute(filepath)) { ... return }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } ...
}
``` [2](#0-1) 
`filepath` itself is only checked for being non-absolute (`isAbsolute`), not for symlink escapes — that responsibility is delegated entirely to `resolveWithin`.

2. **Copilot merge-conflict context builder** — the stronger primitive, because it actually reads file bytes rather than just revealing a path in Finder/Explorer:
```
app/src/lib/copilot-conflict-context.ts:390-438
absolutePath = await resolveWithin(workingDirectory, file.path)
...
content = await readFile(absolutePath, 'utf8')
``` [3](#0-2) 
`file.path` is the repository-relative path of a conflicted file surfaced from the working tree during a merge/rebase; an attacker who controls the cloned/fetched repository can place a symlink at that path.

### Impact Explanation
An attacker who controls a repository the victim clones (or a fork/branch fetched during a PR checkout) can commit a symlink whose relative target climbs out of the repo and lands in a sibling directory that merely shares the root directory's name as a string prefix (a very common real-world case: GitHub wiki repos are conventionally cloned as `<repo>.wiki` right next to `<repo>`, and users commonly keep numbered/backup clones like `<repo>-old`, `<repo>2`, etc. in the same parent folder). When Desktop later resolves a repository-relative path against that repo root — either via the "Open in Desktop" `filepath` deep link or via the Copilot conflict-resolution feature — `resolveWithin` incorrectly treats the sibling directory as "inside" the repository, defeating the guard's stated purpose. Through the Copilot path this results in the *content* of a file outside the repository (e.g., from `<repo>.wiki`) being read into memory and forwarded as model context — a read of arbitrary content outside the intended repository boundary, matching the "file read outside the repo" impact class.

### Likelihood Explanation
The victim only needs to (a) clone/open an attacker-authored repository that contains a crafted symlink, and (b) either click a normal-looking "Open in Desktop"/`openRepo` link or hit a merge/rebase conflict in that repository while a same-parent sibling directory whose name extends the repo's name exists (wiki clones being the most natural occurrence). No admin rights, local access, or pre-existing malware are required — this is exactly the unprivileged "attacker controls a cloned/fetched repository" + "a link the user clicks" primitive the report scope calls out. The existing tests only exercise the "escape-then-return" and "escape entirely" symlink cases, not the sibling-prefix boundary case, so the bug is not caught by current unit tests. [4](#0-3) 

### Recommendation
Change the containment check in `_resolveWithin` to require a path-separator boundary (or exact equality) after the root, e.g.:
```
const sep = require('path').sep
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
using the platform-appropriate separator from the `options` object (`Path`, `Path.posix`, or `Path.win32`) rather than the ambient OS separator, and add a regression test with a sibling directory such as `<root>.evil` to lock in the fix.

### Proof of Concept
1. Attacker publishes a repository `octocat/Hello-World` and separately controls or knows the victim will also have `Hello-World.wiki` cloned in the same parent folder (Desktop's default clone location groups repos by parent org/user folder).
2. Inside `Hello-World`, the attacker commits a symlink `leak -> ../Hello-World.wiki/secret.md` (relative target, valid git symlink blob).
3. Victim clones `Hello-World` via Desktop, then clicks a link:
   `x-github-client://openRepo/https://github.com/octocat/Hello-World?filepath=leak`
4. `parseAppURL` accepts `filepath=leak` (not absolute, passes the `testForInvalidChars`/`isAbsolute` checks). [5](#0-4) 
5. `openRepositoryFromUrl` calls `resolveWithin(repository.path, 'leak')`. `realpath` follows the symlink to `.../Hello-World.wiki/secret.md`; `realRoot` is `.../Hello-World`. `realResolved.startsWith(realRoot)` is `true` because `"…/Hello-World.wiki/secret.md".startsWith("…/Hello-World")` even though `.wiki` is a sibling, not a subdirectory — the guard passes incorrectly.
6. In the deep-link path this reveals the out-of-repo file via `shell.showItemInFolder`; in the Copilot conflict-context path (same `resolveWithin` call with a symlink placed at a conflicted file's path) the out-of-repo file's *contents* are read via `readFile` and returned in `IFileConflictContext.rawContent`, exfiltrating data outside the repository boundary that the guard was meant to enforce. [6](#0-5)
