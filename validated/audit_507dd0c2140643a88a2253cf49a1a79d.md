Based on the exploration, the closest local analog to the "address ownership doesn't carry across chains" bug class is in the relayer fee withdrawal path in `pallet-relayer`, where a cross-chain beneficiary redirect address is accepted and later used to pay funds on a different chain without validating that the address bytes are the correct format/length for that destination chain type.

### Title
Unvalidated cross-chain `beneficiary_address` length in relayer fee withdrawal can misdirect/lose relayer fees on EVM destinations - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-relayer::withdraw()` lets a relayer redirect their accumulated fee payout to an arbitrary `beneficiary: Option<Vec<u8>>` address that is not required to match the destination chain's native address format. For substrate destinations the code strictly validates the beneficiary is exactly 32 bytes via `AccountId32::try_from`, but for EVM destinations the same raw bytes are passed straight into `WithdrawalParams` with no length check, mirroring the Beanstalk report's core flaw: an identity/address representation from one chain domain being reused on another domain without verifying it actually resolves to the same controlled account there.

### Finding Description
`Pallet::<T>::withdraw` computes the payout beneficiary as: [1](#0-0) 

For the substrate branch, the beneficiary bytes are strictly parsed into a 32-byte `AccountId32`, so malformed input errors out: [2](#0-1) 

For the non-substrate (EVM) branch, the raw `beneficiary_address: Vec<u8>` is forwarded unchecked into `WithdrawalParams` for ABI encoding, with no assertion that it is a valid 20-byte EVM address: [3](#0-2) 

The origin of this redirect address is the cross-chain "beneficiary_details" mechanism in fee accumulation, which is explicitly designed to let a relayer whose delivery key is only valid on one chain family (e.g., an Sr25519/Ed25519 substrate key) redirect their EVM-chain fee credit to a different address, authenticated only by a signature over `(nonce, state_machine, beneficiary)`: [4](#0-3) [5](#0-4) 

Because the signature scheme only binds the beneficiary to a signer key — not to a correctly-shaped destination address — a relayer (or a client-side bug producing malformed beneficiary bytes) can register/withdraw with a beneficiary value whose byte length or encoding does not correspond to a real, controllable EVM address (e.g., a 32-byte substrate public key). The `withdraw()` extrinsic doc explicitly acknowledges this is "fire and forget": the fee ledger is zeroed once the ISMP message is dispatched, and the actual payout correctness is left entirely to whatever address bytes end up on the destination chain: [6](#0-5) 

This is the direct analog of the Beanstalk report: an address value that is valid/owned in one chain's addressing scheme is propagated and consumed on a different chain without a check that the same account/format actually controls it there, and once the local ledger entry (the fertilizer NFT / relayer fee balance) is zeroed/consumed, the value effectively becomes unrecoverable if the destination address turns out to be wrong or uncontrolled.

### Impact Explanation
If the destination-side EVM contract decodes/truncates the oversized or malformed `beneficiary_address` bytes into an `address` type (a standard ABI/Solidity operation such as `address(bytes20(...))`), the resulting EVM address is effectively arbitrary and not necessarily controlled by the relayer who earned the fee. Since `Fees::<T>` is zeroed at the pallet layer regardless of what happens downstream, this results in a genuine loss of already-accrued relayer rewards — funds are dispatched to an address nobody can access, matching the bounty's "loss of funds" and "wrong beneficiary or amount" impact categories.

### Likelihood Explanation
Exploitation requires no privileged role: any relayer who has accrued fees can call `withdraw()` (via `WithdrawalInputData`) with a `beneficiary` of the wrong shape for the chosen `dest_chain`, either by mistake in off-chain tooling or by deliberately supplying a malformed address for griefing/anomalous-state testing. The substrate branch is protected by a length check, but the EVM branch has no equivalent guard, so this is a straightforward missing-validation bug reachable through the pallet's public extrinsic path — not one requiring a malicious relayer/prover/admin collusion beyond the normal-permission relayer role that is expected to call this function anyway.

### Recommendation
Add an explicit length/format check on `beneficiary_address` matching the target `dest_chain` type before dispatching the withdrawal message — e.g., require exactly 20 bytes (and reject non-checksummed/zero addresses) for EVM destinations, symmetric to the existing `AccountId32::try_from` 32-byte check used for substrate destinations. Reject the extrinsic with a descriptive error (e.g., `InvalidBeneficiaryFormat`) rather than allowing the ISMP message to be dispatched with unvalidated bytes.

### Proof of Concept
1. A relayer accrues fees for delivering messages to an EVM-destination chain, tracked in `Fees::<T>::get(dest_chain, address)`.
2. The relayer (or buggy client code) calls the withdraw extrinsic with `WithdrawalInputData { signature: Signature::Sr25519 { public_key, .. }, dest_chain: <EVM chain>, beneficiary: None }`.
3. In `withdraw()`, `beneficiary_address = withdrawal_data.beneficiary.unwrap_or(address.clone())` — `address` is the 32-byte Sr25519 public key (see `modules/pallets/relayer/src/withdrawal.rs:82-86`).
4. Since `dest_chain` is EVM, the match falls into the `_` arm, and the 32-byte value is packed into `WithdrawalParams { beneficiary_address, amount, token }.abi_encode()` with no length validation (`modules/pallets/relayer/src/withdrawal.rs:144-158`).
5. `Fees::<T>` for this relayer/chain pair is zeroed and the ISMP message is dispatched to the destination `HostManager`/`EvmHost::withdraw` (`evm/src/core/HostManager.sol:95-104`), which is expected to interpret the beneficiary as a 20-byte EVM address.
6. If the destination decodes/truncates the oversized bytes into an `address`, the resulting address is not one the relayer controls — the fee is unrecoverably lost even though the pallet-side ledger already recorded it as paid out. [7](#0-6)

//!
//! Once fees have been accumulated into [`crate::pallet::Fees`] by
//! [`crate::accumulate`], relayers withdraw them via [`Pallet::withdraw`].
//! The flow:
//!
//! 1. The relayer signs a `(nonce, dest_chain, beneficiary?)` payload with their per-chain key (EVM
//!    secp256k1 / sr25519 / ed25519).

//!    POST request to the destination's host manager (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate)
//!    instructing it to disburse `available_amount` of the fee token to the beneficiary.
//! 3. The `Fees` entry is zeroed so the same balance cannot be withdrawn twice.
//!
//! The on-chain effect is just dispatching the message; the destination chain settles the

		let address = match &withdrawal_data.signature {
			Signature::Evm { address, .. } => address.clone(),
			Signature::Sr25519 { public_key, .. } => public_key.clone(),
			Signature::Ed25519 { public_key, .. } => public_key.clone(),
		};

		let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
		let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());

		match &withdrawal_data.signature {
			Signature::Evm { address, .. } => {
				let eth_address = withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
				if &eth_address != address {
					Err(Error::<T>::InvalidPublicKey)?
				}
			},
			Signature::Sr25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
			Signature::Ed25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
		};
		let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());

		if available_amount <
			Self::min_withdrawal_amount(withdrawal_data.dest_chain)

			Ok::<(), ()>(())
