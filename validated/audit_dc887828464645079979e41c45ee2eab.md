## Analysis

I found a real Agave analog to the "lastGoodPrice updates during divergence" bug class: `apply_state_changes` in `core/src/repair/cluster_slot_state_verifier.rs` can persist a bank hash into blockstore as an "unconfirmed anchor" even in the very same state-change batch where the slot has just been flagged as a cluster mismatch (`MarkSlotDuplicate`), because `MarkSlotDuplicate` does not clear the pending write, mirroring how `OracleAdapterV4` updates `lastGoodPrice` in the same refresh flow that trips the divergence circuit breaker.

### Title
Blockstore persists an unconfirmed/mismatched bank hash as the local "confirmed" anchor in the same batch that flags the slot as duplicate - (File: `core/src/repair/cluster_slot_state_verifier.rs`)

### Summary
`on_frozen_slot` builds a `Vec<ResultingStateChange>` that, for a slot with no prior cluster confirmation, always begins with `BankFrozen(frozen_hash)` and then, if `is_slot_duplicate` is true, appends `MarkSlotDuplicate(frozen_hash)` in the same batch. `apply_state_changes` processes `BankFrozen` by setting a local `not_duplicate_confirmed_frozen_hash = Some(bank_frozen_hash)` and, at the end of the loop, unconditionally persists it via `blockstore.insert_bank_hash(slot, frozen_hash, false)` unless a later `DuplicateConfirmedSlotMatchesCluster` change cleared it. Critically, the `MarkSlotDuplicate` arm never resets `not_duplicate_confirmed_frozen_hash`, so a slot that is simultaneously frozen and flagged as duplicate still gets its (disputed) hash written to blockstore as the local recorded bank hash. [1](#0-0) [2](#0-1) 

### Finding Description
The state machine that tracks per-slot consensus status (`SlotStateUpdate` / `ResultingStateChange`) computes a batch of changes and then applies them all via `apply_state_changes`. In that function:

```
BankFrozen(bank_frozen_hash) => {
    if !fork_choice.is_duplicate_confirmed(&(slot, bank_frozen_hash)) ... {
        not_duplicate_confirmed_frozen_hash = Some(bank_frozen_hash);
    }
}
MarkSlotDuplicate(bank_frozen_hash) => {
    fork_choice.mark_fork_invalid_candidate(&(slot, bank_frozen_hash));
    // does NOT clear not_duplicate_confirmed_frozen_hash
}
...
if let Some(frozen_hash) = not_duplicate_confirmed_frozen_hash {
    blockstore.insert_bank_hash(slot, frozen_hash, false);
}
``` [3](#0-2) 

`on_frozen_slot` is the producer of exactly this combination: whenever `is_slot_duplicate` is true and there is no stronger `cluster_confirmed_hash` signal available yet, it emits `[BankFrozen(frozen_hash), MarkSlotDuplicate(frozen_hash)]` together. [1](#0-0) 

`is_slot_duplicate` originates purely from `duplicate_slots_tracker.contains(&slot)`, which is populated the moment a `SlotStateUpdate::Duplicate` signal (from a Turbine/WindowService duplicate-shred detection) has been processed once, well before any duplicate-confirmation or epoch-slots agreement threshold is reached. [4](#0-3) [5](#0-4) 

This is functionally the same broken invariant as the report: a value meant to represent a "verified/confirmed" anchor (`lastGoodPrice` in the oracle case; the recorded bank hash in blockstore for this slot) gets written using data from the very refresh cycle in which a mismatch/divergence with the rest of the network was detected, because the "divergence detected" branch does not suppress or invalidate the "record as good" branch that runs in the same pass.

### Impact Explanation
`insert_bank_hash(slot, frozen_hash, false)` writes the local bank hash for the slot into blockstore even though the slot has simultaneously been marked duplicate by `mark_fork_invalid_candidate`. Later code paths (e.g. ancestor-hashes-service integrity checks in `handle_sampled_validators_reached_agreement`, and `check_slot_agrees_with_cluster`/`BankStatus::Frozen` lookups) treat `blockstore.get_bank_hash(slot)` as the local "frozen" record and compare it against cluster-agreed hashes to decide dump/repair actions and to detect impossible mismatch sequences. [6](#0-5) 
Because a disputed/duplicate-flagged hash is stored there without any explicit "not yet confirmed" or provisional marker distinguishing it from a hash that was frozen without any duplicate signal, downstream logic that depends on `blockstore.get_bank_hash` (e.g. ancestor sample integrity assertions, which `panic!` on "impossible" mismatch patterns) can be driven into unexpected states, and stale/incorrect bank-hash bookkeeping can persist through the repair/dump cycle if the freeze-vs-duplicate race isn't otherwise re-triggered. This is a data-integrity/bookkeeping gap in the consensus-safety machinery rather than a direct fund-theft path, so severity is best characterized as low/medium relative to the guarded invariant.

### Likelihood Explanation
Both a `BankFrozen` and a `MarkSlotDuplicate` change require the slot to have been (a) processed by replay/freeze and (b) previously observed as duplicate via `duplicate_slots_tracker`, which happens naturally whenever Turbine delivers two shreds for the same slot index with different content (a routine, low-cost, single-slot duplicate-shred event, not requiring any privileged/malicious-validator assumption beyond ordinary duplicate-block propagation already handled elsewhere in the same file). This occurs on the standard freeze path (`replay_stage.rs` `process_replay_results`), so the condition is reachable under normal validator operation whenever a duplicate block is seen before/around freeze time. [7](#0-6) 

### Recommendation
In `apply_state_changes`, clear `not_duplicate_confirmed_frozen_hash` (or otherwise skip the `insert_bank_hash` call) whenever a `MarkSlotDuplicate` change for the same hash is present in the batch, so a hash that has been identified as conflicting with the cluster is never persisted as the "current" bank hash without an explicit marker that it is disputed. Alternatively, only call `insert_bank_hash` after the loop has confirmed no `MarkSlotDuplicate`/dump-triggering change occurred for that slot in the same batch.

### Proof of Concept
1. A validator freezes slot `S` and computes hash `H` locally, with no prior cluster-confirmed hash for `S` yet, but `duplicate_slots_tracker` already contains `S` (i.e., a duplicate-shred notification for `S` arrived via Turbine before/around freeze, calling `check_slot_agrees_with_cluster` with `SlotStateUpdate::Duplicate`).
2. `on_frozen_slot` is invoked with `is_slot_duplicate == true` and `cluster_confirmed_hash == None`, producing `state_changes = [BankFrozen(H), MarkSlotDuplicate(H)]`. [8](#0-7) 
3. `apply_state_changes` processes `BankFrozen(H)` first, setting `not_duplicate_confirmed_frozen_hash = Some(H)`, then processes `MarkSlotDuplicate(H)`, which only calls `fork_choice.mark_fork_invalid_candidate` and does not clear the pending flag. [9](#0-8) 
4. After the loop, since `not_duplicate_confirmed_frozen_hash` is still `Some(H)`, `blockstore.insert_bank_hash(S, H, false)` is executed, persisting `H` as the recorded bank hash for `S` in the same pass that marked `S` as duplicate/invalid for fork choice. [10](#0-9)
