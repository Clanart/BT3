### Title
Pointer-contract addresses are derived via plain `CREATE` from a single shared module nonce, making address prediction unreliable and funds sent to a predicted pointer address can land in an unrelated contract - (File: x/evm/keeper/pointer_upgrade.go)

### Summary
`UpsertERCPointer` deploys every ERC20/CW20/CW721/CW1155 pointer contract with the plain `CREATE` opcode using the EVM-mapped module address as the deployer, so the resulting contract address is `keccak(rlp(evmModuleAddress, nonce))` — a purely nonce-dependent address exactly like the `createClone`/`PositionFactory` pattern described in the referenced Frankencoin report.

### Finding Description
`UpsertERCPointer` computes the pointer contract address with `evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))` rather than `CREATE2` with a deterministic salt tied to the pointee (token/denom/cw-address). [1](#0-0) 
Because `evmModuleAddress` is a single, chain-wide account shared by *all* pointer types (native, CW20, CW721, CW1155) for *all* users, its nonce is a global counter incremented by every unrelated pointer-registration transaction on the chain, not one scoped to the specific token/denom being pointed. [2](#0-1) 
The integration test suite explicitly relies on `eth_call`-style address prediction ahead of transaction inclusion: `pointer.addNativePointer.staticCall(denom)` is used to predict the address, and only afterward is the real transaction submitted: [3](#0-2) 
This is the same pattern flagged in the referenced report: address derivation depends only on a mutable nonce, so anything that changes the nonce between prediction and confirmation (another `addNativePointer`/`addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` call landing first, transaction reordering, or a reorg) causes the actually-deployed contract to land at a *different* address than the one predicted and acted upon by the client — and conversely, some *other* pointee's pointer contract can be deployed at the address the original caller predicted for their own token.

### Impact Explanation
If a caller (or downstream tooling) predicts the pointer address via `staticCall`/simulation and sends native `usei`/`wei` value to that predicted address before the real registration transaction is included (e.g., to pre-fund an anticipated contract, or simply because a wallet/integration displays and uses the predicted address optimistically), a reorg or even ordinary mempool reordering of concurrent pointer-registration transactions from any other user can consume the expected nonce slot first. The value transfer then lands on an address that is either still an EOA-like account or that later receives a completely unrelated pointer contract's bytecode, permanently orphaning the sent funds from the intended pointer/denom, since the pointer contracts have no mechanism to reconcile or refund value sent prior to their deployment. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Unlike the original report's single-user reorg scenario, this shared-nonce design makes the address-shift condition trigger under *any* unrelated pointer creation on the chain (native, CW20, CW721, or CW1155, for any token, by any user), not only during a rare chain reorg. Given the pointer precompile is a public, permissionless, unprivileged-user-reachable EVM entry point (`0x100b`) and the test suite itself demonstrates the "predict-then-act" pattern, the preconditions for divergence between predicted and actual address are realistically reachable by ordinary chain activity, not just black-swan reorg events.

### Recommendation
Deploy pointer contracts via `CREATE2` with a salt derived from the pointee identifier (token denom / CW20 address / CW721 address / CW1155 address) instead of plain `CREATE` off a shared, globally-incrementing module nonce, so the resulting address is deterministic per-pointee and independent of unrelated transaction ordering or reorgs.

### Proof of Concept
1. Attacker/observer watches the mempool or simply issues `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer`/`addNativePointer` calls in rapid succession for arbitrary tokens/denoms they control.
2. A victim predicts their pointer's address via `pointer.addNativePointer.staticCall(denom)` (as shown in the test at [4](#0-3) ) and sends native value to that predicted address, or a downstream contract records/uses that predicted address before the victim's `addNativePointer` transaction is actually included.
3. Before the victim's transaction is included, one of the attacker's own pointer-registration transactions is included first (via normal block ordering, or surviving a reorg while the victim's tx does not), consuming the `evmModuleAddress` nonce slot the victim's prediction assumed.
4. `UpsertERCPointer` at [5](#0-4)  deploys the attacker's pointer contract at the address the victim had predicted and sent funds to; the victim's pointer for their own denom is deployed at a different address, and any value sent to the originally-predicted address remains stranded/inaccessible to the victim.
