### Title
PedPoP `Commitments::read` / `ThresholdKeys::new` accept identity points and never reject an attacker-controlled group key, letting a DKG participant force an unspendable or fully-known threshold key - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
The report's bug class is a function that *presents itself* as the checked variant (`safeMint`) while actually invoking the unchecked operation (`mint`), so assets can be delivered to a recipient that can never use them. Serai has the same shape: every point deserialization in the PedPoP DKG and in `ThresholdKeys::read` uses `Ciphersuite::read_G`, which validates canonicity and torsion but **does not reject the identity point**, even though the same codebase deliberately ships the checked variant — `Curve::read_G` rejects identity — and applies "unusable key" rejection everywhere else. The result is that a participant can feed the DKG commitments / verification shares that yield an unusable (identity or attacker-known) group key, and the threshold address then receives funds that are unspendable or stealable.

### Finding Description
- `ciphersuite::Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) rejects non-canonical and non-torsion-free points but accepts the identity element.
- `frost::Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) is the "safe" variant explicitly documented as "Read a point from a reader, rejecting identity" — i.e., the codebase acknowledges identity points must be refused in key-like positions.
- PedPoP, however, is generic over `Ciphersuite` (not `Curve`), so every read path falls back to the unchecked `Ciphersuite::read_G`:
  - `Commitments::read` (`crypto/dkg/pedpop/src/lib.rs:115-127`) — all `t` coefficient commitments, including the constant coefficient `commitments[0]` used as the PoK public key, may be the identity.
  - `EncryptionKeyMessage::read` (`crypto/dkg/pedpop/src/encryption.rs:57-59`) — the ECDH `enc_key` may be the identity.
  - `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:620-623`) — all `verification_shares` may be identity.
- `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-390`) computes `group_key` by interpolating the first `t` verification shares but never checks `group_key != identity` — despite `ThresholdKeys` being the sole root of trust that downstream gets turned into the network's multisig address.
- In `verify_r1` (`crypto/dkg/pedpop/src/lib.rs:300-338`) the only check on a commitment message is a Schnorr proof of knowledge against `commitments[0]`. A PoK over the identity trivially verifies (`SchnorrSignature::sign(0, r, c)` produces `R = s·G`, and `verify` checks `R + c·A − s·G = 0` which holds with `A = identity`). Proving *knowledge* of a discrete log does not prevent choosing a cancelling value — a participant who observes the honest participants' broadcast commitments before publishing their own can set their constant coefficient to `target − Σ a_j[0]` for any `target` scalar they choose, satisfy the PoK, and thereby fully determine the interpolated group key.

### Impact Explanation
- **Identity group key → unspendable funds**: by choosing a cancelling constant coefficient, an attacker participant forces `group_key = identity` (secret key 0). `ThresholdKeys::new` accepts this silently. Downstream, Serai registers the resulting key as the multisig's address; any funds sent to it are permanently frozen (or trivially signable by anyone, since the discrete log is publicly 0). This is the exact consequence of the original report: an asset delivered to a recipient incapable of using it, while the code path appeared to be the validated one.
- **Attacker-known group key → theft**: the same rushing choice of `target` lets the attacker set the group key to any point whose discrete log they know, giving them unilateral signing ability over the threshold wallet — a key-compromise impact realized purely through `Commitments::read` bytes sent by an unprivileged DKG participant.
- The inconsistency demonstrates the missing check is not intended behavior: `Curve::read_G`, `Signed::read` (which rejects identity `R`), and `PublicKey::new`/`Eventuality::read` (which error on "unusable key") all reject degenerate keys elsewhere in the same codebase.

### Likelihood Explanation
An unprivileged DKG participant reaches this path directly: `Commitments`/`EncryptionKeyMessage` bytes are the protocol's public input, read via `Commitments::read` in `verify_r1`. No honesty assumption on other participants is required — the attacker's own malformed/cancelling commitment message is sufficient, and the PoK does not stop it because it only proves knowledge of the scalar, not that the scalar wasn't chosen after seeing others' commitments (rushing within a broadcast round). Thresholds/collusion are not needed.

### Recommendation
- Use an identity-rejecting point read (equivalent of `Curve::read_G` / `safeMint`) for all PedPoP inputs: `Commitments` coefficients, `EncryptionKeyMessage::enc_key`, `EncryptedMessage::key`, and `ThresholdKeys::read`'s `verification_shares`.
- In `ThresholdKeys::new`, reject a `group_key` that `is_identity`, and in `ThresholdKeys::read` re-validate that the loaded `group_key` is non-identity.
- Bind each participant's commitments to a commit-before-reveal phase (or equivalent round structure) so a participant cannot select cancelling coefficients after observing others' commitments; the PoK alone is insufficient.

### Proof of Concept
1. Attacker (participant `k`) runs `KeyGenMachine` and waits for all honest `EncryptionKeyMessage<Commitments>` broadcasts on the authenticated channel.
2. Attacker computes `S = Σ_j commitments_j[0]` over honest constant commitments, then sets own constant coefficient `a'[0] = -dl_target` chosen such that the interpolated group key becomes `identity` (or `target·G` for a `target` they know): specifically they build a polynomial `f'(x)` whose constant coefficient is the needed canceller, publish `commitments[0] = a'[0]·G`, and attach a valid PoK `SchnorrSignature::sign(a'[0], r, challenge(...))` — `verify_r1` accepts it since `msg.sig.verify(commitments[0], c)` holds.
3. In the degenerate form, the attacker can additionally submit all-`identity` commitments (`f'(x) = 0`), which `Commitments::read` accepts because `C::read_G` (Ciphersuite) never calls the identity check that `frost::Curve::read_G` performs, and the PoK with `private_key = 0` verifies.
4. `KeyMachine::calculate_share` → `ThresholdKeys::new` computes `group_key = Σ verification_shares[i]·λ_i` with no `is_identity`/known-key check; the resulting `ThresholdKeys` serialize, register a group address, and deposits are sent to a key either publicly known (`0`) or known only to the attacker — funds frozen or stolen, matching the "minted to an incapable recipient" impact of the original issue.
