Confirmed: `vote`, `unvote`, and `castVotes` in `WombatBribeManager.sol` carry no `onlyOwner`/`nonReentrant`/cooldown restrictions — any vlMGP-locked EOA can call all three in the same transaction/block. Combined with `BaseRewardPoolV2`'s instant, non-time-weighted reward distribution model, the attack described is valid.

### Title
Instant snapshot-based bribe distribution allows JIT vote/unvote to steal pro-rata share of bribes with zero time-weighted contribution - (File: rewards/BaseRewardPoolV2.sol, rewards/BribeRewardPool.sol, wombat/WombatBribeManager.sol)

### Summary
`BribeRewardPool` (via `BaseRewardPoolV2._provisionReward`) distributes bribe rewards by instantly increasing `rewardPerTokenStored` proportional to `totalStaked()` (i.e. `BribeRewardPool.totalSupply`) at the exact moment `queueNewRewards` is called, with no time-weighting or streaming (`rewards/BaseRewardPoolV2.sol:290-314`). Because `WombatBribeManager.vote`, `castVotes`, and `unvote` are all unrestricted public functions (`wombat/WombatBribeManager.sol:182,223,241`), any vlMGP holder can call `vote()` to inflate a pool's `totalSupply` immediately before triggering `castVotes()` (which harvests and queues bribes via `queueNewRewards`), then call `unvote()` with `claim=true` in the same block to capture a share of the harvested bribe proportional to their instantaneous balance, despite having contributed zero real historical voting weight to the bribe accrual period.

### Finding Description
`BribeRewardPool.stakeFor`/`withdrawFor` maintain their own `totalSupply`/`_balances` (`rewards/BribeRewardPool.sol:18-19,57-85`), decoupled from `BaseRewardPoolV2.totalStaked()`'s default MasterMagpie-balance implementation, and are driven solely by `onlyOperator` (the `WombatBribeManager`) calls originating from user-callable `vote`/`unvote`.

The reward-per-token accounting in `_provisionReward` (`rewards/BaseRewardPoolV2.sol:290-314`) computes:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
```
This is a single instantaneous update based on the current `totalStaked()` snapshot — there is no `rewardRate`/`periodFinish` streaming (unlike Synthetix-style pools) and no checkpoint of balance history. `_earned` (`rewards/BaseRewardPoolV2.sol:316-321`) then pays each account `balance * (rewardPerToken - userRewardPerTokenPaid)`, meaning whoever holds balance at the exact instant `queueNewRewards` fires earns a full pro-rata share, regardless of whether they held that balance for one block or one year.

`WombatBribeManager.castVotes` (`wombat/WombatBribeManager.sol:241-296`) is `public` with no access control, and internally calls `wombatStaking.vote(...)` which calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)` (`wombat/WombatStaking.sol:411`) using bribe rewards actually harvested from Wombat's external bribe contracts (accrued based on votes cast in the *previous* `castVotes` cycle — independent of any vote delta submitted in the current call). `WombatBribeManager.vote` (`wombat/WombatBribeManager.sol:182-220`) and `unvote` (`wombat/WombatBribeManager.sol:223-237`) are likewise unrestricted and carry no cooldown, minimum holding period, or block-based checkpoint requirement.

Exploit flow (single transaction, e.g. via an attacker contract, or same-block sequence):
1. Attacker (holding any amount of vlMGP voting power) calls `vote()` on a target pool with a positive delta, which calls `BribeRewardPool.stakeFor` → increases `totalSupply` and `_balances[attacker]`, and syncs `userRewardPerTokenPaid[attacker]` to the *current* (pre-harvest) `rewardPerTokenStored`.
2. Attacker calls `castVotes()` (public, callable by anyone) → `wombatStaking.vote` harvests bribes accrued from Wombat's real voter/bribe contracts and calls `queueNewRewards`, which bumps `rewardPerTokenStored` using `totalStaked()` that now includes the attacker's freshly added stake from step 1.
3. Attacker calls `unvote()` with `claim=true` → `BribeRewardPool.withdrawFor(..., true)` runs `updateRewards` (crediting attacker `balance * (new rewardPerToken - old paid)`) then `_getReward` transfers the earned bribe tokens immediately, and removes the attacker's stake/vote.

No modifier, reentrancy guard, or accounting mechanism prevents this: `updateRewards`/`updateReward` only synchronize per-token indices at each call, they do not distinguish "how long" a balance has been present since the last distribution. `unvote` only requires `pool.isActive` to be true; it enforces no minimum vote duration.

### Impact Explanation
This is theft of unclaimed yield: the attacker captures bribe tokens proportional to a stake they held for effectively zero time (one transaction/block), diluting the payout owed to genuine long-term voters who actually contributed the voting weight that caused Wombat's external bribe contracts to accrue the harvested rewards in the first place. This matches the Immunefi impact class "theft of unclaimed yield" and is a direct value transfer from honest depositors to the attacker with no attacker capital lockup beyond momentarily holding voting power they already control (no real token transfer of the underlying vlMGP is even required, since `stakeFor`/`withdrawFor` are purely internal accounting operations on already-locked voting power).

### Likelihood Explanation
Preconditions are minimal: the attacker only needs any nonzero amount of locked vlMGP (`getUserVotable`) and gas to execute a single transaction. `castVotes` is fully public and permissionless, so the attacker does not need to wait for or front-run a third party — they can self-trigger the harvest atomically. The attack is repeatable every time meaningful bribes have accrued and are ready to be harvested (i.e., each `castVotes` cycle), and scales with the size of the harvested bribe and the attacker's chosen instantaneous stake relative to `totalSupply`. This makes it highly feasible and low-cost.

### Recommendation
Replace the instantaneous, balance-at-distribution-instant accounting with a time-weighted mechanism: either (a) stream rewards over a fixed duration via `rewardRate`/`periodFinish` (Synthetix-style), so instantaneous stake spikes cannot capture a full share of a lump-sum distribution, or (b) enforce a minimum holding/lock period for vote positions in `WombatBribeManager` (e.g., disallow `unvote`/`vote`-delta changes within the same block/epoch as the corresponding `castVotes` harvest, or snapshot voter balances prior to reward harvest rather than at time of distribution).

### Proof of Concept
Foundry test plan:
1. Deploy `BribeRewardPool`/`WombatBribeManager` test harness with a mock `wombatStaking`/`voter` that returns a fixed non-zero bribe amount on `vote()` calls (simulating externally-accrued bribes).
2. Setup: user A locks vlMGP and calls `vote()` on pool P with delta `D_A` in block N-1; call `castVotes()` once to establish a baseline `rewardPerTokenStored` (no reward yet, or a first round with no attacker present) and record balances.
3. In block N: attacker calls `vote()` on pool P with delta `D_atk` (attacker's own vlMGP), immediately calls `castVotes()` (triggering mock harvest of bribe amount `R`), then immediately calls `unvote()` with `claim=true`.
4. Assert: `attacker_claimed = D_atk * R / (D_A + D_atk)` (or however the mock computes it) is greater than zero despite attacker having zero votes prior to block N, and that `IERC20(rewardToken).balanceOf(attacker)` increased by this non-zero amount.
5. Assert conservation violation: sum of (`A`'s and attacker's) time-weighted contribution to the bribe-generating votes (`D_A` held for the whole period vs `D_atk` held for 0 seconds) does not match the proportional payout — i.e., attacker's earned reward exceeds their fair time-weighted share (which should be ~0), demonstrating value diverted from user A.     function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

            revert LengthMismatch();

        uint256 length = _lps.length;
        int256 totalUserVote;

        for (uint256 i; i < length; i++) {
            Pool storage pool = poolInfos[_lps[i]];
            if (!pool.isActive)
                revert PoolNotActive();
            int256 delta = _deltas[i];
            totalUserVote += delta;
            if (delta != 0) {
                if (delta > 0) {
                    pool.totalVoteInVlmgp += uint256(delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] += uint256(delta);
                    IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
                } else {
                    pool.totalVoteInVlmgp -= uint256(-delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta);
                    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
                }
            }
        }

        if (msg.sender != delegatedPool) {
            if (totalUserVote > 0) {
                userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);
                totalVlMgpInVote += uint256(totalUserVote);
            } else {
                userTotalVotedInVlmgp[msg.sender] -= uint256(-totalUserVote);
                totalVlMgpInVote -= uint256(-totalUserVote);
            }
        }
