One more check on the encryption PoP sender binding and how blame flows upstream.### Title
`VerifyBlame` passes `accuser`/`accused` in swapped order to `AdditionalBlameMachine::blame`, letting any participant get an honest validator fatally slashed with a fabricated share message (and causing honest accusers to be slashed) - ([File: processor/src/key_gen.rs](processor/src/key_gen.rs))

### Summary
In the OpenClaw advisory, a write-scoped path reached an admin-only control-plane operation because authorization was checked on the wrong scope. The Serai analog is the DKG blame-verification path: `CoordinatorMessage::VerifyBlame` is driven by an accusation any participant can raise (`ProcessorMessage::InvalidShare`), and it adjudicates a fatal slash — an action meant to be reachable only by the protocol's accountability logic. In `processor/src/key_gen.rs` the handler invokes `AdditionalBlameMachine::blame(sender, recipient, msg, proof)` with the roles swapped, so the PedPoP blame logic verifies the proof-of-possession against the wrong participant and attributes fault to the wrong party.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` are documented and implemented as `blame(sender, recipient, msg, proof)`, where `msg` is "a copy of the encrypted secret share from the accused sender to the accusing recipient" (crypto/dkg/pedpop/src/lib.rs:615-617,674-682). In `blame_internal`, the share's Schnorr PoP is verified with `pop_challenge(context, R, msg.key, sender, msg)` — i.e., bound to `sender`'s participant index (crypto/dkg/pedpop/src/encryption.rs:374-379,302-324), and the optional `EncryptionKeyProof` DLEq is checked against `enc_keys[&recipient]` (encryption.rs:381-390). The unit test confirms the ordering: `blame(ONE, TWO, msg_from_ONE_to_TWO)` blames `ONE` (pedpop/src/tests.rs:156-159).

In `VerifyBlame`, the submitted `share` is the message from `accused` to `accuser`, so the correct call is `blame(accused, accuser, share, blame)`. Instead, `processor/src/key_gen.rs` calls `.blame(accuser, accused, substrate_share, substrate_blame)` and `.blame(accuser, accused, network_share, network_blame)` (lines 543-556), then emits `Blame { participant: accused }` if either call returns `accused` (lines 558-563).

Two consequences, both wrong:
- For a genuine accused→accuser share message, `msg.pop.verify` runs `pop_challenge` with `from = accuser` while the PoP was generated by `accused`, so it always fails → `DecryptionError::InvalidSignature` → `blame_internal` returns `sender` = `accuser`. Every honest accusation is inverted and the accuser is fatally blamed (key_gen.rs:563). A genuinely faulty sender is never blamed.
- An attacker "accuser" can fabricate `share` entirely: they create an `EncryptedMessage` with their own ephemeral key `k` and a valid Schnorr PoK over the challenge with `from = accuser` (they know `k`, so the PoK verifies). They submit `blame = None`. `decrypt_with_proof` then returns `Err(InvalidProof)` because no proof was given, and `blame_internal` returns `recipient` = `accused` (lib.rs:587). The handler emits `Blame { participant: accused }` — the honest accused is marked at fault.

### Impact Explanation
`ProcessorMessage::Blame` results in the named participant being fatally slashed (the in-code comment notes "this being called means *someone* is getting fatally slashed", key_gen.rs:535-537). The swapped arguments invert the accountability mechanism: (a) a participant who reports a truly invalid share is slashed instead of the faulty sender, and (b) any participant can submit an accusation with a self-fabricated `EncryptedMessage` and no `EncryptionKeyProof`, causing an arbitrary honest participant to be blamed and slashed. This is a forged-accusation primitive that breaks liveness of honest validators and removes any deterrent against actually-invalid shares.

### Likelihood Explanation
An accuser only needs to emit an `InvalidShare` accusation during key generation; the coordinator then issues `VerifyBlame` carrying the accuser-controlled `share` bytes, which every processor feeds through `EncryptedMessage::read` and `AdditionalBlameMachine::blame` (key_gen.rs:504-563). Fabricating a passing `msg.pop` is trivial — it is a Schnorr PoK over a key the attacker chooses, bound to `from = accuser`, so `InvalidSignature` is avoided and the `None` proof short-circuits to blaming `recipient` (the accused). Both the substrate and network evaluations are independently wrong, and the framing path requires no collusion, no keys, and no privileged position beyond being a DKG participant.

### Recommendation
Swap the arguments so the accused's message is evaluated as `sender`: call `.blame(accused, accuser, substrate_share, substrate_blame)` and `.blame(accused, accuser, network_share, network_blame)` in `processor/src/key_gen.rs` `CoordinatorMessage::VerifyBlame` handling. Add a regression test where `VerifyBlame` is fed (1) a genuinely invalid share (expect `Blame { participant: accused }`) and (2) a fabricated share with no proof (expect `Blame { participant: accuser }`).

### Proof of Concept
```rust
// Attacker P1 wants to frame honest P2 during KeyGenId { session, attempt }.

// 1. P1 fabricates `share`: an EncryptedMessage<Ristretto, SecretShare<F>>
//    with ephemeral key k chosen by P1, ciphertext of arbitrary bytes, and
//    a SchnorrSignature proving knowledge of k under
//    pop_challenge(context, R=k*G, key=k*G, sender=P1, ciphertext).
//    P1 knows k, so the PoP verifies when evaluated with from = P1.
let share = fabricated.serialize();
let blame: Option<Vec<u8>> = None;

// 2. P1 raises the accusation; the coordinator issues:
CoordinatorMessage::VerifyBlame { id, accuser: P1, accused: P2, share, blame };

// 3. Each processor runs key_gen.rs:
//    EncryptedMessage::read succeeds (well-formed bytes).
//    AdditionalBlameMachine::blame(accuser /*=sender*/, accused /*=recipient*/,
//      substrate_share, None)
//      -> decrypt_with_proof(P1, P2, msg, None)
//      -> pop.verify(pop_challenge(..., from=P1, ...)) == true   // forged PoP
//      -> proof is None -> Err(InvalidProof)
//      -> blame_internal returns recipient = P2 (the accused)
//    => ProcessorMessage::Blame { participant: P2 }
//    Honest P2 is fatally slashed on the basis of a message P2 never sent,
//    which was never authenticated as originating from P2.
//
// Symmetrically, if P2 actually sent an invalid share and P1 reports the real
// ciphertext, the PoP fails because it was made under from = P2 but is checked
// under from = P1, so blame_internal returns sender = P1 and the honest
// accuser is slashed instead of the faulty P2.
```

Root cause: `blame(accuser, accused, …)` at processor/src/key_gen.rs:549,556 must be `blame(accused, accuser, …)` to match `blame(sender, recipient, msg, proof)` in crypto/dkg/pedpop/src/lib.rs:674-682 and the `sender`-bound `pop_challenge` in crypto/dkg/pedpop/src/encryption.rs:374-390.
