## Analysis Result

### Title
Reward-per-token rounds to zero on `queueNewRewards`/`donateRewards` when an attacker sandwiches the call with a large temporary stake, permanently freezing the injected reward tokens - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool` (and its clones `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`, `vlMGPBaseRewarder.sol`) update `rewardPerTokenStored` as a single lump-sum increment computed from `totalStaked()` at the moment reward tokens are injected, rather than a time-decayed rate. An unprivileged actor can inflate `totalStaked()` immediately before a reward-funding call and withdraw immediately after, forcing the reward-per-token computation to truncate to zero via integer division — identical in root cause to the Kwenta USDC precision bug, but triggered through stake/withdraw sandwiching instead of rapid `stake`/`unstake` calls over a time window.

### Finding Description
`_provisionReward` computes the reward-per-token increment in one shot: [1](#0-0) 

```solidity
rewardInfo.rewardPerTokenStored =
    rewardInfo.rewardPerTokenStored +
    (_amountReward * 10**stakingDecimals()) /
    this.totalStaked();
```

This is called from `queueNewRewards` (manager-triggered, e.g. a routine weekly reward distribution) and `donateRewards`, which is directly callable by any unprivileged wallet: [2](#0-1) 

`totalStaked()` is read live from `MasterMagpie`'s balance for the pool's staking token: [3](#0-2) 

`MasterMagpie.deposit`/`withdraw` have no lock-up or cooldown — a user can deposit and withdraw the same staking token in immediate succession: [4](#0-3) [5](#0-4) 

Because `_provisionReward` only queues the reward (`rewardInfo.queuedRewards += _amountReward`) when `totalStaked() == 0`, it has no protection for the case where `totalStaked()` is merely large enough to make `(_amountReward * 10**stakingDecimals()) / totalStaked()` truncate to zero while still being nonzero. An attacker can therefore:

1. Front-run (or simply time their transaction ahead of) a manager's `queueNewRewards` call by depositing a very large amount of the pool's staking token via `MasterMagpie.deposit`, inflating `totalStaked()`.
2. Let the reward-funding call execute; the reward tokens are pulled into the contract via `safeTransferFrom`, but `rewardPerTokenStored` increases by zero (or negligibly) due to truncation.
3. Immediately call `MasterMagpie.withdraw` to remove the inflated stake, restoring `totalStaked()` to its normal level.

The freshly transferred reward tokens are now sitting in the pool's balance but are unaccounted for: they were not queued (since `totalStaked() != 0` at provisioning time), and `rewardPerTokenStored` was not meaningfully increased, so no existing staker's `earned()` value reflects them. This mirrors the root cause identified in the Kwenta report — a reward-per-token formula that truncates to zero for low-magnitude rewards relative to the staked base — but is reachable here purely through unprivileged deposit/withdraw actions around a routine (non-malicious) reward-funding transaction.

### Impact Explanation
Legitimate stakers permanently lose the reward tokens injected during the sandwiched call — the funds remain custodied by the contract but are never distributed nor re-queued, resulting in a permanent freeze/loss of unclaimed yield for all stakers in that pool. Any registered reward token with a decimal count small relative to the staking token's decimals (e.g. a 6-decimal token, similar to USDC in the original report) is especially exposed, but even 18-decimal tokens are exploitable given sufficient stake inflation.

### Likelihood Explanation
The attack requires the attacker to temporarily control an amount of the staking token large enough to make the division truncate to zero (`_amountReward * 10**stakingDecimals() < totalStaked()`), and to time the deposit/withdraw around a reward-funding transaction. This is feasible for staking tokens that are liquid/flash-loanable, or when reward amounts are modest relative to the pool's TVL, and costs only the gas for two extra deposit/withdraw calls (no protocol fee/lockup prevents it). This matches the same low-cost, non-privileged griefing profile that Sherlock accepted as Medium severity in the referenced Kwenta finding.

### Recommendation
Avoid lump-sum division truncation in `_provisionReward`: scale `_amountReward` to a high-precision fixed-point value before dividing by `totalStaked()`, and if the resulting increment would still round to zero, add the entire `_amountReward` to `rewardInfo.queuedRewards` (as already done for the `totalStaked() == 0` case) instead of silently discarding it. Additionally, consider computing `totalStaked()` using a time-weighted or snapshot-based approach so that flash-stake sandwich attacks cannot manipulate the denominator used in reward-per-token calculations.

### Proof of Concept
```solidity
// Pseudocode illustrating the sandwich
// Assume rewardToken has 6 decimals, stakingToken has 18 decimals

// 1. Attacker inflates totalStaked() right before the manager's reward call
vm.prank(attacker);
masterMagpie.deposit(stakingToken, HUGE_AMOUNT); // e.g. flash-loaned LP tokens

// 2. Manager (rewards notifier / distributor) funds the pool as part of normal operations
vm.prank(manager);
baseRewardPool.queueNewRewards(10_000e6, usdcLikeToken);
// rewardPerTokenStored increment = (10_000e6 * 1e18) / (HUGE_AMOUNT + normalStaked) == 0 due to truncation

// 3. Attacker immediately withdraws the inflated stake
vm.prank(attacker);
masterMagpie.withdraw(stakingToken, HUGE_AMOUNT);

// Result: 10_000e6 USDC-like tokens are now held by baseRewardPool,
// but rewardPerToken(usdcLikeToken) did not increase and rewardInfo.queuedRewards is untouched
// (totalStaked() != 0 at provisioning time), so legitimate stakers can never claim this reward batch.
assertEq(baseRewardPool.rewardPerToken(usdcLikeToken), 0); // funds permanently stuck/unaccounted
```

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
