### Title
Stale line-index selection allows silent corruption of partial commits when the working-directory diff changes between selection and staging - (File: app/src/lib/git/apply.ts)

### Summary
The TribalChief bug is a case of an accounting value (`user.rewardDebt`) being computed from the wrong, stale magnitude (`user.virtualAmount`, the whole balance) instead of the actual delta being applied (`virtualAmountDelta`), silently corrupting internal state. The equivalent broken invariant in GitHub Desktop's partial-commit ("stage selected lines") pipeline is that `DiffSelection` stores line inclusion state as **integer positions in a specific diff snapshot** (`absoluteIndex = hunk.unifiedDiffStart + lineIndex`), but `applyPatchToIndex` re-fetches a **fresh** diff from disk at staging time and blindly re-applies that stale positional selection to it, with no check that the new diff's line layout still matches the one the user actually reviewed.

### Finding Description
`DiffSelection.isSelected(lineIndex)` and `withRangeSelection` operate purely on integer line indices computed relative to a specific `ITextDiff`'s hunks (`app/src/models/diff/diff-selection.ts:121-136, 231-282`). These indices carry no notion of *which* diff they were derived from, nor any content hash/anchor.

When the user commits, `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) calls `applyPatchToIndex` for every partially-selected file. That function does **not** use the diff the user was looking at when they made their selection; instead it fetches a brand-new diff at staging time: [1](#0-0) 

and immediately feeds that fresh diff plus the (old) selection into `formatPatch`: [2](#0-1) 

`formatPatch` walks the new diff's hunks and, for every non-context line, calls `file.selection.isSelected(absoluteIndex)` using the *new* diff's `hunk.unifiedDiffStart` offsets: [3](#0-2) 

If the working-directory content changes between the moment the UI diff was rendered (and the selection built) and the moment `applyPatchToIndex` runs — e.g. lines are added/removed by a background process, a `.gitattributes` clean/smudge filter, a file-watcher-triggered formatter, or a git hook — the hunk boundaries and `unifiedDiffStart` offsets shift. The stored `divergingLines` set (raw integers) then no longer points at the lines the user actually clicked; `isSelected()` will happily return `true`/`false` for the wrong lines in the new hunk layout. There is a partial mitigation elsewhere (`app-store.ts:3478-3496`) that recomputes `selectableLines` when the *live* diff shown in the Changes list changes, but that update path is separate from, and not guaranteed to run synchronously before, the commit-time `applyPatchToIndex`/`getWorkingDirectoryDiff` re-fetch — there is no diff-identity/hash check inside `applyPatchToIndex` or `formatPatch` itself that aborts or re-validates the selection against the diff actually used to build the patch. This is structurally the same flaw as the TribalChief bug: a stateful positional value (`user.virtualAmount` / line-index selection) is reused against a context that has since diverged (the pool's actual delta / the actual current diff), instead of being recomputed or validated against the current, authoritative state at the time of the effectful operation.

### Impact Explanation
If exploited, a user could unknowingly stage/commit (or discard, via the analogous `formatPatchToDiscardChanges` + `discardChangesFromSelection` path in `app/src/lib/git/apply.ts:102-120`) different lines than the ones they explicitly selected in the UI — i.e., silent corruption of what the user commits or pushes, which is explicitly in-scope impact. In the worst case this could cause unintended code (including attacker-influenced content introduced via a clean/smudge filter or hook shipped with a cloned repository) to be committed or, conversely, cause the user's intended change to be silently dropped while unrelated hunks are discarded.

### Likelihood Explanation
The window between diff computation and commit/discard is normally short, and Desktop already disables line-selection UI while committing (`app/src/ui/changes/changes.tsx:65-67`, `lineSelectionDisabled`), which mitigates but does not eliminate the race — `applyPatchToIndex` still re-fetches the diff independently and there is no hard verification that it matches the diff snapshot the selection was built against. A malicious/cloned repository that ships a `.gitattributes` clean/smudge filter or a working-directory-modifying hook (e.g., `post-checkout`, or a filter invoked by `git diff`/`git add` itself) could reliably widen or trigger this window without any unusual local-access assumptions, since such filters execute automatically as part of normal Desktop operations on that repository. I was not able to fully verify from the index whether a synchronous re-diff-and-compare guard exists elsewhere in `app-store.ts`'s commit path (the relevant `_commitIncludedChanges`/staging orchestration in `app-store.ts` was not fully retrievable within the tool budget), so likelihood should be treated as moderate/unconfirmed pending direct code review of that call path.

### Recommendation
Before calling `formatPatch`/`formatPatchToDiscardChanges` in `applyPatchToIndex` / `discardChangesFromSelection`, verify that the diff just fetched (`getWorkingDirectoryDiff`) is structurally identical (or content-hash equal) to the diff that produced the `DiffSelection`, and fail/re-prompt rather than silently applying a positionally-stale selection. Consider anchoring `DiffSelection` entries to line content/old-new line numbers instead of raw diff-relative integer offsets, similar to how `getLineInOriginalDiff` maps expanded-diff indices back to original diff coordinates for the interactive-range case (`app/src/ui/diff/diff-explorer.ts:85-123`).

### Proof of Concept
1. Clone a malicious repository containing a `.gitattributes` entry with a `clean`/`smudge` filter (or a `post-checkout`/other hook, depending on which git operations Desktop triggers) for a tracked file, where the filter appends/removes a line non-deterministically or based on wall-clock/environment.
2. In Desktop, open the file's diff, select only specific lines (e.g., line 10) to include in the commit, leaving others unselected.
3. Before the user clicks "Commit," have the filter/hook alter the file so that `git diff` reflow shifts hunk boundaries (e.g., insert a line above the hunk the user selected).
4. Click "Commit." `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the old `DiffSelection`'s raw indices against the new hunk layout in `formatPatch` (`app/src/lib/patch-formatter.ts:143-170`), producing a patch that stages a different line than the one the user selected — verifiable by diffing `git show :<path>` (index) content against the lines the user actually clicked in the UI.

(Note: I could not fully trace the exact call path in `app-store.ts` from UI "Commit" click through to `stageFiles`/`applyPatchToIndex` within the available tool budget — confirming whether an intermediate synchronous re-diff/hash check exists would require direct review of `_commitIncludedChanges` or equivalent orchestration code in `app/src/lib/stores/app-store.ts`.)
