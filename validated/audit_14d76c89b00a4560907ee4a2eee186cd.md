## Title
Boundary check in `resolveWithin()` uses raw string-prefix comparison, allowing path-traversal escape to sibling directories via attacker-controlled deep-link `filepath` — (File: `app/src/lib/path.ts`)

### Summary
The external report's broken invariant is a comparison that is *supposed* to gate a security-relevant decision but is missing an edge case, letting attacker-influenced data slip past the guard and cause a silently wrong result. The Desktop analog is the containment check inside `_resolveWithin()`, which validates that a resolved path stays inside a trusted root directory before the app acts on it (e.g. `shell.showItemInFolder`). The check uses a raw string prefix test instead of a path-boundary-aware test, so a sibling directory whose name merely starts with the root directory's name passes the check.

### Finding Description
`_resolveWithin()` computes the final containment check like this: [1](#0-0) 

`realResolved.startsWith(realRoot)` treats `realRoot` as a plain string prefix, with no check that the next character in `realResolved` is a path separator (or that the strings are equal). Given `realRoot = "/Users/victim/Documents/GitHub/myrepo"` and a sibling directory `"/Users/victim/Documents/GitHub/myrepo-evil"`, the string `"/Users/victim/Documents/GitHub/myrepo-evil/secret.txt"` legitimately starts with `"/Users/victim/Documents/GitHub/myrepo"`, so the function returns this path as "resolved" and "safe" even though it is outside the intended root.

This is reachable from attacker-controlled input through the deep-link (`x-github-client://openRepo/...`) handler. `dispatcher.ts` parses the `filepath` query parameter from the URL, blocks only *absolute* paths, and then calls `resolveWithin`: [2](#0-1) 

A relative traversal payload such as `filepath=../myrepo-evil/secret.txt` is not rejected by `isAbsolute()`, is joined/normalized, and `path.resolve(root, "../myrepo-evil/secret.txt")` legitimately pops out of `myrepo` into the sibling `myrepo-evil`. The intended guard (`realResolved.startsWith(realRoot)`) does not stop this because it never checks the separator boundary, exactly mirroring the original report's pattern: an "if" check that looks like it enforces an invariant but is missing the edge case where the raw value coincidentally satisfies the naive comparison.

### Impact Explanation
This falls in the class of "attacker controls a deep link the user clicks, resulting in ... file read outside the repo." If the victim's clone directory naming (which itself is influenced by the attacker-controlled clone URL via `sanitizeCloneName` in `app/src/lib/remote-parsing.ts`) or any coincidentally-named sibling folder exists, a single crafted deep link can cause Desktop to resolve and act (`shell.showItemInFolder`) on a path outside the intended repository root, defeating the explicit purpose of `resolveWithin` as a containment boundary. The same primitive (`resolveWithin`) is reused elsewhere in the app (e.g. `app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`), so any other caller relying on it for a security boundary inherits the same weakness — call sites beyond `dispatcher.ts` were not fully re-verified in this session due to tool-call limits.

### Likelihood Explanation
Exploitation requires: (1) the victim clicks a crafted `x-github-client://openRepo/...` deep link, and (2) a directory sibling to the repo whose name is prefixed by the repo's directory name exists on disk. Condition (2) makes real-world exploitation situational rather than universal, but the underlying boundary check is unconditionally broken — it is a logic bug, not a probabilistic one — so any code path or future caller that assumes `resolveWithin` enforces strict containment is silently unsafe.

### Recommendation
Fix the containment check in `app/src/lib/path.ts` to be boundary-aware, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the same `options`-provided separator semantics (`Path.sep` vs `Path.win32.sep`/`Path.posix.sep` depending on which resolver variant is used), and add regression tests with sibling directories that share a name prefix (analogous to `app/test/unit/clone-path-safety-test.ts`).

### Proof of Concept
1. Victim has GitHub Desktop open and has (or will have) a local clone at `~/Documents/GitHub/myrepo`, with an unrelated sibling directory `~/Documents/GitHub/myrepo-secrets` containing sensitive files.
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Fsecret.txt`.
3. `parseAppURL` extracts `filepath = "../myrepo-secrets/secret.txt"` [3](#0-2) .
4. `openRepositoryFromUrl` passes the `isAbsolute` check (the path is relative) and calls `resolveWithin(repository.path, filepath)` [2](#0-1) .
5. `_resolveWithin` resolves to `.../myrepo-secrets/secret.txt`, and because `realResolved.startsWith(realRoot)` is true (naive string prefix), the function returns this out-of-root path as valid [1](#0-0) .
6. Desktop calls `shell.showItemInFolder(resolved)`, revealing/opening the file outside the intended repository boundary.
