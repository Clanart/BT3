### Title
Webhook shop binding relies on unverified `X-Shopify-Shop-Domain` header, allowing cross-shop session/data mutation via HMAC replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` only checks that the HMAC over the raw request body matches the shared app secret (or `old_secret`); it never binds that HMAC to the `shop` value used by downstream jobs. `ShopifyApp::WebhookVerification#shop_domain` and the declarative-webhook controller template both read the shop identity straight from the attacker-controlled `X-Shopify-Shop-Domain` header, which is not covered by the HMAC at all. Because the app's client secret (and `old_secret`) is shared across every shop that installs the app, any actor who can produce (or replay) one validly-HMAC-signed body can pair it with an arbitrary shop-domain header and cause a shop-scoped destructive job (`AppUninstalledJob`, `ShopRedactJob`, or a generated declarative webhook job) to run against a victim shop of their choosing.

### Finding Description
- `verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` (lines 15-21) computes HMAC only over `request.raw_post`, comparing against `ShopifyApp.configuration.secret` / `old_secret` in `PayloadVerification#hmac_valid?` (`lib/shopify_app/controller_concerns/payload_verification.rb` lines 13-23). No header, including `X-Shopify-Shop-Domain`, is part of that computation.
- `shop_domain` (`webhook_verification.rb` line 23-25) and the generated `webhook_controller.rb.tt` (`lib/generators/shopify_app/add_declarative_webhook/templates/webhook_controller.rb.tt` line 8) both derive the acting shop from `ShopifyAPI::Webhooks::Request#shop`, which is populated from the `X-Shopify-Shop-Domain` request header — not from any value that is cryptographically bound to the signed body.
- Generated job templates (`app_uninstalled_job.rb.tt` lines 4-19, `shop_redact_job.rb.tt` lines 4-19, `webhook_job.rb.tt` lines 1-14) take that unverified `shop_domain` value directly, look up the `Shop` record by it, and perform destructive/state-changing actions (`shop.destroy`, `shop.with_shopify_session`) against whichever shop the header names.
- Because the HMAC secret is the app's single shared client secret (not per-shop), a valid HMAC merely proves the body+secret pairing is authentic for *some* shop under this app, not that it originated from or targets the shop named in the header. An attacker who controls their own installed shop can capture one of their own genuinely Shopify-signed webhook deliveries (body + HMAC unchanged) and resend it to the endpoint with the header rewritten to `victim.myshopify.com`. Since the raw body is untouched, `hmac_valid?` still returns true, `verify_request` passes, and the job is enqueued with `shop_domain: "victim.myshopify.com"`.
- No control in this codebase — no `ActiveSupport::SecurityUtils.secure_compare` misuse aside, no session-id derivation, no scope check — ties the verified HMAC to the specific shop value consumed downstream, so the check that would stop this (binding shop identity to the signed content) does not exist.

### Impact Explanation
This is a cross-tenant/session-confusion issue matching Shopify's "improper access control / broken authentication between tenants" class: an attacker who controls any single shop that has the app installed can trigger `shop.destroy` (uninstall handling) or shop-redact/data-privacy flows against an unrelated victim shop, tearing down the victim's stored session/access token and app data without ever compromising the victim's credentials. The concrete effect is denial-of-service against an arbitrary victim merchant (forced app uninstall/session loss), and potentially data loss if the merchant integrator's redact job deletes shop-scoped records.

### Likelihood Explanation
Feasibility is bounded by one real precondition: the attacker must have at least one shop with the app installed (to receive one authentic Shopify-delivered webhook whose body+HMAC they can capture and replay verbatim), or possession of a leaked `old_secret`. Because `old_secret` support exists specifically to allow a grace period after secret rotation, an attacker who obtains an old rotated secret can also forge fresh bodies at will, not just replay. Given the attack requires no victim secret, no victim session, and no host misconfiguration — only control of the header on an otherwise-valid POST — this is repeatable and low-effort for anyone who has (or once had) legitimate shop-level access to the app.

### Recommendation
Do not use the `X-Shopify-Shop-Domain` header (or `ShopifyAPI::Webhooks::Request#shop`, which is header-derived) as the trusted shop identity for side-effecting operations. Instead, verify the shop domain by deriving it from a value that is cryptographically bound to the request (e.g., require the webhook body's own JSON payload where applicable and/or cross-check against Shopify's registered webhook per-shop callback/topic mapping), or, at minimum, mark HMAC verification as only proving "signed by an app secret," and require an additional authoritative lookup (not client/header supplied) before performing destructive actions such as `shop.destroy`. Consider migrating to per-webhook secrets or requiring re-validation via the Admin API for critical topics like `app/uninstalled` and `shop/redact`.

### Proof of Concept
```ruby
# test/integration/webhooks_controller_test.rb (added)
test "a validly HMAC-signed webhook body with a forged shop header targets the header's shop, not the signing shop" do
  body = { some: "genuine_payload_from_attacker_shop" }.to_json
  secret = ShopifyApp.configuration.secret
  hmac = Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, body))

  # Attacker replays their own validly-signed body but swaps the shop header to the victim
  post "/webhooks/app_uninstalled",
    params: body,
    headers: {
      "HTTP_X_SHOPIFY_HMAC_SHA256" => hmac,
      "HTTP_X_SHOPIFY_SHOP_DOMAIN" => "victim.myshopify.com",
      "CONTENT_TYPE" => "application/json",
    }

  assert_response :ok
  assert_enqueued_with(job: AppUninstalledJob, args: [{ topic: "app/uninstalled", shop_domain: "victim.myshopify.com", webhook: anything }])
  # Expected (secure) behavior: job should NOT be enqueued for "victim.myshopify.com" since the
  # HMAC-signing shop is not victim.myshopify.com — this assertion demonstrates the header is trusted unverified.
end

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
