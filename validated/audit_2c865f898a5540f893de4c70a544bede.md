### Title
Fee-on-transfer input tokens cause escrow ledger to overstate actual custody in Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal escrow ledger `_orders[commitment][token]` with the user-requested (fee-reduced-only-by-protocol-fee) amount, without ever measuring what the contract actually received from `safeTransferFrom`. For a fee-on-transfer ERC20 used as an order input, the contract's real token balance will be lower than the sum of amounts recorded in `_orders`, silently under-collateralizing the pool and enabling later legitimate withdrawals to fail or, in a shared-liquidity scenario, allowing earlier claimants to drain balances that were actually funded by other users' deposits.

### Finding Description
In `placeOrder` (no-predispatch branch), the contract transfers tokens in with the caller-specified amount and then unconditionally credits the ledger with the (protocol-fee-reduced) requested amount, not the actual amount received: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));

        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus the protocol fee percentage — it is never adjusted for what `safeTransferFrom` actually delivered: [2](#0-1) 

The predispatch branch has the same flaw — it uses `balance = IERC20(token).balanceOf(dispatcher)` only to detect *excess* dust, but still credits `reducedInputs[i].amount` (computed from the original requested amount) into `_orders`, not the balance actually swept into the gateway: [3](#0-2) 

This is the exact analog of the reported bug class: the contract "always sends/records the flat amount specified in the function's parameter, rather than the amount actually transferred," so any deflationary/fee-on-transfer token creates a mismatch between recorded internal accounting and real custodied balance.

Contrast with the primary EVM `IntentGatewayV2.sol` (non-Tron), which explicitly snapshots balances before/after transfer and mutates `order.inputs[i].amount` to the actually-received value before computing `reducedInputs` and the commitment: [4](#0-3) 

The Tron deployment lacks this balance-based accounting entirely, meaning the fix applied to the primary EVM contract was not carried over to the Tron fork.

### Impact Explanation
Because `_orders[commitment][token]` is the ledger the contract trusts when authorizing withdrawals/refunds/redemptions for a given commitment, crediting more than what was actually deposited breaks the fund-custody invariant: total recorded liabilities per token can exceed the contract's actual token balance. In a contract that pools funds across many concurrent orders of the same token, this insolvency lets whichever commitment is redeemed/cancelled/filled first successfully withdraw its full recorded (inflated) amount, consuming balance that rightfully belongs to other users' un-redeemed orders — a direct "loss of funds" / wrong-beneficiary-amount scenario matching the bounty's fund-safety criteria. Even without cross-order interference, the depositor's own order becomes unfulfillable/reverting on withdrawal since the escrow slot claims more tokens than the contract holds for that token, causing fund lock.

### Likelihood Explanation
This requires only an unprivileged user placing an order (`placeOrder`) with a fee-on-transfer/deflationary ERC20 as an input asset — no relayer, prover, or admin compromise is needed. Whether a fee-on-transfer token is used as input is entirely under the caller's control (or determined by which tokens IntentGateway allows as inputs on the Tron deployment), so likelihood depends on whether such tokens are permitted/whitelisted for this Tron gateway; the code contains no restriction preventing arbitrary ERC20 tokens as input.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the contract's actual token balance before and after each `safeTransferFrom` (and after the predispatch sweep), and base `reducedInputs`/`_orders` crediting strictly on the amount actually received, not the caller-specified `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a 1%-fee ERC20 token (e.g. the `FeeOnTransferToken` test helper already present in the repo's test suite) and use it as an input token on the Tron `IntentGatewayV2`.
2. Call `placeOrder` with `inputs[0].amount = 1000e18`. The contract executes `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000e18)` but due to the 1% fee only receives `990e18`.
3. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount` (≈`1000e18` minus only the protocol fee, e.g. `997e18` at 30bps), which exceeds the `990e18` actually held by the contract.
4. Repeating this with multiple orders compounds the shortfall between recorded `_orders` liabilities and the real ERC20 balance held by the gateway, so a subsequent full-amount withdrawal for any of these orders (or an unrelated order sharing the same token) can fail or drain the pool at another depositor's expense.

Note: the exact `withdraw`/`onAccept` payout logic in the Tron file (`function withdraw(...)`, referenced at lines ~530 and ~625) was located but its full body was not retrieved before the tool budget was exhausted; the analysis above assumes it pays out based on the `_orders[commitment][token]` value (consistent with the equivalent logic in the primary EVM contract). Confirming the exact transfer-out code path is recommended before remediation to ensure the fix is applied consistently across `placeOrder`, `withdraw`, and any partial-fill accounting in the Tron contract.
