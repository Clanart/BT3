### Title
`send_move_to_vault_tx` does not verify the signed transaction's actual input matches the caller-supplied `deposit_outpoint` — ([File: core/src/rpc/aggregator.rs])

### Summary
The aggregator's `send_move_to_vault_tx` RPC accepts a raw, fully-signed move-to-vault transaction plus a separate `deposit_outpoint` parameter used purely for bookkeeping/metadata, but never checks that `movetx.input[0].previous_output` actually equals the supplied `deposit_outpoint`.

### Finding Description
In `send_move_to_vault_tx` [1](#0-0) , the handler deserializes `raw_tx` and parses `deposit_outpoint` from the request as two independent fields. It then validates the shape of the transaction (`input.len()==1`, `output.len()==2`), output amounts, and output script pubkeys against the generic N-of-N + security-council vault address [2](#0-1) . Nowhere in this validation is `movetx.input[0].previous_output` compared against `deposit_outpoint`. The `deposit_outpoint` value supplied by the caller is then stored as-is into `TxMetadata.deposit_outpoint` when the transaction is queued for broadcast [3](#0-2) .

Because the vault output script pubkey is identical for every deposit (same N-of-N `nofn_xonly_pk` + security council multisig, independent of which specific deposit outpoint was spent — see `create_move_to_vault_txhandler` [4](#0-3) ), the output checks cannot distinguish which specific deposit a given raw move-tx actually corresponds to. The only way to correctly bind the `TxMetadata.deposit_outpoint` (and downstream bookkeeping keyed by it) to the "real" spent deposit is to inspect the transaction's own input, which the function never does.

This mirrors the reported bug class item 3: "rewardIdentifier and bribeIdentifier can point to different rounds/tokens" — here, the caller-supplied `deposit_outpoint` identifier (used for tracking/metadata) is never bound to the transaction's actual spent outpoint (the equivalent of "bribeIdentifier"), letting an unprivileged caller submit a validly-signed move tx for deposit A while asserting to the aggregator's bookkeeping that it is for deposit B.

### Impact Explanation
The actual movement of BTC into the vault is still gated by the N-of-N MuSig2 signature over the specific `deposit_outpoint`'s scriptPath (this signature can only be produced through the full `new_deposit` verifier-signing flow), so an attacker cannot forge a signature to steal a different depositor's funds outright. However, the mismatch means the on-chain `move_to_vault_txid` for deposit A can be recorded in the aggregator's tx-sender metadata as belonging to deposit outpoint B. This is a bookkeeping/attribution bug rather than a direct fund-drain: it does not, by itself, cross the "operator reimbursed for a payout it never funded" or "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" bar, since the deposit→move-tx binding used for payout/reimbursement decisions elsewhere in the codebase (e.g., `insert_deposit_data_if_not_exists`, which independently computes `move_to_vault_txid` from `deposit_data` server-side [5](#0-4) ) is derived deterministically from the deposit data itself rather than trusted from this RPC call's metadata. I was not able to fully trace every downstream consumer of `TxMetadata.deposit_outpoint` from the tx-sender within the available context to confirm whether any payout/reimbursement decision path trusts this specific field without re-deriving/verifying it independently.

### Likelihood Explanation
Reaching this code path requires only calling the aggregator's `SendMoveTxRequest` RPC with any two independent, self-consistent (`raw_tx`, `deposit_outpoint`) pairs; no privileged role, verifier, or operator credentials are needed for the call itself beyond whatever transport-level authentication is configured (mTLS `client_verification`, which is optional in `create_aggregator_grpc_server` [6](#0-5) ). The attacker still needs a validly-signed move-to-vault transaction for some deposit (i.e., must have gone through the normal deposit-signing flow for outpoint A) — obtainable by simply being any legitimate depositor. Given this, likelihood of triggering the *metadata mismatch* is moderate, but I could not confirm (due to index limits on downstream tx-sender/payout code) whether this mismatch translates into a concrete custody-boundary violation as required by the analog rules, versus being purely cosmetic bookkeeping.

### Recommendation
In `send_move_to_vault_tx`, explicitly assert `movetx.input[0].previous_output == deposit_outpoint` before accepting the transaction, and reject the request with `Status::invalid_argument` if it does not match, exactly mirroring how output amounts/scriptpubkeys are already validated.

### Proof of Concept
1. Depositor A completes `new_deposit` for `deposit_outpoint_A`, obtaining a validly-signed `raw_move_tx_A` from the aggregator (see the test flow in `aggregator_deposit_movetx_lands_onchain` [7](#0-6) ).
2. Any caller (not necessarily depositor A) invokes `send_move_to_vault_tx` with `raw_tx = raw_move_tx_A` but `deposit_outpoint = deposit_outpoint_B` (an unrelated, previously-registered deposit outpoint).
3. The handler's checks on input/output count, amounts, and vault script pubkey all pass since they do not depend on which specific deposit is being spent [2](#0-1) .
4. The transaction is queued with `TxMetadata { deposit_outpoint: Some(deposit_outpoint_B), tx_type: MoveToVault, .. }` even though the broadcast transaction actually spends `deposit_outpoint_A` [8](#0-7) , creating a metadata/attribution mismatch between the recorded deposit identifier and the actually-spent UTXO.

I was unable to fully confirm within the indexed code whether any reimbursement/payout logic trusts this metadata field directly (rather than re-deriving the deposit-to-move-tx binding from `deposit_data`), which is necessary to establish concrete custody impact beyond a bookkeeping inconsistency.

pub fn create_move_to_vault_txhandler(
    deposit_data: &mut DepositData,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler<Unsigned>, BridgeError> {
    let nofn_xonly_pk = deposit_data.get_nofn_xonly_pk()?;
    let deposit_outpoint = deposit_data.get_deposit_outpoint();
    let nofn_script = Arc::new(CheckSig::new(nofn_xonly_pk));
    let security_council_script = Arc::new(Multisig::from_security_council(
        deposit_data.security_council.clone(),
    ));

    let deposit_scripts = deposit_data.get_deposit_scripts(paramset)?;

    Ok(TxHandlerBuilder::new(TransactionType::MoveToVault)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            SpendableTxIn::from_scripts(
                deposit_outpoint,
                paramset.bridge_amount,
                deposit_scripts,
                None,
                paramset.network,
            ),
            SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_scripts(
            paramset.bridge_amount,
            vec![nofn_script, security_council_script],
            None,
            paramset.network,
        ))
        // always use 0 sat anchor for move_tx, this will keep the amount in move to vault tx exactly the bridge amount
        .add_output(UnspentTxOut::from_partial(anchor_output(Amount::from_sat(
            0,
        ))))
        .finalize())
}

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
