### Title
`SignableTransaction::new` checks fee sufficiency and maximum weight before accounting for the attacker-controlled OP_RETURN output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Velodrome bug class is: a sufficiency check (`gasLeft() >= req.gas`) is evaluated *before* additional, unaccounted overhead is consumed, so the post-check amount available for the actual operation is less than what was verified. `SignableTransaction::new` in the in-scope `networks/bitcoin/src/wallet/` crate exhibits exactly this shape: it appends a variable-size OP_RETURN output to the transaction, then computes the fee (`needed_fee`), the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check on a weight estimate built only from `payments` — omitting the OP_RETURN output entirely.

### Finding Description
In `SignableTransaction::new`, the `data` parameter (up to 80 bytes, checked at send.rs:171) is encoded as an OP_RETURN output and pushed into `tx_outs` at send.rs:194-202. Immediately after, the fee and weight are computed:

```rust
// send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (send.rs:62-127) builds a mock `Transaction` whose `output` vector is constructed **only** from `payments` (and optionally `change`). The OP_RETURN `TxOut` — roughly 91 bytes (8-byte value + ~83-byte script) ≈ 364 WU ≈ 91 vbytes — is never included in `weight`, `vbytes`, `needed_fee`, the `DEFAULT_MIN_RELAY_TX_FEE` check at send.rs:211, or the `MAX_STANDARD_TX_WEIGHT` check at send.rs:241. The same omission applies to the change path at send.rs:225-227, where `fee_with_change` is again computed over `payments` only.

The actual fee paid is fixed as `sum(inputs) - sum(outputs) = needed_fee` (send.rs:138-141), but the real signed transaction is ~91 vbytes larger than estimated. An unprivileged party can reach this path because `data` corresponds to arbitrary data attached to a payment/instruction sent to the multisig (external users supply instruction data; the processor's literal test at processor/src/tests/literal/mod.rs demonstrates externally supplied `data` flowing into a Bitcoin transaction the multisig signs).

### Impact Explanation
Two concrete failure modes:

1. **Underpaid fee / non-relayable transaction.** If the coordinator selects a fee rate at or near the minimum relay fee, the check `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` passes for the *estimated* vsize, but the real transaction's effective feerate is `needed_fee / real_vsize`, which can fall below `DEFAULT_MIN_RELAY_TX_FEE`. The signed transaction will not propagate; the inputs it consumes have already been consumed by the scheduler, freezing those funds (an eventual retry would also re-derive the same underfunded size).

2. **Non-standard weight.** With a large input set (the processor targets up to `MAX_INPUTS = 520` per processor/src/networks/bitcoin.rs:575, tuned to just under the standard limit), the added ~364 WU OP_RETURN pushes the real weight above `MAX_STANDARD_TX_WEIGHT` even though the check at send.rs:241 passed, producing a transaction Bitcoin nodes reject as non-standard.

Either way, the multisig produces a signed transaction paying for inputs that cannot be broadcast — funds accounted as spent are not actually spendable/deliverable, directly analogous to the forwarder forwarding with less gas than verified.

### Likelihood Explanation
The deficit is bounded (~91 vbytes per OP_RETURN, ~364 WU), mirroring the original report's "very small range of values for the grief." Exploitation requires: (a) the attacker embedding maximal `data` in a payment routed through the multisig (reachable via user-supplied instruction/refund data), and (b) the coordinator choosing a fee rate near the protocol minimum, or a transaction near the weight limit. It is a griefing/margin correctness bug rather than a routine failure — hence Medium, matching the source report.

### Recommendation
Include all outputs actually being created in the weight estimate. Pass the constructed `tx_outs` (or `payments` plus the OP_RETURN script and the change script) into `calculate_weight_vbytes` instead of `payments` alone — i.e., compute the estimate over `tx_outs` after the OP_RETURN push, and recompute including the change output. Alternatively, adopt the Optimism-style fix from the report: add a conservative fixed overhead (e.g., 100 vbytes) to every estimate so post-check additions can never invalidate the fee/weight bounds.

### Proof of Concept
```rust
// Conceptual: in-network test against networks/bitcoin/src/wallet/send.rs
// Choose inputs so needed_fee equals the bare minimum relay fee,
// then attach 80 bytes of data.

let payments = [(p2tr_script_buf(key).unwrap(), PAYMENT)];
let data = Some(vec![0xaa; 80]); // passes the <= 80 check at send.rs:171

// fee_per_vbyte chosen such that needed_fee == DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000
let tx = SignableTransaction::new(inputs, &payments, None, data, fee_per_vbyte).unwrap();
// All checks pass: NotEnoughFunds, TooLowFee, MAX_STANDARD_TX_WEIGHT.

let signed = sign(&keys, &tx); // FROST signing completes
// signed.vsize() is ~91 vbytes larger than the estimated `vbytes`,
// so signed's effective feerate < 1 sat/vbyte = DEFAULT_MIN_RELAY_TX_FEE.
// send_raw_transaction is rejected by relay policy; the consumed inputs' funds are stuck.
assert!(signed.vsize() as u64 > /* estimated vbytes */);
```

The root cause is that `calculate_weight_vbytes` is fed `payments` rather than the actual `tx_outs` (which already includes the OP_RETURN and later the change output), so every bound check is evaluated on a transaction smaller than the one that will be signed and broadcast.
