## Analysis

The trace holds up: `pr.head.sha` / `pr.base.sha` come from `IAPIPullRequestRef` (raw GitHub API JSON, no format validation) [1](#0-0) , are persisted verbatim by `pull-request-store.ts` with no SHA-format check (`sha: pr.head.sha`, `sha: pr.base.sha`) [2](#0-1) , and eventually reach `getCommitsBetweenCommits(repository, baseBranchSha, targetBranchSha)`, which builds `revRange(baseBranchSha, targetBranchSha)` and calls `getCommitsInRange` [3](#0-2) .

In `getCommitsInRange`, the `range` string is placed as the **first positional argument** right after the `rev-list` subcommand, before the trailing `--` separator:
```
const args = ['rev-list', range, '--reverse', `--oneline`, `--no-abbrev-commit`, '--']
``` [4](#0-3) 

The `--` at the end only separates revisions from pathspecs — it does **not** protect the `range` token, which is evaluated by git's own revision-argument parser as soon as it is seen. Execution itself is safe from shell metacharacter injection because `git()` calls dugite's `exec(args, path, opts)` with an argv array (no shell) [5](#0-4) , so classic shell injection is not possible. The concern here is **git option-argument injection**, not shell injection.

Because `revRange` simply concatenates `${from}..${to}` [6](#0-5) , if a malicious `from`/`to` (a crafted `base.sha` or `head.sha` from a PR API response) begins with a recognized git option prefix such as `--pretty=`, `--output=`, or similar, the combined token `"--pretty=format:%H%x00..<othersha>"` is still parsed by git's option matcher via `skip_prefix`-style checks, which only look at the *prefix* of the whole argv token, not the full string. This means:

1. `commitSummaryRe = /^([a-z0-9]{40}) (.*)$/` [7](#0-6)  can silently fail to match or match different data than intended if the output format is redefined via an injected `--pretty=`-style token, corrupting the `CommitOneLine[]` (`sha`/`summary` pairs) returned to callers.
2. Because `getCommitsBetweenCommits` feeds this list directly into the rebase/cherry-pick preview flow in `rebase.ts`/`dispatcher.ts`/`update-branch.ts`, a corrupted commit list can cause the app to silently apply, skip, or mis-order commits during a rebase — this squarely matches the in-scope impact "silent corruption of what the user commits or pushes."
3. Certain git options (e.g. `--output=<path>`) open a file for writing before/independent of revision validation, which in the worst case could redirect git's output to an attacker-chosen path — a potential file-write-outside-repo primitive, though I was not able to execute git locally to confirm the exact open-before-parse timing for the specific git version bundled with Desktop.

I could not find any SHA-format validation (e.g., `/^[0-9a-f]{40}$/`) applied to `pr.head.sha`/`pr.base.sha` anywhere between the API response and `getCommitsInRange`, nor any use of `--` immediately before the `range` argument to force git to treat it strictly as a revision rather than an option.

### Title
Unsanitized PR head/base SHA reaches `git rev-list` as a leading argument, enabling git option injection and corrupted commit parsing - (File: app/src/lib/git/rev-list.ts)

### Summary
`getCommitsInRange` places the caller-supplied `range` (built from `IAPIPullRequestRef.sha` values returned by the GitHub API) as the first argument to `git rev-list`, ahead of the `--` end-of-options marker, with no validation that the SHA is a well-formed 40-character hex string.

### Finding Description
`revRange(from, to)` returns `"${from}..${to}"` with no escaping or validation [6](#0-5) . `getCommitsBetweenCommits` passes PR-derived `baseBranchSha`/`targetBranchSha` straight into this function [3](#0-2) , and `getCommitsInRange` puts the resulting string as `args[1]`, before any `--` separator, when invoking `git rev-list` [4](#0-3) . Since `pr.head.sha`/`pr.base.sha` are stored from the raw API object without format validation [2](#0-1) , a malicious/compromised GitHub API response (or Enterprise Server) can supply a SHA value that is actually a git option string, which git's revision parser will honor as an option rather than a revision.

### Impact Explanation
A corrupted `range` token can change what `git rev-list` outputs (e.g., via an injected `--pretty=` option), causing `commitSummaryRe` to mismatch and yielding a wrong/incomplete `CommitOneLine[]` list that downstream rebase/cherry-pick logic (`rebase.ts`) relies on to decide which commits to replay — a silent corruption of what gets committed during the rebase flow. Depending on the specific option injected (e.g., an `--output=` style flag), it may also be possible to influence where git writes command output, though I could not fully verify this behavior at runtime.

### Likelihood Explanation
Requires the attacker to control (or MITM/spoof) a GitHub API PR response's `head.sha`/`base.sha` fields, which is plausible for a malicious GitHub Enterprise Server host or a compromised/malicious API response per the stated scope ("a GitHub API object" is attacker-controlled).

### Recommendation
Validate that any SHA used to build a git revision range matches a strict `^[0-9a-f]{7,40}$` pattern before use, and/or always place `--` immediately before the revision argument (and after `--`, nothing) is not sufficient here since the injection happens on the revision itself — the fix should be input validation on the SHA, not argument ordering.

### Proof of Concept
1. Mock a GitHub API `GET /repos/:owner/:repo/pulls` response where `head.sha` is `"--pretty=format:%H%x00"` instead of a real 40-hex SHA.
2. Let this flow through `pull-request-store.ts` storage into a `PullRequest` model, then into a rebase/merge-preview action that calls `getCommitsBetweenCommits(repository, baseSha, "--pretty=format:%H%x00")`.
3. Observe the constructed `args` passed to `git()` in `getCommitsInRange` — the crafted string ends up as part of `range` at `args[1]`, ahead of the `--` separator, and is passed unescaped to `git rev-list`.
4. Verify (via mocked/spied `git` call or an actual git invocation) whether the output format/behavior of `rev-list` changes, corrupting the `commitSummaryRe` match and the returned commit list.

Note: full confirmation of the exact git-side option-parsing behavior (whether it treats the whole concatenated string as the option value, and whether it opens/writes a file before failing) requires running git directly, which I could not do in this review; a Devin session with terminal access could execute step 4 to confirm concretely.
