### Title
`mWOMSVBaseRewarder._calExpireForfeit()` never forfeits rewards, breaking the mWomSV lock-forfeit redistribution mechanism - (File: `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit()` is supposed to slash a portion of a user's accrued reward based on their current mWomSV "rewardable percent" (i.e., how much of their locked position is still eligible/vested), and re-queue the forfeited amount as new rewards for the remaining stakers — exactly like the sibling `vlMGPBaseRewarder` does. Instead, the mWomSV version is implemented so that the forfeited amount is always `0`, regardless of the user's actual eligibility.

### Finding Description
Compare the two "reward forfeit" implementations that are otherwise structurally identical:

`vlMGPBaseRewarder._calExpireForfeit` correctly queries the locker for the account's real rewardable percentage and computes the forfeit from it: [1](#0-0) 

`mWOMSVBaseRewarder._calExpireForfeit`, however, sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0`, and the `getRewardablePercentWAD`-style check that exists on `mWomSV` (confirmed present in `wombat/mWomSV.sol`) is never called at all: [2](#0-1) 

This function is invoked from `_sendReward`, which runs on every ordinary user reward claim path (`getReward`/`getRewards`, callable via MasterMagpie by any mWomSV holder harvesting rewards): [3](#0-2) 

Because `forfeitAmount` is always `0`, the `_queueNewRewardsWithoutTransfer` re-distribution branch is dead code for mWomSV rewards: [4](#0-3) 

### Impact Explanation
The forfeiture mechanism exists to slash reward entitlement from users whose mWomSV lock position is not (or no longer) fully "rewardable" (e.g., partially unlocked/expired positions), redistributing the slashed portion to the remaining, still-eligible stakers via `rewardPerTokenStored`. With this check permanently disabled:
- Users who should be penalized by the protocol's lock/vesting design instead always receive 100% of their computed reward, walking away with yield that was supposed to be forfeited and redistributed.
- The forfeited yield that legitimate long-term stakers were entitled to is permanently lost — it is neither slashed from the departing user nor re-queued into `rewardPerTokenStored` for other stakers, since `_queueNewRewardsWithoutTransfer(forfeitAmount, ...)` is only called `if(forfeitAmount > 0)`, which never triggers.
- This results in permanent misallocation/loss of reward-token yield rightfully due to other, fully-vested stakers — a permanent freezing/loss of unclaimed yield for those users, triggered purely by ordinary reward-claim transactions with no privileged or malicious actor involved.

### Likelihood Explanation
High. This path is exercised on every normal `getReward`/`getRewards` call for the mWomSV reward pool — no special conditions, admin actions, or attacker sophistication are required. Any user whose mWomSV position is not fully "rewardable" will trigger the broken logic simply by claiming rewards through the standard flow.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`: query the actual rewardable percentage from the `mWOMSV` locker (e.g., `mWOMSV.getRewardablePercentWAD(_account)`) and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`, so the slashed portion is correctly withheld and re-queued to remaining stakers via `_queueNewRewardsWithoutTransfer`.

### Proof of Concept
1. A user stakes mWomSV and accrues MGP-denominated rewards in `mWOMSVBaseRewarder`.
2. Assume the user's position should only be, say, 50% "rewardable" per `mWomSV`'s lock-forfeit rules (e.g., partially exited lock) — under correct behavior, `getReward`/`getRewards` should forfeit 50% of the accrued reward back into `rewardPerTokenStored` for other stakers.
3. The user calls `getReward`/`getRewards` (via MasterMagpie), which internally calls `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`.
4. Because `_calExpireForfeit` hardcodes `rewardableAmount = _amount`, `forfeitAmount` computes to `0` regardless of the account's actual lock/vesting state.
5. The user receives 100% of the accrued reward (`toSend = userRewards - 0`), and no funds are re-queued for other stakers — permanently denying the correctly-forfeited yield to the remaining honest stakers.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**mWOMSVDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }
