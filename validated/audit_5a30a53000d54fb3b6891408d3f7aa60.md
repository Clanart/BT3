## Confirmed Local Analog

At `placeOrder`, the fee token is resolved live from the host and the actual ERC-20 amount is pulled from the user into the gateway under a fixed sentinel key: [1](#0-0) 

At redemption (`_withdraw` / `withdraw`), the fee is paid out by re-querying `IDispatcher(host()).feeToken()` **at redemption time**, rather than using the token that was actually escrowed at placement time: [2](#0-1) [3](#0-2) 

The escrow accounting itself is keyed only by the sentinel `TRANSACTION_FEES` constant — not by the actual token address that was collected: [4](#0-3) 

### Title
Fee-token drift between `placeOrder` and escrow redemption causes wrong-token payout / fund lock in IntentGatewayV2 - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` escrows the order's relayer/dispatch fee by pulling `IDispatcher(host()).feeToken()` **at order-placement time** and records only the *amount* under the fixed sentinel key `TRANSACTION_FEES` in `_orders[commitment][...]` — it never records *which* token was actually collected. When the order is later settled (`_withdraw`/`withdraw` on `RedeemEscrow` or `RefundEscrow`), the code re-reads `IDispatcher(host()).feeToken()` **at redemption time** and transfers that *current* token to the beneficiary. If Hyperbridge governance updates the host's `feeToken` (a supported, documented operation — see `EvmHost.updateHostParams`) between order placement and redemption, the gateway ends up paying the beneficiary in a token that was never actually escrowed for that order.

### Finding Description
`EvmHost` explicitly supports rotating `feeToken` via governance-driven `updateHostParams`, guarding only the **host's own** balance of the old fee token: [5](#0-4) 

This guard has no visibility into balances held by downstream `IApp` contracts such as `IntentGatewayV2`. The gateway's own escrow bookkeeping (`_orders[commitment][TRANSACTION_FEES] = order.fees`) stores only a *value*, with the *token identity* implicitly tied to whatever `feeToken()` returned at `placeOrder` time. Nothing pins that token address into the escrow record or the order commitment fee slot itself.

At settlement, `_withdraw` (EVM) / `withdraw` (Tron variant) blindly resolves `feeToken()` again:
```
uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
if (fees > 0) {
    delete _orders[body.commitment][TRANSACTION_FEES];
    IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
}
```
If `feeToken()` has changed since placement:
- The gateway attempts to `safeTransfer` the *new* fee token for an amount that was never escrowed in that token. Since the gateway is a shared contract holding many orders' input/output escrows and dust concurrently, if the gateway happens to hold a balance of the new fee token (from other unrelated orders' `inputs`/dust), this **redirects funds belonging to other orders/users to this beneficiary** — a wrong-beneficiary/wrong-amount payout out of a shared pool, structurally identical to the reported bug's core defect: a value accounted under one identity gets moved through a stale/mismatched lookup instead of the one that actually corresponds to it.
- If no such balance exists, the transfer reverts, permanently orphaning the originally-escrowed old-fee-token balance (undiscoverable by normal `_orders` bookkeeping, since the record was already `delete`d before the transfer attempt reverts the whole transaction — actually the delete and transfer are in the same call so a revert rolls back the delete too, but the fee remains stuck forever unless governance manually reconstructs the historical fee-token address and issues a `SweepDust` for it) — mirroring the original report's "locked funds in wrong/unintended location" impact.

### Impact Explanation
This breaks the Hyperbridge pivot requiring that "bridged assets, order escrow, refunds, paymaster balances, relayer rewards ... must move exactly once and only to the rightful beneficiary and amount." A fee-token rotation — a normal, expected governance operation supported by `EvmHost` — silently desynchronizes the token identity backing every in-flight order's escrowed fee, producing either (a) transfer of unrelated escrowed funds belonging to other orders to an arbitrary beneficiary, or (b) permanent loss of the originally escrowed fee amount.

### Likelihood Explanation
Fee-token changes are an intended, documented governance capability (`HostParams.feeToken` update path), and it is realistic for many `IntentGatewayV2` orders to be in-flight (unfilled/unredeemed) at any time such a rotation occurs. No malicious peer, relayer, or compromised key is required — this is triggered purely by ordinary governance operation combined with the passage of time, and it silently corrupts the correctness of the escrow.

### Recommendation
Persist the actual fee-token address alongside the escrowed fee amount at `placeOrder` time (e.g., store it in the order struct's fee accounting or in a dedicated `_orderFeeToken[commitment]` mapping), and use that stored token address — not a live `feeToken()` re-query — when redeeming or refunding the fee in `_withdraw`/`withdraw`. Additionally, mirror `EvmHost`'s own protection by having `IntentGatewayV2.onAccept`'s `UpdateParams`/host-level `feeToken` rotation path reject or drain-check outstanding fee escrows before allowing the change, or require draining all `TRANSACTION_FEES` balances before feeToken rotation is permitted.

### Proof of Concept
1. User calls `placeOrder` with `order.fees = 100e18` while `host.feeToken() == TokenA`. Gateway pulls 100 `TokenA` from the user and sets `_orders[commitment][TRANSACTION_FEES] = 100e18`.
2. Before the order is filled/redeemed, Hyperbridge governance rotates `EvmHost.feeToken` from `TokenA` to `TokenB` via `updateHostParams` (permitted since the host's own `TokenA` balance is zero — this check does not inspect `IntentGatewayV2`'s balance).
3. A different, unrelated order deposits `TokenB` into the gateway as part of its `inputs` escrow (normal flow), giving the gateway a nonzero `TokenB` balance.
4. The first order is later filled/refunded; `_withdraw` executes `IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, 100e18)`, which now resolves to `TokenB` and pays out 100 `TokenB` — drawn from the pool that actually belongs to the second, unrelated order's escrow — to the first order's beneficiary, an amount/token never legitimately escrowed for that beneficiary.
