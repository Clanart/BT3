### Title
Case/typo-sensitive `action` field comparison silently degrades intended `block` rules to advisory-only `warn` - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`Rule.from_dict` reads the `action` frontmatter field verbatim with no normalization or validation: `action=frontmatter.get('action', 'warn')` [1](#0-0) . The dataclass field itself is documented only as `"warn" or "block" (future)` with no enum/allowed-value enforcement [2](#0-1) . Downstream, `RuleEngine.evaluate_rules` uses a strict, case-sensitive equality check `if rule.action == 'block':` to route matches into `blocking_rules`; anything else (including `"Block"`, `"BLOCK"`, `"blck"`, or trailing whitespace) falls through to the `else` branch and is appended to `warning_rules` instead [3](#0-2) . Warning-only matches produce a `systemMessage` but return no `hookSpecificOutput.permissionDecision: deny`, so the operation is allowed to proceed [4](#0-3) , unlike the blocking path which explicitly returns `"permissionDecision": "deny"` for `PreToolUse`/`PostToolUse` events [5](#0-4) .

Rule files are loaded directly from the repository's own `.claude/hookify.*.local.md` files via `glob.glob(os.path.join('.claude', 'hookify.*.local.md'))` with no signature, provenance, or origin check [6](#0-5) . Because these files are ordinary repository content, an attacker who can contribute a PR (or influence `/hookify`'s LLM-driven rule generation, per the documented `action: {warn|block}` template [7](#0-6) ) can introduce or modify a rule file with a subtly malformed `action` value (e.g. `action: Block` — visually indistinguishable from `action: block` to a human reviewer). The parser accepts it without error, the rule silently becomes an advisory `warning_rule`, and the maintainer believes a blocking guardrail (e.g. against `rm -rf`, `dd`, sensitive file writes) is active when it is not.

### Impact Explanation
This is a silent, code-reviewable-yet-deceptive downgrade of a security control: a rule file that a maintainer visually approves as `action: block` (case/spelling drift makes it look correct) never actually blocks the dangerous Bash command or file write it was written to prevent — Claude proceeds with the systemMessage shown but the operation still executes. This directly breaks the "deny means deny" invariant for hookify's PreToolUse/PostToolUse blocking enforcement [8](#0-7) .

### Likelihood Explanation
Highly feasible and fully deterministic — no LLM behavior or privilege is required at the code level; a plain-text edit to a `.local.md` frontmatter value (e.g. one uppercase letter or a single-character typo) reliably reproduces the bug on every load, since `load_rule_file`/`Rule.from_dict` performs no case-folding or allowed-value validation [9](#0-8) . The only precondition is that such a file (attacker-authored, PR-contributed, or LLM-generated with drift) is present in `.claude/` and loaded by `load_rules()`.

### Recommendation
In `Rule.from_dict`, normalize and validate the `action` value: lower-case/strip the input, map known synonyms (e.g. `block`, `deny`) to `"block"`, and raise a `ValueError` (surfaced as a load warning, as already done for `ValueError` in `load_rule_file`) for any unrecognized action value instead of silently defaulting to `"warn"`. Apply the same allow-list check in `RuleEngine.evaluate_rules` as a defense-in-depth measure so an unrecognized action can never be treated as non-blocking by default.

### Proof of Concept
Add a unit test in a new `plugins/hookify/tests/test_config_loader.py`:
```python
import pytest
from hookify.core.config_loader import Rule

@pytest.mark.parametrize("action_value", ["Block", "BLOCK", "blck", "block ", "deny"])
def test_action_typo_does_not_silently_warn(action_value):
    frontmatter = {"name": "block-rm", "enabled": True, "event": "bash",
                   "pattern": r"rm\s+-rf", "action": action_value}
    rule = Rule.from_dict(frontmatter, "dangerous!")
    # Expect either normalization to 'block' or an explicit failure —
    # never a silent 'warn' for a near-miss of 'block'.
    assert rule.action == "block" or rule.action not in ("warn",)
```
And an integration assertion against `RuleEngine.evaluate_rules`:
```python
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

rule = Rule(name="block-rm", enabled=True, event="bash",
            conditions=[Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")],
            action="Block", message="blocked")
result = RuleEngine().evaluate_rules([rule], {
    "hook_event_name": "PreToolUse", "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"}
})
assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Currently this second assertion fails: the result only contains `systemMessage` with no `permissionDecision: deny`, demonstrating the operation is allowed to proceed despite the rule author's intent to block.
