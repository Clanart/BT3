### Title
Stale `DiffSelection` line indices after hunk expansion silently flip which lines are staged/committed - ([File: app/src/ui/diff/text-diff-expansion.ts])

### Summary
When a user expands a diff hunk (up/down or the whole file) in the side-by-side diff viewer, `expandTextDiffHunk`/`expandWholeTextDiff` rebuild the hunk list and shift the `unifiedDiffStart`/`unifiedDiffEnd` absolute-line indices of every hunk that follows the expanded one by `numberOfNewDiffLines`, and merge adjacent hunks when the expansion closes the gap between them [1](#0-0) . The user's partial-staging selection (`DiffSelection`), however, is a set of *absolute line indices* (`divergingLines`) computed against the *previous* hunk layout [2](#0-1)  and is not re-derived/shifted when the diff is replaced by the expanded diff in `onExpandWholeFile`/`onExpandHunk` [3](#0-2) [4](#0-3) .

### Finding Description
`isSelected(lineIndex)` and `isSelectable(lineIndex)` in `DiffSelection` operate purely on the numeric absolute index of a line within the diff, with no knowledge of which hunk or which source line that index used to represent [5](#0-4) . `formatPatch()`, which builds the git patch actually applied to the index/commit, resolves selection state by recomputing `absoluteIndex = hunk.unifiedDiffStart + lineIndex` against the *current* diff hunks and calling `file.selection.isSelected(absoluteIndex)` [6](#0-5) .

The bug-class parallel to the smart-contract finding is structural: in the original report, a shared value (`valueChange`) computed against one accounting frame (pre-rebalance) was applied unmodified to a different frame (the underbalanced side) without adjusting for the different basis, silently corrupting the balance. Here, a shared value (the *set of diverging line indices*, i.e. the "not default" selection state) computed against one indexing frame (the diff before expansion) is carried over unmodified and reused against a different frame (the diff after expansion, whose hunk `unifiedDiffStart` values have shifted or merged), silently corrupting which lines are treated as selected.

Concretely: `expandTextDiffHunk` shifts every following hunk's `unifiedDiffStart`/`unifiedDiffEnd` by `numberOfNewDiffLines` [7](#0-6) , and when hunks are merged the header/line-index layout of the merged hunk differs from either original hunk [8](#0-7) . `onExpandWholeFile` swaps `this.state.diff` for the expanded diff and stores the old diff only for later "collapse" restoration (`this.diffToRestore`), it does not touch `this.props.file.selection` at all [3](#0-2) . `onExpandHunk` similarly just calls `expandHunk(...)` and updates local UI state, again with no re-basing of the file's `DiffSelection` object [4](#0-3) .

The only place that reconciles selection state to a new diff is `withSelectableLines`, invoked from `app-store.ts` when a *file's underlying diff is reloaded from disk* after a status refresh [9](#0-8) ; this path is not exercised by the in-memory hunk-expansion UI action, which mutates the rendered diff directly in component state.

### Impact Explanation
Because `divergingLines` indices are absolute and not remapped, after an expansion that shifts or merges hunks, the same numeric index in the (unchanged) `DiffSelection` object now refers to a different physical diff line than it did before expansion. When the user then commits a partial selection (some lines checked, some not), `formatPatch()` will stage/exclude the wrong lines relative to what the user intended for the post-expansion view — i.e., it can silently include lines the user thought were excluded (or vice-versa) in the commit/patch that gets applied to the index and ultimately pushed. This is a "silent corruption of what the user commits" class of bug: the resulting git object history reflects unintended content with no error or warning shown to the user.

### Likelihood Explanation
Requires no attacker capability beyond normal usage: any user doing partial (line-level) staging via the side-by-side diff view, expanding a hunk (up/down or "Expand Whole File") before finishing their selection, is on the affected path. This is a fairly common workflow (reviewing more context before committing part of a change). No malicious repository content is strictly required, though a repository/file crafted to produce many small hunks close together (increasing the chance that expansion merges hunks or shifts indices non-trivially) would make the corruption more likely and more severe, fitting the "attacker controls a cloned/fetched repository" impact criterion (a repo authored to maximize hunk churn on expansion could reliably desynchronize a reviewer's partial selection).

### Recommendation
When a hunk is expanded or merged (`expandTextDiffHunk`, `expandWholeTextDiff`, and the "collapse" path that restores `diffToRestore`), recompute/re-base the associated `DiffSelection`'s `divergingLines` (and `selectableLines`) against the new hunk layout before or immediately after swapping `state.diff`, analogous to what `withSelectableLines` already does for full diff reloads. Concretely, build the new `selectableLines` set from the expanded diff's hunks and translate any previously diverging indices through the old-hunk → new-hunk line mapping (matching on `oldLineNumber`/`newLineNumber` rather than raw absolute index) rather than leaving the `DiffSelection` untouched across a diff-shape change.

### Proof of Concept
1. Open a file with two hunks separated by more than `DefaultDiffExpansionStep` (20) lines of unchanged context, so they are shown as separate hunks (`DiffHunkExpansionType.Both` per `getHunkHeaderExpansionType` [10](#0-9) ).
2. In the Changes view, deselect a single added line inside the second hunk (partial selection), which records that line's absolute index in `divergingLines`.
3. Click "Expand" on the first hunk downward enough times (or use "Expand Whole File") so that the gap between hunk 1 and hunk 2 is closed and they get merged via `mergeDiffHunks`, which drops the second hunk's header line and shifts all of hunk 2's remaining lines' absolute indices [11](#0-10) [1](#0-0) .
4. Without reselecting anything, commit the partial selection. `formatPatch` recomputes `absoluteIndex` for each line using the *new* merged hunk's `unifiedDiffStart` and checks it against the stale `divergingLines` set [6](#0-5) ; because the index that used to correspond to the deselected line now points to a different line (shifted by the removed hunk-header line and any added context lines), a different line than the one the user deselected ends up included in (or excluded from) the resulting commit.

Note: I was unable to fully trace the exact `expandHunk`/`getSelection` wiring in `side-by-side-diff.tsx` before running out of tool calls, so the precise sequence of state updates inside that component (and whether any other code path re-bases selection during expansion) could not be triple-confirmed with a full read of that file. The core defect — that `DiffSelection.divergingLines` are absolute-index based and that `text-diff-expansion.ts` freely shifts/merges those absolute indices without any selection-remapping API being invoked from the expansion call sites I did inspect — is confirmed directly from the cited files.

/** Merges two consecutive hunks into one. */
function mergeDiffHunks(hunk1: DiffHunk, hunk2: DiffHunk): DiffHunk {
  // Remove the first line in both hunks, because those are hunk header lines
  // that will be replaced by a new one for the resulting hunk.
  const allHunk1LinesButFirst = hunk1.lines.slice(1)
  const allHunk2LinesButFirst = hunk2.lines.slice(1)

  const newHunkHeader = new DiffHunkHeader(
    hunk1.header.oldStartLine,
    hunk1.header.oldLineCount + hunk2.header.oldLineCount,
    hunk1.header.newStartLine,
    hunk1.header.newLineCount + hunk2.header.newLineCount
  )

  // Create a new hunk header line for the resulting hunk
  const newFirstHunkLine = new DiffLine(
    newHunkHeader.toDiffLineRepresentation(),
    DiffLineType.Hunk,
    null,
    null,
    null,
    false
  )

  const newHunkLines = [
    newFirstHunkLine,
    ...allHunk1LinesButFirst,
    ...allHunk2LinesButFirst,
  ]

  return new DiffHunk(
    newHunkHeader,
    newHunkLines,
    hunk1.unifiedDiffStart,
    hunk1.unifiedDiffStart + newHunkLines.length - 1,
    // The expansion type of the resulting hunk will match the expansion type
    // of the first hunk:
    // - If the first hunk can be expanded up, it means it's the very first
    //   hunk, so the resulting hunk will be the first too.
    // - If the first hunk can be expanded but short, that doesn't change after
    //   merging it with the second one.
    // - If it can be expanded up and down (meaning it's a long gap), that
    //   doesn't change after merging it with the second one.
    // - It can never be expanded down exclusively, because only the last dummy
    //   hunk can do that, and that will never be the first hunk in a merge.
    hunk1.expansionType
  )
}

export function getHunkHeaderExpansionType(
  hunkIndex: number,
  hunkHeader: DiffHunkHeader,
  previousHunk: DiffHunk | null
): DiffHunkExpansionType {
  const distanceToPrevious =
    previousHunk === null
      ? Infinity
      : hunkHeader.oldStartLine -
        previousHunk.header.oldStartLine -
        previousHunk.header.oldLineCount

  // In order to simplify the whole logic around expansion, only the hunk at the
  // top can be expanded up exclusively, and only the hunk at the bottom (the
  // dummy one, see getTextDiffWithBottomDummyHunk) can be expanded down
  // exclusively.
  // The rest of the hunks can be expanded both ways, except those which are too
  // short and therefore the direction of expansion doesn't matter.
  if (hunkIndex === 0) {
    // The top hunk can only be expanded if there is content above it
    if (hunkHeader.oldStartLine > 1 && hunkHeader.newStartLine > 1) {
      return DiffHunkExpansionType.Up
    } else {
      return DiffHunkExpansionType.None
    }
  } else if (distanceToPrevious <= DefaultDiffExpansionStep) {
    return DiffHunkExpansionType.Short
  } else {
    return DiffHunkExpansionType.Both
  }
}
