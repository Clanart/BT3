### Title
FROST cached preprocess seed reused across `share`/`complete` re-executions enables nonce reuse and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's `SigningProtocol::preprocess_internal` caches a FROST preprocess RNG seed in the DB under a context key, and every invocation of `share_internal` (and transitively `complete`) deterministically reconstructs the *same* nonces from that cached seed via `AlgorithmSignMachine::from_cache`. The cache is never deleted or rotated. Any two `share_internal` executions under the same `(b"DkgConfirmer", attempt)` context that sign differing effective inputs (different `msg` or different participant/preprocess sets) reuse identical nonce scalars `d, e`, allowing third-party recovery of the validator's MuSig secret key share — the exact "multiple callbacks sharing one object, all invalidated/reused once one completes" lifetime bug from the File Picker CVE.

### Finding Description
`CachedPreprocesses` maps `context -> [u8; 32]` seed: [1](#0-0) 

On first use a seed is generated, XOR-encrypted, and stored; on every subsequent call the *same* seed is decrypted and fed to `from_cache`: [2](#0-1) 

`from_cache` → `seeded_preprocess` derives `nonces` and `commitments` deterministically from `ChaCha20Rng::from_seed(*seed.0)`: [3](#0-2) 

There is no `CachedPreprocesses::remove`/`delete` anywhere — the same nonce pair is re-issued for every `share_internal` call under that context: [4](#0-3) 

Critically, `DkgConfirmer::complete` re-executes `share_internal` a second time to rebuild the signature machine: [5](#0-4) 

So within a single attempt there are at minimum two `sign()` executions with identical nonces: once when `share()` produces this node's share (with whatever preprocess set was available), and once inside `complete()` (with the preprocess set passed at completion time). The context `("DkgConfirmer", attempt)` is constant for both: [6](#0-5) 

If the preprocess map differs between the two calls — e.g., additional validators' preprocesses became known before `complete`, or a different `KeyPair`/removed-set reaches the message — the binding factors `rho` (computed over the participant transcript and `hash_msg`) and/or the challenge differ, while the nonce scalars `d, e` are identical: [7](#0-6) 

The FROST spec's own comment acknowledges this failure mode: "the only way for this seeded RNG to fail is if a preprocess is loaded multiple times": [8](#0-7) 

### Impact Explanation
FROST share `s_i = λ_i·sk_i + (d_i + e_i·ρ_i)·c`. Two published shares under the same `(d_i, e_i)` but different `(ρ_i, c_i)` yield `sk_i` by linear elimination: knowing `s_1, s_2, ρ_1, ρ_2, c_1, c_2, λ_1, λ_2` (all public in the transcripts/commitments) an attacker recovers the validator's MuSig secret share, then the full static secret `self.key` used for `musig(...)`. Recovery of a validator's signing key enables forging that validator's participation in DKG confirmations and is a direct, documented consequence of preprocess reuse.

### Likelihood Explanation
Reachable by an unprivileged party only insofar as the two `share_internal` executions see different inputs. `share()` and `complete()` are driven by finalized tributary data; the preprocess set available at share time vs. completion time can legitimately differ (validators publish preprocesses asynchronously, and `complete` may be invoked with a different/fuller set than `share` used, or with a different `key_pair` if the confirmation payload differs). The shares are broadcast publicly on the tributary, so any observer can perform the recovery once divergence occurs. No validator needs to be malicious — ordinary timing divergence between the two calls suffices. Uncertainty: I did not fully trace `handle.rs` to confirm how often the preprocess set passed to `complete` diverges from the set used in `share`; if they are guaranteed identical byte-for-byte (same set, same key_pair), the two signatures are identical and no leak occurs — but nothing in the code enforces that equality, and the header comment lists this on-chain-preprocess-matches check as an open TODO. [9](#0-8) 

### Recommendation
- Delete or rotate the cached seed after a successful `sign()`: add `CachedPreprocesses::del(txn, &context)` once a share for a given context has been produced, so a second `share_internal` under the same context errors instead of silently reusing nonces.
- Before publishing a share, verify on-chain that the commitments derived from the cached seed equal the commitments already published for this context (the TODO at line 51), so a rebuilt/re-executed session with divergent inputs aborts rather than signing.
- Bind the exact preprocess set digest and message hash into the `CachedPreprocesses` context key so any divergence produces a distinct (fresh-seeded or hard-error) session rather than reuse.

### Proof of Concept
1. DKG attempt `a` begins; `preprocess_internal` stores seed `S` under `("DkgConfirmer", a)` and publishes commitments `C(S)`.
2. `DkgConfirmer::share(preprocesses_A, kp)` → `share_internal` → `from_cache(S)` → `sign(preprocesses_A, msg_A)` → publishes share `s_1 = λ_A·sk + (d + e·ρ_A)·c_A`.
3. More preprocesses finalize; `DkgConfirmer::complete(preprocesses_B, kp', shares)` → `share_internal(preprocesses_B, kp')` → `from_cache(S)` again → `sign(preprocesses_B, msg_B)` internally produces share `s_2 = λ_B·sk + (d + e·ρ_B)·c_B` with identical `d, e` (same ChaCha20Rng seed).
4. Observer with `(s_1, ρ_A, c_A, λ_A)` and `(s_2, ρ_B, c_B, λ_B)` — all derivable from the public commitments/participant set — solves the 2×2 linear system for `sk` whenever `ρ_A·c_A ≠ ρ_B·c_B`, i.e., whenever the preprocess set or message differed at all.
