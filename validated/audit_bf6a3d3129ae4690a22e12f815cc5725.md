### Title
Identity encryption key accepted, producing a publicly computable ECDH secret and leaking DKG shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
PedPoP accepts the identity group element as a participant's encryption key because `EncryptionKeyMessage::read` uses `C::read_G`, which enforces canonicality but does not reject identity. When another participant encrypts a secret share to that identity key, ECDH evaluates to the identity point. Since the cipher derives its ChaCha20 key solely from the DKG context and the serialized ECDH point, anyone who observes the encrypted share can reconstruct the keystream and recover the secret share.

### Finding Description
`EncryptionKeyMessage::read` deserializes `enc_key` with `C::read_G` and performs no identity check. [1](#0-0)  The generic `Ciphersuite::read_G` implementation validates the point encoding and canonicality, then returns the point without excluding the identity. [2](#0-1)  This contrasts with FROST's `Curve::read_G`, which explicitly rejects identity points. [3](#0-2) 

During share distribution, the registered key is stored without validation and later used as the ECDH public key. [4](#0-3)  Encryption computes `public * private`, so an identity public key always yields an identity shared secret regardless of the ephemeral private scalar. [5](#0-4)  That shared secret is serialized into the public transcript used to derive the ChaCha20 key. [6](#0-5)  Finally, `Encryption::encrypt` passes the registered recipient key directly into `encrypt`. [7](#0-6) 

### Impact Explanation
An unprivileged DKG participant can register an identity encryption key and cause every peer's encrypted secret share for that participant to be encrypted under a publicly known key. Any observer of the authenticated DKG messages can derive the same ChaCha20 key, decrypt the `SecretShare` bytes, and recover the participant's received shares. Recovering enough shares can enable reconstruction of the threshold secret or at least compromise key material that PedPoP is designed to keep confidential.

The recipient's own decryption path also accepts the resulting ciphertext normally: it derives the same identity ECDH value and decrypts the message before checking that the decoded scalar satisfies the share commitments. [8](#0-7)  Thus the malformed registration can pass the protocol while stripping confidentiality from the share transfer.

### Likelihood Explanation
The attack requires only a malicious participant to place a canonical identity encoding in the `enc_key` field of its public `EncryptionKeyMessage`. No discrete-log knowledge, validator compromise, collusion, malformed encoding, or implementation misuse is required. The identity key is accepted during `EncryptionKeyMessage::read`, and every peer's subsequent `encrypt` call will deterministically use it.

### Recommendation
Reject identity points for all public keys and ephemeral keys used in PedPoP encryption. At minimum, `EncryptionKeyMessage::read` should check `msg.enc_key.is_identity()` and return an error. `EncryptedMessage::read` should likewise reject an identity `key`, since that value also becomes an ECDH public input. Prefer introducing a dedicated non-identity point reader for DKG encryption inputs rather than relying on the generic canonical `Ciphersuite::read_G`.

### Proof of Concept
1. A malicious participant serializes an `EncryptionKeyMessage` whose `enc_key` field is the canonical encoding of `C::G::identity()`.
2. Honest peers accept it because `C::read_G` only requires canonical point encoding and does not reject identity.
3. When an honest peer sends a share to that participant, `encrypt` computes:

   ```rust
   ecdh = identity * ephemeral_secret = identity
   ```

4. `cipher` derives the ChaCha20 key from the public context and `identity.to_bytes()`. An observer can execute the same transcript derivation and apply the resulting keystream to `msg`.
5. The observer recovers the serialized `SecretShare`; after canonical scalar decoding, they obtain the actual field-element share intended only for the malicious participant.

The vulnerable flow is:

```text
EncryptionKeyMessage.enc_key = identity
        |
        v
Encryption::encrypt(..., to = identity, share)
        |
        v
ecdh(ephemeral_secret, identity) = identity
        |
        v
ChaCha20 key = transcript(context || identity.to_bytes())
        |
        v
share ciphertext publicly decryptable
```

  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
