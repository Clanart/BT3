### Title
Untrusted `ReceivedOutput` bytes can fabricate unspendable wallet inputs - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an attacker-controlled scalar offset, arbitrary `TxOut`, and arbitrary `OutPoint` without proving that the referenced output exists or was produced by `Scanner`. A forged object can therefore enter `SignableTransaction::new`, where its claimed value is counted as wallet funds and its claimed outpoint is inserted into the transaction. `SignableTransaction::multisig` only validates that the serialized `script_pubkey` matches the tweaked threshold key; it does not validate that the outpoint exists, belongs to the wallet, or contains the claimed amount. The result is a wallet-accepted input that reports funds which cannot actually be spent. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ReceivedOutput` is the wallet’s internal representation of a spendable deposit: an HDKD offset, the previous output’s `TxOut`, and the `OutPoint` identifying it on-chain. The trusted producer is `Scanner::scan_transaction`, which derives this object only after matching an output’s `script_pubkey` against a registered wallet script and binding it to the transaction’s actual `txid` and `vout`. [4](#0-3) 

The deserializer bypasses that provenance. `ReceivedOutput::read` accepts any canonical scalar, then consensus-decodes any `TxOut` and any `OutPoint`, returning the composite object without checking ownership, existence, maturity, or consistency with a scanner registration. [1](#0-0) 

Downstream, `SignableTransaction::new` trusts those fields. It sums the attacker-controlled `TxOut` values as available inputs, copies each `offset`, and places each attacker-selected `outpoint` directly into a transaction input. [2](#0-1)  The signing eligibility check compares only the supplied previous-output `script_pubkey` to the wallet’s tweaked key; the attacker can satisfy this by copying a legitimate wallet output script while inventing the outpoint and amount. [5](#0-4) 

### Impact Explanation
A forged `ReceivedOutput` can report arbitrary Bitcoin as received and cause the wallet/signing pipeline to construct and threshold-sign a transaction spending a nonexistent or incorrectly valued UTXO. Because the signature commits to the supplied `TxOut` through `Prevouts::All`, the signing machinery authorizes the attacker-shaped transaction once the script check passes. [6](#0-5) 

The resulting transaction cannot be valid on Bitcoin if the outpoint does not exist, was already spent, or has a different amount. This causes funds to be reported received that are not spendable, corrupts balance and coin-selection accounting, and can make the threshold signing ceremony produce a transaction that Bitcoin nodes reject. If a fabricated outpoint references an unrelated UTXO that nevertheless pays to the wallet script with a different amount, the transaction may instead commit to an incorrect value and pay an unintended fee. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
The prerequisite is acceptance of a serialized `ReceivedOutput` from an unauthenticated or attacker-controlled source. No private key, validator compromise, malformed curve point, or protocol participant privilege is needed: the attacker only supplies bytes to `ReceivedOutput::read`. A legitimate wallet `script_pubkey` is public information, and both the previous-output amount and outpoint are attacker-selectable fields. [1](#0-0) [9](#0-8) 

`Offset` does not prevent the attack because the attacker can keep or guess an offset whose tweaked public key maps to the copied wallet script, including the zero offset registered for the base key. `Scanner::new` registers that base script with `Scalar::ZERO`, demonstrating a directly usable offset for outputs paying to the base wallet key. [10](#0-9) 

### Recommendation
Treat `ReceivedOutput` serialization as an internal trusted format rather than a public input format. Prefer not to expose unauthenticated deserialization, or authenticate it with a keyed MAC bound to the wallet/scanner identity.

If public deserialization must remain supported, reconstruct spendability cryptographically before use:

- Require the output to have been found by `Scanner::scan_transaction` or `Scanner::scan_block`.
- Re-scan the referenced transaction and compare `txid`, `vout`, `script_pubkey`, and value.
- Verify the referenced outpoint exists in confirmed blockchain data and is unspent and mature.
- Reject any `ReceivedOutput` whose claimed `TxOut` differs from the chain’s actual `TxOut`.
- In `SignableTransaction::new`, derive `prevouts` and input authority from authenticated chain/scanner state rather than trusting the serialized fields.

### Proof of Concept
Conceptually, an attacker constructs bytes equivalent to:

```rust
ReceivedOutput {
  offset: Scalar::ZERO,
  output: TxOut {
    value: Amount::from_sat(1_000_000),
    // Copied from any legitimate output paying to the wallet's base P2TR key.
    script_pubkey: victim_wallet_script,
  },
  outpoint: OutPoint {
    txid: attacker_chosen_or_nonexistent_txid,
    vout: 0,
  },
}
```

`ReceivedOutput::read` accepts these fields independently, with no ownership or blockchain consistency check. [1](#0-0)  `SignableTransaction::new` then counts `1_000_000` sats as available input and inserts the fabricated outpoint into `tx.input`. [2](#0-1)  Finally, `multisig` accepts the forged input whenever `p2tr_script_buf(keys.offset(Scalar::ZERO).group_key())` equals the copied `script_pubkey`, and the FROST machine signs the invalid spend. [3](#0-2)
