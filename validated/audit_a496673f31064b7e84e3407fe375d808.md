Based on my research, I found a genuine analog in the NFT royalty/offer flow: the royalty amount owed to an NFT creator is computed by dividing the offered amount by the royalty split *before* multiplying by the percentage, exactly mirroring the Tapioca bug's root cause — performing division/truncation on a proxy quantity before the proportional multiplication, which loses precision against the party that should be paid.

### Title
NFT royalty division-before-multiplication truncates royalty payments below the entitled amount - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` and the static `royalty_calculation()` helper both compute the royalty owed to an NFT creator by integer-dividing the offered/requested amount by `royalty_split` (the count of royalty-enabled NFTs on one side of a trade) *before* multiplying by the royalty `percentage` and dividing by `MAX_ROYALTY_BASIS_POINTS`. This mirrors the external report's root cause: dividing by one quantity first (analogous to using "share" units) before applying the percentage-based conversion, instead of doing the multiplication first and dividing once at the end. This ordering systematically truncates the resulting royalty amount to a value less than the mathematically correct proportional amount.

### Finding Description
`compute_royalty_amount`, used when constructing the actual royalty-paying `CreateCoin` in `NFTWallet.make_nft1_offer`, and its display counterpart `royalty_calculation`, both compute: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

and [2](#0-1) 

Both perform `abs(amount) // royalty_split` (integer floor division) first, then multiply by `percentage`, then floor-divide by `10000`. Mathematically the correct proportional royalty is `amount * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`. Truncating during the first division discards remainder information that the later multiplication by `percentage` could have preserved, so the final result is always `<=` the mathematically correct value, and strictly less whenever `amount % royalty_split != 0`.

This is invoked from `make_nft1_offer`, which builds the actual `CreateCoin` royalty payment sent to the NFT creator's address when an offer with multiple royalty-enabled NFTs on one side is completed: [3](#0-2) 

The test suite's own unit test for this function documents the truncation as expected behavior rather than treating it as a bug: `test_small_amount_truncates_to_zero` in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` shows a small `offered_amount` combined with `royalty_split=1` truncating to `0`, and `test_royalty_split_across_multiple_nfts` exercises the `royalty_split > 1` path.

This is directly analogous to the Tapioca `_isSolvent` bug: both compute a proportional (percentage-based) value by applying integer division on an intermediate quantity (`collateralShare` / `amount // royalty_split`) before the percentage multiplication, rather than multiplying first and dividing once at the end, and in both cases the truncation is not in favor of the party owed the correct proportional amount (the protocol's solvency margin / the NFT creator's royalty).

### Impact Explanation
Every offer taker or maker who structures a trade so that a fungible payment (XCH or CAT) is split across multiple royalty-enabled NFTs on one side of the trade (`royalty_split > 1`) causes the creator's royalty to be truncated below the intended percentage, and the difference is instead kept by the trading counterparties. Since `royalty_split` is fully controlled by the party constructing the offer/trade (any unprivileged wallet user or offer counterparty), this allows systematically underpaying NFT creator royalties on every multi-NFT bundled trade — a "settlement theft" analog. The magnitude per trade is bounded (`royalty_split - 1` mojo-scale rounding error, scaled up by percentage), so unlike the CDP case this is a rounding-loss issue rather than an open-ended insolvency, which caps the severity.

### Likelihood Explanation
High likelihood of occurrence: any wallet client using `NFTWallet.make_nft1_offer` with more than one royalty-enabled NFT on the offering side (a supported, documented use case — see `test_complex_nft_offer` / `test_royalty_split_across_multiple_nfts`) will trigger this rounding path on essentially every such trade, with no special conditions required. It is fully reachable from a standard, unprivileged wallet operation (constructing/accepting an offer).

### Recommendation
Reorder the arithmetic to multiply before dividing, and divide once at the end to minimize precision loss:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
Apply the same fix to `royalty_calculation()`'s per-summary computation so the RPC preview matches the amount actually paid.

### Proof of Concept
Using `compute_royalty_amount` directly (`chia/wallet/nft_wallet/nft_wallet.py:67-75`):
- `offered_amount = 999`, `royalty_split = 2`, `percentage = 5000` (50%)
- Current code: `999 // 2 * 5000 // 10000` = `499 * 5000 // 10000` = `2495000 // 10000` = `249`
- Correct proportional amount: `999 * 5000 // (2 * 10000)` = `4995000 // 20000` = `249.75` → floor `249`... 

For a case that clearly diverges, use `offered_amount = 1999`, `royalty_split = 2`, `percentage = 5000`:
- Current: `1999 // 2 * 5000 // 10000` = `999 * 5000 // 10000` = `499`
- Correct: `1999 * 5000 // (2*10000)` = `9995000 // 20000` = `499` (equal here, but rounding down happens earlier and compounds when `royalty_split` and `percentage` combine with amounts not evenly divisible — e.g. `offered_amount = 3`, `royalty_split = 2`, `percentage = 10000` (100%, edge case aside) illustrates the truncation step: `3 // 2 = 1`, vs correct un-truncated intermediate `3/2 = 1.5`, discarding the fractional royalty that a single-division formula would retain when multiplied by a larger `percentage` before dividing.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
