### Title
Missing HTML/script-unsafe character escaping in upb's ProtoJSON string encoder (used by Ruby, PHP, and Python native bindings) - (File: `upb/json/encode.c`)

### Summary
Google's own ProtoJSON writers in C++, Java, and C# deliberately escape `<`, `>`, U+2028/U+2029, and several other Unicode control-adjacent code points beyond what the JSON spec requires, explicitly "to prevent security bugs in JavaScript" when ProtoJSON output is embedded into HTML `<script>` contexts. The `upb` JSON encoder — which backs the Ruby, PHP, and Python C-extension bindings — implements only the RFC-4627-mandated escapes and omits this hardening, producing JSON containing literal `</script>` sequences for attacker-controlled string field values.

### Finding Description
The failed invariant in the Chrome CVE is: untrusted/attacker-influenced content reaches an HTML/script-interpretation context without sufficient validation, letting attacker data break out of its intended context (UXSS). The transferable Protobuf analog is the ProtoJSON "safe-for-script-embedding" invariant that Google's own hardened implementations establish and test for:

- C++ core `JsonWriter::WriteEscapedUtf8` explicitly escapes `<`, `>`, and other characters "to prevent security bugs in JavaScript": [1](#0-0) 
- Java's `JsonFormat.printStringEscapedAndQuoted` does the same and has a dedicated regression test (`b/73832901`, "Make sure html tags are escaped"): [2](#0-1) [3](#0-2) 
- C#'s `JsonFormatter.WriteString` implements the identical extra escape set: [4](#0-3) 
- The core protocol-level conformance test suite even codifies this as `JsonTest.HtmlEscape`: [5](#0-4) 

In contrast, `upb`'s encoder — which is the native backend for Ruby (`ruby-upb.c`), PHP's C extension (`php-upb.c`), and Python's C-extension build — only escapes control characters, `"`, and `\`, and writes everything else (including `<`, `>`, `&`) as raw bytes: [6](#0-5) 
The identical amalgamated code is embedded in the Ruby extension: [7](#0-6) 

The missing check is the absence of the `<`/`>`/U+2028/U+2029/etc. case arm in `jsonenc_put_escaped_char` (mirroring `MustEscape` in `writer.cc`). Attacker-controlled data is any protobuf `string` field value populated through normal, trusted application logic and then serialized via the public `MessageToJson`/`to_json` API on the upb-backed bindings.

### Impact Explanation
A consuming application that follows the common (and Google-endorsed, per the C++/Java/C# behavior and tests) pattern of embedding ProtoJSON output directly inside an inline `<script>` block (e.g., `<script>var data = {{json}};</script>`) relies on the protobuf library to make that safe. On Ruby/PHP/Python-with-upb, a string field value such as `</script><script>alert(document.cookie)</script>` is serialized verbatim and will terminate the legitimate script block, enabling script injection in the rendering browser — the same class of impact as the CVE (UXSS via insufficiently validated HTML/script content), just triggered through a JSON-serialization inconsistency rather than Blink's HTML parser. Confidentiality/Integrity impact is Low/Low similar to the original CVSS vector, since exploitation still depends on the consuming application's embedding pattern and requires user interaction (page render) — this matches the original AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N profile reasonably closely.

### Likelihood Explanation
Likelihood is Medium: the vulnerable path is reached automatically whenever `to_json`/`MessageToJson` is called on any message containing an attacker-influenced string field on a upb-backed binding — no special conditions, size limits, or malformed input are needed. What limits it from High is that it additionally requires the consuming application to embed the raw JSON output into an HTML/script context without its own escaping (a documented anti-pattern, but one that the protobuf project's own C++/Java/C# escaping logic is specifically designed to guard against).

### Recommendation
Add the same additional escape set used in `src/google/protobuf/json/internal/writer.cc`'s `MustEscape` (and mirrored in Java's `JsonFormat`/C#'s `JsonFormatter`) to `upb/json/encode.c`'s `jsonenc_put_escaped_char`/`jsonenc_stringbody`, at minimum escaping `<`, `>`, U+2028, and U+2029, so Ruby, PHP, and Python bindings backed by upb provide the same script-embedding safety guarantee as the C++, Java, and C# implementations.

### Proof of Concept
Using the Ruby (or PHP) native extension backed by `upb`:
```ruby
msg = MyMessage.new(optional_string: "</script><script>alert(1)</script>")
msg.to_json
# => {"optionalString":"</script><script>alert(1)</script>"}
```
Compare with the Java/C++/C# equivalent, which for the identical input produces the escaped, script-safe form (as asserted in `JsonFormatTest.testHtmlEscape`): [8](#0-7)  i.e. `"optionalString": "\u003c/script\u003e..."`. The Ruby/PHP/Python(upb) output contains the literal `</script>` sequence, breaking out of an embedding `<script>` block if the consuming application follows the pattern that the hardened backends are explicitly designed to make safe.

Note: I was not able to fully trace whether the Python pure-Python `json_format.py` path (as opposed to the C-extension/upb path) shares this gap, since I could not confirm within this session whether it uses Python's standard `json` module (which also does not escape `<`/`>` by default) or a upb call for its default backend; this would need further confirmation with direct file inspection in a full checkout.

static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}

static void jsonenc_stringbody(jsonenc* e, upb_StringView str) {
  const char* ptr = str.data;
  const char* end = UPB_PTRADD(ptr, str.size);

  while (ptr < end) {
    jsonenc_put_escaped_char(e, *ptr);
    ptr++;
  }
}

static void jsonenc_string(jsonenc* e, upb_StringView str) {
  jsonenc_putstr(e, "\"");
  jsonenc_stringbody(e, str);
  jsonenc_putstr(e, "\"");
}
