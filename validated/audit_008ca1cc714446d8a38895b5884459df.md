## Finding

Found a concrete decimal-scaling analog to the underflow report — not an underflow itself (Rust's checked `pow`/`saturating_sub` prevents a panic), but a silent *wrong-direction clamp* that produces incorrect cross-chain amounts, reachable by any ordinary user through the public `send()` entrypoint of `hyper-fungible-token`.

### Title
Decimal-scaling `saturating_sub` clamp in `hyper-fungible-token` silently skips required scaling, causing incorrect minted/transferred amounts across the bridge - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` compute a scaling exponent as `erc_decimals.saturating_sub(local_decimals)` (and vice-versa) instead of a signed subtraction that can scale in either direction. [1](#0-0) 

### Finding Description
`convert_to_balance` is meant to convert an inbound ERC20 `U256` amount (denominated in `erc_decimals`) to a local balance (denominated in `local_decimals`) by dividing by `10^(erc_decimals - local_decimals)`. This is only correct when `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals`, the correct operation is to *multiply* by `10^(local_decimals - erc_decimals)`, but `saturating_sub` clamps the exponent to `0`, so the divisor becomes `1` and the raw ERC20-scale value is used unscaled as the local balance — under- or over-crediting depending on direction. [2](#0-1) 

Symmetrically, `convert_to_erc20` multiplies by `10^(erc_decimals - local_decimals)` (again via `saturating_sub`) to scale a local balance up to ERC20 precision before sending it in the wire `Message`. When `local_decimals > erc_decimals` (i.e., the local asset has *finer* precision than the destination ERC20 token), the correct operation is to *divide* by `10^(local_decimals - erc_decimals)`, but the clamp again yields a multiplier of `10^0 = 1`, leaving the raw local-precision value unscaled in the outgoing `erc20_amount` field. [3](#0-2) 

This helper is used directly in the public `send()` extrinsic to build the cross-chain `Message.amount`: [4](#0-3) 

And symmetrically in `on_accept` (minting/crediting the beneficiary on message delivery) and `on_timeout` (refunding the original sender), both of which run automatically without any admin/governance gating once a message arrives at the host: [5](#0-4) [6](#0-5) 

### Impact Explanation
Whenever a token pair is configured such that the local asset's decimals differ from the remote ERC20 token's registered `Precisions` decimals in the "wrong" direction (local decimals > remote `erc_decimals` for `send`/outbound, or the analogous mismatch for inbound `on_accept`/`on_timeout`), the amount encoded in the cross-chain `Message` is not rescaled at all — it is transmitted at the wrong power-of-ten. The receiving side then mints/transfers/refunds a quantity that is off by a factor of `10^|decimals_diff|` relative to what was actually escrowed/burned on the source side. Depending on which side of the pair has more decimals, this either inflates the amount credited on the destination chain (value created from nothing, draining the pallet's custodial account or the paymaster/liquidity backing it) or deflates it (funds effectively locked/lost for the user). Both are within the bounty's "stealing or loss of funds" / "false ... acceptance" impact categories.

### Likelihood Explanation
This requires no malicious peer, relayer, or governance actor — it is a deterministic consequence of the decimals configured for a token pair (via `Precisions`) combined with the pallet's own asset metadata (`T::Decimals`/`Assets::decimals`). Any legitimate, unprivileged user calling `send()` on such a misconfigured pair triggers the miscalculation, and the mint/refund paths (`on_accept`, `on_timeout`) apply the same flawed helper without further checks. The bug is latent in every deployment where the local asset's decimal count differs from a bridged ERC20 partner's decimal count in the direction that makes `saturating_sub` clamp to zero — a very plausible real-world configuration (e.g., a 12-decimal Substrate asset bridged to a 6-decimal stablecoin ERC20, or an 18-decimal native currency bridged to a 6-decimal token).

### Recommendation
Replace the `saturating_sub`-based exponent computation with an explicit signed comparison that scales in the correct direction regardless of which side has more decimals:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add unit tests covering both directions of decimal mismatch (local > erc_decimals and local < erc_decimals) for `send`, `on_accept`, and `on_timeout`.

### Proof of Concept
1. Governance registers a token pair where the local Substrate asset has `local_decimals = 12` and the destination ERC20 contract is registered in `Precisions` with `erc_decimals = 6`.
2. A user calls `send()` with `amount = 1_000_000_000_000` (i.e., `1.0` unit at 12 decimals). The local asset is burned/escrowed for exactly that amount.
3. `convert_to_erc20(1_000_000_000_000, erc_decimals=6, local_decimals=12)` computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(12u8) = 0`, so `erc20_amount = 1_000_000_000_000 * 10^0 = 1_000_000_000_000`.
4. The correct erc20-scale value should have been `1_000_000_000_000 / 10^6 = 1_000_000` (i.e., `1.0` unit at 6 decimals). Instead, the destination ERC20 contract receives an `amount` field of `1_000_000_000_000` — a million times the correct value — and mints/transfers that inflated amount to the beneficiary. [3](#0-2)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
