### Title
Unvalidated stSTX staking ratio bypasses the oracle's staleness/confidence gating, allowing mispriced stSTX/zstSTX collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s oracle pipeline gates every Pyth/DIA price with both a confidence check (`check-confidence`) and a monotonic staleness check (`oracle-timestamp-fresh`) before it is used in health/LTV math. However, for `stSTX` and `zstSTX` the base STX price is multiplied by an external staking ratio (`call-ststx-ratio`) that carries **no timestamp, no staleness bound, and no confidence/sanity check at all**. This mirrors the AfEth H-01 pattern: a validated price feed is composed with an unvalidated ratio, and a deviation in the ratio (independent of the price feed's own freshness guarantees) can silently produce a wrong collateral/debt valuation and thus a wrong health verdict.

### Finding Description
In `price-resolve`, the base oracle price is gated: [1](#0-0) 

The STX price passes `oracle-price-legal` and `oracle-timestamp-fresh` (which also enforces monotonicity via `last-update`) before `resolve-callcode` is applied. For `stSTX` (`CALLCODE-STSTX`) and `zstSTX` (`CALLCODE-ZSTSTX`), `resolve-callcode` calls `resolve-ststx`, which multiplies the already-validated STX price by a ratio fetched from a separate external call with zero validation: [2](#0-1) 

The ratio getter itself returns only a bare `uint`, with no timestamp, no confidence interval, and no bound check applied anywhere in `market.clar`: [3](#0-2) 

Compare this to the STX/DIA price path, where `check-confidence` and `oracle-timestamp-fresh` are mandatory gates before a price is accepted. The ratio has no equivalent gate: `resolve-ststx` unconditionally trusts whatever the external ratio contract returns and folds it directly into the final collateral/debt price used by `get-notional-evaluation` → `calculate-asset-notional-value` for health checks, borrow limits, and liquidation thresholds: [4](#0-3) 

This is exactly the composition bug called out in the AfEth mitigation report: a well-gated oracle price (STX/USD via Pyth, with confidence + staleness checks) is combined with a second, ungated value (a staking ratio) to derive the final asset price. If the ratio value diverges from the true STX:stSTX exchange rate at the moment it's read — whether due to a stale read from the ratio source, a transient reporting anomaly, or any other deviation the ratio contract can produce — `market.clar` has no mechanism to detect or reject it, unlike its own Pyth/DIA price paths.

### Impact Explanation
- If the ratio is transiently inflated relative to the true stSTX:STX exchange rate, `stSTX`/`zstSTX` collateral is overvalued in `get-notional-evaluation`, letting a borrower extract more debt (STX, sBTC, USDC, USDH) than their real collateral supports — theft of protocol funds once the ratio reverts and the position is left undercollateralized (protocol insolvency / theft of user/protocol funds).
- If the ratio is transiently deflated, `stSTX`/`zstSTX` positions could be wrongly flagged unhealthy and liquidated at incorrect prices — temporary freezing/loss of collateral value for the affected user.
- Because the ratio has no staleness gate at all (unlike the STX price, which is checked against `max-staleness` and must be monotonically increasing), the window for this mismatch is unbounded by design, not just narrow like the Pyth 2% deviation case in the original report.

This lands on the in-scope **Critical/High** impact class: direct mispricing of collateral/debt leading to protocol insolvency or theft of funds, depending on ratio direction at the time of borrow/liquidation.

### Likelihood Explanation
Likelihood depends entirely on how volatile/manipulable the external `block-info-nakamoto-ststx-ratio-v2` ratio can be within or across blocks, which is outside this codebase and cannot be fully verified from the indexed contracts (the ratio contract itself is not in-repo). Within `market.clar`, the vulnerability is structural and always present: there is no code path that validates the ratio's freshness or bounds before use, so any deviation the ratio source can produce — however it arises — propagates directly into every stSTX/zstSTX price resolution, borrow, and liquidation check.

### Recommendation
Apply the same rigor to the ratio that is applied to Pyth/DIA prices: require `call-ststx-ratio` (or its underlying oracle) to return a timestamp, enforce a max-staleness bound and a maximum per-update deviation (analogous to `check-confidence`), and reject `resolve-ststx` if the ratio falls outside expected bounds relative to its last observed value, mirroring `oracle-timestamp-fresh`'s monotonic/staleness gating already used for the base price feeds.

### Proof of Concept
Conceptual trace (cannot be executed against the external ratio contract from this repo alone):
1. STX/USD Pyth price is fresh and within confidence bounds, passes `oracle-timestamp-fresh`/`check-confidence` in `resolve-pyth`/`price-resolve`.
2. `resolve-ststx` reads `call-ststx-ratio` at a moment where the reported ratio diverges upward from the true stSTX:STX redemption rate (no check exists to prevent this).
3. `mul-div-down p ratio STSTX-RATIO-DECIMALS` produces an inflated `stSTX`/`zstSTX` price.
4. `get-notional-evaluation` → `calculate-asset-notional-value` uses this inflated price to compute `coll-total`, allowing a borrow against `stSTX`/`zstSTX` collateral that exceeds its real USD value.
5. Once the ratio normalizes, the position is undercollateralized; if liquidation incentives are insufficient to cover the gap, the protocol absorbs a loss (bad debt). [5](#0-4) [3](#0-2)

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
