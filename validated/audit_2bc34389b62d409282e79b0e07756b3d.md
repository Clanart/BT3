### Title
Silent, unauthenticated re-pointing of a trusted `origin` remote based on owner/name-matched (not repository-ID-verified) GitHub API data - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported EIP712 bug is fundamentally about a security-relevant decision (`permit()` signature validation) trusting a value that can become inconsistent with the live state of a mutable identifier (token name), because the code compares/derives from a stale cached representation instead of re-validating identity through a stable, non-spoofable channel. The closest structural analog in this Desktop codebase is `updateRemoteUrl()` [1](#0-0) , which silently rewrites the local `git remote set-url` target for `origin` based on comparing a *cached* `gitHubRepository.cloneURL` (persisted from a previous API fetch, keyed by owner/name string matching) against a freshly fetched API repository object, without ever re-verifying that the two are the same repository via a stable identifier (repo ID).

### Finding Description
`repositoryWithRefreshedGitHubRepository()` in `app-store.ts` re-associates a local repository with its GitHub counterpart by:
1. Parsing the *current* git remote URL to derive `owner`/`name` purely from hostname + path matching via `matchGitHubRepository()` [2](#0-1) , `matchGitHubRepository` itself only checks hostname equality and extracts owner/name from the URL string [3](#0-2) .
2. Fetching `api.fetchRepository(owner, name)` — an owner/name lookup, not an ID-based lookup — and, if that succeeds, calling `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [4](#0-3) .
3. Inside `updateRemoteUrl`, the decision to silently execute `git remote set-url` is based entirely on string comparisons: whether the *previously cached* `gitHubRepository.cloneURL` still matches the current remote (`remoteUrlUnchanged`) and whether the freshly-fetched `apiRepo.clone_url` differs from it (`!urlsMatch`) [5](#0-4) . If those string conditions align, `gitStore.setRemoteURL()` is called, which directly executes `git remote set-url <name> <url>` with no user prompt [6](#0-5) .

The broken invariant: nowhere in this flow is the GitHub repository's stable, unique `id` used to confirm that the "old" repository and the "new" `apiRepo` are actually the same repository. The comparison is entirely based on the mutable owner/name/URL string, exactly as the EIP712 bug used a mutable `token.name`/`token.symbol` without re-deriving/caching consistently. If the underlying GitHub repository at a given `owner/name` path is deleted and a different repository is created at that same `owner/name` (e.g., after a rename/transfer frees the old slug, or after an org/user rename cycle), `api.fetchRepository(owner, name)` will return a legitimate-looking `IAPIRepository` for a completely different, potentially attacker-controlled repository, and Desktop's cached `gitHubRepository.cloneURL` will still "match" the user's existing `origin` remote, satisfying `remoteUrlUnchanged`. This causes `updateRemoteUrl` to silently repoint `origin` to the new `apiRepo.clone_url`.

### Impact Explanation
If exploited, an attacker who can cause a `owner/name` slug to be reused (by acquiring a renamed/deleted repo's former name, which is a routinely available and low-cost action on GitHub) can get Desktop to silently rewrite the victim's trusted `origin` remote URL to point at the attacker's repository, with no user confirmation dialog. This corrupts what the user's subsequent `git push`/`git fetch`/`git pull` operations target: the user believes they are still pushing to their own repository, but pushes/fetches now flow through a different remote (this matches the requested impact class of "silent corruption of what the user commits or pushes"). Depending on git credential-helper behavior, this could also result in the user's credentials/token being sent in HTTPS auth flows for the newly resolved remote host if the new `clone_url` differs in host (though the protocol/host constraints in the function reduce, but do not eliminate, this risk since `owner/name` string reuse can occur under the very same host).

### Likelihood Explanation
This path executes automatically and silently as part of routine background refresh logic (`repositoryWithRefreshedGitHubRepository` is invoked e.g. on account changes and repository selection, see `refreshSelectedRepositoryAfterAccountChange`) [7](#0-6) , requires no unusual user action, and depends only on an attacker being able to claim a previously-used `owner/name` path on the same GitHub host — a realistic scenario after any repository rename/transfer/deletion, which GitHub explicitly allows for reuse. No local access, admin rights, or social engineering is required beyond normal repository-rename hygiene issues that are outside the victim's control.

### Recommendation
Do not rely solely on owner/name/URL string matching to decide whether to trust a freshly-fetched `apiRepo` as the "same" repository before silently rewriting `origin`. Compare the immutable GitHub repository `id` (already stored as `GitHubRepository.dbID`/underlying `id` from the API) between the cached `gitHubRepository` and the newly fetched `apiRepo` before calling `updateRemoteUrl`/`setRemoteURL`, and require user confirmation (or at least a warning) whenever the repository ID changes even though the owner/name path superficially matches.

### Proof of Concept
1. Victim clones `https://github.com/alice/project` and adds it as `origin` in Desktop; Desktop persists `GitHubRepository.cloneURL = https://github.com/alice/project` from the initial API fetch.
2. Alice renames/transfers/deletes `alice/project` on GitHub, freeing the `alice/project` slug (a normal, permitted GitHub action outside the victim's control).
3. Attacker (or anyone) creates a new repository at the now-available `alice/project` path (assuming attacker controls or squats the `alice` account/org, or the rename made `alice/project` available on the same host under a different but now-current owner they control).
4. On the victim's next repository selection/account refresh, `repositoryWithRefreshedGitHubRepository` re-derives `owner=alice, name=project` from the still-unchanged git remote URL, calls `api.fetchRepository('alice','project')`, and gets the attacker's new repo data back.
5. `updateRemoteUrl` sees `remoteUrlUnchanged === true` (victim's local remote still equals the old cached `cloneURL`) and `urlsMatch === false` (new clone_url differs), so it silently calls `gitStore.setRemoteURL('origin', <attacker clone_url>)`, repointing the victim's trusted `origin` remote without any prompt.

Note: I was unable to fully verify within the available tool calls whether `IAPIRepository`/`GitHubRepository` expose a persistent numeric `id` field that is actually populated and comparable at the point of `updateRemoteUrl` (I saw `dbID` used as Desktop's own database primary key, and API responses likely include a GitHub-assigned `id`, but I could not fully confirm the exact field name/availability in `IAPIRepository`). A background Devin session with full repository access would be needed to confirm the exact field to use for the ID-based fix and to validate the exact conditions under which `repositoryWithRefreshedGitHubRepository` is triggered without user interaction.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)

      await gitStore.loadRemotes()

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
