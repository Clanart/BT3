## Title
Access-scope reauthorization check silently bypassed for sessions with empty scope - ([File: `lib/shopify_app/access_scopes/user_strategy.rb`])

### Summary
`ShopifyApp::AccessScopes::UserStrategy.covers_scopes?` treats an empty/blank `scope` on a stored session as automatically "covering" all currently-required scopes, short-circuiting the very check meant to force re-authentication when a session's granted scopes are insufficient. This is the same bug class as the reported Solidity issue: a value that represents "unset/zero" is fed into a security-relevant comparison as if it were a valid, sufficient value, instead of being treated as the failing/needs-correction case.

### Finding Description
`covers_scopes?` is defined as:

```ruby
def covers_scopes?(current_shopify_session)
  # NOTE: this not Ruby's `covers?` method, it is defined in ShopifyAPI::Auth::AuthScopes
  current_shopify_session.scope.to_a.empty? || current_shopify_session.scope.covers?(ShopifyAPI::Context.scope)
end
``` [1](#0-0) 

This is invoked from `ShopifyApp::LoginProtection#activate_shopify_session`, the central gate every `EnsureHasSession`-based request passes through:

```ruby
if ShopifyApp.configuration.reauth_on_access_scope_changes &&
    !ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)
  clear_shopify_session
  return redirect_to_login
end
``` [2](#0-1) 

The check's intent is: if the stored session's granted `scope` does not cover the app's currently configured required scopes, force the session to be cleared and redirect to login/OAuth so the merchant/user re-consents. However, when `current_shopify_session.scope` is empty (`to_a.empty?` is `true`), the method returns `true` unconditionally via the `||` short-circuit — the same pattern as `initialWeight == 0` needing a corrected minimum but the raw (uncorrected) value being propagated into a later gate. Here, an "empty" scope — which should be the strongest signal that scope-validation must fail and reauth must be forced — instead makes the check trivially pass, permanently disabling the reauthorization control for any session that has (or ends up with) an empty recorded `scope`, exactly mirroring how a `weight == 0` in the report should have been corrected to a safe minimum but instead flowed unchanged into a check that assumed non-zero.

`current_shopify_session` is resolved from an inbound cookie or `Authorization` bearer session token via `load_current_session`, so this logic executes on every request that presents such credentials, without any additional privilege beyond having previously obtained a session (e.g. an app installed under online/user tokens, or scopes never populated by the session storage implementation). [3](#0-2) 

### Impact Explanation
Any session whose stored `scope` is empty (unset by a custom/older `SessionRepository` storage implementation, or an online token record created before scopes were tracked) permanently bypasses the `reauth_on_access_scope_changes` enforcement documented for `covers_scopes?`/`ShopAccessScopesVerification`. The app will continue activating and using such a session as if it satisfied all currently required access scopes, defeating the security control whose entire purpose is to force re-consent when scopes are insufficient or have changed. This directly undermines the access-scope check category the app relies on for authorization correctness.

### Likelihood Explanation
This triggers automatically and deterministically for any qualifying session — no attacker interaction beyond presenting a previously valid session credential (cookie or bearer token) whose `scope` is empty. No signature forgery or brute force is required; it is a pure logic bypass in the scope validation code path exercised on every authenticated request through `LoginProtection#activate_shopify_session`.

### Recommendation
Remove the `current_shopify_session.scope.to_a.empty?` short-circuit (or invert its meaning) so that an empty/blank scope is treated as **not** covering the required scopes, forcing reauthorization instead of trivially passing:

```ruby
def covers_scopes?(current_shopify_session)
  current_shopify_session.scope.to_a.covers?(ShopifyAPI::Context.scope)
end
```
or explicitly return `false` when scope is empty and the app has non-empty required scopes.

### Proof of Concept
1. Configure `ShopifyApp.configuration.reauth_on_access_scope_changes = true` and require a non-empty scope list (e.g., `config.scope = ["read_products"]`).
2. Persist/load a `current_shopify_session` whose `scope` attribute is empty (`[]`/`nil`) — e.g. via a `UserSessionStorage`/custom storage implementation that never populated `access_scopes`, matching the code path exercised in [1](#0-0) .
3. Send an authenticated request using that session's cookie/bearer token to any controller including `EnsureHasSession`.
4. Observe `activate_shopify_session` calls `covers_scopes?`, which returns `true` solely because `scope.to_a.empty?`, so the `clear_shopify_session`/`redirect_to_login` branch in [2](#0-1)  never executes, and the request proceeds using a session that never actually satisfied the required scopes.
