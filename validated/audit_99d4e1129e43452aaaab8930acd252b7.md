### Title
Reward-decay forfeiture bypass via `forceUnLock` skipping harvest-before-zero ordering - (File: `VLMGP.sol`, `rewards/vlMGPBaseRewarder.sol`)

### Summary
`VLMGP.getRewardablePercentWAD` penalizes users who let a cooldown slot sit past `endTime` without withdrawing, by decaying that slot's weight over time [1](#0-0) . `unlock()` correctly harvests pending MGP/rewards through `MasterMagpie.multiclaimFor` *before* zeroing the slot [2](#0-1) , but `forceUnLock()` zeroes the slot without ever triggering a harvest [3](#0-2) . An attacker can call `forceUnLock` and then immediately harvest (e.g. `MasterMagpie.multiclaim`) in the same block, causing `_calExpireForfeit` to read a post-zero state that erases the decay penalty on already-accrued pending yield.

### Finding Description
`getRewardablePercentWAD(_user)` computes the fraction of a user's vlMGP position considered "rewardable" for forfeiture purposes in `vlMGPBaseRewarder`. For a slot still within its cooldown window it is weighted at 100% [4](#0-3) , but for a slot whose `endTime` has already passed (expired but not yet withdrawn) it is weighted by a decaying `(endTime-startTime)/(timeNow-startTime)` factor [5](#0-4) , which lowers the overall `percent` and therefore increases `forfeitAmount` computed in `_calExpireForfeit` [6](#0-5) . This is used both by `queueMGP` (routing vesting MGP from `MasterMagpie`) [7](#0-6)  and by `_sendReward` for other reward tokens [8](#0-7) .

`expectedPenaltyAmount` shows that once `block.timestamp - startTime > endTime - startTime` (i.e., the slot has expired), `unlockFactor` remains at its initialized maximum (`1e12`), so `penaltyAmount` collapses to zero [9](#0-8) . This confirms `forceUnLock` can be called on an already-expired slot at no principal cost, purely to zero it out.

`forceUnLock` calls `_unlock(slot.amountInCoolDown)` and zeroes `slot.amountInCoolDown`/resets `slot.endTime` without calling `MasterMagpie.multiclaimFor` at all [3](#0-2) . Contrast this with `unlock()`, which explicitly harvests first via `multiclaimFor` and only then zeroes the slot [10](#0-9) . Because `forceUnLock` does not harvest, an attacker can:
1. Let a large cooldown slot sit past `endTime` while other reward/MGP accrues in `unClaimedMgp`/`vlMGPBaseRewarder` reward balances, accumulating a decayed (heavily forfeitable) `getRewardablePercentWAD`.
2. Call `forceUnLock(_slotIndex)` — zero principal penalty since the slot is expired — which zeroes `amountInCoolDown` for that slot.
3. Immediately (same block/tx via a wrapper contract, or same-block front-run) call `MasterMagpie.multiclaim`, which routes pending MGP through `vlMGPBaseRewarder.queueMGP` / claims other reward tokens through `_sendReward`, both of which call `_calExpireForfeit` → `vlMGP.getRewardablePercentWAD(_account)` at that point, now reading the slot as zeroed and computing near-100% "rewardable" instead of the decayed percentage that should have applied.

This lets the attacker collect pending yield without the forfeiture that the protocol's decay mechanism intends, simply by re-ordering "zero the slot" before "harvest" — an ordering only available through `forceUnLock`, not through the normal `unlock()` path which correctly harvests first.

### Impact Explanation
This is theft of unclaimed/vesting yield: MGP and other reward tokens that should be forfeited to `vlMGPBaseRewarder`'s reward pool (via `_queueNewRewardsWithoutTransfer`, benefiting other lockers) are instead captured in full by the attacker [7](#0-6) . This matches the "theft of unclaimed yield" impact class and directly reduces funds available to honest vlMGP stakers.

### Likelihood Explanation
No privileged role is required — any vlMGP holder can create a cooldown slot via `startUnlock`, let it expire, accrue pending MGP/rewards, then call `forceUnLock` followed by a harvest call in the same block or transaction (trivially bundled via a simple wrapper contract calling both `VLMGP.forceUnLock` and `MasterMagpie.multiclaim`). The attack is repeatable per slot/user and scales with the size of the position and how long the pending rewards were allowed to accrue against a decayed percentage.

### Recommendation
Make `forceUnLock` harvest the user's pending rewards through `MasterMagpie.multiclaimFor` **before** zeroing `slot.amountInCoolDown`/`slot.endTime`, mirroring the ordering already used in `unlock()`, so that `getRewardablePercentWAD` reflects the pre-forceUnLock state at the time forfeiture is calculated.

### Proof of Concept
Foundry test plan:
1. Lock a small `L` amount and start an unlock cooldown for a large `C` amount via `startUnlock`, with a short `coolDownInSecs`.
2. Warp time past `slot.endTime` so the slot is "expired" (decayed weight applies in `getRewardablePercentWAD`).
3. Have `MasterMagpie` accrue pending MGP/reward tokens for the user (e.g., via normal pool reward accrual) so `unClaimedMgp` is non-zero.
4. Baseline: call `MasterMagpie.multiclaim` directly (without calling `forceUnLock`) and record `forfeitAmount`/`rewardableAmount` emitted by `vlMGPBaseRewarder.queueMGP`/`_sendReward` — expect nonzero forfeiture due to decay.
5. Attack: reset state, instead call `VLMGP.forceUnLock(_slotIndex)` then immediately `MasterMagpie.multiclaim` in the same transaction (via a helper contract) or same block; record `forfeitAmount`/`rewardableAmount`.
6. Assert that the attack-path forfeiture is significantly lower (approaching zero) than the baseline forfeiture for the same pending amount and elapsed time, demonstrating that sequencing `forceUnLock` before harvest nullifies the intended decay-based forfeiture.

    function expectedPenaltyAmount(uint256 _slotIndex) public view returns(uint256 penaltyAmount, uint256 amontToUser) {
        UserUnlocking storage slot = userUnlockings[msg.sender][_slotIndex];

        uint256 coolDownAmount = slot.amountInCoolDown;
        uint256 baseAmountToUser = slot.amountInCoolDown / 5;
        uint256 waitingAmount = coolDownAmount - baseAmountToUser;

        uint256 unlockFactor = 1e12;
        if((block.timestamp - slot.startTime) <= (slot.endTime - slot.startTime))
            unlockFactor = ((block.timestamp - slot.startTime) * 1e12 / (slot.endTime - slot.startTime)) ** 2 / 1e12;

        uint256 unlockAmount = waitingAmount * unlockFactor / 1e12;
        amontToUser = baseAmountToUser + unlockAmount;
        penaltyAmount = coolDownAmount - amontToUser;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
