### Title
Lossy hard-coded UTF-8 decoding of diff output silently corrupts unmodified context lines when partially staging non-UTF-8 text files - (File: app/src/lib/git/diff.ts)

### Summary
`GenericLogic.sol` in the ZeroLend report assumed all price-feed inputs shared a uniform format (decimals) and summed them without normalization, silently corrupting a security-critical value (health factor). The GitHub Desktop analog is `diffFromRawDiffOutput` in `app/src/lib/git/diff.ts`, which assumes every diff buffer produced by `git diff` is UTF-8 and decodes it unconditionally with `output.toString('utf-8')`, even though the comment right above it acknowledges this is an assumption ("for now we just assume the diff is UTF-8"). Files that Git treats as text but that are actually encoded in a legacy/non-UTF-8 charset (Shift-JIS, GBK, Windows-1252, or simply containing invalid UTF-8 byte sequences without a NUL byte, so Git's binary heuristic doesn't flag them) will have their raw bytes replaced with the Unicode replacement character (`U+FFFD`) during this decode. That lossy string is exactly what is fed to the partial-commit pipeline (`formatPatch` in `app/src/lib/patch-formatter.ts`), which reuses `line.text` verbatim for unmodified context lines and pipes the resulting patch text back into `git apply --cached` (`app/src/lib/git/apply.ts`). The net effect is that content the user never touched gets rewritten with different bytes than what's on disk when they commit a partial selection.

### Finding Description
`diffFromRawDiffOutput` is the single choke point that converts every `git diff` invocation's raw stdout `Buffer` into a JS string for parsing: [1](#0-0) 

This function is called from `buildDiff`, which itself backs `getWorkingDirectoryDiff` — the diff Desktop shows for any file the user is about to (partially) commit: [2](#0-1) [3](#0-2) 

Node's `Buffer.toString('utf-8')` is a *lossy* decode: any byte sequence that is not valid UTF-8 is replaced with `U+FFFD` (the replacement character), and information about the original bytes is discarded — there is no round-trip back to the original bytes. This is conceptually identical to the audit finding's core flaw: heterogeneous inputs (arbitrary byte encodings from different files/commits, just like heterogeneous price-feed decimals from different oracles) are combined and processed under a single fixed assumption without verification or normalization.

The corrupted string then flows into `DiffParser.parse`, which splits it into hunks/lines by naive `\n` scanning: [4](#0-3) 

When the user performs a **partial commit** (selects only some lines/hunks of a modified file), `formatPatch` reconstructs a patch using `line.text` as-is for both selected lines and — critically — for context lines and "unselected deletions turned into context": [5](#0-4) 

That patch string (which now contains `U+FFFD` glyphs anywhere the original file had non-UTF-8 bytes) is sent to `git apply --cached` via stdin: [6](#0-5) 

When Node/dugite writes that JS string to the child process's stdin, it re-encodes it (UTF-8 by default), turning each `U+FFFD` into the 3-byte sequence `EF BF BD`. Those bytes are then written into the git index/blob by `git apply`, permanently replacing whatever the original (non-UTF-8) bytes were on disk — for lines the user never selected or intended to change. This differs from the plain "select-all" staging path (`updateIndex`/`git add`), which stages the file bytes directly from the filesystem and is therefore not affected; only the partial-selection path re-serializes content through the lossy UTF-8 round trip.

I was not able to fully trace dugite/`core.ts`'s exact child-process stdin encoding call (tool budget was exhausted before completing that lookup), so the exact byte-level re-encoding step should be verified by a Devin session, but the lossy decode at `diffFromRawDiffOutput` and the verbatim reuse of `line.text` in `formatPatch` for untouched context/deletion lines are both confirmed in the code shown above, and together they are sufficient to establish that committed bytes can diverge from working-directory bytes without any warning to the user.

### Impact Explanation
This causes silent corruption of what the user commits and pushes — one of the explicitly valid impact categories. A user working on a repository containing legacy-encoded source files (e.g., Shift-JIS-encoded Japanese comments, Windows-1252 Latin-1 text, or any file with invalid-as-UTF-8 byte sequences that isn't flagged by Git's binary heuristic) who performs a partial/line-level commit will have unrelated, unselected file content silently mangled in the resulting commit. The corruption is invisible in Desktop's own diff/warning UI: `DiffContentsWarning` only surfaces bidirectional-Unicode and line-ending warnings, not encoding-loss warnings, so the user has no signal that their commit differs from their working tree: [7](#0-6) 

Repeated commits/pushes on such a file progressively replace more of the original bytes with `U+FFFD`-derived bytes, degrading source integrity and potentially breaking builds, tests, or downstream tooling that depends on the original encoding, and this happens without the attacker (whoever authored the non-UTF-8 file, e.g. a repository owner or a contributor whose PR is cloned) doing anything overtly malicious — the "attacker-controlled" element is simply committing a legitimately non-UTF-8-encoded but textual file to a repository the victim clones/fetches.

### Likelihood Explanation
Non-UTF-8 source files are common in real-world repositories (legacy Windows/Japanese/Chinese codebases, files with stray non-UTF-8 bytes in comments or string literals). Desktop's partial-commit / line-selection UI is a core, heavily used feature. No special user action beyond normal use (open such a repo, edit a file, select some but not all lines to commit) is needed, satisfying the "no unnatural user steps" requirement. The bug requires no admin rights, no local/physical access, and no prior compromise — it triggers purely from cloning/opening a repository containing such a file and using the standard partial-staging workflow.

### Recommendation
- Detect decode losses: after `output.toString('utf-8')`, verify round-trip fidelity (e.g., re-encode and compare byte length/content, or use a strict UTF-8 decoder that throws/flags on invalid sequences) before using the string for anything that will be re-serialized and written back (i.e., partial-commit patches).
- For files whose diff buffer fails strict UTF-8 validation, disable partial/line-level staging for that file and fall back to whole-file staging (`git add`) which stages bytes directly from disk without a lossy round trip.
- Surface a warning in the UI (similar to the existing bidi/line-ending warnings in `DiffContentsWarning`) when a file's encoding could not be reliably determined, so users are not silently exposed to corruption.
- Longer term, honor `.gitattributes`/`core.diff.textconv` filters and encoding hints already available to Git before assuming UTF-8.

### Proof of Concept
1. Create a text file `notes.txt` containing bytes that are valid ISO-8859-1/Shift-JIS but invalid UTF-8 (e.g., a lone `0x82 0xA0` sequence, common when saving Japanese text in Shift-JIS) with no NUL bytes so Git treats it as text.
2. Commit this file, then modify one line elsewhere in the file, keeping the non-UTF-8 bytes in an adjacent (unmodified) context line within the same hunk.
3. In GitHub Desktop, open the Changes view for `notes.txt`, and use the line-level selection UI to stage only the newly modified line (leaving the non-UTF-8 context line unselected/unmodified).
4. Commit the partial selection.
5. Inspect the resulting blob with `git show HEAD:notes.txt | xxd` — the previously Shift-JIS byte sequence `82 A0` in the untouched context line will have been replaced with the UTF-8 encoding of `U+FFFD` (`EF BF BD`), even though the user never selected that line for modification, confirming silent corruption of committed content that the underlying `git diff`/`toString('utf-8')` assumption introduced.

/**
 * Render the diff for a file within the repository working directory. The file will be
 * compared against HEAD if it's tracked, if not it'll be compared to an empty file meaning
 * that all content in the file will be treated as additions.
 */
export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}

 *
 * Parses the output from a diff-like command that uses `--path-with-raw`

function diffFromRawDiffOutput(output: Buffer): IRawDiff {
  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')

  const pieces = result.split('\0')
  const parser = new DiffParser()
  return parser.parse(forceUnwrap(`Invalid diff output`, pieces.at(-1)))
}

  private nextLine(): boolean {
    this.ls = this.le + 1

    // We've reached the end of the diff
    if (this.ls >= this.text.length) {
      return false
    }

    this.le = this.text.indexOf('\n', this.ls)

    // If we can't find the next newline character we'll put our
    // end pointer at the end of the diff string
    if (this.le === -1) {
      this.le = this.text.length
    }

    // We've succeeded if there's anything to read in between the
    // start and the end
    return this.ls !== this.le
  }

  /**
   * Advances to the next line and returns it as a substring
   * of the raw diff text. Returns null if end of diff was
   * reached.
   */
  private readLine(): string | null {
    return this.nextLine() ? this.text.substring(this.ls, this.le) : null
  }

          oldCount++

        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.

          file.status.kind === AppFileStatusKind.Untracked

          return
        }

        if (line.type === DiffLineType.Add) {

          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
