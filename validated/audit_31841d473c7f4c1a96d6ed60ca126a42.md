### Title
Nil-pointer dereference in `SetCodeTx.AsEthereumData()` crashes nodes processing an EIP-7702 transaction with an empty `to` field - ([File: x/evm/types/ethtx/set_code_tx.go])

### Summary
`SetCodeTx.Validate()` treats the `to` field as optional (it is only format-checked "if present"), but `SetCodeTx.AsEthereumData()` unconditionally dereferences the pointer returned by `GetTo()`, which is `nil` when `to` is empty. A transaction sender who submits an EIP-7702 (`SetCodeTx`) `MsgEVMTransaction` with an empty `to` field passes validation and then crashes any node (mempool `CheckTx`, block `DeliverTx`, or the ante-handler's authorization pre-association logic) that attempts to convert the transaction to its go-ethereum representation, exactly mirroring the OpenSSL CVE pattern of dereferencing an ASN.1-optional field without checking its presence.

### Finding Description
`SetCodeTx.GetTo()` returns `nil` whenever `tx.To == ""`: [1](#0-0) 

`SetCodeTx.AsEthereumData()` immediately dereferences that pointer without a nil check: [2](#0-1) 

`SetCodeTx.Validate()` never requires `to` to be non-empty — it only validates the address format `if tx.To != ""`, unlike the mandatory checks it performs for `GasTipCap`, `GasFeeCap`, and `ChainID`: [3](#0-2) 

Per EIP-7702, a `SetCodeTx` (type 0x04) cannot be a contract-creation transaction and must always carry a non-nil `to`. Because this codebase does not enforce that invariant in `Validate()`, an attacker-controlled `MsgEVMTransaction` carrying a `SetCodeTx` with `to == ""` passes basic message validation and later panics in `AsEthereumData()`.

This function is invoked directly from the EVM ante pipeline on every incoming EVM transaction of a type allowed under the `Prague` signer version (which includes `SetCodeTxType`): [4](#0-3) [5](#0-4) 

It is also invoked a second time, unconditionally, from the EIP-7702 authorization pre-association helper that runs in the same ante handler: [6](#0-5) 

### Impact Explanation
A panic inside `PreprocessUnpacked`/`AnteHandle` (called from `CheckTx` for every submitted transaction and from `DeliverTx`/block processing for every included transaction) will crash the node process unless recovered by an outer `recover()`. Cosmos SDK's baseapp normally recovers panics inside `runTx`, turning them into an error result rather than a full crash for `DeliverTx`; however, for public JSON-RPC / mempool `CheckTx` paths and any code path that calls `AsEthereumData()` outside of that specific recovery wrapper (e.g., `MsgEVMTransaction.AsTransaction()` used elsewhere in RPC/query serving), this can produce a crash of a default-configuration node reachable by any unprivileged transaction sender or public RPC client — a Denial of Service, matching the CVE's DoS impact class.

### Likelihood Explanation
High. `SetCodeTx` (EIP-7702) is a normal transaction type accepted from any external sender once the chain has upgraded to the `Prague` signer version, and constructing a `SetCodeTx` with an empty `to` requires no privileges — only a valid signature over the crafted fields. No special network position, validator collusion, or leaked keys are needed.

### Recommendation
Enforce the EIP-7702 invariant in `SetCodeTx.Validate()` by rejecting the transaction when `tx.To == ""`, and/or make `AsEthereumData()` defensive by checking `GetTo() == nil` before dereferencing, returning an error/no-op path instead of panicking.

### Proof of Concept
1. Craft a `MsgEVMTransaction` wrapping an `ethtx.SetCodeTx` Any, with `To` left as the empty string but all other required fields (`ChainID`, `GasTipCap`, `GasFeeCap`, valid `V/R/S`, non-empty `AuthList`) populated so `Validate()` passes.
2. Sign it and submit via `eth_sendRawTransaction` (or directly broadcast the wrapped Cosmos tx) to a node running the `Prague` signer version.
3. The ante handler's `Preprocess`/`PreprocessUnpacked` (or `associateAuthorizationAuthorities`) calls `setCodeTx.AsEthereumData()`, which executes `To: *tx.GetTo()` on a `nil` pointer, causing a runtime panic (`invalid memory address or nil pointer dereference`).

Because I could not execute code in this environment, I was unable to directly confirm at which exact layer (CheckTx vs. a non-recovered code path) the panic ultimately terminates the process versus being caught by baseapp's panic recovery; a Devin session with test/build tooling would be needed to reproduce the crash end-to-end and confirm whether it escapes existing recovery wrappers.

func (tx SetCodeTx) Validate() error {
	if tx.GasTipCap == nil {
		return errors.New("gas tip cap cannot nil")
	}

	if tx.GasFeeCap == nil {
		return errors.New("gas fee cap cannot nil")
	}

	if tx.GasTipCap.IsNegative() {
		return fmt.Errorf("gas tip cap cannot be negative %s", tx.GasTipCap)
	}

	if tx.GasFeeCap.IsNegative() {
		return fmt.Errorf("gas fee cap cannot be negative %s", tx.GasFeeCap)
	}

	if tx.GasFeeCap.LT(*tx.GasTipCap) {
		return fmt.Errorf("max priority fee per gas higher than max fee per gas (%s > %s)",
			tx.GasTipCap, tx.GasFeeCap,
		)
	}

	if !IsValidInt256(tx.Fee()) {
		return errors.New("fee out of bound")
	}

	amount := tx.GetValue()
	// Amount can be 0
	if amount != nil && amount.Sign() == -1 {
		return fmt.Errorf("amount cannot be negative %s", amount)
	}

	if tx.To != "" {
		if err := ValidateAddress(tx.To); err != nil {
			return errors.New("invalid to address")
		}
	}

	if err := validateAccessList(tx.Accesses); err != nil {
		return err
	}
	if err := validateAuthList(tx.AuthList); err != nil {
		return err
	}
	if err := validateSignatureValue("v", tx.V, 32); err != nil {
		return err
	}
	if err := validateSignatureValue("r", tx.R, 32); err != nil {
		return err
	}
	if err := validateSignatureValue("s", tx.S, 32); err != nil {
		return err
	}

	chainID := tx.GetChainID()

	if chainID == nil {
		return errors.New(
			"chain ID must be present on AccessList txs",
		)
	}

	return nil
}
