### Title
Unbounded `Vec::with_capacity` on attacker-controlled participant count causes asymmetric memory allocation in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes a `u16` participant count `n` from untrusted bytes and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector, before validating `n` against `t` or reading any coefficient bytes. A ~15-byte input can therefore force an allocation of up to `65535 * size_of::<C::F>()` (~2 MiB for 32-byte fields), an amplification of ~100,000× per call. This is the same bug class as GHSA-4qg8-fj49-pxjh (CWE-405: allocation proportional to untrusted length data).

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s (lines 591-602), then reads a one-byte interpolation tag. For tag `0` (`Constant`), it executes `Vec::with_capacity(usize::from(n))` at line 608 before any bound check on `n` — `ThresholdParams::new(t, n, i)` (which would reject `t > n`, but not a large `n` alone) is only invoked at line 626, after the allocation. `n` is fully attacker-controlled, capped only by `u16::MAX`. A malicious byte stream of roughly 4 + `C::ID.len()` + 7 bytes triggers an immediate allocation of `65535 * size_of::<C::F>()` bytes (≈ 2 MiB for Ristretto/Secp256k1 scalars), even though the subsequent `read_F` loop fails on EOF almost instantly. The oversized allocation is performed and then dropped, turning each invocation into a cheap memory-pressure primitive. `ThresholdKeys::read` is explicitly an untrusted-bytes entry point for this codebase.

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` can cause ~2 MiB of heap allocation per ~15 bytes of input. Repeated calls (e.g., corrupt/malicious key-share blobs submitted in parallel, or a service that retries deserialization) force rapid allocator churn and memory exhaustion, crashing the process. This is a remote denial of service via asymmetric resource consumption, analogous in mechanism and impact to the referenced advisory (rated High in the Go ecosystem; here the per-call amplification is bounded by `u16`, so the practical ceiling is lower).

### Likelihood Explanation
The vulnerability triggers on any call to `ThresholdKeys::read` over bytes the caller does not fully control — e.g., key material received from another participant, restored from untrusted storage, or relayed through a coordinator. No cryptographic validity is required; the allocation precedes all semantic validation. Exploitation requires only reaching the deserializer repeatedly, which is plausible wherever key blobs are accepted over a network channel. Impact is memory-only DoS (no secret leakage, no forgery), and per-call amplification is bounded, so severity is Medium rather than High.

### Recommendation
Replace `Vec::with_capacity(usize::from(n))` at `crypto/dkg/src/lib.rs:608` with `Vec::new()` (growth proportional to bytes actually read), or cap `n` early: reject `n` exceeding a protocol maximum (e.g., `MAX_KEY_SHARES_PER_SET`) immediately after reading it, before any allocation. The same audit should be applied to other length-prefixed reads reachable from untrusted input (`SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs:78-85` uses a `u32` count, though it pushes incrementally and is bounded by input length — still worth an explicit limit).

// Conceptual PoC for crypto/dkg/src/lib.rs ThresholdKeys::read
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ristretto;
use dkg::ThresholdKeys;

fn main() {
  let mut bytes = vec![];
  // Curve ID length + ID (must match C::ID to pass the early check)
  bytes.extend_from_slice(&(Ristretto::ID.len() as u32).to_le_bytes());
  bytes.extend_from_slice(Ristretto::ID);
  // t = 1, n = 0xffff (65535), i = 1
  bytes.extend_from_slice(&1u16.to_le_bytes());
  bytes.extend_from_slice(&u16::MAX.to_le_bytes());
  bytes.extend_from_slice(&1u16.to_le_bytes());
  // interpolation = Constant -> Vec::with_capacity(65535) immediately
  bytes.push(0u8);
  // No coefficient bytes follow; read_F fails on EOF,
  // but ~2 MiB was already allocated for ~20 bytes of input.
  let _ = ThresholdKeys::<Ristretto>::read(&mut Cursor::new(bytes));
}
