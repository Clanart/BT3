Based on my research, the strongest local analog to the Perennial "zero-amount kills the whole rebalance" bug is in the intent-settlement escrow-release path, not the fill path (which was already hardened against zero amounts).

### Title
Zero-value escrowed token entry causes `withdraw()` to permanently revert and lock the *entire* order's escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Perennial bug reduces to: a legitimately-computed zero amount is passed into a state-changing function that has an unconditional invariant/guard which was never designed to tolerate zero, so the whole operation reverts and the system gets stuck instead of treating the zero leg as a no-op. The same shape exists in `IntentGatewayV2.withdraw()`: it iterates every token in the withdrawal request and unconditionally reverts the *entire* function if any single token's escrow balance happens to be `0`, rather than skipping that zero leg and continuing to release the rest.

### Finding Description
`withdraw()` loops over `body.tokens` (the list of escrowed input tokens to release) and, for each entry, does: [1](#0-0) 

```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
    _orders[body.commitment][token] -= amount;
```

`_orders[commitment][token] == 0` is treated as "this order is unknown" and reverts the whole call — but `0` is not only produced by an unknown/forged order; it is also the natural value for a **legitimate order leg whose input amount was zero at placement**. `placeOrder()` only validates `order.inputs.length != 0` and, in the predispatch-calldata branch, that individual predispatch/input amounts are non-zero: [2](#0-1) 

Outside that predispatch branch, there is no per-token `amount != 0` check on `order.inputs[i]`, so a multi-input order can be placed with one input leg's `amount == 0` (e.g. a user only wants to escrow on some of the legs but still lists a zero-value token for indexing/consistency with the outputs array). That token is transferred with `safeTransferFrom(..., 0)` (a no-op) and `_orders[commitment][token]` is left at `0` — a fully valid, expected state, not a "forged commitment" indicator.

When the order is later filled and settled (or cancelled/refunded), `withdraw()` is invoked with `body.tokens` built from `order.inputs`/`escrowedInputs` for the *whole* order (see `IntrinsicIntents._fillSameChain`'s `escrowedInputs` array and `ExtrinsicIntents._fillCrossChain`'s `order.inputs`): [3](#0-2) [4](#0-3) 

The zero-value leg reaches `withdraw()` alongside the other, genuinely-escrowed tokens. Because the loop reverts on the very first zero it encounters, it never gets to process the remaining nonzero tokens — the entire settlement transaction (`onAccept`'s `RedeemEscrow`/`RefundEscrow` handling, or the storage-proof driven `onGetResponse` refund path) reverts.

This mirrors the Perennial invariant exactly: existing guards ("if amount == 0, treat this as no state change") do not exist here; instead a guard designed to catch a *different* error condition (unknown/forged commitment) fires on a legitimate zero and blocks the whole downstream operation.

### Impact Explanation
Once a fill (or cancellation) is dispatched with a zero-value leg included, `withdraw()` cannot ever succeed for that commitment — `_orders[commitment][token]` for that token stays `0` forever (there is no code path to change it), so every future call to `withdraw()` for that commitment hits the same `revert UnknownOrder()`. This permanently locks:
- the solver's payout of all other escrowed input tokens on a cross-chain fill (`RedeemEscrow`), and
- the user's refund of all escrowed tokens on cancellation/timeout (`RefundEscrow`/`onGetResponse`),

for that order. This is a fund-lock / stuck-settlement condition reachable by an ordinary user constructing a valid multi-input order with one zero-amount leg — no malicious relayer, prover, or admin required, matching the bounty's "stealing or loss of funds" / "logic attack" impact classes.

### Likelihood Explanation
Likelihood is bounded by whether `placeOrder()` truly permits a zero-amount input outside the predispatch branch (confirmed absent there) and by whether a solver/relayer would actually construct a fill/withdrawal batch containing that zero-value token. Given `escrowedInputs`/`order.inputs` are built directly and unconditionally from the order data (not filtered for zero), any order with a zero-amount input leg will naturally produce this state on first attempted settlement. This is a moderate/edge-case likelihood, structurally identical to the accepted Perennial Medium finding.

### Recommendation
In `withdraw()`, skip (continue) tokens whose `body.tokens[i].amount == 0` instead of asserting `_orders[commitment][token] != 0`, or validate at `placeOrder()` time that every `order.inputs[i].amount > 0` (extending the existing check to the non-predispatch path) so a zero-amount leg can never enter escrow accounting in the first place.

### Proof of Concept
1. Call `placeOrder()` with `order.inputs = [{token: A, amount: 100}, {token: B, amount: 0}]` and a matching two-asset output — no predispatch calldata, so the `amount == 0` check at `evm/src/apps/IntentGatewayV2.sol:233` is never reached.
2. `_orders[commitment][A] = 100`, `_orders[commitment][B] = 0`.
3. Solver fully fills the order; `escrowedInputs`/`order.inputs` (including the zero-amount `B` leg) is sent in the `WithdrawalRequest.tokens` array to `withdraw()`.
4. Loop hits `B`: `_orders[commitment][B] == 0` → `revert UnknownOrder()` — the whole transaction reverts, and token `A`'s legitimate 100 units are never released to the solver (nor later refundable to the user), permanently stuck in the gateway.

Note: I could not fully verify whether the primary (non-tron) `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` implementation contains the identical `== 0` guard versus a different check, due to index/context limits on that file — this should be confirmed directly in the repo before treating the tron variant as the only affected instance.
