### Title
Automatic remote-URL rewrite trusts unvalidated hostname from GitHub API response, silently redirecting `origin` to attacker infrastructure - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The bug-class in the Sherlock report is: a state-transition function replaces a trusted resource reference (the yield strategy) with a new one, using a stale/incomplete check, allowing subsequent computations to silently operate on corrupted state. The GitHub Desktop analog is `updateRemoteUrl`, which replaces the local git `origin` remote URL with a URL taken from a GitHub API response, while validating only the URL **scheme** (`http`/`https`) and not the **hostname**, allowing a malicious or compromised GitHub Enterprise Server (or an on-path proxy serving repository API responses) to silently redirect the user's git remote to attacker-controlled infrastructure.

### Finding Description
`updateRemoteUrl` is invoked by `repositoryWithRefreshedGitHubRepository` in `app-store.ts` every time Desktop refreshes a repository's association with the GitHub API (a routine, automatic background operation, not a user-initiated "change remote" action): [1](#0-0) 

Inside `updateRemoteUrl`, the function pulls `clone_url` straight from the freshly fetched `apiRepo` object and compares it against the current remote: [2](#0-1) 

The only safety checks performed before overwriting the local remote are:
1. `protocolsMatch` — compares URL **scheme** only (`https === https`), not host.
2. `remoteUrlUnchanged` — confirms the user hasn't manually edited the *existing* remote away from the *previously stored* `gitHubRepository.cloneURL`.
3. `!urlsMatch` — confirms the *new* URL differs from the current remote.

None of these checks verify that the **new** `clone_url`'s hostname matches the original repository's hostname/endpoint. If all three conditions hold, Desktop calls: [3](#0-2) 

which invokes `gitStore.setRemoteURL`, ultimately running `git remote set-url origin <new_url>` against the actual git config on disk: [4](#0-3) [5](#0-4) 

By contrast, `urlMatchesRemote` (used elsewhere, e.g. to detect whether the user manually changed the remote) does compare hostname/owner/name: [6](#0-5) 

but this stricter comparison is applied only to the *old* stored `cloneURL` vs. the *current* remote — never to the *new* `apiRepo.clone_url` that ends up being written to disk. The corrupted value is the on-disk git `origin` remote URL (a value that determines where the user's future `git push`/`git fetch` operations go), and it is corrupted with no host validation and no user confirmation, unlike the analogous `UpstreamAlreadyExists` dialog flow which *does* prompt the user before rewriting the `upstream` remote: [7](#0-6) 

### Impact Explanation
If a GitHub Enterprise Server instance is compromised, malicious, or its API responses are served through an on-path proxy (an explicitly in-scope attacker primitive — "a git remote/proxy response"), it can return a repository object whose `clone_url` points to an entirely different host under attacker control. On the next automatic repository refresh, Desktop silently rewrites the local `origin` remote to that attacker URL with no dialog, confirmation, or warning shown to the user. Subsequent pushes/fetches from that repository would silently go to attacker infrastructure — this is precisely the "silent corruption of what the user commits or pushes" impact category, and can also lead to credential exposure if Git's credential helper subsequently negotiates auth material against the new (attacker) host.

### Likelihood Explanation
This requires the GitHub API endpoint the account is configured against (typically a GHES instance) to be compromised or intercepted — a realistic threat model for enterprise deployments using self-hosted GitHub Enterprise Server behind proxies, and one the task's valid-impact list explicitly includes ("a git remote/proxy response"). The refresh path (`repositoryWithRefreshedGitHubRepository`) runs automatically as part of normal repository refresh cycles, requiring no unusual user action, and the missing hostname check is a straightforward, reproducible logic gap rather than a theoretical corner case.

### Recommendation
In `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts`), before calling `gitStore.setRemoteURL`, validate that the hostname of `apiRepo.clone_url` matches the hostname of the account's configured `endpoint` (or of the existing remote), not just the URL scheme. Consider reusing `urlMatchesRemote`/`urlsMatch`-style hostname comparison, and/or surfacing a user-facing confirmation (similar to the `UpstreamAlreadyExists` dialog) before silently rewriting `origin`.

### Proof of Concept
1. Configure Desktop against a GitHub Enterprise Server account/endpoint (or intercept its API traffic via a malicious proxy).
2. Have the compromised/malicious server return, for a repository the user has cloned, an updated `clone_url` field pointing to `https://attacker.example.com/owner/repo.git` (same `https` scheme, different host) in the `fetchRepository` response consumed by `repositoryWithRefreshedGitHubRepository`.
3. Trigger a normal repository refresh in Desktop (happens automatically, e.g., on repository selection/periodic refresh).
4. Observe that `updateRemoteUrl` passes its `protocolsMatch`/`remoteUrlUnchanged`/`!urlsMatch` checks (host is never checked) and calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/owner/repo.git')`, rewriting `.git/config` without any dialog.
5. The next `git push`/`git fetch` performed through Desktop's UI silently targets `attacker.example.com`.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
