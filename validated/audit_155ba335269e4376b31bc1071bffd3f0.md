## Title
Positional (not identity-based) splicing of AI-generated conflict resolutions lets attacker-controlled file content silently corrupt what the user commits - ([File: app/src/lib/copilot-conflict-context.ts, app/src/lib/copilot-conflict-resolution.ts])

## Summary
The Hats finding's broken invariant is that a per-item existence check ("does *this* entry already have this value?") is used to gate an insert into a *shared, order-dependent* structure, so the safety of the whole structure silently depends on an assumption (one insert per distinct value) that the attacker can violate. The GitHub Desktop analog with the same shape: `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts:179-279` identifies conflict "hunks" purely by scanning for literal marker regexes (`<{7}`, `|{7}`, `={7}`, `>{7}`) with no correlation to git's own record of where a conflict actually is. The resulting hunk list is later re-spliced into the file **by ordinal position, not by identity** in `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), which explicitly states it matches resolutions "by order, not by line number." If the attacker-controlled repository content causes the hunk count/order the model sees to diverge from the hunk count/order this splicer finds on disk, resolutions get spliced into the wrong conflict blocks — and the result is written straight to disk and `git add`-ed with no diff shown to the user before staging (`app/src/lib/stores/app-store.ts:7258-7259`).

## Finding Description
`extractConflictHunks` treats any line matching `^<{7}`, `^\|{7}`, `^={7}`, `^>{7}` as a conflict boundary. There is no verification that these markers correspond to git's actual `MERGE_HEAD`-driven conflict regions — it is a pure text scan over `readFile(absolutePath, 'utf8')` content (`app/src/lib/copilot-conflict-context.ts:429-460`). A malicious/fetched repository fully controls the content of a conflicted file, including regions that are **not** part of the real conflict (e.g. a documentation file, a fixture, a string literal, or a previously-mis-resolved region containing literal `<<<<<<<`/`=======`/`>>>>>>>` text as ordinary content). Such content will be counted as one or more extra hunks by `extractConflictHunks`.

That hunk list, in file order, is sent to the Copilot model, which is asked to return one `resolvedContent` per hunk "matching the 'Conflict 1 of N', 'Conflict 2 of N' order from the input" (system prompt, `app/src/lib/copilot-conflict-resolution.ts:245`). The reconstruction step, `reassembleResolvedFile`, independently re-scans the *same* raw file for marker blocks and splices `hunkResolutions[hunkIndex]` into the `hunkIndex`-th block found, purely by counting order (`app/src/lib/copilot-conflict-resolution.ts:559-596`). There is no check that `hunkResolutions.length` equals the number of blocks encountered, nor that the blocks line up 1:1 with what the model was actually shown (e.g. if the model dropped/merged a hunk, or if the two independent scans of the file diverge in any way). When the counts or ordering diverge, the splicer will drop content into the wrong marker block (`hunkIndex < hunkResolutions.length` check just silently stops replacing once resolutions run out, while any real, later conflict blocks are left with the *previous* hunk's resolved text applied to them) — an attacker-shaped file can deterministically cause a specific unrelated block to receive a mismatched, or even attacker-influenced, resolution.

`_applyCopilotConflictResolutions` then writes this content directly to disk with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and immediately `git add`s the path (`app/src/lib/stores/app-store.ts:7258-7267`) before the user commits — the UI dialog (`copilot-conflicts-changes.tsx`) shows a diff for review, but the underlying corruption is in which text landed in which block, which is not something a casual diff review reliably catches when it's plausible-looking merged code.

## Impact Explanation
This is a "silent corruption of what the user commits" primitive as called out in the Valid Impact criteria: an attacker who controls a cloned/fetched repository's file content (not requiring local/physical access, admin rights, or leaked credentials) can cause GitHub Desktop's AI-assisted conflict resolver to write incorrect content into a conflict-adjacent region of a file the user then commits and pushes — without any indication to the user that the wrong block was patched. Because the corrupted region is adjacent to real code the user reviewed and expects, and the model's resolutions read as plausible merged code, this can introduce subtly wrong logic, reintroduced vulnerabilities, or reverted security fixes into the codebase that ships from the user's commit.

## Likelihood Explanation
Exploitation requires only that the victim (a) has an account/model configured for Copilot conflict resolution enabled (`enableCopilotConflictResolution()`), (b) merges/rebases/cherry-picks against a branch/commit whose content the attacker controls (a fork, PR branch, or any fetched ref), and (c) clicks "Resolve with Copilot" and "Continue Merge" — normal, expected user actions, not unnatural steps. The attacker's contribution is limited to shaping file text so `extractConflictHunks`'s naive marker scan produces a hunk count/order that diverges from what a correct git-anchored parse would give (e.g., embedding literal 7-character marker sequences in a string/comment inside a file that also has a real conflict). This is plausible in ordinary text/config/documentation files and doesn't require unusual repository structure.

## Recommendation
Do not rely on a second, independent full-text rescan (`reassembleResolvedFile`) to align with the first scan (`extractConflictHunks`) purely by ordinal position. Instead:
- Carry the exact character/line offsets of each detected hunk from `extractConflictHunks` through to reconstruction (rather than re-deriving them), and splice by offset, not by re-parsing.
- Validate that the number of hunks re-detected during reassembly exactly equals the number of hunks originally extracted and that markers are byte-identical at the same character positions before accepting any resolution.
- If counts/positions diverge, fail closed for that file (mark it skipped, requiring manual resolution) rather than applying a partial/misaligned splice.
- Additionally, disambiguate literal marker-like text from real git conflict markers where feasible (e.g., cross-check against `git diff --check`/`git status` unmerged path boundaries) rather than a bare regex scan of arbitrary file content.

## Proof of Concept
1. Attacker prepares a branch/fork containing a file, `notes.md`, with two regions:
   - Region A: legitimate merge conflict markers produced by the actual merge (e.g. two competing edits to a real function).
   - Region B: a documentation/code-sample block the attacker adds *earlier in the file* that contains literal text matching the marker regexes, e.g.:
     ```
     Example git conflict markers look like this:
     <<<<<<< HEAD
     old text
     =======
     new text
     >>>>>>> feature
     ```
     This text is a legitimate part of the file (e.g. a markdown tutorial) but is textually indistinguishable from a real conflict block to `extractConflictHunks`.
2. Victim fetches/merges the attacker's branch, causing a real merge conflict in the same file (region A). Git's own machinery is unaware of region B at all, since region B is not touched by the merge and contains no `MERGE_HEAD`-level conflict — it's just static file content that predates the merge.
3. Victim opens "Resolve with Copilot." `extractConflictHunks` scans the whole file text and finds **two** hunks: the attacker's fake region B and the real region A, in that file order.
4. The model returns two `resolvedContent` values, one per hunk, in the order it was given.
5. `reassembleResolvedFile` re-scans the raw file, again finds two marker blocks in the same order, and — relying purely on order — splices hunk 0's model output into region B and hunk 1's output into region A.
6. Because the model was told these are two "conflicts to resolve," and the "resolvedContent" for the fake hunk is nonsensical relative to real intent (it was resolving fabricated conflicting content, not a real design decision), the write to disk in `_applyCopilotConflictResolutions` silently replaces the attacker's crafted tutorial text with model-invented content **and**, more importantly, demonstrates the exact mechanism (ordinal, non-identity-based splicing across two independent full-file scans) that a more subtle attacker-crafted file — e.g., one designed to shift the *count* of hunks by exactly one via a malformed-but-recoverable marker sequence — could exploit to shift every subsequent real resolution by one position, corrupting the actually-merged code region without the discrepancy being obvious in the result dialog's diff.

Note: I was not able to execute this end-to-end (no runtime access), so the PoC is derived from static analysis of `extractConflictHunks`, `reassembleResolvedFile`, and `_applyCopilotConflictResolutions` reproduced above; the exact minimal crafted-marker sequence that reliably shifts hunk *count* by one (rather than just adding an extra, clearly-fake hunk) would need to be validated with a live run of the parser to confirm the precise misalignment window. export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue

Field rules:

hunks: An ordered array with one entry per conflict in the file, matching the "Conflict 1 of N", "Conflict 2 of N" order from the input. Each entry's resolvedContent is ONLY the merged content that replaces that specific conflict marker block (the region between <<<<<<< and >>>>>>>). Do NOT include surrounding non-conflicted code — the application splices each resolution into the original file automatically. If the resolution is to accept one side entirely, return that side's content verbatim. For an intentional deletion, use an empty string. For delete-vs-modify conflicts, hunks must be an empty array.

action: Only for delete-vs-modify conflicts. Set to "keep" to preserve the modified file, or "delete" to accept the deletion. Use commit messages and PR context to determine intent — if the deletion was part of a refactoring that moved functionality elsewhere, prefer "delete"; if the modifications add important functionality that should be preserved, prefer "keep". Omit this field for regular text conflicts.

reasoning: Terse, direct prose — enough detail to verify the decision, not a wall of text. State what each side did in this file, what you kept, and any trade-off. Typically 1-4 sentences depending on complexity.

summary: A markdown banner with exactly two ### headings ("Conflicting changes" then "Resolution"). Write natural prose a developer would say to a teammate. Be brief — per-file detail belongs in reasoning, not here. When many files conflicted, summarize them ("several menu components") rather than listing each. Refer to PRs as "#1234" and commits as short SHAs (no URLs — the app linkifies them). Do not address the user as "you"; write "the current branch". Bold any trade-off where one side's change was dropped.

references: The PRs and commits a reader would open to understand the conflict. Include every genuinely informative one — skip merge commits, WIP/fixup/squash commits, and low-signal messages. "type" is "pullRequest" or "commit"; "id" is the PR number (no #) or hex SHA. Cite the PR instead of its squash-merge commit when both exist. Return an empty array only when no PRs or commits exist in context.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
