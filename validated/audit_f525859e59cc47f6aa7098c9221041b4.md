### Title
Diff line-selection is tracked by numeric index, not by line identity, allowing silent inclusion/exclusion of unreviewed content in a commit when the working-directory diff is refreshed mid-selection - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`DiffSelection` records which lines a user wants to commit as a `Set<number>` of *line indices* (`divergingLines`), not as a hash or content fingerprint of the line itself. When the working-directory diff for the selected file is reloaded (`updateChangesWorkingDirectoryDiff`), the code only re-validates that a previously-diverging index is still "selectable" in the *new* diff — it never checks whether the text at that index is still the *same* line the user actually reviewed and checked. If the file's on-disk/indexed content shifts between the time the user made a partial selection and the time the diff is silently refreshed (e.g. because of a fetch/pull/checkout that touched the file, or any other background repository refresh), a stale index can now point at completely different content, and that content is committed (or excluded) without the user ever seeing or approving it.

### Finding Description
`DiffSelection.isSelected` and `isSelectable` operate purely on integer line indices: [1](#0-0) 

The comment in `withSelectableLines` explicitly documents the weak invariant being relied upon — it only prunes indices, it does not verify the underlying content is unchanged: [2](#0-1) 

The consumer of this, `updateChangesWorkingDirectoryDiff`, reloads the diff for the currently selected file and reconciles it with the existing (possibly stale) selection purely by recomputing which indices are still "includeable", explicitly acknowledging the diff "might have changed dramatically since last we loaded it": [3](#0-2) 

Nowhere in this reconciliation path is the actual line text compared against what it was when the user selected/deselected it. The only guard is whether the *same index* still happens to be an includeable (addition/deletion) line in the freshly loaded diff — which will very often be true even though the line's content has completely changed (e.g. after a hunk shifts by the same number of lines, or after an upstream change replaces a line 1:1).

The corrupted selection then feeds directly into patch generation, which trusts `file.selection.isSelected(absoluteIndex)` at commit time with no additional validation: [4](#0-3) 

This is the same broken invariant as the reported bug class: a stateful collection (there, a dynamic array cast to/from a static array; here, a `Set<number>` of "selected" indices) is silently reinterpreted across a boundary where its length/shape assumptions no longer hold, and the mismatch is absorbed rather than surfaced — resulting in wrong data (wrong array elements there, wrong committed lines here) being used.

### Impact Explanation
This can result in silent corruption of what the user commits and pushes — a Valid Impact category. A user could review and select specific hunks/lines of a file for a partial commit, then (before committing) trigger any action that causes Desktop to refresh the working-directory diff for that file — most plausibly a `git pull`/fetch-and-fast-forward from a remote that also modifies the same tracked file, or any external/background change to the file that Desktop's file watcher picks up. If the attacker controls that remote/branch (a Valid Impact precondition: "a git remote/proxy response"), they can craft new content for the file so that after the merge/checkout, the still-"includeable" line indices the user previously selected now correspond to attacker-controlled or otherwise unintended text. The victim's next partial commit will silently include (or exclude) that content without any re-review, re-diffing UI change, or warning — this is a genuine "commit what you didn't intend" primitive, not a crash or display glitch.

### Likelihood Explanation
This requires no local access, admin rights, or pre-existing malware — only a normal collaborative workflow: the victim has partial (line-level) selections pending in the Changes view, and a `pull`/fetch/checkout occurs (user-initiated or background) against a remote the attacker can push to. GitHub Desktop actively encourages partial/line-level staging as a first-class feature, and background refreshes of the diff for the currently selected file happen routinely (e.g., after any git operation, external editor save, or repository status refresh) — increasing the odds this race window is hit in practice. Likelihood is moderate: it depends on timing (the user must not have committed before the file changed), but no unnatural user steps beyond normal usage are required.

### Recommendation
- Do not key selection persistence purely on numeric line index across diff reloads. Instead, invalidate/reset the selection for any hunk whose content actually differs from what was previously diffed (e.g., compare line text/hash at each surviving index, not just "is it still includeable").
- When `updateChangesWorkingDirectoryDiff` detects the diff has structurally changed since the last load, prefer clearing partial selections back to "no selection" for affected files (as is already done in `updateChangedFiles`'s `clearPartialState` path) rather than silently remapping indices.
- Surface a UI warning/refresh prompt when a file with a pending partial selection changes underneath the user, forcing explicit re-review before committing.

### Proof of Concept
1. Victim has a repository with `origin` pointing to an attacker-writable/malicious remote (e.g., a compromised or attacker-created upstream branch the victim tracks).
2. Victim modifies `file.txt` locally and opens the Changes view; Desktop renders a diff with hunks and the victim selects only specific added/deleted lines (say lines at index 10–12) for a partial commit, leaving the commit box open (not yet clicked "Commit").
3. Attacker pushes a commit to the tracked remote branch that also touches `file.txt`, restructuring it so that lines at the same unified-diff indices (10–12) now represent different content than what the victim reviewed, while keeping the same number of includeable lines (so `withSelectableLines` does not prune them).
4. Victim performs a normal `git pull`/fetch-and-merge (or Desktop performs a background refresh of the diff for the selected file, e.g., after an external process touches the file). `updateChangesWorkingDirectoryDiff` reloads the diff and calls `currentlySelectedFile.selection.withSelectableLines(selectableLines)`, which keeps line indices 10–12 marked as diverging/selected because they are still "includeable" — despite their content having changed.
5. Victim clicks "Commit" without re-inspecting the diff (since the UI does not force a re-review). `formatPatch` uses `file.selection.isSelected(absoluteIndex)` to include the new, attacker-influenced lines at indices 10–12 in the generated patch, and they are committed/pushed as if the victim had explicitly selected that exact content — which they never saw.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

  /**
   * Returns a copy of this selection instance with a specified set of
   * selectable lines. By default a DiffSelection instance allows selecting
   * all lines (in fact, it has no notion of how many lines exists or what
   * it is that is being selected).
   *
   * If the selection instance lacks a set of selectable lines it can not
   * supply an accurate value from getSelectionType when the selection of
   * all lines have diverged from the default state (since it doesn't know
   * what all lines mean).
   */
  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }
