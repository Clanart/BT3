### Title
Quadratic transcript cloning enables remote resource exhaustion during MuSig key aggregation - ([File: crypto/dkg/musig/src/lib.rs](crypto/dkg/musig/src/lib.rs))

### Summary
`musig_key_multiexp`, `musig_key`, `musig_key_vartime`, and `musig` construct one transcript containing every participant public key, then clone and hash that entire transcript once per key. A 65,535-key participant list—the maximum accepted size—therefore causes approximately 128 GiB of transcript data to be copied and hashed from only approximately 2 MiB of public input. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`binding_factor_transcript` encodes the context, key count, and every serialized public key into a single `Vec<u8>`. [4](#0-3)  `binding_factor` then receives that vector by value and hashes it, requiring a complete copy for every participant index. [5](#0-4)  `musig_key_multiexp` invokes `binding_factor::<C>(transcript.clone(), i)` inside the `1 ..= keys_len` loop, creating quadratic total bandwidth in the number of supplied keys. [6](#0-5)  `musig` repeats the same pattern while constructing threshold keys. [7](#0-6) 

### Impact Explanation
An unprivileged participant able to supply a public-key list can stall the process performing MuSig key aggregation or threshold-key construction. For the maximum accepted `u16::MAX` keys, each cloned transcript is approximately 2,097,154 bytes, and cloning it 65,535 times copies approximately 128 GiB before accounting for hashing and allocation overhead. [8](#0-7) [9](#0-8) [6](#0-5)  The work is therefore disproportionate to the roughly 2 MiB serialized input and can make the affected key-generation or aggregation operation unavailable.

### Likelihood Explanation
The attacker-controlled `keys` slice is public input to `musig_key`, `musig_key_vartime`, and `musig`. [10](#0-9)  `check_keys` permits as many as `u16::MAX` entries and only rejects empty, oversized, or duplicate lists. [1](#0-0)  No key ownership, secret knowledge, threshold participation, or malformed encoding is required to trigger the quadratic path. [11](#0-10) 

### Recommendation
Avoid cloning the complete key transcript for every participant. Hash the context, length, and keys once into a reusable transcript state, then derive each participant’s binding factor by appending only the participant index to a cloned transcript state or by using a transcript API that supports incremental state reuse. Alternatively, precompute a digest of the serialized key list and calculate each binding factor from that fixed-size digest plus the index.

### Proof of Concept
The following input is valid under `check_keys` and reaches the quadratic cloning path:

```rust
// Approximately 2 MiB of distinct public keys.
let keys: Vec<C::G> = (1_u16 ..= u16::MAX)
  .map(|i| C::generator() * C::F::from(u64::from(i)))
  .collect();

// Each iteration clones and hashes a ~2 MiB transcript.
let _ = musig_key_vartime::<C>([0; 32], &keys);
```

`keys.len()` is 65,535, `binding_factor_transcript` emits approximately `32 + 2 + (65,535 * point_size)` bytes, and the loop at `musig_key_multiexp` clones that vector once for every key. [2](#0-1) [6](#0-5)

fn binding_factor_transcript<C: Ciphersuite>(
  context: [u8; 32],
  keys_len: u16,
  keys: &[C::G],
) -> Vec<u8> {
  debug_assert_eq!(usize::from(keys_len), keys.len());

  let mut transcript = vec![];
  transcript.extend(&context);
  transcript.extend(keys_len.to_le_bytes());
  for key in keys {
    transcript.extend(key.to_bytes().as_ref());
  }
  transcript
}

fn binding_factor<C: Ciphersuite>(mut transcript: Vec<u8>, i: u16) -> C::F {
  transcript.extend(i.to_le_bytes());
  C::hash_to_F(b"dkg-musig", &transcript)
}

  let transcript = binding_factor_transcript::<C>(context, keys_len, keys);

  }
