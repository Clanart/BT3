### Title
Freezing a code object does not prevent new mutable packages from being deployed to the same address - ([File: aptos-move/framework/aptos-framework/sources/code.move])

### Summary
`object_code_deployment::freeze_code_object` (and the underlying `code::freeze_code_object`) is documented as making an on-chain code object permanently immutable, with no "unfreeze" path by design. In practice, freezing only marks the upgrade policy of the *packages that already exist* in the `PackageRegistry` at that address as immutable. The owner of the object (who still retains the `ExtendRef` in `ManagingRefs`, since freezing never revokes it) can still call `object_code_deployment::upgrade()` afterward with a *new* package name whose module names don't collide with the frozen package's modules. Because `code::publish_package` only enforces the immutability check (`check_upgradability`) when the new package's name matches an existing package, a differently-named package skips that check entirely (`check_coexistence` is used instead, which never inspects `upgrade_policy`). This lets new, fully mutable/arbitrary-policy code be added to a supposedly frozen/immutable object address.

### Finding Description
`code::publish_package` decides which validation path to take purely by comparing package `name`: [1](#0-0) 

- If `old.name == pack.name`, `check_upgradability` is invoked, which aborts with `EUPGRADE_IMMUTABLE` if the existing package's `upgrade_policy` is already immutable: [2](#0-1) 
- If the names differ, only `check_coexistence` runs, which merely verifies that module names in the new package don't clash with the old package's module names — it never looks at `old_pack.upgrade_policy`: [3](#0-2) 

`code::freeze_code_object` only mutates the `upgrade_policy` of packages currently stored in the registry; it never revokes the object's `ExtendRef`/`ManagingRefs`, so the object owner retains the ability to generate the code-object signer indefinitely: [4](#0-3) 

`object_code_deployment::upgrade` only checks that the caller owns the object and that `ManagingRefs` exists — it does not check whether the object has been frozen as a whole: [5](#0-4) 

Because of this, the sequence: deploy package "A" → `freeze_code_object` → `upgrade` with a differently-named package "B" (whose module names don't overlap "A"'s modules) succeeds and adds a brand-new, non-immutable package "B" to the very same code-object address that was supposedly made permanently immutable.

This directly parallels the report's core defect class: a lock-down/immutability action (`transferOwnershipToZeroAddress` / `freeze_code_object`) that fails to account for a still-valid secondary authority path (`pendingOwner`/`confirmOwnershipTransfer` vs. the retained `ExtendRef` + differently-named-package publish path) that can still mutate the supposedly locked state.

### Impact Explanation
Users and dependent packages that treat a frozen code object as permanently immutable (e.g., listing it as a dependency with the expectation that "immutable" means no new code can ever appear at that address, or relying on the module's own documentation: "there is no unfreeze function... once modules are marked immutable, they cannot be made mutable again") are misled. The object owner can silently introduce new mutable/arbitrary-policy modules at the same address after freezing, undermining trust guarantees that other on-chain code or off-chain verifiers place on "frozen"/immutable code objects. This is a code-safety/upgrade-policy invariant violation with mainnet relevance, since object code deployment is a supported production publish path.

### Likelihood Explanation
The owner of the code object needs no special privilege beyond what they already had before freezing (they never lose the `ExtendRef`). All that's required is publishing a package with a different `name` field and module names that don't collide with the already-frozen package's modules — both fully within the owner's control at initial-deploy or upgrade time. This makes the bypass trivial and always available whenever `freeze_code_object` has been used, i.e., a systemic property of the current design rather than an edge case, though it can only be exercised by the object's own owner (not an arbitrary third party) since `object::is_owner` is still checked.

### Recommendation
- Track an object-level "frozen" flag (e.g., a boolean in `ManagingRefs` or a new `key` resource) set by `freeze_code_object`, and have `object_code_deployment::publish`/`upgrade` (or `code::publish_package`) reject any new-package publish to that address once the object-level flag is set, regardless of package name.
- Alternatively, have `code::freeze_code_object` also revoke/burn the `ExtendRef` capability (or otherwise disable future signer generation for the object), so no further `publish_package_txn` calls can originate from that address at all.
- Update `check_coexistence` (or add a new check) to also assert that none of the co-existing old packages are immutable before allowing a new differently-named package into the same registry/address.

### Proof of Concept
1. `publisher` calls `object_code_deployment::publish` with package `pack_initial` (module `test`), creating object `O` with `ManagingRefs`.
2. `publisher` calls `object_code_deployment::freeze_code_object(publisher, O)`; the registry at `O` now has package `pack_initial` with `upgrade_policy = immutable`.
3. `publisher` calls `object_code_deployment::upgrade(publisher, metadata_for_pack_new, code_for_pack_new, O)` where `pack_new` has a distinct `name` and modules whose names don't collide with `test` (e.g., module `test2`).
4. Inside `code::publish_package`, `old.name != pack.name`, so `check_coexistence` runs (no `upgrade_policy` check) instead of `check_upgradability`; the transaction succeeds and a brand-new mutable package `pack_new` is added to the registry at the "frozen" address `O`.

This can be verified by extending `aptos-move/e2e-move-tests/src/tests/object_code_deployment.rs`'s `object_code_deployment_freeze_code_object` test to attempt a subsequent `Upgrade` action with a differently-named package/module set instead of re-using the same package, and observing that it succeeds instead of aborting.

    public fun freeze_code_object(publisher: &signer, code_object: Object<PackageRegistry>) acquires PackageRegistry {
        let code_object_addr = code_object.object_address();
        assert!(exists<PackageRegistry>(code_object_addr), error::not_found(ECODE_OBJECT_DOES_NOT_EXIST));
        assert!(
            object::is_owner(code_object, signer::address_of(publisher)),
            error::permission_denied(ENOT_PACKAGE_OWNER)
        );

        let registry = borrow_global_mut<PackageRegistry>(code_object_addr);
        registry.packages.for_each_mut(|pack| {
            let package: &mut PackageMetadata = pack;
            package.upgrade_policy = upgrade_policy_immutable();
        });

        // We unfortunately have to make a copy of each package to avoid borrow checker issues as check_dependencies
        // needs to borrow PackageRegistry from the dependency packages.
        // This would increase the amount of gas used, but this is a rare operation and it's rare to have many packages
        // in a single code object.
        registry.packages.for_each(|pack| {
            check_dependencies(code_object_addr, &pack);
        });
    }

    /// Checks whether a new package with given names can co-exist with old package.
    fun check_coexistence(old_pack: &PackageMetadata, new_modules: &vector<String>) {
        // The modules introduced by each package must not overlap with `names`.
        old_pack.modules.for_each_ref(|old_mod| {
            let old_mod: &ModuleMetadata = old_mod;
            let j = 0;
            while (j < vector::length(new_modules)) {
                let name = vector::borrow(new_modules, j);
                assert!(&old_mod.name != name, error::already_exists(EMODULE_NAME_CLASH));
                j += 1;
            };
        });
    }

    /// Upgrades the existing modules at the `code_object` address with the new modules passed in `code`,
    /// along with the metadata `metadata_serialized`.
    /// Note: If the modules were deployed as immutable when calling `publish`, the upgrade will fail.
    /// Requires the publisher to be the owner of the `code_object`.
    ///
    /// Note: In order to publish a new package to an existing code object,
    /// this `upgrade` function should be called, rather than `publish`.
    public entry fun upgrade(
        publisher: &signer,
        metadata_serialized: vector<u8>,
        code: vector<vector<u8>>,
        code_object: Object<PackageRegistry>,
    ) {
        let publisher_address = signer::address_of(publisher);
        assert!(
            object::is_owner(code_object, publisher_address),
            error::permission_denied(ENOT_CODE_OBJECT_OWNER),
        );

        let code_object_address = code_object.object_address();
        assert!(exists<ManagingRefs>(code_object_address), error::not_found(ECODE_OBJECT_DOES_NOT_EXIST));

        let extend_ref = &borrow_global<ManagingRefs>(code_object_address).extend_ref;
        let code_signer = &extend_ref.generate_signer_for_extending();
        code::publish_package_txn(code_signer, metadata_serialized, code);

        event::emit(Upgrade { object_address: signer::address_of(code_signer), });
    }
