Confirmed: this is a real logic bug reachable by an unprivileged account.

### Title
mWOMSVBaseRewarder._calExpireForfeit ignores getRewardablePercentWAD, allowing users in full unlock cooldown to claim rewards with zero forfeiture - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never queries `mWOMSV.getRewardablePercentWAD(_account)` and instead always sets `rewardableAmount = _amount`, so `forfeitAmount` is always zero regardless of the user's lock/cooldown state. The sibling contract `vlMGPBaseRewarder._calExpireForfeit` correctly multiplies by `vlMGP.getRewardablePercentWAD(_account)` [1](#0-0) , confirming the intended design that was dropped in the mWOMSV variant [2](#0-1) .

### Finding Description
`mWomSV.getRewardablePercentWAD(_user)` computes the fraction of a user's mWomSV that is still fully locked versus in cooldown/unlocked, intended to reduce rewards for users who have started unlocking [3](#0-2) . When a user calls `startUnlock` for their full balance, `getUserTotalLocked` drops to 0 and `getRewardablePercentWAD` should approach 0, meaning nearly all pending rewards should be forfeited on claim.

However, in `mWOMSVBaseRewarder._sendReward`, the forfeit amount is computed via `_calExpireForfeit(_account, userRewards[_rewardToken][_account])` [4](#0-3) . The implementation of `_calExpireForfeit` is:

```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
``` [2](#0-1) 

This never calls `mWOMSV.getRewardablePercentWAD(_account)`, so `rewardableAmount` is unconditionally equal to `_amount`, making `forfeitAmount` always `0` (the `_account` parameter is unused for anything meaningful). Compare this to the correct pattern in `vlMGPBaseRewarder.sol`:
```solidity
uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
``` [5](#0-4) 

`getReward` is externally reachable by any account through `MasterMagpie` (which enforces `onlyMasterMagpie`), and there is no other check that reduces `userRewards` for accounts that are mid-cooldown or fully unlocked. Since `balanceOf` in the rewarder still counts staking-info balance (locked + cooldown) for reward accrual purposes [6](#0-5) , a user keeps earning reward-per-token credit while unlocking, and then claims 100% of it with no forfeiture, whereas the design intent (as shown by the analogous vlMGP contract and the presence of `ForfeitRewardAdded`/`_queueNewRewardsWithoutTransfer` logic) was to redistribute forfeited rewards from unlocking users back to fully-locked holders.

### Impact Explanation
This is a theft of unclaimed yield meant to be forfeited and redistributed to still-locked mWomSV holders. Any user who has started unlocking (`rewardablePercentWAD` near 0) can still call `getReward`/`getRewards` and receive 100% of `userRewards[token][account]`, with `forfeitAmount` permanently 0. This directly reduces the yield that should have been redirected to remaining locked stakers via `_queueNewRewardsWithoutTransfer`, causing a real, quantifiable, repeatable diversion of protocol reward funds — matching the "theft of unclaimed yield" impact class.

### Likelihood Explanation
No special privileges are required — any holder of mWomSV can trigger this by simply calling the public `startUnlock` function (via mWomSV/MasterMagpie) for their full balance and then calling `getReward` through MasterMagpie's normal harvest flow. This is deterministic, requires no timing, front-running, or flash loans, and is repeatable by every mWomSV holder for every reward token continuously, since the forfeiture logic is always inert. This is a design/implementation regression (dead code) rather than a governance or oracle issue, making exploitation trivial and universal for the user base.

### Recommendation
Fix `_calExpireForfeit` in `rewards/mWOMSVBaseRewarder.sol` to mirror `vlMGPBaseRewarder.sol`: fetch `mWOMSV.getRewardablePercentWAD(_account)` and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`, ensuring `ILocker`/`mWomSV` exposes `getRewardablePercentWAD` consistently and that the interface used (`mWOMSV`) supports the call.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, and `MasterMagpie` per existing test fixtures.
2. Attacker locks `X` mWomSV via `lock`/`lockFor`.
3. Fast-forward time and call `queueNewRewards`/`donateRewards` on the rewarder to accrue `earned(attacker, token) = R > 0`.
4. Attacker calls `startUnlock(X)` (moving 100% of balance into cooldown, driving `mWomSV.getRewardablePercentWAD(attacker)` toward 0).
5. Immediately (or after any delay, since forfeiture logic never fires) attacker calls `getReward(attacker, attacker)` through MasterMagpie.
6. Assert: `IERC20(rewardToken).balanceOf(attacker) == R` (full amount transferred) and `rewards[rewardToken].queuedRewards == 0` (no forfeited amount redirected), despite `mWOMSV.getRewardablePercentWAD(attacker)` being near 0 at claim time — demonstrating `claimed == earned` with zero forfeiture in the fully-unlocked state.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
