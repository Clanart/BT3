### Title
Silent corruption of committed content via stale diff-offset reuse in partial-file staging - (File: `app/src/lib/git/apply.ts`)

### Summary
The Wells `read-only reentrancy` report boils down to a broken Checks-Effects-Interactions invariant: a value is *checked/read* at one point in time, an external/async operation intervenes, and the *effect* (the on-chain state change) is produced from a second, independent read that no longer matches what was validated. GitHub Desktop has a structurally identical pattern in its partial-commit ("stage some lines/hunks") flow: the user's line-selection is computed against one `git diff` read, but the actual patch that gets staged and committed is built from a *second, unguarded* `git diff` read taken later, with no check that the two reads agree.

### Finding Description
When a user partially selects lines/hunks of a file to commit, Desktop stores that selection as byte offsets into a diff (`DiffSelection`, computed via `updateChangesWorkingDirectoryDiff`, which calls `getWorkingDirectoryDiff(repository, file, this.hideWhitespaceInChangesDiff)`) [1](#0-0) .

When the user clicks "Commit", `_commitIncludedChanges` reads the currently selected files straight out of the `repositoryStateCache` and passes them, unchanged, into `createCommit` after an `await` on `formatCommitMessage` [2](#0-1) .

`createCommit` → `stageFiles` routes any file with a partial (non-`All`) selection through `applyPatchToIndex` [3](#0-2) .

`applyPatchToIndex` does **not** reuse the diff the selection was computed against. It calls `getWorkingDirectoryDiff(repository, file)` again — a brand-new `git diff` invocation — and then feeds that fresh diff plus the *stale* `DiffSelection` (which encodes only integer line/hunk offsets, not content hashes) into `formatPatch` to build the patch that is `git apply --cached`'d into the index [4](#0-3) . There is no check anywhere in this path that the second diff is identical to the first; the only invariant assumed is "the offsets still mean the same thing," which is exactly the "reserves haven't changed" assumption that failed in the Wells report.

Contrast this with numerous other places in `app-store.ts` that *do* implement the correct guard — re-reading state after an `await` and bailing if it changed underneath (`updateChangesWorkingDirectoryDiff`'s "stateAfterLoad" check [5](#0-4) , `updateChangesStashDiff`'s "Something has changed... bail" check [6](#0-5) , and `merge-choose-branch-dialog.tsx`'s tip-mismatch bail [7](#0-6) ). The commit-staging path in `apply.ts` is missing the equivalent guard.

### Impact Explanation
If the working-directory content that `git diff` returns for a file changes between the first read (used to render the diff and let the user pick lines) and the second read inside `applyPatchToIndex` (used to actually build the patch), the user's line-offset selection is silently reapplied to different underlying content. This can result in the user unknowingly staging/committing lines they never reviewed or approved — a direct instance of "silent corruption of what the user commits or pushes." Such divergence between two consecutive `git diff` invocations of the same path can occur with attacker-supplied repository configuration (e.g., `.gitattributes` normalization/`text=auto`/`eol=` settings, or configured clean/smudge filters that don't round-trip content deterministically) shipped inside a cloned/fetched repository, combined with the natural async window Desktop itself introduces between diff-selection and commit (`await formatCommitMessage(...)` in `_commitIncludedChanges`).

### Likelihood Explanation
The vulnerable code path is exercised on every partial commit (a very common, everyday Desktop action), and the missing invariant check is unconditional — it isn't guarded by any feature flag. What's uncertain (and I could not fully verify from the available index) is exactly how reliably an attacker-controlled repository configuration alone can force two consecutive `git diff` calls on the same working-tree file to disagree without any additional local write happening in between; this would need to be validated empirically (e.g., with autocrlf/renormalization filters or a race against Desktop's own background status refresh) to confirm real-world reachability without any local trust step.

### Recommendation
In `applyPatchToIndex` (and anywhere else a stored `DiffSelection` is reapplied to a freshly fetched diff), pin the selection to the diff it was computed from — e.g., store and re-verify a content hash/identity of the diff (or the file's blob OID / mtime+size) at commit time, and abort the commit (surfacing an error/refresh prompt to the user) if the working-directory diff for that path has changed since the selection was made, mirroring the "bail if state changed underneath" pattern already used elsewhere in `app-store.ts`.

### Proof of Concept
Conceptual reproduction (not fully verified end-to-end against the live app):
1. Modify a tracked file and open it in Desktop's Changes view; select only a subset of lines/hunks to commit (partial selection), leaving the commit dialog open.
2. Before clicking "Commit", cause the working-tree diff for that same file to change without altering the on-disk bytes the user is looking at — e.g. via a repository-configured `.gitattributes` normalization/filter (`text=auto`, `eol=lf`/`crlf`, or a custom clean/smudge filter) that produces different normalized output on a second `git diff` invocation, or via a concurrent write racing Desktop's own async gap in `_commitIncludedChanges` between capturing `selectedFiles` and the later `applyPatchToIndex` call.
3. Click "Commit". `applyPatchToIndex` re-fetches the diff, and `formatPatch` reapplies the stale line-offset selection to the new diff, staging different content than what was shown/approved, which `_commitIncludedChanges` then commits without any warning. [4](#0-3) [2](#0-1) [3](#0-2)

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
