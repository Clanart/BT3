### Title
Attacker-supplied identity point in FROST preprocess/aggregate nonce crashes Bitcoin signing via unhandled panic on point-at-infinity - ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
CVE-2016-4574 is an off-by-one / boundary decode error on untrusted bytes that causes an out-of-bounds read and a remote denial of service. The analog in Serai is a malformed-point decode path: points received from untrusted participants (FROST `Commitments`/`Preprocess` bytes parsed through `Commitments::read` / `read_preprocess`) flow into `Hram::hram` → `x()`/`x_only()`, which panic on the point at infinity instead of returning an error. A malicious participant can abort any Bitcoin signing session by submitting preprocess bytes that decode to (or sum to) the identity point.

### Finding Description
`networks/bitcoin/src/crypto.rs` decodes secp256k1 points without any error channel for infinity:

```rust
// networks/bitcoin/src/crypto.rs:13-23
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
pub(crate) fn x_only(key: &ProjectivePoint) -> XOnlyPublicKey {
  XOnlyPublicKey::from_slice(&x(key)).expect("x_only was passed a point which was infinity or odd")
}
```

`Hram::hram` (lines 59-73) calls `x(R)` and `x(A)` directly, and `Schnorr::verify` (lines 138-150) calls `needs_negation(&sig.R)`. The aggregate nonce `R` is the sum of per-participant nonce commitments, which arrive as untrusted bytes deserialized via `read_G` inside `TransactionSignMachine::read_preprocess` (`networks/bitcoin/src/wallet/send.rs:351-353`). `read_G` (`crypto/ciphersuite/src/lib.rs:91-100`) only checks canonicality — it does not reject the identity element — so a participant whose nonce commitments sum to the identity (a lone malicious signer can trivially arrange this by choosing its commitments as the negation of the honest sum) makes `R` the point at infinity. When `TransactionSignMachine::sign` → `AlgorithmSignMachine::sign` → `IetfSchnorr`/`Hram::hram` is reached, `x(R)` executes `expect("point at infinity")` and panics.

The same panic exists for `x(A)` if the tweaked group key is the identity, and in `verify` via `needs_negation(&sig.R)`. The doc comments ("Panics on invalid input", "may panic if called with nonces … which are the point at infinity (which have a negligible probability for a well-reasoned caller, even with malicious participants present)") assume negligibility, but a malicious participant can deterministically force the aggregate nonce to infinity — it is not a probabilistic event.

### Impact Explanation
Any remote peer participating in a Bitcoin threshold signing session can crash the signing process (and every honest participant processing the malicious preprocess) with a panic, causing denial of service of the wallet/signing round. This mirrors the CVE's class: malformed decoded input reaching a code path with no error handling, producing a crash reachable by an unprivileged party supplying public bytes.

### Likelihood Explanation
Trivially triggerable by any single signing participant in a `t`-of-`n` Bitcoin FROST session: they broadcast preprocess commitments chosen so the summed nonce is the identity point (or directly submit an identity-encoding nonce if the encoding for their curve admits it through `from_bytes`). No collusion, key material, or off-path capability is needed — only bytes passed to `read_preprocess`. One caveat: whether `k256`'s `PrimeGroup::from_bytes` accepts the SEC1 infinity encoding (`0x00`) through the canonical check in `read_G` is curve-encoding dependent; the aggregate-sum route is unconditional regardless, since the resulting `R` is computed in-circuit and is not re-validated.

### Recommendation
Validate the aggregate nonce and group key for non-identity before calling `Hram::hram`/`verify` (e.g., an `is_identity()` check in `Schnorr::verify`/`verify_share` and in the FROST sign path that rejects offending participants via `FrostError`), and/or have `read_G`/commitment parsing reject the identity point. Replace the `expect`/`from_slice().expect` in `x()`/`x_only()` with a `Result`-returning API so malformed input yields an error, not a panic.

### Proof of Concept
Conceptual: in a `SignableTransaction` → `TransactionMachine` session with ≥1 malicious participant:
1. Attacker reads honest participants' preprocesses (or goes first and fixes its own later) and crafts nonce commitments `D', E'` such that `D' + Σ_honest D = identity` (send `D' = -(Σ_honest D)`, likewise for the binding component).
2. Attacker serializes these via `Preprocess::write`; honest nodes deserialize them with `read_preprocess`.
3. `TransactionSignMachine::sign` computes aggregate `R = identity` and calls `Schnorr`/`Hram::hram` → `x(&identity)` → `encoded.x().expect("point at infinity")` → panic, aborting the session on every honest node.
