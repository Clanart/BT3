## Finding: Dependency upgrade-policy invariant is never enforced at publish time [1](#0-0) 

### Title
Package upgrade-policy vs. dependency-strength invariant (`EDEP_WEAKER_POLICY` / `EDEP_ARBITRARY_NOT_SAME_ADDRESS`) is dead code on the normal publish path, letting `immutable`/`compatible` packages silently depend on weaker-policy code — (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
`check_dependencies` is the only function in `code.move` that enforces that a package's dependencies have an upgrade policy at least as strong as the package itself, and that `arbitrary`-policy dependencies live at the same address as the depending package [2](#0-1) . This is exactly the guarantee documented in the Move book ("an `immutable` package cannot refer directly or indirectly to a `compatible` package") [3](#0-2)  and codified as Requirement 5 in the module's own formal-verification spec, marked "This has been manually audited" [4](#0-3) .

However, tracing all call sites of `check_dependencies` shows it is invoked **only** from `freeze_code_object` [5](#0-4) . The main publish/upgrade entry point, `publish_package` (lines 150-231), never calls `check_dependencies` — it only calls `check_upgradability` (own-package policy monotonicity) and `check_coexistence` (module-name clashing), then dispatches straight to the native `request_publish`/`request_publish_with_allowed_deps`, which only validate that declared dependency *bytecode* references match the metadata (`allowed_deps`), not the dependency *policy strength* [6](#0-5) .

### Finding Description
`check_dependencies` performs two policy-safety checks per declared dependency:
- `assert!(dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy, EDEP_WEAKER_POLICY)`
- `assert!(dep.account == publish_address, EDEP_ARBITRARY_NOT_SAME_ADDRESS)` when the dependency itself is `arbitrary`

Neither check runs when a package is first published or upgraded via `publish_package`/`publish_package_txn` [7](#0-6) , nor via the account-based `code_publish_package_txn`, resource-account publishing [8](#0-7) , or object-code `publish`/`upgrade` (which both just forward to `code::publish_package_txn`) [9](#0-8) . The check only fires if and when the code-object owner explicitly calls `freeze_code_object`. For any account-published package (there is no object at all, hence no freeze entrypoint reachable via `code::freeze_code_object`, since that requires `Object<PackageRegistry>`), the check is unreachable for the lifetime of the package.

So a malicious or careless publisher can declare their package's own `upgrade_policy` as `immutable` (or `compatible`) in `Move.toml`/`PackageMetadata` while listing a dependency (`PackageDep`) whose on-chain package has policy `compatible` or even `arbitrary`. The metadata will pass all on-chain checks — `check_upgradability` only looks at the package's own prior version, and the native `allowed_deps` check only verifies the dependency's modules are actually the ones referenced in bytecode, not that its policy is compatible/frozen.

### Impact Explanation
This breaks the documented "no unexpected updates can happen under the hood" guarantee for supposedly immutable/frozen packages. Any package or user that depends on, or reasons about, a package's `immutable` label as a transitive-safety guarantee (e.g., other contracts, indexers, or auditors verifying via `aptos move verify-package` that upstream code cannot change) can be misled: the "immutable" package can freely reference a mutable dependency that is later swapped for arbitrary bytecode by its owner (especially dangerous for `arbitrary`-policy deps at another address, where the `EDEP_ARBITRARY_NOT_SAME_ADDRESS` same-address containment is also unenforced). This is precisely the "Compatibility, upgrade-policy, or allowed-dependency bypass that places forbidden bytecode on chain" impact class called out in the task's publish-impact gate — mismatched declared vs. enforced dependency policy places code on chain that violates the package's own claimed upgrade guarantee.

### Likelihood Explanation
High: this is a simple metadata-construction issue reachable by any permissionless publisher through the standard `aptos move publish` / `deploy-object` flow — no special privileges are required, and it requires no race condition, only crafting `PackageMetadata.deps` and `upgrade_policy` fields that are inconsistent with the true on-chain policies of the referenced packages.

### Recommendation
Call `check_dependencies` (or an equivalent policy-strength/arbitrary-locality check) from `publish_package` for every publish/upgrade, not only from `freeze_code_object`. If the intent was to defer this validation to freeze time only, that should be reflected by removing the `EDEP_WEAKER_POLICY`/spec-requirement-5 language claiming the invariant is enforced generally (currently the doc, spec, and comments all state it as a general, always-enforced guarantee).

### Proof of Concept
1. Publish `PackageB` at address `0xB` with `upgrade_policy = compatible`.
2. Publish `PackageA` at address `0xA` with `upgrade_policy = immutable` and `deps = [{account: 0xB, package_name: "PackageB"}]`, where `PackageA`'s modules genuinely reference `PackageB`'s modules (so the native `allowed_deps`/bytecode check passes).
3. This publish succeeds today because `publish_package` never calls `check_dependencies`, so the `EDEP_WEAKER_POLICY` assertion (`dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy`) is never evaluated.
4. Later, upgrade `PackageB` (allowed, since it is `compatible`) to change its behavior/bytecode arbitrarily within compatibility rules (or, if `PackageB` were `arbitrary`, with no compatibility constraints at all).
5. `PackageA`, published/labeled `immutable`, has now transitively changed behavior — contradicting its declared, audited-as-enforced invariant.

Test coverage in the repo (`code_publishing_faked_dependency` in `aptos-move/e2e-move-tests/src/tests/code_publishing.rs`) only exercises the bytecode-vs-metadata dependency-hiding case (`CODE_DEPENDENCY_CHECK` feature flag / `EPACKAGE_DEP_MISSING`/native `CONSTRAINT_NOT_SATISFIED`), not the policy-strength (`EDEP_WEAKER_POLICY`) case, which is consistent with there being no test that publishing (as opposed to freezing) enforces `check_dependencies`. [10](#0-9) 

**Note on confidence/limitations:** I could not view `code.move` lines 150-180 (truncated by the index) which contain the beginning of `publish_package`; based on the visible continuation at line 181 onward and the spec file's `aborts_if` clauses (which only mention the `upgrade_policy <= arbitrary` check, not dependency-policy checks), I am confident `check_dependencies` is not called there, but a full read of that function body would be needed to rule out an alternate call path with absolute certainty.

    fun check_dependencies(publish_address: address, pack: &PackageMetadata): vector<AllowedDep>
    acquires PackageRegistry {
        let allowed_module_deps = vector::empty();
        let deps = &pack.deps;
        deps.for_each_ref(|dep| {
            let dep: &PackageDep = dep;
            assert!(exists<PackageRegistry>(dep.account), error::not_found(EPACKAGE_DEP_MISSING));
            if (is_policy_exempted_address(dep.account)) {
                // Allow all modules from this address, by using "" as a wildcard in the AllowedDep
                let account: address = dep.account;
                let module_name = string::utf8(b"");
                vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
            } else {
                let registry = borrow_global<PackageRegistry>(dep.account);
                let found = vector::any(&registry.packages, |dep_pack| {
                    let dep_pack: &PackageMetadata = dep_pack;
                    if (dep_pack.name == dep.package_name) {
                        // Check policy
                        assert!(
                            dep_pack.upgrade_policy.policy >= pack.upgrade_policy.policy,
                            error::invalid_argument(EDEP_WEAKER_POLICY)
                        );
                        if (dep_pack.upgrade_policy == upgrade_policy_arbitrary()) {
                            assert!(
                                dep.account == publish_address,
                                error::invalid_argument(EDEP_ARBITRARY_NOT_SAME_ADDRESS)
                            )
                        };
                        // Add allowed deps
                        let account = dep.account;
                        let k = 0;
                        let r = vector::length(&dep_pack.modules);
                        while (k < r) {
                            let module_name = vector::borrow(&dep_pack.modules, k).name;
                            vector::push_back(&mut allowed_module_deps, AllowedDep { account, module_name });
                            k += 1;
                        };
                        true
                    } else {
                        false
                    }
                });
                assert!(found, error::not_found(EPACKAGE_DEP_MISSING));
            };
        });
        allowed_module_deps
    }

fn code_publishing_faked_dependency(enabled: Vec<FeatureFlag>, disabled: Vec<FeatureFlag>) {
    let mut h = MoveHarness::new_with_features(enabled.clone(), disabled);
    let acc1 = h.new_account_at(AccountAddress::from_hex_literal("0xcafe").unwrap());
    let acc2 = h.new_account_at(AccountAddress::from_hex_literal("0xdeaf").unwrap());

    let mut pack1 = PackageBuilder::new("Package1").with_policy(UpgradePolicy::compat());
    pack1.add_source("m", "module 0xcafe::m { public fun f() {} }");
    let pack1_dir = pack1.write_to_temp().unwrap();
    assert_success!(h.publish_package(&acc1, pack1_dir.path()));

    // pack2 has a higher policy and should not be able to depend on pack1
    let mut pack2 = PackageBuilder::new("Package2").with_policy(UpgradePolicy::immutable());
    pack2.add_local_dep("Package1", &pack1_dir.path().to_string_lossy());
    pack2.add_source(
        "m",
        "module 0xdeaf::m { use 0xcafe::m; public fun f() { m::f() } }",
    );
    let pack2_dir = pack2.write_to_temp().unwrap();
    let result = h.publish_package_with_patcher(&acc2, pack2_dir.path(), |metadata| {
        // Hide the dependency from the lower policy package from the metadata. We detect this
        // this via checking the actual bytecode module dependencies.
        metadata.deps.clear()
    });
    if !enabled.contains(&FeatureFlag::CODE_DEPENDENCY_CHECK) {
        // In the previous version we were not able to detect this problem
        assert_success!(result)
    } else {
        assert_vm_status!(result, StatusCode::CONSTRAINT_NOT_SATISFIED)
    }
}
