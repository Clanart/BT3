### Title
Missing zero-value validation on `kip71.gastarget` governance parameter causes division-by-zero panic in base fee calculation - (File: params/kip71_config.go)

### Summary
The reported bug class ("Lack of input validation" on governance-controlled numeric parameters that are later used in unchecked arithmetic) has a direct analog in Kaia's governance parameter system. The `Kip71GasTarget` parameter (`kip71.gastarget`) is validated with a no-op `FormatChecker` that accepts any `uint64` value, including `0`. This value is later used as a divisor in `KIP71Config.NextMagmaBlockBaseFee`, which is invoked by every full node during block header verification and block/tx-pool base-fee computation. A ratified vote setting `gastarget` to `0` causes a division-by-zero panic across the entire network.

### Finding Description
In `kaiax/gov/param.go`, most numeric governance parameters that must never be zero are protected by explicit format checkers, e.g. `Kip71BaseFeeDenominator` explicitly rejects zero: [1](#0-0) 

However, `Kip71GasTarget` uses `noopFormatChecker`, which always returns `true` regardless of the value: [2](#0-1) [3](#0-2) 

This value flows unchecked into `NextMagmaBlockBaseFee` in `params/kip71_config.go`, where `gasTarget` is used as a divisor without a zero-check (unlike `BaseFeeDenominator`, which does have an explicit `== 0` fallback a few lines above): [4](#0-3) 

Specifically, when `parentGasUsed != gasTarget` (the overwhelmingly common case once `gasTarget == 0`), the code computes `x.Div(x, new(big.Int).SetUint64(gasTarget))`, which panics on `big.Int` division by zero.

This governance vote is validated for format only (`NewVoteData`/`FormatChecker`) and by `checkConsistency`, which does not check `Kip71GasTarget` at all — it falls into the catch-all branch that accepts the vote without value constraints: [5](#0-4) 

Once ratified, this parameter becomes part of the effective `ParamSet`/`KIP71Config` and is consumed on every node in the base-fee calculation path, which is called from block validation, the tx pool, block building (miner/worker), and gas price oracle: [6](#0-5) 

/ referenced also in `blockchain/block_validator.go` (`VerifyMagmaHeader`), `work/worker.go`, `node/cn/gasprice/gasprice.go`, and `node/cn/gasprice/feehistory.go`.

### Impact Explanation
Once a `kip71.gastarget = 0` vote is ratified via header governance (in `single` mode, cast by the governing node; in `none` mode, by any GC member), every full node in the network that processes the next Magma-enabled block will call `NextMagmaBlockBaseFee` with `gasTarget = 0`. As soon as `parentGasUsed != 0`, this triggers a Go runtime panic (`division by zero`) in a core consensus/state-transition code path (block header verification, tx pool reset, and block building). Because this function is called unconditionally by every node processing every block after the parameter takes effect, this results in a **network-wide chain halt** — all conforming nodes crash or fail to build/verify blocks, which is a severe availability/consensus-liveness impact analogous to "acceptance of an invalid transaction or block" / state divergence in the report's accepted-impact categories.

### Likelihood Explanation
The precondition is a ratified governance vote setting `kip71.gastarget` to `0`. This requires either a compromised/malicious governing node (in `single` mode, the standard Kaia governance mode) or an operator/validator error, similar to how the original Audius report's `setVotingPeriod`/`addServiceType` issues also required a call from a governance-privileged actor. Because governance parameter validation is explicitly a reachable, in-scope attack surface per the assessment rules, and because none of the existing validation layers (`FormatChecker`, `checkConsistency`) reject zero for this specific parameter, a single vote transaction is sufficient to trigger the fault deterministically at the next epoch boundary.

### Recommendation
Add an explicit non-zero `FormatChecker` for `gov.Kip71GasTarget` (mirroring `Kip71BaseFeeDenominator`'s check), e.g.:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, as defense-in-depth, add a zero-guard for `kc.GasTarget` in `NextMagmaBlockBaseFee` (analogous to the existing `BaseFeeDenominator == 0` fallback) so that a corrupted or legacy configuration cannot crash node processing.

### Proof of Concept
1. Governing node (or governance quorum in `none` mode) casts a header-governance vote: `governance_vote("kip71.gastarget", 0)`. `NewVoteData` accepts it because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`. [2](#0-1) 
2. `VerifyVote`/`checkConsistency` place no additional constraint on this parameter, so the vote is accepted into the block header and ratified at the next epoch boundary. [7](#0-6) 
3. Once ratified and effective, `GetParamSet(N).ToKip71Config()` yields `GasTarget = 0`.
4. On the next Magma block where `parentHeaderGasUsed != 0` (essentially any active block), `NextMagmaBlockBaseFee` is invoked from `blockchain/block_validator.go` (header verification), `blockchain/tx_pool.go` (pool reset), and `work/worker.go` (block assembly), executing:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // gasTarget == 0
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // division by zero -> panic
``` [8](#0-7) 
5. This panics on every node executing this code path, crashing block validation/production network-wide.
