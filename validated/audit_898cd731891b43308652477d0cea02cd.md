## Title
Governance-settable `GasTarget = 0` causes divide-by-zero panic in KIP-71 base fee calculation - (File: `params/kip71_config.go`)

## Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance parameter `GasTarget` when computing the base fee delta for the next block. The governance parameter `Kip71GasTarget` is registered with a `noopFormatChecker`, meaning any `uint64` value — including `0` — passes format validation and can be voted into the chain config. Once `GasTarget == 0` and any block uses gas above zero, `NextMagmaBlockBaseFee` performs `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics in Go's `math/big` (`division by zero`). This mirrors the reported bug class: a parameter that can reach zero is used unconditionally as a divisor in a price-formula code path without a dedicated zero-check branch.

## Finding Description
The parameter registration for `Kip71GasTarget` explicitly uses a no-op format checker, unlike the sibling parameter `Kip71BaseFeeDenominator` which does check `v != 0`: [1](#0-0) 

Governance votes are validated with exactly this per-parameter `FormatChecker` and nothing more: [2](#0-1) 

So a validator vote setting `governance.kip71.gastarget = 0` is accepted as a valid vote and, once it reaches the required consensus/epoch threshold, becomes part of the active `ChainConfig.Governance.KIP71.GasTarget`.

In `NextMagmaBlockBaseFee`, `gasTarget := kc.GasTarget` is used as-is. The function only special-cases `parentGasUsed == gasTarget` (which, with `gasTarget == 0`, only holds when a block uses exactly 0 gas). For any other block (i.e., any block with `GasUsed > 0`), execution falls into the "gas used above target" branch and divides by `gasTarget`: [3](#0-2) 

and symmetrically in the "gas used below target" branch: [4](#0-3) 

`big.Int.Div`/`Quo` panics on a zero divisor (there is no error return in this API), so this is an unrecoverable panic, not a graceful revert.

This function is invoked from block header verification (`VerifyMagmaHeader`) and from `feehistory.go`'s `processBlock` (used by `eth_feeHistory`/gas price oracle, reachable via public RPC): [5](#0-4) [6](#0-5) 

Both are triggered by ordinary block processing / public RPC calls once the malformed `GasTarget = 0` config becomes active — no special privilege beyond being able to submit a governance vote (a normal validator action) is required to introduce the value, and no privilege at all is required to trigger the panic afterward (any block with nonzero gas usage, or any `eth_feeHistory` RPC call over such a block, does it).

## Impact Explanation
Once `GasTarget` reaches `0` via governance, every Kaia node computing the next base fee for a non-empty block (which is virtually every block) will panic inside `NextMagmaBlockBaseFee`. This is invoked:
- During header verification during block processing/import (`VerifyMagmaHeader`) on all full/consensus nodes.
- During gas price oracle / `eth_feeHistory` handling on RPC-serving nodes.

A panic in the block-verification hot path halts node processing and, depending on how the panic is recovered (or not) at higher layers, can crash the node process or otherwise stop chain progress network-wide, since every honest node runs identical logic against the same governance config and the same blocks. This is a chain-halting Denial-of-Service condition triggered purely by an on-chain governance parameter combined with normal block production — a state-transition/consensus availability impact, not merely a local resource issue.

## Likelihood Explanation
Likelihood depends on a governance vote for `governance.kip71.gastarget` reaching `0` and being finalized (governance votes require validator consensus per Kaia's governance rules), so this is not directly triggerable by an arbitrary unprivileged sender. However, per the allowed analog surface ("governance parameters" is explicitly listed as reachable), and given that the format checker for this specific parameter is a no-op (unlike its sibling `BaseFeeDenominator`, which is checked), this is a clear, concrete gap: the validation the system already applies to prevent zero-divisors for `BaseFeeDenominator` was not applied to `GasTarget`, despite `GasTarget` being used as a divisor in the same formula. A single malicious or careless governance proposal (needs validator support, as with all governance changes) is sufficient to introduce the fault; from that point, any subsequent block deterministically triggers the panic on every node with no further attacker action required.

## Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and any other KIP-71 parameter used as a divisor) that rejects `0`, consistent with the existing check on `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, defensively guard `NextMagmaBlockBaseFee` against `gasTarget == 0` (e.g., treat it like the existing `BaseFeeDenominator == 0` fallback) so that a corrupted or legacy config value cannot panic the node.

## Proof of Concept
1. Submit/accumulate governance votes to set `governance.kip71.gastarget = 0` (passes `NewVoteData` because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`).
2. Once the vote is finalized and applied to `ChainConfig.Governance.KIP71.GasTarget`, produce or import any subsequent block with `GasUsed > 0` (essentially any normal block).
3. `NextMagmaBlockBaseFee` computes `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)`, which is `> 0` and thus `!= gasTarget (0)`, executing the branch `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, causing a panic that propagates through `VerifyMagmaHeader` during header verification, or through `eth_feeHistory` request handling.

			logger.Error("Invalid vote name", "name", name)

		return nil
	}

		voter: voter,
		name:  gov.ParamName(name),
		value: cv,
	}
