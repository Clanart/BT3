### Title
`distribution` precompile's `rewards()` view accepts ETH value with no non-payable check, permanently stranding funds sent to the precompile address - (File: precompiles/distribution/distribution.go)

### Summary
The `distribution` precompile at `0x...1007` dispatches its `rewards` method without validating that `msg.value == 0`, unlike essentially every other view/query method on the same precompile.

### Finding Description
In `Execute`, most read-only query methods (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) are dispatched by passing `value` into the handler, and those handlers call `p.validateInput(value, args, N)` / `pcommon.ValidateNonPayable(value)` to reject non-zero `msg.value`, as seen for example in `delegationRewards` at [1](#0-0) . In contrast, `RewardsMethod` is dispatched with `return p.rewards(ctx, method, args)` — `value` is not even passed to the handler: [2](#0-1) 
And the `rewards` handler itself never calls `ValidateNonPayable` or inspects `value` at all: [3](#0-2) 

This same missing check is present identically across the legacy versioned copies of the precompile (`v580`, `v605`, `v606`, `v610`, `v614`, `v620`, `v630`, `v640`, `v65`, `v66`, `v67`), e.g. [4](#0-3)  and [5](#0-4) .

The repository's own integration-test documentation confirms this is a known, intentional-but-unfixed quirk: "distribution.rewards accepts value (no non-payable check)" and "a value-bearing call would succeed and strand the funds" [6](#0-5) , and the spec file explicitly documents the same: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)" [7](#0-6) .

Because `bank`, `staking`, `gov`, and `wasmd` are the only precompiles registered as "payable" in the EVM keeper's suppression list (used to hide transfer events to/from precompile addresses), [8](#0-7)  the distribution precompile address is not expected to hold or move ETH/usei balance at all — there is no withdraw/sweep path for any usei that lands on it. Any `wei`/`usei` value attached to a `rewards()` call is debited from the caller by the EVM's normal value-transfer mechanics and credited to the precompile's account balance in the StateDB, but no code path in the distribution module ever reads or moves that balance back out.

### Impact Explanation
Any unprivileged EVM caller (contract or EOA) that calls `rewards(address)` on the distribution precompile with non-zero `msg.value` will have that ETH/usei permanently locked in the precompile's balance with no code path to retrieve it — a genuine, reachable "permanent freezing of funds" bug matching the accepted impact class. This is distinct from, but analogous in root cause to, the reported `PeripheryPayments.refundETH()` issue in that it is an unprotected/unchecked payable surface reachable by any caller; here the vulnerability is the inverse direction (funds get stuck instead of being drained) but the loss of user funds is equally real and irreversible.

### Likelihood Explanation
This is trivially and cheaply reachable: any address that has completed EVM address association can call `rewards()` with any positive `value` (a single transaction, no special privileges, no multi-step setup). It's plausible for this to happen accidentally too (e.g., a frontend or contract that reuses payable-call boilerplate for all precompile view calls), increasing real-world likelihood beyond pure malicious intent.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` (or route `value` into `rewards` and call `p.validateInput(value, args, 1)`, consistent with the other view methods) at the top of the `rewards` handler in `precompiles/distribution/distribution.go`, and backport the same fix to all legacy versioned copies (`legacy/v580` through `legacy/v67`) that expose the same `RewardsMethod` dispatch.

### Proof of Concept
1. Associate an EVM address with a Sei account (standard `associateViaTx`, as done in the existing test fixture at [9](#0-8) ).
2. Call the `distribution` precompile at `0x0000000000000000000000000000000000001007` with `rewards(delegatorAddress)` and set `{ value: ethers.parseEther("1") }` (any positive value).
3. The call succeeds and returns valid reward data (since the handler ignores `value`), but the EVM has already deducted 1 ETH-equivalent from the caller and credited it to the precompile's account balance.
4. Query the precompile address's EVM balance — it now holds the transferred value.
5. There is no `rewards`/`distribution` precompile method, nor any other reachable code path, that transfers balance out of the precompile's own address, so the funds are permanently unrecoverable.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

	case WithdrawMultipleDelegationRewardsMethod:
		if readOnly {
			return nil, 0, errors.New("cannot call distr precompile from staticcall")

			return nil, 0, err
