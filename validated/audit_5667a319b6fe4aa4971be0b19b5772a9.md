### Title
Missing identity group-key validation in `ThresholdKeys::read` allows a guaranteed panic during BIP-340 signing - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes attacker-controlled `t`, `n`, interpolation coefficients, `secret_share`, and all `verification_shares` without checking that the resulting group key is non-identity. A crafted serialization whose first `t` verification shares (or constant-interpolation coefficients) sum to the point at infinity yields a `ThresholdKeys`/`ThresholdView` whose `group_key()` is the identity. When these keys are used with the Bitcoin `Schnorr` algorithm, `Hram::hram` calls `x(&group_key)` / `x(&R)`, which `expect`s the point to be non-infinity and panics — a deterministic, repeatable crash reachable purely from bytes fed to `ThresholdKeys::read` plus a normal `sign` call.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an `Interpolation` (for `Interpolation::Constant`, `n` attacker-chosen `C::read_F` coefficients), the `secret_share`, and `n` verification shares via `read_G`, then calls `ThresholdKeys::new` and returns the result without rejecting a group key equal to the identity [1](#0-0) . With constant interpolation the coefficients are directly serialized, so an attacker can make `sum(coefficients) == 0` (or pick verification shares summing to identity), while still producing a consistent `secret_share` for participant `i`, so any consistency checks in `ThresholdKeys::new` pass.

On the signing side, the Bitcoin `Schnorr` algorithm's challenge function hashes `x(R) || x(A) || m`, where `A` is the group key; `x` calls `key.to_encoded_point(true)` and `expect("point at infinity")` on the x-coordinate [2](#0-1) . `hram` is invoked from `Schnorr::sign_share` during `AlgorithmSignMachine::sign` [3](#0-2)  and is explicitly documented as panicking when `R` or `A` is the point at infinity [4](#0-3) .

Note that `p2tr_script_buf`/`SignableTransaction::multisig` does not guard this path — it merely returns `None` for unusable keys [5](#0-4) , and `AlgorithmMachine::new` accepts the `ThresholdKeys` directly [6](#0-5) .

### Impact Explanation
Analogous to CVE-2023-21962 (repeated, crash-inducing input ⇒ complete availability loss), feeding the crafted serialized `ThresholdKeys` into any consumer that runs the Secp256k1 `Schnorr` signing algorithm causes an unconditional `expect` panic in `x()` the first time a signature share is produced. The panic aborts the signing operation (and, absent isolation, the process), and is fully repeatable — every signing attempt with the crafted key material crashes, matching the "hang or frequently repeatable crash (complete DOS)" bug class.

### Likelihood Explanation
The trigger requires only untrusted bytes processed by `ThresholdKeys::read` — an explicitly supported deserialization path over fully attacker-controlled fields — followed by an ordinary `sign` invocation. The malicious key set can be made internally consistent (valid `t`/`n`/`i`, consistent secret share and shares), so no validation short of an explicit identity check on the computed group key would reject it, and none exists in `ThresholdKeys::read`. The panic is deterministic once the crafted keys are used, requiring no races or probabilistic conditions.

### Recommendation
Reject identity group keys during `ThresholdKeys::new`/`ThresholdKeys::read` (check `interpolation.group_key()` / `sum(verification_shares[1..=t]).is_identity()` and return an `io::Error`). Defense-in-depth: make `x()`/`x_only()`/`Hram::hram` return `io::Error`/`FrostError` (or `Option`) instead of panicking on infinity inputs, since both `R` and `A` are influenced by deserialized data.

### Proof of Concept
1. Construct a `ThresholdParams` with `t = 2, n = 2, i = 1`.
2. Build serialized `ThresholdKeys<Secp256k1>` bytes: valid `C::ID`, `t`, `n`, `i`, interpolation tag `0` (Constant) with coefficients `[c0, c1]` where `c1 = -c0` (so the group key `c0·G + c1·G` is the identity), a `secret_share` consistent with that polynomial at `i`, and `n` verification shares (e.g., `c0·G` and `-c0·G`-consistent per-participant shares).
3. `ThresholdKeys::<Secp256k1>::read(&mut bytes)` succeeds.
4. `AlgorithmMachine::new(Schnorr::new(), keys)` → `preprocess(rng)` → `sign(preprocesses, msg)`: `sign_share` calls `Hram::hram(&R, &group_key, msg)`, `group_key` is the identity, `x()` hits `expect("point at infinity")` at `crypto.rs:15` and panics, crashing the signing session every time.
