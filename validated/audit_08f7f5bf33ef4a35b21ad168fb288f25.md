### Title
Withdrawer can self-spend their own withdrawal UTXO with an arbitrary operator pubkey in OP_RETURN, forging a "payout" that triggers a real operator's automated kickoff/reimbursement for BTC it never fronted - ([File: core/src/verifier.rs], [File: core/src/database/verifier.rs])

### Summary
`Verifier::update_finalized_payouts` treats *any* transaction that spends a registered withdrawal UTXO as the operator's payout transaction, extracting the operator identity purely from an unauthenticated OP_RETURN push and writing it into `withdrawals.payout_payer_operator_xonly_pk`. Since the withdrawal UTXO's spending key belongs to the withdrawer (not the bridge), the withdrawer can spend it themselves with a self-authored transaction that never pays the intended recipient, embedding a target operator's real x-only pubkey in the OP_RETURN. The operator's `PayoutCheckerTask` blindly trusts this DB row and starts the reimbursement kickoff for a payout it never made.

### Finding Description
Broken binding: the code assumes `withdrawals.payout_payer_operator_xonly_pk == <operator that actually broadcast a correctly-formed create_payout_txhandler tx paying the withdrawer>`. In reality the binding only enforces `payout_payer_operator_xonly_pk == <OP_RETURN bytes of whichever tx first spends withdrawal_utxo_txid:vout>`.

Path:
1. Attacker (as withdrawer) calls Citrea `withdraw`, choosing a withdrawal UTXO they control the key for, exactly as `Operator::withdraw` expects (`core/src/operator.rs:560-627` checks only that `withdrawal_utxo == input_utxo.outpoint`, never that a bridge-authorized entity holds the key).
2. Before any operator funds a real payout, attacker crafts and broadcasts their own key-spend transaction consuming that UTXO, paying an arbitrary destination, with a second output `OP_RETURN <victim operator's real xonly pubkey>` (mirrors `op_return_txout` format produced by `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`).
3. Once finalized, `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) calls `Database::get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`), whose SQL join matches purely on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`, i.e. whatever transaction actually spent the UTXO — attacker's, not an operator's.
4. `update_finalized_payouts` then parses the OP_RETURN of that transaction (`core/src/verifier.rs:2312-2342`) and calls `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`), storing the attacker-chosen `operator_xonly_pk`, the attacker's `payout_txid`, and the block hash — with zero validation that this operator actually broadcast the tx or that it pays the withdrawer's committed output/amount.
5. The victim operator's background `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) polls `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) filtered only by `payout_payer_operator_xonly_pk = $1` and `is_payout_handled = FALSE`. It finds the poisoned row and unconditionally calls `Operator::handle_finalized_payout` → obtains a kickoff connector → proceeds through the normal kickoff/reimburse tx graph.
6. On the verifier side, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) only re-checks internal DB consistency: that `operator_xonly_pk` from `get_payout_info_from_move_txid` matches `kickoff_data.operator_xonly_pk`, and that the committed truncated blockhash in the kickoff witness matches `payout_tx_blockhash` — both of which are already the attacker-poisoned values, so this check passes.
7. Neither `verify_storage_proofs` nor the bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs:116-236`) ever validates that the payout transaction's *output* actually pays the withdrawer's committed destination/amount — they only check that the input at `payout_input_index` spends the correct withdrawal outpoint and that an OP_RETURN xonly pubkey exists. Consequently, the disprove/challenge path also cannot catch this forgery, since it is only designed to detect a mismatched *operator* claim, not an unpaid withdrawal.

Root cause: the system conflates "a transaction spending the withdrawal UTXO with an OP_RETURN naming operator X" with "operator X funded this withdrawal," but the withdrawal UTXO is user-custodied, not bridge-custodied, so any third party (including the withdrawer) can produce such a transaction unilaterally.

### Impact Explanation
This lets an unprivileged attacker (the withdrawer) forge a false "operator fronted this payout" record for any targeted operator, causing that operator's own automation to kick off and eventually be reimbursed from the deposit's move-to-vault UTXO for a payout that was never actually paid to the withdrawer. This is BTC leaving a move-to-vault UTXO without a matching fronted withdrawal — Critical impact. It is repeatable per deposit/withdrawal pairing and can target any operator whose xonly pubkey is public (all operator pubkeys are known/public in the protocol). The blast radius covers every withdrawal registered before an operator has actually funded it, across all deposits and operators.

### Likelihood Explanation
Preconditions are trivial and match the stated attacker capabilities exactly: attacker must be the legitimate withdrawer of a Citrea withdrawal (which they always are for their own withdrawal) and must broadcast one Bitcoin transaction spending their own UTXO before any operator fronts payout — a race the attacker fully controls since they choose the timing. Cost is a single small on-chain transaction fee. No verifier collusion, no key compromise, and no majority hashrate are required. This is fully reproducible against the current logic in `update_finalized_payouts`, `get_payout_txs_for_withdrawal_utxos`, and `PayoutCheckerTask`.

### Recommendation
Do not treat "any transaction spending the withdrawal UTXO" as proof of operator payment. The bridge circuit / verifier's `update_finalized_payouts` and the on-chain disprove logic must additionally verify that the spending transaction's non-OP_RETURN output(s) actually pay the exact `output_script_pubkey`/`output_amount` committed for that withdrawal (as authorized by the user's off-chain signature and/or committed on Citrea), not merely that the correct input outpoint was spent and an OP_RETURN with a valid-looking xonly pubkey exists. Additionally, `PayoutCheckerTask` (and `handle_finalized_payout`) should cross-check against the operator's own locally signed/sent payout transaction (e.g., `tx_sender` records) before treating a DB-observed payout as self-funded, rather than trusting on-chain OP_RETURN content alone.

### Proof of Concept
```rust
// core/src/database/verifier.rs (add to existing #[cfg(test)] mod tests)
#[tokio::test]
async fn attacker_can_forge_payout_payer_via_self_spend() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();

    // Attacker's own withdrawal registration
    let move_txid = Txid::from_byte_array([0xAA; 32]);
    let index = 7;
    let victim_operator_pk = generate_random_xonly_pk(); // targeted operator, not attacker

    // Attacker-controlled withdrawal UTXO
    let withdrawal_utxo = bitcoin::OutPoint {
        txid: Txid::from_byte_array([0xBB; 32]),
        vout: 0,
    };

    let mut dbtx = db.begin_transaction().await.unwrap();
    let block_id = db
        .insert_block_info(Some(&mut dbtx), &BlockHash::all_zeros(), &BlockHash::all_zeros(), 0)
        .await.unwrap();

    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), index, &move_txid)
        .await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), index, withdrawal_utxo, block_id)
        .await.unwrap();

    // Attacker's SELF-authored spend of their own UTXO (not any operator's payout tx),
    // identified only by attacker_spend_txid, spending withdrawal_utxo.
    let attacker_spend_txid = Txid::from_byte_array([0xCC; 32]);
    db.insert_txid_to_block(&mut dbtx, block_id, &attacker_spend_txid).await.unwrap();
    db.insert_spent_utxo(
        &mut dbtx, block_id, &attacker_spend_txid,
        &withdrawal_utxo.txid, withdrawal_utxo.vout.into(),
    ).await.unwrap();

    // Simulate update_finalized_payouts' OP_RETURN parse: attacker embedded victim operator's pk.
    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx),
        vec![(index, attacker_spend_txid, Some(victim_operator_pk), BlockHash::all_zeros())],
    ).await.unwrap();

    // ASSERTION 1: the DB now believes the victim operator "paid" this withdrawal,
    // even though attacker_spend_txid was never produced by that operator and never
    // paid the withdrawer's intended output — this is the broken binding.
    let unhandled = db
        .get_first_unhandled_payout_by_operator_xonly_pk(Some(&mut dbtx), victim_operator_pk)
        .await.unwrap();
    assert!(unhandled.is_some(), "victim operator's PayoutCheckerTask would pick up a payout it never made");
    let (idx, returned_move_txid, _blockhash) = unhandled.unwrap();
    assert_eq!(idx, index);
    assert_eq!(returned_move_txid, move_txid);

    // ASSERTION 2 (equality check before/after): payout_payer_operator_xonly_pk equals
    // victim_operator_pk despite victim operator never broadcasting attacker_spend_txid.
    let payout_info = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid).await.unwrap().unwrap();
    assert_eq!(payout_info.0, Some(victim_operator_pk));
    assert_eq!(payout_info.2, attacker_spend_txid); // proof the "payout" is the attacker's tx, not an operator tx
}
```
This proves, purely from DB/business logic already present (no mainnet, no live Citrea), that `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-111`) will treat `attacker_spend_txid` as the victim operator's fronted payout and proceed to `handle_finalized_payout` → kickoff → reimbursement, since `is_kickoff_malicious` only re-validates against these same poisoned DB fields.
