### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo`/`MofN.from_memo` parsing enables wallet-crash denial of service - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
The CVE describes `dissect_llrp_parameters` recursing without a depth limit on attacker-supplied packet data, letting a remote peer exhaust memory/stack and crash the dissector. The same bug class — unbounded recursion driven entirely by attacker-controlled nested data — exists in the CHIP-0043 custody-memo parser in `chia/wallet/puzzles/custody/custody_architecture.py`.

### Finding Description
`PuzzleWithRestrictions.from_memo()` reconstructs an unknown custody puzzle tree from a `Program` memo attached to a coin: [1](#0-0) . When the memo indicates an `MofN` node (`further_branching`), it calls `MofNHint.from_program()` to get `member_memos`, then recurses into `PuzzleWithRestrictions.from_memo(memo)` for **every** member, with no depth or size bound: [2](#0-1) . `MofNHint.from_program` itself just unpacks whatever the attacker put in the program: [3](#0-2) .

Because the recursion depth is controlled entirely by the shape of the memo `Program` (which is attacker-suppliable data attached to a coin, exactly like an LLRP parameter list controlled by a remote sender), a maliciously crafted memo with thousands of nested `MofN` levels will drive Python's call stack to `RecursionError`, or in pathological cases crash the interpreter, before any semantic validation of the puzzle occurs.

This mirrors the CVE-2016-2532 root cause precisely: a dissector/parser recurses on nested attacker structure with no depth cap, so a single crafted input causes denial of service in the parsing code path, before any cryptographic or consensus check is applied.

### Impact Explanation
A wallet or client that reconstructs a `PuzzleWithRestrictions` from an untrusted memo (e.g. a custody/DAO participant importing a peer-supplied custody spec, or any code path that calls `from_memo` on data taken from a coin's memo/hint) can be forced into unbounded Python recursion by a single crafted memo. This is a spend/wallet-action-triggered processing halt (RecursionError/crash) consistent with the "spend-triggered transaction-processing halt" impact category — a local availability failure of the wallet process handling custody data, not requiring any privileged position.

### Likelihood Explanation
Likelihood is limited by how directly `from_memo` is fed with untrusted, unbounded-depth CLVM data outside of test code — the search confirms `from_memo`/`PuzzleWithRestrictions` usage is presently concentrated in `chia/wallet/puzzles/custody/custody_architecture.py`, `chia/pools/plotnft_drivers.py`, and test files under `chia/_tests/clvm/`. I could not fully confirm within the indexed context whether a production RPC or coin-state-processing path (e.g. wallet sync ingesting coin memos automatically) calls `from_memo` on attacker-supplied data without prior size/depth vetting, versus it only being invoked when a user explicitly imports/loads a custody spec they were given out-of-band. This uncertainty affects likelihood but not the root-cause validity of the missing recursion guard itself.

### Recommendation
Add an explicit recursion-depth (or iterative-stack-based) bound in `PuzzleWithRestrictions.from_memo` / `MofN.from_memo` reconstruction, similar to the depth guard already enforced elsewhere in the codebase for untrusted nested tree data (e.g. Data Layer's `RecursionDepthExceededError` check surfaced in `chia/_tests/core/data_layer/test_data_store.py`). Reject memos whose `MofN` nesting exceeds a sane maximum before recursing, and/or rewrite the reconstruction to use an explicit work-stack instead of Python call recursion.

### Proof of Concept
Construct a `Program` memo shaped as `("CHIP-0043" [nonce, [], 1, [1, [<memo>, <memo>, ..., <memo>]]])` where the `MofN` hint's `member_memos` entries are themselves deeply nested `MofN` memos (depth N ≈ tens of thousands). Calling `PuzzleWithRestrictions.from_memo(crafted_memo)` recurses once per nesting level via [4](#0-3)  and raises `RecursionError`, terminating whatever process invoked it (analogous to the LLRP dissector's uncontrolled recursion causing Wireshark to crash on a crafted packet).

    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
