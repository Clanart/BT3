### Title
`ReceivedOutput::read` accepts an attacker-controlled spend-key offset without checking it against the output's script - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The OIDC bug class is "an unvalidated attacker-supplied parameter silently redirects where a sensitive value flows" (callback URL → token exfiltration). The Serai analog lives in the Bitcoin wallet: `ReceivedOutput` couples a spendable `TxOut`/`OutPoint` with the scalar `offset` that determines *which key* can spend it. `ReceivedOutput::read` deserializes all three fields from untrusted bytes and performs zero consistency checking between the `offset` and the `output.script_pubkey`, even though the offset is what redirects the derived signing key.

### Finding Description
`Scanner::register_offset` correctly maps `offset → p2tr_script_buf(key + offset·G)` and `scan_transaction` correctly pairs a matched output with the registered offset [1](#0-0) [2](#0-1) . However, the deserialization path bypasses that invariant entirely:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;   // arbitrary scalar, unchecked
  ...
  output = TxOut::consensus_decode(&mut buf_r)...
  outpoint = OutPoint::consensus_decode(&mut buf_r)...
  Ok(ReceivedOutput { offset, output, outpoint })
}
``` [3](#0-2) 

Like the Audiobookshelf callback cookie, the offset is stored/treated as authoritative metadata and later consumed to derive the spending key (`keys.offset(offset)` → `tweak_keys`), yet nothing re-derives `p2tr_script_buf(self.key + G·offset)` and compares it to `output.script_pubkey`. The only documented warning (`register_offset`: "offsets must be securely generated") covers *registration*, not the `read` path which accepts arbitrary bytes [4](#0-3) .

### Impact Explanation
An attacker who can feed crafted bytes to `ReceivedOutput::read` (the explicitly in-scope `read_*` surface) supplies an output legitimately owned by the multisig together with a bogus `offset`. The spend path then derives `key + offset·G` (+ TapTweak), producing a signature under a key that does not match the output's committed key. The transaction is unspendable/invalid — **funds reported received become not spendable** with that `ReceivedOutput`. Because the attacker's chosen offset has no known discrete log relationship to a key they control, they cannot steal the funds, but they can deterministically burn/DoS specific received outputs. This matches the report class: attacker-chosen redirection target, secret material (the signature/signing operation) directed to a destination the system never authorized.

### Likelihood Explanation
Reachability requires an unprivileged party to control the serialized `ReceivedOutput` bytes (e.g., a data-sync/gossip payload carrying scanner results between components). Where the scanner itself produced the bytes locally, there is no attack. The severity is bounded to Medium: no key-share or nonce recovery, no forged signature — the outcome is permanently unspendable-looking outputs (until the offset is corrected), analogous to funds-reported-received-but-not-spendable.

### Recommendation
On `read` (or before signing in the spend path), recompute the expected script: store `key` alongside or require the caller to pass the `Scanner`, then verify `p2tr_script_buf(scanner.key + GENERATOR·offset) == Some(output.script_pubkey)` and reject otherwise. Alternatively, store only the `outpoint`/`TxOut` in serialized form and re-derive the offset by re-scanning, removing the attacker-malleable key-derivation input entirely.

### Proof of Concept
1. Honest `Scanner::new(multisig_key)`; `register_offset(o)` returns `o` for `script = p2tr(key + o·G)`.
2. Attacker intercepts the serialized `ReceivedOutput` for a real deposit `tx:vout` and rewrites field 1 to `o' = random scalar` (passes `read_F` since any canonical scalar is accepted).
3. Processor loads it via `ReceivedOutput::read` → obtains `{offset: o', output, outpoint}`.
4. Spend code does `tweak_keys(keys.offset(o'))`, signs the sighash under `key + o'·G + tweak`; the script_pubkey commits to `key + o·G`, so the Bitcoin network rejects the tx. The deposit is recorded as received but every spend attempt with the corrupted record fails.

**Caveat:** I could not read `networks/bitcoin/src/wallet/send.rs` within the available iterations to confirm the exact `keys.offset(...)` consumption site, so the spend-path details are inferred from `tweak_keys`/`ThresholdKeys::offset` semantics rather than verified line-by-line.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
