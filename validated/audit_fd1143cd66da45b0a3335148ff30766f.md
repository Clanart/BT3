## Finding: Nested precompile calls corrupt `BalanceHandler` bracket bookkeeping, causing double-application of bank balance events to EVM StateDB

### Title
Balance desync between `x/bank` and EVM StateDB via nested precompile calls corrupting `BalanceHandler.prevEventsLen` bracket — (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The reported bug class (two `nonReentrant` guards nested on the same call causing inconsistent/broken guard semantics) maps onto Cosmos EVM's `BalanceHandler` bracket, which is the mechanism that keeps the EVM `StateDB` balances synchronized with `x/bank` after a precompile executes a native (Cosmos SDK) balance-changing action. This bracket is not reentrancy-safe: nested precompile invocations within a single EVM call each open independent `BeforeBalanceChange`/`AfterBalanceChange` windows over the *same* growing `ctx.EventManager()` event log, and the outer window is not aware of what the inner window already consumed.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())` and `AfterBalanceChange` replays `events[prevEventsLen:]` to apply `CoinSpent`/`CoinReceived`/fractional-balance events onto the `StateDB` via `AddBalance`/`SubBalance`: [1](#0-0) [2](#0-1) 

Each call to a stateful precompile (`RunNativeAction` → `runNativeAction`) opens a fresh window over the *shared* Cosmos SDK event log for the duration of the precompile call: [3](#0-2) 

Because `ctx.EventManager()` events accumulate globally and monotonically, if a precompile call (window A) triggers, during its native action, a nested call back into any precompile (window B) — e.g. via a contract's ERC20 `_beforeTokenTransfer`/`_beforeTokenTransfer` hook calling another precompile mid-transfer, or via `evmKeeper.CallEVMWithData` reentering EVM execution — window B will consume and apply events `[prevEventsLen_B:]` to the StateDB, then return. When window A resumes and eventually calls its own `AfterBalanceChange`, it replays `events[prevEventsLen_A:]`, which **still includes** all events already applied by window B, because slicing by index doesn't account for events "already consumed" — only for events emitted after A started. This causes the balance deltas from the inner precompile call to be applied a second time to the StateDB.

This exact defect is already demonstrated and named in the repository's own test suite, describing "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB": [4](#0-3) 

Production trigger paths exist for nested precompile-call scenarios: contracts that implement ERC20 hooks calling into another stateful precompile mid-transfer, as exercised by `ERC20RecursiveRevertingPrecompileCall._beforeTokenTransfer`, which invokes `distribution.DISTRIBUTION_CONTRACT.claimRewards` from inside a token transfer flow: [5](#0-4) 

and `StakingReverter`'s patterns of nested/try-catch precompile calls that specifically exercise state consistency "before and after" reverts within a single outer call: [6](#0-5) 

### Impact Explanation
If confirmed reachable through production stateful precompiles (staking/distribution/erc20/ics20/gov/slashing, all of which wire a `BalanceHandlerFactory`), double-application of `CoinReceived`/`CoinSpent` events onto the EVM `StateDB` would credit or debit an address's EVM-visible balance twice for a single real bank-module movement. This directly produces unauthorized duplication of spendable value in the EVM balance view without a corresponding backing movement in `x/bank`, i.e., unbacked EVM balance that can subsequently be spent/transferred out — a critical accounting-corruption / unauthorized-value-duplication impact per the allowed impact gate.

### Likelihood Explanation
Reachability requires an unprivileged user to deploy or interact with a contract that, from within a stateful precompile's native action, triggers a nested call into another (or the same) stateful precompile before the outer call's `AfterBalanceChange` executes. The repository's own test scaffolding (`ERC20RecursiveRevertingPrecompileCall`, `StakingReverter`, `DebugPrecompileCaller`, and the dedicated `BalanceHandlerTestSuite`) shows this nested-call pattern is a known, exercised code path, and the existence of the dedicated test that explicitly documents the bug ("demonstrates the balance handler bug") strongly suggests the underlying defect is present and tracked. I could not fully verify from the indexed code whether the currently-shipped production precompile wiring (`runNativeAction` creating a *new local* `BalanceHandler` per call in `precompiles/common/precompile.go`) fully eliminates the double-counting versus the older/`debug` precompile pattern that calls a persistently-stored `p.GetBalanceHandler()` — the `GetBalanceHandler()` accessor's definition and whether it returns a shared vs. per-call instance in the current production precompile struct was not found in the retrieved index. This is the key remaining uncertainty.

### Recommendation
- Make the balance-event replay window reentrancy-aware: instead of only tracking `prevEventsLen`, track a global "high-water mark" of events already applied to the StateDB (e.g., a monotonically-increasing "last processed event index" stored on the StateDB/journal rather than per-call locally), so nested/inner windows advance the shared cursor and outer windows only ever replay events strictly beyond what any nested call has already consumed.
- Alternatively, disallow/guard nested precompile-to-precompile reentrancy explicitly (a true, single, correctly-scoped reentrancy guard keyed off the StateDB/journal), consistent with the `MaxPrecompileCalls` depth counter already present in `AddPrecompileFn`, but extended to prevent overlapping `BeforeBalanceChange`/`AfterBalanceChange` windows rather than just capping call count.
- Add/extend the existing `balance_handler_test.go` and `BalanceHandlerTestSuite` assertions to explicitly assert StateDB balances equal bank-keeper balances after nested precompile calls across all production stateful precompiles (staking, distribution, erc20, gov, slashing, ics20), not just the debug precompile.

### Proof of Concept
Conceptual reproduction (already partially scaffolded in-repo):
1. Deploy an ERC20-precompile-integrated contract overriding `_beforeTokenTransfer` to call a second stateful precompile (e.g., distribution `claimRewards` or staking `delegate`) that itself performs a bank-balance-changing operation, mirroring `ERC20RecursiveRevertingPrecompileCall._beforeTokenTransfer`.
2. Trigger an ERC20 `transfer`/`transferFrom` precompile call on this contract so that, mid native-action, the nested precompile call opens/closes its own `BeforeBalanceChange`/`AfterBalanceChange` window while the outer transfer's window is still open.
3. Inspect StateDB balances vs. `x/bank` balances after the call (as done in `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile`, which already asserts specific unexpected event/debug counts resulting from this exact recursive-call pattern) to confirm double-counted balance deltas.
