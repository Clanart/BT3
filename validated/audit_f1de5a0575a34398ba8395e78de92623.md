### Title
Bitcoin vault transactions hardcode relay-policy constants with no mechanism to detect upstream policy/consensus upgrades - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class in the external report is: the vault assumes an external component (token contract) has fixed behavior, with no detection/freeze mechanism when that component's rules change. In `bitcoin-serai`, the analogous external dependency is Bitcoin's relay/mining policy and consensus environment. `SignableTransaction::new` and the processor's aggregation logic bake in the current Bitcoin Core policy (`DEFAULT_MIN_RELAY_TX_FEE`, `MAX_STANDARD_TX_WEIGHT`, `DUST = 546`, `COST_TO_AGGREGATE = 800` sats assuming ~1 sat/vbyte) and assume mempool-chaining and `Prevouts::All` sighash semantics are stable. If Bitcoin Core ships a policy upgrade (e.g., changed minimum relay fee, changed dust thresholds, new standardness rules for OP_RETURN/witness items), the FROST-signed transactions Serai produces can become non-standard/unrelayable or mispriced, with no detection or pausing mechanism.

### Finding Description
- `SignableTransaction::new` computes `needed_fee = fee_per_vbyte * vbytes` and rejects only if below `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`, a constant copied from the currently compiled `bitcoin` crate — not queried from the connected node (`bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE` is a compile-time constant of the dependency, literally an "upgradable" external component). [1](#0-0) 
- `DUST` is hardcoded to `546` with a comment acknowledging it is derived from Bitcoin Core `policy.cpp` — policy, not consensus — yet is enforced permanently for every payment and change output. [2](#0-1) 
- Standardness weight limit `MAX_STANDARD_TX_WEIGHT` is likewise treated as a fixed invariant. [3](#0-2) 
- The processor hardcodes `COST_TO_AGGREGATE: u64 = 800` sats, justified by an assumed ~4 sat/vbyte minimum fee environment; a fee-market/policy change makes this estimate silently wrong (overpayment = loss, underpayment = stuck aggregation tx). [4](#0-3) 
- Signing commits to `Prevouts::All` and `TapSighashType::Default` and assumes the witness contains exactly one 64-byte signature; weight estimation bakes this in via `Witness::from_slice(&[vec![0; 64]])`. [5](#0-4) 
- The scanner assumes the current consensus layout — skipping `block.txdata[0]` as coinbase (`block.txdata[1 ..]`) — and treats the node's reported blocks at `N::CONFIRMATIONS` depth as final; there is no version/policy check on the connected node before producing or signing transactions. [6](#0-5) 

### Impact Explanation
After a Bitcoin Core policy upgrade (these occur regularly: min-relay-fee changes, dust-rule revisions such as ephemeral-dust/TRUC discussions, standardness relaxations/tightenings), Serai-built transactions may be rejected by the mempool while Serai has already burned/scheduled the corresponding outputs, permanently stalling aggregation and payout transactions — vault funds become unspendable in practice until manual intervention and a code upgrade, exactly the "vault breaks when the external component upgrades" failure of the report. Conversely, if policy loosened, `COST_TO_AGGREGATE` and `DUST` over-reserve cause quantifiable loss of funds on every aggregation/change transaction. No code path detects a policy mismatch; `get_block`/`get_latest_block_number` failures only map to `NetworkError::ConnectionError`, never to a policy-incompatibility halt.

### Likelihood Explanation
Medium likelihood, matching the external report's Medium severity: it does not require an attacker — only a routine upstream Bitcoin Core release whose relay policy diverges from the constants pinned in `bitcoin::policy` at compile time. Every deposit/withdrawal flows through `SignableTransaction::new` and the fixed `COST_TO_AGGREGATE`, so a divergence affects the entire vault's liveness/cost accounting rather than an edge case. The probability of such divergence over the vault's lifetime is non-negligible (min relay fee and dust rules have changed multiple times historically).

### Recommendation
- Query the connected node's actual policy at runtime (`getmempoolinfo`/`getnetworkinfo` for `minrelaytxfee`, `incrementalfee`) instead of relying on `bitcoin::policy::*` constants, and refuse/err when the node's policy disagrees with compiled assumptions.
- Add a startup check of node version/policy and a pause/freeze path when it changes, mirroring the report's recommendation.
- Make `DUST` and `COST_TO_AGGREGATE` runtime-configured or derived from live estimates rather than hardcoded.

### Proof of Concept
1. Upgrade the Bitcoin Core node Serai's `Rpc` connects to, such that `DEFAULT_MIN_RELAY_TX_FEE` or the dust threshold differs from the compiled `bitcoin` crate values (e.g., a node requiring a higher minimum relay fee).
2. A user sends a deposit to the vault P2TR address; the scanner registers it via `Scanner::scan_transaction`. [7](#0-6) 
3. Serai builds the aggregation/payout transaction via `SignableTransaction::new`, which passes the `TooLowFee` check against the stale compiled constant and returns a transaction the upgraded mempool rejects as non-standard / underpaying.
4. The FROST threshold signature is produced (`TransactionMachine::complete`) over `Prevouts::All`, the tx is broadcast, never confirms, and Serai has no policy-mismatch detection — the vault stalls while the scanned outputs are already booked as received. Funds are frozen pending manual recovery, demonstrating the identical impact class: "external component upgraded; vault functionality broken; loss of funds/liveness."

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
