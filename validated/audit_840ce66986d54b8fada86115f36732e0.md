### Title
App Proxy signature verification lacks timestamp/replay-freshness enforcement, allowing indefinite replay of captured signed proxy requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#verify_proxy_request` authenticates App Proxy requests solely by recomputing an HMAC-SHA256 signature over the query parameters (including the `timestamp` param) and comparing it to the request's `signature` parameter with `ActiveSupport::SecurityUtils.secure_compare`. It never checks that `timestamp` is recent, so a captured, validly-signed proxy request/URL remains permanently replayable.

### Finding Description
`query_string_valid?` deletes the `signature` key, recomputes the HMAC over the sorted remaining params (`shop`, `path_prefix`, `timestamp`, and any app-supplied query params) using `ShopifyApp.configuration.secret`, and does a constant-time comparison against the supplied signature. [2](#0-1) 

Unlike the on-chain `ApprovedCallsPolicy` bug class, where a signed approval becomes permanently unusable after being consumed once (via an incrementing nonce), this verification path has **no** mechanism to invalidate a signature after use or after time has passed — the `timestamp` field is present in the signed payload but is never read or validated against `Time.now`. Any URL that was ever validly signed by Shopify for this app's proxy endpoint (e.g., one that leaked via browser history, a shared link, a referrer header, server logs, or a proxy/cache) remains a valid, replayable authenticated request indefinitely, from any origin, since `AppProxyVerification` is the sole authentication gate on that controller action and it explicitly skips `verify_authenticity_token` (standard Rails CSRF protection). [3](#0-2) 

This mirrors the report's root cause precisely: a signed message intended to authorize a single action is missing an anti-replay binding (there, an incrementing nonce; here, timestamp-window enforcement), so the same signed artifact can be resubmitted to trigger the authorized action again outside its intended validity period.

### Impact Explanation
If a shop's App Proxy endpoint performs any state-changing action (e.g., creating a review, submitting a form, granting a discount, recording a vote/loyalty action) based solely on `AppProxyVerification` passing, an attacker who obtains one previously valid signed proxy URL can resubmit it at will — long after the original request — to repeat that state change as if it were a fresh, legitimate, Shopify-proxied request. This is an accepted forged/replayed signed request bypassing the app's only authentication mechanism for that route.

### Likelihood Explanation
App Proxy URLs are GET/POST requests that pass through the storefront and are commonly logged (server access logs, CDNs, browser history, `Referer` headers on subsequent third-party requests) or bookmarked/shared, so a captured URL is easy to obtain without any privileged access. No secret material needs to be leaked — only one historical signed request needs to be observed, satisfying "reachable from an anonymous/unrelated request."

### Recommendation
Validate the `timestamp` query parameter against the current server time and reject requests outside a small tolerance window (as Shopify's own documentation recommends for App Proxy signature verification), e.g.:
```ruby
def verify_proxy_request
  head(:forbidden) unless query_string_valid?(request.query_string) && timestamp_fresh?(params[:timestamp])
end
```
Additionally, consider that this is a generic pattern shared with the reported bug class: any signature scheme lacking single-use/expiry enforcement is vulnerable to replay; the fix should ensure freshness is always checked wherever this HMAC-verification helper is reused.

### Proof of Concept
1. Observe (via logs, referrer headers, browser history, or a shared link) any previously-issued, validly-signed App Proxy request to `GET /app_proxy/<action>?shop=...&timestamp=<T>&...&signature=<S>` for a target shop.
2. At any later time (minutes, days, or years later), replay the exact same URL/query string verbatim to the app.
3. `query_string_valid?` recomputes the same HMAC over the same parameters (since none of them, including `timestamp`, are checked for freshness) and it matches `S`, so `verify_proxy_request` allows the request through, executing the underlying controller action again.

```ruby
    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
