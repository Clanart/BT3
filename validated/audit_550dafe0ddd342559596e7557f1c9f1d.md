### Title
Webhook shop identity (`shop`/`shop_domain`) is trusted from an unsigned header/field while HMAC only authenticates the raw body, enabling cross-shop identity substitution - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The reported `BribeVault` bug is a case where a privileged, verified operation (the ERC20 transfer) is decoupled from the identifier that determines *who it applies to* (`bribeIdentifier`/`briber`), letting a trusted caller apply a validated action to an arbitrary target identity. The same pattern of "verify the payload, but trust an unbound identifier for the tenant/target" exists in `shopify_app`'s webhook handling: `ShopifyApp::WebhookVerification#verify_request` computes the HMAC only over `request.raw_post` [1](#0-0)  and the accompanying `hmac_valid?` helper in `PayloadVerification` also only signs `data` (the body) [2](#0-1) . The shop identity used for all downstream tenant-scoped processing (`shop_domain`) is read from the `X-Shopify-Shop-Domain` header, which is not part of the HMAC-signed content [3](#0-2) .

### Finding Description
`WebhooksController#receive` and the generator-produced custom controllers pass the raw request straight to job processing keyed by the shop identity extracted from the webhook headers [4](#0-3) , and the documented custom-controller pattern explicitly forwards `shop_domain` (sourced from `shop_domain`/the request's shop header) to a background job together with the body [5](#0-4) . The generated job templates then use that `shop_domain` value directly to look up the tenant `Shop` record and open an authenticated Shopify session for it (`shop.with_shopify_session`) [6](#0-5) [7](#0-6) .

Because `verify_request` only asserts that the *body* matches the HMAC computed with the shared secret, and never checks that the `X-Shopify-Shop-Domain` header is consistent with, or derived from, that same signed payload, an attacker who can obtain any one validly-HMAC'd webhook request (e.g., from their own installed shop, which legitimately receives correctly-signed webhooks from Shopify) can resend that exact `(body, hmac)` pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to name a different, victim shop. `verify_request` still passes because it never examined the header, and the job is then dispatched with `shop_domain` pointing at the victim tenant while the body/content is attacker-controlled.

This directly mirrors the BribeVault root cause: a role/consumer (`DEPOSITOR_ROLE` in the report, the webhook job pipeline here) performs a verified/authorized action (`safeTransferFrom` / HMAC-validated dispatch) but binds it to an identifier (`briber` / `shop_domain`) that was never actually checked against what was cryptographically verified.

### Impact Explanation
If a multi-tenant `shopify_app`-based application uses the documented pattern of trusting `shop_domain` from webhook headers to select a tenant's stored access token and act with it (as all generator templates do), a malicious or compromised merchant that has any legitimately-installed instance of the app can:
- Forge a header-substituted webhook request that is accepted as "verified" for a shop they do not own.
- Cause the app to process attacker-controlled `webhook` body content under a victim shop's session/access token context, i.e., cross-shop confusion of the kind the "Accept only... cross-shop or cross-user access, accepted forged signed request" rule calls for.

The severity depends on what the app-specific job does with `webhook` data under the victim's `shop.with_shopify_session` (e.g., writing data, updating orders/products, or triggering irreversible business logic) — this part is app-specific and cannot be fully confirmed from the gem alone, since the actual processing logic lives in generated/overridden job code, not in `shopify_app` itself.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one validly-signed webhook body/HMAC pair, which is trivially obtainable by any merchant who installs the app (any webhook triggered by their own store actions is legitimately HMAC-signed by Shopify with the app's shared secret). No secret material needs to be broken; only the unauthenticated header needs to be altered on replay to the app's public webhook endpoint. This is a realistic, low-effort attack path for any app that follows the gem's documented job dispatch pattern.

### Recommendation
- Do not trust `X-Shopify-Shop-Domain` (or any other unsigned header/field) as the tenant identity for privileged, per-shop actions.
- Bind the shop identity to the verified payload: e.g., include the shop domain inside the HMAC-covered body (as Shopify's REST webhooks JSON payload often does for certain topics) and validate it, or use the `ShopifyAPI::Webhooks::Registry`/topic-specific verified fields instead of the raw header, ensuring the identity used for job dispatch is itself covered by the signature check in `verify_request`/`hmac_valid?`.
- At minimum, document and enforce in `ShopifyApp::WebhookVerification` that `shop_domain` must be cross-checked (e.g., against an `Idempotency-Key`/nonce store, replay-protection window, and a signed shop reference) before being used to select a tenant session.

### Proof of Concept
1. Merchant installs the app on `attacker-shop.myshopify.com` and legitimately triggers a webhook (e.g., `carts/update`), receiving/observing a request Shopify sends with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker crafts a POST to the app's webhook endpoint (`/webhooks/carts_update`) with the exact same raw body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` [1](#0-0) , which only checks the body against secret `S` — this passes since `B`/`H` are a genuinely valid pair.
4. The controller/job dispatch uses the (unverified) header value as `shop_domain` [8](#0-7) , causing the job to load `victim-shop`'s session and process attacker-controlled `webhook` content as though it came from the victim shop.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
