### Title
Payout attribution trusts unauthenticated OP_RETURN of whichever tx spends the withdrawal UTXO, letting anyone redirect reimbursement credit - (File: core/src/verifier.rs)

### Summary
The bridge determines "which operator fronted withdrawal `i`" solely by parsing the OP_RETURN of whatever Bitcoin transaction is found on-chain spending the withdrawal UTXO, with no check that the party named in the OP_RETURN produced, signed, or funded that transaction. Since the user's `SinglePlusAnyoneCanPay` signature only commits to input 0 and output 0, anyone can take an already-broadcast payout, front the payout amount themselves, and attach any operator's x-only pubkey to the OP_RETURN, redirecting bridge reimbursement credit to that operator.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk` for withdrawal `i` == the xonly pubkey of the party whose Bitcoin funds actually paid the withdrawal output for withdrawal `i`.

`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a payout tx with input 0 = the user's committed withdrawal UTXO (spent with `SpendPath::KeySpend` and `SinglePlusAnyoneCanPay`), output 0 = user's payout, and an OP_RETURN output naming `operator_xonly_pk`. Because the user's signature uses `SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`, enforced sighash type), it only commits to input 0's prevout and output 0; any additional inputs (fee/amount funding) and any other outputs, including the OP_RETURN, are completely unconstrained and can be freely substituted by anyone who reuses input 0 + output 0 verbatim.

When a block is processed, `update_finalized_payouts` (`core/src/verifier.rs:2283-2354`) looks up whichever transaction actually spent the tracked withdrawal UTXO and confirmed in that block (`get_payout_txs_for_withdrawal_utxos`), then simply parses that confirmed transaction's first OP_RETURN output for a 32-byte value that decodes as a valid `XOnlyPublicKey` (line 2319-2321) and writes it straight into `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` — with no signature check, no verification that the named key's owner actually supplied the funding inputs, and no cross-reference to any operator-side record of an intended payout txid.

This DB value is then trusted as ground truth in two places:
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) treats a kickoff as non-malicious if `operator_xonly_pk == kickoff_data.operator_xonly_pk`, purely from the DB value.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) calls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` — i.e., each operator's own automation polls the DB for payouts attributed to *its own* key, and if found, automatically proceeds to `handle_finalized_payout` → kickoff → reimbursement, without ever checking whether it itself broadcast that specific payout transaction.
- `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) similarly only checks `payer_xonly_pk == self.signer.xonly_public_key` from the DB.

Exploit flow: an attacker observes a legitimate operator's already-broadcast (unconfirmed) payout tx in the mempool. They construct a new transaction reusing input 0 (withdrawal UTXO) and output 0 (user payout) verbatim with the original valid `SinglePlusAnyoneCanPay` signature, add their own funding input(s) covering the payout amount plus fee, and attach a new OP_RETURN naming a different, real, registered operator's x-only pubkey (not their own). If this substitute transaction confirms instead of the original (via direct submission to a miner with sufficient fee, or RBF/fee competition — no special privilege beyond broadcast + fee payment needed), `update_finalized_payouts` attributes the payout to the named operator. That operator's own `PayoutCheckerTask` will then detect an "unhandled payout" credited to itself and automatically drive the kickoff/reimbursement flow, causing the bridge to reimburse that operator for a withdrawal it never actually funded.

Existing guards fail because none of them re-derive "who funded this tx" from the transaction's actual inputs/signatures — they all just trust the OP_RETURN bytes parsed from whatever tx happened to confirm.

### Impact Explanation
An operator can be reimbursed by the bridge's collateral/kickoff mechanism for a withdrawal it never funded — this is one of the explicitly listed Critical impacts. The attacker (or a colluding operator) pays the withdrawal amount once but the bridge treats a different (or the same, self-dealing) operator as having fronted it, so reimbursement collateral flows to a party with no matching real expenditure. This is repeatable across every withdrawal and every operator, since the vulnerable code path (`update_finalized_payouts`) is generic and runs for every confirmed payout transaction on every deposit/withdrawal cycle.

### Likelihood Explanation
No special role is required: the attacker only needs standard Bitcoin broadcast/fee-paying capability and enough BTC to front the withdrawal output amount plus fees in place of the real operator. The main cost/constraint is winning the on-chain race against the honest operator's already-broadcast transaction (e.g., via higher fee, RBF, or direct submission to a miner) before it confirms — this is normal fee-market/mempool behavior, not a hashrate or consensus attack. This makes the attack costly per attempt (attacker must front the full withdrawal value) but requires no bridge role, no key compromise, and no majority hashrate.

### Recommendation
Do not derive payout attribution purely from an unauthenticated OP_RETURN byte string. Require the confirmed payout transaction's actual funding input(s) to be provably controlled/spent by the named operator (e.g., verify a signature over the OP_RETURN commitment from the named operator's key, or require operators to pre-register the exact payout txid/witness they intend to broadcast and only accept attribution matching that pre-registered record) before treating a payout as "fronted" by that operator for reimbursement purposes.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
