### Title
Recursive clone disables Git's clone-time config protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` always passes `--recursive` and sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every repository clone Desktop performs, including clones of repositories reached via a deep link (`x-github-client://openRepo/<url>`) or a URL returned from the GitHub API. This disables the safeguard Git added specifically to prevent a just-cloned, attacker-controlled repository's own configuration/submodule definitions from taking effect during that same clone.

### Finding Description
Git's clone protection (governed by `GIT_CLONE_PROTECTION_ACTIVE`, on by default in modern Git) exists precisely because a repository being cloned is untrusted input: its `.gitmodules` and embedded config can define submodule URLs (including `file://`/relative paths that resolve outside the intended tree, or `ext::`-style transports in older/misconfigured Git builds) and other settings that Git would otherwise apply automatically during the recursive submodule checkout that follows a `--recursive` clone. By forcing `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally, Desktop removes that safeguard for every clone, regardless of whether the URL came from a trusted, user-typed source or from attacker-controlled input (a deep link's embedded URL, or an API-returned `clone_url`). The existing guards elsewhere in the codebase — `sanitizeCloneName`/`isClonePathSensitive` (destination-path traversal) and `resolveWithin`/`isAbsolute` checks in `openRepositoryFromUrl` (post-clone file access) — only protect the *destination path on disk* and the *filepath parameter after cloning*; none of them re-enable or replace the config-injection protection that Git's own clone-protection mechanism provides for the *contents* of the cloned repository and its submodules. [5](#0-4) 

### Impact Explanation
An attacker who controls a repository (a public repo, a fork, or a repo pointed to by a crafted `x-github-client://openRepo/<attacker-url>` link) can embed a `.gitmodules`/config payload that leverages the disabled clone protection to have local, protected settings honored during the automatic recursive submodule checkout that follows `clone --recursive`. Depending on the exact Git version bundled with Desktop, this can lead to reading/writing files outside the intended clone directory or, in the worst case, arbitrary command execution during the clone — matching the "code execution" / "file write or read outside the repo" impact classes, without requiring any local access, admin rights, or prior malware.

### Likelihood Explanation
Likelihood is meaningful but not certain without confirming the exact underlying Git version's vulnerable behavior when protection is disabled: cloning is a normal, expected user action (clicking "Clone" or a deep link), so the attacker-controlled input reaches the vulnerable code path with no unnatural steps. The severity of the outcome depends on which specific clone-time config injection scenario the disabled protection was guarding against in the bundled Git version.

### Recommendation
Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or scope it narrowly and only for cases where Desktop has already independently validated the repository as trusted), and audit whether `--recursive` should be deferred until after a repository/submodule URL allow-list check, consistent with the `allowFileProtocol` opt-in pattern already used in `updateSubmodulesAfterOperation`.

### Proof of Concept
1. Attacker publishes a repository whose `.gitmodules`/embedded config is crafted to exploit the class of clone-time config-injection issue that `GIT_CLONE_PROTECTION_ACTIVE` protects against (exact payload depends on the bundled Git version's protected-config list).
2. Attacker sends the victim a link such as `x-github-client://openRepo/https://github.com/attacker/evil-repo`, which Desktop's `parseAppURL`/`dispatcher.openRepositoryFromUrl` resolves to `openOrCloneRepository`.
3. Desktop calls `clone()` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, so the embedded malicious configuration in the attacker's repo is honored during the clone/submodule-update phase instead of being blocked.

**Note:** I was not able to fully verify, from the indexed portion of the codebase, exactly which Git version is bundled or precisely which protected-config scenario this disables in that version — this would need to be confirmed in a live/full checkout of the repository (e.g., via a Devin session) before treating the exploitability as certain.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
