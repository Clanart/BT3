## Divide-by-Zero Panic in KIP-71 Base Fee Calculation via Unvalidated `GasTarget` Governance Parameter

### Title
Divide-by-zero panic in `KIP71Config.NextMagmaBlockBaseFee` due to unvalidated `kip71.gastarget=0` governance vote - (File: `params/kip71_config.go`)

### Summary
The Magma/KIP-71 base-fee formula in `params/kip71_config.go` divides by `kc.GasTarget` without checking for zero. Unlike `BaseFeeDenominator`, which has an explicit zero-guard, `GasTarget` has none. The governance vote pipeline for `kip71.gastarget` uses `noopFormatChecker` (accepts any `uint64`, including 0) and `checkConsistency` performs no bound/zero check for this parameter, so a value of `0` can be legitimately enacted as a governance parameter and will crash every node evaluating base fee for the next block.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the next block's base fee using `gasTarget := kc.GasTarget` as a divisor in both the "gas used above target" and "gas used below target" branches: [1](#0-0) 

Notice `BaseFeeDenominator` is explicitly protected against zero: [2](#0-1) 

But `GasTarget` is used raw, with only an early-return when `parentGasUsed == gasTarget` (i.e., both zero). Any nonzero `parentGasUsed` combined with `gasTarget == 0` reaches `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor, which panics in Go's `math/big`.

The governance parameter definition for `Kip71GasTarget` uses a no-op format checker that accepts anything, including zero: [3](#0-2) 

Confirmed by the vote fuzz test: `Kip71GasTarget` bad-value list checks type mismatches (string, int, bool) but never rejects `uint64(0)`: [4](#0-3) 

And `checkConsistency` in the header-governance vote verifier explicitly routes `gov.Kip71GasTarget` into the "no more checks here" bucket, alongside other parameters that only need to pass the (no-op) format check: [5](#0-4) 

This means a `kip71.gastarget = 0` vote can be cast by a validator/governing node, get enacted at the next epoch via `VerifyGov`/`getExpectedGovernance`, and once active, `NextMagmaBlockBaseFee` will panic for any block where `parentGasUsed != 0`. This function is called both by the block proposer while preparing the header (`VerifyMagmaHeader`) and by every validating node, as well as by RPC-facing code such as `node/cn/gasprice/feehistory.go`'s `processBlock`: [6](#0-5) 

### Impact Explanation
Once `GasTarget=0` is enacted, every full node that processes a block with nonzero gas usage (essentially guaranteed) panics inside `NextMagmaBlockBaseFee`. Because this function is invoked both during block production and during header verification by all other nodes, this results in a network-wide chain halt / crash — a supply/availability-critical bug in the state-transition/fee-accounting path, not merely a resource-exhaustion issue. It is also invoked by public RPC handlers (`eth_feeHistory`), so even nodes serving RPC calls after the bad parameter takes effect will crash while answering ordinary queries.

### Likelihood Explanation
The vote is gated by validator/governing-node membership checks (`VerifyVote`'s council/proposer checks), so it requires a validator (or, in single mode, the governing node) to cast the vote — this matches the permitted "governance parameters" reachable surface. There is no bounds validation anywhere in the vote pipeline preventing this specific value, so the likelihood of a malicious or misconfigured governance actor triggering it is high once such a vote is cast and reaches consensus at an epoch boundary.

### Recommendation
Add an explicit zero-guard for `GasTarget` in `NextMagmaBlockBaseFee` (mirroring the existing `BaseFeeDenominator` fallback), and/or add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, and add a corresponding `checkConsistency` validation in `kaiax/gov/headergov/impl/header.go` to reject `kip71.gastarget == 0` votes at proposal time.

### Proof of Concept
1. A validator (or governing node in single mode) casts a vote `kip71.gastarget = 0` via `headergov.NewVoteData`. This passes `NewVoteData` (format checker is a no-op) and `VerifyVote`/`checkConsistency` (no value check exists for this parameter) as shown in `kaiax/gov/headergov/impl/header.go` lines 214-220.
2. At the next epoch boundary the vote is enacted into `ParamSet.GasTarget = 0` and reflected into `ChainConfig.Governance.KIP71.GasTarget`.
3. On the following block, any node calls `KIP71Config.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` with `parentHeaderGasUsed > 0` (normal for any block with transactions).
4. Since `parentGasUsed != gasTarget(0)`, execution enters the `>` or `<` branch and executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics (`division by zero` in `math/big`), crashing the node process — affecting block proposers, validators, and RPC servers alike.
