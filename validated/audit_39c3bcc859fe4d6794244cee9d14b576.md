### Title
`isGitHubHost()` misclassifies attacker-controlled third-party domains as trusted GitHub hosts via a stale allowlist and overly broad regex fallback - (File: `app/src/lib/api.ts`)

### Summary
`isGitHubHost()` decides whether a URL "belongs to a GitHub host" using a hand-maintained `knownThirdPartyHosts` set plus regex fallbacks. Like the ZkSync `CURRENT_MAX_PRECOMPILE_ADDRESS` bug — a manually-tracked boundary constant that silently drifts out of sync with the actual set of special addresses — this Desktop classification depends on a manually-curated list of "known non-GitHub" hosts that can never be exhaustive, and falls back to a loose substring/regex heuristic that a repository/URL an attacker fully controls can satisfy.

The invariant the code is trying to enforce is: `isGitHubHost(url) === true` should only hold for `github.com`, `api.github.com`, or a genuine GHE instance. Just as `CURRENT_MAX_PRECOMPILE_ADDRESS` was supposed to track "every address that is a precompile" but wasn't updated when `ECADD`/`ECMUL` were added, `knownThirdPartyHosts` is supposed to track "every non-GitHub host that could otherwise trip the loose regex," but it is a fixed, incomplete list that will never cover the full universe of third-party or attacker-registerable domains. The regex fallback `/(^|\.)(github)\./` matches any hostname that contains a `.github.` label anywhere — including domains attackers can legitimately register/host content on, such as GitHub Pages subdomains (`*.github.io` does not match this particular pattern, but any domain an attacker registers or a subdomain they control containing a `github.` label, e.g. `attacker.github.example.net` or a spoofed enterprise-style host, would incorrectly return `true`). Because the exclusion list (`knownThirdPartyHosts`) is finite and static while the inclusion regex is broad and unconditioned on any actual verification (no TLS cert check, no `/meta` endpoint probe, no DNS confirmation of the real GHE instance), the boundary between "trusted GitHub host" and "arbitrary host" is not closed — exactly the same class of defect as the stale `CURRENT_MAX_PRECOMPILE_ADDRESS` boundary in the report.

### Impact Explanation
I was not able to trace, within the available indexed context, every call site of `isGitHubHost()` to confirm the exact downstream consequence (e.g., whether its `true` result gates credential attachment, auto sign-in, or repository trust decisions). This limits my ability to state a concrete high-severity impact with full certainty. What is verifiable from the code itself is that the trust decision is made by an incomplete, hardcoded exclusion set combined with an unauthenticated substring/regex heuristic — the same broken-invariant pattern as the reference finding (a boundary meant to be exhaustive that isn't, and isn't defended by any cryptographic or network-verified check). If any caller uses `isGitHubHost()` to decide whether to treat a repository/URL as GitHub-authenticated (e.g., for special handling of PR/branch metadata, telemetry, or UI trust indicators), a crafted hostname could be misclassified as a GitHub host.

### Likelihood Explanation
An attacker only needs to control (or register) a hostname that isn't in the small `knownThirdPartyHosts` set but satisfies the `github.`/`bitbucket.`/`gitlab.` substring heuristics — no privileged access, malware, or credentials are required, and the URL could arrive via a cloned repository's remote configuration, a PR/link the user opens, or a deep link, consistent with the allowed attacker-controlled vectors in scope.

### Recommendation
Replace the static exclusion-list + substring-regex approach with a check anchored to a verified endpoint (e.g., confirm the URL's origin matches a configured/signed-in GHE endpoint exactly, or perform a `/meta`-style verification with certificate/host validation) rather than inferring trust from a `.github.` substring match combined with a necessarily incomplete list of "known other" hosts. At minimum, do not rely on the substring regex being the deciding factor when the hostname is not equal to (or a properly-anchored subdomain of) a known, registered endpoint.

### Proof of Concept
Because I could not confirm the exact security-relevant consumer of `isGitHubHost()`'s return value within the indexed portion of the codebase, I cannot provide a fully concrete end-to-end exploit chain with certainty. The demonstrable code-level flaw is:

```ts
// hostname fully controlled by attacker's DNS registration
isGitHubHost('https://ci.github.evil-corp.example/') 
// -> hostname = "ci.github.evil-corp.example"
// -> not in knownThirdPartyHosts
// -> /(^|\.)(github)\./.test("ci.github.evil-corp.example") === true
// -> function returns true, misclassifying an attacker-owned host as a GitHub host
```

Given the uncertainty about the exact downstream trust impact (I could not fully verify all call sites due to indexing limits), this should be treated as a **probable** rather than **confirmed** high-impact analog. If a Devin session with full repo access confirms `isGitHubHost()` gates a security-sensitive decision (credential attachment, silent trust of remote content, etc.), this would become a directly confirmed medium/high finding matching the reported bug class; otherwise it remains a defense-in-depth weakness worth hardening.
