## Analog Found

### Title
Wallet Trusts Offer-Supplied `driver_dict` PuzzleInfo Without Validating It Against the Actual On-Chain Puzzle Structure - (File: `chia/wallet/trade_manager.py`)

### Summary
The Sherlock finding is a generic "assign external config to a critical field without validating that the underlying contract/object actually implements the claimed interface" bug (`avail = newAvail` in `initialize()` never checks that `newAvail` conforms to `IWrappedAvail`). The same trust pattern exists in Chia's offer/trade code: an `Offer` carries a `driver_dict: dict[bytes32, PuzzleInfo]` that is deserialized/accepted verbatim from a (potentially malicious) offer counterparty, and this declared "type"/interface metadata is used to construct wallets and puzzle reveals without independently verifying it matches the real CLVM puzzle actually being spent.

### Finding Description
`Offer` is a `@streamable` dataclass whose `driver_dict` field is populated directly from the bytes of an offer file created by the other party, not necessarily re-derived by inspecting the real coin puzzles: [1](#0-0) .

`__post_init__` only checks that a driver entry exists for every *requested* asset ID — it never validates that `driver_dict[asset_id]` actually matches the puzzle structure of the *offered* coins being received: [2](#0-1) .

Separately, `_get_offered_coins` independently derives the true puzzle driver for each spent coin via `match_puzzle(parent_puzzle)` against the *real* puzzle reveal, but this independently-verified `PuzzleInfo` is only used locally to bucket coins by `asset_id` — it is discarded rather than cross-checked against `self.driver_dict`: [3](#0-2) .

When a taker accepts an offer, `respond_to_offer` calls `maybe_create_wallets_for_offer`, which for every arbitrage asset directly instantiates a wallet using the offer's declared (unverified) `driver_dict` entry: [4](#0-3) [5](#0-4) .

`create_wallet_for_puzzle_info` then dispatches purely on `puzzle_driver.type()` / `puzzle_driver.also()` to decide which wallet subclass to instantiate and with which parameters, with no re-derivation from the real puzzle reveal: [6](#0-5) .

Downstream, `CRCATWallet.create_from_puzzle_info` takes `authorized_providers` and `proofs_checker` straight out of the attacker-suppliable `puzzle_driver`/`cr_layer` PuzzleInfo and persists them as the wallet's enforced CR-CAT policy: [7](#0-6) . Likewise `RCATWallet.create_from_puzzle_info`/`match_puzzle_info` trust the declared `hidden_puzzle_hash` from the driver info: [8](#0-7) .

This is the same root cause as the reported issue: a security-relevant configuration object (`IWrappedAvail` / `PuzzleInfo`'s "also" sub-layer) is accepted and wired into state without checking that it actually corresponds to / is implemented by the real underlying object (the contract address / the on-chain puzzle reveal).

### Impact Explanation
Because `driver_dict`'s sub-layer metadata (revocation `hidden_puzzle_hash`, CR `authorized_providers`/`proofs_checker`) is not cross-verified against the actual puzzle_reveal of the received coin, a malicious offer maker can cause the taker's wallet to instantiate a CAT/CR-CAT/RCAT wallet whose recorded policy diverges from what is actually enforced by the on-chain puzzle. This can lead to the taker's wallet mis-tracking asset identity/authorization semantics for coins it now custodies (e.g. believing a coin is revocable/restricted under parameters that don't match the real puzzle, or vice versa), which can subsequently produce incorrect spend construction, incorrect balance/authorization assumptions, or wallet state diverging from consensus-enforced coin behavior.

### Likelihood Explanation
Reachable by any offer counterparty: a taker calling `respond_to_offer`/`take_offer` on an attacker-crafted offer file is a normal, unprivileged wallet-user flow (`chia/wallet/wallet_rpc_api.py` `take_offer`), requiring no special access — only that the victim chooses to accept a malicious offer.

### Recommendation
Before using `offer.driver_dict[asset_id]` to create or configure a wallet (in `maybe_create_wallets_for_offer` / `create_wallet_for_puzzle_info` / `create_from_puzzle_info`), re-derive the `PuzzleInfo` for that asset by calling `match_puzzle` against the actual puzzle reveal of the corresponding coin spend in the offer's bundle, and reject/ignore the offer if the declared driver does not exactly match the independently derived one (analogous to validating `newAvail` actually implements `IWrappedAvail` before trusting it).

### Proof of Concept
1. Attacker mints a CR-CAT coin whose real on-chain CR layer enforces `authorized_providers = [DID_A]` and a specific `proofs_checker`.
2. Attacker crafts an `Offer` bytes blob (`chia/wallet/trading/offer.py`) whose `_bundle` spends that real coin, but whose serialized `driver_dict[asset_id]` declares a different/weaker `also` sub-layer (e.g. plain `CAT` type with no CR restriction, or CR restriction with different `authorized_providers`/`proofs_checker`) — nothing in `Offer.__post_init__` validates this against the real puzzle.
3. Victim calls `take_offer` → `TradeManager.respond_to_offer` → `maybe_create_wallets_for_offer` → `WalletStateManager.create_wallet_for_puzzle_info(offer.driver_dict[key])`, which creates a `CATWallet`/`CRCATWallet` using the attacker-declared (unverified) policy rather than the coin's true on-chain policy.

    def __post_init__(self) -> None:
        # Verify that there are no duplicate payments
        for payments in self.requested_payments.values():
            payment_programs: list[bytes32] = [p.name() for p in payments]
            if len(set(payment_programs)) != len(payment_programs):
                raise ValueError("Bundle has duplicate requested payments")

        # Verify we have a type for every kind of asset
        for asset_id in self.requested_payments:
            if asset_id is not None and asset_id not in self.driver_dict:
                raise ValueError("Offer does not have enough driver information about the requested payments")

    async def match_puzzle_info(self, puzzle_driver: PuzzleInfo) -> bool:
        if (
            AssetType(puzzle_driver.type()) == AssetType.CAT
            and puzzle_driver["tail"] == self.info.limitations_program_hash
        ):
            inner_puzzle_driver: PuzzleInfo | None = puzzle_driver.also()
            if inner_puzzle_driver is None:
                raise ValueError("Malformed puzzle driver passed to RCATWallet.match_puzzle_info")
            return (
                AssetType(inner_puzzle_driver.type()) == AssetType.REVOCATION_LAYER
                and bytes32(inner_puzzle_driver["hidden_puzzle_hash"]) == self.info.hidden_puzzle_hash
            )
        return False
