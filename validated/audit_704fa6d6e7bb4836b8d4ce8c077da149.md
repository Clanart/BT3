### Title
Unvalidated `open-external` IPC handler allows arbitrary-scheme URLs to reach `shell.openExternal` - (File: app/src/main-process/main.ts)

### Summary
The `open-external` IPC handler is described as only logging (not rejecting) when the supplied `path` does not start with `http://`/`https://`, then unconditionally forwarding the raw string to `shell.openExternal`. If this handler is registered via the raw `ipcMain.handle` (as most handlers in `main.ts` are) rather than the sender-checked `handle` wrapper in `ipc-main.ts`, an untrusted or compromised renderer/frame can invoke the channel with a non-http URI.

### Finding Description
`shell.openExternal` on Electron will hand off arbitrary URI schemes to the OS shell (e.g., `file://`, custom registered protocol handlers, or on Windows, executable/UNC-style paths). A handler that only logs a warning for non-http(s) schemes but still calls `shell.openExternal(path)` breaks the intended invariant that this channel is restricted to opening web URLs. This is a documented Electron anti-pattern (see Electron security guide on `shell.openExternal`) precisely because non-http schemes can trigger local file access or process launches via OS-level protocol/URI handling. [3](#0-2) 

### Impact Explanation
If reachable by attacker-controlled content (e.g., a crafted link inside a repository's README rendered in-app, or a malicious deep link), this could result in opening arbitrary local files or invoking OS-registered protocol handlers that spawn other applications — potentially leading to code execution depending on what protocol handlers are registered on the victim's OS.

### Likelihood Explanation
Likelihood depends entirely on whether (a) the `open-external` handler is reachable from an untrusted sender (chained from the question-1 sender-check bypass), and (b) whether links containing non-http schemes can be surfaced to the user from untrusted repository/API content and routed to this channel. I could not confirm the exact call sites that feed user/repo-controlled strings into the `open-external` IPC invocation within this session.

### Recommendation
Enforce the URL-scheme check as a hard reject (return early / throw) rather than a log-only warning, and ensure the `open-external` handler is registered through the sender-validated `handle` wrapper in `app/src/main-process/ipc-main.ts` so `isTrustedIPCSender` applies uniformly.

```typescript
function safeListener<E extends IpcMainEvent | IpcMainInvokeEvent, R>(
  listener: (event: E, ...a: any) => R
) {
  return (event: E, ...args: any) => {
    if (!isTrustedIPCSender(event.sender)) {
      log.error(
        `IPC message received from invalid sender: ${event.senderFrame?.url}`
      )
      return
    }

  }
```

```typescript
import { WebContents } from 'electron'

// WebContents id of trusted senders of IPC messages. This is used to verify
// that only IPC messages sent from trusted senders are handled, as recommended
// by the Electron security documentation:
// https://github.com/electron/electron/blob/main/docs/tutorial/security.md#17-validate-the-sender-of-all-ipc-messages
const trustedSenders = new Set<number>()

/** Adds a WebContents instance to the set of trusted IPC senders. */
export const addTrustedIPCSender = (wc: WebContents) => {
  trustedSenders.add(wc.id)
  wc.on('destroyed', () => trustedSenders.delete(wc.id))
}

/** Returns true if the given WebContents is a trusted sender of IPC messages. */
export const isTrustedIPCSender = (wc: WebContents) => trustedSenders.has(wc.id)
```
