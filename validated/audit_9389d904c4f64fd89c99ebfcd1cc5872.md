## Title
Sending value with `rewards()` calls to the distribution precompile permanently strands usei with no refund or recovery path - (File: `precompiles/distribution/distribution.go`)

### Summary
The distribution precompile's `Execute` dispatcher routes every state-changing (payable) call through explicit payment handling and routes every other view method through `pcommon.ValidateNonPayable(value)` — except `rewards()`. Because `rewards()` neither validates that `value == 0` nor forwards `value` to any refund/payment logic, an EVM caller who attaches `msg.value` to a `rewards(address)` call has that usei/wei silently absorbed with no compensating transfer, no refund, and no mechanism to later withdraw it — a permanent freeze of funds analogous to the JUSDExchange report where deposited tokens become unrecoverable because the contract provides no withdrawal path.

### Finding Description
In `Execute`, all transaction (payable/mutating) methods explicitly call `pcommon.ValidateNonPayable(value)` or process `value` via `pcommon.HandlePaymentUsei`, and other read-only methods (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) all still forward `value` into their handler: [1](#0-0) 

But the `RewardsMethod` case calls `p.rewards(ctx, method, args)` — notably omitting `value` entirely, meaning no non-payable validation is even possible for this path: [2](#0-1) 

Compare this with `WithdrawValidatorCommissionMethod`, which explicitly guards against payable calls before proceeding: [3](#0-2) 

The integration test suite for this precompile explicitly documents this as a known quirk, confirming the analysis and that the value-bearing call succeeds rather than reverting: [4](#0-3) 

Because EVM `CALL` semantics transfer `msg.value` (usei/wei) to the target address's balance as part of normal EVM value-transfer processing before precompile logic even runs, any usei sent alongside a `rewards()` call lands in the precompile's associated Sei account. Since `rewards()` performs no debit/refund logic (it is a pure state query, run on a cache context per `Execute`'s branching for non-transaction methods), that usei is never returned to the caller and there is no other precompile method (e.g., an owner/admin sweep) capable of retrieving it back out.

### Impact Explanation
This results in permanent, unrecoverable freezing of user funds: any usei sent via `msg.value` to `rewards()` becomes stuck at the distribution precompile's backing account. Unlike delegate/withdraw functions where value is deliberately consumed for a defined economic purpose, here the value is stranded with zero economic effect and no code path to reclaim it — directly matching the "Impact" criteria of concrete permanent freezing of funds.

### Likelihood Explanation
Likelihood is non-trivial: it requires only a single unprivileged EVM transaction from any external account (or contract) that calls `rewards(address)` on `0x0000000000000000000000000000000000001007` with a nonzero `value`. No association, authorization, or special privilege is required — an ordinary EVM client mistakenly or programmatically attaching value to what looks like a read-only query call would trigger the freeze.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `rewards()` dispatch path in `Execute` (and thread `value` into `p.rewards(...)` so it can be checked), mirroring the guard already used for `withdrawValidatorCommission` and other view methods: [5](#0-4) 

### Proof of Concept
1. From any EVM account (no association with a Sei address required for a value-bearing call to reach the precompile dispatch), call the distribution precompile at `0x0000000000000000000000000000000000001007` with function selector for `rewards(address)` and a nonzero `msg.value` (usei/wei encoded per the standard split, e.g. `ethers.parseEther("1")`).
2. The EVM value-transfer mechanics debit the caller and credit the precompile's Sei-mapped account balance as part of normal call processing.
3. `Execute` dispatches to `case RewardsMethod: return p.rewards(ctx, method, args)`, which never inspects `value`, never calls `ValidateNonPayable`, and never issues a refund via `HandlePaymentUsei`.
4. The transaction succeeds and returns reward data; the sent usei remains permanently at the precompile's balance with no exposed function to sweep or reclaim it. [2](#0-1) [6](#0-5)
