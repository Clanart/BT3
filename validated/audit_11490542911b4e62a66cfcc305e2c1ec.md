## Title
`discardChanges` batch loop aborts on first `moveItemToTrash` failure without resetting/checking out already-trashed files, corrupting working-tree state when an attacker-controlled repo contains a Trash-hostile file name - (File: `app/src/lib/stores/git-store.ts`)

## Summary
The reported DEX bug is a batch-cancellation loop that transfers refunds one item at a time and reverts the *entire* transaction the moment a single transfer target cannot receive funds, leaving the whole operation (and all not-yet-processed dangerous items) untouched. The same broken invariant — "abort mid-batch on a single item failure, without reconciling state already mutated for prior items" — exists in GitHub Desktop's `discardChanges` implementation, which iterates over a list of working-directory files, moves each to the OS trash, and only performs `git reset`/`git checkout-index` for the whole batch as a separate step *after* the per-file trash loop completes.

## Finding Description
`GitStore.discardChanges` iterates the array of files to discard: [1](#0-0) 

For every file it calls `this.shell.moveItemToTrash(...)`. If that call throws and `askForConfirmationOnDiscardChangesPermanently` is true, the function immediately `throw`s a `DiscardChangesError`: [2](#0-1) 

This throw happens **inside** the `for...of` loop, before the accumulated `pathsToReset`/`pathsToCheckout` arrays (built unconditionally for every file, including ones already sent to trash) are ever passed to the subsequent `git reset` / `git checkout-index` calls. Per the project's own documentation, the flow is sequential and batched — trash *all* files first, then reset paths, then checkout paths — not per-file: [3](#0-2) 

Consequently, if file #`k` in the batch throws during `moveItemToTrash`, files `1..k-1` have already had their on-disk content physically removed (sent to the OS trash) by the time the exception propagates, but the `git reset HEAD` / `git checkout-index -f -u` calls that are supposed to restore/reconcile those paths from the index **never execute at all**, because the throw happens before the code path that issues them is ever reached. The caller in `AppStore._discardChanges` only catches the error to show a retry dialog; it does not attempt to reconcile files that were already trashed: [4](#0-3) [5](#0-4) 

An attacker who controls a cloned/fetched repository can place a tracked file whose path is known to unreliably support OS-level "move to trash" semantics on the victim's platform (e.g., paths with a trailing dot/space, or other characters that Win32 shell APIs silently reinterpret, causing `shell.trashItem` — Electron's wrapper — to throw for that specific entry while succeeding for others). If the victim has multiple modified files staged for "Discard All Changes" in a single batch and one of them is such a poisoned path, the loop will physically delete on-disk content for the files processed before the poisoned entry, then abort without ever invoking `git reset`/`checkout-index` for **any** file in the batch — not even the ones already trashed.

## Impact Explanation
Because reset/checkout never runs for the successfully-trashed files, git's index still records those paths as tracked with their prior blob, but the working tree now has no file there. `git status` will therefore report those paths as **deleted** rather than "reverted to clean," inverting the user's intent (they asked to discard modifications, not delete the files). If the user does not notice and proceeds to commit/push (a very plausible outcome, since the UI's mental model is "discard = clean"), the resulting commit silently deletes files from the repository that were never meant to be removed — this is a silent corruption of what the user commits and pushes, driven entirely by content in an attacker-controlled/cloned repository.

## Likelihood Explanation
This requires: (1) an attacker-controlled repository containing a file whose path reliably breaks the OS trash operation on the target platform, and (2) the victim performing a multi-file "Discard Changes" that includes both the poisoned path and other legitimately-modified files, with the poisoned path ordered before at least one other file in the array. Both conditions are plausible in normal Desktop usage (bulk discard is a common workflow) and require no special local access, admin rights, or social engineering beyond opening/cloning the malicious repository — matching the "unprivileged, attacker controls a cloned/fetched repository" impact bar. The main uncertainty (not verifiable from the indexed source alone) is the exact platform-specific trigger condition for `shell.trashItem` failing on one specific filename while succeeding on others; this needs empirical verification against Electron's `shell.trashItem` implementation on Windows/macOS/Linux, which was outside what I could confirm purely from the indexed files (the reset/checkout call sites themselves, past line 1603 of `git-store.ts`, were also not retrievable in this session and should be reviewed directly).

## Recommendation
- Perform `git reset`/`checkout-index` reconciliation incrementally, or wrap the whole batch so that any already-trashed file is reconciled (reset+checkout) even when a later file in the batch fails to move to trash.
- Alternatively, do not abort the entire loop on a single file's trash failure: collect failures, continue processing the rest of the batch, and only surface the retry dialog for the failed subset, exactly like the original DEX mitigation of "skip/continue instead of reverting the whole batch."
- Add a post-failure invariant check: if `moveItemToTrash` fails for any file after some files were already trashed, force a `git checkout-index` for the already-trashed paths before propagating `DiscardChangesError`, so the working tree is never left in a state where trashed content is unaccounted for by the index reset step.

## Proof of Concept
1. Attacker publishes/clones a repo containing a tracked file with a path known to fail Electron's `shell.trashItem` on the victim's OS (e.g., a trailing-dot/space filename on Windows) alongside other normal files.
2. Victim modifies several files (including the poisoned one) and selects "Discard all changes" in Desktop, triggering `Dispatcher.discardChanges` → `AppStore._discardChanges` → `GitStore.discardChanges`.
3. The loop processes files in array order; files before the poisoned entry are moved to the OS trash successfully.
4. On reaching the poisoned entry, `shell.trashItem` throws; `discardChanges` throws `DiscardChangesError` immediately, before any `git reset`/`checkout-index` call runs for the batch.
5. `AppStore._discardChanges`'s catch block only calls `emitError`, showing a "Discard Changes Retry" dialog; the earlier-trashed files' working tree entries are never restored from the index.
6. `git status` in the repository now shows the earlier files as deleted rather than as clean/reverted; if the user commits at this point, the deletions are silently included in the commit/push.

(Note: exact filenames that reliably break `shell.trashItem` per-OS were not empirically verified in this session and should be confirmed against Electron's trash implementation before treating this as a fully weaponized PoC.)

  public async _discardChanges(
    repository: Repository,
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true
  ) {
    const gitStore = this.gitStoreCache.get(repository)

    const { askForConfirmationOnDiscardChangesPermanently } = this.getState()

    try {
      await gitStore.discardChanges(
        files,
        moveToTrash,
        askForConfirmationOnDiscardChangesPermanently
      )
    } catch (error) {
      if (!(error instanceof DiscardChangesError)) {
        log.error('Failed discarding changes', error)
      }

      this.emitError(error)
      return
    }

    return this._refreshRepository(repository)
  }

/**
 * Handler for when an action the user attempts to discard changes and they
 * cannot be moved to trash/recycle bin
 */
export async function discardChangesHandler(
  error: Error,
  dispatcher: Dispatcher
): Promise<Error | null> {
  if (!(error instanceof DiscardChangesError)) {
    return error
  }

  const { retryAction } = error.metadata

  if (retryAction === undefined) {
    return error
  }

  dispatcher.showPopup({
    type: PopupType.DiscardChangesRetry,
    retryAction,
  })

  return null
}
