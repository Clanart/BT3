### Title
`SmartWomConvert.smartConvert` reverts under wom/mWom pool manipulation and DoSes deposit/depositLP/withdraw - ([File: wombat/SmartWomConvert.sol])

### Summary
`smartConvert()` hard-codes `_minRec = _amountIn` when calling `_convertFor`, so any buyback leg through the `womMWomPool` that nets out below 1:1 causes the whole call to revert with `MinRecNotMatch()`. Because `WombatStaking._sendRewards` calls `smartConvert` unconditionally (no try/catch) whenever the `isMWOM` fee is active, and `_sendRewards` is invoked from `_toMasterWomAndSendReward`, a revert there propagates up through `deposit`, `depositLP`, `withdraw`, and `harvest`, blocking all of them.

### Finding Description
`smartConvert()` decides its swap strategy purely from on-chain, attacker-manipulable pool state: [1](#0-0) 
- `currentRatio()` samples the mWom→wom spot price with a fixed `1e18` probe against `womMWomPool` via `IWombatRouter.getAmountOut` [2](#0-1) .
- `maxSwapAmount()` is derived from the live `cash`/`liability` gap of the wom `IAsset` [3](#0-2) .
- Based on whether `currentRatio() < buybackThreshold`, `smartConvert` picks a `convertRatio` and then calls `_convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode)` — note `_minRec` is fixed to the full `_amountIn`.

Inside `_convertFor`, if a buyback leg is taken it swaps `buybackAmount` of `wom` for `mWom` on the same `womMWomPool` with **zero slippage protection** (`minOut = 0` in `swapExactTokensForTokens`), then only checks the combined result against `_minRec` at the end: [4](#0-3) 

Since `currentRatio()`/`maxSwapAmount()` are read from the same pool that the actual swap later executes against, and Wombat pools expose public swap functions, an attacker can sandwich the caller's transaction (front-run/back-run swaps against `womMWomPool`) to shift `cash`/`liability` and the spot price so that: (a) the branch condition (`currentRatio() < buybackThreshold`) is flipped relative to the "safe" state, and/or (b) the size/direction of the buyback trade experiences price impact that makes `convertAmount + amountRec < _amountIn`. Because `_minRec == _amountIn` with no tolerance, any shortfall — even a small one caused by AMM haircut fees/slippage on the manipulated pool state — triggers `revert MinRecNotMatch()`.

This revert is not contained: `smartConvert` is called directly (no try/catch) from `WombatStaking._sendRewards` whenever `feeInfo.isMWOM && rewardToken == wom && smartWomConverter != address(0)`: [5](#0-4) 
and `_sendRewards` is invoked unconditionally from `_toMasterWomAndSendReward`, which itself is called from `deposit`, `depositLP`, `withdraw`, and `harvest`: [6](#0-5) [7](#0-6) [8](#0-7) 

There is no `whenNotPaused` bypass, no reentrancy guard interaction, and no fallback path that skips the mWom conversion when it fails — a revert anywhere in this chain aborts the entire user deposit/withdraw transaction, for every user, not just the attacker.

### Impact Explanation
Any accrued wom reward routed through the `isMWOM` fee branch forces a call into `smartConvert`. If an attacker sandwiches the `womMWomPool` to make the buyback leg net below `_amountIn`, `deposit`, `depositLP`, and `withdraw` all revert for every caller on that pool until the manipulated ratio/pool state is unwound. Since `withdraw()` is blocked, principal (and unclaimed yield sitting in the rewarder queue) cannot be retrieved — this matches "Temporary freezing of funds" (High), and is repeatable each time a user attempts to interact while the attacker maintains/re-applies the manipulation.

### Likelihood Explanation
- No privileged role is required: `womMWomPool`/router swaps are public, and `deposit`/`depositLP`/`withdraw` are called by ordinary users, involuntarily triggering the vulnerable internal call.
- The precondition is that `smartWomConverter` is configured and the `isMWOM` fee is active — this is the intended production configuration for the mWom fee-conversion feature, not an attacker-induced misconfiguration.
- The attack is capital-bounded by the depth of `womMWomPool`, but can be repeated across blocks/transactions at the cost of swap fees/slippage, and only needs to nudge the ratio near `buybackThreshold` (9000/10000) or the cash/liability gap, not fully drain the pool.

### Recommendation
Do not use the caller's full `_amountIn` as `_minRec` for the buyback leg. Instead:
- Compute an expected/quoted `amountRec` off-chain or via a TWAP-resistant on-chain quote, and only revert if the shortfall exceeds a defined slippage tolerance rather than requiring `>= _amountIn`.
- Wrap `IConverter(smartWomConverter).smartConvert(...)` in `WombatStaking._sendRewards` with a try/catch (or make the mWom conversion optional/best-effort with a plain `IMWom.deposit` fallback) so that a revert in the discretionary buyback path can never block `deposit`, `depositLP`, `withdraw`, or `harvest`.
- Consider adding slippage protection (`minOut > 0`) to the internal `swapExactTokensForTokens` call itself, decoupled from the top-level `_minRec == _amountIn` check.

### Proof of Concept
Hardhat test plan (mock Wombat pool/router + `SmartWomConvert` + `WombatStaking`):
1. Deploy mock `IWombatRouter`/`IAsset`/`IMWom` and `SmartWomConvert` with `buybackThreshold = 9000`.
2. Fund the mock pool so `currentRatio()` initially returns >= 9000 (no buyback branch, deposits succeed).
3. Simulate a sandwich: have an "attacker" call the mock router's public swap function (or set mock state) to push `womAsset.cash`/`liability` and the mWom↔wom exchange rate such that `currentRatio() < 9000` and the subsequent `swapExactTokensForTokens` call (invoked inside the same `smartConvert` call) returns `amountRec` such that `convertAmount + amountRec < _amountIn`.
4. Call `WombatStaking.deposit(...)` (with `isMWOM` fee active) or `smartConvert` directly with a nonzero `_amountIn`.
5. Assert the call reverts with `MinRecNotMatch()`.
6. Assert that in the same manipulated state, a normal user's `withdraw()` call on the pool also reverts (propagated via `_toMasterWomAndSendReward` → `_sendRewards` → `smartConvert`), demonstrating principal is frozen despite the caller holding sufficient receipt tokens/liquidity.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
