### Title
`updateEndRemainingAllocation()` can be re-called to reset the bonus-denominator snapshot after it has already been set, letting a late claimant fix an artificially low denominator and steal a disproportionate share of `totalBonus` - ([File: rewards/Airdrop.sol])

### Summary
`updateEndRemainingAllocation()` unconditionally overwrites `totalEndRemainingAllocation` with the current `totalRemainingAllocation` any time it is called after `periodsEndTime[4]`, with no guard preventing re-invocation once the snapshot has already been taken [1](#0-0) . Because `claim()` only auto-triggers this snapshot when `totalEndRemainingAllocation == 0`, any unprivileged address can wait until other users have already claimed (shrinking `totalRemainingAllocation`), then call `updateEndRemainingAllocation()` directly right before its own `claim()`, fixing a much smaller denominator for its own `getBonusAmount()` computation [2](#0-1) . Since `totalBonus` is never decremented as bonuses are paid out, and the denominator is not immutable, the sum of bonus payouts across all claimants is no longer guaranteed to equal `totalBonus`, breaking the accounting invariant and letting the manipulator drain a disproportionate amount of the shared `aidropToken` balance at the expense of later legitimate claimants.

### Finding Description
The bonus math is: `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation`, intended to distribute `totalBonus` proportionally among the users who still hold an allocation at the moment period 4 ends [3](#0-2) . This design only produces a correct partition of `totalBonus` if `totalEndRemainingAllocation` is captured exactly once, at the instant `periodsEndTime[4]` is reached, and never changes afterward.

In `claim()`, the snapshot is only taken lazily and guarded by `if (totalEndRemainingAllocation == 0)` [4](#0-3) . However `updateEndRemainingAllocation()` itself is a public, unguarded function with no check that the snapshot hasn't already been taken:

```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4]) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
``` [5](#0-4) 

Any unprivileged caller can invoke it repeatedly after `periodsEndTime[4]`, and each call resets `totalEndRemainingAllocation` to whatever `totalRemainingAllocation` currently is. Because every prior `claim()` call reduces `totalRemainingAllocation` (`totalRemainingAllocation -= userAllocation`, line 164), a caller who lets other users claim first, then calls `updateEndRemainingAllocation()` immediately before their own `claim()`, fixes a smaller denominator than the one used (or that should have been used) for everyone before them. Since `totalBonus` is only ever additive (incremented on forfeit at line 167, never reduced when bonus is paid out), there is no accounting mechanism preventing the sum of `bonusAmount` payouts from exceeding `totalBonus` once the denominator is manipulated downward mid-stream. The manipulator's `bonusAmount` can be inflated far beyond their fair share of `totalBonus`, funded out of the shared `aidropToken` balance that also backs other users' principal allocations, until `claimableAmount > aidropToken.balanceOf(address(this))` starts reverting for the remaining, honest, late claimants.

No modifier, reentrancy guard, or one-time-set flag prevents this re-invocation; the only zero-check exists inside `claim()`'s call-site, not inside the shared function itself.

### Impact Explanation
This breaks the stated invariant that `totalBonus` and `aidropToken.balanceOf(address(this))` must reconcile deterministically regardless of call ordering. A manipulator can extract more than their proportional share of `totalBonus`, taken directly from the token balance meant to back other users' principal allocations and bonuses, and can cause later, honest claimants to be unable to claim their full entitlement (reverting on `InsufficientBalance`) — a direct theft of/permanent freeze on other users' funds, matching the Critical "Direct theft of user funds" class.

### Likelihood Explanation
No privileged role is required — `updateEndRemainingAllocation()` and `claim()` are both unrestricted external/public functions callable by any EOA holding a nonzero allocation. The only precondition is reaching `periodsEndTime[4]` and having at least one prior claim/forfeit event lower `totalRemainingAllocation` (or `totalBonus` accumulated from forfeits) before the manipulator's own `claim()`, which is a natural and likely condition once the airdrop enters its final period with many participants claiming at different times. The attack costs only gas and is trivially repeatable by any late claimant who monitors the mempool or simply waits.

### Recommendation
Add a one-time-set guard directly inside `updateEndRemainingAllocation()` (e.g., `if (totalEndRemainingAllocation != 0) return;` or a boolean `snapshotTaken` flag) so the snapshot can only ever be written once, regardless of caller or call path, consistent with the guard already present in `claim()`. Additionally consider decrementing `totalBonus` proportionally as bonuses are paid out, or otherwise formally verifying that the sum of distributed `bonusAmount` cannot exceed the `totalBonus` recorded at snapshot time.

### Proof of Concept
Hardhat test plan:
1. Deploy `Airdrop` with `startTime` in the near future; register several users (`A`, `B`, `C`, attacker `M`) with allocations via `register()`.
2. Warp time to `periodsEndTime[4]`.
3. Run A: have `A` and `B` call `claim()` normally (each internally calling `updateEndRemainingAllocation()` once via the zero-guard, forfeiting nothing or some amount so `totalBonus` grows) — record final `totalBonus` and `aidropToken.balanceOf(airdrop)`.
4. Run B (differential): reset to same initial state; have `A` and `B` claim first (reducing `totalRemainingAllocation`), then have attacker `M` directly call `updateEndRemainingAllocation()` (re-snapshotting to the now-smaller `totalRemainingAllocation`) before calling `claim()`.
5. Assert that in Run B, `M`'s `bonusAmount` (from `getBonusAmount(M)` before claim) is strictly greater than what `M` would have received in Run A with the original snapshot, and that total bonus paid out across all claimants in Run B exceeds `totalBonus` recorded at the true end-of-period snapshot, or that a later legitimate claimant's `claim()` reverts with `InsufficientBalance` in Run B while it succeeds in Run A.
6. This demonstrates `totalBonus` and `aidropToken.balanceOf(address(this))` no longer reconcile identically between the two economically-equivalent execution orders.
