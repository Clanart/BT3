### Title

Empty DLEq relations are accepted as valid proofs - ([File: crypto/dleq/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary

`DLEqProof::verify` only checks that `generators.len() == points.len()` before calculating the Fiat-Shamir challenge. Both slices may therefore be empty, producing a proof that claims equality of discrete logarithms across no points at all. A proof created with `DLEqProof::prove` over an empty generator list verifies successfully, letting a caller forge a valid proof for an empty relation.

### Finding Description

`DLEqProof::verify` rejects mismatched statement lengths, but does not reject the zero-statement case. After `transcript.domain_separate(b"dleq")`, the iteration over `generators.iter().zip(points)` adds no statements, and verification reduces to checking that `self.c` equals the context-derived challenge. [1](#0-0) 

`DLEqProof::prove` has the corresponding behavior: for an empty `generators` slice, it writes no generator, nonce, or point to the transcript, calculates `c`, and returns `s = r + c * scalar` even though no statement was proven. [2](#0-1) 

This is analogous to the RDS state-machine error path: the protocol accepts a terminal/degenerate condition without enforcing the invariant that at least one valid relation must exist before entering the successful-verification state.

### Impact Explanation

Any application that derives the `generators`/`points` vectors from protocol input and permits them to become empty can accept a forged DLEq proof for an arbitrary scalar. The forged proof verifies without demonstrating knowledge of, or equality between, any discrete logarithm.

The in-scope generator-promotion path currently supplies two generators and two points, so that specific call site is not exploitable through an empty relation. [3](#0-2)  The vulnerable behavior nevertheless exists in the public `DLEqProof::verify` API and affects any other verifier that can reach it with an empty relation.

### Likelihood Explanation

An unprivileged party only needs to cause a verifier to evaluate a zero-length statement list. Verification APIs that dynamically construct statement vectors, filter invalid statements, or treat “nothing to verify” as success are susceptible. The issue is not exploitable at the current fixed-size `GeneratorPromotion::complete` call site.

### Recommendation

Reject empty statement relations in both `DLEqProof::prove` and `DLEqProof::verify`. Add `generators.is_empty()` and `points.is_empty()` checks before calculating the challenge. Apply the same invariant to inner vectors in `MultiDLEqProof`, which similarly permits each individual relation to contain zero generator/point pairs. [4](#0-3) 

### Proof of Concept

```rust
use zeroize::Zeroizing;
use rand_core::OsRng;
use transcript::RecommendedTranscript;
use dleq::DLEqProof;
use dalek_ff_group::Ristretto;
use ciphersuite::Ciphersuite;

// Any scalar is sufficient: no statement is actually proven.
let scalar = Zeroizing::new(<Ristretto as Ciphersuite>::F::ONE);

let forged = DLEqProof::prove(
  &mut OsRng,
  &mut RecommendedTranscript::new(b"empty relation"),
  &[],
  &scalar,
);

assert!(
  forged
    .verify(
      &mut RecommendedTranscript::new(b"empty relation"),
      &[],
      &[],
    )
    .is_ok()
);
```

This produces a syntactically valid proof whose challenge is bound only to the transcript context, not to any claimed generator or point.

  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[G],
    points: &[G],
  ) -> Result<(), DLEqError> {
    if generators.len() != points.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"dleq");
    for (generator, point) in generators.iter().zip(points) {
      Self::verify_statement(transcript, *generator, *point, self.c, self.s);
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }
