## Analysis

The HAL-01 report's core issue is a **broken invariant**: a value used to gate a state-changing operation (`amountOutMinimum`) is computed from data that an adversary can influence, and the code trusts it without an independent, tamper-resistant check.

The closest structural analog I could find in this GitHub Desktop codebase is not a price-manipulation bug (irrelevant to a git client) but a **safety-check bypass for submodule transport**: Desktop explicitly re-enables `file://` protocol support for submodule operations, which is exactly the class of vulnerability Git itself patched via `protocol.file.allow` (CVE-2022-39253) because it lets a malicious repository's `.gitmodules` cause the client to read/clone from arbitrary local paths. [1](#0-0) 

### Title
Submodule updates unconditionally re-enable `file://` protocol, allowing attacker-controlled repositories to read/exfiltrate local paths - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation()` accepts an `allowFileProtocol` boolean and, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation, which overrides Git's own hardened default (introduced after CVE-2022-39253) that disallows `file://` submodule URLs by default. [2](#0-1) 

### Finding Description
Git added `protocol.file.allow=user` as the default in response to a class of bugs where a cloned/fetched repository could declare a submodule with a `file://` URL (or a local path) pointing at an arbitrary location on the victim's filesystem (e.g. `file:///home/victim/.ssh`, or a relative path that escapes the checkout via `../../..`). When such a submodule is initialized, Git will happily "clone" that local directory into the submodule's working tree, exposing its contents inside the parent repository — which the user may then browse, diff, or even commit/push, exfiltrating the data to a remote the attacker controls.

Desktop's `updateSubmodulesAfterOperation()` in `app/src/lib/git/submodule.ts` takes a caller-supplied `allowFileProtocol: boolean` flag; when set, it unconditionally adds `-c protocol.file.allow=always` to the submodule-update command, re-enabling exactly the behavior Git hardened against. [3](#0-2) 

This is called from at least two locations that also carry the same flag — `app/src/lib/git/checkout.ts` (4 matches for `allowFileProtocol`) — meaning ordinary checkout/clone/pull flows can pass `true` for repositories whose provenance is entirely attacker-controlled (a cloned or fetched repository whose `.gitmodules`/tree the user does not author). Unlike the `Payments.swapStableToBCUT()` case — where `_getAmountOut()`'s stale price is at least computed on-chain immediately before the swap — here the "guard" (`protocol.file.allow`) exists specifically to stop this attack, and the code actively disables it rather than merely failing to refresh a stale value.

I was not able to fully verify, within this session, the exact conditions under which `checkout.ts` passes `allowFileProtocol: true` for a normal (non-test) checkout/clone/pull of a remote-supplied repository — this would require reading the full contents of `app/src/lib/git/checkout.ts`, which I did not get to examine before running out of tool calls. That file should be reviewed directly to confirm whether the flag is gated on some trust signal (e.g. same-origin submodule URLs) or whether it is passed unconditionally for any repository the user clones/pulls.

### Impact Explanation
If `allowFileProtocol: true` is reachable for a repository that the user simply clones or pulls (i.e., content fully controlled by a remote/attacker), a malicious `.gitmodules` entry can:
- Read arbitrary files/directories outside the intended repository (credential stores, SSH keys, other repositories) into the submodule working tree.
- Silently corrupt/populate what the user later commits and pushes, exfiltrating local file-outside-repo content to an attacker-controlled remote once the user stages and pushes the submodule contents.

This matches the "Valid Impact" criteria: file read outside the repo and possible credential exfiltration, triggered purely by cloning/fetching an attacker-controlled repository — no local access, admin rights, or social engineering beyond "clone this repo" is required.

### Likelihood Explanation
Likelihood depends entirely on whether the call sites in `checkout.ts` pass `allowFileProtocol: true` for untrusted, user-cloned/pulled repositories rather than only for internal/test-controlled flows. The test fixtures/helpers explicitly rely on `protocol.file.allow=always` for local-fixture submodule setup [4](#0-3) , which shows the app-level plumbing for this flag is exercised by real application code paths (`checkout.ts`, `submodule.ts`), not only by tests. Confirming exploitability in production requires inspecting the exact call sites and their gating logic in `checkout.ts`.

### Recommendation
- Default `allowFileProtocol` to `false` for any submodule update triggered by operations on repositories obtained from an untrusted remote (clone, fetch, pull, checkout of a branch not authored locally).
- Only allow `file://` submodule protocol for scenarios fully under the application's control (e.g., internal test fixtures), and require explicit user confirmation (similar to the existing "repository appears to be owned by another user… may automatically execute files" trust prompt shown in `add-existing-repository.tsx`/`missing-repository.tsx`) before ever enabling it for real user repositories. [5](#0-4) 

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` file with an entry such as:
   ```
   [submodule "leak"]
     path = leak
     url = file:///Users/victim/.ssh
   ```
2. Victim clones or pulls the repository in GitHub Desktop, and Desktop's submodule-update flow invokes `updateSubmodulesAfterOperation` with `allowFileProtocol: true` (path to confirm in `checkout.ts`).
3. The generated command effectively becomes:
   ```
   git -c protocol.file.allow=always submodule update --init --recursive
   ```
   which permits Git to "clone" `/Users/victim/.ssh` into the `leak/` submodule directory. [6](#0-5) 
4. The victim's `.ssh` directory contents now appear as tracked files in the Desktop working copy; if the victim stages/commits/pushes (or even just browses/exports via Desktop), the data can be exfiltrated to the attacker's remote or read by any process with access to the checkout.
