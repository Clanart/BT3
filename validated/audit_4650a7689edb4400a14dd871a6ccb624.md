### Title
BEEFY consensus client ignores the caller-supplied `consensus_state_id`, letting one registered client's verified proof overwrite another client's state-commitment slot - (File: modules/ismp/clients/beefy/src/consensus.rs)

### Summary
`BeefyConsensusClient::verify_consensus` takes `_consensus_state_id` as a parameter but never uses it. Instead, at lines 152-158 it recomputes the `consensus_state_id` to insert into `VerifiedCommitments` purely from `host.host_state_machine()`, hardcoding it to `PASEO_CONSENSUS_STATE_ID` for a Kusama-hosted deployment or `POLKADOT_CONSENSUS_STATE_ID` for a Polkadot-hosted deployment: [1](#0-0) 

### Finding Description
The generic ISMP `ConsensusClient` trait is invoked by `update_client` with the actual `msg.consensus_state_id` that was used to look up both the concrete client implementation and the trusted consensus state to verify against: [2](#0-1) 

Every other consensus client implementation in this codebase (GRANDPA, BSC, Optimism, sync-committee/beacon, Pharos, Tendermint) correctly threads the passed-in `consensus_state_id` argument into the `StateMachineId` key that tags the resulting verified commitment, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) 

The BEEFY client is the outlier: it discards the argument (`_consensus_state_id`) and substitutes a fixed constant selected only by which chain Hyperbridge itself is deployed on, not by which registered consensus state actually presented/verified the proof: [6](#0-5) [7](#0-6) 

Consequence: if governance ever registers a second consensus state (e.g. `create_client` with a different `consensus_state_id`, but `consensus_client_id = BEEF`, as is architecturally supported — `ConsensusStateClient` maps arbitrary `ConsensusStateId -> ConsensusClientId` many-to-one) — any unprivileged relayer who submits a *valid* BEEFY proof against that second registration's own trusted state will have the resulting verified parachain state commitments silently written into the hardcoded `POLKADOT_CONSENSUS_STATE_ID`/`PASEO_CONSENSUS_STATE_ID` slot instead of the slot for the `consensus_state_id` that was actually verified: [8](#0-7) 

This breaks the core invariant that a `StateMachineId{state_id, consensus_state_id}` commitment must only ever be attributed to the exact consensus state/trust root that produced it. It defeats the entire purpose of maintaining independently-configured consensus states (each with its own unbonding period, challenge period, and frozen/expired status) for the same underlying relay chain family, since any of them can inject commitments into any other's namespace without their being frozen, expired, or otherwise compromised themselves — the values just land in the wrong bucket unconditionally, on every single successful call.

### Impact Explanation
If a secondary/backup/staging BEEFY consensus state is ever registered for redundancy or migration purposes (a legitimate and architecturally-supported operation via `create_client`), a normal, unprivileged relayer submitting a completely valid consensus proof against that secondary trust root will have its output commingled into the primary `DOT0`/`PAS0` client's commitment namespace. This can let state finalized under a different security/challenge-period configuration be accepted as if it came from the primary, differently-configured trust root, potentially bypassing the intended challenge-period/freeze semantics of the primary client and enabling downstream ISMP request/response state proofs to be accepted against commitments that were never actually produced under the primary consensus state's own verification path.

### Likelihood Explanation
Exploitability strictly depends on more than one `consensus_state_id` being registered against the BEEFY consensus client (`consensus_client_id = BEEF`) at the same time, which requires a privileged `create_client` action to set up. This is a plausible, architecturally supported operational pattern (multiple registrations pointing at the same client id are explicitly represented in storage via `ConsensusStateClient`), but I could not find evidence in this snapshot that the production Gargantua/Nexus runtimes actually register more than one BEEFY consensus_state_id simultaneously — I was unable to fully verify current production `create_client` invocations within the remaining tool budget. Given the scope explicitly excludes assumptions requiring compromised/malicious infrastructure, and requires only *unprivileged* input to trigger the bad state once the precondition (multiple registered ids) exists, this is a real broken invariant in the code (confirmed by contrast with every sibling consensus client's correct handling of the same parameter) but its real-world reachability hinges on an operational/governance decision to register a second BEEFY-backed consensus state, which I could not confirm currently exists in the live deployment.

### Recommendation
Use the passed-in `_consensus_state_id` parameter (rename it to drop the underscore) instead of recomputing a hardcoded constant from `host.host_state_machine()` when constructing `StateMachineId` in the loop at lines 152-172, matching the pattern used by `GrandpaConsensusClient`, `BscConsensusClient`, and other clients in this repo.

### Proof of Concept
1. Governance calls `create_client` twice for the BEEFY consensus client (`consensus_client_id = BEEF`): once with `consensus_state_id = "DOT0"` and once with `consensus_state_id = "DOT1"`, each with its own trusted BEEFY consensus state (both tracking Polkadot, e.g. one as primary and one as a staged/rotated backup).
2. An unprivileged relayer submits `update_client` with `msg.consensus_state_id = "DOT1"` and a BEEFY/parachain proof that is valid against `DOT1`'s stored trusted state.
3. Inside `verify_consensus`, `_consensus_state_id` (`"DOT1"`) is discarded; at lines 152-158 the code observes `host.host_state_machine() == StateMachine::Polkadot(_)` and hardcodes `consensus_state_id = POLKADOT_CONSENSUS_STATE_ID` (`"DOT0"`).
4. The verified intermediate state is inserted as `StateMachineId { state_id: StateMachine::Polkadot(para_id), consensus_state_id: "DOT0" }` and persisted via `host.store_state_machine_commitment` in `update_client`, even though `"DOT0"`'s own trust root never verified this proof — only `"DOT1"`'s did.
