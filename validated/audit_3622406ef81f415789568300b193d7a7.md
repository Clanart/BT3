### Title
Griefing/invariant corruption of ERC20↔Coin bridge accounting via open, permissionless `burn`/`burnFrom` on `ERC20MinterBurnerDecimalsContract` - (File: contracts/solidity/ERC20MinterBurnerDecimals.sol)

### Summary
`ERC20MinterBurnerDecimals.sol`, the contract the `x/erc20` module deploys/uses for both the mint-and-burn (native coin) and lock-and-mint (native ERC20) bridging flows, inherits OpenZeppelin's `ERC20Burnable` while also defining a separate, role-gated `burnCoins`. `ERC20Burnable` exposes public `burn(uint256)` and `burnFrom(address,uint256)` with **no access control**, exactly mirroring the Tapioca `OTAP.burn` bug: a permissionless burn path exists alongside a privileged one that the keeper's accounting invariants assume is the only way supply changes.

### Finding Description
`x/erc20/keeper/msg_server.go`'s `convertERC20IntoCoinsForNativeToken` and `ConvertCoinNativeERC20` assume the ERC20 contract's balance/supply only changes through `transfer`/`mint`/`burnCoins` calls issued by the keeper itself, and they enforce this via explicit before/after balance-diff invariant checks: [1](#0-0) [2](#0-1) 

However, because `ERC20MinterBurnerDecimals` inherits `ERC20Burnable`, any holder — including the module account itself or a user who has ERC20 tokens escrowed/minted to them mid-flow — can call the open `burn`/`burnFrom` functions directly, bypassing the keeper entirely: [3](#0-2) [4](#0-3) 

The role-gated `burnCoins` (only callable by `BURNER_ROLE`, i.e., the module) is clearly intended as *the* controlled burn path used to keep ERC20 supply/escrow in sync with bank `Coins`, but `ERC20Burnable`'s open `burn`/`burnFrom` sit right next to it with no role check, so the "single controlled burn path" invariant is not actually enforced at the contract level — identical in shape to the Tapioca `OTAP` contract having both a controlled burn (called from `TOB.exitPosition`) and an open, permissionless `burn` that any token owner/approved party could call directly.

Concretely, for a `TokenPair` where `pair.IsNativeERC20()` (external owner), the bridge model is: user calls `ConvertERC20` → tokens are `transfer`'d from user to `types.ModuleAddress` (escrow) → bank `Coins` are minted 1:1 to the receiver. Later, `ConvertCoin` reverses this: bank `Coins` are escrowed to the module, module `transfer`s escrowed ERC20 tokens back to the receiver, and finally the escrowed `Coins` are burned: [5](#0-4) 

If any party holding tokens that back this escrow (or the module's own escrowed balance, if the module is ever granted no special protection against being called by others with allowance, or more directly if a user still holding minted ERC20 tokens post-`ConvertCoin`/pre-transfer calls `burn`) invokes the open `burn`, the ERC20 total supply is permanently reduced without a corresponding reduction of outstanding bank `Coins` (or vice-versa for the escrowed balance). This breaks the 1:1 backing invariant the bridge depends on: outstanding bank `Coins` for that denom become permanently over-collateralized relative to redeemable ERC20 supply, so some `Coins` holders can never successfully complete `ConvertCoin` (the balance-diff invariant check in `ConvertCoinNativeERC20` will start failing with `ErrBalanceInvariance` once the escrow balance is insufficient), effectively freezing part of the escrowed/owed value.

### Impact Explanation
This falls under "Critical permanent freezing/locking of token-pair-backed balances" and "irreversible accounting corruption of spendable user value": once the ERC20 supply backing a `TokenPair`'s bank `Coins` is unilaterally reduced via the open `burn`, the affected `Coins` holders can be permanently unable to convert back to the underlying ERC20 (module-controlled `ConvertCoinNativeERC20` will fail its balance invariant), and there is no reconciliation or governance path in the reviewed code to detect/repair the mismatch other than the pair being deleted on self-destruct (a different code path).

### Likelihood Explanation
Any ERC20 holder for a registered `TokenPair` (an unprivileged, permissionless actor — `RegisterERC20` can itself be permissionless when `params.PermissionlessRegistration` is set) can trigger this by simply calling `burn`/`burnFrom` on their own balance or on an approved balance, exactly as in the original Tapioca report. This requires no privileged role, relayer, or validator collusion.

### Recommendation
Remove or gate the inherited `ERC20Burnable` `burn`/`burnFrom` functions in `ERC20MinterBurnerDecimals.sol` so that all burns must go through the `BURNER_ROLE`-gated `burnCoins`, consistent with the mitigation Tapioca applied (disable open burn; only allow the privileged/module-controlled path to call it). Additionally, add invariant/telemetry checks in `x/erc20` keeper flows that detect ERC20 total-supply drift for `OWNER_EXTERNAL`/`OWNER_MODULE` pairs outside of keeper-controlled transfers.

### Proof of Concept
1. Register a `TokenPair` for an ERC20 deployed from `ERC20MinterBurnerDecimalsContract` (e.g., via `RegisterERC20`).
2. User mints/acquires ERC20 tokens and calls `ConvertERC20` to lock tokens in `types.ModuleAddress` and mint corresponding bank `Coins`.
3. Before further `ConvertCoin` calls exhaust the escrow, an attacker (any holder with an ERC20 balance/allowance related to the pair) calls the contract's inherited `burn(amount)` or `burnFrom(holder, amount)` directly on the ERC20 contract — bypassing `x/erc20` keeper entirely (no ante/msg-server involvement needed, this is a raw EVM call).
4. Total ERC20 supply/escrow balance decreases while previously-minted bank `Coins` remain unchanged.
5. Subsequent `ConvertCoin` calls for the affected denom fail with `ErrBalanceInvariance` in `ConvertCoinNativeERC20`'s balance-diff check [2](#0-1) , permanently freezing the remaining Coins holders' ability to redeem into the underlying ERC20.

**Uncertainty note:** I was not able to fully trace every code path that grants the module's own escrow balance (`types.ModuleAddress`) protection (or lack thereof) against third-party `burnFrom` calls (which would require an ERC20 allowance from the module account), nor whether `PermissionlessRegistration` is enabled by default in this deployment's genesis params — these details affect exact exploitability/severity and would benefit from a full Devin session with repository access to confirm at runtime.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}
