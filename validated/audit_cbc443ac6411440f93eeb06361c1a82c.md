### Title
Divergent conflict-marker boundary detection between context extraction and AI-resolution splicing lets a crafted merged file silently corrupt what the user commits - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`DLoopCoreBase::_deposit()` trusts a *count*/tolerance check (`observedDiffBorrow` within `BALANCE_DIFF_TOLERANCE` of `amount`) instead of the *actual* value, then acts on the wrong value downstream, causing a revert or fund loss. GitHub Desktop's Copilot merge-conflict-resolution feature has the same broken-invariant shape: it validates only the *count* of conflict hunks returned by the model, never the exact boundaries/content, while two independent pieces of code compute those boundaries with different heuristics. A crafted conflicted file can make the two heuristics disagree, so the AI's per-hunk resolutions get spliced into the wrong regions of the file that is written to disk and staged for commit.

### Finding Description
`extractConflictHunks` (app/src/lib/copilot-conflict-context.ts:179-279) parses a conflicted file once, sequentially: for each `<<<<<<<` marker it consumes lines until the *first* line matching `^={7}$` (or a `|||||||` base marker), then consumes until the *first* line matching the theirs marker. The resulting hunk count (`file.hunks.length`) is sent to the Copilot prompt as "Conflict i of N" (app/src/lib/copilot-conflict-context.ts:560-562) and is used later as the ground truth in `validateResolutionPaths` (app/src/lib/copilot-conflict-resolution.ts:509-520), which only compares `resolution.hunks.length !== expectedCount`.

`reassembleResolvedFile` (app/src/lib/copilot-conflict-resolution.ts:549-599), which actually splices the model's `resolvedContent` back into the on-disk file, uses a *different* boundary heuristic: it scans ahead from a `<<<<<<<` line and sets `hasSeparator = true` if **any** line anywhere before the next theirs-marker matches `^={7}$` [1](#0-0) , then treats the **first** theirs-marker line as the block's `closingIndex` and slices the whole span with `i = closingIndex + 1` [2](#0-1) . It has no awareness of the `|||||||` diff3 base marker at all, unlike `extractConflictHunks`, which explicitly handles it [3](#0-2) [4](#0-3) .

Because both functions independently re-derive hunk boundaries from the raw text using "first match wins" heuristics rather than sharing computed offsets, a file whose ours/theirs content legitimately contains a line that is exactly seven `=` characters (a common divider in Markdown/RST/ASCII banners/changelogs) or a diff3-shaped run can make `extractConflictHunks` and `reassembleResolvedFile` disagree about where one hunk ends and the next begins, while still reporting the *same total hunk count* — the only thing `validateResolutionPaths` checks [5](#0-4) . The model's resolution for "hunk N" (matched purely by array index, per the docstring "matched by order, not by line number" [6](#0-5) ) is then spliced against boundaries it was never computed for.

The corrupted result flows straight to disk and into the index with no further check: `_applyCopilotConflictResolutions` calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and then `git add` [7](#0-6) . The only existing guard that could catch a mismatch — `validateResolutionPaths`'s count check — does not, since it never inspects boundaries or content, exactly mirroring how `_deposit()`'s tolerance check let a wrong `observedDiffBorrow` slip through and then be used inconsistently downstream.

### Impact Explanation
This is a "silent corruption of what the user commits or pushes" scenario: the merged file written and staged can contain misaligned source lines and AI-resolved text (e.g. dropped hunks, duplicated lines, or one side's code injected into the wrong location), while the UI only shows the model's narrative summary/reasoning, not a verified diff of the actual splice. If the user accepts and pushes, this ships incorrect/broken code (or reintroduces removed security-relevant lines, or silently drops a hunk's change) without any error being raised — there is no crash to alert the user, unlike the original report's DoS case.

### Likelihood Explanation
Requires only that a conflicted file (introduced by a branch/fork the attacker controls, e.g. a PR the victim later merges) contain, inside one of the two conflicting regions, a line that is exactly `=======` or a `|||||||`-shaped structure that isn't a real conflict marker — plausible in documentation about git, changelog dividers, RST underlines, or test/fixture files that themselves illustrate conflict markers. The victim must be using the Copilot conflict-resolution feature and accept the AI's resolution without manually diffing every hunk, which is the feature's intended fast-path usage. No local access, admin rights, or social engineering beyond a normal PR/merge is needed.

### Recommendation
Make `reassembleResolvedFile` consume the same `IConflictHunk` boundary data already computed by `extractConflictHunks` (offsets/line ranges) instead of re-scanning the raw text with an independent, looser heuristic. At minimum, unify the two marker-detection algorithms (identical "first-match" semantics, identical diff3 `|||||||` handling), and have `validateResolutionPaths` (or a post-reassembly check) verify that the number of `<<<<<<<...>>>>>>>` blocks actually consumed during reassembly equals `extractConflictHunks`'s count for that exact same file content, failing closed (falling back to manual resolution) rather than silently accepting a possibly-misaligned splice.

### Proof of Concept
1. Create a repository where a merge produces a conflict in a file whose *theirs* side contains a documentation/changelog block using a bare seven-equals divider, e.g.:
```
<<<<<<< HEAD
function real() { return ours(); }
=======
function real() { return theirs(); }
// Appendix
=======
Legacy notes
>>>>>>> feature
```
(a file discussing/documenting conflict markers, or a changelog with a `=======` section rule, produces this shape naturally when it collides with a real code conflict).
2. `extractConflictHunks` stops collecting "ours" at the *first* `=======` and "theirs" at the *first* `>>>>>>>`, yielding one hunk whose `theirsContent` is `function real() { return theirs(); }\n// Appendix` (the second `=======`/`Legacy notes` text truncated out or displaced).
3. `reassembleResolvedFile`'s lookahead independently finds `hasSeparator = true` from either `=======` occurrence and `closingIndex` at the same `>>>>>>>`, so the *count* still matches, but the model's `resolvedContent` — generated against the content `extractConflictHunks` sent it — gets spliced against boundaries derived from a scan that never validated it matched the exact text the model saw.
4. `validateResolutionPaths` only checks `resolution.hunks.length !== expectedCount`, which passes.
5. `_applyCopilotConflictResolutions` writes the spliced result to disk and runs `git add`, staging file content that does not match what the model actually reasoned about or what the dialog's summary describes, with no error surfaced to the user.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
