### Title
`Scanner::scan_transaction` reports arbitrarily small outputs as received funds, and the wallet's `DUST = 546` bound only reflects the relay minimum — outputs can be credited to the wallet that are economically unspendable, permanently locking value - (File: networks/bitcoin/src/wallet/mod.rs, networks/bitcoin/src/wallet/send.rs)

### Summary
`Scanner::scan_transaction` accepts any output paying to a registered script regardless of its value (`networks/bitcoin/src/wallet/mod.rs:199-214`), and the only amount check anywhere in the wallet is `DUST = 546` sats (`networks/bitcoin/src/wallet/send.rs:32`), which is merely Bitcoin's relay dust floor — not a spendability bound. This mirrors the audited bug class: a hard-coded economic threshold set far below the real cost of using the credited resource, so the system can report/accept "funds" that can never be profitably moved.

### Finding Description
In `Scanner::scan_transaction`, any transaction output whose `script_pubkey` matches a registered offset is pushed into the result as a `ReceivedOutput` with no minimum-value check (`mod.rs:205-211`). An unprivileged attacker can send a Bitcoin transaction paying, e.g., 546 sats (or even 1 sat — there is no floor at all) to the wallet's P2TR script, and the wallet will report it as received value.

Separately, in `SignableTransaction::new` (`send.rs:165-234`), the same `DUST = 546` constant is used to decide whether a change output is worth creating (line 229: `if value >= DUST`). A change output of 546 sats requires ~57 vbytes of witness/input data to spend (a Taproot key-path input is ~230 WU ≈ 57 vB); at any fee rate above ~9.5 sat/vB — routine during congestion — spending it costs more than it is worth. The same applies to attacker-supplied inputs: an output of value below `57 * fee_per_vbyte` sats that is reported by the scanner can never be profitably included, and including it forces `NotEnoughFunds` or silently subsidizes it from other inputs.

The protocol's own downstream code recognizes this exact hazard: `Bitcoin::DUST` in `processor/src/networks/bitcoin.rs:606-638` documents that a P2TR input costs ~57 vB to spend, that relay rules can be raised, and sets the acceptance floor to 10,000 sats ("order of magnitude" above spend cost) — but the in-scope wallet crate that actually performs scanning and transaction construction uses the bare relay minimum with no such margin.

### Impact Explanation
- Attacker-dusted outputs are reported by `scan_transaction`/`scan_block` as received wallet funds while being economically unspendable (cost to spend ≥ value), so the wallet's bookkeeping credits value it cannot realize.
- `SignableTransaction::new` can produce change outputs in `[546, spend_cost)` sats that are reported as received but can never be spent profitably — permanently burning wallet funds up to the difference.
- During high-fee periods (the same conditions as in the original report), the gap between the 546-sat bound and the true spend cost widens, increasing the amount of value stranded.

### Likelihood Explanation
Sending dust outputs to a watch-only P2TR script requires only a normal on-chain Bitcoin transaction — fully reachable by any unprivileged party with public inputs (a Bitcoin transaction they send). Triggering the unspendable-change path additionally requires the wallet to build transactions at elevated fee rates, which is the normal operating environment during congestion.

### Recommendation
Apply a spendability floor rather than the relay minimum in the wallet crate:
- Have `scan_transaction`/`scan_block` (or the `ReceivedOutput` consumer) filter out outputs below a value that covers the cost of spending them at a conservative fee rate (e.g., the ~10,000 sat margin the processor already adopted).
- In `SignableTransaction::new`, treat change below that same bound as fee rather than emitting an unspendable output, and reject or explicitly account for inputs whose value is below their spend cost at `fee_per_vbyte`.

### Proof of Concept
1. Compute the wallet's deposit script via `p2tr_script_buf(key)` and send a confirmed transaction with an output of `value = 600` sats to it.
2. `Scanner::scan_block(block)` returns a `ReceivedOutput` with `value() == 600` — reported as received funds.
3. At `fee_per_vbyte = 20` (below recent congestion levels), spending that input costs `57 vB * 20 = 1140` sats > 600 sats: `SignableTransaction::new` either returns `NotEnoughFunds` or consumes the subsidy from other inputs. The output can never be profitably spent and remains stranded value the scanner credited. The same math applies to a change output of 600 sats emitted via the `value >= DUST` check at `send.rs:229`.
