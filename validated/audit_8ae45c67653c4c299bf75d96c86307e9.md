## Title
Unbounded full-database scan via `getProgramAccounts` without a result-size limit causes single-request RPC node degradation - (File: `rpc/src/rpc.rs`)

### Summary
The reference bug is a Solidity DoS where an unprivileged caller supplies an attacker-controlled list (`creators`) that is iterated with per-item external calls whose cost is not bounded, letting a single call blow past a fixed resource ceiling (the block gas limit). The Agave analog is `getProgramAccounts`: an unprivileged RPC client supplies a single `program_id`, and when the (default, opt-in) secondary `ProgramId` account index is not enabled, the server performs a full linear scan of the *entire* accounts database and materializes every matching account, with no byte/result-size limit applied — unlike the indexed path, which does enforce `scan_results_limit_bytes`.

### Finding Description
`get_program_accounts` in `rpc/src/rpc.rs` dispatches to `get_filtered_program_accounts`: [1](#0-0) 

When the node's `account_indexes` does not contain `AccountIndex::ProgramId` (this index is disabled by default and must be explicitly enabled via validator config), the code falls into the `else` branch, which calls `bank.get_filtered_program_accounts(&program_id, filter)` inside a `spawn_blocking` task, with an explicit comment acknowledging no byte limit is applied on this path: [2](#0-1) 

`Bank::get_filtered_program_accounts` forwards to `Accounts::load_by_program_with_filter`, which performs `scan_accounts` over the whole `AccountsDb` (all accounts owned by any program), filtering by `owner()` only inside the scan callback with `ScanConfig::default()` (no abort/size limit): [3](#0-2) [4](#0-3) 

Contrast this with the indexed lookup path (`get_filtered_indexed_accounts`), which explicitly threads a `byte_limit_for_scans` value from `self.config.scan_results_limit_bytes` and aborts the scan once results exceed that size, via `accumulate_and_check_scan_result_size` / `maybe_abort_scan`: [5](#0-4) [6](#0-5) 

The un-indexed `get_filtered_program_accounts` fallback has no equivalent guard — it iterates and collects every account in the database matching `owner() == program_id` into a `Vec` in memory before returning, unbounded by count or bytes.

### Impact Explanation
A single unprivileged client can send one `getProgramAccounts` request for a widely-owned program (e.g. the System Program, which owns the vast majority of accounts on a live cluster, or SPL Token) against any RPC node that has not enabled the `program-id` secondary account index (the default configuration). This forces the node to:
- Scan the full accounts index/storage (potentially tens of millions of accounts),
- Allocate and hold an unbounded `Vec<(Pubkey, AccountSharedData)>` of matching accounts in memory,
- Serialize/encode the entire result set to JSON.

This falls squarely into "single-client low-rate RPC crash/degradation": a single low-rate request can consume enough CPU and memory to degrade or crash the RPC node process, denying service to other RPC clients on that node — the direct analog of the Solidity report's single-call gas exhaustion via an unbounded, cost-unlimited loop.

### Likelihood Explanation
Likelihood is high for any RPC node that has not opted into the `program-id` account index (which is the out-of-the-box default), since the request requires no special privileges, no fee beyond a normal RPC call, and no on-chain state manipulation — only knowledge of a heavily-owned `program_id`, which is public information. The `spawn_blocking` isolates this from the async runtime thread pool but does not bound CPU/memory consumption of the scan itself, so a single such request can still exhaust node memory or starve the blocking-task thread pool used by other RPC calls.

### Recommendation
Apply the same `scan_results_limit_bytes` (or an equivalent per-request byte/count cap) to the un-indexed `get_filtered_program_accounts` fallback path in `rpc/src/rpc.rs`/`accounts-db/src/accounts.rs`, mirroring the abort mechanism already implemented for `load_by_index_key_with_filter`, so that a single `getProgramAccounts` call without a secondary index cannot unboundedly consume memory/CPU. Consider also documenting/enforcing that `getProgramAccounts` without filters and without the secondary index be rejected or rate/size-limited by default, consistent with community guidance to disable or restrict this call on public RPC endpoints.

### Proof of Concept
Not independently executed against a live cluster; this is derived from local code inspection. Conceptually:
1. Start a validator/RPC node with default configuration (no `--account-index program-id`).
2. Issue `getProgramAccounts` for the System Program (`11111111111111111111111111111111`) or another program owning a very large fraction of all accounts.
3. Observe that `get_filtered_program_accounts` takes the un-indexed branch and calls `bank.get_filtered_program_accounts`, which scans and collects every matching account with no size cap, unlike the indexed path guarded by `scan_results_limit_bytes`.

Note: I could not fully confirm the exact default value/wiring of `scan_results_limit_bytes` end-to-end (e.g., whether some deployments set a global scan limit elsewhere) due to index coverage limits on some config files; a Devin session with full repository access would be needed to trace `RpcJsonRequestProcessor` construction and confirm there is no other enforced cap on the un-indexed path before treating this as fully confirmed exploitable in all configurations.

        bank: &Arc<Bank>,

        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(

    async fn get_filtered_program_accounts(
        &self,
        bank: Arc<Bank>,
        program_id: Pubkey,
        mut filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> RpcCustomResult<Vec<(Pubkey, AccountSharedData)>> {
        optimize_filters(&mut filters);
        if self
            .config
            .account_indexes
            .contains(&AccountIndex::ProgramId)
        {
            if !self.config.account_indexes.include_key(&program_id) {
                return Err(RpcCustomError::KeyExcludedFromSecondaryIndex {
                    index_key: program_id.to_string(),
                });
            }
            self.get_filtered_indexed_accounts(
                &bank,
                &IndexKey::ProgramId(program_id),
                &program_id,
                filters,
                sort_results,
            )
            .await
            .map_err(|e| RpcCustomError::ScanError {
                message: e.to_string(),
            })
        } else {
            // this path does not need to provide a mb limit because we only want to support secondary indexes
            let mut accounts = self
                .runtime
                .spawn_blocking(move || {
                    bank.get_filtered_program_accounts(
                        &program_id,
                        |account: &AccountSharedData| {
                            filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                        },
                    )
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })
                })
                .await
                .expect("Failed to spawn blocking task")?;
            if sort_results {
                // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
                accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
            }
            Ok(accounts)
        }
    }

    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    fn maybe_abort_scan(
        result: ScanResult<Vec<KeyedAccountSharedData>>,
        config: &ScanConfig,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        if config.is_aborted() {
            ScanResult::Err(ScanError::Aborted(
                "The accumulated scan results exceeded the limit".to_string(),
            ))
        } else {
            result
        }
    }

    pub fn load_by_index_key_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }
