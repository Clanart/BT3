### Title
Invalid DKG share blame misattributes sender's encryption fault to the honest accuser, fatally slashing an honest validator - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`BlameMachine::blame_internal` assumes that a decryption failure during blame verification always means the accusing recipient supplied a wrong ECDH key, and returns `recipient` as the faulty party. A malicious sender can craft an `EncryptedMessage` that is undecryptable under the recipient's correct key; the honest recipient's accusation then bounces back onto itself and it is removed from the validator set — the same class as CVE-2023-20882, where a transport fault is wrongly attributed to a healthy party which is then pruned from the pool.

### Finding Description
In `calculate_share`, when a recipient cannot decrypt a sender's share (or the decryption statement fails in the `BatchVerifier`), the recipient emits `PedPoPError::InvalidShare { participant: l, blame: None }` blaming the sender `l`, and the processor escalates this as an `InvalidDkgShare` accusation (processor/src/key_gen.rs `CoordinatorMessage::VerifyBlame`).

The accusation is adjudicated by `blame_internal`: [1](#0-0) 

```
Err(DecryptionError::InvalidSignature) => return sender,
Err(DecryptionError::InvalidProof)    => return recipient,
```

- `InvalidSignature` covers a message not properly authenticated by the sender → sender blamed. Correct.
- `InvalidProof` covers **any** failure of `decrypt_with_proof` to recover the plaintext under the recipient's ECDH key → recipient blamed.

The second case conflates two distinct faults. The ECDH key proof only proves which key the recipient used; it cannot distinguish "the recipient revealed a wrong key" from "the sender never encrypted to the recipient's correct key". A faulty sender can encrypt the share under a wrong/ephemeral-mismatched key, or otherwise produce a ciphertext which fails decryption under *any* key, while still correctly signing the envelope. The honest recipient's accusation is then adjudicated against the recipient itself.

The upstream consequence is severe: `ProcessorMessage::Blame { participant: accuser }` (processor/src/key_gen.rs:563) is converted to `Transaction::RemoveParticipantDueToDkg`, which increments `VotesToRemove` and, at threshold `t`, calls `fatal_slash` on the participant (coordinator/src/tributary/handle.rs:281-283), permanently removing the honest validator and reducing `present_shares` — with an explicit infinite-loop halt if remaining shares drop below `t` (coordinator/src/tributary/scanner.rs:271-279).

### Impact Explanation
Denial of service via wrongful removal. Each dishonest DKG dealer can cause the fatal slashing of one honest validator per accusation, simply by sending it an undecryptable share instead of a valid one. This exactly mirrors the CVE: a fault on the sender's side causes the healthy "backend" (honest validator) to be marked failed and removed from the pool. Repeated across dealers, `present_shares` can be driven below `t`, permanently halting the Tributary (`scanner.rs` spins forever logging "we no longer meet the threshold"). The removed validator also loses its stake/slash status despite correct behavior.

### Likelihood Explanation
Reachable by any DKG participant sending attacker-controlled bytes that flow through `EncryptedMessage::read` → `calculate_share` → `blame` — all explicitly in-scope public-input surfaces. The attack requires no collusion: a single faulty sender triggers it deterministically. It does require the sender to be a validator in the DKG set, and exploitation is bounded by the number of honest validators it can get to accuse it; each successful exploitation also requires the victim to actually file blame (which is the protocol-mandated response to an undecryptable share). Rated Medium: the per-instance cost to the attacker is being slashed for its own malformed share only if adjudication went the other way — here adjudication protects the attacker instead.

Note on confidence: this rests on `DecryptionError::InvalidProof` being returned whenever decryption under the revealed key fails, including when the ciphertext was never validly encrypted to that key. If `decrypt_with_proof` internally distinguishes "ciphertext malformed" from "wrong key" and blames the sender for the former, the flaw does not exist. The code comments ("Decryption will fail if the provided ECDH key wasn't correct for the given message" → `return recipient`) indicate no such distinction is made.

### Recommendation
In `blame_internal`, only blame the `recipient` when the recipient's ECDH key proof verifies *and* the ciphertext is well-formed but decrypts to a share inconsistent with the sender's commitments in a way attributable to the recipient. Specifically:

- Verify the sender's `EncryptedMessage` structure/signature first (already done via `InvalidSignature`).
- Have `decrypt_with_proof` return a third variant for "ciphertext undecryptable under the proven-correct key" and map it to `sender`, since a correct sender implementation always produces ciphertext decryptable by the intended recipient.
- The only case attributable to `recipient` is a valid-looking ciphertext that decrypts to a canonical, commitment-consistent share while the accuser claimed failure — i.e., an invalid ECDH key proof, not a generic decryption error.

### Proof of Concept
1. Honest validator `R` and malicious validator `S` participate in a PedPoP DKG round.
2. `S` constructs `EncryptedMessage<C, SecretShare>` for `R` such that it carries a valid Schnorr signature from `S`'s key, but the ciphertext/key encapsulation does not correspond to `R`'s encryption key (e.g., `S` ECDH-encrypts to a key other than the one `R` proved in its `EncryptionKeyMessage`).
3. `R` calls `KeyMachine::calculate_share` with all shares; the `BatchId::Decryption(S)` statement fails in `batch.verify_with_vartime_blame` (lib.rs:493-499), yielding `PedPoPError::InvalidShare { participant: S, blame: None }`. `R` publishes `Transaction::InvalidDkgShare` accusing `S`, as required.
4. Coordinator calls `AdditionalBlameMachine::blame(accuser=R, accused=S, msg, None)` → `blame_internal` → `decrypt_with_proof` fails decryption under `R`'s proven key → `Err(DecryptionError::InvalidProof)` → returns `recipient` = `R`.
5. `VerifyBlame` returns `ProcessorMessage::Blame { participant: R }`; coordinator emits `RemoveParticipantDueToDkg { participant: R }` (coordinator/src/main.rs:537-549); once votes reach `t`, `R` is `fatal_slash`ed and excluded from subsequent DKG attempts (`removed_as_of_dkg_attempt`).
6. Repeat against `n - t` honest validators to push `present_shares < t`, deadlocking the Tributary in the `loop { sleep(60) }` at scanner.rs:271-279 — full availability loss caused entirely by blaming healthy parties for a sender-side fault.
