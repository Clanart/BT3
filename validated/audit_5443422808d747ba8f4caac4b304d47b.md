### Title
Liquidation curve exponent truncated to nearest integer power in `calc-liq-factor-exp()` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The reported `rebaseMul()` bug class — a scaling operation that only supports whole-number factors and silently drops any fractional component — has a direct analog in Zest's graduated-liquidation math. `calc-liq-factor-exp()` is meant to apply a configurable curve exponent (`liq-factor^alpha`) to the linear liquidation factor, but it only correctly supports exponents that are exact integer multiples of `BPS`, and for any exponent below `BPS` it hard-codes the exponent to `0.5` regardless of the configured value.

### Finding Description
`calc-liq-factor-exp` is:
```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
``` [1](#0-0) 

- For `exp > BPS` (i.e., alpha > 1.0), `(/ exp BPS)` is an **integer division that floors the exponent**. E.g. `exp = 15000` (alpha = 1.5) yields `(/ 15000 10000) = 1`, so the code computes `factor^1` instead of `factor^1.5` — the fractional `0.5` component of the configured curve exponent is silently discarded, exactly mirroring the `rebaseMul()` defect of only accepting whole-number factors.
- For `exp < BPS` (i.e., alpha < 1.0), the code doesn't even read the configured value — it unconditionally computes `sqrti(factor * BPS)`, i.e. `factor^0.5`, no matter what fractional alpha (0.3, 0.7, 0.9, etc.) was actually configured.

This result, `liq-pct-scaled`, feeds directly into the liquidation penalty and max-repayable-debt calculations:
```
(liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
(liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
(max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled))
``` [2](#0-1) 

Because `liq-pct-linear` is a fraction in `[0, BPS]` (i.e., `0 ≤ x ≤ 1`), and for `0 < x < 1`, raising `x` to a *smaller* exponent than intended always produces a *larger* result (`x^1 > x^1.5` for `0<x<1`). So when the DAO configures a graduated curve with alpha > 1 (concave-down curve intended to liquidate less aggressively early in the range), the truncated exponent computation produces a systematically larger `liq-pct-scaled` than intended.

### Impact Explanation
A larger-than-intended `liq-pct-scaled` propagates into:
1. `calc-liq-factor-bound` → a higher liquidation penalty than the curve was designed to apply at that LTV.
2. `calc-liq-debt-repay` → a higher `max-debt-usd`, allowing the liquidator to seize more debt/collateral in a single liquidation than the configured curve intended.

Both push more collateral value from the borrower to the liquidator than the DAO-designed liquidation curve intended, at any LTV point inside the partial-to-full liquidation band. This is a fund-flow correctness bug (wrong liquidation-percentage/penalty verdict) rather than a misconfiguration issue — the truncation occurs for *any* non-integer-multiple-of-`BPS` exponent value, including textbook values like 1.5x or 0.5x/0.3x that a DAO would reasonably configure for a graduated curve. This lands on theft of user (borrower) collateral beyond what the intended liquidation curve authorizes, which is an economic/fund-transfer impact tied to a live pricing/health computation used during liquidation.

### Likelihood Explanation
Likelihood is high in the sense that any curve exponent that isn't an exact multiple of `BPS` (10000) — which is the entire fractional design space the "graduated liquidation curve" feature exists to support — triggers the bug on every liquidation call that reaches `calc-liq-factor-exp`. No attacker action beyond being (or targeting) a liquidatable position is required; the bug fires deterministically whenever `curve-exponent` is not a whole multiple of `BPS`.

### Recommendation
Rework `calc-liq-factor-exp` to support fractional exponents precisely, e.g., by using a fixed-point exponentiation routine (numerator/denominator representation of alpha, or a `ln`/`exp` fixed-point approximation) rather than truncating integer division for the `exp > BPS` branch and hard-coding `factor^0.5` for the `exp < BPS` branch.

### Proof of Concept
1. DAO configures an egroup with `LIQ-CURVE-EXP = 15000` (intending alpha = 1.5).
2. A borrower's position enters the partial-liquidation band with `liq-pct-linear = 4000` (0.4 in BPS terms).
3. Intended result: `0.4^1.5 ≈ 0.253` (in BPS terms ≈ 2530).
4. Actual code path (`exp=15000 > BPS=10000`): `(/ 15000 10000) = 1` → computes `factor^1 / BPS^0 = factor = 4000`.
5. The liquidator's `max-debt-usd` and `liq-penalty` are computed off `4000` instead of the intended `2530`, letting the liquidator repay/seize roughly 58% more debt/collateral than the configured graduated curve intended, purely due to integer-division truncation of the exponent in [1](#0-0) .
