Based on the local code, the closest real Agave analog is the **rent-state transition invariant** enforced by the SVM after every transaction executes. It has the same shape as the reported bug: a strict equality/inequality check against a **live, externally-mutable value** (account lamports) that an unprivileged attacker can perturb with a trivial, permissionless action (a plain SOL transfer), causing a *legitimate, unrelated* transaction to fail — while the victim still pays the transaction fee.

### Title
Unprivileged dust-lamport donation griefs account-closing/draining transactions via strict `RentState` transition enforcement - (`svm/src/rent_calculator.rs`)

### Summary
Agave enforces a strict post-execution invariant on every writable account touched by a transaction: an account that is `RentExempt` (or `Uninitialized`) before the transaction may never end the transaction as `RentPaying`, and an account that is `RentPaying` may only remain `RentPaying` if its size is unchanged and its lamports did not increase. This is exactly the same class of bug as TRST-M-2: an over-granular, byte-exact check performed against externally donatable state (account lamports), which any unprivileged actor can nudge with a negligible, permissionless system transfer to make an otherwise-correct transaction revert.

### Finding Description
The rule lives in `transition_allowed`: [1](#0-0) 

and is applied to every writable account for every transaction via `verify_changes` / `check_rent_state_with_account`: [2](#0-1) [3](#0-2) 

This is invoked at the end of every transaction's execution in `load_execute_and_commit_transaction`/equivalent path in the batch processor: [4](#0-3) 

Many programs (including common "close account" / "drain to zero" / "withdraw all" patterns used across the ecosystem, and system-program-based full transfers) compute the amount to move based on a **client-supplied, precomputed exact value** meant to leave the account at exactly `0` lamports (transitioning `RentExempt`/`RentPaying` → `Uninitialized`) or exactly at the rent-exempt minimum. Because `account.lamports()` is a public, globally writable-by-anyone-crediting value (any unprivileged party can send lamports to *any* pubkey via a normal `system_instruction::transfer`, regardless of the destination account's owner), an attacker can:

1. Observe a pending transaction in the mempool that closes/drains account `A` by moving out a fixed, precomputed amount (computed off-chain from `A`'s currently known balance) so that `A` ends at `0` lamports.
2. Send a dust transfer (e.g. 1 lamport) directly to `A` before the victim's transaction lands.
3. When the victim's transaction executes, the fixed instruction-level transfer amount no longer drains `A` to `0` — it leaves `1` lamport behind.
4. `get_post_exec_account_rent_state` computes `A`'s post-state as `RentPaying { lamports: 1, .. }` (since `1 < min_balance`), while `A`'s pre-state was `RentExempt`.
5. `transition_allowed(RentExempt, RentPaying{..})` returns `false` (line 196 in `rent_calculator.rs`), so `check_rent_state_with_account` returns `TransactionError::InsufficientFundsForRent`, and the whole transaction is rejected/reverted — even though the program's own instruction logic executed exactly as intended.

The victim's transaction fee is still charged (fee payment happens during loading, before the rent-state check), so the attacker inflicts real, repeatable, asymmetric cost on victims for the price of a single dust transfer, exactly mirroring the "donate a negligible amount to break an exact-ratio/exact-amount check" primitive from TRST-M-2.

### Impact Explanation
This does not steal funds directly, but it is a low-cost, unprivileged, permissionless, repeatable griefing/DOS primitive against arbitrary victim transactions that close or drain accounts to an exact target balance. The victim loses the transaction fee (and any compute already spent) on every attempt, while the attacker's cost is a single dust lamport transfer plus its own transaction fee — an asymmetric cost imposed on unrelated users, identical in spirit to the reported vault DOS.

### Likelihood Explanation
Any account and any pending transaction targeting a fixed/precomputed exact lamport amount is a valid target; the attacker needs no special privileges, no validator/leader position, and no cooperation from any other party — only the ability to submit an ordinary system transfer, which is available to every wallet on the network. The check is fully deterministic and always triggers under the described sequencing (attacker's donation lands before the victim's transaction).

### Recommendation
Avoid basing the runtime-level rent-state invariant purely on an exact-equality/inequality comparison against externally donatable live balances for the "close to zero" case; e.g., allow a `RentPaying` post-state with `lamports` below a very small dust threshold to still transition to `Uninitialized`-equivalent handling, or let programs explicitly signal "close-account" intent (sweeping any residual dust) rather than relying on a fixed precomputed transfer amount. This mirrors the vault team's shift away from a byte-exact ratio check toward a design that tolerates externally injected dust.

### Proof of Concept
1. Create account `A`, owned by any program, with balance exactly `rent.minimum_balance(A.data_len())` (`RentState::RentExempt`).
2. Construct victim transaction `T` that transfers exactly `rent.minimum_balance(A.data_len())` lamports out of `A` (client precomputed this amount from `A`'s currently observed balance), intending to leave `A` at `0` lamports.
3. Before `T` lands, attacker sends `system_instruction::transfer(attacker, A, 1)` — a normal, permissionless transfer.
4. When `T` executes, `A`'s balance after `T`'s transfer is `1`, not `0`.
5. `TransactionAccountStateInfo::new_post_exec` computes `A`'s post-state as `RentPaying { lamports: 1, data_size }` [5](#0-4) ; `transition_allowed(RentExempt, RentPaying{..})` returns `false` [6](#0-5) , so `verify_changes` returns `TransactionError::InsufficientFundsForRent`, and `T` fails despite executing its logic correctly, while its fee is still charged.

pub fn get_account_rent_state(
    account_lamports: u64,
    account_size: usize,
    min_balance: u64,
) -> RentState {
    if account_lamports == 0 {
        RentState::Uninitialized
    } else if account_lamports >= min_balance {
        RentState::RentExempt
    } else {
        RentState::RentPaying {
            data_size: account_size,
            lamports: account_lamports,
        }
    }
}

pub fn transition_allowed(pre_rent_state: &RentState, post_rent_state: &RentState) -> bool {
    match post_rent_state {
        RentState::Uninitialized | RentState::RentExempt => true,
        RentState::RentPaying {
            data_size: post_data_size,
            lamports: post_lamports,
        } => {
            match pre_rent_state {
                RentState::Uninitialized | RentState::RentExempt => false,
                RentState::RentPaying {
                    data_size: pre_data_size,
                    lamports: pre_lamports,
                } => {
                    // Cannot remain RentPaying if resized or credited.
                    post_data_size == pre_data_size && post_lamports <= pre_lamports
                }
            }
        }
    }
}

pub(crate) fn verify_changes(
    pre_state_infos: &[TransactionAccountStateInfo],
    post_state_infos: &[TransactionAccountStateInfo],
    transaction_context: &TransactionContext,
) -> Result<()> {
    for (i, (pre_state_info, post_state_info)) in
        pre_state_infos.iter().zip(post_state_infos).enumerate()
    {
        if let (Some(pre_state_info), Some(post_state_info)) =
            (pre_state_info.info.as_ref(), post_state_info.info.as_ref())
        {
            check_rent_state(
                &pre_state_info.rent_state,
                &post_state_info.rent_state,
                transaction_context,
                i as IndexOfAccount,
            )?;
        }
    }
    Ok(())
}
