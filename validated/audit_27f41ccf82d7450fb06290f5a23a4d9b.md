### Title
`conflictMarkerCount === 0` is treated as proof-of-resolution across Desktop, but it is only a proxy derived from `git diff --check`, not a scan of the file for literal markers - ([File: app/src/lib/git/diff-check.ts])

### Summary
Desktop decides whether a merge/rebase conflict is "resolved" purely from a single integer, `conflictMarkerCount`, computed once per status refresh and then trusted everywhere (staging, committing, and the Copilot conflict-resolution UI) as if it were a direct, ground-truth read of the file's conflict-marker text. In reality that number is not obtained by scanning the working-tree file for `<<<<<<<`/`=======`/`>>>>>>>` — it comes from parsing the textual output of `git diff --check`, a Git subcommand whose marker detection depends on Git's own conflict-marker-size resolution and diff-hunk visibility, both of which are influenced by content that can arrive from a merged/fetched branch (e.g. `.gitattributes`). This mirrors the Angle finding's structure exactly: a cheap boolean/zero-check ("is `lockedProfit` 0?" → "is `conflictMarkerCount` 0?") is substituted for the real invariant it's supposed to approximate ("is the real APR non-zero?" → "does the file still contain unresolved conflict markers?"), and the two can diverge.

### Finding Description
`getFilesWithConflictMarkers` runs `git diff --check` and regex-parses lines matching `leftover conflict marker` to build a `Map<path, count>`: [1](#0-0) 

That count becomes `conflictMarkerCount` on `ConflictsWithMarkers`: [2](#0-1) 

From that point on, `conflictMarkerCount === 0` is used app-wide as the single source of truth that a conflicted file has "no conflicts remaining," with no independent verification against the actual file bytes:

- `hasUnresolvedConflicts()` — gates the merge-conflicts UI and, more importantly, whether the file is presented for staging as resolved: [3](#0-2) 

- `stageManualConflictResolution()` — silently returns/short-circuits ours/theirs resolution once `conflictMarkerCount === 0`, on the theory that the user already resolved it manually via an editor: [4](#0-3) 

- `isFileResolvedExternally()` in the Copilot conflict-resolution dialog — treats a zero count as authoritative proof the on-disk edit is "the source of truth" and overrides any prior ours/theirs choice: [5](#0-4) 

- `getResolvedFileStatusSummary()` / `mapStatus()` — render the file as "Resolved" / "No conflicts remaining" in the commit-conflicts dialog based on the same flag: [6](#0-5) [7](#0-6) 

The broken invariant: `conflictMarkerCount === 0` is supposed to mean "this file's content contains no leftover `<<<<<<<`/`=======`/`>>>>>>>` text," but it actually only means "`git diff --check` did not print a `leftover conflict marker` line for this path." Those are not the same thing, because:
1. Git's marker-size expectation for `diff --check` is resolved per-path via the `conflict-marker-size` gitattribute, which is itself repository content that can be shipped in the branch/remote being merged. Notably, Desktop's own separate, independent implementation of marker detection (used for the Copilot feature) hard-codes a 7-character marker width via regex and has no knowledge of this attribute at all: [8](#0-7) 
   This is a second, textbook illustration of the same class of bug: two independent "is this file still conflicted" computations exist in the codebase (`git diff --check`'s Git-attribute-aware count vs. the fixed 7-char regex scanner), and nothing guarantees they agree — exactly the "estimate that's correct in one regime but silently wrong outside it" pattern from the source report.
2. `git diff --check` is a *diff*-based check: it reports marker lines that show up in the diff between the working tree and the index. Content that is not part of the visible diff hunk for that invocation (already present with no delta at the point of comparison) will not be flagged as `leftover conflict marker` even though the literal marker bytes are sitting in the file that Desktop is about to let the user stage/commit.

Neither of the two code paths that ultimately gate "should this be treated as a clean, committable file" (`hasUnresolvedConflicts`, `isFileResolvedExternally`) fall back to actually re-reading and pattern-scanning the working tree file to confirm the absence of marker text before letting the file be staged — they trust the previously cached porcelain-status-derived count.

### Impact Explanation
If an attacker controls a branch, remote, or fetched repository that the victim merges/rebases/cherry-picks against (the prompt's accepted "cloned/fetched repository or git remote" primitive), they can arrange for a conflicted file's `conflictMarkerCount` to read `0` while the file still contains literal, unresolved `<<<<<<<`/`=======`/`>>>>>>>` conflict text (or attacker-chosen content the user never actually reviewed as a diff). Desktop will then:
- Display the file as "Resolved" / "No conflicts remaining" in the Changes/merge-conflicts UI, and
- Allow it to be staged and committed via the normal commit flow, and pushed to the user's remote.

This is a silent corruption of what the user commits and pushes — the exact class of impact explicitly called out as valid in the prompt (`silent corruption of what the user commits or pushes`) — without any local access, admin rights, or social engineering beyond the normal act of merging/pulling from a repository the user already trusts enough to fetch from.

### Likelihood Explanation
Medium-to-low. Exploitation requires the attacker to control (or poison) `.gitattributes`/merge-driver configuration or otherwise arrange a merge outcome where `git diff --check`'s marker-size expectation or diff-hunk visibility diverges from the literal on-disk content — this is a non-trivial but realistic setup fully achievable from a crafted branch/remote the victim merges against, with no local access needed. It does not require the victim to do anything unusual: a normal "merge branch" / "pull" / conflict resolution flow is sufficient once the malicious repository state exists. I could not fully validate the exact Git-internal trigger conditions for `conflict-marker-size` divergence with a live `git diff --check` run (no terminal access here), so the precise minimal repro should be confirmed with a real Git checkout before treating this as fully proven, but the architectural weakness — trusting a diff-derived proxy as ground truth for "no conflict markers remain," with two independently coded marker detectors that can disagree — is confirmed directly from the source.

### Recommendation
Before allowing a conflicted file with `conflictMarkerCount === 0` to be treated as resolved and staged, perform a direct scan of the working-tree file content for the marker patterns (reusing/aligning with `oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker` in `copilot-conflict-context.ts`, made attribute-aware) rather than relying solely on `git diff --check`'s diff-scoped, attribute-dependent output. At minimum, reconcile the two independent marker-detection implementations (`app/src/lib/git/diff-check.ts` vs `app/src/lib/copilot-conflict-context.ts`) so they cannot silently disagree about the same file.

### Proof of Concept
Conceptual (not independently verified against a live Git binary in this environment):
1. Attacker prepares a branch/remote with a `.gitattributes` entry setting a non-default `conflict-marker-size` for a target file, and content on `theirs` engineered so that after the 3-way merge, the resulting conflicted file's marker lines fall outside what `git diff --check` reports as `leftover conflict marker` for that path (or outside the working-tree/index diff visibility window), while still containing literal marker text or attacker payload the user never saw as a reviewable diff.
2. Victim clones/fetches this repository and merges the attacker's branch into their own; Git leaves the file in a conflicted state.
3. `getFilesWithConflictMarkers()` runs `git diff --check` and returns `0` for that path because no `leftover conflict marker` line was emitted for it: `app/src/lib/git/diff-check.ts:9-27`.
4. Desktop's status pipeline sets `conflictMarkerCount: 0` on the file's `ConflictsWithMarkers` status: `app/src/lib/git/status.ts` (via `getMergeConflictDetails`), `app/src/models/status.ts:58-63`.
5. `hasUnresolvedConflicts()` returns `false` (`app/src/lib/status.ts:66-84`), `mapStatus()` reports `'Resolved'` (`app/src/lib/status.ts:33-37`), and the conflicts dialog shows "No conflicts remaining" (`app/src/ui/lib/conflicts/unmerged-file.tsx:483-494`).
6. The victim commits and pushes the file believing it is clean, silently including attacker-controlled/unresolved content.

```typescript
export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}
```

```typescript
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
```
