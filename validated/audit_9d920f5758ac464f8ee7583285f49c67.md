### Title
Fee-refund push transfer in `EvmHost.dispatchTimeOut` permanently reverts and locks cross-chain requests when the payer is denylisted by the fee token - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchTimeOut(PostRequestTimeout, ...)` and its GET-timeout counterpart unconditionally push the relayer-fee refund to `meta.sender` (the original `payer` recorded at dispatch time) using `safeTransfer` *after* successfully invoking the source application's timeout callback, in the same top-level call. If the fee token (e.g. a USDC-style asset with a denylist) blocks a transfer to `meta.sender`, the `safeTransfer` reverts and unwinds the entire transaction — including the already-executed `onPostRequestTimeout` callback and the deletion of `_requestCommitments`. Because the request has already exceeded its timeout window, it can never be delivered through the normal path either (`handlePostRequests` rejects with `MessageTimedOut()`), so the request becomes permanently stuck: it can be resubmitted forever but will always revert for the same reason, and the application's timeout logic — which typically releases/refunds escrowed assets (e.g. Intent Gateway orders) — never executes durably.

### Finding Description [1](#0-0) 

```solidity
function dispatchTimeOut(
    PostRequestTimeout memory timeout,
    FeeMetadata memory meta,
    bytes32 commitment
) external restrict(_hostParams.handler) {
    // replay protection
    delete _requestCommitments[commitment];
    (bool success,) = _bytesToAddress(timeout.request.from)
        .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

    if (!success) {
        // so that it can be retried
        _requestCommitments[commitment] = meta;
        return;
    }

    if (meta.fee != 0) {
        // refund relayer fee
        IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
    }
    emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
}
```

Only the *application callback failure* path (`!success`) is defensively made retryable. The fee-refund `safeTransfer` call has no such protection: it is a direct, unguarded external call outside any try/catch or low-level `.call`. If it reverts, Solidity propagates the revert to the top of `dispatchTimeOut`, which rolls back:
1. The `delete _requestCommitments[commitment]` replay-protection update.
2. Any state changes the source app made inside its (successful) `onPostRequestTimeout` handler.

`meta.sender` is the `payer` field set by the application at dispatch time — see [2](#0-1)  where `IntentGateway`'s cross-chain fill flow sets `payer: msg.sender` (the solver) on the `DispatchPost`. This value is attacker/user-controlled indirectly: it is simply whichever externally-owned account calls `fillOrder`/`cancelOrder`. If that account is later placed on a fee-token denylist (a routine, real-world event for USDC-class tokens, and the `feeToken` is explicitly configurable per `HostParams.feeToken`), every future call to `dispatchTimeOut` for a request whose fee was funded by that account will revert unconditionally.

This is the same broken invariant as the external report: a mandatory push-transfer to a party that can become permanently un-payable is embedded inside a critical state-transition path with no pull/escrow fallback, so denylisting one address blocks the entire operation rather than just the transfer. Here, the blocked operation is the ISMP timeout path itself (permissionlessly callable via `IHandler.handlePostRequestTimeouts`), not just a token transfer — making the blast radius worse than the original report, since it also nukes the app-level side effects of a successful timeout callback.

### Impact Explanation
Once the request has timed out, delivery via `handlePostRequests` is rejected with `MessageTimedOut()` — see [3](#0-2) . If `dispatchTimeOut` also always reverts due to the blacklisted `meta.sender`, the request has no path left to resolve. Any application relying on `onPostRequestTimeout` to recover funds (e.g. Intent Gateway using `IntentGateway`'s cancel/refund flow, which dispatches a `DispatchPost` with `payer: msg.sender`) can have its escrowed assets tied to that commitment permanently locked, since the callback that would trigger the refund logic never durably executes. This is a direct fund-lock/loss condition reachable without any malicious relayer, prover, or admin — only a fee token with denylist semantics and an ordinary account transition to that denylist.

### Likelihood Explanation
The `feeToken` is explicitly documented as configurable and "typically DAI," but deployments may configure USDC or other denylist-capable stablecoins as the fee token. Any account that dispatches a fee-bearing POST request as `payer` (which includes ordinary solver/user accounts driving Intent Gateway flows) and is later denylisted by that token — for entirely unrelated compliance reasons, or deliberately by an adversary targeting a specific counterparty they know will act as payer — triggers the permanent deadlock. No special privileges are required to trigger the underlying condition; it activates as soon as a real-world denylist event occurs for a payer with a pending or future timeout request.

### Recommendation
Do not let the fee-refund transfer be part of the same atomic path as the replay-protection/callback state update. Options:
- Wrap the `safeTransfer` in a low-level `.call` and, on failure, credit the amount to a per-address pull-balance (escrow) that `meta.sender` (or anyone) can withdraw later, mirroring the Teller fix's escrow-vault pattern.
- Perform the state mutation (`delete _requestCommitments`) and the app callback dispatch unconditionally, then attempt the refund in a way whose failure cannot roll back the already-committed timeout state (e.g. via `try/catch` on an internal wrapper, storing the fee in a claimable mapping on failure instead of reverting the whole call).
- Apply the same fix to the analogous unguarded transfers in `dispatchIncoming(GetResponse)` (relayer reward) and `dispatchTimeOut(GetRequestTimeout)` (payer refund) at [4](#0-3) .

### Proof of Concept
1. Deploy `EvmHost` with `feeToken` set to a mock ERC20 that implements a `blacklist(address)` admin function causing `transfer`/`transferFrom` to that address to revert (mirrors USDC `isBlacklisted`).
2. From account `P`, call an application (e.g. `IntentGateway.fillOrder` for a cross-chain order) that internally calls `IDispatcher(host).dispatch(DispatchPost{..., fee: X, payer: P})`, funding `X` fee tokens.
3. Let the request's `timeoutTimestamp` elapse without delivery.
4. Blacklist account `P` on the fee token.
5. Anyone calls `IHandler.handlePostRequestTimeouts` with a valid timeout proof for the commitment, which invokes `EvmHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)`.
6. Observe: `onPostRequestTimeout` executes successfully (app would normally proceed to release escrow), but the subsequent `IERC20(feeToken()).safeTransfer(P, X)` reverts due to the blacklist, reverting the entire transaction — `_requestCommitments[commitment]` is never deleted and the app's refund logic never durably executes.
7. Repeat step 5 indefinitely: it always reverts identically. The request, and any escrowed funds gated behind its timeout callback, are permanently unrecoverable.
