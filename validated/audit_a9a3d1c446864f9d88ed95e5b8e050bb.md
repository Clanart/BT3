### Title
Forged `ReceivedOutput` deserialization injects attacker-controlled prevout value/offset into transaction construction - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the CVE-2020-21394 SQL injection (an untrusted `tablename` parameter is trusted as authoritative metadata about a real object), `ReceivedOutput::read` accepts a fully attacker-controlled record — offset, `TxOut` (including `value` and `script_pubkey`), and `OutPoint` — and downstream code treats these claims as ground truth. `SignableTransaction::new` computes input value, fee, and change purely from the *claimed* `TxOut.value`, and `TransactionSignMachine::sign` commits the claimed prevouts into the BIP-341 sighash via `Prevouts::All`, with no consistency check that the claimed outpoint's on-chain output matches the claimed value. The only validation that exists (`multisig`) checks `script_pubkey` against the offset-derived key — value and outpoint authenticity are never verified.

### Finding Description
`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` deserializes `offset` via `Secp256k1::read_F`, then `TxOut` and `OutPoint` via `consensus_decode` — all from untrusted bytes, with no binding between them. [1](#0-0) 

`SignableTransaction::new` then uses `input.output.value` as the spendable input sum for the `NotEnoughFunds` check and for the change calculation (`input_sat - payment_sat - fee_with_change`), and copies `input.output` wholesale into `prevouts`. [2](#0-1) [3](#0-2) 

`multisig` only verifies the claimed `script_pubkey` equals `p2tr_script_buf(offset.group_key())`; it does not check the outpoint resolves on-chain or that the value is accurate. [4](#0-3) 

Finally, `sign` commits these unverified prevouts into the signature message: `cache.taproot_key_spend_signature_hash(i, &prevouts, TapSighashType::Default)` where `prevouts = Prevouts::All(&self.tx.prevouts)`. [5](#0-4) 

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (an explicitly reachable read API) can inject a record pairing a real group-controlled outpoint with a fabricated value, or pair an outpoint with a mismatched offset:

- **Inflated value + change address:** the change output is sized from the fake input sum, so the multisig produces a transaction whose outputs exceed real input value — invalid and unbroadcastable, yet it consumes a full threshold signing session and can repeatedly poison spends (funds reported/received and queued, but not spendable through the produced transaction).
- **Deflated value:** triggers false `NotEnoughFunds` rejections, or with no change output, constructs a transaction committing wrong prevout amounts — BIP-341 sighash validation requires committed amounts equal the real UTXO amounts, so every produced signature is invalid on-chain.
- **Mismatched offset/script:** `multisig` returns `None`, silently aborting the signing session — a liveness failure reachable purely from crafted bytes.

Because each poisoned input forces an invalid or aborted transaction, real UTXOs become unspendable for as long as forged `ReceivedOutput`s are supplied — "funds reported received that are not spendable" via injected untrusted fields, directly paralleling attacker-chosen `tablename` steering the backup to arbitrary data.

### Likelihood Explanation
Reachable whenever `ReceivedOutput` bytes cross a trust boundary (network gossip, DB state written by another component, or an RPC/peer-supplied payload) — the struct is explicitly designed for serialization (`serialize`/`write`/`read`) and is listed as an accepted untrusted-read target. No key material, collusion, or validator status is required; the attacker only needs to supply bytes. Exploitation is deterministic: every field is read verbatim with no cross-validation. Severity is bounded to Medium because the existing script/offset check prevents a *valid* signature under the wrong key, and BIP-341's amount commitment prevents the forged values from yielding a consensus-valid theft — the impact is invalid/aborted spends and poisoned change math, i.e., integrity and availability of fund movement rather than direct key compromise.

### Recommendation
Bind the fields at trust boundaries: after `ReceivedOutput::read`, verify the claimed `outpoint` exists on-chain and that its `TxOut` (value and script_pubkey) matches the chain data, and re-derive `offset` via `Scanner::scan_transaction`'s `scripts` map rather than trusting the serialized scalar — i.e., reject any `ReceivedOutput` not produced by `Scanner::scan_transaction`/`scan_block` against observed blocks, mirroring how `Scanner` itself derives `offset` from the real `output.script_pubkey`. [6](#0-5) 

### Proof of Concept
1. Attacker obtains a real UTXO `O` paying to the group's external key (value 100,000 sats, script `S = p2tr(key)`).
2. Attacker crafts `forged_bytes = Scalar::ZERO.to_bytes() || serialize(TxOut{ value: 1_000_000, script_pubkey: S }) || serialize(outpoint_of_O)` and submits to `ReceivedOutput::read` — it parses cleanly since fields are independent.
3. `SignableTransaction::new(vec![forged], payments=[(dest, 50_000)], change=Some(group_change), None, fee)` computes `input_sat = 1_000_000`, emits a change output of ~949,000 sats, and passes all checks.
4. `multisig`/`sign`/`complete` run a full FROST signing session and return a signed transaction whose inputs (100k sats) cannot cover its outputs (~1M sats) — invalid, unbroadcastable, and the signing session is burned. Repeating with the real outpoint keeps the funds unspendable through this path indefinitely.

    let mut res = Vec::new();

      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
