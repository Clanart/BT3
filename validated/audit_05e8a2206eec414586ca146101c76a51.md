## Analog Vulnerability Found

### Title
Pool reward coins are never marked spent in `PlotNFTStore`, causing repeated inclusion of already-claimed reward coins and permanent failure of future reward claims - (File: `chia/wallet/plotnft_wallet/plotnft_store.py`, `chia/wallet/plotnft_wallet/plotnft_wallet.py`)

### Summary
The external report describes `rewardAllowance` being overwritten instead of accumulated, so a user's already-earned-but-unclaimed reward tracking value is silently discarded on the next update. The analogous chia bug is the mirror-image failure mode in the PlotNFT2 pooling flow: the persistent record that is supposed to be *updated* once a pool reward is spent (`spent_height`) is never actually updated in practice, so the store keeps re-offering already-spent reward coins as claimable, corrupting future accounting and blocking legitimate future claims.

### Finding Description
`PlotNFTStore.get_pool_rewards()` selects unclaimed rewards by filtering on `spent_height IS NULL`: [1](#0-0) 

The only method that ever sets `spent_height` to a non-null value is `mark_pool_reward_as_spent()`: [2](#0-1) 

A repository-wide search shows this method is never called anywhere else in the codebase — it is dead code. The only other place `spent_height` is touched is `rollback_to_block()`, which only ever *resets* it back to `NULL` on reorg: [3](#0-2) 

Reward coins are added to `pool_reward2s` exclusively in `PlotNFT2Wallet.coin_added()`, in the branch that handles p2-singleton reward coins: [4](#0-3) 

Critically, `PlotNFT2Wallet` implements `coin_added()` but has **no `coin_removed()` implementation**, so there is no hook that fires when a previously-added reward coin is later spent (via `claim_rewards()` or `forward_pool_reward()`) that would call `mark_pool_reward_as_spent()`. The reward coin is also never inserted into the generic `WalletCoinStore`/`WalletCoinRecord` table, so the generic spent-coin bookkeping path in `WalletStateManager._add_coin_state()` (`coin_store.set_spent(...)`) does not apply to it either, since that path keys off `local_record` from `coin_store`, not `plotnft2_store`: [5](#0-4) 

As a result, `claim_rewards()` unconditionally trusts `get_pool_rewards()`'s result set to build the next claim spend bundle and to compute `total_reward_amount`: [6](#0-5) 

Once a reward coin has been spent on-chain by one successful `claim_rewards()` call, its row in `pool_reward2s` still has `spent_height = NULL` forever, so it keeps being returned by subsequent `get_pool_rewards()` calls (both for `claim_rewards()` while self-pooling, and for `forward_pool_reward()` while pooling, per the "LOSE REWARDS" test flows that walk the same store): [7](#0-6) 

### Impact Explanation
Because the stale (already-spent) reward coin is bundled into every subsequent claim attempt, the resulting `SpendBundle` references a coin that no longer exists on-chain (already spent). A `SpendBundle` is atomic — all coin spends inside it must be valid — so any legitimate, still-unclaimed pool rewards batched together with the stale, already-spent entry will also be rejected by the mempool/consensus layer. This permanently halts the user's ability to claim any newly farmed pool rewards for that PlotNFT (a spend-triggered transaction-processing halt), since the poisoned stale entry is never purged and is included again on every retry. The plotnft owner's legitimately earned rewards become unclaimable, i.e., reward funds get effectively frozen/lost from the user's perspective, mirroring the "loss of rewards" impact in the source report, though the underlying mechanism (stale tracking record vs. overwritten allowance) differs.

### Likelihood Explanation
This is deterministically triggered by any normal use of the pooling reward flow: any wallet user with a self-pooling PlotNFT who calls `claim_rewards()` (via `pw_absorb_rewards` RPC) more than once across separate reward-earning periods will hit this — the first successful claim of one or more reward coins permanently poisons the pool wallet's `get_pool_rewards()` result set for all reward coins claimed so far. No malicious peer or attacker involvement is required — this is a self-inflicted correctness bug reachable by any unprivileged plotnft owner performing ordinary wallet operations through the standard RPC.

### Recommendation
- Call `PlotNFTStore.mark_pool_reward_as_spent()` when a pool reward coin is actually spent, e.g., add a `coin_removed()` hook on `PlotNFT2Wallet` (matching the pattern other wallets use, such as `nft_wallet.py`/`vc_wallet.py`) that detects spent reward coins tracked in `pool_reward2s` and marks them spent, or alternatively update `claim_rewards()`/`forward_pool_reward()` call sites to explicitly mark the rewards passed into `claim_pool_rewards()`/`forward_pool_reward()` as spent immediately after building the spend bundle.
- As defense in depth, `claim_rewards()` should validate (e.g., via a coin-record lookup against the full node) that all `rewards_to_claim` coins are still actually unspent before constructing the claim transaction, to avoid submitting spend bundles doomed to fail due to stale local state.

### Proof of Concept
1. Create a self-pooling `PlotNFT2Wallet` and farm blocks to its `p2_singleton_puzzle_hash` so that `coin_added()` inserts N reward coins via `add_pool_reward()`.
2. Call `claim_rewards()` (e.g. via `pw_absorb_rewards` RPC) and let the transaction confirm — this spends all N reward coins on-chain, but no code path calls `mark_pool_reward_as_spent()`, so all N rows in `pool_reward2s` still have `spent_height = NULL`.
3. Farm additional blocks to earn M new reward coins; `coin_added()` inserts M new rows into `pool_reward2s`.
4. Call `claim_rewards()` again. `get_pool_rewards()` returns all N + M rows (since `spent_height IS NULL` for all of them), and `claim_pool_rewards()` builds `CoinSpend`s for all N + M coins, including the N coins that were already spent in step 2.
5. Pushing this spend bundle fails (the N stale coin spends reference coins that no longer exist), and because a `SpendBundle` is all-or-nothing, the M legitimately new and unclaimed rewards also fail to be claimed. Every future retry of `claim_rewards()` repeats this failure indefinitely, since the stale rows are never cleared.
