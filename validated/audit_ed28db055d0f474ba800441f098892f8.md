This confirms the finding is invalid. The premise of a "race" between reading `package_immutable` and writing `packages.borrow_mut(index)` doesn't hold at either the intra-transaction or inter-transaction level:

1. **Within a single transaction**: `publish_package` in `code.move` executes as ordinary sequential Move bytecode inside one VM session. The `borrow_global<PackageRegistry>(addr)` read at line 188 and the `borrow_global_mut<PackageRegistry>(addr)` write at line 206 happen atomically within that one transaction's execution — there is no concurrency inside a single transaction's Move execution, so there is no "race" to exploit here. [1](#0-0) 

2. **Across two transactions in the same block**: Aptos uses Block-STM parallel execution, which tracks per-transaction read-sets and write-sets and validates them against transaction *index order*, not actual wall-clock execution order. Both publish transactions touch the same `PackageRegistry` resource at the same address — one via read (`borrow_global`) and one via write (`borrow_global_mut`) — which are recorded as conflicting accesses on the same `StateKey`. [2](#0-1) 

3. Block-STM's validation logic re-validates a transaction's prior read-set against the versioned multi-version hashmap (`read_set.validate_data_reads(...)`) whenever an earlier-indexed transaction writes to a key that a later transaction has already read. If the check fails, the later transaction is aborted and re-executed.
