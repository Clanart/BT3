### Title
Front-runnable share-price manipulation on first `PublicDelegation.stake()` call via direct-transfer donation to a `CLPool` - ([File: contracts/bindings/publicdelegation/PublicDelegation.go])

### Summary
`PublicDelegation` is an ERC4626-style vault contract used for consensus liquidity (CL) staking introduced in the Prague hardfork (KIP-226). It exposes `convertToShares`, `convertToAssets`, `previewDeposit`, `previewRedeem`, and a `stake`/`Staked(user, assets, shares)` flow that mints shares based on `totalSupply()`/pool balance, mirroring the Knox `Queue.processDeposits` pattern flagged in the external report (mint at 1:1 `ONE_SHARE` price when supply is zero, otherwise `shares = assets * totalSupply / totalAssets`). [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The reward module documentation confirms `PublicDelegation`/`CLPool` addresses hold native KAIA balances that are directly used to compute a consolidated node's total effective stake and reward split (`cn.Split(reward)` proportionally splits rewards between CNStaking and CL pool based on their balances). [4](#0-3) [5](#0-4) 

If `PublicDelegation`'s internal share accounting (as exposed by `convertToShares`/`convertToAssets`) computes price-per-share from `totalSupply()` and the pool's native balance (`address(this).balance` style accounting typical of such vaults), then — exactly like the Knox `Queue` bug — the first depositor into a freshly-deployed or supply-drained `PublicDelegation` pool is vulnerable to a front-run/donation attack: an attacker can send KAIA directly to the pool address (or call a privileged unstake/redelegate path) before the victim's `stake()` transaction lands, inflating `totalAssets` relative to `totalSupply` and manipulating the price-per-share the victim receives, similar to the classic ERC4626 "first depositor / inflation" attack. This is a single-transaction/front-run reachable by any unprivileged sender who can submit a plain value-transfer or `stake()` call to a `PublicDelegation` pool address.

### Impact Explanation
If confirmed, this would let an attacker steal or dilute a first staker's shares in a consensus-liquidity delegation pool, directly causing loss of staked value/rewards for legitimate users — a concrete value-movement bug, consistent with the "unauthorized value movement" acceptance criterion.

### Likelihood Explanation
Likelihood is uncertain to confirm from this index. The Solidity source of `PublicDelegation.sol` (the actual `stake()`/`_convertToShares` implementation, and whether it uses a decimals-offset/virtual-shares mitigation as OpenZeppelin's modern ERC4626 does) is **not available in the indexed codebase** — only the compiled Go bindings/ABI/bytecode were found. I was unable to locate `DECIMALS_OFFSET`, virtual-share, or minimum-liquidity-lock patterns anywhere in the repo, and could not verify whether `totalAssets()` is computed from `address(this).balance` (donation-attackable) or from an internally tracked accounting variable (not donation-attackable). [6](#0-5) 

### Recommendation
Given the missing source, I cannot confirm this as a definitive finding rather than a plausible analog. Due to index size limits, the full `PublicDelegation.sol` source (and any `CLPool`/staking-pool share-accounting logic) is not available here — starting a Devin session with full repository access would be needed to locate the actual `stake`/`_convertToShares`/`totalAssets` implementation and confirm whether donation/front-run first-depositor share inflation is actually exploitable, or whether it is already mitigated (e.g., virtual shares, minimum liquidity burn, or internal balance accounting decoupled from `address(this).balance`).

### Proof of Concept
Not constructable without the `PublicDelegation.sol` source; the described PoC pattern (front-run a first `stake()` call with a direct balance donation, deposit-check via `getContractBalance()`/`address(this).balance`) cannot be confirmed against a real function body from the indexed artifacts.

- **Prague rule (KIP-226)**: The rule since the KIP-226 hardfork with `istanbul.policy == 2` and `reward.deferredtxfee = true`.
  - MR: The consensus liquidity is introduced. The validator's total staking amount is summed up with the KAIA staked in consensus liquidity.
    - If the validator has staked more than `reward.minstake` in staking-only (CNStaking) contract, the validator's total staking amount will be summed up with the consensus liquidity.
    - In this case, the reward between staking-only and consensus liquidity will be distributed proportionally to their staking amounts. The consensus liquidity portion is rounded down, and the remainder goes to the validator's AddressBook reward address.
    - Otherwise, validator will not be eligible for rewards.
