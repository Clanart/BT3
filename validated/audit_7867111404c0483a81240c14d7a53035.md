### Title
`GeneratorPromotion::complete` panics on `proofs.get(&i).unwrap()` when a peer substitutes a proof under our own participant index - (File: crypto/dkg/promote/src/lib.rs)

### Summary
The upstream SCTP bug (CVE-2023-53296) is a stale-index flaw: a count/membership bound captured before a blocking wait becomes invalid by the time the operation resumes, so a resumed send dereferences a stream slot that no longer exists. The same shape exists in Serai's generator-promotion DKG: `GeneratorPromotion::complete` validates the *quantity* and *upper bound* of the `proofs` map, then indexes it by position assuming the map's keys are exactly `1..=n` minus our own index. A peer-controlled map that satisfies both checks while omitting a required participant key causes an unconditional `unwrap()` panic.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two checks on the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

- `proofs.len() == n - 1` (line 125) — only the count is checked.
- `u16::from(i) <= params.n()` for every key (lines 132–136) — only the upper bound is checked.

It then iterates `i in 1..=params.n()`, skips `params.i()`, and unconditionally calls `proofs.get(&i).unwrap()` (line 146).

Because no check rejects a proof keyed by `params.i()` itself, an attacker can supply `n - 1` proofs consisting of every honest participant *plus* an entry under the victim's own index `params.i()`, while omitting some honest participant `j`. Both validations pass (`len == n-1`, all keys `<= n`, `Participant` is nonzero by construction), but `proofs.get(&j)` returns `None` and `.unwrap()` panics.

This mirrors the kernel bug: the `len`/bound check is the analog of the stale stream-count snapshot, and the `get(&i).unwrap()` is the analog of indexing into a stream array whose membership changed — the validation establishes a *cardinality*, not the *identity* of the required entries, so a slot that "should" exist does not.

For comparison, `dkg`'s `ThresholdKeys::new`/`view` and FROST's `sign`/`complete` do not have this flaw: `view` verifies the sorted `included` list contains `params.i()` and rejects `> n` (dkg/src/lib.rs:474–491), `sign` checks the last included index and duplicates (frost/src/sign.rs:297–310), and PedPoP's `calculate_share` uses `validate_map` which explicitly checks each expected key is present and that our own index is absent (pedpop/src/lib.rs:57–83). `GeneratorPromotion::complete` is the odd one out — it performs the weaker check.

### Impact Explanation
An unprivileged participant in a generator-promotion ceremony (which runs when promoting key shares to a new generator, e.g., Bitcoin's tweaked generator) can crash every honest participant's `complete` call by sending a well-formed `GeneratorProof` map whose key set covers the victim's own index instead of one honest participant. The panic aborts the promotion and, in a host process without per-call panic isolation, takes down the key-management thread — a denial of service against the DKG/promotion round reachable purely through peer-supplied proof messages, matching the Medium/availability-only impact profile of the referenced CVE.

### Likelihood Explanation
The `proofs` map is assembled from per-participant `GeneratorProof` messages broadcast during promotion — untrusted, attacker-influenced input. The attacker only needs to label one of their proofs with the victim's `Participant` index (or get a relay to key it so) and withhold a proof for one other participant. The missing-key condition is fully within the sender's control; no race or special timing is required, unlike the kernel original.

### Recommendation
Replace the implicit-membership assumption with an explicit one, mirroring `pedpop::validate_map`: verify each `i in 1..=n` other than `params.i()` is present in `proofs`, and that `params.i()` is *not* present (i.e., return `PromotionError::InvalidParticipant` or a dedicated error instead of indexing with `get(&i).unwrap()`). Equivalently, iterate the map's keys and require them to equal the expected set rather than counting them.

### Proof of Concept
```rust
// crypto/dkg/promote — conceptual PoC
// Victim runs: promotion.complete(&proofs) with params = (t, n, i = 2)
// Attacker-controlled `proofs` map:
//   keys = {1, 3, 4, ..., n} minus {j}, plus {2}   // includes victim's own i, omits j
// proofs.len() == n - 1        -> passes check at line 125
// all keys <= n                -> passes check at lines 132-136
// loop reaches i == j          -> proofs.get(&j) == None -> unwrap() panics (line 146)
```
Construct `proofs` as `HashMap` containing valid `GeneratorProof`s for all participants except honest participant `j`, plus a `GeneratorProof` keyed by the victim's `params.i()` (any point parses as `GeneratorProof` since it is only verified inside the loop). `GeneratorPromotion::complete` panics before reaching proof verification.
