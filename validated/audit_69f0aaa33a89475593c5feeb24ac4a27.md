## Title
Attacker-controlled `.gitmodules` `file://` submodule URL enables local file exfiltration during branch/commit checkout - (File: `app/src/lib/git/checkout.ts`, `app/src/lib/git/submodule.ts`)

### Summary
The Sherlock report's broken invariant is: a value the code trusts to select a *safe* behavior (`isNativeToken`/`marginToken`) is never validated against the value that is actually acted upon later, so an attacker can substitute one asset for another. The closest structural analog in Desktop is the `allowFileProtocol` flag threaded through `checkoutBranch()` / `checkoutCommit()` into `updateSubmodulesAfterOperation()`. This flag decides whether Desktop re-enables `protocol.file.allow=always` for the subsequent `git submodule update --init --recursive` call, but the actual submodule URLs that get "protected" or not are read from `.gitmodules` — content that is part of the checked-out tree and therefore fully attacker-controlled once a malicious branch/commit/fork is checked out. Nothing in this path validates that the submodule URLs are legitimate remote URLs rather than `file://` paths pointing at the local filesystem.

### Finding Description
`checkoutBranch()` and `checkoutCommit()` accept an `allowFileProtocol: boolean` parameter and forward it unchanged to `updateSubmodulesAfterOperation()`: [1](#0-0) 

`updateSubmodulesAfterOperation()` turns that flag directly into a Git config override that re-enables the `file://` transport for submodules, which upstream Git disabled by default (see CVE-2022-39253) precisely because a malicious `.gitmodules` can point a submodule at an arbitrary local path and have Git "clone" (copy) that local directory into the working tree: [2](#0-1) 

The decision of *whether* to allow `file://` is made by the caller based on some notion of the top-level repository/remote being trusted (e.g., that it's a GitHub-hosted repo), but the actual submodule URLs consumed by `git submodule update --init --recursive` come from `.gitmodules`, which is ordinary repository content — the same trust-boundary confusion as the Sherlock bug, where `params.isNativeToken` (a caller-supplied, unvalidated flag) determined which asset was transferred while `request.marginToken` (a separate, unchecked field) determined what got debited from the pool. Here, the flag that grants the dangerous capability (`allowFileProtocol`) is disconnected from the data that determines what that capability is used against (submodule URLs in `.gitmodules`), and there is no check that the submodule URLs are not `file://`.

### Impact Explanation
If Desktop checks out a branch/commit whose tree contains a `.gitmodules` entry such as `url = file:///Users/victim/.ssh` (or any other sensitive local path) while `allowFileProtocol` is true for that checkout, `git -c protocol.file.allow=always submodule update --init --recursive` will copy the contents of that local directory into the repository's working tree as a "submodule." This is a read of files outside the repository's intended scope, and because the copied files now live inside the working directory, a subsequent `git add`/commit/push by the unsuspecting user silently exfiltrates local secrets (SSH keys, other repositories, config files) to whatever remote the repository is pushed to — matching the "silent corruption of what the user commits or pushes" and "credential exfiltration" impact classes.

### Likelihood Explanation
Exploitability depends entirely on whether any caller of `checkoutBranch`/`checkoutCommit` ever passes `allowFileProtocol = true` for a checkout whose source tree is not fully trusted (e.g., checking out a pull-request branch from a fork, or a commit from a repository the user doesn't control). I was not able to fully trace, within the remaining tool budget, every call site that supplies `true` for this parameter versus relying on the default `false`, so I cannot confirm with certainty that an untrusted-tree code path currently sets this flag to `true`. This is the main open question that would need to be resolved (e.g., via `grep` for `allowFileProtocol: true` / `checkoutBranch(...,\s*true)` across the dispatcher/app-store) to fully confirm reachability.

### Recommendation
- Never pass `protocol.file.allow=always` based on a coarse "is this checkout trustworthy" heuristic; instead validate each submodule URL parsed from `.gitmodules` and reject/ignore `file://` (and other local-path) schemes regardless of the `allowFileProtocol` flag, unless the submodule was already present and initialized with that exact URL before the checkout.
- Treat `.gitmodules` content as untrusted input on every checkout, not just as a static feature flag, and surface a warning to the user before performing a submodule update that would touch local file-system paths.
- Ensure `allowFileProtocol` can only be `true` for repositories/paths the user has explicitly whitelisted (analogous to Git's own `safe.directory`), not implicitly derived from unrelated trust signals.

### Proof of Concept
1. Attacker crafts a repository (or a branch/PR in a repository the victim will check out) whose tree includes a `.gitmodules` file:
   ```
   [submodule "loot"]
       path = loot
       url = file:///Users/victim/.ssh
   ```
2. Victim opens/clones this repository in Desktop and checks out the malicious branch or commit via `checkoutBranch`/`checkoutCommit` on a code path where `allowFileProtocol` is `true`.
3. Desktop runs `git -c protocol.file.allow=always submodule update --init --recursive`, which copies `/Users/victim/.ssh` into `<repo>/loot`.
4. The victim's normal `git add -A && git commit && git push` workflow now includes the copied SSH keys/secrets, which are pushed to whatever remote the repository points to — completing the exfiltration without any unusual or unnatural user action beyond a normal checkout.

Note: reachability of step 2 (a real call site invoking these functions with `allowFileProtocol = true` on an untrusted tree) was not fully confirmed within the available search budget and should be verified against the dispatcher/app-store call sites before treating this as fully proven end-to-end.

  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,

          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
