## Title
Melting a Plot NFT while it holds unclaimed pool rewards permanently strands those rewards - (File: `chia/wallet/plotnft_wallet/plotnft_wallet.py`, `chia/pools/plotnft_drivers.py`)

### Summary
The Velocimeter bug is: rewards are only claimable while the identity token (`veNFT`) exists; `merge()` burns the token before rewards can be swept, and burned tokens can never claim again, so at least one epoch of rewards is permanently lost. The `PlotNFT2Wallet` / `PlotNFT` singleton has a structurally similar dependency: pool-farmed rewards live in separate p2-singleton coins whose puzzle hash is derived from the Plot NFT's `singleton_id`/`launcher_id`, and claiming them requires producing a spend of the *live* Plot NFT singleton that emits a `SEND_MESSAGE` authorizing each reward coin's spend (`chia/pools/claim_pool_rewards_dpuz.clsp` / `PlotNFT.claim_pool_rewards()` in `chia/pools/plotnft_drivers.py:590-642`). If the singleton is melted via `plotnft_melt` (`PlotNFT2Wallet.melt_plotnft`, exposed through `wallet_rpc_api.py:3089-3101`, driven by `PlotNFT.melt()` in `plotnft_drivers.py:723-748`, which emits the `-113` melt condition and destroys the singleton), any pool rewards that have not yet been claimed become permanently unclaimable, because there is no remaining live singleton coin able to produce the required `SEND_MESSAGE` authorization.

### Finding Description
`PlotNFT.claim_pool_rewards()` builds a `SEND_MESSAGE` condition per reward coin from the *currently existing* Plot NFT singleton coin, and the reward coin's own puzzle (`claim_pool_rewards_dpuz.clsp`) requires receiving that exact message, keyed to `SINGLETON_STRUCT_HASH`/`singleton_id`, in order to release the reward amount: [1](#0-0) [2](#0-1) 

`PlotNFT.melt()` produces a spend that runs the `-113` melt condition on the singleton, permanently destroying it (no successor singleton coin is created): [3](#0-2) 

This is exposed at the wallet/RPC layer via `PlotNFT2Wallet.melt_plotnft` and `WalletRpcApi.plotnft_melt`: [4](#0-3) 

Neither `melt_plotnft` (via `plotnft_wallet.py`) nor the `plotnft_melt` RPC handler checks whether there are still unclaimed pool rewards (`plotnft2_store.get_pool_rewards`) tracked for the Plot NFT before allowing the melt to proceed, unlike `claim_rewards`, which explicitly checks `pooling` state and raises "Cannot claim rewards while pooling": [5](#0-4) 

Once the singleton coin is spent with the melt condition, no future spend of that singleton can exist to produce the `SEND_MESSAGE` needed by `claim_pool_rewards_dpuz.clsp`. Any reward coin(s) sitting at the `RewardPuzzle` puzzle hash (`self.reward_puzhash()` derived from `singleton_id`) that had not yet been swept by `claim_rewards`/`claim_pool_rewards` become permanently stuck — structurally identical to the Velocimeter bug where `_burn(_from)` makes the `veNFT`'s locked-but-uncollected rewards forever unclaimable because `RewardsDistributor.claim` requires ownership of a token that no longer exists.

### Impact Explanation
This is a direct, spend-triggered loss of funds path reachable by a normal Plot NFT owner (unprivileged wallet action), analogous to the accepted High-severity Sherlock finding: an ordinary user action (melt) destroys the sole identity/authorization mechanism needed to later collect already-farmed-but-unclaimed pool rewards, permanently orphaning those coins (they remain spendable only by a puzzle that can never again be satisfied). This qualifies as concrete "unsigned or unauthorized coin movement"/loss of funds under the validation criteria, since the reward coins become permanently unspendable rather than merely delayed.

### Likelihood Explanation
Likelihood depends on user behavior: a user (or a wallet UI/CLI flow) that calls `plotnft_melt` without first calling `claim_rewards` while pooling rewards are still pending will trigger the loss. Given that `claim_rewards` explicitly forbids claiming while pooling ("Cannot claim rewards while pooling. If you're a pool, try `forward_pool_rewards`") and `melt_plotnft` performs no equivalent "pending rewards" guard, this is easy to hit accidentally, particularly right after leaving a pool / before the final forwarded reward is swept, or if a user melts immediately after self-pooling receives a reward but before claiming.

### Recommendation
Before allowing `melt_plotnft` (and any other Plot NFT state transition that changes/loses the singleton identity in a way that could break the `SEND_MESSAGE` authorization path), check `plotnft2_store.get_pool_rewards(plotnft_id=...)` and reject the melt (raising a `ValueError` similar to the "Cannot claim rewards while pooling" and "No rewards to claim" guards already present in `claim_rewards`) if there are unclaimed pool rewards outstanding, forcing the user to claim first.

### Proof of Concept
Conceptual PoC (not executed, based on code inspection):
1. Create a Plot NFT via `PlotNFT2Wallet` and let it self-pool or pool, accumulating reward coins at `plotnft.reward_puzhash()` (see `chia/_tests/wallet/plotnft_wallet/test_plotnft_wallet.py:206-287`, "RECEIVE REWARDS").
2. Do not call `claim_rewards`/`claim_pool_rewards`.
3. Call `melt_plotnft` (`PlotNFT2Wallet.melt_plotnft` → `PlotNFT.melt()` in `plotnft_drivers.py:723-748`), which spends the singleton with the `-113` melt condition and no successor coin.
4. Attempt to claim the previously-farmed reward coins via `claim_pool_rewards()` — this requires spending the Plot NFT singleton (now destroyed) to emit the required `SEND_MESSAGE`; no such spend can ever be produced again, so the reward coin(s) remain permanently unclaimable. [6](#0-5) [4](#0-3)

    async def claim_rewards(
        self,
        *,
        action_scope: WalletActionScope,
        fee: uint64 = uint64(0),
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> None:
        rewards_to_claim = await self.wallet_state_manager.plotnft2_store.get_pool_rewards(plotnft_id=self.plotnft_id)
        if len(rewards_to_claim) == 0:
            raise ValueError("No rewards to claim")
        total_reward_amount = uint64(sum(reward.coin.amount for reward in rewards_to_claim))
        if fee > total_reward_amount:
            raise ValueError("Fee is greater than the total amount of rewards")
